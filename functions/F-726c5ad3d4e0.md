# F-726c5ad3d4e0

## Purpose

F-726c5ad3d4e0 modifies links among existing records. Under a conventional binary-tree interpretation, it performs a **right rotation**: the pivot’s left child replaces the pivot in its incoming link, and the pivot becomes that promoted record’s right child.

The rotation interpretation is inferred from the resulting link topology. The established behavior is a fixed sequence of four-byte field accesses, comparisons, and writes. The function does not validate that the records form a tree, that parent and child links agree, or that required addresses are accessible.

There is no returned result. Successful execution is observable through modified memory.

## Interface

### Inputs and representation

The function receives two 32-bit address-bearing arguments:

- **Context address:** identifies storage containing a header-like address at byte offset `+16`.
- **Pivot address:** identifies the record whose field at byte offset `+8` supplies the address of the record to promote.

All accessed link fields are four bytes wide. This contract describes that representation, not native-width pointers on an arbitrary host. Adapting the operation to a wider address space requires an explicit representation decision.

Offsets are measured in bytes. No ordering comparison, multiplication, or variable index calculation occurs. Address calculations add fixed offsets to address-bearing values. Behavior when those calculations exceed the valid address range is not established.

### Accessed layout

| Record role | Byte offset | Width | Interpretation |
|---|---:|---:|---|
| Context | `+16` | 4 bytes | Address of a header-like record |
| Header-like record | `+4` | 4 bytes | Distinguished incoming-link slot |
| Pivot or linked record | `+4` | 4 bytes | Parent-like link |
| Pivot or linked record | `+8` | 4 bytes | Left-child-like link |
| Pivot or linked record | `+12` | 4 bytes | Right-child-like link |

“Parent,” “left,” “right,” and “root” are structural interpretations, not independently established type information.

The function does not explicitly access offset `+0`, keys, payloads, counts, balancing metadata, or allocation metadata. Their locations and existence are unknown.

### Output and ownership

The function returns no value, success flag, or error code.

It makes no calls and performs no explicit allocation or release. It rewrites links between supplied records; no ownership transfer or lifetime change is explicitly represented. Storage must remain accessible for the accesses actually performed.

### Preconditions for ordinary rotation behavior

The conventional final topology requires:

- Accessible context and pivot fields.
- A valid promoted-record address in the pivot’s initial `+8` field.
- A promoted-record `+12` field containing either zero or an address with a writable `+4` field.
- An accessible header-like address in context `+16`, with a readable `+4` field and a writable one when the distinguished-slot branch is taken.
- On the non-root branch, a valid parent-like address in pivot `+4`, with the child fields required by that branch.
- Participating field storage that does not overlap in ways that change later reads or overwrite unrelated links.
- Stable storage during execution if ordinary tree-rotation results are required.

These are caller obligations, not checks performed by the function. In particular, a missing promoted record is not treated as an empty rotation.

## Behavior

### Record roles and retained values

The **pivot** is identified by the second argument.

The **promoted record** is identified by the four-byte value initially read from pivot `+8`. That address is retained throughout the operation; subsequent changes to pivot `+8` do not change which record is promoted.

The **transferred subtree** is the record identified by promoted-record `+12`, when the relevant read is nonzero. That field is read repeatedly rather than captured once for all uses.

The **distinguished slot** is the field at offset `+4` in the record addressed by context `+16`. Its address is calculated after the initial link updates and retained for the comparison and possible replacement.

On the non-root branch, a parent address is read from pivot `+4` and retained for that branch’s child-field comparison and write. Under stable, non-overlapping inputs, this is the pivot’s original parent.

### Ordered memory behavior

The following stages describe the order established by the supplied body. They do not establish a machine-instruction schedule, atomicity, or a complete ordering among operand evaluations within a single assignment.

1. **Identify the promoted record.**  
   Read pivot `+8` and retain the resulting four-byte address-bearing value.

2. **Replace the pivot’s left-like link.**  
   Read promoted-record `+12` and write that value to pivot `+8`.

3. **Conditionally update a transferred record’s parent.**  
   Read promoted-record `+12` again and compare the result with zero.

   If it is zero, skip the transferred-record parent update.

   If it is nonzero, read promoted-record `+12` once more to obtain a destination address, then write the pivot address to destination `+4`.

   The value copied into pivot `+8`, the value checked against zero, and the value used as the destination address therefore come from distinct reads. Without stable storage, they need not agree. A nonzero condition read does not guarantee that the subsequent destination read is nonzero.

4. **Assign the promoted record’s parent-like link.**  
   Read pivot `+4` and copy its four-byte value to promoted-record `+4`.

5. **Locate and compare the distinguished slot.**  
   Read context `+16`, add the `+4` field offset, and retain the resulting slot address. Read that slot and compare its contents with the pivot address.

   This comparison observes memory after the preceding writes, not a snapshot taken at entry.

6. **Replace one incoming link.**
   - If the distinguished slot equals the pivot address, write the promoted-record address to that retained slot address.
   - Otherwise, read pivot `+4` and retain the resulting parent-like address. Read that parent’s `+12` field and compare it with the pivot address.
     - If equal, write the promoted-record address to the retained parent’s `+12` field.
     - If unequal, write the promoted-record address to the retained parent’s `+8` field.

   The last alternative does not read or validate the parent’s `+8` field before overwriting it.

7. **Attach the pivot below the promoted record.**  
   Write the pivot address to promoted-record `+12`.

8. **Update the pivot’s parent-like link.**  
   Write the promoted-record address to pivot `+4`.

Normal return follows if all required accesses complete.

### Conditional structure

There are **three conditional decision points** in the body:

1. Whether the promoted record’s `+12` field is nonzero.
2. Whether the distinguished slot equals the pivot address.
3. Whether the selected parent’s `+12` field equals the pivot address.

The third condition is evaluated only when the distinguished-slot comparison is unequal. There are no loops.

The first condition controls only the transferred-record parent write. It does not determine whether the remaining rotation updates occur.

### Conventional final topology

For valid, stable, non-overlapping records, successful completion establishes:

- Pivot `+8` contains the promoted record’s initial right-child-like link.
- If that link is nonzero, the transferred record’s `+4` field contains the pivot address.
- Promoted-record `+4` contains the pivot’s original parent-like value.
- The selected incoming link contains the promoted-record address.
- Promoted-record `+12` contains the pivot address.
- Pivot `+4` contains the promoted-record address.

The selected incoming link is the distinguished slot when it initially compares equal to the pivot at the relevant stage. Otherwise it is the retained parent’s right-like field if that field equals the pivot, or its left-like field if the right-like comparison fails.

The promoted record’s left-like field and the pivot’s right-like field are not explicit write targets. Their preservation requires that they do not alias another write target.

No deeper subtree traversal occurs.

### Inconsistent links and aliasing

Distinguished-slot equality takes precedence over inspecting parent-child links. On that branch, the function does not inspect the parent-like record’s child fields.

On the non-root branch, the right-like child field takes precedence. If both child fields contain the pivot address, only the right-like field is replaced.

If neither child field contains the pivot address, the left-like field is still overwritten. There is no inconsistency report or repair of other links.

Aliasing can change subsequent reads. For example, a write to a field overlapping context `+16`, pivot `+4`, or promoted-record `+12` can affect a later destination or branch. Such inputs are governed by the ordered accesses, not by the conventional final-topology description.

## Side effects

The function performs five explicit four-byte writes when the transferred-record parent update is skipped, and six when that update is taken:

| Order | Target | Written value |
|---:|---|---|
| 1 | Pivot `+8` | Value read from promoted-record `+12` |
| 2, conditional | Address obtained by rereading promoted-record `+12`, then offset `+4` | Pivot address |
| 3 | Promoted-record `+4` | Value read from pivot `+4` |
| 4 | Distinguished slot or selected parent child field | Promoted-record address |
| 5 | Promoted-record `+12` | Pivot address |
| 6 | Pivot `+4` | Promoted-record address |

These counts describe explicit writes in a completed execution, including assignments whose value matches existing contents. They do not imply that the targets are distinct under aliasing.

Context `+16` is explicitly read, not explicitly written. The header-like record’s distinguished slot is explicitly written only when its comparison succeeds. Aliasing can cause other writes to affect either location.

There are no explicit global accesses, dependency calls, allocation or release operations, I/O operations, or synchronization operations.

The update is not transactional. Earlier writes precede later potentially invalid accesses, and there is no rollback or recovery path in the body. A failure may therefore leave partially changed links. Exact fault behavior and the visibility of partial changes depend on the execution environment.

The function provides no guarantee of a coherent intermediate graph for concurrent observers.

## Acceptance examples

These are conditional predictions from static evidence, not executed tests. Unless an example states otherwise, assume valid, stable, non-overlapping storage.

### Distinguished-slot pivot with a nonempty transferred subtree

Initially, the distinguished slot identifies the pivot; pivot `+8` identifies the promoted record; and promoted-record `+12` identifies a nonzero subtree record.

Expected completion:

- The distinguished slot identifies the promoted record.
- Pivot `+8` identifies the subtree.
- Subtree `+4` identifies the pivot.
- Promoted-record `+4` receives the pivot’s original parent-like value.
- Promoted-record `+12` identifies the pivot.
- Pivot `+4` identifies the promoted record.

The parent’s child fields are not inspected. Six four-byte writes occur.

### Non-root pivot in its parent’s right-like field

The distinguished slot differs from the pivot, and the parent selected from pivot `+4` has the pivot in its `+12` field.

That parent’s `+12` field becomes the promoted-record address. Its `+8` field is not explicitly written. The other rotation updates still occur.

### Non-root pivot in its parent’s left-like field

The distinguished slot differs from the pivot, the selected parent’s `+12` field differs from the pivot, and its `+8` field identifies the pivot.

The selected parent’s `+8` field becomes the promoted-record address. The function does not read that field to confirm the relationship before writing it.

### Empty transferred subtree

If promoted-record `+12` remains zero during the relevant reads:

- Pivot `+8` becomes zero.
- No transferred-record parent write occurs.
- The incoming-link replacement and final parent-child updates still occur.
- Five four-byte writes occur.

The promoted record itself must still be accessible.

### Both parent child fields identify the pivot

If the distinguished slot differs from the pivot and both child fields of the selected parent identify it, only the parent’s `+12` field is replaced. The `+8` field continues to identify the pivot.

This demonstrates right-like-field precedence, not topology validation.

### Neither parent child field identifies the pivot

If the distinguished slot differs from the pivot and neither selected-parent child field identifies it, the parent’s `+8` field is nevertheless overwritten with the promoted-record address.

No error is returned, and no broader consistency repair occurs.

### Missing promoted record

If pivot `+8` initially contains zero, the operation still attempts the promoted-record `+12` read using that value as the base. There is no early return or empty-child error path.

Whether that access faults or has some other effect is environment-dependent. A successful rotation is not required for this invalid ordinary-tree input.
