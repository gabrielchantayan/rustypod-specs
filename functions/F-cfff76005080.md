# F-cfff76005080

## Purpose

The supplied static representation describes a procedure that interleaves indirect calls with writes to computed memory addresses, then enters an unconditional repeating sequence.

Its application-level purpose is unknown. The evidence does not establish that the addressed memory represents ordinary objects, device registers, a table, or an encoded execution environment. Names such as “initialize,” “allocate,” or “release” would introduce unsupported semantics.

The contract below describes the visible operations conditionally: execution must reach each operation, preceding calls must return, and required memory accesses must succeed. The supplied representation includes warnings about invalid instruction data and removed unreachable regions. Consequently, this is a contract for the represented path, not proof that the underlying executable has exactly this behavior.

### Arithmetic notation

The following expressions describe represented address calculations:

## Behavior

### Indirect-call notation

Every unresolved indirect invocation is denoted **F-unknown**. This is an opaque placeholder, not a claim that different occurrences call the same function.

A **four-call result group** means exactly four successive F-unknown invocations with no explicit arguments shown. Only the fourth result is retained by the visible procedure. The other three calls still occur and can have observable effects.

“No explicit arguments shown” does not establish that the target has a zero-argument interface. Hidden arguments, register state, and actual calling conventions remain unknown.

### 1. Initial first-input writes

The first visible operation is a four-byte write:

- Destination: four times **first**, plus `0x14`.
- Value: **first**.

There is no visible validation before this write.

The following operations then occur in order:

1. Invoke F-unknown with **first**.
2. Invoke F-unknown without explicit arguments; pass its result to the next F-unknown invocation.
3. Invoke F-unknown without explicit arguments again; pass that result to another F-unknown invocation.
4. Execute a four-call result group. Call its retained result **first index**.
5. Write **first**, as four bytes, at four times **first index**, plus `0x14`.
6. Invoke F-unknown with four times **first index**.
7. Execute another four-call result group. Call its retained result **table index**.
8. Write four times **table index**, as four bytes, at sixteen times **table index**, plus `0x14`.

Retain the four-scaled **table index** for a later lookup calculation. The value is not reloaded from the just-written memory.

### 2. Fourth-input write and retained base

Next:

1. Invoke F-unknown with the retained four-scaled **table index**.
2. Invoke F-unknown without explicit arguments; forward its result to the next F-unknown invocation.
3. Invoke F-unknown without explicit arguments again; forward its result to another F-unknown invocation.
4. Execute a four-call result group. Call the retained result **fourth-input index**.
5. Write **fourth**, as four bytes, at four times **fourth-input index**, plus `0x14`.
6. Invoke F-unknown with four times **fourth-input index**.
7. Execute another four-call result group. Call the retained result **base index**.
8. Retain sixteen times **base index** as **base**.
9. Write four times **base index**, as four bytes, at **base** plus `0x14`.

Also derive the retained **primary lookup position** by clearing bit 31 of the earlier four-scaled **table index**, then logically shifting right by seven.

This position uses the earlier retained arithmetic value. It does not read the stored table entry, and it does not use **base index**.

### 3. Base rewrite and first byte update

The next indirect invocation receives three explicit arguments, in order:

1. **base**;
2. **base** again;
3. **third**, logically shifted right by seven.

Then:

1. Execute a four-call result group.
2. Write **base**, as four bytes, at **base** plus `0x14`.
3. Invoke F-unknown with four times the group’s retained result.
4. Execute another four-call result group. Call its unsigned retained result **first packed result**.
5. Read one unsigned byte at **primary lookup position** plus one.
6. Write the low byte of four times **first packed result** to address `0x11` plus the byte just read.

The write in step 2 targets the same retained address used at the end of the preceding phase. Unknown intervening calls can modify that memory, but the later write does not recompute **base** from it.

### 4. Second byte update

Next:

1. Invoke F-unknown with three identical arguments, each four times **first packed result**.
2. Invoke F-unknown without explicit arguments.
3. Forward that result to the next F-unknown invocation.
4. Execute a four-call result group.
5. Reread the byte at **primary lookup position** plus one.
6. At address `0x11` plus this newly read byte, write the low eight bits of **first packed result** after masking with `0x3fffffff` and shifting right by twenty.
7. Invoke F-unknown with four times the group’s retained result.
8. Execute another four-call result group. Call its unsigned retained result **second packed result**.

The stored byte in step 6 corresponds to bits 20 through 27 of **first packed result**. Bits 28 and 29 survive the intermediate mask and shift but are discarded by the one-byte store.

The lookup byte is reread. The destination need not equal the destination of the previous byte write.

### 5. Fourth-input-derived byte write and primary lookup clears

Retain four times **second packed result** as **secondary scaled value**.

Then perform these operations in order:

1. Write the low byte of **secondary scaled value** at the address formed by logically shifting **fourth** right by seven and adding `0x1c`.
2. Read the byte at **primary lookup position** plus one.
3. Write zero to address `0x11` plus that byte.
4. Invoke F-unknown with **fourth** logically shifted right by seven.
5. Invoke F-unknown without explicit arguments.
6. Invoke F-unknown with **second packed result**, masked with `0x3fffffff`, then logically shifted right by six.
7. Execute a four-call result group.
8. Reread the byte at **primary lookup position** plus one.
9. Write zero to address `0x11` plus that newly read byte.
10. Invoke F-unknown with four times the group’s retained result.
11. Execute another four-call result group.

The clear in step 3 follows the fourth-input-derived byte store without an intervening call. Those accesses must not be collapsed: the earlier store can alias the lookup byte or its eventual destination.

The clear in step 9 is a separate read and write, with several calls intervening.

### 6. Transition to the repeating sequence

From the last group’s unsigned result, derive **initial loop field** by masking with `0x3fffffff` and logically shifting right by twenty-five.

Thus, **initial loop field** is between zero and 31 inclusive.

Next:

1. Read one byte at 1,024 times **secondary scaled value**, plus one.
2. Write zero to address `0x11` plus that byte.
3. Invoke F-unknown with twice **initial loop field**.
4. Invoke F-unknown without explicit arguments; retain its result as the initial **carried result**.

The argument in step 3 is between zero and 62 inclusive.

### 7. Unconditional repeating sequence

Each iteration performs the following observable sequence:

1. Invoke F-unknown with two arguments:
   - the current **carried result**;
   - the current **loop field**, logically shifted right by eight.
2. Execute a four-call result group.
3. Read one byte at 1,024 times the retained **secondary scaled value**, plus one.
4. Write zero to address `0x11` plus the byte just read.
5. Invoke F-unknown with four times the group’s retained result.
6. Execute another four-call result group.
7. Set the next **carried result** to four times the final retained result.
8. Set the next **loop field** to that same final result shifted left by twenty-six.
9. Repeat without a visible termination test.

The first iteration uses **initial loop field**, so its second argument in step 1 is necessarily zero.

Subsequent iterations use the newly shifted field. They do not reuse the initial five-bit extraction. Under a 32-bit wrapping interpretation, that later argument depends on the low six bits of the preceding final result; the signed-shift caveat still applies.

The indirect target for the first invocation of the first iteration differs in its represented derivation from the corresponding invocation on later iterations. Equal argument patterns do not establish a common callee.

## Side effects

No disjointness is established among any addresses. Writes may affect future lookup bytes, earlier stored values, or state used by dependencies.

## Acceptance examples

These examples are conditional static expectations, not executed tests.

### Initial address calculation

If **first** is 3, arithmetic is representable, and the initial address is writable:

- The first visible operation writes the four-byte value 3 at address `0x20`.
- The first indirect invocation follows that write and receives 3.

### Third-input shift boundary

If execution reaches the three-argument base call:

- A **third** value of 127 supplies zero as its third argument.
- A **third** value of 128 supplies one.
- A **third** value of `0xffffffff` supplies `0x01ffffff`.

The other two arguments remain the retained **base**.

### Low-byte truncation

If **first packed result** is `0x12345678`:

- Its first lookup-selected store writes `0xe0`.
- Its second lookup-selected store writes `0x23`.

These are not necessarily writes to the same address: the selector is read again after intervening calls.

### Lookup selector changes

If the primary lookup byte is 2 for one lookup write, that write targets `0x13`.

If a dependency changes the lookup byte to 255 before the next lookup read, the next lookup write targets `0x110`. Reusing the earlier destination would violate the represented access sequence.

### Fourth-input-derived store

If **fourth** is 128 and **second packed result** is 65:

- The direct byte-store address is `0x1d`.
- The stored byte is 4, from the low byte of 260.
- The subsequent primary lookup clear still performs its own selector read.

### First loop argument and repeated clears

If execution reaches the first loop iteration, its two-argument call receives zero as its second argument regardless of the initial five-bit field.

Each completed iteration performs another secondary lookup read and zero write. An implementation must not replace these with a one-time clear merely because the written value is always zero.
