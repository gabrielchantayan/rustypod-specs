# F-54931a77e61f

## Purpose

F-54931a77e61f writes a header, initializes two groups of 52-byte records, links the second group, invokes F-925c2124ca9b during and after initialization, and clears three control bytes after the final invocation returns.

The first group receives sequential identifiers and values from 16-byte descriptors. The second group receives identifiers derived from the primary count and a fixed classification value. These structural effects are established by the supplied representation. Their application-level purpose is unknown.

This contract distinguishes direct accesses from dependency effects and distinguishes retained pointers from fresh reads of shared pointer-bearing locations. It does not assume those values remain equal.

## Behavior

### 1. Establish header linkage and reset selected fields

The function first captures the header-control base, then the record-area base. It separately reads the header-control shared location to form an address four bytes beyond that base.

The first linkage store uses fresh reads of the shared header-control and record-area locations: it writes the latter record-area address at offset 4 of the former header-control address. The representation does not establish operand-read order within that store.

The remaining initialization proceeds in this order:

1. Write the separately formed header-control-plus-4 address to offset 4 of the captured record-area base.
2. Write 127 to header offset 36.
3. Write zero to header offset 32.
4. Write zero to header offset 0.
5. Write zero to header offset 28.
6. Write zero to header offset 48.
7. Capture the primary-count pointer.
8. Write a 32-bit zero at offset 8 of the initially captured header-control base.

If the shared locations remain stable, these stores form cross-references between the record header and header-control offset 4. If they change between reads, the linkage need not connect the captured bases.

### 2. Evaluate and populate the primary group

The primary identifier starts at 1. **Every condition evaluation**, including the terminating evaluation, performs these reads in order:

1. Refresh the aggregate-control pointer.
2. Refresh the secondary-count pointer.
3. Refresh the descriptor-table base.
4. Dereference the captured primary-count pointer and perform a signed comparison.

An iteration executes when the identifier is less than or equal to that primary count. Zero and negative primary counts therefore skip the body, but do not skip the three pointer refreshes.

For primary identifier *i*, the destination is at record-area offset 52 × *i*, and the descriptor begins at the iteration’s retained descriptor-table base plus 16 × *i*.

The observable record and descriptor accesses occur in this order:

1. Store *i* at record offset 32.
2. Store zero at record offset 8.
3. Store 256 at record offset 28.
4. Read descriptor offset 12 and store that word at record offset 36.
5. Store zero at record offset 48.
6. Clear byte 40.
7. Clear byte 41.
8. Read descriptor offset 4 and store that word at record offset 20.
9. Read descriptor offset 8 and store that word at record offset 24.
10. Invoke F-925c2124ca9b.
11. Read descriptor offset 0 and store that word at record offset 12.
12. Store zero at record offset 44.
13. Advance the record cursor by 52 bytes and increment the identifier.

The dependency invocation occurs before this iteration’s assignments to offsets 12 and 44. If the dependency can access the destination, it can observe that intermediate state.

The post-call descriptor read uses the descriptor-table base retained for the iteration, not a freshly read shared base. Changing the shared descriptor pointer alone does not redirect that read. Changing the selected descriptor’s contents can affect it.

The primary count is reread at each condition. Dependency changes to that pointed-to count can shorten or extend the loop. Changing only its shared pointer-bearing location does not replace the captured primary-count pointer.

### 3. Store a combined count through freshly obtained pointers

After primary-loop termination, the function stores a 32-bit sum at offset 4 of a **freshly read aggregate-control base**. The sum uses:

- A read through the captured primary-count pointer.
- A read through a **freshly obtained secondary-count pointer**.

These reads do not replace the retained aggregate-control or secondary-count pointers from the terminating condition.

Consequently, the combined-count store can target a different control area from the subsequent chain-head accesses. Its secondary operand can also come from different count storage than that used for chain construction.

The representation does not establish the relative read order among operands within this store expression.

### 4. Select and populate the secondary chain

The function reads the count through the **retained secondary-count pointer**.

- If that count is exactly zero, it stores a null pointer at offset 16 of the **retained aggregate-control area**.
- Otherwise, it rereads the primary count and stores the address at record-area offset 52 × (primary count + 1) there.

It then reads the head pointer back from that same retained aggregate-control area.

The secondary identifier starts at 1. Each condition rereads the retained secondary count and compares it with the identifier using a signed comparison. For each reached record, the accesses occur in this order:

1. Store 256 at offset 28.
2. Store the address 52 bytes beyond the current record at offset 0.
3. Read the primary count through its captured pointer.
4. Store 126 at offset 36.
5. Store zero at offset 8.
6. Store the previously read primary count plus the secondary identifier at offset 32.
7. Clear byte 40.
8. Clear byte 41.
9. Store zero at offset 44.
10. Advance the cursor by 52 bytes and increment the secondary identifier.

The primary count used in each identifier is not necessarily the one used to select the head or publish the combined count.

After loop termination, the function rereads the retained secondary count. If it is nonzero, it clears the link at the address 52 bytes before the advanced cursor.

For a stable positive count, this clears the last initialized record’s link. Until then, that link points one record beyond the populated group.

A stable negative count selects a non-null head, executes no secondary iterations, and still clears the predecessor’s link. Negative counts are therefore not equivalent to empty groups.

If the retained count changes between head selection, loop evaluations, and the final nonzero check, those decisions can disagree. The function does not reconcile them.

### 5. Invoke the final dependency and clear control bytes

The final invocation of F-925c2124ca9b has this displayed argument sequence:

1. The final-call value.
2. 512.
3. 126.
4. The **retained secondary-count pointer**, not its pointed-to count.

If the invocation returns normally, the function performs these 8-bit stores in order:

1. Clear byte 0 of the retained aggregate-control area.
2. Clear byte 1 of that same area.
3. Clear byte 0 of the initially captured header-control area.

The aggregate-control pointer used here is not refreshed from the shared location used by the combined-count store.
