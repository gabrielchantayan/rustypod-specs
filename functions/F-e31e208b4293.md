# F-e31e208b4293

## Purpose

F-e31e208b4293 conditionally updates a four-byte table entry and fields within a supplied record. Under ordinary non-overlapping conditions, its effect is consistent with inserting the record at the front of a doubly linked chain.

The established behavior is a sequence of guarded memory accesses. The chain interpretation is inferred intent, not an independently established data-model guarantee.

The function proceeds only when:

- Subtracting one from the record’s 32-bit selector produces a value whose signed 32-bit interpretation is nonnegative.
- Bit 0 of the record’s status byte is clear.

Otherwise, it returns without writing memory. It provides no explicit result indicating whether insertion occurred.

No overlap checks are present. Consequently, table accesses and the final indirect write may affect the supplied record itself, including bytes outside the fields explicitly addressed relative to that record.

### Fixed record-relative fields

Offsets below are byte offsets from the supplied record address.

| Offset | Width | Established use |
|---|---:|---|
| +8 | 4 bytes | Selector, read before other memory accesses. |
| +12 | 4 bytes | Cleared when insertion proceeds. |
| +16 | 4 bytes | Receives the selected table entry, then is reread for the final conditional update. |
| +20 | 1 byte | Status byte; bit 0 gates insertion and is set during insertion. |

The fixed record-relative accesses do not address offsets +0 through +7. This is **not** a guarantee that those bytes remain unread or unchanged: a selected table entry or the destination of the final indirect write can alias them.

For example, when the table base equals the record address and the selector is 1, the selected table entry is at record offset +0. An eligible call then reads and writes that location.

The apparent meanings of +12 and +16 as reverse and forward links are inferred. No semantic meaning is established for other record bytes.

### Selector and address arithmetic

For a selector bit pattern \(s\), define the derived 32-bit index as:

\[
i = (s - 1) \bmod 2^{32}.
\]

The signed eligibility check examines this derived index, not the selector directly.

When insertion proceeds, the selected entry is located at the table base plus four times the index. Under the represented 32-bit address-arithmetic model, multiplication and address addition retain their low 32 bits.

No capacity check accompanies this calculation. A value accepted by the signed guard need not identify an entry within any actual table.

These bit-pattern rules describe the supplied representation. They do not establish portable signed-overflow behavior for an arbitrary implementation language or guarantee that a wrapped address is valid.

## Behavior

### Eligibility evaluation

The first memory access reads the four-byte selector at record offset +8. The function derives the index by subtracting one.

If the index’s signed 32-bit interpretation is negative, the function returns:

- The status byte is not read.
- No table entry is read.
- No memory is written.

Otherwise, the function reads the status byte at +20 and tests bit 0:

- If bit 0 is set, the function returns without further memory accesses.
- If bit 0 is clear, insertion proceeds.

The selector bit patterns reaching the status-byte test are `0x00000001` through `0x80000000`, inclusive.

In particular:

- Selector zero produces index `0xFFFFFFFF` and is rejected before the status read.
- Selector `0x80000000` produces index `0x7FFFFFFF` and reaches the status test.
- Selectors `0x80000001` through `0xFFFFFFFF` produce signed-negative indices and are rejected before the status read.

Bits 1 through 7 of the status byte do not affect eligibility.

### Ordered insertion accesses

After eligibility succeeds, the supplied representation establishes this order:

1. Write four zero bytes to record offset +12.
2. Read the selected four-byte table entry.
3. Write that entry value to record offset +16.
4. Write the supplied record address into the selected table entry.
5. Read the status byte at +20 again, set bit 0, and write the resulting byte back.
6. Read the four-byte field at record offset +16 and test whether it is nonzero.
7. If that test succeeds, read the +16 field again as an address and write the supplied record address into the four-byte location 12 bytes beyond that address.
8. Return.

The status update uses a fresh read after the table write. It preserves bits 1 through 7 of that later byte, which need not match the byte used for eligibility if intervening writes alias the status location.

Likewise, the final indirect update does not unconditionally use a retained copy of the original table entry. It uses the +16 field as reread after the status update.

The source expresses separate +16 reads for the nonzero test and the eventual destination address. With stable ordinary memory, they observe the same value. If the value changes between those reads, there is no second nonzero check on the address used for the final write.

These are source-level access relationships. They do not establish atomicity, synchronization, machine-instruction ordering, or volatile-access semantics.

### Ordinary non-overlapping result

When all reached locations are valid, the selected entry and affected record fields do not overlap, and no concurrent modification occurs:

- Record +12 becomes zero.
- Record +16 becomes the former selected table entry.
- The selected table entry becomes the supplied record address.
- Status bit 0 becomes one.
- Other status bits remain unchanged.
- If the former table entry was nonzero, the four-byte field at that address plus 12 becomes the supplied record address.
- If the former entry was zero, no final indirect write occurs.

Under these conditions, the operation has the apparent effect of prepending the record to a chain.

The previous contents of the supplied record’s +12 and +16 fields do not determine eligibility. They are overwritten during insertion.

### Aliasing and inconsistent state

The ordinary final-state description is conditional. No check prevents overlap among the table, supplied record, and final indirect destination.

Established consequences include:

- If the selected table entry is record +12, the clear occurs before the table read. The entry read therefore obtains zero rather than its pre-call contents.
- If the selected table entry is record +16, the table write replaces that field with the supplied record address. The later nonzero test and indirect update use the changed value.
- If the table entry overlaps the status byte, the subsequent status read observes the preceding write’s effect. The exact byte value depends on layout and endianness.
- If the selected entry lies at record +0 or +4, those bytes are read and written even though they are not among the fixed record-relative fields.
- If the final indirect destination lies within record offsets +0 through +7, the function writes there. No exclusion protects those bytes.

There is also no check that the supplied record is absent from the selected chain. If the selected entry already equals the supplied record address while status bit 0 is clear, ordinary otherwise-distinct accesses produce a self-reference at +16. The final indirect write then replaces the earlier zero at +12 with the record’s own address.

The function neither detects nor repairs that condition.

## Side effects

### Writes

A rejected call performs no writes.

An eligible call performs:

- A four-byte zero write at record +12.
- A four-byte write at record +16.
- A four-byte write to the selected table entry.
- A one-byte status update at record +20.
- A conditional four-byte indirect write, when the final +16 nonzero test succeeds.

These operations need not target distinct locations. The final indirect write can also overwrite a location modified earlier.

No explicit logging, callback, allocation, release, synchronization operation, or external-function call appears.

## Acceptance examples

These are conditional criteria derived from static evidence, not executed tests. Unless an example explicitly introduces overlap, assume valid reached locations, no relevant overlap, and no concurrent mutation.

### Empty selected chain

Given selector 1, first table entry zero, and status byte `0xA4`:

- The first table entry becomes the supplied record address.
- Record +12 and +16 become zero.
- The status byte becomes `0xA5`.
- No final indirect write occurs.

### Nonempty selected chain

Given selector 3, status bit 0 clear, and a valid nonzero address in the third table entry:

- The third entry becomes the supplied record address.
- Record +12 becomes zero.
- Record +16 becomes the former third-entry value.
- The former head’s +12 field becomes the supplied record address.
- Status bit 0 becomes one, with the other status bits preserved.

### Status-based rejection

Given selector 1 and status byte `0x81`:

- The selector and status byte are read.
- No table entry is read.
- No memory is written.

This does not verify whether the record actually belongs to any chain.

### Zero selector

Given selector zero:

- The derived index is `0xFFFFFFFF`.
- The function returns before reading the status byte.
- No table or link access occurs.
- No memory is written.

### High-bit boundary

Given selector `0x80000000` and status bit 0 clear:

- The index is `0x7FFFFFFF`.
- Insertion is attempted rather than rejected by the signed guard.
- Under 32-bit wrapping arithmetic, the table displacement is `0xFFFFFFFC`.

Completion still requires the resulting locations to be valid.

Given selector `0x80000001`, the index is `0x80000000`; the function returns before reading the status byte.

### Table entry at record offset +0

Given table base equal to the record address, selector 1, status byte `0xA4`, and an initial four-byte zero value at record +0:

- The selected table entry is record +0.
- The function reads zero from that location after clearing record +12.
- Record +16 becomes zero.
- Record +0 is overwritten with the supplied record address.
- The status byte becomes `0xA5`.
- No final indirect write occurs.

This demonstrates that excluding +0 through +7 from the fixed record-relative access list does not exclude those bytes from actual accesses.

### Final indirect write at record offset +0

Given selector 1, status bit 0 clear, and a distinct selected table entry containing the nonzero address 12 bytes before the supplied record:

- Record +16 receives that address.
- The selected table entry becomes the supplied record address.
- The final indirect write targets record +0 and stores the supplied record address there.

This example assumes all reached addresses are valid and no other overlap changes the sequence.

### Repeated call

After an ordinary successful insertion, a second call with unchanged selector and status:

- Reads the selector and status.
- Finds status bit 0 set.
- Performs no writes.

### Record already selected

Given status bit 0 clear and the selected entry already equal to the supplied record address:

- Record +16 becomes its own address.
- The final indirect write makes record +12 equal its own address.
- Status bit 0 becomes one.

This is an observed consequence of the access sequence, not evidence that self-linking is intended.
