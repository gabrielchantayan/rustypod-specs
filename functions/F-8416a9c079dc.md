# F-8416a9c079dc

## Purpose

F-8416a9c079dc requests a 384-byte context, resolves a selected backend, installs comparison-related entries, and conditionally attempts to open a resource. It publishes a context address through a caller-provided output slot and returns the low eight bits of a final status.

The initialization/open interpretation is inferred from the visible operations and symbol labels. Those labels do not establish the complete semantics of the resource, backend, or comparison operations.

Failure does not uniformly produce a null output. The routine explicitly replaces the context address with zero only when allocation returned zero or the **full final status equals 7**. Other final statuses can accompany a nonnull, partially initialized context.

There is no explicit output-slot validation or early output initialization. For normal completion, the output address must permit the final 32-bit write. If it aliases other storage, that write can alter the aliased storage; the routine provides no alias isolation.

### Result

The return value is the full final status masked with `0xff`, yielding a value from 0 through 255.

The cleanup decision precedes this masking and compares the entire 32-bit status against 7. Thus, `0x00000107` returns 7 without taking the explicit cleanup branch.

## Behavior

### Allocation and initialization

The first dependency call is F-1c177d5ba9f6 with a size argument of `0x180`, or 384 bytes.

A zero result bypasses context initialization, backend resolution, registration, and opening. The routine still reaches final status handling with a null context. Allocation failure alone does not establish the returned status.

For a nonzero result, the initial direct writes are ordered: 8 at `0x4c`, `0x000000ff` at `0x18`, and zero at `0x38`. The routine then reads an external initial-state word. After that read, it writes zero at `0x3c`, 2 at `0x04`, and the captured word at `0x40`.

The embedded-area pointer at `0x08` is set to context base plus `0x14c`. An unidentified transfer dependency then receives destination context base plus `0x50`, an externally supplied source value, and length `0x28`. The call establishes these arguments, not the helper’s exact copying or failure semantics.

After that call, direct initialization writes byte 1 at `0x1c`, byte `0xff` at `0x21`, and word zero at `0x24`. The word at `0x0c` is then read, ORed with `0x8040`, and written back. Other bits in the value read are preserved; the routine does not first clear that word.

F-c247d7bfe027 is subsequently called on context subareas `0x114`, `0x128`, and `0xf4`, in that order. Each call also receives 3 and zero.

These ordering constraints matter if dependency effects or overlapping storage influence later reads.

### Backend resolution

F-2e88c9fc2422 receives the backend selector. On its return, the routine reads a second external state word and retains it for later failure-path use. Only after that read does it store the backend-resolution result at context offset `0x00`.

If resolution returns zero, the retained state word is written at `0x40`. F-a061acf353ed then receives:

- The context.
- Status argument 1.
- A diagnostic pointer formed by advancing **two bytes from the start of a named static symbol**.
- The backend selector.

The underlying diagnostic bytes are not supplied. The symbol name suggests the interpretation “no such vfs: %s”, but that text is **inferred, not an established literal format**. The established argument is the symbol-relative pointer.

This branch performs no named registrations or open attempt. Completion still obtains its status from F-0b90d48d906b rather than returning the diagnostic argument 1 directly.

### Initial registrations and first gate

With a nonzero backend result, four F-8685dec604a9 calls occur in this order:

| Entry label | Arguments following the name argument |
|---|---|
| `BINARY` | 1, 0, externally read callback value, 0 |
| `BINARY` | 3, 0, externally read callback value, 0 |
| `BINARY` | 2, 0, externally read callback value, 0 |
| `RTRIM` | 1, 1, externally read callback value, 0 |

Each call also receives the context first. These labels identify the supplied named symbols; their full byte contents and comparison semantics are not independently exposed.

The callback-value storage is read for each call. The routine does not capture one value for all four registrations, so an intervening dependency effect can change a later argument.

After all four calls, the byte at context offset `0x1e` is tested. If nonzero, lookup and opening are skipped, the state captured immediately after backend resolution is written at `0x40`, and final status handling follows.

The routine has not explicitly initialized this gate byte. Its readable value must come from allocation behavior, dependency effects, or an external invariant.

### Comparison-entry setup and open attempt

With the first gate clear, F-4a95613e1504 receives the context, 1, the `BINARY` name argument, 6, and zero.

The following order is established and must be preserved:

1. The lookup returns.
2. A separate external callback value is read and captured.
3. The lookup result is stored at context offset `0x2c`.
4. F-8685dec604a9 receives the context, the `NOCASE` name argument, 1, 0, the captured callback value, and 0.

In particular, the callback read occurs **before** the context store. This cannot be reordered on an unsupported assumption that the two storage locations do not alias. The registration uses the captured value even if the intervening store changes the external storage.

After registration returns, the pointer at context offset `0x2c` is read again, and byte 1 is written five bytes beyond that pointer. This is not necessarily the pointer originally returned by the lookup: the intervening registration may have changed the context field. There is no null check.

F-4a95613e1504 then receives the context, 1, the `NOCASE` name argument, 6, and zero. A nonzero result receives byte 2 at offset 5. A zero result suppresses only this marker write; it does not suppress opening.

The requested flags are processed as unsigned 32-bit values:

- Stored flags are the requested flags AND `0xffff80f7`.
- Open flags are the stored flags OR `0x00000100`.

The mask clears bit 3 and bits 8 through 14. All remaining bits are retained. Consequently, bit 8 is clear in the stored flags and set in the open flags.

After storing the masked flags at `0x10`, the routine invokes F-94e50f72111d with the context, resource argument, zero, 2000, open flags, and an address four bytes beyond the pointer read from context offset `0x08`.

The argument 2000 has no established unit or interpretation.

If the open result is nonzero, F-a061acf353ed receives the context, that result, and zero. After the call, the state captured after backend resolution is written at `0x40`, and final status handling follows. The open result does not directly determine the routine’s return.

### Successful-open record setup

A zero open result leads to record setup through the pointer field at `0x08`.

The first F-96819d3b47ed call receives the context and the 32-bit word four bytes beyond the current embedded-area pointer. Its result is written at embedded offset `0x14`, using the pointer field read after the call.

The second F-96819d3b47ed call receives the context and zero. Its result is written at embedded offset `0x2c`, again using the pointer field read after the call.

Thus, a dependency can change the destination base between the argument read and the result write. The routine does not guarantee that both operations concern the same embedded area.

Next, the following direct writes occur in order:

| Destination relative to the current embedded pointer | Value |
|---|---|
| `0x00` | Address of one external static object |
| `0x09` | Byte 3 |
| `0x18` | Address of a different external static object |
| `0x21` | Byte 1 |

The embedded-pointer field is read for the relevant accesses rather than being treated as permanently equal to its initial value. After these writes, another external state word is read and stored at context offset `0x40`.

If the embedded pointer remains context base plus `0x14c`, the highest visible record write occupies context offsets `0x178` through `0x17b`, within the 384-byte allocation. This bound does not establish safety if a dependency changes the pointer.

The gate byte at `0x1e` is then tested again. A nonzero byte bypasses the remaining success callbacks and proceeds to final status handling without restoring the earlier captured state.

With the second gate clear, the calls occur in this order:

1. F-a061acf353ed with context, zero, and zero.
2. F-48141463f6eb with context.
3. F-8444dd50b4c6 with context.
4. F-0b90d48d906b with context.

If this intermediate status is exactly zero, F-a061acf353ed is called again with only the context and zero as visible arguments. No third argument is established for that invocation.

All these paths subsequently perform a separate final status call.

### Final status and publication

F-0b90d48d906b receives the retained context address, including zero after allocation failure.

If its full 32-bit result equals 7, F-ff6d0e3505c3 receives the context. After that call returns, the routine replaces its retained context address with zero.

The routine then writes the retained address to the output slot and returns the final status masked with `0xff`. The status used for the return is the captured final result; the cleanup call does not trigger another status query.

## Side effects

Directly established effects comprise the allocation request, listed memory accesses, dependency invocations, and final output-slot write. Dependency-internal effects are not constrained by this function’s visible operations.

The routine’s explicit output publication occurs after final status evaluation and any status-7 cleanup call. Dependencies are not proven unable to access or alter the output location independently.

The unchecked first marker write requires the pointer read from `0x2c` to identify writable storage through offset 5. Other indirect accesses likewise require live, appropriately accessible storage. These are requirements for normal completion, not validations performed by this routine.

Pointer offsets are expressed in bytes in a 32-bit address representation. The evidence does not establish valid behavior for address overflow, misalignment, inaccessible addresses, or expired objects.

F-ff6d0e3505c3 has cleanup-like placement, but actual release, ownership transfer, and attached-resource handling are unknown. A nonnull published address does not by itself establish that the context is usable or specify its eventual release operation.

No dependency is assumed to preserve globals, context contents, object lifetime, status, or owned resources.

## Acceptance examples

These are conditional consequences of the static representation, not executed tests.

1. **Allocation failure.** If allocation returns zero, final status handling receives zero. If the final status is 7 and cleanup returns normally, cleanup also receives zero, the output receives zero, and the return is 7.

2. **Missing backend.** If resolution returns zero, the diagnostic call receives status argument 1, the pointer two bytes into the named diagnostic symbol, and the selector. No initial registrations or open attempt occur. No exact diagnostic bytes are asserted.

3. **First gate set.** If the gate is nonzero after the four initial registrations, both lookups and opening are skipped. The post-resolution captured state is written at `0x40`.

4. **Aliased callback storage.** Suppose the external callback storage read after the first lookup aliases context offset `0x2c`. Registration receives the value read before the lookup result overwrites that location, not a value reread after the store.

5. **Registration changes the first entry pointer.** If the `NOCASE` registration changes `0x2c` to another valid writable entry address, the byte-1 marker is written through that replacement address.

6. **All requested flag bits set.** For `0xffffffff`, the context receives flags `0xffff80f7`, and the open dependency receives `0xffff81f7`.

7. **Second entry absent.** A zero `NOCASE` lookup result skips its byte-2 marker write but still permits opening, assuming preceding accesses complete normally.

8. **Open failure retained.** A nonzero open result is passed to F-a061acf353ed. If the final status is not exactly 7, the context address is still published.

9. **Second gate set after successful opening.** Record setup and the new state write occur. The success diagnostic call, both success callbacks, and intermediate status query are skipped; the final status query still occurs.

10. **Intermediate success, final cleanup.** An intermediate status of zero triggers the additional two-visible-argument call. A subsequent final status of 7 nevertheless triggers cleanup and null publication.

11. **Truncated status.** A final status of `0x107` returns 7 but does not trigger explicit cleanup. A final status of `0x100` returns zero, likewise without cleanup.
