# F-2084b678aaca

## Purpose

F-2084b678aaca positions an external I/O-like object, reads two 32-bit header fields into a caller-supplied record, and conditionally loads and transforms a sequence of 32-bit entries.

The established behavior is narrower than a complete format parser:

- A selector determines whether the starting position is advanced by 12 or 20 bytes.
- Two four-byte reads populate the record’s first two fields.
- When the first field is zero, the function allocates storage for a signed, upper-bounded number of entries, reads those entries, and transforms each entry through F-76bf07f4ac67.
- On successful completion, the record’s third field is set to zero.

The return value is a 32-bit status: zero for the function’s success path and one for every explicit failure path. Failure does not imply that the record, external object, or allocated memory remains unchanged.

Interpreting the first field as a format discriminator, the second as an entry count, and the third as a cursor is plausible intent, not an established format definition.

## Interface

| 2 | A reference to an object whose first machine word supplies an indirect-operation table. |
| 3 | The unsigned low 32 bits of a starting position. |

The visible operations are consistent with a 32-bit address model: allocated addresses and record fields occupy four bytes. Portability to another address width is not established.

### Record layout

Offsets are measured in bytes from the eighth argument.

| Offset | Width | Established use |
|---|---:|---|
| 0 | 4 bytes | Destination of the first header read; subsequently tested for zero. |
| 4 | 4 bytes | Destination of the second header read; interpreted as a signed 32-bit count when the first field is zero. |
| 8 | 4 bytes | Written with zero only on the success path. |
| 12 | 4 bytes | Written with the allocation result on the entry-loading path; subsequently used as the base address for entry transformations. |

The non-loading path visibly accesses only the first 12 bytes. The loading path also requires the field at offset 12. A generally valid record should therefore provide at least 16 accessible bytes.

The function does not check record size, alignment, object validity, operation-table validity, allocation size validity, or whether these objects overlap.

### Indirect operations

Two operations are resolved from the second argument’s operation table:

- The operation at table byte offset 20 receives the object, that operation’s own callable address, the adjusted low position word, the adjusted high position word, and a final zero argument. Its result must be exactly zero to continue.
- The operation at table byte offset 16 receives the object, a destination address, a requested byte count, and a mode value. Header reads use mode 1; the entry-block read uses mode 2. Each result is compared with the requested byte count.

“Positioning” and “reading” describe inferred roles. The supplied body establishes the arguments, ordering, destinations, and result comparisons, but not the full contracts of either indirect operation.

## Behavior

### 1. Initial rejection

If the signed high position word is negative, or the record pointer is null, the function returns one.

On this path, the visible body does not invoke any dependency or write any record field. A valid second argument is not needed for this rejection path because it is not dereferenced.

A negative high word is rejected even if treating the combined words as an unsigned position would otherwise be meaningful.

### 2. Adjusted position

The selector chooses an increment:

- Zero selects 12 bytes.
- Any nonzero value selects 20 bytes.

The increment is added to the unsigned low position word. The resulting low word is reduced to 32 bits. An unsigned carry from this addition contributes one to the high word.

Consequently, a low-word wrap advances the high word rather than being discarded. There is no subsequent rejection if the resulting high word has its sign bit set. In particular, an initially nonnegative maximum signed high word can become the bit pattern `0x80000000` through carry.

The function then invokes the operation at table offset 20 with the adjusted words. A nonzero result causes return value one, without either header read.

No restoration of the prior external position is visible on failure.

### 3. Header reads

After a zero result from the positioning operation, the function performs these requests in order:

1. Four bytes into record offset 0, using mode 1.
2. Four bytes into record offset 4, using mode 1.

The second request occurs only if the first returns exactly four. Processing continues only if the second also returns exactly four.

Any other result—including a negative result, zero, a short count, or a count greater than four—causes return value one.

Read destinations are the caller’s actual record fields, not temporary storage. Thus, a failing or short read may already have modified a field. The function does not restore previous field values.

The body does not independently decode the header bytes. It examines the resulting 32-bit field contents after the indirect operation returns. Byte order and any conversion performed by mode 1 remain properties of that operation.

### 4. Conditional loading

After both header reads succeed, the current first field is tested.

If it is nonzero, allocation, entry-block reading, and entry transformation are skipped. The function proceeds to the final success write. The second field is not used as a count on this path, and the field at offset 12 is not explicitly assigned.

If the first field is zero, the current second field is interpreted as a signed 32-bit count. The working count is selected as follows:

- Values greater than 32,768 are reduced to 32,768.
- Values at or below 32,768 are retained.

There is no lower-bound check. In particular, negative counts are not converted to zero.

The cap affects the working count only. The record’s second field is not explicitly rewritten to contain the capped value.

### 5. Allocation and block read

For ordinary nonnegative working counts, the requested storage size is four times the working count, ranging from zero through 131,072 bytes.

F-fab3799b3190 is called with the four-byte-scaled count. Its 32-bit result is written to record offset 12 before the result is checked for zero.

If the result is zero, the function returns one immediately. This includes a zero-count request if that dependency returns zero for a zero-sized allocation.

If the result is nonzero, the function requests an entry-block read:

- Destination: the nonzero result returned by F-fab3799b3190.
- Requested length: four times the working count.
- Mode: 2.

The destination for this call is the saved allocation result. It is not obtained by rereading record offset 12.

The read result must equal four times the working count. Otherwise the function returns one. It does not visibly release the allocation or clear the stored address.

For negative counts, the body still attempts allocation and, if the returned address is nonzero, a block read. The visible four-byte scaling does not establish a safe size interpretation for such inputs. No contract for successful negative-count handling can be inferred.

### 6. Entry transformation

After an accepted entry-block read, the function processes indices starting at zero while the signed index is less than the working count.

For each index:

1. It reads the current base address from record offset 12 and forms the address of that index’s four-byte entry.
2. It passes that entry address to F-76bf07f4ac67.
3. After the dependency returns, it reads the base field again and writes the returned 32-bit value to that index’s entry under the then-current base.

For positive counts, calls occur in ascending index order. There is one dependency invocation and one explicit four-byte result write per index.

The two base-address observations matter. If a dependency changes the record’s base field through an alias or other shared state, the address passed to F-76bf07f4ac67 and the address receiving its result need not belong to the same allocation. The body provides no protection against this.

The working count remains the locally selected count; later changes to the record’s second field do not visibly change the loop bound.

A working count of zero performs no transformations. A negative working count also performs no transformations if execution reaches this phase, because the initial index is not less than a negative bound.

### 7. Success completion

After the non-loading path or after all required transformations, the function writes zero to record offset 8 and returns zero.

There is no explicit write to offset 8 on any earlier failure path. However, a dependency could modify that field through aliasing; preservation cannot be promised without a dependency contract.

## Side effects

### Record changes

Observable explicit writes occur in this order, subject to successful progression:

1. Header-read effects at offset 0.
2. Header-read effects at offset 4.
3. Allocation-result assignment at offset 12, only when the first field is zero.
4. Per-entry transformed-value writes, if applicable.
5. Zero assignment at offset 8, only on success.

The record is not initialized as a whole. A successful non-loading call can leave offset 12 holding its previous value. An allocation failure explicitly leaves zero at offset 12.

### External state and partial progress

The external object may change state during positioning and reads. Its exact position after any call, especially a short or failed read, is not established here.

Failure is nontransactional. Possible surviving effects include:

- A changed external position.
- Partially or completely overwritten header fields.
- An allocated address stored in the record.
- A partially populated entry buffer.
- Dependency-specific state changes.

The function contains no visible release operation. Neither successful completion nor a failed block read establishes who must eventually release the allocation. F-fab3799b3190’s ownership rules are unknown.

The function has no explicit exception handling or recovery from invalid addresses, invalid indirect targets, or dependency faults.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Unless stated otherwise, assume valid memory, returning dependencies, and no dependency mutations beyond the described read destinations.

1. **Invalid initial input.** With a negative high position word or a null record pointer, the result is one. No indirect operation is invoked.

2. **Selector distinction.** With a zero selector and no low-word carry, the positioning request uses the supplied position plus 12. With any nonzero selector, including a negative selector value, it uses the supplied position plus 20.

3. **Position carry.** With low word `0xFFFFFFFC`, high word zero, and selector zero, the positioning request receives low word 8 and high word 1.

4. **High-word sign transition.** With high word `0x7FFFFFFF` and a low-word addition that carries, the positioning request receives high word `0x80000000`. The initial guard does not reject this adjusted value.

5. **Positioning failure.** If the positioning operation returns any nonzero value, the result is one and neither header read occurs.

6. **Short first header read.** If the first header request returns three, the result is one and the second request does not occur. Any three-byte modification already performed is not undone.

7. **Nonzero first field.** If both header reads return four and the first field is nonzero, no allocation or entry transformation occurs. Offset 8 is set to zero and the result is zero, regardless of the second field’s value.

8. **Ordinary entry loading.** If the first field is zero and the second field is three, the allocation request is 12 bytes. A nonzero allocation and a block-read result of 12 lead to transformations of indices zero, one, and two, in that order, followed by the final zero write and success.

9. **Upper cap.** If the second field is 40,000 on the loading path, the working count is 32,768 and the allocation and block-read length is 131,072 bytes. The second field remains 40,000 absent dependency mutation.

10. **Zero count.** The allocation dependency is still called with zero. A zero result causes failure. A nonzero result permits a zero-length block-read request; a returned zero satisfies its comparison, no entries are transformed, and the call succeeds.

11. **Block-read failure.** After a nonzero allocation result, a mismatched block-read result causes failure. No transformations or final zero write occur. The allocated address remains stored absent dependency mutation, and no release is visible.

12. **Base mutation during transformation.** If F-76bf07f4ac67 changes the stored base before returning, its result is written using the updated base. A contract that requires the original input address also to be the output address would not match the visible behavior.
