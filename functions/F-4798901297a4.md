# F-4798901297a4

## Purpose

F-4798901297a4 saves an eight-byte record from a supplied source position, calls an external dependency with arguments describing a shift of intervening storage toward higher addresses, and writes the saved record at a supplied destination position. It then conditionally updates a signed 32-bit position field in the containing object.

**Established behavior:** the function performs the ordered reads, dependency invocation, writes, and position update described below. It does not validate positions, storage bounds, or the dependency’s effects.

**Inferred intent:** move one record toward a lower position while keeping a tracked position associated with the same logical record.

A complete reordered sequence is guaranteed only under additional conditions on arithmetic, storage, aliasing, and the dependency’s effects. In particular, an overlap-safe transfer alone is insufficient: the dependency must also leave other relevant record storage unchanged, preserve the relevant object fields, and not introduce effects that invalidate subsequent accesses.

## Interface

### Arguments

The supplied representation has three integer arguments:

| Argument | Meaning within this contract |
|---|---|
| Object address | Address used to access the tracked-position field and storage-address field. |
| Source position | Position of the record saved before the dependency invocation. |
| Destination position | Position at which the saved record is written after the dependency returns. |

The representation uses four-byte integer and address-field accesses, consistent with a 32-bit address model. It does not establish a portable pointer ABI or a higher-level container type.

Positions participate in signed integer comparisons. Address and transfer-size calculations use integer expressions whose overflow and external-call conversions are not fully established.

### Accessed object layout

| Byte offset from object address | Width | Role |
|---|---:|---|
| 8 | 4 bytes | Signed 32-bit tracked position, read after the record writes and conditionally overwritten. |
| 12 | 4 bytes | Record-storage address, read before and after the dependency call. |

No other object fields are directly accessed.

Each record occupies eight bytes: a first four-byte word followed by a second four-byte word. Both words are opaque. Their contents receive no interpretation as pointers, counters, resource handles, or ownership markers.

### Result

There is no explicit return value. Observable results consist of memory accesses, the external call, any effects of that call, and the function’s subsequent writes.

### Access preconditions

For normal completion of the function’s own operations:

- The object fields must be accessible for their stated reads and conditional write.
- The initial storage address must permit reading both words at the source position.
- The storage address reread after the dependency returns must permit writing both words at the destination position.
- Calculated addresses must be usable in the execution environment.
- Access alignment must satisfy the environment’s requirements.
- The dependency must return normally and leave the state needed for later accesses usable.

These are conditions for meaningful execution, not validations performed by the function.

For results expressed using ordinary mathematical positions and byte offsets, all intermediate calculations must also be representable without relying on unresolved overflow or conversion behavior.

## Behavior

### Saving the source record

The function first reads the storage-address field at object offset 12.

Using that initial address, it locates the source record at a byte displacement of eight times the source position. It reads the first four-byte word and then the second four-byte word.

Both values are retained across the dependency call. The eventual destination contents therefore come from these pre-call reads, not from a later reread of the source record.

### Calling the transfer dependency

The function invokes **F-opaque-01** with three arguments, in this order:

| Argument | Supplied value |
|---|---|
| First address | Initial storage address plus eight times the destination position plus one record. |
| Second address | Initial storage address plus eight times the destination position. |
| Transfer amount | Eight times the source position minus the destination position. |

More precisely, the first displacement is eight multiplied by the sum of the destination position and one. The transfer amount is eight multiplied by the difference between the source and destination positions.

Both address arguments use the storage address read before the call.

For nonnegative positions with destination below source, these values describe transferring the records from the destination through the position immediately before the source into positions one higher. For a difference of at least two records, the two ranges overlap.

The dependency’s return value is not inspected. Later operations occur only if it returns normally.

### Reloading storage and writing the saved record

After the dependency returns, the function rereads the storage-address field at object offset 12. It uses this new value to locate the destination record.

It writes:

1. The saved first word to the first four bytes of the destination record.
2. The saved second word to the next four bytes.

These are separate four-byte writes. No atomic eight-byte replacement is established.

The address reload is behaviorally significant. If the dependency changes the storage-address field, the transfer arguments still designate the initial storage, but the saved record is written into the newly designated storage. No transfer of the remaining records into that new storage is established by this function.

### Updating the tracked position

Only after both destination-word writes does the function read the signed 32-bit tracked-position field at object offset 8.

Its decision uses that newly read value:

| Condition | Explicit update |
|---|---|
| Tracked position equals source position | Write destination position. |
| Tracked position is below source position and at least destination position | Write tracked position plus one. |
| Otherwise | Do not write the tracked-position field. |

Equality with the source takes precedence.

Under ordinary reorder conditions, a tracked source record follows the saved record to the destination. A tracked record in the intervening shifted interval advances one position. Other tracked positions remain numerically unchanged.

The function does not snapshot this field on entry. The value used may reflect dependency effects or, when storage aliases the object, the preceding destination-word writes.

### Conditions for a complete reorder guarantee

The complete-order interpretation requires all of the following:

- Positions are nonnegative, and destination is no greater than source.
- The source and all affected positions designate existing, accessible eight-byte records.
- Arithmetic, addresses, alignment, and the dependency’s amount interpretation support the stated byte ranges without unresolved overflow or conversion.
- The dependency performs an overlap-safe transfer from its second address to its first address for the stated amount, using the pre-transfer bytes as the source contents.
- **Within the relevant record storage, the dependency modifies only the specified transfer destination range.** Records and bytes outside that range remain unchanged.
- **The dependency preserves both accessed object fields:** the storage address and tracked position.
- **The relevant record storage is disjoint from the object’s accessed fields.** In particular, the final metadata write cannot change record contents, and the record writes cannot change either accessed field.
- No concurrent or other external mutation changes the relevant storage or fields during the operation.

These conditions establish both the intended transfer and the necessary frame conditions. They are not promises made about the unknown dependency.

Without them, the contract is limited to the ordered local accesses and the conditional tracked-position update. For example, a dependency could perform the described transfer and also overwrite an unrelated record; overlap safety alone would not prevent that result.

### Boundary and atypical cases

**Equal source and destination.** The dependency is still called. The transfer amount is zero, while its first address is one record beyond the destination. The saved record is then rewritten. If the tracked position equals that position, the function explicitly writes the same numeric value back.

Zero transfer amount does not establish that the dependency has no effects or accepts the calculated addresses.

**Source below destination.** There is no rejection or alternative higher-position move. Under nonoverflowing signed arithmetic, the transfer amount is negative. Its interpretation at the dependency boundary is unknown. A correct move toward higher positions is not established.

**Negative positions.** No nonnegativity check exists. Calculated addresses can precede the nominal storage address.

**Oversized positions.** No bounds or overflow checks exist. Relevant calculations include destination plus one, source minus destination, multiplication by eight, and addition to storage addresses. Portable wrapping, signed-overflow behavior, and unsigned conversion at the external boundary are not established.

**Tracked-position increment.** Within the stated signed 32-bit interpretation, the increment branch cannot overflow: it requires the tracked position to be strictly below the source position, so the tracked position cannot be the maximum signed 32-bit value.

**Aliased storage.** Aliasing is not rejected. Destination writes can change the tracked-position field before it is read. Conversely, the final tracked-position write can change record storage. Such cases follow the ordered accesses, not an unconditional sequence-reordering guarantee.

## Side effects

The statically expressed order is:

1. Read the initial storage-address field.
2. Read the source record’s first word.
3. Read the source record’s second word.
4. Invoke F-opaque-01.
5. Reread the storage-address field.
6. Write the saved first word at the destination.
7. Write the saved second word at the destination.
8. Read the tracked-position field.
9. Conditionally write that field.

This describes the supplied representation’s access order, not a hardware memory-ordering or concurrency guarantee.

No allocation, deallocation, reference-count adjustment, destructor, resource release, synchronization, record-count update, or capacity update is directly shown. There is no separate source-clearing operation.

The two saved words are copied without explicit ownership handling. Whether they carry ownership significance is unknown. The dependency’s allocation, release, and ownership effects are also unknown.

There is no visible error result, rollback, exception handler, or transactional guarantee. If an access fails or the dependency does not return normally, completion of later operations is not established.

## Dependencies

### F-opaque-01

This is a contract-local opaque identifier for the sole external dependency. It does not identify a verified library routine.

Established facts:

- It receives two calculated addresses and a calculated transfer amount.
- Both addresses derive from the initial storage-address read.
- The call occurs after both source-word reads and before either destination-word write.
- Its return value is unused.

The conditional transfer interpretation requires overlap-safe copying of the specified bytes from the second address to the first. The stronger **complete reorder** interpretation additionally requires that, within relevant record storage, only the specified transfer destination is modified, both accessed object fields are preserved, and record storage is disjoint from those fields. The remaining arithmetic, accessibility, and interference conditions stated above also apply.

No unconditional preservation of object fields, globals, other records, allocation state, or ownership is assumed.

- Effects outside the apparent transfer destination.

- Whether normal return is guaranteed.
- Allocation, release, global-state, and object-field effects.

## Acceptance examples

These are conditional acceptance cases derived from static evidence. No runtime tests have been performed.

### Complete-order example conditions

Every complete-order example below assumes the full reorder conditions stated in Behavior. In particular:

- Arithmetic and accesses are valid.
- The dependency performs the specified overlap-safe transfer.
- Within relevant record storage, it changes only the transfer destination.
- It preserves the storage-address and tracked-position fields.
- Relevant record storage is disjoint from both accessed object fields.
- No other mutation interferes.

The tracked-position inputs in these examples are therefore also the values read after the destination writes.

### Move an interior record toward the beginning

Given records A, B, C, D, E, source position 3, and destination position 1, the final order must be:

A, D, B, C, E.

Independent tracked-position cases are:

| Initial tracked position | Final tracked position |
|---:|---:|
| 0 | 0 |
| 1 | 2 |
| 2 | 3 |
| 3 | 1 |

The preservation of E depends on the dependency’s restricted effects. It does not follow merely from performing the requested transfer.

### Move to the immediately preceding position

Given A, B, C, D, source position 2, and destination position 1, the final order must be:

A, C, B, D.

A tracked position of 1 becomes 2. A tracked position of 2 becomes 1.

### Equal positions

With source and destination both 2, the dependency must still receive a zero transfer amount and a first address one record beyond position 2.

Under the complete-order conditions, relevant record storage remains numerically unchanged after the saved record is rewritten. All tracked positions remain numerically unchanged. If the tracked position is 2, an explicit same-value metadata write still occurs.

Acceptance must not require skipping the call or suppressing record writes.

### Dependency changes the storage address

Suppose the dependency changes the storage-address field to another valid buffer and returns normally.

The saved pre-call source words must be written at the destination in that newly referenced buffer. These final writes must not use the initial storage address.

This case does not satisfy the complete-order assumptions. No complete sequence arrangement in either buffer is guaranteed.

### Dependency changes the tracked position

Suppose the dependency sets the tracked position to the source position, returns normally, and the destination writes do not overlap that field.

The final tracked position must become the destination position, regardless of its entry value.

### Aliased destination and metadata

Suppose valid destination writes overlap the tracked-position field.

The position decision must use the field value present after both record-word writes, not its entry value or its value immediately after the dependency returns. A subsequent metadata write may alter record bytes.

No complete-order guarantee applies.

### Reversed positions

For source position 1 and destination position 3, the transfer-amount expression is negative sixteen under ordinary nonoverflowing signed arithmetic.

Acceptance is limited to the supplied call arguments and the later local behavior if the dependency returns with valid state. Correct higher-position movement, rejection, and safe failure are not established.
