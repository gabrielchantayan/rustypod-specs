# F-8a92d5d60703

## Purpose

F-8a92d5d60703 searches an indexed sequence using a caller-supplied comparison callback. It returns a 32-bit match indicator and writes a 16-bit position to caller-provided storage.

The established behavior is a midpoint-based search over a count obtained from the sequence object. Each comparison receives the caller’s search argument and an address computed through a reverse-addressed table of unsigned 16-bit offsets.

**Inferred intent:** When the sequence is ordered consistently with the callback, the written position identifies either a matching entry or the insertion position for a missing entry.

The function does not establish ordering, validate addresses, or validate the callback’s behavior. Without those preconditions, its branch-and-position behavior remains defined by the observed comparisons, but the result need not represent a valid lookup or insertion position.

## Interface

### Inputs

The interface has four arguments:

| Argument | Observed role |
|---|---|
| Descriptor address | Base address of an object containing a callback pointer and a 16-bit table-position field. |
| Sequence address | Base address of an object containing a 16-bit entry count and supplying the origin for table and candidate addresses. |
| Search argument | An opaque 32-bit value passed unchanged as the callback’s first argument. |
| Position destination | Address at which the function writes one 16-bit result before normal return. |

The supplied representation uses 32-bit address arithmetic. The search argument is not dereferenced by this function; a callback may interpret it as an address or another kind of value.

### Observed layouts

Only the following fields are established:

| Object | Byte offset | Width | Meaning established by use |
|---|---:|---:|---|
| Descriptor | 8 | 32 bits | Callable address, captured once on entry. |
| Descriptor | 28 | 16 bits, unsigned | Quantity used to locate the offset table relative to the sequence base. |
| Sequence | 10 | 16 bits, unsigned | Entry count, captured once on entry. |

No complete object size, allocation layout, field name, or metadata meaning is established.

For a logical entry index \(j\), the function reads an unsigned 16-bit offset at:

\[
\text{sequence base}+\text{table-position field}-2-2j
\]

It then obtains the candidate address by adding that unsigned offset to the sequence base.

Thus, increasing logical indexes correspond to decreasing offset-table addresses. This does not establish the ordering or placement of the candidate objects themselves.

### Outputs

On normal completion:

- The direct return is the 32-bit value **1** when a callback invocation returns zero.
- The direct return is the 32-bit value **0** when the search interval becomes empty without such a result.
- The position destination receives exactly one 16-bit write.

For a match, the written position is the midpoint index whose comparison returned zero. For a non-match, it is the final lower search bound.

No separate error result is present.

### Preconditions

For normal completion, the required descriptor and count fields must be readable, and the position destination must be writable. On a nonempty search, the captured callback address must be callable, each selected table entry must be readable, and each callback invocation must complete with a compatible signed 32-bit result.

The function performs no explicit null, bounds, alignment, object-validity, or callback-validity checks. A zero count avoids indirect calls and offset-table reads, but does not avoid the initial descriptor and count reads or the final output write.

## Behavior

### Initial observations

The function obtains its initial state in this order:

1. Reads the callback address from descriptor byte offset 8.
2. Reads the unsigned 16-bit table-position field from descriptor byte offset 28.
3. Reads the unsigned 16-bit count from sequence byte offset 10.

These values are captured once. The function does not reload them after invoking the callback.

The initial search interval starts at index zero and ends at one less than the count. The count is promoted before subtraction, so a count of zero creates an upper bound of negative one rather than wrapping to 65,535.

### Empty-interval completion

Before selecting each candidate, the function checks whether the upper bound is less than the lower bound.

When the interval is empty, it writes the lower bound to the position destination as a 16-bit value and returns zero. No additional comparison or table read occurs for that empty interval.

For an initial count of zero, this is the first search action: the function writes position zero and returns zero without invoking the callback.

### Candidate selection and comparison

For a nonempty interval, the selected index is the floor of the average of the current lower and upper bounds. It therefore chooses the lower of the two central indexes when the interval has an even number of entries.

The function then:

- Reads the unsigned 16-bit table entry associated with that selected index.
- Adds the zero-extended table value to the sequence base.
- Calls the captured callback with the original search argument first and the computed candidate address second.
- Interprets the callback result as a signed 32-bit integer.

Only the sign of that result affects the search:

| Callback result | Effect |
|---|---|
| Negative | Retain only indexes strictly below the selected index. |
| Zero | Write the selected index and return one. |
| Positive | Retain only indexes strictly above the selected index. |

A zero result ends the search immediately. The function does not continue looking for an earlier or later equivalent entry.

### Ordering contract for lookup semantics

For the result to describe an ordered lookup, callback results must be consistent with the logical index order:

- A negative result must indicate that any possible match belongs at a lower logical index.
- A positive result must indicate that any possible match belongs at a higher logical index.
- Zero must indicate an acceptable match.

This describes the required comparison direction without assigning an undocumented meaning to the candidate objects.

Under a stable ordering with those properties, a failed search writes the insertion boundary between lower-index entries producing positive comparisons and higher-index entries producing negative comparisons.

If equivalent entries exist, the function returns whichever equivalent entry it first selects. It does not guarantee the lowest or highest matching index.

### Widths and arithmetic

The count and table-position field are unsigned 16-bit quantities, each in the range 0 through 65,535.

The search bounds and callback result are treated as signed 32-bit quantities. A selected index is always between zero and count minus one. While an interval is nonempty, the sum used to select its midpoint is nonnegative and no greater than 131,068. Midpoint arithmetic therefore does not approach signed 32-bit overflow.

A failed search can produce a position from zero through count inclusive. Even when the count is 65,535, its possible final position of 65,535 fits in the 16-bit output. A matching index cannot exceed 65,534.

Table addressing subtracts two bytes per logical index. Its fixed-width address calculations are subject to 32-bit wraparound; they are not checked or widened into a validated object-relative range. Adding the unsigned table value to the sequence base likewise does not establish that the resulting address belongs to a valid object.

The table-position field is not required by the function to be even, large enough to cover the table, or consistent with the count. Such constraints, if required by the actual data format or execution environment, are caller obligations.

## Side effects

### Direct accesses

The function directly performs:

- Three initial metadata reads.
- One 16-bit offset-table read for each comparison.
- One indirect callback invocation for each comparison.
- One 16-bit position write immediately before normal return.

It does not itself read candidate contents. Candidate inspection, if any, occurs inside the callback.

The position destination is not initialized before searching. During callback execution, it retains whatever value is present unless the callback or another actor changes it.

### Callback-visible changes and aliasing

The callback is an externally supplied dependency whose effects are not established.

Changing the descriptor’s callback field, table-position field, or the sequence count during a callback does not change the corresponding values already captured by this invocation.

Offset-table entries are read when their indexes are selected, not captured together at entry. A callback’s modification to a subsequently accessed table location can therefore affect a later candidate address.

No non-aliasing guarantee is established for the position destination. If it overlaps input storage, the function’s final 16-bit write can overwrite that storage. There are no further input reads or callback invocations after that final write on the normal path.

### Ownership and lifetime

No direct allocation, deallocation, ownership transfer, or reference-management operation is present.

This does not establish that the callback preserves memory or global state. The caller must ensure that required storage remains valid for every access that actually occurs. Callback-induced invalidation of later-accessed storage is not detected.

## Acceptance examples

These examples are conditional behavioral checks derived from static evidence. They have not been executed.

### Empty sequence

Given a readable descriptor, a readable count of zero, and a writable position destination:

- The initial callback and table-position fields are still read.
- No offset-table entry is read.
- The callback is not invoked.
- Position zero is written.
- The function returns zero.

The stored callback need not be invoked successfully in this case because no call occurs.

### Immediate match among four entries

Given a count of four, the first selected logical index is one.

If the corresponding callback invocation returns zero:

- Only that comparison is performed.
- Position one is written.
- The function returns one.

This remains true even if another logical entry would also compare equal.

### Search before every entry

Given a count of four and a callback that returns a negative value at every selected candidate, the selected indexes are one and then zero.

The function then writes position zero and returns zero.

### Search after every entry

Given a count of four and a callback that returns a positive value at every selected candidate, the selected indexes are one, two, and three.

The function then writes position four and returns zero. Position four is an insertion boundary, not an existing entry index.

### Search between two entries

Given a count of four:

- The comparison at index one returns positive.
- The next comparison, at index two, returns negative.

The interval then becomes empty. The function writes position two and returns zero.

### Offset decoding

Given a table-position field of 20 and selection of logical index three, the offset-table read occurs at sequence base plus 12.

If that 16-bit entry contains 40, the callback receives sequence base plus 40 as its second argument, assuming these additions do not wrap. The table entry is an unsigned offset, not an absolute address.

### Captured metadata versus later reads

If the first callback changes the sequence count, subsequent search bounds still derive from the count read at entry.

If that callback instead changes an offset-table entry selected later, the later candidate address uses the changed entry value, provided the storage remains valid and readable.
