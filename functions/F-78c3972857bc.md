# F-78c3972857bc

## Purpose

F-78c3972857bc updates bookkeeping in a supplied context, conditionally advances an embedded collection, and processes records associated with the collection’s current entry.

For each non-null record, it performs a dependency-mediated lookup. A zero lookup result triggers temporary-value preparation, candidate resolution, and temporary cleanup. A nonzero candidate then supplies a replacement working argument and is passed to registration and notification dependencies.

This is a static behavioral contract. Collection terminology, lookup, registration, and notification describe apparent roles, not independently established dependency semantics.

Changes to the working argument are local to this invocation. No direct writeback to the caller’s argument storage is shown.

## Behavior

### 1. Initial collection inspection

The function calls F-18dde3a4696c with the address of the context’s embedded object at `0xA0`.

If that call returns zero:

1. It calls F-fc900472ddea with the same embedded-object address.
2. It reads the first 32-bit word at the returned address.
3. It calls F-5483c642aeea with the context and that word.

There is no null check on the returned address before dereferencing it, and no nonzero requirement on the word passed to F-5483c642aeea.

If the initial status result is nonzero, this access and callback are skipped.

### 2. Bookkeeping updates

After the initial inspection and any callback:

1. The 32-bit field at context offset `0xB0` is read and replaced by its value minus four.
2. The 32-bit field at context offset `0xC0` is read and replaced by its value minus one.

The update at `0xB0` precedes the update at `0xC0`. These operations use the field values present after F-5483c642aeea returns, if it was called; the function does not retain pre-callback copies.

There are no checks for zero, underflow, alignment to four, or consistency between the two fields. The body shows 32-bit subtraction and storage, not saturation or checked arithmetic. At a fixed-width machine-word level, wraparound follows reduction modulo \(2^{32}\); language-level signed-overflow guarantees are not established by this representation.

### 3. Conditional collection operation

The function calls F-18dde3a4696c again.

It then calls F-522ecb0fe768 with the embedded-object address if either:

- The new status result is nonzero; or
- The status result is zero and the current 32-bit fields at `0xB0` and `0xB4` are equal.

The equality test is short-circuited when the status is nonzero. The supplied representation does not establish a relative evaluation order between the two field reads used for equality.

The status dependency runs after the bookkeeping updates and could itself alter state. Consequently, the equality condition is not necessarily a comparison of the value just written at `0xB0` against an unchanged boundary.

Calling F-522ecb0fe768 when status is nonzero is explicitly part of the observed behavior. Its validity and effect cannot be inferred from an assumed “empty collection” interpretation.

### 4. Post-operation inspection

The function calls F-18dde3a4696c a third time, regardless of whether F-522ecb0fe768 was called.

- A nonzero result ends the invocation.
- A zero result causes another call to F-fc900472ddea, followed by a read of the first 32-bit word at its returned address.

If this word is zero, the invocation ends without record enumeration.

If it is nonzero, the function:

1. Initializes the first word of its 16-byte temporary storage from the fourth argument.
2. Calls F-39b0846ca4e1 with the nonzero entry.
3. Retains the returned 32-bit signed count.
4. Reads and retains one global 32-bit selector.
5. Begins indexed processing at index zero.

The global selector is read after the count dependency returns. The same retained selector is used throughout the loop, even if later dependencies change the underlying global location.

### 5. Index progression and termination

Each iteration compares a signed index against the retained signed count. Processing occurs only while the index is less than the count.

After an iteration, the index becomes the sign-extended low 16 bits of its previous value plus one. This yields:

- No iterations for counts of zero or less.
- Indices zero through count minus one for counts from 1 through 32,767.
- Wrap from 32,767 to −32,768 rather than progression to 32,768.

For any positive signed count of 32,768 or greater, the loop condition cannot become false through this index progression: every possible signed 16-bit index is smaller than the retained count. If dependencies continue returning normally, iteration cycles through signed 16-bit values and includes negative indexed-record requests.

This is an established arithmetic consequence, not a claim that such counts are valid inputs to the surrounding system.

### 6. Per-record processing

For each index that passes the loop condition:

1. F-2c6bf41c5b21 is called with the retained entry and the current signed index.
2. A zero result skips the rest of that iteration.
3. For a nonzero record, the function reads its 32-bit value at offset `0x14`.
4. It calls F-838218ef65c4 with:
   - The current 32-bit context field at `0xCC`.
   - The retained global selector.
   - The captured record value.
   - The address of the temporary storage.
   - The current working argument.

The record value is captured before the lookup call. It is reused later in that iteration without rereading offset `0x14`.

A nonzero lookup result skips candidate preparation, temporary cleanup, registration, and notification for that record.

A zero lookup result instead causes this sequence:

1. F-f4fd698ba468 receives the temporary-storage address and the record address plus `0x10`.
2. F-42d4d107a16d receives the context and the current first word of temporary storage.
3. Its returned candidate value is retained.
4. F-8a5aadac202f receives the temporary-storage address.

The cleanup-like call occurs before testing whether the candidate is zero. Thus, it occurs for both zero and nonzero candidate results on this branch.

The function does not reset temporary storage between records. A lookup or preparation dependency can therefore affect the first word passed to later candidate-resolution calls. The other three words have no explicit initialization in this body.

### 7. Nonzero-candidate processing

After temporary cleanup, a zero candidate ends the current iteration’s processing.

For a nonzero candidate:

1. The 32-bit word at candidate offset `0x18` is read.
2. The working argument is replaced by that word plus `0x1C`.
3. F-7656802f08c9 is called with:
   - A fresh read of the context field at `0xCC`.
   - The retained global selector.
   - The retained record value.
   - The candidate.
4. F-8349c252c168 is called with the candidate and the integer value `0x1B`.

The addition of `0x1C` applies to the value loaded from candidate offset `0x18`; it is not an offset applied directly to the candidate address. No overflow check is shown.

The working argument changes before registration and notification. Its replacement is used by later lookup calls, but does not retroactively affect the lookup that produced this candidate.

There is no explicit finalization call after the loop.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests.

1. **Initial callback precedes decrements.**  
   Given an initial zero status and a readable accessed word, F-5483c642aeea receives that word before either bookkeeping update. If the callback changes `0xB0` to 20 and `0xC0` to 7, and no intervening mutation occurs, the direct updates write 16 and 6.

2. **Second status short-circuits equality.**  
   Given a nonzero second status, F-522ecb0fe768 is called without requiring equality of `0xB0` and `0xB4`. A third status query still follows.

3. **No collection operation on unequal fields.**  
   Given a zero second status and unequal fields when compared, F-522ecb0fe768 is skipped. This does not skip the third status query.

4. **Final status stops enumeration.**  
   Given a nonzero third status, there is no subsequent collection access, count request, global-selector read, or record lookup.

5. **Zero entry stops before setup.**  
   Given a zero third status and a zero word from collection access, the function does not call the count dependency or initialize temporary storage from the fourth argument.

6. **Nonzero lookup result bypasses cleanup.**  
   Given a nonzero record and nonzero F-838218ef65c4 result, the preparation, candidate-resolution, temporary-cleanup, registration, and notification calls are all skipped for that record.

7. **Zero candidate still follows cleanup.**  
   Given a zero lookup result and zero candidate result, temporary preparation and cleanup both occur. The working argument remains unchanged, and registration and notification are skipped.

8. **Candidate updates later lookups.**  
   Given a nonzero candidate whose word at `0x18` is `0x1000`, the working argument becomes `0x101C` before registration. A later lookup receives `0x101C` unless another successful candidate replaces it first.

9. **Count boundary changes termination.**  
   Given count 32,767 and normally returning dependencies, record requests use indices 0 through 32,766. Given count 32,768, the index eventually wraps from 32,767 to −32,768; ordinary loop progression does not terminate enumeration.
