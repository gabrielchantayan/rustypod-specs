# F-3f0536d71f99

## Purpose

F-3f0536d71f99 performs two ordered indirect dispatches. The first dispatch selects a callable through a table associated with the supplied object-like storage. Its returned value identifies the storage used to select the second callable. The function invokes that second callable and, if both calls return normally, returns without a value.

The established behavior is a dispatch chain, not an independently established operation such as construction, destruction, notification, or resource release. Those interpretations would require information about the selected callees and their calling conventions.

The relationship between the two dispatches is significant: the second dispatch uses the first call’s returned value. It does not necessarily use the original input, the original dispatch table, or an object with the same layout beyond the accesses described below.

## Interface

### Input

The function accepts one pointer-valued input, referred to here as the **input object address**.

The supplied representation treats the addressed storage as containing an integer-sized value at byte offset zero. That value is then used as the base address of a dispatch table. A callable address is obtained from byte offset 28, hexadecimal 0x1c, relative to that table base.

The input is therefore subject to these operational preconditions:

- Its address must permit the initial integer-sized read.
- The value read must identify storage permitting a callable-address read at byte offset 28.
- The retrieved callable must be invocable under the actual machine-level calling convention.
- If that invocation returns normally, its returned value must support the second dispatch described below.

No length, explicit type tag, ownership flag, or error-output location is supplied.

### Intermediate result

The first selected callable returns a value that the function interprets as another object address. Call this the **returned object address**.

The function reads an integer-sized value at byte offset zero of this returned object. It uses that value as a second dispatch-table base, then obtains a callable address at byte offset 8 of that table.

The returned object may be the same object as the input, a different object, shared storage, or some other address compatible with these accesses. No identity relationship is enforced.

### Output

F-3f0536d71f99 has no explicit return value. The second callable’s result, if any, is not used to produce an output or make another visible decision.

The function has no explicit success or failure indicator. Normal return establishes only that the visible dispatch sequence completed; it does not establish any higher-level operation’s success.

### Width and layout qualification

The supplied representation uses integer-sized reads for both object headers and converts those values into addresses. It does not provide an authoritative target data model.

Under a 32-bit interpretation, each header read occupies four bytes. If callable addresses are also four bytes wide and tables are densely packed, the offsets correspond to the eighth and third table entries, respectively. Those entry numbers are conditional interpretations, not additional established layout facts. The established selectors are byte offsets 28 and 8.

The callable-address width, alignment requirements, integer-to-address conversion rules, and behavior of address arithmetic near the address-space boundary remain undocumented.

## Behavior

### First dispatch

The function first reads the integer-sized value at the input object address. It uses that value as a dispatch-table base.

It then obtains the callable address stored at byte offset 28 from that base and invokes the selected dependency, identified below as F-indirect-01.

The displayed call expression supplies no explicit arguments. This does **not** establish that the machine-level callee receives no arguments. In particular, it does not establish whether a receiver is supplied through a register, whether an existing register value remains relevant, or whether an ABI-specific convention applies.

The function interprets the first call’s result as the returned object address. There is no visible null check, range check, type check, or success check before that result is used.

### Second dispatch

After F-indirect-01 returns normally, the function reads the integer-sized value at the returned object address. It uses this newly read value as the second dispatch-table base.

It obtains the callable address stored at byte offset 8 from that base and invokes the selected dependency, identified below as F-indirect-02.

This call also has no explicit arguments in the supplied representation. Its machine-level argument and receiver conventions are not established.

After the second call returns normally, the function returns. No additional explicit state update or returned-value processing is visible.

### Observable ordering

For a normally completing invocation, the established order is:

1. Read the input object’s header value.
2. Read the first callable address using that header value and byte offset 28.
3. Invoke F-indirect-01 and obtain its result.
4. Read the returned object’s header value.
5. Read the second callable address using that header value and byte offset 8.
6. Invoke F-indirect-02.
7. Return without a value.

The second object-header read occurs after the first call. Consequently, it observes storage as it exists after that call, subject to the execution environment’s ordinary memory semantics.

If the first call returns the input object address, the header is read again. The function does not visibly reuse the earlier header value. A change to that header during the first call can therefore change the second dispatch target.

### Failure and interruption

No visible recovery branch handles an invalid input, invalid table base, invalid callable address, or unusable first-call result.

If the first call does not return normally, the visible sequence does not reach the second dispatch. If the second call does not return normally, the function does not reach its ordinary return through this sequence.

Invalid memory access or invalid control transfer has no specified error result here. A crash, trap, exception, or other outcome must not be promised without the missing runtime and ABI information.

## Side effects

The function contains no explicit store to the input object, returned object, dispatch tables, or global state in the supplied representation.

That narrow observation does not make the function pure. Either selected dependency may modify memory, update globals, perform I/O, invoke callbacks, alter synchronization state, or terminate execution. None of those effects is established or excluded.

No explicit allocation, deallocation, reference-count adjustment, ownership transfer, or resource release is visible in the wrapper. In particular:

- Passing the input does not visibly transfer ownership.
- Receiving the intermediate address does not visibly acquire ownership.
- Performing the second dispatch does not establish that the returned object is released.
- Normal return does not establish that either object remains valid.

The function retains no explicit persistent reference to either object. Any retention by a dependency is unknown.

For valid execution, storage must remain usable through each access that consumes it. For example, if the first call invalidates the input object but returns a different valid object, the visible wrapper does not subsequently require another read from the original input. If it instead returns the now-invalid input address, the next header read lacks the required validity.

Concurrent modification and synchronization requirements are undocumented. The observed read order does not itself establish atomicity, mutual exclusion, or freedom from data races.

## Acceptance examples

These are conditional contract examples, not executed tests.

### Distinct valid objects

Given valid input storage whose first dispatch selects a callable that returns a different valid object, the function must select the second callable using the returned object’s header and byte offset 8. It must not select that callable using the original input’s table merely because the original input remains valid.

### Same object, changed header

Given a first callable that changes the input object’s header and then returns the input object address, the second dispatch must use the header read after the first call. The earlier table base does not determine the second target.

### Shared dispatch table

Given two object addresses whose headers identify the same table, the first and second dispatches still use their respective byte offsets, 28 and 8. Sharing a table does not collapse the two selections into one.

### First call does not return

Given a first selected callable that never returns normally, the wrapper must not perform the second object-header read through the ordinary sequence described here. Effects performed within that callable are outside this wrapper’s established behavior.

### Null intermediate result

Given a first callable that returns a null address, there is no visible branch that treats it as “nothing to do.” The next specified operation attempts to read the returned object’s header. The resulting failure mechanism is undocumented.

### Second call produces a value

Given a normally returning second callable that produces a machine-level result, the wrapper does not visibly inspect that result or expose it as its own return value.
