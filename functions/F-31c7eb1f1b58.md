# F-31c7eb1f1b58

## Purpose

F-31c7eb1f1b58 selects a binary-resource record, stores its signed dimension in an output object, checks the record’s data offset, and requests destination storage. If the allocation dependency reports success, the function conditionally copies source bytes into a strided destination layout, initializes additional output fields, and calls a final processing dependency.

These operations are established by the supplied static body. A font-resource interpretation is inferred intent, not a required interpretation of the data.

The operation is not transactional. Output writes precede both offset rejection and allocation failure, and the function performs no explicit rollback.

## Interface

### Arguments

The function receives three 32-bit arguments:

1. **Output-object address:** identifies writable output state and associated-object references.
2. **Resource-holder address:** identifies storage containing a 32-bit intermediate-object address.
3. **Selector:** a 32-bit integer controlling record selection.

The intermediate object’s field at byte offset `0x84` contains the resource-header address.

The intermediate object is dereferenced before its address is checked for zero. Consequently, a null intermediate-object address does not guarantee an ordinary error return. The preliminary read must be accessible for execution to reach the explicit null checks.

### Result

The exposed return is a 64-bit composition of two 32-bit parts:

| Part | Behavior |
|---|---|
| Low 32 bits | Status selected or obtained during processing. |
| High 32 bits | Original resource-holder address on paths that do not reach the allocation attempt; zero on paths that reach that attempt. |

Directly established status values are:

- **`6`:** an explicit intermediate-object or resource-header nonzero check fails, assuming the earlier dereference completes.
- **`3`:** the selected data offset fails the strict upper-bound check, after any enabled diagnostic returns normally.
- **`0`:** the allocation status is zero and remains zero through subsequent processing.
- **Other values:** may be supplied through the allocator’s writable status argument. Later modification through an escaped reference is not excluded.

The high part is not the destination address and is not an independent success flag.

## Behavior

### Discovery and record selection

The function reads the intermediate-object address from the resource holder, then reads the resource-header address from intermediate-object offset `0x84`. Only afterward does it test both addresses for nonzero values.

Failure of either explicit check selects status `6`. This path performs no explicit output-object write and calls none of the listed dependencies.

For an accepted header:

- A zero selector selects the unsigned byte at header offset `0x6E`, without decrementing it.
- A nonzero selector selects the 32-bit result of subtracting one, used as an unsigned index.

Selector one therefore selects index zero. Negative selectors are not rejected and can produce very large indices. There is no visible record-count check.

The discriminator selects the record size and table displacement. The selected address combines the base read from header offset `0xA4`, the displacement, and the index multiplied by the record size. There is no visible overflow or address-range check for this calculation.

The function reads the record’s signed 16-bit dimension and writes its sign-extended value to output offset `0x50`. It then reads the data offset using the selected layout. This write-before-offset-read ordering matters if the output object aliases the resource.

### Offset validation

The selected offset is compared with the unsigned 32-bit field at header offset `0x0C`. Acceptance requires the offset to be **strictly smaller**. Equality fails.

On rejection, the function reads a signed 32-bit diagnostic-control field at offset `0xCC` of a globally referenced object. If that value is greater than one, it calls F-4457a9a44a68 with a fixed invalid-resource-offset diagnostic. If that call returns normally, status `3` is selected.

The dimension write remains observable. This branch neither attempts allocation nor explicitly clears output offset `0x58`.

The comparison checks only the selected starting offset. It does not validate the record address, the complete source range, or destination capacity.

### Allocation preparation and call

For an accepted offset, the function rereads the base at header offset `0xA4` and adds the selected offset to obtain the initial source address. This is a new base read, not necessarily the same value used for record selection.

A signed count is derived from the original signed 16-bit dimension by adding seven and applying a signed right shift of three positions. For nonnegative dimensions, this equals division by eight rounded upward. The addition fits within signed 32-bit range. Negative dimensions are accepted; their precise shifted result depends on the target’s signed-shift semantics.

The allocation context is read through output offset `0x04`, followed by offset `0x64` of the referenced object. The function then:

1. Stores the derived count at output offset `0x54`.
2. Reads the unsigned 16-bit header width at `0x64` and stores its zero-extended value at output offset `0x4C`.
3. Writes byte value one at output offset `0x5E`.

The high return part becomes zero before the allocation call.

F-6dd003795db7 receives, in order:

1. The allocation context.
2. The current 32-bit width from output offset `0x4C`.
3. Zero.
4. The derived signed count.
5. Zero.
6. The address of local 32-bit status storage initialized to zero.

The returned address is stored at output offset `0x58` before the status is tested.

A nonzero status skips byte rearrangement and final initialization. No explicit release, rollback, or returned-address validity check occurs. A zero status proceeds even when the returned address is null.

### Byte rearrangement and its termination conditions

The outer loop executes once per positive unit of the locally derived count. The local count decreases after each iteration. Changes to output offset `0x54` do not change that iteration limit.

A global 32-bit value is read before every outer-loop condition test, including the terminating test. Thus it is read even when the initial count is zero or negative.

Each outer iteration rereads the full unsigned 32-bit width at output offset `0x4C` and forms an endpoint by adding that width to the current source address. It starts a destination cursor at the allocation result plus the outer-iteration position.

**Before every byte copy, the function tests whether the current source address is strictly less than the endpoint.** The test is relational, not merely an inequality or an instruction to continue until equality.

When the comparison succeeds, the function:

- Reads the current source byte and writes it to the current destination address.
- Reads the 32-bit stride from output offset `0x54` and advances the destination cursor by that value.
- Advances the source cursor by one byte.

The source cursor carries forward into the next outer iteration. The destination starting address advances by one byte between outer iterations, independently of whether any bytes were copied.

If the endpoint is equal to or ordered below the current source address, that outer iteration copies nothing and leaves the source cursor unchanged. In particular, the allocator can modify the subsequently reread width; the original 16-bit header width does not constrain later width reads.

The strict less-than condition is established. The exact behavior of overflowing address addition, pointer ordering across unrelated regions, and invalid address formation is not independently established by this static body. No unconditional wraparound model is imposed here.

For stable width and stride, a positive count, valid accessible buffers, nonwrapping address calculations, and no aliasing that changes source data or controlling fields, the layout is transpose-like:

- Source offset: group number multiplied by width, plus position within the group.
- Destination offset: group number, plus position within the group multiplied by count.

Under those conditions, the group number ranges from zero through count minus one, and the position ranges from zero through width minus one. Without those conditions, this mapping is not a general guarantee.

### Final state initialization

After the outer loop terminates, including when it performs no byte copies, the function performs these actions in order:

1. Reads the associated-object address at output offset `0x9C` and writes 32-bit one at that object’s offset `0x04`.
2. Clears the 32-bit output field at `0x64`.
3. Reads the unsigned 16-bit header field at `0x54`.
4. Stores that value, zero-extended, at output offset `0x68`.
5. Stores the global value obtained during the terminal outer-loop condition evaluation at output offset `0x48`.
6. Reads the current dimension at output offset `0x50`, shifts it left six positions, and stores the result at `0x18`.
7. Reads the current width at output offset `0x4C`, shifts it left six positions, and stores the result at `0x1C`.
8. Stores the copied header value shifted left six positions at `0x24`.
9. Rereads the dimension, shifts it left six positions, and stores the result at `0x28`.
10. Clears the 32-bit field at `0x20`.
11. Calls F-6f91c5ea8ecb with the address of output offset `0x18` and a fresh width read shifted left six positions.
12. Rereads the local status for the low return part.

The final dependency’s return value is unused.

The scaled fields are 32 bits, not arbitrary-precision products. Original nonnegative dimensions and original 16-bit widths fit after scaling by 64. Mutations, negative signed operands, and target shift semantics require separate consideration; later field reads are not guaranteed to retain their initial values.

## Side effects

Explicit writes include partial output initialization, storage of the allocation result, individual destination-byte writes, associated-object modification, and final output-state initialization. The invalid-offset branch may also invoke a diagnostic dependency.

Allocation failure leaves the dimension, count, width, flag, and returned address already stored. Offset rejection leaves at least the dimension write. There is no explicit deallocation on any visible path.

Ownership of the allocation result is not established. Neither retention of the status address nor release obligations can be inferred from this caller alone. Safe use requires an external lifetime contract for any retained address.

Aliasing is not excluded. Destination stores may affect later source bytes, width reads, stride reads, header reads, or associated-object references. The function uses forward, byte-at-a-time accesses; it does not establish overlap-safe copying.

Dependencies are not assumed to preserve globals, output fields, referenced objects, or status storage. Memory faults, nonreturning calls, and other exceptional behavior are not converted into a defined status by the visible body.

## Acceptance examples

These examples are conditional static consequences, not executed tests.

1. **Default record selection.** With selector zero and header default-index byte four, index four is selected. The default byte is not decremented.

2. **Explicit first record.** Selector one selects index zero. Exact discriminator `0x0300` selects a six-byte record at displacement `0x94`; any other discriminator selects a four-byte record at displacement `0x76`.

3. **Extended offset decoding.** Extended offset bytes `34 12 00 00`, in increasing address order, produce offset `0x1234`, independently of native multibyte representation.

4. **Rejected boundary.** If the offset equals the upper-bound field, allocation is not attempted. After any enabled diagnostic returns normally, the low return part is `3`, the high part retains the resource-holder address, and the dimension write remains.

5. **Allocator failure.** With an accepted offset and allocator status nine, the low return part is nine and the high part is zero. The returned address is stored even if null. Rearrangement and final initialization are skipped.

6. **Stable positive transpose.** With dimension nine, unchanged width three, unchanged stride two, status zero, accessible disjoint buffers, and valid nonwrapping addresses, six consecutive source bytes are written to destination offsets `0, 2, 4, 1, 3, 5`, in that order.

7. **Zero count.** With dimension zero and allocation status zero, allocation is attempted but no bytes are copied. The global read, final initialization, and F-6f91c5ea8ecb call still occur, assuming all required accesses and calls complete.

8. **Zero reread width.** With a positive count and status zero, if the width read for an iteration is zero, its endpoint equals its current source address. That iteration copies nothing. Its source cursor remains unchanged, while the next destination starting address advances by one.

9. **Endpoint ordered below source.** If an allocator-modified width produces an endpoint ordered below the current source address under the target’s address rules, the strict comparison fails immediately. No source-byte read or destination-byte write occurs in that iteration, and the source cursor remains unchanged. Whether a particular overflowing addition produces that endpoint is `documented_only`.

10. **Null result with successful status.** A null allocation result is not independently rejected. If the inner comparison succeeds, a destination write is attempted through that result. If no comparison succeeds, copying alone does not dereference it; final initialization still requires its own valid accesses.
