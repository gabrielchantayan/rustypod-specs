# F-3a75ad37fd68

## Purpose

F-3a75ad37fd68 conditionally updates a destination object using a source object and four dependencies. Equal destination and source argument values bypass all object-memory accesses and dependency calls. Distinct values trigger preparation, replacement of a primary link, updates to two boundary fields, and a late copy of a trailing 32-bit object field.

The result is a packed 64-bit value. Its low half contains the destination argument; its high half contains a local state slot’s contents when the return value is constructed. The preparation dependency receives the address of that slot. Its contents are not necessarily fixed when preparation returns, because retention and later use of that address are unresolved.

**Inferred intent:** The field pattern is consistent with assignment of a header-based linked container. This interpretation does not establish a container type, traversal algorithm, element representation, ownership policy, or meaning for the trailing field.

## Interface

### Arguments

| Argument | Width | Established use |
|---|---:|---|
| Destination | 32 bits | Compared with the source, used to address destination storage, and placed in the result’s low half. |
| Source | 32 bits | Compared with the destination, initially placed in a local state slot, and used to address source storage on the distinct-address path. |
| Auxiliary value | 32 bits | Neither read nor forwarded by the visible function. |
| Preparation value | 32 bits | Copied into a local slot whose address is passed to F-8310debf75fb. |

The destination and source are address-like 32-bit values. The supplied representation does not establish portable native-pointer types or a source-level calling convention.

### Directly accessed memory layout

Each listed field is four bytes wide.

| Location | Structural name | Direct use |
|---|---|---|
| Object + `0x10` | Header reference | Locates header storage. |
| Object + `0x14` | Trailing field | Read from the source and written to the destination near completion. |
| Header + `0x04` | Primary link | Read from source storage; written and later conditionally read in destination storage. |
| Header + `0x08` | First boundary | Initially read from destination storage, then overwritten. |
| Header + `0x0c` | Second boundary | Overwritten in destination storage. |

These names identify positions, not established data-structure semantics. In particular, the trailing field is not established as a size or count. Dependencies may access other fields or unrelated storage.

### Result

The returned value has this numerical bit layout:

- Bits 0–31: the original destination argument’s 32-bit representation.
- Bits 32–63: the local state slot’s 32-bit contents when the return value is constructed.

The state slot initially contains the source argument. On the distinct-address path, it is overwritten with a destination header reference before its address is supplied to F-8310debf75fb.

For equal arguments, both halves therefore contain the same argument value. For distinct arguments, the upper half is neither an established status code nor necessarily a header reference.

This specifies bit placement, not memory byte order.

### Preconditions

On the distinct-address path, every directly accessed location must support the required four-byte read or write. Validity must hold at the time of each access, including accesses through header references reloaded after dependencies return.

Dependencies may impose additional requirements concerning representation, alignment, ownership, or lifetime. Those requirements are not supplied, and this function performs no visible validation of them.

On the equal-address path, the visible function does not require dereferenceable object storage. This does not establish requirements imposed by callers or the surrounding execution environment.

## Behavior

### Equality shortcut

The function initializes the local state slot with the source argument, then compares the destination and source argument values.

If they are equal, it constructs the packed result without accessing object storage or invoking a dependency. Neither the auxiliary value nor the preparation value affects this path.

This is exact 32-bit value equality. The function does not detect distinct addresses that refer to shared storage or represent the same logical object.

### Preparation

For distinct arguments, the visible order before the first dependency call is:

1. Read the destination header reference into the local state slot.
2. Read the destination header reference again, then read the first boundary at offset `0x08` through that reference into a separate local slot.
3. Copy the preparation value into another local slot.

The two destination header-reference reads are separate accesses. Stable storage makes their values equal; equality of those reads is not an unconditional guarantee.

F-8310debf75fb is then invoked with these arguments, in logical argument order:

1. Address of the local preparation-value slot.
2. Destination argument.
3. Address of the local boundary-value slot.
4. Address of the local state slot.

No return value from this dependency is consumed.

The dependency can modify the supplied local slots through their addresses. Only the state slot is subsequently read directly by this function. The boundary and preparation slots are not subsequently consulted directly, but this does not make their mutation or escape irrelevant to dependency behavior.

No preservation guarantee is established for object storage, shared state, header references, or any supplied local slot. In particular, the state slot’s contents immediately after this call are not necessarily its contents at return construction: the evidence does not exclude retention of its address and later writes through that retained address.

### Obtaining and installing the replacement primary link

After preparation returns, F-d9b87d7c419b is called with:

1. The destination argument.
2. The source primary link, obtained by reading the source header reference and then its field at offset `0x04`.
3. The destination header reference read after preparation.

The supplied representation does not establish the relative evaluation order of the independent source-derived and destination-derived arguments. The source header must be obtained before reading the primary link through it, and all argument values must be obtained before the invocation.

F-d9b87d7c419b returns a 32-bit value. After that call returns, the function reloads the destination header reference and writes the returned value to that header’s primary-link field.

The post-call reload determines the write target. If the dependency changed the destination header reference, this write can target a different header from the one passed to the dependency.

The function then selects a branch by testing the returned value for zero. It does not reread the installed primary-link field to make this decision.

### Zero replacement

When the replacement result is zero, the function:

- Writes a destination header reference into a destination header’s first-boundary field at offset `0x08`.
- Reads the destination header reference again.
- Uses that last-read reference as both the target header and stored value for the second-boundary write at offset `0x0c`.

The first-boundary assignment separately evaluates the destination header reference for its target and for its stored value. Their internal evaluation order is not established.

With stable, non-overlapping storage, these operations install zero in the primary link and the current header reference in both boundary fields. Unusual overlap can cause earlier writes to affect later header-reference reads.

Neither F-f7abac73474b nor F-08b7ebd3054b is called on this branch.

### Nonzero replacement

For any nonzero replacement result, the function performs this sequence:

1. Invoke F-f7abac73474b with no explicit arguments.
2. Reload the destination header reference.
3. Store that dependency’s 32-bit result in the first-boundary field.
4. Reload the destination header reference and read its primary link.
5. Invoke F-08b7ebd3054b with that freshly read primary-link value.
6. Reload the destination header reference after the call.
7. Store F-08b7ebd3054b’s 32-bit result in the second-boundary field.

F-f7abac73474b receives no explicit primary link, header, or object argument. Its inputs through ambient state and the meaning of its return value are unknown.

The argument supplied to F-08b7ebd3054b need not equal the earlier replacement result. F-f7abac73474b, aliasing writes, or other relevant effects may have changed the primary link before it is read.

Likewise, installation of the replacement result and first-boundary result does not guarantee that those values survive F-08b7ebd3054b. That dependency may modify either field even if it preserves the destination header reference.

Both boundary results are stored without validation. A zero boundary result is not treated locally as an error.

### Final copy and return construction

After either branch completes its second-boundary write, the function reads the source trailing field at offset `0x14` and writes that 32-bit value to the destination field at the same offset.

This source read occurs after every dependency invocation and after all three direct header-field writes. It is not an entry-time snapshot.

The function then constructs its packed result using the local state slot’s contents at that point. A value written into that slot during preparation reaches the upper half only if it remains the slot’s value until return construction.

There is no visible status validation, rollback, or consistency check between the trailing field and the installed structure.

## Side effects

### Direct writes and ordering

Every normally completed distinct-address execution performs four direct object-memory writes in this order:

1. Primary link at a destination header’s `0x04` offset.
2. First boundary at a destination header’s `0x08` offset.
3. Second boundary at a destination header’s `0x0c` offset.
4. Trailing field at the destination object’s `0x14` offset.

Dependencies can interleave additional effects between these writes. The three header writes need not target the same header, because their targets depend on separately obtained references.

These are write events, not unconditional final-value guarantees. Later dependencies or aliasing accesses can change fields already written.

### Aliasing

Only exact argument equality suppresses work. The function does not check for overlapping objects, shared headers, or overlap between header fields and object fields.

Consequences include:

- Earlier writes can change values read later.
- The final source trailing-field read can observe effects from earlier dependencies or direct writes.
- A boundary write can affect a later header-reference read under unusual overlap.
- The final trailing-field write can affect other logical fields if their storage overlaps.

Source preservation and final-field guarantees therefore require appropriate non-aliasing and dependency-preservation assumptions.

### Local storage and lifetime

Three local-slot addresses are exposed to F-8310debf75fb. Whether that dependency retains them, makes them accessible to later dependencies, or causes later writes through them is unresolved.

The slots are invocation-local storage, not established durable storage after return. No guarantee about safe post-return use follows from their exposure.

### Ownership and failures

The visible function performs no explicit allocation, release, or ownership-transfer operation. Dependencies may do so; allocation-free execution and preservation of existing destination contents are not established.

There is no explicit error result convention or recovery path. A zero replacement selects an ordinary branch, not an identified failure branch. Invalid accesses, dependency failures, and nonlocal exits have no specified recovery behavior here. Already performed writes have no visible rollback.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests.

### Equal arguments

For equal destination and source values of `0x12345678`:

- No object-memory access or dependency invocation occurs.
- The numerical result is `0x1234567812345678`.

The shortcut itself does not require that value to identify valid object storage.

### Zero replacement with stable storage

Assume distinct valid objects, no relevant overlap, a stable destination header reference H, and normal dependency return.

If F-d9b87d7c419b returns zero:

- The function installs zero in the primary link.
- It installs H in both boundary fields.
- Neither boundary dependency is invoked.
- The destination trailing field receives the source trailing value read after those writes.

Under these assumptions, with no other relevant modification, those installed header values remain at completion.

### Nonzero replacement: installation versus final state

Assume distinct valid objects, no relevant overlap, a stable destination header reference, and no external concurrent modification. Suppose:

- F-d9b87d7c419b returns nonzero R.
- F-f7abac73474b returns L and leaves the installed primary link unchanged.
- F-08b7ebd3054b returns U.

The supported sequence is:

- R is installed in the primary link.
- L is installed in the first boundary before F-08b7ebd3054b is called.
- F-08b7ebd3054b receives R.
- U is subsequently installed in the second boundary.

These assumptions alone do **not** establish that the final primary link is R or the final first boundary is L. F-08b7ebd3054b may change both while preserving the header reference.

If F-08b7ebd3054b additionally preserves the primary-link and first-boundary fields, the stated stability and non-overlap assumptions establish final header values R, L, and U respectively.

### Preparatory state mutation

Suppose F-8310debf75fb writes `0x89abcdef` into the supplied state slot. If that slot remains unchanged afterward until return construction and execution completes normally, the result’s upper half is `0x89abcdef`; the lower half contains the original destination.

Without the unchanged-slot condition, that write alone does not determine the upper half. For example, if a later dependency validly reaches the still-live slot through a retained address and changes it to `0x76543210`, which then remains unchanged, the upper half is `0x76543210`.

Mutating another supplied local slot does not directly supply return bits, but indirect dependency effects remain unspecified.

### Header replacement

If F-d9b87d7c419b changes the destination header reference before returning, its result is written through the reloaded reference, assuming the resulting access is valid. An implementation that always uses the pre-call header would not preserve this behavior.

### Unused auxiliary value

Holding other inputs and external behavior fixed, changing only the auxiliary value changes no visible operation of this function. It is not forwarded to a dependency.

## Evidence
