# F-401f74d2d000

## Purpose

F-401f74d2d000 processes one acquired event-like object against a state object obtained from the current context. For a non-null event payload, it conditionally updates three 32-bit state fields, places the acquired object into an auxiliary record, invokes several downstream operations, and submits a separately constructed object. It then performs a common final state check.

If the acquired object has a null payload, the function instead invokes that object's virtual operation at byte offset 4 and proceeds directly to the common final check.

These are structural descriptions. Event names, field meanings, synchronization semantics, and ownership-transfer rules are not established by the supplied source.

## Behavior

### 1. Acquire the working objects

The observable call and read sequence begins as follows:

1. Call F-605cb486b37f and retain its result as the context address.
2. Call F-0a77364c41cc with the value 12.
3. Pass that result, the first opaque descriptor, and zero to F-afb630a7107c. Retain its result as the acquired-object address.
4. Read the state-object address from context offset 4.
5. Call F-338d16f9ce72 with the address of state offset 268.
6. Read the payload address from acquired-object offset 8.

The state pointer is read after the first construction sequence, not immediately after obtaining the context. The payload is read after the operation on state offset 268. Those dependencies can therefore affect memory observed by subsequent reads; their preservation behavior is not established.

### 2. Handle an absent payload

If the payload address is zero:

- If the acquired-object address is nonzero, read its virtual-table address and invoke the entry at table byte offset 4, passing the acquired object.
- Skip all event-identifier handling, auxiliary-record construction, and second-object submission.
- Continue to the common final check.

The acquired-object null check does not make a null acquired-object result safe: the offset-8 payload read has already occurred.

The virtual operation might be cleanup, but its release or destruction semantics are not established.

### 3. Dispatch a present payload

Read the signed 32-bit event identifier from payload offset 4. Dispatch first compares it with T:

- Equality with T takes precedence over every literal event value and writes 1 to field A.
- Otherwise, an identifier below T is eligible only for the lower-branch cases.
- An identifier above T is eligible only for the upper-branch cases.

A literal value appearing in the following tables is not an unconditional handler. Its relationship to T must select the corresponding branch.

#### Lower-branch cases: identifier less than T

| Identifier | Direct behavior |
|---|---|
| 0x6600000D | Write 0 to field B, then write 0 to field A |
| 0x66000014 | Perform the increment operation described below |
| 0x66000015 | Perform the conditional decrement operation described below |
| 0x66000017 | Write 0 to field B, then write 0 to field A |
| Any other value | No direct write to fields A, B, or C in dispatch |

**Increment operation**

Read field B and compare it with −1.

- If it equals −1, call F-87be4aa684d1, use the returned object's virtual-table entry at byte offset 364 / 0x16C, and store the returned 32-bit value into field B.
- Then read field B, add 1, and write the result to field B.

The increment is not conditioned on the fetched value becoming nonnegative. A fetched value of −1 is stored and then becomes 0. The lazy-fetch store and increment store are distinct observable writes.

**Conditional decrement operation**

Read field B and compare it with −1.

- If it equals −1, use the same dependency and virtual-table slot as the increment operation, then store the returned 32-bit value into field B.
- Read field B again.
- If the value is strictly positive under signed comparison, subtract 1 and store the result.
- Otherwise, perform no decrement write.

Consequently, a zero or negative fetched result remains in field B after the initial store. Without a fetch, an existing nonpositive value is left unwritten by this operation.

#### Upper-branch cases: identifier greater than T

| Identifier | Direct behavior |
|---|---|
| 0x6600001A | Write 0 to field A |
| 0x6600001B | Perform the field-A toggle operation described below |
| 0x66000024 | Copy one 32-bit value through the pointer at payload offset 12 into field C |
| Any other value | No direct write to fields A, B, or C in dispatch |

**Field-A toggle operation**

Read field A.

- If it is −1, call F-87be4aa684d1 and invoke the returned object's virtual-table entry at byte offset 396 / 0x18C. Use that operation's signed 32-bit result as the candidate value.
- Otherwise, use the original field-A value as the candidate.
- Candidate 1 causes a write of 2 to field A.
- Candidate 2 causes a write of 1 to field A.
- Every other candidate causes no direct field-A write.

Unlike field B's lazy fetch, this fetched candidate is not first stored into field A. If field A starts at −1 and the operation returns 0, this function does not directly replace field A with 0.

**Field-C copy**

Read the pointer stored at payload offset 12, read a 32-bit value from its target, and write that value to field C. This is an indirect value copy, not a copy of the pointer itself. There are no visible null checks on either level.

### 5. Perform the common final check

Both payload paths converge on the following behavior:

- Read a pointer from state offset 268.
- If it is null, return.
- Otherwise, read its first 32-bit word.
- If that word is zero, return.
- Otherwise, invoke the target held in the final opaque global, then return if that invocation returns.

This is a fresh read of state offset 268 after preceding calls. It is not a decision based on a pointer cached before dispatch.

## Side effects

### Direct state and memory writes

The direct writes visible in this function are:

- Field A: 0, 1, or 2 on selected paths.
- Field B: zero, a fetched value, or an incremented/decremented value.
- Field C: the indirectly loaded 32-bit value.
- Auxiliary-record offset 4: the acquired-object address.

Write order matters. In particular, reset events write B before A, and a lazy field-B fetch is written before the arithmetic result.

Dependencies and virtual operations may perform additional writes, alter globals, or affect pointed-to objects. Their effects cannot be excluded from postconditions.

### Arithmetic limits

Field-B arithmetic uses the signed 32-bit representation shown in the source.

- The increment has no explicit upper-bound check.
- Incrementing 2,147,483,647 exceeds the signed 32-bit range. The supplied material does not establish whether the executable wraps or has another source-level interpretation; no saturation or explicit overflow error is present.
- The decrement is performed only after a strictly-positive signed comparison, so the subtraction itself cannot underflow the signed 32-bit range.

### Ownership and failures

The acquired-object address is retained in an auxiliary record on the present-payload path. This establishes pointer storage and subsequent passing of the record, not a proven ownership transfer.

There is no explicit release of the acquired object on that path. The null-payload virtual operation cannot be asserted to release it without its own contract. Likewise, the lifetimes of both 12-byte construction results, the eight-byte record, and the second constructed object remain unspecified.

No visible allocation-failure handling, rollback, retry, or status propagation exists. If a dependency fails to return normally, later operations are not guaranteed to occur, and earlier writes are not visibly undone.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed tests. Direct-write expectations exclude additional effects of unknown dependencies.

1. **Null payload:** Given valid context and acquired-object memory, with acquired-object offset 8 equal to zero, invoke its offset-4 virtual operation. Do not construct the eight-byte record or second object. Then evaluate the final state-offset-268 check.

2. **Threshold equality overrides a reset literal:** If T equals 0x6600000D and the event has that identifier, write 1 to field A. Do not execute the lower-branch B-then-A reset.

3. **Reset ordering:** If 0x66000017 is less than T and is the event identifier, write B = 0 before A = 0, then execute the full present-payload downstream sequence.

4. **Increment without lazy fetch:** If 0x66000014 is less than T and B initially equals 7, do not call F-87be4aa684d1 for dispatch. Write B = 8.

5. **Increment after lazy fetch:** Under the same event gate, if B starts at −1 and the virtual operation returns 5, write B = 5 and subsequently B = 6.

6. **Decrement boundaries:** If 0x66000015 is less than T, an existing B of 1 becomes 0; an existing B of 0 receives no dispatch write. If B starts at −1 and the fetched value is −3, write −3 but do not decrement it.

7. **Toggle with a fetched non-toggle value:** If 0x6600001B is greater than T, A starts at −1, and the virtual operation returns 0, perform no direct write to A. If it returns 2 instead, write A = 1.

8. **Indirect field-C copy:** If 0x66000024 is greater than T and payload offset 12 points to a readable word containing 0x89ABCDEF, write that 32-bit pattern to C.

9. **Unrecognized present event:** If the identifier is unequal to T and matches no literal in its selected branch, perform no direct dispatch field writes, but still execute the complete present-payload downstream sequence.

10. **Final check observes later state:** If a preceding dependency changes state offset 268 to null, the final check returns without invoking the global target. A non-null pointer whose first word is zero likewise suppresses that invocation.
