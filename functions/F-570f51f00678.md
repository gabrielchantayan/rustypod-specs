# F-570f51f00678

## Purpose

F-570f51f00678 performs a position-dependent extraction through an object's indirect operations. It obtains an initial four-byte discriminator, selects one of two layouts, and then obtains:

- A four-byte field.
- An eight-byte result, either read directly or constructed by sign-extending a four-byte field.
- A final two-byte field.

The function returns a 32-bit status: zero only when every required operation reports the exact expected result; one otherwise.

The established behavior is an ordered sequence of indirect calls and output writes. Interpreting the indirect operations as seeking and reading, or the fields as a particular file format, is inferred intent rather than an independently established dependency contract.

## Interface

The function has seven argument positions. All scalar argument slots and pointer representations in the supplied evidence use a 32-bit model.

| Position | Contract role | Width and use |
|---|---|---|
| 1 | Unused argument | One 32-bit value. No explicit use or dereference is shown. |
| 2 | Operation-bearing object | Pointer to an object whose first 32-bit word identifies an operation table. |
| 3 | Position low word | Unsigned 32-bit value used in the initial positioning request. |
| 4 | Position high word | 32-bit value checked as signed, then used in unsigned position arithmetic. |
| 5 | Four-byte destination | A 32-bit address-like value forwarded as a destination to an indirect operation. |
| 6 | Eight-byte destination | Pointer to storage used either for two explicit 32-bit stores or an indirect eight-byte transfer. |
| 7 | Two-byte destination | A 32-bit address-like value forwarded as a destination to an indirect operation. |

The operation table contains callable entries at byte offsets 16 and 20. These are described under **Dependencies** using specification-local opaque function IDs.

### Preconditions

For ordinary completion rather than a memory-access or indirect-call fault:

- The object and its operation table must be readable whenever accessed.
- Each operation-table entry used must identify a callable operation with the required calling convention.
- Each destination must satisfy the access, size, alignment, and lifetime requirements of the operations that receive it.
- The eight-byte destination must permit explicit 32-bit stores at byte offsets zero and four when the compact layout is selected.
- The indirect transfer operation must populate the requested destination consistently with its reported result if meaningful extracted values are required.

The function performs no explicit null, bounds, alignment, or callable-target validation. These preconditions are not converted into a status-one failure by any visible validation.

No non-aliasing requirement is enforced. Overlapping destinations, or destinations overlapping the object or operation table, can affect later calls and final contents. Stable-object, disjoint-buffer examples below are therefore conditional cases, not guarantees for arbitrary aliases.

### Return value

- **0:** All required positioning requests returned zero, and all transfer requests returned exactly their requested byte counts.
- **1:** The initial signed-high-word check failed, a positioning request returned nonzero, or a transfer request returned a value other than the exact required count.

The function does not propagate an indirect operation's original error value. Faults, exceptions, or other nonlocal behavior of dependencies are not shown being caught.

## Behavior

### 1. Validate the supplied high word

The fourth argument is interpreted as a signed 32-bit integer for the initial check.

If bit 31 is set, the function returns one immediately. It performs no indirect calls and no explicit destination writes on this path.

Otherwise, it initializes a private four-byte temporary from that argument and proceeds.

This check applies to the original high word. There is no second signed-range check after position adjustment.

### 2. Request the initial position

The function invokes the operation at table offset 20 with these five argument roles:

1. The object.
2. A callable-address value obtained from that same operation-table slot.
3. The original low word plus eight, reduced modulo \(2^{32}\).
4. The original high word plus a carry, reduced modulo \(2^{32}\).
5. The value zero.

The carry is one exactly when the original low word is greater than `0xfffffff7`; otherwise it is zero. Thus the pair of adjusted words represents addition of eight to the supplied two-word position.

The call target and the callable-address argument are expressed through separate accesses to the slot. The evidence does not establish a relative evaluation order for those accesses or an atomic snapshot of the table. With a stable table, they identify the same entry.

If this operation returns anything other than zero, the function returns one without attempting the initial transfer.

### 3. Obtain the discriminator

After a zero result from the initial positioning operation, the function invokes the operation at table offset 16 with:

- The object.
- The address of the private four-byte temporary.
- A requested count of four.
- A final argument of one.

Only a reported result of exactly four permits further processing. Any other result causes return one.

The private temporary is the discriminator storage. Assuming the dependency writes four bytes as expected, those bytes replace the earlier high-word initialization. The function does not itself verify that a dependency reporting four actually wrote those bytes.

After this transfer succeeds, the function retrieves and retains the current operation-table entry at offset 20. That retained entry supplies both the call target and callable-address argument for the next positioning operation.

### 4. Select a layout

The function tests the upper eight bits of the discriminator's native 32-bit value:

- If those bits are all zero, it selects the **compact layout**.
- Otherwise, it selects the **wide layout**.

This is a mask test against `0xff000000`. It is not a signedness test. For example, `0x01000000` selects the wide layout even though its signed 32-bit interpretation is positive.

The discriminator selects the layout only. It is not copied into a caller destination as an output field.

### 5. Process the compact layout

The retained positioning operation is invoked with:

- The object.
- The retained callable address.
- A low displacement word of eight.
- A high displacement word of zero.
- A final argument of one.

A nonzero result causes immediate return one.

On a zero result, the function performs these actions in order:

1. Request a four-byte transfer into the destination in argument position five, with final argument one.
2. Require the returned count to equal four; otherwise return one.
3. Request a four-byte transfer into the private temporary, with final argument one.
4. Require the returned count to equal four; otherwise return one.
5. Store the temporary's 32-bit value into the first word of the eight-byte destination.
6. Store its sign-extension word into the second word of that destination.

The second stored word is zero when the temporary's bit 31 is clear and `0xffffffff` when it is set.

The two output stores are ordered: the low word is stored first, then the sign-extension word. They are not an atomic eight-byte write.

The initial discriminator's upper-byte restriction does not constrain this later four-byte value. A compact-layout extracted value may therefore be negative when interpreted as signed 32-bit.

### 6. Process the wide layout

The retained positioning operation is invoked with:

- The object.
- The retained callable address.
- A low displacement word of sixteen.
- A high displacement word of zero.
- A final argument of one.

A nonzero result causes immediate return one.

On a zero result, the function:

1. Requests a four-byte transfer into the destination in argument position five, with final argument one.
2. Requires a returned count of exactly four.
3. Requests an eight-byte transfer directly into the destination in argument position six, with final argument one.
4. Requires a returned count of exactly eight.

A count mismatch at either transfer causes immediate return one.

Unlike the compact layout, the wide layout does not explicitly decode, sign-extend, or rewrite the eight-byte result after the transfer.

### 7. Obtain the final field

After either layout has completed its earlier operations successfully, the function requests a two-byte transfer into the destination in argument position seven, with final argument one.

It returns zero only if this call reports exactly two. Otherwise it returns one.

No subsequent operation is shown.

## Side effects

### Ordered external operations

For a normally completing compact-layout success, the externally relevant sequence is:

1. Initial positioning request.
2. Four-byte transfer into private storage.
3. Compact-layout positioning request.
4. Four-byte transfer into the first caller destination.
5. Four-byte transfer into private storage.
6. Explicit low-word store to the eight-byte destination.
7. Explicit sign-extension-word store to that destination.
8. Two-byte transfer into the final destination.

For a wide-layout success, the corresponding sequence is:

1. Initial positioning request.
2. Four-byte transfer into private storage.
3. Wide-layout positioning request.
4. Four-byte transfer into the first caller destination.
5. Eight-byte transfer into the second caller destination.
6. Two-byte transfer into the final destination.

Each indirect transfer obtains its callable entry from the object's then-current table. The function does not retain one transfer entry for the whole invocation.

The second positioning entry is obtained after the discriminator transfer, not necessarily from the same table or target used for the initial positioning request.

### Failure is not transactional

There is no explicit rollback of destination contents or object state.

Consequently:

- A failed transfer may already have modified its destination.
- A successful first field can remain written when a later operation fails.
- The compact-layout eight-byte result remains explicitly written if the final two-byte transfer fails.
- A failed wide-layout eight-byte transfer may leave a partially modified eight-byte destination.
- Positioning or transfer operations may leave object state changed even when the function returns one.

A status-one result therefore does not imply unchanged outputs.

### Ownership and lifetime

The function contains no explicit allocation, deallocation, ownership transfer, or resource-release operation. It supplies caller destinations and a private temporary to indirect operations.

The evidence does not establish whether those dependencies retain pointers, release resources, alter global state, or modify the object. Such behavior must not be excluded merely because it is absent from the visible caller.

The private temporary has invocation-local storage. Safe synchronous use is consistent with the call pattern; dependency retention of its address would require a separate lifetime contract not present here.

## Acceptance examples

These examples are conditional on callable dependencies returning normally and providing the stated results. They are behavioral acceptance cases, not executed tests.

### Rejection before any dependency call

Given a high word of `0x80000000`, the function returns one. The supplied low word and output destinations do not affect that decision.

The same applies to every high word with bit 31 set.

### Position adjustment without carry

Given low word `0x00000020` and high word zero, the initial positioning request receives low word `0x00000028`, high word zero, and mode zero.

If that operation returns nonzero, no transfer is attempted.

### Position adjustment across the low-word boundary

Given low word `0xfffffff8` and high word seven, the initial positioning request receives low word zero and high word eight.

Given low word `0xfffffff7`, no carry is added; the adjusted low word is `0xffffffff`.

### High-word sign boundary after adjustment

Given high word `0x7fffffff` and low word `0xfffffff8`, the initial check passes. The adjusted positioning words are low zero and high `0x80000000`.

The function makes the call; it does not reject the adjusted high word for becoming negative under signed interpretation.

### Compact-layout sign extension

Assume:

- The discriminator transfer reports four and supplies numeric value `0x00ffffff`.
- Both positioning operations report zero.
- The first caller-destination transfer reports four.
- The compact value transfer reports four and supplies `0x80000001`.
- The final transfer reports two.

The function returns zero. It explicitly stores `0x80000001` into the first word of the eight-byte destination and `0xffffffff` into the second.

For a compact value of `0x7fffffff`, the second stored word is zero.

### Wide-layout selection

A discriminator value of `0x01000000` selects the sixteen-unit positioning request and the direct eight-byte transfer path.

If the two positioning results are zero and the transfer results are four, four, eight, and two in order, the function returns zero.

### Exact-count failure

If a four-byte transfer reports three or five, the function returns one. Neither result is accepted as sufficient.

Similarly, a reported count of seven or nine fails an eight-byte request.

### Failure after completed outputs

Assume the compact path completes both explicit stores to the eight-byte destination, then the final two-byte transfer reports one.

The function returns one. It does not undo the earlier four-byte destination transfer or either explicit store.
