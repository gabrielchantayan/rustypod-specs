# F-4944ce526800

## Purpose

F-4944ce526800 changes one bit in a selected record’s 32-bit mask, updates that record’s activity indicator, and consults external dependencies before choosing a final notification.

Its direct behavior has two possible endings:

- A reset status causes the masks of records 0, 1, and 2 to be cleared, followed by notification value 1.
- Any other status causes the activity indicators of those three records to be inspected, followed by notification value 3 when activity is observed or 2 otherwise.

“Mask,” “activity,” “status,” and “notification” are descriptive contract terms. Their application-level meanings are inferred rather than established by the supplied evidence.

The contract distinguishes direct record operations from dependency effects. In particular, the final decision need not reflect only the record changes made by this function: the consultation dependencies run before that decision and have no supplied preservation guarantees.

### Validity requirements

A record selector greater than 2 is rejected through F-a817d8d58c10 before any direct record access. The comparison is signed. Negative values are not rejected.

A selector from 0 through 2 keeps the selected-record operations within the nominal three-record region, provided the supplied base and storage are valid. A negative selector instead requires accessible storage before that region.

For a normally completing invocation:

- The selected flags and mask fields must be readable and writable.
- Ordinary completion requires readable flags fields for records 0, 1, and 2.
- Reset completion requires writable mask fields for those three records.
- Record-address calculations must produce valid addresses without relying on unresolved arithmetic behavior.

The represented address calculations use signed 32-bit quantities, including the record-stride multiplication and address additions. No overflow check is present. Signed arithmetic does not establish modular wraparound. Alignment requirements, invalid-address behavior, and the actual target’s address interpretation remain unresolved.

### Bit-selection limits

Only the low eight bits of the bit selector determine the effective shift count. Thus, for example, selectors 3 and 259 supply the same count.

The one-bit quantity is formed by shifting a signed integer value of one; the unsigned destination does not change the type of that operation. Under a 32-bit signed-integer source-level interpretation:

- Counts 0 through 30 yield representable one-bit values.
- Count 31 exceeds the representable positive range of the signed result.
- Counts 32 through 255 exceed the permitted shift-count range.

The unambiguous mask-update contract therefore applies to effective counts 0 through 30. Actual target behavior outside that range is **documented_only**. The evidence does not establish rejection, hardware count masking, a particular resulting bit, or any other machine-level outcome.

## Behavior

### Selection and rejection

The selector check precedes all direct record reads and writes. When the signed selector exceeds 2, the function calls F-a817d8d58c10 without explicit arguments. That dependency is identified as non-returning.

Neither its termination mechanism nor its diagnostic behavior is supplied. A continuation following an unexpected return is not an established part of this contract.

All remaining behavior assumes the selector takes the continuing path and the required arithmetic and accesses are valid.

### Selected-record state transition

The selected record’s activity indicator is cleared before its mask is changed. This is an actual flags write even when bit 0 was already clear, and even when activity will immediately be restored.

The mask change affects one bit: a zero enable selector clears it, while any nonzero enable selector sets it. Negative enable values therefore request setting. For an effective count within the established range, every other mask bit is preserved.

Activity is then determined from the entire updated mask, not merely from the bit just changed:

| Updated selection mask | Directly established activity state | Consultation payload |
|---|---|---|
| Zero | Bit 0 clear | Zero |
| Nonzero | Bit 0 set | Selected flags with bit 0 set |

Upper flags bits are preserved from the initial flags read. When activity is restored, the function does not reread the flags field. Its restoring write uses the previously captured upper bits. Consequently, an intervening external change to those bits is not guaranteed to survive that write.

A zero mask leaves the consultation payload zero even if the selected flags retain nonzero upper bits.

The observable selected-record access order is a flags read and clearing write, then a mask read and updated-mask write, followed by a second flags write only when the updated mask is nonzero. These accesses precede the consultation calls.

The call sites do not establish input-only, output-only, or bidirectional parameter contracts. They likewise do not establish whether either dependency changes the record region or global state.

### Status decision

The first 32-bit status element undergoes character-width conversion for comparison with values 1 and 2. This is a conversion of the element’s value, not evidence of a separate read from a particular byte address.

Under the represented eight-bit truncating interpretation, the low eight bits determine whether reset is selected:

- Values converting to 1 or 2 select reset.
- Every other converted value selects ordinary handling.

If the dependency leaves the initial value 4 unchanged, ordinary handling follows.

Character signedness does not change equality with representable values 1 and 2. However, the evidence does not independently establish a target-language rule for every out-of-range conversion to a signed character type. Examples depending on truncation of a larger status value are conditional on that interpretation.

### Ordinary completion

Ordinary handling samples the 32-bit flags of records 0, 1, and 2 in ascending record order. All three reads occur; observing activity in an earlier record does not suppress later reads.

Only bit 0 of the combined observations affects the final notification:

| Activity observed in the three samples | Argument to F-1b765582ee90 |
|---|---:|
| None | 2 |
| At least one | 3 |

Upper flags bits do not affect that choice. The branch makes no additional direct record writes.

These samples occur after both consultation dependencies return. They can therefore observe dependency changes. They are also separate reads, not a guaranteed simultaneous snapshot.

### Reset completion

Reset handling writes a 32-bit zero to the selection masks of records 0, 1, and 2, in that order. It then calls F-1b765582ee90 with value 1.

Reset does not directly clear any flags field. In particular, activity restored during the selected-record update may remain set after the corresponding mask has been cleared. The function provides no final reconciliation between masks and flags.

If the notification dependency returns, the function returns without an explicit result.

## Side effects

### Ordering and visibility

For the continuing path, the direct record update finishes before F-b9d333145f3e is called. That call finishes before F-ca2888499290 is invoked. The subsequent status decision precedes either the three flags samples or the three mask-clearing writes. The final notification follows those branch-specific accesses.

This ordering is static evidence about the represented operations. It establishes no lock, atomic read-modify-write, memory barrier, or concurrency protocol.

The temporary clearing of activity is part of the represented write sequence. The contract does not promise that an asynchronous observer can or cannot see it.

### Ownership and lifetime

The record storage is caller-designated. No allocation, deallocation, or explicit ownership transfer is shown.

The payload and status storage belong to the current invocation. Their addresses are passed to F-ca2888499290. That fact alone establishes neither permission to retain the addresses nor safe access after the invocation ends.

No dependency may be assumed to preserve globals, refrain from accessing other reachable memory, or own or release any resource.

### Failures and partial completion

The function has no shown rollback or error-recovery path.

Selected-record changes already precede consultation. If a consultation dependency fails to return, those earlier writes are not undone by any shown operation.

Likewise, reset writes precede the final notification. Notification failure or non-return does not imply reversal of the reset.

Invalid memory, arithmetic outside the established range, and dependency failures have no supplied recoverable-error contract. The absence of an explicit result prevents the caller from interpreting normal return as a separately reported success status.

These examples are conditional static acceptance cases, not executed tests. Unless a case states otherwise, they assume valid storage and arithmetic, effective counts from 0 through 30, returning dependencies, and no dependency modification of the record region.
