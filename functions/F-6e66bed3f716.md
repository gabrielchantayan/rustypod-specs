The direct writes occur at the points specified; they are not necessarily final-state guarantees after subsequent dependency calls.

Registry operations use the retained registry base. A dependency that changes the shared location from which that base was obtained does not thereby establish that later registrations use a newly published base.

No explicit deallocation, reference-count adjustment, rollback, lock acquisition, or exception handling appears. Ownership of Object, node storage, allocation results, registration results, and the returned address is undocumented. Passing or storing an address does not by itself prove ownership transfer.

The guard is written before registration completes. An interrupted or failing initialization can therefore leave a set guard and a partially populated registry. The function contains no visible recovery path for that condition.

Concurrent or reentrant initialization is not shown to be safe. In particular, a reentrant invocation can observe the set guard before the outer invocation has completed its registrations.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests.

1. **Registry already populated at slot zero.**  
   Given a nonzero slot-zero value when the condition is evaluated, the function skips all 27 allocation requests and registrations. It does not read the guard byte for that condition. The final initialization call still occurs.

2. **Guard set while slot zero is empty.**  
   Given a zero slot-zero value and any nonzero guard byte, the registry block is skipped. The function does not attempt to repair or complete the registry.

3. **Initialization permitted.**  
   Given a zero slot-zero value and zero guard byte, the first direct effect of the registry block is setting the guard to 1. Allocation and registration then follow the exact order above.

4. **High-bit registry index.**  
   If a registration result exposes byte value 0xFE at offset 0xB4, its slot is at registry base + 0x3F8. The byte is unsigned; it is not interpreted as −2. Successful execution requires that destination to be writable.

5. **Duplicate indices.**  
   If two registrations produce the same index, the later registration writes its result over the earlier value. Assuming no intervening dependency changes that slot, the later value remains until another write changes it.

6. **Derived return differs from Object.**  
   If Second structure is 0x1070, Result address is 0x1000. Both the first argument to F-8cfdbb54e05e and the function’s return value are 0x1000, regardless of whether Object has that address.

7. **Allocation failure.**  
   If F-8157a180d901 returns zero, there is no caller-side early return or error conversion. Execution proceeds to the corresponding registration dependency with the arguments established above. The resulting outcome depends on that dependency and subsequent address validity.
