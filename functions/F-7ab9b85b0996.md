# F-7ab9b85b0996

## Purpose

F-7ab9b85b0996 implements a stateful acquisition operation with two paths:

- When the context’s state byte is nonzero, it reports success without performing the allocation-and-transfer sequence.
- When the state byte is zero, it obtains a length, checks that length against a limit, requests an allocation, and requires a transfer operation to report both success and an exact count.

Every ordinary return follows a finalization call on temporary working state. Failure additionally invokes a release dependency and clears selected context fields and both outputs.

**Inferred intent:** the context appears to cache an acquired resource or payload. The nonzero state byte appears to indicate that acquisition has already completed. These meanings are not established by the dependency implementations. In particular, the value written to the first output on fresh success is not directly the allocation result, and the already-marked path writes zero to that output.

## Interface

### Arguments and return

The function takes three pointer arguments:

| Argument | Observable use |
|---|---|
| Context pointer | Supplies configuration and mutable state through fixed offsets. |
| First output pointer | Receives one 32-bit value. |
| Second output pointer | Receives one 32-bit value, normally the context’s length field. |

The return value is 32 bits:

- **1:** an ordinary success path completed.
- **0:** an ordinary failure path completed.

These are control-flow results, not a guarantee that the finalization dependency succeeded internally. Its return value is not inspected.

### Context layout

Offsets are byte offsets from the context pointer. Four-byte fields have the target representation and byte order, which are not independently established here.

| Offset | Width | Role established by use |
|---|---:|---|
| +0 | 32 bits | Value passed to temporary-state initialization. |
| +4 | 8 bits read | Character-valued configuration passed to initialization after integer conversion. |
| +8 | 32 bits | Upper bound used in an unsigned comparison against the length. |
| +12 | 32 bits | Allocation result or resource value; overwritten after allocation and passed to release on failure. |
| +16 | 32 bits | Length/result field supplied by address to one dependency, checked against the limit, and used by later operations. |
| +20 | 8 bits | State marker: zero selects acquisition; nonzero selects the already-marked success path. |

Only the byte at +4 is read from the four-byte region beginning there. Only the byte at +20 is directly written by this function at that location; adjacent bytes are not explicitly cleared or set.

The context therefore requires accessible storage through byte +20. The output destinations each require writable four-byte storage on ordinary returning paths.

### Preconditions and ownership boundary

There are no explicit null-pointer, alignment, accessibility, or overlap checks.

For the straightforward behavior described below, callers must provide valid context and output storage, with output destinations separate from the context and from each other. Overlapping arguments are not rejected, but they expose the exact write order and can change subsequent reads.

The function does not establish:

- Who originally owns the value at context offset +12.
- Whether that value is valid for the release dependency.
- Whether the allocation result and the first output refer to related storage.
- Whether any dependency retains pointers or changes externally reachable state.

Those properties require dependency contracts.

## Behavior

### 1. Temporary initialization occurs on every invocation

The function first initializes its provisional first-output value to zero.

It then invokes **F-3fc3239fa339** with:

1. A pointer to temporary working storage.
2. The 32-bit context value at +0.
3. The integer value 1.
4. The character value read at +4, converted to an integer.
5. The integer value 1024.
6. The integer value 1.
7. The integer value 0.

Initialization occurs before the state marker at +20 is tested. Consequently, an already-marked context does not bypass initialization or its side effects.

The character’s signedness is not established. Values whose high bit is clear have an unambiguous nonnegative conversion; values with the high bit set require target character-signedness information.

A temporary status location is subsequently tested on the acquisition path. The supplied material does not show a separate explicit assignment to that location. Its initialization appears to depend on the initialization operation or on the actual layout of its working storage.

### 2. Nonzero marker: already-marked success

If the marker read after initialization is nonzero:

1. The function writes zero to the first output.
2. It reads the current 32-bit length at context +16 and writes that value to the second output.
3. It writes the byte value 1 to context +20.
4. It invokes **F-a19c2808de87** on the temporary working storage.
5. It returns 1.

This path does not explicitly inspect the temporary status, obtain a new length, compare the length with the limit, allocate, transfer, or release the stored allocation value.

Any nonzero marker is accepted, not just 1. The function’s own marker write normalizes it to 1 before finalization.

### 3. Zero marker: acquisition gates

When the marker is zero, acquisition proceeds only while each gate succeeds, in this order:

1. The temporary status value must equal zero.
2. **F-5c1bc43ac1f8** is called with the temporary working storage and the address of context +16. Its return must equal zero.
3. The current 32-bit length at +16 must be less than or equal to the current 32-bit limit at +8, using an **unsigned** comparison.

A failed gate skips the remaining acquisition operations and enters common failure handling.

The length dependency receives the actual context field by address, not a separate staged result. Its writes can therefore remain visible even if a later gate fails, until common failure handling explicitly clears that field.

A length equal to the limit is accepted. The comparison itself does not impose a positive minimum length.

### 4. Allocation request

After the gates pass:

1. **F-9b3e7c03cf13** is called with no arguments.
2. Its 32-bit result is added to the current 32-bit length at context +16.
3. The resulting 32-bit value is passed to **F-fab3799b3190**.
4. That dependency’s 32-bit result is stored immediately at context +12.
5. A zero result selects common failure handling; a nonzero result continues.

There is no explicit overflow check, widened allocation-size check, or comparison between the calculated allocation request and the context limit. The established limit check covers the length alone.

At the represented 32-bit arithmetic level, the allocation request is the low 32 bits of the sum. For example, an addend of 4 and a length of 4,294,967,295 produce a request value of 3. Whether such a request can succeed, or whether it is safe for subsequent operations, is not established.

An existing value at context +12 is overwritten without an explicit preceding release when this allocation call is reached. Conversely, failures before this overwrite pass the preexisting value to common failure handling.

### 5. Transfer and exact-count requirement

For a nonzero allocation result:

1. **F-3cb5472b4a81** is called with no arguments.
2. Its 32-bit result becomes the provisional value for the first output.
3. **F-8737e491f1cd** is called with:
   - The temporary working storage.
   - The current 32-bit length at context +16.
   - The result from F-3cb5472b4a81.
   - The address of a temporary 32-bit count/result location.

The represented transfer result occupies 64 bits, but only its low 32 bits are used as the status test.

Fresh acquisition succeeds only if:

- The low 32 bits of the transfer result are zero; and
- The temporary 32-bit count equals the length read from context +16 after the transfer call returns.

The high 32 bits of the transfer return do not determine acceptance. The count comparison is equality of 32-bit values, without a separate range or sign check.

The requested length is read before the transfer call, while the length used for the final equality test is read afterward. The function does not preserve an independent immutable copy for that comparison. If a dependency can mutate the context indirectly, the requested and compared lengths need not be identical.

A zero-length acquisition can pass: it still requires a nonzero allocation result, zero transfer status, and a reported count equal to zero, subject to any intervening context changes.

### 6. Fresh-success completion

After a successful transfer and count comparison:

1. The provisional value returned by F-3cb5472b4a81 is written to the first output.
2. The current length at context +16 is read and written to the second output.
3. The state byte at context +20 is written as 1.
4. F-a19c2808de87 is invoked on the temporary working storage.
5. The function returns 1.

The allocation result remains at context +12 unless a dependency or an overlapping output write changes it. The function does not explicitly release it on this success path.

### 7. Common failure handling

Every ordinary acquisition failure reaches this sequence:

1. Read context +12 and pass that value to **F-58ba61416cc9**.
2. Write 32-bit zero to the first output.
3. Write 32-bit zero to context +12.
4. Write 32-bit zero to the second output.
5. Write 32-bit zero to context +16.
6. Write byte zero to context +20.
7. Invoke F-a19c2808de87 on the temporary working storage.
8. Return 0.

The release call occurs even if the allocation operation was never reached, and even if context +12 contains zero. No local validity or ownership check precedes it.

The supplied body does not expose distinct error codes for initialization status, length retrieval, limit rejection, allocation failure, transfer failure, or count mismatch.

## Side effects

### Direct writes

Without argument overlap or dependency-induced mutation:

| Outcome | First output | Second output | Context +12 | Context +16 | Context +20 |
|---|---|---|---|---|---|
| Already-marked success | 0 | Existing length | Unchanged | Unchanged | 1 |
| Fresh success | F-3cb5472b4a81 result | Current length | Allocation result | Current length | 1 |
| Failure | 0 | 0 | 0 | 0 | 0 |

These entries describe the function’s explicit writes before finalization. They do not assert that unknown callees preserve those values.

### Observable ordering and overlap

Success writes the first output before reading the length for the second output. Thus, if the first output overlaps the length field, the second output can observe the newly written value rather than the prior length.

Failure releases the stored value before clearing either output or the context fields. A release dependency can therefore observe the pre-clear context through any access it independently has.

Both paths write the state marker before finalization. A dependency capable of accessing the context can observe that intermediate state.

The first output is not universally a nonzero success token: it is explicitly zero on already-marked success, and a zero result from F-3cb5472b4a81 is not itself rejected on fresh acquisition.

### Exceptional or nonreturning dependencies

The normal return contract assumes each invoked dependency returns normally. No visible exception recovery, rollback, or alternate finalization mechanism is established. If a dependency faults or does not return, later writes and finalization are not guaranteed.

## Acceptance examples

These are conditional static expectations, not runtime test results. Unless otherwise stated, assume valid nonoverlapping storage, normally returning dependencies, and no indirect context or output mutation by dependencies.

1. **Previously marked context.**  
   Given marker 7 and length 23, the function initializes temporary state, writes first output 0 and second output 23, writes marker 1, finalizes, and returns 1. It does not invoke the length, allocation, transfer, or release dependencies.

2. **Length exactly at the limit.**  
   Given marker 0, zero temporary status, a successful length operation producing 4096, and limit 4096, the limit gate passes. If allocation is nonzero and transfer status is zero with count 4096, the function returns 1 and reports length 4096.

3. **Unsigned limit rejection.**  
   Given length 4,294,967,295 and limit 2,147,483,647, the comparison rejects the length. No allocation is requested. The currently stored value is passed to F-58ba61416cc9, outputs and selected state fields are cleared, and the function returns 0.

4. **Initialization-status failure with an existing stored value.**  
   Given marker 0 and nonzero temporary status, the length dependency is not called. The existing value at context +12 is nevertheless passed to F-58ba61416cc9 before it is cleared.

5. **Zero allocation result.**  
   If earlier gates pass but F-fab3799b3190 returns zero, zero is first stored at context +12 and then passed to F-58ba61416cc9. Neither the accessor-like dependency nor the transfer dependency is called.

6. **Successful transfer status with a short count.**  
   Given requested length 100, low transfer status zero, and reported count 99, acquisition fails. The function does not accept partial completion.

7. **Nonzero transfer status despite an exact count.**  
   Given low transfer status 1 and count equal to the length, acquisition fails. The count does not override the status.

8. **Zero first output on fresh success.**  
   If F-3cb5472b4a81 returns zero but the transfer still reports zero status and an exact count, acquisition succeeds with first output zero. No explicit nonzero check rejects that value.

9. **Zero-length success.**  
   Given length and limit both zero, a nonzero allocation result, zero transfer status, and count zero, acquisition succeeds. The transfer call is not skipped merely because the length is zero.
