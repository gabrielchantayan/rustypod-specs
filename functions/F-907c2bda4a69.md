# F-907c2bda4a69

## Purpose

F-907c2bda4a69 updates an object’s embedded resource field and three one-byte settings, invokes a dependent state update, and performs two virtual dispatches on the object. One particular incoming mode enables an additional query of the embedded resource; that query can change the effective mode from 1 to 2.

This is a source-facing behavioral contract. It describes the operations visible in the supplied static evidence, not the complete behavior of the dependencies or virtual targets. No runtime tests have been performed.

The apparent intent is to configure an object from a supplied resource and several settings, then notify or refresh other state. That interpretation is inferred. The established behavior is the ordered sequence of field accesses and calls described below.

## Interface

The function has five explicit inputs and no explicit return value:

| Input | Representation in the supplied evidence | Role |
|---|---|---|
| Destination object | Pointer to a structure addressed through integer-sized words | Contains a virtual-dispatch pointer, an embedded resource field, and three settings bytes |
| Source resource field | Pointer to an integer-sized word | Supplies the value passed to the resource-assignment dependency, unless it is exactly the destination’s embedded resource-field address |
| Incoming mode | Integer | Controls the optional resource query and supplies the effective mode |
| Incoming secondary setting | Integer | Initializes a query output location and supplies a stored settings byte |
| Incoming auxiliary setting | One byte | Supplies a stored settings byte |

The supplied representation uses four-byte integer words and 32-bit address arithmetic. The offsets below follow that representation. It does not establish portability to a target with different integer or pointer widths.

The destination layout accessed directly by this function is:

| Byte offset from destination | Access |
|---|---|
| 0 | Read as the destination’s virtual-dispatch-table pointer |
| 24 | Address of the embedded resource field |
| 36 | Write the low eight bits of the effective mode |
| 37 | Write the low eight bits of the original secondary setting |
| 38 | Write the auxiliary setting byte |

The source resource field supplies one four-byte value when replacement occurs. The function does not directly inspect other source fields.

Two virtual-dispatch layouts are used:

- The object returned by F-e38e6836b640 has a dispatch-table pointer at offset 0. A callable entry is obtained at byte offset 172 within that table.
- The destination has a dispatch-table pointer at offset 0. A callable entry is obtained at byte offset 88 within that table.

These are byte offsets, not method indices.

Normal completion requires all executed accesses and calls to be valid. In particular:

- The destination must support the required reads, writes, and dispatches.
- The source must be readable when the replacement path reads its four-byte value.
- When the incoming mode is exactly 1, F-e38e6836b640 must return an object usable by the query dispatch.
- Every executed virtual target must be callable with the observed arguments.

There are no visible null checks, bounds checks, or validation checks. Violating these requirements has no established recovery behavior.

## Behavior

### 1. Prepare query state and identify the embedded field

The function establishes two local integer values:

- A query-mode value initialized from the incoming mode.
- A query-secondary value initialized from the incoming secondary setting.

These values provide writable storage to the optional resource query. They are distinct from the original input values used elsewhere in the function.

The embedded resource field is located 24 bytes from the destination base.

### 2. Replace the embedded resource unless the field addresses match

The function compares the address of the destination’s embedded resource field with the source resource-field pointer.

If the addresses are equal, it skips both resource-management dependencies. This is an address-identity check, not a comparison of stored resource values.

If the addresses differ, the function:

1. Calls F-561858688f94 with the destination’s embedded resource-field address.
2. Reads the four-byte value at the source resource-field address.
3. Calls F-83300d26ff95 with the embedded resource-field address and the value just read.

The source value is therefore obtained after F-561858688f94 returns. It is not visibly saved before that call. If the first dependency changes storage that affects the source value, the subsequent read observes the resulting storage contents.

The replacement path is taken even if the two distinct fields initially contain equal values. Conversely, exact field-address identity suppresses replacement regardless of the field contents.

The names and call shapes suggest reset/release followed by assignment, but their ownership semantics are not established. This contract does not assume that either dependency retains, releases, copies, or transfers ownership of any resource.

### 3. Optionally query the embedded resource

The optional query runs only when the incoming integer mode is exactly 1. The comparison occurs before the mode is narrowed to a byte.

On that path:

1. F-e38e6836b640 is called with the embedded resource-field address.
2. Its returned object is used for virtual dispatch through table byte offset 172.
3. The query receives that returned object, the address of the query-secondary integer, and then the address of the query-mode integer.
4. After the query returns, the function examines the query-secondary integer.

If that integer equals exactly 16, the effective mode becomes 2. Otherwise, the effective mode remains 1.

The query-mode integer is writable by the virtual target, but its value after the call is not read by the visible function. Changing it does not directly change the effective mode.

The query-secondary integer affects only the decision to replace mode 1 with mode 2. Its final value is not used for the secondary settings-byte write.

When the incoming mode is not 1, the resource extraction and query dispatch are both skipped. The effective mode is then the original incoming mode.

### 4. Store three settings bytes

After any replacement and optional query, the function performs these direct writes in order:

1. At destination offset 36, store the effective mode narrowed to one byte.
2. At destination offset 37, store the original incoming secondary setting narrowed to one byte.
3. At destination offset 38, store the incoming auxiliary byte.

For the supplied 32-bit representation, narrowing retains the low eight bits. The evidence does not establish whether consumers interpret those stored bytes as signed or unsigned.

The secondary byte comes from the original input even when the optional query has changed the query-secondary integer.

No widening, saturation, range rejection, or validation is visible.

### 5. Invoke the dependent state update

F-130b752ac461 is called with:

- The destination object.
- The effective mode as an integer, before byte narrowing.

The integer argument can therefore differ from a later integer interpretation of the byte at offset 36. For example, an effective mode of 257 produces a stored byte of 1 while passing 257 to this dependency.

All three direct settings-byte writes occur before this call. The dependency may have additional effects that are not visible in the supplied evidence.

### 6. Perform the first destination dispatch

After F-130b752ac461 returns, the function dispatches through the destination’s virtual-table entry at byte offset 88.

The arguments are:

1. The destination object.
2. A first shared four-byte value.
3. A second shared four-byte value.

The shared values come from two distinct fixed storage locations. Their meanings are unknown. The evidence establishes that both are supplied for this invocation, but not the relative evaluation order of the two shared reads or of those reads versus dispatch-target acquisition.

The destination’s dispatch-table pointer is acquired after F-130b752ac461 returns. This contract does not assume that the dependency preserved it.

### 7. Obtain a value and perform the second destination dispatch

After the first destination dispatch returns, the function calls F-e262d9d2f7fc with the destination object.

It then dispatches again through destination virtual-table byte offset 88, supplying:

1. The destination object.
2. A third shared four-byte value.
3. The four-byte result returned by F-e262d9d2f7fc.

The third shared location is distinct from the two used for the first dispatch.

The second dispatch resolves its target after the intervening calls; the function does not visibly retain and reuse the first dispatch’s target. If an intervening callee changes the destination’s dispatch-table pointer, the second invocation can select a different target.

After this invocation returns normally, F-907c2bda4a69 returns without an explicit result.

## Side effects

- Conditional calls that may modify the embedded resource field at offset 24.
- Three ordered byte writes at offsets 36, 37, and 38.
- A conditional virtual query that receives writable addresses of two local integers.
- A state-update dependency call.
- Two destination virtual dispatches, separated by a value-producing dependency call.
- Reads of three shared four-byte values for the destination dispatches.

The function contains no explicit allocation or deallocation operation. This does not imply that its dependencies avoid allocation, deallocation, reference-count changes, or ownership transfer.

There is no visible rollback. If a later dependency or virtual dispatch fails to return normally, earlier operations have already occurred. The supplied evidence does not define exceptions, fault handling, error codes, or recovery.

The three stored bytes are not guaranteed final postconditions: subsequent callees receive the destination and may modify them. Likewise, no global-preservation guarantee is established for any dependency or virtual target.

If a virtual target retains the addresses of the query integers, those addresses refer to invocation-local storage. The function does not establish a valid lifetime for their use after its return.

No synchronization or atomic-publication protocol is visible. The evidence does not support a thread-safety guarantee.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Each assumes valid storage, callable dispatch entries, and normal return from every invoked callee.

### Exact embedded-field alias

If the source pointer is exactly destination plus 24 bytes:

- Neither F-561858688f94 nor F-83300d26ff95 is called.
- This replacement branch does not read a source word.
- The optional query, settings writes, and later calls still occur according to the incoming mode.

This does not mean later dependencies avoid reading the embedded field.

### Distinct fields with equal stored values

If source and embedded-field addresses differ but initially contain equal words:

- F-561858688f94 is still called.
- The source word is read after that call.
- F-83300d26ff95 receives the word observed at that later read.

Value equality does not enable the alias shortcut.

### Mode 1 with secondary input 7 and query result 16

If the incoming mode is 1, the secondary input is 7, and the query leaves its secondary integer equal to 16:

- The effective mode is 2.
- The direct writes store 2 at offset 36 and 7 at offset 37.
- F-130b752ac461 receives integer mode 2.

The query result does not replace the original secondary setting.

### Mode 1 with query-secondary unchanged at 16

If the incoming mode is 1 and the secondary input is 16, and the query does not modify the secondary integer:

- The effective mode becomes 2.
- No explicit write by the query is required to trigger that transition.
- The secondary settings byte is 16.

### Query changes only its mode integer

If the incoming mode is 1, the query leaves the secondary integer unequal to 16, and it changes only the query-mode integer:

- The effective mode remains 1.
- The byte written at offset 36 is 1.
- F-130b752ac461 receives 1.

### Full-width mode differs from its stored byte

If the incoming mode is 257:

- The optional query is skipped because 257 is not exactly 1.
- The byte at offset 36 is written as 1.
- F-130b752ac461 receives integer 257.

A low byte equal to 1 does not activate the query.

### Negative secondary setting

If the incoming secondary setting is −1 in the supplied 32-bit representation:

- The direct byte write at offset 37 stores the bit pattern 255.
- On the mode-1 path, the query-secondary integer initially contains −1, not 255.
- Mode promotion requires that integer to equal 16 after the query.

### Later dispatch observes intervening changes

If the first destination dispatch or F-e262d9d2f7fc changes the destination’s dispatch-table pointer:

- The second dispatch uses the pointer obtained for that later invocation.
- It is not required to invoke the same target as the first dispatch.

Similarly, changes to the third shared value before its final-call read can affect the second dispatch’s argument.
