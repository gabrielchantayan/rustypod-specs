# F-1ead22e76231

## Purpose

F-1ead22e76231 coordinates event handling for a receiver object. It conditionally performs a preliminary notification, offers certain events to an early handler, invokes one of two main handlers, and may invoke a final receiver-specific handler.

The established behavior is dispatch and return-value propagation. The meanings of the event categories, subtypes, receiver fields, and handler results are not established.

Three characteristics are essential to the contract:

- A preliminary notification does not itself terminate processing.
- Any reached result-bearing handler that returns a nonzero value terminates processing, and that exact value becomes the function result.
- Event fields and dispatch information are read again at later stages. Changes made by a dependency can therefore affect subsequent routing.

This is a static behavioral specification. No runtime tests have been performed.

## Interface

### Inputs and result

The function accepts two inputs:

1. **Receiver:** an address identifying an object with data fields and an indirect dispatch-table reference.
2. **Event:** an address identifying a record whose category and associated value determine routing.

It returns an integer represented as 32 bits in the supplied material.

A zero return means that none of the result-bearing handlers actually reached returned a nonzero value. It does not establish that the event was ignored, that receiver state is unchanged, or that no side effects occurred.

A nonzero return is propagated unchanged from an invoked result-bearing handler. There is no visible normalization to a Boolean, filtering of negative values, or translation into a different result domain.

## Behavior

### 1. Preliminary notification

The function first reads the event category at offset `0x04`.

If the category is not `0x16`, it does not read a payload subtype during this stage and does not invoke the preliminary dependency.

If the category is `0x16`, it:

1. Reads the payload address from event offset `0x08`.
2. Reads the subtype at payload offset `0x04`.
3. Evaluates whether subtracting `0x2500` from that subtype produces `2`.

For a valid 32-bit subtype value of `0x2502`, this condition is satisfied. This stage is not a range test.

When the condition succeeds, the function reads the four-byte receiver field at `0x11C`, converts it to a character-sized value, and invokes F-5385d6aade50 with:

- The original receiver address.
- The converted character value.

Only the character-width portion of the receiver field is passed. Whether values with the high bit set are passed as negative or nonnegative values depends on character signedness and the calling convention, neither of which is established.

The caller does not use a result from F-5385d6aade50 to decide whether to return. If that dependency returns normally, execution continues into the next stage.

### 2. Optional early handler

The function reads the event category again. The result of the first category read is not reused.

If this new category is `0x16`, the function reads the event’s payload address again and then reads the subtype from that payload. If this freshly observed subtype is zero, it resolves and invokes the early handler through dispatch-table offset `0x124`.

The receiver’s dispatch-table address is obtained from receiver offset `0x00` for this dispatch. The handler receives the original receiver and event addresses.

If the early handler returns a nonzero integer, that exact value is returned immediately. Neither main handler nor the final handler is subsequently invoked.

If the early handler is ineligible or returns zero, execution continues.

This rereading matters after the preliminary notification. F-5385d6aade50 may have changed the category, payload address, subtype, or receiver dispatch table; no preservation guarantee is supplied.

### 3. Main-handler selection and invocation

The function reads the event category again.

If the current category is `0x16`, it reads the current payload address and then the current subtype. It selects:

- Dispatch-table offset `0x10C` when the subtype is `0x2A`.
- Dispatch-table offset `0x110` for any other subtype.

If the current category is not `0x16`, it selects dispatch-table offset `0x110` without reading a subtype during this stage.

The receiver’s dispatch-table address is read for this dispatch. The selected handler receives the original receiver and event addresses.

Exactly one main handler is invoked on every execution that reaches this stage and completes target resolution. There is no fall-through from the special main handler to the ordinary main handler, or vice versa.

If the selected main handler returns nonzero, that exact result is returned immediately. The final stage is skipped.

If it returns zero, processing continues.

### 4. Optional final handler

After a zero main-handler result, the function reads the event category once more.

If the category is not `0x0F`, it returns zero without reading the receiver’s match field.

If the category is `0x0F`, it reads:

1. The event’s four-byte value at offset `0x08`.
2. The receiver’s four-byte value at offset `0x50`.

If those values differ, it returns zero.

If they are equal, it resolves the final handler through the receiver’s current dispatch table at offset `0xE0` and calls it with the original receiver and event addresses.

A nonzero final-handler result is returned unchanged. A zero final-handler result produces a zero function result.

The comparison is between the values observed at this final stage. It is not tied to the event’s initial category or initial contents.

### Call ordering and termination

For an execution in which all invoked dependencies return normally, the possible order is:

1. Preliminary notification, when eligible.
2. Early handler, when eligible.
3. One main handler, unless the early handler returned nonzero.
4. Final handler, when eligible and the main handler returned zero.

Each listed role is invoked at most once by this function. Dependencies may themselves invoke other behavior; that is outside this contract.

The maximum visible number of dependency invocations is four. Reaching all four requires intervening changes to event state: the preliminary, early, and final stages use different eligibility conditions. This is possible only conditionally; the supplied material does not show a dependency that performs those changes.

## Side effects

### Direct accesses

The function visibly reads receiver fields, event fields, payload subtype fields, and indirect dispatch entries. It does not visibly write receiver fields, event fields, payload fields, or global storage.

It performs no explicit allocation, deallocation, ownership transfer, reference-count update, or resource release.

These observations apply only to the function’s direct behavior. Every invoked dependency may have additional effects.

### Dependency effects and lifetime

No supplied dependency contract establishes that a dependency:

- Preserves receiver or event contents.
- Preserves the receiver’s dispatch table.
- Preserves payload storage.
- Preserves globals.
- Acquires, transfers, or releases ownership.
- Returns normally.

Consequently, the contract must not treat the receiver, event, or payload as immutable across calls.

### Read ordering

The repeated category reads are distinct operations in the supplied representation. Subtype reads are likewise repeated at the stages where category `0x16` is observed.

The function does not take a single event snapshot and route entirely from it. In particular:

- A preliminary dependency can affect early-handler eligibility.
- An early handler returning zero can affect main-handler selection.
- A main handler returning zero can affect final-handler eligibility.
- A dependency can change which dispatch table supplies a later target.

This sequential behavior does not establish thread safety, atomicity, synchronization, or defined behavior under concurrent unsynchronized mutation.
