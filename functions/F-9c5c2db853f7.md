# F-9c5c2db853f7

## Purpose

F-9c5c2db853f7 conditionally replaces a value stored in an owner object, performs owner-directed notifications, derives a 32-bit value from the owner’s current state, and propagates changes into an optional associated object.

The associated-object path conditionally updates one of two field groups, sets an update flag, invokes a processing dependency, optionally issues an indirect notification, and sets a flag in an object returned by a final indirect call.

These operations are established by the supplied static evidence. Interpreting the stored value as a measurement, the derived value as a coordinate, or the associated object as a particular UI component would be inferred intent, not an established contract.

## Interface

The function has three arguments:

| Argument | Representation | Observed role |
|---|---|---|
| Owner | Address of an object accessed through 32-bit words and byte offsets | Supplies state, indirect dispatch tables, and associated-object references; receives a conditional state write |
| Replacement | A pointer-shaped, 32-bit value | Compared with and stored into an owner field; not directly dereferenced by this function |

The pointer-shaped replacement is subsequently used through the owner’s stored 32-bit field as arithmetic input. The evidence does not establish whether the public interface genuinely treats it as a pointer, an integer encoded as a pointer, or another address-sized token.

No error code, status result, exception translation, rollback, or recovery path is present in the supplied body.

## Behavior

### 1. Decide whether to perform the initial update

When Force is zero, read the owner’s field at `+0x20` and compare its 32-bit value with Replacement.

Perform the initial update when either:

- Force is nonzero; or
- Force is zero and the stored value differs from Replacement.

When Force is nonzero, the decision does not require reading the old stored value.

When Force is zero and the values match, skip only the initial update sequence. The later owner dispatches, arithmetic, and optional associated-object processing still occur.

### 2. Perform the conditional initial update

When the initial update is selected, perform these operations in order:

1. Store Replacement into the owner’s `+0x20` field.
2. Call F-438680ffebfe with the address of the owner’s embedded region at `+0x8C` and a fixed data address.
3. Obtain the indirect receiver from the owner’s `+0x88` field, resolve its dispatch entry at table offset `+0x40`, and invoke that entry with the receiver and the owner’s then-current `+0x20` value.

The fixed data address’s contents and meaning are unavailable.

The final argument in step 3 is a read of owner state after F-438680ffebfe. It is not guaranteed to equal the original Replacement: that dependency may have changed the field. Similarly, the receiver used in step 3 is not established before the dependency call.

There is no null check for this indirect receiver.

### 3. Perform three owner dispatches

Invoke the owner’s indirect dispatch entry at table offset `+0x58` three times, in this order:

1. Owner plus two fixed 32-bit data values.
2. Owner plus another two fixed 32-bit data values.
3. Owner plus one fixed 32-bit data value retained locally from before the second call.

There are five fixed-value roles across these calls, with the third call reusing the first explicit data argument supplied to the second call. The actual values and their meanings are unknown.

The retained value for the third call is loaded after the first call and before the second call. A change to its backing storage during the second call does not change the retained argument used by the third call.

The third invocation has fewer explicit arguments in the supplied evidence than the first two. A uniform prototype or an implicit extra argument must not be invented.

Dispatch resolution is performed for each call; the evidence does not justify assuming that earlier calls preserve the owner’s dispatch table or global data.

### 4. Calculate a derived value

After all three owner dispatches, inspect the owner byte at `+0x2D` and use the owner’s current 32-bit value at `+0x20`.

If the selector byte equals `3`:

- Form the arithmetic input from the stored value minus `76000`, multiplied by `20`.
- Call F-870c4fcf7295 with that input and `1000`.
- Add `18` to its returned 32-bit value.

For every other selector-byte value:

- Form the arithmetic input from the stored value minus `88000`, multiplied by `14`.
- Call F-870c4fcf7295 with that input and `1000`.
- Add `20` to its returned 32-bit value.

The second argument `1000` does not establish that F-870c4fcf7295 performs division, rounding, scaling, or clamping. Those semantics remain unknown.

The visible arithmetic uses 32-bit integer values. No explicit widening, range validation, saturation, or overflow handling is shown. Exact overflowing behavior is documented_only without a stronger target-language or instruction-level arithmetic contract.

### 5. Resolve the optional associated object

Read the owner’s reference at `+0x94` after F-870c4fcf7295 returns.

If it is null, return immediately. The initial update, owner dispatches, and arithmetic dependency call have already occurred.

Otherwise, retain this associated-object reference for the remaining work. Later modifications to the owner’s `+0x94` field do not, by themselves, redirect the locally retained reference.

### 6. Select at most one eligible field group

Eligibility for a 32-bit word means:

- Clear bit `0x20`.
- Compare the resulting unsigned bit pattern with `0x80000002`.

Thus, exactly `0x80000002` and `0x80000022` qualify. Other bits are not ignored.

Evaluate the first group before the second:

1. Read the word at `+0x54`.
2. Only if it qualifies, read and test the word at `+0x60`.
3. If both qualify, select the first group and do not examine second-group eligibility.
4. Otherwise, read the word at `+0x6C`.
5. Only if that word qualifies, read and test the word at `+0x78`.
6. Select the second group only if both second-group words qualify.

When the first group is selected:

1. Write the derived value to `+0x64`.
2. Read the source word at `+0x80` and write it to `+0x58`.

When the second group is selected:

1. Write the derived value to `+0x7C`.
2. Read the source word at `+0x80` and write it to `+0x70`.

When neither group qualifies, neither pair of destination fields is explicitly written.

The first group has strict precedence. Both groups are never explicitly updated during one invocation.

### 7. Mark and process the associated object

Regardless of whether a group qualified:

1. Read the associated object’s flags at `+0x48`.
2. Write those flags back with bit `0x20` set.
3. Call F-6d16652f2d03 with the associated-object address and the address of its field at `+0x80`.

The second argument is an address into the associated object, not a copied field value. The dependency’s access size, mutation behavior, and retention of that address are unknown.

### 8. Optionally notify another object

After F-6d16652f2d03 returns:

1. Read the associated object’s notification-target reference at `+0x34`.
2. If it is null, skip this notification without requiring the condition byte.
3. If it is nonnull, inspect the low byte at `+0xA0`.
4. If that byte is zero, resolve the target’s dispatch entry at table offset `+0x128` and invoke it.

A nonzero condition byte suppresses the call.

These conditions use post-dependency state. F-6d16652f2d03 may therefore affect whether this notification occurs and which target is used.

No explicit arguments are shown for this indirect invocation. In particular, an explicit receiver argument must not be inferred from the dispatch-table lookup alone.

### 9. Obtain and mark a final object

Invoke the associated object’s dispatch entry at table offset `+0x5C`, supplying the associated object as the explicit receiver argument.

Treat its result as an address. At that address plus `+0x48`:

1. Read a 32-bit flags word.
2. Write it back with bit `0x40` set.

There is no null check on the returned address. Successful execution requires a valid writable object at that point.

## Side effects

Explicit writes are limited to:

- The owner’s `+0x20` field, only when the initial update is selected.
- One eligible associated-object field group, or neither.
- The associated object’s `+0x48` flags word whenever the associated object is nonnull.
- The final returned object’s `+0x48` flags word.

The flag updates preserve all other bits from their respective immediately preceding reads. They are ordinary read-modify-write operations; no atomicity or synchronization is established.

The two flag destinations may alias. If they are the same word and intervening dependencies preserve it, both bits will remain set. Such preservation cannot be assumed.

No explicit allocation, deallocation, reference-count operation, or ownership transfer appears in the function body. This does not establish that dependencies avoid those effects.

The function provides no rollback after an early write. A later invalid access, failing dispatch, or nonreturning dependency may leave earlier mutations observable.

## Acceptance examples

These examples are conditional static acceptance criteria, not observed runtime results. Unless stated otherwise, dependencies return normally and all reached objects remain valid.

1. **Equal replacement without force.** If Force is zero and the owner’s stored value equals Replacement, there is no explicit replacement write, F-438680ffebfe call, or initial receiver notification. All three owner dispatches and the arithmetic dependency still occur.

2. **Forced refresh of an equal value.** If Force is any nonzero 32-bit value, including a negative signed value, the initial update occurs even when the stored value already equals Replacement.

3. **Dependency changes the stored value.** If F-438680ffebfe changes the owner’s `+0x20` field, the initial receiver notification uses the changed value. Later arithmetic also uses the value present at its own read, which may have changed again during the owner dispatches.

4. **Selector-specific zero arithmetic input.** If the selector byte is `3` and the stored value is `76000`, F-870c4fcf7295 receives `0` and `1000`. If it returns a value \(r\) for which adding `18` is representable, the derived result is \(r+18\). For a selector other than `3` and stored value `88000`, the analogous result is \(r+20\).

5. **Null associated object.** If the reference read at `+0x94` is null, execution ends after the arithmetic dependency. No associated-object flags, optional notification, or final returned-object flag are processed.

6. **First-group precedence.** If all four eligibility words qualify, only the first group receives the derived value and source copy. The second group’s eligibility words need not be read.

7. **Ignored eligibility bit.** A first-group pair containing `0x80000002` and `0x80000022` qualifies. Replacing either with `0x80000003` makes that group fail.

8. **Neither group qualifies.** The group destination fields receive no explicit writes, but bit `0x20` is still set and F-6d16652f2d03 still runs.

9. **Post-processing notification suppression.** If F-6d16652f2d03 leaves a nonnull notification target but a nonzero low byte at `+0xA0`, the optional notification is skipped. The final associated-object dispatch still occurs.

10. **Final flags preservation.** If the final dispatch returns an object whose flags word is `0x00000005`, and nothing changes that word between its read and write, the final write is `0x00000045`.
