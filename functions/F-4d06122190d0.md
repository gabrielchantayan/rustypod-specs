# F-4d06122190d0

## Purpose

F-4d06122190d0 conditionally invokes an acquisition dependency or increments a 16-bit field in a caller-supplied object. Its decision depends on a stored 32-bit identity, a two-bit mode, and an identity returned by a dependency.

The established behavior includes:

- Rejecting a null object with status 26.
- Conditionally invoking a preliminary dependency and propagating its nonzero result.
- Rejecting a matching-identity request in mode 1 with status 15.
- Incrementing the 16-bit field for a matching identity in mode 2, except when that field is already 65535.
- Otherwise invoking an acquisition dependency and, on success, storing the previously obtained identity and setting the 16-bit field to 1.

The layout and branching suggest ownership and recursive acquisition bookkeeping. Those meanings are inferred intent, not independently established semantics. In particular, successful synchronization, actual ownership, and release behavior cannot be established without the dependency contracts.

## Behavior

### 1. Null handling

If the input pointer is null, return 26 immediately.

This path performs no object access, discriminator comparison, or dependency call.

### 2. Conditional preliminary processing

For a nonnull input, compare the 32-bit field at offset 0 with a separately stored discriminator.

- If they differ, skip the preliminary dependency.
- If they match, invoke F-621dae46a146 with the original object pointer and a second argument of zero.
- If that invocation returns nonzero, return its result immediately.
- If it returns zero, continue.

The comparison takes place before any possible preliminary invocation. Configuration and identity processing occur afterward. Consequently, mutations made by a successful preliminary dependency may affect subsequent decisions.

The discriminator’s value and meaning are unknown. Equality establishes only whether this dependency is called; it does not establish a public object type or validity guarantee.

### 3. Capture the mode, then obtain an identity

Read the 16-bit configuration word at offset 14 and derive the mode from bits 4–5.

The mode is always one of 0, 1, 2, or 3. Bits 0–3 and 6–15 do not affect this function’s mode selection.

Next, invoke F-196812b4b122 with no arguments and retain its 32-bit result.

The order matters:

1. The mode is captured.
2. The identity dependency executes.
3. The stored identity at offset 4 is read for comparison.

A configuration change during the identity call does not change the captured mode for this invocation. A stored-identity change during that call can affect the subsequent comparison.

There is no failure branch for the identity dependency’s result. Every returned 32-bit value is used as an identity value, including zero or a value that would be negative under a signed interpretation.

### 4. Matching-identity special cases

If the stored identity equals the retained identity, modes 1 and 2 have special handling.

#### Mode 1

Return 15 immediately.

This path does not invoke F-6f7f27926f9e and performs no direct write to the stored identity or the 16-bit field.

#### Mode 2

Read the field at offset 18 as an unsigned 16-bit value.

- If its value is 65535, return 39 without changing it.
- Otherwise, write its value plus one back to offset 18 as a 16-bit quantity and return zero.

The overflow guard’s effective boundary is exactly 65535. Values from 65280 through 65534 are not rejected merely because they lie near the top of the 16-bit range.

For every permitted starting value, the mathematical increment remains between 1 and 65535. Thus this branch does not wrap 65535 to zero.

This path does not invoke the acquisition dependency and does not directly rewrite the stored identity. It also does not validate that the starting field is nonzero: a starting value of zero becomes one.

#### Modes 0 and 3

Even with a matching identity, these modes continue to the ordinary acquisition path. Identity equality alone is not a success condition.

### 5. Ordinary acquisition path

Invoke F-6f7f27926f9e with a pointer to byte offset 20 within the input object.

This path is selected when either:

- The stored identity differs from the retained identity, regardless of mode; or
- The identities match and the captured mode is 0 or 3.

If the dependency returns nonzero, propagate that result immediately. This function performs no subsequent identity or counter write on that path.

If the dependency returns zero:

1. Store the retained 32-bit identity at offset 4.
2. Store the 16-bit value 1 at offset 18.
3. Return zero.

The stored identity is the value obtained before the acquisition call. The identity dependency is not called again after acquisition.

The previous value at offset 18 is not read by this function on this path. Successful acquisition replaces it with 1 even if it previously contained zero, a larger value, or 65535.

## Side effects

### Direct object writes

Only two direct write patterns are established:

- Matching identity, mode 2, field below 65535: write the incremented 16-bit value at offset 18.
- Ordinary acquisition returning zero: write the 32-bit identity at offset 4, then write 1 at offset 18.

There are no other direct object writes in the visible behavior.

### Dependency effects and failure paths

Every dependency’s side effects remain outside this function’s established contract. A dependency may modify the object, external state, or both.

Therefore, “no direct write” does not mean “object unchanged”:

- A preliminary dependency may modify state before returning an error.
- The identity dependency may modify state before a local status 15 or 39 is returned.
- The acquisition dependency may modify state before returning an error.

No rollback is visible. Effects already performed by a dependency are not undone.

On successful ordinary acquisition, this function overwrites offsets 4 and 18 after the dependency returns. It makes no corresponding promise about other fields.

### Ownership and concurrency

The input remains a caller-supplied pointer throughout the visible body. No direct allocation, deallocation, or pointer retention is shown. Whether dependencies retain pointers or acquire resources is unknown.

The direct identity and counter operations are ordinary accesses in the supplied representation. No atomic update, memory barrier, or protection against concurrent access is established here. An atomic check-and-increment guarantee must not be inferred from the mode-2 branch alone.

## Acceptance examples

These examples are conditional consequences of the static behavior. They have not been executed. Except where stated otherwise, assume valid storage, no concurrent mutation, and dependencies that do not alter relevant fields.

1. **Null object**  
   A null input returns 26. No dependency is called.

2. **Preliminary failure**  
   The offset-0 field matches the discriminator, and F-621dae46a146 returns a nonzero status. That exact status is returned. The mode is not subsequently read, and neither later dependency is called.

3. **Preliminary success changes configuration**  
   The discriminator matches, and the preliminary dependency changes the configuration word before returning zero. Mode selection uses the word read after that return.

4. **Matching identity in mode 1**  
   The identity dependency returns the same value subsequently read at offset 4, and the captured mode is 1. Return 15 without calling the acquisition dependency or directly changing the field at offset 18.

5. **Matching identity in mode 2, starting at zero**  
   The 16-bit field is zero. Write 1 and return zero. There is no separate rejection of this starting state.

6. **Upper boundary progression in mode 2**  
   With matching identities, 65534 becomes 65535 and succeeds. A later invocation that still takes this branch with 65535 returns 39 and leaves the field unchanged directly.

7. **High values below the boundary**  
   With matching identities and mode 2, 65280 becomes 65281. The upper portion of the 16-bit range is not categorically rejected.

8. **Different identity in mode 2**  
   The identities differ and the field contains 65535. The function does not apply the mode-2 increment guard. If acquisition returns zero, it stores the retained identity, resets the field to 1, and returns zero.

9. **Matching identity in mode 0 or 3**  
   The acquisition dependency is called despite identity equality. If it returns nonzero, that status is propagated without the function’s final bookkeeping writes.

10. **Identity dependency changes configuration**  
    Mode 2 was captured before the identity call, but that call changes the configuration to mode 1. If the subsequent identity comparison matches, this invocation still follows mode 2.

11. **Acquisition changes external identity state**  
    The identity dependency returns value A. Acquisition later changes the state from which identity values are obtained and returns zero. The final stored identity is still A; there is no second identity query.
