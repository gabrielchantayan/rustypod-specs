# F-76eb2ffc0351

## Purpose

F-76eb2ffc0351 conditionally initializes a shared interface, requests construction of an object, obtains an associated value, and submits the constructed object through an indirect callback.

On ordinary completion, its result is the construction dependency’s result. A zero construction result suppresses association and submission. A zero association result selects a dependency identified as nonreturning.

**Established static evidence:** the supplied representation establishes the accesses, calls, branches, offsets, and return-value relationships described below.

**Inferred intent:** the size-taking dependency appears to request storage, and the shared interface appears to support registration or collection. These interpretations do not establish allocation, ownership, or application-level semantics.

**Verification status:** static analysis only. No runtime tests have been performed.

### Result

- If construction returns zero, the function returns zero.
- If the initialization result is zero and execution nevertheless completes the preceding writes and publication, the function returns the original first argument.

### Shared-base reads

1. Its first value is retained for later publication and callback preparation.
2. After the fourth argument is copied into the local slot, the global is read again to address the initial interface-field test.

This contract calls those values the **retained base** and the **initial lookup base**, respectively. They come from the same global but are not established as equal if that global changes between the reads.

The initial test reads four bytes at **initial lookup base +8**. Initialization publication and the eventual pre-dispatch reload instead access **retained base +8**.

## Behavior

### Initial state inspection

The function first reads and retains the shared-base global. It then copies the fourth argument into its local four-byte slot. It separately reads the shared-base global again and tests the four-byte field at offset +8 of that second value.

A nonzero field skips initialization. A zero field enters initialization.

The test does not establish the contents of the field at the retained base when the two base reads differ. In particular:

- A nonzero field at the initial lookup base can suppress initialization even if the retained base’s field is zero.
- A zero field at the initial lookup base can trigger initialization even if the retained base’s field is already nonzero.

No additional comparison between the two bases or their interface fields is shown.

### Conditional initialization

When the initial field test yields zero, the function performs these operations in order:

1. Calls F-8157a180d901 with literal size 24.
2. Discards that call’s returned value.
3. Calls F-e194f3fbdfaa without explicit arguments.
4. Reads a separate shared initialization value and writes it as four bytes at offset +0 of the returned address.
5. Writes one byte with value 1 at offset +16.
6. Writes four-byte zero at offset +20.
7. Publishes the returned address into the four-byte field at retained base +8.
8. Tests whether the returned address is zero.

Publication targets the **retained base**, not necessarily the base whose field triggered initialization. The function does not reload the shared-base global for this store.

The null check occurs after all three writes through the initialization result and after publication. Consequently, a zero result does not establish a safe allocation-failure return. The function first attempts writes at addresses corresponding to offsets 0, 16, and 20 from zero. If those accesses cannot complete, execution may fail before reaching the check.

Only if the preceding accesses and publication complete does a zero initialization result cause return of the original first argument. That branch skips the 156-byte request and all construction, association, transfer, and submission work.

No writes to the other bytes of the nominal 24-byte region are established.

### Storage request and construction

After shared-state handling, unless the late initialization-null branch returned, the function calls F-8157a180d901 with literal size 156.

It retains that call’s four-byte result without a local zero check, overwrites the local slot with zero, and invokes F-1a1fd76d2df8 with seven arguments:

| Position | Value |
|---|---|
| 1 | Result of the 156-byte request. |
| 2 | Original first argument. |
| 3 | Original second argument. |
| 4 | Original third argument. |
| 5 | Literal 7. |
| 6 | A read of a shared configuration global. |
| 7 | Another read of that same configuration global. |

The two configuration positions use the same global source. Their relative evaluation order is not established, and equal values are not guaranteed if that global can change between the reads.

If construction returns zero, the function returns zero. It performs no association call, +152 store, transfer call, or callback submission. Completed initialization is not locally rolled back.

### Association and exceptional branch

For a nonzero construction result, the function calls F-a2c46f03f6cf with that result as its sole argument.

If association returns zero, the function calls F-feee9156a257 with the **construction result**, not the zero association result. The supplied representation identifies this dependency as nonreturning. No normal continuation beyond this call is established for the zero-association branch.

For a nonzero association result, the function stores that value as four bytes at construction-result offset +152.

No local validation establishes that either result denotes valid storage. The association result is subsequently used in address arithmetic.

### Transfer call

After the +152 store, the function calls F-e7c5183babcf with:

- The construction-result address plus **2 bytes**.
- The association-result address plus **6 bytes**.

These are byte increments, not four-byte element increments. The call has no explicit size argument.

The dependency’s memory direction, extent, alignment requirements, error behavior, and ownership effects are unknown. No returned value from it affects the visible control flow.

### Callback selection and submission

After F-e7c5183babcf returns, the function:

1. Reloads the four-byte interface field from **retained base +8**.
2. Writes the construction result into the local four-byte slot.
3. Reads the selected interface’s first four-byte word as a dispatch-table address.
4. Reads the callable entry at table offset +28.
5. Calls that entry with the selected interface and the address of the local slot.

The shared-base global is not reloaded for this operation. Changes to that global after the retained-base capture do not redirect this field access. Changes to the field at retained base +8 can redirect it.

There are no local null checks on the reloaded interface, table address, or callable entry.

The callback’s second argument is a pointer to a slot containing the construction result, not the construction result directly. A callback may modify that slot, but its resulting contents are not used to choose this function’s return value.

If the callback returns normally, the function returns the construction result. The callback’s return value is ignored.

## Side effects

### Direct memory effects

The function’s direct nonlocal writes are:

- On initialization, writes at initialization-result offsets +0, +16, and +20.
- Publication into retained base +8.
- After nonzero association, a four-byte store at construction-result offset +152.

Its local slot receives, in order, the fourth argument, zero before construction, and the construction result before callback submission, subject to reaching each stage.

The initial lookup field is not necessarily the publication field. If the two initial base values differ, initialization can leave the lookup field unchanged while replacing the retained base’s field.

### Dependency effects and failure behavior

No dependency is assumed to preserve globals, interface fields, previously written memory, or object lifetime. Thus the direct-write sequence does not guarantee those values remain unchanged after later calls.

The function contains no explicit cleanup or rollback sequence and no established local recovery for invalid memory accesses. Only the visible return-value branches and the identified nonreturning call are specified.

### Ownership and lifetime

No explicit release of either size-request result is shown. Allocation, retention, transfer, and release responsibilities remain unknown; the absence of a visible release does not establish a leak.

The callback receives an address into invocation-local storage. No mechanism extends that storage’s lifetime beyond the invocation. Whether the callback retains the address, and whether retention is permitted by its own contract, are undocumented.

No explicit locking, atomic publication, or reentrancy guard is shown. Thread-safe initialization and coherent concurrent access are not established.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Each assumes the relevant memory accesses and normally returning dependencies can complete.

### Stable base, existing interface, successful construction

If both initial global reads yield the same valid base, its +8 field is nonzero, and construction and association return nonzero:

- Initialization is skipped.
- The 156-byte request precedes construction.
- The association store precedes F-e7c5183babcf.
- Submission uses the interface reloaded from that retained base after the transfer call.
- Normal completion returns the construction result.

### Different bases, nonzero initial lookup field

If the first global read yields one base and the second yields another, whose +8 field is nonzero:

- Initialization is skipped based solely on the second base’s field.
- Successful submission later reloads the first base’s +8 field.
- If that first field is zero, there is no local guard preventing an attempted dispatch through it.

A nonzero lookup field alone therefore does not establish a valid eventual dispatch interface.

### Different bases, zero initial lookup field

If the two initial reads yield different valid bases and the second base’s +8 field is zero:

- Initialization runs even if the retained base’s field was nonzero.
- The initialized pointer is published into the retained base’s +8 field.
- This function does not directly publish it into the second base’s field.
- Later dispatch reloads the retained base’s field.

### Construction returns zero

After shared-state handling, if construction returns zero:

- The function returns zero.
- Association, the +152 store, transfer, and submission are skipped.
- Any completed initialization publication has no local rollback.

### Association returns zero

With nonzero construction and zero association:

- F-feee9156a257 receives the construction result.
- No normal return is specified.
- The +152 store and later calls are not reached under the supplied nonreturning characterization.

### Callback changes the submission slot

If the callback replaces the slot’s contents and returns normally, the function still returns the construction result, not the replacement value.

### An intervening dependency changes shared state

If a dependency changes retained base +8 to another valid interface before dispatch, the reload selects that replacement.

If it changes only the shared-base global, the dispatch field access still uses the originally retained base. Effects of any accompanying memory changes remain separate.

### Initialization returns zero

A zero initialization result does not by itself imply a clean early return. The initialization writes and publication precede the null test. Only if they complete does the function return the original first argument.
