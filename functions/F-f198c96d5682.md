# F-f198c96d5682

## Purpose

F-f198c96d5682 conditionally obtains a new buffer of 32-bit words, copies an existing word sequence into it when an existing buffer is present, and zeroes the extension up to a requested word count.

The visible routine does not install the returned buffer into the supplied record, update the record’s count, release the old buffer, or explicitly initialize the extra word included in the allocation request.

Three explicit rejection or failure conditions lead to a diagnostic dependency and, if that dependency returns, a null result:

- The requested count is at least 16,777,216.
- Bit `0x2` is set in the record’s flags word.
- The allocation dependency returns null.

This is not a general-purpose validated resize operation. In particular, negative counts, shrinking requests, inconsistent records, and arithmetic overflow are not explicitly rejected.

## Interface

The interface has four arguments, with the following visible roles:

| Position | Interpretation | Visible use |
|---|---|---|
| First | Address of a record containing 32-bit fields | Supplies an existing buffer address, an existing count, and flags |
| Second | Signed 32-bit requested word count | Controls the initial limit check, allocation size, and extension length |
| Third | Opaque 32-bit value | Not read or forwarded by the visible routine |
| Fourth | Opaque 32-bit value | Passed twice to the allocation dependency |

The record’s observed layout is:

| Byte offset | Width | Meaning used here |
|---|---:|---|
| `0` | 32 bits | Existing buffer address |
| `4` | 32 bits | Existing word count, used in signed arithmetic and shifts |
| `8–15` | Unestablished | Not explicitly accessed |
| `16` | 32 bits | Flags; only bit `0x2` is tested |

The representation is consistent with a 32-bit address space and four-byte words. No byte order is established by the supplied evidence. Copying preserves complete word values rather than performing a byte-order conversion.

### Output

If allocation returns a non-null address and execution completes normally, the function returns that address.

For an explicitly rejected request or a null allocation result, the function calls F-4fc89ec41a6d and then returns null if that dependency returns normally.

No separate status value is returned. Successful allocation is not itself proof that all subsequent memory accesses are valid: the visible routine performs no buffer-capacity or consistency validation.

### Preconditions for the ordinary, bounded-use case

A caller seeking the intended copy-and-zero-extension behavior must provide:

- A nonnegative requested count below 16,777,216.
- A readable record with bit `0x2` clear.
- A nonnegative existing count no greater than the requested count.
- A readable existing buffer containing at least the existing number of words, unless the existing buffer address is null.
- A record and source buffer that remain valid through the allocation dependency call.
- A returned allocation large enough for the requested allocation size and suitably aligned for 32-bit word accesses.

If the existing address is null but the existing count is positive, the routine does not synthesize the missing prefix. A fully defined logical result therefore additionally requires an existing count of zero in that case, or a separate guarantee about the allocator’s contents.

These are safe-use conditions inferred from the accesses, not checks implemented by this routine.

## Behavior

### 1. Requested-count gate

The first decision is a signed comparison of the requested count against 16,777,216.

A value at or above that threshold selects diagnostic reason `0x72`. This route does not explicitly read the supplied record and does not call the allocation dependency.

The comparison does not reject negative values. A negative requested count passes this gate.

### 2. Flags gate

For a count below the threshold, the routine reads the 32-bit flags field at byte offset `16` and tests bit `0x2`.

If that bit is set, the routine selects diagnostic reason `0x69` without calling the allocation dependency. Other flag bits do not affect this decision.

There is no null-record check before this read.

### 3. Allocation request

When both gates permit continuation, the routine calls F-43da6b23bd44 with five arguments, in this order:

1. Four times the requested count plus one word: `4 × (requested count + 1)`.
2. Zero.
3. Zero.
4. The fourth argument supplied to F-f198c96d5682.
5. The same fourth argument again.

The extra word is included in the requested allocation size, but the ordinary copy-and-extension path only populates the logical range ending just before the requested count.

For a nonnegative count admitted by the gate, the allocation-size expression ranges from 4 through 67,108,864 bytes and fits within a signed 32-bit integer.

For negative counts, the visible expression can produce zero or negative values, and sufficiently negative values can exceed the representable signed 32-bit range during multiplication. The callee’s interpretation of such arguments and the precise overflow semantics are not established.

If F-43da6b23bd44 returns null, the routine selects diagnostic reason `0x41`. It does not proceed to read the existing buffer address or perform copying and zero filling.

### 4. Existing-prefix copy

After a non-null allocation result, the routine reads the existing buffer address from the record.

This read occurs after the allocation dependency returns. The routine must not be described as using a pre-call snapshot of the record: the dependency’s effects on the record or other memory are unknown.

If the existing buffer address is null, the entire copy stage is skipped.

Otherwise, the existing count controls copying in groups of four words followed by a remainder. For ordinary nonnegative counts, this copies exactly that many words, beginning at the source and destination base addresses.

The visible access ordering within each full four-word group is:

- Read source words at relative positions one, two, and three.
- Read source word zero and write destination word zero.
- Write destination word one.
- Write destination word two.
- Write destination word three.

The groups progress from lower to higher addresses. The remainder is copied in descending position order:

- A three-word remainder copies positions two, one, then zero.
- A two-word remainder copies positions one, then zero.
- A one-word remainder copies position zero.

These details distinguish the operation from an unconditional bytewise forward copy. They matter if source and destination overlap or if access order is externally significant.

No overlap check or overlap-safe-copy guarantee is present. Ordinary correctness requires independently valid source and destination storage, or an overlap arrangement for which these particular accesses are safe.

The supplied representation also reads the count for the full-group calculation and reads it again for the remainder calculation. A single immutable count snapshot is not established. Concurrent mutation, or destination writes aliasing record fields, can invalidate the ordinary interpretation.

### 5. Extension zeroing

After copying or skipping the copy, the routine obtains a destination position using the record’s existing count as a word offset from the new allocation.

It calculates the requested count minus the existing count. For an ordinary nonnegative difference, it:

- Writes complete groups of eight zero-valued 32-bit words, in increasing address order.
- Writes the remaining zero-valued words, also in increasing address order.

Consequently, when the existing count is nonnegative and does not exceed the requested count, destination words from the existing count through requested count minus one are set to zero.

The existing count is consulted again during this stage. The start position, group count, and remainder count must not be assumed to derive from one protected snapshot when record mutation or aliasing is possible.

The word at index equal to the requested count is not explicitly initialized under the ordinary safe-use conditions. Its value is whatever the allocation dependency and any other relevant memory effects leave there. No terminator, sentinel, or guaranteed zero may be inferred.

### 6. Return or diagnostic handling

After the copy and zero-fill stages, the new allocation address is returned without further explicit dependency calls.

All three explicit failure routes call F-4fc89ec41a6d with:

| Argument position | Value |
|---|---:|
| First | `3` |
| Second | `0x78` |
| Third | Selected reason: `0x72`, `0x69`, or `0x41` |
| Fourth | `0` |
| Fifth | `0` |

The ordering establishes rejection precedence: the requested-count gate precedes the flags gate, and both precede allocation failure.

Null is returned afterward only if this dependency returns normally. The supplied evidence does not establish whether the diagnostic dependency always returns, throws, terminates, or performs other control transfer.

## Side effects

### Explicit memory activity

On the ordinary successful path, the routine:

- Reads the record’s flags, existing address, and count.
- Reads existing-buffer words when the existing address is non-null and the copy calculations request accesses.
- Writes copied values into the returned allocation.
- Writes zero words into the extension region.

There are no explicit assignments to the record’s address, count, or flags fields. There is no explicit release of the existing buffer.

Those statements describe direct operations, not unconditional preservation guarantees. A dependency may modify memory, and a returned destination that aliases the record or existing storage may cause the routine’s buffer writes to affect those objects.

## Acceptance examples

These examples are conditional behavioral expectations derived from static evidence, not results of execution.

1. **Ordinary extension.**  
   Given an existing count of three, readable source words with values 11, 22, and 33, a requested count of six, clear gating flags, and a successful independent allocation, the allocation request is 28 bytes. The returned buffer contains 11, 22, and 33 at indices zero through two, and zero at indices three through five. Index six has no value guaranteed by this routine.

2. **Unchanged logical length.**  
   Given an existing count and requested count both equal to two, a valid non-null source, and successful allocation, 12 bytes are requested. Two words are copied. No extension words are written, and the extra word is not explicitly initialized.

3. **Empty input and zero request.**  
   Given an existing count of zero, a null existing address, and a requested count of zero, the routine requests four bytes. If allocation succeeds, it returns the address without explicitly writing any buffer words.

4. **Null source with a positive existing count.**  
   Given an existing count of two, a null source, and a requested count of five, the copy stage is skipped. Indices two through four are zeroed. Indices zero and one are not explicitly initialized.

5. **Limit rejection has precedence.**  
   A requested count of 16,777,216 selects reason `0x72`, regardless of the flags value. The record is not explicitly read and allocation is not attempted.

6. **Flag rejection.**  
   With a requested count of ten and flags containing bit `0x2`, the diagnostic call uses reason `0x69`; allocation is not attempted.

7. **Null allocation.**  
   With an admitted count and clear gating bit, a null allocation result selects reason `0x41`. No existing-buffer copy or extension write follows.

8. **Shrinking is not a validated operation.**  
   An existing count of five and requested count of four is not rejected by either gate. The routine still attempts the existing-prefix copy rather than truncating it. The negative extension difference does not establish a safe no-op: the low-three-bit remainder calculation can produce zero writes beyond the copied prefix. A caller must not treat this case as supported shrinking behavior.

9. **Negative request is not a range error here.**  
   A requested count of minus one passes the initial gate and yields a zero allocation-size expression. What follows depends on the flags, the allocation dependency’s zero-size behavior, and subsequent arithmetic and addresses. Reason `0x72` is not selected merely because the count is negative.
