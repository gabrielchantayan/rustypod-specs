## Behavior

### Candidate capture precedes dependency execution

The function first reads and saves the signed candidate from the third integer slot of the input record.

This read occurs before calling F-392d97f6cbd4. Therefore:

- Dependency execution cannot prevent the initial candidate read.
- The dependency is called even when the candidate is negative.
- A dependency-side change to the candidate field does not replace the saved candidate used by this invocation.

An unreadable candidate field can cause an access failure before the dependency runs. There is no visible validation or fallback for that condition.

### Dependency result gates further record access

After saving the candidate, the function invokes F-392d97f6cbd4 with no explicit arguments shown in the available representation.

A zero dependency result causes a normal return of −1 without explicitly reading either the input’s address-bearing word or the referenced upper bound.

### Negative candidates are rejected without reading the bound

When the dependency returns nonzero, a negative saved candidate is rejected with −1.

On this path, the function does not explicitly read the address-bearing word or the upper-bound field. In particular, a negative candidate does not require a valid referenced object for the visible body’s later reads.

### Nonnegative candidates trigger the indirect read

1. Reads the address-bearing word from the input record.
2. Uses that address to read the signed upper bound at byte offset 4 of the referenced object.

Both reads occur after the dependency returns. The address is not cached before the call, and the upper bound is not read beforehand.

Accordingly, if the dependency changes the address-bearing word, the function uses the changed address. If the dependency changes the referenced upper-bound field, the function observes the value available at the subsequent read.

There is no visible null check, object-type check, or bounds validation before this indirect access.

### Acceptance uses a strict signed upper bound

For a nonnegative saved candidate, acceptance requires that the candidate be strictly less than the signed upper bound.

The recovered decision distinguishes equality from the remaining ordering comparison. Its resulting behavior is:

- Candidate equal to upper bound: reject.
- Candidate greater than upper bound: reject.
- Candidate less than upper bound: accept, provided the dependency returned nonzero and the candidate is nonnegative.

The upper bound is interpreted as signed. A zero or negative upper bound admits no candidate.

There is no subtraction, increment, multiplication, or candidate-derived address calculation. The candidate is compared directly and, if accepted, returned unchanged. The strict boundary therefore does not depend on arithmetic such as computing “upper bound minus one.”
