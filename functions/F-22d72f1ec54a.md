# F-22d72f1ec54a

## Purpose

F-22d72f1ec54a updates three fixed-offset fields in a caller-supplied memory region. It stores two opaque 32-bit values and then clears an adjacent 8-bit field.

The established behavior is limited to these stores. The supplied static evidence does not identify the containing object, the meanings of the two values, or the role of the cleared byte. Describing the operation as configuration, initialization, or a state reset would be inferred intent rather than an established interface guarantee.

This contract describes behavior visible in the supplied source representation. No runtime tests have been performed.

## Interface

The function receives three arguments, in this order:

| Argument | Contract |
|---|---|
| Base | An address-bearing integer used to locate the destination fields. It is not itself a pointer to a separately described object type in the available evidence. |
| First value | An opaque four-byte, 32-bit value stored at offset `0xF4` from the base. |
| Second value | An opaque four-byte, 32-bit value stored at offset `0xF0` from the base. |

The function has no return value. In particular, it does not return a success indicator, the destination address, or either previous field value.

The destination layout, expressed relative to the base, is:

| Byte range | Width | Value after normal completion |
|---|---:|---|
| `0xF0`–`0xF3` | 4 bytes | Second value |
| `0xF4`–`0xF7` | 4 bytes | First value |
| `0xF8` | 1 byte | Zero |

The two four-byte arguments are transferred as opaque values. No arithmetic, masking, sign interpretation, byte swapping, or value-dependent selection is expressed.

The source representation establishes the four-byte and one-byte store widths. It does not independently establish the ABI width of the base argument, the address-space width, the target byte order, or the alignment rules governing the four-byte accesses.

### Preconditions

For an ordinary successful invocation:

## Behavior

### Established store sequence

The function expresses three stores in the following order:

1. Store the first value as four bytes at base plus `0xF4`.
2. Store the second value as four bytes at base plus `0xF0`.
3. Store zero as one byte at base plus `0xF8`.

The ordering matters: the higher-addressed four-byte field is assigned before the lower-addressed four-byte field. The byte clear follows both.

After these stores, the function returns without a result.

There are no branches, loops, dependency calls, or value-dependent alternatives in the supplied body. The same three-store sequence applies regardless of the contents of either value argument or the previous destination contents.

### Reads and preservation

No read of the prior contents of any destination field is expressed. This is replacement behavior, not a read-modify-write operation.

The arguments are used to compute addresses and supply stored values. Neither four-byte value is dereferenced. Consequently, a bit pattern that happens to resemble an address has no special meaning within this function.

For valid, ordinary memory, the directly written byte ranges are exactly those listed in the interface table. Bytes before `0xF0` and after `0xF8` are not directly written by the function. In particular, clearing the byte at `0xF8` does not express a four-byte clear spanning `0xF8`–`0xFB`.

This preservation statement concerns direct accesses expressed by this function. It does not rule out effects caused by memory-mapped devices, address aliases, concurrent agents, or execution-environment mechanisms.

### Ordering and visibility limits

The sequence above is the order represented by the supplied source. The evidence does not establish:

- Atomicity of either four-byte store.
- Atomicity of the complete update.
- A synchronization operation or memory barrier.
- A guarantee that another execution agent observes the three updates in that order.
- A transaction that hides intermediate states.

The final zero byte therefore must not be treated as a proven publication or completion signal without an external concurrency contract.

### Invalid access and interruption

There is no explicit validation, error return, recovery path, or rollback.

If execution fails or is interrupted before normal completion, the function provides no all-or-nothing guarantee. For example, the first destination may already have changed before a later access fails. Exact fault delivery, partial-store behavior, and visibility of earlier writes depend on the target and cannot be determined from this body.

Address overflow and invalid integer-to-address behavior are likewise not defined by the available evidence. The contract does not prescribe wrapping arithmetic or a particular fault outcome.

## Side effects

The established side effects are two four-byte destination assignments and one one-byte destination assignment.

There is no expressed allocation, deallocation, ownership transfer, reference-count adjustment, or resource release. The function does not inspect or release the previous values before overwriting them.

If either old field value represented an owned resource under a larger object protocol, this function alone does not establish how that resource is managed. Similarly, storing a new value does not establish that the function acquires ownership of anything represented by that value.

The function does not initialize the entire containing region. Fields outside the three written ranges retain their prior contents under ordinary-memory assumptions.

## Acceptance examples

The following are conditional acceptance examples, not reported test results. Unless stated otherwise, they assume valid, suitably aligned, ordinary writable memory, valid address arithmetic, and no concurrent modification.

### Distinct values preserve argument placement

Given a first value of `0x11223344` and a second value of `0xAABBCCDD`, normal completion must leave:

- The four-byte field at `0xF4` holding `0x11223344`.
- The four-byte field at `0xF0` holding `0xAABBCCDD`.
- The byte at `0xF8` holding zero.

The lower-addressed field receives the second value, not the first. Exact individual byte sequences depend on the target’s byte order.

### Previous contents do not affect the result

Given arbitrary previous contents in all three destination fields, normal completion must replace them with the two supplied values and zero. No prior field value selects a different operation.

### Clearing remains byte-sized

Given nonzero sentinel bytes at `0xF8`, `0xF9`, `0xFA`, and `0xFB`, normal completion must clear `0xF8`. The function must not directly overwrite the sentinel bytes at `0xF9`–`0xFB`.

### Boundary value patterns are opaque

Given one four-byte value with all bits set and the other with all bits clear, each destination must receive its corresponding value without clamping, rejection, sign extension into neighboring fields, or special interpretation.

### Repeated calls replace the same fields

Given two successful calls using the same base, the second call replaces both four-byte fields with its own arguments and again writes zero to `0xF8`. No counter, toggle, or accumulated state is expressed.

### Failure does not imply preservation

If the first four-byte store completes but a later access cannot complete, preserving the entire original region is not an acceptance requirement. The function contains no rollback mechanism. The exact resulting memory and control-flow outcome remain environment-dependent.
