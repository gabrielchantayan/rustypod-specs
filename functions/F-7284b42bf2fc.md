# F-7284b42bf2fc

## Purpose

F-7284b42bf2fc traverses a linked structure, then either returns a selected candidate address or invokes a dependency whose output becomes the result. It writes a four-byte result token and a one-byte disposition into caller-provided storage.

Established behavior depends on a container byte:

- **Zero:** perform additional candidate checking, except when a boundary condition immediately selects the insertion-dependency path.
- **Nonzero:** invoke the insertion dependency after the initial search without additional candidate checking.

An ordered-tree insertion operation with optional duplicate acceptance is **inferred intent**. The supplied evidence does not establish ordering semantics, tree invariants, or successful insertion.

The disposition identifies the chosen path: zero for returning an existing candidate, one for returning an insertion dependency’s output. It is not an independently checked success status.

## Interface

### Arguments and result

The function receives:

1. **Result-storage address:** storage accepting a four-byte write at offset 0 and a one-byte write at offset 4.
2. **Container address:** used for field access and passed to dependencies.
3. **Incoming token:** an opaque four-byte value passed to comparison and insertion dependencies.

There is no explicit return value. On normal completion, the caller-visible output is:

| Offset | Width | Meaning |
|---|---|---|
| 0 | Four bytes | Selected candidate address, or contents of the insertion-output slot |
| 4 | One byte | Zero for candidate selection; one for an insertion-dependency path |

The four-byte result write precedes the disposition write. No direct caller-output writes occur beyond offset 4.

### Widths and layouts

The supplied representation uses four-byte tokens and address-bearing slots, one-byte flags, and byte-addressed offsets. Address use is consistent with a 32-bit model; portability to wider addresses is not established.

Comparison results are represented as integers and tested only for zero versus nonzero. Sign and nonzero magnitude do not affect branch selection.

Directly used container locations are:

| Offset | Access | Role |
|---|---|---|
| 16 | Four-byte address read | Header address |
| 24 | One-byte read | Mode |
| 25 | Address formation | Comparison-context address |

The comparison context’s extent and contents are unknown. Forming and passing its address does not itself establish a direct read there.

Linked storage has these observed roles:

| Offset | Width or use | Role |
|---|---|---|
| 0 | One-byte read | Marker during candidate selection |
| 4 | Four-byte link | Root when accessed through the initial header; parent during upward traversal |
| 8 | Four-byte link | Search child for nonzero comparison; header boundary; structural-selection link |

These roles describe access paths, not proven object types. In particular, an address retained as a header can subsequently participate in structural accesses if the control flow reaches them.

Offsets 8 and 12 are consistent with left and right child links, and the header boundary with a leftmost-node link. Those names are inferred, not required for the offset-based behavior below.

### Preconditions and unsupported inputs

Normal completion requires valid memory for every access actually reached, compatible address representations, and normally returning dependencies. Traversal must terminate, including parent-chain and descendant-chain traversal.

The function supplies no validation for null arguments, invalid links, cycles, inconsistent parent relationships, or output overlap with other objects.

There is **no unconditional requirement that the insertion dependency initialize its output**. The output slot has path-dependent initial contents, described below. If those contents are initialized and left unchanged, they are copied to the caller. Where the slot is uninitialized, the supplied evidence establishes no determinate result token.

Aliasing is not checked. The final output writes can modify container or node memory if the caller overlaps those objects with result storage.

## Behavior

### Initial acquisition and search

The remembered comparison result starts at one.

The function reads the header address at container offset 16, then the root link at that header’s offset 4. It separately reads container offset 16 again to establish the initial attachment address.

The two header reads are distinct. Without stable storage, the root can come from one header observation while the initial attachment comes from another.

For each non-null search node:

- Two distinct four-byte temporary slots are reset to zero. These later serve, respectively, as the boundary-shortcut insertion output and the general-insertion output.
- F-f75c770a6cd7 is invoked with the comparison-context address, incoming token, and current node’s offset-16 address.
- The current node becomes the retained attachment.
- A zero comparison result selects the node’s offset-12 link.
- Any nonzero result selects its offset-8 link.

The selected link is read after the comparison dependency returns. Mutation by that dependency can therefore affect the next node.

The search ends when the selected link is null. The attachment is the last visited node, or the separately acquired header if no node was visited. The remembered comparison is the last dependency result, or one for an empty search.

Every search iteration resets both insertion-output slots before calling the comparison dependency. Consequently, a nonempty search establishes zero initial contents for both slots, subject to the later overwrite of the general slot described below. An empty search performs neither reset.

### Mode decision

After traversal, the function reads the byte at container offset 24.

Any nonzero byte selects general insertion immediately. Zero selects candidate checking. This read occurs after all search comparison calls, so their effects can influence the observed mode.

### Zero-mode candidate checking

The preliminary candidate is the retained attachment.

If the last comparison was zero, structural candidate selection is skipped and the function proceeds to final candidate comparison.

If the last comparison was nonzero, the function reloads the header through container offset 16, reads that header’s offset-8 boundary link, and stores that link in the **general-insertion output slot**. This overwrites any zero previously placed there.

The retained attachment is then compared with that boundary address.

#### Boundary shortcut

Equality immediately invokes F-d96aaf447a13 with:

- The address of the separate boundary-shortcut output slot;
- The container address;
- A literal zero;
- The retained attachment;
- The incoming token.

After normal return, the function copies the slot’s four-byte contents to result offset 0 and writes disposition one.

No candidate-token extraction or final comparison occurs on this path.

The shortcut-output slot initially contains zero after a nonempty search. It is uninitialized after an empty search. Loading the boundary address into the general-output slot does not initialize this separate slot.

#### Structural candidate selection

If attachment and boundary differ, the function reads the attachment’s one-byte marker.

When the marker is zero, it reads the attachment’s offset-4 parent link and then that parent’s offset-4 link. If the latter equals the attachment, the candidate becomes the attachment’s offset-12 link.

A nonzero marker bypasses those parent reads. If the marker shortcut does not select a candidate, the function uses descent or ascent.

**The repeated link reads are distinct observations.** The following describes their order without assuming agreement.

First, the attachment’s offset-8 link is loaded as a prospective descent address. The same field is read again to choose the branch:

- If the second read is null, the function selects ascent. The first loaded address is not used for descent.
- If the second read is non-null, descent starts using the address obtained by the first read.

During descent, each iteration selects the current descent address as candidate. It then reads that candidate’s offset-12 link as the prospective next address and separately rereads the same field for the continuation decision.

- A null second read ends descent with the current candidate.
- A non-null second read continues using the first read’s address.

Thus, the continuation test does not validate the saved next address. If the two observations disagree, the function can stop despite having saved a non-null next address, or continue using a null or otherwise different address. It performs no reconciliation or retry.

During ascent, the starting child is the attachment. Each step reads that child’s offset-4 parent, selects the parent as candidate, and reads the parent’s offset-8 link. Ascent continues if that link equals the child just ascended from; otherwise the selected parent remains the candidate.

There are no general null guards, cycle checks, or traversal limits.

**With stable links**, descent follows offset 8 once and then offset 12 until null; ascent finds the first parent whose offset-8 link is not the child just left. This is consistent with predecessor selection, but that interpretation depends on additional structural invariants.

### Final candidate comparison

When candidate checking reaches this stage:

1. F-fcff71612ea5 receives the selected candidate address and returns an opaque four-byte token.
2. F-f75c770a6cd7 receives the comparison-context address, that returned token, and the incoming token.

The operand arrangement differs from search comparison: the incoming token is now the third argument rather than the second.

A zero final comparison causes the selected candidate address to be written to result offset 0, followed by disposition zero. The insertion dependency is not invoked.

Any nonzero final comparison selects general insertion.

The candidate and original attachment remain retained across these calls. The function does not redo traversal or revalidate them afterward.

### General insertion

F-d96aaf447a13 receives:

- The address of the general-insertion output slot;
- The container address;
- A literal zero;
- The original search attachment;
- The incoming token.

The attachment is not replaced by the candidate used for final comparison.

After normal return, the slot’s four-byte contents are copied to result offset 0, followed by disposition one. There is no independent insertion-status check.

### Insertion-output initial contents

The insertion dependency receives writable storage whose prior contents are established as follows:

| Search and subsequent path | Boundary-shortcut slot | General-insertion slot |
|---|---|---|
| Nonempty search; nonzero mode | Not used | Zero |
| Nonempty search; zero mode; last comparison zero | Not used | Zero |
| Nonempty search; zero mode; last comparison nonzero | Zero if shortcut taken | Reloaded boundary address if general insertion is reached |
| Empty search; nonzero mode | Not used | Uninitialized |
| Empty search; zero mode | Uninitialized if shortcut taken | Reloaded boundary address if general insertion is reached |

For zero mode after an empty search, the remembered comparison remains one, so boundary loading necessarily precedes any insertion call.

These are caller-side initializations, not dependency guarantees. The dependency can observe them through its output-storage argument. If it returns without modifying an initialized slot, the unchanged zero or boundary-address token is copied to the caller. No determinate unchanged token is established for an uninitialized slot.

## Side effects

### Direct effects

Externally addressed writes in the supplied body are limited to the four-byte result and one-byte disposition.

Other direct operations include container and link reads, marker reads, private temporary initialization, and reading the insertion-output slot after a dependency returns. No direct allocation, release, link update, or balancing operation is present.

The function performs fixed-offset address formation. No bounds checks or overflow handling are supplied for these accesses.

### Dependency-mediated effects

No dependency is established as pure or as preserving globals, container state, node links, or incoming-token referents.

Observable sequencing includes:

- Temporary zeroing before each search comparison.
- Selected child-link reads after each search comparison.
- Mode reading after the complete search.
- Header and boundary reloading only in zero mode with a nonzero last comparison.
- Candidate extraction before final comparison.
- Reading insertion-output storage after insertion returns.
- Writing the four-byte caller result before disposition.

The repeated structural reads have no intervening dependency call, but synchronization or stability is not established. They must not be collapsed into single observations without a stable-memory precondition. This description does not establish support for concurrent mutation.

### Ownership, errors, and lifetime

The function explicitly acquires or releases no ownership. Whether dependencies allocate, retain references, copy values, release objects, or invalidate candidates is unknown.

There is no explicit error result, recovery branch, or insertion-success verification. Invalid memory, malformed links, nontermination, and abnormal dependency completion can prevent normal output.

An insertion dependency that leaves its output unchanged does not necessarily leave an unspecified token: initialized slots retain their established zero or boundary-address contents. Uninitialized-slot outcomes remain unresolved.

## Acceptance examples

These are conditional static expectations, not executed tests.

### Nonzero mode after a nonempty search

Given a terminating nonempty search and any nonzero mode byte:

- Candidate extraction and final comparison are skipped.
- General insertion receives the original search attachment.
- Its output slot initially contains zero.
- If the dependency leaves the slot unchanged, the caller receives token zero and disposition one.

This does not prove successful insertion.

### Nonzero mode after an empty search

Given a null initial root and nonzero mode:

- No search comparison or temporary reset occurs.
- General insertion receives the header from the second initial header read.
- Its output slot is uninitialized.
- If the dependency writes a complete token **T**, the caller receives **T** and disposition one.
- If it leaves the slot unchanged, no determinate result token is established.

### Nonempty boundary shortcut

Given zero mode, a nonzero last search comparison, and attachment equal to the reloaded boundary:

- The general-output slot receives the boundary address.
- Insertion instead receives the separate shortcut-output slot, initially zero.
- An unchanged shortcut slot yields result zero and disposition one.
- Neither candidate extraction nor final comparison occurs.

### Empty conventional header

Given an empty search, identical initial and reloaded headers, and a header boundary pointing to itself:

- Zero mode takes the boundary shortcut.
- The shortcut-output slot is uninitialized, despite the boundary address having been stored in the other slot.
- A complete dependency write of **T** yields **T** and disposition one.

### General insertion after structural checking

Given zero mode, a nonzero last comparison, attachment unequal to boundary, valid terminating candidate selection, and a nonzero final comparison:

- General insertion receives the original attachment, not the checked candidate.
- Its output slot initially contains the reloaded boundary address.
- If left unchanged, that boundary address is returned with disposition one.

### Candidate acceptance

Given a path reaching final comparison and a zero final result:

- The selected candidate address is returned with disposition zero.
- No insertion dependency is invoked.
- Any previously stored boundary token is irrelevant to this result.

### Distinct descent observations

Given that the first attachment offset-8 read yields address **A**, while the second yields a different non-null address **B**, descent starts at **A**, not **B**.

If a descent candidate’s first offset-12 read yields **C**, but its second read is null, descent stops at the current candidate rather than following **C**.

Both expectations require all accesses actually reached to be valid; they do not assert supported concurrent-mutation semantics.
