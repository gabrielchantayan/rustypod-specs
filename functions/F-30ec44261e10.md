# F-30ec44261e10

## Purpose

F-30ec44261e10 describes a represented control-flow fragment that repeatedly invokes unresolved dependencies, transforms 32-bit values, accesses memory through implicit and calculated addresses, and conditionally executes a software halt.

The supplied representation includes invalid instruction data and incomplete control flow. It does not establish a business-level purpose, a conventional standalone calling convention, or normal return behavior. This contract therefore describes observable operations and state transitions without characterizing the fragment as an allocator, serializer, validator, or ordinary returning API.

The following distinctions apply throughout:

- **Established static evidence:** operations, widths, predicates, ordering, and state assignments visible in the supplied representation.
- **Inferred intent:** structural interpretations that impose no additional behavioral requirements.
- **documented_only:** behavior not resolved by that representation.

No runtime tests have been performed.

## Interface

### Explicit inputs

The represented interface has three 32-bit inputs:

| Input | Established role |
|---|---|
| First input | No direct use appears in the represented body. |
| Second input | No direct use appears in the represented body. |
| Third input, called **control** | Selects arithmetic, contributes to calculated addresses, and is replaced between iterations. |

The lack of direct uses of the first two inputs does not establish that dependencies cannot observe their incoming machine-state representations. Actual dependency calling conventions are unresolved.

### Implicit and retained state

Execution also depends on:

- A 32-bit implicit **carry**.
- An implicit address state called **live base**.
- An incoming **link-like state** used to select the first indirect-call target.
- Accessible memory and dependency behavior.

Their initial values are not established by the explicit interface.

The **retained next-base candidate** is distinct from the live base. It is captured during each iteration and later assigned back to the live base. A dependency or halt handler may change the live base without changing the retained candidate. Consequently, restoring the candidate can overwrite an intervening live-base change.

Other named values below describe retained results in the representation. They do not establish a general machine-level register-preservation convention.

### Outputs, widths, and termination

No normal return or return value is represented. Execution can repeat indefinitely, encounter the software halt, or reach an invalid-instruction termination marker after a dependency call. There is no established success code, recoverable-error protocol, or rollback mechanism.

A word is 32 bits, a halfword 16 bits, and a byte 8 bits. One dependency returns a represented 64-bit value, divided below into **low word** and **high word**.

Unsigned 32-bit arithmetic wraps modulo \(2^{32}\). Address calculations are represented in a 32-bit address model; wraparound does not establish address validity. Logical right shifts introduce zero bits. Stores narrower than their source retain its low bits.

Some expressions pass through signed 32-bit intermediates. The contract identifies their represented bit-pattern results without claiming portable source-language behavior at every signed-overflow boundary. Signed right-shift interpretation and independent machine-level validation remain documented_only.

## Behavior

### 1. Ordered dependency prefix

Each iteration begins with these eight calls, in order:

| Dependency | Established role |
|---|---|
| F-indirect-01 | Target selected using the current link-like state plus `0xEE0`. |
| F-indirect-02 | Supplies a 32-bit **prefix result**. |
| F-indirect-03 | No explicit result is retained. |
| F-indirect-04 | No explicit result is retained. |
| F-indirect-05 | No explicit result is retained. |
| F-indirect-06 | No explicit result is retained. |
| F-indirect-07 | Supplies a 32-bit value. |
| F-indirect-08 | Receives that value logically shifted right by 13 and supplies the represented 64-bit result. |

Except for F-indirect-01, these targets use fixed represented address expressions. The IDs distinguish call roles, not independently resolved function identities.

Two captures occur between calls:

- Immediately after F-indirect-02, **threshold** becomes prefix result minus 3.
- After F-indirect-04 and before F-indirect-05, **advanced carry** becomes the then-current carry plus 6.

Advanced carry is therefore a retained calculation, not a later reread of carry. Calls after its capture may affect implicit state.

### 2. Control-dependent calculations

When control is zero:

- Threshold retains prefix result minus 3.
- **Saved value** is advanced carry.
- **Auxiliary value** is advanced carry logically shifted right by 12.

When control is nonzero:

- Threshold becomes advanced carry logically shifted right by 20, minus `0x55`, modulo \(2^{32}\).
- Saved value becomes twice the low word modulo \(2^{32}\).
- Auxiliary value captures the then-current carry, before the subsequent unconditional carry replacement.

The nonzero threshold calculation is represented as a logical shift by 8 followed by a signed shift by 12. The first shift produces a nonnegative signed intermediate, so the combined logical shift by 20 preserves that calculation.

Next:

1. **Next control** becomes control minus `0x53`, modulo \(2^{32}\).
2. **Sign bit** becomes 1 when bit 31 of the low word is set, otherwise 0.
3. Carry becomes twice the low word modulo \(2^{32}\).
4. A 32-bit store writes the low word at the then-current live base plus `0x28C`.

The sign test concerns bit 31 of the low word, not bit 63 of the full result.

### 3. Initial next-base capture and additional-memory predicate

Define **difference** as low word minus threshold modulo \(2^{32}\). The initial **working result** has the bit pattern

\[
\text{difference}-(1-\text{sign bit}) \pmod{2^{32}}.
\]

Following the unconditional word store, and before the additional-memory predicate is evaluated, the representation captures the live base as the retained next-base candidate. The intervening working-result calculation has no represented memory access or call.

This capture is independent of later live-base changes. It is not deferred until the footer.

The additional-memory path is selected only if both unsigned comparisons hold:

- Low word is less than or equal to threshold.
- Sign bit is less than or equal to difference.

These predicates must not be replaced by a signed comparison or an assumed conventional carry/borrow test.

If the path is skipped, the footer receives the working result and high word. The retained next-base candidate remains the value captured here; it does not track subsequent changes to the live base.

### 4. Additional-memory path and halt continuation

On entry to this path:

1. A 32-bit **saved word** is read at the then-current live base plus `0x2CC`.
2. A software halt with immediate `0x26` is executed.

The halt's continuation and handler effects are unresolved. All following operations on this path are conditional on execution resuming at the represented continuation.

After resumption:

- **Displacement** becomes control minus `0x21`.
- **Record address** becomes threshold plus `0x70`.
- A 16-bit store writes the low 16 bits of record address at displacement plus the then-current carry.

The carry used by this halfword store is live implicit state. It must not be assumed still to equal twice the low word if the halt handler can change it.

Five 32-bit stores follow in this order:

| Destination | Stored value |
|---|---|
| Then-current live base minus `0x04` | Fixed address value `0x0894A20A`; referent unresolved |
| Then-current live base minus `0x08` | Saved value |
| Then-current live base minus `0x0C` | Saved word captured before the halt |
| Then-current live base minus `0x10` | High word |
| Retained candidate described below | Auxiliary value |

Each base-relative destination uses the live implicit base at its represented evaluation point, not the earlier retained candidate.

When the final store is prepared, the retained next-base candidate is replaced with the then-current live base minus `0x14`. The auxiliary value is then stored through that retained address. This is the second candidate capture point.

The five stores therefore cannot unconditionally be described as writes below the pre-halt base. If the live base remains stable throughout these stores, they occupy five consecutive descending words below that stable value. Stability across the halt or other unresolved effects is not established.

After the stores, execution reads, in order:

1. A 32-bit **record word** at record address.
2. A 32-bit **record offset** at threshold plus `0x74`.

Both reads precede the following branch condition. Neither is protected by its record-address nonzero check.

### 5. Branch ending in invalid instruction data

This branch is selected when both conditions hold:

- Record address is nonzero.
- Threshold plus `0x3E`, interpreted as signed 32-bit, is greater than `−51`.

A byte store is supplied by two 32-bit reads:

- The word at threshold plus `0x7C` supplies a destination address, to which `0x1D` is added.
- The word at threshold plus `0x80` supplies the stored low byte.

**The relative order of these reads is unresolved.** They appear in opposite operands of one represented assignment. Neither may be specified as necessarily preceding the other, including when reads have side effects or one faults.

If both reads and the byte store complete, the subsequent order is:

1. Store record word as a 32-bit value at displacement plus record offset.
2. Read a 32-bit value at the then-current live base plus `0x24C`.
3. Invoke F-a041a7d81f49 with that value and record offset plus `0x50`.
4. Reach the represented invalid-instruction termination marker if the call returns into the shown continuation.

The base-relative argument read uses live base, not the retained next-base candidate.

No continuation from this branch to the footer is represented. Its earlier writes are not rolled back if the dependency fails, does not return, or returns into invalid instruction data.

### 6. Alternate additional-memory branch

If the preceding two-part condition is false, execution instead:

1. Reads a 32-bit word at threshold plus `0x7C`.
2. Replaces carry with that word logically shifted right by 12.
3. Reads an unsigned byte at the new carry plus `0x14`.
4. Replaces next control with that byte, zero-extended to 32 bits.
5. Calls F-a3ad1bfc4246 with record word, displacement, the zero-extended byte, and the shifted argument described below.
6. Calls F-indirect-09 and retains its represented signed 32-bit result as the working result.
7. Replaces the second footer argument with that result signed-shifted right by 22.

The fourth argument of F-a3ad1bfc4246 is formed by interpreting record offset as signed 32-bit, shifting right by 20, converting the result to unsigned 32-bit, and logically shifting right by 8.

For a negative record offset, this is not generally equivalent to one logical right shift by 28.

The retained next-base candidate remains the address captured when the final base-relative store was prepared. Changes to live base by either dependency do not themselves update that candidate.

### 7. Footer and repetition

F-indirect-10 receives the working result and the current second footer argument.

Its target uses offset `0xEB0` with a path-dependent fixed address value: one applies when additional memory was skipped, and another after F-indirect-09.

Before this call, the represented link-like state is assigned `0x085721CD`. The next iteration's first target calculation uses the link-like state available then. The assignment is established; preservation of that implicit state across F-indirect-10 is not independently established.

If F-indirect-10 returns:

1. Control becomes next control.
2. The retained next-base candidate is assigned back to live base.
3. Execution repeats.

The final assignment can overwrite a live-base change made by F-indirect-10 or an earlier dependency.

Accordingly:

- On the skip path, the restored base equals the value captured after the unconditional word store—not necessarily the iteration-entry base or the live base immediately before the footer.
- On the continuing additional-memory path, the restored base equals the live base observed when the final base-relative store was prepared, minus `0x14`—not necessarily the iteration-entry base minus `0x14`.

“Unchanged” and “decreased by `0x14`” describe net iteration effects only under additional state-stability assumptions.

## Acceptance examples

These are conditional static consequences, not executed tests.

### Predicate boundaries

If low word and threshold are both zero, difference and sign bit are zero. Both comparisons hold, working result is `0xFFFFFFFF`, and additional memory is selected.

If both are `0x80000000`, difference is zero but sign bit is one. The second comparison fails; additional memory is skipped, and the footer receives working result zero and the high word.

If low word is zero and threshold is one, difference is `0xFFFFFFFF` and working result is `0xFFFFFFFE`. Additional memory is selected.

### Skip-path restoration overwrites a footer change

Suppose the post-store candidate capture observes live base `0x1000`, and additional memory is skipped. If the footer changes live base to `0x3000` and returns, the subsequent assignment restores `0x1000`.

This does not establish that the iteration-entry base was `0x1000`.

### Halt-modified base and carry

Suppose the initial candidate is `0x1000`, but the halt resumes with live base `0x2000`, which then remains stable until the final base-relative store is prepared.

The five stores target `0x1FFC`, `0x1FF8`, `0x1FF4`, `0x1FF0`, and `0x1FEC`. The final preparation replaces the candidate with `0x1FEC`. If the alternate path and footer return, live base is ultimately assigned `0x1FEC`, even if a dependency changed it meanwhile.

If the halt also changes carry, the halfword-store address uses that changed carry, not necessarily twice the low word.

### Signed dependency argument

For record offset `0x80000000`, the fourth argument to F-a3ad1bfc4246 is `0x00FFFFF8`, assuming arithmetic signed right shift. A single logical shift by 28 would instead yield `0x00000008`.

### Reads before the null check

If threshold is `0xFFFFFF90`, record address wraps to zero. Following halt continuation and the preceding stores, reads at addresses zero and four are attempted before the record-address condition. A fault can prevent that condition from being evaluated.

### Halt and unordered-read limits

If the halt does not resume, the unconditional word store and pre-halt saved-word read have occurred; the later stores and record reads are not established to occur.

On the truncated branch, either relative order of the two reads supplying the byte store is consistent with the representation. If one faults, whether the other already occurred is unresolved.

## Uncertainties

- **documented_only — representation fidelity:** Invalid instruction data and truncated control flow prevent a complete executable specification.
- **documented_only — implicit state:** Initial carry, live base, and link-like state are unspecified.
- **documented_only — preservation:** Dependency and halt-handler changes to implicit state are unresolved. Candidate capture and later restoration are nevertheless explicit represented operations.
- **documented_only — halt:** Termination, trapping, resumption, and handler effects are unknown.
- **documented_only — operand evaluation:** The two reads supplying the truncated branch's byte store have no established relative order.
- **documented_only — arithmetic:** Independent confirmation of signed shifts, signed-overflow boundaries, and signed conversions is unavailable.
- **documented_only — memory model:** Endianness, alignment, address validity, concurrency, and memory-mapped access effects are unspecified.
- **Inferred intent:** Descending stores and candidate restoration resemble frame-like bookkeeping, but establish neither stack ownership nor a conventional frame.
- **Inferred intent:** Repetition resembles continuation-driven control flow, but no higher-level protocol is established.
