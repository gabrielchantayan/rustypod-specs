## Behavior

### Dependency-call phase

The visible execution begins with a long straight-line series of indirect calls. No explicit input-dependent branch or loop is represented in this phase.

The first dependency’s 32-bit result is shifted left by eight bit positions and supplied to the next dependency. Later calls repeatedly consume similarly shifted primary results, upper halves of combined results, secondary call-produced values, and explicit zero arguments.

The ordering of calls is significant even when:

- A call has no displayed arguments.
- Its primary result is discarded.
- A later call receives only zero arguments.
- Two argument expressions appear numerically redundant.

A call without displayed arguments is not established to be context-free. Its real signature and implicit state requirements remain unknown. Likewise, ignored results do not make a dependency side-effect-free.

The main visible classes of argument transformation are:

- Left shifts of 32-bit quantities, often by eight positions.
- Extraction of upper and lower 32-bit portions of 64-bit results.
- Unsigned right shifts.
- Bit masking before a shift.
- Reuse of an earlier result after intervening calls.
- Repetition of the same transformed value in multiple argument positions.
- Explicit propagation of zero values.

Masks select fields of various widths, including 24, 22, 20, 19, 17, 14, 13, 12, and 11 bits. The selected fields are not established to be lengths, addresses, flags, or encoded characters.

For example, masking a 32-bit quantity with 0x000fffff and then shifting right by ten selects original bits 10 through 19 and produces a value between zero and 1023. A subsequent left shift by five places it in the range zero through 32736. This must not be interpreted as a 20-bit right shift of an unmasked quantity.

Some intermediates are explicitly set to zero and later shifted or masked without another visible assignment. Under the represented arithmetic, these remain zero. This fact does not authorize removal of surrounding dependency calls.

### Arithmetic boundaries

The representation uses both signed-looking and unsigned-looking 32-bit expressions. This contract does not silently resolve every expression into portable modulo arithmetic.

For unsigned 32-bit operations, masking, zero-filling right shifts, and retention of the low 32 bits after a left shift provide a definite bit-vector interpretation. For signed-looking left shifts and multiplications, overflow behavior is **documented_only** without the underlying execution semantics.

Consequently:

- Byte stores retain the low eight bits of the supplied value.
- Halfword stores retain the low sixteen bits.
- Byte reads used in word assignments are zero-extended.
- Address scaling must not be treated as unlimited-precision multiplication.
- Chained shifts can discard information before a later operation.
- A shift followed by the opposite shift is not generally an identity.

One late byte assignment uses a signed-looking word shifted right by a count derived from an address’s low byte. The count can exceed 31. Neither the handling of oversized counts nor the signed right-shift rule is established sufficiently to define that byte for every possible input.

### Transition into direct memory mutation

After the long dependency-call phase, execution enters a region containing explicit reads and writes, with no intervening dependency calls shown until the final transfer.

Its first observable mutations establish a useful ordering boundary:

- A word derived from an earlier shifted result is written at offset 0x14 from the upper half of the latest combined result.
- A byte is written at offset 9 from another computed base.
- A word is written at offset 0x54 from a base formed by scaling the latest lower result.
- The byte at the earlier offset-9 destination is written again with a different source.

These are distinct writes. The first byte value cannot be discarded merely because the destination is written again later.

Subsequent operations clear fields, read byte and word fields, publish values at other offsets, and modify fixed storage. Values read after a write depend on the memory state at that point, including all aliases.

For example, a word field is cleared and later read, but a byte-derived write intervenes elsewhere. Without a non-aliasing guarantee, the later word read cannot universally be replaced with zero.

## Acceptance examples

These examples are conditional static acceptance criteria, not runtime test results.

### Input forwarding

Given first input 0x12345678 and second input 0x90abcdef, if the entry dependency is reached, its displayed argument sequence is 0x12345678, 0x90abcdef, 0x12345678.

No requirement to dereference either input follows.

### Shift truncation

If a relevant unsigned 32-bit result is 0x12345678, shifting it left by eight produces 0x34567800. Shifting that result right by eight produces 0x00345678, not the original value.

Acceptance requires preserving the lost upper byte.

### Masked field extraction

If a relevant value is 0x000fffff, selecting its low twenty bits and shifting right by ten yields 1023. Shifting that selection left by five yields 32736.

Upper bits outside the selected twenty-bit field do not contribute.

### Mixed-width literal stores

If all three 0x3a destinations are valid and distinct, acceptance requires an 8-bit write, a 16-bit write, and a 32-bit write at their respective destinations.

A replacement that emits three bytes does not preserve the represented effects.

### Repeated writes

If the repeated region targets observable writable storage, acceptance cannot be based solely on its final word values. The byte and word writes occur repeatedly in the represented order.

Whether that storage is actually externally observable is **documented_only**.

### Aliasing-sensitive reads

If an intervening write aliases a word field that was previously cleared, a later read of that field must observe the then-current bytes. Assuming the read returns zero requires an additional non-aliasing or memory-semantics condition.

### Final invocation

If all preceding operations complete and the final target is executable, acceptance requires four displayed arguments with 0x72 first. The remaining arguments use their captured values; they are not automatically reread from their original locations at transfer time.
