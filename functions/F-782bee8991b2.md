# F-782bee8991b2

## Purpose

F-782bee8991b2 coordinates a two-input, 32-bit-word operation into a destination object. It selects the input with the greater signed length, conditionally requests destination capacity, delegates the common-length prefix to an opaque dependency, and handles the longer input’s remaining words.

The visible continuation interprets a nonzero prefix result as a carry of one. It propagates that carry through unsigned 32-bit words, appends a word of value one if necessary, and copies any remaining suffix.

**Established behavior:** the visible suffix processing performs increment-and-wrap carry propagation.

**Inferred intent:** the complete operation may be multiprecision addition. That interpretation is not an unconditional contract because the common-prefix dependency’s arithmetic is unknown.

Normal completion returns 1 and clears the destination field at byte offset 12. The only explicit failure return is 0 after a zero result from the capacity dependency.

## Interface

### Arguments and representation

The function receives three object references, in order:

1. A mutable destination descriptor.
2. The first input descriptor.
3. The second input descriptor.

The supplied representation uses the following four-byte fields:

| Byte offset | Use |
|---|---|
| 0 | Backing-storage address, represented in a 32-bit field |
| 4 | Signed 32-bit logical word count |
| 8 | Signed 32-bit capacity |
| 12 | Metadata cleared on normal completion |

The function explicitly reads only offsets 0 and 4 of the input descriptors. It reads or writes all four listed destination fields.

Backing-storage elements are unsigned 32-bit words, spaced four bytes apart. Increasing indices are treated as successive carry positions. The byte order within a word is not established by the supplied body.

The meaning of the fourth field is unknown beyond its final zero write. No sign, ownership, or status interpretation is established.

### Results

- **0:** a required capacity operation returned zero. The wrapper performs no subsequent initial-length publication, prefix call, suffix processing, or final metadata clearing.
- **1:** execution reached the normal end.

The return value is not the carry value and does not report the final length. An outstanding carry is represented by a trailing word and a length-field increment.

There is no explicit rejection path for negative lengths, inaccessible storage, invalid addresses, unsupported overlaps, or arithmetic overflow.

### Preconditions for ordinary word-array behavior

Ordinary use requires:

- Valid, readable input descriptors.
- A valid destination descriptor writable through byte offset 15.
- Accessible storage for every read and write made by this function and its dependencies.
- Lengths and addresses for which signed arithmetic and four-byte indexing remain valid.
- Capacity semantics compatible with F-08bc2fc94856.
- Aliasing supported by both the prefix dependency and the visible forward-processing order.

Nonnegative lengths are a suitable precondition for the inferred arithmetic operation, but the function does not enforce them.

These conditions do not establish dependency preservation. A dependency may change descriptors, backing words, allocation state, or other memory unless an independent contract excludes those effects.

## Behavior

### Input selection and retained lengths

Input lengths are compared as signed 32-bit values.

- If the first input is shorter, the second becomes the **selected longer input**, and the first becomes the **selected shorter input**.
- Otherwise, the first remains the selected longer input.

Equal lengths therefore favor the first input. This choice determines the order of backing addresses supplied to the prefix dependency.

The selected lengths are retained before either dependency is called. Subsequent loop bounds and prefix count use those retained values, not refreshed descriptor lengths.

The supplied body evaluates the length-selection condition twice before the capacity stage. Under stable descriptor contents, both evaluations select consistently. No contract is established for concurrent mutation between these reads.

### Capacity gate

The destination capacity is compared, as a signed 32-bit value, with the retained longer length plus one.

If capacity is smaller, F-08bc2fc94856 is called with:

- The original destination descriptor.
- The requested capacity: retained longer length plus one.

A zero result immediately returns 0. A nonzero result permits continuation.

The returned value is not adopted as a replacement destination descriptor. All later destination descriptor accesses use the original argument. If storage management relocates the backing allocation, any required address update must therefore be visible through that original descriptor.

The extra word is requested whether or not the eventual prefix result or suffix values produce a final carry.

No rollback is visible on failure. Changes already made by the capacity dependency are not restored.

### Initial length publication and backing-address capture

After the capacity gate passes, the wrapper writes the retained longer length to the destination length field.

It then reads the destination backing address and the selected longer input’s backing address. The selected shorter input’s backing address is read for the prefix call.

Consequences:

- The initial length write precedes prefix processing.
- Backing addresses are obtained after capacity management.
- Descriptor aliasing can affect which backing addresses are observed.
- The destination and longer-input addresses used by the continuation are captured before the prefix call and are not refreshed afterward.

The initial length write is not a promise about the final length. The prefix dependency may change that field, and a no-carry path does not restore it.

### Common-prefix processing

F-630ff3ddabe3 receives:

1. Captured destination backing address.
2. Captured selected-longer backing address.
3. Selected-shorter backing address.
4. Retained shorter length.

The wrapper interprets the result only as zero or nonzero:

- Zero skips carry propagation.
- Any nonzero value initiates propagation of one.

The result’s magnitude is not added to a word. A result other than one still causes increments of exactly one.

The dependency determines the common-prefix output. The wrapper alone does not establish the resulting values below the retained shorter length.

The dependency’s effects are not restricted to that prefix by the supplied evidence. In particular, it is not established that the dependency preserves longer-input suffix words, destination metadata, globals, or the validity of captured addresses.

### Carry propagation

Continuation begins at the retained shorter-length index, using the captured destination and longer-input backing addresses.

When the prefix result is nonzero and the current index is below the retained longer length, each propagation step:

- Reads the current longer-input word.
- Increments it modulo \(2^{32}\).
- Writes the result to the corresponding destination position.
- Advances to the next position.

Propagation continues only when the increment wraps:

- A source value from 0 through 4,294,967,294 becomes one greater and absorbs the carry.
- A source value of 4,294,967,295 becomes zero and leaves carry outstanding.

The source read precedes the corresponding destination store. Exact same-position aliasing is compatible with this visible step, provided the storage remains valid. This does not establish safety for shifted overlap or for the prefix dependency.

The source values used are those present when continuation reads them. Pre-call input values are not necessarily preserved across the opaque prefix call.

### Final carry insertion

If carry remains outstanding when the current index reaches or exceeds the retained longer length, the wrapper:

1. Writes word value 1 at the current destination cursor.
2. Reads the destination’s then-current length field and increments it by one.

For ordinary nonnegative lengths, the cursor is at the retained longer-length position. Equal input lengths reach this case immediately when the prefix result is nonzero.

The length update is an increment of the current field, not an assignment of the retained longer length plus one. If the prefix dependency or an overlapping write changed the field, that changed value is incremented.

The trailing-word store occurs before the length increment. Metadata/storage overlap can therefore affect the length value subsequently read.

### Remaining suffix copy

After carry handling, the wrapper compares the current destination and source cursor addresses.

If they are equal, suffix copying is skipped. Otherwise, remaining words are copied from the captured longer-input storage into the destination in increasing index order, up to the retained longer length.

This is not a general overlap-safe copy:

- There is no backward-copy branch.
- There is no visible temporary buffer.
- A destination store may overwrite a later source word under shifted overlap.

After a final carry insertion, ordinary processing has already exhausted the retained suffix, so no suffix words remain to copy.

### Completion

The destination field at byte offset 12 is set to zero, then the function returns 1.

No visible step removes leading zero words, normalizes an empty result, reduces capacity, or restores destination length after the prefix dependency.

## Side effects

### Explicit wrapper writes

On a successful path, the wrapper can write:

- The retained longer length to destination offset 4 before prefix processing.
- Incremented suffix words during carry propagation.
- A trailing word of value 1.
- An incremented destination length after trailing-word insertion.
- Unprocessed suffix words during forward copying.
- Zero to destination offset 12 at completion.

Prefix output and capacity-management mutations are additional dependency effects, not characterized by these wrapper writes.

### Observable ordering

The established sequence is:

1. Select operands and retain lengths.
2. Read destination capacity.
3. Optionally call capacity management.
4. Stop immediately if that call returns zero.
5. Publish the initial destination length.
6. Obtain backing addresses.
7. Invoke prefix processing.
8. Use retained bounds and captured addresses for carry handling and suffix copying.
9. Clear the fourth destination field.
10. Return 1.

Later descriptor reads can observe dependency mutations. Conversely, captured addresses are not updated to follow any relocation performed during prefix processing.

### Ownership and failure

No direct allocation or release is visible in this wrapper. Capacity management is delegated to F-08bc2fc94856.

The wrapper does not explicitly transfer ownership of input descriptors or release their storage. This does not establish that dependencies preserve ownership or refrain from releasing memory.

A capacity failure is not established to be atomic. The dependency may have modified the destination or other state before returning zero. The wrapper performs no recovery.

These examples describe the visible wrapper under their stated conditions. For examples involving continuation, captured storage must remain valid. Values specified at continuation entry are values **after F-630ff3ddabe3 returns**, not assumptions about preserved pre-call inputs.

- If F-08bc2fc94856 returns zero, the wrapper returns 0.

### Equal-length ordering

Given stable input lengths of 2:

- The first input is selected as longer.
- The second input is selected as shorter.
- The prefix dependency receives count 2.

If it returns zero, the wrapper performs no suffix-word writes and does not restore destination length. A final length of 2 requires that dependency effects and overlapping writes leave the initial length publication unchanged.

If it returns nonzero, the wrapper writes 1 at captured destination word 2. If the destination length is still 2 when the subsequent increment reads it, the resulting length is 3.

### Zero result with a longer suffix

- The wrapper copies words 2 and 3 from the captured longer-input storage, unless the suffix cursors are equal.
- The copied values are those encountered by the forward reads after the dependency returns.
- If those source words contain 6 and 9 at continuation entry and remain unaffected before their reads, destination words 2 and 3 become 6 and 9.
- Length is 4 only if no dependency effect or overlapping write changes the initial value.
- The fourth destination field is cleared.

Nothing about destination words 0 and 1 follows without a prefix-dependency contract.

- The capacity threshold is 1.
- After the capacity gate passes, the wrapper writes destination length zero.
- Prefix processing is still called with count zero.

If the dependency returns zero, there are no suffix-word writes and no later length assignment. The destination length remains zero **only if the dependency and overlapping writes leave that field unchanged**.

If the dependency returns nonzero, the wrapper writes 1 at captured destination word 0 and increments the then-current destination length. The resulting length is one only if that increment reads zero.

Whether the prefix dependency accepts count zero is unknown.

## Uncertainties

The following remain **documented_only**:

- **Complete arithmetic meaning:** carry-like continuation does not prove the prefix operation is addition.
- **Signed overflow:** longer length plus one, index increments, and destination length increments use signed metadata arithmetic. No portable wrapping contract is established at signed limits.
- **Negative lengths:** the wrapper does not reject them, but valid dependency counts and indexed addresses are not established.
- **Address arithmetic:** four-byte offsets must remain representable and within accessible storage.
- **Dependency preservation:** neither dependency is known to preserve globals, descriptors, suffix values, captured storage, or ownership.
- **General aliasing:** exact cursor equality bypasses copying; shifted overlap and prefix alias safety remain unestablished.
- **Metadata/storage overlap:** backing-word writes may alter descriptors if regions overlap.
- **Failure atomicity:** no rollback guarantee is supplied.
- **Fourth-field meaning:** only its final zero write is established.
- **Concurrency:** no synchronization or concurrent-mutation guarantees are visible.
