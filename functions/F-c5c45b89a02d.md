# F-c5c45b89a02d

## Purpose

F-c5c45b89a02d transfers a bounded number of 16-bit payload elements from one length-prefixed memory region to another. It writes the resulting element count into the destination’s leading 16-bit field.

The source’s leading field supplies the available count. The caller supplies an independent upper bound. For valid, non-overlapping memory, the destination receives the smaller of those two counts followed by that many source payload elements.

The operation is a forward, element-by-element transfer. It does not provide snapshot-copy semantics for overlapping regions. In particular, writing the destination count can change source payload that has not yet been read.

This is a static behavioral contract. No runtime tests have been performed.

## Interface

### Inputs

The function receives three values:

- **Source address:** the address of a readable sequence of 16-bit unsigned elements. The first element is a count; subsequent elements are payload.
- **Destination address:** the address of a writable sequence of 16-bit unsigned elements using the same count-prefixed layout.
- **Limit:** an unsigned 32-bit maximum number of payload elements to transfer. Its unit is elements, not bytes.

Either address may be null. If either is null, the function returns without accessing either memory region.

For non-null addresses, let:

- **L** be the unsigned 16-bit value read from the source’s first element.
- **N** be the smaller of L and the limit.

N is therefore in the inclusive range 0 through 65,535, regardless of how large the limit is.

### Memory layout

Both regions have the following logical layout:

| Element position | Meaning | Width |
|---|---|---|
| 0 | Payload count | 16 bits |
| 1 through count | Payload elements | 16 bits each |

In an 8-bit-byte address model, adjacent elements are two bytes apart. A destination holding N payload elements requires space for N + 1 elements, or 2 × (N + 1) bytes.

The function does not read or verify an allocation size. The count stored at the source is treated as data, not as proof that the corresponding memory exists.

The operation transfers numeric 16-bit elements. The source does not establish a portable byte-order encoding or perform byte swapping.

### Result

There is no return value. For a completed call with valid, non-overlapping memory:

- The destination count is N.
- The next N destination elements equal the corresponding source payload elements.
- Destination elements after that transferred range are unchanged.

No status code distinguishes a successful transfer from the null-address no-op.

### Preconditions for defined memory access

For non-null inputs:

- The source count element must be readable.
- The destination count element must be writable.
- Each of the N source payload elements must be readable when its turn is reached.
- Each of the N destination payload elements must be writable when its turn is reached.
- Addresses, alignment, and address arithmetic must be valid under the execution environment.

A zero limit does not remove the requirement to read the source count or write the destination count.

## Behavior

### Null-address handling

The function checks whether either address is null before dereferencing either one.

If either is null:

- It does not read a source count.
- It does not write a destination count.
- It does not access payload.
- It returns without reporting an error.

Consequently, when one address is null, this path does not require the other address to reference accessible memory.

### Count acquisition and destination header writes

For non-null inputs, the function first reads the source count once. That captured value is L.

It then writes L to the destination count field unconditionally.

Only after that initial write does it apply the limit:

- If the limit is less than L, it writes the limit to the destination count field as a second write and selects the limit as N.
- Otherwise, it performs no second count write and selects L as N.

The distinction is observable in the represented memory-access sequence. A limiting call does not merely write the final count: it first writes the original source count, then replaces it with the smaller count.

The conversion of the limit to a 16-bit count is safe on the branch where it occurs. That branch requires the limit to be less than L, and L cannot exceed 65,535. Thus the value written there is representable without truncation.

### Payload transfer

After completing the count-field writes, the function processes payload positions in increasing order, beginning immediately after each count field.

For each position from 1 through N:

1. It reads the current 16-bit source payload element.
2. It writes that value to the corresponding destination payload element.
3. It proceeds to the next position.

All count-field writes precede every payload read. Each payload read precedes its corresponding payload write, and that write precedes the next payload read.

The operation does not:

- Scan for a terminator.
- Interpret payload values.
- Stop at a zero-valued element.
- Clear unused destination capacity.
- Add a trailing terminator.
- Copy the entire source merely because the destination has room.

When N is zero, there are no payload reads or writes.

### Loop bounds and arithmetic

The represented loop uses a 32-bit unsigned working count, decrements it before deciding whether to transfer another element, and interprets the decremented value as signed for termination.

Within the reachable count range, this produces exactly N transfers:

- Starting from zero, the first decrement wraps to the all-ones 32-bit value. Its signed interpretation is negative, so no payload is accessed.
- Starting from a positive N, each value from N − 1 down through zero permits one transfer.
- The next decrement wraps from zero to the all-ones value and terminates the loop.

The signed test therefore does not prematurely stop any reachable positive count. N never approaches the positive-to-negative boundary of a signed 32-bit value.

The destination cursor is advanced before the termination check, including the check that ends the loop. No element is dereferenced as a result of that final advance. Address validity still depends on the execution environment and the caller-provided regions; the function performs no overflow or boundary validation.

### Aliasing and overlap

The function does not inspect whether the regions overlap and does not preserve an independent copy of source payload.

If source and destination are identical:

- The source count is captured before any count write.
- Limiting the transfer replaces the shared count with N.
- Each transferred payload element is read and written at the same location.
- Payload beyond N is not accessed by the transfer.

For other overlap arrangements, earlier writes can affect later reads. This includes the initial destination count write, not just payload writes.

Accordingly, “destination payload equals the original source payload prefix” is guaranteed only when the memory relationship prevents writes from changing unread source payload. It must not be assumed for arbitrary overlap.

## Side effects

The function’s explicit side effects are writes to the destination count field and selected destination payload elements.

For non-null inputs, the represented operation performs:

- One read of the source count.
- One destination count write, plus a second count write if the limit is smaller than the captured source count.
- Exactly N payload reads and N payload writes, assuming execution completes normally.

The source region is not explicitly written through the source address. It can nevertheless be modified when destination storage overlaps it.

No allocation, deallocation, ownership transfer, global-variable access, logging, or dependency call appears in the supplied body. The function neither retains either address nor releases either region.

The destination count is published before the payload transfer finishes. No synchronization, atomicity, transactional update, or rollback is established. If execution stops during a payload access, the destination can contain the selected count together with only a partially transferred payload.

The source-level sequence does not by itself establish hardware-level access ordering for concurrent observers, memory-mapped devices, or other environments requiring explicit volatile or synchronization semantics.

## Dependencies

No external function dependencies are present in the supplied body.

The operation depends on the execution environment for:

There is no callee whose memory ownership, global-state preservation, or error behavior must be assumed.

## Acceptance examples

These examples are conditional predictions from static evidence, not executed tests. Bracketed sequences show 16-bit elements, with the count first.

### Full transfer below the limit

Given a source containing **[3, 11, 22, 33]**, a separate destination with sufficient writable space, and a limit of 8:

- The destination becomes **[3, 11, 22, 33]** over the affected range.
- There is one destination count write.
- Exactly three payload elements are transferred.
- Later destination elements remain unchanged.

### Truncation by the limit

Given a source containing **[4, 10, 20, 30, 40]**, a separate destination, and a limit of 2:

- The destination count is first written as 4, then as 2.
- The resulting destination prefix is **[2, 10, 20]**.
- Source payload elements 30 and 40 are not read by the transfer.
- Destination storage after the second payload element is unchanged.

### Zero limit with a nonzero source count

Given a readable source count of 7, a writable destination count, and a limit of zero:

- The source count is read.
- The destination count is written as 7, then as 0.
- No payload is accessed.
- Payload storage need not be read or written for this call.

### Empty source

Given a source count of zero and valid count-field addresses:

- The destination count is written as zero once.
- No payload is accessed, regardless of the limit.

### Null-address no-op

If either address is null:

- Neither count field nor any payload is accessed.
- No destination state changes through this operation.
- The function returns without a status result.

### Identical addresses with truncation

Given shared source and destination storage **[3, 10, 20, 30]** and a limit of 2:

- The shared count becomes 2.
- The two selected payload elements remain 10 and 20.
- The third payload element remains 30.
- The resulting storage is **[2, 10, 20, 30]**.

### Destination starts at the first source payload element

Given backing storage **[3, 10, 20, 30, 40]**, the source at its first element, the destination at its second element, and a limit of at least 3:

- The initial destination count write replaces 10 with 3.
- The first payload read then observes that newly written 3.
- Each subsequent forward write replaces the next source value before it is read.
- The resulting backing storage is **[3, 3, 3, 3, 3]**.

This case demonstrates why snapshot-copy semantics are not part of the contract.

### Maximum source count

Given a source count of 65,535, a limit of at least 65,535, and valid non-overlapping regions:

- N is 65,535.
- Exactly 65,535 payload elements are transferred.
- The affected destination region contains 65,536 elements, including its count.

A larger 32-bit limit cannot increase the transfer beyond the 16-bit source count.
