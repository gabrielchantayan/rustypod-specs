# F-751713b3ad7c

## Purpose

F-751713b3ad7c conditionally updates a one-byte state value in an indirectly referenced object and, when an update is required, writes the value 1 to a separate one-byte field.

The decision compares the existing byte against the **full 32-bit unsigned input**, not against that input reduced to one byte. The stored state value, however, is only the input’s low eight bits. Consequently, an input greater than 255 always takes the update path, even when its low byte already matches the stored byte.

The second byte appears intended to indicate that state has changed or requires attention. That interpretation is inferred intent. The established behavior is simply a conditional write of 1; this function does not establish who reads that field or what its values mean elsewhere.

## Interface

### Inputs

The function receives two inputs:

| Input | Represented width | Meaning |
|---|---:|---|
| Object address | 32 bits | Address used to locate a four-byte indirect-object address field. |
| Requested value | 32-bit unsigned | Value compared against the existing byte and, on the update path, narrowed for storage. |

The first input is represented as an integer in the supplied static material but is used for memory addressing. No validation establishes that it is a valid object address.

### Referenced layout

Offsets are in bytes.

| Relative location | Access width | Role |
|---|---:|---|
| Object address + 0xF00 | 4 bytes | Address of an indirectly referenced object. |
| Indirect-object address + 0xB78 | 1 byte | State value being compared and conditionally replaced. |
| Indirect-object address + 0xB90 | 1 byte | Field conditionally assigned 1. |

The two byte fields are 0x18 bytes apart when reached through the same indirect-object address. These offsets establish access locations, not a complete object layout or allocation size.

The four-byte address field is read separately for the comparison, the state write, and the final write as those operations become necessary. A single retained indirect-object address must not be assumed.

### Output

There is no return value and no explicit status result.

An ordinary return can mean either:

- The existing state byte matched the full requested value, so no writes were performed.
- The comparison did not match, and both byte writes were performed.

### Preconditions

For ordinary completion, each memory access actually reached must be valid:

- The four-byte address field must be readable whenever it is accessed.
- The state byte used for comparison must be readable.
- On the update path, the resolved state destination and the subsequently resolved second destination must be writable.

The supplied material does not establish alignment requirements, address-space boundaries, or defined behavior for invalid address arithmetic. These remain environmental preconditions rather than checked conditions.

## Behavior

### Comparison and early return

The function first reads the indirect-object address from the object’s address field. Through that address, it reads the existing state as an **unsigned eight-bit value**.

It compares that value, numerically in the range 0 through 255, with the complete 32-bit unsigned requested value.

If the values are equal, the function returns immediately. In this case:

- The indirect-object address field has been read once.
- The state byte has been read once.
- No state byte is written.
- The second byte is neither read nor written.
- The indirect-object address field is not read again by this function.

Equality is possible only when the requested value is at most 255. The function does not mask or narrow the requested value before this comparison.

### Update path

If the comparison is unequal, the function performs two ordered writes.

First, it reads the indirect-object address field again. At offset 0xB78 from this newly obtained address, it stores the requested value narrowed to one byte. The stored byte is the requested value modulo 256.

Second, after that state write, it reads the indirect-object address field again. At offset 0xB90 from this third address, it stores the one-byte value 1.

The function then returns.

Neither destination byte is read as part of these assignments. In particular, the second byte is not checked for an existing value of 1 before being written.

### Width-sensitive cases

Comparison width and storage width are deliberately distinct in this contract:

- Requested value 255 can compare equal to an existing byte of 255.
- Requested value 256 cannot compare equal to any existing state byte. Its stored byte is 0.
- Requested value 257 cannot compare equal to an existing byte of 1. Its stored byte is nevertheless 1.
- Requested value 4,294,967,295 cannot compare equal to any existing state byte. Its stored byte is 255.

The byte-store representation is relevant here; no signed interpretation of the resulting stored byte is needed to describe the observable result.

### Repeated address resolution

Under stable, non-overlapping storage, all three address-field reads on the update path yield the same address, so the two writes affect the expected pair of fields in one indirect object.

That stability is not checked or guaranteed by the function itself. If an intervening write or environmental action changes the address field, later accesses use its later contents.

In particular, if the first byte-store destination overlaps the address field, that store can alter the address used for the final byte write. The function does not retain the earlier indirect-object address to prevent this. Whether such an overlapping layout is valid in the surrounding execution environment is unknown.

## Side effects

The established effects are confined to the described memory accesses.

On the equality path, the function performs no writes. It does not clear, normalize, or otherwise modify the second byte.

On the update path:

1. It writes one byte at the state destination resolved for that write.
2. It then writes one byte containing 1 at the second destination resolved afterward.

A write remains part of the behavior even if the destination already contains the same byte value. This matters especially when a requested value above 255 has a low byte equal to the existing state: both writes still occur.

No allocation, deallocation, ownership transfer, external function call, logging, or explicit synchronization is present in the supplied material. The function uses caller-accessible storage directly; it does not establish or extend that storage’s lifetime.

The two writes are not described as a transaction. There is no explicit rollback mechanism. If execution is interrupted or fails after the first write, the supplied material does not guarantee completion of the second write or restoration of the first.

The access order above describes the supplied static behavior. It does not establish hardware atomicity, inter-thread visibility guarantees, or a memory-ordering protocol.

## Acceptance examples

These are conditional behavioral examples, not executed tests. Unless otherwise stated, they assume valid memory, a stable indirect-object address, ordinary non-overlapping storage, and uninterrupted execution.

| Initial state byte | Requested value | Initial second byte | Required result |
|---:|---:|---:|---|
| 7 | 7 | 0 | Return without writes; both bytes remain unchanged. |
| 7 | 7 | 9 | Return without writes; the second byte remains 9 rather than being cleared or normalized. |
| 7 | 8 | 0 | Write state byte 8, then write second byte 1. |
| 7 | 8 | 1 | Write state byte 8, then write second byte 1 even though it already contains 1. |
| 0 | 256 | 0 | Take the update path; write state byte 0, then second byte 1. |

| 255 | 4,294,967,295 | 0 | Take the update path; write state byte 255, then second byte 1. |

Additional conditional acceptance cases:

- If the initial comparison matches and the second destination would be inaccessible, the function does not access that destination.
- If the initial comparison differs, later changes to the state byte do not trigger a second comparison; the function proceeds with the two writes.
- If address-field contents change between resolutions in an environment where such changes have defined behavior, each later access uses the newly read address rather than a cached initial address.

## Uncertainties

The following are **documented_only**:

- The application-level meaning of either byte field.
- Whether callers restrict requested values to 0 through 255.
- Whether the address field is immutable during execution.
- Whether valid objects can overlap the address field or other referenced storage.
- Alignment, byte order, and fault-handling requirements of the execution environment.
- Behavior for null, dangling, unmapped, or otherwise invalid addresses.
- Concurrency guarantees and whether these locations can denote special-purpose memory.
- Any broader object ownership or lifetime protocol.

Inferred intent: the function resembles a state setter with a change indicator. That inference does not justify changing the full-width comparison, avoiding same-byte stores on the update path, or clearing the second byte on the equality path.

## Evidence

Established static evidence consists of the supplied function body: one full-width equality decision using an unsigned byte read, an immediate no-write return on equality, and an unequal path containing two ordered byte assignments with repeated address-field reads.

The represented input widths, access widths, offsets, narrowing behavior, and absence of explicit calls or validation support this contract. No broader program behavior is established.

No runtime tests have been performed. The acceptance examples are consequences of the static behavior under their stated preconditions, not observed execution results.
