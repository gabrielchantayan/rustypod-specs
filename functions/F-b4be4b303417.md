# F-b4be4b303417

## Purpose

The supplied static representation establishes a memory-mutating operation followed by an indirect transfer of control. It does not establish a reliable application-level purpose.

The operation writes to several interconnected address regions, replaces link-like fields, stores low-order portions of addresses in byte and halfword locations, reads three global data slots, and supplies three arguments to an unresolved indirect target.

Names such as “list insertion,” “initialization,” or “object update” would imply invariants not supported by the evidence. None is adopted here.

This contract describes the visible memory effects and their ordering. It does not certify that the supplied representation accurately recovers the original executable’s function boundary, calling convention, or control flow.

## Interface

### Explicit inputs

| Input | Represented width | Established use |
|---|---:|---|
| Payload | 32 bits | Written to several word fields; its least-significant byte is also written separately. |
| Tag | 8 bits | Written once to a byte field early in the operation. |
| External base | 32-bit address representation | Receives a word containing its own address at offset `0x54`. |

No explicit result value is established. The supplied representation declares no result and shows a return after the indirect operation, but the indirect target’s actual return behavior is unknown.

### Implicit inputs

The operation also depends on three incoming machine-state values not represented as formal parameters:

- **Primary base:** the principal writable address region.
- **Secondary base:** another writable address region.
- **Seed base:** a value used both as an address and as data.

These are required inputs to the visible behavior, not initialized local state. Their provenance and calling-convention roles are unknown.

Three additional global data slots are read near the end:

- **Global address slot A:** a 32-bit value used in address arithmetic and truncated stores.
- **Global address slot B:** a 32-bit value used in address arithmetic and passed to the indirect target.
- **Global payload slot:** a 32-bit value written through an address derived from slot B.

The indirect destination is an additional unresolved execution dependency.

### Memory model and preconditions

The representation uses 8-bit byte accesses, 16-bit halfword accesses, and 32-bit word accesses. Addresses and link-like values are represented in 32-bit quantities.

Successful execution requires every reached access to be valid with the requested width and access permission. This includes addresses formed by:

- Adding fixed offsets to incoming or loaded bases.
- Adding two address-like values.
- Doubling a loaded or global value.
- Converting a loaded byte to a 32-bit value and adding `0x44` or `0x45`.

No validation of these requirements is visible. Null, alignment, bounds, and arithmetic checks are absent from the supplied representation.

The necessary valid-memory region is not merely a fixed-size structure at each input. Later accesses depend on pointers read from fields, and earlier writes may alter those fields.

## Behavior

### Interpretation rules

All offsets below are byte offsets. “Word,” “halfword,” and “byte” mean 32, 16, and 8 bits respectively.

A low-byte or low-halfword write retains only the corresponding least-significant bits of its source value. It does not write the rest of that value.

Descriptions of a **retained** value refer to an earlier read whose value is reused. Descriptions of a **fresh read** require observing memory at that later point. This distinction matters if storage aliases or changes externally.

The phases below preserve the order visible in the supplied representation. They describe required observations at that level, not guaranteed processor-level transactions after compilation.

### 1. Initial writes and replacement of the primary link

The opening effects, in order, are:

1. The primary word at `0x44` receives the seed base, followed by the tag at primary byte `0x11`.
2. The primary word at `0x74` is read and retained.
3. Primary byte `0x0D` receives the seed base’s low byte.
4. The secondary word at `0x10` receives the payload.
5. The seed base is written again to primary word `0x44`.
6. Secondary byte `0x10` receives the payload’s low byte.
7. Primary word `0x54` and secondary word `0x60` receive the payload, in that order.
8. Primary word `0x74` is read again. This second result supplies the **former linked base** used below.
9. Primary word `0x74` is replaced with the seed base.
10. The former linked base’s word at `0x40` receives the payload.
11. Primary byte `0x0D` receives the low byte of the first retained `0x74` read.

The byte store at secondary offset `0x10` follows a word store to the same starting address. It remains a separate visible write. Without a byte-order specification, the resulting word must not simply be assumed equal to the original payload.

### 2. Traversal through the former link and seed

The former linked base’s word at `0x44` is read. Primary word `0x54` then receives the primary base itself, and the external base’s word at `0x54` receives the external base itself.

Next, the former linked base’s word at `0x14` supplies a **former child**. Seed byte `0x11` receives the low byte of the previously read former-link `0x44` value.

The seed word at `0x14` is read, and its low byte is written to the former child’s byte at `0x15`. The seed word at `0x14` is then read again to select a **seed child**. These two reads must not be merged in the presence of aliasing or externally changing memory.

Primary word `0x64` is read and retained. The seed child’s word at `0x20` receives `0x00000073`. Primary word `0x64` is read again; the low byte of this second read is written to seed-child byte `0x09`.

### 3. Modification of the seed child’s successor

The seed child’s word at `0x74` selects a **successor**.

At that successor, the operation:

- Writes the primary base’s low byte to offset `0x0D`.
- Reads word `0x54` and writes that same value back to the same word.
- Writes byte `0x74` to offset `0x09`.

The self-assignment is an explicit read followed by an explicit write in the representation. Its final ordinary-memory value may be unchanged, but it cannot be omitted from this contract, particularly for device-backed or otherwise externally observable memory.

Primary word `0x44` then receives the first retained primary `0x64` value. The successor’s word at `0x34` receives the primary base.

The successor’s word at `0x04` selects a **successor child**. Its word at `0x24` receives the second retained primary `0x64` value. Primary byte `0x19` receives the low byte of the first retained primary `0x64` value.

### 4. A second traversal from the current primary link

The successor child’s word at `0x74` is read and retained as a **carried link**. Its word at `0x04` is then read and retained as a **carried word**.

A fresh read of primary word `0x74` selects the **current root**. Although an earlier write placed the seed base there, aliasing may have changed that word subsequently.

The current root’s word at `0x14` selects a target whose word at `0x54` receives the carried link. The current root’s word at `0x04` is then read.

Primary byte `0x0D` receives the low byte of the second retained primary `0x64` read twice in succession. Primary word `0x64` receives the carried word. The just-selected current-root child’s word at `0x30` receives `0x00000074`.

A fresh traversal through current-root word `0x04`, then offset `0x74`, selects a **branch base**. Primary word `0x64` is read again; its low byte is retained and written to primary byte `0x1D`.

### 5. Rewriting primary links and branch fields

A fresh read of primary word `0x44`, followed by a word read at offset `0x14` from that value, selects a **replacement child**.

The branch base’s word at `0x34` receives the carried link. Primary word `0x14` receives the replacement child. Primary word `0x54` is read and retained before the replacement child’s byte at `0x09` receives the primary base’s low byte.

A traversal through branch-base word `0x04`, followed by word `0x74`, selects a **branch descendant**. Its byte at `0x15` receives the carried link’s low byte.

Then, in order:

- Primary word `0x54` receives the primary base.
- Primary byte `0x11` receives the branch base’s low byte.
- Branch-descendant byte `0x11` receives the low byte of the retained primary `0x54` read.
- Branch-descendant word `0x64` is read and retained.
- Primary byte `0x09` receives the retained low byte from the earlier fresh primary `0x64` read.

### 6. Operations on a freshly loaded branch child

A fresh read of branch-base word `0x04` selects a **branch child**.

Its byte at `0x09` receives the primary base’s low byte. Its word at `0x50` is then read and retained. The child’s byte at `0x11` receives the low byte of the retained branch-descendant `0x64` value, and its byte at `0x09` receives the primary base’s low byte again.

Primary word `0x14` receives the retained branch-descendant `0x64` value. Primary byte `0x0D` receives the branch child’s low address byte. The branch child’s byte at offset zero receives the low byte of its retained `0x50` word.

Branch-base words `0x74` and `0x14` are read, in that order. The former becomes a retained **indexed component**; the latter selects a **branch parent**.

The branch child’s word at `0x54` receives its own address.

### 7. Constant stores and preparation for computed addressing

The branch parent’s word at `0x04` selects a **leaf base**.

The following writes occur in order:

- Leaf byte `0x10` receives decimal `100`, or `0x64`.
- Primary word `0x54` receives `0x00000064`.
- Leaf word `0x40` receives `0x00000064`.
- Primary byte `0x0D` receives the low byte of the retained branch-descendant `0x64` value.
- Branch-parent byte `0x09` receives the leaf base’s low byte.
- Primary word `0x24` receives the retained branch-descendant `0x64` value.
- Branch-parent byte `0x11` receives the primary base’s low byte.

Thus, the primary `0x54` field is not left as a self-link by the visible write sequence: a later word store places numeric `100` there. Subsequent aliasing or indirect-target behavior can still change it.

### 8. Computed halfword stores and byte-derived addressing

Global address slot A is read. Primary word `0x74` is then read freshly and retained as the **final link**.

The operation performs these accesses in order:

1. A halfword at the address formed by adding the final link and primary base receives the final link’s low 16 bits.
2. A halfword at twice the leaf base receives the low 16 bits of global address slot A’s retained value.
3. A byte is read at the sum of the retained indexed component and primary base.
4. A halfword at the sum of retained global slot A and the final link receives the final link’s low 16 bits.
5. The first halfword store, at final link plus primary base, is repeated.
6. A word at the byte-derived address plus `0x45` receives `0x00000045`.

The loaded byte is represented as passing through a plain-character interpretation before conversion to an unsigned 32-bit value. Whether byte values `0x80`–`0xFF` become `128`–`255` or sign-extended values is not established independently of the target character model.

### 9. Final global reads, writes, and indirect transfer

Global address slot B is read, followed by the global payload slot. Primary word `0x44` is then read freshly and retained for the final argument.

Next:

- A byte at the byte-derived address plus `0x44` receives `0x44`.
- A word at twice the retained global slot B value receives the global payload.
- A halfword at the carried link plus the retained global slot B value receives that global value’s low 16 bits.

The indirect target is then invoked with three represented arguments:

1. The byte-derived 32-bit value bitwise-ORed with `0x44`.
2. The retained value from global address slot B.
3. The final fresh read of primary word `0x44`.

Bitwise OR in the first argument is not interchangeable with adding `0x44`, nor does it necessarily identify either preceding byte-derived store address.

## Side effects

The visible effects are in-place memory reads and writes, including writes of addresses, truncated addresses, numeric constants, self-links, and a read/write of unchanged word data.

No allocation, deallocation, reference-count operation, or ownership transfer is explicitly established before the indirect transfer. Writing a self-address or link-like value does not establish ownership.

No guarantee is made that the indirect target preserves global state, preserves the modified regions, returns normally, or leaves allocation state unchanged.

Aliasing is unrestricted by the supplied evidence. Consequently:

- Distinct descriptive bases may identify overlapping storage.
- Byte and halfword writes may alter later pointer-like word reads.
- A later traversal cannot generally be substituted with an earlier cached path.
- Final field contents cannot be summarized safely using only the last syntactically named store to each base and offset.

No synchronization or atomicity contract is established. The representation’s access order is not evidence of cross-thread visibility guarantees.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

1. **Early tag replacement.** If primary byte `0x11` is ordinary writable memory, the initial tag store occurs. If execution reaches the later primary-byte store without a conflicting alias, the branch base’s low byte replaces that tag. An implementation preserving the tag throughout would not match the visible sequence.

2. **Repeated accesses remain observable.** If the successor’s word at `0x54` is instrumented storage, the operation must account for both its read and same-value write. If primary byte `0x0D` is similarly observable, the two consecutive identical stores in phase 4 remain separate represented effects.

3. **Independent primary `0x64` reads.** If the first and second reads return different values, primary word `0x44` receives the first retained value, while the successor child’s word at `0x24` receives the second. Treating both reads as one observation would lose established behavior.

4. **Width truncation.** If the final link is `0x12345678` and the relevant computed addresses are valid, each specified final-link halfword store writes `0x5678`, not the complete address. The byte order of that halfword remains target-dependent.

5. **Low-byte address case.** If the computed byte read returns `0x02`, its signedness is immaterial. The subsequent word store starts at `0x47`, the byte store starts at `0x46`, and the first indirect argument is `0x46`.

6. **High-byte address case.** If that byte is `0x80`, the resulting address and first indirect argument depend on the character-extension model. A contract selecting one interpretation without further evidence is unacceptable.

7. **No guaranteed error result.** If a required derived address is invalid, no checked failure path or status return is established. The contract must not invent a recoverable error, rollback, or completion guarantee.
