# F-94989df6c6d2

## Purpose

F-94989df6c6d2 transfers four individual bytes from a source region to destinations selected through a mutable output cursor. It advances the stored cursor by one byte before each destination-byte write.

For ordinary, non-overlapping storage, the effect is to append four source bytes to an output region and leave the cursor immediately after them. The transfer is sequential, not an atomic four-byte operation: each source byte is read separately, and the cursor is read again for every byte.

**Established:** four byte-transfer stages, four cursor updates, no explicit result, and no visible validation.

**Inferred intent:** a fixed-size four-byte append operation.

**Not established:** a larger serialization format, the meaning of the transferred bytes, or any caller-level ownership or capacity policy.

## Behavior

### Transfer ordering

The function performs four successive stages, corresponding to source offsets zero through three.

Within each stage, the visible ordering is:

1. Read the current destination address from the cursor slot.
2. Read the byte at that stage’s source offset.
3. Store the destination address advanced by one byte into the cursor slot.
4. Write the previously read source byte to the destination address obtained at the beginning of the stage.

This ordering is material to the contract. The destination-byte write uses the address read before the cursor update, not the incremented address. The source byte is also captured before that update.

The next stage reads the cursor slot again. There is no single cursor read followed by four writes using a permanently retained starting address. There is likewise no initial snapshot of all four source bytes.

These are the access-order relationships established by the supplied representation. They do not independently establish hardware transaction boundaries, compiler barriers, or synchronization guarantees.

### Ordinary non-overlapping result

When the cursor slot, the four source bytes, and the four destination bytes do not interfere with one another, successful completion has these effects:

- The first source byte is written at the initial destination cursor.
- The following three source bytes are written at the next three consecutive addresses.
- The cursor slot finishes four bytes beyond its initial value.
- The source region is unchanged.

Each cursor update advances by one byte. This is not an advance by the size of a four-byte word.

### Overlapping source and destination

Overlap does not cause a separate handling path. Later source reads observe memory after earlier cursor and destination writes.

In particular, a destination write can replace a source byte that has not yet been read. That replacement can then propagate through later stages. Therefore, the function does not promise preservation of the source’s entry-time four-byte sequence under overlap.

Identical source and destination addresses are a distinct case: when the cursor slot is separate, each byte is read before being written back to its own location, and the cursor still advances four bytes.

### Overlap involving the cursor slot

The cursor slot is ordinary mutable storage in the visible operation. No disjointness check protects it.

If a destination-byte write overlaps the slot, it can alter the address representation that the next stage reads. Subsequent destinations may therefore cease to be consecutive. The final slot value need not equal the initial value plus four.

If the source overlaps the slot, later source reads can observe bytes written by earlier cursor updates. Within a particular stage, however, the source byte is read before that stage updates the slot.

The exact results of these cases depend on address representation, endianness, overlap position, and whether the resulting accesses remain valid. They must not be reduced to an unconditional “copy four bytes and add four” rule.

If an access fails, the function does not specify a recoverable outcome. Earlier effects may remain.
