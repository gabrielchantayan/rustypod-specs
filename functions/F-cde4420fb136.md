# F-cde4420fb136

## Purpose

F-cde4420fb136 performs an in-place structural rearrangement consistent with a left rotation of a linked binary-tree node. It promotes the selected node’s right child, moves that child’s left subtree into the selected node’s former right-child position, and makes the selected node the promoted node’s left child.

That tree interpretation is inferred from the field relationships and writes. The established behavior is narrower: the function reads and rewrites particular 32-bit fields, conditionally updates either a root slot or an incoming parent link, and returns without a result value.

The function does not search for a node, allocate storage, release storage, check structural validity, or update balancing metadata. Correct tree behavior depends on valid incoming structure and writable storage.

## Behavior

### Structural result under valid, non-overlapping input

For a well-formed tree with stable memory, normal completion produces these relationships:

1. The selected node’s right child becomes the promoted node’s former left child.
2. If that transferred subtree is nonzero, its parent becomes the selected node.
3. The promoted node takes the selected node’s former parent reference.
4. The selected node’s incoming link—either the root slot or one child field in its former parent—is redirected to the promoted node.
5. The promoted node’s left child becomes the selected node.
6. The selected node’s parent becomes the promoted node.

The selected node’s left child and the promoted node’s right child are not directly modified. No balance factor, height, color, count, key, payload, or other metadata is accessed in the supplied body.

### Observable access order

The operation is a sequence of ordinary field accesses, not an atomic structural update. Its ordering matters for aliased storage, concurrent access, and interruptions.

**Subtree transfer occurs first.** The function captures the selected node’s right-child reference as the promoted-node address. It reads the promoted node’s left-child field and writes that value into the selected node’s right-child field.

Only after that write does it read the promoted node’s left-child field again to decide whether a parent-link repair is needed. If that read is nonzero, the field is read once more to obtain the destination node, and that destination’s parent field is written with the selected-node address.

Thus, the supplied body does not use one immutable snapshot of the transferred-subtree reference for the transfer, the zero test, and the parent update. With conventional non-overlapping objects and no concurrent mutation, those reads agree. With overlapping storage or intervening changes, they need not agree.

**The promoted node then inherits a parent reference.** The selected node’s parent field is read and copied into the promoted node’s parent field. This occurs before the context’s root-holder reference is read.

**The incoming link is then replaced.** The function derives the root slot from the context and compares the root reference with the selected-node address:

- If equal, it writes the promoted-node address into the root slot.
- If unequal, it reads the selected node’s parent field again. It examines that parent’s left-child field. If the left-child reference equals the selected-node address, that field is replaced with the promoted-node address. Otherwise, the parent’s right-child field is replaced with the promoted-node address.

The non-root fallback does not verify that the parent’s right child actually references the selected node. Failure of the left-child comparison is sufficient to select the right-child field.

The root decision depends on the root-slot comparison, not on whether the selected node’s parent reference is zero.

**The local parent-child pair is completed last.** The promoted node’s left-child field is written with the selected-node address. Finally, the selected node’s parent field is written with the promoted-node address.

Consequently, the incoming link is redirected before the two final writes establish the completed local relationship.

### Conditional behavior and boundaries

The transferred-subtree zero check is the only explicit null-like check. A zero transferred-subtree reference is copied into the selected node’s right-child field, but no parent update through that reference is attempted.

By contrast:

- A zero selected-node address is not rejected.
- A zero promoted-node reference is not rejected.
- A zero context root-holder reference is not rejected.
- A zero parent reference on the non-root path is not rejected.

Such inputs still cause address-based accesses. Their validity and consequences depend on the surrounding address space and execution environment.

The parent value copied to the promoted node and the parent value later used to repair a non-root incoming link are separate reads. They coincide under the normal structural assumptions, but the function does not enforce that correspondence.

These examples are conditional static expectations, not runtime results. Except where stated otherwise, assume valid, distinct objects, stable memory, and adequate access permissions.

### Root rotation with no transferred subtree

Initially:

- The root slot references the selected node.
- The selected node’s right child is the promoted node.
- The promoted node’s left child is zero.
- The selected node’s parent contains an arbitrary valid root-parent representation.

- The promoted node’s parent contains the selected node’s former parent value.

### Rotation with a transferred subtree

Expected on normal completion:

- That child becomes the selected node’s right child.
- Its parent field becomes the selected-node address.
- The promoted node’s left child becomes the selected node.
- The remaining incoming-link changes follow the root or non-root case.

This distinguishes an empty transfer from a transfer requiring a parent-link repair.

### Non-root selected node on its parent’s left

Expected on normal completion:

- That parent’s left-child reference becomes the promoted-node address.
- Its right-child reference is not directly changed.
- The root slot is not written.
- The promoted node inherits the selected node’s former parent reference.

### Non-root selected node on its parent’s right

Initially, the root slot differs from the selected-node address, the parent’s left child differs from the selected node, and the parent’s right child is the selected node.

Expected on normal completion:

- The parent’s right-child reference becomes the promoted-node address.
- Its left-child reference and the root slot are not directly changed.

### Inconsistent incoming link

Initially, the root slot differs from the selected-node address, and neither child field in the selected node’s stated parent references the selected node.

If all accesses remain valid, the function nevertheless overwrites that parent’s right-child field with the promoted-node address. It does not report the inconsistency.

This is established branch behavior, not acceptance of the input as a valid tree.

### Missing promoted node

No successful tree-rotation outcome is specified. The function attempts to read the left-child field using that zero promoted-node reference before any explicit validity check. Whether execution faults or accesses mapped storage is environment-dependent.
