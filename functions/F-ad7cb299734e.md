# F-ad7cb299734e

## Purpose

F-ad7cb299734e conditionally dispatches an input record through handlers obtained from a receiver’s dispatch table. It has three ordered stages:

1. An optional preliminary call, selected by an outer discriminator of `0x16` and a nested-discriminator arithmetic comparison.
2. One principal call, selected using newly read discriminator values.
3. An optional fallback call, considered only after a zero principal result and selected by an outer discriminator of `0x0F` plus a field-equality comparison.

Any nonzero handler result terminates dispatch and is returned unchanged. A zero result permits the next stage, if any. If no invoked handler returns nonzero, the function returns zero.

“Receiver,” “record,” “preliminary,” “principal,” and “fallback” describe structure and ordering. They do not establish application-level message meanings, validation responsibilities, or ownership.

## Interface

### Arguments and result

The function receives two argument values:

- **Receiver:** identifies storage whose initial field supplies a dispatch-table address. Another receiver field participates in fallback eligibility.
- **Record:** identifies storage containing an outer discriminator and an associated field. The associated field is interpreted as a nested-record address during certain selections, or as a comparison value during fallback eligibility.

Every invoked handler receives the original receiver and record argument values, in that order. The nested-record address is never substituted for the record argument.

The result is an integer. A nonzero handler result is propagated without Boolean normalization. Under the represented signed-integer interpretation, negative results terminate dispatch just as positive results do. No success, failure, or error-code meaning is established for either sign or for zero.

### Path-dependent preconditions

Ordinary completion requires readable storage and valid indirect-call targets only where the execution path actually accesses them:

- The record’s outer discriminator must remain readable at every reached stage.
- **During preliminary eligibility and principal selection only**, an outer-discriminator read of `0x16` requires the associated field to be readable as an address and the nested discriminator reached through that address to be readable.
- **During fallback eligibility**, no outer-discriminator value causes a nested-record access. A value other than `0x0F`, including `0x16`, requires only the outer-discriminator read before the function returns zero.
- If fallback eligibility observes `0x0F`, the associated comparison field and receiver comparison field must be readable. The associated field is not dereferenced as an address on this path.
- Whenever a handler call is reached, the receiver’s dispatch-table field and selected table entry must be readable, and the selected target must be callable with the two supplied arguments.

These requirements apply at the time of each access. Validity at function entry alone is insufficient if a handler later invalidates needed storage.

There are no explicit null, bounds, alignment, lifetime, or callable-target checks. Invalid accesses and invalid indirect calls have no specified recoverable outcome within this contract.

## Behavior

### Preliminary eligibility

The function first reads the record’s outer discriminator at offset `0x04`.

If that value differs from `0x16`, preliminary dispatch is skipped. This stage does not read the associated field or nested storage on that path.

If the value is `0x16`, the function reads the associated address at record offset `0x08`, then the nested discriminator at nested-record offset `0x04`. It subtracts `0x2500` from the nested discriminator and compares the result with `3`.

For values whose subtraction is representable under the signed 32-bit interpretation, equality selects nested discriminator `0x2503`. Under a 32-bit wrapping interpretation, the same comparison selects the `0x2503` bit pattern. The supplied representation does not independently settle signed-overflow semantics for other inputs; those cases remain documented_only.

If the arithmetic comparison succeeds, the function reads the receiver’s dispatch-table address, resolves F-0130 through table offset `0x130`, and calls it with the original arguments.

- A nonzero result is immediately returned.
- A zero result continues to principal selection.

If eligibility fails, execution continues directly to principal selection. Preliminary dispatch is not retried.

### Principal selection and call

The function reads the outer discriminator again rather than reusing the preliminary-stage value.

If this read yields `0x16`, the function reads the associated address and then the nested discriminator:

- A nested discriminator of `0x2A` selects F-010C through table offset `0x10C`.
- Any other nested discriminator selects F-0110 through table offset `0x110`.

If the newly read outer discriminator differs from `0x16`, F-0110 is selected without reading the associated field or nested storage for principal selection.

After determining the entry offset, the function reads the receiver’s then-current dispatch-table address and the selected entry. It calls the selected handler with the original receiver and record arguments.

Exactly one principal handler is called whenever this stage is reached:

- A nonzero result is returned immediately.
- A zero result advances to fallback eligibility.

Returning zero from one principal handler does not cause the other principal handler to be called.

### Fallback eligibility and call

Following a zero principal result, the function reads the outer discriminator again.

If that value differs from `0x0F`, the function returns zero. It does not read the associated field, the receiver comparison field, a nested discriminator, or a fallback-table entry on this path.

In particular, an outer discriminator of `0x16` at this stage does **not** cause nested access. A zero-returning principal handler may leave the outer discriminator as `0x16` and the associated field containing an invalid nested address without violating any nested-memory requirement for the remaining path.

If fallback eligibility observes `0x0F`, the function reads:

1. The associated value at record offset `0x08`.
2. The receiver comparison field at offset `0x50`.

These values are compared for equality. The associated value is treated as a value, not followed as a pointer.

If the values differ, the function returns zero without calling a fallback handler. If they are equal, the function reads the receiver’s current dispatch-table address, resolves F-00E0 through table offset `0x0E0`, and calls it with the original arguments.

The fallback result becomes the function result: nonzero is returned unchanged, while zero leads to a zero return. No stage is revisited.

### Mutation and repeated reads

Handler effects can change later decisions:

- A zero-returning F-0130 can change the outer discriminator, nested address, or nested discriminator before principal selection.
- A zero-returning principal handler can change the outer discriminator or either comparison value before fallback eligibility.
- A handler can replace the receiver’s dispatch-table address or alter its entries before a later call is resolved.

A previously observed discriminator, nested address, or table address is not a preservation guarantee for a later stage. Conversely, later stages access only the fields their own branches require. Fallback never needs nested storage, even if the preceding principal selection did.

The described order is the access and call structure of the supplied representation. It does not establish atomicity, synchronization, thread safety, volatile-access semantics, or a consistent snapshot under concurrent mutation.

## Side effects

The function contains no explicit writes to receiver, record, nested-record, dispatch-table, or global storage. Its direct observable actions are memory reads, indirect calls, and result propagation.

Handler effects are not bounded by the function body. A handler may modify reachable storage, globals, external resources, allocation state, or ownership relationships. No dependency is known to preserve globals or to retain, consume, free, or otherwise transfer either argument.

A zero handler result does not establish that the handler:

- Left the record or receiver unchanged.
- Performed no externally visible work.
- Preserved the dispatch table.
- Preserved the lifetime of either argument or nested storage.

If a handler invalidates storage that a later stage actually reads, the function proceeds without a lifetime check. If it invalidates storage that no remaining branch accesses, that invalidation alone does not create an additional access requirement.

On a normally completing valid path, at least one handler is called. There can be at most three calls: preliminary, principal, then fallback. Calling all three requires state changes between stages, because unchanged preliminary-eligible state has an outer discriminator of `0x16`, whereas fallback requires `0x0F`.

No explicit allocation, release, resource acquisition, or ownership transfer occurs in this function itself.
