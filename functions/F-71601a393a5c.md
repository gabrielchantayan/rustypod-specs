# F-71601a393a5c

## Purpose

F-71601a393a5c forwards its second 32-bit input to a dynamically selected operation associated with an object obtained from another function. The acquired object is also supplied to the selected operation.

The first input has no explicit use in the supplied representation. It does not participate in object acquisition, target selection, or the arguments explicitly supplied to the selected operation.

This is a narrow dispatch contract. The evidence establishes the dispatch sequence, not the acquired object's meaning, the selected operation's purpose, or their memory-management responsibilities. An object-oriented method invocation is a plausible interpretation of the layout, but is not required to describe the observed behavior.

## Behavior

### Established sequence

For an invocation that proceeds normally, the represented behavior has this order:

1. Invoke F-unresolved-01 with no explicit arguments.
2. Interpret its result as an address of object-associated storage.
3. Read the initial integer-sized word at that address.
4. Use that word as the base of a dispatch structure and select the entry at byte offset **0x20**, or **32 decimal**.
5. Read the callable target represented by that entry.
6. Transfer control to the selected target, F-unresolved-02, supplying the acquired object address first and the original second input second.
7. Complete without a specified return value if the selected operation returns control through the represented call path.

There is one explicit acquisition invocation and one explicit dynamically selected invocation. No retry, alternative target selection, loop, or fallback is shown.

The acquisition completes before the object word is read. The object word determines the dispatch-entry location, and the entry supplies the target before the indirect transfer occurs.

These ordering statements describe the supplied representation. They do not claim atomicity, a particular processor instruction sequence, or synchronization with concurrent agents.

### Object and dispatch layout

The acquired address must support the initial integer-sized read. The value read there is used as an address-like dispatch base rather than as the final callable target.

The callable entry lies **32 bytes from that dispatch base**, not 32 bytes from the object address. There are therefore two levels of lookup:

- The object's initial word supplies the dispatch base.
- The dispatch structure supplies the callable target at the fixed byte displacement.

The representation is consistent with a 32-bit environment, using a four-byte initial word and four-byte callable-address entries. On that interpretation, the selected entry is the ninth four-byte slot when counted from one, or slot eight when counted from zero.

The byte displacement is more directly established than the slot interpretation. A complete platform ABI, address width, callable representation, alignment requirement, and byte order are not independently established by the supplied material.

No additional object fields, dispatch entries, or allocation boundaries are described.
