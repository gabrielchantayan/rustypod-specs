# F-aa7713c91af4

## Purpose

F-aa7713c91af4 interprets a zero-terminated byte format against zero-terminated input, optionally writes conversion results through a sequence of destination addresses, and returns a signed 32-bit assignment count or a path-dependent exhaustion result of −1.

Formatted scanning is the inferred intent. The established behavior is not interchangeable with a conventional formatted-input interface. Notable differences include automatic space and tab skipping before character conversions, nonstandard numeric width handling, retained format position after percent matching, writes during some suppressed conversions, and bounded bracket conversions that filter a span rather than stop at its first nonmember.

This contract describes static evidence. No runtime tests have been performed.

## Interface

### Inputs and representation

The function receives three addresses:

1. Input bytes terminated by zero.
2. Format bytes terminated by zero.
3. Consecutive 32-bit slots containing destination addresses.

The visible widths are:

| Item | Width |
|---|---:|
| Input and format elements | 8 bits |
| Character output and count prefixes | 8 bits |
| Short numeric output | 16 bits |
| Other numeric output | 32 bits |
| Destination-address slot | 32 bits |
| Width, numeric accumulator, assignment count | 32 bits |
| Bracket membership table | 256 bits |

Advancing the destination sequence moves by four bytes. The function does not return the final input, format, or destination-sequence position.

Width parsing uses unsigned 32-bit arithmetic. Several later width decisions interpret those bits as signed 32-bit values. Numeric byte order and alignment requirements are not independently established by the supplied representation.

### Preconditions, storage, and ownership

Input and format must be readable through every byte examined. Destination slots must be readable whenever accessed. Each destination must support all writes performed by its conversion, including terminators and count prefixes. No output-capacity argument or capacity check is present.

Top-level addresses are not validated. A null conversion destination causes an ordinary stop where explicitly checked; invalid addresses, undersized storage, and unsuitable store alignment have no established recovery behavior.

No allocation, release, or ownership transfer is visible locally. No ownership or memory-preservation guarantee is established for the opaque dependency.

Aliasing is not rejected. Writes overlapping unread input, format, or destination slots may affect subsequent behavior. Unless explicitly stated otherwise, acceptance examples require stable, sufficiently sized, nonoverlapping storage and no concurrent mutation.

### Result

The ordinary result is the number of completed, unsuppressed assignments. Suppressed conversions never increment this count, but some still write and advance the destination sequence.

Exhaustion can return either the current count or −1, depending on control flow. A return of −1 does not necessarily mean no earlier assignment occurred. A return of zero does not establish that input was untouched or that no destination was written.

## Behavior

### Entry and outer scanning

The first format byte is examined before input contents:

- Empty format returns zero without reading input contents or destination slots.
- Nonempty format with initially empty input returns −1 before processing format whitespace.

At each outer scanning step, input spaces and tabs are skipped first; format spaces and tabs are skipped afterward. Only bytes 0x20 and 0x09 receive this automatic treatment. Line feed, carriage return, and other whitespace-like bytes are not automatically skipped.

This handling also precedes `c` and bracket conversions. Consequently, those conversions ordinarily cannot capture leading input spaces or tabs.

Ordinary format bytes match equal input bytes in order. A mismatch returns the current count without undoing earlier consumption or writes. Encountering input space or tab during literal matching returns control to outer whitespace handling. Thus input `a b` can match format `ab`.

Exhaustion rules are path-dependent:

- A required literal encountered with empty input returns −1.
- If a literal consumes the last input byte and the next format byte is space or tab, the function returns −1.
- Finishing the format returns the current count.
- After a completed conversion or percent match, processing stops with the current count if either input or format is exhausted.
- If outer whitespace skipping exhausts input while format remains, the function returns a nonzero current count, or −1 if that count is zero.

These rules do not make every incomplete conversion an exhaustion error. For example, consuming a numeric sign and then failing initial numeric eligibility returns the current count.

### Conversion syntax

A percent introducer permits, in this order:

1. Optional `*` suppression.
2. Decimal width digits.
3. Repeated recognized modifiers.
4. A conversion byte.

Recognized conversions are `d`, `u`, `o`, `x`, `s`, `c`, `[`, and `%`. Unsupported or incomplete syntax stops with the current count.

Modifiers have these effects:

| Modifier | Effect |
|---|---|
| `h` | Select a 16-bit numeric store |
| `l` | Select a 32-bit numeric store |
| `#` | Select character-count-prefix behavior |

Each recognized modifier clears the other modifier modes, so the last one wins. Numeric output defaults to 32 bits; `#` also leaves numeric stores at 32 bits. Neither `h` nor `l` changes character-output element width.

Width digits accumulate modulo 2³² without an overflow diagnostic. Omitted width is represented by 4,294,967,295. Explicit digits or wrapped arithmetic can produce that same value.

For numeric, string, and bracket conversions, all-ones selects unlimited processing. For `c`, every all-ones width is replaced with one before character processing, regardless of how that width arose.

### Percent conversion

A percent conversion requires the current input byte to be percent. A mismatch stops without assignment. A match consumes one input byte but leaves the format position on the percent byte used as the conversion byte.

If input remains, that retained format percent can introduce another conversion on the next outer step. For example, input `%42` with format `%%d` reaches a decimal conversion and assigns 42.

If matching percent exhausts input, the function instead returns immediately with the current count. Percent matching neither accesses nor advances destination slots and never increments the assignment count.

### Numeric conversions

#### Sign and eligibility

Every numeric conversion consumes one leading plus or minus if present. A minus requests final negation only for `d`; for `u`, `o`, and `x`, it is discarded. Plus never requests negation. A sign does not reduce the conversion width.

After sign handling, the next byte must be an ASCII digit or a letter in `a`–`f` or `A`–`F`. Otherwise, the conversion stops processing with the current count and no assignment.

This initial eligibility test is broader than decimal and octal consumption. A decimal or octal conversion starting with an eligible letter can complete with zero while leaving that letter unconsumed.

#### Accumulation

The accumulator begins at zero.

- `d` and `u` consume decimal digits, multiplying by ten and adding the digit value.
- `o` consumes all decimal digits, including eight and nine, multiplying by eight and adding the digit value.
- `x` consumes hexadecimal digits, multiplying by sixteen and adding the result supplied by F-dc5033eeec80.

There is no hexadecimal-prefix recognition. An unlimited `x` conversion on `0x10` consumes the first zero and stops before `x`.

Accumulation and final decimal negation use 32-bit values without visible range checks or overflow recovery. Portable signed-overflow semantics are not established.

#### Numeric widths

A bounded numeric loop validates a candidate digit before deciding whether the width permits consuming it. Width handling differs from character-copy limits:

| Width value | Maximum eligible digits consumed |
|---:|---:|
| 0 | 1 |
| 1 | 0 |
| 2 | 1 |
| 3 | 2 |
| 2,147,483,647 | 2,147,483,646 |
| 2,147,483,648 through 4,294,967,294 | 0 |
| 4,294,967,295 | Unlimited branch |

For zero width, the first decrement wraps to all-ones and permits one eligible digit. At a second eligible candidate, the previous width is negative under the signed comparison, so processing stops. The conversion does not switch from bounded to unlimited processing.

Initial eligibility remains required even when the width permits no digit consumption.

#### Destination handling

Numeric scanning, dependency calls, accumulation, and any final negation precede destination checking.

For an unsuppressed conversion:

- A null destination stops with the current count.
- `h` stores the low 16 result bits; every other modifier state stores 32 bits.
- A successful store advances one destination slot and increments the count.

The current numeric destination slot is read for its null check and again for the store. A single-fetch guarantee is not established.

A suppressed numeric conversion does not read or advance destination slots. It still consumes input and invokes F-dc5033eeec80 for consumed hexadecimal digits.

### String and character conversions

Both `s` and `c` fetch and null-check the current destination before consuming conversion input, including under suppression. A null destination stops processing.

For `c`, all-ones width is normalized to one. For `s`, all-ones selects unlimited processing.

Unlimited `s` consumes nonzero bytes until space or tab. Line feed and carriage return do not terminate it.

Bounded `s` and `c` consume nonzero bytes up to the signed width limit. Spaces and tabs inside that bounded span do not terminate conversion.

The bounded loop reads a candidate before applying its width boundary. Every nonzero candidate increments an internal character count, including the candidate rejected at that boundary:

- If a nonzero byte follows the consumed span, the count is consumed length plus one.
- If zero immediately follows the span, the count equals consumed length.
- A zero or negative signed width consumes nothing, but a nonzero first candidate makes the count one.

For very large spans, count-overflow semantics remain unresolved.

Without `#`, unsuppressed data begins at the destination. An `s` conversion writes a trailing zero at the output cursor; `c` writes no terminator.

With `#`:

- The first destination byte receives the low eight bits of the internal character count.
- String data begins one byte after that prefix.
- Character data begins at the destination itself, so the final prefix write overwrites its first copied byte.
- No terminator is written.

Suppression prevents character-copy writes, but not an `s` terminator or a `#` prefix write. Every completed `s` or `c` advances one destination slot, including suppressed conversions. Only unsuppressed completion increments the assignment count.

### Bracket conversions

#### Membership construction

The bracket specification constructs a 256-bit membership table. A leading caret requests complementing the completed table.

A closing bracket in the initial member position, including immediately after the optional caret, is inserted as a singleton. Parsing then moves to the next format byte without testing that initial bracket as a range start. A following hyphen therefore does not turn it into a range.

For example, `%[]-a]` contains exactly three members: closing bracket, hyphen, and `a`. It does not include caret, underscore, or backtick.

For other member positions, the current member is inserted and can start a range when followed by hyphen and an endpoint that is neither zero nor closing bracket. The endpoint is consumed as part of the range syntax.

Range expansion advances an 8-bit value:

- Ascending ranges with endpoints below 255 include both endpoints.
- A descending range ordinarily adds only its starting member; its endpoint is not separately inserted.
- A start of 255 wraps to zero on its first increment. With an endpoint below 255, the table therefore includes 255 and zero through that endpoint.
- An endpoint of 255 makes the visible expansion loop nonterminating: the increment wraps, and no byte value exceeds the endpoint.

A zero format byte encountered before the closing delimiter stops with the current count, before accessing this conversion’s destination. Complementing occurs only after a closing delimiter is found.

#### Consumption, output, and advancement

After completing the table, the function fetches and null-checks the current destination, including under suppression.

With all-ones width, it consumes the contiguous nonzero input prefix belonging to the set. The first nonmember remains unconsumed.

With any other width, it consumes nonzero input bytes up to the signed width limit regardless of membership. Only members are copied. Thus a bounded bracket conversion filters a consumed span rather than stopping at its first nonmember. Zero or negative signed widths consume nothing. The boundary candidate is read before stopping.

Suppression prevents member-copy writes but does not prevent consumption or the final zero write. Every completed bracket conversion:

- Writes zero at its resulting output cursor.
- Advances the destination sequence by one slot, whether suppressed or unsuppressed.
- Increments the assignment count only if unsuppressed.

For a suppressed conversion, the output cursor has not advanced through copies, so the terminator is written at the supplied destination itself. A subsequent conversion uses the next destination slot. The `#` modifier does not replace the bracket terminator with a count prefix.

## Side effects

Locally visible writes affect destination storage and local working storage. No explicit global access is visible in this function. That does not establish that the opaque dependency preserves global or caller-visible memory.

Relevant ordering is:

- Initial format inspection precedes initial input inspection.
- Outer input whitespace skipping precedes format whitespace skipping.
- Conversion syntax is processed before conversion-specific destination access.
- Numeric scanning and accumulation precede numeric destination checks.
- String, character, and completed-bracket destination checks precede their consumption loops.
- Character copies occur in input order.
- Terminators and count prefixes are written after copying.
- Destination advancement and assignment counting follow the conversion-specific suppression rules.

For each consumed hexadecimal digit, the input position advances before F-dc5033eeec80 is called.

No rollback occurs after a later mismatch, null destination, unsupported syntax, or exhaustion. There is no separate truncation result or structured error description. Suppression is neither a general no-write guarantee nor a general guarantee that the destination sequence remains unchanged.

## Evidence

The supplied body establishes byte-oriented scanning, 16-bit and 32-bit result stores, four-byte destination-slot advancement, unsigned width accumulation, signed width comparisons, membership-table construction, and the visible opaque dependency interface.

Two separate bracket-control-flow facts are decisive:

- Completed bracket conversions reach a shared completion path that advances the destination sequence unconditionally; suppression controls only the assignment-count increment.
- An initial closing bracket is inserted through a dedicated singleton path that advances directly to the next member. It bypasses the ordinary range-start test, including when preceded by the complement marker.

Other static evidence establishes sign consumption, retained percent format position, all-ones normalization for `c`, and continued bounded processing after a zero numeric width wraps.
