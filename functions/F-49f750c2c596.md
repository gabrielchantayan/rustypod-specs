# F-49f750c2c596

## Purpose

F-49f750c2c596 provides a special-value query and an integer-field lookup through the same interface.

A zero search value requests the value of a shared integer. It does not request a search for a record containing zero, and it does not require access to the supplied collection descriptor.

A nonzero search value requests the earliest matching position in a count-bounded record sequence. With stable, valid collection storage, the result is either the index of the first matching record or the position immediately beyond the searched range. A nonpositive count produces an empty search and a result of zero.

The comparison is integer equality. The supplied evidence does not establish whether the comparison field represents an identifier, handle, address, or another application value.

## Interface

The function receives two integer-represented arguments and returns an integer.

| Interface element | Contract |
|---|---|
| Collection argument | Represents the address of a descriptor. It is unused for descriptor access when the search value is zero. |
| Search argument | Zero selects the shared-value query. Any nonzero value selects the record search, including negative values. |
| Result | The shared integer for a zero search argument; otherwise, a zero-based match or exhaustion position. |

The recovered representation uses signed integer values for the arguments, result, count, comparison field, and index. The working data model is 32-bit signed integers and 32-bit integer-held addresses. An authoritative target ABI is not supplied, so the exact machine interpretation of these recovered types remains **documented_only**. In particular, an integer-held address must not be treated as evidence of a portable native-pointer interface.

The relevant storage layout is:

| Storage component | Byte displacement | Meaning |
|---|---:|---|
| Descriptor | 4 | Signed record count |
| Descriptor | 8 | Integer-held address of the record sequence |
| Each record | 20 | Signed comparison field |

Under the recovered 32-bit model, each observed integer field occupies four bytes. Record index \(i\) selects a comparison field at a byte displacement of \(24i + 20\) from the sequence base. Other descriptor and record bytes have no established role in this function.

A separate shared integer supplies the special-value result. Its address, application meaning, initializer, and lifetime are not established.

Every invocation requires the shared integer to be readable, including invocations requesting a nonzero search.

A nonzero search also requires a readable descriptor count. Sequence-address and record-field validity are needed only for candidates admitted by the count bound. Consequently, a zero or negative count does not require readable sequence-address storage or readable record storage for this function’s shown accesses.

All accessed storage must satisfy the actual execution environment’s representation, alignment, and lifetime requirements. Address calculations must be valid under that environment’s integer and address rules.

## Behavior

### Zero search value

The result is the value obtained from the shared integer during this invocation. Every representable value of that integer, including zero and negative values, is eligible to be returned without reinterpretation as a status code.

The collection descriptor and its records are not inspected on this path. The collection argument therefore need not identify readable descriptor storage, provided the invocation and shared-integer access are otherwise valid.

The supplied representation contains one shared-integer read and no subsequent refresh before return. A change to that storage after the represented read does not alter the value already obtained.

### Nonzero search value

The result depends on the collection search rather than on the value obtained from the shared integer. The shared read nevertheless remains present in the supplied representation.

For stable memory, let the descriptor count be \(n\):

- If \(n \leq 0\), the result is zero.
- If \(n > 0\) and one or more records in positions zero through \(n-1\) have a comparison field equal to the search value, the result is the smallest such position.
- If \(n > 0\) and none of those records matches, the result is \(n\).

This defines an ordered search, not an arbitrary choice among matching records. Duplicate matches do not change the precedence of the earliest position.

An early match limits the storage that must be accessible: later records are not inspected. Exhaustion does not inspect a comparison field at position \(n\). The count bound excludes that position before any corresponding sequence-address or record-field access.

The function has no independent success indicator. With a stable positive count, a result below the count identifies a match, while a result equal to the count identifies exhaustion. A nonpositive count returns zero even when the count is negative; the count itself is not returned in that case.

A result of zero is therefore ambiguous without the call context. It can mean a match in the first record, an empty search, or the shared value returned by a zero search argument.

### Access ordering and collection changes

At the level of the supplied representation, the shared-integer read precedes collection access. Within the search, the current count bound governs whether a candidate may be inspected. An admitted candidate requires the sequence address before its comparison field can be obtained.

The count and sequence address are not established as entry-time snapshots:

- A mismatch is followed by another count evaluation before the next candidate can be inspected.
- The sequence address is obtained separately for each admitted candidate.
- A matching comparison ends the search without another count evaluation.
- Previously examined positions are not revisited.

These facts constrain the represented access order. They do not establish a supported concurrent-mutation protocol. In particular, the contract does not promise that a changing descriptor behaves like one immutable sequence, that a result remains valid after return, or that concurrent readers and writers are synchronized.

Physical load counts and timing are not independently established. No volatile qualification, atomic access, memory ordering, or generated-machine-code evidence is supplied.

### Integer and address boundaries

The index is nonnegative and advances only past records that fail equality. The signed count bound limits admission of candidates. Under the recovered signed-integer model, index advancement does not require a value greater than the maximum representable count.

That observation does not make large counts safe. Record addressing introduces multiplication by 24 and additions involving the sequence address and the comparison-field displacement. These operations can encounter representation or storage limits before the count bound becomes relevant.

A valid final-looking address is not sufficient if an intermediate calculation violates the actual arithmetic rules. The evidence does not establish wraparound, trapping, or another overflow policy. No result is promised when the required calculations or accesses are invalid.

Negative search values have no special arithmetic role. They participate in the same equality comparison as positive nonzero values.
