# F-918216db7a4d

## Purpose

F-918216db7a4d determines whether a supplied address is non-null and the signed 32-bit value at that address compares equal to a global comparison operand. Normal completion produces a four-byte result representing either 0 or 1.

The null-address case always produces 0. For a non-null address, the result is 1 exactly when the equality evaluation is true; otherwise it is 0.

This is a value predicate, not an address-identity test or a storage-validity check. An affirmative result does not establish that the supplied address belongs to a particular object, remains usable after the call, or carries any ownership rights.

The global operand’s declaration is absent from the evidence. Consequently, its type, width, and signedness are unresolved. The contract cannot unconditionally describe the operation as equality between two signed 32-bit integers. Equality is determined after the conversions required by the actual operand types.

The function accepts one pointer to a signed 32-bit integer.

A null pointer is an accepted input. It does not designate an integer value and is not interpreted as a stored zero.

For a non-null input, normal defined execution requires storage suitable for reading the represented integer. Nullness alone does not establish readability, alignment, object lifetime, or permission to access that storage. The function provides no separate validation of those conditions.

The result is a truth indicator, not an ordering result, difference, count, or returned copy of either operand.

## Behavior

### Null-input guarantee

Nullness gates evaluation of the comparison. For a null input, the function returns 0 without reading a pointed-to integer or evaluating the global comparison operand.

This guarantee does not depend on the global value. It remains applicable even when a hypothetical integer zero would compare equal to that operand. A null address and a readable address containing zero are observably different inputs.

The null case also does not require an assumption that the global operand is initialized or readable: that operand is not evaluated on this path.

### Equality for non-null inputs

For a non-null input, the predicate compares the integer designated by the pointer with the global operand. It compares the pointed-to value, not the numerical address.

There is no explicit restriction excluding zero, negative integers, or either endpoint of the signed 32-bit range. There is no explicit magnitude comparison, masking, byte-order conversion, normalization, or adjustment of the input value.

Those absences do not remove language-level operand conversions. In particular, the function does not establish that the original mathematical values must be identical before conversion.

For example, under comparison rules that convert a signed 32-bit value of −1 to unsigned 32-bit, that operand becomes 4,294,967,295 for equality. A global unsigned operand with that value can then yield 1. This is conditional behavior, not evidence that the actual global is unsigned.

By contrast, if the global is a wider signed integer and the comparison preserves both original values, −1 and 4,294,967,295 compare unequal.

The global declaration is also insufficiently evidenced to impose integer-only comparison semantics. If it is an arithmetic type requiring a different comparison domain, that domain’s conversion and equality rules control the outcome. No unconditional claim about floating-point rounding, special values, or exceptions follows from the supplied body.

### Observable evaluation order

The null decision precedes and controls the entire equality evaluation.

For a non-null input, both comparison operands participate in equality, but their relative evaluation order is not established. A specification requiring the pointed-to read before the global evaluation, or the reverse, would exceed the evidence.

The body provides no explicit loop, retry, cache, or second validation pass. This establishes the absence of those source-level operations; it does not establish an exact number of physical memory transactions. Access qualifiers, generated instructions, and hardware behavior are not supplied.

No coherent snapshot of independently changing storage is guaranteed. Any claim about atomicity, synchronization, or consistent observation across concurrent updates requires additional evidence.

### Completion and errors

A failed equality comparison is an ordinary false result, not an error.

A non-null pointer that cannot support the required access is different. The function does not recognize such a pointer and deliberately convert it into 0. The resulting behavior may depend on the storage defect and execution environment; no particular fault, recovery mechanism, or ordinary return is established.

Likewise, there is no explicit recovery path for a failure during evaluation of the global operand or the comparison.

No explicit addition, subtraction, multiplication, division, or shift occurs. The signed 32-bit minimum is not negated or otherwise arithmetically transformed by an explicit operation. Conversion effects remain relevant despite the absence of explicit arithmetic.
