# F-da96c45f001c

## Purpose

F-da96c45f001c searches a fixed-stride table for a 32-bit composite key and copies two associated 32-bit words into caller-supplied output storage.

The supplied representation establishes three normal outcomes: no table descriptor is available, the search interval becomes empty, or a matching row is found. Every normal outcome returns the 32-bit value zero. Consequently, the return value does not distinguish success from absence. A successful match whose associated words are both zero is indistinguishable from absence through the final output values alone.

The inferred intent is a binary search over an ascending table of composite keys. Sortedness, valid storage, and suitable arithmetic bounds are prerequisites for reliable lookup; the function does not validate them.

## Interface

### Inputs

The interface has four arguments:

| Argument | Representation and role |
|---|---|
| Context address | A 32-bit address-valued argument. A descriptor address is read from byte offset `0x1E8` within the referenced context. |
| Upper-key contributor | A 32-bit argument whose bit pattern is shifted left by 16 positions when constructing the search key. |
| Existing key bits | A 32-bit unsigned argument ORed with the shifted upper-key contributor. |
| Output address | Address of two writable, consecutive 32-bit words, occupying eight bytes. |

Argument names in this contract describe roles rather than source identifiers.

The effective search key is the 32-bit bitwise OR of:

- the existing key bits; and
- the upper-key contributor shifted left by 16 positions, retaining the resulting 32-bit pattern.

This is not an unconditional concatenation of two independently masked 16-bit values. In particular, the existing-key-bits argument can already contain set bits in its upper half, and those bits remain set.

The left-shift operation appears with a signed operand in the supplied representation. Its intended 32-bit bit-pattern effect is described above. Portable signed-language overflow or shift guarantees cannot be established from that representation.

### Output and return value

The output consists of two raw 32-bit words:

- For a match, the associated words from the selected row.
- For either ordinary absence outcome, two zero words.

Every explicit return supplies the 32-bit value zero. There is no separate found flag, row index, error code, or returned pointer.

For ordinary, well-defined lookup behavior:

- The output address must permit two consecutive 32-bit stores.
- The context must permit reading its descriptor field.
- A nonzero descriptor address must permit reading both descriptor fields.
- The table must provide every row visited by the search.
- The count must be nonnegative, and address formation and midpoint calculations must remain within the applicable 32-bit address and signed-difference limits.
- Rows must be ordered nondecreasingly by their computed **unsigned 32-bit** keys.

No alignment handling or recovery from inaccessible memory is established.

## Behavior

### Initialization precedes lookup

The function first writes zero to the first output word, then writes zero to the second output word. These stores occur before reading the context’s descriptor field.

It then reads the descriptor address from context offset `0x1E8`.

If that address is zero, the function returns zero immediately. On this path it does not read the table address, count, or any table row.

This ordering matters when output storage overlaps context storage: the initial clearing can alter the descriptor value before it is read. The function contains no established non-aliasing check.

### Search setup

For a nonzero descriptor, the function forms the requested composite key. It reads the table address from descriptor offset `0x24`, followed by the count from offset `0x28`.

Rows have a stride of four 32-bit words, or 16 bytes. The initial interval covers the first row through the row immediately before the address computed as table address plus count times 16.

The table address and count are not reloaded on each iteration. Subsequent changes to their descriptor fields do not, by themselves, refresh the captured search state.

### Interval processing

Before reading a candidate row, the function checks whether the current upper row address precedes the current lower row address. An empty interval causes the first output word and then the second output word to be written as zero again, followed by return of zero.

For a valid nonempty interval, the candidate is the lower-biased midpoint: the lower row plus half the row distance between the lower and upper rows, rounded down.

The represented midpoint calculation uses a signed byte-address difference, a right shift by four positions to obtain a row distance, and division by two. The ordinary midpoint interpretation therefore depends on a nonnegative, representable address difference. Behavior after signed-difference overflow or address wrap is not established as a valid search contract.

The candidate key uses the candidate’s words at offsets `0x00` and `0x04`. Both key words contribute to the comparison; the relative evaluation order of these two reads is not established.

Comparison proceeds as follows:

- Equality selects the candidate immediately.
- A requested key greater than the candidate key discards the candidate and every row below it.
- A requested key less than the candidate key discards the candidate and every row above it.

The relational key comparison is unsigned. A key with its highest bit set therefore sorts above every key without that bit set.

The process repeats until a matching candidate is selected or the remaining interval is empty.

### Match handling

For an equal key, the function:

1. Reads the selected row’s word at offset `0x08` and writes that value to the first output word.
2. Reads the selected row’s word at offset `0x0C` and writes that value to the second output word.
3. Returns zero.

The two payload values are not established as a snapshot read before either output store. If the first output store overlaps the selected row’s second payload word, it can change the value subsequently read for the second output.

Duplicate keys do not trigger a scan. The first equal candidate reached by the midpoint search is selected. There is no general first-duplicate or last-duplicate guarantee.

### Empty, malformed, and unsorted inputs

For a zero count under ordinary address arithmetic, the initial upper-bound position is one row before the table address. The interval is empty, no row is dereferenced, and both output words are cleared again.

There is no explicit null-table check. In particular, a nonzero count with a zero table address is not converted into a documented absence result.

Negative counts, overflowing address calculations, inaccessible rows, and concurrent mutation are not validated or reported. An unsorted table does not produce a dedicated error: the search can miss an existing key because it discards intervals according to ordering that the data does not satisfy.

## Side effects

The established explicit writes are confined to the two output words. Nevertheless, overlapping storage can make those writes modify context fields, descriptor fields, table keys, or table payloads.

For disjoint output storage, the normal write sequences are:

| Outcome | Output-store sequence |
|---|---|
| No descriptor | First word zero, then second word zero. |
| Exhausted interval | Initial zero pair, followed later by another zero pair. |
| Match | Initial zero pair, followed by the selected first payload word and selected second payload word. |

Repeated zero stores are part of the represented access sequence even when they do not change ordinary memory contents. The source does not establish a volatile-memory or device-register access contract.

The function contains no visible allocation, deallocation, ownership transfer, callback, or external function call. It copies payload bit patterns without interpreting them. If a payload encodes an address or resource handle, this function does not establish ownership of the referenced resource.

No synchronization or atomic publication of the output pair is visible. A reader observing the output during execution could encounter the cleared state or a partially updated pair, subject to the surrounding execution environment.

There is no explicit memory-fault handling. Fault delivery and the externally visible state after a fault are environment-dependent; the routine does not provide rollback.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, storage is valid, disjoint, stable, and correctly ordered.

### Missing descriptor

Given a zero descriptor field, the function must clear both output words and return zero without reading descriptor fields or table rows.

The prior contents of the output do not affect this result.

### Zero-row table

Given a nonzero descriptor and a count of zero, the function must read the table address and count, determine that the initial interval is empty, clear the output pair again, and return zero without reading a row.

### Single matching row

Given one row whose key contributors are `0x00000012` and `0x00003456`, the computed row key is `0x00123456`.

A request with upper-key contributor `0x00000012` and existing key bits `0x00003456` must select that row. If its payload words are `0x89ABCDEF` and `0x76543210`, those exact 32-bit patterns must be written to the output in that order. The return remains zero.

### Unmasked existing key bits

Given an upper-key contributor of `0x00000012` and existing key bits of `0x80003456`, the requested key is `0x80123456`, not `0x00123456`.

The same rule applies to row keys. An implementation that truncates the existing-key-bits word to 16 bits would not satisfy this contract.

### Unsigned ordering

Given ascending keys `0x7FFFFFFF` and `0x80000000`, a request for `0x80000000` must treat that key as greater than `0x7FFFFFFF`. Signed key ordering is not equivalent.

### Absent key

Given ascending keys `0x00010000`, `0x00030000`, and `0x00050000`, a request for `0x00040000` must exhaust the search interval, leave both output words zero, and return zero.

### Duplicate keys

Given four rows with equal keys and distinct payloads, the initial lower-biased midpoint is the second row. Its payload must be selected immediately; the function must not continue searching for the first or last duplicate.

### Zero-valued payload

Given a matching row with both payload words zero, the final output and return must both be identical to those of an ordinary miss. A consumer cannot use those values alone to distinguish the two outcomes.

### Payload overlap

Suppose the first output word occupies the selected row’s second-payload location, and the row’s first payload is `0x11223344`. Conditional on that row still being selected after initial clearing, the first payload store replaces the row’s second payload before it is read. The second output consequently receives `0x11223344`, rather than a guaranteed copy of the row’s original second payload.
