# F-9119574c2936

## Purpose

F-9119574c2936 prepares object-associated resources, reads a byte-oriented configuration, processes two collections of length-prefixed records, and performs completion callbacks.

Successful completion stores a one-byte finalization result in the object and returns a zero low-order status word. Detected failures normally invoke a failure callback and return low word `0xffffffff`. Header rejection is an exception: it returns failure without that callback.

Resource preparation, parsing, and failure handling are not transactional. Earlier writes and dependency effects remain observable unless a dependency reverses them.

The interpretation as configuration initialization is inferred intent. The contract below describes established caller behavior without assigning a protocol identity or assuming dependency ownership and cleanup semantics.

## Interface

### Arguments and return value

The address and word model is 32 bits. The function receives:

1. A pointer to a mutable object.
2. A 32-bit value used as the input-descriptor address.
3. An otherwise uninterpreted 32-bit value.

Two addressable working words are initialized from arguments two and three. F-1fc83df66bd7 receives their addresses and may modify them. Changing the working word initialized from argument two does not change the original descriptor address used to obtain the input buffer.

The 64-bit result contains:

| Bits | Meaning |
|---|---|
| 31–0 | `0` after completed success; `0xffffffff` on a detected failure |
| 63–32 | Current working word initialized from argument two |

The working word initialized from argument three is not directly returned.

### Object layout

Offsets are byte offsets. Fields are 32-bit words unless stated otherwise.

| Offset | Observed role |
|---|---|
| `0x00` | Dispatch-table pointer |
| `0x04` | Receives a word read through a global pointer |
| `0x08` | Auxiliary construction result |
| `0x0c` | Primary resource value |
| `0x10` | Primary logical size |
| `0x14` | Tested for zero |
| `0x18` | Written with `0x40000` when `0x14` is zero |
| `0x1c` | Secondary resource value |
| `0x20` | Secondary logical size |
| `0x34` | One-byte finalization result |
| `0x3c`–`0x3f` | Four individually written header bytes |
| `0x40` | Header-derived width |
| `0x44` | First-record count; subsequently read as signed 32-bit |
| `0x48` | Second-record count; subsequently read as signed 32-bit |
| `0x194` | First-record storage base |
| `0x198` | Second-record storage base |

Indirect callbacks use dispatch-table offsets `0x48`, `0x58`, and `0x14`. These are not object-field offsets.

The input descriptor contains a 32-bit buffer pointer at `0x34` and a signed 32-bit buffer length at `0x38`.

### Preconditions

Every reached object, descriptor, dispatch-table, global, descriptor-allocation, and record-storage access must reference suitably accessible memory. There is no general pointer validation.

In particular:

- The two 16-byte descriptor allocations are dereferenced without local null checks.
- The eight-byte allocation is passed to a constructor without local rejection.
- Record storage must remain adequate for every slot actually accessed, not merely for the initially decoded count.
- A dependency that changes a live record count or storage base must leave subsequent accesses valid.
- Offset calculations and pointer additions require a meaningful, accessible result. Comprehensive overflow protection is absent.

No input-buffer ownership transfer is established.

## Behavior

### Entry and resource preparation

Before reading configuration bytes, the function performs these operations in order:

1. Reads a word through a global pointer and stores it at object offset `0x04`.
2. Initializes both working words.
3. Calls the same unidentified external dependency twice with `(0x20000, 0, 1)`.
4. Reads a global-region word at offset `0x314`, sets bit 0, and writes it back.
5. Calls F-604a1cb36c2a.
6. Captures the global resource-registry base used for later descriptor publication.

The two external return values are unused. Their other effects are unknown.

If object offset `0x0c` is nonzero, primary creation is skipped. Otherwise, the function:

- Stores a global size value at `0x10`.
- Requests a 16-byte allocation from F-8157a180d901.
- Rereads `0x10` after that call.
- Initializes the returned descriptor, in order, with raw value zero, logical size from that reread, adjusted value zero, and a one-byte marker of zero.
- Calls F-638beded7699 with the captured logical size plus `0x40`, and second argument `3`.
- Stores its result as the descriptor’s raw value.

The descriptor layout is:

| Offset | Width | Meaning |
|---|---|---|
| `0x00` | 32 bits | Raw resource result |
| `0x04` | 32 bits | Adjusted resource value |
| `0x08` | 32 bits | Logical size |
| `0x0c` | 8 bits | Creation marker |
| `0x0d`–`0x0f` | 3 bytes | Not initialized by this function |

For a nonzero raw result, adjustment adds `0x1f` using 32-bit unsigned arithmetic and clears the low five bits. The aligned value is stored at descriptor offset `0x04`.

If bit `0x08000000` of the addition result is set, F-20810a394e6a receives the aligned value and the descriptor’s current logical size. After that call, bit `0x80000000` is set in the descriptor’s then-current adjusted word. The function does not simply restore the previously calculated aligned value.

A following loop has no body and establishes no buffer clearing. The marker is then set to one. A nonzero raw result does not itself guarantee a nonzero adjusted result.

The descriptor is published at captured registry offset `0x04`. Its current adjusted word is then copied to object offset `0x0c`. Zero causes common failure handling; publication has already occurred.

Once primary setup permits continuation, a zero object word at `0x14` causes `0x18` to receive `0x40000`. No allocation for that field is visible.

A zero word at `0x1c` triggers secondary creation using the same descriptor pattern, with these differences:

- Object offset `0x20` and descriptor logical size are set to `0x50`.
- F-638beded7699 receives `(0x180, 3)`.
- Publication uses captured registry offset `0x08`.
- The adjusted result is stored at object offset `0x1c`.

A zero adjusted secondary result causes common failure handling.

### Auxiliary setup and initial callback

When object offset `0x08` is zero, the sequence is:

1. Request eight bytes through F-8157a180d901.
2. Pass the result and `0x23` to F-c6bf6c2a3ff7.
3. After that call returns, capture the global auxiliary value.
4. Store the construction result at object offset `0x08`.
5. Call F-9d7922b16667 with the construction result and the captured global value.
6. Call F-5b11d8d4a9e9.

The global read precedes the object store. If the global value’s storage aliases `0x08`, F-9d7922b16667 receives the value captured before that store, not the newly stored construction result. No non-aliasing assumption is required.

Neither allocation nor construction result is locally rejected here.

Next, the callback at dispatch-table offset `0x48` receives the object. Only after it returns does the function read the buffer pointer, then the signed length, from the original input descriptor. Those captured buffer and length values govern subsequent parsing; descriptor-field changes are not subsequently reread.

### Header

A signed length of 6 or less causes common failure without copying header bytes.

For a longer buffer, the first four bytes are read and copied individually, in order, to `0x3c` through `0x3f`. Each destination write precedes the next source-byte read; no independent four-byte snapshot is established.

After all four copies, acceptance requires:

- Byte 0 equals `0x01`.
- Byte 1 equals `0x42`.
- Unsigned byte 3 is at most `0x1e`.

Byte 2 is not validated. Rejection returns failure immediately, without the failure callback.

For an accepted header, byte 4 masked with `3`, plus one, is stored at `0x40`. Byte 5 masked with `0x1f` is stored at `0x44`. The locally computed width is checked to be below 5; its construction already guarantees values 1–4. The initially decoded first count is 0–31.

### Record-storage allocation

First-record slots occupy `0x300` bytes; second-record slots occupy `0x40` bytes.

For each collection:

- If its storage base is zero, F-fab3799b3190 is requested to allocate at least two slots: the larger of the initially decoded count and two, multiplied by the slot size.
- If storage already exists and the initially decoded count is at most two, it is reused without a capacity check.
- If storage exists and that count exceeds two, F-58ba61416cc9 is called with no explicit arguments. The corresponding object count is then reread, used to calculate the replacement request, and the returned base overwrites the object field.

The replacement branch does **not** reapply the two-slot minimum after the count reread. Zero, negative-bit-pattern, or very large values introduced by the dependency therefore do not follow the absent-storage minimum policy.

The first request uses a 32-bit multiplication by `0x300`; the second uses a 32-bit shift left by six. Dependency-modified counts can produce wrapped request values. A zero returned base causes common failure after being stored in the object.

F-58ba61416cc9 has no identified release target in this caller. Replacing a base does not establish that its former allocation was released.

### First-record loop and live state

Parsing begins at buffer offset 6. The loop index starts at zero.

**Before every attempted iteration, including the terminating test, the function rereads object offset `0x44` and compares the index against it as a signed 32-bit count.** The number of records processed is therefore not fixed by header byte 5 or by the allocation request.

At each entered iteration:

1. The current storage base at `0x194` is read.
2. Using that base plus index times `0x300`, the function writes one byte of zero at slot offset `0x7c`, then 16-bit values of one at `0x7e` and `0x80`.
3. The record envelope is checked.
4. F-1fc83df66bd7 is called.
5. The storage base at `0x194` is **reread**, and that base plus the same index displacement supplies the parser destination.
6. A successful parser result advances the cursor and index before the next live count test.

Thus, F-1fc83df66bd7 can redirect parsing to a slot different from the one initialized earlier in the iteration. Neither the initialization writes nor storage capacity migrate automatically to that new destination.

Either record dependency can also change the count used by the next condition. Reducing it can terminate iteration early; increasing it can require additional records and slots. A zero or negative count at a condition admits no iteration for a nonnegative index.

Validity requires adequate writable storage at **each** base used, including the pre-helper initialization base and the post-helper parser base. The original allocation size alone does not establish this after mutation.

### Record envelopes and parser calls

Both collections use the same local envelope rules. At current cursor \(p\), with captured signed buffer length \(N\):

- The function first requires enough bytes for the two-byte length.
- It decodes an unsigned, big-endian 16-bit length \(L\).
- It requires \(L \ge 2\) and enough bytes through offset \(p + L + 2\).

These inequalities describe ordinary non-overflowing offsets. The implementation’s 32-bit additions and signed comparisons are not a general overflow-safe validation scheme.

For an accepted envelope, the byte at \(p+2\) is passed to F-1fc83df66bd7. Its next arguments are, in order, the address of the working word initialized from argument three and the address of the word initialized from argument two.

The appropriate parser then receives:

- Payload start at buffer offset \(p+3\).
- End of the entire captured buffer.
- The current collection’s destination slot.

F-e208fff7ea87 processes first records; F-0ac99c98434e processes second records. A nonzero result causes common failure. Zero advances the cursor to the previously calculated \(p+L+2\), regardless of how much data the parser actually consumed.

The parser does not receive the declared record end. Local envelope checks therefore do not prove that parser reads remain within that record.

First-slot initialization precedes envelope validation, so even a missing length field can leave those writes behind.

### Second-record loop and completion

After the first loop terminates, at least one byte must remain. That unsigned byte is stored at object offset `0x48` as the second count, initially 0–255, and the cursor advances by one. Storage preparation follows the policy above.

**Every second-loop condition rereads `0x48` as a signed 32-bit count.** As in the first loop, dependency mutation can shorten or extend iteration independently of the decoded count and allocation size.

No per-slot initialization is visible for second records. After envelope validation and F-1fc83df66bd7, the function reads the current base at `0x198` and adds index times `0x40` for F-0ac99c98434e. A helper-induced base change therefore affects the current parser destination.

After the second loop terminates:

1. The callback at dispatch-table offset `0x58` receives the object and zero.
2. An unidentified external dependency is called with no explicit arguments.
3. Another unidentified external dependency returns a byte, which is stored at object offset `0x34`.
4. The low return word becomes zero.

There is no cursor-equals-length check. Trailing bytes are accepted.

Common failure invokes the callback at dispatch-table offset `0x14` with the object, then returns failure. Dispatch information is obtained for each reached callback; it is not captured once at entry.

## Side effects

Observable writes include object fields, global bit state, descriptor contents, registry publications, first-slot initialization, dependency-written records, and working-word mutations.

Failure does not explicitly undo resource creation, publication, replaced bases, copied header bytes, counts, or partially processed records. Failure-callback cleanup is unknown.

No general preservation of globals, object fields, buffer contents, or memory ownership is assumed across dependencies. Conversely, mutation possibilities do not imply that any dependency actually mutates them.

Capturing a value matters: the registry base, input buffer, input length, auxiliary global argument, and calculated record end are retained across the relevant later operations. Counts and parser storage bases have the live-read behavior specified above.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, accesses are valid, arithmetic does not overflow, allocations succeed, parsers accept, and dependencies preserve relevant state.

1. **Minimal configuration.** `01 42 00 1e 00 00 00` permits success: width one, no records. Absent storage still causes allocation of two slots for each collection.

2. **Short input.** Length 6 causes common failure after setup and the initial callback, without header-byte copies.

3. **Header rejection.** A seven-byte input beginning `02 42 00 00` has four header bytes copied, then returns failure without the failure callback.

4. **Masked fields.** Header byte 4 of `0xff` yields width four; byte 5 of `0xe0` initially yields zero first records.

5. **Minimum envelope.** Declared length two occupies four bytes: two length bytes, the helper byte, and one payload byte. Parser acceptance remains required.

6. **Malformed first envelope.** A truncated envelope fails after its slot’s three initialization writes.

7. **First destination redirection.** If F-1fc83df66bd7 changes `0x194` from base A to valid base B, initialization remains at A plus the current slot displacement; parsing targets B plus that displacement.

8. **Live count reduction.** If the first parser changes `0x44` from three to one during index zero, successful return from that parser is followed by termination at the next condition. The next byte at the declared cursor is treated as the second count.

9. **Live second-count expansion.** If the second helper changes `0x48` from one to two during the first iteration, a successful parser leads to a second iteration. Success additionally requires another valid envelope and sufficient storage at the then-current base.

10. **Auxiliary aliasing.** If the auxiliary global occupies the same storage as object `0x08`, F-9d7922b16667 receives the captured pre-store global value alongside the construction result.

11. **Return high word.** If the working word initialized from argument two becomes `0x12345678` and remains so, that is the returned high word on either subsequent success or detected failure.

12. **Trailing bytes.** Extra bytes after the processed collections do not independently cause rejection.
