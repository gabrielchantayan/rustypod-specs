# F-2d0a8320c497

## Purpose

F-2d0a8320c497 conditionally records a configuration in caller-supplied storage or attempts to record a nonzero status in that storage.

The successful configuration path requires all of the following:

- The selector belongs to a three-value set derived from a shared base value.
- The requested operation equals 4.
- The signed extent is nonnegative.

On that path, the function stores the selector, payload, and effective extent; sets a configuration field to 4; and copies one existing object field into another.

Otherwise, the function selects a fallback status. It writes that status only if the selected status is nonzero and the object’s existing status is zero. An existing nonzero status is preserved.

“Configuration,” “selector,” “extent,” “payload,” and “status” are descriptive labels, not established application-level meanings. The supplied material does not establish what subsystem consumes these values.

## Behavior

### Selector derivation and recognition

At entry, the function first derives a value equal to the shared base plus 11. It then separately derives a value equal to the shared base plus 5.

These are separate reads of the base, in that order. The direct base value is read again during subsequent comparisons. The function does not visibly capture one base snapshot for the whole operation.

With a stable base and representable arithmetic, the recognized selectors are:

- Base.
- Base plus 11.
- Base plus 5.

The first recognition check compares the selector against those alternatives in that order, stopping when recognition is established. If the selector matches none of them, the function replaces its working requested-operation value with 1280.

The function then performs another recognition check, again testing the direct base, the previously derived base-plus-11 value, and the previously derived base-plus-5 value.

For ordinary, stable shared state, the two checks agree. Behavior involving changes to the base between reads is not equivalent to checking membership against one fixed three-value set.

### Choice of status candidate

Before deciding whether to configure the object, the function establishes a status candidate:

- If the second recognition check fails, the candidate remains the working requested-operation value. With a stable base and an unrecognized selector, that value is 1280.
- If the second recognition check succeeds, the function reads the shared fallback status and makes it the status candidate.

The fallback-status read occurs for a recognized selector even when the invocation will subsequently take the success path. In particular, it precedes the requested-operation comparison and the signed extent check.

For stable shared state, an unsupported requested operation is not itself used as the fallback status when the selector is recognized. The shared fallback status is used instead.

### Successful configuration

The success path is taken only when the second recognition check succeeds, the working requested operation is exactly 4, and the extent is signed nonnegative.

An extent of zero requests a default:

- If the selector equals the directly read base, the effective extent becomes 4.
- Otherwise, if the selector equals either previously derived selector, the effective extent becomes 16.

A positive extent is stored unchanged. There is no visible upper-bound check, rounding, scaling, or validation of its relationship to the selector.

With a stable base and representable arithmetic, every recognized selector receives one of the stated defaults when the supplied extent is zero. If the base changes between comparisons, recognition and default selection need not reflect the same direct base value; this contract does not invent a stable-snapshot guarantee.

The success path performs these object accesses in order:

1. Write 4 to slot 100.
2. Write the selector to slot 101.
3. Write the payload to slot 102.
4. Write the effective extent to slot 107.
5. Read slot 694.
6. Write the value read from slot 694 to slot 103.
7. Return.

The copied source field is therefore read after the first four writes, not before them.

This path does not read or write slot 0. An existing status, whether zero or nonzero, neither blocks configuration nor gets cleared by it.

### Fallback behavior

If the success path is not taken, the function uses the status candidate described above:

- If the candidate is zero, it returns without accessing the object.
- If the candidate is nonzero, it reads slot 0.
- If slot 0 is zero, it writes the candidate to slot 0.
- If slot 0 is nonzero, it leaves that field unchanged.

No configuration fields are written on this path.

For stable shared state, the resulting cases are:

| Selector | Requested operation | Extent | Result |
|---|---|---|---|
| Recognized | 4 | Nonnegative | Configure object |
| Recognized | Not 4 | Any value | Attempt to record shared fallback status |
| Recognized | 4 | Negative | Attempt to record shared fallback status |
| Unrecognized | Any value | Any value | Attempt to record 1280 |

“Attempt to record” includes preserving an already nonzero status and, when the candidate is zero, making no object access at all.

## Side effects

The established side effects are limited to shared-state reads and the object accesses listed above.

Important consequences include:

- Successful configuration preserves the status field.
- Failed configuration preserves all configuration fields.
- Fallback preserves an existing nonzero status regardless of the newly selected candidate.
- Payload is stored only on success and is not otherwise inspected.
- The copied value comes from slot 694 at the time of its late read.
- There is no visible rollback if an object access faults partway through the success-path writes.

The access order described here is the order expressed by the supplied representation. No atomicity, locking, memory-ordering primitive, or hardware-level observation guarantee is established. Concurrent access to the object or shared inputs requires an external contract not provided here.

No external I/O, callback, allocation, release, or explicit global write is visible.

A large positive extent is likewise accepted without a visible upper-bound check, provided it is representable in the input integer type.

### Existing status does not block success

Given a valid success-path request and slot 0 initially containing a nonzero value, configuration still occurs. Slot 0 retains its original value and is not read by this path.

### Recognized selector with another operation

- Slot 0 becomes 37.
- No configuration field is written.
- The supplied extent and payload do not produce object-field writes.

If slot 0 initially contains 8 instead, it remains 8.

### Negative extent

Given requested operation 4, selector 105, extent −1, shared fallback status 37, and slot 0 initially zero, the function records 37 in slot 0 and performs no configuration writes.

The negative extent is not converted into a default.

### Unrecognized selector

Given selector 101 and slot 0 initially zero, the function records 1280, regardless of the original requested operation, extent, payload, or shared fallback-status value.

The shared fallback status is not read in this stable-state case.

### Zero fallback status

Given a recognized selector, an unsuccessful configuration request, and shared fallback status zero, the function returns without reading or writing the object.

This is a path-specific lack of object access, not a general guarantee that null or invalid object arguments are supported.

### Copy timing

For a successful request with slot 694 containing a particular value and no intervening mutation, slot 103 receives that value after the other four configuration fields have been written. Slot 694 itself is not written.
