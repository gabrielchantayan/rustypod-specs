# F-be82b9a4788a

## Purpose

F-be82b9a4788a conditionally encodes a 28-bit unsigned value and a one-bit selector into four bytes beginning at byte offset 22 from a supplied base address.

The encoded representation contains:

- The value’s 28 bits, ordered from least-significant byte to most-significant nibble.
- The selector in bit 4 of the final byte.
- A fixed marker in bit 6 of the final byte.
- Zeroes in bits 5 and 7 of the final byte.

The function rejects values outside the accepted numeric ranges before accessing the destination. Successful encoding replaces all four destination bytes; it does not merge the encoding with existing destination contents.

This describes a byte-formatting operation. The supplied static evidence does not establish what larger object contains these bytes, what the value identifies, or what semantic meaning the selector and fixed marker have.

## Behavior

### Numeric validation

Encoding is accepted only when both conditions hold:

1. Bits 28 through 31 of the unsigned 32-bit value are all zero.
2. The unsigned 32-bit selector is less than 2.

These conditions are equivalent to the accepted numeric domains given above. They are not truncation rules. An out-of-range value is rejected even if its lower 28 bits would otherwise form a valid encoding. An out-of-range selector is rejected even if its least-significant bit is 0 or 1.

The supplied representation evaluates the value condition before the selector condition, with the second condition needed only if the first succeeds. These checks operate on the input values and perform no destination access.

If validation fails, the function returns 0xFFFFFFFF without writing any destination byte.

### Encoded layout

On the accepted path, the destination receives the following byte layout:

| Byte offset from base | Stored content |
|---|---|
| 22, or 0x16 | Value bits 0–7 |
| 23, or 0x17 | Value bits 8–15 |
| 24, or 0x18 | Value bits 16–23 |
| 25, or 0x19 | Value bits 24–27 in bits 0–3; selector in bit 4; fixed 1 in bit 6; zeroes in bits 5 and 7 |

Thus, the final byte lies in one of two ranges:

- Selector 0: 0x40 through 0x4F.
- Selector 1: 0x50 through 0x5F.

The value portion is explicitly arranged least-significant byte first. This layout follows from individual byte stores and does not require the host’s multibyte integer memory order to match it.

The first three stores retain only the relevant eight bits. Any signed interpretation of a stored byte by later consumers is separate from this function’s byte-pattern behavior.

### Observable write order

For accepted inputs, the function performs four byte writes in this order:

1. Offset 22.
2. Offset 23.
3. Offset 24.
4. Offset 25.

It then returns the success status.

Each write replaces its entire destination byte. In particular, the final write does not preserve preexisting bits 5 or 7: both become zero. Its bit 6 becomes one regardless of the previous contents.

The operation is not established as an atomic four-byte update. There is no visible synchronization, transaction, rollback, or explicit memory barrier. If an observer can see intermediate writes, the field may temporarily contain a mixture of old and new bytes.

If an address access faults, the supplied evidence does not establish a normal return or recovery behavior. Earlier completed writes are not explicitly undone.

### Integer-width considerations

The value test concerns the upper four bits of a 32-bit unsigned input, leaving exactly 28 encodable bits.

The extraction shifts are by 8, 16, and 24 bits. Their purpose is to select successive portions of that input; they do not widen the accepted domain.

The selector contributes to the output only after validation has limited it to 0 or 1. Consequently, shifting its accepted value left by four positions contributes either 0x00 or 0x10, without overflow.

Address calculations use fixed positive offsets from the supplied base. The source representation does not establish safe behavior for a base whose address arithmetic overflows or produces invalid addresses. Such cases are outside the successful-call preconditions, not additional status-returning validation cases.
