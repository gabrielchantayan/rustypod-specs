# F-78d86e98287a

## Purpose

F-78d86e98287a conditionally invokes a dependency and, when that dependency returns zero, updates two fields in a caller-supplied object.

A zero third argument bypasses the dependency and all object accesses visible in this function. A nonzero third argument is passed through to F-c0024185e7b8. The dependency’s return value determines whether the local updates occur, and that same return value becomes the function’s result.

The updates are consistent with recording a completed quantity and marking status bits. Those meanings are **inferred intent**, not established field semantics. The supplied evidence establishes the operations and their order, but not what the object or quantity represents.

## Interface

### Inputs

The function has three arguments:

| Argument | Representation | Established use |
|---|---|---|
| Object reference | Pointer represented as addressing 16-bit unsigned elements | Forwarded to F-c0024185e7b8; subsequently used as the base for two fields if the dependency returns zero |
| Opaque argument | 32-bit value with unspecified interpretation | Forwarded unchanged to F-c0024185e7b8 |
| Adjustment | Signed integer, treated as 32 bits in the supplied representation | Tested against zero, forwarded unchanged, and added to the accumulator after a zero dependency result |

The opaque argument is not locally dereferenced, interpreted, or modified. Its classification as a pointer, handle, integer, or packed value is unknown.

### Result

The result is a signed integer, treated as 32 bits:

- If the adjustment is zero, the result is zero.
- Otherwise, the result is exactly the value returned by F-c0024185e7b8.

The local field updates do not replace or normalize the dependency’s result.

Zero therefore has two distinguishable origins: a bypassed operation or a dependency invocation that returned zero. The result alone does not distinguish them.

### Object layout used locally

Offsets are measured in bytes from the object reference.

| Byte offset | Access width | Local operation |
|---|---:|---|
| 0 | 16 bits | Read, combine with mask 0xFF00 using bitwise OR, then write |
| 360, hexadecimal 0x168 | 32 bits | Read as an integer accumulator, add the adjustment, then write |

The accumulator offset follows from an offset of 180 elements through a pointer whose elements are 2 bytes wide. It is not a byte offset of 180.

These fields do not overlap. The function’s own accesses require storage through byte offset 363, inclusive, on the path that performs both updates. This is an access requirement, not evidence of a complete object size or an allocation boundary.

The evidence does not establish byte order, packing rules beyond these accesses, or permission to use unaligned storage.

## Behavior

### Zero-adjustment path

When the adjustment equals zero:

- F-c0024185e7b8 is not invoked.
- Neither object field is read or written.
- The opaque argument has no local effect.
- The function returns zero.

There is no local validation of the object reference on this path. In particular, the visible behavior does not require an object dereference merely to return zero.

### Nonzero-adjustment path

Every nonzero adjustment, including a negative value, takes the dependency path.

F-c0024185e7b8 is invoked once with the original three argument values, in their original positions. The accumulator and status field are not locally read or written before this invocation.

If the dependency returns normally with a nonzero result, the function returns that result without either local field update. This does **not** establish that the object is unchanged: the dependency may already have modified it or other state.

If the dependency returns normally with zero, the function performs the following ordered field operations:

1. Read the 32-bit accumulator at byte offset 360.
2. Add the original adjustment to that value and store the result back into the accumulator.
3. Read the 16-bit field at byte offset 0.
4. Set bits 8 through 15 of that field and write the resulting 16-bit value back.
5. Return the dependency’s zero result.

The accumulator input is its value **after** the dependency returns. Likewise, the status input is the value read at the later status-update step. The function does not take a pre-call snapshot of either field.

### Status-field transformation

The status operation sets every bit selected by 0xFF00 and preserves bits 0 through 7 from the value read during that operation.

Consequently:

- The resulting numeric upper eight bits are all one.
- The resulting numeric lower eight bits equal those of the status value read after the accumulator store.
- Bits already set remain set.
- A dependency’s earlier modifications to the lower eight bits are retained, provided nothing else changes the field before the local read.

“Upper” and “lower” describe bit positions within the 16-bit value. Their correspondence to memory-byte addresses depends on byte order, which is not established here.

### Integer boundaries

The adjustment is not restricted to positive values. A negative adjustment can reduce the accumulator if the dependency returns zero.

The supplied representation uses signed integer addition for the accumulator update. A portable overflow rule is not established. For an existing accumulator value \(a\) and adjustment \(d\), the straightforward arithmetic result is specified here only when:

\[
-2^{31} \leq a+d \leq 2^{31}-1.
\]

A replacement must not silently interpret the evidence as establishing saturation, unsigned wrapping, rejection, or a special overflow error. Behavior outside the representable signed range is **documented_only**.

## Side effects

### Locally established effects

The function’s own memory writes occur only when the adjustment is nonzero and F-c0024185e7b8 returns zero.

On that path, it writes:

1. The 32-bit accumulator at byte offset 360.
2. The 16-bit status field at byte offset 0.

The accumulator write precedes the status read and write. The visible operation is therefore not specified as one atomic update of the object.

No other direct memory writes, allocation operations, release operations, or global accesses are visible in the supplied body.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence. They have not been executed. Unless stated otherwise, storage remains valid, execution is sequential, arithmetic is representable, and the dependency returns normally.

### Zero adjustment bypasses the object

Given an adjustment of zero, the function returns zero without invoking F-c0024185e7b8 and without accessing either field. This remains the established local behavior even when no dereferenceable object storage is supplied.

### Positive adjustment after a zero result

Given an adjustment of 7, and a dependency result of zero, suppose the accumulator is 20 when the dependency returns and the status value is 0x1234 when read.

The accumulator becomes 27. The status becomes 0xFF34. The function returns zero.

### Negative adjustment is accepted by the branch

Given an adjustment of −5, a dependency result of zero, and a post-dependency accumulator of 20, the accumulator becomes 15.

If the subsequently read status is 0x00A6, the stored status is 0xFFA6. The function returns zero. No local sign check rejects the negative adjustment.

### Nonzero dependency result suppresses local updates

Given an adjustment of 7 and a dependency result of −3, the function returns −3 without reading or writing either field locally.

Any effects already performed by the dependency remain outside this suppression guarantee.

### Dependency changes are used

Suppose the accumulator is 100 before invocation, but the dependency changes it to 40 and returns zero. With an adjustment of 2, the local accumulator update produces 42, not 102.

The same post-call principle applies to the status field: the local OR operation uses the status value it reads after the dependency and accumulator update, not a pre-call copy.

### Already-set status bits remain set

Given a status read of 0xFF61 on the update path, the stored status is also 0xFF61. This does not eliminate the write from the represented behavior.

### Overflow is not assigned a guessed result

Given the maximum signed 32-bit accumulator and an adjustment of 1 after a zero dependency result, this contract does not require a particular resulting accumulator, return sequence, or completion behavior. That boundary requires evidence beyond the supplied representation.
