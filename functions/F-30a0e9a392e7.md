# F-30a0e9a392e7

## Purpose

F-30a0e9a392e7 conditionally obtains a replacement storage handle, processes an array of records, and installs that handle after processing completes. Selected records receive consecutive offsets. Certain unselected records are converted into links through an object-held head value.

The apparent intent is storage compaction with reclamation of specially marked records. That intent is inferred from the access pattern; it does not establish the meaning of size fields, the direction of data movement, or resource ownership.

A zero field at object offset `0x34` disables the operation. Otherwise, a zero control argument enables an additional eligibility check. Nonzero control bypasses that check, but not the initial gate or acquisition failure.

The function has no explicit result indicating success, failure, or the reason for an early return.

## Interface

### Arguments and result

The function accepts:

- **Object address:** identifies mutable storage with accessed fields extending through byte offset `0x37`.
- **Control:** a 32-bit integer tested only for equality with zero. All nonzero values take the same control path.

The function returns no value.

The supplied representation uses 32-bit integer words and 32-bit address-bearing values. The following layouts describe observed accesses, not a complete public type or ownership model.

### Object fields

| Byte offset | Width | Established use |
|---|---:|---|
| `0x08` | 32 bits | Address of a slot containing the record-array base address. |
| `0x10` | 32 bits | Stored backing handle. Its first word supplies a base address for selected-record calls. Replaced during finalization. |
| `0x1c` | 32 bits | Unsigned record traversal bound, read at each loop condition. |
| `0x20` | 32 bits | Head value read and replaced during special-marker conversion. |
| `0x24` | 32 bits | Finalization destination for the then-current value at `0x28`. |
| `0x28` | 32 bits | Used in eligibility, acquisition-size arithmetic, and finalization. |
| `0x34` | 32 bits | Initial work gate, acquisition-size adjustment, and field cleared during finalization. |

“Backing handle” and “head” are usage labels. They do not establish allocation, release, validity, or external interpretation.

### Record fields

Each traversed record occupies eight bytes:

| Record offset | Width | Established use |
|---|---:|---|
| `0x00` | 32 bits | Selected-record offset, or a value inspected for a special marker. |
| `0x04` | 32 bits | Selected-record length argument and advancement quantity, or a stored link after marker conversion. |

The special marker is the exact bit pattern `0x80000001`. Conversion replaces it with `0x80000000`. Their signed 32-bit interpretations are −2147483647 and −2147483648.

No visible check limits selected records to nonnegative lengths or offsets.

### Preconditions and validity

Every address actually reached must support its indicated read or write. In particular:

- The initial read at object offset `0x34` must be valid.
- Reached dependencies must receive inputs valid under their own contracts.
- A nonnull replacement handle must permit reading its first 32-bit word.
- Successful acquisition requires valid indirection through object offset `0x08`, even if no records are visited.
- Traversed records must support the accesses selected by their predicates.
- Selected-record processing must permit dereferencing the current handle at object offset `0x10`.
- Record and object destinations must be writable when their update paths are reached.

The function does not visibly validate address ranges, record counts, offset signs, transfer lengths, replacement capacity, or handle aliasing.

The general access description does not assume records, object fields, handles, and dependency-accessed storage are disjoint. Numerical examples below state stronger non-aliasing assumptions where needed.

## Behavior

### Initial gate and measurement

The first observable object access is a 32-bit read at offset `0x34`.

If that value is zero, the function returns immediately. It makes no dependency call and performs no direct write.

Otherwise, it calls F-ec8cbc7f302e with the object address. The returned value is retained as an unsigned 32-bit **measurement**.

The initial gate value is not retained for subsequent calculations. Later uses of `0x34` read it again. Consequently, effects of the measurement dependency can change later inputs without changing the fact that the initial gate passed.

### Optional eligibility check

For zero control, the function calls F-d7be9cfb4000 with:

1. The retained measurement.
2. A fresh 32-bit read from object offset `0x34`.

Its result is interpreted as unsigned 32-bit.

The function proceeds beyond eligibility only if both conditions hold:

- The result is between 0 and 5 inclusive.
- The measurement is strictly greater, under unsigned comparison, than the value subsequently read at object offset `0x28`.

A result of 6 or greater causes an early return without that comparison’s `0x28` read. For results 0–5, equality between the measurement and `0x28` also causes an early return.

Nonzero control skips F-d7be9cfb4000 and both eligibility conditions.

An eligibility return does not reverse changes made by dependencies already called.

### Acquisition request

If processing continues, the function calls F-ab873b3337c6 with one 32-bit request quantity:

\[
Q=(V_{28}+M-V_{34})\bmod 2^{32}
\]

Here, \(M\) is the retained unsigned measurement, and \(V_{28}\) and \(V_{34}\) are reads from their respective object fields while forming this request.

The measurement’s unsigned type makes this request calculation unsigned 32-bit arithmetic. Overflow and underflow wrap modulo \(2^{32}\); neither is locally rejected.

These field values are not entry snapshots. The relative order of the two field reads within the request expression is not established by the supplied representation.

If acquisition returns null, the function returns without:

- Obtaining the record-array base.
- Calling record predicates or the selected-record dependency.
- Calling the final old-handle dependency.
- Performing its final object-field writes.

Earlier dependency effects, including effects of the failed acquisition attempt, remain outside any local rollback.

### Successful-acquisition setup

For a nonnull replacement handle, the function performs these operations in order:

1. Reads the handle’s first word as the initial replacement destination address.
2. Reads the address-bearing field at object offset `0x08`, then reads the record-array base through that address.
3. Initializes a running compacted offset to zero.
4. Initializes an unsigned 32-bit record index to zero.

The replacement destination and record-array base are captured locally. Later changes to their originating slots do not themselves refresh these captured values.

The traversal bound is not captured. Before each iteration, the unsigned index is compared with a fresh read of object offset `0x1c`.

A zero bound prevents record processing but does not prevent the successful-acquisition setup reads.

### Record classification

For every visited record, F-88337f8f5d95 is called with that record’s address before its fields are interpreted by either branch.

The predicate’s return is tested only for zero versus nonzero. Its contract is otherwise unknown. In particular, the function does not establish that the predicate preserves record contents, object fields, or global state.

### Selected-record processing

For a nonzero predicate result, F-70a021fc7c24 receives three arguments:

1. The first word obtained through the handle currently stored at object offset `0x10`, plus the current record’s first word.
2. The current replacement destination address.
3. The current record’s second word.

These are argument positions, not a proven source/destination contract. Treating them as source address, destination address, and transfer length is consistent with the surrounding behavior but remains dependent on F-70a021fc7c24’s unknown contract.

The relative evaluation order of the reads forming these arguments is not established.

After the call returns normally, the function performs these updates in order:

1. Writes the current compacted offset into the record’s first word.
2. Reads the record’s second word and adds it to the compacted offset.
3. Reads the record’s second word again and adds it to the replacement destination address.

No length snapshot spans the dependency call. Thus, the length passed to the dependency need not equal the length used for either advancement. The post-call reads also occur after the first-word write; aliasing must be considered when that write can overlap other relevant storage.

The stored backing handle is reread for each selected record. A dependency that changes object offset `0x10` can therefore change the handle used by a later selected-record call.

The running offset, destination address, and selected-record address expression use signed-width arithmetic in the supplied representation. Their overflow behavior is not established as unsigned wrapping; valid-range behavior is specified here without asserting overflow safety.

### Unselected-record processing

For a zero predicate result, the function reads the record’s first word after the predicate returns.

If it differs from `0x80000001`, the function performs no direct record update for that iteration.

If it equals `0x80000001`, the following ordered operations occur:

1. Write `0x80000000` into the record’s first word.
2. Read object offset `0x20` and write that value into the record’s second word.
3. Write the unsigned record index plus one into object offset `0x20`.

The stored link is therefore the head value actually read during that conversion—not necessarily the head present at entry, before the predicate, or before an intervening record was processed.

The marker write precedes the head read. If record storage aliases the head field, that ordering can affect the value read.

This sequence resembles insertion into a one-based linked structure. That interpretation does not establish valid link ranges or the meaning of an existing head.

Neither unselected-record case directly advances the compacted offset or replacement destination.

### Traversal progression

After either branch, the record address advances by eight bytes, and the unsigned 32-bit index increments. The continuation check then rereads object offset `0x1c`.

Dependency effects or aliased direct writes that change the bound can shorten or extend traversal. There is no fixed entry-time record count and no independent iteration limit.

### Finalization

After the loop ends, the function performs these operations in order:

1. Calls F-ccce16ca3877 with the handle then read from object offset `0x10`.
2. Writes zero to object offset `0x34`.
3. Writes the acquired replacement handle to object offset `0x10`.
4. Reads object offset `0x28` and writes that value to object offset `0x24`.
5. Returns.

The final dependency receives the handle present after traversal, which need not be the handle present at entry.

The value copied to `0x24` is read after that dependency and after the preceding finalization writes. It need not equal the value used in eligibility or acquisition arithmetic.

No status check or recovery follows the final dependency.

## Side effects

Direct writes can affect:

- The first word of selected records.
- Both words of specially marked unselected records.
- Object offset `0x20` during special-marker conversion.
- Object offsets `0x34`, `0x10`, and `0x24` during finalization.

These are logical write destinations. Aliasing can make a record write also affect object fields or other reachable storage.

Dependencies may produce additional memory, global-state, resource, or external effects. Normal return does not imply preservation of any object field, record, or global.

The operation is not visibly transactional. Record updates precede final handle installation, and no rollback is shown if later processing terminates abnormally. No explicit synchronization or exception recovery is established.

On normal completion, the acquired handle is stored in the object. It is unknown whether acquisition transfers ownership, whether F-ccce16ca3877 releases anything, or whether old and replacement handles can alias.

## Acceptance examples

These are conditional static acceptance examples, not observed executions. They assume valid reached addresses, normal dependency returns, and arithmetic within valid signed/address ranges unless the example explicitly concerns the unsigned request calculation. Additional preservation assumptions are stated where needed.

### Disabled operation

With object offset `0x34` equal to zero, either control class causes immediate return. No dependency is called and no direct write occurs.

### Eligibility boundaries

Assume the initial gate is nonzero and control is zero:

- Eligibility result 5 and measurement equal to the subsequently read `0x28`: return before acquisition.
- Eligibility result 5 and measurement greater than that value: proceed to acquisition.
- Eligibility result 6: return before acquisition, without reading `0x28` for the eligibility comparison.

The comparison is unsigned. A measurement of `0xffffffff` exceeds a field value of `1`.

### Nonzero control

With a nonzero initial gate and any nonzero control value, measurement occurs and acquisition is attempted without an eligibility call. Changes made by measurement still influence the freshly read acquisition fields.

### Wrapped request

If the acquisition expression reads `0x28 = 0x10`, retains measurement `8`, and reads `0x34 = 0x20`, the request is `0xfffffff8`.

The function makes no local underflow rejection.

### Null acquisition

If acquisition returns null, no record predicate, selected-record call, or final old-handle call follows. The function makes no finalization writes. This does not establish that earlier dependencies left the object unchanged.

### Consecutive selected records

Suppose two records are visited and selected, with lengths 3 and 5, and the captured destination is \(D\). Assume distinct record storage disjoint from object fields, stable record lengths, and dependency preservation of the relevant handle, records, and traversal bound.

The selected-record calls receive destination arguments \(D\) and \(D+3\). The first words become 0 and 3. The final running compacted offset is 8.

### Special-marker ordering with preservation

Assume:

- The head is initially 9.
- Exactly three records are visited.
- Records 0 and 2 return zero predicates and retain marker `0x80000001` until inspected.
- Record 1 returns a zero predicate and has a different marker.
- Records are mutually disjoint and do not overlap object fields.
- Every dependency called before completion of record 2 preserves the head.
- No concurrent or reentrant action changes the head.

Record 0 receives marker `0x80000000` and link 9; the head becomes 1. Record 1 makes no direct update. Record 2 receives marker `0x80000000` and link 1; the head becomes 3.

The preservation and non-aliasing conditions are necessary to derive those numerical links from the initial head.

### Special-marker ordering without preservation

Suppose a zero-returning predicate leaves its record marked `0x80000001` but changes the object head to 17. If the subsequent marker write does not alias the head, the record receives link 17, regardless of the entry-time head.

A later conversion similarly stores the head actually read during that conversion. An earlier insertion does not alone determine the later link.

### Successful acquisition with zero records

With a stable bound of zero and a nonnull acquisition result, the function still reads the replacement base and follows the record-base indirection. No per-record dependency is called. The final old-handle call and ordered finalization writes still occur.
