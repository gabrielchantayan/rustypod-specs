# F-7b4f63a2c721

## Purpose

F-7b4f63a2c721 is a guarded indirect-dispatch operation. It examines a signed field in a caller-supplied object, rejects values below one, and otherwise invokes a selector callback. The selector’s result determines which of two further callbacks supplies the operation’s final result.

The established behavior is limited to the supplied static representation. The meaning of the object, the eligibility field, the callbacks, and the returned status values is not established.

The description “guarded dispatch” expresses inferred intent, not an additional behavioral requirement. In particular, there is no evidence that the initial guard validates the complete object or makes subsequent callback execution safe.

## Interface

### Inputs

The operation receives two inputs:

| Input | Established representation | Use |
|---|---|---|
| Object reference | Pointer to storage accessed as consecutive 32-bit integer words | Supplies the eligibility field and dispatch-table base; explicitly passed to two callbacks |
| Auxiliary value | Uninterpreted 32-bit value | Explicitly forwarded only to the nonzero-selector callback |

The object reference must permit the accesses required by the selected execution path. No null check, allocation-size check, or dispatch-target validation is visible.

The auxiliary value has no established interpretation as an integer, pointer, handle, flags, or other domain value. The operation does not visibly dereference or transform it.

### Result

The result is an uninterpreted 32-bit value.

- Rejection produces the bit pattern `0xFFFFFFFF`.
- Every normally returning eligible path returns the selected terminal callback’s 32-bit result unchanged.
- No result normalization, translation, masking, or success classification is visible.

Although `0xFFFFFFFF` is the representation of negative one in a signed 32-bit interpretation, the result’s signedness and domain meaning are not established. A callback may also return this same bit pattern. The result alone therefore does not distinguish guard rejection from a callback-generated result.

### Object and dispatch layout

The visible accesses establish the following byte-relative layout:

| Location | Interpretation used by this operation |
|---|---|
| Object offset 0 | Value used as the dispatch-table base |
| Object offset 4 | Signed 32-bit eligibility field |
| Dispatch-table offset 100 (`0x64`) | Selector callback entry |
| Dispatch-table offset 140 (`0x8C`) | Zero-selector terminal callback entry |
| Dispatch-table offset 148 (`0x94`) | Nonzero-selector terminal callback entry |

These offsets are byte offsets. The eligibility field is the second 32-bit word, not a field at byte offset 1.

The representation uses a 32-bit integer value as the dispatch-table base. A 32-bit address model is consistent with that representation, but the exact machine ABI, pointer encoding, function-entry width, alignment rules, and byte order are not independently established.

The three callback roles are assigned opaque dependency identifiers in this document:

- **F-D01:** selector callback.
- **F-D02:** zero-selector terminal callback.
- **F-D03:** nonzero-selector terminal callback.

These identifiers denote runtime-resolved roles, not proven fixed function identities.

## Behavior

### Eligibility decision

The operation first reads the signed 32-bit field at object offset 4.

If that value is less than one, the operation returns `0xFFFFFFFF` immediately. This includes zero and every negative signed 32-bit value.

On this rejection path:

- No dispatch-table base read is shown.
- No callback-entry read is shown.
- None of F-D01, F-D02, or F-D03 is invoked.
- The auxiliary value is unused.
- No direct write is shown.

The comparison is signed. A field containing the bit pattern `0xFFFFFFFF` is therefore ineligible; it is not treated as a large positive count.

If the field is at least one, dispatch proceeds. The magnitude of the positive value does not otherwise affect the visible behavior. There is no visible decrement, loop, reservation, or consumption of that value.

### Selector invocation

For an eligible object, the operation reads the dispatch-table base from object offset 0, resolves the callback entry at byte offset 100, and invokes F-D01.

The object reference is the sole explicit argument shown for F-D01. The auxiliary value is not explicitly supplied.

F-D01 produces a value represented as a 32-bit integer. The operation distinguishes only zero from nonzero:

- Exactly zero selects F-D02.
- Any nonzero bit pattern selects F-D03.

A negative selector result follows the same branch as a positive nonzero result. It is not treated as an error by this operation.

The selector result is a routing decision, not the final result. A normally completed eligible execution invokes a terminal callback after F-D01 returns.

### Zero-selector branch

When F-D01 returns zero, the operation resolves the entry at byte offset 140 from a dispatch-table base read from the object after the selector call.

The supplied representation shows no explicit arguments for the invocation of F-D02. This is an observation about the recovered call expression, not proof of a complete zero-argument machine-level interface. The indirect transfer was not fully recovered, so implicit argument state, register contents, or a tail-transfer convention remain unknown.

If F-D02 returns normally with a 32-bit result, that result becomes the operation’s result without visible modification.

F-D03 is not invoked on this branch.

### Nonzero-selector branch

When F-D01 returns any nonzero value, the operation resolves the entry at byte offset 148 from a dispatch-table base read from the object after the selector call.

F-D03 receives two explicit arguments, in this order:

1. The original object reference.
2. The original auxiliary 32-bit value.

No transformation of either argument is shown. In particular, the auxiliary value is not replaced by the selector result.

If F-D03 returns normally with a 32-bit result, that result becomes the operation’s result without visible modification.

F-D02 is not invoked on this branch.

### Ordering and callback mutation

The represented access and call order is:

1. Read the eligibility field.
2. If eligible, read the object’s dispatch-table base and resolve F-D01.
3. Invoke F-D01 and obtain its result.
4. Read the object’s dispatch-table base again and resolve the selected terminal callback.
5. Invoke that terminal callback.
6. Return its result, if it returns normally.

The terminal lookup must not be described as necessarily using the dispatch-table base observed before F-D01. The supplied representation performs another lookup through the object after the selector returns.

Consequently, if F-D01 changes the object’s dispatch-table base and leaves the object valid, the terminal callback is resolved through the changed base. This is a conditional consequence of the visible accesses, not evidence that any particular selector performs such a change.

The eligibility field is not visibly reread after F-D01. If F-D01 changes it to zero or a negative value, this operation does not perform another eligibility check before terminal dispatch.

No assumption is made that F-D01 preserves global variables, object contents, callback entries, allocation state, or other process state.

### Arithmetic and access limits

The eligibility decision is a signed comparison against one. There is no arithmetic on that field.

Dispatch lookup uses fixed byte displacements of 100, 140, or 148 from the table-base value. The supplied representation does not establish safe behavior when those address calculations overflow, produce invalid addresses, or encounter unsuitable alignment.

No modulo-addressing guarantee, bounds check, or recovery path may be inferred. Valid storage and callable entries are preconditions for a normal returning dispatch execution.

## Side effects

The operation visibly performs object-field reads, callback-entry reads, and indirect control transfers. No direct memory write appears in the supplied representation.

That absence of direct writes does not make the operation pure or read-only. The callbacks may have effects not shown here, including changes to the object, dispatch tables, globals, external resources, or ownership state.

### Ownership and lifetime

No direct allocation, deallocation, reference-count adjustment, ownership transfer, or cleanup is visible.

This does not establish that the callbacks leave ownership unchanged. In particular:

- F-D01 must leave the original object reference usable for the later lookup if execution is to continue normally.
- The selected terminal callback must be callable through the entry resolved after F-D01.
- No lifetime guarantee for the auxiliary value can be inferred merely because its bits are forwarded.
- No post-callback cleanup by this operation is visible.

If F-D01 invalidates the object and returns, the subsequent object access has no defined successful outcome in the available evidence. The operation contains no visible defense against that condition.

### Errors and abnormal control flow

The only explicit locally generated result is `0xFFFFFFFF` for an ineligible field value.

No explicit handling is shown for:

- An invalid object reference.
- An invalid dispatch-table base.
- An unreadable or noncallable callback entry.
- A callback that fails to return.
- An exceptional or other nonlocal transfer from a callback.
- Concurrent changes to the object or dispatch table.

The behavior of such situations is documented_only. They must not be recast as guaranteed sentinel returns.

## Acceptance examples

These examples are conditional static acceptance criteria, not reports of executed tests. Eligible examples assume readable storage, valid callback entries, compatible invocation conventions, and normally returning callbacks.

### Ineligible zero

Given an eligibility field of zero:

- The result is `0xFFFFFFFF`.
- No callback is invoked.
- The dispatch-table base is not needed for the visible rejection path.

This example does not waive the requirement that the eligibility field itself be readable.

### Ineligible negative value

Given an eligibility field with bit pattern `0xFFFFFFFF`:

- The signed field value is negative.
- The result is `0xFFFFFFFF`.
- Dispatch does not occur.

An implementation that interprets the field as unsigned and proceeds would differ from the represented behavior.

### Smallest eligible value and zero selector

Given an eligibility field of one, F-D01 returning zero, and F-D02 returning `0x12345678`:

- F-D01 is invoked first with the object reference.
- F-D02 is selected through the post-selector lookup at byte offset 140.
- The final result is `0x12345678`.
- F-D03 is not invoked.

This criterion does not establish additional arguments for F-D02.

### Negative selector result

Given a positive eligibility field and F-D01 returning a negative 32-bit value:

- F-D03 is selected because the selector result is nonzero.
- F-D03 receives the original object reference and original auxiliary bits.
- The final result is F-D03’s result.

No special error branch is established for a negative selector result.

### Unmodified auxiliary forwarding

Given a nonzero selector result and auxiliary bits `0x80000001`:

- F-D03 receives those same 32 bits.
- The selector result is not substituted for the auxiliary value.
- No signedness-based conversion of the auxiliary value is visible.

### Dispatch-base replacement by the selector

Given that F-D01 changes the object’s dispatch-table base to another valid table before returning:

- A zero selector result resolves F-D02 through the replacement table.
- A nonzero selector result resolves F-D03 through the replacement table.

Retaining the original table for terminal dispatch would not match the represented post-selector lookup.

### Eligibility changed during selection

Given an initially positive eligibility field, and F-D01 changing that field to zero before returning:

- The operation still selects a terminal callback according to F-D01’s result.
- It does not return the guard sentinel merely because of the changed field.

The object and selected callback must still remain valid.

### Indistinguishable sentinel result

Given eligible execution whose terminal callback returns `0xFFFFFFFF`:

- The final result is `0xFFFFFFFF`.
- The operation does not replace or annotate that result.
- The returned bits alone do not reveal whether rejection or callback execution occurred.
