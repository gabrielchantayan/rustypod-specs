# F-08de07bf2940

## Purpose

The established behavior is a sequence of address calculations, memory writes, an indirect control transfer, and a terminal breakpoint/bad-instruction sequence. No application-level purpose is established.

The visible path derives addresses and values from a 32-bit input, writes two halfwords and three words, writes another halfword, and invokes an unresolved dependency with four arguments. If that invocation returns normally, the supplied representation next reaches a software breakpoint and then an invalid-instruction termination marker. A normal return to the caller is not shown.

This contract describes the supplied static representation. Its instruction-decoding and control-flow warnings limit confidence that the representation accurately describes executable behavior. No runtime tests have been performed.

## Behavior

### Arithmetic model and derived quantities

For the following description, let **X** denote the unsigned 32-bit fourth argument.

The visible unsigned calculations establish these quantities:

| Quantity | Meaning | Range |
|---|---|---|
| **Low field** | Bits 9 through 18 of X, interpreted as an unsigned value | `0`–`0x3FF` |
| **High field** | X shifted right by 18 bits | `0`–`0x3FFF` |
| **Address field** | X shifted right by 22 bits | `0`–`0x3FF` |
| **Adjusted field** | X shifted right by 4 bits, then increased by `0xF4`, then shifted right by 18 bits | `0`–`0x400` |
| **Block selector** | X shifted right by 4 bits, then increased by `0xE7`, then shifted right by 20 bits | `0`–`0x100` |
| **Word-block base** | The block selector shifted right by 4 bits, multiplied by `0x2000` | `0`–`0x20000`, in increments of `0x2000` |
| **Tail selector** | The block selector shifted right by 8 bits | `0` or `1` |

The additions following the four-bit right shift do not overflow 32 bits. Their maximum results are `0x100000F3` and `0x100000E6`, respectively.

The tail selector is `1` exactly when X is at least `0xFFFFF190`; otherwise it is `0`.

All right shifts of X and these unsigned derived quantities are logical shifts.

### Ordered visible effects

The following order applies when preceding operations complete successfully.

1. **Write the low field as a 16-bit value.**

   The destination address is represented as:

   **Argument 2 × `0x02000000` + `0x1A`**

   The low field is at most `0x3FF`, so conversion to 16 bits does not discard any set bits.

   The address expression involves signed arithmetic in the supplied representation. Overflow behavior is not established by that representation. Under a 32-bit wrapping address model, only the low seven bits of Argument 2 affect this address, and every resulting address has low 25 bits equal to `0x1A`. That wrapping interpretation is conditional, not an independently established language-level guarantee.

2. **Write the adjusted field as a 16-bit value.**

   The destination address is:

   **Address field + `0x12`**

   It lies between `0x12` and `0x411`, inclusive. The stored value is at most `0x400`, so narrowing it to 16 bits loses no information.

   This address is not necessarily halfword-aligned. Its alignment depends on the address field.

3. **Do not take the visible traversal branch under the represented types.**

   The branch compares the address field with `0xFFFFFF09`.

   Because an unsigned 32-bit value shifted right by 22 bits cannot exceed `0x3FF`, this comparison cannot succeed. The traversal and its associated memory reads are therefore unreachable under the stated input width and shift semantics.

4. **Write three consecutive 32-bit words.**

   The destination layout is:

   | Offset from word-block base | Width | Value |
   |---|---:|---|
   | `+0` | 32 bits | Adjusted field |
   | `+4` | 32 bits | Stack-sourced value |
   | `+8` | 32 bits | High field |

   These writes occur in the listed order. The word-block base is always a multiple of `0x2000`, so all three addresses are four-byte aligned.

   These operations constitute three individual stores, not an established atomic update.

5. **Write a final 16-bit value.**

   The destination address is:

   **Tail selector + `0xA`**

   The stored value is the tail selector shifted left by 12 bits, narrowed to 16 bits.

   Consequently, this operation has exactly two cases:

   - X below `0xFFFFF190`: write `0x0000` at address `0xA`.
   - X at or above `0xFFFFF190`: write `0x1000` at address `0xB`.

   The latter address is odd. Successful execution therefore depends on the target’s handling of unaligned halfword stores.

6. **Invoke the unresolved dependency.**

   The four argument values are:

   | Position | Value |
   |---|---|
   | 1 | Tail selector shifted left by 24 bits |
   | 2 | The same value as argument 1 |
   | 3 | Stack-sourced value |
   | 4 | `0x010E8000` |

   The first two values are therefore both `0x00000000` or both `0x01000000`.

   There is no visible use of a return value. No preservation of registers, globals, memory, or ownership may be inferred for this dependency.

7. **Reach the terminal sequence only if the dependency returns normally.**

   The next represented operation is a software breakpoint with immediate `0xB4`. An invalid-instruction termination marker follows it.

   The supplied evidence does not establish whether the breakpoint stops execution, transfers control to a handler, permits continuation, or has another platform-specific effect. It does not establish a normal return after this sequence.
