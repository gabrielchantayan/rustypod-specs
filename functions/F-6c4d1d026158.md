# F-6c4d1d026158

## Purpose

F-6c4d1d026158 conditionally replaces a stored pointer value. The caller supplies storage containing an integer representation of the current pointer and supplies a replacement pointer separately.

Pointer equality determines whether any replacement occurs. Equal pointers leave the storage unchanged and cause no indirect call. Unequal pointers cause a replacement write, with an indirect operation beforehand if the current pointer is non-null.

The indirect operation is selected through information obtained from the current object. Its purpose is not established. In particular, the available evidence does not establish destruction, deallocation, reference-count adjustment, or ownership transfer.

This contract describes static evidence. No runtime tests have been performed.

## Interface

### Inputs and result

**Destination storage** identifies a readable signed-integer cell. Its contents are interpreted through an integer-to-object-pointer conversion. If replacement occurs and execution reaches the write, the same cell receives an integer conversion of the replacement pointer.

**Replacement** is an object pointer, possibly null. The function compares it with the decoded current pointer. It does not directly access the replacement’s referent.

The function returns no value. Its observable results are any destination write and any effects of the indirectly invoked target.

### Widths and representation

The destination cell and the field read from the current object have the same represented signed-integer type. The adjustment used to locate the indirect target also takes place in that type.

The available evidence does not establish:

- The signed integer’s width or numerical range.
- Object-pointer or callable-pointer width.
- Pointer and integer conversion rules.
- Alignment requirements or byte order.
- A particular integer representation of null.

These properties remain **documented_only**. A fixed adjustment of four does not establish a four-byte integer type, a native pointer width, or a particular entry number in a dispatch table.

### Referenced layout

For a non-null current pointer that differs from the replacement, the referenced object must expose a readable signed-integer field at its starting address.

The value of that field is an integer address descriptor, not an independently established table pointer. The callable-target slot is located by converting the field value after a signed addition of four. The slot supplies the callable target.

This distinction constrains the layout contract: converting the original field value and then applying pointer displacement is not established as equivalent. Describing the slot as four bytes beyond an encoded base address is valid only if the target’s address representation and conversion rules justify that interpretation.

No further object fields or table entries are directly accessed by this function.

### Preconditions for defined completion

Destination storage must support the initial integer read and its conversion for comparison.

On a replacement path, the replacement must admit the required integer conversion, and destination storage must remain valid and writable until the final write.

On the path involving an indirect operation, the current object’s initial field must be readable, the signed addition must be defined, the resulting conversion must identify a readable callable-target slot, and the fetched target must support invocation with the actual call state.

The function performs no explicit validation of these conditions.

## Behavior

### Equality governs replacement

The decision concerns pointer values, not object contents and not an expressly established comparison of raw integer encodings.

When the decoded current pointer equals the replacement, the function completes without writing the destination or consulting the current object. This applies to equal non-null pointers and to two null pointers.

An equal non-null pointer therefore need not identify readable object contents for this function’s direct accesses. The destination read and the initial conversion must still be valid.

When the pointers differ, the function commits to the replacement path. There is no subsequent equality decision.

### Null current value

A null current pointer requires no indirect operation. When it differs from the replacement, the destination receives the replacement’s signed-integer representation.

This path performs no dispatch-related reads and no direct access to the replacement object. It neither validates nor initializes that object.

### Non-null current value

For a differing, non-null current pointer, the indirect operation precedes the replacement write. Selection of that operation depends on the current object’s initial integer field and the callable-target slot derived from it.

The observable ordering is constrained as follows:

- The destination read and pointer comparison precede dispatch-related accesses.
- The object-field read precedes the callable-target fetch.
- The target fetch precedes invocation.
- The destination write occurs only after the invocation returns normally.

There is no destination write by this function before the indirect operation. If the operation returns normally and the remaining prerequisites hold, the replacement is converted to the destination’s integer representation and written.

The function does not directly inspect the replacement object on this path either.

### Arithmetic boundary

The adjustment of four is signed integer arithmetic. No widening, overflow check, saturation, or unsigned wrapping behavior is established.

A field value greater than the represented signed maximum minus four would overflow the addition. Under the represented signed-arithmetic semantics, that case has no defined continuation. The contract does not accept wraparound to another target address as guaranteed behavior.

Adding positive four to an existing valid signed value cannot overflow below the type’s minimum. Even when the sum is representable, however, it need not convert to a valid target-slot address. Numerical validity and address validity are separate requirements.

The exact numerical boundary remains **documented_only** because the signed width is not supplied.

### Effects of an intervening call

The replacement decision is based on the destination’s original decoded value. The destination is not read again after the indirect operation.

Consequently, a normally returning target that changes destination storage does not cause the function to reconsider its decision. If the destination remains writable, this invocation subsequently writes its own replacement value over the intervening contents.

This behavior does not imply that the destination still contains its original value at call entry. Other execution or aliases may have changed it. The established guarantee is narrower: this invocation has not yet performed its replacement write.

The function provides no protection against the target invalidating the destination. A normal return alone is insufficient to make the subsequent write safe.

### Completion and errors

The equality path completes without a replacement write. The differing-null path completes after its write without invoking a target. The differing-non-null path reaches its write only after normal return from the target.

A non-returning target prevents this invocation from reaching its final write. Abnormal control transfer has no shown local recovery or cleanup.

There is no explicit error result, validation-failure branch, fallback target, retry, or handler. Invalid memory access, unsupported conversion, signed overflow, or incompatible invocation prevents a defined successful-completion guarantee. The concrete failure manifestation is **documented_only**.

## Side effects

At the level of the supplied representation, the function reads the destination once.

An equal-pointer invocation performs no destination write. An unequal-pointer invocation performs one destination write if execution reaches it.

Only the differing, non-null path directly reads the current object’s initial integer field and the derived callable-target slot. The replacement’s referent is never directly read or written.

These are direct accesses attributable to this function, not limits on accesses performed by the target.
