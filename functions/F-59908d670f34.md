# F-59908d670f34

## Purpose

F-59908d670f34 changes two signed-integer fields within a caller-supplied memory region. It adds an adjustment to the first field and subtracts the same adjustment from the third field. If the adjusted first field exceeds the adjusted third field, it clears all four fields.

The established behavior is an in-place arithmetic update followed by a strict ordering check. Equality is accepted without clearing.

An inferred interpretation is that the first and third fields represent ordered bounds, with a positive adjustment moving them inward and a negative adjustment moving them outward. The supplied evidence does not establish that interpretation, the meaning of the second and fourth fields, or the meaning of an all-zero state.

## Interface

### Inputs

The function accepts:

- A pointer to signed-integer storage.
- A signed-integer adjustment supplied by value.

For this contract, the storage positions are called the **first**, **second**, **third**, and **fourth** fields. These labels describe consecutive integer positions relative to the supplied pointer; they do not imply a known structure type.

The pointer is not checked for nullness, alignment, validity, or available storage.

### Width and layout

The supplied representation uses the signed integer type `int` for both the storage elements and the adjustment. It does not independently establish the target ABI or the width of that type.

Let:

- \(S\) be the size of one integer element in addressable bytes.

The fields begin at offsets \(0\), \(S\), \(2S\), and \(3S\) from the supplied pointer. There is no additional gap between these array positions.

If the applicable ABI uses 32-bit, four-byte integers, the offsets are 0, 4, 8, and 12 bytes. That concrete layout is conditional, not established solely by the supplied representation. Byte order is also unspecified.

### Output and ownership

There is no return value or separate status result. The result is the mutation of caller-supplied storage.

### Preconditions

For the complete behavior, including the clearing branch, the supplied pointer must address at least four consecutive writable integer elements. The first and third fields must also contain values that can validly be read as signed integers.

The second and fourth fields are never read. Their initial contents do not participate in the decision.

## Behavior

### Arithmetic transformation

Let the initial first field be \(a\), the third field value obtained during execution be \(c\), and the adjustment be \(d\).

For executions without interfering memory changes and with defined arithmetic, the adjusted values are:

\[
a' = a + d
\]

\[
c' = c - d
\]

The function preserves these adjusted values when \(a' \leq c'\). It clears all four fields when \(a' > c'\).

The decision is based on the adjusted values, not on the ordering of the original fields. An initially reversed pair is therefore not sufficient by itself to determine the result: a negative adjustment can make the adjusted pair ordered.

### Memory-access order

The supplied representation establishes the following source-level sequence:

1. Read the first field.
2. Write the adjusted value to the first field.
3. Read the third field.
4. Write the adjusted value to the third field.
5. Compare the adjusted values derived from the captured inputs.
6. Either return immediately or clear the four fields.

The third-field read occurs after the first-field write. The first and third fields are updated before the ordering decision.

The comparison does not reread either field from memory. Its operands are derived from the values previously obtained and the adjustment. Consequently, the decision is not a validation of the storage contents at some later instant.

This sequence describes the supplied source-level behavior. It does not establish physical bus transactions, atomicity, memory barriers, or an exact optimized instruction sequence.

### Ordered-result branch

When \(a' \leq c'\):

- The first field contains \(a'\).
- The third field contains \(c'\).
- The second and fourth fields are unchanged by this function.
- Execution returns without further writes.

Equality belongs to this branch. An adjusted first field equal to the adjusted third field does not trigger clearing.

### Reversed-result branch

When \(a' > c'\), the function writes zero to the fields in this order:

1. First field.
2. Second field.
3. Third field.
4. Fourth field.

Execution then returns.

On this branch, the first and third fields have each already received an adjusted value before being overwritten with zero. The function does not first check whether the adjustment would reverse their ordering and then choose a single final write.

The resulting four-zero state is established behavior. Whether callers interpret it as empty, invalid, disabled, or something else is unknown.

### Zero and negative adjustments

A zero adjustment still causes the first and third fields to be read and written before comparison.

- If the original first field is no greater than the original third field, field values remain unchanged.
- If the original first field exceeds the original third field, all four fields are cleared.

A negative adjustment decreases the first field and increases the third field, provided both operations are representable. There is no rejection or special handling of negative adjustments.

## Side effects

All explicit side effects are writes to the supplied memory region.

On the ordered-result branch, the function performs two source-level writes: first field, then third field.

On the clearing branch, it performs those two writes followed by four zero writes. The second and fourth fields are written only on the clearing branch.

There are no explicit external calls, global-variable accesses, logging operations, callbacks, allocations, or releases in the supplied body. The storage itself could nevertheless be part of global or shared state; the pointer’s origin is unknown.

No synchronization is present. The function does not promise that another observer sees the entire transformation atomically. Concurrent conflicting access requires an external execution model or synchronization arrangement; its results are not specified here.

No error-reporting path is present. Invalid memory access or arithmetic outside the defined range must not be interpreted as a deliberate failure result, and there is no rollback mechanism.

## Acceptance examples

These examples are conditional specifications, not runtime observations. Each tuple lists the first through fourth fields. All listed arithmetic fits within a signed 32-bit range and within conventional wider signed integer types.

### Ordered adjustment

Initial fields: \((10, 7, 30, 9)\). Adjustment: \(5\).

The adjusted first and third fields are 15 and 25. Since 15 is no greater than 25, the final fields must be:

\[
(15,\ 7,\ 25,\ 9)
\]

The second and fourth fields remain unchanged.

### Equality is retained

Initial fields: \((10, 7, 20, 9)\). Adjustment: \(5\).

Both adjusted fields equal 15. The final fields must be:

\[
(15,\ 7,\ 15,\ 9)
\]

Clearing would violate the strict condition for the clearing branch.

### Reversal clears all fields

Initial fields: \((10, 7, 19, 9)\). Adjustment: \(5\).

The adjusted first field is 15 and the adjusted third field is 14. The final fields must be:

\[
(0,\ 0,\ 0,\ 0)
\]

At the source level, the writes of 15 and 14 precede the four clearing writes.

### Negative adjustment can retain an initially reversed pair

Initial fields: \((20, 7, 10, 9)\). Adjustment: \(-6\).

The adjusted first and third fields are 14 and 16. The final fields must be:

\[
(14,\ 7,\ 16,\ 9)
\]

An implementation that clears solely because the original first field exceeds the original third field would not match this behavior.

### Zero adjustment still applies the ordering rule

Initial fields: \((9, 7, 8, 6)\). Adjustment: \(0\).

The adjusted pair remains reversed, so the final fields must be:

\[
(0,\ 0,\ 0,\ 0)
\]

### Overflow is outside the established result contract

Under a signed 32-bit interpretation, an initial first field of 2,147,483,647 with adjustment \(1\) requires an unrepresentable addition.

This contract does not require wrapping, saturation, clearing, or any particular final tuple for that case.
