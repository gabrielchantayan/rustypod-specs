# F-80de2f8a602f

## Purpose

F-80de2f8a602f conditionally updates one of five 32-bit fields in a selected record within caller-supplied storage. It accepts eight consecutive record identifiers. Three field selectors accept every 32-bit value; two enforce numeric restrictions. One accepted update also invokes F-e4e2db384d33.

Rejected requests can set a status word at the beginning of the caller-supplied storage. This is a first-error-style operation: the function writes that word only when the selected error value is nonzero and the existing word is zero. Successful ordinary updates do not clear or otherwise inspect the status word.

These are structural observations. The semantic meanings of the records, fields, numeric units, and status values are not established.

## Interface

The function has four inputs and no explicit return value:

| Input | Representation | Role |
|---|---|---|
| Storage address | Pointer in the supplied 32-bit address model | Base for record-field addressing and address of a 32-bit status word |
| Record identifier | 32-bit integer | Selects one of eight accepted records |
| Field selector | 32-bit quantity | Selects the update operation |
| Proposed value | Signed 32-bit integer | Value to validate and, when accepted, store |

The accepted record identifiers are **0x4000 through 0x4007, inclusive**. The range test uses unsigned subtraction, rather than a signed comparison. In the represented 32-bit model, it accepts exactly those eight bit patterns.

The implementation obtains three values from global storage:

- **Address adjustment:** a value used in record-field address calculation.
- **Validation status:** a 32-bit value used when a recognized, range-restricted field rejects its proposed value.
- **Dependency argument:** a value loaded and passed to F-e4e2db384d33 on the accepted 0x1206 path.

The actual contents, semantic types, mutability, and ownership implications of these globals are not supplied.

### Storage layout

Let the supplied storage address be the base address. For an accepted record identifier, the function forms a record address using:

**base address + address adjustment + record identifier × 168 bytes**

The identifier is used directly. It is **not** first reduced by 0x4000. Consequently, the identifier-dependent contribution ranges from 0x2A0000 through 0x2A0498. Any relationship between the global adjustment and that large contribution is unknown.

The selected field lies at one of these byte offsets from the calculated record address:

| Field selector | Field offset | Stored width |
|---|---:|---:|
| 0x1205 | 100 / 0x64 | 32 bits |
| 0x1206 | 104 / 0x68 | 32 bits |
| 0x1207 | 88 / 0x58 | 32 bits |
| 0x1208 | 92 / 0x5C | 32 bits |
| 0x1209 | 96 / 0x60 | 32 bits |

The status word is a separate logical location at byte offset zero from the supplied base address. The evidence does not establish that it cannot physically overlap a calculated field address.

The caller must supply valid, writable storage for every location actually accessed on the chosen path. No buffer length, null check, address validation, bounds check, or alignment repair is present. Required alignment and the consequences of invalid memory depend on the execution environment.

## Behavior

### 1. Record selection

The function first checks whether the record identifier is in the eight-element accepted range.

For an out-of-range identifier:

- It does not calculate a record-field address.
- It does not read the address-adjustment or validation-status globals.
- It selects the fixed status value **0x500**, decimal **1280**.
- It proceeds to the conditional status-update behavior below.

For an accepted identifier, the represented operation order is:

1. Read the global address adjustment and form the identifier-dependent address contribution.
2. Read and retain the global validation-status value.
3. Dispatch on the field selector.

Thus, accepted identifiers cause both globals to be read even if the selector is unsupported, the proposed value is rejected, or the eventual update requires no error reporting.

This is the operation order exposed by the supplied representation, not a claim about atomicity, compiler memory ordering, or concurrent observation.

### 2. Selector 0x1205

This selector accepts proposed values from **0 through 0x800000 inclusive**, equivalent to **0 through 8,388,608**.

On acceptance:

- Write the proposed value as one 32-bit field at offset 0x64.
- Return immediately.
- Do not read or modify the status word.
- Do not invoke F-e4e2db384d33.

On rejection:

- Do not write the field.
- Use the previously read validation-status value in the conditional status-update operation.

Negative values and values greater than 0x800000 are rejected.

### 3. Selector 0x1206

This selector accepts either:

- Any value from **0 through 0x5A0000 inclusive**, equivalent to **0 through 5,898,240**; or
- The single additional value **0xB40000**, equivalent to **11,796,480**.

The interval between 0x5A0001 and 0xB3FFFF is rejected. Values above 0xB40000 are also rejected. All negative values are rejected.

On acceptance, the function:

1. Writes the proposed value as one 32-bit field at offset 0x68.
2. Reads the dependency-argument global.
3. Calls F-e4e2db384d33 with that value as its single visible argument.

The write precedes the call. There is no visible rollback if the dependency fails, terminates execution, transfers control elsewhere, or modifies memory.

The supplied representation marks this dependency call as non-returning. That annotation does not independently establish the dependency’s behavior. If the dependency does not return normally, this function performs no later local status operation. If it does return normally, the represented continuation reaches conditional status handling with the validation-status value captured before the call.

On rejection:

- Do not write the field.
- Do not read the dependency-argument global.
- Do not call F-e4e2db384d33.
- Use the captured validation-status value in conditional status handling.

### 4. Selectors 0x1207, 0x1208, and 0x1209

These selectors impose no value restriction.

They store the proposed 32-bit value at offsets 0x58, 0x5C, and 0x60, respectively, then return immediately. Negative values, zero, and the signed 32-bit extrema are all accepted.

These paths do not read or write the status word and do not invoke F-e4e2db384d33.

### 5. Unsupported selectors

For an accepted record identifier and any selector other than the five listed values:

- Do not write a record field.
- Select fixed status value 0x500.
- Perform conditional status handling.

The global address adjustment and validation-status value have already been read before this unsupported-selector decision. The captured validation-status value is superseded by 0x500.

For an invalid record identifier, the field selector and proposed value do not change the outcome: conditional status handling uses 0x500.

### 6. Conditional status handling

This operation takes a selected 32-bit status value:

- If the selected value is zero, return without reading or writing the caller’s status word.
- If it is nonzero, read the 32-bit word at the supplied base address.
- If that word is zero, write the selected status value there.
- If that word is nonzero, leave it unchanged.
- Return.

There is no special treatment of negative status values. Any nonzero 32-bit value is eligible to be written.

A rejected value can therefore leave all caller-supplied storage unchanged when the validation-status global is zero. Conversely, a pre-existing nonzero status survives both fixed-status errors and value-validation errors.

This is a separate read followed by a conditional write, not an established atomic “set if zero” operation.

## Side effects

### Direct memory effects

Excluding effects of F-e4e2db384d33, a completed path performs at most one direct write to caller-supplied storage:

- One selected field write on an accepted ordinary update;
- One status write on an error path whose selected status is nonzero and whose existing status is zero; or
- No write.

The accepted 0x1206 path is exceptional: it writes its field before calling the dependency. If that dependency returns, the represented continuation can additionally write the status word.

A field update does not consult the old field value. It is performed even when the old and proposed values are equal.

If a calculated field address aliases the base status word or another externally meaningful location, the actual write affects that location. No separation check is visible.

### Global effects and dependency effects

No direct global write is visible. Reads occur as described above. The callee’s effects on global storage, the caller’s storage, or other state are unknown.

In particular, this contract does not assume that F-e4e2db384d33 preserves globals. If it returns after changing the validation-status global, the caller’s represented continuation still uses the value captured before the call. Its later status-word read, if required, observes the memory state then present rather than a saved pre-call status word.

### Ownership and failures

No allocation, deallocation, reference-count change, or ownership transfer is visible in the function itself.

Passing the dependency-argument value does not establish whether that value denotes memory, whether ownership is transferred, or whether the dependency releases anything. Those questions are documented_only.

There is no explicit exception handler, failure return value, or recovery mechanism. Invalid addresses and dependency-originated failures have no locally specified handling.

## Acceptance examples

These examples are conditional expectations from static evidence, not executed tests. They assume valid memory and no unmodeled concurrent interference. “Unchanged” below excludes unknown dependency effects.

1. **Lower accepted record, upper 0x1205 boundary.**  
   Given identifier 0x4000, selector 0x1205, and value 0x800000, write that value at base + address adjustment + 0x2A0000 + 0x64. Do not access the status word.

2. **Rejected 0x1205 value with writable zero status.**  
   Given an accepted identifier, selector 0x1205, value 0x800001, validation status 7, and existing status zero, leave the selected field unchanged and set the status word to 7.

3. **Rejected value with zero validation status.**  
   With the same rejected value but validation status zero, leave the field unchanged and do not even read the status word.

4. **Preservation of an existing error.**  
   Given a rejected value, nonzero validation status, and existing status 12, preserve 12 rather than overwrite it.

5. **0x1206 range discontinuity.**  
   Value 0x5A0000 is accepted. Value 0x5A0001 is rejected. Value 0xB40000 is accepted as an isolated additional value. Value 0xB40001 is rejected.

6. **Accepted 0x1206 update ordering.**  
   For any accepted 0x1206 value, the field write must precede the dependency call. Whether execution returns, and what the dependency changes, remain dependency-specific.

7. **Unrestricted signed value.**  
   Given identifier 0x4007, selector 0x1208, and value −2,147,483,648, write that 32-bit value at base + address adjustment + 0x2A0498 + 0x5C. Do not access the status word.

8. **Unsupported selector.**  
   Given identifier 0x4000, unsupported selector 0x1204, and existing status zero, read the two accepted-identifier globals, write no field, and set status to 0x500.

9. **Identifier boundaries.**  
   Identifiers 0x3FFF and 0x4008 are rejected. Each selects status 0x500 without reading the record-address or validation-status globals. Identifier 0x4007 remains accepted.

10. **Successful update with an existing error.**  
    An accepted 0x1207 update still writes its field when the status word is already nonzero. It neither checks nor clears that error.

11. **Unexpected normal return from the dependency.**  
    If F-e4e2db384d33 returns normally after an accepted 0x1206 update, conditional status handling uses the earlier captured validation status. A zero captured value prevents any subsequent status-word access; a nonzero captured value permits the usual read and conditional write.

## Uncertainties

The following are documented_only:

- The semantic names, units, and intended consumers of all five fields.
- The actual global adjustment and status values.
- The object’s allocation size and whether all calculated addresses belong to it.
- Whether any field can alias the status word or global storage.
- Endianness, alignment guarantees, and fault behavior.
- Exact machine-level handling of address arithmetic that exceeds the representable address range. The identifier multiplication itself fits in 32 bits for every accepted identifier; adding the unknown adjustment and base may not.
- The dependency argument’s declared width and meaning.
- Whether F-e4e2db384d33 actually never returns.
- Dependency ownership, release behavior, and effects on memory or globals.
- Thread-safety, interrupt safety, synchronization, and atomicity.

The 168-byte record stride and selector-dependent offsets suggest repeated records with configurable properties. The conditional status write suggests preservation of an earlier error. These are inferred intent, not established semantic guarantees.
