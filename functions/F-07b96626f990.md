# F-07b96626f990

## Purpose

F-07b96626f990 conditionally processes an object obtained through a caller-supplied handle. It clears one field of the initially selected object, invokes F-cfa516687f12 twice, selects an object again through the handle, traverses that object’s table of chains, and performs a sequence of indirect operations.

The established contract concerns explicit memory accesses, argument values, call ordering, guards, and retained state. A teardown or cleanup purpose is inferred, not established. Neither the traversal nor the dependency names establish destruction, deallocation, or ownership transfer.

Execution after any dependency call is conditional on that call returning and the storage needed by subsequent operations remaining accessible. Dependencies are not assumed to preserve globals, object contents, or storage lifetime.

### Table and chain layout

The table contains 32-bit chain-head addresses at four-byte intervals. A zero head denotes an empty chain.

Each nonzero chain position must support a 32-bit next-address read at offset +4. Zero terminates the chain. No other node field is explicitly accessed.

### Global and dispatch storage

Two distinct global locations provide the middle arguments of the two F-cfa516687f12 invocations. Each supplies a 32-bit value. Distinct locations need not contain different values.

A separate shared location supplies dispatch-storage addresses. It is read twice during dispatch setup:

- The first result is retained for the mandatory operation and final optional operation.
- The second result supplies the initial optional-target lookup.

The two results need not be equal.

| Dispatch offset | Width | Established use |
|---|---:|---|

The optional targets are checked for zero. The mandatory target is not. Neither dispatch-storage address is checked for zero before its field access.

## Behavior

### Entry guards and initial write

If the first input is zero, the function returns without reading handle storage, writing object storage, or invoking dependencies.

Otherwise, it reads the object address at handle offset +8. If that address is zero, it returns without an object write or dependency call.

For a nonzero initial object address, the function writes a 32-bit zero at that object’s +32 field. This write precedes both preliminary calls.

The object receiving this write is not necessarily the object used for traversal. The handle field is read again during argument evaluation and after both preliminary calls.

### Preliminary calls

F-cfa516687f12 is invoked twice in a fixed order.

The first invocation has three recovered arguments:

1. A value read from handle offset +8.
2. A value read from the first global argument-value location.
3. A separately read value from handle offset +8.

The second invocation has the same arrangement, using the second global argument-value location.

Within each invocation, the relative evaluation order of the global read and the two handle-field reads is unresolved. The two object-address arguments are separate reads, not a guaranteed shared snapshot. Equality requires the handle field to remain unchanged across those reads.

The second global value is obtained for the second call, after the first call returns. The first call can therefore affect the value supplied to the second call. Neither global value has an established constant value or semantic interpretation.

There is no intervening null guard that suppresses the second call. If the first call leaves the handle’s +8 field zero, the second call still occurs, provided argument evaluation and execution remain possible.

### Traversal-object selection

After both preliminary calls return, the function reads handle offset +8 again.

If that read yields zero, execution returns. The initial zero write and both preliminary calls have already occurred.

Otherwise, this newly read address becomes the retained traversal-object address. Subsequent table and bound accesses use that object. The later object-directed indirect operations also receive this retained address.

A later change to the handle field does not itself replace the retained traversal object. Changes to that object’s contents or lifetime can still affect execution.

### Outer table traversal

The traversal index starts at zero and is unsigned 32-bit.

Before every outer-loop body, including the first, the function reads the traversal object’s +12 field and compares the index with that value as unsigned. An iteration occurs only if the index is less than the freshly read bound.

Each entered iteration:

- Reads the table address from traversal-object offset +0.
- Selects the table entry at a four-byte stride from that address.
- Reads its 32-bit chain-head address.
- Traverses the selected chain.
- Increments the index after the chain terminates.

For table-entry selection, multiplication of the index by four and addition to the table address are reduced modulo \(2^{32}\). The resulting address is not checked for validity.

The index increment is unsigned 32-bit arithmetic. The bound is also a 32-bit unsigned value; an all-one-bit bound means 4,294,967,295, not a negative number.

The bound is reloaded for every outer condition. The table address is reloaded for every entered iteration. Neither value is an immutable traversal-wide snapshot.

### Chain traversal and mutation timing

A zero chain head produces no chain-loop call.

For each nonzero chain position, the function reads the next address at offset +4 before invoking F-5990a26eaaa3. If that call returns, traversal continues using the already-read next address.

Consequently:

- Changing the processed position’s next field during the call does not change the next address already selected for that step.
- Changing a future position’s next field can affect a later read.
- Changing the table-address field does not redirect the active chain.
- Changing the outer bound does not immediately interrupt the active chain.

The chain-loop invocations have no recovered explicit arguments. No contract assigns the current position, next position, or table address as an argument to those invocations.

The outer bound matters again only after the active chain terminates and the index increments. A reduction during one chain-loop call does not establish that the next outer iteration will be skipped: a later call in the same chain can increase the bound again. The next iteration decision depends on the value actually read by the next outer condition.

No cycle detection, chain-length limit, or general termination guarantee is established.

### Table-associated call

After the outer loop ends, the function reads traversal-object offset +0 again and invokes F-5990a26eaaa3 with that value as an explicit argument.

This call occurs even when the initial bound is zero and no table entry is visited. Its argument is not checked for zero.

The supplied table address is the value read at this point. It need not equal any address used during an earlier iteration.

### Dispatch sequence

After the table-associated call returns, the function performs these operations in order:

1. Reads the shared dispatch-address location and retains the result.
2. Reads that shared location again.
3. Reads an initial optional target at +48 using the second result.
4. Invokes that target if it is nonzero.
5. Reads a mandatory target at +24 using the retained first result, then invokes it without a zero-target check.
6. Reads a final optional target at +48 using the retained first result.
7. Invokes the final target if nonzero; otherwise returns directly.

The initial optional invocation has eight recovered argument positions: the traversal-object address, zero, the selected target’s own address, the original fourth input, and four machine-context words. Their complete calling convention and meanings are unresolved.

The mandatory invocation has the traversal-object address as its recovered argument.

The final optional invocation has two recovered arguments: zero and one.

Later changes to the shared dispatch-address location do not replace the retained first address. Changes within the storage at that retained address can affect the mandatory and final target reads.

Even if both initial dispatch-address reads yield the same address, the two +48 target reads occur at different times and need not yield the same target.

## Acceptance examples

These examples are conditional consequences of static evidence, not executed tests. Except where an early return applies, continuation requires valid accessed storage, callable invoked targets, and returning dependencies.

### Absent handle or initial object

A zero first input causes return without a handle read or dependency call.

A valid nonzero handle whose +8 field is zero causes one initial object-address read followed by return, without the object-field write or preliminary calls.

### Preliminary calls observe distinct read times

If both global argument-value locations contain the same value when their respective arguments are evaluated, both calls receive that same middle argument.

If the first preliminary call changes the second global location from value A to value B, and B remains until the second call’s argument read, the second call receives B.

### Object removed or replaced

If the initial handle lookup selects object A, A’s +32 field is cleared before either preliminary call.

If the post-call lookup is zero, traversal and dispatch are skipped after both calls.

If that lookup selects object B instead, subsequent traversal and object-directed indirect operations use B. This function need not have cleared B’s +32 field.

### Zero traversal bound

If the first outer-condition read yields zero, no table entry or chain link is read. The function still reads the current table-address field, passes it to F-5990a26eaaa3, and proceeds to dispatch.

### Two-position terminating chain

For a visited entry selecting a two-position terminating chain, the observable order is:

- First position’s next-link read.
- First chain-loop call.
- Second position’s next-link read.
- Second chain-loop call.
- After outer traversal ends, the separate table-associated call.

This establishes call count and ordering, not pointer arguments or deallocation.

### Bound reduced and still low at the next condition

Suppose an iteration at index zero processes a terminating chain, and a chain-loop call reduces the bound to zero. If the next outer condition actually reads zero after chain termination and index advancement to one, another table iteration is prevented.

The reduction alone is insufficient. This outcome is conditional on the value read at that later condition.

### Bound reduced and then raised within the same chain

Suppose an iteration at index zero processes a two-position chain. The first chain-loop call changes the bound to zero; the second changes it to two. If the next outer condition reads two, index one is less than the bound, so another table iteration is entered.

This sequence is permitted because no dependency-preservation guarantee excludes the second change.

### Different dispatch-storage addresses

If the first shared dispatch-address read yields A and the second yields B, the initial optional target comes from B at +48. The mandatory and final optional targets come from A at +24 and +48 respectively.

### Optional target installed later

If the initial optional-target read yields zero, that call is skipped. If the mandatory operation leaves a nonzero target at +48 of the retained dispatch storage, and the final lookup reads it, the final invocation occurs with zero and one.

### Wrapped table-entry address

For a loaded table address of 4,294,967,292 and an entered iteration at index one, the four-byte offset produces entry address zero modulo \(2^{32}\).

This specifies the calculated address, not the validity or outcome of reading it.

### Large unsigned bound

A bound of 4,294,967,295 does not suppress traversal as a negative value. The initial index zero compares less than that bound. Address validity and eventual termination remain separate requirements.
