# F-105972290119

## Purpose

F-105972290119 performs a bounded, first-match lookup over records spaced 16 bytes apart. It compares each examined record’s 32-bit key with a supplied key. On the first match, it transfers two 32-bit fields to caller-supplied output locations and returns 1. If the search reaches its count limit without a match, it returns 0 without accessing either output location.

The result transfer is ordered rather than atomic. The first result is read and written before the second result is read. Output storage that overlaps record storage can therefore affect the second result.

Record-address calculation uses unsigned 32-bit arithmetic and reduces modulo 2³². This establishes the calculated integer address value, not whether its conversion to a pointer produces valid, accessible storage.

These are static behavioral conclusions. No runtime tests have been performed.

## Interface

The function accepts five positional inputs and returns a 32-bit status value.

| Position | Meaning | Representation |
|---|---|---|
| 1 | Record-sequence base | Signed 32-bit integer used in address calculation |
| 2 | Maximum number of records to examine | Unsigned 32-bit integer |
| 3 | Search key | Signed 32-bit integer compared for equality with record keys |
| 4 | First output destination | Pointer to a writable 32-bit integer when the successful path reaches its first store |
| 5 | Second output destination | Pointer to a writable 32-bit integer when the successful path reaches its second store |

The only established normal return values are:

- **0:** the search exhausted the supplied count without finding a matching key.
- **1:** a match was found and both result transfers completed.

There is no separate normal status for invalid memory, unsuitable alignment, pointer-conversion problems, or an inaccessible destination.

### Record layout

Record-start integer addresses are calculated with a stride of 16 bytes. Once a calculated address is interpreted as a record pointer, the function uses the following layout:

| Byte offset | Width | Role |
|---|---|---|
| 0 | 32 bits | Key |
| 4 | 32 bits | Not accessed by this function |
| 8 | 32 bits | First result source |
| 12 | 32 bits | Second result source |

The layout establishes only the fields used by this function. It does not establish the meaning of the unused field or a complete record schema.

The key and result fields are accessed as 32-bit integers, not decoded byte by byte. Byte order and access-alignment requirements remain dependent on the execution environment.

### Preconditions and ownership

Normal completion requires each reached memory access to be valid when it occurs:

- Each examined key must be readable.
- A matched record’s first result must be readable before the first output store.
- The first output destination must be writable.
- The matched record’s second result must be readable after that first store.
- The second output destination must be writable.

The function performs no explicit validation of these conditions. Its requirements are path-dependent: a zero-count call accesses neither records nor outputs; an unsuccessful search accesses keys but neither result fields nor outputs.

No allocation, deallocation, ownership transfer, or retention of the supplied storage is established. Storage remains externally managed.

Disjoint storage is not required or checked. For independent, unaffected result values, callers should supply destinations that do not overlap either result source or each other. Other overlap cases follow the ordered accesses described below, subject to the environment’s memory-access rules.

## Behavior

### Search bounds and selection

The search index starts at zero and is an unsigned 32-bit quantity. Before each candidate record access, the function compares that index with the unsigned count. If the index is greater than or equal to the count, the function returns 0.

For an index below the count, the function calculates the candidate’s record-start integer address, converts it to a pointer, and reads the key at offset 0. If the key equals the supplied search key, searching stops immediately. Otherwise, the index increases by one and the bound check repeats.

Consequences include:

- A zero count causes no record-address conversion or record access.
- A successful search examines keys in increasing index order through the first match.
- Later matching records cannot replace the first match.
- An unsuccessful search examines one key for every index below the count, assuming all accesses complete.
- Result fields are not read for nonmatching records.
- The field at offset 4 is not directly accessed.
- No key value is treated as an empty-slot marker, terminator, or special case.

The key comparison is equality, not an ordering comparison. Negative search keys are eligible to match negative record keys.

### Record-address arithmetic

For each examined index, the record-start integer value is calculated in two unsigned 32-bit stages:

1. Multiply the index by 16, retaining the result modulo 2³².
2. Convert the signed 32-bit base to unsigned 32-bit form, add it to that product, and retain the sum modulo 2³².

Equivalently, the calculated integer address is:

**(unsigned-32(base) + 16 × index) mod 2³².**

Converting a negative base to unsigned 32-bit form gives its value modulo 2³². For example, a base of −16 contributes the unsigned value 4,294,967,280.

Both multiplication overflow and addition overflow therefore have established modular integer results in the supplied representation. Neither is an explicit error condition, and neither causes an early failure return.

The subsequent conversion of that integer to a pointer is a separate matter. Modular arithmetic does not establish that the resulting pointer is meaningful, suitably aligned, within a valid object, or readable. Likewise, access to fields at offsets 8 and 12 requires valid pointer-relative accesses; the integer formula alone does not establish their validity.

The function does not require the calculated addresses to increase monotonically. Distinct indices can produce the same integer address: indices separated by 268,435,456 have identical products modulo 2³². If the count is large enough to reach both indices, the address calculation repeats. Whether those repeated integer values support valid accesses remains an environmental prerequisite.

### Index boundary

Index arithmetic and address arithmetic have different boundary behavior.

The largest possible count is 4,294,967,295. For that count, the last examined index on an unsuccessful search is 4,294,967,294. Its increment produces 4,294,967,295, and the following bound check returns 0.

Thus, ordinary loop termination does not require the index itself to wrap. Address multiplication and addition may nevertheless wrap much earlier.

### Successful result transfer

After a matching key is found, the function performs these data accesses in order:

1. Read the matched record’s 32-bit first result at offset 8.
2. Store that value through the first output destination.
3. Read the matched record’s 32-bit second result at offset 12.
4. Store that value through the second output destination.
5. Return 1.

The second result is not captured before the first output store. If that store modifies the second source, the subsequent read can observe the modification.

The function does not resume searching after either output store. A store that changes a record key therefore does not trigger a renewed comparison.

### Unsuccessful result

When the bound check ends the search, the function returns 0 without reading or writing through either output pointer.

For ordinary memory without independent external changes, both output locations retain their previous contents. Those retained contents are not newly produced results and do not indicate success.

## Side effects

The only explicit data writes are the two output stores after a match, in first-output then second-output order.

Important overlap consequences are:

- **Identical output destinations:** both stores target the same location. The second store determines its final value after normal completion.
- **First output equals the second result source:** the first store changes the value that the subsequent second-source read obtains in ordinary sequential memory.
- **An output overlaps a key:** record storage is modified, but no further searching occurs.
- **An output designates unrelated writable storage:** that storage is modified; the function does not restrict destinations to dedicated result buffers.
- **Partial overlap:** the exact resulting integer values depend on byte order and supported overlapping-access semantics. No platform-independent numeric result is established.

The body contains no rollback. If an earlier output store completes and a later access fails, there is no explicit operation that restores the earlier contents. Whether execution faults, terminates, or exhibits some other behavior is not established.

There are no explicit external calls, allocation operations, releases, global-variable accesses, logging operations, synchronization operations, or persistent bookkeeping. Supplied addresses can nevertheless designate globally visible storage, so the absence of named global accesses does not imply the absence of externally visible mutation.

No transactional, atomicity, or concurrency guarantee is established. The stated access order describes the supplied static body; it does not independently establish hardware transaction behavior, memory-mapped-device semantics, or a concurrent-memory contract.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless an example states otherwise, assume valid, ordinary, non-overlapping memory and successful accesses.

### Empty search

With a count of zero, the function returns 0 without accessing record storage or either output destination. Those addresses need not be dereferenceable for this path because no dereference occurs.

### First match and duplicate keys

If the first record matches and its result fields contain 20 and 30, separate output destinations receive 20 and 30, respectively, and the function returns 1.

If later records have the same key, their keys and result fields are not inspected.

### Later match

For three records with keys 4, 9, and 12, searching for 9 reads the first two keys, transfers the second record’s results, and returns 1. It does not read the third key or either result field of the first record.

### Negative key

A record key of −7 matches a search key of −7. No nonnegative-key restriction or sentinel interpretation is applied.

### No match

If all keys within the count differ from the search key, the function returns 0. Neither output destination is accessed, and neither receives an initialization value.

### Shared output destination

If the matched result fields contain 20 and 30 and both output pointers designate the same separate 32-bit location, that location receives 20 followed by 30. After normal completion it contains 30, and the function returns 1.

### First output aliases the second source

If the matched result fields initially contain 20 and 30, and the first output designates the second result field, the first store replaces 30 with 20. In ordinary sequential memory, the following second-source read obtains 20. A separate second output receives 20, and the function returns 1.

### Address addition wraps

Suppose the signed base is −16. Its unsigned contribution is 4,294,967,280. At index zero, the calculated integer address is 4,294,967,280; at index one, it is 0 because the addition reduces modulo 2³².

These integer results are required. Reaching index one additionally requires a count greater than one and a completed, nonmatching first-key access. Successfully reading the second key requires the integer value 0 to convert to a valid readable pointer in the relevant environment; that validity is not promised.

### Address multiplication wraps

At index 268,435,456, multiplying by 16 produces 0 modulo 2³². The calculated record-start integer value therefore equals the unsigned-converted base, just as at index zero.

This arithmetic is established. Reaching that index requires a sufficiently large count and successful, nonmatching earlier accesses. It does not establish that such a traversal can execute successfully.

### Invalid destination after a match

A matching key followed by an inaccessible output destination does not require return value 0. No validation or recovery branch is present. If the first output store completed before a later access failed, the body provides no rollback.

## Uncertainties

The following remain **documented_only**:

- The semantic meanings of the key and two result values.
- The full record type and purpose of the field at offset 4.
- The platform ABI, byte order, and alignment guarantees.
- The interpretation and validity of integer-to-pointer conversions, including wrapped address values.
- Whether the reached record and field accesses satisfy the environment’s object and memory-access rules.
- Fault behavior for inaccessible, misaligned, or otherwise invalid accesses.
- Caller guarantees about aliasing and storage lifetime.
- Concurrency and special-memory semantics.

The integer address calculation itself is not unresolved: its multiplication and addition reduce modulo 2³². What remains unresolved is whether the resulting pointer and subsequent accesses are valid.

The apparent intent is to retrieve two values associated with a key. That is an inference. The established contract is a bounded linear equality search followed by two ordered transfers.

## Evidence

The supplied static body establishes an unsigned index initialized to zero, an unsigned bound comparison before each record access, a 16-byte stride, and equality comparison against the record’s first 32-bit field.

Its operand types establish unsigned 32-bit multiplication and conversion of the signed base to unsigned before addition. Both address-calculation operations consequently reduce modulo 2³².

The successful path establishes immediate termination of the search at the first match, a read and output store from offset 8, a later read and output store from offset 12, and return value 1. The exhausted-search path establishes return value 0 without output access.
