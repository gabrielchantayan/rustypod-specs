# F-66f05038f9df

## Purpose

F-66f05038f9df conditionally loads a table of variable-length records from an associated input context into an associated state object. Each record contains a 16-bit element count and a pointer to an array of two-component, 32-bit values. Each component obtained from the input dependency is shifted left by two bits before storage.

The routine accepts the table only when the first header value equals `0x00010000` and the second header value matches a value reached through the state object. It exposes no return status. Some failures leave state modified, and one failure path performs partial rollback.

This description is based solely on the supplied static source representation. “Load,” “input,” “allocation,” and “release” describe inferred roles where the dependency implementations are unavailable; the observable calls and memory operations are distinguished below.

## Interface

### Invocation and result

The routine takes one argument: a reference to a caller-supplied object. The supplied representation uses 32-bit address-bearing values and offsets.

There is no explicit return value. The routine communicates through:

- Writes to the associated state object and constructed records.
- Calls to a caller-provided callback and six opaque dependencies.
- Changes those calls may make to input position, memory, or other state.

The routine does not propagate the callback’s status or either locally checked dependency status to its caller.

### Required object layout

The argument object supplies these fields:

| Offset | Width | Use |
|---|---:|---|
| `0x68` | 32 bits | Reference to an input/context object. |
| `0x1F8` | 32 bits | Callable reference for the initial callback. |
| `0x2A0` | 32 bits | Reference to the destination state object. |

The input/context object supplies:

| Offset | Width | Use |
|---|---:|---|
| `0x1C` | 32 bits | Context token passed to allocation-like and release-like dependencies. |

The destination state object supplies:

| Offset | Width | Use |
|---|---:|---|
| `0x08` | 32 bits | Reference to an object whose first 32-bit value is the expected record count. |
| `0x10` | 8 bits | Set to `1` before the initial callback. |
| `0x14` | 32 bits | Destination table reference, overwritten when the outer allocation-like call returns. |

The expected-count reference is dereferenced only when the first header value equals `0x00010000`.

### Constructed data layout

Each outer table record occupies eight bytes:

| Record offset | Width | Meaning |
|---|---:|---|
| `0x00` | 16 bits | Element count, taken from the low 16 bits of a reader result. |
| `0x02` | 16 bits | Not explicitly written by this routine. |
| `0x04` | 32 bits | Reference returned for the record’s element array. |

Each element also occupies eight bytes:

| Element offset | Width | Meaning |
|---|---:|---|
| `0x00` | 32 bits | First reader result shifted left by two bits. |
| `0x04` | 32 bits | Second reader result shifted left by two bits. |

The routine does not explicitly initialize the two-byte gap in each outer record. Any initialization performed by a dependency is unknown.

### Preconditions

Safe completion requires valid, appropriately accessible objects, callable references, and storage for every address actually read or written on the selected path. The routine contains no explicit null, alignment, capacity, or arithmetic-overflow checks.

A zero status from an allocation-like dependency is treated as permission to use its returned storage. Whether that dependency guarantees sufficient, aligned, non-null storage is outside the available evidence.

## Behavior

### 1. Capture context and mark state

The routine first reads, in order:

1. The input/context reference from the argument object.
2. The destination state reference from the argument object.
3. The context token from the input/context object.

These values are retained for later use. In particular, the context token is captured before the callback runs; later calls do not reload it from the input/context object.

The routine then writes the single byte `1` at destination offset `0x10`. This occurs before any callback result or header validation is known. No path explicitly restores the previous byte.

### 2. Invoke the initial callback

The callback reference is obtained from the argument object. The callback receives four arguments, in order:

1. The original argument object.
2. A fixed externally stored value whose contents and semantic role are unavailable.
3. The captured input/context reference.
4. A reference to a local 32-bit output slot.

The local output slot has no explicit initialization before this call.

If the callback returns a nonzero 32-bit status, the routine returns immediately. It does not call F-d036abe1e536 or F-9787e15c337d on that path.

If the callback returns zero, the routine calls F-d036abe1e536 with the captured input/context reference and the value in the callback’s output slot. Consequently, successful callback behavior must provide a usable output value, unless another unavailable contract establishes that the slot need not be initialized.

If F-d036abe1e536 returns nonzero, the routine returns immediately. F-9787e15c337d is not called on this failure path either.

### 3. Read and validate the header

After both preceding statuses are zero, the routine calls F-77339711215b twice, each time with the captured input/context reference.

The first result is the format discriminator. The second result is the proposed outer record count. Both results are held as 32-bit integer values.

Both calls occur even when the first result is not `0x00010000`.

Validation then proceeds as follows:

- If the discriminator differs from `0x00010000`, no table allocation is attempted.
- If it equals `0x00010000`, the routine reads the reference at destination offset `0x08`, then reads its first 32-bit value.
- Allocation is attempted only if that expected value equals the second header result.

Either validation failure leads to F-9787e15c337d with the captured input/context reference, followed by return.

The destination table field is not explicitly cleared or replaced on these validation failures. The byte at offset `0x10` has nevertheless already been set.

### 4. Request the outer table

For an accepted header, the routine calls F-6dd003795db7 with six arguments:

1. The captured context token.
2. `8`.
3. `0`.
4. The second header result.
5. `0`.
6. A reference to a local 32-bit status slot.

The status slot is zero at this point. The returned 32-bit address-bearing value is written to destination offset `0x14` before the status is examined.

If the status is nonzero:

- No record is populated.
- No explicit release of the returned value occurs.
- The destination field retains the returned value, subject to any later dependency side effects.
- F-9787e15c337d is called, then the routine returns.

There is no separate check of the returned reference. A zero status is sufficient to enter record processing.

### 5. Populate records

The routine processes records in increasing index order, starting at zero, while the signed index is less than the captured second header result.

For each record:

1. F-7efb5338f0fa is called with the captured input/context reference.
2. The low 16 bits of its result are stored as the record’s element count.
3. F-6dd003795db7 is called with the captured context token, `8`, `0`, that unsigned 16-bit count, `0`, and the local status reference.
4. The returned value is stored in the record’s pointer field.
5. The status is checked.

If the status is nonzero, element processing for that record does not begin; the partial-rollback behavior below applies.

If the status is zero, elements are processed in increasing index order. Each iteration:

- Calls F-7efb5338f0fa for the first component.
- Stores its two-bit-left-shifted result at element offset `0x00`.
- Calls F-7efb5338f0fa for the second component.
- Stores its two-bit-left-shifted result at element offset `0x04`.

Thus, the first component write precedes the second component read.

The element-loop bound is read from the current record’s 16-bit count field on each condition evaluation; it is not exclusively a saved copy of the original count. The element-array reference is also read from the record when performing component stores. Effects of unknown callees on these locations cannot be excluded.

After a record completes, the working outer-record address advances by eight bytes. Normal construction uses this working address, rather than reloading the destination table field for each record.

### 6. Partial rollback on an inner allocation status

If an inner F-6dd003795db7 call reports nonzero status, the current record already contains both its count and the returned pointer value.

The routine then visits only earlier records, in reverse index order. For each:

1. It reads the destination table reference from destination offset `0x14`.
2. It reads that earlier record’s pointer field.
3. It calls F-bf7242c98d06 with the captured context token and that pointer.
4. It reloads the destination table reference.
5. It writes zero to that earlier record’s pointer field.

After all earlier records have been visited, the routine:

1. Calls F-bf7242c98d06 with the captured context token and the current value of destination offset `0x14`.
2. Writes zero to destination offset `0x14`.
3. Calls F-9787e15c337d with the captured input/context reference.
4. Returns.

The current failing record’s pointer is not separately passed to F-bf7242c98d06. The routine therefore relies on an unavailable dependency contract if a failed inner request can return storage requiring separate release.

### 7. Normal completion

After all records complete, the routine calls F-9787e15c337d with the captured input/context reference and returns.

No successful-completion flag, record count, or result status is explicitly written beyond the described table contents and initial byte flag.

## Side effects

### Persistent state

The byte at destination offset `0x10` is always explicitly set to `1` once the initial object reads succeed. It is not evidence of successful loading: callback failure, preparation failure, header rejection, and allocation failure all occur after this write.

The destination table reference is overwritten only after an outer allocation-like call returns. Existing contents are not first released or preserved by this routine. Callers must not assume that invoking it safely replaces a previously owned table.

On successful construction, the table and its element arrays remain referenced from destination offset `0x14`. Their eventual owner and destruction protocol are not established.

### Input and dependency state

The routine invokes reader dependencies in a defined sequence but does not directly expose their errors. Any input advancement, byte order, bounds enforcement, buffering, or exception behavior belongs to their unknown contracts.

After F-d036abe1e536 succeeds, every explicit return path passes through F-9787e15c337d. Before that success, neither early-return path calls it.

This pairing suggests acquisition/preparation and finalization, but does not establish those meanings.

### Arithmetic and widths

The header count is used in a signed 32-bit loop comparison. No nonnegativity check precedes the outer allocation-like call. A negative accepted header count is passed to that dependency; if it reports zero status, the population loop performs no iterations.

Record counts are explicitly narrowed to 16 bits and subsequently treated as unsigned values from `0` through `65535`.

Component storage uses the full reader result as represented by a 32-bit integer, not an explicitly narrowed 16-bit value. The reader’s extension convention is unknown. The visible operation shifts left by two and stores 32 bits; no saturation or range validation is present. For values whose shift raises signedness or overflow questions, exact behavior requires the underlying execution semantics.

Record and element addressing uses eight-byte strides. There is no visible protection against address wraparound, excessive allocation sizes, or inconsistent storage supplied by dependencies.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, dependencies return normally and do not independently mutate the destination.

1. **Initial callback fails.**  
   Given a nonzero callback status, the destination byte is set to `1`; F-d036abe1e536, both header reads, table allocation, and F-9787e15c337d are not invoked.

2. **Preparation fails.**  
   Given a zero callback status followed by nonzero F-d036abe1e536 status, no header is read and F-9787e15c337d is not invoked.

3. **Unsupported discriminator.**  
   Given successful initial stages and a first header value other than `0x00010000`, both header reads still occur. The expected-count reference is not dereferenced, no table request occurs, and F-9787e15c337d is invoked.

4. **Count mismatch.**  
   Given the accepted discriminator but unequal second-header and expected-count values, the existing destination table field receives no explicit write. Finalization still occurs.

5. **One record with two elements.**  
   Given matching header count `1`, record count `2`, successful storage requests, and component results `1`, `2`, `3`, and `4`, the two stored pairs are `(4, 8)` and `(12, 16)`. The record’s count is `2`; its two-byte gap receives no explicit write.

6. **Zero elements in a record.**  
   A record count of zero still causes an inner F-6dd003795db7 call with count zero. With zero status, no component reader is called for that record.

7. **Outer request fails.**  
   Given nonzero outer-request status and returned value R, R is first stored at destination offset `0x14`. No explicit release or clearing follows; F-9787e15c337d is invoked.

8. **Third record’s request fails.**  
   Given successful first and second records and nonzero status for the third record’s inner request, rollback visits the second record, then the first, zeroing each pointer after its release-like call. It then releases the outer reference and clears the destination table field. The third record’s pointer is not separately released.

9. **Accepted negative header count.**  
   Given matching negative 32-bit count values, the negative value reaches the outer request. If that request reports zero status, no records are populated before finalization.

## Uncertainties

The following are **documented_only**:

- The object types and semantic meaning of the flag, expected-count object, callback selector, and context token.
- All dependency ownership, allocation, release, input-validation, and error contracts.
- Whether callback success guarantees initialization of its output slot.
- The reader’s sign-extension or zero-extension behavior for component values.
- Exact shifted results outside the range where signed arithmetic is unambiguous.
- Behavior after invalid memory access, nonreturning dependencies, or asynchronous mutation.
- Whether F-9787e15c337d changes the constructed state before return.
- Whether negative counts, preexisting tables, or nonzero failure references are valid inputs under a broader caller contract.

The inferred intent is to construct a count-validated table of scaled component pairs with rollback for inner allocation failure. That intent does not strengthen the explicit failure handling or establish missing dependency guarantees.
