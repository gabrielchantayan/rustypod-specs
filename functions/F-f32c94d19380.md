# F-f32c94d19380

## Purpose

F-f32c94d19380 obtains a new block address and incorporates it into a mutable state object containing two four-word records, an address-table field, and table-size metadata. A classification dependency selects initialization or extension. Extension either uses the next table slot or obtains a replacement table, copies a range of existing entries, and appends the new block address.

“Block,” “table,” “primary record,” and “secondary record” describe their use in this function. A segmented-container interpretation is plausible but is not an established interface guarantee.

The function delegates record construction to F-f1741872dc8d. Its return value packs the first two words of the temporary record left by the final call to that dependency.

This contract distinguishes direct operations from dependency behavior. Allocation, release, ownership transfer, and preservation of state by dependencies are not established.

## Interface

### Inputs

The function accepts four arguments:

1. The address of a mutable state object.
2. A 32-bit word.
3. A 32-bit word.
4. A 32-bit word.

Before any dependency call, it initializes a temporary four-word record:

| Word | Initial contents |
|---|---|
| First | State address converted to a 32-bit word |
| Second | Second argument |
| Third | Third argument |
| Fourth | Fourth argument |

The temporary record is subsequently passed by address to F-f1741872dc8d. Its contents are not reset between the two record-construction calls on the growth path.

The represented address-bearing values are 32 bits wide. Support for state or allocation addresses outside that representation is not established.

### State layout

Offsets below are byte offsets from the state address.

| Offset | Width | Established direct use |
|---|---:|---|
| 0 | 32 bits | Primary record’s first word; read as an address-bearing helper argument during growth |
| 4–11 | Two 32-bit words | Primary record contents; written and copied |
| 12 | 32 bits | Primary record’s fourth word; used as a table-slot address during growth |
| 16 | 32 bits | Secondary record’s first word; written, but never read by this function |
| 20–27 | Two 32-bit words | Secondary record contents; written |
| 28 | 32 bits | Secondary record’s fourth word; used as a table-slot address |
| 32–35 | 32 bits | Not directly accessed |
| 36 | 32 bits | Table-base address field |
| 40 | 32 bits | Table-size metadata |

The secondary record’s first word has no established address interpretation. Its placement in a similarly sized record does not establish the same semantics as the primary record’s first word.

Other record-word meanings remain unknown. Dependencies may access state beyond the fields directly accessed here.

### Result

The result is a 64-bit bitwise concatenation:

- Bits 0–31 contain the final temporary record’s first word.
- Bits 32–63 contain its second word.

No sign extension is applied to the low word. The third and fourth temporary words participate in state writes but not in return packing.

### Preconditions and representation

Normal completion requires readable and writable state, valid accessed table slots, and valid dependency-supplied addresses. There are no explicit checks for null addresses, allocation failure, inconsistent metadata, arithmetic overflow, or copy-range validity.

Size expressions and address-bearing calculations use represented 32-bit quantities. Unsigned shifts and masks have explicit bit-level meaning. Signed subtraction, signed shifts, and overflowing signed expressions require execution-model assumptions not supplied here.

The modulo-2³² identities described below establish equality of represented address offsets; they do not establish that the corresponding memory accesses are valid.

## Behavior

### Common preparation

Before classifying the state, the function:

1. Initializes the temporary record from the four arguments.
2. Calls F-a2ee2ea15a51.
3. Forms a size argument by shifting that result left by two bits.
4. Calls F-871e64ddc6de with that size argument and zero.
5. Retains the returned 32-bit address-bearing value as the new block address.
6. Calls F-83d59a117d49 with the state address.

Thus the new-block request precedes classification on every path. A classification result cannot avoid that request.

Only whether the classification result is zero matters. A nonzero result selects initialization; zero selects extension.

### Initialization

For nonzero classification:

1. Call F-a2ee2ea15a51 a second time.
2. Store its result in table-size metadata.
3. Call F-871e64ddc6de with this second result shifted left by two bits, followed by zero.
4. Store the returned address in the table-base field.
5. Reread the current size metadata, interpret it as unsigned, and take its logical half. Store the new block address at the returned table address plus four times that half.
6. Call F-a2ee2ea15a51 a third time.
7. Call F-f1741872dc8d with:
   - The temporary-record address.
   - The new block address plus four times the unsigned half of the third sizing result.
   - The current table-base field plus four times the unsigned half of the current size metadata.
8. Write the four temporary words into the primary record in increasing word order.
9. Copy the primary record into the secondary record in increasing word order.
10. Return the packed first two temporary words.

The three sizing results are distinct observations. The function does not require them to be equal.

The initial table-slot write uses the retained allocation result, not a fresh read of the table-base field. Its index uses metadata reread after the allocation dependency returns. The record helper’s arguments use state fields read after the third sizing call. These distinctions matter if dependencies mutate state.

The primary-to-secondary copy reads each corresponding primary word for its write. It is not a second direct copy from the temporary record.

### Extension decision

For zero classification, the function reads and retains the secondary slot address from offset 28. It compares that address with:

**table base + 4 × table-size metadata − 4**

Equality selects growth. Any inequality selects the existing-table path.

This is not a bounds check. An inconsistent address outside the table can still select the existing-table path.

The source establishes the comparison’s inputs, but not a separate externally observable order between field reads within the address expression.

### Existing-table path

When the retained secondary slot address differs from the calculated final slot:

1. Add four bytes to that retained address.
2. Store the advanced address in the secondary record’s fourth word.
3. Store the new block address at the advanced address.
4. Call F-f1741872dc8d with the temporary-record address, the new block address, and the current secondary record’s fourth word.
5. Write all four temporary words into the secondary record in increasing word order.
6. Return the packed first two temporary words.

The helper receives the block base, with no interior offset.

The advanced secondary slot field is published before the table-slot write and before the helper call. The helper-produced fourth word subsequently replaces that field and need not equal the advanced address.

There are no direct writes to the primary record, table-base field, or size metadata on this path. That does not guarantee those fields remain unchanged: dependencies and overlapping storage can affect them.

### Growth calculations

When the retained secondary slot address equals the calculated final slot, the function derives:

- **Distance:** the represented subtraction of the current primary slot address from the retained secondary slot address, followed by a signed right shift of two bits.
- **Count:** distance plus one, represented as an unsigned 32-bit value.
- **Copy offset:** twice count, with the lowest two bits cleared in the 32-bit result.

For a valid, aligned, nonnegative address difference without problematic signed arithmetic, distance counts four-byte intervals and count counts the inclusive occupied slots.

The replacement-table request uses **8 × count** as its size argument, with zero as its second argument.

The following identity holds for every 32-bit count under modulo-2³² arithmetic:

**copy offset = 4 × logical-half(count with its highest bit cleared), modulo 2³²**

This identity includes counts whose highest bit is set. It does not depend on treating count as an ordinary small positive integer.

### Copying and replacing the table

After obtaining the replacement address, the function:

1. Rereads the secondary slot address and captures an endpoint four bytes beyond it.
2. Rereads the primary slot address as the copy start.
3. Copies successive 32-bit words into the replacement allocation beginning at the copy offset.
4. Calls F-ff1bdc376dcd with the current table-base field, current size metadata, and zero.
5. Stores the retained replacement address in the table-base field.
6. Stores the new block address in the calculated appended slot.
7. Rebuilds and writes the primary record.
8. Rebuilds and writes the secondary record.
9. Stores twice count in table-size metadata.
10. Returns the packed first two words of the final temporary record.

The copy is a forward, word-at-a-time operation. Each iteration reads one source word and writes one destination word before advancing both positions by four bytes. The endpoint comparison precedes each iteration; if the initial source address equals the endpoint, no words are copied.

The copy start and endpoint are read after the allocation dependency returns. Distance and count were calculated before it. A dependency mutation can therefore make the copied range differ from the range implied by count.

No range validation is performed. Overlapping source and destination storage is not protected by a snapshot or overlap-aware copy. If repeated four-byte advances cannot safely reach the endpoint, safe completion is not established.

### Appended slot and record reconstruction

The appended-slot write uses the retained replacement address plus:

**4 × [distance + logical-half(count with its highest bit cleared)] + 4**

The primary-record helper receives:

- The temporary-record address.
- The current primary record’s first word.
- The current table-base field plus the copy offset.

After that helper returns, the function writes the four temporary words into the primary record in increasing word order.

The secondary-record helper then receives:

- The same temporary-record address, retaining changes from the first helper call.
- The new block address.
- The current table-base field plus the copy offset, plus 4 × distance, plus 4.

After that helper returns, the function writes the four temporary words into the secondary record in increasing word order, then publishes twice count as the new size metadata.

For the same replacement base, the appended-slot address and the secondary helper’s slot argument coincide in represented 32-bit arithmetic, including when count’s highest bit is set. Their apparent difference in offset construction does not create a high-bit exception.

Their actual bases can differ: the appended-slot write uses the retained allocation result, while the secondary helper’s argument rereads the table-base field after the primary helper call and primary-record writes. No preservation of that field by the helper is established.

## Side effects

Direct effects include:

- One new-block request before classification.
- An additional table request on initialization or growth.
- A call concerning the previous table on growth.
- Table-slot writes.
- Writes to one or both records.
- Table-base and size-metadata writes on initialization and growth.

No direct initialization of the new block’s contents is shown. No direct operation explicitly releases that block, and there is no rollback path.

Ownership cannot be assigned from these calls alone. In particular, F-ff1bdc376dcd is not established to release storage, and F-871e64ddc6de is not established to transfer ownership.

Publication is nontransactional:

- Initialization publishes size metadata before requesting the table.
- Existing-table extension publishes an advanced secondary slot before constructing its replacement record.
- Growth copies before calling the old-table dependency.
- Growth publishes the replacement base before either record-construction call.
- Growth publishes new size metadata only after both record updates.

Consequently, absent dependency mutations, growth helpers can observe the replacement base together with the previous size metadata. No synchronization, atomicity, or reentrancy protection is shown.

There is no explicit error result or recovery branch. A zero returned address is used without a dedicated failure check. Exceptions, nonreturning dependencies, and cleanup on dependency failure remain unspecified.

## Acceptance examples

These are conditional static expectations, not runtime observations. Unless stated otherwise, assume valid aligned nonoverlapping storage, representable ordinary arithmetic, and dependencies that preserve state except for specified temporary-record updates.

### Initialization with independent sizing results

Suppose the three sizing calls return 8, 6, and 10, and classification is nonzero.

Expected:

- New-block request size: 32.
- Table request size: 24.
- Size metadata: 6.
- New block address stored at table base plus 12.
- Record-helper address arguments: new block base plus 20, and table base plus 12.
- Primary record written from the helper result, then copied into the secondary record.

Using one cached sizing result for all three purposes would not satisfy this behavior.

### Existing table with a following slot

Suppose table base is 4096, size metadata is 4, and the secondary slot address is 4100.

The calculated final slot is 4108, so growth is not selected.

Expected:

- Secondary slot field first becomes 4104.
- New block address is stored at 4104.
- The helper receives the block base and slot address 4104.
- The helper-produced record replaces the secondary record.
- No direct primary-record write occurs.

The secondary record’s first word remains semantically unknown even though the helper supplies its stored value.

### Growth with three occupied slots

Suppose table base and primary slot address are 4096, size metadata is 3, and secondary slot address is 4104.

Expected:

- Distance: 2; count: 3.
- Replacement request size: 24.
- Copy offset: 4.
- Old slot words copied to replacement offsets 4, 8, and 12.
- New block address stored at replacement offset 16.
- Primary helper slot argument: replacement base plus 4.
- Secondary helper slot argument: replacement base plus 16.
- Size metadata becomes 6 only after both record updates.

### High-bit offset identity

For a represented count of hexadecimal 80000003, twice count modulo 2³² is 6, so clearing its lowest two bits yields a copy offset of 4. Clearing count’s highest bit first gives 3; its logical half is 1, and multiplying by four also gives 4.

Thus high-bit-set count alone does not separate the two slot-offset formulas. This arithmetic example does not establish a valid corresponding copy range or memory execution.

### Table-base mutation during reconstruction

Suppose growth retains replacement base R, but the primary record helper changes the table-base field to S.

The appended block has already been written using R. The subsequent secondary helper uses S in its slot argument. Equality of the offset formulas does not make those actual addresses equal.

### Return packing

If the final temporary record begins with hexadecimal words 89ABCDEF and 01234567, the returned value is hexadecimal 0123456789ABCDEF, without sign extension from the first word.
