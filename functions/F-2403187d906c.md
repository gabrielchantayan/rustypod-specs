# F-2403187d906c

## Purpose

F-2403187d906c repeatedly invokes a processing dependency on a caller-supplied object until either:

- A previously obtained unsigned bound is less than or equal to the object’s current unsigned progress field; or
- A conditionally evaluated elapsed-value comparison exceeds a nonzero caller-supplied limit.

This is an operational description, not a claim about the object’s domain. The supplied representation supports a progress-oriented loop and a timeout-like calculation. It does not establish that the quantities are counts, milliseconds, or any particular kind of timestamp.

The function has no explicit return value. It does not distinguish its two normal exit conditions through a returned status.

## Interface

### Inputs

The recovered interface has four inputs:

| Input | Recovered width and interpretation | Use |
|---|---|---|
| Object address | 32-bit address-bearing integer | Identifies storage read directly and passed to dependencies. |
| Limit | Unsigned 32-bit integer | Compared against an unsigned interpretation of a calculated difference. Zero disables that exit condition, but does not suppress the calculation. |
| Initial first value | Signed 32-bit integer | Copied into local storage that is subsequently exposed to a dependency and used as an arithmetic input. |
| Initial second value | Opaque 32-bit value | Copied into separate local storage, exposed to a dependency before object preparation, and later used as an arithmetic input. |

The address-bearing interpretation follows from pointer-style operations in the supplied representation. An independently verified calling convention is not available.

### Object layout used directly

Only these relative locations are established:

| Byte offset from object address | Direct use |
|---|---|
| `+4` | Read as an unsigned 32-bit progress value. |
| `+12` | Its address is passed to F-3952b8ae1dfd. The contents and extent of that subobject are unknown. |

The function also passes the base object address to F-875e056ead2c and F-939fc1469d10. Those dependencies may use additional fields; their layouts are not established here.

The function performs no explicit null, bounds, lifetime, or alignment checks. Valid readable storage for the direct field reads, and storage satisfying all dependency preconditions, are caller obligations. No clean failure behavior is established for invalid addresses.

### Outputs and ownership

There is no explicit result value, output buffer, or returned ownership.

Two local 32-bit values are initialized from the third and fourth inputs. Their addresses are passed to dependencies at different points. These are addresses of local storage, not caller-provided output parameters. The dependency contracts are unavailable, so pointer retention, access extent, and ownership behavior must not be invented. In particular, this function alone does not establish whether either dependency retains a supplied address.

The body contains no explicit allocation, release, or ownership transfer.

## Behavior

### Initialization and bound acquisition

The following sequence precedes all loop termination checks:

1. Copy the initial first value into one local 32-bit slot.
2. Copy the initial second value into another local 32-bit slot.
3. Invoke F-c082dad756a2 with the address of the second slot.
4. Invoke F-875e056ead2c with the object address.
5. Invoke F-3952b8ae1dfd with the address at object offset `+12`.
6. Retain the returned value as an unsigned 32-bit bound.

Thus, even an execution that exits at its first progress check has already invoked those three dependencies in that order.

The bound is obtained once. This function does not call F-3952b8ae1dfd again to refresh it, including after processing changes the object. Whether a dependency or an exceptional memory effect can affect local state is outside the supplied dependency contracts.

### Progress check

At the beginning of every iteration, the function reads the unsigned 32-bit field at object offset `+4`.

If the retained bound is less than or equal to that field, the function returns immediately. Equality is sufficient. The comparison is unsigned, so values whose high bit is set are not treated as negative.

On this exit path, the current iteration does not invoke:

- The arithmetic dependency;
- The local-value refresh dependency; or
- The processing dependency.

If the bound is greater than the progress field, execution continues.

### Conditional arithmetic path

After a failed progress check, the function reads the object’s `+4` field again and invokes F-d7be9cfb4000 with:

- That newly read field value; and
- The integer constant `10`.

The second read is distinct from the read used for the progress comparison. The function does not explicitly retain and reuse the earlier field value. If the object changes between reads, the dependency can therefore receive a different value.

The decision that follows uses an auxiliary result associated with this invocation:

- If the auxiliary result is nonzero, the elapsed-value calculation is skipped.
- If it is zero, the elapsed-value calculation is performed.

The supplied representation exposes this auxiliary value separately from the dependency’s primary result. Its exact ABI meaning is unresolved. Although the call shape is compatible with quotient/remainder arithmetic, the available evidence does not justify specifying either division or a “multiple of ten” condition as established behavior.

The primary result of this first arithmetic invocation is not otherwise used by this function.

### Elapsed-value calculation and limit check

When the auxiliary result is zero, the function performs these operations in order:

1. Invoke F-4085480a3d85 with the address of the local first-value slot.
2. Invoke F-d7be9cfb4000 with the current first-slot value and the integer constant `1000`. Retain its primary result.
3. Invoke F-d7be9cfb4000 with the current second-slot value and the integer constant `1000`.
4. Overwrite the first local slot with the primary result of the second `1000` invocation.
5. Subtract that second result from the retained first result.
6. Interpret the difference as unsigned for comparison with the unsigned limit.
7. Return if the limit is strictly less than that unsigned difference and the limit is nonzero.

The two arithmetic invocations are ordered. The second slot is read for its arithmetic call after the first arithmetic call has completed. Unknown dependency side effects must not be replaced with an assumption that all other memory remains unchanged.

The local overwrite in step 4 is significant: the first slot does not retain the first conversion result. Its value becomes the result derived from the second slot before subtraction and the possible return.

The comparison is strict. A difference equal to the limit does not cause this exit.

A zero limit disables this exit condition, but only after entry into the elapsed-value path. It does not prevent the refresh call, either `1000` arithmetic call, the local overwrite, or calculation of the comparison operand.

### Arithmetic boundaries

The representation uses 32-bit signed values for the two primary results in the elapsed-value path and explicitly treats their difference as unsigned for the limit comparison.

For differences representable as signed 32-bit values, the comparison behavior is established. For example, a mathematical difference of `-1` becomes unsigned `4,294,967,295`, rather than being treated as an expired interval of zero or as an error.

The behavior when the signed subtraction itself overflows is not independently established. A machine-level wrapping result may be intended, but the supplied representation is insufficient to promote that interpretation into an unconditional contract.

The constants `10` and `1000` are established operands. Their units and arithmetic meanings depend on F-d7be9cfb4000 and remain unknown.

### Processing and repetition

If neither exit condition applies, the function invokes F-939fc1469d10 with the object address.

It then begins the next iteration with a fresh unsigned read of the `+4` field.

The processing dependency is invoked whether:

- The auxiliary arithmetic result was nonzero and the elapsed-value path was skipped; or
- The elapsed-value path ran but its exit condition was false.

There is no explicit sleep, retry bound, cancellation check, or error-status inspection. Termination requires a qualifying progress-field observation or a qualifying elapsed-value result. Neither is guaranteed by this body.

## Side effects

### Directly established effects

The function:

- Initializes two local 32-bit slots;
- Exposes their addresses to dependencies at different times;
- Overwrites the first slot during every elapsed-value calculation;
- Reads the object’s `+4` field once for each progress check;
- Reads that field a second time on each iteration that passes the progress check; and
- Calls dependencies in the order specified above.

There are no explicit writes to the object’s fields in the supplied body.

### Dependency-mediated effects

The absence of direct object writes does not make the operation read-only. The base object address and a subobject address are passed to dependencies, and two dependencies receive addresses of local storage.

The dependencies may have object, global, external-resource, or synchronization effects not described here. This contract does not assume they preserve globals, release memory, retain no pointers, or return normally.

The ordering above describes the represented reads and calls. It is not a concurrency guarantee. Atomicity, volatile access semantics, memory barriers, and safety under concurrent mutation are not established.

## Acceptance examples

These are conditional static acceptance cases, not runtime observations. They assume dependencies return normally and produce the stated values.

### Immediate completion after setup

If F-3952b8ae1dfd returns `8` and the first progress read is `8`, the function returns after the initialization, preparation, and bound-acquisition calls.

No arithmetic, refresh, or processing call occurs. The same result follows if that first progress read is `9`.

### Unsigned progress ordering

If the bound is `2,147,483,648` and the progress field is `2,147,483,647`, the function does not exit at the progress check.

A signed comparison would produce a different result and would not satisfy this contract.

### Nonzero gate result

If the bound exceeds the observed progress field and the arithmetic gate’s auxiliary result is nonzero, the function skips the refresh and both `1000` arithmetic calls. It invokes F-939fc1469d10 and repeats.

This remains true even if the nonzero limit would otherwise be small enough to trigger an elapsed-value exit.

### Limit equality

Suppose the gate result is zero, the two elapsed-value arithmetic results are `107` and `100`, and the limit is `7`.

The difference is `7`. Because the comparison is strict, processing occurs rather than returning through the limit condition.

With the same arithmetic results and a limit of `6`, the function returns before processing.

### Zero limit

Suppose the gate result is zero and the limit is `0`.

The refresh call and both `1000` arithmetic calls still occur. The local first slot is still overwritten. The limit condition does not return, regardless of the resulting unsigned difference, provided execution of the arithmetic itself has defined behavior.

### Negative representable difference

Suppose the two elapsed-value arithmetic results are `99` and `100`, and the limit is `1`.

The signed difference is `-1`, which becomes unsigned `4,294,967,295` for comparison. The function returns before processing.

This case does not require signed-subtraction overflow.

### Progress achieved by processing

Suppose the bound is `3`, the first progress check observes `2`, the gate permits processing without a limit exit, and F-939fc1469d10 changes the progress field to `3`.

The next progress check returns. No further arithmetic gate call occurs.

- Whether that dependency performs division, remainder calculation, scaling, or another operation.
- The units, representation, and temporal meaning of either local value.
- The signed-overflow behavior of the elapsed-value subtraction.
- The complete object and subobject layouts.
- Dependency memory-access extents, pointer retention, ownership rules, global effects, and failure modes.
- Whether processing changes the progress field, and whether progress is monotonic.
- Whether termination is guaranteed for any general class of inputs.
- Concurrent-access safety and the machine-level observability of the represented reads.

Inferred intent is limited to a repeated progress operation with a conditionally checked timeout-like bound. That interpretation must not replace the established call order, unsigned comparisons, strict limit condition, or unresolved arithmetic semantics.
