# F-222f1190a568

## Purpose

F-222f1190a568 obtains a node, copies an eight-byte value into it, attaches it to a caller-selected location in a linked tree, performs color-based repair, and returns the new node through an output slot.

The visible links and repair cases are consistent with insertion into a red–black tree whose header also tracks the root and two extrema. That interpretation is inferred intent. The established behavior is the specific attachment, byte writes, pointer accesses, and dependency calls described below. Successful balancing, ordering, allocation, and node initialization depend on contracts not supplied here.

This operation is not a general search-and-insert interface. It receives an attachment node and a flag that can force one attachment direction. It performs at most one visible comparison and contains no duplicate-rejection path.

## Interface

The operation has five inputs and no visible scalar return value.

| Input | Role | Required accessible storage |
|---|---|---|
| Result slot | Receives the acquired node address at completion | One writable 32-bit slot |
| Container address | Supplies header, count, and dependency context | Fields described below |
| Attachment flag | A 32-bit value tested for zero versus nonzero | Passed by value |
| Attachment node | Header or ordinary node used as the insertion location | Link fields, and conditionally payload |
| Source value | Supplies the new payload and, conditionally, a comparison operand | Two readable consecutive 32-bit words |

The supplied representation uses 32-bit address-bearing fields and 32-bit integer operations. The color/status field is one byte. Signedness is not relevant to the attachment flag: every nonzero bit pattern follows the same branch.

### Container layout

Offsets are relative to the container address.

| Offset | Width | Visible use |
|---|---:|---|
| `+0x10` | 4 bytes | Address of the tree header |
| `+0x14` | 4 bytes | Count read, incremented by one, and written back |
| `+0x19` | Address only | Context address supplied to the comparison dependency |

No read or write of the byte at `+0x19` is directly visible in this operation. A dependency receives that address and may access storage reachable from it.

### Header and node layout

The same link offsets are used with different roles:

| Offset | Width | Ordinary-node interpretation | Header interpretation |
|---|---:|---|---|
| `+0x00` | 1 byte | Color/status | Not directly used as a header color |
| `+0x04` | 4 bytes | Parent | Root |
| `+0x08` | 4 bytes | Left child | Leftmost node |
| `+0x0c` | 4 bytes | Right child | Rightmost node |
| `+0x10` | 4 bytes | First payload word | No payload use established |
| `+0x14` | 4 bytes | Second payload word | No payload use established |

The extrema names are inferred from the update pattern. The offsets and update conditions are established.

During repair, byte value zero selects the red-like case. A nonzero byte selects the black-like case. When this operation explicitly assigns those states, it writes exactly zero or one.

### Preconditions and ownership

The caller must provide valid, suitably accessible addresses for every path actually taken. There is no visible input validation, alignment repair, cycle detection, or structural consistency check.

The acquired node must support link and color accesses. Its initial child links and color are not initialized by the visible body before use. Any required initial state must therefore come from F-1b3469a98d5f or an external invariant.

The source value is copied as two 32-bit words; its address is not visibly retained in the node. The function neither releases the source storage nor establishes ownership of resources represented by those words.

The acquired node becomes linked into the container and is returned by address. No release operation is visible. Allocation policy, ownership transfer, failure behavior, and later destruction remain dependent on external contracts.

## Behavior

### Acquisition and payload transfer

The first visible action is a call to F-1b3469a98d5f with the container address. Its returned address is treated as the new node.

The operation then tests whether the address sixteen bytes beyond that node is nonzero. If it is nonzero:

1. The first source word is read and written at node offset `+0x10`.
2. The second source word is read and written at node offset `+0x14`.

These are ordered word transfers, not an established atomic eight-byte copy. In particular, the first destination write precedes the second source-word read. Overlapping storage can therefore affect the transferred value.

This condition is not a conventional check that the node itself is nonnull. A null node address does not, by itself, suppress the payload writes. If the tested address is zero, both payload transfers are skipped, but subsequent insertion continues.

Next, the current count at container offset `+0x14` is read, incremented by one, and written back. This precedes comparison, structural attachment, and repair. No capacity or overflow check is visible.

### Choosing the attachment side

The header address is read from container offset `+0x10`.

A left-side attachment is selected without comparison if either:

- The attachment node equals the currently loaded header; or
- The attachment flag is nonzero.

Otherwise, F-bcefa5957e76 is called with:

1. The container address plus `0x19`;
2. The source-value address;
3. The attachment-node address plus `0x10`.

A nonzero result selects left-side attachment. Zero selects right-side attachment. No particular comparison ordering, key type, equality semantics, or strict-order property is established by this body.

The payload copy and count increment have already occurred when this comparison is called. The comparison receives the original source address, not the copied node payload.

### Left-side attachment

The new node address is first written to the attachment node at `+0x08`.

The header address is then reloaded. If it equals the attachment node:

1. The new node is written to the header’s `+0x04` root field.
2. The header address is reloaded again.
3. The new node is written to that header’s `+0x0c` field.

In this case, the initial `+0x08` attachment write also sets the header’s leftmost field, provided the attachment node and subsequently used header are the same object.

If the reloaded header differs from the attachment node, its `+0x08` field is inspected. That field is replaced with the new node address only if its previous value equals the attachment node.

Thus an ordinary left attachment updates the tracked leftmost node conditionally, rather than unconditionally.

### Right-side attachment

The new node address is first written to the attachment node at `+0x0c`.

The header address is then reloaded. Its `+0x0c` field is inspected and replaced with the new node address only if the previous value equals the attachment node.

Thus an ordinary right attachment conditionally updates the tracked rightmost node.

### Parent assignment and repair

After attachment and any extrema update, the attachment-node address is written into the new node’s parent field at `+0x04`.

The repair cursor initially designates the new node. At each loop condition, the operation reloads the header address and its root field. Repair stops if that root equals the cursor.

Otherwise, the cursor’s parent is loaded and its color byte examined. A nonzero parent byte stops repair. A zero parent byte causes the grandparent and neighboring child links to be examined.

#### Parent is the grandparent’s left child

The uncle is taken from the grandparent’s right-child field.

If the uncle exists and its color byte is zero:

1. The parent’s byte is set to one.
2. The uncle’s byte is set to one.
3. The grandparent reached again through the cursor’s parent chain is set to zero.
4. The cursor moves to the grandparent reached through that chain.

The loop then repeats.

If the uncle is absent or has a nonzero color byte:

- When the cursor is the parent’s right child, F-7265777c1e19 is called with the container and parent. The cursor is then changed to the previously held parent address.
- The parent reached through the current cursor is set to one.
- The grandparent reached through the current cursor is set to zero.
- F-726c5ad3d4e0 is called with the container and the grandparent reached through the current cursor.

Links used after a dependency call are reread. The operation does not visibly preserve a complete ancestry snapshot across that call.

#### Parent is not the grandparent’s left child

The would-be uncle is the grandparent’s left-child link. The function does not separately verify that the parent is the grandparent’s right child.

If that uncle exists and its color byte is zero, the same three color writes and cursor promotion described above occur.

Otherwise:

- When the cursor is the parent’s left child, F-726c5ad3d4e0 is called on the parent, with additional supplied values discussed under Dependencies. The cursor then changes to the previously held parent address.
- The parent reached through the cursor is set to one.
- The grandparent reached through the cursor is set to zero.
- F-7265777c1e19 is called with the container and the grandparent reached through the cursor.

The repair structure is consistent with mirrored rotation cases. The actual transformations remain dependency behavior.

### Completion

After the repair loop ends:

1. The header address and its root link are reloaded.
2. The byte at that root address is set to one.
3. The originally acquired node address is written to the result slot.

The returned address is the new node, not the final repair cursor or necessarily the final root.

No status code distinguishes attachment direction, comparison outcome, duplicate values, or repair cases.

## Side effects

Established direct mutations include:

- Up to two payload-word writes to the acquired node;
- One increment of the container count;
- One attachment-link write;
- Conditional root and extrema writes;
- One parent-link write to the new node;
- Zero or more repair color writes;
- One final root-byte write;
- One final result-slot write.

Dependencies may introduce additional effects. Their memory ownership, global effects, allocation behavior, and failure modes are not established.

The operation is not visibly transactional. Count and payload changes precede comparison and repair. There is no visible rollback path if a dependency fails to return normally or an access fails.

No synchronization is visible. Correct use with concurrent readers or writers requires an external contract.

Aliasing restrictions are not stated. Because writes are interleaved with later reads, aliasing among the result slot, source value, container, header, attachment node, and acquired node can change behavior. In particular, the final result-slot write occurs after the final root-color write and can overwrite tree storage if the slot aliases it.

## Acceptance examples

These examples are conditional static acceptance cases, not executed tests.

1. **Insertion through the header.**  
   Assume a stable header, a valid initialized new node, nonaliasing storage, and normal dependency completion. If the attachment node is the header, no comparison occurs. The header’s leftmost, root, and rightmost fields become the new node address. The node’s parent becomes the header. The repair loop immediately recognizes the new root, the root byte becomes one, and the result slot receives the new node.

2. **Forced left attachment.**  
   With a non-header attachment node and any nonzero flag, no comparison occurs. Its left-child field is replaced. The header’s leftmost field changes only if it previously designated that attachment node. No check rejects an already occupied child field.

3. **Comparison-selected right attachment.**  
   With a zero flag, a non-header attachment node, and a zero comparison result, the right-child field receives the new node. The rightmost field changes only if it previously designated the attachment node.

4. **Noncanonical nonzero parent color.**  
   If the new node is not the root and its parent byte is two, repair stops at the parent-color check just as it would for byte one. The final root byte is nevertheless written as exactly one.

5. **Red-like uncle propagation.**  
   With a zero-colored parent and a present zero-colored uncle, both receive one and the grandparent receives zero. Repair continues from the grandparent. There is no rotation dependency call for that particular iteration.

6. **Comparison failure after preliminary mutation.**  
   If the comparison dependency does not return normally, the payload transfer and count increment have already happened. This body provides no rollback or final result-slot write for that interrupted execution.

7. **Equal values.**  
   No equality-specific rejection exists. If the comparison reports zero for equal payloads, the selected path is right attachment, subject to the same structural preconditions as any other zero result.
