# F-062e6c77d9d0

## Purpose

F-062e6c77d9d0 finds or appends a three-word record using a normalized pair of signed inputs, then submits the selected record’s index to a dependent operation.

The record lookup uses only the first two words. The third word is initialized when a record is appended but is neither compared nor updated when an existing record matches.

The function has no explicit return value. An optional output word reports the selected index only after two dependent operations both report success. Otherwise, that word remains at its initial sentinel value, subject to aliasing and effects of dependencies.

**Established behavior:** lookup, conditional append, and downstream submission are distinct stages. An appended record is not rolled back when a later stage reports failure.

**Inferred intent:** the table appears to intern normalized pairs and associate their indices with another object. This interpretation does not establish the meaning of the pair, the mode word, or the dependent operations.

## Interface

### Arguments

The interface has five arguments:

| Argument | Contract |
|---|---|
| Table reference | Writable reference to a structure containing a record count, capacity, record-storage address, and an embedded object beginning immediately afterward. |
| First input | Signed 32-bit value used to derive the first lookup key. |
| Second input | Signed 32-bit value used to derive the second lookup key and, for new records, a mode word. |
| Context | Opaque 32-bit value forwarded to dependencies. Its interpretation and ownership are not established. |
| Optional index output | Either null or a writable reference to one unsigned 32-bit word. |

The function returns no value. Dependency failures are not returned directly to the caller.

### Table and record layout

The supplied representation uses 32-bit words and 12-byte records.

| Byte offset from table reference | Width | Meaning |
|---|---:|---|
| 0 | 4 bytes | Unsigned record count |
| 4 | 4 bytes | Unsigned record capacity |
| 8 | 4 bytes | Address of record storage |
| 12 | Unknown extent | Embedded object passed by reference to F-c2a5aac558d4 |

Each record contains:

| Byte offset within record | Width | Meaning |
|---|---:|---|
| 0 | 4 bytes | First signed lookup key |
| 4 | 4 bytes | Second signed lookup key |
| 8 | 4 bytes | Mode word |

The embedded object’s size, alignment beyond its observed address, and internal layout are unknown.

### Preconditions and validity boundaries

There are no explicit checks for a null table reference, inaccessible storage, corrupted counts, arithmetic overflow, or a malformed embedded object.

For ordinary, non-overlapping use:

- The table header must be readable and writable as described.
- Every record examined during lookup must be readable.
- A destination record used without successful storage replacement must already be writable.
- A non-null index output must be writable.
- The embedded object must meet F-c2a5aac558d4’s requirements.
- Dependencies must provide any validity guarantees necessary for subsequent accesses.

These are memory-safety requirements, not validations performed by this function.

No explicit non-aliasing checks exist. If the index output overlaps the table, record storage, or another relevant object, its sentinel write can alter subsequent behavior. The ordinary acceptance examples below assume such overlap is absent.

## Behavior

### 1. Normalize the lookup inputs

The function derives two lookup keys and a prospective mode:

| Condition on second input | First key | Second key | Mode for a new record |
|---|---|---|---:|
| Nonnegative | First input | Second input | 0 |
| Negative, other than −21 | First input | 0 | 1 |
| Exactly −21 | First input minus 21 | 0 | 3 |

This normalization takes place before the optional output initialization.

All ordinary negative second inputs therefore share a normalized second key of zero. The distinguished value −21 also changes the first key.

For the distinguished case, the recovered operation is signed 32-bit subtraction by 21. The supplied evidence does not independently establish the execution environment’s treatment of signed overflow. Inputs whose mathematical subtraction falls outside the signed 32-bit range require the arithmetic qualification in **Uncertainties**.

### 2. Initialize the optional output

If an index-output reference is present, the function writes `0xffffffff` to it.

This happens before reading the table’s count and record-storage address. Consequently, an overlapping output reference can affect the table state used for lookup.

The sentinel is an unsigned 32-bit value. It is not a returned dependency error code.

### 3. Search existing records

After the sentinel write, the function reads the table count and record-storage address. It searches records in ascending index order, beginning at zero and stopping before the captured count.

For each examined record:

1. It reads the first key.
2. Only if that key matches does it read and compare the second key.
3. It stops at the first pair match.
4. Otherwise, it advances by 12 bytes.

The mode word is not read for matching.

The search count is the value captured at the start of this stage. The search does not repeatedly reload the count or storage address between records.

On a match:

- The selected index is the first matching record’s index.
- No append or capacity adjustment occurs.
- This function performs no explicit record write.
- The record’s existing mode is preserved, even if it differs from the mode implied by the current inputs.

Execution then proceeds to downstream submission.

### 4. Append when no record matches

For a miss, the selected index is the captured old count. The requested new count is the old count plus one, using unsigned 32-bit arithmetic.

The function then reads the capacity and distinguishes three cases.

#### Requested count is below capacity

No storage dependency is called. The function proceeds directly to initialize the new record in existing storage.

#### Requested count equals capacity

No storage dependency is called. Equality is accepted as sufficient capacity, and the new record is initialized in existing storage.

This equality case differs in internal control flow from the below-capacity case but has the same ordinary append result.

#### Requested count exceeds capacity

The function computes a requested capacity by adding eight to the old count as an unsigned 32-bit quantity and clearing the low three bits.

For counts that do not wrap, this produces the next multiple of eight strictly greater than the old count. Examples include an old count of zero producing eight and an old count of eight producing sixteen.

The function initializes a local status word to zero, then calls F-6dd003795db7 with:

- The context.
- An element size of 12 bytes.
- The previously read capacity.
- The computed requested capacity.
- The table’s record-storage address read for this call.
- A writable reference to the status word.

On return, the function unconditionally stores the dependency’s returned 32-bit value into the table’s record-storage-address field.

Only after that store does it inspect the status word:

- If the status is zero, it stores the requested capacity into the table’s capacity field and proceeds with the append.
- If the status is nonzero, it returns immediately.

Thus, failure does not preserve the original storage-address field: the returned value is stored even on reported failure. The function does not restore the previous address.

The dependency is responsible for any storage semantics associated with its result. This function does not itself copy or release the old allocation.

### 5. Initialize and publish the appended record

On an append path that proceeds, the function obtains the destination from the table’s then-current storage address and the requested new count.

For ordinary non-overflowing counts, this is the record at the old count. The observable explicit writes occur in this order:

1. Write zero to the destination’s first word.
2. Write zero to its second word.
3. Write zero to its third word.
4. Store the requested new count in the table’s count field.
5. Write the normalized first key.
6. Write the normalized second key.
7. Write the derived mode.

The count is therefore updated after zero-initialization but before the final keys and mode are written.

No dependency call occurs between these writes. The function nevertheless contains no synchronization or atomic-publication mechanism; it does not establish a concurrent-reader contract.

### 6. Submit the selected index

After either finding or appending a record, the function calls F-c2a5aac558d4 with:

- A reference to the embedded object at table offset 12.
- The context.
- A writable reference to a local opaque 32-bit result.

If that dependency returns nonzero, processing stops. The selected index is not submitted to the next dependency.

If it returns zero, the function calls F-277c3b9f6f6a with:

- The opaque result supplied through the preceding call’s output.
- The selected record index.
- The context.

If this second dependency returns zero and the optional index output is present, the function writes the selected index to that output.

A null index-output reference does **not** suppress either dependency call. It suppresses only the initial sentinel write and final index write.

There is no rollback if either downstream dependency reports failure. In particular, a newly appended record remains appended unless a dependency independently changes that state.

## Side effects

### Explicit writes by this function

Depending on the path, the function can write:

- The sentinel and, on full downstream success, a selected index to the optional output.
- A replacement storage address after a growth call, including a growth call reporting failure.
- A new capacity after a growth call reporting zero status.
- Three zero words to a new record.
- The incremented count.
- The new record’s normalized keys and mode.

A successful lookup does not explicitly modify the record or the count.

### Dependency effects

All three dependencies receive the context. One receives the embedded object by reference; another receives the existing storage address.

Their effects on globals, aliased objects, allocation state, and memory ownership are not established by this function. Claims about unchanged state apply only to this function’s explicit actions, not to arbitrary dependency behavior.

### Ownership and lifetime

The function does not explicitly release storage or destroy objects. It replaces the storage-address field with the growth dependency’s result without retaining an explicit recovery copy for failure handling.

It is unknown whether the growth dependency allocates, reallocates, copies, frees, or borrows memory. Likewise, the lifetime and ownership of the opaque result passed between the other two dependencies are unknown.

### Error reporting

There is no explicit error return or diagnostic.

The optional output remains at the sentinel when this function does not reach the final successful write, assuming dependencies and aliases do not modify it. The sentinel alone does not distinguish:

- Storage-growth failure.
- Failure of F-c2a5aac558d4.
- Failure of F-277c3b9f6f6a.

Invalid-memory access and overflow-related failures are not explicitly handled.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. They assume valid, non-overlapping memory, non-overflowing arithmetic, and dependencies limited to their stated example effects.

1. **Existing pair, different mode.**  
   A record contains keys `(10, 0)` and mode 3. Inputs are first input 10 and second input −2. The function selects that record because the normalized pair is `(10, 0)`. It does not rewrite the mode to 1. If both downstream dependencies return zero, the output receives that record’s index.

2. **First duplicate wins.**  
   Records at indices 2 and 5 both match the normalized pair. Index 2 is selected; index 5 is not examined after the match. The index submitted downstream is 2.

3. **Distinguished negative input.**  
   Inputs are first input 100 and second input −21. Lookup uses `(79, 0)`. If absent, the appended record receives keys `(79, 0)` and mode 3.

4. **Negative and zero inputs can share a record.**  
   With first input 7, second inputs −1 and 0 both normalize to `(7, 0)`. If one call has already appended that pair, the other can reuse it without changing its mode.

5. **Capacity equality permits append.**  
   Count is 3, capacity is 4, and no match exists. The function appends at index 3 without calling F-6dd003795db7, sets count to 4, and leaves capacity unchanged.

6. **Growth request.**  
   Count and capacity are both 8, and no match exists. The function requests capacity 16 with element size 12. If the growth status is zero, it stores the returned address, stores capacity 16, and appends at index 8.

7. **Growth failure still replaces the address field.**  
   Under the preceding growth conditions, suppose the dependency returns address value R and writes a nonzero status. The function stores R into the storage-address field and returns without explicitly updating count or capacity, initializing the new record, or invoking either downstream dependency.

8. **Downstream failure retains an append.**  
   A record is appended successfully, then F-c2a5aac558d4 returns nonzero. F-277c3b9f6f6a is not called. The output remains at the sentinel, and this function does not undo the append.

9. **Null output still performs submission.**  
   With a null index-output reference, a selected record still reaches both downstream dependencies when the first returns zero. No output word is written.

10. **Empty table does not require readable records for lookup.**  
    With count zero, the search reads no record keys. Whether append can proceed depends on capacity, storage validity, and any growth result.
