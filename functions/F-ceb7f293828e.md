# F-ceb7f293828e

## Purpose

F-ceb7f293828e traverses a counted sequence, recognizes twelve specific element values, and conditionally submits two descriptors to F-945301cd184f. Recognized values select adjacent boundaries from a table. A nonnegative starting boundary permits submission; a negative starting boundary suppresses it. Each submitted element also advances a local cursor by a signed span.

The recognized values correspond to decimal digits, colon, and period in an ASCII-compatible encoding. Interpreting the boundaries as glyph regions and the submissions as rendering operations is **inferred intent**, not an established dependency contract.

The established behavior consists of the reads, arithmetic, local writes, calls, and traversal rules described below.

## Interface

The function accepts three arguments and has no explicit return value.

| Argument | Established role |
|---|---|
| Object address | Supports accesses at byte offsets `0xA8`, `0xAC`, `0xB0`, and `0xB4`. |
| Context word | Opaque 32-bit value forwarded unchanged to each submission. |
| Coordinate-record address | Identifies four consecutive signed 32-bit fields at byte offsets 0, 4, 8, and 12. |

The coordinate fields are called **first**, **cursor**, **edge**, and **fourth**, in storage order. These names describe their visible roles without establishing an external coordinate convention.

The relevant object fields are:

| Offset | Caller access |
|---|---|
| `0xA8` | Read as a signed 32-bit mode value and compared with `0x10`. |
| `0xAC` | Read as an opaque 32-bit resource value before the query and again before each submission. |
| `0xB0` | The address of this field is passed to indexed lookup. The caller does not explicitly read its contents. |
| `0xB4` | Read as an opaque 32-bit value passed to count acquisition. |

A separate **table-base global** supplies a 32-bit address-bearing value. Alternate-table selection accesses this global twice.

The representation uses 8-bit bytes, 16-bit table entries, and 32-bit integer fields and address-bearing values. Byte order is not established.

Ordinary successful execution requires:

- Readable object and coordinate fields for all accesses actually performed.
- Readable selected table entries.
- Valid intermediate and final address calculations under the applicable target rules.
- Dependencies accepting the supplied arguments and local-storage addresses.
- Query results that make the subsequently consumed output fields valid to read.
- Defined behavior for the arithmetic and conversions encountered.

The caller performs no explicit null checks, allocation-bound checks, or memory-fault recovery.

## Behavior

### Initial coordinate reads and table selection

The function first reads all four coordinate fields, in storage order, and copies them into a local coordinate record. It does not subsequently reread the original coordinate-record address.

The initial first and fourth values are overwritten before any submission uses that local record. Their initial reads nevertheless occur.

Table selection follows this access order:

1. Read the table-base global.
2. Read the object mode at offset `0xA8`.
3. If the mode equals `0x10`, read the table-base global again and select that second value plus 26 bytes.

For any other mode, the first global value is selected unchanged.

Consequently, alternate-table selection does not necessarily mean “the first global value plus 26.” If the global changes between its two reads, the second value determines the alternate region.

The chosen base is then retained throughout traversal. The caller does not reread the mode or table-base global. Changes to those locations by dependencies do not themselves trigger reselection. Table entries remain separately read for each recognized element.

### Resource query and extent

After selecting the table base, the function reads object offset `0xAC` and calls F-c24767c70ad0 with:

1. An address of local output storage.
2. The resource value just read.

**The caller contains no explicit writes initializing this query-output storage.** It passes the address to the dependency and subsequently reads fields from that storage. Any population of the output by F-c24767c70ad0 is dependency-mediated behavior; its complete write contract is unavailable.

After the call, the function consumes signed 32-bit fields at byte offsets 0 and 8 relative to the supplied output address. The complete output layout and required writable capacity are unresolved.

The extent calculation has two stages:

- Subtract the field at offset 0 from the field at offset 8 using signed 32-bit arithmetic.
- Mask the subtraction result with `0xFFFF`, retaining an unsigned 32-bit extent.

When the signed subtraction is representable, the extent is the low 16 bits of the difference and lies between 0 and 65,535. A difference of −1 therefore produces 65,535; a difference of 65,536 produces zero.

The mask does not establish wrapping behavior for an earlier signed overflow. If the mathematical difference is outside the signed 32-bit range, the extent remains **documented_only** pending target-level confirmation.

The extent is captured once and reused. The caller does not validate ordering between the query fields, check a query status, or substitute initialized defaults.

### Count and traversal

The function next reads object offset `0xB4` and passes that value to F-d8cbf9aa79a9. The caller captures an unsigned 8-bit count from the result.

Traversal starts with an unsigned 8-bit index of zero. Before each lookup, the function returns if the index is greater than or equal to the captured count. Otherwise, it calls F-08e2860e8e52 with:

1. The address at object offset `0xB0`.
2. The current index.

The lookup result is treated as a 32-bit element value. Exactly these values are recognized:

- `0x30` through `0x39`;
- `0x3A`;
- `0x2E`.

No broader character decoding, normalization, or termination convention is established.

After handling or skipping an element, the function increments the index. It does not refresh the count. A count of 255 visits indices 0 through 254, then returns when the index reaches 255; normal traversal therefore does not wrap the index.

A zero count still follows the initial coordinate reads, table selection, resource query, extent calculation, and count acquisition. It causes no indexed lookup.

### Boundary reads and span

Each recognized element selects two consecutive 16-bit table entries:

| Element | Start-entry byte offset | End-entry byte offset |
|---|---:|---:|
| Digit with numeric value 0–9 | Twice the numeric value | Twice the numeric value, plus 2 |
| Colon | 20 | 22 |
| Period | 22 | 24 |

The selected region occupies 26 bytes. Neighboring recognized values share boundary entries.

For each recognized element:

- The start entry is read first, interpreted as signed 16-bit, and extended to 32 bits.
- The end entry is read second, interpreted as unsigned 16-bit, and extended to 32 bits.
- The span is calculated before checking whether the start is negative.

The span calculation subtracts the start from the end in the unsigned 32-bit domain, multiplies the result by 65,536 in that domain, converts to signed 32-bit, and performs a signed right shift by 16.

With the corresponding signed conversion and sign-extending shift behavior, this extracts the signed interpretation of the low 16 bits of the boundary difference:

- `0x0000` through `0x7FFF` represent 0 through 32,767.
- `0x8000` through `0xFFFF` represent −32,768 through −1.

The target rules for the out-of-range signed conversion and negative signed right shift are **documented_only**. Negative-span examples below explicitly assume the sign-extending interpretation.

The resulting decisions are:

- Unsupported element: no boundary reads, no submission, and no explicit cursor update.
- Recognized element with negative start: both boundary reads and span calculation occur, but no submission or explicit cursor update follows.
- Recognized element with nonnegative start: submission occurs even if the span is zero or negative.

There is no monotonicity or nonnegative-span validation.

### Descriptor construction

For an accepted element, the function prepares a first descriptor containing four 32-bit fields:

| Field | Value |
|---|---|
| 0 | Zero |
| 1 | Signed start |
| 2 | Captured unsigned extent |
| 3 | Start plus signed span |

Under the signed-span interpretation above, an accepted start lies between 0 and 32,767, and start plus span lies between −32,768 and 65,534. This addition cannot overflow signed 32-bit arithmetic.

The second descriptor is the local coordinate record:

| Field | Value immediately before submission |
|---|---|
| 0 | Edge minus extent, with the conversion rules below |
| 1 | Current cursor |
| 2 | Current edge |
| 3 | Current cursor plus signed span |

The explicit preparation-store order is:

1. First descriptor, field 3.
2. Coordinate descriptor, field 3.
3. First descriptor, field 0.
4. Coordinate descriptor, field 0.
5. First descriptor, field 1.
6. First descriptor, field 2.

Cursor and edge are not rewritten during this preparation.

**Edge minus extent is unsigned 32-bit subtraction.** The signed edge is converted to unsigned before subtraction, and subtraction is modulo \(2^{32}\). The result is then converted into the signed 32-bit first coordinate field. An unsigned result above 2,147,483,647 requires target-specific signed-conversion behavior; it is not an unconditional signed-subtraction result.

**Cursor plus span is signed 32-bit addition.** It occurs once when preparing the fourth coordinate field and again after submission when updating the cursor. Neither operation has an explicit overflow check, saturation, or clamp. Out-of-range results remain **documented_only**.

### Submission and post-call state

After preparing the descriptors, the function rereads object offset `0xAC` and calls F-945301cd184f with:

1. The resource value read at that point.
2. The original context word.
3. The first descriptor’s address.
4. The local coordinate descriptor’s address.
5. The numeric value 255.

The meaning of 255 is unresolved.

After the call returns, the function adds the saved span to the **then-current** local cursor. It does not restore the pre-call cursor. If the dependency changed that field, the addition uses the changed value.

A dependency change to the local edge similarly affects later descriptor preparation. The first and fourth coordinate fields are recalculated for the next accepted element. The caller does not restore any coordinate field from the original input record.

## Acceptance examples

These are conditional static deductions, not runtime observations. Unless otherwise stated, assume valid memory and address arithmetic, normal dependency returns, query fields made valid by the dependency, no relevant mutation, and unchanged descriptor fields across submission.

### Empty sequence

For count zero:

- All four initial coordinate reads occur.
- Table selection, query, extent calculation, and count acquisition occur.
- No lookup or submission occurs.
- The caller performs no explicit initialization of query-output storage.
- No explicit write reaches the original coordinate record.

### Ordinary digit

Suppose the query fields at offsets 0 and 8 contain 100 and 120, respectively. The cursor is 7, the edge is 100, and the only element is digit `3`, with boundaries 12 and 17.

Extent is 20 and span is 5. One submission receives:

- First descriptor: `(0, 12, 20, 17)`.
- Coordinate descriptor: `(80, 7, 100, 12)`.

After return, the local cursor becomes 12.

### Distinct table-base reads

Suppose the first global read returns address A, the mode is `0x10`, and the second global read returns address B.

The selected region is B plus 26 bytes. If the mode instead differs from `0x10`, there is no second global read and the selected region is A.

### Unsupported and disabled elements

Consider an unsupported value, followed by a digit whose start is −1, followed by a digit with start 10 and end 13.

All three indices are looked up. The unsupported value causes no boundary reads. The negative-start digit reads both boundaries but does not submit. Only the final digit submits and explicitly advances the cursor, by 3.

### Extent boundaries

Query fields 100 and 99 produce extent 65,535 because the signed difference −1 is representable.

Fields 0 and 65,536 produce extent zero.

Fields −1 and 2,147,483,647 require a signed difference of 2,147,483,648. The mask does not justify predicting an extent; this case remains **documented_only**.

### Unsigned coordinate subtraction

With edge 5 and extent 20, unsigned subtraction produces 4,294,967,281.

If the target converts that value to the corresponding two’s-complement signed value, the first coordinate field becomes −15. That signed result is conditional on the conversion rule.

### Zero and negative spans

Start 12 and end 12 produce span zero. Submission still occurs; absent dependency mutation, the cursor remains unchanged.

Start 0 and end 65,535 produce span −1 under sign-extending span extraction. Submission still occurs. The first descriptor’s fourth field is −1, and the coordinate descriptor’s fourth field is cursor minus one, provided the signed addition is representable.

### Dependency mutation

If the saved span is 5 and F-945301cd184f changes the local cursor to 200, the post-call update produces 205.

If that dependency also changes the object resource field, the next submission uses the newly read resource value. The initial query is not repeated.
