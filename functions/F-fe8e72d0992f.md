# F-fe8e72d0992f

## Purpose

F-fe8e72d0992f obtains a block-address-like value, installs it in an object-associated address table, and updates one or two four-word state records through a dependency.

**Established static behavior:** the function requests the block before choosing among three paths:

- Initialize table storage and both state records.
- Add an entry after the existing trailing table slot.
- Obtain replacement table storage, copy an active range, add an entry, and update both records.

**Inferred intent:** the object resembles a segmented sequence whose two endpoint records refer into a table of block addresses. The operation appears to extend its trailing end. This interpretation does not establish the object type, the meaning of the supplied arguments, or any dependency’s ownership contract.

The normal return is a 64-bit concatenation of two words from a dependency-modifiable temporary record. Its semantic meaning is unknown.

## Interface

### Inputs and representation

The function receives an object address and three additional 32-bit arguments. It initially forms a temporary record containing four 32-bit words:

| Temporary word | Initial contents |
|---|---|
| 0 | Object address represented in 32 bits |
| 1 | First additional argument |
| 2 | Second additional argument |
| 3 | Third additional argument |

This initialization precedes all dependency calls. F-6bc2587a4cd2 subsequently receives the temporary record’s address and may alter its contents.

The supplied representation uses 32-bit addresses and four-byte words. The object has these directly accessed locations:

| Byte offset | Observed role |
|---|---|
| 0, 4, 8, 12 | First four-word state record |
| 16, 20, 24, 28 | Second four-word state record |
| 12 | Source-range start address during expansion |
| 28 | Trailing table-slot address |
| 36 | Address-table base |
| 40 | Capacity-like word |

Offset 32 is not directly accessed. Access to the word at offset 40 requires object storage extending through byte 43.

“Table,” “capacity,” and “state record” describe observed uses, not independently established types or invariants.

### Output

Every visible normal-return path produces the same output layout:

- Bits 0–31: final temporary word 0.
- Bits 32–63: final temporary word 1.

The low word is not sign-extended. Temporary words 2 and 3 do not directly contribute to the return value.

On expansion, “final” means after the second F-6bc2587a4cd2 call. On the other paths, it means after the sole call to that dependency.

### Preconditions and failure boundary

There is no visible argument validation, allocation-result check, explicit error return, or rollback mechanism.

Safe normal execution requires storage suitable for all selected accesses, including the object, table slots, copied source range, and dependency-produced addresses. Alignment, accessibility, and sufficient allocation size are not checked here.

Expansion additionally requires the source traversal to reach its retained endpoint through four-byte increments without invalid accesses. Malformed ranges are not rejected.

Dependency failure conventions, nonlocal exits, exceptions, and recovery behavior are **documented_only**. A zero allocation-like result is not specially handled.

## Behavior

### Widths and arithmetic model

Object words, address representations, and the integer quantities used in the visible calculations are 32 bits. Table entries occupy four bytes.

Unsigned halving uses a logical right shift by one. The expansion range difference uses a signed right shift by two, interpreted here as an arithmetic shift of the signed 32-bit difference.

The formulas below describe low-word, modulo-\(2^{32}\) results where arithmetic overflows. They do not establish that every signed intermediate operation has defined behavior in an original source language. Arithmetic identities also do not establish that resulting addresses are valid.

### Common sequence

After initializing the temporary record, the function:

1. Calls F-6bf88c96e2f7 without arguments.
2. Calls F-871e64ddc6de with that result shifted left by two, at 32-bit width, and a second argument of zero.
3. Retains the returned 32-bit value as the new block address.
4. Calls F-ee993636c085 with the object address.
5. Selects initialization for a nonzero result; otherwise examines the existing table.

The new-block request therefore precedes the state-selection call and every path-specific object update. No visible action undoes this request if subsequent execution fails.

Repeated calls to F-6bf88c96e2f7 are distinct observations. Their results and side effects must not be assumed equal.

### Initialization

A nonzero result from F-ee993636c085 selects this path.

The function calls F-6bf88c96e2f7 a second time and stores its result at object offset 40. It then requests table storage through F-871e64ddc6de, passing this retained result shifted left by two and zero. The returned table address is stored at offset 36.

Next, it reads the capacity-like word at offset 40 and writes the new block address into the slot at:

**returned table address + 4 × logical-half(current capacity)**.

This first slot write uses the retained allocation result as its base. The capacity is reread after the allocation call; interference by that dependency can therefore affect placement.

The function then calls F-6bf88c96e2f7 a third time. F-6bc2587a4cd2 receives:

- The temporary-record address.
- New block address + 4 × logical-half(third result).
- Current object table base + 4 × logical-half(current capacity).

The base and capacity for this call are read after the third unit-producing call. They need not equal their earlier values if that dependency changes the object.

After F-6bc2587a4cd2 returns, the function writes temporary words 0, 1, 2, and 3 to object offsets 0, 4, 8, and 12, in that order. It then performs four ordered read/write pairs:

- Read offset 0 and write offset 16.
- Read offset 4 and write offset 20.
- Read offset 8 and write offset 24.
- Read offset 12 and write offset 28.

Thus the second record is copied from the newly written first record, rather than independently populated from the temporary record. Under ordinary noninterfered execution, both records match.

The second unit result supplies the table-allocation request. The third supplies the block-relative argument. Equality between these results is not established.

No release-like call for prior table storage occurs on this path.

### Existing table: path selection

For a zero result from F-ee993636c085, the function captures the word at offset 28 as the trailing slot address. It compares that address for equality with:

**table base + 4 × capacity − 4**,

using the words at offsets 36 and 40.

Equality selects expansion. Any inequality selects the simple append path. This is not a less-than comparison: an out-of-range trailing address beyond the calculated last slot still selects simple append.

### Existing table: simple append

The function first writes the captured trailing slot address plus four to object offset 28. It then writes the new block address into the slot at that incremented address.

F-6bc2587a4cd2 receives:

- The temporary-record address.
- The retained new block address.
- The current word at object offset 28.

After the call, temporary words 0–3 replace object offsets 16, 20, 24, and 28, in that order. The temporary record’s first two words determine the return value.

The intermediate advancement of offset 28 is observable to the dependency. Its final value can differ because temporary word 3 is written there afterward.

This path makes no direct writes to offsets 0–12, 36, or 40. It does not establish that dependencies preserve those locations.

### Existing table: expansion arithmetic and timing

Expansion begins by calculating:

- **d:** the signed 32-bit difference between the previously captured trailing slot and the word read at offset 12, arithmetically shifted right by two.
- **n:** the 32-bit unsigned result of adding one to d.

For a conventional aligned, nonnegative inclusive range, d is one less than its entry count and n is its entry count.

The function requests replacement storage through F-871e64ddc6de with **8n**, reduced to 32 bits, and zero. It retains the returned replacement-table address.

Only after that call does it:

1. Reread the trailing slot from offset 28.
2. Calculate **b = 2n masked with 0xFFFFFFFC**.
3. Establish the copy destination at replacement-table address + b.
4. Read offset 12 to establish the copy source.

Consequently, d and n precede the replacement-allocation call, whereas b is calculated after that call and after the trailing-slot reread. Nevertheless, b depends exclusively on retained n, not on the reread object fields.

### Existing table: copying and replacement

The copy uses the reread trailing slot plus four as its retained stopping address. Starting at the address obtained from offset 12, it repeatedly reads one four-byte source word and writes it to the corresponding replacement-table word, advancing both traversal addresses by four.

The stopping comparison occurs before each copy. For a conventional valid range, this copies the source through the retained trailing slot inclusively. If the initial source already equals the stopping address, it copies no entries.

This is forward, word-at-a-time copying, not an established overlap-safe bulk operation. Earlier destination writes can affect later source reads if the ranges overlap.

After copying, the function calls F-ff1bdc376dcd with the current words at offsets 36 and 40, followed by zero. The replacement base has not yet been installed at this point.

After that call returns, the function:

1. Writes the retained replacement-table address to offset 36.
2. Stores the new block address at replacement-table displacement **4 × (d + logical-half(n masked with 0x7FFFFFFF)) + 4**.
3. Calls F-6bc2587a4cd2 with the temporary-record address, the current object word at offset 0, and the current table base plus b.
4. Writes the resulting temporary words to offsets 0, 4, 8, and 12, in order.
5. Calls F-6bc2587a4cd2 again with the same temporary-record address, the retained new block address, and the current table base plus **b + 4d + 4**.
6. Writes the resulting temporary words to offsets 16, 20, 24, and 28, in order.
7. Writes **2n**, reduced to 32 bits, to offset 40.

The temporary record is not reinitialized between the two state-update calls. The second call receives its contents as left by the first call.

No further F-6bf88c96e2f7 calls occur on the expansion path.

### Equality of the expansion displacements

Under the stated 32-bit low-word model:

**4 × logical-half(n masked with 0x7FFFFFFF) = (2n masked with 0xFFFFFFFC) = b.**

This holds for every 32-bit n, including patterns with bit 31 set. Masking off that bit before halving does not change the final low-word result after multiplication by four.

Therefore, both the appended-address store and the second state-update slot use displacement:

**b + 4d + 4**.

There is no bit-pattern-dependent discrepancy between these displacements.

Their complete addresses can still differ if the first state-update dependency changes offset 36: the store uses the retained replacement address, whereas the second call uses the table base reread from the object. This is a dependency-interference issue, not an arithmetic inequivalence.

Defined signed arithmetic and address validity remain separate uncertainties.

## Side effects

Directly established effects include:

- One initial block-storage request on every normal path.
- A second storage request on initialization or expansion.
- Writes of the retained new block address into table storage.
- Forward copying of existing entries on expansion.
- Updates to one or both four-word records.
- Installation of a replacement table base and capacity on expansion.
- An expansion-only call to F-ff1bdc376dcd.

No direct write initializes the new block’s contents. F-6bc2587a4cd2 receives block-related addresses, but its effects are unknown.

**Ownership is not established.** Allocation-like and release-like call shapes do not prove allocation guarantees, ownership transfer, deallocation, or argument retention. The visible function does not directly release individual copied block addresses or the newly requested block.

Dependency interference matters at several boundaries:

- Initialization rereads capacity after obtaining table storage.
- Expansion sizes the request using pre-call n but obtains copy bounds after allocation.
- The release-like call receives current base and capacity before the replacement base is installed.
- Expansion state-update calls occur before the final capacity write.
- The second expansion state-update call rereads the table base after the first call.

No dependency is assumed to preserve object fields, globals, or other accessible storage. Concurrent modification and reentrancy guarantees are unknown.

## Acceptance examples

These are conditional static examples, not runtime tests. Unless stated otherwise, dependencies preserve unrelated state, storage is valid and nonoverlapping, and addresses do not overflow.

### Initialization with distinct unit results

Suppose the three F-6bf88c96e2f7 results are 8, 6, and 10, and the state selector returns nonzero.

Required observations:

- Initial storage request: 32 and zero.
- Table-storage request: 24 and zero.
- New block address stored at table displacement 12.
- State-update arguments include new block address + 20 and table address + 12.
- The resulting temporary record populates the first object record; the second is copied from it.

Using the second unit result to calculate the block-relative argument would not satisfy this behavior.

### Simple append

Suppose table base is M, capacity is 8, and the trailing slot is M + 12.

The calculated final slot is M + 28, so simple append is selected. Offset 28 first becomes M + 16, that slot receives the new block address, and the state-update dependency receives M + 16 as its slot argument. Its resulting temporary record then replaces offsets 16–28.

### Expansion with five active entries

Suppose capacity is 8 and the active range extends from M + 12 through M + 28.

Then d = 4, n = 5, and b = 8.

Required observations:

- Replacement request: 40 and zero.
- Five entries copied to replacement displacements 8, 12, 16, 20, and 24.
- New block address stored at displacement 28.
- First state-update slot: replacement displacement 8.
- Second state-update slot: replacement displacement 28.
- Final capacity: 10.

The replacement allocation occurs before the trailing-slot reread and b calculation.

### Allocation-time range interference

Start with the preceding five-entry case. Suppose replacement allocation changes offset 12 to M + 16 but leaves the trailing slot unchanged.

The retained d and n remain 4 and 5. The request remains 40, and subsequently calculated b remains 8. However, the copy now traverses four source entries, from M + 16 through M + 28, placing them at replacement displacements 8 through 20. The appended-address displacement remains 28.

This demonstrates the mismatch possible between retained sizing information and post-call copy bounds.

### High-bit arithmetic identity

As a bit-pattern-only example, let n be 0x80000005 and d be 0x80000004. Then b is 8, and both appended-address displacement expressions reduce to 0x0000001C under low-word arithmetic.

This is not a safe-execution example: it establishes neither defined signed arithmetic nor valid storage.

### Return and malformed state

If final temporary words 0 and 1 are 0x89ABCDEF and 0x01234567, the return pattern is 0x0123456789ABCDEF.

If a trailing slot lies beyond, rather than equals, the calculated final slot, simple append is still selected. Rejection or repair is not established.
