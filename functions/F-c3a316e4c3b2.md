# F-c3a316e4c3b2

## Purpose

F-c3a316e4c3b2 performs mode-dependent preparation of an object accessible through a context-associated handle, invokes a common operation, optionally invokes two follow-on dependencies, and returns the common operation’s result.

Mode zero selects one of two preparation sequences, invokes an object operation on a context state region, validates that region, and stores a one-byte property. Every nonzero mode instead validates the existing state region and passes it to an object operation.

Both successful preparation branches write a one-byte marker before invoking the common operation. Follow-on calls occur only when the common result is nonzero, the unsigned mode is below two, and a property byte read afterward is nonzero.

These are structural roles established by the supplied representation. Domain meanings for the state, property, marker, and operations are not established.

## Behavior

### Entry and first global capture

Every invocation first calls F-eb24201e389b with the local handle region’s address and the context address plus `0xB4`.

After that call returns, the function reads a global 32-bit lookup-container value and retains it. This **initial container capture** occurs for every mode, including nonzero modes that perform no lookup.

The initial capture therefore reflects the global after F-eb24201e389b returns. It must not be treated as a value read before that dependency.

### Zero-mode lookup selection

When mode is zero, the function reads the lookup-container global again. This **first-lookup base** is a separate read from the initial container capture.

It reads the four-byte word at the first-lookup base plus four and calls F-9b9c1c7483f4 with:

- The first four-byte lookup destination.
- That newly read word.
- The first four-byte auxiliary region.

The initial container capture is not the base expression used for this first lookup. Equality between the captured base and the reread base is not guaranteed.

After F-9b9c1c7483f4 returns, the function accesses a second global, the **lookup-context global**, twice:

1. It reads and retains a 32-bit value as the **captured lookup context**.
2. It separately reads the same global again to supply the first argument to F-8094c3d72052.

F-8094c3d72052 receives the second read’s value and the result returned by F-9b9c1c7483f4. Its first argument is not specified as the retained capture. Those two global reads need not produce equal values.

After F-8094c3d72052 returns, F-8a5aadac202f is called on the first lookup destination. Only then does the function act on the selection result:

- Zero selects the first preparation sequence.
- Any nonzero result selects the second preparation sequence.

### First zero-mode preparation sequence

For a zero selection result, the function obtains an object address by calling F-e38e6836b640 on the local handle region. It reads the object’s dispatch table and invokes the entry at `0x38`.

No explicit arguments are shown for this indirect call. In particular, the object address used to locate the entry is not shown as an explicit receiver argument. Implicit-register requirements and the actual callable signature remain unknown.

The call’s result is not consumed by the visible function.

### Second zero-mode preparation sequence

For a nonzero selection result, the function performs another lookup using the second lookup destination and second auxiliary region.

This lookup uses the **initial container capture**, not a fresh read of the lookup-container global and not the separately read first-lookup base. At this later point, the function reads the four-byte word at the captured address plus four and passes it to F-9b9c1c7483f4.

Thus, the two lookups can differ in both base and read time:

- The first uses a separately reread global base.
- The second uses the entry-time capture made after handle establishment.
- Each reads its own base-plus-four word when its lookup is performed.
- Even if both bases happen to be equal, the two word reads are not one cached read.

F-1b0572bf841e then receives the **captured lookup context** and the second lookup result. It does not receive a new global read or necessarily the value passed earlier to F-8094c3d72052.

After F-1b0572bf841e returns, the function calls F-8a5aadac202f on the second lookup destination.

The remaining sequence is:

- Obtain an object address through F-e38e6836b640.
- Call F-1c06d0a5910b with the 20-byte temporary region, the result from F-1b0572bf841e, and a literal zero.
- After that dependency returns, read the previously obtained object’s dispatch table and invoke entry `0x1EC`, passing the object address and the result of F-1c06d0a5910b.
- Call F-c1466ea05103 on the 20-byte temporary region.

Object acquisition precedes F-1c06d0a5910b, but dispatch-table access follows it. The function does not visibly reacquire the object between those operations. No dependency-preservation guarantee is established.

### Zero-mode state operation and property write

After either preparation sequence, the function calls F-e38e6836b640 again. This is a fresh acquisition through the handle, not a required reuse of an earlier object address.

It invokes dispatch entry `0x1F4` with the newly obtained object address and the context address plus `0xD0`.

Next, F-b7abcf60c990 receives the state-region address:

- A zero result transfers control to F-a817d8d58c10, marked nonreturning in the supplied representation.
- A nonzero result allows normal preparation to continue.

After successful validation, F-e6fe164a3cfa receives the state-region address. Its one-byte result is stored at context offset `0xE4`.

The store preserves the supplied byte value; no conversion to a Boolean zero-or-one representation is shown.

### Nonzero-mode preparation

For every nonzero mode, the function calls F-b7abcf60c990 on the state region before obtaining an object for the mode-specific dispatch.

A zero result transfers control to F-a817d8d58c10. A nonzero result is followed by object acquisition through F-e38e6836b640 and invocation of dispatch entry `0x1EC`, with the object address and state-region address as explicit arguments.

This branch performs neither lookup, does not read the lookup-context global, does not invoke `0x1F4`, and does not directly store the property byte. The initial lookup-container capture still occurs before this branch.

Absence of a direct property store does not imply preservation: dependencies may affect context memory.

### Common operation, follow-on calls, and return

After successful preparation in either branch, the function writes the byte value one at context offset `0xC6`.

It then invokes F-4fd087f2325e with the context and the original unsigned mode. Its signed 32-bit result is retained.

Follow-on eligibility is evaluated in this order:

1. The retained result must be nonzero.
2. The unsigned mode must be less than two.
3. The byte at context offset `0xE4` is then read and must be nonzero.

The property read is skipped if either preceding condition fails. A negative common-operation result satisfies the nonzero test. Modes from two through the maximum unsigned 32-bit value fail the mode test.

The property read occurs after the common operation returns. It is not a test of a cached value from zero-mode preparation.

When all conditions hold, F-6a21f4f07f67 is called, followed by F-814d4ee17e01. Neither call shows explicit arguments; neither result is used. The condition is not reevaluated between them.

Finally, F-24edd96d1422 receives the local handle region. After it returns, the function returns the retained common-operation result unchanged.

## Side effects

The function directly writes two context bytes:

- At `0xE4`, only after successful zero-mode validation.
- At `0xC6`, after either preparation branch succeeds and before the common operation.

These are ordered writes, not guarantees about final memory contents. Later dependencies may alter the same memory.

Other effects are dependency-mediated. Passed addresses include local storage, context subregions, and obtained object addresses. Global access and mutation inside dependencies are unknown.

Calls ending the visible use of temporary regions occur at these points:

- Each used lookup destination is passed to F-8a5aadac202f after its immediate consumer.
- The 20-byte temporary is passed to F-c1466ea05103 after dispatch `0x1EC`.
- The handle region is passed to F-24edd96d1422 after the common operation and any follow-on calls.

These are cleanup-shaped call patterns, not proof of destruction, deallocation, reference-count changes, or ownership transfer. The function does not establish that a dependency may safely retain a pointer to local storage beyond the invocation.

Validation failure has no ordinary error return in the represented control flow. No marker store, common operation, final handle cleanup, or normal return follows the marked nonreturning call. In mode zero, earlier lookups and object operations may already have occurred.

No rollback or exceptional cleanup path is shown for other dependencies that fail to return normally.

## Acceptance examples

These are conditional static criteria, not executed tests. They assume valid accessible storage, compatible dispatch targets, and normal dependency returns unless otherwise stated.

1. **Different container reads.** Suppose the initial container capture yields address A, while the separate zero-mode reread yields address B. The first lookup receives the word read at B plus four. If selection is nonzero, the second lookup receives the later word read at A plus four. No equality between A and B is required.

2. **Different lookup-context reads.** Suppose the capture after the first lookup yields value X, and the separate reread for F-8094c3d72052 yields Y. The first consumer receives Y. If its result selects the second sequence, F-1b0572bf841e receives X, regardless of whether X equals Y.

3. **Captured address, changing contents.** If selection is nonzero and earlier dependencies change memory at the initially captured container address plus four, the second lookup reads that changed word. Changing only the container global does not redirect the second lookup.

4. **Zero selection.** First lookup cleanup precedes dispatch `0x38`. No second lookup occurs. A fresh object acquisition precedes dispatch `0x1F4`; successful validation then leads to the property store, marker store, and common operation.

5. **Nonzero selection.** Second lookup cleanup precedes object acquisition and temporary preparation. Dispatch `0x1EC` precedes temporary cleanup, which precedes the fresh acquisition for dispatch `0x1F4`.

6. **Nonzero-mode validation failure.** With mode one or any larger unsigned mode, zero validation reaches F-a817d8d58c10 before the branch’s object acquisition. The initial container-global read has already occurred, but no lookup or lookup-context read occurs. The represented path has no subsequent marker store or common operation.

7. **Negative common result.** With mode one, a negative common result and a nonzero post-operation property byte cause both follow-on calls in order. After handle cleanup returns, the same negative result is returned.

8. **Mode boundary.** With mode two or unsigned mode `0xFFFFFFFF`, no follow-on call occurs, even for a nonzero common result. The conditional property read is skipped.

9. **Property changed by the common operation.** A nonzero byte stored during zero-mode preparation does not trigger follow-on calls if the common operation changes it to zero. Conversely, a byte changed from zero to nonzero can satisfy the condition when the other conditions hold.

10. **Zero common result.** Successful preparation writes the marker before the common operation returns zero. The property condition is not read, follow-on calls are skipped, handle cleanup occurs, and zero is returned.
