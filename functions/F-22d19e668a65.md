# F-22d19e668a65

## Purpose

F-22d19e668a65 coordinates two ordered operations against a shared context. It substitutes storage for absent inputs, optionally prepares a replacement for the first input, combines operation reports, performs conditional follow-ups, and publishes separate operation statuses.

The function’s return value reports orchestration completion or an early failure. It does **not** report overall operation success: either operation status may be nonzero while the function returns zero.

This contract describes the supplied static evidence. Terms such as “storage acquisition,” “preparation,” “report,” and “release” identify boundary roles; they do not establish the dependencies’ internal semantics.

## Interface

### Arguments

The represented model uses 32-bit pointers and 32-bit integer words.

| Argument | Representation | Boundary role |
|---|---|---|
| Context reference | Pointer | Passed to dependencies; its first word is read on selected paths. |
| First input | Nullable pointer | Supplies the first operation’s input, unless preparation selects replacement storage. |
| Second input | Nullable pointer | Supplies the second operation’s input. |
| Options | Unsigned 32-bit value | Bits `0x1` and `0x8` enable preparation. |
| First status destination | Nullable pointer to a writable 32-bit word | Receives entry initialization and, on normal completion, the first operation status. |
| Second status destination | Nullable pointer to a writable 32-bit word | Receives entry initialization and, on normal completion, the second operation status. |

A present input must support each reached read of its first 32-bit word and all accesses required by dependencies. The context must support any reached first-word read and the requirements of dependencies receiving the reference.

There is no general validation of nonnull pointers. Distinctness is not required by the visible logic. Aliasing can change behavior because status initialization precedes input inspection.

### Local boundary objects

Each operation uses the same report region containing two adjacent 32-bit words:

| Offset | Interpretation within this function |
|---|---|
| `0` | Primary report bits |
| `4` | Auxiliary report bits; also represented as a pointer-shaped value |

The auxiliary word is combined as a 32-bit bit pattern and may be forwarded as an argument. This function does not dereference it.

Each operation also has a separate 32-bit status slot. Addresses associated with those slots are placed in call-associated scratch storage before the respective operation calls. The visible material does not establish a complete calling convention for these outputs.

Preparation exposes a descriptor with an indicated extent of 16 bytes. After the descriptor helper returns, this function assigns the context pointer at offset `0` and the temporary-base pointer at offset `4`. It does not explicitly assign the remaining eight bytes at that stage.

### Return values

| Outcome | Return |
|---|---|
| Normal completion, including an empty input pair | `0` |
| Required acquisition supplies a null base | `-108` |
| Preparation dispatch returns nonzero | The same nonzero 32-bit value, after the release call |

Negative 108 has the 32-bit two’s-complement representation `0xFFFFFF94`.

Processing statuses and direct processing return values do not become the function’s return value.

## Behavior

### Entry and completion guarantees

Every present status destination receives an initial zero. The first destination is written before the second. Both writes precede acquisition and input-content inspection.

Normal completion publishes both final statuses, again first destination before second. Publication precedes any normal release call.

Early failure does not perform final publication. The entry writes have nevertheless occurred. They do not guarantee that the destinations still contain zero at return: aliases and intervening dependency effects may change that memory.

For an empty pair, the final statuses are both zero. For a processed pair, they are the status values consumed after both operations have returned.

### Effective input selection

When both input pointers are nonnull, they are initially used as supplied. If either pointer is null, one call to F-17359762a6dd obtains a temporary base before any input-content inspection.

A successful acquisition substitutes addresses only for missing inputs:

| Missing input | Effective address |
|---|---|
| First | Temporary base |
| Second | Temporary base plus 5,216 bytes |
| Both | The two addresses above, derived from one acquisition |

The displacement is `0x518` four-byte words: 1,304 words, or 5,216 bytes. It is not a 1,304-byte displacement.

A supplied nonnull input remains selected. No second acquisition is needed merely because both inputs are absent.

A null acquired base causes immediate return of `-108`. No input-content inspection, processing, or release of that null result occurs.

The acquired base is retained for later release. The derived second-input address is not separately released. Storage acquisition does not establish initialization, size, alignment, or ownership guarantees; those remain prerequisites for valid execution.

### Work classification

Work is absent only when both effective inputs’ first words are observed as zero.

The first input is inspected first. A nonzero observation establishes work without inspecting the second input’s first word for this decision. Only a zero first observation requires the second read.

An empty pair bypasses the preparation gate, preparation dependencies, both operations, and both follow-ups. It still receives normal zero-status publication and release of any acquired base.

These reads are not an atomic snapshot. In particular, entry status writes and acquisition-side effects occur earlier and can affect the observed input words.

### Preparation eligibility and replacement

Preparation is enabled when the supplied options contain either `0x1` or `0x8`. The represented normalization sets `0x1` when `0x8` is present without clearing other supplied bits. No other option bit has an established effect here.

Every nonempty pair invokes F-b7f290db7df2 with the context reference and zero, including when preparation is option-disabled.

Preparation occurs only when all three conditions hold:

- The gate returns zero.
- Preparation is option-enabled.
- A new read of the first input’s first word is nonzero.

The new input read occurs only when the first two conditions hold. A nonzero gate result suppresses preparation, not processing, and is not propagated as a failure.

The later input observation need not equal the work-classification observation. For example, the gate can change the first word between them.

Selected preparation requires a temporary base. A base already obtained for missing inputs is reused. Otherwise, F-17359762a6dd is called at this point; a null result returns `-108` before processing or final status publication.

Preparation has these boundary ordering requirements:

| Boundary event | Required relationship |
|---|---|
| F-ad023a375886 receives the current first input, temporary base, and one opaque static argument | Before descriptor preparation |
| F-c67cb20988a1 receives the descriptor address and `16` | Before this function assigns the descriptor’s two pointer fields |
| F-3182ac1ca82f receives the current first context word, another opaque static argument, and descriptor address | After those assignments |

The first context word is read for dispatch after the preceding preparation dependencies have returned. Their effects must not be assumed absent.

The direct return values of F-ad023a375886 and F-c67cb20988a1 are ignored.

A zero dispatch result selects the temporary base as the first operation’s input. The second input remains unchanged, including when it already refers to the same acquired region at the 5,216-byte displacement.

A nonzero dispatch result requires a call to F-5d781b4e2431 with the temporary base, followed by propagation of the dispatch result. This path has no processing, follow-ups, or final status publication.

### Operation outputs

For a nonempty pair that reaches processing:

- F-9ac3b87b26f9 runs before F-39bc885ebe39.
- Each receives its selected input, the context reference, zero, and the same report-region address.
- Both words of the first report are captured before the second operation can overwrite the report region.
- Both operation statuses are consumed only after the second operation returns.

The first operation’s status is therefore not protected by a demonstrated capture between the two calls. The second dependency must not be assumed incapable of changing it.

For stable, defined operation outputs, the resulting decisions are:

| Derived quantity | Definition |
|---|---|
| Combined primary report | Bitwise OR of both primary report words |
| Report-follow-up condition | Bitwise OR of both auxiliary report words, additionally including `0x20` when the second status is nonzero |
| Status-follow-up condition | Either consumed operation status is nonzero |

These are 32-bit bitwise combinations, not arithmetic addition. The first status does not directly contribute to the report-follow-up condition.

The direct return values of both operations are ignored.

The represented accesses also distinguish output consumption from a single simultaneous snapshot. The first report’s auxiliary word is captured before its primary word. After the second call, its primary word is consumed for the combination, and its auxiliary word is read for combination and again for the retained follow-up payload. The second status is loaded before the first status and is checked again for the `0x20` contribution. If these exposed locations can change between accesses, a single stable-output interpretation requires additional guarantees not supplied here.

### Follow-ups

F-8372b6f032fd is invoked if either the combined primary report or the report-follow-up condition is nonzero. Its arguments are:

- The context reference.
- The retained second operation’s auxiliary report word.
- The combined primary report.

The condition is not the payload. A bit contributed solely by the first auxiliary report, or solely by the second-status `0x20` rule, can trigger this call while both report-valued arguments are zero.

F-fd61d89535ad is invoked if either consumed status is nonzero. It receives the current first context word and `1`.

When both follow-ups occur, the report follow-up precedes the status follow-up. The context-word read for the latter occurs after the former returns, so changes made by the report follow-up can affect its argument.

Both follow-up return values are ignored. The status values retained for final publication have already been consumed before these calls.

## Side effects

The function’s direct nonlocal writes are the optional status-destination writes. It also writes local boundary storage and exposes local report, descriptor, and status-related addresses to dependencies.

Important externally relevant ordering constraints are:

| Earlier event | Later event |
|---|---|
| First entry status write | Second entry status write |
| Entry status writes | Acquisition and input inspection |
| Work classification | Preparation gate |
| Successful selected preparation | First operation |
| First report capture | Second operation |
| Report follow-up, when present | Status follow-up |
| First final status write | Second final status write |
| Normal final status publication | Normal release |

If both status destinations identify the same word, the second final status is the last direct status write on normal completion. A subsequent release dependency may still affect that memory.

The base is passed to F-5d781b4e2431 on normal completion and preparation-dispatch failure whenever an acquisition succeeded. Caller-supplied inputs are not released merely because they were supplied.

These observations establish release-call responsibility, not allocator ownership semantics. They do not prove that acquisition transfers ownership, that release frees storage, or that another dependency neither retains nor invalidates exposed memory. Dependencies may also affect context, inputs, global state, and output destinations.

## Acceptance examples

These are conditional static expectations, not executed tests. Except where stated otherwise, memory is valid, output values remain stable while consumed, dependencies return normally, and there are no additional relevant mutations.

| Scenario | Required result |
|---|---|
| Both supplied inputs have zero first words | First input is inspected before second. No acquisition, gate, processing, or follow-up occurs. Present destinations receive entry and final zeros; return is zero. |
| Only the second input is missing | Acquisition supplies its address at base plus 5,216 bytes. The first input remains supplied. Normal release receives the base, not the displaced address. |
| Both inputs are missing | One acquisition supplies both effective addresses. Selected preparation reuses that base. |
| Acquisition fails for a missing input | Entry status clearing occurs, but input inspection and processing do not. Return is `-108`, with no release of the null result. |
| First status destination aliases the first input’s initial nonzero word; second input is zero | Entry clearing makes the first observed input word zero. Without another mutation, the pair is classified empty. |
| Options equal `0x8`, gate returns zero, and the later first-input word is nonzero | Preparation is selected even though supplied bit `0x1` was clear. |
| First input initially reads zero, second reads nonzero, and the gate changes the first word to nonzero | With preparation enabled and a zero gate result, the later read permits preparation. |
| Gate returns nonzero | No preparation-specific input reread or dispatch occurs. Both operations still run. |
| Preparation needs a new acquisition and it returns null | Return is `-108`; no operation or final status publication occurs. |
| Preparation dispatch returns nonzero | Release receives the temporary base before that result is returned. Neither operation runs. |
| Only the first auxiliary report is nonzero | Report follow-up occurs with zero second auxiliary payload and zero combined primary report. Zero statuses suppress status follow-up. |
| Only the first status is nonzero; all reports are zero | Report follow-up is omitted. Status follow-up occurs. Final publication reports both statuses; return is zero. |
| Only the second status is nonzero; all reports are zero | The `0x20` contribution triggers report follow-up with zero report-valued arguments, followed by status follow-up. Return is zero. |

## Uncertainties

The following remain **documented_only**:

- Domain meanings and complete layouts of the inputs and context.
- Acquisition size, initialization, alignment, address-range safety, and ownership guarantees.
- Whether acquired storage supports the displaced second input and all dependency accesses.
- Whether dependencies preserve, retain, release, or invalidate any exposed memory or global state.
- The identities and representations of the two opaque static arguments.
- Descriptor-helper behavior and descriptor bytes beyond the two explicit pointer fields.
- The complete status-output calling convention and guarantees that consumed report and status words are defined.
- Report-bit meanings, operation-status meanings, and dependency error conventions beyond the explicit branches.
- Behavior for invalid memory, indeterminate outputs, asynchronous mutation, or dependencies that do not return normally.

Acquisition is represented with a wider-than-pointer result at one call site and a pointer-sized result at another. The low 32 bits select the base used here. An upper word is extracted in the wider representation, but no externally observable use of it is established on the represented paths.
