# F-72036880fdd9

## Purpose

F-72036880fdd9 conditionally creates, prepares, and submits an object using a context obtained from an external dependency. Eligibility depends on a byte in a supplied descriptor, a nonzero 32-bit input, and the low byte of another input.

The established behavior is a sequence of dependency calls, explicit memory reads and writes, and a packed 64-bit return value. The object’s application-level meaning is unknown. Terms such as “descriptor,” “context,” and “submission” are descriptive labels, not established type or ownership guarantees.

The function has two normal return forms:

- **Completed path:** the upper 32 bits reproduce the second input’s bit pattern; the lower 32 bits are 1.
- **Non-completed path:** the upper 32 bits contain the zero-extended low byte of the first input; the lower 32 bits are 0.

These forms describe normal returns only. Invalid memory access or abnormal behavior in a dependency is not converted into a reported error.

### Output

The output is a 64-bit integer with independently specified upper and lower 32-bit words.

Let the **effective selector** be the original selector’s low eight bits, interpreted as a value from 0 through 255.

| Outcome | Upper 32 bits | Lower 32 bits |
|---|---:|---:|
| Completed path | Original payload bit pattern | `0x00000001` |

The return value is not a conventional Boolean. A non-completed outcome can return a nonzero 64-bit value. Consumers must inspect the lower word if they use it as the completion indicator.

The upper word is a bit-pattern field. If the 64-bit result is interpreted as signed, a completed result with the payload’s top bit set is negative. The packing itself does not discard or sign-normalize the payload.

## Behavior

### Initial context acquisition

Every invocation first calls F-62673223987f without arguments. The function then reads a 32-bit value at offset `0x298` from the returned address and retains that value as the context address.

This call and read occur even when the selector or payload will later make the request ineligible. There is no early return that avoids context acquisition for a zero payload, an effective selector of zero, or an effective selector of four.

There is no explicit null check on the provider result before the offset read.

The selector is then reduced to its low eight bits. Upper selector bits have no further effect within this function.

### Eligibility

The function reads the descriptor byte at offset `0x10`. Continuation requires all of the following:

1. The descriptor byte equals 7.
2. The payload is nonzero.
3. The effective selector is nonzero.
4. The effective selector is not 4.

The descriptor-byte check is first in the short-circuit eligibility expression. Consequently, a zero payload or excluded selector does not protect an invalid descriptor address from being read.

If eligibility fails, the function returns the non-completed result. It does not invoke the allocation, initialization, temporary-record processing, or submission dependencies.

A nonzero payload is accepted by this gate regardless of its sign. No range restriction other than nonzero is visible.

### Allocation and initialization attempt

For an eligible request, the function initializes the temporary record with the payload followed by the descriptor address.

It then calls F-8157a180d901 with the numeric argument `0x20`, or 32 decimal. The result is passed directly to F-d0d9c9d6a6d3 together with the descriptor address.

The established operation is a request with argument 32. Treating this as a request for a 32-byte allocation is plausible intent, but the dependency’s allocation contract is not supplied.

There is no explicit check of F-8157a180d901’s result before the initialization call. In particular, a zero result from that dependency is still passed to F-d0d9c9d6a6d3.

If F-d0d9c9d6a6d3 returns zero:

- No further dependency in the completed-path sequence is called.
- Neither explicit object-byte clearing occurs.
- The function returns the non-completed result.
- No explicit release of the allocation result appears in this function.

This does not establish a leak: the initializer may consume or release the supplied resource. Its behavior is unknown.

A nonzero initializer result becomes the object address used for all subsequent object operations. The function does not require it to equal the allocation result.

### Completed-path sequence

After a nonzero initialization result, the remaining operations occur in this order:

1. Read one byte from the retained context at offset `0x08`.
2. Call F-b5f4a3351c2f with the temporary record’s address, the effective selector, the retained context address, and the context byte just read.
3. Call F-46f0b3cb316e with the initialized object’s address plus `0x04` and the same temporary record’s address.
4. Call F-289ec4311c64 with the temporary record’s address.
5. Write zero to the object byte at offset `0x0C`.
6. Write zero to the object byte at offset `0x0D`.
7. Call F-7c3e30682ee7 with the retained context address and the initialized object address.
8. Return the completed result.

The temporary record is not restored between calls. Any changes made through its address by one dependency are available to the next dependency. In particular, F-46f0b3cb316e receives the record after F-b5f4a3351c2f has had an opportunity to modify it, and F-289ec4311c64 receives it afterward.

The two object bytes are cleared after the temporary-record calls, not before them. F-7c3e30682ee7 is invoked after both clearing writes. Its own effects may subsequently change those bytes, so their value at function return is not guaranteed without its contract.

The retained context address is not reloaded from the context-provider result. Earlier dependencies may alter global state or the memory behind that address. The late context-byte read observes the memory at that time, rather than a snapshot taken during initial context acquisition.

No result from the completed-path processing or submission calls is checked. If those calls return normally, the function reports completion even if a dependency internally encountered or encoded a failure.

## Side effects

### Explicit memory effects

Direct reads comprise:

- The 32-bit context-address field at provider-result offset `0x298`.
- The descriptor byte at offset `0x10`.
- On the completed path, the context byte at offset `0x08`.

Direct writes comprise:

- Initialization of the two-word temporary record on the eligible path.
- On the completed path, one zero byte at object offset `0x0C`, followed by one zero byte at offset `0x0D`.

The function performs no explicit direct write to the descriptor or retained context. Dependencies may do so.

### Lifetime and ownership

The temporary record belongs to this invocation. Its address is supplied to three dependencies. No persistent validity after the invocation is established; a compatible dependency contract must account for its temporary lifetime.

The function does not explicitly release the initialized object. It passes that object to F-7c3e30682ee7, but this alone does not prove ownership transfer.

F-289ec4311c64 is positioned like temporary-record cleanup, but its name and call position do not establish what it destroys, releases, or preserves.

No assumption is justified that any dependency preserves globals, leaves pointed-to memory unchanged, or leaves resources owned by this function.

### Preconditions and failure exposure

Normal execution requires:

- A normally returning context provider whose result permits the 32-bit read at offset `0x298`.
- A descriptor address permitting the byte read at offset `0x10`, even for requests that fail later eligibility checks.
- On the completed path, a retained context permitting the byte read at offset `0x08`.
- A nonzero initializer result permitting the two byte writes and all dependency-specific object accesses.

The visible function provides no validation, exception translation, rollback, synchronization, or recovery for violations of these conditions.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. They assume all reached memory accesses are valid and all reached dependencies return normally.

1. **High selector bits are ignored.**  
   With selector `0x12340004`, the effective selector is 4. After context acquisition and the descriptor-byte read, the function returns `0x0000000400000000`. The allocation dependency is not called, even if the descriptor byte is 7 and the payload is nonzero.

2. **A non-completed result can be nonzero.**  
   With effective selector 9 and a descriptor byte other than 7, the result is `0x0000000900000000`. The lower word, not the whole 64-bit value, distinguishes completion.

3. **Zero payload does not bypass the descriptor read.**  
   With payload zero, the descriptor byte is still read after context acquisition. If that read is valid, the result has the effective selector in the upper word and zero in the lower word. No allocation attempt occurs.

4. **Initializer failure preserves the non-completed return form.**  
   With descriptor byte 7, payload 23, and effective selector 2, suppose F-d0d9c9d6a6d3 returns zero. The result is `0x0000000200000000`. None of the subsequent processing calls, explicit object clears, or final submission call occurs.

5. **Allocation output is forwarded without a zero check.**  
   Under the same eligible inputs, suppose F-8157a180d901 returns zero. F-d0d9c9d6a6d3 is still called with that zero value and the descriptor address. Its return determines whether execution continues.

6. **Successful packing uses the payload, not the selector.**  
   With selector `0x00000102`, payload `0x12345678`, descriptor byte 7, and a nonzero initializer result, the completed result is `0x1234567800000001`, provided all subsequent calls return normally. The helper receives effective selector 2.

7. **Negative payloads pass the eligibility gate.**  
   With payload −1, effective selector 2, descriptor byte 7, and a completed path, the result bits are `0xFFFFFFFF00000001`.

8. **The context byte is sampled after initialization.**  
   If an earlier dependency changes the byte at retained-context offset `0x08`, F-b5f4a3351c2f receives the byte read after initialization. There is no earlier cached byte value.

9. **Clearing precedes submission, not necessarily final return state.**  
   On the completed path, writes of zero to offsets `0x0C` and `0x0D` occur in that order before F-7c3e30682ee7 is called. Acceptance must not require those bytes to remain zero after that dependency executes.
