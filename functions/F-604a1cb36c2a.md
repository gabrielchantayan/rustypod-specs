# F-604a1cb36c2a

## Purpose

F-604a1cb36c2a conditionally performs an initialization-like sequence using externally supplied references.

The function first retains an address from a control reference. It then separately uses the control reference to locate the byte governing its branch. If that tested byte is nonzero, the function returns two. If it is zero, the function calls one dependency twice, performs four 32-bit field writes, writes a one-byte marker to the initially retained control address, and returns zero.

**The branch-test address and final marker address are not unconditionally identical.** They arise from separate uses of the control reference. They coincide when that reference remains stable across those uses. The supplied representation does not establish their equivalence under intervening mutation or establish exact machine-level load timing.

“Initialization,” “success,” and “already initialized” are inferred interpretations. The established behavior is the conditional sequence of accesses, calls, writes, and return values described below.

## Behavior

### Control-address selection and branch

The supplied representation orders two control-reference uses before the branch:

1. An address is obtained and retained as the destination of a possible final marker write.
2. A separate use of the control reference locates the byte tested against zero.

There is no intervening dependency call. With an ordinary stable control reference, both uses identify the same byte. The source representation nevertheless does not justify specifying them as a single unconditional address selection.

This distinction describes the represented behavior, not a guarantee of two separate machine instructions or defined behavior under concurrent mutation. The excerpt does not establish whether, or how, distinct observations can occur on the actual target.

The branch tests zero versus nonzero, not zero versus one. Every nonzero byte value selects the immediate-return path, independently of character signedness.

### Nonzero-byte path

When the tested byte is nonzero, the function returns two.

It makes no dependency calls, performs none of the four field writes, and does not write the final marker. It does not need to consult the primary or secondary reference on this path.

There is no check that the initially retained marker address contains the same value as the tested byte. If the two control-reference uses identify different addresses, the byte at the test address determines the branch.

### First call and primary field updates

When the tested byte is zero, the function reads the primary reference and passes the resulting address, together with 72, to F-EXT-01.

After that call returns, it obtains and retains a primary base. The representation then separately uses the primary reference as the base for the 32-bit zero write at offset 64. The following 32-bit write of 16 uses offset 68 from the retained primary base.

Thus, three roles must remain distinct:

- The primary address passed to the first call.
- The primary base retained after that call.
- The primary base used by the separately expressed offset-64 destination.

The dependency may change the primary reference during the first call, so its argument need not equal either later base. No call intervenes between retaining the post-call base and the offset-64 write. With a stable reference during that interval, both primary field writes use the same base. Exact machine-level observations under mutation remain unresolved.

The primary offset-64 write precedes the primary offset-68 write. Neither precedes the first dependency call.

### Second call and secondary field updates

The second invocation of F-EXT-01 receives the retained post-first-call primary base plus 72 bytes, together with the numeric argument 72.

This address is not obtained from the secondary reference. It also does not require a fresh primary-reference observation. A later change to the primary reference does not, by itself, redirect this retained-base calculation.

After the second call returns, the function obtains and retains a secondary base. It then separately uses the secondary reference for a 32-bit zero write at offset 64. The following 32-bit write of 16 targets offset 68 from the retained secondary base.

Both dependency calls precede these secondary-reference uses. Either call may therefore affect the reference value subsequently observed.

As with the primary pair, stable secondary-reference state makes the two writes share one base. The representation does not establish that equivalence under mutation or prescribe exact machine-level load timing.

### Marker and completion

After both calls and all four field writes, the function writes the byte value one to the control address retained before the initial branch test. It then returns zero.

The function does not reload the control reference to select the marker destination. Redirecting that reference during a dependency call does not redirect the final marker write.

There is also no second control-byte test. A dependency’s change to the tested byte does not cause the remaining sequence to be skipped.

## Side effects

### Ordered direct effects

On a normally completed zero-byte path, the direct stores occur in this order:

1. Primary offset-64 destination: 32-bit zero.
2. Retained primary base plus 68: 32-bit 16.
3. Secondary offset-64 destination: 32-bit zero.
4. Retained secondary base plus 68: 32-bit 16.
5. Initially retained control address: one-byte value one.

The first dependency call precedes every direct store. The second dependency call occurs between the primary and secondary field pairs.

This order does not guarantee that all written values remain present at return. The second dependency call may overwrite primary fields. Later direct stores may overlap earlier destinations.

### Aliasing and reference changes

No disjointness checks are shown. In particular, the function does not establish that:

- Primary and secondary bases identify separate objects.
- The secondary base equals the retained primary base plus 72.
- Field destinations are disjoint from either control address.
- Field destinations are disjoint from reference-bearing locations.
- Dependency effects are confined to the addresses passed to them.

If a direct write overlaps a reference-bearing location used later, that write may affect later address selection. Retained addresses remain retained values; they are not automatically refreshed to match a changed reference.

Any final-state claim must therefore account for dependency effects and the complete ordering of overlapping accesses. A claim that both field pairs and the marker all remain intact requires suitable non-overlap and preservation assumptions.

### Ownership, lifetime, and failure

Addresses retained across calls must remain usable for later required accesses if execution is to complete normally. The function does not enforce their lifetime.
