# F-4026e44599a7

## Purpose

F-4026e44599a7 performs release-like accounting associated with a non-null address and an eight-byte metadata prefix. It validates a header, adjusts seven context-relative counters, and invokes dependencies with a captured context address and the metadata address.

Counter adjustment and dependency invocation are established behavior. Actual memory reclamation, ownership transfer, and synchronization are not established. “Release-like” describes inferred intent, not an ownership or lifetime guarantee.

A null input returns immediately. For a non-null input, rejection depends on the header values observed during validation, which occurs after an initial dependency call.

## Interface

**Input:** one address-valued argument represented as a 32-bit integer.

**Output:** no explicit return value. Normal completion returns control to the caller. Header rejection invokes a dependency identified as non-returning in the supplied representation.

The following descriptive labels are used:

- **P:** the supplied address.
- **C:** the context address captured after the initial dependency returns.
- **Q:** the masked header quantity captured before the first counter update.
- **R:** the masked header quantity obtained for the final counter update.

These labels are specification notation, not interface symbols.

### Metadata layout

For non-null P, the metadata-directed reads use this prefix:

| Address | Width | Interpretation |
|---|---:|---|
| P − 8 | 32 bits | Header validation and quantity extraction |
| P − 4 | 16 bits, unsigned | First metadata index |
| P − 2 | 16 bits, unsigned | Second metadata index |

The quantity mask is `0x3ffffffc`:

- Bits 2–29 contribute.
- Bits 0, 1, 30, and 31 do not contribute.
- The result ranges from zero to `0x3ffffffc`, inclusive, in multiples of four.
- A zero masked quantity is not itself grounds for rejection.

There are no separate payload-directed accesses. However, computed counter destinations can overlap the metadata prefix or bytes at P and above. Such overlap permits explicit counter reads and writes in those regions; the function does not check disjointness.

### Context-relative counter layout

All listed counter accesses are 32 bits wide.

| Address relative to C | Operation |
|---|---|
| `0x224 + 4 × first metadata index` | Subtract Q |
| `0x30c` | Subtract Q |
| `0x0e0 + 4 × second metadata index` | Subtract Q |
| `0x220` | Subtract Q |
| `0x310 + 4 × dependency-provided index` | Subtract one |
| `0x390` | Subtract one |
| `0x008` | Subtract R |

These formulas establish addresses, not array bounds, field independence, or intended object boundaries. No index bounds checks or overlap checks are present.

### Preconditions for normal execution

Normal execution requires that:

- The initial dependency returns.
- The context-pointer source is readable when accessed.
- Each metadata location is readable when accessed.
- Every computed counter location supports its required 32-bit read and write.
- The captured context and metadata remain usable through their later accesses and dependency calls.
- Address calculations and alignment are valid for the execution environment.
- Dependencies permit the subsequent operations to proceed.

These are environmental requirements, not checks performed by this function. It does not establish that P is an allocation, that C is non-null, that counters have sufficient values, or that indexed destinations belong to a particular object.

## Behavior

### Null input

If P is zero, the function returns immediately.

This path has no explicit memory accesses and no dependency calls.

### Initial dependency and context capture

For non-null P, the first action is a call to F-2fd8826557a4 with no explicit arguments.

After that call returns, the function reads the context-pointer source and captures C. Changes made by this dependency can therefore affect which context is selected. The dependency can also affect metadata later examined by the function; no preservation guarantee is supplied.

The captured C is used for the remaining explicit context operations and context arguments. There is no later explicit recapture of C. This does not mean that dependencies preserve the context-pointer source, the storage addressed by C, or metadata.

### Header validation

Validation uses the 32-bit header at P − 8.

The represented condition rejects when:

1. The header value observed by the zero comparison is zero; or
2. The first comparison does not reject, and the header value observed by the subsequent bit test has bit 0 set.

The condition is short-circuiting. Its representation contains separate header accesses for the zero comparison and the bit test. A stable header is consequently rejected if it is zero or odd. If the header changes between accesses, rejection depends on the individual observed values, not on one assumed snapshot.

On rejection, the function calls F-a817d8d58c10 with no explicit arguments. The supplied representation marks that call as non-returning. No normal continuation from rejection is established.

The initial dependency and context capture occur before rejection. No explicit counter updates occur before rejection. The initial dependency’s own effects remain unknown.

### Context dependency

After successful validation, the function calls F-c0fc6d033caa with C.

This call occurs before the metadata indices and accounting quantity used by the counter updates are read. Its effects can therefore influence those values and the counter contents.

Lock acquisition or entry into a protected region is possible inferred intent, not established behavior. The function does not revalidate the header after this call.

### First two quantity updates

The function reads the unsigned 16-bit index at P − 4 and forms the first indexed counter address, C + `0x224` + four times that index.

It then reads the header at P − 8 and masks it with `0x3ffffffc`, obtaining Q.

The following 32-bit read-modify-write operations occur in order:

1. Subtract Q from the first indexed counter.
2. Subtract Q from the counter at C + `0x30c`.

Q is retained for the next two quantity updates. Later changes to the header do not change these four uses of Q.

If the first indexed destination overlaps the header or another metadata field, its write can change subsequent reads of that storage. There is no separate metadata-directed write, but an aliased counter write is still an explicit write to the overlapping bytes.

### Next two quantity updates

After the preceding two writes, the function reads the unsigned 16-bit index at P − 2 and forms C + `0x0e0` + four times that index.

It then performs, in order:

1. Subtract Q from this second indexed counter.
2. Subtract Q from the counter at C + `0x220`.

Because the second index is read after the first two writes, overlap with those destinations can affect which counter is selected. The operation must not be modeled as capturing all metadata before accounting begins.

### Dependency-selected count updates

The function calls F-09dcb55e8e0a with no explicit arguments. Its returned integer supplies the index for C + `0x310` + four times that result.

The function then performs, in order:

1. Decrement the selected 32-bit counter by one.
2. Decrement the 32-bit counter at C + `0x390` by one.

No sign or range check is present for the returned index. A negative result is not explicitly rejected before address calculation.

These decrements occur even if Q is zero. This dependency’s effects on context, metadata, globals, and storage lifetime are unknown.

### Late quantity update

After the two count decrements, the function obtains R by reading the header at P − 8 again and applying `0x3ffffffc`.

It subtracts R from the 32-bit counter at C + `0x008`.

R need not equal Q. Intervening dependency effects, aliased counter writes, or permitted external mutation can change the header. There is no revalidation or equality check.

The representation establishes that this update follows the preceding count updates. It does not independently establish the physical ordering of the counter read and header read within this final read-modify-write expression.

### Final dependency sequence

After all seven explicit counter updates, the function calls:

1. F-cc6c9b4a0f68 with C and P − 8.
2. F-e586bff64fb7 with C.

If both return, the function returns normally.

The second argument to F-cc6c9b4a0f68 is the metadata address, not P. There are no subsequent explicit metadata or counter accesses by this function. Nevertheless, F-e586bff64fb7 still receives C after the preceding dependency returns; nothing establishes that the earlier call preserves the object addressed by C.

### Arithmetic and aliasing

The counter destinations hold 32-bit words. No saturation, insufficient-balance check, overflow report, or rollback is present.

The quantity subtractions use an unsigned 32-bit masked operand in the supplied representation. Their low-32-bit results correspond to subtraction modulo \(2^{32}\). The two one-unit decrements are represented using signed integer operations. A wrapping machine interpretation produces `0xffffffff` when decrementing zero, but portable signed-overflow semantics are not established by this representation.

Each unsigned metadata index is between 0 and 65,535. Multiplication by four is at most 262,140 and fits in 32 bits. This does not establish the validity of subsequent additions to C.

The dependency-provided index is not restricted to that unsigned 16-bit range. Its scaling, address arithmetic, and possible overflow require target-specific interpretation.

Counter destinations can coincide with one another or overlap metadata or payload storage. Updates are sequential: a later operation uses the storage contents then present, including earlier writes. No atomic or simultaneous seven-counter adjustment is established.

## Side effects

On a normally completing non-null path, the function explicitly performs seven 32-bit counter read-modify-write operations in the stated order.

It also performs metadata-directed reads and captures C after the initial dependency. There are no separate payload-directed accesses and no separate metadata-directed writes. Computed counter destinations are not checked for disjointness, so their reads and writes may access metadata or payload bytes.

Dependency effects are not limited by the supplied evidence:

- F-2fd8826557a4 can affect both context selection and subsequent validation inputs.
- F-c0fc6d033caa can affect accounting metadata and counters before their reads.
- F-09dcb55e8e0a can affect state before the count decrements and late header read.
- F-cc6c9b4a0f68 receives the metadata address and may affect its lifetime.
- F-e586bff64fb7 receives the captured C after the preceding dependency.

No call alone establishes ownership transfer, memory release, synchronization, or global preservation.

The operation is not explicitly transactional. If execution stops after some writes, no rollback is shown. Earlier writes may remain observable, subject to the unknown execution and concurrency model.

## Acceptance examples

These are conditional deductions from static evidence, not executed tests. Normal-path cases require valid accesses, defined address arithmetic, returning dependencies, and the stated preservation assumptions.

### Null input

Given P = 0, the function returns without explicit memory accesses or dependency calls.

### Validation observes zero

Given non-null P, a returning initial dependency, and a valid context-pointer read, if the header value observed by the validation zero comparison is zero, the function invokes F-a817d8d58c10.

The bit test is skipped. No explicit counter updates occur.

A zero header only at function entry is insufficient to guarantee this outcome: F-2fd8826557a4 executes before validation and may change it.

### Validation observes a set low bit

Given that the zero comparison observes a nonzero header and the subsequent bit test observes `0x00000005`, the function invokes F-a817d8d58c10 without explicit counter updates.

Equivalently, a header of `0x00000005` preserved through the initial dependency and both validation accesses is rejected. Its entry value alone does not establish rejection.

### Stable nonzero header with zero quantity

Suppose the header is `0x00000002` at both validation accesses and both quantity reads. Assume distinct counter destinations disjoint from metadata and no unrelated counter mutations.

Validation succeeds. The five quantity updates subtract zero, but still perform their counter accesses. The two count updates subtract one. Both final dependencies are invoked in order.

### Masked high bits

Suppose the header remains `0xc0000026` through validation and accounting, with valid distinct counter destinations disjoint from metadata.

The masked quantity is `0x24`, or 36. The five quantity counters decrease by 36 under 32-bit subtraction, and the two count counters decrease by one where those decrements are defined. Bits 30, 31, and 1 do not contribute.

### Header changed by a dependency

Suppose Q is 32. F-09dcb55e8e0a changes the header so its masked quantity becomes 64, and subsequent operations preserve that header until the late read.

With otherwise valid, non-overlapping destinations, the first four quantity updates subtract 32. The update at C + `0x008` subtracts 64. The function does not reconcile the difference or repeat validation.

### Counter destinations coincide

Suppose both metadata-selected destinations identify the same word, no other relevant overlap exists, Q is 16, and dependencies do not alter that word.

The word undergoes two separate subtractions of 16. It is not updated only once.

### Counter destination overlaps payload

Suppose the first computed counter address equals P and supports a valid 32-bit access.

The first counter update explicitly reads and writes the four bytes beginning at P. No dedicated payload operation is necessary for this effect. The function contains no disjointness check that would reject the overlap.

### Insufficient counter value

A quantity counter initially containing 8, with Q = 16 and no intervening mutation, receives the 32-bit result `0xfffffff8`.

Under a wrapping 32-bit interpretation, a count counter initially zero becomes `0xffffffff` when decremented. This second result remains conditional on the target’s signed arithmetic interpretation.

Neither case has an explicit insufficient-balance error branch.
