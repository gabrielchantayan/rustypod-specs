# F-70e7511e4343

## Purpose

F-70e7511e4343 performs a two-stage operation using a 32-bit value held in a caller-supplied object. Both stages must return a value other than the distinguished failure result before the function performs two additional dependency calls, marks a byte in the object, invokes a final dependency on an interior address, and returns success.

The established behavior is an ordered sequence of calls, object-field reads, and one explicit byte write. The meanings of the operation selectors, the object’s fields, and the dependency operations are not established.

The function reports success as the 32-bit value 1 and failure as the 32-bit value 0. These results describe its own branch decisions. They do not establish that every dependency completed a semantically successful operation, because only the first two dependency results are inspected.

2. **Auxiliary value.** An opaque 32-bit value forwarded unchanged to each of the first two dependency calls. The function does not directly dereference or interpret it.

### Second preliminary stage

| Position | Value |
|---|---|
| 1 | The newly read value from object offset 8 |

There is no explicit rollback of the first stage or of any partial effects of the second stage.

### Final sequence

If both preliminary results differ from 0xFFFFFFFF, the function performs the following operations in order:

1. Reads the 32-bit field at object offset 8 and calls F-3cd5bc80f1ac with that value and selector 131.
2. After that call returns, reads the same field again and calls F-3cd5bc80f1ac with the newly read value and selector 2.
3. After that call returns, writes the 8-bit value 1 at object offset 12.
4. Calls F-5bcae2eff9a7 with the address at object offset 16.
5. After that call returns, returns the 32-bit value 1.

The results of the two F-3cd5bc80f1ac calls and the F-5bcae2eff9a7 call do not participate in the function’s success/failure decision.

The final selectors are used in the opposite order from the preliminary selectors: the preliminary stages use 2 and then 131; the subsequent pair uses 131 and then 2. The reason for this ordering is unknown.

### Fresh reads and intervening effects

There are up to four distinct reads of the field at offset 8, one immediately before each reached call that consumes it. The function does not explicitly cache a single value for the entire operation.

Consequently, if a dependency changes that field and the object remains valid, a later call receives the changed value. This is especially relevant because both preliminary calls receive the object address directly. Other dependencies might also affect the object through aliases or global state; their implementations are unavailable.

The explicit byte write precedes the final dependency call. The final call therefore occurs after that write, but a normal return of 1 does not by itself prove that the byte still contains 1: the final dependency could modify it through an alias.

## Side effects

The function does not explicitly clear that byte on entry or on either failure path. Thus, a return of 0 does not mean the byte is zero. It may retain an earlier value or have been changed by a dependency.

The function also exposes state through dependency calls:

- F-5bf0cc325ea6 receives the object address and auxiliary value on each reached invocation.
- F-3cd5bc80f1ac receives the current field value and a selector.
- F-5bcae2eff9a7 receives an interior address derived from the object.

No explicit allocation, deallocation, ownership transfer, lock operation, or global write is visible in this function. This does not establish their absence inside dependencies.

Ownership remains documented_only. Passing the object address or its interior address does not, by itself, prove borrowing, retention, transfer, or release. Safe normal execution requires any dependency effects to leave all subsequently accessed storage valid.

The sequence is not established to be atomic or transactional. Failure after a successful first stage can leave externally visible partial effects.
