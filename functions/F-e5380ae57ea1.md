# F-e5380ae57ea1

## Purpose

F-e5380ae57ea1 traverses an object’s entry storage, invokes dependencies for each visited entry, submits the object’s current storage address to another dependency, and then performs allocation-related accounting and header processing.

The established behavior consists of memory accesses, arithmetic updates, branches, and dependency calls. Destruction of an object followed by allocator bookkeeping and release is inferred intent, not an established ownership contract. No supplied dependency implementation establishes deallocation, synchronization, or preservation of global state.

A null object address returns without observable work. A non-null address must support all accesses actually reached, including metadata preceding the object. There is no recoverable error result.

## Interface

**Input:** one object address.

**Output:** no return value. Observable results are memory accesses, direct accounting writes, dependency invocations, and any effects of those dependencies.

The supplied representation uses 32-bit address-bearing values and 32-bit integer words. The relevant object layout is:

| Offset from object address | Width | Established use |
|---|---:|---|
| −4 bytes | 32 bits | Displacement for deriving the allocation anchor |
| +0 bytes | Signed 32 bits | Entry-loop bound |
| +12 bytes | 32 bits | Entry-storage address |

Each entry occupies 12 bytes:

| Offset within entry | Width | Established use |
|---|---:|---|
| +0 bytes | 32 bits | Argument to F-841dc33ee157 |
| +4 bytes | 32 bits | Argument to F-94cb53877c15 |
| +8 bytes | 32 bits | Not directly accessed by this function |

The **allocation anchor** is the object address minus the displacement read at object offset −4. Its relevant preceding metadata is:

| Offset from allocation anchor | Width | Established use |
|---|---:|---|
| −16 bytes | 32 bits | Header, validation bits, and masked accounting amount |
| −12 bytes | Unsigned 16 bits | First context-table index |
| −10 bytes | Unsigned 16 bits | Second context-table index |
| −8 bytes | 32 bits | Global-accounting amount |

A global location contains an accounting-base address. The function reads that location multiple times rather than obtaining one base for all accounting accesses. Another global location is used to obtain the context address after F-2fd8826557a4 returns.

Address calculations use the represented 32-bit target widths. A numerically derived address is not thereby valid. Accessible storage, appropriate alignment, and compatibility with dependency requirements are caller or environment preconditions; this function does not validate them.

## Behavior

### Null handling and entry traversal

An initially null object address returns immediately. No entry-storage field, global accounting location, allocation metadata, or dependency is accessed.

For a non-null object, the entry-storage address at offset +12 is captured before evaluating the first loop condition. Consequently, this field is read even when the count is zero or negative.

Traversal starts at entry index zero. Before each iteration, the index is compared against the signed 32-bit count at object offset +0. The count is reread for every condition, including the condition that terminates traversal.

Each accepted iteration has this order:

1. Read the current entry’s first 32-bit word.
2. Invoke F-841dc33ee157 with that word.
3. After that dependency returns, read the current entry’s second 32-bit word.
4. Invoke F-94cb53877c15 with the second word.
5. Advance the captured traversal address by 12 bytes and advance the index by one.

The third entry word is not directly read.

The two arguments for an entry are not captured together. F-841dc33ee157 can affect the later second-word read if it modifies that memory. Either entry dependency can affect subsequent traversal by changing the object’s count. Changing the object’s storage-address field does not redirect the already captured traversal address.

Zero and negative counts produce no entry-level dependency calls. No storage-size check establishes that a positive count is backed by enough records.

### Final storage-address invocation

After traversal ends, the function rereads object offset +12 and invokes F-94cb53877c15 with that value.

This invocation occurs even if no entries were visited. There is no explicit null check on its argument. The value may differ from the storage address captured before traversal.

The function continues to access the object and its allocation metadata after this dependency returns. The dependency must not be assumed to preserve or release any particular memory. If it invalidates storage needed by later operations, the supplied function provides no recovery.

### Global-base capture and allocation metadata

Immediately after the storage-address invocation returns, the function reads the global accounting-base location and captures its value. This captured base will supply the destination of the upper-word accounting write.

A second null check of the object address follows that capture. The function has not reassigned its local object address, so an initially non-null argument has no ordinary path through this second check’s return branch. In particular, this check is not a check for dependency-induced invalidation of the object.

The function then:

- Reads the displacement at object offset −4 and derives the allocation anchor.
- Reads the 32-bit accounting amount at anchor offset −8.

These metadata operations occur after the initial accounting-base capture and before the later accounting-base rereads.

### Global accounting: distinct bases and ordered accesses

The accounting update must not be described as operating on a single stable structure without an additional stability assumption.

There are four distinct reads of the global accounting-base location during this stage. In order:

| Base observation | Subsequent use |
|---|---|
| Initial capture, immediately after the storage-address dependency | Upper-word write destination at captured base +60 |
| Next read, after the allocation amount is read | Lower-word source at that base +56 |
| Next read | Formation of the upper-word source address at that base +60 |
| Next read | Lower-word write destination at that base +56 |

The established sequence is:

1. Capture the initial accounting base.
2. Perform the second object-null check and the allocation-metadata reads described above.
3. Reread the accounting base and read the lower source word at offset +56.
4. Reread the accounting base and retain the resulting upper source address at offset +60.
5. Reread the accounting base and write the lower result at offset +56 of that newly observed base.
6. Read the upper source word through the address retained before the lower write.
7. Write the upper result at offset +60 of the initially captured base.

Thus, the upper source **address** is established before the lower write, but the upper source **contents** are read afterward. A lower write that overlaps that retained source location can affect the upper value subsequently read. Changing the global accounting base during the lower write does not redirect the already retained upper source address or the initially captured upper destination.

For the arithmetic, let:

- \(S\) be the unsigned 32-bit amount read from anchor offset −8.
- \(L\) be the lower source word.
- \(H\) be the upper source word read after the lower write.
- \(b=1\) when \(L<S\), and \(b=0\) otherwise.
- \(s=0\) when bit 31 of \(S\) is clear, and \(s=-1\) when it is set.

The stored results, reduced to 32 bits, are:

\[
\text{lower result}=L-S \pmod {2^{32}}
\]

\[
\text{upper result}=H-(s+b) \pmod {2^{32}}
\]

When bit 31 of \(S\) is clear, the upper result subtracts the borrow. When that bit is set, the upper result adds one minus the borrow.

Even with a stable base, this is not ordinary unsigned 64-bit subtraction for every possible amount. With differing base observations, the source and destination words need not even belong to the same accounting structure.

These writes precede header validation. A later rejection does not undo them.

### Context selection and special anchor

After the global accounting update, the function invokes F-2fd8826557a4 without explicit arguments. It then reads and captures the context address through a global location.

The context selection therefore occurs after any effects of that dependency. Later operations use the captured context address; they do not reselect it from the global location.

If the allocation anchor equals numeric address 8, the function returns at this point. It does not validate a header, invoke the accepted-header dependencies, or perform context accounting.

This special case does not bypass earlier work. The amount at anchor offset −8 has already been read, the global accounting writes have occurred, F-2fd8826557a4 has returned, and the context address has been read. For anchor 8, the earlier amount read is at numeric address zero. Whether that access can succeed is documented_only.

### Header validation

For an anchor other than 8, the header address is anchor −16.

The header is rejected if:

- The first validation read yields zero; or
- The first read is nonzero and a second validation read has bit 0 set.

The second read occurs only if the zero test does not reject. The function does not capture one header value and apply both tests to it. For example, a nonzero first observation followed by a zero second observation passes these two tests, because the second observation is tested only for bit 0.

Rejection invokes F-a817d8d58c10, represented as non-returning. No recovery path or error return is supplied. All earlier entry processing, the final storage-address invocation, global accounting, and context-selection work have already occurred.

### Accepted-header context updates

After validation accepts, the function invokes F-c0fc6d033caa with the captured context address.

After that dependency returns, it reads the first unsigned 16-bit index at anchor −12. It then rereads the header and derives:

\[
A=\text{header}\mathbin{\&}\texttt{0x3ffffffc}
\]

Only bits 2 through 29 contribute. The possible masked amount ranges from zero through `0x3ffffffc`. Validation does not guarantee a nonzero masked amount.

Using the captured context address, the function performs these 32-bit read-modify-write operations in order:

| Order | Context-relative location | Update |
|---:|---|---|
| 1 | \(548+4\times\text{first index}\) | Subtract \(A\) |
| 2 | 780 | Subtract \(A\) |
| 3 | \(224+4\times\text{second index}\) | Subtract \(A\) |
| 4 | 544 | Subtract \(A\) |

The second unsigned 16-bit index is read from anchor −10 after the update at context offset 780 and before its indexed update. Earlier writes can therefore affect that index if the relevant storage overlaps.

The function next invokes F-09dcb55e8e0a without explicit arguments. Its result supplies the index for the remaining indexed count update:

| Order | Context-relative location | Update |
|---:|---|---|
| 5 | \(784+4\times\text{returned index}\) | Decrement by one |
| 6 | 912 | Decrement by one |
| 7 | 8 | Subtract a freshly read and masked header amount |

The amount for the final subtraction is obtained by rereading the retained header address and applying `0x3ffffffc` again. It can differ from \(A\), including because of intervening writes or dependency effects. No second header validation is performed.

Finally, the function invokes F-cc6c9b4a0f68 with the captured context address and header address. If that invocation returns, it invokes F-e586bff64fb7 with the captured context address.

No index-range validation, saturation, underflow rejection, or rollback is shown. Updates to overlapping locations are sequential operations on the values present at each access, not independent calculations from an initial snapshot.

## Side effects

Direct writes comprise:

- The lower global-accounting result at the destination selected by a late global-base reread.
- The upper global-accounting result at the destination selected by the initial base capture.
- The seven context accounting updates on the accepted-header path.

These are descriptions of write destinations, not proof that distinct regions are modified. Address overlap can make a write affect other fields or a later read.

The function does not explicitly clear the object, reset its count, erase its storage-address field, clear entry records, or mark the header released. Such effects could nevertheless arise through aliasing or dependencies.

Ownership transfer, deallocation, lock acquisition, and lock release are not established. Repeated invocation is not established as safe.

There is no transactional boundary. If a dependency fails to return or an access fails, prior effects are not locally reversed.

## Acceptance examples

These are conditional static expectations, not executed tests. Each assumes that reached accesses are valid and preceding dependencies return unless stated otherwise.

### Null and empty inputs

A null object causes immediate return without dependency calls or accounting accesses.

A non-null object with count zero still has its storage-address field read before the first loop condition and reread for F-94cb53877c15 afterward. No entry-level invocation occurs. Allocation processing follows. A negative count has the same loop-skipping behavior.

### Entry mutations

With a stable count of two, the entry-stage calls are F-841dc33ee157 and F-94cb53877c15 for the first entry, then the same pair for the second entry, then F-94cb53877c15 for the reread storage address.

If the first dependency changes the current entry’s second word, the second dependency receives the later-read word. If a dependency reduces the count to one during the first iteration and it remains one, no second entry is visited.

### Distinct accounting-base observations

Conditionally, if the four accounting-base reads yield addresses \(B_0,B_1,B_2,B_3\), respectively:

- The lower source is read from \(B_1+56\).
- The upper source address is retained as \(B_2+60\).
- The lower result is written to \(B_3+56\).
- Only afterward is the upper source read from \(B_2+60\).
- The upper result is written to \(B_0+60\).

Equality of these bases is not a prerequisite encoded by the function. This example does not assert that differing observations are possible under every execution environment or that concurrent mutation is supported.

### Accounting arithmetic

With a stable base, non-overlapping accounting words, \(L=5\), \(H=9\), and \(S=7\), the lower result is `0xfffffffe` and the upper result is 8.

Under the same conditions, with \(L=0\), \(H=9\), and \(S=\texttt{0x80000000}\), the lower result is `0x80000000` and the upper result remains 9.

### Rejection and masked amounts

If the first validation read is zero, F-a817d8d58c10 is invoked after global accounting but before accepted-header context updates.

A stable header of `0xc0000022` passes validation and supplies masked amount 32. If it remains unchanged, each amount-based context subtraction uses 32; the two count updates each decrement by one.

A stable header of 2 also passes validation, but its masked amount is zero. Amount-based updates still occur, and the two count updates still decrement by one.

## Uncertainties

The following remain documented_only:

- Complete object type, platform ABI, byte order, and alignment requirements.
- Memory ownership and allocation lifetime.
- Validity of the numeric-zero access on the special-anchor path.
- Stability requirements for the global accounting base and context-selection globals.
- Permitted aliasing, concurrent mutation, reentrancy, and synchronization rules.
- Actual context-table capacities and valid index ranges.
- Range and interpretation of the result from F-09dcb55e8e0a.
- Meaning of header flags and the excluded accounting bits.
- Whether amounts with bit 31 set are valid inputs.
- Dependency behavior for null values, invalid addresses, or invalidated memory.
- Behavior if F-a817d8d58c10 unexpectedly returns.
- Runtime fault behavior and language-level guarantees for invalid or overflowing address calculations.

None of these unknowns authorizes an assumption that dependencies preserve globals, retain storage, release storage, or make this operation safe to repeat.
