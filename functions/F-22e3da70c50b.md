# F-22e3da70c50b

## Purpose

F-22e3da70c50b conditionally updates a destination record using a second, address-bearing input and two identified transformation dependencies. A 16-bit discriminator at the start of the destination determines whether the routine performs a basic update, an extended update, or no explicit update.

The established behavior consists of dependency calls, their ordering, and fixed-width destination writes. The meanings of the fields and the complete behavior of the dependencies are not established.

The extended path stores two 32-bit dependency results as sign-extended, two-word values. Both active paths also transform one 16-bit destination field and store three further 32-bit dependency results.

## Behavior

### Discriminator selection

The routine first reads the 16-bit destination discriminator and compares it with 2.

- If that read equals 2, execution takes the extended path.
- Otherwise, the routine reads the discriminator again and compares that read with 1.
- If the second read equals 1, execution takes the basic path.
- Otherwise, the routine returns without invoking any dependencies or performing explicit destination writes.

Thus, for a stable discriminator:

| Value | Path |
|---:|---|
| 1 | Basic |
| 2 | Extended |
| Any other value | Immediate return |

There are two discriminator evaluations on the non-2 route in the supplied body. The contract does not replace them with a single cached read or promise atomic observation under concurrent modification.

Once an active path is selected, the routine does not explicitly read the discriminator again.

### Shared prefix of both active paths

Both active paths perform the following operations in order:

1. Invoke the unidentified external dependency with destination address `+0x30`, source address `+0x20`, and third argument 16.
2. After that invocation returns, invoke the same dependency with destination address `+0x40`, source address `+0x54`, and third argument 16.
3. After the second invocation returns, read the 16-bit destination field at `0x38` and pass its value to F-0ec8efa9c769.
4. Retain the 16-bit result of F-0ec8efa9c769.
5. Store result bits 7–0 into destination byte `0x38`.
6. Store result bits 15–8 into destination byte `0x39`.

The last two operations explicitly establish low-byte-first layout for this transformed field. They are separate stores, with the low-byte store preceding the high-byte store; no atomic 16-bit replacement is promised.

The transformation input is the destination field’s value **after both external calls**. It is not necessarily the field’s value on entry. Even though `0x38` lies in the first call’s apparent destination region, the second call occurs before the read and may have relevant effects under aliasing or an unknown dependency contract.

The recovered input type for this field is a signed 16-bit short. Its exact argument promotion or register-extension convention is not established. The stored result is determined by the retained 16-bit result’s bit pattern.

### Extended-only updates

After the shared prefix, the extended path performs two additional dependency calls and paired writes.

First:

- Invoke F-4055be9c3f18 with source address `+0x36`.
- Retain its result as a signed 32-bit value.
- Store the result’s 32-bit pattern at destination `0x58`.
- Store its arithmetic sign-extension word at destination `0x5C`.

Second:

- Invoke F-4055be9c3f18 with source address `+0x40`.
- Retain its result as a signed 32-bit value.
- Store the result’s 32-bit pattern at destination `0xA8`.
- Store its arithmetic sign-extension word at destination `0xAC`.

Each sign-extension word is:

- `0x00000000` when the corresponding result is nonnegative;
- `0xFFFFFFFF` when the corresponding result is negative.

The low-word write precedes the sign-extension-word write. The first pair is completed before the second dependency invocation begins.

These operations construct the low and high words of a sign-extended 64-bit representation. They are not established as single 64-bit stores. Native byte order within each 32-bit store is not specified by the body.

### Common trailing updates

After the shared prefix and any extended-only updates, both active paths perform these operations:

| Order | Dependency invocation | Explicit write after return |
|---:|---|---|
| 1 | F-4055be9c3f18 with source address `+0x48` | Store the 32-bit result at destination `0x0C` |
| 2 | F-4055be9c3f18 with source address `+0x4C` | Store the 32-bit result at destination `0x10` |
| 3 | F-4055be9c3f18 with source address `+0x50` | Store the 32-bit result at destination `0x1C` |

Each write occurs before the next dependency invocation. The routine then returns.

The three results are stored as 32-bit patterns without the explicit sign-extension words used by the extended-only updates.

## Side effects

### Explicit mutations

The routine’s explicit writes are limited to:

- destination bytes `0x38` and `0x39`;
- destination words at `0x0C`, `0x10`, and `0x1C`;
- on the extended path only, destination words at `0x58`, `0x5C`, `0xA8`, and `0xAC`.

This list does not bound dependency side effects.

There is no explicit write to the discriminator or source memory. Nevertheless, dependency behavior and source/destination aliasing may make additional changes observable.

### Ordering and partial completion

The operation is not transactional. Earlier dependency effects and writes precede later calls. There is no rollback or explicit cleanup path.

If an invocation fails to return normally, the later operations are not reached by normal sequential execution. The body provides no evidence that earlier mutations would be undone.

No explicit validation is performed for null addresses, record size, alignment, overlap, field ranges, or dependency results.

### Ownership and global state

The body contains no explicit allocation, deallocation, ownership transfer, or global-variable access.

That does not establish any corresponding guarantee for the dependencies. Their effects on memory ownership, global state, or other observable state remain unknown. In particular, the two address-taking dependencies cannot be assumed to be read-only or non-retaining from this body alone.
