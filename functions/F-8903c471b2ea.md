# F-8903c471b2ea

## Purpose

F-8903c471b2ea operates on a six-record region obtained through a dependency. It searches for the first record matching a two-part key, conditionally invokes an external transfer operation to close the resulting gap, and then searches for a position at which to write a candidate record.

The insertion decision is delegated to F-bf17c96cba49. A negative result causes insertion at the currently examined position. If all six results are nonnegative, the function returns without writing the candidate.

**Inferred intent:** maintain a bounded, ordered collection with replacement of an existing key. This interpretation depends on the comparison and external transfer dependencies. The supplied evidence does not establish their implementations, the ordering relation, or an empty-record convention.

The function is not established to be transactional. Removing a matching record does not guarantee that the candidate will subsequently be inserted.

## Interface

The supplied interface has five arguments:

| Argument | Width and interpretation | Role |
|---|---|---|
| Object address | 32-bit address-bearing value | Supplies an embedded dependency input at byte offset 44 and a one-byte update location at byte offset 102. |
| Selector | Unsigned 32-bit integer | Compared, without narrowing, against a stored unsigned byte during duplicate detection. Only its low eight bits enter the candidate. |

The address-bearing arguments and computed addresses require an execution environment in which the indicated accesses are valid. There is no visible null, alignment, capacity, or arithmetic-overflow check.

### Output

There is no explicit return value. Observable results consist of dependency calls and memory effects.

There is no explicit status distinguishing:

- Successful insertion.
- No acceptable insertion position.
- Removal followed by no insertion.
- A dependency failure that manifests through behavior outside this body.

### Candidate representation

Before calling any dependency, the function constructs a local candidate occupying three consecutive 32-bit words, totaling 12 bytes:

| Candidate offset | Contents |
|---|---|
| 0–3 | Primary key. |
| 4–7 | Packed word described below. |
| 8–11 | Payload. |

The packed word has these logical bit fields:

- Bits 0–7: selector bits 0–7.
- Bits 8–15: primary-key bits 8–15.
- Bits 16–31: all 16 auxiliary-value bits.

Consequently, primary-key bits 16–31 do not survive in this packed word, although the complete primary key remains in the first word. Selector bits 8–31 do not enter the candidate.

On a little-endian target, candidate byte offsets 4, 5, and 6–7 respectively contain the narrowed selector, the selected primary-key byte, and the auxiliary value. The supplied fragment establishes the packed word’s bit composition; little-endian byte interpretation is a target assumption, not independently demonstrated here.

## Behavior

### 1. Obtain the record region

The function calls F-702f08e79f1a with the object address plus 44 bytes.

It treats the returned 32-bit value as a storage base. The six-record region begins 20 bytes after that base. Each record is 12 bytes, so the region spans 72 bytes.

For a zero-based record index from 0 through 5:

- The first 32-bit word is at record offset 0.
- The selector byte examined during duplicate detection is at record offset 4.
- The remaining two 32-bit words occupy offsets 4 and 8.

The storage base and record-region address are retained for subsequent operations. There is no visible second lookup after dependency calls.

No validity check is performed on the returned address.

### 2. Search for the first matching record

Records are examined in increasing index order, starting at index 0 and ending at index 5.

At each record, the function first reads the unsigned byte at offset 4 and compares it with the full unsigned 32-bit selector argument.

Only if that comparison succeeds does it read the record’s first 32-bit word and compare it with the primary key. The first record satisfying both conditions is selected. Later records are not searched once a match is found.

This establishes two important boundaries:

- A selector greater than 255 cannot match any record during this search, even if its low byte matches the stored byte.
- For a selector mismatch, this function does not perform the associated first-word key read at that record.

If no record matches, processing proceeds directly to insertion-position selection. No tail-clearing write or removal-transfer call occurs on that path.

### 3. Process a matching record

If the matching record has index 0 through 4, the function calls the external transfer dependency with:

- Destination: the matched record.
- Source: the immediately following record.
- Byte count: 12 multiplied by the number of records after the match.

The resulting byte counts are:

| Match index | Byte count |
|---|---:|
| 0 | 60 |
| 1 | 48 |
| 2 | 36 |
| 3 | 24 |
| 4 | 12 |

For a match at index 5, this transfer call is omitted.

The source and destination ranges overlap for match indices 0 through 3. Correct left-shifting therefore requires overlap-safe transfer semantics; those semantics are not established by the supplied dependency implementation.

After the transfer call returns, or immediately for a match at index 5, the function writes a zero-valued 16-bit quantity at storage-base offset 86.

This location is record-region offset 66: byte offset 6 within record 5. On a little-endian target, it is the auxiliary-value portion of that record’s packed second word. The function does not clear the complete final record, its primary key, its selector byte, or its payload.

This halfword write occurs whenever a matching record was found, regardless of whether a later insertion succeeds.

### 4. Search for an insertion position

The insertion search always begins at record 0. It does not begin at the removed record’s index.

At each index in increasing order, the function calls F-bf17c96cba49 with:

1. The address of the local 12-byte candidate.
2. The address of the current record.

The result is interpreted as a signed 32-bit integer.

- A negative result selects the current index for insertion.
- Zero and positive results cause the search to continue.
- After a nonnegative result at index 5, the function returns.

There are at most six comparison calls. There are fewer if an earlier result is negative.

The caller performs no visible record-content filtering before these calls. In particular, it does not independently identify empty records or skip records based on their keys, selector bytes, or auxiliary values.

The candidate is passed by address. The supplied interface does not establish that F-bf17c96cba49 treats either argument as read-only. If it modifies the candidate or record storage, later behavior can reflect those modifications.

### 5. Insert at the selected position

For a selected index, the function first calls the external transfer dependency with:

- Destination: the record immediately after the selected record.
- Source: the selected record.
- Byte count: 12 multiplied by the number of records after the selected index.

The byte counts are again 60, 48, 36, 24, 12, and 0 for indices 0 through 5.

Unlike the removal path, insertion at index 5 still invokes the dependency, with a zero byte count and a destination at the end of the six-record region.

For selected indices 0 through 3, the nonempty source and destination ranges overlap. The intended right-shift interpretation therefore also depends on overlap-safe transfer behavior.

After that call returns, the function writes the selected record in this order:

1. Candidate first word to record offset 0.
2. Candidate packed second word to record offset 4.
3. Candidate third word to record offset 8.

These writes use the candidate’s then-current contents, not an independently preserved immutable copy.

Finally, the function writes the byte value 1 at object offset 102 and returns.

If the external transfer behaves as an overlap-safe byte move, this insertion preserves records before the selected index, shifts subsequent retained records right by one position, and discards the previous final record. That outcome is conditional on dependency behavior.

## Side effects

### Direct memory effects

The body directly performs only the following writes to externally addressed storage:

- A zero-valued 16-bit write at storage-base offset 86, but only after finding a matching record.
- Three consecutive 32-bit record writes, but only after a negative comparison result.
- A one-byte write of 1 at object offset 102, after those three record writes.

The function does not directly clear the object’s update byte on entry or on a no-insertion return.

Absence of a direct write does not establish that a dependency leaves the same memory unchanged.

### Call ordering

The observable call and write sequence is:

1. Construct candidate locally.
2. Call F-702f08e79f1a.
3. Search for a matching record.
4. If matched before the final record, call the removal transfer.
5. If matched anywhere, perform the tail halfword clear.
6. Call F-bf17c96cba49 in index order until selection or exhaustion.
7. If selected, call the insertion transfer.
8. Write the candidate’s three words.
9. Write the object update byte.

No rollback is visible. In particular, removal-related effects precede all insertion comparisons and remain possible even when no comparison selects a position.

### Ownership and lifetime

No direct allocation, deallocation, or ownership transfer is visible.

The candidate resides in local storage whose lifetime ends when this function returns. Its address is exposed to F-bf17c96cba49. Safe retention or later use of that address is not established.

The ownership and lifetime of storage returned by F-702f08e79f1a are unknown. Successful completion requires that storage remain usable for the accesses and dependency calls actually performed.

Nothing in this body establishes that dependencies preserve globals, refrain from releasing memory, or avoid modifying the object or record region.
