# F-d4e440af2e49

## Purpose

F-d4e440af2e49 conditionally updates accounting associated with an address whose preceding eight bytes contain metadata, then delegates processing of that metadata address.

For a nonzero input that passes header validation, its direct accounting effects are five size subtractions and two count decrements. Four size subtractions share one masked header value; the fifth uses a later header read. Two metadata indices and one dependency-returned index select some of the affected fields.

**Inferred intent:** removal of a tracked allocation from accounting, followed by release-related processing. Actual memory release, ownership transfer, synchronization, and the domain meaning of the accounting fields are not established.

## Interface

### Input and return

The function accepts one address-valued input represented as a 32-bit integer in the supplied material.

- A zero input returns immediately.
- A nonzero input is used to access metadata immediately before that address.
- There is no explicit return value.
- Normal completion follows the return of the final dependency.
- Header rejection invokes a dependency annotated as non-returning.

The function has no direct payload access at or beyond the input address. Dependencies may access additional storage.

### Metadata layout

For a nonzero input, the directly accessed metadata is:

| Offset from input address | Width | Interpretation in this function |
|---|---:|---|
| −8 | 32 bits | Header used for validation and masked subtraction amounts |
| −4 | 16 bits, unsigned | First accounting index |
| −2 | 16 bits, unsigned | Second accounting index |

The metadata address passed to a later dependency is the input address minus eight.

Both metadata indices are zero-extended before multiplication by four. Each therefore ranges from 0 through 65,535, and its scaled displacement ranges from 0 through 262,140. The multiplication alone fits within 32 bits; this does not establish that adding it to the context address is safe.

### Captured context and accounting locations

After the first dependency returns, the function reads a global context reference and retains the resulting address. All subsequent explicit context accesses and context-taking calls use this captured address.

The directly updated locations are:

| Offset from captured context | Field width | Direct update |
|---|---:|---|
| `0x224 + 4 × first metadata index` | 32 bits | Subtract first masked amount |
| `0x30C` | 32 bits | Subtract first masked amount |
| `0x0E0 + 4 × second metadata index` | 32 bits | Subtract first masked amount |
| `0x220` | 32 bits | Subtract first masked amount |
| `0x310 + 4 × dependency-returned index` | 32 bits | Decrement by one |
| `0x390` | 32 bits | Decrement by one |
| `0x008` | 32 bits | Subtract later masked amount |

These are observed address formulas, not established array boundaries. No context extent or accepted index range is supplied.

### Preconditions for normal completion

Normal completion requires:

- Readable metadata at each actual metadata access.
- A readable global context-reference location when it is accessed.
- Valid storage at each computed accounting address when read or written.
- A captured context that remains usable for later accesses and calls.

The function does not visibly enforce these requirements. In particular, a nonzero input is not itself evidence of a valid object or valid metadata.

## Behavior

### Null input

A zero input returns before all dependency calls, metadata reads, context-reference reads, and accounting writes.

This behavior does not depend on the contents of any metadata or global state.

### Preparation precedes validation

For a nonzero input, the first operation is a call to **F-2fd8826557a4**, with no explicit arguments.

Only after this call returns does the function read the global context reference and capture the context address. The dependency may therefore affect which context is captured.

The header has not yet been validated at this point. Neither its entry value nor the entry value of the global reference determines what later reads will observe: preservation by F-2fd8826557a4 is not established.

If this dependency does not return normally, context capture, header validation, and all subsequent direct accounting operations are not reached.

### Header validation and rejection

Validation first reads the 32-bit header at input address minus eight.

- If that read observes zero, the function invokes **F-a817d8d58c10**.
- Otherwise, validation performs another header read and invokes F-a817d8d58c10 if bit 0 of that read is set.
- If neither rejection condition is met, execution continues.

F-a817d8d58c10 is annotated as non-returning. No normal continuation from that call is established.

Rejection occurs after preparation and context capture, but before the function’s explicit accounting writes. The preparation and rejection dependencies may themselves have side effects.

The two validation reads must not be collapsed into a guarantee about one immutable header snapshot. For example, a nonzero first read followed by a zero second read satisfies neither rejection condition. Conversely, an entry header of zero does not guarantee rejection if preparation changes it before validation.

Bits other than bit 0 are not independently rejected. A nonzero header with a zero masked accounting amount can pass.

### Context operation before accounting

After validation passes, the function calls **F-c0fc6d033caa** with the captured context.

The metadata indices and first accounting amount are obtained after this call. The dependency is not known to preserve metadata, context contents, the global reference, or ownership.

There is no repeated validity check after this call. A header change made by this dependency can affect subtraction amounts without causing another rejection.

The function does not reload the global context reference. Any later change to that reference does not redirect the function’s explicit accesses away from its previously captured context.

### First accounting group

The first group uses one retained amount: a 32-bit header read masked with `0x3FFFFFFC`. This retains bits 2 through 29 and discards bits 0, 1, 30, and 31. The result is an unsigned multiple of four between zero and `0x3FFFFFFC`, inclusive.

The first metadata index is read before this amount is obtained. The second metadata index is read after the first two accounting writes.

The four read-modify-write updates occur in this order:

| Order | Target relative to captured context | Amount subtracted |
|---:|---|---|
| 1 | `0x224 + 4 × first metadata index` | Retained first amount |
| 2 | `0x30C` | Same retained amount |
| 3 | `0x0E0 + 4 × second metadata index` | Same retained amount |
| 4 | `0x220` | Same retained amount |

The header is not independently reloaded for each of these four subtractions.

The second index is not necessarily its entry value or its value when the first index was read. Earlier writes can affect it if storage overlaps, and external modification is not excluded.

### Count updates

After the four size updates, the function calls **F-09dcb55e8e0a**, with no explicit arguments.

Its signed 32-bit result selects the field at captured context plus `0x310 + 4 × result`. The function decrements that field by one, then decrements the field at captured context plus `0x390` by one.

No nonnegative check, bounds check, or normalization of the returned index is visible. Validity of the resulting address is an external requirement.

The dependency may modify memory before these decrements. Its preservation of previously updated fields or subsequently accessed metadata is unknown.

### Final size update

After both count decrements, the function uses another header read, masked with `0x3FFFFFFC`, to reduce the field at captured context plus `0x008`.

This is a fresh amount, not the retained amount used in the first accounting group. F-09dcb55e8e0a and the intervening direct writes can affect what this read observes.

No zero-header or bit-0 validation is repeated. The supplied expression does not independently establish the evaluation order between the target-field read and this header read; both supply the final subtraction.

### Delegation and completion

After all seven direct accounting writes, the function calls:

1. **F-cc6c9b4a0f68**, with the captured context and the metadata address.
2. **F-e586bff64fb7**, with the captured context, if the preceding call returns normally.

The function then returns if F-e586bff64fb7 returns normally.

No status inspection, error translation, or compensating update is visible.

## Side effects

### Direct memory effects

A successful path reaching all accounting operations performs seven explicit 32-bit writes, in the order listed above: four first-amount subtractions, two decrements, and one fresh-amount subtraction.

There are no explicit writes to the metadata or the global context reference, and no direct payload reads or writes. This does not guarantee that metadata remains unchanged: accounting targets can overlap metadata, and dependencies may modify it.

The seven writes need not affect seven distinct locations. If targets alias, later field reads observe earlier writes absent intervening modification. The function does not merge or deduplicate updates.

### Arithmetic

The size updates combine 32-bit field values with unsigned 32-bit masked amounts. Their stored results have unsigned 32-bit subtraction behavior. There is no saturation or underflow check; subtracting a larger amount wraps modulo \(2^{32}\).

The count updates are represented as signed 32-bit decrements. No lower-bound check or overflow handling is visible. Behavior when decrementing the signed minimum is **documented_only**; a portable wraparound guarantee is not established.

The dependency-selected index participates in signed address arithmetic. Metadata-derived indexing also ultimately requires valid context-relative addresses. Address overflow, input-address subtraction overflow, and invalid memory access behavior remain undocumented.

### Ownership and partial completion

No direct operation establishes that the input denotes owned memory, that ownership transfers, or that memory is released. F-cc6c9b4a0f68 receives the metadata address, but its allocation or release semantics are unknown.

Earlier accounting writes precede later dependencies. If a later call fails to return normally, this function contains no visible rollback. Neither recovery behavior nor the resulting externally observable state is otherwise guaranteed.

No atomicity or synchronization guarantee follows from the direct operations.

## Acceptance examples

These are conditional expectations derived from static evidence, not executed tests. Where an example reaches a later phase, all required earlier accesses and calls are assumed to complete normally.

### Zero input

Given an input of zero, the function returns without calling any dependency or accessing the described metadata, global context reference, or accounting fields.

### Zero observed by validation

Given a nonzero input:

- F-2fd8826557a4 returns normally.
- The context-reference read completes.

This example requires usable context and metadata storage. It makes no claim about subsequent dependency behavior.

### Odd header during validation

If the header remains `0x00000041` throughout validation, that condition is satisfied. Its masked size does not prevent rejection.

### Stable, distinct accounting targets

Assume:

- All relevant header reads observe `0x00000042`.
- Both metadata indices are zero.
- F-09dcb55e8e0a returns zero.
- All seven target locations are valid and distinct.
- Dependencies do not disturb the values relevant to these expectations.
- Each size field starts at 512 and each count field starts at 3.

Immediately after the direct accounting updates:

- Each of the five size fields contains 448, because the masked amount is 64.
- Each count field contains 2.
- The two final dependencies are called in their specified order if they return normally.

Bit 1 does not cause rejection.

### Zero masked amount

If every relevant header read observes `0x00000002`, validation passes and all five size subtractions use zero. The two count decrements still occur, followed by the final dependencies if execution continues normally.

This path is neither the null-input path nor a rejection path.

### Different amounts across phases

Assume the first accounting amount is 64. F-09dcb55e8e0a then changes the header so the final mask yields 128, with accessed storage remaining valid and no other relevant interference.

The first four size updates subtract 64; the final size update subtracts 128. No intervening revalidation rejects the changed header.

### Aliased count targets

If F-09dcb55e8e0a returns 32, the selected target is the fixed field at context offset `0x390`.

If that field initially contains 3 at the first decrement and no interference occurs, the two consecutive updates leave it at 1. There is no deduplication.

### Unsigned subtraction underflow

If a size field contains 16 when an update subtracts 64, the stored 32-bit result is `0xFFFFFFD0`.

This expectation applies to the individual direct write; later aliases or dependencies may modify that storage again.
