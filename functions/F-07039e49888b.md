# F-07039e49888b

## Purpose

F-07039e49888b compares two records and returns an unsigned Boolean result: **1** when the left record orders strictly after the right record, and **0** otherwise.

For stable inputs and normally completing conversions, the ordering is lexicographic:

- Primary elements are compared as unsigned integers.
- Equal primary elements cause the secondary elements to be converted to a signed integer type and compared.
- A greater left primary, or equal primaries with a greater converted left secondary, produces 1.
- A smaller left record or an equal record produces 0.

This is not a three-way comparator. The result does not distinguish equality from a left record that orders before the right record.

The comparisons establish this ordering behavior. Use as a sorting predicate or another application-specific ordering operation is inferred intent; no particular consumer or record meaning is established.

## Behavior

### Ordering for stable inputs

For valid, stable inputs with normally completing conversions:

| Primary relationship, unsigned | Secondary relationship, after signed conversion | Result |
|---|---|---:|
| Left is smaller | Not evaluated | 0 |
| Left is greater | Not evaluated | 1 |
| Primaries are equal | Left is smaller | 0 |
| Primaries are equal | Secondaries are equal | 0 |
| Primaries are equal | Left is greater | 1 |

Unequal primary elements determine the result regardless of the secondary values. The secondary ordering concerns the **converted signed values**, not necessarily their stored unsigned magnitudes.

### Conditional evaluation and read order

The established evaluation order consists of three comparison stages:

1. A strict unsigned primary comparison.
2. If that comparison is false, a non-strict unsigned primary comparison.
3. If the second comparison is true, a non-strict comparison of the signed-converted secondary elements.

A true first comparison suppresses both later stages. A false second comparison suppresses the secondary stage.

For stable inputs, the secondary stage is reached exactly when the primary elements are equal. This equality is a consequence of the two preceding comparisons; the function does not take a snapshot or perform a separate equality check.

The primary elements participate in both primary comparison stages. Thus, the source expresses repeated primary evaluations on paths that continue past the first stage. It does not establish whether an implementation reuses values or issues separate machine loads.

Within any individual comparison, the relative evaluation order of the left and right operands is not established. In particular, the evidence does not guarantee:

- That the left primary is read before the right primary.
- That the left secondary is read or converted before the right secondary.
- A fixed physical load count or instruction sequence.
- A bus-access trace, speculation policy, or device-memory protocol.

The contract establishes conditional evaluation between stages, not a physical memory-access schedule.

### Secondary conversion

Each secondary element is stored in the unsigned element type and converted to the signed comparison type before the secondary comparison.

A value representable in the signed destination retains its mathematical value. For values outside that range, the supplied material does not establish the conversion result or whether conversion completes normally.

Under model M, a stored secondary value of 4,294,967,295 converts to −1, and 2,147,483,648 converts to −2,147,483,648. Those results depend on model M’s explicit conversion rule, not merely its signed representation.

When the primary elements differ, these conversions are not evaluated.

### Result formation and arithmetic

The comparison condition is reduced to either 0 or 1, then inverted using exclusive-or with 1. The final result therefore remains exactly 0 or 1.

This is Boolean inversion, not a bitwise complement that could produce an all-ones integer.

The function does not subtract keys or compute a numeric distance between records. Consequently, key-difference overflow is not part of its behavior. Addressing the secondary element still requires valid element storage; the function provides no bounds protection.
