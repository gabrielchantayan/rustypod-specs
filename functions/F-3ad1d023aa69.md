# F-3ad1d023aa69

## Purpose

F-3ad1d023aa69 performs four byte lookups using two input-byte positions and a globally supplied table address. It writes four result bytes in a fixed order and returns a 32-bit zero on normal completion.

For ordinary, nonoverlapping storage and a stable table address, the result is two pairs: the first pair comes from the first input byte, and the second pair comes from the second input byte. Each pair contains a lookup from a lower table region followed by a lookup from a region 256 bytes above it.

That description is inferred intent, not an unconditional replacement for the observed behavior. The function rereads each input position, and the output may overlap input, table storage, or other relevant state. Such overlap can change later lookups.

## Interface

**Inputs**

- An input address identifying two byte positions, at offsets 0 and 1.
- An output address identifying four byte positions, at offsets 0 through 3.
- An implicit global value used as a table address.

Input bytes are unsigned 8-bit values. Each lookup index therefore ranges from 0 through 255; bytes with the high bit set are not negative indices.

**Output layout**

Under stable-address, nonoverlapping conditions, let \(T\) be the table base and let \(a\) and \(b\) be the two input bytes:

| Output offset | Result |
|---|---|
| 0 | Byte at \(T+a\) |
| 1 | Byte at \(T+256+a\) |
| 2 | Byte at \(T+b\) |
| 3 | Byte at \(T+256+b\) |

Each output position receives exactly one byte. No terminator, length field, padding, or additional result is written.

**Return value**

Normal completion returns a 32-bit value whose bits are all zero. The return value does not describe the input, report a count, or distinguish successful lookup cases.

**Storage requirements**

Defined execution requires:

- Readable storage for every input-byte read actually performed.
- A readable global table-address value.
- Readable storage at every table address actually selected.
- Writable storage for all four output-byte stores.
- Address arithmetic that produces valid accesses under the execution environment.

With a stable table address, a contiguous readable 512-byte table is sufficient for every possible input byte. It is not necessary to read all 512 bytes during one call; only four selected table-byte reads are visible in the supplied body.

There is no explicit null check, bounds check, overlap check, or table-validity check.

**Ownership**

The function neither allocates nor explicitly releases storage. Its visible behavior does not transfer ownership of input, output, or table memory. The caller must arrange usable storage for the duration of the accesses. No stronger ownership or lifetime guarantee is established.

## Behavior

### Table-address acquisition

The visible body first reads the global table-address value and retains it for later address calculations.

The first table lookup separately reads that global value again. Thus the evidence shows two global-value evaluations, not one shared table-base snapshot for all four lookups.

If both evaluations return the same value, all four results refer to the expected pair of adjacent 256-byte table regions. If they differ, the first result uses the second value, while the remaining three results use the initially retained value.

The supplied body contains no intervening explicit store between those two global evaluations. A difference would therefore require behavior beyond ordinary stable memory, such as external modification or special read semantics. Whether such behavior is supported is not established.

### Ordered reads and writes

The four output assignments occur in ascending output-offset order.

1. For output offset 0, the function reads input offset 0, uses its unsigned value as an offset from the separately evaluated global table address, reads one table byte, and stores that byte at output offset 0.
2. After that store, it forms the upper-region address by adding 256 to the initially retained table address.
3. For output offset 1, it reads input offset 0 again, reads one byte from the upper region using that index, and stores the result at output offset 1.
4. For output offset 2, it reads input offset 1, reads one byte from the lower region based on the initially retained table address, and stores the result at output offset 2.
5. For output offset 3, it reads input offset 1 again, reads one byte from the upper region using that index, and stores the result at output offset 3.
6. After the fourth store, it returns zero.

Each assignment obtains its source byte before storing its result. The four table results are not all collected before output begins.

Within the first lookup expression, the relative evaluation order of the global-value read and the input-byte read is not established by the supplied representation. Both contribute to that lookup before its output store.

### Repeated input reads

The function does not retain a single value for either input position across both corresponding lookups:

- Input offset 0 is read before the first store and again after that store.
- Input offset 1 is first read after the first two stores, then again after the third store.

Consequently, the two lookups associated with an input position need not use the same index if intervening writes or external activity change that position.

### Overlap behavior

No visible operation rejects overlapping storage.

If output overlaps input, earlier result stores can change later input reads. In particular:

- The first store can affect the second lookup’s index.
- Either of the first two stores can affect the index used for the third lookup.
- The third store can affect the index used for the fourth lookup.

If output overlaps table storage, an earlier output store can change a table byte that a later lookup reads. The result then depends on the specified sequence of accesses, not solely on the table’s entry-time contents.

If output overlaps the storage holding the global table address, an output store can alter that global storage. However, the visible later table calculations use the already retained address; the function does not explicitly reload the global after the first output store.

These observations describe the visible access sequence. They do not establish that every such aliasing arrangement is valid under the original language’s memory rules or the target platform.

### Integer widths and address arithmetic

All lookup data and output stores are one byte wide. Input indices are unsigned and span exactly 256 possible values.

The upper region begins at a byte displacement of 256. Within either region, the selected displacement is the unsigned input-byte value. For a stable base, the largest nominal table displacement is therefore 511.

The return quantity is four bytes wide. The recovered address calculations are expressed through integer-valued temporaries, but the supplied material does not independently establish the target address width, signed-overflow rules, or pointer-conversion semantics. Address wraparound must not be assumed to provide a valid lookup. Valid address formation remains a precondition.

## Side effects

On normal completion, the function performs four ordered byte stores at output offsets 0, 1, 2, and 3. It does not skip a store when the value already present is equal to the lookup result.

The body also visibly evaluates the global table-address value twice, reads input bytes four times, and reads table bytes four times.

No explicit allocation, release, callback, logging, synchronization, or separate global update appears in the supplied body. Output aliasing can nevertheless cause the stores to modify input storage, table storage, or global storage.

There is no rollback mechanism. If an access fails after earlier stores have occurred, the body contains no operation that restores those earlier bytes. The precise fault behavior and whether control returns are environment-dependent and undocumented here.

For disjoint ordinary memory, the function writes no location outside the four-byte output range.

| Table displacement | Byte |

### Boundary indices

This example distinguishes unsigned-byte indexing from signed indexing. The value 255 selects the last entry of each region, not an address below either region.

### Exact input/output overlap

Assume a valid overlapping arrangement in which output begins at the input address and four writable bytes are available. Assume a stable, disjoint table with:

- Lower-region entry \(x\): \(x+1\), reduced modulo 256.
- Upper-region entry \(x\): \(x+16\), reduced modulo 256.

Let the initial input bytes be 2 and 7.

Expected output bytes are 3, 19, 20, 35:

- The first store replaces the first input byte with 3.
- The second lookup rereads 3 and stores 19 into the second input position.
- The third lookup reads that new value, 19, and stores 20.
- The fourth lookup still reads 19 and stores 35.

For disjoint buffers with the same initial input and table, the output would instead be 3, 18, 8, 23. An implementation that snapshots both input bytes before writing would not preserve the observed overlapping behavior.

This is an access-sequence expectation, not a claim that concurrent modification is safe.
