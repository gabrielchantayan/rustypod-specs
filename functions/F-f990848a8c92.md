# F-f990848a8c92

## Purpose

F-f990848a8c92 computes the signed numerical difference between two integers obtained through caller-supplied addresses. The value selected by the first argument is the minuend; the value selected by the second argument is the subtrahend.

The result includes magnitude, not just ordering. Observing nine through the first address and four through the second requires a result of five. A positive comparison indicator alone would not satisfy the contract.

The defined numerical contract requires valid operand accesses and a mathematical difference representable in the native signed integer type used by the interface. It does not provide a safe comparison operation for every possible pair of representable operands.

**Established static evidence:** The operation obtains two integer values through addresses and returns their difference in argument order.

**Inferred intent:** Restricted-range comparison is a possible application. No caller evidence establishes that purpose or shows that callers enforce the necessary arithmetic bounds.

There is no output buffer, size argument, status result, or separate error channel. Zero is an ordinary successful result when the observed values are equal; it is not an error sentinel.

For the defined numerical result:

## Behavior

### Numerical result

For valid accesses and representable arithmetic, the result is the first observed integer less the second observed integer.

This requires:

- Zero for equal observations.
- A positive result when the first observation is greater.
- A negative result when the first observation is smaller.
- The complete difference, rather than a normalized ordering indicator.

Subtracting a negative value can increase the result. There is no established absolute-value operation, saturation, sign normalization, or intentional modular reduction.

For stable ordinary objects, relocating the same values to different valid addresses cannot change the required answer. Argument position determines the values’ arithmetic roles.

### Reads and their ordering

The operation requires a value from each designated object. The supplied evidence does not establish that the first argument’s object is read before the second argument’s object, or vice versa.

Argument order therefore specifies subtraction order, not temporal access order.

There is no established simultaneous-snapshot guarantee. Neither observation is guaranteed to equal the corresponding object’s contents at function entry. For stable ordinary objects this distinction is immaterial. For storage that can legally change during execution, the numerical result depends on the observations permitted by that environment.

Passing the same address twice does not create synchronization. Stable storage requires a zero result. For changing storage, address identity alone does not establish equal observations.

These are value-level requirements. The evidence does not establish an exact number of physical loads, a machine transaction width, an instruction schedule, or hardware access ordering. Those details remain **documented_only**.

### Arithmetic limits

The native signed integer type has a minimum and a maximum representable value. Their concrete numerical values are unresolved.

A mathematical difference equal to either endpoint remains within the defined domain and must be returned exactly. A difference beyond either endpoint is outside that domain under ordinary signed-integer semantics.

No explicit overflow detection, wider-arithmetic recovery, or alternate result is established. An out-of-range subtraction therefore provides no prescribed:

- Wrapped numerical result.
- Reliable comparison sign.
- Saturated endpoint.
- Error indicator or diagnostic.
- Trap or exception.
- Normal return or continuation.

A particular machine’s apparent wrapping behavior would not, by itself, establish a wrapping contract. Any deployment-specific arithmetic policy requires additional evidence.

### Invalid accesses and error handling

The operation establishes no argument-validation stage and no recoverable error protocol.

An invalid, expired, inaccessible, misaligned, or otherwise unsuitable operand address falls outside the defined access domain. The contract prescribes neither a returned value nor a particular failure mechanism for such an address.

A memory fault on one deployment would not establish a portable error response. Conversely, an apparently successful return would not make an invalid access valid.

No rollback or recovery guarantee is established after an invalid access or an unrepresentable subtraction. There is no reserved numerical result by which callers can reliably detect either condition.
