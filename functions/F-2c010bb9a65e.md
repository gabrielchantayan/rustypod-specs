# F-2c010bb9a65e

## Purpose

F-2c010bb9a65e conditionally retrieves a three-word record associated with a receiver, applies its words through three indirect receiver operations, and may process and dispatch a stack-resident context.

Its return distinguishes three entry and lookup outcomes:

- A null association returns null.
- A non-null association with zero stored control returns the captured association pointer.
- An attempted lookup that returns null produces a null return.

After a successful lookup, the result instead comes from the first word of the local context.

The application-level meanings of the association, record, receiver operations, and context are not established. Interpreting them as rendering, event delivery, or resource management would be an inference rather than part of this contract.

## Interface

### Inputs and representation

The function accepts:

1. **Receiver:** a pointer to storage accessed as 32-bit words.
2. **Unused argument:** a 32-bit value not read or forwarded by the supplied body.
3. **Caller control:** a 32-bit integer. When the association is non-null, the receiver’s stored control replaces this value. When the association is null, execution does not proceed regardless of this value.

The supplied representation uses 32-bit integer words and 32-bit pointer-bearing fields. The following offsets are byte offsets from the receiver:

| Offset | Established use |
|---|---|
| `0x00` | Pointer to an indirect-operation table |
| `0x34` | 32-bit value captured before context initialization and conditionally used in address formation |
| `0x38` | Association pointer |
| `0x44` | Stored control value |
| `0x80` | Start address of an embedded region passed to dependencies |
| `0xA0` | 32-bit word converted to an eight-bit character value for a zero comparison |

The relevant indirect-operation table entries are:

| Table byte offset | Arguments |
|---|---|
| `0x11C` | Receiver, record word at byte offset `0x04` |
| `0x120` | Receiver, record word at byte offset `0x08` |
| `0x118` | Receiver, record word at byte offset `0x00` |

These offsets address the table, not fields of the receiver.

Two distinct global inputs are relevant:

- A **global lookup operand**, read when preparing the lookup call. Its declaration, width, value, and mutability are not supplied.
- A **global enable pointer**, through which a byte is read on the optional-dispatch eligibility path. Its declaration, initialization, and ownership are not supplied.

They must not be treated as the same global input or assumed constant.

### Output

The function returns a pointer-typed value in the represented 32-bit environment:

| Condition | Normal return |
|---|---|
| Captured association is null | Null |
| Captured association is non-null and stored control is zero | Captured association pointer |
| Association and stored control are nonzero, but lookup returns null | Null |
| Lookup succeeds | Final contents of the local context’s first word |

The association returned on the zero-control path is the value read at entry, not a later reread of the receiver field.

The successful-lookup result is initially the receiver pointer, but dependencies receiving the context address may change it. Neither a non-null result nor a return equal to the original receiver is guaranteed on that path. No ownership-transfer rule is established.

### Preconditions

The body does not validate the receiver, table pointer, callback targets, global locations, or record extent before using them.

Normal completion requires, on each reached path:

- Readable receiver fields at the accessed offsets.
- Valid global storage for each global read actually performed.
- A callable lookup dependency when lookup is attempted.
- A non-null lookup result exposing three readable 32-bit words when consumed.
- A usable receiver table and callable entries for the three indirect operations.
- Storage remaining valid across intervening calls whenever it is accessed afterward.
- Arguments satisfying the unavailable contracts of invoked dependencies.

These requirements are path-dependent. A zero stored control avoids the lookup, global lookup-operand read, receiver operations, and all context processing.

All normal-return descriptions assume invoked dependencies return control. Faults, exceptions, nonlocal exits, and dependency-specific failures have no handling specified by this body.

## Behavior

### Entry gating and early returns

The function first reads and captures the association pointer at receiver offset `0x38`.

If that pointer is null, the function returns null. It does not read the stored control at `0x44`, read the global lookup operand, or invoke a dependency.

If the association is non-null, the function reads the stored control at receiver offset `0x44`, replacing the caller control for the subsequent gate.

If the stored control is zero, the function returns the captured association pointer. This is not a lookup failure and does not return null.

Any nonzero stored control permits lookup. There is no positive-only, sign, or range check.

The caller control cannot change the selected path: a null association prevents further work, while a non-null association causes the stored control to supersede it.

### Lookup and global operand read

When both the captured association and stored control are nonzero, the function calls F-5710a8628cba with:

1. The captured association pointer.
2. The value read from the global lookup-operand location while preparing this call.

The second argument is a global data read, not an established literal or immutable operand. Its meaning and value are unavailable. This read occurs after entry gating and before the lookup and receiver callbacks. The body does not cache it across invocations or establish that another invocation sees the same value.

A null lookup result causes an immediate null return. No receiver operation, query, or context processing follows.

A non-null result is used as a record containing three 32-bit words:

| Record byte offset | Use |
|---|---|
| `0x00` | Argument to the third receiver operation |
| `0x04` | Argument to the first receiver operation |
| `0x08` | Argument to the second receiver operation |

The function does not snapshot all three words before invoking callbacks. Each word is consumed for its corresponding call. Mutations to words not yet consumed can affect later calls, provided the record remains valid.

### Ordered receiver operations

After successful lookup, the function invokes:

1. The table entry at `0x11C`, with the receiver and record word at `0x04`.
2. The table entry at `0x120`, with the receiver and record word at `0x08`.
3. The table entry at `0x118`, with the receiver and record word at `0x00`.

The table pointer is obtained from the receiver separately for successive operations. An earlier callback can therefore change which table supplies a later target.

The third target is explicitly captured before the third call. That same captured target is later stored in the local context. A table change during the third call does not replace this saved target.

For the first two calls, the supplied expression does not establish a finer ordering between evaluating the target and reading that call’s record argument. The established boundaries are that each call is prepared before invocation and completes before the next operation is prepared.

Return values from these operations are not inspected. There is no rollback if a later stage skips work or fails to produce a recipient.

### Local context

After the third receiver operation returns, the function initializes a four-word local context:

| Context byte offset | Initial value |
|---|---|
| `0x00` | Receiver pointer |
| `0x04` | Address of receiver offset `0x80` |
| `0x08` | 32-bit value `1` |
| `0x0C` | Captured target of the third receiver operation |

The embedded-region value is an address formed from the receiver, not the contents of the word at `0x80`. Its extent is not established.

The context occupies local stack storage. Only dependencies on the optional processing path receive its address explicitly. Their interpretation of its fields and their ability to modify or retain it are unavailable.

### Dispatch eligibility

After initializing the context, the function invokes F-3fac671648b8 with no explicit arguments.

Optional context processing occurs only if these conditions succeed in order:

1. The query result is nonzero.
2. The eight-bit character conversion of the receiver word at `0xA0` is zero.
3. The byte obtained through the global enable pointer is nonzero.

The conditions short-circuit:

- A zero query result prevents the receiver flag read and global enable-byte read.
- A nonzero converted flag prevents the global enable-byte read.

The flag comparison tests the low-order eight-bit value produced by the conversion, not whether the entire 32-bit word is zero. Upper bits alone do not reject the path. The character value’s signedness does not change whether that eight-bit value is zero.

These checks follow all three receiver operations. Rejection here suppresses only the later context-processing path.

The global enable access occurs at this later point; the function does not use an entry-time snapshot of that state. Earlier dependencies are not assumed to preserve it.

### Context initialization and extension

If eligibility passes, the function first captures the 32-bit value at receiver offset `0x34`.

It then invokes F-e57b05520b65 with:

1. The context address.
2. The address of receiver offset `0x80`.
3. That same embedded-region address again.

The equality of the last two arguments is established. Their semantic roles are not.

If the previously captured value at `0x34` is nonzero, the function next invokes F-ee8733a08210 with:

1. The context address.
2. The captured value plus `0xD0`.

Both the nonzero decision and addition use the captured value. A change to receiver offset `0x34` during F-e57b05520b65 does not replace it.

The captured value is represented as a 32-bit integer, and the addition is used to form the second argument. No bounds, alignment, or overflow check appears. The supplied representation does not establish a portable signed-overflow rule or justify promising modular wraparound. Overflow behavior remains documented_only.

A zero captured value skips only F-ee8733a08210. It does not skip context initialization or recipient resolution.

### Recipient resolution and dispatch

The function next invokes F-ffe0d92c57b7 with the receiver.

If the result is zero, neither dispatch dependency is called.

If it is nonzero, the function invokes, in order:

1. F-c9b5d17d8d1e with the resolved value and context address.
2. F-4d037ecf0f82 with the same resolved value and the same context address.

There is no second resolution between these calls. Context modifications made by the first dispatch are available to the second. A change to receiver state during the first dispatch does not cause the recipient to be recomputed.

The body does not inspect either dispatch’s return value.

### Final return

Every normally completing successful-lookup path returns the first context word after any optional processing.

If context processing is skipped, that word remains initialized to the receiver in the supplied body. If processing occurs, its final value depends on the invoked dependencies.

No explicit cleanup, record release, context destruction, or recipient release is performed by this body.

## Side effects

Direct writes shown by the body initialize local state and the stack context. No direct receiver-field or global-storage write is shown.

Indirect operations and dependencies may modify receiver storage, record storage, globals, or other state. Their effects are not constrained by unavailable contracts.

The established ordering of observable stages is:

1. Capture the association pointer.
2. If non-null, read stored control.
3. If stored control is nonzero, read the global lookup operand and perform lookup.
4. If lookup succeeds, perform the three receiver operations in their specified order.
5. Initialize the local context.
6. Invoke the eligibility query.
7. If permitted, read the receiver flag, then access the global enable pointer and byte.
8. If eligible, capture the extension base before context initialization.
9. Initialize context through F-e57b05520b65, then optionally extend it.
10. Resolve the recipient, then perform the two dispatches if nonzero.
11. Read the context’s first word for the successful-lookup return.

No allocation, deallocation, ownership transfer, retry, diagnostic, or recovery operation is explicitly identified in the body. This does not establish that dependencies allocate nothing, release nothing, or preserve global state.

The context’s stack lifetime ends with this invocation. Retaining its address for later use would require a separate lifetime arrangement not established here.

## Acceptance examples

These are conditional static scenarios, not executed tests. They assume valid reached storage, returning callees, and the dependency effects stated in each example.

1. **Null association:** With a null association, the result is null regardless of caller control. Stored control and the global lookup operand are not read.

2. **Zero stored control:** With a non-null association and zero stored control, the result is that captured association pointer, even if caller control is nonzero. There is no lookup or lookup-operand read. Conversely, nonzero stored control permits lookup even when caller control is zero.

3. **Lookup miss:** With nonzero association and stored control, the global lookup operand is read and passed to F-5710a8628cba. If lookup returns null, the result is null—not the association—and no receiver operation or query occurs.

4. **Changing lookup operand:** If the global lookup value changes between invocations, each invocation reaching lookup supplies the value obtained by its own read. No fixed value or cross-invocation snapshot is required.

5. **Record order:** For an unchanged record containing words `[10, 20, 30]`, operations at table offsets `0x11C`, `0x120`, and `0x118` receive `20`, `30`, and `10`, respectively.

6. **Mutation between callbacks:** If the first operation changes the record’s third word from `30` to `40`, the second receives `40`, provided the record remains valid.

7. **Table replacement:** If the first operation replaces the receiver’s table pointer, the second target is obtained from the replacement table. The third target is likewise selected at its later preparation point.

8. **Query rejection:** A zero query result occurs after all three receiver operations. The receiver flag and global enable byte are not read, and the context’s first word is returned as initialized to the receiver.

9. **Flag boundary:** With a nonzero query result, `0x00000100` passes the zero-character condition while `0x00000101` fails it. Only the former permits the subsequent global enable-byte check.

10. **Captured extension base:** If `0x34` contains a valid nonzero base and F-e57b05520b65 changes that field, F-ee8733a08210 still receives the original captured value plus `0xD0`, assuming the addition is valid.

11. **No recipient:** A zero recipient result suppresses both dispatch calls but does not undo context initialization or an already performed extension.

12. **Modified return:** If a context-processing dependency replaces the first context word and subsequent dependencies leave it unchanged, that replacement is returned. A replacement of null produces null despite successful lookup.
