# F-fd61d89535ad

## Purpose

F-fd61d89535ad conditionally updates bit 2 of an object’s flag byte, then either processes a 16-bit counter or invokes two dependencies.

Processing is controlled by an initial dependency result and a comparison between the **entire unsigned 32-bit request** and the current flag bit, interpreted as zero or one. The request is not normalized to a Boolean before comparison or path selection.

On a mismatch:

- Request zero clears the flag bit and enters a gated counter-decrement path. A decrement to zero may lead to an object-associated callback.
- Any nonzero request stores its least significant bit in the flag and invokes two dependencies, returning the second dependency’s result.

**Inferred intent:** the flag may describe an enabled state, and the counter may track references or participation. Neither interpretation is established. In particular, a nonzero even request clears the flag bit but follows the nonzero-request dependency path.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

### Inputs and representation

The function receives:

1. **Object address:** a 32-bit address-bearing value used to locate fields and passed onward to dependencies.
2. **Request:** an unsigned 32-bit value, ranging from zero through `0xffffffff`.

All offsets below are byte offsets from the supplied object address.

| Offset | Width or form | Direct use |
|---|---|---|
| `0x20` | 8-bit field | Read as a flag byte; bit 2 may be replaced |
| `0x40` | 16-bit field | Read as an unsigned counter and conditionally decremented |
| `0x4c` | Callback-address slot in the 32-bit representation | Read only when a decrement reaches zero and the final gate succeeds |
| `0x54` | Computed address within the object | Passed as the first argument to F-ebd0ee53699f; not directly dereferenced here |

The flag mask is `0x04`. A flag update preserves the other seven bits from the byte previously read by this function.

Two separate external storage references also participate:

- A configuration datum supplied to F-ebd0ee53699f.
- A callback-context datum captured as a 32-bit value.

Their storage identities are distinct in the supplied representation. Their contents, initialization, and possible aliasing with other memory are not established.

### Return value

The function returns an unsigned 32-bit value whose source depends on the path:

| Condition | Returned value |
|---|---|
| Initial gate returns zero in its low 32 bits | Zero |
| Request equals the extracted flag value | Original flag byte, zero-extended |
| Counter gate returns zero | Zero |
| Counter is already zero | Zero |
| Decremented counter remains nonzero | Decremented counter, zero-extended |
| Counter becomes zero and final gate returns zero | `0xffffffce` |
| Callback is invoked and returns normally | Callback’s 32-bit result |
| Nonzero-request dependency path completes | F-ebd0ee53699f’s 32-bit result |

Zero is therefore not a unique success, failure, or no-operation indicator. A nonzero result is not necessarily an error or a counter value.

### Preconditions and ownership

Every address actually accessed must remain valid for the required operation at the time of access. This includes validity after intervening dependency calls.

Specifically:

- The flag byte must be readable after the initial gate succeeds.
- The flag byte must be writable on a request/flag mismatch.
- The counter must be readable after the counter gate succeeds and writable when its value is nonzero.
- The callback-context storage must be readable after a counter decrement.
- The callback slot must be readable after a successful final gate, and its contents must identify a callable target accepting the observed arguments.
- The configuration storage must be readable when the nonzero-request dependency call is prepared.

No explicit null, bounds, alignment, callback-validity, or lifetime checks are visible. Address calculations must designate valid locations in the applicable execution environment; the evidence does not establish portable behavior for invalid or overflowing address calculations.

No direct allocation, release, ownership transfer, or lifetime extension is visible. Dependencies and the callback have unknown ownership effects.

## Behavior

### Initial gate

The first operation is a call to F-06f4ceb6a4f2 with no explicit arguments.

Its low 32-bit result determines whether object processing begins:

- If zero, return zero without directly accessing the object.
- If nonzero, read the flag byte at offset `0x20`.

The first call’s representation includes an upper result component. That component does not affect the subsequent observable decisions in this function. The dependency’s complete return convention is not established.

### Full-width comparison

The function extracts bit 2 from the flag byte and interprets it as exactly zero or one.

It compares that value with the entire unsigned 32-bit request.

If equal, the function returns the **whole original flag byte**, zero-extended to 32 bits. It performs no direct flag write, counter access, or further dependency call.

Consequences include:

- Request zero matches only a clear flag bit.
- Request one matches only a set flag bit.
- Requests from two through `0xffffffff` never match, regardless of their least significant bit.

### Flag replacement and branch selection

On a mismatch, the function writes one byte at offset `0x20`:

- Bit 2 becomes the request’s least significant bit.
- All other bits retain their values from the previously read flag byte.

Even requests clear bit 2; odd requests set it. A write occurs even if the resulting byte is identical to the original byte.

This write precedes every later dependency call and counter access on the selected path. There is no intervening flag reread.

The next branch tests whether the **whole request is zero**:

- Zero enters the counter path.
- Every nonzero value enters the dependency path.

The stored flag bit does not control this branch. For example, request two clears bit 2 and nevertheless selects the nonzero-request path.

### Nonzero-request dependency path

After the flag write, the function:

1. Calls F-92ee90fe6e9f with no explicit arguments.
2. Obtains the configuration value used for the next call.
3. Calls F-ebd0ee53699f with these arguments, in order:
   - The address formed from the object address plus `0x54`.
   - The configuration value.
   - The original object address.
4. Returns F-ebd0ee53699f’s 32-bit result.

F-92ee90fe6e9f’s return value is unused.

The configuration value is obtained after F-92ee90fe6e9f returns. A configuration change made by that dependency can therefore affect the argument supplied to F-ebd0ee53699f.

This function performs no direct counter access on this path. Neither dependency is established to preserve the object, its fields, global storage, or ownership.

### Zero-request path: counter gate

After writing the flag byte, the function calls F-06f4ceb6a4f2 again.

If that call returns zero in the tested 32-bit result:

- Return zero.
- Do not directly read the counter.
- Perform no direct rollback of the preceding flag write.

The flag write occurred before this call. The flag’s resulting contents and the object’s continued lifetime depend on the dependency’s unknown effects.

If the gate succeeds, read the unsigned 16-bit counter at offset `0x40`.

If the counter is zero, return zero without:

- Writing the counter.
- Reading the callback-context datum.
- Calling the final gate.
- Reading or invoking the callback.

### Zero-request path: decrement and context capture

For a nonzero counter, subtract one and store the result as a 16-bit value at offset `0x40`.

The counter was zero-extended before arithmetic. Since zero is excluded before subtraction, the established path does not wrap zero to `0xffff`. The possible decrement results range from zero through `0xfffe`.

After storing the counter, read the 32-bit callback-context datum.

This read occurs even when the decremented counter remains nonzero. If the new counter is nonzero, return it zero-extended to 32 bits. The captured context value is not passed onward on that path.

For example, an initial counter of `0xffff` produces a stored counter of `0xfffe` and a return value of `0x0000fffe`.

### Zero-request path: transition to zero

If the decrement produces zero, call F-06f4ceb6a4f2 a third time.

If this final gate returns zero, return `0xffffffce` without directly reading the callback slot or invoking the callback.

The flag and counter writes occur before the final gate call. This function performs no rollback after that call; the fields’ resulting contents and the object’s continued lifetime depend on the dependency’s unknown effects.

The return pattern `0xffffffce` represents −50 if interpreted as signed 32-bit data. Its symbolic meaning is not established.

If the final gate succeeds:

1. Read the callback target from offset `0x4c`.
2. Invoke that target with:
   - The original object address.
   - The previously captured 32-bit context value.
3. Return the callback’s 32-bit result.

The context is captured **before** the final gate. The callback target is read **after** it. Therefore:

- A final-gate change to the context datum does not replace the already captured argument.
- A final-gate change to the callback slot can change the selected target.
- A final-gate change to the counter does not cause this function to reconsider the callback decision; there is no counter reread.
- If the final gate invalidates the object or callback slot, a safe callback lookup is not established.

## Side effects

The direct object writes are limited to:

- One flag-byte write on a request/flag mismatch.
- One 16-bit counter write when request zero reaches a nonzero counter.

These are executed writes, not guarantees about the fields’ contents after subsequent dependency or callback execution.

For a path reaching the callback, the established direct sequence is:

1. Initial gate call.
2. Flag-byte read.
3. Flag-byte write.
4. Counter gate call.
5. Counter read.
6. Counter write.
7. Callback-context read.
8. Final gate call.
9. Callback-slot read.
10. Callback invocation.

For a nonzero-request mismatch, the sequence is:

1. Initial gate call.
2. Flag-byte read.
3. Flag-byte write.
4. F-92ee90fe6e9f call.
5. Configuration-value read.
6. F-ebd0ee53699f call.

These sequences describe the supplied function body. They do not establish synchronization, atomicity, memory barriers, or safe concurrent access. In particular, preserving seven flag bits from an earlier byte read is not a guarantee against lost concurrent updates.

Dependencies and the callback may alter object fields, external storage, or memory ownership. No preservation is assumed.

If a dependency or callback does not return normally, the later steps and ordinary return described for that path are not established to occur. No explicit recovery or cleanup mechanism is visible.

## Acceptance examples

These are conditional consequences of the static evidence, not executed tests. Unless a case specifies otherwise, dependencies return normally and make no additional relevant changes to fields, external storage, or object lifetime.

1. **Initial gate rejects processing.**  
   For any request, a zero initial gate result yields zero with no direct object access. This does not constrain effects performed inside the gate itself.

2. **Clear flag already matches zero.**  
   With flag byte `0xa0`, request zero, and a successful initial gate, return `0x000000a0`. No flag write, counter access, or subsequent call occurs.

3. **Set flag already matches one.**  
   With flag byte `0xa4`, request one, and a successful initial gate, return `0x000000a4` without a direct object write.

4. **Noncanonical odd request still performs work.**  
   With flag byte `0xa4` and request three, write `0xa4` despite no byte-value change. Then call F-92ee90fe6e9f and F-ebd0ee53699f.

5. **Nonzero even request clears the flag but avoids the counter path.**  
   With flag byte `0xa4` and request two, write `0xa0`, then follow the nonzero-request dependency path. No direct counter read or decrement occurs.

6. **Dependency return is forwarded.**  
   With flag byte `0xa0` and request one, write `0xa4`. If F-ebd0ee53699f subsequently returns `0x12345678`, return that value.

7. **Configuration is obtained after the preceding dependency.**  
   If F-92ee90fe6e9f changes the configuration datum, F-ebd0ee53699f receives the value read after that call, not a value captured before it.

8. **Counter gate rejects after the flag write.**  
   With flag byte `0xa4`, request zero, and a successful initial gate, write `0xa0`. If the counter gate returns zero, return zero without directly accessing the counter. Under the default no-mutation assumption, the flag remains `0xa0`; without that assumption, its resulting contents are unknown.

9. **Counter is already zero.**  
   With request zero, an initial flag mismatch, successful preceding gates, and counter zero, return zero without a counter write, context read, or final gate call.

10. **Counter remains positive.**  
    With counter two on the decrement path, store one, read the context datum, and return one. Do not call the final gate or read the callback slot.

11. **Zero transition followed by gate failure.**  
    With counter one, store zero and capture the context before calling the final gate. If it returns zero, return `0xffffffce` without invoking the callback. If that gate also overwrites the flag or counter, this function does not restore either field.

12. **Earlier context, later callback target.**  
    With counter one and a successful final gate, suppose that gate changes both external context storage and the callback slot while leaving the required memory valid. Invoke the target read from the changed slot, passing the context captured before the gate.

13. **Counter mutation does not cancel callback selection.**  
    If the final gate succeeds but changes the stored counter from zero to another value, proceed to callback lookup without rereading the counter.

14. **Maximum counter.**  
    With counter `0xffff` on the decrement path, store `0xfffe`, read the context datum, and return `0x0000fffe`. Do not reach the final gate.
