# F-c49bb656f717

## Purpose

F-c49bb656f717 performs an ordered initialization sequence over caller-supplied storage and two storage locations obtained through successive calls to F-5b24edfb22c0.

The established behavior is a series of fixed-width writes, with two dependency calls interleaved among them. The first dependency result receives one caller-supplied 32-bit value. The second receives a mixture of caller-supplied values, zero values, and an all-one 32-bit value.

The pattern suggests initialization of a compound object containing nested state. That interpretation is inferred intent, not an established object model. The available evidence does not establish field names, type identities, allocation behavior, or ownership.

This contract describes normal execution when all required accesses are valid and both dependency calls return normally. It does not establish recovery behavior for invalid addresses, dependency failures, or interrupted execution.

### Widths and arithmetic

The stores at R2 + 20 and R2 + 28 are one byte each. They must not be treated as four-byte zeroing or four-byte argument stores. In particular, the zero at offset 20 does not itself initialize the three following bytes.

The only visible address calculations add fixed positive byte offsets. There is no visible checked arithmetic or bounds validation. Valid, representable address calculations are preconditions for normal execution; the evidence does not define portable wraparound behavior.

The supplied representation uses a 32-bit intermediate for dependency results before further address use. This supports a 32-bit address-model interpretation, but the exact machine address width and calling convention remain unestablished. A wider-address implementation would need separate evidence about conversion semantics rather than silently assuming these results can represent arbitrary wider addresses.

### One-byte zero boundary

Assume bytes 20–23 relative to R2 initially contain nonzero values and neither dependency effects nor aliasing alter them after R2 becomes available.

After completion, byte 20 must be zero. Bytes 21–23 must retain their previous values. Replacing the byte write with a four-byte zero would violate this boundary behavior.

### Dependency returns a different address

Assume the second dependency returns a valid address distinct from its argument.

The final six writes must use the returned address as R2. They must not instead use R1 + 12 merely because that address was passed into the dependency.

### Later overlapping write

Assume valid storage and address relationships such that R2 + 8 equals R1 + 8, with no intervening dependency modification of that location.

The Value C write occurs first. The later all-one write replaces those same four bytes. A final-state assertion that the location must still contain Value C would be incorrect.

### Interrupted execution
