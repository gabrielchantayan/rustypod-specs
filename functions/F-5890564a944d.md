# F-5890564a944d

## Purpose

F-5890564a944d searches a fixed-stride sequence for the first entry whose two integer fields equal two supplied search values. It returns the address of that entry, represented as an integer, or zero when traversal reaches the sequence’s end marker.

The established behavior is an ordered equality search. The apparent interpretation as a collection of records is inferred from the constant stride and field offsets; the supplied material does not establish a record type, collection owner, allocation scheme, or application-level meaning for either search value.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

The function accepts three integer-valued arguments and returns an integer-valued result:

| Argument | Meaning established by its use |
|---|---|
| Container address | An integer used as the base address for two memory reads that define traversal. |
| First search value | Compared for equality with the integer field at entry-relative byte offset `0x04`. |
| Second search value | Compared for equality with the integer field at entry-relative byte offset `0x08`, but only after the first comparison succeeds. |

The result is:

- The integer representation of the first matching entry’s address; or
- Zero if the current traversal address equals the end marker before any match is returned.

There is no separate status value, output parameter, or explicit error result.

### Memory layout used by the function

Offsets are byte offsets from the indicated base address.

| Base | Offset | Use |
|---|---:|---|
| Container address | `0x44` / 68 | Initial traversal address, read once. |
| Container address | `0x48` / 72 | End marker, read at the beginning of every traversal iteration. |
| Current entry address | `0x04` / 4 | First comparison field. |
| Current entry address | `0x08` / 8 | Second comparison field, read conditionally. |

Successive candidate addresses differ by `0x1c`, or 28 bytes. This establishes the traversal stride, not the complete layout or allocation size of an entry. The function does not inspect an entry’s first four bytes or any fields beyond the two comparison locations.

### Widths and representation

The supplied representation uses `int` for arguments, return value, stored traversal addresses, and comparison fields. It does not provide an independent target ABI or an explicit integer-width declaration. Consequently, a precise integer width and pointer width remain **documented_only**.

Under a 32-bit interpretation, each integer read is four bytes wide, the two container fields are adjacent, and the comparison fields occupy entry-relative bytes 4–7 and 8–11. Those byte spans are conditional on that interpretation, not independently verified target facts.

The interface passes addresses through integers. Portable representability of all relevant addresses, integer-to-pointer conversion behavior, alignment requirements, and byte order are not established by the supplied material.

## Behavior

### Traversal and selection

The function first reads the initial traversal address from the container’s field at offset `0x44`. That value becomes the first candidate address.

Before inspecting a candidate, the function reads the end marker from the container’s field at offset `0x48`. If the candidate address equals that marker, the function returns zero immediately. It does not read either comparison field at the end-marker address.

Otherwise, the function reads the candidate’s field at offset `0x04` and compares it with the first search value.

- If the first field does not match, the field at offset `0x08` is not read.
- If the first field matches, the function reads the field at offset `0x08` and compares it with the second search value.
- If both fields match, the function immediately returns the current candidate address.
- If either required comparison fails, the next candidate address is the current address plus 28 bytes.

The same process repeats, including a new end-marker read before each candidate inspection.

The function therefore chooses the earliest matching entry in traversal order. It does not continue searching for duplicates, validate uniqueness, or prefer any later entry.

### Observable read order

The established order of explicit memory accesses is:

1. One read of the initial traversal address.
2. An end-marker read before each candidate examination.
3. A read of the first comparison field, unless the candidate equals the end marker.
4. A read of the second comparison field only when the first comparison succeeds.

A successful match returns without another end-marker read. A failed candidate advances traversal before the next end-marker read.

This distinction matters for invalid memory, memory-mapped storage, or changing memory: the second field of a first-field mismatch is not part of the required read set, whereas the end marker is revisited throughout traversal.

These statements describe the accesses expressed by the supplied representation. Exact processor transactions, speculative accesses, and compiler transformations are not established.

### Termination and bounds

The only explicit exhaustion condition is equality between the current candidate address and the end marker. The function does not compare addresses by ordering, compute a record count, or check that an address lies inside an allocation.

For stable metadata and ordinary non-overflowing address arithmetic, a finite sequence of \(N\) candidates has an end marker equal to the initial address plus \(28N\). If none matches, traversal reaches that marker and returns zero.

An end marker that is not reachable by repeated 28-byte advances does not establish safe exhaustion. The function may encounter unreadable memory or arithmetic failure before any return. The supplied evidence does not justify specifying an infinite loop or wraparound as the guaranteed outcome.

## Acceptance examples

These examples are conditional behavioral criteria, not executed tests. Unless stated otherwise, assume stable memory, valid accesses, representable address arithmetic, and an environment supporting the described integer-address representation.

### Empty sequence

Given identical initial and end-marker addresses:

- The result is zero.
- The function reads the initial address and the end marker.
- It does not read either comparison field at that address.

This applies even when the shared address would not be valid for reading an entry, provided the container metadata reads themselves are valid.

### First candidate matches

Given a first candidate distinct from the end marker, with both comparison fields equal to the supplied search values:

- The result is the first candidate’s address.
- No later candidate is examined.
- The end marker is not reread after the matching fields are read.

### First field rejects a candidate

Given a candidate whose first field differs from the first search value:

- Its second comparison field is not read.
- Traversal advances by 28 bytes.
- The end marker is read again before the next candidate is examined.

An inaccessible second field alone therefore does not prevent rejection of that candidate when the first field differs.

### Second field rejects a candidate

Given a matching first field but a differing second field:

- Both comparison fields are read, in that order.
- That candidate is not returned.
- Traversal advances by 28 bytes.

### Duplicate matching entries

Given two matching candidates before the end marker:

- The earlier candidate in traversal order is returned.
- The later matching candidate is not examined.

### Exhaustion after mismatches

Given a reachable end marker after several nonmatching candidates:

- Each candidate is examined according to the conditional-read rules.
- When traversal reaches the marker, the result is zero.
- The marker address is not treated as another candidate.

### Candidate beyond a numerically smaller end marker

Given a candidate address numerically greater than the end marker but unequal to it:

- There is no explicit bounds-order rejection.
- The function attempts candidate inspection, subject to memory validity.
- No safe result is promised merely because an apparent range boundary has been crossed.

### Zero as a candidate address

Zero is not explicitly rejected as a candidate. If the execution environment permits the required accesses at offsets from address zero, the end marker is different, and the fields match, the returned value is zero.

Thus zero is operationally the exhaustion result but is not separately protected against collision with a successful zero-address match. In conventional environments, such a candidate is likely invalid; that environmental expectation is not a check performed here.
