# F-d496c13a4117

## Purpose

F-d496c13a4117 performs an indirect operation on a caller-supplied object and conditionally follows it with a second indirect operation. It returns the integer result of the first operation.

The first operation receives the address of a temporary four-byte value initialized from the second input. A result of exactly −1 suppresses the second operation. Every other result, including zero and other negative values, causes the second operation to be called with that result.

The purpose of the operations is not established. A dispatch-table interpretation is supported by the access pattern, but descriptions such as allocation, registration, acquisition, release, or cleanup would require additional evidence.

## Behavior

### Temporary value preparation

Before the first indirect operation is invoked, the function initializes a local four-byte storage location with the second input.

The first operation receives the address of this storage, not merely its initial contents. Consequently, the operation can observe that initial four-byte value and may modify the storage through the supplied address. The visible wrapper does not read the storage again after the operation returns.

This does not establish that the value is an output parameter, that the operation writes it, or that any change is communicated back to the caller. The caller supplied the value by value; the wrapper’s local copy is distinct from the caller’s original argument storage.

### First indirect operation

The wrapper accesses the object’s initial stored value as a dispatch-table base and uses byte offset 0x4c to obtain the first call target.

The first operation is invoked with five arguments in this logical order:

1. The original object address.
2. The address of the initialized local four-byte storage.
3. A callable address obtained from byte offset 0x4c through the object’s dispatch-table reference.
4. The unchanged fourth input.
5. The original object address again.

The first and fifth arguments therefore carry the same object address.

The dispatch entry used as the call target and the entry supplied as the third argument are represented as separate lookup expressions. Their evaluation order is not established by the supplied source representation. If the object’s dispatch reference and the relevant entry remain stable during call preparation, the third argument equals the selected call target.

Without that stability condition, equality is not guaranteed by this evidence. The contract does not collapse the two expressions into a single captured lookup, nor does it prescribe which expression is evaluated first.

The integer returned by this operation becomes the wrapper’s result and controls the conditional second operation.

### Result-dependent second operation

If the first operation returns exactly −1, the wrapper skips the second operation and returns −1.

For every other integer result, the wrapper performs a new dispatch lookup:

- It reads the object’s dispatch-table reference after the first operation has returned.
- It obtains a callable entry at byte offset 0x2c.
- It invokes that entry with the original object address followed by the first operation’s integer result.

The wrapper does not retain the original table reference for this second dispatch. If the first operation changes the object’s dispatch-table reference, the second operation is selected through the changed reference.

The second operation’s result is ignored. If it returns normally, the wrapper returns the integer originally obtained from the first operation.

There is no visible retry, result normalization, range validation, or additional success test. In particular:

- Zero takes the second-operation path.
- Positive values take the second-operation path.
- Negative values other than −1 take the second-operation path.

### Observable ordering

The visible sequencing establishes these boundaries:

1. The local four-byte value is initialized before the first operation begins.
2. The first operation completes before its result is tested.
3. The offset-0x2c lookup and second invocation occur only on the non-−1 path, after the first operation completes.
