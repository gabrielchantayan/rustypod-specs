# F-60e855c11286

## Purpose

F-60e855c11286 coordinates a consistency check over numbered objects associated with a handle. After an acquisition attempt, it establishes a temporary visitation map, invokes a metadata-based check, processes caller-supplied roots, and examines numbered entries according to their visitation state and a classification dependency.

“Page,” “root,” “free list,” and “read lock” are domain interpretations supported by diagnostic labels and usage. Their complete semantics are not established by the supplied evidence.

The function exposes two separate result channels: a 32-bit return value and a caller-provided 32-bit status output. On the map-based path, dependencies receive writable operation state containing both eventual results. A zero return does not independently establish that the check found no problems.

This contract describes ordinary execution in which dependencies return normally and all performed memory accesses and arithmetic are valid. Exceptional transfers and dependency-internal behavior remain unresolved.

## Interface

### Inputs and result

| Input | Width and interpretation |
|---|---|
| Handle | Address of a record containing at least two 32-bit words. Offset 0 supplies an owner or connection reference; offset 4 supplies the working-object reference. |
| Root-array address | Address of consecutive 32-bit entries, with a four-byte stride. Root eligibility comparisons use signed 32-bit interpretation. |
| Root count | Signed 32-bit traversal bound. A nonpositive count prevents root-array reads by the root loop itself. |

The return occupies 32 bits. No universal success/error encoding is established.

The function does not directly decrement the continuation budget. Dependencies receiving operation state can potentially change it. Loop continuation therefore depends on the value observed at each loop-condition check, not solely on the input value.

No explicit nonaliasing check exists. Overlapping output, handle, root, or object storage can affect later reads. This contract does not promise preservation where direct writes or dependency effects overlap those inputs.

## Behavior

### Entry and acquisition outcomes

The working-object reference is read from handle offset 4 before F-0b4658e20c99 is called without explicit arguments. After that call, the handle’s offset-0 word is read and written to working-object offset 4.

Consequently, the working-object address is captured before the entry dependency, but the word copied into it is obtained afterward.

Next, the function follows the working-object offset-0 reference and captures the referenced 32-bit field at offset 72. It then calls F-9a463b3fd053 with the handle.

A nonzero acquisition result selects the failure path:

1. F-96dd78c4ca33 receives the handle.
2. F-390b24edc64e receives an acquisition-failure diagnostic.
3. The diagnostic dependency’s 32-bit result is returned.

There is no direct status-output write, map allocation, or F-ce2b2a7a0121 call on this path. This absence of direct writes does not constrain dependency side effects.

### Initialization and bound selection

After a zero acquisition result, the function captures the current owner-like reference in operation state and stores the working-object reference there. The captured owner reference need not equal the one used before acquisition.

F-f3192f39e4f6 is called without explicit arguments, and its result initially supplies the state’s upper bound. The state’s status field is set to zero, followed by a direct zero write to the caller’s status output.

The function then reads the candidate bound at working-object offset 24 and copies the input budget into state. Bound selection uses a separate second read of offset 24:

- If the second read is nonzero, the candidate from the first read is selected.
- If the second read is zero, the fallback result from F-f3192f39e4f6 is selected.
- If that fallback is also zero, the empty-check path is taken.

For a stable object field, this means a nonzero object bound takes precedence over the fallback. The two reads must nevertheless remain distinct in the contract. For example, a first read of zero followed by a nonzero second read selects zero without taking the empty-check path.

F-f3192f39e4f6 is called even when the object-provided candidate is ultimately selected.

### Empty-check path

When the second candidate read and fallback are both zero, the function calls F-ce2b2a7a0121 with the working object, then F-96dd78c4ca33 with the handle, and returns zero.

No map is allocated. Neither root processing nor numbered-entry processing occurs. The final owner-field comparison is omitted.

The caller’s status output has already received a direct zero write. There is no final status write after the two terminal dependency calls, so preservation of that zero depends on their effects.

### Allocation and allocation failure

Outside the empty-check path, the selected bound is stored in operation state. F-391e3d30e634 receives a requested byte count corresponding to four bytes for each map index from zero through the bound:

**4 × (bound + 1)**

The calculation uses 32-bit integer expressions. No guard establishes that addition or multiplication is representable, or that the selected bound is nonnegative.

A zero allocation result selects this sequence:

1. F-ce2b2a7a0121 receives the working object.
2. The caller’s status output is directly set to 1.
3. F-96dd78c4ca33 receives the handle.
4. F-1983453691c7 receives the handle’s then-current offset-0 word, an allocation-failure diagnostic, and the size expression evaluated for that diagnostic.
5. Its result is returned.

The handle word used for the diagnostic is read after the handle-level terminal call. It is not guaranteed to equal the word copied into the working object at entry.

There is no map-release call on allocation failure.

### Map preparation and initial metadata check

On allocation success, every map slot from index zero through the current upper bound, inclusive, is directly initialized to zero. Each slot occupies four bytes. A negative upper bound skips this initialization loop; that does not establish safe behavior for the remaining path.

F-d7be9cfb4000 is called with:

- The 32-bit value 0x40000000.
- The working-object offset-28 value narrowed to signed 16-bit width.

One is added to its signed 32-bit result. If the resulting index is at most the current upper bound, the corresponding map slot is set to 1.

There is no lower-bound check. A resulting index of zero passes whenever the upper bound is nonnegative; a negative result can also pass the comparison and lead to an access before the map. Safe execution therefore requires more than the visible upper-bound condition.

The operation-state return field is then set to zero.

Two calls to F-d1e995cfb2d3 obtain metadata-derived values:

1. From the address 36 bytes beyond the reference reached through working-object offset 12 and intermediate offset 68.
2. From the address 32 bytes beyond a freshly evaluated instance of that reference chain.

The first call is not assumed to preserve the reference chain used by the second.

F-6775624e3900 then receives the operation-state address, the value 1, the second metadata result, the first metadata result, and a main-free-list diagnostic label.

This initial check occurs even when the budget is zero. Its effects can determine whether either subsequent loop runs.

### Root processing

Root positions are considered in ascending order, starting at zero. A position is visited only if it is below the signed root count and the current state budget is nonzero when the loop condition is evaluated.

For each visited position:

- The root is read as a 32-bit value.
- An initially zero root causes no root-specific dependency call.
- For an initially nonzero root, the current mode byte is tested.
- If that observed mode byte is nonzero and the initially read root is greater than 1 under signed comparison, F-dd9084b10921 receives the state address, that root, 1, 0, and 0.
- F-57c23a3626e9 then receives the state address, a fresh read of the same root-array entry, zero, and a root-list diagnostic label.

The second root dependency is selected by the initial nonzero test, but receives the reread value. It can therefore receive zero if the optional preceding dependency changes the entry to zero.

There is no intervening budget check between the optional call and F-57c23a3626e9. A budget change during either call can prevent later root positions from being visited, but does not cancel the already-selected second call for the current position.

Mode is evaluated for each visited nonzero root; an earlier observation does not establish the mode during a later visit. Negative nonzero roots reach F-57c23a3626e9 when visited, but do not qualify for the optional greater-than-1 processing.

### Numbered-entry processing

The scan begins at entry 1. It continues while the current entry is at most the current state upper bound and the state budget is nonzero.

For an initially zero map slot, F-c76bdec3f9e1 receives the retained working-object reference and the entry number. An unused-page report is sent to F-32091aaab4f3 if either:

- The classification result differs from the entry number; or
- The result equals the entry number and the subsequently tested mode byte is zero.

The report receives the state address, zero, an unused-page diagnostic, and the entry number. The map slot is reread after this first stage, whether or not a report occurred.

A second classification stage occurs if the slot was initially nonzero or is nonzero on that reread. F-c76bdec3f9e1 is called again. If its result equals the entry number and the then-observed mode byte is nonzero, F-32091aaab4f3 receives the state address and zero. No diagnostic payload is visible at this call site.

Consequences include:

- An initially zero slot can cause two classification calls in one iteration.
- An initially zero slot that remains zero does not enter the second stage.
- A zero slot classified as its own entry is not reported as unused when the tested mode is nonzero.
- The mode byte is not read for the first report decision when classification already differs, nor for the second report decision when classification differs.
- There is no budget check between these within-iteration operations.

The next loop condition observes the then-current bound and budget. Dependency changes can therefore shorten or extend subsequent processing, subject to valid arithmetic and storage.

1. F-ce2b2a7a0121 receives the retained working-object reference.
2. The current owner-like reference at working-object offset 0 is followed, and its offset-72 field is compared with the pre-acquisition capture.

## Acceptance examples

These are conditional acceptance criteria, not executed tests. They assume valid accesses, representable arithmetic, and normal dependency returns.

1. **Acquisition failure:** If F-9a463b3fd053 returns nonzero, handle-level termination precedes the acquisition diagnostic. No allocation or direct status-output write occurs. The diagnostic result is returned.

2. **Stable empty bounds:** If both candidate reads and the fallback are zero, the direct status-zero write precedes the working-object and handle terminal calls. The return is zero. Even a positive root count does not cause root traversal.

3. **Allocation failure:** With a stable selected bound of 12, the allocation request is 52 bytes. A zero allocation result leads to working-object termination, a direct status write of 1, handle termination, and the allocation diagnostic, in that order.

4. **Persistently zero budget:** With successful allocation and a valid positive bound, an input budget of zero does not suppress initialization, reserved marking, or the initial metadata check. If that check leaves the budget zero, both loops are skipped. Final comparison and terminal handling still occur.

5. **Four root visits:** Suppose the root count is four, roots remain 0, 1, 2, and −1 through their relevant reads, and the budget is nonzero at every loop-condition check needed to visit all four positions. Zero is skipped; 1, 2, and −1 each reach F-57c23a3626e9. Only root 2 can qualify for F-dd9084b10921, and it does so only if the mode byte observed during that visit is nonzero. No mode preservation across earlier calls is assumed.

6. **Budget exhaustion between roots:** Under the same root arrangement, if processing root 1 leaves the budget zero at the next loop-condition check, roots 2 and −1 are not visited. An initially nonzero budget alone does not require their processing.

7. **Current-root completion:** If the optional dependency for a visited root changes the budget to zero, F-57c23a3626e9 still executes for that position and receives the reread root. Later visits remain conditional on subsequent budget checks.

8. **Changed map slot:** If an initially zero slot becomes nonzero during its first-stage classification or report, the second classification stage executes without an intervening budget check. If the slot remains zero, that stage is skipped.

9. **Changed owner field:** A differing final owner-field value causes a report after working-object termination but before handle termination and map release, regardless of the remaining budget.
