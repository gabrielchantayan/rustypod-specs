# F-891c06385ffa

## Purpose

F-891c06385ffa initializes selected fields in caller-provided storage, conditionally obtains two auxiliary regions, optionally invokes another initializer, and reaches a registration operation through either a direct write or a dependency call.

Two normal-return statuses are established:

- **−50:** the original flags request mask 4 or mask 8 without mask 1.
- **0:** execution completes the registration branch. Auxiliary acquisition failure does not itself produce an error status; it instead triggers cleanup-like calls, clears two stored fields, and clears masks 4 and 8 from the current stored flags.

The result packs the object-address value and status into one 64-bit value. It is not merely a signed status.

Construction, allocation, cleanup, and registration are inferred roles. The supplied static evidence establishes calls and memory operations, but does not establish the dependencies’ semantic contracts.

### Return value

The represented result is 64 bits:

| Bits | Content |
|---|---|
| 63–32 | Current 32-bit object-address slot |
| 31–0 | Status word |

The low word is either:

- `0xFFFFFFCE`, interpreted as signed 32-bit −50; or
- `0x00000000`, interpreted as zero.

Address bits are packed without sign extension into the upper half. Consumers must extract the low word before interpreting the status.

The local object-address slot initially contains the supplied object address. The delegated registration dependency receives the address of that slot. If it changes the slot and returns normally, the final result reflects the replacement value. No such replacement is explicitly performed on the direct registration branch.

## Behavior

### Initial dependency call and writes

The first operation is a call to F-c67cb20988a1 with the supplied object address and size 88.

After that call returns, the function performs these 32-bit writes in order:

1. The externally supplied word to object offset 0.
2. The value 512 to object offset 40.
3. The original flags to object offset 4.
4. The value 16 to object offset 44.

The dependency may be intended to initialize the storage, but its byte-level effect is unknown. In particular, zero-initialization of the complete object is not an established postcondition.

These operations precede validation. Rejected input therefore still causes the initial dependency call and all four explicit writes.

### Flag validation

Validation uses the original flag argument, not a later read of the stored flags.

First, mask 8 is checked. If it is set while mask 1 is clear, the function returns status −50.

If execution continues and mask 4 is set, mask 1 is also required. Without it, the function returns status −50.

Thus either mask 4 or mask 8 requires mask 1. Other flag bits do not directly cause rejection in the supplied representation.

A rejection performs no subsequent explicit acquisition calls, optional initialization, byte-87 write, or registration. Earlier effects are not rolled back.

### Conditional acquisition

Mask 4 controls this stage. If it is clear, the entire stage is skipped, including its field-clearing and region-initialization operations.

When mask 4 is set and validation succeeds, the ordered operations are:

1. Call F-d33f6d597e5d with size 262,144.
2. Store its 32-bit result at object offset 20.
3. Call F-d33f6d597e5d with size 131,072.
4. Store its 32-bit result at object offset 24.
5. Read the current field at offset 20 for comparison against zero.
6. If that field is nonzero, compare the retained second return value against zero.

Both acquisition calls occur even when the first returns zero.

The decision is based on the **current offset-20 field after the second acquisition call**, together with the **retained second return value**. It is not based solely on the two originally returned values.

Consequently:

- Two nonzero return values do not guarantee the successful branch. The second dependency may have changed offset 20 to zero.
- A zero first return value does not, by itself, determine the eventual branch if the second dependency can change offset 20.
- The second check does not reload offset 24. The stored second-result field and the retained second return value have distinct roles.

No preservation of object fields by an acquisition dependency is assumed.

### Acquisition-failure branch

If the checked offset-20 field is zero or the retained second return value is zero, the function performs this sequence:

1. Call F-5e3309c9d083 with no explicit argument visible in the supplied representation.
2. Read the current offset-24 field and pass it to another call to F-5e3309c9d083.
3. Write zero to offset 20.
4. Write zero to offset 24.
5. Read the current stored flags at offset 4, clear masks 4 and 8, and write the result back.

The second cleanup argument is read after the first cleanup call. It must not be specified as necessarily equal to the original second acquisition result.

The flag update is a 32-bit read-modify-write using mask `0xFFFFFFF3`. It preserves all other bits of the field as read at that point. It does not reconstruct the flags from the original input.

The first cleanup call’s effective argument is unresolved. The evidence does not justify describing it as releasing the first acquisition result.

Execution continues after this branch. There is no acquisition-failure status and no early return here.

### Acquisition-success branch

This branch is selected only when both of the following hold at the decision point:

- The current offset-20 field is nonzero.
- The retained second return value is nonzero.

The function then calls F-c67cb20988a1:

1. With the current offset-20 field and size 262,144.
2. With the current offset-24 field and size 131,072.

The second field is read after the first initialization call returns. That dependency is not established to preserve offset 24.

These are guarantees about call selection and argument reads, not guarantees that the referenced regions remain usable or become zero-filled. In particular, the branch predicate does not independently validate the offset-24 value used by the second call.

### Optional initialization

After the acquisition stage, or directly after validation when mask 4 is clear, the original auxiliary argument is tested.

- Zero suppresses this call.
- Any nonzero value causes F-fac138f80b6d to receive the address at object offset 56 and the original auxiliary argument.

No dependency result is used by the visible function.

Acquisition failure does not suppress optional initialization. Its destination extent, data format, ownership effects, and error behavior remain unknown.

### Registration preparation

The function then performs these operations in order:

1. Read the global registration-container address.
2. Write zero to object byte 87.
3. Read the insertion-position pointer from offset 4 of the saved container address.
4. Read the boundary pointer from offset 8 of that container.
5. Compare the two pointer values for equality.

The global-address read precedes the byte write. The container-field reads follow it. No non-aliasing guarantee is supplied.

The byte-87 write occurs after optional initialization and therefore overwrites any earlier value at that byte. Later dependency effects are not constrained to preserve it.

### Equal insertion and boundary pointers

Equality selects F-06026af60735. Its arguments are:

1. A fresh read of the global registration-container address.
2. The saved insertion-position pointer.
3. The address of the local object-address slot.

The fresh global read is distinct from the earlier read used to obtain the compared fields.

This function performs no explicit entry write or cursor advancement on this branch. Whether the dependency grows storage, inserts the object, changes the local slot, or transfers ownership is not established.

If the dependency returns normally, the function returns status zero using the then-current object-address slot.

### Unequal insertion and boundary pointers

The function first writes the saved insertion position advanced by one 4-byte entry to offset 4 of the saved container.

It then tests the original insertion-position pointer:

- If nonzero, it writes the current object address as a 32-bit entry at that position.
- If zero, it skips the entry write.

Cursor advancement therefore precedes the entry write. A zero insertion position does not prevent the advancement write when the pointers compare unequal.

Only equality is tested. The function does not validate pointer ordering, available capacity, entry alignment, or address overflow. Safe pointer advancement and writable destination storage are preconditions, not consequences of this branch.

After completing the branch, the function returns status zero.

## Side effects

### Object storage

Initial writes occur even on validation failure. Acquisition-related fields are explicitly assigned only when mask 4 selects that stage. Without that stage, their contents depend on prior storage and the initial dependency.

The failure branch explicitly zeroes offsets 20 and 24 and clears masks 4 and 8 from the current stored flags. The successful branch does not explicitly clear those fields.

Byte 87 is zeroed on every path reaching registration, but not on a validation-rejection path.

Dependency calls may have additional effects on these fields. The explicit writes do not imply preservation afterward.

### Auxiliary memory and ownership

Two acquisition-like calls occur for valid requests containing mask 4. Their results are stored in the object.

On failure, two cleanup-like calls occur, but release of either acquired region is not established:

- The first effective cleanup argument is unknown.
- The second argument is the current offset-24 field and can be zero.
- Null handling and release semantics are unknown.

On the successful branch, this function performs no explicit cleanup of the auxiliary regions before returning.

Ownership transfer, eventual destruction responsibility, and leak-freedom require dependency and lifecycle contracts not supplied here. No explicit operation acquires or releases the caller-provided object itself.

### Shared state and failure handling

The direct registration branch changes the container cursor and conditionally writes an entry. Dependencies may also modify shared state, object storage, or globals.

There is no visible synchronization, rollback, or conversion of dependency failures into a distinct status. Faults, nonlocal transfers, and dependencies that do not return are outside the established normal-return outcomes.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. They assume valid accessed storage and dependencies that return normally. Preservation assumptions are stated where needed.

1. **Flags 0; auxiliary argument zero.**  
   The initial call and four field writes occur. Acquisition and optional initialization are skipped. Byte 87 is zeroed, the applicable registration branch executes, and the returned status is zero.

2. **Flags 8.**  
   Initial side effects occur, followed by status −50. No acquisition, optional initialization, final-byte write, or registration is explicitly performed.

3. **Flags 4.**  
   Validation rejects the request after initial writes. Neither acquisition call occurs.

4. **Flags 9.**  
   Validation succeeds. Mask 8 does not independently select acquisition; mask 4 is clear. Registration remains reachable.

5. **Flags 5; successful decision predicate.**  
   Both acquisition calls occur in size order 262,144 then 131,072. If the current offset-20 field is nonzero when checked after the second call, and the retained second return value is nonzero, the successful branch is selected. Both region-initialization calls occur if they return normally. The second call uses offset 24 as read after the first initialization call; usable addresses require additional conditions.

6. **Flags 5; both acquisition returns nonzero, but offset 20 changed to zero.**  
   Suppose the second acquisition dependency returns a nonzero value while changing the object’s offset-20 field to zero. The function takes the cleanup branch, not the region-initialization branch. Nonzero or usable return values alone are insufficient.

7. **Flags 13; retained second return value zero.**  
   Both acquisition calls occur, then cleanup is selected. Offsets 20 and 24 are explicitly cleared. If the stored flags are still 13 when read for the update, they become 1. Execution continues toward registration and status zero.

8. **Nonzero auxiliary argument following acquisition failure.**  
   F-fac138f80b6d still receives object offset 56 and the original auxiliary argument. Failure does not suppress the call.

9. **Unequal registration pointers; insertion position nonzero.**  
   The cursor write advancing by four bytes occurs before the object-address entry write.

10. **Unequal registration pointers; insertion position zero.**  
    The cursor write occurs, but no entry is written through the zero pointer. Validity of this container state is documented_only.

11. **Equal registration pointers; dependency changes the local address slot.**  
    If F-06026af60735 writes a replacement 32-bit value through its third argument and returns normally, that replacement occupies the upper half of the final result. The low half remains zero.
