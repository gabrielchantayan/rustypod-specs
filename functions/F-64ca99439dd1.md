# F-64ca99439dd1

## Purpose

F-64ca99439dd1 obtains a starting offset and a corresponding extent from an indexed offset table associated with a caller-supplied context.

Two table encodings are supported:

- Two-byte unsigned, big-endian entries, scaled by two after decoding.
- Four-byte unsigned, big-endian entries, used without scaling.

The return value is the selected starting offset. A separate caller-provided output receives the extent. Ordinarily, the extent is the next offset minus the selected offset. When the prospective next offset is numerically smaller than the selected offset, a context field supplies an alternative endpoint.

An index outside the table produces a zero return value and a zero extent. A final table entry has no successor; its own offset is used as its prospective endpoint, normally producing a zero extent.

These are established behaviors of the supplied static representation. Interpreting the table as boundaries of stored objects, or the alternative endpoint as a total data length, is inferred intent rather than an established data-format definition.

## Interface

### Inputs

The function accepts three arguments:

1. **Context address.** A 32-bit address-bearing value identifying a readable context with the fields listed below.
2. **Entry index.** An unsigned 32-bit integer.
3. **Extent-output address.** An address identifying writable storage for one 32-bit integer.

The static representation uses a signed 32-bit integer type for the context address. Operationally, that argument is used as an address base, not as a signed numerical quantity.

### Context layout

Offsets below are byte offsets from the context address.

| Offset | Width | Access | Established role |
|---|---:|---|---|
| `0x0D2` | 16 bits | Read only for an in-range index | Encoding selector: zero selects two-byte entries; every nonzero value selects four-byte entries |
| `0x298` | 32 bits | Read only when the prospective endpoint is smaller than the start | Alternative endpoint |
| `0x2B4` | 32 bits | Always read | Unsigned entry count |
| `0x2B8` | 32 bits | Read only for an in-range index | Address of the encoded offset table |

The context fields are native typed loads. Their byte order is not independently established by the snippet. In contrast, table entries are explicitly assembled from bytes in big-endian order.

The selector is tested only for equality to zero. No particular nonzero value has a distinct meaning.

### Outputs

- **Return:** an unsigned 32-bit starting offset.
- **Output storage:** one 32-bit extent written through the third argument.

Although the output storage is typed as a signed integer, the calculation is a 32-bit subtraction. Its bit pattern can therefore represent a negative signed value when the unsigned difference exceeds the maximum signed 32-bit value. The representation supplies no separate success indicator.

### Preconditions

For the accesses actually taken:

- The context count field must be readable.
- The extent-output address must be writable for a 32-bit integer, including when the index is out of range.
- An in-range index requires readable selector and table-address fields.
- The selected table entry must be readable.
- If the successor boundary condition succeeds, the successor entry must also be readable.
- If the prospective endpoint is smaller than the start, the alternative-endpoint field must be readable.
- Address calculations and comparisons must refer to a valid, consistently laid-out table region.

No explicit null, alignment, address-overflow, or accessible-memory validation appears. Behavior for invalid addresses or unsupported alignment is not established.

## Behavior

### Initial selection and out-of-range handling

The function first reads the unsigned 32-bit entry count from the context.

It compares the unsigned index against that count. If the index is greater than or equal to the count:

- It does not read the table-address field.
- It does not read the encoding selector.
- It does not read table bytes.
- It does not read the alternative endpoint.
- It writes zero to the extent output.
- It returns zero.

A count of zero therefore makes every index out of range. An index with its high bit set remains a large unsigned index; it is not treated as a negative index.

### In-range setup

For an in-range index, the function reads the table address and then the 16-bit encoding selector.

It selects an entry width of two bytes for a zero selector and four bytes otherwise. The selected entry begins at the table address plus the index multiplied by that width.

The count determines the calculated end of the encoded table. Successor availability is tested by comparing the address immediately after a complete successor entry with that calculated end. Equality satisfies the test.

For ordinary valid address arithmetic, a successor is available exactly when the selected entry is not the last entry. The implementation expresses that condition through address arithmetic rather than solely through an index comparison.

### Two-byte encoding

Each encoded entry is an unsigned 16-bit big-endian quantity. Its effective offset is twice that quantity.

Consequently:

- Effective offsets range from 0 through 131,070.
- Every effective offset is even.
- Scaling occurs in a 32-bit value, so the largest decoded entry does not overflow during scaling.

The current entry is first decoded to initialize a prospective endpoint. If a complete successor fits within the calculated table extent, that successor is decoded and replaces the prospective endpoint.

The current entry is then decoded again to obtain the returned start. Both the start and the prospective endpoint are multiplied by two.

The repeated current-entry read matters when describing observable access behavior. For a final entry, the prospective endpoint comes from the earlier read, while the start comes from the later read. With stable memory they are equal; with independently changing memory, equality is not guaranteed.

### Four-byte encoding

Each entry is an unsigned 32-bit big-endian quantity. The first byte contributes bits 31–24, followed by bits 23–16, bits 15–8, and bits 7–0.

The current entry is decoded once to obtain the start. The same decoded value initially supplies the prospective endpoint.

If a complete successor fits within the calculated table extent, the successor is decoded and replaces that endpoint.

There is no scaling or signed interpretation of decoded table entries. Values from zero through 4,294,967,295 participate in the endpoint comparison as unsigned 32-bit quantities.

### Extent calculation

After decoding, the function compares the prospective endpoint with the start using an unsigned comparison.

- **Endpoint at least as large as start:** the extent is endpoint minus start.
- **Endpoint smaller than start:** the function reads the context’s alternative endpoint and uses alternative endpoint minus start instead.

The alternative endpoint does not undergo another monotonicity check. If it is also below the start, the function still performs the subtraction. There is no clamping, rejection, or error return.

Subtraction produces a 32-bit result. In particular, the alternative-endpoint path may yield a wrapped result. The signed output type does not imply that the function verifies a nonnegative signed extent.

After calculating the extent, the function writes the output once and returns the previously obtained start.

### Final-entry behavior

With stable valid table memory, the final entry has no successor, so its prospective endpoint equals its start. Its extent is zero.

The alternative endpoint is **not** automatically used for the final entry. It is consulted only when the prospective endpoint compares below the start. An interpretation in which the final entry always extends to the alternative endpoint would contradict the supplied behavior.

## Side effects

The sole explicit write is the final 32-bit extent-output store. The function does not explicitly modify context fields or table bytes.

All table and conditional context reads precede that store. Therefore, if the extent-output storage overlaps a context field or table bytes, the write can alter caller-owned data, but it does not change values already read during this invocation. Whether a particular overlap is valid under the original execution environment’s alignment and aliasing rules is not established.

The function contains no explicit allocation, deallocation, ownership transfer, callback, or external call. Nothing indicates that it acquires ownership of either the context or the table.

There is no explicit error object, diagnostic, logging, or recovery path. Invalid-memory behavior belongs to the execution environment and is not converted into a defined function-level error result.

The supplied representation establishes the ordering of the major operations described above. It does not establish a strict left-to-right order for individual byte loads within a multi-byte decoding expression. It also supplies no synchronization or coherent-snapshot mechanism for concurrently changing storage.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless stated otherwise, all addresses are valid, address arithmetic does not wrap, memory is stable, and output storage is separate from input storage.

### Empty table

Given a count of zero and any unsigned index:

- The return is zero.
- The stored extent is zero.
- No selector, table-address, table-byte, or alternative-endpoint read is required.

### Index equal to the count

Given a count of three and an index of three:

- The return is zero.
- The stored extent is zero.

An index equal to the count is not a valid entry.

### Two-byte decoding and scaling

Given a zero selector and consecutive entries with bytes `00 03` and `00 09`, selecting the first entry:

- The start is 6.
- The prospective endpoint is 18.
- The stored extent is 12.
- The alternative endpoint is not read.

### Four-byte decoding

Given a nonzero selector and consecutive entries encoding `0x01020304` and `0x01020314`, selecting the first entry:

- The return is `0x01020304`.
- The stored extent is 16.
- The alternative endpoint is not read.

The result is independent of the host byte order used for native context fields, provided those context fields already contain the stated values.

### Equal neighboring offsets

Given consecutive effective offsets of 40 and 40:

- The return is 40.
- The stored extent is zero.
- Equality does not activate the alternative endpoint.

### Decreasing neighboring offsets

Given consecutive effective offsets of 100 and 20, with an alternative endpoint of 160:

- The return is 100.
- The stored extent is 60.
- The alternative endpoint is read because 20 is unsigned-less-than 100.

### Alternative endpoint also below the start

Given a start of 100, a prospective endpoint of 20, and an alternative endpoint of 80:

- The return is 100.
- The extent bit pattern is `0xFFFFFFEC`, the 32-bit subtraction result.
- Under conventional two’s-complement signed interpretation, the stored integer is −20.
- No additional rejection or correction occurs.

### Final entry

Given a stable table whose final effective offset is 100, selecting that final entry:

- The return is 100.
- The stored extent is zero.
- An alternative endpoint of 160 does not change the result and is not read.

### Large unsigned extent

In four-byte mode, given a start of zero and a successor of `0xFFFFFFFF`:

- The return is zero.
- The extent bit pattern is `0xFFFFFFFF`.
- The alternative endpoint is not read.
- The output may appear as −1 when interpreted as a conventional signed 32-bit integer; it is not a separately signaled error.
