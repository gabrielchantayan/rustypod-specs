# F-b207c4d0351b

## Purpose

F-b207c4d0351b performs two queries, invokes three externally targeted state operations, searches a globally referenced node structure, and conditionally changes one byte in a selected node’s payload. A changed byte is followed by two virtual calls.

The 32-bit return value reports only the outcome of the final F-f063d8ade9f7 call:

- `1` when that call returns zero.
- `0` when that call returns nonzero.

A return value of `1` does not establish that a byte changed or that any notification occurred.

“Search,” “container,” “header,” “payload,” and “notification” describe observed roles or inferred intent. The contract does not assume a standard container implementation or conventional comparator semantics.

## Interface

### Input and output

The sole input is a 32-bit address-like value identifying an object. The function directly reads only the 32-bit field at byte offset `0x2c` within that object. It reads this field twice, once for each initial query.

The output is a 32-bit word containing zero or one on normal return. No separate error code is constructed.

### Required validity

Each reached memory access requires an appropriately readable or writable address. Each reached direct or indirect call requires a valid callable target. In particular:

- The input field must be readable at both query-argument reads.
- Container and header addresses must support the fields accessed through them.
- Traversed nodes must support the comparison input and whichever link is read.
- A selected node used on the final zero-result path must provide a readable payload pointer at `+0x14`.
- The payload state byte must be readable and, when different from the desired value, writable.
- A notification receiver must support virtual dispatch through its first word and table entry `+0x58`.

The function performs no explicit null, bounds, alignment, lifetime, or callable-target validation. Invalid accesses and dependency failures do not have an established recovery result.

### Widths and layouts

Offsets are byte offsets. Address-like values, ordinary words, saved node values, and key words have the supplied representation’s 32-bit width.

The search key occupies two consecutive 32-bit words, eight bytes in total:

1. A word loaded from a global token.
2. The saved second query result masked with `0xff`.

The second word is initially between 0 and 255. Dependencies receive the key’s address, so its contents are not established as immutable.

The desired payload byte is independently derived from the saved second query result. It is not subsequently obtained from the second key word. Changes to the key therefore need not change the desired byte.

No checked address arithmetic is visible. The offsets describe accesses in the supplied 32-bit representation, not a guarantee of valid addressing near an address-space boundary.

## Behavior

### 1. Perform both queries

The function reads the input field at `+0x2c` and passes its value to F-73272d0d9682. It saves whether that call’s result is nonzero.

It then reads the same input field again and passes the newly read value to F-8175799f844a. The second result is saved as a 32-bit unsigned value.

Both calls occur on the normal path, regardless of the first result. If the first call changes the input field, the second query receives the changed field value rather than the first query’s argument.

### 2. Invoke three state operations

U01 is called three times. Each call obtains its target argument from a different global location. The Boolean arguments are, in order:

1. Whether the first query was nonzero **or the full 32-bit second query result was nonzero**.
2. Whether the first query was nonzero.
3. Whether the first query was nonzero.

The first Boolean does not use a low-byte-only test. A second result of `0x00000100` makes that Boolean true even though its low byte is zero.

The calls’ return values are not used. Their effects are unknown and may affect later reads, including later state targets and the globals used for search initialization.

### 3. Initialize search state with three distinct container-global reads

Initialization follows this order:

1. Read the container global and retain that address for later comparison-context and header accesses.
2. Load the global token into the first key word.
3. Independently reread the container global. Read that container’s header field at `+0x10`, then read the header’s `+0x04` field to obtain the initial traversal node.
4. Independently reread the container global again. Read that container’s header field at `+0x10` to obtain the initial candidate.
5. Initialize the second key word from the saved second query result masked with `0xff`.

The initial traversal node and initial candidate are not derived from one shared header snapshot. Their container addresses come from separate global reads, and their header fields are separately read.

The first captured container supplies the comparison context throughout the search and the later header reads. It does not supply the initial traversal-root or initial-candidate accesses merely by virtue of having been captured first.

If the container global and header fields remain stable, these accesses can resolve to the same container and header. Stability is an external condition, not an enforced property.

### 4. Traverse using zero-versus-nonzero comparisons

While the traversal node is nonzero, F-bcefa5957e76 is called with:

1. The first captured container address plus `0x19`.
2. The current traversal node address plus `0x10`.
3. The address of the two-word key.

Only zero versus nonzero matters:

- **Zero result:** read the current node’s `+0x08` link, use that link destination as the next traversal node, and assign the same destination to the candidate.
- **Nonzero result:** read the current node’s `+0x0c` link and use it as the next traversal node. The function makes no explicit candidate assignment on this branch.

The zero-result branch records the link destination, not the node just compared. A zero `+0x08` link therefore sets both traversal and candidate values to zero.

Negative and positive nonzero comparison results take the same branch. No ordering convention beyond these predicates is established.

There is no explicit iteration limit or cycle detection. Normal completion requires the traversed links eventually to produce zero and every reached dependency to return normally.

### 5. Validate the candidate or select a fallback header

After traversal, the function reads a header from `+0x10` of the first captured container into a separate local slot.

It calls F-f063d8ade9f7 with the addresses of the candidate slot and that header slot.

If the result is nonzero, it selects the fallback path.

If the result is zero, it:

1. Calls F-539f08165386 with the candidate slot’s current value.
2. Calls F-bcefa5957e76 with the captured container plus `0x19`, the address of the key, and the 32-bit value returned by F-539f08165386.

This comparison uses a different argument arrangement from traversal: the key is the second argument rather than the third.

If this comparison returns zero, the candidate slot is selected. Otherwise, the fallback path is selected.

The fallback path freshly reads the first captured container’s header field at `+0x10` into another slot. It does not simply reuse the header value supplied to the preceding F-f063d8ade9f7 call.

Address-passing dependencies are not assumed to preserve their pointed-to slots. Candidate use and selection follow the contents remaining after those calls.

### 6. Make the final comparison

The selected slot’s value is copied into a final selected-value slot. The function separately reads another header value from the first captured container’s `+0x10` field.

F-f063d8ade9f7 receives the addresses of these two slots.

If it returns nonzero, the function returns `0`. The visible remainder performs no payload-byte access, receiver acquisition, or virtual notification on this path.

If it returns zero, execution continues using the final selected-value slot as it exists after the call. Thus the final dependency may affect which node is subsequently accessed if it changes that slot.

### 7. Compare and possibly write the payload byte

On the final zero-result path, the function reads the selected node’s payload pointer at `+0x14`, then reads the byte at payload offset `100`.

That byte is interpreted as an unsigned value from 0 through 255 and compared with the saved second query result masked with `0xff`.

If equal, the function returns `1` without an explicit payload write, receiver acquisition, or virtual notification.

If different, the function rereads the selected node’s payload pointer at `+0x14` and writes the saved second query result’s low eight bits to offset `100` through that newly read pointer.

The pointer used for the write is not explicitly reused from the comparison read. If the pointer field changes between these accesses, the comparison and write can address different payloads.

### 8. Perform two virtual notifications

After the byte write, F-9d0ecc5f6adf is called once to obtain a receiver.

Two virtual calls follow, using that same receiver address. Each dispatch obtains its target through the receiver’s first word and table entry at `+0x58`.

Each call receives:

- The receiver.
- An event token read from a global location.
- The current first word of the local key.

The two event-token locations are distinct, and the calls occur in a fixed order. The second call reevaluates its dispatch chain and argument reads; it does not explicitly reuse the first target or a separately preserved original key token.

Consequently, effects of the first notification can affect the second dispatch and its arguments if they change the relevant accessible state. No such preservation or mutation is assumed.

Notification return values are unused. After both calls return normally, the function returns `1`.

## Side effects

The function explicitly performs three unconditional U01 calls, search-related dependency calls, and the reads described above. On the changed-byte path, it performs at most one explicit byte write, followed by one receiver-acquisition call and two virtual calls.

There is no explicit allocation, deallocation, receiver release, synchronization, transaction, or rollback.

No ownership transfer is established for the input object, container, nodes, payload, receiver, tokens, or dependency-produced values. In particular, absence of an explicit receiver release does not establish that the receiver is borrowed or globally owned.

Addresses of local key and selection slots are supplied to dependencies. Their storage exists during this invocation. Whether dependencies retain those addresses, and whether any such retention is valid, is **documented_only**.

Unknown dependencies are not assumed to preserve globals, referenced objects, or slots passed by address. Repeated reads must therefore remain distinct parts of the contract.

If a notification does not return normally, the payload write has already occurred. No compensating action is visible.

## Acceptance examples

These are conditional static predictions, not executed tests. Unless an example states otherwise, dependencies return normally and preserve the relevant state.

1. **Both queries return zero.** The Boolean arguments are false, false, false. The second key word is initialized to zero. Search still occurs; the return value is not determined by these query results.

2. **First query is nonzero and second query is zero.** All three Boolean arguments are true. The desired byte remains zero.

3. **First query is zero and second query returns `0x00000100`.** The Boolean arguments are true, false, false. The initial second key word and desired byte are zero.

4. **The initial container-global reads yield three different valid addresses.** Comparison context and later header reads use the first captured address. The traversal root comes through the second address’s header. The initial candidate comes from the third address’s header. The contract does not merge these origins.

5. **The global container address is unchanged, but its header field changes between initial header reads.** The traversal root can come from one header while the initial candidate is another header. A single shared header snapshot is not required.

6. **A traversal comparison returns zero and the `+0x08` link is zero.** Traversal ends with a zero candidate. The first F-f063d8ade9f7 call still occurs; there is no independent null-candidate rejection before it.

7. **The final F-f063d8ade9f7 returns nonzero.** The function returns `0` without its subsequent payload access or notifications. Earlier calls and their effects have already occurred.

8. **The final comparison returns zero and the payload byte already matches.** The function returns `1` without an explicit write or notifications.

9. **The final comparison returns zero, the desired byte is `0xab`, and the existing byte is `0x12`.** With stable pointers, the function writes `0xab`, obtains one receiver, and makes both virtual calls in order. Normal completion returns `1`.

10. **A dependency changes the key’s second word.** Later key comparisons can observe that change. The desired payload byte still comes from the saved query result, not the modified key word.

11. **The first notification changes the receiver’s dispatch table.** The second dispatch uses the table entry read for that second call, rather than necessarily invoking the first target again.

- Whether the node structure is a tree or an ordered associative container.
- Comparator ordering conventions and the relation implemented by F-f063d8ade9f7.

- Dependency mutation, retention, ownership, lifetime, and reentrancy rules.
- Notification semantics and dependency failure behavior.
- Required synchronization and whether concurrent mutation is supported.
- Faults, exceptions, nonlocal exits, and address-arithmetic behavior outside valid-address preconditions.

A conventional lookup-and-notify interpretation is plausible intent. It does not override the distinct initial global reads, link-destination candidate assignment, mutable address-passed slots, or final comparison predicate.
