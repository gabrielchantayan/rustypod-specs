# F-10323b21a777

## Purpose

F-10323b21a777 compares a supplied 32-bit expected value with shared state and, on normal completion, writes a two-word result. Before the comparison, it writes an incremented counter value and conditionally initializes the shared value through a guard-controlled sequence.

The first result word comes from either a fresh shared-value read or F-8157a180d901. The second result word is zero.

A saved counter value selects the result source:

- Zero or 4,294,967,295 selects the shared-value read.
- Every other value selects F-8157a180d901, followed by an additional counter decrement.

The initial counter-address capture, counter entry-value read, and increment-store destination involve three separate evaluations of the counter address-bearing reference. Subsequent decrements use the captured address. Describing all these operations as updates to one object requires an explicit address-stability assumption.

**Inferred intent:** the guard sequence resembles one-time initialization, and the counter-dependent selection may distinguish nesting levels. Neither interpretation establishes synchronization, ownership, or balanced counter updates.

## Interface

### Inputs

The function accepts:

1. **Result destination:** an address for two consecutive 32-bit words.
2. **Expected value:** a 32-bit integer compared with the captured shared-value object after guard handling.

Normal completion requires writable storage at the destination base and four bytes later. The body performs no explicit null, bounds, alignment, or accessibility checks.

The expected value is also the argument to F-feee9156a257 on mismatch. It is not automatically copied into the result.

### Shared storage and references

| Storage or reference | Established use |
|---|---|
| Shared-value address-bearing reference | Evaluated once to capture the shared-value address |
| Guard address-bearing reference | Evaluated for address capture and separately for each reached guard dependency call |
| Counter address-bearing reference | Evaluated for address capture, again for the entry read, and again for the increment-store destination |
| Initialization-value storage | Read when initialization is selected |

| Captured guard object | Read as an unsigned 32-bit word; only its least-significant bit controls guard acquisition |

Counter operands and arithmetic are unsigned and 32-bit. Addition and subtraction wrap modulo \(2^{32}\). Shared values, the expected value, and the first output word are represented as 32-bit integers.

The result consists of two 32-bit words at offsets zero and four bytes. Pointer width and byte order are not established.

### Outputs

There is no explicit return value.

On normal completion, the function writes:

1. The selected 32-bit result at the destination base.
2. A 32-bit zero four bytes later.

These are ordered, separate stores, not an established atomic two-word publication. A failure during the second store can occur after the first has completed.

### Preconditions and ownership

Each reached memory operation requires accessible storage for that operation. Captured addresses must remain usable through their last reached access; capturing an address neither establishes ownership nor extends storage lifetime.

The body explicitly allocates and releases no memory. Dependency ownership behavior is unknown. No dependency may be assumed to preserve, retain, release, or leave accessible any object.

Storage disjointness is not checked. The destination, shared objects, and address-bearing references may affect one another if their storage overlaps. Arithmetic examples that describe independent objects require the stated separation and preservation assumptions.

## Behavior

### Address capture and initial counter operations

The function first captures, in order:

1. The shared-value address.
2. The guard address.
3. The counter address.

It then evaluates the counter reference again and reads the unsigned 32-bit value at that address. This saved entry value later controls result selection.

Next, it evaluates the counter reference again to obtain the increment-store destination. It writes the saved entry value plus one, modulo \(2^{32}\), to that destination.

These evaluations have distinct roles:

- The captured counter address selects the object used by later decrements.
- The entry-read address selects the object supplying the saved value.
- The increment-store address selects the object receiving the saved value plus one.

The increment does not read its destination to obtain an operand. If the entry-read and increment-store addresses differ, the latter object receives the former object’s value plus one.

No dependency call occurs between these counter-reference evaluations. This does not independently establish reference stability or authorize concurrent changes under an unspecified execution model.

The increment store precedes guard handling, every dependency call, comparison, and output publication.

### Guard decision and initialization

The function reads the captured guard object and tests its least-significant bit.

- If the bit is set, guard acquisition and initialization are skipped.
- If the bit is clear, the function calls F-b255b26284e6.

The acquisition argument is obtained by evaluating the guard reference at the call site. It need not equal the captured address used for the bit test.

The acquisition result is tested for zero versus nonzero:

- Zero skips both initialization and F-d08d3ca17b81.
- Nonzero selects initialization and the completion call.

When initialization is selected, the function reads the 32-bit initialization value and writes it into the captured shared-value object. It then calls F-d08d3ca17b81 with an address obtained from another evaluation of the guard reference.

Consequently, the guard-bit test, acquisition call, and completion call can use different addresses if the reference changes. The body does not enforce equality among those addresses.

The initialization write precedes the completion call. Comparison occurs only after that call returns normally. Any completion-call mutation of the shared value can therefore affect the comparison.

Only the least-significant guard bit matters. A nonzero guard word with that bit clear still selects acquisition.

The body contains no explicit guard-object write. Guard mutation, synchronization, blocking, and failure semantics remain unknown.

### Expected-value comparison and mismatch

After guard handling and any resulting calls return, the function reads the captured shared-value object and compares its 32-bit value with the expected value.

On mismatch, it calls F-feee9156a257 with the expected value.

The supplied static representation annotates this dependency as non-returning. Under that annotation:

- The earlier local increment store has occurred.
- Any selected initialization write has occurred.
- Neither subsequent local counter decrement is reached.
- Neither output store is reached.
- No subsequent local rollback code is reached.

These facts describe execution order, not persistence. F-feee9156a257 may overwrite affected storage, reverse earlier effects, invalidate storage, or otherwise change observable state before it terminates or transfers control. Resulting memory contents and persistence of earlier effects therefore remain dependent on this unknown callee.

The body has no local error-result publication or explicit recovery operation.

The non-returning annotation is static evidence, not runtime proof. If the dependency unexpectedly returns, the visible continuation proceeds to the ordinary decrement and result-selection logic; there is no additional explicit termination barrier in the supplied body.

### Ordinary counter decrement

On the ordinary matching path, the function reads the unsigned 32-bit value at the captured counter address and writes that value minus one back to the same address, modulo \(2^{32}\).

This is a fresh read. The decrement does not restore the saved entry value and does not reevaluate the counter reference.

The decremented object can differ from the initial entry-read object or increment-store destination. Even if all addresses are equal, intervening dependency effects or overlapping writes can change the decrement operand.

### Result selection and additional decrement

Selection uses the saved entry value, not a newly read counter value. The function adds one using unsigned 32-bit arithmetic and tests whether the wrapped result is less than two.

The direct-read branch is selected exactly for:

- Saved value zero, whose incremented value is one.
- Saved value 4,294,967,295, whose incremented value wraps to zero.

On this branch, a fresh read of the captured shared-value object supplies the first output word.

This read follows the ordinary decrement and is separate from the comparison read. A successful comparison does not guarantee that the output equals the expected value. For example, overlapping storage could allow the intervening decrement to change the shared value, if such aliasing is permitted by the execution environment.

For every other saved entry value, the function:

1. Calls F-8157a180d901 with the 32-bit integer zero.
2. Saves its 32-bit result for output.
3. Reads the current unsigned value at the captured counter address.
4. Writes that value minus one back there, modulo \(2^{32}\).

The additional decrement follows every normal return from F-8157a180d901, regardless of the returned value. It uses the captured address and freshly read contents, even if the dependency changes the counter reference or the counter object.

If a dependency does not return normally, later operations on that path are not established as occurring.

### Result publication

After selecting the result and completing all reached decrements, the function stores the result at the destination base and then stores zero four bytes later.

No explicit shared-object or counter access follows these output stores.

Output aliasing can overwrite shared storage or an address-bearing reference. The function performs no disjointness enforcement or rollback.

## Side effects

### Explicit writes

Depending on the path, the body performs:

- One increment store through a separately evaluated counter reference.
- One initialization write to the captured shared-value object.
- One ordinary decrement at the captured counter address.
- One additional decrement there after a normal return from F-8157a180d901.
- Two ordered output stores on normal completion.

The initial increment and later decrements must not be summarized unconditionally as changes to one counter object.

If all three initial counter-reference evaluations designate the same object, storage is disjoint, no other operation changes that object, and execution completes normally:

- The direct-read path leaves the counter equal to the saved entry value.
- The dependency-result path leaves it equal to the saved entry value minus one, modulo \(2^{32}\).

Without those conditions, these net-change conclusions do not follow.

On mismatch, the increment store has already occurred, but the annotated non-returning call prevents subsequent local decrements and output stores from being reached. This does not establish that any object remains incremented: the mismatch dependency may change or invalidate it.

### Ordering and visibility

Established local order includes:

- Increment store before guard handling.
- Initialization write before the completion call.
- Completion’s normal return before comparison.
- Successful comparison before the ordinary decrement.
- Result selection and any additional decrement before output publication.

The evidence does not establish atomicity, memory barriers, data-race safety, or a language-level concurrency guarantee.

Memory-access failures can occur after earlier operations. No explicit fault recovery is present. Dependency effects, including any reversal of earlier writes, remain outside the supplied implementation evidence.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

### Stable counter reference, zero entry

Assume all initial counter-reference evaluations designate one object containing zero, the guard bit is set, the shared value equals the expected value, storage is disjoint, and no other operation changes the relevant objects.

The increment writes one. Guard dependencies are skipped. Comparison succeeds, and the ordinary decrement writes zero.

A fresh shared-value read supplies the first output word, followed by a zero store. F-8157a180d901 is not called.

### Distinct counter-reference evaluations

Conditionally assume the execution environment permits the three evaluations to designate different accessible objects:

- Capture selects an object containing ten.
- Entry read selects another object containing one.
- Increment store selects a third object.

Also assume a set guard bit, successful comparison, disjoint storage, and no dependency mutation of the captured counter.

The increment store writes two into the third object. The ordinary decrement changes the captured object from ten to nine. Saved entry value one selects F-8157a180d901 with argument zero. After its normal return, the additional decrement changes the captured object to eight. The destination receives the dependency result followed by zero.

The entry-read object is not incremented merely because it supplied the saved value. Whether changing-reference execution is supported remains documented_only.

### Initialization selected

Assume the captured guard bit is clear and F-b255b26284e6 returns nonzero normally.

The initialization value is written to the captured shared-value object before F-d08d3ca17b81 is called. Comparison follows completion’s normal return and uses the shared object’s contents at comparison time.

If acquisition changes the guard reference, completion receives its later value, not necessarily the acquisition argument. No preservation of the initialization write by completion is assumed.

### Acquisition returns zero

With a clear captured guard bit and a zero acquisition result, this function performs neither the initialization write nor the completion call. It compares the expected value with the captured shared-value object’s then-current contents, which may include acquisition effects.

### Mismatch

If the comparison finds unequal values, F-feee9156a257 receives the expected value.

The increment store and any selected initialization write have occurred before this call. Under the non-returning annotation, no subsequent local decrement, output store, or rollback code is reached.

No final counter or shared-value contents are prescribed. The dependency may overwrite those locations, reverse earlier effects, or invalidate their storage before terminating or transferring control.

### Stable counter reference, entry one

Assume successful comparison, a stable counter reference, disjoint storage, and no other counter mutations, including during F-8157a180d901.

The counter changes from one to two, then back to one. F-8157a180d901 receives zero. After its normal return, the additional decrement writes zero. The destination receives its returned value followed by zero.

### Stable counter reference, maximum entry

The direct-read branch is selected. F-8157a180d901 is not called.

### Dependency changes the captured counter
