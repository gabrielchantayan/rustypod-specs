# F-0a55578b6991

## Purpose

F-0a55578b6991 updates a four-word allocation state through one of three paths:

- Remove the first entry from a nonempty reusable-entry chain.
- Advance an existing allocation cursor by 12 bytes.
- Create and link a region descriptor, install a new cursor/end pair, and advance the cursor by 12 bytes.

The function has no explicit return value. Its observable results are state changes, descriptor writes, and calls to F-871e64ddc6de.

**Inferred intent:** the state manages a pool of 12-byte entries, with a reusable-entry chain and a linked list of region descriptors. The function appears to consume or reserve one entry. Neither the method by which a caller obtains that entry nor its payload layout is established.

A region-creation invocation does not access entry-storage contents. It stores the second dependency result as an address value and performs arithmetic with it. Consequently, usable entry storage is an external pool or caller invariant, not a source-established requirement for this invocation to complete.

## Interface

### Inputs

The function accepts:

- **State address:** an address identifying four consecutive 32-bit state words.
- **Allocation mode:** a 32-bit integer tested only for equality with zero. All nonzero values select the same behavior when mode selection is reached.

The supplied representation uses 32-bit words for both addresses and numeric quantities. It does not establish a native 64-bit pointer layout or a particular calling convention.

### State layout

| Byte offset | Width | Meaning |
|---|---:|---|
| 0 | 32 bits | Region-descriptor head address, or zero |
| 4 | 32 bits | Reusable-entry head address, or zero |
| 8 | 32 bits | Allocation cursor |
| 12 | 32 bits | Allocation end address |

A reusable entry exposes its successor address in its first 32-bit word. No other reusable-entry fields are accessed.

A newly created descriptor has this layout:

| Byte offset | Width | Meaning |
|---|---:|---|
| 0 | 32 bits | Previous descriptor address |
| 4 | 32 bits | Selected entry capacity |
| 8 | 32 bits | Entry-storage address value |

The descriptor allocation request is 12 bytes. The entry-storage request is capacity multiplied by 12 using unsigned 32-bit arithmetic.

### Outputs

There is no explicit scalar or pointer result.

Under distinct-storage conditions and without intervening dependency mutations:

- The reusable-entry path changes only the reusable-entry head.
- The existing-region path changes only the cursor.
- The region-creation path initializes a descriptor and changes the descriptor head, cursor, and end.

No entry payload is initialized, read, or written.

### Access requirements

The selected path determines which memory must be accessible:

- The reusable-entry-head field must be readable.
- A nonzero reusable-entry head must identify a readable 32-bit successor word; the head field must be writable.
- With an empty reusable-entry chain, cursor and end must be readable, and the cursor must be writable.
- Normal growth reads the descriptor-head field and, if nonzero, the capacity word at that descriptor’s offset 4.
- Region creation requires the state fields receiving updates to be writable.
- The first dependency result must identify descriptor storage supporting all three 32-bit writes and the subsequent read at offset 8.
- The second dependency result need only be representable as the address-bearing word used by this function. This function does not require the memory denoted by that value to be accessible.

For intended pool operation, an external invariant would normally require sufficient usable entry storage. That requirement is separate from the accesses performed here.

Alignment, supported address ranges, and precise consequences of invalid accesses remain **documented_only**.

## Behavior

### Reusable-entry priority

The reusable-entry head is examined first.

If nonzero, the function reads the successor word from the addressed entry, stores it into the reusable-entry-head field, and returns immediately.

On this path, the function does not directly:

- Compare cursor with end.
- Consult allocation mode.
- Read a descriptor capacity.
- Call F-871e64ddc6de.
- Advance the cursor.
- Clear the removed entry.
- Release storage.

A reusable entry therefore takes precedence over region exhaustion and mode selection.

The removed entry’s address is not returned or placed in a separate result field. Any caller mechanism for retaining that address is outside the established contract.

### Existing-region advancement

With an empty reusable-entry chain, the function compares cursor and end for equality.

If unequal, it reads the cursor, adds 12, writes the result back, and returns.

The comparison is not a bounds or remaining-space check. A cursor beyond the end, or less than 12 bytes before the end, still takes this path. The function does not verify alignment, allocation membership, or a whole-entry remaining span.

The final cursor addition is represented as signed 32-bit addition. Behavior at signed overflow is not established by the supplied representation; wrapping must not be assumed for that operation.

### Region creation

Region creation occurs only when the reusable-entry head is zero and cursor equals end.

#### Capacity selection

A nonzero allocation mode selects capacity one without reading the previous descriptor’s capacity.

Mode zero selects normal growth:

- A zero descriptor head selects capacity 32.
- Otherwise, the current head descriptor’s capacity is read as an unsigned 32-bit value.

For previous capacity \(c\), the candidates are:

\[
a=(c+32)\bmod 2^{32}
\]

\[
b=\left(c+\left\lfloor c/2\right\rfloor+
\left\lfloor c/8\right\rfloor\right)\bmod 2^{32}
\]

The fractional terms come from logical right shifts of the unsigned capacity. The selected capacity is the larger candidate under an unsigned comparison. Equality selects the second candidate, with no numeric difference.

Without overflow, this combines an additive increase of 32 with growth of approximately 1.625 times the previous capacity. That is inferred intent, not a guarantee of monotonic growth for all inputs.

There is no overflow rejection, minimum-capacity enforcement, or check that the result exceeds the old capacity.

#### Dependency calls

After selecting capacity, the function calls F-871e64ddc6de twice, in order:

1. Byte count 12; second argument zero.
2. Byte count \((12\times\text{capacity})\bmod 2^{32}\); second argument zero.

The first result is retained as the descriptor address. The second is retained as the entry-storage address value.

Neither result is checked. If the first call returns normally with an unusable descriptor address, the second call is still attempted before the first descriptor write.

The first result is subsequently dereferenced. The second result is not dereferenced as an entry-storage address. A zero, inaccessible, or insufficiently backed second result is therefore not, by itself, evidence that this invocation cannot complete. It may instead leave unusable pool state for later consumers.

#### Ordered descriptor and state updates

After both calls return, the explicit operations occur in this order:

1. Write the second result into the new descriptor’s storage-address field.
2. Read the state’s then-current descriptor head and write it into the new descriptor’s previous-link field.
3. Write selected capacity into the new descriptor’s capacity field.
4. Write the new descriptor address into the state’s descriptor-head field.
5. Read the descriptor’s storage-address field.
6. Write that reread value into the state’s cursor field.
7. Write the reread storage value plus the capacity-times-12 quantity into the state’s end field.
8. Read the state’s cursor, add 12, and write it back.

The end-address calculation combines the storage value with an unsigned 32-bit product; its 32-bit numeric result is modulo \(2^{32}\). The subsequent cursor increment has the signed-overflow uncertainty described above.

Under non-overlapping storage and representable cursor addition, the final cursor is storage base plus 12. No access is made to that entry’s contents.

The previous-link value is obtained after both dependency calls. It is not necessarily the descriptor head used earlier for capacity selection. Dependency mutation may therefore cause capacity selection and linkage to refer to different descriptors.

The reusable-entry head, cursor/end comparison, mode decision, and selected capacity are not reconsidered after the calls. State publication is not atomic: the new descriptor head is stored before cursor and end are installed.

## Side effects

### Direct writes

Depending on the selected path, the function writes:

- The reusable-entry-head field only.
- The cursor field only.
- Three descriptor words, then the descriptor head, cursor, end, and cursor again.

The function performs no explicit entry-payload writes and invokes no release dependency.

### Retention and ownership

The descriptor is retained through the state’s descriptor-head link. The second result is retained in the descriptor and used to construct cursor/end values.

These references do not establish ownership, validity, or lifetime guarantees. The evidence does not determine:

- Who releases either allocation.
- Whether the allocations are independent.
- Whether the dependency uses a heap, arena, pool, or another mechanism.
- Whether removing a reusable entry transfers ownership.
- Whether entry storage is actually backed by the requested number of bytes.

In particular, retaining the second result does not validate it.

### Dependency mutation and aliasing

F-871e64ddc6de may modify state or other memory; preservation is not assumed. The described ordinary final values require appropriate non-mutation conditions.

Returned descriptor storage may also overlap state or other relevant storage unless excluded externally. Such overlap can alter later reads, including the descriptor storage-address reread and the final cursor read. The function performs no overlap checks.

No direct entry-storage access is made through the second result. If that value happens to equal another accessed address, accesses through the descriptor or state still follow their own ordered operations; the equality does not introduce a separate entry-storage access.

Supported aliasing and reentrancy remain **documented_only**.

### Errors and partial completion

There is no explicit error result, rollback, allocation-result validation, or recovery branch.

An invalid first result can prevent completion when descriptor storage is accessed. Invalid state or reusable-entry addresses can similarly prevent completion. Exact fault, exception, or termination behavior is unknown.

An invalid second result need not cause an immediate failure here because the function only stores and computes with that value.

If a dependency does not return normally, or a later access fails, previously completed calls and writes are not visibly undone. Descriptor-head publication may precede failure during later state updates.

## Acceptance examples

These are conditional criteria derived from static evidence, not executed tests.

### Reuse overrides exhaustion

Given a nonzero reusable-entry head whose first word contains a successor address, even with cursor equal to end:

- The reusable-entry head becomes that successor.
- No dependency call occurs.
- Cursor, end, and descriptor head receive no direct writes.
- Allocation mode does not affect the path.

### Unequal cursor and end

Given an empty reusable-entry chain, cursor 1,000, and end 1,024:

- Cursor becomes 1,012.
- No dependency call occurs.

Given cursor 1,020 and end 1,024, cursor becomes 1,032. Insufficient remaining space does not cause region creation.

### First normal region

Given an empty reusable-entry chain, equal cursor and end, zero descriptor head, and mode zero:

- Capacity is 32.
- Requests are 12 bytes followed by 384 bytes.

If the calls return a readable/writable descriptor address \(D\) and a storage value \(B\), with no relevant dependency mutation or overlap:

- Descriptor \(D\) records previous link zero, capacity 32, and storage value \(B\).
- Descriptor head becomes \(D\).
- End becomes \(B+384\), modulo \(2^{32}\).
- Cursor becomes \(B+12\), provided that cursor addition does not encounter unresolved signed overflow.

No accessibility check or entry-storage access at \(B\) occurs.

### Second result is zero

Under the same initial conditions, suppose the first result supplies valid distinct descriptor storage and the second result is zero. Assume both calls return normally without relevant state mutation.

Expected completion:

- The descriptor stores storage value zero and capacity 32.
- Cursor is first set to zero, then advanced to 12.
- End becomes 384.
- The function does not access memory at address zero through the second result.

This example establishes behavior of this invocation, not validity of the resulting state for future entry use.

### Normal growth and wrapped sizes

Previous capacity 32 selects 64: the candidates are 64 and 52.

Previous capacity 64 selects 104: the candidates are 96 and 104. The second request is 1,248 bytes.

Previous capacity 220,254,734 selects 357,913,942: its candidates are 220,254,766 and 357,913,942. The second request is 8 bytes because multiplication by 12 wraps modulo \(2^{32}\). No size-overflow rejection occurs.

### Nonzero mode

With an empty reusable-entry chain, equal cursor and end, and any nonzero mode:

- Capacity is one.
- Both requests are 12 bytes.
- The old capacity is not read.

With suitable distinct descriptor storage, no dependency mutation, and non-overflowing cursor addition, final cursor equals new end.

### Head mutation during allocation

If normal growth selects capacity from one descriptor, but a dependency changes the descriptor head before publication:

- The selected capacity remains in use.
- The new descriptor’s previous link receives the head read after both calls.

### Unusable first result

If the first call returns an unusable descriptor address but returns normally:

- The second call is still attempted.
- No result check protects the subsequent descriptor write.
- Completion and failure mechanism depend on the memory environment.
