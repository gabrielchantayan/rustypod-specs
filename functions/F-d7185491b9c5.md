# F-d7185491b9c5

## Purpose

The callback is invoked only when the byte examined by the condition is nonzero. The returned byte is read after the conditional callback completes. Consequently, the return value need not equal the byte that caused the callback to run.

The routine resembles a byte-controlled notification or dispatch operation. That interpretation is inferred intent, not an established application-level meaning. The supplied evidence does not identify the byte as a Boolean, status code, character, readiness flag, or error indicator.

## Behavior

### Entry capture and conditional read

The routine first captures the current shared byte pointer for use when obtaining the eventual return value. It does not capture the pointed-to byte as its result.

It then evaluates whether a byte reached through the shared byte pointer is nonzero. The supplied representation expresses another use of the shared pointer for this condition, rather than explicitly using only the captured pointer.

In an ordinary execution without an intervening modification, both pointer evaluations identify the same storage. The excerpt does not establish synchronization, atomicity, or permission for concurrent mutation. It therefore does not define supported behavior for a racing writer or prove a particular number of physical memory loads.

### Zero branch

If the conditional byte read produces zero:

1. No callback is invoked by this routine.
2. The receiver’s first integer and callback entry are not needed for dispatch.
3. The routine reads through the entry-captured byte pointer and returns that value.

The final read remains a separate logical operation from the condition. With stable storage it also produces zero. A broader guarantee that the two reads must always agree would require assumptions about external mutation that are absent from the evidence.

### Nonzero branch

If the conditional byte read produces any nonzero character value, the routine performs one indirect callback invocation.

The callback target is obtained through the receiver’s first integer-sized quantity and the entry at the resulting base plus 88. The invocation supplies three arguments, in this order:

1. The receiver itself.
2. The first shared callback argument.
3. The second shared callback argument.

The receiver passed to the callback is the original explicit argument. The visible routine does not substitute a derived receiver or adjust its address.

The evidence does not establish a total order among the reads used to prepare the callback invocation. In particular, it does not justify ordering the two shared-argument reads relative to the receiver-base or callback-entry read. The branch decision precedes the invocation; the invocation completes before the final result read on a normal return path.

No callback return value is used to determine this routine’s result. Whether the callback has a meaningful return value is itself unspecified.

### Final result read

After the callback returns, or immediately after bypassing it on the zero branch, the routine reads one character-sized value through the pointer captured at entry.

This establishes two important distinctions:

- Changing the contents of the captured storage can change the result.
- Replacing the shared byte pointer does not, by itself, redirect the final read.

For example, a callback may change the original byte from nonzero to zero; this routine then returns zero. Alternatively, a callback may redirect the shared pointer to different storage while leaving the original byte unchanged; this routine still reads the original storage.

There is no second callback dispatch, loop, retry, or repeated condition evaluation in the visible routine.
