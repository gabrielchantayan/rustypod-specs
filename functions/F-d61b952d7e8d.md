# F-d61b952d7e8d

## Purpose

F-d61b952d7e8d obtains a selector through an indirect callback, conditionally obtains an index through F-364a7aebb37d, evaluates context state, optionally invokes F-94b556dacbc2, and invokes F-2bb3dbfa7286 after successful acquisition.

Its ordinary return value is either 0 or 3:

- Effective selectors 3 and 4 return 0 without acquisition.
- Effective selectors 0 and 1 select acquisition modes 0 and 1, respectively.
- All other effective selectors return 3.
- After successful acquisition, context state and any conditional processing result determine the return status and whether a context byte is cleared.

“Acquisition,” “processing,” and “final dependency” describe call positions, not established resource-management semantics. In particular, the final dependency is not established to release anything.

The index resides in mutable local storage whose address is exposed to F-364a7aebb37d. Conditional processing receives one evaluated index value; final entry-address formation uses a later read of that storage. Those values are not established to be identical.

## Interface

The function accepts four inputs and returns a four-byte status value.

| Input | Representation in the supplied evidence | Use |
|---|---|---|
| Context address | Address-bearing 32-bit integer | Base for context accesses and entry-address formation; passed to dependencies |
| Callback object | Pointer to an object beginning with a dispatch-table reference | Supplies the indirect selector callback |

Only return values 0 and 3 are produced by the visible function on ordinary completion. Their domain meanings are unknown. Return 0 does not establish that conditional processing occurred, and return 3 does not establish that state remained unchanged.

## Behavior

### Selector callback and dispatch

Before invoking the callback, the function initializes the index slot to zero, its pending return status to zero, and the selector word from the initial selector input.

It then invokes the callback obtained through dispatch-table offset 8, supplying:

1. The callback object address.
2. The address of the selector word.

The callback’s return value is ignored. After it returns, dispatch uses only the low eight bits of the selector word.

| Effective low byte | Subsequent action |
|---|---|
| 0 | Call F-364a7aebb37d with mode 0 |
| 1 | Call F-364a7aebb37d with mode 1 |
| 3 or 4 | Return 0 immediately |
| Any other value | Return 3 immediately |

The callback always precedes dispatch, even if the initial selector already appears acceptable. The initial input therefore does not independently determine the branch.

Upper selector bits do not directly affect dispatch. For example, callback outputs `0x00000001` and `0xFFFFFF01` both select mode 1.

The immediate-return branches perform no direct context-field accesses and invoke none of the three named dependencies. The callback may nevertheless already have caused effects.

### Acquisition

For effective selector 0 or 1, F-364a7aebb37d receives:

1. The context address.
2. The corresponding 32-bit mode, exactly 0 or 1.
3. The address of the index slot initialized to zero.

A nonzero result causes immediate return of status 3. On that path, this function does not directly read the listed context fields, clear `0x1084`, or invoke either later dependency. Effects of the callback or acquisition dependency are not rolled back.

A zero result permits continuation. The function performs no additional check that an index was written. If the slot has not been changed, it remains zero.

The slot remains mutable after acquisition. F-364a7aebb37d has received its address, and the supplied evidence does not establish that the address cannot be retained or made available to another dependency during this active invocation.

### Post-acquisition state and processing gate

After acquisition returns zero, the function reads the byte at context offset `0x1390`.

If that byte equals 3:

- The pending return status becomes 3.
- The gate byte at `0x1398` is not directly read.
- F-94b556dacbc2 is not called.
- No direct clear of `0x1084` occurs.
- Execution proceeds to the final dependency.

If the state byte is not 3, processing control determines whether the gate is examined:

- Processing control zero: skip the gate read and skip F-94b556dacbc2.
- Processing control nonzero: read the byte at `0x1398`.
  - Gate nonzero: skip F-94b556dacbc2.
  - Gate zero: invoke F-94b556dacbc2.

When invoked, F-94b556dacbc2 receives the context address and the value read from the index slot for that call. This second argument is a value, not the address of the slot.

A nonzero processing result selects pending status 3. A zero result leaves pending status 0.

Neither the state byte nor the gate byte is reread after processing. Mutations of those fields during F-94b556dacbc2 do not cause their branch conditions to be reevaluated.

### Conditional context clear

The function writes one zero byte at context offset `0x1084` if:

- The tested state byte was not 3; and
- Conditional processing was skipped or returned zero.

Consequently, the clear occurs even without a processing call when processing control is zero or the gate byte is nonzero, provided the state byte was not 3.

The clear is omitted when the state byte equals 3 or invoked processing returns nonzero. Omitting this direct write does not establish that the byte retains its entry value: dependencies may modify it.

### Separate index observations

The index slot is observed at distinct points:

1. If conditional processing is invoked, its index argument is evaluated before that call begins.
2. The final entry address uses the slot’s value when that address is evaluated, after conditional processing has returned and after any direct clear.

The earlier index argument is not cached for reuse in the final address.

F-94b556dacbc2 does not directly receive the slot’s address from this function. Nevertheless, F-364a7aebb37d previously received that address. The evidence does not exclude a retained alias through which F-94b556dacbc2, or behavior it invokes, changes the slot while the invocation is still active.

Thus, the entry address supplied to the final dependency need not correspond to the index value previously passed to processing. This is an unresolved aliasing possibility, not evidence that such modification actually occurs.

### Final dependency and return

Every normally continuing path after successful acquisition invokes F-2bb3dbfa7286 with:

1. The four-byte value then read from context offset `0x1380`.
2. The address formed from the context address, plus `0x1270`, plus 80 times the index slot’s value at final address evaluation.

Both argument evaluations occur after any processing call and any direct clear. Their relative evaluation order is not established by the supplied evidence. In particular, the contract does not impose an ordering between the four-byte field read and the final index-slot read.

The value at `0x1380` is not saved before the earlier dependencies. Changes they make to it may affect the final call. Likewise, changes to the index slot before final address evaluation may affect the second argument.

F-2bb3dbfa7286 is called even when the pending status is already 3. Its return value is ignored. If it returns normally, this function returns the previously selected status.

The address argument is evaluated before the final call begins. A later slot mutation during that call does not retroactively change the already supplied argument.

### Integer and address limits

The selector word is unsigned 32-bit storage, reduced to eight bits for dispatch. Processing control is tested only for zero versus nonzero. The index slot is represented as signed 32-bit storage.

The visible address calculation multiplies the index by 80 and adds the context address and `0x1270`. It does not constrain the index to be nonnegative or within an entry count.

Valid portable behavior for signed overflow, address wraparound, negative indices, or addresses outside the relevant allocation is not established. The contract requires valid arithmetic and addressing on paths that reach the final call rather than assuming modular wraparound.

## Side effects

The only explicit direct context write is the conditional one-byte clear at `0x1084`.

The ordered direct context operations are:

1. After successful acquisition, read the state byte at `0x1390`.
2. If required, read the gate byte at `0x1398`.
3. If required, invoke conditional processing.
4. On the accepted branch, clear `0x1084`.
5. Evaluate the final call’s arguments, including the four-byte read at `0x1380`.

The final index read also belongs to final argument evaluation. No relative order between that read and the field read at `0x1380` is established.

Dependency-internal effects may occur between these operations. No dependency is assumed to preserve globals, context fields, or reachable mutable local storage.

There is no explicit allocation, deallocation, ownership transfer, rollback, locking, or unlocking in the visible body. Such effects inside dependencies remain unknown.

Retaining a local address for use while its object remains alive is not inherently improper. Whether either exposed address escapes, who can access it, and how it is subsequently used are unknown. Use after the local object’s lifetime ends is a separate validity concern; the evidence supplies no lifetime extension.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Each assumes valid accesses, valid arithmetic, and normally returning dependencies.

1. **Immediate success after callback.** If the callback leaves `0xA1B2C303`, return 0 without invoking the three named dependencies or directly clearing the context byte. The callback’s own effects remain possible.

2. **Low-byte dispatch.** If the callback leaves `0xFFFFFF01`, acquisition receives mode 1. If it leaves a low byte of 2 or 255, return 3 without acquisition.

3. **Acquisition failure.** If selector 0 causes acquisition to return nonzero, return 3 without processing, final invocation, or a direct clear.

4. **Blocking state.** After successful acquisition, a state byte of 3 suppresses the gate read, processing, and direct clear. The final dependency is still called, and the function returns 3.

5. **Processing disabled.** After successful acquisition with state not 3 and processing control zero, do not directly read the gate. Clear `0x1084`, invoke the final dependency, and return 0.

6. **Gate suppresses processing.** With state not 3, nonzero processing control, and nonzero gate, skip processing but perform the clear and final call, then return 0.

7. **Processing failure.** With the processing conditions satisfied, a nonzero processing result suppresses the direct clear. The final call still occurs, followed by return 3.

8. **Late context-field observation.** If processing changes `0x1380` and returns zero, and no intervening effect changes that field again, the final call receives the changed value. The direct clear precedes final argument evaluation.

9. **Distinct processing and final indices.** Suppose the slot contains 2 when the processing argument is evaluated. Processing receives 2. If an available retained alias changes the slot to 5 before final address evaluation, the final address is context plus `0x1400`, not context plus `0x1310`.

10. **Concrete final address.** If the slot contains 2 when the final address is evaluated, the second final-call argument is context plus `0x1310`, since `0x1270 + 2 × 0x50 = 0x1310`. Acquisition initially supplying 2 is insufficient by itself; the value must still be 2 at this later observation. Any earlier processing argument is a separate observation.
