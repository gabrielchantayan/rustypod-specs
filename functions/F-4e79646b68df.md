# F-4e79646b68df

## Purpose

F-4e79646b68df conditionally detaches a designated node from a linked, sentinel-based structure, performs color-dependent structural repair, inserts the detached node into a container-held chain, decrements a 32-bit count, and writes a result token to caller-provided storage.

The link patterns suggest a red-black-tree removal operation with cached extrema and a retained-node chain. These are inferred roles, not independently established data-structure guarantees. The contract follows the visible branches rather than substituting a conventional tree-removal algorithm. In particular, repair after a missing replacement and repair with a missing sibling require the distinctions documented below.

A comparison dependency can select an early exit without this function directly changing tree links, chain membership, or the count. Dependency effects remain outside that guarantee.

## Interface

### Arguments and result

| Argument | Established role |
|---|---|
| Output address | Receives one 32-bit result word on normal completion. |
| Container address | Identifies mutable container storage. |
| Input-token address | Identifies a 32-bit word copied initially and independently reread later to select the removal target. |

There is no explicit return value or status code.

The initial token copy is local storage whose address is supplied to dependencies. On the removal path, the final output reads that local word at function completion. It is not an independently preserved snapshot of the value immediately following the token-preparation dependency.

No payload layout is exposed. The function performs no explicit payload copy, payload destruction, allocation, or deallocation.

## Behavior

### Comparison gate and result storage

The function first reads the input-token word into local storage, then reads the container’s header-address word into a separate local word. F-27df7c446fb9 receives the addresses of those two local words.

Only zero versus nonzero matters for its returned result.

If the result is nonzero, the function rereads the header address from the container, replaces the local result token with that value, writes the token to the output address, and returns. It does not call F-50ef9e9e7cc8 or directly perform structural removal, chain insertion, or count decrement. Effects performed by F-27df7c446fb9 are not excluded.

If the result is zero, F-50ef9e9e7cc8 receives the address of the local token. After that call, the function independently rereads the caller’s input-token word and uses the reread value as the removal target.

Consequently:

- Changes to the caller’s token storage during either dependency can change the selected target.
- Changes to the local token do not themselves select the target.
- The container’s header is not established as stable across dependencies.
- The final output is the local token’s value when the final output assignment reads it. A value produced by F-50ef9e9e7cc8 is the final result only if subsequent effects leave that word unchanged.

The dependencies’ retention or later use of the escaped local-storage addresses is unknown.

### Target with no children

The target’s left-child field is examined first. If it is zero, the right-child field is examined. When both are zero, the target’s parent is the initial repair node.

If that parent equals the container’s currently stored header address, the function writes the empty-state links in this order:

1. Header rightmost becomes the parent address.
2. Header leftmost becomes the parent address.
3. Header root becomes zero.

The header address is obtained from container storage for these accesses; the implementation does not establish a permanently cached header.

Otherwise, the parent’s left-child field is compared with the target. Equality selects the left link; inequality selects the right link without separately checking that the right link names the target.

The selected link is cleared with four consecutive single-byte writes in increasing address order. These are not one 32-bit store.

Only the corresponding extremum cache is then considered: leftmost for a selected left link, rightmost for a selected right link. If that cache equals the target, it becomes the parent.

### Target with exactly one child

The nonzero child becomes the replacement and initial repair node.

The replacement’s parent field is written before the incoming link to the target is redirected. The header root is checked first. If it equals the target, it becomes the replacement. Otherwise, the target’s parent’s left link is checked; equality selects that link, and inequality selects the right link.

Extremum updates follow:

- If the target is the cached leftmost node and its right child is zero, the cache becomes the target’s parent.
- If the target is cached leftmost and its right child is nonzero, the cache becomes the leftmost descendant of the replacement.
- If the target is cached rightmost and its left child is zero, the cache becomes the target’s parent.
- If the target is cached rightmost and its left child is nonzero, the cache becomes the rightmost descendant of the replacement.

Descendant searches follow the relevant child links until zero. They contain no cycle detection.

The original target remains the node later inserted into the chain.

### Target with two children

The function selects the leftmost node of the target’s right subtree as the relocated node. The relocated node’s right child, possibly zero, is the replacement for its former position.

Structural changes occur before the color-like bytes are exchanged:

1. The target’s left child receives the relocated node as parent.
2. The relocated node receives the target’s left-child link.
3. The relocated node’s former position is repaired.
4. The target’s incoming root or parent link is redirected to the relocated node.
5. The relocated node receives the target’s parent.
6. The relocated node and target exchange their one-byte fields.

If the relocated node is the target’s immediate right child, its nonzero right child receives the relocated node as parent. No separate adoption of the target’s right-subtree link occurs in this case.

Otherwise, the relocated node’s nonzero right child receives its former parent. That former parent’s left link becomes the replacement. The relocated node then adopts the target’s right subtree, whose parent field is updated.

Incoming-link selection uses the same root-first, otherwise-parent-left-or-right rule as the one-child branch.

If the replacement is zero, the repair node becomes the relocated node itself. If it is nonzero, it remains the replacement. This is not an implicit null-leaf repair model.

The original target—not the relocated node—is detached and later inserted into the chain. Its byte after the exchange determines whether color-dependent repair is entered. This branch does not directly update the cached extrema.

### Color-dependent repair

After detachment, the function rereads the header address. Repair is skipped if the repair node equals that header. Otherwise, the detached target’s current byte is read; zero also skips repair.

When repair is entered, each iteration first compares the repair node with the current root. A root match bypasses the loop body and leads to a write of one to the repair node’s byte. For a non-root node, a byte other than one has the same terminating effect.

There is no general null-repair-node check. A zero repair address can reach an invalid byte access or the final byte write; a root comparison is not a general null-safety guarantee.

For a non-root repair node whose byte is one, the parent is loaded and orientation is selected:

| Repair node’s position | Sibling | Near child | Far child |
|---|---|---|---|
| Equals parent’s left link | Parent’s right child | Sibling’s left child | Sibling’s right child |
| Otherwise | Parent’s left child | Sibling’s right child | Sibling’s left child |

The second orientation does not independently verify that the repair node equals the parent’s right child.

**Missing sibling.** The function writes zero to the current repair node, makes the parent address the next repair node, and repeats the root/byte decision.

Every visible route into this continuation supplies a parent-address value. With an initially absent sibling, the previously loaded parent remains available. With an absent sibling following the zero-byte-sibling rotation, the repair node’s parent has explicitly been reloaded after the call. Although an intermediate working value elsewhere holds a widened color byte, that color value does not reach this continuation.

A dependency can still change the links from which a parent address is reloaded. The reload establishes the value’s source, not its validity.

**Sibling byte zero.** The sibling’s byte becomes one, then the parent’s byte becomes zero. The orientation-specific dependency is called:

- Left-child repair orientation: F-f3fe7d95fb9b.
- Opposite orientation: F-850ce195b4aa.

These calls visibly receive the container and the repair node’s parent address. After return, the parent and sibling links are reloaded. A now-absent sibling takes the missing-sibling continuation above.

**Both sibling children absent or byte one.** The sibling’s byte becomes zero. The next repair node is obtained by rereading the current repair node’s parent, and iteration continues.

**Far child absent or byte one, without the preceding both-children case.** A nonzero near child receives byte one, then the sibling receives byte zero. The complementary dependency is called: F-850ce195b4aa for the left-child repair orientation, F-f3fe7d95fb9b for the other orientation.

At these call sites, only the container argument is visible. No missing argument is supplied by this contract.

The sibling is then reloaded through the repair node’s current parent. If it is absent, repair terminates by writing one to the current repair node; this is distinct from the missing-sibling continuation described earlier.

**Final rotation case.** The sibling receives the current parent’s byte, the parent receives one, and a nonzero far child receives one. The orientation-specific dependency is called with the container and current parent address. The function then writes one to the current repair node and ends repair.

These cases establish the visible operations, not a guarantee that red-black invariants are restored.

### Chain insertion, count, and final output

After repair is skipped or completed:

1. The current chain head is read from container offset +4 and written to the detached target’s offset +12.
2. The target becomes the container’s chain head.
3. The 32-bit count is read, reduced by one, and stored.
4. The local result-token word is read and written to the output address.

The target’s parent, left link, and byte are not generally cleared. Its former right-child field becomes a chain link.

The count has no underflow check or error branch. Its storage and update are 32-bit; no widened count is maintained. Because the supplied representation expresses the update through a signed 32-bit operation, behavior outside the representable signed range is **documented_only**. This contract does not assert modulo-\(2^{32}\) behavior without additional evidence.

## Side effects

Direct writes affect the local token words, output storage, container fields, header links, node links, and one-byte fields described above. Dependencies may affect additional storage.

The node is retained through the container-held chain. A reuse or free-list purpose is inferred; ownership transfer, eventual reclamation, and permission to reuse the node are not established. This function itself contains no explicit release operation.

Significant ordering constraints include:

- Both initial dependency calls precede the reread selecting the target.
- Replacement-parent writes precede incoming-link redirection in the one-child branch.
- Two-child structural changes precede the byte exchange.
- Chain insertion precedes count decrement.
- Final output follows the other direct completion writes.

These are sequential access observations, not atomicity, locking, or publication guarantees.

Aliasing is unchecked. Output storage overlapping a container or node field can overwrite that field after removal work. Input-token storage affected by dependencies can select a different target than the initial token copy. Arbitrary alias safety is not promised.

No rollback is visible. An inaccessible address, nonterminating traversal, or dependency that fails to return can leave partial mutations without chain insertion, decrement, or output completion.

## Acceptance examples

These are conditional static criteria, not executed tests.

1. **Comparison rejects removal.** If F-27df7c446fb9 returns nonzero normally, output must equal the header-address word reread afterward. F-50ef9e9e7cc8 is not called. This function performs no direct removal, chain insertion, or count decrement.

2. **Sole-node removal.** With stable dependencies, a childless target whose parent equals the header produces root zero and both extrema equal to the header, in rightmost–leftmost–root write order. Repair is skipped. The target becomes chain head and the count decreases once within its defined arithmetic range.

3. **Zero-byte non-root leaf.** The selected parent link is cleared through four increasing-address byte writes. A matching corresponding extremum becomes the parent. Repair is skipped, then chain insertion occurs.

4. **One-child root replacement.** The child’s parent is written before root redirection. If repair is entered, the replacement matches the root and receives byte one before chain insertion.

5. **Two-child identity.** The leftmost node of the right subtree occupies the target’s structural position. The original target enters the chain. No payload-copy behavior is required.

6. **Prepared token differs from caller token.** If F-50ef9e9e7cc8 changes the local token while leaving caller token storage unchanged, removal selects the caller-stored target. Output equals the changed local token only if subsequent effects leave that local word unchanged.

7. **Initially missing sibling.** For an entered repair iteration with a valid non-root byte-one node and absent selected sibling, that node receives zero and iteration continues at the previously loaded parent address.

8. **Sibling disappears after the zero-byte-sibling call.** If the reloaded sibling is absent, the current repair node receives zero and iteration continues at the explicitly reloaded parent address—not at a widened color value. Validity of the reloaded parent remains a precondition.

9. **Output overlaps count.** With otherwise-valid completion and output storage equal to the count address, decrement occurs first and the result token subsequently overwrites it. A final decremented count is not promised.
