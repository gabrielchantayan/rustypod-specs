# F-b9d144e0e393

## Purpose

F-b9d144e0e393 produces the componentwise arithmetic negative of a three-element signed-integer sequence in caller-provided destination storage.

The operation has a fixed extent: exactly three source elements contribute to exactly three corresponding destination elements. It preserves component order and does not use the previous destination values.

Both exact overlap and valid partial overlap are supported. All three source values are acquired before any destination element is modified, so the function’s own writes cannot change an input still needed by that invocation.

A geometric-vector interpretation is plausible intent, not established behavior. The evidence establishes neither coordinates nor units.

This contract describes static evidence and its conditional consequences. No runtime tests have been performed.

## Interface

### Parameters and result

The interface has two ordered address parameters:

| Position | Meaning | Required access |
|---|---|---|
| First | Beginning of the destination sequence | Write access to three consecutive signed-integer elements |
| Second | Beginning of the source sequence | Read access to three consecutive elements of the same signed-integer type |

There is no returned value. Results are communicated through destination storage. The interface provides no element count, stride, error result, or layout option.

The function does not explicitly write through the source parameter. Nevertheless, source storage changes wherever it is also destination storage.

Existing destination values are not inputs. They need not contain initialized arithmetic values, provided the destination objects otherwise satisfy the requirements for valid writes.

### Width and layout

The evidence identifies a signed-integer element type but does not establish its bit width, byte size, signed representation, or byte order.

Let \(B\) denote the size of one element in the execution environment’s bytes. Each region has element offsets \(0\), \(B\), and \(2B\), and occupies \(3B\) bytes. There is no padding or caller-selected stride between these array elements.

If an environment uses four-byte elements, these offsets are 0, 4, and 8 bytes and each region spans 12 bytes. That layout is conditional; a fixed 12-byte interface is not established by the supplied evidence. Likewise, a four-byte element alone does not establish a 32-bit value width unless the environment’s byte width and representation are known.

### Preconditions

Defined completion requires:

- Three valid readable source elements and three valid writable destination elements.
- Appropriate object lifetimes, alignment, and addressing for every access.
- An arithmetic negative representable in the element type for each acquired source value.
- No conflicting concurrent access or other violation of the environment’s memory-access rules.

The regions need not be disjoint. Overlapping regions must still be valid views of the required objects. The overlap guarantee does not authorize misaligned or otherwise invalid byte-level reinterpretations.

There is no validation before the accesses. Null parameters, insufficient storage, inaccessible memory, and invalid alignment have no specified rejection behavior.

## Behavior

### Result relation

For every defined completion, destination elements one, two, and three contain the arithmetic negatives of the acquired source elements one, two, and three, respectively.

The result is position-preserving. There is no cross-component combination, normalization, saturation, scaling, sorting, or conditional omission. Every valid invocation processes all three components.

With no external modification during execution, the acquired values are the source values present at entry. The function does not provide a synchronized snapshot in circumstances involving external mutation.

### Access ordering

The source-level ordering establishes that the second source element is read before the third, and the third before the first. Every source value is therefore available before the destination changes.

Destination updates are ordered first element, second element, then third element. The first result is stored before the later two destination updates. The evidence does not require all three arithmetic negations to have been evaluated before the first store.

These are semantic ordering relationships, not a promise of a particular machine-instruction trace. The supplied accesses are not declared atomic or volatile, and generated instructions have not been inspected. Physical load counts, store widths, cache effects, and visibility to concurrent observers are not established.

For a valid ordinary execution, each source element contributes one acquired value and each destination element receives one result. Previous destination contents do not affect those results.

### Overlap and preservation

Exact overlap performs in-place negation. All original inputs are acquired before any of the shared objects changes.

Valid partial overlap is supported in either direction, including a destination beginning one or two elements after the source. A destination write cannot become a replacement input for a later component. The operation consequently does not cascade through overlapping storage.

Overlap does not preserve a second copy of the original source sequence. A shared object ends with the value assigned to its destination position, which may differ from the negative associated with its source position.

For example, if a particular object is both the second source element and the first destination element, its final value is the negative of the original first source element. Its original value still supplies the second destination result.

Objects outside the destination region are not explicitly modified. This applies even to source elements outside that region.

### Arithmetic boundaries

Negation uses the declared signed-integer type:

- Zero produces numeric zero.
- A positive value produces its negative counterpart when representable.
- A negative value produces its positive counterpart when representable.

No explicit overflow check, unsigned conversion, clamping, or recovery mechanism is present.

On a conventional two’s-complement signed 32-bit environment, the value −2,147,483,648 has no positive counterpart in the same type. Acquiring that value violates the representable-negation precondition. Wraparound, saturation, rejection, and any particular stored result must not be promised.

The precondition applies independently to all three inputs. If any negation is unrepresentable, this contract provides no destination-state guarantee for the invocation. In particular, the source-level update order does not justify promising a correctly updated prefix before an arithmetic failure.

No assumption about the location or handling of a hardware arithmetic exception is established.

### Completion and errors

With all preconditions satisfied, the function updates the three destination elements and returns without a value.

There is no explicit error branch, diagnostic, rollback, or status indication. Invalid inputs do not have a defined clean-failure outcome.

The update is not transactional. The function establishes neither atomic publication of the three results nor recovery guarantees if execution is interrupted.

## Side effects

The explicit memory modifications are confined to the three destination elements.

With disjoint regions, source contents remain unchanged. With overlapping regions, source objects shared with the destination change according to their destination positions.

The supplied body contains no explicit allocation, release, address retention, ownership transfer, global-state access, input/output operation, synchronization operation, or function call.

The storage remains caller-provided. The operation requires temporary access to it but does not establish ownership of either region or release either region.

There is no explicit persistent internal state. Results persist only through the destination storage and any aliases of that storage.

These statements describe the supplied function’s direct effects under its preconditions. They do not establish process-level behavior after an invalid access, guarantees for memory-mapped devices, or machine-level transaction boundaries.

## Acceptance examples

These examples are conditional deductions from static evidence, not observed executions. Unless stated otherwise, assume valid storage, suitable alignment and lifetimes, no conflicting concurrent access, and an element type capable of representing every input and result shown.

### Separate regions

A source containing **(7, −4, 0)** must produce destination contents **(−7, 4, 0)**.

The source remains **(7, −4, 0)**. Any prior destination values are irrelevant.

This checks component correspondence and the treatment of positive, negative, and zero inputs.

### Exact overlap

If a single region initially contains **(2, −9, 5)** and serves as both source and destination, its final contents must be **(−2, 9, −5)**.

Separate storage is not required. Original values, rather than values already modified by this invocation, supply all three results.

### Destination one element after the source

Consider four consecutive elements initially containing **(3, 5, 8, 99)**. The source is the first three elements; the destination is the last three.

The final four-element sequence must be **(3, −3, −5, −8)**.

The initial 99 does not contribute to the result. The first element stays 3 because it is outside the destination. The second and third results use the original inputs 5 and 8, not values introduced by earlier destination writes.

### Destination one element before the source

Consider four consecutive elements initially containing **(99, 3, 5, 8)**. The source is the last three elements; the destination is the first three.

The final sequence must be **(−3, −5, −8, 8)**.

The last element remains 8 because it is outside the destination, even though it supplies an input.

### Conditional signed 32-bit boundary

Under a conventional two’s-complement signed 32-bit interpretation, source contents **(2,147,483,647, −2,147,483,647, 0)** must produce **(−2,147,483,647, 2,147,483,647, 0)**.

Under the same interpretation, any source component equal to **−2,147,483,648** lies outside the representable-negation precondition. No unchanged destination, partial result, wrapped value, or clean rejection is required.
