# F-e14749c2e14c

## Purpose

F-e14749c2e14c advances a mutable storage-management state by one available entry. Its behavior has three mutually exclusive paths:

1. If a recycled-entry link is present, replace that link with its successor and return.
2. Otherwise, if the current sequential cursor equals its limit, obtain and link a new storage block, then advance its cursor by one entry.
3. Otherwise, advance the existing sequential cursor by one entry.

The established entry stride is 16 bytes. Newly created block descriptors occupy 12 bytes and record a predecessor link, an entry count, and a backing-storage address.

The function returns no entry address or status. Interpreting it as an allocation or reservation operation is inferred intent; the directly established behavior is mutation of the supplied state and, on block creation, calls to an external dependency.

## Interface

### Inputs and result

The function accepts:

- **State address:** a writable address identifying at least four consecutive 32-bit words.
- **Mode:** a 32-bit integer. Only equality with zero matters. All nonzero values select the same block-sizing behavior.

There is no explicit return value.

### State layout

Offsets are byte offsets from the supplied state address.

| Offset | Width | Meaning established by use |
|---|---:|---|
| +0 | 32 bits | Address of the current block descriptor, or zero |
| +4 | 32 bits | Address of a recycled-entry node, or zero |
| +8 | 32 bits | Current sequential cursor |
| +12 | 32 bits | Sequential-storage limit |

Addresses are represented in 32-bit words. A zero address is treated specially only where explicitly described below; there is no general null-pointer validation.

### Block-descriptor layout

A newly obtained descriptor has this layout:

| Offset | Width | Stored value |
|---|---:|---|
| +0 | 32 bits | Previous descriptor address |
| +4 | 32 bits | Entry count |
| +8 | 32 bits | Backing-storage address |

The previous descriptor is retained through the predecessor link. The function does not traverse that chain.

### Recycled-entry layout

A nonzero recycled-entry address must identify readable storage whose first 32-bit word is the next recycled-entry address. No other node fields are accessed by this function.

### Preconditions

For an ordinary successful execution:

- The state must be readable and writable for the fields used by the selected path.
- A nonzero recycled-entry address must support a 32-bit read at its base.
- When growth sizing uses a nonzero current descriptor, that descriptor must support a 32-bit read at offset +4.
- The first dependency result on the growth path must support the three descriptor writes.
- Addresses and arithmetic must be valid under the execution environment’s 32-bit representation.
- Any interference by the dependency, concurrent actors, or aliasing must be compatible with the access sequence described below.

These are caller or environment obligations, not conditions checked by the function.

## Behavior

### 1. Recycled-entry path takes precedence

The function first examines the recycled-entry address at state offset +4.

If that address is nonzero, the function reads the 32-bit word at the referenced node’s base and writes that value back to state offset +4. It then returns immediately.

Consequences:

- The sequential cursor is not advanced.
- The cursor and limit are not compared.
- No new descriptor or backing storage is requested.
- The current descriptor address is not intentionally changed.
- The removed node is not cleared, initialized, or explicitly released.
- The removed node’s address is not returned.

This precedence applies even when the sequential cursor equals its limit. A recycled-entry address therefore prevents growth during this invocation.

### 2. Sequential availability is determined only by equality

If the recycled-entry address is zero, the function compares the cursor at offset +8 with the limit at offset +12.

If they differ, no growth occurs. The function proceeds directly to advancing the cursor by 16 bytes.

The check is equality, not an ordering or bounds check. In particular, a cursor beyond the limit, or another inconsistent unequal pair, does not trigger repair or rejection. Such a state still reaches the increment operation, subject to arithmetic validity.

If the cursor equals the limit, block creation occurs before the increment.

### 3. Entry count for a new block

The entry count is calculated before either dependency call.

#### Nonzero mode

For every nonzero mode, the entry count is exactly 1.

The previous descriptor’s entry count is not consulted. Nonzero mode does not prevent descriptor allocation or predecessor linking.

#### Zero mode with no current descriptor

If mode is zero and the current descriptor address is zero, the entry count is 32.

The backing-storage request is therefore 512 bytes.

#### Zero mode with a current descriptor

If mode is zero and the current descriptor address is nonzero, the function reads its entry-count word at offset +4 as an unsigned 32-bit value. Call that value \(c\).

It forms two unsigned 32-bit candidates:

- \(a = c + 32\), reduced modulo \(2^{32}\).
- \(b = c + \lfloor c/2 \rfloor + \lfloor c/8 \rfloor\), with the additions reduced modulo \(2^{32}\).

The new count is the larger of \(a\) and \(b\) under an unsigned comparison. Equality selects \(b\), although that distinction does not change the resulting count.

The two fractional terms are computed separately using logical right shifts. This is not, in general, identical to rounding a single product by \(13/8\).

For ordinary, nonoverflowing values, this rule selects the larger of an additive increase of 32 entries and approximately 62.5% proportional growth. That growth interpretation is inferred intent. The established arithmetic is the unsigned, fixed-width calculation above.

There is no overflow guard, count validation, or minimum-count correction after this calculation.

### 4. Ordered block creation and publication

Once the count has been selected, the function performs the following externally significant sequence:

1. Call **F-871e64ddc6de** with first argument 12 and second argument zero. Retain the returned value as the new descriptor address.
2. Call **F-871e64ddc6de** again with first argument equal to the count shifted left by four bits in 32-bit unsigned arithmetic, and second argument zero. Retain the returned value as the backing-storage address.
3. Write the backing-storage address to the new descriptor at offset +8.
4. Read the current descriptor address from state offset +0 and write it to the new descriptor at offset +0.
5. Write the selected count to the new descriptor at offset +4.
6. Write the new descriptor address to state offset +0.
7. Read the backing-storage address from the new descriptor at offset +8.
8. Write that address to the state cursor at offset +8.
9. Write the backing-storage address plus the count multiplied by 16 to the state limit at offset +12.
10. Perform the final cursor increment described below.

The previous descriptor link is read **after both dependency calls**. It is not necessarily the descriptor address inspected during count selection. If the dependency changes state offset +0, the new descriptor links to the value present at this later read.

Similarly, the descriptor’s backing-storage field is read after publication rather than being treated solely as an unobservable retained value.

This sequence describes accesses visible in the supplied static representation. It does not establish processor-level ordering, synchronization, or atomic publication guarantees.

### 5. Final cursor increment

Every invocation that does not return through the recycled-entry path finishes by adding 16 to the state cursor and storing the result back at offset +8.

For a newly created block with backing-storage address \(p\), the ordinary resulting state is:

- Cursor: \(p + 16\).
- Limit: \(p + 16n\), where \(n\) is the selected count.
- Current descriptor: the newly obtained descriptor.

For a one-entry block, the cursor equals the limit immediately after this increment.

The 16-byte entry itself is not initialized. The cursor movement is the only direct operation on entry availability; the function does not write entry contents.

### 6. Arithmetic boundaries

The count, candidate calculations, backing-storage request size, and count-times-16 term use 32-bit unsigned arithmetic.

Consequently:

- Large counts can wrap during growth calculation.
- A nonzero count can produce a zero backing-storage request after the left shift.
- The requested byte size need not equal the unbounded mathematical value \(16n\).
- The limit-address calculation does not establish that the resulting address lies after the backing-storage address in ordinary integer ordering.

The final cursor increment is expressed as addition to a signed 32-bit state word. The supplied evidence does not establish portable wraparound behavior when that signed addition overflows. Successful-address examples below avoid that boundary.

No inference that storage is sufficiently large is justified merely from the count and limit fields.

## Side effects

### Direct writes

Depending on the selected path, the function directly writes:

- Only the recycled-entry link on the recycled path.
- Only the cursor when sequential space is treated as available.
- All three new descriptor fields, the state’s current descriptor, the cursor, and the limit when creating a block.

On the block-creation path, the cursor is written twice: first to the backing-storage address, then to that address plus 16.

### External effects

The growth path calls F-871e64ddc6de twice. Those calls may have additional effects not described by the available evidence.

The function contains no explicit release operation for:

- The previous descriptor.
- Its backing storage.
- A removed recycled-entry node.
- Either result of a partially completed block-creation sequence.

The retained predecessor link is consistent with preserving older blocks, but ownership and eventual release responsibility are not established.

### Errors and partial state

There is no explicit error return, failure check, rollback, or recovery branch.

If the first dependency call returns an unusable descriptor address and the second call returns normally, the subsequent descriptor write still proceeds without validation. If either call does not return, later writes do not occur.

A later fault can leave earlier writes visible. In particular, this function is not established to update the descriptor and state transactionally.

No guarantee is made that the dependency preserves state, unrelated globals, memory contents, or previously returned storage.

## Dependencies

### F-871e64ddc6de

**Established use:**

- Called only when there is no recycled entry and the cursor equals the limit.
- Called exactly twice if both calls return normally.
- Receives arguments in this order:
  1. Size 12, second argument zero.
  2. Size equal to the selected count shifted left four bits, second argument zero.
- Its first result is used as a writable descriptor address.
- Its second result is stored as the backing-storage address.

**Inferred intent:** an allocation-like service providing a descriptor and backing storage.

**Not established:** allocation guarantees, alignment, zero initialization, failure signaling, exception behavior, zero-size behavior, aliasing restrictions, ownership transfer, release mechanism, or preservation of caller-visible state. The second argument’s meaning is unknown beyond its observed value of zero.

## Acceptance examples

These examples are conditional static acceptance cases, not reports of executed tests. Unless stated otherwise, assume valid nonoverlapping storage, normally returning dependency calls, no interfering state changes, and arithmetic within the valid signed-address range.

### Recycled entry overrides exhaustion

Given a nonzero recycled-entry address whose first word is zero, and a cursor equal to the limit:

- The recycled-entry field becomes zero.
- No dependency call occurs.
- The descriptor, cursor, and limit remain unchanged.

The same result applies for zero and nonzero mode.

### Existing sequential space

Given a zero recycled-entry address, cursor 4096, and limit 4160:

- No dependency call occurs.
- The cursor becomes 4112.
- The descriptor and limit remain unchanged.
- Mode has no effect on this invocation.

### Initial zero-mode growth

Given a zero recycled-entry address, equal cursor and limit, no current descriptor, and zero mode:

- The dependency requests are 12 bytes and then 512 bytes, both with second argument zero.
- The new descriptor records predecessor zero and count 32.
- If the backing-storage address is 8192, the resulting cursor is 8208 and the limit is 8704.

### Nonzero-mode growth

Given exhaustion, no recycled entry, and any nonzero mode:

- The selected count is 1.
- The dependency requests are 12 bytes and then 16 bytes.
- The new descriptor links to the current descriptor read after both calls.
- With backing storage at 8192, both resulting cursor and limit are 8208.

### Additive and proportional sizing

With zero mode and an existing descriptor:

- Previous count 32 produces candidates 64 and 52, so the new count is 64 and the backing request is 1024 bytes.
- Previous count 64 produces candidates 96 and 104, so the new count is 104 and the backing request is 1664 bytes.
- Previous count 55 produces candidates 87 and 88, so the new count is 88. Separately truncating the two fractional terms is significant.

### No bounds repair

Given zero recycled-entry address, cursor 4160, and limit 4096:

- The unequal values do not cause growth.
- The cursor becomes 4176.
- No error is explicitly reported.

This illustrates the equality-only decision; it does not establish that the initial state is valid for a caller.

### Wrapped request size

With zero mode and previous count \(2^{31}\):

- The additive candidate is 2,147,483,680.
- The proportional candidate is 3,489,660,928 and is selected.
- Shifting that selected count left by four in 32 bits produces zero.

The second dependency call therefore receives a size of zero. Its behavior and the validity of subsequent address operations remain documented_only.

## Uncertainties

The following are **documented_only**:

- The application-level meaning of advancing one entry without returning its address.
- Whether callers retain a pre-call cursor or recycled-node address elsewhere.
- Required alignment of state, descriptors, nodes, and backing storage.
- Dependency failure and ownership contracts.
- Whether aliasing between state and dependency results is forbidden by an external contract.
- Whether concurrent access is permitted; no synchronization is established here.
- Exact machine behavior for signed cursor overflow.
- Whether overflowed counts and zero-size backing requests are reachable in valid application states.
- Whether a zero or otherwise unusable backing-storage result can be returned normally.
- How descriptor chains and recycled nodes are eventually reclaimed.

Allocation-like terminology describes inferred intent, not an additional guarantee.

## Evidence

**Established static evidence:** the supplied representation shows four state words, 12-byte descriptors, a 16-byte cursor stride, recycled-link precedence, equality-triggered growth, unsigned count arithmetic, two ordered dependency calls, descriptor publication, and an unconditional final increment on the non-recycled path.

**Inferred intent:** the state manages sequential entries across linked storage blocks and may reuse entries through a linked recycled list.

**Unknowns:** external dependency behavior, broader ownership rules, valid-state invariants, and platform-specific overflow behavior are not supplied.

No runtime tests have been performed. The acceptance examples are arithmetic and control-flow consequences of the supplied static evidence, subject to their stated assumptions.
