# F-220eb07542db

## Purpose

F-220eb07542db conditionally attempts a two-result initialization. It obtains an intermediate value from one dependency and then calls another dependency up to twice with identical explicit arguments.

The routine evaluates a global record-address value twice before checking eligibility. The first evaluation supplies a **captured record address** for later direct record writes. The second supplies a **gate-check address**, whose 32-bit field at offset `0x10` determines whether the routine returns immediately. These addresses are equal only under an explicit stability assumption.

If the gate permits entry and the arguments are eligible, the routine clears both outputs, writes the selector into the captured record, and begins the dependency calls. Successful completion records both nonzero results and the context address.

Failure handling is asymmetric. Some failure paths conditionally invoke a dependency described here as “cleanup”; another bypasses that decision. Returning failure paths clear both outputs but do not explicitly undo the selector write.

“Initialization,” “selector,” “context,” and “cleanup” describe apparent roles, not established application semantics. Resource ownership and dependency internals remain unknown.

## Interface

### Arguments and result

The routine has four arguments and no explicit return value.

| Argument | Representation | Established use |
|---|---|---|
| Selector | 32-bit integer | Tested for nonzero and written at captured-record offset `0x10` on an eligible attempt. |
| First output address | Pointer to a 32-bit integer | Receives the first result; its current contents also control certain cleanup paths. |
| Second output address | Pointer to a 32-bit integer | Receives the second result. |
| Context address | Pointer represented in 32 bits | Checked for nonzero and a clear sign bit, passed to both result-producing calls, and stored on success. |

Each direct integer output write occupies four bytes. The stored context address also occupies four bytes.

No addition, subtraction, or ordering comparison is performed on the selector or result values. Any nonzero selector is eligible with respect to that argument, including a bit pattern interpreted as a negative signed integer. Any nonzero result is accepted without a sign check.

### Global address evaluations and record layout

The supplied representation establishes this sequence:

1. Evaluate the global record-address value and retain it as the captured record address.
2. Evaluate that global value again to obtain the gate-check address.
3. Read the 32-bit field at gate-check offset `0x10`.

These are two evaluations in the supplied representation, not a claim about the number of physical machine loads.

All later direct record writes use the captured address, not a fresh global evaluation:

| Offset | Width | Direct use |
|---|---:|---|
| `0x04` | 32 bits | Stores a nonzero first result; cleared after a returning cleanup call. |
| `0x08` | 32 bits | Stores a nonzero second result. |
| `0x0c` | 32 bits | Stores the original context address on success. |
| `0x10` | 32 bits | Stores the selector before the first dependency call. |

No direct access at offset `0x00` is established. The initial gate read belongs to the gate-check address, which need not identify the captured record.

Subsequent changes to the global record-address value do not redirect this invocation’s direct record writes. This does not establish that dependencies preserve the captured record’s contents, allocation, or lifetime.

### Preconditions for defined completion

The global value must be readable for both initial evaluations. The gate-check address must permit a 32-bit read at offset `0x10`.

If the gate value is nonzero, the routine returns without accessing either output location or directly accessing storage through the captured address. Thus, the captured address need not be dereferenceable on that path.

If the gate value is zero, requirements depend on the subsequent path:

- The cleanup decision requires a readable first output word.
- Final output clearing requires both output words to be writable.
- An eligible attempt requires both output words to be writable before any dependency call.
- Each reached captured-record write requires its target field to remain writable.
- Dependencies impose additional, unknown requirements on their arguments and accessible state.

There are no explicit checks for alignment, allocation extent, lifetime, or overlapping storage. Null or otherwise invalid arguments are not generally rejected safely.

Record offsets are byte offsets in the supplied 32-bit representation. No behavior is established for address formation that overflows or fails to identify valid storage; ordinary access descriptions assume valid field addresses.

## Behavior

### Initial gate

The routine first captures the global record-address value, then evaluates the global again, then reads the gate-check record’s 32-bit field at offset `0x10`.

If this field is nonzero, execution returns immediately:

- No dependency is called.
- Neither output location is read or written.
- No direct captured-record write occurs.

Existing output values therefore remain unchanged by this routine.

There is one gate-field check. The routine does not recheck that field before storing the selector or calling a dependency. In particular, it does not separately check the captured record’s gate unless the two initial address evaluations identify the same record.

### Eligibility

After a zero gate value, an initialization attempt is eligible exactly when:

- The selector is nonzero.
- The first output address is nonnull.
- The second output address is nonnull.
- The context address is nonnull.
- The context address, interpreted as a signed 32-bit integer, is nonnegative.

Together, the context conditions admit address representations `0x00000001` through `0x7fffffff`, inclusive.

The sign test concerns the context address representation, not the word stored at that address. No equivalent sign restriction applies to either output address or to the selector.

Eligibility does not prove that the context is usable by a dependency. The routine does not directly read or write context contents merely to validate the address.

Failed eligibility enters failure handling rather than returning immediately. That path may read the first output, invoke cleanup, and write both outputs even when an argument failed a null check.

### Eligible attempt

Before any dependency call, the routine performs these writes in order:

1. Zero to the first output word.
2. Zero to the second output word.
3. The selector to captured-record offset `0x10`.

It then calls F-1375398b8c0d with the single explicit argument zero and retains its returned 32-bit intermediate value.

If the intermediate value is zero, no result-producing call occurs. Execution proceeds to the cleanup decision. The prior output clearing does not guarantee that the first output remains zero: F-1375398b8c0d may have changed accessible memory.

For a nonzero intermediate value, the routine calls F-1705bbfb646a with these explicit arguments, in order:

1. The intermediate value.
2. The original context address.
3. The integer one.
4. The integer zero.

The first returned 32-bit result is written to the first output. The next branch tests that returned value, not a fresh read from the output location.

If the first result is zero, the routine bypasses the cleanup decision. It writes zero to the first output, writes zero to the second output, and returns.

If the first result is nonzero, it is written to captured-record offset `0x04`. F-1705bbfb646a is then called again with the same four explicit arguments. Identical arguments do not imply identical results or effects.

The second returned 32-bit result is written to the second output. The branch again tests the returned value rather than rereading output memory.

If the second result is nonzero, the routine:

1. Writes it to captured-record offset `0x08`.
2. Writes the original context address to captured-record offset `0x0c`.
3. Returns.

The routine does not require distinct result values. It performs no additional output repair after these record writes; aliasing can therefore affect the final output contents.

If the second result is zero, execution proceeds to the cleanup decision.

### Cleanup decision and final clearing

The cleanup decision is reached after:

- Failed eligibility;
- A zero intermediate value from F-1375398b8c0d; or
- A zero second result from F-1705bbfb646a.

It is bypassed after a zero first result.

At the decision, the routine reads the current 32-bit word at the first output address. A nonzero word causes a call to F-88503fb8bb83.

The cleanup argument is:

- The intermediate value returned by F-1375398b8c0d, if that call occurred; otherwise
- An incoming machine-state value whose source and meaning are not established by the four-argument interface.

The argument is not the first result merely because that result may occupy the first output.

A zero intermediate value can therefore be passed to cleanup if the first output is nonzero at the decision. Conversely, a previously nonzero first result does not guarantee cleanup if the output has since become zero.

After cleanup returns, the routine writes zero to captured-record offset `0x04`. If the first output was zero at the decision, both the cleanup call and this record clear are skipped.

The routine then writes zero to the first output, writes zero to the second output, and returns. The zero-first-result path performs these final writes without the cleanup decision.

All normal-completion descriptions assume successful memory accesses and normally returning dependencies. No local recovery from invalid access or nonreturning dependencies is shown.

## Side effects

### Persistent state and gate behavior

The selector write precedes all initialization dependencies. No direct failure-path operation explicitly resets captured-record offset `0x10`.

With nonoverlapping storage and no relevant dependency mutations, a failed eligible attempt leaves the captured record’s gate set to the selector. A later invocation returns immediately only if its own gate-check address identifies a record with a nonzero gate. That consequence is not unconditional when the global record-address value changes.

The entry check does not, by itself, protect the captured record from modification. If the two initial global evaluations yield different records, a zero gate in the gate-check record permits writes to the captured record even if the captured record’s gate was already nonzero.

Failure does not comprehensively clear captured-record state:

- Offset `0x04` is explicitly cleared only after cleanup returns.
- Offsets `0x08` and `0x0c` have no explicit failure-path clears.
- A zero first result bypasses cleanup and its associated record clear.
- A zero intermediate value does not alone cause a record clear.

Stale fields can remain. No rule for interpreting those stale fields is established.

### Aliasing and access order

No non-overlap requirement is checked. The stated write order remains significant when outputs, context, record fields, or global-address storage overlap.

If both outputs identify the same independent word, the second result overwrites the first. A zero second result then leaves zero for the cleanup decision, suppressing cleanup unless another effect changes the word.

Output writes that overlap record fields can change those fields outside their nominal update paths. In particular, final output clearing can clear the captured gate if an output aliases it. Assertions that failure leaves the gate nonzero therefore require nonaliasing and absence of relevant dependency mutations.

If context storage overlaps an output, initial output clearing can change memory later consumed through the context address.

A write to global-address storage after the two initial evaluations does not redirect the already captured write target. More generally, dependencies may modify accessible memory; the contract does not presume preservation.

### Ownership, lifetime, and synchronization

The routine visibly performs stores and calls dependencies. It does not directly establish allocation or release.

F-88503fb8bb83 is called “cleanup” only as an inferred role. Its invocation does not prove that a result, intermediate object, or context allocation is released.

Storing the context address does not establish ownership transfer, reference acquisition, borrowing duration, or required lifetime.

No locking, atomic transaction, or reentrancy guarantee is shown. Separate global evaluations, the gate-field read, and the later selector write do not establish synchronization or an atomic claim of the captured record.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless an example states otherwise, assume valid, distinct, nonoverlapping storage; both initial global evaluations identify the same record; dependencies return normally without additional relevant memory changes.

1. **Already gated.** A gate value of `7` causes immediate return. Outputs initially `41` and `42` remain unchanged. No dependency is called, even with selector zero or context null. Both global address evaluations still precede the gate read.

2. **Different capture and gate-check records.** Suppose the first global evaluation identifies record A and the second identifies record B. If B’s gate is nonzero, the routine returns without inspecting A’s gate or modifying A. If B’s gate is zero and arguments are eligible, direct record writes target A, even if A’s gate was initially nonzero. This specifies the consequence of differing evaluations, not how such a difference arises.

3. **Two-result success.** With gate zero, selector `9`, eligible context, intermediate `12`, and results `101` and `202`, outputs finish as `101` and `202`. Captured-record offsets `0x04`, `0x08`, `0x0c`, and `0x10` contain `101`, `202`, the context address, and `9`. Cleanup is not called.

4. **Negative selector.** Selector representation `0xffffffff` satisfies the nonzero test. With other eligibility conditions met, those same 32 bits are stored at captured-record offset `0x10`.

5. **Zero intermediate.** Both outputs finish zero. Neither result-producing call occurs. Cleanup is skipped because the first output remains zero under the example assumptions. The selector remains stored; prior values at captured-record offsets `0x04`, `0x08`, and `0x0c` remain unchanged.

6. **Zero first result.** The first result-producing call returns zero. There is no second call and no cleanup decision. Both outputs finish zero. Captured-record offset `0x04` retains its prior value.

7. **Zero second result.** The first result is `101`; the second is zero. Cleanup receives the intermediate value. After it returns, captured-record offset `0x04` and both outputs are zero. Offsets `0x08` and `0x0c` retain prior values, and the stored selector remains.

8. **Aliased outputs suppress cleanup.** Both outputs identify one independent word. Results are `101` and zero. The second output write makes that word zero, so cleanup is skipped. Captured-record offset `0x04` remains `101`.

9. **Context boundary.** Representation `0x7fffffff` passes the context eligibility test; `0x80000000` fails it. This establishes neither address’s usability. Failed eligibility still proceeds toward the first-output read and final clearing.

10. **Ineligible with zero first output.** With selector zero and valid outputs, the routine skips initialization calls, reads zero from the first output, skips cleanup, and clears both outputs. No direct record write occurs.

11. **Ineligible with nonzero first output.** With selector zero and a nonzero first output, cleanup is invoked with an argument not determined by the public inputs. If cleanup returns and accesses remain valid, captured-record offset `0x04` and both outputs are cleared. Acceptance must not invent a deterministic cleanup argument or characterize this as safe validation.

12. **Retry after failure.** If failure leaves the captured gate nonzero and a later invocation’s gate-check address identifies that same unchanged record, the later invocation returns without touching its outputs. Without that address and state condition, retry suppression is not established.

## Uncertainties

The following remain **documented_only**:

- Application meanings and valid domains of the selector, context, intermediate value, and results.
- Dependency memory, ownership, lifetime, and error contracts.
- External guarantees that the two initial global evaluations yield the same address.
- Whether those evaluations correspond to distinct physical loads.
- How a differing captured address and gate-check address could arise in an actual execution.
- External alignment, allocation, non-overlap, and record-lifetime guarantees.
- Behavior of invalid or overflowing field-address calculations.
- Whether the context sign restriction is intentional application policy.
- The source or calling-convention meaning of the incoming cleanup argument on ineligible paths.
- External gate-reset, synchronization, and reentrancy rules.
- Behavior after invalid memory access or a dependency that does not return normally.

The apparent intent is gated two-result initialization with conditional cleanup. That interpretation does not establish transactional rollback, safe argument rejection, resource release, or protection of the captured record by its own gate.

## Evidence

**Established static evidence:** the supplied representation evaluates the global record-address value once for capture and again for the gate-check address. It then reads the gate-check field at offset `0x10`; subsequent direct record writes use the captured address. The representation also establishes the 32-bit fields, context sign check, explicit call arguments, output-write order, returned-value branches, current-output cleanup decision, and absence of an explicit failure reset of the captured gate.

**Inferred intent:** the descriptive roles “initialization,” “selector,” “context,” and “cleanup.” These labels add no ownership or domain guarantees.

**Unknown:** dependency internals, external invariants, address stability, physical load realization, and the source of the cleanup argument when no intermediate value was obtained.

No runtime tests have been performed.
