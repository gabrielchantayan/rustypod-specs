# F-039e2803b28c

## Purpose

F-039e2803b28c conditionally replaces a resource reference in a caller-supplied record, updates a capacity-like field when replacement is requested, and records a requested logical size.

The established behavior is a comparison, an optional dependency call and failure-reporting call, followed by ordered record writes. The names “resource reference,” “logical size,” and “capacity” describe inferred roles; the supplied evidence does not establish the resource’s format, the units of either size field, or the semantics of the replacement operation.

This function does not itself copy, initialize, inspect, or release resource contents. Such effects, if any, belong to its dependencies and are not specified by the available evidence.

## Interface

### Inputs

The function receives:

1. A reference to a writable record containing at least three consecutive integer-width fields.
2. An unsigned requested size.

The recovered interface is interpreted here using 32-bit integer fields and 32-bit unsigned arithmetic. Under that interpretation, the record layout is:

| Offset | Width | Role in this contract |
|---|---:|---|
| 0 bytes | 32 bits | Resource reference, supplied to F-e74413f3255f and conditionally replaced by its result |
| 4 bytes | 32 bits | Logical size, written with the requested size on normal completion |
| 8 bytes | 32 bits | Capacity-like value, read as unsigned for the initial comparison and conditionally replaced |

The first field is represented as an integer in the supplied interface. Its interpretation as an address, handle, allocation token, or another kind of reference is not established.

The record fields are presented as signed integers, but the capacity comparison explicitly uses an unsigned interpretation. Accordingly, capacity values with the high bit set participate in comparison as large nonnegative values, not as negative capacities.

### Output

There is no explicit return value or success status.

If execution reaches the end, the logical-size field has been written with the requested size. Whether that state represents a successfully resized resource depends on the dependency results and, on the zero-result path, whether the failure-reporting dependency returns.

### Preconditions

The caller must provide a record reference suitable for the accesses performed:

- The capacity field must be readable.
- The logical-size field must be writable.
- If the growth branch is taken, the resource-reference field must be readable, and the resource-reference and capacity fields must be writable.
- The record must remain valid through intervening dependency calls for the subsequent writes to be meaningful.

The function contains no explicit null check, record-length check, alignment check, or validation of the stored resource reference.

Requirements imposed by F-e74413f3255f on its first argument are unknown. In particular, the evidence does not establish whether a zero resource reference is valid or whether the reference must identify a resource previously created by a particular allocator.

## Behavior

### Initial decision

The function reads the third record field and compares its unsigned value with the requested size.

- If the stored capacity is less than the request, it takes the growth branch.
- If the stored capacity equals or exceeds the request, it skips that branch.

The comparison is strict. An exact-capacity request does not call either dependency.

This decision does not depend on the record’s existing logical size. That field is not read by this function.

### Request within the stored capacity

When the stored capacity is at least the requested size, the function writes the requested size into the logical-size field and returns.

On this path, the function performs no direct write to the resource-reference or capacity fields and invokes neither dependency. It does not inspect the resource reference.

Consequences include:

- Reducing the logical size does not request resource shrinking.
- Requesting the existing logical size still performs the logical-size write.
- Requesting zero always skips the growth branch under the unsigned comparison.
- A large stored capacity bit pattern can prevent replacement even if the record would be considered invalid by a higher-level invariant. No such invariant is checked here.

### Request exceeding the stored capacity

When the request is greater than the unsigned stored capacity, the function obtains the first record field and calls F-e74413f3255f with four arguments, in these positions:

| Position | Value |
|---|---|
| First | The resource-reference value read from the record |
| Second | The requested size plus 16, using unsigned arithmetic |
| Third | The constant 24 |
| Fourth | The constant 1 |

The source establishes these argument values, not their meanings. In particular, it does not establish whether 24 is an element size, alignment, category, or another parameter. It also does not establish the meaning of 1.

The result is retained for a zero/nonzero test and, if execution continues, for storage into the first record field.

### Nonzero dependency result

If F-e74413f3255f returns a nonzero value, the function performs these direct writes in order:

1. Store the returned value in the resource-reference field.
2. Store the requested size plus 16 in the capacity field.
3. Store the requested size in the logical-size field.

It then returns without an explicit status.

The function does not verify that the returned reference actually provides the recorded capacity. It also does not inspect the referenced resource after the call.

### Zero dependency result

If F-e74413f3255f returns zero, the function calls F-49825a8405da with:

1. The value 4.
2. A reference to a fixed static object.

The static object’s contents and purpose are unavailable. Calling it a diagnostic message or error descriptor would be an inference.

This call occurs before any of the growth branch’s three direct record writes.

The subsequent behavior depends on whether F-49825a8405da returns:

- **If it returns normally:** the function stores zero in the resource-reference field, stores the requested size plus 16 in the capacity field, writes the requested logical size, and returns.
- **If it does not return:** the later direct writes do not occur along that execution path.

There is no explicit rollback, preservation of the previous reference, retry, or alternate allocation path. A returning failure handler therefore permits normal completion with a zero resource reference and updated size fields.

### Arithmetic and boundary behavior

Under the 32-bit unsigned model, adding 16 is modulo \(2^{32}\). There is no explicit overflow check, saturation, or rejection of large requests.

Examples of the computed capacity argument include:

| Requested size | Requested size plus 16 |
|---:|---:|
| 0 | 16 |
| 100 | 116 |
| 4,294,967,279 | 4,294,967,295 |
| 4,294,967,280 | 0 |
| 4,294,967,295 | 15 |

The addition is relevant only when the growth branch is taken. A zero request does not enter that branch, regardless of the initial capacity bit pattern.

The branch condition compares the original requested size with the original stored capacity. It does not compare the wrapped addition with the stored capacity. Consequently, a request exceeding the stored capacity can result in a dependency argument and recorded capacity smaller than the request.

The final stores also place unsigned quantities into fields represented as signed integers. This contract describes the intended 32-bit stored bit patterns, rather than claiming that every possible native C implementation must handle out-of-range signed conversion identically.

## Side effects

### Direct record access order

Excluding effects inside dependencies, the observable sequence is:

1. Read the capacity field for the unsigned comparison.
2. On the growth branch, read the resource-reference field.
3. Call F-e74413f3255f.
4. If its result is zero, call F-49825a8405da.
5. If execution continues on the growth branch, write the resource-reference field.
6. Write the capacity field.
7. Write the logical-size field.

On the non-growth path, only the capacity read and logical-size write occur.

The direct record updates are not an atomic transaction. The function contains no synchronization operation or mechanism to conceal intermediate states.

### Dependency interference

Neither dependency is established to preserve global state, the record, or referenced memory.

If a dependency changes the record but returns with the record still accessible, the function does not reread the original capacity to reconsider its branch. On the growth path, its later direct writes replace all three record fields with the retained result, the computed capacity value, and the requested size.

The original resource-reference argument has already been obtained before F-e74413f3255f executes. Subsequent dependency changes to the first field do not change that completed call’s argument.

Other dependency effects are not undone by this function.

### Ownership and resource lifetime

The evidence does not establish whether F-e74413f3255f:

- Reuses the original resource.
- Allocates a replacement.
- Copies existing contents.
- Releases the original resource.
- Leaves the original resource valid when returning zero.

F-039e2803b28c performs no separate release. When execution continues through the growth-path writes, it overwrites the record’s old resource-reference value regardless of whether the dependency returned zero or nonzero.

No ownership guarantee can be derived solely from that overwrite.
