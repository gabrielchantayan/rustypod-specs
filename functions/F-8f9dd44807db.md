# F-8f9dd44807db

## Purpose

F-8f9dd44807db processes a request containing a one-byte operation selector and a decoded 32-bit argument. It acquires an auxiliary object, selects an operation-specific callback descriptor, optionally performs operation-specific preparation, and invokes the callback against an adjusted context address.

The normal return values distinguish four outcomes:

| Return value | Established meaning |
|---|---|
| 0 | The selected callback returned a zero low-order 32-bit result; the success-state update and any required follow-up completed. |
| 1 | A supported operation reached callback selection, but its descriptor did not qualify for invocation. |
| 2 | The selected callback returned a nonzero low-order 32-bit result. |
| 4 | The request type or selector was rejected, or operation 5 failed its unsigned bounds check. |

Failure to acquire the auxiliary object, or a zero result from initialization, instead enters a dependency shown as non-returning.

The apparent intent is operation dispatch with shared lifecycle handling. Operation names, application-level meaning, and the meaning of the numeric statuses are not established beyond the behavior described here.

## Interface

The function receives two address-valued arguments represented as 32-bit values:

- **Request address:** identifies a request record.

The request record exposes these fields:

The payload exposes:

The decoder supplies an unsigned 32-bit argument. Its input encoding, read extent, alignment requirements, and failure behavior are unknown.

The context exposes a byte at offset +748, or +0x2EC. Operations 2, 3, 4, and 8 compare that byte with 2. The callback mechanism can also access a receiver derived from the context rather than the context’s starting address.

### Shared state

Two shared pointer locations participate:

- **Dispatch-table pointer:** identifies memory holding callback descriptors.
- **State pointer:** identifies memory containing a success-related byte at offset +4 and a 32-bit field at offset +28.

These names identify their observed roles, not ownership or application-level types.

After successful object acquisition, the function invokes initialization and then captures the state pointer followed by the dispatch-table pointer. Those captures occur before the initialization result is tested for zero.

The saved state pointer is used for the eventual success-byte write. The saved dispatch-table pointer is used specifically for operation 5. Other operation descriptors are read through the dispatch-table global after initialization, at their respective selection points.

## Behavior

### Request admission and decoding

The first observed request access is the 16-bit discriminator at offset +12.

If it is not 5, the function returns 4. It does not read the payload, decode an argument, acquire an object, or invoke finalization.

For discriminator 5, the function reads the selector from the payload’s first byte, then invokes F-c25a2fcc75b5 with the payload address advanced by one byte.

Decoding occurs before selector validation. Therefore, even selector 0 or a selector from 10 through 255 causes a decoder call.

Only selectors 1 through 9 continue. Other selectors return 4 after decoding, without acquiring an object or invoking finalization.

### Object acquisition and initialization

For a supported selector:

1. The two callback-descriptor words begin as zero.
2. F-be45cd43f92d is invoked with the numeric argument 0.
3. Its returned object pointer is stored in a local handle.
4. A null object pointer causes entry into F-a817d8d58c10.
5. For a non-null object, F-b7af80e829ec is invoked without explicit arguments.
6. The shared state pointer and dispatch-table pointer are captured, in that order.
7. A zero initialization result causes entry into F-a817d8d58c10.

F-a817d8d58c10 is shown as not returning. No normal finalization call follows either of these failure paths in the supplied representation. Whether the dependency terminates execution, transfers control, or performs cleanup internally is unknown.

Once these steps succeed, the tentative normal return value is 1.

|---|---:|---:|---|

**Selector 1.** Only the exact unsigned 32-bit value 0xFFFFFFFF is replaced with zero. This normalization is not established for other selectors.

**Selectors 2, 3, and 4.** The context mode byte is compared with 2. The supplied representation includes argument-dependent branches under that condition, but all displayed alternatives have no visible effect. It does not establish argument remapping, rejection, or a different callback selection. Assigning such behavior would require additional evidence.

**Selector 5.** The function invokes an indirect object method through byte offset +0x108 in the object’s method table, passing the object as receiver. Its 32-bit result is treated as unsigned.

The decoded argument must be strictly less than that result:

- If the comparison fails, the tentative return becomes 4. Both descriptor words remain zero, so callback dispatch is skipped.
- If it succeeds, a temporary 32-bit value is initialized to 1. An object method at method-table byte offset +0xAC receives the object and the temporary’s address. Its return value is not used. The descriptor is then read from the previously captured dispatch-table pointer.

The object’s method-table pointer is obtained for the later method call rather than being assumed unchanged across the earlier call. Any modification of the temporary by the preparation method has no later visible use.

**Selector 8.** The descriptor is read before examining the context mode byte.

If that byte equals 2:

1. A 32-bit value of 3 is written at offset +28 through the then-current shared state pointer.
2. An object method at method-table byte offset +0x74 is invoked with the object as receiver.

This preparation occurs even if the captured descriptor will subsequently fail the callback-presence test. Changes made by the object method do not cause the descriptor to be reloaded.

### Callback presence and receiver resolution

A descriptor qualifies for invocation when either:

- Its first word is nonzero; or
- The low bit of its second word is set.

Consequently, a zero first word does not necessarily mean “no callback.” A descriptor whose first word is zero and second word is odd proceeds through indirect dispatch.

The second word has two roles:

- Bit 0 chooses direct versus method-table-based target resolution.
- Its signed 32-bit value, arithmetically shifted right by one bit, supplies a byte displacement added to the context address.

The resulting address is the callback receiver. The displacement is not established as nonnegative.

Target resolution is:

- **Low bit clear:** the first descriptor word supplies the callable target directly.
- **Low bit set:** the adjusted receiver supplies a method-table pointer. The first descriptor word, with its bottom two bits cleared, is a byte offset into that table. The callable target is read from that location.

No range checks are shown for receiver adjustment, the table offset, or the resolved target. The 32-bit address model is evident, but behavior for invalid address arithmetic is not defined by the supplied material.

The callback receives, in order:

1. The adjusted receiver.
2. The acquired auxiliary object.
3. The decoded argument, including selector 1’s normalization when applicable.

### Callback result and success handling

Immediately before invocation, the tentative return value becomes 2.

The callback result is represented as a 64-bit quantity, but only its low-order 32 bits determine success:

- Nonzero low-order 32 bits leave the return value at 2.
- Zero low-order 32 bits enter success handling.

On success, a single zero byte is written at offset +4 through the state pointer captured after initialization. This is not a fresh lookup of the shared state pointer.

The tentative return value then becomes 0.

For selectors other than 5 and 7, F-c5890456f563 is invoked with the original context address and the acquired object, in that order. Selectors 5 and 7 skip this follow-up but still perform the success-byte write.

The callback result’s high-order portion does not have an established externally observable use here. It is not passed to the success follow-up.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. They assume valid memory and normal return from all dependencies except the explicitly non-returning dependency.

1. **Wrong request discriminator.** With a discriminator other than 5, return 4 without decoding, acquiring an object, or finalizing.

2. **Unsupported selector.** With discriminator 5 and selector 0 or 10, invoke the decoder, then return 4. Do not acquire an object.

3. **Acquisition failure.** With a supported selector and a null acquisition result, enter F-a817d8d58c10 without calling initialization. Do not claim a normal status or finalization call.

4. **Selector 1 normalization.** If decoding produces 0xFFFFFFFF and the callback is present, pass argument 0. If that callback’s low-order result is nonzero, finalize and return 2 without clearing the success byte or invoking the success follow-up.

5. **Absent descriptor.** If both descriptor words are zero, skip callback invocation, finalize, and return 1, except when selector 5 has already selected status 4.

6. **Indirect descriptor with zero first word.** If the first word is zero and the second is odd, do not classify the descriptor as absent. Resolve the target using table offset zero at the adjusted receiver.

7. **Selector 5 boundary.** If the bound is 8, argument 7 proceeds to preparation and descriptor selection; argument 8 returns 4 after finalization. The comparison is unsigned, so 0xFFFFFFFF also fails against bound 8.

8. **Selector 5 success.** After a qualifying bound, preparation, and callback with zero low-order result, clear the saved state’s byte at +4, omit F-c5890456f563, finalize, and return 0.

9. **Selector 8 without a callback.** In mode 2 with a zero descriptor, write 3 at current state +28 and invoke the +0x74 object method. Then skip the callback, finalize, and return 1.

10. **State-pointer replacement during a callback.** If the callback replaces the shared state pointer and returns a zero low-order result, clear byte +4 in the previously saved state object, not automatically in the replacement object.

11. **High callback-result bits.** A result with zero low-order 32 bits and nonzero high-order bits still enters success handling. High-order bits alone do not produce status 2.
