# F-d87ec25b1c61

## Purpose

F-d87ec25b1c61 conditionally replaces a pointer-valued field in a caller-supplied object. It compares the field’s existing value with a supplied replacement. If the values differ, it invokes an indirect operation on the existing value when that value is non-null, then stores the replacement.

The established behavior is pointer comparison, conditional indirect dispatch, and assignment. Interpreting the indirect operation as destruction, release, or reference-count decrement is inferred intent, not an established ownership contract.

An identical replacement is a no-op after the initial field read. In particular, the function does not invoke the indirect operation when both values are the same non-null pointer.

## Interface

### Inputs

The function has two explicit inputs:

- **Containing-object address.** The first input supplies the base address used to locate the managed field. The field begins at byte offset **0x34**, or **52 decimal**, from this address.
- **Replacement pointer.** The second input supplies the pointer value that may be stored in that field. Null is accepted by the visible control flow. The function itself does not dereference this input.

The supplied representation declares the containing-object address as an integer and the replacement as a pointer to an integer-sized element. Their visible use is more specific than those declarations: the first is used as an address, and the second is compared and stored as a pointer. No integer-element access through the replacement is established.

### Output

The function has no explicit return value. Its observable result is the optional indirect invocation and the optional update to the field.

It does not return the previous pointer, report whether a replacement occurred, or expose the indirect operation’s return value.

### Widths and layout

The visible layout has three relevant locations:

| Location | Visible role |

| Beginning of the non-null previous pointee | Value used as the base address of a dispatch structure |

The offsets are byte offsets. The dispatch offset is **4 bytes**, not four entries and not four times the host pointer size.

However, the excerpt does not independently establish the target ABI, pointer width, endianness, alignment requirements, or signed-address arithmetic rules. The offset addition is address calculation. No bounds check or overflow check is visible. An implementation reproducing this behavior must use the source target’s layout and address rules rather than silently substituting the host platform’s native pointer layout.

### Preconditions

For defined, successful execution:

- The containing-object address plus 0x34 must identify readable storage for the pointer-valued field.
- If the pointers differ and execution reaches the assignment, that field must also be writable.
- If the previous pointer is non-null and differs from the replacement, the previous pointee must support the dispatch reads described above.
- The resulting callable address must be valid under the target calling convention.
- If the indirect operation returns normally, the containing-object field must still be valid for the subsequent write.

The function contains no explicit validation of these conditions.

## Behavior

### Initial read and comparison

The first established memory access is a read of the pointer-valued field at containing-object offset 0x34. The value obtained by this read becomes the previous pointer used for the decision.

That pointer is compared directly with the replacement pointer. There is no comparison of pointed-to contents, object identity beyond pointer equality, or dispatch metadata.

If the two values are equal, the function returns immediately. On this path:

- There is no explicit write to the field.
- There is no indirect invocation.
- Neither pointer is dereferenced by the visible function after the field read.
- No replacement validation occurs.

This rule includes both equal non-null pointers and two null pointers.

### Replacement when the previous value is null

If the previous pointer is null and the replacement differs, the function skips indirect dispatch and writes the replacement into the field.

Because this branch requires inequality, its replacement is necessarily non-null under the ordinary null-pointer interpretation. The visible function does not inspect the replacement’s target before storing it.

No initialization, acquisition, retention, or validation operation is visible on this path.

### Replacement when the previous value is non-null

If the pointers differ and the previous pointer is non-null, the function performs an indirect call before assigning the replacement.

The dispatch lookup has this dependency order:

1. Read the dispatch-base value from the beginning of the previous pointee.
2. Read the callable address from byte offset 4 relative to that dispatch base.
3. Invoke the resulting callable.
4. If the invocation returns normally, write the originally supplied replacement into the containing-object field.

These are the accesses and ordering established by the visible function. The indirect operation may perform additional accesses or cause other effects; those are not constrained by this excerpt.

The call expression shows no explicit arguments. That does not establish that the callee receives no meaningful receiver or context: hidden calling-convention state is not resolved by the supplied representation. Conversely, a receiver argument must not be invented as an established fact.

The function does not explicitly store the replacement before the call. Consequently, on entry to the indirect operation, this function has not yet changed the field. Whether the callee observes the previous value depends on whether anything else has modified the field.

### Assignment after the call

Following a normal return from the indirect operation, the function stores the supplied replacement into the field.

There is no visible reread of the field, second equality check, or validation between the call and the store. Thus, if the callee changes the field and returns while the containing object remains valid, the outer invocation still writes its originally supplied replacement. It does not condition that write on the field retaining its initial value.

The same issue applies to reentrant calls: the visible routine has no reentrancy guard or conflict detection. Any completed nested update can be superseded by the outer assignment.

These statements describe the visible control flow, not a guarantee that the callee preserves the containing object or permits execution to continue safely.

## Side effects

The function directly performs:

- One initial read of the managed field.
- Additional dispatch-related reads only when the previous pointer is non-null and differs from the replacement.
- One indirect invocation on that same path.
- One write of the replacement on either unequal-pointer path, provided any required indirect call returns normally.

It performs no explicit allocation, deallocation, reference-count update, logging, synchronization, or error reporting.

### Ownership

The excerpt does not establish ownership transfer.

The indirect call before replacement is consistent with releasing or disposing of a previous association. That interpretation remains inferred. The callable could have another purpose, could retain the previous object, or could affect unrelated state.

Likewise, storing the replacement does not establish that the containing object acquires ownership, increments a reference count, or assumes responsibility for future destruction. No visible operation is performed on the incoming pointee.

There is also no established guarantee that the old and new pointers refer to independent storage. Pointer inequality alone does not exclude aliasing between their reachable objects.

Invalid containing-object storage, invalid dispatch metadata, or an invalid callable address is not converted into a structured error by this function. The concrete failure mode depends on the execution environment.
