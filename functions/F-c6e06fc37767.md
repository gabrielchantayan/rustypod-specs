# F-c6e06fc37767

## Purpose

F-c6e06fc37767 performs a lookup and conditionally attempts insertion into a caller-supplied container. It communicates a position descriptor and an insertion indicator through F-3358fa3c1fcb.

Two outcomes are established by the visible control flow:

- A nonzero lookup result is reported with the initial position token and an insertion indicator of zero.
- A zero lookup result selects allocation, construction, optional growth preparation, insertion, and reporting with an insertion indicator of one.

The insertion indicator identifies the path taken. It is not an independently checked success result. In particular, a zero allocation result does not prevent the insertion call or change the indicator to zero.

Unique-key insertion is inferred intent. The key-equivalence rule, container organization, meaning of a position token, and actual success conditions are not established here.

## Interface

The function accepts three arguments and has no explicit return value.

| Argument | Width and established use |
|---|---|
| Reporting destination | An opaque 32-bit value, retained for F-3358fa3c1fcb. This function does not directly dereference it. |
| Container address | A 32-bit address used for metadata access and to locate embedded storage. |
| Input record address | A 32-bit pointer to words of 32 bits each. Words zero and one participate in lookup preparation. Words zero through two are read again during construction if allocation is nonzero. |

Two growth dependencies produce 64-bit results. Each result is subsequently separated into low and high 32-bit halves.

### Directly accessed container layout

Offsets below are in bytes from the container address.

| Offset | Access width | Established use |
|---|---:|---|
| +4 | 32 bits | Displacement added to the container address for F-58cc241cfb6b. |
| +8 | 32 bits | Argument to F-0ec3a2a1b51e when growth preparation is selected. |
| +12 | 32 bits | Threshold compared using unsigned ordering. |
| +16 | Address | Beginning of embedded storage passed to position and insertion dependencies. |
| +32 | 32 bits | Count-like quantity used in the growth decision and request calculation. |

“Count,” “threshold,” and “embedded storage” describe observed roles rather than a proven container type. This function does not directly increment a container count.

### Position descriptor

The reporting dependency receives the address of a temporary descriptor comprising two consecutive 32-bit words:

| Descriptor offset | Content immediately before reporting |
|---|---|
| +0 | Selected position token. |
| +4 | Existing-entry pointer or allocation-derived insertion pointer. |

It also receives the address of a separate 32-bit insertion indicator. These addresses refer to temporary storage, not a documented persistent result object.

### Preconditions

Normal execution requires valid readable container fields and valid input reads at the times described below. The first two input words are needed for initial lookup preparation. The third word is additionally needed if the missing-entry path obtains a nonzero allocation.

A nonzero allocation must support the direct writes through offset +16. The allocator is asked for 24 bytes, but the caller does not independently verify its returned region, alignment, or accessibility.

There are no explicit null checks for the container or input. No explicit bounds, alignment, concurrency, or aliasing checks appear. Allocation disjointness from the input is not established.

Dependencies intervene between the initial input reads and the later copy. Validity and unchanged contents across those calls cannot be assumed merely from their interfaces.

## Behavior

### Lookup preparation and branch selection

The first dependency call is F-58cc241cfb6b. Its arguments are:

- The container address plus the displacement read at container offset +4.
- The container address.
- Input word zero.
- Input word one.

The resulting 32-bit value is retained for position calculations. The supplied representation does not establish the relative order of the independent input and container reads used to assemble this call’s arguments.

F-d930d59892c3 is then called with the embedded-storage address at container offset +16 and the retained value. Its 32-bit result becomes the initial position token.

F-e1a0d3f7ef55 is called next with the container address and that token. Its result is treated as a pointer:

- Nonzero selects existing-entry reporting.
- Zero selects the allocation and insertion path.

The calls occur in that order. There is no second F-e1a0d3f7ef55 call later, including after growth preparation.

### Existing-entry reporting

For a nonzero lookup result, the function prepares:

- A descriptor containing the initial token followed by the returned pointer.
- A separate 32-bit insertion indicator equal to zero.

It calls F-3358fa3c1fcb with the original reporting destination, the descriptor address, and the indicator address, then returns normally if that dependency returns normally.

The allocation, initialization, growth, and insertion sequence is skipped. There are no direct input-record reads beyond those used for the initial lookup preparation on this path.

The descriptor and indicator values are established immediately before reporting. The reporting dependency may modify the supplied storage; its behavior is not constrained here.

### Allocation and preliminary initialization

On a missing entry, the function prepares the embedded-storage address and temporary bookkeeping, including a tracked allocation pointer initially set to zero.

It calls F-871e64ddc6de with arguments 24 and zero, then retains the returned allocation pointer.

Next, an external dependency without a supplied opaque ID receives temporary storage and a size argument of 24. This call occurs even if the allocation pointer is zero. The size argument does not, by itself, establish that all 24 bytes are initialized or what values they contain.

After that call, the fifth 32-bit word of the temporary storage is set to zero.

If allocation is nonzero, direct allocation writes occur in this order:

1. Copy the temporary storage’s first word to allocation offset +0.
2. Copy its second word to allocation offset +4.
3. Copy its third word to allocation offset +8.
4. Copy its fourth word to allocation offset +12.
5. Write zero to allocation offset +16.

No direct write to allocation offset +20 is visible. Neither the allocator nor the external initializer is established to supply any particular value there.

### Input-copy read and write ordering

After preliminary allocation initialization, and only when the tracked allocation pointer is nonzero, the input copy has this observable ordering:

1. Read input word one and retain its 32-bit value.
2. Read input word zero and write that value to allocation offset +0.
3. Write the previously retained input word one to allocation offset +4.
4. Read input word two and write that value to allocation offset +8.

The read of input word one therefore precedes both the read of input word zero and the write to allocation offset +0. The read of input word two follows the write to allocation offset +4.

This is not an entry-time snapshot, a simultaneous three-word snapshot, or a sequence that reads each input word immediately before writing the corresponding destination in increasing index order. Aliasing can distinguish those behaviors.

Immediately after the copy, the direct-write results are:

| Allocation offset | Established content |
|---|---|
| +0 | Input word zero captured after the read of input word one and before the destination write at +0. |
| +4 | Input word one captured before the destination writes at +0 and +4. |
| +8 | Input word two captured after the destination write at +4. |
| +12 | Fourth temporary word copied during preliminary initialization. |
| +16 | Zero written during preliminary initialization. |
| +20 | No direct initialization established. |

These entries describe values captured at their respective read times. They do not describe the input’s values at function entry. Preliminary allocation writes may themselves affect aliased input before these reads occur.

Lookup preparation, allocation, and external initialization all precede this copy. Changes during those operations can make the copied values differ from the words used for lookup.

A zero allocation result skips all allocation writes and these three input-copy reads. It does not skip the external initialization call or the subsequent growth decision, insertion, and reporting.

### Growth decision

After construction, the function reads the unsigned 32-bit count-like field at container offset +32. It calculates its increment by one using 32-bit unsigned arithmetic.

It then reads the threshold at container offset +12. Growth preparation is selected when the threshold is less than or equal to the incremented quantity under unsigned comparison. Equality selects growth.

The requested quantity is the unsigned maximum of:

- The original count-like value plus that value logically shifted right by one bit.
- The count-like value incremented by one.

Both additions wrap modulo \(2^{32}\). The calculation is therefore not an unrestricted mathematical multiplication by 1.5.

The count-like field is read after construction, not at function entry. Dependency-mediated or alias-induced changes before that read can affect the decision.

### Selected growth sequence

When growth preparation is selected, the calls occur in this order:

1. F-0ec3a2a1b51e receives the 32-bit field read from container offset +8 and returns a retained 64-bit value.
2. F-9e5e664c8ae7 receives the computed requested quantity and returns another retained 64-bit value.
3. F-596e18a33aec receives four 32-bit arguments: the low half and high half of the second result, followed by the low half and high half of the first result.
4. F-936416edf8a5 is called without explicit arguments.
5. F-1cd4c8db3fc1 is called without explicit arguments.
6. Its result, represented as a signed 32-bit quantity, is incremented by one and supplied to F-ffa34101f302 together with the container address.

The numeric meanings of these transformations are unknown. The supplied representation does not safely resolve signed-overflow behavior for the final increment.

After this sequence, F-d930d59892c3 is called again with the embedded-storage address and the original retained result from F-58cc241cfb6b. The new token replaces the initial token.

Without selected growth, the initial token is reused. Token recomputation depends on the earlier growth decision, not on a separately tested success result from the growth dependencies.

### Insertion and final reporting

The insertion pointer is formed as:

- Allocation address plus 16 bytes, for nonzero allocation.
- Zero, for zero allocation.

The tracked allocation pointer is then cleared before calling F-e96639aeb0c2. That dependency receives:

- The embedded-storage address.
- The insertion pointer.
- The selected position token.

Its outcome is not explicitly tested.

After the insertion call returns, the function prepares the descriptor with the selected token and insertion pointer, sets the 32-bit insertion indicator to one, and calls F-3358fa3c1fcb.

A subsequent cleanup operation is guarded by the tracked allocation pointer being nonzero. The visible ordinary sequence has already cleared that pointer, so it does not release the allocation through that guard.

Clearing the tracked pointer suggests relinquishment of local cleanup responsibility. It does not prove that insertion, reporting, or any other dependency takes ownership.

## Side effects

### Direct effects

Direct writes affect temporary storage and, for nonzero allocation, the allocation fields described above. Temporary bookkeeping includes phase flags and the tracked pointer; those flags are not passed as explicit arguments to the listed dependencies.

No direct container metadata update is visible. Membership changes, count updates, capacity changes, link changes, and backing-storage replacement would have to occur through dependencies.

Input and allocation regions are not proven disjoint. Accordingly, allocation initialization and copying may change storage subsequently read through the input address.

### Dependency-mediated effects and lifetime

No dependency is established to preserve globals, input storage, container state, allocation contents, or other reachable memory.

The reporting descriptor and indicator are temporary. Retaining their addresses for later use requires a lifetime arrangement not established by this function.

The allocation-derived insertion pointer addresses offset +16, not the allocation base. Whether a dependency can recover or release the base allocation is unknown.

### Errors and abnormal completion

There is no explicit error return, allocation-failure report, rollback, or retry.

If allocation returns zero and all subsequent calls return normally, insertion receives zero and reporting still receives indicator one.

Invalid memory access or a dependency that faults, raises an exception, terminates execution, or otherwise fails to return may prevent later operations. Exceptional cleanup and unwinding behavior are not established.

## Acceptance examples

These are conditional static expectations, not runtime test results. They assume valid accesses and normal dependency returns. Each example additionally assumes that unspecified dependency effects do not invalidate its stated conditions.

### Existing entry

If F-e1a0d3f7ef55 returns a nonzero pointer, reporting receives the initial token and that pointer, with indicator zero. The missing-entry allocation and insertion sequence does not occur.

### Insertion without growth

If lookup misses, the count-like field reads as 3, and the threshold reads as 8, the incremented quantity is 4 and growth is not selected.

For a nonzero allocation, insertion receives allocation address plus 16 and the initial token. Reporting receives those same position values with indicator one.

### Equality and larger requests

With a count-like value of 3 and threshold 4, equality selects growth. The requested quantity is 4. The token is recomputed afterward without repeating the existing-entry lookup.

With a count-like value of 10 and threshold 11, growth is selected and the requested quantity is 15.

### Aliased input-copy ordering

Suppose a valid input record begins four bytes before the allocation base. Immediately after preliminary allocation initialization:

- Input word zero, just before the allocation, contains 17.
- Allocation offset +0 contains 34.
- Allocation offset +4 contains 51.

The copy first captures input word one from allocation offset +0, retaining 34. It next reads input word zero and writes 17 to allocation offset +0. It then writes the retained 34 to allocation offset +4.

Only afterward does it read input word two, which aliases allocation offset +4 and now contains 34. It writes that value to allocation offset +8.

The resulting first three allocation words are therefore 17, 34, and 34. Reading input word one only after writing allocation offset +0 would instead capture 17 and would not preserve the established behavior.

### Zero allocation

If lookup misses and allocation returns zero, external temporary initialization still occurs. No allocation initialization or input-copy reads occur. If later calls return normally, insertion receives zero, and reporting receives a zero position pointer with indicator one.

### Unsigned boundary

For a count-like value of 4,294,967,295, incrementing wraps to zero.

- With a positive threshold, growth is not selected.
- With a zero threshold, growth is selected and the requested quantity is 2,147,483,646.

No explicit rejection of this boundary appears.
