## Behavior

### 1. Resolve and invoke the indirect callback

Before either named dependency is called, the function resolves an indirect target.

The lookup has this dependency order:

1. Use the source-designated base value to locate the slot at byte offset 4.
2. Read the object pointer from that slot.
3. Read the dispatch-table address from the beginning of the pointed-to object.
4. Locate the function-pointer slot at byte offset 100 from that table address.
5. Read the function pointer and invoke it.

These are dependent reads: each later address requires a value obtained by the preceding lookup. The evidence does not support replacing this chain with a fixed target or resolving it after either named dependency has run.

Both offsets are byte offsets. The 100-byte offset is not an index of 100 table entries. Under a four-byte function-pointer layout, it corresponds to zero-based slot 25. That slot-number interpretation is conditional on pointer width; the byte offset itself is directly established.

The table-base value is represented through an integer-valued read, rather than through a declared table structure. The visible operation adds 100 to that integer before treating the resulting address as a function-pointer location. No bounds or overflow check is visible. A portable wrapping rule for overflowing signed address arithmetic is not established by the supplied source representation.

No explicit argument is supplied to the callback. In particular, the object pointer used to find the dispatch table is not explicitly passed as a receiver. The actual callback ABI, including any implicit context or machine-state inputs, remains unspecified.

The wrapper does not inspect a callback result or branch on it. If the callback returns normally, execution proceeds to F-c26f463fe480.
