# F-e2a82179d27a

## Purpose

F-e2a82179d27a searches a bounded range of candidate records for a zero availability marker, then stores four 32-bit input values at a destination derived from the selected candidate index. It optionally reports that index through caller-provided storage.

The search covers 50 candidate positions at a 16-byte stride. This establishes an 800-byte search extent relative to an unchanged base, not the actual size of the backing allocation. Storage outside that extent may exist but is not searched.

The global table base is evaluated separately for each occupancy probe and again when constructing the destination after a zero marker is found. Consequently, the destination corresponds to the record whose marker was observed as zero only if the base remains unchanged across the relevant reads. Continued validity of both storage regions is not sufficient to ensure that correspondence.

Exhaustion does not produce an ordinary capacity-error return. If all 50 probes find nonzero markers, the function proceeds to an attempted store through a null destination.

The apparent purpose is record registration or slot allocation. That interpretation is inferred; the meanings of the four stored values and their resource lifecycle are not established.

## Behavior

### Initial rejection

The first decision tests whether the first value is zero.

If it is zero, the function immediately returns `0xFFFFFFCE`. It does not read the global table base, inspect candidate storage, write a record, or access the optional index destination.

Thus, invalid table storage or an invalid non-null output destination is not accessed on this path.

### Ordered probing and base evaluation

For a nonzero first value, the candidate index starts at zero. Each probe has this explicit access sequence:

1. Read the current global table-base value.
2. Form the candidate address using that value and the current index’s 16-byte offset.
3. Read the 32-bit marker at that address.
4. Continue to the next index if the marker is nonzero, or stop probing if it is zero.

Indices increase strictly from 0 toward 49. No index greater than 49 is probed.

When a zero marker is found, the function performs an additional read of the global table base. It uses this newly evaluated base and the same candidate index to construct the record destination. It does not simply retain the address used for the successful probe, and it does not check the marker at the newly constructed destination.

This distinction constrains the selection guarantee:

- With an unchanged base and unchanged relevant markers, the lowest available candidate in the searched range is selected.
- If the base changes between probes, different indices may be inspected relative to different bases.
- If the base changes between the successful probe and destination construction, the writes may target a record whose marker was not observed as zero.
- Even if the base is unchanged, an intervening change to a marker can invalidate the assumption that the destination remains available.

These statements describe the supplied access sequence, not a guarantee about how concurrent execution, compilers, or hardware expose such changes.

At the representation level, finding the first zero marker at index \(k\) entails \(k+1\) marker reads and \(k+2\) global-base evaluations: one for each probe and one for destination construction. A zero at index 0 therefore entails two base evaluations. A zero at index 49 entails 51. Exhaustion entails 50 base evaluations and 50 marker reads, with no successful destination-construction step.

The index increments and multiplication by 16 remain within small 32-bit values: the index reaches at most 50, and the largest probed offset is 784. This does not establish that adding an offset to an arbitrary base is valid or cannot overflow an address representation.

### Record and output writes

Once a destination is constructed, the function writes four separate 32-bit fields in this order:

1. First value at relative offset 0.
2. Second value at relative offset 4.
3. Third value at relative offset 8.
4. Fourth value at relative offset 12.

These stores use the constructed destination. No further global-base evaluation is shown for these four writes.

The marker is written first, with a nonzero value, before the remaining fields. The function therefore does not provide an atomic record publication operation. The explicit sequence permits a partially updated record to have a nonzero marker; no hardware visibility or inter-thread ordering guarantee is established.

After the four record stores, the optional index destination is checked. If non-null, it receives the selected index as one unsigned 32-bit store. If null, that store is omitted.

The function then returns zero. Successful completion does not establish that the record was still free when written, that the original probed address was used, or that the output did not overwrite part of the record.

### Search exhaustion

If all 50 probes read nonzero markers, the index reaches 50 and the record destination remains null.

The first value is still nonzero, so execution proceeds toward the record stores. The first attempted store is the first value through that null destination.

Index 50 is not a selected candidate index. There is no ordinary successful path selecting an additional candidate, and no guaranteed output store of 50.

This behavior concerns 50 nonzero probe results. With a changing global base, those results need not describe one fixed table.

The alternative `0xFFFFFF94` return is therefore not reachable through ordinary execution of the shown control flow. It must not be treated as a recovery path for exhaustion.

## Side effects

### Direct memory effects

On an ordinary successful invocation with stable storage and no relevant overlap, the function:

- Reads the global base for each probe and once more for destination construction.
- Reads each visited candidate’s first field.
- Writes four fields at the constructed destination.
- Optionally writes the selected index to caller-provided storage.

It does not read the destination’s other fields before overwriting them. No separate count update, clearing operation, compaction, allocation, or release is shown.

These are direct-access descriptions. Aliasing can make a record or output store affect storage with another role, including global state.

### Output overlap and partial completion

No overlap check is performed. The optional index store occurs after all four record stores.

If it aliases one of the destination fields, it replaces that field with the selected index. For example, when index 0 is selected and the output aliases the destination marker, the final store replaces the nonzero first value with zero. The function can return success while leaving that record available according to its own marker criterion.

An output destination may also overlap another candidate or other shared storage. Such effects are not rejected or repaired.

No rollback is shown. If a later record store fails, earlier stores may already have completed. If a non-null output destination is invalid, all four record stores may have completed before the output access fails.

### Ownership and lifetime

The function uses pre-existing storage. No allocation, deallocation, ownership transfer, reference counting, or lifetime extension is shown.

The four inputs are stored as integer values. If callers interpret any as encoded addresses or resource handles, this function does not establish ownership or release obligations for those resources.

The optional destination is not retained in any explicit persistent state. This does not rule out indirect effects when that destination overlaps other storage.

### Synchronization and stability requirements

No lock, atomic reservation, retry, or synchronization operation is shown.

For the ordinary interpretation “write the first free record in one table,” callers need more than valid storage: the base must remain unchanged across probing and destination construction, and relevant markers must not change in a way that invalidates selection.
