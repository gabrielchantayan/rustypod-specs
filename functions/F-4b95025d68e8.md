# F-4b95025d68e8

## Purpose

F-4b95025d68e8 conditionally removes a selected node from a linked, color-tagged binary tree, repairs selected structural and tag relationships, passes the removed node’s payload address to a dependency, and places the removed node on a container-maintained chain.

The layout and repair cases are consistent with red-black-tree erasure. That is inferred intent, not an established guarantee that arbitrary inputs produce a valid red-black tree.

The function has no explicit status return. It writes one 32-bit word through its output argument. A dependency-controlled bypass produces a freshly read header address; the removal path produces the current contents of a local result cell exposed to dependencies.

## Interface

### Arguments and widths

| Argument | Established use |
|---|---|
| Output location | Address receiving one 32-bit result word |
| Container address | 32-bit address of the container described below |
| Selection location | Address of a readable 32-bit word containing the selected-node address |

The represented address model is 32-bit. Structural addresses and links occupy four bytes; tags occupy one byte. A native 64-bit pointer layout is not covered without adaptation.

The selection word is read before the initial dependency call and again after the second dependency call. The first read does not permanently determine the removal target.

### Container layout

| Byte offset | Width | Observed role |
|---|---:|---|
| +4 | 32 bits | Head of the chain receiving the removed node |
| +16 | 32 bits | Header address |
| +20 | 32 bits | Count decremented after payload processing |

No meaning is established for other container fields.

### Header and node layouts

| Byte offset | Width | Ordinary node | Header |
|---|---:|---|---|
| +0 | 8 bits | Tag | Not assigned a general meaning |
| +4 | 32 bits | Parent address | Root address |
| +8 | 32 bits | Left-child address | Cached minimum address |
| +12 | 32 bits | Right-child address | Cached maximum address |
| +16 | Unspecified | Payload begins | Not established |

The removed node’s +12 field is repurposed as a chain link.

Tag 0 behaves like red and tag 1 like black in the repair logic. Those names describe inferred intent. Some decisions test for exactly 1; the initial repair gate instead tests for any nonzero tag. Other tag values are neither rejected nor globally normalized.

### Preconditions for normal completion

All accessed storage must support the reads and writes described here. Traversals must terminate, and dependencies must return with enough accessible state for subsequent operations.

There is no visible validation of:

- Node membership, ordering, or parent-child consistency.
- Null or otherwise invalid selected addresses.
- Cycles or malformed traversals.
- Count consistency.
- Tag validity.
- Argument aliasing or concurrent mutation.

Descriptions such as “parent,” “successor,” and “minimum” identify structural roles. They do not supply missing validation guarantees.

## Behavior

### Initial decision and result preparation

The function first reads the selection word into a local 32-bit result cell, then reads the container’s header word into another local 32-bit cell. It passes the addresses of both cells to F-e1c8edf49b9a.

If that dependency returns nonzero, the function:

1. Reads the container’s header word again.
2. Replaces the result cell with this fresh value.
3. Writes that value to the output location.
4. Returns.

This branch does not execute the function’s visible removal, repair, payload-processing, chain-insertion, or count-decrement operations. Side effects performed by the dependency remain possible.

If the dependency returns zero, the function calls F-4193c824164f with the result-cell address. After that call returns, it rereads the selection word and uses the new value as the structural target.

The visible body makes no subsequent direct assignment to the result cell on the removal path. The final output is that cell’s current contents. Neither successor semantics nor preservation against dependency side effects is established. Mutation of the separate local header cell has no direct subsequent use in the visible body.

### Structural removal: no children

The function reads the target’s left child first. If it is null, it examines the right child. When both are null, the target’s parent becomes the initial repair anchor.

If that parent equals the container’s current header address, the structural writes occur in this order:

1. Header maximum receives the parent/header address.
2. Header minimum receives the same address.
3. Header root receives zero.

Otherwise, the function reads the parent’s left link:

- If it equals the target, the parent’s left link is cleared.
- Otherwise, the parent’s right link is cleared, without a separate membership check.

Each clearing operation consists of four zero-byte writes in increasing byte-offset order, not one represented word write.

The function then chooses one header cache: minimum for the left-link case, maximum otherwise. It replaces that cache with the parent only if the cache currently equals the target. It does not update the other cache on this branch.

### Structural removal: exactly one child

The non-null child becomes both the replacement and the initial repair anchor.

The function first copies the target’s parent word into the replacement’s parent field. It then redirects the structural incoming link:

- If the current header root equals the target, the root receives the replacement.
- Otherwise, the target parent’s left link is redirected if it equals the target; failing that test, the parent’s right link is redirected.

The cached minimum is checked before the cached maximum. Each is updated only if it currently equals the target.

For a minimum update:

- If the target’s right child is null at the relevant read, the new minimum is the target’s parent.
- Otherwise, the function follows left links from the replacement until reaching a node with no left child.

For a maximum update:

- If the target’s left child is null at the relevant read, the new maximum is the target’s parent.
- Otherwise, the function follows right links from the replacement until reaching a node with no right child.

These are conditional cache repairs, not an unconditional recomputation of both extremes.

### Structural removal: two children

When both children are non-null, the function follows left links from the target’s right child to obtain that subtree’s leftmost node. This is the structural successor. The successor’s right child, possibly null, is its replacement at the successor’s old position.

The successor moves into the target’s position. The original target remains the node later passed to payload processing and inserted into the chain. No payload copying is visible.

The structural and tag writes proceed in this order:

1. The target’s left child receives the successor as its parent.
2. The successor receives the target’s left-child link.
3. If the successor is the target’s immediate right child, its non-null replacement receives the successor as parent.
4. Otherwise:
   - A non-null replacement receives the successor’s former parent.
   - The successor’s former parent receives the replacement in its left link.
   - The successor receives the target’s right-child link.
   - That right child receives the successor as parent.
5. The header root, or the target parent’s selected child link, receives the successor.
6. The successor receives the target’s parent.
7. The successor’s original tag is retained temporarily; the successor receives the target’s tag; the target receives the successor’s original tag.

There is no explicit extreme-cache update in this branch.

The initial repair anchor is the successor replacement when non-null. When the replacement is null, the successor itself becomes the anchor. The removed target’s post-exchange tag controls the initial repair gate.

### Repair entry and iteration

Repair is skipped when the initial anchor equals the current header address. Otherwise, repair is entered only if the removed node’s tag is nonzero.

Thus, an initial tag of 2 enters repair just as tag 1 does; this does not imply identical behavior within repair.

At each iteration, the function first compares the anchor with the current header root. If they are equal, it proceeds to the final anchor-tag write without first testing the anchor’s tag. Otherwise, an anchor tag other than exactly 1 also leads to that final write.

For an anchor whose tag is exactly 1 and which is not the root, the function reads its parent and compares the anchor with that parent’s left child:

- Equality selects the left-anchor case, whose sibling is the parent’s right child.
- Otherwise, the right-anchor case uses the parent’s left child as sibling.

The second case is selected without separately verifying that the parent’s right child equals the anchor.

“Inner child” below means the sibling child nearer the anchor; “outer child” means the other child.

### Null sibling, including after transformation

If the sibling is initially null, the function writes tag 0 to the current anchor, advances the anchor to the parent already read for that iteration, and repeats.

A sibling with tag 0 is first transformed as follows:

1. The sibling receives tag 1.
2. The anchor’s parent receives tag 0.
3. A structural dependency is called.
4. The function explicitly rereads the anchor’s parent.
5. It obtains the new sibling from that reloaded parent.

If this new sibling is null, the same null-sibling handling applies: the current anchor receives tag 0, and the next anchor is the **reloaded parent**.

This applies to both mirrored cases. The next anchor is not a retained sibling-tag value of zero. Invalid parent links introduced or exposed by a dependency remain possible under unknown dependency contracts, but the visible parent reload does not itself establish a stale-tag null-anchor hazard.

### Non-null sibling

A tag-0 sibling undergoes the transformation and reload described above before the remaining sibling tests. A nonzero sibling tag does not trigger that transformation.

The function examines the inner child and, when needed, the outer child. If both children are absent or have tag exactly 1:

1. The sibling receives tag 0.
2. The anchor advances to its parent, reread from the current anchor.
3. Repair repeats.

If that condition does not hold, the outer child is examined again. When it is absent or has tag exactly 1:

1. A non-null inner child receives tag 1.
2. The sibling receives tag 0.
3. The opposite structural dependency is called.
4. The anchor’s parent is reread to obtain a new sibling.

If this sibling reload produces null, the function proceeds directly to the final anchor-tag write. It does **not** take the null-sibling propagation path described above.

Otherwise, the final transformation is:

1. The sibling receives the current parent’s tag.
2. The current parent receives tag 1.
3. A non-null outer child receives tag 1.
4. A structural dependency is called.
5. Repair proceeds to the final anchor-tag write.

The dependency directions are mirrored between left-anchor and right-anchor cases.

### Final repair write

Every repair exit reaching the common completion point writes tag 1 to the current anchor.

This write is not performed when repair was skipped at its initial gate. In particular, entering repair and immediately recognizing the anchor as the root still performs the write.

### Payload processing, chain insertion, count, and output

After structural removal and any repair, the function:

1. Reads the container chain head at +4.
2. Writes that word into the removed target’s +12 field.
3. Calls F-8a5aadac202f with the address at target +16.
4. After return, writes the target address into the container chain head.
5. Reads the container count at +20, decrements it, and writes the result.
6. Writes the current result-cell word to the output location.

The chain-head snapshot precedes payload processing. The count read follows it. A payload dependency that changes the count therefore changes the value subsequently decremented.

The represented decrement is 32-bit and has no zero guard. At the word level, decrementing zero yields all one bits. Count signedness and a portable source-language overflow policy are not established.

## Side effects

Directly visible mutations include header links and caches, node links, one-byte tags, the removed target’s repurposed +12 field, container chain head and count, and the final output word. Dependencies may cause additional mutations.

No allocation or storage-release operation is directly visible. The receiving chain suggests reuse or deferred reclamation, but that ownership interpretation is inferred.

F-8a5aadac202f receives the payload address rather than the node base. Its destruction, release, and mutation semantics are unknown. After it returns, the function still publishes the removed node address as the chain head. Normal operation therefore requires dependency behavior compatible with that retained address; the call alone does not prove that storage is preserved.

There is no visible rollback or synchronization. Faults, non-returning dependencies, or invalid links can leave partial mutations.

The output write occurs last. If the output aliases a container or node field, it can overwrite an earlier mutation. Selection, container, and node aliasing can likewise affect later reads. The contract supplies no general non-aliasing or concurrency guarantee.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, referenced storage remains accessible and dependencies return normally.

1. **Fresh-header bypass.** If F-e1c8edf49b9a changes the container header word and returns nonzero, output is the newly read header word, not its earlier snapshot. The visible removal path does not run.

2. **Selection reread.** If either initial dependency changes the selection word through a reachable alias, the structural target is the selection value read after F-4193c824164f returns.

3. **Single-node tree.** For a childless target whose parent is the header, structural writes set maximum and minimum to the header, then root to null. The initial anchor is the header, so repair is skipped.

4. **Childless left-side removal.** If a non-header parent’s left link equals the target, that link is cleared by four ascending zero-byte writes. The minimum cache changes to the parent only if it equals the target.

5. **Original target retained.** In a two-child removal, the successor takes the target’s structural position. F-8a5aadac202f receives the original target’s payload address, and the original target is placed on the chain.

6. **No successor replacement.** If the successor has no right child, the initial repair anchor is the successor itself, not null. Repair remains conditional on the initial gate.

7. **Initially null sibling.** For a non-root anchor tagged 1 whose selected sibling is null, the anchor receives tag 0 and repair advances to its parent. This holds on either mirrored path.

8. **Null sibling after tag-0 transformation.** Suppose a tag-0 sibling is recolored and the corresponding structural dependency returns. If the anchor’s reread parent is a particular accessible node and that parent’s selected sibling link is null, the current anchor receives tag 0 and repair continues with that reread parent. It does not continue with numeric zero merely because the former sibling tag was zero.

9. **Null after inner-child transformation.** If the sibling reload after the inner-child transformation is null, repair finishes by tagging the current anchor 1 rather than advancing it through the null-sibling path.

10. **Payload call ordering.** F-8a5aadac202f observes the target’s +12 field after it receives the earlier chain head. The function publishes the target as the new container head only after the call returns.

11. **Count mutation and underflow.** If payload processing leaves count 9, the decrement stores 8. If it leaves count zero, the represented 32-bit decrement produces all one bits. These outcomes assume no aliasing overwrite changes the relevant storage before the decrement.
