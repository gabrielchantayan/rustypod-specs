# F-12dea72fc587

## Purpose

F-12dea72fc587 conditionally removes a node from a pointer-linked structure, adjusts links and one-byte tags, places the removed node at the head of a container-maintained chain, decrements a count-like field, and writes a prepared position value to an output slot.

The observed layout and operations are consistent with a red-black tree having a header, cached extrema, and a removed-node reuse chain. These are inferred roles. They do not establish key ordering, dependency semantics, or equivalence to a conventional tree-deletion algorithm.

This contract describes static evidence only. No runtime tests have been performed.

## Behavior

### Initial decision and position preparation

The function first reads the position slot into one temporary and then reads container +16 into another. It calls F-425cd6ff9d42 with the addresses of these temporaries.

A nonzero result selects the skip path:

- Container +16 is read again after the call.
- That newly read header address becomes the output value.
- Direct removal, repair, chain insertion, and count decrement are skipped.
- The output slot is written before return.

The dependency may itself have changed memory. Consequently, this path does not guarantee an unchanged container.

A zero result selects removal:

- F-d92e879159c4 receives the address of the position temporary.
- After that call, the original position slot is read again.
- This re-read value identifies the target node.
- On normal completion, the then-held position temporary is written to the output slot.

The removal target and prepared output therefore come from different storage after the calls. Successor-position semantics are plausible but not established.

### Selecting the structural case

The target’s left-child field is read first.

- If it is zero, the right-child field determines whether the target is a leaf or has one child.
- If the left child is nonzero, the right-child field distinguishes one child from two.
- With two children, traversal starts at the right child and follows left-child links until a node with a zero left-child field is found.

For a one-child target, its child becomes the repair working node.

For a leaf, its parent becomes the repair working node.

For a two-child target, the selected node’s original right child becomes the working node when nonzero. Otherwise, the selected node itself becomes the working node.

The original target remains the node ultimately added to the removed-node chain. No key comparison or payload copy is visible.

### Leaf removal

The function reads the target’s parent and compares it with the current header address.

If they match, the following stores occur in order:

1. Header +12 receives the header address.
2. Header +8 receives the header address.
3. Header +4 receives zero.

This is the explicitly represented empty-tree transition.

Otherwise, the parent’s left-child field is read to determine whether it names the target. The selected child link is cleared through four separate 8-bit zero stores in increasing address order:

- Offsets +8 through +11 when the left link matches.
- Offsets +12 through +15 otherwise.

The corresponding header cache is then examined: +8 for the left-link case, +12 otherwise. It is replaced with the parent address only if it equals the target.

The parent remains the working node. The body does not introduce a separate null-child placeholder.

### One-child removal

The replacement child’s parent field first receives the target’s parent.

Next, the function examines the current header’s root field:

- If it names the target, it receives the replacement.
- Otherwise, the target parent’s left link is tested. A matching left link is replaced; otherwise, the right link is replaced.

Cached extrema are handled afterward, lower before upper:

- If header +8 names the target, the target’s right-child field is examined. A zero value causes the cache to receive the target’s parent. Otherwise, F-c5e056907a6d is called with the replacement, and its returned 32-bit value is stored in the current header’s +8 field.
- If header +12 names the target, the target’s left-child field is examined. A zero value causes the cache to receive the target’s parent. Otherwise, F-da8d15161b11 is called with the replacement, and its returned 32-bit value is stored in the current header’s +12 field.

The destination header is read after each lookup call. The function does not establish that a dependency preserves container +16, target fields, or other memory used by subsequent operations.

### Two-child removal

The selected node is structurally moved into the target’s position.

First:

1. The target’s left child receives the selected node as its parent.
2. The selected node’s left-child field receives the target’s left-child address.

If the selected node is the target’s immediate right child, its nonzero right child receives the selected node as parent.

Otherwise:

1. The selected node’s nonzero right child receives the selected node’s former parent.
2. The former parent’s left-child field receives that right-child address, including zero.
3. The selected node’s right-child field receives the target’s right subtree.
4. That subtree’s root receives the selected node as parent.

The target’s root or parent-child link is then replaced with the selected node. The selected node receives the target’s parent address.

Finally, the selected node’s original 8-bit tag is saved, the selected node receives the target’s tag, and the target receives the saved tag. If the selected node’s original right child was zero, the selected node is used as the working node.

Only tags are exchanged. The visible branch does not directly update the cached extrema or copy payloads.

### Repair entry and completion

Repair is entered only when:

- The working node differs from the currently read header address; and
- The removed target’s current tag is nonzero.

The target tag is not read for this gate when the working node equals the header. For two-child removal, the tested target tag is the tag transferred from the selected node.

**Skipping repair performs no repair-completion tag store.** Earlier structural operations may nevertheless have changed tags.

Once repair is entered, every normal exit reaching repair completion performs the same operation: **the current working node’s tag receives the 8-bit value 1**. This includes:

- Exit because the working node equals the current root.
- Exit because its tag is not exactly 1.
- Exit after an inner-child preparation dependency returns and the re-read sibling is null.
- Exit after a final restructuring dependency returns.

The completion store occurs after the relevant dependency call and before removed-node chain insertion. It is not merely an initial recoloring or an assumption that a dependency preserves the tag.

The current working node can differ from the node with which repair began because repair may move upward.

### Repair decisions and restructuring

At each iteration, the current root is checked first. If it equals the working node, repair completes without first reading the working node’s tag for the loop condition. Otherwise, iteration continues only if that tag equals exactly 1.

The parent is read, then its left-child field determines the working node’s side. The opposite child is the sibling.

For a left-side working node, the sibling’s left child is the inner child and its right child is the outer child. These roles are reversed for a right-side working node.

The observed cases are:

- **Sibling absent:** The working node receives tag 0. The working position moves to the parent, and the loop conditions are checked again.
- **Sibling tag 0:** The sibling receives tag 1, the parent receives tag 0, and a structural dependency is called. The working node’s parent and sibling are then re-read. A now-absent sibling takes the absent-sibling path.
- **Both sibling children absent or tagged exactly 1:** The sibling receives tag 0. The working position moves to the working node’s parent, and iteration resumes.
- **Outer child absent or tagged exactly 1, without the preceding both-child condition:** A nonzero inner child receives tag 1, the sibling receives tag 0, and an inner-child preparation dependency is called. The sibling is re-read through the working node’s current parent. If it is null, repair completes, including the working-node tag store of 1.
- **Final restructuring:** The sibling receives the current parent’s tag, the parent receives tag 1, and a nonzero outer child receives tag 1. A structural dependency is called. After it returns, repair completes by writing 1 to the working node’s tag.

For a left-side working node, F-80308ed22950 is used for the tag-0-sibling and final restructuring cases; F-263390bbe2c8 is used for inner-child preparation. For a right-side working node, these dependency roles are reversed.

The tag-0-sibling and final calls visibly include a parent argument. Inner-child preparation calls visibly expose only the container argument. Their complete argument requirements remain unresolved.

Tag 0 behaves like a red color and tag 1 like a black color, but this is interpretation. The entry test accepts any nonzero removed-target tag, whereas the loop and child tests distinguish exactly 1. Arbitrary nonzero tags must not be treated as interchangeable.

### Chain insertion, count, and output

After structural work and any entered repair has completed:

1. Container +4 is read and stored in the original target’s +12 field.
2. The original target address is stored in container +4.
3. Container +20 is read, decremented by one, and written back.
4. The prepared 32-bit position value is written to the output slot.

The removed target becomes the chain head. Its +12 field now carries the former chain head rather than an active-tree right-child link.

The count operation is represented as signed 32-bit addition of −1. No zero or lower-bound check is visible. Zero becomes −1 without signed overflow; behavior at the minimum signed value is unresolved.

## Side effects

Direct writes can affect header metadata, parent and child links, node tags, the removed target’s chain link, the container chain head and count, and the output slot.

Repair completion adds a required 8-bit tag write on every normally completing entered-repair path. On dependency-mediated completion paths, this store occurs after the dependency returns, even if that dependency changed the working node’s tag.

The leaf unlink’s four byte stores are distinct from the 32-bit link stores elsewhere. No atomicity, synchronization, concurrent-reader safety, or transactional behavior is established.

No explicit allocation, deallocation, payload destruction, logging, or error reporting appears in the body. Chain insertion suggests reuse or deferred reclamation but does not establish ownership transfer or eventual release. Dependencies may affect ownership or memory lifetime. Continued execution requires subsequently accessed storage to remain valid.

The final output write may overwrite other state if the output slot aliases it. It does not retroactively change which earlier removal or repair operations occurred.

## Acceptance examples

These are prospective, conditional criteria, not executed tests. Unless an example states otherwise, relevant storage is valid, fields do not alias, and dependencies have no additional effects.

### Skip path observes the post-call header

If F-425cd6ff9d42 returns nonzero after changing container +16, the output must contain the new header address. The visible body performs no removal, chain insertion, count decrement, or repair-completion store.

### Single-node removal

For a childless target whose parent is the header, with removal permitted:

- Header +12 and then +8 receive the header address.
- Header +4 receives zero.
- Repair is skipped because the working node equals the header.
- No repair-completion tag store occurs.
- The target becomes chain head, a count of 1 becomes 0, and the prepared position is output.

The target’s parent need not be cleared.

### Leaf without entered repair

For a non-root leaf tagged 0, the matching parent link is cleared through four byte stores. The corresponding extreme cache changes only if it names the target. Repair is skipped; chain insertion and decrement still occur.

### One-child root replacement

For a root with exactly one child, the child’s parent is written before header +4 receives the child. Applicable cache handling follows. If repair is entered and immediately completes because the child is now the root, the child’s tag receives 1.

### Two-child identity preservation

For a two-child target with a terminating leftward traversal in its right subtree, the selected node takes the target’s structural position. The original target—not the selected node—becomes chain head. Only the two tag bytes are exchanged; payload copying is not part of the visible behavior.

### Completion after final restructuring

Suppose entered repair reaches final restructuring and the dependency returns with the current working node’s tag changed to 0, while leaving its storage valid. The function must subsequently write 1 to that tag before chain insertion. A pre-call tag value of 1 is not sufficient acceptance evidence.

### Completion after preparation yields no sibling

Suppose an inner-child preparation call returns and the sibling re-read yields zero. Repair completes without final restructuring, but still writes 1 to the current working node’s tag before chain insertion. This path is not equivalent to skipping repair.

### Prepared output differs from the target

If F-d92e879159c4 changes only the position temporary, removal uses the original slot’s re-read value while output uses the changed temporary. The two values may differ.

### Count starts at zero

An otherwise executable removal with count zero is not visibly rejected. The count becomes −1. Nonnegative counts are a caller-maintained invariant, not a checked condition.
