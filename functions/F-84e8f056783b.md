# F-84e8f056783b

## Purpose

F-84e8f056783b conditionally transfers nodes from two endpoint-controlled positions onto a separate forward-linked chain. It first attempts transfers from the first endpoint, then may attempt transfers from the second endpoint. F-de83b823984c supplies a separate zero-versus-nonzero decision for each eligible attempt.

The established behavior is a sequence of address reads and 32-bit field writes. Interpreting the structure as a doubly linked live list plus a detached-node chain is **inferred intent**. That interpretation requires structural and noninterference assumptions; the function does not validate them.

The function returns no value. Its direct outputs are mutations of the control record and addressed node fields.

## Interface

The sole explicit input is the address of a control record containing at least these fields:

| Byte offset | Width | Contract name | Role |
|---|---:|---|---|
| 0 | 32 bits | First endpoint | Starting address for first-phase traversal |
| 4 | 32 bits | Second endpoint | Starting address for second-phase traversal |
| 8 | 32 bits | Detached-chain head | Value installed into each transferred node’s forward field before that node is published as head |

These names describe observed roles, not established application-level types.

All three fields contain 32-bit values used as addresses. The supplied representation does not establish a layout using wider native pointers. Substituting native-width fields would change the observed offsets and access widths.

### Node fields

| Byte offset from a node address | Width | Contract name | Uses |
|---|---:|---|---|

An accessed field must have four accessible bytes at its specified offset. When both fields are accessed, the required extent reaches byte offset 315 inclusive. This is not evidence of the complete node size or payload layout.

No node payload field is directly accessed.

For ordinary defined operation:

- Address-plus-offset calculations must designate valid fields in the target execution environment.

There is no initial null-endpoint check. In particular, two zero endpoint values do not establish a supported empty-structure case: the function attempts to read the forward field through the first endpoint before comparing the endpoints.

The representation establishes 32-bit fields and fixed byte offsets. It does not establish portable behavior for overflowing address arithmetic, invalid integer-to-address conversions, misalignment, or inaccessible storage. No wraparound-based traversal or failure result should be inferred.

## Behavior

### Decision dependency

F-de83b823984c receives no explicit arguments. Its result is tested as a 32-bit integer:

- Zero declines the pending transfer.
- Any nonzero value permits it, including a negative value.

The sign and magnitude of a nonzero result have no additional local significance.

A call occurs only after the relevant endpoint’s link has been observed to be nonzero. Each eligible attempt gets its own call. A decision is not reused for another transfer or phase.

The dependency’s memory effects are unknown. The function rereads endpoint and link values after a permitting result rather than committing to the address examined before the call.

### First phase

The function reads the first endpoint and then that node’s forward link.

If the forward link is zero, the first phase ends without a dependency call for that attempt. If it is nonzero, the function calls F-de83b823984c. A zero result ends the first phase without this function performing the pending transfer’s writes.

After a nonzero result, the function reads the first endpoint again and retains that address for the current transfer. The following effects occur in order:

1. The retained node’s forward link is read. The backward field of the node designated by that value is set to 32-bit zero.
2. The control record’s first endpoint is read afresh, followed by its forward link. That link value is written into the first-endpoint field.
3. The then-current detached-chain head is read and written into the retained node’s forward field.
4. The retained node’s address is written into the detached-chain-head field.

The phase then repeats its eligibility check.

The endpoint retained after the dependency call need not be the endpoint examined before the call. Nor is the previously examined forward link saved for the transfer. A dependency mutation can therefore change the selected node or invalidate the preliminary eligibility condition. There is no second explicit nonzero-link check before the transfer writes.

The fresh endpoint and link reads within the update also matter when storage overlaps. The boundary-clearing write can affect what later reads observe. Replacing these reads with previously saved values would require additional assumptions.

Under consistent-list and noninterference assumptions, a completed first-phase transfer removes the old first node, makes its successor the first endpoint, clears that successor’s backward link, and links the removed node onto the detached chain.

This phase does not explicitly write the retained node’s backward field. In a conventional valid list, the old first node already has a zero backward link.

### Phase transition

After the first phase ends, the function compares the current endpoint values.

- Equal endpoint values cause return.
- Different endpoint values cause entry into the second phase.

When the values are equal, the function does not inspect the second endpoint’s backward link.

A zero decision in the first phase stops only that phase. It can be followed by second-phase dependency calls and transfers.

Endpoint equality is tested at this transition, not before each second-phase iteration.

### Second phase

The function reads the second endpoint and then that node’s backward link.

A zero backward link causes immediate return without a dependency call for that attempt. A nonzero link causes a call to F-de83b823984c. A zero result causes return without this function performing the pending transfer’s writes.

After a nonzero result, the function rereads the second endpoint and retains that address. The effects occur in this order:

1. The retained node’s backward link is read. The forward field of the node designated by that value is set to 32-bit zero.
2. The control record’s second endpoint is read afresh, followed by its backward link. That value is written into the second-endpoint field.
3. The then-current detached-chain head is read and written into the retained node’s forward field.
4. The retained node’s address is written into the detached-chain-head field.

The phase repeats until its link check or a zero decision causes return.

Under conventional list assumptions, this removes the old last node, makes its predecessor the second endpoint, and clears that predecessor’s forward link.

The retained node’s backward field is not explicitly changed by this phase. It can retain a reference into the live structure. Consequently, the function does not construct a clean doubly linked detached list.

### Chain ordering and retained nodes

The unconditional local linking behavior is limited to the ordered assignments: each completed transfer writes the then-current detached-chain-head value into the retained node’s forward field, then writes the retained node’s address into the head field.

This does **not**, by itself, guarantee a persistent reverse-chronological chain. F-de83b823984c can replace the head or alter previously linked nodes between transfers. Overlapping storage can cause one write to alter another relevant field, including a field written earlier in the same transfer.

A reverse-chronological chain followed by the original detached chain is guaranteed only when:

- The original detached chain has the intended valid forward-linked structure.
- Its nodes and the transferred nodes are appropriately disjoint.
- Control fields and node fields do not overlap in ways that interfere with these operations.
- Dependency calls and concurrent actors preserve the head and relevant links except for this function’s specified writes.

Under those assumptions, each transfer prepends one node, so the final detached order reverses the chronological transfer order and then reaches the original chain. All first-phase transfers precede all second-phase transfers.

For a finite consistent live list with noninterfering execution, at least one live node remains. With continuously permitting decisions, the first phase reaches the last node, observes its zero forward link, and returns through endpoint equality. With earlier first-phase rejection, second-phase traversal stops at a zero backward link or a rejecting decision. This retained-node property is conditional, not a guarantee for malformed or externally mutated structures.

## Side effects

### Direct writes

The function’s explicit writes target:

- The first-endpoint field during first-phase transfers.
- The second-endpoint field during second-phase transfers.
- The detached-chain-head field during every transfer.
- A successor’s backward field during first-phase transfers.
- A predecessor’s forward field during second-phase transfers.
- The retained node’s forward field during every transfer.

All writes are 32 bits wide. Boundary-clearing writes store zero.

This list identifies the fields targeted by the operations. With overlapping storage, an operation can also change another logical field represented by the same bytes.

A transfer is not atomic: boundary clearing precedes endpoint replacement, which precedes detached-link installation and head publication. No explicit synchronization or rollback operation appears. Intermediate memory states can matter to later reads or to an external observer.

### Ownership and lifetime

The body contains no direct allocation, deallocation, destruction, or payload cleanup operation. Transferring a node does not establish that its storage has been released.

The detached chain may support deferred processing or reuse, but that is **inferred intent**. Ownership transfer, reclamation duties, and valid node lifetimes remain **documented_only**.

F-de83b823984c’s effects are not constrained by this body. In particular, this contract does not assume that it preserves globals, retains storage, avoids allocation or release, or leaves the detached chain unchanged.

### Failures and termination

There is no explicit validation, error status, recovery path, or rollback.

Invalid storage, dependency-driven invalidation, and inconsistent links can cause invalid accesses or other behavior outside the ordinary-operation preconditions. No portable failure outcome is established.

There is no iteration limit. Cycles, repeated structural mutation, or a dependency that does not return can prevent completion.

## Acceptance examples

Except where explicitly changed, these examples assume a valid finite doubly linked live list, distinct nonoverlapping storage, a valid detached chain initially headed by Q, no concurrent interference, and dependency calls that alter no relevant memory. Node labels denote addresses. These are conditional expectations, not reported executions.

### Singleton

A is both endpoints, with zero forward and backward links.

Expected:

- No dependency call.
- No direct writes.
- Both endpoints and the detached-chain head remain unchanged.

### Repeated first-phase transfers

The live order is A–B–C. Decisions are nonzero, then nonzero.

Expected:

- A transfers first, then B.
- C becomes both endpoints and has zero backward link.
- The detached forward chain becomes B → A → Q.
- There is no third call: C has no forward successor, and the endpoint comparison succeeds.

The chain-order expectation depends on the noninterference and nonoverlap assumptions stated above.

### First-phase rejection does not end the function

The live order is A–B–C. Decisions are zero, nonzero, zero.

Expected:

- The first phase leaves A in place.
- The second phase transfers C, then rejects transferring B.
- The live endpoints are A and B; B’s forward link is zero.
- The detached chain is C → Q.
- C’s backward field still refers to B.

### Transfers from both endpoints

The live order is A–B–C–D. Decisions are nonzero, zero, nonzero, zero.

Expected:

- A transfers during the first phase.
- The next first-phase attempt is rejected.
- D transfers during the second phase.
- The next second-phase attempt is rejected.
- B and C remain as endpoints, with B’s backward and C’s forward fields zero.
- The detached chain is D → A → Q.

### Negative decision

The live order is A–B. The first decision is a negative 32-bit value.

Expected: A transfers, B becomes both endpoints, and no second dependency call occurs. Nonzero, not positivity, controls permission.

### Dependency replaces the detached-chain head

The live order is A–B–C. The first call permits transfer without mutation, producing A → Q. During the second call, the dependency replaces the detached-chain head with R and returns nonzero. R heads a separate valid chain; all relevant storage remains valid and nonoverlapping.

Expected:

- B’s forward field receives R, not A.
- B becomes the detached-chain head.
- C becomes both live endpoints.
- The resulting detached chain begins B → R.
- A retains its link to Q unless otherwise modified, but is not necessarily reachable from the final detached-chain head.

This outcome satisfies the local linking behavior while disproving an unconditional guarantee that all transferred nodes remain chained in reverse chronological order.

### Dependency changes an endpoint

The first endpoint initially has a nonzero forward link. The dependency changes that endpoint and returns nonzero.

Expected: the transfer uses the reread endpoint, not necessarily the one that made the call eligible. A concrete final structure is **documented_only** without the dependency’s exact mutation and validity guarantees.
