# F-74565b2f85a5

## Purpose

F-74565b2f85a5 consumes encoded bytes from a stateful input object and writes decoded bytes into caller-provided storage. It invokes an initialization or positioning dependency first, then processes buffered input until the destination extent is complete, a recognized terminator is encountered, or an error occurs.

The established transformation differs from conventional hexadecimal decoding:

- Uppercase `A` through `F` contribute values 10 through 15.
- Lowercase `a` through `f` contribute values 0 through 5.
- A classification-table entry equal to exactly `0x20` overrides all explicit character rules.
- A recognized `>` contributes a zero-valued component before ending processing successfully.
- Input exhaustion is an error if another input byte is needed.

“Hexadecimal-like decoding” describes inferred intent, not an external format guarantee. The mappings, ordering, memory effects, and termination rules below define the behavior supported by the supplied static evidence.

## Interface

The function accepts four arguments and returns an integer status.

| Argument | Established role |
|---|---|
| Destination | Address of caller-provided writable byte storage. |
| Requested extent | Signed 32-bit integer added to the destination address to form an exclusive end address. |
| Initialization value | Opaque 32-bit value passed unchanged to F-e40a3ceddab2. |
| Context | Reference to an object containing an input-object reference at byte offset `0x68`. |

The supplied representation uses 32-bit integers and references, with 8-bit input, output, and classification-table elements. It does not establish a portable ABI, pointer-provenance model, or general signed-overflow policy.

The function reads the context’s input-object reference once, before initialization, and retains that reference throughout the invocation. Subsequent changes to the context field do not select a different input object.

A 32-bit input-object field at byte offset `0x04` participates in refill availability calculations. Its broader meaning and validity rules are unknown.

### Results

| Status | Meaning |
|---|---|
| `0` | Initialization succeeded, and processing stopped through destination completion, recognized termination, or an initially false destination-loop condition. |
| `0xA0` / 160 | A refill availability calculation produced zero, or an examined byte failed all applicable acceptance rules. |
| Nonzero result from F-e40a3ceddab2 | Returned unchanged. |
| Nonzero result from F-0c21b5cad025 | Returned unchanged. |

No output count, examined-input count, or termination-reason indicator is returned. A dependency status may numerically overlap `0xA0`; the result alone does not distinguish its origin.

### Preconditions

Useful, defined operation requires:

- A readable context field at offset `0x68`.
- An input-object reference valid for dependency calls and the field access at offset `0x04`.
- Destination storage sufficient for the requested positive extent.
- Valid destination-address addition and ordering comparisons.
- A classification dependency result that supports the reference and table accesses described below.
- Refill results that identify initialized bytes within the 256-byte local buffer.

These conditions are not explicitly validated. Dependencies may impose additional requirements that are not supplied here. Zero extent does not bypass context access or initialization.

## Behavior

### Initialization and destination bounds

The function first reads the input-object reference from the context, then calls F-e40a3ceddab2 with that reference and the initialization value.

A nonzero initialization result is returned immediately. The function has not directly accessed destination bytes at this point; effects performed by the dependency remain possible.

After successful initialization, the function computes the destination end address, starts in the first-component phase, and marks the input buffer as empty. Processing continues while the current destination address is below the computed end address.

For zero extent, the loop is initially skipped. Successful initialization therefore yields zero without refill or classification calls.

For negative extent, ordinary nonwrapping address arithmetic could place the end before the destination and skip the loop. The evidence does not establish valid pointer arithmetic or comparison for that case. Negative extents and address wraparound are not supported-use guarantees.

### Input refill

The function maintains a local 256-byte input buffer. At the start of an iteration, it refills when the current input position is at or beyond the recorded buffer end.

The observable refill order is:

1. Call F-b03b1199772e with the retained input-object reference and capture its reported position.
2. Read the input-object field at offset `0x04`.
3. Subtract the captured position from that field using the represented 32-bit arithmetic, and interpret the result as an unsigned available amount.
4. Return `0xA0` if that amount is zero.
5. Otherwise call F-0c21b5cad025 with the input object, local-buffer address, and the smaller of that amount and 256.
6. Return any nonzero read status immediately.
7. After a successful read, call F-b03b1199772e again.
8. Use the second position minus the first position as the new buffered extent, starting at the local-buffer beginning.

The requested read size is between 1 and 256 inclusive. The inferred buffered extent is separate: it comes from position advancement, not from a returned byte count.

The field read occurs after the first position call. Its value can therefore reflect changes made by that call. Likewise, the second position result is obtained after the read dependency returns.

No explicit negative-availability check exists. A negative mathematical field-minus-position difference can become a large unsigned amount and select a 256-byte request, subject to unresolved signed-overflow semantics.

The function does not validate that successful reading advanced the position positively or by at most 256 bytes. It also does not repeat the buffer-exhaustion check immediately after refill. Consequently, a zero or invalid inferred extent can still be followed by an attempted byte load from the buffer beginning. Stale, uninitialized, or out-of-bounds access is not converted into a specified error status.

### Per-byte classification and read order

For each examined byte, the function performs these operations in order:

1. Load the current buffered byte once and capture it as an unsigned value from 0 through 255.
2. Call F-2a4c402ba617.
3. Dereference the returned reference to obtain a table address.
4. Read the one-byte table entry indexed by the previously captured byte.
5. Apply classification and explicit character rules using that same captured byte.

The input byte is **not reloaded after F-2a4c402ba617 returns**. Both the table index and every explicit character comparison use the pre-call value.

This ordering matters even though dependency effects are unknown. If a classification call can modify the refill buffer—for example, through an address previously retained by another dependency—the current iteration still processes its captured byte. A modified byte at a later buffer position can affect a later iteration when that position is loaded. The table reference and entry, by contrast, are read after the classification call and can reflect changes made by it.

The selected table entry must equal exactly `0x20` to activate the classification rule. This is not a bit-presence test.

When the entry equals `0x20`, the component value is the low eight bits of the captured input byte minus `0x30`. This rule precedes every explicit character rule, including whitespace and termination.

Otherwise, the explicit rules are:

| Captured byte | Effect |
|---|---|
| `a` through `f` | Contribute 0 through 5. |
| `A` through `F` | Contribute 10 through 15. |
| Space, tab, carriage return, line feed, form feed, or NUL | Ignore without changing output phase. |
| `>` | Contribute zero, mark termination, and stop after applying the component. |
| Any other value | Return `0xA0`. |

The ignored values are exactly `0x20`, `0x09`, `0x0D`, `0x0A`, `0x0C`, and `0x00`. Vertical tab is not included.

ASCII digits have no independent acceptance branch. Their usual component values depend on table entries equal to exactly `0x20`.

### Destination construction

Accepted components alternate between first-component and second-component phases. Ignored input does not change phase.

In the first-component phase, the function overwrites the current destination byte with the low eight bits of the component shifted left by four. It does not read the old destination byte or advance the destination address.

In the second-component phase, the function reads the current destination byte, adds the component, stores the low eight bits of the sum, and advances the destination address by one byte.

The destination read in the second phase occurs after the classification call and table lookup. A dependency-induced modification of that destination byte can therefore affect the addition. The function does not preserve a separate copy of the first phase’s stored byte.

Each accepted component toggles phase. A completed pair ordinarily causes two writes to the same destination byte. The second operation is addition, not bitwise combination. Classification-derived components are not restricted to 0 through 15, so truncation and carries can affect the stored byte.

After a nonterminating accepted or ignored byte, the buffered-input position advances by one. An invalid byte returns before that local advancement. The local position is not exposed as a consumed-byte count and does not undo underlying read-ahead.

### Termination and completion

A recognized `>` applies a zero-valued component through the same output rules, then exits successfully:

- In the first-component phase, it overwrites the current destination byte with `0x00` without advancing the destination address.
- In the second-component phase, it reads and rewrites the current destination byte by adding zero, then advances the destination address.

The terminator’s local buffer position is not advanced after that application because processing exits immediately. This does not restore the underlying input position.

If destination completion stops the loop, no terminator is required and following input is not classified. A refill may already have fetched bytes beyond the last examined byte. The function neither returns those bytes to the input object nor rewinds it.

Errors preserve completed and partial writes. There is no rollback.

## Side effects

### Destination storage

The function writes directly into caller-provided storage. It does not explicitly allocate replacement storage, release the destination, or transfer its ownership.

It does not clear the destination in advance. Bytes it does not touch retain their contents unless dependencies or aliasing change them.

Success can leave only part of the requested extent touched. In particular, an immediate recognized terminator writes one zero byte when the loop is active, then succeeds.

### Input and other state

Initialization and refill dependencies can change input state. Batched reads of up to 256 bytes can advance the underlying position beyond the characters actually examined. No rollback occurs on success, errors, or termination.

The function explicitly uses a local 256-byte buffer and performs no explicit allocation or release operation. This does not establish allocation, retention, or ownership behavior for its dependencies.

F-0c21b5cad025 receives the local-buffer address. That storage has invocation-local lifetime. Whether any dependency retains or exposes the address is unknown; no safe post-return retention contract is established.

No guarantee is made that dependencies preserve globals, classification state, input-object fields, destination contents, or aliased memory. In particular, captured-byte behavior must not be confused with a guarantee that the buffer remains unchanged across classification calls.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid storage, successful dependencies, accurate positive refill progress within buffer bounds, no dependency-induced destination changes, table entries exactly `0x20` for ASCII digits, and nonmatching entries for other illustrated characters.

1. **Uppercase pair.** With extent one and input `AF`, the destination becomes `0xAF`; status is zero.

2. **Lowercase pair.** With extent one and input `af`, the destination becomes `0x05`, not `0xAF`.

3. **Ignored bytes preserve phase.** With extent one and input `A`, space, tab, NUL, then `F`, the destination becomes `0xAF`.

4. **Immediate terminator.** With extent two, initial bytes `0x77, 0x88`, and input beginning with `>`, the destination becomes `0x00, 0x88`; status is zero.

5. **Terminator after a first component.** Under the same initial storage, input beginning with `A>` leaves `0xA0, 0x88`; status is zero.

6. **Exhaustion after a first component.** With extent one and only `A` available, a subsequent zero availability calculation returns `0xA0`; the partial destination byte remains `0xA0`.

7. **Invalid input after partial output.** With extent one and input `AG`, where `G` is not classification-accepted, status is `0xA0` and the destination remains `0xA0`.

8. **Completion before invalid trailing input.** With extent one and input beginning `AFG`, output is `0xAF` and status is zero. `G` is not classified, although read-ahead may already have consumed it from the underlying object.

9. **Classification overrides lowercase handling.** With extent one, input `a0`, and the entry for `a` equal to `0x20`, its component is `0x31`. The shifted first write is `0x10`; the final output is `0x10`.

10. **Classification overrides termination.** With extent one, input `>0`, and the entry for `>` equal to `0x20`, `>` contributes `0x0E` rather than terminating. Output becomes `0xE0`.

11. **Captured byte survives an intervening buffer mutation.** Suppose the current buffered byte is `A`. After it is loaded, F-2a4c402ba617 changes that buffer location to `G`, while the returned table entry for `A` remains nonmatching. The current iteration still contributes 10 and, in the first phase, writes `0xA0`. It neither indexes by `G` nor rejects the iteration as `G`.

12. **Later bytes are not captured early.** Suppose a buffer contains `AF`. During classification of the already captured `A`, a dependency changes the next buffered byte from `F` to `G`. If `G` is not classification-accepted and no other mutation intervenes, the next iteration rejects it. The partial `0xA0` remains.

13. **Zero extent still initializes.** Context access and initialization occur. Successful initialization returns zero without refill or classification; a nonzero initialization status propagates instead.

## Uncertainties

The following remain **documented_only**:

- The actual classification table and intended meaning of entry value `0x20`.
- Whether the lowercase mapping is intentional.
- Position units, ranges, failure representation, and arithmetic-overflow behavior.
- Successful-read progress and initialization guarantees.
- Behavior outside valid buffer extents or destination-address ranges.
- Dependency effects on globals, aliasing, object lifetimes, allocation, release, and retained addresses.
- Whether a classification call can actually reach the refill buffer; the captured-byte ordering is established regardless.
- Thread safety, reentrancy, and classification-state stability.
- Broader caller requirements, including whether a terminator is expected.

The function does not enforce or resolve these external contracts.

## Evidence

Established static evidence includes the argument uses, 32-bit field operations, object offsets, dependency-call order, 256-byte buffer, exact table-entry comparison, character mappings, byte-width destination stores, status propagation, and stopping conditions.

The buffered-byte load precedes F-2a4c402ba617. The returned reference is dereferenced afterward, and the captured unsigned byte supplies both the table index and explicit character decisions. There is no intervening reload of the current buffered byte.

Inferred intent is limited to buffered hexadecimal-like decoding with an initialization or positioning step. That interpretation does not override the observed mappings, classification precedence, partial writes, or read-ahead behavior.

No runtime tests have been performed. Acceptance examples are deductions from the supplied static evidence under their stated conditions.
