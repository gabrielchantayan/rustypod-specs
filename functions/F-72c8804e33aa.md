# F-72c8804e33aa

## Purpose

F-72c8804e33aa writes initial count and selector information into a caller-supplied record, conditionally clears its child-storage fields, and attempts to construct children in order. It stops at the first child that fails selector-dependent field checks, then reports the preceding accepted-child count through the record and the caller’s count location.

Under stable, non-overlapping input storage and dependencies that preserve the destination count, the population path attempts at most nine children. **Nine is not an unconditional bound:** entry is controlled by a read of the caller’s count, while construction is controlled by repeated signed reads of the destination count. Overlap or dependency-induced changes can separate those values.

After an admitted population attempt, the function invokes two final dependencies, including when no children were attempted or a child was rejected. An entry count of ten or greater skips population and both final dependencies, but not the initial record writes.

This contract describes visible behavior. It does not establish that the resulting record is valid, that rejected children are released, or that dependencies preserve unrelated state.

### Access and validity requirements

The destination and caller-count storage must support the accesses actually taken. No null, alignment, overlap, or size validation is visible.

For each attempted child, the address returned by F-53d23e2c87a5 must support these conditional 32-bit reads if execution is to continue normally:

- Offset 0x74 is always read after the child address is stored.
- If 0x74 is nonzero and the first validation selector observation is zero, offset 0x7C is read.
- On that selector-zero path, offset 0x80 is read only if 0x7C is nonzero.
- If 0x74 is nonzero, the first validation selector observation is nonzero, and the subsequent selector observation is one, offset 0x78 is read.
- Other selector values impose no additional child-field read in the visible body.

Each listed field occupies four bytes. Thus the field at 0x80 extends through byte 0x83. Readability through that byte is a sufficient maximum envelope for the explicit validation fields, **not a necessary condition for every accepted child**. An accepted child on an ordinary selector-other-than-zero-or-one path only needs the explicit validation field at 0x74 to be readable.

If rejection reaches indirect cleanup with a nonzero current slot, the returned object’s first 32-bit word and the dispatch entry at offset 0x0C from the table address held there must also be readable. The indirect dependency may impose additional requirements not supplied here.

Dependencies may require more storage than these visible accesses establish.

## Behavior

### Initial writes and entry decision

The visible sequence is:

1. Read the caller’s count and write it to destination offset 0x00.
2. Read the caller’s count again and write it to destination offset 0x04.
3. Write the supplied selector byte to destination offset 0x08.
4. Read the caller’s count again and compare it with ten as an unsigned 32-bit value.

These are distinct source-level reads. There is no single captured count used for all three purposes. Overlap can make an earlier destination write affect a later caller-count read. Concurrent access behavior and atomicity are not established.

If the comparison value is ten or greater, execution proceeds to the return without:

- Consulting external default storage.
- Clearing child slots or auxiliary bytes.
- Calling either child-construction dependency.
- Calling either final dependency.

The initial writes have already occurred. A large request is therefore neither a no-op nor an explicitly reported error.

### Effective eighth argument

When the entry comparison admits population, the function examines the eighth argument.

A nonzero value is used directly. If it is zero, a 32-bit value is read from external default storage and becomes the effective value used for child initialization.

The default lookup occurs once, before clearing storage, even if construction will attempt no children. A retrieved zero is not replaced again. The body contains no later default lookup for subsequent children.

### Fixed clearing

The function performs exactly ten clearing iterations on every admitted path.

For each index from zero through nine, it writes:

1. A zero 32-bit value to the corresponding child-address slot.
2. A zero byte to the corresponding auxiliary position.

The writes are interleaved by index. All ten slots and all ten auxiliary bytes are cleared regardless of the eventual number of construction attempts.

No disposal of the previous slot contents is visible before those contents are overwritten.

### Construction bound and arithmetic

The construction index begins at zero. Before every attempt, the function reads destination offset 0x00 and compares the index and that word using signed 32-bit comparison semantics.

The index is maintained as an unsigned 32-bit quantity and incremented by one after an accepted iteration. Its unsigned increment is modulo \(2^{32}\); the loop test interprets it as signed. No independent ten-slot capacity check appears in the construction loop.

Under stable, disjoint storage and dependencies that preserve the count, the admitted count is zero through nine. In that case, construction attempts that many children unless rejection stops it earlier.

Without those assumptions:

- The live destination count can differ from the count that admitted entry.
- A live bound interpreted as negative can prevent the first attempt.
- A dependency can increase or reduce the bound before the next loop test.
- Construction can reach indices beyond the ten cleared slots.
- An excessive index can cause writes outside the described child-slot region.

The entry comparison alone does not establish memory-safe indexing. Behavior after invalid address calculations or accesses is not defined by the supplied evidence.

### One child attempt

For each admitted iteration, the externally relevant sequence is:

1. Call F-8157a180d901 with the size value 0xA4, equal to 164 bytes.
2. Obtain the initializer’s selector argument from the destination word at offset 0x08, converted to a character-sized value.
3. Call F-53d23e2c87a5 with:
   - The result of F-8157a180d901.
   - The destination address.
   - That converted selector.
   - Arguments four, five, and six, in order.
   - The effective eighth argument.
4. Store the address returned by F-53d23e2c87a5 in the current child slot.
5. Read the returned object’s field at offset 0x74 and continue with the acceptance checks.

The initializer’s selector observation occurs after F-8157a180d901 returns. The selector is not necessarily the original third argument: it is recovered from destination storage, which earlier writes or dependencies may have changed.

The two dependency return values need not be identical. The second return value is the address stored, validated, and used to locate the indirect dispatch table on rejection.

There is no visible null check before the offset-0x74 read.

### Acceptance checks and read order

All child-field checks are 32-bit zero/nonzero tests.

The common field at offset 0x74 is read first. If zero, the child is rejected without reading selector-specific fields.

If the common field is nonzero, validation proceeds as follows:

| Selector observations | Additional reads and acceptance condition |
|---|---|
| First validation observation is zero | Read 0x7C. Reject if zero; otherwise read 0x80 and accept only if that field is nonzero. |
| First observation is nonzero; second observation is one | Read 0x78 and accept only if it is nonzero. |
| First observation is nonzero; second observation is not one | Accept without an additional child-field check. |

The selector-zero test and selector-one test are separate observations of the destination word. The second occurs only when the first did not select the zero branch. This distinction matters if storage changes between observations; the contract does not replace them with one immutable selector value.

With stable selector storage, the ordinary rules are:

- Selector zero requires nonzero fields at 0x74, 0x7C, and 0x80.
- Selector one requires nonzero fields at 0x74 and 0x78.
- Every other selector requires only nonzero 0x74.

### Rejection and partial completion

On the first rejected child, the function rereads the current child slot.

If the slot is nonzero, it invokes an indirect dependency selected from the returned object’s first word: that word supplies a table address, and the callable entry is at table offset 0x0C. The guard uses the stored slot, while dispatch lookup uses the returned object address.

If the indirect call returns normally, or the slot was zero and the call was skipped, the function then:

1. Clears the current child slot.
2. Writes the current zero-based index to the caller’s count.
3. Writes that index to destination offset 0x00.
4. Terminates the construction loop.

The visible rejection handler does not release preceding accepted children or clear their slots.

The indirect call resembles cleanup, but its ownership effect is unknown. Its argument convention and any implicit receiver cannot be established from the visible call expression.

Destination offset 0x04 is not explicitly revised by rejection handling. Under disjoint storage and dependencies that preserve it, this second copy retains its initial value while offset 0x00 receives the accepted-prefix count. Overlap can invalidate that distinction.

### Final dependencies and return

After the construction loop ends, the function calls:

1. F-b00260d1087a with the destination address plus 0x40.
2. F-79048eba87f4 with the destination address plus 0x48, followed by the destination address plus 0x40.

These calls occur after normal loop completion, a zero-iteration loop, or ordinary child rejection. They do not occur on the unsigned entry-rejection path.

Their return values do not control visible subsequent behavior. Their mutations are unknown, so the rejection writes are not unconditional guarantees about final memory contents after these calls.

If execution reaches the final return, the original destination address is returned.

## Side effects

Direct effects include initial count copies and the selector-byte write on every normally reached entry sequence.

An admitted population path additionally:

- Reads external default storage when the eighth argument is zero.
- Clears ten child-address slots and ten auxiliary bytes.
- Calls the two child dependencies for each attempted child.
- Stores each initializer-returned address.
- Reads conditional child-validation fields.
- May invoke indirect cleanup.
- On rejection, clears one slot and writes the accepted-prefix count to two locations in the specified order.
- Calls the two final dependencies.

Reinitializing a populated record overwrites old slot values without visible disposal. Safe reuse, ownership transfer, and leak freedom are not established.

There is no visible rollback for abnormal allocation, initialization, validation access, indirect cleanup, or final-dependency termination. In particular, a null initializer result is stored and then used for the common field read; it is not safely converted into ordinary rejection by an explicit null check.

No dependency is assumed to preserve globals, destination fields, the caller’s count, previous children, or allocation ownership.

## Acceptance examples

These are conditional expectations, not runtime observations. Unless varied explicitly, assume valid disjoint storage, stable count and selector values, dependencies preserving relevant record fields, normal dependency returns, and a target representation in which the written selector byte supplies the converted selector value.

1. **Request of ten.** Both destination count words receive ten and the selector byte is written. No default lookup, clearing, construction, or final dependency call occurs. The destination address is returned.

2. **Request of zero and zero eighth argument.** The default is read once. All ten slots and auxiliary bytes are cleared. No child is attempted. Both final dependencies run in order.

3. **Nine accepted children.** The stable count is nine and every attempted child satisfies its branch’s checks. Exactly nine attempts occur. This example depends on count preservation; it does not establish a universal nine-child limit.

4. **Selector one with three accepted children.** Each returned child has readable, nonzero fields at 0x74 and 0x78. No validation read at 0x7C or 0x80 is required. The three addresses remain stored, and both final dependencies run.

5. **Selector other than zero or one.** A child has a readable, nonzero field at 0x74. The visible validation accepts it without reading 0x78, 0x7C, or 0x80. Readability through offset 0x80 is not a prerequisite for this path.

6. **Selector zero with zero 0x7C.** The common field is nonzero, but 0x7C is zero. The child is rejected without a validation read at 0x80. Any cleanup access requirements still apply.

7. **Selector zero rejects index two at 0x80.** The third child has nonzero 0x74 and 0x7C but zero 0x80. Its nonzero slot causes indirect dispatch. After that call returns, the slot is cleared, two is written to the caller’s count, and then two is written to destination offset 0x00. The first two slots remain; offset 0x04 retains the original request under the assumptions above.

8. **Zero common field.** The first child has zero at 0x74. No selector observation or selector-specific field read is needed for its rejection. Ordinary rejection reports zero, then both final dependencies run.

9. **Initializer changes the live count.** Entry admits a request of one, but the first initializer changes destination offset 0x00 to twelve. If subsequent dependencies preserve twelve and every child is accepted, the visible loop admits twelve attempts, including indices beyond the ten cleared slots. Safe completion requires storage sufficient for the resulting accesses; the function supplies no capacity check.

10. **Initializer returns null.** Null is stored, followed by an attempted read at offset 0x74 from that address. Graceful rejection, corrected counts, final dependency execution, and a normal return are not established.

## Uncertainties

### Inferred intent

The destination appears to aggregate child objects. The two count fields appear intended to distinguish current population from the initial request. The size-request dependency appears allocation-related, and the indirect rejection call appears cleanup-related. These interpretations add no ownership or success guarantees.
