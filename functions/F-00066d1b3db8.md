# F-00066d1b3db8

## Purpose

F-00066d1b3db8 conditionally transfers bytes from a caller-maintained source cursor into a destination, updates two caller-maintained state cells, and optionally delegates further processing according to an operation selector.

The admission condition compares a signed sum of the current accounting value and the requested transfer amount against a supplied limit. It is not independently a memory-bounds check: the function does not establish that the source or destination has the required storage, or that the accounting value accurately represents that storage.

An important distinction is that the fallback result, the 32-bit value **4**, does not uniquely indicate rejection or lack of side effects. The function also returns 4 after an admitted transfer when the selector does not select either dependency.

This contract describes the supplied static representation. No runtime tests have been performed.

## Interface

The function has eight positional inputs and returns a 32-bit result. The following descriptive names identify interface roles, not source-level identifiers.

| Position | Contract name | Representation and role |
|---|---|---|
| 1 | Limit | Signed 32-bit integer used as the right-hand side of the admission comparison. |
| 2 | Selector | Signed 32-bit integer controlling dependency dispatch after an admitted operation. |
| 3 | Amount | Signed 32-bit integer used in admission arithmetic, byte-transfer iteration, state advancement, and one dependency argument. |
| 4 | Auxiliary word | Opaque 32-bit value forwarded only to F-0053e5955c80. |
| 5 | Source-cursor cell | Address of a writable 32-bit integer cell whose contents represent the current source address. The cell is read immediately on entry. |
| 6 | Accounting cell | Address of a writable signed 32-bit integer cell. Its contents participate in admission and are updated after an admitted operation. |
| 7 | Destination address | Address-valued 32-bit integer identifying the start of the byte destination. |
| 8 | Context word | Opaque 32-bit value forwarded only to F-0053e5955c80. |

The recovered representation uses 32-bit integers and words, with individual transfer accesses of one byte. It does not establish a portable language-level interface for platforms with different integer or pointer widths.

There is no demonstrated structure layout beyond the two separately supplied 32-bit state cells. The transferred region is treated as bytes: there are no observed headers, terminators, element conversions, or alignment adjustments.

### Preconditions for defined, ordinary operation

For a normal, nonfaulting execution:

- Both state-cell addresses must permit their required reads. On admitted paths, they must also permit the required writes.
- For a positive admitted amount, the source address captured from the source-cursor cell must identify that many readable bytes, and the destination must identify that many writable bytes.
- Signed addition and address arithmetic must have defined behavior for the applicable execution environment. The supplied representation alone does not settle overflow behavior.
- Any selected dependency must have its own preconditions satisfied. Those preconditions are not supplied here.

A nonpositive amount does not cause transfer-buffer accesses in the visible byte loop. It does not eliminate state-cell accesses, arithmetic, state writes, or dependency invocation.

## Behavior

### Admission and initial observations

The function first reads the source-cursor cell and retains its 32-bit contents as the source address for this operation. This read occurs even when admission will subsequently fail.

It next reads the accounting cell and evaluates whether:

**current accounting value + amount ≤ limit**

The comparison is signed in the supplied representation. There is no separate check that the amount, limit, or accounting value is nonnegative.

If the admission condition is false:

- No byte transfer is performed by the visible body.
- Neither state cell is written by the visible body.
- Neither dependency is called.
- The result is the 32-bit value 4.

The initial state-cell reads are therefore observable even on rejection. A bad source-cursor-cell address is not made safe merely by arranging for the admission comparison to fail.

### Byte-transfer semantics

When admission succeeds, a positive amount causes exactly that many byte assignments. Transfer proceeds in increasing offset order, starting at offset zero.

For each offset, the byte at the captured source address plus that offset is read, then written to the destination address plus the same offset. The next offset is processed only after the current assignment.

Consequences of this ordering include:

- The operation is not an atomic whole-buffer replacement.
- The complete input is not snapshotted before writing begins.
- Source and destination overlap is not rejected.
- Writes can affect later source reads when the regions overlap.
- Destination bytes beyond the requested positive amount are not written by the visible transfer.
- No terminating byte is appended.

If the amount is zero or negative, the loop performs no byte reads or writes. Admission success still proceeds to state advancement and dispatch.

The source base used throughout the loop is the value captured at entry. Changes to the source-cursor cell during the transfer do not redirect the remaining transfer accesses. Changes to memory at the captured source addresses can, however, change bytes read at later offsets.

### State advancement

After the byte loop finishes, the function reads the accounting cell again, adds the amount to that newly read value, and writes the sum back to that cell.

This is not necessarily an update based on the value used for admission. In particular, if destination writes overlap the accounting cell, the update uses the cell contents after those writes.

After the accounting write, the function writes the following value to the source-cursor cell:

**source address captured at entry + amount**

This write is based on the captured source address, not a fresh read of the source-cursor cell.

The ordered visible state changes on an admitted path are therefore:

1. Transfer bytes, if the amount is positive.
2. Re-read and update the accounting cell.
3. Update the source-cursor cell using the original captured source address.
4. Select and, where applicable, invoke a dependency.

Aliasing can make this ordering significant. If both state-cell arguments designate the same storage, the source-cursor write follows and overwrites the accounting update, provided execution reaches that write. The interface contains no visible disjointness check.

### Selector-dependent result

Dispatch occurs only after successful admission and the state writes.

| Selector | Visible dispatch | Function result |
|---|---|---|
| 1 or 2 | Invoke F-606c845c02bd with no explicit arguments | The dependency’s returned 32-bit value |
| Greater than 2 | Invoke F-0053e5955c80 | The dependency’s returned 32-bit value |
| Zero or negative | No dependency invocation | 4 |

F-0053e5955c80 receives five arguments in this order:

1. Amount.
2. Selector.
3. Auxiliary word.
4. Destination address.
5. Context word.

F-606c845c02bd receives no explicit arguments in the supplied representation. That does not establish that it is independent of global or otherwise shared state.

The caller’s amount, selector, auxiliary word, destination address, and context word are passed as values where listed. The original limit and the two state-cell addresses are not explicit arguments to either dependency.

A dependency result is returned without visible translation, validation, or substitution. Thus a result of 4 may also originate from a dependency.

### Zero, negative values, and arithmetic limits

A zero amount is not a special early-return case. If admitted, it causes no transfer-buffer access, but the accounting cell is read again and written, the source-cursor cell is written, and dispatch proceeds normally.

A negative amount can also be admitted. For ordinary representable arithmetic:

- No bytes are transferred.
- The accounting update decreases the value read after the loop.
- The source-cursor update moves the captured address backward by the magnitude of the amount.
- A selector greater than 2 forwards the negative amount to F-0053e5955c80.

These are established consequences of the visible conditions, not evidence that negative requests are intended or safe for downstream processing.

The admission sum, accounting update, and source-address advancement all require attention to 32-bit boundaries. The supplied representation does not justify choosing signed wraparound, saturation, trapping, or rejection for overflow. Boundary cases involving overflow are documented_only.

## Side effects

### Direct memory effects

The visible body can:

- Read the source-cursor cell once at entry.
- Read the accounting cell for admission.
- Read and write transfer bytes in ascending offset order.
- Read the accounting cell again after transfer.
- Write the accounting cell.
- Write the source-cursor cell.

For disjoint, ordinary memory, the byte loop does not modify the source region. That is not an unconditional source-preservation guarantee: destination overlap and state-cell aliasing can modify memory that also belongs to the source region.

There is no visible allocation, deallocation, ownership transfer, resource acquisition, or resource release in the function body. The inputs behave as caller-supplied storage references, but the supplied evidence does not establish ownership rules for either dependency.

### Dependency effects and failures

Both dependencies run after the direct transfer and state updates. Their effects on globals, supplied buffers, state cells reachable through other means, and resource ownership are unknown.

The visible body contains no rollback for dependency failure. If a dependency returns an error-like value normally, the function returns that value without visibly undoing prior writes. Whether a particular returned value is an error is not established.

Invalid memory accesses, arithmetic faults, and nonreturning dependency behavior have no visible local recovery mechanism. Their externally observable handling depends on the execution environment and the dependencies.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, assume valid disjoint storage, ordinary memory, representable arithmetic, and normally returning dependencies.

### 1. Rejected positive request

Given accounting value 8, amount 3, and limit 10:

- Admission fails because 11 exceeds 10.
- The source-cursor cell is nevertheless read before the comparison.
- No transfer bytes or state cells are written.
- No dependency is invoked, regardless of selector.
- The result is 4.

### 2. Exact-limit transfer without dispatch

Given accounting value 8, amount 2, limit 10, and selector 0:

- Admission succeeds at equality.
- Two source bytes are copied in increasing offset order.
- The accounting cell becomes 10.
- The source-cursor cell advances by two address units.
- No dependency is invoked.
- The result is 4 despite the completed writes.

### 3. Dispatch after committed direct updates

Given an admitted amount of 3 and selector 2:

- Three bytes are transferred.
- Both state updates occur.
- F-606c845c02bd is then invoked.
- If it returns the 32-bit value 9, this function returns 9.

No assertion is made about final memory after that dependency returns unless its effects are separately constrained.

### 4. Argument forwarding for a larger selector

Given an admitted amount of 5 and selector 3:

- The transfer and state updates precede the call.
- F-0053e5955c80 receives, in order, 5, 3, the auxiliary word, the destination address, and the context word.
- Its result is returned unchanged.

### 5. Admitted zero amount

Given accounting value 7, amount 0, limit 7, and selector 1:

- No transfer-buffer access occurs.
- The accounting cell is re-read and written with the same numerical value.
- The source-cursor cell is written with the captured source address.
- F-606c845c02bd is invoked.

Unchanged numerical state does not imply absence of writes.

### 6. Admitted negative amount

Given accounting value 7, amount −2, limit 10, and selector −1:

- Admission succeeds because 5 is at most 10.
- No transfer bytes are accessed.
- The accounting value becomes 5.
- The source-cursor value decreases by 2.
- No dependency is invoked.
- The result is 4.

This example is conditional on representable, valid address arithmetic; it does not establish that backward cursor movement is an intended use.

### 7. Forward overlap

Suppose the source begins with bytes A, B, C, D, and the destination starts one byte after the source. For an admitted amount of 3, with state cells elsewhere:

- The first assignment writes A over B.
- The second reads that newly written A and writes it over C.
- The third reads the next newly written A and writes it over D.

The four-byte region becomes A, A, A, A before dispatch. Snapshot-copy behavior would not satisfy this contract.

### 8. Shared state-cell storage

If the source-cursor cell and accounting cell are the same valid 32-bit cell, and execution is admitted without arithmetic faults:

- The accounting update is written first.
- The captured-source-plus-amount value is written second to the same cell.

Before any dependency effects, the final cell contents are determined by the second write.
