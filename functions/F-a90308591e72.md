# F-a90308591e72

## Purpose

F-a90308591e72 conditionally prepares an associated object and submits a sequence of row-oriented transfer requests to an external dependency. It returns a 32-bit status indicating whether execution reached the end of that sequence.

The visible behavior supports an inferred intent of moving rows from an associated source into a caller-supplied destination, with optional mode reconfiguration. That interpretation is not an established contract for the external dependency: the supplied evidence does not establish that it copies bytes, its overlap rules, or whether it can fail.

Established behavior includes:

- An initial gate and a distinguished handle value can prevent processing.
- Two preparatory operations can report failure and cause an immediate zero return.
- A cached 16-bit mode is updated only after both preparatory operations report success.
- Row requests use a fixed initial width, a caller-provided destination step, and a source step reread after every request.
- Reaching the loop’s end returns one, including when no rows were requested.

No runtime tests have been performed.

## Behavior

### Initial eligibility checks

The function first reads the global gate.

- If that read is nonzero, it reads the context’s 32-bit handle at offset 100.
- If that read is zero, it does not read the context at this stage.

It then reads the global gate again. If this second read is zero, it returns zero immediately.

If the second gate read is nonzero, it rejects a previously read handle equal to −1. When the first gate read was zero, the local eligibility value remains zero rather than containing a context handle. Consequently, if the gate changes from zero to nonzero between the two reads, the function can proceed without having checked the context’s handle against −1.

The two gate reads must not be treated as one stable snapshot. No later gate check is visible.

### Preparation and object resolution

After passing eligibility checking, the function performs these operations in order:

1. Reads the context token at offset 104 and calls F-0eeabd45a2a0 with that value.
2. Reads the context handle at offset 100 again and passes it to F-f6358965d277.
3. Reads the 32-bit field at offset 84 of the returned object, retaining it as the secondary-object address.

The return from F-0eeabd45a2a0 is not used. The handle passed to F-f6358965d277 is a fresh read, not necessarily the value inspected during eligibility checking.

The secondary-object address is obtained before optional mode configuration. The function retains that address across the following calls; it does not reload it from the resolved object afterward.

### Conditional mode configuration

The function reads the context’s cached mode as an unsigned 16-bit value and compares its zero-extended value against the full unsigned 32-bit requested mode.

If they are equal, both configuration dependencies and the cached-mode write are skipped.

If they differ:

1. F-1422394ed772 receives the resolved-object address, the full requested mode, and the constant 2.
2. A nonzero return causes an immediate zero return from F-a90308591e72.
3. Otherwise, F-6c10861922bc receives the retained secondary-object address and the constant 0.
4. A nonzero return causes an immediate zero return from F-a90308591e72.
5. Only after both calls return zero does the function write the low 16 bits of the requested mode to context offset 96.

The comparison and write have different widths. A requested mode greater than 65,535 cannot equal any cached 16-bit mode, even when its low 16 bits match the cache. If accepted by both dependencies, such a request is stored only in truncated form and will still compare unequal on a later call with the same full-width request.

There is no visible rollback. A failure from the second configuration dependency does not undo effects of the first. Nor does an early return guarantee that dependencies left the cached mode or other state unchanged.

### Row submission

After mode handling, the function reads the secondary object’s signed 32-bit source step at offset 84, followed by its initial source address at offset 88.

It derives one row-width value from that initial source step:

- A nonnegative step is used unchanged.
- A negative step is negated.

This derived width is retained for every row request. It is not recomputed if the source-step field changes later.

A signed row counter starts at zero. Before each possible request, the function rereads the signed 32-bit loop bound at secondary-object offset 76. A request occurs only while the counter is less than that current bound.

Each iteration has this order:

1. Invoke D-01 with the current destination address, current source address, and retained row-width value.
2. Add the destination step to the current destination address.
3. Reread the signed source step at secondary-object offset 84 and add it to the current source address.
4. Increment the row counter.
5. Reevaluate the loop condition using a fresh loop-bound read.

D-01 is an opaque label assigned here to the unmapped external row dependency; no supplied stable function ID is available for it.

The destination and source advances occur even after the last request. In particular, the source-step field is read after the final request before the next loop-bound check determines that iteration is finished.

For a stable loop bound of zero or a negative number, the loop makes no requests. The initial source-step and source-address reads still occur, and the function returns one.

A zero initial source step produces a width argument of zero. With a positive loop bound, this does not suppress calls to D-01.

## Side effects

The wrapper itself does not visibly write destination bytes. Destination modification, if any, belongs to D-01.

### Dependency-visible effects

Calls occur in the order described above. Their side effects are not constrained by the supplied evidence beyond their arguments and the wrapper’s use of their returns.

In particular:

- F-0eeabd45a2a0 may affect the handle subsequently reread from the context.
- Configuration dependencies may change fields subsequently read from the secondary object.
- D-01 may affect the source step used immediately afterward or the loop bound used in the next condition.

No preservation of globals, object fields, or allocation state may be assumed for an unknown dependency.

### Ownership and lifetime

The evidence establishes no ownership transfer, allocation, deallocation, reference-count operation, or lock discipline.

Passing an address or token to a dependency does not establish whether that dependency retains, releases, or owns it. Successful continuation requires that storage used by later visible accesses remain valid.

### Errors and partial progress

## Acceptance examples

These are conditional expectations from static evidence, not executed tests.

1. **Gate remains disabled.**  
   If both gate reads are zero, the result is zero. No context field is read, no dependency is called, and no cached-mode write occurs.

2. **Rejected handle.**  
   If both gate reads are nonzero and the initially read handle is −1, the result is zero without dependency calls.

3. **Gate becomes enabled between reads.**  
   If the first gate read is zero and the second is nonzero, processing proceeds to preparation. The handle read for F-f6358965d277 is not subject to the earlier −1 check.

4. **Stable matching mode and two rows.**  
   Assume valid stable objects, a cached mode equal to the requested mode, loop bound 2, source step 12, initial source address S, initial destination address T, and destination step 20. The configuration calls are skipped. D-01 receives, in order, destination/source/width values of T, S, 12 and then T + 20, S + 12, 12. The function returns one if all calls return normally and arithmetic is representable.

5. **Negative source step.**  
   With a stable source step of −12 and loop bound 2, the width is 12 for both calls, but source addresses are S and S − 12.

6. **Full-width mode differs despite matching low bits.**  
   With cached mode 1 and requested mode 65,537, configuration is attempted. If both checked dependencies return zero, the cached value written is 1. The function does not reject the request merely because it exceeds 16 bits.

7. **Second configuration call fails.**  
   If the first configuration call returns zero and the second returns nonzero, the function returns zero, performs no row requests, and does not itself perform the cached-mode write. Effects already caused by either dependency remain unspecified.

8. **Nonpositive loop bound.**  
   With otherwise successful preparation and a stable bound of −3 or 0, no row requests occur and the result is one.

9. **Source step changes during a row request.**  
   If the initial step is 12 but the first D-01 call changes it to −8, the next source address is S − 8. Later requests still receive width 12.

10. **Loop bound changes during submission.**  
    If the bound initially permits a request but becomes zero during that request, the post-request address advances occur, then the next condition terminates the loop. An initial bound is not a fixed request count.
