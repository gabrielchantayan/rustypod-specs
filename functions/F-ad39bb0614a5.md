# F-ad39bb0614a5

## Purpose

F-ad39bb0614a5 traverses variable-length records in a data region located through F-e81ed1edd673. It compares each record’s decoded key with a requested unsigned 32-bit key and selects either a numbered match or, subject to a counter-wrap limit, the last match encountered.

The result is an unsigned 32-bit offset relative to a data base, not a pointer. Zero is the failure or no-selection sentinel. For a nonzero selected offset and a nonnull output pointer, the function decodes an additional field from the selected record and writes that value to the output.

“Container,” “record,” “extent,” and “metadata” describe structural roles visible in the supplied representation. Their external format and application meanings are not established.

This contract distinguishes directly established operations from behavior requiring a fixed-width machine-arithmetic interpretation. In particular, unsigned bound addition has defined modulo behavior, whereas certain signed intermediate expressions do not have a fully defined overflow result under literal language semantics.

## Interface

The function accepts five inputs and returns an unsigned 32-bit value.

| Input | Observed role |
|---|---|
| Base holder | Pointer to a slot represented as a signed 32-bit integer containing a data-base address. |
| Occurrence selector | Unsigned 32-bit value controlling match selection. |
| Requested key | Unsigned 32-bit value compared with decoded record keys; also passed twice to F-e81ed1edd673. |
| Output pointer | Optional pointer to a writable unsigned 32-bit value. Passed to F-e81ed1edd673 and conditionally written locally. |
| Dependency argument | Opaque 32-bit value forwarded to F-e81ed1edd673. |

There is no separate error code, returned length, or Boolean status.

### Input validity

A null base holder, or a holder initially containing zero, produces an immediate zero return without calling the dependency.

Otherwise, safe execution requires every address actually accessed to be valid. The function does not validate allocation sizes, field availability, pointer alignment for the final output store, or output writability.

The dependency receives the holder and output pointer. This function does not establish that either remains unchanged across that call.

### Container and record layout

The dependency’s nonzero result is represented as a signed 32-bit container offset. The traversal position and returned offset are unsigned 32-bit quantities.

The container has the following locally observed structure:

| Displacement from container start | Local use |
|---|---|
| 0–3 | Four-byte encoded extent, reread at each traversal condition |
| 4–19 | No explicit local read |
| 20 | Initial candidate record begins here |

The displacement of 20 is a fixed positioning rule, not a decoded pointer field.

Each candidate record has these observed fields:

| Displacement from record start | Local use |
|---|---|
| 0–3 | Encoded step added to the current record offset |
| 4–7 | Encoded key |
| 8–11 | Encoded metadata, read only after nonzero selection when an output pointer is supplied |

The function does not require the decoded step to be at least 12, and it does not verify that these fields fit within the stated container extent.

### Four-byte decoding and its arithmetic qualification

Every locally decoded field uses the same expression structure.

Under a **fixed-width, low-32-bit machine-arithmetic interpretation**, decoding four bytes means:

- Multiply each byte independently by 23.
- Retain the low eight bits of each product.
- Assemble those four transformed bytes in most-significant-byte-first order.

Carries do not propagate between byte positions. This is not multiplication of an ordinary big-endian 32-bit value by 23.

Examples under that interpretation:

| Encoded bytes | Decoded unsigned value |
|---|---:|
| `00 00 00 01` | 23 |
| `00 00 00 02` | 46 |
| `00 00 00 0C` | 20 |
| `00 00 01 00` | 5,888 |
| `06 00 00 00` | `0x8A000000` |

The final example requires the arithmetic qualification. The most-significant-byte contribution is formed by a signed multiplication by `0x17000000`. Its byte operand is nonnegative, but a byte value of 6 or greater makes the mathematical product exceed the signed 32-bit maximum. Literal language semantics therefore do not independently establish a result for those inputs.

For most-significant byte values 0 through 5, that multiplication is representable. The other three byte multiplications are also representable because their largest product is 255 × 23 = 5,865.

The masked lower-byte terms have unsigned 32-bit type. Consequently, the combined decoded expression has unsigned 32-bit type. That unsigned result type does not retroactively make the earlier most-significant-byte multiplication unsigned.

## Behavior

### Initial gate and dependency invocation

The function first checks whether the base-holder pointer is null. If so, it returns zero without dereferencing it.

For a nonnull holder, it reads the contained value. An initially zero value also produces zero without a dependency call.

For a nonzero initial value, F-e81ed1edd673 is called once with these arguments, in order:

1. The original base-holder pointer.
2. The opaque dependency argument.
3. The requested key.
4. The original output pointer.
5. The requested key again.

The occurrence selector is not passed.

A zero dependency result causes a zero return without local traversal or a local output write. A nonzero result is used as the container offset. The function then reloads the base-holder value and retains that base for traversal. It does not check the reloaded value for zero.

### Initial record position

The initial candidate is positioned 20 bytes after the container offset.

This initial addition is a **signed 32-bit intermediate operation**, followed by assignment to an unsigned 32-bit traversal position. It is not established as unsigned addition merely because its destination is unsigned.

When the signed addition is representable, a negative result is converted to its unsigned 32-bit representation. For positive container offsets above `0x7FFFFFEB`, adding 20 exceeds the signed 32-bit maximum. The supplied representation alone does not establish literal-language behavior in that case.

Under a fixed-width wrapping machine interpretation, the initial position is the low 32 bits of the container offset plus 20. That interpretation must be explicit when accepting such overflowing inputs.

### Traversal condition and field-read order

At every condition evaluation, including the evaluation that terminates traversal, the function:

1. Replaces the current return candidate with the retained last-match offset.
2. Reads and decodes the four-byte container extent using the retained traversal base.
3. Compares the unsigned current record offset with the computed unsigned bound.

The bound is the container offset plus decoded extent, modulo \(2^{32}\). The decoded extent expression has unsigned 32-bit type, so the container offset is converted to unsigned for this addition.

**Bound wraparound is established unsigned arithmetic, not an unresolved signed-overflow case.** If decoding itself encounters the signed multiplication issue described above, the extent value still requires the stated machine interpretation; the addition’s unsigned type is not uncertain.

A candidate is admitted only when its unsigned offset is strictly less than the bound. Equality rejects it. A rejected candidate causes no local key or step read.

For an admitted candidate, the function reads and decodes the key at displacement 4. If that key does not match the requested key, selection state is unchanged.

Unless a matching record causes an immediate exit, the function then reads and decodes the step at displacement 0 and advances the unsigned record offset by that step, modulo \(2^{32}\).

Thus the local field-level order is:

- Extent before candidate admission.
- Key after admission.
- Step after key processing, unless selection exits immediately.
- Selected metadata only after traversal finishes with a nonzero selection and a nonnull output pointer.

The order of individual byte loads within one decoded field is not established.

### Match counting and selection

The match counter begins at zero. Each matching key increments it and clears bit 16 of the result.

Starting from zero, this maintains a counter in the range 0–65,535 with the sequence:

1 through 65,535, then 0, then 1 again.

For each match, the current record offset becomes a provisional return candidate. The updated counter is compared with the full unsigned 32-bit occurrence selector.

If equal, traversal exits immediately. The selected record’s step is not read.

If not equal:

- Selector zero updates the retained last-match offset.
- A nonzero selector leaves the retained last-match offset unchanged at zero.

The next condition evaluation restores the return candidate from that retained offset. Consequently, a provisional match does not make a numbered search succeed unless counter equality causes immediate exit.

The resulting selection rules are:

| Selector | Selection rule |
|---|---|
| 1–65,535 | Exit at the corresponding matching record, if reached |
| 0 | Retain successive matches, but exit immediately at the 65,536th match |
| 65,536–4,294,967,295 | Never equal the counter; return zero if traversal terminates normally |

Selector zero is therefore not an unlimited “find the last match” operation. Before the wrap boundary it returns the last match reached by a terminating traversal. At the boundary it selects the 65,536th match without examining subsequent records.

### Completion and optional output

A selected offset of zero is treated as no local success, even if traversal selected that numerical offset through counter equality.

For a zero selected offset, the function returns zero without a local output write.

For a nonzero selected offset and a null output pointer, it returns the offset without reading metadata.

For a nonzero selected offset and a nonnull output pointer, it:

1. Reloads the base-holder value.
2. Reads and decodes the selected record’s four-byte metadata at displacement 8 using that reloaded base.
3. Writes the decoded unsigned 32-bit value through the output pointer.
4. Returns the selected offset.

The final base is not necessarily the value retained for traversal. No post-reload null check is performed. Metadata decoding completes before the local output store.

### Termination and malformed data

The function has no explicit guard against:

- Zero steps.
- Steps smaller than the observed record prefix.
- Unsigned offset wraparound.
- Cycles or repeated record positions.
- Incomplete records.
- Inaccessible container or record storage.
- Excessive traversal length.

A stable, admitted, nonmatching record with step zero can prevent termination indefinitely.

A repeatedly visited matching record with step zero can terminate a selector from 1 through 65,535 when the counter reaches that selector. Selector zero terminates on its 65,536th matching visit. Larger selectors cannot terminate through counter equality.

Unsigned bound wraparound can also reject the initial position or change which offsets qualify. It is not interpreted as an automatically invalid container.

## Side effects

Directly visible local effects are limited to reads and a conditional output store:

- At most one call to F-e81ed1edd673.
- An initial holder read, another holder read after a nonzero dependency result, and a final holder read when producing local output.
- Repeated container-extent reads and conditional record-field reads.
- One unsigned 32-bit output store after nonzero selection with a nonnull output pointer.
- No explicit local allocation, deallocation, base-holder store, or record-data store.

The dependency’s effects are not constrained by these observations. In particular, a zero function result does not guarantee that the output remained unchanged: the dependency may have written it.

No ownership transfer or memory-lifetime guarantee is established. The absence of local allocation and release does not imply that the dependency preserves allocations, globals, or referenced storage.

The output pointer may alias the base-holder slot or data storage; no local alias exclusion is enforced. In that case, the final output store can modify the aliased object after metadata has been read.

There is no established synchronization or concurrent-mutation contract. Invalid accesses are not translated into defined error returns.

## Acceptance examples

These are conditional static expectations, not runtime test results. Unless an example states otherwise, assume valid accessible storage, stable data, representable signed address calculations, representable initial-position addition, and decoded fields whose most-significant bytes do not trigger signed multiplication overflow.

### Null or initially empty base

### Dependency returns zero

### Three matching records

Suppose the dependency supplies container offset `0x100`, with decoded extent 89. The unsigned bound is `0x159`.

Three records begin at `0x114`, `0x12B`, and `0x142`. Each has decoded step 23 and key 23. Their decoded metadata values are 46, 69, and 92 respectively. Advancing from the third record reaches the excluded bound.

For requested key 23:

| Selector | Return | Local output value, if supplied |
|---|---:|---:|
| 0 | `0x142` | 92 |
| 1 | `0x114` | 46 |
| 2 | `0x12B` | 69 |

| 4 | 0 | No local write |
| 65,536 | 0 | No local write |

For a key absent from all three records, every selector returns zero without a local output write.

### Immediate selection avoids later fields

If the first admitted record matches and the selector is 1, its step field is not read.

If the output pointer is also null, its metadata is not read. These statements do not constrain accesses made by the preceding dependency call.

### Empty traversal

For an ordinary positive container offset and decoded extent 20, the initial position equals the bound. No record body is entered.

A smaller extent also rejects the initial position when these additions do not wrap.

### Unsigned bound wraparound

Suppose the dependency result represents signed −32, whose unsigned representation is `0xFFFFFFE0`, and the decoded extent is 64.

The initial signed addition is representable: −32 + 20 = −12, yielding unsigned position `0xFFFFFFF4`. The bound addition is unsigned and wraps to `0x00000020`.

Provided the extent bytes are accessible, the initial position fails the unsigned less-than comparison. No record body is entered, and the function returns zero.

### Signed overflow qualifications

For a container offset of `0x7FFFFFF0`, adding 20 overflows signed 32-bit arithmetic. This contract does not assign an unconditional result under literal language semantics. A separately established wrapping-machine interpretation would give initial position `0x80000004`.

Likewise, bytes `06 00 00 00` decode to `0x8A000000` under the explicit low-32-bit machine interpretation, but that value is not unconditionally established by literal signed multiplication semantics.

### Counter-wrap boundary

If traversal reaches 65,536 matching visits with selector zero, it exits on the 65,536th match and does not seek a later last match.

Selector 65,536 cannot equal the counter. If traversal terminates normally, it returns zero regardless of how many matches were visited.
