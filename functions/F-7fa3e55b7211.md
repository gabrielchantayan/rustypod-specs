# F-7fa3e55b7211

## Purpose

F-7fa3e55b7211 selects between a whole-structure operation followed by explicit field resets and a loop that captures a position value, invokes an advancement-like operation, and processes the captured value.

Range removal, with a shortcut for a complete range, is **inferred intent**. The supplied body establishes access order, dependency arguments, branch conditions, writes, and return construction. It does not establish that any dependency removes items, destroys objects, releases memory, or maintains a particular container invariant.

The return is a 64-bit concatenation of two 32-bit components. On the loop path, those components are read from temporary slots when the return expression is evaluated. They are not necessarily the values immediately following the last processing call: addresses of both slots have been exposed to a dependency, and subsequent calls may modify them through retained references or shared state during this activation.

- The upper component occupies bits 63–32.
- The lower component occupies bits 31–0.

Concatenation preserves each component’s 32-bit pattern. For example, a lower component of `0xFFFFFFFF` contributes those low 32 bits; it does not sign-extend across the upper component.

Address-bearing values are represented with four bytes in the supplied body. A 32-bit address representation is supported by that evidence. Native calling convention, a higher-level return type, and byte order for storing the resulting 64-bit value elsewhere remain `documented_only`.

## Behavior

### Entry write and boundary snapshot

Before any dependency call, the function:

1. Reads the owner’s header reference at offset `0x10`.
2. Writes that 32-bit value to the output destination.
3. Rereads the owner’s header reference.
4. Reads the field at offset `0x08` in the newly referenced header into temporary boundary storage.

The second header-reference read cannot generally be replaced with the first. If the output write overlaps the owner’s header-reference field, it participates in the state from which the boundary snapshot is obtained.

The function then initializes two 32-bit return-component slots:

- The lower slot receives the output destination’s address representation.
- The upper slot receives the owner address representation.

It invokes F-a1ecaae6738a with position storage and the address of the boundary snapshot.

This first result is tested for **nonzero**, not for equality to `1`.

### Shortcut eligibility

A zero first comparison result leads directly to the loop.

For a nonzero first result:

1. The current owner header reference is read into a separate temporary snapshot.
2. F-a1ecaae6738a is invoked with the endpoint token and the address of that snapshot.
3. If this second result is nonzero, the owner’s count-like field at offset `0x14` is read.
4. The shortcut is selected only if that field is also nonzero.

The count-like field is not read for this gate when the second comparison returns zero.

Both comparison gates and the count gate accept any nonzero 32-bit pattern. There is no positivity requirement. A count-like value of `0x80000000`, for example, passes the visible gate.

Failure of either later gate leads to a fresh loop comparison. None of the shortcut comparisons substitutes for that comparison.

### Whole-structure operation and reset

On the shortcut path, the function reads the current header reference and the field at offset `0x04` in that header. It calls F-1e7c072bdd93 with the owner address and that field’s value.

The dependency’s return value is unused.

If the call returns normally, the function completes these assignments in order:

1. Assign a current owner header reference to offset `0x08` of a currently referenced header.
2. Clear offset `0x04` of a currently referenced header.
3. Assign a current owner header reference to offset `0x0C` of a currently referenced header.
4. Clear the owner’s count-like field at offset `0x14`.
5. Read the owner’s header reference and write that value to the output destination.

The header reference is reread in these expressions. The function does not freeze the pre-call header. If F-1e7c072bdd93 replaces that reference, subsequent accesses use post-call reads.

Where an assignment requires both a destination header reference and a reference value to store, the supplied representation does not establish a finer ordering between those operand reads. The order of completed assignments above is established.

Aliasing also matters between assignments. A reset store that overlaps the owner’s header-reference field can affect the reference used by a later assignment.

The shortcut then returns:

- Upper 32 bits: the header-reference value read for the final output write.
- Lower 32 bits: the lower return-component slot’s contents at return evaluation.

The lower slot was initialized with the output destination’s address representation and is not explicitly reassigned on this path. Its address is not supplied to the shortcut dependencies. Under ordinary storage separation and absent other interference, it therefore retains that initial representation.

No loop comparison or loop iteration follows a successful shortcut.

### Loop comparison and iteration

At the top of every loop pass, including the first, F-a1ecaae6738a receives position storage and the endpoint token.

The loop terminates only if the returned 32-bit value is **exactly `1`**. Every other result causes an iteration, including zero, `2`, and negative signed interpretations.

Each iteration performs the following sequence:

1. Read and save the first four bytes of position storage.
2. Invoke F-dcbd5e1e578f with position storage.
3. Assign the saved, pre-call position value to the lower return-component slot.
4. Invoke F-29578640674e with the upper-slot address, the owner address, and the lower-slot address, in that argument order.
5. Read the upper slot and write its current 32-bit value to the output destination.
6. Return to the loop comparison.

The captured value precedes the advancement-like call, but its assignment to the lower slot follows that call. Thus F-29578640674e initially receives the saved position value in the lower slot, regardless of changes F-dcbd5e1e578f made to position storage.

The return value of F-dcbd5e1e578f is unused. Actual advancement and item removal remain dependency semantics, not established properties of this body.

F-29578640674e receives addresses of both return-component slots. It may change either slot. The subsequent output write uses the upper slot’s contents after that call returns.

No loop store is explicitly addressed through the position argument, and no loop store explicitly names the owner’s count-like field. This does **not** establish that either memory region remains unchanged: an output write can modify either through aliasing, and dependencies may also modify them.

### Loop termination and return

When a loop comparison returns exactly `1`, there is no further explicit output write. The function concatenates the upper and lower slots’ contents as they exist when the return expression is evaluated.

After a processing call has received both slot addresses, it may retain those addresses during the active invocation. A later comparison call can potentially reach them through shared state and modify either slot before returning `1`. Preservation is not established for that comparison or any other dependency.

Consequently:

- The eventual return components need not equal their immediate post-processing values.
- The last explicit output write need not equal the eventual upper return component.
- A dependency may also alter the output memory after the last explicit write.

If the loop terminates without an iteration, the component slots have only their explicit initializations in this body, and their addresses have not been passed to F-29578640674e. Under noninterference assumptions, the return packs the owner address above the output destination address. The output retains the entry header-reference write only if intervening effects have not changed it.

Termination is not guaranteed. It requires a comparison to return exactly `1`, and all preceding calls to return normally.

## Side effects

### Explicit writes and aliases

The body explicitly writes:

- Output storage at entry.
- Local snapshots and return-component slots.
- Three header fields and the owner’s count-like field on the shortcut path.
- Output storage after each loop processing call.
- Output storage immediately before the shortcut return.

The absence of a store expressed through a particular argument is not an absence of writes to its underlying memory. In particular:

- Output overlapping position storage makes an explicit output write a position-memory write.
- Output overlapping owner offset `0x14` makes an explicit output write a count-memory write.
- Output overlapping other accessed fields can change subsequent reads or reset destinations.

The function supplies no alias protection or restoration.

### Ownership and lifetime

No allocation or deallocation is explicit.

Values passed to processing dependencies do not establish ownership transfer, destruction, reclamation, or continued validity. Those properties remain `documented_only`.

Temporary addresses are valid during this function activation. Retaining them for use by another dependency before return is not excluded by the visible body. Dereferencing them after the activation ends would require a separate lifetime guarantee not supplied here.

### Errors and external state

Dependencies’ effects on globals and reachable memory are unknown. Their preservation cannot be assumed.

There is no explicit error status interpretation, rollback, exception translation, or recovery. If a dependency fails to return normally, completion behavior is not established, and earlier writes may already have occurred. Invalid accesses likewise have no defined recovery path in the supplied body.

## Acceptance examples

These are conditional static cases, not executed tests. Except where stated, they assume valid, nonoverlapping storage, normal returns, and no dependency effects beyond those specified.

### Immediate loop completion

If the first comparison returns zero and the first loop comparison returns `1`:

- Output receives the initial header reference.
- Neither F-dcbd5e1e578f nor F-29578640674e is called.
- The return packs the owner address above the output destination address.

### Successful shortcut

If both shortcut comparisons return nonzero and the subsequently read count-like field is nonzero:

- F-1e7c072bdd93 receives the owner and the current header’s offset-`0x04` value.
- Header offsets `0x08` and `0x0C` receive the header reference.
- Header offset `0x04` and owner offset `0x14` are cleared.
- Output receives the final header reference.
- The return uses that reference as its upper component and the original output destination address as its lower component.
- No loop comparison occurs.

These field outcomes assume stable header references and nonoverlapping layout during the resets.

### Zero count or failed second comparison

If both shortcut comparisons are nonzero but the count-like field is zero, no shortcut processing or reset occurs; execution performs a fresh loop comparison.

If the second comparison returns zero, the shortcut count read is skipped, and execution likewise performs a fresh loop comparison.

### Noncanonical comparison results

A result of `2` passes either shortcut comparison gate.

A loop-comparison result of `2` instead causes an iteration. The position value is captured before F-dcbd5e1e578f, then supplied through the lower slot to F-29578640674e.

### Preserved return components

Suppose one processing call leaves upper and lower slots containing `0x11223344` and `0xAABBCCDD`. If the next comparison returns `1` without changing those slots:

- The iteration’s explicit output write stores `0x11223344`.
- The return is `0x11223344AABBCCDD`.

Equality with the post-processing values depends on the stated preservation assumption.

### Mutation during the terminating comparison

Suppose the same processing call leaves those values and retains both slot addresses. The next comparison changes the slots through shared state to `0x55667788` and `0x01020304`, then returns `1`.

If it does not change output memory:

- The last explicit output write remains `0x11223344`.
- No additional output write occurs at termination.
- The return is `0x5566778801020304`.

### Output aliases position storage

If output is exactly the first four bytes of position storage, the entry output write replaces that position value with the header reference before the first dependency call.

Each later explicit iteration output write also changes position memory, even though no store is expressed through the position argument.

### Output aliases the count-like field

If output addresses owner offset `0x14`, the entry output write changes the count-like field. Under otherwise noninterfering dependencies, a later shortcut gate observes that written value rather than the field’s pre-entry contents.

### Header replacement by the shortcut dependency

If F-1e7c072bdd93 replaces the owner’s header reference with a valid replacement, the subsequent reset accesses use reread references. Substituting the pre-call header throughout would not preserve the established behavior.
