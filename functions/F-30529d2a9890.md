# F-30529d2a9890

## Purpose

F-30529d2a9890 conditionally constructs a context’s cached array of candidate references. It enumerates candidates in ascending source-index order, filters nonzero references through a dependency, and stores accepted references consecutively.

In mode 5, when a source companion table is present, it also constructs a companion table associating selected opaque source values with positions in the compacted candidate array.

Cache construction, filtering, and table transformation are established by static evidence. The application-level meanings of candidates, mode values, companion values, and the calls bracketing enumeration are not established.

## Interface

### Input and return value

The function receives one 32-bit context address and returns a 32-bit result.

| Result bits | Signed interpretation | Condition |
|---|---:|---|
| `0x00000000` | 0 | The cache is already present, or construction completes. |
| `0xFFFFFFCE` | −50 | F-267f68fe54d6 returns zero on the construction path. |
| `0xFFFFFF94` | −108 | F-f195b74c9758 or F-beb2daa7838d returns zero. |

There is no explicit null-context check. Every address actually accessed must designate suitably readable or writable storage. Storage returned by dependencies is checked for zero only where described below; a nonzero value is not otherwise validated.

### Context fields

Offsets are in bytes from the supplied context address.

| Offset | Width | Access |
|---|---:|---|
| `0xE3C` | 8 bits | Configuration value captured for candidate enumeration. |
| `0xEEC` | 32 bits | Primary cache address; zero selects construction. |
| `0xEF0` | 32 bits | Companion output address published after construction, possibly zero. |
| `0xEF4` | 32 bits | Retained-candidate count published after construction. |

Only the primary cache address determines whether construction occurs. The existing companion address and retained count are not checked on the cached path.

### Referenced layouts

The result of F-8ff48652068d is retained as an address. A 32-bit field at offset `0xF60` is read from that address twice on the successful construction path.

The descriptor returned by F-267f68fe54d6 has these accessed fields:

| Offset | Width | Meaning within this function |
|---|---:|---|
| `0x40` | 32 bits | Address of a nested structure. |
| `0x558` | 32 bits | Optional source companion-table address, read only in mode 5. |

The nested structure contains an unsigned 16-bit candidate count at offset `0x2E`.

The primary output holds 32-bit candidate references. Only its prefix of published-count elements is explicitly populated.

Both companion tables use a 32-bit count followed by pairs of 32-bit words. Under ordinary, nonwrapping indexing, entry number *j*, numbered from zero, has:

- An opaque value at word offset `2j + 1`.
- A boundary or position at word offset `2j + 2`.

The source count and source index calculations are unsigned 32-bit quantities. The output count and output index expressions are signed 32-bit quantities. These distinctions constrain the mathematical layout description; see **Arithmetic and storage boundaries**.

## Behavior

### Entry and cache decision

The first observable operation is a call to F-8ff48652068d with the context. Its result is saved.

The primary cache field is read only after that call returns. If it is nonzero, the function returns zero without further dependency calls or explicit cache-field writes.

Consequently, a dependency can affect the cache decision. The cached path is not established to be side-effect-free, and the initial dependency result need not be dereferenceable on that path because this function does not then read through it.

### Construction preparation

When the primary cache field is zero, preparation proceeds in this order:

1. F-267f68fe54d6 receives the context. A zero result immediately returns `0xFFFFFFCE`.
2. The descriptor’s nested address and unsigned 16-bit candidate count are read. Four times that count is passed to F-f195b74c9758.
3. A zero result from F-f195b74c9758 immediately returns `0xFFFFFF94`.
4. F-be0967308708 receives the context and supplies the mode.
5. The context’s 8-bit configuration value is captured.
6. The nested address and unsigned 16-bit candidate count are read again. This second count is captured as the enumeration limit.

The two candidate-count reads are independent. Dependencies called between them may change the descriptor or nested storage. The function does not compare the counts or resize the primary output after the second read.

If the mode is 5, the source companion-table address is read from descriptor offset `0x558`. A nonzero address enables companion preparation:

- The source table’s unsigned 32-bit count word is read and passed directly to F-beb2daa7838d.
- A zero result returns `0xFFFFFF94`.
- Otherwise, the returned output table’s count word is written as zero.

The argument to F-beb2daa7838d is a count, not an explicitly calculated byte size. Its capacity guarantee is unknown.

For any other mode, the source companion address is not read. In mode 5, a zero source address also disables companion construction.

These failure exits perform no explicit publication or cleanup. In particular, failure of companion preparation does not explicitly release the already obtained primary storage.

### Enumeration and filtering

After preparation, the function reads the 32-bit field at offset `0xF60` from the address returned by the initial dependency. It passes that value to F-94b6eb7b70a5.

Enumeration then visits every source index from zero up to, but excluding, the captured second candidate count.

For each source index:

- F-f8ec0897aceb receives the descriptor, captured mode, captured 8-bit configuration, and source index.
- A zero candidate reference is skipped, with no predicate call.
- A nonzero candidate reference is passed to F-fe9998d8ffdf with the context and a zero third argument.
- A zero predicate result rejects the candidate. Any nonzero result accepts it.

Accepted references are appended to the primary output in source-index order. Neither a zero candidate nor a rejected candidate consumes an output position. Companion processing, when enabled and eligible, occurs before the current accepted reference is stored.

After enumeration, the `0xF60` field is read again from the same saved base address. Its current value is passed to F-0b8b101e723b. The earlier field value is not reused, and the base-producing dependency is not called again.

### Companion eligibility

Companion processing maintains an unsigned 32-bit source cursor, initially zero, and a 32-bit threshold, initially `0xFFFFFFFF`.

For every accepted candidate with companion construction enabled, the source table’s count word is read anew. That value is saved for this candidate’s selection process; it is not repeatedly fetched during cursor advancement.

Selection occurs only if:

- The cursor is below the saved count under unsigned comparison.
- The threshold, interpreted as signed 32-bit, is no greater than the current source index interpreted as signed 32-bit.

The initial threshold therefore acts as −1. A nonempty source table permits selection at the first accepted candidate regardless of the first entry’s boundary.

A rejected or zero candidate triggers neither this source-count read nor companion selection.

### Cursor advancement and boundary reads

Once selection is eligible, advancement checks the current cursor against the saved count **before** incrementing it. If the cursor is below the count, it advances by one and then unconditionally reads the boundary at that incremented cursor. That boundary is compared unsigned with the current source index.

If the boundary is no greater than the source index, advancement repeats, beginning with another cursor-versus-count check. Otherwise, advancement stops.

This ordering has a material storage consequence: when advancement reaches the saved count, the function still reads the boundary for entry index equal to that count. It does not first establish that the incremented cursor names a declared entry. A table providing only its declared entries therefore does not establish that this access is valid.

After advancement:

- If the cursor differs from the saved count, its boundary is read again and saved as the next threshold. This is a separate read from the advancement comparison.
- The cursor is decremented once to identify the selected entry.
- If advancement reached the count, the threshold becomes `0x7FFFFFFF` during the subsequent emission sequence.

With stable storage, ordered boundaries, ordinary nonwrapping indexing, and valid access to the boundary beyond the declared entries, selection chooses the entry immediately before the first later boundary exceeding the current source index, or the final declared entry if advancement exhausts the count.

Only one companion entry is emitted per eligible accepted candidate. Advancing across several source entries does not emit them individually.

### Companion emission and access ordering

For a selected entry, the output operations have the following established ordering:

1. The signed output count is read and captured for locating the next two destination writes.
2. The selected source boundary is loaded.
3. The selected source opaque value is read and copied to the first destination word located using the captured output count.
4. The previously loaded boundary is written to the second destination word located using that same captured count.
5. If source advancement exhausted the saved count, the threshold is set to `0x7FFFFFFF`.
6. The output count is read again to locate a destination second word. The current retained-candidate count is written there.
7. The output count is read again, incremented, and stored back into the count word.

The retained-candidate count in step 6 is the primary-array position about to receive the current accepted candidate.

When the preceding writes preserve the output count and relevant storage, step 6 overwrites the boundary written in step 4, replacing it with the compacted position. Without those conditions, it need not target the same entry. In particular, writes aliasing the count word can change the later destination and the value subsequently incremented.

The selected boundary is loaded before the opaque-value copy. Thus an opaque-value destination that aliases the selected boundary does not change the boundary value already captured for step 4. Other aliasing effects remain possible.

After companion emission, the accepted candidate is written to its primary-array position and the retained-candidate count advances.

### Publication

After F-0b8b101e723b returns, successful construction publishes three fields, in order:

1. Primary output address at `0xEEC`.
2. Companion output address, or zero when disabled, at `0xEF0`.
3. Retained-candidate count at `0xEF4`.

The function returns zero.

It does not recheck the cache before publication. No atomic publication, constructor exclusion, or concurrent-reader safety follows from this sequence.

### Arithmetic and storage boundaries

The first storage request is exactly four times an unsigned 16-bit count, ranging from zero through 262,140. The captured enumeration count is at most 65,535; enumerated indices are therefore at most 65,534, and the retained count cannot exceed 65,535 through ordinary enumeration.

Source cursor, saved source count, and source word-index expressions use unsigned 32-bit arithmetic. Multiplication by two and addition of one or two wrap modulo \(2^{32}\). For unrestricted source counts, an entry’s calculated word index can therefore wrap and cease to correspond to the simple mathematical layout above.

For example, a cursor of `0x80000000` gives a boundary word index of 2 after unsigned wrapping. This describes the index expression, not a separately established rule for every subsequent address calculation.

With nonwrapping indices, reaching a declared count *n* reads word `2n + 2`: the boundary of entry *n*, beyond entries zero through *n*−1. Validity requires accessible storage for that actual read; an assumed allocation of exactly one count word plus *n* pairs is insufficient.

Output count, doubled output indices, their additions, and count increment are signed expressions. Overflow behavior is not established by the supplied representation. This contract does not assign them unsigned wrapping semantics. The ordinary append interpretation requires values and calculations within the signed range and valid resulting destinations.

Boundary comparisons also differ by phase: advancement compares boundaries unsigned, whereas eligibility interprets the saved threshold as signed. A boundary with its high bit set must not be treated as a large positive threshold in both places.

## Side effects

Explicit effects include dependency calls, output-storage writes, and successful publication of three context fields.

There is no explicit deallocation, no initialization of unused primary elements, and no initialization of unused companion entries beyond the count word. A nonzero companion output address may accompany a zero emitted count.

No store is explicitly directed through the source-table address. This does not establish source immutability when output storage or context fields overlap it.

Publishing output addresses does not establish ownership transfer, allocator compatibility, candidate retention, or eventual release responsibility. Dependencies may modify reachable state, including context fields and tables; no preservation guarantee is assumed.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless qualified, they require normally returning dependencies, stable input contents, sufficient storage, non-overlap, and arithmetic within the ordinary indexing ranges.

### Existing cache

If the primary cache field is nonzero after F-8ff48652068d returns, the result is zero. No construction dependency or explicit cache-field write follows. The initial dependency still occurs.

### Preparation failures

If descriptor acquisition returns zero, the result is `0xFFFFFFCE`, with no storage-preparation or enumeration-bracketing calls.

If the first candidate count is 12, F-f195b74c9758 receives 48. If it returns zero, the result is `0xFFFFFF94`; mode selection does not occur.

If companion preparation returns zero after primary preparation succeeded, the result is `0xFFFFFF94`. The function neither explicitly releases the primary output nor publishes it.

### Candidate filtering

For four enumerated indices producing, respectively, accepted A, zero, rejected B, and accepted C, the initialized primary prefix is A followed by C. The published retained count is two. The predicate is not called for the zero candidate.

### Companion remapping

Suppose a three-entry source table has boundaries 0, 3, and 6, with accepted candidates only at indices 1, 4, and 7. Also provide valid storage for the boundary read at entry index 3.

The three opaque source values are emitted in order with compacted positions 0, 1, and 2. Selection at index 7 reads the boundary beyond the declared entries before selecting the final declared entry.

If the first accepted candidate is instead index 7, only the final source entry is emitted, at compacted position zero. Earlier entries are skipped, not emitted as empty groups.

### Declared entries alone

A source table declaring one entry and providing storage only for its count and that pair does not satisfy the access precondition for first selection. Advancement attempts to read the boundary at entry index 1, word offset 4, before selecting entry zero. No return-value behavior for an invalid access is established.

### Empty enumeration

If the second candidate count is zero and preparation succeeds, both bracketing dependencies are still called, but no candidate or predicate calls occur. The published retained count is zero. Primary preparation is attempted even when its requested size is zero.
