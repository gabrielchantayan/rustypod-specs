# F-808c5d99c3bd

## Purpose

F-808c5d99c3bd conditionally processes a numbered entry in a caller-supplied state object. Depending on object flags, processing either decrements an entry-associated reference count or immediately marks the entry with a fixed 32-bit value and adds an entry-associated quantity to an object accumulator.

The function also accepts an entry number of zero. After the initial dependency and object eligibility checks succeed, zero returns success without accessing an entry or modifying the object directly.

The established behavior is narrower than a general release, deletion, or deallocation operation. The visible body changes counters and a marker; it does not directly free memory. The meanings of the marker, accumulator, flags, and entry data are not established.

## Interface

### Inputs

The function accepts two values:

- **Object address:** a 32-bit address-like value identifying a writable state object and, when required by the selected path, indirectly referenced storage.
- **Entry number:** a signed 32-bit integer. Zero selects the no-entry path. Positive values identify entries starting at one. Negative values are rejected, but only after the initial dependency and eligibility checks.

The supplied representation uses 32-bit integer values to carry both addresses and ordinary numeric data. It does not establish a portable interface for wider addresses.

### Output

The function returns a 32-bit value:

| Result | Bit pattern | Signed 32-bit interpretation |
|---|---:|---:|
| Success | `0x00000000` | 0 |
| Rejection | `0xFFFFFFCE` | −50 |

The same rejection value covers all visible explicit failure conditions. No separate error classification or error-reporting write is shown.

Success does not necessarily mean that an entry was marked. It can mean that the entry number was zero, that a reference count was decremented but remained nonzero, or that marking and accumulation occurred.

### Object layout

Offsets are byte offsets from the object address. The visible accesses have the following layout:

| Offset | Width | Observed role |
|---|---:|---|
| `+0x04` | 32 bits | Flags; bits `0x40` and `0x01` affect behavior |
| `+0x08` | 32-bit address | Address of a cell containing the entry-table base address |
| `+0x0C` | 32-bit address | Address of a cell containing the reference-count-table base address |
| `+0x1C` | Signed 32 bits | Upper bound for positive entry numbers |
| `+0x30` | 32 bits | Eligibility field that must equal zero |
| `+0x34` | 32 bits | Accumulator updated when an entry is marked |

Both table bases use two levels of reading from the object: the object field supplies an address, and the cell at that address supplies the table base. The object fields are not themselves treated as direct table bases.

For a positive entry number \(n\):

- The reference-count slot occupies four bytes beginning at reference-count-table base plus \(4(n-1)\).
- The entry occupies eight bytes beginning at entry-table base plus \(8(n-1)\).
- The entry’s first four bytes receive the marker `0x80000001`.
- The entry’s second four bytes supply the quantity added to the accumulator.

No other object fields or entry bytes are directly accessed in the visible body.

## Behavior

### Initial dependency and eligibility

The first observable operation in the visible body is a call to F-0aff6a5050f5, with no explicit arguments.

If that dependency returns zero, F-808c5d99c3bd returns the rejection value. No direct object read or write by this function precedes that return.

If the dependency returns nonzero, the function reads the 32-bit field at object offset `+0x30`.

- A nonzero value causes rejection.
- A zero value permits a read of the flags at `+0x04`.

When flags are read, bit `0x40` must be clear. If it is set, the function returns rejection.

These checks precede all interpretation of the entry number. Consequently, entry number zero does not bypass the dependency, the `+0x30` check, or the `0x40` flag check.

Any dependency-induced changes to accessible state can affect the object values subsequently read. The supplied evidence does not establish that the dependency preserves globals, pointed-to memory, or ownership.

### Entry-number handling

Once eligibility succeeds:

- Entry number zero returns success immediately.
- A negative entry number returns rejection.
- A positive entry number causes a signed 32-bit read of the bound at `+0x1C`.
- A positive entry number greater than that bound returns rejection.
- A positive entry number equal to the bound is accepted for processing.

The bound is not read for zero or negative entry numbers. A zero or negative bound admits no positive entry number.

No direct object write occurs on these rejection paths.

### Reference-count decision

For an accepted positive entry number, bit `0x01` of the previously read flags selects the next action.

**Bit clear:** the function skips the reference-count table entirely and proceeds directly to entry marking and accumulation.

**Bit set:** the function resolves the reference-count-table base through the address at `+0x0C`, reads the selected four-byte counter, subtracts one, and writes the result back to the same slot. It then tests the resulting value for equality with zero.

- A zero result proceeds to entry marking and accumulation.
- A nonzero result returns success without directly accessing the entry table or accumulator.

The zero test uses the decremented value. There is no visible pre-decrement check requiring a positive count, and no special rejection for zero or negative counts.

For example, a starting count of zero becomes −1 under ordinary signed 32-bit arithmetic and does not trigger marking. Negative counts whose decrement is representable likewise remain nonzero and do not trigger marking.

### Entry marking and accumulation

When marking is selected, the function resolves the entry-table base through the address at `+0x08` and locates the eight-byte entry for the accepted entry number.

The visible data-dependent operation is:

1. Read the object accumulator and the entry’s second 32-bit word.
2. Add those values and write the result to the accumulator at `+0x34`.
3. Write `0x80000001` to the entry’s first 32-bit word.
4. Return success.

The accumulator write precedes the marker write in the supplied body. The supplied representation does not establish which of the two addition operands is read first.

If the reference-count path was taken, its counter write occurs before the entry-table access and accumulator update.

The function does not first read or validate the entry’s existing marker. It also does not clear the entry’s second word. Thus, where the flags select immediate marking, repeated successful calls can add the same entry-associated quantity repeatedly.

### Direct access ordering

The established branch-dependent order is:

- Dependency call before direct object access.
- `+0x30` read before flags read.
- Flags eligibility check before entry-number validation.
- Positive-entry bound check before either table is accessed.
- Counter decrement and write, when selected, before the marking path.
- Accumulator write before marker write.

An exact physical load/store trace, compiler reordering constraints, and concurrency guarantees are not established.

## Side effects

Direct writes are limited to:

- One selected reference-count slot, when flag bit `0x01` is set and a positive entry number passes validation.
- The accumulator at `+0x34`, when marking is selected.
- The first word of the selected eight-byte entry, when marking is selected.

The function visibly performs no allocation, deallocation, pointer clearing, table resizing, bound adjustment, or flag update.

There is no visible rollback. In particular, a reference-count write precedes later accesses on the marking path. The body does not provide a recovery mechanism if a later access faults.

The supplied source does not require the object, pointer cells, and tables to occupy disjoint storage. If they alias, earlier writes can affect later reads. The ordinary interpretation of separate object fields and tables therefore requires a non-aliasing precondition where that interpretation matters.

Ownership transfer is not established. Neither the marker write nor the accumulator update proves that memory has been released.

All statements about “no writes” on rejection describe this function’s direct operations. They do not exclude side effects of F-0aff6a5050f5.
