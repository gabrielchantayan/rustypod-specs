# F-319098183eb7

## Purpose

F-319098183eb7 traverses a globally selected linked collection using a two-word search record, conditionally selects an entry, and checks that selection through an opaque dependency. If the final check permits continuation, the function compares an associated byte against the full unsigned second input. A difference causes a low-byte write followed by two ordered indirect calls.

On normal completion, the function returns 1 when the final check permits the byte operation and 0 when that check rejects it. Return value 1 does not distinguish an unchanged byte from an executed write and notification sequence.

**Established static evidence:** linked traversal, dependency-controlled selection, two checks involving addresses of local storage, a byte comparison and conditional write, and two indirect calls.

**Inferred intent:** collection lookup, end-marker checks, and change notifications. The application meanings of the collection, byte, and indirect calls are not established.

## Behavior

### Three ordered initialization reads

Initialization reads the global context location three separate times, with distinct uses:

1. **First global read:** retain its value as the saved context address.
2. **Second global read:** use this newly read context address to load its field at offset 0x10, then read that header’s field at offset 0x04 as the initial traversal node.
3. **Third global read:** use this newly read context address to load its field at offset 0x10 as the initial candidate.

The second and third lookups do not use the saved context address. No immutability or synchronization contract establishes that the three global reads return the same value.

Consequently, the saved comparison context, initial traversal tree, and initial candidate can originate from different context objects. Subsequent comparison-context addresses and subsequent context-field reads use the saved context from the first read. The visible function does not read the global context location again after these three initialization reads.

After these reads, the function initializes the two-word local search record from the inputs.

### Traversal

Traversal continues while the current node address is nonzero.

For each node, F-bcefa5957e76 receives, in argument order:

1. The saved context address plus 0x19.
2. The current node address plus 0x10.
3. The local search-record address.

Only zero versus nonzero is inspected.

- **Zero result:** read the node’s link at offset 0x08. That link becomes both the next traversal node and the candidate.
- **Nonzero result:** read the node’s link at offset 0x0c. That link becomes the next traversal node; the candidate remains unchanged.

The link read occurs after the dependency returns. If the dependency changes the relevant node storage, the subsequent read can observe that change.

The zero branch saves the followed link, not the node from which it was read. A zero link therefore sets both traversal state and candidate to zero. This must not be replaced by a conventional tree-search rule that remembers the current node.

No comparison relation is established. Zero and nonzero must not be equated with equality, less-than, or greater-than without a separate dependency contract.

A cycle can prevent termination. The function provides no traversal bound or cycle detection.

### First candidate check

After traversal ends, the function:

- Reads the field at offset 0x10 of the saved context into a local header snapshot.
- Copies the candidate into separate local candidate storage.
- Calls F-f063d8ade9f7 with the addresses of that candidate storage and the header snapshot.

Both local values are exposed by address. Their preservation is not established.

If the check returns nonzero, selection proceeds to the fallback path.

If it returns zero:

1. F-539f08165386 receives the value currently in candidate storage.
2. Its returned word becomes an operand to F-bcefa5957e76.
3. That comparison receives the saved context plus 0x19, the search-record address, and the returned operand, in that order.
4. A zero comparison result selects the value currently in candidate storage.

The search record is the second argument in this comparison, whereas it is the third argument during traversal.

Selection does not necessarily use the candidate’s pre-check value. The first check receives its storage address, and no preservation guarantee is supplied. Nor is preservation across subsequent dependency calls established.

If either the first check or the subsequent comparison returns nonzero, the fallback selection is a fresh read of the saved context’s field at offset 0x10. It is not necessarily the earlier header snapshot or the initial candidate.

### Final entry check

The selected value is copied into separate local entry storage. The function then obtains another fresh snapshot of the saved context’s field at offset 0x10.

F-f063d8ade9f7 receives the addresses of the entry storage and this new snapshot.

- **Nonzero result:** return 0, without performing the associated-byte operation or notification sequence.
- **Zero result:** continue using the entry value currently present in entry storage.

The entry used for subsequent dereferences is therefore the post-call value, not necessarily the value supplied before the check.

It is inferred that this dependency checks an entry against an end marker. Its actual semantics are unknown. In particular, selecting the fallback header does not by itself establish that the final check rejects it.

### Byte comparison and write

After a zero final-check result, the function reads the associated-object address from entry offset 0x14 and then reads its byte at offset 0x64.

The byte is interpreted as a value from 0 through 255 and compared against the full unsigned 32-bit second input.

If equal, the function returns 1 without a byte write, provider call, or indirect notification call.

If unequal:

1. Read the associated-object address again from entry offset 0x14.
2. Write the low eight bits of the original second input to that object’s byte at offset 0x64.
3. Execute the notification sequence.
4. Return 1 if execution reaches the normal return.

The repeated associated-object read is part of the visible behavior. It is not replaced by reuse of the first address. In the absence of a concurrency or mutation contract, the byte read and byte write are not guaranteed to address the same object.

The stored value is the original second input modulo 256. Truncation occurs for storage, not before comparison. Thus every second input above 255 takes the write path after an accepting final check, regardless of whether its low byte already equals the observed byte.

### Notification sequence

After the byte write, F-9d0ecc5f6adf is called without explicit arguments. Its returned value is retained as the receiver for both indirect calls.

Each call uses the target found through the receiver’s dispatch-table pointer and slot at byte offset 0x58. Each receives:

1. The retained receiver.
2. A selector loaded from a global location.
3. The current first word of the local search record.

The first call uses one selector location. After that call returns, the second call uses a distinct selector location.

The dispatch-table pointer and slot are read again for the second call. The second call can therefore target a different implementation if the first call or another permitted mutation changes dispatch state.

The search-record word is also supplied separately for each call. If an earlier dependency retained access to that storage and it is changed before the second call’s argument is obtained, the two calls need not receive the same word.

The source establishes the order of the two calls, but not a required evaluation order between the selector load, search-record load, and dispatch-target loads within an individual call.

The indirect-call return values are ignored. No notification-success status is incorporated into the function’s result.

## Acceptance examples

These are conditional static expectations, not executed tests. Each assumes valid memory, the specified dependency outcomes, and normal completion unless stated otherwise.

1. **Distinct initialization contexts.**  
   Suppose the three global reads return contexts A, B, and C respectively. Traversal starts from the header obtained through B; the initial candidate comes from C. Comparison-context addresses and later header snapshots use A. The contract must not collapse these into one context.

2. **Accepted entry with unchanged byte.**

3. **Accepted entry with changed byte.**

4. **Equal low byte does not suppress writing.**

5. **Maximum second input.**  
   With second input 4,294,967,295, every possible observed byte compares unequal. The written byte is 255.

6. **Final rejection.**  
   A nonzero final F-f063d8ade9f7 result produces return 0. This function then performs no associated-byte access or notification sequence, regardless of earlier dependency side effects.

7. **Zero branch reaches a zero link.**  
   A zero traversal comparison followed by a zero link at offset 0x08 makes the candidate zero. The first check receives that value through local storage. Safe rejection is conditional on dependency behavior, not guaranteed here.

8. **Search-record mutation.**  
   If a comparator changes the first search-record word, later indirect calls use its then-current value. Changing the second search-record word alone does not change the original second input used for byte comparison and storage.

9. **Final check changes the entry.**  
   If the final check replaces the entry value and returns zero, subsequent associated-object access uses the replacement entry.

10. **First call changes dispatch.**
