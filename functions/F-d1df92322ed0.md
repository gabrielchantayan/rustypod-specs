# F-d1df92322ed0

## Purpose

F-d1df92322ed0 conditionally detaches a selected node from a linked structure, repairs selected links and color-like state, prepends the detached node to a container-maintained chain, decrements a 32-bit counter, and writes a 32-bit result to caller-provided storage.

The structure is consistent with a red–black tree containing a header, cached extrema, and a detached-node chain. These meanings are inferred. The contract preserves the visible operations rather than substituting a conventional tree-deletion algorithm, particularly for missing replacement children and repair-dependency dispatch.

All evidence is static. No runtime tests have been performed.

No separate return value is established. The explicit output is the final four-byte destination write.

Pointer-bearing fields are 32-bit words. The representation does not establish compatibility with native 64-bit pointers. All offsets below are byte offsets.

## Behavior

### Initial calls and branch decision

The function reads the selection word first, then the header address at container offset 16. It places these values in separate temporary 32-bit words and calls F-73b7871d4f8c with their addresses, selection temporary first.

Only zero versus nonzero in the dependency’s integer result affects control flow.

For a nonzero result, the function re-reads the container’s header address and uses that value as its result word. It skips its own structural removal, chain insertion, and counter decrement, then writes the result destination. This path is not necessarily side-effect-free: the dependency has already executed.

For a zero result, F-ec352f140c12 receives the address of the selection-derived temporary. After that call, the original selection address is read again. This new read identifies the node to remove; neither the initial snapshot nor the temporary’s current contents determine that node.

The selection-derived temporary remains the result source on the removal path. Consequently, the output word and detached node address need not match. Their relationship depends on dependency effects and changes to selection storage.

### Structural case selection

The selected node’s left link is read first. When it is absent, the right link determines whether removal concerns a leaf or a one-child node. When the left link is present, the right link distinguishes a one-child node from a two-child node.

For two children, traversal begins at the right child and follows left links until a node without a left child is reached. This node is the structural successor. Its right link supplies the prospective replacement at its former position.

Several link tests visibly re-read fields. The contract does not replace repeated reads with a single immutable snapshot.

### Leaf removal

The selected node’s parent becomes the repair candidate.

If that parent equals the current header address, the function performs these writes in order:

1. Header right extreme becomes the parent/header address.
2. Header left extreme becomes that address.
3. Header root becomes zero.

Otherwise, the parent’s left link is compared with the selected node. Equality selects the parent’s left-child field for clearing; inequality selects its right-child field, without independently checking that the right link names the selected node.

The chosen parent child-link field is cleared through four ordered byte writes at increasing offsets. This is not established as one atomic 32-bit store.

The function then examines the corresponding cached extreme: left for the left-link case, right otherwise. If that cache names the selected node, it becomes the parent address.

The selected node’s own parent field at offset 4 is not explicitly cleared. The selected node remains the detached node.

### One-child replacement

The surviving child first receives the selected node’s parent link.

The function compares the selected node with the current header root. If equal, the root becomes the surviving child. Otherwise, it reads the selected node’s parent and redirects that parent’s left link when it matches the selected node, or its right link otherwise.

Cached extrema are maintained afterward, left before right:

- If the selected node is the cached left extreme, an absent selected-node right child makes the new cache its parent. Otherwise, the replacement subtree is traversed through left links to find the new left extreme.
- If the selected node is the cached right extreme, an absent selected-node left child makes the new cache its parent. Otherwise, the replacement subtree is traversed through right links to find the new right extreme.

The surviving child is the repair candidate. The originally selected node is detached.

### Two-child successor relocation

The successor object moves into the selected node’s structural position. The selected node remains the object eventually chained; payload copying is not performed.

The principal write order is:

1. The selected node’s left child receives the successor as parent.
2. The successor receives the selected node’s left link.
3. The successor’s former position is repaired.
4. The header root or selected node’s parent child-link is redirected to the successor.
5. The successor receives the selected node’s parent link.
6. The successor and selected node exchange color bytes.

When the successor is the selected node’s immediate right child, its right link remains in place. If that right child is nonzero, the child receives the successor as parent.

For a deeper successor, a nonzero successor right child first receives the successor’s old parent. The old parent’s left link is then replaced by that child address, including zero when absent. Next, the successor receives the selected node’s right link, and that right subtree’s root receives the successor as parent.

Root redirection tests the header root. Non-root redirection chooses the selected node’s parent left link if it matches, and the right link otherwise. This path performs no explicit cached-extreme updates.

A nonzero successor right child becomes the repair candidate. If that child is absent, the relocated successor itself becomes the candidate. This is not a conventional absent-child candidate with a separately saved parent.

After the color exchange, the detached node holds the successor’s former color.

### Repair eligibility and termination

Repair is entered only if the candidate differs from the currently read header address and the detached node’s color byte is nonzero. A zero detached color skips repair. Entry does not require that color to equal one.

At each repair-loop entry, the current header root is compared with the candidate. A candidate equal to the root terminates repair without requiring a candidate-color read for that test. Otherwise, a candidate color other than exactly one terminates repair.

Every repair termination path writes color one to the current candidate. Skipping repair altogether does not perform this final recoloring.

For a continuing iteration, the candidate’s parent is read. Equality between the candidate and the parent’s left link selects the left-candidate branch. Any other relationship selects the opposite branch.

### Repair cases and exact dependency dispatch

For a left candidate, the sibling is the parent’s right child; the near child is the sibling’s left child and the far child is its right child. For the opposite branch, sibling, near, and far directions are reversed.

| Repair case | Candidate equals parent’s left child | Opposite branch |
|---|---|---|
| Sibling color is zero | F-ba7d9afb55b3, with container and parent value visibly supplied | F-cd5e6c93f84c, with container and parent value visibly supplied |
| Inner restructuring | F-cd5e6c93f84c, with only container visibly supplied | F-ba7d9afb55b3, with only container visibly supplied |
| Terminal restructuring | F-ba7d9afb55b3, with container and parent value visibly supplied | F-cd5e6c93f84c, with container and parent value visibly supplied |

These branch-to-dependency relationships are established independently of uncertainty about the dependency implementations or complete calling conventions.

**Absent sibling.** If the sibling is absent initially, or becomes absent after the zero-color-sibling call and link refresh, the current candidate is colored zero. The candidate becomes the parent, and repair repeats.

**Zero-color sibling.** A present sibling with color zero is first colored one, then the parent is colored zero. The corresponding two-visible-argument dependency in the table is called. The candidate’s parent and the sibling link are re-read afterward.

**Both sibling children absent or color one.** The near child is examined first. If it is absent or has color exactly one, the far child is examined. If both satisfy that condition, the sibling becomes color zero, the candidate becomes its current parent, and repair repeats. This path does not explicitly recolor the former candidate.

**Inner restructuring.** When propagation did not apply, the far child is checked again. If absent or color one, a present near child is colored one, the sibling becomes zero, and the listed one-visible-argument dependency is called. The sibling is then re-read through the candidate’s current parent. If it is now absent, repair terminates and the candidate becomes color one; it does not use absent-sibling propagation.

**Terminal restructuring.** The sibling receives the parent’s current color, the parent becomes one, and a present far child becomes one. The listed two-visible-argument dependency is called, then repair terminates by writing one to the candidate.

Child links and color bytes are re-read in some tests, including the far-child test. Dependency calls therefore cannot be modeled as leaving a previously observed shape unchanged.

Zero, exactly one, and other byte values have distinct effects. “Zero is red, one is black” is an inferred interpretation, not a license to treat every nonzero value identically.

### Chain insertion and completion

After structural work and any repair, the function:

1. Reads the current chain head from container offset 4.
2. Writes that word to the detached node’s offset 12.
3. Writes the detached node address to container offset 4.
4. Reads the 32-bit counter at offset 20, subtracts one, and writes it back.
5. Writes the result-carrying temporary to the result destination.

The detached node’s parent and left links are not explicitly cleared. Its right-link field becomes the chain link.

The counter is represented as signed 32-bit arithmetic, without a guard, saturation, or underflow handler. Zero becomes negative one, represented by all bits set on the represented machine. Portable behavior when subtracting one from signed minimum is not established; boundary wraparound remains documented_only.

## Side effects

Direct writes can affect header links, node links and color bytes, the chain head, the counter, and the result destination. Dependencies may have additional effects not established here.

No direct allocation, memory release, payload destruction, logging, or explicit error result is visible. Chaining records the node address; it does not prove allocator ownership transfer or continued allocation.

No atomicity, locking, rollback, or exception guarantee is established. Intermediate states include partially cleared parent links, partially relocated successors, and chain insertion before counter decrement. An invalid access or nonlocal dependency exit can prevent completion after earlier writes.

Repeated header and link reads remain significant. The function does not promise that one initial header snapshot governs all subsequent accesses.

## Acceptance examples

These are conditional static expectations, not executed tests. Each assumes normal dependency returns and sufficient accessible storage.

1. **Early result.** If F-73b7871d4f8c returns nonzero, the result is the header address re-read afterward. F-ec352f140c12 is not called. This function does not perform removal, chaining, or counter decrement.

2. **Selection changes.** If selection storage changes before its post-F-ec352f140c12 read, the newly read address identifies the removal node. The output still comes from the separate temporary.

3. **Singleton leaf.** If the leaf’s parent equals the header, header right extreme becomes the header, then left extreme becomes the header, then root becomes zero. Repair is skipped when the candidate still equals the header. Chaining and decrement follow.

4. **Non-root zero-color leaf.** If the parent’s left link names the leaf, that parent child-link is cleared through four byte writes. Otherwise, the parent’s right-child field is cleared. The applicable extreme is conditionally updated. Repair is skipped. The leaf’s own parent field is not explicitly cleared; its offset-12 field receives the former chain head.

5. **One-child root.** The child receives the selected node’s parent and becomes the header root. If repair is entered and dependencies have not changed that relationship, the root test immediately terminates repair and colors the child one.

6. **Immediate successor.** A right child without a left child relocates into the selected node’s position. The selected node, not the successor, is chained. Their colors are exchanged before repair eligibility is determined.

7. **Deeper successor without right child.** The successor’s old parent left link becomes zero. The relocated successor becomes the repair candidate. Acceptance must not substitute a null-child repair model.

8. **Left-candidate dispatch.** A zero-color right sibling triggers F-ba7d9afb55b3 with two visible arguments. A reached inner restructuring triggers F-cd5e6c93f84c with only container visibly supplied. A reached terminal restructuring uses F-ba7d9afb55b3 with two visible arguments.

9. **Opposite-side dispatch.** A zero-color left sibling and terminal restructuring use F-cd5e6c93f84c with two visible arguments. Inner restructuring uses F-ba7d9afb55b3 with only container visibly supplied.

10. **Unexpected candidate color.** If repair is entered with a non-root candidate whose color is two, its color test terminates repair and writes one without a repair dependency call.

11. **Zero counter.** If completion reaches the decrement with counter zero, negative one is written before the result destination. No zero guard prevents this.
