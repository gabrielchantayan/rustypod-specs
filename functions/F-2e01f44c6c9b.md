# F-2e01f44c6c9b

## Purpose

Construct and publish a dynamically allocated descriptor with a 20-byte header and 24-byte records. Each record receives a copied identifier/reference, three numeric fields, and two classification-related fields. A conditional second pass replaces the middle numeric field.

**Established static behavior:** preparation and allocation each have a checked status point. Passing both checks permits construction and eventual publication. Publication is not guarded by a final status check; the function returns the status location’s then-current value.

**Inferred intent:** the numeric scaling and classification annotations suggest an axis-description structure with 16.16-style numeric values. This interpretation does not establish valid input ranges, identifier semantics, ownership, or category encodings.

## Interface

### Arguments and accessible memory

The function accepts:

1. A 32-bit object address.
2. A 32-bit address of a writable four-byte output location.

Before invoking any dependency, it reads these object fields, in order:

| Object-relative byte offset | Four-byte value |
|---|---|
| 100 | Allocator/context value |
| 524 | Address of a secondary-state structure |

Both values are captured. Later changes to these object fields do not cause this invocation to recapture them. The contents of the captured secondary-state structure are read later, however, and are not snapshotted at entry.

The secondary-state accesses are:

| Byte offset | Use |
|---|---|
| 0 | Value tested by the replacement predicate |
| 4 | Value whose low eight bits provide the shift count |
| 88 + 12 × record index | Address passed to conditional conversion |
| 140 | Four-byte argument passed to conditional preparation |

The function does not initialize or clear the caller’s output location on entry.

### Preparation storage

F-c8ea3798e9f0 receives the object address and an address into local storage. Subsequent operations consume that storage as follows:

| Offset from supplied address | Consumed data |
|---|---|
| 0 | Unsigned 32-bit count |
| 4 | Additional four-byte header value |
| 8 onward | Three-word input records, 12 bytes each |

The visible local input-record area contains twelve four-byte words: space for four triplets. Each triplet supplies an identifier/reference and two signed 32-bit endpoints.

The caller does not validate the count against this capacity. The dependency’s write extent, initialization guarantees, and maximum-count contract are **documented_only**.

### Descriptor layout

The allocation request uses the count read at allocation time:

\[
S=(20+24n_{\mathrm{allocation}})\bmod 2^{32}.
\]

No overflow or capacity check is shown.

The five four-byte header fields are:

| Byte offset | Explicit initialization |
|---|---|
| 0 | Current preparation count, read after allocation |
| 4 | Current additional preparation value |
| 8 | `0xFFFFFFFF` |
| 12 | Allocation address plus 20 |
| 16 | Zero |

The count stored in the header need not equal the count used to calculate the allocation size if a dependency changes the preparation storage between those reads.

The inline record layout is:

| Record-relative byte offset | Explicit initialization or later use |
|---|---|
| 0 | Identifier/reference copied from an input triplet |
| 4 | First endpoint shifted left by 16 bits |
| 8 | Ordinary middle value; conditionally replaced |
| 12 | Second endpoint multiplied by 65536 |
| 16 | Classification field, initialized to `0xFFFFFFFF` |
| 20 | Additional field, initialized to `0xFFFFFFFF` |

Header offset 12 contains a four-byte address, not an allocation-relative offset. Record accesses use the current address read from this header field, rather than an established immutable record-area snapshot.

### Return value

The result is the signed 32-bit value held in the status location at return.

- Preparation’s return value is assigned to that location and checked.
- If it is zero, allocation receives the location’s address.
- The location is checked again after allocation.
- No later status check controls construction, replacement, or publication.

A nonzero preparation status causes an immediate return without allocation. A nonzero status after allocation prevents initialization and publication.

After both checks pass, zero is returned only if the status remains zero. The available dependency contracts do not exclude retained aliases or later changes to that location.

Nonzero status meanings are **documented_only**.

## Behavior

### Preparation and allocation

After capturing the two object fields, the function invokes F-c8ea3798e9f0 with the object address and preparation-storage address.

If the returned status is nonzero, no allocation, descriptor initialization, classification, replacement predicate, or output publication occurs.

Otherwise, the function reads the current unsigned count, calculates the 32-bit allocation size, and invokes F-3ce007b692cc with:

- The captured allocator/context value.
- The calculated byte count.
- The status location’s address.

Continuation depends solely on the status read after this call. There is no independent null-address check. Zero status must therefore be accompanied by storage suitable for subsequent accesses for execution to proceed safely.

The preparation count is not established as immutable. Preparation has received its address, and the supplied contracts do not prohibit retained aliases. Allocation can therefore occur using one count while later initialization or traversal observes another.

### Header initialization

After the second status check passes, the function writes the header fields in increasing offset order: current count, current additional preparation value, all-one bits, inline-record address, and zero.

No allocation-wide clearing is shown. The header count is not subsequently used as the record-loop bound. Both loops consult the local preparation count.

### Initial record pass

The first pass starts with unsigned 32-bit index zero. Before each iteration, it compares that index with the then-current preparation count. After each completed iteration, the index increments by one.

The bound is reread; it is not an immutable allocation-time or header-time count. A dependency called during an iteration can therefore affect whether a later iteration occurs.

For each visited index, explicit initialization proceeds in this order:

1. Read the corresponding input identifier/reference and write record offset 0.
2. Read the first endpoint, shift it left by 16 bits, and write offset 4.
3. Read the second endpoint, multiply it by 65536, and write offset 12.
4. Read the stored first scaled endpoint, add the second endpoint’s scaled value, divide the signed sum by two, and write offset 8.
5. Write `0xFFFFFFFF` at offset 20.
6. Write `0xFFFFFFFF` at offset 16.
7. Perform classification.

The middle calculation uses the scaled endpoints. It is not established as an unscaled average followed by scaling. Where the signed operations are defined and representable, division truncates toward zero.

The second endpoint’s value used for the middle calculation is the value already read for that iteration. The first scaled value is read back from record memory.

### Classification calls and global reads

The classification dependency’s opaque ID is unavailable. Each invocation receives:

- The identifier/reference read from offset 0 of the current record destination.
- A designated label address.

A zero result selects that category. The three label positions are associated by annotations with “Weight,” “Width,” and “OpticalSize”; the annotations do not establish their exact bytes or comparison semantics.

For each visited record, the observable sequence is:

| Stage | Call, then unconditional read | Continuation |
|---|---|---|
| First | Compare against the first label; immediately afterward read the first four-byte global category constant | If comparison returned zero, select that loaded constant; otherwise continue |
| Second | Compare against the second label; immediately afterward read the second four-byte global category constant | If comparison returned zero, select that loaded constant; otherwise continue |
| Third | Compare against the third label; immediately afterward read the third four-byte global category constant | If comparison returned zero, select that loaded constant; otherwise make no classification replacement |

Each constant read occurs regardless of its immediately preceding comparison result. Thus an all-nonmatching record causes three comparison calls and all three global constant reads.

A first match prevents the second and third calls and their constant reads. A second match prevents the third call and its constant read.

The constants are read after the corresponding calls, not before them. A comparison dependency that modifies a category global can therefore affect the value subsequently selected. The second label address is four bytes after the first constant’s location; the third label address is four bytes after the second constant’s location. Exact contents remain unresolved.

If a category is selected, the function writes the loaded constant to offset 16 using the record-area address read for that store. Each comparison also obtains its identifier/reference through the record-area address used at that point. A dependency-induced header change can redirect later accesses within the same iteration.

If all comparisons are nonzero, this function performs no classification replacement. That does not guarantee that offset 16 still contains `0xFFFFFFFF`: a dependency may have modified the record or redirected its address.

### Conditional replacement pass

After the first pass terminates, the function evaluates the predicate using the captured secondary-state address:

- Read the word at offset 0.
- Compare it with one shifted left by the low eight bits of the word at offset 4.

The supplied representation establishes these operand accesses but does not establish an ordering between their two reads.

For shift counts 0 through 30, the comparison is against \(2^{\text{count}}\). Count 31 and larger counts have unresolved signed-shift behavior. The eight-bit extraction is not an explicit five-bit shift-count mask.

If the predicate is false, no replacement preparation or conversion is invoked. This does not establish that earlier dependencies preserved the ordinary middle values.

If the predicate is true:

1. Read secondary-state offset 140.
2. Invoke F-7685ee6e4fba with that value and a four-word local result area.
3. Start a second unsigned-index traversal at zero.
4. Before each iteration, compare the index with the current preparation count.
5. Invoke F-540f73b4639f with the address at secondary-state offset \(88+12i\) and word \(i\) of the local result area.
6. Write its four-byte return value to record offset 8, using the record-area address read after the call.

The conditional preparation result is not checked. Each conversion result is stored without status interpretation, range checking, or comparison with the ordinary middle value.

Conditional preparation runs whenever the predicate is true, even if the count was zero when the first pass ended. Because the second loop reads the count afterward, conditional preparation can change a previously zero count and cause conversions.

Conversely, later calls can reduce or increase subsequent loop bounds. Counts exceeding four can exceed either visible local array’s capacity.

### Publication

After the optional replacement pass, the function writes the original allocation address to the caller’s output location. It then returns the status location’s current value.

There is no final status check. Publication can therefore occur even when a later dependency has changed the status to a nonzero value.

## Side effects

The function explicitly writes the allocated descriptor and, on completion, the output location. Dependencies receive addresses into local storage and may write through those addresses.

There are no explicit writes to the object or secondary-state structure. This is not a preservation guarantee: dependency effects on aliased memory, globals, descriptor contents, preparation storage, or status storage are unknown.

The function shows no release, reference-count adjustment, identifier duplication, or destruction operation. Copying an identifier/reference does not establish ownership or extend the referenced entity’s lifetime. Publishing the allocation does not establish the caller’s release obligation or release API.

Only the two checked status points provide explicit error exits. There is no visible recovery for invalid addresses, excessive counts, uninitialized dependency outputs, arithmetic outside supported ranges, or dependency-level abnormal termination. No release is shown if execution fails after allocation but before publication.

Safe execution requires valid memory for every actual access, including accesses selected by changing counts and record-area addresses. The caller performs no independent validation of these conditions.

## Acceptance examples

These are conditional requirements derived from static evidence, not observed executions.

### Checked failures

If preparation returns a nonzero status, return that status without allocation or explicit output publication.

If preparation returns zero but allocation leaves a nonzero status at its check, return that status without initializing the returned address or explicitly publishing it.

These statements concern this function’s writes; they do not exclude dependency writes through aliases.

### Stable one-record construction

Assume valid storage, normal completion, defined arithmetic, a count fixed at one, endpoints fixed at 2 and 6, and dependencies that preserve relevant preparation data, status, header fields, and record contents except for specified outputs. Assume the replacement predicate is false.

Then:

- The allocation request is 44 bytes.
- The header count is one.
- Numeric offsets 4, 8, and 12 contain 131072, 262144, and 393216 respectively.
- Publication follows classification.
- The returned status is zero.

Without those preservation assumptions, these are not guaranteed final field values.

### Classification sequencing

If a record’s first comparison returns zero, the first category global is still read after that call. Its loaded value is written to the classification destination, and later comparisons are skipped.

If all comparisons return nonzero, all three constants are nevertheless read, each after its corresponding call. This function makes no classification replacement. Retention of the initial all-one value requires dependencies to preserve that field and its addressing.

### Replacement

Assume the predicate observes secondary-state value 8 and shift count 3. It selects conditional preparation.

With a stable count of one and valid initialized conditional output, one conversion occurs. Its return value is explicitly written to offset 8 at the record destination selected after that conversion. The ordinary middle value imposes no constraint on the replacement.

### Zero count and changing count

With a count that remains zero, allocation requests 20 bytes, the header is initialized, and neither record loop has an iteration. The predicate is still evaluated. If true, conditional preparation still runs.

If conditional preparation changes the count from zero to one, the second pass can perform one conversion despite the first pass having performed no initialization. Safe execution then requires adequate allocation, valid destination addressing, and initialized conversion inputs; the function supplies no capacity correction.

### Publication with changed status

Assume both checked statuses are zero. If a later dependency changes the exposed status location to a nonzero value and execution otherwise completes, the function still publishes the allocation address and returns that nonzero value.

### Excessive count

A count of five has no visible rejection path. It exceeds the visible four-triplet preparation capacity and four-word conditional-result capacity. Safe successful construction is not an acceptance guarantee.

Numeric construction instead uses signed left shift, signed multiplication, signed addition, and signed division. The conditional predicate likewise does not establish behavior for shift counts outside 0–30.

Dependency-driven count changes can invalidate allocation-size assumptions or local-array bounds. Such changes are not shown to occur, but they cannot be excluded by the supplied contracts.
