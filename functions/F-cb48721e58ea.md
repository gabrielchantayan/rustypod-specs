# F-cb48721e58ea

## Purpose

F-cb48721e58ea initializes a caller-supplied, three-word descriptor, obtains a storage address from F-871e64ddc6de, and traverses a requested number of positions spaced 16 bytes apart. At each position whose address is nonzero, it invokes F-d6cd7ca5aac9 with that address and an opaque caller-supplied value.

The descriptor ultimately contains a base address and two computed endpoint addresses. The storage request uses at least 32 positions, but traversal uses exactly the caller’s requested count.

**Inferred intent:** The descriptor resembles a contiguous collection with base, logical-end, and capacity-end fields. F-871e64ddc6de appears allocation-like, and F-d6cd7ca5aac9 appears initialization-like. Those interpretations are not established contracts of the dependencies.

**Established limitation:** This function does not check that the returned address denotes usable storage, detect size overflow, or provide an explicit failure result. A zero storage address does not generally prevent subsequent dependency calls.

## Interface

### Inputs

The function receives three arguments:

| Argument | Representation | Required interpretation |
|---|---|---|
| Descriptor address | Address of at least three consecutive writable 32-bit words | Destination for initialization and final endpoint values |
| Requested count | Unsigned 32-bit integer | Number of traversal positions |
| Opaque value | 32-bit value | Forwarded unchanged to each invocation of F-d6cd7ca5aac9 |

The descriptor occupies 12 bytes:

| Byte offset | Width | Meaning on ordinary completion |
|---|---:|---|
| 0 | 32 bits | Base-address word, initially set from the return of F-871e64ddc6de |
| 4 | 32 bits | Logical-end address, computed using the requested count |
| 8 | 32 bits | Capacity-end address, computed using the selected capacity |

“Base-address word” does not imply that this word remains equal to the dependency’s original return value throughout execution. The function rereads it when constructing the endpoint fields.

### Return value

On ordinary completion, the function returns the same descriptor address supplied by the caller. It does not return the storage address directly and does not return a separate success indicator.

### Preconditions and representation

The descriptor address must support the three initial 32-bit stores. A null, unmapped, read-only, or otherwise invalid descriptor address is not handled.

The supplied representation uses 32-bit address-valued words and 32-bit integer arithmetic. Address calculations below describe the resulting 32-bit bit patterns. Conversion of such a pattern to a usable memory address remains subject to the execution environment.

Successful traversal additionally requires whatever address validity, alignment, storage, and opaque-value conditions F-d6cd7ca5aac9 imposes. Those conditions are unknown. In particular, the nonzero-address test is not a storage-validity check.

No initialization requirement is imposed on the descriptor’s previous contents: all three words are overwritten before either dependency is invoked.

## Behavior

### Initial descriptor reset

The first observable descriptor writes occur in this order:

1. Store zero at byte offset 0.
2. Store zero at byte offset 4.
3. Store zero at byte offset 8.

The prior field values are not read. No release operation is performed on any address that the descriptor previously contained.

Consequently, reusing a descriptor that already refers to owned storage may discard that reference without releasing its resources. Whether such reuse is valid is a caller-level ownership question, not something this function checks.

### Capacity selection and storage request

The selected capacity is the greater of 32 and the unsigned requested count.

The function calls F-871e64ddc6de once with:

- First argument: selected capacity multiplied by 16, retaining the low 32 bits.
- Second argument: zero.

The capacity comparison occurs before multiplication. The storage-request size is not a widened mathematical product.

For requested counts from 0 through 31, the selected capacity is 32 and the request size is 512 bytes. At a requested count of 32, the same 512-byte request is made. Above 32, the requested count itself determines capacity, subject to 32-bit multiplication wraparound.

The dependency’s returned 32-bit address word is stored at descriptor offset 0. This store occurs after the dependency returns and before any traversal callback.

The same returned word also establishes the first traversal address. The traversal address is subsequently advanced independently of the descriptor’s base field.

### Traversal and callback conditions

Traversal considers exactly as many positions as the unsigned requested count, provided execution continues normally. A count of zero produces no calls to F-d6cd7ca5aac9.

For each position, in increasing position order:

- If the current 32-bit traversal address is nonzero, call F-d6cd7ca5aac9 with that address as its first argument and the opaque input value as its second argument.
- If the current address is zero, omit that call.
- Advance the traversal address by 16, using the resulting 32-bit address pattern.

The callback’s return value is not used. There is no visible callback-result test, early exit, retry, or rollback.

Skipping a zero address does not terminate traversal. In particular, a zero result from F-871e64ddc6de skips only the initial position. With a requested count of at least two, the next considered address is 16 and is passed to F-d6cd7ca5aac9.

Address wraparound can also produce a zero traversal address after nonzero positions. That position is skipped, and traversal continues.

The callback address sequence is determined by the original storage-return address and successive 16-byte increments. Changing the descriptor’s base word during a callback does not redirect the remaining traversal.

### Final endpoint writes

After traversal completes, the function writes the endpoint fields in this order:

1. Read the current base word at descriptor offset 0, add the selected capacity multiplied by 16, and store the low 32-bit result at descriptor offset 8.
2. Read the base word again, add the requested count multiplied by 16, and store the low 32-bit result at descriptor offset 4.

Thus, the capacity endpoint is written before the logical endpoint, despite residing at the higher offset.

The endpoint calculations use the descriptor’s base word as it exists after traversal, not necessarily the address originally returned by F-871e64ddc6de. If a dependency changes that word through an accessible alias, final endpoints reflect the changed value.

There is no dependency call between the two final endpoint writes. Under ordinary single-threaded execution with an ordinary, non-overlapping three-word descriptor, both calculations therefore use the same final base value. Concurrent mutation, special memory semantics, and aliasing with dependency-managed state are not resolved by the available evidence.

### Arithmetic boundaries

All size and endpoint calculations must account for 32-bit truncation:

- Capacity remains at least 32 as an unsigned count.
- Capacity multiplied by 16 need not represent a nonzero or sufficiently large byte request.
- Requested count multiplied by 16 can wrap independently of whether traversal completes.
- Adding an offset to a base address can wrap to a numerically smaller address.
- Numerical ordering of the three descriptor words is not guaranteed.

For example, a requested count of 268,435,456 selects that same capacity, but multiplying it by 16 produces zero in 32 bits. The function still requests traversal of 268,435,456 positions if dependencies and the environment allow execution to continue.

The implementation does not establish an invariant that all traversed positions lie within the storage returned by F-871e64ddc6de.

## Side effects

### Descriptor mutation

The function performs these explicit descriptor writes on ordinary completion:

- Three zero stores before the storage dependency call.
- One store of the storage dependency’s result into the base field.
- One capacity-end store after traversal.
- One logical-end store after the capacity-end store.

During traversal, the function itself does not update either endpoint field. Unless dependencies change them, both remain zero until the final writes.

A callback with access to the descriptor can therefore observe a populated base field alongside zero endpoint fields. That is an intermediate state, not a completed descriptor.

### Dependency effects

F-871e64ddc6de may obtain storage or have other effects; its full contract is unknown. F-d6cd7ca5aac9 may modify the addressed region or other accessible state; its full contract is likewise unknown.

No assumption is made that either dependency preserves globals, preserves descriptor contents accessible through aliases, acquires ownership, or releases memory.

### Ownership and failure handling

This function contains no explicit storage-release action, either for the descriptor’s previous contents or for the newly returned address. It contains no visible cleanup path.

No explicit error value is produced for:

- A zero storage-return address.
- An overflowed storage-request size.
- A wrapped endpoint.
- A callback failure reported through its return value.

Faults, nonlocal exits, or other abnormal dependency behavior can interrupt execution before final endpoint writes or before the descriptor address is returned. The function does not provide a visible recovery mechanism.

If the storage dependency fails to return normally, the descriptor’s three reset stores have already occurred. If a traversal callback fails to return normally, the original storage result has already been stored, but final endpoint construction has not yet occurred; dependency-induced changes may also be present.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, assume dependencies return normally, the descriptor remains writable, arithmetic has the specified 32-bit behavior, and dependencies do not mutate the descriptor.

### Zero requested positions

Given a requested count of zero and a storage return of `0x00001000`:

- The storage request is 512 bytes with second argument zero.
- No traversal callbacks occur.
- The final descriptor contains base `0x00001000`, logical end `0x00001000`, and capacity end `0x00001200`.
- The returned value is the descriptor address.

The zero count does not suppress the storage dependency call.

### Count below the minimum capacity

Given a requested count of two and a storage return of `0x00001000`:

- The storage request remains 512 bytes.
- Callback addresses, in order, are `0x00001000` and `0x00001010`.
- Each callback receives the same opaque input value.
- Final logical end is `0x00001020`.
- Final capacity end is `0x00001200`.

### Count above the minimum capacity

Given a requested count of 33 and a storage return of `0x00001000`:

- The selected capacity is 33.
- The storage request is 528 bytes.
- Thirty-three nonzero callback positions occur, ending at `0x00001200`.
- Both final endpoint fields contain `0x00001210`.

### Zero storage return

Given a requested count of two and a storage return of zero:

- The position at address zero is skipped.
- The next callback is attempted at `0x00000010`.
- If that callback returns normally, the final base remains zero, logical end is `0x00000020`, and capacity end is `0x00000200`.

This example does not assert that address `0x00000010` is valid. It demonstrates that zero storage return is not handled as an immediate failure.

### Traversal wraparound

Given a requested count of two and a storage return of `0xFFFFFFF0`:

- The first callback address is `0xFFFFFFF0`.
- Advancing by 16 produces zero, so the second position is skipped.
- Final logical end is `0x00000010`.
- Final capacity end is `0x000001F0`.

### Descriptor mutation through a dependency

Given a requested count of two and an original storage return of `0x00001000`, suppose the first callback changes the descriptor base to `0x00002000` and no later operation changes it:

- The second callback still receives `0x00001010`.
- Final logical end is `0x00002020`.
- Final capacity end is `0x00002200`.

This distinguishes the independent traversal address from the reread descriptor base.
