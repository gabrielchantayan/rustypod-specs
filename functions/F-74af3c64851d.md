# F-74af3c64851d

## Purpose

F-74af3c64851d searches up to four dynamically selected objects in sequence order. For each attempted object, it invokes an indirect operation and tests the operation’s 32-bit result. A nonzero result ends the search.

On that successful path, the function rereads the current selection byte and returns the contents of the context slot selected by that fresh read. It does not necessarily return the object on which the successful operation ran.

An initial zero selector disables the search. Four zero operation results exhaust the search. Both paths return zero. A successful operation can also lead to a zero function result if the final slot load produces zero.

The apparent intent is a first-accepting-object search. That interpretation is inferred; the contract below describes the established accesses and decisions without assuming what the operation means.

## Interface

### Inputs

The function receives two values:

- **Context address:** a 32-bit address-bearing value used to locate a selector and indexed object-pointer slots.
- **Operation argument:** an uninterpreted 32-bit value passed unchanged as the second argument of each indirect invocation. Its meaning and signedness are unresolved.

The visible context layout is:

| Context-relative offset | Access width | Interpretation |
|---|---:|---|
| `0xC4` | 32 bits | Selector tested for zero and subsequently used in a table lookup |
| `0x38 + 4 × selection byte` | 32 bits | Object-pointer slot |

Selection bytes are unsigned 8-bit values. Their representable range is 0–255, giving slot starting offsets from `0x38` through `0x434`. The byte-to-offset calculation itself fits within 32 bits. Adding that offset to the context address still requires an address-arithmetic interpretation and accessible resulting storage.

No narrower selection-byte range is established. The layout does not prove that selector storage and indexed slots are disjoint: selection byte 35 identifies the slot at offset `0xC4`, which is also the selector location.

### Output

The function returns a 32-bit value:

- Zero if the first selector read is zero.
- Zero if all four indirect operations return zero.
- Otherwise, the contents of the context slot selected by a fresh read of the successful position’s selection byte.

The indirect operation’s result is used only for its zero/nonzero classification. Its numeric value is not returned.

The returned slot contents are not checked for zero, validity, object identity, or ownership. Consequently, a zero function result does not uniquely distinguish disabled search, exhausted search, and successful operation followed by a zero slot load.

### Path-dependent memory requirements

A normally completing execution requires each address actually accessed to be readable when that access occurs. This includes:

- The context selector for its initial read.
- On the nonzero-selector path, the global table-base value, the selector’s second read, and the selected 32-bit table entry.
- Each selection-byte address reached by the search.
- Each context slot selected for an attempt.
- Each attempted object’s first 32-bit word and the indirect-call entry at dispatch-table offset `0x14`.
- On success, the current selection-byte address again after the invocation, followed by the context slot selected by that reread.

A readable four-byte selection region is **not required on every execution**. Early success leaves later positions unread. Each reached byte must be readable at its actual access, and the successful position must remain or become readable for its post-invocation reread.

A four-byte region that remains readable at all relevant accesses is a sufficient selection-storage condition, but not a necessary one. It also does not establish the validity of slots, objects, dispatch tables, or call targets.

No explicit validation of these memory relationships is visible.

## Behavior

### Initial selector decision

The function first reads the 32-bit selector at context offset `0xC4`.

If that read produces zero, the function returns zero without consulting the search table, reading a selection byte, loading an object slot, or invoking an operation.

The selector read itself is not guarded by a context-address check. An invalid context does not have a defined recovery path in the supplied representation.

### Sequence-address lookup

If the first selector read is nonzero, the function obtains a sequence address through a global table-base value and a further read of the context selector.

The selected table entry is a 32-bit value at the address formed from:

- The table base.
- Four times the second selector value.
- A subtraction of four bytes.

For selector values and addresses for which this arithmetic is valid without overflow, selector 1 chooses the entry at the table base, selector 2 chooses the next four-byte entry, and so forth.

The initial zero test and this lookup are separate selector accesses. The function does not establish that both observe the same value. In particular, the initial nonzero decision is not a validation of the selector value subsequently used for indexing. If the second read yields zero, the displayed lookup expression identifies the entry four bytes before the table base, subject to the unresolved arithmetic and address model.

The representation does not establish the relative evaluation order of the global-base access and selector access within the lookup expression.

The sequence address is obtained once before any indirect invocation. The function does not repeat this lookup between attempts.

### Ordered attempts

The search reaches sequence positions 0, 1, 2, and 3 in that order, unless an earlier invocation returns nonzero or execution fails to return normally.

For each reached position, the established access relationships are:

1. Read one unsigned selection byte from that position.
2. Read the 32-bit context slot selected by the byte.
3. Use that slot’s contents as the attempted object address.
4. Read the object’s first 32-bit word as a dispatch-table address.
5. Read the indirect-call target at dispatch-table byte offset `0x14`.
6. Invoke that target with the attempted object as its first argument and the original operation argument as its second argument.
7. Test the invocation’s 32-bit result for zero.

The next position is attempted only after the current invocation returns zero.

The function does not preload the four selection bytes, cache object pointers across attempts, or deduplicate repeated selections. A later attempt performs its own byte, slot, and dispatch accesses after earlier invocations have completed.

### Successful return

A nonzero invocation result stops the search. The function then:

- Rereads the selection byte at the successful position, using the retained sequence address.
- Reads the context slot selected by that new byte value.
- Returns the slot contents without further validation or invocation.

Thus, the attempted object and returned value are distinct observations. They agree only when the relevant storage remains suitably unchanged.

The successful operation may change the current selection byte, replace the selected slot, or clear a slot. The return follows the fresh reads, not a saved copy of the attempted object.

The successful byte address must be readable again after the invocation. Readability before the invocation alone is insufficient. Likewise, the final slot must be readable at the return-path load, even if it differs from the slot used for the invocation.

No later sequence position is accessed by this search after success.

### Exhaustion

After a zero invocation result, the function advances to the next position. After the fourth zero result, it returns zero.

There is no success-path byte or slot reread following a zero result. Exhaustion does not access a fifth selection byte.

### Mutation across invocations

No preservation guarantees are established for the indirect operation.

Changes to a later selection byte can affect a later attempt. Changes to a context slot can change the object attempted at that position. Changes to an object’s dispatch information can change a later call target.

Changing the context selector, global table base, or selected table entry during an invocation does not cause this function to obtain another sequence address. The address already obtained remains the basis for subsequent sequence accesses. Changes to memory at that retained address can still affect those accesses.

These are consequences of the visible access structure, not guarantees about concurrent execution, memory visibility, or safe object lifetime.

### Widths and arithmetic

The supplied representation establishes:

- 32-bit inputs, selector accesses, table-entry accesses, object-slot accesses, dispatch-address values, indirect results, and function result.
- Unsigned 8-bit selection loads, widened before multiplication by four.
- Four ordered positions, numbered 0 through 3.
- No visible range check or explicit widening for selector multiplication and address additions.

The position counter does not approach its width limit during normal execution. Selection-byte scaling also remains bounded. Selector scaling and address addition have no equivalent established safety bound.

The selector is represented as a 32-bit integer. The initial condition accepts every nonzero value, not only positive values. Negative signed interpretations and overflowing arithmetic must not be assigned safe indexing or wraparound semantics without additional execution-model evidence.

## Side effects

### Direct effects

The visible body reads memory and performs indirect calls. It contains no explicit writes to the context, search table, selection storage, objects, or dispatch tables.

It contains no explicit allocation, release, reference-count adjustment, synchronization, diagnostic output, or error-reporting operation.

These observations concern the function’s own visible operations. They do not constrain the effects of its indirect dependencies.

### Indirect effects and state

An invocation returning zero may still modify memory or other observable state. The function provides no rollback before continuing to the next attempt.

An invocation returning nonzero may also modify state before the return-path reads. Such changes can determine the outward result.

No assumption is made that an invocation preserves globals, context contents, selection storage, object dispatch data, or memory ownership.

### Ownership and lifetime

The representation establishes no ownership transfer for either input or the returned value. It shows no explicit retention or release surrounding an invocation.

Every dereferenced address must remain accessible at its actual access for normal completion. In particular, post-invocation readability of the current selection byte and final context slot is a separate requirement from their earlier readability.

The function does not dereference the returned slot contents before returning them. Whether that value identifies a live object, a borrowed reference, or an owned reference is documented_only.

### Errors and abnormal completion

No explicit handling is shown for invalid addresses, inaccessible storage, invalid call targets, or indirect operations that fail to return normally.

Zero is an ordinary result of the visible control flow, not an established error code for invalid memory or failed dispatch. Fault handling, exception propagation, and nonlocal control flow are documented_only.

## Acceptance examples

These are conditional contract examples, not runtime observations. Each assumes that the addresses actually accessed are readable, the reached targets are callable, and the invocations return normally unless stated otherwise.

### Disabled search

If the first selector read is zero, the result is zero and no invocation occurs. Table storage, selection storage, and object slots need not be readable for this path because they are not accessed.

### First-position success with inaccessible later positions

Suppose the selected sequence address permits reading position 0, while positions 1–3 are inaccessible. If the first invocation returns nonzero, position 0 is readable again afterward, and the final selected slot is readable, the function returns that slot’s contents.

The inaccessible later positions do not prevent this path from completing: they are never accessed.

### Successful position loses readability

Suppose position 0 is readable for the first selection, but the invoked operation makes that address unreadable before returning nonzero.

The function still attempts to reread position 0. The earlier successful read does not satisfy the return path’s memory requirement. No ordinary return value or recovery behavior is established for the failed reread.

### Third-position success

For operation results zero, zero, and nonzero:

- Positions 0, 1, and 2 are attempted in order.
- Position 2 is reread after its invocation.
- Position 3 is not accessed.
- The return comes from the slot selected by the fresh position-2 byte.
- Effects of the first two invocations are not undone.

Position 3 need not be readable on this path.

### Four unsuccessful operations

For four zero results, exactly four invocations occur and the function returns zero. Each position must be readable when first reached. No successful-path reread and no fifth-byte access occurs.

### Repeated selection

If all reached selection bytes identify the same slot, that slot is loaded for each attempt. Earlier invocations may replace its contents, so repeated selection need not imply repeated calls on the same object.

### Successful operation redirects the return

If an invocation uses slot A, changes its current selection byte to identify slot B, and returns nonzero, the function returns the newly loaded contents of slot B. It does not invoke an operation on slot B as part of that success path.

If that load produces zero, the function returns zero despite the nonzero operation result.

### Earlier operation changes a later byte

If the first invocation changes position 1 and returns zero, the second attempt reads the changed byte. The four-byte sequence is not snapshotted before invocation begins.

Established static evidence consists solely of the supplied function representation:

- An initial 32-bit selector test and a separate selector access for table indexing.
- One sequence-address lookup before the attempts.
- Up to four ordered unsigned-byte selections.
- Four-byte context-slot indexing.
