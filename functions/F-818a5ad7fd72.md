# F-818a5ad7fd72

## Purpose

F-818a5ad7fd72 coordinates operations on three-component objects using a base descriptor, a mutable destination descriptor, a window parameter, two opaque operation arguments, and a control object.

**Established static behavior:** allocate and initialize scratch storage; validate two conditions; select either a three-component transfer path or a table-based processing path; invoke dependencies in a defined sequence; inspect dependency-produced scratch data; and release scratch on the normal success and checked-operation failure paths.

**Inferred intent:** the table-based path resembles windowed exponentiation. Its unary and combining operations have no independently established mathematical meaning.

The operation is not transactional. Dependency effects preceding failure are not reversed. Two validation exits omit release of the already allocated scratch object.

The function accepts six arguments:

| Destination descriptor | Pointer to three consecutive 32-bit component handles with the same layout. |

Pointer-bearing fields in the supplied representation are 32 bits. Replacing them with wider native-pointer fields would change the represented layouts.

There are no explicit null, alignment, readability, writability, or component-validity checks for caller descriptors. Valid storage is a path-dependent precondition wherever the function or a dependency accesses it. No general aliasing guarantee is established.

### Results

The result is a 32-bit value:

| Result | Condition |
|---|---|
| 4 | The initial 36-byte allocation returns null. |
| 0 | A selected processing path reaches its success exit. |
| 1 | A checked transfer or transformation dependency returns nonzero. |
| Loaded window-rejection word | Window validation rejects the supplied window. |
| Loaded control-rejection word | The control validator returns something other than exactly 1. |

The two rejection results are **loads from separate external 32-bit data words**, not established immutable constants. Their values are obtained at their respective rejection exits. Their numeric values, distinctness, and possible equality with 0, 1, or 4 are unknown.

For all checked transfer and transformation calls, zero alone means success. Every nonzero 32-bit status, including a high-bit-set status, produces the enclosing function’s result 1 rather than propagating the dependency status.

## Behavior

### Allocation and scratch initialization

Before validation, F-d33f6d597e5d receives the size 36.

A null result causes an immediate result of 4, without validation, processing, or release.

For a non-null result, the function performs these direct writes in order:

1. A zero 32-bit word at allocation offset 0.
2. A 32-bit pointer to allocation offset 8 at allocation offset 4.

The allocation therefore initially contains an 8-byte header and 28 bytes of inline backing storage. The backing bytes are not initialized by this function before dependency use.

### Validation and path selection

Window rejection occurs if the window is zero or its signed 32-bit interpretation exceeds 4. Thus:

- 1 through 4 pass.
- Zero and 5 through 2,147,483,647 fail.
- 2,147,483,648 through 4,294,967,295 pass this validation.

On rejection, the function reads the external window-rejection word and returns that loaded value. This read occurs **after allocation and scratch initialization**. No explicit release follows.

Otherwise, F-d72f047fba8b receives the control object. Exactly 1 is required. For any other result, the function reads the external control-rejection word and returns the loaded value without explicit release. That load occurs **after the validator returns**; the validator may have changed the word.

After successful validation, F-5395d095cd07 receives the control object. Exactly 1 selects the short path. Every other result selects the ordinary path; such a result is not independently an error.

### Short path

F-eee1239b9042 is called with these component-handle pairs, in order:

1. Destination component 0, base component 0.
2. Destination component 1, base component 1.
3. Destination component 2, base component 2.

Each later call requires a zero result from the preceding call. Three zero results lead to cleanup and result 0. The first nonzero result leads to cleanup and result 1.

The descriptor fields supplying each pair are read for that call. They are not established to be a snapshot taken before earlier dependencies execute. Relative evaluation order between the two argument-field reads within one call is unspecified by the representation.

Calling this operation a copy from the second argument to the first is inferred intent, not an established dependency contract.

### Ordinary-path temporary layout

The function initializes a 16-entry temporary table. Each entry is a 12-byte triple of 32-bit pointers to component descriptors.

There are three banks of component descriptors, each containing sixteen 8-byte descriptors. Every descriptor receives:

- A zero 32-bit field at offset 0.
- A 32-bit pointer at offset 4 to a 28-byte backing region.

The 48 backing regions occupy one contiguous 1,344-byte area. Entry spacing is 84 bytes; its three component regions begin at relative offsets 0, 28, and 56.

For each entry, direct initialization writes occur in this order:

1. The three zero header fields, in component order.
2. The three backing pointers, in component order.
3. The table’s three descriptor pointers, in component order.

The backing contents remain uninitialized by these writes.

The initialization index is unsigned 32-bit, starts at zero, and is compared unsigned with 16. After each iteration it is incremented using unsigned 32-bit arithmetic, then bit 16 is cleared. From this starting point and bound, the visited indices are exactly 0 through 15; the bit clearing does not alter those iterations.

All entries are initialized regardless of the window. Entry 0 receives no explicit subsequent population call in this function.

### Initial position and preparation

F-f7b210fb9ec5 receives the control object. Its result is used as a signed 32-bit value, from which one is subtracted to establish the initial position. No result validation precedes that subtraction. A result of −2,147,483,648 would require an unrepresentable signed subtraction; its behavior is not established.

Preparation then proceeds sequentially:

1. Three F-eee1239b9042 calls with destination and base components 0, 1, and 2.
2. Three F-eee1239b9042 calls with table entry 1 and base components 0, 1, and 2.
3. F-d35d9d726fb2 with operation argument B, table entry 2, the complete base descriptor, and operation argument A.
4. Formation of a signed 32-bit table bound by left-shifting signed 1 by the low eight bits of the window.
5. Construction of later table entries through F-897a6ddff8eb.

Each checked call must return zero before the next step occurs.

The construction index starts at unsigned 32-bit value 3. Its **signed 32-bit interpretation** is compared with the signed table bound. After each successful construction call, the unsigned index is incremented and bit 16 is cleared.

Each construction call receives, in order:

- Operation argument B.
- The current table entry.
- Operation argument A.
- The preceding table entry.
- The complete base descriptor.

For windows 1, 2, 3, and 4, the bounds are 2, 4, 8, and 16. Entry 2 is prepared even for window 1; later construction visits entries 3 through one below the bound.

These ordinary cases do not justify a general unbounded mathematical-loop interpretation. The masked index update can cycle back to zero after 65,535, and the table contains only sixteen entries. A larger construction bound can require invalid table addresses before any such cycle.

The shift also has independent limits: a count of 31 makes signed positive 1’s shifted result unrepresentable, and counts of 32 or greater exceed the represented width. No target-specific outcome is established for these cases.

### Full-window processing

Each full-window attempt derives a reduced position from the current position and the window.

The subtraction combines a signed 32-bit position with the unsigned 32-bit window. Under the represented mixed-width arithmetic, subtraction is unsigned 32-bit, modulo \(2^{32}\). Its result is then assigned to a signed 32-bit position. A result above 2,147,483,647 requires a signed conversion whose target-specific outcome is not independently supplied.

The actual boundary test adds signed 32-bit 1 to that assigned reduced position and compares the signed result with 1. If the comparison is less-than, processing transfers to the residual phase using the **previous current position**, not the reduced position.

This is equivalent to testing whether the reduced position is negative only when the assignment interpretation is established and the subsequent signed addition is defined. In particular, adding 1 to a reduced position of 2,147,483,647 is not representable as signed 32-bit arithmetic.

When the boundary permits a full window:

1. An unsigned 32-bit unary-operation index starts at zero.
2. Its signed interpretation is compared with the window’s signed interpretation.
3. Each iteration calls F-d35d9d726fb2 with operation argument B, the destination descriptor as both output and input, and operation argument A.
4. After each successful iteration, the unsigned index is incremented and bit 16 is cleared.

For windows 1 through 4, this produces exactly that many unary calls. For a high-bit-set window, the signed comparison initially compares zero against a negative value, so this unary loop has no iterations if reached. That fact does not establish safety of the surrounding processing.

After successful unary processing:

- F-eee1239b9042 receives scratch and the control object.
- F-347405e096bf receives scratch and the reduced position.
- Both must return zero.
- The function reads scratch’s current pointer field at offset 4 and obtains a 32-bit word through that pointer.
- It multiplies that word by a newly loaded external 32-bit multiplication word and passes the represented 32-bit product, followed by the table bound, to F-d7be9cfb4000.

The multiplication word is loaded **for every extraction call**, after the preceding dependencies. It must not be treated as cached or immutable. Its load’s relative evaluation order against the scratch-word load is not established.

The representation establishes a 32-bit multiplication operand/result path, not a wider mathematical product. Any signed-overflow interpretation of that multiplication remains unresolved.

After F-d7be9cfb4000 returns, the reduced position becomes the current position. Its ordinary return value is not checked. A secondary signed 32-bit result controls further processing:

- Zero skips combining and begins another full-window attempt.
- Nonzero supplies the table-entry selection for F-897a6ddff8eb.

That combining call receives operation argument B, the destination descriptor, operation argument A, the destination descriptor again, and the selected table-entry address. Zero continues processing; nonzero terminates with result 1 after cleanup.

No range check establishes that the secondary result denotes an entry in the 16-entry table. Invalid selection arithmetic, invalid addresses, or invalid dependency-visible storage are not converted into a defined checked failure.

### Residual processing

At the residual check, a signed current position below 1 means success.

For a positive position, the function:

1. Calls F-d35d9d726fb2 in place on the destination.
2. Calls F-eee1239b9042 with scratch and the control object.
3. Decrements the signed position by one.
4. Calls F-347405e096bf with scratch and that decremented position.
5. Re-reads scratch’s current pointer field and tests bit 0 of the referenced 32-bit word.

Each dependency in this sequence must return zero. Because the decrement occurs only for a positive signed position, that decrement itself is representable.

If bit 0 is clear, the residual check repeats. If set, F-897a6ddff8eb first receives operation argument B, the destination descriptor, operation argument A, the destination descriptor again, and the base descriptor. A zero result returns to the residual check; nonzero causes failure.

Residual processing does not load the external multiplication word or call F-d7be9cfb4000.

### Cleanup

Every normal success exit and every checked-operation failure exit calls F-5e3309c9d083 once with the original scratch allocation pointer. Its result is not used.

Allocation failure makes no release call. Both validation-rejection exits also omit release despite successful allocation.

No separate release of temporary table descriptors, backing regions, or dependency-attached storage is visible.

## Side effects

- **Destination mutation:** Dependencies receive destination component handles and later the complete descriptor. Unary calls explicitly alias their output and input descriptor arguments.
- **Partial progress:** Failed operations may leave earlier and current dependency effects visible. There is no rollback.
- **Fresh descriptor reads:** Later component calls can observe descriptor changes made by earlier dependencies.
- **Scratch mutation:** Dependencies may change scratch’s header, pointer, and referenced storage. Reads use the current pointer field, not an assumed original inline pointer.
- **External-word observations:** Rejection words are read only on their respective exits. The multiplication word is read anew at each full-window extraction. Unknown dependencies may change any of these words.
- **Temporary lifetime:** Table descriptors, pointer triples, and backing regions are invocation-local. Safe retention by dependencies is not established.
- **Ownership:** The function visibly requests one allocation and normally passes it to a release dependency. Allocation ownership and recursive release of attached storage are unknown.
- **Resource risk:** The two validation exits omit explicit release. Whether this constitutes a leak depends on the allocation dependency’s unknown ownership contract.
- **Global effects:** No dependency is assumed to preserve globals, external data words, or other reachable objects.

## Acceptance examples

These are conditional static expectations, not runtime test results. Any example reaching dependency-visible storage assumes that storage and its accesses are valid.

1. **Allocation failure:** A null allocation produces result 4. No scratch initialization, validation, or release follows.

2. **Rejected window:** With successful allocation and window 5, scratch initialization precedes the window-rejection-word load. The loaded value is returned without control validation or release.

3. **Changed rejection word:** If allocation changes the external window-rejection word, a later window rejection reads its then-current value, not a value captured before allocation.

4. **Control rejection:** If the validator changes the control-rejection word and returns 2, the subsequent rejection load observes that word after the validator. No explicit release follows.

5. **High-bit window on short path:** Window 2,147,483,648 passes validation. If classification selects the short path and all three component calls return zero, cleanup returns 0 without shift formation or table construction.

6. **Partial short-path failure:** If component calls return zero and then 7, no third call occurs. Scratch is released and result 1 is returned without rollback.

7. **Window 2 preparation:** Successful preparation constructs entry 2 through F-d35d9d726fb2 and entry 3 through F-897a6ddff8eb. No construction call for entry 4 occurs.

8. **Zero initial position:** If F-f7b210fb9ec5 returns 1 and the window is ordinary, successful preparation is followed by residual success without processing-loop transformations.

9. **Window 1, initial position 1:** One full-window unary operation precedes extraction at position zero. A zero secondary result skips combining. A nonzero result permits a defined combining path only if it selects a valid table address with valid dependency-visible storage. Under those preconditions and zero checked statuses, processing reaches cleanup and result 0. Successful statuses alone do not establish safety.

10. **Repeated extraction:** If preceding dependencies change the multiplication word between two full-window extractions, each extraction uses its own newly loaded word. No common multiplier is guaranteed.

11. **Residual set bit:** A set low bit after successful residual scratch processing causes a combining call with the base before the next residual check.

12. **High-bit failure status:** A checked result of 4,294,967,295 causes cleanup and result 1.
