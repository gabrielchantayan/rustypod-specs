# F-a886da7a3894

## Purpose

F-a886da7a3894 updates a record associated with an input object, conditionally inserts that record into a global singly linked list, and then performs a notification call and a conditional indirect call.

The established behavior is:

- Three dependency calls precede a direct write to the selected record.
- A nonzero record status causes an early return after that write.
- For a zero status, two preparation calls precede a delay-field read.
- A nonzero delay triggers a calculation and list insertion.
- Both the zero-delay path and the completed insertion path reach the notification and conditional dispatch stage.

Scheduling an inactive record is inferred intent. The factor of 1,000, a value-producing dependency, and comparator-directed insertion support that interpretation, but do not establish time units, a clock source, list ordering, or notification semantics.

This contract describes static evidence only. No runtime tests have been performed.

## Behavior

### Initialization and record selection

The function first reads the object’s record reference at offset 192 and passes that value to F-936a8728139d.

After that call returns, it reads the object’s record reference again. F-6904f7699031 receives this second record reference and a value from G-B. The supplied representation establishes both arguments, but does not require a particular relative evaluation order for their reads.

After F-6904f7699031 returns, the function reads the object’s record reference a third time. This third reference is retained for subsequent direct record operations.

F-936a8728139d is then called again. No explicit arguments are recoverable for this occurrence. The earlier call’s argument must not be assigned to this second call by assumption.

After the second F-936a8728139d call returns, the function:

1. Reads G-A and writes that value to offset 32 of the retained record.
2. Reads the retained record’s status at offset 28.
3. Returns immediately if that status is nonzero.

The offset-32 write therefore occurs even on the early-return path. The status observation occurs after that write, which matters if accessed storage aliases.

The retained record reference is not refreshed after the third object-field read. Later changes to the object’s record-reference field do not redirect this function’s subsequent direct record accesses.

### Preparation when status is zero

When the observed status is zero:

1. F-338d16f9ce72 is called with a value read from G-C.
2. F-add44d4e9aaa is called with the retained record reference.
3. The delay-like value at record offset 4 is read and retained.

The delay is therefore observed after both preparation calls. Those calls may change it.

There is no second status check after preparation. A dependency’s change to the status field does not itself prevent the subsequent delay-dependent path.

### Zero-delay path

If the captured delay is zero, the function skips the entire calculation and insertion block. In particular, it does not directly:

- Call F-U1.
- Read G-D to select head storage.
- Write record offset 8.
- Read G-E or write record offset 24.
- Read the list head or compare list candidates.
- Publish the record through a list link.
- Write status 1 or update the record’s next link.

Execution proceeds to final notification and conditional dispatch.

These exclusions concern direct operations in this function. They do not constrain dependencies’ effects on the same storage.

### Nonzero-delay calculation and head-storage selection

For a nonzero captured delay, the following order is established:

1. F-U1 is called, producing the value used in the calculation.
2. Immediately after that call returns, the function reads G-D and retains the resulting head-storage reference.
3. It writes the calculated value to record offset 8.
4. It reads G-E and writes that value to record offset 24.
5. It reads the current list head through the previously retained head-storage reference.

The calculation is:

**F-U1 result + captured delay × 1,000**

The delay operand is the value captured before F-U1. It is not reread after that call.

Selecting the head-storage reference and reading the head are separate observations. Selection occurs before both record writes; reading the selected storage occurs after both writes. The function does not reacquire the head-storage reference from G-D between these operations or during insertion.

This distinction is observable when storage aliases. For example, a record write that changes G-D does not replace the already retained head-storage reference. Conversely, a record write that changes the contents of the selected head storage affects the subsequent head read.

The calculation writes a four-byte field. The supplied representation uses signed-looking 32-bit arithmetic operands, but does not establish a portable overflow rule. The following are established:

- Zero is the only delay value excluded by the branch.
- Negative delay bit patterns are not explicitly rejected.
- No range check, clamp, or arithmetic-error branch is visible.
- The multiplication factor is exactly 1,000.

Wrapping, trapping, or other overflow consequences remain unresolved. The factor alone does not establish a conversion between particular time units.

### Comparator-directed insertion

Traversal begins with the head read through the retained head-storage reference and with no predecessor.

For each non-null candidate, F-0d70d6f9010c receives:

1. The address of the candidate’s field at byte offset 8.
2. The address of the retained record’s field at byte offset 8.
3. The third input argument.
4. The fourth input argument.
5. The additional value of unresolved origin.

A zero comparison result causes traversal to continue. The function reads that candidate’s next link at offset 0 after the comparison returns, then treats the candidate as the predecessor.

A nonzero comparison result stops traversal at the current candidate without advancing through its next link. Reaching a null candidate also stops traversal, without calling the comparison for that null candidate.

The comparison may modify memory; no preservation contract is available. In particular, a next-link modification made during a comparison returning zero can affect the immediately following traversal read.

Insertion performs these direct writes in order:

1. If there is no predecessor, write the retained record reference to the selected head-storage location. Otherwise, write it to the predecessor’s next link.
2. Write exactly 1 to the retained record’s status at offset 28.
3. Write the stopping candidate reference, possibly null, to the retained record’s next link at offset 0.

The record is thus published through the head or predecessor before its status and next link are updated. No atomic grouping of these writes is established.

The comparison contract is only “continue on zero; stop on nonzero.” Ascending order, descending order, equality handling, and stability are unknown.

### Final notification and conditional dispatch

After either the zero-delay path or completed insertion, the function calls F-5bcae2eff9a7 with a value read from G-F.

Only after that call returns does it inspect dispatch state:

1. It reads G-C to obtain a reference to storage.
2. It reads that storage to obtain an object reference.
3. If the object reference is null, it skips the indirect call.
4. Otherwise, it reads the referenced object’s first four-byte field.
5. If that field is zero, it skips the indirect call.
6. If that field is nonzero, it obtains the target through G-G and calls F-U2.

The null check applies to the object reference read through G-C, not to the storage reference supplied by G-C. The latter is dereferenced without a visible null check.

No explicit arguments to F-U2 are recoverable. Its result, if any, is not visibly used. The checks use post-notification state, not a snapshot retained from preparation.

## Side effects

### Direct writes and state transitions

Direct writes can affect:

- Record offset 32 before every status-based early return.
- Record offsets 8 and 24 on the nonzero-delay path.
- The selected list-head storage or a predecessor’s next link.
- Record offset 28, set to 1 during insertion.
- Record offset 0, set to the stopping candidate.

An already-nonzero status is not directly normalized. A zero-delay path performs no direct status update.

These are access-relative descriptions. Aliasing can cause a write nominally directed at one field to alter another observed role.

### Ownership and lifetime

No explicit allocation, deallocation, object copy, or reference-count operation is visible.

Insertion creates list reachability; it does not establish ownership transfer. Unknown dependencies must not be assumed to preserve globals, retain objects, release no memory, or leave references valid.

Safe completion requires every accessed object and storage location to remain valid at its actual access time. This includes retained references reused after dependency calls. There is no visible lifetime validation.

### Preconditions, errors, and concurrency

No explicit error result, exception handling, allocation-failure handling, or recovery path is established.

The object reference and its offset-192 field are used without validation. The retained record and selected head storage are also used without null or bounds checks. Traversed candidates must support the accessed fields. The final dispatch condition does not validate the indirect target.

For ordinary linked-list operation, a finite list that does not already contain the inserted record is an inferred operational precondition, not an enforced condition. A cycle whose comparisons keep returning zero may prevent termination. Existing membership or aliasing can produce self-links or other unexpected topology.

The dependency calls may provide synchronization, but that is not established. The visible insertion writes alone do not guarantee atomic publication, exclusion, reentrancy safety, or protection from concurrent observation.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless an example specifies mutation or aliasing, assume dependencies return normally, relevant storage remains valid and unchanged by them, and arithmetic is representable.

1. **Nonzero status.** With retained-record status 7, the three initial dependency calls occur and offset 32 is written. The function then returns without preparation, insertion, final notification, or indirect dispatch.

2. **Changing record selection.** If the first dependency changes the object’s record reference, F-6904f7699031 receives the second observed reference. If that call changes it again, subsequent direct record accesses use the third observed reference.

3. **Zero delay.** With status zero and delay zero after preparation, F-U1, head-storage selection, and traversal are skipped. F-5bcae2eff9a7 still runs, followed by the dispatch checks.

4. **Captured arithmetic operand.** With captured delay 3 and F-U1 result 20,000, offset 8 receives 23,000. An F-U1 change to the stored delay does not replace the captured operand.

5. **Head-storage selection before writes.** If G-D supplies head-storage reference H after F-U1 returns, H is retained before offsets 8 and 24 are written. If those writes change G-D through aliasing, the function still reads and, when applicable, updates H rather than reacquiring another head-storage reference.

6. **Head contents read after writes.** If either record write changes H’s contents through aliasing, traversal starts from the contents observed after both writes. Capturing H earlier does not capture its earlier contents.

7. **Empty list.** With a null head observed through H and nonzero delay, no comparison occurs. H receives the record reference, status is set to 1, and the record’s next link is set to null, in that order.

8. **Insert before the first candidate.** A nonzero first comparison result causes head replacement. The retained record’s next link becomes the stopping first candidate.

9. **Insert after one candidate.** If the first comparison returns zero and the second returns nonzero, the first candidate’s next link receives the record reference. Status is then set to 1, followed by the record’s next link being set to the second candidate.

10. **Comparison changes traversal.** If a comparison returns zero after changing its candidate’s next link, traversal follows the link read after that call, not a pre-call snapshot.

11. **Append.** If every comparison returns zero and traversal reaches null, insertion updates the last visited candidate’s next link and gives the retained record a null next link.

12. **Post-notification dispatch.** A null object reference read through G-C suppresses F-U2. A non-null object whose first field is zero also suppresses it. A non-null object with a nonzero first field reaches the indirect call through G-G.
