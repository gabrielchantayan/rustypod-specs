# F-06ed623de53f

## Purpose

F-06ed623de53f selects one of two allocation-shaped workflows using whether its first input is zero.

- A zero first input and a positive signed request select an allocation call, optional notifications, and conditional initialization of the first result byte.
- A nonzero first input and a positive signed request select an allocation call, three additional calls if the result is nonzero, and optional notifications.
- A nonpositive signed request returns zero without invoking any dependency, but still reads two global table references.

These are established static behaviors. “Allocation,” “source,” and “observer” are descriptive roles, not guarantees about dependency semantics. In particular, the nonzero-source workflow is consistent with replacement of existing storage, but copying, deallocation, and ownership transfer are not established.

All sequences below assume each preceding operation completes normally. No runtime tests have been performed.

## Interface

### Inputs

The function accepts five 32-bit inputs in this order:

| Input | Representation | Established use |
|---|---|---|
| Source | 32-bit word, compared with zero | Selects the workflow; forwarded to dependencies in the nonzero-source workflow. |
| Extent | Opaque 32-bit word | Forwarded unchanged to two dependencies after a nonzero allocation result in the nonzero-source workflow. |
| Requested | Signed 32-bit integer | Determines whether processing occurs; forwarded unchanged to allocation and observer dependencies; determines eligibility for a first-byte store. |
| Context A | Opaque 32-bit word | Forwarded to allocation and observer dependencies. |
| Context B | Opaque 32-bit word | Forwarded to allocation dependencies and zero-source observers, but not nonzero-source observers. |

Source is not dereferenced directly by this function. Extent is not validated, compared with Requested, or used directly for local memory access. Its units and signedness are unresolved.

### Result

The function returns a pointer-shaped value in the supplied 32-bit model:

- Zero when Requested is nonpositive.
- Otherwise, exactly the value returned by the selected allocation-shaped dependency.

Observer and processing return values do not replace this result. There is no separate status output.

A nonzero result is directly dereferenced only in the conditional first-byte initialization described below. The function alone establishes no capacity, alignment, lifetime, uniqueness, or ownership guarantee.

### Referenced state and layout

Two global references identify control tables. This contract calls them the **zero-source global reference** and **nonzero-source global reference**. A further global reference identifies a marker byte.

Accessed table fields are 32-bit words at these byte offsets:

| Offset | Zero-source table | Nonzero-source table |
|---|---|---|
| 0 | State word reset through a fresh global-reference read | Not directly accessed |
| 4 | State word conditionally reset through the captured reference | Not directly accessed |
| 12 | Required allocation callable | Required allocation callable |
| 24 | Not directly accessed | Required final successful-result callable |
| 40 | Optional observer callable | Not directly accessed |
| 44 | Not directly accessed | Optional observer callable |

These are accessed fields, not complete structure definitions. Contiguous storage covering every referenced field would extend through byte 43 for the zero-source table and byte 47 for the nonzero-source table. Individual paths need access only to the fields they actually use.

At entry, the function reads and captures:

1. The nonzero-source global reference.
2. The zero-source global reference.

It captures reference values, not copies of either table.

Two later operations depart from ordinary use of those captured references:

- The positive zero-source path resets offset 0 through a **fresh read** of the zero-source global reference.
- The nonzero-source pre-observer check and invocation each independently read the nonzero-source global reference.

All other table accesses described here use the appropriate entry-captured reference.

### Preconditions

For the selected path to execute normally:

- Accessed global-reference storage and table fields must be accessible with the required widths and permissions.
- Every invoked callable must be valid and accept the displayed argument sequence.
- A result receiving the marker store must designate at least one writable byte at the time of that store.
- Dependency-specific preconditions must hold.

Only observer fields receive explicit zero checks. A successful observer presence check does not establish that a later callable reload remains valid. The function supplies no synchronization, lifetime protection, or validation of callable signatures.

## Behavior

### Entry and nonpositive requests

The entry reads occur in a fixed order: nonzero-source global reference first, zero-source global reference second. Both precede workflow-specific processing, including the early return for a nonpositive request.

Requested is interpreted as signed 32-bit. When it is zero or negative:

- The result is zero.
- No dependency is called.
- No table field is directly reset.
- No marker-byte reference or marker byte is accessed.
- No result storage is accessed.

The entry reads do not themselves dereference either table. Consequently, this path requires readable storage for the two global references, but does not require accessible table fields merely because their reference values were captured.

A nonzero Source does not cause explicit disposal on this path.

### Positive request with zero Source

The observable sequence is:

1. Read the zero-source global reference again.
2. Store a 32-bit zero at offset 0 of the table designated by that fresh reference.
3. Read offset 40 of the entry-captured zero-source table to check observer presence.
4. If that checked field is nonzero:
   - Store a 32-bit zero at offset 4 of the captured table.
   - Read its offset-40 callable again and invoke it with zero, Requested, Context A, Context B.
5. Read offset 12 of the captured zero-source table and invoke that callable with Requested, Context A, Context B. Retain its pointer-shaped result.
6. Read offset 40 of the captured table again to check post-observer presence.
7. If that checked field is nonzero, reload the callable from that field and invoke it with the allocation result, Requested, Context A, Context B.
8. If the result is nonzero and Requested is greater than 2048, read the marker-byte reference, read the designated byte, and store that byte at the result address.
9. Return the allocation result.

The offset-0 reset does **not** necessarily target the captured table. If the zero-source global reference changes between entry capture and the fresh read, offset 0 is reset in the newly designated table, while offset 4, allocation, and observer accesses still use the captured table.

The initial observer presence check controls the offset-4 reset. If that check finds zero, this function does not directly reset offset 4. If it finds nonzero, the reset occurs before the observer callable is reloaded for invocation.

The allocation callable is read after the pre-observer returns. A pre-observer can therefore change the allocation target by modifying offset 12 of the captured table. Replacing only the global reference does not redirect this allocation lookup.

Pre- and post-observer presence are checked separately. A dependency can install, remove, or replace the captured table’s observer between them. Thus either notification can occur without the other, and their targets may differ. Within each notification, the checked callable is also reloaded for invocation; equivalence requires the field to remain unchanged between those accesses.

A zero allocation result is still supplied to an enabled post-observer. It suppresses the marker access and store, not the post-notification.

The marker store follows the post-observer. It can overwrite a byte previously written by that observer, and the observer is not guaranteed to see the final marker value. Any marker-reference or marker-byte changes made before the marker read can affect the stored byte.

### Positive request with nonzero Source

The observable sequence is:

1. Read the current nonzero-source global reference and inspect offset 44 of the table it designates.
2. If that observer presence check finds nonzero:
   - Independently reread the nonzero-source global reference.
   - Read offset 44 of the table designated by this second read.
   - Invoke that newly loaded callable with Source, zero, Requested, Context A.
3. Read offset 12 of the entry-captured nonzero-source table and invoke that callable with Requested, Context A, Context B.
4. If the allocation result is nonzero, invoke these dependencies in order:
   - F-D04 with result, Source, Extent.
   - F-80308ee0e93f with Source, Extent.
   - The callable read from offset 24 of the captured nonzero-source table, with Source.
5. Read offset 44 of the captured nonzero-source table to check post-observer presence.
6. If that field is nonzero, reload its callable and invoke it with Source, result, Requested, Context A.
7. Return the allocation result.

The pre-observer’s presence check and invocation do not share a captured current-global reference or a captured callable. If state changes between the two lookups, the invocation may use another table, another callable, or a zero or invalid target. There is no second presence check. A nonzero checked field therefore does not by itself guarantee a valid invocation.

The entry-captured nonzero-source table remains the basis for allocation, the offset-24 call, and the post-observer. Changing the global reference does not redirect those accesses. Changing fields within the captured table can affect targets read later.

The offset-24 callable is read only after F-D04 and F-80308ee0e93f return. Its value need not match its entry-time value.

When allocation returns zero, all three successful-result calls are skipped. The post-observer check still occurs, and an invoked post-observer receives zero as its second argument.

There is no direct marker access or result-byte initialization on this workflow, regardless of Requested.

### Widths and arithmetic

Requested’s signed range is −2,147,483,648 through 2,147,483,647. Values with the high bit set are negative here, not large positive allocation requests.

The marker decision uses 32-bit subtraction and signed-overflow information. On the reachable positive-request path, its effective condition is exactly:

- Result is nonzero; and
- Requested is strictly greater than 2048.

For positive signed Requested, subtracting 2048 ranges from −2047 through 2,147,481,599, so the reachable subtraction does not overflow signed 32-bit arithmetic. Requested equal to 2048 does not trigger the store; 2049 does.

This arithmetic does not adjust the allocation argument. Allocation receives Requested unchanged. Extent receives no corresponding range or capacity check.

## Side effects

### Direct writes

The function directly performs only these established writes:

| Condition | Write |
|---|---|
| Source is zero and Requested is positive | A 32-bit zero at offset 0 through the freshly read zero-source global reference. |
| Same workflow, initial observer presence check is nonzero | A 32-bit zero at offset 4 through the entry-captured zero-source reference. |
| Same workflow, result is nonzero and Requested exceeds 2048 | One marker byte at the result address, after any post-observer. |

The two state resets can target different tables. Their order is offset 0 first, then the initial observer check, then any offset-4 reset.

The nonzero-source workflow has no comparable direct table reset or result-byte store.

### Dependency effects, ownership, and failures

Dependency effects are unresolved. No called function is assumed to preserve globals, table contents, marker state, Source storage, or result storage.

The final successful-result dependency has a release-shaped signature, but actual release, invalidation, reference-count adjustment, and ownership transfer remain unknown. The function does not establish that:

- Result differs from Source.
- Extent fits within source or result storage.
- Source remains live when supplied to the post-observer.
- Result remains live when returned or when the marker store occurs.
- A zero allocation result leaves Source or global state unchanged.

There is no local retry, rollback, alternate result, or explicit result cleanup if a later dependency does not return normally. Later operations are conditional on all earlier accesses and calls completing normally.

## Dependencies

The following opaque IDs identify dependency roles. F-D01 through F-D05 are documentary labels, not resolved identities.

| ID | Established invocation |
|---|---|
| F-D01 | Callable at offset 12 of the selected captured table; receives Requested, Context A, Context B. Its result becomes this function’s result. |
| F-D02 | Zero-source observer at offset 40 of the captured table; receives zero or result, Requested, Context A, Context B. Return value unused. |
| F-D03 | Nonzero-source observer at offset 44; receives Source, zero or result, Requested, Context A. Pre-call lookup uses independent current-global reads; post-call lookup uses the captured table. Return value unused. |
| F-D04 | Unresolved external dependency; receives result, Source, Extent after a nonzero allocation result. Return value unused. |
| F-80308ee0e93f | Receives Source, Extent after F-D04. Return value unused. |
| F-D05 | Callable at offset 24 of the captured nonzero-source table; receives Source after the preceding two successful-result calls. Return value unused. |

Different tables or reloads may yield different targets for a single documentary role. No identity relationship between callable fields is established.

## Acceptance examples

These are conditional specifications, not executed tests. Unless stated otherwise, accessed storage is valid, relevant references remain stable, and dependencies return normally.

1. **Nonpositive request.** With Requested equal to zero or −1, either Source value produces zero. The nonzero-source global reference is read before the zero-source global reference. No table field is dereferenced or reset, and no dependency is called.

2. **Fresh reset target differs from captured table.** Entry captures zero-source table A. Before the positive zero-source reset, the global reference changes to table B. Offset 0 of B is reset. Observer checks, any offset-4 reset, and allocation use A. The function does not reset A’s offset 0 merely because A was captured.

3. **No zero-source observer.** With Requested equal to 128 and the captured observer field remaining zero, the fresh-reference offset-0 reset occurs, offset 4 is not directly reset, and allocation receives 128 and both context words. No marker store occurs.

4. **Marker boundary.** With zero Source and a nonzero allocation result, Requested equal to 2048 produces no direct result-byte store. Requested equal to 2049 produces a one-byte marker store after any post-observer.

5. **Failed large zero-source allocation.** With Requested equal to 4096 and allocation returning zero, an enabled post-observer receives zero. No marker reference or marker byte is read.

6. **Observer installed during allocation.** If the captured zero-source observer field is initially zero but allocation installs a callable there, no pre-observer runs and offset 4 is not reset. The installed callable receives the post-notification if it remains present.

7. **Nonzero-source pre-observer reload.** The presence check reads table A and finds a nonzero observer. Before invocation lookup, the global reference changes to table B. The invocation uses B’s offset-44 callable, not A’s checked callable. If B’s field is zero, the function attempts that target without another presence check.

8. **Captured allocation table survives global replacement.** Entry captures nonzero-source table A. A pre-observer changes the global reference to B without modifying A. Allocation, the successful-result offset-24 call, and the post-observer continue to use A.

9. **Successful nonzero-source allocation.** A nonzero result causes F-D04, F-80308ee0e93f, and F-D05 in that order, followed by any enabled post-observer. No marker store occurs, even when Requested exceeds 2048.

10. **Failed nonzero-source allocation.** A zero result skips F-D04, F-80308ee0e93f, and F-D05. An enabled post-observer receives Source, zero, Requested, Context A.

11. **Context forwarding.** Both allocation workflows receive Context B. F-D02 receives it; F-D03 does not.

## Uncertainties

The following remain **documented_only**:

- Allocation units, capacity, alignment, initialization, and failure semantics beyond the returned zero/nonzero distinction.
- Whether F-D04 copies memory, and what Extent measures.
- The effects of F-80308ee0e93f and whether F-D05 releases anything.
- Ownership and lifetime of Source, result, tables, and marker storage.
- Reentrancy, thread safety, synchronization, and stability between separate reads.
- Meanings of the reset state words and marker byte.
- Permitted aliasing among tables, globals, Source, result, and marker storage.
- Behavior after invalid memory access, invalid callable invocation, or abnormal dependency termination.
- Exact source-level types and calling-convention details beyond the displayed widths and argument sequences.

The inferred allocation-and-replacement intent does not resolve these unknowns.
