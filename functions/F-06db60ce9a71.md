# F-06db60ce9a71

## Purpose

F-06db60ce9a71 advances a state object by one 40-byte record, decrements a 32-bit count, and invokes an indirect operation associated with the original record. The operation is resolved through **two successive data reads**: the record’s first word supplies a pointer-slot address, and that slot supplies the callable pointer.

After the operation returns, the function examines the current state and may perform a boundary transition. That transition consumes one transition-stream word and calls two dependencies. A subsequent count read selects one of two installation paths:

- Nonzero count: obtain a four-word tuple and install it directly in the active descriptor.
- Zero count: obtain a four-word tuple, install it in a secondary descriptor, copy that descriptor into the active descriptor, and issue a final notification.

The 64-bit return is assembled from the first two words of the local tuple. It is not obtained by rereading the active descriptor.

**Inferred intent:** “record,” “boundary,” “transition stream,” “descriptor,” and “notification” describe structural roles. They do not establish domain semantics or ownership.

## Interface

### Inputs

The function receives:

1. A state-object address.
2. A 32-bit value used to initialize tuple word 1.
3. A 32-bit value used to initialize tuple word 2.
4. A 32-bit value used to initialize tuple word 3.

The supplied representation uses 32-bit words, including words interpreted as addresses.

### Record and pointer-slot layout

The entry value at state offset 0 identifies the original record. The function retains this address while advancing state offset 0 by 40 bytes.

Only the record’s first 32-bit word is explicitly read. That word is **not the callable pointer**. It is interpreted as the address of a readable pointer slot. Reading that slot yields the callable pointer.

The lookup therefore has three distinct stages:

1. Read the first word at the retained record address.
2. Interpret that value as a slot address and read the callable pointer from that slot.
3. Invoke the resulting target.

Both data reads occur after the initial state updates and local tuple initialization. Neither the record word nor the slot contents are prefetched before those updates.

### Local tuple and output

The function initializes a local tuple of four 32-bit words:

| Tuple word | Initial value |
|---|---|
| 0 | Original state-object address |
| 1 | Second input |
| 2 | Third input |
| 3 | Fourth input |

F-9e3528e6ab0e receives the tuple’s address on boundary paths and may modify its contents.

The return is a 64-bit concatenation:

- Bits 31–0: tuple word 0.
- Bits 63–32: tuple word 1.

This establishes bit placement, not memory byte order or sign extension. Tuple words 2 and 3 participate in descriptor installation but do not directly contribute return bits.

### Preconditions

For defined execution on the selected path:

- Each accessed state field must be readable or writable as required.
- The retained record address must support the first 32-bit read **at the time of lookup**, after the preceding writes.
- The value obtained from that read must identify a readable pointer slot.
- The value obtained from the slot must identify a callable target under the actual execution environment.
- Every dereferenced transition-stream address must designate readable storage.
- Dependencies must satisfy the actual calling convention and return normally for subsequent behavior to occur.

The function performs no visible validation of these conditions.

The visible arithmetic consists of a 40-byte record advance, a four-byte stream advance, and subtraction of one from a 32-bit count. Overflow and underflow are not checked. The supplied representation does not establish a portable overflow or address-wraparound contract; ordinary acceptance examples assume representable arithmetic.

An entry count of zero does not cause an early return. The decrement still occurs.

## Behavior

### Initial state updates

The function reads and retains the entry active record address from state offset 0.

It then performs these actions in order:

1. Writes the retained record address plus 40 bytes to state offset 0.
2. Reads the count at offset 32, subtracts one, and writes the result to offset 32.
3. Initializes the four-word local tuple from the original state address and the other three inputs.

The original state-object address remains the destination base for subsequent state accesses. Replacing tuple word 0 later does not redirect descriptor writes to that replacement address.

### Indirect-operation lookup and invocation

After the updates and tuple initialization, the function:

1. Reads the first 32-bit word of the retained original record.
2. Reads the callable pointer through the slot address supplied by that word.
3. Invokes the resulting target.

The lookup uses the original record address, not the newly advanced state value. However, it uses the record word and slot contents as they exist **after** the preceding writes.

This order matters when storage aliases:

- If the retained record’s first word overlaps a state field already written, the first lookup read observes the updated field.
- If the pointer slot overlaps such a field, the second lookup read observes the updated field.
- The function does not read the callable pointer directly from the record’s first word and does not cache either lookup value before advancing state.

The visible invocation supplies no explicit arguments. This does not establish the complete external calling convention or exclude access to registers, globals, or the updated state.

No ordinary callback return value is used to construct the final 64-bit return. An auxiliary post-call value appears in the boundary-decision setup; its limited relevance is described below.

### Boundary decision after the operation

The function rereads the count after the indirect operation returns. It does not use a saved decrement result.

If this first post-operation count read is nonzero, it samples:

1. The active address at offset 0.
2. The boundary address at offset 8.

It then reads the count again. A zero at this second read selects the boundary transition. Otherwise, the decision uses the comparison values established by the preceding setup.

With stable state across these reads, the condition is:

- Count zero: take the boundary transition.
- Count nonzero and active address equal to boundary address: take the boundary transition.
- Count nonzero and addresses unequal: return without a boundary transition.

If the first count read was zero, no active or boundary address is sampled during the setup. Instead, the comparison operands are zero and an auxiliary post-call value whose meaning is not established. Thus, if the first count read is zero but the second becomes nonzero, transition selection depends on that auxiliary value. The stable-state simplification must not be extended to this unstable case.

No synchronization, atomic snapshot, or concurrent-mutation protocol is visible.

Without a boundary transition, no named dependency is called. Under the assumption of no unmentioned tuple mutation, the return contains the original state address in its low half and the second input in its high half. State changes made by the indirect operation remain in effect.

### Transition-stream consumption and first notification

On a boundary transition, the function reads and retains the transition-stream address at state offset 12.

It then performs these actions in order:

1. Writes the retained stream address plus four bytes to state offset 12.
2. Reads one 32-bit value from the retained old stream address.
3. Calls F-5681dacec8f5.
4. Calls F-ff1bdc376dcd with the stream value, the 32-bit result of F-5681dacec8f5, and a literal zero.

The stream-pointer write precedes the stream-value read. If the old stream address aliases state offset 12, the read therefore obtains the newly written address value rather than the previous contents.

The consumed value is retained across the F-5681dacec8f5 call. No state-preservation guarantee is assumed for either dependency.

After the first F-ff1bdc376dcd call returns, the function reads the count again. This later observation selects the installation path independently of the count that originally triggered the transition.

### Nonempty installation

If the count is now nonzero:

1. The function reads the current transition-stream address from offset 12.
2. It reads the 32-bit value at that address.
3. It calls F-9e3528e6ab0e with the local tuple address and that value.

This call has two explicit arguments in the supplied representation. No explicit third zero argument is established for this path.

The stream address is obtained after both preceding dependencies return. It may differ from the address written during stream consumption. This second stream read does not itself advance the pointer.

After F-9e3528e6ab0e returns, the function installs tuple words 0 through 3 at state offsets 0, 4, 8, and 12, respectively, in that order.

It then returns the concatenation of tuple words 1 and 0. This path contains no direct secondary-descriptor installation and no final notification.

### Empty installation

If the count is zero after the first notification, the function calls F-9e3528e6ab0e with three explicit arguments:

1. The local tuple address.
2. Zero.
3. Zero.

After the call returns, tuple words 0 through 3 are written to state offsets 16, 20, 24, and 28, in that order.

The function then copies the secondary descriptor into the active descriptor through four ordered read/write pairs:

1. Read offset 16; write offset 0.
2. Read offset 20; write offset 4.
3. Read offset 24; write offset 8.
4. Read offset 28; write offset 12.

This is not an atomic descriptor replacement.

Finally, F-ff1bdc376dcd is called with the current values at offsets 36 and 40 and a literal zero. Those argument values are obtained after descriptor installation. Their relative evaluation order is not established.

On normal return from the final notification, the function returns the first two local tuple words as the specified 64-bit concatenation. It does not reread the active descriptor.

The empty path does not explicitly force the count to zero. Zero selects the path; later dependency effects are not constrained.

## Side effects

### Direct memory effects

The function directly writes:

- State offset 0 before resolving the indirect operation.
- State offset 32 before resolving the indirect operation.
- State offset 12 when consuming a transition word.
- State offsets 0–12 after either tuple-producing dependency call.
- State offsets 16–28 on the empty installation path.
- The local tuple during initialization.

The record word and pointer slot are directly read, not directly written as part of lookup. If either aliases a state field, direct state writes can nevertheless change the value subsequently observed through that storage.

F-9e3528e6ab0e receives writable access to the tuple. Its actual writes are not established.

Effects are not transactional. The address advance and count decrement occur before either indirect-lookup read and remain performed even if lookup or invocation cannot complete. Likewise, stream advancement precedes the stream read and subsequent calls.

### Ownership and lifetime

No direct allocation, deallocation, or ownership transfer is established.

Neither the slot lookup nor any dependency call proves that records, pointer slots, transition storage, or descriptor contents are owned or released by this function. Dependency ownership contracts remain unknown.

The tuple is invocation-local storage. Passing its address establishes access during the call, not a valid lifetime after this function returns. The supplied evidence does not establish whether a dependency retains that address.

### Errors and exceptional completion

There is no explicit error result, pointer validation, target validation, count-underflow guard, rollback, or recovery path.

Behavior for inaccessible record storage, an inaccessible pointer slot, an invalid callable pointer, invalid stream storage, or arithmetic overflow is not established. No cleanup guarantee is visible if a dependency fails to return normally.

Reentrancy and concurrent mutation are not controlled here.

## Acceptance examples

These are conditional consequences of static control flow, not executed tests. Unless stated otherwise, they assume valid storage, representable arithmetic, normal returns, and no unmentioned mutation.

### Interior record

Suppose the entry count is three, the retained record’s first word contains a readable slot address, and the slot contains a callable pointer.

The function advances the active address by 40 bytes, decrements the count to two, and initializes the tuple. It then reads the slot address from the original record, reads the callable pointer from the slot, and invokes that target.

If the operation preserves the relevant state and the advanced address differs from the boundary, no boundary dependency is called. The return combines the original state address and second input.

Calling the record’s first word directly would not satisfy this case.

### Pointer slot aliases the active-address field

Suppose the original record is separate from the state, but its first word designates state offset 0 as the pointer slot.

After the initial advance, the slot contains the original record address plus 40 bytes. The second lookup read obtains that advanced address as the callable pointer. If that address is callable, it is the invoked target.

Using the entry contents of state offset 0 as the target would violate the required lookup order.

### Record word aliases the active-address field

Suppose the retained record address equals the state-object address. The initial advance overwrites the retained record’s first word with the state address plus 40 bytes.

The later first lookup read therefore obtains that updated value as the pointer-slot address. The function then reads the callable pointer from that slot before invoking it. This case additionally requires the resulting slot and target to be valid.

### Boundary reached with work remaining

Suppose the entry count is two and the indirect operation preserves the decremented count and advanced address. If the advanced address equals the boundary:

- The count remains one.
- The stream pointer advances before the consumed word is read.
- F-5681dacec8f5 precedes the first F-ff1bdc376dcd call.
- If the count remains nonzero, F-9e3528e6ab0e receives the tuple address and the value at the current stream address.
- The resulting tuple is installed directly in the active descriptor.
- No final notification occurs.

### Last record and empty installation

Suppose the entry count is one and the operation leaves the decremented count at zero.

With stable count observations, the boundary transition occurs regardless of active and boundary addresses. If the first notification leaves the count zero, F-9e3528e6ab0e receives the tuple address and two zeros.

The resulting tuple is installed in the secondary descriptor, copied fieldwise into the active descriptor, and followed by the final notification using current offsets 36 and 40.

### Dependencies change subsequent behavior

If the boundary transition begins with count zero but the first notification leaves it nonzero, the nonempty installation path is selected. Conversely, a transition entered with work remaining selects the empty path if the count is zero after that notification.

On the empty path, the final notification may modify the active descriptor. If it leaves the local tuple unchanged, those descriptor changes do not change the packed return.
