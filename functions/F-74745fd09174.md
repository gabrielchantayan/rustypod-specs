# F-74745fd09174

## Purpose

F-74745fd09174 coordinates a count-limited operation using an existing buffered region and, when necessary, one additional backing operation.

Its established behavior is to prepare the state, consume an available buffered quantity, and choose between direct delivery and a buffered refill. It replaces the caller’s requested count with the quantity credited during the invocation and updates a separate two-word accounting field for quantities reported by the backing dependency.

The apparent intent is buffered reading. That interpretation is inferred: the supplied body establishes dependency arguments, status handling, and surrounding state changes, but does not independently establish that the dependencies copy bytes or read a stream.

A significant distinction applies after an accepted refill: the amount passed to the transfer dependency is not necessarily the amount subsequently credited or used to advance the cursor. The backing dependency has received the address of the amount storage. Preservation of that storage during the later transfer call is not established.

## Interface

### Inputs and result

| Input | Representation | Established use |
|---|---|---|
| State address | 32-bit address-valued input | Passed to dependencies and used for fixed-offset field accesses. |
| Count address | Address of a writable 32-bit unsigned quantity | Supplies the request after preparation and receives the credited count on ordinary completion. |
| Destination address | 32-bit address-valued input | Passed to transfer and backing dependencies; advanced locally after initial buffered delivery. |
| Fourth input | 32-bit unsigned quantity | Initially stored in local amount storage, but overwritten before that stored value affects an observable operation. |

The result is a 32-bit signed status. Zero is treated as success. Status −39 has special handling only on the buffered-refill path. Other dependency statuses are returned without translation on the paths described below.

### State layout

Offsets are relative to the state address. Every listed field occupies four bytes.

| Offset | Role established by use |
|---|---|
| +0x08 | Opaque argument to the backing dependency. |
| +0x10 | Direct-versus-refill threshold and initial refill request. |
| +0x18 | Buffered cursor or current buffered address. |
| +0x1c | Base address supplied as the refill destination. |
| +0x20 | End-like address assigned after an accepted refill. |
| +0x28 | Low word of backing accounting. |
| +0x2c | High word of backing accounting. |

The accounting fields implement a two-word unsigned counter. They are not updated atomically as one 64-bit object.

The total state size, actual object type, alignment requirements, and meanings of other fields are unknown. The end-like field is assigned base plus amount minus one; interpreting it as an inclusive buffer end is inferred intent.

### Preconditions and ownership

The body contains no explicit null, capacity, alignment, range, or overlap checks.

Ordinary execution requires valid accesses on the selected path and satisfaction of each dependency’s own requirements. Preparation success always leads to a count read, including for a zero request.

No explicit allocation, release, or ownership transfer appears in the body. Dependency ownership effects are unknown.

The backing dependency receives an address into this invocation’s local storage. The body does not prevent retention of that address or later modification through it while the invocation remains active. This observation does not establish any right to use that address after the invocation returns.

## Behavior

### 1. Preparation

The first dependency call is F-8d88f6e0df46, receiving the state address and integer 1.

A nonzero result is returned immediately. On that path, this body does not itself read or write the caller’s count or explicitly access the listed state fields. The preparation dependency may nevertheless affect those locations.

After preparation returns zero, the function reads the requested count. Preparation-time changes to that location therefore affect the request used.

The retained request, caller-credit accumulator, and status are distinct from the writable amount storage later exposed to the backing dependency. Credit and status initially equal zero.

### 2. Zero request

If the count read after preparation is zero, the function writes zero through the count address and returns zero.

It makes no availability, transfer, or backing call. Preparation still occurs, so a zero request is not an unconditional no-op.

### 3. Initial buffered delivery

For a nonzero request, F-0d05d1544f78 receives the state address. Its result is interpreted as a 32-bit unsigned quantity, not a signed status.

If the result is zero, initial delivery is skipped. Otherwise, the selected amount is the unsigned minimum of the request and availability.

The function then:

1. Reads the buffered cursor at +0x18.
2. Calls F-70a021fc7c24 with that address, the current destination, and the selected amount.
3. Reduces the retained request by the selected amount.
4. Advances the local destination by that amount.
5. Reloads +0x18 and writes the reloaded value plus that amount.
6. Establishes initial caller credit equal to that amount.

No transfer result is consulted.

The cursor reload matters: a transfer-side change to +0x18 affects the value subsequently advanced. The function does not necessarily advance the address originally passed to the transfer.

If no request remains, it writes the credited count and returns zero without a backing operation.

### 4. Path selection

For a remaining nonzero request, the function reads +0x10 after the availability call and any initial transfer.

The comparison is unsigned:

- Remaining request greater than threshold: direct backing operation.
- Remaining request less than or equal to threshold: buffered refill.

Equality selects refill. There is no loop and at most one backing call per invocation.

### 5. Direct backing operation

The writable local amount is initialized to the remaining request. F-6ec743d9b657 receives:

1. The value read from +0x08.
2. The address of the local amount.
3. The current caller destination.

After the call, the amount storage supplies the backing-reported quantity.

Regardless of backing status, the function credits that quantity to the caller and adds it to backing accounting. More specifically, it reads the low accounting word, adds the reported quantity to caller credit, writes the low accounting sum, and then reads and writes the high word using the low-word carry.

It finally writes caller credit through the count address and returns the backing status unchanged.

There is no clamp to the requested amount, retry, or conversion of a short successful direct result to −39. A direct result of −39 remains −39 even if a nonzero amount is credited.

This path makes no explicit post-backing cursor or end assignment. That does not guarantee preservation by dependencies or aliased writes.

### 6. Buffered refill

The local amount initially contains the threshold, not necessarily the smaller remaining request. F-6ec743d9b657 receives:

1. The value read from +0x08.
2. The address of that same local amount storage.
3. The buffer base read from +0x1c.

Immediately after the backing call, the function retains a separate snapshot of the reported amount for the later short-refill status decision.

Backing status −39 is normalized to zero for refill acceptance. Status zero is also accepted. All other statuses reject buffered delivery.

The function updates backing accounting before acting on acceptance. Thus even a rejected refill contributes its reported amount to accounting.

#### Rejected refill

For a status other than zero or −39:

- No subsequent transfer call occurs.
- No explicit cursor or end assignment occurs.
- The refill amount contributes no caller credit.
- Initial buffered credit, if any, remains.
- The original nonzero backing status is returned after the final count write.

Backing accounting and caller credit can therefore differ.

#### Accepted refill: setup and transfer arguments

For status zero or −39, the function performs these actions before the transfer call:

1. Reads +0x1c and writes that value to +0x18.
2. Reads +0x1c again and writes base plus the current amount minus one to +0x20.
3. Replaces the writable amount with the remaining request if the remaining request is no greater than its current value.
4. Sets status to −39 if the separately retained backing-reported amount is smaller than the remaining request; otherwise status remains zero.
5. Reads +0x18 and calls F-70a021fc7c24 with that cursor, the current caller destination, and the current amount.

In ordinary noninterfering execution, the transfer argument is the unsigned minimum of remaining request and reported refill amount.

The transfer call occurs even when that argument is zero.

#### Accepted refill: credit after transfer

After the transfer returns, the function reads the writable amount again when adding caller credit. It then reloads +0x18 and uses the amount storage again when advancing the cursor.

The body does **not** unconditionally reuse the amount supplied as the transfer argument. F-6ec743d9b657 previously received the address of this storage; retention and use of that address during F-70a021fc7c24 are not excluded.

Consequently, a transfer-time change to the escaped amount can change caller credit and cursor advancement without changing:

- The amount already passed to the transfer.
- The end field already assigned.
- The status already selected from the saved refill report.

The familiar rule “credit and advance by the minimum of request and refill report” requires the additional, unestablished assumption that the amount storage is preserved during the transfer.

An accepted backing status of −39 may become final status zero when the saved reported amount meets the remaining request. Conversely, a saved report smaller than the remaining request produces −39 even if the transfer later increases the escaped amount.

For a zero report without intervening mutation, the end calculation gives base minus one modulo 2³², the transfer receives zero, and the selected status is −39. Post-transfer credit and advancement are zero only if the exposed amount remains zero.

### 7. Completion

Except for preparation failure, ordinary completion writes the accumulated caller credit through the count address and returns the selected status.

The original request is replaced, not preserved.

## Side effects

### Backing accounting

Each backing call causes an accounting update regardless of status:

1. Read the low word at +0x28.
2. Write its sum with the backing-reported amount, retaining 32 bits.
3. Read the high word at +0x2c.
4. Write that high word plus the unsigned carry from the low addition.

The direct path adds caller credit between the low-word read and low-word write. The refill path retains the reported-amount snapshot and processes −39 acceptance before its low-word write.

With ordinary separate storage and no interfering mutation, the two fields implement addition modulo 2⁶⁴. High-word overflow wraps. Initial buffered delivery does not directly affect this accounting.

A later mutation of the escaped amount during accepted-refill transfer does not retroactively change accounting already performed.

### Widths and arithmetic

Requests, availability, amounts, accounting words, and address-like values use 32-bit representations. Quantity comparisons are unsigned.

The exposed arithmetic retains 32-bit results for cursor movement, end calculation, destination advancement, and caller credit. No overflow or wraparound protection appears.

An excessive backing report can therefore produce caller credit beyond the original request, including wraparound. On accepted refill, transfer-time mutation of the escaped amount can independently produce excessive or wrapped credit and cursor movement.

### Aliasing and ordering

No non-aliasing guarantee is established.

The final count write can overwrite a state field if the count address overlaps it. Dependency writes can likewise affect later field reads. The two buffer-base reads during refill setup are separate; the body does not establish a single immutable base snapshot.

Some quantities are retained separately, including the remaining request and saved refill report used for status selection. The amount storage is different: its address escapes to the backing dependency and it is read again after the subsequent transfer call. It must not be treated as an immutable retained quantity.

No synchronization or atomicity mechanism is visible. Concurrent or dependency-mediated interference must not be replaced with an entry-state snapshot model.

## Acceptance examples

These are conditional contracts, not executed tests. Unless an example states otherwise, assume valid accesses, no arithmetic wrap, stable unrelated state, and preservation of the escaped amount during the later transfer call. The last assumption is additional dependency behavior, not a guarantee of this body.

1. **Preparation rejection.** Preparation returns 7. The function returns 7 without itself reading or writing the count or calling another dependency.

2. **Zero request.** Preparation succeeds and the subsequently read request is zero. The function writes zero and returns zero without availability or backing calls.

3. **Buffer satisfies request.** Request 5, availability 8. The initial transfer receives 5; caller credit becomes 5; the reloaded cursor advances by 5. No backing call occurs.

4. **Direct short success.** Request 12, availability 2, threshold 4. The backing call receives amount 10 and the caller destination advanced by 2. A report of 7 with status zero produces output count 9 and status zero, without retry.

5. **Threshold equality.** Request 4, availability zero, threshold 4. Refill is selected. The backing destination is the buffer base. Status zero and report 4 produce transfer amount 4, output count 4, and status zero.

6. **Accepted short refill.** Remaining request 6, threshold 8, report 3, status zero. Accounting increases by 3; end becomes base plus 2; transfer receives 3; caller credit increases by 3; status is −39.

7. **Accepted −39 with sufficient data.** Remaining request 3, threshold 8, report 5, backing status −39. End becomes base plus 4, transfer receives 3, and final status is zero.

8. **Rejected refill still accounts.** Request 6, availability 1, threshold 8. After initial delivery, backing reports 2 with status 12. Accounting increases by 2, output count remains 1, status is 12, and no refill transfer occurs.

9. **Zero refill.** With a positive remaining request, status zero and report zero establish end at base minus one modulo 2³² and invoke transfer with zero. If that call preserves the amount, credit and cursor receive no additional increment; status is −39.

10. **Accounting carry.** Low word 0xfffffffe and report 3 produce low word 1 and a high-word increment modulo 2³², regardless of refill acceptance.

11. **Escaped amount changes during transfer.** No initial delivery; remaining request 3; threshold at least 3; accepted backing report 5. End is assigned base plus 4 and transfer receives 3. If that transfer changes the escaped amount to 9 while preserving the cursor, final caller credit is 9 and the cursor becomes base plus 9. Status remains zero and end remains base plus 4. Accounting increased by 5, not 9.

12. **Post-call cursor reload.** If a transfer changes the cursor to another address, advancement applies to that post-call address. For accepted refill, the increment also depends on the amount read after the call, not necessarily its argument.
