# F-d006504fe20d

## Purpose

F-d006504fe20d searches an object-associated sequence of 16-bit values for the value selected by an unsigned input from an external lookup table. It returns the zero-based position of the first match, or the 32-bit all-ones value when the search is disabled, the selector is outside its accepted range, or no match is found.

The established behavior is a linear equality search. Interpreting the sequence as a mapping, membership list, character set, or other application-specific structure would be inferred intent, not an established part of this contract.

## Interface

### Inputs

The function has two inputs:

1. **Object address carrier:** A 32-bit signed integer used as an address for accessing an object’s fields. Its signed declaration does not establish a meaningful range of signed numeric object identifiers. Its observed role is address formation.
2. **Selector:** A 32-bit unsigned integer. Only values from 0 through 255, inclusive, permit a search.

The object has these relevant fields:

| Byte offset from object address | Observed access width | Role |
|---|---:|---|
| `0x00C` | 32 bits, interpreted as unsigned | Sequence element count |
| `0x488` | 32-bit address value | Sequence base address; zero disables searching |

The sequence consists of adjacent 16-bit elements with a two-byte stride. Matching reads begin at the sequence base and proceed in increasing index order.

An external address-bearing datum supplies the base address of a second sequence of 16-bit elements. The selector indexes this lookup sequence with a two-byte stride. The provided material does not establish who initializes this address, how much storage backs it, or whether it can change.

### Output

The result is a 32-bit unsigned integer:

- A matching element’s zero-based index, if a match is found.
- `0xFFFFFFFF`, numerically 4,294,967,295, otherwise.

No separate status, output buffer, exception interface, or error object is shown.

### Preconditions for defined successful access

The object must support a readable 32-bit access at offset `0x488` even when the selector is out of range. The sequence-address test occurs before the selector-range test.

Additional access requirements depend on the execution path:

- If the sequence address is zero, neither the count nor either sequence needs to be accessible for this function’s shown operations.
- If the selector is at least 256, the count and sequence contents are not accessed after the initial sequence-address read.
- If the sequence address is nonzero and the selector is accepted, the count field must be readable.
- Each attempted comparison requires the selected sequence element, the external lookup address datum, and the selected lookup element to be readable.

Alignment requirements, byte order, and the behavior of invalid or overflowing address accesses are not established by the supplied material.

## Behavior

### Search eligibility

The function first reads the 32-bit sequence address at object offset `0x488`.

If that value is zero, it returns `0xFFFFFFFF`. The count field is not examined, and no element comparison takes place.

If the sequence address is nonzero, the function checks whether the unsigned selector is less than 256. A selector of 256 or greater produces `0xFFFFFFFF`, without entering the search.

These are separate reasons for the same result. The return value does not distinguish a disabled sequence from an invalid selector or an unsuccessful search.

The eligibility check is not an object-validity check. In particular, an out-of-range selector does not make an invalid object address safe: the sequence-address field is examined first.

### Search traversal

When both eligibility conditions hold, the search begins at index zero.

Before each attempted comparison, the current index is compared, as an unsigned 32-bit value, with the count read at object offset `0x00C`. A comparison is attempted only when the index is strictly less than that count.

For each attempted comparison:

- The sequence element is selected using the sequence address from object offset `0x488` and a byte displacement equal to twice the current index.
- The lookup element is selected using the external lookup base and a byte displacement equal to twice the selector.
- The two elements are read as 16-bit quantities and compared for equality.

If they are equal, the function immediately returns the current index. No later index is examined by the shown control flow.

If they differ, the index advances by one and the loop condition is evaluated again.

If the loop condition fails, the function returns `0xFFFFFFFF`.

With stable, valid object fields and backing storage, this returns the smallest index below the count whose element equals the selected lookup value.

### Empty sequences and duplicate values

An eligible sequence with count zero produces `0xFFFFFFFF` without reading an element from either sequence.

If several sequence elements match, only the first matching index is returned. A match at index zero returns zero, not a Boolean success value.

A 16-bit element containing all one bits is an ordinary searchable value. It is not a terminator and is unrelated to the 32-bit all-ones failure result.

### Widths and arithmetic

The selector, count, search index, and result are 32-bit unsigned quantities. The element width is 16 bits.

Although the elements are represented as signed 16-bit reads in the supplied material, the operation is equality between two values of that same width and interpretation. Consequently, equal 16-bit patterns match, including patterns whose high bit is set. There is no ordering comparison and no rejection of negative signed 16-bit values.

The accepted selector range bounds its lookup displacement to 0 through 510 bytes. Reading selector 255 therefore requires the two bytes beginning at lookup offset 510 to be accessible whenever a comparison occurs.

The count is not checked against allocation size or against the range of safe address arithmetic. Sequence displacement grows by two bytes per index in the shown 32-bit address model. The material does not establish safe behavior when that computation overflows or when the resulting address does not identify valid storage. Such inputs must not be treated as a supported large-array interface merely because the count field can represent them.

For a stable count of `0xFFFFFFFF`, the numerical loop bound permits indices zero through `0xFFFFFFFE`. Index `0xFFFFFFFF` cannot pass the unsigned loop condition for any 32-bit count, so it cannot be returned as a matching index. The failure sentinel is therefore distinct from every index the shown loop can return.

### Field stability and read ordering

The eligibility read of the sequence address precedes the first count read. The loop condition precedes its corresponding element comparison. A successful comparison precedes the return and prevents further search iterations.

The count appears in the loop condition rather than being captured once before traversal. The sequence-address field and external lookup base appear in the comparison performed on each iteration. The supplied representation therefore does not establish a snapshot of these inputs at function entry.

This matters when describing dependencies: the initial nonzero sequence-address check is not evidence that later accesses use a separately retained, validated address. Likewise, the selected lookup value is not shown as being captured once before the search.

The supplied comparison expression does not establish which of its two operand reads occurs first. It also does not establish machine-level reload frequency, atomicity, or synchronization guarantees. Behavior under concurrent mutation cannot be specified as a coherent snapshot or a supported concurrent-search protocol.

## Side effects

The only explicit output is the return value. No ownership transfer is expressed:

- The object remains caller-owned or otherwise externally owned.

These observations describe the shown operations, not unknown properties of the backing memory. Reads from memory-mapped devices or other read-sensitive storage could have effects outside the ordinary memory model; such uses are not specified here.
