# F-58326c7630ef

## Purpose

F-58326c7630ef performs an in-place structural transformation on pointer-linked records. It promotes the record referenced at offset +8 of a designated pivot, transfers the promoted record’s offset +12 link to the pivot’s offset +8 link, reconnects the surrounding structure, and makes the pivot the promoted record’s offset +12 child.

**Inferred intent:** If offset +8 denotes a left child, offset +12 denotes a right child, and offset +4 denotes a parent, this is a right rotation of a binary-tree subtree. The supplied representation establishes the link manipulation, but does not establish ordering rules, balancing rules, node types, or the meaning of any payload.

The operation does not validate that its inputs describe a tree. Its ordinary structural interpretation depends on valid, writable records and consistent relationships.

## Interface

The function accepts two address-bearing arguments and has no return value:

| Argument | Role |
|---|---|
| Context address | Identifies a record containing an anchor-record address at offset +16. |
| Pivot address | Identifies the record around which the transformation occurs. |

The supplied representation uses 32-bit integer values for arguments and link fields. Every explicit field access reads or writes four bytes. Link values are interpreted as addresses when dereferenced. Zero is tested as the absence of the transferred child; it is not generally treated as a safe value for every link.

The relevant layouts are:

| Record | Offset | Observed use |
|---|---:|---|
| Context | +16 | Address of an anchor record |
| Anchor | +4 | Distinguished node link, conditionally replaced |
| Pivot | +4 | Parent-like link |
| Pivot | +8 | Link selecting the record to promote; subsequently replaced |
| Promoted record | +4 | Parent-like link, overwritten |
| Promoted record | +12 | Link transferred to the pivot; subsequently replaced by the pivot |
| Transferred child, when present | +4 | Parent-like link, overwritten |
| Pivot’s parent, on the non-anchor branch | +12 | Tested for equality with the pivot; conditionally overwritten |
| Pivot’s parent, on the fallback branch | +8 | Overwritten without an equality check |

These offsets describe accessed fields, not complete record definitions. No meaning is established for other bytes.

For a successful, well-formed transformation, the caller must provide:

- A readable context field at offset +16 and a valid anchor address in that field.
- A readable and writable anchor field at offset +4.
- A readable and writable pivot record covering the accessed fields.
- A valid, nonzero promoted-record address in the pivot’s offset +8 field.
- A readable and writable promoted record covering offsets +4 and +12.
- If the promoted record’s offset +12 link is nonzero, a writable offset +4 field at that linked address.
- If the anchor’s offset +4 link does not equal the pivot, a valid parent-like address in the pivot’s offset +4 field, with the relevant parent fields accessible.
- Stable memory and relationships throughout the operation if the caller expects the tree-rotation interpretation.

Alignment requirements, byte order, address-space rules, and the consequences of invalid accesses are not established by the supplied material.

## Behavior

### Structural result under ordinary preconditions

For this description:

- **Pivot** is the second argument.
- **Promoted record** is the address initially read from the pivot’s offset +8 field.
- **Transferred child** is the promoted record’s initial offset +12 link.
- **Original parent** is the pivot’s initial offset +4 link.
- **Anchor** is the record reached through the context’s offset +16 field.

Assuming these records do not overlap in ways that interfere with the accessed fields, the transformation has the following result:

1. The pivot’s offset +8 link becomes the transferred child.
2. If the transferred child is nonzero, its offset +4 link becomes the pivot.
3. The promoted record’s offset +4 link becomes the original parent.
4. One incoming link that previously identified the pivot is redirected to the promoted record:
   - If the anchor’s offset +4 link equals the pivot, that anchor field is replaced.
   - Otherwise, if the original parent’s offset +12 link equals the pivot, that field is replaced.
   - Otherwise, the original parent’s offset +8 field is replaced.
5. The promoted record’s offset +12 link becomes the pivot.
6. The pivot’s offset +4 link becomes the promoted record.

The final fallback does **not** verify that the parent’s offset +8 field originally referenced the pivot.

The function does not compare payloads or keys. It does not modify any visible balance, height, color, count, or version field.

### Access and mutation order

The supplied representation establishes the following logical order of field accesses. This is the source-facing access order, not a claim about instruction scheduling or concurrent visibility in an unavailable executable.

First, the function reads the pivot’s offset +8 link and retains that address as the promoted record for the remainder of the operation.

It then reads the promoted record’s offset +12 link and writes that value into the pivot’s offset +8 field.

Next, it reads the promoted record’s offset +12 field again to test whether the link is zero. If the test is nonzero, it reads that field again to obtain the destination record address, then writes the pivot address into that record’s offset +4 field.

The function then reads the pivot’s offset +4 field and writes the obtained value into the promoted record’s offset +4 field.

Only after those mutations does it read the context’s offset +16 field to locate the anchor. It reads the anchor’s offset +4 field and compares that value with the pivot address.

- On equality, it writes the promoted-record address into the anchor’s offset +4 field.
- Otherwise, it reads the pivot’s offset +4 field again to locate the parent-like record. It reads that record’s offset +12 field and compares it with the pivot address.
  - On equality, it writes the promoted-record address into that offset +12 field.
  - Otherwise, it writes the promoted-record address into the parent-like record’s offset +8 field.

Finally, it writes the pivot address into the promoted record’s offset +12 field, then writes the promoted-record address into the pivot’s offset +4 field.

There is no subsequent verification.

### Repeated reads and aliasing

The function does not capture every original relationship before making changes. In particular:

- The promoted record’s offset +12 field is read repeatedly.
- The pivot’s offset +4 field is read once for the promoted record’s parent-like link and may be read again when reconnecting the incoming parent link.
- The context-to-anchor link is read after several writes have already occurred.

Consequently, the ordinary structural result above is conditional on stable, noninterfering storage. If records overlap, a write may change a field that is read later. For example, the nonzero test and the subsequent destination-address read are separate accesses; they are not represented as a single saved transferred-child address.

The implementation contains no explicit rejection of self-links, cycles, overlapping records, or inconsistent parent-child relationships. The supplied material does not establish those malformed arrangements as supported inputs.

## Side effects

All visible effects are writes to existing records. The function neither allocates nor releases memory, and it makes no dependency calls.

On an ordinary successful execution, it performs:

- Four unconditional writes: pivot offset +8, promoted record offset +4, promoted record offset +12, and pivot offset +4.
- One incoming-link replacement: either anchor offset +4, parent offset +12, or parent offset +8.
- One additional write to the transferred child’s offset +4 field when the tested transferred-child link is nonzero.

Thus, the ordinary path executes five or six four-byte writes. Aliasing can cause distinct write operations to target the same storage.

No ownership transfer is expressed beyond changing links. The function does not establish who owns any record, whether the context manages node lifetimes, or whether callers may retain references to the pivot or promoted record.

The transformation is not represented as atomic. Intermediate states include a pivot whose offset +8 link has already changed while its incoming link and parent-like link have not yet been updated. No locking, synchronization, rollback, or publication protocol is present.

Invalid memory can be encountered after earlier writes have occurred. There is no explicit error return, validation failure path, or recovery mechanism. Exact fault behavior is environment-dependent.

### Non-anchor pivot linked through parent offset +8

After completion, the parent’s offset +8 field identifies the promoted record. Its offset +12 field remains unchanged.

### No transferred child

The pivot’s offset +8 field becomes zero. No transferred-child parent field is written. The function still reconnects the incoming link and attaches the pivot at the promoted record’s offset +12 field.

### Inconsistent parent relationship

Provided all accesses remain valid, the function nevertheless overwrites the parent’s offset +8 field with the promoted-record address. It does not report the inconsistency. Acceptance must not require rejection or preservation of that preexisting offset +8 link.
