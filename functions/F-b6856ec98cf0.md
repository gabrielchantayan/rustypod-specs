# F-b6856ec98cf0

## Purpose

F-b6856ec98cf0 performs a key-directed search over records described by a caller-supplied object. It repeatedly reads a selected record’s unsigned key and narrows an index interval according to the key’s relationship to a requested unsigned value.

The established interface exposes neither the matching index nor a success indicator. Both a matching-key exit and an exhausted-interval exit complete without a specified return value. The routine also contains no explicit memory writes. Consequently, ordinary callers cannot distinguish “found” from “not found” through a documented result or mutation.

The access pattern is consistent with binary search over ascending keys. That interpretation is inferred intent, not an enforced input property. The routine neither checks ordering nor checks the validity of the object or its record storage.

## Interface

### Inputs

The routine accepts two arguments:

- **Object address:** an address used to locate a record count and a record-storage address.
- **Requested key:** an unsigned integer compared against keys read from selected records.

The supplied representation declares the first argument as an integer rather than a typed object pointer. Its operational role is nevertheless an address. This contract does not assign it a separate arithmetic meaning.

### Object and record layout

Under the apparent 32-bit data model, the relevant layout is:

| Location | Width | Meaning |
|---|---:|---|
| Object address plus hexadecimal offset 10 | 32 bits | Unsigned record count |
| Object address plus hexadecimal offset 14 | 32 bits | Record-storage address |
| Record-storage address plus eight times a selected index | 32 bits | Unsigned comparison key |

Offsets and record stride are byte quantities.

Only the first four bytes at each selected eight-byte record position are explicitly read. The remaining four bytes of that record are not accessed by this routine. Their meaning is unknown.

The count and key operations use an unsigned integer type. The address-bearing fields use integer-sized values in the supplied representation. A 32-bit interpretation is consistent with these accesses, but the excerpt does not independently establish the target ABI, byte order, or alignment rules. Those details must be supplied by the execution environment before this becomes a byte-exact portable contract.

### Output

There is no specified return value, output parameter, matching-record pointer, or matching index.

The distinction between a successful comparison and interval exhaustion exists only in the internal control flow and the resulting read trace.

### Preconditions

For an execution without memory-access failure:

- The count field must be readable.
- If the initial count is nonzero, the record-storage address field must be readable.
- Every selected key address must be readable with the required access width and alignment.
- Address calculations must have defined behavior in the target execution model.

For the search to have the usual binary-search interpretation, the keys must additionally be in nondecreasing unsigned order, and the midpoint calculation must behave as an in-range interval midpoint. The routine does not enforce either condition.

No ownership transfer is expressed by the interface.

## Behavior

### Initialization and empty input

The routine initializes the lower search bound to zero and reads the count field once. That count becomes the initial exclusive upper bound.

Before selecting a record, it compares the current upper and lower bounds as unsigned values. If the upper bound is less than or equal to the lower bound, it returns.

An initial count of zero therefore causes a return after the count read. In that case, the record-storage address field is not read and no record key is read. Valid record storage is unnecessary for this particular path, although the object’s count field must still be accessible.

The count is not refreshed during the search. A later change to the count field does not change the locally retained search bounds.

### Record selection and read order

For each iteration whose interval is nonempty, the routine:

1. Calculates a selected index by adding the current bounds in the unsigned integer width and shifting the sum right by one bit.
2. Reads the record-storage address from the object.
3. Reads the unsigned key at the selected record position.
4. Compares that key with the requested key.

These are the explicit logical memory reads shown by the supplied representation. Compiler-level or hardware-level access behavior, including speculation or access coalescing, is not established here.

The record-storage address is read again for every selected key. It is not explicitly cached across iterations. Thus, the source-level behavior does not establish one immutable record array for the entire call. An environment in which the field changes could cause later iterations to use different storage. Whether such changes are permitted or reliably observable depends on synchronization and memory semantics not provided in the excerpt.

### Equality and interval changes

If the selected key equals the requested key, the routine immediately returns. It does not inspect adjacent records, retrieve the record’s remaining contents, or communicate the selected index.

If the selected key is smaller than the requested key, the lower bound becomes one greater than the selected index. The upper bound remains unchanged.

If the selected key is greater than the requested key, the upper bound becomes the selected index. The lower bound remains unchanged.

The next iteration again checks for an empty interval before reading another record.

Equality is handled before the remaining ordering decision. Although the subsequent comparison includes equality, that equality case cannot be reached after the earlier equality exit.

### Ordering and duplicates

With stable, nondecreasing unsigned keys and midpoint arithmetic that does not wrap, the interval updates implement conventional binary-search narrowing:

- Keys below the request discard the selected position and all lower positions from the retained interval.
- Keys above the request exclude the selected position and all higher positions.
- Equality ends the operation immediately.

Duplicate keys are accepted by the comparison logic. There is no requirement to locate the first or last equal record, and no equal record is returned to the caller.

Unsorted input is not rejected. It can cause the search to return through interval exhaustion even when an equal key exists elsewhere in the storage.

### Width and arithmetic limits

The midpoint is formed from the sum of the two bounds, not from a difference-based expression. This distinction matters for large counts.

Under a 32-bit unsigned interpretation:

- Bound addition is reduced modulo \(2^{32}\).
- The right shift divides that reduced unsigned value by two, rounding down.
- Multiplication of the selected index by eight is also subject to the applicable integer-width arithmetic.
- Address formation does not itself establish that the resulting address identifies the intended record.

If the bound sum wraps, the selected index can fall below the lower bound. A subsequent lower-bound update can then fail to make progress or can move the bound backward. Consequently, termination and conventional binary-search correctness are not established for the entire unsigned count range.

A sufficient count restriction for avoiding midpoint-sum overflow in a conventional valid interval is a count no greater than \(2^{31}\). This is not a complete memory-safety restriction: record offsets and address calculations still need to be representable and backed by readable storage.

The routine contains no overflow detection, maximum-count validation, or fallback search.

## Acceptance examples

These examples describe conditional expected behavior from static inspection. They are not runtime test results. Except where stated otherwise, they assume stable readable storage, a 32-bit unsigned model, valid address calculations, and no midpoint overflow.

### Empty collection

Given an object whose count is zero, the routine reads the count and returns.

It must not require a readable record-storage address field or a readable record for this path.

### One matching record

Given count one and a sole key of 25, a request for 25 selects index zero, reads that key, and returns through the equality path.

There is no specified success value or object mutation.

### One nonmatching record

Given count one and a sole key of 25:

- A request for 24 reads index zero, reduces the upper bound to zero, and returns at the next interval check.
- A request for 26 reads index zero, advances the lower bound to one, and returns at the next interval check.

Neither case produces a specified failure value.

### Ordered multi-record search

Given keys 10, 20, 30, 40, and 50, a request for 40 selects indices two and four and then three. It reads keys 30, 50, and 40 in that order, then returns.

The count is read once. The record-storage address is read for each of those three key selections.

### Duplicate matches

Given keys 7, 7, and 7, a request for 7 selects index one and returns immediately.

It does not read indices zero or two to identify a duplicate boundary.

### Unsorted storage

Given keys 30, 10, and 20, a request for 30 selects indices one and two, reads keys 10 and 20, and exhausts the interval without reading index zero.

This is accepted by the routine’s control flow, despite an equal key existing in storage. No ordering error is reported.

### Large-count arithmetic

If a reachable pair of bounds has a sum that exceeds the unsigned maximum, acceptance must follow the wrapped midpoint calculation rather than an ideal mathematical average.

There is no general acceptance requirement that such an execution terminate, remain within the current interval, or find an existing key. Readability of every address actually selected remains a separate prerequisite.
