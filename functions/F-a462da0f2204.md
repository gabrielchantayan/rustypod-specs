# F-a462da0f2204

## Purpose

F-a462da0f2204 returns a raw 16-bit value selected using caller-provided state storage, an unsigned 32-bit selector, and ambient lookup resources.

There are three result paths:

- An ordinary candidate associated with the current selector.
- A special candidate checked against byte value 59.
- A default associated with the selected state.

A mapping lookup can replace the selector and restart state selection. Termination is not guaranteed.

The candidate-result address is not unconditionally the mathematical address of a 16-bit array element at the candidate index. Its byte offset is calculated by doubling the candidate in **unsigned 32-bit arithmetic**, which can wrap before combination with the result-table base.

The arrangement suggests compressed lookup with fallback. Application-specific interpretations—such as parser states or character classes—are inferred intent, not established behavior.

## Interface

### Explicit inputs

**State-storage address**

The first argument supplies an address used for signed 32-bit word reads.

Each attempt reads:

1. The signed 32-bit word at the supplied address, called the state position here.
2. A signed 32-bit state word at word displacement `5 × state position + 3` from that address.

Where these calculations are valid, the second read has byte displacement `20 × state position + 12`. This relationship does not establish a separate header or record-layout convention.

The source performs signed state-address calculations. It does not establish defined overflow behavior for extreme positions, a wider intermediate calculation that prevents overflow, or bounds validation.

**Selector**

The second argument is an unsigned 32-bit selector. The initial selector is not truncated to eight bits.

A replacement obtained from the mapping resource is an unsigned byte widened to an unsigned 32-bit selector.

### Ambient inputs

Ambient inputs include both table storage and the global values supplying its bases:

| Resource | Accessed representation | Use |
|---|---|---|
| State-base base value and storage | Signed 16-bit elements | Obtain an offset from the selected state |
| Candidate limit | Unsigned 32-bit value | Bound ordinary and special candidate indices |
| Candidate-check base value and storage | Bytes | Validate a candidate |
| Candidate-result base value and storage | Raw 16-bit values | Supply ordinary or special results |
| State-default base value and storage | Raw 16-bit values | Supply state-specific defaults |
| Selector-mapping base value and storage | Unsigned bytes | Obtain a replacement selector and decide whether to retry |

A base value is distinct from the contents of storage it identifies. Stability of one does not establish stability of the other.

The source references these base values on the paths that use them. In particular, the two mapping reads contain **separate references to the mapping-table base**, even though they use the same current selector.

Lengths, backing allocations, initialization, storage ownership, update rules, and consistency guarantees are not supplied.

### Output

The function returns one raw 16-bit value read from either the candidate-result resource or the state-default resource.

No success code, error code, distinguished result, or signed interpretation is established. A bit pattern with its high bit set is not inherently an error.

### Preconditions for a defined return

Every reached access must identify valid storage with the alignment required by its access width. This includes accesses formed using whichever base values are evaluated on that path.

State-address calculations must also be valid under the applicable arithmetic and addressing rules. Candidate-index wrapping and candidate-result scaling, specified below, do not make unrelated signed address calculations safe.

Termination additionally requires that the reached sequence of attempts eventually takes a returning path. The function checks neither memory validity nor progress.

## Behavior

### State selection and the upper-state decision

At the beginning of every attempt, the function reads the state position and then the selected state word.

A selected state **greater than 389**, using a signed comparison, goes directly to the state-default path.

A state less than or equal to 389 reaches the state-base lookup. The signed 16-bit value read there is sign-extended for subsequent use.

There is no lower-state bound check. A negative state reaches a negatively indexed state-base access rather than being rejected or automatically defaulted. Whether such an access is valid depends on the actual storage and addressing conditions.

The state-base value **−62** is a sentinel. It sends execution directly to the state-default path.

The state-base address involves signed scaling of the state by two. Its overflow behavior is not established as unsigned wrapping.

### Ordinary candidate

For a non-sentinel base, the ordinary candidate is the sum of:

- The sign-extended state-base value.
- The entire current unsigned 32-bit selector.

The result is an unsigned 32-bit value, modulo \(2^{32}\).

An ordinary candidate succeeds only when:

1. Its unsigned value is strictly less than the candidate limit evaluated for this check.
2. The unsigned byte read from the candidate-check resource at that candidate offset equals the entire current selector.

The check byte is not read if the bound comparison fails.

Because the check value is an unsigned byte, no selector greater than 255 can satisfy the equality. Passing the candidate bound does not change that restriction.

On success, the function forms the candidate-result address as specified under **Candidate-result address formation**, reads a raw 16-bit value, and returns it.

### Failed ordinary candidate

If the ordinary candidate fails and the current selector is zero, execution takes the state-default path. Selector zero therefore has an ordinary lookup opportunity before defaulting.

For a failed ordinary candidate with a nonzero selector:

- A selector greater than 137 bypasses mapping and proceeds to the special candidate.
- A selector from 1 through 137 reaches two mapping-byte reads.

The mapping reads have distinct roles and occur in this order:

1. Using a reference to the mapping base and the current selector, read an unsigned byte and save it as the replacement selector.
2. Using a separate reference to the mapping base and the same current selector, read a byte and test whether it is zero.

These are not necessarily reads of the same address. They use the same selector offset, but the base values may differ. Even with a stable base, the contents need not remain unchanged between the reads.

If the second read is nonzero, another attempt begins using the **first read’s value** as the selector. The next attempt rereads the state position and selected state.

If the second read is zero, execution proceeds to the special candidate for the current attempt. The saved replacement value does not determine that special candidate.

No cycle detection or iteration limit is present.

### Special candidate

The special candidate is the current attempt’s sign-extended state-base value plus 59, represented modulo \(2^{32}\).

The source obtains it through arithmetic involving the ordinary candidate and the current selector. Unsigned cancellation makes the resulting candidate equivalent to base plus 59, even when the ordinary addition wrapped.

The special candidate succeeds only when:

1. Its unsigned value is strictly less than the candidate limit evaluated for this special check.
2. Its candidate-check byte equals 59.

The check byte is not read when the bound fails. The special comparison uses character value 59; character signedness does not affect which byte matches.

A successful special candidate returns a raw 16-bit candidate-result read using the address calculation below. Otherwise, execution takes the state-default path.

The ordinary and special bound expressions reference the candidate limit separately. The source does not establish that they observe the same value.

### Candidate-result address formation

Both successful candidate paths use the same scaling rule:

- Double the unsigned 32-bit candidate.
- Retain the unsigned 32-bit result, modulo \(2^{32}\).
- Combine that byte offset with the candidate-result base referenced on the selected path.
- Read 16 bits from the resulting address.

Thus, candidates below \(2^{31}\) have the usual mathematical two-byte element displacement. Candidates at or above \(2^{31}\) have a wrapped doubled offset.

For example, candidate 4,294,967,294 produces byte offset **4,294,967,292**, not 8,589,934,588.

The candidate-limit comparison precedes this scaling and does not establish that scaling cannot wrap. No supplied invariant restricts the limit enough to exclude all such candidates.

This unsigned scaling rule is separate from signed state-based addressing. It also does not establish additional rules for overflow or validity when the resulting offset is combined with the base address.

### State default

The default path references the state-default base, forms an address using twice the current attempt’s selected signed state, reads a raw 16-bit value, and returns it.

The index is the selected state, not the state position.

Defaulting occurs when:

- The selected state is greater than 389.
- The state-base value is −62.
- The ordinary candidate fails for selector zero.
- The special candidate fails.

There is no default-table bounds check. A state above 389 is not guaranteed to have an accessible default merely because the control flow selects that path. Negative states likewise receive no special protection.

The state-based doubling is signed arithmetic in the supplied representation. The unsigned wrapping rule for candidate-result scaling must not be applied to it.

## Side effects

### Reads and sequencing

The function contains no explicit writes to caller storage, table storage, or the ambient global values. Its visible body performs no allocation or deallocation.

At the source-operation level, the significant read ordering is:

1. Read the state-position word.
2. Read the selected state word.
3. If required, reference the state-base base and read the signed 16-bit base entry.
4. If required, evaluate the ordinary bound.
5. Only after a passing bound, reference the candidate-check base and read the ordinary check byte.
6. Follow the selected result, mapping, special, or default path.

On an ordinary success, the candidate-result base is referenced for the result address after the successful check.

On a mapping path, the first mapping read supplies the replacement value before the second mapping read supplies the zero test. Each uses its own base reference. A retry begins state selection again.

On a special path, the special bound is evaluated before the special check-byte read. A successful check is followed by a candidate-result read; failure leads to a default read.

A direct default caused by the state upper bound omits the state-base lookup. A sentinel default omits candidate checking. Neither requires mapping reads.

These sequencing relationships do not specify an evaluation order among operands within an individual address expression where the source provides none. They also do not guarantee a particular number or ordering of physical machine loads after compilation.

### No invocation-wide snapshot

The body does not establish a coherent snapshot of:

- State storage across retries.
- Table contents across accesses.
- Base values across separate references.
- The candidate limit across ordinary and special checks.

Consequently, describing both mapping reads as accessing one entry requires a stable mapping base. Describing them as returning the same value additionally requires stable contents.

No synchronization, atomicity, or permitted concurrent-update model is established. This contract records the separate source references without asserting that arbitrary concurrent mutation has defined execution semantics.

### Ownership and failure behavior

The supplied state address is not visibly retained, released, or transferred. The function returns a value, not a pointer into ambient storage.

Neither the table bases nor the reads establish ownership of any backing allocation. No right to release that storage follows from this interface.

There is no explicit invalid-input result, recovery path, or exception handling. Invalid address formation or access is not converted into a defined return value.

An endlessly repeating mapping sequence can prevent a return without reporting an error.

## Acceptance examples

The following are conditional static examples, not executed tests. Unless an example varies them explicitly, relevant state, bases, contents, and limits are stable. Every described access and address calculation must be valid.

### Ordinary success

Selected state 12 has base 100, and the selector is 7.

The ordinary candidate is 107. If the limit exceeds 107 and check byte 107 equals 7, the function returns the 16-bit read at byte offset 214 from the candidate-result base referenced on this path.

Mapping and default storage are not read.

### Negative base without candidate underflow

With base −3 and selector 5, the unsigned candidate is 2.

If its bound and check succeed, the result read uses byte offset 4. A negative base does not by itself require defaulting.

### Wrapped ordinary candidate rejected by the bound

With base −3 and selector 1, the candidate is 4,294,967,294.

If the limit is 1,000, no ordinary check byte is read. Selector 1 then reaches the mapping path.

### Sentinel and state boundary

For state 12 with base −62, the function returns the state default without checking candidates.

State 389 remains eligible for a state-base read. State 390 bypasses that resource and reads its state default, conditional on valid signed address formation and accessible default storage.

### Selector zero

With selector zero and base 20, an in-range check byte of zero permits an ordinary result read at byte offset 40.

If the ordinary candidate fails, the function defaults without mapping or a special attempt.

### Stable nonzero mapping

Suppose selector 8 fails its ordinary candidate and both mapping reads yield 4.

The function starts another attempt with selector 4. It rereads state storage rather than guaranteeing reuse of the previous state.

### Separately referenced mapping bases

Suppose selector 8 fails. The first mapping-base reference identifies storage whose byte at offset 8 is 4. The second reference identifies different storage whose byte at offset 8 is zero.

The function takes the special path for the current attempt; it does not retry with 4.

Conversely, if the first read yields zero and the second yields a nonzero byte, the next attempt uses selector zero. These examples describe outcomes conditional on such reference observations being valid under the surrounding execution model.

### Mapping zero and a special result

With base 100, selector 8, a failed ordinary candidate, and a zero second mapping read, the special candidate is 159.

If its bound and check succeed, the returned 16-bit read uses byte offset 318 from the candidate-result base. Otherwise the function defaults.

### Large selector

Selector 256 cannot match any ordinary check byte, even if its candidate is in range.

After ordinary failure, mapping is bypassed because 256 exceeds 137. The special candidate is attempted.

### High special candidate with wrapped result scaling

Let the base be −61 and the selector be 138. The ordinary candidate is 77; suppose its check fails.

Mapping is bypassed. The special candidate is 4,294,967,294. With limit 4,294,967,295, this candidate passes the unsigned bound.

If the special check byte equals 59, the result offset is **4,294,967,292**, obtained by unsigned 32-bit doubling. It is not the mathematical doubled offset 8,589,934,588.

This example requires valid storage and address formation for the large check offset and the wrapped result offset; the function does not establish those conditions.

### Mapping cycle

If selectors 4 and 8 map to each other, their ordinary candidates always fail, and the relevant state and mapping observations remain unchanged, attempts can alternate indefinitely. Neither special fallback nor defaulting is guaranteed.
