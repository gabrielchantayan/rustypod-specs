# F-c0987eb09f73

## Purpose

F-c0987eb09f73 inserts a newly obtained node at a caller-supplied position in a linked tree, updates boundary links and an element count, performs color-based balancing, and returns the inserted node through caller-provided storage.

**Established static behavior:** the function copies a 12-byte payload, links the node on one of two child sides, applies recoloring and structural helper calls, and finally writes color value 1 to the node designated as the root.

**Inferred intent:** the layout, sentinel links, and symmetric balancing cases are consistent with insertion into a red-black tree. Color value 0 behaves as red; color value 1 behaves as black. These names describe the apparent algorithm, not independently verified dependency contracts.

The function does not search for an insertion position or independently establish that the requested position is valid.

## Interface

The interface has five arguments and no explicit return value:

| Argument | Meaning established by use |
|---|---|
| Result destination | Address receiving one 32-bit node address after balancing completes. |
| Container address | Address of the structure holding the header address, element count, and comparator-related state. |
| Placement override | A 32-bit integer. Any nonzero value selects the child field at offset 8 without invoking the comparison dependency. |
| Attachment-node address | Address of the existing node or header beneath which the new node is attached. |
| Payload address | Address of three readable 32-bit words, copied into the new node. |

The observed representation uses 32-bit words and addresses. Colors are accessed as individual bytes. The source does not establish byte order or signed comparison semantics for payload contents.

## Behavior

### Node acquisition and payload transfer

The first action is a call to F-04e09896b2b6 with the container address. Its returned address is retained as the identity of the inserted node and is ultimately written to the result destination.

Before linking, the function conditionally copies the payload into the returned node at offsets 16, 20, and 24. The condition tests whether the returned address plus 16 is nonzero. It does **not** test whether the returned address itself is nonzero.

Consequently, this condition is not an ordinary allocation-failure guard. Under a wrapping 32-bit address interpretation, a zero returned address would still enter the copy path, while address `0xfffffff0` would skip it. Neither case is established as valid or supported.

When the copy occurs, the explicit access order is:

1. Read the second 32-bit payload word.
2. Read the first 32-bit payload word and write it at node offset 16.
3. Write the previously read second word at node offset 20.
4. Read the third 32-bit payload word and write it at node offset 24.

This ordering can matter if payload storage overlaps destination storage. No general overlap guarantee is established.

The function does not explicitly initialize the new node’s child links or initial color before balancing. Any required initial values must come from F-04e09896b2b6 or another pre-existing condition.

### Count update

After the payload-copy condition, the function reads the count at container offset 20, adds one, and stores the result back to the same field.

This occurs:

- After node acquisition and the attempted payload transfer.
- Before comparison.
- Before attachment.
- Before balancing.
- Before the result destination is written.

There is no overflow check or rollback path. The evidence shows a 32-bit field accessed through a signed integer interpretation, but does not establish portable behavior at the signed maximum. A valid-use contract should require that the increment be representable rather than assume wraparound.

### Attachment-side selection

The first-child side, at attachment-node offset 8, is selected immediately if either:

- The attachment-node address equals the header address currently stored at container offset 16; or
- The placement override is nonzero.

These paths do not call F-4a197a0807f0.

Otherwise, the function calls F-4a197a0807f0 with:

1. The address at container offset 25.
2. The payload address.
3. The attachment-node address plus 16.

Only zero versus nonzero is tested:

- A nonzero result selects attachment-node offset 8.
- A zero result selects attachment-node offset 12.

The comparison occurs after the count increment and payload transfer. The original payload address, rather than the new node’s payload address, is supplied to the comparison dependency.

No independent duplicate-key rule is visible. In particular, the function does not distinguish equality from any other condition represented by a zero comparison result.

### Attachment and boundary updates

For first-child attachment:

1. Write the new node address to attachment-node offset 8.
2. Re-read the header address from container offset 16.
3. If that header address equals the attachment node:
   - Write the new node address to header offset 4.
   - Write the new node address to offset 12 of the header then obtained from the container.
4. Otherwise:
   - Examine offset 8 of the re-read header.
   - Replace it with the new node address only if it equals the attachment-node address.

Under the inferred empty-tree convention, attachment to the header establishes all three header links: first boundary, root, and last boundary.

For second-child attachment:

1. Write the new node address to attachment-node offset 12.
2. Obtain the header address from the container.
3. Replace header offset 12 with the new node address only if that field currently equals the attachment-node address.

After the selected attachment and boundary updates, write the attachment-node address to new-node offset 4.

The function overwrites the chosen child slot without checking that it is empty. Supplying an occupied slot can disconnect an existing subtree.

Header accesses are not all made through one permanently cached address. Dependencies capable of changing the container’s header field can therefore affect subsequent accesses; their effects must not be assumed away.

### Balancing

The balancing cursor initially denotes the newly obtained node.

Each iteration first obtains the current root through the container’s header field. Balancing stops if the cursor is that root. Otherwise, it reads the cursor’s parent and stops if the parent’s color byte is nonzero.

Thus:

- Color 0 causes the parent to be treated as requiring repair.
- Any nonzero parent color stops the loop.
- Explicit recoloring writes only 0 or 1.

If repair is required, the function obtains the grandparent through the parent link and determines whether the parent equals the grandparent’s first child.

#### Parent on the first-child side

The grandparent’s second child is treated as the uncle.

If the uncle exists and has color 0:

1. Set the parent’s color to 1.
2. Set the uncle’s color to 1.
3. Set the color of the grandparent reached through the cursor’s current parent links to 0.
4. Move the cursor to that grandparent and repeat.

Otherwise:

- If the cursor is the parent’s second child, call F-c3b5aab03a9c on the container and parent, then make the previous parent the cursor.
- Set the cursor’s current parent color to 1.
- Set that parent’s current parent color to 0.
- Call F-6372ad19c9b6 on the container and the grandparent obtained through the current links.
- Reevaluate the loop.

#### Parent on the other side

The grandparent’s first child is treated as the uncle. The branch does not separately validate that the parent is actually the grandparent’s second child.

If that uncle exists and has color 0, perform the same three recolorings and move upward.

Otherwise:

- If the cursor is the parent’s first child, call F-6372ad19c9b6 on the container and parent, then make the previous parent the cursor.
- Set the cursor’s current parent color to 1.
- Set that parent’s current parent color to 0.
- Call F-c3b5aab03a9c on the container and the grandparent obtained through the current links.
- Reevaluate the loop.

These helper roles are consistent with opposite-direction rotations. Their actual contracts are not available.

### Completion

After the balancing loop:

1. Obtain the header address from container offset 16.
2. Obtain the root address from header offset 4.
3. Write color 1 to that root.
4. Write the originally obtained new-node address to the result destination.

The returned node identity does not change when the balancing cursor moves or structural helpers run.

## Side effects

Directly observable writes include:

- Up to 12 bytes of new-node payload.
- One count-field update.
- One attachment-child update.
- Conditional header boundary and root updates.
- The new node’s parent field.
- Color-byte updates during balancing.
- The final root color write.
- The final result-address write.

Dependencies may introduce additional effects. Their allocation, global-state, callback, synchronization, and failure behavior is unknown.

The function does not explicitly release any memory. Its direct behavior attaches the acquired node to the container and exposes its address to the caller. This suggests container retention and a node handle, but does not establish an ownership-transfer or deallocation contract.

There is no explicit error status, exception handling, recovery, or transactional rollback. If a dependency fails or an invalid memory access occurs after the count update, completed writes need not be undone. Abnormal termination behavior is documented_only.

The function provides no visible synchronization or protection against reentrant mutation. Comparison observes a container whose count has already increased but whose new node has not yet been linked.

## Acceptance examples

These examples are conditional predictions from static evidence, not runtime results.

### Empty-tree insertion

Given a valid header used as the attachment node, a usable acquired node, compatible initial node state, and no disruptive dependency effects:

- Comparison is skipped even when the placement override is zero.
- The header’s offset-8, offset-4, and offset-12 links become the new node.
- The new node’s parent becomes the header.
- The count increases once.
- The root check ends balancing immediately.
- The new node receives color 1 and is written to the result destination.

### Forced first-child insertion

Given a non-header attachment node, a nonzero placement override, an empty first-child slot, and a nonzero parent color:

- Comparison is skipped.
- Attachment occurs at offset 8.
- The first-boundary link changes only if it previously equaled the attachment node.
- No balancing helper is called.
- The current root is assigned color 1.

This behavior does not validate that the override agrees with payload ordering.

### Comparison-selected second-child insertion

Given a zero placement override, a non-header attachment node, and comparison result zero:

- The comparison occurs after the count increment.
- Attachment occurs at offset 12.
- The last-boundary link changes only if it equaled the attachment node.
- No separate duplicate rejection occurs.

### Color-zero parent and uncle

Given a cursor below a color-zero parent, a valid grandparent, and an existing color-zero uncle:

- Parent and uncle become color 1.
- Grandparent becomes color 0.
- The cursor moves to the grandparent.
- That iteration performs no structural helper call.
- On eventual completion, the current root becomes color 1.

### Inner-child repair

Given a color-zero parent, an absent or nonzero-color uncle, and an inner-child configuration:

- The corresponding parent-pivot helper runs before recoloring.
- Subsequent recoloring and the grandparent-pivot call use links read after that helper.
- The result destination still receives the original acquired node, not the moved balancing cursor.
