# F-65576a99eee9

## Purpose

F-65576a99eee9 conditionally obtains two 32-bit resource-like values, stores them in shared state, and may install them into an associated object while replacing two auxiliary-object fields.

A separate path calls a dependency and then clears the first shared resource slot. This is not a symmetric reset: the routine does not explicitly clear the second resource slot or reset the associated object.

“Resource,” “acquisition,” “installation,” and “cleanup” describe the apparent roles of operations. They do not establish allocation, release, ownership transfer, or the meanings of dependency results.

A critical distinction is that early eligibility checks reference the global base separately, while later acquisition, installation-state reads, and cleanup use a base captured at entry. Those references identify the same shared-state object only under an explicit stability assumption.

### Base-reference model

The supplied representation establishes the following reference order:

1. Read the global base and retain that address as the **captured base**.
2. Separately reference the global base to read the associated-object field at `+0x10`.
3. If the entry check permits continuation, separately reference the global base to test the first resource slot at `+0x04`.
4. If that slot is zero, separately reference the global base to test the second resource slot at `+0x08`.
5. If both slots are zero, separately reference the global base to read and signed-test the request at `+0x0C`.

These early field accesses are not expressed through the captured base. Short-circuit evaluation can omit steps 4 and 5.

Subsequent request arguments, acquisition-result stores, installation-state reloads, and cleanup accesses use the captured base. They do not follow later changes to the global base.

If the global base remains unchanged throughout the early checks, all these references identify one shared-state object. Without that assumption, the initial capture and individual gate checks need not refer to the same object.

### Associated-object and dispatch layouts

After a nonzero second acquisition result, the routine reads the associated-object address from the captured base. That address supplies these fields:

| Byte offset | Width | Established use |
|---|---:|---|
| `+0x68` | 32 bits | Destination for a derived dependency result. |
| `+0x74` | 32 bits | Destination for the retained first resource value. |
| `+0x78` | 32 bits | Destination for the second acquisition result. |
| `+0x7C` | 32 bits | First auxiliary-object address, later overwritten with a replacement result. |
| `+0x80` | 32 bits | Second auxiliary-object address, later overwritten with a replacement result. |

Each auxiliary object used for dispatch begins with a 32-bit dispatch-table address. The selected callable entry is at byte offset `+0x04` within that table.

### Widths and preconditions

Field values, addresses, and stored dependency results are 32 bits in the supplied representation. Only the request eligibility comparison is signed. Its accepted range is `1` through `2,147,483,647`; zero and values with the high bit set fail that comparison. Other presence checks distinguish zero from nonzero.

The routine performs fixed-offset addressing, not resource-size arithmetic. No overflow handling, address-range validation, or alignment validation is shown.

Every reached address must support its required read, write, or dispatch operation. This applies separately to each global-based early access and to later captured-base accesses. An address captured at entry need not be dereferenced on an immediate-return path.

Dependency calls must leave any subsequently used memory valid for execution to continue normally. The routine does not establish or enforce that lifetime condition.

## Behavior

### Entry gate

The routine first captures the global base. It then separately references the global base and reads the associated-object field at `+0x10`.

If that field is zero, the routine returns immediately. No resource-slot check, dependency call, or explicit write follows.

This gate does not validate the associated-object field belonging to the captured base unless both base references identify the same shared-state object.

### Acquisition eligibility

After a nonzero entry-gate result, the routine evaluates these conditions in order:

1. The first resource slot, addressed through a fresh global-base reference, is zero.
2. The second resource slot, addressed through another global-base reference, is zero.
3. The request field, addressed through another global-base reference and interpreted as signed 32-bit, is greater than zero.

A failed condition skips the remaining conditions and reaches the cleanup decision.

If all three pass, the routine calls F-1375398b8c0d with the single argument `0`.

- A zero result reaches the cleanup decision.
- A nonzero result is retained for subsequent acquisition calls and for cleanup if that path is later reached.

The positive request check does not guarantee that either acquisition receives a positive request. Acquisition arguments come from the captured base, not from the earlier global-based request observation, and are read after a dependency call.

### First acquisition

The routine calls F-1705bbfb646a with these arguments, in order:

1. The retained nonzero result from F-1375398b8c0d.
2. The current 32-bit request field at captured-base offset `+0x0C`.
3. `1`.
4. `0`.

It writes the 32-bit result to the first resource slot at captured-base offset `+0x04`.

If that result is zero, the routine returns immediately. There is no second acquisition and no cleanup call, even if the dependency changed other memory.

The initial eligibility test does not independently guarantee that this destination slot was zero: that test used a separate global-base reference.

### Second acquisition

After a nonzero first result, the routine calls F-1705bbfb646a again with the same argument pattern. It rereads the request field from the captured base.

The two acquisitions therefore need not receive equal request values. No signed-positive check is repeated.

The second result is written to the second resource slot at captured-base offset `+0x08`.

- A zero result reaches the cleanup decision.
- A nonzero result enters the installation checks.

The second result is retained for installation. The routine does not reload the second resource slot to select the value installed into the associated object.

### Installation-state reads and eligibility

After a nonzero second result, the routine reads, in order:

1. The first resource slot from the captured base.
2. The associated-object address from the captured base.
3. The first auxiliary-object address at associated-object offset `+0x7C`.
4. The second auxiliary-object address at `+0x80`, but only if the first auxiliary-object address is nonzero.

The associated-object address is not checked for zero before its first field access. A nonzero result from the entry gate does not protect this access if the base references differed or the associated-object field changed.

Installation requires a nonzero first auxiliary-object address, a nonzero checked second auxiliary-object address, and a nonzero reloaded first resource value. The second acquisition result is also tested for nonzero, although the enclosing path already requires that result to be nonzero.

The first auxiliary field is read even when the reloaded first resource value is zero. If the first auxiliary field is nonzero, the second auxiliary field is also read before the resource-value condition prevents installation.

If installation is ineligible, the routine returns without cleanup. Acquisition-result stores already performed are not undone.

### Indirect calls and installation writes

When installation is eligible, the observable sequence is:

1. Invoke the dispatch entry at table offset `+0x04` for the captured first auxiliary object.
2. Reread the second auxiliary-object field at associated-object offset `+0x80`; resolve and invoke its dispatch entry at table offset `+0x04`.
3. Write the retained, reloaded first resource value to associated-object offset `+0x74`.
4. Write the retained second acquisition result to offset `+0x78`.
5. Call F-798fb9f4fe09 with arguments `(2, 240, 320, 320)`.
6. Store that result at offset `+0x7C`.
7. Call F-798fb9f4fe09 again with arguments `(2, 240, 320, 320)`.
8. Store that result at offset `+0x80`.
9. Call F-6d4e5f4e1b57 with the second replacement result and `4`.
10. Store the final result at offset `+0x68`.
11. Return.

The associated-object address remains the captured installation destination throughout this sequence. Changes to the global base or shared-state associated-object field do not redirect these writes.

The second indirect target is resolved after the first indirect call. It can therefore differ from the object checked during installation eligibility. No new null check protects this dispatch.

Neither replacement result is validated. A zero second replacement result is still stored and passed to F-6d4e5f4e1b57. The derivation argument is the dependency result, not a reread of the second auxiliary field.

The indirect invocations show no explicit arguments. Their implicit receiver handling and calling convention remain unspecified.

### Cleanup decision

Cleanup is reached when:

- Any acquisition-eligibility condition fails;
- F-1375398b8c0d returns zero; or
- The second acquisition returns zero.

The routine reads the first resource slot through the captured base.

If it is zero, the routine returns without a cleanup call or explicit write.

If it is nonzero, the routine calls F-88503fb8bb83, then writes zero to captured-base offset `+0x04`, then returns.

The cleanup argument is:

- The result of F-1375398b8c0d if that dependency was called, including a zero result; or
- An unspecified incoming machine value if eligibility failed before that call.

The argument is not loaded from the first resource slot. “Release the first resource” is therefore not an established interpretation.

The clearing write occurs after the cleanup dependency returns. It overwrites any intervening change that dependency made to the captured first slot. No corresponding explicit clearing write targets the second slot.

- Captured-base offset `+0x04` after the first acquisition.
- Captured-base offset `+0x08` after the second acquisition.
- Captured-base offset `+0x04` after a reached cleanup call.
- Associated-object offsets `+0x74`, `+0x78`, `+0x7C`, `+0x80`, and `+0x68` during installation.

Dependencies and indirect calls may have additional effects. No preservation of globals, shared state, object fields, or memory lifetime is established.

Stores do not establish ownership transfer. The two indirect calls precede overwriting the auxiliary fields, which is consistent with teardown intent, but their actual semantics are unknown. Aliasing between auxiliary objects is not checked; the routine does not deduplicate the calls.

No synchronization, atomic publication, or rollback is shown. Partial updates can be observable. Fields can also alias through memory arrangements not constrained by the supplied evidence; no non-aliasing guarantee is established.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, assume the global base remains stable, dependencies return normally without modifying relevant memory, and all reached addresses are valid.

1. **Entry-disabled object.** With an associated-object field of zero, the routine returns after the entry check, regardless of resource-slot contents. The initial base capture still occurs.

2. **Nonpositive request.** With a nonzero associated-object field and both resource slots zero, request values `0`, `−1`, and `−2,147,483,648` fail eligibility. Cleanup reads the zero first slot; no dependency call or explicit write occurs.

3. **Existing first slot.** A nonzero first slot short-circuits the second-slot and request checks. Cleanup calls F-88503fb8bb83 with the unspecified incoming machine value, then clears the first slot.

4. **Existing second slot only.** A zero first slot and nonzero second slot skip the request check and acquisition. Cleanup sees a zero first slot, so no dependency call or explicit write occurs.

5. **Different capture and gate bases.** Suppose the initial capture identifies object A, while all subsequent early global-base references identify object B. If B passes the entry and eligibility gates, acquisition arguments and result stores still use A. A nonpositive request in A is passed without revalidation. A preexisting first slot in A can be overwritten.

6. **Different gate and cleanup objects.** Under the same A/B distinction, a nonzero first slot in B can fail eligibility while cleanup reads A’s first slot. If A’s first slot is zero, no cleanup call occurs and B’s nonzero slot is not explicitly cleared.

7. **First acquisition fails.** A zero first acquisition result is stored, followed by immediate return. There is no second acquisition or cleanup call.

8. **Second acquisition fails.** A zero second result is stored. If the captured first slot remains nonzero, cleanup receives the retained selection result and then clears that first slot.

9. **Selection returns zero after mutation.** If F-1375398b8c0d returns zero but leaves the captured first slot nonzero, cleanup calls F-88503fb8bb83 with zero, then clears the slot.

10. **Installation ineligible.** With two nonzero acquisition results and a zero first auxiliary field, there is no eligibility read of the second auxiliary field, no indirect call, and no installation write. The routine returns without cleanup.

11. **Complete installation.** Valid nonzero resource values and auxiliary fields produce the two indirect calls, resource writes, replacement calls and stores, and derivation call and store in the specified order. Zero replacement results do not stop that sequence.

12. **Mutation during indirect dispatch.** If the first indirect call changes the second auxiliary field to another valid object, the second call targets that object. If it clears the field, the subsequent dereference has no local null guard.

13. **Request changes between acquisitions.** If the first acquisition changes the captured request to a negative 32-bit value, the second acquisition receives that value without a new eligibility test.
