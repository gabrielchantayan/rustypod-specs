# F-1a8d164bef13

## Purpose

F-1a8d164bef13 records a requested selection in an object, lazily obtains an associated resource and companion handle, conditionally invokes resource-related dependencies according to a predicate result and a selected table entry, and then performs three indirect notifications through the object’s dispatch table.

The established behavior is the sequence of field writes, field reads, conditional calls, and indirect dispatches described below. Names such as “selection,” “resource,” “companion handle,” and “notification” are descriptive labels, not established application-level meanings.

The function does not establish that the requested selection is valid, that resource acquisition succeeds, or that any dependency completes successfully. Its ordinary completion has no explicit return value.

## Interface

### Inputs

The function receives two arguments:

1. **Object address.** A pointer to mutable storage interpreted using the field layout below.
2. **Requested selection.** A 32-bit integer written to the object and used to address an eight-byte table entry.

The supplied representation uses 32-bit integer fields and four-byte address-bearing words. The following contract describes that model; it does not establish portability to another data model.

### Object layout

Offsets are byte offsets from the object address.

| Offset | Width | Role in this function |
|---|---:|---|
| `0x00` | 4 bytes | Address of a dispatch table. Read separately for each indirect notification. |
| `0x48` | 4 bytes | Stored requested selection. Written before any dependency call. |
| `0x90` | 4 bytes | Address of an entry table. Reloaded for each entry-status observation actually reached. |
| `0xAC` | 4 bytes | Associated resource word. Zero triggers initialization; a nonzero value suppresses initialization. |
| `0xB0` | 4 bytes | Companion handle passed to several dependencies. Initialized from the acquired resource only when the resource word was initially observed as zero. |

The object must provide readable or writable storage for every field accessed on the executed path. It is not enough merely to provide storage through offset `0x48`.

### Referenced layouts

**Associated resource:** when initialization occurs, the returned word is treated as an address. A four-byte field at resource offset `0x28` is read and copied into object offset `0xB0`.

**Entry table:** entries have an eight-byte stride. The function reads only the four-byte field at entry offset `0x04`. For requested selection \(s\), the relevant address is:

\[
\text{table address} + 8s + 4
\]

Zero and nonzero are the only distinctions made about this field. Its first four bytes are not read by this function.

**Dispatch table:** two slots are used:

| Slot offset | Use |
|---|---|
| `0x58` | Called twice, each time with the object and two additional argument values. |
| `0x74` | Called once, with the object and three additional argument values, the last of which is zero. |

There is no explicit result value or reported error status.

For defined ordinary execution, the caller must provide valid object storage, valid referenced storage on every reached path, and callable dispatch targets with compatible calling conventions. No selection bounds check is present. A negative selection is not rejected; whether it addresses valid storage depends on the actual address arithmetic and memory layout.

## Behavior

### 1. Store the requested selection

The function first writes the requested selection to the four-byte field at object offset `0x48`.

This precedes initialization, predicate evaluation, table-entry reads, and notifications. It occurs even if a later operation cannot complete.

Subsequent entry addressing uses the original requested-selection argument, not a reread of object offset `0x48`. A dependency can therefore change the stored selection without changing the selection used by later table-entry reads in this invocation.

### 2. Initialize the resource conditionally

The function reads object offset `0xAC`.

- If the observed value is nonzero, initialization is skipped. The function does not refresh or validate offset `0xB0`.
- If the observed value is zero:
  1. Invoke F-d189d16d5a68 with no explicit arguments.
  2. Store its returned 32-bit word at object offset `0xAC`.
  3. Read four bytes at offset `0x28` from the address represented by that returned word.
  4. Store the read value at object offset `0xB0`.

There is no null or failure check between the acquisition return and the resource-relative read. A zero return is not handled as a graceful initialization failure.

The address used for the resource-relative read is the acquisition return itself. The function does not reread object offset `0xAC` to obtain that address.

### 3. Obtain and retain a predicate result

The function invokes F-c7ba4c901230 with:

1. The current word at object offset `0xB0`.
2. The object address.

Its 32-bit result is retained for the remaining branch decisions. Zero and nonzero are distinguished; no particular nonzero value has special meaning.

The predicate is evaluated once. Later dependency effects do not cause reevaluation.

### 4. Perform conditional resource operations

The entry-status observations below are distinct reads. Each uses the then-current table address at object offset `0x90` and the original requested selection.

#### Predicate result is zero

1. Read the selected entry’s status field.
2. If this first observation is zero, skip all remaining conditional resource operations and proceed directly to the notifications.
3. If it is nonzero, invoke F-8f9bd59e3ec5 with the current companion handle and object address.
4. Read the selected entry’s status again.
5. If this second observation is nonzero, invoke F-4756a9fdee45 with the current resource word from object offset `0xAC`.

F-3e5212464798 is not called on the zero-predicate path, regardless of later entry changes.

In particular, the first nonzero observation does not guarantee a call to F-4756a9fdee45. F-8f9bd59e3ec5 may change the table pointer, the selected entry, or other state before the second observation.

#### Predicate result is nonzero

1. Read the selected entry’s status field.
2. If this observation is nonzero, invoke F-4756a9fdee45 with the current resource word.
3. Read the selected entry’s status again.
4. If this second observation is zero, invoke F-3e5212464798 with the current companion handle and object address.

F-8f9bd59e3ec5 is not called on this path.

The second observation occurs whether the first observation was zero or nonzero, provided execution reaches it. Consequently, when F-4756a9fdee45 runs, its effects can determine whether F-3e5212464798 subsequently runs.

### 5. Perform three indirect notifications

All normally completing paths converge on three indirect calls in this order:

1. A call through dispatch-table slot `0x58`.
2. Another call through dispatch-table slot `0x58`.
3. A call through dispatch-table slot `0x74`.

To describe the arguments without assigning unsupported meanings, define four fixed-location data words:

- **Shared word**
- **First payload**
- **Second payload**
- **Final payload**

The supplied material identifies four separate locations but does not reveal their values or semantic types.

Before the first notification, the function captures the shared word into a retained value. The calls have these argument shapes:

| Call | Arguments, in order |
|---|---|
| First `0x58` dispatch | Object, shared word read for this call, first payload |
| Second `0x58` dispatch | Object, retained shared word, second payload |
| `0x74` dispatch | Object, retained shared word, final payload, zero |

The shared-word argument of the first call is expressed as a separate read from the earlier retained value. The supplied representation alone does not establish whether the underlying executable performs two physical loads or reuses one load. Without an intervening change, the values coincide.

The second and third calls use the retained shared value even if an earlier notification changes the shared data location. Their payloads are obtained for their respective calls, rather than being shown as captured before the first notification.

For each notification, the function reads the object’s dispatch-table pointer and selects the relevant slot anew. It does not establish one dispatch-table snapshot for all three calls. An earlier notification can therefore affect a later dispatch by changing the object’s table pointer or its entries.

Exact ordering among operand reads within an individual indirect-call expression is not established by the supplied representation. The ordering of the three calls is established.

## Side effects

### Direct writes

The function directly writes:

- Object offset `0x48`, on every invocation reaching its first operation.
- Object offset `0xAC`, only during lazy initialization.
- Object offset `0xB0`, only during lazy initialization.

It does not directly write the selected entry’s status field.

There is no rollback of the initial selection write or initialization writes if a later operation fails to complete.

### Dependency-visible state

Dependencies can observe the selection write because it precedes every call. Their other effects are unknown.

Later argument loads and entry observations use current object state. In particular:

- The predicate can change the table before the first entry observation.
- F-8f9bd59e3ec5 can change the resource before F-4756a9fdee45’s argument is loaded.
- F-4756a9fdee45 can change the entry before the next status observation.
- A notification can change subsequent dispatch targets or payload data.

No preservation of object fields or global data by dependencies is assumed.

### Ownership and lifetime

The acquisition result and its companion field are stored without an explicit retain, duplication, release, or ownership transfer operation in this function.

The calls do not, by themselves, establish that any dependency allocates, owns, retains, or frees an object. Continued validity of the object and referenced storage across calls is an execution precondition where later accesses require it.

No locking, atomic synchronization, exception handling, retry, or explicit error reporting is shown.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Each assumes valid storage, valid dispatch targets, and normal completion of invoked dependencies.

### Stable entry status

Assume dependencies do not change the relevant fields, table, entry status, or dispatch targets.

| Predicate result | Entry status | Conditional calls, in order |
|---|---|---|
| Zero | Zero | None |
| Zero | Nonzero | F-8f9bd59e3ec5, then F-4756a9fdee45 |
| Nonzero | Zero | F-3e5212464798 |
| Nonzero | Nonzero | F-4756a9fdee45 |

Each case then performs the two `0x58` notifications followed by the `0x74` notification.

### Initialization required

Given a zero resource word and an acquisition return identifying valid resource storage:

- The requested selection is stored first.
- The acquisition return is stored at object offset `0xAC`.
- Its field at offset `0x28` is copied to object offset `0xB0`.
- The predicate receives that companion value, absent intervening external mutation.

### Initialization skipped

Given an initially nonzero resource word, acquisition is not called. The existing companion handle is used, even if it does not correspond to the resource word. This function does not check that relationship.

### Entry cleared by F-8f9bd59e3ec5

Given a zero predicate and a first nonzero status observation, suppose F-8f9bd59e3ec5 changes the subsequently selected status to zero.

F-4756a9fdee45 is skipped. F-3e5212464798 is also skipped because the retained predicate result is zero.

### Entry cleared by F-4756a9fdee45

Given a nonzero predicate and a first nonzero status observation, suppose F-4756a9fdee45 changes the subsequently selected status to zero.

F-3e5212464798 is then called with the companion handle current at that point.

### Stored selection changed by the predicate

Suppose the predicate changes object offset `0x48` to a different selection. Later table reads still use the original argument. The object field is not automatically restored.

### Notification changes dispatch state

Suppose the first notification replaces the object’s dispatch-table pointer. The second notification resolves slot `0x58` through the replacement table. The final notification likewise uses the table current when its dispatch is resolved.
