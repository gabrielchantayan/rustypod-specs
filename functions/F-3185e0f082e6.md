# F-3185e0f082e6

## Purpose

F-3185e0f082e6 conditionally offers an input to a preliminary handler and, unless that handler reports a nonzero result, attempts to obtain a recipient and forward the input to it.

The established behavior has three possible terminal paths:

1. An input whose discriminator equals 15 is accepted by dependency F-0014ea7be460, which returns nonzero. No recipient lookup or forwarding follows.
2. Preliminary handling does not terminate processing, and recipient acquisition returns null. Processing ends without forwarding.
3. Preliminary handling does not terminate processing, and recipient acquisition returns a non-null pointer. An indirect operation associated with that recipient receives the recipient pointer and the original input address.

“Accepted,” “recipient,” and “forwarding” describe the apparent roles of these operations. Their domain-specific meanings are inferred rather than established. The static evidence does not identify an event system, user interface, protocol, or ownership-transfer mechanism.

## Behavior

### Initial classification

The first established operation is a 32-bit read from the input at byte offset 4.

If the value is anything other than 15, the function skips F-0014ea7be460 and proceeds directly to recipient acquisition. No other discriminator value receives distinct local treatment.

If the value is 15, the function invokes F-0014ea7be460 with two explicit arguments, in this order:

1. The original context address.
2. The original input address.

The result is tested for zero versus nonzero:

- Any nonzero result terminates this function immediately.
- A zero result permits recipient acquisition.

The result is not required to equal one. Negative values, under a signed interpretation, are also nonzero and select the early-return path.

The discriminator is not read again by this function. If the preliminary handler changes it, that change does not cause reclassification within this invocation.

### Recipient acquisition

If processing continues, the function obtains a callable target through the context:

1. It reads the dispatch-table address from the context’s first field.
2. It reads the callable entry at byte offset 204 within that table.
3. It invokes that entry and interprets the result as a recipient pointer.

The recovered call supplies no explicit arguments. In particular, it does not visibly pass the context address as an argument. The contract must not replace this operation with an ordinary context-taking method call without separate calling-convention evidence.

For the discriminator-15 path, these context and dispatch-entry reads occur after F-0014ea7be460 returns zero. Consequently, a change made by that dependency to the context’s first field or to the selected dispatch-table entry can affect recipient acquisition. The function does not visibly cache either value before calling the preliminary handler.

A null recipient result terminates processing. There is no retry, alternative recipient lookup, fallback operation, or error result.

### Forwarding

For a non-null recipient, the function:

1. Reads the dispatch-table address from the recipient’s first field.
2. Selects the callable entry at byte offset 48 within that table.
3. Invokes the selected operation with the recipient address followed by the original input address.

The input is forwarded by address. There is no visible copy, conversion, reconstruction, or replacement of the input.

The function does not reread or restore the input before forwarding it. If a prior dependency modified the input through its address, the forwarding operation receives the same address and can observe those changes, subject to that dependency’s actual behavior.

No return value from the forwarding operation is used or propagated.

### Observable ordering

For operations directly attributable to this function, the established order is:

- Initial discriminator read.
- Optional preliminary-handler invocation and result test.
- Context dispatch-table and acquisition-entry reads.
- Recipient-acquisition invocation.
- Null-result test.
- For a non-null result, recipient dispatch-table and forwarding-entry reads.
- Forwarding invocation.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not reports of executed tests. Each assumes valid storage and callable dependencies for the path being described.

### Special discriminator with a nonzero preliminary result

Given an input whose 32-bit discriminator is 15, and F-0014ea7be460 returning any nonzero value:

- The preliminary handler receives the original context and input addresses.
- This function performs no subsequent acquisition dispatch.
- It performs no forwarding dispatch.

This remains the required local control flow if the result is negative rather than positive.

### Special discriminator with a zero preliminary result

Given discriminator 15 and a zero preliminary result:

- Recipient acquisition occurs after the preliminary handler returns.
- The context dispatch information used is read at that later point.
- A null acquired recipient ends processing.
- A non-null recipient receives the forwarding call with the original input address.

A zero result does not itself suppress forwarding.

### Any other discriminator

Given a discriminator of 0, 14, 16, or any other 32-bit value unequal to 15:

- F-0014ea7be460 is not invoked by this function.
- Recipient acquisition is attempted directly.
- A non-null recipient selects forwarding.

These examples do not imply that those discriminator values are meaningful or valid to the forwarding dependency.

### Null acquired recipient

Given that acquisition returns null:

- No recipient dispatch-table read occurs.
- No forwarding call occurs.
- No retry or explicit error result is produced.

Effects already performed by dependencies are not visibly rolled back.

### Mutated input during preliminary handling

Given discriminator 15, a preliminary handler that modifies the input and returns zero, and a non-null acquired recipient:

- The initial discriminator is not reevaluated.
- Forwarding receives the original address, not an earlier copy.
- The function performs no restoration of the modified contents.

The dependency’s ability and permission to make that modification remain separate contract questions.

### Changed dispatch information

Given a preliminary handler that changes the context dispatch information and returns zero:

- Acquisition uses the dispatch information read after that handler returns.
- The function does not use a locally preserved pre-handler table pointer.

This example assumes the changed information remains valid.
