# F-97802979f8fe

## Purpose

F-97802979f8fe conditionally processes byte-valued items associated with an object, updates a progress word, and may pass a status mask to a dependency. Every explicit normal return yields the original object pointer.

The behavior has two principal paths:

- If the object's initially observed status word is nonzero, reset the progress word and submit that saved status, optionally augmented by a flag-derived bit.
- If the initially observed status is zero, optionally invoke a preliminary dependency, then either return immediately or enter an item-processing loop.

**Inferred intent:** The loop resembles examining input, classifying its low byte, and advancing while classification succeeds. The dependency implementations are unavailable, so terms such as “input,” “classification,” and “advance” describe apparent roles, not established external semantics.

### Referenced layout

Two address origins are used:

1. The original object pointer.
2. A dynamically resolved adjusted base.

The adjusted base is obtained by:

- Reading the address-like word at object byte offset `0`.
- Reading a signed 32-bit displacement from 12 bytes before that referenced address.
- Adding that displacement to the original object address.

The body references these locations:

## Behavior

### Entry and initial decision

The function first resolves the adjusted base and reads its status word at offset `0x10`. It saves this value for subsequent control flow.

It then writes zero to the progress word at original-object offset `4`.

This ordering matters: the initial status is sampled **before** the reset. If those locations alias through the supplied layout, the branch decision still uses the value read before the write.

The initial status is not re-read to select a different principal path after dependency calls.

### Initially nonzero status

When the saved initial status is nonzero:

1. No preliminary dependency or item-processing dependency is called directly by this body.
2. The function forms a status mask from the saved initial status.
3. If option bit `0x10` is set, it ORs `0x04` into that mask.
4. It freshly resolves the adjusted base and calls F-8434be7161a5 with that base address and the mask.
5. It returns the original object pointer.

Option bit `0x04` does not enable processing on this path.

The progress reset has already occurred before the status dependency is called. The progress word's value after that call is not guaranteed because the dependency's side effects are unknown.

### Initially zero status: preliminary action

When the saved initial status is zero, the function freshly resolves the adjusted base and reads its word at offset `0x38`.

If that word is nonzero, it calls F-6b7721c24036. No explicit arguments are shown for this call. Its return value, if any, is not used.

This conditional call occurs before testing option bit `0x04`. Consequently, it can occur even when item processing is disabled.

If option bit `0x04` is clear, the function returns the original object pointer immediately. It does not submit a status through F-8434be7161a5, even if option bit `0x10` is set.

### Loop initialization

If the initial status was zero and option bit `0x04` is set:

1. The function freshly resolves the adjusted base and reads the opaque word at offset `0x34`.
2. It passes that word to F-17fd030b083e.
3. The returned 32-bit value becomes the current item word.
4. After that call returns, it resolves and saves the signed displacement used for the classification-context address.

That saved displacement is reused throughout the loop when forming the address at adjusted-base offset `0x18`. The body does not refresh it on each iteration.

By contrast, the opaque field at offset `0x34` is resolved and read again during each successful processing iteration.

### Loop entry check

At the beginning of every iteration, the function:

- Writes the 32-bit all-ones pattern `0xFFFFFFFF` into a scratch marker.
- Calls F-bc87c1bea934 with the addresses of the current item word and that marker.

These arguments identify writable scratch storage. The dependency may modify either word; the body does not establish read-only semantics.

If F-bc87c1bea934 returns nonzero, the loop ends and the function proceeds to status submission using terminal status `0x02`.

If it returns zero, the function takes the low eight bits of the current item word **as it exists after this call**. The other 24 bits do not enter the subsequent classification argument.

The all-ones marker does not, by itself, establish an end-of-input convention. The branch is controlled by the dependency's return value.

### Classification and early return

For a zero result from the loop entry check:

1. The function calls F-cde265cd2c93 with the address formed from the original object, the saved displacement, and byte offset `0x18`.
2. It calls F-3e0e547bb25a with:
   - The opaque result of F-cde265cd2c93.
   - The value `1`.
   - The zero-extended low byte selected from the current item word.

If F-3e0e547bb25a returns zero, the function immediately returns the original object pointer.

On this early-return path:

- The subsequent item-operation dependency is not called.
- No progress increment occurs for this iteration.
- No terminal status is submitted.
- Option bit `0x10` has no direct effect.

If classification returns nonzero, processing continues.

### Item operation and progress update

After a nonzero classification result:

1. The function freshly resolves the adjusted base and reads the opaque word at offset `0x34`.
2. It saves that word as the argument for the following item-related calls.
3. It calls F-f41833c4f215 with the saved word.
4. It stores that dependency's 32-bit result in scratch storage.
5. It writes `0xFFFFFFFF` into a second scratch word.
6. It calls F-bc87c1bea934 with the addresses of those two scratch words.

If this second check returns zero, the function calls F-17fd030b083e with the **same saved opaque word** used for F-f41833c4f215. Its result replaces the current item word.

The field at offset `0x34` is not re-read between those two calls. A dependency changing the object's field therefore does not change the argument used for this particular refresh.

If the second check returns nonzero, the function instead assigns `0xFFFFFFFF` to the current item word.

The function then reads the progress word, adds one, writes the result back, and begins the next iteration.

The increment occurs after the optional refresh call. It uses the progress value present at that time, not a locally maintained count. Dependency writes to that field can therefore affect the resulting value.

A nonzero result from the second check does **not** immediately cause terminal status submission. The next iteration still invokes the loop entry check, which determines whether the loop ends.

### Terminal status submission

When a loop entry check returns nonzero, the submitted status is:

- `0x02` if option bit `0x10` is clear.
- `0x06` if option bit `0x10` is set.

The function freshly resolves the adjusted base, calls F-8434be7161a5 with that address and the status, then returns the original object pointer.

## Side effects

### Direct writes

The established direct writes are:

- One zero write to the progress word on entry.
- One progress-word increment after each iteration that reaches the end of the item-operation sequence.
- Writes to local scratch words used in dependency calls.

The body does not directly write the adjusted-base status word, the opaque field at `0x34`, or the word at `0x38`.

Passing the adjusted base to F-8434be7161a5 does not establish which fields that dependency modifies.

### Observable ordering and dependency effects

The call sequence is serial. In particular:

- Initial status read precedes progress reset.
- Progress reset precedes all dependency calls.
- The optional preliminary call precedes the processing-option test.
- Initial item retrieval precedes capture of the displacement reused for classification.
- Classification precedes the item operation.
- Item operation, second check, and optional refresh precede progress increment.
- Terminal status submission follows a nonzero loop entry check.

Unknown dependencies may alter object storage, layout metadata, global state, or externally visible resources. No preservation guarantee is supplied. Fresh address resolutions and reads must therefore remain distinguishable from cached ones.

### Arithmetic and termination

Option and status masks are 32-bit values. Byte selection retains exactly the low eight bits.

The progress update is expressed as signed integer addition in the supplied representation. Behavior at signed overflow is not established; this contract does not promise saturation or portable modulo arithmetic.

The body provides no independent iteration bound. Termination depends on dependency results and successful return from calls. Exceptions, faults, nonlocal exits, and dependency-level error handling are undocumented.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless stated otherwise, assume valid, stable layout data, non-overflowing arithmetic, and dependencies that do not modify the object.

1. **Initially nonzero status.**  
   Initial status `0x08`, options `0x10`: reset progress, call F-8434be7161a5 with status `0x0C`, and return the original pointer. No item-processing calls occur.

2. **Processing disabled after preliminary action.**  
   Initial status zero, offset `0x38` nonzero, options `0x10`: reset progress, invoke F-6b7721c24036, and return. No status submission occurs.

3. **Immediate loop termination.**  
   Initial status zero, options `0x14`, first loop entry check nonzero: perform initial item retrieval, then submit `0x06`. No classification or progress increment occurs.

4. **Classification rejects the first item.**  
   First entry check zero, current item `0x1234ABCD`, classification result zero: pass byte value `0xCD` to classification and return without item operation or terminal status submission.

5. **The entry check changes the item.**  
   Initial retrieval returns `0x11223344`; the entry check replaces it with `0x55667788` and returns zero: classification receives byte `0x88`, not `0x44`.

6. **One completed iteration followed by termination.**  
   First entry check zero, classification nonzero, item-operation check zero, next entry check nonzero: perform the refresh before incrementing progress to one, then submit terminal status.

7. **Item-operation check reports nonzero.**  
   After successful classification, the second check returns nonzero: skip refresh, set the current item to `0xFFFFFFFF`, increment progress, and invoke another loop entry check. Terminal submission is conditional on that next check.

8. **Progress changed by a dependency.**  
   A dependency leaves the progress word at seven immediately before the increment: the direct update writes eight. It does not overwrite the field with a separately tracked iteration count.
