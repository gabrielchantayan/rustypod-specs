# F-0c60c178a59c

## Purpose

F-0c60c178a59c writes a caller-supplied 32-bit value, with two bits forced on, to a selected record and then polls that record. It returns the 32-bit value 1 when any of three conditions occurs:

- Bit 1 of a status word is set.
- Bit 31 of the record’s first word is clear.
- A polling dependency returns a nonzero result.

The return value does not distinguish these conditions. In particular, it does not separately report completion, failure, or expiration.

**Inferred intent:** The record layout and repeated reads resemble a command-and-status interface, potentially for memory-mapped hardware. The two dependencies resemble a timing-token acquisition operation and an elapsed-time check. These interpretations are not established by the supplied evidence and are not required to describe the observable control flow.

## Behavior

### Initial address capture and write

The function first reads the shared base-address value and retains that value for polling.

It then writes one 32-bit word to offset 0 of the selected record. The address for this write is formed using a separate use of the shared base-address location and the second argument’s 32-byte stride.

The written value is the third argument bitwise-ORed with `0x48000000`. Consequently:

- Bit 30 is set.
- Bit 27 is set.
- Every other bit retains the value supplied by the caller.
- Bit 31 is not forced either on or off.

This is not a read-modify-write of the destination. The visible body does not first read the destination to preserve any preexisting bits.

The initial store precedes both the first dependency call and the first status read.

The distinction between the captured polling base and the separately obtained write base matters if the shared base can change between those operations. In that case, the write and polling accesses can target different record regions. The body does not reconcile them.

### Acquisition dependency

After the initial write, the function calls dependency F-000000000001 with no explicit arguments.

Its 32-bit result becomes a token passed to the later polling dependency. The body does not inspect, transform, validate, or compare this token.

This call occurs even if the first subsequent status read will immediately cause a return.

### Polling order

Each polling iteration begins by reading the selected record’s 32-bit word at offset 8, using the captured polling base.

If bit 1 is set, the function immediately returns 1. It does not read offset 0 or invoke the polling dependency during that iteration.

If bit 1 is clear, the function reads the selected record’s 32-bit word at offset 0.

If bit 31 of that word is clear, the function returns 1. It does not invoke the polling dependency during that iteration.

Only when both conditions hold—

- status bit 1 is clear, and
- bit 31 of the first word is set—

does the function call F-000000000002. It supplies:

1. The unchanged token returned by F-000000000001.
2. The integer value 100.

A nonzero result from F-000000000002 causes an immediate return of 1. A zero result starts another iteration, beginning with another read at offset 8.

The order is significant. The status condition takes precedence over reading the first word. The first-word condition takes precedence over calling F-000000000002.

### Repeated observations and termination

The body performs fresh polling reads rather than deciding from the value initially written. External changes to either polled word can therefore affect subsequent control flow.

The token is acquired once, not once per iteration. Every invocation of F-000000000002 receives that same token and the same second argument.

The visible body has no iteration limit. If every status read has bit 1 clear, every first-word read has bit 31 set, and every call to F-000000000002 returns zero, polling continues indefinitely.

The value 100 does not by itself establish a duration, unit, deadline, sleep interval, or maximum iteration count.

## Acceptance examples

These examples are conditional contracts derived from static evidence, not executed tests. They assume valid address calculations, successful memory accesses, and returning dependencies.

### Forced command bits

If the third argument is `0x00000000`, the initial store writes `0x48000000`.

If the third argument is `0x80000000`, the initial store writes `0xC8000000`.

If the third argument is `0xFFFFFFFF`, the initial store writes `0xFFFFFFFF`.

These examples concern the store value only. They do not predict what later reads will observe.

### Immediate status exit

If the first status read returns `0x00000002`, the function returns 1 after the initial store and F-000000000001 call.

No first-word read and no F-000000000002 call occur in that iteration.

### First-word exit

If the first status read has bit 1 clear and the following first-word read returns `0x48000000`, the function returns 1 without calling F-000000000002.

This depends on the observed first-word value, not merely on the value initially written.

### Nonzero dependency result

If status bit 1 is clear, the following first-word read has bit 31 set, and F-000000000002 returns any nonzero value, the function returns 1 without another polling iteration.

### Continued polling

If those same memory conditions hold but F-000000000002 returns zero, another status read follows. If that next status read has bit 1 set, the function returns 1 without a second first-word read.

### Different write and polling bases

If the shared base changes after its initial capture but before the separate base use for the store, the store uses the later base while polling uses the earlier captured base. No corrective write or base refresh is shown.
