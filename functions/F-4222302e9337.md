# F-4222302e9337

## Purpose

F-4222302e9337 scans blocks containing 16 fixed-stride marker positions. Candidate markers trigger workspace processing. Exact equality between a workspace value and a request-derived requirement selects preparation and completion. Exhausting a block can lead to acquisition of another block or an extension-related operation.

These operations are established by static control flow. Interpreting markers as directory entries, the workspace value as a contiguous-run length, or extension as allocation is **inferred intent**, not an established contract.

One path returns a dependency-supplied 32-bit completion status unchanged. Every other terminating path returns zero. Zero therefore does not distinguish failure from completion with status zero.

## Interface

### Arguments and result

| Input | Established representation and use |
|---|---|
| Destination state | Address of writable storage containing at least seven consecutive 32-bit fields. |
| Source state | Address of storage containing at least two consecutive 32-bit fields; also passed to dependencies with unknown mutation behavior. |
| Request | Opaque 32-bit value supplied to request processing and later preparation. |

The result is an unsigned 32-bit value, not a normalized Boolean.

### Destination-state layout

Offsets are in bytes.

| Offset | Width | Established use |
|---|---:|---|
| `+0x00` | 32 bits | Context address, initially copied from source `+0x00`. |
| `+0x04` | 32 bits | Preexisting workspace address; not explicitly initialized here. |
| `+0x08` | 32 bits | Initial position supplied by F-a08c4da10b41. |
| `+0x0c` | 32 bits | Current position, initially equal to the initial position. |
| `+0x10` | 32 bits | Record-index field, cleared at specified transitions and set after successful preparation. |
| `+0x14` | 32 bits | Cleared during initialization. |
| `+0x18` | 32 bits | Most recently stored block address. |

The function maintains a separate internal scan index. It does not write that index to `+0x10` for every marker. It does not explicitly update `+0x08` when the current position changes.

Source `+0x00` supplies a context address; source `+0x04` supplies an opaque 32-bit resolution argument.

### Referenced storage and preconditions

The workspace supports a region beginning at `+0x40`, including a 32-bit value at `+0x40` and a byte at `+0x48`. Dependencies receive either the workspace address or the region address.

Each scanned block supports marker-byte accesses from `+0x18` through `+0x1f8`, spaced `0x20` bytes apart. This does not establish the intervening record layout.

Context storage supports a 16-bit discriminator at `+0x6c`. Fallback paths also access a 32-bit field at source-context `+0x70`.

Addresses and address-bearing fields are represented as 32-bit quantities. Later block acquisitions supply a represented 64-bit result containing a lower 32-bit block address and an upper 32-bit auxiliary word. Its complete ABI is **documented_only**.

No explicit pointer, alignment, range, ownership, or non-aliasing validation is visible. Storage must support every reached access and dependency requirement. Acquired zero blocks are checked; zero context and workspace addresses are not independently rejected.

Aliasing and dependency mutation must remain possible. A later state-field reload cannot generally be replaced by an earlier snapshot. Ordering described below is explicit statement and control-flow ordering; evaluation order between separate argument expressions of one call is not independently established.

## Behavior

### Request processing and initialization

Before any explicit destination-state write, F-1cb585febd84 receives the request. Its 32-bit result, increased by 12, and the constant 13 are passed to F-d7be9cfb4000. That result, increased by one, supplies the required workspace value used in equality comparisons.

These are 32-bit expressions with no visible wider intermediate or overflow check. Exact signed-overflow behavior is **documented_only**. The dependency names do not establish division, rounding, string length, or request encoding.

Initialization proceeds in this order:

1. Copy source `+0x00` to destination `+0x00`.
2. Clear destination `+0x14`.
3. Call F-a08c4da10b41 with the source-state address.
4. Store its result at destination `+0x08`, then `+0x0c`.

A zero initial position returns zero immediately. No explicit initialization of destination `+0x10` or `+0x18` has occurred.

For a nonzero position, clear destination `+0x10`, call F-04b7df4e1a09 with the destination context and current position, and store the block result at `+0x18`. A zero block returns zero without workspace initialization or common cleanup.

For a nonzero block:

- F-31748fbe220b receives the workspace address and supplies a retained byte.
- The internal end-marker flag becomes false.
- F-8e0ab1d7a3f2 receives the workspace-region address, with one explicit argument.
- The auxiliary return-register word associated with that initialization call becomes the initial scan’s carried auxiliary value.
- The retained byte is written at workspace `+0x48`, using a fresh workspace-field read.

Consequently, mutation of the workspace field by the initialization dependency can redirect the byte store. The active block remains the originally acquired block.

### Block scanning and marker classification

Every scanned block starts with internal index zero and an explicit clear of destination `+0x10`. Marker addresses advance by `0x20`, covering 16 positions in ascending order. The active block is retained independently of destination `+0x18`.

Classification is:

- A zero marker sets the end-marker flag and selects candidate processing.
- A marker represented as signed −27, corresponding to eight-bit `0xe5`, selects candidate processing.
- Once the end-marker flag is set, subsequent markers select candidate processing regardless of their values.
- Otherwise, the marker selects the noncandidate operation.

The end-marker flag persists across block boundaries.

The representation first tests the marker for zero and, on the nonzero branch, evaluates the marker again for the `0xe5` comparison. A single atomic read is not established.

### Carried auxiliary value

The noncandidate F-8e0ab1d7a3f2 call has two explicit arguments: the current workspace-region address and a carried 32-bit auxiliary value. Its visible dataflow is:

| Event | Carried value afterward |
|---|---|
| Initial workspace initialization | Auxiliary return-register word associated with the one-argument F-8e0ab1d7a3f2 call. |
| Start of a subsequent acquired block | Upper 32-bit word of that block-acquisition result. |
| First workspace `+0x40` read in candidate processing | The 32-bit value just read. |
| Candidate operation F-51e448cd1d6a, when called | Auxiliary return-register word associated with that call. |
| Noncandidate F-8e0ab1d7a3f2 | Auxiliary return-register word associated with that call, replacing the value passed as its second argument. |

The later-block rule applies both to successful transition acquisition through F-04b7df4e1a09 and successful post-extension acquisition through F-509db5f0f60d. The lower word supplies the active block; the upper word starts that block’s auxiliary sequence.

The second workspace read in candidate processing tests equality but does **not** replace the carried value. Thus, absent an exit, a later noncandidate call receives the first candidate read or the candidate operation’s auxiliary result, not necessarily the latest workspace value.

These origins, replacements, and argument uses are established by the supplied representation. Their application meaning and complete calling convention remain **documented_only**.

### Candidate processing and completion

Candidate processing first reads the 32-bit workspace value at `+0x40`, replacing the carried auxiliary value as described above.

If that value differs from the requirement, F-51e448cd1d6a receives the workspace-region address, current position reloaded from destination `+0x0c`, and internal scan index. Its auxiliary return-register state replaces the carried value.

The workspace value is then read again, whether or not the candidate operation ran. Only exact equality selects preparation. A greater value does not qualify merely because it exceeds the requirement.

On equality, F-3a6ee676402e receives the workspace-region address. F-915450f6c307 then receives the destination context, workspace-region address, and original request.

A zero preparation result causes F-2b1ba6d8de9d to receive the retained active block and flag 1, followed by common cleanup.

For nonzero preparation:

1. Store the internal scan index at destination `+0x10`.
2. Call F-4a58994bf609 with the selected marker address and workspace address.
3. Call F-c7bbf7146083 with a fresh read of destination `+0x18`.
4. If its unsigned 32-bit status is nonzero, call F-eacf2e4e8b78 with the workspace and destination context.
5. Call F-2b1ba6d8de9d with the retained active block and a binary flag.
6. Return the completion status unchanged.

The final flag is 1 for status zero and 0 for every nonzero status, including statuses greater than one.

F-c7bbf7146083 can receive a different block from F-2b1ba6d8de9d: completion uses a state-field reload, whereas the latter uses the retained scan block. Completion never enters common cleanup, even for status zero.

### Exhausting a block

After all 16 markers without completion, F-2b1ba6d8de9d receives the active block and flag 0. F-f915a78bdf25 then receives the destination-state address.

A nonzero transition result causes F-04b7df4e1a09 to receive the destination context and current position. The acquisition’s lower word is stored at destination `+0x18`. A nonzero block resumes scanning with the acquisition’s upper word as the new carried auxiliary value. A zero block enters common cleanup.

The function does not explicitly advance current position on this branch; any such change is delegated to F-f915a78bdf25.

A zero transition result selects the extension-related path.

### Extension-related path

The function reads the source context through source `+0x00` and inspects its 16-bit discriminator. If it is not 8, F-d51dfd79b768 receives the source-state address. A nonzero result returns zero immediately without common cleanup. A discriminator of 8 bypasses that call.

Extension resolution then follows a distinct snapshot/reload sequence:

- Snapshot the destination context and inspect its discriminator.
- Call F-40e4fc419124 with that snapshotted context and source `+0x04`.
- Only if the **pre-call discriminator was 8** and the resolution result is zero, call F-51d0c0e686a6.
- That fallback receives a reloaded destination context and the 32-bit field at `+0x70` of the context then referenced by the source state.

Changing the discriminator during resolution cannot change fallback eligibility. Changing destination context can change the fallback’s first argument.

F-1b715a5faa3a next receives a newly read destination context and the resolved value. Its result replaces the retained extension token, initially zero. A zero token returns zero immediately without common cleanup.

For a nonzero token, F-08426f0ea83d receives the destination context and token. Its result is stored as current position, then destination `+0x10` is cleared. F-344d07e6c0c6 receives the destination context and token.

A zero gate result enters common cleanup without new acquisition. Otherwise, F-509db5f0f60d receives the destination context and current position. Its lower result word is stored at `+0x18`. A nonzero block resumes scanning using its upper word as the carried auxiliary value; a zero block enters common cleanup.

Successive context arguments are reloaded, not guaranteed equal. The extension token survives later transitions until another reached token-producing call replaces it.

### Common cleanup

Common cleanup independently snapshots the destination context and inspects its discriminator before calling F-40e4fc419124 with that context and source `+0x04`.

Only a **pre-call discriminator of 8** combined with a zero resolution result selects F-51d0c0e686a6. Here the fallback receives the **source context**, not the extension path’s reloaded destination context, together with source-context `+0x70`.

After resolution, including any fallback, the function reloads destination context. F-05324c739c5c receives that context, the resolved value, and the retained extension token. Its return value is ignored; the function returns zero.

Thus fallback eligibility belongs to the earlier discriminator snapshot, while the final cleanup context belongs to a later reload.

## Side effects

Explicit writes affect destination fields and workspace byte `+0x48`. No explicit scanned-marker write appears. Dependencies may perform additional mutations or resource operations, but their contracts are unavailable.

The carried auxiliary value is internal state passed to noncandidate calls, not a separately exposed destination field. Its propagation does not establish ownership or application-level meaning.

F-2b1ba6d8de9d receives flag 0 after exhaustion, flag 1 after preparation failure, and the completion-dependent flag otherwise. These patterns do not establish release, commit, rollback, or ownership transfer.

Destination `+0x18` is not explicitly cleared after those calls. Its continued validity on return is unknown.

Common cleanup is not universal. Zero initial position, zero initial block, rejection by F-d51dfd79b768, zero extension token, and completion return directly. No universal state restoration or resource release is established.

## Acceptance examples

These are conditional static cases, not executed tests. Assume valid storage, representable arithmetic, and no mutations contradicting stated conditions.

1. **Zero initial position.** Both position fields become zero after context copying and the `+0x14` clear. No acquisition occurs. The result is zero.

2. **Zero initial block.** The nonzero position is stored, `+0x10` is cleared, and `+0x18` becomes zero. Workspace initialization and common cleanup are skipped.

3. **Initial auxiliary propagation.** Initialization supplies auxiliary word 37. The first marker is noncandidate. Its F-8e0ab1d7a3f2 call receives 37 as its second argument. If that call supplies auxiliary word 91, a following noncandidate call receives 91.

4. **Candidate auxiliary replacement.** An `0xe5` marker is reached before any zero marker. The first workspace read is 4 and the requirement is 7, so F-51e448cd1d6a runs. If its auxiliary word is 23 and the second workspace read remains unequal, a following noncandidate call receives 23, not 4.

5. **Second read does not replace auxiliary state.** The first candidate read equals the requirement, so the candidate operation is skipped. If the second read differs and scanning continues, the carried value remains the first read’s value.

6. **New-block auxiliary seed.** A successful later acquisition supplies a nonzero lower word and upper word 55. The new block’s first noncandidate call receives 55, regardless of the preceding block’s final carried value. This applies to both acquisition paths.

7. **End marker across blocks.** A zero marker sets the persistent flag. After successful acquisition of another block, an ordinary nonzero, non-`0xe5` marker still takes candidate processing.

8. **Value above requirement.** If the value differs before the candidate operation and remains above the requirement afterward, preparation does not occur.

9. **Preparation failure.** Equality followed by zero preparation produces an active-block call with flag 1, then common cleanup and a zero return.

10. **Completion statuses.** Status 2 triggers F-eacf2e4e8b78, active-block flag 0, and return 2. Status zero skips that additional operation, uses flag 1, and returns zero without common cleanup.

11. **Zero extension token.** The exhausted block has already received flag 0. A zero token returns immediately without F-05324c739c5c.

12. **Extension discriminator mutation.** A snapshotted discriminator of 8 and zero resolution result select fallback even if resolution changes the discriminator. The fallback uses a reloaded destination context.

13. **Discriminator changes to 8 too late.** A pre-call discriminator other than 8 prevents fallback despite a zero resolution result and a subsequent change to 8. This applies independently to extension resolution and cleanup.

14. **Cleanup context distinctions.** With a snapshotted discriminator of 8 and zero resolution, cleanup fallback receives the source context. If fallback changes destination context, F-05324c739c5c receives the destination context reloaded afterward.

## Uncertainties

The following remain **documented_only**:

- Application-level record format, request encoding, discriminator meaning, and status meanings.
- Whether the workspace value represents length, count, or another quantity.
- Application meaning of auxiliary words and the complete multiword-return/register convention.
- Dependency mutation, allocation, ownership, release, persistence, and rollback behavior.
- Exact overflow behavior of request-derived additions and address arithmetic.
- Byte order, alignment requirements, concurrency guarantees, and invalid-storage behavior.
- Termination when dependencies continue supplying blocks without completion.

Auxiliary dataflow is established even though auxiliary meaning is unknown. No dependency is assumed to preserve reachable or global state, retain ownership, or release memory merely because of its call-site role.

## Evidence

Established behavior comes from the supplied static representation: widths, offsets, explicit accesses, branch conditions, argument flow, retained values, and return expressions.

The auxiliary sequence is supported by initialization’s associated return-register state, upper-word extraction on subsequent acquisitions, replacement by the first candidate workspace read, replacement after the candidate operation, and replacement after each noncandidate operation. The second candidate workspace read controls equality without replacing the carried value.

Both resolution paths inspect the destination-context discriminator before resolution. Extension fallback reloads destination context; cleanup fallback uses source context; final cleanup reloads destination context after resolution.

No dependency implementations or independent interface definitions were supplied. No runtime tests have been performed.
