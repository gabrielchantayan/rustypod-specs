# F-bbbf6c163239

## Purpose

F-bbbf6c163239 conditionally searches an indirectly referenced collection for an entry whose 32-bit unsigned key equals the requested key. It returns the matching entry’s address, represented by the function’s integer return value, or zero when the search is disabled, the requested key is zero, no collection becomes available, or the examined entries contain no match.

The collection may be populated by a dependency when its reference is initially zero. The search combines midpoint probes with a final ascending scan of at most two positions for ordinary valid collection sizes.

**Established behavior:** comparisons use unsigned 32-bit entry keys. The function does not validate collection ordering, pointer validity, allocation size, or entry contents.

**Inferred intent:** the collection is an ascending key-sorted index, and the returned address identifies an existing entry rather than a newly created result. Sortedness is necessary for general search completeness, but is not enforced.

## Interface

### Inputs

The function takes two machine-level arguments:

| Input | Representation | Meaning |
|---|---|---|
| Object address | Integer-form address in the supplied 32-bit layout | Identifies an object containing the collection reference at byte offset `0x900`. |
| Requested key | Unsigned 32-bit integer | Key to locate. Zero disables collection access and searching after the initial dependency call. |

The object’s full layout is unknown. Only the following fields are accessed directly:

| Structure | Byte offset | Width | Interpretation |
|---|---:|---:|---|
| Object | `0x900` | 4 bytes | Collection address; zero means unavailable. |
| Collection | `0x08` | 4 bytes | Signed entry count. |
| Collection | `0x0C + 4 × position` | 4 bytes | Address of the entry at the zero-based position. |
| Entry | `0x20` | 4 bytes | Unsigned search key. |

The collection therefore exposes a four-byte-stride array of entry addresses beginning at byte offset `0x0C`. The contents before the count field, and any other entry fields, are not established.

### Output

The return value is a 32-bit integer-form entry address, or zero.

A nonzero result is obtained from a collection slot; the function does not construct a result object. The return type alone does not establish ownership, lifetime, mutability, or whether callers may release the returned entry.

### Preconditions for defined, reliable searching

For a search that reaches collection access:

- The object must permit the four-byte reference reads at offset `0x900`.
- The selected collection must permit reading its count and every slot the search examines.
- Each examined slot must contain an address permitting a four-byte key read at offset `0x20`.
- Address calculations and signed search arithmetic must remain within the applicable representation and arithmetic rules.
- The collection must remain sufficiently stable for repeated reads to describe a coherent search.
- For a general guarantee of finding a present key, the entry keys must be in nondecreasing unsigned order.

There are no explicit checks enforcing these conditions. Invalid memory does not have an established zero-return recovery path.

## Behavior

### 1. Initial gating

F-06f4ceb6a4f2 is called once, before testing whether the requested key is zero and before any direct object-field access.

If that dependency returns zero, F-bbbf6c163239 returns zero. It performs no direct collection-reference, count, slot, or entry-key reads.

If the dependency returns nonzero but the requested key is zero, the function also returns zero without directly accessing those fields.

Consequently, a zero key does not make the function side-effect-free: the initial dependency still runs. Likewise, an invalid object address is not directly dereferenced on either early-exit path, but that observation does not establish what the dependency may access through other means.

### 2. Collection availability

When the initial dependency returns nonzero and the key is nonzero, the function reads the collection reference at object offset `0x900`.

- If that read is nonzero, the population dependency is not called.
- If that read is zero, F-40f9148e1210 is called with the object address. Its return value is ignored. The object’s collection reference is then read again.
- If the post-call reference remains zero, the function returns zero.

Once availability has been established, the function reads the collection reference again and uses that value as the collection address for the search.

Thus, the direct reference-read sequence is significant:

- Initially available collection: one availability read, followed by a separate selection read.
- Initially unavailable collection: one availability read, the population call, one post-call availability read, and—if nonzero—one separate selection read.

The value used for searching is the final selection read, not necessarily the value observed by an earlier availability read. There is no further nonzero check on the selected value.

No successful population result is inferred from the dependency’s return value. The post-call object field alone controls whether execution advances.

### 3. Search initialization

The selected collection’s signed 32-bit count is read once.

The initial lower search position is zero. The initial upper position is the count minus one. The implementation does not separately validate that the count is nonnegative or that the backing slot array has that many entries.

For ordinary nonnegative counts:

- Count zero produces no slot or key reads and returns zero.
- Count one proceeds directly to checking position zero.
- Count two proceeds directly to checking positions zero and one in ascending order, stopping at the first match.
- Larger counts may enter the midpoint-search phase.

For negative counts where the subtraction is representable, neither search phase examines an entry, and the function returns zero. This is an observed consequence of the bounds, not evidence of a supported negative-count convention.

### 4. Midpoint-search phase

While the upper and lower positions differ by more than one, the function probes their midpoint.

The midpoint is derived using signed addition and signed division by two. With ordinary nonnegative, representable bounds, this selects the lower middle position when the sum is odd.

For each midpoint probe, the function:

1. Reads the entry address from the midpoint slot.
2. Reads the unsigned 32-bit key at entry offset `0x20`.
3. Compares that key with the requested key.

If the keys are equal, the function reads the midpoint slot again and immediately returns the address obtained by that second slot read.

If the requested key is less than the probed key under unsigned comparison, the upper position becomes the midpoint. Otherwise, the lower position becomes the midpoint.

The midpoint is retained as a boundary rather than excluded. Consequently, a slot or entry key already examined during midpoint probing may be read again during a later probe or the final scan.

A match at a midpoint terminates immediately. There is no attempt to find the first or last occurrence of a duplicate key.

### 5. Final scan

After midpoint probing ends, the function examines the remaining positions in ascending order, including both bounds.

For each position, it reads the slot once, reads the referenced entry’s key, and compares that key with the requested key. A match returns the address already read from that slot; unlike the midpoint-match path, this path does not reread the slot before returning.

For ordinary nonnegative counts and valid arithmetic, the final scan examines at most two positions. An empty collection examines none.

If no examined key matches, the return value is zero.

### Ordering and duplicate keys

Unsigned nondecreasing ordering makes the bound updates suitable for locating an equal key. No ordering check is performed.

An unsorted collection can yield zero even when a matching key exists in an unexamined slot. Conversely, a matching key encountered in any probed slot is accepted without checking the rest of the collection.

With duplicate keys, the selected entry depends on the search path:

- An equal midpoint entry wins immediately.
- If no midpoint match occurs, the first equal entry encountered in the ascending final scan wins.

There is no general lowest-position, highest-position, or stable-identity guarantee across collection rearrangements.

- Availability and collection selection use separate reference reads.
- Slots and keys may be read more than once.
- A midpoint match rereads its slot after comparing the earlier referenced entry’s key.

Stable collection state is therefore a precondition for interpreting every successful return as an address whose current key matches the request. Atomicity and concurrent-mutation semantics are not established.
