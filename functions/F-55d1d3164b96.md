# F-55d1d3164b96

## Purpose

F-55d1d3164b96 conditionally returns an existing record or constructs a second record using selected fields from the input.

The established decision is controlled by the low bit of the input record’s sixth integer field:

- A null input produces a null result without calling a dependency.
- A nonnull input whose control field has bit 0 clear is returned unchanged by identity.
- A nonnull input whose control field has bit 0 set enters a construction path. The function requests a destination record, obtains storage for a primary region, conditionally obtains storage for two auxiliary regions, and returns the destination if every checked request succeeds.
- A checked failure causes an error-reporting call and a null return. Failures after destination creation also trigger cleanup calls.

The apparent intent is to turn a flagged record into a separately backed record. That interpretation is **inferred**, not a complete established ownership contract. The supplied evidence does not establish the semantics of the storage, transfer, length-like, or cleanup dependencies.

## Interface

The function accepts one record pointer and returns one record pointer.

## Behavior

### Entry and construction gate

The function begins with its locally retained auxiliary-B allocation value set to zero.

It first checks whether the input pointer is null. If so, it returns null immediately.

Otherwise, it reads the control field and tests bit 0. If the bit is clear, it returns the input pointer. This path performs no destination writes, error reporting, or dependency calls.

If bit 0 is set, the function reads the control field for the call to F-c42e42f98364. That call receives the field value, not merely the tested bit.

The field is not established to be snapshotted for the entire operation. Subsequent reads can observe changes made through aliases or by dependencies.

### Destination creation

It then returns null. No cleanup call is visible on this path.

If destination creation succeeds, the function proceeds directly to obtaining the primary region. It does not first initialize the complete destination record.

### Primary region

The function calls F-43da6b23bd44 with:

1. The input’s primary extent.
2. Zero.
3. Zero.

It writes the returned value to the destination’s primary-address field, including when the return is zero.

A zero return enters the common post-creation failure path. A nonzero return is passed as the first argument to the external transfer dependency. That dependency also receives the input’s primary address as its second argument and the input’s primary extent as its third argument.

The apparent interpretation is a transfer from the input region to the newly obtained region. The actual transfer direction, unit, overlap rules, failure behavior, and extent interpretation are not established by the dependency’s name-free call interface alone.

After that call returns, the function performs these destination stores in order:

1. Input primary extent into destination primary extent.
2. Input metadata into destination metadata.
3. Zero into destination auxiliary A.
4. Zero into destination auxiliary B.

The extent used in the first store is read after the external call. It need not equal the value previously passed to the storage request or transfer if intervening activity changes the input.

The function does not visibly check the transfer dependency’s return value.

### Auxiliary B

After the primary-region setup and the two auxiliary-field zero stores, the function reads the input’s auxiliary-B field.

If that value is zero, it skips this auxiliary allocation and transfer.

If it is nonzero:

1. F-1cb585febd84 is called with no explicit arguments shown.
2. One is added to its integer result.
3. F-43da6b23bd44 is called with that incremented value, zero, and zero.
4. The result is retained locally and written to destination auxiliary B.
5. A zero result enters the common failure path.
6. A nonzero result is passed to the external transfer dependency with the then-read input auxiliary-B value and the same incremented extent.

The input auxiliary-B value used in the transfer is read after both intervening dependency calls. The evidence does not establish that it is the same nonzero value that caused entry into this branch.

Although “length plus one” suggests a terminated-data copy, F-1cb585febd84 receives no explicit source argument in the supplied representation. Its association with auxiliary B, its units, and any terminator convention remain unknown.

### Auxiliary A

The function then reads the input’s auxiliary-A field.

If that value is zero, it skips this auxiliary allocation and transfer.

If it is nonzero:

1. F-1cb585febd84 is called again with no explicit arguments shown.
2. One is added to this invocation’s result.
3. F-43da6b23bd44 is called with that incremented value, zero, and zero.
4. The result is written to destination auxiliary A.
5. A zero result enters the common failure path.
6. A nonzero result is passed to the external transfer dependency with the then-read input auxiliary-A value and the incremented extent.

This branch occurs after auxiliary B, not before it. Each branch obtains its own result from F-1cb585febd84.

As with auxiliary B, the branch test does not snapshot the source value for the later transfer.

### Successful completion

After both optional branches complete or are skipped, the function reads the input control field, combines it with hexadecimal mask 0xD using bitwise OR, and writes the result into the destination control field.

The mask sets bits 0, 2, and 3 and preserves all other bits from that final input read. Under the 32-bit model, the mask is 0x0000000D.

The function then returns the destination pointer.

The final control value is not necessarily derived from the value used for the initial branch or destination-creation request. The intervening dependencies may have changed accessible state.

## Side effects

### Record writes

The function contains no explicit stores through the input pointer as such. This is not a guarantee that the input remains unchanged: the destination may alias it, and dependency behavior is unknown.

The identity-return path makes no record writes.

The construction path writes the destination progressively. It is not an atomic publication operation:

- The primary-address field is written before its allocation result is checked.
- Metadata and extent are written only after the primary transfer returns.
- Both auxiliary fields are cleared before either optional auxiliary branch.
- Each attempted auxiliary allocation result is stored before its zero check.
- The control field is written only on success.

On failure, a partially populated destination may exist until cleanup acts on it.

## Acceptance examples

These examples are conditional static expectations, not observed runtime results.

1. **Null input.**  
   Given a null input, the result is null and no dependency is called.

2. **Identity return.**  
   Given a readable input whose control field is 0x0000000C, the result is exactly the input pointer. No other field needs to be inspected by this function.

3. **Successful primary-only construction.**  
   Given stable input fields, control value 1, both auxiliary fields zero, nonnull destination creation, and a nonzero primary-storage result, the function performs one transfer call. It stores the input metadata and extent, leaves destination auxiliary A and B zero, stores control value 0x0000000D, and returns the destination.

4. **Destination-creation failure.**  
   If F-c42e42f98364 returns null, the error tuple is `(8, 101, 13, 0, 0)`. The function returns null without calling F-43da6b23bd44 or the cleanup dependency.

5. **Primary-storage failure.**  
   If destination creation succeeds but the first storage request returns zero, destination primary address is written as zero before error reporting. If error reporting leaves that field zero, the conditional no-explicit-argument cleanup call is skipped, and cleanup is called with the destination pointer.

6. **Auxiliary-A allocation failure after auxiliary-B success.**  
   If auxiliary B has obtained a nonzero storage result and auxiliary A’s request returns zero, the common error tuple is emitted. Cleanup first receives the retained auxiliary-B value. The primary-address-dependent cleanup call follows if its condition is true, then cleanup receives the destination pointer.

7. **Zero primary extent.**  
   A zero extent does not bypass the primary-storage request. Whether construction can succeed depends on that request’s result and the dependencies’ zero-extent behavior.

8. **Input mutation by a dependency.**  
   If an intervening dependency changes the input control field to 0x20 before the final read, successful completion stores 0x2D. This example assumes the mutation is otherwise valid and the record remains accessible.
