# F-81b2e9c93c15

## Purpose

F-81b2e9c93c15 performs an in-place structural transformation consistent with a **right rotation of a parent-linked binary tree**.

The operation promotes the target node’s left child, places the target beneath that promoted node as its right child, and transfers the promoted node’s former right subtree into the target’s left-child position. It also reconnects the promoted node to the target’s former parent or updates an indirectly stored root reference.

The rotation interpretation is inferred from the field relationships. The supplied static evidence establishes the memory accesses and assignments, but does not establish a tree type, balancing policy, key ordering, ownership policy, or valid-input checks.

## Interface

### Inputs

The function receives two address-bearing arguments:

- **Context address:** identifies an object containing, at byte offset 16, an address used to locate the root-reference holder.
- **Target address:** identifies the node around which the transformation occurs.

The source represents both arguments and the node-link values as integer-sized quantities. This contract describes the apparent **32-bit layout**: links and root references occupy four-byte fields, and all offsets below are byte offsets. The exact target ABI and pointer-conversion rules are not independently supplied.

## Behavior

### Ordered access behavior

The order below describes the observable memory-access sequence exposed by the supplied static representation. It is not a guarantee about processor-level ordering, atomicity, or concurrent visibility.

1. **Select the promoted node.**  
   The target’s left-child field is read. Its value becomes the promoted-node address used throughout the operation; the target’s left-child field is not reread to select a different promoted node.

2. **Transfer the middle-subtree reference.**  
   The promoted node’s right-child field is read, and that value is written into the target’s left-child field.

3. **Conditionally repair the middle subtree’s parent.**  
   The promoted node’s right-child field is read again and compared with zero. If nonzero, that field is read again to obtain the address whose parent field receives the target address.

   Thus the supplied representation contains repeated reads of this field. It does not capture one initial middle-subtree value and reuse it for all subsequent purposes. Under stable, non-overlapping storage, the reads agree. Under interference or overlapping fields, that agreement is not guaranteed.

4. **Give the promoted node the target’s parent.**  
   The target’s parent field is read and copied into the promoted node’s parent field.

5. **Locate and inspect the root slot.**  
   The holder reference is read from the context at offset 16. The root slot at holder offset 4 is then read and compared with the target address.

6. **Reconnect the upper edge.**
   - If the root slot equals the target address, the root slot is overwritten with the promoted-node address.
   - Otherwise, the target’s parent field is read again. That parent’s right-child field is read and compared with the target address.
     - If equal, the parent’s right-child field is overwritten with the promoted-node address.
     - Otherwise, the parent’s left-child field is overwritten with the promoted-node address.

   The non-root fallback does **not** check that the parent’s left-child field previously pointed to the target.

7. **Attach the target below the promoted node.**  
   The promoted node’s right-child field is overwritten with the target address.

8. **Complete the reciprocal parent link.**  
   The target’s parent field is overwritten with the promoted-node address.

The operation then returns normally.

### Intended final relationships

For a well-formed, non-overlapping tree whose relevant storage remains stable during the call:

- The target’s left child becomes the former middle subtree.
- A non-null middle subtree has the target as its parent.
- The promoted node inherits the target’s former parent reference.
- The target becomes the promoted node’s right child.
- The promoted node becomes the target’s parent.
- The old incoming reference to the target is redirected to the promoted node:
  - through the root slot when the target was the root; or
  - through a child field of the former parent otherwise.

The promoted node’s left-child field and the target’s right-child field are not directly accessed or modified.

### Root handling

Root replacement is selected solely by equality between the root-slot value and the target address.

The target’s parent field is copied into the promoted node’s parent field even on the root path. The function does not separately assign a null parent or a sentinel parent to the new root. Consequently, any root-parent convention is preserved only insofar as the target’s existing parent field already represents it.

### Arithmetic and comparisons

The visible address calculations add fixed byte offsets of 4, 8, 12, or 16. There is no index scaling, traversal, counter, size computation, or allocation-size arithmetic.

The visible decisions are equality comparisons:

- a child reference against zero;
- the root reference against the target address;
- a parent’s right-child reference against the target address.

There are no signed ordering comparisons. The source’s use of integer address expressions does not establish portable behavior for overflow, pointer conversion, or addresses near the address-space boundary.

## Side effects

Under the intended layout, the function performs these writes:

- Always: target left-child field.
- Conditionally: middle-subtree parent field.
- Always: promoted-node parent field.
- Exactly one upper-link field:
  - the root slot;
  - the former parent’s right-child field; or
  - the former parent’s left-child field.
- Always: promoted-node right-child field.
- Always: target parent field.

This yields five four-byte writes when the middle-subtree condition is false and six when it is true.

These are assignment counts, not necessarily counts of distinct addresses. Overlapping storage can make multiple roles refer to the same location and invalidate the ordinary rotation interpretation.

The mutation is incremental, not transactional. Earlier writes occur before the upper link and reciprocal parent relationship are fully repaired. No rollback or recovery path is visible. If execution is interrupted or an access fails, the evidence supplies no guarantee that the original structure remains intact.

No allocation, deallocation, external call, synchronization operation, logging, or explicit error reporting appears in the function. It rewires references without visibly creating or releasing objects. Ownership transfer, lifetime extension, and reclamation policy are not established.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, storage is valid, fields do not overlap, and no concurrent modification occurs.

### Root rotation with a non-null middle subtree

Initially:

- The root slot identifies the target.
- The target’s left child is the promoted node.
- The promoted node’s right child is a separate middle-subtree node.
- The target has an existing root-parent value.

After normal completion:

- The root slot identifies the promoted node.
- The promoted node’s parent equals the target’s previous root-parent value.
- The promoted node’s right child is the target.
- The target’s parent is the promoted node.
- The target’s left child is the middle subtree.
- The middle subtree’s parent is the target.

The root-parent value is copied, not normalized.

### Non-root target occupying a right-child position

Initially, the root slot does not identify the target, and the target’s parent has the target in its right-child field.

After completion, that right-child field identifies the promoted node. The root slot is unchanged. The internal rotation relationships are those described above.

### Non-root target occupying a left-child position

Initially, the root slot does not identify the target, the parent’s right-child field does not identify the target, and the parent’s left-child field does identify it.

After completion, the parent’s left-child field identifies the promoted node. The parent’s right-child field is unchanged.

### Empty middle subtree

If the promoted node’s right-child field is zero and remains stable during the relevant reads:

- The target’s left-child field becomes zero.
- No middle-subtree parent write occurs.
- The remaining reconnection and parent updates proceed normally.

A null middle subtree is handled; a null promoted node is not checked.

### Inconsistent parent membership

If the non-root target’s parent identifies the target in neither child field, the function nevertheless overwrites that parent’s left-child field with the promoted-node address.

This is the established fallback behavior, not a guarantee of structural validity. No rejection or error result is visible.
