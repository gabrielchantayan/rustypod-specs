## Behavior

The first operation passes the address at input offset `0x58` to F-e881608892f7.

### 2. Conditionally invoke the secondary callback

After the first dependency returns, the function examines the four-byte field at input offset `0xD8`.

If the field is zero, the secondary callback and its associated field-clearing write are skipped.

If the field is nonzero, the function:

- Uses the referenced address to obtain a table address from the beginning of that referenced object.
- Obtains a callable target from table offset `0x04`.
- Invokes that target.
- After the invocation returns normally, writes four zero bytes to input offset `0xD8`.

The visible callback invocation has no explicit arguments. In particular, the supplied representation does not explicitly pass the referenced object as a receiver. An implicit receiver, register-based context, or incomplete argument recovery remains an ABI uncertainty; none is promised by this contract.

The clearing write happens after the callback, not before it. Thus the callback can observe the field before this function clears it. If the callback changes the field to another nonzero value and returns, the visible subsequent write still clears that field in the original input object.

The callback’s effect on the referenced allocation is unknown. Its invocation must not be equated with destruction or deallocation.

### 3. Capture the shared value

After the conditional callback phase completes, the function reads the shared source and retains that four-byte value for the second primary-object invocation.

This capture occurs even when the nullable-field branch was skipped. When the branch was taken, it occurs after the callback returns and after the field is cleared.

The retained value is not a promise that the global itself remains unchanged. It separates the second invocation’s middle argument from later changes to the shared source.

### 4. Perform the first primary-object invocation

The function resolves an operation through the primary object’s table, at table offset `0x58`.

The visible argument list contains, in order:

1. The original input address.
2. A value read from the shared source for this invocation.
3. A value read from the first-only source.

The shared-source argument for this invocation is not visibly supplied from the retained value described above. The representation shows a separate use of the global source.

Absent an intervening change, the two shared-source reads yield the same value. Their equivalence is not unconditional: concurrency, volatile access rules, or other mechanisms affecting global observation are not specified.

The evidence does not establish a total evaluation order among this invocation’s table lookup and its global argument reads. The contract therefore specifies their roles without inventing a left-to-right memory-access order.

No result from this invocation is visibly tested or used to select whether the second invocation occurs.

### 5. Perform the second primary-object invocation

After the first primary-object invocation returns, the function again resolves the operation through the primary object’s table at offset `0x58`.

Its visible arguments are:

1. The original input address.
2. The retained shared-source value captured before the first invocation.
3. A value read from the second-only source for this invocation.

The table lookup is expressed again rather than as reuse of a previously captured target. Therefore, a table change made by the first invocation can affect the second target.

Likewise, a change to the second-only source made by the first invocation can affect the second invocation’s final argument. A change to the shared source during the first invocation does not replace the already captured middle argument.
