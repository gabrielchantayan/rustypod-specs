# F-8d3b1594bc36

## Purpose

F-8d3b1594bc36 performs mode-dependent conditional dependency calls and, for modes 0 and 1, optionally processes a nonzero address through metadata validation, accounting updates, and two final dependency calls.

The established behavior is a sequence of calls and memory accesses. The metadata layout and accounting reductions are consistent with releasing an allocated object, but allocation ownership, synchronization semantics, and actual reclamation are not established by this function alone.

The function returns no value. Invalid metadata reaches a dependency identified as nonreturning; no recoverable error result is visible.

For the five conditional inputs, this body establishes only zero-versus-nonzero tests. It does not establish that they are pointers, handles, sizes, or values passed to F-5e3309c9d083. The displayed calls to that dependency have no explicit arguments.

## Behavior

### 1. Mode-dependent preliminary calls

If mode is below 6:

1. A nonzero conditional input 1 causes one call to F-5e3309c9d083.
2. After that call returns, a nonzero conditional input 2 causes another call to F-5e3309c9d083.

These are independent conditions. Two nonzero inputs cause two calls, even if their values are equal.

After these checks, mode greater than 1 causes an immediate return. Consequently:

- Modes 2 through 5 permit only the first two conditional calls.
- Modes 6 through the maximum unsigned 32-bit value return without any dependency calls or memory accesses shown in the body.
- Only modes 0 and 1 continue.

For modes 0 and 1, conditional inputs 3, 4, and 5 are examined in that order. Each nonzero input causes a separate call to F-5e3309c9d083.

No assumption may be made that these dependency calls preserve global state. Any changes they make occur before later address processing.

### 2. Zero-address handling and setup

For modes 0 and 1, a zero subject address returns after the applicable conditional calls. It does not invoke the address-processing dependencies or access the metadata.

For a nonzero subject address, the function performs this sequence:

1. Calls F-187ab9ba4eb6.
2. Calls F-2fd8826557a4.
3. Reads the shared global location to capture the accounting-context address.

The supplied representation contains repeated zero-address guards around this setup. They test the same incoming scalar; they are not repeated reads of an external pointer slot. They do not establish additional cleanup or error behavior.

The captured context address is used for the remaining accounting operations and context-taking calls. A later change to the global context location does not, by itself, retarget those operations.

### 3. Header validation

The function examines the 32-bit header at subject offset −8.

Validation fails if either:

- The header is zero; or
- Bit 0 of the header is set.

The zero test precedes the bit-0 test. If the zero test succeeds, the second header read is skipped. Otherwise, the bit-0 condition is evaluated from another header read.

Failure invokes F-a817d8d58c10, identified by the supplied static representation as nonreturning. No accounting updates, F-cc6c9b4a0f68 call, or final F-e586bff64fb7 call occur afterward in the shown flow.

A successful check establishes only that the tested header was nonzero and had bit 0 clear. It does not establish that its masked accounting amount is positive, that its indices are valid, or that its later contents remain unchanged.

### 4. Accounting updates

After successful validation, the function calls F-c0fc6d033caa with the captured accounting-context address.

Only after that call returns does the function read the first 16-bit metadata index and read the header for the accounting amount. Thus, validation does not protect a frozen copy of the metadata against changes made by this dependency.

The first accounting amount is the then-read header masked by `0x3ffffffc`. This mask clears bits 31, 30, 1, and 0. Its possible result is a multiple of four from zero through `0x3ffffffc`, inclusive.

The following updates occur in order:

1. Read the unsigned 16-bit index at subject offset −4. Subtract the first accounting amount from the 32-bit cell at context offset `0x224 + 4 × index`, and store the result.
2. Subtract the same captured amount from the 32-bit cell at context offset `0x30c`, and store the result.
3. Read the unsigned 16-bit index at subject offset −2. Subtract that same amount from the 32-bit cell at context offset `0xe0 + 4 × index`, and store the result.
4. Subtract that same amount from the 32-bit cell at context offset `0x220`, and store the result.
5. Call F-09dcb55e8e0a.
6. Use its represented 32-bit signed return value as a four-byte-scaled index. Decrement the 32-bit cell at context offset `0x310 + 4 × returned index` by one.
7. Decrement the 32-bit cell at context offset `0x390` by one.
8. Read the header at subject offset −8 again, mask it by `0x3ffffffc`, and subtract this newly obtained amount from the 32-bit cell at context offset `0x08`.

The amount used in step 8 is not necessarily the amount used in steps 1 through 4. F-09dcb55e8e0a executes between those reads and cannot be assumed to preserve the header or accounting memory. Earlier stores could also affect subsequent reads if the supplied addresses alias.

Each accounting operation is a read-modify-write of its target word. The order matters when derived addresses coincide. For example, two operations targeting the same cell apply sequentially to that cell; they are not independent updates to a snapshot.

No saturation, zero floor, or failure branch is visible for subtraction or decrement. The represented 32-bit word operations can wrap when a mathematical result lies outside the representable word range. Exact signed-overflow semantics of the original implementation language are not established by this representation.

The unsigned 16-bit metadata indices range from 0 through 65,535. Their scaled offsets therefore range from 0 through 262,140 bytes before adding the table’s base offset. No tighter bound is enforced here. The index supplied by F-09dcb55e8e0a has no visible range or nonnegativity check.

### 5. Final dependency calls

After all accounting writes:

1. F-cc6c9b4a0f68 receives the captured accounting-context address and the address of the header at subject offset −8.
2. If that call returns, F-e586bff64fb7 receives the same captured context address.
3. If that call returns, F-8d3b1594bc36 returns without a value.

There is no explicit metadata access after F-cc6c9b4a0f68. Whether that dependency releases, retains, modifies, or transfers the referenced storage is not established here.

## Side effects

The visible direct side effects are the ordered accounting writes described above. Other effects may occur through dependencies.

Important boundaries:

- Conditional calls happen before subject-address validation.
- Both setup calls and the global context read happen before header validation.
- The nonreturning invalid-header path has no visible balancing final call.
- Accounting changes occur before F-cc6c9b4a0f68.
- The function does not roll back earlier writes if a later dependency fails to return normally.
- No explicit write to the payload, metadata header, or shared global context location appears in this body.
- No explicit return-status channel, output parameter, diagnostic text, or exception handler appears.

Synchronization is not established. The setup and context-taking dependencies may participate in synchronization, but their identities and ordering alone do not prove locking, atomicity, or exclusion from concurrent mutation.

Ownership is likewise undocumented. This function’s use of a preceding header and accounting reductions does not by itself prove that the caller owns the subject, that the subject becomes unusable, or that any particular dependency frees it.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests.

### Mode excludes all work

Given mode 6, the function returns without any shown dependency call or metadata access, regardless of the other input values. A numerically negative value interpreted as the unsigned mode likewise exceeds the eligible range.

### Intermediate mode permits only two checks

Given mode 3 and nonzero conditional inputs 1 and 2, the function calls F-5e3309c9d083 twice, in order, then returns. Conditional inputs 3 through 5 and the subject address do not enable further work.

### Zero subject does not suppress earlier calls

Given mode 0, all five conditional inputs nonzero, and a zero subject address, the function makes five calls to F-5e3309c9d083 and then returns. It does not call either setup dependency.

### Invalid header after setup

Given mode 1, a nonzero subject address, normally returning setup dependencies, and a zero header at validation time, the function captures the context and then invokes F-a817d8d58c10. No accounting write precedes that invocation.

A nonzero header with bit 0 set follows the same terminal branch.

### Ordinary accounting with stable, distinct storage

Assume all dependencies return normally, metadata and relevant accounting cells remain stable except for the specified writes, and all accounting targets are distinct.

For a header of `0x00000102`, the accounting amount is `0x100`, or 256 bytes. The first four accounting targets and context offset `0x08` each decrease by 256. The cell selected by F-09dcb55e8e0a and the cell at context offset `0x390` each decrease by one. The two final dependencies then run in order.

### Accepted header with zero masked amount

A stable header of `0x00000002` passes validation but produces a zero masked amount. The amount-based updates still perform their read-modify-write operations, while the two count cells are decremented. Header validity therefore does not imply a positive accounting amount.

### Header changes across the index dependency

Assume the first accounting amount is 256. If F-09dcb55e8e0a changes the header to a valid word whose masked amount is 512, and no other relevant aliasing intervenes, the first four amount-based updates subtract 256 while the update at context offset `0x08` subtracts 512. There is no consistency recheck.
