# F-ed2ac8d21267

## Purpose

F-ed2ac8d21267 coordinates scratch-state preparation, a status-producing operation, a flag check, and an optional four-byte output write.

Its established behavior is:

- Invoke a preparation dependency with a literal zero and a scratch-area address.
- Invoke a second dependency with the two supplied input values and another scratch-area address.
- Return that second dependency’s status unchanged if it is nonzero.
- If that status is zero, inspect bit `0x10` of a one-byte scratch value.
- If the bit is set, return `7` without performing the function’s direct output write.
- Otherwise, obtain a four-byte value from a third dependency, store it through the caller’s output pointer, and return zero.

The semantic meaning of the two inputs, the scratch contents, the flag, and the resulting four-byte value is not established. In particular, there is no basis for naming the output as a handle, pointer, identifier, timestamp, or allocated object.

This contract describes normal control flow visible in the supplied static representation. It does not assign undocumented behavior to dependencies.

**3. Handle a nonzero status.**

- Read the flag byte.
- Invoke F-4055be9c3f18.
- Store through the output address.

**4. Inspect the flag after a zero status.**

If F-89d1e7e68fff returns zero, the function reads the one-byte flag and tests its bit selected by mask `0x10`.

Only that bit affects this decision. Other bits do not independently cause rejection.

The flag decision precedes this dependency call. There is no visible flag recheck afterward. Consequently, any flag-related state change during that call does not create another rejection branch in this function.

- At most one four-byte store through the caller’s output address.

The direct output store occurs only after F-89d1e7e68fff returns zero, the tested flag bit is found clear, and F-4055be9c3f18 returns normally.

The output address remains caller-supplied storage. No transfer of ownership of that storage is visible.

### Failure and partial effects

## Acceptance examples

These are conditional contract examples, not results of executed tests. Each assumes dependencies return normally and all accesses needed by the example are valid.

### Nonzero status takes precedence over the flag

If F-89d1e7e68fff returns `5`, the function returns `5`.

F-4055be9c3f18 is not called. The function does not read the flag, even if the flag would otherwise contain `0x10`. It does not directly write the output location.

### A dependency status of `7` is not distinguished from local rejection

If F-89d1e7e68fff returns `7`, the function returns `7` without inspecting the flag.

If that dependency instead returns zero and the flag contains `0x10`, the function also returns `7`, but through the flag-rejection path.

The return value alone does not distinguish these causes.

### A set rejection bit blocks output production

If F-89d1e7e68fff returns zero and the flag contains `0x90`, the function returns `7`, because `0x90` includes bit `0x10`.

The final dependency is not called, and there is no direct output write.

### Unrelated flag bits do not reject

If F-89d1e7e68fff returns zero and the flag contains `0xEF`, the tested bit is clear.

F-4055be9c3f18 is called. If it returns the four-byte value `0x12345678`, that value is stored through the output address, and the function returns zero.

No external byte ordering for that store is implied.

### A zero produced value is still accepted

If the status is zero, the rejection bit is clear, and F-4055be9c3f18 returns a four-byte zero, the function stores zero and returns zero.

There is no visible produced-value failure check.

### Invalid output storage is not validated

If execution takes the accepted path with an invalid output address, the function still reaches the attempted four-byte store. The supplied source establishes no recoverable status for that condition.

On a path that returns before the store, the function itself does not dereference the output address. This does not establish universal safety for invalid addresses, because dependency behavior and aliasing remain unknown.
