# F-04e09896b2b6

## Purpose

F-04e09896b2b6 selects one 28-byte record from caller-supplied state and partially initializes that record. It prefers a record available through a linked list. Otherwise, it consumes a record from a sequential storage region, allocating a new region when the current cursor equals its limit.

The function has no explicit return value and does not directly return the selected record’s address. Its observable results are state updates, writes to the selected record, and, when needed, calls to F-871e64ddc6de.

The organization suggests a reusable-record pool with linked backing blocks. That interpretation is inferred intent. The established behavior is the address selection, arithmetic, dependency calls, and memory operations described below.

## Interface

### Input and return

The sole argument is an address of mutable state containing at least four consecutive 32-bit fields. The supplied representation uses 32-bit address values.

| State offset | Width | Operational role |
|---|---:|---|
| +0 | 32 bits | Address of the current backing-block descriptor, or zero |
| +4 | 32 bits | Address of the first reusable record, or zero |
| +8 | 32 bits | Sequential allocation cursor |
| +12 | 32 bits | Sequential allocation limit |

These names describe how the function uses the fields; they do not establish an external type definition.

There is no explicit return value, success flag, error code, or output parameter containing the selected address.

### Backing-block descriptor

A descriptor is accessed as three consecutive 32-bit fields:

| Descriptor offset | Width | Operational role |
|---|---:|---|
| +0 | 32 bits | Previous backing-block descriptor address |
| +4 | 32 bits | Record capacity |
| +8 | 32 bits | Backing-storage address |

An existing descriptor’s capacity influences the size of a newly allocated block. Its storage address and predecessor are not traversed when choosing an existing sequential slot.

### Selected record

Each record occupies 28 bytes. The function accesses these portions:

| Record offset | Width | Use |
|---|---:|---|
| +0 | 8 bits | Cleared during initialization |
| +4 | 32 bits | Cleared during initialization |
| +8 | 32 bits | Cleared during initialization |
| +12 | 32 bits | Read as a successor address when reusing a record; subsequently cleared |

Bytes +1 through +3 and +16 through +27 are not explicitly initialized.

### Preconditions

For ordinary successful execution:

- The state address must support the reads and writes described here.
- A nonzero reusable-record address must permit a 32-bit read at offset +12 and the subsequent initialization writes.
- A selected sequential address must permit those initialization writes.
- If a new block is required and the descriptor head is nonzero, that descriptor must permit a 32-bit capacity read at offset +4.
- Dependency results must identify storage suitable for the subsequent descriptor and record accesses.
- The memory model must permit the shown 32-bit accesses, including any required alignment.

The function does not validate these conditions. It also does not check that the cursor is below the limit, that the remaining storage contains a complete record, or that capacity calculations fit without wrapping.

## Behavior

### Selection precedence

The reusable-record list takes priority over sequential storage. A nonzero field at state offset +4 selects that path regardless of the cursor, limit, or backing-block descriptor.

Only when the reusable-record field is zero does the function consider sequential storage. It requests new storage only when the cursor and limit are exactly equal.

### Reusing a record

When state offset +4 contains a nonzero address:

1. That address becomes the selected record.
2. The function reads the 32-bit successor address at selected-record offset +12.
3. It writes that successor into state offset +4.
4. It initializes the selected record as specified below.

The successor is consumed before its field in the selected record is cleared. A zero successor empties the reusable-record list. A nonzero successor becomes the next list head without validation.

This path makes no direct dependency calls and does not explicitly write state offsets +0, +8, or +12.

### Consuming an existing sequential slot

When the reusable-record field is zero, the function reads the cursor and compares it with the limit.

If they differ:

1. The cursor address becomes the selected record.
2. State offset +8 is advanced by 28 bytes.
3. The selected record is initialized.

The comparison is equality, not an ordering or bounds check. A cursor numerically greater than the limit still follows this path. So does a cursor that differs from the limit by fewer than 28 bytes.

No backing-block descriptor is needed on this path, and no dependency call occurs.

### Choosing a new block’s capacity

If the cursor equals the limit, a new block is requested.

If state offset +0 is zero, the chosen capacity is 32 records.

Otherwise, the function reads the existing descriptor’s 32-bit capacity and computes two unsigned 32-bit candidates:

- The old capacity plus 32.
- The old capacity plus its logical right shift by one bit plus its logical right shift by three bits.

The second expression approximates growth by a factor of 1.625 before considering integer truncation and overflow. That factor is inferred intent, not a separate arithmetic guarantee.

Each addition uses 32-bit unsigned arithmetic. The chosen capacity is the larger candidate under unsigned comparison. Equality selects the same numeric capacity either way.

There is no minimum-capacity correction after arithmetic wrapping and no overflow rejection.

### Allocating and publishing a new block

After choosing the capacity, the function makes two calls to F-871e64ddc6de, in this order:

1. A request with first argument 12 and second argument zero.
2. A request with first argument equal to the chosen capacity multiplied by 28, and second argument zero.

The multiplication produces a 32-bit request size; overflow is not checked.

The first result is used as a descriptor address. The second result is used as its backing-storage address. No descriptor fields are explicitly initialized between these two calls.

After both calls return, the function performs these operations in order:

1. Writes the backing-storage address to descriptor offset +8.
2. Reads the current descriptor head from state offset +0 and writes it to descriptor offset +0.
3. Writes the chosen capacity to descriptor offset +4.
4. Writes the new descriptor address to state offset +0.
5. Reads the backing-storage address from descriptor offset +8.
6. Makes that address the selected record.
7. Writes the selected address plus the capacity-times-28 extent to state offset +12.
8. Writes the selected address plus 28 to state offset +8.
9. Initializes the selected record.

The predecessor stored in the new descriptor is the state head read after both dependency calls. It must not be assumed to equal the head used earlier for capacity selection: the dependency’s effects on shared memory are undocumented.

Likewise, the selected storage address is read back from the descriptor after the new head is published. Under ordinary non-overlapping storage this is the address just stored there. Aliasing or external mutation can affect that read; the function contains no protection against either.

The first record of the new block is consumed immediately. The cursor therefore advances one record beyond the block’s starting address.

### Record initialization

All selection paths converge on the following ordered writes to the selected record:

1. A 32-bit zero at offset +4.
2. A 32-bit zero at offset +8.
3. A 32-bit zero at offset +12.
4. An 8-bit zero at offset +0.

This is partial initialization, not clearing all 28 bytes. There is no explicit write to the remaining bytes.

State updates occur before these initialization writes. Consequently, if an access fails during initialization, the supplied behavior provides no rollback of an already advanced list head, advanced cursor, or published descriptor.

## Side effects

### State and memory changes

Under valid, non-overlapping memory with no external mutation:

| Path | Explicit state changes |
|---|---|
| Reusable record | Replaces the reusable-record head with the selected record’s successor |
| Existing sequential slot | Advances the cursor by 28 |
| New block | Publishes a new descriptor head, replaces the limit, and advances the cursor past the first record |

Every path performs the four record-initialization writes.

The new-block path also initializes all three descriptor fields. It retains the prior descriptor address as a predecessor link rather than replacing it without a link.

These descriptions identify explicit accesses. They do not promise that other memory remains unchanged when addresses overlap, or that dependency calls preserve caller-visible memory.

### Ownership and lifetime

The function contains no explicit deallocation, destructor invocation, or release operation. It does not release the previous block.

The new descriptor and backing-storage addresses are retained through caller state and the descriptor chain. This supports an inference that another operation manages their eventual lifetime. The supplied material does not establish that operation, the ownership rules, or the correct release dependency.

Removing a record from the reusable list is an observable state transition. It does not, by itself, establish language-level ownership transfer.

### Errors and synchronization

There is no explicit error return, allocation-failure branch, rollback, or diagnostic operation.

A zero result from either dependency call is not checked before later memory access. The resulting platform behavior is unspecified here; a particular exception or fault must not be promised.

No synchronization operation appears. Concurrent access to the same state, descriptors, or records requires an external contract that is not supplied.

## Acceptance examples

These are conditional acceptance examples derived from static evidence. No runtime tests have been performed.

### Reusable record takes precedence

Given valid, disjoint memory:

- The reusable-record head identifies record A.
- Record A’s successor field identifies record B.
- The cursor equals the limit.

Expected behavior:

- A is selected.
- The reusable-record head becomes B.
- No dependency call occurs despite sequential exhaustion.
- The descriptor head, cursor, and limit receive no explicit writes.
- A’s fields at offsets +4, +8, and +12 become 32-bit zero, then its byte at +0 becomes zero.

### Last reusable record

Given a nonzero reusable-record head whose successor field is zero:

- The selected record is removed.
- The reusable-record head becomes zero.
- Its successor field is then cleared as part of initialization.
- No sequential slot is consumed.

### Existing sequential capacity

Given a zero reusable-record head, a cursor at address X, and a different limit:

- X is selected.
- The cursor becomes X plus 28, subject to the represented address arithmetic.
- The limit and descriptor head receive no explicit writes.
- No dependency call occurs.

This branch selection still applies when X is numerically above the limit. Memory safety then depends on external validity, not on a check performed here.

### First backing block

Given an empty reusable list, equal cursor and limit, and a zero descriptor head, with suitable non-interfering dependency results:

- Capacity is 32 records.
- Dependency request sizes are 12 and 896, in that order.
- The new descriptor records a zero predecessor, capacity 32, and the returned storage address.
- The limit becomes storage address plus 896.
- The cursor becomes storage address plus 28.
- The first record is partially initialized.
