# F-510f6a9797d0

## Purpose

F-510f6a9797d0 traverses a fixed-stride record sequence, conditionally calls a dependency for selected records, and then conditionally performs accounting and further dependency calls associated with a newly selected storage address.

Two stages are established:

1. Traverse using the descriptor’s initially read count and storage address.
2. Re-read the descriptor’s storage address; unless it is null or equal to an address within the descriptor, process preceding metadata, update accounting, and possibly process a block header.

“Descriptor,” “record,” “inline storage,” “accounting state,” and “allocator state” are descriptive roles. Cleanup and storage release are inferred intent, not established dependency behavior.

The body contains no descriptor-directed or record-directed stores and no explicit descriptor-reset operation. This does **not** establish that descriptor or record memory remains unchanged: accounting destinations may overlap that memory, and dependencies have unknown effects. Successful return does not establish that any memory was released.

## Interface

### Input and result

The function accepts one 32-bit descriptor address and has no explicit return value.

The descriptor accesses are:

| Byte offset | Width | Use |
|---|---:|---|
| +8 | 32 bits, interpreted as signed | Initial record count |
| +16 | 32-bit address | Initial storage address; read again after traversal |
| +24 | Address within descriptor | Equality-comparison target for the second storage selection |

Offset +24 is used to form an address. The function does not read a pointer field at that offset for this comparison.

The record accesses are:

| Record-relative offset | Width | Use |
|---|---:|---|
| +0 | 32 bits | Argument to F-841dc33ee157 when selected |
| +12 | 8 bits | Bit 0 determines selection |
| Stride | 40 bytes | Distance between successive records |

For an unselected record, the function does not directly read the field at offset +0. Other record bytes are not inspected by the traversal itself.

### Preconditions for normal continuation

Accessible memory is required for every access actually reached:

- Both descriptor fields initially read.
- Each visited record’s flag byte and each selected record’s first field.
- The descriptor’s storage field when re-read.
- Metadata preceding the post-traversal storage and adjusted storage addresses.
- Accounting fields selected by separate global-pointer observations.
- Allocator fields selected by the retained state address and computed indices.

No visible bounds checks protect either metadata-derived index or the index returned by F-09dcb55e8e0a. The later null-storage check does not protect the initial traversal: positive count with initially null storage can cause record accesses before that check.

Normal continuation also requires dependencies to return at the relevant call sites. F-a817d8d58c10 is separately marked non-returning.

### Widths and arithmetic

Addresses, ordinary metadata fields, and counters are 32-bit quantities. The two metadata indices are unsigned 16-bit quantities, zero-extended before address calculation. Selection flags are 8 bits.

Unsigned accounting operations retain their low 32 bits. No overflow or underflow checks are visible. Signed decrements and signed address expressions require the boundary qualifications in **Uncertainties**. A computed 32-bit address, including one obtained by wraparound under a target interpretation, is not thereby valid memory.

## Behavior

### Initial traversal

The function reads the signed count first and the initial storage address second. Those values determine the traversal; changes to the descriptor fields do not reload either selection.

Each loop-condition evaluation performs these operations in order:

1. Read and retain the current global accounting-state pointer.
2. Decrement the retained signed count.
3. Enter the body only if the decremented count is nonnegative.

The accounting-state pointer is captured even on the final condition evaluation that exits the loop. That final capture later selects the high-word accounting destination.

For an initial count from zero through 2,147,483,647, the traversal performs exactly that many iterations, assuming normal continuation and accessible addresses. Counts from −2,147,483,647 through −1 produce no iterations. The minimum signed value is unresolved at the signed-decrement boundary.

Each iteration:

- Reads the current record’s flag byte at offset +12.
- If bit 0 is set, reads the 32-bit field at offset +0 and passes it to F-841dc33ee157.
- Advances the retained record address by 40 bytes.

Selection uses the flag value observed when the record is reached, not a snapshot of all initial flags. A callback can therefore change whether a later record is selected or change the argument read from that record.

A callback can also change a global-pointer value observed by a later loop condition. Changes to the descriptor’s count or storage field do not redirect the retained traversal, although changes to the underlying record memory can affect it. No preservation guarantee is established for any callback.

### Post-traversal storage selection

After traversal, the function re-reads the descriptor’s storage field.

It first compares the result with the descriptor address plus 24. Equality causes immediate return. Otherwise, it tests for zero and returns if zero.

These returns occur after any record callbacks but before subsequent metadata accesses, accounting writes, or allocator-related calls.

The newly selected storage address need not equal the traversed address. A callback can change or suppress the second stage by changing the descriptor’s storage field without redirecting traversal.

### Metadata selection

For a non-null, non-inline post-traversal storage address:

1. Read a 32-bit displacement four bytes before that address.
2. Subtract the displacement from the storage address to obtain the **adjusted storage address**.
3. Read a 32-bit accounting amount eight bytes before the adjusted address.

No displacement, address, or amount validation precedes these accesses. The displacement is not established to be positive or restricted to a particular allocation layout. The address calculation is 32-bit; signed-expression boundary behavior remains qualified below.

### Global accounting

Accounting fields are located at offsets +56 and +60 from selected accounting-state addresses. Their source and destination selections are independent.

After reading the accounting amount, the function:

1. Reads the global accounting-state pointer and obtains the old low word at offset +56 through that selection.
2. Reads the global accounting-state pointer again and retains the address of its field at offset +60 as the high-word source.
3. Reads the global accounting-state pointer again and writes the low-word result at offset +56 through this third selection.
4. Reads the old high word through the retained high-source address.
5. Writes the high-word result at offset +60 through the pointer captured by the final loop-condition evaluation.

The four roles are therefore:

| Role | Selection time |
|---|---|
| Low-word source | First pointer read after the amount |
| High-word source | Second pointer read after the amount |
| Low-word destination | Third pointer read after the amount |
| High-word destination | Final traversal-condition evaluation |

Equality or stability of these selections is not established. They must not be unconditionally described as one accounting object.

Let \(L\) be the retained unsigned low-source word and \(A\) the accounting amount. The low result is:

\[
(L-A)\bmod 2^{32}.
\]

Let \(H\) be the subsequently read high-source word. Define a sign-extension term \(S\) as zero when bit 31 of \(A\) is clear and −1 when it is set. Define borrow \(B\) as one when \(L<A\) under unsigned comparison and zero otherwise. The high result is:

\[
(H-S-B)\bmod 2^{32}.
\]

The borrow depends on the retained low-source value, not the previous contents of the low destination.

The low write occurs before the high-source read. If those addresses overlap, the write can affect the high-source value used in the calculation.

Under stable selections and noninterfering memory, these operations subtract a sign-extended 32-bit amount from a two-word total. They are not unconditionally subtraction of a zero-extended unsigned amount.

### Intermediate dependency and allocator-state selection

After both accounting writes, the function calls F-2fd8826557a4 without explicit arguments.

After that call returns, it reads through a separate global pointer location to obtain an allocator-state address. That address is retained for subsequent allocator operations. Neither global preservation nor memory preservation by F-2fd8826557a4 is established.

The function then compares the adjusted storage address with the numeric address 8. Equality causes return.

Thus, the adjusted-address-equals-8 path still performs:

- The accounting-amount access.
- Both accounting writes.
- F-2fd8826557a4.
- Allocator-state selection.

It does not access the block header or perform the remaining calls.

### Header validation

For an adjusted storage address other than 8, the header address is 16 bytes before the adjusted address.

Validation uses separate observations:

1. Read the 32-bit header and reject if it is zero.
2. If the first read was nonzero, read the header again and reject if bit 0 is set.

Rejection calls F-a817d8d58c10 without explicit arguments. The call site is marked non-returning; no normal recovery path is shown.

A changing header need not have the same value in both reads. In particular, a nonzero first observation followed by a zero second observation passes these two tests. Passing validation establishes only the tested observations, not continued header validity.

The accounting writes occur before rejection. No explicit rollback operation appears in this body, but persistence of those values after any dependency is not guaranteed.

### Allocator-state updates and final calls

After validation, the function calls F-c0fc6d033caa with the retained allocator-state address. It then performs these operations in order:

| Order | Operation |
|---:|---|
| 1 | Read an unsigned 16-bit index 12 bytes before the adjusted address |
| 2 | Read the header and retain its value masked with `0x3ffffffc` |
| 3 | Subtract that amount from the field at allocator state +548 + four times the first index |
| 4 | Subtract the same amount from the field at allocator state +780 |
| 5 | Read an unsigned 16-bit index 10 bytes before the adjusted address |
| 6 | Subtract the retained amount from the field at allocator state +224 + four times the second index |
| 7 | Subtract the retained amount from the field at allocator state +544 |
| 8 | Call F-09dcb55e8e0a without explicit arguments |
| 9 | Decrement the 32-bit field at allocator state +784 + four times the returned index |
| 10 | Decrement the 32-bit field at allocator state +912 |
| 11 | Read the header again, mask with `0x3ffffffc`, and subtract that newly obtained amount from the field at allocator state +8 |

Each counter update reads the selected counter and writes its result. The five amount-based subtractions retain 32-bit results. The two unit decrements have signed-boundary qualifications and no visible checks.

The mask clears bits 31, 30, 1, and 0. Its result is a multiple of four from zero through `0x3ffffffc`. A header that passes validation can produce a zero amount.

The first four amount-based updates share one retained amount. The final subtraction uses a fresh header observation after F-09dcb55e8e0a. Dependencies or overlapping stores can make these amounts differ. Likewise, earlier writes can affect the second metadata index before it is read.

The function finally calls:

1. F-cc6c9b4a0f68 with the retained allocator-state address and header address.
2. F-e586bff64fb7 with the retained allocator-state address.

It then returns. Neither call’s ownership or release behavior is established.

## Side effects

The normally completed validated-block path includes:

- Ordered callbacks for selected records.
- Two global-accounting store operations.
- Seven allocator-counter store operations.
- The additional dependency calls described above.

These are operations, not necessarily distinct memory locations. Selected destinations can overlap one another, metadata, the descriptor, or records unless a separate contract excludes that aliasing.

There are no stores explicitly directed through descriptor fields or record fields. Nevertheless, indirect accounting stores and dependency effects can mutate those regions. Descriptor preservation, record preservation, and unchanged selection bits cannot be assumed.

The body provides no transactional guarantee. Accounting writes precede validation; allocator-counter writes precede the final two calls. Subsequent dependencies can overwrite earlier results, and abnormal termination can interrupt the sequence.

No allocation, ownership transfer, successful release, locking discipline, thread safety, or reentrancy guarantee follows from this body. Repeated invocation is not established as safe.

## Acceptance examples

These are conditional static examples, not executed tests. Each assumes the necessary accesses are valid and dependencies return wherever continuation is described.

### Record selection and inline return

Suppose three initially readable records have flags 1, 2, and 3. Assume callbacks and all other intervening effects preserve each later record’s selection bit until its flag is read, preserve traversal accessibility, and leave post-traversal storage equal to the descriptor address plus 24.

F-841dc33ee157 receives the first fields of records one and three, in order. Record two produces no callback. The function then returns without second-stage metadata accesses or accounting writes.

Initial flags alone are insufficient: the first callback could set record two’s bit 0 or clear record three’s bit 0, changing the callback sequence even if post-traversal storage remains inline.

### Callback changes storage to null

Suppose a callback changes the descriptor’s storage field to zero without invalidating retained traversal memory or causing later effects to restore another value before the post-traversal read.

Traversal continues using its retained address sequence and count. The final storage re-read causes return. This does not make initially null storage safe for positive-count traversal.

### Stable accounting with borrow

With stable accounting selections, no interfering aliasing, low word 3, high word 10, and amount 5:

- The low write stores `0xfffffffe`.
- The high write stores 9.

These are values written at those steps, not guaranteed final values after subsequent dependencies.

### Independent accounting selections

Suppose all four accounting roles select distinct, nonoverlapping objects. The low source contains 3, the high source contains 10, and the amount is 5.

The third post-amount selection receives `0xfffffffe` at offset +56. The final-loop selection receives 9 at offset +60. The previous values at these destinations do not determine either result.

### Low write overlaps high source

Suppose the low destination equals the retained high-source address. With low-source value 3 and amount 5, the low write stores `0xfffffffe` there.

With no intervening modification, the subsequent high-source read obtains that value. The high write therefore stores `0xfffffffd`.

### Accounting amount with bit 31 set

With stable, noninterfering accounting state, low word 0, high word 10, and amount `0x80000000`:

- The low write stores `0x80000000`.
- The sign-extension term is −1.
- The borrow is 1.
- The high write stores 10.

### Adjusted address equals 8

If valid preceding accesses produce adjusted address 8, the accounting-amount read and both accounting writes occur, followed by F-2fd8826557a4 and allocator-state selection. No header access or later call occurs.

### Header rejection

A first header observation of zero calls F-a817d8d58c10 without the second validation read. A nonzero first observation followed by a second observation with bit 0 set also calls it.

Both accounting writes occur before this non-returning call. Their persistence afterward is not established: the dependency has unknown memory effects and may overwrite or reverse those values before terminating.

### Stable validated header

With header `0x104` at every relevant read, valid indices, accessible counters, and no interfering metadata or counter changes, all five amount-based subtractions use 260. The two unit decrements subtract one within their ordinary signed range. The final calls receive the retained allocator-state and header addresses in the stated order.

## Uncertainties

The following remain **documented_only**:

- Semantic identities, lifetimes, and ownership of the descriptor, records, and payloads.
- Allocation layout beyond the accessed fields.
- Meaning of the adjusted-address-equals-8 exception.
- Valid ranges for metadata values and dependency-selected indices.
- Equality or stability of separately observed accounting pointers.
- Permitted aliasing among globals, descriptor memory, records, metadata, and counters.
- Dependency preservation, synchronization, ownership, release, and termination guarantees.
- Behavior on inaccessible memory or malformed metadata.
- Source-level versus target-level behavior at signed-overflow boundaries, including minimum initial count, unit decrements, and signed address calculations.
- Operand-evaluation ordering not explicitly sequenced within individual expressions.
- Lifecycle rules governing repeated calls.

The apparent intent is record teardown followed by backing-storage accounting and disposal. That inference establishes neither release success nor preservation of earlier writes.
