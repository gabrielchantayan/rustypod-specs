# F-8e61a306c2e4

## Purpose

F-8e61a306c2e4 conditionally initializes a metadata area near the end of a caller-provided memory region, then invokes a worker dependency in batches. Processing is gated by an object field, a mode argument, and a caller-provided control byte.

Its observable result is a 32-bit value selected from:

- **3** when the object gate is zero, or after invoking an alternate-mode indirect operation.
- **2** when normal processing observes the control byte equal to one.
- **0** when normal processing reaches its completion check without invoking the worker.
- The most recent worker result when normal processing reaches its completion check after one or more worker calls.

These values describe observed return behavior, not established success or error meanings. In particular, a worker result is not inspected for failure before subsequent processing.

The apparent intent is bounded, block-oriented processing with a small metadata trailer and progress reporting. That interpretation is inferred; the contract below rests on the supplied static evidence.

## Behavior

### Arithmetic notation

The following descriptive names are mathematical labels, not implementation identifiers:

- **Aligned end**: region base plus the region size rounded down to a multiple of four.
- **Block value**: the value captured from object offset `0x434` after the first conversion call.
- **Batch capacity**: the first result obtained from F-d7be9cfb4000.
- **Target count**: the final count selected during setup.
- **Target bytes**: the final byte budget selected during setup.

Unless stated otherwise, arithmetic feeding addresses, counts, budgets, and comparisons uses 32-bit word arithmetic. Unsigned subtraction can wrap, and products can wrap before comparison. No wider intermediate arithmetic or saturation is established.

The block value is loaded from a field represented as a signed 32-bit integer, but several subsequent operations combine it with unsigned words. Its positive-size interpretation is therefore a precondition of the inferred block-processing use, not a validated property.

### 1. Entry gate and alternate mode

The function first reads the word at object offset `0x010`.

If it is zero, the function returns **3** immediately. It does not directly inspect the mode-specific configuration, access the control byte, initialize metadata, or invoke a dependency on this path.

If the gate is nonzero and mode is nonzero:

1. Read the dispatch-table pointer from the object's first word.
2. Obtain the callable entry at table offset `0x24`.
3. Invoke that entry with the object as its argument.
4. Return **3**, ignoring the callee's return value.

No direct normal-path metadata writes occur on this path. Effects of the indirect operation remain observable and unspecified.

### 2. Normal-path metadata initialization

When the gate is nonzero and mode is zero, calculate the aligned end by clearing the lowest two bits of the region size and adding the result to the region base.

The function then performs these operations in order:

1. Store aligned end minus 28 at object offset `0x43C`.
2. Store zero in the 32-bit word at aligned end minus 4.
3. Store zero in the 32-bit word at aligned end minus 8.
4. Invoke F-37a208cf00f1 with the object and the current word at object offset `0x438`.
5. Store that dependency's 32-bit result at aligned end minus 12.
6. Store zero at aligned end minus 16.
7. Read the control byte.

The function does not directly initialize the word at aligned end minus 28 merely because its address is stored in the object. Nor does it directly initialize the intervening words at minus 24 or minus 20.

If the control byte is exactly one, the function returns **2** after this initialization. Thus an initially asserted control byte does not suppress metadata initialization or the first F-37a208cf00f1 call.

### 3. Processing-budget setup

If the first control-byte observation is not one:

1. Capture the block value from object offset `0x434`.
2. Invoke F-d7be9cfb4000 with **65,536** and the captured block value. Its result becomes the batch capacity.
3. Invoke F-d7be9cfb4000 with:
   - region size minus 16, using unsigned 32-bit subtraction;
   - captured block value plus 12, represented at 32-bit width.
4. Initially use the second result as the target count.
5. Compute the available difference as the unsigned 32-bit difference between the current words at object offsets `0x424` and `0x438`.
6. Initially set target bytes to the 32-bit product of target count and captured block value.

If the available difference is strictly less than that product:

- Replace target bytes with the available difference.
- Invoke F-d7be9cfb4000 with the available difference and the captured block value.
- Replace target count with that result.
- If the 32-bit product of the replacement count and block value is strictly less than the available difference, increment target count by one, at 32-bit width.

The calls resemble quotient calculations, and the final adjustment resembles rounding upward for a partial block. Neither division semantics nor rounding behavior of F-d7be9cfb4000 is established by the supplied body.

The function does not subtract 16 from the aligned region size here: it subtracts 16 from the original size argument. This distinction matters for sizes not divisible by four and for sizes below 16.

### 4. Batched processing

Initialize:

- The iteration position to zero.
- The saved worker result to zero.
- Remaining bytes to target bytes.
- Remaining count to target count.

At the start of each iteration, compare the iteration position and target count as unsigned 32-bit values. If the position is greater than or equal to the target count, return the saved worker result.

Otherwise, derive:

- The batch count as the smaller of remaining count and batch capacity.
- The batch byte amount as the smaller of remaining bytes and the 32-bit product of captured block value and batch capacity.

Invoke F-2ea6a6cf7b63 with four arguments:

1. The object.
2. Region base plus iteration position multiplied by the **currently read** word at object offset `0x434`.
3. The batch byte amount.
4. The batch count.

Save its return value, replacing the previous worker result.

After the worker returns:

1. Subtract the batch count from remaining count.
2. Subtract the batch byte amount from remaining bytes.
3. Read the word at aligned end minus 8, add the batch count at 32-bit width, and write it back.
4. Invoke F-37a208cf00f1 with the object and target bytes minus remaining bytes.
5. Store its result at aligned end minus 16.
6. Read the control byte.

If this control-byte observation equals one, return **2**.

Otherwise, add batch capacity to the iteration position at 32-bit width and repeat the completion check.

The iteration position advances by batch capacity, not by the selected batch count. Worker addressing rereads the object's block field, whereas batch-byte calculations continue using the captured block value. Dependency changes to that field can therefore affect addresses without changing the cached sizing basis.

### 5. Completion and stopping precedence

The control byte is not checked immediately before every worker call. It is checked after initial metadata setup and after each worker call plus its progress updates.

Consequences include:

- A stop request observed after a worker does not prevent that worker's associated counter and progress writes.
- If the last batch causes the control byte to become one, the function returns **2**, not the last worker result.
- If the target count is zero and the initial control observation is not one, the function returns **0** without a worker call or per-batch progress conversion.
- Worker results do not directly determine continuation.

No explicit nontermination guard exists. For example, a zero batch capacity with a positive target count leaves the iteration position unchanged. Continued execution then depends on external effects, including later control-byte observations.

## Side effects

Direct writes are limited to:

- Object offset `0x43C`.
- The four 32-bit metadata words at aligned end minus 4, minus 8, minus 12, and minus 16.
- Repeated updates to the latter counter and progress locations during batching.

Dependencies may cause additional effects. Their implementations are unavailable, so the contract does not assume they preserve object fields, metadata, control storage, global state, or memory ownership.

Aliasing matters. If the object, metadata locations, control byte, or worker-accessed storage overlap, earlier writes or dependency effects can change later reads. In particular:

- The counter update reads its existing memory value after the worker returns; it does not maintain an independently protected counter.
- The available difference uses object fields read after preceding dependency calls.
- The worker address uses a fresh block-field read each iteration.
- The initial control observation occurs after metadata initialization and the first conversion dependency.

The supplied evidence establishes operation order, not atomicity, synchronization, or suitability for concurrent access.

## Acceptance examples

These examples are conditional static acceptance criteria, not reports of executed tests.

### Gate disabled

Given a readable object whose gate word is zero:

- The result is **3**.
- No dependency is called by this function.
- The region and control pointers need not be accessed by this function.

### Alternate mode

Given a nonzero gate and any nonzero mode, with a valid dispatch target:

- The indirect operation receives the object once.
- Normal metadata initialization is bypassed.
- If the operation returns normally, the function returns **3**, regardless of that operation's return bits.

### Initially stopped normal path

Given a nonzero gate, zero mode, and a control byte observed as one after initialization:

- The object receives aligned end minus 28.
- The four metadata writes and initial F-37a208cf00f1 call occur in the specified order.
- No F-d7be9cfb4000 or worker call occurs.
- The result is **2**.

### Zero target count

Given an initial control observation other than one and dependency results that produce target count zero:

- Setup completes.
- No worker call occurs.
- The result is **0**.
- The progress word at aligned end minus 16 retains the directly initialized zero unless some dependency has changed that storage.

### Two batches with a partial final batch

Assume:

- The captured and subsequently read block value remains 1,024.
- F-d7be9cfb4000 yields batch capacity 64 and final target count 100.
- Target bytes are 102,400.
- Dependencies do not alter relevant storage.
- Every control observation differs from one.

Then the worker receives:

1. Region base, 65,536 bytes, count 64.
2. Region base plus 65,536, 36,864 bytes, count 36.

The counter becomes 64 and then 100. Progress conversions receive 65,536 and then 102,400. The function returns the second worker result.

### Stop after a batch

Given a worker that causes the next control observation to equal one:

- Its selected count is added to the metadata counter.
- The cumulative byte progress is passed to F-37a208cf00f1 and stored.
- The function then returns **2**, even if that worker completed all remaining work.

### Rounded metadata location

For a size of 101 and address arithmetic without wraparound, the aligned end is region base plus 100. The counter is at region base plus 92. Capacity setup nevertheless passes 85, not 84, as the first argument of its second F-d7be9cfb4000 call.
