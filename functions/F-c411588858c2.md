# F-c411588858c2

## Purpose

F-c411588858c2 coordinates source acquisition, destination preparation, mapped-storage access, format-dependent processing, status reporting, and descriptor finalization.

Two format-dependent paths are established:

- Equal 16-bit format identifiers select repeated source operations that receive a mapped address and extent.
- An accepted mismatch selects explicit expansion of 16-bit input values into four-byte output units.

An image or pixel-transfer purpose is **inferred intent**, supported by the format checks and expansion. The direct path does not itself establish that any output storage is written.

Outcomes use two distinct numeric conventions:

| Outcome category | Reported status | Function return |
|---|---:|---:|
| Normal completion | `0` | `0` |
| Source unavailable or source operation fails | `2` | `1` |
| Destination unavailable, preparation fails, or initial mapping fails | `1` | `2` |

Normal completion means that control reaches the success-reporting path. It does not independently establish that the requested amount was written.

Descriptions below assume that dependencies return normally unless identified otherwise, and that each accessed location is valid when accessed. Dependency internals are unknown.

## Behavior

### Initial context operations and source acquisition

The function first resolves a context through F-418cc7cf316c using the second argument. It selects that object’s operation at offset `0x0c` and invokes it with the object and `1`.

It then calls F-418cc7cf316c again with the same argument. This second result is discarded, but the call remains part of the observable sequence.

Next, F-acf545428419 is called without explicit arguments.

If source acquisition returns null:

1. Resolve the context again.
2. Call F-51d91bb495ef with that resolution result, the original second argument, and status `2`.
3. Return `1`.

No destination acquisition or descriptor initialization occurs on this path.

There is no null check on the context used for the initial virtual dispatch.

### Destination acquisition and retained target

For a nonnull source, the function resolves the context again and calls F-a27a0f558363 with that result, `0`, and `1`.

If destination acquisition returns null, it resolves the context again, reports status `1`, and returns `2`. No descriptor has been initialized.

Otherwise, another context resolution supplies the object whose offset-`0x14` operation returns the metadata address. That virtual operation has no explicit arguments.

Metadata words `0` and `2` are multiplied to produce the retained 32-bit target. No overflow or sign validation is present. Later target comparisons use unsigned interpretation. The representation does not independently establish the relative order of these two metadata reads.

The target is not recomputed after later dependency calls, even if metadata changes.

### Descriptor preparation and initial mapping

The function performs these operations in order:

1. Initialize the persistent descriptor through F-be6dda74bd4d.
2. Set mapped extent to zero.
3. Set mapped address to zero.
4. Invoke destination offset `0x40` with the destination and the target twice.

A zero preparation result causes context resolution, status-`1` reporting, persistent-descriptor finalization through F-b6472f509e99, and return `2`.

For a nonzero preparation result:

1. Invoke destination offset `0x34` with the temporary-descriptor address and destination.
2. Call F-12ebaf6618b2 with the persistent and temporary descriptor addresses.
3. Finalize the temporary descriptor through F-b6472f509e99.
4. Call F-f47bc434ce71 with the persistent descriptor, mapped-address output address, mapped-extent output address, `0`, and `0`.

Initial mapping is accepted only if its return is nonzero and the unsigned mapped extent is at least the retained target. Otherwise, the function resolves the context, reports status `1`, finalizes the persistent descriptor, and returns `2`.

These preparation and mapping failure paths do not explicitly invoke context offset `0x24`.

### Associated-object operations

After accepted mapping, the function reads the associated-object pointer at persistent-descriptor offset `0x04`. It selects that object’s offset-`0x2c` operation and invokes it without explicit arguments.

After the call returns, the associated-object pointer is read again. The newly loaded pointer selects offset `0x50`; that operation receives the reloaded pointer and the preceding result minus one.

Consequently, the two operations need not use the same object. The first dependency is not assumed to preserve the descriptor-associated pointer.

The subtraction is unchecked 32-bit arithmetic. A preceding result of zero supplies the all-ones 32-bit value to the second operation.

The function then sets progress to zero and calls F-bfade2068003 with `0x19` and `1`. These operations occur even when the retained target is zero.

### Format selection and short-circuit checks

After F-bfade2068003 returns, the function resolves the context and compares its 16-bit field at offset `0x6c` with the low 16 bits of metadata word `7`.

Equal bit patterns select the direct path. The representation does not independently fix the relative order of the two field reads within this comparison.

On inequality, a separate short-circuit check occurs:

1. Read metadata word `7` again.
2. Compare its low 16 bits with `0x1888`.
3. If unequal, invoke F-a817d8d58c10 without performing the additional context resolution below.
4. If equal, resolve the context again.
5. Compare the newly resolved context’s 16-bit field at offset `0x6c` with `0x0565`.
6. Invoke F-a817d8d58c10 on inequality; otherwise select conversion.

These observations do not constitute one stable metadata/context pair. Metadata is reread, context resolution is repeated conditionally, and dependencies may modify shared state.

### Direct path

While unsigned progress is below the target, source offset `0x14` receives:

- The source object.
- Current mapped address plus cumulative progress.
- Current mapped extent.

The supplied extent is not capped at the remaining target.

A source result interpreted as signed and below `1` causes transfer failure. For a positive result, the function:

1. Subtracts the result from mapped extent.
2. Calls F-f47bc434ce71 with the persistent descriptor, the same two output addresses, and two zeros.
3. Adds the source result to cumulative progress.
4. Rechecks progress against the target.

The remapping return value is ignored. Its output parameters are nevertheless used by subsequent iterations. Remapping occurs even after a source result sufficient to reach or exceed the target.

The next source address combines the newly supplied mapped base with total cumulative progress, not merely the previous source result.

No check requires a positive source result to fit the supplied extent or remaining target. Extent subtraction, address calculation, and progress addition can wrap at 32 bits. Overshooting the target can cause normal completion.

This path contains no explicit output stores. Passing an address and extent does not establish the source operation’s memory effects.

### Conversion path

After the mismatch checks succeed, F-fab3799b3190 receives `0x10000`.

A nonnull result becomes the temporary input buffer. A null result selects the 32-byte local fallback buffer; allocation failure alone is not an error outcome.

Conversion iterations occur while unsigned progress is below the target and mapped extent is nonzero. Each iteration invokes source offset `0x14` with the source object and temporary-buffer address. No explicit extent argument is shown.

A result interpreted as signed and below `1` causes transfer failure.

For a positive result:

1. Clear its low bit to obtain an even input-byte count.
2. Reduce mapped extent by twice that count, using unchecked 32-bit arithmetic.
3. Read consecutive native-order unsigned 16-bit input values.
4. For each input value, explicitly store four bytes beginning at mapped address plus cumulative progress.

For input halfword \(s\), the stored byte values are:

| Byte position | Value |
|---|---|
| First | \((s \mathbin{\&} 0x001f)\times 8\) |
| Second | \((s \mathbin{\&} 0x07e0)/8\) |
| Third | \((s \mathbin{\&} 0xf800)/256\) |
| Fourth | `0` |

Each halfword is loaded before its four stores. Stores occur first byte, second byte, third byte, then zero byte. Progress advances by four for each halfword; its update precedes the fourth store in the supplied sequence.

The transformation places channel bits without replicating low bits for full-range scaling.

Extent reduction occurs before the batch’s input loads and output stores. The function does not remap during conversion and does not check remaining target or extent within a batch. A batch can cross either boundary. Extent underflow wraps rather than selecting an error.

A positive result of `1` rounds to zero: no halfword is read, no output byte is stored, and progress does not advance. Repeated results of `1` can prevent termination.

After loop exit, F-58ba61416cc9 receives the original allocation result. This includes null when fallback storage was selected; the fallback-buffer address is not passed.

Loop exit proceeds toward normal completion without an additional target-completion check. This is a control-flow rule, not a claim that every progress/extent combination is reachable.

### Transfer failure and completion

On either path, a source result below `1` causes:

1. Context resolution.
2. Status-`2` reporting through F-51d91bb495ef.
3. Another context resolution.
4. Invocation of that context’s offset-`0x24` operation without explicit arguments.

On conversion failure, F-58ba61416cc9 then receives the original allocation result. Both paths subsequently finalize the persistent descriptor and return `1`.

Normal completion performs context resolution, status-`0` reporting, persistent-descriptor finalization, and return `0`. Conversion allocation-result cleanup precedes that sequence.

Status-reporting and finalization return values are not inspected. No explicit rollback occurs. Persistence of earlier storage contents across these unknown calls is not established.

## Acceptance examples

These are conditional static examples, not executed tests. They assume valid accesses and normally returning dependencies except for the identified nonreturning operation.

1. **Source unavailable.** A null source result produces status `2` and return `1`, after both initial context resolutions and the initial virtual operation. Destination acquisition does not occur.

2. **Insufficient initial mapping.** Target `16`, nonzero mapping result, and extent `15` produce status `1`, persistent-descriptor finalization, and return `2`. No source transfer operation occurs.

3. **Associated pointer replacement.** If offset `0x2c` changes the descriptor-associated pointer to another valid object, offset `0x50` is selected from that replacement and receives the replacement pointer.

4. **Mismatch short-circuit.** If initial equality fails and the metadata reread is not `0x1888`, F-a817d8d58c10 is invoked without the additional context resolution for the `0x0565` check.

5. **Distinct format observations.** Initial inequality followed by metadata low bits `0x1888` and a newly resolved context field `0x0565` selects conversion. The initial comparison need not have observed that same pair.

6. **Direct-path completion.** With target `8`, equal formats, initial extent `8`, and source result `8`, one source operation is followed by remapping, status `0`, finalization, and return `0`. This does not establish that eight bytes—or any bytes—were written.

7. **Failure after a positive result.** A positive direct-path source result followed by zero produces status `2`, another context resolution, offset `0x24`, finalization, and return `1`. No explicit rollback occurs; storage effects and persistence remain unknown.

8. **Explicit conversion values.** Input halfwords `0x001f`, `0x07e0`, and `0xf800` produce store sequences `(248, 0, 0, 0)`, `(0, 252, 0, 0)`, and `(0, 0, 248, 0)` respectively.

9. **Odd conversion count.** Result `3` rounds to two input bytes: one halfword is converted, progress increases by four, and extent decreases by four. This function retains no trailing-byte carry.

10. **Conversion boundary crossing.** With target `4`, extent `4`, and source result `4`, two halfwords are converted. Progress becomes `8`, extent becomes `0xfffffffc`, and eight explicit output-byte stores occur, assuming those accesses are valid. No within-batch boundary check prevents this.

11. **Zero target.** Accepted preparation and mapping still lead through associated-object operations and F-bfade2068003. Format selection still occurs. Equal formats require no source operation; accepted conversion still performs allocation and allocation-result cleanup; unsupported mismatch invokes F-a817d8d58c10.
