# F-1476b82dc9cd

## Purpose

F-1476b82dc9cd performs a local restructuring of linked records. Under the inferred tree layout and ordinary non-aliasing invariants, it rotates a selected node to the left: the selected node’s right child takes its place, the promoted node’s former left subtree becomes the selected node’s right subtree, and the selected node becomes the promoted node’s left child.

The established behavior is a sequence of address-based reads, conditional decisions, and writes. The tree interpretation explains that sequence but does not establish that the input structure is a tree, that it satisfies search-order constraints, or that it is balanced.

The operation has no explicit result value. Its result is expressed through updates to node links and, when applicable, a root slot reached through the context.

## Interface

### Inputs

The function receives two address-valued inputs:

- **Context address:** identifies a record containing, at byte offset `+16`, an address used to locate a root slot.
- **Selected-node address:** identifies the node whose links are to be rearranged.

The supplied representation declares both arguments as integers and uses their values to construct addresses. It exposes four-byte link storage and integer comparisons against zero. The behavioral model below uses 32-bit link values, consistent with that representation. The native calling convention, signedness of address interpretation, and complete target ABI are not independently established.

### Relevant layout

All offsets are byte offsets.

| Record or location | Offset | Observed use |
|---|---:|---|
| Context | `+16` | Address of a separate root-holder record |
| Root-holder record | `+4` | Root slot, compared with the selected-node address and conditionally replaced |
| Node | `+4` | Parent link |

Only these locations are directly accessed. Their interpretation as parent, left child, right child, and root is inferred from the complete update pattern.

The **promoted node** is the address initially read from the selected node’s `+12` field. That address is retained for use throughout the operation; later accesses do not reselect it from the selected node’s right link.

### Output and completion

The function returns without an explicit value. It provides no success flag, status code, or reported error.

On an ordinary valid tree, completion leaves a left rotation at the selected node. For arbitrary addressable memory, only the ordered accesses and decisions described below are established; a valid tree-shaped result is not guaranteed.

### Preconditions for the intended structural result

The following are required to obtain the inferred rotation safely:

- The context and selected-node addresses identify suitably accessible storage.
- The selected node has a nonzero right-child address identifying a valid promoted node.
- The promoted node’s left-child link is either zero or identifies a valid node.
- The context’s `+16` field identifies an accessible root-holder record.
- If the selected node is not the root, its parent link identifies an accessible parent record.
- The selected node occupies the expected left or right position within that parent.
- Distinct logical records and their relevant fields do not overlap unexpectedly.
- No concurrent or reentrant mutation changes the links during the operation.

These conditions are not checked by the function.

## Behavior

### Ordered access and update contract

The following sequence describes the established source-level behavior. It does not promise processor-level atomicity or a machine-instruction trace.

1. **Select the promoted node.**  
   Read the four-byte link at selected node `+12`. Retain this address as the promoted node.

2. **Move the promoted node’s left link into the selected node’s right slot.**  
   Read promoted node `+8` and write that four-byte value to selected node `+12`.

3. **Conditionally repair the transferred child’s parent link.**  
   Read promoted node `+8` again and compare that newly read value with zero.

   If it is nonzero, read promoted node `+8` again to obtain the destination node address, then write the selected-node address to that node’s `+4` field.

   Consequently, the child link used for the zero test is not explicitly retained for the subsequent destination access. With stable, non-overlapping records, all these reads identify the same transferred child. With aliasing or external mutation, that equivalence is not established.

4. **Set the promoted node’s parent link.**  
   Read selected node `+4` and copy its four-byte value to promoted node `+4`.

5. **Locate the root slot and test root membership.**  
   Read the address at context `+16`, then read the root slot at offset `+4` from that address. Compare the root-slot value with the selected-node address.

   This lookup occurs after the preceding writes. If relevant storage overlaps, it is not necessarily a lookup through the context’s entry-state value.

6. **Reconnect the promoted node to the surrounding structure.**

   - If the root-slot value equals the selected-node address, write the promoted-node address into that root slot.
   - Otherwise, read selected node `+4` again to obtain its parent address. Read that parent’s `+8` field and compare it with the selected-node address.
     - If equal, write the promoted-node address to the parent’s `+8` field.
     - Otherwise, write the promoted-node address to the parent’s `+12` field.

   The non-root path does not check whether the parent’s right link actually points to the selected node. Failure of the left-link comparison is sufficient to choose the right slot.

7. **Attach the selected node below the promoted node.**  
   Write the selected-node address to promoted node `+8`.

8. **Finish the selected node’s parent update.**  
   Write the promoted-node address to selected node `+4`.

The final two writes occur after the root or parent reconnection. The function then returns.

### Result under ordinary tree invariants

Assume distinct, stable records, with the promoted node initially the selected node’s right child and a possible transferred subtree initially the promoted node’s left child. On completion:

- The selected node’s right link identifies the transferred subtree, or is zero if that subtree is absent.
- A nonzero transferred subtree has its parent link changed to the selected node.
- The promoted node’s parent link receives the selected node’s former parent value.
- The root slot or the selected node’s former parent link is redirected to the promoted node.
- The promoted node’s left link identifies the selected node.
- The selected node’s parent link identifies the promoted node.

Under those same assumptions, the selected node’s left link and the promoted node’s right link are unchanged. No node payload, ordering key, balance value, or color field is accessed explicitly.

## Side effects

### Memory writes

For stable, distinct records, the function writes:

- Selected node `+12`.
- Transferred child `+4`, only when the promoted node’s repeatedly read left link is nonzero.
- Promoted node `+4`.
- Exactly one of:
  - Root-holder record `+4`.
  - Former parent `+8`.
  - Former parent `+12`.
- Promoted node `+8`.
- Selected node `+4`.

With unusual aliasing, these may refer to overlapping physical locations rather than distinct fields.

The operation is not transactional. Several links are changed before the surrounding root or parent link is updated, and the selected node’s final parent write occurs last. An interruption or invalid access after earlier writes may leave partially modified storage.

## Acceptance examples

These are conditional consequences of the static behavior, not runtime test results.

### Root rotation with a transferred subtree

Given distinct, valid records where:

- The root slot identifies the selected node.
- The selected node’s right link identifies the promoted node.
- The promoted node’s left link identifies a transferred child.
- All relevant links remain stable during execution.

Expected completion:

- The root slot identifies the promoted node.
- The promoted node’s parent field contains the selected node’s former parent value.
- The promoted node’s left link identifies the selected node.
- The selected node’s parent link identifies the promoted node.
- The selected node’s right link identifies the transferred child.
- The transferred child’s parent link identifies the selected node.

The copied parent value is not forced to zero merely because the selected node was found in the root slot.

### Root rotation without a transferred subtree

Given the same conditions, except that the promoted node’s left link is zero:

- The selected node’s right link becomes zero.
- No transferred-child parent write occurs.
- The remaining root, promoted-node, and selected-node updates proceed as above.

Zero is accepted for the transferred-child link, not for the promoted-node address itself.

### Non-root node occupying its parent’s left slot

Given a root slot that does not identify the selected node, and a selected-node parent whose `+8` field does identify it:

- The parent’s `+8` field is replaced with the promoted-node address.
- The root slot is not written.
- The remaining rotation updates occur.

### Non-root fallback to the parent’s right slot

Given a root slot that does not identify the selected node, and a parent whose `+8` field does not identify it:

- The parent’s `+12` field is overwritten with the promoted-node address.
- No comparison against the previous `+12` value is required.

This remains the established branch behavior even if neither parent child-link originally identifies the selected node. Such an input violates the intended structural preconditions but is not explicitly rejected.

### Missing right child

Given a selected node whose `+12` field is zero:

- The function still attempts to read promoted node `+8`, using the zero link as the address base.
- There is no specified no-op, validation failure, or status return for this case.
- Whether an access faults depends on the execution environment.

### Overlapping records

Given overlapping selected-node and promoted-node storage, an early write may change a later read. The ordinary rotation result is therefore not an acceptance requirement for that input. Only the source-level access sequence is established; any concrete outcome requires the precise address layout and memory semantics.
