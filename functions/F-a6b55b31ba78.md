# F-a6b55b31ba78

## Purpose

F-a6b55b31ba78 conditionally replaces the storage described by a three-field header with a larger allocation for 16-bit elements. When replacement occurs, it copies the existing element range, invokes a dependency on the old storage, and rewrites the header to describe the replacement.

The inferred intent is a reserve-like operation: increase capacity without changing the logical contents or logical element count. That intent is conditional, not an unconditional guarantee. In particular, the meaning of the sizing dependency, allocator failure behavior, and the effects of releasing old storage are not established by the supplied evidence.

This function returns no value. Successful completion is observable through header changes, copied storage, and dependency calls.

## Interface

### Inputs

The function accepts:

- A pointer to a mutable header containing three consecutive 32-bit fields.
- A 32-bit unsigned requested capacity, expressed in units of 16-bit elements.

The header has the following apparent layout:

| Byte offset | Width | Interpretation used by this function |
|---|---:|---|
| 0 | 32 bits | Beginning address of element storage |
| 4 | 32 bits | End address of the current element range |
| 8 | 32 bits | End address of allocated capacity |

These are interpretations of how the fields are used, not independently established type declarations. The supplied representation stores addresses in 32-bit integer fields and accesses elements in two-byte units.

The normal storage invariant is inferred to be:

- The beginning, current end, and capacity end belong to one storage region.
- Their ordering is beginning ≤ current end ≤ capacity end.
- Their differences are multiples of two bytes.
- All source elements traversed during copying are readable.
- Any successful replacement allocation is large enough for the copied elements and reported capacity.

The function does not validate these invariants.

### Outputs

There is no explicit return value or returned status.

If the capacity comparison says the existing capacity is sufficient, the function makes no direct header or element-storage writes. An oversized request can nevertheless cause a dependency call before that comparison.

If replacement completes, the function directly writes all three header fields. The final current end depends on a second call to F-421ee22ef2f3, rather than on a locally retained count of copied elements.

### Width and arithmetic model

The supplied evidence uses 32-bit unsigned quantities for the request, growth calculations, selected capacity, and allocation-byte calculation. Unsigned addition and left shift therefore operate modulo \(2^{32}\).

Header address differences are represented as signed 32-bit expressions before right shifting by one bit. The initial capacity comparison then treats the shifted result as unsigned.

The exact machine interpretation of signed overflow and signed right shift is not independently established. For valid, nonnegative, even byte differences within the signed range, the calculation is unambiguous: the element capacity is half the byte difference. Behavior outside that domain must not be inferred from ordinary mathematical subtraction or division.

## Behavior

### 1. Oversized-request notification precedes capacity checking

A request strictly greater than 2,147,483,647 causes a call to F-5829ec5988c0.

That call receives:

1. The numeric value 8.
2. An address identifying an opaque static object.
3. The same address again.

The contents and meaning of that static object are unknown.

The request is not replaced with 2,147,483,647. Although that limit is placed in temporary state before the call, the later replacement path overwrites the temporary growth candidate before using it to select an allocation size.

Consequently, this is not an established clamping operation. If F-5829ec5988c0 returns normally, processing continues with the original unsigned request, including a request whose high bit is set. Whether the dependency normally reports an error, throws, terminates, or returns is unknown.

### 2. Compare requested capacity with the header’s apparent capacity

After any oversized-request call returns, the function reads the header’s beginning and capacity-end fields. It forms their signed byte difference, shifts that difference right by one bit, and interprets the result as an unsigned element capacity.

Replacement occurs only if that computed capacity is strictly less than the original requested capacity.

Otherwise, the function returns without:

- Calling the sizing dependency.
- Allocating replacement storage.
- Copying elements.
- Calling the old-storage dependency.
- Directly changing the header.

Equality therefore does not trigger replacement. A zero request also does not trigger replacement, because no unsigned computed capacity is less than zero.

This decision uses header state observed after the oversized-request dependency has returned. The evidence does not establish that the dependency preserves the header or other program state.

### 3. Obtain a sizing value and select replacement capacity

When replacement is required, F-421ee22ef2f3 is called with the header pointer. Its first returned value is treated as an unsigned 32-bit quantity for growth calculations.

The function forms two candidates:

- The returned value plus 32.
- The returned value plus its unsigned right-shift-by-one value plus its unsigned right-shift-by-three value.

The latter approximates 1.625 times the returned value when no arithmetic wraps. The separate shifts discard their fractional portions before addition.

The larger candidate is selected using unsigned comparison. The replacement capacity is then the larger of that candidate and the original requested capacity.

All additions in these calculations are 32-bit unsigned operations. Thus the selection is the maximum of the wrapped candidate values, not necessarily the maximum of their unbounded mathematical values.

There is no separate overflow rejection or saturation at this stage.

The role of F-421ee22ef2f3 is unknown. It plausibly reports the current element count, but the contract cannot equate its result with the header’s end-minus-beginning distance without a dependency contract.

### 4. Request replacement storage

F-871e64ddc6de is called with:

1. The selected replacement capacity shifted left by one bit.
2. Zero.

The first argument is a byte count derived from two bytes per element. It is a 32-bit calculation, so a selected capacity of at least \(2^{31}\) loses its high bit when converted to bytes.

The function does not check the returned address for allocation success before proceeding into the copying phase.

Importantly, the source-range addresses used for copying are read after this allocation call. They are not snapshots taken before the sizing and allocation dependencies ran.

### 5. Copy the current range in increasing address order

After the allocator returns, the function obtains the current end and beginning addresses from the header.

It traverses the source range from beginning toward the captured current end, advancing by two bytes per iteration. The destination starts at the returned allocation address and likewise advances by two bytes per iteration.

For each element:

- If the current destination address is nonzero, a 16-bit source value is read and written to that destination.
- If the current destination address is zero, that iteration performs no source-element read or destination-element write.
- Both traversal positions advance regardless of whether that iteration performed a copy.

For ordinary successful allocation, this is a forward, element-by-element copy. The function does not implement a general overlap-safe move; correctness therefore requires an appropriate relationship between old and replacement storage.

The zero-address condition is not an allocation-failure handler. It applies to each destination position, not to the allocation as a whole. A zero allocation result with a nonempty source range does not cause a clean early return.

The copy termination condition requires the source traversal to reach the captured end exactly. Invalid ordering, misalignment, unreachable end addresses, or inaccessible memory are not diagnosed.

### 6. Traverse the old range without element work

After copying, the function rereads the header’s beginning address and performs another traversal toward the header’s current end, advancing by two bytes.

The supplied body performs no element read, element write, or per-element dependency call during this traversal. In particular, it provides no evidence of element destruction.

For a well-formed, stable header, this traversal has no direct element-storage effect. Its termination still relies on a reachable end address. The endpoint is expressed as a header read during this phase rather than as the copy phase’s saved endpoint.

### 7. Invoke the old-storage dependency

F-ff1bdc376dcd is then called with:

1. The old beginning address saved for the second traversal.
2. The current capacity-end field minus that saved beginning address, shifted right by one bit.
3. Zero.

The second argument is an element-unit quantity derived from a signed address difference. It is not the allocation-byte argument used earlier.

The apparent intent is to release the previous allocation. The evidence establishes the call and its arguments, but does not establish that the dependency actually frees memory, that it accepts null addresses, or that it preserves the header.

No direct header update has yet occurred.

### 8. Recompute the end position and publish the header

After F-ff1bdc376dcd returns, F-421ee22ef2f3 is called again with the header pointer.

At the moment this second sizing call begins, this function has not yet replaced any of the three header fields. Any changes made by dependencies may nevertheless already be present.

The second return value determines the new current end. It is not required by the visible caller to match the first sizing result or the number of elements copied.

The direct header stores occur in this order:

1. Current end becomes replacement beginning plus twice the second sizing result.
2. Beginning becomes the replacement address.
3. Capacity end becomes replacement beginning plus twice the selected replacement capacity.

These are separate stores, not an atomic header replacement. An observer able to inspect intermediate state could see a new end paired temporarily with old beginning and capacity fields.

## Side effects

Established direct effects are:

- Reading the three-field header.
- Reading and writing 16-bit element values during a replacement copy.
- Writing the header’s current end, beginning, and capacity end in that order.
- Calling dependencies in the sequence described above.

On a replacement path that reaches every call, the dependency order is:

1. Optional oversized-request notification.
2. F-421ee22ef2f3.
3. F-871e64ddc6de.
4. F-ff1bdc376dcd.
5. F-421ee22ef2f3 again.

The copy and empty traversal occur between the allocation and old-storage calls.

Ownership transfer is inferred, not established: the function appears to acquire replacement storage and relinquish old storage. It contains no visible recovery path that releases the replacement allocation if copying or a later dependency fails. It also provides no visible rollback after old-storage processing.

No exception-safety guarantee, thread-safety guarantee, or guarantee of global-state preservation is established.

## Acceptance examples

These are conditional static expectations, not executed tests.

### Existing capacity is sufficient

Assume a stable, valid header describes 100 elements of capacity and the request is 100.

Expected behavior:

- No oversized-request notification.
- No replacement.
- No sizing, allocation, or old-storage calls.
- No direct header or element writes.

The same applies to any request below 100.

### Small-range growth uses the additive candidate

Assume:

- Existing capacity is 10 elements.
- The request is 11.
- The first sizing result is 10.
- Dependencies return normally and do not alter the header.

The candidates are 42 and 16. The selected replacement capacity is 42, and the allocation argument is 84 bytes.

If the source range contains 10 elements, allocation succeeds, and the second sizing result is also 10, those elements are copied in order. The final header describes 10 current elements and 42 elements of capacity.

### Proportional growth exceeds additive growth

Assume existing capacity is 100, the request is 101, and the first sizing result is 100.

The additive candidate is 132. The other candidate is 162: 100 plus 50 plus 12.

The selected capacity is 162, producing a 324-byte allocation request. This numerical result does not independently prove that 100 is the logical element count.

### The explicit request dominates growth

Assume existing capacity is 10, the request is 200, and the first sizing result is 10.

The growth candidate is 42, so the selected capacity is 200 and the allocation argument is 400 bytes.

### Oversized request is not clamped

Assume the request is 2,147,483,648 and the notification dependency returns normally. With a normal small existing capacity and small sizing result, the request dominates capacity selection.

The selected capacity remains 2,147,483,648. Its 32-bit byte conversion is zero. The visible function therefore calls the allocator with a zero first argument; it does not visibly replace the request with 2,147,483,647.

Successful storage behavior in this scenario is not established.

### The second sizing result changes the published end

Assume allocation and copying succeed, but the second sizing result differs from the copied element count.

The final current-end field follows that second result. The function does not compare it with the copied count or selected capacity. Any resulting inconsistency is not corrected locally.

## Uncertainties

The following are **documented_only**:

- The semantic meaning of either sizing result.
- Whether oversized-request notification returns.
- Allocation failure behavior and the validity of a zero returned address.
- Exact ownership and release behavior.
- Dependency mutations of the header, globals, or element storage.
- Signed arithmetic behavior outside valid, representable address differences.
- Address arithmetic at wraparound boundaries.
- Behavior for malformed headers, overlapping allocations, or concurrent mutation.
- Exception propagation, cleanup obligations, and resource guarantees on interrupted execution.

These unknowns prevent an unconditional promise that logical size and contents are preserved for every input.

## Evidence

The established behavior comes solely from static inspection of the supplied function representation and the provided opaque dependency mapping.

Static evidence supports the argument widths and header layout, strict capacity comparison, growth formulas, unsigned byte-count wraparound, forward 16-bit copying, dependency order, lack of a local allocation-failure exit, and final header-store order.

The reserve-like purpose, element-count interpretation of the sizing dependency, allocation ownership, and old-storage release are inferred intent rather than independently established dependency behavior.

No runtime tests have been performed.
