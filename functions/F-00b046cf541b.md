## Behavior

### Normalization and the zero path

The input is normalized using its leading-zero count. The function tests the resulting pattern for zero, rather than testing the original argument before normalization.

If the normalized pattern is zero, the function returns the all-zero word without performing the remaining encoding calculation.

For every nonzero input under the intended 32-bit normalization semantics, the normalized pattern has bit 31 set. Such an input therefore follows the encoding path.

For an all-zero input, returning zero is the apparent intent. However, a conventional leading-zero count of 32 makes normalization request a shift by the full operand width. The supplied body does not establish that this operation has defined execution semantics. Zero-to-zero is consequently a conditional result, not an unconditional runtime guarantee.

### Significand and exponent interpretation

For a nonzero input, the location of its highest set bit determines the exponent. Before rounding, the biased exponent is 158 minus the leading-zero count.

The normalized pattern divides into:

| Normalized bits | Role |
|---|---|
| 31 | Implicit leading significand bit |
| 30–8 | Twenty-three stored fraction bits |
| 7 | Half-unit rounding indicator |
| 6–0 | Evidence that the discarded portion exceeds an exact halfway point |

The leading bit is implicit in the inferred binary32 value and is not stored in the fraction field.

The arithmetic in the supplied body combines a signed right-shifted normalized value with an exponent-related contribution. With sign-extending right shift, the negative contribution from the leading bit yields the exponent and fraction layout described above.

This detail matters: substituting a zero-filling right shift into that arithmetic without changing the rest of the transformation would not preserve the result.

An input with bit 31 set has no leading zeros. Under the inferred contract, it is an unsigned magnitude at least 2³¹, not a negative value requiring a sign bit or magnitude adjustment.

### Rounding rule

The function implements the following rounding behavior under the stated representation assumptions:

| Discarded portion | Result relative to the encoding before rounding |
|---|---|
| Bit 7 is clear | Retain the encoding |
| Bit 7 is set and at least one of bits 6–0 is set | Advance to the next encoding |
| Bit 7 is set and bits 6–0 are all clear | Choose the neighboring encoding with an even least significant significand bit |

The last case is an exact halfway case. The selected encoding has bit 0 clear, whether the lower or upper neighbor is chosen.

An exact input, with all discarded bits clear, does **not** require an even result bit. The evenness adjustment applies only when the halfway indicator is set and all lower discarded bits are clear.

Rounding advances the complete encoded word. It is not confined to the fraction field. A carry through an all-ones fraction therefore increases the exponent.

No caller-supplied rounding mode exists. The visible calculation selects rounding from integer bits and does not explicitly consult a floating-point environment.
