# F-1f2e67c575ed

## Purpose

F-1f2e67c575ed performs two ordered indirect dispatches using the same supplied object reference. Each dispatch selects the callable entry at byte offset `0x58` from a dispatch base read through that object.

The two calls obtain their selectors from distinct shared-storage sources; the resulting values may be equal.

Before the first dispatch, the function captures a 32-bit value from a third shared-storage source. The second dispatch receives this captured value. The first dispatch instead receives a value from a separate read of that same source.

The established behavior is the sequence of dispatches, their lookup rules, and their argument selection. The application meanings of the selectors, shared value, and dispatched operations are unknown. Initialization, registration, notification, and similar interpretations are not established.

This contract describes the normal path represented by the supplied static evidence. It does not promise successful execution when an object, dispatch entry, or dependency is invalid, or when a dependency does not return.

## Interface

### Input and layout

The function accepts one object reference. The visible representation uses that reference to read a value at the start of the object, then uses the resulting value as a dispatch base.

| Location | Established use |
|---|---|
| Start of the supplied object | Holds the value used as the dispatch base |
| Byte offset `0x58` from the dispatch base | Holds the callable entry selected for an indirect invocation |

No other object fields are directly accessed in the supplied representation. The full object layout is unknown.

Each selected callable receives three arguments, in these positions:

1. The original object reference.
2. A selector obtained from shared storage.
3. A value associated with a separate shared-storage source.

For this contract, the three shared-storage locations are called the **first selector source**, **second selector source**, and **shared value source**. These labels describe their roles, not their application types or meanings.

The first and second selector sources are distinct locations. Nothing establishes that their contents differ, that their values are nonzero, or that either value belongs to a particular enumeration.

## Behavior

### Initial capture

Before either indirect invocation, the function reads the shared value source and retains its 32-bit value for the second invocation.

This capture is separate from the shared-value read used to prepare the first invocation’s third argument. The supplied representation therefore exposes two reads of the shared value source before entry into the first callable:

- An initial read whose value is retained for the second invocation.
- A separate read whose value is supplied to the first invocation.

The initial capture precedes the first invocation’s preparation expression. The relative ordering of reads within that later expression is not established.

If the shared value source remains stable, the two reads produce the same value. If the execution environment permits the source to change between them, their results can differ. The source does not establish volatility, atomicity, synchronization, or permission for concurrent mutation; those properties must not be inferred from the presence of two represented reads.

### First dispatch

The function reads a dispatch base through the supplied object and obtains the callable entry at byte offset `0x58` from that base.

The first invocation receives:

| Argument position | Value |
|---|---|
| First | Original object reference |
| Second | Value read from the first selector source |
| Third | Value separately read from the shared value source for this invocation |

The retained initial capture is not the represented source of the first invocation’s third argument.

The supplied representation does not establish a relative order among the dispatch-resolution reads, the first selector read, and the shared-value read within this invocation’s preparation. Their required relationship is that they supply the first invocation before its selected callable begins executing.

No local condition filters the first selector or shared value. In particular, the function contains no visible zero-value rejection, selector comparison, null-object guard, or callable-entry validation.

### Effects between dispatches

The first invocation occurs before the second dispatch is prepared.

Its body is unavailable. It must not be assumed to preserve the object, the dispatch base, dispatch entries, either selector source, the shared value source, or other global state. It may also affect external state or fail to return.

The function visibly performs no restoration or rollback after this dependency.

On a well-formed return, the retained 32-bit capture remains the selected third argument for the second invocation. This is not a guarantee against memory corruption, calling-convention violations, or other invalid execution.

### Second dispatch

After the first invocation returns, the function again reads a dispatch base through the original object reference and obtains the callable entry at byte offset `0x58`.

This is a repeated lookup, not a specified reuse of the previously selected callable. The two lookups may select the same target or different targets.

The second invocation receives:

| Argument position | Value |
|---|---|
| First | Original object reference |
| Second | Value read from the second selector source after the first invocation returns |
| Third | The 32-bit value captured before the first invocation |

Consequently:

- A valid change to the object’s dispatch base can affect the second target.
- A valid change to the selected dispatch entry can affect the second target.
- A change to the second selector source can affect the second selector argument.
- A change to the shared value source does not replace the retained third argument.

The function supplies the same object-reference value to both invocations. This establishes argument identity, not continued validity, unchanged contents, or retained ownership of the referenced object.

The ordering of the second selector read relative to the second dispatch-resolution reads is not established. They occur after the first invocation returns and before the second selected callable begins executing.

### Completion and interruption

If both invocations return normally and all required accesses succeed, the function returns without a value.

The representation contains no local retry, alternate target, error conversion, cleanup action, or rollback.

If the first invocation does not return to this function, the second dispatch is not reached on the represented path. If the object becomes invalid during the first invocation, there is no visible guard before its subsequent use.

Precise behavior for access faults, invalid indirect transfers, exceptions, and nonlocal control transfers is not established. The absence of local handling does not establish any particular platform-level propagation behavior.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence. They are not executed tests.

### Stable storage and dispatch

Given valid storage, an unchanged dispatch base and entry, and dependencies that return normally:

- Exactly two indirect invocations occur on the represented normal path.
- Both receive the original object reference.
- The first selector comes from the first selector source.
- The second selector comes from the second selector source.
- Both third arguments equal the stable shared value.
- Both dispatch lookups select the unchanged callable entry.

### Equal selectors from distinct sources

Suppose both selector sources contain the same compatible value, such as 4, and all normal-path preconditions hold.

Both invocations receive 4 as their second argument. Equality does not suppress, combine, or reorder the invocations. The requirement concerns distinct source locations, not unequal contents.

### Shared value changed by the first dependency

Suppose the shared value source contains 7 during both initial reads. The first dependency changes that source to 9 and returns normally.

The second invocation receives 7 as its third argument. The function has no visible requirement to restore the shared source, so the source may remain 9 subject to other dependency effects.

### Different values at the initial reads

Suppose the environment validly permits the shared value source to contain 7 during the initial capture and 8 during first-invocation preparation.

The first invocation receives 8 as its third argument. The second receives the retained 7, assuming normal continuation.

This example does not establish that an unsynchronized concurrent write is valid in the underlying execution model.

### Second selector changed by the first dependency

Suppose the first dependency changes the second selector source from 2 to 5, and that value remains stable until the second selector read.

The second invocation receives 5. It must not receive a value cached from that source before the first invocation.

### Dispatch base replaced

Suppose the first dependency validly replaces the object’s dispatch base with another usable base and returns normally.

The second dispatch resolves offset `0x58` using the replacement base. Unconditionally reusing the first callable would not preserve the represented behavior.

### Zero values

Suppose either selector or the shared value is zero while all accesses and callables remain valid.

The function still attempts both dispatches on normal continuation. Whether either callable accepts zero is unknown; the function itself performs no zero-value rejection.

### First dependency does not return

If the first dependency never returns to this function, the second dispatch does not occur on the represented path. No compensating action is specified.

### Invalid or expired object

A null, unreadable, or no-longer-live object has no specified successful outcome. The representation contains no guard that converts it into a no-op or returned error.

## Evidence
