# F-ce267b08801d

## Purpose

F-ce267b08801d destructively processes reachable records and prepends them through a caller-supplied head field. It reuses each processed record’s four-byte field at byte offset 12 as a successor link.

For each record, the routine first recursively processes the link at offset 12, then prepends the record, then continues through the link read at offset 8. The offset-8 read occurs after the recursive invocation returns.

Under the interpretation of offset 8 as a left-child link and offset 12 as a right-child link, a finite, nonshared tree with nonoverlapping record storage is processed in right–record–left order. Prepending reverses that order: the converted records are linked in left–record–right order.

That ordering does **not**, by itself, establish a well-formed chain followed by an unchanged preexisting suffix. Under the ordinary tree assumptions, the last record in the converted order receives the initial head value. If that value identifies a converted record, the result can contain a cycle.

Preserving a preexisting suffix additionally requires that conversion not overwrite its successor fields. Suffix records disjoint from both the input records and state storage are a sufficient separation condition. Merely copying the initial head value does not require readable suffix storage.

No allocation, record copying, or deallocation is shown.

## Interface

The routine accepts two arguments:

- **State address:** an address-valued integer identifying storage whose four-byte field at byte offset 4 holds the accumulating head.
- **Starting-record address:** an address-valued integer identifying the first record to process. Zero terminates processing.

There is no explicit return value and no reported success or failure status.

## Behavior

### Empty input

When the starting-record address is zero, the routine returns immediately.

It does not read or initialize the state head, inspect any record, or perform any persistent write. In particular, it does not clear a preexisting head.

### Access and processing order

For each nonzero current-record address, the established sequence is:

1. Read the four-byte field at the current record’s offset 12.
2. Invoke F-ce267b08801d recursively with the same state address and that field value as the starting-record address.
3. After the invocation returns, read the four-byte field at the current record’s offset 8 and retain its value as the continuation.
4. Read the four-byte head at state offset 4.
5. Write that head value into the current record’s offset-12 field.
6. Write the current-record address into the state’s offset-4 field.
7. Continue with the retained continuation, stopping when it is zero.

The recursive invocation therefore precedes both the continuation read and the head read.

The offset-8 value used for continuation is its value **after** recursive processing. If recursive activity changes that storage through overlap, the later value is used. The routine does not preserve the original offset-8 contents before recursion.

Once read, the continuation is retained across the two prepend writes. If either write overlaps the continuation field, it does not change the value already retained for the current iteration.

Similarly, prepending uses the head present after recursive processing. The routine does not save an earlier head and restore it afterward.

### Ordinary tree interpretation

For this interpretation:

- Offset 8 identifies the left child.
- Offset 12 identifies the right child.
- Zero means no child.
- Input records form a finite, nonshared tree.
- Record storage does not overlap other record storage or the state.
- No external mutation interferes.

Under these conditions, every input record is processed once. Processing order is right subtree, record, left subtree. Among the converted records, the resulting successor order is left subtree, record, right subtree.

More precisely:

- The final state head identifies the first record in that converted order.
- Each converted record except the last has an offset-12 successor identifying the next converted record.
- The last converted record’s offset-12 field contains the initial state-head value.
- The last record in the converted order is the first record prepended during execution.
- Offset-8 fields are not directly changed.

These statements describe the converted records and the terminal value copied into them. They do not imply that following successors reaches zero or enters an unchanged suffix.

No payload comparison occurs. The ordering is structural, not a guarantee of numeric or key sorting.

### Initial head and suffix preservation

The initial head contributes a value, not an independently traversed input structure. Under the ordinary tree conditions, it is copied into the first record prepended, which becomes the last record in the converted order.

There are three distinct guarantees:

- **Head-value copying:** The initial head value becomes that terminal successor value.
- **Ordering of converted records:** Their successor fields connect them in the structural order described above.
- **Preservation of a preexisting suffix:** This requires an additional noninterference condition on the suffix’s successor storage.

For example, if the initial head identifies one of the converted records, the terminal successor points back into the converted sequence. A cycle can result even though the original input tree was finite, nonshared, and processed without interference.

An existing suffix remains unchanged only if none of its relevant successor fields overlaps storage written by conversion. Requiring all suffix records to be disjoint from the input records and state storage is sufficient. Exclusive access is also needed to exclude unrelated changes.

If the suffix was initially a valid finite chain and these preservation conditions hold, the final result is the converted sequence followed by that unchanged suffix. If the suffix was already cyclic or otherwise malformed, preserving its fields does not repair it.

The initial head need not identify readable storage for this routine’s copying operation. Requirements imposed by later consumers are separate.

### Shared records, cycles, and overlap

The routine maintains no visited set. Reaching an address again processes its then-current fields.

Because processing overwrites offset 12, a later visit may follow a different recursive link from an earlier visit. Shared records, cycles, partially overlapping records, or overlap with the state can cause repeated processing, altered traversal, malformed successor structures, invalid accesses, or nontermination.

The local access sequence remains established, but the ordinary tree conclusions do not apply without their structural conditions. No general graph-conversion result is established.
