# F-94f8b710221d

## Purpose

F-94f8b710221d prepares an owner-associated record and, when eligible, inserts that record into a singly linked collection using a computed 32-bit key and an external comparison operation. Except on an early-return path, it then calls a completion dependency and conditionally invokes an indirect callback.

**Inferred intent:** the record may represent scheduled or timed work. The supplied representation does not establish time units, ordering semantics, synchronization guarantees, or the callback’s purpose.

An already-marked record still undergoes preparation calls and a metadata write before returning. A zero insertion quantity skips insertion, but not completion or callback-gate processing.

A shared global has two visible uses: its value is passed to F-338d16f9ce72, and it is independently reread after F-5bcae2eff9a7 to obtain the address used for the final callback-gate lookup. Those reads are not interchangeable snapshots.

### Execution preconditions

No pointer, storage-size, alignment, list-integrity, or callback-target validation is visible.

Every reached access must refer to suitable storage for normal execution. In particular, final gate processing requires the newly read shared gate-source value to identify a readable cell. The function dereferences that address without first checking it for null. It checks the pointer obtained from the cell, not the cell address itself.

Traversal terminates only if it encounters a null node or a nonzero comparison result. No cycle detection is visible.

## Behavior

### Preparation and record selection

The initial observable sequence is:

1. Read owner +184 and call F-bac16c793e7a with the owner address and that value.
2. Read owner +180 and call F-6904f7699031 with that value and the constant 125.
3. Reread owner +180 and retain the resulting working-record address.
4. Call F-936a8728139d with no explicit arguments.
5. Read the preparation metadata global and write its 32-bit value to working-record +32.
6. Read working-record +28.

Earlier calls may affect later reads. The record selected after F-6904f7699031 therefore need not be the record whose address was passed to that dependency.

Once selected, the working-record address is retained. A subsequent change to owner +180 does not by itself redirect this function’s direct record accesses.

If the marker at +28 is nonzero, the function returns immediately. It does not reach F-338d16f9ce72, inspect the quantity, insert the record, call F-5bcae2eff9a7, or evaluate the callback gate.

### Eligibility and quantity capture

For a zero marker, the function:

1. Reads the shared gate-source global and passes that value to F-338d16f9ce72.
2. Calls F-add44d4e9aaa with the retained working-record address.
3. Reads and captures the 32-bit quantity at working-record +4.

This quantity read occurs after both dependencies return. Their changes to that field can therefore affect insertion eligibility and key computation.

A zero quantity skips the entire key-computation and insertion path. Completion and final gate processing still follow.

Every nonzero 32-bit quantity enters the insertion path. There is no positive-only check, range check, or special exclusion for a high-bit-set value.

### Key computation and head selection

The insertion path calls an unidentified dependency with no explicit arguments and uses its returned 32-bit value in the key computation.

The stored key is the low 32 bits of the sum of:

- The returned value.
- The captured quantity multiplied by 1000.

No saturation, overflow notification, or wider stored result is visible. Signed semantic meaning and intended wraparound interpretation remain unresolved; the observable destination is a 32-bit field.

The quantity was captured before the value-producing call. A change by that dependency to record +4 does not replace the captured quantity for this computation.

After the dependency returns, the function performs these operations in order:

1. Read the head-address global and retain the address of the head cell.
2. Write the computed key to working-record +8.
3. Read the insertion metadata global and write its value to working-record +24.
4. Read the collection head through the retained head-cell address.

The head-cell address and its contents are distinct reads. The collection is not selected from an entry-time snapshot.

### Traversal and insertion

Traversal starts at the head just read, with no predecessor.

For each nonnull current node, F-0d70d6f9010c receives:

- The address at current-node +8.
- The address at working-record +8.
- The third explicit input.
- The fourth explicit input.
- The unresolved ambient 32-bit value.

Only zero versus nonzero is tested:

- Zero continues traversal.
- Any nonzero value stops traversal before the current node.

No positive-versus-negative distinction is visible. Ascending order, descending order, equality treatment, and stability depend on the unknown comparator contract.

After a zero result, the current node’s next link is read, and that node becomes the predecessor. The link read occurs after the comparison returns, so comparator changes to that link can redirect traversal. The comparison receives addresses rather than copied keys; repeated comparisons may observe changes to the addressed data.

Traversal stops at either a nonnull node with a nonzero comparison result or a null node. Insertion then makes three ordered stores:

1. Write the working-record address to the retained head cell if there is no predecessor, otherwise to predecessor +0.
2. Write exactly 1 to working-record +28.
3. Write the stopping-node address, possibly null, to working-record +0.

The record becomes reachable through the updated collection link before its marker and next link are finalized by this function. Atomic publication or exclusion of concurrent observers is not established.

The selected record itself is linked. No direct allocation, record copy, identity search, or deallocation is visible.

### Completion and callback gate

Both the zero-quantity path and the completed-insertion path continue as follows:

1. Read the completion-handle global and call F-5bcae2eff9a7 with that value.
2. After the call returns, **reread the shared gate-source global**.
3. Treat this newly read value as a cell address and read a 32-bit pointer from that cell.
4. If the pointer is nonnull, read its first 32-bit word.
5. If both the pointer and that first word are nonzero, invoke the callback obtained from the separate callback-target global, with no explicit arguments.

The shared gate-source global in step 2 is the same global whose earlier value was passed to F-338d16f9ce72. The earlier argument is not reused. Any intervening dependency, including F-5bcae2eff9a7, can change that global and thereby redirect the final cell lookup.

A null pointer read from the cell suppresses the first-word access and callback. A nonnull pointer with a zero first word suppresses the callback. There is no corresponding null check on the cell address before the cell is read.

The inspected first word is a gate, not the callback target. A passing gate does not validate the separate callback-target global. No callback result is visibly consumed.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Except where stated, dependencies return normally and do not modify storage relevant to the example.

### Already-marked record

If the selected record has marker 7 when checked, the initial three dependencies run and record +32 is updated. The function then returns without calling F-338d16f9ce72 or reaching completion and gate processing. Any nonzero marker has this effect.

### Zero quantity

If the marker is zero and the quantity read after F-add44d4e9aaa is zero, F-338d16f9ce72 and F-add44d4e9aaa run, but no key-producing call, comparison, or direct insertion write occurs. F-5bcae2eff9a7 and the final shared-global reread still occur.

### Empty collection

With a nonzero quantity and a null head, no comparison occurs. After key and metadata writes, the head cell receives the record address, the marker receives 1, and the record’s next link receives null, in that order.

### Comparison outcomes

If the first comparison returns any nonzero 32-bit value, insertion occurs before the first node.

If all comparisons return zero and traversal reaches a null next link, the last node’s next link receives the record address. The record’s next link is subsequently set to null.

### Arithmetic boundaries

For captured quantity 3 and returned value 400, the stored key is 3400.

For captured quantity 1 and returned value 4,294,967,000, the stored 32-bit key is 704. No separate overflow report is visible.

### Record replacement during preparation

If F-6904f7699031 changes owner +180 from one valid record address to another, the subsequent reread selects the replacement. Changing owner +180 later, during F-936a8728139d, does not by itself replace the retained working record.

### Redirected final gate

Suppose the shared gate-source global initially contains the address of cell A. F-338d16f9ce72 receives that address.

If an intervening dependency changes the global to the address of cell B, and that value remains through F-5bcae2eff9a7’s return, the final gate reads cell B, not cell A. Cell A’s pointer and first word do not control that final decision.

If cell B contains null, the callback is suppressed even if cell A would have enabled it. Conversely, a valid pointer in cell B with a nonzero first word enables callback dispatch even if cell A would have suppressed it.

### Gate validity versus gate outcome

A valid gate cell containing null suppresses the callback without a first-word access.

A valid gate cell containing a valid nonnull pointer to a zero word also suppresses it.

A valid gate cell containing a valid nonnull pointer to a nonzero word reaches callback dispatch, assuming a usable callback target.

A null or invalid address in the shared gate-source global is not a safe “disabled” state: the cell access is attempted before the nullable pointer check.
