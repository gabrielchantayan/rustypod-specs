# F-a7dd7848f4b0

## Purpose

F-a7dd7848f4b0 obtains a node from a dependency, prepares part of its payload, attaches it beneath a caller-selected parent, performs ancestry-dependent recoloring and balancing calls, and publishes the originally obtained node address.

The caller supplies the attachment position. This function does not search for an insertion point, establish ordering, reject duplicates, or check whether the chosen child position is vacant.

The structure is consistent with red–black tree insertion. That interpretation is **inferred intent**, not a proven postcondition. Correct ordering, balance, initialization, and lifetime depend on contracts not supplied for the dependencies.

This document describes established static behavior. No runtime tests have been performed.

## Behavior

### Node acquisition, payload preparation, and count

The first dependency invoked is F-a34c918948fb, with the container address. Its returned address is retained as the original new node throughout the operation, independently of subsequent movement through the ancestry.

Payload preparation is conditional on the address 16 bytes beyond that node being nonzero. This condition is not a null check on the node address itself.

When that derived address is nonzero, F-f4fd698ba468 receives it and the source address. After the dependency returns, four bytes are read from source offset 4 and written at offset 4 from the dependency’s returned address. Thus:

- Source changes made by the dependency are visible to the explicit copy.
- The returned address, not necessarily the supplied payload address, determines the copy destination.
- No broader payload-copy guarantee follows from this explicit four-byte transfer.

When the derived address is zero, both the preparation call and the explicit copy are omitted. Insertion otherwise continues.

The container count is read and increased by one after payload preparation and its explicit copy, but before comparison or attachment. Its read therefore observes any relevant changes made by preceding dependencies.

The count operation uses a signed four-byte representation. Behavior at signed overflow is not established; this contract does not choose wrapping, trapping, or any other overflow policy. Likewise, the exceptional address-arithmetic case that makes the derived payload address zero has no established portable interpretation.

### Attachment decision

The header address is read from the container before deciding whether comparison is necessary. This header read occurs even when the selector is nonzero.

First-child attachment is selected without comparison if the supplied parent equals that header, or if the selector is nonzero. Otherwise, F-31a0b2b5649a receives these three addresses, in order:

1. Container offset 25.
2. The source address.
3. Supplied-parent offset 16.

A nonzero comparison result selects the first child; zero selects the second child. No signed ordering or three-way comparison meaning is established.

Two values are also retained for a possible expanded balancing call. They initially contain the original selector and supplied-parent address. Entering the comparison path replaces both retained values with zero, before the comparison dependency is invoked. Their later values do not depend on the comparison result.

Comparison occurs after the count update and before any attachment write. Its effects are not constrained to comparison: it cannot be assumed to preserve source data, header state, topology, globals, or ownership.

### Attachment and header maintenance

Attachment replaces the selected child field of the supplied parent with the original new-node address. There is no vacancy check and no preservation of the displaced link.

Header maintenance follows that parent-child write and uses a freshly read header address.

| Selected position | Header maintenance |
|---|---|
| First child, reloaded header differs from supplied parent | Replace the reloaded header’s first extreme only if its current value equals the supplied parent. |
| First child, reloaded header equals supplied parent | Set that header’s root to the new node; reload the container’s header again; set the newly obtained header’s second extreme unconditionally. |
| Second child | Replace the reloaded header’s second extreme only if its current value equals the supplied parent. |

On the first-child path where the header equals the supplied parent, the initial attachment write already targets header offset 8. With an unchanged header, this produces writes to header offsets 8, 4, and 12, in that order.

After the applicable header maintenance, the supplied-parent address is written into the new node’s parent field.

The important ordering boundary is therefore: count update precedes comparison if needed; the selected child link is then replaced; header maintenance follows; the new node’s parent field is assigned last among these attachment effects. Header decisions do not reuse the header snapshot from attachment selection.

### Balancing semantics

Balancing begins with the new node as the current node under consideration.

At each reevaluation, the current root is obtained through the container’s current header. If the current node equals that root, balancing stops without inspecting its parent’s color. Otherwise, a nonzero parent-color byte stops balancing.

Only zero versus nonzero is tested. Recoloring writes the exact byte values 0 and 1. Describing zero as red and one as black is an inferred interpretation; a different nonzero byte still satisfies a nonzero-color test.

For a zero-colored parent, the function obtains the grandparent and determines the orientation by comparing the parent with the grandparent’s first child. Equality selects the first-child-parent orientation. Inequality selects the mirrored orientation without proving that the parent occupies the second-child position.

The opposite child of the grandparent is treated as the uncle. The following cases govern the balancing effects:

| Condition | Established effect |
|---|---|
| Uncle is non-null and zero-colored | Color the parent 1, then the uncle 1, then the ancestry-derived grandparent 0; advance the current node to an ancestry-derived grandparent and reevaluate. |
| Uncle is null or nonzero-colored; parent has first-child orientation | If the current node occupies the parent’s second-child position, invoke F-ebd170a93754 on that parent and then use the pre-call parent as the current node. Recolor the current parent 1 and current grandparent 0, then invoke F-6b3ab84173ed on an ancestry-derived grandparent. |
| Uncle is null or nonzero-colored; mirrored orientation | If the current node occupies the parent’s first-child position, invoke the expanded form of F-6b3ab84173ed on that parent and then use the pre-call parent as the current node. Recolor the current parent 1 and current grandparent 0, then invoke F-ebd170a93754 on an ancestry-derived grandparent. |

The ancestry-derived targets are significant. In the recoloring-only case, the grandparent used for the color write is reached after the parent and uncle writes. The ancestry used to advance the current node is read after the grandparent color write. In the other cases, ancestry is consulted after any inner dependency call and again following recoloring to obtain the outer call’s target.

Consequently, cached ancestry must not be substituted for later observations when dependencies or overlapping storage can change the links. A balancing dependency’s effects on the header, root, ancestry, or other accessible state are unknown; subsequent accesses observe whatever state it leaves.

There is no iteration bound, cycle detection, or topology validation. Termination and structural correctness are conditional on the supplied state and dependency behavior.

### Completion

After balancing stops, the function reloads the header and obtains its root. It writes color byte 1 to that root, even if no balancing iteration occurred.

Only after this root-color write does it publish the original new-node address through the output location.

The published node need not be the final root or the final node considered during balancing. If the output location overlaps container or node storage, publication can itself overwrite previously established state.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless an example explicitly varies them, assume valid, non-overlapping storage, normal dependency returns, stable relevant state, sufficient node initialization, and representable arithmetic.

### Header-parent insertion

If the supplied parent equals the unchanged header, comparison is bypassed. After payload handling and the count increment, header fields at offsets 8, 4, and 12 receive the new-node address in that order. The new node’s parent becomes the header.

Because the current node then equals the root, no balancing dependency is invoked. The root is colored 1 before the original node address is published.

### Forced first-child attachment

For a non-header parent and a nonzero selector, comparison is bypassed. The parent’s first-child link is replaced. The header’s first extreme changes only if its observed value equals that parent.

If the parent is nonzero-colored and the new node is not the root, balancing stops at the parent-color check. Final root coloring and publication still occur.

### Comparison selects the second child

For a zero selector and a parent unequal to the initially observed header, comparison occurs after the count increment. A zero result selects the second child.

The parent’s second-child link is replaced, and the reloaded header’s second extreme changes only on equality with the supplied parent. Any later expanded balancing call receives zero in its fifth and sixth positions.

### Preparation changes the source and returns different storage

If F-f4fd698ba468 changes the source field at offset 4 and returns a valid address distinct from the supplied payload address, the explicit copy uses the changed source value and writes it at returned-address offset 4. It does not necessarily write into the new node’s payload.

### Zero-colored parent and uncle

For valid ancestry with a non-null zero-colored uncle, the parent is colored 1 before the uncle is colored 1. The ancestry-derived grandparent is then colored 0, and balancing proceeds upward. Normal completion subsequently colors the then-current root 1.

### Expanded call with a null uncle

In the mirrored orientation, suppose the uncle is null, the current node occupies its parent’s first-child position, and the grandparent address is represented by `0x00001000`.

The inner F-6b3ab84173ed invocation receives a null third value and `0x00001000` as its fourth value. Its final two values follow the comparison-path rule, not the uncle’s nullness.

### Noncanonical nonzero color

A parent color byte of 7 stops balancing just as a byte of 1 does, provided root equality did not already stop it. This does not normalize that parent’s color. The independently obtained final root still receives byte 1.
