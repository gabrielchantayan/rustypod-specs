# F-34798fb5fd75

## Purpose

F-34798fb5fd75 transfers a requested number of source bytes to selected output registers. It polls a status register before each batch and, when the tested status bits are clear, writes up to 16 bytes without another status check. Some iterations invoke two dependencies before polling again.

The register accesses suggest a polled device-output operation. That is **inferred intent**, not an established device protocol. The contract below describes the observable accesses, dependency calls, arithmetic, and control flow supported by the supplied static representation.

Normal completion invokes an exit dependency and returns a 32-bit zero. There is no explicit timeout, cancellation mechanism, transferred-count return, or error return.

## Interface

### Inputs

| Input | Width and interpretation |
|---|---|
| Context address | A target address represented by a 32-bit integer-shaped argument. Used to locate three fields. |
| Byte count | Unsigned 32-bit number of bytes requested. |
| Source address | Address of the next source byte. Advanced internally after each output write. |

The context supplies the following fields:

| Offset | Access width | Use |
|---|---|---|
| `0x01` | 8 bits | Bank selector, reread before each status read and each output write. |
| `0x04` | 32 bits | Argument for the entry and exit dependencies, read separately for each call. |
| `0x858` | 32 bits | Signed arithmetic input read once before the entry call. |

No complete context layout, allocation size, alignment contract, or validation procedure is established.

Two global storage locations are relevant:

- A register-base global, read **three times in order** after the entry call.
- A pacing global, read only on qualifying post-transmission iterations.

The supplied representation uses 32-bit target addresses and arithmetic values. Exact address-overflow behavior and platform memory-access requirements remain environment-dependent.

### Output

On normal completion, the result is the 32-bit value zero.

The function does not return the number of bytes written, an updated source address, a device status, or a dependency result. An invocation that polls indefinitely does not return.

### Preconditions and ownership

For normal execution:

- Every context field must be readable when accessed.
- The source must permit each byte read actually reached.
- Selected status and output addresses must permit the specified 32-bit accesses.
- The globals must be readable at their respective access points.
- Dependencies must accept their arguments and return if completion is expected.

There are no explicit checks for null pointers, insufficient source storage, invalid selectors, or inaccessible register banks.

The function does not visibly allocate, release, or retain either input address beyond the invocation. Neither the context address nor source address is directly passed to a dependency. This does not establish that dependencies cannot reach them through shared state or affect ownership.

A zero count avoids source and register accesses, but still performs initialization, three register-base global reads, and the entry and exit calls.

## Behavior

### Initial arithmetic

Before testing the byte count, the function reads the signed 32-bit context field at `0x858`. It multiplies that input by 13, converts the product to unsigned 32-bit form, and shifts that unsigned value right by one bit.

The resulting value is retained for later dependency arguments. The context field is not visibly reread.

For inputs whose product is representable as signed 32-bit arithmetic, the calculation is established. The conversion before the shift means the shift is logical, not sign-extending. For example, an input of `-1` produces an unsigned converted product of `0xFFFFFFF3`, then a retained value of `0x7FFFFFF9`.

The supplied representation alone does not establish behavior when the signed multiplication overflows. Such cases are **documented_only**.

### Entry and ordered bank initialization

After computing the retained arithmetic value, the function:

1. Reads the 32-bit context field at `0x04`.
2. Calls F-opaque-01 with that value.
3. Reads the register-base global and retains that value as the **first captured bank**.
4. Reads the same global again and retains the newly read value plus `0x4000` as the **second captured bank**.
5. Reads the same global a third time and retains that newly read value plus `0x8000` as the **fallback captured bank**.

These are three ordered global-read expressions, not one read reused for three calculations.

Each resulting bank address is retained independently for the rest of the invocation. The function does not visibly reload these addresses during polling or transmission.

If the global has the same value at all three reads, the captured banks differ by the stated offsets. If it changes between reads, no such relative-offset relationship is guaranteed. For example, the second captured bank need not equal the first captured bank plus `0x4000`.

All three reads occur after F-opaque-01 returns and before the first zero-count check. An entry-dependency change to the global can therefore affect initialization. Later changes to the global do not themselves replace already captured bank addresses.

This describes the supplied representation’s access sequence; it does not independently establish machine-level volatile or synchronization guarantees.

### Completion check

The remaining count is tested against zero before entering polling.

When it is zero, the function:

1. Reads the context field at `0x04` again.
2. Calls F-opaque-02 with that newly read value.
3. Returns a 32-bit zero.

The entry and exit arguments can differ if the field changes between their reads. No shared cached argument is used.

After a batch that leaves either zero or a high-bit-set remaining count, control returns to this same completion check. Only an actual zero completes the operation.

### Bank selection

Before each status read and before each output write, the selector byte at context offset `0x01` is read anew.

| Selector byte | Selected bank |
|---|---|
| `0` | Fixed address `0x3CC00000` |
| `1` | First captured bank: the first register-base global value |
| `2` | Second captured bank: the second global value plus `0x4000` |
| `3` through `255` | Fallback captured bank: the third global value plus `0x8000` |

The equality comparisons produce this mapping regardless of whether the selector byte is displayed as signed or unsigned.

The selector is not fixed for an invocation, a polling cycle, or a transmission batch. A changed selector can redirect a later access without changing any captured bank address.

### Status polling

For a nonzero remaining count, the function selects a bank and reads its 32-bit status value at offset `0x18`.

The decision uses mask `0x000002F0`, covering bits 4, 5, 6, 7, and 9:

- If every masked bit is clear, the function transmits a batch.
- If any masked bit is set, the function takes the busy path.

Bits outside the mask do not affect this branch.

“Ready” and “busy” are descriptive branch names. The individual bits’ hardware meanings are not established.

### Ready path: byte transfer

A ready status permits a batch equal to the smaller of the unsigned remaining count and 16.

The entire batch size is subtracted from the remaining count **before** the batch’s source reads and output writes.

For each byte, in increasing source-address order:

1. Read the selector byte again and select the destination bank.
2. Read one unsigned source byte.
3. Write that byte’s numeric value as a 32-bit value to the selected bank at offset `0x20`.
4. Advance the internal source position by one byte.

Each output value is between 0 and 255; its upper 24 bits are zero. Source accesses are byte-wide. Destination accesses are 32-bit.

There is no status read between writes within the batch. Consequently:

- A single clear status sample permits up to 16 writes.
- A subsequent status change does not interrupt the batch through any visible check.
- Different bytes in one batch can target different banks.
- A write can target a different bank from the one whose status permitted the batch.

The function does not verify that the device accepted a write.

### Post-transmission scheduling

After the complete batch, the remaining count is interpreted as signed 32-bit and compared with one.

If that signed value is less than one, the function returns directly to the completion check without invoking the scheduling pair. This includes:

- Zero.
- Every unsigned value from `0x80000000` through `0xFFFFFFFF`.

A high-bit-set remaining count therefore skips this scheduling pair but does not terminate the transfer.

If the signed remaining count is at least one, the function:

1. Reads the pacing global.
2. Forms a 32-bit argument from that value plus 16 times the retained arithmetic value.
3. Calls F-d7be9cfb4000 with the formed argument and `1000`.
4. Calls F-opaque-03 with first argument zero and second argument equal to the complete 32-bit result of F-d7be9cfb4000.
5. Rereads the selector and status for the next iteration.

The pacing global is read anew on each qualifying post-transmission step. It is not cached at entry.

### Busy path

When any masked status bit is set:

- No source byte is read.
- No output write occurs.
- The remaining count and source position are unchanged.
- The pacing global is not visibly read.

The function calls F-d7be9cfb4000 with the retained arithmetic value plus `999`, and second argument `1000`. It then calls F-opaque-03 with zero and the complete 32-bit helper result.

After those calls return, it rereads the selector and status. A busy result can therefore be followed by polling a different bank.

If every status check remains busy and dependencies keep returning, this cycle can continue indefinitely.

### Integer boundaries

The remaining count and batch subtraction are unsigned 32-bit. The batch size never exceeds the remaining count, so that subtraction does not underflow.

The signed post-batch comparison is distinct from a nonzero test:

- Starting at `0x80000010`, one 16-byte batch leaves `0x80000000`; post-transmission scheduling is skipped.
- Starting at `0x80000000`, one 16-byte batch leaves `0x7FFFFFF0`; post-transmission scheduling occurs.

The retained arithmetic value is unsigned 32-bit. Its multiplication by 16 and its addition of `999` use 32-bit unsigned arithmetic, retaining the low 32 bits. The scheduling argument is then held in a signed 32-bit representation. Exact out-of-range unsigned-to-signed conversion semantics and dependency interpretation of that argument are **documented_only**.

Address additions must not be treated as unbounded mathematical arithmetic.

## Side effects

### Directly established accesses and calls

The function performs:

- One initial arithmetic-field read.
- Separate entry-argument and exit-argument reads.
- An entry call before bank initialization.
- Three ordered reads of the register-base global, each contributing to a separately retained bank.
- Repeated selector and 32-bit status reads.
- Sequential source-byte reads and 32-bit output writes on ready paths.
- Conditional pacing-global reads.
- Conditional F-d7be9cfb4000 and F-opaque-03 calls.
- An exit call on normal completion.

It does not visibly write the context, globals, or source as ordinary storage. Output-register aliasing could nevertheless make a write affect those regions; no non-aliasing guarantee is supplied.

The remaining count and advancing source position are internal state, not caller-visible output fields.

### Synchronization and failures

F-opaque-01 and F-opaque-02 bracket processing on the normal-return path. Their placement does not establish locking, interrupt masking, ownership acquisition, or a matched acquire/release protocol.

No dependency result is tested for failure. There is no explicit recovery or cleanup path for invalid memory accesses, nonreturning dependencies, interrupted execution, or partial device acceptance.

The representation establishes an access order, not a complete hardware memory model. Atomicity, barriers, bus behavior, and compiler treatment of concurrent changes are not independently established.

## Acceptance examples

These are conditional static acceptance examples, **not executed tests**. Unless specified otherwise, accesses are valid, relevant arithmetic is defined, dependencies return, and no unmentioned changes occur.

### Zero count still initializes all banks

Given a byte count of zero:

- The arithmetic field is read and the retained value calculated.
- F-opaque-01 receives the first read of the context argument.
- The register-base global is read three times in order, forming the three independent captured banks.
- F-opaque-02 receives a fresh context-argument read.
- The function returns zero.

There are no selector, status, source-byte, output-register, pacing-global, or scheduling-pair accesses. The source address is not dereferenced.

### One ready byte

Given count one, selector zero throughout, a clear masked status, and source byte `0xE7`:

- Status is read at `0x3CC00018`.
- The selector is reread before the output.
- A 32-bit value of `0x000000E7` is written at `0x3CC00020`.
- No post-transmission scheduling pair occurs.
- The exit call precedes the zero return.

### Seventeen ready bytes

Given count 17 and clear masked status on both checks:

- The first check permits 16 ordered writes.
- The remaining count becomes one.
- The pacing global is read, followed by F-d7be9cfb4000 and F-opaque-03.
- A new selector and status read precede the last byte.
- The final byte is followed by the exit path without another scheduling pair.

### Busy, then ready

Given count one, an initially busy status, and a later ready status:

- The busy iteration consumes no source byte and performs no output write.
- F-d7be9cfb4000 receives the retained arithmetic value plus `999`, and `1000`.
- Its complete result is passed to F-opaque-03.
- The selector and status are reread before transmission.

### Different values during bank initialization

Suppose the ordered register-base global reads return `0x10000000`, `0x20000000`, and `0x30000000`.

The captured banks are respectively:

- Selector one: `0x10000000`.
- Selector two: `0x20004000`.
- Other nonzero selectors: `0x30008000`.

A later global change does not cause this function to reload those banks. They are not required to be offsets from one common captured value.

### Selector changes after status

Given a ready status with selector one, followed by selector two before an output write:

- The status access uses the first captured bank plus `0x18`.
- The output uses the second captured bank plus `0x20`.

There is no unconditional `0x4000` relationship between these captured banks. That relationship holds only if the relevant initialization reads observed the same global value.

### High-bit remaining count

Given count `0x80000010` and a ready first status:

- Sixteen bytes are written.
- The remaining count becomes `0x80000000`.
- The scheduling pair is skipped.
- The completion check finds a nonzero count.
- Polling continues.

### Entry changes shared state

If F-opaque-01 changes the register-base global and the new value remains stable through all three subsequent reads, all captured banks use that new value with their respective offsets.

If the global changes between those reads, each bank uses its own observed value.

A change by F-opaque-01 to the arithmetic context field does not recompute the already retained arithmetic value. A change to the context field at `0x04` can affect the later exit argument.

## Uncertainties

The following remain **documented_only**:

- Signed overflow in the initial multiplication.
- Target-specific unsigned-to-signed conversion and address-overflow behavior.
- Device identity, status-bit meanings, output capacity, and safety of 16-write batches.
- Whether the scheduling dependencies implement delay or pacing, and in what units.
- Actual global values and whether they remain stable across the three initialization reads.
- Dependency side effects, ownership effects, failure conventions, and termination.
- Atomicity, volatility, synchronization, and visibility of concurrent changes.
- Fault behavior for invalid or unsupported accesses.
- Effects of overlap among source, context, globals, and register regions.
- Whether written values are accepted or transmitted by hardware.

These unknowns do not justify assuming one underlying global read, stable selectors, preserved shared state, guaranteed device receipt, or eventual completion.
