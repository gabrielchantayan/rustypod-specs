# F-226d97c76fa5

## Purpose

F-226d97c76fa5 conditionally changes a 32-bit selection value in a caller-supplied object and reconciles an associated pointer with the result of dependency F-84fa32dd6ef0.

Two comparisons govern its behavior:

- If the requested selection equals the selection already stored in the object, the function returns without resolving or inspecting the associated pointer.
- Otherwise, it stores the requested selection, resolves a candidate pointer, and compares that candidate with the associated pointer read **after** resolution. Only unequal pointers trigger replacement. A non-null displaced pointer additionally triggers an indirect callback before replacement.

The established behavior is a selection update followed by conditional pointer replacement. Interpreting the selection as a resource identifier, the pointer as an owned resource, or the callback as a release operation is inferred intent, not an established ownership contract.

## Behavior

### Selection comparison and early return

The first direct object access is a read of the 32-bit selection at offset `0x5c`.

If its value equals the requested selection, the function returns immediately. On this path, it performs no direct writes, does not call F-84fa32dd6ef0, does not read the associated-pointer field, and does not invoke the indirect callback.

This is a selection-based short circuit, not a consistency check. Even if the associated pointer is null, stale, or inconsistent with the selection, equal selections do not cause reconciliation.

### Selection publication before resolution

If the selections differ, the function writes the requested 32-bit value to offset `0x5c` before calling any dependency.

It then invokes F-84fa32dd6ef0 with:

1. The requested selection.
2. An integer zero.

The first argument is the incoming request, not a fresh read of the selection field. The result is treated as a candidate pointer.

The selection write is therefore visible to dependency execution before pointer replacement has occurred. There is no direct rollback operation. If resolution does not return normally, the function does not reach its subsequent pointer handling; effects already performed remain subject to whatever behavior caused that interruption.

### Associated-pointer comparison after resolution

After F-84fa32dd6ef0 returns, the function reads the associated pointer from offset `0x3c`.

This ordering is significant. The pointer compared with the candidate is the value present **after** resolution, not a value captured at function entry. If resolution changes the associated-pointer field, that changed value participates in the comparison.

If the two pointers are equal, the function returns without:

- Invoking the indirect callback.
- Writing the associated-pointer field.

This applies both when the pointers are non-null and when both are null.

The selection field is not read again. Any modification of that field by F-84fa32dd6ef0 is not directly corrected by this function.

### Replacement of an unequal pointer

If the candidate and the associated pointer differ, the function examines whether the associated pointer read after resolution is null.

If it is null, no callback is invoked. The candidate is written directly to offset `0x3c`, and the function returns.

If it is non-null, the function:

- Reads a dispatch-structure address through the displaced pointer.
- Obtains the callback address at byte offset `+4` within that structure.
- Invokes that callback.
- After normal callback return, writes the previously resolved candidate to offset `0x3c`.
- Returns.

The old pointer therefore remains in the associated-pointer field when the callback is entered, unless another actor has changed the field. The replacement write occurs only after the callback returns normally.

The function does not re-read the associated-pointer field or repeat the pointer comparison after the callback. A callback-side change to that field is consequently overwritten by the final candidate store, provided execution reaches it.

The callback’s return value, if any, is not used to decide whether to store the candidate.

### Widths and arithmetic

The selection comparison and selection store operate on the represented 32-bit integer values. No range check, normalization, narrowing operation, increment, or other arithmetic is performed on the requested selection.

Negative values, zero, and positive values receive the same local control-flow treatment: equality determines the initial branch, and an unequal request is passed unchanged to F-84fa32dd6ef0. Whether particular values are valid inputs to that dependency is unknown.

Pointer handling consists of equality comparison, a null check, fixed-offset field accesses, and dispatch lookup. There is no evidenced size calculation, index multiplication, or allocation-size arithmetic.

The fixed offsets describe byte positions. The evidence does not establish safe behavior when address calculations exceed valid object storage or encounter an invalid address.

## Side effects

### Direct memory effects

The function can perform these direct writes:

- A selection-field write whenever the initial selection differs from the request.
- An associated-pointer write whenever the candidate differs from the pointer read after resolution, provided any required callback returns normally.

It makes no direct write on the equal-selection path.

No other direct object-field writes, allocations, or deallocations are shown.

### Dependency effects and intermediate states

Neither dependency is established to be pure. Both may have effects not described by this function’s direct accesses.

The function exposes an intermediate state in which the requested selection has been stored but the associated pointer has not yet been reconciled. During the displaced-pointer callback, the final candidate has still not been installed by this function.

There is no evidenced locking, atomic transaction, rollback, exception handling, or reentrancy guard. Accordingly, the sequence must not be described as an atomic change of a selection-and-pointer pair.

### Ownership

The candidate is stored without an explicit retain, duplication, or ownership-acquisition operation.

The displaced pointer receives a callback when non-null and unequal to the candidate. Although that pattern is consistent with releasing a previous resource, the callback’s actual operation is unknown. It must not be specified as destruction, deallocation, reference-count decrement, or ownership transfer without additional evidence.

Pointer equality suppresses that callback. This establishes a local behavioral rule, not a complete lifetime policy.

If a dependency invalidates the object, the candidate, or required dispatch storage, safe continuation is not established.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless stated otherwise, dependencies return normally and do not alter relevant fields.

### Equal selections avoid all reconciliation

Given a stored selection of `7` and a request of `7`, the function reads the selection and returns.

F-84fa32dd6ef0 is not called, the associated-pointer field is not read, and no callback or direct write occurs. This remains the expected behavior even if that pointer is null or inconsistent with selection `7`.

### Different selections with the same resolved pointer

The selection becomes `8` before resolution. The associated pointer is read after resolution. No callback or associated-pointer store follows.

### Replacement from null

Given a differing request and a null associated pointer, suppose resolution returns non-null pointer Q.

The selection is written, resolution occurs, null is read from the pointer field, and Q is stored. No indirect callback is invoked.

### Replacement by null

Given a differing request and associated pointer P, where P is non-null, suppose resolution returns null.

The callback obtained through P is invoked before the associated-pointer field is set to null. Null is accepted as a candidate; the function does not emit an explicit error for it.

### Both pointers null

Given a differing request, suppose resolution returns null and the associated-pointer field is null when subsequently read.

The selection has been written, but there is no callback and no associated-pointer write.

### Resolution changes the associated pointer

Suppose the pointer field initially contains P, but F-84fa32dd6ef0 changes it to R and returns Q.

The comparison is between R and Q. If they differ and R is non-null, the callback is selected through R, not P.

### Callback changes the associated pointer

Suppose the displaced-pointer callback writes R into the object’s associated-pointer field and then returns normally.

The function subsequently overwrites R with the previously resolved candidate. It performs no post-callback comparison.

### Resolution changes the selection

Suppose the request is `8`, but resolution changes the selection field to `9`.

The function does not restore `8`. Its initial write is established; a final selection of `8` is conditional on dependencies not changing it.
