# F-4e4f097b74bf

## Purpose

F-4e4f097b74bf conditionally modifies a destination word array using a source word array. Its observable outcomes are an unchanged return, a descending copy, an ascending carry-propagating combination, or an ascending subtraction-like combination followed by optional reversal and removal of high zero words from the reported extent.

**Inferred intent:** in-place signed multiple-precision addition, with a signed length header and least-significant payload word first.

**Established limitation:** that interpretation depends on configuration values, compatible payload encodings, valid counts, and the behavior of F-a6b5d842289c. These are not supplied. The unconditional contract is therefore about word-array transformations, not mathematical signed addition.

## Interface

### Arguments and layout

The first argument identifies the **source** array. The second identifies the **destination** array.

Each array consists of 32-bit words:

| Position | Role |
|---|---|
| 0 | Header, interpreted as signed where used for comparisons or count derivation |
| 1 onward | Payload words, processed from lower positions toward higher positions during arithmetic |

The copy path instead processes payload positions in descending order.

The supplied representation uses 32-bit pointer components when constructing the result. It does not establish alignment requirements, byte order, or a portable interface for wider pointers.

There is no capacity argument, explicit error channel, or allocation descriptor.

## Behavior

### Word arithmetic and count interpretation

Payload products, stored results, carry inputs, and packed return components have 32-bit widths. Payload multiplication and addition retain the low 32 bits. Carries are determined using unsigned 32-bit operands.

Header-derived products are tested as signed values. Counts are obtained by multiplying a header by the relevant count factor and conditionally negating a negative result.

This does not provide a valid nonnegative count for the most-negative signed 32-bit value. Nor does the supplied representation independently establish a portable signed-overflow policy. Normal-operation claims below require well-defined count derivation and bounded indexing.

For the arithmetic descriptions, an **incoming borrow** is either zero or one. The subtraction path internally maintains its complementary meaning: one means no incoming borrow, and zero means an incoming borrow. This state remains binary under coherent word reads.

The descriptions of a position’s decoded operands assume that repeated reads contributing to that position observe consistent values. No synchronization or atomic snapshot guarantee is established for concurrent mutation.

### Shortcut decisions

The first decision tests whether the source header multiplied by the gate factor is zero.

If so, the visible body returns immediately:

- No destination header or payload is inspected.
- No destination storage is written.
- F-a6b5d842289c is not called.
- The result contains the source pointer above the destination pointer.

This is a product test, not necessarily a test for a zero source header. An unknown factor or word-width multiplication can make the product zero for a nonzero header.

Otherwise, the destination header multiplied by the gate factor is tested.

If that product is zero and the pointers are identical, the function returns the destination pointer in the upper component and zero in the lower component. No write or dependency call occurs.

If that product is zero and the pointers differ, the function performs a copy:

- It reads the source header again and writes that value to the destination header.
- It derives the copy count from that saved header and the copy-count factor.
- It copies payload positions from the count down through position 1.
- It returns the destination pointer above an all-one lower component.

A zero copy count results in a header-only write. Destination storage outside the copied range is not cleared.

The header write precedes payload copying. Distinct pointers do not establish disjoint storage; partial overlap can therefore affect the values subsequently read.

### Arithmetic selection and dependency boundary

When neither shortcut applies, a signed product involving the destination header, two references to the gate factor, and the source header selects the arithmetic path:

- A nonnegative tested result selects addition.
- A negative tested result selects subtraction.

This is equivalent to a same-sign/opposite-sign decision only under additional restrictions on factor values and overflow.

On either arithmetic path, the destination and source counts are computed before calling F-a6b5d842289c. The dependency receives the destination pointer and returns a 32-bit value retained for final header construction.

Those pre-call counts remain the selected extents even if the dependency changes headers, payloads, or count factors. Subsequent payload processing acts on storage after the call. The caller does not visibly restore the earlier contents or configuration.

### Addition

Addition starts with zero carry and processes payload positions in ascending order.

Within the shared extent, each destination and source word is transformed by multiplication with the addition decode factor. The two resulting 32-bit words and the incoming carry are added. The low word is multiplied by the retained addition encode factor and written to the destination. Unsigned overflow supplies the carry for the next position.

After the shared extent:

- If the destination is longer, its remaining decoded words are combined with the carry and rewritten.
- If the source is longer, its remaining decoded words are combined with the carry and written into corresponding destination positions.

A destination word outside its original extent need not be read merely because the source is longer.

If carry remains after the longer input is exhausted, one additional payload position is written with the encoded carry. The output count includes that position.

Finally, the destination header is written as the low 32 bits of the product of:

- The addition-header factor referenced for header construction.
- The output count.
- The retained dependency result.

Addition does not trim high zero words. The count therefore remains the larger selected input count, increased by one if a carry word was appended.

The addition encode factor is retained once after the dependency call. In contrast, the decode factor is referenced throughout processing; no single whole-loop sample is established.

### Subtraction

Subtraction processes the larger selected input extent in ascending order. Its initial arithmetic state means no incoming borrow.

Within the shared extent, each operand is decoded by multiplication with the subtraction decode factor. The stored low word represents the decoded destination minus the decoded source minus any incoming borrow, multiplied by the subtraction encode factor. The next state records whether that unsigned subtraction required a borrow.

Within a destination-only tail, the same operation uses zero for the absent source word. Within a source-only tail, it uses zero for the absent destination word.

These descriptions concern the decoded words encountered by the operation. They do not establish subtraction of the original arrays’ mathematical values when decoding and encoding are incompatible.

#### Reversal

If the final state indicates an outstanding borrow, the function revisits the entire processed destination extent in ascending order.

It decodes the already-written destination words and performs a wordwise complement with a carried one across the extent, encoding each replacement word. This is a fixed-width two’s-complement-style reversal of the decoded intermediate payload.

The retained dependency result is then negated.

Calling this a reversal of mathematical magnitude additionally requires compatible decode and encode factors. Without that condition, it remains a second transformation of the stored intermediate words.

Neither the subtraction decode factor nor its encode factor is established as a whole-pass retained sample.

#### Trimming and final header

After any reversal, destination positions are inspected from the highest processed position downward. A position is treated as zero when multiplication of its stored word by the subtraction decode factor produces a zero word.

The retained count is the highest position that fails this test, or zero if all processed positions pass. Inspection stops at the first retained word.

This is decoded-zero detection, not necessarily raw-word zero detection. It changes the reported extent but does not erase discarded storage.

The final destination header is the low 32 bits of the product of:

- The subtraction-header factor.
- The retained dependency result, negated if reversal occurred.
- The trimmed count.

The return’s upper component remains the smaller pre-call input count. It is not replaced by the trimmed output count.

These statements do not constrain F-a6b5d842289c. Its effects are unresolved.

Established ordering relevant to callers includes:

- Copying writes the destination header before reading the copied payload positions.
- Arithmetic count derivation precedes the dependency call.
- Arithmetic payload writes follow the dependency call.
- Each arithmetic position consumes its required operands before replacing that destination position.

No explicit failure status or rollback exists. If an access or arithmetic precondition fails, the supplied body establishes no recovery behavior and no guarantee against partial mutation.

## Acceptance examples

These are conditional static examples, not executed tests. Arithmetic examples assume sufficient capacity, valid counts, nonoverlapping arrays, stable relevant reads, unit configuration factors, and a dependency that returns one without changing memory or configuration, unless stated otherwise.

### Initial shortcut

If the initial source-header/gate product is zero, the visible body makes no destination access and returns the packed pointer pair. A destination that would not support a header read does not, by itself, invalidate this selected path.

### Header-only copy

Suppose the initial product is nonzero, the destination product is zero, the pointers differ, and the copy-count factor is zero.

The destination header becomes the reread source header. No payload position is copied. The result has the destination pointer above an all-one lower component.

### Addition extending the payload

A source with header 1 and payload \([1]\), combined with a destination with header 1 and payload \([2^{32}-1]\), selects addition under the stated assumptions.

The destination becomes header 2 with payload \([0,1]\). The return components are upper 1 and lower 2. Capacity for the extra payload word is required.

### Subtraction without reversal

A source with header −1 and payload \([3]\), combined with a destination with header 1 and payload \([5]\), selects subtraction.

The destination becomes header 1 with payload \([2]\). Both return components are 1.

### Subtraction with reversal

Changing those payloads to source \([5]\) and destination \([3]\) produces destination payload \([2]\) and header −1.

The upper return component is 1. The lower component is the 32-bit representation of −1.

### Cancellation and reported extent

A source with header −2 and payload \([7,1]\), combined with a destination with header 2 and the same payload, produces header zero after subtraction and trimming.

Both processed payload words become zero. Storage beyond them is not cleared. The return’s upper component is 2 and its lower component is zero.

### Decoded-zero trimming

If trimming encounters a stored word of \(2^{31}\) while the subtraction decode factor is 2, that word’s 32-bit product is zero. It is therefore discarded from the reported extent despite its nonzero stored bits.

This example concerns the trimming decision; it does not assert how that intermediate payload was produced.

### Dependency changes

If F-a6b5d842289c changes a header after the counts have been derived, processing still uses the retained counts. If it changes payload or configuration consumed afterward, subsequent arithmetic uses that post-call state rather than an assumed original snapshot.
