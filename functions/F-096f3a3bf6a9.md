# F-096f3a3bf6a9

## Purpose

F-096f3a3bf6a9 conditionally removes a selected node from a pointer-linked structure, performs color-dependent structural repair, calls a node-disposition dependency, decrements a container count, and writes a 32-bit result to caller-provided storage.

A tree with a header, cached extrema, and red-black-like colors is the inferred abstraction. The established behavior is the specific link manipulation and repair described below, not a guarantee of conventional red-black deletion. In particular, deletion of a leaf uses its former parent as the repair position; relocation of a successor without a right child uses the successor itself.

The result is read from a temporary position word at the final output store. Dependencies receive that word’s address and can potentially modify it during later calls. Its value is not necessarily fixed when the initial position-processing call returns.

| Selection address | Address of a 32-bit word, read initially and read again on the removal path to obtain the selected node. |

Pointers and pointer-bearing fields in the supplied representation are 32 bits wide. They must not be silently replaced with wider native-pointer fields when interpreting the layout.

### Preconditions

Every executed access requires accessible storage of the corresponding width. Traversed links must be valid, and traversals must terminate. On the removal path, the selected node must have the structural relationships needed by the executed branches.

There is no direct validation of membership, count, color range, cached extrema, parent-child consistency, or acyclicity.

Two initialized 32-bit temporary words are exposed by address to dependencies. Their storage remains live through the final result read. Retaining an address for use during a later dependency call is not, by itself, storage invalidation. Use after this routine returns would require a separate lifetime contract.

## Behavior

### 1. Initial decision and result preparation

The routine performs these initial operations in order:

1. Reads the selection word into a temporary position word.
2. Reads the container’s header pointer into a second temporary word.
3. Calls F-eac694802fc1 with the addresses of both temporary words.

The second temporary is a copy of the header pointer, not an alias for the container’s header field.

If F-eac694802fc1 returns nonzero, the routine rereads the container’s header pointer, assigns that value to the temporary position word, and proceeds to the final output store. This path performs no direct structural modification, disposition call, or count decrement. Effects of F-eac694802fc1 remain possible.

If F-eac694802fc1 returns zero, the routine calls F-357c4c54c6ea with the temporary position word’s address. It then rereads the original selection word to obtain the selected node.

On this removal path, the routine makes **no further direct assignments** to the temporary position word. It nevertheless does not capture or freeze that word’s value after F-357c4c54c6ea. Either initial dependency can retain its address, and later dependency effects can modify the still-live word. The final output is whatever value is present when the routine reads it for the final output store.

For example, F-357c4c54c6ea can write value A, and F-6c0157fd1d46 can later write value B through a retained address. The final output is then B, provided nothing changes the word again before its final read.

The selected node is obtained independently from the reread selection storage. Changes to that storage by either initial dependency can therefore change the removal target.

### 2. Structural removal

The **selected node** is the node obtained from that reread. It remains the disposition target in every structural branch, including when a successor takes its position.

The routine inspects its left and right links to distinguish the following cases.

#### No children

The selected node’s parent becomes the repair position.

If the parent equals the current container header, the routine writes, in order:

1. Header maximum link: the header address.
2. Header minimum link: the header address.
3. Header root link: zero.

Otherwise, the routine compares the parent’s left link with the selected node.

- On equality, it clears the parent’s left-link field using four individual byte writes in increasing address order. It then changes the header’s cached minimum to the parent only if that cache equals the selected node.
- Otherwise, it clears the parent’s right-link field using four individual byte writes in increasing address order. It then changes the header’s cached maximum to the parent only if that cache equals the selected node.

The alternative branch does not separately verify that the parent’s right link identifies the selected node.

These byte writes are distinct from the ordinary 32-bit link stores elsewhere. Their granularity and order can matter to instrumented memory or observers of intermediate state.

#### Exactly one child

The sole child becomes both the replacement and the repair position.

First, the routine copies the selected node’s parent link into the child’s parent field. It then replaces the selected node in the header’s root link if the current root equals the selected node. Otherwise, it updates the parent’s left link when that link equals the selected node, and the parent’s right link otherwise.

Cached extrema are handled afterward:

- If the selected node is the cached minimum, the new minimum is its parent when it has no right child. Otherwise, the routine follows left links from the replacement child until reaching the leftmost node.
- If the selected node is the cached maximum, the new maximum is its parent when it has no left child. Otherwise, the routine follows right links from the replacement child until reaching the rightmost node.

Only matching caches are rewritten.

#### Two children

The routine follows left links from the selected node’s right child to find the **successor**. The successor’s right child, possibly zero, is the replacement for its old location.

Structural writes occur in this order:

1. The selected node’s left child receives the successor as parent.
2. The successor receives the selected node’s left link.
3. The successor’s old location is handled:
   - If it is the selected node’s immediate right child, its nonzero right child receives the successor as parent.
   - Otherwise, its nonzero right child receives the successor’s former parent; that former parent’s left link receives the right child; the successor receives the selected node’s right link; and that right subtree receives the successor as parent.
4. The header root link, or the appropriate selected-node parent link, receives the successor.
5. The successor receives the selected node’s parent link.
6. The successor’s original color is saved, the successor receives the selected node’s color, and the selected node receives the saved color.

The root-link comparison and parent-side selection follow the same pattern as the one-child case. No payload exchange occurs.

The repair position is the successor’s original right child if nonzero. Otherwise, it is the relocated successor itself.

This branch makes no direct cached-minimum or cached-maximum update.

### 3. Color-dependent repair

After structural removal, the routine rereads the container header.

Repair is skipped when the repair position equals that header. In that case, the disposition target’s color need not be read for the repair gate. Otherwise, repair is skipped if the disposition target’s color is zero. Any nonzero target color passes this gate.

At the start of each repair iteration:

- If the repair position equals the current root, repair finishes without needing its color for this decision.
- Otherwise, its color is read. Any value other than 1 finishes repair.

Finishing an entered repair writes color 1 to the current repair position. Skipping repair at the initial gate does not perform this finishing write.

For an active iteration, the routine reads the repair position’s parent and checks whether the position is that parent’s left child. The opposite child is the sibling. A nonmatching left link selects the right-side case without separate membership validation.

#### Missing sibling

If the sibling is zero, the routine writes color 0 to the current repair position, moves the repair position to its parent, and repeats.

#### Sibling color is zero

The routine writes color 1 to the sibling and color 0 to the parent. It then calls:

- F-4b53288e056a for a left-side repair position.
- F-63a2b3ccf83b for a right-side repair position.

These calls expose the container and an explicit parent operand.

After the call, it rereads the repair position’s parent and the sibling on the same side. If the sibling is now zero, it takes the missing-sibling behavior using the reread parent.

#### Both sibling children are black-like

For these child tests, “black-like” means either zero or a node whose color is exactly 1.

The child nearer the repair position is inspected first. When that child is black-like, the far child is inspected to determine whether both are black-like.

If both are black-like, the sibling receives color 0 and the repair position moves to its parent. Unlike the missing-sibling branch, this branch does not first recolor the current repair position.

#### At least one sibling child is not black-like

If the far child is black-like, the routine:

1. Writes color 1 to the near child if present.
2. Writes color 0 to the sibling.
3. Calls F-63a2b3ccf83b for a left-side repair position, or F-4b53288e056a for a right-side repair position.
4. Rereads the sibling through the repair position’s current parent.

The supplied rendering exposes only the container operand for these preliminary calls. A particular additional argument must not be assumed.

If the reread sibling is zero, repair finishes, including its finishing color write.

Otherwise, whether or not a preliminary call was needed, the routine:

1. Copies the parent’s current color into the sibling.
2. Writes color 1 to the parent.
3. Writes color 1 to the far child if present.
4. Calls F-4b53288e056a for a left-side repair position, or F-63a2b3ccf83b for a right-side repair position, with the container and an explicit parent operand.
5. Finishes repair.

The dependencies are not assumed to implement rotations or preserve globals. Subsequent reads use state present after their calls.

### 4. Disposition, count, and final output

After structural work and any repair, the routine calls F-6c0157fd1d46 with the container, selected node, and additional value 1.

Only after that call returns does it read the 32-bit count, subtract one, and write the result back. Thus, any disposition-induced count change precedes the decrement.

There is no zero-count guard. Under 32-bit wrapping arithmetic, zero becomes 4,294,967,295. The exact source-language signed-overflow model is not established.

Finally, the routine reads the temporary position word and writes that 32-bit value to the output address. This read occurs after disposition and the count write, not immediately after position processing. Later dependency modifications through a retained temporary address therefore affect the result without requiring storage invalidation.

## Side effects

Direct effects include link rewrites, color writes, possible extremum-cache updates, a count decrement, and the final output overwrite. Intermediate structural states exist before repair and disposition complete.

No direct allocation, payload destruction, or storage release is established. F-6c0157fd1d46 may perform such operations, but its ownership contract is unknown.

Dependencies can retain exposed addresses and cause later effects while those addresses remain valid. Nothing establishes that they preserve the temporary position, container fields, node fields, or other global state.

There is no direct error result, rollback, locking, or recovery path. Invalid accesses can occur after earlier writes; cyclic traversals can fail to terminate. Dependency failure or nonlocal control transfer can prevent subsequent operations.

Output aliasing is not rejected. The final output write can overwrite a container or node field if the caller supplies an overlapping destination. Selection storage may also overlap other accessible state. Such overlap does not establish safe container semantics; effects follow executed accesses and their order.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Nonzero initial decision.** If F-eac694802fc1 returns nonzero, the output equals the container header pointer reread after that call. No other dependency is called, and no direct count decrement occurs.

2. **Only node removed.** Given a childless selected node whose parent is the header, with relevant state preserved by dependencies, the header maximum and minimum become the header, then the root becomes zero. Repair is skipped. Disposition receives the selected node and 1.

3. **Non-root left leaf.** Given a childless selected node matching its parent’s left link, that field is cleared by four increasing-address byte writes. The minimum cache changes to the parent only if it matched the selected node. Repair starts at the parent.

4. **One-child root replacement.** Given a selected root with one child, the child receives the header as parent before becoming the root. The selected node, not the replacement child, remains the disposition target.

5. **Deep successor relocation.** Given two children and a successor below the immediate right child, the successor’s former parent receives its right child as a left child. The successor occupies the selected node’s former position; payload bytes are not directly exchanged.

6. **Successor without a right child.** The relocated successor is the repair position. Substituting an implicit null repair node would not match the established behavior.

7. **Disposition changes the count.** If disposition returns with count 12, the subsequent count write is 11, regardless of its earlier value.

8. **Stable transformed position.** If the initial decision is zero and F-357c4c54c6ea writes value A to the temporary position, the output is A only provided normal completion occurs and no later effect modifies that temporary before its final read.

9. **Later retained-address modification.** If either initial dependency retains the temporary position address, F-357c4c54c6ea leaves A there, and disposition later writes B through the retained address, the output is B provided no intervening effect changes it again. The temporary storage can remain valid throughout.
