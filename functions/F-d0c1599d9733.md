# F-d0c1599d9733

## Purpose

F-d0c1599d9733 updates a destination descriptor from a distinct source descriptor and returns the destination descriptor’s address. Exact descriptor identity causes an immediate return without helper calls or descriptor accesses.

The established behavior combines range-processing calls, optional allocation, processing of an old destination range, and updates to descriptor fields. The apparent intent is assignment of a sequence whose elements occupy 40 bytes each. That interpretation depends on helper semantics not supplied here.

A significant observable detail is that the destination’s third field does not always retain its previous value. On the non-growing, storage-reuse path, it is overwritten with the new logical end. On the growing, storage-reuse path, this function does not explicitly write the third field. A behavioral contract must preserve that distinction rather than normalize both paths to conventional container assignment.

## Interface

The function accepts four arguments:

| Argument | Established role |
|---|---|
| Destination descriptor address | Returned unchanged as an address; selected fields are read and written on non-identity paths. |
| Source descriptor address | Compared with the destination address and used for helper queries and source-range endpoints. |
| First auxiliary unsigned value | Copied into temporary storage on non-identity entry, but overwritten before it can affect subsequent behavior. |
| Second auxiliary unsigned value | Likewise has no established effect on calls, writes, or the return value. |

The auxiliary arguments are 32-bit unsigned values. No validation or behavioral interpretation of them is established.

The descriptor is accessed as at least three consecutive 32-bit words:

| Byte offset | Access and apparent interpretation |
|---|---|
| 0 | Read as a storage address; explicitly replaced on the allocation path. |
| 4 | Read as a range end; explicitly updated on all completed non-identity paths. |
| 8 | Explicitly updated on the allocation path and the non-growing reuse path. Apparently a storage-limit address. |

These meanings are inferred from usage, not established declarations of a public container type. The supplied representation uses 32-bit words for stored addresses and address arithmetic. It does not establish portability to a different pointer width, byte order, or ABI.

The return value is the original destination descriptor address on every explicit return. No separate success indicator is returned.

For non-identity operation, the descriptors and any ranges accessed through them must satisfy the requirements of the invoked helpers. This function supplies no null checks, descriptor-consistency checks, overlap checks, or arithmetic-overflow checks.

## Behavior

### Identity handling

The first operation compares the two descriptor addresses.

If they are equal:

- Return the destination address immediately.
- Do not call any dependency.
- Do not read or write descriptor fields.
- Do not use either auxiliary argument.

This is descriptor-address identity, not equality of the descriptors’ contents or underlying storage.

### Initial path selection

For distinct descriptors, the function performs these queries in order:

1. Call F-8be3a5940f42 with the source descriptor.
2. Call F-bed5d5d6f858 with the destination descriptor.
3. Compare the second result against the first as unsigned 32-bit quantities.

If the destination-query result is smaller, take the allocation path. Otherwise, take the storage-reuse path.

F-8be3a5940f42 appears to report an element count. F-bed5d5d6f858 appears to report a capacity-like count. Their actual contracts are not supplied. Repeated queries are observable calls, and their results are not assumed stable.

### Allocation path

The allocation path first makes fresh count-like queries:

1. Call F-8be3a5940f42 with the source descriptor.
2. Call F-8be3a5940f42 with the destination descriptor.

Let the latter result be the destination count used for growth calculation. Compute two unsigned 32-bit candidates:

- The destination count plus 32.
- The destination count plus its unsigned right shift by one, plus its unsigned right shift by three.

Choose the larger candidate using an unsigned comparison. Then choose the larger of that candidate and the freshly queried source count.

All additions in this calculation are 32-bit unsigned arithmetic. They wrap rather than implementing an unbounded mathematical growth formula. In the absence of wraparound, the second candidate approximates 1.625 times the destination count, with each fractional contribution truncated separately.

The selected count is retained for the eventual storage-limit calculation. The function then proceeds in this order:

1. Multiply the selected count by 40 and call F-871e64ddc6de with that size and a second argument of zero.
2. Retain the returned 32-bit value as the new storage address.
3. Call F-82bab15a2c1c with the source’s then-current first and second fields, the new storage address, and the destination descriptor address.
4. Call F-f4ccd33a6308 with the destination descriptor address and its then-current first and second fields.
5. Read and retain the destination’s first field.
6. Call F-bed5d5d6f858 with the destination descriptor.
7. Call F-ff1bdc376dcd with the retained first-field value, the result of that query, and zero.
8. Write the retained new storage address to destination offset 0.
9. Call F-8be3a5940f42 with the source descriptor again.
10. Write destination offset 4 as its then-current first field plus 40 times this latest source-query result.
11. Write destination offset 8 as its then-current first field plus 40 times the retained selected allocation count.
12. Return the destination descriptor address.

The destination’s old range is therefore passed to F-f4ccd33a6308 only after the new range-processing call has returned. The explicit first-field replacement occurs after both old-range processing and the subsequent F-ff1bdc376dcd call.

The function does not check the allocation result before passing it onward. Nor does it verify that the final source-query result still fits the allocation count selected earlier.

### Storage reuse with a growing logical range

When the initial capacity-like query is not smaller than the initial source count, the function calls F-8be3a5940f42 first on the destination and then on the source.

If the destination result is smaller, it takes the growing reuse path:

1. Query the destination again through F-8be3a5940f42 and retain that result as a prefix count.
2. Call F-3b74fd4fa4b0 with:
   - The source’s current first field.
   - That source address plus 40 times the retained prefix count.
   - The destination’s current first field.
3. Query the source again through F-8be3a5940f42.
4. Write destination offset 4 as its current first field plus 40 times that latest source count.
5. Call F-82bab15a2c1c with:
   - The source’s current first field plus 40 times the retained prefix count.
   - The source’s current second field.
   - The destination’s current first field plus 40 times the retained prefix count.
   - The destination descriptor address.
6. Return immediately.

The destination end-field write occurs **before** the trailing range-processing call. A callback or other observer inside that helper can therefore encounter the new end value before the helper completes its work.

This function does not explicitly write destination offset 8 on this path. That is not a guarantee that the field remains unchanged: any invoked helper might modify it.

### Storage reuse without a growing logical range

If the queried destination count is at least the queried source count:

1. Call F-3b74fd4fa4b0 with the source’s current first field, the source’s current second field, and the destination’s current first field.
2. Retain its 32-bit return value.
3. Call F-f4ccd33a6308 with the destination descriptor address, that retained return value, and the destination’s current second field.
4. Query the source through F-8be3a5940f42 again.
5. Compute an end address from the destination’s current first field plus 40 times the latest source count.
6. Write that address to destination offset 4.
7. Write the same retained address to destination offset 8.
8. Return the destination descriptor address.

The start of the range passed to F-f4ccd33a6308 comes from F-3b74fd4fa4b0’s return value, not from a locally calculated count-based address.

The final two descriptor writes use the same calculated address. Consequently, the explicit result has equal second and third fields on this path, even when the original destination had spare storage.

### Arithmetic and read timing

The element stride is consistently 40 bytes. Count multiplication and address addition use the supplied 32-bit machine-word representation. There is no visible widened multiplication, checked addition, saturation, or rejection of unrepresentable ranges.

An allocation byte count can therefore wrap independently of the comparisons that selected the allocation count. Resulting range validity is not established.

Descriptor fields are generally read when preparing a particular call or write, not captured once at entry. A helper’s modifications to descriptors, shared state, or backing memory can affect later arguments. In particular:

- The allocation path retains the chosen allocation count but re-queries the source count afterward.
- The growing reuse path retains its prefix count across subsequent calls.
- The non-growing reuse path retains the first helper’s returned address across the next helper call.
- The allocation path reads the old storage address before the capacity-like query used as the second argument to F-ff1bdc376dcd.

No left-to-right evaluation order among individual arguments of a single helper call is established. The call-level ordering described above is established.

## Side effects

Explicit effects are limited to helper calls and destination descriptor writes. The function contains no direct element-by-element payload access.

Depending on the path, it explicitly writes:

| Path | Offset 0 | Offset 4 | Offset 8 |
|---|---|---|---|
| Identity | No | No | No |
| Allocation | New storage address | Recomputed end | Recomputed storage limit |
| Growing reuse | No | Recomputed end, before trailing processing | No |
| Non-growing reuse | No | Recomputed end | Same address as offset 4 |

These are this function’s explicit writes only. They do not constrain helper side effects.

The source descriptor is never explicitly written by this function. Nevertheless, source immutability is not guaranteed: helpers receive its address for queries or receive storage addresses derived from it, and aliasing is not excluded.

Ownership is documented_only. The helper ordering suggests allocation, range construction or copying, old-range destruction, and storage release. The supplied evidence does not establish that these operations actually acquire ownership, release memory, preserve globals, or leave either descriptor unchanged.

Distinct descriptors may overlap each other or reference overlapping backing storage. Only exact descriptor identity receives special treatment. Safe operation for other overlap patterns is unknown.

There is no explicit error-reporting path, rollback, or allocation-failure recovery. If a dependency fails to return normally, this function supplies no visible recovery procedure; already completed calls and writes must not be treated as undone.

## Acceptance examples

These are conditional contract examples, not runtime test results. Unless stated otherwise, they assume valid non-overlapping ranges, successful helper completion, stable query results, no helper descriptor mutations, and arithmetic that does not wrap.

1. **Exact self-assignment.** If both descriptor arguments are the same address, the function returns that address without helper calls or descriptor-field accesses. Auxiliary argument values do not change this outcome.

2. **Allocation from a destination count of 10.** Suppose the source count is 50 and the destination capacity-like result is 20. Allocation is selected. The growth candidates are 42 and 16, so the selected count is 50. F-871e64ddc6de receives a byte-size argument of 2,000 and zero. After successful processing, the destination’s second and third fields both equal the new storage address plus 2,000.

3. **Growth reserve exceeding source size.** With a destination count of 100, capacity-like result of 110, and source count of 120, allocation is selected. The growth candidates are 132 and 162. The selected allocation count is 162, producing a 6,480-byte request. The resulting end is 4,800 bytes beyond the new base; the storage-limit field is 6,480 bytes beyond it.

4. **Growth within existing storage.** With destination count 2, capacity-like result 8, and source count 5, storage is reused. F-3b74fd4fa4b0 receives the first 80 bytes of the source range. The destination end is then written as its base plus 200. Only afterward is the remaining source range passed to F-82bab15a2c1c. No explicit third-field write occurs.

5. **Shrink within existing storage.** With destination count 5, capacity-like result 8, and source count 2, the full source range is passed to F-3b74fd4fa4b0. Its return value becomes the start argument to F-f4ccd33a6308. Both destination offsets 4 and 8 are finally written as the destination base plus 80.

6. **Empty source.** With stable zero source count and a capacity-like result that is not smaller, the non-growing reuse path is taken. The range-processing calls still occur, including F-f4ccd33a6308. Both final address fields equal the destination base. Zero count does not itself suppress those calls.

7. **Changing source query result.** On allocation, if the final source query returns a larger value than the selected allocation count, the function still calculates and writes that larger end address. It performs no intervening capacity recheck. The safety of the resulting descriptor is not established.
