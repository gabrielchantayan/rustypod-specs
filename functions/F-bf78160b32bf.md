# F-bf78160b32bf

## Purpose

The supplied static representation describes a routine that derives several 32-bit values from an implicit context, performs a sequence of external calls, obtains a destination address from a 16-bit memory value, and writes a six-word record there. Further external calls follow the record construction.

The routine’s application-level purpose is not established. The record could represent initialization or registration state, but neither interpretation is part of the established contract.

This is a **documented_only** contract. The supplied representation explicitly reports unreliable instruction decoding and truncated control flow. Consequently, the operations below describe the visible recovered path, not a verified complete implementation. In particular, the terminal decoding failure does not establish that the actual routine intentionally halts.

## Behavior

### 1. Capture initial values

The first visible operation captures the fixed global word.

The routine then reads the 32-bit context field at byte offset 16 twice. These are separate accesses, not one read reused twice:

- The first read supplies a value scaled by 65,536. Call the resulting value **A**.
- The second read supplies a value shifted left by 12 bits. Call the resulting value **B**.

A and B therefore need not describe the same observed field value if the memory changes between the reads. No synchronization or snapshot mechanism is visible.

The global word is captured before either context-field read. Its captured value is later written into the record; there is no visible reread of that global before the record writes.

### 2. Perform six calls before the lookup

Six external calls precede the 16-bit lookup.

1. The first target is computed by adding 4,094 bytes to the incoming link-related value. Its one explicitly represented argument is the second explicit input plus A.
2. The second call receives A shifted left by five bits.
3. The third call has no explicitly represented arguments.
4. The fourth call has no explicitly represented arguments.
5. The fifth call has no explicitly represented arguments.
6. The sixth call has no explicitly represented arguments.

Except for the link-derived first target, these targets are represented as arithmetic involving literal addresses. The supplied representation does not show them being loaded from a mutable function-pointer table.

“No explicitly represented arguments” is not a verified zero-argument ABI declaration. The recovered representation may omit live register inputs.

### 3. Obtain the destination

After the sixth call, the routine reads an unsigned 16-bit quantity at byte address B + 46.

That quantity is zero-extended and interpreted directly as the destination address. No additional visible base address or dereference participates in this conversion.

Under the represented 32-bit address model, the resulting numerical destination is between 0 and 65,535 inclusive. This does not establish that the address is valid, writable, aligned, or outside a reserved region.

A seventh external call occurs **after** the lookup and **before** the first record write. It has no explicitly represented arguments.

The destination retained by the visible representation comes from the completed lookup. There is no visible repeat of the lookup after this seventh call. Changes made by that call to the lookup location do not, in this representation, select a new destination.

The routine performs these stores in order:

| Byte offset from destination | Width | Stored value |

The record occupies 24 bytes. Its second word is a self-address value, not the address of the second word.

The supplied representation establishes field offsets and store order, but not byte order. It also shows no atomic publication, locking, validity flag, rollback, or protection against another observer seeing an incomplete record.

No destination alignment check is visible. If an access fails partway through construction, earlier stores may already have occurred; exact fault and partial-access behavior depends on the execution environment.

## Acceptance examples

These are conditional criteria derived from static evidence, not executed tests. Each assumes successful accesses, compatible arithmetic, and external calls that return so the described point is reached.

### Stable context and complete record

Suppose both context reads observe 1, the captured global word is 9, the saved incoming value is 7, and the lookup supplies destination address 4,096.

Then:

- A is 65,536.
- B is 4,096.
- The lookup address is 4,142.
- The second call receives 2,097,152.
- Call 10 receives 32,768.
- The six direct record writes contain, in order: 65,536; 4,096; 0; 7; 9; 4,096.

If the second explicit argument is 3, the first call’s represented argument is 65,539.

### Distinct context observations

Suppose the first context read observes 1 and the second observes 2.

Then A is 65,536, B is 8,192, and the lookup address is 8,238. The record’s first and sixth words reflect different observations. An implementation that unconditionally replaces both reads with one shared observation would not preserve the represented access behavior.

### Global mutation before record construction

Suppose the initial global read captures 9, and an early external call subsequently changes that global to 10.

The direct write at record offset 16 still uses the captured value 9. No visible reread substitutes 10. This criterion does not restrict later callee writes to the record.

### Lookup mutation during call 7

Suppose the lookup returns destination 4,096, after which call 7 changes the lookup memory to contain 8,192.

The visible direct writes still target the record beginning at 4,096. If call 7 instead invalidates that destination, successful construction is no longer assured.

### Zero destination

Suppose the unsigned lookup returns zero.

The visible path does not reject it. If execution continues, it attempts the ordered stores at addresses 0, 4, 8, 12, 16, and 20. Whether those stores succeed or fault is environment-dependent.

### Observation during construction

An observer acting between the second and third stores may see the new first word and self-address word while later fields retain earlier contents. The body supplies no visible mechanism guaranteeing an all-at-once record update.
