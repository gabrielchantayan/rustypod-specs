# F-0772945d9f4a

## Purpose

F-0772945d9f4a describes a condition-dependent sequence of software-interrupt requests and coprocessor operations, followed by a terminal bad-instruction operation.

The supplied representation does not establish a conventional application-level purpose. It contains an explicit warning about invalid instruction data and terminates at truncated control flow. Consequently, this contract distinguishes:

- **Established static evidence:** conditions, operation arguments, repetition counts, and ordering visible in the supplied representation.
- **Inferred intent:** possible architectural interpretations of condition indicators and coprocessor operations.
- **Unknown behavior:** actual instruction validity, exception handling, coprocessor effects, and execution beyond the truncated boundary.

The sequence below is a **conditional continuation contract**. Later events are required by the visible representation only if every earlier operation returns or otherwise permits execution to continue. An interrupt, coprocessor access, or terminal operation may prevent the full sequence from occurring.

No runtime tests have been performed.

## Interface

### Calling interface

The representation declares no explicit parameters and no returned value. It nevertheless depends on incoming machine context that is not initialized within the visible body:

| Input category | Required information |
|---|---|
| Condition state | A zero indicator, a negative indicator, and an overflow indicator |
| Address inputs | Two independently supplied integer-valued address bases |
| Coprocessor inputs | Four incoming coprocessor-related values, designated here as inputs A, B, C, and D |

These are descriptive roles, not an established public calling convention. No argument registers, stack layout, linkage convention, or caller-save obligations are established.

For this contract:

- **Z** means the truth value of the incoming zero indicator.
- **E** means that the incoming negative and overflow indicators compare equal.
- **P** means that Z is true or E is false.
- **Base A** is the address input used with displacement `0x260`.
- **Base B** is the address input used with displacement `0x25c`.

The equality comparison is significant independently of Z. In particular, Z being true does not suppress either coprocessor load when E is also true.

### Widths and representations

The coprocessor inputs are represented as four-byte, uninterpreted quantities. This supports a nominal 32-bit width, but does not establish whether the underlying architectural operands are values, register selectors, or artifacts of the recovered representation.

The address inputs are represented as integers. Their actual machine width and address interpretation are not established. A 32-bit interpretation is plausible, but is not sufficient evidence to promise wrapping 32-bit arithmetic.

The negative and overflow indicators appear as character-sized values, while the zero indicator appears as Boolean. The visible behavior requires only:

- truth testing of the zero indicator; and
- equality or inequality comparison between the other two indicators.

No byte order, memory-record layout, alignment requirement, or serialized format is established.

### Results and termination

## Behavior

### Condition selection

The visible sequence divides into two main behaviors:

- **P false:** Z is false and the negative and overflow indicators are equal.
- **P true:** Z is true, or the negative and overflow indicators differ.

Two additional selections remain independent:

- Both coprocessor loads are selected exactly when E is true.
- The software interrupt with operand `0x1edf1d` is selected exactly when Z is false.

The supplied representation uses the same incoming condition values throughout. It contains no visible assignment changing those values between decisions. This establishes the static selections below; it does not establish that real interrupt handlers or coprocessor operations preserve architectural flags or other machine state.

### Interrupt-dominant behavior: P true

Subject to continuation after each operation, the observable sequence has four ordered groups.

**Opening group**

1. Two consecutive calls to F-000000000001, each with operand `0x1ddf1d`.
2. If E is true, one call to F-000000000003 with arguments: `5`, coprocessor input A, and Base A plus `0x260`.
3. Four further consecutive calls to F-000000000001, each with operand `0x1ddf1d`.
4. If Z is false, one call to F-000000000001 with operand `0x1edf1d`.

**Central interrupt group**

Seven consecutive calls to F-000000000001 use operand `0x1cdf1c`. They are followed by one call to F-000000000002 with arguments:

- `0xf`;
- `7`;
- `0`;
- coprocessor input C;
- coprocessor input C again.

Both final argument positions reference the same incoming coprocessor input. The representation does not establish whether these positions designate separate reads, register selectors, or another dependency-specific interpretation.

**Post-transfer interrupt group**

Immediately after that transfer operation, the sequence requests:

1. one interrupt with operand `0x1cdefc`;
2. one interrupt with operand `0x1dcebb`;
3. ten consecutive interrupts with operand `0x1ddf1d`.

These events are not interchangeable or coalescible. Their distinct operands, repetition counts, and relative order are part of the visible contract.

**Closing group**

If E is true, F-000000000003 receives arguments `5`, coprocessor input A, and Base B plus `0x25c`.

Four consecutive interrupts with operand `0x1cdf1c` follow. F-000000000004 is then invoked.

For this behavior, the full visible sequence contains:

- sixteen interrupts with operand `0x1ddf1d`;
- eleven interrupts with operand `0x1cdf1c`;
- one interrupt each with operands `0x1cdefc` and `0x1dcebb`;
- optionally, one interrupt with operand `0x1edf1d`.

The total is therefore 29 interrupt requests when Z is true and 30 when Z is false.

### Transfer-dominant behavior: P false

This case necessarily has Z false and E true.

Subject to continuation, the event order is:

1. F-000000000002 with arguments `0xf`, `5`, `0`, coprocessor input C, and coprocessor input D.
2. F-000000000003 with arguments `5`, coprocessor input A, and Base A plus `0x260`.
3. F-000000000001 with operand `0x1edf1d`.
4. F-000000000002 with arguments `0xf`, `5`, `0`, coprocessor input B, and coprocessor input D.
5. F-000000000003 with arguments `5`, coprocessor input A, and Base B plus `0x25c`.
6. F-000000000004.

None of the repeated interrupt groups from the interrupt-dominant behavior occurs in this case.

### Address calculations and load ordering

The two address expressions use different bases and different displacements:

- first load: Base A plus `0x260`, equivalent to decimal 608;
- second load: Base B plus `0x25c`, equivalent to decimal 604.

The first load precedes the second whenever both are reached. They are separate operations; equal effective addresses would not justify merging them.

There is no visible address validation, overflow check, alignment check, or range check before either load operation.

For inputs whose mathematical sums are representable in the actual execution model, those sums define the address arguments. Boundary behavior is **documented_only**: the evidence does not settle signed overflow, pointer conversion, address truncation, or wraparound.

The word “long” does not establish the number of bytes read. No load width, destination layout, or writeback behavior can be specified from this representation alone.
