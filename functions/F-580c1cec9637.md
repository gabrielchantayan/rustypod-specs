# F-580c1cec9637

## Purpose

F-580c1cec9637 traverses a memory-resident table, selects registered handlers for supported subtable formats, and conditionally invokes a construction dependency. Validation and construction are inferred dependency roles, not established guarantees about their implementations.

The function distinguishes initial header rejection from subsequent processing outcomes:

- An unavailable initial header or unsupported header version produces the 32-bit return value `8`.
- After accepting a version-zero header, exhausting the declared records or encountering an incomplete next record produces the 32-bit return value `0`.
- Unsupported formats, nonzero validation status, and nonzero construction returns do not independently change that eventual `0`.

Thus, `0` does not establish table completeness, successful validation, or creation of any object.

A zero construction return triggers an unchecked four-byte store through an address taken from a local output-address slot. This function does not initialize that slot or verify that construction assigned it. Output-address validity, assignment, ownership, and disjointness remain dependency-contract unknowns.

## Interface

### Input object

The function accepts one address-valued argument identifying an existing object. The supplied representation uses 32-bit addresses and the following object fields:

| Object-relative offset | Width | Established use |
|---|---:|---|
| `0x108` | 16 bits | Read and zero-extended after validation-state initialization for each matched handler. |
| `0x1F0` | 32 bits | Table base address, read at entry and retained. |
| `0x1F4` | 32 bits | Table length, read initially for the cached end and reread for each nonzero subtable-offset check. |

There is no explicit null check for either the object or table address. Safe execution requires accessible storage for every reached read and write, including descriptor accesses and the final output-relative store.

The initial length contributes to a cached end address. Later length reads do not update that end or replace the retained table base.

### Table layout

Fields assembled directly from table bytes use big-endian encoding.

| Header-relative offset | Width | Meaning |
|---|---:|---|
| `0` | 16 bits | Version; only zero is accepted. |
| `2` | 16 bits | Declared record count. |

Records begin at table offset `4` and occupy eight bytes each:

| Record-relative offset | Width | Meaning |
|---|---:|---|
| `0` | 16 bits | First identifier placed in construction context. |
| `2` | 16 bits | Second identifier placed in construction context. |
| `4` | 32 bits | Subtable offset relative to the retained table base. |

An eligible subtable begins with a two-byte big-endian format identifier. No additional subtable layout is established by this function.

### Return and indirect output

The direct return is a 32-bit value:

- `8` when the initial header-availability check fails or the version is nonzero.
- `0` when traversal terminates after accepting version zero.

These descriptions assume dependencies return normally and no invalid memory access or other exceptional condition interrupts execution.

There is no caller-supplied output argument. F-e504f72ffcc9 receives the address of a local 32-bit output-address slot. The function does not initialize this slot before passing its address and does not explicitly reset it between construction attempts.

When F-e504f72ffcc9 returns zero, the function reads the slot and stores a saved 32-bit result at offset `0x14` from the address it contains. It does not check whether the dependency assigned the slot, whether the address is null, or whether the destination is writable. A zero construction return alone therefore does not establish a valid indirect output.

## Behavior

### Initial header decision

The function reads the table base, reads the object’s length, and forms the cached end address. It compares the address four bytes after the base with that end.

If the comparison indicates that four bytes are unavailable, it returns `8` without calling the diagnostic dependency.

Otherwise, it decodes the two-byte version:

- Version zero permits decoding of the record count and traversal.
- A nonzero version causes one call to F-4457a9a44a68 with an unsupported-version diagnostic and a version value, followed by return `8`.

The version supplied to the diagnostic is assembled from the table bytes again. With stable bytes it equals the value that caused rejection; equality is not established if those bytes change between reads. The record count is not decoded on this rejection path.

For ordinary nonwrapping addresses, the availability check corresponds to requiring at least four bytes. The supplied address comparison must not be replaced unconditionally with a mathematical length comparison: wrapped-address semantics are not fully established here.

### Record traversal

The cursor starts at table offset `4`. The 16-bit count is zero-extended into a 32-bit unsigned remaining count.

Before accessing each record, the function checks the remaining count. Zero terminates traversal with `0`. Otherwise, if the address eight bytes after the cursor exceeds the cached end, traversal also terminates with `0`, without decoding that record or issuing a truncation diagnostic.

For a complete record, the observable preparation order is:

1. Decode and save the first 16-bit identifier.
2. Decode and save the second 16-bit identifier.
3. Calculate the next-record address.
4. Clear the second 32-bit construction-context word.
5. Decode the 32-bit subtable offset.
6. Advance the cursor to the calculated next-record address.
7. Process or skip the subtable.
8. Decrement the remaining count once.

This establishes ordering between the combined field decodings, not a separate chronological order for individual byte loads within each decoding expression.

Records are visited in stored order. There is no sorting, deduplication, or uniqueness check. The count is decoded once; later header changes do not resize traversal.

A table containing fewer complete records than declared can therefore return `0`. This return is not a completeness assertion.

### Subtable eligibility

An offset of zero is skipped immediately. It causes no length reread, format read, or registry search.

For a nonzero offset, the function rereads the object’s 32-bit length and checks whether the offset is at most that length minus two. Subtraction and comparison use unsigned 32-bit arithmetic.

With a stable length of at least two and nonwrapping address arithmetic, this check leaves room for the two format bytes within the declared table length. It does not establish availability of any format-specific payload.

An eligible nonzero offset may point into the header or record array. No requirement places subtables after the records.

Unsigned underflow matters:

- Length zero minus two is `0xFFFFFFFE`.
- Length one minus two is `0xFFFFFFFF`.

A later length change to zero or one can therefore admit offsets that would fail a conventional bounds check. Such a change may result from dependency effects or from this function’s own output-relative store.

The subtable address always uses the retained original base. The object’s table-base field is not reread.

### Handler selection

For an eligible offset, the function reads and zero-extends the 16-bit format identifier.

It searches a globally referenced array of 32-bit descriptor addresses. A zero entry terminates the search. For each nonzero entry, the descriptor’s 32-bit field at offset `0x14` is compared with the zero-extended format. Values above `65535` cannot match.

The first matching descriptor is selected. If none matches, the record is skipped without a diagnostic.

Later matching descriptors are not tried after validation rejection or construction failure. Each later eligible record starts a fresh registry search. Preservation of the registry across dependency calls is not established.

### Matched-handler processing

For a selected descriptor, the function initializes a saved 32-bit result to zero and writes the original input-object address into the construction context.

It calls F-bc303070dba5 with:

- An address of local validation-state storage.
- The selected subtable address.
- The cached table-end address.
- A zero-valued fourth argument.

After that call returns, it reads the object’s 16-bit field at `0x108`, zero-extends it, and saves it locally. No later explicit consumption of that saved value is shown; possible use through dependency or runtime conventions is unresolved.

Next, F-3756c6e16ed7 receives a separate local work-area address. The representation reserves 384 bytes for that area.

If F-3756c6e16ed7 returns zero, the function obtains the callback from descriptor offset `0x18` and invokes it with the subtable address and validation-state address. The callback’s 32-bit return replaces the saved result.

If F-3756c6e16ed7 returns nonzero, the callback is skipped and the saved result remains zero.

The function then reads a separate local 32-bit status word. No explicit initialization of that word appears in this function. A defined status value depends on dependency behavior or runtime conventions not established by the supplied evidence.

### Construction or rejection

A zero status causes a call to F-e504f72ffcc9 with the selected descriptor, subtable address, construction-context address, and address of the local output-address slot.

The context contents explicitly established before that call are:

| Context-relative offset | Width | Content |
|---|---:|---|
| `0` | 32 bits | Original input-object address. |
| `4` | 32 bits | Zero. |
| `8` | 16 bits | First record identifier. |
| `10` | 16 bits | Second record identifier. |

These are local scalar stores. Their in-memory byte order is not established merely by the table’s big-endian encoding.

The output-address slot is uninitialized by this function. Passing its address is not an assignment to the slot.

If construction returns zero, the function uses the slot’s contents without checking that construction wrote them. It then stores the saved 32-bit result at output offset `0x14`. This occurs even when the callback was skipped and the saved result is zero.

If construction returns nonzero, the function does not read the output-address slot for this store and does not issue a construction-failure diagnostic.

A nonzero status prevents construction. Instead, F-4457a9a44a68 is called twice: first with an operation-identifying diagnostic, then with a diagnostic indicating that a broken subtable was ignored.

After either path, traversal continues, assuming normal returns.

## Side effects

### Direct writes and unchecked output use

Explicit local writes prepare record identifiers, context fields, the saved result, and other saved values. The function does **not** explicitly initialize the local output-address slot or the separate status word. Any dependency writes to those locations are distinct from this function’s own assignments.

The explicit external result write is four bytes at output offset `0x14`, conditional on a zero construction return. Neither output assignment nor destination validity is checked.

There are no separate explicit stores addressed through the input-object base or retained table base. This does not establish preservation: an assigned output address may make the result store overlap either region.

For example, if construction assigns the input-object address plus `0x1E0`, the result store lands on the length field at `0x1F4`. A saved result of zero then sets that field to zero. Later nonzero-offset checks reread the changed length and apply unsigned subtraction.

An output address can also make the store overlap unread records, subtable bytes, registry storage, or other accessible state. Subsequent reads may observe those modifications. Already saved identifiers, the cached end, retained base, and decoded count are not automatically recomputed.

If construction returns zero without assigning a usable address, the evidence does not establish a defined destination or successful continuation. The behavior must not be described as a guaranteed write to a constructed object.

### Ordering and lifetime

The matched-record sequence is validation-state initialization, object-property read, work-area dependency, conditional callback, status inspection, construction or rejection diagnostics, and—only after zero construction return—the unchecked output-relative store.

Dependency effects and that store can affect later reads. Processing may combine the original base and cached end with changed object length, table bytes, or registry contents.

No explicit allocation or release operation appears here. Dependency allocation, attachment, reference management, and cleanup are unknown. No ownership transfer of the input object or table is established.

Validation storage, work area, construction context, and output-address slot are local. Their addresses are valid during this invocation; whether dependencies retain them is unknown.

## Acceptance examples

These are conditional static expectations, not runtime results. Unless stated otherwise, addresses are accessible, arithmetic does not wrap, dependencies return normally, and relevant storage is stable.

1. **Incomplete header.** Length three fails the initial check. Return `8`; no diagnostic.

2. **Unsupported version.** A complete header begins with bytes `00 02`. Stable bytes produce one unsupported-version diagnostic carrying `2`, then return `8`. Records are not processed.

3. **Zero records.** Header bytes `00 00 00 00` produce `0` without registry search, validation, or construction.

4. **Incomplete record.** A version-zero header declares one record, but only seven record bytes are available. Return `0`; that record’s fields are not decoded.

5. **Zero offset.** A complete record with offset zero is skipped without rereading length or reading a format.

6. **Format boundary.** With length twenty, offset eighteen is eligible; offset nineteen is not. Eligibility establishes only the two-byte format boundary.

7. **No matching handler.** The registry terminates without a match. No validation or construction call occurs for that record.

8. **Duplicate handlers.** Two descriptors match. Only the first is selected, even if processing rejects the subtable or construction fails.

9. **Assigned successful output.** The callback returns a specified 32-bit value, status is defined as zero, and construction returns zero after assigning a usable output address. That exact value is stored at output offset `0x14`.

10. **Skipped callback.** F-3756c6e16ed7 returns nonzero, status is nevertheless defined as zero, and construction returns zero after assigning writable output storage. The result store writes zero.

11. **Rejected status.** Status is nonzero. Two diagnostics occur in the stated order; construction is not called. Later records remain eligible for traversal.

12. **Construction failure.** Status is zero and construction returns nonzero. No output-relative result store or construction-failure diagnostic occurs, regardless of whether construction assigned the slot.

13. **Zero return without output assignment.** Construction returns zero without writing the slot. The function still uses its contents; it performs no assignment check or error return. A valid destination, completed store, and subsequent normal return cannot be required from this evidence.

14. **Output aliases length.** Initial length is twenty-four, with two complete records. The first record reaches construction with saved result zero; construction assigns the input-object address plus `0x1E0` and returns zero. The store changes length to zero. A second-record offset of sixty-four now passes eligibility because sixty-four is at most `0xFFFFFFFE`. If backing storage there is readable, format decoding proceeds beyond the original declared end. Validation initialization still receives the original cached end.

15. **Output aliases an unread record.** Construction assigns an address placing the result store within a later record and returns zero. Subsequent decoding observes the modified bytes. Exact values depend on overlap and scalar-store byte order.
