# F-27385576fa62

## Purpose

F-27385576fa62 performs a mode-dependent lookup, optionally processes one continuation, and updates a caller-supplied result area. Unless a result flag suppresses representation generation, it attempts conversion into inline storage and may allocate replacement storage after a particular conversion status.

“Lookup,” “continuation,” and “representation” describe the observed data flow. Their application-level meanings are not established.

The operation is not transactional. A nonzero return can follow changes to the caller’s in/out word, result fields, or dependency-controlled state. No local rollback restores those changes.

## Interface

### Arguments

Seven arguments are visible:

| Position | Role and established use |
|---|---|
| 1 | Context address. The function reads a 16-bit discriminator at byte offset `0x02`, a 32-bit pointer at `0x158`, and, on applicable paths, a 32-bit dependency argument at `0x18c`. |
| 2 | Opaque 32-bit lookup argument forwarded to dependencies. |
| 3 | 32-bit input reference. Zero/nonzero controls argument derivation, auxiliary lookup, and a post-lookup dependency call. |
| 4 | 32-bit companion value. Replaced by a dependency result only when this value is zero and argument 3 is nonzero. Its units and semantic signedness are unresolved. |
| 5 | 32-bit argument with no visible use in the supplied body. |
| 6 | Result-area address, also used to select record storage. |
| 7 | Address of a 32-bit in/out word. Its initial value seeds temporary request state; selected paths write a resulting value back. |

The represented addresses and pointer fields are 32 bits wide. No local validation establishes nullability, alignment, accessible extents, or permitted overlap. Valid memory for every reached access is therefore a precondition; the function does not provide a checked failure status for invalid addresses.

### Modes and record selection

A context discriminator of `0x482b` selects **mode A**. Every other 16-bit value selects **mode B**.

The original selected record address is:

- Mode A: the result-area base.
- Mode B: the result-area base plus `0xfc` bytes.

A mutable lookup descriptor initially contains that address, a 32-bit value of `0x238` in mode A or `0x66` in mode B, and a 32-bit value of one.

The original selected address is retained independently. Local record inspection and fallback calls use it even if a dependency changes the descriptor’s address. The same mutable descriptor is passed to any second lookup; it is not locally restored first.

### Result-area layout

All offsets are bytes from argument 6.

| Offset | Width | Established role |
|---|---:|---|
| `0x208` | 16 bits | Flags. Bit `0x10` suppresses representation generation. Bit `0x01` is set after a nonzero allocation result and tested for conversion-error cleanup. |
| `0x20a` | 16 bits | Low 16 bits of the current 32-bit size value at conversion finalization. |
| `0x20c` | 32 bits | Auxiliary result obtained through F-4055be9c3f18. |
| `0x210` | 32 bits | Representation address. |
| `0x214` | Dependency-defined extent | Inline destination supplied with initial capacity `0x20`. |

Bit `0x01` does **not** reliably identify an allocation made by this invocation. The function does not initialize or clear an incoming set bit before conversion. Its meaning at cleanup depends on incoming state and intervening dependency effects.

The capacity unit and the required byte extent of inline storage are not established by the numeric capacity alone.

### Return status

The function returns a 32-bit status:

- `0`: successful completion.
- `0x30`: a lookup/fallback or mode-B record-compatibility result.
- `-108`: the allocator returned a zero address.
- Other statuses: returned according to the routing below.

The lookup and conversion results held as signed 16-bit values are sign-extended to 32 bits. For example, a 16-bit result pattern of `0xffff` becomes `-1`, not `65535`. Other dependency statuses must not automatically be assigned this narrowing rule.

## Behavior

### Preparation and initial reads

The function first reads and retains the mode decision. It does not reread the discriminator after dependency calls.

It initializes the descriptor and retains the original record address. If argument 3 is nonzero and argument 4 is zero, F-1cb585febd84 receives argument 3 and supplies the effective fourth argument. Otherwise, the supplied fourth argument remains effective.

F-a0c5d57d1d48 receives the context, argument 2, argument 3, effective fourth argument, temporary metadata storage, and zero.

A nonzero preparation result returns immediately. At this point, the body has not yet performed its lookup-handle dereference or read the caller’s in/out word. This does not constrain accesses or side effects inside the dependencies.

After successful preparation, the body reads, in order:

1. The 32-bit pointer at context offset `0x158`.
2. The first 32-bit word through that pointer, retaining it as the lookup handle.
3. The caller’s 32-bit in/out word, copying it into temporary request state.

It then clears an adjacent 16-bit request field. Other request bytes are not established as initialized by these operations.

### Primary lookup

If argument 3 is zero, the primary lookup argument is `0xffffffff`.

Otherwise, F-f987e285db03 receives argument 2, the current context field at `0x18c`, and an address-output slot:

- On zero status, the first 32-bit word at the returned address becomes the lookup argument.
- On nonzero status, the lookup argument becomes `0xffffffff`.

An auxiliary-lookup failure is not directly returned.

F-7cae4aaa5e45 receives the retained lookup handle, temporary request storage, the selected lookup argument, the mutable descriptor, and temporary output storage. The same request-storage address appears in two argument positions.

Its signed 16-bit status is widened. For this initial lookup, `0x20` is changed to `0x30`.

A nonzero status other than `0x30` returns immediately. Status `0x30` selects fallback. Zero selects record inspection.

### Fallback

The same fallback selection is used after either lookup:

- **Mode A:** F-f6310772ddb8 receives the context, argument 2, argument 3, effective fourth argument, temporary metadata, original selected record address, and caller’s in/out address.
- **Mode B:** F-079b3af77906 receives the effective fourth argument, argument 3, and the address of a 32-byte temporary buffer. F-9a0ed9935fa9 then receives the context, argument 2, that same buffer address, zero, temporary metadata, original selected record address, and caller’s in/out address.

The 32-byte extent is the temporary buffer’s visible size. It does **not** establish that F-079b3af77906 initializes all 32 bytes, writes any particular number of bytes, or produces a complete object. Its output contract remains unresolved.

A nonzero fallback status returns. Successful fallback proceeds to final result processing without local continuation inspection or the local in/out-word assignment used on ordinary lookup-success paths. The fallback dependencies themselves receive the in/out address and may modify it.

### Successful primary lookup and continuation inspection

After an initial zero lookup status, a nonzero argument 3 causes F-af25767f2ba8 to receive the current context field at `0x18c`, argument 2, and the address of the temporary 32-bit request value. No local branch uses this dependency’s return status.

The body reads the 16-bit type at the original selected record address:

| Type | Continuation quantity | Continuation-data address |
|---|---|---|
| `3` or `4` | Direct 32-bit read at record offset `0x04` | Record plus `0x08` |
| `0x300` or `0x400` | Result of F-4055be9c3f18 using record plus `0x0a` | Record plus `0x0e` |
| Any other type | No continuation interpretation | Not applicable |

For types `0x300` and `0x400`, the displayed extraction call also receives a value associated with an additional return register from the preceding lookup or post-lookup dependency. Its meaning and ABI status are unresolved.

An unrecognized type causes the temporary 32-bit request value to be written to the caller’s in/out word, followed by final processing.

For a recognized type:

- Zero continuation quantity proceeds directly to final processing, skipping the local in/out-word write.
- Nonzero continuation quantity selects the continuation operation.

### One continuation operation

F-360d49b83f75 receives the nonzero quantity, continuation-data address, retained mode decision, and temporary metadata. No local status check follows this call.

The body then clears the temporary 32-bit request value and adjacent 16-bit field. It calls F-7cae4aaa5e45 again with the retained lookup handle, the same descriptor address, and lookup argument `0xffffffff`.

The second signed 16-bit status is handled as follows:

- `0`: write the temporary request value to the caller’s in/out word, then proceed.
- `0x20` or `0x30`: select fallback.
- Any other nonzero value: return that status.

No local loop inspects the second result for another continuation. Unlike the initial lookup, the second lookup routes `0x20` directly to fallback rather than first replacing it with `0x30`.

### Auxiliary output and suppression

Following successful lookup or fallback processing, F-4055be9c3f18 is called on a field in temporary metadata. Its 32-bit result is stored at result offset `0x20c`.

Only after that store does the function test flag bit `0x10`.

When the bit is set:

- Mode A returns zero without locally initializing the representation address or length.
- Mode B rereads the type at the original selected record address. A type other than `0x100` or `0x200` returns `0x30`.
- For either accepted mode-B type, F-c158f6e5f468 receives the context, original selected record address, and result base. The function then returns zero without locally performing conversion finalization.

These statements concern local operations; dependencies may have changed result fields.

### Representation generation

When suppression is clear, the body first stores result base plus `0x214` into the representation-address field.

#### Mode A

F-8a6756c94146 receives temporary source data, a source extent, inline destination, 32-bit size-output storage, capacity `0x20`, and constants `0x3a` and zero.

The source extent is formed by zero-extending a 16-bit metadata count and doubling it. Its range is `0` through `131070`; this multiplication does not overflow 32 bits. Later calls form their extent from the metadata count at those uses; dependency preservation is not independently established.

Any status other than `0x3f` proceeds to conversion finalization.

Status `0x3f` causes F-54585861452f to calculate a 32-bit unsigned size from the source, corresponding doubled extent, and constants `0x3a` and zero. The allocator is then called with that size plus one.

A nonzero allocation result selects a second F-8a6756c94146 call with the allocated destination and size-plus-one capacity. There is no third conversion attempt.

#### Mode B

After installing the inline address, the body requires record type `0x100` or `0x200`. An incompatible type selects status `0x30` and conversion finalization without calling a converter.

For an accepted type, F-c158f6e5f468 runs first. F-03ee4c791a9a then receives the context, temporary metadata beginning at its 16-bit count field, capacity `0x20`, size-output storage, and inline destination.

Its signed 16-bit result determines the next step:

- `0`: conversion finalization with success.
- `0x3f`: allocation using the reported size plus one, followed, for a nonzero address, by one retry of F-03ee4c791a9a.
- Any other status: F-6ae731bb6fd8 receives the metadata, capacity `0x20`, the same size-output storage, and inline destination. Its status replaces the first conversion status.

The alternate converter’s `0x3f` does not trigger allocation. A failed allocated retry likewise does not select the alternate converter.

### Allocation arithmetic and failure

Every size-plus-one expression uses a 32-bit unsigned size. Addition wraps modulo \(2^{32}\). In particular, size `0xffffffff` produces an allocation argument of zero. No overflow rejection or larger-width allocation request is visible.

The retry capacity is also formed by 32-bit unsigned size-plus-one arithmetic. Allocation units, zero-request semantics, and dependency preservation remain unresolved; arithmetic wrap is established independently of those unknowns.

The allocation result is stored at result offset `0x210` before testing it:

- Zero causes immediate return of `-108`.
- Nonzero causes flag bit `0x01` to be set before the conversion retry.

Allocation failure bypasses local length storage and conversion-error cleanup. It does not locally clear an incoming allocation bit.

### Conversion finalization

Every path reaching this stage stores the low 16 bits of the current 32-bit size at result offset `0x20a`, even when returning an error.

For mode-B record rejection, no preceding converter initializes that size in the visible body. Consequently, a deterministic length value on that branch is not established.

If the final status is nonzero and the current flag bit `0x01` is set:

1. F-f09338a20fc0 receives the current representation address.
2. The body clears flag bit `0x01` with a 16-bit read/modify/write.
3. The body clears the representation address through two successive 16-bit stores, first at `0x210`, then at `0x212`.

The final conversion status is returned. Successful conversion does not locally release storage or clear the allocation bit.

## Side effects

Established local ordering includes:

- Mode selection before dependency calls.
- Preparation before handle dereference and initial in/out-word read.
- Applicable in/out-word assignment before auxiliary-result storage.
- Auxiliary-result storage before suppression testing.
- Inline-address installation before conversion-path mode-B type rejection.
- Allocation-address storage before zero-address testing.
- Length storage before error release, flag clearing, and the two pointer-clearing stores.

Dependencies may add reads, writes, resource operations, or global-state changes. Their preservation behavior is not established. Aliasing can also make a write through one argument observable through another address.

Successful allocation is retained on successful conversion. Later caller release is plausible intent, not a complete established ownership contract.

A preexisting set allocation bit is particularly consequential: after the inline address is installed, a conversion error can cause that inline address to be passed to F-f09338a20fc0. No local check restricts cleanup to allocations made during this call. Safe incoming state and dependency-compatible ownership are required, but their full rules are unresolved.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Dependency effects must satisfy each stated condition.

1. **Preparation failure:** If preparation returns `7`, the function returns `7` before its local handle dereference or in/out-word read.

2. **Auxiliary failure:** With argument 3 nonzero, a nonzero auxiliary-lookup status supplies `0xffffffff` to the primary lookup rather than becoming the function’s immediate return status.

3. **Lookup fallback:** An initial lookup status of `0x20` selects fallback through normalization to `0x30`. A second-lookup status of `0x20` selects fallback directly.

4. **Zero continuation:** A successful primary result of type `3` with zero quantity performs neither continuation processing nor a second lookup, and skips the local in/out-word assignment.

5. **Single continuation:** A nonzero quantity followed by second-lookup success causes the second request value to be written back. Even if the returned record describes another continuation, the body does not inspect it again.

6. **Suppressed representation:** Successful mode-A processing with suppression set stores the auxiliary result and returns zero without local pointer or length initialization.

7. **Mode-B rejection:** With suppression clear and incompatible record type, the inline pointer is installed before status `0x30` reaches finalization. The stored length is not deterministically established by the body.

8. **Wrapped allocation request:** If the size used for allocation is `0xffffffff`, the allocator receives zero. A zero returned address produces `-108`; a nonzero address is not rejected merely because the request wrapped.

9. **Allocation failure:** A zero allocation result leaves the representation address zero and returns `-108` without local length storage or cleanup-bit clearing.

10. **Incoming cleanup bit:** If bit `0x01` is already set, no allocation occurs, the inline address remains current, and conversion fails, cleanup passes that inline address to F-f09338a20fc0.

11. **Allocated retry failure:** If allocation succeeds, the retry fails, and the cleanup bit remains set, finalization stores the truncated size, passes the current pointer for release, clears the bit, and clears both pointer halves.

## Uncertainties

The following remain **documented_only**:

- Domain meanings of records, statuses, metadata, and representation contents.
- Complete argument, metadata, and buffer contracts of dependencies.
- How much of the 32-byte fallback buffer F-079b3af77906 writes or initializes.
- Global-state effects, aliasing permissions, and preservation guarantees.
- The additional return-register value associated with certain continuation types.
- Required memory extents, alignment, and overlap restrictions.
- Size and capacity units, termination requirements, and allocator behavior for zero requests.
- Release compatibility and safe incoming allocation-bit/pointer invariants.
- Deterministic length on conversion paths lacking an established size initialization.
- Exact dependency ABI where displayed call shapes differ.

Unsigned size-plus-one wrap is not an uncertainty; its resource consequences depend on the unresolved allocation contract.
