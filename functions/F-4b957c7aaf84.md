# F-4b957c7aaf84

## Purpose

F-4b957c7aaf84 changes a caller-supplied cursor according to address-valued relationships in memory. Its result is the value left in the cursor cell; it returns no value.

Two selection rules are established:

- When the starting record has a nonzero branch link, selection follows descent links to their zero-terminated end.
- Otherwise, selection follows upward links while a reciprocal relationship holds. A separate closing relationship determines whether the first unaccepted proposal becomes the result.

The contract includes intermediate cursor changes, not merely the final destination. An implementation that calculates a destination and writes it once would not preserve the established behavior for all supported memory arrangements.

**Inferred intent:** The relationships resemble traversal to a successor in a linked binary tree. Neither a tree representation nor successor semantics is established as an input requirement.

## Interface

### Input and output

The sole argument designates a readable and writable cell containing a signed integer. That integer is used as an address representation when locating links.

The cell’s location and its contents have different roles:

- The argument locates the cursor cell.
- The cell’s contents identify storage from which links may be read.
- Link values can subsequently replace the cell’s contents.

Normal completion returns no value or status. Depending on the selected relationships, the cursor may receive several writes, one write, or no write.

No separate output buffer, length, flags, allocator, or error channel is present.

### Partial storage layout

The function recognizes three address-relative link locations:

| Role | Byte offset | Use |
|---|---:|---|
| Upward link | 4 | Supplies a proposal during upward selection |
| Descent link | 8 | Continues descent selection |
| Branch link | 12 | Chooses the initial mode and participates in upward comparisons |

All three links are read using the same signed integer type as the cursor contents.

This is a partial access layout, not a complete record definition. The evidence establishes no access at offset zero, payload format, total record size, allocation boundary, or separation between records.

The four-byte spacing of link locations does not, by itself, establish the width of each link. If the integer type is four bytes wide, the three accesses occupy bytes 4–7, 8–11, and 12–15 respectively. That layout remains conditional on the width assumption.

### Representation and arithmetic

**Established:** Cursor contents, retained link values, and the bases used for offset arithmetic are signed integers of the same represented type.

**documented_only:** Exact integer width, pointer width, byte order, and alignment requirements are not supplied. The argument’s pointer width need not equal the width of a stored address representation.

Each link location is formed through signed integer addition of its offset and conversion of the result to an address. Defined execution therefore requires both valid arithmetic and a valid resulting access. The function does not establish modular address arithmetic, truncation, or recovery from signed overflow.

Zero has specific control significance, but is not a universal null check. Negative values receive no explicit rejection. Their usability, like that of any other address representation, depends on the execution environment.

### Access and termination preconditions

Defined execution requires:

- A live cursor cell valid for every required read and write.
- Readable link storage at every location actually reached.
- Valid address calculations and supported integer-to-address conversions.
- Alignment, lifetime, and access permissions appropriate to the represented types.
- Any overlapping storage to satisfy the environment’s memory-access rules.

These conditions do not guarantee termination. Normal completion also requires the selected relationships to reach a stopping condition.

## Behavior

### Selection model

The initial mode is determined by the branch link of the record identified by the entry cursor value. This link is read before any cursor write.

A nonzero initial branch value is a retained descent destination. A zero initial branch value selects upward traversal.

Retention matters: a value already obtained from a link remains the basis for specified later accesses. It is not necessarily reconstructed from the current cursor contents. Retaining an address value does not copy the addressed record, protect its storage, or acquire ownership.

### Descent result and update obligations

For stable storage, descent selects the last record in the chain beginning at the initial branch destination and continuing through nonzero descent links.

Every nonzero destination in that chain must be installed in the cursor, in chain order. Each installation precedes the read of that destination’s descent link. The terminating zero is not installed.

Consequently:

- Even a chain containing only one destination causes a cursor write.
- The descent-link read uses the retained destination as its address base.
- The cursor is not reread to obtain that base.
- No upward link is needed in this mode.
- No visited destination’s branch link is needed after the initial mode decision.

A reachable descent cycle with no zero terminator can prevent normal completion. There is no traversal limit or cycle-detection behavior.

### Upward result and update obligations

An upward proposal is obtained from an upward link. Its reciprocal relationship succeeds when the proposal’s branch link equals the current cursor value.

Successful proposals are intermediate destinations and must be installed in the cursor. Each installation precedes the upward-link read that supplies the following proposal. That read uses the retained accepted destination as its base.

The first proposal whose reciprocal relationship fails ends this repeated selection, but is not necessarily discarded. It remains the candidate for a distinct closing decision:

| Closing relationship | Required result |
|---|---|
| The current record’s branch link differs from the retained proposal | Install the proposal |
| The current record’s branch link equals the retained proposal | Make no closing cursor write |

The reciprocal relationship and the closing relationship examine different link locations. Failure of the first does not determine the outcome of the second.

A zero upward proposal receives no special exemption from these rules. Its branch link is still accessed at the location derived from integer zero plus 12. A normal result is established only if that access is valid and the remaining conditions are satisfied.

### Read and write ordering

The established ordering constrains more than the final value:

| Access or decision | Required ordering |
|---|---|
| Initial branch-link read | Before every cursor write |
| Descent-link read for a selected destination | After that destination is installed |
| Upward intermediate installation | After its reciprocal relationship succeeds |
| Upward-link read supplying the next proposal | After the accepted proposal is installed |
| Closing relationship | After the first failed reciprocal relationship |
| Closing installation, if required | After the closing branch-link read |

Upward mode obtains its first upward-link base through another cursor read after the initial branch decision. It does not establish an entry-state snapshot shared by both accesses.

Each reciprocal comparison reads the proposal’s branch link and the cursor cell. The supplied representation does not establish the relative order of those two reads.

The closing branch-link access obtains its base from a cursor read. It is not specified to reuse the cursor value read during the failed reciprocal comparison.

These are source-level access constraints for defined execution. They do not promise atomicity, synchronization, or a distinct physical memory transaction for each ordinary read.

### Aliasing and mutable relationships

Cursor storage is not explicitly required to be disjoint from link storage. Where overlap is otherwise valid, a cursor installation may change a link that will be read later in the same call.

For example, if the cursor cell occupies a selected destination’s descent-link location, installing that destination changes the storage used by the following descent-link read. The result cannot then be derived from an immutable copy of the entry relationships.

Stable-chain descriptions therefore apply only when the relevant storage remains stable. With permitted overlap, the access ordering governs the result and may also change whether traversal terminates.

No concurrent-mutation protocol is established. The absence of a snapshot is not permission to introduce data races.

## Side effects

### Memory and state

The cursor cell is the only explicit write destination. Record links are otherwise read-only from this function’s perspective.

If storage overlaps, a cursor write can also change bytes serving as a link or other caller-visible data. The function supplies no transaction, rollback, restoration, or preservation of the original cursor value.

No named global object is explicitly accessed. Caller-provided addresses may nevertheless designate global storage, so effects are not restricted to heap or stack memory.

### Ownership and lifetime

No allocation, release, reference-count adjustment, or function call is present.

Replacing an integer address in the cursor establishes neither ownership transfer nor destruction of the previous destination. It does not extend the lifetime of any visited record.

Application-level ownership obligations remain unspecified beyond the access-validity requirements.

### Invalid execution and nontermination

There is no explicit diagnostic, recoverable error result, or failure branch.

Invalid arithmetic or memory access has no portable outcome established here. In particular, the function does not promise an exception, signal, preserved cursor, or recoverable partial result.

Some cursor writes precede later link reads. If a later read is invalid, that ordering alone does not guarantee an observable post-failure cursor value.

Nontermination is distinct from invalid access. A traversal can continue indefinitely while every access remains valid, including through a nonzero descent cycle or indefinitely successful upward relationships.

## Acceptance examples

These examples are conditional deductions from static evidence, not runtime observations.

Unless an example says otherwise, assume stable link storage, a disjoint cursor cell, valid address arithmetic and conversions, and readable required locations. A, B, C, and D denote distinct nonzero address values. All stated relationships must be simultaneously representable in memory.

### One descent destination

The cursor contains A. A’s branch link is B, and B’s descent link is zero.

**Required:** B is installed before its descent link is read. Normal completion leaves B in the cursor. There is exactly one cursor write; zero is never installed. A’s upward link is not required.

### Several descent destinations

A’s branch link is B. B’s descent link is C, C’s descent link is D, and D’s descent link is zero.

**Required:** Cursor installations occur in the order B, C, D. Each precedes the corresponding descent-link read. The final cursor value is D.

Writing only D would preserve the stable-storage result but not the established update behavior.

### Immediate upward replacement

The cursor contains A. A’s branch link is zero and its upward link is B. B’s branch link differs from A.

**Required:** B fails the reciprocal relationship and is not installed as an intermediate destination. The closing relationship compares A’s zero branch link with nonzero B and requires installation of B.

B’s upward link is not needed.

### Several accepted upward destinations

The relationships are:

| Record | Branch link | Upward link |
|---|---|---|
| A | Zero | B |
| B | A | C |
| C | B | D |
| D | A value other than C | Not required |

The cursor initially contains A.

**Required:** B and C are accepted and installed. D fails the next reciprocal relationship. The closing relationship compares C’s branch link, B, with D and requires installation of D.

The complete write sequence is B, C, D. Returning with C would omit a required closing update.

### Closing replacement suppressed

The cursor contains A. A’s branch link is zero and its upward link is B. B’s branch link is A and its upward link is A.

**Required:** B is accepted and installed. The next proposal, A, fails because A’s branch link is zero rather than B. The closing relationship finds B’s branch link equal to proposal A.

No closing write occurs. The cursor remains B.

This example demonstrates the relationships without asserting that they describe a valid application-level tree.

### Zero proposal with no cursor write

The cursor contains A. Both A’s branch and upward links are zero. Additionally, the branch-link location derived from integer zero is valid and contains zero.

**Required:** The zero proposal fails its reciprocal relationship because its branch value differs from A. The closing relationship compares A’s zero branch value with the zero proposal and suppresses replacement.

Normal completion leaves A with no cursor write. Without the additional valid-access assumption, no normal outcome is established.

### A read becomes invalid after installation

A’s branch link is B, but B’s descent-link location is inaccessible.

**Established:** The required ordering places installation of B before the descent-link access.

**Not established:** Recoverable failure, rollback, or a guaranteed observable cursor value after the invalid access.

### Valid but nonterminating descent

A’s branch link is B. B’s descent link is C, and C’s descent link is B. All required storage remains valid and stable.

**Required consequence:** No terminating zero is reached. Cursor installations alternate between B and C without normal completion. No cycle error or traversal bound is supplied.
