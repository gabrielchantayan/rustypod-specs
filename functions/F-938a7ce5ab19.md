# F-938a7ce5ab19

## Purpose

F-938a7ce5ab19 performs an ordered traversal of a caller-described range of four-byte elements. It invokes one captured callback for each element, passing the element’s value rather than its address. On normal completion, it returns that captured callback address.

The range is represented by a beginning address and an exclusive ending address stored in an input descriptor. Both addresses and the callback are captured before traversal. The routine does not subsequently reread those descriptor fields or the callback source.

This is a behavioral contract based on static evidence only. The operation performed by the callback, including whether it releases resources, is unknown. Descriptions such as “destroy,” “free,” or “cleanup” are not established purposes.

## Interface

### Input descriptor

The routine accepts one input value used as the base address of a descriptor. The supplied representation treats this input as an integer participating in address calculations; operationally, it must identify accessible storage.

Two descriptor fields are relevant:

| Byte offset from descriptor base | Meaning |
|---|---|
| `0x14` / 20 | Beginning address of the element range |
| `0x18` / 24 | Exclusive ending address of the element range |

The fields are interpreted as addresses of four-byte elements. No other descriptor fields are explicitly accessed.

Each element is a four-byte word. Consecutive elements are four bytes apart. The supplied evidence does not establish whether an element is semantically an integer, a pointer, a handle, or another 32-bit representation.

The descriptor-field offsets are established. The native width of the address fields, byte order, alignment requirements, and calling convention are not independently established by the supplied evidence. In particular, the four-byte element width does not, by itself, prove that every pointer involved has that width.

### Callback input

The callback address comes from one external storage location, not from the descriptor. That address is read once before the descriptor’s range fields.

Each invocation receives one four-byte element value. The callback is not explicitly passed:

- The descriptor address.
- The current element address.
- An index or element count.
- The ending address.
- A separate context argument.

The source representation does not establish the callback argument’s signedness or machine-level argument extension.

### Output

On normal completion, the routine returns the callback address captured at entry. This is true for both empty and nonempty ranges.

The return value is not an element count, a status code, or a callback result. Any value returned by a callback invocation is unused by the visible routine.

## Behavior

### Initial reads and their order

The visible operation order is:

1. Read and retain the callback address from external storage.
2. Read and retain the ending address from descriptor offset `0x18`.
3. Read and retain the beginning address from descriptor offset `0x14`.
4. Compare the current element address with the retained ending address.

This ordering matters if reads themselves are observable or if the underlying storage can change between reads. The ending address is read before the beginning address, despite appearing later in the descriptor.

The routine does not obtain a synchronized snapshot of the descriptor as a whole. There is no visible lock, atomic protocol, consistency check, or retry. Concurrent mutation therefore has no established safety guarantee.

### Empty range

If the captured beginning and ending addresses are equal, traversal is empty:

- No element is read.
- The callback is not invoked.
- The captured callback address is returned.

The initial callback and descriptor-field reads still occur. An empty range does not bypass the need for an accessible descriptor.

Because no element is dereferenced in this case, the visible logic does not require the equal range addresses to identify a readable element. Any additional validity constraints imposed by the actual execution environment remain unknown.

### Nonempty range

For every iteration whose current address differs from the captured ending address, the routine:

- Reads one four-byte element at the current address.
- Invokes the captured callback with that value.
- After the callback returns normally, advances the current address by one four-byte element.
- Compares the advanced address with the captured ending address.

Consequently, each element is read before its corresponding callback begins. The next element is not read until the preceding callback has returned.

For a valid finite contiguous range, callbacks occur in increasing element-address order. The element at the ending address is not read or passed to the callback.

The loop’s stopping condition is address equality. There is no visible ordering test, byte-length calculation, iteration limit, or check that the ending address lies after the beginning address.

### Captured control values and live element contents

The callback address and both range endpoints are captured once. Later changes to their original storage do not change the routine’s retained traversal control values.

Element contents are different: they are read individually as traversal proceeds. There is no initial copy of the range. A callback that changes a future element can therefore affect the value delivered by a later invocation, provided the access remains valid.

The value already read for the current invocation is not reread before being passed. Changing that element’s storage during the invocation does not retroactively change the argument already delivered.

Changing the external callback source during an invocation does not redirect subsequent invocations in this traversal. Likewise, changing the descriptor’s beginning or ending field does not shorten, extend, or restart the current traversal.

These capture rules do not imply that callback side effects are otherwise isolated.

### Preconditions for normal finite completion

A straightforward valid call requires:

- Readable storage for the external callback source.
- A descriptor whose two relevant address fields can be read.
- A finite sequence of readable four-byte elements beginning at the captured beginning address and ending immediately before the captured ending address.
- A callable callback compatible with the invocation mechanism whenever the range is nonempty.
- Every invoked callback to return normally.
- Continued validity of all element storage needed by later iterations.

For such a range, the distance between the endpoints is a nonnegative multiple of four bytes, and the number of invocations is that distance divided by four.

The routine does not validate these conditions. A malformed range is not converted into an empty range or a reported error.

Address advancement is by four bytes, not one byte. The supplied evidence does not establish a portable wraparound rule for address overflow or out-of-object pointer traversal. A specification must not promise eventual termination merely because repeated fixed-width arithmetic could theoretically revisit an address.

### Abnormal execution

No explicit error result, exception handler, recovery branch, or rollback is visible.

If a required read fails, the callback cannot be invoked successfully, or a callback does not return normally, the routine has no established normal return. Any callbacks already completed may already have produced lasting effects.

The precise manifestation of invalid memory, an invalid callback address, or incompatible calling conventions depends on the execution environment and is not established here.

## Side effects

### Direct effects

The routine explicitly performs reads of:

- The external callback source.
- The descriptor’s ending-address field.
- The descriptor’s beginning-address field.
- Each visited four-byte element.

It makes no explicit writes to the descriptor, element storage, or external callback source. It does not explicitly clear processed entries, reset range fields, allocate storage, or release storage.

Its traversal cursor changes internally. That is not an update to the descriptor’s beginning field.

### Callback-mediated effects

The callback may have effects that are not described in the supplied evidence. These may include writes to elements, changes to global state, allocation, release, recursive calls, or nonlocal control transfer. None is guaranteed or prohibited by the visible routine.

In particular, the callback must not be assumed to preserve globals merely because the outer routine captures its callback address.

The routine also does not establish ownership transfer. Passing a four-byte value to the callback is evidence of argument delivery, not evidence that either party owns or releases a resource represented by that value.

If the callback invalidates storage needed for later iterations, the retained addresses do not make subsequent reads safe. No lifetime management or defensive copying is visible.

## Dependencies

### External callback source

One externally stored callback address is required. Its initialization, mutability, accessibility, and lifetime are outside the supplied evidence.

No opaque function ID for the callback target is available. It is therefore an unresolved dynamic dependency, not an identified function with an independently established contract.

### Callback target

The only established interaction with the callback is repeated invocation with one four-byte element value. Its return value does not influence visible traversal.

The callback target’s accepted value domain, ownership rules, side effects, failure behavior, and reentrancy properties are unknown.

### Execution environment

Correct execution depends on the environment’s address representation, memory-access rules, and indirect-call convention. The supplied evidence does not establish synchronization guarantees or special handling for volatile or memory-mapped storage.

## Acceptance examples

The following are conditional behavioral examples, not runtime observations.

1. **Empty range.**  
   Given readable descriptor fields containing equal beginning and ending addresses, the routine reads the callback source, then the ending field, then the beginning field. It performs no element reads or callback invocations and returns the captured callback address.

2. **Three ordinary elements.**  
   Given a valid range containing the four-byte values 7, 11, and 19, with the ending address immediately after the third element, a normally returning callback receives 7, then 11, then 19. Each value is read immediately before its invocation. The routine returns the captured callback address after the third invocation.

3. **Exclusive endpoint.**  
   Given a valid two-element range with additional readable storage at the ending address, the value stored at that ending address is not processed. Its readability does not extend the range.

4. **Future-element mutation.**  
   Given a valid two-element range, if the first callback changes the second element from 11 to 23 before returning, and the second element remains valid, the second invocation receives 23.

5. **Callback-source replacement.**  
   If the first invocation replaces the externally stored callback address with another target, subsequent invocations still use the originally captured target. Normal return also yields the original address.

6. **Descriptor mutation.**  
   If a callback changes the descriptor’s ending field, the active traversal still uses the ending address captured before the first invocation. This does not guarantee safety if the mutation accompanies invalidation of element storage.

7. **Duplicate values.**  
   Given two distinct valid elements containing the same value, the callback receives that value twice. There is no deduplication.

8. **Invalid nonempty range.**  
   If the ending address cannot be reached through valid four-byte advances from the beginning address, no successful finite traversal is guaranteed. There is no established validation error or safe early exit.

9. **Nonreturning callback.**  
   If a callback never returns, no later element is read by this invocation and the routine does not reach its normal return.

An array-like range of resource values is a plausible interpretation, but it is inferred intent rather than established behavior. No resource-release semantics are adopted by this contract.

## Evidence

Established static evidence supports:

- One callback-source read before both descriptor-field reads.
- Ending-field access at byte offset 24 before beginning-field access at byte offset 20.
- Equality-based termination against a captured exclusive endpoint.
- Four-byte element reads and four-byte traversal increments.
- One callback invocation per visited element, with the element value as its sole explicit argument.
- Element reads interleaved with callback execution rather than performed in advance.
- No explicit writes to descriptor fields or element storage.
- Return of the captured callback address after normal traversal.

No runtime tests have been performed. The acceptance examples state consequences of the visible operations under their stated preconditions; they do not assert observed execution results.
