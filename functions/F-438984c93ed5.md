# F-438984c93ed5

## Purpose

F-438984c93ed5 conditionally delegates an operation using a context, a bounded 32-bit selector, and a caller-supplied output region. It initializes a leading 16-bit output field, obtains a bound through the context, and rejects selectors outside that bound. Eligible selectors trigger preparation and resolution dependencies. Successful resolution leads to a final dependency call.

After the final dependency returns normally, the function writes the selector divided by two, rounded down, into the leading output field and returns the dependency’s 32-bit result unchanged.

The domain meanings of the selector, context, resolved object, and trailing output are not established. The selector is not explicitly passed to any dependency; its visible uses are eligibility checking and calculation of the leading output field.

This contract separates established static behavior, derived consequences, inferred intent, and unresolved requirements. No runtime tests have been performed.

## Behavior

### Initial write and context acquisition

The first established memory operation is a 16-bit zero store at the output address. The null check follows that store.

For a non-null output address, the function calls F-8ff48652068d without explicit arguments. Its result supplies the context address used by subsequent reads. There is no visible validity check on this result before it is used.

The context supplies an initial object address through a 32-bit read at offset `0xF58`. This address is retained for the later resolver call.

The bound is determined as follows:

- A zero initial object address produces a bound of zero without a nested-object read.
- A nonzero initial object address causes a 32-bit address read at object offset `0x40`, followed by an unsigned 16-bit read at offset `0x2E` from that nested address.

The bound is zero-extended to 32 bits, giving a possible range of 0 through 65,535.

The initial object’s zero value is explicitly handled. Invalid nonzero object addresses, invalid nested addresses, and an invalid context address have no visible recovery path.

### Eligibility

A selector is eligible only when:

- Its signed 32-bit interpretation is nonnegative.
- Its unsigned value is strictly less than the acquired bound.

Equality with the bound is rejected. A bound of zero rejects every selector.

Because the bound cannot exceed 65,535, every eligible selector lies between 0 and 65,534 inclusive. The unsigned comparison already excludes every selector whose high bit is set, independently of the explicit signed check.

For a rejected selector:

- The function returns `0xFFFFFFCE`.
- It does not call F-94b6eb7b70a5, F-f8ec0897aceb, or F-5ef10d079522.
- It makes no further direct write to the leading output field.

F-8ff48652068d has already run. Its effects are not constrained by this body, so the initial zero store alone does not prove the field’s value at return.

### Preparation and resolution

For an eligible selector, the function reads a 32-bit value from context offset `0xF60` and passes it as the sole explicit argument to F-94b6eb7b70a5. The supplied body does not use that dependency’s return value.

It then calls F-f8ec0897aceb with:

1. The initial object address retained from the earlier read at context offset `0xF58`.
2. The integer value 1.

The initial object address is not reacquired after preparation. Consequently, changing the context’s `0xF58` field during preparation does not, by itself, change the address explicitly passed to the resolver.

If F-f8ec0897aceb returns zero, the function reads the opaque static return value and returns it. No final dependency call or selector-derived completion store occurs.

A nonzero resolver result is used as an object address for further reads. Beyond this zero/nonzero distinction and subsequent address use, the result’s semantic meaning and ownership are unknown.

### Final dependency arguments

After successful resolution, F-5ef10d079522 receives four explicit arguments:

| Argument | Established formation |
|---|---|
| First | The 32-bit value reread from context offset `0xF60`, with `0xC0` added. |
| Second | A 32-bit value at offset `0x28` from an intermediate address obtained by a 32-bit read at resolved-object offset `0x20`. |
| Third | The caller’s output address advanced by two bytes. |
| Fourth | An address identifying local stack storage. |

The first argument uses a fresh read of context offset `0xF60`, after preparation and resolution. It need not be based on the value previously passed to F-94b6eb7b70a5.

The caller dereferences the resolved object and its intermediate address while forming the second argument. Those accesses must succeed to reach the final dependency. The first argument is different: the caller forms and passes the sum but does **not** visibly dereference that resulting value.

Accordingly, this call site does not establish that the first argument must designate valid storage. It also does not establish that an address-shaped result involving machine wraparound would necessarily be rejected. Those requirements depend on F-5ef10d079522.

The supplied representation treats the reread value and addition as signed 32-bit arithmetic. If the mathematical sum lies within the signed 32-bit range, the represented addition is unambiguous. Outside that range, language-level signed-overflow semantics do not establish a defined wrapped result. Conversely, the representation alone does not prove what the underlying machine execution does in that case. A modulo-\(2^{32}\) result may be described only conditionally, if machine wraparound is independently established.

The memory-derived arguments are obtained before entry into F-5ef10d079522. Their relative evaluation order is not established by the supplied representation.

No initialization of the addressed stack storage is visible before the call. Its contents are not visibly inspected afterward. Its extent, access direction, and purpose remain unknown.

### Completion store and return

After F-5ef10d079522 returns normally, the function writes a selector-derived value to the leading 16-bit output field, regardless of the dependency’s returned bit pattern.

The calculation uses a 32-bit unsigned left shift by 15 followed by a logical right shift by 16, then a 16-bit store. Over the eligible selector range, this is exactly:

\[
\left\lfloor \frac{\text{selector}}{2} \right\rfloor
\]

The reachable output range is 0 through 32,767. In particular, the largest eligible selector, 65,534, produces 32,767.

The function then returns the final dependency’s 32-bit result without interpreting it. A result that conventionally denotes failure still leads to the completion store, provided the dependency returned normally and the store succeeds.

## Side effects

### Direct writes

The supplied body establishes two direct caller-region writes:

1. A leading 16-bit zero store at entry.
2. A leading 16-bit completion store after normal return from F-5ef10d079522.

The completion store occurs after any synchronous dependency activity and therefore replaces any value that the dependency may have placed in that leading field, assuming the field remains writable.

The dependency receives an address two bytes beyond the leading field. This identifies the supplied address, not a proven boundary on all of its memory effects.

On early-return paths, the function makes no direct leading-field store after initialization. That does not establish that the field remains zero: dependency effects and aliasing remain unconstrained.

### Read and call ordering

The established path order is:

1. Initial leading-field store.
2. Null decision.
3. Context acquisition.
4. Initial object read and any required nested bound reads.
5. Eligibility decision.
6. Preparation argument read and preparation call.
7. Resolver call.
8. On resolution success, final-argument reads and final call.
9. On normal final-call return, completion store and return.

The initial object address and bound are obtained before preparation. The context-associated value at `0xF60` is not held constant across all calls; it is read again for the final invocation.

On resolver failure, the static return value is read after the resolver call. The supplied body does not establish that preceding dependencies preserve that storage.
