# F-9d122d3a77c6

## Purpose

F-9d122d3a77c6 modifies a counted sequence of fixed-size records stored within a caller-supplied memory region.

A negative selector clears two metadata fields without clearing record storage. A nonnegative selector scans the active sequence and, upon finding a matching record, replaces it with the current last active record and reduces the active count.

This is an unordered removal operation, but it is **not a guaranteed remove-all operation**: after a replacement, scanning advances to the next index without examining the replacement at the current index. Matching records can therefore remain active.

These behaviors are established by static inspection of the supplied representation. The intended application-level meanings of the records and metadata are unknown.

## Interface

### Inputs

The function has two inputs:

- **Storage base:** a value represented as a 32-bit integer and used as the base address of mutable storage.
- **Selector:** a signed 32-bit integer. Its sign selects between metadata clearing and record scanning.

There is no explicit capacity, storage length, allocator, callback, or error-output parameter.

### Storage layout

Offsets below are byte offsets from the storage base.

| Offset | Width | Observed role |
|---|---:|---|
| `0x58` | 4 bytes | Signed active-record count |
| `0x5c` | 4 bytes | Secondary metadata field |
| `0x60` onward | 16 bytes per record | Contiguous record storage |

For zero-based record index \(i\), the record begins at offset \(0x60 + 16i\).

Each record consists of four consecutive 4-byte words:

| Record-relative offset | Observed interpretation |
|---|---|
| `0x00` | Signed 32-bit key compared with the selector |
| `0x04` | Opaque 32-bit payload |
| `0x08` | Opaque 32-bit payload |
| `0x0c` | Opaque 32-bit payload |

The payload words are copied without arithmetic or semantic interpretation. Their types, internal encodings, and possible ownership significance are unknown.

The secondary field receives zero on the clearing path and the current count after every successful removal. Its broader meaning is not established. In particular, the function does not ensure that it equals the count when no removal occurs.

### Output

The function has no explicit return value. Its observable result consists of memory reads and writes.

There is no explicit success indicator, removal count, not-found result, or reported validation failure.

### Preconditions

For a defined, ordinary use of the clearing path, both metadata locations must be writable.

For the scanning path:

- The count location must be readable and writable.
- Every record key reached by the scan must be readable.
- A successful match requires the complete current last active record to be readable, the matched record to be writable, and the secondary metadata field to be writable.
- Address calculations must identify valid storage in the execution environment.
- For predictable single-threaded behavior, other actors must not modify the count or relevant record storage during execution.

The supplied representation does not establish an address-space model, alignment requirements, storage capacity, or behavior for invalid addresses. These requirements cannot be reduced to a complete allocation-size check from the function alone.

## Behavior

### Negative selector: metadata clearing

When the selector is negative, the function performs these writes in order:

1. Writes a 4-byte zero to offset `0x58`.
2. Writes a 4-byte zero to offset `0x5c`.
3. Returns.

This path does not inspect the previous count and does not read or write record contents.

The clearing operation is therefore logical rather than physical: previously stored records remain in memory, but the active count becomes zero.

Every negative signed 32-bit selector takes this path, including the minimum signed 32-bit value. No selector negation or magnitude calculation is involved.

### Nonnegative selector: forward scan

The scan starts at record index zero.

Before each candidate record is inspected, the function reads the signed count at offset `0x58` and tests whether the current index is less than that count. Consequently:

- A count of zero causes no record access.
- A negative count also causes no record access.
- The loop uses the current count, not a count snapshot taken at entry.

For an admitted index, the function reads that record’s first 4-byte word and compares it with the selector as a signed 32-bit value.

If the key does not match, the function makes no metadata or record writes for that iteration. It advances the index by one and repeats the count test.

If the key matches, the function performs the replacement procedure below and then advances the index by one.

### Matching-record replacement

For a match, the observable memory-access order in the supplied representation is:

1. Read the count again.
2. Subtract one from that value.
3. Write the reduced count to offset `0x58`.
4. Use the reduced count as the index of the source record: the former last active record.
5. Read that source record’s payload word at relative offset `0x04`.
6. Read its payload word at relative offset `0x08`.
7. Read its payload word at relative offset `0x0c`.
8. Read its key at relative offset `0x00`.
9. Write that key to the matched record’s relative offset `0x00`.
10. Write the three previously read payload words to the matched record, in increasing offset order.
11. Read the count at offset `0x58` again.
12. Write that value to offset `0x5c`.

The count update therefore precedes the record-copy reads and writes. The secondary metadata update follows the record copy.

These accesses are not presented as a transaction. The supplied representation establishes no atomicity, synchronization, memory barriers, or rollback.

The read order is also not a simple increasing-address traversal of the source record: the three payload words are captured before the key is read.

### Scan advancement and retained matches

After a successful replacement, the next candidate index is the previous candidate index plus one.

The function does not:

- Restart scanning from the beginning.
- Recheck the newly copied record at the same index.
- Hold the index constant after shrinking the sequence.
- Continue until it has proved that no matching key remains.

A matching key copied from the last active record can survive because it is placed at an index the scan has already passed.

An additional matching record can also cease to be considered simply because the active count has decreased before the next loop test.

Thus, even with stable, valid storage, the strongest general description is a **single forward scan with a shrinking active bound and last-record replacement**, not removal of every matching record.

### Last-record matches

When the matched record is already the last active record, source and destination refer to the same record.

The function still reduces the count, performs the source reads, writes all four words back to that record, and updates the secondary metadata field. There is no special case that suppresses the self-copy.

The removed record’s bytes remain in storage outside the resulting active range.

### Integer widths and arithmetic

The count, selector, record key, and loop index are represented as signed 32-bit integers. Each record-copy word is 32 bits wide, and the stride is 16 bytes.

Under stable metadata and valid storage, an admitted iteration has a nonnegative index strictly below a positive count. A matching iteration can therefore reduce that positive count by one without signed underflow.

Address calculations include the base value, the index multiplied by 16, and fixed offsets. The supplied representation does not establish whether overflowing address calculations wrap, trap, or have some other execution-level consequence. This contract does not promise modular address arithmetic.

No byte order is established by the supplied text. Word-level comparison and copying do not require assigning a byte order in this contract.

## Side effects

### Metadata

- A negative selector writes zero to both metadata fields.
- A successful match reduces the active count by one.
- After each successful match, the secondary field receives a fresh read of the active count.
- A nonnegative selector with no matches leaves both metadata fields unchanged.
- A nonpositive initial count with a nonnegative selector leaves both metadata fields unchanged.

With stable storage, the secondary field equals the final count whenever at least one match is processed. Without a match, any preexisting discrepancy between those fields is retained.

### Records

Each processed match overwrites the matched record with all four words of the former last active record. This can change active-record ordering.

The function does not erase the former last record, clear unused capacity, or scrub payload data. It performs no general compaction that preserves order.

No record writes occur on the negative-selector path or during unmatched scan iterations.

### Ownership and resources

There are no explicit allocation, release, destruction, or reference-count operations.

The function does not interpret payload words as pointers. If those words represent resources in a larger system, this function alone does not establish how displaced payloads are released, how copied payloads are owned, or whether stale copies outside the active range are significant.

The caller retains responsibility for the validity and lifetime of the storage. No ownership transfer is expressed by the interface.

## Acceptance examples

These examples are conditional expectations derived from static inspection, not runtime test results. Unless stated otherwise, they assume valid storage, stable metadata, representable address calculations, and no concurrent mutation. Lists show active record keys; payloads travel with their complete records.

### Negative selector clears metadata only

Given:

- Selector `-1`
- Count `3`
- Secondary metadata `17`
- Active keys `[4, 5, 6]`

Expected result:

- Count becomes `0`.
- Secondary metadata becomes `0`.
- Record bytes remain unchanged.
- The count write precedes the secondary-field write.

The same branch applies to every other negative selector.

### Zero count does not synchronize metadata

Given selector `4`, count `0`, and secondary metadata `17`:

- No record is read.
- Count remains `0`.
- Secondary metadata remains `17`.

### Negative count is not repaired by a nonnegative selector

Given selector `4`, count `-2`, and secondary metadata `17`:

- The first loop condition fails.
- No record is accessed.
- Both metadata fields retain their values.

This is observed behavior, not evidence that negative counts are valid application state.

### No match preserves metadata and records

Given selector `9`, active keys `[1, 2, 3]`, count `3`, and secondary metadata `17`:

- Keys are examined in index order.
- No record or metadata writes occur.
- Count remains `3`.
- Secondary metadata remains `17`.

### Interior removal uses the last record

Given selector `2` and active records with keys `[1, 2, 3, 4]`:

- The record with key `2` is replaced by the complete record with key `4`.
- The resulting active keys are `[1, 4, 3]`.
- Count and secondary metadata are both `3`.
- The original final slot still contains its prior bytes outside the active range.

### A copied matching record can survive

Given selector `7` and active keys `[7, 8, 7]`:

- The first match reduces the count to `2`.
- The former last record, also keyed `7`, replaces the first record.
- Scanning advances to index one, whose key is `8`.
- The resulting active keys are `[7, 8]`.
- Count and secondary metadata are both `2`.

A contract requiring all matching keys to disappear would reject behavior that this function actually exhibits.

### Repeated keys can produce multiple removals without removing all matches

Given selector `7` and active keys `[7, 7, 7]`:

- The match at index zero reduces the count to `2`.
- The match at index one reduces it to `1`.
- The next index fails the reduced-bound test.
- One active record with key `7` remains.
- Count and secondary metadata are both `1`.

### Single matching record performs a self-copy

Given selector `5` and one active record keyed `5`:

- Count becomes `0`.
- The record’s four words are read and written back to the same record.
- Secondary metadata becomes `0`.
- The record bytes remain present outside the empty active range.
