# F-a0863aef0797

## Purpose

F-a0863aef0797 resolves a record, compares a proposed two-word position against a two-word boundary, and either advances directly or invokes a dependency before updating state. It reports a 32-bit quantity through caller-provided storage and returns a 32-bit status.

The established behavior has two successful paths:

- A proposed position at or below the boundary causes a direct advance by the requested amount.
- A proposed position above the boundary causes a helper call. On helper success, the function selects an increment, updates the saved record, reports the helper’s low result word, and calls a final dependency.

Two address sources must remain distinct: an address saved immediately after lookup, and a writable lookup-output slot that is read again for the final dependency call. The record explicitly updated after helper success need not be the record passed to that final dependency.

A cursor-like or allocation-related purpose is **inferred intent**. Application-level meanings, dependency ownership rules, and invariants restricting helper results are not established.

### Lookup-output slot and saved address

The function provides F-4e6cefe281de with the address of an internal, 32-bit lookup-output slot. Immediately after the lookup returns, it copies that slot’s contents into a separately saved address, before testing the lookup status.

These are distinct state:

- **Lookup-output slot:** writable storage whose address has escaped to F-4e6cefe281de.
- **Saved address:** the value copied from that slot immediately after lookup.

Initial comparison, helper-argument preparation, and the direct path use the lookup-output slot as their record-address source. Explicit updates after helper success use the saved address. The final dependency’s argument is obtained by reading the lookup-output slot again after those updates and the caller-result write.

There is no visible intervening call between the initial copy and the direct path. Nevertheless, slot immutability is not an established dependency contract. In particular, F-4e6cefe281de could retain access to the slot, enabling a later dependency to change its contents.

## Behavior

### Lookup and failure

F-4e6cefe281de receives, in argument order:

1. The context address displaced by `0x3EC`.
2. The lookup token.
3. The address of the lookup-output slot.

After the slot value is saved, a zero lookup status causes return `3`. No explicit caller-result write, record-field update, or later dependency call occurs on this path. This does not undo effects of the lookup dependency.

A nonzero status permits record access without independent validation of the supplied address.

### Proposed position and branch decision

For stable record contents, let \(P_L,P_H\) be the position words, \(B_L,B_H\) the boundary words, and \(N\) the request. All words are 32 bits.

The proposed position has:

\[
Q_L=(P_L+N)\bmod 2^{32},
\]

\[
Q_H=(P_H+c)\bmod 2^{32},
\qquad
c=
\begin{cases}
1 & P_L+N\ge 2^{32},\\
0 & \text{otherwise}.
\end{cases}
\]

The comparison is unsigned: compare high words first, then low words when the high words match. The helper path requires the proposed position to be **strictly greater** than the boundary. Equality takes the direct path.

The full position addition wraps modulo \(2^{64}\). There is no separate overflow rejection or saturation. A wrapped proposal may therefore compare below the boundary even though the mathematical, unbounded sum exceeds it.

The field accesses are not an atomic snapshot. The representation shows a position-low read for the proposed low word, then a boundary-high read, followed by position-high and another position-low read for the proposed high word and carry. When the high words match, the boundary low word is read for comparison; it can be read again to exclude equality. The relative evaluation order within a single expression is not independently established.

Consequently, the formulas describe coherent, stable inputs. Concurrent or other asynchronous mutation can make separate reads observe different values. No retry or consistency check is visible.

### Direct success

When the proposal does not exceed the boundary, the function uses the lookup-output slot as the address source and performs these explicit updates in order:

1. Reads the current position low word and writes that word plus \(N\), modulo \(2^{32}\).
2. Reads and updates the position high word by the low-word carry, modulo \(2^{32}\).
3. Reads the flag byte and writes it with bit `0x80` set.
4. Writes \(N\) to the caller’s 32-bit result storage.

It then returns `0`.

The position is read again for this update rather than simply storing the earlier proposed pair. With stable state, the results coincide.

Other flag bits are preserved by the flag read-modify-write, subject to later aliasing or external mutation. The boundary-copy words are not explicitly written. Neither F-6e23bd067b9e nor F-4f50bb4f244a is called.

A zero request is not a no-op: this path still performs the position writes, sets the flag bit, and stores zero through the result address.

### Helper invocation and failure

When the proposal is strictly above the boundary, F-6e23bd067b9e receives these arguments:

1. The 32-bit field at `0x94`.
2. The embedded address at displacement `0x10`.
3. The unsigned 32-bit request.
4. A zero 32-bit word.
5. The 32-bit field at `0x104`.
6. An address for two adjacent 32-bit result words.

The record-address source for preparing these arguments is the lookup-output slot, not a post-helper reload of the saved address. Argument numbering does not establish the evaluation order of the individual argument reads.

A nonzero helper status immediately causes return `0x11`. The function has not yet performed its explicit success-path position writes, boundary copies, flag update, caller-result write, or final dependency call.

This is not rollback: helper-side changes to records, the lookup-output slot, globals, or other accessible storage are not reversed.

### Increment selection after helper success

A zero helper status causes consumption of two adjacent 32-bit result words, denoted \(R_L\) and \(R_H\).

Define:

\[
b=
\begin{cases}
1 & R_L<N \text{ under unsigned comparison},\\
0 & \text{otherwise}.
\end{cases}
\]

The selected increment is the helper pair exactly when:

\[
\operatorname{signed32}(R_H)<b.
\]

Otherwise, the selected increment is the pair with low word \(N\) and high word zero.

This is not an unconditional unsigned minimum:

- If \(R_H=0\), the helper pair is selected exactly when \(R_L<N\).
- If \(R_H\) is positive under signed 32-bit interpretation, the requested pair is selected.
- If the high bit of \(R_H\) is set, its signed interpretation is negative and the helper pair is selected regardless of the low-word comparison.
- With \(R_H=0\) and \(R_L=N\), the requested pair is selected, although both pairs have the same numerical value.

Both helper result words must have defined contents for this selection and subsequent arithmetic to have a determinate result. The helper’s initialization guarantees are not supplied.

### Helper-success updates and final call

After increment selection, the saved address—not the current lookup-output slot—identifies the record for all explicit record writes.

The function performs the following ordered effects:

1. Reads the saved record’s current position low word and writes its sum with the selected low word, modulo \(2^{32}\).
2. Updates that record’s position high word by adding the selected high word and low-word carry, modulo \(2^{32}\).
3. Reads its boundary low word at `0x28` and writes that value to `0x30`.
4. Reads its boundary high word at `0x2C` and writes that value to `0x34`.
5. Reads its flag byte and writes it with bit `0x80` set.
6. Writes \(R_L\) to the caller’s result storage.
7. Reads the lookup-output slot again and passes its then-current address value to F-4f50bb4f244a.
8. Returns `0` if the final call returns normally.

The position and boundary values consumed here are read after the helper returns. Earlier values are not restored, and the branch decision is not recomputed.

The reported quantity is always \(R_L\), not necessarily the selected increment’s low word. The reported amount and actual position increment can differ.

Changing the lookup-output slot during the helper does not redirect these explicit record updates: they remain directed to the saved address. It can, however, redirect the final call. No equality check, validation, or reconciliation of the two addresses occurs.

## Side effects

### Explicit memory effects

Direct success writes both position words, the flag byte, and the caller’s result.

Helper success writes those fields in the saved record, additionally copies both boundary words, and then calls the final dependency with the separately reloaded slot value.

The flag update precedes the caller-result write. On helper success, all these explicit writes precede the final call. They do not establish the state after that call, because its mutation behavior is unknown.

Aliasing can change the apparent outcome. If result storage overlaps a position word, the result write can overwrite the completed position update. If it overlaps the flag’s containing storage, it can replace the flag byte after bit `0x80` was set. Any such modification occurs before the final dependency is invoked.

### Dependency access and lifetime

The lookup-output slot’s address is exposed to F-4e6cefe281de. Retention or later indirect modification is not prohibited by any supplied contract. There is no explicit restoration of the slot after F-6e23bd067b9e.

The saved address is a value copy, not evidence of acquired ownership or a retained lifetime. If a dependency invalidates the saved record, the subsequent explicit accesses are not protected by any visible lifetime check.

No explicit allocation, release, ownership transfer, locking, or rollback operation appears in this function. Dependencies may nevertheless perform such operations. F-4f50bb4f244a receives the slot’s current value; whether it mutates, retains, releases, or publishes the addressed object is unknown.

No synchronization or atomic multiword update is established.

## Acceptance examples

These are conditional static predictions, not executed tests. Unless an example states otherwise, assume valid nonoverlapping storage, initialized dependency outputs, stable relevant state, and normally returning dependencies.

1. **Lookup failure.** If F-4e6cefe281de returns zero, the result is `3`. Neither later dependency is called, and this function performs no explicit caller-result write.

2. **Below the boundary.** Position `40`, boundary `100`, and request `12` produce direct success: position `52`, flag bit `0x80` set, reported quantity `12`, status `0`. Boundary-copy words are explicitly untouched.

3. **Equality.** Position `90`, boundary `100`, and request `10` take the direct path. Reaching the boundary does not invoke the helper.

4. **Low-word carry.** Position high word `2`, low word `0xFFFFFFFE`, request `3`, and a sufficient boundary produce high word `3`, low word `1`, and reported quantity `3`.

5. **Helper failure.** Position `95`, boundary `100`, and request `10` invoke the helper. A nonzero helper status produces `0x11` without explicit success updates. Helper-side changes are not rolled back.

6. **Smaller helper result.** For that crossing request, helper success with pair `(high 0, low 4)` advances the saved record by `4`, copies its post-helper boundary, sets its flag, reports `4`, and invokes the final dependency.

7. **Larger helper result.** With request `10` and helper pair `(high 0, low 15)`, the selected increment is `10`, but the reported quantity is `15`.

8. **Signed-negative high word.** Helper pair `(high 0xFFFFFFFF, low 4)` is selected regardless of the request’s low-word comparison. The increment is `0xFFFFFFFF00000004` modulo \(2^{64}\), not merely `4`.

9. **Full-width wrap.** Position `0xFFFFFFFFFFFFFFFF`, request `1`, and boundary zero produce a wrapped proposal of zero. Equality selects direct success, storing position zero.

10. **Zero request above the boundary.** A position already above the boundary still selects the helper path when the request is zero.

11. **Redirected final target.** Suppose lookup supplies address A and it is saved. The helper succeeds with `(high 0, low 4)` and changes the lookup-output slot to address B. With request `10` and an initially crossing proposal, the explicit updates apply to A, the caller receives `4`, and F-4f50bb4f244a receives B. There are no explicit record-field updates to B merely because the slot changed.

12. **Post-helper field changes.** If the helper changes A’s position and boundary but leaves A valid, the saved-record updates use those changed fields. The initial comparison is not repeated, and the copied boundary is the post-helper boundary.
