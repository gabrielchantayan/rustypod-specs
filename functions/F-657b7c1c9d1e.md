# F-657b7c1c9d1e

## Purpose

F-657b7c1c9d1e traverses records through two address-bearing fields and destructively links processed records through one of those fields. A field in a caller-supplied context holds the destination head.

For each nonzero current record, the function recursively processes the value at record offset 12, reads the continuation at record offset 8, copies the current destination head into record offset 12, and makes the current record the destination head. It then continues using the saved offset-8 value.

This access and insertion order is established by static evidence. Interpreting the input as a binary tree, the destination as a free list, or the operation as reclamation is inferred intent. No allocation, deallocation, destruction, or ownership transfer is established.

A final chain containing all processed records followed by the original destination chain requires additional caller assumptions. In particular, the original destination chain must not contain any processed record. Without that separation, the writes can produce a cycle even when the traversal input itself is a single acyclic record.

- **Context address:** Identifies storage containing a destination-head field beginning at byte offset 4.

## Behavior

### Empty input

If the initial record address is zero, the function returns without reading or writing either object.

A context address that would be invalid to dereference therefore does not prevent the empty path from returning. This does not make that address valid for nonempty execution.

### Per-record access order

For each nonzero current record, the established observable memory-access order is:

1. Read the four-byte value at current-record offset 12.
2. Invoke F-657b7c1c9d1e recursively with the same context address and that value as the initial record.
3. After the recursive invocation returns, read the integer-width value at current-record offset 8.
4. Read the four-byte destination head at context offset 4.
5. Write that head value to the current record’s four-byte offset-12 field.
6. Write the current record address to the integer-width field at context offset 4.
7. Continue within the current invocation using the continuation saved from offset 8.

A zero continuation ends the current invocation.

These statements describe program-level access order. They do not establish atomicity, memory barriers, or the sequence of hardware transactions.

### Values are read after recursive processing

The continuation at offset 8 is not saved before recursion. If recursive writes affect that storage through aliasing, the caller uses the value present after the recursive call returns.

The destination head is also read after recursion. Recursive insertions can therefore change the head that the current record receives as its new link.

Conversely, the continuation is saved before either insertion write. If those writes overlap the continuation’s storage, the next iteration still uses the saved value rather than rereading that storage.

The original offset-12 traversal target is consumed before recursion. The function does not reread that field afterward to choose another recursive target for the same insertion.

### Insertion order under tree assumptions

Assume:

- Address and link representations are compatible.
- The traversal describes a finite tree with no repeated record.
- Relevant record storage is nonoverlapping, and the context field does not overlap it.
- No outside mutation changes the accessed storage.
- Every reached access is valid.

Under these conditions, insertion order is:

- All records reached through the offset-12 subtree.
- The current record.
- All records reached through the offset-8 subtree.

The same rule applies recursively within each subtree. Offset-12 traversal uses recursive calls; offset-8 traversal advances the current invocation’s loop.

This insertion-order statement does not require the destination head to identify a disjoint chain. Destination overlap can corrupt the resulting links without changing insertion order under these traversal assumptions.

### Conditions for a final-chain claim

Each insertion places the previously read head value in the current record and then publishes that record as the head. To conclude that the final result is a well-formed chain containing the processed records followed by the original destination chain, additionally assume:

- The original destination chain is finite, acyclic, and well formed under the same link representation.
- No record in that original chain is processed by this invocation.
- Destination-chain record storage does not overlap processed-record storage or the context field.

With these assumptions, following final offset-12 links visits processed records in reverse insertion order, then visits the original destination chain unchanged. A zero original head gives an empty original suffix.

The function itself does not traverse the original destination chain merely because it is the destination. A nonzero original head can be copied without being dereferenced. Thus, a readable, well-formed original chain is required for the final-chain interpretation, not necessarily for the function’s own accesses.

### Destination overlap

Separation between distinct record objects is not the same as separation between traversal membership and destination membership. A processed record can already be the destination head even when all object storage is otherwise nonoverlapping.

For example, if the initial record has both traversal fields zero and is also the initial destination head, the function copies that record’s own address into its offset-12 field. Execution then returns normally, leaving a self-cycle.

More generally, inserting a record already present in the destination chain can create a cycle or invalidate the interpretation of the original chain as an unchanged tail. No membership or overlap check prevents this.

### Termination and exceptional execution

There is no cycle detection, visited-record set, traversal limit, or explicit recursion-depth limit.

A finite, valid tree satisfying the stated nonaliasing assumptions terminates. Arbitrary cyclic, shared, or overlapping structures do not receive that guarantee. Earlier writes may alter fields encountered later.

Offset-12 depth determines recursive nesting; offset-8 continuation is iterative within each invocation. Stack exhaustion is possible for sufficiently deep recursion, but its exact manifestation is environmental and unspecified.

## Side effects

### Direct writes

Each completed insertion performs two direct stores, in order:

- Replace the current record’s four-byte offset-12 field with the destination head just read.
- Replace the context’s integer-width offset-4 field with the current record address.

There is no direct store targeting the current record’s offset-8 field. That storage can nevertheless change through overlap with another write target.

Replacing offset 12 destroys that record’s original recursive traversal link. The original input structure is not preserved.
