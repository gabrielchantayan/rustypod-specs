# F-6ee71f0e99b3

## Purpose

F-6ee71f0e99b3 produces a contiguous sequence of 16-bit destination pixels while traversing source rows in reverse order. A dependency-derived value is calculated once per output row and controls pixel processing.

A byte read during setup selects one of two paths:

- **Zero:** transform each pixel using inline packed-integer operations.
- **Nonzero:** obtain each output pixel from F-9f966b076dec.

The function has no explicit return value or status result. Its observable behavior consists of memory accesses, destination writes, dependency calls, and any effects those dependencies produce.

**Established static evidence:** reverse-row source traversal, forward destination traversal, descriptor access widths, call order, one-time mode selection, and the packed-integer transformation.

**Inferred intent:** processing RGB565-like pixels with a row-dependent intensity or blend progression. Neither that interpretation nor a valid parameter range is established by the supplied body.

## Interface

### Descriptor arguments

The function receives two descriptor addresses. The supplied representation uses 32-bit addresses and integers, with 16-bit pixel elements.

| Descriptor | Byte offset | Access and role |
|---|---:|---|
| Destination | 0 | 32-bit address loaded as the initial destination pixel pointer |
| Destination | 6 | Unsigned 16-bit read for setup; later signed 16-bit read for the outer-loop counter |
| Source | 0 | 32-bit address used to calculate the initial source pixel pointer |
| Source | 4 | Unsigned 16-bit width for initial positioning and subsequent row rewinds |
| Source | 4–7 | 32-bit read at each row’s start, narrowed to a 16-bit inner-loop counter |
| Source | 6 | Unsigned 16-bit height for initial positioning |

For the inner-loop count, the 32-bit source-descriptor read is converted to a signed 16-bit value. Its low 16 bits supply the count in the represented layout. The descriptor must therefore support the full four-byte access, not merely a two-byte width access.

No destination width or destination stride is consulted. Every completed pixel iteration writes the next contiguous 16-bit destination element.

The two offset-6 fields are independent:

- The destination field supplies a setup argument and, through a later read, the number of output rows.
- The source field determines the initial source row.

There is no visible requirement check that these fields match.

## Behavior

### Setup and observable sequencing

Setup occurs before checking whether the eventual output-row count is zero.

The established sequence is:

1. Capture the initialization parameter.
2. Load the destination pixel address.
3. Calculate the initial source pixel address from the source base, width, and height.
4. Read the destination offset-6 field as an unsigned 16-bit value.
5. Call F-f79d2cf69ee3 with a four-byte temporary’s address and a fresh read of the initialization parameter. Retain the return value.
6. Explicitly initialize a separate four-byte temporary to zero.
7. Call F-f990848a8c92 with that zero-initialized temporary’s address and the retained return value. Store its return value in another four-byte temporary.
8. Call F-edaa79d0c3ee with the address of that result temporary and the previously read destination field shifted left by 16 bits. Retain the return value as the row increment.
9. Call F-f79d2cf69ee3 with the running-state temporary’s address and the initialization parameter captured at entry. Ignore this call’s return value.
10. Capture the row parameter.
11. Read the mode pointer and its pointed-to byte; select the zero or nonzero path.
12. Read the destination offset-6 field again as the outer-loop counter.

The two initialization-parameter reads are distinct. No dependency call intervenes between them, but the first setup call uses the direct read, whereas the later setup call uses the captured value.

The destination field used to derive the row increment is also distinct from the later loop-count read. Setup dependencies may affect the later value; the body does not require equality between the two reads.

The first four-byte temporary and the running-state temporary are not explicitly initialized before their addresses are passed to F-f79d2cf69ee3. Passing those addresses does not prove that the dependency writes them.

### Initial source address

The initial source address is calculated as:

\[
\text{source base} + 2W(H-1)\text{ bytes},
\]

where \(W\) and \(H\) are the unsigned 16-bit source width and height read during setup.

The height-minus-one expression is formed using 32-bit integer arithmetic. Multiplication by the explicitly unsigned width places the displacement calculation in 32-bit unsigned arithmetic. The displacement is not a checked buffer-size calculation.

For ordinary nonzero dimensions with valid address formation, this selects the first pixel of the last declared source row.

A zero source height does not suppress the calculation. With zero height and nonzero width, the displacement has the 32-bit unsigned representation of \(-2W\). Whether the resulting address is valid remains a caller/platform matter.

### Per-row behavior

For each nonzero outer-loop counter value:

1. Call F-f79d2cf69ee3 with a per-row temporary’s address and the captured row parameter. Ignore its return value.
2. Call F-785d6405556f with the current running-state value and the per-row temporary’s value. Retain its 32-bit return value as the row processing value.
3. Read four bytes at source descriptor offset 4 and narrow the result to the 16-bit inner-loop counter.
4. Process pixels until that counter reaches zero.
5. Read the source width again as an unsigned 16-bit value.
6. Rewind the current source pointer by twice that width in **16-bit elements**, equivalent to four times that width in bytes.
7. Add the retained row increment to the running state.
8. Decrement the 16-bit outer-loop counter.

The per-row temporary is not explicitly initialized before its address is passed. It is not explicitly reset between rows. Its subsequent value cannot be specified without the dependency’s behavior.

For a stable width \(W\), the pixel loop advances the source by \(W\) elements, and the rewind subtracts \(2W\) elements. The net movement is therefore one row backward.

The width used for initial positioning, the width used for a particular inner-loop count, and the width used for that row’s rewind are separate reads. Changes to the source descriptor may make them differ.

The destination pointer advances only through completed pixel iterations. It is neither rewound nor reloaded from the destination descriptor.

A zero-width row still performs both per-row dependency calls, the width reread, and the running-state update.

### Per-pixel behavior and mode stability

The mode is selected once. Later changes to the mode pointer or pointed-to byte do not trigger reselection.

For every pixel in either path:

- A 16-bit source pixel is read.
- Its output value is calculated or obtained from a dependency.
- A 16-bit destination pixel is written.
- Both retained pixel pointers advance by two bytes.
- The 16-bit inner-loop counter is decremented.

The current source pixel is read before its corresponding destination write. There is no visible row buffer or immutable source snapshot.

### Zero-mode transformation

The zero path makes no per-pixel dependency call.

The source word is partitioned using these masks:

| Mask | Packed field |
|---|---|
| `0xF800` | Upper five bits |
| `0x07E0` | Middle six bits |
| `0x001F` | Lower five bits |

The 32-bit row processing value is shifted right by eight as a signed value. Call the resulting bit pattern the **scale**. Its intended range is unknown; signed right-shift behavior for negative inputs is platform-dependent unless separately specified.

Two expanded pixel quantities are formed:

- The upper masked field shifted left eight bits, combined with the lower masked field shifted left three bits.
- The middle masked field shifted right three bits.

The scale participates in unsigned 32-bit multiplication with each quantity.

For the upper/lower quantity, retain the wrapped 32-bit product and logically shift it right eight bits. Call this result **P**.

For the middle quantity, retain the wrapped 32-bit product and mask it with `0x0000FF00`. Combine that result with P masked by `0xFFFF00FF`; call the combined word **Q**.

The destination word combines:

- Q shifted right five bits and masked with `0x07E0`;
- P bits 3–7, placed in destination bits 0–4;
- Q shifted right eight bits and masked with `0xF800`.

The final lower-field extraction discards all other P bits through 32-bit shifting and truncation. It is not a saturation operation.

All wrapping, masking, and truncation are part of the visible transformation. No validation restricts the row processing value to a nominal brightness range. Negative or large values must not be described as independently clamped channel scaling.

### Nonzero-mode transformation

For each pixel, F-9f966b076dec receives:

1. The current 16-bit source pixel value.
2. A fresh read of the global pixel parameter.
3. The 32-bit signed expression \(65536-\text{row processing value}\).

The result is narrowed to 16 bits and written to the current destination element.

The relative evaluation order of the source-pixel read and the global-parameter read within the call expression is not established. Both supply arguments to that invocation.

After the dependency returns, the destination write occurs before the next pixel’s parameter read. Consequently, a dependency’s change to the pixel parameter reaches the next call only if no intervening operation overwrites it. In particular, destination storage overlapping that parameter can overwrite the changed value.

The visible body does not establish whether F-9f966b076dec blends, clamps, scales, or performs some other operation.

### Counter and arithmetic boundaries

Both loop counters are represented as signed 16-bit values. Their continuation condition is “not zero,” not “positive.”

For initial values 1 through 32767, the corresponding number of iterations follows directly.

For bit patterns with the high bit set, the count depends on the represented narrowing behavior when decrementing past the signed minimum. Under 16-bit wrapping/narrowing behavior, the iteration count equals the original pattern interpreted as unsigned: `0x8000` gives 32768 iterations and `0xFFFF` gives 65535. Portability of that behavior is **documented_only**.

- Initial pixel pointers are retained.
- The row parameter and row increment are retained.

## Acceptance examples

### Stable two-row traversal

Given stable descriptors, width 3, source height 2, destination row count 2, valid nonoverlapping storage, normally returning dependencies, and usable temporary contents:

- Source elements 3, 4, and 5 supply the first output row.
- Source elements 0, 1, and 2 supply the second output row.

- In nonzero mode, F-9f966b076dec occurs six times in that source-element order.

### Zero output rows

If the destination count is zero at the post-setup read:

- All setup calls and the initial source-address calculation still occur.
- The mode byte is still read.
- No per-row calls, pixel reads, or destination-pixel writes occur.

This does not waive setup-time storage requirements.

### Zero source width

With a stable zero width and a positive output-row count:

- Both per-row dependency calls still occur.
- No pixels are read or written.
- Each rewind is zero.
- Running state is updated once per row.

### Zero-mode arithmetic anchors

For a row processing value of zero, every processed pixel produces zero.

For a row processing value of 65536, the shifted scale is 256 and the packed operations reproduce the original 16-bit source word.

These anchors establish neither saturation nor a general color-space model.

### Fresh parameter reads

In nonzero mode, suppose a pixel call changes the global pixel parameter and returns. The function then writes that call’s result to the destination.

The next pixel call reads the parameter again. It receives the dependency’s changed value only if no intervening modification—including that destination write—replaces it.

### Setup changes the output count

If the first destination-field read is 2, but a setup dependency changes that field to zero before its later read:

- The row-step setup argument remains `0x00020000`.
- The outer loop executes zero rows.

This example requires no assumption that the two reads agree.

### Mismatched heights

If the output-row count exceeds the source height, stable-width traversal continues backward beyond the declared source rows. There is no clipping to source height. All actual accesses still require valid backing storage.
