# F-603a395115a8

## Purpose

F-603a395115a8 performs an ordered teardown or reset of resources associated with a caller-supplied object. It invokes object-specific callbacks, passes selected object fields to two external dependencies, clears associated state, and finally clears the object’s callback-table field.

**Established behavior:** the routine makes the calls and writes described below. Several resource-like fields are explicitly set to zero after their values have been passed to a dependency. Other fields are passed by address and are not explicitly cleared by this routine.

**Inferred intent:** the combination of release-like calls, optional callbacks, and state clearing suggests object cleanup. This does not establish that any dependency frees memory, that the object itself is destroyed, or that a second invocation is safe.

## Interface

### Input and result

The routine accepts one argument: an object base address represented by a 32-bit value in the supplied representation. It has no explicit return value.

The object must provide readable and writable storage for the accesses below. The greatest fixed-offset access is a one-byte read at offset `0x304`. Thus, absent aliasing or an unusual memory layout, the fixed accesses require storage extending through that byte. A separate two-byte write uses a runtime-supplied offset and may require additional storage.

Offsets in this contract are byte offsets from the object base unless explicitly identified as callback-table offsets. Widths are exact access widths, not inferred types.

## Behavior

The following order describes this routine’s own observable accesses and calls. Dependency internals may introduce additional effects. Progress past each call assumes that call returns normally.

### 1. Capture entry state and invoke optional callbacks

The routine first reads the 32-bit context at `0x064`, then reads the 32-bit callback-table address at `0x210`. Both values are retained for later use.

If the captured table address is nonzero:

1. The table entry at `0x050` is inspected and invoked with the object base if nonzero.
2. After that invocation returns, the entry at `0x064` in the same captured table is inspected and invoked with the object base if nonzero.

The second entry is not snapshotted before the first callback. Changes to that table entry made by the first callback can therefore affect the second invocation. Changing the object’s `0x210` field does not redirect these lookups; the table base was already captured.

### 2. Process the `0x304`-controlled group

The routine reads the byte at `0x304` after the optional callbacks.

If that byte is nonzero:

- It reads the 32-bit field at `0x2f0`.
- If that field is nonzero, it calls F-840cb7b3952f with the current 32-bit context from `0x068` and the address of `0x2f0`.
- It then clears `0x2f4`, `0x2f8`, and `0x2fc`, using separate 32-bit writes in that order.

Those three clears occur even when `0x2f0` is zero and the dependency call is skipped. If the controlling byte is zero, this entire group is skipped.

The routine does not explicitly clear either `0x2f0` or the controlling byte at `0x304`.

### 3. Process the `0x2dc` group

F-840cb7b3952f is called unconditionally with the current context from `0x068` and the address of `0x2dc`.

After it returns, the routine clears four 32-bit fields in this order:

`0x2e0`, `0x2e4`, `0x2e8`, `0x2ec`.

### 4. Process the `0x090` and `0x09c` groups

F-bf7242c98d06 receives the entry-captured context from `0x064` and the current 32-bit value at `0x090`. There is no nonzero check on that value.

After the call returns, the routine clears `0x090`, then `0x08c`, each with a 32-bit write.

It next calls F-bf7242c98d06 with the same captured context and the then-current value at `0x09c`. After return, it clears `0x09c` with a 32-bit write and `0x098` with a 16-bit write.

The write at `0x098` does not itself clear bytes `0x09a` or `0x09b`.

### 5. Process the `0x1f0`, `0x2a4`, and `0x2ac` groups

The routine calls F-840cb7b3952f with a fresh read of the context at `0x068` and the address of `0x1f0`. It then clears the 32-bit field at `0x1f4`.

Next it captures the current 32-bit context at `0x068` once and uses that captured value for two successive F-840cb7b3952f calls:

1. With the address of `0x2a4`.
2. With the address of `0x2ac`.

Only after both calls return does it clear `0x2a8`, followed by `0x2b0`, using 32-bit writes.

If the first call changes the object’s `0x068` field, the second call still receives the previously captured context.

### 6. Process the `0x124`-controlled group

The routine reads the byte at `0x124` at this point, not at entry.

If it is nonzero:

1. F-bf7242c98d06 receives the entry-captured context and the current value at `0x14c`.
2. The routine clears `0x14c` with a 32-bit write.
3. F-bf7242c98d06 receives the same context and the then-current value at `0x150`.
4. The routine clears `0x150` with a 32-bit write.
5. It clears the byte at `0x124`.

Neither resource value is checked for nonzero. The second field is read only after the first call and clear, so dependency effects on `0x150` can affect the second call.

If the flag is zero, this group performs none of those calls or writes.

### 7. Process `0x21c`, the runtime-selected field, and the required callback

The routine calls F-bf7242c98d06 with the captured context and the current value at `0x21c`.

After return, it reads a global 32-bit offset value. It then:

1. Clears `0x21c` with a 32-bit write.
2. Writes a 16-bit zero at the object base plus the captured global offset.
3. Loads and invokes the callback at offset `0x034` in the entry-captured callback table, passing the object base.

There is no null check for either the captured table or this callback entry.

The global offset is read after the dependency call but before the clear of `0x21c`. The selected two-byte write is not constrained by any visible bounds or overlap check.

### 8. Process the final fields and detach the table

After the required callback returns, F-bf7242c98d06 is called successively for the then-current values at:

1. `0x014`, followed by a 32-bit clear of `0x014`.
2. `0x018`, followed by a 32-bit clear of `0x018`.
3. `0x020`, followed by a 32-bit clear of `0x020` and then a 32-bit clear of `0x01c`.
4. `0x294`, followed by a 32-bit clear of `0x294`.

All four calls use the context captured at entry. None is conditional on the resource value being nonzero.

Finally, the routine clears the 32-bit callback-table field at `0x210` and returns.

## Side effects

### Explicit state changes

The routine performs the ordered zero writes described above. These are individual writes of the specified widths, not a whole-object reset.

Fields passed by address to F-840cb7b3952f are not explicitly cleared by this routine. Their final contents depend on that dependency and any other relevant side effects.

The byte at `0x304` is not explicitly cleared. The byte at `0x124` is cleared only when its cleanup group is entered.

### Dependency-visible state

Calls observe partially processed object state. In particular:

- The optional callbacks run before any explicit clearing.
- The required callback runs after processing `0x21c` and the runtime-selected two-byte field, but before the final four resource calls.
- The callback-table field is not explicitly cleared until all calls have returned.
- The second of the paired F-840cb7b3952f calls precedes both associated metadata clears.

A later dependency may modify fields already cleared. Accordingly, a completed invocation does not establish that every previously cleared field remains zero. The final explicit write establishes a zero value at `0x210` at that point, subject to external interference.

### Ownership and failure behavior

Passing a value to F-bf7242c98d06 is not proof of ownership transfer or deallocation. Passing a field address to F-840cb7b3952f is not proof that the field is nulled or its referenced storage is released.

The routine contains no visible status checks, error return, rollback, or recovery path. Return values from calls, if any, do not influence its visible control flow. A fault, nonreturning callback, or other abnormal transfer can leave a partially processed object; later writes and calls are not guaranteed in that case.

## Acceptance examples

These are conditional contract examples, not results of executed tests.

1. **Skipped conditional groups.** If the flag bytes are zero when inspected, all calls return normally, and dependencies do not introduce overlapping mutations, neither conditional resource group is processed. The required callback and all unconditional calls still occur.

2. **Enabled group with an empty addressed field.** If `0x304` is nonzero and `0x2f0` is zero when inspected, there is no F-840cb7b3952f call for `0x2f0`. The three metadata fields at `0x2f4`, `0x2f8`, and `0x2fc` are nevertheless cleared.

3. **Zero values in the second conditional group.** If `0x124` is nonzero and both associated resource values are zero when read, both F-bf7242c98d06 calls still occur with zero second arguments. Normal progress depends on the dependency accepting those arguments.

4. **Context mutation.** If an early callback changes `0x064`, subsequent F-bf7242c98d06 calls still use the original value. If it changes `0x068`, later fresh reads of that field observe the changed value.

5. **Mutation between paired calls.** If the F-840cb7b3952f call for `0x2a4` changes `0x068`, the immediately following call for `0x2ac` retains the context captured before the first call.

6. **Null callback table.** A zero table value at entry skips the optional callbacks but does not provide a successful empty-object path. The later required callback lookup still uses that zero captured base.

7. **Required callback changes late resources.** If the required callback changes `0x014`, the following resource call receives the changed value, because that field is read afterward.

8. **Narrow clear.** With nonoverlapping runtime-selected storage and no dependency mutation, clearing `0x098` zeroes its two bytes without clearing the adjacent two bytes at `0x09a` and `0x09b`.

## Uncertainties

The following are **documented_only**:

- The object’s semantic type, allocation size, and alignment requirements.
- Dependency ownership rules and whether any call actually releases memory.
- Callback and dependency behavior under zero arguments, reentrancy, or partial initialization.
- Whether the runtime-selected write overlaps another field, callback-table storage, or the global offset source.
- The global offset’s intended signedness and valid range. The supplied representation uses 32-bit address-bearing arithmetic; no bounds, overflow, or wraparound protection is visible. Successful use requires a valid resulting two-byte destination.
- Synchronization, atomicity, and concurrent mutation rules.
- Whether repeated invocation is intended. Clearing the table field makes repeat safety unsupported without additional initialization.
- Whether dependencies preserve the object’s lifetime and the readability of the captured callback table. Normal completion requires those accesses to remain valid.
