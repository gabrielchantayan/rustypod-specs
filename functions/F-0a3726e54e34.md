# F-0a3726e54e34

## Purpose

F-0a3726e54e34 resets two four-byte fields associated with a supplied address and conditionally rewrites linked-record and context state.

Under a conventional doubly linked-list interpretation, the conditional operation moves an existing record to the front of a list. That interpretation is supported by the link updates, but the supplied material does not establish the surrounding data structure, its invariants, or the meanings of the reset fields. The contract below therefore distinguishes the directly established memory behavior from the inferred list operation.

The reset occurs on every invocation that reaches those stores successfully, including when the record is already the context’s selected record. No validation, allocation, deallocation, synchronization, or explicit error reporting is visible.

## Interface

The function receives two integer-valued arguments used as addresses:

| Contract name | Meaning |
|---|---|
| **C** | Base address of a context containing fields at byte offsets +12 and +16. |
| **P** | Address from which the affected record is located by subtracting 20 bytes. |

Define **N = P − 20**, the affected record’s base address. Define **A** as the address value read from the context field at **C + 16**, after the two unconditional reset stores.

These names describe contract roles, not externally established type names.

## Behavior

### Unconditional reset and selection decision

The first established memory effects are, in order:

1. A four-byte zero is written at N + 8.
2. The four-byte pattern `0xFFFFFFFF` is written at N + 12.
3. The address value A is read from C + 16.

The relative ordering matters when the supplied memory regions overlap. A is not a snapshot taken before the resets; a reset that aliases C + 16 can affect the value subsequently read as A.

If A equals N, the function performs no further accesses shown in the supplied body. In this case, it does not inspect either record link and does not deliberately rewrite the context’s other field.

“Already selected” therefore means that the address obtained from C + 16 **after the resets** equals N. It is not a check of the context’s entry-time contents.

### Conditional link rearrangement

If A differs from N, the function first writes N into C + 16.

It then updates a linked record using the current contents of N’s two link fields: the value at N + 4 is written to offset +4 of the record addressed by the value at N + 0.

This operation is unconditional within the unequal-address branch. A zero link at N + 0 is not handled as an empty-list or boundary case. It would lead to an attempted store at address 4 under the represented address model.

The function next reads the link at N + 4 to select one of two boundary-update behaviors:

- **Zero link:** the current value at N + 0 is written to C + 12.
- **Nonzero link:** the current value at N + 0 is written to offset +0 of the record addressed by the link at N + 4.

Finally, the function establishes three links in this order:

- N + 4 receives the saved address A.
- N + 0 receives zero.
- A + 0 receives N.

The final destination uses the previously saved A, not a fresh read of C + 16.

The body contains repeated accesses to N’s link fields. The contract does not replace these with entry-time snapshots. Earlier writes may affect later reads if memory overlaps. The supplied expression structure also does not independently establish the relative machine-level order of address-forming and value-forming reads within a single assignment; no stronger ordering is claimed for those reads.

### Conventional list interpretation

With distinct, valid records and standard doubly linked-list invariants, the layout can be interpreted as:

- N + 0: predecessor link, toward the front.
- N + 4: successor link, toward the back.
- C + 16: front record.
- C + 12: back record.

Under that interpretation, for a record that is not already first:

- Its predecessor is connected to its successor.
- If it had a successor, that successor is connected back to its predecessor.
- Otherwise, the context’s back-record field becomes its predecessor.
- N becomes the front record, with no predecessor and with A as its successor.
- A’s predecessor becomes N.

This interpretation requires a valid existing membership relationship. The function does not establish that N belongs to the context’s list, that neighboring links agree, or that A denotes a valid front record.

For a valid singleton list where A equals N, only the reset fields change. The links need not be read.

### Arithmetic boundaries

The record base is calculated by subtracting 20 bytes from P. Link-field accesses use fixed offsets of 0 or 4 bytes; the reset fields use offsets of 8 and 12 bytes from N.

There is no range check before subtraction or addition. The supplied material does not establish behavior for overflowing integer-address calculations, wraparound, invalid pointer conversion, or inaccessible low addresses. Such inputs are outside the documented successful-execution preconditions rather than defined error cases.

## Side effects

### Memory mutation

The two reset writes occur regardless of whether link rearrangement is needed.

When A differs from N, the function can additionally modify:

- C + 16;
- the four-byte field at offset +4 of the record addressed by N’s first link;
- either C + 12 or the four-byte field at offset +0 of the record addressed by N’s second link;
- both link fields of N;
- the four-byte field at A + 0.

These are logical access locations, not a guarantee that they refer to distinct storage.

The operation is not transactional. The context’s selected-record field is changed before neighboring links are repaired, and the final front-link arrangement is written later. If execution stops on an invalid access, earlier successful writes may already be visible. No rollback path is shown.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless noted otherwise, assume valid four-byte links, distinct nonoverlapping storage, no concurrent mutation, and representable address arithmetic.

### Record already selected

Given C + 16 contains N:

- N + 8 becomes zero.
- N + 12 becomes `0xFFFFFFFF`.
- Neither link of N is read or rewritten by the remaining body.
- C + 12 is not accessed.
- C + 16 is read but not rewritten.

Consequently, this branch does not require valid neighbor addresses. It still requires valid reset storage and a readable selected-record field.

### Moving an interior record

Given a valid list ordered **A → B → N → D → E**, with C + 16 identifying A and C + 12 identifying E:

- The resulting order is **N → A → B → D → E**.
- B’s successor becomes D.
- D’s predecessor becomes B.
- N’s predecessor becomes zero and its successor becomes A.
- A’s predecessor becomes N.
- The back-record field remains E.
- N’s two reset fields receive their unconditional values.

### Moving the last record

Given a valid list ordered **A → B → N**, with N’s successor equal to zero:

- The resulting order is **N → A → B**.
- B’s successor becomes zero.
- C + 12 becomes B.
- N becomes the front record.
- A’s predecessor becomes N.

The predecessor’s successor write occurs before the back-record update.

### Null previous front

Given A is zero and A differs from N, there is no empty-list insertion path. If execution reaches the final store, it attempts to write N at address zero.

This input is not accepted as a defined successful insertion merely because the context has no selected record. Earlier writes may already have occurred.

### Null predecessor in the rearrangement branch

Given A differs from N and N + 0 contains zero, the first neighbor update attempts a store at address 4. The function does not recognize or repair the inconsistency between “not selected” and “no predecessor.”

### Aliased context and reset storage

If C + 16 aliases N + 8, and both accesses refer to the same four-byte address representation, the zero reset determines the subsequently loaded A.

A contract implementation must not move the selected-record read ahead of the reset writes while claiming equivalent behavior for overlapping storage.
