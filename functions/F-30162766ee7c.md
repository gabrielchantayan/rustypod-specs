# F-30162766ee7c

## Purpose

F-30162766ee7c searches a mutable keyed structure and uses a supplied 32-bit value to select removal, replacement, or insertion:

- **Zero requested value:** remove a matching entry, if found.
- **Nonzero requested value:** replace a matching entry’s value, or prepare and submit a new entry for insertion if no match is found.

The returned 32-bit word has several meanings:

| Outcome | Return |
|---|---|
| Matching entry replaced or removed | Its previously stored value |
| No matching entry; removal requested | Zero |
| New entry submitted to the insertion dependency, which returns normally | Zero |
| Entry allocation failure, key-allocation failure, or initialization leaving capacity zero | Requested nonzero value |

The result is therefore not an unambiguous success indicator. A previous value can equal a failure return, and an existing entry containing zero can produce the same return as successful insertion.

“Container,” “key,” “bucket,” “allocation,” and “release” describe roles inferred from the visible accesses and calls. They do not establish undocumented dependency behavior.

## Interface

### Inputs and result

The function accepts four inputs:

1. **Container address:** an address supporting the reached reads and writes within a structure whose visible fields extend through byte offset 19. There is no local null check.
2. **Key input:** a 32-bit word. It is passed to dependencies and either stored directly or passed as an apparent source address to an external dependency.
3. **Key extent:** a 32-bit quantity passed unchanged to several dependencies and stored in a new entry. It also supplies the argument to a key-storage allocation request. No local range check is visible.
4. **Requested value:** a 32-bit word, tested for equality with zero.

The result is one 32-bit word. No separate diagnostic, error object, or explicit exception-handling mechanism is visible.

The representation uses 32-bit address fields and 32-bit integer fields. Equal widths do not imply equal interpretation or ownership.

### Container layout

Offsets are in bytes from the container address.

| Offset | Width | Visible use |
|---|---:|---|
| 0 | 8 bits | Selector supplied to F-3da36e01ea24 |
| 1 | 8 bits | Zero/nonzero mode controlling key handling |
| 4 | 32 bits | Overall entry count |
| 8 | 32 bits | Capacity-like field; zero suppresses the initial lookup |
| 12 | 32 bits | Link replaced when removing an entry with no predecessor |
| 16 | 32 bits | Address of a directory of 8-byte bucket records |

Bytes 2 and 3 have no direct use in the supplied body.

### Entry layout

Entry allocation requests 20 bytes.

| Offset | Width | Visible use |
|---|---:|---|
| 0 | 32 bits | Successor address |
| 4 | 32 bits | Predecessor address |
| 8 | 32 bits | Stored value |
| 12 | 32 bits | Stored key word or apparent key-storage address |
| 16 | 32 bits | Stored key extent |

The function does not locally initialize the link fields before calling the insertion dependency. It writes the requested value only after that dependency returns. Allocator- or dependency-provided initialization is unknown.

### Bucket layout

Each selected bucket is addressed using an 8-byte stride:

| Offset | Width | Visible use |
|---|---:|---|
| 0 | 32 bits | Bucket count |
| 4 | 32 bits | Entry address |

Bucket-selection range and directory bounds are not checked locally.

### Preconditions for defined, safe execution

Every reached address must support its corresponding access. Callable results and dependency-produced entry addresses must be valid for their subsequent uses. Dependencies must leave any subsequently accessed storage usable.

In particular, nonzero capacity must be compatible with the directory and selection mechanism; returned entries and links must permit the reached updates; and address arithmetic must identify valid storage.

A null key is not locally rejected. However, the selected callable receives it before the later insertion branch that permits storing zero directly. Whether null is acceptable there is unknown.

These are safety requirements, not validations performed by this function.

## Behavior

### Dispatch precedes the capacity decision

The first direct container access reads the selector byte at offset 0. F-3da36e01ea24 receives that selector and returns a callable. The callable is then invoked with the key input and key extent. Its 32-bit result is retained as a selection token.

These calls occur before reading the capacity field, including for removal requests and containers whose capacity was initially zero.

The capacity governing the initial search is therefore the value read **after both calls return**. Neither call is established to preserve the container or other reachable state.

### Search when the observed capacity is nonzero

If that capacity read is nonzero:

1. F-870c4fcf7295 is called with the retained token.
2. An auxiliary result associated with that call is supplied to F-42dffdf1b496.
3. F-42dffdf1b496 receives the container, key input, key extent, auxiliary result, and original requested value.

The visible first call to F-870c4fcf7295 supplies only the token; the insertion-time call visibly supplies both token and capacity. The exact signature and auxiliary-result convention remain unresolved.

A null lookup result leads to the absent-entry path. A non-null result is treated as an entry address.

### Existing entry: capture and replace

For any existing entry, the stored value at offset 8 is read and retained for the eventual return.

If the requested value is nonzero:

1. Write the requested value at entry offset 8.
2. Read the container’s mode byte.
3. If that byte is zero, overwrite entry offset 12 with the current key input.
4. Return the captured previous value.

If the mode is nonzero, the stored key field is not directly changed. The stored extent is not directly changed in either mode.

No local allocation, external key-preparation call, or release call occurs on this replacement path. In zero mode, replacement can therefore change the key word while retaining its old extent.

### Existing entry: remove

If the requested value is zero, removal proceeds as follows:

1. Inspect the entry’s predecessor field.
2. If it is zero, write the entry’s successor to container offset 12. Otherwise, write that successor to the predecessor’s successor field.
3. If the entry’s successor is nonzero, write the entry’s predecessor to the successor’s predecessor field.
4. Read the directory address and select a bucket using the auxiliary selection result and an 8-byte stride.
5. If the bucket’s entry address equals the removed entry, replace that address with the removed entry’s successor.
6. Decrement the bucket count.
7. If the decremented count is signed-less-than one, clear the bucket’s entry address.
8. Read the mode byte. If nonzero, pass the entry’s stored key field to F-94cb53877c15.
9. Pass the entry address to F-94cb53877c15.
10. Read the container’s overall count, decrement it, and store the result.
11. If that result is signed-less-than one, call F-36922d617719 with the container.
12. Return the captured previous value.

The overall count is read after the release-designated calls, not snapshotted before them. Their effects can therefore affect the count subsequently decremented.

The signed-less-than-one conditions include zero and negative values, not just zero. F-36922d617719’s effects are unknown; it must not be described as necessarily clearing fields, preserving storage, or freeing the container.

### Absent entry: zero requested value

If the initial capacity read is zero, or lookup returns null, a zero requested value returns zero.

This path performs no direct container write and no local allocation request. Dispatch, the selected callable, and any lookup-related calls already reached may have had effects.

### Absent entry: allocate and prepare a new entry

For a nonzero requested value, F-391e3d30e634 receives an allocation request of 20.

If it returns zero, return the requested value. This function has not incremented the overall count.

After a nonzero result, read the current mode byte:

- If mode is zero, store the key input directly at entry offset 12.
- If mode is nonzero but the key input is zero, store zero there.
- Otherwise, call F-391e3d30e634 with the key extent.

For this last branch, write the allocation result to entry offset 12 **before** testing it for zero.

If it is zero, pass the entry address to F-94cb53877c15 and return the requested value. There is no overall-count increment and no separate release call for the zero key-allocation result.

If it is nonzero, invoke an unidentified external dependency with these observed arguments, in order:

1. The key-allocation result.
2. The original key input.
3. The supplied key extent.

The apparent intent is to prepare copied key storage. The supplied body does **not** establish that this dependency copies exactly the extent, preserves the input, omits transformations, writes a terminator, or leaves unrelated state unchanged. Its actual memory effects and preservation guarantees remain unknown. Any claim about the resulting key bytes requires an additional dependency contract.

A zero extent is passed through unchanged. Neither allocation nor external-call behavior for that extent is established.

### Record extent, increment count, and initialize capacity

After the selected key-preparation branch completes:

1. Store the key extent at entry offset 16.
2. Read, increment, and write the overall count at container offset 4.
3. Read the capacity field.

If capacity is zero, call F-d579c4e32016 with the container and 16. Ignore its direct result and reread capacity.

If the reread remains zero, use the initialization-failure path below.

Otherwise, compare capacity with the current overall count using a signed comparison. If capacity is less than count, call F-d579c4e32016 with the container and the capacity shifted left by one bit.

This is a 32-bit capacity-derived growth request, not a guaranteed mathematically valid doubling for every bit pattern. There is no visible overflow check.

No success check follows this growth call. In particular, insertion does not branch on its direct result or repeat the zero-capacity failure check afterward.

### Select a bucket and submit the entry

Using the retained token and the capacity then read from the container, call F-870c4fcf7295 again.

After that call, read the directory address and form a bucket address using its auxiliary result and an 8-byte stride. Pass the container, bucket address, and new entry to F-f32d03db7833.

After F-f32d03db7833 returns:

1. Write the requested value at entry offset 8.
2. Return zero.

There is no visible insertion-status check. The insertion dependency receives the entry before this function writes its value field. The directory read follows bucket selection; it must not be assumed to use a directory snapshot from before that call.

### Initialization failure after count increment

If the initialization call leaves capacity zero:

1. Write zero to the overall count.
2. Read the mode byte.
3. If nonzero, read the entry’s stored key field and pass it to F-94cb53877c15.
4. Pass the entry address to F-94cb53877c15.
5. Return the requested value.

The count is reset to zero, not restored to its value before incrementing.

The cleanup mode read is separate from the earlier key-preparation mode read. Dependencies may change it. Consequently, cleanup must not be specified as determined solely by the mode at function entry or allocation time.

This path can pass a null stored key to F-94cb53877c15. Null acceptance is unknown.

## Side effects

### Ownership and lifetime

The visible branches suggest a mode-controlled distinction between directly stored keys and independently prepared key storage:

- Zero mode directly stores the key input and suppresses local key-release calls at the relevant mode checks.
- Nonzero mode with a nonzero insertion key requests additional storage and invokes the unidentified external dependency.
- Removal and initialization-failure cleanup submit the stored key for release when their own mode reads are nonzero.

These observations do not prove copying semantics, ownership transfer, successful deallocation, or mode stability. In particular, newly allocated key storage has no established byte-content guarantee from this body alone.

Stored values are not locally submitted for release. Replacement and removal return the captured previous value as a word.

A submitted entry is not locally released on the normal insertion path. Its retention and later lifetime depend on the dependencies.

### Intermediate state

Removal updates links and bucket metadata before release calls and before decrementing the overall count.

Insertion increments the overall count before initialization or growth, then calls the insertion dependency before writing the requested value. The unidentified external call also occurs before the extent write and count increment.

No locking, atomic-publication mechanism, reentrancy guard, or general rollback mechanism is visible. Callback observation and concurrent access require contracts not supplied here.

### Arithmetic and errors

Counts, capacity, selection components, and stored addresses are 32 bits. Relevant arithmetic includes count changes, capacity shifting, bucket-stride multiplication, and address addition.

The body exposes signed comparisons for growth and decremented-count thresholds. It does not establish portable overflow semantics for all arithmetic. The contract therefore does not promise saturation, mathematical unbounded arithmetic, or reliable modular behavior outside valid ranges.

No local recovery is shown for invalid pointers, invalid callable results, dependency traps, non-returning calls, or unusable state after growth.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume reached accesses remain valid and dependencies return normally.

1. **Replacement in zero mode.** Given a lookup result whose value is 41, requested value 73, and mode zero when read after the value write: return 41, store 73, and overwrite the stored key with the current key input. Do not directly change the extent.

2. **Replacement in nonzero mode.** With the same values but a nonzero mode at that read: return 41 and store 73 without directly changing key or extent.

3. **Skipped lookup for removal.** If capacity is zero **when read after F-3da36e01ea24 and the selected callable return**, and the requested value is zero: return zero without local allocation or direct container mutation. Initially zero capacity alone is insufficient. If either dependency establishes nonzero capacity, lookup can run and a found entry can be removed.

4. **Entry allocation failure.** Given an absent-entry path and requested value 73, a zero result from the 20-byte request returns 73 without a local count increment.

5. **Key allocation failure.** Given nonzero mode at key preparation and a nonzero key, a successful entry allocation followed by zero key allocation stores zero in the entry’s key field, submits the entry for release, and returns the requested value without incrementing the count.

6. **External key preparation.** With successful key allocation, observe the external call receiving that allocation result, the input key, and the extent. Exact copied bytes are not an acceptance condition unless a separate contract establishes the callee’s memory effects.

7. **Insertion without growth.** If preparation completes and the post-increment capacity is nonzero and signed-greater-than-or-equal-to the current count, select a bucket, submit the entry, then write its requested value and return zero. The submission call precedes that value write.

8. **Initialization leaves capacity zero.** After preparation and count increment, if initialization leaves capacity zero at the reread, set count to zero, perform cleanup according to the newly read mode, submit the entry for release, and return the requested value.

9. **Ignored growth result.** If nonzero capacity is signed-less-than count, request growth. Whatever its direct return, continue toward bucket selection using subsequently read state. Safe continuation requires that state to remain usable.

10. **Removal threshold after release calls.** If the overall count read after the release-designated calls is one, store zero and invoke F-36922d617719. Return the previously captured entry value if execution completes normally.

- The unidentified external dependency’s actual memory effects, transformations, extent interpretation, and preservation guarantees.
- Contents of allocated key storage after that call.
- Allocation initialization, alignment, zero-size behavior, and large-extent behavior.
- Whether release accepts null or actually deallocates storage.
- Dependency preservation of container fields, links, globals, and reachable memory.
- Required mode stability and consequences of mode changes across calls.
- Overflow behavior outside valid arithmetic ranges.
- Complete initialization and destruction requirements.
- Thread safety, callback safety, and reentrancy.
- Recovery from dependency failures other than the explicitly checked zero results.
- Final state after growth, insertion, or final-container cleanup.

The inferred intent is a hash-indexed container with optional separately prepared key storage. That interpretation does not replace the observed control flow or resolve these unknowns.
