# F-9896eba253e3

## Purpose

F-9896eba253e3 performs an ordered lookup over two candidate positions. For each reached position, it obtains a table base from an externally stored global value, reads a 32-bit address representation from the corresponding table slot, and compares the unsigned 16-bit value at that address with the supplied unsigned 32-bit search value.

The first successful comparison ends the search. To obtain the result, the function evaluates the table-base global again and reads the 32-bit slot at the successful position using that newly evaluated base. If neither comparison succeeds, it returns zero.

**Established static evidence:** the search considers position zero before position one; candidate keys are unsigned 16-bit values; the search input and return value are 32 bits; the table-base global is evaluated for each reached candidate and again for a successful return.

**Inferred intent:** this is a two-entry lookup of objects identified by an initial 16-bit key. Neither a larger object layout nor the semantic meaning of the key is established.

A fixed storage location for the table-base global does **not** establish an immutable table origin. Without external stability guarantees, the two candidate examinations and the successful return need not use the same table base.

## Interface

### Input

The sole explicit argument is an unsigned 32-bit search value, ranging from 0 through 4,294,967,295.

Each candidate key is read as an unsigned 16-bit value and compared numerically against the full search value. The input is not reduced to its low 16 bits.

Consequently:

- Values from 0 through 65,535 can match.
- Values above 65,535 cannot equal a successfully read candidate key.
- An input above 65,535 does not bypass memory access. The ordinary candidate reads still occur unless execution is interrupted.

The function takes no explicit table, count, allocator, or synchronization argument.

### Implicit input: table-base global

An externally stored global value supplies the table base. The function evaluates that value when locating each reached candidate. After a successful comparison, it evaluates the global again to locate the return-value slot.

The global is therefore a repeated implicit input, not merely a one-time source of a saved table address.

For normal completion, the global’s storage must be initialized, live, and readable at every reached evaluation. Each resulting base must support the particular slot access that follows it. The source does not establish who initializes the global, how long its storage remains valid, or whether another component may change it.

### Table and target layout

Each evaluated table base is used with the following slot layout:

| Candidate position | Byte offset from the evaluated base | Slot interpretation |
|---|---:|---|
| First | 0 | 32-bit address representation |
| Second | 4 | 32-bit address representation |

For a candidate examination, the selected slot supplies an address from which an unsigned 16-bit key is read at offset zero. No later field of that target is accessed.

For a successful return, the selected slot is read as a raw 32-bit result. That return operation does not dereference the address represented by the returned value.

The evidence establishes the 4-byte slot spacing, 16-bit key access, and 32-bit result access. It does not establish byte order, alignment requirements, the declaration or storage width of the base global, or all rules governing conversion of stored values into usable addresses.

### Output

The function returns a 32-bit value:

- After a successful comparison: the contents of the slot at the successful position, located using a fresh evaluation of the table-base global.
- After two unsuccessful comparisons: zero.

The result is not explicitly a saved copy of the address used to read the matching key.

There is no separate success flag, invalid-memory result, or duplicate-key error. Zero is the explicit no-match result, but it is not established as a universally unambiguous failure indicator under every permitted memory model or mutation scenario. For example, a successful comparison followed by a changed base or changed slot could produce a zero return value.

## Behavior

### Candidate order and bounded traversal

The function begins at position zero. It reaches position one only if the first key comparison fails. A mismatch at position one ends the search with a zero result.

The position calculation uses a 32-bit unsigned increment followed by a mask that clears bit 16, counting the least significant bit as bit zero. Starting from zero, the reachable progression is zero, one, then two. The mask does not change those values, and continuation requires a position below two.

Thus:

- Exactly two candidate positions are available.
- No index overflow occurs on the demonstrated path.
- The mask does not introduce wrapping, additional candidates, or repeated traversal.
- A successful first comparison prevents examination of position one.

The only reachable slot offsets are zero and four bytes. No third slot is examined.

### Read ordering for a reached candidate

At the source-expression level, each candidate examination has these read dependencies:

1. Evaluate the table-base global.
2. Read the 32-bit address representation from the selected slot relative to that base.
3. Read the unsigned 16-bit key at the represented address.
4. Compare that key against the complete unsigned 32-bit input.

A mismatch advances the search or, after the second candidate, produces zero.

A match instead leads to these additional reads:

1. Evaluate the table-base global again.
2. Read the 32-bit result slot at the successful position relative to this newly evaluated base.
3. Return that slot value without reading a key through it.

The successful position remains the same for the return expression. The table base and slot contents are not explicitly preserved from the comparison.

These are source-level evaluation relationships. They do not establish a distinct physical memory transaction for every expression evaluation. Volatile qualification, compiler transformations, atomicity, and device-memory semantics are not supplied.

### Stable-memory outcomes

The ordinary lookup interpretation requires stability of all relevant state: the table-base global, the reached table slots, and the referenced keys.

Under that condition:

- If the first key matches, the function returns the first slot value.
- Otherwise, if the second key matches, it returns the second slot value.
- Otherwise, it returns zero.
- If both keys match, the first slot wins.
- If both slots contain the same address representation, the same ordering still applies.

There is no uniqueness check, duplicate report, or examination of a matching target beyond its initial 16-bit key.

### Changing bases, slots, or keys

If the platform permits changes between source-level evaluations, the function provides no snapshot guarantee.

A base change after the first mismatch can cause position one to be examined in a different table from position zero. The function does not restart or require the second base to equal the first.

A base change after a successful comparison can cause the result to be read from an entirely different table. The result still comes from the successful position: offset zero after a first-position match, or offset four after a second-position match.

Even if the base remains unchanged, a slot change between comparison and return can change the returned value. A key change after its read likewise does not cause revalidation.

The returned value therefore need not represent the address whose key matched. Nor does the function establish that the target represented by the returned value has the requested key, remains readable, or even exists.

These statements describe the source’s absence of preservation and revalidation. They do not promise that unsynchronized concurrent mutation is supported or well-defined.

### Invalid memory and exceptional execution

The function contains no explicit validation of:

- The table-base global’s storage.
- The evaluated base.
- A reached table slot.
- An address obtained from a candidate slot.
- The referenced 16-bit key storage.

A zero-valued candidate slot is not treated as an empty entry or terminator. The function attempts the indirect key read through that value before deciding whether to continue.

An unreadable first candidate can prevent a valid second candidate from being reached. Conversely, a first-position match avoids the second-position access entirely.

A successful key comparison does not guarantee normal return: the subsequent global evaluation or return-slot read may itself fail.

The source supplies no explicit error recovery. Whether an invalid or misaligned read traps, faults, is handled externally, or has some other consequence is platform-dependent and remains unresolved.
