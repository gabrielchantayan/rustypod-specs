# F-30d819234273

## Purpose

F-30d819234273 conditionally transfers data associated with a selected entry into a caller-supplied destination, then publishes two 32-bit entry attributes through output pointers.

The established behavior is a gated sequence of three indirect calls, signed capacity and transfer-count checks, and two final output writes. Return values are:

| Return value | Established meaning |
|---|---|
| 0 | The transfer dependency returned a value equal to the subsequently observed entry length, and both final output writes were performed. |
| 3 | An eligibility condition failed, the preparation dependency returned nonzero, the positioning dependency returned nonzero, or the transfer result did not equal the subsequently observed entry length. |
| 4 | Preparation returned zero, but the caller’s signed capacity was less than the entry length observed immediately afterward. |

“Preparation,” “positioning,” “transfer,” “length,” and “metadata” are descriptive roles inferred from usage. They do not establish the underlying object type, units, external protocol, or dependency semantics.

## Interface

### Arguments

The function has six arguments:

1. **Receiver**: a pointer to an object whose relevant fields are described below.
2. **Destination token**: a 32-bit value. Zero prevents entry into the callback sequence. A nonzero value is forwarded unchanged to the transfer dependency. Its use as a writable buffer address is inferred, not established by direct memory access in this function.
3. **Capacity**: a signed 32-bit integer, compared against an entry’s signed 32-bit length.
4. **Length-output pointer**: a pointer to a writable 32-bit word. It is also passed twice to the preparation dependency.
5. **Metadata-output pointer**: a pointer to a writable 32-bit word.
6. **Preparation token**: an opaque 32-bit value forwarded unchanged to the preparation dependency.

The result is a 32-bit word containing 0, 3, or 4 on an ordinary return.

There is no direct null check for the receiver or either output pointer. The receiver is dereferenced before eligibility is established. Output-pointer validity is required when a reached dependency accesses an output pointer, or when the function reaches its final stores.

### Receiver layout

The supplied representation uses 32-bit pointer-bearing words. Offsets below are byte offsets from the receiver:

| Offset | Width | Observed role |
|---|---:|---|
| 0x000 | 32 bits | Pointer to a dispatch table used for preparation. |
| 0x008 | 32 bits | Pointer to a secondary object used for positioning and transfer. |
| 0x040 | 32 bits | Pointer to a word interpreted as a signed upper bound during eligibility checking. |
| 0x21C | 32 bits | Selected index, interpreted as signed. |
| 0x228 | 32 bits | Base address of a table of 32-bit lengths; also required to be nonzero during eligibility checking. |
| 0x22C | 32 bits | Base address of a table of 32-bit metadata values. |
| 0x230 | 32 bits | Base address of a table of 32-bit positioning tokens. |

Each table is addressed with a four-byte stride. The secondary object’s first 32-bit word supplies its dispatch-table pointer.

These roles are not validated type declarations. In particular, a nonzero table address does not prove that any indexed element is readable.

### Preconditions for defined completion

Every memory access and indirect call reached by the selected path must be valid. This includes receiver fields, the eligibility-bound word, selected table entries, dispatch-table entries, dependency targets, and any reached output stores.

No alignment checks, bounds enforcement beyond the initial eligibility test, exception recovery, or memory-fault conversion are visible.

## Behavior

### 1. Initial eligibility

The function first reads the receiver’s bound-pointer field at offset 0x040.

If that pointer is zero, eligibility fails and the function returns 3 without invoking a dependency.

If it is nonzero, the function reads the length-table base at offset 0x228. A zero base likewise makes eligibility fail without invoking a dependency.

When both are nonzero, the function reads the selected index at offset 0x21C and then reads the signed 32-bit bound through the previously obtained bound pointer.

The index and bound must satisfy both of these signed conditions:

- The index is less than the bound.
- The index is nonnegative.

The destination token must also be nonzero. Otherwise, the function returns 3.

The index comparison is represented using a 32-bit subtraction, its sign, and its signed-overflow indication. Its established meaning is signed “index less than bound,” not merely “the wrapped subtraction has its high bit set.” For example, signed overflow in the subtraction does not make an otherwise invalid index eligible.

The bound word is read before a negative index or zero destination token prevents callback execution. A zero destination token therefore does not make an otherwise invalid receiver or bound pointer safe.

### 2. Preparation dependency

After eligibility succeeds, the function invokes the receiver dependency found at dispatch-table byte offset 0x34. Its five arguments, in order, are:

1. The receiver.
2. The preparation token.
3. A function-pointer value obtained from the preparation dispatch slot.
4. The length-output pointer.
5. The same length-output pointer again.

If this dependency returns any nonzero 32-bit value, F-30d819234273 returns 3.

A zero result permits processing to continue. It does not establish that receiver fields, tables, output memory, or global state remain unchanged.

### 3. Post-preparation index and capacity check

After preparation returns zero, the function reads the selected index again from offset 0x21C. This newly read index is retained for all subsequent table indexing in the function.

It is not checked again against zero or the bound. Consequently, a dependency-induced index change can cause later accesses to use an index that would have failed the original eligibility test.

Using the current length-table base and this retained index, the function reads a signed 32-bit entry length. If the signed capacity is less than this length, it returns 4 immediately.

This is a signed comparison. Negative capacities and negative lengths are not explicitly rejected. For example, capacity −1 is not less than length −2, so that combination passes this check if all reached accesses are valid.

No positioning or transfer dependency is invoked on the return-4 path. Preparation has already run and may already have changed state.

### 4. Positioning dependency

If the capacity check passes, the function obtains the secondary object from receiver offset 0x008 and selects its dependency at dispatch-table byte offset 0x14.

It also reads the positioning-token table base at receiver offset 0x230 and obtains the 32-bit token at the retained index.

The positioning dependency receives five arguments, in order:

1. The secondary object.
2. The selected positioning function-pointer value.
3. The indexed positioning token.
4. Zero.
5. Zero.

If the dependency returns nonzero, the function returns 3 without invoking the transfer dependency.

The exact evaluation order among independent argument expressions and dispatch-target loads within this indirect-call expression is not established. All occur after the capacity check and before the positioning call begins.

### 5. Transfer dependency and result comparison

If positioning returns zero, the function obtains the secondary object and its dispatch table again. Thus, changes made by positioning to the receiver’s secondary-object field can affect the next call.

It selects the dependency at secondary dispatch-table byte offset 0x10 and invokes it with four arguments:

1. The currently obtained secondary object.
2. The original destination token.
3. A freshly read length-table entry at the retained index.
4. The integer value 2.

This length need not equal the value used for the capacity check. The capacity is not checked again after positioning.

After the transfer call returns, the function reads the length-table entry again, using the retained index and the then-current table base. It compares that 32-bit value with the dependency’s 32-bit result.

If they differ, the function returns 3. There is no visible retry, partial-transfer adjustment, rollback, or separate interpretation of negative results.

The comparison is against the post-call table value, not a saved copy of the requested amount. A dependency that changes the entry can therefore change whether the comparison succeeds.

### 6. Final output publication

When the transfer result equals the freshly read length, the function performs these actions in sequence:

1. Read the metadata-table base and the indexed 32-bit metadata value.
2. Store that value through the metadata-output pointer.
3. Read the length-table base and the indexed 32-bit length value again.
4. Store that value through the length-output pointer.
5. Return 0.

The metadata store precedes the final length read, not merely the final length store. Aliasing can therefore affect both the value subsequently read and the location from which it is read.

No output staging or disjointness enforcement is visible.

### Arithmetic and address formation

Table offsets are formed from a 32-bit index multiplied by four, followed by addition to a 32-bit table base. The supplied representation provides no widened arithmetic or overflow check for these calculations.

The contract does not extend this to arbitrary-address safety: wrapped, negative-index, or otherwise invalid effective addresses can fault or encounter behavior outside defined completion. The same caution applies when preparation changes the selected index after its initial validation.

## Side effects

### Direct effects

The function directly writes only the two final output words on its successful path:

- Metadata first.
- Length second.

The destination token is not directly dereferenced by this function. Any data movement through it is performed by a dependency.

The function does not visibly allocate, free, retain, or release memory. It does not directly update the receiver’s index or table fields.

### Dependency effects

All reached dependencies may have side effects not described by the supplied body. In particular:

- Preparation receives the length-output pointer twice and may modify its target even if F-30d819234273 subsequently returns 3 or 4.
- Positioning may alter the secondary object, receiver fields, or tables before transfer arguments are obtained.
- Transfer may modify destination storage, table contents, receiver state, or other reachable state before result comparison and output publication.

There is no basis for assuming that these dependencies preserve globals or that they acquire or release memory ownership.

### Failure and aliasing

Returns 3 and 4 do not imply an unchanged destination, unchanged outputs, or unchanged receiver. They only identify the visible control-flow outcome.

If both output pointers identify the same ordinary writable word, and neither write changes later table access, the final stored value is the length because that store occurs last.

If an output pointer aliases receiver fields or table storage, the metadata store can change the later length access. Such aliasing is not rejected. Its precise effect follows the reached read/write sequence and requires valid memory throughout.

A fault or nonreturning dependency can prevent ordinary return after earlier side effects have already occurred.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, all reached memory accesses are valid, dependencies return normally, and receiver fields and tables remain stable except for the described changes.

1. **Missing bound pointer**  
   A zero bound pointer produces return 3. No dependency is called and neither final output store is performed.

2. **Missing length-table base**  
   A nonzero bound pointer with a zero length-table base produces return 3 without reading the bound word or calling a dependency.

3. **Index outside the signed eligibility range**  
   Index −1 fails even when less than the bound. Index equal to the bound also fails. Either case returns 3 without preparation.

4. **Zero destination token**  
   Otherwise eligible state with a zero destination token returns 3 without preparation. Receiver, table-base, index, and bound reads needed for eligibility still occur.

5. **Preparation failure**  
   Eligible state followed by a nonzero F-D01 result produces return 3. No capacity check, positioning call, transfer call, or final output publication follows. Any preparation side effects remain.

6. **Insufficient signed capacity**  
   F-D01 returns zero, the post-preparation selected entry has length 12, and capacity is 11. The result is 4; F-D02 and F-D03 are not invoked.

7. **Exact capacity and stable success**  
   Capacity and entry length are both 12. F-D01 and F-D02 return zero; F-D03 receives length 12 and returns 12. The function writes the selected metadata, writes length 12, and returns 0.

8. **Positioning failure**  
   Capacity is sufficient, but F-D02 returns nonzero. The function returns 3 without transfer or final output publication.

9. **Transfer mismatch**  
   F-D03 receives length 12, returns 10, and the post-call length remains 12. The function returns 3. Any data already written by F-D03 is not rolled back.

10. **Length changes during transfer**  
    F-D03 receives length 12, changes the entry length to 10, and returns 10. The equality check succeeds against 10. With no further changes, the function publishes metadata and length 10 and returns 0.

11. **Length grows after the capacity check**  
    Capacity and checked length are 12. F-D02 changes the length to 20 and returns zero. F-D03 receives 20 despite the original capacity of 12. If it returns 20 and the entry remains 20, the function can return 0. No second capacity guard exists.

12. **Index changes during preparation**  
    The original index passes eligibility. F-D01 changes it and returns zero. Subsequent table accesses use the changed index without renewed eligibility checking. Successful completion is conditional on those accesses and all later operations being valid.
