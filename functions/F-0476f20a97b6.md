# F-0476f20a97b6

## Purpose

F-0476f20a97b6 searches a linked structure using an opaque caller-supplied value, then either publishes a candidate address or delegates an operation to F-0ffa01c040fd. Its output consists of a four-byte result word followed by a one-byte status.

A container byte selects two behaviors:

- **Zero mode:** additional boundary handling, possible candidate adjustment, and a final comparison determine whether to publish a candidate or invoke F-0ffa01c040fd.
- **Nonzero mode:** F-0ffa01c040fd is invoked immediately after the initial search.

Status zero identifies the candidate-publication path. Status one identifies a path on which F-0ffa01c040fd returned. Status one is not an independently checked success indication.

**Inferred intent:** the structure and traversal resemble an ordered tree, with zero mode rejecting equivalent values and nonzero mode allowing them. These interpretations require dependency contracts and structural invariants not established by the supplied representation.

## Interface

### Arguments and output

The function receives three arguments:

| Argument | Established interpretation |
|---|---|
| Result destination | Address of storage writable for a four-byte word at offset `0x00` and a one-byte status at offset `0x04` |
| Container address | Four-byte address identifying the container |
| Value argument | Opaque four-byte value passed unchanged to dependencies |

There is no established return-value result. The explicit caller-visible result is written through the result destination.

The result word is either:

- A candidate address on the status-zero path; or
- The four-byte contents of dependency result storage after F-0ffa01c040fd returns, on a status-one path.

The function does not explicitly write beyond destination offset `0x04`.

### Accessed layouts

Addresses, pointer fields, result words, and the internal words described below are four bytes. Mode, marker, and status accesses are one byte. Comparison results are tested only for zero versus nonzero; their sign is not used.

Container fields:

| Offset | Access | Role |
|---|---|---|
| `0x10` | Four-byte read | Header pointer |
| `0x18` | One-byte read | Mode selector |
| `0x19` | Address formation | Context argument to F-0423ab0b78da |

Header and traversed-object fields:

| Offset | Access | Role |
|---|---|---|
| `0x00` | One-byte read | Marker used during candidate adjustment |
| `0x04` | Four-byte read | Initial search link or upward link |
| `0x08` | Four-byte read | Boundary word or traversal link, depending on the object |
| `0x0c` | Four-byte read | Traversal link |
| `0x10` | Address formation | Node-associated argument to F-0423ab0b78da |

These are accessed fields, not a complete object definition. Forming an address at offset `0x10` or `0x19` does not establish the size or representation of the object expected there by a dependency.

### Preconditions and arithmetic

Every actual dereference and destination write requires suitable accessible storage. Dependency arguments must satisfy contracts that are not supplied.

The function performs fixed byte-offset address calculations. It contains no explicit overflow, null, range, or alignment validation. The four-byte address representation does not establish safe behavior when an addition exceeds the valid address range.

Traversal requires links compatible with the accesses taken. Cycles can prevent termination. Null protection exists for the initial search loop, but not for every header, candidate, parent, or subtree access.

Aliasing is not rejected. The destination may overlap container or node storage if the resulting accesses remain valid. Such overlap can overwrite that storage during publication; it does not cause later container reads or dependency calls within this function, because those have already finished.

## Behavior

### Initial search and temporary state

For describing result-storage history, this contract names two internal four-byte slots **result slot A** and **result slot B**. These are descriptive names, not interface fields. Their initial contents are not explicitly established at function entry.

The function starts with a nonzero direction value. It then:

1. Reads the container’s header pointer and that header’s `0x04` link to obtain the first search node.
2. Reads the container’s header pointer again to initialize the retained search position.

The second header read is separate from the first. If the reads differ, the initial search node comes from the first header, while the initial retained position comes from the second.

For each non-null search node, the function performs these actions in order:

1. Clears all four bytes of result slot A.
2. Clears all four bytes of result slot B.
3. Calls F-0423ab0b78da with the context address at container offset `0x19`, the original value argument, and the current node’s address plus `0x10`.
4. Retains that node as the search position.
5. Follows its `0x0c` link if the comparison returned zero, or its `0x08` link otherwise.

The link read occurs after the comparison call. The function does not establish that the dependency leaves the node or container unchanged.

At search termination:

- The retained position is the last visited node, or the separately read header if the search was empty.
- The retained direction is the last comparison result, or the initial nonzero value if the search was empty.
- Both result slots have been explicitly cleared once per visited node, before that node’s comparison. With an empty search, neither has yet been explicitly initialized.

The mode byte is read only after the search. Search-dependency effects can therefore affect the observed mode.

### Nonzero mode

A nonzero mode bypasses the boundary call, candidate adjustment, and final comparison.

The function invokes F-0ffa01c040fd with, in order:

1. The address of result slot B.
2. The container address.
3. A literal zero argument.
4. The retained search position.
5. The original value argument.

After that call returns, the function publishes result slot B and status one.

For an empty search, result slot B has no explicit initialization before this call. For a nonempty search, its latest explicit initialization was the clear before the final search comparison. There is no additional clear immediately before F-0ffa01c040fd on this path.

### Zero mode: boundary decision

In zero mode, candidate storage is initialized to the retained search position.

If the retained direction is zero, the function skips boundary handling and candidate adjustment.

If the retained direction is nonzero, the function:

1. Rereads the container’s header pointer.
2. Reads that header’s four-byte field at offset `0x08`.
3. Stores that word in result slot B, replacing its previous contents.
4. Calls F-73b7871d4f8c with the address of candidate storage and the address of result slot B.

Both arguments expose writable internal storage. The supplied function does not establish that F-73b7871d4f8c preserves either value or refrains from retaining either address.

If the boundary dependency returns nonzero, the function immediately invokes F-0ffa01c040fd using **result slot A**, together with the container, literal zero, retained search position, and original value argument. It then publishes result slot A and status one.

On this immediate-modification path:

- An empty initial search leaves result slot A without explicit initialization before the modification call.
- A nonempty search has cleared result slot A before every search comparison, most recently before the final one.
- No clear of result slot A occurs between the boundary call and the modification call.

If the boundary dependency returns zero, candidate adjustment uses the candidate value present after that call. The retained search position remains the separate position used for any later modification call.

### Zero mode: candidate adjustment

Adjustment begins by reading the candidate’s one-byte marker at offset `0x00`.

If the marker is zero, the function reads the candidate’s `0x04` link and then the linked object’s `0x04` link. If the resulting address equals the candidate, the candidate becomes its `0x0c` link, and the ordinary adjustment below is skipped.

Otherwise, ordinary adjustment begins with **two separate reads** of the candidate’s `0x08` link:

1. The first read supplies a saved subtree address.
2. The second read independently chooses upward traversal when null, or subtree traversal when non-null.

The second read does not replace the saved address from the first.

**Upward traversal:** when the second read is null, the saved subtree address is discarded. The function reads the candidate’s `0x04` link as a prospective parent. Each step reads that parent’s `0x08` link, compares it with the previous candidate, and then assigns the parent as the new candidate. Equality causes another step through the parent’s `0x04` link; inequality stops the walk. The parent becomes the candidate even on the terminating unequal step.

**Subtree traversal:** when the second read is non-null, traversal starts from the address obtained by the first read. Each iteration assigns the current traversal address as candidate, reads its `0x0c` link as the saved next address, and separately rereads the same `0x0c` field to decide whether to continue.

Consequently:

- A non-null second `0x08` read does not guarantee that the first read supplied a non-null traversal address.
- A non-null continuation read of `0x0c` causes traversal to continue using the preceding read’s value, even if the two values differ.
- A null continuation read stops at the current candidate, regardless of the preceding saved link.

No synchronization or dependency contract establishes agreement between these repeated reads.

**Inferred intent:** under stable conventional tree links, this resembles predecessor traversal with a header-specific special case. The actual read sequence, including mismatched-read possibilities, is the established behavior.

### Zero mode: final comparison

Unless the boundary decision already selected immediate modification, zero mode reaches the final comparison.

Before calling the comparison dependency, the function clears a separate four-byte scratch word and then clears all four bytes of result slot B. The scratch word has no subsequent explicit use in the supplied representation.

The function then calls F-0423ab0b78da with:

1. The context address at container offset `0x19`.
2. The candidate’s address plus `0x10`.
3. The original value argument.

The last two argument positions are reversed relative to the initial search.

If the comparison returns zero, the function publishes the candidate address and status zero, without invoking F-0ffa01c040fd.

If it returns nonzero, the function invokes F-0ffa01c040fd using result slot B, the container, literal zero, the **retained search position**, and the original value argument. It publishes result slot B and status one.

The clear of result slot B precedes the final comparison, not the modification call immediately. Where boundary handling occurred, this is the same storage that previously held the boundary word and whose address was exposed to F-73b7871d4f8c. Retained-pointer effects during later calls cannot be excluded. Likewise, candidate storage was exposed by the boundary call; a later dependency is not established to preserve it through indirect access.

## Side effects

### Publication order

On every normally completing path, publication consists of:

1. A four-byte write at destination offset `0x00`.
2. Local status bookkeeping.
3. A one-byte write at destination offset `0x04`.

All dependency calls and all explicit container and node reads precede the first destination write. There are no subsequent dependency calls or container/node reads between the two output writes.

The destination is not initialized at entry. A fault or nonreturning dependency before publication can leave it unchanged. A failure during publication can leave only a partial result.

On modification paths, the result slot is read for publication before the local status bookkeeping. The status bookkeeping assigns zero or one to a byte of internal storage; it does not retroactively alter the already-published four-byte word.

### Result-storage guarantees

The function does not check whether F-0ffa01c040fd initializes its entire output word. If that dependency leaves bytes untouched, the selected slot’s prior state matters:

| Modification path | Result slot | Caller-established history |
|---|---|---|
| Nonzero boundary result | A | Cleared before each search comparison; no explicit initialization if search was empty |
| Nonzero mode | B | Cleared before each search comparison; no explicit initialization if search was empty |
| Nonzero final comparison in zero mode | B | Explicitly cleared before the final comparison; may previously have held the boundary word and been exposed by address |

These are initialization histories, not unconditional guarantees about contents at modification-call entry. Intervening dependency effects remain unknown.

### Other effects and ownership

F-0423ab0b78da is called once per visited search node, with at most one additional final comparison. F-73b7871d4f8c is called only in zero mode with a nonzero retained direction. F-0ffa01c040fd is called at most once on a terminating execution.

No direct allocation, release, ownership transfer, locking, rollback, or explicit error reporting is established. Dependency behavior may include such effects. The original value is not established to be copied, retained, consumed, or released.

## Acceptance examples

These are conditional static scenarios, not executed tests.

### Empty search in nonzero mode

With a null initial search link and nonzero mode:

- No comparison or boundary call occurs.
- F-0ffa01c040fd receives result slot B and the separately read retained header.
- Result slot B has not been explicitly initialized.
- If the dependency writes all four result bytes and returns, those bytes are published with status one.
- If it leaves bytes untouched, no fixed value for those bytes is established.

### Empty search with immediate boundary-selected modification

With an empty search, zero mode, and a nonzero boundary result:

- The initial nonzero direction causes the boundary call.
- Result slot B first receives the header boundary word.
- F-0ffa01c040fd instead receives result slot A, which has not been explicitly initialized.
- No candidate adjustment or final comparison occurs.

### Partial result after a nonempty search

Assume a nonempty search, nonzero mode, no dependency effects changing result slot B before modification, and a modification dependency that writes only part of its result:

- Untouched bytes retain the zero values established before the final search comparison.
- Written bytes reflect the dependency’s writes.
- Status is one regardless of whether the resulting word is zero.

### Boundary storage reused for final modification

Assume zero mode, a zero boundary result, successful adjustment, and a nonzero final comparison:

- Result slot B receives the boundary word before the boundary call.
- That same slot is cleared before the final comparison.
- F-0ffa01c040fd receives that same slot afterward.
- Any pointer retained by the boundary dependency still designates that storage; later effects through it are not excluded.

### Differing adjustment-link reads

If the first candidate `0x08` read yields address P and the second yields non-null address Q, subtree traversal starts at P, not Q. If P is null, the non-null second read does not make the ensuing traversal valid.

If the second read is null, upward traversal is selected regardless of P.

### Candidate publication and modification position

With zero retained direction and zero mode, boundary handling is skipped. A zero final comparison publishes the candidate and status zero.

With an adjusted candidate and a nonzero final comparison, modification receives the retained initial-search position, not the adjusted candidate.

### Destination overlapping a node

If the destination overlaps node storage and all preceding accesses are valid, publication overwrites the overlapping bytes. No further dependency call or node read in this function observes those output writes.

## Evidence

Established behavior comes from static inspection of the supplied function representation: access widths and offsets, separate repeated reads, branch conditions, dependency argument order, internal-storage initialization and reuse, and publication ordering.

The two result slots have distinct histories. Both are cleared before each search comparison; only one holds the boundary word and is exposed alongside candidate storage; that same slot is cleared before the final comparison. These facts constrain partial-result behavior without establishing dependency contracts.

Ordered-tree insertion, predecessor selection, and duplicate rejection remain inferred intent.

No runtime tests have been performed. The acceptance examples are conditional consequences of static evidence, not observed executions.
