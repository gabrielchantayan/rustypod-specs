# F-118b1376b25b

## Purpose

F-118b1376b25b conditionally converts a sequence of numeric byte values into an integer, using conversion state held in a caller-provided object.

The routine supports direct accumulation for radices 2, 8, and 16. It delegates nonempty decimal conversion to F-fbdfd33b3145. It also records an initially empty sequence or an excessive significant length in the object’s status field.

This is a conversion of **numeric digit bytes**, not an established character parser. For example, the byte value 7 contributes seven; there is no visible conversion from the character encoding of “7,” and no visible validation that each byte is less than the selected radix.

The contract below describes established static behavior. The apparent intent is conversion into a 32-bit integer with optional negation. Pointer validity, target arithmetic semantics, and the decimal dependency impose qualifications described under **Uncertainties**. No runtime tests have been performed.

## Interface

These offsets describe the apparent 32-bit layout: four-byte integer fields and a four-byte stored pointer. They do not establish a portable layout for another ABI. The object’s other fields and its total size are not established.

Sequence elements are unsigned bytes. They are consumed as numeric values in the range 0 through 255.

### Output

The function returns an integer result. There is no separate success indicator in the return value. Zero may mean:

- Conversion was skipped because the initial status was nonzero.
- The initial sequence was empty.
- All bytes were zero.
- The radix was unsupported.

The status field must therefore be considered separately from the returned integer.

## Behavior

### Entry gating and empty input

The result begins at zero.

The status field is read first. If it is nonzero, all conversion work is skipped. The function still reads the flags field before returning.

If status is zero, the stored sequence-start pointer is read and compared with the supplied endpoint.

When these pointers are equal:

- Status is replaced with 1.
- The radix is not read.
- No sequence byte is read.
- The final flags processing still occurs.
- The returned numeric value remains zero.

Status 1 is an observed write value; its broader meaning in the surrounding system is not established.

### Leading-zero scan

For an initially nonempty sequence, the function advances a local position over bytes whose numeric value is zero.

At each position, it checks endpoint equality before reading the byte. It stops either:

- At the endpoint, after skipping all bytes; or
- At the first nonzero byte.

This movement is local. The function does not visibly update the stored sequence-start pointer.

Only after this scan does the function read the radix field. Thus, an unsupported radix does not prevent the initial sequence scan.

An initially nonempty sequence containing only zero bytes is distinct from an initially empty sequence. The all-zero sequence does not receive status 1. On the ordinary direct-radix paths it produces zero without changing status.

### Direct binary, octal, and hexadecimal conversion

For radices 2, 8, and 16, the function first checks whether the remaining significant span fits a radix-specific size bound.

Let \(n\) denote the number of bytes from the first nonzero position to the endpoint. If the scan reached the endpoint, \(n=0\). Under a valid forward range and exact address arithmetic, the checks are:

| Radix | Accepted span | Additional boundary case |
|---|---|---|
| 2 | \(n \leq 32\) | \(n=33\) is accepted only if the first remaining byte is less than 1. |
| 8 | \(n \leq 10\) | \(n=11\) is accepted only if the first remaining byte is less than 4. |
| 16 | \(n \leq 8\) | \(n=9\) is accepted only if the first remaining byte is less than 1. |

Larger spans are rejected.

Because the leading-zero scan normally leaves a nonzero first byte, the extra binary and hexadecimal cases cannot succeed for stable input storage. The octal boundary permits an eleven-byte significant span beginning with 1, 2, or 3.

The boundary checks can read the first remaining byte again. These are additional reads, not a guarantee that the value observed by the scan is reused.

If the check fails:

- Status is replaced with 128.
- No accumulation loop is entered.
- The result remains zero.
- Final flags processing still occurs.

The check is a significant-length and leading-byte check, not general digit validation. In particular, it does not reject an out-of-radix byte merely because its value is too large for a digit.

When the check succeeds, bytes are read in forward order through the exclusive endpoint. Each next byte contributes to positional accumulation: the accumulated value is multiplied by the radix, then the unsigned byte value is added.

For inputs whose intermediate values remain representable, this establishes the ordinary positional value. Behavior involving signed overflow requires the arithmetic qualification under **Uncertainties**.

A zero-length significant span performs no accumulation and returns zero.

### Decimal conversion

For radix 10, the function compares the post-scan position with the endpoint.

If that position is strictly before the endpoint, F-fbdfd33b3145 is called with the original object pointer. Its return value becomes the result.

The wrapper does **not** visibly:

- Pass the endpoint to the dependency.
- Pass the post-scan position to the dependency.
- Store the post-scan position in the object.
- Apply its own direct-radix size check.
- Validate decimal digits.
- Restore object fields after the call.

Consequently, the wrapper’s leading-zero scan establishes whether delegation occurs; it does not establish where or how the dependency reads decimal input.

If the scan reaches the endpoint, no dependency call occurs and the result remains zero.

### Unsupported radix

If the radix is neither 2, 8, 10, nor 16:

- No accumulation or dependency call occurs.
- The result remains zero.
- The wrapper makes no status write on that basis.

The preceding leading-zero scan has already occurred.

### Final sign handling

All normal paths converge on a final flags read.

If bit `0x2000` is set in the flags value read at that point, the result is arithmetically negated. Otherwise, it is returned unchanged.

For delegated decimal conversion, this read occurs after F-fbdfd33b3145 returns. A dependency change to the flags field can therefore affect the returned sign. No preservation of flags is assumed.

Negating zero leaves the numeric result zero. Negating the minimum representable signed integer has the arithmetic qualification described below.

## Side effects

- Status becomes 1 for an initially empty sequence when initial status was zero.
- Status becomes 128 when a direct-radix size check fails.

There is no visible status write for successful direct conversion, unsupported radix, or an initially nonempty all-zero sequence.

No direct write to the radix, flags, stored start pointer, or sequence bytes is shown.

### Observable access order

The established high-level order is:

1. Read status.
2. If status is zero, read the stored start pointer.
3. Either write status 1 for initial emptiness, or scan leading zero bytes.
4. For initially nonempty input, read radix.
5. Perform the selected size check, accumulation, dependency call, or unsupported-radix fallthrough.
6. Read flags.
7. Return the result, optionally negated.

In the direct conversion paths, accumulation rereads sequence bytes after the leading-zero scan and any boundary-byte inspection. The implementation does not establish snapshot semantics for mutable sequence storage.

The ordering above is logical static access order, not a synchronization or device-memory guarantee. Concurrent mutation, unusual aliasing, and volatile-memory behavior are not defined by the supplied evidence.

## Uncertainties

### Established static evidence

The control-flow gates, field indices, status writes, supported radix values, scan behavior, size-check conditions, dependency argument, and final flags read are directly established.

The function contains no visible digit validation, allocation, release, or direct sequence write.

### Inferred intent

The radix checks appear intended to bound results to 32 bits after removing leading zeros. Status 1 appears associated with empty input, and status 128 with an oversized direct conversion. Their system-wide symbolic meanings are not established.

Bit `0x2000` appears to request a negative result.

### documented_only: integer and pointer semantics

The apparent target model uses 32-bit integer arithmetic and pointer representations. Target ABI confirmation is absent.

The direct accumulation includes signed multiplication before addition involving an unsigned byte value. Signed multiplication can exceed the signed range even when the intended unsigned result fits 32 bits. Conversion of an out-of-range unsigned result back to a signed integer also requires target-specific semantics. Therefore, a universal modulo-\(2^{32}\) signed-return rule is not established.

Likewise, final negation of the minimum signed value is not portable signed arithmetic.

The size checks use address differences and signed arithmetic. Extremely large spans can overflow these calculations under a 32-bit model. Their behavior must not be replaced with unbounded mathematical length checks without target confirmation.

### documented_only: invalid ranges and mutation

A start beyond the endpoint is not rejected before scanning. The scan advances until pointer equality rather than enforcing a forward bound; invalid ranges may therefore cause reads outside valid storage.

Behavior under concurrent mutation, object/digit aliasing, or changes between repeated byte reads is not established as a supported use case.

### documented_only: decimal behavior

Decimal input syntax, bounds, sign interpretation, errors, and ownership remain dependent on F-fbdfd33b3145. No broader decimal guarantees can be inferred from the wrapper.
