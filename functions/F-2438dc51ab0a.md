# F-2438dc51ab0a

## Purpose

F-2438dc51ab0a conditionally returns a pointer obtained through a caller-supplied handle. Its decision depends on comparing a 32-bit value read from one input with the result of dependency F-c1596eeadd7b.

There are two established normal-return cases:

- The comparison differs: return the pointer currently stored in the handle through the output location.
- The comparison matches and that pointer equals the address of the comparison input: return that same pointer through the output location.

When the comparison matches but the pointer differs from the comparison input’s address, the function instead updates two linked-memory fields, conditionally invokes an indirect callback, and calls F-feee9156a257. The supplied static evidence marks that final call as non-returning. No output-store operation is established on this path.

The link updates resemble removal of an element from a doubly linked structure. That interpretation is inferred intent, not an established container or ownership contract.

## Interface

The function accepts three pointer arguments and has no direct return value:

| Argument | Role | Established access |
|---|---|---|
| Output location | Receives a pointer encoded in one 32-bit word on normal return | One 32-bit write, after the decision and dependency call |
| Comparison location | Supplies the initial comparison value; its address also participates in an identity comparison | One initial 32-bit read |
| Handle location | Holds a pointer to a record used by the function | Passed to F-c1596eeadd7b, then read as described below |

These are descriptive roles, not claims that the arguments are distinct or non-aliasing.

### Widths and address representation

The supplied representation uses four-byte integer fields and stores pointers in those fields. The contract therefore describes the observed 32-bit address representation:

- The initial comparison value is 32 bits.
- The value returned by F-c1596eeadd7b is compared with that 32-bit value.
- The handle contains a pointer represented in one 32-bit word.
- The output receives that pointer representation in one 32-bit write.
- Record offsets and indirect table offsets are measured in bytes.

The equality decision depends on matching the represented values; it does not involve ordering, signed arithmetic, or an explicit numeric conversion.

This is not evidence that the interface can be widened to native pointers on another architecture without changing its layout.

### Record and indirect-dispatch layout

For a record addressed through the handle, the function accesses these fields:

| Byte offset | Width | Use |
|---|---:|---|
| +4 | 32 bits | Pointer used as one link |
| +8 | 32 bits | Pointer used as another link |
| +12 | 32 bits | Optional pointer used for indirect dispatch |

Offset +0 of the record is not directly accessed by this function.

If the +12 field is nonzero when tested, indirect dispatch uses:

1. The pointer obtained from the +12 field.
2. A pointer read from offset +0 of that referenced object.
3. A callable address read at byte offset +4 in the resulting table.

The invocation has no explicit arguments in the supplied representation. Its actual ABI, any implicit receiver, and the meaning of the callback remain unknown.

### Preconditions

Successful execution requires valid memory for the accesses actually taken:

- The comparison location must permit an initial four-byte read.
- The handle must satisfy whatever requirements F-c1596eeadd7b imposes, and must permit the later handle reads.
- On normal return, the output location must permit a four-byte write.
- On the link-update path, the referenced record and both link destinations must support the accesses described below.
- When indirect dispatch is selected, the object, table, and callable entry must be valid for that invocation.

There are no established null checks for the arguments, the record pointer, or either link pointer. Only the optional dispatch field is explicitly tested for zero.

## Behavior

### Initial observation and dependency call

The function first reads the 32-bit value at the comparison location. This is a saved value: the function does not reread that location to make the subsequent value comparison.

It next invokes F-c1596eeadd7b with the handle location itself, not merely with the pointer stored there.

The saved value is compared with the dependency’s result after that invocation completes. Any mutation performed by the dependency can therefore affect later handle reads, but does not replace the saved comparison value.

The supplied function imposes no established preservation requirement on F-c1596eeadd7b. Its effects on the handle, other memory, or global state are unknown.

### Different comparison values

If the saved value differs from the dependency’s result:

1. The function reads the pointer currently stored at the handle location.
2. It writes that pointer representation to the output location.
3. It returns normally.

This path does not directly inspect the referenced record’s link or dispatch fields. Consequently, a zero record pointer is not itself rejected or dereferenced by this function on this path. It can be written as the output, subject to the dependency’s independent requirements.

### Matching comparison values and identical addresses

If the saved value equals the dependency’s result, the function reads the pointer currently stored at the handle location.

It compares that pointer with the address of the comparison location. This is an address-identity test, not another comparison of the values stored at those addresses.

If the addresses match:

1. No link updates are performed.
2. No optional callback is invoked.
3. F-feee9156a257 is not called.
4. The saved record pointer is written to the output location.
5. The function returns normally.

Thus equal stored comparison values do not by themselves select the non-returning path. Address identity determines the remaining branch.

### Matching comparison values and different addresses

If the saved value equals the dependency’s result, but the record pointer differs from the comparison location’s address, execution performs the following stages.

**First link update.** Using the record pointer already loaded for the address comparison, the function:

- Obtains the pointer field at record offset +8.
- Obtains the 32-bit field at record offset +4.
- Writes the latter value to offset +4 of the object addressed by the former pointer.

In conventional link notation, the neighbor selected by the +8 field has its +4 field replaced with the original record’s +4 value. This notation does not establish semantic names such as “previous” or “next.”

**Second link update.** After the first write, the function rereads the handle while obtaining the operands for another write:

- A pointer from offset +4 of a record reached through the handle identifies the destination object.
- The destination is that object’s field at offset +8.
- A 32-bit value from offset +8 of a record reached through the handle supplies the replacement value.

This second update is not established to use the original record pointer saved for the address comparison. If the first write aliases the handle or later-read fields, subsequent reads observe the resulting memory.

The supplied expression contains separate handle reads for the destination and replacement value. Their relative evaluation order within that expression is not established. A contract requiring one of those operand reads to occur first would exceed the evidence.

**Optional indirect invocation.** After both link writes, the function examines the +12 field of a record reached through the handle.

- If this field is zero, indirect invocation is skipped.
- If it is nonzero, the function performs the dispatch-table lookup described under Interface and invokes the resulting callable.

The dispatch expression reloads the handle and dispatch field rather than explicitly retaining the value used for the zero test. No snapshot guarantee between the check and dispatch is established for environments that permit intervening mutation.

**Final dependency call.** After the optional callback returns, or immediately if it was skipped, the function rereads the handle and passes the pointer currently stored there to F-feee9156a257.

The argument is not necessarily the record pointer used for the initial address comparison. In particular, an indirect callback that changes the handle can change the final dependency’s argument.

The supplied static representation marks F-feee9156a257 as non-returning. Accordingly, this branch has no established normal completion and no established output write. Behavior if that dependency unexpectedly returns is documented_only.

### Aliasing and sequencing

No non-aliasing restriction is established.

On a normal-return path, the output write occurs after the initial comparison read, the dependency call, the value comparison, and the handle read. If the output aliases the handle or comparison location, that final write overwrites the aliased location only after its relevant earlier observation.

On the link-update path, earlier writes may alter addresses or values used by later accesses. The implementation does not establish atomic removal, transactional rollback, or a consistent snapshot of all link fields.

Execution order is established between the two link-write statements, the optional invocation, and the final dependency call. Operand evaluation order within an individual compound expression is not fully established.

## Side effects

Directly established effects are:

- One initial 32-bit read from the comparison location.
- One invocation of F-c1596eeadd7b with the handle location.
- One 32-bit output write on either normal-return path.
- Alternatively, two ordered 32-bit link writes, a conditional indirect invocation, and a call to F-feee9156a257 on the matching-but-distinct path.

No direct allocation or explicit ownership transfer is visible. The final dependency’s placement after link updates is consistent with disposal, but does not prove deallocation, destruction, termination, or any particular ownership rule.

There is no established error return, status field, exception handler, or rollback mechanism. Invalid pointers and invalid callable addresses are not translated into a documented recoverable error by this function.

Effects of either named dependency and the indirect callback are unknown beyond the observable invocation structure. They must not be assumed to preserve global state or to acquire, retain, or release memory.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

### Different values return the post-dependency pointer

Given an initial comparison value of 7, a dependency result of 8, and a handle containing pointer P after the dependency returns:

- The output receives P.
- This function performs no link writes or indirect invocation.
- It does not call F-feee9156a257.
- It returns normally.

If the dependency changed the handle from Q to P, P is the relevant value.

### Matching values with address identity return normally

Given a saved comparison value equal to the dependency result, and a post-dependency handle pointer equal to the comparison location’s address:

- The output receives that address.
- No record-link or dispatch-field access is required by this branch.
- The function returns normally.

### Matching values with distinct addresses update links

Given matching comparison values and a handle pointing to a distinct record R, suppose R has +4 link A and +8 link B. Assume valid, non-overlapping memory and no intervening mutations.

- The first write stores A at B’s +4 field.
- The second write stores B at A’s +8 field.
- Both writes precede any optional indirect invocation.
- The output location is not written before the final non-returning call.

The non-overlap condition makes this example simpler than the full alias-sensitive contract.

### Absent dispatch skips only the callback

On the link-update path, if the +12 field tested after both writes is zero:

- No indirect invocation occurs.
- The final handle read and call to F-feee9156a257 still occur.

### Callback changes the final argument

On the link-update path, suppose a valid callback runs and replaces the handle contents with S before returning.

- F-feee9156a257 receives S.
- It is not required to receive the earlier record pointer.

### Dependency changes the comparison location

Suppose the function initially reads 5, and F-c1596eeadd7b later changes that location to 9 but returns 5.

- The equality branch is selected using the saved 5.
- The later address-identity test still uses the comparison location’s address, regardless of its new contents.
