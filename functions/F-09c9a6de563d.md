# F-09c9a6de563d

## Purpose

F-09c9a6de563d updates caller-supplied storage by transferring an opaque four-byte value, replacing the original value with an address representation, advancing an object-relative signed integer, and conditionally replacing an object-relative address.

The conditional decision affects only the final address-field replacement. A candidate address that does not satisfy the comparison does not cancel the payload transfer, source replacement, or integer update.

**Established static behavior:** the destination receives the source payload before that source is replaced. The integer update observes storage after those payload-slot mutations. The address-selection decision observes storage after the integer update and selects replacement only when the source address compares strictly below the address then held in the tracked field.

**Inferred intent:** these effects are consistent with inserting a location into a linked structure while maintaining a count and a lowest-address marker. The evidence does not establish that interpretation. In particular, the function does not traverse a structure, count its members, validate links, or establish an allocation relationship.

## Interface

### Arguments and result

The operation accepts three inputs:

| Input | Behavioral role |
|---|---|
| Object locator | A signed integer used to locate fields at byte offsets 12 and 16. It is not independently established as an object pointer. |
| Destination address | Identifies the storage receiving the initial payload. This address is subsequently recorded at the source location. |
| Source address | Identifies the storage supplying the initial payload. This address itself is the candidate for the tracked-address update. |

There is no return value or explicit status output.

“Source” and “destination” describe the payload transfer, not permissions or ownership. Both locations are written. The value stored in the source is not the candidate used for address selection; the candidate is the source location’s address.

### Storage layout and widths

| Storage role | Location | Required access |
|---|---|---|
| Destination slot | Destination address | Four-byte payload write |
| Source slot | Source address | Four-byte payload read and replacement write |
| Tracked-address field | Object locator plus 12 bytes | Address-valued read; conditional address-valued write |
| Integer field | Object locator plus 16 bytes | Signed-integer read and write |

The payload-slot width is explicitly four bytes. The integer field uses the represented signed-integer type, and the tracked-address field uses a pointer type. Their independently confirmed target widths are unavailable.

Four-byte integers and four-byte pointers would make the two object-relative fields adjacent and would permit an address-sized value to occupy a payload slot without narrowing. That model is consistent with the representation, but it is not independently verified. Field spacing alone does not prove field width or disjointness. A wider tracked-address access could overlap the integer field.

The source replacement records the destination address in the source slot. The representation does not establish how an address wider than that four-byte slot would be converted or encoded. Such a case is **documented_only**; truncation, rejection, or a wider replacement must not be assumed.

## Behavior

### Result with independent storage

When the four storage roles do not overlap, no external participant modifies them, and the required arithmetic and address operations are supported, normal completion establishes the following:

| Storage | Required result |
|---|---|
| Destination slot | The source slot’s entry four-byte payload |
| Source slot | The destination address in the supported four-byte representation |
| Integer field | The successor of its entry signed value |
| Tracked-address field | The source address if it compares strictly below the observed tracked address; otherwise its existing value |

The payload is opaque. Its contents are transferred without being interpreted or followed. A payload whose bits resemble a null address or an inaccessible address does not, for that reason alone, cause a rejection or a dereference.

Selection is strict. Equality does not select replacement. Neither does a greater candidate under the applicable ordering. Those outcomes leave the other mutations in force.

The tracked-address decision concerns the source address, not the transferred payload and not the destination address recorded in the source.

### Observation boundaries

The behavior is not an all-at-entry snapshot.

The destination’s payload comes from the source before the source replacement. The recorded destination address therefore cannot become the transferred payload merely because it is written during the same invocation.

The integer’s relevant value is the value present after both slot mutations. If a slot mutation changes the integer storage, that changed value supplies the increment.

The tracked address is observed after the integer update. Its value can consequently reflect an earlier slot mutation or an overlapping integer write. Any selected tracked-address replacement occurs after that observation.

These are logical access relationships established by the supplied representation. They do not specify machine instructions, atomic access sizes, barriers, or a physical bus trace. There is no independent logical read of the destination’s old contents; those contents matter only if another accessed storage role overlaps them.

### Aliasing and overlapping storage

The independent-storage result must not be applied unchanged when locations overlap.

**A shared source and destination slot.** The payload transfer does not preserve the entry payload in a separate location. The shared slot is subsequently replaced by its own address representation. That is its final content only if later field updates do not affect the same bytes.

**Destination overlapping the integer field.** The transferred payload can determine the integer representation that is subsequently incremented. With compatible four-byte representations and exact coincidence, a payload representing signed 20 leads to an integer result of 21, regardless of the integer field’s entry value.

**Source overlapping the integer field.** The destination receives the source’s entry payload. The source replacement then changes the storage observed by the integer update. The later integer write can overwrite the recorded destination address. No general numerical result follows without knowing the address representation and its interpretation as the signed integer.

**A slot overlapping the tracked-address field.** The comparison can observe a value introduced by the slot mutations instead of the field’s entry address. A selected tracked-address write can, in turn, replace part or all of a slot result.

**The two object-relative fields overlapping.** The integer update can affect the address used by the later comparison. The conditional address write can affect the integer’s final bytes. Their starting offsets alone do not exclude this possibility without a confirmed width model.

Partial overlap additionally depends on byte order, widths, alignment, and the validity of accessing the same bytes through the represented types. A universal byte-level result is **documented_only**.

The absence of a conditional tracked-address write does not imply preservation of that field’s entry bits: an earlier overlapping mutation may already have changed them.

### Integer and address semantics

The integer update is signed. Negative values are not rejected; they advance when their successors are representable.

No overflow check or saturation behavior is visible. Modular wraparound is not an established guarantee. Under a signed 32-bit model, an observed value of 2,147,483,647 has no specified normally completing successor.

The object locator is also signed. Forming its field locations requires additions of 12 and 16 and interpretation of the resulting values as addresses. Valid source and destination slots do not compensate for unsupported locator arithmetic or inaccessible object-relative fields.

The strict address comparison does not establish a portable numerical ordering over every possible address representation. Unrelated allocations, null addresses, or invalid representations require applicable target semantics. Describing the tracked field as a “minimum” is therefore conditional on a suitable ordering model.
