# F-2399e3fb9a97

## Purpose

F-2399e3fb9a97 performs a multi-phase finalization of a caller-supplied state object:

1. Processes its records in reverse order, invoking context operations and handling attached pair arrays.
2. Processes records in forward order, conditionally rewriting fixed-width entries in a context-associated stream.
3. Invokes cleanup operations for selected record attachments.
4. Updates global allocation accounting and conditionally returns the enclosing allocation through an allocator interface.

These phases and their ordering are established by static evidence. Describing the routine as a finalizer, its context operations as emission, or its dependency calls as deallocation is inferred intent. The supplied material does not establish the full semantics of those dependencies.

The routine has no explicit result value. Its observable results are dependency calls, changes to stream entries, changes to accounting state, and any effects performed by dependencies. One invalid-allocation path invokes a dependency identified as non-returning.

## Behavior

### 1. Capture context and invoke initialization

The routine first reads the descriptor-region address and the context address obtained through the parent object.

It then invokes F-9d122d3a77c6 with:

- The parent-object address.
- The 32-bit value `0xFFFFFFFF`.
- The third argument.
- The fourth argument twice.

Only after this call does it read the signed 16-bit descriptor count used for reverse traversal. Consequently, changes made by that dependency to the captured descriptor region can affect the reverse-pass count. Replacing the state’s descriptor pointer does not replace the already captured address.

### 2. Process records in reverse order

A positive descriptor count produces record order from count minus one down to zero. Zero or a negative signed count produces no reverse iterations.

For each record:

1. Invoke F-2148ac0f693b with the captured context and record field +36.
2. If record field +44 differs from `0x17`, invoke F-887ba2404a49 with the context as its only explicitly shown operand.
3. If the signed pair-count field is nonzero, process the attached pair array as described below.
4. Invoke F-2148ac0f693b with the context and record field +28.
5. If record field +12 is nonzero, perform the additional operation group described below.

#### Attached pairs

A nonzero pair count first causes F-2148ac0f693b to receive record field +32.

The routine then rereads the pair count and obtains the array address. Positive counts traverse the array in reverse pair order. Each pair contains two 32-bit words. For each pair, in order:

- Invoke F-2f5fbad4fdef with the context and the second word plus one.
- Invoke F-887ba2404a49 with the context, selector `0x67`, the first word, and the second word.
- Invoke F-2f5fbad4fdef with the context and the second word minus one.

The plus-one and minus-one expressions are 32-bit operations; there is no explicit saturation or overflow handling.

After the loop, invoke F-94cb53877c15 with the record’s array-address field as read at that time.

A negative nonzero pair count enters this branch but executes no pair operations. It still performs the initial context-selection call and the final F-94cb53877c15 call. Thus negative and zero counts are observably different.

#### Additional operation group

When record field +12 is nonzero:

1. Invoke F-211638bb75da with the context and selector `0x7B`; retain its 32-bit result.
2. Invoke F-211638bb75da with selector `0x7C` and the descriptor value at the current reverse index, offset +32.
3. If record field +24 is signed nonnegative, invoke F-211638bb75da again with selector `0x7C`, with no further explicit operand shown.
4. Invoke F-887ba2404a49 with selector `0x5B`, a zero operand, and record field +40.
5. Invoke F-a2b3e96577b2 with the context, the retained result, and the current context field +12.

The final context-field read occurs after the preceding calls. It must not be treated as a value captured at function entry.

### 3. Select the common context position

After reverse traversal, invoke F-2148ac0f693b with the context and state field +20.

### 4. Process records in forward order

The forward pass begins at record zero. Before every iteration it rereads the signed 16-bit descriptor count from the captured descriptor-region address. Unlike the reverse pass, this is not a single fixed-count traversal.

For each reached record, the routine reads that record’s descriptor index and obtains the referenced object through descriptor offset +20.

Forward processing proceeds only when:

- The object’s byte at +53 is zero; and
- Its 32-bit field at +24 is zero.

A nonzero discriminator prevents the +24 read. Either a nonzero discriminator or a nonzero +24 field skips all remaining forward work for that record.

#### Conditional descriptor operation

For an eligible record, invoke F-211638bb75da with selector `0x20` and the descriptor’s +32 value only when both conditions hold:

- The state’s mode byte at +4 is zero.
- The record flags do not contain `0x00080000`.

A nonzero mode byte skips this call regardless of the flags.

#### Mapping operation and stream rewrite

If the eligible record’s mapping address at +16 is nonzero:

1. Invoke F-211638bb75da with selector `0x20` and record field +24.
2. Reread the mapping address.
3. If it is now zero, skip the scan.
4. Otherwise capture the record flags and call F-b05552b91301 with the context and state field +12.
5. After that call, read the context’s +12 field as the scan limit and reread state field +12 as the initial scan index.

The returned address is the first 20-byte stream entry considered. The scan advances by 20 bytes while its signed index is less than the captured signed limit. No visible end-marker check is performed.

Only entries whose identifier at +4 equals record field +20 are candidates for modification:

| Entry kind | Additional condition | Modification |
|---|---|---|
| `0x03` | Entry operand matches an element in the mapping array. | Replace operand with the first matching zero-based mapping index, then replace identifier with record field +24. |
| `0x27` | None. | Replace identifier with record field +24, then change kind to `0x35`. |
| `0x7C` | Captured record flags contain `0x00080000`. | Change kind to `0x17`; leave identifier and operand unchanged. |
| Any other kind | — | No modification. |

For kind `0x03`, the mapping search proceeds from index zero upward using the signed mapping count. A zero or negative count yields no match. Duplicate mapping values resolve to the first matching index. An unmatched operand leaves the entry unchanged.

The scan continues after each match, so multiple entries may be changed. Later records can revisit entries modified by earlier records.

### 5. Process record attachments

When the forward pass terminates, the routine reaches a null-state check. Under ordinary valid entry conditions the state address cannot become null merely because dependencies changed memory.

It then traverses records from zero while the index is less than the signed state field +24, rereading that bound for successive iterations. For every record with nonzero field +72, it invokes F-94cb53877c15.

No explicit argument is visible at this call site. It is not established that the tested attachment value is passed to the dependency.

### 6. Update enclosing-allocation accounting and release

The routine computes an enclosing-base address by subtracting the 32-bit word immediately preceding the state from the state address. It reads a 32-bit accounting amount at enclosing base minus eight.

A global accounting object contains low and high 32-bit words at offsets +56 and +60. The low word is reduced by the accounting amount. The high word is reduced by the sum of:

- The accounting amount’s arithmetic sign extension, represented as either zero or minus one.
- The unsigned borrow from the low-word subtraction.

All stored results are 32 bits. This is not unconditionally an unsigned 64-bit subtraction: amounts with their top bit set use the signed-extension term.

The routine next invokes F-2fd8826557a4, then reads a global allocator-state address.

If the enclosing-base numeric value is eight, it returns without the remaining allocator operations. The preceding accounting updates and dependency call have already occurred.

Otherwise it reads an allocation header at enclosing base minus 16. A zero header or a header with bit zero set invokes the non-returning F-a817d8d58c10. Earlier phases and accounting changes are not rolled back.

For an accepted header:

1. Invoke F-c0fc6d033caa with the allocator-state address.
2. Derive a size by masking the current header with `0x3FFFFFFC`.
3. Subtract that size from four allocator counters:
   - Counter family based at +548, indexed by the unsigned 16-bit value at enclosing base minus 12.
   - Aggregate counter at +780.
   - Counter family based at +224, indexed by the unsigned 16-bit value at enclosing base minus 10.
   - Aggregate counter at +544.
4. Invoke F-09dcb55e8e0a and use its result as an index to decrement a counter based at +784.
5. Decrement the counter at +912.
6. Subtract the freshly reread masked header size from allocator field +8.
7. Invoke F-cc6c9b4a0f68 with the allocator-state address and header address.
8. Invoke F-e586bff64fb7 with the allocator-state address, then return.

The counter arithmetic has no visible underflow checks. No dependency’s name or placement establishes synchronization or ownership semantics by itself.

## Side effects

Established direct effects include:

- Ordered dependency invocations.
- Conditional in-place stream changes.
- Global accounting subtraction.
- Allocator statistics updates.

The routine does not visibly clear released attachment fields, clear pair-array addresses, or mark the state as finalized. Repeated invocation is therefore not established as safe.

Memory release is suggested by the placement of F-94cb53877c15 and the allocator dependencies, but their actual ownership rules are unknown. A caller must not infer that an attachment remains usable, has been released, or can be released again without those dependency contracts.

No rollback is visible. A dependency failure, invalid access, or non-returning allocation failure can occur after earlier observable effects.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, dependencies return normally and do not change the relevant input fields.

1. **Two records with positive count:** Reverse processing visits record one before record zero. Forward processing visits record zero before record one.

2. **Zero descriptor count:** Both record-processing phases are skipped. The common context-selection call and subsequent cleanup/accounting phases still occur.

3. **Negative pair count:** The pair-selection call and F-94cb53877c15 call occur, but no individual pair operations occur.

4. **Two attached pairs:** The second pair is processed before the first. Each pair produces the plus-one operation, selector-`0x67` operation, and minus-one operation in that order.

5. **Nonzero object discriminator:** The object’s +24 field is not read, and the record performs neither forward selector-`0x20` operation nor stream scanning.

6. **Mapping changed to zero by the first mapping-related call:** The initial nonzero mapping causes the replacement selector operation, but the subsequent zero reread prevents the scan.

7. **Kind `0x03`, operand matching mapping positions two and five:** The operand becomes two and the identifier becomes the replacement identifier. Position five is not selected.

8. **Kind `0x7C` with the controlling flag set:** A matching entry becomes kind `0x17`; its identifier is not replaced.

9. **Kind `0x27` with a matching identifier:** Identifier replacement occurs before the kind becomes `0x35`. The operand is unchanged.

10. **Zero or odd allocation header:** The non-returning failure dependency is reached after earlier finalization and global accounting effects. No transactional restoration is visible.
