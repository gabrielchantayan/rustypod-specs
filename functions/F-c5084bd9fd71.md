# F-c5084bd9fd71

## Purpose

F-c5084bd9fd71 updates selected records in a fixed-stride array. It derives a 32-bit output value from records designated as anchors, then marks each successfully updated record.

**Established behavior:** anchor designation, eligibility checks, coordinate comparisons, dependency calls, output writes, and status-bit changes follow the rules below. Anchor selection uses signed coordinate differences bounded by strict sentinel comparisons, not an unrestricted nearest-neighbor search.

**Inferred intent:** the operation resembles interpolation between anchors and extrapolation from a single anchor. The mathematical behavior of either dependency is not established here, so those names describe the apparent purpose rather than a guaranteed numerical result.

## Interface

The function accepts two arguments:

1. **Context address:** an address providing access to a record count, a record-array address, and a configuration-array address.
2. **Configuration index:** a signed 32-bit integer used to select one configuration entry.

There is no explicit return value. Results are communicated through record-memory writes and any effects of dependencies.

### Configuration access

Before checking whether there are records to process, the function reads one opaque 32-bit configuration word at:

**configuration-array address + configuration index × 204 + 200**

The selected entry therefore has an apparent stride of 204 bytes, with the accessed word at offset 200. No index validation or configuration-array bounds check is visible.

The configuration word is captured once and reused for every single-anchor dependency call during this invocation.

### Record layout

Records are 48 bytes apart.

| Offset | Width | Meaning used by this function |
|---|---:|---|
| 12 | 32 bits | Control word; bits `0x02` and `0x04` are examined |
| 16 | 32 bits | Status word; bits `0x10`, `0x20`, and `0x40` are used |

| 21 | 8 bits | Second comparison byte |

Bit `0x10` in the status word designates an anchor. This function does not directly change that bit.

Bit `0x20` is set after a target receives an output value. Its broader meaning is unknown.

## Behavior

### Entry reads and traversal

The function first captures the record-array address. It then fetches the configuration word and finally captures the outer record count.

Consequently, a zero count does **not** suppress the configuration access. It does suppress record-field processing.

For an ordinary nonnegative count, the function visits the corresponding number of records in array order, advancing 48 bytes after each visit. The outer traversal uses its captured count and captured starting address; it does not reload them to decide how many outer visits remain.

The anchor search described below is different: each eligible target reloads the record-array address and count from the context.

### Anchor records are skipped

For each visited record, the function first reads the status word at offset 16.

If bit `0x10` is set, the record is skipped. This path performs no direct control-word, output-value, or completion-bit write.

Being skipped as a target does not prevent the record from serving as an anchor for other targets.

### Eligibility of non-anchor records

For a non-anchor record, the function reads its control word at offset 12.

If bit `0x02` is clear, the record proceeds directly to anchor searching.

If bit `0x02` is set, processing is conditional:

1. If the byte at offset 20 equals 4, skip the record.
2. Otherwise, if the bytes at offsets 20 and 21 differ, skip the record.
3. Otherwise, if status bit `0x40` is clear and control bit `0x04` is also clear, skip the record.
4. Otherwise, clear control bit `0x02`, preserving the other bits of the captured control word, and continue.

These checks short-circuit. The offset-21 byte is not needed when the first byte equals 4. The additional status-word read for bit `0x40` occurs only after the byte checks permit it.

Clearing bit `0x02` occurs **before** searching for anchors. That change remains even if the search finds no usable anchor and no output is written.

### Anchor search

For an eligible target, the function captures its signed coordinate from offset 36. It then reloads the record-array address and count and scans that many records, but only while the reloaded count is positive.

Each candidate’s status word is examined. Only candidates with bit `0x10` set participate.

For each participating candidate, the function calculates:

**candidate coordinate − captured target coordinate**

It maintains two independent selections:

- **Nonpositive-side anchor:** the candidate with the greatest difference that is at most zero and strictly greater than −32000.
- **Positive-side anchor:** the candidate with the smallest difference that is strictly greater than zero and strictly less than 32000.

Thus:

- Difference zero belongs to the nonpositive side.
- Difference −32000 is excluded.
- Difference +32000 is excluded.
- Under ordinary non-overflowing arithmetic, accepted differences range from −31999 through +31999.
- A tie does not replace an existing selection, so the first equally ranked anchor in scan order wins.

An anchor outside these strict bounds is ignored even when it is the only anchor.

The scan reads candidate coordinates while selecting anchors. Later calculations reread coordinates or outputs from selected anchors; the scan does not capture a complete immutable snapshot of them.

### No selected anchor

If neither side has a selected anchor, the function advances to the next outer record without writing the target’s output or setting bit `0x20`.

Any earlier clearing of control bit `0x02` remains effective.

### Exactly one selected anchor

When only one side has an anchor, the function calls **F-74efb2674226** with:

1. The captured target coordinate minus a newly read coordinate from the selected anchor.
2. The configuration word captured at entry.

After the call returns, the function reads the selected anchor’s output at offset 44 and adds it to the dependency’s returned value.

The resulting 32-bit value becomes the target output.

The post-call output read matters: if the dependency changes the selected anchor’s output without invalidating the access, the addition uses the changed value, not a pre-call snapshot.

An exact-coordinate anchor is not automatically copied in this case. If it is the only selected anchor, F-74efb2674226 is called with a first argument of zero.

### Both sides selected

When both sides have selected anchors:

- If the saved nonpositive difference is zero, the function directly reads and uses the nonpositive anchor’s output. Neither dependency is called.
- Otherwise, on ordinary stable execution, the function calls **F-8f41f510c86c** with three 32-bit arguments:
  1. Captured target coordinate minus the nonpositive anchor’s newly read coordinate.
  2. Positive anchor output minus nonpositive anchor output.
  3. Positive anchor coordinate minus nonpositive anchor coordinate.

After F-8f41f510c86c returns, the function rereads the nonpositive anchor’s output and adds it to the returned value.

The supplied representation also contains a branch that directly selects the positive anchor’s output when the saved positive-side distance is zero. Under the stated selection rule, that distance is set only from a strictly positive difference, so this branch is not reachable in ordinary execution. It does not establish another supported selection mode.

The three dependency arguments are established, but the relative evaluation order of their separate memory reads is not.

### Committing a result

After obtaining a result, the function:

1. Writes the 32-bit output at target offset 44.
2. Reads the target’s current status word at offset 16.
3. Writes that word with bit `0x20` set.

The status update therefore preserves the bits present at this final read, rather than restoring the status snapshot taken at the start of processing.

There is no check for an already-set bit `0x20`. Such records remain eligible for recalculation.

## Side effects

The function’s direct writes are limited to:

- Clearing control bit `0x02` for records that pass the conditional eligibility checks.
- Writing an output value for records with usable selected anchors.
- Setting status bit `0x20` after an output write.

The visible operation does not directly allocate, release, retain, or transfer ownership of memory. This does not establish the ownership behavior of either dependency.

The function provides no transactional rollback:

- A cleared control bit remains cleared if no anchor is found.
- An output write precedes the completion-bit write.
- A dependency failure or invalid memory access may interrupt processing after earlier records have changed.

No explicit error return, diagnostic, or recovery path is present.

There is no visible synchronization. Concurrent mutation can affect eligibility, anchor selection, values reread after selection, and the final status update. No thread-safety guarantee is established.

Dependencies must not be assumed to preserve context fields, records, configuration storage, or unrelated global state. In particular:

- Later anchor searches reload the context’s array address and count.
- The outer traversal continues from its previously captured address.
- The configuration word remains the entry snapshot.
- Selected-anchor output values may be read after a dependency returns.

If a dependency invalidates record storage, the subsequent accesses are not protected.

## Acceptance examples

These examples are conditional specifications derived from static evidence, not runtime observations. Unless stated otherwise, they assume valid stable memory, non-overflowing signed arithmetic, and dependencies that return normally without modifying the relevant records.

1. **Zero records still require configuration access.**  
   With count zero and valid entry addresses, the configuration word is read, then the function returns without reading record fields. An invalid configuration access is not made safe by the zero count.

2. **Anchor records are untouched by direct target processing.**  
   A visited record with status bit `0x10` set receives no direct writes, regardless of its control bits or byte values.

3. **Conditional rejection leaves the target unchanged.**  
   A non-anchor with control bit `0x02` set and byte 20 equal to 4 is skipped. No anchor search, control clearing, output write, or completion-bit write occurs.

4. **Control clearing can occur without output completion.**  
   A non-anchor has control bits `0x02` and `0x04` set, equal comparison bytes other than 4, and no usable anchors. Bit `0x02` is cleared; bit `0x04` is preserved. Its output and status remain unchanged.

5. **Strict search boundaries exclude distant anchors.**  
   For target coordinate 100, anchors at −31900 and 32100 have differences −32000 and +32000. Neither is selected. Anchors at −31899 and 32099 are within the respective accepted boundaries.

6. **Equal-coordinate ties use the first anchor.**  
   Two anchors both have coordinate 90 and the target coordinate is 100. If neither is superseded by a closer nonpositive anchor, the first in scan order is selected.

7. **A lone exact match still calls the single-anchor dependency.**  
   A target and its only selected anchor both have coordinate 100. F-74efb2674226 receives zero and the captured configuration word. If it returns 7 and the subsequently read anchor output is 40, the target receives 47.

8. **An exact match with both sides selected bypasses dependencies.**  
   With an anchor at coordinate 100, another at 110, and target coordinate 100, the target receives the first selected coordinate-100 anchor’s output directly.

9. **Two-sided calculation uses dependency output, not an assumed formula.**  
   A target at 100 has selected anchors at 90 and 110 with outputs 20 and 60. F-8f41f510c86c receives 10, 40, and 20. If it returns 13, the target receives 33. A result of 40 is not guaranteed without the dependency’s contract.

10. **Completion preserves the current status word.**  
    After a successful output calculation, a status word of `0x40` becomes `0x60`. If the dependency changed other status bits before the final status read, those currently present bits are preserved by the bitwise update.
