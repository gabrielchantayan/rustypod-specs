# F-8f49ed59b67e

## Purpose

F-8f49ed59b67e attempts to obtain two bytes from a stream-like object, interpret them as an unsigned big-endian 16-bit value, and advance the object's position by two.

Two access modes are established:

- Direct access through an address derived from the object's base and position.
- Indirect access through an object-supplied callback.

A detected bounds failure or callback return other than exactly two causes an explicit status write of `0x55`, followed by two diagnostic calls and, if both calls return, a zero return.

The operation is not transactional. Callback effects are not rolled back. Status storage may alias object fields. Dependencies are not established to preserve globals, object state, status storage, or ownership.

## Interface

### Arguments

The supplied representation has four arguments:

| Argument | Representation | Established use |
|---|---|---|
| Object address | Pointer to 32-bit words | Supplies the fields described below |
| Status address | Pointer to a 32-bit word | Receives explicit status writes |
| Auxiliary word | 32 bits | No operational use established on the non-null-object path; replaced by global metadata for the null-object diagnostic |
| Initial scratch word | 32 bits | Initializes an addressable local scratch cell used as the callback destination |

The scratch initializer can affect the result if the callback reports two without replacing both bytes that the function subsequently consumes.

### Object layout

Offsets are relative to the object address.

| Byte offset | Width | Role |
|---|---:|---|
| 0 | 32 bits | Base address used for direct access |
| 4 | 32 bits | Size used by the bounds comparison and failure diagnostics |
| 8 | 32 bits | Current position |
| 12–19 | Not accessed directly here | No behavior established |
| 20 | 32 bits | Callback address; zero selects direct access |

The representation uses 32-bit address-bearing words. No portable interface for wider pointers is established. This table does not establish the complete object layout or fields accessed by dependencies.

### Return value and status

The return is a 32-bit integer.

- Successful conversion returns a value from zero through 65,535.
- A detected failure returns zero if both failure diagnostics return.
- Direct access whose computed address is zero also returns zero, without a local error report, and follows the successful position-update path.

A zero return therefore does not distinguish successful conversion, the zero-address special case, and detected failure.

The function explicitly writes a full 32-bit zero to the status destination before examining bounds. On detected failure, it subsequently writes `0x00000055`.

A final status of zero on success requires that no intervening dependency or aliased object write changes the status location. The function does not restore zero immediately before returning.

### Preconditions and limits

Ordinary completion requires:

- Writable 32-bit status storage.
- An object permitting all field accesses required by the selected path.
- A callable callback when its field is nonzero.
- Two accessible bytes at any nonzero address selected for conversion.
- Valid address formation and position arithmetic in the execution environment.
- Returning dependencies wherever the described outcome requires execution to continue.

The function checks for a zero object address, but does not locally return or branch away after the associated diagnostic. Safe handling of that case depends on the diagnostic not returning or otherwise preventing subsequent invalid accesses.

There is no corresponding local check for a zero status address. Invalid memory accesses are not converted into the documented status failure.

## Behavior

### Entry and null-object diagnostic

The function first initializes its local 32-bit scratch cell from the fourth argument.

When the object address is zero, it prepares assertion-related diagnostic arguments. The global metadata reads have an explicit order:

1. Read the stored 32-bit value that will become diagnostic argument three.
2. Read the stored address-bearing value that will become diagnostic argument two.
3. Call F-540af0155702 with the diagnostic format-like address as argument one and those two captured values as arguments two and three.

Thus, the metadata for argument three is read before the metadata for argument two, even though the latter appears earlier in the diagnostic argument list. These are global reads, not reads through the supplied object or status addresses. The exact metadata contents and diagnostic text are not supplied.

The original auxiliary argument does not supply diagnostic argument three on this path. The original status address is likewise not substituted for the stored value used as diagnostic argument two.

There is no explicit return after F-540af0155702. If it returns, execution continues with the status write and an attempted position read through the zero object address. A clean null-object error return is not established.

### Initial status write and bounds check

After the null-object handling, if execution continues, the function:

1. Writes a 32-bit zero to the status destination.
2. Reads and captures the object's position.
3. Compares the captured position, incremented by one using 32-bit unsigned arithmetic, against the object's size interpreted as unsigned.

Access is admitted only when:

**(captured position + 1 modulo 2³²) < unsigned size**

For positions that do not wrap during this addition, this requires both requested byte offsets to lie below the size. Position 8 with size 10 passes; position 9 with size 10 fails.

At position `0xFFFFFFFF`, the unsigned addition produces zero. Any nonzero size therefore passes the numerical guard at that position. This does not establish the validity of subsequent address formation or position arithmetic.

If the guard fails, the function takes the failure path without consulting the callback field, invoking the callback, or reading data bytes.

Because the status write precedes the position capture and size comparison, aliasing status storage with object fields can change the decision.

### Access-mode selection

After a passing bounds check, the callback field determines the access mode:

- Zero selects direct access.
- Nonzero selects an indirect call through that field.

The callback field is not an ownership indicator. Its interpretation here establishes only a callable target and the zero/nonzero selection.

### Direct access

For direct access, the function derives a candidate address from the base-address field and the previously captured position.

If the candidate address is nonzero, the conversion uses:

- The byte at the candidate address as the high-order byte.
- The byte at candidate address plus one as the low-order byte.

The resulting value is:

**256 × high-order byte + low-order byte**

Both bytes are treated as unsigned. The result is a nonnegative integer no greater than 65,535.

This establishes byte significance, not temporal load order. The supplied expression does not establish whether the byte at the lower address or the byte at the higher address is loaded first.

If the candidate address is zero, the function skips both data-byte loads, retains a result of zero, and continues to the successful position update. It does not set an error status for this case.

The zero test applies to the computed address, not independently to the base field. A zero base with a nonzero position is not automatically rejected.

The representation does not establish portable wrapping semantics for overflowing direct-address arithmetic.

### Indirect access

The callback receives four arguments, in this order:

1. Object address.
2. Captured position.
3. Address of the local 32-bit scratch cell.
4. Requested byte count, exactly two.

The callback return is compared with exactly two. Every other result takes the failure path, including zero, one, negative values, and values greater than two.

When the callback returns two, the conversion uses:

- The byte at the scratch address as the high-order byte.
- The byte at scratch address plus one as the low-order byte.

As with direct access, byte significance is established, but the temporal order of these two loads is not.

The function does not verify that the callback wrote either byte. It does not clear the scratch cell immediately before the call or obtain a replacement data pointer from the callback return. A callback that reports two after writing only part of the requested data can cause retained scratch bytes to participate in conversion.

The retained bytes come from the fourth argument's 32-bit representation. Their correspondence to particular bits of that argument depends on the host word representation, which is not independently established here.

The scratch storage has local-call lifetime. No allocation or explicit ownership transfer is shown. A callback may retain the address, but later use after this function returns is not supported by that storage lifetime.

### Successful position update

After conversion, or after skipping data loads because the direct candidate address is zero, the function reads the object's position again, adds two, and writes the result to the position field. It then returns the converted or retained result.

This is a fresh position read, not an update based exclusively on the position captured before the callback.

Consequently, if a callback changes position from the captured value to 20 and returns two, the function increments 20 to 22, assuming valid arithmetic.

The supplied representation expresses this update using signed integer addition. Unlike the unsigned bounds increment, overflowing position updates are not established to have portable wraparound behavior.

### Detected failure

A failed bounds check or callback return other than two causes this sequence:

1. Write the full 32-bit value `0x55` to the status destination.
2. Call F-4457a9a44a68 with a short-read-related diagnostic label.
3. If that call returns, obtain the object's position and size for a second call to F-4457a9a44a68, together with a position/size diagnostic format-like argument.
4. If the second call returns, return zero.

The second diagnostic uses field values obtained for that call, not necessarily the values used by the earlier bounds decision. The relative order of the position and size reads used as its arguments is not established by the supplied expression.

The status error write precedes both diagnostics. The first diagnostic may affect state before the second diagnostic's field values are obtained.

There is no explicit successful-path position increment on failure and no rollback. A rejected callback may already have modified the position, other object fields, scratch storage, or external state.

## Side effects

### Explicit local and memory effects

The supplied material establishes:

- Initialization of one local 32-bit scratch cell.
- Ordered global metadata reads on the null-object path.
- A zero write to status before bounds examination.
- A later `0x55` status write on detected failure.
- Object-field reads needed for bounds, mode selection, direct addressing, position updating, and diagnostics.
- Two byte loads for conversion when the selected data address is nonzero.
- A position read and write on the successful path.
- Calls to the selected callback and diagnostic dependencies.

No explicit allocation, deallocation, resource close, or release appears.

### Aliasing and dependency effects

No non-aliasing checks are present.

If status aliases the position word, the initial status write sets position to zero before it is captured. If status aliases size, callback, or base storage, the same write may alter bounds, access-mode selection, or direct addressing.

On failure, writing `0x55` may alter an aliased object field before diagnostics inspect it. On success, the position write may change status storage if the two overlap.

Dependencies may introduce further effects. Neither the callback nor the diagnostic functions are established to preserve globals, object memory, status memory, resources, or ownership. Claims of unchanged state require explicit assumptions excluding relevant aliasing and dependency effects.

## Acceptance examples

These are conditional deductions from static evidence, not executed tests. Unless an example says otherwise, assume valid storage and arithmetic, non-overlapping status storage, returning diagnostics, and no dependency effects beyond those stated.

1. **Direct conversion.**  
   Position 4, size 6, zero callback field, and bytes `0x12` and `0xAB` at offsets 4 and 5 produce return `0x12AB`, final position 6, and status zero. No ordering between the two byte loads is required.

2. **Unsigned maximum.**  
   A successful conversion using high byte `0xFF` and low byte `0xFF` returns 65,535, not −1.

3. **One byte remains.**  
   Position 5 and size 6 fail the guard. Status becomes `0x55`; both failure diagnostics are called; the return is zero. No data access or explicit position increment occurs.

4. **Callback completion.**  
   A callback that writes `0x80` at the scratch address, writes `0x01` at the next address, and returns two produces 32,769. If it leaves position unchanged, position advances by two.

5. **Excess count rejected.**  
   A callback return of three takes the failure path even if both requested bytes were written.

6. **Callback changes position and succeeds.**  
   With captured position 4, a callback that sets position to 20 and returns two causes the successful update to store 22.

7. **Callback changes position and fails.**  
   A callback that sets position to 20 and returns one is not rolled back. If diagnostics leave the object unchanged, position remains 20.

8. **Zero direct address.**  
   If bounds pass but direct address formation yields zero, no data bytes are loaded. The function returns zero and still performs the successful position update.

9. **Unsigned guard wraparound.**  
   Position `0xFFFFFFFF` and size 1 pass the numerical guard. This example makes no claim about subsequent valid address formation or overflowing position updates.

10. **Status aliases position.**  
    The initial status write sets the captured position to zero. If the operation succeeds without other position changes, the later position write stores two in that same location; its final contents are therefore not a zero status.

11. **Null-object metadata order.**  
    With a zero object address, metadata supplying diagnostic argument three is read first, metadata supplying argument two is read second, and F-540af0155702 is then called. If it returns, there is no clean local error return: the function continues toward status and object accesses.
