# F-896114e013fb

## Purpose

F-896114e013fb attaches a newly obtained node to a caller-selected position in a tree-like structure, updates header links and a stored count, performs color-based rebalancing, and returns the new node address through an output location.

The supplied static evidence is consistent with red–black tree insertion: a one-byte color, parent and child links, a header containing root and extreme-node links, recoloring, and two rotation-like dependencies. Those semantic names are inferred intent. The established contract is the sequence of field accesses, conditional updates, and dependency calls described below.

This function does not search for an insertion position or check for an existing equal value. The caller supplies the proposed parent and a placement control. Correct ordering and structural validity therefore depend on caller preconditions and dependency behavior.

## Interface

The function has five inputs and no direct return value:

| Input | Representation | Role |
|---|---|---|
| Output location | Address of a writable 32-bit slot | Receives the new node address on normal completion. |
| Container address | 32-bit address | Provides the header pointer, count, and comparator-related state. |
| Placement control | 32-bit integer | Any nonzero value forces attachment through the selected parent’s first child link. Zero permits a comparison unless the parent is the header. |
| Selected parent | 32-bit address | Node or header beneath which the new node is attached. |
| Value address | Address of a readable 32-bit word | Supplies the payload word and, when comparison is needed, an argument to the comparison dependency. |

The evidence uses 32-bit pointer-bearing fields and 32-bit integer fields. It does not establish portability to wider pointers.

### Preconditions

For a normal successful insertion:

- Every address accessed on the selected path must designate suitably readable or writable storage.
- The node-producing dependency must return a usable node with the initialization required by the balancing logic.
- The header, parent links, child links, and color bytes must form a structure on which the balancing walk terminates safely.
- The selected parent and placement control must describe a valid insertion position. Existing child links are overwritten without occupancy checks.
- Dependency behavior must be compatible with the mutations already performed before each call.
- The output and value locations must remain valid for their respective accesses.

No general non-aliasing guarantee is established. Aliasing the inputs with structural fields can change behavior because values and header pointers are read at different stages.

## Behavior

### 1. Obtain the node and copy the payload

The function first calls F-ffe3c25e7ae8 with the container address. Its returned address becomes the new node address.

It then checks whether the address sixteen bytes beyond that result is nonzero. If so, it reads one 32-bit word from the value address and writes that word at offset 16 in the new node.

This is not a conventional null-result check. A zero node address does not, by itself, make the checked payload address zero under ordinary 32-bit address arithmetic. Conversely, the effective payload address could be zero for a particular near-boundary node address. No safe allocation-failure behavior follows from this condition.

The payload operation is a single 32-bit copy, not a demonstrated deep copy. If the word represents a pointer or handle, the function does not explicitly duplicate or release its referent.

### 2. Increment the count

After the conditional payload copy, the function reads the 32-bit count at container offset 20, adds one, and stores the result back to that field.

This happens before comparison, attachment, or rebalancing. It is not deferred until successful completion, and no rollback is visible.

The evidence does not establish a supported overflow case. The field is 32 bits, but the presented signed addition does not justify promising defined wraparound for every execution model.

### 3. Select the attachment direction

The function reads the current header pointer from container offset 16 and compares it with the selected parent.

The first-child path is selected if either:

- The selected parent equals that header pointer; or
- The placement control is nonzero.

No comparison dependency is called on either path.

Otherwise, the placement control is zero and the selected parent differs from the header. The function calls F-bcefa5957e76 with:

1. The address at container offset 25.
2. The original value address.
3. The address at selected-parent offset 16.

A nonzero result selects the first-child path. A zero result selects the second-child path. The result is not interpreted as a negative/zero/positive ordering.

Because the comparator receives the original value address, not the newly copied payload address, changes to the source word before that call can affect comparison independently of the stored payload.

### 4. Attach the node and maintain header links

On the first-child path, the function first writes the new node address to selected-parent offset 8. It then reloads the container’s header pointer.

If the reloaded header differs from the selected parent:

- The header’s offset-8 field is inspected.
- That field is replaced with the new node address only if its current value equals the selected parent.

If the reloaded header equals the selected parent:

- The new node address is written to header offset 4, establishing the root.
- The container’s header pointer is read again.
- The offset-12 field of that resulting header is unconditionally set to the new node address.

For a stable, initially empty header selected as the parent, these operations set its root and both extreme links to the new node.

On the second-child path:

- The new node address is written to selected-parent offset 12.
- The current header pointer is read from the container.
- The header’s offset-12 field is replaced with the new node address only if it currently equals the selected parent.

Finally, after these attachment and header updates, the selected parent address is written to the new node’s offset-4 parent field.

There is an observable interval in which a parent or header points to the new node but the function has not yet stored the new node’s parent field. The function provides no visible synchronization or atomic multi-field update.

### 5. Rebalance

The balancing walk starts with the new node as its current node.

At each loop test, the function reloads the header pointer and reads its root link. If the current node is the root, the walk stops. Otherwise, it reads the current node’s parent and examines that parent’s color byte. Any nonzero parent color stops the walk.

When the parent’s color is zero, the function reads the parent’s parent as a grandparent and distinguishes two structural cases.

#### Parent is the grandparent’s first child

The grandparent’s second child is treated as the opposite-side node.

If that node exists and its color byte is zero:

1. The parent’s color is set to 1.
2. The opposite-side node’s color is set to 1.
3. The grandparent reached through the current node’s then-current parent chain has its color set to 0.
4. The current node advances to the grandparent reached through that chain.

If the opposite-side node is absent or has a nonzero color:

- When the current node is the parent’s second child, F-1476b82dc9cd is called with the container and parent. After it returns, the current node becomes the previously captured parent address.
- The parent reached from the current node is colored 1.
- The grandparent reached from the current node is colored 0.
- F-cfe689dcfe89 is called with the container and a grandparent address read through that parent chain.

#### Parent is not the grandparent’s first child

This branch is taken for every inequality, not only after an explicit check that the parent is the grandparent’s second child.

The grandparent’s first child is treated as the opposite-side node.

If that node exists and its color byte is zero, the same recoloring-and-upward-advance behavior applies.

Otherwise:

- When the current node is the parent’s first child, F-cfe689dcfe89 is called, and the current node subsequently becomes the previously captured parent address.
- The parent reached from the current node is colored 1.
- The grandparent reached from the current node is colored 0.
- F-1476b82dc9cd is called with the container and a grandparent address read through that parent chain.

The inner F-cfe689dcfe89 call has additional arguments in the supplied evidence; they are documented under Dependencies.

Color reads distinguish zero from every nonzero byte. Color writes use exactly 0 and 1. Calling these states “red” and “black” is inferred intent, not an independently established interface definition.

### 6. Finish and publish the result

After the balancing loop, the function reloads the container’s header pointer, reads its root pointer, and writes color byte 1 to that root.

Only then does it write the original new node address to the output location.

Thus, successful result publication follows root recoloring. If the output location aliases another field, this last write may overwrite earlier state changes.

## Side effects

Direct side effects can include:

- A 32-bit payload write to the new node.
- One 32-bit count increment.
- Replacement of a selected parent’s child link.
- Updates to root and extreme-node links.
- A parent-pointer write in the new node.
- Color-byte writes to ancestors and opposite-side nodes.
- A final color-byte write to the current root.
- A final 32-bit write to the output location.

Dependencies may produce additional effects. Their global-state behavior, allocation behavior, and memory ownership effects are not established by this function.

There is no explicit deallocation, payload destruction, diagnostic emission, error return, duplicate rejection, or rollback. This does not prove that dependencies never perform such actions.

The function is not transactionally isolated: the count and attachment changes occur before balancing completes. Failure or nonlocal exit after those changes can leave partially modified state.

## Acceptance examples

These examples are conditional static expectations, not runtime test results.

### Empty-header insertion

Given a stable header selected as the parent, a valid node returned by F-ffe3c25e7ae8, valid storage, and no disruptive dependency effects:

- No comparison occurs.
- The payload word is copied, subject to the payload-address condition.
- The count increases by one within its supported range.
- Root and both extreme links become the new node.
- The new node’s parent becomes the header.
- Balancing immediately recognizes the new node as root.
- The root color becomes 1 before the output receives the node address.

### Forced first-child attachment

Given a non-header parent and any nonzero placement control:

- No comparison occurs.
- The parent’s offset-8 link is replaced.
- The header’s offset-8 link changes only if it currently equals that parent.
- Balancing then proceeds from the new node.

The function does not reject an already occupied child slot.

### Comparator-selected second-child attachment

Given zero placement control, a non-header parent, and a comparator result of zero:

- The parent’s offset-12 link receives the new node.
- The header’s offset-12 link is updated only when it equals the selected parent.
- The new node’s parent field is subsequently written.
- The retained final two arguments for any reachable six-argument balancing call are zero.

### Nonzero parent color

Given that the new node is not root and its parent’s color byte is 7, the balancing loop stops at the parent-color check. The function still writes 1 to the current root’s color and publishes the new node.

### Zero-colored opposite-side node

Given a zero-colored parent and an existing opposite-side node whose color is zero, that balancing iteration recolors both to 1, recolors the grandparent to 0, and advances upward without calling either rotation-like dependency in that iteration.

### Invalid node result

A zero result from F-ffe3c25e7ae8 does not imply graceful failure. The payload-address condition does not establish null-node handling, and later operations require usable node storage.
