# F-e2e160a9301a

## Purpose

F-e2e160a9301a classifies an incoming event selector and, for a recognized event, conditionally invokes one handler on a supplied receiver.

Its observable distinction is **recognized versus unrecognized**, not handler success:

- A recognized selector produces the 32-bit result **1**, including when a matching event is suppressed by an event-family sentinel.
- A selector that fails every comparison produces the 32-bit result **0**.
- Handler return values do not determine this function’s result.

The supplied static representation establishes an ordered dispatch mechanism. It does not establish the semantics of the comparison dependency, the actual sentinel values, the concrete event-string bytes, or the behavior of the selected handlers.

### Output

### Sentinel state

Two distinct global sentinel locations participate in suppression:

- **Sentinel A:** associated with the first five event positions.
- **Sentinel B:** associated with the remaining six event positions.

Their values are unknown. The evidence does not establish that they differ, remain constant, or are unaffected by dependencies.

The timing of the reads is part of the contract.

#### Sentinel A timing

Immediately after the first comparison returns, Sentinel A is read and captured, before the first comparison result is acted upon.

- If the first event matched, the suppression check uses a **fresh read of Sentinel A**, not the previously captured value.
- If a later event in positions 2–5 matches, its suppression check uses the value captured after comparison 1.
- Comparisons 2–5 do not refresh that captured value.

Thus, modifications to Sentinel A by a later comparison do not affect suppression for positions 2–5 in that invocation.

#### Sentinel B timing

Sentinel B is read only after all first-five comparisons have returned nonzero.

The sixth comparison, for the selection event, runs first. Immediately after it returns, Sentinel B is read and captured, before that comparison result is acted upon.

- If position 6 matched, the suppression check uses a **fresh read of Sentinel B**.
- If a later event in positions 7–11 matches, its suppression check uses the value captured after comparison 6.
- Comparisons 7–11 do not refresh that captured value.

Consequently, even an entirely unrecognized selector causes both initial sentinel captures: Sentinel A after comparison 1 and Sentinel B after comparison 6.

The supplied representation shows these separate accesses. Whether an underlying compiled execution preserves separately observable reads, and whether concurrent changes are permitted, is not independently established.

### First event family: positions 1–5

For a recognized event in this family:

- Equality between the event argument and the applicable Sentinel A value suppresses the handler.
- A suppressed event returns 1 without reading the receiver’s dispatch-table base or the selected function-pointer entry in this function.
- Otherwise, the function reads the receiver’s first word, loads the event’s designated table entry, and invokes that target with the receiver and event argument, in that order.
- If the target returns normally, the function returns 1.

No further selector comparisons occur after the match.

For position 1, “applicable Sentinel A value” means the fresh read taken for its equality check. For positions 2–5, it means the captured value taken after comparison 1.

### Second event family: positions 6–11

For a recognized event in this family:

- Equality between the event argument and the applicable Sentinel B value suppresses the handler.
- A suppressed event returns 1.
- Otherwise, positions 6–9 and 11 invoke their respective direct dependencies.
- Position 10 reads the receiver’s first word, loads the entry at byte offset `0x128`, and invokes that target.
- Every invoked handler receives the original receiver and original event argument, in that order.
- If the target returns normally, the function returns 1.

For position 6, the applicable sentinel is the fresh read taken for its inequality check. For positions 7–11, it is the captured value taken after comparison 6.

### Unrecognized selectors

If all eleven comparisons return nonzero, the function returns 0.

There is no event-argument validation, fallback handler, or indirect receiver access on this local path. Sentinel captures and comparison calls have already occurred; their effects are not undone.

## Side effects

### Established local effects

The function visibly:

- Calls the comparison dependency between one and eleven times.
- Reads Sentinel A after the first comparison.
- Reads Sentinel A again for the first-event suppression check when that event matches.
- Reads Sentinel B after the sixth comparison, if that comparison is reached.
- Reads Sentinel B again for the sixth-event suppression check when that event matches.
- On an unsuppressed indirect-dispatch path, reads the receiver’s table-base word and then the selected function-pointer entry.
- Invokes at most one event handler.

No explicit write to receiver storage, sentinel storage, selector storage, or event-argument storage appears in the supplied representation. There is no visible allocation, release, ownership transfer operation, or retained-pointer assignment performed directly by this function.

### Dependency effects and ownership

The absence of local writes does not imply a side-effect-free call. Comparison calls and handlers may change globals or other state.

In particular:

- Later comparisons may change a sentinel after its captured value has been taken.
- A comparison may change receiver state before a later dispatch-table read.
- A handler may modify or invalidate the receiver.
- A handler may allocate, release, or retain memory.

None of those behaviors is established or prohibited by this function alone. Ownership remains **documented_only** beyond the fact that arguments are passed to the identified dependencies. The contract must not assume that a dependency preserves globals or refrains from releasing memory.

### Preconditions and failure boundaries

A valid executable target is required whenever an indirect handler is actually invoked. The receiver’s first word and selected entry must be readable under the execution environment’s memory rules.

A readable receiver is not locally required for a suppressed event or for an entirely unrecognized selector, because those paths do not dereference it here. That is not a general guarantee that arbitrary receiver values are safe: direct handlers receive the receiver, and unknown dependencies may have additional requirements.

No visible mechanism handles:

- Invalid selector data.
- An unreadable receiver or dispatch table.
- A null or invalid function-pointer entry.
- A dependency failure.
- An unsupported event argument.

The only explicit negative classification result is 0 for an unrecognized selector.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests.

1. **First event, handler suppressed.**  
   Given a zero result from comparison 1, and an event argument equal to the fresh Sentinel A read used for the suppression check, the result is 1. No handler is invoked, and this function does not read the receiver’s dispatch table.

2. **First event, handler invoked.**  
   Given a zero result from comparison 1 and an event argument unequal to the fresh Sentinel A value, the function invokes the current entry at `0x154` with the original receiver and event argument. If that handler returns normally, the result is 1 regardless of its return value.

3. **Later first-family event uses the earlier capture.**  
   Suppose comparison 1 returns nonzero, Sentinel A is then captured as value X, and comparison 2 changes Sentinel A to Y before returning zero. With event argument X, dispatch is suppressed even if Y differs from X. The result is 1.

4. **Selection event uses a post-comparison sentinel read.**  
   Suppose comparisons 1–5 return nonzero, and comparison 6 changes Sentinel B before returning zero. Suppression is determined from the Sentinel B read used by the selection branch, not from any value before comparison 6.

5. **Later second-family event uses the captured Sentinel B.**  
   Suppose Sentinel B is captured as X after comparison 6 returns nonzero. A subsequent comparison changes it to Y, and the highlight comparison returns zero. With event argument X, F-e7680695fe4c is not invoked, even if Y differs from X.

6. **Remote video event dispatch.**  
   Given nonzero results for positions 1–9, a zero result for position 10, and an event argument unequal to captured Sentinel B, the entry at `0x128` is invoked exactly once. Position 11 is not compared.

7. **Fully unrecognized selector.**  
   Given eleven nonzero comparison results and normal dependency completion, the result is 0. No event handler is called. The initial reads of both sentinels still occur.

8. **Multiple potential matches.**  
   If the comparison dependency would report zero for both the artist and album operands, the artist match takes precedence. The album comparison is never attempted.

9. **Handler failure is not successful classification completion.**  
   If a selected handler does not return normally, the evidence does not establish a normal result of 1. Recognition alone does not override dependency control flow.
