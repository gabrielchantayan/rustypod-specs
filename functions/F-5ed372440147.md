# F-5ed372440147

## Purpose

F-5ed372440147 conditionally snapshots a four-word record associated with a receiver, publishes that snapshot to caller-supplied storage, and invokes two operations using a separate, mutable working copy.

The condition is whether a 32-bit field at receiver offset `0xEC` is zero. If it is zero, the function does not write the output record or invoke either dependency. Its return value then consists of the original receiver value in the low 32 bits and the original second argument in the high 32 bits.

If the field is nonzero, the function copies four words from the referenced object, writes those words to the output, passes its working copy to F-45424d41541c, and subsequently invokes an indirectly selected operation. The returned 64-bit value consists of the first two working words as they exist after both calls return.

This is a structural description. The semantic meanings of the receiver, associated object, four-word record, and second argument are not established. In particular, the evidence does not establish that the record represents coordinates, dimensions, or any other domain-specific value.

## Interface

### Inputs

The function has three arguments:

| Argument | Established role |
|---|---|
| Receiver | A 32-bit value used as the base address of an object. It is also passed unchanged as the first argument to F-45424d41541c. |
| Auxiliary value | A 32-bit integer passed unchanged as the second argument to F-45424d41541c. It also supplies the high return word when the conditional branch is not taken. |
| Output address | An address used for four consecutive 32-bit writes when the conditional branch is taken. |

The supplied representation uses 32-bit integer and address-bearing values. The interface should therefore be understood as a 32-bit addressing model, not as a portable native-pointer interface of unspecified width.

The receiver is dereferenced unconditionally. A zero receiver is not handled as an absent receiver.

The dispatch-table interpretation describes the observed indirection. A particular object model, language ABI, or class identity is not established.

### Return value

The result is a 64-bit bit-vector formed from two 32-bit words:

- Bits `31:0`: the first working word.
- Bits `63:32`: the second working word.

Equivalently, its unsigned interpretation is the low word plus the high word multiplied by \(2^{32}\). Each word contributes its existing 32-bit pattern. There is no additional sign extension from the low word into the high word.

No status-code interpretation is established. The third and fourth working words do not contribute directly to the return value.

### Preconditions and completion

For normal completion:

- The receiver field at offset `0xEC` must be readable.
- If that field is nonzero, the four source words must be readable and all four output words must be writable.
- Both dependencies must accept their supplied arguments and return normally.
- The post-helper dispatch reads must resolve to usable object, table, and callable addresses.

The function contains no explicit checks for these conditions and exposes no explicit error return. Invalid addresses, nonreturning dependencies, or dependency failures have no established recovery behavior.

## Behavior

### Initial observation and default return state

The function first reads the 32-bit field at receiver offset `0xEC`.

Its initial working state places the receiver value in the first word and the auxiliary value in the second word. The remaining two working words do not have established initial values on the untaken branch, but they are neither passed to a dependency nor used in the return value on that branch.

### Zero associated-object field

If the initial field read is zero:

- No source record is read.
- The output address is not dereferenced.
- Neither dependency is invoked.
- The return value has the original receiver bits in its low word and the original auxiliary bits in its high word.

Consequently, this path does not require the output address to designate writable storage. That does not remove the unconditional requirement for the receiver-field read to be valid.

### Nonzero associated-object field: snapshot

If the initial field read is nonzero, that value supplies the base for four 32-bit reads, in this order:

1. Offset `0x80`.
2. Offset `0x84`.
3. Offset `0x88`.
4. Offset `0x8C`.

These values replace all four words of the function’s working record.

All four reads occur before any explicit output write. This matters when output storage overlaps the source record: the published values come from the completed working snapshot, rather than from an interleaved read-and-write copy.

The source base for these four reads is the initially obtained nonzero value. The function does not independently reload the receiver’s associated-object field between the four source reads.

### Publishing the snapshot

The function writes the four working words to the output address, in order, at byte offsets `0`, `4`, `8`, and `12`.

These writes precede both dependency calls. The directly published output is therefore the pre-helper snapshot, not a copy of the working record after processing.

The function performs no further explicit writes to the caller’s output record. That does not guarantee the output remains unchanged: dependencies may have access to the same storage through aliases, globals, or reachable objects.

The publication is not established to be atomic. The visible sequence contains four separate word writes, and no synchronization mechanism is shown.

### Processing the working record

After publication, the function invokes F-45424d41541c with:

- The original receiver value.
- The original auxiliary value.
- The address of its four-word working record.

The output address is not explicitly passed to this dependency.

The dependency is not assumed to preserve the working record, receiver fields, associated objects, dispatch structures, globals, or aliased output storage. Any return value it produces is not explicitly used by this function.

### Indirect dispatch after processing

After F-45424d41541c returns, the function obtains dispatch information through receiver offset `0xEC` again. It does not deliberately reuse the initially saved associated-object address for this operation.

The indirect target is reached by reading an object address through that field, reading the object’s leading dispatch-table address, and reading the callable at table byte offset `0x68`.

The indirect operation receives:

- An object address obtained through receiver offset `0xEC`.
- The address of the same working record supplied to F-45424d41541c.
- A zero-valued third argument.

There is no second zero check before this dispatch. If the helper or an earlier aliased output write has made the dispatch state unusable, no local fallback is established.

The supplied expression contains separate accesses to the receiver field for target selection and for the object argument. Their relative evaluation order is not established. The contract therefore does not promise that these accesses observe an identical object if the field changes during evaluation.

The indirect operation’s return value is not explicitly used.

### Final result

After the indirect operation returns, the function returns the first and second words of its working record as the low and high halves of the 64-bit result.

Either dependency may have modified these words through the supplied record address. Thus, on the taken branch:

- The output writes publish the initial snapshot.
- The return value reflects the final first two working words.
- Those two observations need not agree.

## Side effects

### Direct effects

The established direct effects are:

- A read of receiver offset `0xEC` on every invocation.
- Four source-word reads when the initial field is nonzero.
- Four ordered output-word writes on that branch.
- Invocation of F-45424d41541c.
- Further receiver, object, and dispatch-table reads for the indirect call.
- Invocation of the indirectly selected operation.

There is no explicit allocation, deallocation, ownership transfer, logging, or synchronization in the visible body.

### Ownership and lifetime

The caller supplies the receiver and output storage. The function does not explicitly release either.

The working record is temporary storage belonging to this invocation. Both dependencies receive its address. The visible body establishes its availability during those synchronous calls, but does not establish that either dependency refrains from retaining the address.

No ownership or release behavior may be attributed to either dependency from this evidence alone. Safe retention beyond the invocation is not established.

### Aliasing and mutation

No non-aliasing restriction is explicitly checked.

If output storage overlaps the source record, the complete source snapshot precedes publication. If output storage overlaps the receiver field or dispatch-related memory, publication may change the state subsequently used by the helper or indirect call.

There is no rollback after output publication. If later processing fails to return normally, the earlier output writes have already occurred, subject to the execution environment’s memory semantics.

The later indirect target and object argument are obtained through the replacement state. The earlier snapshot remains sourced from the original object.

If the replacement is zero or otherwise unusable, successful dispatch is not guaranteed; the function has no second guard.
