# F-08d8ffa87760

## Purpose

F-08d8ffa87760 conditionally synchronizes three cached 32-bit values with three observed values and, when synchronization is required, makes ordered calls concerning two opaque objects.

An update uses different data generations for different purposes:

- The existing first and second cache values determine geometry limits.
- The newly observed third value determines complementary controls.
- All three observations replace their corresponding caches before any dependency is called.

Every normally completing invocation returns the 32-bit value **1**, whether or not an update occurs. This result does not establish that any dependency achieved its intended effect.

The geometry and complementary controls suggest presentation or compositing behavior. That interpretation is inferred intent, not an established meaning of the objects, dimensions, or dependency arguments.

## Interface

### Input and result

The sole explicit input is an address identifying a memory object. The supplied representation uses 32-bit address-bearing fields, 32-bit integer fields, and one byte-sized selector.

The result is a 32-bit word equal to 1 on normal completion. There is no explicit error return, input validation, or recovery path.

## Behavior

### Update decision and observation consistency

An update occurs if any observed value differs from its corresponding cache.

The observations are captured before any direct write or dependency call. They are not an atomic snapshot. The established read order is:

- First cache.
- First record address and its observation.
- Second record address and its observation.
- Third cache, conditionally.
- Third record address and its observation.

The third cache is read only when the first observation matches the first cache. The second cache is read for comparison only when both the first and third comparisons match.

Thus, comparison precedence is first, third, then second, although the second observation is obtained before the third observation. A first mismatch avoids the third-cache comparison read; a mismatch in either of the first two comparisons avoids the second-cache comparison read.

When all comparisons match, the function returns 1 without direct writes or dependency calls. It does not need the base dimensions, selector, or opaque-object fields on that path.

An update always includes a later read of the second cache for geometry. If the second comparison determined the update, the comparison read and geometry read are separate. They need not agree if memory changes between them.

### Geometry limits

The width limit depends on the first cache value captured before the observations. The height limit depends on the second cache value read during update processing. Replacement observations do not determine these limits.

Subject to the signed-arithmetic qualifications in **Uncertainties**, each cache value is converted as follows:

- Apply a bias of 32,767 in signed 32-bit arithmetic.
- Discard sixteen fractional bits by signed right shift.
- Reduce the result to a multiple of four by clearing its two least significant bits.
- Bound the result below by zero and above by the axis maximum.

The width maximum is **320**; the height maximum is **240**. Both resulting limits are nonnegative multiples of four.

For arithmetic signed right shift and a representable biased sum, an equivalent mathematical description of the value before clamping is:

\[
4\left\lfloor
\frac{\left\lfloor(\text{signed cache}+32767)/65536\right\rfloor}{4}
\right\rfloor .
\]

This is not general rounding to the nearest multiple of four. For example, cache values equal to seven and eight times 65,536 produce limits of four and eight, respectively.

### Retained dimensions and placement

The base width is read before the base height.

Each axis has a retained dimension and a crop offset. If the base dimension is no greater than its limit, it is retained unchanged and its crop offset is zero. Otherwise, the crop offset is the base dimension’s half minus the limit’s half, with each division independently truncating toward zero. The retained dimension is the base dimension less twice that offset.

For positive dimensions, this produces equal integer cropping on opposite sides. Since each limit is even:

- A cropped even base dimension becomes exactly its limit.
- A cropped odd base dimension becomes one greater than its limit.
- An odd positive base dimension can therefore retain one unit even at a zero limit.

Negative dimensions are not rejected or normalized. They are below every possible limit, remain unchanged, and receive zero crop offsets.

Horizontal placement is 160 minus half the retained width. Vertical placement is 120 minus half the retained height. These divisions truncate toward zero, and each resulting coordinate is bounded below by zero. There is no explicit upper bound.

For example, a retained width of −5 yields horizontal coordinate 162. Such a width prevents geometry submission, but its coordinate calculation still occurs.

Once the limits have been established, the crop and placement calculations remain within signed 32-bit range for signed 32-bit base dimensions. The unresolved overflow concern is the earlier biased addition used for limit conversion.

### Cache commitment and external interactions

Every update commits all three captured observations, including observations whose comparisons were skipped. The stores occur in this order:

1. Third observation to the third cache.
2. Second observation to the second cache.
3. First observation to the first cache.

These are separate 32-bit writes, not an atomic transaction. Every store precedes every dependency call. The vertical coordinate’s lower-bound adjustment occurs after the stores and before the calls; no dependency intervenes.

An update then has the following externally observable call order:

| Order | Interaction |
|---|---|
| First | Control call for object A |
| Second | Control call for object B |
| Third, when eligible | Geometry call for object B |
| Next | Final interaction for object A |
| Last | Final interaction for object B |

There is no rollback. A dependency that fails to return can leave the caches updated while later interactions remain unperformed. A subsequent invocation may consequently find no changes to propagate.

### Complementary controls

The third observation supplies an extracted value between 0 and 255. Its bit pattern is increased by 32,767 using unsigned 32-bit arithmetic, with wraparound modulo \(2^{32}\). Bits 16 through 23 of that result form the extracted value; all other bits are discarded.

This conversion wraps rather than saturates.

| Selector byte | Object A control | Object B control |
|---|---:|---:|
| Zero | Extracted value | 255 minus extracted value |
| Nonzero | 255 minus extracted value | Extracted value |

The selector is read after cache commitment and before the first control call. It is not read again between the two calls.

F-460b2abbbbbe receives object A first, then object B. Each control argument is a 32-bit value whose numeric range is 0–255.

Object B is read from `0x24` after the first control call returns. A dependency-induced change to that field can therefore affect the second control call. It does not cause the selector or captured observation to be reconsidered.

### Final interactions

F-1d891874186d is called for object A with the associated value at `0x1C`, then for object B with the associated value at `0x18`.

These object and associated-value fields are read after the controls and any geometry call. The fields for the second final interaction are read after the first final interaction returns.

The supplied representation does not establish the relative order of the two field reads within either individual final-call argument pair. It does establish that later calls do not necessarily use the object values seen by earlier calls.

## Side effects

The function’s only direct writes are the three cache stores on an update. There are no direct writes on the unchanged path.

No explicit allocation, deallocation, reference-count change, or ownership-transfer operation is present. Passing an opaque value to a dependency does not establish whether that dependency borrows, retains, releases, or otherwise manages it.

Dependency return values are not inspected. There is no explicit retry, compensation, or error-reporting mechanism.

Dependency effects are unresolved. In particular, dependencies must not be assumed to preserve globals, opaque-object fields, aliased records, or memory lifetimes. If a dependency invalidates memory needed by a later access, normal completion is no longer assured.

Captured observations and computed geometry are not explicitly reloaded after dependency calls. Later opaque-object and associated-value reads, however, remain sensitive to mutations.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not runtime observations. Unless stated otherwise, assume stable valid memory, normally returning dependencies, arithmetic signed right shifts, and representable signed limit additions.

### Unchanged observations

If every observation equals its corresponding cache, the result is 1. All three records are read, and both conditional cache comparisons are reached. No cache changes or dependency calls occur.

### First mismatch

If the first observation differs from the first cache, an update occurs regardless of the other values. The third cache is not read for comparison. The second cache is still read for geometry, and all three observations are committed.

### Geometry uses existing caches

Suppose the first and second caches are \(100\times65{,}536\) and \(80\times65{,}536\), the first observation changes to \(200\times65{,}536\), and the base dimensions are 200 by 160.

The limits remain 100 by 80. Horizontal and vertical crop offsets are 50 and 40. Retained dimensions are 100 by 80, positioned at 110 horizontally and 80 vertically.

After its object argument, the geometry call receives:

**110, 80, 40, 50, 100, 80, 100, 80.**

The caches already contain the new observations when this call occurs.

### Odd dimensions at zero limits

For an update with both size caches zero and base dimensions 5 by 3, the crop offsets are 2 horizontally and 1 vertically. The retained dimensions are 1 by 1 at destination 160, 120, so geometry is submitted.

With base dimensions 4 by 3 instead, the retained width is zero and geometry is omitted. The two control calls and two final interactions still occur.

### Upper limits

Caches equal to \(400\times65{,}536\) and \(300\times65{,}536\) produce limits of 320 and 240. Base dimensions 640 by 480 yield crop offsets 160 and 120, retained dimensions 320 by 240, and destination 0, 0.

### Extraction and polarity

A third observation of `0x00800000` produces extracted value 128. A zero selector assigns 128 to A and 127 to B; a nonzero selector reverses them.

A third observation of `0x00FFFFFF` produces zero, not 255. With a zero selector, A receives zero and B receives 255.

For `0xFFFFFFFF`, the unsigned bias addition wraps to `0x00007FFE`, also producing extracted value zero.

### Negative dimension

On an update with base width −5, retained width remains −5, horizontal crop is zero, and horizontal destination is 162. Geometry is omitted regardless of height. Cache commitment and all four non-geometry calls remain required.

### Mutation between interactions

If the first control call replaces the value at `0x24` with another valid object value, the second control call uses the replacement.

If the first final interaction changes `0x24` or `0x18`, the second final interaction uses the resulting fields. Object identity is not guaranteed to remain constant across calls.
