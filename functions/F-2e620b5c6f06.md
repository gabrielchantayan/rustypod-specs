# F-2e620b5c6f06

## Purpose

F-2e620b5c6f06 destructively incorporates records into a singly linked structure whose head is stored in a caller-supplied context. It recursively processes one record reference, prepends the current record to the shared head, and then continues through another record reference.

**Established behavior:** the four-byte field at record offset 12 supplies a recursive traversal reference before being overwritten with an output link. The four-byte field at record offset 8 supplies the continuation, read only after recursive processing returns. The context head occupies four bytes at context offset 4.

**Inferred intent:** the operation converts a binary tree into a chain. Interpreting offset 8 as the left child and offset 12 as the right child, insertion follows right–current–left order; prepending reverses that order in the resulting links. The function does not inspect keys or establish any sorting invariant.

Tree-order and successful-conversion guarantees require more than distinct, mutually non-overlapping records: **the context head field must also be disjoint from all input-record storage**. Preserving a preexisting chain requires additional separation conditions described below.

## Behavior

### Empty input

A zero starting reference causes an immediate return without any context or record field access. The context need not be dereferenceable for this path.

The empty-input behavior does not imply that the same context is usable with a nonzero starting reference.

### Processing and observable access order

For a nonzero current record, the function first reads its offset-12 reference and recursively invokes F-2e620b5c6f06 with that reference and the same context.

After recursion returns, it reads and retains the current record’s offset-8 continuation. Only then does it read the context head. It writes that head value into the current record’s offset-12 field, followed by writing the current record reference into the context head. Processing continues using the retained continuation.

This ordering establishes three important boundaries:

- Neither the continuation nor the insertion head is an entry-time snapshot; both are read after recursive processing.
- The continuation is retained before either insertion write. Subsequent writes cannot change that retained value, even if they change its original storage.
- The output-link write precedes the head update. They are separate writes, not a single transaction.

Recursive processing can modify shared storage before the caller resumes. In particular, overlapping storage can change the caller’s continuation before its post-recursion read.

### Conditional tree-conversion guarantee

The following ordering guarantee applies when:

- The two input links describe a finite binary tree with each record occurring exactly once.
- Input records are distinct and mutually non-overlapping.
- The context head’s entire four-byte storage is disjoint from every input record’s storage.
- All required accesses and address calculations are valid.
- No concurrent or external mutation intervenes.
- Execution has sufficient stack capacity and completes normally.

Under those conditions, each input record reaches insertion exactly once. With offset 8 interpreted as left and offset 12 as right, insertion order is right subtree, current record, left subtree.

Let the initial context-head value be H. After completion, following offset-12 links from the final head visits the input records in left–current–right order. The last input record in that order contains H in its offset-12 field.

This is an **attachment-of-value guarantee**. Without additional assumptions about H and the storage reachable from it, it is not a guarantee of a finite, acyclic output chain or of preservation of the structure that H originally designated. H may identify an input record, inaccessible storage, or an already cyclic structure.

The context-separation requirement is essential. A head update that overlaps an input field can change traversal itself, even when all input records are mutually disjoint and their initial links form a tree.

### Preserving a preexisting chain

Preservation of an existing chain requires its records to be valid and disjoint from:

- All input-record storage.
- Every storage location modified by this call, including the context head field.

Assume additionally that no external mutation occurs and that the preexisting chain has the validity and termination properties required by its consumer.

Under these conditions, the initial chain remains unchanged and follows the newly incorporated records. If the initial chain was finite and zero-terminated, the resulting chain is the tree’s in-order record sequence followed by that unchanged chain.

Without these separation conditions, only attachment of the initial head value is established. A record already reachable from that value may have its links overwritten because it is also an input record, or its storage may overlap a write target. The resulting structure can differ from the original chain or contain cycles.

### Destructive changes

Every record reaching insertion has its offset-12 field replaced. Its original recursive link is not restored. The conversion therefore destroys part of the input-link structure.

Offset-8 links are not cleared or rebuilt. Under the separation conditions, they retain their stored values; otherwise, overlapping writes can change them. The result is not established to be a doubly linked list or a fully normalized replacement for every input field.

- A’s offset-12 field is zero.

### One isolated record and an arbitrary head value

Let A again have zero input links, and let the initial head value be H.

After completion, the head identifies A and A’s offset-12 field contains H. H is not dereferenced merely for this insertion.

Thus, even an isolated input record does not guarantee an acyclic result when the initial head overlaps the input set by reference.
