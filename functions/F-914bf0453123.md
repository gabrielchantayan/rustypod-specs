# F-914bf0453123

## Purpose

F-914bf0453123 conditionally updates one of five byte-sized state entries associated with a small set of recognized event codes. It returns either the original event code or zero.

The established behavior has two modes:

- With a zero mode argument, it clears a selected entry only if that entry is currently nonzero.
- With a nonzero mode argument, it invokes an external decision function. Depending on that result and a remembered event byte, it either sets the selected entry, leaves it untouched, or records the event and refreshes a four-byte state value through another external function.

The interpretation of these entries as event flags, the remembered byte as a previous event, and the four-byte value as a token is inferred intent. Their application-level meaning is not established. This contract uses those terms only as descriptive labels.

The return value is not an ordinary success/failure result: some paths that write state return the original code, while other paths that write state return zero.

## Interface

### Inputs and result

| Item | Representation | Established use |
|---|---|---|
| Event code | 32-bit unsigned value | Compared against five recognized constants; returned unchanged on several paths. |
| Mode | 32-bit signed value | Tested only for equality with zero. Every nonzero value selects the same branch, including negative values. |
| Result | 32-bit unsigned value | Either the original event code or zero. |

The recognized event codes and their selected byte offsets are:

| Event code | Decimal | Selected offset |
|---|---:|---:|
| `0x6E` | 110 | 0 |
| `0x5A` | 90 | 1 |
| `0x59` | 89 | 2 |
| `0x6F` | 111 | 3 |
| `0x10` | 16 | 4 |

Recognition compares the complete 32-bit event value. A value with the same low byte as a recognized code but additional high bits set is not recognized.

### Referenced state

The function obtains an anchor address from global state near entry. Call this the **captured anchor**. The recovered address representation is 32 bits.

Relative to an anchor, the following locations are used:

| Relative location | Width | Role in this contract |
|---|---:|---|
| −13 | 1 byte | Remembered event |
| −8 through −5 | 4 bytes | State token |
| 0 through 4 | 1 byte each | Five selected state entries |

These offsets identify accessed locations, not a proven structure declaration. The source does not establish a contiguous allocation, padding layout, object type, or the contents of intervening bytes.

A second global value supplies an argument to an external function. Its semantic type, width, and ownership are not established by the supplied material.

### Preconditions and ownership

For defined execution, every location actually accessed on the chosen path must be valid for the corresponding read or write. In particular:

- The global anchor value must be readable even for an unrecognized event, because its acquisition precedes event rejection.
- A recognized event with zero mode requires a readable selected state byte.
- A recognized event with nonzero mode requires a readable four-byte state token before the first external call.
- Later paths may require a readable remembered-event byte or writable state locations.

The supplied material establishes no allocation, deallocation, ownership transfer, or lifetime extension. Reading or storing the four-byte token does not establish that it is a pointer or an owned resource.

The caller must also satisfy the external functions’ unknown preconditions. Invalid addresses, incompatible external interfaces, and external failures are not converted into a defined error result.

## Behavior

### 1. Capture the anchor and recognize the event

The function first obtains the anchor from global state and retains that value for subsequent writes and certain subsequent reads.

It then checks whether the complete event code is one of the five recognized values.

For an unrecognized code:

- The function returns the original 32-bit event value.
- It performs no explicit state-memory write.
- It does not invoke either external function.
- It does not read a selected state entry, remembered-event byte, or token through the captured anchor.

The mode argument does not affect this rejection path.

For a recognized code, the function selects the offset from the table in the interface section.

### 2. Zero-mode behavior

When the mode is zero, the function reads the selected state byte using the anchor referenced by global state at that expression.

If the byte is zero:

- It returns the original event code.
- It performs no explicit state write.
- It invokes neither external function.

If the byte is nonzero:

- It writes a single zero byte at the selected offset relative to the captured anchor.
- It returns zero.
- It invokes neither external function.

The read tests only zero versus nonzero. An existing value such as `0x02` or `0xFF` is treated like `0x01` and is cleared.

There is a source-level distinction between the anchor referenced for the read and the previously captured anchor used for the write. Under stable, ordinary global state, they identify the same anchor. The supplied material does not establish volatile semantics, atomicity, or guarantees under asynchronous mutation; it therefore does not support a stronger concurrency contract.

### 3. Nonzero-mode decision call

When the mode is nonzero, the function invokes dependency **F-opaque-01** with:

1. The four-byte token read at offset −8 from the anchor referenced by global state.
2. The value obtained from the second global location.

Both argument values are obtained before the dependency executes. Their relative evaluation order is not established.

The dependency result is interpreted as a 32-bit value tested for zero versus nonzero. No particular nonzero value has a distinct meaning in this function.

The selected state byte is not read before this call.

### 4. Nonzero decision result

If F-opaque-01 returns nonzero, the function performs these operations in order:

1. It writes the low eight bits of the event code to the remembered-event byte at offset −13 from the captured anchor.
2. It invokes **F-opaque-02** with no explicit arguments.
3. If that invocation returns normally, it writes the dependency’s four-byte result to the token location at offset −8 from the captured anchor.
4. It returns the original event code.

Every recognized event fits in one byte, so the remembered-event write preserves the entire recognized code despite its one-byte width.

This path does not explicitly read or write the selected state entry. That does not guarantee the entry remains unchanged: either external function may have side effects not described in the supplied material.

The captured anchor remains the basis of both explicit writes even if a dependency changes the global anchor. No anchor refresh occurs between the decision call and those writes.

The remembered-event write precedes F-opaque-02. Consequently, F-opaque-02 may observe that updated byte if it accesses the same storage. If the dependency does not return normally, the final token write and normal function return are not established; the earlier remembered-event write has already occurred.

### 5. Zero decision result

If F-opaque-01 returns zero, the function reads the remembered-event byte at offset −13 from the captured anchor. This read occurs after the dependency returns.

The byte is interpreted as an unsigned value for comparison with the full event code.

If the values are equal:

- The function returns the original event code.
- It performs no explicit write after the dependency call.
- It does not invoke F-opaque-02.

If the values differ:

- The function writes the single byte `0x01` at the selected offset relative to the captured anchor.
- It returns zero.
- It does not invoke F-opaque-02.

The selected state byte is not consulted before being set to one. Its previous value can be zero, one, or any other byte value.

Because the remembered-event read follows F-opaque-01, mutations made by that dependency can change whether this path sets the selected entry. The function does not use a remembered-event snapshot taken before the call.

## Side effects

### Explicit writes

Ignoring any dependency side effects, the possible writes are exactly:

| Condition | Explicit writes, in order | Result |
|---|---|---|
| Unrecognized event | None | Original event |
| Zero mode; selected byte zero | None | Original event |
| Zero mode; selected byte nonzero | Selected byte becomes zero | Zero |
| Nonzero mode; decision result nonzero | Remembered event becomes the event byte; then token becomes F-opaque-02’s result | Original event |
| Nonzero mode; decision result zero; remembered event matches | None | Original event |
| Nonzero mode; decision result zero; remembered event differs | Selected byte becomes one | Zero |

All listed writes use the captured anchor.

The function contains no explicit write to either global value from which the anchor and external argument are obtained. This does not establish that those globals remain unchanged: external calls or aliasing with accessed storage could affect them.

### Ordering and visibility

Established logical ordering includes:

- Anchor acquisition before event rejection.
- Selected-byte read before a zero-mode clear.
- Token and secondary-global argument acquisition before F-opaque-01.
- F-opaque-01 completion before the remembered-event read on its zero-result path.
- Remembered-event write before F-opaque-02 on its nonzero-result path.
- F-opaque-02 completion before the token replacement.

These are behavioral orderings visible in the supplied static representation. They are not promises about machine instruction counts, atomic accesses, memory barriers, or concurrent observers.

### Errors and interrupted execution

There is no explicit error-reporting branch and no rollback.

The function does not validate an anchor, token, selected byte, or dependency result beyond the comparisons described above. It does not catch external failures or compensate for state already written before a failing or nonreturning dependency.

## Dependencies

The external functions have no supplied mapping to published opaque identities. The following opaque IDs are document-local labels, not assertions of resolved identity.

### F-opaque-01

- Called exactly once for every recognized event whose mode is nonzero, assuming normal execution reaches the call.
- Receives the four-byte token and a second global value.
- Produces a result tested as a 32-bit zero/nonzero value.
- Is not called for zero mode or unrecognized events.
- May affect globals or referenced memory; preservation is not established.
- Its ownership behavior, failure behavior, and semantic purpose are unknown.

### F-opaque-02

- Called only when F-opaque-01 returns nonzero.
- Receives no explicit arguments.
- Returns a four-byte value that replaces the token.
- Executes after the remembered-event byte has been written.
- Its side effects, ownership behavior, failure behavior, and semantic purpose are unknown.

No assumption is made that either dependency allocates, releases, retains, or preserves any resource.

## Acceptance examples

These examples are conditional behavioral requirements, not runtime observations. Unless stated otherwise, they assume valid memory, a stable global anchor, normal dependency returns, and no dependency side effects beyond the specified return value.

1. **Unrecognized event.**  
   With event `0x12345678` and any mode, the result is `0x12345678`. Neither dependency is called, and no explicit state-memory write occurs.

2. **Recognition is not a low-byte test.**  
   With event `0x0000016E`, the result is that same value. Offset 0 is not selected merely because the low byte is `0x6E`.

3. **Inactive zero-mode entry.**  
   With event `0x5A`, mode zero, and the byte at offset 1 equal to zero, the result is `0x5A`. No byte is written.

4. **Clearing a noncanonical entry.**  
   With event `0x59`, mode zero, and the byte at offset 2 equal to `0xFF`, that byte becomes zero and the result is zero. The function does not require an initial value of one.

5. **Setting after a zero decision result.**  
   With event `0x10`, any nonzero mode, F-opaque-01 returning zero, and the remembered-event byte different from `0x10` after that call, offset 4 becomes one and the result is zero. F-opaque-02 is not called.

6. **Suppressing a set when the remembered event matches.**  
   With event `0x6F`, nonzero mode, F-opaque-01 returning zero, and the post-call remembered-event byte equal to `0x6F`, the result is `0x6F`. The function does not explicitly modify offset 3, even if that byte is zero.

7. **Refreshing state after a nonzero decision result.**  
   With event `0x6E` and F-opaque-01 returning any nonzero result, the remembered-event byte becomes `0x6E` before F-opaque-02 runs. If F-opaque-02 returns `0x12345678`, the four-byte token becomes `0x12345678`, and the function returns `0x6E`. Endianness determines the physical byte ordering of that token; it is not established here.

8. **Dependency mutation affects the later comparison.**  
   If F-opaque-01 returns zero after changing the captured anchor’s remembered-event byte to the current event, the function takes the matching-byte path. A different value present before the dependency call does not override that post-call observation.

9. **Global-anchor replacement does not retarget captured writes.**  
   If F-opaque-01 changes the global anchor and returns nonzero, the remembered-event write and eventual token write still target the anchor captured before the call. This example requires the original storage to remain writable.

- The identities and complete interfaces of the two external dependencies.
- The type and width of the secondary global argument.
- Whether the token represents a count, timestamp, handle, pointer, or another value.
- Memory allocation boundaries, object ownership, alignment requirements, and aliasing relationships.

The static representation uses signed ordering while selecting among already-recognized codes. All recognized codes are small positive values, so that signed comparison does not introduce an additional accepted range or alter the mapping table.

Address offsets are fixed byte offsets. The function establishes no bounds checking or recoverable behavior for invalid address arithmetic.
