# F-d0ab8e462b50

## Purpose

F-d0ab8e462b50 selects between two behaviors using an ordered pair of dependency checks:

- If both initial checks return zero, it marks a shared state field, optionally invokes a notification-like dependency, and waits until a later check returns nonzero. This path returns zero without dispatching the supplied argument.
- If either initial check returns nonzero, it clears that state field, invokes a prerequisite dependency, and conditionally dispatches callbacks through an associated object.

These are established control-flow properties. Descriptions such as “notification,” “prerequisite,” and “associated object” are explanatory labels, not established domain semantics. In particular, the evidence does not establish that either check measures readiness, that a nonzero check result is an error, or that the two checks inspect the same resource.

The argument’s signedness and semantic type are not established. It could represent a scalar, handle, or address-sized value; none of these interpretations is required by the visible behavior.

## Behavior

### Initial checks and base capture

The function first invokes F-e59fcf35bdf8 without visible explicit arguments.

After that call returns, it captures the base address from the shared pointer source. This capture occurs before any initial invocation of F-b5828561cbb4.

The initial selection then follows short-circuit ordering:

- If F-e59fcf35bdf8 returned nonzero, F-b5828561cbb4 is not called for the initial selection. Execution takes the dispatch path.
- If F-e59fcf35bdf8 returned zero, the function calls F-b5828561cbb4 without visible explicit arguments.
- If this second dependency returns nonzero, execution takes the dispatch path.
- Only when both initial results are zero does execution take the waiting path.

This timing matters for shared-state mutation. F-e59fcf35bdf8 may affect the base address that is subsequently captured. A later dependency may change the shared pointer source, but the function continues using its already captured base for the state field and the other two base-relative fields.

No assumption is made that any dependency preserves shared memory.

It then obtains the separate flag-word address and reads the word at that address. If the word is nonzero, it invokes F-5bcae2eff9a7 without visible explicit arguments. If the word is zero, that dependency is skipped.

2. F-b5828561cbb4 is invoked only if the first check returns zero.

### Dispatch path

The function writes the 32-bit value zero to the state field at the captured base.

It then invokes F-bafc2e4b678f without visible explicit arguments. If this dependency returns nonzero, the function immediately returns that result. The associated object is not inspected by this function on that exit.

If the dependency returns zero, the function reads the associated object reference at base offset +4.

- If the reference is null, the function returns 17.
- Otherwise, it proceeds to the first callback position.

The first callback address is obtained from associated-object offset +8. If that address is null, this callback is skipped. If nonnull, the function invokes the captured callback address with one argument: the 32-bit word read from captured-base offset +8.

The first callback’s return value does not determine this function’s result.

After the first callback returns—or after it is skipped—the function accesses the associated object reference again and examines its callback at offset +36. This is not guaranteed to be the same object examined before the first callback. A first callback that changes the base-relative object reference can therefore redirect the second callback lookup.

If the second callback address is null, the function returns zero. Otherwise, it invokes that callback with the original 32-bit input argument and returns the callback’s result unchanged.

The second callback position is tested and then accessed for invocation. The evidence does not establish an atomic snapshot of that position across those accesses, nor a concurrency guarantee.

### Mutation-sensitive boundaries

The null check on the associated object occurs before the first optional callback. No fresh null check is visible before the later associated-object dereference.

Consequently, a first callback that sets the object reference to null can make the subsequent lookup invalid. A first callback that destroys the referenced object without leaving a valid replacement can likewise invalidate later accesses. This function supplies no visible lifetime protection against those changes.

The first callback’s argument is taken from the captured base’s +8 field when the callback is about to be invoked. It is not a snapshot taken before the initial checks or before F-bafc2e4b678f.
