# F-c9188ee0f4a4

## Purpose

F-c9188ee0f4a4 normalizes one four-coordinate record to a zero origin and updates a second four-coordinate record according to a flag in an associated object.

Two behaviors are established:

- With the flag clear, the second record retains its first two coordinates and receives recalculated third and fourth coordinates based on the normalized first record’s extents.
- With the flag set, the second record is saved temporarily, replaced with the normalized first record, and passed to another function together with the saved record.

The coordinate records are consistent with rectangles represented by two corners. Calling their components left, top, right, and bottom is an inferred interpretation, not proof of a particular geometry convention. Inclusive versus exclusive endpoints, coordinate units, and the meaning of the flag are not established.

## Interface

The function has three inputs and no explicit return value:

| Input | Role | Required accessible storage |
|---|---|---|
| Object address | Supplies an initial dependency argument and a later branch flag | A readable four-byte field at byte offset `0x220`, and a readable four-byte flag field at byte offset `0x48` |
| First record address | Supplies extents and is normalized in place | Four consecutive readable and writable 32-bit coordinate elements |
| Second record address | Receives the branch-dependent update | Four consecutive readable and writable 32-bit coordinate elements |

Each coordinate record has this layout:

| Byte offset | Coordinate interpretation |
|---|---|
| `0x00` | Left |
| `0x04` | Top |
| `0x08` | Right |
| `0x0C` | Bottom |

The recovered data model uses four-byte integers for coordinates and four-byte object fields. Coordinate arithmetic is presented as signed integer arithmetic; the flag is tested as an unsigned bit field.

The flag mask is `0x02000000`, or bit 25 when numbered from zero. Other flag bits do not directly affect the branch.

The function does not validate addresses, storage size, alignment, object type, or coordinate ordering. Its ordinary successful execution therefore requires valid storage for every access actually reached. Additional preconditions imposed by its dependencies are unknown.

No distinctness check is made between the two record addresses or between either record and the object. Consequently, a contract that requires non-overlapping records would be stricter than the available evidence. Overlap affects behavior and must not be silently treated as equivalent to separate records.

## Behavior

### 1. Invoke the initial dependency

Before reading either coordinate record, the function reads the four-byte field at object offset `0x220` and passes that field’s value to F-59fa3fd3efc5.

The field value is passed, not the address of the field.

All subsequent coordinate reads occur after this call returns. The behavior therefore depends on the records as they exist after the call, not necessarily as they existed on entry.

No assumption is established that F-59fa3fd3efc5 preserves the object, either record, global state, or memory reachable through the supplied value. If that dependency changes relevant memory, the later operations observe those changes.

### 2. Determine the first record’s extents

After the initial dependency returns, the function determines:

- Horizontal extent: first-record right minus first-record left.
- Vertical extent: first-record bottom minus first-record top.

The horizontal extent is determined before the vertical extent. Both are retained before any normalization write occurs.

The order of the individual operand reads within either subtraction is not established by the supplied representation. The established ordering is between the two extent calculations and the later writes.

There is no absolute-value operation, coordinate sorting, clipping, or rejection of inverted coordinates. Zero and negative extents are retained when their arithmetic is representable.

### 3. Normalize the first record in place

The function writes the first record in this order:

1. Left becomes zero.
2. Top becomes zero.
3. Right becomes the retained horizontal extent.
4. Bottom becomes the retained vertical extent.

Thus, for independent ordinary memory, the first record becomes a zero-origin record with the same signed extents it had immediately after the initial dependency returned.

These are actual mutations of caller-provided storage, not merely construction of a temporary normalized record.

### 4. Read the branch flag

Only after all four normalization writes does the function read the flag field at object offset `0x48`.

This timing matters:

- The initial dependency can affect the flag subsequently observed.
- If normalization writes overlap the flag field, the branch observes the field after those writes.

The function then selects one of the following paths.

### 5. Flag-clear path: update the second record’s endpoints

When bit `0x02000000` is clear, the function performs two ordered updates.

First, it writes the second record’s bottom coordinate as:

**second-record top + (current first-record bottom − current first-record top).**

Second, it writes the second record’s right coordinate as:

**second-record left + (current first-record right − current first-record left).**

The bottom write precedes the right-coordinate calculation and write.

For non-overlapping records, this preserves the second record’s left and top coordinates and assigns it the first record’s signed horizontal and vertical extents.

The implementation reads the first record again for these calculations. It does not simply use the retained extents from the normalization step. This distinction is observable when the records overlap: the bottom write can change storage subsequently read while calculating the right coordinate.

There is no explicit write to the second record’s left or top on this path. This is not a guarantee that their underlying storage remains unchanged under arbitrary overlap with the first record.

No second dependency is called on this path.

### 6. Flag-set path: save, replace, and delegate

When bit `0x02000000` is set, the function first copies the current four coordinates of the second record into temporary local storage, in coordinate order.

This snapshot occurs after first-record normalization. If the records overlap, it therefore captures the second record as affected by that normalization, not necessarily its entry contents.

Next, the function prepares to replace the second record:

- It retains the current first-record top, right, and bottom coordinates before beginning the replacement writes.
- It reads the current first-record left coordinate and writes it to the second record’s left coordinate.
- It writes the retained top, right, and bottom coordinates to the corresponding second-record positions, in that order.

For independent records, this replaces the second record with the normalized first record. The retained coordinates also prevent earlier replacement writes from changing the values used for the later three writes when the records overlap.

After replacement, the function calls F-cca11044abb5 with:

1. The caller’s second-record address.
2. The address of the temporary four-coordinate snapshot.

The second dependency’s return value, if any, is not used. The function performs no further explicit coordinate or object writes after that call returns.

The final contents of the second record on this path are not established solely by this function: F-cca11044abb5 receives its address and may modify it. Nor is preservation of other accessible state by that dependency established.

## Acceptance examples

These are conditional static examples, not observed runtime results. Unless stated otherwise, they assume valid non-overlapping storage, representable arithmetic, and an initial dependency that returns without changing the relevant records or flag.

### Flag clear: preserve destination origin

Given:

- First record: `(10, 20, 40, 70)`.
- Second record: `(100, 200, 900, 900)`.

The first record becomes `(0, 0, 30, 50)`.

### Identical record addresses

If both record addresses identify the same record, initially `(10, 20, 40, 70)`, normalization produces `(0, 0, 30, 50)`.

With the flag clear, both endpoint calculations leave that record unchanged.

With the flag set, the saved record is already `(0, 0, 30, 50)`, because the snapshot follows normalization. The dependency does not receive the original entry coordinates through the snapshot.

### Partial overlap exposes write order

Suppose five consecutive coordinate-sized cells initially contain:

`(10, 20, 40, 70, 100)`.

The first record starts at the first cell. The second record starts one cell later. Assume neither record overlaps the object, and the flag is clear.

Normalization leaves the cells as `(0, 0, 30, 50, 100)`.

The second-record bottom update changes the fifth cell to `80`. The later right update changes the fourth cell to `30`.

The resulting cells are `(0, 0, 30, 30, 80)`. Consequently, the first record ends as `(0, 0, 30, 30)`, despite initially being normalized to height `50`.
