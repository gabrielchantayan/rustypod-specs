# F-bd252fa22770

## Purpose

F-bd252fa22770 obtains a 16-bit count from an input object, checks that count against two bounds, obtains a storage-address value, requests a data transfer into that storage, and validates the resulting bytes as relative indices. Successful validation publishes the count and storage address into a destination object.

The count must not exceed either the destination-configured limit or the fixed inclusive maximum of 258. Zero is eligible.

The function returns a 64-bit composite value. The low 32 bits represent status. The high 32 bits contain the original input-object address on exits before storage acquisition, and zero on all outcomes after the acquisition stage is entered.

On failure after acquisition is attempted, the low half is read from a writable status slot **after cleanup returns**. It need not equal the error that caused cleanup: earlier dependencies received the slot’s address and could make it accessible to cleanup.

The apparent purpose is to load a bounded relative-index table. That interpretation is inferred. The established contract is the sequence of calls, checks, memory accesses, publication, and return construction described below.

## Interface

### Arguments and object layout

The function accepts four arguments:

| Argument | Width | Established role |
|---|---:|---|
| Destination address | 32 bits | Identifies the configured-limit field and two publication fields. |
| Input-object address | 32 bits | Passed to decoding and transfer dependencies; also supplies a directly read context field. |
| Unused value | 32 bits | No visible use or forwarding. |
| Initial status | 32 bits | Initializes a local status slot whose address is passed to dependencies. |

The destination has the following accessed fields:

| Byte offset | Width | Access |
|---|---:|---|
| `0x108` | 16 bits | Read as an unsigned configured count limit after successful decoding. |
| `0x264` | 16 bits | Written with the decoded count after successful validation. |
| `0x268` | 32 bits | Written with the returned storage address immediately after the count write. |

The input object has a 32-bit context field at byte offset `0x1c`. Its value is captured before the first dependency call and reused for acquisition and cleanup.

These are address-based arguments. No explicit checks establish non-nullness, alignment, accessible extent, or separation between objects.

### Return value

The result consists of two independently composed 32-bit halves:

| Path | High 32 bits | Low 32 bits |
|---|---:|---|
| Decoding leaves nonzero status | Original input-object address bits | Status slot after decoding |
| Count exceeds either bound | Original input-object address bits | `3` |
| Acquisition leaves nonzero status, followed by cleanup | `0` | Status slot after cleanup |
| Transfer returns nonzero status, followed by cleanup | `0` | Status slot after cleanup |
| Byte validation fails, followed by cleanup | `0` | Status slot after cleanup |
| Successful validation and publication | `0` | `0` |

For a cleanup path, the cause of failure determines the slot value **before** cleanup, not necessarily the returned value. Cleanup may change the slot through a reference retained by an earlier dependency. In particular, cleanup could leave zero, producing an all-zero return without successful publication.

The low half is incorporated as 32 bits, not sign-extended into the high half. Interpreting the entire result as a signed 64-bit integer is separate from interpreting its status field.

### Preconditions and limits

Ordinary completion requires accessible memory for every executed direct read and write. On a positive-count path reaching validation, the returned storage address must support the byte reads actually performed.

Dependencies can impose additional requirements that are not established here. Their contracts are needed to determine whether an arbitrary initial status, zero-size storage request, or cleanup of an acquisition-failure address is valid.

No disjointness precondition is established. Destination fields, input-object fields, returned storage, and memory reachable by dependencies may overlap. Descriptions of access order do not imply isolation between those regions.

## Behavior

### Context capture and decoding

The function first reads the 32-bit context value at input-object offset `0x1c`. This read occurs even when the initial status is nonzero.

It initializes a local 32-bit status slot from the fourth argument, then calls F-8f49ed59b67e with:

- The input-object address.
- A writable reference to that status slot.

The dependency returns an unsigned 16-bit count. The function widens it to 32 bits without sign extension, giving a possible range of 0 through 65,535.

The function checks the slot after the call. A nonzero value ends processing immediately. On this path, the function does not read the destination limit, attempt acquisition, request transfer, validate bytes, invoke cleanup, or perform the two publication stores.

The initial status is not independently checked before decoding. Whether decoding preserves, replaces, or clears it is unknown.

### Count eligibility

If decoding leaves status zero, the function reads the destination’s unsigned 16-bit limit at offset `0x108`.

Eligibility requires both:

- Count no greater than the configured limit.
- Count no greater than 258.

If either condition fails, the function writes `3` into its status slot and returns with the original input-object address in the high half. Neither acquisition nor cleanup is called.

The fixed-bound logic admits the full interval from 0 through 258. It does not require a positive count or a minimum of 256. Counts 255, 256, 257, and 258 are all eligible when the configured limit permits them; 259 is not.

The intermediate fixed-bound arithmetic remains within signed 32-bit range for every possible decoded count.

### Acquisition

After eligibility succeeds, the function sets the retained return-high-half value to zero. It then calls F-6dd003795db7 with these six arguments, in order:

1. Captured context value.
2. Constant `1`.
3. Constant `0`.
4. Widened count.
5. Constant `0`.
6. Writable reference to the status slot.

The slot is zero when this call begins. The dependency returns a 32-bit value used subsequently as the storage address.

If the slot is nonzero after acquisition, transfer and validation are skipped. Cleanup is called with the captured context and the exact returned address value. There is no separate nonzero-address requirement.

The context field is not reread. A dependency’s modification of input-object offset `0x1c` therefore does not change the context argument selected by this function for acquisition or cleanup.

### Transfer

When acquisition leaves status zero, the function calls F-0c21b5cad025 with:

- Input-object address.
- Returned storage address.
- Widened count.

The dependency’s 32-bit return value replaces the local status slot. Any modification of that slot during this dependency call is therefore superseded by the returned value when the assignment completes.

A nonzero return leads directly to cleanup. A zero return permits validation.

The available evidence does not establish the transfer’s precise input consumption, write extent, partial-transfer behavior, or error meanings.

### Validation

Validation reads one byte at each storage position, in ascending order, starting at zero and stopping before the count.

For each visited position, the function adds the promoted byte value to that position. The sum is accepted exactly when it lies in the inclusive interval from zero through the count.

Consequences include:

- A sum of zero is accepted.
- A sum equal to the count is accepted, although it is one past the last storage position.
- A negative sum or a sum greater than the count is rejected.
- The computed index is not dereferenced.
- There is no visible traversal of links, cycle detection, or reachability check.

The first invalid sum stops validation. No later storage byte is read by this validation loop. The function writes `3` to the status slot and invokes cleanup.

The supplied representation uses a character-sized load without independently establishing whether high-bit bytes are promoted as signed or unsigned. Under signed interpretation, the byte contributes −128 through 127; under unsigned interpretation, it contributes 0 through 255. Exact acceptance of high-bit values remains **documented_only**.

Bytes below `0x80` are unaffected by that uncertainty. With count at most 258, position-plus-byte arithmetic fits within signed 32-bit range under either interpretation.

For count zero, validation reads no storage bytes.

### Publication and successful return

After every required byte passes, the function performs two stores in this order:

1. The decoded count, as 16 bits, to destination offset `0x264`.
2. The returned storage address, as 32 bits, to destination offset `0x268`.

It then returns the constant all-zero result. No cleanup is invoked.

These are separate writes, not an established atomic publication. The function provides no visible synchronization mechanism.

The function does not read or explicitly release the previous address in the destination’s publication field. Replacement ownership must therefore be determined externally.

### Cleanup and final status

Every failure path after acquisition has been attempted calls F-bf7242c98d06 with:

- The captured context.
- The address value returned by acquisition.

Before cleanup, the slot contains:

- Acquisition’s resulting nonzero status, if acquisition failed.
- Transfer’s nonzero return, if transfer failed.
- `3`, if validation failed.

After cleanup returns, the function reads the slot to construct the low return half. Cleanup’s own return value is not used.

Although cleanup does not receive the slot address explicitly in this call, decoding and acquisition did receive it. Either could have retained the address in state available to cleanup. Consequently, preservation of the pre-cleanup status is not established.

The high return half remains zero regardless of such a status change. A zero low half after cleanup does not cause validation, publication, or any other success-path action to resume.

## Side effects

### Direct memory activity

The visible direct nonlocal access sequence is:

1. Read the context field from the input object.
2. Call decoding.
3. If decoding succeeds, read the configured limit.
4. If eligibility, acquisition, and transfer succeed, read storage bytes in increasing position order.
5. If validation succeeds, store the destination count and then the destination address.

Apart from writes to its function-owned status slot, the two destination publication stores are the function’s only explicit nonlocal stores.

Their effects on other named regions depend on aliasing. If the input object overlaps a publication field, publication can modify the input object. If acquired storage overlaps a publication field, publication can modify that storage. The function does not establish that either region is separate from the destination.

All validation reads precede publication. Overlapping destination stores therefore can alter bytes after those bytes have been validated; there is no subsequent validation pass.

### Dependency effects and ownership

Dependencies may modify the input object, destination, storage, globals, retained status references, or other reachable state. No preservation guarantee follows from the absence of an explicit argument naming a particular region.

“No publication on failure” means the function does not execute its two destination stores on that path. It does not guarantee that dependencies leave those fields unchanged.

No rollback of input consumption, storage writes, or other dependency effects is visible.

Successful publication retains the returned address without calling cleanup. This suggests a resource handoff, but does not establish allocation, release, or ownership semantics. Cleanup after failure is likewise an established call, not proof that memory is freed.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume accessible memory, normal dependency return, and no additional effects beyond those specified in each example.

1. **Decoding failure.** If decoding leaves status `7`, the return high half is the original input-object address and the low half is `7`. The configured limit is not directly read.

2. **Configured-limit rejection.** Count 12 with configured limit 11 produces low half `3` and high half equal to the original input-object address. Acquisition and cleanup are not called.

3. **Fixed-limit rejection.** Count 259 with configured limit 65,535 is rejected before acquisition. A permissive configured limit does not override the fixed maximum.

4. **Inclusive maximum.** Count and limit both 258, successful acquisition and transfer, and 258 zero bytes permit publication. Every computed index equals its position. The result is zero.

5. **Inclusive end index.** For count 2, byte values 2 and 1 produce sums 2 and 2. Both pass despite identifying the one-past-end index.

6. **Early validation failure.** For count 2, a first byte of 3 fails. Validation does not read the second byte. The slot is set to `3` before cleanup; the returned low half is whatever the slot contains afterward.

7. **Signedness-sensitive bytes.** For count 2, bytes zero and `0xff` pass under signed interpretation, producing sums zero and zero. Under unsigned interpretation, the second sum is 256 and fails. A first byte of `0xff` fails under either interpretation for this count.

8. **Acquisition failure with preserved status.** If acquisition leaves status `9` and returns address value A, cleanup receives A and the captured context. Transfer is skipped. If cleanup preserves the slot, the return halves are zero and `9`.

9. **Cleanup changes status.** Under the same acquisition failure, if cleanup changes the retained slot to `4`, the low half is `4`. If it changes the slot to zero, the entire return is zero, but no publication occurs.

10. **Zero count.** Successful decoding of zero passes both bounds. Acquisition and transfer are still called with zero count. If both report success, validation reads no bytes, publication writes zero and the returned address, and the result is zero.

11. **Publication aliases storage.** If a destination publication field overlaps acquired storage, successful validation is followed by writes that may alter the validated bytes. No post-publication revalidation occurs.
