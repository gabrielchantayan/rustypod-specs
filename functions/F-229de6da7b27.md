# F-229de6da7b27

## Purpose

F-229de6da7b27 performs an ordered series of memory reads and writes, then transfers control to an unresolved indirect target with three arguments.

Its established effects are mutations of pointer-linked storage, writes to numerically derived addresses, and an indirect invocation. The available static representation does not establish an application-level purpose, object model, ownership protocol, or success condition.

This contract describes the supplied representation, not independently verified machine instructions. In particular, the represented function boundary and the treatment of the final indirect transfer as a returning call remain uncertain.

## Interface

| Input | Represented width | Visible use |
|---|---:|---|
| First argument | 32 bits | No visible use. |
| Second argument | 32 bits | Written in full to one destination; its low byte is written twice to another destination. |

The interface has no defined explicit return value. If the final indirect invocation returns normally, the representation proceeds to an ordinary return. No return-register contents or status are specified.

### Widths, addresses, and notation

All offsets are byte offsets. The representation uses:

- 8-bit byte accesses.
- 16-bit halfword accesses.
- 32-bit word accesses.
- 32-bit integer quantities for the displayed integer-based address calculations.

Pointer-bearing fields are represented as word-sized fields. The original pointer model and integer-to-address interpretation require execution-environment information that is not supplied.

Record names below identify captured addresses, not types or allocation boundaries. Different names may identify the same or overlapping storage. A captured value remains available for later use even if its source memory changes; an explicitly described reread must instead observe the memory at that later stage.

### Preconditions and errors

Reaching the indirect invocation requires all preceding accesses to be valid at their actual computed addresses and widths. This includes destinations formed by addition, numeric doubling, and conversion of a plain-character byte to an unsigned word.

The interpretation of that character byte is conditional: plain-character signedness is not established. It must not be assumed that high-bit bytes always produce either sign-extended or zero-extended values.

The indirect target must support the eventual transfer and argument convention. No visible validation enforces these requirements. There is no defined error result, recovery path, rollback, or guarantee that execution reaches the target after an invalid access.

## Behavior

### 1. Initial publication and captures

The routine reads a word at secondary base offset `0x04` and uses it as the **entry record** address.

It then performs these operations in order:

1. Writes the full second argument to entry record offset `0x24`.
2. Writes the ambient byte to primary base offset `0x19`.
3. Reads entry record offset `0x74`, retaining the **linked value**.
4. Reads entry record offset `0x04`, retaining the **entry payload**.
5. Reads primary base offset `0x74`, retaining the **initial controller** address.
6. Reads initial controller offset `0x14` to obtain a destination, then writes the linked value to that destination’s offset `0x54`.
7. Reads initial controller offset `0x04`, retaining the **initial branch** address.
8. Writes the low byte of the second argument to primary base offset `0x0D`, twice consecutively.
9. Writes the entry payload as a word to primary base offset `0x64`.
10. Writes the word `0x00000074` to initial branch offset `0x30`.

The two byte stores in step 8 are separately present in the representation. They are not a single store merely because they carry the same value.

### 2. Traversal and primary-state mutation

The routine rereads initial controller offset `0x04` and then reads offset `0x74` through the resulting address. This produces the **working record** address. The first of these reads is fresh; intervening aliasing writes may make its result differ from the initial branch.

It then:

1. Reads the word at primary base offset `0x64`, retaining its low byte as the **payload byte**.
2. Writes the payload byte to primary base offset `0x1D`.
3. Reads primary base offset `0x44`, then reads offset `0x14` through that result, retaining the **attachment address**.
4. Writes the linked value as a word to working record offset `0x34`.
5. Writes the attachment address as a word to primary base offset `0x14`.
6. Reads primary base offset `0x54`, retaining the **previous primary word**.
7. Writes the low byte of the primary base to attachment address offset `0x09`.

Next, it reads working record offset `0x04` and then offset `0x74` through the result, producing the **nested record** address.

The following operations occur in order:

1. Writes the low byte of the linked value to nested record offset `0x15`.
2. Writes the primary base as a word to primary base offset `0x54`.
3. Writes the low byte of the working record address to primary base offset `0x11`.
4. Writes the low byte of the previous primary word to nested record offset `0x11`.
5. Reads nested record offset `0x64`, retaining the **nested payload**.
6. Writes the payload byte to primary base offset `0x09`.

The previous primary word is captured before the self-address store. The payload byte is likewise retained from the earlier word read, not reread for each byte store.

### 3. Branch mutation and replacement stores

The routine rereads working record offset `0x04`, obtaining the **active branch** address. This read cannot generally be replaced with an earlier branch capture.

It then:

1. Writes the low byte of the primary base to active branch offset `0x09`.
2. Reads the word at active branch offset `0x50`, retaining the **branch payload**.
3. Writes the low byte of the nested payload to active branch offset `0x11`.
4. Writes the low byte of the primary base to active branch offset `0x09` again.
5. Writes the full nested payload to primary base offset `0x14`.
6. Writes the low byte of the active branch address to primary base offset `0x0D`.
7. Writes the low byte of the branch payload to active branch offset `0x00`.

Next, it reads working record offset `0x74`, retaining the **displacement value**, and then working record offset `0x14`, retaining the **side record** address.

It writes the active branch address as a word to active branch offset `0x54`, then reads side record offset `0x04`, retaining the **leaf address**.

Three stores of decimal 100 follow:

1. An 8-bit store at leaf address offset `0x10`.
2. A 32-bit store at primary base offset `0x54`.
3. A 32-bit store at leaf address offset `0x40`.

It then performs these stores:

1. Low byte of the nested payload to primary base offset `0x0D`.
2. Low byte of the leaf address to side record offset `0x09`.
3. Full nested payload to primary base offset `0x24`.
4. Low byte of the primary base to side record offset `0x11`.

These are ordered writes, not an atomic or simultaneous update. In non-overlapping storage, the store of 100 replaces the earlier primary self-address at offset `0x54`. Aliasing with other destinations can introduce additional effects.

### 4. Arithmetic-derived accesses and character conversion

The routine reads the first fixed word, then rereads primary base offset `0x74`, retaining the **current controller value**. This value need not equal the initial controller.

It then performs the following operations in order:

1. Writes the low halfword of the current controller value to the address formed by adding the current controller value and the primary base.
2. Writes the low halfword of the first fixed word to the address formed by numerically doubling the leaf address.
3. Reads one byte at the address formed by adding the displacement value and the primary base. This access uses a plain-character interpretation, followed by conversion to a 32-bit unsigned value. The result is the **converted byte value**.
4. Writes the low halfword of the current controller value to the address formed by adding the first fixed word and the current controller value.
5. Writes that same halfword again to the sum of the current controller value and the primary base.
6. Writes the word `0x00000045` at converted byte value plus `0x45`.

Numeric doubling is not a field access at offset `0x02`. Similarly, adding two captured address-like values is not a conventional traversal unless the execution environment gives it that meaning.

The character conversion has two unresolved interpretations:

| Stored byte | Signed plain character | Unsigned plain character |
|---|---:|---:|
| `0x00`–`0x7F` | `0x00000000`–`0x0000007F` | Same |
| `0x80`–`0xFF` | `0xFFFFFF80`–`0xFFFFFFFF` | `0x00000080`–`0x000000FF` |

For example, a stored byte of `0x80` becomes either `0xFFFFFF80` or `0x00000080`. Neither interpretation is established by the supplied plain-character type alone.

The additions involving the converted byte value are represented as 32-bit unsigned arithmetic and therefore reduce modulo \(2^{32}\). Other address additions and numeric doublings use signed integer quantities in the representation; signed overflow must not simply be assigned unsigned wrapping semantics. Valid address conversion and actual fault behavior remain environment-dependent.

### 5. Final reads, writes, and invocation

After the word store at converted byte value plus `0x45`, the routine reads, in order:

1. The second fixed word.
2. The fixed payload.
3. The current word at primary base offset `0x44`.

It then writes:

1. Byte `0x44` at converted byte value plus `0x44`.
2. The fixed payload as a word at twice the second fixed word.
3. The low halfword of the second fixed word at linked value plus second fixed word.

Finally, it invokes the unresolved indirect target with three represented 32-bit arguments, in this order:

1. Converted byte value bitwise-ORed with `0x00000044`.
2. The captured second fixed word.
3. The captured word from primary base offset `0x44`.

The first argument uses bitwise OR, not addition.

The final three writes occur after all three final reads. If those writes overlap a source location, the arguments still use the captured values. No further memory operation is visible after the indirect invocation. If it returns normally, the represented routine returns without defining a result.

## Side effects

The routine mutates potentially overlapping storage through field accesses and arithmetic-derived destinations.

Its observable ordering includes repeated stores, intermediate replacements, and fresh reads:

- Primary base offset `0x0D` receives two argument-byte stores, then the active-branch address byte, then the nested-payload byte.
- Primary base offset `0x14` receives the attachment address and later the nested payload.
- Primary base offset `0x54` is read before receiving the primary base and later decimal 100.
- Active branch offset `0x09` receives two primary-base byte stores with other operations between them.
- The halfword at current controller value plus primary base is written twice.

Aliasing can cause earlier writes to change later pointer fields, payloads, fixed-location contents, or arithmetic inputs. No non-aliasing guarantee is established. Endianness also matters when differently sized accesses overlap.

These operations have the order shown in the static representation. Whether duplicate or intermediate stores are externally observable depends on memory properties and the execution model. No atomicity, synchronization, or concurrency guarantee is supplied.

There is no visible allocation, deallocation, reference-count update, or explicit ownership-transfer operation before the indirect invocation. Writing an address does not itself establish ownership. The indirect dependency may have additional effects; none may be assumed absent.

A fault or failed transfer can occur after partial mutation. No rollback is visible.

## Acceptance examples

These are conditional deductions from static evidence, not executed tests. Each assumes that execution reaches the relevant operation and that the stated memory conditions hold.

### Full-width and byte argument stores

For second argument `0x123456AB`, the entry record’s offset `0x24` receives the word `0x123456AB`. The two initial stores to primary base offset `0x0D` each write `0xAB`.

Keeping only `0xAB` for the word store would not match the represented behavior. Later stores to offset `0x0D` still occur.

### Captured low byte

If the word read from primary base offset `0x64` is `0xA1B2C3D4`, the payload byte is `0xD4`. That captured byte is used at primary base offsets `0x1D` and `0x09`.

This extraction does not depend on memory byte order. Aliasing may affect the word read or later contents, but does not turn the second byte store into a fresh payload read.

### Replacement of primary state

With non-overlapping destinations and successful execution, primary base offset `0x54` first receives the primary base and later receives the word 100.

A model that preserves only the final value omits an established intermediate write.

### High-bit character conversion

If the arithmetic-derived byte is `0x80`:

- With signed plain characters, the converted value is `0xFFFFFF80`, and the first indirect argument is `0xFFFFFFC4`.
- With unsigned plain characters, the converted value is `0x00000080`, and the first indirect argument is `0x000000C4`.

The word-store address at converted value plus `0x45` is correspondingly `0xFFFFFFC5` or `0x000000C5`. The byte-store address at converted value plus `0x44` is `0xFFFFFFC4` or `0x000000C4`.

These numeric results do not establish that either address is accessible or that execution reaches the invocation.

### Bitwise argument construction

If the byte is `0x01`, both character interpretations produce first argument `0x00000045`.

If it is `0x44`, both produce `0x00000044`, not `0x00000088`. Substituting addition for OR is incorrect.

### Fresh traversal under aliasing

If a preceding write changes working record offset `0x04`, the active branch comes from the later read of that field. Reusing a previously captured branch is equivalent only when the relevant memory configuration independently establishes equality.

### Final argument capture

If one of the final three stores overlaps primary base offset `0x44`, the third indirect argument still uses the word captured before those stores. Re-reading that field afterward can change behavior.

### Invalid destination

If a required destination is unwritable, the representation supplies no defined clean error return or unchanged-memory guarantee. Earlier stores may already have taken effect.
