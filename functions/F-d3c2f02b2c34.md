# F-d3c2f02b2c34

## Purpose

F-d3c2f02b2c34 performs an indexed state update in caller-supplied memory. It reads a four-byte counter, optionally invokes two external dependencies, writes a one-byte marker selected using the previously read counter, and advances the counter. If the stored counter is subsequently observed as a signed value greater than one, it is replaced with zero.

The apparent intent is to alternate between two marker positions associated with a selected entry. That interpretation is supported for initial counter values zero and one, but it is not a complete description of the established behavior. The function does not validate the selector, constrain the initial counter to those two values, clear another marker, or establish that the calculated addresses lie within an allocation.

## Interface

The function has three integer-shaped inputs and no explicit return value:

| Input | Role |
|---|---|
| Base | Integer representation of the address from which both counter and marker locations are calculated. |
| Selector | Index-like value used in two address calculations with different strides. |
| External-action flag | Any nonzero value requests both external calls. Zero skips both. |

For this contract, the following names identify calculated locations and a captured value:

- **Counter location:** Base + 4 × Selector + 4.
- **Captured counter:** the four-byte integer read from the counter location before either optional external call.
- **Marker location:** Base + 56 × Selector + 28 × Captured counter + 8.

These are descriptions of byte offsets, not declarations of a complete structure layout. In particular, the counter and marker calculations do not establish an array element type or a structure size.

The supplied representation identifies the counter as a four-byte integer and the marker as one byte. Counter comparison is signed. The apparent integer and address-calculation model is 32-bit, but the exact target ABI, signed-overflow behavior, pointer conversion rules, and address wraparound behavior are not independently established.

The function returns without an explicit result. Its observable outputs are memory effects and, when enabled, effects of the two external dependencies.

For an ordinary successful invocation, the caller must provide memory for the required reads and writes and satisfy the target’s alignment and access requirements. The function contains no bounds, null-address, alignment, or counter-range checks.

## Behavior

### Initial counter capture

The function first calculates the counter location and reads a four-byte integer from it. This read occurs regardless of the external-action flag.

The captured value determines both:

- Which marker address will receive the byte value one.
- Which incremented value will later be written to the counter location.

The counter is not refreshed after the optional external calls for either of those purposes. Consequently, a dependency’s modification of the counter does not replace the captured value used in the function’s later calculations.

If the initial read cannot complete, the supplied body provides no recovery path or error result.

### Optional external actions

If the external-action flag is nonzero, the function invokes F-EXT-01 and then F-EXT-02. If the flag is zero, neither is invoked.

These calls occur after the initial counter read and before either of the function’s explicit memory writes. The supplied call expressions contain no explicit arguments, and no returned values are consumed.

Normal continuation to the marker write requires both calls to return normally. The body does not check a status code or provide a local failure branch.

The calls must not be treated as harmless notifications. Their implementations are unavailable: they may have observable effects, modify shared state, or affect the validity or contents of the memory subsequently accessed. This contract does not assume that they preserve globals or retain, release, or otherwise manage any particular allocation.

### Marker update

After the optional calls, the function writes the byte value one at the marker location.

The location uses the counter captured before the calls. There is no check that this value is zero or one, and no check that the calculated location belongs to an intended marker region.

Only one explicit marker byte is written. The function does not clear a previous marker, initialize neighboring bytes, or explicitly write a four-byte marker value.

### Counter update and conditional reset

After the marker write, the function writes Captured counter + 1 as a four-byte value at the counter location.

It then reads a four-byte integer from that location and compares the result, as a signed value, with one:

- If the observed value is greater than one, the function writes four bytes of zero at the counter location.
- Otherwise, it performs no reset write.

The comparison is therefore against a read of the stored counter, rather than solely against a retained arithmetic result. In ordinary stable memory, without outside interference, that read observes the increment just written. If another actor or unusual memory semantics changes what is observed, the reset decision follows the value read.

For initial counter values zero and one, with valid addresses, normal dependency returns, no interference, and ordinary arithmetic:

- Zero selects the first of the two apparent marker positions and leaves the counter at one.
- One selects the second apparent marker position and leaves the counter at zero.

For other values, the behavior is not equivalent to validating or normalizing the counter before use. The marker write happens first and uses the original value. For example, an initial value of two selects an offset of 56 bytes within the counter-dependent part of the marker calculation before the counter is reset.

### Observable access order

On a normal path, the function’s explicit accesses and calls occur in this order:

1. Read the four-byte counter.
2. Invoke F-EXT-01 if the flag is nonzero.
3. Invoke F-EXT-02 if the flag is nonzero.
4. Write one byte of value one at the marker location.
5. Write the four-byte incremented captured counter at the counter location.
6. Read the four-byte counter for the signed comparison.
7. Write four bytes of zero at the counter location only if that comparison succeeds.

This order does not establish atomicity, synchronization, or a transaction boundary. Effects inside the dependencies are not enumerated by this sequence.

## Side effects

The function directly accesses caller-addressed memory. On normal completion it performs:

- Two four-byte reads at the counter location.
- One one-byte write at the marker location.
- One unconditional four-byte write at the counter location.
- One additional four-byte write at the counter location when the observed counter exceeds one.

It explicitly allocates no memory, releases no memory, and transfers no ownership. The Base input is used to calculate addresses; it is not returned.

The optional dependencies may introduce additional side effects. Their ownership behavior and effects on global or shared state are unknown.

The body does not enforce separation between the calculated memory regions. If a supported address configuration causes writes to affect overlapping storage, the access order governs their interaction; the contract does not promise that the marker remains one after a later overlapping write.

No explicit rollback exists. If execution fails or a dependency does not return after an earlier effect has occurred, the function provides no mechanism for restoring prior memory or undoing dependency effects.

There is no explicit error return, error object, logging action, or local exception-handling path. Whether an invalid address or arithmetic edge produces a fault, wraparound, or another outcome depends on execution semantics not established here.

## Acceptance examples

These examples are conditional behavioral expectations derived from the supplied representation, not results of runtime testing. Unless stated otherwise, assume valid ordinary memory, representable arithmetic and addresses, no outside interference, and normal return from any enabled dependency.

### Initial counter zero, external actions disabled

Given a counter value of zero and a zero flag:

- Neither dependency is called.
- The byte at Base + 56 × Selector + 8 is set to one.
- The counter is written as one.
- The comparison observes one, so no reset write occurs.

No clearing of another marker is required or implied.

### Initial counter one, external actions enabled

Given a counter value of one and any nonzero flag:

- The counter is captured before either dependency runs.
- F-EXT-01 runs before F-EXT-02.
- The byte at Base + 56 × Selector + 36 is set to one.
- The counter is written as two.
- The comparison observes two, so the counter is then written as zero.

The value 36 includes the fixed offset eight and the counter-dependent offset 28.

### Dependency changes the counter

Given an initially captured counter of zero, suppose an enabled dependency changes the counter location to seven and otherwise leaves subsequent memory accesses valid:

- The marker calculation still uses zero.
- The function’s subsequent counter write stores one, replacing seven.
- With no further interference, the comparison observes one and does not reset it.

This expectation concerns the function’s own accesses; it does not constrain other dependency effects.

### Initial counter two

Given an initial counter of two:

- The marker byte is written at Base + 56 × Selector + 64.
- The counter is written as three and subsequently reset to zero.

Resetting the counter does not prevent the preceding marker write outside the two apparent ordinary positions.

### Initial counter negative one

Given an initial counter of negative one, with the resulting address valid:

- The marker location is Base + 56 × Selector − 20.
- The counter is written as zero.
- The comparison does not request a reset.

This illustrates the absence of a nonnegative-counter check.

### Comparison observes a changed value

If the comparison read observes a value other than the increment just written:

- A signed observed value greater than one triggers the zero write.
- A signed observed value of one, zero, or a negative number does not.

This is not a guarantee that concurrent access is safe.

- **Storage layout:** Allocation size, selector bounds, entry count, marker-region size, and permitted aliasing are unknown.
- **External behavior:** Neither dependency’s state effects, ownership behavior, failure reporting, nor termination is known.
- **Concurrency:** No synchronization mechanism is visible. Atomicity, memory ordering, and behavior under data races are not established.
