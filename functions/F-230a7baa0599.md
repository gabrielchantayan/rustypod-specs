# F-230a7baa0599

## Purpose

F-230a7baa0599 performs an ordered sequence of memory updates using three implicit base addresses, four explicit arguments, and addresses loaded from memory. It then invokes an unresolved indirect dependency with four arguments.

The established behavior is memory mutation and indirect dispatch. The available evidence does not establish an application-level purpose, an object model, or a conventional data-structure operation. In particular, the writes must not be characterized as list maintenance, registration, initialization, or ownership transfer without additional evidence.

The ordering is material. Several locations are overwritten, and later reads may observe earlier writes when address ranges overlap. A contract that describes only final field values would omit observable behavior.

| First argument | 32 bits | Stored at primary-base offset `0x10`. |
| Second argument | 32 bits | Its low byte is stored at fixed address `0x67`; its full value is temporarily stored at primary-base offset `0x44`. |

- **Secondary base:** supplies one early destination.

These names are descriptive labels, not recovered type names. Their setup and the surrounding calling convention are unknown. The visible explicit argument list alone is therefore insufficient to invoke the function reliably.

The function also depends on:

### Output and return

## Behavior

The following phases specify the order represented by the static evidence. The address labels introduced within them refer to values captured by particular reads, not to fields that are automatically reread.

### 1. Publish initial values and a byte marker

The function first stores the complete first argument at primary-base offset `0x10`.

Next, it stores the linked-base value as a four-byte quantity at secondary-base offset `0x44`. It then writes the low byte of the second argument to the fixed byte location at address `0x67`.

After that fixed-location write, the function reads the byte at address `0x67` and stores it at primary-base offset `0x09`. It next stores the low byte of the primary-base value at linked-base offset `0x09`.

Finally, within this phase, it stores the complete second argument at primary-base offset `0x44`.

The source supports a fixed-byte write followed by a fixed-byte read. The read must not be silently replaced in the contract with the original argument byte, particularly where overlapping addresses or externally changing memory could matter.

### 2. Capture a derived base and perform byte updates

The function reads a four-byte value from primary-base offset `0x54`. This captured value is the **derived base** for subsequent accesses.

After capturing that value, it again reads the byte at fixed address `0x67` and writes it to primary-base offset `0x09`. This is a second store to that primary byte, even if it writes the same value as before.

It then stores the fourth argument at derived-base offset `0x0D`, followed by a four-byte store of the third argument at linked-base offset `0x54`.

The derived base is taken from memory at this point in the sequence. It is not established as an independent entry-time input. Earlier stores can affect it if their ranges overlap its source location.

### 3. Capture a payload and replace the primary fields

The function reads a four-byte **payload value** from primary-base offset `0x14`.

It then writes the fourth argument at linked-base offset `0x11`, followed by the low byte of the captured derived base at primary-base offset `0x09`.

Next, it stores the entire captured derived-base value at primary-base offset `0x44`. This replaces the earlier second-argument store at that location in the absence of intervening overlap.

The payload read precedes these three writes. Later changes to its source memory do not change the captured payload value used below.

### 4. Capture another address and write the halfword marker

The function reads a four-byte value from linked-base offset `0x04`. This captured value is the **index address**.

It then stores the 16-bit value `0x0065` at the numeric address obtained by doubling the index address.

This destination is not the linked base plus twice an index. No additional base is present in the visible address expression.

After the halfword store, the function reads a four-byte value from index-address offset `0x64`. This captured value is the **forward value**. It is subsequently used both as data and as the basis of another doubled-address destination.

The halfword write precedes the forward-value read. If the two ranges overlap, the read observes memory after that write, subject to the actual memory model.

### 5. Update the derived object and capture dispatch data

The function stores the low byte of the captured payload at derived-base offset `0x11`.

It then stores the four-byte numeric value `100`, equivalent to `0x00000064`, at derived-base offset `0x54`.

Only after those stores does it read a four-byte **dispatch value** from index-address offset `0x74`.

It next reads a four-byte **destination base** from linked-base offset `0x64`.

Both reads occur after the derived-base writes. If either source overlaps an earlier destination, that ordering determines which memory contents are captured.

### 6. Complete the visible memory updates

The function stores the low byte of the captured index address at linked-base offset `0x09`.

Next, it stores the complete captured forward value at destination-base offset `0x54`.

It then stores the complete captured destination-base value at the numeric address obtained by doubling the forward value.

The final store is four bytes wide. It differs from the earlier doubled-address store, which is two bytes wide. Neither destination is visibly checked before use.

### 7. Invoke the unresolved dependency

After all preceding memory accesses, the function invokes the unresolved indirect target with these four arguments, in order:

1. The numeric constant `0x72`, decimal 114.
2. The captured forward value.
3. The original third explicit argument.
4. The captured dispatch value.

The fourth call argument is the value read from index-address offset `0x74`, not the earlier payload read from primary-base offset `0x14`.

The target-selection mechanism is not recovered. The evidence presents an indirect invocation and a subsequent return, but does not establish a reliable target set or the target’s effects.
