# F-86c2e7865113

## Purpose

F-86c2e7865113 conditionally appends a short attribute prefix to a caller-provided destination. It recognizes six three-byte input identifiers and emits one of these fragments:

- `/CN=`
- `/C=`
- `/L=`
- `/ST=`
- `/O=`
- `/OU=`

On an accepted input, the function also writes a trailing zero byte, updates a destination count, and returns a 32-bit zero value. On a rejected input, it returns a configurable global value without performing any explicit destination writes.

The association with attribute names is inferred intent. The established behavior is the byte mapping, validation, address calculation, and write sequence described below. The function does not append an attribute value, parse a complete name, or establish that the resulting destination is a valid string.

This contract describes static evidence from the supplied representation. No runtime tests have been performed.

## Interface

### Inputs

The function has two arguments:

1. **Destination base**: an address whose first four bytes are accessed as an integer count. Subsequent byte writes are addressed relative to this same base.
2. **Descriptor base**: an address used to access a four-byte integer field at offset 4 and a pointer field at offset 8.

The supplied representation uses a 32-bit address model: addresses are carried through integer-sized expressions, the destination count and descriptor integer are four bytes, and the return value is four bytes. The representation does not independently establish byte order or all machine-level overflow behavior.

### Destination layout

For ordinary, nonnegative counts, the apparent layout is:

| Offset from destination base | Role |
|---|---|
| 0–3 | Four-byte count |
| 4 onward | Byte-oriented output area |

The count is treated as the existing output length. There is no read or validation of the existing output bytes, and no check that a zero terminator is already present at that length.

The numerical capacity checks are consistent with a 200-byte output area, including space for a trailing zero. An actual allocation size is not supplied to the function. The caller must provide accessible storage for every address the function reaches.

### Descriptor layout

| Offset from descriptor base | Access |
|---|---|
| 0–3 | Not accessed |
| 4–7 | Four-byte integer used in the initial product gate |
| 8 onward | Pointer to input identifier bytes |

The pointed-to identifier is examined as individual bytes. It is not treated as a zero-terminated string.

The pointer field is not read unless the product gate passes. The second and third identifier bytes are read only after the preceding byte comparisons pass.

### Global inputs

Two global values participate:

- **Gate multiplier**: multiplied by the descriptor integer and compared with 3.
- **Rejection result**: returned on every explicit rejection path.

The supplied representation shows both as integer-sized values. Their initial values, configuration mechanism, and meanings are unknown.

### Output

- **Accepted path:** returns the 32-bit value zero.
- **Rejected path:** returns the rejection-result global.

The rejection-result global is not established to be nonzero. A caller therefore cannot assume that a zero return alone distinguishes acceptance from rejection without an external constraint on that global.

There is no separate error object, output-length return, or explicit fault-recovery mechanism.

## Behavior

### Validation and input-read progression

The function first reads the destination’s four-byte count. This read occurs even when the descriptor would subsequently fail validation.

It then obtains the gate multiplier and the descriptor integer at offset 4, multiplies them, and compares the result with 3. If the comparison fails, it returns the rejection-result global.

The relative evaluation order of the two product operands is not established by the supplied expression. Both precede any access through the descriptor’s identifier pointer.

If the product gate passes:

1. The identifier pointer is read from descriptor offset 8.
2. The first identifier byte is read and must equal hexadecimal `55`, the ASCII byte for `U`.
3. The second identifier byte is read and must equal hexadecimal `04`.
4. The third identifier byte is read and selects the output abbreviation.

Failure at either fixed-byte comparison returns the rejection-result global. A third byte outside the accepted set also returns that value.

The function does not check a descriptor length before reading these identifier bytes. Passing the product gate does not itself prove that three bytes are accessible: the descriptor integer is used in arithmetic, not directly compared with an independently established byte length.

### Accepted identifiers

All accepted identifiers begin with bytes `55 04`.

| Third byte | Abbreviation | Appended bytes | Count increase |
|---|---|---|---:|
| `03` | `CN` | `/CN=` | 4 |
| `06` | `C` | `/C=` | 3 |
| `07` | `L` | `/L=` | 3 |
| `08` | `ST` | `/ST=` | 4 |
| `0A` | `O` | `/O=` | 3 |
| `0B` | `OU` | `/OU=` | 4 |

Third bytes `04`, `05`, and `09` are explicitly rejected. Every other unlisted third byte is rejected as well.

No bytes after the selector are read.

### Capacity checks

Let **N** denote the four-byte destination count captured at entry.

For a one-letter abbreviation, the function rejects when the unsigned 32-bit result of **N + 4** exceeds 200.

For a two-letter abbreviation, it rejects when the unsigned 32-bit result of **N + 5** exceeds 200.

These are unsigned comparisons. They must not be replaced in the general contract with an assumption that the entry count was already a valid nonnegative length.

For ordinary nonnegative counts without arithmetic wraparound:

- One-letter output is accepted through **N = 196**.
- Two-letter output is accepted through **N = 195**.
- The resulting count is at most 199.
- The trailing zero fits at output-area index 199 or earlier.

The checks do not explicitly reject all negative counts. Under the displayed 32-bit unsigned conversion, for example, a count of −1 produces a guard value of 3 or 4 and passes the corresponding capacity check. Such a count can cause output writes to overlap the count field. Nonnegative, structurally valid destination state is therefore a necessary precondition for ordinary append behavior, not a validation guarantee supplied by this function.

### Successful write sequence

Under the ordinary non-overlapping layout, with a valid entry count **N**, the resulting output fragment begins at output-area index **N**, meaning destination-base offset **N + 4**.

The observable write order is not the left-to-right order of the finished fragment:

1. Write the first abbreviation byte at destination-base offset **N + 5**.
2. For a two-letter abbreviation, write its second byte at offset **N + 6**.
3. Read the destination count again and use that current value to locate the slash write.
4. Write `/`, byte `2F`, at destination-base offset equal to that re-read count plus 4.
5. Write `=`, byte `3D`, using an address derived from the original captured count:
   - Offset **N + 6** for a one-letter abbreviation.
   - Offset **N + 7** for a two-letter abbreviation.
6. Write a zero byte immediately after the equals sign.
7. Store the updated four-byte count:
   - **N + 3** for a one-letter abbreviation.
   - **N + 4** for a two-letter abbreviation.
8. Return zero.

For ordinary valid storage, the count re-read in step 3 still equals **N**. The result is therefore the expected contiguous fragment followed by a zero byte. The count excludes that terminating zero.

The distinction between the captured count and the later count read matters under aliasing or malformed destination state. Earlier abbreviation writes can modify the count bytes if their computed addresses overlap the header. In that case, the slash address follows the modified count, while the equals-sign address, zero-byte address, and final count value remain derived from the original captured count.

### Rejection behavior

Every explicit rejection happens before the first destination write:

- Product gate failure.
- First identifier byte mismatch.
- Second identifier byte mismatch.
- Unsupported selector.
- Capacity check failure.

These paths do not reset the count, remove existing bytes, or write a terminator. They return the rejection-result global.

Invalid memory access is distinct from an explicit rejection. The function has no visible mechanism for converting inaccessible memory into the rejection result.

## Side effects

### Memory mutation

On acceptance, the function performs:

- One or two abbreviation-byte writes.
- One slash-byte write.
- One equals-sign-byte write.
- One zero-byte write.
- One four-byte count store.

The count store occurs last. This does not make the operation atomic: a fault or concurrent observation can expose a partially written fragment.

With a well-formed, non-overlapping destination, pre-existing output bytes before the append position remain unchanged. No output-area clearing is performed beyond the single trailing zero.

### Aliasing

No disjointness checks are present.

If the destination overlaps the descriptor, identifier storage, or a global, successful writes can modify that overlapping storage. All identifier bytes needed for selection have already been read before output writes begin, so later mutation of the identifier does not cause reclassification.

Aliasing with the destination count is especially significant because of its second read before the slash write. The final four-byte count store can also overwrite earlier byte writes if their addresses overlap the header.

### Ownership and lifetime

No allocation, deallocation, ownership transfer, callback, or dependency call is visible. The function operates directly on supplied addresses.

This absence does not establish ownership conventions for the surrounding system. The caller must ensure that the storage remains accessible for the accesses described here.

## Dependencies

Its visible dependencies are the gate-multiplier global, rejection-result global, descriptor storage, identifier bytes, and destination storage.

## Acceptance examples

These examples are conditional specifications derived from static evidence, not observed executions. Unless stated otherwise, assume accessible, disjoint storage; a valid nonnegative destination count; stable globals; and a product gate that evaluates to 3.

### 1. Append a two-letter abbreviation

Given:

- Existing output bytes `abc`.
- Entry count 3.
- Identifier bytes `55 04 03`.

Expected result:

- Output bytes become `abc/CN=` followed by a zero byte.
- Count becomes 7.
- Return value is zero.
- `C` and `N` are written before `/`.

### 2. Append a one-letter abbreviation

Given:

- Entry count 0.
- Identifier bytes `55 04 06`.

Expected result:

- Output begins `/C=` followed by a zero byte.
- Count becomes 3.
- Return value is zero.

The initial output bytes need not already contain an empty string; the function writes the complete new fragment and its terminator.

### 3. One-letter capacity boundary

Given identifier bytes `55 04 07`:

- At count 196, the function accepts. It writes `/L=` at output-area indices 196–198, a zero at index 199, and stores count 199.
- At count 197, it rejects before writing any destination bytes.

### 4. Two-letter capacity boundary

Given identifier bytes `55 04 08`:

- At count 195, the function accepts. It writes `/ST=` at output-area indices 195–198, a zero at index 199, and stores count 199.
- At count 196, it rejects before writing any destination bytes.

### 5. Unsupported selector

Given identifier bytes `55 04 09`, the function returns the rejection-result global. The destination count and output bytes receive no explicit writes.

The same outcome applies to selector `FF`, subject to accessible input storage.

### 6. Early input rejection

If the product gate fails, the identifier pointer field is not read. The destination count is nevertheless read first.

If the product gate passes but the first identifier byte is not `55`, neither the second nor third identifier byte is read.

### 7. Ambiguous return value

If the rejection-result global is zero and the second identifier byte is invalid, the function returns zero without appending anything. This demonstrates why successful mutation cannot be inferred from the return value alone unless the rejection-result configuration is known.
