# F-7b7e0fe81115

## Purpose

F-7b7e0fe81115 obtains four values through an indirectly referenced object or handle and combines them into one unsigned 32-bit result.

The construction resembles packing three components into byte-spaced positions and a fourth component into a four-bit position. That interpretation is **inferred intent**, not an established restriction on the inputs. Only the fourth component is explicitly masked. The first three components can contribute overlapping bits when their values exceed an eight-bit range.

The established behavior includes four separate reads of the same input-relative field and four dependency calls in a fixed order. It does not establish that all four calls receive the same field value: an earlier dependency may change the field before a later read.

## Behavior

### Ordered observations and calls

The routine performs these operations in order:

1. It reads the 32-bit field at input offset `0x10` and passes that value to **F-0c00bf6875fa**. It retains the returned value as the first component.
2. After that dependency returns, it reads the same field again and passes the newly read value to **F-4f769beb7e11**. It retains the returned value as the second component.
3. After the second dependency returns, it reads the field again and passes that value to **F-f693c473ce7c**. It retains the returned value as the third component.
4. After the third dependency returns, it reads the field a fourth time and passes that value to **F-ab4f5b639cb8**. It retains the returned value as the fourth component.
5. After all four dependencies return, it combines their returned values and returns the result.

The field is not visibly captured once and reused. Replacing the four reads with one cached read would therefore require additional evidence that the field cannot change during the calls.

The first three completed return values remain the components used in the final combination. They are not visibly recomputed or refreshed after subsequent calls.

### Result construction

The result is the bitwise OR of:

- The complete first component, unshifted.
- The second component shifted left by 8 positions.
- The third component shifted left by 16 positions.
- The low four bits of the fourth component shifted left by 24 positions.

These are OR contributions, not replacements of independent fields. A bit already set by one contribution remains set regardless of the other contributions.

Only the fourth component is explicitly range-limited. Its contribution occupies bits 24 through 27, with bit 0 denoting the least significant result bit. Bits 4 through 31 of that component do not contribute.

The first component is not masked to eight bits. In particular, its bits 8 through 31 can survive directly into the result.

The second and third components are also not explicitly masked to eight bits before shifting. Where the shifts are defined, bits beyond their low byte can affect positions beyond the apparent byte slots. Consequently:

- The second contribution can overlap the third contribution.
- The first contribution can overlap every other contribution.
- The fourth contribution does not exclusively determine bits 24 through 27.
- The fourth-component mask does not guarantee that result bits 28 through 31 are zero.

The supplied representation gives the first and fourth dependency returns unsigned 32-bit treatment and the second and third signed 32-bit treatment. The latter two are shifted while represented as signed values. Their behavior for negative operands, or for positive operands whose shifted mathematical value exceeds the signed 32-bit range, is not established as a portable language-level result.

For nonnegative values, a second component no greater than `0x007FFFFF` and a third component no greater than `0x00007FFF` avoid that signed representability issue. The narrower inferred byte-component range, zero through 255, also avoids it.

A target-level rule that always shifts 32-bit bit patterns and discards bits beyond bit 31 may be a reasonable interpretation, but it is not independently verified by the supplied material. Acceptance cases requiring that rule are therefore conditional rather than unconditional.

Both shifted contributions set the same bit. They are ORed, not added; the result is not `0x00020000`.
