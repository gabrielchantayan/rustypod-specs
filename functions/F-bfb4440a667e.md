# F-bfb4440a667e

## Purpose

F-bfb4440a667e decodes a compact, flag-selected metrics record from a bounded byte stream. It produces two position-like values, two size-like values, an advance-like value, and a two-bit classification. On success, it advances a caller-owned cursor past the decoded record.

The field names above describe inferred roles. The established behavior is byte decoding into six 32-bit outputs; units, coordinate conventions, and downstream interpretation are not established.

The decoder supports variable-width representations selected by a one-byte header. Some representations are signed and others are unsigned, including representations of the same logical field. In particular, the two-byte position and advance representations are **zero-extended**, not sign-extended.

The function returns a 32-bit status: zero on success and eight on a detected shortage of input. A shortage invokes dependency F-4457a9a44a68 before the function returns, if that dependency returns normally.

| Argument | Role |

| Input limit | Exclusive end address of the available input. Equality with the end of a required field is sufficient. |
| Default advance | A 32-bit value used unchanged when the header selects an omitted advance field. |

### Widths and representation

The supplied representation uses eight-bit bytes, 32-bit integer values, and a cursor stored in a 32-bit slot. Porting the behavior to a different pointer width requires an explicit representation decision; it is not evidence that the original cursor slot is wider.

Negative decoded values are delivered through 32-bit unsigned output slots as their two’s-complement bit patterns. For example, a decoded value of −1 is stored as `0xFFFFFFFF`.

Multibyte encoded values use most-significant-byte-first order. This describes the input format, not the machine byte order used for the output stores.

## Behavior

### Record layout and header

The function first reads the input address from the cursor slot. It then checks whether at least one byte is available before reading the header.

The header divides into four selectors:

| Header bits | Meaning |
|---|---|
| 1–0 | Position-pair representation |
| 3–2 | Size-pair representation |
| 5–4 | Advance representation |
| 7–6 | Classification, from zero through three |

All four selector values are handled in each representation group. No header value is rejected merely because of its bit pattern.

Fields appear in this order:

1. Header.
2. Position pair.
3. Size pair, if present.
4. Advance, if present.

There is no padding between fields and no alignment adjustment.

### Position pair

A position pair is always present. Its selector determines both its width and signedness.

| Selector | Bytes after header | Decoding |
|---|---:|---|
| 0 | 1 | First position is the signed high nibble; second position is the signed low nibble. |
| 1 | 2 | First and second bytes are independently interpreted as signed eight-bit values. |
| 2 | 4 | Two unsigned 16-bit values, first position followed by second position, each most-significant byte first. |
| 3 | 6 | Two signed 24-bit values, first position followed by second position, each most-significant byte first. |

For selector zero, each nibble has range −8 through 7. A nibble from zero through seven denotes that nonnegative value; a nibble from eight through fifteen denotes the nibble value minus sixteen. The two nibbles are signed independently.

For selector one, each byte has range −128 through 127 and is sign-extended to 32 bits.

For selector two, each value has range zero through 65,535. Encodings with the high bit set remain positive.

For selector three, each value has range −8,388,608 through 8,388,607. The high bit of the first byte is the sign bit, and the resulting 24-bit value is sign-extended to 32 bits.

### Size pair

Both size values initially equal zero. The size selector determines whether any size bytes are consumed.

| Selector | Bytes | Decoding |
|---|---:|---|
| 0 | 0 | Both size values remain zero. |
| 1 | 1 | High nibble is the first size; low nibble is the second size. Both are unsigned. |
| 2 | 2 | First byte is the first size; second byte is the second size. Both are unsigned. |
| 3 | 4 | Two unsigned 16-bit values, first size followed by second size, each most-significant byte first. |

The respective ranges are zero only, zero through fifteen, zero through 255, and zero through 65,535.

Unlike the position nibbles, size nibbles are never interpreted as negative.

### Advance

The advance initially equals the supplied default advance.

| Selector | Bytes | Decoding |
|---|---:|---|
| 0 | 0 | Preserve the supplied 32-bit default exactly. |
| 1 | 1 | Interpret the byte as signed eight-bit, then multiply its mathematical value by 256. |
| 2 | 2 | Decode an unsigned 16-bit value, most-significant byte first. |
| 3 | 3 | Decode a signed 24-bit value, most-significant byte first, and sign-extend it to 32 bits. |

Selector one produces multiples of 256 in the range −32,768 through 32,512. This scaling applies only to that representation.

Selector two produces values from zero through 65,535. It does not sign-extend or perform the selector-one scaling.

Selector three produces values from −8,388,608 through 8,388,607. There is no additional scaling after decoding.

The evidence establishes these numerical transformations, but not whether they represent fixed-point units.

### Bounds and input consumption

The function checks availability separately for the header, the complete position pair, the complete size pair when present, and the complete advance when present. Each nonempty field’s availability check precedes its byte accesses.

The limit is exclusive. A field ending exactly at the limit is accepted.

Total successful consumption is:

- One header byte;
- Plus one, two, four, or six position bytes;
- Plus zero, one, two, or four size bytes;
- Plus zero, one, two, or three advance bytes.

Thus successful records consume between two and fourteen bytes. Extra bytes beyond the record are neither required nor consumed.

A later bounds failure can occur after earlier fields have already been read. The function does not publish partial decoded results through its own output stores.

### Successful completion

After all required input has been accepted and decoded, the function performs its final stores in this order:

1. First position output.
2. Second position output.
3. First size output.
4. Second size output.
5. Advance output.
6. Classification output.
7. Cursor slot, containing the address immediately after the record.

It then returns zero.

All record decoding precedes these stores. Consequently, an output that overlaps already-read input does not change this invocation’s decoded values, provided the overlap otherwise satisfies the platform’s memory-access requirements.

Overlapping output slots can overwrite earlier results. A cursor-slot overlap is particularly significant because the cursor update is last.

### Insufficient input

If any required availability check fails, the function selects status eight and invokes F-4457a9a44a68 with a fixed diagnostic argument associated with invalid metrics input.

If the dependency returns normally, the function returns eight. It performs none of the seven success stores.

This is a guarantee about direct stores by F-bfb4440a667e, not an unconditional guarantee that caller memory remains unchanged: the dependency’s effects are unknown.

There is no established recovery, retry, partial-output reporting, or alternate error code for malformed storage. Memory faults and invalid pointer operations are outside the explicit shortage-handling contract.

## Side effects

On success, the function reads the cursor slot and the bytes comprising the record, writes six 32-bit outputs, and updates the cursor slot. It does not invoke the identified dependency on this path.

On a detected shortage, it may already have read a valid prefix of the record. It invokes the diagnostic dependency and does not directly update the outputs or cursor.

No allocation, deallocation, ownership transfer, or retention of caller pointers is visible in the function body. Input and output storage remain caller-provided. This observation does not establish that the error dependency performs no allocation, releases no memory, or retains nothing.

No direct global-state access is evident. Global, external-I/O, and memory effects of the dependency remain unknown. The supplied evidence also provides no concurrency, atomicity, or synchronization guarantee.

The ordered output stores are not an atomic commit. Concurrent observers are outside the established contract.
