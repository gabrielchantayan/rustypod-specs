# F-58e3c92f2660

## Purpose

F-58e3c92f2660 selects a count of eight-byte records, constructs a two-word address argument, and invokes two indirect dependencies in sequence. If both numerical result checks pass, it replaces each selected record’s two four-byte words using F-76bf07f4ac67, records the original requested position, and returns zero. Either failed numerical check produces return value three.

The selected count has an upper limit of 32,768 but no lower clamp. A zero count does not bypass either indirect call.

The first indirect call resembles positioning, the second resembles a transfer operation, and the helper calls resemble word normalization. These are inferred intentions, not established semantics. In particular, the second call’s arguments and result comparison do not establish transfer direction, actual storage access, or movement of records.

## Interface

### Arguments and result

The function receives two four-byte arguments:

1. A context address in the represented 32-bit address space.
2. A signed 32-bit requested position.

The result occupies four bytes.

| Result | Established meaning |
|---|---|
| 0 | Both indirect-call checks passed, the selected replacement sequence completed, and the final requested-position write completed. |
| 3 | The first indirect result was nonzero, or the second indirect result differed from the expected quantity. |

No separate result is established for inaccessible memory, arithmetic outside the reliably represented domain, or dependencies that fail to return normally.

### Referenced layout

All offsets below are byte offsets. Each listed field occupies four bytes.

| Location | Observed role |
|---|---|
| Context + 0x08 | Service-object address |
| Context + 0x30 | Descriptor address |
| Context + 0x100 | Unsigned low base word, read at two distinct points |
| Context + 0x104 | Signed high base word; its bit pattern participates in unsigned address arithmetic |
| Descriptor + 0x00 | Signed extent |
| Descriptor + 0x04 | Requested-position field written on successful completion |
| Descriptor + 0x08 | Storage address |
| Service object + 0x00 | Dispatch-table address |
| Dispatch table + 0x10 | Second indirect-call target |
| Dispatch table + 0x14 | First indirect-call target |

Each record spans eight bytes. Its first word begins at record offset zero; its second word begins at offset four. Each helper-result replacement writes four bytes.

“Context,” “descriptor,” “service,” “storage,” and “record” describe observed roles. They do not establish an application-specific object model.

### Preconditions and ownership

The function explicitly validates neither pointers nor alignment, capacity, position, or extent.

Normal completion requires every reached read, write, and indirect target to be valid. A positive selected count requires accessible word locations for the replacement sequence, subject to any reference changes made by dependencies. Additional requirements imposed by those dependencies are unknown.

No ownership transfer, retention, allocation, release, synchronization, or reentrancy guarantee is established. In particular, an unknown dependency must not be assumed to preserve globals, referenced fields, or object lifetimes.

## Behavior

### Count selection

Before either indirect call, the function follows the context’s descriptor address and reads its signed extent.

Within the domain where the signed arithmetic is representable:

- If the extent is no greater than the requested position plus 32,768, the selected count is the extent minus the requested position.
- Otherwise, the selected count is 32,768.

Equivalently within that domain, the selected count is the smaller of 32,768 and the remaining extent. There is no lower clamp.

Consequences include:

- Position equal to extent selects zero.
- Position greater than extent can select a negative count.
- Negative positions are not rejected.
- The selected count cannot exceed 32,768.

The selected count is retained. Changes to the extent or descriptor during a dependency call do not cause it to be recalculated.

Signed overflow in the threshold addition or extent subtraction is **documented_only**. The mathematical minimum interpretation is not established outside the representable domain.

### Address construction and the two low-base reads

The function first reads the unsigned low base word at context offset 0x100. It adds the requested position multiplied by eight and retains the resulting 32-bit low sum.

Position multiplication is a signed operation in the supplied representation. When that multiplication is representable, its result participates in the low-word addition through unsigned 32-bit arithmetic. The retained low sum therefore wraps modulo \(2^{32}\).

This retained sum is formed before resolving the first indirect target.

The first call’s outgoing low address word is the retained low sum plus 16, modulo \(2^{32}\).

Its outgoing high address word combines:

1. The high base word loaded from context offset 0x104.
2. A carry from adding the scaled-position word to a **fresh read** of the low base word.
3. A carry from adding 16 to the retained low sum.

The high base load is signed, but both carry operands are explicitly unsigned 32-bit values. Their addition converts the high base value to unsigned 32-bit arithmetic. Consequently, the outgoing high word is the high base **bit pattern**, plus the two carry contributions, modulo \(2^{32}\). High-word wraparound is established behavior, not an unresolved signed-overflow case.

The displacement carry is one exactly when the retained low sum exceeds 0xFFFFFFEF. Otherwise, it is zero.

The fresh low-base read occurs during argument construction after the first target has been resolved. It is distinct from the earlier read used to form the retained sum. If the reads differ, the outgoing low word depends on the initial observation while the scaled-position carry depends on the later observation. The resulting pair need not represent an offset from any single observed two-word base.

With stable low-base observations and a nonnegative, representable position-times-eight product, the two outgoing words describe the base plus that product plus 16, modulo \(2^{64}\).

That interpretation must not be generalized to a wider or signed product without qualification. The visible calculation does not add upper bits from a wider multiplication and does not explicitly sign-extend a negative scaled value into the high word.

The supplied representation does not establish the relative order of independent argument-expression reads, including the fresh low-base read, high-base read, and service-address read used as the receiver.

### First indirect call

The first target is resolved through the service object’s dispatch-table entry at offset 0x14.

The call receives these arguments in order:

1. A service-object address read from the context.
2. The resolved target address itself.
3. The outgoing low address word.
4. The outgoing high address word.
5. Zero.

The target address is explicitly supplied as the second argument. Its meaning is unknown; it is not established as a mode, position, or other application value.

The four-byte result is compared with zero.

- A nonzero result causes return value three.
- A zero result permits the second indirect call.

On the nonzero path, this function performs no second indirect call, helper calls, replacement stores, or final requested-position write. Effects already performed by the first dependency remain possible.

A zero result establishes only that the numerical check passed. It does not prove that any positioning operation occurred.

### Second indirect call

After the first check passes, the function resolves another target through dispatch-table offset 0x10.

This call receives:

1. A service-object address obtained from the context.
2. A storage address obtained by following the context’s descriptor address and reading descriptor offset eight.
3. A four-byte quantity formed by shifting the retained selected count left by three.
4. The literal value two.

For nonnegative selected counts, the quantity is eight times the count. Its largest established value is 262,144.

The returned four-byte value is compared with the retained count multiplied by eight. Only exact equality passes. There is no retry or acceptance of a partial numerical result.

A mismatch causes return value three without helper calls, replacement stores, or the final requested-position write. The function does not roll back dependency effects.

The call establishes a pointer argument, a quantity argument, a literal argument, and an equality check. It does not establish whether the pointer denotes input or output, whether the quantity bounds actual accesses, or whether any data movement occurs.

References used for this call are resolved after the first dependency returns. The service, descriptor, and storage references must not be assumed equal to earlier observations. Nor is a snapshot relationship established between target resolution and receiver evaluation within the call expression.

### Ordered word replacement

After both numerical checks pass, records are processed in increasing index order, beginning at zero. Processing continues while the signed index is less than the retained count.

For each record, the established sequence is:

1. Resolve the storage address through the current context and descriptor references.
2. Invoke F-76bf07f4ac67 with the address of the record’s first word.
3. Resolve the destination through the context and descriptor again and store the helper’s four-byte result at the first-word offset.
4. Resolve the storage address again.
5. Invoke F-76bf07f4ac67 with the address of the record’s second word.
6. Resolve the destination again and store that result at the second-word offset.

The helper receives an address, not a loaded word value.

The first replacement store precedes the second helper call. Both replacements for a record precede processing the next record. No helper-result failure check appears.

For a nonnegative selected count of \(n\), completed processing performs exactly \(2n\) helper calls and \(2n\) four-byte replacement stores.

Every destination is resolved after its corresponding helper returns. A helper can therefore change a descriptor or storage reference so that its result is stored somewhere other than its argument address. Subsequent helper arguments also use newly resolved references. No snapshot, aliasing, or reference-preservation guarantee is established.

A zero count skips the loop. A negative count also fails the initial signed loop condition if execution reaches it. Whether the preceding negative-count shift and multiplication have defined behavior remains **documented_only**.

### Final state update

After the loop, the function follows the context’s descriptor address again and writes the original requested position at descriptor offset four. It then returns zero.

The written value is the caller’s starting position, not the position advanced by the selected count.

The final descriptor can differ from the descriptor that supplied the extent. Success does not establish that every operation concerned the same descriptor or storage object.

## Side effects

### Explicit writes

The function explicitly writes:

- Each four-byte value returned by F-76bf07f4ac67 to its subsequently resolved word destination.
- The original requested position to the descriptor resolved at completion.

It does not explicitly assign the extent, service address, descriptor address, storage address, or base words. Dependencies may nevertheless modify those fields or other state.

### Partial effects

Neither numerical failure path restores prior state.

The first dependency may produce effects before returning nonzero. The second may produce effects before returning a mismatched quantity. Those effects need not be storage transfers.

If a helper does not return normally after earlier replacements, no visible mechanism rolls those replacements back. Atomic completion and exception recovery are not established.

No allocation or release is explicit in this function. That absence does not establish that dependencies avoid allocating, retaining, replacing, or releasing memory.

### Read stability

The initial extent determines a retained count. Other references are repeatedly resolved, and the low base word has two distinct observations during address construction.

These reads are not guaranteed snapshots. Whether concurrent changes are supported, or whether differing observations can occur in the execution environment, remains **documented_only**.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless otherwise stated, they assume valid accesses, normally returning dependencies, stable referenced fields, and representable signed arithmetic.

### One selected record

For extent 11 and requested position 10:

- The selected count is one.
- With agreeing low-base reads, the address pair represents the base plus 96, modulo \(2^{64}\).
- A zero first result permits the second call with quantity eight and final argument two.
- A second result of eight permits helper calls for storage offsets zero and four.
- Each helper result is stored before the next helper call.
- The final requested-position field receives 10, and the function returns zero.

The matching second result does not prove that eight bytes were transferred.

### Upper count limit

For extent 100,000 and requested position zero:

- The selected count is 32,768.
- The second quantity is 262,144.
- If both checks pass, processing completes 65,536 helper calls and 65,536 replacement stores.
- The final requested-position field receives zero, not 32,768.

### Empty selection

For extent 25 and requested position 25:

- The selected count is zero.
- The first call still occurs.
- A zero first result permits the second call with quantity zero.
- A zero second result permits the final position write without helper calls.
- The function returns zero.

### Numerical failures

A nonzero first result produces three without the second call or explicit success-path writes.

For a selected count of two, a second result of eight fails the expected quantity of 16. The function returns three without replacements or the final position write. Dependency effects remain possible.

### Low-word carry

If both low-base reads yield 0xFFFFFFF8 and the requested position is one:

- The retained low sum is zero.
- The outgoing low word is 0x00000010.
- The scaled-position addition contributes one carry.
- The displacement contributes no carry.

With a high base bit pattern of 0x00000007, the outgoing high word is 0x00000008.

### High-word wraparound

Under the same low-base and position conditions, a high base bit pattern of 0xFFFFFFFF produces an outgoing high word of 0x00000000.

Although that high field is loaded as signed, the carry addition is unsigned. This wraparound is established modulo-\(2^{32}\) behavior and does not require an additional signed-overflow assumption.

### Different low-base observations

Conditionally, suppose the initial low-base read yields zero, the fresh read yields 0xFFFFFFF8, the position is one, and the high base bit pattern is seven.

The retained low sum is eight, the outgoing low word is 0x00000018, and the fresh-read addition contributes one carry. The outgoing high word is eight.

This differs from adding 24 to the initially observed two-word base. Reusing the initial low-base observation for the carry would change the behavior.

### Changed storage reference

If a helper changes the descriptor’s storage address before returning, its replacement result uses the subsequently resolved destination. The helper’s argument address is not guaranteed to receive that result. Later helper calls also use fresh resolutions.

## Uncertainties

The following remain **documented_only**:

- Valid input ranges beyond the established arithmetic domain.
- Signed overflow in position scaling, threshold addition, or count subtraction.
- Negative-count left shifts and potentially overflowing negative-count multiplication for the second result comparison.
- Whether a negative selected count can reach the final update in the actual execution environment.
- Address-arithmetic limits, alignment requirements, and inaccessible-memory behavior.
- Evaluation order among independent reads within argument expressions.
- Whether concurrent mutation is permitted and whether distinct reads can differ in practice.
- Dependency preservation of globals, pointers, memory, ownership, and lifetimes.
- Semantics of the indirect operations, including whether any data movement occurs.
- Meaning of literal arguments and the target-address argument.
- The helper’s transformation, byte order, and additional effects.
- Abnormal termination and recovery.

High-word carry addition is **not** unresolved: it uses unsigned 32-bit arithmetic and wraps modulo \(2^{32}\). This does not resolve the separate signed-arithmetic uncertainties listed above.

## Evidence

The established claims derive solely from the supplied function representation and opaque dependency mapping.

Static evidence establishes the four-byte field accesses, eight-byte record stride, upper count limit without a lower clamp, distinct low-base reads, retained low sum, two carry contributions, and unsigned high-word addition. It also establishes the indirect-call order, numerical checks, address-based helper arguments, repeated destination resolution, final starting-position write, and result values zero and three.
