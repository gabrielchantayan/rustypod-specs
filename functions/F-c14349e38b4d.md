# F-c14349e38b4d

## Purpose

F-c14349e38b4d conditionally creates and initializes a record associated with a caller-supplied context. Two unsigned dimension requests control initialization:

- A nonzero first request establishes or checks a first dimension and may trigger four auxiliary allocations.
- A nonzero second request establishes or checks a second dimension.
- Once both stored dimensions are nonzero, a missing shared data area triggers another allocation and construction of a row-address table.

Zero requests do not clear existing dimensions. Nonzero requests that conflict with already established dimensions produce status 3.

The operation is not transactional. It can publish a record, store allocation results, establish dimensions, and write address tables before subsequently returning an error. No rollback or release operation is visible.

These are static behavioral findings. The interpretation of the dimensions as rows and columns, and of returned 32-bit values as allocation addresses, is inferred from their use rather than independently established dependency contracts.

## Interface

### Inputs

The function accepts four machine-level inputs:

| Input | Width and interpretation |
|---|---|
| Context address | A 32-bit address used to access the context and derive addresses of embedded regions |
| First dimension request | Unsigned 32-bit integer |
| Second dimension request | Unsigned 32-bit integer |
| Auxiliary argument | Opaque 32-bit value passed only to F-3ce007b692cc |

The context must support at least these accesses:

| Byte offset | Access |
|---|---|
| 100, hexadecimal 0x64 | Read an opaque 32-bit dependency handle |
| 524, hexadecimal 0x20c | Read and, on successful record creation, write a 32-bit record address |

The function also forms addresses at context offsets 0x84, 0xa4, and 0x1c8. It stores those addresses into the record; it does not directly dereference those embedded regions.

### Result

The result is a 64-bit composite value:

- Bits 0–31 contain the final 32-bit status.
- Bits 32–63 contain an auxiliary result word.

The status begins at zero. Dependencies receive its address and may modify it. The function itself assigns status 3 for a dimension conflict.

The upper result word begins as the first dimension request. It becomes zero immediately before any call to F-6dd003795db7. Consequently:

- A record-creation failure preserves the first request in the upper word.
- A conflict reached without an F-6dd003795db7 call also preserves that request.
- Any path that calls F-6dd003795db7 returns an upper word of zero.
- A zero first request necessarily produces an upper word of zero.

The upper word is not a general-purpose success indicator or a reliable count of initialized objects.

### Record layout used by this function

Offsets below are relative to the record address. Every listed field is 32 bits.

| Byte offset | Role observed here |
|---|---|
| 0x00 | Stored first dimension |
| 0x04 | Stored second dimension |
| 0x18 | Shared data base and first entry of a row-address table |
| 0x88 | First base returned by the fourth auxiliary allocation |
| 0x8c | Address derived from that base plus four times the first request |
| 0x90 | Address of the context’s embedded region at 0x84 |
| 0x94 | Base returned by the first auxiliary allocation |
| 0xd4 | Address of the context’s embedded region at 0xa4 |
| 0xd8 | Base returned by the second auxiliary allocation |
| 0x11c | Address of the context’s embedded region at 0x1c8 |
| 0x120 | Base returned by the third auxiliary allocation |

These fields participate in variable-length address tables. Their separation is not checked at runtime.

## Behavior

### 1. Obtain the record

The function first reads the dependency handle from context offset 0x64. That captured value is used for all dependency calls in this invocation.

It initializes a local status word to zero, then reads the record address from context offset 0x20c.

If that address is zero, it calls F-3ce007b692cc with these arguments, in order:

1. Captured dependency handle.
2. Size value 0x160, or 352.
3. Address of the local status word.
4. Auxiliary argument.
5. First dimension request.
6. Second dimension request.

If the status is nonzero after the call, the function returns immediately. It does not publish the returned record address.

Otherwise, it writes the returned address into context offset 0x20c and continues using that address. It does not separately check whether the returned address is zero.

If a record address was already present, this creation call and publication write are skipped.

### 2. Process the first dimension request

A zero first request skips first-dimension validation and auxiliary initialization. The function proceeds directly to processing the second request.

For a nonzero first request, the stored first dimension determines the next action:

- If it is nonzero and equal to the request, proceed to the second request.
- If it is nonzero and different from the request, set status to 3 and return.
- If it is zero, perform the auxiliary initialization described below.

#### Auxiliary allocation sequence

Four calls to F-6dd003795db7 occur in this exact order:

| Call | Arguments after handle | Destination of returned word |
|---|---|---|
| First | 0x20, 0, first request, 0, status address | Record offset 0x94 |
| Second | 0xc4, 0, first request, 0, status address | Record offset 0xd8 |
| Third | 0x10, 0, first request, 0, status address | Record offset 0x120 |
| Fourth | 4, 0, first request shifted left by one bit, 0, status address | Record offset 0x88 |

Before each call, the upper result word is set to zero.

After each call, the returned word is stored in its destination before the status is inspected. A nonzero status causes immediate return, preserving all writes and effects already performed. Later calls are not made.

The status word is not explicitly reset between calls. Under ordinary successful dependency behavior it remains zero, but that behavior belongs to the dependency contract.

#### Address-table construction

After all four calls report zero status:

1. The function writes record offset 0x8c with the fourth returned base plus four times the first request.
2. It stores the three context-relative addresses at record offsets 0x90, 0xd4, and 0x11c, in that order.
3. For each unsigned index from 2 through the first request, inclusive, it writes three further table entries in this order:
   - Extend the table beginning at offset 0xd4 by adding 0xc4 to its preceding entry.
   - Extend the table beginning at offset 0x90 by adding 0x20 to its preceding entry.
   - Extend the table beginning at offset 0x11c by adding 0x10 to its preceding entry.
4. Only after that loop does it store the first request as the first dimension at record offset 0x00.

Each table begins with an embedded-context address followed by a dependency-returned address. The loop extends the dependency-backed portion. For a first request of one, no extension iterations occur.

The function allocates using the full first request even though each address table also contains an embedded-context entry. It does not establish how consumers use that extra entry or whether every allocated byte is used.

### 3. Process the second dimension request

A zero second request leaves the stored second dimension unchanged.

For a nonzero second request:

- If the stored second dimension is nonzero and differs from the request, set status to 3 and return.
- Otherwise, write the requested value to record offset 0x04.

A matching nonzero value is therefore written again. A second-dimension conflict can occur after successful first-dimension allocation and initialization; those earlier changes remain in place.

### 4. Establish the shared data area when needed

The function reads the stored first and second dimensions, in that order. It proceeds with shared-data allocation only if:

- Both captured dimensions are nonzero; and
- The word at record offset 0x18 is zero.

It then sets the upper result word to zero and calls F-6dd003795db7 with:

1. Captured dependency handle.
2. Element-size value 4.
3. Zero.
4. Product of the two captured dimensions, calculated as a 32-bit unsigned value.
5. Zero.
6. Address of the local status word.

The returned word is stored at record offset 0x18 before checking status.

If status is nonzero, no remaining row-address entries are initialized.

If status is zero, the function fills entries for row indices one through the captured first dimension minus one. Each entry is:

- Located at record offset 0x18 plus four times the row index.
- Derived from the current word at offset 0x18 plus four times the row index times the captured second dimension.

The base word is read again for each entry. The dimension values used for the allocation and this loop were captured before the dependency call.

If offset 0x18 was already nonzero, the function neither reallocates nor reconstructs this table. It does not verify that the existing area matches the dimensions.

### Arithmetic and bounds

Address additions, products, and the fourth allocation’s left shift use 32-bit arithmetic. Overflow is not rejected.

In particular:

- Doubling the first request can discard its high bit.
- The shared-data element count can wrap before reaching the dependency.
- Table addresses and derived data addresses can wrap.
- Auxiliary-table construction has an inclusive unsigned loop bound. A first request of 0xffffffff allows the increment to wrap, so the loop has no normal bound-driven termination.

No explicit dimension maximum, allocation-capacity check, address-validity check, or multiplication-overflow check is present.

## Side effects

### Observable writes and partial states

The principal write order is:

1. Publish a newly obtained record, if creation reports success.
2. Store each auxiliary allocation result immediately after its call.
3. Store the split address derived from the fourth allocation.
4. Store embedded-context addresses and extend auxiliary tables.
5. Establish the first dimension.
6. Establish or rewrite the second dimension.
7. Store a shared-data allocation result.
8. Populate remaining shared-data row addresses.

A failure can expose any prefix of those writes.

Examples of partial states include:

- A published record whose first auxiliary allocation failed.
- Several stored allocation results while the first dimension remains zero.
- An established first dimension followed by a second-dimension conflict.
- Both dimensions established while shared-data allocation reports failure.
- A nonzero shared-data base stored alongside a failure status, causing a later invocation to skip shared-data allocation if it sees that same base.

### Ownership and lifetime

The function contains no explicit release operation. It does not undo allocations on failure or free an existing record.

That does not establish ownership of returned objects. Dependencies may allocate, borrow, reuse, mutate, or release storage according to contracts unavailable here. The function itself treats returned words as addresses.

Stored embedded-context addresses introduce a lifetime dependency on the context. Safe subsequent use requires those addresses to remain meaningful.

### Preconditions for defined memory access

The context and record must be valid for all accesses taken by the selected path. A creation dependency reporting success must return a usable record address.

The requested size 0x160 is sufficient for the fixed fields listed above, but not for arbitrary table lengths. With a record of exactly that size, auxiliary-table extension for a first request of 17 reaches byte offset 0x160, outside the requested allocation. Earlier auxiliary tables also begin colliding with neighboring table regions at that request size.

A first request no greater than 16 avoids those particular auxiliary-table collisions and out-of-range writes. This is an inferred layout constraint, not an enforced limit or a complete safety guarantee.

Concurrent mutation and dependency-driven mutation of the same record are not guarded against by this function.

## Dependencies

### F-3ce007b692cc

Used only when the context has no record address.

Established contract at this call site:

- Receives the handle, requested size 352, writable status address, auxiliary argument, and both original dimension requests.
- Returns a 32-bit word used as the record address.
- A nonzero status prevents publication and further processing.

Unknown: initialization policy, actual allocation size, ownership, failure cleanup, and other side effects. In particular, this function does not itself zero a newly obtained record.

### F-6dd003795db7

Used for up to five allocation-like operations.

Established contract at this call site:

- Receives six arguments.
- The second argument varies among 0x20, 0xc4, 0x10, and 4.
- The third and fifth arguments are zero.
- The fourth argument is a dimension-derived count.
- The sixth argument is the writable status address.
- Its returned 32-bit word is stored even when the status reports failure.

The size/count interpretation is inferred from subsequent address arithmetic. The exact meaning of the zero arguments is unknown.

No preservation of record contents, context contents, globals, allocation ownership, or unrelated memory is assumed for either dependency. The routine continues using its captured handle and record address rather than rereading the context after every call.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, memory is valid, arithmetic does not wrap, and dependencies have no additional mutations.

1. **Existing complete record, matching requests.**  
   Given stored dimensions 3 and 5, a nonzero shared-data base, and requests 3 and 5, no dependency is called. The second dimension is rewritten as 5. Status is zero and the upper result word is 3.

2. **Zero requests preserve established dimensions.**  
   Given stored dimensions 3 and 5 and a nonzero shared-data base, requests zero and zero make no dimension writes and no dependency calls. Both result words are zero.

3. **First-dimension conflict.**  
   Given a stored first dimension of 3 and first request 4, status becomes 3 before second-dimension processing. The upper result word is 4.

4. **Creation failure.**  
   Given a zero context record address, if F-3ce007b692cc reports status 9 for first request 6, the context’s record address is not written by this function. The result contains status 9 and upper word 6.

5. **Failure during auxiliary initialization.**  
   Given a record with first dimension zero and first request 2, suppose the first auxiliary call succeeds and the second reports status 7. Both returned words are stored. The third and fourth calls do not occur, and the first dimension is not established. The upper result word is zero.

6. **Second conflict after first initialization.**  
   Given first dimension zero, second dimension 8, and requests 2 and 9, successful auxiliary initialization establishes first dimension 2 before status 3 is returned for the second request. The first-dimension changes are retained.

7. **Shared-data initialization.**  
   Given stored dimensions 3 and 5, zero shared-data base, and zero requests, the dependency receives size value 4 and count 15. If it returns address B with zero status, the three row entries become B, B + 20, and B + 40. Both result words are zero.

8. **Wrapped shared-data count.**  
   Given stored dimensions 0x80000000 and 2 with a missing shared-data base, the count passed to the dependency is zero. The function does not reject this overflow. Safe completion is not established.
