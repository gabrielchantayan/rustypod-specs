# F-6da54eb84067

## Purpose

F-6da54eb84067 processes a directory header from a stream-like object, validates that header, publishes directory metadata to a destination object, obtains storage, and transfers four 32-bit words per directory record.

The operation is **not transactional**. Direct destination writes occur before several checked operations can fail. The function contains no direct rollback or explicit deallocation. Unknown dependencies may independently modify the destination, storage, stream, globals, or previously exposed status storage.

Diagnostic content and the 16-byte record structure suggest a font-table directory loader. That is **inferred intent**, not an established binary-format or ownership contract.

## Interface

### Arguments and directly accessed memory

The function takes two address-valued arguments, each represented as a 32-bit integer in the supplied representation:

| Argument | Direct access |
|---|---|
| Destination object | Writes a 32-bit field at `0x94`, a 16-bit field at `0x98`, and a 32-bit field at `0x9c`; later reads the latter two fields. |
| Stream-like object | Reads a 32-bit field at `0x1c`; passes the object to stream-related dependencies. |

The destination fields have these established uses:

| Offset | Width | Use |
|---|---:|---|
| `0x94` | 32 bits | Published header format value. |
| `0x98` | 16 bits | Published record count; subsequent direct reads interpret it as unsigned. |
| `0x9c` | 32 bits | Published storage result; subsequently interpreted as a directory base address. |

Each traversed record occupies 16 bytes, with four 32-bit words at record-relative offsets `0`, `4`, `8`, and `12`.

The temporary header exposes a 32-bit format value followed by a 16-bit count. The complete header layout and any additional fields used by dependencies are **documented_only**.

The stream field at `0x1c` is captured before the entry diagnostic and later passed to F-6dd003795db7. Its semantic type is unresolved; it must not be assumed to be an allocator or ownership token.

### Diagnostic control

A global reference identifies an object with a signed 32-bit diagnostic level at offset `0x48`. A level greater than one enables an applicable diagnostic.

The function reads this global reference twice during entry. The first reference is retained for later checks; the second supplies the entry check. Replacing the global reference later does not itself replace the retained reference. Mutations of the referenced object can affect subsequent checks.

### Return value and exposed status storage

The function returns a 32-bit status value. Most checked dependency results are stored in a current-status location. Its address is passed to F-10d2ce969adf and, on the loading path, F-6dd003795db7.

There is no established guarantee that either dependency relinquishes that address. Later dependencies therefore cannot be assumed to preserve the stored status.

F-d036abe1e536 is different: its nonzero result is returned directly, without using the exposed current-status location.

Normal traversal explicitly resets current status to zero. Zero is the ordinary final result only if subsequent calls leave that storage unchanged. A nonzero result does not identify how much destination or stream state changed.

### Preconditions

Defined normal execution requires:

- Valid memory for all direct object, diagnostic-level, header, and record accesses.
- Objects acceptable to each reached dependency.
- Usable header values after successful processing and validation.
- Adequate, valid storage for the actual traversal range.
- Valid pointer formation, comparison, and advancement for that range.

No direct null checks, destination-size checks, storage-result checks, or independent reconciliation of allocation size and traversal count are visible.

## Behavior

### Entry observations

The initial observable sequence is:

1. Read and retain the diagnostic-control reference.
2. Read and retain the stream’s 32-bit field at `0x1c`.
3. Read the diagnostic-control reference again.
4. Read the signed level through this second reference.
5. If that level exceeds one, call F-4457a9a44a68 with the entry diagnostic and destination argument.

The entry diagnostic receives the destination argument, not either diagnostic-control reference.

### Header acquisition

After the optional entry diagnostic:

1. F-b03b1199772e receives the stream. Its 32-bit result is retained for a later positioning calculation.
2. F-10d2ce969adf receives the stream and current-status address. Its 32-bit result becomes the temporary format value.
3. The function checks current status and returns it immediately if nonzero.
4. A separate unresolved global value is read.
5. F-de70a5256fd2 receives the stream, that just-read global value, and the temporary header address.
6. Its result replaces current status. A nonzero value is returned immediately.

The unresolved global argument is read after the preceding dependencies have run. It is not established to be immutable, a descriptor, or unchanged by those calls.

The temporary count is not explicitly initialized before dependency processing. Successful continuation requires dependencies to make the subsequently used header contents usable; their decoding contract is not supplied.

### Header diagnostics and validation

After successful F-de70a5256fd2:

- The function checks the diagnostic level through the retained entry reference.
- If enabled, it emits a count diagnostic.
- Only after that diagnostic does it check the level again.
- If the second check is enabled, it emits a format diagnostic.

If the first check is disabled, the second check is skipped. The count diagnostic may affect whether the format diagnostic is emitted. Neither diagnostic is assumed to preserve the mutable header or other exposed state.

F-d9b1de2df19f then receives the mutable temporary header and stream. Its result replaces current status.

On nonzero validation status:

- This function has not yet directly written the destination fields.
- A level below two causes immediate return of current status.
- Otherwise, an invalid-directory diagnostic is emitted, followed by return of the then-current status.

The rejection diagnostic can affect exposed status storage. Thus its return path is not guaranteed to return the original validation result. Dependencies may also have modified destination state indirectly; absence of direct publication is not destination preservation.

On zero validation status, publication uses the header contents present after validation. Validation is not assumed to preserve either header field.

### Metadata publication and storage acquisition

The direct publication order is:

1. Write the temporary 16-bit count to destination offset `0x98`.
2. Write the temporary 32-bit format value to destination offset `0x94`.

F-6dd003795db7 then receives six arguments, in order:

1. The stream-associated 32-bit value retained at entry.
2. Element size `16`.
3. Zero.
4. The temporary 16-bit count, widened under an unresolved calling convention.
5. Zero.
6. The current-status address.

Its 32-bit return value is written to destination offset `0x9c`. Only then is current status checked. A nonzero status causes immediate return.

These are historical writes, not an unconditional assertion about all three fields’ values at return. F-6dd003795db7 may modify the previously published count or format through shared or aliased state. The storage-result write nevertheless occurs after that call and before the status check. No direct rollback follows failure.

The function does not directly read or explicitly release the destination’s previous storage reference. The call pattern suggests storage acquisition for 16-byte elements, but allocation, initialization, ownership transfer, and zero-count behavior remain unresolved.

### Positioning and access establishment

If storage acquisition leaves zero status, F-e40a3ceddab2 receives:

- The stream.
- The retained result of F-b03b1199772e plus `12`.

Its result replaces current status. Nonzero status is returned immediately.

The addition uses the visible 32-bit integer representation and has no explicit overflow check. The exact overflow contract is **documented_only**; wrapping must not be assumed.

After successful positioning, the destination count is read as unsigned 16-bit. F-d036abe1e536 receives the stream and that count multiplied by `16`.

This size calculation ranges from `0` to `1,048,560` bytes. The unsigned count is widened before shifting, so this calculation fits in 32 bits.

A nonzero F-d036abe1e536 result is returned directly. No record traversal or F-9787e15c337d call follows that failure.

Neither positioning nor access establishment is assumed to preserve destination fields. Failure establishes the earlier publication history and absence of direct rollback, not unchanged published values.

### Traversal range and record transfer

After successful access establishment, the function:

1. Reads the directory base from destination offset `0x9c`.
2. Rereads the count at `0x98` as unsigned 16-bit.
3. Forms the endpoint for that many 16-byte records.
4. Assigns zero to current status.

The traversal count is read after F-d036abe1e536 returns. It may differ from the count used for the access request. The base and count may also differ from their earlier published values. No direct consistency or capacity check intervenes.

Traversal uses forward pointer comparison against the fixed endpoint. For each reached record:

1. Call F-77339711215b and store its 32-bit result at offset `0`.
2. Call it again and store its result at offset `4`.
3. Call it again and store its result at offset `8`.
4. Call it again and store its result at offset `12`.
5. Check the retained diagnostic object’s level and emit a record diagnostic if enabled.
6. Advance by 16 bytes.

Each store precedes the next reader call. There is no atomic four-word commit.

Reader results are treated as data, not checked statuses. Every normally returned result is stored. Reader error signaling and nonlocal termination are unresolved.

The directory base and endpoint are not reread from destination fields during traversal. Changes to those fields alone do not redirect the established range. Dependencies may nevertheless modify the record storage itself.

### Record diagnostic arguments

An enabled record diagnostic is prepared after the fourth store:

- The first word is reread from record memory and used to derive four character arguments, from its high-order portion toward its low-order portion.
- The third word is reread from record memory.
- The final numeric argument is the saved fourth reader result, not a reread of the fourth word.

Consequently, diagnostic values need not reproduce the originally stored record. Later readers may have changed earlier words before they are reread.

The character expressions use signed integer shifts and a character conversion. Exact behavior and rendering for high-bit values are **documented_only**. They are not established as four unsigned-byte conversions.

### Completion

After normal traversal, including zero iterations, F-9787e15c337d receives the stream. Its return value is not checked.

The function then checks the retained diagnostic object’s level:

- Below two: return current status.
- Otherwise: emit the loaded-directory diagnostic, then return current status.

The loaded diagnostic is not gated by a fresh successful-status check. Readers, record diagnostics, F-9787e15c337d, or the final diagnostic may affect previously exposed status storage.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Distinct entry references.** If the first diagnostic-reference read yields A and the second yields B, the entry check uses B. Later checks use A, even if a dependency replaces the global reference.

2. **Late global argument.** If an earlier header dependency changes the unresolved global argument and execution continues, F-de70a5256fd2 receives the value read after those calls, not an entry snapshot.

3. **Initial failure.** If current status is `7` when checked after F-10d2ce969adf, the function returns `7` without calling F-de70a5256fd2 or directly publishing destination fields.

4. **Validation rejection.** If validation returns `5` and the rejection diagnostic is disabled, the function returns `5`. If enabled, it returns the status present after that diagnostic. Neither branch directly publishes destination fields; indirect modifications remain possible.

5. **Storage failure with possible metadata mutation.** Suppose count and format are published, then F-6dd003795db7 returns address value P and leaves status `3`. The function writes P to `0x9c`, checks status, and returns `3` without positioning. Count and format equal their published values at return only if acquisition did not modify those fields. No direct rollback occurs.

6. **Positioning failure.** If F-e40a3ceddab2 returns `9`, that value is returned without access establishment. The three publication writes occurred earlier. Final destination values depend on dependency effects; the function does not restore them.

7. **Two-record traversal.** With stable count two, adequate valid storage, valid pointer ordering, and successful checked dependencies, access establishment receives `32`. Traversal performs eight reader calls and eight stores through byte offset `28`. F-9787e15c337d follows. Final record contents equal the returned words only if later dependency effects do not overwrite the stores.

8. **Diagnostic rereads.** If the fourth reader changes the first and third stored words before returning L, an enabled diagnostic uses the changed first and third words and saved value L.

9. **Zero count.** With stable zero count, successful dependencies, and valid zero-range pointer semantics, storage acquisition and positioning still occur. Access establishment receives zero, traversal calls no reader, and F-9787e15c337d is called.

10. **Access failure with possible destination mutation.** If F-d036abe1e536 returns `11`, the function returns `11` directly, without record reads or F-9787e15c337d. Earlier publication writes are not directly undone. Their values remain unchanged only if intervening dependencies have not modified them.

11. **Maximum unsigned count.** A count of `65,535` at access-size calculation produces `1,048,560` bytes. This does not establish adequate storage, a matching later traversal count, or valid endpoint formation.
