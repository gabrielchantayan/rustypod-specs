# F-d08635bbe1d7

## Purpose

F-d08635bbe1d7 accepts three 32-bit configuration values and one byte-sized option for a caller-supplied object. It validates the configuration, records accepted portions in the object, compares a complete valid request against a second configuration stored there, and invokes three operations on an embedded receiver.

The established behavior is configuration-oriented. Interpreting the three values as a sample rate, sample width, and channel count is plausible from their accepted ranges, but is **inferred intent**, not a prerequisite for this contract. This document calls them the **rate**, **width**, and **count** for readability.

Rejection is not transactional: some rejected requests still change object fields. Success means that the function reached the end of its call sequence and returned 1. It does not establish that an external device accepted the configuration or that any dependency reported success.

The address calculations and dispatch structure reflect a 32-bit environment. Portability to another pointer width, alignment model, or calling convention is not established.

### Return value

The result is a 32-bit value:

- **0:** one of the configuration checks failed.
- **1:** validation passed, the three dependent operations were invoked, and execution returned normally through the success path.

Dependency results are not used to choose this return value. If a dependency does not return normally, this contract does not establish a return from F-d08635bbe1d7.

## Behavior

### 1. Rate validation

The function first checks the requested rate without accessing object fields.

The observed unsigned arithmetic accepts two adjacent intervals:

- 8000 through 40767;
- 40768 through 48000.

Their union is exactly **8000 through 48000 inclusive**.

The subtractions used to express these tests are 32-bit unsigned operations, with wraparound modulo \(2^{32}\). The interval above accounts for that arithmetic; it is not a signed-range approximation.

If the rate is outside this interval, the function returns 0. No object read, object write, or dependent call is shown on that path.

### 2. Width normalization and first write

For an accepted rate, a requested width of zero is normalized to 16 for subsequent validation, storage, and comparison.

The function then writes the requested rate to `+0x2A178`.

Only after this write does width validation determine whether execution may continue. Accepted effective widths are 8 and 16. Consequently:

- Width 0 succeeds at this stage as effective width 16.
- Width 8 succeeds.
- Width 16 succeeds.
- Every other width causes return 0 after the rate write.

For a rejected width, the function does not write the width field and does not inspect or validate the count through an object access. No dependent call is made.

### 3. Width write and count validation

For an accepted effective width, the function writes that width to `+0x2A17C`.

It then checks the requested count. Only 1 and 2 are accepted.

If the count is rejected, the function returns 0 with the rate and normalized-width writes retained. It does not write the count field or perform the dependent calls.

For an accepted count, it writes the count to `+0x2A180`.

### 4. Comparison against stored configuration

After all three current/requested fields have been written, the function computes a difference flag using the original accepted rate, normalized width, and accepted count.

The comparison reads are short-circuited in this order:

1. Read the comparison rate at `+0x2A184`.
2. Only if that rate equals the accepted requested rate, read the comparison width at `+0x2A188`.
3. Only if both rate and width match, read the comparison count at `+0x2A18C`.

The flag is:

- **0** if all three values match;
- **1** otherwise.

A mismatch does not reject the request. A complete match does not skip the subsequent operations.

This flag is determined before any dependent call. Later changes to the object do not cause it to be recomputed.

### 5. Indirect receiver operation

The function obtains the dispatch pointer stored at the embedded receiver address, object base `+0x04`, and selects its entry at byte offset `+0x08`.

It invokes that entry with:

- the embedded receiver address;
- the difference flag, represented as a 32-bit value of 0 or 1.

This operation occurs on every fully validated request, including requests identical to the comparison configuration.

No returned value from this operation affects the remaining path.

### 6. Rate-related dependency

After the indirect operation returns, the function invokes **F-eae52a1fb753** with:

- the embedded receiver address;
- a newly read 32-bit value from `+0x2A178`;
- a newly read 32-bit value from `+0x2A184`.

These are field reads made after the indirect call, not preserved copies of the original input or earlier comparison value. If that call modifies either field, the later dependency receives the changed value.

The supplied representation does not establish the relative evaluation order of these two argument reads. It does establish that they supply the arguments to F-eae52a1fb753 after the indirect operation has returned.

### 7. State projection and option write

After F-eae52a1fb753 returns, the function performs four 32-bit read-and-write transfers in this order:

1. Read `+0x2A17C`, then write that value to `+0x18`.
2. Read `+0x2A188`, then write that value to `+0x1C`.
3. Read `+0x2A180`, then write that value to `+0x20`.
4. Read `+0x2A18C`, then write that value to `+0x24`.

The values come from the object as it exists after the dependency call. They are not guaranteed to equal either the original inputs or the values seen during the earlier comparison.

Next, the function writes the supplied option byte unchanged to `+0x0D`.

### 8. Final dependency and completion

The function invokes **F-ad37e9c0edc9** with the embedded receiver address.

If that call returns normally, the function returns 1. No additional object writes are shown after this final call.

## Side effects

| Outcome | Direct writes before return | Dependent calls |

| Rate accepted, width rejected | Current rate | None |

There is no rollback on validation failure. Callers must not interpret return 0 as a guarantee that the object is unchanged.

## Acceptance examples

These examples are conditional static acceptance criteria, not reports of executed tests. Unless stated otherwise, assume valid accessible storage, callable dependencies, no concurrent mutation, and dependencies that return normally.

1. **Lower accepted rate boundary.**  
   A request with rate 8000, width 8, and count 1 passes validation. It writes those three values, performs the three calls in order, performs the projection and option writes between the second and third calls, and returns 1.

2. **Upper accepted rate boundary.**  
   Rate 48000 with width 16 and count 2 passes. Rate 48001 returns 0 without object accesses or dependent calls.

3. **Lower rejected rate boundary.**  
   Rate 7999 returns 0 without writing the current-rate field. A 32-bit all-ones rate, including when presented as signed −1, is also rejected.

4. **No gap between rate subranges.**  
   Rates 40767 and 40768 both pass the rate check. Neither is a special rejection point.

5. **Zero-width normalization.**  
   Rate 44100, width 0, and count 2 store width 16. Comparison against the comparison-width field uses 16, not 0.

6. **Rejected width leaves a partial update.**  
   Rate 44100, width 24, and count 2 return 0 after writing 44100 to `+0x2A178`. The function does not directly write the width, count, projection, or option fields and makes no dependent call.

7. **Rejected count leaves two updates.**  
   Rate 44100, width 0, and count 3 return 0 after storing rate 44100 and width 16. The current-count and option fields are not directly written.

8. **Matching configuration still performs work.**  
   If the comparison fields equal rate 44100, width 16, and count 2, a request for rate 44100, width 0, and count 2 supplies flag 0 to the indirect operation. All three calls still occur.

9. **Rate mismatch short-circuits comparison reads.**  
   If the comparison rate differs from the accepted requested rate, the difference flag is 1 without reading comparison width or count for that comparison. Those fields are nevertheless read later for projection if execution reaches that stage.

10. **Post-call field values govern later operations.**  
    If the indirect operation changes the current-rate field, F-eae52a1fb753 receives the changed field value. If F-eae52a1fb753 changes the current-width field, that changed value is copied to `+0x18`.

11. **Option is an uninterpreted byte.**  
    An option byte of `0xFF` is written as `0xFF`, not normalized to 1, after the projection writes and before F-ad37e9c0edc9.
