# F-371eb9c456b3

## Purpose

F-371eb9c456b3 obtains a context and performs one of two operations selected by a signed request:

- For a positive request, it repeatedly consumes a selected entry from a context-associated table and writes each consumed entry’s index to successive output positions.
- For a negative request, it conditionally copies a shared 32-bit value into the context’s first word.
- For a zero request, it performs the context lookup but does not itself access context fields or output storage afterward.

The entry-consumption interpretation is inferred intent. The established behavior is the ordered sequence of dependency calls, field accesses, address calculations, and writes described below. In particular, the function does not establish that an entry exists before consuming it.

## Interface

**Inputs**

1. **Request:** a signed 32-bit integer.
   - Positive values specify the exact number of iterations attempted.
   - Zero selects no iterations.
   - Every negative value selects the same conditional context-update path. Its magnitude has no effect.

2. **Output pointer:** a pointer to successive 32-bit integer locations.
   - A successfully completed positive-request iteration writes one index.
   - The output pointer advances by four bytes after each write.
   - The function does not access this pointer when the context lookup returns null or when the request is nonpositive.
   - No null, capacity, alignment, or overlap checks are visible.

**Return**

There is no explicit return value, status code, or completed-item count.

**Context layout**

The lookup dependency returns either null or a pointer to a context containing at least these relevant locations:

| Byte offset from context | Width | Behavioral role |
|---|---:|---|
| 0 | 32 bits | Destination of the conditional negative-request update |
| 2760 / 0xAC8 | 32 bits in the supplied representation | Table-base address field |
| 2764 / 0xACC | 32 bits | Remaining-entry or availability field |
| 2772 / 0xAD4 | 32 bits | Current selected index or link field |

The role names describe use, not independently established data types or invariants. The source treats the availability field and selected index as signed integers when loading them for arithmetic. It also writes an unsigned 32-bit result into the selected-index field.

Table entries occupy four bytes. The address of a selected entry is formed from the current table-base value plus four times a previously captured selected index.

**Shared state**

The negative-request path reads a shared 32-bit value. Its initialization, ownership, synchronization, and meaning are unknown.

**Preconditions for defined, successful completion**

- A non-null context must provide readable and writable storage for the fields actually accessed.
- Every table address actually used must be valid for the applicable dependency call or 32-bit memory access.
- A positive request requires sufficient writable output storage.
- The dependencies must return normally for execution to continue.
- Address arithmetic and signed arithmetic must remain valid under the intended execution model.

These are caller/environment obligations, not validations performed by this function.

## Behavior

### Context lookup and dispatch

The first operation is a call to F-7fba0909c452 without explicit arguments.

If it returns null, the function returns immediately. It does not inspect the request to select a branch, access output storage, or directly read or write the described context fields or shared value. The lookup dependency may itself have side effects; those are not constrained here.

For a non-null result:

- A negative request selects the conditional shared-value update.
- A zero request returns without entering the iteration body.
- A positive request executes the iteration body exactly as many times as requested, provided all calls and memory operations complete normally.

There is no visible upper bound other than the signed 32-bit request range, and no early-success or empty-table exit inside the positive loop.

### Positive-request iteration

Each iteration proceeds in the following order. The context pointer obtained from the initial lookup remains the pointer used throughout; the function does not repeat the lookup.

1. **Locate the table-base field.**  
   The function uses the address of the context field at byte offset 2760. This field address, rather than the table-base value stored there, is retained for subsequent accesses and is the argument passed to the refill-like dependency.

2. **Check availability.**  
   The function reads the 32-bit field at byte offset 2764 and compares it with zero.

   If it is exactly zero, the function calls F-b018ee7e1687 with:
   - the address of the table-base field; and
   - a second argument whose value is zero.

   A nonzero availability value, including a negative value, skips this call.

   The function does not check availability again after the call. It continues even if that dependency leaves the availability field at zero or makes other relevant state invalid.

3. **Capture the selected index.**  
   After any refill-like call returns, the function reads the field at byte offset 2772 into a signed 32-bit temporary value. That captured index is used for the remainder of this iteration and is eventually written to the output.

   Later dependency mutations of the selected-index field do not replace this captured index.

4. **Call the entry predicate.**  
   The function loads the table-base field and forms an entry address using that base plus four times the captured index. It passes the address to F-a7b33ca08f0c.

   No direct table-entry read by this function precedes this call. What the dependency reads or writes is unknown.

5. **Determine the replacement selected-index value.**
   - If the predicate returns zero, the function loads the table-base field again, reads a 32-bit unsigned word from the entry selected by the captured index, and logically shifts that word right by one bit.
   - If the predicate returns nonzero, the replacement value is the 32-bit pattern 0xFFFFFFFF. This branch does not perform that direct table-entry read.

   The logical shift inserts a zero at the high end. Its result is therefore between 0 and 0x7FFFFFFF, inclusive.

   The table-base field is reloaded after the predicate returns on the zero-result branch. Consequently, the directly read word need not be at the same address passed to the predicate if that dependency changed the base.

6. **Write the replacement selected index.**  
   The function writes the replacement 32-bit value to the context field at byte offset 2772.

   The 0xFFFFFFFF result has the bit pattern conventionally interpreted as signed −1 in a two’s-complement 32-bit representation. Its intended sentinel meaning is not established.

7. **Decrement current availability.**  
   The function reads the availability field as it exists at this point, subtracts one, and writes the result back.

   This is not necessarily a decrement of the value observed before the refill-like or predicate call. Either dependency may have changed the field.

8. **Clear the selected table entry.**  
   The function reloads the table-base field, forms an address using the same captured index, and writes a four-byte zero there.

   This clear happens after both the selected-index update and the availability decrement. It may target a different address from either earlier table access if the base changed.

9. **Write the output index.**  
   The function writes the captured index to the current output position and advances the output pointer by four bytes.

   The emitted value is the index captured before the predicate call, not the replacement selected-index value and not the table word.

The request count then decreases by one. Positive-loop count arithmetic reaches zero without needing to cross the signed lower bound.

### Negative-request update

For a negative request, the function reads the shared 32-bit value.

- If that read is zero, it returns without accessing the context’s first word.
- If it is nonzero, the function reads the context’s first 32-bit word.
  - If the context word is nonzero, it returns without writing it.
  - If the context word is zero, it reads the shared value again and writes that value to the context word.

The tested shared value and copied shared value are separate source-level reads. If the shared state can change between them, the copied value need not equal the first observed value and may be zero. The source provides no synchronization or atomicity guarantee.

This path does not directly access the table-related context fields or output storage.

## Side effects

For each normally completed positive iteration, the function directly performs:

- one selected-index-field write;
- one availability-field write;
- one four-byte table-entry clear; and
- one four-byte output write.

The order is significant: selected index, availability, table clear, then output.

The negative path performs at most one direct context write. The zero-request and null-context paths perform no direct writes after lookup.

Dependency effects are additional and unknown. In particular:

- F-b018ee7e1687 receives a pointer into the context and may alter the table base or adjacent state.
- F-a7b33ca08f0c receives an entry address; neither a read-only effect nor preservation of context or shared state is established.
- F-7fba0909c452 may affect state even when it returns null.

No direct allocation, deallocation, ownership transfer, or explicit resource release is visible. That absence does not constrain resource behavior inside dependencies. If a dependency invalidates storage subsequently used here, the function has no visible recovery mechanism.

Output overlap is not rejected. If an output location aliases a context field or table entry, the final write of that iteration can overwrite an earlier update or clear, affecting subsequent iterations. Likewise, overlap among context fields and table storage can make earlier writes affect later address calculations. Ordinary queue-like behavior therefore requires suitable non-overlap assumptions; the function does not enforce them.

There is no visible rollback. A failure during a late operation can leave earlier state changes in place. For example, a failed output write may occur after the selected index, availability, and table entry have already been modified. The exact failure mechanism is outside the supplied evidence.

## Acceptance examples

These are conditional specification examples, not executed tests. Unless stated otherwise, assume valid non-overlapping storage, valid arithmetic, dependencies that return normally, and no unmentioned mutations.

1. **Null context with any request.**  
   If F-7fba0909c452 returns null, no output value is written and neither other dependency is called. This also applies to negative requests.

2. **Zero request with a non-null context.**  
   The lookup occurs. No availability check, table access, shared-value access, or output access follows.

3. **One ordinary consumption.**  
   Suppose availability is 2, the selected index is 3, the selected entry contains unsigned value 18, and F-a7b33ca08f0c returns zero without modifying state. For request 1:
   - F-b018ee7e1687 is not called.
   - The predicate receives the address at table base plus 12 bytes.
   - The replacement selected index is 9.
   - Availability becomes 1.
   - Entry 3 is cleared.
   - The first output word becomes 3.

4. **Unsigned shift boundary.**  
   If the selected entry contains 0xFFFFFFFF and the predicate returns zero, the replacement selected-index bits are 0x7FFFFFFF, not 0xFFFFFFFF. The consumed entry is still cleared and the captured index is still output.

5. **Nonzero predicate result.**  
   If the predicate returns any nonzero value, the selected-index field receives 0xFFFFFFFF. No direct read of the entry word is needed for deriving that value. The clear and output still occur.

6. **Zero availability followed by refill.**  
   If initial availability is zero and F-b018ee7e1687 changes it to 4 and selects index 6, index 6 is captured after that call. With no later availability mutation, the iteration writes availability 3 and outputs 6.

7. **Refill does not restore availability.**  
   If availability remains zero after the refill-like call and all later operations are otherwise valid, the function still consumes an entry and writes availability −1. There is no empty-state rejection.

8. **Predicate changes the table base.**  
   If the predicate receives an address in table A, changes the context base to table B, and returns zero, the direct word read and subsequent clear use table B at the captured index. The address passed into the predicate is not retained as the clear destination.

9. **Negative-request conditions.**  
   With a non-null context:
   - A zero shared value leaves the first context word untouched.
   - A nonzero first context word is not replaced.
   - A zero first context word and an unchanged shared value of 7 result in that word becoming 7.
   - Output storage is untouched in all these cases.

10. **Output aliases the selected-index field.**  
    If a valid output location is that field, the final output write replaces the newly derived selected index with the consumed index. A later iteration reads this overwritten state.

## Uncertainties

**Inferred intent**

The structure resembles consumption from a linked free-entry pool or table: an index selects a word, shifting extracts a successor, a counter decreases, and the consumed word is cleared. Neither this interpretation nor a specific encoding is established.

**Documented-only unknowns**

- The meaning of the low bit discarded by the shift.
- Whether 0xFFFFFFFF is a deliberate end marker.
- Valid index range, table capacity, and any invariant relating availability to reachable entries.
- Whether negative selected indices are ever valid.
- Dependency behavior, including mutation, allocation, release, and synchronization.
- Whether callers intentionally permit aliasing.
- The meaning and lifecycle of the shared value.
- Observable behavior after invalid access, dependency failure, or arithmetic overflow.

The displayed representation uses four-byte integer fields and a four-byte table-base field, consistent with a 32-bit address model. A complete ABI, byte order, alignment policy, and integer-overflow model are not independently established.

The index-times-four expression is formed using signed integer arithmetic in the supplied representation. It is not justified to promise mathematical addressing for every 32-bit index or to assume wraparound. Similarly, decrementing the minimum signed availability value has no established portable result. These boundary cases require external execution-model evidence.

The access ordering above describes the supplied static representation. It does not establish machine-level atomicity, memory barriers, or valid concurrent access to ordinary shared storage.

## Evidence
