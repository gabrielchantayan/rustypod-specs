# F-d9b87d7c419b

## Purpose

F-d9b87d7c419b incrementally constructs a linked destination hierarchy from a source hierarchy. For each visited source node, it obtains a destination address from F-3c2615c72aa2, establishes links, transfers one metadata byte, and recursively processes the source node’s children.

**Established static behavior:** construction proceeds depth-first, with observable writes before completion. Empty input clears the supplied attachment’s next-sibling field and returns null. No validation, rollback, release, or cycle detection is visible.

**Inferred intent:** the operation resembles copying a tree or forest with an associated region beginning 16 bytes into each source node. The associated region’s meaning and the dependency’s treatment of it are unknown.

A completed copy with preserved metadata and links requires more than valid, distinct destination storage. It also requires relevant source fields to remain stable until read and dependency calls—including calls made during recursive construction—not to corrupt destination fields needed in the final result. Neither preservation property is established by this function.

## Interface

The function accepts three arguments:

1. **Construction context:** a 32-bit value forwarded unchanged to F-3c2615c72aa2 for each visited node, including descendants. This function does not otherwise interpret it.
2. **Source head:** a nullable node address identifying the first source sibling.
3. **Destination attachment:** an address whose next-sibling field will be overwritten. It is required even when the source head is null.

The relevant node layout is:

| Byte offset | Quantity | Observed use |
|---|---|---|
| `+0` | One byte | Source metadata read; destination metadata write |
| `+4` | Address-valued link | Destination predecessor or attachment write |
| `+8` | Address-valued link | Source next-sibling read; destination next-sibling write |
| `+12` | 32-bit address-valued field | Source child-head read; destination child-head write |

The recovered operations are consistent with four-byte address fields: the child-head transfer and terminal next-sibling clear explicitly use 32-bit quantities. This is not evidence for an eight-byte-pointer layout. Complete ABI details, alignment, and byte order remain **documented_only**.

The metadata transfer is exactly one byte; signedness does not change the transferred bit pattern. Other bytes, the associated region’s size, and the complete node extent are not specified.

### Output

The return value is an address, or null for an empty source.

Under the ordinary-copy conditions below, it identifies the first constructed destination sibling. The attachment itself is not part of the returned chain.

There is no separate status output. A null dependency result is not handled as a recoverable construction failure.

## Behavior

### Empty source

For a null source head:

- No F-3c2615c72aa2 call occurs.
- No source-node fields are read.
- A 32-bit zero is written to the attachment’s field at `+8`.
- The function returns null.

The attachment is therefore not optional for empty input. Any previously linked chain is overwritten at the attachment; this function does not traverse or release that chain.

### Per-node observable ordering

For each nonnull source sibling, the established order is:

1. The source-associated address at `+16` is supplied, together with the construction context, to F-3c2615c72aa2.
2. After that call returns, its returned address is written into the current attachment’s next-sibling field.
3. The current attachment address is written into the returned destination’s field at `+4`.
4. The tracked return address may be updated through the address comparison described below.
5. The source metadata byte is read and written to the destination metadata byte.
6. The source child-head field is read.
7. F-d9b87d7c419b is invoked recursively with that child head, the same context, and the new destination as attachment.
8. After recursion returns, its result is written into the destination child-head field.
9. That destination becomes the attachment for the next sibling.
10. The current source node’s next-sibling field is read to determine whether and where traversal continues.

When traversal reaches null, the current attachment’s next-sibling field receives a 32-bit zero, and the tracked address is returned.

This ordering does not describe a source snapshot. Metadata and child-head values are read after the dependency call. The next-sibling value is read after all recursive work for that node. Valid changes made before those reads can change metadata, child traversal, or subsequent sibling traversal.

Likewise, a write performed earlier by this function is not necessarily its final value if a later dependency call changes it. The function does not perform a final restoration pass.

### Recursive linkage and temporary states

Each recursive child construction uses the new destination node as its attachment.

For nonempty children, the parent destination’s next-sibling field initially receives the first child destination address. The first child’s predecessor field receives the parent destination address. Subsequent children receive their preceding child’s address in that field.

After recursion returns, its returned address is stored separately in the parent destination’s child-head field.

The parent’s temporary next-sibling link is later replaced by the enclosing sibling traversal:

- If a following sibling is processed, it becomes the following destination sibling’s address.
- If no following sibling is processed, it is cleared at termination.

For an empty child chain, recursion clears the destination’s next-sibling field and returns null. The caller subsequently writes null into that destination’s child-head field.

Consequently, intermediate storage does not necessarily satisfy the final hierarchy’s link relationships. No atomic publication or observer-safe intermediate representation is established.

### Final structure, conditionally

Under all ordinary-copy conditions—including source stability and dependency noninterference—the completed structure has these properties:

- The supplied attachment links to the first destination sibling, or null for empty input.
- Each destination metadata byte equals its corresponding source byte.
- The first destination sibling’s `+4` field identifies the supplied attachment.
- Each later destination sibling’s `+4` field identifies the preceding destination sibling.
- Each destination child-head identifies the recursively constructed child chain, or null.
- Each sibling chain ends with a null next-sibling field.
- The return value identifies the first destination sibling.

The `+4` field is therefore not uniformly a parent pointer.

Without dependency noninterference, the function’s ordered writes remain established, but these final-state claims do not. For example, the dependency call for a second sibling could overwrite the first destination’s metadata, predecessor, or child-head. Those fields are not restored merely because construction of the second sibling succeeds.

### Return-address tracking

The tracked return address begins as the source-head address. During each iteration, it is replaced by the current dependency result if it equals the current source address.

With distinct, disjoint source and destination storage, this selects the first destination and leaves it selected.

The comparison is not a separate first-iteration indicator. If a returned address equals a source address visited later, the tracked return value can change again. Aliasing can also change pending source reads through destination writes. The ordinary first-destination return guarantee does not extend to such cases.

### Arithmetic and termination

Visible address calculations use fixed byte offsets. No payload-length, allocation-size, or node-count arithmetic is present.

No bounds check or defined handling of invalid address arithmetic is visible. Fixed offsets do not establish that the referenced bytes belong to valid objects. Complete address-width overflow behavior remains **documented_only**.

## Side effects

### Direct memory changes

The function writes:

- The supplied attachment’s next-sibling field.
- Each dependency result’s predecessor field.
- Each dependency result’s metadata byte.
- Next-sibling fields during recursive child attachment and sibling construction.
- Each dependency result’s child-head field after recursion returns.
- A terminal zero into the last attachment’s next-sibling field for every invocation.

It does not directly modify memory designated as source merely because it is source. Source storage may nevertheless change through aliasing or dependency effects.

Previously linked structures are overwritten without a visible detachment or release protocol.

### Ownership and dependency effects

Destination addresses originate from F-3c2615c72aa2. This does not establish allocation, freshness, ownership transfer, or payload copying.

This function performs no explicit release of source nodes, destination nodes, or displaced chains. Ownership and release responsibilities are **documented_only**.

The source-associated address is passed to the dependency. The dependency’s access extent, retention of that address, and lifetime requirements are unknown.

No preservation of globals, source memory, attachment storage, or earlier destination fields may be assumed from this body. Final-copy guarantees explicitly require the relevant preservation; the dependency’s actual compliance remains unresolved.

### Failure and partial construction

The dependency result is used without a null check. For a null result, the function first stores null into the current attachment’s next-sibling field, then attempts a predecessor write at offset `+4` relative to the null result. Platform behavior for that access is not specified here.

Invalid source addresses, invalid destination storage, dependency failure, or interrupted recursion can leave partial changes. There is no visible rollback, cleanup, or conversion to an error result.

- This function performs no release of the displaced chain.

- The attachment links to that destination.

- Dependency calls occur for the first source and then the second.
- The attachment links to the first destination.
- The first destination links to the second; the second links to null.

- Child construction temporarily links the first destination’s next-sibling field to the child.
- The child’s predecessor identifies that first destination.
- The first destination’s child-head receives the child destination after recursion.
- Its next-sibling field is subsequently replaced with the following sibling’s destination address.
- Later dependency calls preserve the completed child relationships and metadata.

The call sequence depends on the relevant source links retaining those values until read.

### Dependency changes source metadata

This establishes the transfer at that point. Its persistence until return additionally requires later noninterference.

### Pending traversal is changed

The same timing principle applies to the child-head field read after the node’s dependency call.

### Null dependency result
