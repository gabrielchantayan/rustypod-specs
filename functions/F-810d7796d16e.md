# F-810d7796d16e

## Purpose

F-810d7796d16e selects two values through either a fallback path or an object-mediated path, supplies them and a captured global value to F-5710a8628cba, stores that dependency’s 32-bit result in the input record, and then invokes F-92bea7c30bd6 with the record.

A significant distinction between the paths is the first argument passed to F-5710a8628cba:

- On the fallback path, it is the current 32-bit value at record offset `0x38`.
- On the object-mediated path, it is the exact nonzero 32-bit result of an indirect dependency selected through object-table offset `0x7C`.

The nonzero result is not merely a Boolean selection flag. Its value is forwarded.

If all calls and memory accesses return normally, F-810d7796d16e returns the 32-bit value `1`. This return does not independently establish that the dependencies succeeded or that the stored result represents success.

The intended domain meaning of the record, lookup selector, global value, indirect operations, and stored result is unknown.

## Interface

The function takes one argument: an address identifying a mutable record in the represented 32-bit address model.

The supplied material shows no null check, size check, alignment check, or explicit validation of this address. The caller must provide storage suitable for the accesses reached during execution. Those requirements also extend to object and dispatch-table storage used on the object-mediated path.

| `0x44` | 32 bits | Argument to the indirect dependency at object-table offset `0x7C` |
| `0xBC` | 32 bits | Fallback third argument to F-5710a8628cba, or argument to the indirect dependency at object-table offset `0x78` |

Offset `0x190` is decimal `400`; both designate the same destination.

These offsets establish accesses, not a complete record definition. They do not establish the meanings of intervening bytes, allocation boundaries, or ownership.

### Output

On normal completion:

- The direct return is the 32-bit value `1`.
- A 32-bit result from F-5710a8628cba has been written to record offset `0x190`.
- F-92bea7c30bd6 has subsequently been invoked with the original record address.

The value at offset `0x190` when the function finally returns is not necessarily the value written by this function: F-92bea7c30bd6 executes after the write, and its effects are unknown.

No payload arithmetic, narrowing conversion, saturation, or range validation is visible. The arithmetic shown is address formation through fixed byte offsets. Behavior for invalid addresses, address overflow, unsuitable alignment, or inaccessible storage is not defined by the supplied material.

## Behavior

### Lookup and global capture

The function first reads the 32-bit field at record offset `0x38` and calls F-682adfd5a561 with:

1. That field value.
2. The fixed selector `0x2B00`.

The return is interpreted as an object address and may be null.

After F-682adfd5a561 returns, the function captures a 32-bit global value. This captured value later becomes the second argument to F-5710a8628cba.

The capture occurs after lookup, not before it. Consequently, a normally returning lookup that changes the global can affect the captured value. Conversely, changes to that global during subsequent indirect calls do not replace the captured argument value.

The global’s meaning and initialization requirements are unknown.

### Null lookup result

If lookup returns null, neither indirect object operation is invoked.

The fallback path then reads:

1. The 32-bit field at record offset `0x38`.
2. The 32-bit field at record offset `0xBC`.

Those values become, respectively, the first and third arguments to F-5710a8628cba.

The read at `0x38` is a new read. It is not a guaranteed reuse of the value supplied to lookup. If F-682adfd5a561 changes the field through an alias or another mechanism, the fallback can observe the changed value.

### Non-null lookup result

For a non-null object address, the function uses the 32-bit address at object offset zero as a dispatch-table address. It selects an indirect dependency through byte offset `0x7C` in that table.

That dependency receives:

1. The object address returned by lookup.
2. The 32-bit value read from record offset `0x44`.

Its 32-bit result determines the next path.

The supplied representation does not establish a complete ordering between dispatch-address reads and the record-field read within this indirect call expression. All are required to perform the call, but finer-grained read ordering is documented_only.

### Zero result from the first indirect dependency

If the indirect dependency at table offset `0x7C` returns zero, the function takes the same fallback path used for a null lookup result.

In particular:

- The indirect dependency at table offset `0x78` is not invoked.
- Record offset `0x38` is reread after the first indirect call returns.
- Record offset `0xBC` is then read for the fallback third argument.
- The zero indirect result is not forwarded as the first argument to F-5710a8628cba. The freshly read field at `0x38` is used instead.

Any changes made by the first indirect dependency to these record fields can therefore affect the fallback arguments. No preservation guarantee is established for that dependency.

### Nonzero result from the first indirect dependency

If the indirect dependency at table offset `0x7C` returns nonzero, that exact 32-bit result is retained as the first argument for F-5710a8628cba.

The function then selects another indirect dependency through byte offset `0x78` of the object’s dispatch table. It passes:

1. The original object address returned by lookup.
2. The 32-bit value read from record offset `0xBC`.

The second indirect dependency’s 32-bit return becomes the third argument to F-5710a8628cba.

The object’s dispatch-table address is obtained again for this second indirect operation. The visible behavior does not require the table address to remain equal to the one used for the first indirect call. If the first indirect dependency changes the table pointer and leaves a valid object, the later dispatch can use the changed table.

The field at `0xBC` is read after the first indirect call returns. It is not captured before that call.

The nonzero result retained from the first indirect operation is not replaced by the second operation’s result. The two results occupy different argument positions in the subsequent call.

As with the first indirect call, the precise ordering of the dispatch-related reads relative to the argument-field read is not established by the supplied representation.

### Common completion path

Both paths converge on a call to F-5710a8628cba with three 32-bit arguments:

| Argument position | Fallback path | Object-mediated path |
|---|---|---|
| First | Current field at record offset `0x38` | Exact nonzero result from the indirect dependency at table offset `0x7C` |
| Second | Captured global value | Captured global value |
| Third | Current field at record offset `0xBC` | Result from the indirect dependency at table offset `0x78` |

After this dependency returns normally, its 32-bit result is written to record offset `0x190`.

The function then invokes F-92bea7c30bd6 with the original record address. The result store precedes that invocation, so the written field is available for that dependency to observe, subject to any other memory effects outside this function’s established behavior.

No return value from F-92bea7c30bd6 is used. If it returns normally, F-810d7796d16e returns `1`.

- Invokes the dependencies in the order described above.
- Writes one 32-bit result to record offset `0x190`.

### Dependency-mediated effects

## Acceptance examples

These examples are conditional consequences of the static evidence, not executed tests. They assume valid storage and normal return from every invoked dependency.

### Null lookup with changed fallback fields

Suppose lookup returns null after changing the field at `0x38` from `0x11111111` to `0x22222222`, while the fallback read at `0xBC` yields `0x33333333`. Suppose the global capture yields `0x44444444`.

Required behavior:

- Neither indirect dependency is called.
- F-5710a8628cba receives `0x22222222`, `0x44444444`, and `0x33333333`, in that order.
- Its result is stored at `0x190`.
- F-92bea7c30bd6 is then called with the record.
- Normal completion returns `1`.

### Non-null lookup followed by zero

Suppose lookup returns a valid object. The dependency selected at table offset `0x7C` returns zero after changing the fields at `0x38` and `0xBC`.

Required behavior:

- The dependency selected at table offset `0x78` is not called.
- The changed fallback fields are read after the zero result.
- The first argument to F-5710a8628cba comes from `0x38`, not from the zero result.

### Non-Boolean nonzero result

Suppose the first indirect dependency returns `0x80000005`, and the second returns `0x12345678`.

Required behavior:

- The object-mediated path is selected.
- F-5710a8628cba receives `0x80000005` as its first argument and `0x12345678` as its third.
- The first argument is not normalized to `1` and is not replaced with the field at `0x38`.

### Global capture boundary

Suppose lookup changes the global to `0x01020304`, which is captured afterward. The first indirect dependency later changes that global to `0xA0B0C0D0`.

Required behavior:

- The second argument to F-5710a8628cba is `0x01020304`.
- This function does not reread the global to obtain that argument after the indirect calls.

### Store followed by further mutation

Suppose F-5710a8628cba returns `0x76543210`, and F-92bea7c30bd6 subsequently changes the field at `0x190`.

Required behavior:

- This function writes `0x76543210` before invoking F-92bea7c30bd6.
- The later change is not undone by a second visible store.
- If execution returns normally, the direct return remains `1`.
