# F-52692d9f9dad

## Purpose

F-52692d9f9dad performs two comparison-driven searches through a linked structure, initializes traversal state from their saved candidates, counts advancement calls, and invokes a final operation with two boundary values.

**Established behavior:** the returned count is the number of calls made to F-017ac946138e during a normally completing invocation. Neither search directly increments that count. Counting stops only when F-ca7a1f20809e returns exactly 1.

**Inferred intent:** the operation resembles locating and processing an interval in an ordered container. The supplied evidence does not establish lower-bound, upper-bound, duplicate-counting, or removal semantics. In particular, candidate updates save a selected child-link value, not the node on which the comparison was performed.

## Behavior

### First search

Initialization has the following read order:

1. Read the structure-reference field at object offset 0x10.
2. Through that reference, read the starting node at offset 0x04.
3. Separately reread the object’s structure-reference field to initialize the first saved candidate.

The two structure-reference reads are distinct in the supplied representation. If their results differ, the starting node and initial saved candidate need not come from the same structure.

For each nonzero current node, the function clears traversal-state word 0 and calls F-4a197a0807f0 with:

1. The object address plus 0x19.
2. The current node address plus 0x10.
3. The search operand.

Only zero versus nonzero affects this search:

| Comparison result | Selected link | Candidate effect |
|---|---|---|
| Zero | Current node + 0x08 | Save the selected link value as the first candidate |
| Nonzero | Current node + 0x0c | Leave the first candidate unchanged |

The selected link becomes the next current node. Its field is read after the comparator returns; neither child link is prefetched by the visible body.

Consequently, the first candidate can be:

- The structure reference obtained by the separate initialization read.
- A link value obtained from a visited node’s offset-0x08 field.
- Zero, including when a zero comparison selects a zero link and ends the search.

The compared node itself is not saved by the candidate-update branch.

### Second search

After the first search, the function reacquires its starting position:

1. Reread the structure reference at object offset 0x10.
2. Read the starting-node field at that reference plus 0x04.
3. Separately reread the object’s structure-reference field to initialize the second saved candidate.

There is no snapshot shared between the searches. The second search can observe a different structure reference, starting node, or link contents.

The first candidate is staged in traversal-state word 2 before this search. At each second-search condition check, including the terminating check, that staged value is copied into word 0. For a nonzero current node, word 0 is then cleared before the comparator call.

F-4a197a0807f0 receives:

1. The object address plus 0x19.
2. The search operand.
3. The current node address plus 0x10.

The comparison operands are reversed relative to the first search. Its branch rules are:

| Comparison result | Selected link | Candidate effect |
|---|---|---|
| Zero | Current node + 0x0c | Leave the second candidate unchanged |
| Nonzero | Current node + 0x08 | Save the selected link value as the second candidate |

Again, the selected link is read after the comparator returns and becomes the next current node.

The second search does not replace the first saved candidate. The second candidate may remain its initialization reference or become an offset-0x08 link value, including zero.

### State preparation

At the terminating second-search condition check, traversal-state word 0 contains the first candidate. The function then:

1. Copies the staged first candidate into word 3.
2. Initializes the count to zero.
3. Clears word 2.
4. Clears word 1.
5. Stores the second candidate in the separate endpoint slot.

Immediately before the first counting comparison, the state is:

| Word | Byte offset | Initial value |
|---|---:|---|
| 0 | 0x00 | First candidate |
| 1 | 0x04 | Zero |
| 2 | 0x08 | Zero |
| 3 | 0x0c | First candidate |

The endpoint slot initially contains the second candidate.

The earlier temporary writes to words 0 and 2 are therefore superseded before counting. The search comparator is not explicitly given the address of this scratch state.

The semantic roles of these four words are unknown. Their contents do not establish a conventional single-pointer iterator layout.

### Counting and advancement

F-ca7a1f20809e is called with:

- The address of the 16-byte traversal state.
- The address of the separate four-byte endpoint slot.

Its result controls the loop as follows:

- **Exactly 1:** stop counting immediately.
- **Any other value:** increment the count, call F-017ac946138e with the traversal-state address, and perform another comparison.

Thus 0, 2, and negative results all continue the loop. A nonzero result is not sufficient to stop it, and no apparent error value receives special treatment.

On any normally terminating execution with defined arithmetic:

- The count equals the number of advancement calls.
- The comparison dependency is called once more than the advancement dependency.
- No advancement follows the terminating comparison.
- The count increment precedes the corresponding advancement call.

There is no explicit iteration limit.

The comparison dependency receives writable addresses for both the state and endpoint. Its behavior is not established as read-only. The advancement dependency receives the state address, but the visible call does not establish which state words it changes or whether it has other effects.

### Final operation and return

After a comparison returns exactly 1, the function performs these operations in order:

1. Copy the current endpoint-slot value into a separate four-byte boundary slot.
2. Copy the current traversal-state word 3 into another four-byte boundary slot.
3. Call F-a601ce3cadf5 with:
   - The address of a four-byte temporary area.
   - The original object address.
   - The address of the copy from traversal-state word 3.
   - The address of the copy from the endpoint slot.
4. Return the count after that call returns.

The four-byte temporary area is not explicitly initialized before the call. The evidence does not establish that the dependency treats it as output-only.

Both boundary values are copied after the terminating comparison returns. They therefore incorporate changes made to those locations during counting, including changes made by the terminating comparison itself. The original candidates are not restored before the final call.

F-a601ce3cadf5’s return value is ignored. The temporary area and boundary-copy slots are not subsequently read by this function.

## Side effects

### Direct effects

The visible body directly:

- Reads the object’s structure-reference field repeatedly.
- Reads starting-node fields and selected node links.
- Writes invocation-local scratch storage.
- Updates its local count.
- Calls the dependencies in the specified order.

No direct write to the supplied object, referenced structure, or visited nodes is visible.

That observation does not establish overall read-only behavior. The comparator receives addresses inside the object and visited nodes, and the final dependency receives the original object address.

### Mutation visibility

Selected child fields are read after comparator calls. A change made to a selected field during its comparator call can therefore affect the next node and, on a candidate-update branch, the saved candidate.

The second search reacquires the structure reference and starting node. It is not constrained to see the values used by the first search.

The state and endpoint supplied during counting are writable. Preserving the four-word state alone does not preserve the endpoint. Likewise, preserving the endpoint alone does not preserve state word 3. Final boundaries depend on both locations’ values after the terminating comparison.

No dependency is established to preserve globals, object fields, links, or dependency-maintained state.

Scratch addresses refer to storage valid during this invocation, not persistent storage available after return. The supplied evidence does not establish whether dependencies retain these addresses or whether such retention would be safe.

## Acceptance examples

The examples below are conditional on valid accesses, defined arithmetic, normally returning dependencies, and the stated terminating behavior. Unmentioned link values remain stable.

### Empty starting structure with both scratch objects preserved

Suppose every structure-reference read returns the same nonzero reference H, and both freshly read starting-node fields are zero.

Neither search calls F-4a197a0807f0. Counting begins with:

- Four-word state: H, zero, zero, H.
- Separate endpoint slot: H.

If the first F-ca7a1f20809e call returns 1 **without modifying either the four-word state or the endpoint slot**, no advancement occurs. The final dependency receives boundary copies H and H, and the function returns zero after that dependency returns.

The evidence does not require F-ca7a1f20809e to return 1 for these inputs; that result is a condition of this example.

### Empty starting structure with endpoint mutation

Use the same empty-search conditions, but let the first counting comparison preserve the four-word state, change the endpoint slot to Y, and return 1.

The final dependency receives a first boundary containing H and a second boundary containing Y. The result is still zero after the final call returns.

Preservation of the array alone is insufficient to conclude that both boundaries are H.

### First search saves a zero child

Suppose the first search begins at a nonzero node, the comparison returns zero, and that node’s offset-0x08 link is zero.

The selected link becomes both the next node and first candidate. The search terminates with candidate zero, rather than preserving the compared node. State words 0 and 3 consequently start counting at zero.

### Second search saves a zero child

Suppose the second search begins at a nonzero node, the comparison returns a nonzero value, and the offset-0x08 link is zero.

The second candidate becomes zero and the search terminates. The endpoint initially contains zero rather than its initialization structure reference.

### Nonzero counting results can continue

Suppose successive F-ca7a1f20809e results are 2, 0, and 1.

There are two count increments and two advancement calls. The third comparison stops counting without another advancement. After the final dependency returns, the function returns 2.

### Comparator changes a selected link

Suppose a comparator changes the child field selected by its eventual return value.

The traversal uses the value read from that field after the call. On a candidate-update branch, that same value also becomes the saved candidate. A pre-call field value does not determine either outcome.

### Terminating comparison changes both boundaries

Suppose the terminating F-ca7a1f20809e call changes state word 3 to X and the endpoint slot to Y, then returns 1.

No further advancement occurs. The final dependency receives addresses of copies containing X and Y, in that order. Those copies are not taken before the terminating comparison.
