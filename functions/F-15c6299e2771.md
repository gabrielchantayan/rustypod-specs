# F-15c6299e2771

## Purpose

F-15c6299e2771 updates two result blocks within a caller-provided destination object. Each block can receive up to sixteen distance values derived from reciprocally linked records. The collected values are sorted in ascending order, and the smallest value is passed through a final conversion dependency.

If a block has no collected values, its conversion input is instead calculated from a shared signed 32-bit field in the destination object.

The function also initializes temporary working storage, conditionally invokes preparation and record-processing dependencies, and invokes a finalization dependency before normal return.

These are statically established operations. The application meaning of the records, distances, shared field, and converted results is not established.

## Interface

The function accepts three arguments:

- **Destination address:** a 32-bit address used to read shared state and write two result blocks.
- **Source address:** a 32-bit address used to read source metadata and passed to preparation dependencies.
- **Opaque argument:** a 32-bit value forwarded unchanged to F-c841521529ba.

There is no explicit return value or status result. Observable results are destination writes and dependency side effects.

### Destination layout

The two result blocks have a stride of `0x188` bytes. Block zero begins at the destination address; block one begins `0x188` bytes later.

| Location | Width | Established use |
|---|---:|---|
| Destination `+0x20` | 32 bits | Shared value copied into temporary scratch state and read when calculating fallback conversion inputs |
| Each block `+0x2c` | 32 bits | Number of collected entries |
| Each block `+0x30` | 12 bytes per entry | Entry array, with at most sixteen entries |
| Each block `+0xf0` | 32 bits | Converted result |

Only the first 32-bit word of a newly collected entry is assigned by this function. Sorting moves all twelve bytes of each entry. Consequently, the remaining eight bytes are not initialized here but can be read and relocated.

The sixteen-entry area occupies offsets `+0x30` through `+0xef` within a block. The converted result immediately follows it.

### Source layout

| Location | Width | Established use |
|---|---:|---|
| Source `+0x64` | 32 bits | Captured before the first dependency call, then stored in the temporary context |
| Source `+0x54` | 32-bit address | References another structure |
| Referenced structure `+0x6e` | Signed 16 bits | Must be strictly positive to enter record preparation |
| Referenced structure `+0x6c` | Address | Passed as the second argument to F-c5c40ffb3792 |

The referenced address is read separately for the positivity check and for the later preparation call. Its stability across intervening calls is not guaranteed by this function.

### Preconditions

The function performs no explicit null, capacity, alignment, or address-range validation. Every access actually reached must be valid in the execution environment.

In particular:

- Both destination counts and both converted-result locations must be writable.
- Destination entry storage used by collection and sorting must support the accesses described below.
- Source fields must be readable when their corresponding paths are reached.
- Record ranges and reciprocal-link targets must be readable wherever traversal examines them.
- Dependencies must support the temporary storage and pointers supplied to them.

These are access requirements, not checks implemented by the function.

## Behavior

### Initial setup and gating

The observable order begins as follows:

1. Read the 32-bit value at source `+0x64`.
2. Invoke an unidentified external initialization operation on a temporary context, with a size argument of `0x74` bytes.
3. Write zero to the count of block zero.
4. Write zero to the count of block one.
5. Store the captured source value at context offset zero.
6. Call F-c841521529ba with the source address and opaque argument.

Record preparation proceeds only if all three gates pass, in this order:

- F-c841521529ba returns nonzero.
- F-1422394ed772, called with the source address, that nonzero return value, and the integer `1`, returns zero.
- The signed 16-bit value at the structure referenced by source `+0x54`, offset `+0x6e`, is greater than zero.

The gates short-circuit. A failed earlier gate prevents later gate calls or reads.

Failure of a gate skips collection but does not skip final result conversion or finalization.

### Temporary preparation state

After the gates pass, the function invokes the same unidentified initialization operation on a separate `0x334`-byte scratch region.

It then explicitly establishes these scratch fields:

| Scratch offset | Width | Assigned value |
|---|---:|---|
| `+0x04` | 32 bits | Source address |
| `+0x08` | 32 bits | `0x00010000` |
| `+0x0c` | 32 bits | `0x00010000` |
| `+0x10` | 32 bits | Zero |
| `+0x14` | 32 bits | Zero |
| `+0x18` | 8 bits | Zero |
| `+0x1c` | 32 bits | Zero |
| `+0x20` | 32 bits | Current value at destination `+0x20` |

It also assigns zero to the 32-bit context field at `+0x68` and stores the scratch-region address at context `+0x70`.

The shared destination value is captured here, after the gate dependencies have run. It is not necessarily the value present at function entry.

F-c5c40ffb3792 is then called with the context address and the address obtained from source `+0x54`, advanced by `0x6c`.

Only a zero return enters the two-block collection loop. A nonzero return skips collection for both blocks.

The meaning and full effects of the initialization operation and preparation dependency are not established. Explicit field assignments above must not be treated as evidence that all other temporary bytes have a particular value.

### Per-block collection

Blocks are attempted in order: block zero, then block one.

For each attempted block:

1. Start a fresh collected-entry count at zero.
2. Call F-ed69baa5ffc4 with the context and the block index narrowed to eight bits.
3. If its return is nonzero, stop the entire collection loop.
4. Otherwise, call F-459d7d5e737c with the same context and narrowed index.
5. Read the record descriptor for that block from the context.
6. Traverse records, collect qualifying distances, sort the collected entries, and finally write the block’s count.

F-459d7d5e737c has no return value used by this function.

The descriptor groups have a `0x1c`-byte stride. Within the context:

| Block | Record count | Record base address |
|---|---|---|
| Zero | `+0x30` | `+0x38` |
| One | `+0x4c` | `+0x54` |

Both fields are interpreted as unsigned 32-bit quantities.

The end address is calculated as the record base plus the count multiplied by `0x30`, using 32-bit arithmetic. Traversal advances by `0x30` bytes while the current address is unsigned-less-than that end address.

This is an address-bound loop, not an independently checked iteration count. Arithmetic wraparound can therefore change or invalidate its apparent range semantics. The function does not detect wraparound.

### Record qualification and distance calculation

For each visited record, the function:

1. Reads a 32-bit linked address at record `+0x10`.
2. Rejects a zero linked address.
3. Otherwise, reads the 32-bit value at linked address `+0x10`.
4. Requires that value to equal the current record address.
5. Requires the current record address to be unsigned-less-than the linked address.

The reciprocal-link read occurs before the address-order test. A linked address must therefore be readable even when the subsequent order test would reject it.

For a qualifying record pair, the function reads signed 16-bit values at offset `+0x02` from the current record and its linked record. Their absolute difference becomes the candidate distance.

Because both operands are signed 16-bit values and subtraction is performed at 32-bit width, the mathematical difference lies between −65,535 and 65,535. The absolute distance lies between 0 and 65,535 and fits in a positive signed 32-bit value.

Only the first sixteen qualifying pairs encountered during traversal are stored. Later qualifying pairs do not replace larger earlier distances. Their link checks and distance calculation still occur.

For each accepted entry, the function writes only its first 32-bit word. It does not assign the other two words.

### Sorting and count publication

After traversal, the function sorts the collected twelve-byte entries by their first word, using signed 32-bit comparisons.

The order is ascending. An entry is exchanged backward while its key is less than or equal to the preceding key. Equal keys can therefore exchange positions; stable ordering of their associated eight bytes is not guaranteed.

Every exchange moves all three 32-bit words of each entry. This makes preexisting contents of the unassigned words relevant to the observable memory transformation.

The block’s count is written only after collection and sorting complete. A failure return from F-ed69baa5ffc4 occurs before this publication step for that block.

### Final result conversion

After the optional collection phase, the function processes both blocks in order, regardless of which preparation gates passed.

For each block:

- Read its 32-bit count.
- If the count is nonzero, read the signed 32-bit first entry value at block `+0x30`.
- If the count is zero, calculate a fallback from the current signed 32-bit value at destination `+0x20`.
- Call F-870c4fcf7295 with the selected value and the integer `5`.
- Write the dependency’s 32-bit result at block `+0xf0`.

For the fallback, first multiply the shared signed value by 50 at 32-bit width. Interpreting that wrapped product as signed, the subsequent adjustment and arithmetic shift produce division by 2,048 rounded toward zero.

If the mathematical multiplication does not fit signed 32-bit range, this must not be described as unlimited-precision multiplication followed by division. The observable calculation uses the 32-bit product.

The shared field is read separately for each fallback. The first conversion call occurs before the second block’s count and possible fallback field are read. Those later reads can therefore observe changes caused by that dependency.

Finally, F-ac5d2e4f2375 is called with the context. Normal return follows that call.

## Side effects

Direct persistent writes are:

- Initial zeroing of both destination counts.
- First-word writes for up to sixteen collected entries per processed block.
- Three-word exchanges during sorting.
- Publication of a collected-entry count after each completed block.
- One converted-result write for each block.

Unused entry slots are not cleared by this function. A zero count does not imply that the entry array contains zeroes or that previous entry contents have been erased.

The function uses temporary context and scratch storage and passes their addresses to dependencies. No direct allocation or deallocation operation is established in the visible body.

F-ac5d2e4f2375 is invoked on every normal path, including paths where the initial gates fail. Its resource-management behavior is unknown; calling it does not establish ownership transfer, release, or successful cleanup.

Dependency calls may have additional effects. No assumption that they preserve destination memory, source fields, global state, or earlier temporary values is justified.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, dependencies leave relevant memory unchanged except for the context preparation needed by the example.

1. **First gate rejects preparation.**  
   F-c841521529ba returns zero. No later preparation gate or record-processing dependency is called. Both counts remain zero. Both conversion inputs come from the fallback calculation, and finalization is still called.

2. **Signed positivity gate fails.**  
   The first two gates pass, but the referenced 16-bit value is zero or negative. Scratch preparation and collection are skipped. A 16-bit bit pattern of `0xffff` is negative, not a large positive count.

3. **Preparation reports nonzero.**  
   F-c5c40ffb3792 returns nonzero. Neither block receives a call to F-ed69baa5ffc4. Final conversion and finalization still occur.

4. **Reciprocal pair appears twice in traversal.**  
   Two visited records link back to each other. Only the record with the lower unsigned address can contribute a distance. The higher-address record fails the ordering condition.

5. **Extreme signed record values.**  
   A qualifying pair contains −32,768 and 32,767. Its stored distance is 65,535, not a wrapped 16-bit result.

6. **Collection is capped before sorting.**  
   Seventeen qualifying pairs produce, in traversal order, sixteen distances greater than zero followed by zero. The count is sixteen. The final zero is not retained, so it cannot become the selected minimum.

7. **Second block stops collection.**  
   Block zero completes, but F-ed69baa5ffc4 returns nonzero for block one. Block zero retains its published entries and count. Block one uses fallback if its count remains zero.

8. **Fallback truncates toward zero.**  
   A shared value of `100` produces a conversion input of `2`; a value of `−100` produces `−2`. These inputs are passed to F-870c4fcf7295; they are not necessarily the stored converted results.

9. **Conversion can affect later reads.**  
   Both counts begin final conversion at zero. If the first conversion call changes the shared destination field, the second fallback calculation observes the changed field rather than a cached earlier value.

## Uncertainties

- The application-level purpose of either result block.
- The meaning of the shared destination field and the constant `5`.
- The initialization operation’s exact effects.
- The complete context and scratch layouts.
- Dependency error meanings, global effects, ownership rules, and memory-retention behavior.
- Whether callers guarantee nonwrapping descriptor arithmetic and valid reciprocal links.
- Whether the two unassigned words in each entry contain meaningful caller-owned data.
- Behavior after invalid memory access, dependency nonreturn, or other execution failure.

Inferred intent: reciprocal linkage plus address ordering appears intended to count each linked pair once, and sorting appears intended to select a minimum among the retained entries. Neither inference changes the established traversal, cap, or side-effect rules.
