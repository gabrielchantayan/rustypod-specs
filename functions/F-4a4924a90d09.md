# F-4a4924a90d09

## Purpose

F-4a4924a90d09 performs two successive indirect dispatches using a caller-supplied receiver. Each invocation receives the original receiver and a different pair of externally stored values.

The established behavior is the dispatch sequence and its recovered address calculation. The available evidence does not establish the application-level purpose of either invocation.

For each stage, the recovered representation reads a signed integer from the receiver’s first location, adds **0x58**, or **88**, in the signed-integer domain, and then converts the sum to a pointer used to load the callable target. This is not represented as pointer arithmetic on an already established dispatch-table pointer.

The calculation is repeated for the second stage. The first invocation can therefore affect the second target by changing the receiver’s first integer or the callable entry subsequently selected.

A recovery warning accompanies the second indirect transfer. The contract below describes the visible recovered sequence while retaining uncertainty about the original second transfer and its return behavior.

### Second dispatch

The second stage again reads the first signed integer at the original receiver address. It independently derives an entry location by adding 88 in the recovered signed-integer domain and then converting the sum to the pointer used to load a callable target.

The resulting target is invoked with the original receiver, B-leading, and B-trailing.

The same original receiver address is passed even if its contents have changed. No previously saved integer, entry address, or callable target is visibly reused.

Consequently:

- Changing the receiver’s first integer can change the second entry location.
- Changing the callable entry at an otherwise unchanged location can change the second target.
- Changing the B sources can change the second invocation’s arguments.
- None of these changes requires a change to the original receiver address.

The recovered representation shows a return after the second invocation. However, the recovery warning reports that an indirect jump was treated as a call. The original transfer may therefore have different continuation semantics. An ordinary returning second call followed by a wrapper return is visible in the recovered representation, but is not independently confirmed as the original machine-level behavior.
