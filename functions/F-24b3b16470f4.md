# F-24b3b16470f4

## Purpose

F-24b3b16470f4 updates a two-field header and a two-field record in a pattern consistent with appending a record to the end of a doubly linked sequence.

The established behavior is narrower than a general list operation: it captures the header’s second field, initializes two fields in the supplied record, updates either the header’s first field or a field reached through the captured value, and finally replaces the header’s second field.

Interpreting these fields as a head pointer, tail pointer, previous link, and next link is **inferred intent**. The routine does not establish that the existing structure is a valid list, that the supplied record is detached, or that any stored address is valid.

## Interface

The routine accepts two address-valued arguments and has no returned value:

| Argument | Required role |
|---|---|
| Header address | Identifies storage containing a first field and a second field. The second field is read initially; both fields can be written during the operation. |
| Record address | Identifies storage containing two fields that are overwritten during the operation. |

Under the recovered 32-bit layout, the relevant fields are:

| Object | Byte offset | Width | Inferred meaning |
|---|---:|---:|---|
| Header | 0 | 32 bits | Head address |
| Header | 4 | 32 bits | Tail address |
| Record | 0 | 32 bits | Previous-record address |
| Record | 4 | 32 bits | Next-record address |

The dependency-directed write also targets a 32-bit field at byte offset 4 from the address captured from the header’s second field.

The source representation uses integer fields to hold address values and uses the integer value zero as the branch discriminator and cleared-link value. A 32-bit integer/address model is consistent with the explicit four-byte displacement and the recovered pointer-to-integer conversions. The actual compilation environment, pointer representation, and integer widths have not been independently verified.

### Preconditions for a defined, successful operation

For the ordinary 32-bit interpretation:

- The header’s second field must be readable.
- Both record fields must be writable.
- The header’s second field must be writable.
- If the captured second field is zero, the header’s first field must be writable.
- If the captured second field is nonzero, the field at byte offset 4 from the represented address must be writable.
- All accesses must satisfy the target’s alignment and memory-access requirements.
- The pointer-to-integer and integer-to-pointer interpretations used by the routine must preserve the relevant addresses.
- Adding four to the captured nonzero value must have a valid interpretation in the target execution model.

These are access requirements, not checks performed by the routine. A null header address or null record address is not accepted through an explicit error path.

No exclusive-ownership requirement is enforced. However, obtaining ordinary list-append behavior requires additional structural assumptions, including a suitable existing tail and a supplied record whose reuse will not corrupt the structure.

## Behavior

### Established access sequence

The supplied representation establishes the following source-level order:

1. Read the header’s second field once and retain its value.
2. Write that retained value into the record’s first field.
3. Write zero into the record’s second field.
4. Select one of two writes based on whether the retained value is zero:
   - If zero, write the record address into the header’s first field.
   - If nonzero, treat the retained value as an address and write the record address into the field four bytes beyond it.
5. Write the record address into the header’s second field.
6. Return without a value.

The branch is governed by the value captured in the first step. It is not governed by a later reread of the header. Likewise, the address used for the nonzero branch comes from that captured value.

The existing contents of the record’s two fields are not read before being overwritten. The header’s first field is not read. The contents of the destination selected by the branch are not read before replacement.

This sequence describes the supplied source representation. It does not establish individual machine instructions, hardware transaction order, atomicity, or visibility guarantees between threads.

### Captured value is zero

With distinct, nonoverlapping header and record storage:

- The record’s first field becomes zero.
- The record’s second field becomes zero.
- The header’s first field becomes the record address.
- The header’s second field becomes the record address.

The prior value of the header’s first field does not affect the decision. Thus, a zero second field causes the first field to be replaced even if it previously contained a nonzero value.

Under the list interpretation, this creates a one-record sequence. That interpretation depends on zero representing an absent link.

### Captured value is nonzero

With distinct storage and a valid existing tail:

- The record’s first field becomes the captured tail address.
- The record’s second field becomes zero.
- The existing tail’s field at offset 4 becomes the record address.
- The header’s second field becomes the record address.
- The header’s first field is not directly written.

The routine does not traverse the sequence, inspect the existing tail’s previous or next links, or verify that the header’s first field reaches the captured tail.

Consequently, “the head remains unchanged” is guaranteed only when the destinations written through the record and captured tail do not overlap the header’s first field.

### Aliasing and record reuse

The routine contains no rejection of overlapping arguments or of a record already present in the structure.

Where overlapping accesses remain valid under the target’s memory and type rules, their effects follow the access sequence above. A later write can overwrite an earlier write to the same storage. Capturing the header’s second field before any writes is significant: subsequent overlap does not change the retained branch discriminator or retained destination address.

For example, if the supplied record is also the captured nonzero tail, the operation first stores that address into the record’s first field and clears its second field. The branch then stores the same record address into its second field. With a distinct header, the resulting record has both links pointing to itself, and the header’s second field still identifies it.

This is not an idempotent append operation. Repeated use of the same record can change link structure even when the header’s tail address does not change.

## Side effects

The ordinary successful path performs:

- One field read.
- Two record-field writes.
- One branch-selected write.
- One final header-field write.

That is four source-level field writes on either branch. Aliasing can reduce the number of distinct storage locations modified.

The routine has no explicit allocation, deallocation, copying of record payload, external I/O, synchronization, or global-variable access. It writes only the fields described above through the supplied or captured addresses.

No ownership transfer or lifetime extension is established. The routine stores an address to caller-supplied storage; it does not establish that the storage will remain alive. Callers relying on the resulting links must arrange suitable lifetimes themselves.

There is no explicit error result, validation failure, rollback, or recovery path. If an access fails during execution, the supplied representation provides no transactional guarantee. Earlier writes may already have taken effect. The exact response to invalid addresses, alignment violations, or invalid integer/address conversions is environment-dependent and is not established here.

Concurrent mutation is not supported by any visible synchronization mechanism. No thread-safe or interrupt-safe publication contract can be derived from these plain accesses.

## Acceptance examples

These examples are conditional consequences of the static representation, not results of runtime tests. Address labels describe storage roles rather than implementation identifiers.

### Empty-header case

Assume a valid header has zero in its second field and the new record occupies distinct writable storage.

After a successful call:

- Both header fields contain the new record’s address.
- Both record fields contain zero.

The record’s previous contents do not matter because neither field is read.

### Existing-tail case

Assume the header’s second field identifies an existing tail, all relevant storage is distinct, and the existing tail’s field at offset 4 is writable.

After a successful call:

- The new record’s first field identifies the old tail.
- The new record’s second field is zero.
- The old tail’s field at offset 4 identifies the new record.
- The header’s second field identifies the new record.
- The header’s first field retains its previous contents.

No acceptance condition requires the old tail’s prior next field to have been zero; the routine overwrites that field without checking it.

### Inconsistent empty-header case

Assume the header’s first field contains an unrelated nonzero address, but its second field is zero.

The routine follows the zero branch. It replaces both header fields with the new record’s address. It does not inspect, traverse, repair, or release anything reachable through the previous first-field value.

### Reappending the current tail

Assume the record argument identifies the same storage as the captured nonzero tail, while the header occupies separate storage.

After successful completion, both record fields contain that record’s own address. The header’s second field contains the same address.

A contract that required the record’s second field always to be zero on return would therefore be incorrect without a nonaliasing precondition.

### Invalid captured destination

Assume the header and new record are accessible, but the captured nonzero value does not identify a valid destination at offset 4.

The routine has no defined validation response. The source-level sequence places the two record writes before the attempted destination write. No error code or rollback is provided; the resulting execution outcome is **documented_only**.
