# F-1d271ae123b6

## Purpose

F-1d271ae123b6 conditionally finds or creates a record in a singly linked list and updates a one-byte value associated with an ordered pair of pointer-sized identities.

The established behavior has three gates:

- An enable byte in the first input object must be nonzero.
- A specific combination of object flags, requested value, and second-input identity suppresses list processing.
- If list processing proceeds, an existing matching record is reused; otherwise, a 16-byte allocation is requested.

The function returns the 32-bit value `0` for both successful processing and intentional no-ops. It returns `7` when a required allocation returns zero.

The apparent intent is to register an association and raise its stored level. That interpretation is inferred, not established. In particular, the update is not a saturating maximum: the comparison uses the full 32-bit requested value, while the eventual write stores only its low eight bits.

## Interface

### Inputs

The visible representation uses 32-bit addresses and 32-bit integer fields. These widths are material to the contract.

| Input | Representation | Established use |
|---|---|---|
| Subject | 32-bit pointer | Identifies an object, supplies control fields, and becomes part of a record’s matching key. |
| Association | 32-bit pointer-shaped value | Used only as an identity for comparison and storage. This function does not dereference it. |
| Requested value | Unsigned 32-bit integer | Participates in the suppression condition and is compared against a stored unsigned byte. |

The association value `1` has a special role in the suppression condition. It is not dereferenced. A zero association is also not rejected and can participate in matching or insertion.

### Subject layout

The function accesses the following locations relative to the subject address:

| Byte offset | Width | Meaning within this contract |
|---|---:|---|
| `0` | 32 bits | Optional control-object address. |
| `4` | 32 bits | List-owner address, captured on entry. |
| `9` | 8 bits | Enable byte; zero disables further processing. |

The fields’ broader meanings and the complete object size are unknown.

### Related layouts

If the control-object address is nonzero, the function reads a 32-bit flags field at byte offset `12` from that address. Only mask `0x4000` affects the visible decision.

The list-owner object contains a 32-bit head address at byte offset `88`.

Each traversed list record has the following accessed layout:

| Byte offset | Width | Meaning within this contract |
|---|---:|---|
| `0` | 32 bits | Subject identity. |
| `4` | 32 bits | Association identity. |
| `8` | 8 bits | Stored value, read as unsigned. |
| `12` | 32 bits | Next-record address. |

A newly requested record occupies 16 bytes. The function does not explicitly initialize bytes `9` through `11`, nor does it unconditionally initialize byte `8`.

### Output

The return value is 32 bits:

- `0`: disabled operation, suppressed operation, reuse of an existing record, or completed insertion.
- `7`: the allocation dependency returned zero when no matching record existed.

A zero return does not establish that a record exists or that any memory changed.

### Preconditions

The subject must permit the initial 32-bit read at offset `4` and the subsequent byte read at offset `9`, even when processing is disabled.

Additional readable and writable storage is required only on paths that access it:

- An enabled subject must permit reading its control-object address.
- A nonzero control-object address must permit reading its flags field.
- Unsuppressed processing requires a readable list-head field and a valid traversable chain.
- Insertion requires the owner’s head field to be writable and the dependency’s nonzero result to designate suitable record storage.
- Updating a stored value requires that record byte to be writable.

There are no visible validity, alignment, capacity, or synchronization checks.

## Behavior

### 1. Capture owner and inspect enable state

The function first reads the 32-bit list-owner address from subject offset `4`. It then reads the enable byte at subject offset `9`.

If the enable byte is zero, the function returns `0`. It does not inspect the control object, read the list head, traverse records, or call the dependency.

The owner-field read therefore occurs even on the disabled path. The owner’s target is not dereferenced on that path.

### 2. Inspect flags and decide whether to suppress processing

For an enabled subject, the function reads the control-object address at subject offset `0`.

- If the address is zero, the flags value used for the decision is zero, and no flags-field access occurs.
- Otherwise, the function reads the 32-bit flags field at control-object offset `12`.

List processing is suppressed only when all of the following hold:

1. The control-object address is nonzero.
2. Its flags have bit `0x4000` set.
3. The requested value is exactly `1`.
4. The association identity is not the address-shaped value `1`.

When suppressed, the function returns `0` without accessing the list.

The flags read precedes this decision. A requested value other than `1`, or an association equal to `1`, does not eliminate the flags access when the subject is enabled and its control-object address is nonzero.

### 3. Search the list

If processing is not suppressed, the function reads the head from offset `88` of the previously captured owner.

Records are examined in list order. For each nonzero record address:

1. Read the association identity at record offset `4`.
2. Compare it with the association input.
3. Only if those identities match, read the subject identity at record offset `0` and compare it with the subject input.
4. If both match, select that record and stop searching.
5. Otherwise, read the next-record address at offset `12` and continue.

Thus, a record whose association does not match does not have its subject-identity field read during that comparison.

The first matching record is selected. The function neither detects nor consolidates duplicate keys. It does not read the selected record’s next link as part of continued traversal.

If the head is zero, or traversal reaches a zero next link without finding a match, the search has no result. Cycles and malformed links are not detected.

### 4. Request and publish a new record when necessary

When no match exists, the function calls F-1c177d5ba9f6 with the argument `16`.

If the returned address is zero, it immediately returns `7`. Before this call, the function has performed no explicit record or list writes. Effects performed inside the dependency remain unknown.

For a nonzero result, the function performs these accesses in order:

1. Store the subject identity at new-record offset `0`.
2. Store the association identity at new-record offset `4`.
3. Read the head again from offset `88` of the captured owner.
4. Store that head address at new-record offset `12`.
5. Store the new-record address into the owner’s head field.

The insertion therefore prepends a record using a head value read after the dependency returns. It does not reuse the head value observed before allocation, and it does not repeat the search.

The captured owner address is retained across the call. The function does not reread subject offset `4` to choose a possibly different owner afterward.

Publication occurs before the stored-value comparison and any byte update.

### 5. Compare and conditionally update the stored byte

For either the selected existing record or the newly inserted record, the function reads the byte at offset `8` as an unsigned value from `0` through `255`.

It compares that value with the complete unsigned 32-bit requested value:

- If the stored byte is less than the requested value, it writes the requested value’s low eight bits to offset `8`.
- Otherwise, it leaves that byte unchanged.

The function then returns `0`.

For requested values from `0` through `255`, this produces the unsigned maximum of the previous byte and the request. For requested values greater than `255`, every possible stored byte compares less than the request, so a write always occurs. The written value is the request modulo `256`, which can be smaller than the prior byte.

For a new record, the comparison reads whatever byte exists at offset `8` after the dependency call and the preceding stores. This function does not first set it to zero.

## Side effects

### Explicit memory changes

The function can:

- Write the subject and association identities into a newly obtained record.
- Write that record’s next link.
- Replace the captured owner’s list head.
- Write a single byte at offset `8` in the selected record.

It does not explicitly change the subject’s control fields, control-object flags, existing-record keys, or existing-record links.

These descriptions identify addressed fields, not a guarantee of disjoint memory. If input objects, records, or dependency-returned storage overlap, a write may also affect later reads through another role. Non-overlapping valid storage is required for the ordinary list interpretation.

### Ownership and lifetime

The function visibly obtains storage only through F-1c177d5ba9f6. It contains no release operation.

A successful insertion makes the returned address reachable through the owner’s head. Who owns that storage, how long it remains valid, and how it is eventually released are not established.

The function stores the two input identities without any visible retain, reference-count, or lifetime-extension operation. No ownership transfer of the subject or association can be inferred.

### Reentrancy and concurrency

There is no visible locking, atomic publication protocol, duplicate prevention across allocation, or concurrent-modification detection. In particular, the new head is published before its stored byte is conditionally updated.

The dependency’s effects on shared state are unknown. The post-call head reread is established; preservation of the owner, records, or other memory by the dependency is not.

## Acceptance examples

These examples are conditional on valid memory and the stated dependency behavior. They are specification cases, not executed tests.

1. **Disabled subject.**  
   Given a readable owner field and an enable byte of zero, return `0` after reading those fields in that order. Do not dereference the captured owner.

2. **Suppressed request.**  
   Given an enabled subject, nonzero control-object address, flags containing `0x4000`, requested value `1`, and association `2`, return `0` without reading the list head.

3. **Special association bypasses suppression.**  
   With the same flags and requested value, but association `1`, perform list processing. Do not dereference address `1` merely because it is the association input.

4. **Existing record increases within byte range.**  
   Given a matching record with stored byte `4` and request `9`, write `9` to that byte and return `0`. Do not allocate.

5. **Existing value already sufficient.**  
   Given a matching record with stored byte `9` and request `4`, leave the byte unchanged and return `0`.

6. **Full-width comparison followed by truncation.**  
   Given a matching record with stored byte `200` and request `256`, write `0`. Given request `257`, write `1`. These are not saturating updates.

7. **Allocation failure.**  
   Given no match and a dependency result of zero, return `7`. No explicit list or record writes occur before that result; dependency-side effects remain outside this guarantee.

8. **Fresh storage is not assumed zeroed.**  
   Given no match, suitable nonzero returned storage, an initial offset-`8` byte of `240`, and request `3`, insert the record but leave that byte `240`.

9. **Duplicate keys.**  
   Given two matching records, select the first encountered. Do not update the later duplicate or allocate a replacement.

10. **Head changes during the dependency call.**  
    If the dependency changes the captured owner’s head while preserving usable storage, prepend the new record to the post-call head. Do not search that changed chain again.
