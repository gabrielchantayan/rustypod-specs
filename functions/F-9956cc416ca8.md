# F-9956cc416ca8

## Purpose

F-9956cc416ca8 increments a shared 32-bit counter and constructs two ordered groups of four object references only when the incremented value equals one. It publishes the references through shared storage, installs links between selected objects, and sets a flag in each group.

On every normal return, the result is the first incoming 32-bit argument, unchanged. The result does not report initialization success.

“Family A,” “Family B,” “backing operand,” “wrapper,” and “template” are descriptive terms for the visible relationships. Application-level identities and ownership semantics are not established.

Every subsequent visible call to this dependency has two arguments: a size and an operand. The actual calling convention and significance of this difference are **documented_only**.

### Shared storage and layouts

The visible representation uses 32-bit words and four-byte references. Relevant shared state comprises:

- A writable initialization counter.
- Separate backing-operand and wrapper-request-operand sources for the two families.
- A template-address source for each family. Each selected template contains two consecutive 32-bit words.
- A publication-address source selecting storage for eight consecutive 32-bit reference slots.

Publication slots 0–7 occupy byte offsets 0, 4, 8, 12, 16, 20, 24, and 28.

A wrapper’s **adjusted reference** is obtained by reading its first 32-bit word as a metadata address, reading a 32-bit displacement 12 bytes before that metadata address, and adding the displacement to the wrapper base. This describes the visible address calculation, not a verified class layout.

Publication checks the wrapper base for null before performing this adjustment. A null base produces a null publication value. A non-null base does not guarantee a non-null or valid adjusted reference.

### Preconditions for normal completion

The counter and every reached shared-state source must be accessible. Reached dependencies must return normally, and all subsequent object, metadata, template, and publication accesses must be valid.

The function does not enforce these conditions. In particular, the post-publication link and flag operations require usable wrapper-0 and wrapper-2 metadata even though earlier publication operations permit null wrappers.

## Behavior

### Counter update and gate

The function reads the counter and writes its incremented value. It then captures Family A member 0’s backing operand, before testing whether the incremented counter equals one.

Consequently, the backing-operand read occurs even when initialization is skipped. If the gate does not match, there are no visible dependency calls or publication writes, and the first argument is returned.

For representable signed arithmetic:

- Zero becomes one and enters initialization.
- One becomes two and skips initialization.
- Minus one becomes zero and skips initialization.

The supplied representation uses signed arithmetic. Overflow behavior, including any possible wraparound-based reinitialization, is **documented_only**. There is no explicit counter reset, decrement, rollback, or completion marker.

### Construction order and request sizes

Family A is constructed, published, linked, and flagged before Family B’s first request.

Each family requests backing member 0, then wrapper 0; backing member 1, then wrapper 1; backing member 2, then wrapper 2; and backing member 3, then wrapper 3. Backing requests all use size 72. Wrapper 0 also uses size 72; wrappers 1–3 use size 68.

A completed branch therefore makes 16 requests: ten with size 72 and six with size 68. Their size arguments total 1,128 bytes. This does not establish that any memory is newly allocated.

A zero backing-request result skips that backing configuration call but does not skip the subsequent wrapper request. A zero wrapper-request result skips its construction path and leaves the corresponding wrapper null. There is no explicit early failure return.

### Backing operands and their snapshots

The distinction between a saved operand and a later shared-source read is observable.

**Family A member 0:** the operand captured immediately after the counter update is retained for wrapper-0 configuration. The first request separately reads the shared backing-operand source again. It does not use the saved value. These two values may differ if the source changes between the reads.

**Members 1 and 2, in both families:** each backing operand is captured before its backing request. The request separately reads the corresponding shared source. The saved value survives the intervening calls and supplies the associated wrapper constructor. Thus the saved operand and the request operand are separate observations, even where they ordinarily agree.

**Member 3, in both families:** its backing request reads its own backing-operand source, but wrapper 3 receives the saved member-2 operand. No member-3 snapshot replaces that saved value.

**Family B member 0:** its backing operand is captured at the Family A publication boundary, before the publication address is captured and before any Family A publication store. This single saved value supplies both Family B’s first request and its later wrapper-0 configuration. It is not reread for that request.

The backing configuration dependencies receive nonzero backing-request results and modes 0, 1, 2, and 2 for members 0–3, respectively. Family A uses F-31343d17619f; Family B uses F-26d34189231b. Their return values are not explicitly consumed.

### Wrapper 0: template snapshots and interior construction

Both families use the same structural process, with different dependencies and template-address sources.

Immediately after the wrapper-0 request returns, the function captures that family’s template-pair address. This address capture occurs even when the request returned zero. On the zero-result path, the template words are not subsequently read by this wrapper-construction path.

For a nonzero request result, the initial metadata word is read through the **current global template-address source**, not through the saved template address, and written at the requested address. The interior-construction dependency then receives the requested address plus eight bytes.

Family A uses F-075c80dad330; Family B uses F-32e1c1ae2f9a. The returned interior address determines the effective wrapper base by subtraction of eight bytes. The function does not check this return for null, consistency with the input, or containment within the requested storage.

After the dependency returns, the template reads use the **previously captured template address**:

- Its first word is read and installed at the effective wrapper base.
- A displacement is read 12 bytes before that word’s metadata address.
- Its second word is written at the position selected by that displacement relative to the effective wrapper base.
- A 32-bit zero is written four bytes before the returned interior address, equivalently four bytes after the effective wrapper base.

The template snapshot saves an address, not the contents of either template word. The interior-construction dependency may change the global template-address source, modify the saved template’s contents, or both. Changes to the source do not redirect the later saved-address reads; changes to the saved template’s contents can affect their values.

The effective-base write precedes the second template-word access. If the relevant regions alias, that write or an earlier metadata write can affect subsequent reads. No disjointness guarantee is visible.

Finally, the function computes the adjusted reference from the effective wrapper’s then-current metadata and invokes:

- F-95ac4f08c8c7 for Family A.
- F-48223db4cfdd for Family B.

Each receives that adjusted reference and the saved member-0 backing operand described above. Its return value is not explicitly consumed. Later publication recomputes the adjustment; it does not retain this earlier adjusted address.

### Wrappers 1–3

For each nonzero wrapper request, the function invokes F-07e65cc048f4 for Family A or F-b3102178e02f for Family B. The arguments are the request result and the selected saved backing operand.

The constructor’s return becomes the wrapper base, including null if it returns null. The function does not require the returned base to equal the request result.

Wrappers 1 and 2 receive their respective saved backing operands. Wrapper 3 receives the saved member-2 operand, despite having followed a separate member-3 backing request.

### Family A publication boundary

After all four Family A wrappers have been constructed, the explicit order is:

1. Capture Family B member 0’s backing operand.
2. Capture the publication-block address.
3. Publish Family A members 0–3.
4. Perform Family A’s link write.
5. Perform Family A’s flag update.
6. Begin Family B’s first request, using the saved backing operand.

The first Family A publication store obtains its destination through the shared publication-address source again. The other three use the captured publication address. Thus the source includes both an address snapshot and a separate use of the shared source for slot 0. There is no dependency call between them, but concurrent changes must not be assumed impossible.

Each publication value is null for a null wrapper base; otherwise, its metadata adjustment is computed before that member’s store. The four stores occur in member order. Earlier stores can affect later accesses if storage aliases.

### Link and flag operations

After each family’s four publication stores, the function recomputes wrapper 0’s adjusted address and writes the **unadjusted wrapper-1 base** at byte offset 56 from it. This is not necessarily the same reference that was published for member 1.

It then accesses the 32-bit field at offset four from wrapper 2’s adjusted address, combines the read value with mask `0x2000`, and writes the result. Under stable addressing, this preserves all other bits of the value read.

Neither operation guards wrapper 0 or wrapper 2 against null. Publication may therefore have completed for that family before an invalid metadata or object access occurs. A null wrapper 1, by contrast, can be stored as the link value without directly dereferencing wrapper 1.

The flag expression contains metadata-dependent address calculations for its read and write. It establishes a logical bit-setting operation, not an atomic instruction or an independently verified machine-level access trace.

### Family B publication and return

Family B follows the same construction, template, link, and flag rules. Its first request and wrapper-0 configuration both receive the backing operand saved before Family A publication.

Its four references are published to slots 4–7 using the publication address captured at the Family A boundary. The function does not reload that address after Family B’s dependency calls.

After Family B’s link and flag operations, the first incoming argument is returned unchanged.

There is no explicit cleanup, restoration of publication contents, or reversal of the counter update on an abnormal exit or invalid access.

## Side effects

Established direct effects include:

- The counter read and incremented write on every invocation.
- The eager Family A member-0 backing-operand capture, including skipped initialization.
- Conditional dependency calls and reads of shared operands.
- Template-address captures after both wrapper-0 requests, including zero results.
- Conditional template, metadata, and zero-field accesses.
- Eight ordered publication stores on a completed initialization branch.
- Two link stores and two flag read-modify-write expressions.

Dependencies may have additional effects. None is established as preserving globals, template contents, metadata, publication storage, or object lifetimes.

Publication is incremental, not transactional. Family A slots are written before its link and flag fields and before Family B construction. Family B slots are likewise written before its final fields. There is no visible synchronization operation.

No explicit release operation appears. That does not establish ownership transfer, retained ownership, absence of release inside dependencies, or safe lifetime after a call. Aliasing and concurrent modification can affect later reads and writes; external coordination and storage-validity requirements remain unresolved.

## Acceptance examples

These examples are conditional static-contract consequences, not runtime observations.

1. **Skipped initialization.** With initial counter seven and valid reached shared accesses, the counter becomes eight. Family A member 0’s backing operand is still captured. No dependency is called, no publication slot is explicitly written, and the first argument is returned.

2. **Distinct Family A member-0 reads.** Suppose the eager capture observes operand P, but the first request’s later read observes Q. With valid subsequent execution, that request receives Q, while F-95ac4f08c8c7 receives P. Reusing Q for both would change the contract.

3. **Template-source replacement.** Suppose a family captures template address T, and its interior-construction dependency changes the global template-address source to U. Later template-word reads still use T. If the dependency instead modifies words at T, those modified contents are eligible to be read. This assumes no other interfering modification or invalid access.

4. **Zero wrapper-0 request.** A zero result still leads to capture of the family’s template address, but not to the wrapper-0 template-word reads or construction calls. Its publication value is null. The later unguarded link operation prevents any promise of graceful completion.

5. **Family B snapshot timing.** Suppose Family B member 0’s operand is P when captured before Family A publication. If a subsequent Family A publication or link write changes its shared source through aliasing, Family B’s first request and wrapper-0 configuration still receive saved P.

6. **Backing failure without early return.** If Family A backing member 1’s request returns zero, F-31343d17619f is skipped for it. The wrapper-1 request still occurs, and a nonzero result is passed to F-07e65cc048f4 with the earlier saved operand.

7. **Member-3 operand reuse.** If saved member-2 operand P differs from member-3 request operand Q, wrapper 3 receives P in either family. Substituting Q is not equivalent.

8. **Null wrapper 1.** With valid wrappers 0 and 2 and otherwise valid execution, a null wrapper 1 is published as null and written as null into wrapper 0’s adjusted-offset-56 field.

9. **Flag preservation.** If the flag read observes `0x00000005`, stable addressing and no interference yield an explicit write of `0x00002005`.

10. **Publication-source change during Family B.** If a Family B dependency changes the publication-address source, slots 4–7 still target the address saved before Family A publication, provided that retained storage remains valid.
