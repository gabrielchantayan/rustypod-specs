# F-c8192756568e

## Purpose

F-c8192756568e obtains a node from a dependency, copies selected input fields into it, attaches it beneath a supplied node, performs color-based structural repair, and publishes the obtained node’s address through an output slot.

The links, header updates, and repair cases are consistent with insertion into a red-black tree whose header tracks the root and both extremes. This is **inferred intent**, not an independently established type or correctness guarantee. The established contract is the visible sequence of reads, writes, branches, and dependency calls.

The function does not search for an insertion position, check whether the selected child link is occupied, reject duplicates, or provide explicit failure recovery. Correct structural behavior depends on the supplied insertion position, existing links, initial node state, and dependency behavior.

## Behavior

### Obtaining and populating the node

The first dependency call is F-6e172d9ec62a with the container address. Its result is retained as the node to attach and eventually publish.

The payload-copy guard checks whether that address plus 16 is nonzero. It is not a check that the obtained address itself is nonzero. A null obtained address therefore does not, by itself, suppress the copy.

If the guard succeeds, the direct access order is:

1. Read the input byte at offset 0 and write it to node offset 16.
2. Read the four-byte input field at offset 8.
3. Read the four-byte input field at offset 12.
4. Read the four-byte input field at offset 4 and write it to node offset 20.
5. Write the previously read offset-8 field to node offset 24.
6. Write the previously read offset-12 field to node offset 28.

This is a selective field copy, not a contiguous block copy. The early byte write can affect later input reads if storage overlaps. No general overlap-safe guarantee is established.

If the guard fails, only this payload-copy phase is skipped. Counter updates, attachment, repair, and output publication remain on the execution path.

### Counter update and attachment selection

After the payload phase, the function reads the four-byte container counter at offset 20, adds one, and writes it back. This precedes the comparison call and structural attachment writes. No rollback is visible.

The supplied representation uses signed 32-bit arithmetic for this update. It supplies neither a range check nor an overflow policy sufficient to promise portable wrapping behavior.

The function then reads the header address from container offset 16.

The offset-8 attachment path is selected without calling F-685cd10e4a2e if either:

- The attachment node equals this header address; or
- The direction override is nonzero.

On this bypass path, the original direction override and attachment-node address remain available for the fifth and sixth apparent arguments of a possible later six-argument call to F-3890c860a6ae.

Otherwise, the function sets both of those retained argument values to zero, then calls F-685cd10e4a2e with:

1. Container address plus 25.
2. The original input-record address.
3. Attachment-node address plus 16.

A nonzero result selects offset 8; zero selects offset 12. Both retained extra-argument values remain zero regardless of the comparison result.

The comparison’s sign, ordering relation, equality meaning, and side effects are unknown. In particular, zero is not established to mean “duplicate.”

### Attachment and parent assignment

**Offset-8 path:**

The obtained node address is first written to the attachment node’s offset-8 link. The function then reloads the header address.

- If this header differs from the attachment node, its offset-8 link is read. That link is replaced with the obtained node address only if it equals the attachment node.
- If this header equals the attachment node, its offset-4 root link is written with the obtained node address. The header address is then reloaded again, and that header’s offset-12 link is written with the obtained node address.

With a stable header and conventional empty-tree state, the latter case sets both extremes and the root to the new node.

**Offset-12 path:**

The obtained node address is first written to the attachment node’s offset-12 link. The function reloads the header address and reads its offset-12 link. That header link is replaced only if it equals the attachment node.

After either path, the attachment-node address is written to the obtained node’s offset-4 parent link.

Thus, the attachment’s child-link write precedes the new node’s parent-link write. Existing child links are overwritten without an occupancy check.

Header reloads are part of the behavior. Neither aliasing nor dependency behavior permits assuming that every header read returns the same address.

### Repair-loop entry

The obtained node becomes the active repair node.

Each loop condition reloads the header address and reads its offset-4 root link. If that root equals the active node, repair stops without reading the active node’s parent color for that iteration.

Otherwise, the function reads the active node’s parent link and then the parent’s color byte. A nonzero parent color stops repair. Only a zero parent color enters the repair cases.

The function then reads the parent’s parent address and that grandparent’s offset-8 child address. It compares the parent address with this child address.

The direct writes use color value 1 for the state conventionally called black and 0 for the state conventionally called red. The entry condition accepts any nonzero parent color as a stopping state, not only 1.

### Parent equals the grandparent’s offset-8 child

The grandparent’s offset-12 child becomes the uncle.

If the uncle is nonnull and has color zero:

1. Write 1 to the previously read parent’s color.
2. Write 1 to the previously read uncle’s color.
3. Resolve the active node’s current parent and grandparent links and write 0 to that grandparent’s color.
4. Resolve those links again and make the resulting grandparent the active node.

The later link resolutions are fresh reads, not a promise to reuse the earlier grandparent address.

If the uncle is null or has nonzero color:

- Read the parent’s offset-12 child link.
- If it equals the active node, call F-5166d0f0eac3 with the container and parent, then make the previously read parent the active node.
- Resolve the active node’s current parent and write its color to 1.
- Resolve the active node’s parent and grandparent links and write the resulting grandparent’s color to 0.
- Resolve those links again and call F-3890c860a6ae with the container and resulting grandparent address.

These calls are consistent with an optional left rotation followed by a right rotation. Their actual implementations are unavailable.

### Parent differs from the grandparent’s offset-8 child

The previously read offset-8 child becomes the uncle. There is no separate verification that the parent is the grandparent’s offset-12 child.

If this uncle is nonnull and has color zero, the same recoloring and upward movement described above occurs.

Otherwise, the function reads the parent’s offset-8 child link. If it equals the active node, the function makes the six-apparent-argument call to F-3890c860a6ae described below, then makes the previously read parent the active node.

After that optional call:

1. Resolve the active node’s current parent and write its color to 1.
2. Resolve the active node’s parent and grandparent links and write the resulting grandparent’s color to 0.
3. Resolve those links again and call F-5166d0f0eac3 with the container and resulting grandparent address.

This is consistent with the mirrored rotation sequence.

## Acceptance examples

These are **conditional static acceptance examples**, not executed tests. Tree-shaped outcomes require valid links and appropriately behaving dependencies.

### Empty structure with a stable header

If the attachment node equals the current header and the obtained node is suitably initialized:

- Comparison is bypassed.
- The counter update precedes attachment.
- Header offset 8 is written first, then offset 4, then offset 12.
- The obtained node’s parent becomes the header.
- With the header remaining stable, repair stops because the obtained node is the root.
- The root color is set to 1 before the node address is published.

### Forced attachment does not imply override equivalence

If execution later reaches the six-apparent-argument F-3890c860a6ae call, its fifth apparent argument is respectively 1 or 2. Overall equivalence between these executions cannot be required without establishing that dependency’s treatment of the argument.

### Comparison-selected offset 8

For a non-header attachment node and zero override, a nonzero comparison result selects offset 8. If the later six-apparent-argument call is reached, its fifth and sixth apparent arguments are both zero—even though the original attachment-node address was nonzero.

### Null uncle at the six-argument site

Assume the parent differs from the grandparent’s offset-8 child, that child is null, and the active node equals the parent’s offset-8 child.

The optional F-3890c860a6ae call has a null third apparent argument and the previously read grandparent address as its fourth. Its fifth and sixth values depend on whether attachment selection bypassed comparison.

### Nonnull, nonzero-colored uncle at that site

Under the same positional conditions, suppose the uncle is nonnull and its color byte is 200.

The call’s third apparent argument is the uncle address; its fourth is unsigned 32-bit value 200, not the grandparent address. A zero color instead selects recoloring and does not take this call at that point.

### Parent or uncle color boundaries

A non-root active node with parent color 7 stops repair at the parent-color check. Final root recoloring still occurs.

A zero-colored parent with a nonnull zero-colored uncle enters recoloring: parent and uncle receive 1, a freshly resolved grandparent receives 0, and repair continues from a freshly resolved grandparent.

### Payload and occupied-link behavior

With nonoverlapping storage and a successful copy guard, input offsets 0, 4, 8, and 12 populate node offsets 16, 20, 24, and 28. Node bytes 17–19 receive no direct initialization.

If the selected attachment child link is already occupied, it is overwritten without a visible rejection or release operation.
