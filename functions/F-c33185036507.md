# F-c33185036507

## Purpose

F-c33185036507 updates an existing two-word record or inserts a new one into a table-like structure. The first input supplies a 32-bit key; the second supplies a 32-bit value.

An existing entry receives a replacement value. A missing entry causes an eight-byte storage request, publication and initialization of the new record, and possibly replacement of the table’s slot array. The count is incremented only after the insertion reaches its final successful status check.

Growth is not transactional. The new record and several metadata changes are published before replacement-array status is inspected. A non-null return does not establish that the table is unchanged, that traversal was skipped, or that an allocator originally reported failure.

The key/value-table interpretation is inferred intent. The access widths, branch conditions, call ordering, and direct writes described below are established by the supplied static representation. No runtime tests have been performed.

## Interface

### Inputs

| Input | Representation | Observed use |
|---|---|---|
| Key | Opaque 32-bit word | Passed to initial lookup and stored as the first word of a new record. |
| Value | Opaque 32-bit word | Written as the second word of an existing or new record. |
| Table | Address of 32-bit fields | Supplies metadata and the slot-array address. |
| Context | Pointer-shaped argument in the represented 32-bit environment | Forwarded to storage-request and old-array dependencies. Not directly dereferenced here. |

The function performs no application-level interpretation of key or value.

### Table and record layout

| Table byte offset | Width | Observed role |
|---|---:|---|
| 0 | 32 bits | Threshold, compared with count using signed ordering. |
| 4 | 32 bits | Capacity-like field; saved as a traversal bound and doubled during growth. |
| 8 | 32 bits | Count, incremented at successful insertion completion. |
| 12 | 32 bits | Slot-array address, overwritten during growth. |

Each slot occupies four bytes and contains zero or a represented record address.

Each record occupies eight bytes:

| Record byte offset | Width | Observed role |
|---|---:|---|
| 0 | 32 bits | Key |
| 4 | 32 bits | Value |

These are properties of the supplied 32-bit representation, not a portable layout for wider-pointer environments.

### Output and status channels

The result is pointer-shaped. Two separate addressable status locations participate:

- **Record status:** initialized to null after initial lookup; its address is supplied to F-3ce007b692cc.
- **Growth status:** initialized to null when growth begins; its address is supplied to F-6dd003795db7.

Ordinary outcomes are:

- Existing entry: null.
- New entry without growth, with null record status: null after count increment.
- New entry with growth, with null final growth status: null after count increment.
- Non-null record status immediately after the record request: that status, without direct publication or initialization of the proposed record.
- Non-null growth status at the final growth check: that status, without count increment.

Growth status is inspected twice: once immediately after replacement-array publication, and again after the optional traversal and old-array call. The first observation controls whether traversal occurs. The final observation controls error return versus count increment.

A non-null final growth status is not necessarily a status originally reported as non-null by the replacement allocator. A dependency may retain the supplied status address and modify it during a later call. The function does not establish otherwise.

The meaning, ownership, and lifetime of a non-null result remain unknown.

### Preconditions

Normal execution requires suitable storage for every access actually reached:

- A readable and writable table with the fields above.
- A readable selected slot, writable on insertion.
- A valid existing record when the selected slot is nonzero.
- Writable eight-byte record storage when record status is null.
- Readable old slots and referenced keys during growth traversal.
- Writable destination slots returned by growth relookup.

No local validation enforces these requirements. In particular, a null storage result accompanied by null status is not separately rejected.

Ordinary table interpretations also require that unrelated table fields, slots, records, and status storage do not overlap destructively. Disjointness is not checked.

## Behavior

### Initial lookup

The first dependency call is F-768f1c147c24, with six visible arguments in this order:

1. Key.
2. Table.
3. Table again.
4. Context.
5. Key again.
6. Value.

Its result is treated as a slot address.

After the call, record status is set to null. The selected slot is then read to distinguish an existing record from a missing record.

Later calls to this same dependency have only two visible arguments. Its complete calling convention is unresolved; the initial call must not be silently normalized to the later apparent lookup interface.

### Existing record

When the selected slot is nonzero, the function uses its contents as a record address and writes the supplied value at record offset four.

It then returns the null record status.

This path makes no direct record-allocation call, key write, count increment, growth comparison, array replacement, or traversal. Those exclusions concern this function’s actions; they do not establish that initial lookup preserves all other state.

### Missing record

When the selected slot is zero, F-3ce007b692cc receives:

1. Context.
2. The size eight.
3. The address of record status.

Its direct result is treated as a proposed record address.

If record status is non-null after the call, the function returns that status. It does not directly publish or initialize the proposed record, enter growth, or increment count. It makes no explicit release call for the proposed address.

If record status is null, the following direct writes occur in order:

1. The proposed record address is stored into the selected slot.
2. Value is stored at record offset four.
3. Key is stored at record offset zero.

Publication precedes initialization, and the value write precedes the key write. No locking or atomic publication mechanism is visible. Concurrent observation of a fully initialized record is not guaranteed.

### Growth decision

After record initialization, the function compares threshold with count as signed 32-bit quantities. Growth is entered when:

**threshold ≤ count**

The count has not yet been incremented for the new record. Therefore, with otherwise unchanged metadata:

- Threshold ten and count nine do not trigger growth.
- Threshold ten and count ten trigger growth.

The comparison uses table contents present at this point, not a count saved before dependency calls.

### Growth setup and replacement request

When growth is entered, the function:

1. Saves the old capacity-like value.
2. Saves the old slot-array address.
3. Initializes growth status to null.
4. Forms a doubled capacity using a 32-bit left shift by one.
5. Writes the doubled value to the capacity field.
6. Calls F-870c4fcf7295 with doubled capacity and three.
7. Writes its 32-bit result to the threshold field.
8. Calls F-6dd003795db7 with context, four, zero, doubled capacity, zero, and the address of growth status.
9. Writes that call’s direct result to the table’s slot-array field.

Only after the replacement-array address has been stored does the first growth-status check occur.

The replacement request appears intended to obtain four-byte slots. Its actual allocation arithmetic, initialization policy, and handling of unusual capacities are unknown. F-870c4fcf7295 appears to calculate a threshold, but neither its formula nor a load factor is established.

### First growth-status check

If growth status is non-null at this first check, traversal is skipped and F-bf7242c98d06 is not called by this function. Execution proceeds to the final growth-status handling.

If growth status is null at this first check, traversal and the subsequent old-array call are entered.

This decision is not continuously reevaluated during traversal. A later change to growth status does not itself stop the traversal or suppress the old-array call.

### Traversal and old-array call

Traversal starts at signed index zero and continues while the index is less than the saved old capacity. Slots are visited in increasing address order, four bytes apart.

For each visited slot:

- Zero causes no relookup or destination write.
- A nonzero slot supplies a record address whose first word is read as a key.
- F-768f1c147c24 is called with that key and the current table.
- The current contents of the old slot are then read and assigned to the returned destination slot.

The address assigned to the destination is read after relookup. If relookup changes the old slot, the assigned address need not equal the record address used for the preceding key read.

The function transfers record addresses; it does not allocate replacement records or copy their two-word contents. The newly inserted record is eligible for traversal because it was published into the old array before growth, provided its slot lies within the traversed range.

After the loop, F-bf7242c98d06 receives context and the saved old-array address. This call occurs even when the loop has zero iterations. No separate return-based failure channel from this call is inspected.

### Final growth-status check and count completion

After the optional traversal and old-array call, the current growth status is copied to record status. Growth status is then checked again.

If it is non-null, that status is returned without incrementing count.

This includes two materially different histories:

- Growth status was non-null at the first check, so traversal and the old-array call were skipped.
- Growth status was null at the first check, so traversal and the old-array call occurred, but status became non-null before the final check.

The second history is possible if the replacement dependency retained the status address and a later dependency modifies that location. Such behavior is not established to occur, but it is not excluded by the supplied contracts.

Conversely, a status that becomes non-null during traversal but is null again at the final check does not prevent count increment. The final observation controls completion.

When growth is unnecessary, or when final growth status is null, the function reads the current count, adds one, and writes it back. It does not increment a saved pre-call count. Intervening dependency changes to count therefore affect the value incremented.

No rollback restores earlier record, slot, or metadata writes on a non-null return.

## Side effects

### Direct state changes

Depending on the path, direct writes affect:

- An existing record’s value.
- A selected slot and a new record’s value and key.
- Capacity, threshold, slot-array address, and count.
- Destination slots during traversal.
- The function’s addressable status storage.

The function publishes the new record before initialization and replacement metadata before checking replacement status.

A non-null final growth status can leave either a partially migrated table or a table whose traversal and old-array call have already completed. In both cases, the function skips its final count increment.

### Ownership and lifetime

On successful insertion, a record address becomes reachable through a slot. During successful first-check growth, addresses are copied into replacement slots, and the saved old array is passed to F-bf7242c98d06.

The function makes no explicit individual-record release call. It also makes no explicit release call for:

- A proposed record associated with non-null record status.
- A replacement-array result associated with non-null growth status.
- The old array when the first growth-status check is non-null.

A non-null **final** growth status alone does not establish whether the old-array call occurred.

These observations do not prove leaks, ownership transfer, or actual deallocation. Dependency contracts are required for those conclusions. Passing status addresses likewise does not establish that dependencies discard those addresses after returning.

No general preservation guarantee is available for globals, context-managed state, table contents, or shared storage across calls.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless otherwise stated, storage is valid, arithmetic remains representable, objects do not overlap destructively, and dependencies leave unrelated state unchanged.

### Existing entry

Given an initial slot containing a valid record address:

- Value at record offset four is replaced.
- Key is not directly rewritten.
- No record request or growth operation is made by this function.
- Count is not directly incremented.
- Result is null.

### Insertion below threshold

Given an empty slot, null record status, threshold ten, and count nine:

- Record address is published before value and key initialization.
- Value is written before key.
- Growth is skipped.
- Count becomes ten.
- Result is null.

### Growth with null status throughout

Given an empty slot, null record status, threshold ten, count ten, and old capacity sixteen:

- Growth uses doubled capacity thirty-two.
- The helper result becomes threshold.
- Replacement-array address is published before the first status check.
- With growth status null at both checks, nonzero old slots are relooked up and assigned.
- The old-array dependency is called.
- Count becomes eleven.
- Result is null.

### Record-status error

Given non-null record status immediately after F-3ce007b692cc:

- That status is returned.
- No new record is directly published or initialized.
- No growth or count increment follows.
- Dependency side effects and ownership remain unspecified.

### Non-null status at the first growth check

Given completed record publication and initialization, followed by non-null growth status at the first check:

- Capacity, threshold, and replacement-array address have already been written.
- Traversal and the old-array call are skipped.
- With status unchanged through the final check, that status is returned.
- Count is not incremented.
- No rollback occurs.

This criterion is about the observed status, not proof that the replacement allocator itself failed.

### Status changes after the first growth check

Given null growth status at the first check, and a later dependency changing the exposed status location to a non-null value that remains present at the final check:

- Traversal proceeds without a status-based early exit.
- The old-array dependency is called.
- The final non-null status is returned.
- Count is not incremented.
- Completed migration writes are not undone.

If that location instead contains null at the final check, count is incremented despite any intermediate non-null value.

## Uncertainties

The following remain **documented_only**:

- Complete lookup calling convention and failure behavior.
- Threshold formula and replacement-array initialization.
- Dependency effects on table fields, old slots, globals, and exposed status storage.
- Whether status addresses are retained or later modified.
- Error-result meaning, ownership, and lifetime.
- Allocation and release ownership guarantees.
- Concurrency and synchronization guarantees.

Integer boundaries require separate caution. Capacity doubling is represented as a 32-bit left shift. Count increment uses recovered signed integer arithmetic. No overflow checks are visible; inputs exceeding representable arithmetic must not receive a portable wraparound guarantee.

Traversal uses signed ordering. A saved capacity of zero or a negative value causes zero iterations, but a null first growth status still leads to the old-array call. This branch consequence does not establish support for malformed capacities.

## Evidence

Established static evidence includes:

- Four inputs and a pointer-shaped result.
- Four-byte table fields, slots, and record words.
- An eight-byte record request.
- Existing-value replacement without direct count increment.
- New-record publication before value and key writes.
- Signed threshold comparison before count increment.
- Metadata and replacement-array publication before status inspection.
- Two distinct growth-status checks.
- Traversal and the old-array call controlled by the first check.
- Non-null return versus count increment controlled by the final check.
- Old-slot rereading after relookup.
- No visible rollback.

The table interpretation and allocation/release terminology express inferred intent. Dependency internals, ownership, retained-reference behavior, and broader validity guarantees remain unresolved. No runtime execution or tests have been performed.
