# F-9e62624e89e5

## Purpose

F-9e62624e89e5 converts a sequence of unsigned 16-bit palette indices into three byte-addressed output planes. Each palette lookup supplies three 8-bit components from the low 24 bits of a 32-bit word.

For dimensions whose loop-counter arithmetic remains representable, the function processes two indices at a time. It emits two luma bytes per pair and, on even-numbered rows, one byte in each chroma plane. Both chroma bytes derive exclusively from the second index of the pair. There is no horizontal or vertical averaging.

The coefficients suggest a limited-range RGB-to-luma/chroma conversion. That interpretation is inferred intent; the component positions, equations, sampling positions, and access order below define the established behavior.

The function contains no explicit validation, allocation, capacity checking, or error reporting.

\[

An index \(k\) is read as an unsigned 16-bit value. Its palette word is read at:

\[

Thus palette entry zero occupies the word immediately after the header. The header determines the index-stream start; it does not bound or validate palette lookups.

Interpreting \(N\) as a palette-entry count is plausible but not enforced. Negative values and values producing invalid pointer arithmetic receive no explicit handling.

## Behavior

### Entry and nonpositive dimensions

The header is read and the initial index-stream pointer is formed before the height check. Strides and the initial luma-base adjustment are also computed before that check.

If \(H\leq0\), there are no index reads, palette reads, or output stores. This does not remove the requirement for a readable header or establish the validity of arbitrary header-derived pointer arithmetic.

If \(H>0\) and \(W\leq0\), the row loop runs without entering the pair-processing loop. No index or palette entry is read, and no output byte is written. Row-address arithmetic still occurs.

Neither condition produces an error status.

### Observable order within a pair

For every pair reached, the established data-access order is:

1. Read the first 16-bit index.
2. Read its 32-bit palette word.
3. Store its luma byte.
4. Read the second 16-bit index.
5. Read its 32-bit palette word.
6. Store its luma byte.
7. If the row is even-numbered, store the first chroma byte.
8. On that same row, store the second chroma byte.

This order matters under aliasing. In particular, the first luma store can change storage that will subsequently be read as the second index or its palette entry.

Both chroma outputs use components already obtained from the second palette read. Neither requires a further palette read after the second luma store.

### Odd-width consequences

For odd widths within the finite-traversal domain, every luma row receives \(W+1\) bytes. The luma stride accommodates this extra byte for these widths.

Each chroma-writing row receives \(Q\) bytes, but the chroma stride is computed from \(\lfloor W/2\rfloor\), not \(Q\). Chroma rows can therefore overlap:

- At \(W=1\), \(S_C=0\), so every chroma-writing row targets the same byte in each chroma plane.
- At \(W=9\), \(S_C=4\), but each chroma-writing row stores five bytes. Its last byte shares an address with the first byte of the next chroma-writing row.

No correction or rejection is present.
