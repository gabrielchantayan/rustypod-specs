# F-9f2bdd821345

## Purpose

F-9f2bdd821345 updates a destination, sequence-like object from a source object and returns the destination object’s address.

The established behavior has three nontrivial paths: allocate replacement storage, extend within existing storage, or copy into existing storage and dispose of the old suffix. Passing the same object address as both operands is a no-op.

The apparent intent is assignment of a sequence of four-byte elements. That interpretation is inferred from the storage layout, four-byte traversal, and dependency calls. Element semantics, allocation ownership, and dependency behavior are not established by the supplied evidence.

A significant observable detail is that the third destination field is not consistently preserved as a storage limit. After the non-extending, storage-reuse path, it is set equal to the destination’s new logical end. After the extending, storage-reuse path, it is left unchanged by this function. This distinction is part of the contract, not normalized into conventional container behavior.

### Object layout

The supplied representation uses three consecutive 32-bit fields:

| Byte offset | Contract name | Observed role |
|---|---|---|
| 0 | Begin | Element-storage address. |
| 4 | End | One-past-logical-end address. |

The evidence supports a 32-bit address-and-integer representation. It does not establish portability to wider pointers, mixed-width metadata, or a different element stride. Byte order is not established.

“Source length” and “destination length” below mean results returned by F-cedf3cfba98d. They are not assumed to be calculated from any particular fields.

### Preconditions

For meaningful sequence-like behavior, the objects and referenced ranges must be valid for all operations actually performed:

- On a non-self call, metadata must be readable, and destination metadata must be writable.
- Destination and source storage must satisfy the dependencies’ respective access requirements.
- Disposal ranges must be reachable by repeated four-byte increments from their starting addresses.
- Address arithmetic and length-to-byte conversion must produce valid ranges.
- Any overlap between distinct objects’ storage must be supported by the dependencies.

These requirements are not checked by this function.

When the two object addresses are equal, the function returns without reading their metadata or calling dependencies. This establishes an address-equality fast path, not general null-pointer support.

## Behavior

### Self-assignment

The first decision compares the object addresses.

If equal, the function returns the destination address immediately. It does not inspect lengths, allocate storage, copy elements, dispose of elements, or write destination fields.

Distinct object addresses do not trigger this protection even if their storage overlaps or is identical.

### Storage-availability decision

For distinct objects, the function first calls F-cedf3cfba98d on the source.

It then compares that unsigned 32-bit result against the destination’s available-slot calculation: the difference between Limit and Begin, shifted right by two and then interpreted as unsigned.

The supplied expression performs the difference and shift through signed-looking 32-bit operations before the unsigned comparison. For valid, nonnegative, four-byte-aligned ranges within the supported arithmetic domain, this corresponds to a four-byte slot count. Negative differences, signed overflow, and nonaligned addresses are not validated and must not be assigned ordinary container semantics.

If the available-slot count is less than this first source-length result, the function takes the replacement-storage path. Otherwise, it takes one of the storage-reuse paths.

### Replacement storage

The replacement-storage path performs the following observable operations in order:

1. Call F-cedf3cfba98d on the source again.
2. Call F-cedf3cfba98d on the destination.
3. Derive a requested slot count from these two results.
4. Call F-871e64ddc6de with the requested slot count shifted left by two and a second argument of zero.
5. Call F-001bc2470f97 with the source’s then-read Begin and End, the returned storage address, and the destination object address.
6. Read and retain the destination’s End, and read its Begin to start a forward disposal traversal.
7. Call F-e0bf74703fb9 once at each address from that starting Begin up to, but excluding, the retained End, advancing by four bytes.
8. Call F-ff1bdc376dcd using the destination’s then-read Begin, its then-calculated slot capacity, and zero.
9. Write the replacement storage address into destination Begin.
10. Call F-cedf3cfba98d on the source again.
11. Write destination End using the destination’s then-read Begin plus four times this latest source-length result.
12. Write destination Limit using a fresh read of destination Begin plus four times the selected requested slot count.
13. Return the destination address.

The requested slot count is selected using unsigned 32-bit arithmetic. Let the destination-length result be the growth basis. Two candidates are formed:

- Growth basis plus 32.
- Growth basis plus its right shift by one plus its right shift by three.

The larger candidate is retained, then compared with the source-length result obtained at the start of this path. The selected request is the larger of that source length and the retained candidate.

For ordinary small lengths, the second candidate approximates 1.625 times the growth basis, rounded down by the component shifts. It is not a multiplication carried out in wider arithmetic.

All additions and the final left shift operate at 32-bit width. Overflow is not checked. Consequently, this rule is not an unbounded mathematical maximum: wrapped candidates or a wrapped byte request can be smaller than their apparent mathematical values.

The allocation-like result is not checked for null or any other failure indicator before it is passed to F-001bc2470f97.

Crucially, the destination fields used for disposal and release are read after F-001bc2470f97 returns. The function does not preserve an independent pre-call snapshot of the old range. If that dependency changes destination metadata, subsequent operations use the changed metadata.

### Reuse with extension

When the initial availability check succeeds, the function calls F-cedf3cfba98d first on the destination and then on the source. If the returned destination length is smaller, it takes the extension path:

1. Query destination length again; this result determines the prefix boundary.
2. Call F-3f67e96e86df on the source range from source Begin through source Begin plus four times that prefix length, targeting destination Begin.
3. Query source length again.
4. Write destination End as the destination’s then-read Begin plus four times this latest source-length result.
5. Call F-001bc2470f97 on the remaining source range, starting at source Begin plus four times the retained prefix length and ending at the source’s then-read End. Its target is destination Begin plus the same byte offset; the destination object address is also passed.
6. Return immediately.

This function does not explicitly write destination Limit on this path. Dependency-side changes remain possible.

The End write occurs before the suffix operation. Therefore, the destination metadata can describe the extended logical range before F-001bc2470f97 has completed its work.

The return value of F-3f67e96e86df is ignored on this path.

### Reuse without extension

If the queried destination length is at least the queried source length:

1. Call F-3f67e96e86df using the source’s current Begin and End and the destination’s current Begin.
2. Retain its returned address as the start of the suffix-disposal traversal.
3. Read and retain destination End.
4. Call F-e0bf74703fb9 at each address from the returned address up to, but excluding, the retained End, advancing by four bytes.
5. Query source length again.
6. Calculate a new end address from the destination’s then-read Begin plus four times that result.
7. Write that address to destination End.
8. Write the same calculated address to destination Limit.
9. Return the destination address.

The returned address from F-3f67e96e86df controls disposal; it is not replaced with an independently calculated destination-prefix boundary.

Equal source and destination lengths take this path, not the extension path. Even when no suffix is disposed, the function explicitly sets Limit equal to the new End.

## Side effects

The function explicitly writes only destination metadata. Dependencies receive storage addresses and, for F-001bc2470f97, the destination object address; their effects can be broader.

Established ordering constraints include:

- Replacement copying occurs before disposal and release calls.
- Replacement Begin is committed after the release call.
- Extension End is committed before the suffix operation.
- On reuse without extension, suffix disposal precedes the final End and Limit writes.
- Disposal proceeds in increasing four-byte address order.

No source metadata writes are explicit. This is not a guarantee that the source remains unchanged: storage may alias, dependencies may have global access, and dependency side effects are unspecified.

The apparent ownership pattern is allocation, population, disposal of old elements, and release of old storage. Actual ownership transfer, element destruction, and deallocation semantics remain unknown. In particular, F-ff1bdc376dcd receives a slot-count-like quantity rather than the byte count passed to F-871e64ddc6de; their argument units must not be assumed interchangeable.

There are no explicit error returns, bounds checks, rollback operations, or failure cleanup paths. If a dependency fails to return normally, successful completion and consistent metadata are not established. The function does not itself provide transactional assignment.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume stable length results, well-formed nonoverlapping ranges, nonoverflowing arithmetic, normal dependency returns, and no unexpected metadata mutation by dependencies.

### Identical object addresses

Given equal destination and source object addresses, the expected result is that same address, with no dependency calls and no metadata access or modification.

### Replacement selected by insufficient capacity

Suppose destination Begin-to-Limit represents eight slots, destination length is six, and source length is ten.

Replacement storage is selected. The two growth candidates are 38 and 9, so the requested slot count is 38 and the allocation-like byte argument is 152.

If F-001bc2470f97 leaves the old destination metadata unchanged, the six old slots are disposed in forward order, followed by the release-like call with slot count eight. On normal completion, Begin identifies replacement storage, End is 40 bytes beyond Begin, and Limit is 152 bytes beyond Begin.

### Extension within available storage

Suppose destination length is three, source length is five, and available storage is eight slots.

The prefix operation covers three source slots. Destination End is then written to Begin plus 20 bytes. The suffix operation covers the remaining two source slots. No release-like call or explicit Limit write occurs.

### Shorter source

Suppose destination length is five, source length is two, and available storage is eight slots. If F-3f67e96e86df returns destination Begin plus eight bytes, the three trailing slots are disposed in ascending address order.

The final End and Limit both equal destination Begin plus eight bytes. The original eight-slot limit is not preserved in the metadata.

### Equal lengths with spare storage

Suppose both lengths are four and available storage is ten slots. If the range operation returns the existing End, no suffix-disposal calls occur. End and Limit are nevertheless both set to Begin plus 16 bytes.

### Empty source

For a stable zero-length source, the non-extending reuse path is selected under a valid nonnegative capacity interpretation. If the range operation returns destination Begin, all old logical elements are disposed. Final End and Limit both equal Begin.

This path contains no explicit storage-release call.

### Changed dependency results

If an early source-length query permits reuse but a later query returns a length exceeding available storage, this function does not introduce a new capacity check. Acceptance of a safe sequence result therefore requires dependency stability or another external guarantee; safety is not established for this case.
