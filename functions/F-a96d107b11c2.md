# F-a96d107b11c2

## Purpose

F-a96d107b11c2 conditionally performs two ordered calls involving a supplied object. It first compares that object’s address with a pointer stored in a context record. If the addresses differ, it examines a masked field in the supplied object. Only when the masked value differs from `0x0800` does the visible path proceed toward the calls.

The first call is to F-96f4ed7653c7. The second is an indirect call through a dispatch table obtained from the object **after the first call returns**.

The established behavior is conditional dispatch, not a proven ownership operation. The available evidence does not establish whether either call detaches, destroys, releases, notifies, or otherwise manages the object.

A null-object comparison appears in the call-selection condition, but it does not provide general null safety: when the stored pointer differs from the supplied object address, the object’s flag field is accessed before that comparison can exclude a null object.

## Behavior

### Initial comparison

The first established memory read obtains the pointer at context offset `0x34`.

That pointer is compared with the supplied object address. This is an address comparison, not a comparison of object contents.

If the addresses are equal:

- The object flag field is not read by this function.
- F-96f4ed7653c7 is not called.
- The indirect target is not resolved or called.
- The function returns without any explicit memory write.

This remains the visible branch behavior when both compared addresses are null, provided the context-field read itself is valid.

### Flag selection when addresses differ

If the addresses differ, the function reads the four-byte field at object offset `0x48` and applies mask `0x1800`.

The selected mask contains bits 11 and 12, counting the least significant bit as bit 0. The branch distinguishes exactly one masked result:

| Masked result | Effect on call selection |
|---:|---|
| `0x0000` | Does not suppress the calls |
| `0x0800` | Suppresses both calls |
| `0x1000` | Does not suppress the calls |
| `0x1800` | Does not suppress the calls |

Bits outside `0x1800` have no effect on this decision. In particular, setting both selected bits does not suppress the calls.

The source uses a pointer-typed temporary for the masked quantity. No dereference of that temporary is shown. Its relevant behavior here is the comparison of the masked result with `0x0800`; it does not establish that the field contains an address.

### Null-object ordering

The explicit non-null test occurs after the flag read on the differing-address path.

Consequently:

- A null object that equals the stored comparison pointer takes the early return path without an object-field read.
- A null object that differs from the stored pointer reaches the read at object offset `0x48` before the later null test can reject it.

The second case is not a defined, safe null-object no-op. The source does not provide recovery for an invalid read. Whether such an access traps, encounters mapped storage, or has another platform-specific consequence is not established.

For ordinary valid operation on a differing-address path, callers must supply an object whose flag field is readable.

### First call

When the addresses differ, the masked flag result is not `0x0800`, and the object is non-null, the function reads the integer-sized value at object offset `0x34`.

It calls F-96f4ed7653c7 with these arguments, in order:

1. The value read from object offset `0x34`.
2. The supplied object address.

The source does not establish the meaning of the first argument. It must not be treated as a handle, parent pointer, allocation identifier, or ownership token without additional evidence.

No return value from F-96f4ed7653c7 is inspected.

### Indirect call after the dependency

If F-96f4ed7653c7 returns normally, the function then:

- Reads the dispatch-table address from object offset `0x00`.
- Reads the callable address at dispatch-table offset `0x04`.
- Invokes that callable with the supplied object address as its sole visible argument.

These reads occur after the direct dependency returns. The indirect target is therefore resolved from the post-call object state, not from a dispatch-table address cached before the call.

If F-96f4ed7653c7 changes the object’s dispatch-table field, that changed field supplies the subsequent dispatch lookup, provided the object remains valid to access.

The function does not visibly repeat the context-pointer comparison or flag test after the first call. A dependency-induced change to those fields does not cause this function to reconsider its earlier branch decision.

The supplied evidence identifies the final transfer as an indirect call, but also reports incomplete recovery of that transfer. The call form and visible argument are the basis of this contract; the exact machine-level transfer semantics remain a documented uncertainty.

## Acceptance examples

These examples are conditional acceptance criteria derived from static evidence. They are not runtime test results.

1. **Stored pointer equals the object address.**  
   Given a readable context field containing exactly the supplied object address, the function returns without reading the object flag field or invoking either dependency.

2. **Both compared addresses are null.**  
   Given a valid context whose comparison field contains null and a null object input, the equality path returns without reading object storage.

3. **Differing addresses with masked value `0x0800`.**  
   Given valid required reads and a flag word of `0x0800`, neither call occurs. The same suppression applies to a flag word of `0x0801`, because the additional low bit is outside the mask.

4. **Differing addresses with neither selected bit set.**  
   Given a non-null, valid object and a flag word of zero, F-96f4ed7653c7 receives the object’s offset-`0x34` value and object address. If it returns and leaves valid dispatch state, the indirect call follows.

5. **Differing addresses with both selected bits set.**  
   Given the same validity conditions and a flag word of `0x1800`, both calls remain selected. Treating any occurrence of bit `0x0800` as suppression would reject this case incorrectly.

6. **Dependency changes the dispatch-table field.**  
   Given a selected path where F-96f4ed7653c7 replaces the object’s dispatch-table address and leaves valid storage, the subsequent lookup uses the replacement table.

7. **Dependency changes the flag field to `0x0800`.**  
   Given a path already selected for calls, such a change does not suppress the subsequent indirect call. No second flag test is shown.

8. **Null object differs from the stored pointer.**  
   This is not accepted as a safe no-op case. The attempted flag-field access precedes the explicit null rejection; a normal-return guarantee is unsupported.

9. **Dependency invalidates the object.**  
   Normal completion is not guaranteed. The visible continuation still requires reads through the supplied object address; no liveness check or alternate path is shown.
