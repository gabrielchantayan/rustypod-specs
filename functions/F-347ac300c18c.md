# F-347ac300c18c

## Purpose

F-347ac300c18c conditionally processes indexed entries associated with a caller-supplied context.

Its visible behavior has three principal paths:

- If the first observed provider count is zero, invoke a fallback dependency and return two writable local words.
- Otherwise, optionally invoke a preparation dependency, then compare a current index against a newly observed count. If the comparison fails, return that count and index.
- If the comparison succeeds, request range endpoints through indirect dispatch, intersect the returned range with locally established bounds, and process the accepted indices.

For each visited index, a nonnull lookup result causes a notification call before the lookup-result storage is dereferenced. The resulting object address is inspected at offset `0x40`. If that field is zero, another dependency receives the embedded context region and the address of a local word.

The result is a 64-bit concatenation whose two words have path-dependent meanings. In particular, the high word after range processing is the contents of an address-exposed local **at return**, not necessarily its value immediately after the last dependency explicitly given its address.

“Provider,” “count,” “index,” “notification,” and “object” are descriptive interpretations of use. Their application-domain meanings are not established.

## Behavior

### Initial observation and fallback

The function first reads the provider address from context offset `0x30`, then reads the provider’s count-like field at offset `0x2b8`.

If that field is zero, the function:

1. Reads the fallback-record address from context offset `0x24`.
2. Reads the word at that record’s offset `0x08`, initializing the local high return word.
3. Reads context offset `0x24` again, initializing the local low return word.
4. Calls F-62f5664b0a3b with an unidentified stack address, the embedded context-region address, the high-word local’s address, and the low-word local’s address.
5. Returns the contents of those two local words after the call.

The two reads of context offset `0x24` are distinct. Their equality is not guaranteed by the body. For example, the high word can originate from a record selected by the first read while the low word comes from a different second observation.

F-62f5664b0a3b can modify both return words through the supplied addresses. Its ordinary return value is not used. This path performs no preparation call, range dispatch, or indexed lookup.

### Optional preparation and fresh observations

When the initial count is nonzero, the function reads context offset `0x38`.

If that value is nonzero, it calls F-3ab4d02fd54b with:

- The context address.
- Zero.
- A separately read value from context offset `0x38`, decreased by one.

The conditional test and argument formation therefore use separate reads. The call’s return value is ignored.

After this optional call, the function reloads the provider address and reads its count. It then reads the unsigned current index at context offset `0x3c`.

These later observations control range entry. The initial count selects only the fallback versus non-fallback branch. A later zero count does not cause fallback.

### Unsigned range-entry test

The current index is compared, as an unsigned 32-bit quantity, with the later count minus one under unsigned 32-bit arithmetic.

If the index is not strictly below that threshold, the function returns immediately:

- High word: the later observed count.
- Low word: the observed current index.

No range dispatch or lookup occurs.

For positive counts and ordinary nonnegative indices, this usually tests whether there is an index after the current one. That interpretation is not valid for every 32-bit representation. A zero count produces the unsigned threshold `0xffffffff`.

If the comparison succeeds, the function establishes:

- A candidate lower bound from current index plus one.
- An original upper bound from count minus one.
- A writable range-start word initialized to the range seed.
- A writable range-end word initialized to the original upper bound.
- A separate high-word local initialized to the candidate lower bound.

The arithmetic limitations described under **Uncertainties** apply at signed boundaries.

### Indirect range request

The indirect dependency, designated D-01 in this contract, is selected through the dispatch table reached from context offset `0x30`, at table offset `0x0c`. It receives a provider address and the addresses of the writable start and end words.

Dispatch selection and the provider argument involve reads of the context’s provider field. Their exact relative evaluation order is not established by the supplied representation; they must not be described as one permanently cached provider observation.

The operation can replace either endpoint. Its ordinary return value is not used as an established result.

Following dispatch, the low-word working result is initialized from the updated range start.

### Range acceptance

Range processing requires all of these conditions:

- Updated start is not `-1`.
- Updated end is not `-1`.
- Candidate lower bound is no greater than updated end, using signed comparison.
- Updated start is no greater than original upper bound, using signed comparison.

For an accepted range, the effective bounds are:

- Lower: the greater of candidate lower bound and updated start.
- Upper: the lesser of original upper bound and updated end.

The loop body executes only while the signed lower bound is no greater than the signed upper bound. Reversed endpoints are not reordered. They can pass the preliminary conditions but still produce an empty effective interval.

If no iteration occurs, the body returns the updated range start as the low word and leaves its initialized high-word local unassigned after dispatch. No address of that high-word local has been supplied to a dependency on this path. The start sentinel `-1` therefore appears as low word `0xffffffff`, not as a separately constructed error code.

A secondary register-derived value appears in the supplied representation when the start is `-1`. Because that same sentinel independently prevents processing, the secondary value does not establish an additional accepted range or visible return meaning.

### Per-index processing

For each visited index, the visible order is:

1. Reload the provider address from context offset `0x30`.
2. Call F-36b67cc7bb38 with that provider and the index.
3. Set the low-word working result to zero.
4. If the lookup returned null, finish this iteration.
5. Otherwise, reload the provider address and call F-dc07b121bb37 with that provider and the same index.
6. After the notification returns, read the first 32-bit word through the lookup-result address. Treat that word as an object address and assign it to the low-word working result.
7. Read the object’s field at offset `0x40`.
8. If that field is zero, assign the object address to the high-word local, pass the embedded context-region address and the high-word local’s address to F-33f2303f9bf9, and assign that dependency’s 32-bit return to the low-word working result.

The lookup-result storage is not dereferenced before F-dc07b121bb37. That dependency can therefore affect which object address is subsequently observed, subject to the storage remaining valid.

A nonzero object field suppresses only F-33f2303f9bf9. It does not suppress notification.

A null lookup does not terminate traversal. Neither does any particular return value from F-33f2303f9bf9. Subject to the arithmetic boundary uncertainty, indices advance by one in ascending signed order through the inclusive effective upper bound.

### Return after range processing

On normal completion, the low word reflects the final iteration:

- Zero if its lookup returned null.
- The observed object address if its field at `0x40` was nonzero.
- The 32-bit return of F-33f2303f9bf9 if that dependency was invoked.

The high word is the high-word local’s contents **when the return is assembled**.

The body initializes that local to the candidate lower bound and overwrites it with an object address immediately before each F-33f2303f9bf9 call. Null lookups and nonzero object fields do not themselves assign to it.

Those facts do not establish preservation across later calls. Once F-33f2303f9bf9 receives the local’s address, no supplied dependency contract prevents it from retaining or sharing that address during the enclosing invocation. A later lookup, notification, or further processing dependency may consequently modify the same storage.

Thus, even the final null-lookup iteration can accompany a changed high word: its lookup dependency may write through a previously retained pointer before returning null. The body then sets only the low result to zero.

## Side effects

Dependencies may mutate external state or address-exposed locals. No supplied contract establishes preservation of:

- Context or provider fields.
- Lookup-result storage or object contents.
- Globals.
- Writable endpoint or return-word storage.
- The high-word local after its address escapes.

The high-word pointer’s exposure is not limited, by any supplied contract, to the duration of the individual F-33f2303f9bf9 call. Retention and use during subsequent calls in the same enclosing invocation remain possible. Use after the enclosing invocation returns has no established validity; this contract grants no extended lifetime.

No ownership transfer, allocation, retention, or release convention is established for any passed or returned address. The body itself shows no allocation or explicit deallocation.

Safe execution requires every selected-path access to valid storage. In particular, a nonnull lookup result must remain readable across notification, and the word read from it must designate an object suitable for the `0x40` access.

There is no visible exception handling, rollback, or explicit error-reporting mechanism. Invalid memory, dependency failures, and nonlocal exits have no established recovery behavior.
