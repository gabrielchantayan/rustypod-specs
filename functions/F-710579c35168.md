# F-710579c35168

## Purpose

F-710579c35168 advances a mutable traversal state toward a preceding position and returns the 32-bit word obtained at that position. When the current position becomes negative after decrementing, it searches for a preceding object through dependency F-64f743a2929d. A successful object transition selects that object's last indexed position before obtaining the return word through an indirect dependency.

The following behavior is established by the supplied static representation:

- The position field is decremented before either lookup path is selected.
- A nonnegative decremented position uses the current object without calling F-64f743a2929d.
- A negative decremented position starts a descending-key search.
- A lookup result whose field at byte offset 12 is zero terminates the search; it is not skipped.
- A nonzero lookup result with a nonzero field at byte offset 12 replaces the current object.
- Successful retrieval returns a word read through a pointer returned by an indirect call.
- An unsuccessful search increments the then-current position field and returns zero.

The interpretation of the state as a reverse iterator, and of the object field at offset 12 as an element count, is inferred intent rather than an independently established type contract.

## Behavior

### 1. Entry mutation and path selection

The function reads the position at traversal-state offset 4, subtracts one, and writes the result back to that field. This write occurs before any dependency call.

The resulting value is tested as signed:

- If nonnegative, execution proceeds directly to indirect retrieval.
- If negative, execution starts the preceding-object search.

The supplied representation uses 32-bit integer quantities. Ordinary cases can be described using signed 32-bit arithmetic, but overflow behavior at the signed limits is not established independently of that representation. In particular, the minimum signed position must not be assigned a wrapping or trapping behavior without additional evidence.

### 2. Retrieval from the current object

For either a nonnegative entry result or an accepted replacement object, retrieval follows this pointer chain:

1. Read the current object address from traversal-state offset 0.
2. Read the dispatch-table address at object offset 8.
3. Read the callable address at table offset 64.
4. Invoke that callable dependency.
5. Read one 32-bit word from the address it returns.
6. Return that word unchanged.

The displayed indirect invocation supplies these argument values:

- The address at current object offset 8.
- The current position from traversal-state offset 4.
- The callable address itself.
- The function's fourth argument.
- Two additional values whose origins and semantics are not established by the supplied body.

The first four values should not be reduced to an assumed conventional two-argument method interface. Conversely, the displayed extra values do not prove a particular source-level prototype or calling convention.

There is no null-result check before reading the returned word. If the dependency returns an invalid address, no successful zero-valued fallback is established.

### 3. Preceding-object search

The search begins with an internal 32-bit distance of one. Its first lookup is unconditional once this path is entered; the lower boundary is not checked beforehand.

Each lookup calls F-64f743a2929d with:

- The unchanged second argument to this function.
- The current object's field at offset 32 minus the current distance.

After the dependency returns, the internal distance is incremented before the search result is processed.

A nonzero result is interpreted as a candidate object address. Its 32-bit field at offset 12 is read:

- If zero, the search terminates unsuccessfully immediately.
- If nonzero, the candidate address is written to traversal-state offset 0. The candidate's field at offset 12 is then read again, one is subtracted, and the result is written to traversal-state offset 4. Execution proceeds to indirect retrieval.

Thus, candidate acceptance uses a zero/nonzero test, not a positivity test. A negative nonzero candidate value is accepted. There is no second nonnegative-position gate between installing a candidate's position and making the indirect call.

The second read of the candidate field is part of the displayed behavior. It must not be replaced in the contract with a promise that the value tested and the value used for the new position are identical under aliasing or external mutation.

If the lookup returns zero, the function evaluates whether to continue. It reads the lower boundary and the then-current object's numeric anchor, and compares:

- Lower boundary, signed;
- Against numeric anchor minus the already-incremented distance, signed.

The next lookup occurs only if the lower boundary is less than or equal to that prospective key.

For stable state and non-overflowing arithmetic, the searched keys descend by one. The distinction between the unconditional first lookup and guarded later lookups is observable: the first lookup can occur even when its key is below the lower boundary.

### 4. Unsuccessful-search completion

The search fails when either:

- A nonzero candidate has a zero field at offset 12; or
- A zero result is followed by a failed continuation comparison.

On this path, the function reads the then-current position field, adds one, writes the result back, and returns the 32-bit value zero. It does not invoke the indirect retrieval dependency.

If dependencies have not modified the traversal state, this final increment reverses the entry decrement. That restoration is conditional, not an unconditional rollback guarantee.

There is no explicit write replacing the current object on the unsuccessful path. Nevertheless, the function does not guarantee that the object address remains unchanged: a dependency may have modified shared or aliased storage.

### 5. Arithmetic boundaries and termination

Position decrement, candidate-position subtraction, search-distance increment, lookup-key subtraction, and failure-position increment all operate on displayed 32-bit quantities.

Signed comparisons govern the initial position gate and the search continuation condition. Candidate acceptance, by contrast, only distinguishes zero from nonzero.

For stable objects, a finite descending range, and arithmetic that does not overflow, repeated zero lookup results eventually exhaust the search range. Unconditional termination is not established when dependencies mutate state or arithmetic crosses its representable limits. No explicit iteration limit is present.

## Side effects

### Explicit writes

The function performs these writes, in order along the applicable path:

1. Entry decrement of the position.
2. On candidate acceptance, replacement of the current object address.
3. On candidate acceptance, installation of the candidate-derived position.
4. Otherwise, on unsuccessful search, increment of the then-current position.

The lower-bound field is not explicitly written.

The object replacement precedes the candidate-derived position write. These changes are not presented as an atomic transaction.

### Dependency-visible state

F-64f743a2929d is called after the entry decrement, so it may observe that decremented position if it can access the state.

The indirect dependency is called after the selected position has been installed. On an object transition, it may therefore observe both the new current object and the new position.

Neither dependency is established to preserve traversal fields, object fields, global state, or memory reachable through the arguments. Subsequent reads use the state visible at their point of execution. The function does not snapshot the entire traversal state across calls.

The supplied expression structure does not establish a total order among every independent read used to prepare a call or comparison. The pointer-chain dependencies, explicit writes, calls, and post-call result read are established; a stronger instruction-level ordering is not.

### Ownership and errors

No allocation, deallocation, retain, release, or ownership-transfer operation is explicit in this body. Ownership effects of dependencies remain unknown.

Zero is the explicit unsuccessful-search result, but it is not a unique error indicator: successful indirect retrieval can also produce a zero word.

No exception handling, rollback after dependency failure, pointer validation, or bounds-error reporting is visible. Fault and exception behavior remains dependent on the execution environment and callees.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, assume valid addresses, stable non-aliased storage, dependencies that do not mutate traversal state, and no arithmetic overflow.

### Existing position remains usable

Given an initial position of 3:

- The position becomes 2.
- F-64f743a2929d is not called.
- The indirect dependency receives position 2.

### Successful transition to a preceding object

Given an initial position of 0, a current numeric anchor of 20, and a lower boundary of 10:

- The position first becomes −1.
- The first lookup key is 19.
- If the lookup returns a candidate whose offset-12 field is 4, that candidate becomes current and the position becomes 3.
- The indirect call is selected through that candidate.
- The word read through its returned address becomes the function result.

### Search includes a guarded boundary key

Given anchor 20, lower boundary 18, initial position 0, and zero lookup results:

- The first lookup uses key 19.
- The continuation comparison permits key 18.
- After key 18 also misses, the prospective key 17 fails the comparison.
- The position is restored to 0 and the function returns zero.

### First lookup occurs below the boundary

Given anchor 20, lower boundary 25, and initial position 0:

- Key 19 is still looked up.
- A zero result stops further lookup because prospective key 18 is below the boundary.
- A nonzero candidate with a nonzero offset-12 field is accepted despite the boundary relationship.

### Empty candidate stops rather than being skipped

Given a first lookup result identifying a candidate with offset-12 field zero:

- No subsequent lookup occurs.
- No explicit current-object replacement occurs.
- The position is restored under the stated stability assumptions.
- The result is zero.

### Negative candidate field is accepted

Given a candidate offset-12 value of −2:

- The candidate passes the nonzero test.
- The installed position is −3.
- The indirect dependency is called with that position.

Whether that indirect call supports negative positions is unknown.

### Zero-valued retrieved data

If successful indirect retrieval returns an address containing zero, this function returns zero. A consumer cannot distinguish this case from unsuccessful search using the return word alone.
