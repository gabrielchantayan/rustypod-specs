# F-802322dc1898

## Purpose

F-802322dc1898 performs one of three actions after acquiring a context and reading a 32-bit value from an input record:

- Returns immediately if the record value is zero.
- Uses the acquired context’s dispatch entry at byte offset 12 if the record value is nonzero and an incoming selector is either zero or negative under a signed 32-bit interpretation.
- Uses a size-producing dependency, the context’s dispatch entry at byte offset 8, and an external dependency if the record value is nonzero and the selector is positive under that interpretation.

The final branch conditionally writes a zero byte to an address derived from the dispatch result and the size-producing result.

A plausible intent is to obtain storage for a byte sequence and terminate that sequence. This is an inference, not an established string-copy contract: the supplied evidence does not establish the semantics of the size-producing dependency, the storage-producing dispatch entry, or the external dependency.

## Behavior

### 1. Acquire a context before examining the record

The first observable operation is a call to F-5b24edfb22c0. Its result is retained as the acquired context.

Only after that call returns does the function read the 32-bit field at byte offset 4 of the input record.

This order matters. F-5b24edfb22c0 is not skipped when the field is zero. If that dependency can change the record, the subsequent read observes the record after those effects.

No preservation of globals, object contents, or memory ownership across this call is established.

### 2. Return for a zero field

If the captured field is zero, the function returns immediately.

After that read, this branch performs:

- No dispatch-table access.
- No size-producing dependency call.
- No external dependency call.
- No explicit memory write.

The initial dependency may already have produced side effects. This branch is not an unconditional no-op.

### 3. Select the remaining branch

For a nonzero captured field, the incoming selector is classified using its 32-bit representation:

- Zero selects the dispatch entry at offset 12.
- Any value with the high bit set selects the dispatch entry at offset 12.
- A nonzero value with the high bit clear selects the size-and-storage branch.

Equivalently, the latter branch requires the selector to be positive when interpreted as a signed 32-bit integer.

The selector’s incoming value supplies no visible call target. Its apparent code-pointer type does not override these branch semantics.

### 4. Zero-or-negative-selector branch

This branch performs these ordered accesses and actions:

1. Read the dispatch-table address from byte offset 0 of the acquired context.
2. Read a callable address from byte offset 12 of that table.
3. Invoke that callable with the acquired context as the sole explicit argument.
4. Return if the call returns normally.

The record value is used to establish that this branch is reachable but is not passed as an explicit argument to this call.

The call’s return value, if any, is not used. There is no explicit memory write after it.

The available representation also contains assignments involving unrecovered machine state before this indirect call. They do not establish an additional memory effect or a different explicit call argument. Whether they reflect meaningful ABI state or reconstruction artifacts remains unresolved.

### 5. Positive-selector branch

This branch uses the record value captured before selector classification.

First, it calls F-af561b6ad9f2 with that captured value as its sole explicit argument. The returned value is represented as a 32-bit integer and is retained as the size-like result.

Only after F-af561b6ad9f2 returns does the function:

1. Read the dispatch-table address from byte offset 0 of the acquired context.
2. Read a callable address from byte offset 8 of that table.
3. Invoke that callable with three explicit arguments, in order:
   - The acquired context.
   - The size-like result.
   - A 32-bit zero.

Thus, mutations by F-af561b6ad9f2 to the acquired context or its dispatch-table reference can affect which callable is selected. The dispatch target is not visibly captured before that dependency executes.

The result of the offset-8 call is represented as a 32-bit address-bearing value.

#### Zero dispatch result

If this result is zero, the function returns immediately.

There is no call to F-unknown-03 and no explicit final byte write. Any effects of the preceding calls remain in place; the function does not visibly undo them.

#### Nonzero dispatch result

If the result is nonzero, the function:

1. Calls F-unknown-03 with three explicit arguments:
   - The nonzero dispatch result.
   - The previously captured record value.
   - The size-like result minus one.
2. After that call returns, writes one zero byte at the address formed from the nonzero dispatch result plus the size-like result minus one.
3. Returns.

The external call precedes the explicit byte write. Its return value is not used, and there is no visible success test between that call and the write.

The address used for the final write is based on the retained dispatch result, not on a replacement pointer returned by F-unknown-03.

### Arithmetic and boundary behavior

The record field, size-like result, dispatch result, and relevant address representations are 32 bits. The explicit final store is exactly one byte.

The function does not visibly validate the size-like result:

- A result of one supplies a zero third argument to F-unknown-03 and places the explicit zero byte at the dispatch result itself.
- A result of zero produces a subtraction result represented as minus one. Under a 32-bit bit-pattern interpretation, that is all bits set.
- A negative result is not rejected.
- Large positive results are not checked against the extent of the returned storage.
- Address overflow is not checked.

The evidence does not fully establish overflow semantics at the arithmetic extremes. A portable implementation must not silently treat signed overflow as defined behavior merely because the target values are represented in 32 bits. Exact wrapping, trapping, or other machine-level behavior for overflowing cases is documented_only pending stronger evidence.
