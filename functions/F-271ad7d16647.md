# F-271ad7d16647

## Purpose

F-271ad7d16647 coordinates two phases of buffer acquisition, optional in-place sample conversion, submission to an embedded consumer, callback notification, and final state cleanup.

The established behavior is a normal acquisition phase followed, under specific state conditions, by a draining phase. The phases differ in acquisition mode, handling of consumer status values, and finalization. Interpreting the data as audio and the state as playback or recording control is inferred intent, not an established dependency contract.

This specification describes static behavior only. No runtime tests have been performed.

## Interface

The function accepts one pointer to a mutable state object and returns no value.

The supplied representation uses:

- 8-bit bytes;
- 16-bit sample accesses;
- 32-bit integer fields, buffer counts, pointer representations, and opaque callback arguments.

The pointer must reference storage accessible through at least byte offset `0x468`, inclusive. This minimum extent does not establish that the embedded objects passed to dependencies are otherwise valid or sufficiently large.

## Behavior

### Entry and phase selection

The first observable dependency call is F-338d16f9ce72, with the address at state offset `0x008`. State decisions occur after that call; its possible mutations must not be ignored.

The function then reads the primary state:

- If it equals one, a zero acquisition/drain byte is changed to one. Normal acquisition proceeds whether that byte was initially zero or nonzero.
- If the primary state does not equal one, a zero acquisition/drain byte skips normal acquisition.
- Otherwise, normal acquisition proceeds.

These conditions are exact-value comparisons. A primary state other than zero or one does not receive the same treatment as either recognized value.

### Normal acquisition

Each iteration begins with:

1. F-5a1289457c41, whose result is passed to the next dependency.
2. F-ea5311aeacf1 with that result, request size `0x80000`, an output location for a buffer address, and mode zero.

The acquisition result is a 32-bit unsigned count. Zero terminates normal acquisition immediately. A zero result causes no conversion, submission, notification, or per-buffer completion calls.

A nonzero result enters the conversion and submission path. Neither primary state nor acquisition/drain state is rechecked to decide whether to continue this loop. A callback clearing those bytes does not itself stop normal acquisition; termination still depends on a subsequent zero acquisition result or nonlocal behavior outside this contract.

### In-place conversion

The width and conversion selectors choose among four behaviors. Transformation lengths are fixed; they are not bounded by the returned count.

#### Width equals eight, conversion selector equals two

The function reads `0x40000` consecutive 16-bit values and writes `0x40000` bytes back at the start of the same buffer.

For each value, the output is its high byte shifted into an unsigned-byte-style representation by adding 128 modulo 256. Equivalently, the high byte’s most significant bit is toggled.

- Read span: `0x80000` bytes.
- Write span: `0x40000` bytes.
- Submitted count: original count divided by two, rounded down.

#### Width equals eight, conversion selector is anything other than two

The function reads `0x20000` pairs of signed 16-bit values. For each pair:

- Each value is independently halved using an arithmetic right shift.
- The two halved values are added.
- The output byte is the high byte of that sum, with 128 added modulo 256.

Independent halving matters for negative odd values. This is not generally equivalent to adding first and then dividing by two.

- Read span: `0x80000` bytes.
- Write span: `0x20000` bytes.
- Submitted count: original count divided by four, rounded down.

#### Width does not equal eight, conversion selector equals one

The function reads `0x40000` pairs of signed 16-bit values. Each pair is reduced to one signed 16-bit value by independently arithmetic-shifting each input right by one and adding the results.

- Read span: `0x100000` bytes.
- Write span: `0x80000` bytes.
- Submitted count: original count divided by two, rounded down.

The one-mebibyte read span is larger than the `0x80000` acquisition request. This discrepancy is established behavior, not a corrected or inferred bound.

The sum lies between −32768 and 32766, so this particular operation fits a signed 16-bit result.

#### Width does not equal eight, conversion selector is anything other than one

The buffer and count are left unchanged by the visible conversion logic.

#### Ordering and arithmetic

Elements are processed in increasing index order. Each source value or pair is read before the corresponding compacted output is written. The output occupies the beginning of the input buffer; storage beyond the compacted output is not cleared.

Count scaling uses unsigned right shifts. Odd counts therefore truncate. A nonzero acquisition count can become zero after conversion, but submission still occurs.

The supplied representation establishes native 16-bit accesses, not a portable byte-order contract.

### Submission and normal-phase status handling

After conversion, the function calls:

1. F-bfade2068003 with `0x30` and zero.
2. F-7cdc14cc6298 with the embedded object at `0x010`, the acquired buffer address, the address of the mutable 32-bit count, and one.

The second dependency returns a status. It may also modify the count through the supplied address. No visible decision here depends on that modified count.

Status two receives special handling before ordinary status notification.

If the refill callback is absent:

1. F-17a48f8c05f3 is called with the embedded object at `0x010`.
2. The primary state is written to zero.
3. The acquisition/drain byte is written to zero.

If the refill callback is present:

1. The callback receives the arguments defined in the interface.
2. F-0629a935adb3 is called with the state pointer, the temporary buffer, current 32-bit values from `0x040`, `0x044`, and `0x048`, the current byte at `0x468`, and one.

Those state fields are read after the refill callback returns. Callback changes can therefore affect restart arguments. No validation of produced contents or produced length is visible.

After status-two handling, the function checks whether the status callback is present. This check occurs after finalization or restart, so it observes any state changes those dependencies make.

If the status callback is present and status is nonzero, F-5a5e4c36dddf is called first. Callback pointer and context selection then follow:

An unrecognized nonzero status still causes F-5a5e4c36dddf when the status callback was present at the check.

3. F-85722f62e20a with `0x30` and `1000`.

### Drain eligibility and draining

After normal acquisition ends, or when it was skipped, draining is considered only if the primary state is exactly zero.

Given that primary state, draining occurs if either:

- The acquisition/drain byte equals one; or
- That byte does not equal one and the drain-request byte equals one.

The drain-request byte need not be read when the acquisition/drain byte already equals one. Other nonzero flag values do not satisfy these exact-one conditions.

On entry to draining, the acquisition/drain byte is written to zero. Each iteration then uses the same acquisition sequence, request size, conversion rules, and submission sequence as normal acquisition, except acquisition mode is one.

A zero acquisition count ends the drain loop immediately.

Drain-phase status handling differs:

| Submission status | Drain-phase event, if callback present |
|---:|---:|
| 0 | No notification |
| 1 | 2 |
| Any other value | 1 |

There is no refill callback, restart call, status-two-specific state clearing, or F-5a5e4c36dddf call in this phase.

Each completed nonzero drain iteration performs the same three per-buffer completion calls as the normal phase.

After the drain loop ends, including when its first acquisition returns zero, the function calls:

1. F-bfade2068003 with `0x30` and zero.
2. F-17a48f8c05f3 with the embedded object at `0x010`.
3. F-85722f62e20a with `0x30` and `1000`.

Drain eligibility is not reevaluated inside the loop.

### Final cleanup

On every ordinarily returning path:

1. The drain-request byte is written to zero.
2. The release-request byte is read.
3. If it is nonzero, it is written to zero, then F-5a1289457c41 and F-6eec02e32132 are called in that order.
4. F-1333331b2da1 is called with the address at state offset `0x008`.

The function does not explicitly normalize any other state at exit. Dependencies called after these writes may modify state again; their preservation is unknown.

## Side effects

Established effects include:

- Conditional state-byte writes described above.
- In-place modification of acquired buffers.
- Consumer submission with a writable count argument.
- Optional application callbacks.
- Conditional consumer finalization, restart, and release-related calls.
- Entry and exit calls involving the embedded object at `0x008`.

No explicit error value is returned. Acquisition zero is treated as phase completion without distinguishing exhaustion from failure. Submission statuses are handled only as specified; unknown statuses are neither rejected nor returned to the caller.

There is no visible iteration limit, retry limit, exception handling, or recovery from invalid memory or invalid callback pointers. A continually nonzero acquisition result can keep either phase running indefinitely.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed tests. They assume dependencies return normally and preserve state except where stated.

1. **Inactive entry without drain request.**  
   With primary state zero and both acquisition/drain and drain-request bytes zero, no acquisition or submission occurs. Final drain-request clearing, conditional release handling, and the exit dependency still occur.

2. **Active entry with immediate exhaustion.**  
   With primary state one and acquisition/drain byte zero, that byte becomes one. If mode-zero acquisition immediately returns zero and primary state remains one, draining is skipped.

3. **Normal status two without refill.**  
   A nonzero buffer followed by submission status two causes consumer finalization and clears primary and acquisition/drain state. If status notification is enabled, event three follows the normal-phase pre-notification dependency. Normal acquisition still attempts another iteration.

4. **Refill changes restart fields.**  
   On normal status two with a refill callback, changes that callback makes to the three 32-bit restart fields and the byte at `0x468` are reflected in the subsequent restart call.

5. **Eight-bit conversion boundaries.**  
   For width eight and selector two, 16-bit patterns `0x0000`, `0x7fff`, `0x8000`, and `0xffff` produce bytes 128, 255, 0, and 127 respectively, subject to native sample interpretation.

6. **Independent signed halving.**  
   A signed pair −1 and +1 produces −1 in the 16-bit combining path, not zero. The corresponding eight-bit combining output is 127.

7. **Short reported count does not shorten conversion.**  
   With width eight, selector two, and acquisition count one, the function still performs the fixed `0x80000`-byte source read span and submits count zero. Storage validity must cover the fixed span.

8. **Wider non-eight-bit combining path.**  
   With width unequal to eight and selector one, safe execution requires the full `0x100000`-byte readable span despite the smaller acquisition request.

9. **Different status-two semantics while draining.**  
   Drain-phase submission status two produces event one when a status callback exists. It does not invoke refill or immediately finalize for that status.

10. **Empty drain still finalizes.**  
    With primary state zero and acquisition/drain byte one, draining clears that byte. An immediate zero mode-one result still leads to the three drain-finalization calls.

11. **Exact flag values matter.**  
    With primary state zero, acquisition/drain byte two, and drain-request byte two, draining does not occur. A release-request byte two nevertheless triggers final release handling.
