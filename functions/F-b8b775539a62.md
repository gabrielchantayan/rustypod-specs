# F-b8b775539a62

## Purpose

F-b8b775539a62 examines a byte-encoded, segmented mapping table using a supplied unsigned 32-bit candidate.

Its behavior depends on a mode argument:

- **Zero mode:** inspect the supplied candidate without updating its storage or returning the computed mapping.
- **Nonzero mode:** search forward from the supplied candidate and write the first candidate whose computed mapping is nonzero.

The successful output is the **candidate**, not its mapped value. Search ordinarily begins strictly above the input; unsigned 32-bit wraparound makes an input of `0xFFFFFFFF` begin at zero instead.

The table resembles a segmented 16-bit character mapping. That domain interpretation is inferred intent, not an established requirement. No particular file format, encoding, or meaning of a mapped value is established.

## Interface

The function accepts three arguments and has no return value.

| Input | Representation | Meaning |
|---|---|---|
| Context address | 32-bit address-bearing argument | Identifies storage containing a 32-bit table address at byte offset `0x10`. |
| Candidate location | Address of a native unsigned 32-bit object | Supplies the initial candidate and receives a candidate on successful nonzero-mode search. |
| Mode | 32-bit integer | Zero selects single-candidate inspection; any nonzero value selects forward search. |

The context’s table-address field and the candidate object are read as native 32-bit objects. Table words are assembled from individual bytes in **big-endian** order.

### Memory preconditions

The function does not check memory validity. Defined execution requires:

- A readable table-address field in the context.
- A readable candidate object.
- Readable table bytes at every address reached by the selected path.
- A writable candidate object if the search reaches its successful final store.
- Native object accesses and address calculations valid for the execution environment.

No table length, output capacity, error destination, or status result is provided.

These access requirements do not establish ownership. The owners of the context, table, and candidate storage, and the parties responsible for their lifetimes, are unknown.

### Table organization

Use the following descriptive quantities:

- **B:** the table address captured from the context.
- **H:** the unsigned 16-bit big-endian word at `B + 6`.
- **N:** H shifted right by one, ranging from zero through 32767.
- **A:** H with its least significant bit cleared, so that `A = 2N`.

An odd H is not rejected. Its low bit does not affect N or A.

During ordinary traversal, zero-based segment index **j** identifies these words:

| Field | Address | Interpretation |
|---|---|---|
| Upper endpoint | `B + 0x0E + 2j` | Inclusive unsigned 16-bit upper bound |
| Lower endpoint | `B + 0x10 + A + 2j` | Inclusive unsigned 16-bit lower bound |
| Adjustment | `B + 0x10 + 2A + 2j` | Unsigned 16-bit modular adjustment |
| Mapping offset | `B + 0x10 + 3A + 2j` | Unsigned 16-bit selector or relative byte displacement |

There is a two-byte gap between the nominal upper-endpoint array and the lower-endpoint array. The function does not explicitly inspect this gap.

The upper-endpoint formula applies only until traversal encounters a matching segment whose mapping offset is `0xFFFF`. That case changes the upper-endpoint cursor as described below. The lower-endpoint, adjustment, and mapping-offset locations retain their ordinary progression.

## Behavior

### Initial reads and empty table

The function performs these initial reads in order:

1. Capture the table address from the context.
2. Capture the initial candidate from its storage.
3. Read H from the captured table.

The internal mapping result initially equals zero.

If N is zero, the function returns immediately. It does not increment the candidate, inspect segment fields, or write the candidate object. Both H equal to zero and H equal to one produce this outcome.

The captured table address and initial candidate are not subsequently reloaded from their original locations.

### Candidate selection and range

In zero mode, the function inspects the initial candidate without incrementing it.

In nonzero mode, it increments the internal candidate before the first inspection and before every subsequent inspection. Incrementing uses unsigned 32-bit arithmetic.

Consequences include:

- Input `0xFFFFFFFF` wraps to zero before inspection.
- Input `0xFFFF` advances to `0x10000`, which is outside the inspected range.
- Every input above `0xFFFF` other than `0xFFFFFFFF` remains outside the inspected range after its first increment.

Only candidates from zero through `0xFFFF`, inclusive, reach segment inspection. An out-of-range candidate returns without a candidate-store operation on reachable execution paths.

The range check occurs after the initial context, candidate, and H reads, but before segment fields are read.

### Segment traversal

Each candidate starts a fresh traversal, with:

- The upper-endpoint cursor at `B + 0x0E`.
- The lower-endpoint cursor at `B + 0x10 + A`.
- A limit of N segment positions.

For each position, the function first reads the lower endpoint. If the lower endpoint exceeds the candidate, the range comparison does not read the upper endpoint.

Otherwise, the function reads the upper endpoint at the current upper cursor. A segment matches when the candidate is no greater than that endpoint. Both endpoints are therefore inclusive.

A nonmatching segment advances the lower cursor by two bytes. The upper cursor ordinarily advances by two bytes as well, but can already have been displaced by an earlier matching `0xFFFF` mapping offset.

No ordering assumption stops traversal early. The function does not validate sorted endpoints, disjoint ranges, or lower endpoints no greater than upper endpoints.

### Mapping-offset selection

After a range match, the function reads the mapping-offset word located **2A bytes after the current lower-endpoint cursor**.

There are three cases.

**Offset `0xFFFF`: continue traversal with a displaced upper cursor.**

The function reads neither an adjustment nor an explicit mapping entry for this segment.

If another segment position remains, its lower cursor advances normally by two bytes, but its upper cursor becomes the address of the mapping-offset word just read. The next upper endpoint is therefore read from that address, not from the next nominal upper-endpoint field.

Later nonmatching segments advance this displaced upper cursor by two bytes. A later matching segment with offset `0xFFFF` can displace it again.

**Offset zero: map the candidate directly.**

The provisional mapping equals the candidate. The function reads the segment’s adjustment, adds it, and retains the low 16 bits.

Traversal stops for this candidate, including when the adjusted result is zero.

**Offset from one through `0xFFFE`: read an explicit mapping.**

The explicit mapping is a big-endian 16-bit word at:

**mapping-offset-field address + offset + 2 × (candidate − lower endpoint)**

The offset is a byte displacement relative to its own field. It is not relative to B. Odd offsets are accepted; the entry is still read as two individual bytes.

The lower-endpoint bytes are read again while forming the explicit-entry addresses. The earlier range-comparison value is not necessarily reused.

If the explicit mapping equals zero:

- The internal mapping result becomes zero.
- The adjustment is not read.
- Traversal stops for this candidate.

If the explicit mapping is nonzero, the function reads the adjustment, adds it, retains the low 16 bits, and stops traversal.

### Overlaps and candidate outcome

A matching segment with offset `0xFFFF` permits examination of later segment positions, subject to its upper-cursor displacement.

Any other matching segment ends traversal for the candidate. This remains true when its explicit mapping is zero or its adjusted result is zero. A later overlapping segment cannot rescue that candidate.

If traversal reaches its segment limit without producing a mapping, the candidate’s result is zero.

In zero mode, the function returns after inspecting the one candidate. It exposes neither the mapping nor a success indication and never writes the candidate object.

In nonzero mode:

- A zero result causes inspection of the next candidate.
- A nonzero result ends the search and stores the successful candidate as a native unsigned 32-bit value.
- Advancing beyond `0xFFFF` ends the search without a store.

Failure does not write a sentinel, the last candidate inspected, or partial progress. There is at most one explicit memory write.

### Arithmetic widths

H, endpoints, mapping offsets, explicit mapping values, and adjustments are unsigned 16-bit quantities decoded from bytes.

The candidate and its increment are unsigned 32-bit quantities. Only the candidate increment’s modulo-\(2^{32}\) wraparound permits a numerically smaller candidate to be inspected after a larger input.

The final mapping is the low 16 bits of the provisional mapping plus the adjustment. The adjustment is not explicitly sign-extended. Its unsigned representation nevertheless gives the same modulo-65536 result as the corresponding signed 16-bit value.

For stable storage, a matched candidate is at least its lower endpoint. Their difference ranges from zero through 65535, and twice that difference is at most 131070; this multiplication is not truncated to 16 bits. Neither this bound nor the 16-bit offset establishes that the resulting address falls within an allocated table.

These numeric relationships do not establish valid native address arithmetic near address-space boundaries.

### Observable access order

At the level of complete expressions and control-flow decisions, the read/write order is:

1. Read the context’s table address.
2. Read the initial candidate.
3. Read H.
4. For each in-range candidate, read lower endpoints in traversal order.
5. Read an upper endpoint only when the lower-bound comparison allows it.
6. Read a mapping offset only after a range match.
7. Read explicit mapping bytes only for offsets from one through `0xFFFE`, including the lower-endpoint rereads used to locate them.
8. Read the adjustment only for a direct mapping or a nonzero explicit mapping.
9. Store the candidate only after successful nonzero-mode search.

The representation does not establish a dependable order between individual byte reads within a multi-byte expression.

Because explicit-entry address expressions reread the lower endpoint, changing table bytes can affect both entry selection and the relationship between the two fetched bytes. Stable storage is required for the coherent-word interpretation used by the mapping rules and examples.

### Aliasing and synchronization

Aliasing is not rejected. The candidate location may overlap the context or table. A successful final store can consequently overwrite shared storage; that store occurs after the reads selecting the successful candidate, and no further search iteration follows.

No synchronization, atomic table snapshot, or protection against concurrent mutation is established. If another actor modifies the candidate storage during execution, the function still searches from its captured value; no broader concurrency guarantees follow.

## Acceptance examples

These are conditional expectations derived from static evidence, not executed tests. Unless stated otherwise, all required accesses are valid and table contents remain stable.

### Empty table

If H is zero or one, N is zero. In either mode, the function reads the initial fields and returns without changing the candidate.

Even an input of `0xFFFFFFFF` is not incremented in this case.

### Direct mapping search

Suppose one segment covers 65 through 67, uses offset zero, and has adjustment one.

- Nonzero mode starting at 64 inspects 65, computes mapping 66, and stores **65**.
- Zero mode starting at 65 computes the mapping internally and performs no store.
- Nonzero mode starting at 65 begins with 66 and stores **66**.

### Adjustment cancels the candidate

Suppose one segment covers 65 through 66, uses direct mapping, and has adjustment `0xFFBF`.

In nonzero mode starting at 64, candidate 65 maps to zero modulo 65536. Candidate 66 maps to one, so the function stores **66**.

### Explicit zero and adjusted zero

Suppose a segment covers 65 through 67 and uses explicit mappings of zero, `0xFFFB`, and two, respectively. Its adjustment is five.

Starting at 64 in nonzero mode:

- Candidate 65 has an explicit zero; its adjustment is not read.
- Candidate 66 becomes zero after adjustment.
- Candidate 67 maps to seven.

The stored output is **67**, not seven.

### Overlapping ranges

Suppose two segments both match a candidate under the actual traversal cursors. The first matching segment has an offset other than `0xFFFF` and produces zero.

The second segment is not examined for that candidate. Zero mode returns without a store. Nonzero mode proceeds to the next candidate.

### Sentinel-induced displacement

Suppose N is two, making A equal to four. Relative to B:

- Nominal upper endpoints are at `0x0E` and `0x10`.
- Lower endpoints are at `0x14` and `0x16`.
- Mapping offsets are at `0x1C` and `0x1E`.

If the first segment matches and its offset is `0xFFFF`, the second position uses its lower endpoint at `0x16`. If the lower comparison permits an upper read, that read uses `0x1C`, whose stable value is `0xFFFF`.

It does not use the nominal second upper endpoint at `0x10`.

### Boundary and wraparound

With N nonzero:

- Nonzero mode starting at `0xFFFF` returns without segment traversal or a store.
- Starting at `0xFFFFFFFE` does likewise.
- Starting at `0xFFFFFFFF` inspects zero first. If zero maps to a nonzero value, the function stores **zero**.
- Starting at `0xFFFE` can succeed at `0xFFFF`. Otherwise, range exhaustion leaves the original candidate unchanged.
- Zero mode can inspect `0xFFFF`, but an input of `0x10000` returns before segment traversal.
