# F-57e2e5fe49f9

## Purpose

F-57e2e5fe49f9 selects among navigation, notification followed by navigation, delivery of a mode-dependent result, and an early return without receiver delivery. Selection depends on two acquired services, service queries, a mode value, and opaque dependencies.

Established behavior includes:

- A preferred-navigation branch requiring both a zero secondary-service query and a nonzero primary-service predicate.
- An early ordinary return when a subsequent primary-service query is nonzero.
- Distinct handling for modes 0, 1, and 2.
- Receiver operations at three different dispatch-table offsets.
- A non-returning dependency reached for a missing primary service, an unsupported mode, or a zero common-construction result.
- An ordinary return whose low 32 bits are always 1 and whose high 32 bits come from mutable local storage at return assembly.

Navigation and loading terminology is inferred from symbolic text labels. Exact application semantics, displayed text, and receiver behavior are not established.

## Interface

### Arguments and representation

The function accepts four arguments:

| Argument | Representation | Established role |
|---|---|---|
| Receiver | Object pointer | Target of branch-dependent indirect calls |
| Auxiliary A | 32-bit word | Initializes the local word used for the high return half; exposed by address during notification |
| Auxiliary B | 32-bit word | Initializes writable local storage passed by address to text construction |
| Auxiliary C | 32-bit word | Initializes writable local storage used for text construction and cleanup |

The supplied representation uses 32-bit object addresses, dispatch-table addresses, and argument words. The receiver and both services are accessed as objects whose first 32-bit field, at byte offset 0, supplies a dispatch-table address. All dispatch offsets in this contract are byte offsets, not entry indices.

The three auxiliary arguments are copied into distinct four-byte local slots before the first dependency call. The evidence does not establish a complete temporary-object layout or permit treating those slots as an independently specified aggregate.

The receiver is not directly dereferenced unless a receiver operation is reached. In particular, the primary-query early-return path does not directly access it. Reached dispatches require valid objects, readable dispatch tables, and callable entries. The secondary-service result has no explicit null check.

### Ordinary return

The returned value is 64 bits:

- Bits 0–31 contain exactly 1.
- Bits 32–63 contain the final 32-bit contents of the local slot initialized from auxiliary A.

This is a bitwise assembly, not a sign-extension rule or a branch-specific status encoding.

On the loading-notification path, the function assigns 1 to the auxiliary-A slot and passes its address to F-7cbd4a877291. The high return half is **not necessarily 1, nor necessarily the value immediately after that call**. It is the slot’s value when return assembly occurs, after the following cleanup, second text construction, receiver dispatch, and final cleanup.

F-7cbd4a877291 may retain the supplied address. Later opaque calls may consequently modify the slot through a retained pointer. Ordinary completion of those calls does not establish preservation.

On other paths, the function contains no explicit reassignment of auxiliary A and does not explicitly pass its address. Under valid local-storage use, its original value remains the high return half.

### Preconditions

Defined execution of the described paths requires:

- Valid storage and callable dispatch entries for every reached object operation.
- Dependency support for the supplied argument widths and temporary-storage protocol.
- Readable shared data wherever a direct global read is reached.
- Validity of any dependency result subsequently used as an object.

The function does not comprehensively validate these conditions. No recoverable error result for invalid pointers or invalid dispatch entries is established.

## Behavior

### Service acquisition and preferred navigation

F-af667771d6ce is called first to acquire the primary service. A zero result immediately reaches F-a817d8d58c10, which is annotated as non-returning. Secondary-service acquisition does not occur on that path.

With a nonzero primary service, F-87be4aa684d1 supplies the secondary service. The function invokes that object’s entry at offset 0x1a4, passing the object as the receiver argument.

Preferred navigation is selected only when:

- Secondary entry 0x1a4 returns zero; and
- F-479af9dba077, called with the primary service, returns nonzero.

F-479af9dba077 is skipped when secondary entry 0x1a4 returns nonzero.

On the preferred-navigation path, secondary entry 0x194 is invoked. A nonzero result causes an additional invocation of secondary entry 0xf0; a zero result skips it. The function then constructs a token associated with the symbolic label “GotoNowPlaying,” delivers that token through receiver entry 0x11c, cleans up its construction storage, and returns ordinarily.

No mode query or common result construction occurs on this path.

### Text-construction protocol

Every text construction uses F-9b9c1c7483f4 with these ordered arguments:

1. Address of the local slot initialized from auxiliary C.
2. Selected text address.
3. Address of the local slot initialized from auxiliary B.

The value returned by F-9b9c1c7483f4 is used as the token. The function does not substitute the construction-storage address or explicitly check the returned value for zero.

Cleanup is an explicit call to F-8a5aadac202f with the address of the auxiliary-C construction slot. Receiver delivery or notification precedes cleanup of the corresponding token.

The loading path performs two constructions using the same local storage and the same auxiliary-B address. There is no reset to the original auxiliary arguments between them. Mutations permitted by the opaque construction and cleanup protocol therefore remain relevant to the second construction.

### Early return and mode selection

If preferred navigation is not selected, the primary service’s entry at offset 0x9c is invoked.

A nonzero result causes an immediate ordinary return. There is no mode query, shared numeric capture, text construction, notification, common result construction, or receiver operation after that result.

A zero result allows F-9ec829d3167d to query the mode using the primary service.

After the mode query returns, the function evaluates two reads of the same shared 32-bit global:

- The first supplies a captured numeric argument.
- The second supplies the operand for a 32-bit addition of 5, producing another captured numeric argument.

The first capture precedes the second expression. Neither is delayed until a mode-specific call. The evidence does not establish an atomic snapshot or equality of the two reads. If both observe a stable value of 20, the captured arguments are 20 and 25.

The addition must not be interpreted as unbounded arithmetic. Its represented width is 32 bits; source-language overflow guarantees are not established.

Modes other than 0, 1, and 2 reach F-a817d8d58c10 **after** these numeric reads.

### Mode 0: notification or alternate delivery

Mode 0 invokes primary entry 0x9c a second time. This is a distinct observable query; the earlier zero result does not constrain its result. The second result is saved before F-40819ce9a421 is called without explicit arguments.

If F-40819ce9a421 returns zero, the function takes the notification-and-navigation path:

- It constructs a notification token.
- It assigns 1 to the auxiliary-A slot.
- It calls F-7cbd4a877291 with a value read from a notification-related global, the token returned by construction, and the auxiliary-A slot’s address.
- It cleans up the notification’s construction storage.
- It constructs a token associated with “GotoGeniusMixLoadingScreen.”
- It delivers the second token through receiver entry 0x11c.
- It cleans up the construction storage again and returns ordinarily.

The notification text address is one byte beyond the symbol labeled “CreatingGeniusMix.” Neither that label nor the address adjustment establishes the exact text bytes.

The notification-related global is read for the notification call after token construction and after the auxiliary-A assignment. It is not established to equal any value it held before construction.

If F-40819ce9a421 returns nonzero, the saved second 0x9c result is passed to F-4e6b58fde38f:

- A nonzero F-4e6b58fde38f result selects receiver entry 0x154 with a 32-bit zero argument, followed by ordinary return. No common result construction occurs.
- A zero result selects primary entry 0xac. Its return value is ignored. Execution then proceeds to common result construction with the previously captured numeric arguments.

Changes to the shared numeric global during these mode-0 calls do not cause the function to reread it for those captured arguments.

### Modes 1 and 2: common result delivery

Mode 1 calls F-ef0964bd9b8a and then reads a separate shared 32-bit global. This later read replaces the previously captured global-plus-5 argument.

Mode 2 calls F-ef0964bd9b8a but retains the earlier global-plus-5 argument. The mode-0 fallback following primary entry 0xac does the same.

All three common-construction paths invoke F-1958950ee503 with four arguments, in order:

1. The value returned by F-ef0964bd9b8a.
2. The first captured numeric value.
3. The mode-selected numeric value.
4. A 32-bit zero.

There is no explicit null check on the first argument.

A zero result from F-1958950ee503 reaches F-a817d8d58c10. A nonzero result is passed to receiver entry 0xd0, followed by ordinary return.

## Side effects

### Ordering and indirect calls

The observable order includes the following constraints:

- Primary acquisition precedes secondary acquisition.
- Secondary entry 0x1a4 precedes any preferred-navigation predicate.
- The first primary entry 0x9c precedes the mode query.
- The mode query precedes both initial numeric reads.
- Both initial numeric reads precede mode-specific dependency calls.
- Mode 1 reads its replacement global after F-ef0964bd9b8a.
- Each text-associated receiver operation precedes its corresponding cleanup.
- Notification cleanup precedes construction of the loading-screen token.
- Return assembly follows every call on the selected ordinary-return path.

Each indirect object operation receives its object as the first argument. Receiver entries 0x11c, 0x154, and 0xd0 additionally receive, respectively, the constructed token, zero, or the nonzero common-construction result. Their return values do not control subsequent behavior.

No general dispatch-table stability guarantee is established across opaque calls. The offsets specify the entries accessed when the corresponding operations are reached.

### Memory and ownership

Direct writes initialize the three auxiliary slots and, on the notification path, replace auxiliary A with 1. The function explicitly reads shared globals but contains no explicit direct write to them.

Opaque dependencies and indirect calls may modify shared state or accessible local storage. In particular, the address of auxiliary A is exposed before several later calls. Neither immediate notification completion nor an intervening cleanup closes that exposure or establishes preservation.

Explicit text cleanup establishes a caller-side cleanup action only. It does not establish allocation strategy, destruction semantics, reference counting, or whether a receiver copies or retains a token.

No explicit release is shown for the acquired services, the result of F-ef0964bd9b8a, or a nonzero result of F-1958950ee503. Delivery to a receiver does not prove ownership transfer. Retained-pointer validity beyond this invocation is not established.

### Abnormal completion

Three explicit conditions reach F-a817d8d58c10:

- Zero primary-service result.
- Unsupported mode.
- Zero common-construction result.

Its non-returning annotation does not identify whether it terminates execution, throws, or transfers control otherwise. No ordinary return is specified for those paths.

Cleanup is established only when intervening operations return ordinarily. No cleanup-on-unwind mechanism is visible.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Reached pointers and dispatch entries are assumed valid. Unless specified otherwise, invoked dependencies return ordinarily.

1. **Missing primary service.** If F-af667771d6ce returns zero, F-a817d8d58c10 is reached without secondary-service acquisition. No ordinary result is required.

2. **Preferred navigation with preparation.** If secondary entry 0x1a4 returns zero, F-479af9dba077 returns nonzero, and secondary entry 0x194 returns nonzero, secondary entry 0xf0 occurs before token construction. Receiver entry 0x11c then receives the construction result, followed by cleanup. A zero 0x194 result skips only the 0xf0 operation.

3. **Predicate short-circuit.** If secondary entry 0x1a4 returns nonzero, F-479af9dba077 is not called. The next branch-selection query is primary entry 0x9c.

4. **Primary-query early return.** If preferred navigation is not selected and the first primary 0x9c result is nonzero, no mode query or receiver delivery follows. With auxiliary A equal to 7 and valid local-storage use, the return halves are 7 and 1.

5. **Notification mutation with subsequent preservation.** On the mode-0 notification path, F-7cbd4a877291 receives auxiliary-A storage containing 1. If it changes that slot to 9 **and no subsequent operation modifies it before return assembly**, the final high half is 9 and the low half is 1.

6. **Notification mutation without preservation.** If that same call writes 9 and retains the address, but a later cleanup changes the slot through the retained address to 12, the high half is 12 provided no later modification occurs. Without a condition on later modifications, an immediate post-notification value of 9 does not determine the final high half.

7. **Mode-0 direct delivery.** If F-40819ce9a421 and F-4e6b58fde38f both return nonzero, receiver entry 0x154 receives zero. F-ef0964bd9b8a and F-1958950ee503 are not called.

8. **Captured arguments survive preparation.** If the two initial numeric reads both observe 20, the captured values are 20 and 25. On the mode-0 fallback, a change to the shared global by primary entry 0xac does not replace either captured value.

9. **Mode-1 replacement timing.** If the first captured value is 20 and the replacement global reads as 80 after F-ef0964bd9b8a returns, F-1958950ee503 receives 20 as its second argument and 80 as its third.

10. **Mode-2 argument selection.** If the two initial numeric reads observe 20 and 30, mode 2 supplies 20 and 35 as the second and third common-construction arguments, assuming the addition is within the represented range.

11. **Common-construction failure.** A zero F-1958950ee503 result reaches F-a817d8d58c10 without invoking receiver entry 0xd0.

12. **Unsupported mode.** A mode other than 0, 1, or 2 still causes the initial numeric reads before the terminal dependency. It causes no common result construction.
