# F-674966a49c41

## Purpose

F-674966a49c41 performs an initial payload operation, updates descriptor bookkeeping, and then processes linked records until it observes an empty pending-record head. Its only explicit normal return value is a 32-bit zero.

The operations are consistent with completing an item and servicing additional waiting items in indexed storage. That interpretation is **inferred intent**, not an established identification of the subsystem.

The visible body is not a complete, self-contained calling contract. It consumes execution-context values whose initialization is absent. It also derives a descriptor address from the third explicit argument; an initial branch selected when that address is zero still proceeds to descriptor-relative accesses.

This contract distinguishes:

- **Established static evidence:** visible accesses, widths, conditions, calls, and sequencing.
- **Inferred intent:** descriptive roles such as “pending record,” “occupancy,” and “high-water.”
- **Unknowns — documented_only:** missing entry conventions, dependency behavior, arithmetic semantics, and memory-validity requirements.

No runtime tests have been performed.

## Behavior

### Initial descriptor and payload operation

The initial descriptor address is formed by multiplying the third argument by `0x400000` and interpreting the result as an address.

Under a 32-bit wrapping interpretation, this is multiplication by \(2^{22}\) modulo \(2^{32}\); only the argument’s low ten bits affect the resulting address. Arguments zero and 1024 therefore both produce address zero under that interpretation. Exact signed-overflow and address-conversion semantics remain **documented_only**.

The initial operation is selected as follows:

- **Derived descriptor address is zero:** read 16 bits directly from the second argument and write 16 bits at the third argument’s address value plus twice the current slot index. Element width is not tested, and transfer-record offset 16 is not consulted.
- **Descriptor is nonzero and width is four:** first read the descriptor’s storage base, then obtain the 32-bit payload address from second-argument offset 16 and read 32 bits through it. Write that value at storage base plus four times the current slot index.
- **Descriptor is nonzero and width is anything else:** invoke F-2489d48d501c with destination storage base plus width times current slot index, and the 32-bit source-like value at second-argument offset 16. No explicit length argument is visible.

Thus initial widths zero, one, and two use the delegated call when the descriptor is nonzero. Their later specialized behavior must not be applied to the initial operation.

The representation does not establish a relative evaluation order between independent operand reads within the delegated-call argument expressions.

### Per-iteration bookkeeping

After the initial payload operation, and after each subsequent payload or no-copy iteration:

1. Read descriptor offset 44, increment it, and write the result there.
2. Read the occupancy-like value at offset 16.
3. Read the high-water-like value at offset 48.
4. If the high-water sample is smaller under an **unsigned 32-bit comparison**, write the sampled occupancy value to offset 48.
5. If the sampled occupancy equals one, read descriptor offset 32. If that field is nonzero, invoke F-6ad030b1b8cc.
6. Read the pending-record head at descriptor offset 20.

The occupancy test uses the sample taken before the optional call. The pending head is read after that call, so changes made by the dependency can affect the next branch.

There is no explicit counter-overflow protection. The high-water comparison is unsigned; the exact overflow semantics of integer increments are not independently established.

### Empty pending head

When the sampled pending head is zero, select the optional termination call:

1. Read the context’s 32-bit link at offset 8.
2. If nonzero, invoke F-unmapped-01 with that value.
3. Otherwise, read comparison-record offsets 8 and 12.
   - If unequal, invoke F-unmapped-01 with the offset-8 value.
   - If equal, read the context byte at offset 1.
   - Invoke F-unmapped-01 with that byte’s unsigned value if nonzero; otherwise skip it.

Then invoke F-unmapped-02 and return zero if execution returns normally.

The comparison record is not accessed by this decision when the context link is nonzero. The context byte is not read unless that link is zero and the comparison fields are equal.

### Pending-head removal: sampled condition, fresh destination

When the pending-head sample identifies a record, removal performs these distinct accesses in order:

1. Read the removed record’s 32-bit next link at offset 0 and retain that sample.
2. Write the sampled link to descriptor offset 20.
3. Test the **original next-link sample** for nonzero.
4. If that sample was nonzero, **reread the removed record’s offset-0 field after the descriptor-head write**. Use this fresh value as the address base for a 32-bit backlink write at offset 4. The value written is the address of descriptor offset 20.

The branch condition and backlink destination therefore come from different reads. The destination must not unconditionally be described as the successor identified by the original sample.

If storage overlaps, the descriptor-head write can change the removed record’s offset-0 bytes before the reread. No alignment or non-overlap restriction is established to exclude that case. A fresh value of zero does not cancel the backlink write when the original sample was nonzero; it instead produces an address calculation based on zero plus four.

If the original sample is zero, the backlink operation is skipped, including its fresh next-link read.

### Removed-record flags and conditional call

After the backlink operation, if any:

1. Read the removed record’s 32-bit flags at offset 28.
2. Clear bit `0x80` and write the masked value back.
3. If the masked sampled value is entirely zero:
   - Read the context link at offset 8.
   - Write that value to the removed record’s offset 0.
   - Write the removed record’s address to the context link.
4. Read the removed record’s offset-8 field.
5. If nonzero, invoke F-f46257aeeddc and, after it returns, write the replacement value to that field.

The insertion decision tests the masked sample; it does not reread the flags after writing them. Clearing `0x80` causes insertion only when no other flag bits remain.

The offset-8 update is conditional and occurs **after** the dependency returns. It is not a pre-call clearing operation, and its value need not be zero.

### Next transfer and index transition

After processing the removed record:

1. Read its intermediate-object address at offset 16.
2. Read the transfer-record address at intermediate-object offset 4.
3. Write the replacement value to transfer-record offset 4.
4. Read, increment, and write descriptor occupancy at offset 16.
5. Read the descriptor index at offset 12 and write its incremented value.
6. If that incremented value equals the index limit, overwrite descriptor offset 12 with the replacement value.
7. Read descriptor offset 12 for the next payload operation.

The limit comparison uses equality, not a range check. An index already beyond the limit is not visibly corrected.

These operations remain separate memory accesses. Aliasing or dependency effects can influence later reads; no disjoint-object invariant is established.

### Subsequent payload operations

For each transfer record selected through a pending record:

| Width | Operation |
|---|---|
| Zero | No explicit payload access; immediately repeat bookkeeping. |
| One | Read storage base, obtain the payload address from transfer-record offset 16, read one byte, and write one byte at storage base plus current index. |
| Two | First obtain the payload address from transfer-record offset 16, then read storage base. Read 16 bits through the payload address and write 16 bits at storage base plus twice the current index. |
| Four | Read storage base, obtain the payload address from transfer-record offset 16, read 32 bits, and write 32 bits at storage base plus four times the current index. |
| Any other value | Invoke F-2489d48d501c with destination storage base plus width times current index, and the 32-bit value at transfer-record offset 16. |

The width-two path replaces the working transfer address with its payload address before reading the 16-bit payload. It does not read a 16-bit value directly from the transfer record itself.

Each operation returns to bookkeeping. There is no explicit iteration bound, and eventual list exhaustion is not guaranteed.

## Side effects

The visible body can write:

- Payload destinations.
- Descriptor index, occupancy, completion counter, high-water field, and pending head.
- A backlink at the freshly reread next-link address plus four.
- Removed-record flags, next link, and conditional-call field.
- The context link.
- The selected transfer record’s offset-4 field.

Dependencies may have additional effects. No dependency is assumed to preserve globals, avoid reentry, or leave memory unchanged.

There is no explicit allocation or deallocation. List removal and insertion do not establish ownership transfer, reclamation, reference counting, or permission to release storage.

No visible locks, atomic accesses, barriers, or rollback mechanisms appear. Thread safety, interrupt safety, and synchronization requirements are **documented_only**.

The zero-descriptor initial branch still proceeds to bookkeeping relative to address zero, beginning with the counter at offset 44. The direct payload write is not a guard against those later accesses.

Aliasing is material throughout the contract. In particular, the descriptor-head write precedes the next-link reread used for the backlink destination. If an access fails or a dependency does not return, earlier writes have no visible rollback.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume valid addressed memory, returning dependencies, and no interfering writes except where overlap is explicitly part of the example.

### Initial and subsequent width-one behavior

With a nonzero derived descriptor and width one:

- The initial operation invokes F-2489d48d501c.
- A subsequently selected transfer uses an explicit byte read and byte write.

Describing every width-one operation as a direct byte copy would be incorrect.

### Zero-width processing

With a nonzero descriptor and width zero, the initial operation invokes F-2489d48d501c. Subsequently selected records receive activation and bookkeeping updates without explicit payload reads or writes.

### Backlink without overlap

Suppose the initial next-link sample is a nonzero address A, and the descriptor-head write does not change the removed record’s offset-0 field.

The function writes A to descriptor offset 20, rereads A from the removed record, and writes the address of descriptor offset 20 to A plus four.

### Backlink with overlap

Suppose a nonzero next-link sample is A, but overlapping storage makes the descriptor-head write change the removed record’s offset-0 value to B.

The branch remains enabled by A. The fresh read supplies B, so the backlink write targets B plus four, not necessarily A plus four.

If B is zero, the write still occurs at address four, assuming that address is valid. Conversely, an original zero sample skips the backlink operation entirely.

### Flag-dependent insertion

Flags `0x80` become zero, enabling context-list insertion. Flags `0x81` become `0x01`, so insertion is skipped.

### Index equality

With index five and limit six, activation first writes six, then replaces it with the replacement value. That final value is zero if the replacement is zero, or nine if the replacement is nine.

With index seven and limit six, incrementing to eight does not trigger replacement.

### Termination selection

| Context link | Comparison fields | Context byte | F-unmapped-01 |
|---|---|---|---|
| Nonzero | Not read by this decision | Not read | Called with link |
| Zero | Unequal | Not read | Called with comparison offset 8 |
| Zero | Equal | Nonzero | Called with unsigned byte |
| Zero | Equal | Zero | Skipped |

F-unmapped-02 follows in every row if preceding execution returns.

### High-water timing

If occupancy is three and high-water is two, bookkeeping writes high-water three. Activating a pending record then increments occupancy to four. That activation alone does not update high-water to four; a later bookkeeping pass must observe it, absent other writes.
