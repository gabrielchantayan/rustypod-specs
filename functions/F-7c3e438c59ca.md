# F-7c3e438c59ca

## Purpose

F-7c3e438c59ca converts an accepted byte sequence into scaled, packed 32-bit words and replaces an output header with a signed, configuration-dependent position.

The conversion consumes bytes from the highest input address toward the lowest. Packed words occupy consecutive output positions beginning at position 1. Position 0 is reserved for metadata.

The final metadata comes from a descending search over output storage. Configuration determines the search range independently of the amount of payload produced. Consequently, the metadata is not necessarily a payload count: it can reflect preexisting output contents, exceed the produced payload count in magnitude, or be negative.

**Established static evidence:** the length boundary, byte transformation, grouping, arithmetic distinctions, configuration observations, output assignments, search criterion, and return behavior described below.

**Inferred intent:** the search may serve a numeric-normalization purpose. That interpretation does not establish a particular number format, constrain configuration values, or limit the search to newly written words.

The numeric packing description is conditional on an execution model with 32-bit integers and four-byte output words. The validity of the address-valued mechanism used during packing remains unresolved.

## Interface

### Arguments and result

| Interface element | Behavioral contract |
|---|---|
| Input address | A signed 32-bit integer from which byte addresses are formed. Validity is not established merely by supplying a numerically plausible value. |
| Input length | An unsigned 32-bit byte count. Values from 0 through 256 are accepted. |
| Output storage | Caller-provided storage addressed as signed 32-bit words at four-byte intervals. |
| Result | An unsigned 32-bit value. Normal completion returns zero. Excessive length returns a separately configured value. |

The rejection result can itself be zero. A zero return therefore does not, by itself, prove that conversion occurred.

### Output layout and capacity

Output position 0 holds metadata. Positions 1 onward hold payload and, potentially, preexisting words examined by the search.

For accepted length \(L\), the number of produced payload words is

\[
N=\left\lceil \frac{L}{4}\right\rceil.
\]

Direct output assignments cover position 0 and positions 1 through \(N\). At the maximum accepted length, 64 payload words are produced, requiring 65 writable words including metadata: 260 bytes under the represented layout.

There is no terminator, and storage beyond the produced payload is not initialized.

Readable capacity can exceed writable capacity. The search can inspect positions beyond \(N\), and the interface supplies no allocation size with which to constrain it.

### Configuration roles

Five external 32-bit locations contribute distinct roles:

| Role | Use |
|---|---|
| Rejection result | Supplies the return value when length exceeds 256. |
| Payload scale | Scales every packed payload word. |
| Metadata scale | Contributes to the search extent, provisional metadata, and final metadata. |
| Extent scale | Multiplies the payload count and one metadata-scale observation to determine search extent. |
| Search scale | Multiplies each examined output value for qualification. |

These are access roles, not guarantees that their storage is disjoint from the arguments.

The payload scale is captured before the length rejection and reused for all payload words. The metadata scale has three distinct represented observations. They must not be collapsed into an assumed single snapshot when describing the supplied representation.

### Preconditions and ownership

Defined completion requires valid configuration accesses, valid input addresses for consumed bytes, writable output positions for assignments, and readable output positions for all candidates actually examined.

It also requires an execution environment supporting the represented address conversions, address arithmetic, word spacing, alignment, and access types. Signed calculations identified below must be representable.

No allocation, release, ownership transfer, retained reference, or storage-lifetime extension is established. The caller remains responsible for storage validity throughout the invocation.

## Behavior

### Accepted and rejected lengths

Every unsigned length greater than 256 is rejected. This includes values with the high bit set; length is not interpreted as a negative signed quantity.

On rejection:

- The payload-scale observation has already occurred.
- The rejection-result location supplies the returned value.
- There are no input-byte reads, payload assignments, metadata assignments, or search reads through the supplied buffer arguments.

This is a distinction between access roles. A configuration read could still access the same physical memory as an argument if the locations alias.

Length zero is accepted. It requires no input-byte access and produces no payload, but it still requires accepted-path configuration accesses and writable metadata storage. It is not an unconditional success case if those accesses or intermediate signed calculations are invalid.

### Byte conversion and packing

Each consumed byte is interpreted as an unsigned value \(b\) between 0 and 255. Its transformed value is

\[
T(b)=(181b-220)\bmod 256,
\]

also between 0 and 255.

Consumption proceeds in descending input-offset order, from \(L-1\) through 0. Up to four consecutive consumed bytes form one payload word:

| Order within a group | Numeric field |
|---|---|
| First consumed byte | Bits 0–7 |
| Second consumed byte | Bits 8–15 |
| Third consumed byte | Bits 16–23 |
| Fourth consumed byte | Bits 24–31 |

Unused high fields in a partial final group are zero. A length divisible by four produces no additional empty word.

These are numeric bit positions, not a claim about the physical byte order of output memory.

Payload groups are assigned to output positions in increasing order, beginning at position 1. Each complete group is written before consumption begins for the next group. A partial final group is written after all of its bytes have been consumed.

### Payload scaling and storage

Each packed word is multiplied by the captured payload scale using unsigned 32-bit arithmetic. The retained result is the low 32 bits of the product. A negative payload scale participates through its unsigned 32-bit representation.

The result is then assigned to signed 32-bit output storage. Results no greater than \(2^{31}-1\) have an unambiguous signed value. For larger unsigned results, the signed conversion is environment-dependent; preservation of the unsigned bit pattern is not established portably.

The input address calculation combines a signed 32-bit address argument with an unsigned 32-bit offset. Its numerical addition is modulo \(2^{32}\). That numerical rule does not establish the validity of an address after wraparound.

### Search extent and provisional metadata

After payload production, the represented observations distinguish:

- A captured search scale.
- A metadata-scale value retained for final metadata.
- A separate metadata-scale value contributing to the search extent.
- Another metadata-scale value contributing to provisional metadata.

Let the signed search extent be \(E\). It is the product of the extent scale, the extent-specific metadata-scale observation, and \(N\). The two scales are multiplied before their product is multiplied by \(N\).

Both products must be representable as signed 32-bit values. In particular, \(N=0\) does not make an overflowing product of the two scales valid.

Before searching, position 0 receives provisional metadata equal to \(N\) multiplied by the provisional metadata-scale observation. This multiplication also requires signed 32-bit representability.

The provisional value is temporary. Normal completion replaces it with final metadata in the same output position.

### Candidate selection

When \(|E|\) is representable as a nonnegative signed 32-bit value, the candidate positions are the positive output positions from \(|E|\) down to 1.

A candidate qualifies when the signed 32-bit product of its stored value and the captured search scale is nonzero. That product must be representable. The selected position is the greatest qualifying position in the configured range; if none qualifies, the selected position is zero.

The following consequences are part of the contract:

- Position 0 is never a candidate.
- Zero extent produces no candidate reads.
- Negative extent still selects from positive output positions.
- The search stops at its first qualifying candidate.
- Search range is not capped by the produced payload count.
- A preexisting word beyond the payload can be selected before any newly produced word is examined.
- Zero search scale does not remove candidate reads. Every candidate is examined and fails qualification.

Nonzero operands alone do not guarantee a defined qualification result: their signed product must also be representable.

The minimum signed extent, \(-2^{31}\), has no representable positive signed magnitude. No completed-result contract is established for that case.

### Final metadata and normal return

Let \(J\) be the selected nonnegative position and let \(M\) be the metadata-scale observation retained for final output.

| Extent | Final metadata |
|---|---|
| Positive | \(M\times J\) |
| Zero or negative | \(M\times(-J)\) |

Negation and multiplication require signed 32-bit representability.

Zero extent therefore yields final metadata zero, provided the preceding accesses and calculations were valid. Negative extent changes the sign applied to the selected position, not the addresses searched. A negative final metadata scale can reverse the sign again.

Normal completion returns zero after the final metadata assignment.

## Side effects

### Observable access ordering

The supplied representation establishes these ordering constraints, without establishing hardware transaction counts or synchronization guarantees:

| Activity | Ordering constraint |
|---|---|
| Payload-scale observation | Precedes rejection and all argument-directed buffer accesses. |
| Input consumption | Descending byte offsets. |
| Complete payload assignment | Follows its four contributing reads and precedes reads for the next group. |
| Partial payload assignment | Follows all remaining input reads. |
| Accepted-path metadata configuration | Follows payload production. |
| Search-scale capture | Precedes capture of the final metadata scale. |
| Extent calculation | Uses a later metadata-scale observation; the relative read order of that observation and the extent scale is not established. |
| Provisional metadata-scale observation | Follows extent calculation. |
| Provisional metadata assignment | Precedes candidate reads. |
| Candidate reads | Descend in position and stop at the first qualifying candidate. |
| Final metadata assignment | Follows candidate selection. |

All configuration values needed for the search and final assignment have been obtained before provisional metadata is written.

No output assignment separates the three metadata-scale observations. Output aliasing alone therefore does not explain differences among them.

Two metadata assignments are represented even when both values are equal. This is not a guarantee of two externally observable hardware writes, atomic publication, or visibility to an unsynchronized observer.

### Overlap and mutation

There is no complete input snapshot or overlap protection. Where the environment permits the overlapping access types, a payload assignment can modify input bytes not yet consumed. Later input reads then observe the modified contents.

Payload assignments can similarly affect configuration storage through aliasing before metadata processing. They cannot change the already captured payload multiplier used by subsequent groups.

If metadata position 0 aliases configuration storage, its provisional assignment occurs too late to alter configuration values already captured for the search, extent, or final assignment.

Distinct represented observations do not establish permission for concurrent mutation, special read semantics, or a memory-ordering protocol.

### Failure and partial effects

Excessive length is the only explicit rejection condition.

No error return, rollback, or recovery behavior is established for invalid memory, unsupported address operations, unsuitable alignment, disallowed overlapping access types, or unrepresentable signed arithmetic.

A failure can occur after payload assignments. A search-related failure can occur after provisional metadata has replaced the previous header. No transactional preservation of the original output is established.

- With payload scale \(-1\), the unsigned payload result is \(0xFFFFFFDC\). If signed conversion preserves that pattern, position 1 contains \(-36\); final metadata remains 1.

### Search beyond the payload

For one input byte equal to 0 and extent scale 2, only position 1 is produced, but the search starts at position 2.

If preexisting position 2 qualifies, final metadata is 2. If position 2 is zero, position 1 qualifies and final metadata is 1. Storage covering only positions 0 and 1 is insufficient.

With stable metadata scale 2 instead, extent and provisional metadata are both 2. A qualifying position 2 produces final metadata 4. A zero position 2 followed by qualifying position 1 produces final metadata 2.
