# F-21c4221b085c

## Purpose

F-21c4221b085c selects one of 128 pointer slots in a caller-provided object and updates the selected record. A zero control value selects a clearing operation. A nonzero control value selects a construction operation, potentially creating a supporting object first.

An existing record whose first 32-bit field is nonzero takes a diagnostic/non-returning path instead of being replaced or cleared normally.

The established behavior is a sequence of address calculations, memory accesses, and dependency calls. Descriptions such as “record,” “supporting object,” and “construction” are descriptive labels, not proof of application-level types or ownership. In particular, the indirect call used when clearing a supporting object is not established to release its storage.

## Interface

The function has six inputs and no explicit return value:

| Input | Width and interpretation | Role |
|---|---|---|
| Container address | 32-bit address-bearing value | Base of the object containing the slot table. |
| Slot index | Unsigned 32-bit integer | Selects a slot when in the range 0–127. |
| Control value | 32-bit integer | Zero requests clearing; every nonzero value requests construction and is passed unchanged to a dependency. |
| First attribute | 16-bit value | Stored at record offset 8 on the construction path. |
| Second attribute | 16-bit value | Stored at record offset 10 on the construction path. |
| Final attribute | 16-bit value | Stored at record offset 12 on either normal update path. |

The first and second attributes are treated as 16-bit bit patterns. Their signedness is not established. Any conversion from a wider caller-side value into these inputs is outside the demonstrated behavior.

For an accepted index, the selected slot is a 32-bit pointer-sized cell at:

**container address + 0xA4 + 4 × slot index**

The first slot is at offset 0xA4; the last is at offset 0x2A0. The selected cell occupies four bytes.

The selected record has the following observed layout:

| Offset | Access width | Observed use |
|---|---:|---|
| 0 | 32 bits | Checked for a blocking nonzero state; later cleared or assigned a dependency result. |
| 4 | 32 bits | Supporting-object pointer or handle, tested against zero and sometimes used as an object address. |
| 8 | 16 bits | First attribute, or zero on clearing. |
| 10 | 16 bits | Second attribute, or zero on clearing. |
| 12 | 16 bits | Final attribute. |
| 14–15 | None observed | Included in the 16-byte allocation request but not directly accessed here. |

There is no established byte-order requirement beyond that of the execution environment. The offsets and access widths are established; a portable serialization format is not.

For valid execution, all addresses actually dereferenced must identify suitably accessible storage. The function does not validate the container, record, supporting object, indirect-call target, or constructor result.

The index multiplication cannot overflow a 32-bit value after the range check: its maximum is 508. Address additions must nevertheless produce valid addresses in the execution environment. The supplied evidence does not establish portable signed-overflow or pointer-provenance semantics.

## Behavior

### Index rejection

An unsigned slot index greater than 127 causes an immediate return.

On this path, the function does not access the container, calculate the selected slot address, or invoke any dependency. An index with its high bit set is rejected under the unsigned comparison; it is not treated as a negative index.

### Selecting or obtaining a record

For an accepted index, the function reads the selected slot.

If that slot is zero, it calls F-638beded7699 with arguments **16** and **0**, then writes the returned 32-bit value into the selected slot. This is an allocation-like operation, but successful allocation, zero initialization, and allocator ownership are not established.

The newly obtained record does not undergo the blocking-state check applied to an existing record. In particular, the function does not read its offset-0 field before choosing the next operation.

If the selected slot was initially nonzero, the function reads the existing record’s offset-0 field:

- If that field is nonzero, it calls F-282eebd7c413 and then, if the first call returns, F-feee9156a257.
- F-feee9156a257 is marked non-returning in the supplied evidence. There is no demonstrated normal continuation after that call.
- If the field is zero, the function explicitly writes a 32-bit zero to offset 0 before examining the supporting-object field at offset 4.

The existing-record blocking check applies to both zero and nonzero control values. A zero control value therefore does not unconditionally clear an occupied record.

### Supporting-object handling

The supporting-object behavior depends on both the initial record state and the control value.

**New record, zero control value.**  
The function writes a 32-bit zero to offset 4 using the address returned by F-638beded7699. It does not first read that field. A zero return from that dependency is not handled safely by a later guard: this write is already attempted.

**New record, nonzero control value.**  
The function calls F-8157a180d901 with **0xB8**, ignores its return value, and then calls F-a891c2749310 with no explicit arguments. It rereads the selected slot after those calls and writes the result of F-a891c2749310 to offset 4 of the record currently selected by that slot.

**Existing record, zero supporting-object field, zero control value.**  
No supporting-object call is made. The field remains zero, subject to any external or dependency-induced changes outside this local sequence.

**Existing record, zero supporting-object field, nonzero control value.**  
The same two-call creation sequence is used: F-8157a180d901 with 0xB8, followed by F-a891c2749310. The second result is written to offset 4 through a freshly read slot pointer.

**Existing record, nonzero supporting-object field, nonzero control value.**  
The existing value is retained by this function. Neither supporting-object creation nor the indirect call is performed.

**Existing record, nonzero supporting-object field, zero control value.**  
The supporting-object value is dereferenced to obtain a table address. A callable address is then read at table offset 4 and invoked. No explicit argument list is shown for that invocation; a receiver-passing convention is not established.

If the indirect call returns, the function rereads the selected slot and writes zero to offset 4 of the record then selected. It does not necessarily clear the same record from which the supporting-object value was originally obtained.

### Final record update

After supporting-object handling, the function rereads the selected slot. If it is zero at this point, it returns without the final field updates.

This guard is not a general allocation-failure check. Earlier steps can already have dereferenced a zero or otherwise invalid record address.

If the slot is nonzero and the control value is zero, the function performs these writes in order:

1. A 32-bit zero at record offset 0.
2. A 16-bit zero at record offset 8.
3. A 16-bit zero at record offset 10.
4. The final attribute as a 16-bit value at record offset 12.

The selected slot is reread for these destination accesses. The first and second attribute inputs are not stored on this path.

If the slot is nonzero and the control value is nonzero, the function:

- Calls F-8157a180d901 with **0x44**.
- Reads the current selected record’s offset-4 value after that call.
- Calls F-f8beff1830ad with the first call’s 32-bit result, the offset-4 value just read, and the original control value.
- Writes the 32-bit result of F-f8beff1830ad to offset 0 of the record selected after that dependency returns.
- Writes the first attribute at offset 8, then the second attribute at offset 10, then the final attribute at offset 12, each as a 16-bit value.

The selected slot is reread for the result store and for each attribute store. There is no second null guard after the construction dependencies. A dependency that changes the slot to zero can therefore make subsequent accesses invalid.

No validation is applied to the control value beyond testing it against zero. Negative nonzero values follow the construction path and are passed unchanged to F-f8beff1830ad.

## Side effects

Directly established writes include:

- Publishing a newly obtained record address in the selected slot.
- Clearing or replacing the record’s offset-0 field.
- Installing or clearing the offset-4 supporting-object field.
- Updating the 16-bit fields at offsets 8, 10, and 12.

The function does not directly clear the selected slot, directly release record storage, or directly write record bytes 14–15.

Dependency effects remain unconstrained by this evidence. Dependencies may affect globals or reachable storage, including the selected slot. Consequently, the contract must preserve the distinction between a retained address and a later slot reread. It must not assume all operations target one immutable record.

The operations are sequential and not transactional. There is no demonstrated rollback after a failed dependency, invalid memory access, or non-returning call. For example, the slot can already contain a newly returned address before supporting-object creation begins, and an existing record’s offset-0 field is cleared before supporting-object handling.

There is no explicit success status, error code, exception handler, lock, or synchronization operation in the supplied body. Memory faults and dependency failures have no locally demonstrated recovery behavior.

Ownership is **documented_only** beyond the observed calls and stores. Allocation sizes do not establish who eventually frees the storage. The indirect call does not, by itself, establish destruction, deallocation, or reference-count behavior.

## Acceptance examples

These examples are conditional on valid memory, returning dependencies where required, and the stated dependency effects. They are acceptance criteria, not executed tests.

1. **Rejected index.** With index 128, the function returns without reading the container or making calls. The same holds for 0xFFFFFFFF.

2. **Highest accepted slot.** With index 127, the selected cell is at container offset 0x2A0. Subsequent behavior depends on that cell’s contents and the control value.

3. **New record cleared.** Suppose the slot is zero, F-638beded7699 returns a valid 16-byte record, and no relevant state changes occur elsewhere. With zero control, the call arguments are 16 and 0; the returned address is published; record offsets 4 and 0 become zero; offsets 8 and 10 become zero; and offset 12 receives the final attribute. Bytes 14–15 are not directly modified.

4. **New record constructed.** Under stable slot state and valid dependency results, nonzero control causes requests of 16 bytes, then 0xB8, then 0x44, in that order. F-a891c2749310 runs between the latter two requests. Its result becomes the supporting field. F-f8beff1830ad receives that field and the original control value. Its result and all three attributes are stored in their respective fields.

5. **Existing supporting object reused.** Given an existing record with offset 0 zero and offset 4 nonzero, nonzero control does not invoke the indirect call or the 0xB8 sequence. The 0x44 sequence still occurs, and the supporting field is supplied to F-f8beff1830ad.

6. **Existing supporting object cleared.** With the same initial record but zero control, the offset-0 zero write precedes the indirect call. If that call returns without changing the slot, offset 4 is then cleared, offsets 0, 8, and 10 are cleared, and offset 12 receives the final attribute. Deallocation is not an acceptance requirement.

7. **Blocked existing record.** If an existing record’s offset-0 field is nonzero, F-282eebd7c413 is called first. If it returns, F-feee9156a257 is called. No normal clearing or construction continuation is established.

8. **Slot redirected during construction.** If F-f8beff1830ad changes the selected slot from one valid record to another, the result store targets the latter record. An implementation that always stores through an earlier cached record address would not preserve the demonstrated access behavior.

9. **Zero allocation result is not graceful failure.** If F-638beded7699 returns zero on the zero-control path, the function attempts the offset-4 write through that result before reaching the final guard. Silent success or an error return is not established.

## Uncertainties

The application meaning of the control value, attributes, record fields, and supporting object is unknown.

The following remain **documented_only**:

- Dependency implementations, failure modes, and effects on shared state.
- Allocation initialization and ownership.
- Indirect-call receiver or hidden-argument conventions.
- Whether result values represent pointers, handles, or another 32-bit representation except where directly dereferenced.
- Thread-safety, reentrancy, and concurrent access guarantees.
- The precise failure behavior for invalid addresses.
- The meaning of the unused final two record bytes.

Inferred intent: the body appears to lazily obtain per-slot storage, maintain an optional supporting object, and construct or clear associated state. That interpretation must not replace the established call order, access widths, or failure limitations.
