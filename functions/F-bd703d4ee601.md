# F-bd703d4ee601

## Purpose

F-bd703d4ee601 selects an entry associated with an object and submits it to an opaque acceptance operation. It either returns the submitted entry after a nonzero acceptance result or returns zero. Zero does not distinguish rejection, traversal completion, an initial gate failure, or successful acceptance of a zero entry reference.

Selection has two paths:

- **Direct:** submit the initial entry when an object callback’s low 32-bit result is nonzero and option bit `0x80` is set.
- **Iterative:** obtain candidates through a dependency, optionally defer selection using extracted 16-bit sequences, and attempt acceptance.

During iteration, a monitored callback value is compared against a baseline until the first difference. That difference resets cycle tracking and optionally causes a one-byte notification.

These descriptions identify control-flow roles, not established domain semantics. In particular, sequence comparison results do not establish equality, ordering, or grouping rules.

## Behavior

### 1. Initialize notification storage and apply initial gates

If the change-output address is nonnull, the function first writes one byte containing zero. This precedes every dependency call and callback dispatch.

It then calls F-b7abcf60c990 with the embedded-structure address at object offset `0x060`. A zero result returns zero immediately.

After a nonzero gate result:

- A zero starting identifier establishes a zero initial entry without lookup.
- Otherwise, F-6ef0016a253f receives the object’s current field at `0x064` and the starting identifier.

A zero lookup result permits processing to continue. A nonzero lookup result is checked by F-6a5af51404be, receiving that entry and the object’s current field at `0x9a8`. A nonzero check result returns zero; a zero check result permits processing.

### 2. Choose the direct or iterative path

The callback at table offset `0x1ac` is invoked with the object.

The direct path is selected only if its low 32-bit result is nonzero and original option bit `0x80` is set. A nonzero high half with a zero low half does not satisfy this condition.

On the direct path, F-66506646b1ee receives:

1. The embedded-structure address.
2. The initial entry, possibly zero.
3. The current object field at `0x9a8`.

A nonzero acceptance result returns the submitted entry; a zero result returns zero. No iterator call, sequence extraction, or monitoring callback follows.

The function itself performs no further write to the change-output byte on this path. Its final contents are not guaranteed: intervening dependencies or callbacks may modify that storage, including through aliases.

Every other case enters iteration.

### 3. Initialize iterative state

Only the first 16-bit element of the retained-sequence workspace is explicitly initialized to zero. If the initial entry is nonzero, F-29854e913c2d receives its field at `0x20` and that workspace. This initial extraction occurs even when special mode is disabled.

The function then, in order:

1. Invokes the callback at `0x1d0` to capture a baseline.
2. Records whether original option bit `0x80` is set.
3. Invokes the callback at `0x1b4` and caches its 32-bit result.

Initially:

- The cycle marker is zero.
- The deferred entry is zero.
- No monitored change has been latched.
- No sequence anchor has been established.

The baseline and cached iterator arguments are not refreshed later. Effective options initially equal the supplied options, but may later be replaced with exactly `3`.

### 4. Obtain a candidate and monitor for change

Each iterator request uses zero as its continuation when the current entry is zero. Otherwise, it reads the current entry’s 32-bit field at `0x10`.

F-fd3640a68912 receives, in argument order:

1. The current object field at `0x064`.
2. That continuation value.
3. `0x33`, or decimal 51.
4. The cached callback result from `0x1b4`.
5. A Boolean indicating whether original option bit `0x80` was set.

Its result becomes the current candidate.

Until change detection has latched, the callback at `0x1d0` is invoked after every iterator call, including one returning zero. If its result differs from the baseline:

- The cycle marker becomes zero.
- Change detection latches for the remainder of this invocation.
- If the output address is nonnull, the function writes one byte containing one.

The output write follows the monitoring callback. The function does not clear the deferred entry, sequence anchor, retained sequence, or effective options because of this change.

After latching, there are no further monitoring callbacks from this loop.

### 5. Detect traversal completion and establish the marker

For a nonzero iterator candidate:

- If the cycle marker is zero, the candidate becomes the marker.
- If the marker is nonzero and equals the candidate, traversal completes.
- Otherwise, processing continues with that candidate.

A zero iterator result also completes traversal.

On completion:

- If the deferred entry is zero, return zero without acceptance.
- Otherwise, select the deferred entry as the candidate, clear the deferred entry, and replace effective options with exactly `3`.
- If the cycle marker is zero, record this selected fallback candidate as the marker before acceptance.
- If the marker is already nonzero, retain it.

The fallback proceeds without another iterator call or monitoring callback. Replacing effective options does not change the cached Boolean derived from original bit `0x80`.

Recording a fallback as the marker is significant when a monitoring change cleared the marker immediately after an iterator returned zero. If fallback entry A is rejected and the next iterator result is A, traversal completes against that marker. With no deferred entry remaining, the function returns zero rather than attempting acceptance of A again.

This is single-marker cycle detection, not a complete visited-entry set.

### 6. Apply sequence-based deferral in special mode

Special mode applies exactly while the low seven effective option bits equal `4`. Otherwise, the candidate proceeds to acceptance.

In special mode, F-29854e913c2d receives the candidate’s field at `0x20` and the candidate-sequence workspace.

The function tests the first retained element before conditionally inspecting the first candidate element. For branching purposes, a sequence is empty when its first 16-bit element is zero. No local terminator scan or full-workspace validation is visible.

#### Before anchor establishment

The candidate establishes the anchor when:

- The retained sequence is empty; or
- The candidate sequence is empty; or
- Both are nonempty and F-1a331ff73558 returns zero.

That comparison receives the retained workspace, candidate workspace, and a third argument of zero, in that order.

On establishment, F-93583d17f15c receives the candidate workspace first and the retained workspace second. The anchor-established state is set, and the candidate becomes the deferred entry. The direction or exact contents of any transfer performed by this dependency are not established.

Whether or not the candidate establishes the anchor, iteration resumes without an acceptance attempt.

#### After anchor establishment

If both sequences are nonempty, F-1a331ff73558 receives the same argument ordering.

- A nonzero result replaces the deferred entry with the current candidate and resumes iteration.
- A zero result ends special processing for this selection.

If either sequence is empty, special processing ends without comparison.

When special processing ends:

- The previously deferred entry becomes the candidate for acceptance.
- The boundary candidate is not submitted at this point.
- The deferred entry is cleared.
- Effective options become exactly `3`.

The function does not repeat the anchor-transfer call as deferred entries change. Comparisons continue using the retained workspace, subject to any modifications opaque dependencies themselves perform.

### 7. Attempt acceptance

F-66506646b1ee receives the embedded-structure address, the selected candidate, and the current object field at `0x9a8`.

A nonzero result returns that candidate.

A zero result resumes iteration. The next continuation is read from the selected candidate at `0x10`, or is zero if the selected value is zero. In particular, rejecting a deferred selection resumes from that deferred entry, not from the boundary candidate that ended special processing.

Acceptance rejection does not itself reset the cycle marker, restore special mode, or recapture cached values.

There is no explicit iteration limit, timeout, or distinct error result. Termination depends on dependency results and traversal behavior.

## Side effects

The function’s established direct writes are:

- The initial zero byte at a nonnull output address.
- At most one later one-byte write of one after detecting a monitored change.
- Local workspace and control-state writes.

These direct-write bounds do not constrain writes by dependencies or callbacks.

Reads remain sensitive to intervening mutations:

- Object field `0x064` is read for lookup when needed and again for each iterator request.
- Object field `0x9a8` is read for each reached initial-entry check or acceptance call.
- Callback dispatch uses the callback-table reference present when that dispatch is reached.
- Entry continuation and sequence-source fields are read when their operations are reached.

The initial output write may therefore affect the initial gate or later reads if the output aliases relevant storage. Likewise, the later write of one may affect candidate processing after monitoring. No alias check or output-content restoration is visible.

The function has no visible allocation, release, retention, or ownership-transfer operation of its own. This does not establish that dependencies preserve objects, entries, globals, workspaces, or output contents. Required lifetime and mutation discipline belongs to the surrounding contract and remains unresolved.

## Acceptance examples

These are conditional static expectations, not executed tests. Dependencies are assumed to return normally and keep storage valid for reached accesses. Additional content-preservation assumptions are stated where needed.

1. **Initial gate stops processing.**  
   With a nonnull output address, the function first writes zero. If F-b7abcf60c990 returns zero, it returns zero without lookup, callback dispatch, or acceptance. The gate’s possible writes are not constrained by this example.

2. **Resolved initial entry is blocked.**  
   Lookup returns a nonzero entry and F-6a5af51404be returns nonzero. The result is zero, and callback `0x1ac` is not invoked.

3. **Direct acceptance succeeds.**  
   Original options include `0x80`, callback `0x1ac` has a nonzero low 32-bit result, and acceptance returns nonzero. The initial entry value is returned. The function performs no further output write after initialization. The byte remains zero only if intervening operations do not modify it.

4. **Only the high callback half is nonzero.**  
   Original options include `0x80`, but callback `0x1ac` has a zero low 32-bit result. The function enters iteration regardless of its high 32 bits.

5. **Ordinary iteration accepts a candidate.**  
   Special mode is disabled. The iterator returns nonzero A without triggering completion, and acceptance succeeds. The result is A. Candidate-sequence extraction is not required, although initial-entry extraction may already have occurred.

6. **Traversal ends without deferral.**  
   The iterator returns zero while no entry is deferred. The still-enabled monitor callback runs before the function returns zero. It may cause the output write of one even though no entry is accepted.

7. **Special mode establishes an anchor.**  
   The retained sequence’s first element is zero. A nonzero candidate establishes the anchor without comparison. F-93583d17f15c is invoked, the candidate is deferred, and iteration continues without acceptance.

8. **Boundary selection submits the previous deferred entry.**  
   An anchor exists and A is deferred. Candidate B produces a nonzero comparison result, replacing A as deferred. Candidate C then produces zero. Acceptance is attempted for B, not C; effective options are now `3`. Rejection resumes from B.

9. **Fallback records a cleared marker.**  
   A is deferred. An iterator call returns zero, and its monitoring callback differs from the baseline, clearing the marker. Fallback selects A, clears deferral, sets effective options to `3`, and records A as the marker. Acceptance rejects A. If the next iterator result is A, traversal completes and returns zero without a second acceptance attempt.

10. **Monitoring latches once.**  
    A monitor difference clears the marker and causes the function’s write of one when an output address is present. Subsequent iterations do not call the monitor again. A current nonzero candidate can establish the replacement marker immediately after that first difference.
