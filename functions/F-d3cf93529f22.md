# F-d3cf93529f22

## Purpose

F-d3cf93529f22 conditionally invokes an operation through the primary object's dispatch table, performs further calls using object-relative and temporary addresses, and conditionally invokes an operation through an auxiliary object's dispatch table.

The established behavior is an ordered sequence:

- An initial dependency's zero result causes an immediate 32-bit result of 3.
- Any nonzero initial result permits the primary-object operation.
- The primary operation's result is saved, without being tested.
- Subsequent dependencies receive temporary storage and an address within the primary object.
- A comparison result other than exactly 1 triggers an additional dependency call.
- The auxiliary-pointer slot is tested after those calls. Its value at that time determines whether auxiliary dispatch occurs.
- Normal completion of the continuing path returns the saved primary-operation result.

The body does not establish lookup, container, removal, or release semantics. Those are possible interpretations, not behavioral guarantees.

## Interface

### Arguments

| Argument | Established representation | Use |
|---|---|---|
| Primary object | Pointer to storage accessed in four-byte units | Provides an object-relative address, a dispatch-table reference, and a later four-byte field |
| Request value | Opaque 32-bit value | Passed by value to two calls, then copied into addressable temporary storage |

The request's signedness and application meaning are not established. The function performs no explicit range check or semantic validation of it.

### Object-relative accesses

| Byte offset from primary-object address | Established use |
|---|---|
| 0 | Read as a dispatch-table reference on the continuing path |
| 0x3EC | Address passed to the initial dependency and two later dependencies |
| 0x3FC | Four-byte field read after the state-producing dependency returns |

The address at 0x3EC follows from advancing 251 four-byte elements: 251 × 4 = 1004 bytes. The field at 0x3FC follows from indexing 255 four-byte elements: 255 × 4 = 1020 bytes. The field is therefore 16 bytes beyond the repeatedly supplied object-relative address.

These accesses do not establish the full object size, the extent of an embedded region, or the meaning of either location.

Two dispatch-table locations are used:

- Primary dispatch: byte offset 0x2C from the primary object's dispatch-table reference.
- Auxiliary dispatch: byte offset 4 from the auxiliary object's dispatch-table reference.

These offsets are relative to dispatch tables, not directly to their objects. Pointer width and a complete ABI are not independently established by the supplied representation.

### Result

The function returns a 32-bit value:

- Exactly 3 when the initial dependency returns zero.
- Otherwise, on normal completion, the value returned by the primary indirect operation.

The primary operation's return bits are preserved as the result; the function does not interpret them as success or failure. Later dependency results do not replace that saved result.

### Preconditions for defined completion

Every reached access and invocation must be valid. In particular:

- The object-relative addresses supplied to dependencies must be usable under those dependencies' contracts.
- On the continuing path, the primary dispatch-table reference and its entry at 0x2C must be readable and callable.
- The field at primary-object offset 0x3FC must be readable when its read occurs.
- Temporary storage consumed by later operations must contain suitable initialized values.
- The auxiliary-pointer slot must contain a defined pointer value when the final null test executes.
- If auxiliary dispatch is reached, the pointer used for dispatch, its dispatch-table reference, and the entry at offset 4 must be valid.
- Required object and temporary lifetimes must extend through their actual uses.

There is no explicit primary-object null check. Producing a valid auxiliary pointer during the initial call is not sufficient by itself: later calls may affect the slot or the pointed-to object before final dispatch.

## Behavior

### Initial dependency and early return

The first call is to F-4e6cefe281de. Its arguments, in order, are:

1. The primary-object address advanced by 0x3EC bytes.
2. The original request value.
3. The address of a temporary auxiliary-pointer slot.

The slot has no visible initialization before this call.

The dependency result is tested against zero. Zero selects the early result 3; every nonzero value selects continuation. No particular positive success value is required.

On the zero path, the function does not inspect the auxiliary-pointer slot, invoke either indirect operation, read the field at 0x3FC, or call the remaining dependencies. This remains true if the initial dependency writes a non-null pointer before returning zero. Effects already performed by that dependency are not visibly reversed.

On the continuing path, a defined value must be available in the auxiliary-pointer slot by the time it is tested. Initialization by F-4e6cefe281de is one possible way to satisfy this requirement, but the body does not establish that dependency's output guarantees.

### Primary-object operation

After a nonzero initial result, the function reads the primary object's dispatch-table reference and invokes its entry at byte offset 0x2C.

The represented call explicitly supplies:

- The primary-object pointer.
- The original request value.

The 32-bit return value is saved for the function's eventual result.

The function does not inspect that value before continuing. A value that a caller considers an error therefore does not suppress any subsequent step.

The initial dependency runs before this dispatch-table read. The primary operation runs before subsequent state production and the later object-field read. Neither dependency is established to preserve the primary object's contents or other reachable state.

### Addressable request copy and state production

After the primary operation returns, the original request value is copied into a separate four-byte temporary cell.

F-a6e1ba6965d3 is then called with:

1. The address of temporary state storage.
2. The primary-object address advanced by 0x3EC bytes.
3. The address of the request-copy cell.

The third argument is an address, not the request value itself. The dependency may access that cell according to its unknown contract. The supplied body does not establish whether it reads, modifies, or retains the address.

A leading four-byte word at the state-storage address is used later on one branch. The complete state representation and the dependency's required write extent are not established.

### Object-field snapshot

After F-a6e1ba6965d3 returns, the function reads four bytes at primary-object offset 0x3FC and copies them into a temporary cell.

The next dependency receives the address of this copy, not the address of the object's field.

This ordering matters. Changes made by preceding calls can affect the value copied. The function does not take an earlier snapshot and does not explicitly reread the object field after the comparison call.

### Comparison and exact branch condition

F-c7e5bb3c4e39 receives:

1. The address of the temporary state storage.
2. The address of the copied object field.

Its result is compared with exactly 1:

- Result equal to 1: omit the conditional additional call.
- Result unequal to 1: perform that call.

This is not a zero-versus-nonzero condition. In particular, 2 selects the additional call just as 0 does. A representable negative result also differs from 1.

Although this dependency occupies a comparison position in the sequence, the body does not establish a read-only contract. Both supplied addresses refer to writable temporary storage, and modifications can affect subsequent behavior.

### Conditional additional operation

If the comparison result is not exactly 1, the function copies the state's leading four-byte word into two separate temporary cells. The first of these copies has no later explicit consumer in the supplied body. The second is supplied by address to F-c63d7eb9eac2.

That dependency receives:

1. The address of a separate four-byte temporary output area.
2. The primary-object address advanced by 0x3EC bytes.
3. The address of the second copied state word.

Both state-word copies occur after F-c7e5bb3c4e39 returns. Consequently, a modification of the leading state word by that dependency can affect the value supplied to F-c63d7eb9eac2.

The additional dependency receives a copy, not the original state-word address. Its temporary output is not subsequently inspected by this function, and its result does not replace the saved primary-operation result.

No removal, erasure, or other particular mutation is established by this call pattern.

### Final auxiliary-pointer test and dispatch

After the comparison and any conditional additional call, the function tests the auxiliary-pointer slot against null.

The deciding value is the slot's value when this test executes, not necessarily the value written during the initial call.

F-4e6cefe281de receives the slot's address. Its contract is unknown, so it cannot be assumed to discard that address. Later calls could modify the slot through a retained address while the temporary remains alive. Accordingly:

- An initially null slot does not guarantee omission of auxiliary dispatch.
- An initially non-null slot does not guarantee auxiliary dispatch.
- Keeping the initially referenced object alive does not establish which pointer will be tested.

If the tested slot is null, auxiliary dispatch is omitted. If it is non-null, the function uses the auxiliary pointer to obtain a dispatch-table reference and invokes the entry at byte offset 4.

The represented invocation supplies no explicit arguments and consumes no result. An implicit receiver convention is not established by this representation.

On normal completion, the function returns the saved primary-operation result.

## Side effects

The explicit direct writes shown by the body are to temporary storage:

- The request-value copy.
- The object-field snapshot.
- Two copies of the state word on the conditional branch.
- The saved primary-operation result.

Additional temporary storage is exposed to dependencies as output or in/out storage. The auxiliary-pointer slot is among the locations whose address escapes to a dependency.

There is no explicit direct assignment to a primary-object field. This does not establish read-only behavior: callees receive object-related addresses, temporary addresses, or object pointers and may modify reachable state.

The established sequence of calls and significant accesses is:

1. Initial dependency, with the auxiliary-slot address.
2. Initial-result test.
3. On continuation, primary dispatch-table access and indirect operation.
4. Request-copy initialization.
5. State-producing dependency.
6. Four-byte object-field read and temporary snapshot.
7. Comparison dependency.
8. On a result other than 1, state-word copies and additional dependency.
9. Auxiliary-slot null test and conditional auxiliary dispatch.
10. Return of the saved primary-operation result.

No dependency is assumed to preserve globals, object contents, or escaped temporary storage. Conversely, receiving an address does not establish that a dependency actually retains it or modifies it.

No explicit allocation, deallocation, ownership transfer, reference-count adjustment, synchronization, or rollback is shown. The auxiliary method's late position does not establish that it releases anything.

There is no visible compensating action if an intervening call fails to return normally. Auxiliary dispatch is reached only after earlier calls on that path return normally.

Temporary-address retention beyond the temporary's valid lifetime is not made safe by this function. The body's passing of those addresses does not establish an ownership transfer or an extended lifetime.

## Acceptance examples

These examples are conditional consequences of the static body, not runtime observations. They assume all reached accesses are valid and all described calls return normally.

### Initial dependency returns zero

If F-4e6cefe281de returns zero, the result is exactly 3.

No later dependency or indirect operation is invoked. A non-null pointer written into the auxiliary slot before that return does not change this outcome.

### Comparison equals 1 and the final slot is null

Suppose the initial result is nonzero, the primary operation returns 0x80000005, and F-c7e5bb3c4e39 returns exactly 1. Suppose also that the auxiliary slot is null when the final test executes.

F-c63d7eb9eac2 and auxiliary dispatch are omitted. The function returns the 32-bit value 0x80000005.

An initially null slot alone would not justify the auxiliary-dispatch conclusion.

### Non-Boolean comparison result

If processing continues and F-c7e5bb3c4e39 returns 2, F-c63d7eb9eac2 is invoked.

Treating every nonzero comparison result as equivalent to 1 would violate the branch condition.

### Error-like primary result

If the primary operation returns 3, the later state-producing call, field snapshot, comparison, and final auxiliary-slot test still occur.

The saved value 3 does not itself select an early exit. Whether the additional call or auxiliary dispatch occurs depends on their respective conditions.

### State production changes the object field

If F-a6e1ba6965d3 changes the field at 0x3FC from A to B, and B remains there until the subsequent read, the comparison receives a temporary containing B.

A snapshot of A taken before that dependency would not preserve the established order.

### Comparison changes the state word

If F-c7e5bb3c4e39 changes the leading state word from X to Y and returns a value other than 1, the subsequent copies use Y, assuming it remains unchanged during those copies.

F-c63d7eb9eac2 receives the address of the copy prepared for it, not the original state address.

### Initially null slot becomes non-null

Suppose the initial dependency writes null and retains the slot's address. A later call uses that address to store a valid auxiliary pointer before the final test, and the pointer remains valid through dispatch.

Auxiliary dispatch occurs despite the initially null value.

### Initially non-null slot becomes null

Suppose the initial dependency writes a valid non-null auxiliary pointer. A later call changes the slot to null before the final test.

Auxiliary dispatch is omitted, even if the initially referenced object remains alive.

### Slot remains non-null

If the slot retains a valid non-null pointer through the final test and dispatch accesses, its table entry at offset 4 is invoked after the optional additional dependency.

This condition concerns the slot's retained value and dispatch validity, not merely the lifetime of the initially supplied object.
