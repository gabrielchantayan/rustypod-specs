# F-fbbd98232430

## Purpose

F-fbbd98232430 prepares a working context, opens an input, reads a fixed-size header, installs selected header fields in a destination, processes records, and attempts cleanup.

“Import” is inferred intent, not an established format or ownership contract. Established behavior consists of the accesses, dependency calls, status selections, and ordering described below. Dependencies may modify accessible memory or globals; their preservation guarantees are unknown.

Completion does not necessarily mean returning a status. When the context’s descriptor field is nonzero during cleanup, execution calls a dependency marked nonreturning.

## Interface

The interface has nine positional arguments and a signed 32-bit result. Addresses and opaque scalar arguments are represented by 32-bit values.

| Argument | Established use |
|---|---|
| A1 | Destination address. Must be nonzero and pass the initial checks. |
| A2 | Opaque value passed to F-2b2edb028a06. |
| A3 | Required nonzero value stored in the context. No direct dereference is shown. |
| A4 | Its low 16 bits are stored in the context. |
| A5 | Required nonzero value stored in the context. |
| A6 | Stored unchanged as 32 bits in the context. |
| A7 | Optional address of a 16-bit output. Cleared at entry and conditionally populated from the header. |
| A8 | Address of a second 16-bit output. Cleared if nonzero, but later written without its own null check when A7 is nonzero. |
| A9 | Optional nonzero token passed to F-5240c36738e7 after successful record processing. |

If A7 is nonzero and header reporting is reached, A8 must also designate writable 16-bit storage. With A7 zero and A8 nonzero, A8 is initially cleared but receives no header-derived value.

The destination’s directly accessed fields extend through offset `0x90f`. Its offset-`0x08` field is read as a 32-bit auxiliary address. Calls involving that address plus `0xbf0` have additional memory requirements determined by an unknown external dependency contract.

The working context has direct accesses through offset `0x4010b`; an address at offset `0x40110` is also passed to an external dependency with a `0x48` argument. Allocation size, alignment, initialization, and the external dependency’s accessible-memory requirements are not established.

Explicitly selected statuses are:

| Status | Condition |
|---:|---|
| `-50` | Initial validation fails. |
| `-108` | Context allocation returns zero. |
| `-39` | Input-information words fail the header-size comparison. |
| `-208` | Signature validation, version-range validation, or initial record-count validation fails. |

Other checked failures retain dependency results. A separate opaque global supplies the status for failure of the required 16-bit header field. These are selected statuses, not unconditional return guarantees: cleanup may not return.

## Behavior

### Entry checks and working state

The function first writes 16-bit zero through A7 if nonzero, then through A8 if nonzero. These writes precede all destination validation.

Validation short-circuits in this order:

1. Reject zero A1.
2. Reject a nonzero 32-bit destination field at offset `0x24`.
3. Call F-65fe7bd54a4b with A1 and reject a nonzero result.
4. Reject zero A3 or A5.

Each rejection selects an immediate return of `-50`. Thus preflight can have effects even when A3 or A5 subsequently causes rejection. The destination field checked before preflight is not rechecked afterward.

F-858f5b8d5984 receives an opaque global value read for that call. A zero result returns `-108`. Otherwise, the returned context receives:

| Offset | Width | Value |
|---|---:|---|
| `0x40004` | 32 bits | A1 |
| `0x40008` | 32 bits | A3 |
| `0x40010` | 32 bits | A5 |
| `0x40014` | 32 bits | A6 |
| `0x400e0` | 16 bits | Low 16 bits of A4 |

Descriptor preparation then has a significant capture order:

- F-8157a180d901 receives `0x10`; its result is used without a visible null check.
- An opaque global descriptor value is captured **after that call and before** F-638beded7699.
- F-638beded7699 receives `0x2000` and `0x31`.
- Its result is stored at descriptor offset `0x08`.
- The previously captured global value is stored at descriptor offset `0x00`, even if F-638beded7699 changed that global.
- Byte `0x31` is stored at descriptor offset `0x0c`.
- F-external-1 receives the descriptor’s current offset-`0x08` value and `0x2000`.
- A 32-bit zero is stored at descriptor offset `0x04`.

No buffer-result failure check is visible.

The descriptor address is then stored at context offset `0x40108`. F-external-2 receives, in order, the context address plus `0x40110`, the destination’s current auxiliary address plus `0xbf0`, and `0x48`.

The argument pattern suggests initialization and a 72-byte copy, respectively, but neither external dependency’s memory semantics is established. In particular, creation of a preserved auxiliary snapshot is not a proven effect.

### Opening and header acquisition

F-2b2edb028a06 receives A2, a 48-byte automatic handle area, `0x20000`, and an opaque global value read for this call. That global read follows the preceding preparation calls.

A nonzero opening result takes the reduced cleanup path described under Side effects. A zero result causes the handle-area address to be stored at context offset `0x40000`.

F-3cbde1b148f3 then receives the handle area and storage interpreted as two adjacent 32-bit output words. If it returns zero, F-ccb28d079bbc receives the context, context address plus `0x40018`, and `0xbc`.

The latter call requests a 188-byte header. **Immediately after it returns, even on failure, the function captures the native-signature global.** A nonzero read result bypasses header processing but does not bypass this global read.

Behaviorally relevant header fields are:

| Relative offset | Width | Use |
|---|---:|---|
| `0x00` | 32 bits | Signature |
| `0x04` | 32 bits | Header extent |
| `0x08` | 32 bits | Expected input-information first word |
| `0x0c` | 32 bits | Version-like value |
| `0x10` | 32 bits | Secondary version-like value |
| `0x14` | 32 bits | Record count |
| `0x21`–`0x23` | Three bytes | Destination metadata |
| `0x30` | 16 bits | Required to equal one |
| `0x48`, `0x4c` | Two 32-bit words | Destination metadata |
| `0x58`, `0x72` | Interior addresses | Preparation arguments |
| `0xa0`–`0xa7` | Four 16-bit values | Destination metadata |

After a successful header read, initial signature recognition performs a **fresh read** of the native-signature global, separate from the captured comparison value. Equality clears context byte `0x400e3`.

Otherwise, recognition reads the alternate-signature global. Equality sets that context byte to one and calls F-2957a1337c1c with the header address. Failure to recognize either signature selects `-208`.

On either recognized path, if A7 is nonzero, the function writes the low 16 bits of the current header field at `0x0c` through A7, then the low 16 bits of the current field at `0x10` through A8.

It next compares the current header signature against the native-signature value captured immediately after the header-read call. Inequality selects `-208`, including after alternate-header processing. It does **not** preserve a successful zero status on this mismatch.

### Header validation and destination installation

After the captured-signature comparison succeeds:

1. The second input-information word must be zero.
2. The current header field at `0x08` must equal the first input-information word.

Failure selects `-39`. Describing these words as a 64-bit input size is inferred intent; the two comparisons are established.

The version-like field at `0x0c` is compared as unsigned 32-bit data and must not exceed one. The record-count field at `0x14` must be nonzero. Either failure selects `-208`.

A 16-bit context field at `0x400d4` receives the low eight bits of the secondary version-like field combined with the version-like field shifted left eight bits, truncated to 16 bits.

F-e33c4bc19e07 receives the header address, `0xbc`, and the current header extent. Its return value is not used as a status gate. It may modify the header; subsequent metadata reads are not frozen to pre-call values.

Destination writes follow this order:

| Destination offsets | Source header offsets | Width |
|---|---|---:|
| `0x904`, `0x905`, `0x906` | `0x21`, `0x22`, `0x23` | One byte each |
| `0x908`, `0x90a` | `0xa0`, `0xa2` | 16 bits each |
| `0x10`, `0x14` | `0x48`, `0x4c` | 32 bits each |
| `0x90c`, `0x90e` | `0xa4`, `0xa6` | 16 bits each |

The source word at header offset `0x4c` is captured before the write to destination offset `0x10`.

**After all these destination writes**, the function reads the opaque header-gate failure global into the retained status. It then tests the current 16-bit header field at `0x30`. If that field is not one, processing stops with the captured failure value.

If the field equals one, these calls must return zero in sequence:

1. F-f0e14e31e1b6 with the context.
2. F-3cd9fd7f0f3a with the context and header addresses at `0x58` and `0x72`.
3. F-a2cc02ba57dc with the context and header extent minus `0xbc`.

The extent for the third call is read **after both preparation dependencies return**.

The function contains no explicit rollback of the metadata writes. Later dependencies may nevertheless change those fields; persistence of the installed values is not guaranteed.

### Records and completion

The record loop starts with unsigned 32-bit index zero and a false shared flag for types 2 and 3. Its continuation comparison rereads the context’s unsigned record count each iteration. Dependencies can change that count after its earlier nonzero validation, including before the first iteration.

Each iteration requests `0x60` bytes through F-ccb28d079bbc into automatic record storage. A nonzero result ends processing. The first four 32-bit words are interpreted as signature, header extent, total extent, and type.

After each successful read, the current context byte at `0x400e3` determines whether those four words are independently byte-reversed. No direct conversion of the remaining 80 bytes is shown.

The record-signature global is then read anew for that record, **after any byte reversal**. A mismatch selects `-208`.

For a matching record:

- F-e33c4bc19e07 receives the record storage, `0x60`, and its current header extent.
- After that call, the function rereads the record’s header extent and calls F-a2cc02ba57dc with that value minus `0x60`.
- Only after a zero advance result does it inspect the current record type.

Neither dependency is established to preserve record storage. Dispatch therefore uses fields as they exist after these calls, not necessarily the initially read or reversed values.

Dispatch is:

- **Type 1:** Save the current destination byte at `0x20`, set bit `0x02`, and call F-9dac6328c13b with the context. After its normal return, reread the destination auxiliary pointer at `0x08`. Call F-external-2 with that current pointer plus `0xbf0`, the retained context-region address at `0x40110`, and `0x48`. Then restore bit `0x02` from the saved byte while retaining all other bits from the destination byte read after the external call.
- **First type 2 or type 3:** Call F-63abcb3a1d18 with the context, then set the shared flag, including when the handler returned an error.
- **Other types, or later type 2/3 records:** Read the current total and header extents at dispatch time and call F-a2cc02ba57dc with their difference.

The type-1 post-handler operations occur before testing its retained result. However, F-9dac6328c13b can modify the context region, and the auxiliary pointer can change. Even assuming copy semantics for F-external-2, restoration of the original auxiliary allocation or contents is not established.

A nonzero checked result ends the loop. After successful completion, nonzero A9 causes F-5240c36738e7 to receive A9 and the current context descriptor field. F-74efbac920ba then receives A1, followed by F-fd61d89535ad with A1 and zero. Their return values do not replace the retained status.

### Arithmetic

Extent subtraction uses 32-bit machine arithmetic. No local minimum-size or extent-order check prevents underflow. For example, a record header extent of `0x20` produces the advance argument `0xffffffc0` when subtracting `0x60`, provided that remains the value after F-e33c4bc19e07.

The loop index increments with unsigned 32-bit arithmetic. Dependency-driven count changes are not constrained by this body.

## Side effects

After successful opening, cleanup proceeds in this order:

1. Call F-49a51558071a with the automatic handle area.
2. Clear context field `0x40000`.
3. Read context field `0x400e8`; if nonzero, call F-1137792fba7d.
4. Reread context descriptor field `0x40108`.
5. If nonzero, call F-da48c7d6d5be, then F-feee9156a257, marked nonreturning.
6. If the descriptor branch is not taken, call F-1137792fba7d with the context and return the retained status.

On opening failure, the close, context-handle clearing, and secondary-resource check are bypassed. The descriptor check and final context-cleanup path remain.

The secondary-resource invocation of F-1137792fba7d has no explicit argument in the supplied representation; its final invocation explicitly receives the context. The actual calling convention remains unresolved.

No ownership transfer, release, or descriptor clearing is proven. In particular, passing the descriptor to F-5240c36738e7 does not prevent its field from being checked again during cleanup.

## Acceptance examples

These are conditional static expectations, not executed tests.

- **Null destination:** Valid output locations are cleared in A7-then-A8 order; the result is `-50`, without preflight.
- **Missing A3:** An otherwise eligible destination undergoes preflight before rejection with `-50`.
- **Descriptor-global mutation:** If buffer acquisition changes the descriptor-value global, descriptor offset `0x00` still receives the value captured before that call.
- **Header-read failure:** The native-signature global is still captured immediately after the failed read; signature recognition is skipped.
- **Alternate-header mismatch:** If alternate processing returns normally but leaves a signature unequal to the captured native value, header outputs are written when A7 is nonzero, then `-208` is selected.
- **Bad input information:** A nonzero second word selects `-39`, even when the first word matches. Header output writes have already occurred.
- **Preparation changes extent:** The pre-record advance uses the extent present after both preparation calls.
- **Record processor changes fields:** The first advance uses the post-processing header extent; dispatch uses the post-advance type; generic skipping uses dispatch-time extents.
- **Late type-1 failure:** Before cleanup, the external operation uses the then-current auxiliary pointer and potentially modified context region. The flag-bit restoration follows that operation. Original auxiliary contents and installed metadata are not guaranteed to survive.
- **Types 3 then 2:** With unchanged dispatch types and successful intervening calls, only the first uses F-63abcb3a1d18.
- **Descriptor retained at cleanup:** A nonzero descriptor field reaches the marked-nonreturning call; an ordinary status return is not established.
- **Descriptor zero at cleanup:** If all remaining calls return normally, final context cleanup precedes return of the retained status.
