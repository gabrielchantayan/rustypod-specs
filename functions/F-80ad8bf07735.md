# F-80ad8bf07735

## Purpose

F-80ad8bf07735 follows a linked sequence of records and returns when either:

- A record satisfies a three-part comparison against the supplied criteria.
- The traversal reaches a null link.

The function has no explicit return value and performs no explicit writes. Consequently, its interface does not communicate whether it found a matching record or exhausted the sequence. Termination, memory access, and possible failure to terminate are the observable distinctions supported by the supplied source.

**Inferred intent:** the comparisons resemble a search using one exact 32-bit criterion and two 16-bit record attributes, with a shared global value enabling wildcard matching for either of the latter criteria.

**Established behavior:** regardless of that interpretation, no matching-record address, Boolean result, count, or status is returned or stored.

## Interface

### Inputs

The function accepts four scalar arguments:

| Argument | Declared representation | Behavioral role |
|---|---|---|
| Root address | Signed 32-bit integer in the apparent target model | Used to derive the address of the initial link slot by adding four bytes. |
| Exact-match criterion | Signed 32-bit integer | Compared with the 32-bit field at offset 4 of each visited record. |
| First attribute criterion | Unsigned 32-bit integer | Compared with the unsigned 16-bit field at offset 12; if unequal, compared with a shared global wildcard value. |
| Second attribute criterion | Unsigned 32-bit integer | Compared with the unsigned 16-bit field at offset 14; if unequal, compared with the same shared global wildcard value. |

The first argument is represented as an integer rather than a typed pointer. Its use nevertheless requires address semantics.

The apparent 32-bit pointer and integer model is supported by the four-byte pointer arithmetic, integer-stored links, and explicit conversion of addresses through an integer representation. Portability to a different data model is not established.

### Memory layout

The starting object must provide a readable link slot at byte offset 4 from the supplied root address, unless that derived slot address itself is null and the function returns before dereferencing it.

A record reached through a non-null link has the following accessed layout:

| Byte offset | Accessed field | Width and interpretation |
|---|---|---|
| 0 | Link to the next record | A 32-bit integer interpreted as an address |
| 4 | Exact-match field | A signed 32-bit integer |
| 12 | First attribute | Unsigned 16-bit integer |
| 14 | Second attribute | Unsigned 16-bit integer |

Bytes at offsets 8 through 11 are not explicitly accessed. Their meaning is unknown.

The function does not treat the root address itself as the first candidate record. It first reads the link at root offset 4 and evaluates the record designated by that link.

### Output

There is no explicit return value.

Both a successful comparison and traversal exhaustion end with an ordinary return. No output argument or global result location is written.

## Behavior

### Traversal entry

The function forms an initial cursor address four bytes beyond the supplied root address. This cursor initially designates a link slot, not a candidate record.

Before dereferencing the current cursor, the function checks whether the cursor address itself is null. A null cursor causes an immediate return.

Otherwise, the function reads one 32-bit value from the cursor address and interprets that value as a record address.

If the loaded address is null, the function returns without accessing candidate fields. The source expresses this through a repeated traversal construct, but it does not repeatedly read the same null link: the null cursor check ends execution.

### Candidate evaluation

For each non-null candidate, comparison proceeds in this logical short-circuit order:

1. Read the signed 32-bit field at offset 4 and compare it with the exact-match criterion.
2. Only if that comparison succeeds, read the unsigned 16-bit field at offset 12 and compare it with the first attribute criterion.
3. Only if the first attribute comparison is unequal, read the shared wildcard value and compare that value with the first attribute criterion.
4. Only if the first attribute condition is accepted, read the unsigned 16-bit field at offset 14 and compare it with the second attribute criterion.
5. Only if the second attribute comparison is unequal, read the shared wildcard value and compare that value with the second attribute criterion.

A candidate matches when all of the following hold:

- Its 32-bit exact-match field equals the exact-match criterion.
- The first attribute criterion equals either the candidate’s first 16-bit attribute or the shared wildcard value.
- The second attribute criterion equals either the candidate’s second 16-bit attribute or the shared wildcard value.

A match causes an immediate ordinary return.

The wildcard alternative applies to the supplied criterion. A record attribute equal to the wildcard value does not, merely by that equality, accept every supplied criterion.

### Advancing after rejection

When a candidate fails any required comparison, the current candidate becomes the location from which the next link is read.

Thus, after rejection:

- The candidate’s address is checked against null.
- Its 32-bit link field at offset 0 is read.
- A non-null link designates the next candidate.
- A null link ends traversal.

The next-link field of a matching record is not read. It is therefore not a precondition for successful termination at that record that its outgoing link be valid or readable.

Similarly, later candidate fields need not be accessed after an earlier comparison rejects the record. An exact-match failure skips both attribute reads and all wildcard reads for that candidate. A first-attribute failure skips the second attribute.

### Integer comparison details

The two record attributes are unsigned 16-bit values. Their possible values are 0 through 65,535.

Each attribute criterion remains a 32-bit unsigned value for the equality decision; the source does not truncate it to 16 bits. A criterion greater than 65,535 therefore cannot equal a record attribute directly. It can still satisfy the attribute condition if it equals the shared wildcard value under the applicable comparison rules.

The exact-match comparison is between the supplied signed integer and the record’s signed integer field. No range check or additional normalization appears.

The declared type and width of the shared global value are absent from the supplied material. Its precise promotion or conversion behavior cannot be specified beyond its participation in equality comparisons with the unsigned criteria.

### Termination and malformed sequences

A finite sequence terminating in a null link returns, provided all reached accesses are valid.

A sequence containing a matching record returns at the first matching record reached.

There is no visited-record set, iteration bound, or cycle detection. With stable memory, a reachable cycle containing no matching record does not terminate. A cycle containing a matching record can terminate when that record is reached.

Invalid non-null addresses are not converted into a clean “not found” result. Access failure behavior depends on the execution environment; the source provides no explicit recovery path.

### Empty sequence

The root’s link slot at offset 4 contains null.

Expected behavior: read that slot and return without reading any candidate fields. No result distinguishes this return from a successful match.

### Exact match without wildcard access

The first linked record contains exact-match field 42, first attribute 7, and second attribute 9. The supplied criteria are 42, 7, and 9.

Expected behavior: evaluate those three fields and return. Neither wildcard comparison is needed. The record’s next-link field is not read.

### First-field rejection

The first linked record’s exact-match field is 41 while the supplied exact-match criterion is 42.

Expected behavior: reject the record without reading either attribute or the wildcard value, then read its next link. This remains true even if its attributes would otherwise match.

### Wildcard accepted for one attribute

The shared wildcard value compares equal to 70,000. A record has exact-match field 42, first attribute 7, and second attribute 9. The supplied criteria are 42, 70,000, and 9.

Expected behavior: the direct first-attribute comparison fails because 70,000 is not a 16-bit attribute value. The wildcard comparison accepts it. The second attribute matches directly, so the function returns.

### No low-16-bit truncation

A record’s first attribute is 1, the supplied first criterion is 65,537, and the wildcard value does not compare equal to 65,537.

Expected behavior: the first attribute condition fails. Equality is not obtained merely because the low 16 bits of the criterion are 1.

### Record-side wildcard value is not sufficient

Assume the wildcard value is 12. A record’s first attribute is 12, but the supplied first criterion is 8.

Expected behavior: the first attribute condition fails. Neither the record attribute nor the wildcard value equals the supplied criterion.

### Immediate match avoids an invalid outgoing link

A candidate’s compared fields satisfy all criteria, but its outgoing link would be invalid if followed.

Expected behavior: return at the match without reading that link. The invalid outgoing link does not itself prevent this path from completing.

### Nonmatching cycle

Two valid records link to each other, and neither satisfies the criteria. Their contents remain unchanged.

Expected behavior: traversal continues indefinitely. No explicit cycle error, timeout, or failure status is produced.
