# F-7d8b20137396

## Purpose

F-7d8b20137396 obtains a buffer object, requests bytes from an opaque source, and passes buffered input to a parsing dependency. On successful completion, it writes the object address to a caller-provided destination and returns a consumed-byte offset.

A signed counter controls continued processing. Parser-result bit `0x01` increments it. When that bit is clear and the counter is nonzero, two zero-valued parser-facing fields cause a decrement. Other results can advance the consumed offset by a primary-size value.

Reading a structured item with possible nested contents is **inferred intent**, not an established format contract. The source abstraction, grammar, and semantic meanings of the parser outputs remain unknown.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

### Inputs and return value

The function takes:

- An opaque **32-bit source token**, forwarded unchanged to F-81e98a37a112.
- An **output address** identifying a writable 32-bit slot. The function performs no local null or accessibility check.

Its return value is a signed 32-bit integer:

- On completion, the consumed-byte offset.
- On explicit failure, −1.

The successful result is not necessarily the number of bytes fetched. Unconsumed bytes may remain buffered. Nonnegative success results and an unambiguous distinction from −1 require external constraints on sizes, cursor updates, and arithmetic; the function does not enforce those constraints.

### Object and address layout

F-83f21a307fbe supplies a 32-bit object address. Zero selects acquisition failure.

A 32-bit word at object byte offset 4 is used as the data-region address. The function reads that field before each source-transfer call and before each parser call. It does not cache one data address for the entire operation.

No other object fields are directly inspected. Object size, capacity representation, alignment requirements, and allocation semantics are unknown. F-9a8ea7637eda returns a zero/nonzero status; its result does not replace the retained object address.

### Parser-facing storage

Each invocation of F-fa1c60bee3f0 receives, in order:

1. An address of three contiguous 32-bit cursor words.
2. An address of five contiguous 32-bit output words.
3. An address of a separate 32-bit output word.
4. An address of four auxiliary bytes.
5. A signed 32-bit available-byte count.

Immediately before each parser call, the function initializes the first cursor word to the current data address plus the consumed offset. It does not explicitly initialize the remaining cursor words, the five output words, the separate output word, or the auxiliary bytes.

Only the first cursor word, the first word of the five-word area, and the separate output word are subsequently read by this function. They are called the **cursor word**, **primary-size word**, and **secondary word** below. These names describe their use, not an established parser schema.

The parser returns a 32-bit flag value. Only bits `0x80` and `0x01` affect this function.

The parser receives addresses of storage that remains in use across later dependency calls. Its pointer-retention behavior is unknown. Values read later therefore cannot automatically be treated as unchanged snapshots from parser return.

## Behavior

### Acquisition and initialization

The fetched offset, consumed offset, and counter begin at zero.

F-83f21a307fbe is called once. If it returns zero, the function calls F-4fc89ec41a6d with `(0x0d, 0x6b, 0x41, 0, 0)` and returns −1. It does not directly write the output slot or call F-28097aea1ffc on this path.

For a nonzero object address, the function calls F-d2eac1cec894 once before processing input. No result from that call is used.

### Lookahead acquisition

At the beginning of each processing iteration, available bytes are represented by fetched offset minus consumed offset, using signed 32-bit arithmetic.

When that difference exceeds eight, the function proceeds directly to parsing.

Otherwise, it computes a request amount of eight minus the difference and:

1. Calls F-9a8ea7637eda with the object and an absolute requested extent equal to fetched offset plus request amount.
2. On a zero result, takes the `0x41` diagnostic failure path.
3. Reads the current data address from object offset 4.
4. Calls F-81e98a37a112 with the source token, data address plus fetched offset, and request amount.

A positive transfer result is added to the fetched offset. No local check ensures that the result is at most the request.

A zero result leaves the fetched offset unchanged and still permits parsing.

For a negative result:

- Equal fetched and consumed offsets select the `0x8e` diagnostic failure path.
- Unequal offsets permit parsing without changing either offset.

The latter condition is inequality, not a validated positive amount of buffered data.

There is only one lookahead transfer attempt per iteration. A short positive result does not cause another lookahead attempt before parsing.

Exactly eight available bytes still select this branch: the capacity request uses the current fetched offset, and the transfer request is zero. Neither call is omitted.

### Parser call and status processing

The function reads the current data address, adds the consumed offset, and retains that address as the pre-call cursor position. It writes the same address to the cursor word, then invokes F-fa1c60bee3f0 with the storage described above and the current available-byte count.

If returned flag `0x80` is clear, processing proceeds to cursor accounting.

If `0x80` is set:

1. F-6a16089b9def is called.
2. Its 32-bit result is masked with `0x0fff`.
3. A masked value other than `0x09b` causes the object to be passed to F-28097aea1ffc, followed by return −1.
4. A masked value of `0x09b` causes F-5b7d885746de to be called, after which processing continues.

The fatal status path does not issue a new F-4fc89ec41a6d diagnostic and does not account for cursor movement.

**Cursor accounting occurs after accepted status handling.** When `0x80` is accepted, the cursor word is read only after both F-6a16089b9def and F-5b7d885746de return. The consumed offset is increased by that observed cursor word minus the retained pre-call cursor position.

The function does not snapshot the cursor word immediately after parser return. If an intervening call can mutate the storage through a retained alias, the later value participates in cursor accounting. Whether such mutation can occur is unknown.

The primary-size and secondary words are also inspected, when their branches require them, only after these status-handling calls. Their values are not protected parser-return snapshots.

No local check verifies that the cursor moves forward, remains within the supplied region, or produces a representable displacement.

### Increment takes precedence

After cursor accounting, returned flag `0x01` takes priority over size processing.

If set, the counter is incremented and processing returns directly to lookahead acquisition. Neither size word is used for payload advancement or counter decrement on that iteration. This direct continuation does not first apply the later signed-positive counter test.

When both tested flag bits are present, `0x80` processing occurs first. The increment is reached only if that processing permits continuation.

### Size selection and counter decrement

With bit `0x01` clear:

- If the counter is zero, the function takes the primary-size path without consulting the secondary word.
- If the counter is nonzero and the primary-size word is nonzero, it takes the primary-size path without needing the secondary word.
- If the counter is nonzero, the primary-size word is zero, and the secondary word is nonzero, it also takes the primary-size path.
- If the counter is nonzero and both words are zero, it decrements the counter and skips the primary-size path.

The secondary word determines whether to decrement in the zero-primary case. It is never substituted as a payload length.

### Primary-size path and distinct reads

The function compares current available bytes with the primary-size word using a signed 32-bit comparison.

If available bytes are insufficient, it computes a deficit from the primary-size word minus available bytes. These primary-size reads occur **before** the following capacity and transfer calls.

It then calls F-9a8ea7637eda with the object and fetched offset plus deficit. A zero result selects the `0x41` diagnostic failure path.

After a nonzero result, source transfers repeat while the signed remaining deficit is positive. Each transfer:

- Uses a newly read data address plus the current fetched offset.
- Requests the entire remaining deficit.
- Fails through the `0x8e` diagnostic path if the result is zero or negative.
- Otherwise adds the result to fetched offset and subtracts it from remaining deficit.

The requested deficit is maintained independently after its initial computation. It is not recomputed from the primary-size word after each call.

After refill completes—or immediately if the initial comparison requires no refill—the function **reads the primary-size word again** and adds that observed value to the consumed offset.

Consequently, there is no preserved primary-size snapshot spanning refill. Mutation through a retained alias during capacity or transfer calls can change the final increment without changing the already-computed refill amount. The function does not revalidate available bytes against a changed final size.

Negative primary sizes are not rejected. With nonnegative available bytes, a negative primary size ordinarily bypasses refill and reduces the consumed offset. Other cases follow the signed comparison and arithmetic; safe behavior is not established for invalid ranges or overflow.

### Completion

After size processing or counter decrement, processing repeats only if the signed counter is greater than zero.

Otherwise, the function writes the retained object address to the output slot and returns the consumed offset.

A result processed while the counter is already zero need not be a terminator: it takes the primary-size path and can complete immediately afterward.

There is no direct buffer compaction, trimming, trailing-byte validation, or successful-path call to F-28097aea1ffc.

### Arithmetic and validity conditions

No explicit checks prevent:

- Overflow in offset differences, additions, deficits, or counter updates.
- Invalid address-plus-offset calculations.
- Transfers reporting more than requested.
- Negative sizes or backward cursor movement.
- Reads from parser-facing storage that the dependency has not initialized.

A safe execution requires valid storage, dependency-compatible initialization, valid address ranges, and representable arithmetic. The supplied evidence does not establish portable or memory-safe behavior outside those conditions.

## Side effects

Both offsets are measured from the data-region base. Capacity requests use absolute end positions, not just additional byte counts.

### Output and ownership boundary

The function directly writes the output slot once, only on successful completion. Explicit failures leave it directly unwritten. This does not guarantee unchanged memory if callees can access an alias.

Operationally:

- Successful acquisition supplies an object retained through processing.
- Completion exposes that object through the output slot.
- Explicit failure after acquisition passes the object to F-28097aea1ffc.
- Acquisition failure and successful completion do not call that dependency.

Allocation, ownership transfer, reference retention, destruction, and actual memory release are not established.

### Diagnostics and call ordering

Acquisition and capacity failures use `(0x0d, 0x6b, 0x41, 0, 0)`.

Selected source-transfer failures use `(0x0d, 0x6b, 0x8e, 0, 0)`.

For these failures after acquisition, diagnostic reporting precedes F-28097aea1ffc. Fatal parser status instead goes directly to that dependency without a new diagnostic call.

No dependency is assumed to preserve global state or storage reachable through retained pointers. In particular, accepted-status handling precedes cursor and size reads, and payload refill separates the size reads used to calculate the deficit from the final size read used for advancement.

## Acceptance examples

These are **conditional static expectations**, not executed tests. Unless specified otherwise, calls return normally, addresses are valid, arithmetic is representable, required storage is initialized, transfers do not exceed requests, and parser-facing words remain unchanged between the relevant reads.

1. **Acquisition failure.**  
   A zero acquisition result causes the `0x41` diagnostic and return −1, without a direct output write or cleanup call.

2. **Flat item with buffered trailing bytes.**  
   The first transfer supplies eight bytes. The parser advances the cursor by two, clears both tested flags, and supplies primary size three. The counter is zero, so the function completes with return value five and the object in the output slot. Three fetched bytes remain beyond the consumed offset.

3. **Short lookahead.**  
   An initial request for eight returns two. The parser receives available length two without another lookahead transfer first. An initial zero transfer similarly permits a parser call with available length zero.

4. **Exactly eight available.**  
   An iteration starting with eight available bytes makes a capacity call for the existing fetched extent and a zero-length transfer call. If that transfer returns zero, parsing proceeds with eight available.

5. **Negative lookahead result.**  
   With three buffered bytes, a negative transfer result still permits parsing those bytes. With equal fetched and consumed offsets, a negative result instead produces the `0x8e` diagnostic, cleanup call, and −1.

6. **Counter priority and closure.**  
   A result with `0x01` set increments the counter even if both size words are zero. A later result with that bit clear, a nonzero counter, and both words zero decrements the counter. A decrement from one to zero permits completion.

7. **Secondary is not a length.**  
   With a positive counter, primary size zero, secondary value seven, and `0x01` clear, the function selects the primary-size path but uses zero, not seven. With nonnegative available bytes, no payload advance occurs and processing continues.

8. **Refill with a stable primary-size word.**  
   After cursor accounting, one byte is available and primary size is four. The deficit is three. Transfers returning one and then two complete refill. **If the primary-size word remains four throughout the capacity and transfer calls**, the final addition is four. A zero or negative refill result instead causes the `0x8e` diagnostic, cleanup, and −1.

9. **Primary-size mutation during refill.**  
   Under the same initial conditions, suppose a dependency changes the primary-size word from four to six through a retained alias during refill. The deficit remains based on three missing bytes. After successful refill, the final reread adds six, without a new sufficiency check. Whether dependencies can perform this mutation is documented_only.

10. **Accepted status and delayed storage reads.**  
    With `0x80` set and masked status `0x09b`, both status dependencies run before cursor accounting. If they can change the cursor word or size words through retained aliases, subsequent processing uses the values observed after those calls. A different masked status causes cleanup and −1 before cursor accounting or size processing.
