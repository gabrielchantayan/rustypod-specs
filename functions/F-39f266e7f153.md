# F-39f266e7f153

## Purpose

F-39f266e7f153 performs staged dispatch using a context object and a record. Its established behavior is:

1. Optionally invoke F-c55da93bc3b9 for a particular initial record classification.
2. Select and invoke one of two context-associated callbacks using a fresh classification.
3. If that callback returns zero, optionally invoke a third callback when a record value matches a context value.
4. Return the first nonzero callback result, or zero.

The optional preliminary call does not itself determine the return value. Its observable effects may nevertheless change subsequent dispatch because relevant record and context fields are read again after that call.

Interpreting the record as an event or message, and the context as an event-handling object, is inferred intent rather than an established interface guarantee. This contract uses “record,” “context,” “type,” and “subtype” as descriptive labels only.

## Interface

### Inputs and result

The function accepts two arguments:

- **Context address:** the address of an object containing a dispatch-table pointer and other fields.
- **Record address:** the address of a record whose fields are interpreted according to its current type.

It returns a 32-bit integer in the supplied representation. Zero and nonzero are the only distinctions made between callback results. A returned nonzero value is propagated unchanged; it is not normalized to one, converted into an error code, or otherwise interpreted.

There is no established null-input behavior, argument validation, allocation failure convention, or exception-handling contract.

## Behavior

### 1. Preliminary classification and optional call

The function first reads the four-byte type at record offset `0x04`.

If that value is not `0x16`, the preliminary stage performs no nested-record access and makes no preliminary call.

If it is `0x16`, the function:

- Reads the nested-record address from record offset `0x08`.
- Reads the four-byte subtype at nested-record offset `0x04`.
- Tests whether subtracting `0x2500` from that subtype produces `2`.

For ordinary 32-bit values, the matching subtype is `0x2502`. This is not a range test: neighboring values do not qualify.

On a match, the function reads the four-byte integer at context offset `0xE4`, converts it to a character-sized value, and invokes F-c55da93bc3b9 with:

- The original context address.
- The converted character-sized argument.

The helper’s result, if any, is not tested or propagated. If the helper returns normally, execution proceeds to primary dispatch.

The conversion is to a one-byte character value, not a four-byte value forwarded unchanged. Character signedness and the callee’s interpretation of values whose high bit is set are not established. The supplied representation also does not settle the language-level overflow semantics of the preceding subtraction for extreme signed values; this limitation does not affect the unambiguous matching example `0x2502`.

### 2. Fresh classification and primary dispatch

The function next reads the record type again. It does not reuse the preliminary stage’s type, nested-record address, or subtype.

For a current type of `0x16`, it reads the current nested-record address from record offset `0x08`, then reads that nested record’s subtype at offset `0x04`.

The special primary callback is selected only when both current conditions hold:

- Record type is `0x16`.
- Nested subtype is `0x2A`.

In that case, the function reads the dispatch-table address from context offset `0x00` and obtains the callback address from table offset `0x10C`.

For every other classification, it reads the dispatch-table address from the context and obtains the callback address from table offset `0x110`.

Exactly one of these two primary callbacks is invoked if execution reaches this stage and the accesses and invocation succeed. Its arguments are the original context and record addresses. Neither a copy of the record nor the nested-record address is substituted.

The primary callback returns a 32-bit integer:

- If the result is nonzero, the function returns that exact value immediately.
- If the result is zero, the function continues to the secondary stage.

A nonzero primary result prevents all later record checks, comparison-field reads, and secondary dispatch by this function.

The fresh classification is significant. For example, F-c55da93bc3b9 may change the record so that the special primary callback is selected, even though the preliminary subtype was `0x2502`. Conversely, no preservation of the context’s dispatch-table pointer is assumed across the helper call.

### 3. Conditional secondary dispatch

This stage is reached only after the primary callback returns zero.

The function reads the record type again, after the primary callback has completed.

If the current type is not `0x0F`, the function returns zero without reading the comparison field at context offset `0x50` and without invoking the secondary callback.

If the current type is `0x0F`, the function reads, in order:

1. The four-byte value at record offset `0x08`.
2. The four-byte value at context offset `0x50`.

It compares the two values for equality. The record field is used as a value in this stage, not dereferenced as a nested-record address.

If they differ, the function returns zero.

If they are equal, the function reads the current dispatch-table address from context offset `0x00`, obtains the callback address at table offset `0xE0`, and invokes that callback with the original context and record addresses.

A nonzero secondary result is returned unchanged. A zero secondary result produces a final return value of zero. No further record or context checks are performed after that callback returns.

### 4. Call ordering and termination

On a normally completed invocation:

- F-c55da93bc3b9 is called zero or one times.
- Exactly one primary callback is called.
- The secondary callback is called zero or one times.

The maximum sequence is preliminary helper, primary callback, then secondary callback. There are no retries or loops.

All later behavior is conditional on earlier callees returning normally. Handling of a callee that does not return, faults, throws across the call boundary, or otherwise transfers control outside the shown path is not established.

## Side effects

The function contains no direct writes to context, record, nested record, or dispatch-table storage. It performs no explicit allocation, deallocation, retention, release, or ownership transfer.

Its observable effects consist of reads, dependent calls, and its return value. Called dependencies may have additional effects that are not described by the supplied evidence.

The function preserves the original context and record addresses as call arguments, but it does not preserve snapshots of their contents. Consequently:

- Preliminary-helper changes can affect primary callback selection.
- Primary-callback changes can affect the secondary type test and equality comparison.
- A dispatch-table replacement by an earlier dependency can affect a later callback lookup.
- A dependency that invalidates storage needed by a later stage can violate the function’s access preconditions.

There is no demonstrated synchronization. Repeated reads establish ordering between the shown stages, not a concurrency protocol or an atomic snapshot of a record.
