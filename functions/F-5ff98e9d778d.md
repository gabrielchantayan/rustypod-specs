# F-5ff98e9d778d

## Purpose

F-5ff98e9d778d conditionally copies two 32-bit fields from a supplied base record and supplies two additional 32-bit values. The additional values are either the constant 65,536 or results returned by dependency F-73d099a86adb.

Every normally completing invocation returns a 32-bit zero. The return value does not distinguish omitted outputs, an absent related record, or particular dependency results.

**Established static behavior:** the function captures a related-record address before any output store. A nonzero captured address selects two dependency calls, even when neither derived output is requested.

**Inferred intent:** the default value and shifted related-record fields may participate in fixed-point calculations. Neither a fixed-point format nor the dependency’s mathematical operation is established by the supplied evidence.

## Behavior

### Initial address capture

The first explicit record access reads the 32-bit related-record address from base offset 0x58.

The captured value determines whether dependency calls occur and supplies the related-record address for both calls. The function does not explicitly reload the base record’s address field afterward.

An output store that aliases that field can therefore change the field in memory without changing the related-record address already selected for this invocation. Likewise, changing the field during the first dependency call does not redirect the second call’s related-record access.

This retention concerns the address value only. It does not imply that storage at that address remains unchanged or valid.

### Direct-output handling

When the first direct output is nonnull, the function reads the 32-bit field at base offset 0x12C and stores that value to the first direct output.

When the second direct output is nonnull, it subsequently reads the 32-bit field at base offset 0x130 and stores that value to the second direct output.

The first direct-output store precedes the second direct-field read. A skipped direct output causes neither its associated field read nor its store.

There is no validation, clamping, scaling, or error interpretation of either direct field.

These operations are sequential observations, not a snapshot of both fields. If the first output aliases the second field, the second field is read after that overwrite. Either direct output may also alias related-record fields or other storage needed later. No non-aliasing check is visible.

### Default and dependency selection

Each derived value has the default bit pattern 0x00010000, decimal 65,536.

If the captured related-record address is zero:

- Neither dependency invocation occurs.
- Neither related-record field is read.
- Both derived values remain 65,536.

If the captured address is nonzero, F-73d099a86adb is invoked twice, in order:

| Invocation | First argument | Second argument | Returned value |
|---|---|---|---|
| First | Unsigned 16-bit field read at related offset 0x0C, extended to 32 bits and shifted left by six | Fresh 32-bit read at base offset 0x130 | First derived value |
| Second | Unsigned 16-bit field read at related offset 0x0E, extended to 32 bits and shifted left by six | Fresh 32-bit read at base offset 0x130 | Second derived value |

On a normally completing nonzero-address path, both calls occur regardless of whether either derived output is nonnull.

The first invocation returns before the second invocation’s argument reads. Thus:

- The first invocation may change the second related-record field before it is read.
- It may change the base field used as the second argument to the second invocation.
- It may affect storage validity or other dependency preconditions.
- It is not assumed to preserve global or externally accessible state.

Earlier direct-output stores may also change either invocation’s argument sources. The relevant values are those present when each individual read occurs, not necessarily those present at entry.

Within either invocation’s argument preparation, the relative order of the related-field read and base-field read is not established by the supplied representation. The contract does not require a finer ordering between those two reads.

### Integer arithmetic

A related-record field contributes an unsigned value from 0 through 65,535. It is extended to 32 bits before being shifted left by six bits.

The resulting first argument is the field value multiplied by 64:

| Field value at its argument read | First argument |
|---:|---:|
| 0 | 0 |
| 1 | 64 |
| 65,535, or 0xFFFF | 4,194,240, or 0x003FFFC0 |

The result fits within 32 bits for every possible field value. Its low six bits are zero. No sign extension occurs: a field containing 0xFFFF at the relevant read does not produce a negative first argument.

The base field used as the second argument undergoes no explicit arithmetic, normalization, or range check.

Dependency return values are retained as 32-bit data. No visible check interprets them as success, failure, or a reason to retain the default.

### Final output stores

After the related-record branch completes, the function:

1. Stores the first derived value if the first derived output is nonnull.
2. Stores the second derived value if the second derived output is nonnull.
3. Returns zero.

Both dependency calls, when selected and normally returning, finish before either derived-output store.

If the derived outputs identify the same writable 32-bit location, the second store overwrites the first. If a derived output aliases an earlier direct output or record field, its later store may overwrite that storage.

A statement that a direct output receives a value describes its store, not a guarantee that the value remains there at function return. Later output stores or dependency effects may change the same location.

## Acceptance examples

These examples are conditional consequences of static evidence, not runtime test results.

### Absent related record

Suppose the initial related-record address read yields zero. All requested accesses are valid, the four outputs are distinct and do not overlap the records, and the direct fields remain unchanged until their reads.

Then:

- The direct outputs receive the respective fields at offsets 0x12C and 0x130.
- Both derived outputs receive 65,536.
- No dependency invocation occurs.
- Normal completion returns zero.

### No requested outputs

With all four output addresses null, the initial related-record address is still read.

If that read yields zero, no direct field or related-record field is explicitly read.

If it yields nonzero, both dependency invocations are still selected, with their associated argument reads. Provided the accesses and invocations complete normally, the function returns zero.

Null outputs therefore do not eliminate dependency effects on the nonzero-address path.

### Unsigned input boundaries at the actual reads

Suppose the captured related-record address is nonzero and:

- The field at related offset 0x0C contains 0xFFFF **when the first invocation’s related-field argument read occurs**.
- The field at related offset 0x0E contains 0x0001 **when the second invocation’s related-field argument read occurs**.
- All required accesses and both invocations complete normally.

The first arguments are then 4,194,240 and 64, respectively.

Merely placing these patterns in the record before entry and preserving readable storage is insufficient. Earlier direct-output stores could alter either field, and the first dependency invocation could alter the second field before its read.

If the dependency returns particular 32-bit results, each requested derived-output store writes its corresponding result. Later overlapping stores can still replace an earlier stored value.

### Direct-output alias changes a later read

Suppose the first direct field contains 7 when read, and the first direct output points to base offset 0x130.

The first direct-output store writes 7 into the second field. If the second direct output is requested and nothing else intervenes to change that field, its subsequent store copies 7.

If the related-record path is selected, the first dependency invocation also receives 7 as its second argument, provided no further intervening mutation changes that field.

### Entry-time related fields do not fix call arguments

Suppose the related fields initially contain 0xFFFF and 0x0001, but a direct-output store overwrites one of those fields before its argument read.

The affected invocation uses the unsigned 16-bit value actually read after that store, shifted left by six. The initial pattern does not determine the argument.

Similarly, if the first dependency invocation changes the second related field to 2 and that value remains present until the second field read, the second invocation’s first argument is 128, not 64.

### Shared derived-output location

If both derived outputs identify the same valid 32-bit location and execution completes normally, the second derived-output store determines its contents at return.

With no related record, the location contains 65,536. With a selected related record and two normally returning calls, it contains the second dependency result.

### Mutation during the first dependency invocation

If the first dependency invocation changes base offset 0x130 and returns normally, the second invocation uses the changed value if it remains present until that argument read.

If it changes related offset 0x0E, the second invocation likewise uses that field’s value at its later read. These deductions require the affected storage to remain readable; normal return of the first invocation alone does not establish that validity.
