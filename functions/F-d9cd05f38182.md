# F-d9cd05f38182

## Purpose

F-d9cd05f38182 performs event-specific handling for an owner object and, unless that handling explicitly suppresses further processing, obtains a recipient through the owner and forwards the event to that recipient.

Two event kinds receive special handling:

- **15:** Compare the event target with two owner-relative addresses. The first match invokes two dependencies. The second match invokes a dependency and clears one state byte.
- **22:** Invoke a dependency that supplies a condition field. If that field is nonzero, invoke an owner-directed dependency whose nonzero result suppresses recipient lookup and forwarding.

Other event kinds receive no special handling before recipient lookup.

“Owner,” “event,” “target,” and “recipient” describe their structural roles. Application-level meanings are not established. In particular, the evidence does not identify the event kinds, the state byte’s purpose, or the significance of the kind-22 helper constant.

## Interface

### Inputs and representation

The function receives two arguments:

1. **Owner address:** The base address of an object used for interior-address comparisons, a conditional state-byte write, and dispatch-table lookup.
2. **Event address:** An integer-valued address used to read event fields and passed onward to dependencies.

The supplied representation uses 32-bit integers and 32-bit address-bearing fields. All offsets in this contract are byte offsets unless explicitly stated otherwise.

| Storage | Offset | Width | Role |
|---|---:|---:|---|
| Owner | 0 | 4 bytes | Dispatch-table address |
| Owner | 0x548 | Address identity only | First target-comparison location |
| Owner | 0x574 | Address identity only | Second target-comparison location |
| Owner | 0x5A0 | 1 byte | State byte conditionally cleared |
| Event | 4 | 4 bytes | Event kind |
| Event | 8 | 4 bytes | Target address, read on the kind-15 path |
| Result from F-682adfd5a561 | 8 | 4 bytes | Condition field for kind-22 handling |

| Recipient | 0 | 4 bytes | Recipient dispatch-table address |
| Recipient dispatch table | 0x30 | 4-byte callable-address field | Event forwarding |

The two owner-relative comparison locations are addresses, not values loaded from those locations. Matching a target does not require reading their contents.

The state clear affects exactly one byte. The four-byte scale used to calculate the owner-relative address does not widen that write.

### Output

There is no explicit return value or returned status.

Normal completion occurs in one of three ways:

- Kind-22 handling produces a nonzero suppression result, causing immediate completion.
- Recipient lookup returns a null address, causing completion without forwarding.
- Recipient lookup returns a nonnull address, and the forwarding dependency returns normally.

Other dependency results are either used internally as described below or ignored. None becomes an explicit result of this function.

### Preconditions and invalid inputs

Every access and call actually reached must be valid:

- The event-kind field must be readable.
- The event-target field must be readable whenever a kind-15 comparison is reached.
- Reached owner-relative address calculations must be valid.
- The state byte must be writable if the second kind-15 match succeeds.
- Reached dispatch-table fields must be readable and contain callable targets.
- A normally returned result from F-682adfd5a561 must support a four-byte read at offset 8.
- A nonnull recipient must remain valid for its dispatch-table reads and forwarding call.

These requirements are path-dependent. For example, suppression on the kind-22 path avoids the owner dispatch-table lookup.

No explicit input validation or error-reporting protocol is visible. Null or invalid addresses, invalid callable entries, and invalidated storage are not converted into documented graceful failures.

## Behavior

### Event-kind selection

The function first reads the four-byte event kind at event offset 4 and compares it with 15.

If it equals 15, the function enters kind-15 handling. It does not subsequently enter kind-22 handling during that invocation, even if a dependency changes the event kind.

If the first comparison fails, the supplied representation reads the event-kind field for a comparison with 22. A stable snapshot shared by both comparisons is not established. If that later comparison equals 22, kind-22 handling runs. Otherwise, execution proceeds directly to recipient lookup.

These are source-visible access and control-flow properties, not guarantees about synchronization or machine-level concurrent observation.

### Kind 15: first target match

The function reads the four-byte event target at offset 8 and compares that address with owner plus 0x548.

If they match, it invokes:

1. F-936a8728139d, with no explicit arguments.
2. F-df68e84bb5d6, with the owner address.

Neither result is used. There is no explicit early return after either call.

Both calls must return normally for execution to reach the second target comparison. Their effects are unknown; neither is established to preserve the target, the owner, global state, or storage needed by subsequent operations.

If the first comparison fails, both calls are skipped.

### Kind 15: second target match

After the first comparison and any calls it triggered, the function reads the event target again. It compares that later value with owner plus 0x574.

This comparison is independent of the first match. It is not an alternative branch chosen only when the first comparison fails.

If the second comparison succeeds:

1. F-936a8728139d is invoked with no explicit arguments.
2. After that call returns normally, zero is written to the single byte at owner plus 0x5A0.

The byte’s previous value is not read or tested. No adjacent byte is directly written by this operation.

The second match is decided before its F-936a8728139d call. Consequently, a target change made by that call does not cancel the already-selected clear. The clear still requires the owner-relative destination to remain valid and writable.

The two comparison addresses differ by 0x2C bytes. Under valid object addressing, an unchanged target cannot match both. Both actions can nevertheless occur if the first target read matches owner plus 0x548 and the later target read, **after both first-match calls return**, matches owner plus 0x574.

A temporary change during the first F-936a8728139d call is insufficient by itself. F-df68e84bb5d6 runs afterward and may replace that value before the second read.

After kind-15 handling finishes, recipient lookup follows. Neither match directly suppresses forwarding.

### Kind 22: conditional suppression

The function invokes F-682adfd5a561 with:

- The original event-address value.
- The 32-bit integer constant 0xF00, equal to 3840.

It then reads a four-byte condition field at offset 8 from the returned address. There is no intervening null check.

If the field is zero, F-a79c5a5f93e5 is skipped and execution proceeds to recipient lookup.

If the field is nonzero, F-a79c5a5f93e5 is invoked with the owner address:

- A zero result permits recipient lookup.
- Any nonzero result causes immediate completion, without recipient lookup or forwarding.

Both decisions use zero versus nonzero, not a positive-value test. A negative nonzero integer has the same branch effect as a positive nonzero integer.

A null result from F-682adfd5a561 is not established as an optional “no result” outcome. The next visible operation requires readable storage at result plus 8.

### Recipient lookup and forwarding

Unless kind-22 handling has already caused immediate completion, the function:

1. Reads the owner’s dispatch-table address at owner offset 0.
2. Reads the callable address at dispatch-table offset 0xCC.
3. Invokes that dependency and interprets its result as a recipient address.

The supplied representation shows no explicit arguments to the lookup invocation. An implicit owner or receiver argument is not established and must not be added to the contract.

If the result is null, processing ends. No recipient dispatch-table access follows.

For a nonnull result, the function:

1. Reads the recipient’s dispatch-table address at recipient offset 0.
2. Reads the callable address at dispatch-table offset 0x30.
3. Invokes that dependency with the recipient address and the original event-address value.

The forwarding result is unused. There is no subsequent explicit operation.

The event address is forwarded unchanged, but the event’s contents need not be unchanged. Earlier dependencies may have modified them. Likewise, recipient lookup uses the owner’s dispatch state as reached after special handling, not a dispatch-table snapshot captured at entry.

## Side effects

### Direct effects and ordering

The only explicit data write is the conditional one-byte zero write at owner plus 0x5A0.

The visible body does not explicitly allocate or release storage, copy an object, replace the event target, store the recipient into the owner, restore dependency-modified state, or record an error.

The significant ordering constraints are:

- On a first kind-15 match, F-936a8728139d precedes F-df68e84bb5d6.
- The second target read follows both of those calls if they execute and return normally.
- On a second kind-15 match, F-936a8728139d precedes the state-byte clear.
- Recipient lookup follows completed special handling.
- Recipient dispatch follows a nonnull lookup result.

No earlier dependency’s mutation is guaranteed to survive a later dependency. In particular, the second kind-15 action depends on the value at the second read, not on whether either earlier call temporarily wrote a particular target.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Unless stated otherwise, reached accesses are valid and dependencies return normally.

1. **Ordinary event, recipient present.**  
   If both event-kind comparisons observe a value other than 15 or 22 and lookup returns a nonnull recipient, none of the four named dependencies is invoked. Lookup is followed by forwarding with that recipient and the original event address.

2. **Ordinary event, recipient absent.**  
   Under the same kind conditions, a null lookup result ends processing without reading a recipient dispatch table or invoking forwarding.

3. **First kind-15 action only.**  
   If the first kind comparison selects 15, the first target read equals owner plus 0x548, and the second target read does not equal owner plus 0x574, the order is F-936a8728139d, F-df68e84bb5d6, then lookup. This function performs no state-byte clear on that path.

4. **Second kind-15 action only.**  
   If the first target read does not match owner plus 0x548 but the second equals owner plus 0x574, F-df68e84bb5d6 is skipped. F-936a8728139d runs once, followed by the one-byte clear and lookup.

5. **Both kind-15 actions.**  
   If the first target read equals owner plus 0x548 and the target equals owner plus 0x574 when reread after **both** F-936a8728139d and F-df68e84bb5d6 return, the function invokes F-936a8728139d a second time. After that invocation returns, the state byte is cleared, then lookup occurs.

6. **A transient target change is insufficient.**  
   If the first F-936a8728139d invocation changes the target to owner plus 0x574 but F-df68e84bb5d6 changes it back to owner plus 0x548 before returning, the second comparison fails. There is no second F-936a8728139d invocation and no direct state-byte clear.

7. **Kind 15, neither comparison matches.**  
   If neither target read matches its respective comparison address, no named dependency is invoked and no state-byte write occurs. Lookup still follows.

8. **Kind 22, zero condition field.**  
   F-682adfd5a561 receives the event address and 3840. If its returned storage contains zero at offset 8, F-a79c5a5f93e5 is skipped and lookup follows.

9. **Kind 22, nonzero suppression result.**  
   If the condition field is nonzero and F-a79c5a5f93e5 returns any nonzero integer, no recipient lookup or forwarding occurs.

10. **Kind 22, zero suppression result.**  
    If the condition field is nonzero but F-a79c5a5f93e5 returns zero, lookup follows. Forwarding then depends solely on whether lookup returns a nonnull recipient.

11. **Invalid helper result.**  
    If F-682adfd5a561 returns an address that cannot support the required offset-8 read, no graceful-return behavior is established. The contract does not treat this as equivalent to a zero condition field.
