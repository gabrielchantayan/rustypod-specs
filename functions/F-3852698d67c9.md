# F-3852698d67c9

## Purpose

F-3852698d67c9 adjusts a stored element count by a signed delta, derives a corresponding byte quantity, and conditionally delegates a storage-size change to F-7eca6144d13b.

The established behavior is a two-stage growth policy and a separate negative-delta policy:

- When the derived byte requirement exceeds the recorded capacity, first request a potentially larger size. If that request fails, retry with the exact derived requirement.
- When the derived requirement does not exceed capacity and the delta is negative, request a size that preserves the previously recorded difference between capacity and used bytes.
- Otherwise, update the count and used-byte fields without calling the dependency.

The interpretation as a resizable collection is inferred intent. The supplied material establishes field arithmetic, comparisons, dependency calls, return handling, and direct writes; it does not establish the underlying allocation mechanism or collection type.

## Interface

### Inputs

The function takes two integer-valued inputs:

1. **Object address.** Identifies a writable object containing the fields below.
2. **Count delta.** A signed adjustment to the recorded element count.

The source-facing model uses 32-bit integer quantities. Object addresses are also carried through an integer-valued input. Address validity and the exact language-level consequences of signed overflow are external preconditions or uncertainties, not checked conditions.

|---|---:|---|---|

The function returns an integer status:

- **Zero:** the function reached its commit point and directly stored the prospective count and derived used-byte quantity.

A failed first growth request is not itself returned. It triggers an exact-requirement retry.

Zero does not independently prove that backing memory exists, has a particular size, or contains preserved data. Those properties depend on F-7eca6144d13b.

## Behavior

### Arithmetic model

For the descriptions below:

- **Prospective count** means the original count plus the supplied delta, calculated as a signed integer expression.
- **Required bytes** means the prospective count multiplied by the element width, with the result stored as an unsigned 32-bit quantity.
- **Original capacity** means the capacity captured before any dependency call.
- **Delta bytes** means the delta multiplied by a fresh read of the element-width field, with the result stored as an unsigned 32-bit quantity.

The capacity comparison and growth-size comparisons are unsigned. Consequently, a negative signed product that is representable before conversion becomes a large unsigned quantity; it is not rejected as negative.

Unsigned additions and subtractions operate modulo \(2^{32}\). In particular, neither the larger growth request nor the negative-delta request is protected against wraparound.

The signed count addition and signed multiplications introduce a separate limitation: the supplied material does not establish a portable result when those signed expressions overflow. A machine-level wrapping interpretation must not be silently substituted for a language-level guarantee.

### Initial observations

The direct reads and computations occur in this order:

1. Read the count at offset +8 and calculate the prospective count.
2. Read the unsigned capacity at offset +16.
3. Read the element width at offset +4 and calculate required bytes.
4. Compare original capacity with required bytes using an unsigned comparison.

The previous used-byte field is not read during this initial sequence.

### Growth path: required bytes exceed original capacity

If original capacity is strictly less than required bytes, the function prepares an enlarged request.

It rereads the element-width field and calculates delta bytes. The enlarged-request increment is selected by:

1. Taking the greater of delta bytes and original capacity.
2. Limiting that value to 65,536.
3. Raising the result back to delta bytes if delta bytes exceeds it.

Equivalently, the increment is:

\[
\max\!\left(\text{delta bytes},
\min\!\left(\max(\text{delta bytes},\text{original capacity}),65{,}536\right)\right).
\]

All quantities in these comparisons are unsigned 32-bit values.

The 65,536 value limits only the capacity-derived contribution to the increment. It is not a limit on the final requested size, and it does not limit an increment when delta bytes itself exceeds 65,536.

The function then calls F-7eca6144d13b with:

1. The original object address.
2. Zero.
3. Original capacity plus the selected increment, using unsigned 32-bit addition.

Two outcomes are distinguished:

- **First call returns zero:** commit the previously calculated prospective count and required bytes. There is no second call.
- **First call returns nonzero:** call F-7eca6144d13b again, with the same object address and zero second argument, but with required bytes as the third argument.

For the second call:

- Zero leads to the commit point.
- Nonzero is returned unchanged, without the function’s direct commit writes.

The retry uses the previously calculated required-byte quantity. The function does not reread the count, width, or capacity after the first call. Any state changes made by that failed call remain relevant to the dependency’s second invocation, but do not change the saved retry size or the values later committed.

The two requested sizes are not required to differ. There is no duplicate-request suppression.

### Non-growth path with a nonnegative delta

If required bytes are less than or equal to original capacity and the delta is nonnegative, the function makes no dependency call.

It proceeds directly to the commit point.

This includes a zero delta. Zero delta is not a general no-op: the count is written back, and the used-byte field is recomputed and written from count times element width.

### Non-growth path with a negative delta

If required bytes are less than or equal to original capacity and the delta is negative, the function reads the old used-byte field at offset +12.

It calculates the requested size as:

\[
\text{required bytes}
+
(\text{original capacity}-\text{old used bytes})
\pmod {2^{32}}.
\]

It then calls F-7eca6144d13b once, with the object address, zero, and that requested size.

- Zero leads to the commit point.
- Nonzero is returned unchanged, without the function’s direct commit writes.

For a coherent object with capacity at least as large as old used bytes, this expression preserves the old absolute amount of unused capacity. That is an interpretation of the arithmetic, not a separately enforced invariant.

If old used bytes exceed original capacity, the subtraction wraps. No inconsistency check or correction is present.

A negative delta does not necessarily select this path. The growth comparison happens first. If conversion produces required bytes larger than original capacity, the growth path is taken instead.

### Commit point

Every successful path performs these direct writes, in order:

1. Store the prospective count at offset +8.
2. Store required bytes at offset +12.

The function then returns zero.

There is no direct write to capacity or element width. If a dependency call changes those fields, this function does not restore them.

The committed count and used-byte values were calculated before any dependency call. Dependency modifications to those same fields can therefore be overwritten by the commit writes.

## Side effects

### Direct effects

On a successful path, the function writes exactly the two identified fields, in count-then-used-bytes order.

On a nonzero return, it performs neither of those direct commit writes. This is not a transactional rollback guarantee: one or two dependency calls may already have changed the object or external state.

The supplied body shows no direct allocation, release, copying, initialization of backing bytes, logging, or explicit global access.

### Dependency-mediated effects and ownership

F-7eca6144d13b receives the original object address and a requested size. Its memory and ownership contract is not supplied.

### Invalid inputs and concurrency

No synchronization is shown. The two reads of element width on the growth path are distinct observations. Safe concurrent mutation and consistency between those reads are not established.
