# F-1b8a25012be3

## Purpose

F-1b8a25012be3 selects a bounded portion of a pending transfer description, updates its accounting, and, when the selected amount is at most 64, programs associated context and device-facing state.

The established behavior consists of field accesses, dependency calls, arithmetic, register accesses, and returned bit patterns. Describing the units as bytes, the arithmetic dependency as division, or the final control write as starting a hardware transaction would require additional evidence.

Two ordering properties are material:

- Transfer accounting occurs before the size check. Rejection does not restore the accounting fields.
- Unresolved address-bearing globals are read at their respective use sites. The device-position offset is read after the command write. The device-state base is read for the byte access and read again for the special-path state write.

## Interface

The function takes one address identifying a mutable request object. The supplied representation uses 32-bit addresses and the following request fields:

| Offset | Access width | Behavioral role |
|---|---:|---|
| `0x34` | 32 bits | Associated context address or opaque context value |
| `0x98` | 32 bits | Unsigned pending count |
| `0x9C` | 32 bits | Unsigned current position |
| `0xA0` | 32 bits | Unsigned portion limit |

On accepted paths with an initially nonzero pending count, the captured context address is used for these writes:

| Context offset | Access width | Stored value |
|---|---:|---|
| `0x80` | 32 bits | Result from F-8f180221fee0 |
| `0x38` | 32 bits | Value derived from the secondary result of F-d7be9cfb4000; possibly overwritten with `0x40` |

Additional storage supplies:

- An unresolved offset used with address `0x38400000` to locate the device-position register.
- An unresolved base address used to access a device-state byte at offset `4` and, conditionally, a 32-bit field at offset `0x18`.

These are separately evaluated global accesses, not immutable configuration parameters. Their storage addresses, declarations, exact load widths, and external mutation rules are not supplied.

No null, alignment, accessibility, range, or ownership validation is visible. Callers must provide storage suitable for each reached access. Captured addresses must remain usable when subsequently dereferenced; the function does not establish that dependencies preserve their validity.

The result consists of two observable 32-bit words:

| Outcome | Low word | High word |
|---|---:|---:|
| Initial pending count is zero | Context value reread after F-ddf4a1f94e38 | `0x80` |
| Selected amount exceeds 64 | `0xFFFFFFFF` | `0x80` |
| Selected amount is at most 64 | `0` | Branch-dependent value |

This specifies result composition, not memory byte order or a portable return convention. The high word is not consistently a status code: it can contain an extracted status, a control-derived word, or `0x38400900`.

## Behavior

### Initially empty request

The first request access is a 32-bit read at offset `0x98`.

If the count is zero, the function reads the value at request offset `0x34` and calls F-ddf4a1f94e38 with that value and `0x80`. After the call returns, it reads request offset `0x34` again. The reread value becomes the low result word; the high word is `0x80`.

The reread is significant. A dependency mutation of the request’s context field can change the returned value without changing the argument already passed.

This path has no explicit accounting writes, reads of request offsets `0x9C` or `0xA0`, context dereferences, or device-register accesses. Effects performed inside the dependency are unknown.

### Portion selection and accounting

For an initially nonzero count, the function reads the original position at request offset `0x9C`, then the limit at offset `0xA0`.

The unsigned comparison determines both the selected amount and the writes:

| Condition | Selected amount | First accounting write | Second accounting write |
|---|---:|---|---|
| Count less than limit | Original count | Zero to `0x98` | Zero to `0x9C` |
| Count at least limit | Limit | Count minus limit to `0x98` | Original position plus limit to `0x9C` |

The position addition is 32-bit unsigned arithmetic, wrapping modulo \(2^{32}\). The subtraction cannot underflow in its selected branch.

Equality takes the second branch. An exact final portion therefore leaves count zero and an advanced position; a shorter final portion clears both fields.

The original position is retained for later device programming. It is not replaced by the updated request position.

A zero limit is accepted by this selection logic. With an initially nonzero count, both accounting writes occur but preserve their previous numeric values, and the selected amount is zero.

### Size check

After both accounting writes, the function:

1. Reads the 32-bit control word at `0x38400900`, retaining that snapshot.
2. Reads the context address from request offset `0x34`.
3. Tests whether the selected amount is below 65.

An amount greater than 64 returns low word `0xFFFFFFFF` and high word `0x80`. The accounting writes remain in effect.

The rejecting path explicitly reads the control register and context field, but does not dereference the context or enter accepted configuration. It does not read either unresolved address-bearing global or call the accepted-configuration dependencies.

### Accepted configuration

Amounts from zero through 64 inclusive enter configuration.

First, F-8f180221fee0 is called without explicit arguments. Its 32-bit result is written to offset `0x80` of the previously captured context address. A change to the request’s context field during that call does not redirect this write.

The command contribution is then determined:

- For amount zero, the contribution is one, without a command-sizing call.
- Otherwise, F-d7be9cfb4000 is called with amount minus one and `0x40`; its primary result is incremented by one.

A 32-bit command word is written to `0x38400910`. It combines by bitwise OR the selected amount, the contribution shifted left by 19, and `0x20000000`. No field-width mask is applied to the contribution before combination.

The dependency’s primary-result range is not established. The representation uses a signed-looking 32-bit intermediate for its increment and shift; overflow and out-of-range shift behavior cannot be promoted into a portable arithmetic guarantee. For ordinary representable results, the described composition is established.

**Only after the command-word write**, the function reads the unresolved device-position offset global. It uses the value obtained at that point to locate the register relative to `0x38400000`, then writes the retained original position masked with `0x7FFFFFFF` as a 32-bit value.

The offset is not captured before F-8f180221fee0 or the optional command-sizing call. Changes those dependencies make to the global can therefore affect the destination. The offset’s numeric value, extension rules, and behavior for invalid effective addresses remain unresolved.

Next, F-d7be9cfb4000 is called with the selected amount and `0x40`, including when the amount is zero. Its exposed secondary result is consumed as a 32-bit word. Three is added modulo \(2^{32}\), then the lowest two bits are cleared.

That derived word is written to captured-context offset `0x38`. If it is zero and the selected amount is nonzero, the same field is immediately overwritten with `0x40`. Amount zero does not trigger this replacement.

### Device-state selection and base evaluation

After the context-size writes, the function reads the unresolved device-state base global and accesses one byte at offset `4` from the resulting base.

This base read occurs after all configuration dependency calls described above. It is not an entry-time snapshot.

The special path requires both:

- The byte read is zero.
- The earlier control snapshot masked with `0x03CC0000` equals `0x000C0000`.

If the byte is nonzero, the masked comparison does not select the special path.

On the special path, the function reads the device-state base global **again**, then writes the 32-bit value `0x80` at offset `0x18` from this newly obtained base. The source does not retain the base used for the byte read.

Consequently, the byte read and state write need not target the same object if the global changes between evaluations. No intervening explicit dependency call is needed to establish the distinction; preservation against external agents or aliased storage is not guaranteed.

The special path then writes `0x39` to `0x38400810`, ORs the earlier control snapshot with `0x04000000`, and writes that control word to `0x38400900`. The result is low word zero and high word `0x38400900`.

The access width at `0x38400810` is not established by the supplied declaration.

### General control path

All other cases take the general path. This path does not perform the special-path reread of the device-state base.

If bits 18–19 of the earlier control snapshot are both set, F-9c06a5856a0f is called with bits 22–25 of that snapshot, extracted as an unsigned value from zero through 15, and a second argument of zero.

The remaining accesses have this order:

1. Read the 32-bit status word at `0x38400B10`. Mask with `0x7FFFFFFF`, then shift right by 29, obtaining a value from zero through three.
2. Read the control word at `0x38400900`.
3. If the first extracted status is not three, write that just-read control word back unchanged. Return the extracted status as the high word.
4. Otherwise, read and extract status again.
5. Read control again and provisionally OR it with `0x84000000`.
6. If the second extracted status is three, write the provisional word and return high word three.
7. If the second extracted status is not three, read control once more, OR this last read with `0x8C000000`, and write the result. That control-derived result is also the high return word.

Every general-path outcome has low word zero. Repeated status and control reads are distinct observations; they cannot be replaced with one stable snapshot.

## Side effects

Explicit writes can affect request accounting, captured-context fields, the command and position registers, the final control register, and special-path state.

There is no rollback. Accounting precedes rejection; accepted configuration precedes final control selection. Even the general branch that preserves a control value performs a control-register write.

The unresolved globals are explicitly read, not explicitly assigned. Their read timing is part of the behavior:

| Global role | Evaluation point |
|---|---|
| Device-position offset | After command write, immediately before the position-register write |
| Device-state base for inspection | After derived context-field writes, before the byte read |
| Device-state base for special update | On the special path, before the offset-`0x18` write |

The function does not explicitly allocate, release, copy, or transfer ownership of storage. This does not establish any dependency’s ownership contract.

Captured request values and the earlier control snapshot are reused across calls. In contrast, the unresolved globals are loaded at the points above. Neither category implies that dependencies preserve globals or pointed-to memory.

No synchronization, explicit memory barrier, polling loop, or local dependency-failure recovery is visible. Hardware ordering, volatility, atomicity, and consequences of aliasing remain unresolved.

## Acceptance examples

These are conditional static predictions, not runtime observations.

1. **Empty request with mutation.** With count zero and context value `0x1000`, F-ddf4a1f94e38 receives `0x1000` and `0x80`. If it changes the context field to `0x2000`, the result is low `0x2000`, high `0x80`.

2. **Short final portion.** Count 12, position `0x1000`, and limit 64 select 12 and clear both accounting fields. The later position-register value is `0x1000`, assuming that write is reached.

3. **Exact final portion.** Count 64, position `0x1000`, and limit 64 produce count zero and position `0x1040`. The selected amount passes the size check.

4. **Rejection after accounting.** Count 100, position `0x1000`, and limit 80 produce count 20 and position `0x1050`, then return low `0xFFFFFFFF`, high `0x80`. Neither unresolved global is explicitly read.

5. **Zero limit.** Count 9 and limit zero preserve accounting values through explicit writes. The command contribution is one. The later arithmetic call with zero and `0x40` still occurs.

6. **Position wrap.** Count 32, position `0xFFFFFFF0`, and limit 32 produce stored position `0x00000010`. The device-position value is `0x7FFFFFF0`, derived from the original position.

7. **Changed position offset.** If a configuration dependency changes the offset global from one valid offset to another, and the latter remains present when the post-command load occurs, the position write uses the latter offset. No earlier offset snapshot controls that write.

8. **Distinct device-state bases.** Suppose the byte-access base evaluates to one object whose offset-`4` byte is zero, and the control mask selects the special path. If the special-path base reread yields another valid object, `0x80` is written at offset `0x18` of the second object. Equality of the two bases is not required by the visible behavior.

9. **Conditional arithmetic interpretation.** If F-d7be9cfb4000 provides quotient and remainder, amount 64 gives command contribution one. Its second call gives remainder zero, causing writes of zero and then `0x40` at context offset `0x38`.

10. **Changing status.** First extracted status three followed by two causes an additional control read. The last read ORed with `0x8C000000` supplies both the final control write and high return word.

11. **Special return.** A zero device-state byte and matching earlier control mask select the special path. Subject to successful accesses, the high word is `0x38400900`; no status-register read occurs.
