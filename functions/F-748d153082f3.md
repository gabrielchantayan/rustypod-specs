# F-748d153082f3

## Purpose

F-748d153082f3 processes a stored movement request against a range and viewport-like state. It computes a candidate position, conditionally adjusts an offset, coordinates an optional attached object, performs conditional refresh work, and reports whether the candidate differs from an earlier position obtained through a dependency.

The Boolean result is a **position comparison**, not a success status. An offset change can occur while the function returns false. A true result does not establish that a dependency successfully committed the requested position.

“Movement,” “viewport,” “coordinate,” and “refresh” describe inferred intent. The field accesses, arithmetic, branch conditions, call arguments, and ordering below are established by the supplied static representation.

## Interface

The function takes one pointer to a mutable object and returns a Boolean.

The returned value is true exactly when the earlier-position result saved from the first F-30ee4f4bfdfc call differs from the computed candidate. The external ABI representation of that Boolean is not established.

## Behavior

### 1. Capture the request and earlier position

The first object read saves the signed 32-bit movement request.

F-30ee4f4bfdfc is then called with the object, the saved request, and the additional arguments 0, 2, and 2. Its integer result is saved as the earlier position.

Only after that call returns does the function read and save the viewport offset. Consequently, the saved offset may already reflect mutations by the first dependency.

If the saved offset is negative, the function writes zero to the offset field. It does not replace the saved negative value: that value remains available for later differences, refresh decisions, and notification comparison.

F-30ee4f4bfdfc is called a second time. The supplied representation displays only the object argument for this invocation. Its actual signature and the significance of the differing displayed argument lists remain unresolved.

### 2. Compute the candidate

The second dependency result is added to the saved movement request to obtain the requested position.

The function then reads the current range limit and range base and subtracts the base from the limit. These reads occur after the second dependency returns.

The candidate is selected using signed comparisons:

- If the requested position is no greater than the computed range length, the candidate is the requested position, except that a negative requested position becomes zero.
- If the requested position is greater than the range length, the candidate is the range length, with no additional nonnegative clamp.

For a nonnegative range length, this is a clamp into the inclusive interval from zero to the range length.

For a negative range length, it is not an ordinary interval clamp. A requested position greater than that negative length produces a negative candidate. A requested position at or below that length produces zero. Reversed bounds are not explicitly rejected.

The saved request, earlier position, saved offset, and candidate are not recomputed from object fields after later dependencies.

### 3. Select an offset-adjustment path

The function compares the candidate with the threshold formed from the current offset plus the product of the current unit size and visible-unit count.

When the candidate is at or beyond that threshold, main dispatch +204 is called with selector 2. A nonzero result selects the later-offset path.

When the candidate is below the threshold, selector 2 is not called. A zero result from selector 2 also prevents entry into the later-offset path.

If the later-offset path is not selected, the function compares the candidate with the current viewport offset. If the candidate is below that offset, main dispatch +204 is called with selector 1. A nonzero result selects the earlier-offset path.

Otherwise, the function takes the non-scrolling path.

The selector calls are not established as pure predicates. For example, a selector-2 call that returns zero may change the offset subsequently used by the selector-1 comparison.

### 4. Earlier-offset path

The function reads the current offset, adds the saved movement request, and writes the result to the offset field. If that computed result is negative, it writes zero to the field.

It then reads and saves the attached-object pointer.

If the pointer is null, all coordinate-conversion, accumulator, attached-dispatch, and embedded-region operations are skipped.

If the pointer is nonnull:

1. F-870c4fcf7295 receives the saved offset minus the current offset, followed by the current unit size.
2. After that dependency returns, its result is multiplied by the coordinate scale then read from the object.
3. The scaled value is added to the current coordinate accumulator and the sum is written back.
4. Attached dispatch +324 is called on the saved attached-object receiver with arguments 0, the scaled value, 1, and 0.
5. F-d156b0b83eb3 is called with the embedded-region address, zero, and the negation of the scaled value.

The attached-object receiver is selected before conversion. A conversion dependency that changes the object’s attached-object field does not replace this saved receiver.

The function then performs the post-scroll refresh decision.

### 5. Later-offset path

The function reads the current offset, adds the saved movement request, and writes the sum to the offset field.

It next saves the current unit size and then the current visible-unit count. It reads the range fields again for the following end condition:

The current range length is less than the saved visible-unit count multiplied by the saved unit size, plus the pre-increment offset, plus the saved movement request.

If that strict inequality holds, F-870c4fcf7295 is called with the candidate and saved unit size. The offset is replaced by the sum of:

- One minus the saved visible-unit count, multiplied by the saved unit size.
- The saved unit size multiplied by the conversion result.

The saved unit size and visible-unit count remain controlling for this replacement even if the conversion dependency changes their object fields.

After this optional replacement, the current offset is checked. A negative value is replaced with zero.

The function then reads and saves the attached-object pointer. A null pointer skips the attached-object work. Otherwise:

1. F-870c4fcf7295 receives the current offset minus the saved offset, followed by the current unit size.
2. Its result is multiplied by the coordinate scale read after the conversion returns.
3. The scaled value is subtracted from the current coordinate accumulator and the difference is written back.
4. Attached dispatch +324 receives 0, the negated scaled value, 1, and 0.
5. F-d156b0b83eb3 receives the embedded-region address, zero, and the scaled value.

The accumulator, attached-dispatch, and embedded-adjustment signs are opposite to those on the earlier-offset path.

### 6. Refresh and position-specific work

After either offset-adjustment path, F-3fac671648b8 is called once. A nonzero result causes F-0d27caf8e50d followed by F-92bea7c30bd6. A zero result skips that pair.

On the non-scrolling path:

1. F-3fac671648b8 is called.
2. If it returns nonzero and the earlier position differs from the candidate, F-3ba0d8b4ad23 is called with the object and earlier position, then with the object and candidate.
3. F-3fac671648b8 is called again, regardless of its first result.
4. The refresh pair runs only if this second result is nonzero and the saved offset is negative.

The two non-scrolling calls are distinct observations. Neither result stability nor absence of side effects is established.

The result of F-92bea7c30bd6 does not determine the function’s Boolean return.

### 7. Notify an offset change

After branch-specific work and any refresh pair, the function reads and saves the current offset for the final change check.

If this value differs from the saved offset, the notification target is read. Only a nonzero target causes F-ca0f66276073 to be called.

Its arguments, in positional order, are:

1. The notification target.
2. The value read from the first notification global.
3. The value read from the second notification global.
4. The offset captured for this final change check.
5. Zero.

The second and third arguments are **global reads, not established constants**. These reads occur when the notification call is reached: after branch-specific work, refresh work, the final offset comparison, and the nonzero notification-target check.

Their values may therefore reflect mutations by any preceding dependency. The supplied representation does not establish an evaluation order between the two global reads. Their argument positions remain distinct regardless of read order.

If the offset is unchanged, the target and notification globals are not needed by this path. If the offset changed but the target is zero, the notification globals are not read for a notification call.

### 8. Dispatch the final position and return

If the earlier position differs from the candidate, main dispatch +280 is invoked with:

- The current range base plus the candidate.
- Flag 1.

This range-base read occurs after any notification call. A notification dependency may therefore affect the absolute position supplied to this final operation.

The function returns the saved earlier-position-versus-candidate comparison. It does not re-query the position or derive success from the final operation’s result.

## Side effects

- Viewport-offset normalization and adjustment.
- Coordinate-accumulator adjustment on nonnull attached-object paths.

Dependencies may additionally change object fields, attached objects, the embedded region, notification globals, other globals, or external state. No preservation guarantee is established.

The principal ordering constraints are:

- The first position call precedes saving the offset.
- Initial offset normalization precedes the second position call.
- Branch authorization precedes the corresponding offset adjustment.
- Accumulator adjustment precedes attached-object dispatch.
- Attached-object dispatch precedes embedded-region adjustment.
- Branch-specific and refresh work precede the final offset comparison.
- The nonzero notification-target check precedes the notification-global reads.
- Notification precedes final-position dispatch.

No explicit rollback, retry, or status-based recovery is shown. Adjustment, notification, refresh, and final-position results are not checked for successful completion. Invalid accesses, non-returning dependencies, and exceptional dependency behavior are outside the established normal-return behavior.

## Acceptance examples

These are conditional static predictions, not executed tests. Unless stated otherwise, assume valid memory, representable signed arithmetic, and no dependency mutations beyond those specified.

1. **Position changes without scrolling.**  
   Range length 100, requested position 12, earlier position 10, offset 0, unit size 10, and visible-unit count 3 produce candidate 12 and threshold 30. Neither selector is called. If the first non-scrolling F-3fac671648b8 result is nonzero, F-3ba0d8b4ad23 receives 10 and then 12. Because the saved offset is nonnegative, the non-scrolling refresh pair is skipped regardless of the second result. Final-position dispatch receives the current base plus 12 and flag 1. The return is true.

2. **Earlier-offset adjustment with an attachment.**  
   Saved offset 20, request −10, candidate 15, and threshold 50 reach selector 1. If it returns nonzero without changing the fields, the offset becomes 10. If conversion of difference 10 with unit size 10 returns 1 and the scale is 4, the accumulator increases by 4, attached dispatch receives displacement 4, and embedded adjustment receives −4.

3. **Later-offset adjustment at threshold equality.**  
   Range length 100, saved offset 20, request 10, unit size 10, visible count 3, and candidate 50 reach selector 2 because equality qualifies. With nonzero authorization, the offset becomes 30. End correction is skipped because 100 is not less than 60. Conversion result 1 and scale 4 produce accumulator decrement 4, attached displacement −4, and embedded displacement 4.

4. **End correction.**  
   Range length 55, offset 20, request 10, unit size 10, visible count 3, and candidate 50 select the later-offset path if authorized. The end condition holds because 55 is less than 60. If conversion of candidate 50 with unit size 10 returns 5, the replacement offset is −20 plus 50, or 30.

5. **Negative saved offset and false return.**  
   A saved offset of −3 is initially normalized to zero. If it remains zero and the earlier position equals the candidate, the function returns false and omits final-position dispatch. A nonzero notification target still causes notification with offset zero because zero differs from −3.

6. **Reversed bounds.**  
   Range length −5 and requested position 0 produce candidate −5. With the same range length, requested position −6 produces candidate zero. Always forcing the candidate nonnegative would change the first case.

7. **Notification observes changed globals.**  
   Suppose the offset changes, the target remains nonzero, and preceding refresh work changes the first and second notification globals to 71 and 93. If those values remain in place until their reads, F-ca0f66276073 receives 71 as its second argument and 93 as its third. Entry-time values are not used merely because they existed earlier. No ordering between these two reads is required.

8. **Notification suppression.**  
   With an unchanged final offset, no notification occurs. With a changed offset but zero target, no notification occurs either. Neither case requires reading the two notification globals for this call.
