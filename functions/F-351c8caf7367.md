# F-351c8caf7367

## Purpose

F-351c8caf7367 traverses a dependency-defined sequence associated with one of two object fields, retains a candidate according to an unsigned 32-bit comparison, and passes the retained address to an indirect method on the selected object. It subsequently calls a cleanup dependency.

The selector determines which field is used:

- A selector equal to zero selects the field at byte offset `0xAC`.
- Any nonzero selector selects the field at byte offset `0xA8`.

For stable, non-null candidates whose comparison fields do not change, the selection is the first candidate having the lowest unsigned 32-bit value at byte offset `0x0C`. This minimum-selection interpretation is conditional: the implementation retains an address, not a snapshot of its comparison value, and dependencies may mutate relevant memory.

No runtime behavior has been tested. This contract distinguishes operations established by the supplied static representation from dependency behavior and inferred intent.

## Interface

### Inputs

The function receives four machine-word arguments:

| Argument | Established use |
|---|---|
| Base address | Address used to locate either of two 32-bit object-reference fields. |
| Selector | A 32-bit integer tested for equality to zero. Also copied into a local output slot before initialization. |
| First state word | An uninterpreted 32-bit value copied into the first word of local traversal state. |
| Second state word | An uninterpreted 32-bit value copied into the immediately following word of local traversal state. |

The supplied representation uses 32-bit integers, four-byte uninterpreted values, and four-byte object and function references. This contract describes that apparent 32-bit model. It does not establish portability to another pointer width or calling convention.

The selector is not normalized before it is copied into the local output slot. Negative values and positive nonzero values select the same object field, but leave different initial bit patterns in that slot.

### Relevant layouts

The following byte offsets are observable:

| Region | Offset | Use |
|---|---:|---|
| Base object | `0xA8` | Object reference used for a nonzero selector. |
| Base object | `0xAC` | Object reference used for a zero selector. |
| Candidate object | `0x0C` | Unsigned 32-bit comparison field. |
| Selected callback object | `0x00` | Reference to a method table. |
| Method table | `0xCC` | Indirect callable reference. |

These offsets are byte displacements. The method-table displacement is `0xCC` bytes, not an element index.

Local storage includes an output slot followed by two adjacent state words:

- The output slot initially contains the selector.
- The first state word initially contains the third argument.
- The second state word initially contains the fourth argument.
- The initialization, traversal, and cleanup dependencies receive the address of the first state word.
- The traversal dependency also receives the address of the output slot.

The visible local arrangement does not establish the complete storage extent expected by any dependency. In particular, the two explicit state words do not prove that dependencies access only eight bytes.

### Output

There is no explicit return value. The chosen candidate is communicated through the indirect method call, not through the function’s return.

An all-zero retained address is passed to that method if no successful traversal result changes the initial retained address. This includes an ordinary empty traversal, subject to the dependencies’ actual behavior.

### Preconditions

Normal completion requires the memory and calls actually reached on the selected path to be valid:

- The chosen base-object field must be readable.
- Dependencies must accept the supplied local-storage addresses and initialization value.
- Any candidate comparison field that is reached must be readable as a 32-bit unsigned value.
- At dispatch time, the selected object, its method-table reference, and the method entry at `0xCC` must support the described reads and call.

There are no explicit checks enforcing these conditions. Invalid addresses are not converted into a documented error result.

## Behavior

### 1. Select and read the initialization reference

The function tests the original selector for equality to zero and reads one 32-bit value from the base object:

- Zero: read at `0xAC`.
- Nonzero: read at `0xA8`.

Only the selected field is explicitly read at this point. The other field is not consulted by the visible logic.

This read precedes initialization of the local traversal words in the supplied representation.

### 2. Prepare local storage and initialize traversal

The function copies the selector into the local output slot and copies the two remaining input words into adjacent traversal-state words.

It then calls F-8ca21d3a8cca with:

1. The address of the first traversal-state word.
2. The value just read from the selected base-object field.

No result from this call is tested. Its implementation and any modifications it makes to accessible storage are not supplied.

After that call returns normally, the function initializes its retained candidate address to zero.

### 3. Request traversal results

The function calls F-b38a3aba0e18 with:

1. The address of the first traversal-state word.
2. The address of the local output slot.

A zero return ends traversal immediately. On that terminating call, the caller does not process the output slot as a candidate, even if the dependency wrote to it.

Any nonzero return causes the current contents of the output slot to be treated as a candidate address. The result is a zero-versus-nonzero control signal; it is not used as a count, candidate address, or ordering value.

The output slot is not explicitly reset between calls. It initially contains the selector, subject to any intervening dependency writes. A successful call that leaves the slot unchanged therefore causes its existing bits to be consumed as an address. The caller does not independently establish that every successful call produced a fresh candidate.

### 4. Update the retained address

For each nonzero traversal result:

- If the retained address is zero, the function assigns the candidate address to it without reading a comparison field.
- Otherwise, it reads the candidate’s unsigned 32-bit field at `0x0C` and the retained candidate’s unsigned 32-bit field at `0x0C`.
- It replaces the retained address only when the new candidate’s value is strictly smaller.

The comparison is unsigned. Values whose high bit is set are therefore greater than every value from `0x00000000` through `0x7FFFFFFF`.

Equal values do not cause replacement. With stable candidate contents and nonzero candidate addresses, the earlier candidate wins a tie.

The retained value is an address, not a cached score. Its comparison field is read again when later candidates are compared. Consequently:

- Mutating the retained candidate’s field can change later outcomes.
- Repeated occurrences of the same address are not deduplicated.
- No globally minimal historical score is preserved if comparison fields change.
- The first retained candidate’s comparison field need not be read at all if traversal terminates immediately afterward.

The comparison requires two field values, but the supplied expression does not establish a portable ordering between those two memory reads. A contract requiring candidate-first or retained-first observation would exceed the evidence.

### 5. Handle zero candidate addresses according to the same rules

The traversal result and candidate address have independent meanings.

If a successful traversal call supplies address zero while the retained address is zero, the retained address remains zero and no candidate comparison field is read.

If a later successful call supplies a nonzero address while the retained address is still zero, that address is retained without comparison.

If a successful call supplies address zero after a nonzero address has been retained, the function attempts the comparison involving the field at address zero plus `0x0C`. There is no special rejection or skip rule. Whether that access faults or otherwise has meaning depends on the execution environment.

Thus, zero is both the initial “nothing retained” value and a possible raw candidate value. The function does not distinguish those cases.

### 6. Reread the dispatch object and call its method

After traversal terminates, the function tests the original selector again and rereads the same selected base-object field.

The dispatch receiver is this newly read reference. It is not necessarily the reference supplied to F-8ca21d3a8cca. Changes to the selected base-object field during traversal can therefore cause initialization and final dispatch to use different objects.

Using the newly read receiver, the function:

1. Reads its method-table reference at byte offset zero.
2. Reads a callable reference at method-table byte offset `0xCC`.
3. Calls that target with the receiver as the first argument and the retained candidate address as the second.

The call occurs even when the retained address is zero. No null-receiver, null-table, null-method, or null-candidate guard is present.

### 7. Perform cleanup

After the indirect method returns normally, the function calls F-d0d3f100effc with the address of the first traversal-state word.

The visible order is dispatch before cleanup. The callback therefore executes before this cleanup call has occurred.

There is no visible exception handler or alternate cleanup path. Cleanup is not established for a dependency that faults, throws, transfers control nonlocally, or never returns.

## Side effects

Established effects of the wrapper are:

- Reading the selected base-object field before initialization and again after traversal.
- Writing the local output and traversal-state words.
- Passing addresses of that local storage to dependencies.
- Reading candidate comparison fields when required by the selection rule.
- Reading a method-table reference and a method entry.
- Calling initialization, repeated traversal, indirect dispatch, and cleanup in the order described.

The wrapper contains no explicit heap allocation, deallocation, reference-count update, or candidate-object write. This does not establish that its dependencies perform none.

Ownership is undocumented. Passing a candidate address to the method does not prove transfer of ownership, borrowing, retention, or destruction. Likewise, the final dependency’s apparent cleanup role does not prove which resources it releases.

The local-storage addresses are valid during this invocation. Their use after return is not established. No assumption is made that dependencies preserve global state, preserve objects reachable through their arguments, or refrain from retaining supplied addresses.

No synchronization is visible. Stable-memory selection semantics require relevant contents not to change unexpectedly during their observation; thread safety is not established.

## Acceptance examples

These examples are conditional on valid memory, normally returning dependencies, and the explicitly stated candidate behavior.

### Empty traversal

If the first call to F-b38a3aba0e18 returns zero, no candidate comparison field is read. The indirect method receives the reread receiver and candidate address zero. Cleanup follows normal method return.

### One nonzero candidate

If traversal supplies one nonzero candidate address and then terminates, that address is passed to the method. The wrapper does not need to read the candidate’s `0x0C` field.

### Stable minimum

If three distinct nonzero candidates have stable unsigned fields of `12`, `4`, and `9`, in that traversal order, the second candidate is passed to the method.

### Equal-value tie

If two distinct nonzero candidates both have a stable field value of `7`, the first remains retained. Equality does not replace it.

### Unsigned boundary

If the first candidate’s field is `0xFFFFFFFF` and the second candidate’s field is `0x00000001`, the second replaces the first. Interpreting the first value as signed negative one would produce the wrong contract.

### Changed retained field

Suppose the first candidate is initially retained, its field later becomes `20`, and the next candidate’s field is `10` when compared. The next candidate replaces it, regardless of what the first candidate’s field contained earlier.

### Changed receiver reference

If the chosen base-object field initially references one object but references another by traversal completion, initialization receives the first reference and final method dispatch uses the second.

### Nonzero selectors

Selectors `1` and `-1` both select offset `0xA8`. They initialize the output slot differently. Equivalent overall behavior requires dependency behavior that makes that initial difference irrelevant.

### Zero candidate after retention

If a successful result supplies address zero after a nonzero candidate was retained, the wrapper attempts a field comparison involving address `0x0C`; it does not silently skip that result.

## Uncertainties

The following are **documented_only**:

- Semantic meanings of the two input state words and complete traversal-state layout.
- Candidate type, comparison-field meaning, and intended collection semantics.
- Dependency failure reporting and whether traversal always terminates.
- Whether successful traversal always writes the output slot.
- Candidate lifetimes and ownership before, during, or after dispatch.
- The indirect method’s operation and any ownership transfer.
- Resource acquisition and release by the dependencies.
- Behavior under invalid addresses, concurrent mutation, or nonlocal control transfer.
- Exact calling convention, alignment requirements, and machine-level fault behavior.

No integer accumulation or score arithmetic is visible. Selection uses a strict unsigned 32-bit comparison. Pointer-offset validity and address-space boundary behavior remain execution-environment preconditions, not validated cases.
