# F-117e11c4474b

## Purpose

F-117e11c4474b creates a node through a dependency, attaches it to a caller-specified position in a linked structure, increments a context counter, performs color-based rebalancing, and publishes the created node through an output slot.

The structure and repair rules are consistent with insertion into a red-black binary-search tree. That interpretation is **inferred intent**. The established behavior consists of specific pointer-field updates, byte-valued color updates, comparisons, and dependency calls. Successful preservation of tree invariants depends on input structure validity and dependency behavior that are not supplied.

This function does not independently search for an insertion position, reject duplicate values, or validate its arguments.

For intended tree behavior, the caller must supply a coherent header, parent links, child links, and insertion position. In particular:

## Behavior

### 1. Request creation of the node

The first dependency invoked is F-1521158aae28. Its six exposed arguments, in order, are:

1. Context.
2. Payload argument.
3. Placement hint.
4. Attachment parent.
5. Placement hint again.
6. Attachment parent again.

Its result is retained as the created node address and remains the value eventually written to the output slot.

This function does not establish how that dependency allocates or initializes the node. It does not explicitly initialize the created node’s color, children, or payload.

### 2. Increment the context counter

After node creation returns, the function reads the 4-byte field at context `+0x14`, adds one, and writes the field back.

The increment occurs before attachment selection and before any comparison call. There is no overflow check, saturation, or rollback path.

The source representation establishes a 32-bit field and addition by one. It does not establish a portable overflow contract for the signed arithmetic shown. Boundary behavior at the maximum signed value is therefore **documented_only**.

### 3. Choose the attachment direction

The left-attachment path is selected without comparison if either:

- The attachment parent equals the header address currently read from context `+0x10`; or
- The placement hint is nonzero.

Otherwise, the function invokes F-a1e786bd6046 with:

1. The address context `+0x19`.
2. The payload argument.
3. The address attachment parent `+0x10`.

A nonzero result selects left attachment. A zero result selects right attachment. No ordering beyond zero versus nonzero is used.

The comparison dependency’s result is not interpreted as a conventional negative/zero/positive comparison. Any nonzero result has the same effect.

The hint and parent values retained for a later, asymmetric repair call are both changed to zero before this comparison call. They remain their original values when comparison is bypassed.

### 4. Attach the node and update endpoint fields

#### Left attachment

The function first writes the created node address to attachment parent `+0x08`.

It then rereads the header address from context `+0x10`.

If that header equals the attachment parent:

1. Header `+0x04` is written with the created node address.
2. The header address is read again from the context.
3. Header `+0x0c` is written with the created node address, without an equality condition.

With a stable header and conventional empty-tree state, this makes all three header references identify the first node.

If the attachment parent is not the reread header, the function examines header `+0x08`. It replaces that endpoint reference with the created node only when its existing value equals the attachment parent.

#### Right attachment

The function first writes the created node address to attachment parent `+0x0c`.

It then reads the header address from context `+0x10` and examines header `+0x0c`. It replaces that endpoint reference with the created node only when its existing value equals the attachment parent.

#### Parent field

After the selected attachment and endpoint updates, the function writes the original attachment parent address to created node `+0x04`.

It does not verify that the selected child field was null. An invalid insertion position can overwrite an existing child reference.

### 5. Perform color-based repair

The repair cursor initially identifies the created node.

Before each iteration, the function follows the current context header reference and reads header `+0x04`. If that root-like reference equals the repair cursor, the loop ends.

Otherwise, it reads the cursor’s parent and the parent’s color byte. A nonzero parent color ends the loop. A zero parent color enters repair and requires a readable grandparent.

The function distinguishes two orientations by comparing the parent address with the grandparent’s left-child reference.

#### Parent is the grandparent’s left child

The uncle is the grandparent’s right child.

If the uncle is non-null and its color byte is zero, the function:

1. Writes color byte `1` to the parent.
2. Writes color byte `1` to the uncle.
3. Writes color byte `0` to the grandparent reached through the cursor’s parent links.
4. Moves the repair cursor to that grandparent.
5. Repeats the root and parent-color checks.

Otherwise, it follows the rotation-like path:

- If the cursor is the parent’s right child, it calls F-80308ed22950 with the context and parent, then makes that saved parent the repair cursor.
- It writes color byte `1` to the cursor’s current parent.
- It writes color byte `0` to the current grandparent.
- It calls F-263390bbe2c8 with the context and the grandparent obtained through the current parent links.

#### Parent is not the grandparent’s left child

This is the mirror-oriented branch. The function does not separately verify that the parent is the grandparent’s right child.

The uncle is the grandparent’s left child.

If the uncle is non-null and its color byte is zero, the same recoloring and upward cursor movement described above occurs.

Otherwise:

- If the cursor is the parent’s left child, the function calls F-263390bbe2c8 using the expanded argument form described under Dependencies, then makes the saved parent the repair cursor.
- It writes color byte `1` to the cursor’s current parent.
- It writes color byte `0` to the current grandparent.
- It calls F-80308ed22950 with the context and current grandparent.

After either rotation-like path, the loop condition is evaluated again. Termination depends on the resulting links and colors; this function contains no iteration limit or cycle detection.

### 6. Force the root color and publish the result

After leaving the repair loop, the function rereads the context’s header reference, reads header `+0x04`, and writes color byte `1` to the referenced node.

Only after that write does it store the created node address in the output slot.

The output is the original creation result, not necessarily the final root or repair cursor.

## Side effects

### Direct writes and their order

The direct-write sequence is:

1. Increment the context counter.
2. Write the selected attachment child field.
3. Perform applicable header endpoint and root updates.
4. Write the created node’s parent.
5. Perform path-dependent color writes interleaved with repair dependency calls.
6. Write color byte `1` to the final root-like node.
7. Write the created node address to the output slot.

Dependency side effects can occur before or between these writes.

The function repeatedly reads header and link fields rather than relying exclusively on an entry-time snapshot. In particular, it reads the counter after node creation, selects attachment after node creation, and reevaluates the root-like reference during repair. Unknown callees must not be assumed to preserve context fields, node links, colors, payloads, or unrelated global state.

### Ownership and lifetime

There is no direct release operation or direct payload copy in the visible body. Node creation, payload handling, allocation ownership, and any resource release performed by dependencies are unknown.

Publishing a node address does not, by itself, establish ownership transfer. The caller must use the surrounding component’s ownership contract, which is not supplied here.

### Errors and partial updates

There is no explicit error status, null-result check, exception handler, or rollback.

If node creation returns an unusable address, the counter increment and attachment writes can occur before a later invalid node access. If another dependency fails or does not return normally, prior effects are not undone by this function.

Concurrency, atomicity, synchronization, and reentrancy are not established.

## Acceptance examples

These examples are conditional contracts derived from the supplied static evidence. They are not runtime test results. Unless stated otherwise, dependencies return normally, memory is valid and non-overlapping, and the header reference remains stable.

### First insertion under the header

Given an attachment parent equal to the header and a creation dependency returning a valid node:

- The comparison dependency is not called.
- The counter increases by one, subject to the overflow limitation.
- Header references at `+0x08`, `+0x04`, and `+0x0c` are written with the created node address, in that order.
- The created node’s parent becomes the header.
- Repair immediately recognizes the created node as the root.
- Its color is written as `1`.
- The output slot receives its address last.

### Nonzero hint forces left attachment

Given a non-header parent, a nonzero hint, and a parent whose nonzero color ends repair:

- No comparison call occurs.
- The parent’s left-child field receives the created node.
- The header’s left endpoint changes only if it previously equaled that parent.
- The new node’s parent field receives the attachment parent.
- The root color is forced to `1` before output publication.

### Zero comparison result selects right attachment

Given a zero hint and a non-header parent, if F-a1e786bd6046 returns zero:

- The parent’s right-child field receives the created node.
- The header’s right endpoint is replaced only if it equals that parent.
- The comparison result does not cause rejection or signal a duplicate.

A negative nonzero result instead selects left attachment, just like any other nonzero result.

### Red-like parent and uncle

Given a repair cursor below a zero-colored parent and a non-null zero-colored uncle:

- Parent and uncle colors become `1`.
- The current grandparent color becomes `0`.
- Repair moves upward to that grandparent.
- No rotation-like dependency is invoked for that iteration.
- Subsequent behavior depends on the newly observed root and parent color.

### Missing uncle

A null uncle is treated like a nonzero-colored uncle for repair branch selection. No color byte is read through that null reference. Other required parent and grandparent references must still be valid.

### Null creation result

If creation returns null, there is no defined failure return from this function. It does not reject that result before incrementing the counter and beginning attachment. Successful completion must not be expected.
