# F-c6cb91d68549

## Purpose

F-c6cb91d68549 validates two numeric inputs, obtains and queries an object, conditionally updates shared record storage, and requests a target value when it differs from the observation.

The record handling has three branches:

- A zero fourth input clears a marker.
- A nonzero fourth input with a nonzero checked marker leaves the record untouched by direct stores.
- A nonzero fourth input with a zero checked marker saves an observation byte and the second input, then sets a marker.

The shared-record pointer is evaluated at multiple source-level points. The pointer retained immediately after the query supplies some destinations, while subsequent evaluations supply the marker-check address and, conditionally, the observation-byte destination. Equality of those pointer values is not established.

A normal return of 0 means that control reached the end. It does not establish that the target value was applied, that the record fields describe one coherent record, or that dependencies preserved shared state.

The apparent purpose of capturing a value once while a marker remains set is **inferred intent**, not an established domain meaning.

## Behavior

### Validation order

The function first compares the second input with 2 using signed interpretation. If it is greater than 2, the function returns 4 immediately.

Only after that check passes does it compare the third input with 2 using unsigned interpretation. If that value is greater than 2, it returns 4 immediately.

Either rejection occurs before acquisition, object dispatch, or shared-pointer evaluation. There is no visible error reporting beyond the return value.

### Acquisition and null handling

### Observation

For a nonnull object, the function reads its dispatch-table address, resolves the entry at byte offset 0x108, and calls it with the object address.

The result is retained as a full unsigned 32-bit observation. It is not restricted to the third input’s accepted range.

The query occurs before any shared-pointer evaluation or direct record access, including when:

- The fourth input is zero.
- The checked marker will be nonzero.
- The observation already equals the target.

Dependency effects on the shared pointer, object, record storage, or other state are unknown. In particular, the pointer used after the query is not a pointer captured before the query.

### Shared-pointer evaluations and record destinations

Immediately after the query returns, the function evaluates the shared-record pointer and retains that value for later use.

Two additional evaluations occur conditionally:

1. If the fourth input is nonzero, the shared pointer is evaluated separately to obtain the address whose offset-0 marker is checked.
2. If that checked marker is zero, the shared pointer is evaluated again to obtain the base address for the offset-1 observation-byte store.

The offset-4 signed-input store and the final offset-0 marker store use the initially retained pointer, not either later evaluation.

These are distinct **source-level evaluations**. They do not establish a particular number of physical machine loads, nor do they establish that the evaluated pointer values differ. Conversely, the contract does not assume that they are necessarily equal.

#### Fourth input zero

After retaining the pointer, the function writes byte value 0 at offset 0 through that retained pointer.

There is no marker read and no separate shared-pointer evaluation for checking a marker or storing the observation byte. The function makes no direct store to offsets 1 or 4 on this branch.

The marker write occurs even if the stored marker was already zero.

#### Fourth input nonzero, checked marker nonzero

The function evaluates the shared pointer separately and reads the byte at offset 0 through that evaluation.

Any nonzero byte suppresses capture, including values such as 2 or 255. The function then skips all direct record stores, including the final marker store.

The retained pointer has been obtained, but this branch does not dereference it for a record access. Its offset-0 byte need not equal the checked marker, and it is not normalized.

Processing continues to the observation/target comparison.

#### Fourth input nonzero, checked marker zero

The function performs the following direct stores in order:

1. Evaluate the shared pointer again and store the converted observation byte at offset 1 through that value.
2. Store the second input as a four-byte signed integer at offset 4 through the initially retained pointer.
3. Store byte value 1 at offset 0 through the initially retained pointer.

The marker that was checked, the observation-byte destination, and the two retained-pointer destinations therefore need not describe one record unless the pointer evaluations resolve accordingly.

The source representation converts the observation to a plain character-sized value for the one-byte store. For observations from 0 through 127, the saved numeric byte value is unambiguous. For other observations, exact conversion behavior and plain-character signedness are **documented_only**. The record cannot be assumed to preserve the full observation.

The full 32-bit observation remains available for the later comparison; the byte conversion does not narrow that comparison.

The marker store is last among these direct stores. This is an ordering fact, not evidence of an atomic publication or synchronization protocol.

### Conditional target operation

After record handling, the function compares the retained full unsigned observation with the third input.

- On equality, it skips the conditional operation.
- On inequality, it reads the object’s dispatch-table address again and calls the entry at byte offset 0x104 with the object address and the third input.

The comparison does not requery the object or use the saved observation byte.

The later dispatch-table read is distinct from the one preceding the query. Equality of the table addresses or preservation of the object’s dispatch state is not established.

Any return value from the conditional operation is ignored. If it returns normally, the function returns 0. There is no subsequent query, confirmation, retry, or rollback.

## Side effects

On an input-valid path, the function invokes acquisition once. Nonnull acquisition leads to one query. Record handling then produces one of three direct-store patterns:

- One marker-clear store.
- No record stores.
- Three ordered stores, potentially using different pointer-evaluation results.

The conditional target operation follows those stores when the observation differs from the target. If that operation fails to return, prior record writes may already have occurred. The same applies to partial capture if an access fails after an earlier store.

Offsets 2 and 3 are not direct store destinations. On a clear branch, offsets 1 and 4 are not direct store destinations. These statements do not guarantee preservation of unrelated logical fields under overlapping storage, aliasing, or dependency effects.

The function does not explicitly change the shared-pointer source, release the acquired object, destroy it, or deallocate record storage. Absence of an explicit release does not establish a leak: ownership and dependency-internal lifetime management are unknown.

No locking, atomic access, or memory barrier is visible. Different source-level pointer evaluations do not establish support for concurrent pointer replacement. Validity under concurrency, reentrancy, aliasing, and unusual memory mappings requires guarantees not supplied here.
