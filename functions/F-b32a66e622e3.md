# F-b32a66e622e3

## Purpose

F-b32a66e622e3 describes a recovered execution fragment that interleaves eighteen indirect dependency invocations with three explicit byte writes. One write derives its value from ambient register state; two write zero to destinations selected through byte-valued memory lookups.

The available evidence does not establish a higher-level purpose such as initialization, device control, serialization, or cleanup. Such interpretations would require information about the dependencies, address space, and calling convention.

The fragment ends at an instruction-decoding failure rather than an established ordinary return. This contract therefore describes the visible execution prefix, conditional on control reaching each operation. It does not establish a complete callable routine with a normal completion path.

- No dependency prevents subsequent execution through a fault, nonlocal transfer, termination, or other control-flow change.

These are conditional execution requirements, not validations performed by the fragment.

## Behavior

### Dependency notation

The opaque IDs F-000000000001 through F-000000000018 identify dependency invocation slots in this contract. They do not assert recovered function identities, names, signatures, or ownership behavior.

The first target is computed from ambient control-transfer state plus a displacement of 4,094 address units. The remaining targets are formed from fixed recovered address expressions. Most use the same displacement; one uses 4,076. Those expressions do not establish valid function boundaries or callable code.

The sequence below assumes each preceding operation completes and each invoked dependency returns.

### Initial invocation group and first byte write

1. Invoke F-000000000001.
2. Invoke F-000000000002.
3. Invoke F-000000000003 and retain its recovered 32-bit integer result as the **first result**.
4. Read one unsigned byte from the location one address unit beyond the ambient address-bearing value.
5. Interpret that byte as an unsigned integer, add 17, and write one byte to the resulting address.

The written byte is obtained by logically shifting the ambient unsigned value right by 22 bits, then retaining the low eight bits. Consequently, the byte consists of original bit positions 22 through 29. Original bits 30 and 31 do not survive byte truncation.

The lookup byte is an address selector, not an offset added to the lookup’s source address. A lookup value of zero selects address 17; a lookup value of 255 selects address 272.

6. Invoke F-000000000004 with one explicit argument: the first result shifted left by two bits.

The byte lookup and write occur after F-000000000003 returns and before F-000000000004 is invoked. Effects of the first three dependencies can therefore affect the memory lookup or its validity. The evidence does not establish that these dependencies preserve otherwise unmodeled machine state.

### Middle invocation group and first zero write

7. Invoke F-000000000005.
8. Invoke F-000000000006.
9. Invoke F-000000000007.
10. Invoke F-000000000008 and retain its recovered 32-bit integer result as the **second result**.
11. Compute a lookup address from the selector multiplied by 1,024, then increased by one.
12. Read one unsigned byte from that lookup address.
13. Add 17 to the unsigned byte and write a single zero byte to the resulting address.
14. Invoke F-000000000009 with four explicit arguments, in this order:
    - The selector shifted left by three bits.
    - The selector shifted left by three bits again.
    - The unshifted selector.
    - The second result shifted left by two bits.

The two selector-derived arguments have equal values wherever the shift interpretation is defined. The evidence does not establish that the implementation must evaluate the shift twice rather than reuse a computed value.

The first zero write precedes F-000000000009. That dependency may therefore observe it, overwrite it, or change memory relevant to the later lookup.

### Later invocation group and second zero write

16. Invoke F-000000000011.
17. Invoke F-000000000012.
18. Invoke F-000000000013 and retain its recovered 32-bit integer result as the **third result**.
19. Again compute the selector-based lookup address: selector multiplied by 1,024, then increased by one.
20. Read an unsigned byte from that address again.
21. Add 17 to the newly read byte and write a single zero byte to the resulting address.
22. Invoke F-000000000014 with one explicit argument: the third result shifted left by two bits.
23. Invoke F-000000000015.
24. Invoke F-000000000016.
25. Invoke F-000000000017.
26. Invoke F-000000000018.

The second selector-based lookup is a distinct read. It is not established as a reuse of the byte read before F-000000000009. Intervening dependencies or other memory activity may change the lookup byte, so the two zero writes need not select the same destination.

This establishes a limit on the available evidence. It does not independently prove that the actual program:

No completion or return contract can be inferred beyond this boundary.

### Arithmetic and width constraints

The unsigned right shift used for the first byte’s value is well specified within the recovered 32-bit model. Its subsequent byte truncation is also explicit.

Other arithmetic requires qualification:

- The selector is represented as a signed 32-bit integer.
- The three retained dependency results are represented as 32-bit integers.
- Left shifts by two or three appear in dependency arguments.
- Multiplication by 1,024 and addition of one appear in the repeated lookup address.

The evidence does not settle whether overflowing or negative signed operations should be interpreted as wrapping target instructions, limitations of the recovered representation, or invalid cases under a source-level arithmetic model. This contract does not silently impose modulo-\(2^{32}\) behavior.

For nonnegative selectors from 0 through 2,097,151, both the selector-based lookup expression and the selector shifted left by three fit within a signed 32-bit positive range. For nonnegative dependency results through 536,870,911, shifting left by two also fits within that range. These ranges avoid the principal signed-overflow ambiguity; they do not guarantee valid memory access or successful invocation.

## Side effects

### Explicit memory effects

The visible fragment performs three byte writes:

1. A derived byte to a destination selected by the ambient-address lookup.
2. Zero to a destination selected by the first selector-based lookup.
3. Zero to a destination selected by a fresh selector-based lookup.

Each destination lies numerically between 17 and 272 inclusive under the recovered byte-to-integer interpretation. This unusually low destination range is established by the visible expressions; it is not evidence that those addresses are mapped, writable, or ordinary RAM.

Each write is one byte wide. The fragment does not explicitly read the previous destination value, update neighboring bytes, or perform a read-modify-write operation. Hardware-specific behavior is unknown.

### Ordering and aliasing

Each lookup read precedes its associated write. The two selector-based reads remain separated by dependency invocations.

The writes may alias one another. A destination may also overlap a lookup source. Consequently:

- The first write can affect a later lookup if the addresses coincide.
- The first zero write can change the byte used by the second lookup if its destination equals the selector-based lookup address.
- Intervening dependencies can change either lookup contents or destination contents.

No non-aliasing guarantee is established.

### Ownership and persistent state

The fragment contains no explicit allocation, release, reference-count update, or ownership annotation. It does not establish an object layout beyond the individual byte accesses described above.

Nothing establishes whether the dependencies allocate, release, retain, or invalidate memory. In particular, their calls cannot be assumed to preserve globals, memory mappings, lookup contents, or unmodeled state.

No explicit error code, recovery branch, rollback, or cleanup path is visible. If execution fails after a write, the evidence provides no mechanism that reverses that write.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests.

### Derived byte extraction

Assume the first lookup returns 42 and the ambient unsigned value is 717,225,984, equivalent to 171 shifted left by 22 bits.

The first explicit write must place byte value 171 at address 59. It must occur after F-000000000003 returns and before F-000000000004 is invoked.

### Byte truncation at the upper end

Assume the ambient unsigned value is 4,294,967,295.

The first written value must be 255: the logical right shift produces 1,023, and the one-byte write retains its low eight bits. The write must not be widened to preserve all ten shifted bits.

### Explicit argument propagation

Assume the selector is 3, and the three retained dependency results are respectively 5, 7, and 9.

Provided the intervening accesses and calls succeed:

- F-000000000004 receives 20.
- F-000000000009 receives 24, 24, 3, and 28, in that order.
- F-000000000014 receives 36.
- Both selector-based lookup reads address 3,073.

The destinations of the zero writes still depend on the bytes read at their respective times.

### Changed lookup between zero writes

Assume the selector is 1. The selector-based lookup address is therefore 1,025. Suppose the first lookup reads 9, and an intervening dependency changes that byte to 10 before the second lookup.

The first zero write must target address 26. The second must target address 27. Reusing the earlier byte would not match the visible behavior.

### Lookup/write aliasing

Assume the selector is zero and the first selector-based lookup reads 20 from address 1.

The zero write targets address 37, not address 21 and not address 1. The byte selects an absolute low address after adding 17.

### Interrupted execution

Assume F-000000000009 does not return.

The first zero write has already occurred. The later dependency invocations and second zero write are not required to occur. No rollback is established.
