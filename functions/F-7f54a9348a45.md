# F-7f54a9348a45

## Purpose

F-7f54a9348a45 conditionally removes a selected node from a linked, color-marked structure, repairs links and colors, calls a finalization dependency, decrements a 32-bit count, and writes a continuation value to caller-provided storage.

The structure resembles a red-black tree with a header containing a root and cached extrema. That interpretation is inferred intent. The contract below distinguishes directly established operations from dependency behavior and conventional tree properties that are not independently established.

A preliminary dependency can select a no-removal path. That path writes the current header reference to output without this function performing structural repair, finalization, or count decrement.

## Interface

### Arguments and result

| Argument | Representation | Role |
|---|---|---|
| Output storage | Address writable for one 32-bit word | Receives the final continuation or header reference |
| Container | 32-bit address-like value | Locates the header reference and count |
| Selection storage | Address readable for one 32-bit word | Supplies an initial continuation value and, on a later read, the node to remove |

There is no explicit return value. The delivered result is the final 32-bit output write.

Selection storage is read before the preliminary dependency and again after continuation preparation. Those reads can yield different references. The structurally removed node is the value obtained by the later read.

### Visible layouts

The container exposes these fields:

| Byte offset | Width | Meaning |
|---|---:|---|
| +16 | 32 bits | Header reference |
| +20 | 32 bits | Count |

The header and ordinary nodes use the following visible prefix:

| Byte offset | Width | Header role | Ordinary-node role |
|---|---:|---|---|
| +0 | 8 bits | Not directly interpreted as header state | Color marker |
| +4 | 32 bits | Root reference | Parent reference |
| +8 | 32 bits | Cached minimum | Left-child reference |
| +12 | 32 bits | Cached maximum | Right-child reference |

Zero denotes an absent child. A distinct, nonzero header sentinel is part of the inferred valid-tree representation. Payload, allocation extent beyond the accessed prefix, and key layout are unknown.

Color zero has the inferred role of red; color one has the inferred role of black. The function distinguishes “zero,” “exactly one,” and “nonzero” at different points. Other byte values do not have an established valid-color interpretation.

### Preconditions and limits

Normal structural removal requires accessible storage, coherent parent and child links, and finite traversals. A selection that belongs to the represented tree is a precondition for interpreting the operations as tree removal.

The function does not visibly validate addresses, membership, cycles, colors, count consistency, alignment, or aliasing. The preliminary dependency is not established to validate those properties.

Output, selection storage, and metadata are not checked for overlap. Arbitrary overlap is not guaranteed safe. In particular, the final output write can overwrite aliased metadata after all preceding work.

## Behavior

### Preliminary decision and continuation

The first explicit reads obtain the selection word and then the container’s header reference. Their values are placed in separate temporary words. F-def435bd6947 receives the addresses of both words.

If its result is nonzero:

- The container’s header reference is read again after the call.
- That current reference becomes the output value.
- Continuation preparation, structural removal, finalization, and count decrement are bypassed.

If its result is zero, F-ab2ec0683d79 receives the address of the first temporary word. Any modification already made to that word by F-def435bd6947 is therefore available to this dependency. F-ab2ec0683d79’s explicit return value is not used; the temporary’s resulting contents supply the removal-path output.

Only after continuation preparation returns does this function reread selection storage and obtain the node used for structural removal. “Selected node” below means this later value.

The apparent intent of continuation preparation is a successor-like iterator operation. Its exact result is not established.

### Structural case selection

The selected node’s left-child field is read first. Right-child fields are then inspected as needed, including repeated reads in the supplied representation.

The structural cases are:

- No children: detach the leaf.
- Exactly one child: replace the selected node with that child.
- Two children: find the leftmost node in the right subtree and relocate that successor.

For two children, traversal begins at the right child and follows left links until a zero left link is encountered. The successor’s right child, possibly zero, is its replacement at its former position.

The selected node remains the finalization argument in every case. No payload copy is visible.

### Leaf detachment

The selected leaf’s parent is read. That parent also becomes the repair position.

If the parent equals the current header, the function performs these writes in order:

1. Header maximum becomes the header.
2. Header minimum becomes the header.
3. Header root becomes zero.

Otherwise, the parent’s left-child reference is compared with the leaf:

- Equality clears the parent’s left link.
- Inequality clears the parent’s right link, without checking that the right link actually equals the leaf.

The clear consists of four individual zero-byte writes, in ascending byte-offset order. It is not represented as a single 32-bit store.

The corresponding extremum cache is then checked: minimum for the left-link case, maximum for the right-link case. If that cache equals the leaf, it becomes the parent. The other cache is not examined by this leaf path. No extremum dependency is called.

### One-child replacement

The replacement child’s parent is first set to the selected node’s parent.

The selected node’s incoming position is then redirected:

- If the current header’s root equals the selected node, root becomes the replacement.
- Otherwise, the selected node’s parent is inspected. Its left link is replaced if equal to the selected node; otherwise its right link is replaced without another membership check.

Cached minimum is processed before cached maximum.

If cached minimum equals the selected node:

- A zero right-child field on the selected node makes the cache become the selected node’s parent.
- Otherwise, F-571f9b0c71c1 receives the replacement. Its 32-bit result is written to the minimum field of the header obtained after that call.

If cached maximum equals the selected node:

- A zero left-child field makes the cache become the selected node’s parent.
- Otherwise, F-93a046b34348 receives the replacement. Its 32-bit result is written to the maximum field of the header obtained after that call.

The maximum check occurs after minimum handling, including any minimum dependency call. Thus it must not be specified from an entry-time snapshot of the header or caches.

The replacement child is the repair position.

### Two-child relocation

The successor is structurally moved; the selected node is not replaced by copying payload.

The visible mutation order is:

1. Reparent the selected node’s left child to the successor.
2. Set the successor’s left link from the selected node’s left link.
3. Handle the successor’s former position and its right-side connections.
4. Redirect the selected node’s former incoming root-or-parent link to the successor.
5. Set the successor’s parent from the selected node’s parent.
6. Exchange the successor’s and selected node’s one-byte colors.

There are two former-position cases.

**Immediate right-child successor.** If the successor is the selected node’s right child, a present successor right child is reparented to the successor. The successor’s existing right link is retained.

**Deeper successor.** A present successor right child is first reparented to the successor’s former parent. That former parent’s left link is then set to the successor’s former right child, including zero. The successor receives the selected node’s right link, and that right child is reparented to the successor.

These are distinct incoming positions:

- The selected node’s former incoming root-or-parent link becomes a link to the successor.
- For a deeper successor, the successor’s own former incoming parent-left link becomes a link to its former right child.

The repair position is the successor’s former right child when present; otherwise it is the relocated successor itself.

The color exchange reads the successor’s color, writes the selected node’s color into the successor, and writes the saved successor color into the selected node. Consequently, the later detached-node color test observes the successor’s former color under noninterfering execution.

This path does not explicitly update either extremum cache. Under the inferred valid-tree interpretation, a node with two children is neither extremum.

### Conditional color repair

The function first reads the current header and compares it with the repair position. Equality skips repair, without reading the detached node’s color for this decision. Otherwise, the detached node’s color is read; zero skips repair.

Once repair is entered, each iteration checks:

1. Whether the repair position equals the current root.
2. If not, whether its color is anything other than exactly one.

Either condition ends iteration and leads to a final write of color one to the current repair position.

For a non-root repair position colored exactly one, its parent is read. If the parent’s left link equals the repair position, the sibling is the parent’s right child. Otherwise, the sibling is the parent’s left child.

The following terms describe both orientations:

- **Near child:** sibling child facing the repair position.
- **Far child:** sibling child facing away from it.

The repair cases are:

- **Missing sibling:** write zero to the repair position, move to the parent reference already loaded for this sibling check, and repeat.
- **Zero-colored sibling:** write one to the sibling and zero to the parent, call an orientation-specific dependency, then reload the repair position’s parent and the sibling.
- **Both sibling children absent or exactly one-colored:** write zero to the sibling, reload the repair position’s parent, move upward, and repeat.
- **Far child absent or exactly one-colored, without taking the preceding case:** recolor a present near child to one, recolor the sibling to zero, call an orientation-specific dependency, and reload the sibling through the repair position’s current parent. A zero reloaded sibling ends iteration.
- **Remaining terminating case:** copy the parent’s color to the sibling, set the parent to one, set a present far child to one, call the opposite orientation-specific dependency, and end iteration.

Every visible entry to the missing-sibling case carries a parent reference: either the parent loaded before the initial sibling check or the parent reloaded after the zero-colored-sibling dependency. Color values used elsewhere do not reach that transition.

For a right sibling, F-f5993da45e67 is used for the zero-sibling-color and terminating cases with container and parent arguments. F-7725b526e473 is used for the near-child preparation case with only the container visibly supplied. For a left sibling, those roles reverse.

After repair iteration ends, the current repair position is written with color one. This write does not occur when repair was skipped at its initial gate.

These operations resemble red-black deletion repair, but dependency signatures and effects remain unresolved. The contract does not replace them with assumed conventional rotations.

### Finalization and completion

After structural handling and any repair, F-88d9235286f8 receives the container, the selected node obtained after continuation preparation, and a literal flag of one.

Only after that dependency returns does the function:

1. Read the 32-bit count.
2. Decrement it by one.
3. Write the count back.
4. Write the continuation temporary to output storage.

The no-removal path instead performs only its final header-reference output write after the preliminary call. There is no separate success status.

## Side effects

Direct effects include header-link changes, node-link changes, individual byte clears, one-byte recoloring, a color exchange, count decrement, and the final 32-bit output store.

The count read occurs after finalization. A count modification by F-88d9235286f8 therefore affects the value subsequently decremented. There is no zero guard or saturation. At the 32-bit machine-word level, decrementing zero yields 0xffffffff; the supplied representation does not independently establish source-language signed-overflow guarantees.

No direct allocation or payload copy is visible. F-88d9235286f8 may destroy or release the selected node, but neither ownership transfer nor deallocation is established. Neither continued usability nor release of the removed node may be assumed.

Dependencies are not assumed to preserve globals, selection storage, container fields, links, colors, or ownership. Explicit post-call reloads matter, particularly for selection, the header, extrema, and repair links. Equally, a saved reference is not implicitly refreshed by a dependency’s mutation.

No rollback, locking, error status, or exception handling is visible. If a dependency does not return normally, later finalization, count update, or output may not occur; preceding writes are not visibly undone. Fault behavior for invalid addresses is outside the established contract.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests.

Except for the explicitly mutation-permitting example, removal examples assume:

- F-def435bd6947 returns zero and all invoked dependencies return normally.
- The stated selection and structural conditions still hold when selection is reread after F-ab2ec0683d79.
- Preliminary and continuation dependencies preserve selection storage and the relevant container, node, link, and color state, apart from their temporary-word results.
- Later dependencies do not interfere with the particular links, colors, caches, or count on which a stated conclusion depends, except for the explicitly described result or repair effects.
- Output storage does not overlap the observed structure or count.

### Preliminary decision selects no removal

If F-def435bd6947 returns nonzero, the function rereads the header after the call and writes that value to output. It does not call F-ab2ec0683d79 or F-88d9235286f8 and performs no direct structural mutation or count decrement.

This example does not require the dependency itself to leave the structure unchanged.

### Sole-node removal

For a coherent singleton whose parent is the header and whose children are zero:

- Maximum becomes the header, then minimum becomes the header, then root becomes zero.
- Repair is skipped because its position is the header.
- The selected node is passed to finalization with flag one.
- A count of one, preserved through finalization, becomes zero.
- Output receives the prepared continuation, which is not independently guaranteed to equal the header.

### Zero-colored non-root leaf

For a coherent non-root leaf with color zero:

- Its corresponding parent-child link is cleared by four byte writes.
- A matching corresponding extremum cache becomes the parent.
- Repair is skipped because the detached node’s color is zero.
- Finalization precedes count decrement.

These conclusions require the shared removal-path and preservation assumptions; leaf shape and color alone do not force removal.

### Node with only a right child

For a selected node with zero left link and a present right child:

- The child’s parent is updated before the selected node’s incoming link.
- That incoming link becomes the child.
- If the current cached minimum equals the selected node, F-571f9b0c71c1 supplies the value stored as minimum.
- Repair depends on the detached color and subsequent state; no particular rotation result is asserted.

### Two children with a deeper successor

For a coherent tree whose successor is deeper than the immediate right child:

- The successor’s former parent-left link becomes the successor’s former right child.
- The successor takes the selected node’s former incoming root-or-parent link.
- The successor receives the selected node’s left and right subtrees, with corresponding parent updates.
- The two nodes exchange colors.
- The original selected node, not the relocated successor, is finalized.

These conclusions do not require payload replacement.

### Continuation preparation changes selection storage

Assume a zero preliminary result and normally returning dependencies. If F-ab2ec0683d79 changes selection storage through another accessible alias, and the new selection supplies a coherent structure:

- Structural removal uses the newly read selection.
- The finalization argument is that later selection.
- Output still comes from the separate continuation temporary.

The shared selection-preservation assumption is intentionally waived here. No claim is made that the entry-time selected node is removed.
