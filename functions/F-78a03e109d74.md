# F-78a03e109d74

## Purpose

F-78a03e109d74 prepares a destination through a sequence of dependency calls, asks another dependency to populate a scratch region, then adds the scratch words into the destination in place. It returns the carry beyond the final processed word.

The dependency arrangement is consistent with computing a multiword square: accumulate off-diagonal products, double that accumulation, generate diagonal products separately, and add the two components. That interpretation is **inferred intent**, not an established arithmetic guarantee. The supplied evidence does not define the dependencies’ operations.

The established contract is the initialization, dependency-call sequence, explicit stores of dependency results, and final unsigned wordwise addition described below.

## Interface

### Inputs and result

The function accepts four arguments:

| Argument | Role visible in this function |
|---|---|
| Destination | Address of a region accessed as 32-bit unsigned words and modified in place. |
| Source | Address of a region passed to dependencies and read for 32-bit scalar arguments. |
| Count | Signed 32-bit word count used to derive offsets, iteration counts, and dependency lengths. |
| Scratch | Address passed to a dependency, then read as a sequence of 32-bit words during final addition. |

The result is a 32-bit unsigned value. For an execution that reaches the positive-length final addition and completes its accesses, the returned value is either zero or one.

The source’s elements are represented only as four-byte quantities in the supplied evidence. Scratch elements are represented as signed 32-bit integers, but the final arithmetic combines them with unsigned 32-bit values. Their bit patterns therefore participate as unsigned words, not as signed numerical addends.

### Layout and extent

For the ordinary, positive-count use case, let \(n\) be the count and let \(L=2n\).

- The destination must support the function’s direct accesses across \(L\) consecutive 32-bit words.
- The scratch region must support reads across \(L\) consecutive 32-bit words after its population dependency returns.
- The source must support the direct scalar reads and interior-pointer construction described below. For \(n\ge2\), the dependency arguments range through the source’s \(n\)-word span, but the dependencies’ actual access requirements remain unknown.
- Each indexed position advances by four bytes.
- The final addition treats position zero as the least-significant word, regardless of the machine’s byte order within a word.

The supplied function does not establish byte endianness, alignment tolerance, allocation provenance, or complete buffer requirements for its dependencies.

### Preconditions and ownership

A supported caller must provide:

- A positive count with representable signed intermediate calculations, including \(2n\).
- Valid address calculations and suitably accessible storage for every direct and transitive access.
- Destination and scratch contents that are valid to read when final addition begins.
- Any additional conditions required by the dependencies.

For signed 32-bit count arithmetic, positivity and representability of \(2n\) require:

\[
1 \le n \le 1{,}073{,}741{,}823.
\]

This is only an arithmetic bound, not a claim that such large buffers or pointer offsets are usable. Address-space and dependency limits may be substantially stricter.

The function itself contains no allocation or release operation. Nevertheless, ownership transfer, memory retention, or release by dependencies is **documented_only**: their implementations are not supplied. A caller must not infer that passing a pointer guarantees preservation of its ownership or lifetime.

## Behavior

### 1. Initial destination writes

Before calling any dependency, the function:

1. Writes zero to destination position \(2n-1\).
2. Writes zero to destination position zero.

This ordering matters when storage overlaps other arguments. A later source read may observe one of these writes.

The initialization is not a full destination clear. No claim that all remaining destination words are initialized follows from these two stores.

### 2. Initial preparation dependency

When \(n>1\), the function invokes F-146d697a6803 with:

- Destination position one as an output-region address.
- Source position one as a source-region address.
- Length \(n-1\).
- The current 32-bit contents of source position zero as a scalar argument.

After the dependency returns, its 32-bit return value is written to destination position \(n\).

The scalar source read occurs after the initial destination writes. The returned-value store occurs after all effects of this dependency call. The dependency may modify memory or other state before that explicit store; its effects are not otherwise constrained by the supplied body.

For \(n=1\), this dependency call and returned-value store are skipped.

### 3. Subsequent preparation dependencies

For each \(j\) from one through \(n-2\), in increasing order, the function invokes F-ff479513efd3 with:

- Destination position \(2j+1\) as an output-region address.
- Source position \(j+1\) as a source-region address.
- Length \(n-j-1\).
- The current 32-bit contents of source position \(j\) as a scalar argument.

After each call, its return value is written to destination position \(n+j\).

There are \(\max(n-2,0)\) such calls for positive \(n\). Their lengths decrease from \(n-2\) to one. Every explicit returned-value store occurs before the next dependency call.

The scalar arguments are read as execution reaches each call. They are not a snapshot taken at function entry. Earlier destination writes or dependency effects can therefore affect later scalar arguments if storage aliases or dependencies modify the source.

The supplied evidence does not establish whether these dependencies initialize, accumulate into, overwrite, or otherwise interpret their output regions.

### 4. Whole-destination dependency

After the preparation calls, the function invokes F-630ff3ddabe3 with:

- The destination address as its first pointer argument.
- The same destination address as its second pointer argument.
- The same destination address as its third pointer argument.
- Length \(2n\).

Thus, all three pointer arguments alias exactly. Supporting this aliasing is a requirement of the actual dependency interaction.

The caller does not branch on or explicitly store a result from this call. Its memory and external-state effects occur before the next dependency.

Interpreting this operation as doubling the prepared destination is plausible, but not established without the dependency’s contract.

### 5. Scratch-generation dependency

The function next invokes F-09c5a4de906c with:

- The scratch address.
- The original source address.
- The original count \(n\).

This call occurs after F-630ff3ddabe3 returns. Its result is not used directly by this function.

The final addition reads scratch only after this call. However, the supplied evidence does not independently prove that the dependency fills all \(2n\) scratch words, preserves the destination, preserves the source, or avoids changing global state.

### 6. Final unsigned addition

After both preceding dependencies return, the function tests whether \(L=2n\) is positive.

If \(L<1\), it returns zero without entering the addition loop. This is not an early validation guard: the initial stores and both unconditional dependencies have already occurred.

For positive \(L\), the function processes destination and scratch positions in increasing order, starting with carry zero.

At each position:

- It adds the incoming carry to the current destination word using unsigned 32-bit arithmetic.
- It adds the corresponding scratch word’s 32-bit bit pattern.
- It stores the low 32 bits of the sum back to that destination position.
- It carries the overflow into the next position.

Equivalently, for each position \(i\), using the values actually read at that position:

\[
T_i=D_i+S_i+c_i,
\qquad
D_i' = T_i \bmod 2^{32},
\qquad
c_{i+1}=\left\lfloor T_i/2^{32}\right\rfloor,
\]

with \(c_0=0\).

Because each operand is at most \(2^{32}-1\) and the incoming carry is at most one, the outgoing carry is at most one. The implementation detects overflow from each of the two additions separately and adds the overflow indicators; under this invariant, both indicators cannot be one simultaneously.

The function processes words in groups of up to four, with exit checks after each word. This grouping does not change the ascending write order. For valid positive counts, \(L=2n\) is even, so the final group contains either two or four words.

The return value is the carry after position \(L-1\). No extra destination word receives this carry.

## Side effects

### Memory and sequencing

Directly established writes are:

- The two initial zero stores.
- Stores of preparation-dependency return values.
- One final-addition store to every destination position from zero through \(2n-1\), for positive valid counts.

Dependencies may perform additional writes. No full write footprint can be asserted without their contracts.

The final addition reads the current storage contents, not immutable copies of destination and scratch. Earlier ascending stores can affect later reads if the regions overlap with an offset.

At the first position of each four-word group, the scratch word is read before the destination word, and the destination store precedes the carry update in the supplied expression sequence. At the other positions, the destination-plus-carry intermediate is formed first; scratch appears in both overflow calculation and result calculation. Consequently, an exact contract should not require a single scratch read per word.

The evidence does not specify a fixed order between operand reads within an individual arithmetic expression, nor does it establish atomic accesses, volatile semantics, or concurrent-update behavior.

### Aliasing

No overlap checks occur.

- Destination/source overlap can change scalar inputs before preparation calls.
- Destination/scratch overlap can change operands during final addition.
- Source/scratch overlap can affect what F-09c5a4de906c reads or writes.
- Exact destination self-aliasing is deliberately passed to F-630ff3ddabe3.

The wordwise arithmetic identity in the preceding section remains a description of values actually read. Interpreting it as addition of two stable, independently prepared multiword integers requires appropriate noninterference assumptions.

### Errors

There is no explicit error code, pointer validation, capacity validation, or dependency-failure branch.

The return value is an arithmetic carry, not a success indicator. An invalid address, insufficient buffer, unsupported overlap, or invalid count is not converted into a defined error result by this function.

Any dependency error mechanism, exception, nonlocal exit, or external-state change is **documented_only**.

## Acceptance examples

These examples are conditional static acceptance criteria, not reports of executed tests.

### Count one

Given valid storage and \(n=1\):

- Destination position one is zeroed before position zero.
- Neither preparation dependency is called.
- F-630ff3ddabe3 receives the destination three times and length two.
- F-09c5a4de906c receives scratch, source, and count one.
- Exactly two destination words undergo final addition.
- The returned value is the carry beyond the second word.

No particular final numerical value is established without specifying the dependencies’ effects.

### Count three

Given valid storage and \(n=3\), the preparation sequence is:

- F-146d697a6803 receives destination offset one, source offset one, length two, and source word zero. Its return is stored at destination position three.
- F-ff479513efd3 receives destination offset three, source offset two, length one, and source word one. Its return is stored at destination position four.
- F-630ff3ddabe3 then receives length six.
- F-09c5a4de906c receives count three.
- Final addition processes six words in ascending order.

The second preparation call may modify destination position three, which already received the first dependency’s return. That earlier store is not a promise that the value survives unchanged.

### Carry propagation

Suppose \(n=1\), the dependencies return normally, and immediately before final addition the destination words are \([2^{32}-1,0]\), while scratch words are \([1,0]\), with no interfering writes.

The destination becomes \([0,1]\), and the function returns zero.

If both destination words instead equal \(2^{32}-1\), with scratch still \([1,0]\), the destination becomes \([0,0]\), and the function returns one.

### Signed-looking scratch data

Suppose \(n=1\), destination is \([0,0]\), and scratch has bit patterns \([2^{32}-1,0]\) immediately before addition.

The result is \([2^{32}-1,0]\), with return zero. A signed interpretation of the first scratch word as negative one does not make the operation subtraction.

### Zero count

A zero count is not accepted as a safe no-op. The first explicit store targets destination position negative one. Even if an unusual memory arrangement makes that access possible, dependencies are still called before the nonpositive-length return check.
