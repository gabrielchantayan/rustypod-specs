# F-a4e3948467d1

## Purpose

F-a4e3948467d1 selects an integer position, optionally performs two receiver-associated indirect operations, and invokes a final dependency with that position.

Its observable behavior has three principal paths:

- A nonzero character-width conversion of a receiver state word routes execution through a separate dependency and then, if that dependency returns, through a dependency identified as non-returning.
- A request equal to `0x7FFFFFFF`, combined with a positive receiver count, selects the count minus one without calling the validation dependency.
- Other requests pass through a validation dependency. A zero result causes an immediate return of `-1`; a nonzero result permits subsequent processing.

A selected position of `-1` suppresses all subsequent indirect operations and the final dependency. Other selected positions cause an unconditional indirect operation after any conditional range operation, followed by the final dependency.

The apparent interpretation is a position-based mutation with special handling for an end-position request and a receiver state requiring exceptional processing. That interpretation is inferred intent, not an established semantic description of the dependencies.

## Interface

### Inputs

The function accepts:

1. **A receiver pointer.** The visible representation is a pointer to integer storage. The receiver also supplies a dispatch-table reference through its first integer word.
2. **An integer request.** This is passed by value. It may become the selected position or be replaced by a value derived from the receiver count.

The visible receiver accesses are:

| Receiver component | Position in integer storage | Observed use |
|---|---:|---|
| Dispatch reference | Word 0 | Locates callable entries at byte displacements `0xB8` and `0xBC` |
| Count-like field | Word 1 | Controls sentinel selection and the conditional range operation |
| State word | Word 4 | Converted to a character type and compared with zero |

The supplied representation does not independently establish the target integer width, pointer width, byte order, character width, or signed-character behavior. In the likely 32-bit integer model, words 1 and 4 lie at byte offsets 4 and 16. Those byte offsets are conditional on that model; the integer-word positions are directly evidenced.

### Result

On an ordinary return, the result is an integer:

- `-1` if the validation dependency returns zero;
- otherwise, the selected position, including `-1` when that value itself was accepted.

The interface provides no separate success indicator. Therefore, a returned `-1` alone cannot distinguish validation rejection from an accepted request of `-1`.

No error object, ownership token, or dependency result is returned.

### Preconditions

For defined execution of the visible accesses:

- The receiver must support the integer-word reads required by the path taken.
- Any dispatch reference used must identify storage containing callable entries at the stated displacements.
- Selected indirect targets must accept the arguments supplied to them.
- Arithmetic must be representable under the target integer semantics.
- Dependencies must return control when subsequent ordinary processing is expected.

There is no visible null check, receiver-size check, dispatch-target check, or local recovery from a dependency failure.

Receiver validity must persist across returning dependency calls whenever later accesses occur. The visible function does not establish that those dependencies preserve receiver storage or its dispatch reference.

## Behavior

### 1. Initial state gate

The first observable receiver read is word 4. Its value is converted to a character type, and that converted result is tested against zero.

This is not visibly a comparison of the complete integer word with zero. A nonzero integer word can produce a zero character-width result on a target with truncating conversion semantics.

When the converted result is nonzero:

1. F-1b252d1a4cf9 is called with the receiver and the original request.
2. If that call returns, F-feee9156a257 is called with no visible arguments.
3. The supplied evidence identifies F-feee9156a257 as non-returning.

This path does not reach ordinary request selection, validation, dispatch-table operations, or the final return under the represented control-flow contract.

The behavior of F-1b252d1a4cf9 is unknown. It may itself fail to return. Its return value, if any, is not used.

If F-feee9156a257 unexpectedly returns, the supplied non-returning model does not establish a supported continuation. This case is documented_only rather than assigned an invented fallback behavior.

When the character-width result is zero, processing continues. The state word is not checked again, even if a later dependency changes it.

### 2. Selection of the position

The request is compared with the exact integer constant `0x7FFFFFFF`, decimal 2,147,483,647.

If the request equals that constant and the receiver count is positive:

- The selected position becomes the receiver count minus one.
- F-402eef64af83 is not called.

The constant is an exact distinguished request value. Calling it the maximum integer value is valid only for a signed 32-bit integer model.

If either part of the condition is false:

- F-402eef64af83 is called with the receiver and the original request.
- A zero result causes an immediate return of `-1`.
- Any nonzero result permits processing to continue with the original request as the selected position.

The validation result is tested only for zero versus nonzero. No distinction between positive and negative nonzero results is visible.

The count is consulted in the sentinel-selection condition only when the request equals `0x7FFFFFFF`. An ordinary request does not require this early count read.

The positive-count check and the subsequent count-minus-one expression are distinct source-level accesses. With no intervening visible call and stable receiver memory, they observe the same count. Concurrent or otherwise externally changing storage is not specified.

### 3. Selected position of `-1`

After successful selection or validation, the selected position is compared with `-1`.

If it equals `-1`:

- Neither dispatch-table operation occurs.
- F-d6032bc0598f is not called.
- The function returns `-1`.

An original request of `-1` still passes through F-402eef64af83 first. The `-1` special case does not bypass validation.

With a stable positive count, sentinel selection cannot produce `-1`: subtracting one from a positive count produces zero or a positive value.

### 4. Conditional range operation

For a selected position other than `-1`, the function evaluates whether the selected position plus one is strictly less than the receiver count.

If that comparison is true, an indirect call is made using the receiver’s dispatch entry at byte displacement `0xB8`. Its visible arguments, in order, are:

1. The receiver.
2. The selected position plus one.
3. The receiver count minus one.
4. The literal `0xFFFFFFFF`.

The two arithmetic arguments resemble inclusive range endpoints, but endpoint meaning is not established. Nor is the meaning of the final literal established.

If the comparison is false, this indirect call is omitted.

The receiver count used here is read after any returning validation call. The function does not retain and reuse a count captured before validation. A validation dependency that changes the count can therefore change whether this operation occurs.

The comparison and the call arguments contain separate count accesses. The evidence establishes the conditional call and its argument expressions, but not a portable total order among reads performed while evaluating different arguments.

### 5. Unconditional indirect operation

For every selected position other than `-1`, provided earlier processing returns normally, the function invokes the receiver’s dispatch entry at byte displacement `0xBC`.

Its visible arguments are:

1. The receiver.
2. The literal `0xFFFFFFFF`.

This call occurs whether or not the `0xB8` operation occurred.

If the `0xB8` operation ran, the dispatch reference for the `0xBC` call is obtained afterward. The visible expression does not establish a dispatch-table snapshot spanning both calls. A changed dispatch reference can therefore affect the second target.

### 6. Final dependency and return

After the `0xBC` operation returns, F-d6032bc0598f is called with:

1. The receiver.
2. The selected position.

If that dependency returns normally, the function returns the selected position.

The return values of both indirect operations and F-d6032bc0598f are unused. They do not replace the selected position or create a visible success/failure branch.

## Side effects

### Direct effects

The function directly reads receiver storage and performs integer selection and comparisons. No direct assignment to receiver memory or a global variable is visible.

For a selected position other than `-1`, the normal call order is:

1. The `0xB8` operation, only if its range condition is true.
2. The `0xBC` operation.
3. F-d6032bc0598f.
4. Return of the selected position.

Validation, when required, precedes that sequence.

### Dependency-mediated effects

The dependencies and indirect targets may mutate receiver state, alter globals, perform external operations, release storage, or terminate execution. Their implementations are not supplied, so none of those effects can be either asserted or excluded.

In particular:

- A successful validation result does not prove the receiver is unchanged.
- The first indirect operation does not establish preservation of the count or dispatch reference.
- No operation is visibly rolled back if a later call fails or does not return.
- A non-returning call prevents later calls and the final return from being observed.

### Ownership

No allocation, retain, release, or ownership-transfer operation is directly visible. The receiver is passed unchanged to dependencies.

This establishes neither a borrowed-ownership guarantee nor a transfer of ownership. Dependency ownership behavior is documented_only. A caller relying on the receiver after this function returns needs information beyond the supplied body.

### Arithmetic and literal widths

The relevant expressions are count minus one and selected position plus one.

Under signed 32-bit semantics:

- Subtracting one from a stable positive count is representable.
- Adding one to `2,147,483,647` is not representable.
- A sentinel request with a nonpositive count reaches validation. If validation accepts that request, subsequent processing attempts the problematic plus-one expression.
- Other accepted requests are not locally checked for arithmetic safety.

The contract does not assign wraparound behavior to signed overflow.

The literal `0xFFFFFFFF` has value 4,294,967,295 before any target-specific typing or call-boundary interpretation. In a 32-bit representation it is all ones, but the evidence does not establish that each indirect callee interprets it as signed `-1`. These call arguments must not be conflated with the explicit integer `-1` used for control flow and return values.

## Acceptance examples

These are conditional static expectations, not runtime test results. Except where stated, assume a zero initial character-width state, stable receiver storage, representable arithmetic, valid dispatch targets, and normal returns from called dependencies.

### Sentinel selects the final counted position

Given request `0x7FFFFFFF` and count 5:

- Validation is skipped.
- The selected position is 4.
- The range condition is false because 5 is not less than 5.
- The `0xBC` operation receives the receiver and `0xFFFFFFFF`.
- F-d6032bc0598f receives the receiver and 4.
- The result is 4.

- The `0xBC` operation follows.
- F-d6032bc0598f receives position 1.

### Rejected request

- The result is `-1`.
- Neither indirect operation nor F-d6032bc0598f is called.

Effects already performed by validation are not undone.

### Accepted `-1`

Given request `-1` and a nonzero validation result:

- The result is `-1`.
- Both indirect operations and F-d6032bc0598f are skipped.

This has the same returned integer as rejection, but a different validation outcome.

### Validation changes the count

- The `0xB8` operation is skipped because 2 is not less than 2.
- The remaining calls occur, and the result is 1.

### Accepted negative position other than `-1`

- The `0xB8` arguments include `-1` and 4 as the arithmetic values.
