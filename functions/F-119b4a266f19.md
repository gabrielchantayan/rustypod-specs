# F-119b4a266f19

## Purpose

F-119b4a266f19 obtains provider-supplied data and conditionally constructs a tagged byte record in caller-supplied storage. The ordinary record contains a two-byte outer header, a one-byte length followed by a byte region, and a one-byte length followed by 32-bit entries encoded most-significant byte first.

Acquisition occurs before the capacity check. If execution reaches the final portion, the function writes both outer-header bytes even when acquisition fails or the payload is rejected.

The established behavior consists of calls, arithmetic, reads, and writes. Serialization is inferred intent. The supplied evidence does not establish that the external operation copies bytes or that the post-acquisition dependency releases a resource.

In particular, payload construction precedes the post-acquisition dependency. Final payload contents are conditional on that dependency preserving the destination payload; only the two outer-header bytes are directly written afterward.

### Ordinary record layout

Define the computed payload size:

**P = (L + 4 × N + 2) modulo 2³².**

For nonnegative L, N no greater than twenty, initialized entries, representable offsets, and provider outputs stable during emission, the direct payload operations describe this layout:

| Byte offset | Width | Intended contents |
|---|---:|---|
| 0 | 1 byte | `0xA3` |
| 1 | 1 byte | Low eight bits of P |
| 2 | 1 byte | Low eight bits of L |
| 3 | L bytes | Region acted upon by the external operation |
| L + 3 | 1 byte | Low eight bits of `4 × N` |
| L + 4 + 4j | 4 bytes | Entry j, most-significant byte first, for 0 ≤ j < N |

This becomes a final serialized record only if the external operation supplies the intended region and subsequent dependency activity preserves the payload. In particular, F-5e3309c9d083 must preserve destination offsets 2 onward. Its contract is not supplied.

The length fields truncate rather than validate. The function does not reject L above 255, P above 255, or an entry-byte count above 255 merely because the associated field is one byte. Separately, N above twenty exceeds the available local entry storage and is not an ordinary valid input.

## Behavior

### Acquisition

The function first establishes a zero payload-size state.

It reads a value through a fixed global location, then calls F-e1bc66d08fcf with that value, selector `3`, and the four output-storage arguments described above. The provider call precedes the capacity decision and all direct destination writes.

A provider result of exactly zero selects successful acquisition. Every nonzero result selects failure. The provider’s status is not propagated as the function’s result.

The width and semantic meaning of the global-derived input are not established by the supplied expression.

### Acquisition failure

On nonzero provider status:

- Payload-size state remains zero.
- No direct payload writes occur.
- The external operation is not called by this function.
- F-5e3309c9d083 is not called by this function.
- Execution proceeds to the outer-header writes and return selection.

This does not establish that the provider left destination-related state unchanged, initialized no outputs, or allocated no resources.

### Size calculation and admission

After successful acquisition, the function calculates P using unsigned 32-bit arithmetic. The multiplication, combination with L, and addition of the two inner length bytes are reduced modulo 2³². A negative L is converted into unsigned arithmetic for this calculation; it is not explicitly rejected.

The payload is rejected precisely when:

**((C − 2) modulo 2³²) < P.**

Rejection sets the retained payload-size state to zero. Admission retains P and enters payload emission.

This comparison is not a complete capacity-safety check:

- For C = 0, C − 2 becomes `0xFFFFFFFE`.
- For C = 1, C − 2 becomes `0xFFFFFFFF`.
- Ordinary small payloads can therefore be admitted with either advertised capacity.
- Arithmetic wrap can make a large mathematical payload produce a small P.

The body contains no overflow detection.

### Admitted payload emission

The observable direct-write and call order is:

1. Store the low eight bits of L at destination offset 2.
2. Call F-unknown-01 with destination offset 3, the source/handle value, and the signed length.
3. Store the low eight bits of the then-current unsigned entry count shifted left by two at the offset formed from the then-current signed length plus three.
4. Emit entries in increasing index order.

For each entry, four separate byte stores occur in this order:

- Bits 31–24.
- Bits 23–16.
- Bits 15–8.
- Bits 7–0.

The signed length state advances by four after each emitted entry. Under stable provider outputs, the first entry begins at L + 4, and each subsequent entry begins four bytes later.

The source entry is referenced separately for each emitted byte. The evidence does not establish a single atomic entry snapshot or any concurrency guarantee.

The loop condition uses the unsigned entry count. There is no visible check against the twenty-entry storage bound. The simple N-entry description assumes that this count remains stable.

P is computed before F-unknown-01 is called and is not recomputed afterward. The function also writes the first inner length byte before that call, then uses length and count state afterward. If the dependency changes those outputs through retained references or aliases, the earlier length byte, retained P, later offsets, and iteration count need not agree. The dependency’s ability or obligation to avoid such changes is **documented_only**.

The return value, if any, of F-unknown-01 is not used for a visible success check. No transfer-error branch is present.

### Post-acquisition call

Following every successful acquisition, the function calls F-5e3309c9d083 with the then-current source/handle value:

- After payload emission when admitted.
- After the admission decision when rejected.
- Before the final outer-header writes in either case.

This call is absent after provider failure.

A resource-release purpose is inferred, not established. The dependency may have destination, global, or ownership effects that the supplied body does not describe.

Consequently, directly emitted payload bytes are not unconditional final-output guarantees. F-5e3309c9d083 can, under the unknown dependency contract, alter them before the header is written. The function does not restore payload bytes afterward.

### Outer header and return

If control reaches the final portion:

1. Destination offset 0 receives `0xA3`.
2. The function calculates **T = (retained payload-size state + 2) modulo 2³²**.
3. Destination offset 1 receives the low eight bits of the retained payload-size state.
4. If C ≤ T, the result is **(C + 1) modulo 2³²**.
5. Otherwise, the result is T.

For an admitted payload, the retained state is P. For failed acquisition or rejected payload, it is zero.

When the retained state is zero:

| C | Result |
|---:|---:|
| 0 | 1 |
| 1 | 2 |
| 2 | 3 |
| Greater than 2 | 2 |

Both header stores are attempted in every row if execution reaches them. Equality with T selects C + 1, not T.

## Side effects

### Destination state

The outer header is written last. Payload rejection and acquisition failure do not cause this function to clear destination bytes beyond offsets 0 and 1.

Successful acquisition introduces dependency activity before those final writes, even when payload admission fails. Therefore, “no direct payload writes” does not guarantee that the payload area is unchanged.

Output is not transactional:

- Payload stores may occur before the external operation returns.
- Additional payload stores follow that operation.
- F-5e3309c9d083 runs after payload construction.
- Header stores occur only afterward.

A fault or non-returning dependency can leave partially modified storage. No rollback, exception recovery, or error-result conversion is visible.

### Global state

The body explicitly reads a global-derived acquisition input and contains no explicit global assignment. This is not a global-preservation guarantee: all dependency side effects remain unspecified.

### Storage and ownership

The twenty-entry array is local storage passed to the provider. Subsequent reads are governed by the provider-supplied count without a bounds check.

No allocator call is directly visible. The source/handle value is forwarded to two dependencies on the admitted path and to F-5e3309c9d083 even after rejection.

No ownership transfer to the caller is established. Neither release nor non-release can be inferred from the name or placement of F-5e3309c9d083. Retention of output-storage addresses by dependencies is likewise unresolved; the function supplies no visible lifetime extension.

## Acceptance examples

These are conditional static examples, not runtime observations.

Unless an example states otherwise, assume valid actual storage, initialized and stable provider outputs, representable signed offsets, and normally returning dependencies. For examples asserting complete final record bytes, additionally assume:

- F-unknown-01 copies exactly L source bytes into its destination region without disturbing other relevant state.
- F-5e3309c9d083 preserves the entire destination payload, including both inner length bytes.

Without the second assumption, the payload sequences below describe construction results before the post-acquisition call, not guaranteed final payload contents.

### One entry: rejection, exact fit, and spare capacity

Given successful acquisition, L = 3, source bytes `11 22 33`, N = 1, and entry `0x12345678`:

- P = 9.
- T = 11.

For C = 10, the admission comparison is 8 < 9, so the payload is rejected. F-unknown-01 is not called. F-5e3309c9d083 is called before the header stores. The direct final header is `A3 00`, and the result is 2. The function makes no direct payload stores on this path.

For C = 11, the payload is admitted. Under the explicit destination-preservation assumption, the final record is:

`A3 09 03 11 22 33 04 12 34 56 78`

The result is 12 because C equals T.

For C = 12, the same conditional final record is produced, and the result is 11.

### Empty successful result

Given successful acquisition, L = 0, N = 0, and C = 5:

- P = 2 and T = 4.
- F-unknown-01 is still called with length zero.
- Both inner length bytes are directly written as zero.
- F-5e3309c9d083 is called afterward.
- The result is 4.

Under the stated transfer and payload-preservation assumptions, the final bytes are `A3 02 00 00`.

Without payload preservation by F-5e3309c9d083, either inner zero byte may differ in the final destination. The final direct header stores remain `A3 02`.

### Acquisition failure

Given any nonzero provider status and C = 8:

- This function performs no payload transfer or entry emission.
- It does not call F-5e3309c9d083.
- Final direct header stores produce `A3 00`.
- The result is 2.

Other destination bytes receive no direct stores from this function. Provider side effects are not constrained by this example.

### Capacity underflow

Given successful acquisition, L = 0, N = 0, and C = 0:

- The capacity subtraction produces `0xFFFFFFFE`.
- P = 2 is admitted.
- The function attempts the nominal four-byte record construction.
- The result is 1.

This example requires actual storage sufficient for the attempted accesses despite C = 0. It demonstrates that advertised capacity alone does not ensure memory safety.

### Truncated outer length

Given successful acquisition, L = 254, N = 0, and C = 259:

- P = 256 and T = 258.
- Admission succeeds.
- The direct final outer header is `A3 00`.
- Payload construction writes `FE` at offset 2 and zero at offset 257.
- The result is 258.

Under the explicit transfer and post-acquisition payload-preservation assumptions, the final record has 258 bytes: the header, `FE`, 254 copied bytes, and the zero entry-byte count.

Without preservation by F-5e3309c9d083, the `FE`, copied region, and trailing zero are not guaranteed final contents. The zero outer length still follows from truncating P.
