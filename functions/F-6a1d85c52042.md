# F-6a1d85c52042

## Purpose

F-6a1d85c52042 conditionally prepares and submits a sequence of frames using an object-associated buffer and an input-address argument. It brackets ordinary execution with two object-associated dependency calls and returns a 32-bit difference between the requested count and its final remaining-count state.

**Established static behavior:** the function writes two frame-header bytes, invokes operations with payload-region and input-region addresses, maintains a continuation state, conditionally changes external state, submits frames, and updates its remaining count.

**Inferred intent:** the three-argument operation appears intended to transfer input bytes into the frame, and the two-argument operation appears intended to fill unused payload space. Neither operation has a supplied implementation or semantic mapping. Actual copying, fill contents, and resulting payload contents are therefore not established.

The return value is progress-accounting arithmetic. It is not a submission status and does not independently establish how many bytes were copied, consumed, or delivered.

## Behavior

### Entry and processing gate

F-338d16f9ce72 is called first with the object address plus `0x44`. Its result is unused.

After that call, the function initializes its remaining count to the requested count, continuation state to zero, restoration latch to false, and saved external-state value to zero.

It then reads the enable byte at object offset `+0x14`. Processing requires both a nonzero enable byte and a zero suppression selector. A disabled object bypasses the processing body without requiring the selector comparison, but does not bypass the entry or ordinary exit calls.

Each iteration additionally requires the remaining count, interpreted as signed 32-bit, to be strictly positive:

- Zero starts no iteration.
- Values from `1` through `0x7fffffff` are initially eligible.
- Values from `0x80000000` through `0xffffffff` start no iteration.

The enable byte and selector are not rechecked at each iteration.

### Producer invocation and size initialization prerequisite

At iteration entry, signed 32-bit submission-count storage is set to zero.

F-d9580b9b8dc6 receives:

1. The object address plus `0x1c`.
2. Remaining count plus one, using unsigned 32-bit arithmetic.
3. The address of unsigned 32-bit size storage.

For an eligible iteration-entry remaining count, the requested size ranges from `2` through `0x80000000`.

**The size storage is not initialized before being passed to the producer.** A defined value must exist before its subsequent decrement. If the first reached producer invocation returns without establishing that value, the decrement reads uninitialized storage; the source supplies no defined fallback size. On later iterations, the storage is still not reset before the producer call, so lack of a fresh output must not be interpreted as a defined default or a newly supplied size.

After the producer returns, its one-byte result is written at frame offset zero. The frame address for this write is read from object offset `+0x2c` after the producer call.

Only after that write does the function decrement the size storage by one, using unsigned 32-bit arithmetic. A defined value of zero therefore becomes `0xffffffff`, without a local validation error.

### Distinct size reads and payload-region operations

The size storage has escaped to a dependency. Its decremented value is not guaranteed to remain constant throughout the iteration.

The function first selects the unsigned minimum of the remaining count and the size value read before the three-argument operation. That selected value becomes the operation’s third argument.

The operation receives:

1. **Destination-like address:** the frame address then read from the object, plus two.
2. **Source-like address:** input address plus requested count minus remaining count.
3. **Unsigned 32-bit quantity:** the selected minimum.

The input offset uses 32-bit unsigned arithmetic. If remaining count exceeds requested count, the offset wraps rather than being rejected. Address calculations do not establish the validity of the resulting memory references.

The operation is invoked even when its third argument is zero. Its actual behavior—including whether it copies bytes, how it treats overlap, and whether zero permits otherwise invalid addresses—is unknown.

After this operation returns, the function reads the size storage again for comparison with the remaining count. This later value, not necessarily the one used to select the preceding third argument, determines the branch:

- If size is smaller than remaining count, no two-argument operation occurs.
- Otherwise, the two-argument operation receives the current frame address plus remaining count plus two, and size minus remaining count.

The second operation is invoked even when its second argument is zero. Its contents, transformation, and memory-access behavior are unknown.

The size comparison and possible second-operation length occur after the first operation. Submission length is read still later, after any second operation and external-state calls. Without a preservation contract, these quantities need not describe one consistent payload size.

### Continuation-state transitions

The continuation state persists across iterations. Its update uses the branch selected by the size comparison after the three-argument operation:

| Comparison at that point | Previous state | Next state |
|---|---:|---:|
| Size smaller than remaining count | `0` | `2` |
| Size smaller than remaining count | `2` | `3` |
| Size smaller than remaining count | `1` or `3` | Unchanged |
| Size at least remaining count | `0` | `0` |
| Size at least remaining count | Any reachable nonzero state | `1` |

On the second branch, the two-argument operation occurs before the state update. A size change during that operation does not cause the branch to be reconsidered.

The resulting state is written as one byte at offset one of the frame address read at that stage. These encoded transitions are established; protocol meanings such as “first,” “middle,” or “last fragment” are inferred intent only.

### Conditional external-state changes

After writing the continuation byte, the function reads the downstream-object value from object offset `+0x0c` and inspects the byte at that address plus eight.

If the byte is nonzero:

1. An unmapped query operation is called with zero.
2. Its 32-bit result replaces the saved external-state value.
3. An unmapped setter operation is called with zero and three.
4. The restoration latch becomes true.

The latch remains true for the rest of the invocation. It is not reset at subsequent iteration boundaries.

Consequently, a later successful iteration can perform restoration despite observing a zero downstream flag. It uses the most recently saved value. A later nonzero flag causes another query and replaces that value.

No supplied contract establishes what state is queried, whether setting three succeeds, or whether other dependencies preserve it.

### Submission and failure

F-85f3130a1b96 receives:

1. The downstream-object value read from object offset `+0x0c`.
2. `0x83`.
3. The frame address read from object offset `+0x2c`.
4. The size storage’s value at submission-argument evaluation, plus two modulo `2^32`.
5. The address of the signed 32-bit submission-count storage.
6. Zero.

The submitted length is not necessarily the earlier selected third argument plus two. The size storage may have changed during intervening operations.

The count storage was initialized at iteration entry, not immediately before submission. Once its address has escaped on an earlier submission, no supplied dependency contract guarantees that its initialized value remains unchanged until a later submission.

If the submission result is nonzero, processing stops immediately:

- No restoration is performed for that submission.
- The remaining count is not updated.
- Earlier writes and external-state operations are not undone.
- Ordinary exit still follows.

A count written during a failing submission does not contribute to the remaining-count update.

### Successful submission and progress

If submission returns zero and the restoration latch is true, the setter is called with zero and the saved external-state value.

Only after that restoration call, if any, does the function read submission-count storage for the remaining-count update:

**New remaining count = old remaining count − count value read at update time + 2, modulo `2^32`.**

Thus progress need not use the count value that existed immediately when submission returned. A dependency retaining access to escaped storage may change it during restoration. The signed count participates in unsigned arithmetic through its 32-bit representation.

There is no validation connecting this count to frame length, the earlier three-argument operation’s quantity, actual input consumption, or delivery. Zero submission status does not guarantee progress.

The next iteration occurs only if the updated remaining-count bit pattern represents a positive signed 32-bit integer.

### Exit and return

F-1333331b2da1 is called with the object address plus `0x44` after ordinary bypass, loop completion, or submission failure.

The return expression is requested count minus final remaining count modulo `2^32`.

No iterations produce zero. A first-submission failure also produces zero, despite possible writes and external-state changes. A later failure contributes no additional arithmetic progress.

Faults, abnormal dependency termination, and nonlocal control transfers have no established exit-call or restoration guarantee.

## Side effects

The observable sequence within an iteration is:

1. Initialize submission-count storage.
2. Invoke the producer with the size-storage address.
3. Write frame byte zero.
4. Decrement size storage and select the three-argument operation’s quantity.
5. Invoke that operation.
6. Re-read size for branching and possibly invoke the two-argument operation.
7. Update and write frame byte one.
8. Inspect the downstream flag.
9. Optionally query and set external state.
10. Read submission arguments, including the then-current size, and submit.
11. On success, optionally restore external state.
12. Read count storage and update remaining count.

Repeated reads of frame and downstream addresses are significant. The function does not capture either field once for the entire invocation. Different stages may use different addresses if a dependency or an aliasing write changes an object field.

The representation does not establish relative evaluation order among independent argument expressions within a single call.

No direct assignment to the listed object fields is visible. Indirect frame writes or unknown dependency effects may nevertheless alter them through aliasing. The function provides no overlap or alias validation.

The two output-storage addresses escape through dependency calls. No non-retention or preservation guarantee is supplied. This contract does not assume those locations are immune to later dependency effects, nor does it authorize retention beyond their valid lifetime.

## Acceptance examples

These are conditional static examples, not executed tests.

Unless an example states otherwise, assume valid reached addresses, defined producer output, and preservation of escaped size and count storage between the relevant writes and reads. Counts below mean values still present when progress is updated, including after restoration.

1. **Processing bypass.** With a zero enable byte, entry and exit calls occur, no producer or submission call occurs, and the result is zero. A nonzero enable byte with a nonzero suppression selector has the same no-iteration result.

2. **High-bit requested count.** With processing enabled and requested count `0x80000000`, the initial signed-positive condition fails. Entry and exit occur; the result is zero.

3. **Single sufficient frame.** Requested count five and producer output six yield decremented size five. The three-argument operation receives the input base, frame plus two, and quantity five in their specified argument positions. The two-argument operation is called with frame plus seven and quantity zero. Continuation state is zero; submission length is seven. A successful submission with update-time count seven leaves remaining count zero and returns five. Five input bytes appear in the frame only if the unknown operation’s contract actually establishes that transfer.

4. **Three submissions with exact completion.** Requested count ten and producer output five on each iteration yield size four. Successful update-time counts six, six, and four produce remaining counts ten, six, two, and zero. Continuation bytes are `2`, `3`, and `1`. On the last iteration, the three-argument quantity is two and the two-argument quantity is two. Returned progress is ten; payload contents remain conditional on dependency semantics.

5. **Three submissions with over-accounting.** Keep the preceding sizes but use update-time count six on all three submissions. Remaining counts become ten, six, two, and `0xfffffffe`. The signed-positive condition then fails. The returned unsigned difference is twelve, not ten.

6. **Failure after external-state change.** If the first iteration observes a nonzero downstream flag and submission fails, query and setter-to-three calls occur, but restoration does not. Ordinary exit follows and the result is zero.

7. **Sticky restoration.** A successful iteration observes a nonzero flag and saves a value. A later successful iteration observes a zero flag. The later iteration still invokes restoration with the saved value.

8. **Size changed by an intervening operation.** With remaining count five and decremented size five, the first operation receives quantity five. If it changes retained size storage to two, the subsequent comparison takes the smaller-size branch and changes state zero to two. If size then remains two, submission length is four. The earlier quantity is not recomputed.

9. **Count changed during restoration.** For remaining count five, suppose submission returns zero with count seven, but restoration changes retained count storage to four. Progress uses four: remaining count becomes three, not zero.

10. **Nonprogress and invalid size initialization.** Repeated successful submissions with update-time count two leave remaining count unchanged and can continue indefinitely. Separately, a defined producer output zero underflows to `0xffffffff`; an absent initial size value instead leaves the decrement without a defined input. These are distinct cases, neither repaired locally.
