# F-4b651926be02

## Purpose

F-4b651926be02 coordinates a transfer between a caller-provided memory region and a backend object. It selects one of two directions, handles an initial partial backend unit through a scratch buffer, transfers complete units directly, and handles any final remainder through the scratch buffer.

The supplied static evidence supports a **512-byte logical transfer quantum** and two backend operation slots. Their apparent roles are reading and writing, but those meanings depend on unavailable backend implementations. Likewise, an external memory-transfer dependency appears to copy bytes, but its implementation and complete calling contract are unavailable.

This contract distinguishes:

- **Established:** control flow, explicit field accesses, visible arguments, arithmetic, and returned values supported by the supplied representation.
- **Inferred intent:** block-oriented read/write behavior and conventional memory-copy semantics.
- **documented_only:** behavior that cannot be determined without dependency contracts, calling-convention information, or additional evidence.

No runtime tests have been performed.

- `21` when the initial checks succeed, the direction is nonzero, and the write-inhibition flag is nonzero.

## Behavior

### 1. Eligibility checks

The function first reads the byte at context offset `0x0C`.

If it is zero, the function returns `2` without reading the backend field or proceeding to conversion or transfer.

Otherwise, it reads and captures the backend address at offset `0x04`. A null captured address also produces `2`.

Only after these checks does a nonzero direction cause the byte at offset `0x18` to be read. If that byte is nonzero, the result is `21`; no conversion or transfer follows.

The read direction bypasses this inhibition check entirely.

These checks do not establish that the context, operation table, buffers, or later reloaded backend addresses are valid.

### 2. Initial position conversion

The function calls F-d7be9cfb4000 with the position token and the 32-bit value read from context offset `0x20`.

The result is represented as 64 bits and consumed as two 32-bit portions:

- The low portion is added to the context value at offset `0x10`, producing the current backend position.
- The high portion determines whether initial partial-unit handling occurs.

The scratch-buffer address at offset `0x50` is then read and captured. This capture occurs after F-d7be9cfb4000 returns. Consequently, mutations by that dependency can affect the subsequently read base and scratch address.

An inferred interpretation is that the result contains a quotient and remainder. This is not an established contract for F-d7be9cfb4000.

### 3. Initial partial-unit handling

If the high portion of the conversion result is nonzero, the function computes:

- A scratch displacement equal to that portion multiplied by 512.
- An available-byte quantity equal to the current context extent at `0x1C` minus that displacement.
- A requested-byte quantity equal to the current transfer count shifted left by nine bits.
- A partial byte count equal to the unsigned minimum of those two quantities.

The unsigned comparison is significant. A negative-looking subtraction result, when interpreted as an unsigned 32-bit value, need not limit the transfer to a small or valid extent.

#### Read direction

The operation at table offset `0x0C` is invoked using the initially captured backend. Its visible arguments are the backend, current backend position, captured scratch address, unit count `1`, and auxiliary value.

A nonzero result is returned immediately.

On zero, the memory-transfer dependency is invoked with the caller buffer as destination, the displaced scratch address as source, and the computed partial byte count as length.

#### Write direction

The operation at table offset `0x0C` is invoked using the initially captured backend, but the supplied representation does not recover its explicit arguments. This is not evidence that the operation takes no arguments.

A nonzero result is returned immediately.

On zero, the memory-transfer dependency is invoked with the displaced scratch address as destination, the caller buffer as source, and the computed partial byte count as length.

The backend field is then reloaded from the context, and its operation at table offset `0x08` is invoked with that backend, current backend position, captured scratch address, unit count `1`, and auxiliary value.

A nonzero result is returned immediately. Any preceding scratch mutation is not undone.

#### Progress after success

After successful initial partial handling:

- The function establishes a zero result.
- The current backend position increases by one.
- The caller-buffer address increases by the partial byte count.
- The remaining transfer count decreases by the partial byte count shifted right by nine bits.

There is no explicit early exit for a zero partial byte count. The visible branch still reaches its backend operations, memory-transfer call, and progress updates if those operations succeed.

### 4. Complete-unit transfer

After any initial partial handling, the function reads context offset `0x20` again and compares it unsigned against the remaining transfer count.

If the geometry value is less than or equal to the remaining count, it calls F-d7be9cfb4000 again. Only the remaining transfer count is explicit in this call’s supplied argument list. Other required inputs, if any, are **documented_only**.

The 32-bit result becomes a backend unit count.

The function reloads the backend from the context and selects:

- Table offset `0x0C` for read direction.
- Table offset `0x08` for write direction.

The selected operation receives the backend, current backend position, current caller-buffer address, calculated unit count, and auxiliary value.

A nonzero result is returned immediately.

On zero:

- The backend position increases by the calculated unit count.
- The caller-buffer address advances by that count multiplied by a newly read extent from context offset `0x1C`.
- The remaining transfer count decreases by that count multiplied by a newly read geometry value from context offset `0x20`.
- The function establishes a zero result.

These post-call field reads matter: a backend operation may change context fields before the progress calculations. The function does not visibly preserve the earlier geometry for those calculations.

No loop repeats the direct-transfer phase. It is attempted at most once per invocation.

### 5. Final remainder handling

If the remaining transfer count is nonzero, the function selects the backend operation at table offset `0x0C`.

#### Read direction

The operation receives a backend reloaded from the context, the current backend position, captured scratch address, unit count `1`, and auxiliary value.

Its result becomes the function result. If it is nonzero, no final memory-transfer call occurs.

On zero, the memory-transfer dependency is invoked with the caller-buffer address and captured scratch address. A length argument is not explicit in the supplied representation. The intended length may be the remaining count multiplied by 512, but that is not established.

#### Write direction

The read-like backend operation is invoked, but its arguments are not explicitly recovered.

Its result becomes the function result. On nonzero, no final scratch modification or write operation occurs.

On zero:

1. The memory-transfer dependency is invoked with the captured scratch address as destination, the current caller-buffer address as source, and the remaining count shifted left by nine bits as length.
2. The context backend is reloaded.
3. Its operation at table offset `0x08` is invoked with that backend, current backend position, captured scratch address, unit count `1`, and auxiliary value.
4. That operation’s result becomes the function result.

No further progress or context-state update is visible.

### Integer behavior and limits

The transfer count and the partial-count comparison are explicitly unsigned 32-bit operations. Byte-count shifts retain only the representable 32-bit result: for example, a count of `0x00800000` shifted left by nine yields zero under 32-bit bit-vector arithmetic.

Other address, position, extent, and product expressions are represented using 32-bit values, some with signed interpretations. Their overflow behavior is not fully specified by this representation. Mathematical integers, checked arithmetic, saturation, and reliable rejection of overflow must not be assumed.

The established partial-count update discards the low nine bits when converting bytes back into transfer-count units. No validation ensures that a computed partial byte count is a multiple of 512.

A zero geometry value is not rejected before the direct-transfer comparison or the subsequent helper call. Any division-by-zero behavior inside the helper is unknown.

## Side effects

The function contains no explicit stores to context fields and no explicit allocation or release operation.

Its observable effects can include:

- Backend operations on the caller buffer or scratch buffer.
- Memory-transfer dependency calls between those buffers.
- Mutations performed by any dependency.
- A read-modify-write sequence for a partial write.
- Partial completion before a later backend failure.

There is no rollback. A failure after a copy or a successful earlier backend operation does not restore buffers or backend state.

The function does not visibly inspect a result from the memory-transfer dependency. Its reported status therefore does not encode a distinct memory-transfer failure.

Ownership is **documented_only**. The explicit body treats the supplied addresses as usable references and does not visibly acquire or relinquish ownership. Unknown callees must not be assumed to preserve global state, retain references, avoid releasing memory, or leave the context unchanged.

In particular, captured references and reloaded references can differ if a dependency mutates the context. The first partial operation uses the initially captured backend; later operations may use a replacement backend. The scratch address remains the captured value even if the context scratch field subsequently changes.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Disabled context.** With a readable readiness byte equal to zero, expect result `2`. No backend-field read or dependency call belongs to this path.

2. **Missing backend.** With readiness nonzero and the initially read backend address zero, expect result `2`. The write-inhibition byte is not needed.

3. **Inhibited write.** With readiness nonzero, a nonnull initial backend, nonzero direction, and nonzero inhibition byte, expect `21`, with no conversion or transfer. The same inhibition byte does not reject read direction.

4. **Partial read failure.** If initial conversion produces a nonzero high portion and the first read-like operation returns status `7`, expect result `7`. No following partial-copy, direct-transfer, or tail operation occurs.

5. **Bounded initial fragment.** Suppose conversion produces a high portion of `1`, the extent is `2048`, and the requested count is `2`. Without arithmetic overflow, the displacement is `512`, available bytes are `1536`, and requested bytes are `1024`. The selected partial byte count is `1024`. Following successful read-like operation and conventional copy behavior, the copy starts 512 bytes into scratch, advances the caller address by 1024, advances backend position by one, and reduces the count by two.

6. **Partial write failure after copying.** If the preliminary read-like operation succeeds and the subsequent write-like operation returns `9`, expect `9`. The preceding scratch-buffer copy has already been invoked; no rollback is established.

7. **Direct transfer uses post-call geometry.** If a successful direct backend operation changes the extent or geometry fields, subsequent caller-address and remaining-count calculations use the values read after that operation, not necessarily those used before it.

8. **Zero-count aligned request.** If initial conversion produces a zero high portion, the remaining count is zero, and geometry is positive, neither partial, direct, nor final processing establishes the result. A guaranteed zero return is not supported.

9. **Final read copy length.** If a nonzero remainder reaches the final read direction and the backend returns zero, expect a memory-transfer invocation with the visible caller and scratch endpoints. An exact copied byte count cannot be accepted without resolving the missing argument contract.
