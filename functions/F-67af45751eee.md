# F-67af45751eee

## Purpose

Prepare an existing object and an associated resource according to an integer mode, optionally perform activation-related operations, apply a shared four-byte appearance value to two resolved targets, and delegate final processing.

**Status: DOCUMENTED ONLY.** The supplied static evidence establishes call ordering, selected memory accesses, and argument values. It does not establish the contracts of the dependencies, the full object layouts, resource identities, or the fallback operation’s behavior. No runtime behavior has been measured.

The interpretation of the four-byte value as a color, and of the mode-dependent work as activation, is inferred intent rather than an established external API contract.

## Interface

- **Object:** A pointer to an existing mutable object.
  - The supplied representation uses 32-bit object words and pointer-valued fields.
  - The object’s first word supplies a virtual-dispatch table.
  - The function directly accesses fields through byte offset `0xE4`.
  - Additional object-layout requirements belong to the dependencies.
- **Mode:** A 32-bit integer.
  - Zero and nonzero values select different behavior.
  - Negative values select the nonzero behavior.
  - The original integer, rather than a normalized Boolean, is forwarded to F-c452dd64d509.

### Output

There is no explicit return value.

On the path that obtains a non-null context for appearance processing, the function returns after F-c452dd64d509 returns. On the null-context path, it invokes F-a817d8d58c10 and then has no further operation in the supplied body. Whether that call returns normally is unknown.

## Behavior

### Common preparation

For nonzero mode, the function first invokes the input object’s virtual entry at table offset `0x118`, passing the input object as receiver. Zero mode skips this call.

It then calls F-cbb06ef5905e with a pointer to 156 bytes of local scratch storage. The scratch contents are not explicitly initialized before that call, and the supplied body does not otherwise inspect them. The dependency’s purpose and any continuing effects are unknown.

Next, it resolves and stores a resource:

1. Obtain a shared root or lookup receiver from F-938c950e5046.
2. Pass that result and a first opaque global argument to F-9e50c66a96dd.
3. Pass the resulting handle and the exact integer `0x7900` to F-682adfd5a561.
4. Store the 32-bit result in the input object at offset `0xB0`.

The first global argument’s value and meaning are unavailable.

### Conditional context-value copy

After storing the resource, the function:

- Calls F-fdd8589eca2d and discards its returned value.
- Calls F-bfa7e30ab583.
- If the latter returns nonzero, calls F-fdd8589eca2d again and copies the 32-bit value at offset `0x70` of that newly returned context into the input object at offset `0xE4`.
- If the latter returns zero, makes no explicit write to the input object’s `0xE4` field.

These context-provider calls are distinct. The supplied evidence does not guarantee that repeated calls return the same object.

### Mode-dependent resource byte

The function reads the resource reference from the input object’s `0xB0` field and writes its byte at offset `0x98C`:

- Zero mode writes `1`.
- Nonzero mode writes `0`.

This write occurs before the final context check. Consequently, a null final context does not prevent the resource-field assignment or this byte write.

### Final context and appearance processing

The function calls F-fdd8589eca2d again and checks the result.

If this final context is null:

- It calls F-a817d8d58c10.
- It does not perform the subsequent target lookups, appearance calls, optional attachment and virtual call, or F-c452dd64d509 call in the supplied body.

If the final context is non-null:

- Read its byte at offset `0xCD`.
- Resolve a first target by calling F-9e50c66a96dd with the previously obtained root and a second opaque global argument.
- Resolve a second target with the same dependency and root but a third opaque global argument.
- Construct four consecutive bytes:
  - If the context byte is exactly `1`: `00 00 00 FF`.
  - For every other byte value: `DD DD DD FF`.
- Call F-17ece020a072 first for the first target, then for the second target, passing a pointer to the local four-byte value each time.

The byte at `0xCD` is tested for equality with `1`, not for general nonzero truth. For example, `2` and `255` select `DD DD DD FF`.

The target identifiers are opaque. Their values, interpretation, and any relationship to the first resource identifier are unavailable.

The four-byte sequence is consistent with a color-like representation, but channel names and dependency interpretation are not established. Both calls use the same local storage. If the first dependency call modifies that storage, the second call can receive modified contents; no restoration occurs between calls.

### Additional nonzero-mode processing

After both appearance calls, nonzero mode performs these operations in order:

1. Call F-8f9bd59e3ec5 with the resource reference currently in the input object’s `0xB0` field and the input object.
2. Obtain another object from F-629034efc606.
3. Invoke that object’s virtual entry at table offset `0xDC`, passing it as receiver and passing the 32-bit argument bit pattern `0xFFFFFFFF`.

Zero mode skips all three operations.

For either mode, the non-null final-context path then calls F-c452dd64d509 with the input object and the unchanged original mode. No further explicit operation follows.

- A one-byte write at offset `0x98C` in the resource read from the input object.
- Two ordered calls using a shared local four-byte appearance buffer, when the final context is non-null.
- Additional dependency calls and virtual dispatch for nonzero mode.
- Invocation of a fallback dependency when the final context is null.

### Ordering and partial progress

There is no explicit rollback.

If the final context is null, earlier operations have already occurred, including the resource-field assignment and mode-dependent byte write. If the conditional copy was selected and completed, that copy has also occurred.

Dependency calls may mutate the input object, referenced resources, shared state, or lookup results. In particular, later reads of the input object’s `0xB0` field are not proven to equal the value originally stored there if intervening dependencies modify the object.

### Lifetimes

The scratch buffer and four-byte appearance buffer are local storage. They are not returned.

Whether dependencies copy, mutate, or retain pointers to these buffers is unknown. Safe use after this function’s return cannot be assumed from this body.
