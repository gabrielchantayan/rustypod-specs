## Behavior

### 1. Invoke the direct dependency

The first dependency action is a call to F-a449eda002e0 with the address 124 bytes beyond the receiver base.

This call completes before the first indirect method call begins. Its return value, if any, is not used.

The function does not first resolve or cache the receiver’s dispatch table. Consequently, changes made by F-a449eda002e0 to the receiver’s first word or to a relevant table can affect the very first indirect call.

### 2. Make the first indirect call

After F-a449eda002e0 returns, the function resolves the receiver’s callable target through the table entry at byte offset 88.

It invokes that target with three arguments, in this order:

1. The original receiver address.
2. The first-call key.
3. The first-call value.

The two data arguments come from their respective global locations. Their values are not captured before the initial dependency call.

The indirect call’s return value is ignored.

### 3. Capture a shared key

After the first indirect call returns, the function reads the shared-key source and saves its 32-bit contents.

This capture is significant: the saved value supplies the keys for the third, fourth, fifth, and sixth indirect calls. Those calls do not obtain their keys by rereading the shared-key source.

The capture occurs after the first indirect call, so any completed change that call makes to the shared-key source can affect the saved value.

### 4. Make the second indirect call

The function resolves the indirect target again through the receiver’s current table address and the entry at byte offset 88.

The arguments are:

1. The original receiver address.
2. A **fresh read** of the shared-key source.
3. The second-call value.

The second argument is not specified as the saved copy from the preceding step. The supplied body contains a separate read of the same global source.

With stable memory and ordinary execution, the saved value and this fresh value coincide. The contract must nevertheless preserve the distinction between a capture and a later read. The supplied material does not establish synchronization, volatility, or an observation model that would justify stronger claims about concurrent changes.

The call’s return value is ignored.

### 5. Make the remaining four indirect calls

The function makes four more calls, in sequence. Each independently resolves its target through the receiver’s then-current table address at byte offset 88.

| Indirect call | First argument | Second argument | Third argument |
|---|---|---|---|
| Third | Original receiver | Saved shared key | Third-call value |
| Fourth | Original receiver | Saved shared key | Fourth-call value |
| Fifth | Original receiver | Saved shared key | Fifth-call value |
| Sixth | Original receiver | Saved shared key | Sixth-call value |

The third through sixth value arguments are obtained for their respective calls, rather than being captured together before the sequence. Earlier dependencies may therefore affect values supplied to later calls by changing the corresponding global locations.

In contrast, changing the shared-key source after its capture does not replace the saved key used by these four calls.
