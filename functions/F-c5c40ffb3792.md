# F-c5c40ffb3792

## Purpose

F-c5c40ffb3792 prepares mutable point records and contour-start entries from an input descriptor. Its direct work includes capacity management, coordinate conversion, circular neighbor linking, direction classification, and conditional point marking. It then invokes a processing dependency on the nonzero-point path.

“Point,” “contour,” “orientation,” and “angle” describe inferred geometric intent. The established contract is the field access, arithmetic, call, and branching behavior specified below.

The operation is not transactional. Direct changes made before a reported storage-growth error are not rolled back. Dependencies may introduce additional changes whose scope is not established.

## Interface

### Arguments and return value

The function receives:

- An address of a writable context.
- An address of an input descriptor.

The supplied representation has 32-bit pointers, 32-bit context slots, and 40-byte point records. These are representation-specific layouts, not portable structure definitions.

The return value is the current value of a local signed 32-bit status. That status:

1. Is initialized to zero.
2. Is supplied by address to each storage-growth call that occurs.
3. Is checked immediately after the returned pointer is stored.
4. Causes an immediate return when the check finds it nonzero.
5. Is returned again at normal completion, without being reset.

Without a dependency contract excluding retention and later use of the supplied status address, normal completion is not an unconditional guarantee of a zero result. No return value from the final processing dependency is used.

### Preconditions

Ordinary bounded processing requires accessible descriptors, valid writable storage, valid array extents, suitable alignment, nonnegative counts, and address calculations that remain valid.

For a nonempty outline, endpoints must describe consecutive nonempty contours covering the point sequence and ending at its final point. The declared contour count must agree with that grouping.

These conditions are not visibly validated. Malformed counts, inconsistent endpoints, invalid pointers, and harmful aliasing do not receive a defined validation error. Dependency-induced mutations must also leave subsequent accesses valid if bounded completion is expected.

## Behavior

### 1. Capture configuration and clear state

The function initializes its local status to zero. It then captures these context values in order:

1. Horizontal conversion parameter.
2. Vertical conversion parameter.
3. Horizontal translation.
4. Storage-growth handle.
5. Vertical translation.

It directly writes zero to context offsets 28, 40, 48, 60, 76, and 88, in that order.

These clears precede both capacity checks. They are not directly undone on an error path.

### 2. Ensure contour-table capacity

The contour count is read as signed 16 bits and extended to 32 bits. The existing capacity is compared with that value using unsigned 32-bit comparison.

When growth is required, the requested capacity is:

\[
(\operatorname{u32}(\operatorname{s16}(\text{contour count}))+3)
\mathbin{\&}\texttt{0xfffffffc}
\]

Addition uses unsigned 32-bit arithmetic. For nonnegative counts, the request rounds the count upward to a multiple of four.

F-6dd003795db7 receives the captured handle, element size 4, existing capacity, requested capacity, existing table pointer, and the address of the local status.

The returned pointer-like value is stored at context offset 44 before status is checked. If status is nonzero, the function returns it immediately and does not perform its subsequent contour-capacity assignment. If status is zero, the function directly assigns the requested capacity at offset 36.

Those statements describe this function’s actions. They do not establish that the dependency left the capacity or other memory unchanged on failure.

### 3. Ensure point-record capacity

The point count is read as signed 16 bits. Growth is required when the existing unsigned 32-bit capacity is less than the sign-extended point count plus two, using unsigned 32-bit arithmetic.

The requested capacity is separately calculated as:

\[
(\operatorname{u32}(\operatorname{s16}(\text{point count}))+11)
\mathbin{\&}\texttt{0xfffffff8}
\]

For nonnegative counts, this rounds **point count plus four** upward to a multiple of eight. The growth threshold and requested-capacity formula therefore use different margins.

F-6dd003795db7 receives the captured handle, element size 40, existing capacity, requested capacity, existing point pointer, and the same status address used for contour growth.

The returned pointer is stored at context offset 32 before status is checked. A nonzero status returns immediately; this function does not then assign the requested point capacity. A zero status leads to that assignment at offset 24.

At either growth-error return, this function has not yet directly initialized point records. Initialization, capacity mutation, release, or other changes performed by the growth dependency remain unspecified. Earlier direct changes are not rolled back.

### 4. Set counts and orientation-related bytes

After capacity processing succeeds, the function rereads the descriptor counts and stores their sign-extended values at context offsets 28 and 40.

It writes byte value 2 at offset 72 and byte value 255 at offset 100, then calls F-fad1b6d0ba63 with the descriptor.

Only a result exactly equal to 1 causes the subsequent direct writes of byte value 254 at offset 72 and byte value 1 at offset 100. Other results cause no replacement writes there; they do not prove that the dependency preserved those bytes.

The captured configuration is then restored in this order:

1. Horizontal conversion parameter.
2. Vertical conversion parameter.
3. Horizontal translation.
4. Vertical translation.

No equivalent restoration of other fields is established.

### 5. Populate point records

After orientation processing and restoration, the point-storage pointer is read from the context. The active point count is then tested.

If that count is zero, all remaining record, link, contour-table, direction, and final-processing work is skipped. The current local status is returned.

On the nonzero path, the coordinate and tag pointers are loaded from the descriptor. A record-range limit is formed from the context’s active point count and the 40-byte stride. Subsequent passes use this retained record range; they do not continually reload the count.

For an ordinary positive count, population proceeds in ascending record order. The dependency-sensitive order within each record is:

1. Read the full horizontal input and store its low 16 bits at record offset 12.
2. Read the full vertical input and store its low 16 bits at offset 14.
3. **Reread the full horizontal input** for F-74efb2674226, passing the captured horizontal conversion parameter.
4. Add the captured horizontal translation to the result.
5. Store the translated result at offsets 16 and 4, in that order.
6. **Read the full vertical input after the horizontal conversion call** for F-74efb2674226, passing the captured vertical conversion parameter.
7. Add the captured vertical translation.
8. Store that result at offsets 20 and 8, in that order.
9. Inspect the tag’s low two bits and replace the full 16-bit classification field.

Thus the narrowed coordinates are written before either conversion call, but the full coordinates supplied to conversion are not both captured beforehand. A horizontal conversion dependency that mutates the vertical input can affect the later vertical conversion without changing the vertical value already narrowed into the record.

The tag mapping is:

| Low two tag bits | Classification |
|---:|---:|
| 0 | 1 |
| 1 | 0 |
| 2 | 2 |
| 3 | 0 |

Tag inspection occurs after both conversion calls. Higher tag bits do not affect the mapping. Translation uses 32-bit arithmetic; no explicit saturation or overflow error is visible.

### 6. Construct circular links

A separate ascending-record pass builds links. Before that pass, the first endpoint is read as a signed 16-bit index. Its record address initially supplies both the contour endpoint and the previous record for the first point.

For each record, the previous pointer is written before the next pointer.

- When the current record address is below the endpoint address, its next pointer selects the following record.
- Otherwise, its next pointer selects the current contour’s first record.
- After closing a contour, if another record remains, that record becomes the next contour start and another endpoint is read.

With valid endpoints, each contour becomes a circular doubly linked list. A one-point contour links to itself in both directions.

The branch uses an address comparison, not a validated endpoint-equality check. Endpoint reads are driven by contour closures encountered during the record pass, not bounded by the declared contour count.

### 7. Populate the contour-start table

The contour-table pointer and active contour count are read from the context at this later stage. The endpoint-array pointer is also loaded for this pass.

Table entries are written in ascending order. The initial start index is zero. Each entry receives the point-storage base plus 40 times the current start index.

After each entry, an endpoint is read and incremented; the result is narrowed to 16 bits and sign-extended for the next start index. An endpoint is read even for the final table entry.

Consequently, endpoint 32767 yields next-start index −32768, not 32768.

This pass uses the context’s contour count, whereas linking uses the retained record range and encountered endpoints. Their consistency is a caller obligation.

### 8. Classify directions and conditionally mark records

Each record is processed in ascending order. The exact call-sensitive sequence is:

1. Read the current and previous records’ signed 16-bit original-coordinate fields and compute the incoming vector: current minus previous.
2. Call F-72e4f251d1ee with that vector.
3. Store the returned low byte at record offset 2.
4. **After that call**, read the next-link and relevant coordinate fields to compute the outgoing vector: next minus current.
5. Call F-72e4f251d1ee with the outgoing vector.
6. Store the low byte of its result at offset 3.
7. **After the second call**, read the classification and incoming-direction byte for branch decisions.

Each vector component is a 32-bit difference between sign-extended 16-bit coordinates, with range −65535 through 65535.

The incoming vector is retained across the calls. The outgoing vector is not computed until after the first direction call. The compared incoming encoding is read from record memory after the second call; it is not necessarily the byte originally returned by the first call.

The outgoing result is retained as a full 32-bit value. Incoming-byte comparisons interpret that byte as signed.

A marker request occurs when:

- The classification read after the second call has nonzero low two bits; or
- The full outgoing result equals the signed incoming byte, except for the equal-to-4 case below; or
- Those direction values are unequal and the signed incoming byte equals the negation of the full outgoing result.

When the classification’s low two bits are zero and both compared directions equal 4:

1. F-269e394bb002 receives the retained incoming vector.
2. F-269e394bb002 receives the retained outgoing vector.
3. The incoming result is subtracted from the outgoing result.
4. Signed remainder modulo 512 is taken.
5. A negative remainder is increased by 512.
6. A result greater than 256 is decreased by 512.

The marker is requested only for normalized differences −1, 0, or 1.

When marking occurs, this function reads the then-current 16-bit classification and writes it back ORed with 256. In the special case, that read occurs after both F-269e394bb002 calls. It need not match the classification previously used to select the branch.

No direct clearing of marker 256 occurs during this pass.

### 9. Invoke final processing and return status

After direction processing, F-4e557a99ae0a is called once with the context. Its result is ignored.

The function returns the current local status. A zero result is conditional on that status remaining zero after the successful growth checks, including through any later access using a retained status address.

## Side effects

No direct release operation is visible. Allocation ownership, release of replaced storage, content preservation, initialization, and failure-pointer semantics belong to the unknown contract of F-6dd003795db7.

- Conversion calls precede later coordinate and tag reads.
- The first direction call precedes outgoing-vector reads.
- The second direction call precedes classification and incoming-byte reads.

The final dependency may modify the prepared context and records. Intermediate writes are therefore not unconditional post-return state guarantees.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless a mutation is explicitly described, they assume valid storage and dependencies that leave relevant inputs and fields unchanged.

1. **Capacity requests.** Contour count 5 and point count 9, both with capacity zero, produce requests for eight four-byte entries followed by sixteen 40-byte records.

2. **Threshold versus request.** Point count 6 with point capacity 8 avoids growth. Capacity 7 triggers growth requesting **16 records**, because the request uses count plus eleven with the low three bits cleared.

3. **Empty storage provisioning.** Point count zero with point capacity zero still triggers a request for eight records. With both counts zero and point capacity at least two, orientation processing still occurs, but record processing and final processing are skipped if the active count remains zero.

4. **First growth error.** If contour growth returns a replacement pointer and sets status to 7, this function stores that pointer, returns 7, and makes no point-growth call or subsequent contour-capacity assignment. Dependency-induced capacity or record changes remain unspecified.

5. **Second growth error.** If contour growth succeeds and point growth reports an error, this function does not undo its earlier contour-capacity assignment. It stores the returned point pointer but does not perform the subsequent point-capacity assignment.

6. **Conversion mutation.** Suppose the vertical input is initially 20 and horizontal conversion changes it to 30 without changing the record. The narrowed vertical field was already written from 20; vertical conversion receives 30.

7. **Direction mutation.** If the first direction call changes the next point’s original-coordinate fields, the outgoing vector uses those changed fields. If the second call changes the stored incoming byte or classification, branch decisions use those changed values.

8. **One-point contour.** Endpoint zero gives self-links. Both vectors are zero if dependencies preserve the relevant coordinates and links. For classification zero, marking still depends on direction results.

9. **Two contours.** Five points with endpoints 1 and 4 produce contour starts at records 0 and 2, with circular links over records 0–1 and 2–4.

10. **Special-angle boundary.** With classification low bits zero and compared directions both 4, normalized differences −1, 0, and 1 request marking; −2, 2, and 256 do not.

11. **Retained status address.** If successful growth leaves status zero but a later dependency validly changes it to 9 through a retained address, normal completion returns 9, despite ignoring that later dependency’s own return value.
