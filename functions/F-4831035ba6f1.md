# F-4831035ba6f1

## Purpose

F-4831035ba6f1 updates a destination descriptor from a distinct source descriptor, choosing among replacement storage, reuse with a longer logical range, and reuse with an equal or shorter logical range. It returns the destination descriptor’s address.

The visible behavior is consistent with assignment of a sequence whose elements occupy 16 bytes. That interpretation is inferred from the count-dependent address calculations and dependency calls; the element type and the dependencies’ element-level semantics are not established.

The distinction between logical extent and storage extent matters:

- Replacement storage establishes both a logical end and a storage end.
- Reuse while increasing the logical extent updates the logical end and leaves the storage-end field untouched by this function.
- Reuse without increasing the logical extent ultimately writes the same computed address to both end fields.

The last behavior is part of the visible contract, even if a conventional container implementation might preserve a larger storage extent.

## Interface

### Arguments and return value

The function receives four arguments:

1. **Destination descriptor address.** Used for identity comparison, dependency calls, and descriptor reads and writes.
2. **Source descriptor address.** Used for identity comparison, dependency calls, and reads.
3. **First additional unsigned word.**
4. **Second additional unsigned word.**

The return value is the original destination descriptor address on every visible normal-return path. No separate status or error value is returned.

The two additional unsigned words do not affect any visible dependency argument, descriptor write, branch outcome, or return value. For distinct descriptors, they are initially copied into temporary storage. On the replacement path, both temporary values are overwritten before use; on the other paths, neither is subsequently used.

### Descriptor layout

The supplied representation exposes three consecutive 32-bit words:

| Byte offset | Observed use | Inferred meaning |
|---|---|---|
| 0 | Base address used in range arguments and address calculations | Beginning of storage |
| 4 | End address passed to range-oriented dependencies and explicitly updated | Logical end |
| 8 | Explicitly updated on some paths | Storage end or capacity boundary |

The source descriptor’s offset-8 word is not directly accessed by this function. Dependencies may access it.

These interpretations do not establish a complete descriptor type or its invariants. The source and destination count and capacity queries are delegated rather than calculated visibly from these fields.

### Widths and arithmetic

The representation uses 32-bit integer words and address-bearing fields. Element offsets are calculated with a stride of 16 bytes. No wider arithmetic is visible in the supplied material.

The replacement-capacity policy uses unsigned 32-bit arithmetic. For a destination count \(n\), its candidate is

\[
\max\left(
(n+32)\bmod 2^{32},
\left(n+\lfloor n/2\rfloor+\lfloor n/8\rfloor\right)\bmod 2^{32}
\right),
\]

where the maximum is selected by unsigned comparison. Intermediate unsigned additions also wrap at 32 bits.

The requested byte count is the chosen capacity shifted left by four bits, retaining only the low 32 bits. It is not an overflow-checked multiplication by 16.

Other address calculations involve count results represented as signed words in portions of the supplied material. Their behavior for values causing signed overflow or invalid addresses is not established. Valid ordinary use therefore requires representable, accessible ranges and suitable count bounds.

### Preconditions and ownership

Except for the identity-only path, callers must provide descriptors and ranges suitable for every dependency invoked on the selected path. No explicit null, range, alignment, overlap, or allocation-success validation appears here.

Ownership is not fully established:

- A dependency returns a word used as replacement storage.
- Another dependency receives the former destination base and a capacity-like value.
- A separate dependency receives destination ranges before that old-storage call.

This suggests a storage lifecycle, but the function bodies and ownership contracts of those dependencies are unavailable. Their names here must not be taken as proof of allocation, destruction, or release semantics.

## Behavior

The following describes normal continuation through the visible calls. A dependency that fails, does not return, or changes relevant state can alter what is subsequently observed.

### 1. Identical descriptor addresses

The first decision compares the source and destination descriptor addresses.

If they are equal:

- No descriptor field is visibly read or written.
- No dependency is called.
- Both additional unsigned arguments are irrelevant.
- The destination address is returned.

This is descriptor identity, not backing-storage identity. Distinct descriptors referring to the same storage do not take this shortcut.

### 2. Initial branch selection for distinct descriptors

For distinct descriptor addresses, the function:

1. Calls F-5dbde81efa3b with the source descriptor.
2. Calls F-8abe585ac5ab with the destination descriptor.
3. Compares the two returned words as unsigned values.

The returns are used as a source count and destination capacity, respectively. Those meanings are inferred; the comparison itself is established.

If the destination query result is less than the source query result, execution takes the replacement-storage path. Otherwise it takes a storage-reuse path.

The function does not preserve a single snapshot of either descriptor. It calls queries repeatedly and rereads descriptor fields after intervening dependency calls.

### 3. Replacement-storage path

This path is selected when the initial destination capacity-like result is smaller than the initial source count-like result.

#### Capacity selection

The function obtains:

1. A fresh source count from F-5dbde81efa3b.
2. A fresh destination count from F-5dbde81efa3b.

Using the destination count, it calculates the two growth candidates described in the interface section. It then selects the larger of:

- That growth candidate.
- The fresh source count.

All these selections use unsigned comparisons. With nonoverflowing values, this corresponds to choosing enough capacity for the source while allowing growth of at least 32 elements or approximately 62.5% of the destination count.

The comparison that selected this path used an earlier source query result. If query results change, the capacity calculation uses the later value, not the initial one.

#### Dependency calls and descriptor updates

The visible order is:

1. Call F-871e64ddc6de with the selected capacity shifted left by four bits and a second argument of zero.
2. Call F-64a1fdb9e73f with the source base, source logical end, returned storage word, and destination descriptor.
3. Call F-4d471b016ddf with the destination descriptor and its then-current base and logical end.
4. Read the destination base.
5. Call F-8abe585ac5ab with the destination descriptor.
6. Call F-ff1bdc376dcd with the base read in step 4, the result of step 5, and zero.
7. Write the returned replacement-storage word into destination offset 0.
8. Call F-5dbde81efa3b with the source descriptor again.
9. Write destination offset 4 as the then-current destination base plus 16 times that count.
10. Compute the then-current destination base plus 16 times the selected capacity.
11. Write that address into destination offset 8.
12. Return the destination descriptor address.

There is no explicit check of the replacement-storage result before it is passed onward.

The destination base supplied to F-ff1bdc376dcd is captured before the immediately preceding capacity query. Conversely, the source count used for the final logical end is queried after the old-storage-related call and after the explicit base replacement. These differences are observable if dependencies mutate state.

### 4. Storage reuse with an increasing logical extent

When replacement was not selected, the function queries the destination count and then the source count through F-5dbde81efa3b.

If the destination result is smaller than the source result, it takes this path:

1. Query the destination count again and retain that result as the split position.
2. Call F-7f7918fbdee2 with:
   - The current source base.
   - That base plus 16 times the split count.
   - The current destination base.
3. Query the source count again.
4. Write destination offset 4 as the current destination base plus 16 times that newly returned count.
5. Call F-64a1fdb9e73f with:
   - The current source base plus 16 times the retained split count.
   - The current source logical end.
   - The current destination base plus 16 times the retained split count.
   - The destination descriptor.
6. Return immediately.

There is no explicit write to destination offset 0 or offset 8 on this path.

The logical end is updated **before** the final dependency call. Thus that dependency receives the destination descriptor after its explicit logical-end update. No rollback is visible if that call fails or does not return.

The dependency result from F-7f7918fbdee2 is ignored on this path.

### 5. Storage reuse without an increasing logical extent

If the reuse-path destination count is not smaller than the source count, the function:

1. Calls F-7f7918fbdee2 with the current source base, source logical end, and destination base.
2. Calls F-4d471b016ddf with:
   - The destination descriptor.
   - The word returned by F-7f7918fbdee2.
   - The current destination logical end.
3. Queries the source count through F-5dbde81efa3b.
4. Computes the current destination base plus 16 times that count.
5. Writes this computed address to destination offset 4.
6. Writes the same computed address to destination offset 8.
7. Returns the destination descriptor address.

The return from F-7f7918fbdee2 is passed directly to F-4d471b016ddf. This function does not independently establish that it equals the expected copied-range end.

Even when source and destination counts are equal, this path writes the computed logical end to the storage-end field.

## Side effects

### Explicit descriptor writes

| Path | Offset 0 | Offset 4 | Offset 8 |
|---|---|---|---|
| Identical descriptors | Unchanged | Unchanged | Unchanged |
| Replacement storage | Replacement result | Recomputed logical end | Recomputed selected-capacity end |
| Reuse, increasing extent | No explicit write | Recomputed before final dependency call | No explicit write |
| Reuse, nonincreasing extent | No explicit write | Recomputed logical end | Same address as offset 4 |

“No explicit write” does not mean a dependency cannot modify that field.

The function performs no direct source-descriptor writes. However, it passes the source descriptor to query dependencies and passes source addresses to range-oriented dependencies. Their mutation behavior is unknown.

The range-oriented dependency calls may read or write element storage. The apparent separation between updating an existing prefix and processing a new suffix is inferred from the ranges and call placement. Exact element reads, writes, construction, destruction, and overlap handling are not established.

No global state is directly referenced in the supplied function body. Dependencies may access globals or perform other externally observable operations; preservation cannot be assumed.

### Errors and partial updates

There is no visible local error handler, explicit failure return, overflow check, or rollback path.

In particular:

- Replacement storage is used without a visible success check.
- The replacement path processes source data before invoking the dependencies associated with the old destination range and storage.
- The increasing-extent reuse path updates the logical end before its final range operation.
- The nonincreasing-extent path invokes both range dependencies before its explicit end-field writes.

The state left by dependency failure is documented_only. A transactional or strong exception guarantee is not established.

For calls with multiple descriptor-derived arguments, all argument values must be obtained for that call, but their mutual read order is not established by the supplied representation. The ordered stages above do not imply a particular order among reads within one argument list.

## Acceptance examples

These are conditional static examples, not executed tests. Except where stated otherwise, assume stable query results, nonmutating queries, normally returning dependencies, valid nonoverlapping storage, and representable address arithmetic.

### Identical descriptors

Given equal descriptor addresses, the function returns that address without invoking any dependency or accessing descriptor fields. This conclusion does not require a valid element range because none is accessed by the visible body on this path.

### Replacement with minimum growth

Given destination count 8, destination capacity 8, and source count 12:

- Replacement is selected because 8 is less than 12.
- The growth candidates are 40 and 13.
- Selected capacity is 40.
- The requested byte count is 640.
- After normal completion without relevant dependency mutations, destination offset 4 is replacement base plus 192, and offset 8 is replacement base plus 640.

### Source size dominates growth

Given destination count 8, destination capacity 8, and source count 100, selected capacity is 100 rather than 40. The requested byte count is 1600.

### Reuse with growth

Given destination count 3, capacity 10, and source count 6:

- The existing prefix operation receives a source range of 48 bytes.
- The explicit logical-end update sets offset 4 to destination base plus 96.
- The final range operation starts at byte offset 48 in both source and destination.
- Offset 8 receives no explicit write.

The final range operation observes the already-updated logical end.

### Reuse with shrinkage

Given destination count 6, capacity 10, and source count 2:

- F-7f7918fbdee2 receives the source’s full logical range.
- Its result becomes the second argument to F-4d471b016ddf.
- After those calls, offsets 4 and 8 are both explicitly set to destination base plus 32.

The prior capacity of 10 is not preserved in offset 8 by the visible writes.

### Empty source

Given a distinct source with count zero and a destination for which replacement is not selected, the nonincreasing-extent path still invokes both range dependencies. After normal completion with stable state, both end fields equal the destination base. There is no empty-range shortcut.

### Wrapped byte request

If the replacement calculation selects capacity \(2^{28}\), the 32-bit left shift by four produces a byte request of zero. The function has no explicit overflow rejection. Whether the dependencies permit or fail on this situation is documented_only.
