# F-001430fff24e

## Purpose

F-001430fff24e partially resets a globally addressed memory object and conditionally installs one of two fixed numeric profiles.

The reset occurs for every input, including inputs that return the all-ones result. Inputs 1 and 2 install profiles and return zero. Inputs 0 and 3 return the 32-bit all-ones value after the reset. Every other input returns zero after the reset without installing a profile.

These are established operations. The semantic meanings of the object, profiles, and return values are unknown. In particular, zero cannot be treated as proof that a profile was installed, and the all-ones result does not imply that memory was left unchanged.

## Interface

### Input

One 32-bit integer selector.

Only equality with 0, 1, 2, and 3 affects control flow. All other 32-bit input patterns follow the same reset-only, zero-return path. This includes negative values under a signed interpretation.

There is no explicit object argument. The function obtains its destination through global state.

### Output

One 32-bit result:

| Selector | Result bit pattern | Profile installed |
|---|---|---|
| 0 | `0xFFFFFFFF` | None |
| 1 | `0x00000000` | Profile 1 |
| 2 | `0x00000000` | Profile 2 |
| 3 | `0xFFFFFFFF` | None |
| Any other value | `0x00000000` | None |

The all-ones result is −1 under a signed 32-bit interpretation and 4,294,967,295 under an unsigned interpretation. The evidence establishes the bit pattern, not the caller’s interpretation.

### Global inputs and destination layout

The function references three global storage locations:

- **Object-base global:** provides the address used for destination writes.
- **Profile-1 word global:** supplies a 32-bit value written when the selector is 1.
- **Profile-2 word global:** supplies a 32-bit value written when the selector is 2.

These are descriptive labels, not source identifiers. The profile words may represent addresses, handles, flags, or ordinary numeric values; their meanings are not established.

All object offsets below are byte offsets. Each listed destination receives a 32-bit write. The highest destination starts at offset `0xEC` and occupies bytes through `0xEF`.

For ordinary successful execution, the destinations used by the selected path must be valid writable storage. A conventional contiguous object covering every listed destination would need to extend through byte `0xEF`, or 240 bytes from its base. That is a sufficient layout model, not evidence that the function validates an allocation of that size.

## Behavior

### 1. Acquire the base and perform the unconditional reset

The function first reads the object-base global and retains that address for subsequent operations.

The first reset write uses a separate evaluation of the object-base global. It writes zero at offset `0x44` relative to that evaluation. The remaining reset writes use the initially retained base.

Under stable, non-aliasing global state, these addresses refer to the same object. The separate evaluations matter if external mutation or unusual aliasing is permitted; a single atomic snapshot of the global is not established.

This is a partial reset, not an object-wide clear. There is no established reset of the gaps between these ranges or of the profile fields described below.

No selector-dependent early return precedes these writes.

### 2. Select the return or profile-installation path

After completing the reset:

- Selector 0 returns `0xFFFFFFFF`.
- Selector 1 installs profile 1.
- Selector 2 installs profile 2.
- Selector 3 returns `0xFFFFFFFF`.
- Every other selector returns zero.

The reset-only paths do not explicitly read either profile-word global and do not explicitly write the profile destinations.

Consequently, a reset-only call can leave a previously installed profile in place while clearing the reset fields. The operation does not restore a neutral profile on those paths.

### 3. Install profile 1 or profile 2

For selector 1 or 2, the function first reads the corresponding profile-word global and writes its 32-bit value at offset `0x70` relative to the retained object base.

That global value is read after the unconditional reset, not captured at function entry. If preceding writes alias the profile-word global, the value copied is the value available at the later read.

The function then writes the fixed values in this table, from top to bottom:

| `0x94` | 1 | 1 |
| `0x98` | 7 | 7 |
| `0x9C` | 20 | 21 |
| `0xA0` | 40 | 42 |
| `0xA4` | 63 | 68 |
| `0xA8` | 82 | 87 |
| `0xAC` | 90 | 95 |

Every entry is a complete 32-bit value, not a byte-sized write. Values are shown in decimal; destination offsets are hexadecimal.

The write at `0xEC` is the final explicit memory write. Afterward, the function returns zero.

Each profile-installation path therefore performs 36 explicit destination writes: 21 reset writes, one global-derived profile-word write, and 14 fixed-value writes. Each reset-only path performs 21.

### Widths and arithmetic

Destination address calculations add fixed byte offsets to an address represented in the supplied evidence as a 32-bit quantity. No index, length, multiplication, or selector-derived offset is used.

All fixed profile values fit within eight bits, but their storage width remains 32 bits. The contract does not narrow those destinations to bytes or infer packed arrays.

There is no explicit overflow check on address addition. Portable behavior for an invalid base, address wraparound, or an unsupported alignment is not established.

## Side effects

The function directly mutates global-addressed memory before deciding its return value. It performs no explicit read of the prior contents of the destination fields.

Under ordinary, stable, non-overlapping storage:

- Every call clears the 21 reset fields.
- Selectors 1 and 2 additionally replace all listed profile fields.
- Other selectors leave the profile fields unchanged.
- Bytes outside the explicit write destinations remain unchanged by this function.

Those preservation claims are conditional on the writes targeting ordinary memory without aliasing or device-specific side effects. They are not guarantees about concurrent writers or memory-mapped hardware.

No allocation, deallocation, reference-count change, or ownership transfer is visible. In particular, writing the word at `0x70` does not establish ownership of any object it might denote. Replacing an existing value there does not visibly release anything previously referenced.

The function contains no explicit validation, rollback, diagnostic output, or error-recovery path. A memory-access failure may occur after some writes have completed; no transactional behavior is established.

There are no visible synchronization operations. The listed read/write sequence describes the supplied static evidence, not a cross-thread atomicity or memory-ordering guarantee.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence. They have not been executed.

### Selector 1 installs its complete profile

Given stable, valid, non-overlapping destination storage and a profile-1 word global containing `0x12345678`, a call with selector 1 must:

- Clear all 21 reset fields.
- Write `0x12345678` at `0x70`.
- Write every profile-1 table entry at its specified offset.
- Return `0x00000000`.

Observing the reset writes before the profile writes is consistent with the established sequence. Installing the profile before the reset would not satisfy that sequence.

### Selector 2 replaces profile 1

Given an object previously configured with profile 1, a call with selector 2 must replace every listed profile destination with profile-2 values and copy the currently read profile-2 word to `0x70`.

For example, `0x9C` becomes 21, `0xD4` becomes 2, and `0xEC` becomes 134. The reset fields become zero, and the return value is zero. No prior profile field value is consulted to compute the replacement.

### Selector 0 changes memory despite its result

Given nonzero reset fields and preexisting profile values, selector 0 must clear the reset fields and return `0xFFFFFFFF`.

Under non-aliasing storage, the fields at `0x70`, `0x94` through `0xAC`, and `0xD4` through `0xEC` retain their prior values. An implementation that returns immediately without the reset would not satisfy the contract.

### Selector 3 follows the same reset-only outcome

Under the same storage assumptions, selector 3 must perform the same reset writes and return the same bit pattern as selector 0. It must not install either profile.

### An unrecognized selector returns zero without installing a profile

For selector 4, or the input bit pattern `0xFFFFFFFF`, the function must clear the reset fields and return zero. It must not explicitly copy either profile word or replace the fixed profile fields.

A caller that interprets this zero return as “profile installed” would be relying on behavior not supplied by this function.

### Later calls preserve stale profile state on reset-only paths

Given a successful selector-2 call followed by selector 0, the second call must return `0xFFFFFFFF` while leaving the profile-2 fields intact, subject to the stated non-aliasing assumptions. The second call is not an undo operation.

## Uncertainties

The following are **documented_only**:

- The business meaning of the two profiles and individual fields.
- Whether the all-ones result means rejection, unsupported mode, or another condition.
- Why unrecognized selectors return zero.
- Whether the word stored at `0x70` is a pointer or non-address data.
- The globals’ concrete values, initialization procedure, and lifetime.
- The complete object layout, including untouched regions.
- Target byte order and alignment requirements.
- Whether any destination denotes ordinary memory, shared memory, or hardware registers.
- Permitted aliasing among destination storage and global storage.
- Behavior under concurrent modification, invalid addresses, or address wraparound.
- Caller expectations concerning ownership, persistence, and error handling.

It is reasonable to infer that the function selects between two configuration profiles while clearing related state. That is inferred intent, not an established interpretation of the numeric fields.
