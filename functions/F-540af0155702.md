# F-540af0155702

## Purpose

F-540af0155702 searches a directory for a requested 32-bit tag. For the first matching entry, it publishes a count, obtains storage, and writes four-byte values derived from resource records. Each value is the record reader’s low 24 bits plus the caller’s base value, with a 32-bit result.

Resource-directory processing is inferred intent. The established behavior includes several constraints that must not be replaced with conventional API assumptions:

- An unexplained processor-condition state can cause an early return.
- Positioning arguments incorporate the address of a mutable local argument-copy area.
- The count-output pointer is captured before that area is exposed to the initial positioning dependency.
- Successful array publication instead uses the array-output pointer currently stored in that area.
- Count publication precedes allocation and record processing.
- Several advancement results are overwritten or not checked.
- Failure results do not have a uniform 64-bit encoding.

This contract describes static evidence. Dependency semantics, resource format, and ownership are unresolved where identified below.

## Interface

The supplied representation exposes four arguments and a 64-bit return value. Addresses and stored array elements are 32 bits wide.

| Input | Width | Established use |
|---|---|---|
| Requested tag | Unsigned 32 bits | Passed to preparation and compared against complete directory tags. |
| Initial array-output address | 32-bit address of a four-byte writable slot | Copied into a mutable local area. Successful publication dereferences the then-current copy, not necessarily this original address. |
| Initial count-output address | 32-bit address of a signed 32-bit slot | Copied into the local area, then captured separately before the initial positioning call. Count writes and subsequent count reads use the captured pointer. |
| Base value | Signed 32 bits | Its bit pattern participates in modulo-\(2^{32}\) addition. A separate copy is placed in the mutable local area. |

### Mutable argument-copy area

Before preparation, the function establishes a local area with this observed layout:

| Byte offset | Initial contents |
|---|---|
| 0 | Initial array-output address |
| 4 | Initial count-output address |
| 8 | Base-value copy |

Each field occupies four bytes. The address of the first field is passed to F-e40a3ceddab2. No dependency contract establishes that this area is read-only or preserved.

After acquisition and before the initial F-e40a3ceddab2 call, the function captures the pointer currently in the count-address field. All subsequent explicit count accesses use that captured pointer. A later change to the local count-address field alone does not retarget those accesses.

In contrast, successful array publication loads the array-output pointer from the local area at publication time. If a dependency has replaced that field with another valid writable address, the explicit publication write targets the replacement.

The record-value calculation uses the input base value, rather than visibly reloading the base-copy field. Changing that field alone is therefore not established to change the arithmetic base.

### Preconditions and outputs

Every address must be accessible for the particular read or write that occurs. There is no explicit pointer validation. In particular:

- The captured count pointer must remain valid for a four-byte write and repeated signed four-byte reads.
- The array-output pointer present at successful completion must designate a writable four-byte slot.
- The allocated address must support every array write actually attempted.

The function does not explicitly read an existing array-output value. It writes the count before its first explicit count read on a matching-entry path.

For an ordinary two-output result, the effective count and publication destinations must be distinct and must not interfere with allocated storage or dependency-visible mutable state. This is a usage condition, not an enforced restriction.

### Return value

The return width is 64 bits:

- Successful publication returns zero.
- Exhausting the directory without a match returns one.
- Several failures return a 32-bit status zero-extended to 64 bits.
- Positioning failures return the dependency’s complete 64-bit result.
- A directory-count read failure combines status and reader-result bits.
- The unexplained early-return branch returns only the acquisition result’s lower 32 bits, zero-extended.

A universal interpretation as a conventional success/error code is not established.

## Behavior

### Preparation, acquisition, and pointer capture

The function initializes the local argument-copy area, then invokes:

1. F-72d6ac25a5a5 with a value loaded from shared state and the requested tag.
2. F-58e7ae060acf with another load from that shared location.
3. F-413e9e177c2e with the integer one.

The first two return values are not explicitly tested. The shared-state value is loaded separately for those calls; the first call must not be assumed to preserve it.

Acquisition supplies a 64-bit result. Its lower 32 bits are subsequently used as an address, and its upper 32 bits are used as the context for later operations.

After acquisition, the function captures the local count-address field. An unexplained zero-condition state then controls an early return. When that condition is true, the function returns the acquisition result’s lower half, zero-extended. No subsequent explicit dereference through that acquisition address or caller-output write occurs.

The supplied evidence does not establish that this condition means “acquisition returned zero” or “acquisition failed.”

On the continuing path, the function reads four bytes through the acquisition result’s lower-half address. This value is retained for allocation and failure-cleanup calls.

### Initial positioning and directory count

F-e40a3ceddab2 receives the context and the address of the mutable argument-copy area.

This exposes the local output-address copies and base copy to a dependency with unknown behavior. Subsequent behavior must not assume those copies remain unchanged. The captured count pointer is already separate; the eventual publication pointer is not yet captured.

Only the lower 32 bits of the positioning result are tested. A nonzero lower half causes the entire 64-bit result to be returned. A zero lower half permits continuation even if the upper half is nonzero.

Next, F-8f49ed59b67e receives the context and the address of a local 32-bit status slot. Its returned value supplies the directory count field.

If the status is nonzero afterward, the function returns a 64-bit value with:

- Bits 0–31 equal to the status.
- Bits 32–47 equal to the reader result’s low 16 bits.
- Bits 48–63 equal to zero.

Otherwise, the number of directory entries to examine is the reader result’s low 16 bits plus one. The range is therefore 1 through 65,536, inclusive.

### Directory traversal

For each entry, dependencies are called in this order:

1. F-10d2ce969adf supplies a complete 32-bit tag.
2. F-8f49ed59b67e supplies a value whose low 16 bits determine the record count.
3. F-8f49ed59b67e supplies a value whose low 16 bits contribute to positioning.

Each receives the context and the status-slot address. After each call, a nonzero status causes an immediate zero-extended 32-bit status return. Later fields of that entry are not read after such a failure.

After all three reads succeed, the function reads a signed 32-bit verbosity value at byte offset 0x34 in shared diagnostic state. If it exceeds one, F-4457a9a44a68 is invoked with a diagnostic format and four tag-byte arguments, ordered from most significant byte to least significant byte.

The full 32-bit tag comparison occurs after this optional diagnostic call. The other two entry values contribute only their low 16 bits to count and positioning calculations.

A nonmatching entry advances the directory loop. If every examined entry is nonmatching, the function returns one without explicitly writing the captured count destination or an array-publication destination.

The first matching entry ends the search. Any subsequent failure returns from that entry’s processing; later duplicate tags are not considered.

### Matching-entry setup

The function writes the matching count field’s low 16 bits plus one through the captured count pointer. This publishes an initial signed count in the range 1 through 65,536 before positioning, allocation, or record extraction.

F-e40a3ceddab2 is then called with:

- The existing context.
- The local argument-copy area’s address plus the entry positioning field’s low 16 bits.

The addition is unscaled and uses a 32-bit address-sized result. It is not visibly relative to the caller’s numeric base or the eventual allocation. The unusual address-based construction is established behavior; its intended meaning is unresolved.

A nonzero lower half of this positioning result causes the complete 64-bit result to be returned. The count has already been explicitly written. No array address has yet been explicitly published.

On positioning success, F-6dd003795db7 receives these six arguments, in order:

1. The retained four-byte value read through the acquisition address.
2. Four.
3. Zero.
4. The current value read through the captured count pointer.
5. Zero.
6. The status-slot address.

Its 32-bit return is treated as an allocation address. A nonzero status causes an immediate zero-extended status return. No explicit cleanup is performed for an address returned together with that allocation error.

The initial count is bounded, but the allocation argument is a fresh read. Dependency or aliasing effects can change it between initial publication and allocation.

### Record processing and publication

After allocation succeeds, the record index starts at zero and the status slot is set to zero.

Before each record, the function rereads the signed count through the captured pointer. If that count is less than or equal to the current index, processing completes immediately:

1. Load the then-current array-output pointer from the mutable local area.
2. Write the 32-bit allocation address through that pointer.
3. Return zero.

Consequently, a count changed to zero or a negative value can cause publication without any record writes, provided allocation has succeeded. The function does not enforce the initially published positive count as an immutable bound.

Otherwise, a record is processed in this order:

1. Call F-d8528f8db63b with the context and two; replace the status slot with its returned 32-bit value.
2. Repeat that call and replace the status slot again.
3. Call F-10d2ce969adf with the context and the status-slot address.
4. Inspect the status slot.
5. If zero, write one four-byte array element.
6. Call F-d8528f8db63b with the context and four; replace the status slot with its return.
7. Increment the index and reevaluate the current count.

The array write is at the allocation address plus four times the index. The value written is the reader result masked to 24 bits, plus the input base bit pattern, reduced modulo \(2^{32}\). There is no saturation or numeric range check.

The first advancement result is overwritten by the second. The second is not independently checked before the reader receives the status-slot address. Whether that reader overwrites or preserves a preceding error is dependency-defined.

The trailing advancement result is not checked before the next loop condition. In particular, a nonzero trailing result after the final required record does not by itself prevent successful publication.

If the record reader leaves a nonzero status, that record is not stored. F-bf7242c98d06 is invoked with the retained allocation-associated value and allocation address. The function then returns the status slot’s value after cleanup, zero-extended. The evidence does not establish that cleanup preserves that status.

Earlier elements may already have been written. This failure path does not explicitly publish the allocation address.

## Side effects

Established direct effects include:

- Initialization of the local argument-copy area.
- Capture of its count-address field before initial positioning.
- Shared-state reads for preparation and diagnostics.
- A four-byte acquisition-address read on the continuing path.
- Exposure of the mutable local area to F-e40a3ceddab2.
- A count write and repeated count reads through the captured pointer.
- Four-byte writes to allocated storage.
- A final reload of the local array-address field and publication through that effective destination.
- Conditional diagnostic invocation.
- Allocation and record-failure cleanup calls.

Changing the local array-address field can redirect successful publication. Changing only the local count-address field after capture does not redirect explicit count accesses. Neither statement establishes immunity from broader dependency side effects on the pointed-to memory.

Successful processing requires the dynamically reread count to remain compatible with available storage. The function performs no visible capacity check against count changes.

The dependency sequence suggests four bytes of leading material, a four-byte value, and four bytes of trailing material per record. A twelve-byte resource-record layout is inferred only if the advancement arguments represent byte counts and the reader consumes four bytes. Those dependency semantics are not established.

No explicit resource-close operation appears. No explicit release follows successful publication. Publication provides access to the allocation but does not establish an ownership-transfer protocol or the correct eventual release operation.

## Acceptance examples

These are conditional static expectations, not executed tests.

1. **Early return.** If acquisition’s lower half is seven and the unexplained condition selects early return, the result is seven with a zero upper half. No subsequent explicit acquisition-address dereference or output write occurs.

2. **Minimum directory size.** A successful directory-count read with low 16 bits zero permits examination of one entry, unless a match or failure terminates processing first.

3. **No match.** If all entry reads succeed and every complete tag differs from the request, the result is one. There are no explicit caller-output writes.

4. **Count before positioning failure.** A matching count field with low 16 bits two causes a write of three through the captured count pointer. A subsequent positioning failure returns its complete 64-bit result without explicit array publication.

5. **Redirected publication.** Suppose the initial positioning dependency replaces the local array-address field with another valid writable address. If that replacement remains in place and processing completes, the allocation address is written through the replacement. The original array-output slot is not the explicit publication destination.

6. **Count-copy mutation after capture.** Suppose the initial positioning dependency changes only the local count-address field. Subsequent explicit count publication and loop-bound reads still use the pointer captured before that call, not the replacement field value.

7. **Conditional output aliasing.** If the captured count pointer and the array pointer loaded at completion designate the same slot, final publication overwrites the count there. Equal original output arguments alone do not guarantee this outcome: a dependency may redirect the local array-address field before completion.

8. **Modulo arithmetic.** With base bit pattern `0xFFFFFFF0` and reader value `0xAB000020`, the stored element is `0x00000010`. The upper reader byte is discarded before addition.

9. **Final advancement failure.** If the final record is stored and trailing advancement returns a nonzero value, completion still publishes the allocation and returns zero if the next count check terminates processing and all required addresses remain valid.

10. **Record-read failure and cleanup.** If the reader leaves status nine, that record is not stored and cleanup is invoked. The return is nine only if cleanup leaves the status unchanged; otherwise the post-cleanup status is returned. No array publication is explicitly performed.

11. **Composite header failure.** If the directory-count reader returns `0x12345678` and leaves status five, the result is `0x0000567800000005`.
