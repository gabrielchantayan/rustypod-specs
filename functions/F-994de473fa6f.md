# F-994de473fa6f

## Purpose

F-994de473fa6f performs an ordered object update with mode-dependent preparation, optional updates to two one-byte fields, and a final delegated operation.

Two paths are established:

- With a zero mode, it substitutes a fixed selector value and invokes an indirect operation on a service object.
- With any nonzero mode, it prepares a temporary value from an object-associated address, then performs two conditional lookup-and-conversion sequences. Successful conditions cause direct writes at object offsets `0xB0` and `0xB1`, respectively.

Both paths begin with the same three dependency calls and service acquisition. Both finish by passing the original object value and original mode to F-876f4b90d114.

On normal completion, the function returns the 32-bit value `1`. This is not an established success report for the delegated operations: the function does not propagate their return values as its own status.

The apparent intent is to prepare an object and refresh two optional byte-valued settings. The meanings of the object, settings, selector constants, and service operations are not established.

The object is not validated locally. The supplied representation uses 32-bit address-bearing values, but does not establish portable pointer arithmetic, address-wrap behavior, alignment requirements, or the validity of any particular address.

No alternate return value, local error code, or early normal return is established. Faults, exceptions, nonlocal exits, and dependency-specific failure behavior remain undocumented.

## Behavior

### Common preparation

The following calls occur in order:

1. F-6a21f4f07f67 is called without explicit arguments. Its return value, if any, is not used.
2. F-d57e37ae0dcc is called without explicit arguments. Its word-sized result is retained.
3. F-46f0b3cb316e receives the object-relative address `object + 0xBC` and that retained result.
4. F-af667771d6ce is called without explicit arguments. Its result is treated as a service-object address.

The fourth input has already been copied into a writable local word. Nothing establishes that the common preparation calls preserve global state or leave the object unchanged.

### Zero-mode preparation

When the original mode is zero:

- The selector is replaced with a fixed 32-bit value read from global storage.
- An indirect operation is invoked using the acquired service object as its first argument and a second fixed global value as its other argument.
- The operation’s target is obtained through the service object’s table, at byte offset `0x58`.

The indirect operation’s identity, return contract, ownership effects, and interpretation of the second argument are unknown. Its result is not used.

Neither optional lookup sequence is performed on this path.

### Nonzero-mode preparation

When the original mode is nonzero, these operations occur in order:

1. F-eb24201e389b receives the address of the writable local word initialized from the fourth input, followed by `object + 0xB4`.
2. F-0ad008decd44 receives the service object and the address of that same local word.
3. F-24edd96d1422 receives the address of that same local word.

The word remains addressable throughout these calls. Any mutation performed through that address affects its subsequent observed contents.

The call to F-24edd96d1422 resembles a release or finalization step, but that interpretation is not established. The enclosing function subsequently copies the word’s contents. Accordingly, a specification must not assume that the word still contains the fourth input, that it remains a valid owned object, or that it has been cleared.

### Addressable staging and global capture

After either preparation path, the function captures a global record pointer for later use.

It also establishes addressable temporary storage containing:

- A copy of the original object value.
- A copy of the original mode.
- The effective selector.
- A separate temporary region whose first word receives the current contents of the preparation word.

The object copy, mode copy, and selector occupy consecutive four-byte slots, in that order. The separate temporary region begins immediately after the selector slot.

This adjacency matters because dependencies receive addresses into this storage. Their permitted read and write extents are not established here. These slots must not be assumed immutable merely because their initial values are known.

On the zero-mode path, staging is followed directly by the final operation. On the nonzero path, the following two conditional updates occur first.

### First conditional update: byte at `0xB0`

The first condition is evaluated in this order:

1. A record pointer is read from the global record location. Its four-byte field at offset `0x0C` is read.
2. F-9b9c1c7483f4 receives:
   - The address of the separate temporary region.
   - The field value just read.
   - The address of the selector slot.
3. After this call returns, a second global word is read and retained as the lookup context.
4. F-8094c3d72052 receives that context and the result of F-9b9c1c7483f4.
5. F-8a5aadac202f receives the separate temporary region’s address.
6. The condition is satisfied if F-8094c3d72052 returned any nonzero integer.

Temporary finalization in step 5 occurs before the conditional branch, regardless of whether the condition was satisfied.

If the condition is satisfied:

1. The four-byte field at offset `0x0C` is read through the previously captured record pointer.
2. F-9b9c1c7483f4 receives:
   - The address of the mode-copy slot.
   - That field value.
   - The address of the object-copy slot.
3. F-cf946f91e683 receives the retained lookup context and the construction result.
4. The observed one-byte result is written directly to `object + 0xB0`.
5. F-8a5aadac202f receives the address of the mode-copy slot.

The direct byte write precedes this finalization call.

If the condition is not satisfied, the function performs no direct write to `object + 0xB0`.

### Second conditional update: byte at `0xB1`

The second sequence runs whether or not the first condition was satisfied, unless an earlier operation failed to return normally.

It follows the same condition-then-conversion structure, with these differences:

- Both field accesses use offset `0x10` through the previously captured record pointer.
- The destination byte is `object + 0xB1`.
- The lookup context is the value already retained during the first condition sequence. The context global is not reread here.

Specifically, the function constructs into the separate temporary region using the selector-slot address, checks the result through F-8094c3d72052, and finalizes that region through F-8a5aadac202f. If the check is nonzero, it constructs into the mode-copy slot using the object-copy-slot address, converts through F-cf946f91e683, writes one byte at `0xB1`, and finalizes the mode-copy-slot region.

The second sequence does not reinitialize the addressable object, mode, selector, or separate temporary storage. Consequently, mutations from earlier dependency calls can influence later calls through these addresses.

### Final operation and return

After the mode-dependent work, F-876f4b90d114 receives the original object value and original mode.

These are not obtained by rereading the addressable object-copy and mode-copy slots. Mutating those slots does not, by itself, change the final call’s arguments.

The final dependency’s return value is not used. If it returns normally, F-994de473fa6f returns `1`.

## Side effects

### Direct writes

The only established direct writes into the caller’s object are:

- A one-byte write at `0xB0`, conditional on the first nonzero-mode check.
- A one-byte write at `0xB1`, conditional on the second nonzero-mode check.

These writes are ordered: any direct `0xB0` write occurs before any direct `0xB1` write.

The conversion results are not normalized to Boolean values. The observed byte returned by F-cf946f91e683 is stored as supplied.

An unsatisfied condition means **no direct store by this function** to the corresponding byte. It does not guarantee that the byte’s entry value survives: earlier or later dependencies may modify the object.

### Global state and read timing

No direct global write is shown. Dependencies may nevertheless change globals.

Two timing distinctions are significant:

- A record pointer is captured before the optional sequences, but the first condition’s `0x0C` field access reads the global record pointer again. Later field accesses use the captured pointer.
- The lookup-context global is read after the first construction call. All subsequent checks and conversions reuse that captured context, even if dependencies later modify the global.

Field contents are read when needed, not snapshotted together. For example, a dependency may change the captured record’s `0x10` field between its condition access and its conversion access.

### Temporary storage and ownership

The function passes stack-resident addresses to dependencies and invokes apparent finalization operations on two kinds of temporary storage. This establishes call ordering, not an ownership model.

There is no established guarantee that dependencies:

- Restrict writes to one word.
- Preserve adjacent slots.
- Preserve globals or object fields.
- Retain or release referenced memory.
- Avoid retaining the supplied addresses.

If a dependency retains a stack address beyond the call’s valid lifetime, safety depends on an external contract not provided here.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Each assumes valid required storage and normal returns from all dependencies.

### Zero mode

Given a zero mode:

- Common preparation and service acquisition occur.
- The fixed-selector substitution and indirect service operation occur.
- Neither conditional lookup sequence occurs.
- F-876f4b90d114 receives the original object and zero.
- The return value is `1`.

This does not imply that the object bytes remain unchanged through dependency side effects.

### Nonzero mode with both conditions false

Given any nonzero mode and zero results from both calls to F-8094c3d72052:

- Both condition constructions and their corresponding finalizations occur.
- F-cf946f91e683 is not called.
- Neither direct byte store occurs.
- Final delegation still occurs, followed by return value `1`.

### Only the first condition accepted

If the first check returns nonzero and its conversion supplies byte `0xA6`, while the second check returns zero:

- `0xA6` is directly stored at `object + 0xB0`.
- No direct store occurs at `object + 0xB1`.
- The first accepted temporary is finalized after its byte store.

No Boolean coercion changes `0xA6` to `1`.

### Both conditions accepted

If both checks return nonzero and the conversions supply bytes `0x00` and `0xFF`:

- `0x00` is stored at `0xB0`.
- The first accepted temporary is finalized.
- The second condition and conversion sequence runs.
- `0xFF` is stored at `0xB1`.
- The second accepted temporary is finalized before final delegation.

A zero converted byte does not invalidate an already accepted condition.

### Global changes during construction

If the first construction changes the lookup-context global before returning, the subsequent context read observes the resulting value. If a later dependency changes that global again, later checks and conversions still receive the retained earlier context.

If a dependency changes the global record pointer after its capture, later accesses through the captured pointer do not automatically follow that replacement.

### Mutation of addressable copies

If a dependency changes the staged object-copy word, a later construction receiving that word’s address can observe the changed contents. The final delegation nevertheless receives the original object argument.
