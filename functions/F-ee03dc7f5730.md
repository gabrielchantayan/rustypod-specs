# F-ee03dc7f5730

## Purpose

F-ee03dc7f5730 decodes a bounded byte sequence into fixed-size records appended to an existing context-held array. Each record contains two scale-like quantities, two displacement-like quantities, an offset-like quantity, and an identifier-like quantity.

The operation is incremental, not transactional. Capacity changes, completed records, and writes to an incomplete record are not rolled back when decoding encounters insufficient input.

A compound-glyph component interpretation is inferred from the diagnostic and record structure. The contract below establishes byte decoding, storage, call ordering, and status handling without assuming broader format semantics.

## Interface

### Arguments and machine model

The function receives:

1. A context address.
2. An input-start address.
3. An exclusive input-end address.

The supplied body uses a 32-bit address and integer model. Input is read as 8-bit bytes. Encoded multibyte quantities are assembled most-significant byte first; this does not establish the native byte order of context or record storage.

There is no explicit null-pointer validation. The caller must provide valid context storage and meaningful address arithmetic. The function computes input-start plus one before deciding whether the header is available.

### Context layout

| Context offset | Width | Role |
|---|---:|---|
| `0x18` | 32 bits | Completed-record count |
| `0x1c` | 32 bits | Array capacity; compared as unsigned |
| `0x20` | 32-bit address | Array base |
| `0x24` | 32-bit address | Address of a location holding a dependency handle |

The handle is obtained by reading the address at context offset `0x24`, then reading a 32-bit value through that address. Both reads precede the initial input-availability check.

The function does not validate count-versus-capacity consistency, nonnegative count, array extent, or the nested handle address. Safe use requires those invariants, sufficient storage for any resulting writes, and representable record-address calculations.

### Record layout

Each record occupies 24 bytes:

| Record offset | Width | Contract name |
|---|---:|---|
| `0x00` | 32 bits | First scale |
| `0x04` | 32 bits | Second scale |
| `0x08` | 32 bits | First displacement |
| `0x0c` | 32 bits | Second displacement |
| `0x10` | 32 bits | Offset-like value |
| `0x14` | 32 bits | Identifier |

These names describe apparent roles, not established units or reference systems.

### Result and cursor

The function returns the current 32-bit local status at its return point.

- Status is initially zero.
- The optional-header dependency’s return value replaces status.
- The allocation dependency receives a writable address of status.
- A local input shortage assigns status `8` before invoking the diagnostic dependency.

Consequently, ordinary success returns zero when no dependency changes status away from zero. A truncation returns `8` only if that assignment remains unchanged through the diagnostic call. Normal return from the diagnostic alone does not guarantee `8`: an earlier allocation dependency received the status address and could retain it for subsequent mutation.

The parsing cursor is local and is not returned. The optional-header dependency receives its writable address and can change it.

## Behavior

### Header and preliminary calls

After initializing status and fetching the nested handle, the function checks whether one header byte fits. An exact fit is accepted.

If the input end precedes input-start plus one, the function does not read a header. It follows the truncation procedure described below, using the input start as its fallback cursor.

Otherwise, it reads one header byte.

If header bit `0x80` is clear, two global values, located at `0x080cd53c` and `0x080cd538`, are read as arguments to F-540af0155702. These reads occur on this path before that dependency is invoked. The supplied body does not establish their values, their declared widths, or their relative evaluation order.

The call also receives assertion-related diagnostic information. No local rejection or explicit error return follows it. If the dependency returns normally, processing continues using the header byte already read.

Header bit `0x08` requests F-129dd09ab861. That dependency receives the writable local-cursor address and input end. Its returned value becomes status:

- Nonzero: array preparation and component decoding are skipped.
- Zero: processing continues from the cursor it leaves.

The function does not independently verify that this resulting cursor remains within the original input interval.

The requested component count is the header masked with `0x3f`. Bit `0x08` therefore contributes eight to the count as well as requesting the dependency call. Bits `0x10` and `0x20` also contribute to the count. Header bit `0x40` has no direct effect in this body.

### Array preparation

After the optional-header stage succeeds, the function reads the existing completed-record count. This captured count determines the initial destination position.

It adds the requested component count to that count to form a 32-bit required capacity, then compares the existing capacity against the result as unsigned.

If growth is required, the requested capacity is rounded upward to a multiple of four by adding three and clearing the lowest two bits. No explicit overflow check accompanies either addition.

F-6dd003795db7 receives:

- The handle fetched before header processing.
- Element size `24`.
- The capacity read from the context for this call.
- The rounded requested capacity.
- The array address read from the context.
- The writable address of local status.

The capacity used for the call is a separate context read from the earlier capacity comparison. The body does not establish an evaluation order among the call’s argument reads.

The returned array address is stored at context offset `0x20` before status is checked.

- If status is nonzero, the function returns the current status immediately. It does not restore the old array address or directly update capacity.
- If status is zero, it writes the rounded capacity to context offset `0x1c`.

The destination address is then formed from the context’s array address and the count captured before allocation, using a 24-byte record stride. Dependency changes to the count do not replace that captured starting index.

Even a zero-component operation reaches destination-address calculation after array preparation. Under valid count and capacity invariants, zero components require no growth.

### Component decoding

Each component consumes fields in this order:

1. Control byte.
2. Optional first scale.
3. Optional second scale.
4. Optional first displacement.
5. Optional second displacement.
6. Identifier.
7. Offset-like value.

Every input-bearing field is checked for its full encoded width before its bytes are read. An exact fit at the input end is accepted. These checks establish upper-bound handling for the current cursor; they do not add a lower-bound check or validate a cursor supplied by a dependency.

#### Scales

After the control byte is available and read, the function writes `65536` (`0x00010000`) to the first scale.

If control bit `0x10` is set, it requires two bytes, interprets them as an unsigned big-endian 16-bit value, multiplies that value by sixteen, and stores the result as the first scale. The result ranges from `0` through `1048560` (`0x000ffff0`). There is no sign extension from encoded bit 15.

Once the first scale is complete, the function writes `65536` to the second scale. Control bit `0x20` requests the same two-byte unsigned encoding for that field.

The default suggests a fixed-point unit value, but that semantic interpretation is not established.

#### Displacements

Control bits `0–1` select the first displacement encoding. Bits `2–3` select the second:

| Selector | Encoded width | Result |
|---:|---:|---|
| `0` | No bytes | Zero |
| `1` | Two bytes | Unsigned big-endian 16-bit value, widened to 32 bits |
| `2` | One byte | Signed 8-bit value, sign-extended to 32 bits |
| `3` | No bytes | Zero |

Selector `3` is accepted without consuming displacement bytes.

The two-byte form ranges from `0` through `65535`; it is not signed. The one-byte form ranges from `-128` through `127`.

Both values are decoded before either destination displacement is written. A shortage in the second displacement therefore leaves both displacement fields untouched, even if the first displacement was decoded successfully.

After both decodes succeed, the first displacement is written, followed by the second.

#### Identifier

After the displacement writes:

- Control bit `0x40` clear: read one unsigned byte.
- Control bit `0x40` set: read two unsigned big-endian bytes.

The widened result is stored at record offset `0x14`.

#### Offset-like value

After storing the identifier:

- Control bit `0x80` clear: read an unsigned big-endian 16-bit value.
- Control bit `0x80` set: read a signed big-endian 24-bit value.

The two-byte form ranges from `0` through `65535`. The three-byte form ranges from `-8388608` through `8388607`, with the first byte supplying the sign extension.

The 32-bit result is stored at record offset `0x10`.

### Record completion and trailing input

After the final field write, the destination advances by 24 bytes. The function then reads the current context count, adds one, and writes it back.

Thus, destination positioning and count updates are distinct: the destination starts from a captured count, while each completion increments the count currently held in the context.

After the requested number of components, the function returns the current status. It does not require the cursor to equal the input end. Trailing input is accepted and is not otherwise examined by this function.

## Side effects

### Direct read and write order

The principal observable sequence is:

1. Initialize local status to zero.
2. Read the nested handle through context offset `0x24`.
3. Check header availability and, if available, read the header.
4. On a clear high header bit, read both global assertion-argument values, in an unspecified relative order, then invoke F-540af0155702.
5. Invoke optional-header processing if requested.
6. Read the count and capacity for array preparation.
7. If needed, invoke allocation, publish its returned address, inspect status, and write capacity only on success.
8. Perform each component’s checks, input reads, and destination writes in the order described above.
9. Increment the context count only after a complete record.

The body performs no direct writes through the input pointer. This does not guarantee input immutability when storage aliases or dependencies modify reachable memory.

### Truncation procedure

Every locally detected input shortage follows this order:

1. Assign the local cursor a fallback address: the beginning of the unavailable header or field.
2. Assign local status `8`.
3. Invoke F-4457a9a44a68 with an invalid-input diagnostic.
4. If the call returns normally, return the current status.

The fallback is the input start for a missing header, the component cursor for a missing control byte, and the start of the particular encoded field for later shortages.

The assignment of `8` precedes the diagnostic call. The returned status remains dependency-sensitive because the allocation dependency may have retained the status address. The optional-header dependency likewise received the cursor address; no non-retention guarantee is established for either address during the call’s lifetime.

### Partial-record boundaries

| Shortage | Direct record writes already performed |
|---|---|
| Control byte | None |
| First explicit scale | First scale default |
| Second explicit scale | Completed first scale and second scale default |
| Either displacement | Both completed scales; neither displacement |
| Identifier | Scales and both displacements |
| Offset-like value | Scales, displacements, and identifier |

The unavailable field is not partially read or partially stored by the local decoding logic. The incomplete record is not counted.

Previously completed records remain written and counted. Published allocation results and successful capacity changes remain in effect. Dependency side effects may add further changes; no rollback is performed.

### Ownership

The context stores the array address, but this body does not establish ownership rules. It performs no explicit release or failure cleanup.

F-6dd003795db7 may replace, preserve, release, or otherwise manage the old allocation; its behavior is unknown here. A nonzero status does not justify assuming that the old address or its storage survives.

## Acceptance examples

These are static, conditional examples, not executed tests. Unless stated otherwise, they assume valid nonoverlapping storage, safe arithmetic, adequate capacity or successful growth, and dependencies that return normally without additional relevant mutations.

1. **Zero components and trailing input.**  
   Header `80` requests no components. With valid existing count and capacity, no record is written and the count is unchanged. Trailing bytes do not cause rejection. Status remains zero.

2. **Minimal record.**  
   Bytes `81 00 2a 12 34` append one record containing scales `65536`, `65536`; displacements `0`, `0`; identifier `42`; and offset-like value `4660`. Count increases by one.

3. **Signed one-byte displacements.**  
   Bytes `81 0a ff 80 07 00 01` produce displacements `-1`, `-128`, identifier `7`, and offset-like value `1`, with default scales.

4. **Unsigned two-byte displacement.**  
   Bytes `81 01 ff ff 07 00 00` produce first displacement `65535`, not `-1`, and second displacement zero.

5. **Selector three.**  
   Bytes `81 0f 07 00 00` consume no displacement bytes and store zero for both displacements.

6. **Unsigned explicit scale.**  
   Bytes `81 10 ff ff 01 00 00` store first scale `1048560`, not a negative value. The second scale remains `65536`.

7. **Wide identifier and signed offset.**  
   Bytes `81 c0 12 34 ff ff ff` store identifier `4660` and offset-like value `-1`. Replacing the final three bytes with `80 00 00` produces `-8388608`.

8. **Truncated offset.**  
   Bytes `81 00 2a 12` leave scales, displacements, and identifier written, but leave the offset field untouched and do not increment count. The function assigns fallback cursor to the offset’s first byte, assigns status `8`, and calls F-4457a9a44a68. It returns `8` only if status remains unchanged.

9. **Retained status address.**  
   Suppose successful growth exposes the status address to F-6dd003795db7, followed by truncation. If subsequent dependency behavior changes that status to `5` during the diagnostic call, normal return from the diagnostic leads to return value `5`, not a forced `8`.

10. **Growth and failure publication.**  
    Count `3`, capacity `3`, and header `81` request capacity `4`. If allocation reports failure, its returned address is still published. The function does not directly update capacity or decode a component before returning the current nonzero status.

11. **Overlapping header roles.**  
    Header `88` invokes F-129dd09ab861 and requests eight components. A zero dependency result leads to eight decode attempts from its resulting cursor.

12. **Clear high header bit.**  
    Header `00` causes both global assertion-argument values to be read before F-540af0155702 is called. Their relative read order is unspecified. If the call returns without relevant mutation, the zero-component path continues; rejection is not guaranteed.
