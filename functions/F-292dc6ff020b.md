# F-292dc6ff020b

## Purpose

F-292dc6ff020b performs a comparison-driven search over an indexed object. It returns a 64-bit value containing a 32-bit index-like result in its low half and one of the supplied 32-bit arguments in its high half.

The established behavior supports two modes:

- **Zero mode:** return an index at which comparison returned zero, or the 32-bit representation of −1 after an unsuccessful nonempty search.
- **Nonzero mode:** return the final midpoint, advanced by one when the last comparison result was negative.

**Inferred intent:** the zero mode resembles exact-match lookup, and the nonzero mode resembles insertion-position lookup. Those interpretations require consistent indexed access and a comparison ordering compatible with the branch directions. Neither ordering nor dependency behavior is established by the supplied evidence.

An initially empty search is distinctive: it returns a low half of zero in either mode, without invoking the indexed-access dependency or the comparison operation.

## Interface

### Inputs

The function receives four arguments:

| Argument | Established role |
|---|---|
| Search object | Address of an object whose first word supplies a dispatch-table address and whose next 32-bit word supplies the initial search extent. |
| First opaque word | A 32-bit value passed to every comparison. It also becomes the high half of the return value when no comparison executes. |
| Second opaque word | A 32-bit value passed twice to every comparison. It becomes the high half of the return value once a comparison executes. |
| Mode | A 32-bit integer. Zero selects exact-match-style finalization; every nonzero value selects position-style finalization. |

The two opaque words have no established pointer, numeric, ownership, or encoding interpretation. Their bit patterns matter.

### Object and dispatch layout

The supplied representation establishes these accessed locations:

- The search object's first word contains a dispatch-table address.
- A signed 32-bit extent is read at byte offset 4 from the search object.
- A callable entry is obtained at byte offset 0x18 from the search object's dispatch table.
- A second callable entry is obtained at byte offset 0x58 from the search object's dispatch table.
- The object returned by the second call supplies its own dispatch-table address in its first word.
- A comparison callable is obtained at byte offset 0x28 from that second dispatch table.

These are byte offsets. The full object layouts, table sizes, callable-pointer widths, and ABI are not supplied. The layout is consistent with a 32-bit object representation, but that does not independently establish every address or calling-convention detail.

### Output

The return value is a 64-bit concatenation:

- **Bits 31–0:** the final 32-bit index-like value.
- **Bits 63–32:** the first opaque word if the comparison loop executes zero times; otherwise the second opaque word.

This is a bit-field contract, not a signed 64-bit index contract. For example, a low half representing −1 does not imply that the complete 64-bit return value is −1.

## Behavior

### Initialization and externally observable order

Before invoking dependencies, the function reads the search extent and forms an initial upper endpoint one less than that extent. The initial lower endpoint is zero. The remembered midpoint and comparison result both start at zero.

The function then performs two calls, in this order:

1. It dispatches through the search object's entry at offset 0x18, passing the search object as the sole explicit argument. The returned 32-bit word is retained for subsequent comparisons.
2. It dispatches through the search object's entry at offset 0x58, again passing the search object as the sole explicit argument. The returned address is retained as the comparison receiver.

These calls occur even when the initial search interval is empty.

The extent is not reread after either call. Consequently, changes to the object's extent during these calls do not change the locally retained initial search interval.

The second dispatch is obtained after the first call. The evidence does not justify assuming that the first call leaves the search object's dispatch-table address or other memory unchanged.

### Search iterations

An iteration occurs while the retained lower endpoint is no greater than the retained upper endpoint, using signed comparisons.

For each iteration, the function:

1. Selects a midpoint from the signed sum of the endpoints divided by two.
2. Calls F-3b5d52fd8e4a with the original search object and that midpoint.
3. Uses the returned 32-bit word as an input to a comparison call on the retained comparison receiver.

The comparison receives these explicit arguments in order:

1. The comparison receiver.
2. The word returned by F-3b5d52fd8e4a for the current midpoint.
3. The word returned by the initial dispatch at offset 0x18.
4. The first opaque input word.
5. The second opaque input word.
6. The second opaque input word again.

The duplicated final argument is established behavior. Its semantic purpose is unknown.

The comparison dispatch entry is obtained from the retained receiver during each iteration, after indexed retrieval. The receiver address is retained across iterations, but the evidence does not establish that its contents or dispatch table remain unchanged.

The comparison's 32-bit result is interpreted as signed:

- **Zero:** terminate the search immediately, retaining the current midpoint.
- **Negative:** move the lower endpoint to one greater than the current midpoint.
- **Positive:** move the upper endpoint to one less than the current midpoint.

A negative result therefore directs the search toward larger indices; a positive result directs it toward smaller indices. The function does not establish which argument is considered “less than” by the comparison operation.

There is no additional comparison after the endpoints cross.

### Finalization

Finalization uses only the retained midpoint, retained comparison result, and mode.

For **zero mode**:

- If the retained comparison result is zero, retain the midpoint.
- Otherwise, replace the low-half result with −1.

For **nonzero mode**:

- If the retained comparison result is negative, return one greater than the retained midpoint in the low half.
- Otherwise, retain the midpoint.

All nonzero mode values follow the same branch. There is no separate treatment for positive and negative mode values.

### Empty and nonpositive extents

For an initial extent of zero, the upper endpoint becomes −1. No iteration executes.

The initial comparison result remains zero and the initial midpoint remains zero, so:

- Zero mode returns low half zero.
- Nonzero mode also returns low half zero.
- The high half is the first opaque word.
- Both initial dispatch calls still occur.
- F-3b5d52fd8e4a and the comparison dispatch are not invoked.

The same behavior follows for negative extents when subtracting one is representable and leaves the upper endpoint below zero. The function does not reject such extents explicitly.

The minimum signed 32-bit extent requires separate treatment because subtracting one is outside the signed 32-bit range; its resulting behavior is not established.

### Integer arithmetic boundaries

The extent, endpoints, midpoint, comparison result, and mode are represented as 32-bit integers in the supplied evidence. Indexed retrieval returns a 32-bit word, as does the initial offset-0x18 dispatch.

For nonnegative endpoints whose sum is representable, midpoint selection has the usual integer midpoint result. However, the midpoint is formed from the endpoint sum, not an explicitly overflow-avoiding difference calculation.

The following operations can encounter signed-range boundaries for unrestricted inputs or sufficiently large ranges:

- Subtracting one from the initial extent.
- Adding the two endpoints to form the midpoint numerator.
- Advancing a midpoint by one.
- Reducing a midpoint by one.

No validation or explicit overflow handling is visible. Overflow cases are **documented_only**: the evidence is insufficient to select a machine-wrap, language-level, or trapping interpretation.

## Side effects

The function has no visible direct writes to object fields, caller-provided buffers, or global storage. Its visible direct updates are to its own retained search state.

Nevertheless, it invokes dependencies that may have externally observable effects:

- Two initialization dispatches occur unconditionally.
- Each executed search iteration invokes indexed retrieval and comparison, in that order.
- Any of those calls may mutate memory, change globals, perform I/O, acquire or release resources, or fail to return.

No preservation of globals or object contents is established.

The function retains the initially returned comparison operand and receiver address. It does not reacquire either through the initialization dispatches during later iterations. Mutating the receiver's contents can still affect later comparison dispatches, because its dispatch information is accessed again.

There is no visible allocation, deallocation, reference-count adjustment, or ownership transfer performed directly by this function. In particular:

- The comparison receiver is not visibly released.
- Values returned by indexed retrieval are not visibly released.
- The original search object is not visibly released.

These observations do not establish ownership. Dependencies may manage resources themselves, and their contracts are unavailable.

No explicit error channel, null check, bounds check, exception handler, or cleanup path is present. A negative comparison result is ordinary search control, not an error indication. Invalid addresses, incompatible dispatch entries, dependency failures, and invalidated objects have no defined recovery behavior in the supplied evidence.

## Acceptance examples

These examples are conditional behavioral checks, not reports of execution. Unless stated otherwise, assume valid dispatch structures, returning dependencies, a stable compatible indexed range, and arithmetic that remains representable.

### Empty range

Given an extent of zero, first opaque word 0x11223344, and second opaque word 0xAABBCCDD:

- The two initialization dispatches execute in order.
- No indexed retrieval or comparison occurs.
- Either mode returns high half 0x11223344 and low half 0x00000000.

The complete return value is therefore 0x1122334400000000.

### Single element, equality

Given an extent of one and a comparison result of zero at index zero:

- Indexed retrieval receives index zero.
- Comparison executes once.
- Either mode returns low half zero.
- The high half is the second opaque word, even if the two opaque words differ.

### Single element, negative comparison

Given an extent of one and a negative comparison result at index zero:

- The search interval becomes empty after that comparison.
- Zero mode returns low half 0xFFFFFFFF.
- Nonzero mode returns low half 0x00000001.
- Both results use the second opaque word as their high half.

### Single element, positive comparison

Given an extent of one and a positive comparison result at index zero:

- Zero mode returns low half 0xFFFFFFFF.
- Nonzero mode returns low half zero.
- Both results use the second opaque word as their high half.

### Multi-step unsuccessful search

Given an extent of five, with a negative comparison at index two followed by a positive comparison at index three:

- Indexed retrieval observes indices two and three, in that order.
- The second update makes the retained interval empty.
- Zero mode returns low half 0xFFFFFFFF.
- Nonzero mode returns low half three.

This result follows from the observed comparison sequence; it does not require assigning semantic names to the compared values.

### Equality among repeated values

Given an extent of five and equality on the first comparison:

- The selected midpoint is two.
- Both modes return low half two.
- No attempt is made to locate an earlier or later equal entry.

Thus, even under a sorted-range interpretation, the function is not established as a first-equal or last-equal search.

### Extent mutation during initialization

Given an initial extent of zero, if an initialization dependency changes the object's stored extent to a positive value:

- The locally retained interval remains empty.
- No search iteration occurs.
- The return follows the empty-range rules.

This example assumes that the remaining initialization dispatch remains valid after the mutation.
