# F-ea9509f76d3f

## Purpose

F-ea9509f76d3f is a non-returning control-transfer routine in the supplied representation. Its externally visible behavior consists of:

- A conditional 16-bit memory copy whose addresses depend on incoming machine state.
- A more restrictive conditional operation that reads address zero and writes a 16-bit value to an address derived from that read.
- An unbounded sequence of two indirect calls followed by software interrupt number 0x5B.

No application-level purpose, data format, allocation policy, or recovery protocol is established.

The behavior below distinguishes explicit operations from consequences derived under a 32-bit machine-address model. That distinction matters: the representation mixes integers, pointers, implicit register inputs, and a stack-derived address. It does not establish a portable high-level language interface.

## Interface

### Explicit input

The routine has one explicit unsigned 32-bit input, referred to here as the **input word**.

Two derived values are important:

- The **scaled input** is the input word multiplied by 4096, retaining the low 32 bits.
- The **double-scaled input** is the input word multiplied by 8192, retaining the low 32 bits.

The scaled input is zero precisely when the input word’s low 20 bits are zero. This includes nonzero inputs such as 0x00100000.

### Outputs and completion

### Arithmetic and access widths

This contract uses the following interpretation:

- Address and word calculations are modulo \(2^{32}\).
- Halfword memory accesses read or write 16 bits.
- Offsets added through a halfword pointer are scaled by two bytes.
- Offsets explicitly expressed as integer additions are byte offsets.
- Boolean contributions are either zero or one.
- A stored halfword retains the low 16 bits of its computed value.

This describes the apparent machine-level behavior. It is not a claim that arbitrary pointer arithmetic or address-zero accesses are valid in a portable language environment.

## Behavior

### Conditional initial copy

If the scaled input is nonzero, the routine performs no explicit data-memory read or write before entering the dispatch loop.

If the scaled input is zero, the routine performs these observable operations in order:

1. Read one unsigned 16-bit value from the incoming source address.
2. Write that value to the address obtained by adding the incoming offset word to the incoming source address, modulo \(2^{32}\).

The offset is a byte offset, not a halfword count. It can therefore produce an odd destination address.

The read precedes the write. If the source and destination are identical, the representation still contains a read followed by a write; the operation must not be described as having no access.

After deriving the destination, the routine computes an adjusted source-address value by subtracting the incoming adjustment word from that destination. This calculation affects subsequent eligibility checks; it does not itself read or write the resulting address.

A failed read prevents the write. A failed write prevents later dispatch. No explicit handler is shown for either failure.

### Restrictive address-zero operation

Under the 32-bit interpretation, the additional memory operation is eligible only when all of the following conditions hold:

1. The scaled input is zero.
2. The incoming link address is zero.
3. The stack-reference address is zero.
4. The incoming comparison word equals the incoming offset word.
5. The incoming adjustment word equals the adjusted source-address value, modulo \(2^{32}\).
6. The incoming auxiliary word is zero.
7. Twice the incoming offset word is zero modulo \(2^{32}\).

The final condition permits two unsigned offset values: zero and 0x80000000.

If these conditions hold and execution has survived the initial copy, the routine:

- Establishes a zero-valued stack-related machine-state value in the displayed representation.
- Uses address zero as the source of an unsigned 16-bit address value.
- Reads a 16-bit value from address zero for an addition of 15.
- Writes the low 16 bits of that addition to the address obtained from the unsigned 16-bit address value.

The destination is consequently in the range 0x00000000 through 0x0000FFFF. It is not scaled by two.

The representation contains two reads from address zero in this operation: one supplies the destination address and one supplies the value to increment. It does not establish their evaluation order. Neither read may be silently replaced by the other in a contract intended to cover volatile or externally changing memory.

If memory is stable between the reads and the halfword at address zero is \(h\), the resulting write is a halfword write of \((h+15)\bmod 65536\) to byte address \(h\).

No null check, bounds check, or alignment adjustment protects this operation. In an environment where address zero is inaccessible, it faults rather than producing a defined error result.

### Reachability of other displayed memory operations

The representation contains additional conditional reads and writes after the operation above. Under the stated 32-bit arithmetic interpretation, their eligibility conditions cannot be satisfied.

The relevant derivation is:

- Reaching the address-zero operation requires the scaled input, incoming link address, and an intermediate stack-derived value to be zero.
- With the scaled input zero, input bit 18 is necessarily clear.
- The stack-derived zero condition therefore restricts the stack-reference address to zero or one.
- A later zero-result condition requires that address plus twice the incoming offset word to be zero. Since twice a word is even modulo \(2^{32}\), the stack-reference address cannot be one.
- The stack-reference address is therefore zero.
- The address-zero operation consequently leaves the updated link-derived base at zero.
- Its following comparison sequence encounters a halfword-pointer increment of one, equivalent to a byte-address increment of two. The resulting comparison value is two rather than zero, stopping eligibility propagation.

Accordingly, the later pointer-sized stores, signed-halfword-derived stores, and variable left-shift calculation are not established reachable behavior in this model.

This is a static reachability result, not runtime evidence. If the intended machine semantics differ from this 32-bit interpretation, those operations require a separate specification rather than being assumed harmless.

### Dispatch loop

The initial dispatch base is the incoming link address. The restrictive address-zero path does not change that outcome: it requires the incoming link address to be zero and leaves the base zero.

Each completed loop iteration performs the following actions in order:

1. Invoke the callable address obtained by adding 0x0EB6 bytes to the current dispatch base, modulo \(2^{32}\).
2. If that call returns, invoke the callable address 0x0857A94B.
3. If that call returns, execute software interrupt number 0x5B.
4. If the interrupt returns, replace the dispatch base with 0x083D4CC2.
5. Begin another iteration.

The first call receives three explicit argument words:

- 0x00000000
- 0x00000000
- 0xFFFFFFA5

The third argument is the unsigned 32-bit bit pattern shown above. Interpreting it as signed gives −91, but the dependency’s signedness expectations are unknown.

The second call has no explicit arguments in the representation. This does not establish that argument registers are cleared or that the dependency accepts a zero-argument ABI.

After the first returning interrupt, every subsequent first call targets address 0x083D5B78. The second call continues to target 0x0857A94B.

No call result is explicitly inspected. The routine does not contain a loop exit, retry limit, delay, or explicit error branch.

## Side effects

No explicit allocation, release, ownership transfer, reference counting, or resource cleanup is shown. Indirect dependencies may nevertheless perform such actions; their behavior is unknown.

There is no guarantee that dependencies preserve global state, memory, registers, or resources. Subsequent behavior is conditional on their returning in a way compatible with continuation of the displayed control flow.
