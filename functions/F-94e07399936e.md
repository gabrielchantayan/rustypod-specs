# F-94e07399936e

## Purpose

F-94e07399936e conditionally invokes an indirect operation associated with a selected table entry. If the selected entry is nonzero and the operation returns normally, the function clears a selected slot and then decrements a context field.

The input has a pointer-shaped declaration, but the supplied representation uses it as a signed 32-bit selector. No dereference of the input itself is shown.

Removal or release of a registered entry is **inferred intent**, not an established ownership contract. The established behavior is selection, indirect dispatch, post-call slot clearing, and a subsequent counter-field update. These actions do not prove that any allocation is released or that the counter accurately represents occupied entries.

The slot-clear destination can alias the counter field. Consequently, the decrement uses the value present **after the slot clear**, which is not necessarily the value left by the indirect operation.

## Behavior

### Context acquisition

F-ecd921e533b1 is called once before selector rejection.

Zero, negative, and out-of-range selectors therefore do not bypass the provider. Its side effects, failures, or failure to return can affect every invocation.

The returned address is retained. The provider is not called again, including after the indirect operation. If that operation changes other state used by the provider, this function still uses its previously retained context address.

### Selector classification

The selector is compared using signed 32-bit ordering.

For a negative selector, the function returns after the provider call without any explicit context-field read, table access, or direct write.

For a nonnegative selector, the function reads the context field at offset 4. Equality with that boundary prevents lookup. A selector greater than the boundary also prevents lookup.

Thus, lookup occurs precisely when the selector is nonnegative and strictly less than the signed boundary.

Consequences include:

- Zero with a positive boundary is eligible.
- Zero with boundary zero is rejected.
- Zero with a negative boundary is rejected.
- Equality with the boundary is always rejected.
- No nonnegative selector passes a negative boundary.

The initial zero comparison does not establish a universal zero-selector rejection rule.

### Selected-entry read

For an eligible selector, the function reads the context’s table-base field and then the four-byte slot at the base plus four times the selector.

No separate checks establish:

- Table allocation size.
- Base-address validity or alignment.
- Address-arithmetic safety.
- Consistency between the boundary and accessible table storage.
- Liveness or type of a nonzero entry.

A valid signed selector comparison does not itself prove safe addressing. Four times an accepted selector can exceed the mathematical range of a 32-bit address. Concrete overflow, conversion, and address-wrapping behavior are **documented_only**.

If the selected entry is zero, the function returns without indirect dispatch or either direct write.

### Indirect operation

No explicit arguments or consumed return value are shown. This does not prove the absence of an implicit receiver, register inputs, or other ABI-level parameters.

Before the operation begins, this invocation has not cleared the selected slot or decremented the counter. The function therefore does not hide the original entry from a reentrant observer before dispatch.

### Post-call slot clear

After normal indirect return, the function reads the table-base field again from the retained context.

Using that newly read base and the original selector, it writes a four-byte zero to the resulting selected-slot address.

The function does not:

- Re-read the boundary.
- Reclassify the selector.
- Re-read the selected entry before clearing.
- Check that the slot still contains the originally dispatched entry.
- Check that the new table is the original table.

Accordingly, an indirect operation that replaces the table base redirects the clear. An operation that replaces the entry in an unchanged table can cause the replacement entry to be cleared.

The slot-clear destination may overlap context storage. If it coincides with the offset-8 counter field, this write sets that field to zero before the decrement reads it. If it instead overlaps another context field, that field can be modified by the clear. No table/context separation is enforced.

### Counter-field update

Only after the slot-clear write does the function read the four-byte field at context offset 8. It subtracts one from that observed value and writes the result back to the same context field.

The decrement therefore uses the value present after both:

1. The indirect operation.
2. The selected-slot clear.

A callback-written counter value survives into the decrement only if the intervening clear does not overwrite it, and no other intervening mutation changes it.

For example, if the operation leaves the counter at 12 and the slot clear does not overlap the counter, the subsequent decrement produces 11, assuming otherwise stable state and ordinary representable arithmetic. If the clear instead writes zero directly over the counter, the decrement reads zero and stores −1.

The function does not guard against zero, negative values, or the minimum signed 32-bit value. The supplied representation expresses signed arithmetic; portable wraparound at signed overflow cannot be promised.

The function then returns.

## Side effects

### Direct access order

The established successful path has this logical order:

1. Call F-ecd921e533b1.
2. Read the boundary.
3. Read the initial table base.
4. Read the selected entry.
5. Read the entry’s dispatch metadata and callable target.
6. Invoke the indirect operation.

8. Write zero to the selected slot calculated from that base.
9. Read the retained context’s offset-8 field.
