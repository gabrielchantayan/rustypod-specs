# F-6c10861922bc

## Purpose

F-6c10861922bc selects a candidate associated with an input object and invokes that candidate’s callback. It can continue searching when a callback returns a status whose least significant byte is hexadecimal 13. A successful callback may trigger a separate dependency call, depending on whether a retry occurred.

The contract distinguishes three outcomes:

- A null input object returns status 6 without accessing object memory.
- A selector satisfying a global additive condition returns status 0 without looking up or invoking a candidate.
- Otherwise, candidate discovery and callback results determine the returned 32-bit status.

These are established control-flow properties. The meanings of the selectors, candidates, status codes, and conditional post-success dependency are not established.

## Interface

### Inputs

The function takes two arguments:

1. **Input object address.** A value used as an address in the represented 32-bit address space. Zero has explicit handling. Every nonzero value is treated as an object address without further validation.
2. **Opaque argument.** A 32-bit value forwarded unchanged as the callback’s third argument. This function neither interprets nor dereferences it.

### Output

The function returns a 32-bit unsigned status.

Established return possibilities include:

- 6 for a zero input object address.
- 0 for the additive bypass condition or a successful callback.
- 7 when candidate discovery initially produces no candidate.
- Any other 32-bit value returned by a callback, subject to the retry rule below.

Status interpretation is not uniformly based on the entire word: success requires the entire status to be zero, whereas retry eligibility depends only on the least significant eight bits.

### Referenced layouts

The supplied representation uses 32-bit address-bearing and data fields. Offsets below are byte offsets.

| Object or storage | Offset | Use |
|---|---:|---|
| Input object | +4 | Address of a first linked object |
| First linked object | +0x60 | Address of a second linked object |
| Second linked object | +4 | Context address |
| Input object | +0x48 | 32-bit selector |
| Context | +0x9c | Initial traversal-state word for the direct-selection path |
| Context | +0xa4 | Initial candidate address for the direct-selection path |
| Candidate | +0x44 | Callback address |

Two global 32-bit words also participate:

- **Additive gate word:** combined with the initial selector to decide whether candidate processing is bypassed.
- **Direct-selection discriminator:** compared with the initial selector to choose between context-resident candidate selection and dependency-based selection.

These labels describe their observed uses, not their application-level meanings.

The callback receives, in order:

1. The candidate address.
2. The original input object address.
3. The opaque second argument.
4. A zero-valued fourth argument.

Its return is consumed as a 32-bit unsigned status.

### Preconditions

Except for the explicitly supported zero input object, the caller must provide accessible memory for all fields actually reached on the chosen path. Candidate callback slots must contain callable addresses compatible with the observed invocation.

No bounds checks, pointer validation, callback-presence checks, synchronization, or recovery from invalid memory access are visible. Requirements for alignment, calling convention, concurrency, and dependency-specific object validity remain undocumented.

## Behavior

### Entry and context acquisition

A zero input object causes immediate return of 6. No context traversal, selector read, global comparison, lookup, or callback occurs on that path.

For a nonzero input object, the function obtains the context before evaluating whether candidate processing is necessary. The observable object-field read order is:

1. Read the address at input-object offset +4.
2. Read the address at offset +0x60 of that linked object.
3. Read the context address at offset +4 of the resulting object.
4. Read the selector at input-object offset +0x48.

Consequently, the additive bypass does not make invalid context-link memory acceptable. The context address is acquired through the link chain even when no candidate will subsequently be used.

The context address is retained for later dependency calls. This function does not retraverse the input object’s links after callbacks or lookups.

### Additive bypass

The initial selector is added to the additive gate word. If that sum is zero, the function returns 0 without performing candidate selection.

This is an additive condition, not a direct comparison with the global word. In particular, selector zero does not by itself establish the bypass.

The represented operands are 32-bit words. Under 32-bit wrapping arithmetic, the condition is satisfied when the selector is the additive inverse of the gate word modulo 2³². The supplied representation does not independently establish signed-overflow semantics; cases relying on overflow are therefore conditional on that machine-arithmetic interpretation.

The direct-selection discriminator is not needed on the bypass path.

### Initial candidate selection

When the additive condition does not bypass processing, the function initializes a local 32-bit traversal-state word to zero and records that no retry has yet occurred.

It compares the saved initial selector with the direct-selection discriminator:

- **Equal:** it first reads the context’s +0x9c word into the traversal state, then reads the candidate address from context offset +0xa4. No initial lookup dependency is called.
- **Unequal:** it calls F-232987963725 with the retained context address, the saved initial selector, and the address of the traversal-state word. The returned value is used as the candidate address.

The initial selector is the value already read from the input object. It is not read again for this comparison or for the initial lookup.

After initial selection, the status is set to 7. If the candidate address is zero, the function returns 7. There is no callback and no post-success dependency call.

### Candidate invocation and status handling

For each nonzero candidate, the function reads the callback address from candidate offset +0x44 and invokes it with the four arguments specified above.

The callback’s complete 32-bit return replaces the current status.

The subsequent decision order is significant:

1. **Whole-word zero:** candidate processing succeeds immediately.
2. **Nonzero with least significant byte other than 0x13:** return the complete status immediately.
3. **Nonzero with least significant byte equal to 0x13:** perform a retry lookup.

For example, 0x00000113 and 0xffffff13 both request a retry. Their upper 24 bits are not normalized or discarded in the retained status.

There is no visible retry limit, candidate-identity check, or cycle detection.

### Retry lookup

After a retry-eligible callback return, the function:

1. Reads the selector again from input-object offset +0x48.
2. Calls F-232987963725 with the retained context address, this freshly read selector, and the address of the same traversal-state word.
3. Uses the dependency’s return as the next candidate.
4. Records that a retry has occurred.

A retry always uses F-232987963725. It does not repeat the additive gate or the direct-selection comparison, even if the freshly read selector would satisfy either condition.

The traversal-state word persists across lookup calls. This function does not reset it between retries. Its contents may originate from zero initialization, the context’s +0x9c field, or dependency writes.

If retry lookup returns zero, candidate processing ends and the most recent callback status is returned unchanged. The function does not replace that status with 7. Since the lookup followed a retry-eligible callback, the returned status is nonzero and has least significant byte 0x13.

If retry lookup returns a nonzero candidate, the invocation and status-handling process repeats.

### Successful completion

A callback returning whole-word zero ends candidate traversal.

- If no retry has occurred, the function returns 0 without calling F-980cb99658b6.
- If at least one retry has occurred, the function calls F-980cb99658b6 with the retained context address and the candidate whose callback succeeded, then returns 0.

The represented success branch also checks that the candidate is nonzero before making this dependency call. Ordinary entry into a callback already requires a nonzero candidate.

The result of F-980cb99658b6 is not used to determine the returned status. Normal completion of that dependency is required to reach the final return.

Whether initial selection was direct or dependency-based does not determine this post-success behavior. The controlling fact is whether a retry occurred.

## Side effects

### Reads and writes performed directly

The function directly reads the linked-object fields, selector, relevant global words, context fields on the direct-selection path, and callback slots described above.

Its explicit writes are to local state: traversal state, current status, current candidate, and retry tracking. No direct write to an input-object field, context field, candidate field, or global word is shown.

The address of the local traversal-state word is passed to F-232987963725. That dependency can affect subsequent lookups through writes to the word. The contract does not assign a meaning to those contents.

### Dependency effects and mutation visibility

Callbacks and dependencies may have effects not shown here. No preservation of globals, object fields, context contents, or memory ownership is assumed.

This matters observably:

- The input selector is reread after every retry-eligible callback.
- The retained context address is reused, rather than reacquired through potentially modified links.
- The additive gate and direct-selection discriminator are not reevaluated during retries.
- A returned candidate’s callback slot is read when that candidate is processed; no callback address is cached across iterations by this function.

The local traversal-state address is exposed to a dependency during lookup. Whether the dependency retains that address is unknown. Valid use after this function returns is not established.

### Ownership and error handling

The function contains no explicit allocation or deallocation.

F-980cb99658b6 must not be assumed to release, retain, transfer, or finalize ownership merely because it is called after some successful retries. Its actual ownership effects are unknown.

No exception, fault, nonlocal-exit, or dependency-failure recovery mechanism is visible. A callback’s nonzero status is treated according to the byte-level rule, not automatically as a terminal error.

## Acceptance examples

These are conditional behavioral examples derived from static evidence, not executed tests. They assume valid accessed memory and normally returning dependencies.

1. **Null input.** Given input object address zero, the result is 6. Neither dependency nor any callback is invoked.

2. **Additive bypass.** Given a nonzero input object whose context links are readable and whose initial selector plus the additive gate word is zero, the result is 0. Context-link and selector reads still occur. No candidate selection occurs.

3. **No initial candidate through lookup.** Given a non-bypassed selector unequal to the direct-selection discriminator, if F-232987963725 initially returns zero, the result is 7. The traversal state supplied to that call initially contains zero.

4. **No direct candidate.** Given a non-bypassed selector equal to the discriminator, if context offset +0xa4 contains zero, the result is 7. The context’s +0x9c word is read before the candidate field.

5. **Immediate success.** Given any nonzero initial candidate whose callback returns 0, the result is 0. F-980cb99658b6 is not called, including when the candidate came from F-232987963725.

6. **Immediate terminal status.** If the first callback returns 0x00000112, that exact value is returned. No retry lookup or post-success operation occurs.

7. **Retry exhaustion preserves status.** If a callback returns 0x00000113 and the following lookup returns zero, the result is 0x00000113, not 7 or 0x13.

8. **Retry followed by success.** If a callback returns 0x13, lookup returns another nonzero candidate, and that candidate’s callback returns 0, F-980cb99658b6 receives the retained context and the successful candidate before the function returns 0.

9. **Selector mutation affects retries.** If a callback changes the input object’s selector before returning a retry-eligible status, the next lookup receives the changed selector. Even if it now matches the direct-selection discriminator, the retry still uses F-232987963725.

10. **Repeated candidate is permitted.** If lookup repeatedly returns the same candidate and its callback repeatedly returns a status ending in byte 0x13, the function continues. No termination guarantee follows from this function alone.
