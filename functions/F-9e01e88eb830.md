# F-9e01e88eb830

## Purpose

F-9e01e88eb830 performs a dependency call, updates selected bytes of a caller-supplied object, and records that object’s address in a shared registry.

For a non-null object, the function selects the first zero-valued entry among four inspected registry entries. If none is zero, it selects the immediately following entry without inspecting it. It stores the selected index in the object and writes the object’s address into the selected registry entry.

This is not an established capacity-checked registration API. In particular, four occupied inspected entries do not cause an error return.

The interpretation of the object as a registration record and the three cleared bytes as initialization state is inferred intent. The byte writes, registry search, and address publication are established static behavior.

## Interface

### Inputs

The function takes two inputs:

- **Object address:** a byte-addressable pointer. Null is explicitly recognized. For a non-null address, the supplied body accesses bytes through offset `0xEFA`, inclusive.
- **Tag byte:** an 8-bit value stored at object offset `0`.

The function also consumes two externally supplied values:

- **Dependency argument:** a shared value read and passed as the second argument to F-c67cb20988a1.
- **Registry base:** a shared address read after the dependency returns and after some object writes. It identifies the registry storage used by this invocation.

These are descriptive labels, not additional parameters. Their initialization, synchronization, and validity are not established by the supplied evidence.

### Output

The function returns a 32-bit result:

| Condition | Result bit pattern |
|---|---|
| Object address is null | `0xFFFFFF93` |
| Non-null execution reaches the end | `0x00000000` |

Under signed 32-bit interpretation, `0xFFFFFF93` is −109. The evidence does not establish a symbolic error name.

The dependency’s return value is not used to determine this result. A successful return means that execution reached the final return, not that an inspected registry vacancy necessarily existed.

No clearing of the intervening bytes is shown.

### Registry layout and widths

Registry entries are inspected at byte displacements `0`, `4`, `8`, and `12` from the captured registry base. Each inspection is a 32-bit comparison against zero.

The selected entry receives the object address. The supplied representation is consistent with a 32-bit address model: the entry stride and inspected integer width are both four bytes. The underlying target ABI is not independently provided; pointer width and address encoding remain an ABI assumption rather than separate runtime evidence.

Within that model:

- A selected index from 0 through 3 addresses an inspected entry.
- A selected index of 4 addresses displacement `16`.
- The full-prefix case requires writable storage through displacement `19`.

Alignment and addressability must meet the target’s requirements for the registry word accesses.

## Behavior

### Null-input path

The first decision is whether the object address is null.

If it is null, the function immediately returns `0xFFFFFF93`. On this path, the supplied body does not:

- Call F-c67cb20988a1.
- Read either shared value.
- Write object bytes.
- Inspect or modify the registry.

The tag byte has no effect on this path.

### Non-null preparation

For a non-null object, the function reads the shared dependency argument and calls F-c67cb20988a1 with:

1. The object address.
2. The value read from that shared argument.

No assumptions are established about what this dependency reads, writes, allocates, releases, or preserves. All subsequent behavior described here is conditional on that call returning normally and leaving the later accesses valid.

After the dependency returns, direct operations occur in this order:

1. Store the supplied tag byte at object offset `0`.
2. Store zero at object offset `0xEF8`.
3. Store zero at object offset `0xEF9`.
4. Read and capture the shared registry base.
5. Store zero at object offset `0xEFA`.

The position of the registry-base read is significant. The function uses the value available after the dependency and the first three object writes. It does not use a base captured before the dependency. Conversely, it does not reload the base after clearing offset `0xEFA`.

These are the access-order relationships represented by the supplied body. They do not establish atomicity or a hardware memory-ordering guarantee.

### Registry selection

Using the captured base, the function inspects entries in increasing index order, starting with index 0.

- A zero-valued 32-bit entry ends the search.
- A nonzero entry advances the candidate index.
- At most four entries are inspected.
- If all four inspected entries are nonzero, the selected index is 4.

The index range is therefore exactly 0 through 4. Its subsequent conversion to an 8-bit stored value loses no information.

The index arithmetic is bounded: the displacement used for registry access is at most `4 × 4 = 16` bytes. This arithmetic does not establish that the resulting address is valid or that a fifth entry belongs to the registry.

The search does not:

- Inspect entry 4 before selecting it in the full-prefix case.
- Search beyond entry 3 for a vacancy.
- Detect an existing occurrence of the object address.
- Reserve a zero entry before later writes.
- Recheck the selected entry before publication.

### Index storage and publication

After selecting the index, the function:

1. Stores that index at object offset `1`.
2. Writes the object address into the selected registry entry.
3. Returns zero.

The index byte is written before the registry entry. There is no separate occupancy update or success flag.

When the first four entries are occupied, the write at index 4 is unconditional. An existing value there is overwritten if the location is writable. Whether that location is a legitimate fifth entry, reserved overflow storage, or outside the intended registry is not established.

### Aliasing and intervening changes

No non-aliasing guarantee appears in the supplied evidence.

If object storage overlaps registry storage, the object writes preceding the search may alter entries that the search subsequently reads. The stored index byte may also alter registry storage after selection but before the final address write.

If an object write overlaps the storage holding the shared registry base, writes before its capture can affect which base is used. A later overlapping write does not cause a reload.

Accordingly, statements about the object retaining all assigned byte values at return require non-overlapping storage. The established behavior is the ordered sequence of writes, not an unconditional final-memory layout under arbitrary aliasing.

Concurrent modification is likewise unspecified. The supplied body contains no lock, atomic reservation, or retry.

## Side effects

For an ordinary non-overlapping execution that returns normally, direct side effects are:

- One call to F-c67cb20988a1.
- Five one-byte object writes.
- Up to four 32-bit registry reads.
- One registry address write.

The function itself shows no allocation, deallocation, reference-count adjustment, or explicit ownership transfer. However, the dependency’s ownership behavior is unknown and must not be inferred from that absence.

The registry receives the caller-supplied address, not a copy of the object. Subsequent users of that entry may therefore depend on the object remaining valid. The evidence does not define who is responsible for that lifetime or how registration is undone.

No rollback is shown. If an access cannot complete after earlier writes have occurred, those earlier effects have already been attempted. The outcome of invalid addresses, misalignment, protection failures, or dependency failure is not defined as a function-level error result.

The only explicit error return is the null-object result. Registry exhaustion within the four inspected entries is not reported as an error.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, assume a normally returning dependency, valid suitably aligned storage, a 32-bit address model, no relevant aliasing, and no concurrent mutation. Registry states describe memory when the scan begins.

### Null object

Given a null object and any tag byte:

- Return `0xFFFFFF93`.
- Do not call F-c67cb20988a1.
- Do not access the registry or write object storage.

### First entry vacant

Given registry entry 0 equal to zero:

- Inspect entry 0 and stop searching.
- Store index byte 0 at object offset `1`.
- Write the object address into registry entry 0.
- Return zero.

Entries 1 through 3 are not inspected by this search.

### Vacancy after occupied entries

Given entries 0 and 1 nonzero and entry 2 zero:

- Inspect entries 0, 1, and 2 in that order.
- Do not inspect entry 3.
- Store index byte 2.
- Replace entry 2 with the object address.
- Return zero.

### Four occupied entries

Given entries 0 through 3 all nonzero, with writable storage for entry 4:

- Inspect exactly entries 0 through 3.
- Select index 4 without reading entry 4.
- Store index byte 4.
- Overwrite entry 4 with the object address.
- Return zero.

If entry 4 is outside valid storage, no normal error-return behavior is established.

### Duplicate object address

Given entry 0 already contains the object address and entry 1 is zero:

- Treat entry 0 as occupied.
- Select entry 1.
- Store the same object address in entry 1.
- Leave the existing occurrence in entry 0 unchanged under the non-aliasing assumptions.

The function does not deduplicate registrations.

### Dependency changes the registry base

If F-c67cb20988a1 changes the shared registry base and returns normally, the later capture uses that changed base, unless an intervening object write changes it again through aliasing.
