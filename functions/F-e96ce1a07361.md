# F-e96ce1a07361

## Purpose

F-e96ce1a07361 delegates an operation to an indirectly selected dependency and, when that dependency returns zero, publishes eight byte-derived quantities and several additional fields into a caller-supplied record.

The established behavior is structural: obtain a receiver from the record, invoke its selected operation with caller data and output-storage addresses, then conditionally update the record. The meanings of the quantities, the operation being requested, and the final constant-like value are not established.

The multiplication of byte-derived values by 64 suggests a scaled numeric representation. That interpretation is inferred intent, not an established unit or semantic type.

## Interface

The function accepts four arguments and has no explicit return value.

| Argument | Role established by the supplied representation |
|---|---|
| A | Address-bearing value used to read a 32-bit field at offset `0x70`. |
| B | Address-bearing value identifying the record to inspect and potentially update. |
| C | Opaque 32-bit value forwarded to the dependency without local interpretation. |
| D | Unsigned 32-bit value forwarded to the dependency. Bit `0x10` also controls two successful-result fields. |

The representation uses four-byte fields for address-bearing values, opaque words, and the main result fields. This contract describes that apparent 32-bit layout; it does not establish portability to another address width or ABI.

### Record and receiver layout

Offsets are byte offsets from the applicable base address.

| Base | Offset | Width | Local use |
|---|---:|---:|---|
| A | `0x70` | 4 bytes | Read and passed as the dependency’s second argument. |
| B | `0x04` | 4 bytes | Read to obtain receiver R. |
| R | `0x210` | 4 bytes | Read to obtain dispatch-table address T. |
| T | `0x48` | 4 bytes | Read to obtain the indirect operation address. |
| R | `0x68` | 4 bytes | Read and passed as the dependency’s fifth argument. |
| B | `0x4C` | Not established | Its address is passed as the dependency’s sixth argument. |
| B | `0x18`–`0x34` | Eight 4-byte fields | Updated only after a zero dependency result. |
| B | `0x48` | 4 bytes | Receives a value read from an external datum after successful numeric-field updates. |
| B | `0x64` | 4 bytes | Receives an unscaled, extended byte-derived value on success. |
| B | `0x68` | 4 bytes | Receives another unscaled, extended byte-derived value on success. |
| B | `0x6C` | 2 bytes | Cleared on success. |
| B | `0x6E` | 2 bytes | Cleared on success. |

The receiver field at `R + 0x68` and the result field at `B + 0x68` are distinct accesses unless the supplied addresses happen to alias.

### Preconditions

Normal completion requires:

- The initial record field, receiver fields, dispatch-table slot, and caller field to be readable.
- The selected operation address to be callable under the applicable ABI.
- The successful-result destinations to be writable if the dependency returns zero.
- The dependency to satisfy the validity requirements of every address it uses.
- The dependency to initialize the scratch bytes consumed after a zero result.

There are no explicit null checks, bounds checks, alignment checks, or output-initialization checks. Invalid storage or an invalid indirect target is not converted into a locally reported error.

No non-aliasing guarantee is established. If caller storage, receiver storage, output storage, or external state overlap, the access ordering below governs what this function itself does.

## Behavior

### 1. Receiver and operation selection

The function reads the four-byte field at `B + 0x04` to obtain R.

It obtains the operation address through the four-byte field at `R + 0x210` and the slot at offset `0x48` within that dispatch table.

It also obtains:

- The four-byte value at `A + 0x70`.
- The four-byte value at `R + 0x68`.

These accesses precede the dependency invocation. The supplied representation does not establish a complete relative ordering among dispatch resolution and the argument-value reads. A consumer must not rely on an unstated ordering between otherwise independent pre-call reads.

The receiver used throughout this invocation is the value obtained from the initial read of `B + 0x04`. The function does not visibly reload that record field after the dependency returns.

### 2. Dependency invocation

The selected operation is invoked once with these seven arguments, in this argument-position order:

1. R.
2. The four-byte value read from `A + 0x70`.
3. C.
4. D.
5. The four-byte value read from `R + 0x68`.
6. The address `B + 0x4C`.
7. An address identifying temporary output storage for eight byte-sized quantities.

For this specification, the temporary quantities are labeled q0 through q7 in the apparent consecutive layout beginning at the supplied temporary-storage address. These are specification labels, not semantic names.

The operation’s return value is compared with zero. Only that comparison is used locally.

The sixth argument points directly into the caller’s record. It is not a private copy. Writes the dependency makes through that address can therefore remain visible whether the dependency reports success or failure.

### 3. Nonzero dependency result

If the dependency returns any nonzero value, this function performs no subsequent explicit record updates and returns without a result value.

This is not a rollback guarantee. The dependency may already have changed the record, receiver, external state, or other accessible memory. Its exact return value is not propagated to the caller.

### 4. Zero dependency result

If the dependency returns zero, the function performs the following updates in the listed order:

1. Store a two-byte zero at `B + 0x6E`.
2. Store a two-byte zero at `B + 0x6C`.
3. Write the eight scaled result fields listed below, in increasing destination-offset order.
4. Read an external four-byte datum and store its value at `B + 0x48`.
5. Write the selected unscaled value at `B + 0x64`.
6. Write the selected unscaled value at `B + 0x68`.

The clearing order is `0x6E` before `0x6C`, not ascending address order.

#### Scaled fields

Each scaled destination is four bytes wide. Each source is extended to a 32-bit value before the represented six-bit left shift.

| Destination | Source | Extension represented |
|---|---|---|
| `B + 0x18` | q1 | Unsigned byte to unsigned 32-bit value |
| `B + 0x1C` | q0 | Unsigned byte to unsigned 32-bit value |
| `B + 0x20` | q2 | Plain character to signed 32-bit integer |
| `B + 0x24` | q3 | Plain character to signed 32-bit integer |
| `B + 0x28` | q4 | Unsigned byte to unsigned 32-bit value |
| `B + 0x2C` | q5 | Plain character to signed 32-bit integer |
| `B + 0x30` | q6 | Plain character to signed 32-bit integer |
| `B + 0x34` | q7 | Unsigned byte to unsigned 32-bit value |

The first two destinations reverse the first two scratch-byte positions: q1 precedes q0 in the destination layout.

For the explicitly unsigned sources, the numerical result is exactly the source value multiplied by 64. The possible range is 0 through 16,320 inclusive. There is no 32-bit overflow in that range.

The supplied representation distinguishes q2, q3, q5, and q6 as plain characters rather than explicitly unsigned bytes. Their treatment above `0x7F` depends on an unresolved character-signedness and target-semantics question. Under a signed-eight-bit interpretation with the ordinary sign-extended shift behavior, their mathematical scaled range is −8,192 through 8,128. Under an unsigned interpretation, it is 0 through 16,320. Both ranges fit in 32 bits.

No saturation, clamping, rounding, or wider intermediate arithmetic is shown.

#### External value

After writing the eight scaled fields, the function obtains the current four-byte value of an external datum and copies it into `B + 0x48`.

The value is not visibly captured before the dependency call. A dependency-induced change to that datum can therefore affect the value copied on success. Its identity, value, and semantic meaning are unknown.

#### Flag-selected unscaled fields

Only bit `0x10` of D affects local post-call behavior.

| Condition | Value at `B + 0x64` | Value at `B + 0x68` |
|---|---|---|
| `(D & 0x10)` is zero | Extended q2 | Extended q3 |
| `(D & 0x10)` is nonzero | Extended q5 | Extended q6 |

These two values are not multiplied by 64. They are stored as four-byte integers using the same plain-character conversion issue described above.

The flag does not alter the source selection for any of the eight scaled fields. Other bits of D are still forwarded unchanged to the dependency and may matter there.

## Side effects

The function has two side-effect phases:

- The dependency invocation, whose complete effects are unknown.
- The successful-result publication, consisting of the explicit ordered stores above.

The successful update is not shown as atomic or transactional. It consists of separate writes, including two separate two-byte clears and multiple four-byte stores. No locking, synchronization, memory barrier, or concurrent-observer guarantee is established.

There is no explicit allocation, deallocation, resource acquisition, or resource release in the local behavior. This does not establish that the dependency avoids those actions.

The temporary output storage is supplied for use during the call. No ownership transfer or permission to retain its address is established. Its lifetime does not provide a usable post-return storage guarantee.

The direct record address `B + 0x4C` has caller-controlled lifetime. The dependency’s permitted write extent and any retention of that address are unknown. The function neither copies that region back afterward nor restores it on failure.

If the dependency does not return normally, the shown successful-result sequence is not reached. No local recovery mechanism is present.

### Selection flag set

With the same temporary bytes and bit `0x10` set, all eight scaled fields remain as above. The unscaled fields instead receive 6 at `B + 0x64` and 7 at `B + 0x68`.

### Nonzero dependency result

Assume the dependency returns a nonzero result after modifying storage through its sixth argument. The function must not perform its successful-result clears or publications. The dependency’s earlier modification is not undone.

### Unsigned-byte boundary

If q1 is 255 and the dependency returns zero, `B + 0x18` receives 16,320, not −64. That source is explicitly unsigned in the representation.

### Conditional character boundary

If q2 has byte pattern `0xFF`, the dependency returns zero, and bit `0x10` is clear:

- Under signed-eight-bit, sign-extended shift semantics, `B + 0x20` receives −64 and `B + 0x64` receives −1.
- Under unsigned plain-character semantics, those values are 16,320 and 255.

Selecting one outcome unconditionally requires additional target evidence.

### Dependency changes the external datum

If the dependency changes the external datum and returns zero, and no later change intervenes, `B + 0x48` receives the changed value. The function does not use an explicitly saved pre-call value.
