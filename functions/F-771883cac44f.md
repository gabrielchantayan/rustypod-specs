# F-771883cac44f

## Purpose

F-771883cac44f performs count-controlled dispatch through an object’s indirect operation table. Each complete pair of count units causes one operation with a two-byte input datum. A remaining single unit causes a different operation without an input datum.

The supplied static representation establishes this dispatch pattern, not its application-level meaning. In particular, it does not establish whether the count measures bytes, characters, output positions, or another quantity. It also does not establish what either indirect operation does with the supplied arguments.

On normal completion, the function returns a four-byte zero. It does not report the indirect operations’ results.

## Interface

### Inputs

The function receives three arguments:

1. **Receiver address.** An address identifying storage used both for dispatch and as the first argument to each indirect operation.
2. **Datum address.** An address to a sequence of two-byte values. One value is read for each complete pair of count units.
3. **Count.** An unsigned count controlling the number and kinds of indirect operations.

The represented interface uses four-byte integers and a four-byte return value, and two-byte datum elements. The receiver layout and dispatch expressions are consistent with a 32-bit address model. These widths describe the supplied representation; they are not a guarantee that the interface can be transplanted unchanged to a different ABI.

### Receiver layout

The function accesses two locations relative to the receiver:

| Byte offset | Represented content | Use |
|---|---|---|
| `0x00` | Dispatch-table address stored in the receiver’s first four-byte word | Locates the indirect operation for each invocation |
| `0x4C` | Four-byte context value | Passed as the second argument to each indirect operation |

Within the table selected through the receiver’s first word:

| Byte offset | Use |
|---|---|
| `0xA8` | Operation invoked once for every complete pair of count units |
| `0xA4` | Operation invoked for a remaining single count unit |

The context value’s meaning is unknown. It might represent an integer, address, handle, or another four-byte quantity. No interpretation or ownership rule is established.

### Output

Normal completion returns the four-byte value zero, regardless of the values returned by the indirect operations.

No additional output buffer or explicit status field is identified. Any externally visible work beyond this return value occurs through the indirect operations and their effects.

### Preconditions

For a zero count, neither input address is dereferenced by this function.

For a positive count:

- The receiver locations used for dispatch and context must be readable.
- The selected table slot must identify a callable operation with a compatible calling convention.
- The receiver, selected table, and context must remain usable whenever they are subsequently accessed.

For each complete pair of count units, the next two-byte datum must also be readable. A positive count of one does not require any datum access.

There are no explicit null, bounds, alignment, or dispatch-target checks. Exact alignment and address-validity requirements depend on the actual execution environment.

## Behavior

### Dispatch count and datum consumption

Let the initial unsigned count be \(N\). Define:

- \(Q = \lfloor N/2 \rfloor\)
- \(R = N \bmod 2\)

On normal completion, the function makes:

- \(Q\) invocations of the operation selected at table offset `0xA8`;
- followed by one invocation of the operation selected at table offset `0xA4` if \(R = 1\).

The function reads exactly \(Q\) two-byte datum elements through its own input-reading behavior. Those elements occupy a contiguous prefix of \(2Q\) bytes starting at the datum address.

An odd count does **not** cause a final one-byte input read. Its final operation receives no datum argument.

### Complete-pair operation

For each complete pair of remaining count units, the function obtains the currently selected operation from table offset `0xA8` and invokes it with:

1. The original receiver address.
2. The four-byte value currently stored at receiver offset `0x4C`.
3. The two-byte value currently stored at the current datum address.

The datum is read and passed as a value. Its address is not passed as an explicit argument.

After that invocation returns normally, the function advances its local datum cursor by two bytes and reduces its local count by two. It repeats while at least two count units remain.

The function does not snapshot the complete input sequence before making calls. A later datum read therefore occurs after preceding indirect invocations have returned. If an earlier invocation changes a later datum through some independently available alias, the later read observes the value present at that time.

### Remaining-single-unit operation

After all complete pairs have been processed, a nonzero remaining count is necessarily one.

In that case, the function obtains the operation selected at table offset `0xA4` and invokes it with:

1. The original receiver address.
2. The four-byte value currently stored at receiver offset `0x4C`.

There is no datum argument, no additional datum read, and no additional input-cursor advance for this operation.

### State is re-read between invocations

The function does not retain a single dispatch-table address or context value for the entire operation. Each invocation selects its operation through the receiver again and reads the context again.

Consequently, if an indirect operation changes the receiver’s dispatch-table address, a table entry, or the context field, those changes can affect subsequent invocations. The same applies to the final remaining-single-unit operation.

The receiver address itself remains the address supplied at entry. Replacing a field inside that receiver does not replace the receiver argument passed to later operations.

### Observable ordering

The following order is established:

- Each invocation’s target and arguments are obtained before that invocation begins.
- A complete-pair invocation returns before the next datum element is read by this function.
- Complete-pair invocations occur in ascending datum-address order.
- Any remaining-single-unit invocation occurs after all complete-pair invocations have returned.
- The zero return occurs only after all required invocations return normally.

The supplied representation does not establish a precise relative evaluation order among the target lookup, context read, and datum read for one invocation. A contract requiring one of those reads to occur first would exceed the evidence.

### Arithmetic boundaries

The count is treated as unsigned. Subtraction by two occurs only when the current count exceeds one, so the represented countdown does not underflow.

Under the represented 32-bit unsigned model:

- Zero causes no invocations.
- The greatest even count, `4,294,967,294`, requests `2,147,483,647` complete-pair invocations and no remaining-single-unit invocation.
- The greatest count, `4,294,967,295`, requests the same number of complete-pair invocations followed by one remaining-single-unit invocation.

These are dispatch-count properties, not guarantees that a valid input extent can exist in the target address space. Datum-cursor arithmetic is unchecked. Address overflow, inaccessible storage, or invalid pointer arithmetic is not converted into a defined error result.

## Side effects

The function’s own direct behavior consists of reading receiver state, reading selected table entries, reading datum elements, and invoking indirect operations. It contains no explicit write to receiver storage, input storage, or global storage.

Its cursor and countdown updates are local. The caller’s pointer variable and count variable are not updated through output parameters.

This does not make the function side-effect-free:

- Indirect operations may alter receiver fields, input storage, global state, devices, or other reachable resources.
- Their effects occur in invocation order.
- They may reenter this function or other code; no reentrancy protection is present.
- They may invalidate storage needed by later invocations; this function performs no subsequent validity check.

No direct allocation, release, ownership transfer, or lifetime extension is shown. Passing the receiver and context values does not establish that an indirect operation preserves, retains, or releases anything they identify.

There is no explicit error handling, retry, or rollback. An indirect operation’s return value does not select a failure path or stop subsequent dispatch. Abnormal termination or failure to return can prevent completion; the four-byte zero is promised only on normal completion.
