# F-0644ced486d8

## Purpose

F-0644ced486d8 conditionally processes a caller-supplied memory region, obtains two 16-byte blocks, invokes an in-place dependency, and conditionally invokes two final operations using addresses derived from the processed region.

**Established static behavior:** progress depends on two zero-result gates involving F-7f14f1ab6851. Each gate supplies two addresses and the literal length 20. The supplied evidence does not establish that this dependency compares bytes or tests equality. After both gates permit progress, the function invokes an in-place operation, applies a count-dependent identifier-presence gate, decodes an offset, and invokes the final dependencies. Normal completion returns zero.

**Inferred intent:** the gates resemble integrity checks, the two blocks resemble cryptographic material, and the in-place operation resembles decoding or decryption. These interpretations are not dependency contracts.

Two distinctions are essential:

- A successful identifier match permits continuation but does not select the matched table position for the subsequent offset lookup.
- The decoded length and count occupy local slots whose addresses have escaped to dependencies. Later uses read those slots again. Their values cannot unconditionally be treated as immutable header snapshots.

## Interface

The function accepts five arguments and returns a 32-bit value.

| Argument | Representation and established use |
|---|---|
| Requested identifier | Unsigned 32-bit value, denoted **Q**. Used in derivation selection and identifier comparisons. |
| Region base | 32-bit address-bearing value, denoted **A**. Represented as signed in the supplied interface, but used to construct memory addresses. |
| Region length | 32-bit value represented as signed, denoted **L**. Used in the leading computation length and trailer-address calculations. |
| Auxiliary argument | Opaque 32-bit value forwarded to F-0b61ef81b7eb. |
| Result argument | Opaque 32-bit value passed first to F-UNMAPPED-01 and then to F-0b61ef81b7eb. Its interpretation as an output address is inferred, not established. |

Return behavior:

- **Zero:** both final dependencies return normally.
- **0xFFFFFFE3:** the second zero-result gate rejects, or the identifier search terminates without a match. This is −29 under signed 32-bit interpretation.
- **A captured global 32-bit value:** the first zero-result gate rejects.

The global value is unknown and can numerically equal either other result.

## Behavior

### 1. Perform the first zero-result gate

The function invokes F-4836ae864413 with:

- source A;
- length L − 20;
- a local output address.

It then invokes F-7f14f1ab6851 with:

- that output address;
- A + L − 20;
- length 20.

After F-7f14f1ab6851 returns, the function reads a 32-bit value from global storage. This read occurs whether the gate result is zero or nonzero.

If the gate result is nonzero, the function returns the captured global value immediately. No header decoding, derivation, in-place processing, search, or final operation follows.

A zero result permits continuation. This establishes result handling, not byte equality. Any equality interpretation is conditional on an independently established contract for F-7f14f1ab6851.

### 2. Populate the header slots

The function invokes F-bbab973b3d34 twice, in order:

1. Source A, destination a local 32-bit **length slot**.
2. Source A + 4, destination a separate local unsigned 32-bit **count slot**.

The dependency’s encoding, source-access width, and byte order are unknown. Four-byte spacing between source addresses does not independently prove native 32-bit loading.

The slot addresses have now escaped. In particular:

- The second decoding call can affect a previously retained length-slot address.
- Later dependencies might also affect either slot through retained pointers or other unspecified side effects.
- The body does not copy both decoded values into immutable snapshots for all subsequent use.

For this contract, **current count** means the count-slot value at the particular read being described. **Current length** similarly means the length-slot value when passed to the in-place operation.

### 3. Select derivation input and concatenate two blocks

Immediately after header decoding, the function examines the count slot and selects an unsigned 32-bit derivation input:

| Count at selection | Derivation input |
|---|---|
| 0 | 1 |
| 1 | Q |
| 2 through 0xFFFFFFFF | That count |

Thus a count of one forwards Q, including Q = 0; it does not necessarily forward one.

F-aa2fc1ceb60a receives the selected value and two local output addresses. The function subsequently reads four 32-bit words from each output area, consuming 16 bytes from each.

Those reads populate a separate contiguous 32-byte local area:

- bytes 0–15 receive the first block;
- bytes 16–31 receive the second block.

No byte-order conversion is shown during these transfers. The dependency’s complete write extents and output meaning remain unknown.

The first block includes a word whose address was previously supplied as the first computation’s output address. These local uses therefore are not entirely disjoint. No preservation requirement across those calls is established.

The concatenated area reflects the block contents read during this copy. The original block addresses remain distinct from the concatenation and are passed later to the in-place dependency; their contents at that later time are not guaranteed to remain identical to the copied material.

### 4. Perform the second zero-result gate

F-4836ae864413 receives:

- the concatenated local area;
- length 32;
- another local output address.

F-7f14f1ab6851 then receives:

- that output address;
- A + L − 80;
- length 20.

If its result is nonzero, the function returns 0xFFFFFFE3. It does not invoke the in-place operation or either final dependency.

If its result is zero, execution continues.

The two trailer starting addresses are 60 bytes apart. The function body assigns no established meaning to the intervening bytes. Neither gate establishes byte equality without an additional dependency contract.

### 5. Invoke in-place processing using the current length slot

Define **B = A + 8**.

The function invokes F-58fc633ffe72 with six arguments, in order:

1. literal 1;
2. first block address;
3. second block address;
4. B;
5. the length-slot value read for this invocation;
6. B again.

The fifth argument is not unconditionally the value initially produced by the first header decoder. Header decoding, derivation, the second computation, and the second gate have intervened since that slot’s address escaped.

Supplying B in both the fourth and sixth positions establishes an in-place invocation pattern. It does not establish transformation semantics, access extent, or ownership.

The return value is ignored. There is no explicit transformation-error branch or rollback.

### 6. Apply the current-count selection gate

After the in-place dependency returns, the function reads the count slot.

If that read yields zero, it skips identifier searching and proceeds to offset decoding. This decision need not agree with the count used earlier for derivation.

Otherwise, it starts an unsigned 32-bit search index at zero. Before each candidate decoding call, the search condition reads the count slot again and requires the index to be less than that current count.

For an admitted index, F-bbab973b3d34 receives:

- source B + 4 × index;
- a separate local 32-bit candidate-output slot.

After the decoder returns, the candidate value is compared directly with Q.

- Equality immediately permits continuation.
- Inequality advances the index by one, followed by another current-count bound check.
- A bound check that fails before a match causes return of 0xFFFFFFE3.

This direct integer equality is established by the body; it is distinct from the undocumented semantics of F-7f14f1ab6851.

The search need not examine a fixed number of entries equal to an earlier count. A decoding call can affect a retained count-slot pointer, changing a later bound. No dependency preservation contract rules that out.

The matching index is discarded for record addressing. Entries after the first match are not searched.

### 7. Decode an offset, then reread the count for record addressing

On either the zero-count bypass or successful-search path, the function reads the count slot to construct the offset decoder’s source address.

Let **N-before** be that read. The supplied address is:

**T = B + 4 × N-before**

F-bbab973b3d34 receives T and a local 32-bit offset-output slot. The offset slot is represented as signed in the supplied evidence.

After the decoder returns, the function reads:

- the count slot again, denoted **N-after**;
- the offset slot, denoted **O**.

It constructs the record base as:

**R = B + 4 × N-after + 20 × O**

The decoder already received the count-slot address during header decoding and might have retained it. Therefore N-before and N-after are not guaranteed to agree.

Only under count preservation across this call does the simpler relation hold:

**R = T + 20 × O**

No explicit branch rejects a negative O, an excessive count, an out-of-region address, or arithmetic overflow.

### 8. Invoke both final dependencies

Using the computed R, the function calls, in order:

1. F-UNMAPPED-01 with the result argument, R + 4, and literal length 16.
2. F-0b61ef81b7eb with R + 22, the result argument, and the auxiliary argument.

The first operation receives a source-like address covering offsets 4–19 if its length argument denotes bytes read. Copy semantics are not established.

The second supplied address is exactly R + 22, not R + 20 or R + 24. The body does not separately decode the first four bytes at R or assign a meaning to offsets 20–21.

The second call uses the previously computed record base. It does not recalculate that base from the count or offset slots after the first final call.

Neither final return value is inspected. If both calls return normally, the function returns zero.

## Side effects

### Observable order

2. First gate call.

4. Length-slot decoding, then count-slot decoding.
5. Derivation-input selection and derivation.
6. Block reads and local concatenation.
7. Computation over the concatenation.
8. Second gate call.
9. Current-length read for the in-place invocation.
10. In-place dependency.
11. Current-count zero test.
12. Repeated count-bound reads and candidate decoding, if searching.
13. Count read for the offset source address.
14. Offset decoding.
15. Count and offset reads for record construction.
16. First final operation.
17. Second final operation.
18. Zero return.

Branch rejection truncates this sequence. Dependency-internal reads, writes, callbacks, and global effects are unknown.

### Mutation, ownership, and failure

The in-place invocation precedes possible search failure. Returning 0xFFFFFFE3 therefore does not imply that the supplied region remains unchanged.

Earlier dependencies may also mutate externally visible state. Even first-gate rejection is not established as side-effect-free.

The result argument is forwarded to both final dependencies only after the selection gate permits continuation. No preservation contract establishes that its contents after the first operation survive the second operation.

The function body shows no explicit allocation, release, rollback, or ownership transfer. This does not establish that dependencies allocate nothing, release nothing, retain no pointers, or preserve globals.

### Aliasing and retained addresses

No overlap checks are present. If the first final operation writes through the result argument and overlaps memory later consumed by F-0b61ef81b7eb, the later operation can observe those writes. Exact behavior is documented_only pending dependency contracts.

Local output addresses also escape. The body’s subsequent reads remain authoritative; an output slot must not be modeled as permanently fixed merely because an earlier call populated it.

## Acceptance examples

These are conditional static expectations, not executed tests. All assume valid accesses, representable arithmetic, and normal dependency return unless stated otherwise. Examples using a stable count explicitly require its preservation over the relevant interval.

1. **First gate rejects.**  
   If the first gate returns nonzero and the following global read yields G, the function returns G. No header decoder or later-stage dependency is invoked. No byte-inequality conclusion follows from the gate result alone.

2. **Second gate rejects.**  
   If the first gate returns zero and the second returns nonzero, the function returns 0xFFFFFFE3 without invoking F-58fc633ffe72 or either final dependency.

3. **Stable zero count.**  
   If count is zero at derivation selection, derivation receives 1 regardless of Q. If count remains zero through the post-processing decision and offset-source calculation, no candidate search occurs and T is B. If it also remains zero during offset decoding, R is B + 20 × O.

4. **Stable one-entry case.**  
   If count remains one throughout and Q is 0x12345678, derivation receives 0x12345678. The candidate at B must decode to Q. Offset decoding then uses B + 4, and R is B + 4 + 20 × O.

5. **A match does not choose its own position.**  
   With count preserved at three, a match at the first candidate skips later candidates but still decodes the offset at B + 12. If O is two, R is B + 52. Final addresses are B + 56 and B + 74.

6. **Length-slot mutation changes the forwarded length.**  
   Suppose header decoding initially writes 64 to the length slot, but an intervening dependency changes it to 96 through a retained pointer. If execution reaches the in-place invocation, its fifth argument is 96, not the original 64.

7. **Derivation count need not govern searching.**  
   Suppose count is zero during derivation selection, so derivation receives 1. If the in-place dependency leaves count equal to two, identifier searching is required afterward; the earlier zero does not force a bypass.

8. **A changing bound can terminate searching early.**  
   Suppose the post-processing count is three. The first candidate does not match, and that decoder changes count to one. The next index is one, which is not less than the current count. The function returns 0xFFFFFFE3 without decoding a second candidate or invoking the final dependencies.

9. **Offset decoding can change the record base.**  
   Suppose a successful selection reaches offset decoding with N-before equal to three. The decoder receives B + 12. If it writes O = 2 and changes count to one, record construction uses N-after = 1: R is B + 44, and final addresses are B + 48 and B + 66. R is not T + 40.

10. **Negative offset has no rejection branch.**  
    With count preserved at one and O = −1, T is B + 4 and R is B − 16. If all required accesses remain valid, processing continues without a negative-offset error return.

11. **Final statuses are ignored.**  
    Any normally returned status values from the final dependencies leave the explicit return equal to zero. Faults, exceptions, or non-returning dependencies are not converted into a specified error result.
