# F-f1e9136c1049

## Purpose

F-f1e9136c1049 selects an indirect execution target through three dependent memory reads and transfers control to that target. Its sole supplied input is a signed integer used in an address calculation.

The lookup uses two fixed byte offsets: 1,072 bytes for the first storage location and 232 bytes for the final target slot. The intermediate values have distinct recovered types: an object pointer, a signed integer, and a code pointer. Their storage widths must not be treated as interchangeable.

The layout suggests method-like dispatch, but that interpretation is **inferred intent**, not an established application-level contract. The supplied representation establishes neither an object type nor a method identity.

## Behavior

### Lookup and selection

The established logical sequence is:

1. Add 1,072 to the signed-integer input.
2. Convert that integer result to an address suitable for reading an object pointer.
3. Read the object pointer.
4. Read a signed `int` at the address supplied by that object pointer.
5. Add 232 to that signed-integer value.
6. Convert the second integer result to an address suitable for reading a code pointer.
7. Read the code pointer and use it for indirect execution.

This sequence describes the observable lookup contract, not an implementation prescription.

The memory reads are data-dependent. The second location depends on the value obtained by the first read; the third location depends on the integer obtained by the second read. No independent destination lookup, cache, retry, or alternative target is visible.

The ordering establishes logical dependencies. It does not establish hardware barriers, atomic access, synchronization with other threads, or a consistent snapshot under concurrent mutation.

### Integer arithmetic and address conversion

Both additions occur in the recovered signed-`int` arithmetic **before** the corresponding conversion to a pointer:

- The first addition operates on the supplied signed integer and 1,072.
- The second addition operates on the signed integer read from memory and 232.

Neither addition is represented as pointer arithmetic. The offsets therefore must not be multiplied by an element size or by an object-pointer or code-pointer width.

The distinction matters even when the second integer is interpreted informally as a table-base address. It remains an integer operand at the point where 232 is added.

The supplied material does not independently establish the executable’s integer width, integer-to-pointer mapping, or overflow behavior. A reconstruction must not silently replace these operations with native-width pointer arithmetic, unbounded arithmetic, or assumed modular arithmetic.

For the portable portion of this contract, each sum must be representable in the applicable signed-`int` type, and each subsequent conversion must identify the required readable storage under the confirmed platform rules. Behavior requiring signed overflow, truncation, sign extension, or address wrapping is **documented_only** until the relevant target semantics are established.

This restriction does not claim that the original executable rejects such values. No rejection is visible; the missing information concerns what the executable actually does with them.
