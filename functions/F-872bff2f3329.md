# F-872bff2f3329

## Purpose

F-872bff2f3329 obtains one 24-byte slot from caller-supplied storage-management state and partially initializes that slot. It prefers a slot identified by a non-null reusable-slot pointer. Otherwise, it consumes the next slot in the current storage region, allocating a new region when the current position equals the region end.

The function has no explicit return value. Its observable results are updates to the management state, optional allocation and block-linking activity, and writes to the selected slot.

**Inferred intent:** this is an internal slot-acquisition operation for a block-backed pool with a reusable-slot chain. The listing does not establish how a caller subsequently obtains the selected slot, why the function has no returned pointer, or what the slot’s payload represents.

## Interface

### Input and representation

The sole argument is a pointer to mutable management state. The supplied listing uses four consecutive 32-bit fields:

| Byte offset | Contract name | Observed role |
|---|---|---|
| 0 | Block head | Address of the current block descriptor, or zero |
| 4 | Reusable head | Address of the next reusable slot, or zero |
| 8 | Current position | Address of the next slot available from the current region |
| 12 | Region end | Boundary address used to decide whether another region is needed |

These names describe observed use, not independently established application types.

A block descriptor occupies 12 bytes:

| Byte offset | Observed content |
|---|---|
| 0 | Previous block-descriptor address |
| 4 | Unsigned 32-bit slot capacity |
| 8 | Storage-region address |

Each slot occupies 24 bytes. The function accesses these parts of a selected slot:

| Byte offset | Width | Access |
|---|---|---|
| 0 | 1 byte | Written as zero |
| 4 | 4 bytes | Written as zero |
| 8 | 4 bytes | Written as zero |
| 12 | 4 bytes | Read as the next reusable-slot address on the reuse path; subsequently written as zero |

Slot bytes 1–3 and 16–23 receive no explicit writes from this function.

The supplied representation uses 32-bit address-bearing fields. This is not evidence that the routine can be transplanted unchanged into a wider-pointer environment. Byte order is not established and is unnecessary to describe the zero stores or the same-representation pointer transfers.

### Output

There is no explicit returned value, selected-slot pointer, or success indicator.

On a normally completed call:

- One reusable slot has been removed from the reusable chain, or the current position has advanced by 24 bytes.
- If allocation occurred, a new descriptor has been installed as the block head and the region end has been replaced.
- The selected slot has received the four initialization writes described below.

### Preconditions for defined, successful execution

The listing performs no validation. Safe execution therefore requires, as applicable:

- A valid management-state address with the required readable and writable fields.
- A non-null reusable head to identify a slot whose 32-bit link at offset 12 is readable and whose initialized fields are writable.

## Behavior

### 1. Prefer an existing reusable slot

The function first reads the reusable head.

If that address is nonzero:

1. That address becomes the selected slot.
2. The function reads the 32-bit value at selected-slot offset 12.
3. It writes that value to the management state’s reusable-head field.
4. It performs the common slot-initialization writes.

On this path, the function does not explicitly read the current-position, region-end, or block-head fields, and it does not call the allocation dependency.

The next reusable address is read before the selected slot’s offset-12 field is cleared. A zero next address empties the reusable chain. No check establishes that a nonzero next address is valid, distinct from the selected slot, or part of an acyclic chain.

### 2. Otherwise, examine the current region

If the reusable head is zero, the function reads the current position and compares it with the region end.

If the two addresses differ:

1. The current-position address becomes the selected slot.
2. The function writes selected-slot address plus 24 to the current-position field.
3. It performs the common slot-initialization writes.

The condition is equality, not an ordered bounds check. A current position beyond the end, below the region, or otherwise invalid still takes this path when it differs from the end.

No allocation occurs merely because the current position is null. For example, a null current position and a non-null region end cause selection of address zero, followed by an attempted advance and slot writes.

### 3. Allocate a region when the current position equals the end

When the reusable head is zero and the current position equals the region end, the function computes a new capacity.

It reads the block head:

- If the block head is zero, the new capacity is 32 slots.
- Otherwise, it reads the unsigned 32-bit capacity from block-descriptor offset 4 and computes two unsigned 32-bit candidates:
  - The old capacity plus 32.
  - The old capacity plus its logical right shift by one, plus its logical right shift by three.

It chooses the larger candidate using an unsigned comparison. Equal candidates produce the same capacity.

For ordinary non-overflowing values, this chooses the greater of a 32-slot increment and growth by approximately 62.5%. The actual operation uses separately truncated right shifts, not a single multiplication followed by division.

All capacity additions are 32-bit unsigned operations. Their results wrap modulo \(2^{32}\). The capacity is therefore not guaranteed to increase.

The function then calls F-871e64ddc6de twice, in this order:

1. Request size 12, with a second argument of zero.
2. Request size equal to the new capacity multiplied by 24, with a second argument of zero.

The multiplication is also evaluated at 32-bit unsigned width. Consequently, the requested storage size can wrap and need not represent the mathematical product of capacity and slot size.

After the calls, the following accesses occur in order:

1. Write the second call’s result to offset 8 of the newly obtained descriptor.
2. Read the management state’s block head and write it to descriptor offset 0.
3. Write the computed capacity to descriptor offset 4.
4. Write the new descriptor address to the management state’s block-head field.
5. Read the storage address back from descriptor offset 8 and select it as the slot address.
6. Write the selected storage address plus the computed 32-bit byte extent to the region-end field.
7. Write the selected-slot address plus 24 to the current-position field.
8. Perform the common slot-initialization writes.

The block-head value linked into the new descriptor is read **after both dependency calls**. It is not necessarily the same value examined before allocation to choose the capacity. No preservation of management state or other memory by the dependency is established.

### 4. Initialize the selected slot

Every path that reaches normal slot initialization performs these writes in this order:

1. Four zero bytes at selected-slot offset 4.
2. Four zero bytes at selected-slot offset 8.
3. Four zero bytes at selected-slot offset 12.
4. One zero byte at selected-slot offset 0.

This is partial initialization, not a 24-byte clear.

On the reusable path, the reusable head has already been updated before these writes. On either current-region path, the current position has already advanced before these writes.

## Acceptance examples

These are conditional behavioral examples derived from the listing, not runtime test results.

### Reusing a slot takes precedence over region exhaustion

Given a nonzero reusable head identifying slot A, with address B stored at A’s offset 12:

- The reusable head becomes B.
- A receives the ordered zero writes at offsets 4, 8, 12, and then byte 0.
- No allocation call occurs.
- Current position and region end are not explicitly accessed.

This remains the selected path even if the current region is exhausted.

### Consuming existing region space

Given a zero reusable head and a current position identifying slot A that differs from the region end:

- The current position becomes A plus 24.
- A receives the common initialization writes.
- The block head is not explicitly accessed.
- No allocation call occurs.

With ordinary disjoint storage, bytes 1–3 and 16–23 of A retain their prior contents.

### First region

Given a zero reusable head, equal current position and region end, and a zero block head:

- Capacity is 32.
- Dependency requests are 12 bytes and 768 bytes, each with second argument zero.
- If both calls return valid storage and preserve the relevant state, the descriptor records previous head zero, capacity 32, and the returned storage address.
- The region end becomes storage address plus 768.
- The current position becomes storage address plus 24.
- The first slot receives partial initialization.

### Capacity growth without overflow

For an existing capacity of 32, the two candidates are 64 and 52. The selected capacity is 64, producing a storage request of 1,536 bytes.

For an existing capacity of 64, the candidates are 96 and 104. The selected capacity is 104, producing a storage request of 2,496 bytes.

These results assume the capacity read before allocation supplies the stated value.

### Capacity arithmetic wraps

- Adding 32 produces 31 modulo \(2^{32}\).
- Adding the two shifted values produces 2,684,354,557 modulo \(2^{32}\).
- Unsigned comparison selects 2,684,354,557.

### Equality is the only exhaustion test

Given a zero reusable head and a current position numerically beyond, but unequal to, the region end, the function does not allocate or report a bounds error. It attempts to consume the current position as a slot.

Safe behavior in this case requires that selected address to be independently valid; the function provides no such guarantee.
