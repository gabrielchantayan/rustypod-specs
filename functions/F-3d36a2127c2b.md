# F-3d36a2127c2b

## Purpose

F-3d36a2127c2b obtains an address from an opaque dependency, makes requests using an aligned working address, and counts inspected 32-bit words whose low 28 bits are zero. The first successful request is inspected starting at the third word of the working area; later successful requests are inspected starting at the first word.

The signed return value is an accumulated count, not a completion status. Exhausting the address-acquisition attempts returns zero. A request returning zero stops traversal and returns the count accumulated before that request. Consequently, zero does not distinguish acquisition failure, an empty traversal, an unsuccessful first request, or a traversal with no matches.

“Acquisition,” “batch,” “extent,” and “budget” describe roles within this function, not established meanings of the external interfaces. In particular, the acquisition dependency receives numeric size arguments; their units are unknown. Interpreting those arguments as byte counts, and the dependency as a memory allocator, is inferred intent rather than an established contract.

## Interface

### Input object

The sole argument is a signed 32-bit value used as the address of an input object. The supplied representation uses 32-bit integers and addresses.

| Object offset | Access width | Established use |
|---|---:|---|
| `0x6c` | Unsigned 16 bits | Shifted right by one and supplied as the second argument to the initial F-d7be9cfb4000 call. |
| `0x78` | 16 bits | Supplied to F-052651f0e13e and freshly read for each F-a63889a8554d call. Signedness at those interfaces is not established. |
| `0x7c` | Signed 32 bits | Captured as the extent and supplied to the second F-d7be9cfb4000 call. |
| `0x80` | Signed 32 bits | Captured as the initial request position. |

The function performs no visible null-address, accessibility, bounds, or alignment checks. Each field must be readable when its access occurs. Not all fields are accessed on every path: total acquisition failure returns before reading offsets `0x78`, `0x7c`, and `0x80`.

The function does not directly write the input object. Dependencies are not assumed to leave it unchanged.

### Return value

The result is a signed 32-bit count:

- Zero when every acquisition attempt returns zero.
- Otherwise, the accumulated number of matching inspected words, if execution reaches the final return.

The interface returns neither the final position nor a success or completeness indicator. A nonterminating traversal returns nothing.

### Execution preconditions

A nonzero acquisition result must support the subsequent address calculations and accesses. Each successful request must leave the words that this function actually inspects readable. The visible function does not verify either condition.

Defined execution also requires valid pointer formation and comparison, and representable signed arithmetic where signed operations occur. Unsigned calculations have explicit modulo-\(2^{32}\) behavior, but this does not make all resulting addresses or signed conversions valid.

No dependency is assumed to return normally, preserve global state, preserve the input object, or establish any particular ownership relationship.

## Behavior

### Initial calculation

The accumulated count begins at zero.

The unsigned 16-bit field at offset `0x6c` is read and shifted right by one. F-d7be9cfb4000 then receives 512 as its first argument and the shifted value as its second argument. The second argument ranges from zero through 32,767. Odd input values lose their low bit; zero is not rejected.

The signed 32-bit result is retained as a scale for later inspection-size calculations. The dependency’s mathematical operation is unknown. The visible arguments do not establish division, rounding, or a special rule for a zero second argument.

### Address acquisition and fallback

The initial acquisition limit is 255. The first numeric size argument supplied to F-d33f6d597e5d is `0x1fe20`, equal to \(255 \times 512 + 32\).

A zero result is treated as acquisition failure. After failure:

- A limit below two causes an immediate zero return.
- Otherwise, the unsigned limit is halved with the remainder discarded, and another acquisition is attempted using \(512 \times \text{limit} + 32\).

If every attempt fails, the limits are 255, 127, 63, 31, 15, 7, 3, and 1, in that order. There are at most eight acquisition calls. The first nonzero result ends fallback and fixes the retained limit.

These are **numeric size arguments**, not established byte counts. Their relationship to later address use suggests a storage-size interpretation, but an opaque dependency could interpret them differently.

On total acquisition failure, there is no selection call, batch request, or cleanup call. The initial F-d7be9cfb4000 call has already occurred, so this return path is not necessarily free of dependency side effects.

### Setup after acquisition

After obtaining a nonzero result, the function reads offset `0x78` and calls F-052651f0e13e with that 16-bit value. Its return value is ignored.

The working address is obtained by adding 32 to the original acquired address using unsigned 32-bit arithmetic, then clearing the low five bits. The result has its low five bits zero. Without address wraparound, it lies between one and 32 bytes beyond the original address. An already aligned address advances by 32 bytes rather than remaining unchanged.

The original acquisition result is retained separately for eventual cleanup.

The initial excluded-word count is two. The function next reads the signed extent at `0x7c`, then the signed initial position at `0x80`. F-d7be9cfb4000 receives the captured extent and the retained scale. Its signed result is increased by one using signed arithmetic, and that value is assigned to an unsigned 32-bit budget.

The initial remaining extent is the captured extent minus one, also using signed arithmetic. Traversal begins only if that result is positive.

Selection and the second calculation occur even when traversal will be skipped, provided the preceding operations complete normally. A captured extent of one therefore produces no batch requests, but still reaches cleanup after these setup calls. An extent of zero also skips traversal after a representable decrement. The minimum signed extent does not have a representable signed decrement and is not assigned a wrapping interpretation by this contract.

Call and read ordering matters:

- F-052651f0e13e occurs before the extent and initial position are read.
- The second F-d7be9cfb4000 call occurs after both reads.
- Changes made by selection can affect those captured fields.
- Changes made by the second calculation do not cause the captured extent or position to be reread.
- Offset `0x78` is read again for every batch request.

### Batch selection and request

Every traversal iteration begins with a positive signed remaining extent.

The requested batch count is selected between the retained acquisition limit and the unsigned budget. The comparison uses their signed 32-bit interpretations: the acquisition limit is selected only when its signed interpretation is strictly less than the budget’s signed interpretation; otherwise, the budget is selected.

For budgets within the nonnegative signed range, this acts as a minimum. It is not an unsigned minimum for every possible budget. Converting a budget above `0x7fffffff` to signed requires target-specific behavior.

The candidate inspection count is the requested count multiplied by the retained scale, minus the current excluded-word count. Because the requested count is unsigned 32-bit, this arithmetic is unsigned and wraps modulo \(2^{32}\), including conversion of the other operands. The result is then assigned to a signed 32-bit inspection count. An unsigned result outside the signed range requires target-specific conversion behavior.

The inspection count is capped at the remaining extent using a signed comparison. Negative inspection counts are not rejected or raised to zero.

F-a63889a8554d receives these arguments, in order:

1. A fresh 16-bit read from offset `0x78`.
2. The current signed position.
3. The aligned working address.
4. The unsigned requested batch count.
5. Zero.

A zero return immediately ends traversal. That request contributes no inspected words and causes no position advancement, budget reduction, or remaining-extent reduction. Any modifications made by the dependency are not undone.

Every nonzero return permits inspection. No distinction among different nonzero results is visible, and no returned transfer length is consulted.

### Successful-request processing

After a nonzero request result, the position advances by the requested batch count. The addition is unsigned 32-bit arithmetic because the batch count is unsigned: the signed position is converted to unsigned, addition wraps modulo \(2^{32}\), and the result is converted back to signed. An out-of-range unsigned-to-signed conversion is target-dependent; the addition itself is not signed-overflow arithmetic.

The inspection start is the working address plus four bytes per excluded word. The end pointer is formed by advancing that start by the signed inspection count in units of 32-bit words.

Before inspecting words, the excluded-word count is set to zero and the unsigned budget is reduced by the requested batch count modulo \(2^{32}\).

Successive 32-bit words are read while the inspection cursor precedes the calculated end pointer. Each visit reads one word and advances the cursor by one word. A word contributes one to the signed accumulated count exactly when its low 28 bits are all zero. Its high four bits do not affect the predicate.

Under valid, non-wrapping pointer arithmetic with a nonnegative inspection count, exactly that many words are read. The first successful request begins inspection eight bytes beyond the working address; all later successful requests begin at the working address. The two-word exclusion applies once, not to every request.

The same storage may be inspected again after subsequent requests. There is no uniqueness check or deduplication.

After inspection, the signed remaining extent is reduced by the selected inspection count. Traversal continues only if the result is positive.

Progress is not enforced. A zero inspection count leaves the remaining extent unchanged. A negative inspection count can increase it, subject to signed-range limits, and may also make end-pointer formation invalid. The function provides no general safe behavior for such cases.

### Cleanup and return

If execution reaches traversal completion or exits because a request returned zero, F-5e3309c9d083 is called once with the original acquisition result. It does not receive the aligned working address. Its return value is ignored, and the accumulated count is returned.

A skipped traversal also reaches this call. Total acquisition failure does not.

Successful acquisition alone does not guarantee cleanup. Nontermination, a nonreturning dependency, or invalid intervening operations can prevent it. The call establishes a cleanup-shaped operation, not proof of resource release or restoration of external state.

## Side effects

The visible body reads input fields and inspected words but performs no direct stores into the input object or working storage. It updates its own count, position, budget, exclusion state, and remaining extent.

Dependencies may modify the input object, working storage, globals, external devices, or ownership state. Their call sites do not establish preservation guarantees.

The acquired address and working address have distinct uses:

- The aligned working address is supplied to batch requests and used for inspection.
- The original acquisition result is supplied to cleanup when cleanup is reached.
- Neither address is returned to the caller.

There is no visible byte-order conversion for inspected words. The predicate applies to the numeric 32-bit value obtained through the execution environment’s native representation. The supplied body alone does not establish endianness.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless an example addresses arithmetic or termination explicitly, arithmetic and storage accesses are assumed valid, and dependencies are assumed to return normally.

### Acquisition failure

If all acquisition attempts return zero, F-d33f6d597e5d receives numeric size arguments corresponding to limits 255, 127, 63, 31, 15, 7, 3, and 1. Each argument equals \(512 \times \text{limit} + 32\).

The initial F-d7be9cfb4000 call precedes these attempts. The function returns zero without selection, batch requests, or cleanup. This example establishes argument values, not their units.

### Successful acquisition with no traversal

If acquisition succeeds and the captured extent is one, selection and the second calculation still occur. The remaining extent becomes zero, no batch request occurs, cleanup receives the original acquired address, and the returned count is zero.

### First-request exclusion and matching

Suppose the scale is 128, the captured extent is five, the second calculation returns zero, acquisition succeeds, and the first request returns nonzero.

The budget is one, so the requested batch count is one. The candidate inspection count is 126, capped to the remaining extent of four.

Words at offsets 8, 12, 16, and 20 from the working address are inspected. If they contain, respectively, `0x00000000`, `0xf0000000`, `0x00000001`, and `0x10000000`, the returned count is three after cleanup. The words at offsets zero and four are excluded.

### Position wraps through unsigned zero

Suppose acquisition succeeds at limit one, the scale is four, the captured extent is seven, the second calculation returns one, and the initial position is negative one. Both required requests return nonzero.

The first request receives position negative one and count one. Unsigned position addition produces zero, so the second request receives position zero.

The first request contributes two inspected words after exclusion; the second contributes four without exclusion. If all six match, the returned count is six. This case does not require an out-of-range unsigned-to-signed conversion.

### Request failure after partial progress

If completed inspections have contributed seven matches and the next request returns zero, no words from that request are inspected. Cleanup is reached, and the result is seven without an indication that traversal ended early.

### Zero budget prevents progress

Suppose a later iteration has a positive remaining extent, no excluded words, and a zero budget. The selected batch count and inspection count are both zero.

If every subsequent request returns nonzero, no words are inspected and position, budget, remaining extent, and count remain unchanged. Traversal does not terminate, so cleanup is never reached.

If a later request returns zero instead, traversal stops and cleanup is reached.

## Uncertainties

The following remain **documented_only**:

- Semantic meanings of the object fields, extent, positions, batches, and inspected entries.
- Mathematical behavior of F-d7be9cfb4000.
- Units of the numeric size arguments supplied to F-d33f6d597e5d. Byte counts are plausible but unestablished.
- Actual acquisition, selection, transfer, release, and ownership behavior of dependencies.
- Whether nonzero request results guarantee initialized, readable inspection spans.
- Whether external contracts exclude negative scales, exhausted budgets, invalid spans, and nonprogress.
- Any intended relationship between the factor 512 in acquisition arguments and the scale used for inspected-word counts.
- Target behavior for out-of-range unsigned-to-signed conversions and invalid pointer operations.
- Whether traversal is guaranteed to terminate.

Unsigned alignment arithmetic, candidate-size arithmetic, position addition, and budget subtraction wrap modulo \(2^{32}\). Their results can still lead to unsupported addresses or target-dependent signed conversions.

The signed increment used to construct the initial budget, the initial extent decrement, subsequent extent subtraction, and match-count increments are separate signed operations. This contract does not assign them wrapping behavior when their mathematical results exceed the signed range.

## Evidence

Established behavior comes solely from static examination of the supplied function representation and opaque dependency mapping. No runtime tests have been performed.

The representation establishes field offsets and widths, dependency argument order, acquisition fallback values, alignment arithmetic, first-request exclusion, the low-28-bit predicate, partial-count returns, and the original-address cleanup argument.
