# F-c31857eba613

## Purpose

F-c31857eba613 searches up to 80 indexed key positions and, on the first successful comparison, copies one 32-bit payload to caller-designated storage. It returns the 32-bit value 1 after completing that write, or 0 after 80 unsuccessful comparisons.

The operation uses shared address-bearing state to locate the records. **The supplied representation does not establish a table base captured once per call or retained from a matching key access.** Each examined key address uses the shared base expression. After a successful comparison, the payload address uses that shared base expression separately.

With a stable base and stable relevant contents, this is a first-match lookup in an 80-record table. Without those stability conditions, the matching key and copied payload need not come from the same table instance.

The application meaning of the keys and payloads is not established.

## Interface

### Explicit inputs

- **Search key:** A 32-bit integer compared for equality with each reached key field. No ordering or range comparison is applied to key values.
- **Output address:** An address used for a single 32-bit write if a comparison succeeds. No existing destination value is read through this argument.

There is no explicit table argument, record-count argument, or table-size argument.

### Implicit input

Shared address-bearing state supplies the base expression used to address records. Its value is used separately for each key-address calculation and, on success, separately again for the payload-address calculation.

The representation does not establish the shared state’s initialization, ownership, lifetime, or permitted mutation.

### Return value

The result is a 32-bit quantity:

| Result | Meaning on normal completion |
|---|---|
| 1 | A key comparison succeeded, a payload was read, and the output write completed. |
| 0 | All 80 key comparisons failed; no payload copy was performed. |

There is no other normal return value in the supplied representation.

The return value is independent of the copied payload’s numerical value. A zero payload is compatible with a successful return of 1.

Invalid memory access is not translated into a failure result by any visible check or recovery mechanism.

### Record layout

Relative to the base used for a particular access, each indexed record has an 8-byte stride:

| Field | Offset within record | Width |
|---|---:|---:|
| Key | 0 bytes | 4 bytes |
| Payload | 4 bytes | 4 bytes |

For index \(j\), with \(0 \leq j < 80\):

- The key starts at offset \(8j\).
- The payload starts at offset \(8j+4\).

A complete table under a single stable base occupies 640 bytes. The final key starts at offset 632; the final payload starts at offset 636 and extends through offset 639.

These offsets describe the access layout. They do not establish pointer width, byte order, alignment requirements, or the representation of the shared address-bearing state.

### Preconditions for normal completion

Every reached evaluation of the shared base expression and every resulting key access must be valid in the execution environment. If a comparison succeeds, the separately addressed payload must be readable and the destination must support a 32-bit write.

A stable, suitably accessible 640-byte table is sufficient for the table accesses, but it is not necessary on every path. An early match avoids all later key accesses, and nonmatching records’ payload fields are not read.

If the shared base changes, validity must hold for the addresses actually selected by each separate use. Validity of the table used for the matching key does not establish validity of the subsequently selected payload address.

Neither sorted keys nor unique keys are required by the visible operation.

## Behavior

### Search order and bound

The search begins at index 0 and proceeds in increasing index order.

For each reached index, the function:

- Uses the shared base expression to address that index’s key field.
- Reads the 32-bit key.
- Compares it with the search key.

A failed comparison advances the index by one. After a failed comparison at index 79, the search ends and returns 0.

The search examines at most 80 keys. It does not examine index 80. No key or payload value acts as a terminator, and no table content changes the fixed search bound.

Increasing index order does not necessarily mean increasing physical addresses when the shared base can change between accesses.

### Shared-base evaluation and read ordering

The representation establishes the following logical access sequence:

1. The key address for the current index uses the shared base expression.
2. The addressed key is read and compared.
3. After a mismatch, the next index’s key address uses the shared base expression again.
4. After a match, the payload address uses the shared base expression separately from the use that addressed the matching key.
5. The selected payload is read before the destination is written.

There is no established single base value governing the entire call. Nor is there an established base retained from the successful key access for the payload access.

For a success at index \(j\), the represented path contains \(j+1\) key-address uses of the shared base expression followed by one payload-address use. A complete miss contains 80 key-address uses and no payload-address use.

These are representation-level ordering and evaluation facts, not claims about exact machine-load counts, compiler optimizations, cache transactions, or hardware atomicity.

### Successful comparison

After a key comparison succeeds at index \(j\), the function separately uses the shared base expression to address the payload at offset \(8j+4\). It reads that 32-bit payload, writes it to the output address, and returns 1.

No later key is examined, and there is no revalidation of the matching key.

If the shared base remains unchanged between the key and payload accesses, the payload address belongs to the same indexed record as the matching key. If the base changes between those accesses, the payload may instead come from index \(j\) under a different base. The key at that new location is not checked.

With a stable base and stable relevant contents throughout the search, the lowest-index matching record supplies the payload. Without those conditions, the unconditional guarantee is narrower: the first successful comparison ends the search, and the payload comes from the subsequently addressed payload position at that same index.

The payload is copied as a 32-bit quantity. No masking, conversion, arithmetic transformation, or application-level interpretation is shown.

### Complete miss

If all 80 comparisons fail, the function returns 0.

On this path:

- Exactly 80 indexed key accesses are represented.
- Each key address uses the shared base expression for that access.
- No payload field is read.
- No access is performed through the output argument.

With a stable base, these are the 80 key fields of one table. With a changing base, they may be key fields selected from different table instances.

The function’s own miss path does not modify output storage. A claim that its contents remain unchanged also requires that no external actor changes that storage.

### Integer and address arithmetic

The represented index is a 32-bit integer. It starts at 0, reaches at most 79 for an access, and becomes 80 after the final mismatch. The bound is 80, not a byte count.

The largest record-stride product used for an access is \(79 \times 8 = 632\). Adding the payload offset gives 636. These index-derived calculations do not overflow a 32-bit integer.

That does not establish safe address arithmetic for an arbitrary base. Address width, representability, object bounds, and memory-access rules remain environment-dependent preconditions.

Key matching uses equality. No reserved key value, sentinel, or significance of the key’s high bit is established.

## Side effects

The sole explicit store is the successful 32-bit payload write through the output address. A normally completing successful path performs one such store; a miss performs none.

The function has no explicit table-update operation. However, it does not check whether the output overlaps:

- A key field.
- A payload field.
- The shared address-bearing state.
- Other accessible storage.

Consequently, a valid successful output write can modify any of those locations if the destination aliases them. The payload read precedes that write. The function returns afterward without another table lookup or shared-base use.

If the destination is also storage read as the selected payload, that storage is read in its role as payload before being written in its role as destination. The absence of a destination read through the output argument does not prohibit such aliasing.

No visible allocation, deallocation, callback, synchronization operation, or called function appears in the body. No ownership transfer is established:

- The function does not visibly allocate or release the table.
- It does not visibly retain or release the output address.
- It does not treat a payload as an owned resource.

A payload that encodes an address or handle is still only copied as a 32-bit quantity by this function.

There is no explicit validation or error-reporting side effect. Fault, exception, signal, or termination behavior for invalid accesses is not established.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Except for examples explicitly describing a base change, they assume a stable shared base and stable relevant contents throughout the call. Every example also assumes valid reached accesses and no unrelated external writes to the destination.

### First-record match

If index 0 has the requested key and payload \(P\), the function uses the shared base expression for the key access, observes the match, separately uses the shared base expression for the payload access, writes \(P\), and returns 1.

No key at indices 1 through 79 is examined.

### Final-record match

If indices 0 through 78 do not match and index 79 does, all 80 keys are examined. The payload access uses the shared base expression separately after the final comparison and addresses offset 636.

The payload is copied, and the function returns 1. Index 80 is not accessed.

### Duplicate keys

If indices 6 and 24 contain the requested key and no earlier index matches, index 6 supplies the payload and the function returns 1. Index 24 is not examined.

This same-record payload guarantee depends on the stable-base assumption, not merely on stable record contents.

### Complete miss

If none of the 80 keys matches and the output initially contains \(Q\), the function returns 0 without a payload read or destination write. Under the stated absence of external destination changes, the output remains \(Q\).

### Zero payload

If the first matching record has payload zero, zero is written to the destination and the function returns 1.

### Matching storage beyond the bound

If indices 0 through 79 all miss, a matching key in adjacent storage beyond the nominal table extent is irrelevant. The function returns 0 without examining it.

### Unusable destination on a miss

If all reached shared-base and key accesses are valid and all comparisons fail, no access is performed through the output argument.

This is not a general guarantee that an invalid pointer is acceptable at the external interface. It establishes only that the represented miss path does not dereference that argument.

### Destination overlapping a later key

If index 2 is the first match and the output designates index 10’s key field, a valid output write replaces that field with index 2’s payload. The function then returns 1 without examining index 10.

### Base change after a matching key

Suppose earlier comparisons fail, and the key access at index 4 uses base A and finds the requested key. Before the payload-address use, suppose the shared base changes to B.

If execution permits this change to be observed as described and all accesses are valid, the payload is read from offset 36 relative to B, not necessarily from offset 36 relative to A. That value is written and the function returns 1.

The key at index 4 under B need not match. It is not checked. This example describes the represented access sequence conditionally; it does not establish that an unsynchronized concurrent mutation has defined behavior in the actual environment.
