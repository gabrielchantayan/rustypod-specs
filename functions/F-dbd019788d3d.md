# F-dbd019788d3d

## Purpose

F-dbd019788d3d conditionally creates a three-word record or replaces the first word of an existing record selected through a dependency.

Its established behavior includes:

- Clearing a 32-bit field in the supplied object.
- Computing a 32-bit quantity and conditionally invoking an object-level dependency before record selection.
- Passing a caller-supplied word and mutable, invocation-local scratch storage to a selection dependency.
- Allocating and publishing a 12-byte record when the selected slot is empty.
- Replacing only the first word when the selected slot already references a record.
- Updating different object fields for successful creation, replacement, and allocation failure.

The function returns the previous first word on replacement. Both successful creation and allocation failure return zero. The return value alone therefore does not distinguish these outcomes.

Interpreting the object as a table, the conditional preliminary operation as capacity maintenance, and the incremented fields as counters is plausible intent, not an independently established contract of the dependencies.

## Interface

### Inputs

The interface has four argument positions:

1. **Object address.** A 32-bit address identifying storage accessed at the offsets listed below.
2. **Supplied word.** An opaque 32-bit value passed to the selection dependency and later stored as the first word of a record.
3. **Unused word.** A 32-bit argument with no established read or other use in this function.
4. **Initial scratch word.** An opaque 32-bit value copied into invocation-local storage. The selection dependency receives the address of that storage and may modify its contents.

No signed interpretation, pointer interpretation, encoding, or ownership transfer is established for the supplied word or initial scratch word.

### Result

The result is one 32-bit word:

| Path | Result |
|---|---|
| Selected slot already contains a record address | Previous first word of that record |
| Empty slot and successful allocation | Zero |
| Empty slot and allocation returns zero | Zero |

A replacement can also return zero if the previous first word was zero.

These roles describe this function’s accesses, not authoritative names or complete semantics for the fields.

### Selected slot and record layout

F-1074569f7759 must return an address from which this function can read a four-byte record address. If creation succeeds, the function also writes a four-byte record address to that same slot.

A nonzero record address is treated as referring to a record whose first word is readable and writable. A newly allocated record has this layout:

| Record offset | Width | Initial content |
|---|---:|---|
| `0x00` | 4 bytes | Supplied word |
| `0x04` | 4 bytes | Zero |
| `0x08` | 4 bytes | Scratch word as read after allocation returns |

There is no direct access to an existing record’s second or third word.

### Preconditions for ordinary completion

The function does not validate the object address, selection result, or nonzero record addresses. Ordinary completion requires that each address be valid for the accesses actually performed, with suitable lifetime and alignment for the execution environment.

In particular, a zero return from F-1074569f7759 is not handled as an empty selection: it would be used as the address of the slot to dereference. Only a zero **value read from the slot** selects the allocation path.

No concurrency or reentrancy protection is visible. Stable object storage, valid slot storage, and any required synchronization are external obligations.

## Behavior

### 1. Entry state and preliminary dependency

The first direct object write stores zero at offset `0x5C`. This happens before any dependency call, even when the eventual operation is a replacement.

The initial scratch word is then copied into invocation-local four-byte storage.

The function calls F-d7be9cfb4000 with:

- The 32-bit field at object offset `0x24`, shifted left by eight bit positions.
- The 32-bit field at object offset `0x0C`.

Both input reads occur before that call. Their relative evaluation order is not established.

The shift operates on the field’s 32-bit representation; it is not established as a widened multiplication by 256. High-order bits cannot be assumed to survive. The source representation treats the loaded field as signed before shifting, so portable behavior for negative values or signed-overflow cases is not established by the supplied evidence.

After F-d7be9cfb4000 returns, the function reads the field at `0x1C` and compares it with the returned 32-bit quantity using unsigned ordering.

- If the field is less than or equal to the returned quantity, it calls F-dd99f95678d6 with the object address.
- If the field is greater, it skips that call.

Equality therefore takes the calling branch. There is no visible second comparison or retry.

The comparison uses the field value available **after** F-d7be9cfb4000 returns. It must not be specified as necessarily using the entry value, because that dependency’s effects are unknown.

The return value of F-dd99f95678d6, if any, is not consumed. Its effects on the object or related storage are not constrained by this function.

### 2. Selection

After the conditional preliminary call, the function invokes F-1074569f7759 with:

1. The object address.
2. The supplied word.
3. The address of the invocation-local scratch word.

The dependency can inspect or modify the scratch word through that address. Its initial content is the fourth argument, but the value later stored into a new record need not equal that argument.

After the dependency returns, the function reads one four-byte address from the returned slot address. That value alone determines whether this invocation takes the creation or replacement path.

There is no visible error check on the returned slot address and no separate error result from the selection operation.

### 3. Empty-slot path

If the address read from the selected slot is zero, the function calls F-43da6b23bd44 with the three arguments:

- `12`
- `0`
- `0`

The result is interpreted as a record address.

#### Allocation returns zero

If the allocation result is zero:

1. The function reads the current field at object offset `0x5C`.
2. It increments that value by one and writes it back.
3. It returns zero.

There is no direct write to the selected slot and no direct increment of `0x40` or `0x24` on this path.

The field at `0x5C` is not unconditionally one at return. Although this function cleared it at entry, intervening dependencies may have changed it. The failure operation increments its then-current value.

#### Allocation returns a nonzero address

If the allocation result is nonzero, the direct operations occur in this order:

1. Write the supplied word at record offset `0x00`.
2. Write zero at record offset `0x04`.
3. Read the current scratch word and write it at record offset `0x08`.
4. Publish the record address by writing it into the previously selected slot.
5. Read, increment, and write the object field at `0x40`.
6. Read, increment, and write the object field at `0x24`.
7. Return zero.

All three record words are initialized before the slot publication in the visible operation order. This establishes no atomic-publication or cross-thread memory-ordering guarantee.

The slot address is retained across the allocation call; it is not selected again. The slot’s contents are not re-read before publication. Consequently, safe use requires that the slot remain valid across that call. The function contains no conflict detection if another action changes the slot in the meantime.

### 4. Existing-record path

If the address read from the selected slot is nonzero:

1. Read the record’s first word.
2. Replace that word with the supplied word.
3. Read, increment, and write the object field at `0x44`.
4. Return the word read in step 1.

No allocation call occurs on this path. The function does not directly modify the selected slot, the record’s other words, or the object fields at `0x40` and `0x24`.

Writing a word equal to the previous first word still takes the replacement path and increments `0x44`; there is no equality-based suppression.

### 5. Arithmetic boundaries

The affected fields and stored results are 32 bits wide. No increment has an explicit overflow check, saturation rule, or error branch.

The source representation uses signed-looking accesses for the increments. It does not establish a portable signed-overflow contract. Applications requiring defined behavior at integer boundaries need a platform-level interpretation beyond this evidence; neither unbounded arithmetic nor guaranteed saturation is supported.

## Side effects

The function directly mutates the object’s entry-status field and, depending on the selected path, a record, its slot, and one or two additional object fields.

Successful creation associates the returned allocation with the selected slot. The function performs no visible deallocation, including on replacement. It does not free, release, or otherwise process the previous first word.

This does **not** establish an ownership policy:

- Whether the supplied word denotes owned memory is unknown.
- Whether replacement transfers responsibility for the returned word is unknown.
- Who eventually releases a created record is unknown.
- Whether any dependency allocates or releases other storage is unknown.

The scratch address passed to F-1074569f7759 refers to invocation-local storage. The function provides no persistent lifetime for that storage after return. Whether the dependency retains the address is unknown; doing so would not create a valid post-return lifetime.

The listed direct writes are not an exhaustive account of externally visible effects: dependencies may have additional effects. No preservation of globals, object fields, or unrelated memory is assumed.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless otherwise stated, assume valid non-overlapping storage, normally returning dependencies, no concurrent mutation, no unexpected dependency writes, and increments within their non-overflowing range.

### Existing record

Given a selected slot pointing to a record whose first word is `0x12345678`, a supplied word of `0xAABBCCDD`, and an initial `0x44` field of seven:

- The first record word becomes `0xAABBCCDD`.
- The `0x44` field becomes eight.
- The result is `0x12345678`.
- No F-43da6b23bd44 call occurs.
- The existing record’s remaining words are not directly changed.

The preliminary calculation and conditional call still occur before selection.

### Successful creation with modified scratch

Given an empty selected slot, a nonzero allocation result, and a selection dependency that changes the scratch word to `0x55667788`:

- The new record contains the supplied word, zero, and `0x55667788`, in that order.
- The slot receives the new record address after initialization.
- The `0x40` field increments before the `0x24` field.
- The result is zero.

This expectation assumes the allocation call does not alter the scratch word.

### Allocation failure

Given an empty slot and a zero allocation result, if no dependency changes the entry-cleared `0x5C` field:

- That field becomes one.
- This function does not publish a record.
- Neither creation counter is directly incremented.
- The result is zero.

If a dependency instead leaves `0x5C` equal to five before failure handling, the direct failure increment produces six, subject to the arithmetic qualifications above.

### Unsigned comparison boundary

If F-d7be9cfb4000 returns ten:

- A subsequently read `0x1C` field of ten causes F-dd99f95678d6 to be called.
- A field of eleven skips it.
- A field of `0xFFFFFFFF` skips it, because the comparison is unsigned.

### Ambiguous zero result

A replacement of an existing zero first word, successful creation, and allocation failure can all return zero. A consumer cannot distinguish them from the return word alone.
