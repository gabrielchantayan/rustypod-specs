# F-b8342e8cae72

## Purpose

F-b8342e8cae72 rewires a small set of address-bearing fields around a supplied node. For a conventional, well-formed binary tree, its effect is a **left rotation**: the node’s right child takes its position, the former node becomes that child’s left child, and the promoted child’s former left subtree becomes the former node’s right subtree.

The rotation interpretation is inferred from the field relationships. The established behavior is the ordered reading and overwriting of particular memory slots. The function does not establish that its inputs actually describe a tree, validate reciprocal links, or enforce an ordering property.

The operation also updates either a distinguished node reference reached through the first argument or a child reference in the former parent. Interpreting that distinguished reference as the tree root is consistent with the implementation, but its broader role is not independently established.

## Interface

### Inputs

The function takes two address-like arguments:

- **Container address:** identifies an object containing a reference at byte offset `+0x10`.
- **Pivot address:** identifies the node around which the transformation occurs.

The supplied representation uses integer-typed address arithmetic and four-byte memory slots. A faithful contract therefore treats the accessed links as 32-bit stored values used as addresses. This does not establish a portable native-pointer interface on a machine with wider pointers.

Offsets below are byte offsets.

### Accessed layouts

The node layout used by this function is:

| Offset | Width | Role under the tree interpretation |
|---|---:|---|
| `+0x04` | 4 bytes | Parent reference |
| `+0x08` | 4 bytes | Left-child reference |
| `+0x0c` | 4 bytes | Right-child reference |

No meaning is established for the node’s first four bytes or for fields beyond those listed.

The container-related layout is:

| Location | Width | Observed use |
|---|---:|---|
| Container `+0x10` | 4 bytes | Reference to an auxiliary object |
| Auxiliary object `+0x04` | 4 bytes | Distinguished node reference, compared with the pivot and possibly replaced |

The auxiliary object is not established to have the complete node layout.

### Output

The function has no explicit return value. Its result consists entirely of memory mutations.

There is no returned success indicator, error code, previous root, or replacement node.

### Preconditions for a conventional rotation

A caller seeking the ordinary tree-rotation result must provide:

- A valid pivot whose right-child reference identifies a valid, nonzero promoted node.
- Readable and writable parent and child slots for all nodes touched.
- A valid container-to-auxiliary-object reference and accessible distinguished reference.
- If the promoted node has a nonzero left-child reference, a valid writable parent slot in that child.
- If the distinguished reference does not identify the pivot, a valid parent reference in the pivot, with accessible child slots in that parent.
- Consistent, nonoverlapping structural objects and no interfering mutation during the operation.

These are caller obligations for the inferred tree operation, not checks performed by the function. In particular, a non-root pivot should be present in exactly one child slot of its parent. The implementation does not verify this invariant.

## Behavior

### Structural result for a well-formed tree

The pivot’s original right child is the **promoted node**. The promoted node’s original left child, if any, is the **transferred subtree**.

With stable memory and ordinary, nonoverlapping tree objects, the resulting relationships are:

- The pivot’s right-child reference identifies the transferred subtree.
- A nonzero transferred subtree has its parent reference changed to the pivot.
- The promoted node’s parent reference becomes the pivot’s former parent reference.
- The reference that formerly selected the pivot from above is changed to select the promoted node.
- The promoted node’s left-child reference identifies the pivot.
- The pivot’s parent reference identifies the promoted node.

The pivot’s left-child slot and the promoted node’s right-child slot are not directly changed. Under the tree interpretation, those subtrees remain attached to their original nodes.

The operation does not inspect payloads, compare keys, update counts, or repair balancing metadata. A left rotation preserves in-order traversal when applied to a valid binary tree, but the function does not check the conditions required for that property.

### Observable access and mutation order

The implementation first obtains the promoted-node address from the pivot’s right-child slot. That selected address is retained for the remainder of the operation.

The lower subtree connection is changed before the connection above the pivot. Specifically, the promoted node’s left-child slot is read and its value is written into the pivot’s right-child slot. The promoted node’s left-child slot is then read again to decide whether a transferred-subtree parent update is required. If that read is nonzero, another read of the same slot supplies the address whose parent slot is overwritten with the pivot address.

Thus, the transferred-subtree reference is not loaded once and reused throughout this part of the operation. In ordinary stable memory the repeated reads agree. In overlapping layouts, memory-mapped storage, or an environment permitting intervening changes, that agreement cannot be assumed.

Next, the pivot’s parent slot is read and copied into the promoted node’s parent slot. Only after that write does the function read the container’s reference at `+0x10` and inspect the auxiliary object’s distinguished reference.

The upper connection is selected as follows:

- If the distinguished reference equals the pivot address, that reference is overwritten with the retained promoted-node address.
- Otherwise, the pivot’s parent slot is read again. The referenced parent’s left-child slot is compared with the pivot address. A match causes the parent’s left-child slot to be overwritten with the promoted-node address. A non-match causes the parent’s right-child slot to be overwritten instead.

The non-root path therefore does not reuse the earlier parent value copied into the promoted node. It obtains the pivot’s parent reference again after the distinguished-reference check.

Finally, the promoted node’s left-child slot is overwritten with the pivot address, and then the pivot’s parent slot is overwritten with the promoted-node address.

This ordering matters: the operation is not an atomic replacement of a tree fragment. During execution, the individual links can temporarily describe an inconsistent structure.

### Branch precedence and unchecked cases

The distinguished-reference comparison takes precedence over inspecting the former parent’s child links. When it identifies the pivot, no former-parent child slot is inspected or rewritten. The pivot’s former parent value is still read and copied into the promoted node’s parent slot.

On the non-root path, the left-child comparison takes precedence over the right-child assignment:

- If both parent child slots identify the pivot, only the left-child slot is selected.
- If neither identifies the pivot, the right-child slot is still overwritten.
- The previous contents of the selected right-child slot are not validated.

Only the promoted node’s left-child value receives a zero check. There is no zero check for the pivot, the promoted node, the auxiliary-object reference, or the former parent used on the non-root path.

### Arithmetic and representation

All field locations are formed through fixed-offset address arithmetic. There is no multiplication, traversal index, allocation-size calculation, or explicit range check.

The supplied representation establishes four-byte loads and stores. It does not establish byte order, alignment requirements, integer-overflow semantics, or the behavior of an address calculation that exceeds the target address range. Valid inputs must permit the required accesses in the actual execution environment; wraparound must not be treated as an established feature.

## Side effects

For ordinary nonoverlapping objects, a completed invocation performs five four-byte writes when there is no transferred subtree and six when the transferred-subtree parent update is taken.

The write targets are:

- The pivot’s right-child slot.
- The transferred subtree’s parent slot, conditionally.
- The promoted node’s parent slot.
- Exactly one upper reference: the auxiliary distinguished reference, the former parent’s left-child slot, or its right-child slot.
- The promoted node’s left-child slot.
- The pivot’s parent slot.

A write still occurs when the value being stored happens to equal the existing value.

The function contains no allocation, deallocation, copying of whole objects, external call, or explicit access to an independently named global object. It does not transfer ownership or establish that any object may be released. All referenced storage must remain usable for the accesses performed.

No synchronization, rollback, or recovery mechanism is present. An invalid access can occur after earlier writes have already changed the structure. Such a failure must not be interpreted as leaving the original tree intact.

Aliasing can cause an earlier write to affect a later read, or cause distinct conceptual updates to target the same physical slot. The conventional rotation postconditions are therefore conditional on a suitable object layout. The implementation supplies no separate alias-safe behavior.

## Acceptance examples

The following are conditional acceptance cases derived from static evidence. They are not reports of executed tests.

### Root rotation with a transferred subtree

Assume the distinguished reference identifies the pivot, the pivot’s right child is the promoted node, and the promoted node’s left child is a valid nonzero subtree.

Accept the result when:

- The distinguished reference identifies the promoted node.
- The promoted node’s parent contains the pivot’s former parent value, whether that value is zero or a valid header reference.
- The pivot’s right child identifies the transferred subtree.
- The transferred subtree’s parent identifies the pivot.
- The promoted node’s left child identifies the pivot.
- The pivot’s parent identifies the promoted node.

With nonoverlapping storage, the pivot’s left child and promoted node’s right child remain unchanged.

### Non-root pivot selected by its parent’s left link

Assume the distinguished reference does not identify the pivot, and the pivot’s parent has the pivot in its left-child slot.

Accept the result when the parent’s left-child slot identifies the promoted node and the distinguished reference remains unchanged. The local parent and subtree relationships must match the rotation described above. The parent’s right-child slot is not directly written.

### Non-root pivot selected through the right-link fallback

Assume the distinguished reference does not identify the pivot and the parent’s left-child slot does not identify it.

Accept the observed behavior when the parent’s right-child slot is overwritten with the promoted-node address. This applies even if that right-child slot did not previously identify the pivot. Such an input does not satisfy the conventional well-formed-tree precondition, but the overwrite is still the statically established branch behavior.

### Empty transferred subtree

Assume the promoted node’s left-child slot is zero throughout the relevant reads.

Accept the result when the pivot’s right-child slot becomes zero and no transferred-subtree parent write occurs. The remaining upper-reference and pivot/promoted-node updates still occur.

### Missing promoted node

Assume the pivot’s right-child value is zero.

There is no supported “nothing to rotate” outcome. The function proceeds to access the left-child field relative to that zero value without first rejecting it. Whether this traps or accesses mapped storage is environment-dependent. Acceptance must not require a clean error return or unchanged memory.
