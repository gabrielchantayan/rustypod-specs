# F-6ca634842830

## Purpose

F-6ca634842830 performs an in-place relinking operation on a node and the node referenced by its field at byte offset +8. Under a conventional binary-tree interpretation, this is a right rotation: the +8 child is promoted, its +12 child moves beneath the original node, and the promoted node replaces the original node in the containing structure.

The pointer assignments establish that structural transformation. The meanings “tree,” “parent,” “left child,” and “right child” are inferred intent, not independently established type information. The function does not inspect keys, compare values, update balancing metadata, or validate the surrounding structure.

The contract below describes both the ordinary structural result and the ordered memory accesses that determine behavior when fields alias.

## Behavior

### Structural result under ordinary non-aliasing conditions

Assume that the fields represent a well-formed tree, the relevant records and fields do not unexpectedly overlap, and no concurrent actor changes them during execution.

The pivot’s initial +8 link identifies the promoted node. The promoted node’s existing +12 link becomes the pivot’s new +8 link. If that transferred link is nonzero, its target’s +4 field is changed to identify the pivot.

The promoted node inherits the pivot’s former +4 link. The surrounding structure then changes its reference to the pivot:

- If the root holder’s +4 field equals the pivot address, that field is replaced with the promoted-node address.
- Otherwise, the former parent is consulted. If its +12 field equals the pivot address, that field is replaced with the promoted-node address. If it does not equal the pivot, its +8 field is replaced instead.

Finally, the promoted node’s +12 field is set to the pivot address, and the pivot’s +4 field is set to the promoted-node address.

No key ordering or other tree invariant is checked. The structural interpretation therefore depends on caller-provided invariants.

### Observable access order

The function does not take a complete snapshot of its inputs before writing. Later reads can observe earlier writes when storage overlaps. The following ordering is established by the supplied static evidence.

**Transfer phase.** The function first reads the pivot’s +8 field and retains that promoted-node address. It reads the promoted node’s +12 field and writes that four-byte value into the pivot’s +8 field.

After that write, it reads the promoted node’s +12 field again to test whether it is zero. If the test is nonzero, the field is read once more to obtain the destination address, and the pivot address is written to that destination’s +4 field.

Thus, a nonzero transfer ordinarily involves three reads of the promoted node’s +12 field: one for the value copied into the pivot, one for the condition, and one for the write destination. These are not guaranteed to yield a single stable value under aliasing or concurrent mutation.

**Parent-link preparation.** After the optional transferred-subtree update, the function reads the pivot’s +4 field and copies it into the promoted node’s +4 field. This read occurs after the preceding writes, not at entry.

Only after that copy does the function read the context’s +16 field to locate the root holder. It then reads the root holder’s +4 field and compares it with the pivot address.

**External-link replacement.** If the comparison matches, the function writes the promoted-node address into that same root-holder field. It does not consult the former parent’s child links on this path.

If the comparison does not match, the function freshly reads the pivot’s +4 field. It uses that address to read the former parent’s +12 field. Equality with the pivot selects a write to the former parent’s +12 field; inequality selects a write to its +8 field.

The fallback does not verify that the former parent’s +8 field actually contains the pivot. It overwrites that field even if neither child-like field identifies the pivot.

**Final attachment.** After the external-link replacement, the function writes the pivot address into the promoted node’s +12 field. Its final observed store writes the promoted-node address into the pivot’s +4 field.

The retained pivot and promoted-node addresses continue to identify the final write targets even though their fields have changed.

## Side effects

The function modifies existing memory in place. Its possible write locations are:

- Pivot +8.
- Transferred-subtree target +4, on the nonzero transfer path.
- Promoted node +4.
- Exactly one selected external-reference location: root holder +4, former parent +12, or former parent +8.
- Promoted node +12.
- Pivot +4.

These are logical write locations; aliasing can make several of them refer to the same physical storage.

This expectation holds even if that +8 field initially identifies an unrelated node. Rejection of inconsistent parent links is not part of the observed behavior.
