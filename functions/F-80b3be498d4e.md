# F-80b3be498d4e

## Purpose

F-80b3be498d4e obtains a candidate descriptor, requests a storage-related value, and, on success, initializes descriptor fields around an external operation.

Its apparent purpose is to duplicate a descriptor and its active backing data while retaining capacity-related and other metadata. This is inferred intent, not an established end-to-end guarantee: the implementations and contracts of all four dependencies are unavailable.

The established behavior is:

- Pass the input descriptor’s fifth word to a construction dependency.
- If construction succeeds, request storage using the candidate’s second word and four times the input’s fourth word, subject to the recovered shift semantics.
- If that request fails, invoke cleanup and return null if cleanup returns normally.
- Otherwise, assign the storage result and an input field to the candidate, invoke an external dependency, copy three more input fields, and return the candidate pointer.

The function does not validate descriptor contents, establish adequate backing-storage capacity, or guarantee that the external dependency preserves fields assigned before its call.

## Interface

### Input descriptor

The sole input is a pointer to a descriptor with five integer-word fields. There is no explicit length argument or null-input check.

The following layout uses four-byte integer words as the working recovered representation:

| Word | Byte offset under that representation | Established use |
|---|---:|---|
| First | 0 | Assigned to the candidate before the external call; read again to form the external call’s third argument |
| Second | 4 | Supplied as the external call’s second argument |
| Third | 8 | Copied to the candidate after the external call |
| Fourth | 12 | Used to form the storage request’s second argument; copied again after the external call |
| Fifth | 16 | Supplied to construction; copied again after the external call |

The supplied body uses integer fields and shifts by two bits. It does not independently establish the original ABI’s integer width, pointer width, alignment, or signed-overflow behavior. Consequently, the byte offsets above are conditional on the four-byte representation; the field ordering and relative word positions are directly established.

“Count,” “backing address,” and “capacity” are plausible semantic names, but are not verified field contracts. In particular, the second word is passed as an integer-valued argument; its interpretation as an address or handle belongs to the dependencies.

### Return value

On ordinary completion, the function returns either:

- Null following a null construction result.
- Null following a zero storage result and normally returning cleanup.
- The same candidate pointer returned by construction, after the success-path operations.

There is no separate status output. The external dependency’s return value is ignored.

A non-null return does not establish:

- That the candidate is distinct from the input.
- That backing storage is newly allocated or exclusively owned.
- That the external operation successfully transferred data.
- That the candidate’s first two words retain the values assigned before that operation.
- That dependencies preserved globals, input contents, or resource lifetime.

### Preconditions for defined ordinary completion

Every access actually reached must be valid. Relevant requirements include:

- The input’s fifth word must be readable before construction.
- After successful construction, the candidate’s second word and the input’s fourth word must be readable for the storage call.
- On the success path, the candidate must remain writable at every reached field assignment.
- The input must remain readable at each later field read.
- Arithmetic and argument values must satisfy the actual machine and dependency contracts.

These are caller or environment obligations, not checks performed by this function. Invalid input is not translated into a defined null-result failure.

## Behavior

### Construction

The function reads the input’s fifth word and supplies that value to F-e6ffa761e067.

A null result terminates processing with a null return. No storage, cleanup, or external-operation call follows on this path.

A non-null result becomes the candidate descriptor used for all subsequent candidate accesses and for the successful return.

Construction may have side effects even when it returns null. Nothing in the supplied body establishes preservation of the input, globals, or resources across this dependency.

### Storage request

After non-null construction, the function invokes F-8b998a07b5e1 with:

1. The candidate’s current second word.
2. The input’s current fourth word shifted left by two bits.
3. Zero.
4. Zero.

Both descriptor reads occur after construction returns. The input’s fourth word is not an earlier snapshot. The supplied expression does not establish the relative evaluation order of the two descriptor reads used for these arguments.

The storage dependency returns an integer-valued result. Exactly zero selects the failure path; any nonzero result selects the success path. There is no additional sign, range, address, or capacity check.

The argument pattern suggests a request involving four bytes per fourth-word unit. Whether the dependency allocates, resizes, replaces, or otherwise manages storage remains unknown.

### Storage failure

When the storage result is zero, F-9aef742d6dcd receives the candidate pointer. If cleanup returns normally, F-80b3be498d4e returns null.

The function does not assign the zero storage result into the candidate before cleanup. Cleanup therefore receives the descriptor in whatever state exists after the storage call, including changes made by that dependency.

This path establishes a cleanup invocation, not successful destruction or resource release. The success-path assignments and external operation are not reached.

### Assignments before the external operation

For a nonzero storage result, the function first writes that result into the candidate’s second word.

It then reads the input’s first word and writes that value into the candidate’s first word.

These assignments occur in that order and precede the external call. If the candidate overlaps the input, either assignment can affect input values subsequently read. The function does not detect or prohibit such aliasing.

The assignments establish values at those points in execution. They do not establish the final values of the first two candidate words: the external dependency may subsequently modify either word through another reference.

### External operation

The function invokes F-unknown-01 with:

1. The nonzero storage result.
2. The input’s second word, read for this call.
3. The input’s first word, read again and shifted left by two bits.

F-unknown-01 is a document-local opaque identifier for the external dependency not identified by the supplied dependency map.

The first argument is the saved storage result, not a fresh read of the candidate’s second word. The third argument uses a fresh input first-word read, not the value previously assigned to the candidate’s first word.

The supplied expression does not establish the relative evaluation order of the input reads used for the second and third arguments.

The argument shape suggests destination, source, and byte count. Actual transfer behavior, overlap handling, zero-size behavior, and error reporting are unknown. The function does not inspect the dependency’s return value.

The dependency must not be assumed to preserve either descriptor, globals, or resource validity. In particular, nonoverlapping input and candidate descriptors do not prevent it from modifying the candidate through an independently held reference.

### Assignments after the external operation

If the external dependency returns normally, the function performs these field copies in order:

1. Input third word to candidate third word.
2. Input fourth word to candidate fourth word.
3. Input fifth word to candidate fifth word.

It then returns the candidate pointer.

Each source value is read at its corresponding assignment, after the external operation. The function does not retain an immutable input snapshot.

Accordingly:

- The final fourth-word copy may use a different value from the storage request.
- The final fifth-word copy may use a different value from construction.
- The first-word value assigned before the external call may differ from the value used to form that call’s third argument.
- There is no explicit restoration of the candidate’s first or second word after the external call.

For distinct, nonoverlapping descriptors with stable input and valid accesses, the final three copies establish the corresponding input values in the candidate. Without those conditions, aliasing and intervening changes must be considered according to the actual read/write order.

### Arithmetic and widths

For a nonnegative operand whose shifted result is representable in the applicable signed integer type, the result equals four times that operand.

## Side effects

### Explicit writes and call boundaries

On the success path, the explicit candidate writes are ordered as follows:

| Position | Write |
|---|---|
| Before external call, first | Second word receives the nonzero storage result |
| Before external call, second | First word receives the input first word read at that point |
| After external call, first | Third word receives the then-read input third word |
| After external call, second | Fourth word receives the then-read input fourth word |
| After external call, third | Fifth word receives the then-read input fifth word |

There are no explicit writes through the input pointer. This does not imply input immutability: candidate/input aliasing and dependency effects can change input memory.

The external call separates two groups of assignments. Its possible modifications to the candidate’s first two words are not undone by any later explicit assignment to those words.

### Ownership and lifetime

The candidate is passed to cleanup only after a zero storage result. On success it is returned without an explicit release.

These observations do not establish ownership transfer or exclusive ownership. The following remain dependency-contract questions:

- Whether construction creates a fresh descriptor.
- Whether the storage result represents fresh, shared, or replacement storage.
- Whether cleanup releases the descriptor, backing storage, both, or neither.
- Whether a failed storage operation preserves any previous resource.
- Whether the caller must eventually release a successful result.

The function performs no independent release of the input or its second-word value. It also performs no independent release of the candidate’s previous second-word resource before replacing that word.

### Errors and abnormal completion

Only two explicit failure conditions are recognized: null construction and zero storage result.

There is no explicit failure branch after F-unknown-01, no rollback of the preceding assignments, and no local handling of faults, exceptions, nonlocal exits, or invalid-memory behavior. Later actions and return values are conditional on dependencies returning normally and required accesses remaining valid.

### Stable, distinct descriptors

- Candidate accesses remain valid.
- The input’s first word is 3 and fourth word is 8.
- Construction and storage succeed.
