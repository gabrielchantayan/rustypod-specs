# F-bd53376b4193

## Purpose

F-bd53376b4193 initializes selected fields of 34 fixed-layout records through a globally supplied table address. It also writes two 32-bit constants into a caller-supplied object.

**Established static behavior:** fixed field assignments, arithmetic and bitwise transformations of external inputs, repeated reads of selected input slots, and repeated reads of the table-base slot. Existing record contents are not examined to select the assignments.

**Inferred intent:** the records resemble descriptors containing two payloads, a category, an associated value, and a flag. Their domain meaning is not established.

Initialization is neither atomic nor transactional. The function does not allocate storage, validate destinations, clear record padding, or report success.

## Interface

### Explicit input and result

The sole explicit input is a 32-bit address-valued argument, called the **object address** here.

The function makes these four-byte writes:

| Object-relative byte offset | Stored value | Timing |
|---:|---:|---|
| 28 | 6 | After record 6’s Flag, before record 7’s Value |
| 24 | 8 | After record 8’s Flag, before record 9’s Value |

There is no specified return value.

### Implicit inputs

The function reads a global table-base slot and external 32-bit data slots. The following names describe their roles without assigning domain meanings:

- **Initial:** supplies record 0’s Value.
- **Anchor A:** supplies the basis for records 1 and 2.
- **Anchor B:** supplies the basis for records 3 and 4.
- **Standalone:** supplies record 5’s Value.
- **Anchor C:** supplies the basis for subsequent Value calculations.
- **Pᵣ:** the external first-payload slot associated with record \(r\).
- **Qᵣ:** an independently supplied second-payload slot where one exists.

A slot name identifies a storage location, not an invocation-wide snapshot. Multiple reads of the same slot can produce different samples.

### Output layout

Records are numbered 0–33 and have a 20-byte stride.

| Record-relative byte offset | Field | Store width |
|---:|---|---:|
| 0 | First payload | 32 bits |
| 4 | Second payload | 32 bits |
| 8 | Kind | 32 bits |
| 12 | Value | 32 bits |
| 16 | Flag | 8 bits |
| 17–19 | Unwritten tail | None |

With a stable base, the final explicitly written byte is table-relative byte 676. Storage for 34 complete records occupies 680 bytes. The function does not write the three tail bytes as part of any record assignment.

### Preconditions

Normal completion requires:

- Readable external input slots and table-base slot.
- Writable destinations for every individual table access through its applicable base.
- Writable four-byte object regions at offsets 24 and 28.
- Address calculations, alignment, and accesses supported by the execution environment.

No null, bounds, alignment, allocation-size, or overlap checks are visible.

Non-aliasing is not established. Table writes or object writes can affect subsequent input or base-slot reads if those regions overlap. Statements about final contiguous records and unchanged tail bytes therefore require stable address mappings and appropriate non-overlap.

## Behavior

### Arithmetic notation and widths

All payloads, anchors, and Value fields are 32-bit quantities. Payload copies preserve their 32-bit patterns.

For the stable-input table below, define:

- **U:** Anchor C + 26.
- **M:** U with bit 4 cleared, using the 32-bit mask `0xFFFFFFEF`.
- **N:** U with bit 1 cleared, using the 32-bit mask `0xFFFFFFFD`.
- **W:** U with bit 3 set.
- **S:** U plus the signed right shift by 26 of the **earlier Q₁₃ sample**.

Bit positions are zero-based. Clearing a bit is not generally equivalent to subtracting its value; setting a bit is not generally equivalent to adding its value.

U is retained as an unsigned 32-bit quantity, but its production uses a signed Anchor C addition in the supplied representation. That distinction matters if the addition overflows.

Operations on U, M, N, W, and S use unsigned 32-bit arithmetic where shown. Their unsigned additions and subtractions wrap modulo \(2^{32}\). In particular, S incorporates the shifted signed sample through unsigned conversion.

Anchor A and Anchor B adjustments, direct Anchor C adjustments, and retained payload subtractions are presented as signed 32-bit arithmetic. Defined modular behavior for overflowing signed expressions is not established.

The signed right shifts have a count of 26. If arithmetic right shift applies, the result is between −32 and 31. The complement used for record 16 is a 32-bit complement of the shifted result.

### Anchor and ordinary payload sampling

The function does not snapshot all inputs at entry.

- Initial is read for record 0’s Value store.
- Anchor A is read after that store and before record 0’s First payload store. Its retained sample supplies both records 1 and 2.
- Anchor B is read after record 2’s Value store but before record 2’s First payload store. Its retained sample supplies records 3 and 4.
- Standalone is read after record 4’s Value store and before its First payload store, then retained for record 5.
- Anchor C is read after record 5’s Value store and before its First payload store, then retained for the later formulas.

- Q₃₀ is read once during record 30 and retained for the second payloads of records 30–32. Records 31 and 32 do not obtain those values by reading record 30.

### Repeated samples of Q₁₃ and P₁₅

Q₁₃ is visibly read twice:

1. After record 13’s First payload store, an earlier sample is retained for calculating S.
2. A subsequent read supplies record 13’s Second payload store.

Record 13’s Kind is then written, and S is calculated before its Flag store. S depends on the earlier sample, not on the sample stored into Second payload.

P₁₅ is also visibly read twice:

1. After record 15’s Value store, an earlier sample is retained for record 16’s mask.
2. A subsequent read supplies record 15’s First payload store.

Record 15’s remaining payload and Kind stores follow. Record 16’s Value uses the signed shift of the earlier P₁₅ sample, not necessarily the bit pattern stored in record 15.

Equality of each pair of samples requires an explicit stability assumption. Neither calculation rereads the completed record.

### Repeated first-payload samples for records 16–21

For each record from 16 through 21:

- The Value is stored first.
- The external first-payload slot is read into a retained sample.
- The same slot is read again to supply First payload.
- Second payload is calculated from the earlier retained sample.

The respective subtractions are 1696, 184, 189, 191, 190, and 183. Records 16 and 17 store Second payload before Kind; records 18–21 store Kind first.

Consequently, Second payload need not equal the actually stored First payload minus the stated constant. That relationship holds only when the two samples agree.

| Base read | Destination use |
|---|---|
| Initial captured base | Record 0’s non-Value fields; all fields of records 1–14; record 15 through Kind |
| Additional direct read for record 0 | Record 0’s Value only |
| Capture after record 15’s Kind | All fields of records 16–30; record 31 through Kind |

The first base capture precedes record 0’s Value assignment, but that assignment uses a separate direct base read. Thus, even record 0 can be split: its Value can reach one table while its other fields reach another.

At the two Flag boundaries, the capture occurs before the separate direct access used by the Flag store. The newly captured address governs subsequent records; it need not equal the Flag’s destination base.

During record 32, its Value is stored through the preceding captured address. Another address is then captured for record 33, followed by a separate direct base access for record 32’s First payload. Record 32’s remaining stores continue through the preceding capture.

## Acceptance examples

These are conditional static expectations, not executed tests.

### Stable initialization and untouched tails

Given stable input slots, one stable table base, disjoint valid destinations, and defined arithmetic:

- The written fields match the record table.
- Object offset 28 receives 6 before offset 24 receives 8.
- Flags equal 1 exactly for records 0, 8, 13, 16, 22, and 31.
- Each record’s bytes 17–19 retain their previous contents.

### Bitwise calculations

With Anchor C equal to 0 and both relevant earlier shift samples equal to 0:

- U is 26.
- Record 12’s Value is 10.
- Record 13’s Value is 6.
- Records 14–16 have Values 26, 27, and 26.
- Records 17 and 18 have Values 24 and 33.
- Records 19 and 20 have Values 26 and 27.

Record 19 is not 34: bit 3 of 26 was already set.

### Distinct Q₁₃ samples

Suppose Anchor C is 0, the earlier Q₁₃ sample is 0, and the later payload sample is `0xFC000000`.

Record 13’s Second payload is `0xFC000000`, but S is 26 and record 14’s Value is 26.

Conversely, with arithmetic right shift, an earlier Q₁₃ sample of `0xFC000000` and a later sample of 0 produce S equal to 25 while storing 0 as record 13’s Second payload.

### Distinct P₁₅ samples

Suppose S is 26, arithmetic right shift applies, the earlier P₁₅ sample is `0xFC000000`, and its later sample is 0.

Record 15’s First payload is 0. Nevertheless, the earlier sample shifts to −1, whose 32-bit complement is zero, so record 16’s Value is zero.

### Derived second payloads

If record 16’s earlier P₁₆ sample is 5000 and its later sample is 6000, its First payload is 6000 and its Second payload is 3304—not 4304.

If the retained Q₃₀ sample is 1000, the second payloads of records 30–32 are 1000, 975, and 989 respectively.

### Split destinations and partial completion

If the initial base capture returns address A and the separate record-0 Value access uses address B, record 0’s Value is written at B + 12, while its other fields use A.

If execution faults during record 9, both object stores have already occurred in the visible sequence. Earlier stores are not rolled back.
