# F-4574f685dc0e

## Purpose

F-4574f685dc0e searches overlapping four-byte windows for an unsigned value within an inclusive range. Each window is interpreted in big-endian byte order. The search advances one byte after each rejected window and reports the number of rejected windows through a caller-provided output location.

The return value distinguishes a match from termination without a match:

- **0:** a qualifying window was found.
- **1:** the remaining-length condition stopped the search.

An important boundary condition is established by the supplied static evidence: the function examines a window only when the remaining length is **at least five**, although each examination reads only four bytes. Consequently, a remaining length of exactly four terminates the search without examining those four bytes. This contract preserves that behavior rather than replacing it with a conventional four-byte search rule.

No runtime tests have been performed.

## Interface

### Inputs

The function receives five arguments, in this order:

1. **Input byte address.** The initial position of the byte sequence to search. Each input element is eight bits.
2. **Length.** A signed 32-bit integer used as the remaining-length value.
3. **Count output address.** A writable location for a signed 32-bit integer. The function initializes this location to zero and updates it after every rejected window.
4. **Lower bound.** An unsigned 32-bit integer.
5. **Upper bound.** An unsigned 32-bit integer.

The supplied representation establishes the widths and signedness above. It does not establish a portable calling convention, pointer width, or alignment policy.

### Outputs

The function returns a 32-bit status value. The only explicitly produced values are 0 and 1.

The count output has these meanings, assuming it is valid writable storage and its writes do not alter bytes being searched:

- On return 0, it contains the zero-based byte offset of the first qualifying window.
- On return 1, it contains the number of windows examined and rejected.
- When the initial length causes immediate termination, it contains zero.

The function does not return a pointer to the matching bytes. A caller may derive the matching position from the original input address and the reported offset when the result is 0.

### Preconditions

For defined, ordinary use:

- The count output address must permit a four-byte integer write, even when no input bytes will be examined.
- Every input byte actually examined must be readable at the time of its read.
- Address advancement through the examined region must be valid.
- The signed length arithmetic must remain within its supported range.
- Storage must not be modified concurrently in a way that invalidates the reads or count updates.

Disjoint input and output storage is the straightforward usage model. Disjointness is not explicitly checked. Overlap is therefore not an error status, but it can make the function modify the very bytes it subsequently searches.

No requirement that the lower bound be less than or equal to the upper bound is enforced. A reversed range simply cannot accept any unsigned value.

## Behavior

### Initialization and stopping rule

The first observable memory operation established by the supplied evidence is a write of zero to the count output.

That write occurs before the first length check and before any input-byte read. Therefore, an invalid count output address is not made safe by a short length or by an otherwise unused input address.

At the start of each search iteration, the function evaluates whether the remaining length minus four is less than one, using signed length arithmetic.

Where that subtraction is representable, this means:

- Remaining length of five or more: examine a window.
- Remaining length of four or less: return 1 immediately.

The stopping check precedes all byte reads for that iteration.

### Window interpretation

An examined window consists of four consecutive bytes beginning at the current input position.

Let their unsigned eight-bit values, in increasing address order, be \(b_0\), \(b_1\), \(b_2\), and \(b_3\). The compared value is:

\[
V = b_0 \times 2^{24} + b_1 \times 2^{16} + b_2 \times 2^8 + b_3.
\]

Thus:

- The first byte is the most significant byte.
- The fourth byte is the least significant byte.
- Values with the top bit set remain unsigned values, not negative integers.
- The resulting value lies between 0 and \(2^{32}-1\), inclusive.

The byte significance is established independently of the machine’s native representation for a 32-bit integer. The supplied evidence does not establish the physical ordering of the four individual byte loads.

### Range acceptance

A window qualifies exactly when both conditions hold:

\[
\text{lower bound} \le V
\quad\text{and}\quad
V \le \text{upper bound}.
\]

Both comparisons are unsigned and inclusive.

For a qualifying window, the function returns 0 immediately. It does not advance to another window and does not increment the count output for the successful window.

If the lower bound exceeds the upper bound, no window can qualify. The search still reads and rejects eligible windows until the length condition terminates it.

### Rejection and progress

After a nonqualifying window:

- The current input position advances by one byte.
- The remaining length decreases by one.
- The count output increases by one.
- The next iteration performs the stopping check before any further window read.

The windows overlap by three bytes. Advancement is not in four-byte units.

At the supplied behavioral level, the count update reads the current integer stored at the output location and writes its incremented value. It is not merely a final count written on return. In ordinary disjoint, nonconcurrent use, the value progresses through zero, one, two, and so on.

### Search extent

For an initial length \(N \ge 5\), with valid arithmetic and storage:

- Eligible starting offsets are 0 through \(N-5\), inclusive.
- At most \(N-4\) windows are examined.
- If every window is rejected, the final count is \(N-4\), and the return value is 1.
- If the first qualifying window starts at offset \(k\), the final count is \(k\), and the return value is 0.

Even if every eligible window is examined, the highest input offset read is \(N-2\). The byte at offset \(N-1\) is not read.

In particular, the four-byte window beginning at offset \(N-4\) is never examined. This is the final window that a conventional search across \(N\) bytes might otherwise consider.

For initial lengths zero through four, no input bytes are read and the result is 1 with a count of zero.

### Integer boundaries

For a positive signed 32-bit length, the count cannot overflow through normal search progress. Its largest possible final value is \(N-4\), which is below the signed 32-bit maximum.

Negative lengths require a distinction:

- When subtracting four is representable, the stopping condition is true, so the function returns 1 after initializing the count.
- For the four smallest signed 32-bit values, subtracting four is not representable as a signed 32-bit integer.

The supplied representation does not establish how that latter case must be interpreted. A wrapping-machine interpretation and a signed-arithmetic language interpretation need not agree. Those four extreme inputs are therefore outside the portable behavioral guarantees of this contract; their treatment is **documented_only**.

## Side effects

### Memory writes

The explicit writes target the count output:

1. A four-byte zero write before any length check.
2. A four-byte count update after each rejected window.

There is no explicit direct write through the input byte address.

If the count output overlaps the input region, however, its initialization or subsequent updates may overwrite input bytes. The search then operates on the resulting memory contents rather than necessarily on the sequence that existed at entry.

The byte pattern produced by an overlapping count write depends on the platform’s integer memory representation and storage rules. That representation is not specified by the supplied evidence.

### Read/write ordering

The established behavioral ordering is:

- Initialize the count before checking whether input examination is necessary.
- Check remaining length before reading a candidate.
- Obtain the candidate bytes and determine acceptance before performing a rejection count update.
- Complete the rejection update before examining the next candidate.

The evidence does not establish individual byte-load ordering, atomicity, memory barriers, or synchronization guarantees. Memory-mapped input and concurrently shared storage therefore require guarantees not provided here.

### Ownership and state

No allocation, release, or ownership transfer is present in the supplied function body.

The caller retains responsibility for input storage and count storage. The function retains no explicit reference after returning. There are no explicit global-state accesses or external calls in the supplied evidence.

The function provides no dedicated status for an invalid address, insufficient accessible storage, misalignment, or arithmetic outside the supported interpretation. Such conditions must not be treated as ordinary return-1 outcomes.

## Acceptance examples

The following are conditional acceptance examples derived from static evidence, not results of executed tests. Unless stated otherwise, input and output storage are valid and disjoint, and arithmetic is representable.

### Immediate match

Given a length of five, first four bytes `12 34 56 78`, and bounds both equal to hexadecimal `12345678`:

- The candidate value is hexadecimal `12345678`.
- The return value is 0.
- The count is zero.
- The fifth byte is not read.

### Exactly four bytes remain

Given a length of four and four readable bytes that would satisfy the bounds:

- No candidate is examined.
- The count is initialized to zero.
- The return value is 1.

The potential match does not override the length rule.

### Match after one rejection

Given length six and bytes `00 01 02 03 04 FF`, with both bounds equal to hexadecimal `01020304`:

- Offset zero produces hexadecimal `00010203` and is rejected.
- The count becomes one.
- Offset one produces hexadecimal `01020304` and qualifies.
- The return value is 0 and the count is one.
- The final byte, `FF`, is not read.

### Exhaustion after one candidate

Given length five, first four bytes representing 7, and a range containing only 8:

- The sole eligible candidate is rejected.
- The count becomes one.
- The remaining length becomes four.
- The return value is 1 without another candidate read.

### Reversed range

Given length seven, a lower bound of 100, and an upper bound of 99:

- No candidate can qualify.
- Three windows are examined and rejected.
- The return value is 1.
- The count is three.

### Unsigned upper-half value

Given length five, first four bytes `80 00 00 00`, and both bounds equal to hexadecimal `80000000`:

- The candidate is the unsigned value \(2^{31}\).
- The return value is 0.
- The count is zero.

A signed-negative interpretation would violate the established unsigned comparison behavior.

### Inclusive endpoints

Given length at least five and an initial candidate exactly equal to either bound, with the lower bound no greater than the upper bound:

- The initial candidate qualifies.
- The return value is 0.
- The count remains zero.

### Short length with unused input

Given length zero and a valid count output:

- The count is written as zero.
- No input byte is read.
- The return value is 1.

An input address need not be dereferenced on this path. This does not waive any independent calling-environment rules concerning argument validity.

## Uncertainties

The following matters are **documented_only**:

- **Extreme negative lengths:** the interpretation of an unrepresentable signed subtraction is not established.
- **Aliased input and output:** the broad effect of count writes on future input is established, but exact resulting byte values require platform representation and concrete overlap details.
- **Individual load order:** four byte values form each candidate, but their physical load order is not established.
- **Fault behavior:** invalid storage has no defined function-level error status in the supplied evidence.
- **Alignment and ABI:** required output alignment, pointer width, and calling convention are not established.
- **Concurrent observation:** no atomicity or synchronization contract is established.

The apparent intent is to locate a four-byte big-endian value within a bounded byte sequence. That intent is an inference. Whether the five-byte threshold is deliberate or an off-by-one defect is unknown; the established behavior remains the five-byte threshold.
