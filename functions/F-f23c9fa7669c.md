# F-f23c9fa7669c

## Purpose

F-f23c9fa7669c coordinates repeated searches, candidate interpretation, table lookup, and conditional application of a four-byte local payload area to an object-associated target.

Established behavior consists of explicit memory accesses, dependency calls, arithmetic, and branch decisions. Decoding or replacement is plausible intent, not an established semantic contract: the search operands, resource representation, interpretation rules, and application operation are unavailable.

The function has no explicit return value or success indicator. Its visible normal-return path occurs when a primary search returns exactly −1. Dependency failures and nonlocal exits are not characterized.

## Interface

### Local storage and address exposure

The visible local storage includes:

- A first eight-byte area and a second eight-byte area, each passed separately to F-5b24edfb22c0 during setup.
- An eight-byte temporary area used in extraction and interpretation preparation.
- A signed 32-bit length slot whose address is passed to F-2884b93238c7.
- A four-byte payload area whose address is passed to F-40e5dda1c270 and F-7c153e68bade.

These are visible storage extents, not established public types or dependency write extents.

The two calls to F-5b24edfb22c0 are setup-shaped calls. No supplied implementation or contract establishes that either call initializes its area, writes any particular bytes, or confines its effects to eight bytes. Subsequent references therefore distinguish the **first area** and **second area**, without assuming either contains initialized state.

The caller does not explicitly initialize the length slot before exposing its address. The slot persists across iterations and is not reset by the caller. F-2884b93238c7 may write it, but neither a write on every path nor preservation across later calls is established.

For the payload area, the caller explicitly clears bytes +3, +2, and +1 on each accepted-candidate path. It does not explicitly initialize byte +0. F-40e5dda1c270 subsequently receives the area’s address, but its write extent and resulting representation are unknown.

Local-address retention is not ruled out. Safe use after the function returns is not established.

### Mapping table

A global slot supplies the table base. The function captures that base once, after the first primary search. Records have a 12-byte stride.

| Record offset | Width | Visible use |
|---|---:|---|
| +0 | 1 byte | Exactly 1 stops lookup; a later reread selects fallback mapping when still exactly 1. |
| +1 | 1 byte | Read as an unsigned mapped value on the nonfallback path; independently reread after application to decide advancement. |
| +8 | 32 bits | Compared against the full interpreted candidate during lookup. |

Bytes +2 through +7 are not directly read by this function.

There is no table count or bounds check. Valid traversal requires accessible records through a stopping record: either its first byte is exactly 1, or its first byte is not 1 and its +8 field equals the candidate. This is an environmental precondition, not a validated property.

### Numeric widths and preconditions

The interpreted candidate is 32 bits. Table matching compares all 32 bits. Acceptance treats the same bits as signed:

- 0x00000001 through 0x7fffffff are accepted.
- Zero and 0x80000000 through 0xffffffff are rejected.

Positions, the length slot, and the table index are signed 32-bit quantities in the supplied representation. Visible arithmetic includes:

- Object field +0x30 plus 0x24.
- Position plus length.
- Position plus one.
- Length plus one.
- Table-index increment and multiplication by 12.
- Address calculations for fields and records.

No explicit overflow checks are present. Examples below assume representable arithmetic and valid address calculations. Overflow behavior and invalid-address behavior remain **documented_only**; wraparound is not promised.

## Behavior

### Setup and first primary search

The visible setup order is:

1. Call F-5b24edfb22c0 with the first area’s address.
2. Call F-5b24edfb22c0 with the second area’s address.
3. Read object field +0x30, add 0x24, and pass the result to F-826f25835f54.
4. Read the returned resource’s +4 field and pass it to F-d8cbf9aa79a9.
5. Call F-a21141daa905 with the retained resource, a fixed primary search operand, and start position zero.
6. Read and retain the global table base.

The first two calls establish call order and address exposure only. They do not establish initialization, allocation, or ownership.

The table-base read occurs even if the first primary search returns −1. Changes to the global slot made by earlier dependencies therefore affect the captured base. Later changes to that slot do not cause the function to reacquire the base. Table contents remain subject to later reads; they are not copied or frozen.

### Primary termination

At the start of each iteration, the current primary-search result is compared with −1.

If equal, the function calls F-289ec4311c64 with the second area, then with the first area, and returns. The second area has no other visible use after its setup-shaped call.

These termination calls are finalization-shaped, but no supplied contract establishes destruction, memory release, ownership, or required prior initialization.

No other primary-search result explicitly terminates iteration. A negative result other than −1 proceeds into extraction unless a dependency contract, not supplied here, excludes it.

### Extraction and interpretation

For a primary result other than −1, the following dependency interactions occur in order:

1. F-ed33cfb647fe receives the temporary area, retained resource, and current position.
2. F-46f0b3cb316e receives the first area and temporary area.
3. F-289ec4311c64 receives the temporary area.
4. F-b9acea4b06ad receives the temporary area and first area.
5. F-2884b93238c7 receives the original object address, the preceding call’s return value, and the length-slot address.
6. F-289ec4311c64 receives the temporary area again.

F-2884b93238c7 returns the 32-bit candidate. Its effects on the length slot are unspecified.

The final temporary-area call occurs after the length-slot address has been exposed. The caller does not preserve an independent copy of any interpreter-written length before that call. If retained or aliased access permits a dependency to modify the slot, a later length read can observe that modification.

The reuse of temporary storage and the names suggested by the call pattern do not establish copying, valid object construction, ownership transfer, or release.

### Lookup before candidate rejection

Lookup starts at record zero. At each record, the function reads the first byte.

- If that byte is exactly 1, lookup stops without reading that record’s +8 field for comparison.
- Otherwise, the function reads the 32-bit +8 field and compares it with the full candidate.
- Equality stops lookup; inequality advances to the next record.

Only after selecting a record does the function test whether the candidate is signed-positive.

For a rejected candidate:

- No secondary search occurs.
- No payload clearing or F-40e5dda1c270 call occurs.
- No F-7c153e68bade application occurs.
- The current position increases by one.
- The next primary search starts at that increased position.

Rejection does not bypass table traversal. Zero and high-bit candidates still require a safely reachable stopping record.

### Secondary search and length adjustment

For an accepted candidate, the function reads the length slot after the final temporary-area call and table lookup. It adds that observed value to the current position and retains the result as the secondary-search start.

F-a21141daa905 is then called with the retained resource, a distinct fixed secondary operand, and that calculated start.

The secondary result is compared with the already calculated start:

- If equal, the caller reads the then-current length slot, adds one, and writes the result back.
- If unequal, the caller performs no length-slot write at this decision point.

These are separate state observations. The value used to calculate the search start need not equal the value incremented after the search. The search may affect exposed storage through retained or aliased access; no preservation contract is supplied.

The rule is exact equality, not general search success. A result at a different position does not trigger the increment. If the calculated start is −1, a secondary result of −1 also satisfies equality; the function has no separate sentinel exclusion here.

The secondary result does not directly determine the next primary-search position.

### Payload selection and application

After the secondary-search decision, the caller clears payload bytes in this order:

1. Byte +3.
2. Byte +2.
3. Byte +1.

Byte +0 has no explicit caller initialization.

The selected record’s first byte is then reread:

- Exactly 1 selects the candidate’s low eight bits.
- Any other value selects the record’s +1 byte, read and widened as unsigned.

The resulting numeric argument is between 0 and 255 inclusive. F-40e5dda1c270 receives that value and the payload address. This is a payload-construction-shaped call, not proof that a particular payload representation is produced.

The mapping decision uses record contents observed after the secondary search. A record originally selected by candidate equality may later select fallback if its first byte becomes 1. A record originally selected by its first byte may instead use its +1 byte if that first byte changes away from 1.

After F-40e5dda1c270 returns, F-7c153e68bade receives:

- The object’s then-read +0x34 field.
- The current position.
- The then-read length slot.
- The payload address.

The supplied representation does not establish a relative order between the target-field read and length-slot read. Both supply the application call after F-40e5dda1c270 returns.

The applied length need not equal the interpreter’s earlier output, the length used to calculate the secondary start, or the value immediately after conditional increment. Likewise, payload bytes explicitly cleared earlier are not guaranteed to remain zero after F-40e5dda1c270.

### Next primary-search position

After application returns, the function rereads the selected record’s +1 byte.

- If it equals the character value for `&`, the current position increases by one.
- Otherwise, the current position remains unchanged.

The next primary search uses that position and the fixed primary operand.

This discriminator is read even when fallback supplied the payload value. Because the read occurs after application, application-time table mutation can affect advancement.

The function does not advance by the applied length. There is no explicit iteration bound or independent progress guard. Repeated search results and nontermination remain possible unless the dependencies or environment ensure progress.

## Acceptance examples

These are conditional static examples, not executed tests. Each assumes returning dependencies, accessible storage, and representable arithmetic.

1. **Immediate termination.** If the first primary search returns −1, both setup-shaped calls have already occurred, and the global table base is still read. F-289ec4311c64 receives the second area before the first. No extraction or application occurs. Nothing in this example requires or establishes that either area was initialized.

2. **Rejected candidates still require lookup.** If interpretation returns zero, lookup reaches a stopping record before rejection. The next primary search starts one position later. Candidate 0x80000001 is also rejected after lookup, although its full 32-bit value participates in table comparison.

3. **Stable ordinary mapping.** Suppose the current position is 10, the candidate is 300, and the length read for the secondary start is 4. Assume the length remains unchanged through application argument capture, the selected record’s first byte remains non-1 through mapping, and its mapped byte is 65 when read. A secondary result other than 14 causes no caller increment; application receives length 4, and F-40e5dda1c270 receives 65.

4. **Stable exact secondary match.** Under the same preservation premises, secondary result 14 causes application with length 5. Result 15 does not trigger the increment.

5. **Length changes during secondary search.** Position 10 and observed length 4 produce start 14. If the search changes the exposed length slot to 8 and returns 14, the caller increments the then-current value to 9. If F-40e5dda1c270 subsequently changes it to 12, application receives length 12. Neither modification changes the already calculated start.

6. **Intervening temporary-area call changes length.** If interpretation writes 4 but the following F-289ec4311c64 call changes the exposed slot to 6, position 10 produces secondary start 16, provided the slot remains 6 until that calculation. This is conditional behavior, not evidence that the dependency actually performs such a write.

7. **Fallback and independent advancement.** For candidate 0x1234, a selected record whose first byte is 1 at mapping time supplies 0x34 to F-40e5dda1c270. If its +1 byte is `&` at the post-application read, the next primary search starts one position later. Fallback does not eliminate that advancement read.

8. **Record mutation changes later decisions.** A record selected by full-width equality may have its first byte changed to 1 during the secondary search. Mapping then uses fallback. If application changes its +1 byte to `&`, advancement uses that later value.

9. **Secondary sentinel equality.** If position plus observed length is representably −1, a secondary result of −1 triggers the length increment. It does not terminate the function; termination is tied to the primary-search result.
