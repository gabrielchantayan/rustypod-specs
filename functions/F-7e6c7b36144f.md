# F-7e6c7b36144f

## Purpose

F-7e6c7b36144f obtains one 40-byte slot from a state-managed collection and clears selected fields within that slot. It prefers a slot from an available-slot chain. If that chain is empty, it consumes the next slot from the current storage region, allocating a new region when the current cursor equals the region limit.

The function has no explicit return value. Its observable results are changes to the supplied state, possible allocation and publication of a new region, and partial initialization of the selected slot.

The interpretation as a reusable-slot pool is inferred intent. The established behavior is the selection, allocation, linking, cursor advancement, and memory writes described below. In particular, this function does not completely zero a slot and does not directly return the selected slot’s address.

## Interface

### Input and representation

The sole explicit input is a pointer to writable state containing four consecutive 32-bit words:

| Byte offset | Contract name | Observed role |
|---|---|---|
| 0 | Region head | Address of the current region descriptor, or zero |
| 4 | Available head | Address of the next reusable slot, or zero |
| 8 | Cursor | Address of the next unconsumed slot in the current region |
| 12 | Limit | Address compared with the cursor to determine whether a new region is needed |

The supplied representation uses 32-bit address-bearing words. A port to a wider pointer model cannot preserve this layout merely by replacing these words with native pointers.

A region descriptor occupies 12 bytes:

| Byte offset | Field | Observed role |
|---|---|---|
| 0 | Previous region | Address copied from the state’s region head when the descriptor is linked |
| 4 | Capacity | Unsigned 32-bit slot count |
| 8 | Storage base | Address returned by the storage allocation request |

Each slot occupies 40 bytes. The function accesses these portions of a selected slot:

| Byte offset | Width | Observed use |
|---|---|---|
| 0 | 1 byte | Cleared during initialization |
| 4 | 4 bytes | Cleared during initialization |
| 8 | 4 bytes | Cleared during initialization |
| 12 | 4 bytes | Read as the next available-slot address on the reuse path, then cleared |

Bytes 1–3 and 16–39 are not initialized by this function.

### Output

There is no explicit return value and no output parameter receiving the selected slot address.

The state changes identify consumption of a slot, but the supplied evidence does not establish how another operation subsequently obtains or uses that slot.

### Preconditions

For an execution to complete through the observed accesses:

- The state must be readable and writable at the fields accessed on the chosen path.
- Every nonzero address dereferenced must refer to accessible memory with the alignment required by the represented 32-bit accesses.
- An available slot must permit a 32-bit read at offset 12 and the initialization writes listed above.
- An existing region descriptor used for growth must permit a 32-bit capacity read at offset 4.
- Allocation results used by the growth path must support the subsequent descriptor and slot accesses.
- The cursor and limit must encode a valid storage arrangement if the caller expects bounded slot consumption. Equality is the only exhaustion check.

The function does not validate these conditions. No independent null-state check, bounds check, overflow check, or allocation-failure branch is established.

## Behavior

### Selection precedence

The available head is read first.

If it is nonzero, that address is the selected slot. The function reads the 32-bit word at selected-slot offset 12 and writes that value to the state’s available head. It then initializes the selected slot.

This path does not explicitly inspect or update the region head, cursor, or limit. It does not call the allocation dependency. Thus an available slot takes precedence even when the cursor equals the limit.

If the available head is zero, the cursor is read and compared with the limit.

- If the two addresses differ, the cursor address becomes the selected slot.
- If the two addresses are equal, the function obtains a new region before selecting its first slot.

The comparison is equality, not an ordering or remaining-capacity check. A cursor beyond the limit, or fewer than 40 usable bytes before the limit, does not independently trigger growth.

### Growth capacity

When growth is needed, the function reads the region head.

If the region head is zero, the new capacity is 32 slots.

Otherwise, it reads the unsigned 32-bit capacity from offset 4 of that descriptor. Let that value be \(n\). The two candidates are:

- Additive candidate: \(A = (n + 32) \bmod 2^{32}\).
- Proportional candidate: \(B = (n + \lfloor n/2 \rfloor + \lfloor n/8 \rfloor) \bmod 2^{32}\).

The new capacity is the larger of the two wrapped candidates under unsigned comparison. Equal candidates produce the same numerical result.

The shifts are applied separately to the original capacity. Consequently, the proportional candidate is not necessarily equal to a single rounded multiplication by \(13/8\).

This is 32-bit arithmetic, not unbounded arithmetic. The function does not reject a capacity because either candidate wrapped. The byte count for storage is also calculated with 32-bit multiplication:

\[
\text{requested bytes} = (40 \times \text{new capacity}) \bmod 2^{32}.
\]

No minimum is imposed after wrapping, and no explicit check establishes that the requested byte count can hold the nominal number of slots.

### Allocation and publication

The growth path calls F-871e64ddc6de twice, in this order:

1. Request 12 bytes, with a second argument of zero.
2. Request the calculated storage byte count, again with a second argument of zero.

The result of the first call is used as the new region descriptor address. The result of the second call is used as its storage address.

After both calls return, the visible write and read sequence is:

1. Store the storage result in the new descriptor at offset 8.
2. Read the state’s current region head and store it in the new descriptor at offset 0.
3. Store the calculated capacity in the descriptor at offset 4.
4. Publish the descriptor address in the state’s region-head field.
5. Read the storage-base field back from descriptor offset 8 and use that address as the selected slot.
6. Store the selected address plus the calculated storage byte count in the state’s limit.
7. Store the selected address plus 40 in the state’s cursor.
8. Initialize the selected slot.

The region head copied into the descriptor is read after both dependency calls. It is not necessarily the same value used earlier to decide or calculate capacity. The function also reads the descriptor’s storage-base field after publication rather than relying solely on the earlier allocation result.

These distinctions matter if the dependency or overlapping memory changes the state or descriptor. The evidence does not establish that the dependency preserves either.

### Consumption without growth

When the available head is zero and cursor differs from limit, the existing cursor address is selected. Before slot initialization, the state’s cursor is advanced by 40 bytes.

This path contains no allocation call, no descriptor access, and no explicit region-head or limit update.

### Slot initialization

On every path that reaches initialization, the selected slot receives these writes in order:

1. A 32-bit zero at offset 4.
2. A 32-bit zero at offset 8.
3. A 32-bit zero at offset 12.
4. A one-byte zero at offset 0.

The function does not read the prior values of these fields during initialization. On the reuse path, the old value at offset 12 has already been read and installed as the new available head before being cleared.

The distinction between the byte write at offset 0 and the three 32-bit writes is part of the contract. The first four bytes of the slot are not all cleared.

## Side effects

### State transitions

Under ordinary nonoverlapping storage and a dependency that does not independently mutate the state:

| Path | Available head | Region head | Cursor | Limit |
|---|---|---|---|---|
| Reuse available slot | Replaced with selected slot’s prior next address | Unchanged | Unchanged | Unchanged |
| Consume current region | Remains zero | Unchanged | Advanced by 40 | Unchanged |
| Allocate region | Remains zero | Replaced with new descriptor | New storage base plus 40 | New storage base plus calculated byte count |

These are direct effects of this function, not guarantees about unknown dependency side effects.

### Ownership and lifetime

The function links a newly allocated descriptor into the state and records its storage allocation. It does not explicitly release either allocation, release any older region, destroy slot contents, or invoke a slot-specific callback.

The available-slot path removes the selected slot from the head of the available chain by replacing that head with its recorded successor.

These operations suggest retention of regions for later reuse or release elsewhere. Actual ownership rules, lifetime guarantees, and the identity of any eventual releasing operation are not established.

### Errors and partial progress

No explicit status reporting or rollback is present.

- Failure of the first allocation is not checked before the second request.
- Failure of either allocation is not handled by an explicit branch before its result is used.
- The available head is updated before reuse-path initialization.
- The cursor is advanced before initialization on the current-region path.
- A new descriptor is published before the new limit, cursor, and slot initialization are complete.

If execution is interrupted by an invalid access or dependency failure, partial state changes may therefore already have occurred. The exact external failure mechanism is unknown.

No locking or atomic publication protocol is established.

## Acceptance examples

These examples are conditional on valid, suitably aligned, nonoverlapping memory and on dependency behavior stated within each example. They are specifications derived from static evidence, not observed test results.

### Available slot overrides region exhaustion

Given a nonzero available head and cursor equal to limit:

- The available slot is selected.
- Its prior 32-bit value at offset 12 becomes the available head.
- No allocation request occurs.
- Cursor and limit receive no direct writes.
- Slot offsets 4, 8, and 12 become 32-bit zero; offset 0 becomes a zero byte.

### Consume an existing slot

Given an available head of zero and a cursor identifying a valid slot distinct from limit:

- The cursor’s original address is selected.
- Cursor advances by 40 before initialization.
- No allocation request occurs.
- The selected slot receives only the specified initialization writes.

In particular, nonzero sentinel bytes at offsets 1–3 and 16–39 remain unchanged absent aliasing or external mutation.

### Allocate the initial region

Given no available slot, cursor equal to limit, and a zero region head:

- The requested capacity is 32.
- The two dependency requests are for 12 bytes and 1,280 bytes, in that order, each with second argument zero.
- If the dependency returns valid separate allocations and leaves the state unchanged, the new descriptor records a zero previous-region address.
- The new cursor is storage base plus 40.
- The new limit is storage base plus 1,280.
- The first storage slot is partially initialized.

### Growth candidates cross over

Given exhaustion of a region whose recorded capacity is 32, the candidates are 64 and 52. The new capacity is 64, and the storage request is 2,560 bytes.

Given exhaustion of a region whose recorded capacity is 64, the candidates are 96 and 104. The new capacity is 104, and the storage request is 4,160 bytes.

### Shift rounding remains observable

Given an exhausted region with recorded capacity 101, the proportional candidate is \(101 + 50 + 12 = 163\), while the additive candidate is 133. The chosen capacity is 163, not 164, and the storage request is 6,520 bytes.

### Invalid cursor ordering is not repaired

Given a zero available head and unequal cursor and limit, the function takes the existing-region path even if the cursor is numerically beyond the limit. It advances the cursor and attempts initialization at the original cursor. Successful completion still requires that memory to be accessible.
