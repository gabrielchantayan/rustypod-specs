# F-e8e67147c5d5

## Purpose

F-e8e67147c5d5 coordinates a chunked operation between two externally supplied objects. It derives a 32-bit work total from an object-provided value and a caller-provided multiplier, prepares each chunk through one object, requests an exact-sized operation from the other, and advances a position after each exact result.

Two distinct failure paths are visible:

- A nonzero preparation result invokes an object-specific handler.
- A result different from the requested chunk size invokes F-7f008c1060db with status value 34.

**Inferred intent:** the function resembles a block-oriented transfer or processing loop, with a four-word descriptor identifying working storage. The supplied evidence does not establish a transfer direction, measurement units, or the descriptor’s interpretation. Those interpretations are not required by this contract.

## Behavior

### Initialization

The following events occur in order:

1. F-603a53835f04 is called with the context input followed by three zero values.
2. Its 32-bit result is retained as an opaque token.
3. The object reference at state-record offset 0x00 is read, its dispatch table is accessed, and the value-provider operation at offset 0x24 is invoked.
4. The provider’s 32-bit result is multiplied by the multiplier to initialize the remaining-work value.

The remaining-work value is used as an **unsigned 32-bit quantity**. The multiplication has no visible widening or overflow check. Its operational result is the low 32 bits of the product; callers must not treat it as an unbounded mathematical count. The supplied representation does not independently establish language-level signed-overflow semantics.

Initialization occurs even if the resulting remaining-work value is zero.

### Iteration entry and chunk selection

At the top of each iteration, zero remaining work causes an immediate ordinary return.

Otherwise:

1. The current object reference is read from the state record and retained for the upcoming preparation call.
2. The 32-bit word at record offset 0x34 is read as an unsigned chunk bound.
3. The requested chunk is the smaller of that bound and remaining work, using an unsigned comparison.

A word with its high bit set is therefore a large unsigned bound, not a negative limit.

The retained object’s value-provider operation at dispatch offset 0x24 is then invoked. The requested chunk and the provider result are passed, in that order, to F-d7be9cfb4000.

For the subsequent preparation call, **only the low 16 bits** of F-d7be9cfb4000’s result are retained. There is no visible check for loss of higher bits.

### Preparation

After the value-provider and helper calls return, the function reads the descriptor words at offsets 0x30, 0x34, 0x38, and 0x3C, in that order, into a temporary four-word descriptor.

The preparation operation at dispatch offset 0x04 is then called with:

1. The object reference retained earlier in the iteration.
2. A pointer to this temporary descriptor.
3. The current position.
4. The 16-bit helper result.

This timing is significant:

- The requested chunk was selected before the provider and helper calls.
- The descriptor is copied after those calls.
- Consequently, descriptor word two need not equal the bound used to select the chunk if a dependency changes the record.
- The object used for preparation is the retained object, even if the state record’s object reference changes meanwhile.
- The preparation dispatch entry is fetched from that retained object for the call; its dispatch table is not established to remain unchanged.

A preparation result of zero permits the chunk operation. Any nonzero result selects the preparation-failure path.

### Preparation-failure path

After a nonzero preparation result:

1. The object reference is fetched again from state-record offset 0x00.
2. Its dispatch-table entry at offset 0x68 is invoked with that object reference and the retained token from initialization.
3. If that handler returns, this function returns.

The chunk operation is not invoked for this iteration. Remaining work and position are not advanced for the failed chunk.

The failure handler can belong to a different object from the one that received preparation if an intervening call changed the state record.

### Chunk operation

After a zero preparation result, the descriptor is copied again from state-record offsets 0x30 through 0x3C, in field order, into a separate temporary four-word descriptor.

This is a fresh read of the record. It is not a copy of the preparation temporary. Direct changes to the preparation temporary do not become this second descriptor; changes to the underlying record can.

The operation object’s dispatch entry at offset 0x10 is invoked with:

1. The operation-object reference.
2. The requested chunk as a 32-bit value.
3. A pointer to the second temporary descriptor.

Its result is interpreted as an unsigned 32-bit count and compared with the requested chunk.

If the result is **not exactly equal** to the request, F-7f008c1060db is called with:

1. The retained initialization token.
2. Status value **34**, hexadecimal **0x22**.
3. Zero.
4. Zero.

If that dependency returns, the function immediately returns. Both short results and oversized results take this path. There is no visible retry, partial-progress accounting, or rollback.

The object-specific preparation-failure handler is not called on this path.

### Exact-result progress

When the chunk result exactly matches the request:

1. The result is subtracted from remaining work.
2. The state record’s object reference is fetched again.
3. That object’s value-provider operation at dispatch offset 0x24 is invoked.
4. F-d7be9cfb4000 is called with the completed count and this new provider result.
5. The helper’s 32-bit result is added to the current position.
6. Execution returns to the iteration-entry check.

Unlike the preparation argument, this helper result is **not truncated to 16 bits** before position advancement. Position addition has no visible overflow check or wider intermediate.

The progress helper and final provider call still occur after a chunk reduces remaining work to zero. Completion is recognized only at the next iteration-entry check.

### Zero-sized chunks and termination

If remaining work is nonzero but the current chunk bound is zero, the function requests a zero-sized chunk.

If preparation succeeds and the chunk operation returns zero:

- The equality check succeeds.
- Remaining work is unchanged.
- The post-operation provider and helper calls still occur.
- Position is updated by the helper’s result.
- Another iteration begins.

There is no built-in zero-progress rejection. Repetition can continue indefinitely if external behavior never changes the bound or produces a terminating failure.

With a positive chunk bound and exact chunk results, remaining work decreases each successful iteration. This conclusion assumes the dependencies return normally; it does not establish that the whole function always terminates.

## Side effects

The visible body does not directly write to the caller’s state record or operation object. Its direct writes are to temporary descriptors and internal scalar state.

Externally observable effects can occur through every dependency and indirect operation. In particular:

- Preparation and chunk operations receive writable pointers to temporary descriptor copies.
- Those copies contain the same four 32-bit values read from the record. If a word represents an address or handle, copying it does not duplicate its referent.
- A dependency may modify shared objects, dispatch tables, descriptor referents, globals, or other externally accessible state. The visible body supplies no preservation guarantee.
- Record changes can affect later reads, including the descriptor copied immediately after preparation.
- Position is maintained internally and supplied to later preparation calls. It is not returned or written to an explicit caller-provided position field.

No allocation, deallocation, reference-count operation, or explicit ownership transfer is visible. The retained token’s ownership is unknown. No explicit token-release call appears on ordinary completion.

Temporary descriptors are valid as local call storage. The evidence does not establish a contract allowing callees to retain their addresses after the calls return.

Failure reporting does not imply rollback. The function neither restores descriptor referents nor reverses effects already performed by a dependency.

## Acceptance examples

These are conditional contract examples, not observed executions.

1. **Zero initial work.**  
   If the initial provider result multiplied by the multiplier produces zero in 32 bits, the function calls F-603a53835f04 and the initial provider, then returns. It does not select a chunk, copy a descriptor, or invoke either failure path.

2. **Two exact chunks.**  
   Suppose initialization yields 12 units, the chunk bound remains 8, and preparation always returns zero. If the chunk operation returns exactly each request, its requested counts are 8 and then 4. Each exact result is followed by a fresh provider call and a progress-helper call, including the final result of 4.

3. **Preparation failure.**  
   For any nonzero preparation result, the current state-record object’s slot 0x68 receives the initialization token. The chunk operation and mismatch reporter are not invoked for that iteration.

4. **Short or oversized result.**  
   If a requested count is 8 and the chunk operation returns 7 or 9, F-7f008c1060db receives status 34. The function performs no progress-helper call for that result and makes no subsequent chunk request if reporting returns normally.

5. **Descriptor changed during preparation.**  
   If preparation changes the underlying record’s descriptor, the chunk operation receives a fresh snapshot reflecting the record when its second copy occurs. If preparation changes only its temporary descriptor, that change alone does not alter the second copy.

6. **Different helper-result widths.**  
   If a pre-preparation helper result has bit pattern 0x00010002, preparation receives the retained 16-bit value 2. If a post-operation helper result has that same bit pattern, position is advanced by the full 32-bit value 65,538, subject to 32-bit arithmetic.

7. **Zero bound with positive remaining work.**  
   If the bound remains zero, preparation succeeds, and the chunk operation repeatedly returns zero, remaining work never decreases. The function does not reject this condition automatically.

8. **Product wraps to zero.**  
   If the initial provider returns 0x00010000 and the multiplier is 65,536, the low 32 bits of the product are zero. Under the represented 32-bit arithmetic, the function returns after initialization rather than processing 4,294,967,296 units.
