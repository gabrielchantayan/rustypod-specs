# F-965c38ad2747

## Purpose

The represented procedure performs byte-wide memory writes, invokes unresolved dependencies, and enters a repeated call-and-write phase with no represented exit.

No application-level purpose is established. The evidence does not identify a protocol, allocator, device operation, or data format. This contract describes observable accesses, dependency invocation order, argument transformations, and carried state without assigning those operations an application meaning.

The supplied representation reports invalid instruction data and removal of unreachable regions. All behavioral statements are conditional on the represented path corresponding to executable behavior and on preceding operations completing normally.

### Widths, layout, and conversions

The representation uses unsigned and signed 32-bit arithmetic values, unsigned eight-bit selector reads, and one-byte stores. It establishes no surrounding structure layout, buffer length, allocation extent, alignment contract, or ownership relationship.

A selector byte selects an absolute numeric destination by adding 17 to its unsigned value. Such destinations range from `0x11` through `0x110`, inclusive. They are not established offsets within the context.

The fourth-input-derived write address is the fourth input logically shifted right by seven, plus 28. This unsigned calculation ranges from `0x0000001c` through `0x0200001b` and does not overflow 32 bits.

Three stores first convert their values to a plain character type. The representation does **not** by itself establish that every such conversion preserves the low eight bits. In particular:

- Conversion of an unsigned input outside the character type’s range requires target-specific interpretation.
- Conversion of a signed intermediate outside the character type’s range also requires target-specific interpretation.
- A byte-wide destination alone does not resolve either conversion.

This contract uses **low-bit-preserving target interpretation** to mean that the relevant conversions produce the low-order bit patterns described below. It is an assumption, not an unconditional property of the represented operations.

## Behavior

### Arithmetic rules and qualifications

Unsigned 32-bit right shifts are logical. Unsigned left shifts retain the low 32 bits.

Signed left shifts are not assigned a general wrapping interpretation here. Negative operands or results outside the signed 32-bit range leave the represented arithmetic unresolved. Signed multiplication and addition likewise require representable results unless a separate machine-arithmetic assumption is made.

The unsigned result of dependency D12 is shifted left by two in unsigned 32-bit arithmetic. The resulting unsigned value is then assigned to a signed 32-bit intermediate. That conversion is numerically established when the unsigned value is at most `0x7fffffff`. Above that boundary, the supplied representation does not establish the signed result or guarantee continuation.

Only after that conversion does the fourth-input-addressed store convert the intermediate to the character type. Thus both conversions matter to the stored byte.

Dependency labels D01–D36 below abbreviate the opaque identifiers **F-965c38ad2747-D01** through **F-965c38ad2747-D36**. They identify invocation sites, not proven semantic callees.

### Initial selected writes and calls

The first direct data-memory operation reads the unsigned selector byte at the incoming context base plus one. The procedure adds 17 to that byte and performs a one-byte store at the selected address. The stored value is obtained by converting the first input to the character type.

Under the low-bit-preserving target interpretation, this stores the first input’s low eight bits. That bit extraction is not an unconditional conversion guarantee.

D01 follows. It receives three explicit arguments, each equal to the second input. Its target is calculated from the incoming control-location value plus `0xfec`. The validity and arithmetic interpretation of that incoming-value calculation remain preconditions.

D02 produces an opaque 32-bit result, which is passed to D03. D04, D05, and D06 follow in order. D07 then produces a represented signed 32-bit result.

After D07 returns, the procedure rereads the selector at the context base plus one. It performs another selected one-byte store, this time after logically shifting the first input right by 22 and converting the result to the character type.

Under the low-bit-preserving target interpretation, the second stored byte contains original input bits 22–29. The shifted value can be as large as 1023, so its conversion is not universally within an eight-bit character type’s range.

The selector read is fresh. The two selected destinations need not be equal.

D08 receives the D07 result shifted left by two, subject to the signed-shift qualification. D09, D10, and D11 follow. D12 then produces an unsigned 32-bit result.

### D12 conversion and fourth-input-addressed store

The procedure performs these value transformations in order:

1. D12’s result is shifted left by two using unsigned 32-bit arithmetic.
2. That unsigned result is assigned to a signed 32-bit intermediate.
3. The intermediate is converted to the character type for a one-byte store.

The store address is the fourth input logically shifted right by seven, plus 28.

**Conditional stored-byte formula:** if the unsigned-to-signed conversion and subsequent character conversion preserve the required low bits and complete normally, the stored byte equals four times D12’s low six bits. Under those assumptions, its unsigned byte interpretation is a multiple of four between 0 and 252.

Without those assumptions, the representation establishes the conversion sequence and destination, but not that formula or range.

For example, D12 result `0x20000000` produces unsigned shifted value `0x80000000`. The intervening signed conversion is outside the signed 32-bit numeric range. A stored byte of zero follows under the stated low-bit-preserving interpretation, not unconditionally from the supplied representation.

After this store, the procedure rereads the context selector and writes zero to the selected address. The fourth-input-addressed store precedes that read and zero store. It may therefore affect the selector if the addresses alias.

D13 receives the fourth input logically shifted right by seven. D14 follows. D15 receives D12’s original bits 6–29, shifted down into an unsigned value from zero through `0x00ffffff`. This extraction does not depend on the intervening signed conversion.

D16, D17, and D18 follow. D19 produces a represented signed 32-bit result. The procedure then rereads the context selector and performs another selected zero store.

### Result-derived selector and loop entry

D20 receives the D19 result shifted left by two, subject to the signed-shift qualification. D21, D22, and D23 follow. D24 produces an unsigned 32-bit result.

The procedure extracts D24 bits 25–29 as an unsigned value from zero through 31.

A new selector address is formed from the signed intermediate retained from the D12 conversion: multiply that intermediate by 1024, then add one. The procedure reads an unsigned byte at that address and writes zero at the resulting byte value plus 17.

The represented multiplication and addition require signed-range validity. Under an additional wrapping 32-bit machine-arithmetic interpretation, together with a low-bit-preserving D12 conversion, the selector address is the low 32 bits of D12 shifted left by 12, plus one. That simplification is conditional, not the unconditional address contract.

D25 receives twice the five-bit extraction from D24. Its explicit argument is therefore even and ranges from zero through 62.

D26 produces the signed 32-bit first argument for the first repeated-phase invocation. Immediately before D26, the representation establishes control-location value `0x08832789`, which supplies the first D27 target calculation.

## Acceptance examples

These are conditional static criteria, not executed tests. They assume accurate represented control flow, valid accesses, and normally completing preceding operations.

### First-input conversions

For first input 1, the initial selected store writes 1 and the second writes zero; both converted values are representable.

For first input `0x00400000`, the low-bit-preserving character interpretation yields initial byte zero and second byte one. Only the second conversion is directly within the character range.

For `0xffffffff`, that interpretation yields `0xff` for both stores. These byte patterns must not be asserted without the conversion assumption.

### Fresh selection

Selector value 5 selects address 22; selector value 9 selects address 26. If an intervening dependency or store changes the selector from 5 to 9, the later store must use address 26.

### Fourth-input boundaries

Fourth inputs zero through 127 select address 28 and supply zero to D13. Input 128 selects address 29 and supplies one.

Input `0xffffffff` selects `0x0200001b` and supplies `0x01ffffff` to D13.

### D12 conversion boundaries

If D12 returns 3, the unsigned shift produces 12, the signed intermediate is 12, and the character conversion stores 12. The later derived selector address is `0x3001`; this example requires no overflowing multiplication.

If D12 returns `0x12345678`, the unsigned shifted value is `0x48d159e0`, within signed 32-bit range. D15 receives `0x0048d159`. The stored byte is `0xe0` only under the low-bit-preserving character interpretation; the later signed address multiplication is outside the representable range.

If D12 returns `0x20000000`, the unsigned shifted value is `0x80000000`. The signed conversion is unresolved. The contract does not unconditionally require a zero byte or even progression to the store. With low-bit-preserving conversions, the byte would be zero.

### Target and carry transitions

If two D27 invocations are reached, their represented targets are respectively `0x08833787` and `0x088337c5`. Using the first target for both would not match the represented state transition.

For every D24 result, D25 receives an even value from zero through 62, and the first D27 second argument is zero.

If D36 returns 3, both carry-producing signed shifts are representable. The next D27 receives 12 and `0x000c0000`, at target `0x088337c5`.
