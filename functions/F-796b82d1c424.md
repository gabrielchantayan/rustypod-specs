# F-796b82d1c424

## Purpose

F-796b82d1c424 conditionally traverses a circular collection of callback entries. For each visited entry whose callback slot is nonzero, it invokes the selected callback with three arguments:

1. A 32-bit value read from the caller-supplied object.
2. The caller’s opaque 32-bit argument.
3. A truth value derived from whether a previously sampled signed 32-bit field is greater than zero.

Traversal is anchored to the entry selected at the beginning. That entry is processed, not skipped as a sentinel. Traversal ends when a subsequently obtained next-entry pointer equals that original entry address.

**Established behavior:** conditional traversal, callback argument selection, callback order, and the termination comparison described below.

**Inferred intent:** notification or event dispatch across registered handlers. The source does not establish application-level meanings for the object, entries, callback arguments, or signed field.

## Interface

### Inputs

The function accepts two arguments:

| Argument | Representation | Role |
|---|---|---|
| Object address | Address represented by a 32-bit integer in the supplied source model | Locates an indirect state pointer and the first callback argument. |
| Forwarded value | Opaque 32-bit value | Passed unchanged as the second argument of every callback actually invoked. |

The object address is used as a memory address, not as an ordinary numeric identifier. The function provides no null, bounds, alignment, or accessibility checks.

### Referenced layout

All offsets below are byte offsets. The supplied representation uses four-byte pointer and scalar slots.

| Region | Offset | Required contents |
|---|---:|---|
| Input object | `0x24` / 36 | Pointer to a state region |
| Input object | `0x90` / 144 | Opaque 32-bit value used as a callback’s first argument |
| State region | `0x00` / 0 | Zero or an address locating the collection holder |
| State region | `0x54` / 84 | Signed 32-bit field used for the positivity test |
| Collection holder | `0x10` / 16 | Pointer to the initial entry |
| Each entry | `0x00` / 0 | Zero or a callback address |
| Each entry | `0x10` / 16 | Pointer to the next entry |

These are minimum access requirements, not complete structure definitions. No meaning is established for intervening bytes.

The input object’s state pointer is read once to obtain the collection-holder address. If that address is nonzero, the state pointer is read again to obtain the signed field. The source therefore does not establish that these two accesses must use the same state region if external mutation is possible.

### Output and completion

There is no explicit return value. Callback return values, if any, are ignored.

Normal completion occurs either:

- Immediately after finding a zero collection-holder address; or
- After traversal obtains a next-entry address equal to the original entry address.

No error result, status flag, or explicit recovery path is present.

## Behavior

### Initial selection

The function first reads the state pointer at object offset 36, then reads the 32-bit address at offset zero of that state region.

If the resulting collection-holder address is zero, the function returns immediately. On that path it does not read:

- The signed field at state offset 84.
- The holder’s initial-entry pointer.
- The object field at offset 144.
- Any entry or callback slot.

The zero test applies to the address read **from** the state region. It is not a null check on the state pointer itself. A null or otherwise invalid state pointer is dereferenced before any such protection could apply.

### Traversal setup

When the collection-holder address is nonzero, the function performs the following source-level accesses in order:

1. Reads the state pointer from object offset 36 again.
2. Reads the signed 32-bit field at offset 84 of that state region.
3. Reads the initial-entry pointer from offset 16 of the already selected collection holder.

The signed value and original entry address are retained for the traversal. The holder is not reselected after a callback changes state. Likewise, changing the holder’s initial-entry pointer does not replace the retained traversal anchor.

The signed field is interpreted using the predicate “greater than zero”:

- Positive values produce true.
- Zero produces false.
- Negative values produce false.

This is not a general nonzero test. In the represented 32-bit model, `0x80000000` is negative and therefore produces false.

### Processing entries

The initial entry is processed at least once. There is no pre-traversal test for a null initial-entry pointer.

For each visited entry:

- Its callback slot at offset zero is tested against zero.
- If the slot is zero, no callback is invoked for that visit.
- If the slot is nonzero, the callback is invoked with the three arguments specified below.
- After the callback returns, or immediately after a zero callback slot, the next-entry pointer is read from offset 16 of the current entry.
- The obtained pointer is compared with the retained original entry address.
- Equality ends traversal. Otherwise, the obtained pointer identifies the next entry to process.

An entry with a zero callback slot still participates in traversal. It is not an end marker and is not removed.

The callback expression uses the entry’s callback slot separately from the preceding nonzero test. Under stable-memory conditions these select the same address. No synchronization or single-read snapshot guarantee is established for a callback slot that changes between those source-level evaluations.

### Callback arguments

Each invocation receives:

| Position | Value |
|---|---|
| First | A fresh 32-bit read from input-object offset 144 |
| Second | The original opaque 32-bit forwarded argument |
| Third | The truth value of the retained signed field being greater than zero |

The first argument is read only for entries with a nonzero callback slot. It is not sampled once for the whole traversal. A callback that changes object offset 144 can therefore affect the first argument supplied to a later callback.

The signed field is different: it is sampled before traversal. A callback that changes that field does not change the third argument used by later callbacks in the same invocation.

The exact physical width and calling-convention placement of the third argument are not established by a callback prototype. Its logical value is established as false or true.

### Mutation during callbacks

The next-entry pointer is read **after** an invoked callback returns. Traversal therefore follows the current entry’s post-callback link, not a link saved before the call.

Consequences include:

- Repointing the current entry’s next link can redirect traversal.
- Repointing that link to the original entry can end traversal immediately after the callback.
- Changing only the holder’s initial-entry pointer does not change the retained termination anchor.
- Moving traversal into a cycle that excludes the original entry prevents normal termination.
- Releasing or invalidating the current entry during its callback can make the subsequent next-link read invalid.

There is no demonstrated mutation protocol, lifetime guard, iteration bound, or general cycle detector.

### Arithmetic and termination boundaries

Address formation uses fixed byte offsets; next-entry selection follows stored pointers. There is no traversal counter or accumulation whose overflow determines completion.

The contract does not grant wraparound addressing as valid behavior. Every address actually dereferenced must resolve to suitable accessible storage.

A self-linked entry is visited once. A multi-entry ring is visited in link order and completes when the last processed entry links back to the original entry. A chain ending in zero is not treated as successful completion unless that zero somehow equals the retained anchor; a zero initial anchor already leads to an invalid first-entry access under ordinary memory assumptions.

## Side effects

The function contains no explicit stores to the input object, state region, collection holder, or entries. It performs no explicit allocation, release, registration, removal, or reference-count operation.

Its observable actions are memory reads and indirect callback invocations. Callback effects are unconstrained by the available evidence. They may include memory changes, global-state changes, resource operations, reentrant calls, failure, or nonreturning execution.

No ownership transfer is established for either input or any callback argument. In particular, passing the value from object offset 144 does not establish that it is a pointer or that the callback owns it.

For successful traversal, storage must remain valid whenever the function later accesses it. Relevant requirements include:

- The input object remains readable for each required offset-144 read.
- Each processed entry remains readable through its post-callback next-link read.
- Each invoked callback address is callable using a compatible three-argument interface.
- The selected links eventually return to the retained original entry if normal completion is required.

A callback that does not return prevents this invocation from advancing. No cleanup or recovery behavior is shown for callback failures or invalid accesses.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Except where stated otherwise, assume valid readable storage, compatible callbacks, returning callbacks, and no unmentioned mutation.

1. **Absent collection holder.**  
   The state region’s offset-zero address is zero. The function returns without invoking a callback or accessing any entry. The signed field need not be read on this path.

2. **One-entry ring with no callback.**  
   The initial entry’s callback slot is zero, and its next link points to itself. The entry is inspected once, no callback runs, and traversal completes after reading its next link.

3. **One-entry ring with a negative signed field.**  
   The signed field is −1, the callback slot is callable, and the entry links to itself. Exactly one callback is invoked with the object’s current offset-144 value, the forwarded value, and false.

4. **Signed boundary.**  
   With all other inputs unchanged, signed field `0x7fffffff` produces true, while `0x80000000` produces false. No unsigned interpretation is accepted for this predicate.

5. **Mixed three-entry ring.**  
   The first and third entries have callbacks; the second has a zero callback slot. The function invokes the first callback, traverses the second entry without invocation, then invokes the third callback. The link from the third entry back to the original entry ends traversal.

6. **First callback changes the first argument’s source.**  
   Before traversal, object offset 144 contains one value. The first callback replaces it with another. A later callback receives the replacement, provided no intervening change occurs.

7. **First callback changes the signed field.**  
   The signed field is positive when sampled, then becomes zero during the first callback. Later callbacks still receive true as their third argument.

8. **Callback redirects its own next link.**  
   A callback changes the current entry’s next link to the retained original entry. The function reads that changed link after return and ends traversal. Entries bypassed by the change are not visited.

9. **Traversal enters another cycle.**  
   A next link redirects traversal into a valid cycle that excludes the original entry. If callbacks continue returning and links stay in that cycle, the function does not normally terminate.

10. **Nonzero holder with a null initial entry.**  
    The function attempts to access an entry at the null address rather than treating the collection as empty. A particular fault or recovery outcome is not specified.
