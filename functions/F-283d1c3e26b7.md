# F-283d1c3e26b7

## Purpose

F-283d1c3e26b7 performs a lookup in a container-like object and, when that lookup reports no match, prepares and submits a new entry. It then delegates result publication to F-2fb441b4c2a2, supplying a lookup-position value, an entry pointer, and a 32-bit branch indicator.

The established branch meanings are:

- **0:** the initial lookup returned a non-null entry pointer; no insertion is attempted by this function.
- **1:** the initial lookup returned null; this function followed its allocation, optional growth, and insertion-submission path.

The second meaning is deliberately narrower than “insertion succeeded.” The function does not check allocation success, growth success, or insertion success before publishing indicator 1.

The apparent intent is an insert-if-absent operation that returns an entry position and an inserted/not-inserted indication. That interpretation is inferred from the control flow. Key equivalence, container invariants, and the final externally visible result format depend on unavailable dependency contracts.

### Preconditions and accessibility

For the visible reads to be valid:

- The container must support the reads at offsets +4, +12, and +32 on a miss, and at +4 on either path. Offset +8 is read only when growth is selected.
- The first two input words must be readable for the initial lookup preparation.
- On a miss with non-null allocation, the first three input words must be readable when the later copy occurs.
- Addresses derived from the container, including the embedded-region address at +16, must satisfy the requirements of the dependencies receiving them.
- The result-publication argument must satisfy the unknown requirements of F-2fb441b4c2a2.

The function performs no visible null checks on the container or input-record address. A hit does not visibly require reading the third input word.

The input record is not snapshotted at entry. Its words are read again after several dependency calls on the miss path. A caller cannot assume the allocated entry receives the same first two values used for the initial lookup if intervening calls or aliases modify the record.

## Behavior

### Initial lookup preparation

The function saves all three input arguments.

It reads the 32-bit relative component at container offset +4 and forms a derived address by adding that component to the container address. It calls F-58cc241cfb6b with:

1. That derived address.
2. The container address.
3. The first input word.
4. The second input word.

The relative component is represented as signed in the supplied material. Negative values therefore participate in address formation; no nonnegative-offset check is visible. Address validity and arithmetic overflow are not checked.

The returned 32-bit value is retained for possible reuse after growth. Its semantic role is unknown; a hash or lookup discriminator is an inference, not an established fact.

Next, F-3ed23f1b4691 receives the embedded-region address at container +16 and that retained value. Its 32-bit result is then passed with the container address to F-16846337587d.

The pointer returned by F-16846337587d controls the only top-level branch. Non-null means the existing-entry path; null means the allocation and insertion-submission path.

The supplied call expressions do not establish a portable evaluation order among the initial call’s separate argument reads. They do establish that the call completes before the position-preparation and lookup calls occur.

### Existing-entry path

When F-16846337587d returns non-null:

- The function retains that entry pointer.
- It prepares a 32-bit indicator equal to 0.
- It prepares a local result descriptor containing the position-preparation result followed by the existing-entry pointer.
- It calls F-2fb441b4c2a2 with the saved result-publication argument, the address of the descriptor’s first word, and the address of the indicator.
- It returns if that dependency returns normally.

This path makes no visible allocation, growth, input-record copy, or insertion call.

The entry pointer is not dereferenced by this function. Its validity, ownership, and lifetime are not established here.

### Allocation and entry preparation after a miss

After a null lookup result, the function prepares local construction state, including an initially null allocation pointer and two one-byte flags initially set to zero.

It requests **24 bytes** from F-871e64ddc6de, passing a second argument of 0. The returned pointer may be null; execution does not terminate or select an error result solely because it is null.

An unmapped external dependency is then called with a local scratch-region address and the value 24. This call occurs even if allocation returned null. Its implementation and contract are unavailable; it must not be assumed to clear, initialize, allocate, or release memory merely from its arguments.

A separate local 32-bit word is assigned zero. If allocation returned non-null, the function then writes into the allocated block:

- Four consecutive 32-bit words taken from the beginning of the scratch region.
- A zero 32-bit word at allocation offset +16.

One local construction flag becomes 1.

If the retained allocation pointer is non-null, the function overwrites allocation offsets +0, +4, and +8 with the first three input words. The visible order within this copy is:

1. Read the second input word.
2. Read the first input word and write it at allocation +0.
3. Write the previously read second input word at allocation +4.
4. Read the third input word and write it at allocation +8.

A second local construction flag becomes 1.

Immediately after these visible writes, and before subsequent dependency calls, the prepared allocation has the following locally established state:

| Allocation range | Established content |
|---|---|
| +0 through +11 | Three copied input words |
| +12 through +15 | Fourth scratch-derived word |
| +16 through +19 | Zero |
| +20 through +23 | No visible write by this function |

No value is established for the last four bytes. The unmapped dependency’s behavior also prevents treating the scratch-derived word as a known constant.

### Growth decision and preparation

After entry preparation, the function reads the unsigned 32-bit count at container +32. It calculates the prospective count by adding 1 in unsigned 32-bit arithmetic.

It then reads the unsigned 32-bit limit at container +12. Growth is selected when:

**limit ≤ prospective count**

Equality therefore triggers growth.

The prospective count wraps modulo 2³². There is no visible overflow check.

When growth is selected, the function calculates an unsigned growth candidate from:

- The current count plus the current count shifted right by one bit, with 32-bit wraparound.
- The prospective count.

It selects the larger of those two values using an unsigned comparison. This is approximately one-and-a-half times the current count only when the first calculation does not wrap. It is not established as a capacity measurement.

The following calls then occur in order:

1. F-0ec3a2a1b51e receives the current 32-bit field at container +8 and produces a 64-bit result.
2. F-9e5e664c8ae7 receives the selected unsigned growth candidate and produces a 64-bit result.
3. F-596e18a33aec receives four 32-bit arguments: low and high halves of the second result, followed by low and high halves of the first result.
4. F-936416edf8a5 is called without visible arguments.
5. F-1cd4c8db3fc1 is called without visible arguments.
6. F-fdbe7954edb6 receives the container address and the preceding call’s signed integer result plus 1.

The two 64-bit results are split at bit 32. No floating-point interpretation, rounding behavior, or relationship among the no-argument calls is established.

The final addition is expressed on a signed integer result. Behavior at the maximum signed value is not sufficiently established to promise wraparound.

If this growth sequence returns normally, F-3ed23f1b4691 is called again with container +16 and the retained value from the initial F-58cc241cfb6b call. This replaces the earlier position value.

There is no second call to F-16846337587d. Growth refreshes the position value, not the match decision.

- For non-null allocation, the pointer is allocation base +16 bytes.
- For null allocation, the pointer is null.

The local allocation holder is then explicitly cleared to null before F-65514a6f4064 is called.

F-65514a6f4064 receives:

1. Container +16.
2. The derived entry-link pointer, possibly null.

The function does not inspect a return status from this call.

A conditional cleanup call to F-ff1bdc376dcd follows. In the visible ordinary flow, its tested local holder has already been cleared to null, so this call is not reached. The source does not establish exceptional unwinding behavior.

## Side effects

The function directly writes its local state and, when allocation succeeds, the allocated block described above. It does not directly write container fields in the visible body. Container mutation, lookup bookkeeping, growth effects, linking, and result publication are delegated.

The order of observable dependency calls is significant:

- Allocation and record preparation occur before the growth decision.
- Growth completes before position recomputation.
- The local allocation holder is cleared before insertion submission.
- Result publication occurs after insertion submission on a miss.
- Result publication occurs without insertion submission on a hit.

The output helper receives addresses of local storage. Their use during the call is visible; their retention afterward is not established as safe.

### Ownership

The function requests storage and does not normally release it itself. Clearing its local allocation holder before insertion submission suggests a handoff, but does not prove that F-65514a6f4064 accepts ownership or eventually frees the allocation.

Neither successful publication nor indicator 1 establishes ownership transfer. Unknown callees must not be assumed to preserve global state, preserve the input record, or own or release passed memory.

### Errors and abnormal completion

There is no explicit error return, local failure indicator, or retry.

In particular:

- A null allocation still leads to insertion submission with a null entry-link pointer.
- Growth results are not checked for success.
- Insertion results are not checked for success.
- Publication is not followed by a separate success check.

Faults, exceptions, non-returning dependencies, and dependency-specific errors are outside the established normal-completion contract.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Each assumes relevant dependencies return normally.

1. **Existing entry.** If F-16846337587d returns a non-null pointer, publication receives indicator 0 and the descriptor containing the initial position value and that pointer. No allocation or insertion call occurs.

2. **Miss without growth.** With count 4 and limit 6, the prospective count is 5, so growth is not selected. If allocation returns address A, insertion receives A +16 and the original position value. Publication receives indicator 1.

3. **Equality at the limit.** With count 4 and limit 5, growth is selected. The growth candidate is 6. The position is recomputed after the growth calls, and insertion uses the recomputed value.

4. **Small-count candidate selection.** With count 1 and limit 2, growth is selected. The one-and-a-half calculation yields 1, while the prospective count is 2; the selected candidate is 2.

5. **Allocation failure.** If allocation returns null, the unmapped scratch dependency is still called. Subject to normal returns, growth is still evaluated, insertion receives null, and publication receives indicator 1. This function does not turn allocation failure into a reported failure branch.

6. **Count wraparound.** With count 4,294,967,295 and limit 1, the prospective count wraps to 0. The unsigned comparison does not select growth. No saturation or overflow rejection occurs.

7. **Wrapped growth candidate.** With count 4,294,967,294 and limit 4,294,967,295, growth is selected. The wrapped one-and-a-half candidate is 2,147,483,645; the prospective count is 4,294,967,295, so the latter is selected.

8. **Intervening input mutation.** If a dependency changes the input record after the initial lookup preparation but before the copy, the allocation receives the later values. The function provides no entry-time snapshot guarantee.
