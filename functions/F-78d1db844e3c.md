# F-78d1db844e3c

## Purpose

F-78d1db844e3c stores a supplied integer in a receiver-associated state field, invokes an indirect operation through a related object, and then invokes another indirect operation through the receiver itself.

The established behavior is a store followed by two ordered indirect transfers. The semantic meaning of the stored field and the operations is not established. Interpreting the first operation as a notification, or the second as a refresh, initialization, or transition, would be inferred intent rather than a supported contract.

This specification describes the supplied static representation. No runtime tests have been performed.

## Interface

### Inputs

The function has two explicit inputs:

- **Receiver:** a pointer represented as pointing to integer-addressable storage. It serves both as the base of several accesses and as an explicit argument to the second indirect operation.
- **Supplied value:** an integer stored directly in the receiver’s state field, without visible validation, normalization, masking, or arithmetic.

The recovered interface declares no return value. Neither indirect operation’s result is visibly consumed.

The supplied representation uses integer words both for ordinary data and for values interpreted as addresses. Its apparent model is a 32-bit integer/address environment. The byte offsets below use four-byte words; the original ABI and compiler data model have not been independently established.

Under this model, the state update is a four-byte write. No multiword representation, byte order conversion, saturation, or range check is visible.

### Preconditions for ordinary completion

The receiver must permit the state-field write and the subsequent receiver-relative reads. The related-object reference, both dispatch references, and the selected indirect targets must be usable when accessed.

These requirements are temporal, not merely entry conditions. In particular, the first indirect operation must leave—or establish—a valid receiver dispatch path if the second operation is to execute successfully.

No explicit validity checks enforce these preconditions. Null pointers, inaccessible storage, invalid targets, or incompatible calling conventions have no defined recovery behavior in the supplied representation.

## Behavior

### 1. Store the supplied value

The function first writes the supplied integer to the receiver’s stored-value field.

This write occurs before either indirect operation is invoked and before the related-object reference is read for the first operation. The old field value is not visibly read.

There is no conditional branch around the write. A zero, negative, or boundary integer receives the same visible treatment as any other representable integer.

The function does not visibly restore the old value if a later access or operation fails. Nor does it guarantee that the field retains the supplied value afterward: either indirect operation may modify it.

### 2. Resolve and invoke the related-object operation

After the store, the function follows this access chain:

1. Read the related-object reference from the receiver.
2. Read the dispatch reference at the beginning of that related object.
3. Read the target at byte offset 104 in that dispatch structure.
4. Invoke the selected target, identified here as **D-01**.

The recovered call displays no explicit arguments. It does not visibly pass either the receiver or the related-object address as an argument.

That observation does not establish that D-01 receives no machine-level context. Implicit register inputs, a specialized calling convention, or omitted argument recovery remain unknown. This contract therefore does not characterize D-01 as a conventional zero-argument API or as a conventional object method receiving an explicit object argument.

No result from D-01 is visibly used.

### 3. Resolve and invoke the receiver operation

If D-01 returns control normally, the function resolves a second indirect target through the receiver:

1. Read the receiver’s leading dispatch reference.
2. Read the target at byte offset 88 in that dispatch structure.
3. Transfer control to that target, identified here as **D-02**, with three visible arguments.

The arguments, in their displayed positional order, are:

1. The receiver address.
2. A value referenced through external data item **G-01**.
3. A value referenced through external data item **G-02**.

G-01 and G-02 are specification-local opaque labels. Their contents, declared widths, types, and meanings are not supplied. They must not be treated as known constants, strings, handles, pointers, or owned resources.

The receiver dispatch reference used for D-02 is obtained after D-01 returns. It is not visibly captured before D-01 executes. Consequently, a dispatch-reference change made by D-01 can affect selection of D-02.

Likewise, the displayed second operation references G-01 and G-02 after the first operation. No earlier snapshot of either value is visible. Their positional argument order is established; the exact evaluation order among their reads and the second target’s resolution is not.

### 4. Completion and abnormal control flow

The recovered representation shows no further local work after the second indirect transfer and presents the function as returning without a value.

However, the second transfer has an explicit recovery warning: an indirect jump was represented as a call. Thus, the static evidence supports the target-selection path and displayed arguments more strongly than it supports the precise call-versus-tail-transfer mechanism.

If either indirect operation does not return, faults, or transfers control elsewhere, ordinary completion is not established. No local error status, rollback, retry, or cleanup path is visible.

## Side effects

### Directly established effects

The only explicit data write performed by F-78d1db844e3c itself is the supplied-value write to the receiver’s stored-value field.

The function also reads receiver-associated addressing information, dispatch entries, and the two external data references used by the second operation. These reads must remain distinct from the effects of executing the selected targets.

### Dependency effects

D-01 and D-02 may have additional effects that are not described by the supplied body. In particular, this specification does not assume that they:

- Preserve receiver fields or dispatch structures.
- Preserve G-01, G-02, or other global state.
- Preserve the lifetime of the receiver or related object.
- Avoid allocation, release, callbacks, or reentrancy.
- Return normally.

The initial store may therefore be observable to D-01, but its persistence after either operation is not guaranteed.

### Ownership and synchronization

No explicit allocation, deallocation, ownership transfer, reference-count update, locking operation, or atomic access appears in the function body.

Passing the receiver to D-02 does not, by itself, establish borrowing, retention, or ownership transfer. Those properties depend on the unknown target contract.

No synchronization guarantee is established for concurrent access. The store-before-call sequence describes this function’s execution order, not a cross-thread visibility guarantee.

## Acceptance examples

These examples are conditional contract checks, not reports of executed tests.

### State visibility at the first operation

Given valid storage and dispatch references, and an execution environment without an intervening mutation, D-01 must observe the stored-value field already updated if it inspects that field.

An execution that invokes D-01 before performing the write would violate the established sequence.

### Integer boundary values

Under the recovered 32-bit signed-integer model, supplied values of zero, minus one, the minimum signed value, and the maximum signed value are stored directly. No visible branch rejects or transforms them.

This example does not specify conversion of caller-side values outside the parameter’s representable range.

### Dispatch replacement by D-01

Suppose D-01 replaces the receiver’s leading dispatch reference and returns normally, leaving the replacement valid. The second operation must be resolved through the replacement reference, not through a receiver dispatch reference cached before D-01.

### Mutation of external data by D-01

Suppose D-01 changes G-01 or G-02 and returns normally, with no subsequent intervening change. The second operation uses the corresponding post-D-01 value. An implementation that snapshots both data values before D-01 would not match the displayed behavior.

The relative order of the two external-data reads is not an acceptance requirement.

### Non-returning first operation

Suppose D-01 does not return. The initial state write has already occurred, but invocation of D-02 is not required. No local continuation around D-01 is visible.

### Invalid related-object path

Suppose the state-field write succeeds but the subsequent related-object access is invalid. The contract provides no rollback of the completed write and no defined error result. It does not require a particular fault mechanism.

### Mutation of the stored field by a dependency

Suppose D-01 overwrites the stored-value field before returning. F-78d1db844e3c does not visibly reapply the supplied value before invoking D-02. Requiring the supplied value to remain in the field at function exit would exceed the static evidence.
