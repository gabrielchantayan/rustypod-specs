# F-f9f07d64c41b

## Purpose

F-f9f07d64c41b conditionally replaces a caller-supplied pair of 32-bit words using fields from an indirectly referenced record. It returns a 32-bit classification indicating which acceptance condition matched, or zero when neither condition matched.

Two record forms are accepted:

- A record whose eligibility byte equals 1 and whose kind byte equals 2. This produces result 2, with no range restriction on the second transferred word.
- A record whose eligibility byte equals 1, whose kind byte equals 15, and whose second transferred word passes a signed range check from 0 through 255 inclusive. This produces result 1.

A zero record reference or an ordinary rejected record produces result 0 without explicit writes to the caller’s pair.

This is an operational description. The domain meaning of the record kinds, eligibility byte, and transferred words is unknown.

## Interface

### Input and output storage

The function receives one pointer to caller-provided storage. The relevant layout is:

| Offset from argument | Width | Role |
|---|---:|---|
| 0 | 32 bits | Initially an address-bearing word; replaced on acceptance |
| 4 | 32 bits | Replaced on acceptance; not otherwise read by this function |

The first word initially identifies a base object. At byte offset 24 within that object is another 32-bit address-bearing word identifying a candidate record.

The relevant candidate-record layout is:

| Offset from candidate record | Width | Interpretation |
|---|---:|---|
| 8 | 8 bits | Kind byte |
| 9 | 8 bits | Eligibility byte |
| 20 | 32 bits | First word transferred on acceptance |
| 24 | 32 bits | Signed range-check operand for kind 15; second word transferred on acceptance |

These are accessed offsets, not a complete object schema. No meaning is established for intervening bytes.

The supplied representation uses 32-bit integer words and a 32-bit return value. Address-bearing words are used as addresses without an explicit conversion or validation routine in the supplied evidence. The target’s byte order, address-space model, and alignment requirements are not established.

### Return value

| Result | Meaning |
|---:|---|
| 0 | No acceptance path completed; no explicit destination writes occurred |
| 1 | The kind-15 acceptance path completed and both destination stores were performed |
| 2 | The kind-2 acceptance path completed and both destination stores were performed |

The second destination word is not a separate return value. It is caller-visible memory modified only on acceptance.

### Preconditions

For ordinary completion:

- The argument must identify readable storage for its first 32-bit word.
- That first word must identify a base object with a readable 32-bit field at offset 24.
- A nonzero candidate reference must support the reads reached along its execution path.
- An accepted candidate must provide readable 32-bit fields at offsets 20 and 24.
- On acceptance, both destination words must be writable.

The function does not check whether the argument or the initial base address is null. A zero candidate reference is handled, but obtaining that reference already requires the initial dereferences.

Invalid addresses, insufficient storage, unsupported alignment, and protection failures have no defined recovery behavior in the supplied evidence. They are not specified to return zero.

## Behavior

### Candidate selection

The function first reads the argument’s first word. It uses that value as the base address for a 32-bit read at offset 24, obtaining the candidate-record reference.

The candidate reference is retained for subsequent record accesses. Replacing the argument’s first word later does not cause the function to select a new candidate.

If the candidate reference is zero, the function returns 0. It performs no candidate-field reads and no destination writes on this path.

Otherwise, the function reads the candidate’s eligibility byte at offset 9. Only the exact value 1 permits further processing. Any other value produces result 0 without destination writes.

### Kind-2 acceptance

After eligibility succeeds, the function reads the kind byte at offset 8.

If that byte equals 2:

1. The function reads the 32-bit field at candidate offset 20.
2. It stores that value into the argument’s first word.
3. It reads the 32-bit field at candidate offset 24.
4. It stores that value into the argument’s second word.
5. It returns 2.

There is no signed or unsigned range check on the second transferred word for this path. All 32-bit representations are accepted if the required accesses complete.

### Kind-15 acceptance

If the first kind-byte read did not equal 2, the function reads the kind byte again and compares it with 15.

If this second read does not equal 15, it returns 0 without destination writes.

If it equals 15, the function reads the 32-bit field at candidate offset 24 and interprets it as signed. It first requires that value to be greater than −1.

If this lower-bound check fails, the function returns 0. It does not perform the upper-bound read.

If the lower-bound check succeeds, the function reads the same field again and requires the signed value from that read to be less than 256.

If the upper-bound check fails, the function returns 0 without destination writes.

If both checks succeed:

1. The function reads the 32-bit field at candidate offset 20.
2. It stores that value into the argument’s first word.
3. It reads the 32-bit field at candidate offset 24 again.
4. It stores that value into the argument’s second word.
5. It returns 1.

With stable memory, the accepted range is exactly 0 through 255 inclusive. The destination still receives a full 32-bit word; the function does not narrow the value to one byte.

### Repeated reads and sequencing

The supplied representation does not take a single snapshot of all candidate fields:

- Eligibility is checked before kind.
- Kind may be read twice.
- For kind 15, the second transfer field may be read three times: lower-bound check, upper-bound check, and final transfer.
- On either successful path, the first destination store precedes the read used for the second destination store.

These distinctions matter when source and destination storage overlap. They also prevent a general promise that the final transferred value is necessarily the same value that passed an earlier check.

The operation is not specified as a transaction. Once the first destination store occurs, no rollback is shown if a later access cannot complete.

## Side effects

On normal rejection, the function performs reads but no explicit writes. The caller’s first and second words therefore remain unchanged by this function.

On acceptance, it performs exactly two explicit 32-bit stores, in order:

1. Candidate offset 20 to argument offset 0.
2. Candidate offset 24 to argument offset 4.

The second source read occurs after the first store. For example, if the argument’s first word occupies the same storage as the candidate’s offset-24 field, the first store changes the source of the second transfer. The function does not reread eligibility or repeat range validation after that store.

No allocation, deallocation, reference-count operation, external call, or explicit global-variable access appears in the supplied body. This establishes only what this function directly does. It does not establish the ownership or lifetime of any address-bearing value.

The function reads the original candidate reference but does not clear or otherwise explicitly modify the base object’s reference field. Overlapping storage can nevertheless make a destination store affect a field otherwise described as source storage.

No synchronization, locking, atomic operation, or memory-ordering guarantee is established.

## Acceptance examples

Unless stated otherwise, these examples assume valid, suitably aligned, non-overlapping storage that remains stable throughout execution. They are conditional acceptance criteria derived from static evidence, not observed runtime results.

### No candidate

The initial base object’s offset-24 field contains zero.

Expected result: 0. Both argument words retain their entry values. No eligibility or kind byte is read.

### Ineligible candidate

The candidate reference is nonzero, but its eligibility byte is 0, 2, or 255.

Expected result: 0. Neither argument word changes. The kind byte is not consulted.

### Kind 2 with an unrestricted second word

Eligibility is 1, kind is 2, and the candidate’s offset-24 word has the signed interpretation −1.

Expected result: 2. The first destination receives candidate offset 20, and the second receives the complete offset-24 word. The negative value does not cause rejection on this path.

### Kind 15 at its boundaries

Eligibility is 1 and kind is 15.

- Offset-24 value 0: result 1 and both transfers occur.
- Offset-24 value 255: result 1 and both transfers occur.
- Offset-24 value −1: result 0 and neither transfer occurs.
- Offset-24 value 256: result 0 and neither transfer occurs.

For successful cases, the second destination contains the full 32-bit source word.

### Unsupported kind

Eligibility is 1 and the stable kind byte is neither 2 nor 15.

Expected result: 0 with no destination writes. The candidate’s fields at offsets 20 and 24 need not be accessed.

### Overlap affecting a successful transfer

The argument’s first word overlaps the candidate’s offset-24 field. Its initial contents also provide a valid base address whose reference field selects this candidate. Eligibility is 1 and kind is 2.

Expected result, if all accesses complete: 2. The first store writes the candidate’s offset-20 word into the overlapping offset-24 field. The second source read then obtains that newly written word, so both destination words receive the offset-20 value.

This example depends on a valid memory arrangement satisfying all stated conditions; it is not a claim about a common caller layout.
