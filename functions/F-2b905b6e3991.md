# F-2b905b6e3991

## Purpose

F-2b905b6e3991 has two principal behaviors:

- When a descriptor identifies an available table, process a selected entry’s previous contents, then install a replacement representation determined by the supplied mode and payload.
- When the table is unavailable, ignore the index and either return without processing the payload or enter a mode-dependent cleanup and accounting sequence.

The function has no explicit return value. Observable results include dependency calls, entry and owner writes, global and allocator-context accounting changes, and a call identified as non-returning when allocation-header validation fails.

Terms such as *owner*, *payload*, *allocation reference*, and *allocator context* describe apparent roles. They do not establish ownership transfer, memory-release guarantees, synchronization, or dependency behavior.

## Interface

| Argument | Representation and use |
|---|---|
| Descriptor | Pointer to a structure containing 32-bit fields. No null check is visible. |
| Requested index | Signed 32-bit integer. Negative values request the last entry; nonnegative values are used directly. |
| Payload | Nullable pointer represented in a 32-bit word. Required readable metadata depends on the selected path. |
| Mode | Signed 32-bit integer controlling replacement or cleanup. Some modes are narrowed to an eight-bit entry tag. |

Relevant descriptor fields:

| Offset | Meaning |
|---|---|
| `+0` | Owner pointer |
| `+12` | Signed entry count |
| `+20` | Table pointer |

The owner has a one-byte marker at offset `+30`. A nonzero marker makes the table unavailable.

Each table entry occupies 20 bytes. This function directly accesses:

| Entry offset | Field |
|---|---|
| `+1` | Eight-bit tag |
| `+16` | 32-bit payload value |

The function itself does not directly write the remaining entry bytes. Dependencies may modify them.

### Return and failure behavior

There is no status result. A normal return can follow an ignored payload, an unresolved negative selection, a completed replacement, or cleanup.

A zero allocation result in mode `−6` causes explicit failure marking. Invalid allocation-header state invokes a dependency identified as non-returning. Other dependency failures, nonlocal exits, and resource failures are **documented_only**.

## Behavior

### 1. Select the available or unavailable path

The first decision reads the descriptor’s table pointer.

- A zero table pointer selects the unavailable path without reading the owner marker.
- Otherwise, the function reads the descriptor’s owner pointer and then the byte at owner offset `+30`.
- A nonzero marker selects the unavailable path; zero selects the available path.

The unavailable path does not use the requested index.

### 2. Select and process an available entry

For a negative requested index, the function reads the entry count and substitutes `count − 1`. If that substituted value is negative, it returns without processing an entry or payload. The original negative index’s magnitude has no further effect.

A nonnegative requested index is used directly, even if it is outside the declared count. The selected address is the table pointer read for address construction plus `20 × selected index`. This table-pointer read occurs after the initial availability decision.

The function then:

1. Reads the entry’s tag and payload value as arguments to F-9ef145997789.
2. Calls F-9ef145997789 with the tag converted from a plain character to the integer argument representation, and the previous payload value.
3. After that call returns, writes zero to entry offset `+16`.

The relative evaluation order of the two argument reads is not established by the supplied representation.

The function performs no direct tag write before or during this call. It does **not** guarantee that the old tag survives the call: F-9ef145997789 may change the tag, payload field, descriptor, or other state. The subsequent zero write overwrites whatever payload-field value exists when the call returns.

The selected entry address remains captured for subsequent writes. The function does not reselect the entry after dependency calls. No comparison protects an incoming payload that aliases the previous payload.

### 3. Install the replacement

The following dispatch occurs after the previous-entry call and payload-field clearing.

#### Mode −14

The function writes the supplied pointer, including null, to the payload field, then writes tag `0xF2` and returns.

This case precedes null-payload handling.

#### Null payload, any other mode

The function writes tag zero and returns. It makes no replacement allocation, transfer, length-determination, or transformation call.

#### Mode −6 with nonnull payload

The function:

1. Reads the 32-bit field at payload offset `+8`.
2. Calculates a 32-bit byte-count expression: five times that field, plus sixteen.
3. Calls F-391e3d30e634 with that count.
4. Stores the returned value in the selected entry’s payload field.

If the returned value is zero, it rereads the descriptor’s owner pointer, writes byte `1` at that owner’s offset `+30`, writes entry tag zero, and returns.

If the result is nonzero, it calls F-unmapped-1 with the allocation result, original payload pointer, and calculated count. After that call returns, it writes tag `0xFA` and returns.

The allocation result is stored **before** F-unmapped-1 is called. The function does not restore the payload field afterward. A final payload-field assertion therefore requires the transfer dependency to preserve that field.

The argument arrangement suggests a transfer into newly supplied storage, but exact transfer semantics are **documented_only**. Source extent, destination capacity, count overflow, and any allocator conversion of the count are not independently checked.

#### Mode −9 with nonnull payload

The function stores the supplied pointer, writes tag `0xFA`, and returns. It does not call the allocation or transfer dependencies.

Successful mode `−6` and direct-storage mode `−9` consequently share a tag without establishing identical ownership.

#### Other negative modes with nonnull payload

The function stores the supplied pointer and then writes the mode narrowed to one byte as the tag.

There is no mode whitelist on this path. Distinct negative modes can produce the same tag; a nonnull payload can be stored with tag zero.

#### Zero or positive mode with nonnull payload

For mode zero, F-1cb585febd84 is first called with the payload. Its result becomes the mode argument for F-7129d6a8d912. Negative results do not restart negative-mode dispatch.

The function then reads the descriptor’s current owner pointer and calls F-7129d6a8d912 with that owner, the payload, and the effective mode. After the call returns, it stores the returned 32-bit value and writes tag `0xFF`.

A zero result still receives tag `0xFF`; no failure-marker write is visible.

### 4. Dispatch unavailable-table cleanup

Mode `−6` returns immediately without inspecting payload storage. For every other mode, a null payload returns without further processing.

For a nonnull payload:

| Mode | Action |
|---|---|
| `−13`, `−12`, `−11`, `−9`, `−1` | Enter common disposal directly |
| `−10`, `−4`, `−3`, `−2` | Return |
| `−8` | Call F-74b5a05d0094 with the payload, then enter common disposal |
| `−7` | Read the first 32-bit payload word; pass it to F-449926a4de34; call F-206e19806905 with the payload and zero; then enter common disposal |
| `−5` | Read the byte at payload offset `+4`; enter common disposal only if bit `0x04` is set |
| All other values | Return |

Thus mode `−14` is ignored on this path.

Common-disposal metadata is read after the mode-specific calls. Those calls are not assumed to preserve metadata or retain the payload’s storage. Safe continuation requires the subsequently accessed memory to remain valid.

### 5. Common disposal: global accounting

The accounting sequence distinguishes several reads of the accounting-global pointer. Their targets must not be treated as one cached structure.

In the observed order, the function:

1. Reads the accounting-global pointer and captures it as the base for the eventual high-word write.
2. Reads the 32-bit displacement immediately before the payload, at offset `−4`.
3. Subtracts that displacement from the payload address to obtain the allocation reference.
4. Reads the 32-bit amount at allocation-reference offset `−8`.
5. Reads the accounting-global pointer again and reads the old low word at that base plus `56`.
6. Reads the accounting-global pointer again and captures the address at that base plus `60` for the later high-word read.
7. Reads the accounting-global pointer again and writes the low-word result at that base plus `56`.
8. Reads the high word through the address captured in step 6, **after the low-word write**.
9. Writes the high-word result at offset `+60` through the pointer captured in step 1.

The low-word result is the old low word minus the amount, modulo \(2^{32}\).

For the high-word calculation, let:

- The sign contribution be `−1` when the amount’s top bit is set, otherwise zero.
- The borrow be one when the old low word is unsigned-less-than the amount, otherwise zero.

The stored high word is the high word read in step 8 minus the sum of those contributions, modulo \(2^{32}\).

When all pointer reads identify one structure and there is no interfering mutation or aliasing, this implements subtraction of a sign-extended 32-bit amount from paired words. That interpretation does not replace the distinct read and write targets above.

The function next calls F-2fd8826557a4, then reads and captures the allocator-context pointer through a separate global pointer location.

These operations occur even when the allocation reference equals `8`.

### 6. Common disposal: header validation and context accounting

If the allocation reference equals `8`, the function returns after the accounting update, F-2fd8826557a4 call, and allocator-context read.

Otherwise, the header address is allocation reference minus sixteen bytes.

Validation first reads the header’s initial 32-bit word and checks for zero. If nonzero, the representation reads that word again to test its least significant bit. A zero first read or a set low bit on the second read invokes F-a817d8d58c10, identified as non-returning.

Earlier accounting writes have already occurred and are not rolled back.

For an accepted header, the function calls F-c0fc6d033caa with the captured allocator context. After that call returns, it:

1. Reads an unsigned 16-bit selector at allocation-reference offset `−12`.
2. **Freshly reads the header word** and masks it with `0x3FFFFFFC`.
3. Uses that fresh masked size for each of the following four subtractions, in order:
   - Context offset `548 + 4 × first selector`.
   - Context offset `780`.
   - Context offset `224 + 4 × second selector`, where the second unsigned 16-bit selector is read at allocation-reference offset `−10` after the preceding two subtractions.
   - Context offset `544`.

The earlier integrity check does not validate the post-call header value. F-c0fc6d033caa may have changed it. No second zero or low-bit validation precedes these subtractions.

The function then:

1. Calls F-09dcb55e8e0a.
2. Uses its returned index to decrement the 32-bit context word at `784 + 4 × index`.
3. Decrements the context word at `912`.
4. Reads the header word again, masks it with `0x3FFFFFFC`, and subtracts that value from the context word at `8`.
5. Calls F-cc6c9b4a0f68 with the captured context and header address.
6. Calls F-e586bff64fb7 with the captured context.

The final masked size can differ from the size used for the first four subtractions. The captured context is not refreshed from its global location after intervening calls. Selector ranges, returned-index bounds, and counter underflow are not checked.

## Side effects

Replacement is not transactional. Previous-entry processing precedes replacement acceptance, and failure does not restore the former entry.

Direct available-path writes target the selected entry’s payload field and tag, plus the currently referenced owner’s marker on allocation failure. Dependencies can introduce additional writes. The owner used for transformation or failure marking can differ from the owner examined during initial path selection.

On selected unavailable-path modes, the function directly modifies global accounting and allocator-context words before making final allocator-related calls. Invalid-header termination occurs after global accounting changes.

Established storage behavior does not establish ownership:

- Mode `−6` stores an allocation dependency’s result.
- Modes `−14`, `−9`, and other negative modes store the supplied pointer directly.
- Nonnegative modes store a transformation dependency’s result.
- Certain unavailable-path modes perform the common disposal sequence.

Whether these operations transfer ownership, release outer storage, release nested resources, or merely update bookkeeping remains **documented_only**.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Last-entry selection:** With a usable table, count three, and valid arithmetic, any negative index selects entry two. With count zero, a negative index resolves to `−1` and returns before previous-entry processing.

2. **Null replacement:** After previous-entry processing returns, mode `−14` writes payload zero and tag `0xF2`. With mode `−9`, a null payload instead leads to tag zero.

3. **Successful mode −6:** A count field of four produces a requested count of 36. On a nonzero allocation result, the function stores that result, calls F-unmapped-1 with it and the original payload, then writes tag `0xFA`. The final payload field equals the allocation result only if the dependency preserves that field.

4. **Failed mode −6:** A zero allocation result is stored before the current owner receives marker `1` and the selected tag receives zero. Previous-entry processing has already occurred.

5. **Derived negative mode:** If mode zero yields `−9` from F-1cb585febd84, F-7129d6a8d912 receives `−9`. Direct-pointer mode `−9` is not selected.

6. **Unavailable mode −6:** The function returns without reading payload storage, regardless of whether the supplied pointer is null.

7. **Conditional disposal:** For unavailable mode `−5`, a clear `0x04` flag returns without common accounting; a set flag permits common disposal, conditional on valid metadata.

8. **Distinct accounting targets:** If successive accounting-pointer reads identify different structures, the low-word read, high-word read, low-word write, and high-word write follow the separately captured targets. The high-word write uses the first captured base, not necessarily the base used for its read.

9. **Changed post-validation header:** If validation accepts a header and F-c0fc6d033caa changes its masked size, the first four context subtractions use the freshly read post-call size without renewed integrity validation.

10. **Sentinel or rejected header:** Allocation reference `8` still permits global accounting and context capture but skips header processing. A rejected nonsentinel header reaches the non-returning dependency only after global accounting changes.
