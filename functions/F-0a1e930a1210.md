# F-0a1e930a1210

## Purpose

F-0a1e930a1210 conditionally constructs two destination sequence representations from a source object, then copies two trailing metadata fields.

The established behavior is a sequence of dependency calls and 32-bit field updates. The first sequence uses an 8-byte element stride; the second uses a 40-byte element stride. Each sequence receives a nominal capacity of at least 32 elements, determined from an initial count query. A separate count query after the transfer operation determines its recorded logical end.

The apparent intent is to copy or initialize an object containing two dynamically stored sequences and trailing metadata. This interpretation is inferred, not an established ownership or construction guarantee. In particular, the supplied evidence does not establish that the two destination addresses returned by F-f4fd698ba468 belong to the same object.

## Acceptance examples

These examples are conditional behavioral obligations derived from the supplied static evidence, not runtime test results.

1. **Disabled operation.** With an enable input of zero, the result is zero and no dependency is called, even if the source address is unusable.

2. **Empty, stable sequences.** If all count queries return zero and dependencies return normally, the allocation-size arguments are 256 bytes for the first sequence and 1,280 bytes for the second. Each recorded logical end equals its post-query base field. Each capacity end equals that base plus the corresponding allocation-size argument, modulo 32 bits.

3. **Capacity boundary.** For either sequence, initial counts of 31 and 32 both select a nominal capacity of 32. An initial count of 33 selects 33. Thus, 33 produces byte-size arguments of 264 for the first sequence and 1,320 for the second.

4. **Count changes between queries.** If the first sequence’s initial count is 2 and its later count is 40, the function requests 256 bytes, records a logical end at base plus 320, and records a capacity end at base plus 256. It does not reject the logical end for exceeding capacity.

5. **Base replacement.** If a transfer dependency changes the destination base field, and the subsequent count dependency leaves that field unchanged, both end fields are calculated from the replacement base rather than the original allocation result.

6. **Independent second anchor.** If the second F-f4fd698ba468 result differs from first anchor +16, second-sequence and metadata writes still use that returned second anchor. The final result is second anchor minus 16.

7. **Trailing byte width.** If source +36 contains `0xA5`, the final metadata operation writes that byte to second anchor +20. It does not directly copy a four-byte word there.

8. **Overflowing capacity product.** If the first count query returns `0x20000000`, the first allocation call receives a zero byte-size argument. Any successful continuation depends on behavior not established here.
