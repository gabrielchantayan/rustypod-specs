# F-660d7b7795ca

## Purpose

F-660d7b7795ca performs ordered writes to caller-related storage, invokes dependencies to derive further addresses, processes a local iteration state until a dependency returns exactly 1, and conditionally consumes a linked structure before a final dependency call.

Its established contract consists of memory accesses, argument identities, call ordering, and branch conditions. In particular, two local slots passed to an initial handoff are later overwritten and passed to a second handoff **at the same addresses**. Their reuse is observable to dependencies that compare addresses or retain aliases.

The sequence is consistent with lifecycle teardown and release of linked records. Those meanings are **inferred intent**, not established guarantees about destruction, ownership, or memory release.

### Conditional handoff and ordered slot reuse

After the first handoff returns, F-1b9e6fff9bc9 receives B − 40 and returns C.

The function identifies:

- The **head slot** at C − 28.
- The **control slot** at C − 12.

It reads the four-byte control value and tests it against zero. If zero, it skips both conditional handoff calls and the entire chain loop. A nonzero head alone does not cause processing.

On the nonzero-control path, the function reuses the two local slots from the first handoff, in this order:

1. It reads the control slot again, treats that value as an address, reads four bytes at that address plus 8, and overwrites the **seed/payload slot** with that payload.
2. It reads the control slot again and overwrites the **result/control slot** with that control value.
3. It calls F-d0acc006efef with the auxiliary-area address, head-slot address, seed/payload-slot address, and result/control-slot address.

The third and fourth arguments to F-d0acc006efef are therefore **exactly the same addresses**, respectively, as the third and fourth arguments previously passed to F-7fa3e55b7211. They do not point to fresh copies.

This establishes both storage identity and overwrite ordering. An alias retained by the earlier dependency refers to the reused storage: first the seed/payload contents are replaced, then the result/control contents. Any observation through such an alias remains subject to the dependency’s actual behavior and valid local-storage lifetime.

The control reads are separate accesses, not a single immutable snapshot. The value tested, the address used for the payload read, and the value copied into the result/control slot are not guaranteed equal under mutation.

After F-d0acc006efef returns, the function calls F-88d9235286f8 with:

- The head-slot address.
- A fresh four-byte value read from the control slot.
- Zero.

Thus, a control-slot change made by F-d0acc006efef affects this later argument. The function does not reload the payload for this call, nor does it pass the result/control slot’s address as the second argument.

### Linked-structure consumption

Still within the nonzero-control branch, the function repeatedly reads the head slot. Zero ends the loop. Each nonzero value is retained as the current record address.

The record fields used directly are:

| Byte offset | Use |
|---|---|
| 0 | Successor value written to the head slot |
| 4 | Second argument of the first per-record call |
| 8 | First argument of the first per-record call |

For each retained record, the head is advanced before either per-record dependency call. The function reads the record’s offset-0 field and writes that value into the head slot.

It then calls F-ff1bdc376dcd twice:

- First with the values from record offsets 8 and 4, followed by zero.
- Then with the retained record address, 1, and zero.

The relative evaluation order of the offset-8 and offset-4 argument reads is not established. Both belong to the first call after the head update; they are not specified as snapshots taken before that write. Aliasing between the head slot and record storage can therefore matter.

The second call uses the retained current-record address, not a newly read head value. The next loop decision, however, reads the head slot again. If either dependency changes the head, traversal follows the value then present rather than an immutable successor snapshot.

These calls are compatible with releasing associated storage and then the record, but actual release and ownership transfer are not established.

## Acceptance examples

These are conditional static expectations, not executed test results. Each assumes valid reached accesses and normally returning dependencies unless stated otherwise.

1. **Immediate predicate completion.**  
   If the first predicate return is 1, no F-dcbd5e1e578f call occurs. The result slot and seed slot are copied into their respective handoff slots.

2. **Exact comparison.**  
   Predicate returns of 0, −1, 2, then 1 produce exactly three advance calls, each between its non-1 result and the next predicate call.

3. **Local address identity across handoffs.**  
   Suppose the seed and result copies contain values S and R when F-7fa3e55b7211 is entered. If the nonzero-control path is later taken, F-d0acc006efef receives the same third-argument address and the same fourth-argument address. Before that call, the former slot is overwritten with the payload, then the latter with the control value. Fresh storage with equal contents would not satisfy this identity requirement.

4. **Zero control with a nonempty head.**  
   If the control test reads zero, the conditional handoffs and chain loop are skipped even when the head is nonzero. The conditional slot overwrites also do not occur. The final dependency remains reachable.

5. **Control mutation during the second handoff.**  
   If F-d0acc006efef replaces the control-slot value, F-88d9235286f8 receives the replacement on its subsequent read, not necessarily the value copied into the result/control slot.

6. **One stable record.**  
   If the post-handoff head identifies one valid record whose successor is zero, with no relevant aliasing or head mutation, the head is set to zero before the two per-record calls. The second call receives that record’s retained address and arguments 1 and zero.

7. **Dependency-directed traversal.**  
   If a per-record dependency replaces the head slot, the next iteration uses that replacement. It need not follow the successor originally copied from the current record.

8. **Nonterminating predicate.**  
   If every predicate return differs from 1 and calls continue returning, execution remains in the iteration phase. Neither handoff after iteration, conditional processing, nor the final call is reached.
