# F-9dfe5f6048f1

## Purpose

F-9dfe5f6048f1 performs ordered dispatch through a primary object, then through objects obtained from a linked sequence, and finally through a fallback dependency.

The established selection rule is:

1. Invoke the primary object’s dispatch operation.
2. If its status is nonzero, return the current contents of a shared four-byte result slot.
3. Otherwise, visit linked entries in order and resolve a candidate object from each entry.
4. Invoke each non-null candidate’s dispatch operation. Stop at the first nonzero status and return the shared result slot.
5. If traversal ends without a nonzero dispatch status, invoke the fallback dependency and return its four-byte result.

The dispatch status and the returned result are distinct. A nonzero status selects a result; it is not itself the result.

**Inferred intent:** This resembles a primary-handler, secondary-handler, and fallback arrangement. The supplied static evidence does not establish application-level meanings for the arguments, statuses, linked entries, or returned bits.

## Behavior

### 1. Establish the shared result slot

The function initializes one four-byte result slot to zero before making any dependency call.

Every dispatch invocation receives the address of this same slot. The function does not reset it between dispatch attempts. Consequently, an unsuccessful dispatch can affect the value later returned by a successful dispatch.

The slot belongs to this invocation. Its address is exposed to dispatch callees, but the evidence establishes no right for a callee to use that address after this invocation ends.

### 2. Attempt primary dispatch

The function reads the primary object’s dispatch-table address, obtains the callable at table byte offset `0x80`, and invokes it with the primary object, all three forwarded arguments, and the result-slot address.

If the returned status is nonzero, the function returns the slot’s current four-byte contents. It does not inspect the linked sequence or call either named dependency on this path.

A dispatch need not write the result slot to cause this return. For example, if primary dispatch returns nonzero without modifying the slot, the function returns the initial zero.

If the status is zero, processing continues. Any result-slot write made by primary dispatch remains in effect.

### 3. Obtain the linked sequence after primary dispatch

Only after a zero primary status does the function read the primary object’s first-entry field at byte offset `0x14`.

This timing is observable: a primary dispatch that changes that field before returning can change which sequence is traversed. The function does not use a first-entry value captured before primary dispatch.

A zero first-entry address skips candidate resolution and proceeds directly to fallback.

### 4. Resolve each linked entry

For each nonzero current-entry address, the function invokes F-682adfd5a561 with:

- The current-entry address.
- The integer selector `6`.

This call occurs once per visited entry. Its return is interpreted as a candidate-object address.

If that address is zero, no candidate dispatch occurs for that entry. Traversal advances using the current entry’s next-entry field.

If the address is nonzero, the function obtains the candidate’s dispatch-table address and invokes its callable at byte offset `0x80`, using the candidate itself as the object argument. Arguments A, B, and C and the shared result-slot address are forwarded unchanged.

Resolution does not itself determine success. A non-null candidate must still return a nonzero dispatch status to stop traversal.

### 5. Select a candidate result or advance

If candidate dispatch returns nonzero, the function returns the current result slot without processing later entries or calling fallback.

If candidate dispatch returns zero, traversal continues. Any writes it made to the result slot remain available to later dispatches.

On every ordinary continuation, the next-entry address is read from byte offset `0x14` of the current entry **after** resolution and any candidate dispatch have completed. The next address is not prefetched before those calls.

Accordingly:

- A callback that changes the current entry’s next field can change subsequent traversal.
- Making that next field zero can terminate traversal.
- Making it point back to an earlier entry can cause repeated visits.
- Invalidating the current entry before continuation can make the subsequent link read invalid.

The function supplies no visited-entry tracking, cycle detection, or traversal bound.

The supplied control structure includes an additional nonzero test of the current-entry value after a successful candidate dispatch. Ordinary entry into that iteration already requires a nonzero value, and no explicit reassignment occurs before the test. It therefore does not establish a separate normal outcome. Effects that corrupt the caller’s execution state are outside the defined preconditions.

### 6. Use fallback on exhaustion

When the initial entry is zero or traversal reaches a zero next-entry address without a successful dispatch, the function calls F-5710a8628cba with:

1. The original primary-object address.
2. Argument A.
3. Argument B.

Argument C and the result-slot address are not passed to this dependency.

The fallback’s four-byte return value replaces the result slot and becomes the function’s return value. Earlier slot writes from zero-status dispatches do not determine the returned value on this path.

No local status check, retry, or interpretation is applied to the fallback return.

## Acceptance examples

These are conditional contract examples, not executed tests. Each assumes valid memory, normal dependency returns, and only the mutations stated.

1. **Primary success without an output write.**  
   Primary dispatch returns status `1` and leaves the slot untouched. The function returns zero. It performs no linked-entry read, resolver call, or fallback call.

2. **Primary result differs from status.**  
   Primary dispatch writes `0x12345678` into the slot and returns a nonzero status. The function returns `0x12345678`, not the status value.

3. **A negative status selects the result.**  
   Under a signed 32-bit interpretation, primary dispatch returns `-1` after writing `9`. Because the status is nonzero, the function returns `9` and does not traverse.

4. **An unsuccessful write survives into later success.**  
   Primary dispatch writes `17` and returns zero. A resolved candidate subsequently returns nonzero without changing the slot. The function returns `17`. This demonstrates that zero status does not discard an output write.

5. **Null candidates are skipped.**  
   Primary dispatch returns zero. The first entry resolves to zero; the second resolves to a candidate that writes `23` and returns nonzero. The function returns `23`. The first entry receives no candidate dispatch, and later entries are not visited.

6. **Fallback supersedes unsuccessful outputs.**  
   All dispatches return zero, although one writes `41` into the slot. Traversal terminates, and F-5710a8628cba returns `52`. The function returns `52`. The fallback receives neither Argument C nor the slot address.

7. **Primary mutation determines the initial entry.**  
   Primary dispatch changes the primary object’s first-entry field and returns zero. Traversal starts from the field value read after that call, not from its earlier value.

8. **Link mutation determines continuation.**  
   Resolution or unsuccessful candidate dispatch changes the current entry’s next field to zero. After the call returns, traversal reads zero and reaches fallback rather than following the previous link.

9. **A nonterminating cycle is not rejected.**  
   Linked entries form a cycle, all resolver and dispatch calls return normally, no dispatch status is nonzero, and no call breaks the cycle. The function continues traversing; no finite fallback or return is guaranteed.
