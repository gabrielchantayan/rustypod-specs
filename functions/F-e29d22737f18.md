# F-e29d22737f18

## Purpose

F-e29d22737f18 performs an ordered sequence of key-based operations on a temporary working object. It selects one of two initial forms, extracts a required component, conditionally converts two optional components, records two presence indications, and obtains a final zero/nonzero acceptance decision.

The function returns a 32-bit value: 1 for acceptance, 0 for an explicit rejection path. Processing is not transactional. Rejection can occur after direct writes to caller storage and after a dependency has received the required component. No direct rollback is present.

“Lookup,” “extraction,” “conversion,” and “working-value adjustment” identify call-site roles. They do not establish a concrete grammar, encoding, ownership model, or dependency implementation.

This contract separates established static behavior from inferred intent and unresolved dependency semantics. No runtime tests have been performed.

| Required-component destination token | 32 bits | Forwarded to F-46f0b3cb316e with the required temporary component. |

The two forwarded tokens are not established to be pointers, handles, or scalar values of any particular application type.

The return value is a 32-bit quantity:

- **0:** both initial lookups return zero; the required delimiter search returns exactly −1; or the final predicate returns nonzero.
- **1:** processing reaches the final predicate, that predicate returns zero, and the subsequent working-object cleanup returns normally.

Other dependency failures have no established mapping to a return value. Normal return is conditional on the invoked dependencies returning normally.

### Configuration reads

After working-object initialization, the function performs two distinct reads of a global configuration pointer:

1. It reads and retains a configuration base.
2. It separately reads the global pointer again and obtains the first initial-form key from offset +0x54 relative to that second pointer value.

The two pointer reads are not required by this contract to produce equal values.

All remaining keys come from the retained first base:

| Offset from retained base | Use |
|---:|---|
| +0x58 | Fallback initial-form key. |
| +0x5c | First optional-value key. |
| +0x60 | Second optional-value key. |
| +0x4c | First presence key. |
| +0x50 | Second presence key. |

Each key is read as a 32-bit quantity when its stage is reached. The fallback key is read only if the first initial lookup returns zero. The other keys are reached only after successful required extraction and adjustment.

Retaining the base does not snapshot its contents. Intervening dependencies may change memory behind it. Later changes to the global pointer do not themselves redirect the retained-base reads.

A separate fixed-address object is passed to delimiter searches. Its contents, size, encoding, and interpretation are unknown.

## Behavior

### Working storage and the shared position

F-b9acea4b06ad first initializes local working storage. The function then performs the configuration reads and initial lookup sequence.

Position-producing calls to F-fdbdf34da83a receive the address of the same writable 32-bit position slot. That slot is reused across stages. There is no visible per-stage immutable position snapshot and no visible independent initialization or validation of the slot.

A successful lookup is therefore operationally expected to leave a usable position, but the body checks only the lookup’s zero/nonzero return. It does not establish that the dependency actually wrote the position.

The position is read again for later calls and arithmetic. If a dependency retains its address and subsequently changes it, later reads can observe a different value. Stable-position explanations are valid only under an additional dependency guarantee that the slot remains unchanged over the relevant interval.

### Initial-form selection

F-fdbdf34da83a receives the context token, working object, first initial-form key, and position-slot address.

- A nonzero result selects the first form and causes a direct byte store of 0 at result offset 2.
- A zero result leads to a second call using the fallback key and the same working object and position slot.

There is no intervening reconstruction or reset of the working object or position slot.

For the fallback:

- A nonzero result causes a direct byte store of 1 at result offset 2.
- A zero result leads to working-object cleanup through F-289ec4311c64 and return 0.

When both initial lookups fail, this body performs no direct result-storage stores and no required-component handoff. That does not exclude dependency side effects.

### Required delimiter search and extraction

After either initial lookup succeeds, F-a21141daa905 receives the working object, fixed delimiter object, and a read of the position slot.

A result of exactly −1 causes working-object cleanup and return 0. The discriminator store has already occurred. No other result field has yet been directly initialized by this body.

Every other search result continues, including other negative values. There is no explicit check that the result is within the working object or at least as large as a position.

For the continuing path:

1. F-ed33cfb647fe receives temporary destination storage, the working object, a position-slot read as the start, and an extent formed by subtracting a position-slot read from the search result.
2. F-46f0b3cb316e receives the required-component destination token and the temporary.
3. F-289ec4311c64 is called on that temporary.
4. F-491a7a9bcafa receives the working object, a later position-slot read as the start, and an extent formed by adding one to the search result and then subtracting a position-slot read.

The search call occurs before the extraction argument reads. Extraction, required-component handoff, and temporary cleanup all occur before the adjustment argument reads. None of those dependencies is established to preserve the shared position slot.

Consequently, extraction and adjustment are not guaranteed to use the same position, and even the search’s starting position need not equal the subsequent extraction start. The representation does not establish an order between separate position reads within one call’s argument expressions.

If the position is stable and the arithmetic is valid, the extraction extent is the search result minus that position, and the adjustment extent is one greater. This conditional relationship does not establish that the adjustment removes text or that one unit means one byte or character.

### Default result stores

After required-component handling and working-value adjustment return normally, the function directly stores, in this order:

1. Byte 0 at offset 0.
2. Byte 0 at offset 1.
3. 32-bit 0 at offset 4.
4. 32-bit 0 at offset 8.

It does not directly rewrite the discriminator at this stage. That absence is not a guarantee that dependencies preserve the discriminator or any other output region.

### First optional value

F-fdbdf34da83a receives the context token, current working object, first optional-value key, and shared position-slot address.

If the lookup returns zero, this optional stage performs no delimiter search, extraction, conversion, or adjustment.

If the lookup returns nonzero, F-a21141daa905 searches using the fixed delimiter object and a position-slot read.

- Search result −1 skips extraction, conversion, and adjustment.
- Any other result continues.

On continuation, F-ed33cfb647fe constructs a temporary using a position-slot read as the start and the search result minus a position-slot read as the extent. F-165e4ac372ff then receives the context token and temporary. Its 32-bit return value is directly stored at result offset 4.

The temporary is cleaned up through F-289ec4311c64. Only afterward does F-491a7a9bcafa receive the working object, a later position-slot read as the start, and an extent formed by subtracting a position-slot read from the search result and then adding one.

The converter result is not inspected for an error sentinel. Zero and every other returned 32-bit pattern are stored without a separate acceptance check.

The extraction, conversion, and cleanup calls precede the adjustment position reads. The position therefore has the same mutability caveat as in required extraction.

### Second optional value

The same conditional sequence follows for the second optional-value key, with the conversion result stored at offset 8.

This stage operates on the working object as it exists after the first optional stage. No original-input snapshot is restored. Each optional stage is attempted at most once.

A missing optional delimiter does not immediately reject the function. Processing continues with later stages, although the preceding lookup or search may have side effects.

### Presence indications

F-fdbdf34da83a is called with the first presence key and a null position-output argument. A nonzero return causes a direct byte store of 1 at offset 0.

The corresponding call for the second presence key follows, also with a null position-output argument. A nonzero return causes a direct byte store of 1 at offset 1.

A zero return causes no new direct store for that presence indication. It does not prove that the earlier zero is still present, because intervening dependencies and aliasing remain unresolved.

These operations use the same evolving working object. Their apparent presence-check role does not establish that they are read-only.

### Final processing and acceptance

F-0a68426fd411 receives the working object and numeric argument 0x20.

After that call, a 32-bit word associated with the local working-storage region is read and passed by value to F-d8cbf9aa79a9. The relationship between that word and the working object’s internal layout is unresolved.

- Predicate result zero: clean up the working object and return 1.
- Predicate result nonzero: clean up the working object and return 0.

Cleanup follows the predicate decision on both paths. The body does not recheck the predicate or inspect output contents after cleanup.

Neither “empty residual input” nor “valid residual input” is established as the predicate’s meaning.

### Integer arithmetic and exceptional ranges

Positions and delimiter-search results are represented as signed 32-bit integers. Conversion results and configuration keys are 32-bit quantities without an established application-level signed interpretation.

The represented extent expressions differ in evaluation grouping:

- Extraction: search result minus a position read.
- Required adjustment: search result plus one, then minus a position read.
- Optional adjustment: search result minus a position read, then plus one.

No bounds or overflow checks are visible. The arithmetic must not be replaced with unbounded mathematical arithmetic or assumed to wrap without execution-model evidence. In particular, equal mathematical results do not imply equal intermediate-overflow behavior.

Only −1 is explicitly rejected as a search result. Other negative results, reversed ranges, and overflowing extents are passed onward if execution reaches the corresponding calls.

## Side effects

### Direct effects and non-transactionality

On the fully traversed path, direct stores and handoffs occur in this order:

1. Discriminator store.
2. Required-component handoff.
3. Four default result stores.
4. First optional conversion store, if reached.
5. Second optional conversion store, if reached.
6. First presence store to 1, if recognized.
7. Second presence store to 1, if recognized.
8. Final processing, predicate evaluation, and working-object cleanup.

Dependencies are interleaved throughout. They may affect globals, configuration contents, shared position storage, output regions, or other reachable state.

There is no direct rollback. This means the function does not explicitly restore earlier values; it does **not** mean that earlier stores necessarily remain the final contents. Final-content guarantees require an explicit assumption that subsequent dependencies do not modify or alias the relevant regions.

### Ownership and lifetime

The function initializes one working object and constructs up to three extracted temporaries. Each temporary construction that returns normally is followed by its consumer and then an explicit F-289ec4311c64 call.

The required temporary is cleaned up before later parsing. Retention beyond that point requires an appropriate independent lifetime arrangement by F-46f0b3cb316e. Copying, sharing, transfer, and borrowing are not distinguished by the available evidence.

Optional converter results are stored as opaque 32-bit quantities. No release of those stored values is visible. No release of pre-existing values at offsets 4 and 8 precedes their replacement with zero.

The working object is explicitly cleaned up on every visible normal return path. This does not establish cleanup during exceptions, nonlocal exits, allocation failure, or invalid-memory behavior.

## Acceptance examples

These are conditional static traces, not executed tests. They assume valid reached accesses, defined arithmetic, and normal dependency returns. Claims about final memory contents additionally require that intervening dependencies neither modify nor alias the specified regions.

### Both initial lookups fail

If both initial lookups return zero, the working object is cleaned up and the function returns 0. There are no direct result stores and no required-component handoff. Dependency effects remain possible.

### Required delimiter is missing

If the first initial lookup succeeds and its delimiter search returns −1, the body stores discriminator 0, cleans up the working object, and returns 0. It performs no direct stores to the other result fields.

If only the fallback succeeds, the discriminator store is 1 instead. Final discriminator contents require cleanup and other dependencies to preserve that region.

### Optional components and presence indications are absent

If required extraction completes, both optional lookups return zero, both presence lookups return zero, and the final predicate returns zero, the body performs all four default stores and returns 1 after cleanup.

Under the additional output-preservation assumption, the final presence bytes and optional fields are zero, and the discriminator records the selected initial form. Without that assumption, only the direct-store trace and return decision are established.

### Optional delimiter is missing

If the first optional lookup succeeds but its search returns −1, no first optional conversion or adjustment is requested. Later stages still execute.

The body makes no replacement store at offset 4 for that stage. Its final value is zero only if dependencies preserve the earlier default store.

### A conversion returns zero

If an optional extraction reaches F-165e4ac372ff and it returns zero, the body stores 32-bit zero in the corresponding field and continues. No conversion-error branch is taken.

Even with output preservation, that field alone cannot distinguish this case from an absent optional value.

### Position changes before adjustment

Suppose a search returns 12 and the extraction argument reads both observe position 5. The requested extraction starts at 5 with extent 7.

If an intervening dependency changes the exposed position slot to 8 and both adjustment reads observe 8, the requested adjustment starts at 8 with extent 5. Extraction and adjustment need not describe the same span.

If instead the position remains 5 throughout, the adjustment extent is 8.

### Final rejection after stores

If the final predicate returns nonzero, the function cleans up the working object and returns 0. Earlier stores and the required-component handoff have already occurred, and no direct rollback follows.

Their persistent effects depend on dependency behavior; failure does not promise either unchanged outputs or preserved intermediate outputs.

### Delimiter equals a stable position

If all relevant position reads have the same value and the search returns that value, extraction is requested with extent zero and adjustment with extent one. Whether those requests are valid remains a dependency-contract question.

- Concrete grammar, key values, delimiter contents, and encoding.
- Position and extent units.
- Whether lookups or searches consume or mutate working content.
- Whether dependencies retain and later modify the position-slot address.
- Internal working-object layout and initialization of the word used by the final predicate.
- Meaning of numeric argument 0x20.
- Optional-result signedness, error conventions, and ownership.
- Aliasing among arguments, result storage, configuration memory, and dependency-managed state.
- Arithmetic overflow semantics and valid dependency ranges.
- Behavior on malformed input, resource exhaustion, abnormal termination, or invalid memory.

The two global-pointer reads are distinct; their equality is not established. Position stability and output preservation likewise require independent guarantees, not assumptions supplied by this contract.
