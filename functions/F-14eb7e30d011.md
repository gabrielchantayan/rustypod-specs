# F-14eb7e30d011

## Purpose

F-14eb7e30d011 performs a two-stage recognition operation against an object-mediated data source. It accepts either:

- A primary signature at an initially selected location, producing a displacement of zero.
- A wrapper signature whose fields are used to calculate a displacement, followed by a primary signature at a second selected location.

The function returns a 32-bit success indicator. It also writes a 32-bit displacement through an output pointer on certain paths. A failed return does **not** imply that the output location is unchanged: the calculated displacement is stored before the second operation is attempted.

The interpretation as a format recognizer is inferred intent. The established behavior consists of indirect calls, helper calls, 16-bit comparisons, displacement arithmetic, output writes, and a finalization call.

## Interface

### Inputs

The function receives three arguments:

1. **Source object reference.** A pointer to an object whose first machine word provides access to an indirect dispatch structure. The function uses callable entries at byte offsets 44 and 12 within that structure.
2. **Base displacement.** A 32-bit integer used in the position arguments of both source operations.
3. **Output displacement pointer.** A pointer to a writable 32-bit integer.

The supplied representation uses 32-bit integer and pointer-sized address operations, 16-bit unsigned header accesses, and a 64-bit helper result split into two 32-bit halves.

The source object and its dispatch structure must be valid whenever accessed. The output pointer must be writable whenever an output-producing branch is reached. There is no explicit null-pointer validation.

### Return value

The function returns:

- **1** when either recognition path succeeds.
- **0** when the first source operation reports a nonzero result, the inspected signatures do not select a successful path, or the second source operation or its signature check fails.

These are exact return values, not propagated dependency status codes.

### Internal data layout

A local working area contains two 32-bit words. Its address is passed to F-d9e0ae06e54d during initialization and to F-cc6f52873d53 during finalization. The first word is also used as the third argument to the object’s source-operation entry.

A separate retained 32-bit context value comes from the object entry at dispatch offset 44.

F-870c4fcf7295 returns a 64-bit value. Its low 32 bits contribute to the first source position. Its high 32 bits contribute to a header address.

Relative to that derived header address, the function uses the following fields:

| Byte offset | Width | Interpretation established by this function |
|---|---:|---|
| 0 | 16 bits, unsigned | Initial signature; later reread after a successful second source operation |
| 20 | Address only | Start address passed to F-4055be9c3f18 |
| 28 | 16 bits, unsigned | Input to the first F-0ec8efa9c769 call |
| 124 | 16 bits, unsigned | Wrapper’s secondary signature |
| 126 | 16 bits, unsigned | Input to the second F-0ec8efa9c769 call |

These offsets do not establish field names, a complete record layout, or the extent consumed by F-4055be9c3f18.

The accesses are unsigned 16-bit loads. The supplied evidence does not independently establish the byte order of the underlying data or any alignment guarantees.

## Behavior

### Initialization and first source operation

The function first invokes the object entry at dispatch offset 44, passing the source object as its sole visible argument. It retains the returned 32-bit context.

It then invokes F-d9e0ae06e54d with the address of the two-word working area and that context.

Next, it invokes F-870c4fcf7295 with the arguments 1024 and the retained context. The returned 64-bit value has two distinct uses:

- The low 32-bit half is added to the caller’s base displacement to obtain the first source-operation position.
- The high 32-bit half is added to the first word of the working area to obtain the header address.

The header address is calculated once and retained. It is not recomputed before the later signature check.

The function invokes the object entry at dispatch offset 12 with five arguments, in this order:

1. The source object.
2. The calculated first position.
3. The first word of the working area.
4. The integer constant 1.
5. The integer constant 0.

The meanings of the last two arguments, the position units, and the amount of data affected are not established. In particular, the argument 1 must not be treated as evidence of a one-byte transfer.

Immediately after this call, the function reads a shared 32-bit comparison value and retains a copy for possible use after the second source operation.

If the first source operation returns nonzero, the function performs no header comparison or direct output write. It proceeds to finalization and returns 0.

### Direct recognition

If the first source operation returns zero, the function reads the unsigned 16-bit value at header offset 0.

It compares that value, zero-extended to 32 bits, with a fresh read of the shared comparison value. Equality causes the function to:

1. Store the 32-bit value zero through the output pointer.
2. Invoke finalization.
3. Return 1.

This branch takes precedence over wrapper recognition. If the primary comparison value is also 17474, an initial header value of 17474 is accepted directly; the wrapper fields are not inspected by this function on that path.

The earlier retained copy of the comparison value is not the operand used for this direct comparison. The source contains a later shared-value read here; no dependency call separates the capture from this comparison.

### Wrapper qualification

If direct recognition fails, the function tests the already-read initial signature against 17474, hexadecimal 4442.

If that test fails, it finalizes and returns 0.

If it succeeds, the function reads the unsigned 16-bit field at header offset 124 and compares its zero-extended value with the shared comparison value read at this check.

A mismatch causes finalization and return 0. No displacement calculation or direct output write occurs.

Thus, entry into the displacement-calculation path requires both:

- An initial signature equal to 17474 that did not take the direct-recognition branch.
- A secondary signature at offset 124 equal to the shared primary comparison value.

### Displacement calculation

Once the wrapper qualifies, dependency calls and header-field reads occur in this order:

1. Read the unsigned 16-bit field at offset 28 and pass it to F-0ec8efa9c769. Retain that call’s 32-bit result.
2. Read the unsigned 16-bit field at offset 126 and pass it to F-0ec8efa9c769. Retain that call’s 32-bit result.
3. Pass the address at header offset 20 to F-4055be9c3f18. No return value from that call is used.
4. Invoke F-b5c826d2ab04 without visible arguments.
5. Pass its 32-bit result and the original retained context to F-d7be9cfb4000. Retain the resulting 32-bit value.

The displacement is the first conversion result plus the product of the second conversion result and the F-d7be9cfb4000 result.

These fields are not all captured before the first dependency call. For example, the field at offset 126 is read only after the first conversion call returns. If dependencies can modify the header storage, the later read observes the storage as it exists then.

The calculated displacement is written through the output pointer **before** the second source operation.

### Second source operation and final recognition

The function invokes the object entry at dispatch offset 12 again, using:

1. The source object.
2. The calculated displacement plus the caller’s base displacement plus 2.
3. The first word of the working area as evaluated for this call.
4. The integer constant 1.
5. The integer constant 0.

The dispatch entry is obtained again; the implementation does not retain the first operation’s callable entry for reuse.

If this operation returns nonzero, the function does not perform the final header load. It finalizes and returns 0, leaving its earlier displacement write in place unless some other effect changes that storage.

If the operation returns zero, the function rereads the unsigned 16-bit signature at the **original retained header address**. It compares that value with the shared comparison value captured immediately after the first source operation, not with a fresh shared-value read.

Equality produces finalization and return 1. Inequality produces finalization and return 0.

### Arithmetic boundaries

The displacement calculation uses 32-bit integer results. Both position calculations likewise combine 32-bit quantities. There is no visible checked arithmetic, range validation, saturation, or explicit rejection of negative values.

For cases where all signed arithmetic results are representable, the expressions above specify the values directly. The supplied representation alone is insufficient to promise a portable overflow rule for the signed multiplication and additions. Overflow-dependent behavior is documented_only.

The header-address calculation also depends on 32-bit address arithmetic. Validity of the resulting address is a caller/dependency precondition, not something checked here.

## Side effects

### Direct writes

The function directly writes the caller’s output in exactly two circumstances:

- Zero on direct recognition.
- The calculated displacement after wrapper qualification and calculation, regardless of whether the subsequent recognition succeeds.

The function does not initialize the output on entry or restore an earlier output value on failure.

Statements about an “unchanged output” must be limited to the absence of a direct write by this function. The object methods, helpers, aliasing, and finalization may have additional effects not specified here.

### Finalization and ownership

Every explicit normal return is preceded by one call to F-cc6f52873d53 with the address of the working area.

The function does not inspect a result from that call. Its return indicator is selected by the recognition path, but finalization occurs before the caller receives that indicator.

The initialization/finalization pairing suggests managed working storage. It does not establish whether either dependency allocates, frees, retains, borrows, or transfers ownership of any memory. No ownership rule for the context, working-area contents, or header address can be inferred solely from the pairing.

### Aliasing and mutable state

The interface contains no visible non-aliasing guarantee. An output store that overlaps header storage, the source object, or other reachable state may affect subsequent behavior. In particular, the calculated displacement store occurs before the second dispatch lookup and source operation.

The retained header address and retained comparison value remain fixed after their respective captures. The bytes at that header address, the object dispatch structure, the working-area contents, and shared state need not remain fixed.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed tests. Assume valid accessible storage, arithmetic within representable ranges, normal dependency returns, and no additional mutations except those stated.

1. **Initial operation fails.**  
   If the first source operation returns 9, the function calls finalization and returns 0. It does not inspect the header or directly write the output.

2. **Direct primary match.**  
   If the first source operation returns zero and the initial unsigned 16-bit signature equals the shared comparison value used at that check, the function stores zero, finalizes, and returns 1. It does not call the wrapper-processing helpers or perform a second source operation.

3. **Neither signature qualifies.**  
   If the initial signature is neither the primary comparison value nor 17474, the function finalizes and returns 0 without directly writing the output.

4. **Wrapper secondary mismatch.**  
   If the initial signature is 17474, direct recognition has failed, and the field at offset 124 differs from the primary comparison value, the function returns 0 after finalization. Neither conversion call occurs.

5. **Successful displaced recognition.**  
   Suppose wrapper qualification succeeds, the conversion results are 7 and 3, and F-d7be9cfb4000 returns 100. The stored displacement is 307. With a base displacement of 20, the second source position is 329. If that operation returns zero and the reread signature equals the earlier retained comparison value, the function returns 1.

6. **Calculated output survives recognition failure.**  
   Under the same arithmetic conditions, if the second operation returns nonzero, the function returns 0 after having stored 307. There is no rollback.

7. **Retained comparison value matters.**  
   If the shared comparison value is 4660 when captured after the first operation and a later helper changes it to 22136, final recognition still requires a reread signature of 4660. A signature of 22136 alone does not satisfy that final comparison.

8. **Comparison width matters.**  
   If the relevant shared comparison value is 65536, no unsigned 16-bit signature can equal it after zero-extension. This function does not truncate the shared value to 16 bits for comparison.
