# F-4049ce15fe5a

## Purpose

F-4049ce15fe5a conditionally accepts a 32-bit selection value for an object. It first rejects values whose signed 32-bit interpretation is negative. Otherwise, it obtains an unsigned bound from F-8180d7378e16 and accepts only a value strictly below that bound.

On acceptance, it writes the selection into an object-relative field and invokes three dependencies in a fixed order. If those calls return normally, the function returns zero. Rejection returns the 32-bit pattern `0xFFFFFFCE`, equivalent to −50 when interpreted as a signed 32-bit integer.

The sequence suggests selection followed by dependent updates, but the semantic meanings of the object, the bound, and those updates are not established. This contract specifies the visible selection gate and call sequence without assigning undocumented meanings to the dependencies.

## Interface

### Inputs

The function takes two arguments:

- **Object base:** represented in the supplied material as a signed integer and used to form addresses relative to an object. Its operational role is an address carrier rather than an ordinary numeric quantity.
- **Selection:** a 32-bit unsigned value. The initial check also interprets this same bit pattern as a signed 32-bit value.

The selection must satisfy both conditions to reach the accepted path:

1. Its signed 32-bit interpretation is nonnegative.
2. Its unsigned value is strictly less than the bound returned by F-8180d7378e16.

Consequently, only selections from `0x00000000` through `0x7FFFFFFF` can be accepted. A large unsigned bound does not bypass the signed-range restriction.

### Output

| Outcome | Returned bit pattern | Signed interpretation |
|---|---:|---:|
| Accepted path completes normally | `0x00000000` | 0 |
| Either selection check fails | `0xFFFFFFCE` | −50 |

No symbolic error classification is established. In particular, the negative result must not be assigned a platform-specific error name without additional evidence.

## Behavior

### 1. Signed-range gate

The function first evaluates whether the selection’s signed 32-bit interpretation is nonnegative.

Selections from `0x80000000` through `0xFFFFFFFF` fail this gate. For such a selection:

- F-8180d7378e16 is not called.
- The selection field is not written by this function.
- None of the three accepted-path dependencies is called.
- The function returns `0xFFFFFFCE`.

This path contains no visible object-memory access. Thus, the supplied body does not require a valid object merely to execute this rejection path. That observation does not establish a broader calling convention permitting invalid objects.

### 2. Bound acquisition and unsigned comparison

For a selection passing the signed-range gate, the function calls F-8180d7378e16 with the address at object offset `0xEE0`.

The returned value is used as an unsigned 32-bit bound. Acceptance requires a strict unsigned comparison: the selection must be less than that bound.

If the selection equals or exceeds the bound:

- The selection field is not written by this function.
- F-53376d904416, F-a96742fec78e, and F-087700124fe9 are not called.
- The function returns `0xFFFFFFCE`.

This rejection is not necessarily side-effect-free. F-8180d7378e16 has already executed and may have effects that are not described by the supplied material.

A zero bound rejects every selection that reaches this comparison. No subtraction, index scaling, or adjustment of the returned bound is visible.

### 3. Selection write

After both checks succeed, the function writes the original 32-bit selection value to object offset `0x28`.

This write precedes every accepted-path dependency call. No prior value from that field is read by the visible body, and no rollback is visible.

The write is the only direct object-memory write established for F-4049ce15fe5a. It does not establish the field’s final value at function return: a later dependency could modify the field, invalidate the object, or otherwise change relevant state.

### 4. Ordered dependent calls

After the selection write, the function invokes:

1. F-53376d904416 with the object base, the selection, and the address at object offset `0xE2C`.
2. F-a96742fec78e with the object base.
3. F-087700124fe9 with the object base.

The order is fixed in the visible body. There is no visible branch between these calls and no visible inspection of their return values.

If all three calls return normally, F-4049ce15fe5a returns zero. This result establishes completion of the local accepted path, not success of undocumented operations performed by the dependencies.

If a dependency fails to return normally, the supplied material establishes no recovery, rollback, or resulting return value.

## Side effects

The directly established effects are:

- A conditional 32-bit write at object offset `0x28`.
- A conditional call to F-8180d7378e16.
- Three additional calls on acceptance, in the order specified above.

The visible body contains no explicit allocation, deallocation, ownership transfer, locking, global-variable access, or input/output operation. This absence applies only to the visible body.

No dependency may be assumed to preserve global state, preserve the object, retain or release memory, or leave previously supplied addresses valid. Passing an address does not itself establish ownership transfer.

The function does not visibly reacquire the bound after writing the selection. Nor does it visibly revalidate the object between dependency calls. Any requirement that the object remain usable across those calls is an external precondition, not a guarantee established here.

Rejection therefore has two distinct effect profiles:

- **Signed-range rejection:** no visible dependency calls or object-memory writes.
- **Bound rejection:** F-8180d7378e16 has executed, but the selection write and remaining calls have not.

## Acceptance examples

These are conditional contract examples derived from static evidence, not executed tests. Accepted-path examples assume valid memory and normally returning dependencies.

### Negative signed interpretation

The same rejection applies to `0x80000000`, even if a hypothetical bound would be `0xFFFFFFFF`.

A later dependency may change the written field; this example does not require its final value to remain zero.
