# F-549c3b0be3d0

## Purpose

F-549c3b0be3d0 conditionally writes caller-addressed byte storage, reads source bytes, and invokes F-870c4fcf7295. Its only explicit normal return is a 32-bit zero.

The body contains operations consistent with initializing and mixing a byte buffer: a fill operation, fixed-position updates, and source-dependent updates at computed addresses. This is **inferred intent**, not an established algorithm classification. Hashing, encryption, validation, and standardized encoding are not established.

After argument capture, the fill parameters describe 24 bytes. The external control values needed to establish execution order are unavailable. Consequently, the body does not establish that every invocation fills 24 bytes, performs the fixed updates, processes source data, or reaches a return.

## Behavior

### Arithmetic and observation model

The representation uses 32-bit integer arithmetic, low-16-bit masks, character narrowing, and byte accesses.

A mask of `0xFFFF` retains 16 bits; a mask of `0xFF` and a byte store retain eight bits. These reductions do not resolve the semantics of earlier signed overflow, signed right shifts, character signedness, integer-to-address conversion, or pointer ordering.

The byte equations below describe low-eight-bit relationships, conditional on the represented operations completing. Where an expression reads a target more than once, a single “old byte” denotes stable storage across those reads. Relative evaluation order within an expression is not independently established.

Repeated references to an external location are not treated as one retained snapshot unless the body explicitly retains a value.

### Dispatch and initial state

The initial dispatch token is read from external storage once, before the loop. Each iteration selects an arm by adding the current local token to a freshly read external dispatch bias.

Most arms replace the local token using external transition data. Two arms calculate a token from comparisons or arithmetic.

Changing initial-token storage after entry does not itself replace the current token. Changing the bias can affect a later selection. A dependency effect or aliased destination write can change an external value before its next read.

The comparison arm compares the current cursor against the endpoint, calculates a replacement token, and copies the cursor into the companion pointer. Its token expression separately references the same external transition location twice. If those observations agree at a value \(R\), the token is \(R\) when the cursor is below the endpoint and \(R-3\) otherwise, subject to arithmetic and pointer-comparison semantics. Repeated fill selections without suitable comparison transitions need not traverse the expected extent, and no unconditional fill-termination guarantee follows.

### Fixed-position updates

After capture, this arm performs zero stores in this order:

1. Offset 0.
2. Offset 3.
3. Offset 23.
4. Offset 20.

An external stride-related value is captured **after the third zero store and before the fourth**.

The arm then updates offset 1. The external adjustment location is referenced separately in the narrowed intermediate and in the final expression; these are not one explicitly retained observation.

For a low-byte description, let:

- \(s\) be the low byte of the captured stride-related value;
- \(k_a\) and \(k_b\) be the low bytes of the adjustment observations used in the intermediate and final expression;
- \(b\) be the destination byte used to form the intermediate;
- \(t=(-k_a-b)\bmod256\).

The stored byte is:

\[
-\left(s\big((t+1)\mathbin{\mathrm{OR}}0xFE\big)-k_b+t+2\right)
\bmod256.
\]

The observations \(k_a\) and \(k_b\) agree only under an additional stability assumption.

Before argument capture, selected offsets are zero and the destination base is null. The arm does not guard against that state. With aliasing, earlier writes can also change later external reads.

A replacement token is read after these updates.

### Index selection and progression

A separate arm resets progression to zero.

The index-selection arm combines progression, the retained first argument, and external arithmetic values. The first argument is multiplied by an external value and masked to 16 bits. Progression and that masked product feed related expressions involving products, complements, low-bit-forcing OR operations, and externally supplied coefficients. One result becomes the working index.

The final selector calculation includes a signed right shift by 31 followed by addition of one. Under arithmetic-right-shift semantics, the selector is zero or one. Its intended comparison and branch polarity remain unresolved.

**The replacement-token expression independently references the same external transition location twice.** Let \(A\) denote the observation used in the term containing an increment, and \(B\) the observation used in the other term. These labels describe expression roles, not a guaranteed temporal read order.

Subject to the documented arithmetic semantics:

- Selector zero produces \(A+1\).
- Selector one produces \(B\).

The body does not explicitly retain one shared transition value. The two alternatives are adjacent values **only if \(A=B\)** and the relevant arithmetic supports that interpretation. If the observations differ, adjacency is not guaranteed. Nor is this arm established as a conventional monotonic loop counter or length comparison.

After each source-processing arm, progression becomes:

\[
p\,(\text{previous progression}+0xEFF1)\,0xEFF1
\bmod 2^{16}.
\]

Here \(p\) is captured after the fourth dependency call and before the final destination write. This masked recurrence does not establish progress toward termination.

### Source-dependent processing

Each execution of this arm makes four calls to F-870c4fcf7295, in order. Each call has two represented 32-bit arguments, with the second always 24. Each supplies a distinct secondary output later used in addressing.

Neither the literal 24 nor the secondary-output use establishes division, remainder, or modulo-24 bounds.

#### First call and first byte update

The arm first multiplies the working index by a freshly read address multiplier. That result is retained as the source offset and passed as the first call’s first argument.

After the call returns, the stride-related external location is read separately for:

- A retained full-width coefficient.
- The first destination-offset calculation.
- A retained narrowed character coefficient.
- A retained doubled value.

The first target offset also uses the first call’s secondary output and a fresh address-multiplier read. The relative order of reads within that address expression is not established.

The first target update has the low-byte relationship:

\[
\text{new target}
=
\text{old target}+\text{source byte}+0x55
\bmod256.
\]

The source byte is then read again at the retained source offset. It is not reused from the first update. If the write aliases that source address, this reread can observe the newly stored byte.

#### Second and third calls

The reread source byte is multiplied by `0x9B` and masked to eight bits. A multiplication by `0x93`, complement, and OR with `0xFF` contribute to the second call’s first argument.

That argument also depends on the retained full-width stride coefficient, the separately retained doubled stride value, fresh external arithmetic coefficients, and a fresh address multiplier.

The third call’s first argument combines the working index, an external additive value, and another address-multiplier observation.

The second call’s secondary output remains associated with the next target even though the third call occurs before that update.

#### Middle destination update

The middle target offset uses:

- The **second** call’s secondary output.
- The full-width stride coefficient retained after the first call.
- A fresh address-multiplier observation.

Before the update, a scaled working-index value is calculated using another external multiplier and retained for the fourth call.

The middle update reads another destination byte at an offset using the **third** call’s secondary output, the retained full-width stride coefficient, and a separate address-multiplier reference.

Its low-byte relationship is:

\[
\text{new target}
=
\text{old target}+\text{other destination byte}-\text{working index}
\bmod256.
\]

The two addresses can coincide. Their independently referenced address multipliers are not guaranteed equal.

#### Fourth call and final update

The fourth call’s first argument combines the retained full-width stride coefficient, the retained scaled index, subtraction, OR with `0xFFFFFF39`, an external additive value, the working index, and a fresh address multiplier.

After the call returns:

1. The progression multiplier is captured.
2. The final target offset is calculated from a fresh address multiplier, the retained full-width stride coefficient, and the **fourth** secondary output.
3. The final target byte is updated.
4. Progression is updated using the already captured multiplier.
5. An external replacement token is read.

The final byte coefficient is the narrowed stride character retained after the **first** call. Later calls do not cause that coefficient to be reread.

For stable target byte \(b\) and retained coefficient \(c\), the stored byte has the relationship:

\[
b-c\left(\big((-2b-1)\bmod256\big)
\mathbin{\mathrm{OR}}0xB1\right)-0x58
\bmod256.
\]

The target appears more than once in the expression. No dependency call intervenes within that expression.

## Side effects

Directly established effects are external control and arithmetic reads, conditional source-byte reads, destination-byte reads and writes, and four dependency calls per processing-arm execution.

Calls and writes are interleaved. Retained values and fresh observations must remain distinct:

- A stride-location change during later calls does not replace the retained full-width or narrowed stride coefficients.
- A later address-multiplier read can observe a dependency’s change.
- A final destination write that aliases progression-multiplier storage does not replace the multiplier already captured for that update.
- A write that aliases replacement-token storage can affect the subsequent token read.
- Independently referenced transition values in one expression are not contractually one snapshot.

There are no explicit stores addressed to external control locations as such. Aliasing and dependency effects can nevertheless modify them. No synchronization or rollback is visible.

## Acceptance examples

These are conditional static criteria, not executed tests.

1. **Immediate return.** If the initial token plus the first bias observation selects the return arm, the result is zero without an explicit source or destination access.

2. **Persistent initial token.** Changing initial-token storage after entry does not itself replace the local token. A later bias change can affect dispatch.

3. **Conditional fill.** If capture and setup occur and transitions implement the apparent bounded fill loop, destination offsets 0–23 receive `0x49`. This alone establishes no subsequent fixed-update phase.

4. **Fixed-store ordering.** After capture, zero stores occur at offsets 0, 3, 23, and 20. The stride observation lies between the stores at 23 and 20; offset 1 is updated afterward.

5. **Stable index transition.** If both transition observations in index selection equal 100, selector zero produces token 101 and selector one produces token 100, assuming the represented arithmetic completes.

6. **Different index-transition observations.** If the increment-bearing observation is 100 and the other observation is 140, selector zero produces 101 and selector one produces 140. The alternatives are not adjacent. This describes the conditional alternatives, not two results from one invocation.

7. **Byte wraparound.** With source byte `0xF0` and old first-target byte `0x30`, the first byte update stores `0x75`.

8. **Source aliasing.** If that first write targets the source address, the subsequent source reread observes the post-write byte absent another modification.

9. **Middle-address coincidence.** If the second-output target and third-output source address coincide and storage remains stable during the expression, the middle update stores twice the old byte minus the working index, reduced to eight bits.

10. **Retained coefficient.** A stride-location change during the second, third, or fourth call does not replace the narrowed coefficient used by the final byte update.

11. **Captured progression multiplier.** Overwriting multiplier storage through the final destination write does not change the multiplier already captured for the immediate progression update.

12. **Extent and default-path limits.** Exactly 24 writable bytes do not prove processing-path safety. An unrecognized selection writes `0x49` through the fill cursor rather than reporting an error.
