# F-1137792fba7d

## Purpose

F-1137792fba7d conditionally processes an address-like input. For a nonzero input, it checks preceding metadata, reduces accounting fields in a captured context, and passes the metadata address to a dependency. A zero input skips metadata processing and accounting updates, but not the entry dependency or the capture of the context reference.

The reductions and metadata handoff are consistent with releasing an allocated object. This is **inferred intent**, not an established ownership contract. The available evidence does not establish that storage is freed, recycled, retained, or transferred.

There are no explicit payload-content accesses or header-marking operations through the payload or metadata reference. However, context-field accesses can read or write payload bytes or metadata if their calculated addresses overlap those regions. In particular, an accounting write can change the header before its later reread.

This contract describes static evidence and conditional consequences. No runtime tests have been performed.

## Interface

**Input:** one integer-valued argument used as an address.

- Zero selects the null-input path.
- A nonzero value identifies a nominal payload address.
- Metadata is addressed relative to that value, beginning eight bytes before it.
- No explicit length, context argument, or error-output argument is supplied.

**Output:** no explicit return value. Normal completion returns control to the caller. Invalid initial metadata leads to a dependency represented as non-returning.

For the descriptions below:

- **P** denotes the supplied payload address.
- **C** denotes the context reference captured from a global location after the entry dependency returns.

These are descriptive labels, not additional interface parameters.

### Preconditions for normal completion

Normal completion requires:

## Behavior

### Entry and null handling

Every invocation first calls **F-2fd8826557a4**, with no explicit arguments shown. After that call returns, the function reads the global location supplying C.

Changes that F-2fd8826557a4 makes to that global location therefore affect the captured context.

Only then is P tested. If P is zero, the function returns without accessing payload metadata or directly updating context fields. None of the remaining listed dependencies is called.

The null path is not an unconditional no-op: the entry dependency has run, and the global context location has been read. The dependency’s effects are unknown.

### Initial metadata gate

For nonzero P, the function checks the 32-bit header at P − 8.

The header is rejected if:

- it is zero; or
- when nonzero, its least significant bit is set.

The zero test precedes the low-bit test. The represented expression accesses the header for each test, with the second test skipped when the first finds zero. This does not establish volatile semantics or an exact number of machine-level loads.

On rejection, **F-a817d8d58c10** is called with no explicit arguments shown. It is represented as non-returning. No local recovery, error result, or continuation into accounting is shown.

The gate does not validate either index or require a positive accounting amount. A stable header of 2 passes while yielding a masked amount of zero.

### Preparing the first accounting amount

After the gate succeeds, the function calls **F-c0fc6d033caa**, passing captured C.

After that dependency returns, the function:

1. Reads the first unsigned 16-bit index at P − 4.
2. Establishes the corresponding indexed context address.
3. Reads the header again and masks it with **0x3ffffffc**.

The resulting amount retains bits 2 through 29 and excludes bits 0, 1, 30, and 31. It is a multiple of four between zero and 0x3ffffffc inclusive.

The accounting amount is not necessarily derived from the value that passed the initial gate. The dependency can change metadata, and no repeated validity gate is shown. Once obtained, this amount is reused for the next four size reductions, even if an intervening write changes the header.

### Four initial size reductions

Using that captured amount, the function performs these operations in order:

1. Reduces the first indexed size field at C + 0x224 + four times the first index.
2. Reduces the first aggregate size field at C + 0x30c.
3. Reads the second unsigned 16-bit index at P − 2.
4. Reduces the second indexed size field at C + 0xe0 + four times the second index.
5. Reduces the second aggregate size field at C + 0x220.

Each reduction reads the destination value and writes the subtraction result.

The second index is read after the first two writes. Consequently, those writes can affect the second index if their storage overlaps its bytes. Similarly, an earlier accounting write can affect a later accounting destination. The function does not snapshot all metadata or all field values before writing.

### Count reductions and final size reduction

After the four initial size reductions, the function calls **F-09dcb55e8e0a**, with no explicit arguments shown.

Its returned integer selects the count field at C + 0x310 plus four times that result. No range check or clamping is shown.

The function then:

1. Decrements the selected count field by one.
2. Decrements the aggregate count field at C + 0x390 by one.
3. Reads the header at P − 8 again, masks it with 0x3ffffffc, and reduces the field at C + 0x08 by that newly obtained amount.

The final header read occurs after the count updates. The relative order of the header read and the destination-value read within the final subtraction is not independently established.

The final amount can differ from the amount used for the first four size reductions. A dependency or an overlapping context write can change the header. No validity gate is repeated before this final use.

All these direct context accesses use captured C. A later dependency changing the global context reference does not redirect them. Changes to the contents of the captured context remain observable by subsequent reads.

### Final handoff

After the accounting updates, the function calls **F-cc6c9b4a0f68**, passing:

- captured C;
- the metadata address P − 8.

The second argument is not P. The function does not reconstruct or restore the header before handing off its address; overlapping accounting writes may already have changed its contents.

If that dependency returns, the function calls **F-e586bff64fb7**, passing C. After it returns, no further direct metadata or context-field access is shown before normal return.

### Arithmetic boundaries

The size reductions use a 32-bit unsigned masked amount and store 32-bit results. In the represented 32-bit unsigned arithmetic, subtraction produces the result modulo 2³². No saturation, insufficient-balance check, or overflow report is shown.

The count decrements are represented as signed integer operations. Their behavior at signed-overflow boundaries is not established as a supported contract. Under a wrapping machine interpretation, decrementing zero yields the bit pattern 0xffffffff; that interpretation does not establish general signed-overflow semantics.

Index and selector address calculations have no visible overflow protection. The unsigned 16-bit metadata indices have bounded scaled values, but that does not prove the resulting addresses are valid. Selector scaling and address formation have additional unresolved range and overflow constraints.

## Side effects

### Direct memory effects

A successful non-null path performs seven ordered accounting read-modify-writes:

- four size reductions using one captured amount;
- two count decrements;
- one size reduction using a fresh masked header value.

These are seven operations, not necessarily seven distinct destinations.

There are no explicit payload-content operations through P and no explicit header-clearing, poisoning, or marking operation through P − 8. This does **not** guarantee that payload bytes or the header remain unchanged:

- A context destination can coincide with P − 8 and modify the header.
- A context destination can coincide with P or another payload address and read and write payload bytes.
- A context destination can overlap either metadata index and affect its later interpretation.
- Two context destinations can coincide, causing sequential reductions of the same field.

Where destinations coincide, later operations use the values available at their execution points, subject to intervening dependency or external changes.

## Acceptance examples

These are conditional consequences of static evidence, not observed executions. Unless an example states otherwise, all accesses are valid, arithmetic stays within the relevant defined range, dependencies return normally without changing relevant memory, and described destinations do not overlap.

### Null input

Given P = 0:

- F-2fd8826557a4 runs.
- C is captured from the global location.
- The function returns without metadata accesses or direct accounting updates.
- No other listed dependency runs.

This does not constrain side effects of the entry dependency.

### Initial rejection

A stable header of zero causes F-a817d8d58c10 to be called before F-c0fc6d033caa or any direct accounting update.

A stable odd header, such as 5, has the same outcome. No particular diagnostic, exception, exit status, or termination mechanism is specified.

### Ordinary accounting

Given header 0x104, first index 2, second index 3, and selector result 4:

- The first four size reductions use 260.
- Their destinations, in order, are C + 0x22c, C + 0x30c, C + 0xec, and C + 0x220.
- Counts are decremented at C + 0x320 and C + 0x390.
- With the header unchanged, C + 0x08 is reduced by 260.
- The final metadata handoff receives P − 8.

### Accepted zero amount

A stable header of 2 passes the gate and produces a masked amount of zero.

The size read-modify-writes still occur, though their arithmetic leaves destination values unchanged. Both count decrements and both final dependency calls still occur.

### Header changed after validation

Suppose the initial header is 0x100 and F-c0fc6d033caa changes it to 0x200.

The first four size reductions use 512, not 256. No second validity check occurs.

If F-09dcb55e8e0a later changes the header to 0x300, the final size reduction uses 768, provided the intervening count writes do not change that header.

### Accounting write clears the header through aliasing

Let P = C + 0x22c, with first index zero and initial header 0x104. Let the remaining destinations avoid the metadata.

The first indexed destination is C + 0x224, exactly P − 8. Its value is the header value 260, and the captured accounting amount is also 260. The first size reduction therefore writes zero to the header.

The other three initial size reductions still use captured 260. With no subsequent header changes, the final size reduction uses zero. There is no renewed rejection, and the metadata handoff receives the address of the now-zero header.

This is an accounting write affecting metadata, not an explicit header-marking operation.

### Accounting write accesses payload bytes

Let P = C + 0x08, with a stable header of 0x104 and earlier accounting destinations outside the metadata and payload location in question.

The final size destination is exactly P. The function reads the 32-bit value at the payload address and writes that value reduced by 260.

Thus the absence of an explicit payload-content operation does not imply that payload bytes are untouched.

### Captured context remains selected

If a dependency replaces the global context reference after C is captured, subsequent direct context accesses and explicit context arguments still use captured C.

The dependency may nevertheless change the contents of that context and thereby affect later reads.
