# F-340f5b231e68

## Purpose

F-340f5b231e68 initializes four local values, passes the address of the first to F-8834e04b2447, copies the resulting local values into four fields of the original object, and performs two indirect calls through that object. Each indirect call receives two values read from distinct global-data locations. On normal completion, the function returns a 64-bit value formed from the first two local values.

The established behavior is an ordered sequence of one direct call, four field stores, two indirect calls with intervening global reads, and return-value assembly. The meanings of the fields, global values, and indirect operations are not established. An initialization-like purpose is plausible **inferred intent**, not a requirement of this contract.

This specification describes static evidence only. No runtime tests have been performed.

## Interface

### Inputs

The function accepts four inputs:

| Input | Representation in the supplied view | Established use |
|---|---|---|
| Original object address | Pointer to integer storage | Initial first local value; destination base for field stores; receiver for both indirect calls |
| Second input | 32-bit integer word | Initial second local value; also passed directly to F-8834e04b2447 |
| Third input | 32-bit integer word | Initial third local value |
| Fourth input | 32-bit integer word | Initial fourth local value |

The supplied view uses four-byte integer elements and a four-byte component for the pointer-valued portion of the return. Its pointer-to-integer conversion and dispatch expressions are consistent with a 32-bit pointer model. The actual target ABI has not been independently established; this contract does not generalize the function to wider pointers.

The original object address is distinct from the first local value. They initially contain the same address, but F-8834e04b2447 receives an address through which the first local value may be changed. Such a change does not redirect the explicit field stores or either indirect-call receiver.

### Object layout accessed

Four consecutive 32-bit stores use the following byte offsets from the original object address:

| Offset | Width | Source |
|---|---:|---|
| `0x44` | 32 bits | Current first local value, converted to an integer word |
| `0x48` | 32 bits | Current second local value |
| `0x4C` | 32 bits | Current third local value |
| `0x50` | 32 bits | Current fourth local value |

The last store covers bytes `0x50` through `0x53`, inclusive. These offsets follow from integer-element indices and the four-byte element width represented by the supplied view.

For each indirect call, the function reads the original object’s first word as a dispatch-table address and selects the callable entry at byte offset `0x58` from that address. No other object-field meaning is established.

### Global inputs

The indirect-call expressions read four distinct global-data locations. This specification gives them opaque labels:

| Global location | Read label | Destination |
|---|---|---|
| Global A1 | A1 | Argument 2 of the first indirect call |
| Global A2 | A2 | Argument 3 of the first indirect call |
| Global B1 | B1 | Argument 2 of the second indirect call |
| Global B2 | B2 | Argument 3 of the second indirect call |

These are four separate global locations, not four names for unspecified operands or necessarily four different values. Their contents, types, widths, and semantic interpretation are **documented_only**.

The reads are not all taken at function entry. The first pair is read after F-8834e04b2447 returns and after all four field stores. The second pair is read after the first indirect call returns.

### Output

On normal return, the function produces a 64-bit bit-pattern:

- Bits 31–0 are the four-byte representation of the final first local value.
- Bits 63–32 are the final second local word.

Equivalently, the result concatenates the second local word above the first local word. It does not sign-extend either component. A set top bit in the second local word becomes bit 63 of the result.

The result is assembled from local values, not read back from the object fields. None of the three dependency-call results contributes directly to the returned value.

## Behavior

### Local preparation

Before the direct dependency call, the function initializes four local values in the order shown by the supplied view:

1. First local value: original object address.
2. Second local value: second input.
3. Third local value: third input.
4. Fourth local value: fourth input.

Only the address of the first local value is explicitly passed to the dependency. The supplied material does not establish an authorized four-word aggregate interface. In particular, the presence of four local values does not establish that the dependency is permitted to traverse or rewrite them as a record.

The precise physical arrangement of these locals is not independently established by ABI or machine-level evidence.

### Direct dependency call

The function invokes F-8834e04b2447 with three arguments:

1. Address of the first local value.
2. Original second input.
3. Zero.

The function does not inspect the dependency’s return value and does not branch on a success indication.

The address argument exposes the first local value to the dependency. The subsequent field store and return construction therefore cannot be specified as always using the original object address in their first component.

The dependency’s implementation is unavailable. Its effects on adjacent storage, the original object, global data, or other reachable memory remain unknown. In particular, it must not be assumed to preserve the four global locations later read for the indirect calls.

If the dependency returns normally, the function proceeds to the four stores.

### Ordered object stores

The function writes the current local values to the original object in increasing destination-offset order:

1. First local value, converted to a 32-bit integer, at `0x44`.
2. Second local value at `0x48`.
3. Third local value at `0x4C`.
4. Fourth local value at `0x50`.

Each is a separate store. No atomic 16-byte update or rollback is established. If execution is interrupted during this sequence, earlier writes may have occurred without the later writes.

All destinations remain relative to the original object address, even if the first local value now contains another address.

The first store’s pointer-to-integer conversion is represented as a 32-bit conversion. Its interpretation on a wider-pointer target is **documented_only**.

### First global pair and indirect call

After the direct call and all four stores, the function evaluates the first indirect-call expression. That expression:

- Reads the dispatch-table address from the original object’s first word.
- Obtains the callable entry at table byte offset `0x58`.
- Reads Global A1 for argument 2.
- Reads Global A2 for argument 3.
- Calls the selected target with the original object address as argument 1.

The argument mapping is fixed: A1 precedes A2 in the argument list. This does not establish whether A1 is read before A2, or whether either is read before the dispatch information. Evaluation order within this call expression is unspecified by the supplied view.

The global reads occur after the earlier direct call, so they can observe values affected by that dependency’s unknown global effects. The four stores also precede these reads; no separate non-aliasing guarantee for the supplied addresses and global storage is provided.

The indirect callee’s return value is unused.

### Second global pair and indirect call

Only after the first indirect call returns normally does the function evaluate the second indirect-call expression. It:

- Reads the dispatch-table address from the original object again.
- Obtains the callable entry at table byte offset `0x58` again.
- Reads Global B1 for argument 2.
- Reads Global B2 for argument 3.
- Calls the selected target with the original object address as argument 1.

B1 and B2 come from their own distinct global locations; they are not reuse of the first pair’s captured values. Their reads occur after the first indirect call, whose unknown global effects may therefore affect them. The direct dependency’s effects may also remain relevant.

As with the first call, argument positions are established but the relative evaluation order of the two global reads and dispatch selection within the expression is not.

The second dispatch is expressed as a fresh lookup, not reuse of a previously captured target. If the first indirect call changes the object’s dispatch-table address or the selected table entry, the second call may reach a different callable target.

There is no visible result check, conditional skip, or retry between the calls. The second call’s return value is also unused.

### Return assembly

After the second indirect call returns normally, the function concatenates the final second local word and the four-byte first local value into its 64-bit result.

Changes made solely to object offsets `0x44` or `0x48` do not change the return components. Conversely, if a dependency has effective access to the local values and changes them after the stores, the returned components may differ from those previously written to the object.

No further explicit object-field stores follow the second indirect call.
