# F-4cc77f915f7f

## Purpose

F-4cc77f915f7f conditionally creates and submits a keyed payload record to a container referenced through a caller-provided slot. If that slot contains zero, it first requests and initializes a container, then publishes its reference through the slot.

The function returns a 32-bit **1** only after payload processing and record submission both return nonzero and the function writes the supplied key into the record. Every explicit failure branch returns a 32-bit **0**, provided the invoked dependencies and memory accesses complete normally.

“Container,” “record,” “descriptor,” “key,” and “payload” describe roles inferred from use. They do not establish application-level types, allocation mechanisms, payload encoding, or ownership.

Two failure classes have different observable effects:

- **General rejection:** reporting followed by return 0, without explicit cleanup or slot clearing.
- **Cleanup failure:** reporting, record cleanup, container cleanup, slot clearing, then return 0.

Descriptor selection is also observable. Creation and cleanup read two distinct descriptor globals at their respective call sites. Cleanup does not reuse descriptor values obtained during creation.

## Interface

### Inputs and result

The supplied representation uses a 32-bit data model.

| Input | Established interpretation |
|---|---|
| Container-slot address | Address of a readable and writable 32-bit cell containing a container reference. A zero address is explicitly rejected. |
| Key | A 32-bit value. Zero is explicitly rejected; no other bit pattern is explicitly rejected. |
| Payload reference | A 32-bit value passed to dependencies. Zero is explicitly rejected. |
| Requested length | A signed 32-bit value. The value −1 requests dependency-derived length calculation. |

The result is a 32-bit success indicator, not an object reference. A newly created container is exposed through the caller’s slot.

The function does not directly inspect payload bytes. The required payload representation and accessible extent depend on the called operations.

### Visible object layouts

Only the following storage is established:

| Object | Directly accessed storage |
|---|---|
| Caller’s slot | One 32-bit container reference. |
| Container | A 32-bit field at byte offset 0 and a 32-bit field at byte offset 4. |
| Record | A 32-bit field at byte offset 0 and a 32-bit field at byte offset 4. |

The record’s offset-0 field receives the key on success. The other fields supply values to dependencies; their underlying types and meanings are unresolved.

Two distinct global storage locations supply descriptors:

- The **container-descriptor global**, read for container creation and again for container cleanup.
- The **record-descriptor global**, read for record creation and again for record cleanup.

Their contents, storage widths, and complete types are not established by the supplied function alone. They must not be treated as a single descriptor source or as immutable captured values.

### Preconditions beyond explicit checks

A nonzero address is not sufficient for safe execution. Each reached access requires valid storage of the appropriate extent. Referenced objects must remain usable through subsequent field accesses and dependency calls.

There is no explicit validation of:

- Existing container validity or object lifetime.
- Payload extent, encoding, or termination.
- Negative lengths other than the special handling of −1.
- Overlap among the slot, objects, payload, or descriptor storage.
- Dependency-specific argument requirements.

The function establishes no recovery from inaccessible memory, invalid object references, abnormal dependency termination, or dependencies that invalidate storage used later.

## Behavior

### Argument rejection

If the container-slot address, key, or payload reference is zero, the function invokes F-4fc89ec41a6d with the displayed arguments **0x22, 0x7e**, then returns 0.

This path performs no explicit slot dereference, descriptor-global read, object creation, length calculation, or cleanup. Effects of the reporting dependency remain possible.

### Effective length and signed limit

For valid nonzero required inputs, the requested length is used directly unless it equals −1.

When it equals −1, F-1cb585febd84 is invoked with five displayed argument values, in this order:

1. Payload reference.
2. Key.
3. Payload reference again.
4. The original requested length, −1.
5. The 32-bit all-ones value, **0xffffffff**.

Its result becomes the effective signed 32-bit length. The displayed call does not establish the dependency’s actual source-level prototype.

The function rejects an effective length **greater than 64 using a signed comparison**. Rejection uses the general reporting path and returns 0 before reading the caller’s slot.

Consequently:

- 64 is permitted.
- Zero is permitted.
- Negative values are permitted by this comparison.
- An explicit negative length other than −1 does not invoke length calculation.
- The bit pattern 0xffffffff represents −1 in this signed interpretation, not an excessive positive length.

There is no visible length increment, terminator allowance, multiplication, or conversion into another unit.

### Container acquisition

After the length check, the function reads the container reference from the caller’s slot.

If nonzero, that reference is retained for later operations. The function does not run the container-creation initialization step and does not explicitly reload the container reference from the slot afterward.

If zero, the following sequence applies:

1. Read the **container-descriptor global** and pass the value obtained to F-e12621595ccc.
2. If the returned reference is zero, enter cleanup failure.
3. Otherwise, read the returned container’s offset-0 field and pass that value and zero to F-8a2270f25b51.
4. If initialization returns zero, enter cleanup failure.
5. Otherwise, write the created container reference into the caller’s slot.

The container is published only after successful initialization. Publication precedes the eligibility operation, record creation, payload processing, and submission.

The descriptor value used for this creation call is not retained as the descriptor argument for later cleanup.

### Eligibility operation

F-e3cb7acb6263 receives the retained container reference and the key.

- A nonzero result takes the general rejection path.
- A zero result permits record creation.

A duplicate-key check is a plausible interpretation, but only the branch behavior is established.

If a new container was published earlier in this invocation, a nonzero eligibility result does not cause explicit cleanup or slot clearing. Reporting can have its own effects, but this function performs no corresponding rollback.

### Record creation and possible second length calculation

After a zero eligibility result, the function reads the **record-descriptor global** and passes the value obtained to F-e12621595ccc. This is a separate global read from the earlier container-descriptor read and occurs later, after the eligibility operation.

A zero record-creation result enters cleanup failure. The retained record reference remains zero until creation returns nonzero.

After successful record creation, the function checks whether the current effective length is still −1. If so, it calls F-1cb585febd84 again, this time with only the payload reference displayed as an argument. The returned value replaces the effective length.

There is **no second comparison against 64**. Thus, when the first length calculation returns −1, the second calculation may produce a value greater than 64, zero, or a negative value, and that value can reach payload processing.

The two displayed call forms must remain distinct; the available evidence does not justify normalizing them into a known common prototype.

### Payload processing, submission, and key assignment

The function reads the record’s offset-4 field and invokes F-bbc440b3aefa with:

- That field value.
- The payload reference.
- The current effective length.

A zero result enters cleanup failure. A nonzero result permits submission.

Only after payload processing returns nonzero does the function read the container’s offset-4 field. It invokes F-754616bec4de with that field value and the retained record reference.

A zero submission result enters cleanup failure. A nonzero result is followed by a 32-bit write of the key to the record’s offset-0 field, then return 1.

The key write occurs **after submission**, not before it. The function does not establish what value submission observes in that field. It also does not reread the container reference from the caller’s slot before submission.

### Cleanup failure

The cleanup path is used for:

- Container creation returning zero.
- Container initialization returning zero.
- Record creation returning zero.
- Payload processing returning zero.
- Submission returning zero.

Its explicit ordering is:

1. Invoke F-4fc89ec41a6d with **0x22, 0x7e, 0x41, 0, 0**.
2. After reporting returns, read the **record-descriptor global**.
3. Invoke F-ac669dc5909f with the retained record reference and that newly read descriptor value.
4. After record cleanup returns, read the **container-descriptor global**.
5. Invoke F-ac669dc5909f with the retained container reference and that newly read descriptor value.
6. After container cleanup returns, write zero into the caller’s slot.
7. Return 0.

Both cleanup calls occur even when their object reference is zero. In particular, the record-descriptor global is still read and record cleanup is still invoked when failure occurred before record creation.

These descriptor reads are not snapshots from creation. Reporting can change the descriptor supplied to record cleanup. Record cleanup can change the descriptor supplied to container cleanup. If reporting changes the container descriptor and record cleanup leaves it unchanged, container cleanup receives that changed value.

Cleanup also applies to an existing caller-supplied container. There is no explicit ownership distinction between an existing container and one created during this invocation.

## Side effects

### Direct memory effects and ordering

The function explicitly performs three kinds of writes:

- Publishing a newly initialized container through the caller’s slot.
- Writing the key into the record after successful submission.
- Clearing the caller’s slot after both cleanup calls.

It directly reads the slot, selected object fields, and the descriptor globals at the points described above. Payload access, allocation, collection mutation, reporting, and resource release occur through dependencies rather than direct payload operations in this function.

Descriptor reads have the following call-relative ordering:

| Read | Established position |
|---|---|
| Container descriptor for creation | After observing an empty slot, before container creation. |
| Record descriptor for creation | After a zero eligibility result, before record creation. |
| Record descriptor for cleanup | After failure reporting returns, before record cleanup. |
| Container descriptor for cleanup | After record cleanup returns, before container cleanup. |

The function provides no isolation from dependency effects. A dependency may change globals, referenced objects, or aliased caller storage. Explicit later writes still occur in the stated order if execution continues normally.

### Ownership and failure state

F-e12621595ccc supplies object references, and F-ac669dc5909f receives references during cleanup. This establishes a creation/cleanup protocol, not proof of heap allocation, deallocation, or ownership transfer.

No explicit cleanup follows successful submission. Whether submission retains, copies, shares, or takes ownership of the record is unknown.

There is no separate visible action to remove a partially submitted record, restore an earlier slot value, or reverse payload processing. Cleanup may perform additional work internally, but that is not established.

Submission must leave the record suitable for the subsequent key write for that access to be valid. The available evidence does not establish that dependency guarantee.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume reached memory accesses are valid and dependencies return normally. State assertions exclude independent dependency writes unless explicitly included.

1. **Null slot address.**  
   General reporting receives 0x22 and 0x7e; the function returns 0 without explicitly dereferencing the slot or reading either descriptor global.

2. **Zero key or payload reference.**  
   General rejection occurs without an explicit read of the slot contents, even if the slot address itself is nonzero.

3. **Explicit length 65.**  
   The signed limit rejects it before the slot is read. Neither creation nor cleanup is explicitly invoked.

4. **Explicit length 64 with successful dependencies.**  
   The payload operation receives 64. Submission precedes the key write, and the function returns 1.

5. **Explicit length −2.**  
   Neither length-calculation call occurs. If intervening operations succeed, payload processing receives −2. This does not establish that processing it is safe.

6. **New container followed by nonzero eligibility result.**  
   Container creation uses the container-descriptor global’s value at creation. Successful initialization is followed by publication. General rejection then returns 0 without explicit cleanup or slot clearing.

7. **Container creation returns zero.**  
   Failure reporting runs first. The record-descriptor global is then read for cleanup of a zero record reference. After that call returns, the container-descriptor global is read for cleanup of a zero container reference. The slot is cleared afterward.

8. **Container initialization returns zero.**  
   The function has not published the created container. Cleanup receives a zero record reference and the created container reference, using the descriptor values freshly read at the respective cleanup points.

9. **Payload failure with an existing container.**  
   Reporting precedes record cleanup, which precedes container cleanup. The existing container reference is passed to cleanup, and the caller’s slot is then cleared.

10. **Reporting changes the record descriptor.**  
    Suppose record creation used descriptor value A, and failure reporting changes the record-descriptor global to B. Record cleanup receives B, not the creation-time value A.

11. **Record cleanup changes the container descriptor.**  
    Suppose container creation used descriptor value C, but record cleanup changes the container-descriptor global to D. Container cleanup receives D. This also applies when the retained container was caller-supplied and no container creation occurred.

12. **Two-stage length calculation.**  
    With requested length −1, a first result of −1 permits the second calculation after record creation. If that result is 100 and other operations succeed, payload processing receives 100 without another upper-bound check.

13. **Submission observes the record before key assignment.**  
    This function has not written the supplied key when F-754616bec4de runs. On its nonzero return, the function writes the key and returns 1.

Inferred intent is limited to adding a keyed payload record to a container. It does not override the signed upper-bound check, fresh cleanup descriptor reads, cleanup of existing containers, or submission-before-key-write ordering.
