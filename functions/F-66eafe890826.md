# F-66eafe890826

## Purpose

F-66eafe890826 processes a palette-indexed image description, converts indices into 16-bit pixel values, and submits one or more image levels through F-4ff785db4cda.

Ten supported format selectors determine the index width, declared palette size, palette-construction mode, and conversion dependency. Level selector zero requests level zero alone. An ordinarily accepted negative selector requests consecutive levels beginning at zero, with dimensions reduced between submissions.

The contract distinguishes:

- **Established static evidence:** control flow, memory accesses, argument values, arithmetic widths, and dependency-call order visible in the supplied representation.
- **Inferred intent:** descriptions such as palette construction, scratch allocation, image submission, and resource release.
- **documented_only:** behavior not established without dependency implementations, external constant contents, or runtime evidence.

No runtime tests have been performed.

### Storage layout and access requirements

The declared-size calculation accounts for a palette followed by indexed image data:

- Either 16 or 256 palette entries.
- Two, three, or four declared bytes per palette entry.
- An initial-level image contribution with each nominal row rounded upward to whole bytes.

This accounting does not fully establish the consumed layout. F-e22048c42378 receives a mutable local input cursor and determines the cursor position used for subsequent decoding. Its actual reads and cursor advancement are unknown.

After palette construction, this function addresses palette entries at four-byte intervals, irrespective of their declared input size. An expanded palette representation is inferred, not established.

**Context readability is path-dependent.** The function’s first direct context-memory read is a 32-bit read at byte offset `0x16E4`, reached only after non-null input, successful preceding validation, and a nonzero palette-construction result. Successful scratch processing reaches a second read of the same field during cleanup.

Earlier validation failures, the matching-size null-input return, and the palette-construction failure path perform no direct context dereference. Some paths nevertheless pass the context to dependencies; any readability or validity requirements those dependencies impose are **documented_only**.

## Behavior

### Validation and error selection

The function first reads an externally stored default error value, even before checking the target.

A target other than `0x0DE1` causes a call to F-375c8199e7c2 with the context and literal error `0x0500`, followed by return. No dimension checks, palette construction, scratch allocation, or submission occur.

For the accepted target, ordinary non-overflowing level arithmetic admits selectors **−12 through zero inclusive**. Positive selectors and ordinary negative selectors below −12 fail validation. The minimum signed 32-bit value is exceptional and is addressed under **Uncertainties**.

Border must be zero on ordinary accepted paths. Subsequent dimension validation proceeds in this order:

1. Reject if either initial dimension is negative.
2. Call F-0a4d875268a5 with width and reject a zero result.
3. Call F-0a4d875268a5 with height and reject a zero result.

The height dependency is not called if width validation returns zero. Neither dimension dependency is called after an earlier target, level, border, or negative-dimension rejection.

The function does not itself establish whether zero, non-power-of-two dimensions, or large positive dimensions are accepted. Those decisions depend on F-0a4d875268a5.

Validation failures other than the wrong-target case report the initially loaded default error. The value is retained locally; later dependency changes to its external storage do not replace that selected value.

### Declared-size comparison and null input

For ordinary non-overflowing arithmetic, the expected count is:

**palette entries × declared bytes per entry + initial height × ceiling(initial width × index width / 8).**

The calculation uses 32-bit intermediates. It forms the width-times-index-width product, adds seven, performs signed division by eight with truncation toward zero, multiplies by height, and adds the palette contribution. Overflow is not checked. The mathematical ceiling expression therefore applies only within the appropriate nonnegative, non-overflowing domain.

A count mismatch reports the default error, regardless of whether input is null.

If the count matches and input is null, the function returns immediately. This path performs:

- No palette construction.
- No direct context-memory read.
- No scratch allocation.
- No submission.
- No error-reporting call by this function.

The comparison accounts for the initial dimensions only. It does not add the payload sizes of later requested levels.

### Palette construction and scratch allocation

For matching-size, non-null input, the function initializes a local cursor to the input address and calls F-e22048c42378 with:

- The address of that cursor.
- The selected palette mode.
- The selected palette-entry count.

Immediately after that call, it reads a different externally stored error value, used for palette or scratch failure.

If palette construction returns zero, that newly read error is reported. There is no direct context dereference, scratch request, or palette cleanup call on this path.

For a nonzero palette result, the function reads the 32-bit field at context offset `0x16E4` and passes its value to F-2dbba9b8dbac together with a scratch-size request of:

**initial height × initial width × 2 bytes.**

The size calculation is unchecked 32-bit arithmetic.

If scratch allocation returns null, F-58ba61416cc9 is called with the palette result before the cached allocation-stage error is reported. There is no second direct context-field read on this failure path.

### Level range and dimensions

After nonzero palette and scratch results:

- Selector zero produces one submission at level zero.
- An ordinarily accepted selector −N produces N submissions, at levels zero through N−1.

Each level starts writing at the beginning of the same scratch allocation. Decoding continues from the position left by the preceding level.

After each submission, width and height are independently reduced:

- A dimension greater than one is shifted right by one, equivalent here to integer halving.
- One remains one.
- Zero remains zero if dimension validation allowed it.

Thus dimensions stop shrinking at one rather than ending the level sequence. The requested level count controls termination.

### Pixel accesses and conversion

Within each level, ordinary non-overflowing positive dimensions produce width × height consecutive 16-bit scratch elements. The represented pixel loop uses a 32-bit countdown tested for nonzero, not a positivity check. Overflowed pixel counts are not validated.

For an eight-bit index, the observable order is:

1. Read one unsigned input byte.
2. Advance the local input cursor by one byte.
3. Call the selected converter with the palette address plus four times that index.
4. Store the resulting 16-bit value at the current scratch destination.
5. Advance the destination by two bytes.

The direct byte index is necessarily between 0 and 255.

For four-bit formats, a decoding state is initialized once before the first level. Its established components are the post-palette cursor and a zero-valued one-byte state. Each pixel then has this order:

1. Obtain an index from F-26c15dc32d74 using that state.
2. Call the selected converter with the palette address plus four times the returned index.
3. Store the resulting 16-bit value.
4. Call F-86eab0b37f0b with the decoding state.
5. Advance the scratch destination by two bytes.

No local range check constrains the four-bit dependency’s result. Its name and role do not prove a 0–15 range.

The decoding state persists across rows and levels. This function supplies no explicit row-padding skip, row restart, or level restart. In particular, the row-rounded size calculation does not prove row-aligned four-bit consumption.

### Ordered submission-value reads

Each converter family selects its own pair of external 32-bit submission-value locations.

**On every pixel-loop condition evaluation, the function first reads the value later passed as submission argument 9, then reads the value later passed as submission arguments 4 and 8.** This ordering holds for both index widths and both converter families.

Both reads occur even when the condition terminates the loop. Consequently:

- The submission uses the pair read by the final, terminating evaluation.
- For a nonempty level, those final reads occur after the last pixel’s converter call and, in the four-bit path, after its state-advance call.
- A zero-pixel level still performs both reads, in argument-9-before-arguments-4-and-8 order, before submission.
- Earlier condition evaluations also perform the reads; they are not merely initialization or one-time submission reads.

The locations are not assumed immutable. The two values are ordered reads, not an established atomic snapshot.

## Acceptance examples

These are conditional static expectations, not executed tests.

1. **Wrong target without a direct context read.** A target other than `0x0DE1` reports `0x0500` and returns. The function does not dereference context directly. Whether the reporting dependency requires a valid context remains unknown.

2. **Positive level selector.** With the accepted target, level selector 1 is rejected before dimension dependencies run.

3. **Matching null input.** Assume dimensions 2 × 2 are accepted, border is zero, level is zero, and format is `0x8B90`. The required count is 48 palette bytes plus two index bytes, totaling 50. Null input with count 50 returns without reporting, palette construction, allocation, submission, or direct context-memory access.

4. **Mismatched null input.** Under the same assumptions, count 49 reports the default error. Null input does not bypass validation or the size comparison.

5. **Eight-bit single level.** For accepted dimensions 2 × 2 and format `0x8B96`, the count is 1,028 bytes. Successful construction and allocation lead to four direct index-byte reads, four 16-bit stores, one level-zero submission, and cleanup. There are five pixel-condition evaluations, each reading the argument-9 global before the arguments-4-and-8 global.

6. **Two levels.** Selector −2 with accepted initial dimensions 4 × 2 produces levels zero and one at 4 × 2 and 2 × 1. Eight indices and then two indices are decoded without resetting the input position. The size comparison still covers only the initial level.

7. **Palette failure.** A zero palette result causes the allocation-stage error to be reported without scratch allocation, palette cleanup, or direct context dereference.

8. **Scratch failure.** After a nonzero palette result, the context field is read once for allocation. A null scratch result causes palette cleanup followed by error reporting, without the successful-cleanup context reread.

9. **Zero-pixel level.** If dimension validation accepts a zero dimension and scratch allocation returns nonnull for the resulting zero-byte request, the level performs no pixel stores. It nevertheless reads the argument-9 submission value first, reads the arguments-4-and-8 value second, and submits the level.

10. **Odd-width four-bit rows.** If dimensions 1 × 2 are accepted, size accounting reserves two image bytes. Conversion requests two indices from continuous decoding state. Actual nibble order and byte consumption remain dependency-defined; no explicit row alignment is supplied.
