# F-ea973540dc32

## Purpose

F-ea973540dc32 obtains a new storage block and updates a caller-supplied state object through one of three paths:

- Initialize state when a dependency reports a nonzero condition.
- Extend the trailing position within the existing pointer table.
- Replace the pointer table, copy its active entries, and establish updated leading and trailing positions.

The routine’s structure is consistent with a segmented container whose positions are four-word records and whose table contains addresses of storage blocks. That interpretation is **inferred intent**, not an established type or ownership contract. The directly established behavior consists of 32-bit reads and writes, dependency calls, table-entry copying, and a 64-bit return assembled from two words of temporary state.

No execution evidence is available. The requirements below describe the supplied static representation, conditional on dependencies returning normally and referenced memory being accessible.

## Interface

### Inputs

The routine receives four arguments:

1. **State address:** an address of mutable storage accessed as 32-bit words.
2. **Second seed word:** a 32-bit value.
3. **Third seed word:** a 32-bit value.
4. **Fourth seed word:** a 32-bit value.

The second through fourth arguments are initially placed into temporary storage. They are not directly interpreted as sizes, flags, or addresses by this routine.

The first argument has two distinct uses:

- It remains the address through which the routine accesses the state object.
- Its 32-bit address value becomes the first word of a temporary four-word record passed to F-3d8e7dd29be8.

Changing the first temporary word does not change the state-object address used by the routine.

### State layout

The routine accesses the following fields relative to the state address:

| Byte offset | Width | Established use |
|---|---:|---|
| 0 | 32 bits | First word of the leading record |
| 4 | 32 bits | Second word of the leading record |
| 8 | 32 bits | Third word of the leading record |
| 12 | 32 bits | Fourth word of the leading record; also used as a table-entry address on the replacement path |
| 16 | 32 bits | First word of the trailing record |
| 20 | 32 bits | Second word of the trailing record |
| 24 | 32 bits | Third word of the trailing record |
| 28 | 32 bits | Fourth word of the trailing record; also used as the current trailing table-entry address |
| 32 | 32 bits | No explicit access by this routine |
| 36 | 32 bits | Table-base address |
| 40 | 32 bits | Table extent or capacity word |

Thus, the state storage must cover at least 44 bytes. Dependencies may impose additional layout requirements.

The leading and trailing “records” are descriptive groupings of four consecutive words. Their actual type and individual word meanings are unknown.

Table entries are four bytes wide. Address-valued fields are handled as 32-bit quantities in the supplied representation.

### Temporary record

Before any dependency call, the routine creates a four-word temporary record containing, in order:

1. The state address represented as a 32-bit word.
2. The second seed word.
3. The third seed word.
4. The fourth seed word.

F-3d8e7dd29be8 receives the address of this record. The routine subsequently reads its words to update state and form its return value. The dependency’s actual writes are not supplied.

### Output

The return is a 64-bit bit pattern:

- Bits 31–0 contain the final first temporary word.
- Bits 63–32 contain the final second temporary word.

This is concatenation, not addition or sign extension. The routine itself does not establish that the result represents a pointer, status, or object.

There is no explicit failure return, null check, rollback, or exception handler.

## Behavior

### Arithmetic conventions and limits

Sizes, table entries, address calculations, and state words are represented with 32-bit quantities. Multiplication, addition, and address formation therefore require attention to 32-bit overflow and wraparound.

Logical right shifts are used where values are explicitly treated as unsigned. The replacement path also contains a signed right shift of an address difference.

The static representation does not establish a portable language-level meaning for every overflowing signed expression. Valid operation should therefore require sizes and address differences to remain within representable, accessible ranges. Where this contract describes wrapped arithmetic, it identifies the represented 32-bit calculation rather than promising safe allocation or access after overflow.

No alignment, overflow, bounds, or consistency validation is present.

### Common prefix

All three paths begin with this observable dependency order:

1. Call F-5d8a0091da0c without arguments.
2. Shift its 32-bit result left by two bits and pass that value, followed by zero, to F-871e64ddc6de.
3. Retain the 32-bit result of F-871e64ddc6de as the **new block address**.
4. Call F-be518f1dc9cf with the state address.
5. Select the initialization path if that result is nonzero; otherwise inspect the existing trailing position.

The new block is obtained before the predicate is evaluated. The routine does not test whether the returned block address is zero or otherwise valid.

The predicate’s return is tested only for zero versus nonzero. Its other behavior, including possible state or global changes, is unknown. State reads after this call use the state then present, not necessarily its entry-time contents.

### Initialization path

When F-be518f1dc9cf returns nonzero:

1. Call F-5d8a0091da0c again.
2. Store its result at state offset 40.
3. Call F-871e64ddc6de with that result shifted left by two bits and a second argument of zero.
4. Store the returned address at state offset 36.
5. Read the capacity word at offset 40 as unsigned, divide it by two using a logical right shift, and write the new block address into that table slot.
6. Call F-5d8a0091da0c a third time.
7. Call F-3d8e7dd29be8 with:
   - The temporary-record address.
   - The new block address plus four times the unsigned half of the third provider result.
   - The current table-base address plus four times the unsigned half of the current capacity word.
8. Copy the temporary record, word by word in increasing offset order, into state offsets 0 through 12.
9. Copy the leading record into the trailing record, again in increasing word order.
10. Return the concatenation of the first two temporary words.

The three F-5d8a0091da0c results are independent observations. Equality or stability between them is not established.

The table slot written before the third provider call and the table-slot address passed afterward are calculated at different times. If an intervening dependency changes relevant state, these addresses need not agree.

The trailing record is copied from state, not directly from the temporary record. Under ordinary nonoverlapping storage, both records receive the same four words. Unusual aliasing can make the sequential reads and writes significant.

### Extension within the existing table

When the predicate returns zero, the routine reads the trailing table-entry address from state offset 28.

It compares that address with:

**table base + four times capacity − four**

If the values differ, the routine takes the extension path. This is an inequality test, not a bounds check: a position outside the table can also satisfy it.

The extension path:

1. Writes the previously read trailing address plus four to state offset 28.
2. Writes the new block address to memory at that same incremented address.
3. Calls F-3d8e7dd29be8 with:
   - The temporary-record address.
   - The new block address, without a midpoint adjustment.
   - The current value read from state offset 28.
4. Copies the temporary record into the trailing record at offsets 16 through 28, in increasing word order.
5. Returns the concatenation of the first two temporary words.

There are no explicit writes to the leading record, table base, or capacity on this path. Dependencies can still affect them.

The intermediate update of offset 28 is observable before the helper call and before the final four-word trailing-record update.

### Table-replacement path

When the trailing address equals the calculated last table-entry address, the routine replaces the table.

Let:

- **D** be the signed 32-bit difference between the previously read trailing address and the current leading-record fourth word, shifted right by two.
- **N** be the 32-bit value D + 1.
- **O** be `(2 × N)` with its lowest two bits cleared, retaining 32-bit arithmetic.

For ordinary valid table positions, D is the number of entry intervals between leading and trailing positions, and N is the number of active entries. This interpretation requires consistent, aligned addresses and no arithmetic overflow.

The observable sequence is:

1. Call F-871e64ddc6de with an allocation-size argument of eight times N and a second argument of zero. Retain its result as the replacement table address.
2. After that call, read the trailing address again.
3. Copy consecutive four-byte entries:
   - Source begins at the then-current leading-record fourth word.
   - Destination begins at replacement table address plus O.
   - Source advances by four bytes per entry.
   - Copying stops when the source reaches the reread trailing address plus four.
4. Call F-ff1bdc376dcd with the current table base, current capacity, and zero.
5. Store the replacement table address at state offset 36.
6. Write the new block address at replacement-table offset:

   **4 × [D + floor((N masked to 31 bits) / 2)] + 4**

7. Call F-3d8e7dd29be8 with:
   - The temporary-record address.
   - The current first word of the leading record.
   - The current table-base address plus O.
8. Copy the temporary record into the leading record.
9. Call F-3d8e7dd29be8 again with:
   - The same temporary-record address, without resetting its contents.
   - The new block address.
   - The current table-base address plus O plus four times D plus four.
10. Copy the temporary record into the trailing record.
11. Store twice N at state offset 40.
12. Return the concatenation of the first two temporary words.

The copy loop terminates by address equality, not by a separate bounded entry count. Misaligned or inconsistent endpoints can prevent termination or cause invalid memory accesses.

D and N are calculated before the replacement-storage request, but the copy endpoints are obtained afterward. A dependency-induced state change can therefore make the copied extent disagree with the allocation size and later positioning calculations.

The capacity update occurs last. Both record-construction calls and their state writes occur while offset 40 still contains its prior value, unless a dependency changes it.

For ordinary nonnegative N without overflow, O equals four times floor(N / 2). The copied entries are therefore positioned near the replacement table’s middle, and the new block entry follows them. This simplification does not establish correctness for arbitrary 32-bit inputs.

## Side effects

### Direct memory changes

Depending on the path, the routine explicitly changes:

- The leading record.
- The trailing record.
- The table-base field.
- The capacity field.
- One newly added table entry.
- On replacement, a consecutive sequence of copied table entries.

There is no explicit write to state offset 32.

Writes are not transactional. Partially updated state is visible to dependencies called between writes. A failure after an intermediate write has no local rollback.

### Allocation and lifetime

F-871e64ddc6de is used in a storage-request role, but its implementation is unavailable. The routine uses returned values directly as addresses.

F-ff1bdc376dcd is called on the replacement path with the old table base and extent. This suggests retirement or release of that table, but actual ownership transfer, release semantics, and the unit of its second argument are unknown.

The routine does not explicitly release:

- The newly obtained block.
- The replacement table.
- Blocks referenced by copied entries.

No broader ownership conclusion follows. In particular, dependencies must not be assumed to preserve memory, own it, or release it.

### Indirect effects

Dependencies may read or modify state, globals, or reachable memory. Their effects are not constrained by the supplied body.

The temporary record is passed by address. Whether a dependency retains that address is unknown; safe use would require it not to outlive the temporary storage.

There is no synchronization or explicit concurrency protocol.

## Acceptance examples

These examples are conditional static acceptance cases, not executed tests. Unless stated otherwise, assume valid accessible storage, no unexpected aliasing, no arithmetic overflow, dependencies returning normally, and no dependency mutation beyond explicitly stipulated temporary-record writes.

### Initialization with distinct provider results

Suppose the three provider results are 8, 6, and 10, and the predicate returns nonzero.

Expected behavior:

- The first storage request receives 32 and zero.
- Capacity becomes 6.
- The second storage request receives 24 and zero.
- The new block address is written at table byte offset 12.
- The record helper receives the new block address plus 20, and the table address plus 12.
- If the helper leaves the temporary record as four specified words, both state records receive those words.
- The return contains the first word in its low half and the second word in its high half.

This case distinguishes the separate provider calls.

### Extension with one available trailing slot

Suppose capacity is 8 and the trailing table-entry address is table base plus 20.

The calculated last slot is table base plus 28, so the extension path is selected.

Expected behavior:

- Offset 28 is first changed to table base plus 24.
- The new block address is written at that slot.
- The helper receives the new block address and that slot address.
- The helper’s resulting temporary record replaces the trailing record.
- The routine performs no explicit leading-record, table-base, or capacity update.

### Replacement with three active entries

Suppose the leading table-entry address is table base, the trailing address is table base plus 8, and capacity is 3.

Then D is 2, N is 3, and O is 4.

Expected behavior:

- The replacement-storage request size is 24.
- Three old entries are copied to replacement byte offsets 4, 8, and 12.
- F-ff1bdc376dcd is called with the old base, 3, and zero.
- The new block address is written at replacement byte offset 16.
- The leading-record helper receives a table position at replacement offset 4.
- The trailing-record helper receives a table position at replacement offset 16.
- Capacity becomes 6 only after both record updates.

### Return assembly

If the final first two temporary words are hexadecimal 89ABCDEF and 01234567, the return bit pattern is hexadecimal 0123456789ABCDEF, regardless of signed interpretations of either word.

### Out-of-range trailing position

If the trailing address is beyond the table’s last slot but is not equal to it, the routine still selects the extension path. Rejection or repair of that state is not established behavior.
