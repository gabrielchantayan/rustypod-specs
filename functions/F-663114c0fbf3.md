# F-663114c0fbf3

## Purpose

F-663114c0fbf3 selects a record through a **table referenced by the context**, stores a value reread from the selected table slot into the context, and returns a 32-bit status. The stored table pointer does not establish ownership of the table or its records.

Two selection modes are established:

- **Explicit-key mode:** search forward for the first record whose key equals the requested key.
- **Distinguished mode:** search backward for records whose keys equal a separate global filter. Select the first preferred subtype combination encountered; if none is found, select the lowest-index matching record.

These index-based rules assume stable inputs and valid, nonwrapping table extents. On success, the selected slot is read again before its value is stored. Consequently, the stored value need not identify the record whose fields were checked if the slot changes between accesses.

Application-level meanings for the keys, subtypes, globals, and status values are not established.

## Behavior

### Entry and mode decision

A null context returns `0x23` before either global input or any context field is read. No destination write occurs.

For a non-null context, the first distinguished-selector read determines the mode:

- A requested key unequal to that value selects explicit-key mode.
- An equal requested key selects distinguished mode.

The record filter does not participate in this decision.

### Explicit-key mode

The table address is read from the context. A null table returns `0x26` without reading the count or writing the destination.

For a non-null table, the signed 32-bit count is read and used to form an endpoint displaced from the table base by that many 4-byte slots. The count is not visibly reread during traversal.

The search begins at the base and proceeds forward. Before accessing each candidate slot, the function checks whether the current position has reached or passed the endpoint. Reaching that boundary returns `6`.

For an admitted candidate, the table slot supplies a record address, and the record’s 32-bit key is compared with the requested key. A mismatch advances the current position by four bytes. A match selects that slot immediately.

Selection causes a second read of the matching table slot. Its then-current 32-bit value is written to context offset `+0x5c`, and the function returns zero. The record associated with this second value is not checked again.

Under stable inputs and an ordinary valid extent:

- The lowest-index matching entry wins.
- Duplicate matching keys do not cause later entries to be considered.
- No subtype field is read.
- A zero count returns `6` without reading any table slot or record.
- Exhaustion performs no destination write.

### Distinguished mode

After the mode has been chosen, the distinguished selector is read a second time, before the table address is read.

The second value is associated with assertion-related state whose only possible use lies behind a null-context condition. The initial null check has already excluded that condition, and the context argument is not reassigned. Therefore, this second value does not reconsider the mode, affect traversal, or cause the diagnostic dependency to run.

A null table returns `0x26`. This path includes the additional selector read, but does not read the count or write the destination.

For a non-null table, the function reads the signed 32-bit count, forms the endpoint using a four-byte slot stride, and begins with no remembered fallback. Traversal moves backward from that endpoint.

Each candidate position is decremented by four bytes **before** the below-base stopping test. For a valid positive count, the first candidate is the highest-index slot.

For each admitted candidate, the table slot is read before the key comparison. That comparison reads both the record key and the global record filter. **Their relative read order is not established.** Neither operand may be assigned a guaranteed earlier position than the other.

A mismatching comparison skips the record without reading either subtype.

After a matching comparison, the signed primary subtype is read, and the candidate slot becomes the remembered fallback. Preference is then determined as follows:

- Primary subtype `3` causes a signed secondary read. Secondary value `10` selects the candidate immediately.
- Primary subtype `0` causes an unsigned secondary read. Secondary value `4` selects the candidate immediately.
- Any other primary subtype requires no secondary read and does not immediately select the candidate.
- A primary value of `3` or `0` with the wrong secondary value remains a fallback candidate, but traversal continues.

The preferred pairs are therefore `(3, 10)` and `(0, 4)`. Neither pair has priority over the other. Traversal order determines which preferred candidate wins.

If traversal passes below the table base without finding a preferred candidate, the remembered fallback is selected. If there is no remembered fallback, the result is `0x26`.

Under stable inputs and valid traversal:

- The highest-index filter match with either preferred pair wins.
- If no matching record is preferred, the lowest-index filter match wins, because every later-encountered match replaces the fallback.
- If no record matches the filter, the function returns `0x26`.

Both preferred and fallback selection reread the chosen table slot. That read supplies the 32-bit destination value, followed by a zero return. Fields belonging to the final value are not revalidated.

For a zero count, the backward decrement still forms a position one slot before the base. If that calculation does not wrap and the below-base comparison behaves ordinarily, the result is `0x26` without any slot or record access.

### Access-order boundaries

The established ordering constraints are limited to what the supplied representation supports:

- The entry null check precedes global and context-field reads.
- The mode-deciding selector read precedes mode-specific traversal.
- Distinguished mode’s additional selector read precedes its table-address read.
- A null table prevents the count read in either mode.
- Each candidate slot read precedes accesses through the record address it supplies.
- In distinguished mode, the key and filter are both read for the comparison, without an established order between them.
- Subtype accesses follow a matching comparison.
- The primary subtype determines whether a secondary access occurs.
- The selected slot is reread before the destination write.

The record filter is accessed during candidate comparisons rather than established as one scan-wide snapshot. Nothing here guarantees stable slot contents or stable global values across accesses.

## Acceptance examples

These are conditional static criteria, not executed tests. Unless stated otherwise, assume stable inputs, valid accessible storage, a writable destination, nonnegative counts, and nonwrapping address calculations.

1. **Null context.** Any request with a null context returns `0x23`. Neither global input nor any context field is read, and no destination write occurs.

2. **Explicit-mode null table.** A request unequal to the distinguished selector with a null table returns `0x26`. The count is not read.

3. **Distinguished-mode null table.** An equal request selects distinguished mode. The selector is read again before the null table address is read; the result is `0x26`, without a count read. A different second selector value does not change modes.

4. **Empty explicit table.** A non-null table with count zero returns `6`, without reading a slot or record.

5. **Empty distinguished table.** A non-null table with count zero returns `0x26` without reading a slot or record, provided that forming the preceding-slot position does not wrap.

6. **Duplicate explicit matches.** If indices 1 and 4 match the requested key, index 1 wins. Its slot is reread for the destination value. Subtypes are irrelevant.

7. **Explicit miss.** If no record key matches, traversal returns `6` without a destination write.

8. **Competing preferred pairs.** If filter-matching indices 2 and 5 have pairs `(3, 10)` and `(0, 4)`, index 5 wins. The pair at index 2 has no intrinsic priority.

9. **Preferred candidate overrides fallback.** A higher-index nonpreferred match becomes a fallback, but a subsequently encountered lower-index preferred match is selected immediately.

10. **Fallback ordering.** If indices 1, 3, and 6 match the filter and none is preferred, index 1 supplies the final slot value.

11. **Mismatching key.** A distinguished-mode candidate whose key differs from the filter has neither subtype read, even if those stored fields contain a preferred pair.

12. **Unordered comparison operands.** After a candidate slot has been read, the acceptance contract permits either relative order of the record-key and global-filter reads. Subtype reads require a matching comparison; an observer must not require key-before-filter ordering.

13. **Other primary subtype.** A filter match with primary subtype `7` becomes a fallback without a secondary read.

14. **No filter match.** Distinguished traversal returns `0x26` without a destination write.

15. **Changed selected slot.** If permitted mutation replaces the selected slot after field inspection but before its final reread, the destination receives the replacement value. Its associated record fields are not rechecked.
