# F-e3ef981e414f

## Purpose

F-e3ef981e414f conditionally replaces a context’s current target, conditionally invokes dependencies associated with the old and incoming targets, and then dispatches through the context’s current target.

Every invocation first clears one flag bit, including invocations where the incoming target equals the existing target. Equality suppresses the replacement-related dependency calls, but does not suppress the final dispatch.

The supplied static evidence establishes these operations. It does not establish the application-level meaning of the targets, flags, stored dependency value, or final dispatch. Descriptions such as “cleanup,” “acquisition,” and “activation” would imply semantics not demonstrated by the evidence.

## Interface

### Inputs

The function has two inputs:

1. **Context address.** A pointer to storage accessed as consecutive 32-bit integer words.
2. **Incoming target value.** A 32-bit integer used both for comparison with the current target and as an address-bearing value.

The context fields accessed directly are:

| Byte offset | Width | Contract role |
|---|---:|---|
| `0x00` | 32 bits | Current target value |
| `0x08` | 32 bits | Flags word |
| `0x0C` | 32 bits | Stored value supplied to one dependency and potentially replaced with another dependency’s result |

The supplied evidence does not access the word at context offset `0x04` directly. That does not establish that dependencies leave it unchanged.

Target-related accesses use these offsets:

| Byte offset from target | Access | Contract role |
|---|---|---|
| `0x10` | Indirect callable-entry read | Final dispatch destination |
| `0x44` | 32-bit integer read | Condition for dependency invocation; also supplies the first argument to F-43da6b23bd44 |

These are byte offsets, not element indices. In particular, `0x44` means 68 bytes after the target address.

### Output

No explicit result value is returned by F-e3ef981e414f. Results from the final dispatch, if any, are not used by the shown body.

Its externally relevant results are memory changes, dependency invocations, and the final indirect dispatch. Normal return depends on the invoked operations returning normally.

Integer comparisons are exact equality or comparisons with zero. There is no range validation, sign-based branch, counter arithmetic, or size computation. Negative nonzero bit patterns are not rejected before being used as address-bearing values.

## Behavior

### Unconditional flag change

The first operation reads the context’s flags word, clears bit 1, and writes the result back to that word.

Bit numbering here starts at zero. The cleared bit has value `0x00000002`. Every other bit is preserved by this direct operation.

This write occurs before the current target is read for comparison. It is not conditional on target equality, target validity, or the contents of either target.

This is a read-modify-write, not an established atomic operation. Dependencies can subsequently change the flags again, so the final flags value is not unconditionally guaranteed to have bit 1 clear.

### Comparison and unchanged-target path

After the flag write, the function reads the context’s current target and compares it with the incoming target value.

If they are equal:

- Neither target’s field at `0x44` is read by the replacement logic.
- Neither F-5990a26eaaa3 nor F-43da6b23bd44 is invoked directly.
- The current-target field is not directly rewritten.
- The stored field at context offset `0x0C` is not directly rewritten.
- Execution proceeds to final dispatch.

Equality is therefore a replacement short-circuit, not a whole-function no-op.

### Changed-target path: old-target handling

If the target values differ, the function examines the saved old target.

When the old target is zero, no old-target field is read and F-5990a26eaaa3 is skipped.

When the old target is nonzero, the function reads its 32-bit field at offset `0x44`. If that value is zero, F-5990a26eaaa3 is skipped. If it is nonzero, the function reads the context’s stored field at offset `0x0C` and passes that value as the sole explicit argument to F-5990a26eaaa3.

The old target’s field is only a condition for this call. Its value is not the argument.

There is no separate check that the stored argument is nonzero or otherwise valid. A zero stored value is passed when the old-target condition enables the call.

The old-target decision uses the target value already read before the call. The incoming target has not yet been written to the context at the point F-5990a26eaaa3 is invoked. Any broader view that the dependency has of the context depends on aliases and external state.

### Changed-target path: replacement and incoming-target handling

After old-target handling completes normally, the function writes the incoming target value to context offset `0x00`.

It then reads the incoming target’s 32-bit field at offset `0x44`. Unlike the old-target access, this access has no zero-target guard.

If the field is zero:

- F-43da6b23bd44 is not invoked.
- The context’s stored field at offset `0x0C` is not directly changed by this part of the function.

The old stored value is therefore not automatically cleared when an incoming target has a zero field, even if F-5990a26eaaa3 was called earlier.

If the incoming field is nonzero, the function reads that field again and invokes F-43da6b23bd44 with three explicit arguments:

1. The value from the second incoming-field read.
2. Zero.
3. Zero.

The two reads are distinct. The first determines whether the call occurs; the second supplies its first argument. Under stable, ordinary memory they agree. The evidence does not establish volatility, synchronization, or freedom from external modification, so equality of those observations is not a universal guarantee.

On normal return from F-43da6b23bd44, its 32-bit result is written to context offset `0x0C`. There is no result validation or special branch for a zero, negative, or otherwise unusual result.

### Final dispatch

Both the unchanged-target path and the changed-target path reach final dispatch.

The function reads the context’s current target again. It obtains a callable entry at offset `0x10` from that target and transfers control to it with the context address as the sole explicit argument.

This target is not necessarily the incoming target. A dependency may have changed the current-target field, directly through an alias or indirectly through shared state. The final dispatch uses the value present at the final read.

There is no explicit null-target check, callable-entry validation, or fallback destination.

### Observable ordering

The established direct ordering is:

1. Read and rewrite the flags word with bit 1 cleared.
2. Read the current target and decide whether replacement is needed.
3. If replacement is needed, conditionally read the old target’s field.
4. If enabled, read the stored context value and invoke F-5990a26eaaa3.
5. Write the incoming target into the context.
6. Read the incoming target’s field for the call condition.
7. If enabled, reread that field, invoke F-43da6b23bd44, and store its result.
8. Reread the context’s current target, obtain its dispatch entry, and invoke it.

This ordering includes no rollback boundary. A later failure does not undo earlier writes or dependency effects.

## Side effects

The function directly writes only these context fields:

- Flags at `0x08`, on every invocation.
- Current target at `0x00`, only when the initially observed target differs from the incoming value.
- Stored value at `0x0C`, only after a normally returning F-43da6b23bd44 call.

Dependencies and the final dispatch may have additional effects. Their effects are not bounded by this evidence.

No direct allocation, deallocation, reference-count update, or resource ownership transfer is established. In particular:

- Calling F-5990a26eaaa3 does not prove that the supplied stored value is released.
- Receiving a result from F-43da6b23bd44 does not prove that it is newly allocated or owned.
- Skipping a write to the stored field does not prove that its contents remain valid.
- Replacing the current target does not prove that either target’s lifetime is extended.

There is no established locking, atomicity, reentrancy protection, exception handling, or failure recovery. Shared access requires external guarantees not supplied here.

Aliasing is not ruled out by the interface. If context and target storage overlap, earlier writes can affect later target reads. No snapshot of either target structure is created.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, storage is valid, fields remain stable except for described writes, and invoked dependencies return normally.

### Equal targets

Given equal valid current and incoming targets and flags `0x00000007`:

- The direct flag write produces `0x00000005`.
- Neither named dependency is invoked.
- No target field at `0x44` is read by the replacement logic.
- Final dispatch still occurs with the context address.

The final flags value may differ if dispatch changes it.

### Replacement without dependency calls

Given different valid targets, a nonzero old target whose field is zero, and an incoming target whose field is zero:

- Both named dependencies are skipped.
- The incoming target is written into the context.
- The stored field receives no direct write.
- Final dispatch resolves through the current target after replacement.

### Both dependency conditions satisfied

Given different targets, a nonzero old-target field, stored value 37, incoming field 91, and an F-43da6b23bd44 result of 123:

- F-5990a26eaaa3 receives 37 before replacement.
- The incoming target is stored.
- F-43da6b23bd44 receives 91, zero, and zero.
- The stored field becomes 123.
- Final dispatch follows.

This example assumes the dependencies do not alter the relevant observations.

### Zero old target

Given an old target of zero and a different, valid incoming target:

- No old-target dereference occurs.
- F-5990a26eaaa3 is skipped.
- Replacement and incoming-target handling proceed normally.

### Zero incoming target

Given a nonzero old target and incoming value zero, the function can perform the flag write and old-target handling, then stores zero as the current target. It subsequently attempts the incoming-field read without a null check.

No normal error result or rollback is established for that case.

If both targets are zero, the replacement path is skipped, but final dispatch still attempts resolution through zero.

### Dependency changes dispatch target

If F-43da6b23bd44 changes the context’s current target to a third valid target, the function still stores the dependency’s result at context offset `0x0C`. Final dispatch then resolves through that third target, not necessarily through the incoming target.
