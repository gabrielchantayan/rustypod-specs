# F-7e8709581b2b

## Purpose

F-7e8709581b2b conditionally publishes an allocated collection built while enumerating candidates. A sizing dependency supplies a nominal capacity. Each nonzero enumeration result is submitted to a selection dependency; a nonzero selection result requests an append.

The established success condition is **enumeration terminating while the allocated block’s count is nonzero**. Success does not require this invocation to have appended a record. If a selected candidate encounters a count greater than or equal to capacity, the function fails rather than publishing a partial collection.

The apparent intent is to produce a filtered collection of enumeration positions and associated address-sized values. This is **inferred intent**. The function does not explicitly initialize the count, and the visible dependency arguments do not establish a dependency-produced origin for the associated values.

This contract describes static evidence only. Dependency implementations, caller contracts, and runtime observations are unavailable.

## Interface

### Inputs

The visible interface has four inputs in a 32-bit address model.

| Input | Representation | Established role |
|---|---|---|
| Context | Opaque 32-bit value | Passed to sizing, enumeration, and selection. |
| Enumeration descriptor | 32-bit address represented as a pointer to pointer-sized elements | Passed to sizing and enumeration; not directly dereferenced by this function. |
| Selection context | 32-bit address | Passed to selection and initially copied into invocation-local storage. The supplied address is not directly dereferenced by this function. |
| Output destination | 32-bit address of a writable 32-bit slot | Receives the block address on success or zero after failure cleanup returns. Its address is also initially copied into invocation-local storage. |

The function does not validate the output destination. Every normally returning path writes through it, so it must designate writable storage when that write occurs. Requirements imposed by dependencies on the other inputs are **documented_only**.

There is no direct store through the output destination on entry or during the sizing, allocation, enumeration, and selection phases. The explicit output-destination store occurs only at publication or after failure cleanup returns. This ordering does **not** guarantee preservation of the slot’s previous contents: dependencies, external actors, or writes through aliased storage may change those contents earlier. Preservation is conditional on the absence of such intervening writes.

### Return value

The supplied representation constructs a 64-bit result from two 32-bit components. The low component carries the visible status:

| Low component | Signed 32-bit interpretation | Condition |
|---|---:|---|
| `0x00000000` | 0 | Enumeration terminates with a nonzero stored count. |
| `0xFFFFFF94` | −108 | Allocation returns zero. |
| `0xFFFFFFCE` | −50 | Enumeration terminates with count zero, or a requested append encounters count greater than or equal to capacity. |

These are numeric values. No external error names or error-domain membership are established.

The high component depends on the exit path:

| Exit condition | High component |
|---|---|
| Allocation failure | Enumeration descriptor address |
| Enumeration termination, whether successful or empty | Address of invocation-local storage initially holding the output destination address |
| Capacity failure | Address of invocation-local storage initially holding the selection context address |

The high component is not the allocated block address. No usable post-return lifetime is established for the invocation-local addresses. Whether the external calling convention exposes the full constructed 64-bit value, or callers interpret its high component, remains **documented_only**.

### Allocated layout

The sizing result is treated as an unsigned 32-bit capacity. The requested allocation size is:

\[
(8 \times \text{capacity} + 8) \bmod 2^{32}.
\]

The visible layout is:

| Byte offset | Width | Treatment |
|---|---:|---|
| 0 | 32 bits | Capacity, explicitly initialized from the sizing result |
| 4 | 32 bits | Count, read and incremented but not explicitly initialized |
| 8 + 8 × record index | 16 bits | Low 16 bits of the enumeration position |
| 10 + 8 × record index | 16 bits | Not written by the append operation |
| 12 + 8 × record index | 32 bits | Value read from invocation-local storage initially holding the output destination address |

These offsets describe target memory accesses, not a portable serialization. Byte order is not supplied. Address calculations use target-width arithmetic; the layout does not establish that the requested or actual allocation covers every possible computed address.

## Behavior

### Global sampling, sizing, and allocation

The function first retains a represented 32-bit global value for later enumeration calls. Sizing receives a separately obtained value from the same global location.

No dependency call intervenes between these represented global reads. Without intervening mutation, they provide the same value. Their data flow nevertheless does not require equality. Physical load behavior, concurrency rules, and the possibility of an intervening external mutation are not established.

F-0104b49ee457 receives the context, enumeration descriptor, and the global value obtained for sizing. Its result becomes the unsigned 32-bit capacity used to compute the wrapped allocation request.

F-858f5b8d5984 receives that request. A zero result selects allocation failure. A nonzero result becomes the block address, and the function writes the capacity into the first 32-bit header word.

There is no explicit initialization of the second header word or record storage. Any initial count or cleared records must come from an independently established environmental property, not from this function’s visible initialization.

### Enumeration and selection

Enumeration starts at position 1. Before each enumeration call, the function selects the address of the invocation-local storage initially holding the output destination address as the prospective high return component.

F-e155b614573e receives:

- The context.
- The enumeration descriptor.
- The retained initial global value.
- The current position.

A zero result terminates enumeration and is not passed to selection.

For a nonzero enumeration result, the prospective high return component changes to the address of invocation-local storage initially holding the selection context address. F-8934ad4fbcbb then receives:

- The context.
- The nonzero enumeration result.
- The original selection context.
- The literal value 1.

Only zero versus nonzero matters in the selection result. Zero rejects the candidate without appending. Nonzero requests an append subject to the current header values.

Neither dependency’s return value is directly stored as the record payload. The visible dependency argument lists do not pass either invocation-local storage address. The local-address assignments therefore do not establish hidden output arguments or a mechanism by which a dependency supplies the payload.

Every enumeration call receives the retained global sample. The function does not refresh that sample after dependency calls. This does not imply that dependencies preserve the global or other reachable state.

### Append eligibility and writes

For an accepted candidate, the function first reads the unsigned 32-bit count, then compares it against the capacity currently stored in the first header word.

The append is allowed only when count is strictly less than capacity. Equality and overfull states both cause capacity failure. No record is written for the candidate that encounters that failure.

The count read for this comparison also identifies the record slot. For an allowed append, the visible effects occur in this order:

1. Write the low 16 bits of the current position into the record’s position field.
2. Write the 32-bit value from the saved-output-address storage into the record’s payload field.
3. Read the count word again, add one using unsigned 32-bit arithmetic, and write the result back.

Thus the count used for addressing and the count used for incrementing come from separate reads. The increment wraps modulo \(2^{32}\). Without an intervening mutation, the eligibility check prevents that increment from overflowing; with intervening mutation, the separately reread value controls the update.

The two bytes between the position and payload fields receive no write from this append operation. Their contents are not otherwise guaranteed to remain unchanged.

Absent an independently established change to its source storage, the payload equals the original output destination address. It is an address value, not the contents of the caller’s output slot. Changing that slot’s contents alone does not change the saved address.

The function performs no visible sorting, duplicate suppression, or validation of preexisting records. Rejected candidates consume enumeration positions but do not consume record slots.

### Position advancement

After a nonzero enumeration result is processed without capacity failure, the position advances through a signed expression apparently intended to retain a signed 16-bit result in a wider integer. Rejection still advances the position.

Under conventional 32-bit wrapping arithmetic with arithmetic right shift, positions progress from 1 through 32767, then −32768 through −1, then 0, and then 1 again. Stored positions contain only the low 16 bits, so different iterations may eventually have identical stored positions.

This sequence is conditional. The supplied signed expression contains overflow-sensitive arithmetic, and instruction-level overflow and right-shift semantics are not provided. Exact boundary behavior is **documented_only**, not a portable arithmetic guarantee.

There is no visible independent iteration limit or pre-boundary termination check.

### Completion and failure

When enumeration returns zero, the function reads the stored count:

- **Nonzero count:** write the block address through the output destination and return low status zero. Cleanup is not called.
- **Zero count:** select low status `0xFFFFFFCE`, call cleanup with the block address, then clear the output destination if cleanup returns.

A capacity failure also selects `0xFFFFFFCE`, calls cleanup with the block address, and clears the output destination after cleanup returns.

Allocation failure selects `0xFFFFFF94`, calls cleanup with zero, and clears the output destination after cleanup returns. No enumeration or selection occurs on this path.

These output-clearing statements are conditional on cleanup returning normally and the final store being valid. The source establishes no alternative completion guarantee if a dependency does not return or a required memory access cannot complete.

## Side effects

### Memory access and ordering

Direct effects include the represented global reads, capacity initialization, count reads and updates, selected-record writes, and final output-destination store.

The function’s explicit store through the output destination is deferred until publication or post-cleanup clearing. That statement describes this function’s store ordering, not continuous preservation of the slot:

- Dependencies may modify the slot if they can reach it.
- External writes are not ruled out.
- Other stores performed by this function may affect it if storage aliases.
- Only without intervening writes does its previous content persist until the final store.

On failure, cleanup executes before the explicit zero store. Consequently, the function does not promise that cleanup observes the output destination already cleared.

No visible synchronization makes header access, record construction, count update, and publication an atomic or concurrent collection protocol. Behavior under concurrent mutation is not established.

### Ownership and lifetime

On success, the block address is published and is not passed to cleanup. This is consistent with transferring responsibility to the caller, but the caller’s release operation and the block’s lifetime are not established.

On failure, the function invokes F-1137792fba7d with the allocation result. The call is established; actual deallocation is not. In particular, zero acceptance, successful release, and normal return cannot be assumed.

There is no direct release of enumeration results or payload values. Dependencies may perform ownership operations, but their contracts are unavailable.

### Bounds and aliasing

The capacity comparison is insufficient to establish memory safety. Allocation-size arithmetic can wrap, the count is not explicitly initialized, and addressing is not checked against actual allocation extent.

Avoiding wrap in the allocation-size expression requires capacity at most `0x1FFFFFFE`. This bound alone does not establish safety: adequate actual extent, usable alignment, valid header state, and absence of harmful intervening mutations are also required.

No non-aliasing requirement is enforced. If the output destination overlaps the allocated block, earlier header or record stores may change its contents, and the final publication or clearing store may overwrite block contents. Similar interactions with other reachable storage are not excluded.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, they assume valid, non-overlapping storage, normally returning dependencies, and no relevant intervening memory mutations.

### Allocation returns zero

If allocation returns zero, cleanup receives zero before the output destination is cleared. Enumeration and selection are not called. The low result is `0xFFFFFF94`; the high component is the enumeration descriptor address.

### One accepted candidate followed by termination

Suppose capacity is 2, count initially equals zero, position 1 yields a nonzero candidate, selection accepts it, and the next enumeration returns zero.

Record zero receives position 1 and the saved output destination address. The append does not write its intervening two bytes. Count becomes 1, the block is published, and cleanup is not called. The low result is zero; the high component is the address of local storage initially holding the output destination address.

### Rejection before acceptance

Suppose count starts at zero, capacity is sufficient, position 1 is rejected, position 2 is accepted, and enumeration then terminates.

One record is appended with stored position 2. The rejection creates no record but still advances enumeration.

### Immediate empty termination

Suppose allocation succeeds with count zero and the first enumeration returns zero.

Selection is not called. Cleanup receives the block before the explicit output-clearing store. The low result is `0xFFFFFFCE`; no empty collection is published.

### Full or overfull header

Suppose selection accepts a candidate while count equals capacity.

No record is written for that candidate. Cleanup receives the block, followed by output clearing if cleanup returns. The low result is `0xFFFFFFCE`, and the high component identifies the local selection-context storage. A count greater than capacity has the same failure outcome.

### Nonzero initial count without an append

Suppose allocation supplies count 1 and enumeration immediately returns zero.

The function publishes the block successfully without appending or validating an existing record. Success follows from the stored count, not from a guarantee that this invocation created records.

### Dependency changes output contents

Suppose a dependency changes the caller’s output slot before enumeration terminates.

Such a change does not contradict this function’s deferred explicit output store. On success, the function overwrites the slot with the block address. On failure, it overwrites the slot with zero only after cleanup returns. A change to slot contents alone does not change the saved address used as a payload.

### Wrapped allocation requests

Capacity `0x20000000` produces a request for 8 bytes while the capacity header, if writable, is initialized to `0x20000000`.

Capacity `0x1FFFFFFF` produces a request for zero bytes. A nonzero allocation result still leads to an attempted capacity write. There is no special zero-size handling.

These examples establish arithmetic and control flow, not adequate storage or safe appends.

### Distinct global samples

If the two represented global reads observe different values, sizing receives the later sample and every enumeration call receives the earlier retained sample. Whether the execution environment permits that observation is unresolved.
