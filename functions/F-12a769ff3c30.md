# F-12a769ff3c30

## Purpose

F-12a769ff3c30 updates a caller-owned accumulation context using two endpoints whose horizontal coordinates have eight fractional bits.

Its behavior has two distinct modes:

- **Different vertical coordinates:** accumulate signed vertical coverage and a horizontal-position-weighted contribution, splitting the contribution at horizontal cell boundaries.
- **Equal vertical coordinates:** select a context key using the ending horizontal cell and the supplied row, conditionally invoke a state-transition dependency, and conditionally clear the accumulators.

The interpretation as coverage or area accumulation is inferred from the arithmetic. The established behavior is the field access, arithmetic, dependency-call sequence, and state transition described below.

## Interface

The function takes six 32-bit arguments and has no explicit return value:

| Argument | Behavioral role |
|---|---|
| Context | Address of readable and writable context storage. |
| Row | Signed row or grouping key; forwarded unchanged to the boundary-transition dependency. |
| Starting horizontal coordinate | Signed fixed-point coordinate with eight fractional bits. |
| Starting vertical coordinate | Signed integer used in vertical differences and subdivision. |
| Ending horizontal coordinate | Signed fixed-point coordinate with eight fractional bits. |
| Ending vertical coordinate | Signed integer used in vertical differences and subdivision. |

The context has the following observed layout. Offsets are byte offsets from its base; all listed fields occupy four bytes.

| Offset | Observed role |
|---|---|
| `0x0c` | Lower horizontal bound used by equal-vertical selection. |
| `0x10` | Exclusive upper horizontal bound used by equal-vertical selection. |
| `0x14` | Inclusive lower row bound. |
| `0x18` | Exclusive upper row bound. |
| `0x1c` | Weighted accumulator. |
| `0x20` | Vertical accumulator. |
| `0x24` | Selection-state value: this function writes zero for accepted selection and one for rejected selection. |
| `0x28` | Stored horizontal cell key. |
| `0x2c` | Stored row key. |

No ownership transfer, allocation, or direct release is visible. The caller must provide storage supporting the accesses actually reached. Behavior for null, invalid, insufficiently sized, or unsuitable addresses is not established.

Horizontal coordinates are separated into:

- A signed cell index obtained by shifting right eight bits.
- A fractional component obtained by subtracting 256 times that cell index.

For an arithmetic right shift, the fraction lies between 0 and 255, including for negative coordinates. For example, a coordinate of −1 has cell index −1 and fraction 255. The arithmetic-shift interpretation is consistent with the supplied representation; exact target semantics remain a qualification in **Uncertainties**.

## Behavior

### Arithmetic conventions

The visible scalar arithmetic and context fields are 32-bit. The arithmetic dependency returns a 64-bit quantity whose lower and upper halves are subsequently used separately.

The contract below describes ordinary integer arithmetic where intermediate values are representable. Overflow-sensitive cases are not assigned an invented mathematical result. Relevant risks include endpoint subtraction, multiplication by 256, weighted products, accumulator addition, cell-index advancement, and negation of the most negative signed value.

Both horizontal coordinates are split into cell and fractional parts before choosing the vertical-coordinate branch.

### Different vertical coordinates: one horizontal cell

When the vertical coordinates differ but both horizontal coordinates have the same cell index:

1. Compute the signed ending-minus-starting vertical difference.
2. Read and update the weighted accumulator by adding that difference multiplied by the sum of the two horizontal fractions.
3. Read the vertical accumulator and add the same vertical difference.
4. Write the vertical accumulator.

No dependency call is visible on this path. The bounds, selection-state value, and stored keys are not consulted or directly changed.

A negative vertical difference contributes negative increments when the other factors are nonnegative. A zero horizontal displacement is permitted here; no division is performed.

### Different vertical coordinates: crossing horizontal cells

When the horizontal cell indices differ, the function traverses cells in the direction selected by the signed horizontal endpoint difference.

For a positive difference:

- The cell step is +1.
- The first horizontal boundary is at fraction 256.
- The distance to it is 256 minus the starting fraction.

For a negative difference:

- The cell step is −1.
- The first horizontal boundary is at fraction zero.
- The distance to it is the starting fraction.
- The horizontal difference is negated for use as the arithmetic dependency’s divisor.

Under representable arithmetic, that divisor is the positive horizontal span.

#### First partial cell

The function calls F-870c4fcf7295 with:

- The vertical difference multiplied by the distance to the first boundary.
- The positive horizontal span.

It interprets the returned 64-bit quantity as two 32-bit halves. If the complete returned quantity is signed-negative, it decrements the lower half and adds the divisor to the upper half. The adjusted lower half becomes the first vertical increment; the adjusted upper half becomes an error term used for subsequent cells.

This adjustment resembles conversion from truncating division to floor division with a nonnegative remainder. That interpretation requires a dependency contract not supplied here; the half extraction and signed-negative adjustment are directly established.

The function then:

1. Reads and updates the weighted accumulator using the first vertical increment multiplied by the sum of the starting fraction and the selected boundary fraction.
2. Reads and updates the vertical accumulator using that increment.
3. Advances the current cell by the selected step.
4. Calls F-b443dcf6eb72 with the context, the advanced cell, and the row.
5. Advances its local current vertical coordinate by the first increment.

The callback therefore observes the first accumulation writes before being called. The current cell passed to it is the newly entered cell, not the cell whose contribution was just accumulated.

#### Complete intermediate cells

If the advanced cell is not yet the ending cell, a second call to F-870c4fcf7295 prepares a full-cell increment.

Its numerator is 256 times the sum of:

- The ending vertical coordinate minus the locally advanced vertical coordinate.
- The first vertical increment.

Without overflow, this is the original vertical difference multiplied by 256. Its divisor is the same horizontal span.

The returned halves receive the same signed-negative adjustment as the first result. Before the loop, the first error term is reduced by one divisor.

For each intermediate cell:

- Add the adjusted upper half of the second result to the error term.
- Use the adjusted lower half as the cell’s vertical increment, increased by one if the updated error is nonnegative.
- Read and update the weighted accumulator by 256 times that increment.
- Advance the local current vertical coordinate.
- Read and update the vertical accumulator by the increment.
- Advance the current cell.
- If the error was nonnegative, subtract one divisor from it.
- Call F-b443dcf6eb72 with the context, newly entered cell, and row.

The loop ends when the current cell equals the ending cell. The callback is still made for the transition that first reaches that ending cell.

No second arithmetic call is made when the first boundary transition already reaches the ending cell.

#### Final partial cell

After the last boundary callback returns, the remaining vertical difference is accumulated in the ending cell.

The weighted multiplier is:

- The ending fraction when moving right.
- The ending fraction plus 256 when moving left.

The function reads and updates the weighted accumulator with the remaining vertical difference times this multiplier, then reads and updates the vertical accumulator with the remaining vertical difference.

There is no final callback after these writes.

Consequently, an endpoint exactly on a boundary can still cause a callback entering the ending cell, followed by a final contribution whose vertical remainder may be zero. A leftward traversal starting exactly on a boundary can similarly perform a zero first contribution before its first callback.

### Equal vertical coordinates: selection and transition

When the vertical coordinates are equal, the function does not perform coverage accumulation. It uses the ending horizontal cell as the proposed horizontal key. The starting horizontal coordinate does not affect this selection.

A selection is accepted exactly when all three signed comparisons hold:

- The row is at least the lower row bound.
- The row is less than the upper row bound.
- The ending horizontal cell is less than the upper horizontal bound.

These checks are ordered and short-circuited:

1. Read the lower row bound.
2. Only if the row passes it, read the upper row bound.
3. Only if the row is below that upper bound, read the upper horizontal bound.

The lower horizontal bound is not an acceptance condition. For an accepted selection, the function reads it and replaces any proposed cell below it with one less than that bound. Thus all such cells share a lower sentinel key.

For an accepted selection, the function compares the resulting cell with the stored horizontal key. It reads the stored row key for this comparison only if the cell matches. A changed cell or row is treated as a key change.

The proposed selection-state value is zero for accepted selection and one for rejected selection.

F-5f57ab3ca437 is invoked if either:

- The stored selection-state value differs from the proposed value.
- The selection is accepted and its key differs from the stored key.

This call occurs before any accumulator clearing or final key writes.

Accumulator clearing is determined as follows:

| Selection result | Key relationship | Clearing behavior |
|---|---|---|
| Rejected | Any | Clear both accumulators. |
| Accepted | Changed cell or row | Clear both accumulators. |
| Accepted | Same cell and row | Clear if the stored selection-state value read for this decision is nonzero. |

For the accepted, same-key case, that clearing decision is captured before the possible dependency call. The function does not recompute it afterward.

When clearing is required, it writes zero first to the weighted accumulator and then to the vertical accumulator. It then writes, in order:

1. The proposed selection-state value.
2. The selected horizontal key.
3. The supplied row.

For rejection, the selected key remains the original ending cell; lower-bound normalization does not occur.

## Side effects

The directly visible effects are context reads and writes, plus dependency calls.

On the different-vertical path, F-b443dcf6eb72 can run between accumulator updates. Subsequent accumulator updates read the then-current fields; they do not restore saved pre-callback accumulator values. Any callback changes to those fields therefore affect later accumulation.

On the equal-vertical path, F-5f57ab3ca437 runs before the final direct state writes. Its changes to fields subsequently overwritten by this function need not survive. No assumption is made about its other effects.

The supplied body contains no direct allocation, release, I/O, or explicit error reporting. Those effects remain possible inside dependencies. There is no visible transactional rollback.

## Acceptance examples

These are conditional examples derived from static evidence, not observed executions.

1. **Contribution confined to one cell.**  
   Starting and ending horizontal coordinates are 64 and 192; vertical coordinates are 10 and 14. Both coordinates are in cell zero. With initial weighted and vertical accumulators of 7 and 3, the final values are 1031 and 7. No dependency is called.

2. **Rightward boundary crossing.**  
   Horizontal coordinates are 128 and 384; vertical coordinates are zero and eight. If F-870c4fcf7295 supplies quotient four and remainder zero for the first subdivision, the function adds 1536 and four to the weighted and vertical accumulators before calling F-b443dcf6eb72 for cell one. If that callback leaves them unchanged, the final partial cell adds another 512 and four. Total increments are 2048 and eight.

3. **Leftward boundary crossing.**  
   Horizontal coordinates are 384 and 128 with the same vertical endpoints. Under the same quotient/remainder and callback conditions, the first weighted increment is 512, the callback enters cell zero, and the final weighted increment is 1536. The total increments again are 2048 and eight.

4. **Repeated accepted key.**  
   The row and ending cell pass the bounds, normalization produces the stored cell, the stored row matches, and the stored selection state is zero. F-5f57ab3ca437 is not called; accumulators remain unchanged. The state and key fields are still written.

5. **Accepted lower sentinel.**  
   The lower horizontal bound is five and the ending cell is two. If the row and upper-bound checks pass, the stored horizontal key becomes four, not five or two. A comparison against the prior key uses four.

6. **Repeated rejection.**  
   The row equals the exclusive upper row bound, and the stored selection state is already one. No transition call is required solely because the proposed key differs. Both accumulators are nevertheless cleared, and the raw ending cell and row are written.

7. **Callback mutation is retained where not overwritten.**  
   If a boundary callback replaces the weighted accumulator, the following partial-cell update adds to that replacement. It does not add to a saved pre-callback value.
