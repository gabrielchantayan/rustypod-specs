# F-71570dd9e091

## Purpose

The candidate is initially zero. A positive status therefore does not guarantee a nonzero result, nor does it establish that the dependency wrote a candidate.

The apparent intent is to obtain a value through an output parameter while using a separate status to determine whether that value is acceptable. That interpretation is **inferred intent**. The established contract concerns the status condition and returned bits, not application-level success, validity, or error meaning.

## Behavior

### Candidate acceptance

The result depends on two distinct channels: the dependency’s signed status and the candidate contents in the first four bytes of temporary storage.

For a positive status, the result is the candidate present after the dependency returns. For a zero or negative status, the result is zero because the function replaces the candidate with zero before returning.

This rule is not a generic nonzero-status test. Negative nonzero statuses reject the candidate.

The status itself is never selected as the return value. A status of seven permits the candidate; it does not cause a result of seven unless the candidate independently contains that value.

There is no local numerical validation of the candidate. In particular:

- Zero remains an acceptable returned candidate on a positive status.
- A candidate whose highest bit is set is not rejected on that basis.
- No sign check, range check, saturation, scaling, or arithmetic adjustment is applied to the candidate.
- No visible conversion reduces the four-byte candidate to a narrower result.

Consequently, candidate bit patterns are preserved on the positive-status path rather than interpreted according to an established application-level numeric meaning.

### Ordering guarantees

The candidate’s four-byte zero initialization occurs before the dependency is invoked. The dependency therefore receives storage whose candidate portion has been initialized, but whose entire eight-byte extent has not been established as zero-filled.

The dependency’s execution lies between that initialization and the function’s final status-dependent handling. If the returned status is nonpositive, the function’s zero replacement occurs after dependency execution. A candidate written by the dependency cannot survive that replacement on a normally completing rejected-status path.

On the positive-status path, there is no further local candidate write before the result is obtained.

The fixed external operand is supplied for the invocation. Its evaluation order relative to the individual argument expressions is not established. The evidence does not support a more detailed schedule of physical loads, stores, register transfers, or bus transactions.

There is one dependency invocation per normally progressing call. No local retry, polling behavior, or alternate dependency is established.

### Partial updates and the second element

A dependency that leaves the candidate untouched leaves it at its initialized zero value. With a positive status, zero is then returned.

If the dependency makes a valid partial update to the candidate and returns a positive status, the resulting four-byte contents determine the result. Bytes not modified remain attributable to the initial zero contents, provided no other permitted actor changes them. Assigning a numeric value to a particular byte-level modification requires target byte-order information that is not supplied.

The second element is not a direct return source. A write confined to that element does not replace the candidate. The dependency may nevertheless use that element internally; its internal reads and writes are unknown.

No defined initial value is promised for the second element. Whether a particular dependency read of that storage is valid cannot be resolved without the dependency’s interface and execution model.

### Completion and error boundaries

A zero return is not a distinct, reliable error signal. It can result from a rejected status, an accepted zero candidate, or an accepted status with no candidate modification.

The function does not expose the dependency’s status separately. Callers cannot recover that status from the result alone.

All result guarantees are conditional on normal dependency return and otherwise defined execution. If the dependency does not return, no local result is produced. No local handling is established for faults, exceptions, nonlocal transfers, or other abnormal completion.
