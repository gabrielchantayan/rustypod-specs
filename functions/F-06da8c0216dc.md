# F-06da8c0216dc

## Purpose

F-06da8c0216dc conditionally processes a four-record primitive. It performs shared-flag rejection, classifies orientation using the first three records, applies a context-controlled orientation filter, optionally prepares per-record attributes, optionally transforms the primitive into another vertex list, and dispatches the resulting triangle or polygon.

The established behavior is the sequence of reads, arithmetic, dependency calls, and dispatch decisions described below. Interpreting the records as vertices, the flags as clipping information, and the orientation filter as face culling is inferred intent, not an independently established API guarantee.

The function has no explicit return value. Its observable results are dependency calls and any memory changes those dependencies produce.

## Behavior

### 1. Shared-flag rejection

The function reads the flags of A, B, C, and D and computes their bitwise intersection, restricted to the low byte and shifted right by two.

If this value is nonzero, processing stops immediately. Equivalently, any single flag bit among bits 2 through 7 that is set in all four records rejects the primitive.

This exit precedes coordinate reads, context-controlled orientation filtering, attribute preparation, scratch initialization, and all mapped dependency calls.

If processing continues, the function reads the flags again and forms their union, again restricted to bits 2 through 7. This saved union determines whether conditional list processing is invoked later. It is not recomputed after dependencies run.

The relative order of operand reads inside a single compound expression is not established by the supplied representation. The distinction between the first intersection-reading phase and the later union-reading phase is established.

### 2. Orientation classification

Only A, B, and C contribute to orientation. D's coordinates do not contribute.

For this calculation, write the signed coordinate triples as:

- A: \((x_A,y_A,z_A)\)
- B: \((x_B,y_B,z_B)\)
- C: \((x_C,y_C,z_C)\)

The determinant form used is:

\[
\Delta =
z_A(x_B y_C-x_C y_B)
-z_B(x_A y_C-x_C y_A)
+z_C(x_A y_B-x_B y_A).
\]

There are two precision stages.

#### Shifted stage

Each coordinate is first arithmetically shifted right by 12 bits. This preserves the sign and discards the lowest 12 bits; for negative values it is not truncation toward zero.

The determinant of those shifted coordinates is evaluated using signed products and explicit multiword carry and borrow handling. The shifted coordinates fit in signed 20-bit values, and this determinant fits in signed 64-bit arithmetic.

The orientation byte is selected as follows:

- Shifted determinant at most −64: orientation is 1.
- Shifted determinant at least 64: orientation is 0.
- Shifted determinant strictly between −64 and 64: use the full-coordinate stage.

Thus both −64 and 64 belong to the outer classification regions, not the fallback region.

#### Full-coordinate stage

For the narrow shifted-determinant interval, the function recomputes the same determinant form from the original signed 32-bit coordinate bit patterns.

The implementation retains a 64-bit result through explicit low-word arithmetic, high-word contributions, and carry/borrow propagation. A mathematical determinant of three unrestricted signed 32-bit coordinates can exceed 64 bits. Consequently, this stage must be understood as a modulo-\(2^{64}\) determinant whose final bit pattern is interpreted as signed, not as an arbitrary-precision determinant.

The resulting orientation is:

- 1 if the retained signed 64-bit result is negative.
- 0 otherwise, including zero.

A geometrically degenerate primitive is not independently rejected here. A zero determinant produces orientation 0 and remains subject to subsequent filtering.

### 3. Orientation filtering

The function compares the byte at context offset `0x901` with the computed orientation byte. Call the resulting inequality boolean **orientation differs**.

Processing continues if either:

- The byte at `0x8ff` is zero; or
- The boolean “byte at `0x914` equals 1” equals **orientation differs**.

Otherwise, the function returns before attribute preparation and list dispatch.

This comparison does not normalize `0x901` to a boolean. For example, a stored value of 2 differs from either possible computed orientation.

### 4. Optional attribute preparation

The function reads the address at context offset `0xa90`, then the signed 32-bit index at offset `4` in that object.

If the index is negative, the entire attribute-preparation phase is skipped. Processing still proceeds to scratch setup and possible dispatch.

If the index is nonnegative, an attribute selector is determined:

- If the byte at `0x8fd` is zero, the selector is 0 and F-f370660ffa4f is not called.
- Otherwise, the selector is 2 when **orientation differs** is true and the byte at `0x8fe` is nonzero.
- In all other enabled cases, the selector is 1.

When attribute preparation is enabled:

1. F-f370660ffa4f is called for D with the context and selector.
2. The function then reads `0x9ec`.
3. If that byte equals 1, F-f370660ffa4f is called for A, then B, then C, using the same selector.

After those calls, the indexed-attribute phase runs. The byte at `0x9ec` is read again to choose its branch:

- If it equals 1, F-02a35f55d6ef receives source attribute addresses from A, B, and C for the first three calls.
- Otherwise, those first three calls all receive D's selected source attribute address.

In either branch, those three calls have indexed attribute addresses belonging to A, B, and C respectively. A fourth call uses D's selected source attribute address and D's indexed attribute address.

The source address is always based on the selected slot at `0x3c + 0x10 × selector`. The indexed address uses `0x6c + 4 × index`.

The index object is reread between successive calls when constructing the later indexed addresses. The first indexed address is constructed after the earlier preparation calls. The context pointer at `0xa90` is also reloaded for these reads. Therefore, a dependency that changes this context field or the pointed-to index can affect subsequent addresses.

The original nonnegative-index decision is not repeated. A later negative or excessive index is not explicitly rejected.

Address calculations use 32-bit address arithmetic. The evidence does not justify replacing them with unbounded arithmetic or adding overflow rejection.

## Acceptance examples

The following are conditional acceptance cases derived from static evidence, not executed tests.

1. **Shared rejection bit.**  
   If all four flag words contain bit 2, the function returns without coordinate reads or dependency calls. Other flag bits do not override that rejection.

2. **Only irrelevant flag bits.**  
   If no record has bits 2 through 7 set, bits 0, 1, and bits above 7 do not cause F-a6abddefd72e to run.

3. **Distributed relevant flags.**  
   If A alone has bit 2 and B alone has bit 3, with no relevant bit common to all four records, shared rejection does not occur. If orientation filtering permits continuation, F-a6abddefd72e is invoked.

4. **Shifted determinant boundaries.**  
   A shifted determinant of −64 selects orientation 1 directly. A shifted determinant of 64 selects orientation 0 directly. Values −63 and 63 require the full-coordinate calculation.

5. **Zero coordinates.**  
   If all coordinates used in orientation are zero, orientation is 0. If the orientation filter permits continuation, the primitive is not rejected merely for this degeneracy.

6. **Exact filter-byte interpretation.**  
   With filtering enabled and **orientation differs** true, a byte value of 1 at `0x914` permits processing; a value of 2 does not. With filtering disabled, that distinction does not reject the primitive.

7. **Negative initial index.**  
   If the initial signed index is −1, neither attribute dependency is called. Scratch setup and list processing remain reachable.

8. **Selector 2 and shared attribute source.**  
   Given a nonnegative index, nonzero `0x8fd`, true **orientation differs**, nonzero `0x8fe`, and a stable `0x9ec` value other than 1, F-f370660ffa4f is called only for D with selector 2. All four F-02a35f55d6ef calls use D's selector-2 source address.

9. **Untransformed four-record dispatch.**  
   With a zero relevant-flag union and continuation through filtering, the function prepares four records in the orientation-selected order and calls F-86f6806bc39e with count four.

10. **Three-record transformed result.**  
    If F-a6abddefd72e returns three valid entries, each receives one ordered preparation call, followed by F-306b6a90102c. The polygon dispatcher is not called.

11. **Discarded transformed result.**  
    If F-a6abddefd72e returns zero, one, or two, no output-record preparation or final dispatch occurs.
