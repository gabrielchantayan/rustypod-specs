# F-4fcc06b56813

## Purpose

F-4fcc06b56813 updates a destination handle using a source handle. Its behavior depends on a signed, four-byte metadata field located twelve bytes before the source’s initially observed data address.

There are two materially different paths:

- If that metadata equals −1, distinct source and destination handle locations are passed to a five-argument dependency. Identical handle locations cause no dependency call and no explicit write.
- For every other metadata value, the function invokes two dependencies in sequence, then copies the source handle’s **current** value into the destination handle.

On normal completion, the function returns the destination handle’s address, not the data address stored in it.

An ownership-aware assignment operation is a plausible interpretation. The provided evidence does not establish reference counting, cloning, destruction, allocation, or a particular container type. Those interpretations are not contractual guarantees.

## Interface

### Inputs

The function receives two addresses:

- **Destination handle address:** identifies a writable handle slot.
- **Source handle address:** identifies a readable handle slot.

Each slot contains a value used as a data address. The supplied representation uses four-byte integer values for those stored addresses and associated metadata. This is a contract for that represented address model, not evidence of a portable interface supporting arbitrary native pointer widths.

The two handle addresses may be identical. Distinct handle addresses may also contain the same data address; that is a different case and does not satisfy the function’s handle-identity check.

### Relevant layout

For the data address initially read from the source handle, the function accesses:

| Relative byte offset | Width | Interpretation established by this function |
|---|---:|---|
| −12 | 4 bytes | Signed discriminator compared with −1 |
| −4 | 4 bytes | Opaque argument supplied on the sentinel path |
| 0 | Not established | Address value passed to a dependency; payload contents are not directly accessed here |

On the sentinel path with distinct handle addresses, the function also reads a four-byte value at offset −4 from the data address obtained from the destination handle.

No accesses to the intervening header bytes or to the data payload are established. The layout does not prove that all of these addresses belong to one allocation.

### Output

On normal return, the result is exactly the destination handle address supplied by the caller.

The function has no explicit failure result or status code. It does not inspect a dependency return value.

### Preconditions

For defined execution of the observed accesses:

- The source handle must initially be readable.
- Its initial stored address must permit a readable four-byte access twelve bytes before it.
- On the sentinel path with distinct handle addresses, the destination handle and the four-byte metadata at offset −4 from both relevant data addresses must be readable.
- On the nonsentinel path, the source handle must be readable and the destination handle writable when the final copy occurs, after both dependencies have returned.

Dependencies may impose additional requirements that are not available here. Their effects may also determine whether later accesses remain valid.

No null checks, bounds checks, address-range checks, or explicit alignment checks appear in the provided evidence. A null handle address cannot be treated as a supported empty handle. A zero stored data address likewise does not select an empty-value path; the function still attempts the preceding metadata access.

## Behavior

### Initial observation and branch selection

The function first reads the value stored in the source handle. That value becomes the **initial source data address**.

It then reads the signed four-byte field twelve bytes before that address. The field selects exactly one of two paths:

- A value of −1 selects the sentinel path.
- Every other value selects the nonsentinel path.

Zero, positive values, and negative values other than −1 all take the same nonsentinel path. There is no further classification of this field.

Branch selection uses this initial observation. The function does not recheck the discriminator after a dependency runs.

### Sentinel path: identical handle addresses

If the discriminator is −1 and the destination and source handle addresses are identical, the function performs no dependency calls and no explicit writes.

It nevertheless has already read the source handle and the field at offset −12. This is not an unconditional early return for self-assignment, and it does not make an invalid source handle safe.

Neither offset −4 metadata field is needed on this path.

### Sentinel path: distinct handle addresses

If the discriminator is −1 and the handle addresses differ, the function invokes F-5aa61f6c87d1 with five arguments, in these argument positions:

1. The destination handle address.
2. Zero.
3. The four-byte value at offset −4 from the address read from the destination handle.
4. The initial source data address.
5. The four-byte value at offset −4 from the initial source data address.

The source address in the fourth argument is the original snapshot, not a new read of the source handle.

All argument-producing reads occur before the dependency is invoked. The evidence does not establish a relative evaluation order among the destination-side metadata reads and the source-side offset −4 metadata read. Argument position alone must not be used to assert that order.

After the dependency returns normally, this function performs no explicit assignment to the destination handle. Any destination update on this path is a dependency effect.

Equal stored data addresses do not suppress the call. Only equality of the two handle addresses does so.

### Nonsentinel path

If the discriminator is not −1, the function performs these operations in order:

1. Invoke F-54e9fd6505cf with the address twelve bytes before the initial source data address.
2. After that invocation returns, invoke F-8a5aadac202f with the destination handle address.
3. After that invocation returns, read the source handle again.
4. Store the newly read value into the destination handle.

The final source read is significant. The copied value is whatever the source handle contains after both dependencies have returned, not necessarily its initial value.

Consequently, a dependency that changes the source handle can affect the final assignment. No preservation of that handle may be assumed from the visible function alone.

There is no handle-identity check on this path. When source and destination handle addresses are identical, both dependencies still run. The final read and write then target that same slot, using its post-dependency value.

### Completion and exceptional execution

Following any normally completed path, the function returns the original destination handle address.

There is no visible local recovery, rollback, or error translation. If an access fails or a dependency does not return normally, the evidence does not establish a normal result or restoration of earlier state.

## Side effects

### Explicit reads and writes

The function directly performs:

- An initial read of the source handle.
- A four-byte discriminator read at offset −12 from the initial source data address.
- On the distinct-handle sentinel path, the reads needed to obtain both offset −4 metadata arguments.
- On the nonsentinel path, a second source-handle read followed by one destination-handle write.

The only explicit write in this function is the final handle assignment on the nonsentinel path.

That statement does not constrain writes performed by dependencies.

### Ownership and lifetime

The function itself does not visibly allocate or free storage, copy a payload, or clear a handle. It supplies addresses and metadata to dependencies that may have ownership-related behavior.

The evidence does not establish:

- Whether F-54e9fd6505cf retains, increments, validates, or otherwise modifies the header.
- Whether F-8a5aadac202f releases, clears, replaces, or merely examines the destination.
- Whether F-5aa61f6c87d1 allocates or copies data.
- Whether any dependency preserves globals, handle slots, metadata, or allocation lifetimes.
- Whether the returned handle implies any ownership transfer.

These are documented-only unknowns, not assumptions that dependencies are harmless.

### Aliasing and ordering

The two handle slots may alias each other. Their stored data addresses may also be equal or related independently of slot identity.

Because the nonsentinel path calls both dependencies before reading the source again, effects on aliased storage can change the final value. In particular, an interpretation in which the final assignment always reproduces the initial source value would be incorrect.

No synchronization or atomicity guarantee is established. The evidence alone does not define safe concurrent access to either handle or its metadata.

## Acceptance examples

These examples are conditional expectations derived from static evidence. They are not reports of executed tests.

### Sentinel self-assignment

Given identical source and destination handle addresses and a readable initial discriminator equal to −1:

- The source handle and discriminator are read.
- No dependency is invoked.
- No explicit write occurs.
- The shared handle address is returned.

The function does not need the offset −4 metadata on this path.

### Sentinel assignment between distinct handles

Given distinct handle addresses, valid required reads, and a source discriminator equal to −1:

- F-5aa61f6c87d1 is invoked once with the five arguments specified above.
- Neither nonsentinel dependency is invoked.
- This function performs no subsequent destination-handle assignment.
- If the dependency returns normally, the destination handle address is returned.

A claim that the destination now contains the initial source address requires additional evidence about F-5aa61f6c87d1.

### Distinct handles holding the same address

Given distinct handle addresses that both contain the same data address, with discriminator −1:

- The sentinel dependency is still invoked.
- Equality of the stored values does not activate the self-assignment bypass.

### Nonsentinel assignment with stable source

Given any discriminator other than −1, valid accesses, and dependencies that return normally without changing the source handle:

- F-54e9fd6505cf runs before F-8a5aadac202f.
- The destination receives the initial source data address after both calls.
- The destination handle address is returned.

The stable-source condition is an example premise, not a guarantee supplied by this function.

### Source changed by a dependency

Given a nonsentinel discriminator and dependencies that leave a different valid value in the source handle:

- The final assignment copies that different value.
- The first dependency still received the header address derived from the original source value.
- The discriminator is not reread to reconsider the branch.

### Nonsentinel self-assignment

Given identical handle addresses and a discriminator of zero:

- Both nonsentinel dependencies run in their specified order.
- The slot is read after both calls and that value is written back.
- No guarantee that its original value survives follows from handle identity.

### Unsupported address

Given an unreadable source handle or an inaccessible discriminator address:

- No defined error return is established.
- The function does not promise to detect the condition before attempting the access.

## Uncertainties

### Inferred intent

The discriminator may distinguish a special ownership mode, and the nonsentinel call sequence may implement a retain-before-release assignment. The offset −4 fields may describe a size or capacity.

These interpretations are plausible but unproven. They must not replace the opaque field and dependency behavior specified above.

### Documented-only unknowns

The following remain unresolved:

- Original declared types and the exact platform ABI.
- Endianness and alignment requirements.
- Whether offset −4 values are signed, unsigned, lengths, capacities, or another kind of metadata.
- Header allocation boundaries and payload format.

- Failure behavior beyond the absence of local handling.

The negative offsets identify byte-relative address calculations. They do not establish a portable wraparound rule for integer underflow or permission to read before an allocation. An implementation must resolve address-width and arithmetic semantics for its actual target rather than guessing them from this representation.
