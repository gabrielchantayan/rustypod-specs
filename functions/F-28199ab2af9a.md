# F-28199ab2af9a

## Purpose

F-28199ab2af9a converts a sequential stream of packed, two-byte color pixels into three separately addressed byte planes: one full-resolution plane and two horizontally and vertically subsampled planes.

The bit extraction is consistent with little-endian RGB565 input. The output arithmetic is consistent with limited-range luma and centered chroma. These format names describe inferred intent; the byte extraction, arithmetic, and write locations below are the established behavior.

The function processes pixels in pairs. It writes one luma byte for each pixel in a pair, but derives both chroma bytes exclusively from the **second pixel of each pair on even-numbered input rows**. It does not average neighboring pixels or rows.

Odd widths are not rejected or handled as incomplete pairs. A final full pair is consumed and produces two luma bytes even when only one nominal pixel remains.

### Derived layouts

For ordinary positive dimensions without arithmetic overflow:

- Luma row stride is the width rounded upward to a multiple of four bytes.
- Chroma row stride is the signed integer quotient of width divided by two, rounded upward to a multiple of four bytes.
- Source row consumption is four bytes multiplied by the number of processed pixel pairs.
- The number of processed pairs per row is the width divided by two, rounded upward.

Consequently, a positive odd width consumes two more source bytes than a tightly packed row of exactly that width would contain.

The source has no separate row-padding adjustment. Each row begins immediately after the bytes consumed by the preceding row.

## Behavior

### 1. Stride derivation and empty work

Before the height check, the function derives both destination strides and an internal starting luma address.

The represented stride arithmetic uses 32-bit operations:

- Luma stride is the low 32 bits of width plus three, with the two lowest bits cleared.
- Chroma stride is formed by first dividing the signed width by two, then adding three with unsigned 32-bit arithmetic, and clearing the two lowest bits.

For positive, non-overflowing widths, these are the alignment rules stated above. Negative widths do not have the same “rounded upward size” interpretation.

If height is less than one, the function returns without reading or writing pointed-to storage. This does not bypass the preceding local arithmetic.

If height is positive but width is zero or negative, each row skips the pixel loop. No source bytes are read and no destination bytes are written. The function still advances its internal row state until the requested positive height is exhausted.

### 2. Row and pair traversal

Rows are numbered from zero. Within each row, pair starts are numbered by even pixel positions: zero, two, four, and so on, while the pair start remains less than width.

For every processed pair:

1. The first two source bytes supply the first pixel.
2. One luma byte is written for that pixel.
3. The following two source bytes supply the second pixel.
4. A second luma byte is written.
5. On an even-numbered row only, one byte is written to each chroma plane using the second pixel’s expanded channels.
6. Processing advances to the next pair.

The source advances by four bytes per pair and is not reset between rows.

For positive width, let:

- \(P=\lceil W/2\rceil\), the number of processed pairs;
- \(S_Y\), the derived luma stride;
- \(S_C\), the derived chroma stride.

Then, under ordinary non-overflowing address arithmetic:

- Input row \(r\) starts at source offset \(4Pr\).
- Luma row \(r\) starts at destination offset \(S_Yr\).
- Pair \(k\) writes luma offsets \(2k\) and \(2k+1\) within that row.
- Even input row \(r\) writes chroma row \(r/2\), at byte offset \(k\) within each chroma row.
- Odd input rows make no chroma writes.

The number of chroma rows written is \(\lceil H/2\rceil\) for positive height.

The equations above give the same final stored bytes for the established channel range; they do not assert that the internal chroma intermediate is a signed quantity.

The stored byte is the low eight bits after the represented narrowing and offset operations. No separate saturation or clamping step exists. For channels in the established range, the equations produce:

### 5. Odd dimensions and padding

An odd width still produces two luma writes in its final pair. Thus the number of luma bytes written per row is \(2\lceil W/2\rceil\), not necessarily the nominal width.

The luma stride can accommodate that extra byte for ordinary positive widths, but the function does not distinguish it from a real pixel’s output.

Chroma stride uses the width divided by two **rounded down before alignment**, while the number of chroma samples written is the width divided by two rounded up. These can disagree in a way alignment does not repair.

In particular:

- Width one gives a zero chroma stride but still writes one chroma sample on every even-numbered input row.
- More generally, positive widths congruent to one modulo eight have a chroma stride one byte shorter than the number of chroma samples written per chroma row.

For those widths, writes can overlap successive nominal chroma rows or extend beyond storage sized solely as stride times row count.

An odd height is accepted. Its final, even-numbered row writes chroma normally; no following row is needed.

The function does not initialize destination padding. Bytes outside the actual write locations remain untouched unless overlap or address wrap makes them coincide with another write.
