# F-1f8d84804e23

## Purpose

F-1f8d84804e23 derives a style description from four named properties associated with a caller-supplied object. It resets and selectively sets two style-flag bits, requests storage for a description, and conditionally populates and publishes that description.

The recognized property names are `SLANT`, `WEIGHT_NAME`, `SETWIDTH_NAME`, and `ADD_STYLE_NAME`. Selection occurs in that order. Description assembly uses a different order: additional style, weight, slant, then set width.

The default description is `Regular`. Recognized slants produce the literal descriptions `Oblique` or `Italic`. A weight beginning with `B` or `b` selects a fixed data item whose complete byte contents are not present in the supplied evidence.

This contract distinguishes directly established operations from string, allocation, and property semantics inferred from how dependencies are used. No runtime tests have been performed.

## Interface

### Arguments

1. **Object address:** a 32-bit address identifying a readable and writable object with the following accessed layout.
2. **Return payload:** an uninterpreted 32-bit value carried into the high half of the return value.

The relevant object fields are:

| Byte offset | Width | Access | Role established by use |
|---|---:|---|---|
| 12 | 32 bits | Read/write | Style flags; cleared at entry, then updated with bits 0 and 1 |
| 24 | 32 bits | Write on specified paths | Description address or opaque storage result |
| 100 | 32 bits | Read | First argument supplied to the storage dependency |
| 140 | 32 bits | Read | Property-collection value supplied to each lookup |

Property lookup results are treated as 32-bit addresses. For each nonzero result:

| Byte offset | Width | Meaning used by this function |
|---|---:|---|
| 4 | 32 bits | Eligibility discriminator; must equal 1 |
| 12 | 32 bits | Address of a candidate byte string |

No object size, complete property-record layout, or meaning for other discriminator values is established.

### Return value

The result is 64 bits:

- Bits 63–32 reproduce the second argument.
- Bits 31–0 contain the final 32-bit status value held in a local status cell.

The status cell starts at zero and its address is passed to the storage dependency. Subsequent execution branches on whether that cell remains zero. The numeric meanings of nonzero statuses are unknown.

There is no direct return of the description address. When published, it is written to object offset 24.

### Preconditions

The object address must support the accesses listed above. Every accepted property record and every dereferenced candidate address must remain valid when accessed.

For ordinary string behavior, selected values must be readable terminated byte strings compatible with the length-like and copy-like dependencies. Requested storage must be writable for all resulting copies, transformations, separators, and termination.

These are caller and dependency requirements, not checks implemented here. The function does not independently validate object bounds, property-record bounds, string termination, allocation extent, or successful-result pointers.

## Behavior

### Entry and observation order

The function initializes its status cell to zero. It then:

1. Reads the 32-bit field at object offset 100.
2. Reads the 32-bit field at object offset 140.
3. Writes zero to the entire 32-bit field at object offset 12.

Both captured input fields are reused later. The property-collection field is not explicitly reloaded between lookups.

The function next performs four property lookups in the order below. Flag updates occur during selection, before any storage request.

### Slant selection

The `SLANT` lookup is eligible only when:

- Its result is nonzero.
- The record discriminator at offset 4 equals 1.
- The candidate address at offset 12 is nonzero.
- The candidate’s first byte is `O`, `o`, `I`, or `i`.

An eligible selection causes a read-modify-write of the flag field, OR-ing in value 1.

The candidate address and its first byte are read again to select the description:

- `O` or `o` selects `Oblique`.
- Otherwise, the accepted path selects `Italic`.

The length-like dependency is called for the selected literal. Its result initializes the accumulated component length, and the component count becomes one.

Only the first byte governs eligibility. For example, a value beginning with `O` need not spell “Oblique.” The reread also means that selecting `Oblique` assumes the candidate has not changed between eligibility checking and the later read.

### Weight selection

The `WEIGHT_NAME` lookup is eligible when its result is nonzero, its discriminator equals 1, its candidate address is nonzero, and the candidate’s first byte is `B` or `b`.

An eligible result:

- Selects a fixed data item as the weight component.
- ORs value 2 into the current flag field.
- Calls the length-like dependency on that fixed item.
- Adds the returned length to the accumulated length.
- Increments the component count.

The source property is not copied as the weight label. The selected fixed item’s full contents are unknown from the supplied evidence.

### Set-width selection

The `SETWIDTH_NAME` lookup is eligible when:

- Its result is nonzero.
- Its discriminator equals 1.
- Its candidate address is nonzero.
- Its first byte is neither zero, `N`, nor `n`.

If eligible, the candidate address is retained as the set-width component, the component count is incremented, and a length-like dependency result is added to the accumulated length.

The displayed dependency call does not expose an explicit argument at this point. Treating its result as the candidate’s string length is inferred intent, not a fully established call interface.

Rejection is based on the first byte alone. Any value beginning with `N` or `n` is omitted, not merely a value spelling “Normal.”

### Additional-style selection

`ADD_STYLE_NAME` uses the same eligibility rules as set width.

An eligible candidate address is retained as the additional-style component, the component count is incremented, and another length-like result is accumulated. Here too, the displayed call does not expose an explicit argument.

Neither set-width nor additional-style selection explicitly modifies the style flags.

### Choosing the description path

After all four lookups, the function chooses the default path when either:

- No components were selected; or
- The accumulated length equals zero.

Otherwise, it chooses composite assembly.

The zero-length condition is independent of the selected-component count. Selection and flag changes are not undone when the default path is chosen.

### Default path

The storage dependency is called with:

- The value captured from object offset 100.
- A requested size of 8.
- The address of the local status cell.

Its 32-bit result is written to object offset 24 immediately, regardless of the status value.

If the status is zero, the copy-like dependency is called with that result as destination and `Regular` as source. If the status is nonzero, the copy is skipped.

The request of 8 bytes accommodates `Regular` and a terminating zero under conventional byte-string semantics.

### Composite path

The requested size is the accumulated length plus the selected-component count.

Under ordinary length semantics, with stable nonempty components, this accommodates all component bytes, one separator per component, and replacement of the last separator by the final zero byte.

The storage dependency receives the same captured first argument and status-cell address as on the default path.

If the returned status is nonzero:

- Assembly is skipped.
- This function does not explicitly assign the returned storage result to object offset 24.

If the status is zero, components are assembled in this order:

1. Additional style, if selected.
2. Fixed weight item, if selected.
3. Slant literal, if selected.
4. Set width, if selected.

For additional style:

- The copy-like dependency is called first.
- The copied destination is scanned from its beginning.
- Each destination byte equal to ASCII space is replaced with `-`.
- The length-like dependency is called on the retained source before every loop-condition comparison, including the terminating comparison.
- A single ASCII space is written after the scanned destination span.

For weight and slant:

- The component is copied.
- Its length is obtained again.
- An ASCII space is written at that offset from the component destination.
- The next component destination is advanced past that space.

For set width:

- The component is copied.
- The same repeated-length scanning and space-to-hyphen replacement used for additional style is applied.
- An ASCII space is written after the scanned span.

After the last selected component, the final separator is overwritten with a zero byte. The resulting storage address is then written to object offset 24.

Only literal ASCII spaces are transformed within additional-style and set-width components. Other whitespace bytes are not explicitly changed. Leading, trailing, and consecutive spaces each become hyphens; they are not trimmed or collapsed.

### Widths and arithmetic

The component count and accumulated lengths use 32-bit integer-sized values. At most four components are selected.

Length accumulation and the composite-size expression have no explicit overflow checks. The source does not establish a safe policy for values exceeding the representable range; mathematical, unbounded addition must not be substituted for these operations.

The normalization-loop counter is 32-bit unsigned. The length-like return used in each comparison is also interpreted as unsigned. A negative signed interpretation of such a return does not provide a negative-length termination condition.

Pointer advancement, separator placement, and final termination are not bounds-checked. Safe composite behavior therefore depends on valid lengths, adequate storage, and sufficient stability across repeated dependency calls.

## Side effects

### Object state

The function explicitly clears all 32 flag bits at entry. Accepted slant and weight selections subsequently OR in values 1 and 2.

In the absence of dependency-induced changes, the resulting flag value is one of 0, 1, 2, or 3. That is not an unconditional whole-execution guarantee: dependencies may affect reachable state, and later flag updates read the then-current field.

Description publication differs by path:

- **Default:** offset 24 is assigned before the status check and before copying.
- **Composite success:** offset 24 is assigned only after assembly and termination.
- **Composite failure:** no explicit assignment to offset 24 occurs.

An existing description is not explicitly read, released, or cleared before replacement.

### Memory and ownership

The function directly modifies successful composite storage through space-to-hyphen replacements, separator writes, and final zero termination. Other description writes are delegated to the copy-like dependency.

There is no explicit release operation in this function. Ownership of prior descriptions, property strings, the fixed weight item, and newly returned storage is not established.

The requested-storage dependency might allocate, reuse storage, or perform other operations; its actual contract is unknown. Likewise, unknown dependencies must not be assumed to preserve globals, avoid aliasing, or leave object fields unchanged.

### Failure behavior

The only explicit error channel is the status cell passed to the storage dependency and returned in the low 32 bits.

No separate error is generated here for missing properties, rejected discriminators, ignored first bytes, null successful-result pointers, invalid strings, arithmetic overflow, or copy failure.

Flag mutations precede the storage request and have no explicit rollback.

## Acceptance examples

Unless stated otherwise, examples assume valid stable records and strings, conventional copy and length behavior, adequate returned storage, zero success status, no overflow, and no unrelated dependency side effects.

1. **No eligible properties.**  
   The function requests 8 bytes, publishes the returned address, and copies `Regular`. Flags remain zero. The return value preserves the second argument in its upper half and has zero in its lower half.

2. **Slant beginning with lowercase `o`.**  
   A valid `SLANT` candidate of `oblique-like` selects `Oblique`, not the original property text. Flag bit 0 is set.

3. **Slant beginning with uppercase `I`.**  
   A valid candidate beginning with `I` selects `Italic`. A candidate beginning with an unrelated byte contributes no slant component.

4. **First-byte exclusion for width.**  
   A valid `SETWIDTH_NAME` candidate of `Narrow` is omitted because it starts with `N`. A candidate of `Condensed` is included.

5. **Component ordering and normalization.**  
   With additional style `Display Face`, italic slant, and set width `Semi Condensed`, but no weight component, the assembled description is `Display-Face Italic Semi-Condensed`.

6. **Repeated spaces.**  
   An additional-style value containing two spaces between words yields two hyphens there. The function does not normalize them to one hyphen.

7. **Weight selection.**  
   A valid weight candidate of `Book` selects the same fixed weight item as any other accepted `B`/`b` candidate. It sets flag bit 1. An exact expected output label is documented_only until the fixed item’s bytes are supplied.

8. **Default-path storage failure.**  
   If no components qualify and the storage dependency reports a nonzero status, its result is still assigned to offset 24. `Regular` is not copied. The reported status appears in the return value’s lower half.

9. **Composite-path storage failure.**  
   If a component qualifies but the storage dependency reports failure, no composite copying or explicit description-field assignment follows. Already performed flag changes remain unless affected by dependency behavior.

10. **Nonzero return payload.**  
    For any second-argument bit pattern, the upper return half reproduces that pattern independently of the storage status.
