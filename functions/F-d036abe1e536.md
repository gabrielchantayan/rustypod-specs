# F-d036abe1e536

## Purpose

F-d036abe1e536 establishes address-like boundaries for a requested byte frame on a mutable object. It selects between two paths:

- **Direct-storage mode:** derive the boundaries from an existing backing address and the current position.
- **Callback-backed mode:** obtain a buffer through a dependency, invoke an object-supplied callback, and publish boundaries after the callback returns.

“Frame,” “backing address,” and “position” are inferred semantic roles. The established behavior consists of field accesses, arithmetic, calls, status handling, and ordered mutations.

The operation is not transactional. An allocation-status failure leaves the backing-address field replaced. A short callback result triggers a release call but still leads to boundary writes and position advancement. An accepted callback result is not necessarily accompanied by a zero return status if a dependency changes the exposed status storage.

## Interface

### Arguments and result

The function accepts:

1. A pointer to a mutable object.
2. An unsigned requested byte count.

It returns an integer status. In the apparent 32-bit representation:

- The requested count and callback result are unsigned 32-bit quantities.
- Position and declared-size comparisons use unsigned 32-bit interpretations.
- The return status occupies a signed integer-sized slot.
- Address-bearing object fields occupy integer-sized slots.

The status is initialized to zero. The function explicitly assigns **85**, hexadecimal **0x55**, on direct-storage rejection and after handling a short callback result. The allocation dependency receives writable access to the status storage and can supply another value.

The return uses the status storage’s then-current value. In particular, the accepted-callback path does not reset that storage after the callback.

These widths and offsets describe the apparent source representation, not an independently verified ABI. Portable pointer semantics, actual address width, and instruction-level behavior are not established.

### Preconditions and assertion behavior

Normal execution requires an object accessible for the relevant reads and writes, a zero entry frame cursor, and values suitable for the selected path.

The entry check short-circuits:

- A null object triggers the assertion call without first reading its frame cursor.
- A non-null object triggers that call if its frame cursor is nonzero.

The assertion call is not followed by an explicit failure return. If it returns, processing continues. A still-null object therefore reaches subsequent object access; no successful outcome for that case is established.

No explicit entry validation covers the frame limit, backing address, declared size, callback validity, or allocation-context validity.

## Behavior

### Entry, assertion arguments, and mode selection

The function first initializes its status storage to zero and performs the entry check.

On assertion failure, it calls **F-540af0155702** with three arguments:

1. A fixed assertion-format diagnostic reference.
2. The numeric line marker **235**.
3. A value loaded from a global datum on this assertion path.

The third argument is a dependency on global state, not merely a fixed diagnostic reference. Its meaning, width, initialization, and permissible values are not supplied. No corresponding read of that datum is established on the ordinary non-asserting path.

If the assertion dependency returns, the function reads the object’s callback field to select the mode. The assertion dependency is not known to preserve object or global state, so this selection must not be described as necessarily using the pre-assertion callback value.

A zero callback field selects direct-storage mode. A nonzero value selects callback-backed mode.

### Direct-storage bounds decision

The function captures the object’s position and interprets it as unsigned. Acceptance requires both:

- Captured position is strictly less than declared size.
- Captured position plus requested count is less than or equal to declared size.

The first comparison gates the second. The declared-size field is consulted by these comparisons; there is no dependency call between them.

Under the apparent 32-bit arithmetic model, position plus count wraps modulo \(2^{32}\). There is no separate overflow test. Consequently, acceptance does not prove that the unbounded mathematical interval fits within the declared storage.

A zero request still requires position to be strictly below declared size. Position equal to declared size is rejected even for a zero request.

### Direct-storage acceptance

On acceptance, direct writes occur in this order:

1. Frame cursor receives backing address plus captured position.
2. Position receives captured position plus requested count.
3. Frame limit receives backing address plus captured position plus requested count.

The backing-address field is read for boundary construction; it is not replaced on this path. The limit calculation still uses the captured position, not the position field written in the preceding step.

No allocation dependency, read callback, or release dependency is invoked. On an ordinary valid-entry execution, the initialized status remains zero.

This path performs no buffer-content read or copy. Numeric acceptance does not establish that the backing address refers to accessible memory or that address-like additions are valid.

### Direct-storage rejection

On rejection, the sequence is:

1. Call **F-4457a9a44a68** with an operation-level diagnostic reference.
2. After that call returns, reread the object’s position and declared-size fields for a second call to **F-4457a9a44a68**, together with the original requested count and a bounds-diagnostic reference.
3. Assign status 85.
4. Return the current status.

The diagnostic position and size are therefore not necessarily the values used to reject the request. The first diagnostic can change the object before those fields are reread. The relative evaluation order of the second call’s argument reads is not independently specified.

The function makes no direct object-field writes on this rejection path. Diagnostic dependencies may have their own effects.

### Callback-backed allocation

The function captures the allocation-context field before calling **F-34a22f177269**. The dependency receives:

- The captured context.
- The requested count.
- The address of the function’s writable status storage.

Its returned address-like value is written to the object’s backing-address field before the status is inspected.

If the status is nonzero at that check, callback processing is skipped. The function returns the then-current status without directly updating position or frame boundaries and without calling the release dependency.

Consequences:

- Backing-address replacement survives an allocation-status failure.
- The previous backing address is not explicitly released before replacement.
- A nonzero allocation result does not override a nonzero status.
- A zero allocation result does not independently cause rejection if status is zero.

The status-storage address is exposed to the allocation dependency. No supplied contract prohibits that dependency from retaining access during the invocation or making that access available to later dependencies.

### Callback invocation and result classification

If the allocation-status check observes zero, the function obtains the callback and position from the object after allocation and invokes the callback with:

1. The object pointer.
2. The object’s then-current position.
3. The allocation dependency’s returned address-like value.
4. The requested count.

The callback buffer argument is the saved allocation result, not a fresh read of the backing-address field.

Allocation can affect which callback is invoked and which position is passed. The supplied evidence does not establish preservation of either field across allocation.

The callback result is interpreted as unsigned and compared with the requested count:

- A smaller result selects short-read handling.
- An equal or larger result bypasses short-read handling.

There is no distinct error-sentinel interpretation, signed-negative check, or rejection of an oversized result.

The status is not rechecked to decide whether to perform the final boundary and position writes. A later status change therefore does not cancel those writes.

### Accepted callback result

For a result at least as large as the request, no short-read diagnostics or release call occur.

The function proceeds directly to these writes:

1. Frame cursor receives the object’s current backing address.
2. Frame limit receives the object’s current backing address plus requested count.
3. Position receives the object’s current position plus callback result.

The callback can therefore affect the published boundaries by changing the backing-address field. It can affect the final position by changing the position field.

The frame span is based on the requested count, while position advancement is based on the returned count. An oversized result is accepted and advances position by that larger value.

The function makes no status assignment on this accepted-result path. It returns the status storage’s then-current value. Zero follows only if that storage remains unchanged after the successful allocation-status check. Without a dependency contract excluding retained access, an accepted callback result cannot unconditionally be equated with a zero return.

### Short callback result

For a result smaller than the request, the sequence is:

1. Call **F-4457a9a44a68** with an operation-level diagnostic reference.
2. Call **F-4457a9a44a68** with a short-read diagnostic reference, requested count, and saved callback result.
3. Call **F-bf7242c98d06** with the previously captured allocation context and the object’s backing address as read at this point.
4. Clear the backing-address field to zero.
5. Assign status 85.
6. Write frame cursor from the backing-address field.
7. Write frame limit from the backing-address field plus requested count.
8. Add the saved callback result to the object’s then-current position.
9. Return the current status.

The release argument need not equal the original allocation result. The callback or either diagnostic can replace the backing-address field before the release argument is read. The context, however, remains the value captured before allocation.

The release dependency’s own effects occur before the explicit backing-address clear and status assignment. In ordinary execution without concurrent or asynchronous mutation, the final backing address and cursor are zero, the limit is numerically the requested count, and the returned status is 85.

The final position read occurs after the diagnostics and release. Their position changes, if any, participate in the final addition. No rollback restores the pre-callback position.

### Arithmetic and zero-count behavior

Under the apparent 32-bit model:

- Position-plus-count and position-plus-result calculations can wrap modulo \(2^{32}\).
- High-bit-set values remain unsigned for the bounds and result comparisons.
- Address-like additions have no explicit overflow or accessibility checks.

For a zero request, callback-backed mode still allocates and, if the allocation-status check passes, invokes the callback. No unsigned callback result is smaller than zero, so short-read handling cannot occur. A positive callback result can advance position even though the published frame span is zero.

## Side effects

The function directly writes only its status storage and the object’s backing address, position, frame cursor, and frame limit. The selected path determines which writes occur and in what order.

It does not directly inspect, fill, or copy buffer contents. Any transfer of bytes belongs to a dependency.

Ownership conclusions are limited:

- Direct-storage acceptance invokes no allocation or release dependency.
- Callback-backed entry replaces the backing-address field.
- A short result invokes the release dependency with the current backing address.
- An accepted result invokes no release before return.
- Allocation-status failure invokes no release here.

It is inferred that direct-storage frames borrow storage and callback-backed frames use obtained storage. The actual ownership contract is unknown. The evidence does not establish who later releases a successful frame, whether a failed allocation can return owned storage, or whether replacement loses an existing ownership obligation.

External dependencies may mutate object fields, globals, and other reachable state. The allocation dependency additionally receives the status-storage address. No preservation guarantee or ownership transfer may be assumed solely from a dependency’s inferred role.

## Acceptance examples

These are conditional static examples, not executed tests. Except where specified, dependencies return normally, do not mutate the object, and do not change status storage after setting the allocation outcome. Arithmetic examples use the apparent 32-bit model.

1. **Direct-storage success.** Backing address 4096, size 100, position 20, zero callback, zero cursor, request 12. Return zero; cursor 4116, position 32, limit 4128. No allocation or callback occurs.

2. **Exact end.** Size 100, position 90, request 10. Direct-storage acceptance writes position 100. Position was strictly below size when checked.

3. **Zero request at end.** Size 100, position 100, request zero. Two diagnostics occur, return is 85, and there are no direct object-field writes.

4. **Diagnostic rereads.** Size 100, position 100, request 1 causes rejection. If the first diagnostic changes position to 7 and size to 8, the second diagnostic receives 7, 1, and 8. The bounds decision is not repeated.

5. **Wrapped bound.** Size 4,294,967,295, position 4,294,967,280, request 32. The sum wraps to 16 and passes the represented predicate. Position becomes 16. This is not evidence of a safe memory interval.

6. **Returning assertion.** A nonzero entry cursor triggers the assertion dependency. Its third argument is the global datum’s value loaded for that call. If it returns, subsequent processing uses the callback field read afterward; assertion recovery alone does not supply an error status.

7. **Allocation-status failure.** Allocation returns address 8192 and sets status 7. Backing address becomes 8192; return is 7. No callback, release, or direct frame/position update follows.

8. **Exact callback result.** Allocation yields 8192 with zero status; position 40, request 10, result 10. Cursor becomes 8192, limit 8202, position 50, and return is zero under the stated status-preservation condition.

9. **Oversized result.** With the preceding setup, result 15 produces limit 8202 and position 55. No short-read release occurs.

10. **Accepted result with changed status.** Suppose allocation retains valid access to the exposed status storage, and the callback changes that storage to 9 through such access while returning 10 for request 10. Final boundary and position writes still occur, and the function returns 9.

11. **Short result.** Allocation yields 8192; position 40, request 10, result 4. Two diagnostics precede release. Backing address and cursor become zero, limit becomes 10, position becomes 44, and return is 85.

12. **Callback mutations.** If the callback changes position from 40 to 100 and returns 10 for request 10, final position is 110. If it instead replaces backing address 8192 with 12288 before returning a short result, nonmutating diagnostics leave 12288 as the release argument.
