# F-159eff45b707

## Purpose

F-159eff45b707 searches a dependency-controlled sequence for a pattern of 16-bit values, using 8-bit comparison values supplied by dependencies. On a completed match, it returns a score determined by one additional dependency result. If the forward-search dependency reports termination before a completed match, it returns zero.

The observable result is a 32-bit value: 0, 10, 100, or 1000 on the defined return paths.

The apparent intent is a scored sequence or text match with special handling for some zero-valued comparison results. That interpretation is inferred, not established. The available evidence does not establish an encoding, a text source, cursor direction, word-boundary semantics, or the meaning of the classification table.

This contract therefore describes dependency calls, comparison rules, and result selection without requiring those interpretations.

## Interface

The function takes four arguments:

| Argument | Established use |
|---|---|
| First | A 32-bit opaque value. Not read or forwarded by the visible function. |
| Second | A 32-bit opaque value. Not read or forwarded by the visible function. |
| Third | A 32-bit address-bearing value used as the base of a sequence of 16-bit pattern entries. |
| Fourth | A signed 32-bit value used as the pattern length and to calculate loop bounds and pattern addresses. |

The return value occupies 32 bits. All explicit returned constants are nonnegative, so their interpretation does not depend on signedness.

For this contract:

- **Pattern base** means the third argument.
- **Length** means the fourth argument.
- **Pattern entry at index _k_** means the 16-bit value read at pattern base plus twice _k_, with offsets measured in bytes.
- **Marker** means the first 16-bit value in an output region supplied to a dependency.
- **Comparison byte** means the first 8-bit value in another output region supplied to a dependency.

These names describe how values are used, not what the dependencies intend them to mean.

The function supplies a 1,036-byte local state region to its dependencies. It also supplies two 4-byte output regions during initial advancement and a separate pair of 4-byte output regions during candidate search, verification, and scoring. The initial marker region is represented as signed 16-bit elements; the later marker region is represented as unsigned 16-bit elements. Only equality with zero is tested in the initial region, so its signedness does not affect that test.

The function consumes only the first 16-bit marker and first comparison byte. No visible decision uses the remaining bytes of these output regions.

A conventional supported-use precondition is a positive length, valid pattern storage for that many 16-bit entries, and address arithmetic that remains valid. The function does not enforce these conditions. Behavior for nonpositive lengths is described below rather than normalized into an empty-pattern rule.

## Behavior

### Initialization and preliminary advancement

The function first calls F-45232d870281 with the local state region.

It then performs preliminary advancement according to the signed comparison against length minus one. For ordinary positive lengths, this results in exactly length minus one calls to F-f5e53ecdfbab before any pattern entry is read.

Each preliminary call receives:

1. The same local state region.
2. The initial marker output region.
3. The initial comparison-byte output region.

After each call, the function checks the first marker for zero. A zero marker returns 0 immediately. The comparison byte produced during preliminary advancement is not used by this function.

For length 1, no preliminary advancement occurs.

The visible function does not initialize the local state or output regions before handing them to dependencies. Defined behavior therefore requires the initializer and later dependencies to establish every value subsequently consumed. Their names or positions in this sequence do not independently prove that they do so.

### Candidate selection

After preliminary advancement, the function repeatedly calls F-f5e53ecdfbab using the local state and the later pair of output regions.

For every such call, processing is ordered as follows:

1. Test the returned marker for zero.
2. If it is zero, return 0 without reading a pattern entry for that candidate.
3. Otherwise, read the pattern entry at index length minus one.
4. Compare that 16-bit entry with the comparison byte extended to 16 bits.
5. If unequal, request another candidate using F-f5e53ecdfbab.
6. If equal, begin verification of the preceding pattern entries.

The comparison is exact. There is no visible case conversion, masking of pattern values, encoding conversion, or truncation of the pattern entry to eight bits. A pattern entry above 255 cannot equal a comparison byte at this comparison site.

The final pattern entry is read anew for each candidate that has a nonzero marker. The function does not snapshot the pattern.

### Verification of preceding entries

After a candidate matches the last pattern entry, verification starts with index length minus two.

If this index is negative, verification is already complete and the function proceeds directly to scoring. In particular, for length 1, the candidate comparison is the only pattern comparison before scoring.

Otherwise, each verification step calls F-a197027bb3c0 with the local state and the same later output regions used during candidate selection.

The resulting marker and comparison byte are handled by these rules:

- **Zero comparison byte and marker other than 32:**  
  If the marker is zero, verification fails for this candidate. If the marker is nonzero, the result consumes no pattern entry: verification requests another result at the same index.

- **Nonzero comparison byte, or marker equal to 32:**  
  The current 16-bit pattern entry is read and compared with the comparison byte extended to 16 bits. Inequality fails verification. Equality completes that entry and decreases the index by one.

Thus, a zero comparison byte with marker 32 is compared normally and can match a zero pattern entry. A zero comparison byte with any other nonzero marker is skipped without a pattern read.

A zero marker is not a universal termination rule during verification. When its comparison byte is nonzero, the function follows the ordinary comparison path and can accept that byte. Only the combination of a zero marker and zero comparison byte immediately fails verification.

Verification succeeds when the index becomes negative. It fails when an ordinary comparison differs or when both the marker and comparison byte are zero.

### Resuming after verification failure

Verification failure does not itself return 0.

Instead, the function resumes candidate selection by calling F-f5e53ecdfbab again with the existing local state. It does not visibly:

- Reinitialize that state.
- Repeat preliminary advancement.
- Save or restore a prior state.
- Rewind to the candidate position.
- Restore output regions.

Consequently, the next candidate depends on whatever state the preceding dependency calls left behind. The visible function does not establish how this affects overlap between candidate matches.

### Scoring a completed match

After verification succeeds, the function makes one additional call to F-a197027bb3c0 using the local state and later output regions.

This call occurs even for a one-entry pattern. Its marker determines the return value; its comparison byte is not used.

The score is selected in this order:

1. If the marker is zero, return **1000**.
2. Otherwise, if the marker is at least 128, return **10**.
3. Otherwise, use the marker as an index into an externally addressed byte classification table:
   - If the selected byte has none of the bits in mask 0xD0 set, return **100**.
   - If any of those bits are set, return **10**.

The marker is treated as an unsigned 16-bit value for scoring. The table access occurs only for markers from 1 through 127 inclusive. Although the address expression includes selection of the marker’s low eight bits, that selection cannot change the index within this range.

There is no visible classification-table access when the marker is zero or at least 128.

### Termination

The function can terminate through:

- A zero marker during preliminary advancement.
- A zero marker during candidate selection.
- A completed match followed by scoring.

Termination is not otherwise guaranteed. Candidate selection may continue indefinitely if dependency results never terminate or match. Verification may also continue indefinitely if it repeatedly receives zero comparison bytes paired with nonzero markers other than 32.

## Side effects

The visible function performs no explicit heap allocation, heap release, pattern write, or classification-table write.

Its direct externally addressed data reads are:

- Selected 16-bit pattern entries.
- A classification-table byte when scoring requires it.
- The externally stored table base used for that access.

The order of dependency calls and pattern reads is significant:

- Initialization precedes all sequence operations.
- Preliminary advancement precedes all pattern reads.
- Candidate-marker termination is checked before the final pattern entry is read.
- Each verification dependency call precedes any pattern read for that verification step.
- Skipped verification results cause no pattern read.
- Scoring makes an additional dependency call before selecting a return value or reading the classification table.

The classification-table base is obtained for scoring after that final dependency call. The contract does not assume earlier dependencies preserve its value or the table contents.

The same caution applies to pattern storage and other external state. The visible function does not write the pattern, but this is not proof that dependencies cannot affect it through other references or globals.

All supplied state and output regions are local to the invocation. The visible function does not return their addresses or explicitly transfer ownership of them. Whether dependencies retain pointers, allocate resources, modify globals, or require cleanup is unknown. No explicit cleanup dependency is called on any return path.

## Acceptance examples

These examples are conditional on dependencies producing the stated outputs, required storage being valid, and arithmetic remaining defined. They are acceptance scenarios derived from static evidence, not executed tests.

### Early termination during preliminary advancement

Given length 3, preliminary advancement would ordinarily require two calls to F-f5e53ecdfbab.

If the first such call produces marker zero:

- The result is 0.
- No second preliminary call occurs.
- No pattern entry is read.
- No F-a197027bb3c0 call occurs.

### One-entry match and maximum score

Given a one-entry pattern containing 65:

- There are no preliminary calls.
- Candidate selection produces a nonzero marker and comparison byte 65.
- No preceding-entry verification calls are needed.
- One F-a197027bb3c0 scoring call occurs.

If that scoring call produces marker zero, the result is 1000, regardless of its comparison byte.

### Candidate mismatch followed by termination

Given a final pattern entry of 65:

- A candidate with nonzero marker and comparison byte 66 is rejected.
- Candidate selection is called again.
- If this next candidate has marker zero, the result is 0 without another pattern read.

### Skipping without consuming a pattern entry

Suppose verification is checking a pattern entry containing 65.

If F-a197027bb3c0 produces marker 33 and comparison byte zero, the pattern entry is not read or consumed. A subsequent result with comparison byte 65 can still satisfy that same entry.

If such skipped results continue forever, verification does not complete.

### Zero comparison byte with marker 32

Suppose the current verification entry is zero.

A result with marker 32 and comparison byte zero matches and consumes that entry. If the pattern entry is nonzero instead, verification fails and candidate selection resumes.

### Zero marker is handled differently during verification

Suppose the current verification entry is 65.

A result with marker zero and comparison byte 65 matches that entry. It does not itself terminate the search.

By contrast, marker zero and comparison byte zero fail verification, even if the current pattern entry is zero. That failure resumes candidate selection rather than returning immediately.

### Classification scores

After a completed match:

- Scoring marker 128 returns 10 without a table lookup.
- Scoring marker 65 with table byte 0x20 returns 100, because 0x20 has no bits in common with 0xD0.
- Scoring marker 65 with table byte 0x10 returns 10.

The scoring comparison byte does not affect these outcomes.

### Pattern entries above the byte range

A pattern entry of 256 cannot match a comparison byte through ordinary comparison. It is not reduced modulo 256.

This applies both to candidate selection and to ordinary preceding-entry verification.

## Uncertainties

- **documented_only — Nonpositive lengths:** There is no explicit rejection or empty-pattern success rule. Where subtraction remains representable, a nonpositive length skips preliminary advancement but candidate selection still reads the pattern at index length minus one after a nonzero marker. That is a negative index. No safe result is established without valid storage at the calculated address.

- **documented_only — Arithmetic overflow:** Length-minus-one, length-minus-two, doubling indices, and adding offsets to the pattern base use finite-width arithmetic in the supplied representation. At signed extremes or invalid addresses, the evidence does not establish a portable overflow policy. This contract does not substitute wraparound, clamping, or validation.

- **documented_only — Alignment and byte order:** Pattern entries are accessed as 16-bit values. Required alignment, byte order, and behavior of invalid memory accesses are not established.

- **documented_only — Dependency output guarantees:** The function assumes relevant output values are available after calls. Their initialization, validity, and relation to sequence exhaustion are not independently established.

- **documented_only — Traversal and overlap:** The relationship between the two sequence-producing dependencies is unknown. State restoration, overlap handling, and sequence-position guarantees cannot be inferred from this function alone.

- **documented_only — Resource ownership:** No explicit release is visible, but dependency contracts are unavailable. Absence of a local release operation does not prove absence of acquired resources or retained references.

- **documented_only — Classification meaning:** The table and mask establish score selection, not a character class, locale rule, or boundary definition.

- **Inferred intent:** The preliminary advancement, final-entry candidate comparison, and preceding-entry verification suggest pattern searching. The distinct scores suggest match-quality classification. Neither interpretation changes the literal call and comparison contract.
