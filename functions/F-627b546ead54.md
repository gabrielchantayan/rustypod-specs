# F-627b546ead54

## Purpose

F-627b546ead54 obtains an object address, initializes selected fields, acquires two nonzero values, establishes and activates two registrations, performs a final external operation, and publishes the object address.

Normal completion returns the original object address. Four explicit failure conditions instead invoke a dependency identified as nonreturning. The visible function provides neither a normal failure return nor explicit rollback.

“Object initialization,” “acquisition,” “registration,” “activation,” and “publication” describe the observed roles of operations. Their application-level meanings are not established. In particular, the source does not establish resource types, ownership transfer, scheduling behavior, or the purpose of the final operation.

## Interface

### Explicit inputs and result

The function takes no explicit arguments.

On normal completion, it returns the address obtained from F-ff29814bf4cc. It does not return an acquisition value, registration result, or shared-state address.

There is no explicit null-result check on the obtained address and no normal null-return failure path.

### External inputs

The function directly depends on three external values:

- A 32-bit initialization value written into the object.
- A 32-bit value supplied to the first registration.
- A shared-base global containing an address used for shared-state accesses.

The shared-base global is read **twice consecutively after the first registration returns**:

1. The first read supplies an address retained for later operations.
2. The second read independently supplies the destination base for the first registration-result store.

No dependency call intervenes between those reads. Nevertheless, the supplied representation establishes neither synchronization nor immunity to asynchronous mutation. The addresses are equal only if both reads observe the same value.

Dependencies may also consume or modify external state. Their preservation of globals, object contents, or shared fields is not assumed.

The supplied representation uses four-byte words and 32-bit integer results. The object-address publication is also a four-byte pointer store in this representation.

All offsets below are byte offsets.

## Behavior

### 1. Obtain and initialize the object

The function calls F-ff29814bf4cc without explicit arguments and retains its result as the object address.

It then performs three direct writes, in this order:

1. Reads the external initialization value and stores it in the object’s first 32-bit word.
2. Stores zero at object offset `0x2D0`.
3. Stores zero at object offset `0x2D4`.

It next calls F-c53d8fb06b23 with the object address.

The zero stores precede that call. They do not guarantee that the fields remain zero afterward: the dependency’s behavior is unavailable.

The initialization value is not established to be a type tag, dispatch address, or ownership indicator.

### 2. Acquire and check the first value

The function calls F-8157a180d901 with the integer 28 and ignores its return value.

It then calls F-72538fc0941d without explicit arguments, stores the returned 32-bit value at object offset `0x2D0`, and tests the returned value:

- Zero selects the terminal failure path.
- Any nonzero value permits continuation.

The check uses the acquisition result, not a fresh read of the object field. The store occurs before the decision. No restriction beyond nonzero is imposed; high-bit-set results are not rejected merely because they could be interpreted as negative.

### 3. Acquire and check the second value

Only if the first acquisition is nonzero, the function repeats the acquisition sequence:

1. Calls F-8157a180d901 with 28, ignoring its return value.
2. Calls F-72538fc0941d.
3. Stores that result at object offset `0x2D4`.
4. Rejects zero through the terminal failure path.

The acquired values need not be distinct. The function neither compares them nor passes them explicitly to the registration dependency. The object address is passed later, so dependencies may inspect its fields.

A first-acquisition failure prevents the second acquisition. Either acquisition failure prevents all registrations.

### 4. Establish the first registration and read both shared bases

The function calls D-01 and uses its returned 32-bit value as the first argument to F-c930571cdede. The remaining arguments are:

- The external first-registration value.
- The original object address.
- Zero.

After F-c930571cdede returns, the following sequence occurs:

1. Read the shared-base global and retain that address.
2. Read the same global again, independently, to obtain the first-result store destination base.
3. Store the 32-bit registration result at offset `0x2C` from the second-read base.
4. Compare the registration result with `-1`.

There is no dependency call between the two global reads. Their equality is nevertheless conditional on the global remaining unchanged between them. Subsequent operations use the retained address from the **first** read, not the destination selected by the second read.

The result is stored before its failure check:

- Exactly `-1`, represented as `0xFFFFFFFF`, selects the terminal failure path.
- Every other 32-bit result permits continuation.

Zero is accepted. Other values that have a negative signed interpretation are also accepted.

The success decision depends on the registration return value, not on either shared region’s contents.

### 5. Activate the first registration

After accepting the first registration result, the function:

1. Calls D-01 again.
2. Reads the 32-bit field at retained-base offset `0x2C`.
3. Calls F-23aadb16b673 with the new D-01 result and that field value.

This field read occurs after D-01 returns. Its value is not guaranteed to equal the first registration result, for two independent reasons:

- The initial result store may have used a different base.
- D-01 or other activity may have changed the retained region’s field.

The function does not validate this freshly read value. In particular, the earlier registration-result check does not reject a later field value of `0xFFFFFFFF`.

The return value of F-23aadb16b673 is ignored.

### 6. Establish the second registration

The function calls D-01 a third time, then calls F-c930571cdede with:

- That fresh D-01 result.
- The integer 500.
- The original object address.
- Zero.

It stores the returned 32-bit result at retained-base offset `0x30`, then checks the result against `-1`.

Exactly `0xFFFFFFFF` selects the terminal failure path. Every other result permits continuation. The store occurs even when the result indicates failure.

Unlike the first-result store, this destination uses the retained base. The shared-base global is not reread.

### 7. Activate the second registration

For an accepted second registration result, the function:

1. Calls D-01 a fourth time.
2. Reads the 32-bit field at retained-base offset `0x30`.
3. Calls F-23aadb16b673 with the new D-01 result and the field value.

The activation receives the value read after D-01, not necessarily the previously stored registration result. No additional sentinel check is performed on that field value.

The activation return value is ignored.

### 8. Perform the final operation and publish

The function calls D-02. The supplied representation treats its result as a 32-bit integer and adds four before passing it to F-379efa3ca9d1.

The arguments to F-379efa3ca9d1 are:

- The D-02 result plus four.
- The integer 10.
- The integer `0x6C`, or 108.

The representation does not establish valid overflow behavior for this addition, nor does it establish that the first argument designates a particular structure or buffer. Address calculations involving shared bases likewise require valid execution-environment semantics; wraparound is not a promised behavior.

After F-379efa3ca9d1 returns, the function stores the original object address at retained-base offset `0x0C`, then returns that address.

This direct publication follows both activation calls and the final operation. It does not prove that the object was inaccessible earlier: dependencies have already received its address.

### Terminal failure path

- First acquisition equals zero.
- Second acquisition equals zero.
- First registration equals `0xFFFFFFFF`.
- Second registration equals `0xFFFFFFFF`.

The supplied representation identifies this dependency as nonreturning. Behavior if it unexpectedly returns is not established.

Before invoking it, the function performs no explicit object release, acquired-value release, registration cancellation, restoration of overwritten shared fields, or clearing of the publication field. Dependency-internal cleanup or termination behavior is unknown.

## Side effects

Direct effects consist of the object writes, shared-field writes, and ordered dependency calls described above.

Important ordering properties are:

- Initial object writes precede F-c53d8fb06b23.
- Each acquisition result is stored before its check.
- Both shared-base reads follow the first registration call.
- The first registration result is stored through the second-read base before its check.
- First activation reads through the retained first-read base.
- First activation precedes the second registration.
- The second registration result is stored through the retained base before its check.
- Final publication uses the retained base and occurs only after the final dependency returns.

The function overwrites destination fields without first inspecting or releasing their previous contents. A failed second registration occurs after the first activation has already been invoked.

These are direct-operation guarantees, not final-memory guarantees. Dependencies may mutate memory or affect lifetimes. Aliasing between the listed regions could also make one write affect another field.

No ownership transfer is established by either the return or publication. Caller release obligations and object lifetime remain unknown. No explicit locking, atomic publication operation, or memory barrier is shown; thread safety and cross-thread visibility are not established.

## Acceptance examples

These are conditional static scenarios, not runtime test results. They assume valid accessed storage, valid arithmetic, and dependency returns wherever continuation is described.

### Ordinary success with stable shared state

Suppose both acquisitions are nonzero, the registrations return 7 and 9, both shared-base reads return the same address, and intervening activity leaves the relevant fields unchanged.

Then:

- The acquisition fields receive their respective results.
- The common shared region receives 7 at `0x2C` and 9 at `0x30`.
- The activations receive 7 and 9 respectively.
- D-01 is called four times, with each result used separately.
- The final operation precedes the publication store.
- The publication field and return value receive the original object address.

### Different addresses from the two shared-base reads

Suppose both acquisitions succeed, the first registration returns 7, the first global read identifies one region, and the second identifies a distinct, nonoverlapping region.

Then:

- The function retains the first region’s address.
- It stores 7 at offset `0x2C` in the second region.
- After the next D-01 call, first activation reads offset `0x2C` in the first region.
- If that field contains 42 at the read, activation receives 42, not 7.
- The second-result store, second activation read, and final publication use the retained first region.

No dependency call is required between the global reads for this distinction to matter; the source does not rule out asynchronous mutation.

### First acquisition failure

If the first acquisition returns zero, object offset `0x2D0` receives zero and the failure dependency is invoked. There is no second acquisition, registration, activation, final operation, or direct publication.

### Second acquisition failure

If the first acquisition is nonzero and the second is zero, both results have been stored before failure. No registration is attempted, and no explicit release of the first acquired value occurs.

### First registration failure

If the first registration returns `0xFFFFFFFF`, the function still performs both shared-base reads and stores the failure result at offset `0x2C` from the second-read base.

It then invokes the failure dependency. Neither activation nor the second registration follows. The retained first-read region is not necessarily the region receiving the failure result.

### Second registration failure

If the first registration is accepted and the second returns `0xFFFFFFFF`, first activation has already occurred. The failure result is stored at retained-base offset `0x30`, then failure is invoked.

There is no second activation, final operation, direct publication, or explicit cancellation of the first registration.

### Accepted zero and later sentinel mutation

A registration result of zero passes its check. If the relevant activation field is still zero when read, activation receives zero.

Separately, if an accepted registration is followed by D-01 changing the relevant retained-region field to `0xFFFFFFFF`, activation receives `0xFFFFFFFF`. The function does not reapply the registration-result failure check to the field.

### Global replacement after both reads

If the shared-base global changes after both reads, that change does not redirect subsequent direct accesses. They continue using the retained first-read address, whose validity remains required.
