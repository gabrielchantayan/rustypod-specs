# F-14f40f321d22

## Purpose

F-14f40f321d22 conditionally initializes a record obtained through two dependencies and publishes its address through caller-provided output storage.

The first dependency determines whether processing continues and may replace a caller-supplied 32-bit value through an in/out argument. A zero status permits the second dependency to obtain a record address. The wrapper then populates selected record fields using the updated value, the original inputs, and a four-byte value read from the referenced object.

The established behavior is an ordered sequence of calls, reads, and writes. Describing the resulting record as an association between a caller context and a referenced object is an interpretation of its fields, not an established domain-level purpose.

## Interface

The function has four inputs and a 32-bit integer return value.

| Input | Representation | Established use |
|---|---|---|
| Context address | Address of storage containing at least one four-byte value | Its first four bytes are read for the first dependency. The address itself is later stored in the result record. |
| Selector | 32-bit integer | Passed to the first dependency, stored in the result record, and compared with exactly 1 to select a one-byte field value. |
| Output address | Address of storage for one 32-bit result address | Written only on the path where the first dependency returns zero and execution reaches publication. |
| Initial reference | 32-bit integer value | Copied into private mutable storage passed to the first dependency. The resulting value is subsequently used as a dependency argument and as an address. |

The return value has two established cases:

- A nonzero result from F-133a6620fb39 is returned unchanged.
- If F-133a6620fb39 returns zero and all subsequent operations complete, the wrapper returns zero after writing the result address to the output location.

There is no separate checked failure result for F-7871c7eca1be. Its return value is used directly as the result-record address.

### Widths and address model

The supplied representation uses four-byte values for integers, stored addresses, and most record fields. The selector-derived field is exactly one byte. Offsets below are byte offsets.

The behavior therefore requires a model in which the addresses used by this routine are representable in the observed 32-bit values. This does not establish a wider platform ABI, alignment policy, or general pointer-conversion rule.

The wrapper performs no explicit numeric range validation, bounds checking, or overflow checking. Address calculations add fixed offsets to supplied or dependency-produced addresses. Behavior when those calculations cannot identify valid accessible storage is not established.

### Preconditions for a normally completing call

The context address must support the initial four-byte read.

If the first dependency returns zero:

- The updated reference must support the four-byte read at offset `0x34` when that read occurs.
- The second dependency must return an address supporting the record writes described below.
- The output address must support a four-byte write.
- The calls and memory accesses must satisfy any external lifetime, alignment, synchronization, and accessibility requirements.

The wrapper does not enforce these preconditions. The requirements involving the record and output storage are conditional: the wrapper does not access those destinations after a nonzero first-dependency result.

## Behavior

### Resolution and status handling

The wrapper creates private four-byte mutable storage initialized from the initial-reference input. It reads the first four bytes at the context address and invokes F-133a6620fb39 with:

- The value read from the context.
- The selector.
- The address of the private mutable reference.

The dependency can replace that private reference. The initial-reference input is passed by value; modifying the private copy does not itself write back to the caller’s original source storage.

If F-133a6620fb39 returns nonzero, the wrapper returns that status. It makes no call to F-7871c7eca1be and performs none of its result-record or output-location writes.

This short path does not establish that the overall operation was free of side effects. F-133a6620fb39 has already run and may have changed other state.

### Record acquisition and source-field capture

If F-133a6620fb39 returns zero, the wrapper passes the current private reference value to F-7871c7eca1be. The returned 32-bit value becomes the result-record address without validation.

After that call returns, the wrapper reads four bytes at offset `0x34` from the object addressed by the current private reference.

This timing is significant. The field is read after F-7871c7eca1be executes, not before it. If that dependency changes the referenced field, the later value is the one copied into the record.

There is also a distinction between the reference value passed into F-7871c7eca1be and the private reference read afterward. They ordinarily coincide if the private storage remains unchanged. However, the earlier dependency received its address, and the supplied evidence does not establish whether that address can escape. Equality across the second call must therefore not be assumed under undocumented dependency side effects.

### Record initialization

After capturing the four-byte source field, the wrapper performs the following writes in the listed order:

| Order | Destination relative to result-record address | Width | Value |
|---|---:|---:|---|
| 1 | `0x48` | 4 bytes | Current private reference |
| 2 | `0x4c` | 4 bytes | Selector |
| 3 | `0x44` | 4 bytes | Previously captured value from reference offset `0x34` |
| 4 | `0x40` | 4 bytes | Original context address |
| 5 | `0x08` | 1 byte | Decimal 100 if the selector equals exactly 1; otherwise zero |

The selector comparison is exact. Negative values, zero, and positive values other than 1 all select a zero byte. The selector itself is nevertheless stored in full in the four-byte field at `0x4c`.

The context field receives the context address, not the four-byte value initially read from that address. Those two values have distinct roles.

The field at `0x44` receives a snapshot taken before these record writes. It is not read again during publication.

The one-byte write at `0x08` does not explicitly initialize adjacent bytes. The wrapper neither clears the record nor initializes fields outside the listed destinations.

### Publication

After all five record writes, the wrapper writes the result-record address to the output location. It then returns zero.

Publication is therefore last among the wrapper’s explicit externally directed writes. It does not establish atomicity, synchronization, or a guarantee that another observer cannot see intermediate record contents.

### Aliasing and overlapping storage

The wrapper contains no overlap checks. The listed ordering remains relevant when the source object, result record, context storage, and output storage overlap.

In particular:

- The source field is captured before the result-record writes. Later overlapping writes do not retroactively change that captured value.
- Record writes can modify context storage if the result record overlaps it. The already-read first dependency argument is not reread.
- If the output location overlaps a record field, the final publication write can overwrite an earlier initialized value.
- If a dependency changes accessible shared storage, those changes are not undone by the wrapper.

Accordingly, the table describes values at each write, not an unconditional promise that every listed field retains that value after arbitrary overlapping writes.

## Side effects

The wrapper’s explicit memory operations are limited to:

- Initializing and using private mutable reference storage.
- Reading four bytes at the context address.
- On the zero-status path, reading four bytes at reference offset `0x34`.
- Writing the five specified record fields.
- Writing the result-record address to the output location.

The wrapper does not explicitly allocate, free, retain, release, or destroy memory. Neither dependency’s ownership behavior is established.

Storing the context address and reference value in the record establishes that those address values are recorded. It does not establish ownership transfer, reference counting, lifetime extension, or permission to release either object.

There is no explicit rollback. If an operation fails to complete after earlier writes have occurred, the supplied evidence provides no recovery behavior or transactional guarantee.

The wrapper does not explicitly access global state. Its dependencies may do so; global-state preservation cannot be inferred.

## Acceptance examples

These are conditional acceptance cases derived from static evidence. They are not reports of executed tests.

### Nonzero first-dependency status

It must not call F-7871c7eca1be or perform its record and output writes. The output location remains unchanged by the wrapper, although a dependency may independently affect aliased or shared storage.

### Updated reference and selector equal to 1

Suppose the first dependency returns zero and replaces the private reference with a valid object address. Suppose the second dependency returns a valid nonoverlapping record address, and neither dependency subsequently changes the private reference unexpectedly.

The wrapper must use the replacement reference rather than the initial reference. After the second dependency returns, it must capture the four-byte field at replacement-reference offset `0x34`.

With nonoverlapping destinations, the completed record must contain:

- The replacement reference at `0x48`.
- The 32-bit value 1 at `0x4c`.
- The captured source field at `0x44`.
- The original context address at `0x40`.
- The byte value 100 at `0x08`.

The output must receive the record address, and the function must return zero.

### Selector other than 1

Under otherwise valid success-path conditions, selectors 0, 2, and −1 must each produce a zero byte at record offset `0x08`. Each selector must still be stored unchanged as a four-byte value at `0x4c`.

### Source field changed by the second dependency

If F-7871c7eca1be changes the four-byte source field before returning, and the subsequent read remains valid, the wrapper must copy the value observed after that dependency call.

A value captured before the call would not match the established ordering.

### Output overlapping the record

If the output location is exactly the four-byte field at record offset `0x44`, the wrapper first writes the captured source value there. Its final publication write then replaces that field with the record address.

This case demonstrates why the ordinary final-field expectations require nonoverlapping output storage.

### Invalid second-dependency result

If F-7871c7eca1be returns an unusable record address, the wrapper has no explicit branch that converts this into a normal error result. A particular fault, exception, or termination mechanism is not established.
