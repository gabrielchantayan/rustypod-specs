# F-3b7c5b30bd55

## Purpose

F-3b7c5b30bd55 selects a state record using a signed integer selector, calls an entry dependency, and chooses among three paths:

- A zero owner-like field causes direct record updates and a return value of zero.
- A nonzero owner-like field equal to a comparison value causes different direct updates and a return value of decimal 10.
- A nonzero, unequal owner-like field causes submission of a local request to F-c81f7910921f. The function then returns the request’s result word.

The record fields and branch structure suggest ownership and repeated acquisition. This is **inferred intent**, not an established synchronization contract. The supplied evidence does not establish mutual exclusion, thread identity, blocking, acquisition, or release.

The established behavior consists of the address selection, represented memory accesses, dependency ordering, request construction, and return-value selection below.

## Interface

### Input

The sole input is a signed 32-bit selector.

The selected record address is calculated from a global base and the selector multiplied by 32 bytes. No local bounds check, negative-selector check, null check, or overflow check is shown.

Ordinary execution requires:

- A selector whose address calculation produces the intended accessible record.
- Readable and writable storage for the fields used on the selected path.
- Readable global pointer storage and readable pointed-to words when accessed.
- Alignment and address-space properties suitable for the represented accesses.
- Callable dependencies satisfying their external prerequisites.

The valid selector range and table capacity are unknown. Negative selectors are not locally rejected; where the arithmetic is supported, they select addresses before the base. The record stride does not establish that every possible selected address belongs to an allocated table.

### Result

The function returns a 32-bit value.

| Branch | Return behavior |
|---|---|
| Initial owner-like field is zero | Zero, assigned after the exit dependency returns |
| Initial owner-like field is nonzero and the later comparison matches | Decimal 10, assigned after the exit dependency returns |
| Initial owner-like field is nonzero and the later comparison differs | The request’s result word after F-c81f7910921f returns |

The return value has no established signed interpretation. Zero and 10 are not proven success or error categories.

### Selected record layout

Records are selected at a 32-byte stride.

| Byte offset | Represented access | Use |
|---|---|---|
| 0 | 32-bit reads and a possible 32-bit write | Owner-like field |
| 4 | A 32-bit read on the matching path | Source value for conversion to signed 16-bit |
| 4 | A 16-bit write on either direct-update path | Stores one, or the converted-and-incremented value |
| 24 | Signed 32-bit read and write | Counter increment |

The 16-bit store beginning at offset 4 addresses bytes 4 and 5. The 32-bit read beginning there covers bytes 4 through 7. These are overlapping accesses of different widths.

**The addressed 16-bit storage is not established to be the numeric low half of the 32-bit field.** Byte order is not supplied. Conversion of a 32-bit numeric value to signed 16-bit and writing a halfword at the original address are separate operations.

The halfword store does not directly write bytes 6 and 7. Whether those preserved bytes represent the numeric upper or lower half of the containing word depends on target byte order.

These widths describe the supplied static representation. Actual machine-instruction access widths are not independently established.

### Submitted request layout

F-c81f7910921f receives the address of the first word. Apart from the second word’s use as the return channel, the words’ semantic meanings are unknown. This layout is not evidence of an independently specified external request ABI.

## Behavior

### Record selection and entry

The record address is calculated before the entry dependency D-01 is called.

If D-01 changes the global base, this function does not recalculate the already selected address. D-01 may nevertheless alter memory at that address. The first owner-like-field test occurs after D-01 returns.

After D-01 returns, the function captures the pointer stored in a second global location. It does not yet read the word through that captured pointer.

The function then reads the selected record’s owner-like field and tests whether it is zero.

### Initially zero owner-like field

When the first owner-like-field test observes zero, the represented operations occur in this order:

1. Read the signed 32-bit counter at offset 24, add one, and write the result there.
2. Read a 32-bit word through the previously captured pointer.
3. Store that word into the owner-like field at offset 0.
4. Store the 16-bit value one beginning at offset 4.
5. Call the exit dependency D-02.
6. Assign zero to the return value and return.

The pointed-to word is read after the counter update, not when the pointer is captured. This ordering matters if the pointer aliases the counter or if relevant memory changes between those events.

There is no check that the assigned owner-like value is nonzero. A pointed-to word of zero leaves the owner-like field zero despite the counter increment and the halfword store.

The halfword store establishes the value one in the addressed 16-bit storage under the target’s representation. It does not establish that the containing 32-bit word’s numeric low 16 bits become one.

The return value does not depend on D-02’s direct result. Record contents are not checked again after D-02 returns.

### Nonzero owner-like field with a matching comparison

When the initial owner-like-field test observes a nonzero value, the function performs a separate comparison between:

- A new read of the record’s owner-like field.
- A word reached through the pointer currently held in the global pointer location.

This comparison uses the global pointer location again rather than requiring use of the earlier captured pointer. If that global changes, the two pointers need not be equal.

The second owner-like-field read need not match the first if intervening modification is possible. The supplied representation does not establish the relative evaluation order of the comparison’s operand reads, atomicity, or synchronization.

If the comparison is equal, the represented operations are:

1. Increment the signed 32-bit counter at offset 24.
2. Read the signed 32-bit field beginning at offset 4.
3. Convert that numeric value to signed 16-bit.
4. Add one after integer promotion.
5. Store the resulting value through a signed 16-bit access beginning at offset 4.
6. Call D-02.
7. Assign decimal 10 to the return value and return.

This path does not directly rewrite the owner-like field.

The read-convert-add-store sequence must not be reduced to “increment the halfword at offset 4.” The input to conversion is the entire 32-bit numeric value. The output is written to the addressed two bytes. Without byte order and conversion semantics, these operations do not define an increment of either numeric half of the containing word.

### Nonzero owner-like field with an unequal comparison

If the comparison differs, the function:

1. Calls D-02.
2. Initializes request offset 16 to zero.
3. Initializes request offset 4, the result word, to zero.
4. Initializes request offset 0 to decimal 14.
5. Initializes request offset 12 to one.
6. Copies the original selector into request offset 8.
7. Calls F-c81f7910921f with the request address.
8. Returns the result word as it exists after that call.

This is the initialization order represented in the supplied material. It is distinct from the request’s increasing-offset layout. Whether individual writes to the not-yet-submitted local storage are externally observable is unknown.

The direct return value of F-c81f7910921f is unused. If it leaves the request’s result word unchanged, this function returns zero. If it writes another 32-bit value there, this function returns that value without local validation or translation.

This branch has no direct record writes. D-02 and F-c81f7910921f are not assumed to leave the record or globals unchanged.

### Integer boundaries

- Selector multiplication by 32 must not be assumed to wrap safely for all signed 32-bit selectors.
- Address formation must not be assumed valid merely because a numeric address can be calculated.
- Incrementing a signed 32-bit counter at its maximum value has no established portable wraparound behavior.
- Conversion from the offset-4 signed 32-bit value to signed 16-bit is exact when that value is representable. Its behavior outside the signed 16-bit range is not established here.

Accordingly, neither automatic modulo-65536 behavior nor saturation is an unconditional contract. No explicit arithmetic-error branch or overflow result is shown.

## Side effects

### Direct memory effects

On the initially zero path, the function directly:

- Increments the counter at offset 24.
- Writes the owner-like field at offset 0.
- Writes two bytes beginning at offset 4.

On the matching path, it directly:

- Increments the counter at offset 24.
- Reads the four-byte field beginning at offset 4.
- Writes a converted-and-incremented value to the two bytes beginning at offset 4.

On both paths, the counter update precedes the other direct record writes. Bytes 6 and 7 are not directly written by the halfword store. No byte-order-independent claim about preservation of the containing word’s numeric upper half follows.

No rollback is shown if a later access or dependency fails.

### Dependency effects

D-01 is called once before the owner-like-field tests. D-02 is called once on each normally progressing branch:

- After the record writes on either direct-update path.
- Before request initialization and submission on the unequal path.

“Entry” and “exit” describe call placement only. They do not establish lock operations, interrupt control, or any other synchronization guarantee.

No dependency is assumed to preserve globals, record contents, or unrelated memory because its direct result is unused.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless otherwise stated, assume valid storage, supported arithmetic, normally returning dependencies, and no dependency or external modification of relevant state.

### Initially zero owner-like field

Given an owner-like field of zero, a counter of seven, and a word of decimal 23 reached through the captured pointer:

- The counter becomes eight.
- The owner-like field becomes 23.
- The addressed 16-bit storage beginning at offset 4 receives one.
- Bytes 6 and 7 are not directly changed by that store.
- D-02 runs after those writes.
- F-c81f7910921f is not called.
- The function returns zero.

No particular resulting 32-bit value at offset 4 is required without the prior contents and byte order.

### Matching nonzero owner-like field

Given an owner-like field of 23 on both relevant reads, a comparison word of 23, a counter of seven, and a signed 32-bit value of four at offset 4:

- The counter becomes eight.
- Conversion to signed 16-bit produces four.
- Addition produces five.
- The 16-bit store beginning at offset 4 writes five.
- The function does not directly rewrite the owner-like field.
- The function returns decimal 10.

Under conventional little-endian representation, the containing word becomes five. Under conventional big-endian representation, it becomes hexadecimal 00050004. These alternatives illustrate why incrementing the containing word’s numeric low half is not an unconditional contract.

### Conversion-dependent boundary

Suppose the matching path reads decimal 65535 from the signed 32-bit field at offset 4.

If the target’s narrowing conversion maps that value to signed 16-bit −1:

- Addition produces zero.
- The addressed halfword receives zero.
- The function returns decimal 10.

With conventional little-endian representation, the containing word then becomes zero. With conventional big-endian representation, it remains hexadecimal 0000FFFF because the addressed first two bytes were already zero.

Without the stated conversion and byte-order conditions, neither outcome is required.

### Unequal owner-like field

Given a nonzero owner-like field unequal to the comparison word and selector five:

- D-02 runs before request initialization.
- At submission, request words in increasing offset order are 14, zero, five, one, and zero.
- If F-c81f7910921f writes decimal 37 to the result word, the function returns 37.
- If it leaves that word unchanged, the function returns zero.

### Zero assigned owner-like value
