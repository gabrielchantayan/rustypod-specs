# F-918901543e8e

## Purpose

F-918901543e8e retrieves a pair of 32-bit values associated with a selected record and one of four supported entries. One returned value is formed by adding a record-specific value to an entry-specific value; the other is copied from the preceding 32-bit field of that entry.

The function reports success or an unsupported entry selector through a 32-bit return value. It does not explicitly validate the record selector, the output address, or the addresses obtained from the selected record.

The apparent intent is a small lookup with a record-dependent adjustment. The meaning of the records, entries, adjustment, and returned pair is not established.

## Interface

The recovered interface has three inputs and one return value:

| Component | Recovered representation | Role |
|---|---|---|
| Record selector | Signed 16-bit integer | Selects a record relative to a globally supplied base address. |
| Entry selector | Unsigned 32-bit integer | Selects one of four entries when its value is less than four. |
| Output address | Address of writable 32-bit integer storage | Receives two consecutive 32-bit values on success. |
| Return value | 32-bit quantity | Indicates success or an unsupported entry selector. |

The output layout is:

| Byte offset from output address | Width | Successful result |
|---|---|---|
| 0 | 32 bits | Record adjustment plus the selected entry’s field at entry-region offset 0xA48. |
| 4 | 32 bits | The selected entry’s field at entry-region offset 0xA44. |

The output therefore requires eight writable bytes on the successful path. The function does not read the existing output contents as output contents. Aliasing with its input structures can nevertheless make those existing locations relevant to later reads.

The return values are:

- **0x00000000:** successful completion of both output stores.
- **0xFFFFFF05:** entry selector outside the accepted range. This bit pattern is −251 if interpreted as a signed 32-bit integer. No symbolic error name is established.

The record selector is signed. Negative values are not rejected. Their use selects addresses before the global base, rather than producing the explicit unsupported-selector status.

The entry selector is unsigned. Consequently, a bit pattern such as 0xFFFFFFFF is rejected; it does not select an entry before entry zero.

## Behavior

### Record selection

The function obtains a base address from global state and forms a selected-record address using a stride of **0x18C bytes**, or **396 bytes**, per record-selector unit.

The signed 16-bit record selector determines displacement in either direction from that base. The multiplication by 396 fits within a signed 32-bit integer throughout the signed 16-bit input range. This does not establish that adding the displacement produces a valid address.

The shown sequence forms this selected-record address before testing the entry selector. Formation of the address is distinct from dereferencing the selected record: an unsupported entry selector does not proceed to the record-field reads.

There is no record-count check, null-base check, or negative-selector check.

### Entry-selector rejection

Entry-selector values **4 through 0xFFFFFFFF**, inclusive, return **0xFFFFFF05**.

On this path, the supplied representation shows:

- No read of the selected record’s fields.
- No read of an entry field.
- No store through the output address.

The global-base access and selected-record address formation precede this rejection. The behavior should therefore not be described as a rejection path that necessarily touches no global state.

### Successful lookup

Entry-selector values **0, 1, 2, and 3** enter the successful path.

The selected record contains at least two relevant 32-bit fields:

| Byte offset within selected record | Observed use |
|---|---|
| 0 | Supplies the base address used to locate entry fields. |
| 4 | Supplies the adjustment added to the first output value. |

The entry selector contributes a displacement of **0x14 bytes**, or **20 bytes**, within the region addressed by the record’s first field.

Relative to the address stored in that first record field, the two source-field offsets are:

| Entry selector | Source for second output | Source contribution to first output |
|---|---|---|
| 0 | 0xA44 | 0xA48 |
| 1 | 0xA58 | 0xA5C |
| 2 | 0xA6C | 0xA70 |
| 3 | 0xA80 | 0xA84 |

Only these two 32-bit fields are read for the chosen entry. The 20-byte stride does not establish the contents or purpose of the other bytes between corresponding fields.

The observable sequence in the supplied representation is:

1. Read the selected record’s first 32-bit field and use it to establish the selected entry address.
2. Obtain the record’s adjustment field and the selected entry’s field at offset 0xA48.
3. Store their sum into output offset 0.
4. Read the selected entry’s field at offset 0xA44.
5. Store that value into output offset 4.
6. Return zero.

The supplied expression does not establish an evaluation order between the adjustment read and the entry-field read used in the sum. Both precede the first output store. A contract requiring either of those two reads to occur first would exceed the evidence.

The selected entry address is established before either output store. The representation does not reload the record’s first field between the stores.

### Arithmetic boundaries

The entry displacement ranges from zero through 60 bytes on the accepted path, so its multiplication by 20 does not overflow a 32-bit integer.

The returned sum has a 32-bit destination. There is no explicit saturation, overflow check, or overflow-status branch. However, the recovered representation uses signed integer operations for relevant values. Its text alone is insufficient to define signed-overflow semantics for a portable reimplementation.

For operands whose mathematical sum is representable as a signed 32-bit integer, the successful result is established without that ambiguity. For sums outside that range, wraparound is not asserted as a verified requirement.

Address additions likewise have no explicit overflow handling. Validity of the resulting addresses is a caller/environment precondition for ordinary successful behavior.

## Side effects

On ordinary successful completion, the function writes exactly two consecutive 32-bit output locations, in increasing output-address order.

It makes no explicit writes to global state or selected-record storage. If the output aliases those locations, its output stores can modify them indirectly.

Aliasing is not checked or prohibited by the shown body. In particular:

- The first output store occurs before the source read for the second output.
- If output offset 0 aliases the second output’s source field, that later read can observe the newly stored first result.
- If the output overwrites the record’s first field, the selected entry address has already been established and is not explicitly recomputed.
- If the output overwrites the adjustment field, the adjustment used for the first result has already been read.

These observations describe the shown sequence, not a general guarantee for volatile memory, concurrent mutation, or all language-level aliasing models.

There is no allocation, deallocation, ownership transfer, or explicit synchronization. The output storage remains caller-supplied. The function does not retain its address in the shown body.

Memory-access failure is not converted into the unsupported-selector return value. If a source read or output store faults, ordinary completion is not established. In particular, failure after the first store need not leave the output unchanged.
