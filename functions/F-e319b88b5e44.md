# F-e319b88b5e44

## Purpose

F-e319b88b5e44 conditionally transforms an input value into an output destination. Its visible control flow recognizes the numeric marker `0x25`, conventionally `%`, and can replace that marker followed by two accepted input units with one accumulated value.

The behavior resembles percent-escape decoding, but that interpretation is not a complete contract. Acceptance of an escape component depends on a classification table, and its numeric contribution comes from a separate dependency. Neither dependency’s contents or full semantics are established here.

Two materially different paths exist:

- If an initial search returns exactly `-1`, the function delegates directly to F-46f0b3cb316e.
- Otherwise, it traverses the input through a cursor, builds a result, delivers that result through F-b287fa5e8a41, and then invokes F-2f51066133e0 on the builder.

The function has no explicit return value or explicit error result.

## Interface

### Arguments

The function accepts two 32-bit values:

1. **Input value.** Passed to the initial search dependency, to the cursor-producing dependency when transformation is selected, and to the direct-path dependency otherwise.
2. **Output destination.** Passed as the first argument to either output dependency.

Their concrete types are not established. The visible operations do not establish that either argument is a raw character pointer, a string object, an owned allocation, or a nullable handle.

### Result

There is no returned data value. Any delivered result is observable through the output destination and the called dependencies.

There is no explicit success flag, length return, exception translation, or recovery path in this function. Dependency-specific failures and abnormal control transfers remain outside the established contract.

### Widths and representation

The visible representation uses:

- 32-bit input and output argument values.
- A 32-bit cursor slot whose address is supplied to the input-reading dependency.
- 32-bit values returned by input reading and passed to the append dependency.
- A 32-bit unsigned accumulator.
- An 8-bit component counter.
- A Boolean pending-marker state.
- A 32-bit builder word used as the base for an indirect operation lookup.
- A 32-bit builder field tested for nonzero and later supplied to the output dependency.

The numeric arithmetic described below is 32-bit unsigned arithmetic, with wraparound before the stated masks are applied.

### Preconditions and dependency requirements

The transformed path requires the constructor dependency to establish usable builder state. The visible function does not independently initialize every builder field before reading it.

The classification table must be readable at offsets from `0` through `255`. Input units are reduced to their low byte for table indexing.

For a nonzero builder count field, the builder’s leading word must support an indirect operation lookup at byte offset `0x40`, and the resulting callable must accept the builder address and numeric zero.

These are access requirements implied by the visible operations, not evidence of argument validation. The function contains no explicit null, bounds, or builder-integrity checks.

## Behavior

### 1. Select the path

The first dependency call is F-a4621b603aad with:

1. The input value.
2. Numeric marker `0x25`.
3. Numeric zero.

Only a return value of exactly `-1` selects the direct path.

On that path, F-46f0b3cb316e receives the output destination followed by the input value. The function then returns. No builder construction, cursor creation, transformed-path output call, or builder-finalization call is visible on this path.

Any other search result selects transformation. The returned position or value is not otherwise used: it neither establishes the cursor position nor limits traversal. The subsequent input sequence is determined by the cursor dependencies.

### 2. Construct transformation state

The transformed path calls F-e194f3fbdfaa with the address of local builder storage.

Through the pointer returned by that call, it then performs two writes in order:

1. At byte offset `0`, it writes a 32-bit value read from a global slot.
2. At byte offset `16`, it writes numeric zero.

The source does not independently prove that the returned pointer equals the builder address supplied to the constructor. Later operations use the supplied builder address, not the returned pointer.

Next, F-44362605ab79 receives the input value. Its result is stored in the cursor slot.

The local decoding state starts with:

- No pending marker.
- Component counter equal to zero.
- Accumulator equal to zero.

### 3. Read input units

Each iteration calls F-d3922c7fe0ec with the cursor-slot address.

A returned value of zero terminates traversal immediately. Zero is therefore a control sentinel at this interface; it is not appended as an ordinary input unit. A zero value produced by decoding, however, is passed to the append dependency.

For every nonzero returned unit, processing depends on whether a marker is pending.

### 4. Process ordinary input

When no marker is pending:

- A unit equal to the full 32-bit value `0x25` starts a pending escape. The accumulator and component counter are reset to zero. The marker itself is not appended.
- Every other unit is passed unchanged to F-a03b19bdffef with the builder address.

Marker recognition uses full-width equality. A larger value whose low byte is `0x25` does not start an escape.

### 5. Classify a pending component

When a marker is pending, the function reads the global classification-table base and inspects the byte indexed by the current unit’s low eight bits.

The unit is accepted as a component if and only if bit `0x20` is set in that table byte.

This classification occurs before any fallback emission for the current unit. It does not itself require that the full unit be an ASCII digit, letter, or byte-sized value.

#### Accepted component

For an accepted unit, F-6f56bb4abd11 receives the full 32-bit unit, not merely the low byte used for classification.

The accumulator is updated in this order:

1. Retain the accumulator bits selected by `0x0FFF0FFF`.
2. Multiply that value by `16`, with 32-bit wraparound.
3. Add the conversion dependency’s 32-bit result, interpreted by its bit pattern, with 32-bit wraparound.
4. Apply the mask `0xFFFEFFFF`, clearing bit 16.

The 8-bit component counter is then incremented.

After the first accepted component, no value is appended, and the marker remains pending.

After the second accepted component, the updated accumulator is passed to F-a03b19bdffef, and the marker-pending state is cleared.

The visible state machine permits at most two accepted components per pending marker. Although the counter has an 8-bit representation, normal execution of this control flow cannot reach counter wraparound.

The function does not mask the decoded result to eight bits. Byte-sized results follow only under additional assumptions about the classification and conversion dependencies.

#### Rejected component

For a unit whose classification byte lacks bit `0x20`, the function emits fallback content through separate append calls:

1. Append numeric `0x25`.
2. If one accepted component preceded this rejection, append a value reconstructed from the accumulator.
3. Append the current rejected unit unchanged.
4. Clear the marker-pending state.

The reconstruction in step 2 uses an unsigned comparison:

- If the accumulator is less than `10`, add `0x30`.
- Otherwise, add `0x37`.

That addition wraps at 32 bits, after which `0xFFFEFFFF` clears bit 16.

Consequently, with conventional hexadecimal conversion results, a previously accepted lowercase component is reconstructed in uppercase. More generally, the reconstructed value is governed by the arithmetic above; it is not guaranteed to be a valid character or an exact copy of the original component.

The rejected unit is not reconsidered as the start of another escape. Under a classification table that rejects `%`, encountering `%` while a marker is pending appends it as fallback content rather than opening a new pending sequence.

### 6. Handle end of input

A zero returned by the reader exits the loop without flushing pending state.

Therefore:

- A marker immediately before termination is discarded.
- A marker followed by one accepted component immediately before termination is discarded together with that component.
- Content already appended remains available for final delivery.

There is no visible error report for either truncated form.

### 7. Deliver and finalize

After traversal, the function first reads a 32-bit fallback value from a global slot.

It then tests the builder’s 32-bit field at byte offset `4`:

- If the field is zero, the fallback value remains the selected output value.
- If the field is nonzero, the function obtains an operation through the builder’s leading word at byte offset `0x40`, then invokes that operation with the builder address and numeric zero. Its return value replaces the selected output value.

F-b287fa5e8a41 is then called with:

1. The output destination.
2. The selected output value.
3. The builder field at byte offset `4`.

The field used for the third argument is read after the optional indirect call. It is not guaranteed to equal the earlier value that selected that call: the indirect operation receives the builder address and may modify builder state.

Finally, F-2f51066133e0 receives the builder address. On normal return from that dependency, the function returns.

## Side effects

### Observable ordering

The direct path has this visible call order:

1. Search.
2. Direct output delegation.

The transformed path has this visible sequence:

1. Search.
2. Builder construction.
3. Global initializer read and builder-related writes.
4. Cursor creation.
5. Repeated input reads, with classification reads, conversion calls, and append calls as required.
6. Global fallback read.
7. Builder count test.
8. Optional indirect builder operation.
9. Output delivery.
10. Builder finalization.

Within rejected-component handling, the marker append precedes any reconstructed-component append, which precedes the rejected-unit append.

No atomicity, rollback, or transactional output guarantee is visible. In particular, failure or abnormal termination during a dependency call need not undo earlier effects.

### Global reads

Three categories of global data are directly read:

- A builder initialization value after construction.
- A classification-table base for each input unit examined while a marker is pending.
- An output fallback value after input traversal.

The function does not visibly write those global slots.

Their values must not be assumed invariant across dependency calls. The classification base is consulted during pending-component processing rather than captured once before the loop. The output fallback is obtained after traversal rather than before it.

### Ownership and lifetime

Local builder and cursor storage are passed by address to dependencies.

The finalization call occurs after output delivery on the transformed path’s normal control flow. That ordering alone does not establish:

- Whether output delivery copies, retains, consumes, or merely observes its second argument.
- Whether the indirect builder operation allocates, transfers, or exposes storage.
- Whether finalization frees memory.
- Whether the constructor returns the same storage address it receives.
- Whether dependencies retain supplied addresses.

A compatible dependency contract must make the delivered result valid despite the subsequent finalization call. The mechanism is unknown.

## Acceptance examples

These are conditional acceptance examples derived from static control flow, not executed tests.

For character examples below, assume the cursor emits the displayed character values followed by zero; the classification table accepts exactly conventional hexadecimal digits; conversion returns values from `0` through `15`; and append operations record their supplied values in order.

### Direct delegation

If the search returns `-1`, F-46f0b3cb316e must receive the destination and original input. The transformed-path constructor, reader, output delivery, and finalization calls must not be invoked by this function.

### Complete escape

For input `A%41B`, the append argument sequence must be:

- `0x41` for the initial `A`.
- `0x41` from the two accepted escape components.
- `0x42` for `B`.

No marker append occurs for the completed escape.

### Decoded zero

For input `%00X`, append receives zero from the completed escape, followed by `0x58`.

The emitted zero does not terminate traversal. Only a zero returned by the reader does so. Whether the builder can preserve an embedded zero is dependency-defined.

### Invalid first component

For input `%G`, append receives `0x25`, then `0x47`. No conversion call is made for `G` under the stated classification assumption.

### Invalid second component and normalization

For input `%aZ`, append receives `0x25`, `0x41`, then `0x5A`.

The accepted lowercase `a` is reconstructed as uppercase `A`; exact preservation of malformed input is therefore not guaranteed.

### Truncated escape

For input `Q%`, append receives only `0x51`.

For input `Q%A`, append also receives only `0x51`.

Both cases still proceed to transformed-path output delivery and finalization.

### Repeated marker

For input `%%41`, append receives `0x25`, `0x25`, `0x34`, and `0x31`.

The second marker is handled as the rejected component of the first pending marker, not as the start of a new escape.

### Full-width distinction

If a reader returns `0x125` while no marker is pending, append receives `0x125` unchanged.

While a marker is pending, that same value is classified using table index `0x25`. If accepted, conversion receives the full value `0x125`.

### Count mutation during output preparation

If the count field is nonzero before the indirect operation and that operation changes it to zero, F-b287fa5e8a41 receives the indirect operation’s result together with a zero count. Selection of the indirect path is not repeated.
