# F-03409a4f0817

## Purpose

F-03409a4f0817 constructs two related tables in an existing destination state using values supplied through stream-like dependencies:

- A first table of 32-bit position-like values, with one more entry than a decoded unsigned 16-bit terminal index.
- An optional row-major second table of 32-bit values, each derived by shifting a supplied value left by two bits.

**Established static behavior:** The function invokes an object-provided callback, captures a base value, requests header decoding, publishes two counts, validates the header, and conditionally constructs the tables. Destination updates are incremental. This function contains no explicit rollback of earlier writes and no explicit allocation cleanup on failure. Dependency implementations are unavailable, so this does not establish that dependencies leave fields, allocations, or stream operations unchanged.

**Inferred intent:** The first table appears to convert relative offsets into absolute positions. The second appears to expand compact entries into four-byte-scaled values. “Allocation,” “preparation,” “repositioning,” and “release” below describe apparent dependency roles, not established ownership or stream contracts.

## Behavior

### Initial callback and base acquisition

After capturing the stream, destination, and context, the function invokes the object-provided callback with:

1. The input object address.
2. The value read from the first opaque global data location.
3. The captured stream address.
4. The address of four bytes of local scratch storage.

The scratch storage is not visibly initialized before the call. This function does not subsequently consume its contents.

A nonzero callback result is returned immediately. No direct destination-field write by this function precedes that return. The callback’s own writes and other effects remain unknown.

After a zero callback result, F-b03b1199772e receives the captured stream. Its 32-bit result is retained as the base used in later address and value calculations. No error check is applied to that result.

Only after F-b03b1199772e returns does the function read the second opaque global argument and call F-de70a5256fd2 with the captured stream and that argument. A nonzero result is returned without publishing the decoded counts.

The callback and F-b03b1199772e must not be assumed to preserve the second global’s contents.

### Count publication and header validation

After a zero decoding result, direct destination writes occur in this order:

1. The decoded unsigned 16-bit row count is zero-extended and stored at `0x18`.
2. The decoded unsigned 16-bit terminal index is zero-extended and stored at `0x20`.

Validation follows these writes.

First, the marker must equal `0x00010000`. Only when it matches does the function read the address at destination `0x08`, read the 32-bit word at that address, and compare its low 16 bits with the decoded column count.

The comparison ignores the word’s upper 16 bits. A marker mismatch bypasses this pointer traversal entirely.

Failure of either condition sets the returned status to **8**. Neither allocation-like call is made on this path. There is no explicit restoration of the two published count fields.

### First-table allocation and preparation

For a valid header, F-6dd003795db7 receives six arguments:

1. The captured context.
2. `4`.
3. Zero.
4. The decoded terminal index plus one.
5. Zero.
6. The address of the local status word.

The fourth argument is based on the decoded local terminal index, not a fresh destination-state read. It ranges from **1 through 65,536**.

The returned 32-bit value is stored at destination `0x24` before the status word is checked. A nonzero status ends processing with that status. This function does not explicitly undo the published result or dispose of it.

On zero status, the function rereads destination `0x20` and adds one to determine the preparation count. It then calls F-d036abe1e536:

- With twice that count when flags bit zero is clear.
- With four times that count when flags bit zero is set.

Other flag bits do not influence this branch.

A nonzero preparation result is returned immediately. No first-region release-like call or second-table processing occurs afterward on that path.

### First-table population

After successful preparation, the local status is explicitly set to zero.

Population starts at index zero. Before each iteration, the unsigned 32-bit index is compared with the current unsigned terminal index at destination `0x20`; an entry is produced while the index is less than or equal to that live bound.

For each entry:

- **Compact mode, bit zero clear:** F-7efb5338f0fa receives the stream. The function retains only the result’s low 16 bits and multiplies that unsigned quantity by two.
- **Full-width mode, bit zero set:** F-77339711215b receives the stream. Its full 32-bit result is used as the displacement without the compact-mode multiplication.

The displacement, decoded base displacement, and captured base are added to form the stored 32-bit value.

The scalar dependency is called before the destination-table pointer is fetched for that entry’s store. The pointer at destination `0x24` is therefore live state, not a permanently retained allocation result. The index advances by one after the store.

After the loop terminates, F-9787e15c337d receives the stream. Its returned value, if any, is ignored.

### Optional second table

After the first release-like call, the function reads destination `0x18`. If it is zero, the second-table branch is skipped. This function performs no direct write to destination `0x1c` on that branch.

For a nonzero row count, F-6dd003795db7 is called again with the captured context and the same fixed arguments `4`, zero, zero, and the status-word address. Its element-count argument is:

**current destination row count × decoded column count**

The returned value is stored at destination `0x1c` before status inspection.

If allocation status is zero, the following gated sequence occurs:

1. F-e40a3ceddab2 receives the stream and the sum of the decoded second-table location and captured base.
2. If that returns zero, F-d036abe1e536 receives the stream and twice the decoded column count multiplied by the newly read destination row count.
3. If preparation also returns zero, population begins.

A nonzero allocation status, repositioning result, or preparation result prevents subsequent stages and becomes the returned status. No second-region release-like call occurs on these failure paths.

Population uses increasing row indices and, within each row, increasing column indices. The outer loop compares its unsigned index against the current row count at destination `0x18`. The column bound is the decoded unsigned 16-bit column count.

Each cell calls F-7efb5338f0fa and stores the supplied 32-bit value shifted left by two bits. There is **no explicit low-16-bit mask** here.

The element index is:

**row × decoded column count + column**

The byte displacement is four times that element index. The second-table pointer is fetched from destination `0x1c` for each store, after the scalar dependency returns.

F-9787e15c337d is called after the loops, including when successful preparation is followed by zero cell iterations. Its result is ignored. The function then returns the local status.

### Widths, arithmetic, and changing bounds

Decoded counts and flags are unsigned 16-bit values. Published counts, loop indices, addresses, table elements, and the visible arithmetic representation are 32-bit.

With relevant state preserved by dependencies:

- First-table allocation count is 1–65,536.
- First-table preparation amount is at most 131,072 in compact mode or 262,144 in full-width mode.
- Second-table element count can reach **4,294,836,225**, or 65,535 squared.
- Twice that maximum exceeds the unsigned 32-bit range.
- Four-byte storage and indexing can exceed a 32-bit address space.

No explicit overflow detection, saturation, dimension rejection, or capacity reconciliation is present. Unsigned 32-bit arithmetic wraps at its width; the supplied representation does not establish a portable result for every signed-looking overflow or left shift.

Allocation counts, preparation counts, and loop bounds are not all snapshots of the same state. Dependency mutation can make them disagree. An unsigned terminal bound of `0xffffffff`, for example, prevents the first loop’s comparison from terminating through ordinary index advancement because the index wraps. The original decoded 16-bit bound cannot itself have that value.

## Side effects

The function makes incremental writes rather than an explicit transaction:

- Counts are published before validation.
- Each allocation-like result is published before checking its status.
- Table elements are written individually in traversal order.
- There is no visible initialization of entries not reached.
- Existing table results are not explicitly released before replacement.
- There is no explicit rollback or allocation cleanup on any failure path.

These are properties of this function’s visible actions. They do not establish that dependencies preserve previous writes, refrain from freeing memory, or leave stream effects in place.

A zero live row count skips direct second-table publication. It does not guarantee that the preexisting second-table field is unchanged by earlier dependencies.

Release-like calls occur after successful preparation and completed traversal, not after preparation failure. Their names here do not establish that they release table storage or provide error cleanup.

The callback and all dependencies may have unknown effects on globals, reachable destination storage, stream state, or memory ownership. The later read of the second opaque global specifically allows intervening effects to influence the decoding argument.

3. **Invalid marker.** Decoded row count 3 and terminal index 4 are published before an invalid marker produces status 8. The comparison pointer at destination `0x08` is not traversed.

4. **Low-half validation.** Column count 2 matches comparison word `0xABCD0002`. Comparison word `0x00010003` fails and produces status 8 after count publication.

6. **Single full-width entry.** Terminal index zero still requests one element. With flags bit zero set, preparation requests four units. Base 1,000, base displacement 40, and displacement 12 produce 1,052.

7. **Failed first preparation.** A preparation result of 23 is returned immediately after the first allocation result has been published. No release-like call or second-table allocation follows. This function performs no explicit rollback or disposal.

8. **Row-major second table.** Two rows and three columns request six elements and twelve preparation units. Supplied values 1 through 6 produce the stored sequence 4, 8, 12, 16, 20, 24.

9. **No second-table truncation.** A second-table scalar result of `0x00010001` produces `0x00040004` when shifted in the represented width without overflow. It does not produce 4.

11. **Nonzero rows, zero columns.** The second branch requests zero elements. If allocation, repositioning, and zero-amount preparation succeed, no cells are read or stored, but the release-like call still occurs.

12. **Second repositioning failure.** Result 31 is returned after second-table publication. No second preparation, cell traversal, or second release-like call follows.
