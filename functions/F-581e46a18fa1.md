# F-581e46a18fa1

## Purpose

F-581e46a18fa1 prepares shared transaction state, submits a bounded request, polls for completion, checks a separate transfer result, and conditionally invokes a copy dependency.

Its established behavior is to:

- Accept unsigned requested counts from 0 through 16, inclusive.
- Perform four transaction-state writes before preparation and submission dependencies run.
- Construct a command from selected bits of the selector and count.
- Poll status until completion is observed or a timeout dependency returns nonzero.
- Write a completion marker before checking the transfer result.
- Invoke the copy dependency only when the transfer-result check returns nonzero.
- Return a 32-bit value of 0 or 1 on its explicit return paths.

**Inferred intent:** diagnostic labels suggest a multiple-register read constrained by FIFO capacity. This does not establish the device protocol, count units, memory mapping, or dependency semantics.

A return value of 1 establishes successful traversal of the caller’s checks and return from the copy dependency. It does not independently establish that valid data reached the destination.

## Behavior

### Entry and count limit

The global context reference is read at entry and retained for later context accesses. This read precedes count rejection.

The requested count is compared as an unsigned 32-bit value against 16:

- Counts 0 through 16 proceed.
- Counts 17 through `0xFFFFFFFF` take the rejection path.

On rejection, F-1b7fa166ef25 receives the count-limit diagnostic, after which the function returns 0 if the diagnostic call returns.

There are no direct transaction-state writes or submission calls on this path. The diagnostic’s own effects remain unknown.

### Transaction preparation

For an accepted count, the global context reference is read again to obtain the transaction-state reference at context offset `0x04`. The supplied body does not use only the context reference retained at entry for this lookup.

The following direct operations occur in order:

1. Write the original requested count to transaction-state offset `0x48`.
2. Write 1 to transaction-state offset `0x4C`.
3. Read the value at offset `0x08` of the retained context and write it to transaction-state offset `0x44`.
4. Write 3 to transaction-state offset `0x04`.
5. Call F-1194c6159740 without explicit arguments.

The state reference used for these four writes is obtained once for this setup sequence. The context supplying the offset-`0x08` value is the one retained at entry. If the global context reference changes between the two reads, those references can identify different contexts.

The setup writes precede F-1194c6159740. They are not guarantees about field contents after that call or any later dependency. Such calls may overwrite fields, change references, or invalidate storage.

### Command construction and submission

F-6e46c43c3113 receives four arguments in this order:

1. The global 32-bit submission value.
2. A constructed 32-bit command word.
3. Zero.
4. The value read at offset `0x14` of the retained context.

These submission arguments are obtained after F-1194c6159740 returns. The source does not establish a relative evaluation order between the separate global and context reads used to prepare arguments to this call.

The command word contains:

- Requested-count bits 2 through 7 in command bits 2 through 7.
- Register-selector bits 2 through 7 in command bits 18 through 23.
- Zero in all remaining bits.

The selector is masked before being shifted left by 16 bits. Its maximum contribution is therefore `0x00FC0000`; selector high bits do not enter the command. The count contribution occupies disjoint bits, so combining the contributions does not introduce a carry.

For accepted counts:

| Requested count | Command’s count contribution |
|---:|---:|
| 0–3 | `0x00` |
| 4–7 | `0x04` |
| 8–11 | `0x08` |
| 12–15 | `0x0C` |
| 16 | `0x10` |

No multiple-of-four constraint is enforced. Discarding the count’s low two bits affects only the command: the state write and any later copy call receive the original count.

If submission returns zero, F-1b7fa166ef25 receives the submission-failure diagnostic followed by the original selector and count. The function then returns 0. No waiting calls follow on this path.

Any nonzero submission result enters the wait path. No particular nonzero success code is required.

### Waiting

After successful submission, the function:

1. Reads offset `0x14` of the retained context again and saves that value as the wait parameter.
2. Calls X-01 without explicit arguments.
3. Retains its 32-bit result as the wait origin and as the first status-query argument.

The wait parameter is a distinct, post-submission sample. It need not equal the offset-`0x14` value supplied to submission.

Each iteration calls F-849e39a4f74b and examines bit 0 of its 32-bit result:

- The first query receives the X-01 result.
- Every subsequent query receives zero.
- Other result bits do not affect this function’s completion decision.

When bit 0 is clear, X-02 receives the saved wait origin and saved wait parameter, in that order.

- Zero from X-02 permits another status query.
- Any nonzero result selects the timeout diagnostic through F-1b7fa166ef25, followed by return 0.

When bit 0 is set, the function proceeds directly to completion handling without calling X-02 for that iteration. Thus completion takes precedence over checking timeout within that iteration.

There is no explicit delay, sleep, iteration limit, or local elapsed-time arithmetic. If status never reports completion and X-02 always returns zero, the loop has no visible local termination condition.

### Completion and copy

After observing status bit 0 set, the function:

1. Reads the transaction-state reference at offset `0x04` of the retained context.
2. Writes 1 to offset `0x38` of that state object.
3. Calls F-472f505654a1 without explicit arguments.

The completion-state reference is read afresh. It is not guaranteed to identify the object used during setup.

If F-472f505654a1 returns zero, F-1b7fa166ef25 receives the transfer-error diagnostic and the function returns 0. The completion write occurred before both calls; neither its persistence nor the continued validity of its target is established after those calls.

For any nonzero transfer-result value, F-b490bea51f76 receives:

1. The original destination argument.
2. The global 32-bit source value with bit 31 forced to 1.
3. The original requested count.

The source value is read for this call after the transfer-result dependency returns. Forcing bit 31 uses bitwise OR with `0x80000000`, not arithmetic addition. An already-set bit 31 remains set; there is no carry or widening.

After the copy dependency returns, the function returns 1 without inspecting any copy result.

## Side effects

### Earlier writes and lack of explicit rollback

The function performs no explicit rollback of its setup writes on submission failure, timeout, or transfer-result failure. It also performs no explicit rollback of its completion write after a failed transfer-result check.

This establishes operation history, not final state:

- On a submission-failure path, the setup writes occurred before F-1194c6159740, submission, and the diagnostic call.
- On a timeout path, the setup writes occurred before preparation, submission, timing, polling, and diagnostic dependencies.
- On a transfer-result-failure path, the completion write occurred before the transfer-result and diagnostic dependencies.

Any of those dependencies may change fields, replace references, or invalidate storage. Resulting field contents and object validity after intervening calls are unknown without their contracts.

The function does not explicitly clear offset `0x38` during setup and does not directly write it on submission failure or timeout. Dependencies may nevertheless modify that field.
