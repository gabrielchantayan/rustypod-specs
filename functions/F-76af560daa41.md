# F-76af560daa41

## Purpose

F-76af560daa41 conditionally removes a node from a pointer-linked structure, repairs selected links and color metadata, places the removed node on a container-associated chain, decrements a 32-bit count, and writes a one-word result.

The established behavior is a sequence of memory accesses and dependency calls. The structure resembles a red-black tree with a header holding the root and extrema. That interpretation is inferred intent, not an independently established guarantee. In particular, the repair logic has details that must not be replaced with a conventional red-black-tree deletion algorithm.

The operation has two principal outcomes:

- A nonzero result from F-ae31a5744f21 bypasses removal and returns the container’s subsequently read header word.
- A zero result invokes F-10b500e14762, performs structural mutation, chains the removed node through its offset-12 field, decrements the count, and returns the first temporary word as left by the dependencies.

No runtime tests have been performed.

## Interface

### Arguments and result

The function receives three arguments:

1. **Result destination:** an address at which one 32-bit word is written on normal completion.
2. **Container address:** a 32-bit address-bearing value identifying a mutable container.
3. **Node-word address:** an address from which one 32-bit word is initially read. On the removal path, this address is read again after dependency calls to obtain the node to remove.

There is no established scalar return value. The result is delivered through the first argument.

The node-word address is not directly advanced or overwritten by this function. The dependencies receive addresses of temporary copies, not that argument itself. Aliasing and dependency side effects can nevertheless change what a later read observes.

### Established layouts

Offsets are byte offsets. Pointer-bearing fields and other word accesses are 32 bits.

|---|---:|---|
| Container | 4 | Read as the previous head of a chain; later replaced with the removed-node address |

| Container | 20 | 32-bit count, decremented on the removal path |
| Header | 4 | Root pointer |

“Root,” “left,” “right,” and “extreme” describe the consistent structural interpretation of these accesses. No key, payload, ordering comparator, or payload size is established.

The node metadata occupies at least 16 addressable bytes. Bytes 1–3 are not explicitly accessed. Color updates write one byte; ordinary link updates write four bytes. One leaf-detachment branch clears a link using four separate byte writes.

### Preconditions and valid operating domain

Normal completion requires readable and writable memory for every access actually reached. The function does not validate arguments, node membership, pointer alignment, parent-child consistency, count range, or structural acyclicity.

For intended structural behavior, callers must supply:

- A valid container and header.
- A removable node with links consistent with that container.
- Traversal paths that terminate.
- Valid parent and child objects wherever the selected branch dereferences them.
- Dependency behavior compatible with the operation’s temporary words and live structure.

These are requirements for a usable input, not checks performed by the function. The header, root, and extreme pointers are mutable state; the function rereads them rather than treating their initial values as permanent snapshots.

## Behavior

### Initial dependency boundary

The observable order begins as follows:

1. Read the word at the node-word address into a first temporary word.
2. Read the container’s offset-16 word into a second temporary word.
3. Call F-ae31a5744f21 with the addresses of those two temporaries.

The function branches on whether that dependency’s result is zero.

For a **nonzero result**, it rereads the container’s offset-16 word, replaces the first temporary with that value, and writes the first temporary to the result destination. There are no explicit structural writes or count changes on this branch. Effects caused inside the dependency remain possible.

For a **zero result**, it calls F-10b500e14762 with the address of the first temporary. Only after that call does it reread the node-word address to obtain the node to remove.

Consequently, the node examined through the first dependency and the node subsequently removed are not guaranteed to be the same if a dependency changes reachable state. The eventual result word also must not be assumed to equal the original node word or an iterator successor: its value depends on the temporary’s state after the calls.

### Selecting the structural case

The function reads the removal target’s left link first.

- If the left link is null, it reads the right link.
  - A nonnull right link becomes the replacement.
  - If both child links are null, the target is handled as a leaf.
- If the left link is nonnull, it reads the right link.
  - A null right link leaves the left child as the replacement.
  - Otherwise, it follows left links from the right child to find that subtree’s leftmost node. This is the successor used for structural relocation. The successor’s right link becomes the initial replacement.

The node eventually added to the container’s chain is the original removal target, including in the two-child case. The successor is moved structurally; no payload copy is established.

### Removing a leaf

For a leaf, the target’s parent becomes the repair candidate.

If that parent equals the container’s currently read header pointer, the function performs these writes in order:

1. Set the header’s upper-extreme link to the header address.
2. Set the header’s lower-extreme link to the header address.
3. Clear the header’s root link.

This is the empty-structure transition.

Otherwise, the function reads the parent’s left link and checks whether it equals the target:

- If equal, it clears the parent’s left link.
- If unequal, it clears the parent’s right link.

That clear consists of four consecutive zero-byte writes, not one word write.

It then selects the corresponding cached extreme field: lower extreme for a left-link removal, upper extreme otherwise. If that field currently equals the removed target, it is replaced with the parent address. The opposite extreme field is not independently checked in this leaf branch.

### Removing a node with one child

The replacement child’s parent link is first set to the target’s parent.

The function then checks the current header root:

- If the root equals the target, the root becomes the replacement.
- Otherwise, the target’s parent is inspected. Its left link is replaced if it equals the target; otherwise, its right link is replaced.

Cached extrema are handled afterward, lower extreme before upper extreme.

If the lower extreme equals the target:

- With no right child on the target, the lower extreme becomes the target’s parent.
- Otherwise, it becomes the leftmost node reached from the replacement.

If the upper extreme equals the target:

- With no left child on the target, the upper extreme becomes the target’s parent.
- Otherwise, it becomes the rightmost node reached from the replacement.

The tests and traversal reads occur after the preceding link changes. These rules are stated as implemented; they are not generalized into a separate minimum/maximum recomputation.

### Removing a node with two children

The successor is the leftmost node in the target’s right subtree. Its left link is therefore null along the traversed path.

The operation proceeds in this order:

1. Set the original left child’s parent to the successor.
2. Set the successor’s left link to the original left child.
3. Repair the successor’s former position:
   - If the successor was the target’s direct right child, a nonnull replacement child has its parent set to the successor.
   - Otherwise, a nonnull replacement child has its parent set to the successor’s former parent; that former parent’s left link is set to the replacement; the successor receives the target’s right subtree; and that subtree’s parent is set to the successor.
4. Replace the target in the root or in its parent’s appropriate child link with the successor.
5. Set the successor’s parent to the target’s parent.
6. Exchange the successor’s and target’s one-byte color values.

Before that color exchange, a null replacement is changed to the successor address for subsequent repair processing. This is a concrete behavior, not an assumption that a null child is represented by a conventional sentinel.

No cached-extreme write is explicit in this relocation branch.

### Conditional color and structural repair

After detachment or relocation, the function rereads the header pointer.

Repair is entered only when both conditions hold:

- The repair candidate differs from that header.
- The detached target’s current color byte is nonzero.

In the two-child case, the target’s current color is the successor’s former color because of the exchange.

The repair loop first tests whether the candidate is the current root. If not, it reads the candidate’s color. Reaching the root, or observing a color other than exactly 1, ends the loop and leads to writing color 1 to the candidate.

For a nonroot candidate with color 1, the function determines its side by comparing it with its parent’s left link. The opposite child is treated as its sibling.

The established repair cases are:

- **Missing sibling:** write color 0 to the current candidate, move the candidate to its parent, and repeat.
- **Sibling color exactly 0:** write color 1 to the sibling and color 0 to the parent, call a structural dependency, then reread the candidate’s parent and sibling before continuing.
- **Both sibling children null or color exactly 1:** write color 0 to the sibling, move the candidate to its parent, and repeat.
- **Far sibling child null or color exactly 1, with the other-child condition requiring repair:** write color 1 to the near child if present, write color 0 to the sibling, call the opposite structural dependency, and reload the sibling. If this reloaded sibling is null, proceed to final candidate coloring.
- **Final repair:** copy the parent’s color to the sibling, write color 1 to the parent, write color 1 to the far child if present, call a structural dependency, and then write color 1 to the candidate.

“Near” means the sibling child toward the candidate; “far” means the other child.

For a candidate on the left, the parent-level structural dependency is F-b8342e8cae72 and the near-child adjustment uses F-b812ad91de18. For a candidate on the right, those roles are reversed.

The exact byte comparisons matter. “Nonzero” at repair entry and “equal to 1” within repair are not interchangeable. Null child checks are explicit in several cases; they do not establish that arbitrary null candidates are safe.

### Final chain insertion and result

After the structural work and any repair:

1. Read the container’s offset-4 word and write it to the removed target’s offset-12 field.
2. Write the removed target’s address to the container’s offset-4 field.
3. Read the count at offset 20, subtract one, and write the 32-bit result back.
4. Write the first temporary word to the result destination.

Thus, the removed node’s former right-child field becomes a chain link. The function does not explicitly clear its parent or left-child field.

The count has no zero guard, saturation, or reported underflow error. The visible update is a 32-bit decrement; signed-overflow semantics of the original implementation are not independently established by the supplied representation.

## Side effects

The removal path mutates existing objects in place. It may change:

- The root and cached extrema.
- Parent and child links.
- Node color bytes.
- The container’s offset-4 chain head.
- The removed node’s offset-12 field.
- The 32-bit count.
- The result destination.

The result write is last on normal completion, including after the count update. If the result destination aliases mutable structure, that final write can overwrite a preceding structural update. No alias exclusion is checked.

There is no explicit allocation or release operation outside the opaque dependencies. Linking a node into a container-associated chain suggests retention or recycling, but does not establish an ownership transfer, allocator contract, or reclamation policy. The dependencies’ memory-management behavior is unknown.

The operation is not shown to be atomic, synchronized, transactional, or recoverable. If execution fails during a dependency or memory access, no rollback is established. Concurrent mutation can invalidate both structure and the function’s repeated reads.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Unless stated otherwise, assume valid memory, coherent links, nonaliasing result storage, and dependencies whose effects satisfy each example’s premises.

1. **Bypass result**
   - Given F-ae31a5744f21 returns nonzero.
   - The result must equal the container’s offset-16 word read after that call.
   - F-10b500e14762, repair dependencies, chain insertion, and count decrement must not be explicitly performed by this function.

2. **Removing the only node**
   - Given the removal path, a leaf whose parent is the header, and stable dependency-visible state.
   - The header’s upper and lower extrema must become the header address, and its root must become null.
   - Repair must be skipped because its candidate is the header.
   - The target must be prepended to the offset-4 chain, and the count must decrease by one.

3. **Removing a leaf held by its parent’s left link**
   - The parent’s left pointer bytes must be cleared.
   - If the header’s lower-extreme field equals the target, it must become the parent.
   - The parent, not a null child, must be the initial repair candidate.

4. **Replacing a root having only a right child**
   - The child’s parent must become the target’s parent before the header root is replaced.
   - If the lower extreme equals the target, it must be updated by following left links from the replacement.
   - Later chain insertion must overwrite the removed target’s offset-12 field.

5. **Relocating a deeper successor**
   - Given a two-child target whose successor is not its direct right child.
   - The successor’s former parent must receive the successor’s right child in its left link.
   - The successor must receive both target subtrees, with the corresponding parent links updated.
   - The original target, not the successor, must enter the container-associated chain.

6. **Null successor replacement**
   - Given two-child removal and a successor with no right child.
   - The successor address must become the repair candidate before repair entry is evaluated.
   - Acceptance must not require a conventional null-child repair representation.

7. **Zero-colored detached node**
   - Given a detached target whose color at repair entry is 0.
   - Repair must be skipped, but chain insertion, count decrement, and the result write must still occur.

8. **Missing sibling during repair**
   - Given a nonroot candidate of color 1 with no opposite sibling.
   - The candidate must be colored 0 before repair continues at its parent.
   - Replacing this with an ordinary sibling-recolor case would not match the established writes.
