A **five-call group** means one invocation with the arguments described for that group, followed by four invocations with no explicitly displayed arguments. The fifth invocation usually supplies the consumed result.

- The first invocation receives the stated opening arguments.
- The second invocation supplies a value passed to the third.

This terminology describes ordering, not shared dependency identity. Undisplayed arguments are not necessarily absent, zero, or unused.

### Initial word stores and first byte pair

\]

This initial address calculation uses unsigned 32-bit arithmetic.

The first five-call group opens with four displayed arguments: the first argument, the first argument again, the third argument, and the first argument again. Its first target is derived from the incoming control-address register. The group's final result selects a second word destination, four times that result plus `0x14`. The stored value is again the original first argument shifted right by seven.

A five-call group then opens with four times the preceding result. Its final unsigned result supplies both values of the first byte pair.

For each store, the function reads an unsigned selector byte from:

\[
(\text{first argument} \gg 8) + 1.
\]

The destination is the selector value plus `0x11`.

The first store writes the low byte of the result shifted left by two. A five-call group follows, opening with that shifted result. Only afterward does the function reload the selector and store the low byte of the original result masked with `0x3FFFFFFF` and shifted right by twenty.

Thus the first byte exposes original result bits 0–5 in byte bits 2–7; the second exposes bits 20–27. The intervening calls can change the selector, so the destinations need not agree.

### Terminal loop

The represented loop has no exit condition. Each iteration:

- Executes a five-call group opening with the current loop value and the current field shifted right by eight.
- Reloads the selector at the retained terminal lookup address and clears the byte it selects.
- Executes a five-call group opening with the latest result shifted left by two.
- Forms the next loop value by shifting the final result left by two.
- Replaces the field with that same final result shifted left by twenty-six.

## Acceptance examples

These are conditional static consequences, not executed tests.

1. **First observable store.** With first argument `0x80`, the function first stores word value `1` at address `0x214`, assuming writable memory. No dependency precedes it.

2. **Byte extraction and selector reload.** A byte-pair result of `0x12345678` supplies bytes `0xE0` and `0x23`. If the selector changes between reads, those bytes can reach different destinations.

3. **Unsigned selector endpoints.** Selector values zero and 255 select `0x11` and `0x110`, respectively.

4. **Captured global.** If the captured global-derived value is 7 and a dependency subsequently changes its source to 9, both explicit third-argument-based stores still write 7.

5. **Nine-call store boundary.** If a high-byte-propagation nine-call group returns a destination-selecting result, its associated retained-value store occurs before the next five-call group's first invocation. A dependency in that next group observes the store's effects unless some other permitted effect intervenes.

6. **Seven-call separation.** Between the final pair's first and second selector-selected byte stores, all seven stated calls precede the second selector read. A selector change during the seventh call can affect the second destination.

7. **Saved-word extraction.** For first saved word `0xAB123456`, the retained upper sixteen bits are `0xAB12`, the top byte is `0xAB`, and the direct final byte destination is `0x1D`.

8. **Adjacent clear.** If the selector read after the direct byte store selects that store's destination, the subsequent clear leaves that byte zero under ordinary byte-memory behavior.

9. **First loop argument.** If execution reaches the loop, its first opening invocation receives zero as its second displayed argument. A complete iteration additionally requires every invocation and access in that iteration to complete.
