# F-4192a4f2eef8

## Purpose

F-4192a4f2eef8 coordinates preparation, two conversions, an update, and conditional callback dispatch for a caller-supplied object. It also submits an eight-byte temporary region to a finalization boundary on every visible normal-return path.

The established result mapping is:

- A nonzero preparation result is returned unchanged.
- A zero preparation result permits both conversions and the update.
- Any nonzero update result becomes return value **7**.
- A zero update result permits callback dispatch and leads to return value **0**, provided the callback and finalization return normally.

These rules describe the visible call boundaries and control flow. They do not establish transactionality, resource ownership, or the semantic meaning of success within any dependency.

## Interface

### Arguments

The function accepts three arguments in this order:

| Argument | Established use |
|---|---|
| **Object address** | Passed to preparation; used to form two object-relative addresses, read an update argument, and select a callback; passed to that callback. |
| **Preparation input** | A four-byte value forwarded unchanged to F-8748c10b2aa2. |
| **Conversion input** | A four-byte value forwarded unchanged to the first invocation of F-44362605ab79. |

The latter two arguments have no established semantic type beyond their represented width. They must not be assumed to be strings, pointers, lengths, or handles.

### Result

The supplied representation models the result and tested statuses as 32-bit integers:

| Reached condition | Result after finalization returns |
|---|---|
| Preparation returns nonzero | Exact preparation status |
| Preparation returns zero; update returns nonzero | **7** |
| Preparation and update return zero; callback returns | **0** |

Only equality to zero is tested. Negative statuses and positive nonzero statuses take the same branch at each respective boundary.

The result of finalization is not used as a status. No result from the callback is consumed.

### Temporary storage

Two distinct local regions are exposed to dependencies:

- An **eight-byte temporary region**, passed to the initial dependency, preparation, the second conversion, and finalization.
- A **four-byte output region**, whose address is passed to preparation and whose contents later supply two update arguments.

The wrapper does not visibly initialize either region before exposing it to a dependency.

On the continuation path, the four-byte output region is read while constructing the update arguments, **after both conversion calls have returned**. Valid contents are required at those eventual reads. The evidence does not establish that preparation itself initializes the region, that its contents are already valid when preparation returns zero, or that they remain unchanged during conversion.

Preparation receives the output region’s address and could make it reachable to later dependencies. Those dependencies could therefore initialize or modify it through retained or otherwise reachable state. Whether this actually happens is unknown.

The eight-byte region’s size does not establish its representation, alignment requirements, or resource semantics.

### Object-relative layout

Using the supplied model’s four-byte integer elements:

| Byte offset | Established use |
|---|---|
| **0** | Read after update success to obtain the callback dispatch-table base. |
| **536**, or **0x218** | Address supplied as update argument 1. The wrapper does not directly read this region’s contents. |
| **1000**, or **0x3E8** | Four-byte contents supplied as update argument 4; address supplied as update argument 7. |

The offset calculations are **134 × 4 = 536** and **250 × 4 = 1000**. The callback entry is selected at **48 bytes**, or **0x30**, from the dispatch-table base.

These are byte displacements, not a complete object layout. They do not independently establish pointer width, callable-entry width, total object size, or a portable platform ABI.

### Preconditions for defined completion

The wrapper performs no explicit null, bounds, alignment, or dispatch-validity checks. Each reached access requires suitable memory and address validity:

- Dependencies must be able to use the arguments they receive according to their own contracts.
- The four-byte output region must have valid contents when its values are obtained for update.
- The object-relative address calculations and reached reads must be valid.
- Successful update must leave callback-dispatch information usable if execution is to proceed normally.

Invalid memory, invalid callback metadata, dependency faults, and nonlocal exits have no established wrapper-level error mapping.

## Behavior

### Initial call and preparation

The first dependency call is F-576ea5ba1d23 with the address of the eight-byte temporary region. No result from this call is visibly used.

Next, F-8748c10b2aa2 receives:

1. The object address.
2. The preparation input.
3. The address of the four-byte output region.
4. The address of the eight-byte temporary region.

Its result determines whether processing continues.

If preparation returns nonzero:

- Neither conversion occurs.
- Update is not invoked.
- Callback dispatch is not attempted.
- Finalization receives the eight-byte temporary region.
- The exact preparation status is returned if finalization returns normally.

This path does not read the four-byte output region in the wrapper.

A zero preparation result enables further processing. It does not, by itself, prove any particular initialization or ownership guarantee.

### Conversion sequence

After preparation returns zero, F-44362605ab79 is called twice:

1. With the caller’s conversion input.
2. With the address of the eight-byte temporary region.

The first call completes before the second begins. Each result is retained as a four-byte value. Neither result is tested for an error code, null value, range, or sentinel.

The conversion order and the later argument placement differ: the second conversion’s result becomes update argument 3, while the first conversion’s result becomes update argument 6.

The calls are therefore not interchangeable. Their order can affect results or shared state, including state reachable through addresses previously exposed by preparation.

### Update argument construction

After both conversions return, F-963a3abbb80c receives seven arguments:

| Position | Value |
|---|---|
| **1** | Address at object byte offset 536 |
| **2** | Four-byte value obtained from the output region |
| **3** | Result of converting the eight-byte temporary region |
| **4** | Four-byte contents obtained from object byte offset 1000 |
| **5** | Four-byte value obtained from the same output region used for argument 2 |
| **6** | Result of converting the caller’s conversion input |
| **7** | Address at object byte offset 1000 |

The output-region accesses occur after both conversions. There is no established earlier snapshot of that region. Both argument positions use the same storage, and the wrapper shows no intervening write or transformation. With stable contents during argument construction, positions 2 and 5 receive the same value. This does not establish stability across the preceding dependency calls or guarantee a synchronized snapshot in the presence of external mutation.

Likewise, the object field at byte offset 1000 is obtained after the conversions. A dependency-induced change to that field can affect argument 4.

Argument 7 addresses the same field whose contents supply argument 4. This is a value-plus-address relationship; it does not establish whether update reads, writes, replaces, or otherwise uses the field.

The supplied representation does not establish an evaluation order among the individual update argument expressions. The established ordering is that preparation and both conversion calls complete before update begins.

### Update failure

If update returns any nonzero status:

- Callback dispatch is skipped.
- Finalization receives the eight-byte temporary region.
- The wrapper returns **7** after finalization returns.

The particular update status is discarded. A status of −1, 7, or 12 produces the same wrapper result.

No rollback is visible. Preparation, conversions, or update may already have changed object state, local storage, resources, or other reachable state.

### Update success and callback

If update returns zero, callback selection occurs afterward:

1. The wrapper reads the dispatch-table base from the object’s first word.
2. It selects the callable entry at byte offset 48 from that base.
3. It invokes the selected callback with the object address as its sole visible argument.

The wrapper does not visibly cache the dispatch-table base before preparation, conversion, or update. Changes made by those dependencies can therefore affect the subsequent selection.

After the callback returns, finalization receives the eight-byte temporary region. The wrapper then returns zero if finalization returns normally.

The zero result does not report a callback-specific status. It indicates that this visible path reached its final return.

### Finalization boundaries

The same finalization boundary is called exactly once on each visible normal-return path:

- After preparation failure.
- After update failure.
- After the callback returns following update success.

This does not establish exception-safe or fault-safe finalization. If a preceding call fails to return normally, the evidence does not guarantee finalization or a function result.

## Side effects

The wrapper directly manages its local storage and reads object-related data. It contains no visible direct assignment to the described object fields.

Dependencies receive mutation-capable addresses:

- Preparation receives the object and both temporary regions.
- The second conversion receives the eight-byte region.
- Update receives object-relative addresses at offsets 536 and 1000.
- The callback receives the object.
- Finalization receives the eight-byte region.

Explicit argument lists do not bound all possible effects. Dependencies may access global state, retain supplied addresses, or reach storage through previously established references. In particular, the output region may be modified between preparation and its eventual reads even though neither conversion receives its address directly in this call sequence.

No allocation or ownership transfer is visibly specified by the wrapper. The evidence does not establish that:

- The initial call allocates or initializes a resource.
- Conversion results are owned or borrowed.
- Update consumes either conversion result.
- Finalization frees memory.
- Any dependency preserves globals, object fields, or another dependency’s resources.

The temporary regions are local to this invocation. Their later lifetime and the permissibility of retaining their addresses are not established by the supplied API evidence. No extended lifetime guarantee may be inferred.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Unless stated otherwise, they assume valid reached accesses and normal return from every invoked dependency.

### Preparation failure

If preparation returns **−3**, finalization must occur and the wrapper must return **−3**. Neither conversion, update, nor callback may be invoked.

The four-byte output region need not be read on this path.

### Successful continuation

If preparation and update both return zero:

- Conversion of the caller’s input must precede conversion of the eight-byte region.
- Update must receive the second conversion result at position 3 and the first at position 6.
- Callback dispatch must occur after update and before finalization.
- The final result must be zero.

### Output initialized after preparation

Suppose preparation returns zero without establishing valid output contents, but makes the output address reachable to a conversion dependency. If a conversion subsequently supplies valid four-byte contents before update argument construction, this sequence is consistent with the visible wrapper.

Acceptance must not reject it merely because initialization did not occur during preparation.

### Output modified during conversion

Suppose preparation establishes output value **10**, and a later conversion changes that region to **20**, leaving it stable through update argument construction. Update arguments 2 and 5 must reflect **20**, not a value cached at preparation return.

### Update field modified during conversion

If a conversion changes the object field at byte offset 1000, the later update receives that field’s post-conversion contents in argument 4, subject to validity and stability at the actual read.

### Update failure

If update returns **12** or **−1**, the callback must be skipped, finalization must occur, and the wrapper must return **7**. No rollback may be required solely from this wrapper’s behavior.

### Indistinguishable final statuses

Preparation returning **7** and update returning **7** both lead to final result 7. Their call sequences differ: preparation failure skips both conversions and update.

### Callback selection changed by update

If update changes the object’s dispatch-table base and returns zero, subsequent callback selection uses the then-current base rather than an earlier cached value.
