# F-9db809c408f4

## Purpose

F-9db809c408f4 conditionally updates parameter state associated with a current context. It accepts a target, a parameter selector, and a parameter value, each represented as a 32-bit integer.

The established behavior is a dispatcher with four kinds of successful update:

- A translated value written to one of two single-byte fields.
- A directly classified value written to a single-byte field.
- A two-component classification written to two single-byte fields in a defined order.
- A zero/nonzero value normalized into a context-local Boolean field.

An invalid target, unsupported selector, or rejected value enters a shared error path. That path installs error value `0x500` only when the context’s existing error word is zero.

If no current context is available, the function returns without performing its own state writes or error reporting.

The parameter values resemble a texture-parameter interface, but that interpretation is inferred intent, not a prerequisite for this contract. In particular, two global values used in dispatch and classification are not established constants.

## Interface

### Inputs

| Input | Representation | Established role |
|---|---|---|
| Target | 32-bit integer | Must equal `0x0DE1` for parameter processing to proceed. |
| Selector | 32-bit integer | Chooses a parameter operation through ordered comparisons. |
| Value | 32-bit integer | Passed to a translator, compared against accepted values, or normalized to a Boolean. |

Ordering comparisons are signed 32-bit comparisons in the supplied representation. Equality comparisons use the complete 32-bit value.

### Output

There is no explicit return value. Results are observable through:

- Writes to context-associated storage.
- Calls to opaque dependencies.
- Possible dependency side effects.
- A conditional update to the context’s error word.

## Behavior

### 1. Acquire the context

F-7fba0909c452 is called before target validation.

If its result is null, processing ends immediately. The function does not call the state resolver, read the dispatch globals, or perform its own error-word or parameter-field accesses on that path.

Any effects of the context-acquisition dependency remain possible and are not constrained by this body.

### 2. Validate the target

For a non-null context:

- Target `0x0DE1` permits further processing.
- Every other target enters the shared error path.

An invalid target does not cause a call to F-1411dcc31aed.

### 3. Resolve parameter storage and dispatch

For a valid target, F-1411dcc31aed is called with the context.

After that call, the function reads the value base into a saved value. This saved value is used later by the secondary classification when selector `0x2801` reaches that operation. The read occurs even on valid-target paths that do not ultimately use the saved value.

Dispatch then follows this priority:

1. Compare the selector with the selector boundary for equality.
2. If unequal, compare the selector boundary with the selector using signed ordering.
3. In the branch where the boundary is less than or equal to the selector, recognize `0x2803` and `0x8191`.
4. In the branch where the selector is less than the boundary, recognize `0x2800` and `0x2801`.
5. Reject all remaining cases.

This ordering matters. The fixed selectors are not independently recognized without regard to the boundary.

For example, if the selector boundary equals `0x2800`, selector `0x2800` selects the first translated-field operation, not the direct classification operation.

The boundary is referenced separately for equality and ordering. The evidence does not establish a single immutable snapshot covering both comparisons.

### 4. Exact boundary match: first translated field

When the selector equals the boundary:

1. Call F-63f3c76ed3e0 with the input value.
2. If the returned 32-bit result is exactly `-1`, enter the shared error path.
3. Otherwise, write the result’s low eight bits to state offset `0x107`.
4. Return.

No additional range validation is visible. A result outside `0` through `255` is not rejected merely for being outside that range.

### 5. Upper dispatch branch

This branch is reached only after the equality case fails and the signed boundary comparison places the selector at or above the boundary.

#### Selector `0x2803`

The translator is called exactly as in the boundary-match case. A result of `-1` is rejected; any other result has its low eight bits written to state offset `0x108`.

#### Selector `0x8191`

The function writes to context offset `0x90A`:

- Zero when the input value is zero.
- One when the input value is nonzero.

Negative values are nonzero and therefore produce one. No translator is called.

The state resolver has nevertheless already been called before this branch is selected.

#### Other selectors

Enter the shared error path.

### 6. Lower dispatch branch: selector `0x2800`

This operation is available only when the selector is below the boundary.

Value acceptance is ordered:

1. Value `0x2600` produces classification `1`.
2. Otherwise, a value equal to the value base produces classification `2`.
3. Otherwise, reject.

An accepted classification is written as one byte to state offset `0x105`, after which the function returns.

If the value base itself equals `0x2600`, the literal comparison takes priority and the stored classification is `1`.

The value-base comparison here is a further global reference, not use of the earlier saved value.

### 7. Lower dispatch branch: selector `0x2801`

This operation computes three 32-bit comparison values from the value base:

- **Offset-100:** value base plus `0x100`.
- **Offset-101:** value base plus `0x101`.
- **Offset-102:** value base plus `0x102`.

The supplied representation references the global separately for these constructions. A stable global makes them consecutive values; that stability is not established by the body alone.

The operation then derives a primary classification and, if accepted, a secondary classification.

#### Primary classification

The comparisons have the following priority:

- Equality with Offset-100 produces `2`.
- Otherwise, when the input is signed-less-than Offset-100:
  - Equality with `0x2600` produces `1`.
  - Otherwise, equality with a further read of the value base produces `2`.
  - Otherwise, equality with `0x2700` produces `1`.
  - Otherwise, reject.
- Otherwise, when the input is not less than Offset-100:
  - Equality with Offset-101 produces `1`.
  - Otherwise, equality with Offset-102 produces `2`.
  - Otherwise, reject.

Rejection occurs before either classification-field write.

On acceptance, the primary classification is written first, to state offset `0x104`.

The signed range gate is significant. Matching the value base or `0x2700` is not sufficient if the input does not enter the less-than-Offset-100 branch.

#### Secondary classification

After the primary write, the function derives and writes the secondary byte:

- Equality with Offset-100 produces `1`.
- Otherwise, when the input is signed-less-than Offset-100:
  - Equality with `0x2600` or the earlier saved value base produces `0`.
  - Otherwise, equality with `0x2700` produces `1`.
  - Otherwise, produce `0xFF`.
- Otherwise:
  - Equality with Offset-101 or Offset-102 produces `2`.
  - Otherwise, produce `0xFF`.

This byte is written to state offset `0x106`, and the function returns.

The secondary classification has no rejection path. In particular, `0xFF` is a stored byte, not a request to report an error. Under stable, ordinary global values, the primary acceptance conditions generally exclude that fallback; the supplied evidence does not justify deleting it from the contract.

### 8. Shared error path

For every rejection described above:

1. Read the context’s 32-bit error word.
2. If it is zero, write `0x500`.
3. If it is nonzero, leave it unchanged.
4. Return.

The error word is inspected when the path is reached, not saved at entry. Consequently, an earlier dependency’s effects on that word may affect whether `0x500` is written.

No rollback or restoration is visible.

## Side effects

### Direct writes

An ordinary accepted operation writes only its selected field, except selector `0x2801`, which writes two fields in this order:

1. State offset `0x104`.
2. State offset `0x106`.

These writes are not established as an atomic pair.

Successful paths do not directly clear or set the error word. Rejected paths do not directly write parameter fields.

### Dependency effects

The function does not establish that any dependency:

- Preserves global words.
- Preserves the context or associated state.
- Avoids allocation or deallocation.
- Returns permanently valid storage.
- Leaves the error word unchanged.

Thus, statements about unchanged storage refer to this function’s direct operations, not to a guarantee about the complete effects of its callees.

### Ownership and failures

No direct allocation, release, reference-count change, or transfer of ownership is visible.

There is no explicit handling for an invalid non-null context, an invalid state address, or a dependency that does not return normally. Fault behavior for such cases is unknown.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless otherwise stated, assume valid non-aliasing storage, normally returning dependencies, stable globals, and arithmetic without signed overflow. “Unchanged” refers to direct writes by this function.

For the classification examples, additionally assume:

- Selector boundary is `0x2802`.
- Value base is `0x2601`.

These are example conditions, not recovered global constants.

| Scenario | Expected direct behavior |
|---|---|
| Context acquisition returns null | Return without parameter or error-word accesses. |
| Non-null context, invalid target, error word zero | Write `0x500` to the error word; do not call the state resolver. |
| Non-null context, invalid target, error word `0x501` | Preserve `0x501`. |
| Valid target, selector `0x2802`, translator returns `7` | Write byte `7` at state offset `0x107`. |
| Valid target, selector `0x2803`, translator returns `0x123` | Write byte `0x23` at state offset `0x108`. |
| Either translated path, translator returns `-1`, error word zero | Write `0x500`; do not write the translated field. |
| Selector `0x8191`, value `-7` | Write Boolean byte `1` at context offset `0x90A`. |
| Selector `0x8191`, value `0` | Write Boolean byte `0` at context offset `0x90A`. |
| Selector `0x2800`, value `0x2600` | Write `1` at state offset `0x105`. |
| Selector `0x2800`, value `0x2601` | Write `2` at state offset `0x105`. |
| Selector `0x2800`, value `0x2700`, error word zero | Write `0x500`; leave the classification field unchanged. |

Under the same example globals, selector `0x2801` yields:

| Value | Primary byte at `0x104` | Secondary byte at `0x106` |
|---:|---:|---:|
| `0x2600` | `1` | `0` |
| `0x2601` | `2` | `0` |
| `0x2700` | `1` | `1` |

| `0x2702` | `1` | `2` |

Value `0x2704` is rejected without either classification write.

A separate precedence example: if the selector boundary is instead `0x2800`, selector `0x2800` invokes the translator and targets offset `0x107`; it does not perform direct classification.

## Uncertainties

The following are **documented_only**:

- Actual values, initialization, mutability, and synchronization of the two global words.
- Whether repeated global references correspond to distinct externally observable memory reads.
- Full machine-level arithmetic semantics when adding `0x100`, `0x101`, or `0x102` exceeds the signed 32-bit range.
- Address validity, alignment requirements, memory aliasing, and object lifetime.
- Whether dependencies preserve globals, context contents, associated state, or ownership.
- Concurrency behavior and visibility of the two ordered classification writes.
- External meanings of the selectors, classifications, translated bytes, and error value.
- Whether the shared error destination has any separately usable interface.
- Abnormal termination, faults, or nonlocal exits caused by dependencies or invalid memory.

If state storage aliases globals or context storage, a parameter write may affect later observations. The ordinary layout assumptions used in the acceptance examples do not establish that such aliasing is impossible.
