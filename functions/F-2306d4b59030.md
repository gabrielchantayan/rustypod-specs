# F-2306d4b59030

## Purpose

F-2306d4b59030 is a recovered, parameterless entry point whose visible behavior is an ordered sequence of five indirect transfers. Four transfers have target expressions represented in the supplied evidence. The fifth has an unresolved target and is explicitly identified as potentially being a jump rather than a conventional call.

The second transfer receives an argument derived from the high-order portion of an incoming integer value. The other transfers have no explicit arguments in the recovered representation.

No application-level purpose is established. In particular, the evidence does not establish initialization, decoding, allocation, validation, or processing of a particular data format. A dispatch or control-flow role is plausible, but remains inferred intent rather than a behavioral guarantee.

This contract describes the supplied static representation. It does not certify that its reconstructed function boundaries, calling conventions, or final return accurately represent the executable.

### Second-transfer argument

The argument to F-U02 is formed by shifting the incoming signed integer right by 24 bit positions.

This is a signed shift in the recovered representation, not an explicit unsigned-byte extraction. No mask, unsigned conversion, or narrowing to an 8-bit argument is visible.

Under a 32-bit signed interpretation with arithmetic right shift:

- Bits 31 through 24 determine the result.
- A clear sign bit produces a result from 0 through 127.
- A set sign bit produces a sign-extended result from −128 through −1.
- The result remains an integer; it is not visibly converted to an unsigned byte.

For example, a high-order byte of `0xFF` produces −1 under those assumptions, not 255.

Signed right-shift behavior for negative values is not independently established by the supplied evidence. A faithful behavioral description must therefore distinguish the visible signed-shift expression from any unverified machine-level interpretation.

The recovered dataflow uses the incoming integer for this calculation. There is no explicit memory load or global-state read supplying a replacement value between F-U01 and F-U02. However, the representation does not establish the physical register-preservation rules needed to validate that dataflow against the executable.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

### Ordered returning path

Given valid destinations and normal return from the first four transfers, the visible transfer order must be F-U01, F-U02, F-U03, F-U04, then F-U05.

Reordering F-U03 before F-U02 would contradict the supplied representation even if no difference were observed for a particular set of destinations.

### Positive shifted argument

Assuming a 32-bit signed incoming integer of `0x12345678`, F-U02 receives `0x12`, or decimal 18.

No additional explicit argument is shown for that transfer.

### Negative shifted argument

Assuming a 32-bit signed integer and arithmetic right shift, an incoming bit pattern of `0xFF000000` produces −1 for F-U02.

An implementation that unconditionally produces 255 would impose unsigned extraction semantics not established by this representation.

### Sign boundary

Under the same assumptions, `0x7F000000` produces 127, while `0x80000000` produces −128.

These examples distinguish sign-extending shift behavior from zero-extending byte extraction.

### Earlier destination does not return

If F-U01 does not return, this body does not independently continue to F-U02 or any later transfer.

No timeout, retry, or alternate continuation is visible.

### Final destination is a jump target

If F-U05 is a non-returning jump, acceptance does not require execution of the represented concluding return. Requiring normal return would resolve the explicit control-flow uncertainty without evidence.
