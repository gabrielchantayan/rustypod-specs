# F-f385d619c451

## Purpose

F-f385d619c451 conditionally populates a four-word output region and then updates a one-byte status field in a caller-supplied object.

An associated-object reference controls whether any processing occurs. If that reference is zero, the function makes no explicit writes and calls no dependencies. Otherwise, a mode byte selects either a direct copy from the associated object or a calculation involving four dependency calls. Both active paths then invoke a final dependency whose zero/nonzero result determines the status byte.

**Inferred intent:** The four-word regions may represent two coordinates followed by two extents. The calculation may implement a rectangle intersection if its dependencies choose appropriate bounds. Neither the geometric interpretation nor those dependency semantics is established by the supplied representation.

This contract distinguishes the function’s explicit operations from effects that unknown dependencies could introduce.

## Behavior

### Initial gate

The first explicit operation reads the associated-object reference at `0xae0`.

If it is zero, the function returns without:

- Reading the mode byte.
- Writing the output words or status byte.
- Calling any dependency.

Thus, on this path, the function itself leaves the existing output and status unchanged.

If the reference is nonzero, the function reads the mode byte at `0x130`. The associated address obtained by the initial read is retained for later direct accesses. The reference field is not explicitly reloaded, even if a dependency subsequently changes it.

The mode byte is also not explicitly reread. Every nonzero byte value selects the same calculation path.

### Zero-mode path

The function transfers the associated object’s four words into the output region without arithmetic or normalization.

The represented access sequence is:

1. Read the associated word at `0x90`.
2. Read the associated word at `0x94`.
3. Read the associated word at `0x98`.
4. Read the associated word at `0x8c`, then write it to object offset `0x9b0`.
5. Write the three previously captured words to object offsets `0x9b4`, `0x9b8`, and `0x9bc`, respectively, in that order.

These are 32-bit transfers. Their order matters if source and destination storage overlap: the last three source words have already been captured before the first destination write.

The final dependency’s first argument is the associated object’s original region beginning at `0x8c`. It is not the output region at `0x9b0`.

Consequently, matching contents do not make those arguments interchangeable. The final dependency can distinguish their addresses or modify the associated region. The function does not copy the source again after that call.

### Nonzero-mode path: coordinate results

The function first calls **F-a836bb8e1d17** twice:

- First with the addresses of the associated word at `0x8c` and the object word at `0x118`.
- Then with the addresses of the associated word at `0x90` and the object word at `0x11c`.

Each call supplies the associated-object address first. The first 32-bit result is retained as the first coordinate result; the second is retained as the second coordinate result.

The function passes addresses to actual fields. It does not capture all source values before these calls. Any dependency mutation can therefore affect later calls or subsequent direct reads.

### Nonzero-mode path: endpoint sums and temporary identities

Two distinct temporary 32-bit locations are used for endpoint sums. Their address identities are significant:

- **A** is the location receiving the associated first-coordinate sum.
- **B** is the location receiving the object first-coordinate sum.

After both coordinate calls have returned:

1. The associated words at `0x8c` and `0x94` are read and added; their sum is stored in A.
2. The object words at `0x118` and `0x120` are read and added; their sum is stored in B.
3. **F-7e1b17cbc42a** is called with addresses **(A, B)**.
4. Its 32-bit result is retained as the first endpoint result.

After that endpoint call returns:

1. The associated words at `0x90` and `0x98` are read and added; their sum is stored in **B**.
2. The object words at `0x11c` and `0x124` are read and added; their sum is stored in **A**.
3. **F-7e1b17cbc42a** is called with addresses **(B, A)**.
4. Its 32-bit result becomes the second endpoint result.

Thus, the second endpoint call reverses the first call’s address order. It still receives the associated sum first and the object sum second, but those semantic roles occupy different physical locations.

This reversal is observable to an address-sensitive dependency. A dependency retaining the first call’s first pointer would hold A, which is overwritten with the object second-coordinate sum before the second call. Its retained second pointer would hold B, overwritten with the associated second-coordinate sum.

The function establishes the order of the two sum assignments in each pair. It does not establish an evaluation order between the two operand reads within an individual addition.

The second pair of sums is calculated after the first endpoint call, not from an entry snapshot. Effects of either coordinate call or the first endpoint call can influence later reads.

### Nonzero-mode path: extents, output, and final temporary region

After the second endpoint call returns, the function calculates:

- The second extent result as the second endpoint result minus the retained second coordinate.
- The first extent result as the first endpoint result minus the retained first coordinate.

The second extent is calculated before the first extent.

The function then explicitly writes the object output fields in this order:

1. First extent to `0x9b8`.
2. Second extent to `0x9bc`.
3. First coordinate to `0x9b0`.
4. Second coordinate to `0x9b4`.

For the final dependency, the supplied temporary-storage representation indicates a separate four-word region ordered as:

1. First coordinate.
2. Second coordinate.
3. First extent.
4. Second extent.

The extent words are populated during the subtraction stage. The two coordinate words in that temporary region are populated after the four object output writes.

The final dependency receives the beginning of this temporary region, not either sum location and not the object output region. The represented layout supports four consecutive 32-bit words; the dependency’s actual read or write footprint remains unknown.
