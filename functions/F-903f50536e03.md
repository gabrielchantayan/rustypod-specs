# F-903f50536e03

## Purpose

- **Zero second input:** return a 64-bit value containing the first input’s 32-bit representation in the upper half and the constant 9 in the lower half.
- **Nonzero second input:** obtain two 32-bit results from dependencies, deliver them to another dependency together with a field read through the first input and the original inputs, invoke a further dependency, and then invoke a dependency identified as non-returning.

This is a source-facing behavioral contract derived solely from the supplied static fragment. Descriptive roles such as “delivery” identify argument flow, not an established application-level purpose. The fragment does not establish whether the inputs represent objects, handles, errors, resources, or another domain concept.

The distinction between the returning and non-returning paths is essential. The nonzero path is not shown returning the value used by the zero path.

## Acceptance examples

These are conditional acceptance criteria, not executed tests.

### Zero input selects the returning path

Given a first input of `0x12345678` and a zero second input, the result must be `0x1234567800000009`, regardless of the third-input byte. None of the listed dependencies is called, and the offset-20 field is not read.

### Upper-half bits are preserved

Given a first input of `0x80000000` and a zero second input, the result must be `0x8000000000000009`. The high bit does not cause an additional sign extension beyond the specified upper 32 bits.

Given both first and second inputs equal to zero, the result must be `0x0000000000000009`.

### Nonzero values share the same branch

A second input of `0xFFFFFFFF` selects the nonzero path just as a second input of one does. No rejection based solely on a signed-negative interpretation is demonstrated.

### Results arrive in reversed helper order

Suppose the first helper returns `0x11111111`, the second returns `0x22222222`, and the subsequent field read obtains `0x33333333`. The first three delivery arguments must be, in order:

- `0x33333333`
- `0x22222222`
- `0x11111111`

The remaining arguments must be the original third, first, and second inputs, respectively.

### A helper-induced field change is visible

Suppose the offset-20 field initially contains one value, and the second helper changes it to another before returning. If the address remains readable and no intervening actor changes it, the delivery call receives the latter value. Reading the initial value before the helpers would violate the established ordering.

### The byte is not normalized

Given a third input of `0xA5` and a nonzero second input, delivery argument four carries that byte value. Substituting a Boolean true value would not match the demonstrated behavior.

### Subsequent calls require normal completion

If delivery transfers control without returning, neither F-09ba55c206ac nor F-feee9156a257 is reached by this function’s subsequent sequence.
