# F-0971503afae0

## Purpose

F-0971503afae0 delegates creation or selection of a writable object to F-793a94891814, then applies a fixed, sparse initialization pattern to the returned address.

The second input selects between two dependency-call configurations. Zero selects selector 17 and one externally stored 32-bit value; every nonzero value selects selector 18 and a different externally stored 32-bit value. The original second input is also passed to the dependency without normalization.

After the dependency returns, this function writes nine 32-bit values and six single-byte constants at fixed byte offsets from the returned address. It returns no value.

The apparent intent is to initialize an object containing a leading word and several tagged fields. That interpretation is inferred, not established: the object type, meanings of the words, and meanings of the byte constants are unknown.

## Behavior

### 1. Select the dependency configuration

The second input is compared with zero.

- If zero, the function selects numeric selector **17** and reads **Zero configuration**.
- Otherwise, it selects numeric selector **18** and reads **Nonzero configuration**.

Only the selected configuration source is explicitly read by this function on that invocation.

The branch does not convert a nonzero second input into one. Positive and negative nonzero values select the same configuration, but their original values remain distinguishable in the dependency’s sixth argument.

### 2. Invoke the dependency

The function makes one call to F-793a94891814 with six arguments in this order:

| Position | Value |
|---:|---|
| 1 | Original first input |
| 2 | Selector 17 for zero, otherwise selector 18 |
| 3 | The selected 32-bit configuration value |
| 4 | Numeric value 9 |
| 5 | Numeric value 55 |

This is argument order, not a claim about register assignment, stack layout, or physical argument-evaluation order.

The configuration value is read before the call. The dependency therefore receives the selected value as read for this invocation; it is not asked to read the configuration source itself.

The dependency’s result is interpreted as the base address for the subsequent writes. No explicit null check, error-result check, retry, or alternate path appears between return from the dependency and initialization.

## Acceptance examples

These are conditional specification examples, not executed tests. Unless otherwise stated, assume ordinary readable sources, a normally returning dependency, and writable, non-overlapping destination storage.

### Zero branch

Given a second input of zero, the dependency receives selector 17, the value read from Zero configuration, constants 9 and 55, and zero as its sixth argument. Its first argument equals the original first input.

After normal completion, the destination contains all fifteen specified writes.

### Nonzero inputs retain their value

Given a second input of −1, the dependency receives selector 18, the value read from Nonzero configuration, and −1 as its sixth argument.

Given a second input of 7, the same selector and configuration source are selected, but the sixth argument is 7. Treating both sixth arguments as one would violate this contract.

### Byte writes preserve neighboring bytes

Suppose offsets 29–31 contain arbitrary bytes when the dependency returns, and no other actor changes them. Initialization sets offset 28 to 9 while leaving offsets 29–31 unchanged.

The same single-byte rule applies to the marker stores at offsets 40, 124, 136, 148, and 160.

### Payloads are obtained after the dependency

Suppose the dependency changes Payload-120 from one 32-bit value to another and then returns. If that source remains unchanged until its subsequent read, offset 120 receives the newer value.

An implementation that captured all payloads before calling the dependency would not preserve the specified behavior.

### Payload-24 is captured early

If the offset-0 destination aliases the Payload-24 source, and the accesses are otherwise valid, offset 24 receives Payload-24’s value from before the offset-0 store. It does not receive a replacement obtained by rereading that source afterward.

### No guaranteed success for invalid storage

If the dependency returns an address that cannot support the required writes, this contract provides no successful-completion guarantee. It does not require a clean error return, rollback, or null rejection.
