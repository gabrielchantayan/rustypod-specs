# F-4dc39f88fe67

## Purpose

F-4dc39f88fe67 conditionally invokes a supplied operation callback using state obtained from a caller-provided control object. It coordinates that invocation with two dependency calls, handles the callback’s status, optionally processes a notification flag, and returns a masked status.

The established behavior is a stateful dispatch operation, not a complete bounds-checked transfer API. The visible bound comparison does not establish that a requested range is nonnegative or that any referenced memory is valid.

**Inferred intent:** the two calls surrounding the callback may delimit a protected operation; status 4 may indicate that an associated object should be retired; and the trailing flag may represent a pending notification. These meanings are not established dependency contracts.

## Interface

### Inputs

The function accepts five arguments:

1. **Control address.** Identifies an object containing the fields described below. Although represented as an integer in the supplied material, it is used as an address.
2. **Opaque operation value.** A 32-bit value forwarded unchanged as the callback’s fourth argument. Its interpretation is unknown.
3. **Extent.** A recovered signed 32-bit integer used in the admission comparison and forwarded as the callback’s third argument.
4. **Displacement.** A recovered signed 32-bit integer used in the admission comparison and added to a control-object field to form the callback’s second argument.
5. **Operation callback.** A callable address used only when the admission comparison succeeds and the saved active-object field is nonzero.

“Extent” and “displacement” are descriptive labels, not evidence of byte units, nonnegative values, or transfer semantics.

### Referenced layouts

Offsets are byte offsets. The supplied representation uses 32-bit words for the following fields:

| Object | Offset | Observed use |
|---|---:|---|
| Control | +0x04 | Signed comparison bound |
| Control | +0x08 | Signed base value added to displacement |
| Control | +0x0C | Handle address, loaded separately for dependency and callback arguments |
| Control | +0x10 | Active-object address; captured before the callback sequence and conditionally cleared afterward |
| Control | +0x14 | Context address; captured at function entry |
| Object reached through the handle address | +0x00 | 32-bit value passed to each surrounding dependency |
| Saved active object | +0x74 | 32-bit callback-status destination on the non-4 branch |
| Saved context | +0x14 | 32-bit callback-status destination on the non-4 branch |
| Saved context | +0x18 | 32-bit mask read near return |
| Saved context | +0x1E | One-byte notification flag, tested for nonzero and conditionally cleared |

The callback receives, in argument order:

1. The current 32-bit handle-address field from control offset +0x0C.
2. The current signed base field at control offset +0x08, plus displacement.
3. Extent.
4. The opaque operation value.

The callback result is treated as an unsigned 32-bit status.

### Output

The function returns an unsigned 32-bit value:

- **1** when the admission comparison fails.
- Otherwise, the selected status bitwise-ANDed with either:
  - **0x000000FF**, when the saved context address is zero; or
  - the 32-bit mask read from saved context offset +0x18.

The selected status is initially 4 when no active object exists, or the callback result when a callback occurs. A nonzero context notification flag subsequently replaces it with 7.

### Preconditions

Defined successful execution requires valid, appropriately accessible memory for every access reached on the selected path. In particular:

- The control object must support the entry context read and bound read.
- Entering the active-object path requires a callable callback and readable handle indirection at both surrounding dependency calls.
- A callback result other than 4 requires writable saved-context offset +0x14 and saved-active-object offset +0x74.
- A nonzero saved context requires readable flag and mask fields, and a writable flag when it is initially observed as nonzero.
- Dependency-specific preconditions are unknown.

There is no visible general pointer validation, ownership validation, or arithmetic-overflow handling.

## Behavior

### Entry and admission

The context address is read from control offset +0x14 before the admission decision. This saved address is used for all later context work; changes to the control field do not cause it to be reloaded.

The function compares extent plus displacement against the signed bound at control offset +0x04. If the sum is greater than the bound, it returns 1 immediately.

This rejected path performs no visible dependency call, callback invocation, or direct memory write. It still requires the entry context-field read: rejection is not a way to avoid that access.

The comparison is signed in the supplied representation. There is no separate check for negative extent or displacement. For operands whose sum is representable as signed 32-bit, equality with the bound is accepted.

Behavior when this addition overflows the recovered signed width is **documented_only**: the supplied material does not establish a portable overflow rule or prove the underlying instruction semantics.

### Selecting whether to invoke the callback

After admission succeeds, the active-object address is read from control offset +0x10 and saved.

If this address is zero:

- The selected status becomes 4.
- Neither surrounding dependency is called.
- The operation callback is not called.
- No status is written to the context or active-object status fields.
- Processing continues to the context-dependent return stage.

If the saved active-object address is nonzero, the function performs the callback sequence below.

### Callback sequence and handle reloads

The first dependency call is F-0b4658e20c99. Its argument is obtained by reading the current handle-address field at control offset +0x0C and then reading the first 32-bit word at that address.

After this dependency returns, the operation callback is invoked. Its handle-address argument and base field are read for this invocation; neither is established as an entry snapshot. Therefore, a change made by F-0b4658e20c99 to these control fields can affect the callback arguments.

After the callback returns, F-96dd78c4ca33 is called. Its argument is obtained through another read of control offset +0x0C and another first-word dereference.

Consequently:

- The first and second surrounding dependencies are not guaranteed to receive equal values.
- The callback is not guaranteed to receive the handle address used to obtain the first dependency’s argument.
- A callback change to the handle-address field or its pointed-to first word can affect the second dependency’s argument.
- The saved context and active-object addresses remain the earlier captured values.

The order among separate argument-field reads within a single call expression is not established. The call-level order is established: first dependency, callback, second dependency, then status handling.

Return values from the two surrounding dependencies are not used in the visible logic. Their memory effects and any failure behavior remain relevant and unknown.

### Handling the callback status

Status handling occurs after F-96dd78c4ca33 returns.

If the callback status equals 4:

1. F-86f4fded1b58 is called with the saved active-object address.
2. After that call returns, control offset +0x10 is overwritten with a 32-bit zero.

This clear is unconditional within that branch. It can overwrite a different active-object value installed by any preceding dependency, including F-86f4fded1b58 itself. The visible behavior does not compare the current field with the saved address.

No direct status write to saved context offset +0x14 or saved active object offset +0x74 occurs on this branch.

If the callback status is anything other than 4:

1. The status is written as a 32-bit word at saved context offset +0x14.
2. The same status is written as a 32-bit word at saved active object offset +0x74.

This order is observable if the locations alias, accesses fault, or another observer can observe the writes. The function does not clear control offset +0x10 on this branch.

Importantly, the first status write occurs **before** the later check for a zero saved context address. A zero saved context is therefore not safely accommodated on this branch. The later zero-context fallback does not guard the earlier write.

### Context-dependent status and return

After the no-active-object branch or callback-status handling completes, the saved context address is examined.

If it is zero, the function selects mask 0x000000FF and returns that mask ANDed with the current status. It performs no context flag read or notification call.

If it is nonzero, the function reads the byte at saved context offset +0x1E.

When that byte is zero, it proceeds directly to reading the 32-bit mask at saved context offset +0x18.

When that byte is nonzero:

1. F-a061acf353ed is called with the saved context address, integer 7, and integer 0.
2. After the dependency returns, the selected status becomes 7.
3. The byte at saved context offset +0x1E is overwritten with zero.
4. The 32-bit mask at saved context offset +0x18 is read.

The flag clear occurs after the notification call, so it overwrites any nonzero value that call leaves at the flag location. The mask read also occurs after the notification call and can observe a mask changed by that dependency.

The final return is the mask ANDed with the selected status. Thus notification replaces, rather than supplements, the callback or no-active-object status for return-value purposes. It does not itself rewrite either earlier status destination.

## Side effects

The function’s direct writes are limited to these conditional operations:

- Clearing control offset +0x10 after the status-4 dependency returns.
- Recording a non-4 callback status at saved context offset +0x14, followed by saved active object offset +0x74.
- Clearing the saved context’s one-byte notification flag after the notification dependency returns.

Dependency and callback effects are additional and unspecified.

The visible body performs no explicit allocation or copying of a payload. No buffer interpretation can be assigned to the opaque operation value.

Ownership is **documented_only**. Passing the saved active object to F-86f4fded1b58 does not establish that it frees, releases, closes, or consumes the object. Likewise, the surrounding dependencies cannot be assumed to acquire and release a lock.

The function continues using saved addresses after external calls. Valid execution therefore depends on those objects remaining usable where subsequent accesses require them. The supplied material does not establish that dependencies preserve their lifetime.

No non-aliasing guarantee is visible. Dependencies or direct writes can alter later-observed fields through aliases. No concurrency or atomicity guarantee is established.

5. **Status 4 clears the active-object field.**  
   The callback returns 4. F-86f4fded1b58 receives the saved active-object address, then control offset +0x10 is set to zero. With a zero saved context, the result is 4. This result does not prove that the active object was freed.

6. **Notification overrides the returned status, not the recorded status.**  
   The callback returns 2, the context flag is nonzero, and its mask is 0x00000005. The two status destinations receive 2. F-a061acf353ed receives the saved context, 7, and 0; the flag is cleared; the result is 5.

   The active-object address is zero, but the saved context is valid and its flag is nonzero. The callback and its surrounding dependencies are skipped. F-a061acf353ed is still called. If the final mask is 0xFFFFFFFF, the result is 7.
