# F-d043b32e01f3

## Purpose

F-d043b32e01f3 processes entries observed through shared list-head storage, updates entry fields and shared counters, and conditionally transfers a one-, two-, or four-byte value into a destination region. When a fresh list-head observation is zero, it evaluates auxiliary state, optionally calls one dependency, calls a final dependency, and returns a 32-bit zero if those calls return normally.

The apparent intent is work-list processing with width-dependent payload movement. That interpretation is inferred, not an ownership or synchronization guarantee. Address-valued field assignments, the unusual index-reset value, and repeated observations of shared storage are part of the established behavior.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

### Explicit input and result

The explicit input is a 32-bit value used as the address of a **current object**. Before the first list inspection, that object must support a 32-bit read at byte offset 16.

The only established normal result is a 32-bit zero. No explicit error result is visible. Execution may instead continue indefinitely, encounter an invalid memory access, or fail to return because a dependency does not return.

A separate arithmetic operand is initialized locally to `0x08001fbc`. Before later outer dependency calls, it is replaced by an observed shared-index value. It is not an additional independently initialized caller input.

## Behavior

### Initial call and outer repetition

Before inspecting the list, the function calls F-2489d48d501c with:

- The destination-base contents plus transfer width multiplied by the literal `0x08001fbc`.
- The 32-bit contents of current-object offset 16.

The multiplication initially uses the literal address-like number, not the contents stored at that address. The destination-base contents are added separately. Relative evaluation order between the two arguments’ memory reads is not established.

After an entry is processed with a width other than zero, one, two, or four, the function calls F-2489d48d501c again. This later call uses:

- A shared-index value captured after that entry’s counter updates as the multiplication operand.
- A fresh destination-base read.
- A fresh read of offset 16 of the most recently selected current object.

No ordinary return value from this dependency is used.

### Per-visit counter and service observations

Each list-processing visit performs these distinct observations and updates:

1. Read the high-water value into temporary state.
2. Read the visit count, increment it, and write it back.
3. Read the high-water value again and read the progress count for an unsigned 32-bit less-than comparison.
4. If that comparison succeeds, read the progress count again and write this newly observed value into the high-water cell.
5. Read the progress count separately for comparison with one.
6. Only if that observation equals one, read the service gate. If the gate is nonzero, call F-6ad030b1b8cc.
7. Begin the list-head observation sequence described below.

The first high-water observation is not reused for the comparison. The comparison’s progress observation is not necessarily the value assigned to high-water. The later service predicate does not reuse either progress observation.

The representation does not establish relative evaluation order between the two reads within the less-than comparison. It does establish that both occur after the visit-count increment, and that the assignment’s additional progress read occurs only if the comparison succeeds.

The initially saved high-water value, including its possible replacement by an auxiliary machine result from F-6ad030b1b8cc, does not determine a subsequent externally visible decision here.

The service call precedes all list-head observations. Its effects may therefore influence those observations.

### List-head observations and removal

The list-head sequence must not be reduced unconditionally to one head read:

1. Read the list head and retain that address as the **entry to process**.
2. Read the list head again and test this fresh observation for zero.
3. If the tested observation is nonzero, read the list head again and read the 32-bit offset-0 field through this third observed address. Retain that field value as the **candidate next address**.

A zero result at step 2 selects the empty-list path, regardless of the entry address retained at step 1.

If the candidate next address is nonzero:

1. Read the list head yet again and read its offset-0 field. Retain this separately obtained address as the **back-reference target**.
2. Write the candidate next address into the list-head cell.
3. Write `0x08001fd0` into offset 4 of the back-reference target.
4. Read the list-head cell again.
5. Write that last observed value back into the list-head cell.

Thus, the back-reference target is obtained before the first head update, but its offset-4 field is written after that update.

If the candidate next address is zero, write zero into the list-head cell. The additional back-reference-target observation and write do not occur.

Subsequent entry processing uses the address retained by the first head read—not necessarily the address tested, dereferenced, or installed by later observations.

Under stable, nonaliasing storage, these operations remove the retained head, make its successor the new head, and update that successor’s back-reference. Without that assumption, the retained entry, candidate next address, and back-reference target can differ. A successful nonzero test does not guarantee that a later head read is nonzero or valid.

### Empty-list path

When the second head observation is zero:

1. Read the 32-bit field at primary-state offset 8.
2. If it is nonzero, call D-01 with that value.
3. Otherwise, read comparison-state offset 8, then comparison-state offset 12.
   - If the values differ, call D-01 with the value observed at offset 8.
   - If they are equal, read the byte at primary-state offset 1. Call D-01 only if that byte is nonzero, passing its zero-extended 32-bit value.
4. Call D-02.
5. Return 32-bit zero.

D-01 can receive zero when the comparison-state fields differ and the offset-8 observation is zero.

The comparison-state fields are not read when primary-state offset 8 is nonzero. The primary-state byte is read only when that field is zero and the comparison-state observations are equal.

These operations follow the visit-count, high-water, and service behavior. Neither a previously retained nonzero entry address nor earlier list contents prevent this path.

### Retained-entry updates

After the nonempty removal sequence:

- Read the retained entry’s 32-bit flags at offset 28.
- Clear bit 7 and write the resulting 32-bit value back.
- If the masked value is zero, read primary-state offset 8, write that value into retained-entry offset 0, and then write the retained entry’s address into primary-state offset 8.

The zero test uses the masked flags value, not a fresh field read. Other flag bits are retained.

Next, read retained-entry offset 8. If it is nonzero, call F-f46257aeeddc and then write `0x08001fcc` into that field. There is no visible retest after the call.

The retained entry remains in use after this dependency returns. The source does not establish that the dependency preserves it or transfers ownership. Valid subsequent storage is a precondition, not an inferred dependency guarantee.

### Object selection and counters

Read retained-entry offset 16, then read offset 4 through that intermediate pointer. The latter value replaces the current-object address.

Then:

1. Write `0x08001fcc` into current-object offset 4.
2. Read, increment, and write the progress count.
3. Read, increment, and write the shared index.
4. Read the shared index again and compare it for equality with the inherited index limit.
5. If equal, write `0x08001fcc` into the shared-index cell.

The equality test is not a greater-than-or-equal check. The replacement is the literal `0x08001fcc`, not zero. The comparison does not necessarily observe the increment result if storage changes between accesses.

### Width-dependent action

After those updates:

| Width | Action |
|---:|---|
| 0 | No payload read or destination write; begin another list-processing visit. |
| 1 | Read a source pointer from current-object offset 16, read one byte through it, and write one byte at destination base plus shared index. |
| 2 | Read the source pointer, read 16 bits through it, and write 16 bits at destination base plus twice the shared index. |
| 4 | Read the source pointer, read 32 bits through it, and write 32 bits at destination base plus four times the shared index. |
| Other | No width-specific payload transfer; repeat the outer dependency call using a captured shared-index value. |

The one-, two-, and four-byte destination calculations use fresh reads of destination base and shared index, not an index value cached before increment or reset. Under stable storage, they consequently use the post-increment, possibly reset index.

Before distinguishing width four from the unsupported-width path, the function separately reads the shared index into the arithmetic operand. Width four still reads the shared index again for its destination calculation; it does not use that captured operand for the transfer.

Within a transfer expression, relative evaluation order between source-side and destination-address reads is not established. The source value must be obtained before its destination write. No bounds, overlap, or alignment validation is visible.

## Side effects

Established effects include dependency calls, shared-counter updates, list-head writes, back-reference writes, flag modification, conditional relinking, marker-field overwrites, current-object field modification, and conditional payload writes.

Writes may affect later observations when referenced regions alias. For example, the back-reference write precedes the final head reread; it cannot be assumed irrelevant to that reread without a nonaliasing assumption.

No allocation, deallocation, locking, rollback, or error translation is directly visible. Dependencies may have such effects; their contracts are unknown. The access order establishes neither atomicity nor synchronization.

Progress and high-water are represented as unsigned 32-bit quantities. The visit count, shared index, transfer width, and address-forming arithmetic are represented with 32-bit integer operations, including signed representations in several expressions. Unsigned comparison and the 32-bit flag mask are established. Universal modulo-\(2^{32}\) behavior for signed increments and address arithmetic is not established; overflow cases remain **documented_only**.

## Acceptance examples

These are conditional static consequences, not executed tests. Unless specified otherwise, assume valid, stable, nonaliasing storage, returning dependencies, no arithmetic overflow, and no unmentioned interference.

1. **Empty list without D-01.**  
   With a zero second head observation, zero primary-state offset 8, equal comparison-state fields, and zero primary-state byte 1, D-01 is skipped. D-02 runs and the result is zero. The initial call and per-visit updates still occur.

2. **Optional call with zero.**  
   With primary-state offset 8 equal to zero and comparison-state observations zero and five, D-01 receives zero. The argument’s zero value does not suppress the call.

3. **Distinct high-water observations.**  
   If high-water is initially read as 100, but the later comparison observes high-water 2 and progress 3, the comparison succeeds. If the assignment’s separate progress read observes 9, high-water receives 9—not 3 or 100. The service predicate then makes another progress observation.

4. **Distinct head observations.**  
   Suppose the retained-entry read yields address A and the zero-test read yields nonzero B. A later head read yields C, whose offset-0 field is N. If N is nonzero, another head read yields D, whose offset-0 field is W. The function writes N into the head, writes `0x08001fd0` at W plus 4, rereads and rewrites the head, then processes A. No equality among A, B, C, D, N, and W is implied.

5. **Fresh empty observation.**  
   If the retained-entry read is nonzero but the following head read is zero, the empty-list path is taken. The retained address is not processed on that path.

6. **Flag masking.**  
   Flags `0x00000080` become zero and trigger relinking through primary-state offset 8. Flags `0x00000081` become one and do not trigger that relinking.

7. **Stable successor removal.**  
   With a stable head A whose next pointer is N, where N is nonzero, the new head is N, offset 4 of N receives `0x08001fd0`, and A is processed.

8. **Two-byte transfer and reset.**  
   With width two, initial index three, and limit other than four, one processed entry produces index four and a 16-bit write at destination base plus eight. If the limit is four instead, the destination uses twice `0x08001fcc`.

9. **Unsupported width.**  
   Width three still performs entry processing and counter updates. It performs no width-specific payload transfer and repeats F-2489d48d501c using the captured index.
