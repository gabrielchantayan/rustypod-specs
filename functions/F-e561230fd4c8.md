## Behavior

### Search and bound checks

The search begins at index zero.

Before each comparison, the function reads the signed 32-bit count at offset 0x19c. If the count is less than or equal to the current index, the function immediately returns zero.

Consequences include:

- A count of zero produces no comparison calls.
- A negative count also produces no comparison calls.
- The comparison table and associated-value table are not accessed on either of those paths.
- The count is read again for each subsequent iteration. It is not captured once at entry.

When the current index is below the count, the function reads the comparison-table address from offset 0x1a0, then reads the 32-bit entry at the current four-byte slot. It calls the comparison dependency with:

1. The unchanged second explicit input.
2. That selected table-entry word.

The comparison dependency’s opaque function ID is not provided in the dependency map. Its name and implementation are not part of this contract.

A comparison result of exactly zero selects the current index. Any nonzero result rejects that index and advances the search by one. The sign and magnitude of a nonzero result do not otherwise affect the search.

The first zero result ends the search. Later entries are not compared.

### Dynamic state during searching

Because the count and comparison-table address are read during the loop, mutations made by a comparison call can affect later iterations.

In particular:

- A decreased count can stop the search at the next bound check.
- An increased count can make additional indices eligible.
- A changed comparison-table address can redirect the next table-element read.
- A zero comparison result proceeds directly to the matching path without another count check.

No preservation guarantee for the object, its tables, or global state can be attributed to the comparison dependency from the supplied evidence.

The index is nonnegative throughout ordinary execution. With a signed 32-bit count, an iteration can pass the bound check only while its index is strictly below 2,147,483,647. Advancing after such an iteration can reach that maximum, but the next bound check must terminate because no signed 32-bit count is larger. Thus the visible loop does not require a signed index increment past that maximum.

This does not establish that every four-byte table displacement is representable as a valid address calculation. Address arithmetic and memory-validity limits remain separate preconditions.

### Matching path

Once an index is selected, the function performs these externally relevant operations in order:

1. Reads the associated-value-table address from offset 0x1a4.
2. Reads the selected 32-bit associated value using the same index and four-byte stride.
3. Calls F-4af36158f863.
4. Reads one 32-bit word from the address returned by that call.
5. Calls F-c05d0f17ecc7 using the selected associated value and the argument information described below.
6. Writes the saved word back to the same address returned by F-4af36158f863.
7. Returns the 32-bit result from F-c05d0f17ecc7.

The associated value is therefore captured before F-4af36158f863 runs. A later mutation of its table slot does not replace the value already selected for this call.

The address used for the final restoration is also retained from the earlier F-4af36158f863 result. The function does not call that dependency again to obtain a fresh address.

## Acceptance examples

These are conditional contract examples, not executed tests. Each assumes valid memory and normally returning dependencies unless stated otherwise.

1. **Empty collection.**  
   If the first count read is zero, the result is zero. There are no comparison calls, no table-element reads, and no calls to either mapped dependency.

2. **Negative count.**  
   If the first count read is negative, behavior matches the empty-collection case. The negative value is not treated as a large unsigned length.

3. **No selected entry.**  
   With a stable count of three and three nonzero comparison results, indices zero, one, and two are compared in order. The next count check returns zero. The associated-value table is not read.

4. **First selected entry wins.**  
   With a stable positive count and a zero comparison result at index zero, no later index is compared. The associated value at index zero is selected.

5. **Later selected entry.**  
   With a stable count of at least two, a nonzero result at index zero followed by zero at index one selects the associated-value slot at byte displacement four. Both comparison calls receive the same second explicit input.

6. **Count changes after rejection.**  
   Suppose index zero is compared while the count is two. If that call returns nonzero and changes the count to one, the next bound check returns zero without comparing index one.

7. **Associated table changes during comparison.**  
   If the successful comparison changes the associated-value-table address, the subsequent associated-value read uses the changed address, because that field is read after the successful call.

8. **Saved cell changes during conversion.**  
   If the saved cell initially contains a particular 32-bit pattern and F-c05d0f17ecc7 replaces it, the function writes the original saved pattern back after the dependency returns normally. It then returns the dependency’s result unchanged.

9. **Zero conversion result.**  
   A successful search followed by a zero result from F-c05d0f17ecc7 returns zero. That return value alone does not distinguish this execution from search exhaustion.

10. **Abnormal conversion exit.**  
    If F-c05d0f17ecc7 does not return normally, this contract does not promise restoration of the saved word or a normal return from F-e561230fd4c8.
