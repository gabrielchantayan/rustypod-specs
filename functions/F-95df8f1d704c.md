# F-95df8f1d704c

## Purpose

F-95df8f1d704c conditionally obtains and checks a 32-bit value associated with an object, using a caller-supplied 32-bit slot as a gate. If the check succeeds, the function returns the obtained value without explicitly clearing the slot. Otherwise, if the slot was initially nonzero, the function may invoke an indirect callback associated with its current contents and then clears the slot.

The operation is bracketed by calls to F-338d16f9ce72 and F-1333331b2da1 using an address 20 bytes into the object. Their placement suggests synchronization or another acquire/release discipline, but that interpretation is inferred, not established.

The normal fallback result is the 32-bit pattern `0xFFFFFFFF`. This pattern is not necessarily distinguishable from a successful result: the successful path returns the obtained value without excluding that pattern.

## Interface

| Slot address | An address of a readable and, on the fallback path, writable 32-bit slot. The slot contains either zero or an address-like value. |

No input validation or explicit null-pointer rejection is visible. Validity requirements depend on the path taken:

- If a later observation of the slot is nonzero on the failed-check path, its contents must support the indirect-callback lookup described below.
- If the initial slot observation was nonzero and the check fails, the slot must be writable after the optional callback returns.

The supplied representation uses 32-bit integer and address-like quantities. It does not establish a portable interface for systems with wider pointers.

## Behavior

### Entry and opening dependency

The function computes the object address plus 20 bytes and retains that computed address for its closing call. It then calls F-338d16f9ce72 with that address.

The first explicit read of the caller’s slot occurs only after this dependency returns. Consequently, the branch depends on the slot value at that time, not necessarily its value at function entry. No guarantee is available that the dependency leaves the slot, the object, or other accessible state unchanged.

The byte offsets are fixed. There is no visible length, bounds check, or overflow check. A safe calling precondition is that the relevant address calculations and accesses are valid in the target execution environment. Behavior for malformed or overflowing addresses is not established by the supplied evidence.

### Initially zero slot

If the first slot read is zero:

- Neither F-892319a374a5 nor F-87b34b1e9a5b is called.
- No callback lookup is performed.
- The function performs no explicit write to the slot.
- F-1333331b2da1 is called with the previously computed object-plus-20 address.
- After that call returns, the function returns `0xFFFFFFFF`.

This path does not require the object field at byte offset 12 to be read by this function. The opening and closing dependencies may have their own requirements.

### Initially nonzero slot: obtaining and checking a value

If the first slot read is nonzero, the function reads the 32-bit object field at byte offset 12 and passes that value to F-892319a374a5.

The 32-bit result of F-892319a374a5 becomes the candidate result.

After that call returns, the function reads the object field at byte offset 12 again. It passes this second field value and the candidate result to F-87b34b1e9a5b.

These are separate field reads. The first field value is not reused as the first argument of the checking call. If F-892319a374a5 changes that field, the later call receives the changed value. The same distinction applies to modifications by any other permitted actor; synchronization guarantees are unknown.

The result of F-87b34b1e9a5b is interpreted only as zero or nonzero. No narrower success code, sign requirement, or range restriction is visible.

### Nonzero check result

If F-87b34b1e9a5b returns nonzero:

- The function calls F-1333331b2da1 with the previously computed object-plus-20 address.
- After that call returns, the function returns the candidate result.

This path contains no explicit slot clearing and no indirect callback invocation. It does not reread the slot after the checking call.

Accordingly, an initially nonzero slot does not imply that it remains nonzero on successful return. Dependencies could modify it. The established guarantee is only that this function does not explicitly clear it on this path.

There is no exclusion for a candidate result of zero or `0xFFFFFFFF`. Either can be returned through the successful path if the check result is nonzero.

### Zero check result and callback processing

If F-87b34b1e9a5b returns zero, the function reads the slot again.

If that observation is zero, callback dispatch is skipped. The function nevertheless writes zero to the slot before calling the closing dependency.

If that observation is nonzero, the function performs an indirect callback lookup:

- It obtains the slot’s address-like contents for dispatch.
- It reads the leading 32-bit word at that address.
- It uses that word as a dispatch-table base.
- It reads the callback target at byte offset 4 from that base.
- It invokes that target.

The supplied representation contains no explicit callback arguments and does not use a callback return value. It does not establish the complete machine-level calling convention, implicit arguments, or callback semantics.

The nonzero test and the slot read used for dispatch are separate accesses in the supplied representation. The slot-referenced address is not established to be a stable snapshot across them. Without an external stability guarantee, a nonzero test alone does not prove the subsequent dispatch access is valid.

After the callback returns normally, the function writes zero to the caller’s slot. Thus a callback that writes a new value into the same slot has that value overwritten by this explicit clearing operation.

The function then calls F-1333331b2da1 with the retained object-plus-20 address and returns `0xFFFFFFFF` after that call returns.

### Normal-path ordering

Every visible normally completing path calls F-338d16f9ce72 once and F-1333331b2da1 once, in that order.

On the failed-check path, optional callback execution and explicit slot clearing occur before the closing call. On the successful-check path, the closing call occurs before the candidate is returned.

No exception handler, fault recovery, retry, or compensating action is visible. If a dependency or callback does not return normally, the subsequent steps are not guaranteed.

## Side effects

The only direct memory write visible in this function is a 32-bit zero written to the caller’s slot when both conditions hold:

1. The initial slot read was nonzero.
2. F-87b34b1e9a5b returned zero.

That write occurs regardless of whether the later slot test permits callback dispatch.

All other side effects are delegated:

- F-338d16f9ce72 may affect state before the first slot read.
- F-892319a374a5 may affect state before the second object-field read.
- F-87b34b1e9a5b may affect state before the later slot test.
- The callback may affect state before the explicit slot clear.
- F-1333331b2da1 may affect state after any explicit slot clear and before return.

In particular, the function does **not** unconditionally guarantee a zero slot at return on the failed-check path. It writes zero before the closing dependency, whose effects are unknown.

No allocation, deallocation, reference-count adjustment, or ownership transfer is directly established. Clearing the slot removes its stored value; it does not by itself prove that the previously referenced entity was destroyed or released. The callback may perform such an operation, but that remains unknown.

## Acceptance examples

These are conditional contract examples, not executed tests.

### Zero gate after the opening call

Assume the opening dependency returns normally and the slot then contains zero.

Expected behavior: both candidate-related dependencies and callback dispatch are skipped. The closing dependency is called, followed by return of `0xFFFFFFFF`. No direct slot write occurs.

### Successful check with an ordinary candidate

Assume the first slot observation is nonzero, F-892319a374a5 returns `0x0000002A`, and F-87b34b1e9a5b returns any nonzero 32-bit result.

Expected behavior: the closing dependency is called, then the function returns `0x0000002A`. No callback or explicit slot clear occurs.

### Successful check with the fallback bit pattern

Assume the candidate is `0xFFFFFFFF` and the check returns nonzero.

Expected behavior: the function takes the successful path and returns `0xFFFFFFFF` after the closing call. The return value alone cannot distinguish this case from fallback.

### Field mutation between dependent calls

Assume object + 12 initially contains value A. During F-892319a374a5, it changes to value B.

Expected behavior: F-892319a374a5 receives A; F-87b34b1e9a5b receives B together with the candidate. Reusing A for the check would not match the visible behavior.

### Failed check with a zeroed slot

Assume the initial slot observation is nonzero, the check returns zero, and the slot is zero at the later test.

Expected behavior: callback dispatch is skipped, zero is explicitly written to the slot, the closing dependency is called, and the function returns `0xFFFFFFFF`.

### Failed check with a stable dispatchable slot

Assume the initial slot is nonzero, the check returns zero, the slot remains stable through callback lookup, and the indicated callback is valid and returns normally.

Expected behavior: that callback runs before the slot is explicitly cleared. The closing dependency runs afterward. The result is `0xFFFFFFFF`.

### Callback or closing-call mutation

Assume the callback stores a nonzero value in the slot and returns normally.

Expected behavior: the function overwrites that value with zero before the closing call. If the closing dependency subsequently stores another value, the function performs no further explicit clearing.
