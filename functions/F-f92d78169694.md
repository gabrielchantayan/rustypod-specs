# F-f92d78169694

## Purpose

F-f92d78169694 conditionally removes an object from a parent-maintained doubly linked list, clears its linkage fields, and adjusts two 16-bit counters on the original parent and each subsequently visited ancestor. A visited ancestor matching a context selection field triggers two dependency calls.

**Established static behavior:** a zero parent field causes immediate return. A nonzero parent causes capture of the original parent and context addresses, optional notification, list updates, linkage clearing, decrement selection, and ancestor traversal, in that order.

**Inferred intent:** the flag and counter sources appear to distinguish ordinary objects from objects representing aggregate counts. Their application meanings are not established.

The function performs no explicit allocation or memory release. Nothing in the supplied representation establishes whether its dependencies allocate, release, transfer ownership, or preserve referenced storage.

## Interface

The function accepts two inputs:

- **Object address:** an address of mutable storage containing the fields below.
- **Mode:** a 32-bit signed integer. Zero and nonzero select different behavior. The original value is forwarded unchanged to the optional notification dependency.

It returns no value and provides no explicit error result.

The represented address and word width is 32 bits. Counter accesses use 16 bits; flag accesses use 8 bits. All offsets below are byte offsets. Byte order is not established.

## Behavior

### Initial gate and retained addresses

The function first reads the object’s parent field at +0x04.

If that value is zero, it returns without further field accesses, writes, or dependency calls. In particular, it does not read the context, inspect the flag, clear links, or adjust counters.

Otherwise, it retains the original parent address and reads and retains the context address from object +0x00. Subsequent changes to the object’s parent or context fields do not replace these retained addresses.

The object address must therefore support the initial parent read even on the no-action path. The function does not validate the object address.

### Optional notification

Before its own list writes, the function considers F-8372b6f032fd. The call occurs only if all of the following hold:

1. Mode is nonzero.
2. Bit 0 of the byte at object +0x1D is clear.
3. The 32-bit value at object +0x20 is nonzero.

These conditions short-circuit in that order. Zero mode avoids the notification-related flag and value checks. A set flag bit avoids the notification-value check.

The call receives:

1. The value supplied from object +0x20.
2. The original mode.
3. Zero.
4. 4096.

Any return value is ignored.

The original parent and context have already been retained. The list links and decrement sources have not been captured as a stable snapshot. If this dependency returns after changing those later-read fields, its changes can affect detachment or counter adjustment.

No storage-lifetime or ownership guarantee is established for this call. Continued execution requires the storage used afterward to remain usable.

### List updates and linkage clearing

After the optional notification returns, or immediately when notification is skipped, the function performs two list updates.

First, it tests the object’s previous link at +0x0C:

- If zero, it stores the object’s next-link value into original parent +0x20.
- Otherwise, it stores the object’s next-link value into the referenced previous object’s +0x08 field.

Second, it tests the object’s next link at +0x08:

- If zero, it stores the object’s previous-link value into original parent +0x24.
- Otherwise, it stores the object’s previous-link value into the referenced next object’s +0x0C field.

The first update precedes the second. The links are accessed during these operations, not retained together before notification or detachment. Consequently, aliasing can allow the first write to affect fields read for the second update. The source does not establish a complete ordering among operand reads within an individual assignment.

After both updates, the function writes zero to:

1. Object +0x04, the parent field.
2. Object +0x08, the next link.
3. Object +0x0C, the previous link.

These stores do not change the retained original parent or context addresses.

There is no list-consistency check. The function does not verify that neighboring objects point back to the removed object or that the parent’s head and tail agree with the links.

### Decrement selection

After clearing the linkage fields, the function reads bit 0 at object +0x1D again. This observation is separate from any earlier notification eligibility check.

If the bit is clear, it selects:

- A decrement of 1 for ancestor +0x2E.
- A decrement of 0 for ancestor +0x2C.

If the bit is set, it selects the decrements in this order:

1. Read the signed 16-bit value at object +0x2E for the ancestor +0x2E decrement.
2. Read the **32-bit word** at object +0x2C, convert its numerical low 16 bits to a signed 16-bit value, promote that value for addition, add 1, and narrow the result to 16 bits for the ancestor +0x2C decrement.

The second calculation is not a halfword read followed by addition. The full word read remains part of the access contract even though only its numerical low 16 bits affect the resulting decrement.

Both selected decrements are retained for the entire ancestor walk. Later changes to the removed object’s flag or source storage do not recalculate them.

At the represented target-width level, narrowing retains the low 16 result bits. For the word-derived decrement:

- Numerical low bits 0x0000 produce decrement bits 0x0001.
- Numerical low bits 0x7FFF produce decrement bits 0x8000.
- Numerical low bits 0xFFFF represent −1 before addition and produce decrement bits 0x0000.

The promoted addition ranges from −32767 through 32768, so it does not overflow a 32-bit signed integer. The significant boundary operation is narrowing back to 16 bits.

### Ancestor traversal

Traversal starts at the retained original parent, which is nonzero.

For each visited ancestor, the function performs the following ordered operations:

1. Read the signed 16-bit counter at +0x2E, subtract its selected signed 16-bit decrement after integer promotion, and store the narrowed 16-bit result.
2. Read the signed 16-bit counter at +0x2C, subtract its selected signed 16-bit decrement after integer promotion, and store the narrowed 16-bit result.
3. Read retained context +0x40 and compare that address with the current ancestor.
4. If equal, perform the dependency sequence below.
5. Read current ancestor +0x04 to obtain the next ancestor.

The promoted counter subtractions fit within a 32-bit signed integer. Stored results retain 16 bits, giving modulo-65536 result bits. There is no saturation, underflow rejection, or conceptual-count validation. A decrement whose signed value is negative can numerically increase a counter.

The +0x2C counter is still read and written when its decrement is zero.

On a selection match:

1. F-fd61d89535ad receives the current 32-bit value at retained context +0x0C and the value 1.
2. After it returns:
   - Zero mode selects F-4da249f41b2c with retained context and 1.
   - Nonzero mode selects F-f20c359c7131 with retained context.

There is no second selection comparison between these calls. A change to context +0x40 during the first call does not cancel the already-selected second call.

The next-ancestor field is read only after these calls return. Dependency changes to current ancestor +0x04 can therefore terminate or redirect traversal. Context +0x40, and context +0x0C on a match, are read anew on later visits.

Traversal ends when a next-ancestor read yields zero. There is no cycle detection or visit limit.

## Side effects

Explicit writes comprise:

- A parent head or previous-object next-link update.
- A parent tail or next-object previous-link update.
- Three linkage clears on the removed object.
- Two 16-bit counter writes per visited ancestor.

The function does not explicitly clear the object’s context, flag, notification value, or decrement-source storage. Aliasing may nevertheless cause writes through other addresses to overlap those fields.

There is no rollback. Notification precedes direct list changes; list changes precede linkage clearing; linkage clearing precedes ancestor accounting; each ancestor’s counter writes precede its conditional calls. An invalid access, interrupted execution, or nonreturning dependency may leave partial changes.

No explicit memory release occurs. Removal and linkage clearing do not prove destruction, continued object lifetime, or ownership transfer.

For normal finite completion, every subsequently accessed address must remain valid, every write destination must be writable, and the ancestor sequence actually observed must reach zero. The function does not enforce these conditions. A retained context address is used during every ancestor visit, including when mode is zero.

## Acceptance examples

These are conditional consequences of static evidence, not execution results. Unless stated otherwise, assume valid nonoverlapping objects, a finite ancestor chain, and dependencies that return without modifying relevant storage.

### Already detached

If object +0x04 is zero, either mode causes return after the parent read. There are no writes or dependency calls. Other fields are not consulted.

### Sole member with clear flag

For a nonzero parent, zero next and previous links, clear flag bit 0, and zero mode:

- The original parent’s head is written to zero, then its tail.
- The object’s parent, next, and previous links are cleared in order.
- Each ancestor’s +0x2E counter decreases by one in 16-bit arithmetic.
- Each ancestor’s +0x2C counter is read and written unchanged.
- Notification is skipped.
- A selection match invokes F-fd61d89535ad, then F-4da249f41b2c.

### Middle member with notification

For nonzero neighboring links, clear flag bit 0, nonzero notification value, and mode 7:

- F-8372b6f032fd receives the notification value, 7, 0, and 4096 before direct list writes.
- The previous object’s next link is replaced with the removed object’s next link.
- The next object’s previous link is replaced with the removed object’s previous link.
- A selection match invokes F-fd61d89535ad, then F-f20c359c7131.

Any other nonzero mode selects the same second dependency, while notification receives that mode’s exact value.

### Word-derived decrement wraps to zero

Suppose flag bit 0 is set and the **32-bit word loaded at object +0x2C has numerical low 16 bits 0xFFFF**.

The +0x2C decrement is zero: the low bits convert to signed −1, addition produces zero, and narrowing retains zero. Every visited ancestor’s +0x2C counter is read and written unchanged.

This premise does not specify a halfword value at object +0x2C or independently determine the overlapping halfword at +0x2E without byte-order information. The other decrement follows that separate +0x2E read.

### Separate counter underflow example

If flag bit 0 is set and the signed halfword read at object +0x2E is 3, an ancestor +0x2E counter with bits 0x0001 is stored as 0xFFFE.

This example imposes no independent value on the overlapping word-derived source. Its +0x2C decrement must be calculated from the actual 32-bit word read.

### Notification changes later inputs

If notification is eligible and F-8372b6f032fd changes the flag to set before returning, decrement selection follows the set-flag branch. It uses the later halfword read at +0x2E and later full-word read at +0x2C.

Changes to the object’s parent or context fields do not replace the addresses already retained.

### Ancestor callback redirects traversal

On a selection match, if a dependency changes current ancestor +0x04 to zero and returns, traversal ends after that visit. If it supplies another valid ancestor address, traversal continues there.

Changing context selection during F-fd61d89535ad does not suppress the mode-selected call for the current visit.
