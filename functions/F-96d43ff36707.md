# F-96d43ff36707

## Purpose

F-96d43ff36707 conditionally preprocesses an event-like record, dispatches that record through receiver-associated indirect handlers, and returns the first nonzero handler result.

The established behavior is an ordered dispatch chain, not a single classification of an immutable event. Record fields and dispatch-table pointers are reread after calls. A dependency that changes those fields can therefore change subsequent routing.

The apparent intent is event handling with special treatment for several numeric event codes. The meanings of those codes, the receiver’s concrete type, and the handlers’ business semantics are not established.

## Interface

### Inputs

The function receives two arguments:

1. **Receiver reference.** An address used to access a dispatch-table reference and selected receiver fields.
2. **Record reference.** An address used to access a top-level discriminator and a secondary field that is interpreted differently for different discriminator values.

Both original argument values are forwarded, in the same order, to every indirect handler invoked by this function. Forwarding the same addresses does not imply that the referenced contents remain unchanged.

### Layout and widths

Offsets below are byte offsets from the indicated base.

| Base | Offset | Observed use |
|---|---:|---|
| Receiver | `0x00` | Dispatch-table reference |
| Receiver | `0x50` | Integer compared with the record’s secondary field during final dispatch |
| Receiver | `0x10C` | Integer converted to plain character type for preprocessing |
| Record | `0x04` | Top-level discriminator |
| Record | `0x08` | Payload reference when the discriminator is `0x16`; comparison value when it is `0x0F` |
| Payload | `0x04` | Nested discriminator |

The supplied representation uses integer-indexed receiver accesses corresponding to `0x50` and `0x10C` under a four-byte integer model. This contract uses that apparent 32-bit integer layout. A complete target ABI, including pointer width, byte order, alignment, and character signedness, is not supplied.

The value at record offset `0x08` is not always a pointer. Its interpretation depends on the discriminator observed at the particular decision point.

The dispatch table is accessed at these byte offsets:

| Table offset | Contract-local dependency ID | Role |
|---:|---|---|
| `0x124` | F-I01 | Preliminary handler for nested discriminator zero |
| `0x10C` | F-I02 | Main handler for nested discriminator `0x2A` |
| `0x110` | F-I03 | Main handler for all other cases |
| `0x0E0` | F-I04 | Final handler for a matching `0x0F` record |

F-I01 through F-I04 are opaque, contract-local labels for indirect call sites. They do not establish the identities of the runtime targets. The same runtime function could occupy multiple slots.

Receiver offset `0x10C` and dispatch-table offset `0x10C` belong to different objects and have unrelated roles.

### Output

The function returns an integer:

- The exact nonzero result from the first invoked indirect handler that returns nonzero; or
- Zero if no invoked indirect handler returns nonzero.

A negative result is nonzero and terminates processing just as a positive result does.

The preprocessing dependency’s result, if any, is not used to select the function’s return value.

### Preconditions

For normal completion, every address actually accessed must be valid for the required read or call at the time of that access. This includes:

- The record discriminator field.
- The record’s secondary field when its branch requires it.
- The nested discriminator when the record is observed as type `0x16`.
- Receiver fields required by the branches taken.
- The current dispatch-table reference and the selected callable entry.

There are no explicit null, bounds, alignment, or callable-target checks. An inaccessible payload is not necessarily a problem for a non-`0x16` record, because the payload is not dereferenced on that branch.

## Behavior

### 1. Optional preprocessing

The function first reads the record discriminator at offset `0x04`.

If it is not `0x16`, preprocessing is skipped without reading a nested discriminator.

If it is `0x16`, the function reads the payload reference from record offset `0x08`, then reads the nested discriminator at payload offset `0x04`. The represented arithmetic subtracts `0x2500` and compares the result with `2`.

For ordinary defined 32-bit signed arithmetic, this condition selects nested discriminator `0x2502`. It does not select nested discriminator `2`.

When selected, the function reads the receiver integer at offset `0x10C`, converts it to plain character type, and passes that converted value to F-4fd087f2325e together with the receiver reference. The record reference is not an explicit argument to that dependency.

The character conversion narrows the receiver value before the call. Its exact interpretation for values outside the character type’s range depends on the target character width and signedness. In particular, the supplied evidence does not establish whether an eight-bit value with its high bit set is received as negative or nonnegative.

After F-4fd087f2325e returns normally, processing continues. Its return value does not terminate the dispatch chain.

### 2. Optional preliminary dispatch

The function rereads the record discriminator. It does not reuse the value from preprocessing.

If this new value is `0x16`, it rereads the payload reference and nested discriminator. If that nested discriminator is zero, it invokes F-I01:

- Read the receiver’s current dispatch-table reference.
- Select the entry at table offset `0x124`.
- Call that entry with the original receiver and record references.

A nonzero F-I01 result is returned immediately. No main or final dispatch follows.

If F-I01 returns zero, or its selection condition is false, processing continues.

This stage can become applicable because preprocessing changed the record. Conversely, preprocessing can make a previously applicable condition cease to hold.

### 3. Main dispatch

The function again reads the record discriminator.

If it is `0x16`, the function reads the current payload reference and then its nested discriminator. F-I02 is selected only when that nested discriminator is `0x2A`.

All other cases select F-I03, including:

- Any discriminator other than `0x16`.
- A `0x16` record with nested discriminator zero.
- A `0x16` record with nested discriminator `0x2502`.
- Any other nested discriminator.

After making this selection, the function reads the receiver’s current dispatch-table reference and loads the selected entry:

- Offset `0x10C` for F-I02.
- Offset `0x110` for F-I03.

The selected target receives the original receiver and record references.

A nonzero result is returned immediately. A zero result permits final dispatch.

Subject to earlier calls returning normally and F-I01 not returning nonzero, exactly one main handler is invoked. F-I02 and F-I03 are alternatives, not sequential handlers.

### 4. Optional final dispatch

After a zero main-handler result, the function reads the record discriminator again.

If this value is not `0x0F`, it returns zero without reading the record’s secondary field for the final comparison.

If it is `0x0F`, the function:

1. Reads the record’s secondary integer at offset `0x08`.
2. Reads the receiver integer at offset `0x50`.
3. Compares the two values.

If they differ, the function returns zero.

If they are equal, the function reads the receiver’s current dispatch-table reference, selects the entry at table offset `0x0E0`, and invokes F-I04 with the original receiver and record references.

A nonzero F-I04 result is returned unchanged. A zero F-I04 result leads to a zero return.

The final condition is based on the state after the main handler returns. It need not match the record’s initial discriminator or secondary value.

## Side effects

### Direct effects

No explicit store to receiver memory, record memory, payload memory, or global memory is shown in F-96d43ff36707.

Its directly established external interactions are reads and dependency calls. The absence of explicit stores does not make it side-effect-free: invoked dependencies may perform writes or other externally visible operations.

### Call ordering

The maximum normal call sequence is:

1. F-4fd087f2325e.
2. F-I01.
3. Either F-I02 or F-I03.
4. F-I04.

Each optional call requires its selection condition to hold at its own decision point. Every nonzero indirect-handler result suppresses all later calls.

These conditions can be satisfied across different states of the same record. The initial discriminator does not permanently determine the entire sequence.

### State visibility

No record snapshot or dispatch-table snapshot is retained across the whole operation.

Established rereads mean that changes made by earlier dependencies can affect:

- Whether the preliminary handler runs.
- Which main handler runs.
- Whether the final handler runs.
- Which runtime callable is obtained from a selected table slot.

This establishes visibility through later reads; it does not establish that any dependency actually mutates those locations.

### Ownership and lifetime

No allocation, explicit release, reference-count update, or ownership-transfer operation is shown.

The function passes references to dependencies, but the evidence does not establish whether those dependencies retain, release, or otherwise manage them. It is therefore not valid to promise that the receiver, record, payload, or globals remain alive or unchanged merely because a dependency was called.

For the stated normal behavior to continue, all subsequently accessed objects must remain usable after earlier dependencies return.

### Errors and abnormal completion

There is no explicit error-conversion or recovery path.

A nonzero handler result may represent successful handling, an error, or another status; its meaning is unknown. The function only applies zero-versus-nonzero control flow.

Invalid accesses, invalid indirect targets, dependency nonreturn, and other abnormal dependency behavior have no established recovery behavior.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence. They are not executed tests. Each assumes valid accessed memory, normal dependency return, and no unmentioned state changes.

### Ordinary record

Given a record whose discriminator is neither `0x16` nor `0x0F`:

- Preprocessing and F-I01 are skipped.
- F-I03 is called.
- If F-I03 returns zero and leaves the discriminator unchanged, the result is zero.
- The nested payload discriminator is never read.

### Special preprocessing value

Given an initial discriminator of `0x16` and nested discriminator `0x2502`:

- F-4fd087f2325e is called with the narrowed receiver field.
- If it leaves relevant state unchanged, F-I01 is skipped and F-I03 is selected.
- A preprocessing return value alone does not cause an early return.

### Zero nested discriminator

Given a stable `0x16` record with nested discriminator zero:

- F-I01 runs before the main handler.
- If it returns `-7`, the overall result is exactly `-7`; no main handler runs.
- If it returns zero, F-I03 runs next.

### Alternate main handler

Given a stable `0x16` record with nested discriminator `0x2A`:

- Preprocessing and F-I01 are skipped.
- F-I02 runs.
- F-I03 does not run.
- If F-I02 returns `5`, the function returns `5` without final dispatch.

### Matching final-dispatch record

Given a `0x0F` record whose secondary integer equals the receiver integer at offset `0x50`:

- F-I03 runs first.
- If F-I03 returns zero and preserves the relevant fields, F-I04 runs.
- If F-I04 returns `12`, the overall result is `12`.

A nonzero F-I03 result prevents F-I04 even though the comparison would otherwise match.

### Nonmatching final-dispatch record

Given the same discriminator but unequal comparison values, and a zero F-I03 result:

- The two integers are read and compared.
- F-I04 is not called.
- The result is zero.

### Preprocessing changes routing

Given an initial `0x16` record with nested discriminator `0x2502`, suppose F-4fd087f2325e changes the nested discriminator to zero:

- The next stage observes zero and invokes F-I01.
- If F-I01 returns zero and leaves that state unchanged, F-I03 follows.

Using the original nested discriminator for all decisions would violate the contract.

### Main handler enables final dispatch

Suppose the main handler returns zero after changing the record to discriminator `0x0F` and making its secondary integer equal the receiver field at offset `0x50`.

F-I04 is then eligible even if the record was not initially type `0x0F`.

### Dispatch-table replacement

Suppose F-I01 returns zero after replacing the receiver’s dispatch-table reference.

The main handler target must be loaded from the replacement table, not a table reference cached before F-I01.
