# F-4205bde72877

## Purpose

F-4205bde72877 conditionally performs two writes through an indirectly obtained address.

It reads a character from an indirect base plus an externally supplied displacement and compares that character with the second input using integer promotion and the usual arithmetic conversions. Equality returns without either explicit write. Inequality writes a character-converted version of the second input at offset `0xB43`, then writes the one-byte value one at offset `0xB90`.

The comparison displacement is unresolved. The comparison location must not be assumed to be the first write destination.

An interpretation such as “update a value and mark an object as changed” is plausible intent, not established behavior. The meanings of the two destinations and any ownership or lifecycle consequences remain unknown.

## Interface

The function accepts two inputs of the signed integer type:

- **Object-bearing address:** Used in integer address arithmetic to locate a base-address field at offset `0xF00`.
- **Requested value:** Used in the comparison and, on inequality, converted to the plain character type for storage.

There is no explicit return value, success flag, error code, or validation result. Normal completion occurs either at the equality return or after both writes.

The first input is an integer, not a declared object reference with a known layout or lifetime. The supplied representation establishes neither an allocation boundary nor ownership of the addressed storage.

## Behavior

### Comparison and numeric conversions

The comparison uses a base read from offset `0xF00` and the external displacement to locate a character. The relative evaluation order of the displacement and the base-field read is not established. Both contribute to the address before the character can be read.

The character undergoes integer promotion. The resulting operand and the requested signed integer then undergo the usual arithmetic conversions before equality is decided. The requested value is not first narrowed to the character type.

Two conversion cases matter:

- **The character promotes to the signed integer parameter type.** Both comparison operands then have that signed integer type. Equality compares the promoted character value directly with the requested integer.
- **The character promotes to the corresponding unsigned integer type.** This is possible if plain character is unsigned and the signed integer type cannot represent its full range. The requested signed integer is then converted to the unsigned integer type for comparison.

In the second case, a negative requested value can compare equal to a nonnegative character value. Conversion to the unsigned integer type is modulo one more than that type’s maximum value. In particular, negative one converts to the maximum unsigned integer value. If the character can represent that maximum and contains it, equality succeeds.

Consequently, the following range conclusion is conditional: **when the character promotes to the signed integer parameter type, a requested value outside the character’s possible promoted range cannot compare equal.** This conclusion applies to the conventional eight-bit-character, 32-bit-integer model. It does not apply unconditionally when character promotion produces an unsigned integer.

Plain-character signedness also matters before these conversions. A stored high-bit representation can denote a negative character value in a signed-character model and a nonnegative value in an unsigned-character model. The fragment does not select a signedness or signed representation.

### Equality path

Equality after all required comparison conversions causes an immediate return.

On this path:

- Neither explicit destination write occurs.
- The base field is not re-evaluated for either write.
- Neither write destination is separately read to check or preserve its previous contents.

Equality does not establish that offset `0xB43` already stores the requested value. The comparison displacement may select another location. Even if it selects that offset, the applicable comparison and storage conversions must be considered before drawing conclusions about stored representation.

Equality also does not establish that offset `0xB90` contains one. That location receives no explicit write on this path.

### Inequality path and access order

Inequality leads to two ordered assignments. The first uses another evaluation of the base field and writes the requested value, converted to the plain character type, at offset `0xB43`. After that assignment, the second uses a further evaluation of the base field and writes one at offset `0xB90`.

Thus the source-level access structure contains:

- One base-field evaluation on the equality path.
- Three base-field evaluations on the inequality path: one for comparison and one for each write.
- A comparison-character read before either explicit write.
- Completion of the first assignment before evaluation of the later assignment.

The function does not explicitly retain one base for all three accesses. A stable, noninterfering base field can yield the same base each time, but stability is not enforced.

These source-level evaluations do not guarantee an exact machine-load count. No volatile qualification or other requirement for a particular machine-level access trace is established by the fragment.

### Stored values

The first assignment converts the original requested signed integer to the plain character type. It does not store the comparison operand or an explicitly retained unsigned comparison result.

For an unsigned plain-character type, storage conversion is modulo one more than that character type’s maximum value. With eight-bit unsigned characters, this is modulo 256.

For a signed plain-character type, a representable requested value retains its numeric value. The outcome of an out-of-range conversion depends on the applicable implementation and language rules, which are not supplied. This contract does not promise a portable low-eight-bit result or unconditional normal completion for that case.

The second assignment stores one. It does not increment, toggle, accumulate, or combine the previous destination value.

### Arithmetic, layout, and aliasing

The address-field lookup and the two fixed-offset destination calculations use signed integer expressions in the supplied representation. Their widths are unknown, and defined modular wraparound must not be assumed. The external displacement’s type is not supplied, so the precise arithmetic conversions in the comparison-address addition are also unresolved.

No disjointness between the base field, comparison location, and write destinations is established.

The first write can therefore overlap storage belonging to the base field. If that write changes the field’s subsequently read value, the second assignment uses the changed base. A contract that forces both assignments to use the first write’s base would exclude this visible possibility.

With an unchanged base and ordinary byte-addressed interpretation, the fixed offsets differ by `0x4D`, or 77 bytes. That separation does not prove that the actual destinations are distinct when separate base evaluations yield different values. Nor does it prove that all accessed locations belong to one allocation.

## Acceptance examples

These examples are conditional static consequences, not runtime observations. Unless an example states otherwise, assume valid ordinary memory, valid arithmetic, a stable base, nonoverlapping relevant storage, and normal completion of conversions.

1. **Equality suppresses both writes.**  
   The comparison character promotes to signed integer value 12, and the requested value is 12. The function returns without either explicit write. If offset `0xB90` initially contains zero, this function does not set it to one.

2. **Inequality performs the ordered assignments.**  
   The comparison character promotes to signed integer value 12, and the requested value is 13. The character type represents 13. Offset `0xB43` receives 13, followed by offset `0xB90` receiving one.

3. **Equality can leave a different update destination untouched.**  
   The comparison displacement selects a location distinct from offset `0xB43`. Its character promotes to signed integer value 12, and the requested value is 12. A value of 99 at offset `0xB43` remains without an explicit update.

4. **Matching eventual storage values do not imply comparison equality.**  
   Assume eight-bit unsigned plain characters and 32-bit signed integers. The comparison character contains one, and the requested value is 257. The character promotes to signed integer one, so comparison is unequal. The first assignment stores one through modulo-256 conversion; the second stores one.

5. **Character signedness can change the branch in the conventional model.**  
   Assume eight-bit characters, 32-bit signed integers, and comparison representation `0xFF`. Under a two’s-complement signed-character model, that character promotes to negative one, so a requested value of negative one takes the equality return. Under an unsigned-character model, it promotes to signed integer 255, so the same requested value takes the unequal path. In that unsigned-character model, the first assignment stores 255 and the second stores one.

6. **Unsigned promotion can make negative one compare equal.**  
   Assume a target on which plain character is unsigned, its range reaches the corresponding unsigned integer maximum, and it promotes to that unsigned integer type because the signed integer type cannot represent its entire range. The comparison character contains that maximum, and the requested signed integer is negative one. The usual arithmetic conversions convert negative one to the unsigned maximum. Equality succeeds, and neither write occurs. This remains an equality case even though negative one is outside the promoted character’s nonnegative range.

7. **Aliasing can redirect the second write.**  
   Assume the first destination overlaps a byte of the base field and the first assignment changes that field into another valid, readable base value. The second assignment uses the newly evaluated field and addresses offset `0xB90` from that changed base.

8. **The marker assignment replaces the old value.**  
   On an unequal path with a stable, nonoverlapping base, an initial value of seven at offset `0xB90` becomes one. It does not become eight or a bitwise combination with one.

## Evidence

**Established static evidence:** The fragment declares two signed integer inputs and no return value. It compares a plain-character read with the requested integer, returns immediately on equality, and otherwise performs two ordered assignments through separately evaluated base-field expressions. The explicit fixed offsets are `0xF00`, `0xB43`, and `0xB90`. The first assignment converts the requested input to plain character; the second writes one.
