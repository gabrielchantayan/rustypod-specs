# F-5e3309c9d083

## Purpose

F-5e3309c9d083 performs header validation and release-like accounting for a nonzero address, then delegates a block operation to another function. A zero input returns immediately.

The established behavior is narrower than memory release: the function checks a preceding header, updates seven context-derived accounting locations in order, and calls dependencies. Whether the delegated operation frees, merges, recycles, or otherwise transforms storage is unknown.

The function has no explicit payload-relative access. That does **not** establish that payload storage is untouched: context-derived accounting addresses may alias the supplied address or other payload storage.

Allocator bookkeeping and paired synchronization are inferred intent, not established ownership, reclamation, or locking contracts.

## Interface

### Input and result

The function accepts one 32-bit integer used as an address.

- Zero returns without invoking dependencies or accessing the described storage.
- A nonzero value identifies an address whose preceding eight bytes contain the directly inspected header.
- The function returns no specified value.
- Normal completion follows the final dependency call.
- Invalid header conditions invoke a dependency marked nonreturning. Its termination mechanism is unknown.

A normally completing nonzero invocation requires accessible storage for every header, global-slot, and context-derived access actually reached. The function supplies no bounds, lifetime, or alignment checks establishing those conditions.

### Header layout

Offsets are byte offsets relative to the supplied address.

| Offset | Width | Use |
|---|---:|---|
| −8 | 32 bits | Validation word and source of masked accounting quantities |
| −4 | Unsigned 16 bits | First accounting selector |
| −2 | Unsigned 16 bits | Second accounting selector |

The header address passed to the final block dependency is the supplied address minus eight.

These explicit input-relative accesses precede the supplied address. However, the function also reads and writes context-derived addresses. If the retained context equals the supplied address minus eight, its accounting word at offset `0x008` is exactly the supplied address. Payload access through aliasing is therefore not excluded.

### Context-derived locations

A global pointer slot supplies a context address after the first two dependency calls. That address is retained for subsequent explicit operations.

| Context-relative offset | Width | Update |
|---|---:|---|
| `0x224 + 4 × first selector` | 32 bits | Subtract captured masked quantity |
| `0x30C` | 32 bits | Subtract captured masked quantity |
| `0x0E0 + 4 × second selector` | 32 bits | Subtract captured masked quantity |
| `0x220` | 32 bits | Subtract captured masked quantity |
| `0x310 + 4 × dependency result` | 32 bits | Decrement by one |
| `0x390` | 32 bits | Decrement by one |

These formulas do not establish separate arrays or nonoverlapping fields. Addressed locations may overlap one another, header fields, payload storage, or other relevant storage. No disjointness check is visible.

### Widths and arithmetic

The accounting mask is `0x3FFFFFFC`. It retains bits 2 through 29 and excludes bits 0, 1, 30, and 31. The resulting unsigned quantity is a multiple of four from zero through `0x3FFFFFFC`.

Each header selector is unsigned 16-bit, ranging from zero through 65,535. Scaling by four produces zero through 262,140 before context and fixed-offset additions. Neither selector is range-checked against an object or table boundary.

The selector dependency returns a 32-bit integer used in a scaled address expression. No negative-result rejection or upper-bound check is visible.

The four initial subtractions and final masked subtraction use unsigned 32-bit quantities, producing modulo-2³² subtraction results. The two decrement expressions are represented using signed 32-bit integers. No saturation or explicit underflow handling is shown, but language-level behavior at signed-overflow boundaries is not independently established. Wrapping examples for those decrements are conditional on 32-bit machine wrapping semantics.

Address calculations also use 32-bit values. Valid-address preconditions are required; the supplied material does not establish portable overflow semantics or a policy for wrapped addresses.

## Behavior

### Zero input and preparation

Zero input returns immediately. No dependency call, context lookup, header inspection, or accounting access occurs.

For a nonzero input, the function invokes:

1. F-187ab9ba4eb6, without explicit arguments.
2. F-2fd8826557a4, without explicit arguments.

It then reads the global context-pointer slot and retains the resulting address.

Additional zero checks appear after the initial check, but the supplied input value is not reassigned. They introduce no additional reachable branch under ordinary execution of the represented function.

Neither preparation dependency is assumed to preserve global state or block storage. Their changes to the global slot can affect the context subsequently captured.

### Header validation

The function identifies the header word eight bytes before the supplied address.

It rejects either of these conditions:

- The first header-word read is zero.
- Otherwise, bit 0 is set in the header-word read for the second condition.

The first condition short-circuits the second. A zero first read therefore reaches rejection without evaluating the bit-test operand.

Rejection calls F-a817d8d58c10, marked nonreturning. The context-entry dependency, accounting updates, and final dependencies are not reached on that path. Preparation calls and the context-pointer lookup have already occurred.

For stable storage, validation accepts exactly a nonzero header with bit 0 clear. A positive masked quantity is not required: a word containing only bit 1, bit 30, or bit 31 can pass while its masked quantity is zero.

Validation does not set or clear header flags. The meanings of the tested and excluded bits remain unknown.

### Context entry and quantity capture

After successful validation, F-c0fc6d033caa receives the retained context address.

The function then:

- Reads the unsigned 16-bit first selector at input offset −4.
- Forms the corresponding context-derived counter address.
- Reads the header word again and masks it with `0x3FFFFFFC`.

This masked quantity is captured for the next four accounting subtractions.

The validation reads do not supply the captured quantity. Changes made by F-c0fc6d033caa can therefore affect both the first selector and the quantity used for accounting. No validation is repeated after that call.

### Four initial accounting updates

The following read-modify-write operations occur in order:

1. Subtract the captured quantity at context offset `0x224 + 4 × first selector`.
2. Subtract that quantity at context offset `0x30C`.
3. Read the unsigned 16-bit second selector at input offset −2, then subtract the captured quantity at context offset `0x0E0 + 4 × second selector`.
4. Subtract the captured quantity at context offset `0x220`.

Each target’s current 32-bit value supplies its subtraction, and that operation completes before the next listed update.

The second selector is read after the first two writes. An earlier write that aliases its storage can change the selector subsequently used.

The captured quantity remains fixed throughout these four updates. If an update aliases and modifies the header, that does not change the already captured quantity. If targets alias one another, later updates use the values resulting from earlier writes.

### Count updates

After the four subtractions, F-09dcb55e8e0a is called without explicit arguments.

Its result selects the word at context offset `0x310 + 4 × result`. The function decrements that word by one, then decrements the word at context offset `0x390` by one.

A result of 32 makes the selected offset equal `0x390`. The same word is then decremented twice in sequence.

The context address is not reloaded after this dependency. Changes to the global context-pointer slot do not redirect subsequent explicit accesses, although changes to storage reached through the retained context can affect them.

### Final accounting and delegation

After both decrements, the function reads the header again, applies `0x3FFFFFFC`, and subtracts that fresh quantity from the word at context offset `0x008`.

This quantity need not equal the quantity captured for the first four subtractions. Dependency effects or preceding aliased writes may have changed the header. No further validation occurs.

The expression requires both a header read and a destination-word read before the destination write. The supplied representation does not establish their relative evaluation order within that final subtraction.

The function then invokes:

1. F-cc6c9b4a0f68 with the retained context address and the header address.
2. F-e586bff64fb7 with the retained context address.

Normal return follows the second call. No further explicit header or counter accesses are shown.

## Side effects

An accepted nonzero path reaching completion performs seven explicit 32-bit accounting read-modify-write operations:

- Four subtractions using one captured masked quantity.
- Two decrements.
- One subtraction using a fresh masked quantity.

Seven operations do not imply seven distinct words. Aliasing can make multiple updates affect the same storage.

There is no payload-preservation guarantee. Although no accounting expression is explicitly based on a payload offset, context-derived accesses may target payload storage. In particular, when the context equals input minus eight, the final update at context offset `0x008` directly reads and writes the word at the supplied address.

The function does not explicitly rewrite the header as a header-management step. Nevertheless, accounting writes may modify header storage through aliasing, and dependencies may modify it independently.

Dependency side effects are not bounded by this body. No assumption is made that a dependency:

- Preserves globals, counters, selectors, or header contents.
- Acquires or releases a lock.
- Maintains the lifetime or accessibility of either object.
- Allocates, releases, or transfers ownership of storage.
- Returns normally, apart from the explicit nonreturning annotation on F-a817d8d58c10.

F-c0fc6d033caa and F-e586bff64fb7 resemble entry and exit operations around shared-state updates. That interpretation does not establish synchronization.

No transaction, rollback, or compensating update is shown. If execution stops after some writes, the function contains no visible recovery path undoing them. Invalid accesses and dependency failures have no locally specified handling.

## Acceptance examples

These are conditional consequences of static evidence, not runtime test results. Unless specified otherwise, assume accessible addresses, stable relevant storage except for listed updates, normally returning dependencies, and distinct accounting targets that do not overlap the header.

### Zero input

For input zero:

- The function returns.
- No dependency is called.
- No global-context or header read occurs.
- No explicit accounting write occurs.

### Zero header

If the first header read is zero:

- Both preparation calls and the context lookup occur first.
- F-a817d8d58c10 is invoked.
- The bit-test condition is not evaluated.
- No context-entry call or accounting update is reached.

### Rejected flag

For a stable header of `0x00000005`, the word is nonzero but bit 0 is set. Validation invokes F-a817d8d58c10. No masked accounting subtraction is reached.

### Ordinary nonzero quantity

For a stable header of `0x00000022`, first selector 2, second selector 3, and F-09dcb55e8e0a returning 4:

- Validation succeeds.
- The captured masked quantity is 32.
- The first four targets are context offsets `0x22C`, `0x30C`, `0x0EC`, and `0x220`, in that order.
- The decrement targets are `0x320`, then `0x390`.
- The final target is `0x008`, reduced by 32 if the header remains unchanged.
- F-cc6c9b4a0f68 receives the retained context and input minus eight.
- F-e586bff64fb7 subsequently receives the retained context.

### Accepted zero quantity

For a stable header of `0x40000002`:

- Validation succeeds.
- Both masked quantities are zero.
- All five subtraction operations still occur, leaving their numerical target values unchanged.
- Both decrements and both final calls still occur.

### Header mutation between accounting stages

Suppose the captured quantity is 32, and F-09dcb55e8e0a changes the header so its masked quantity becomes 64.

The first four subtractions use 32. The final subtraction uses 64, provided no subsequent operation changes the header again. The function imposes no equality check between these quantities.

### Coincident decrement targets

If F-09dcb55e8e0a returns 32, both decrement operations target context offset `0x390`.

Starting from 10, that word becomes 9 and then 8. Conditional on 32-bit wrapping semantics, starting from zero instead produces `0xFFFFFFFF` and then `0xFFFFFFFE`. No explicit underflow rejection intervenes.

### Payload access through context aliasing

Assume:

- The retained context equals the supplied address minus eight.
- The header remains `0x00000022`.
- Both header selectors are zero.
- F-09dcb55e8e0a returns zero.
- Dependencies do not change the relevant storage.
- The 32-bit word at the supplied address initially contains 100.

The earlier accounting targets do not coincide with that payload word under these conditions. The final target, context offset `0x008`, is exactly the supplied address.

The final subtraction therefore reads 100 from the supplied address and writes 68 there. This is direct payload storage access through a context-derived address, despite the absence of an explicit payload-relative expression.
