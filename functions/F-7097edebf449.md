# F-7097edebf449

## Purpose

F-7097edebf449 operates on a container-like object whose storage consists of 40-byte records. It accepts an enclosing object address and a source-record address, updates storage-related state, and returns a 32-bit value interpreted in the supplied representation as an address.

**Inferred intent:** append a copy of the source record, obtaining additional storage when necessary. The records appear to contain two nested sequences, another subobject, a 32-bit field, and a byte field.

**Established limitation:** the visible behavior is not uniformly describable as a conventional append operation. The three principal branches have different return expressions. One full-container branch contains a backward traversal that, under ordinary unchanged-state assumptions, does not terminate after a small number of records. Calls with incomplete argument information also prevent establishing some destination addresses.

This contract therefore specifies the visible operations and their ordering without correcting anomalous behavior or assigning undocumented semantics to dependencies.

### Output

The visible result is a 32-bit address-like value, but its meaning depends on the branch:

- Existing-capacity branch with an initial logical end of zero: zero.
- Existing-capacity branch with a nonzero initial logical end: the second F-f4fd698ba468 result minus 16.
- Full-container branch taking the first capacity comparison’s true path: the logical end saved at function entry.
- Reallocation branch: the newly stored outer storage limit, not the inserted-record address.

There is no visible, branch-independent success flag or error code.

The function first obtains the address of the outer descriptor at enclosing-object offset +20 and reads the logical end at offset +24.

It compares that saved logical end against the storage limit read at offset +28.

- Unequal values select the existing-capacity path.
- Equal values select one of two full-container paths.

The saved logical end is retained for later operations even where the live descriptor is reread.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Unequal end and limit, zero end.**  
   Given a readable descriptor with logical end zero and a nonzero storage limit, the function writes 40 to the logical-end field and returns zero. It does not enter the nested allocation work.

2. **Existing capacity with stable small nested counts.**  
   If both calls for the first nested count return 5, and both calls for the second return 3, the allocation requests are respectively 256 and 1,280 bytes, each with a second argument of zero. Subject to unchanged destination bases, the corresponding logical ends are base plus 40 and base plus 120. Capacity endpoints use 32 elements, not the smaller counts.

3. **Count changes across a copy dependency.**  
   If the first 8-byte nested count is 5 and the later count is 7, the allocation still requests 256 bytes, while the logical-end expression uses 56 bytes. The function does not recompute capacity from the second count.

4. **Ordinary growth arithmetic.**  
   If reallocation is selected and its growth-count call returns 64, the candidates are 96 and 104. The allocation request is 4,160 bytes. If the retained final outer count is also 64 and address arithmetic is valid, the final end is new base plus 2,600, the limit is new base plus 4,160, and the return equals that limit.

5. **Backward traversal with an unchanged end.**  
   If the preliminary calls leave the outer end unchanged and their comparison selects the traversal branch, a short one-record append is not an acceptable characterization. The visible loop continues backward by 40-byte steps unless access failure, dependency behavior, or eventual modular equality changes the outcome.

6. **Wrapped allocation arithmetic.**  
   If a selected count multiplied by its stride wraps at 32 bits, acceptance follows the wrapped request visible at the dependency boundary. This function supplies no local rejection for that condition.
