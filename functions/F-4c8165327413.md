# F-4c8165327413

## Purpose

F-4c8165327413 transforms one of two selectable 32-bit fields in a sequence of fixed-size records. It first initializes per-record working fields, processes groups according to a mode-specific flag, and then copies the working result back into the selected field.

The established behavior has three group cases:

- **No flagged record:** no group-specific transformation occurs.
- **Exactly one flagged record:** the function applies that record’s working-field difference to every other record in the group.
- **Multiple flagged records:** the function delegates ranges between flagged records, including boundary ranges, to F-04cc69fad3ed.

**Inferred intent:** the selected fields may represent two coordinate components, with flagged records acting as anchors. Neither coordinate semantics nor the transformation performed by F-04cc69fad3ed is established here. This contract therefore uses neutral terms such as “selected field,” “reference field,” and “flagged record.”

## Interface

### Inputs

The function takes two inputs:

1. **Context address:** represented as a 32-bit integer in the supplied interface and used as an address.
2. **Mode selector:** a 32-bit integer. Zero selects one mode; every nonzero value selects the other. Positive and negative nonzero values are equivalent for the visible mode decisions.

The context is accessed using the following byte offsets:

| Offset | Width | Meaning |
|---|---:|---|
| +0x1C | 32 bits | Record count |
| +0x20 | 32-bit address | Base of the contiguous record sequence |
| +0x28 | 32 bits | Group-table entry count |
| +0x2C | 32-bit address | Base of the group table |

Each group-table entry is a 32-bit address identifying the first record of a group.

### Record layout

Records have a stride of **40 bytes**. The visible accesses establish the following fields; they do not establish the meanings of the intervening bytes.

| Record offset | Width | Visible use |
|---|---:|---|
| +0x00 | 16 bits | Flags |
| +0x04 | 32 bits | Zero-mode reference source |
| +0x08 | 32 bits | Nonzero-mode reference source |
| +0x10 | 32 bits | Zero-mode selected field |
| +0x14 | 32 bits | Nonzero-mode selected field |
| +0x18 | 32 bits | Working result |
| +0x1C | 32 bits | Working reference |
| +0x24 | 32-bit address | Inclusive group endpoint, read from the group’s first record |

The last field occupies bytes 36–39 of the 40-byte record. It is read as a pointer, not as an element count or relative offset.

### Outputs and ownership

There is no explicit return value. Results are communicated through memory writes and dependency effects.

The function performs no visible allocation, deallocation, or ownership transfer. It accesses caller-supplied records and the group table in place. F-04cc69fad3ed’s ownership behavior is unknown; the visible call sites do not establish that it preserves, retains, or releases any supplied object.

### Preconditions

For a defined, successful traversal:

- The context and all accessed fields must be readable.
- Record fields written by this function must be writable.
- Record and group-table addressing must be valid for the underlying 32-bit execution environment.
- Counts and address calculations must describe valid ranges without unsupported overflow.
- Group endpoints must be inclusive endpoints reachable from their corresponding group starts in 40-byte steps.
- The single-flag arithmetic must either remain within the supported signed 32-bit range or have separately established target-specific overflow semantics.
- Any memory or state required by F-04cc69fad3ed must satisfy that dependency’s contract, which is not supplied.

The function does not validate these conditions or expose a structured error result.

## Behavior

### 1. Capture traversal state and choose the mode

The function reads the record base, the group-table base, and the group-table entry count, in that order. It computes a group-table end address using four bytes per entry.

It then selects the flag mask:

| Mode selector | Flag mask | Selected field | Reference source |
|---|---:|---:|---:|
| Zero | 0x0040 | +0x10 | +0x04 |
| Nonzero | 0x0080 | +0x14 | +0x08 |

After this selection, it reads the record count and computes the record-sequence end address using 40 bytes per record.

These bases and end addresses are retained for the visible traversal. They are not reread from the context after dependency calls.

### 2. Initialize every record’s working fields

The function traverses the contiguous record sequence in increasing address order. At each record, it performs two 32-bit copies, in this order:

1. Read the selected field and write it to the working result at +0x18.
2. Read the mode-specific reference source and write it to the working reference at +0x1C.

Thus:

- Zero mode initializes the working result from +0x10 and the working reference from +0x04.
- Nonzero mode initializes the working result from +0x14 and the working reference from +0x08.

All initialization completes before any group-table entry is processed. A group is not initialized on demand when its table entry is encountered.

The copies preserve the 32-bit field contents. Their interpretation as signed integers matters later only in the single-flag arithmetic.

### 3. Process group-table entries in order

For each group-table entry, the function:

1. Reads the group-start address from that entry.
2. Reads the inclusive endpoint address from offset +0x24 of the first group record.
3. Searches for records whose 16-bit flags contain the selected mask.

Group processing follows table order. The visible implementation does not sort, deduplicate, or reject overlapping groups. If the same record is processed more than once, later processing can observe working-field changes made earlier.

The group endpoint is captured once for that group. Flag fields, by contrast, are read as the searches reach them; the function does not snapshot all flags before calling dependencies.

### 4. Find the first flagged record

Starting at the group’s first record, the search advances in 40-byte steps. It reads a candidate’s 16-bit flags only while the candidate address is at or before the inclusive endpoint.

The search stops when either:

- A candidate contains the selected mask; or
- The candidate address has advanced beyond the inclusive endpoint.

For a valid nonempty group with no matching flags, the search examines the endpoint record and then advances one record past it. It does not read flags at that past-end address.

If no flagged record is found, group processing ends without a group-specific write or dependency call.

### 5. Handle exactly one flagged record

After locating the first flagged record, the function scans later group records for additional flags.

If none is found, it reads the flagged record’s working result and working reference as two signed 32-bit values, in that order. Their difference is the group adjustment.

It then updates every other group record:

- Records before the flagged record are updated first, in ascending address order.
- Records after the flagged record are updated next, also in ascending address order.
- Each update reads that record’s working reference and writes the reference plus the group adjustment to its working result.
- The flagged record’s working result is not rewritten by this branch.

No F-04cc69fad3ed call occurs in this case.

The two values used to calculate the adjustment are captured before these updates. The adjustment is not recalculated from each record, and it is not a difference involving the record being updated.

### 6. Handle multiple flagged records

Whenever the forward scan encounters another flagged record, it calls F-04cc69fad3ed with four visible address arguments:

1. The record immediately after the preceding flagged record.
2. The record immediately before the newly encountered flagged record.
3. The preceding flagged record.
4. The newly encountered flagged record.

The newly encountered flagged record then becomes the preceding flagged record for the next such call.

This call is made even when the two flagged records are adjacent. In that case, the first supplied range boundary is the later flagged record, while the second is the earlier flagged record. The caller does not suppress or normalize this reversed boundary pair.

After the forward scan finishes, the function makes another four-address call:

1. The record immediately after the last flagged record.
2. The captured inclusive group endpoint.
3. The last flagged record.
4. The first flagged record.

This call also occurs when the last flagged record is the group endpoint, producing a first boundary beyond the second boundary.

Finally, if the **overall record-sequence base address** is less than the first flagged record’s address, the function makes a further call to F-04cc69fad3ed. The supplied representation shows only two explicit arguments:

1. The group’s first record.
2. The record immediately before the first flagged record.

This condition is not a comparison between the group start and the first flagged record. Consequently, a group beginning after the overall record base can trigger this call even if its first record is already flagged.

The dependency’s result is not inspected. The visible caller does not test a success indicator, and it does not restore working fields or flags after a call.

### 7. Copy working results back to the selected field

After all group-table entries have been processed, the function traverses the original contiguous record sequence in increasing address order.

For each record, it reads the 32-bit working result at +0x18 and writes it to:

- +0x10 in zero mode; or
- +0x14 in nonzero mode.

This pass covers the whole original record sequence, including records not named by any group.

The function does not directly copy the working reference back to either reference source. It leaves the working fields in memory rather than clearing or restoring them.

## Side effects

### Direct writes

The function directly writes:

- Every traversed record’s working result during initialization.
- Every traversed record’s working reference during initialization.
- Non-anchor working results in single-flag groups.
- Every traversed record’s selected field during final copy-back.

It does not directly write the context, group-table entries, flags, endpoint pointers, or the unselected field.

These are statements about direct accesses only. Dependency effects and overlapping memory can produce additional changes.

### Ordering and aliasing

The visible phase order is significant:

1. Capture traversal metadata.
2. Initialize all records.
3. Process groups in table order.
4. Copy all working results back.

Within each initialization step, the working-result write precedes the reference-source read. Within single-flag updates, the working reference is read before the corresponding working result is written.

If the context, group table, records, or dependency-accessed memory overlap, these writes can affect later reads. The function neither detects nor isolates such overlap.

### Failure and partial progress

There is no visible error reporting, rollback, or cleanup path. An invalid address, unsupported arithmetic result, or dependency failure may interrupt execution after earlier writes have occurred.

No atomicity, synchronization, or thread-safety guarantee is established.

## Acceptance examples

These are conditional examples derived from static evidence. They have not been executed. Unless otherwise stated, memory is valid, arithmetic is representable, and distinct described objects do not overlap.

### Mode selection and initialization without groups

Given one record with:

- Zero-mode selected field: 120
- Nonzero-mode selected field: 300
- Zero-mode reference source: 20
- Nonzero-mode reference source: 70
- Group-table entry count: zero

Then:

- Zero mode leaves the working result at 120 and the working reference at 20, and copies 120 back to the zero-mode selected field.
- Any nonzero mode leaves the working result at 300 and the working reference at 70, and copies 300 back to the nonzero-mode selected field.

The unselected field is not directly modified.

### One flagged record

Given a three-record group in zero mode with only the middle record containing flag 0x0040, suppose initialization yields:

| Record | Working result | Working reference |
|---|---:|---:|
| First | 900 | 10 |
| Middle | 100 | 30 |
| Last | −5 | 50 |

The adjustment is 70. The resulting working results, and subsequently the selected fields, are 80, 100, and 120. No dependency call occurs.

### No selected flag

Given a valid group in zero mode whose records contain no 0x0040 flag, the function performs no group-specific transformation. A 0x0080 flag alone does not qualify in this mode.

If no other group or dependency changes those records, their initialized working results are copied back unchanged.

### Adjacent flagged records

Given exactly two adjacent flagged records, the function calls F-04cc69fad3ed for the interval between them despite the reversed boundaries. It subsequently makes the trailing call. Exact resulting record values remain documented_only because the dependency behavior is unknown.

### Leading-call condition uses the overall base

Given a group starting after the overall record-sequence base, with its first record flagged and at least one later flagged record, the leading two-explicit-argument call is made. Its second boundary is one record before the group start.

This follows from the overall-base comparison; it is not evidence that the supplied range is valid for the dependency.

### Zero records does not independently disable group processing

If the record count is zero, the initialization and final copy-back passes perform no iterations. A positive group-table count can still cause group reads, writes, and dependency calls. Safe behavior therefore cannot be inferred from the record count alone.
