# F-62f5664b0a3b

## Purpose

F-62f5664b0a3b performs a range-oriented mutation of a container-like object, publishes a 32-bit result through caller-provided storage, and returns a packed 64-bit value.

Two execution paths are established:

- A special path calls a bulk-operation dependency and resets several fields to an empty-looking configuration.
- Otherwise, a loop advances a cursor and calls a per-element mutation dependency until a comparison returns **exactly 1**.

The field layout, comparisons, and reset pattern suggest range erasure in a sentinel-based ordered container. That interpretation is **inferred intent**, not an established requirement on the dependencies. The directly supported contract is the sequence of accesses, calls, writes, and return-value construction below.

## Interface

### Inputs

The function receives four arguments:

| Argument | Established representation | Direct use |
|---|---|---|
| Output slot | Address of writable 32-bit storage | Receives an initial container field and subsequent path-dependent values. |
| Container address | 32-bit address-like value | Base for fields at byte offsets `0x10` and `0x14`; also passed to dependencies. |
| Cursor storage | Address of 32-bit storage | Passed to comparison and advancement dependencies; its first word is read during each loop iteration. |
| Boundary operand | 32-bit opaque value | Passed to comparison dependencies. The function does not directly dereference it. |

The boundary operand is used in positions consistent with an address of iterator-like storage, but its actual representation is a dependency contract that is not supplied.

### Return value

The return is a 64-bit bit-pattern formed by concatenating two 32-bit words:

- Bits 63–32: the upper result word.
- Bits 31–0: the lower result word.

This is bit concatenation, not signed arithmetic. The signedness of address-like words does not change their placement in the result. No semantic designation such as “success code” or “returned iterator” is established for the packed value.

The output-slot write is a separate observable result. It must not be assumed to equal either half of the return on every path.

### Directly accessed layout

All listed fields are 32 bits wide, and all offsets are in bytes.

| Base | Offset | Established use |
|---|---:|---|
| Container | `0x10` | Address-like link, repeatedly read |
| Container | `0x14` | Nonzero gate for the special path; set to zero on that path |
| Object referenced by container `+0x10` | `0x04` | Passed to the bulk-operation dependency; later set to zero |
| Same referenced object | `0x08` | Read for the initial comparison snapshot; later set to the current container link |
| Same referenced object | `0x0C` | Set to the current container link |
| Cursor storage | `0x00` | Captured before each cursor-advancement call |

For descriptive purposes, the object referenced by container `+0x10` is called the **linked object**. Calling it a sentinel is an inference.

### Preconditions

For a normal, defined execution:

- The output slot must permit the 32-bit writes actually reached.
- Container and linked-object accesses must refer to valid, suitably accessible storage.
- Cursor storage must permit the direct 32-bit reads reached in the loop and whatever operations its dependencies require.
- Dependency-specific preconditions must hold.

No null checks, bounds checks, allocation checks, or explicit address validation are visible. Alignment requirements and the consequences of invalid addresses are not established by the supplied evidence.

Distinctness between arguments is not enforced. Aliasing can change later reads and therefore behavior.

## Behavior

### 1. Initial publication and snapshot

The function first reads the 32-bit link at container `+0x10` and writes that value to the output slot.

It then reads container `+0x10` again and reads the word at offset `0x08` of the resulting linked object. That word is stored in temporary 32-bit storage for comparison.

These are separate reads of the container link. The function does not establish an immutable entry-time linked-object address.

This order matters if the output slot aliases the container, the linked object, or cursor storage: the initial output write occurs before the snapshot read and before any dependency call.

Two result words are initialized for later use:

- The lower result word initially contains the output-slot address.
- The upper result word initially contains the container address.

A separate temporary word initially receives the cursor-storage address. On entry to the special-path checks, that temporary is replaced with a fresh read of container `+0x10`.

### 2. Special-path recognition

The function calls **F-8e016e73ddbc** with:

1. The cursor-storage argument.
2. The address of the temporary snapshot taken from linked-object `+0x08`.

Any nonzero return enters the next recognition step. A zero return bypasses the remaining special-path checks and proceeds to the loop.

If the first return is nonzero:

1. The function reads container `+0x10` into another temporary word.
2. It calls **F-8e016e73ddbc** with the boundary operand and the address of that temporary.
3. If this second call returns nonzero, it reads container `+0x14`.

The special path is taken only when all three conditions hold:

- The first comparison returns nonzero.
- The second comparison returns nonzero.
- The subsequent read of container `+0x14` is nonzero.

If the second comparison returns zero, the field at container `+0x14` is not read by this gate.

The gate is a zero/nonzero test over a 32-bit field. A value with its high bit set still qualifies as nonzero; positivity is not required.

The dependencies receive addresses of temporary words. Those words are not assumed immutable across the calls. The first snapshot and second temporary are not subsequently used as authoritative copies of the container link.

### 3. Special-path mutation

When the gate succeeds, the function reads the current linked object from container `+0x10`, obtains its field at offset `0x04`, and calls **F-b11699857ce8** with:

1. The container address.
2. That 32-bit field value.

After this call returns normally, the function performs the following direct updates in the listed statement order:

1. Set linked-object `+0x08` to the current value of container `+0x10`.
2. Set linked-object `+0x04` to zero.
3. Set linked-object `+0x0C` to the current value of container `+0x10`.
4. Set container `+0x14` to zero.
5. Read container `+0x10` and write the resulting word to the output slot.

The linked-object accesses use fresh reads of container `+0x10`; they are not explicitly tied to the object used before the dependency call. Therefore, if F-b11699857ce8 changes that link, the subsequent updates follow the post-call link.

Within a single assignment that both reads the container link as a value and uses it to locate a destination, the evidence does not establish the relative order of those constituent reads. It does establish the ordering between the separate updates above.

The function then returns:

- Upper 32 bits: the link value just read and written to the output slot.
- Lower 32 bits: the lower result word, initialized to the output-slot address and not explicitly reassigned on this path.

No loop comparison or per-element dependency is executed after this special-path return.

The final output write occurs after the reset writes. If the output slot aliases one of the reset fields, that final write can overwrite the reset value.

### 4. Iterative path

If the special path is not taken, the function repeatedly calls **F-8e016e73ddbc** with the original cursor-storage argument and the original boundary operand.

The loop terminates only when this call returns **exactly 1**.

This differs from special-path recognition:

- Special-path comparisons accept any nonzero result.
- The loop-stop comparison accepts only 1.
- Zero, negative results, and positive results other than 1 all cause a loop body execution.

For each body execution, the following order is established:

1. Read the 32-bit word currently stored at the cursor-storage address and capture it.
2. Call **F-de786f046894** with the cursor-storage argument.
3. Replace the lower result word with the captured pre-advancement word.
4. Call **F-646805e2d5b7** with:
   - The address of the upper result word.
   - The container address.
   - The address of the lower result word.
5. Read the current upper result word and write it to the output slot.

The cursor-storage address is unchanged as an argument, but the storage it designates may be changed by dependencies. Each iteration takes a new capture from that storage.

The per-element dependency receives writable access to both result words. Consequently:

- The upper result word after the call is not assumed to remain the container address.
- The lower result word after the call is not assumed to remain the captured cursor word.
- The subsequent output write uses the post-call upper result word.
- The eventual packed return uses the result words as they stand when the loop terminates.

Advancement occurs before the per-element dependency. The latter is given a copy of the pre-advancement cursor word, rather than the cursor-storage address itself as its third argument.

After each body execution, the next loop comparison occurs. There is no explicit iteration limit.

### 5. Iterative return

When a loop comparison returns exactly 1, the function immediately returns the packed result words:

- Upper 32 bits: the current upper result word.
- Lower 32 bits: the current lower result word.

There is no additional output-slot write on loop termination.

If the loop executes zero bodies, the function’s own initializations leave:

- Upper result word: the container address.
- Lower result word: the output-slot address.

The function’s direct output-slot write on that path remains the initial write of container `+0x10`. Dependency side effects may still affect caller-visible storage.

The function itself writes:

- The output slot at entry.
- The output slot after every completed per-element dependency call.
- On the special path, linked-object fields at offsets `0x08`, `0x04`, and `0x0C`, followed by container `+0x14`, followed by the output slot.

No direct allocation, deallocation, global write, or I/O operation is shown.

If the loop comparison never returns exactly 1, no normal return is reached, assuming execution otherwise continues.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Unless stated otherwise, assume valid, distinct storage, normal dependency returns, and no dependency side effects beyond those explicitly described.

### Special path with a stable link

Suppose both recognition comparisons return nonzero and container `+0x14` contains 3. Suppose F-b11699857ce8 leaves container `+0x10` unchanged.

Expected behavior:

- The bulk dependency receives the container and the then-current linked-object `+0x04` value.
- Linked-object `+0x08` and `+0x0C` become the link value.
- Linked-object `+0x04` and container `+0x14` become zero.
- The output slot receives the link value.
- The return has that link value in its upper half and the output-slot address in its lower half.

### Empty-looking gate falls through

Suppose both recognition comparisons return nonzero, but container `+0x14` is zero.

Expected behavior:

- The bulk dependency is not called.
- No special-path reset writes occur.
- A loop comparison is still performed.
- If that comparison returns exactly 1 immediately, the packed return contains the container address above the output-slot address.

The output slot was nevertheless written at entry.

### A noncanonical true value does not stop the loop

Suppose the loop comparison returns 2.

Expected behavior: the body executes. Treating 2 as a loop-stop result would violate the established exact comparison against 1.

If 2 is instead returned by either recognition comparison, it satisfies that recognition step’s nonzero condition.

### One completed iteration

Suppose a loop comparison returns zero, cursor storage contains a word identifying element A, and advancement changes cursor storage to identify element B. Suppose the per-element dependency writes result words U and L, and the next comparison returns 1.

Expected behavior:

- Element A’s word is captured before advancement.
- The per-element dependency initially receives A’s word through the lower-result storage.
- The output slot receives U after that dependency returns.
- The function returns U in the upper half and L in the lower half.
- No additional output write occurs at termination.

### Bulk dependency changes the link

Suppose the special-path gate succeeds, and F-b11699857ce8 replaces container `+0x10` with another valid linked-object address.

Expected behavior: subsequent reset accesses follow fresh reads of the replacement link, not a cached pre-call address.
