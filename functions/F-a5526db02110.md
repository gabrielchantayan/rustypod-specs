# F-a5526db02110

## Purpose

F-a5526db02110 conditionally updates an indexed table and neighboring object links, then clears bit 0 of the supplied object’s flag byte.

The updates are consistent with removing an object from an indexed doubly linked list. That interpretation is inferred intent, not a validated structural guarantee. The function neither checks reciprocal links nor establishes that the object is reachable from the selected table entry.

The operation has no return value. It does not allocate or release memory, explicitly clear the supplied object’s links, or report whether a removal occurred.

The sole argument represents the supplied object’s address. The supplied representation uses an integer-typed argument for address comparisons and memory accesses; it does not establish a public pointer type or nullable-handle convention.

The function returns no value or status. Its observable behavior consists of memory reads, conditional writes, and return if those operations complete. Invalid-access and out-of-range arithmetic behavior are not defined by an explicit error-handling path.

Link values are tested against zero and used to form addresses. Their stored width is four bytes. Byte order and the target’s complete address representation remain unspecified.

### External table state

An external memory location supplies the table base address. Table entries are four bytes wide.

For an index-field value \(n\), the selected entry address is:

\[
\text{table base} + 4 \times (n - 1)
\]

**Subtraction occurs before scaling.** The address is not \(\text{table base} + 4 \times n - 1\).

For ordinary representable arithmetic, index 1 selects the entry at the base, index 2 selects the entry four bytes after the base, and index 3 selects the entry eight bytes after the base. A one-based selector is therefore the apparent intended convention.

The evidence does not establish table capacity, allocation, or valid index bounds. The external base is read for the initial table access and read again if the head-update branch is taken.

The function performs no explicit address, bounds, alignment, or structural validation.

## Behavior

### Initial membership gate

The first established access reads the supplied object’s flag byte at `+0x14` and tests bit 0.

If bit 0 is clear, the function returns without any subsequent object-field reads, table accesses, or writes established by the body. Bits 1 through 7 do not affect this decision.

If bit 0 is set, the function continues through the update sequence. It does not test membership again before changing links.

### Table selection

The function reads the four-byte index field, subtracts one, and retains that adjusted value for table addressing. Each table-entry address uses four times that retained value:

\[
\text{entry address} = \text{currently read table base} + 4 \times (\text{initial index value} - 1)
\]

The index field is not reread for the later table-head write. Thus, a change to that field after selection does not cause the write to select a different index.

The selected four-byte table entry is read and retained for the head comparison. The head case requires both:

- The retained entry equals the supplied object address.
- The retained entry is nonzero.

For a nonzero supplied address, equality already implies the second condition, but the nonzero condition remains part of the observed decision.

No table bounds are consulted. Zero, negative, and oversized index values are not explicitly rejected. Their validity and arithmetic consequences depend on target details that are not established here.

### Table-head or preceding-object update

One of the following alternatives occurs.

**Head case.** If the retained entry matches the supplied address and is nonzero, the selected table entry receives the supplied object’s following-link value.

The destination uses another read of the external table base, together with the retained adjusted index. Consequently, the table-entry read and table-entry write need not address the same memory if that base changes between accesses. The entry itself is not reread to confirm that it still identifies the supplied object.

The preceding link is not tested to choose this branch.

**Non-head case with a nonzero preceding link.** If the head case does not apply, the function reads the supplied object’s preceding link and tests it against zero. When nonzero, the following-link field at offset `+0x10` of the referenced object receives the supplied object’s following-link value.

The preceding link is read again to form the destination. The value used as an address is therefore not guaranteed to equal the value that passed the nonzero test.

**Non-head case with a zero preceding link.** If the head case does not apply and the tested preceding link is zero, this stage makes no write.

There is no search for the supplied object, verification of a reciprocal link, repair of a missing predecessor, or inconsistency report.

### Following-object update

After the preceding stage completes, the function reads the supplied object’s following link and tests it against zero.

If nonzero, the preceding-link field at offset `+0x0C` of the referenced object receives the supplied object’s preceding-link value.

The following link is read again to form this destination. Its tested value is not guaranteed to be the same as its address-forming value.

This stage does not depend on a successful head match or a preceding-object write. An object with a nonmatching table entry and a zero preceding link can still cause a following object’s preceding link to become zero.

Because this stage occurs after the earlier write, aliases can change what it observes. The function does not operate on an immutable snapshot of the object’s original links.

### Final membership-bit clear

After the link-update stages, the function reads the flag byte again and writes it with bit 0 cleared.

Bits 1 through 7 are preserved from this final read, not necessarily from the initial gate read. If the byte has changed in the meantime, the final write uses the later byte’s upper seven bits.

This is a byte read-modify-write. Atomic bit-clear semantics are not established.

The function then returns.

### Observable ordering

The established stage order is:

1. Initial flag read and gate.
2. Index read, index adjustment, and selected table-entry read.
3. Conditional table-head or preceding-object write.
4. Following-link test and conditional following-object write.
5. Final flag read and byte write.

Within an individual assignment, the supplied representation does not establish a total order among all reads needed to obtain the destination and the value. This contract therefore does not require an unsupported operand-level ordering.

## Side effects

### Direct memory writes

An active invocation that completes performs:

- At most one four-byte write during the table-head or preceding-object stage.
- At most one four-byte write during the following-object stage.
- One byte write to the supplied object’s flags.

An inactive invocation performs no writes.

The body contains no explicit reset of the supplied object’s index or links. Under ordinary nonaliasing conditions, those fields remain unchanged. That is not an unconditional preservation guarantee: a neighbor destination or table destination may alias the supplied object’s storage.

Self-links and overlapping memory can also cause earlier writes to alter later reads, including the final flag read.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, assume accessible memory, valid arithmetic, stable values, and no unintended aliasing.

### Inactive object

Given a flag byte of `0xA4`, bit 0 is clear.

Expected behavior: read the flag byte and return without table access, link access, or writes. Invalid table or link values do not matter on this path because those locations are not accessed.

### Correct entry selection

Given an active object with index 2, the selected entry starts at table base plus four bytes.

If the entry at that address equals the supplied nonzero object address, the head branch updates that entry. The selection is not table base plus seven bytes; subtraction precedes multiplication.

Likewise, index 1 selects the entry at the table base.

### Head with a following object

Given a matching nonzero table entry, a zero preceding link, and a following link identifying another object:

- Replace the selected table entry with the following-object reference.
- Set the following object’s preceding link to zero.
- Clear bit 0 in the supplied object’s flags.

The supplied object’s following link is not explicitly cleared.

### Interior object

Given a nonmatching table entry and valid nonzero preceding and following links:

- Set the preceding object’s following link to the following-object reference.
- Set the following object’s preceding link to the preceding-object reference.
- Leave the selected table entry unchanged.
- Clear bit 0.

Neither neighbor is required to have previously pointed to the supplied object; no such check occurs.

### Tail object

Given a non-head object with a valid nonzero preceding link and a zero following link:

- Set the preceding object’s following link to zero.
- Perform no following-object write.
- Clear bit 0.

### Sole head object

Given a matching nonzero table entry and both links zero:

- Write zero to the selected table entry.
- Perform no neighbor-field writes.
- Clear bit 0.

### Inconsistent non-head object

Given a nonmatching table entry, a zero preceding link, and a nonzero following link:

- Leave the table entry unchanged.
- Perform no preceding-object write.
- Set the following object’s preceding link to zero.
- Clear bit 0.

No inconsistency status is produced.

### Changed table base

Suppose the initial table read uses one base and finds a matching nonzero entry, but the external base changes before the head write.

Conditional on these reads and valid destinations, the write uses the later base with the original adjusted index. It does not necessarily update the entry used for the comparison.

### Flag preservation and repeat invocation

If the final flag read yields `0xB7`, the final byte written is `0xB6`.

After normal completion, a second invocation with no intervening flag change follows the inactive path. Stale links do not cause another unlink operation while bit 0 remains clear.

### Zero index boundary

For index zero, the mathematical entry displacement is negative four bytes because \(4 \times (0 - 1) = -4\).

This is not an accepted-index guarantee or a guaranteed executable wraparound rule. Completion depends on the target arithmetic and memory mapping, neither of which is established for this case.
