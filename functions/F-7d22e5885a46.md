# F-7d22e5885a46

## Purpose

F-7d22e5885a46 replaces four references in a mutable state object, traverses a linked sequence of nodes, and performs order-sensitive bitmap updates using two record sequences obtained for each node. After traversal, it copies a header-determined number of payload words from one bitmap to another.

This contract names the four reference fields by their visible roles:

- **Accumulated bitmap:** receives unconditional bit insertions from each node’s second sequence.
- **Conditional bitmap:** receives bit insertions from each node’s first sequence when the corresponding accumulated bit is absent.
- **Copied bitmap:** receives the final payload copy.
- **Fourth reference:** receives an initialization result but is not subsequently accessed through that field.

These names do not establish application semantics. Interpreting the first two bitmaps as “definitions encountered” and “uses before definitions” is inferred intent, not an established contract.

The function has no established return value or explicit success/failure result. Its outputs are memory changes and dependency interactions.

## Interface

### Argument and representation

The function accepts the address of a mutable state object. The supplied representation uses 32-bit address-bearing values and 32-bit integer words. Offsets below are byte offsets.

| State offset | Width | Role |
|---|---:|---|
| `+0x04` | 32 bits | Configuration reference |
| `+0x0c` | 32 bits | Head-node reference; zero means no nodes |
| `+0x14` | 32 bits | Accumulated-bitmap reference |
| `+0x18` | 32 bits | Conditional-bitmap reference |
| `+0x1c` | 32 bits | Copied-bitmap reference |
| `+0x20` | 32 bits | Fourth reference |

The configuration object provides two arguments to F-106b019354f2:

- At `+0x04`, a reference to a cell whose first 32-bit word supplies the first argument.
- At `+0x20`, a 32-bit word supplying the second argument.

Their domain meanings are unknown.

Each node has a 32-bit next-node reference at offset zero. Other node fields are interpreted only by dependencies.

Each consumed record reference must support the identifier reads described below at record offset `+0x10`. Each identifier read is unsigned and 32 bits wide.

### Bitmap addressing

The visible operations treat a bitmap reference as identifying a header followed by payload words:

| Bitmap offset | Width | Role |
|---|---:|---|
| `+0x00` | 32 bits | Header |
| `+0x04` onward | 32 bits per word | Payload |

For a stable identifier \(x\), the selected payload word is \(\lfloor x/32\rfloor\), and the mask selects bit \(x\bmod32\). Payload word zero begins at `+0x04`.

The implementation does not necessarily obtain word selection and bit selection from one identifier snapshot. The individual reads are part of the behavior specified below. Without stable memory, the selected word and mask can come from different values, and in the second pass even from different record references.

Only the copied bitmap’s header is directly read. Treating that header as a bit count is consistent with its use but remains inferred intent.

### Path-dependent access requirements

There is no visible validation. Normal completion requires valid storage for the accesses actually reached, not dereferenceable results from all four initialization calls.

In particular:

- The state fields must support their reached reads and writes. Configuration and argument-cell dereferences must be valid each time initialization arguments are prepared.
- The accumulated bitmap needs suitable storage when a consumed first-sequence entry tests it or a consumed second-sequence entry updates it.
- The conditional bitmap needs suitable storage when a first-sequence entry requires an insertion or the final copy has a nonzero word count. Merely reading its reference field does not dereference the reference.
- The copied bitmap reference used after traversal is always dereferenced for its header. Its payload needs writable storage only for the computed copy extent.
- The fourth initialization result is only stored. It need not itself be dereferenceable for this function to complete, provided aliasing or dependency effects do not cause that value to be used elsewhere.
- Traversed nodes, consumed temporary entries, and reached record fields must be readable. Normal termination also requires a terminating node chain and terminating enumeration scans.

These requirements apply to the reference values present when accesses occur. Dependencies can replace fields or mutate reachable storage; an initialization result is not guaranteed to remain the value later used.

No visible requirement enforces distinct bitmap storage, zero-filled payloads, valid capacities, or absence of overlap.

## Behavior

### Initialization

F-106b019354f2 is called four times. Each returned 32-bit value is stored immediately, in this order:

1. State `+0x14`.
2. State `+0x18`.
3. State `+0x1c`.
4. State `+0x20`.

Each invocation obtains its arguments through fresh configuration reads. Values used by an earlier invocation are not retained as fixed arguments for later invocations. A dependency that changes configuration or related state can therefore change later arguments.

The supplied representation does not establish an exact order among all reads used to prepare the two arguments within one invocation. It does establish that each result store precedes preparation and execution of the next call.

Existing references are overwritten without a visible release operation. The function does not directly initialize bitmap headers or clear payload words.

### Traversal and temporary sequences

After initialization, the function reads the head reference at state `+0x0c`. A zero head skips node processing, but initialization and the final copy still occur.

For each nonzero current node:

1. F-93a6f85390ff supplies the endpoint used for the first sequence.
2. The first sequence is consumed completely.
3. F-bf3b72c7b3bc supplies the endpoint used for the second sequence.
4. The second sequence is consumed completely.
5. The current node’s next reference is read from offset zero.

The next reference is not captured before the enumeration calls. Dependency changes to the current node’s link can affect traversal. The state’s head field is not reread to obtain each subsequent node.

Both enumeration calls receive the current node, the beginning of a temporary region of 64 four-byte slots, and the address immediately after that 256-byte region. Each returned value is treated as an exclusive endpoint. Consumption begins at the first slot and advances in four-byte steps until the cursor equals that endpoint.

The function does not check that an endpoint is aligned, within the supplied region, or reachable by the scan. It does not visibly truncate excessive results.

Passing the temporary addresses does not establish that either dependency writes entries on a particular invocation. If a returned endpoint causes entries to be consumed, those entries must already contain readable, suitable record references.

### First-sequence updates

For each consumed first-sequence slot, the direct access sequence is:

1. Read the slot’s 32-bit record reference once.
2. Read the unsigned identifier at that record’s `+0x10` to select the payload word.
3. Read the unsigned identifier at the same record address again to select the mask bit.
4. Read the accumulated-bitmap reference and the selected accumulated payload word.
5. Test that payload word against the mask.
6. If the bit is absent, read the conditional-bitmap reference and update its corresponding payload word by bitwise OR with the mask.

Both identifier reads precede the accumulated payload test. The slot’s record reference is retained for these two reads, but the identifier value is not captured once and reused.

With stable record memory, word index and bit position agree with a single identifier. Without that stability, the first identifier read determines the word and the second determines the bit. The conditional update uses this same selected word and mask.

If the accumulated bit is present, this occurrence performs no direct conditional-payload access or write.

This pass does not directly insert bits into accumulated storage as a separate operation. Aliasing can nevertheless make a conditional write affect storage also serving another role.

### Second-sequence updates

For each consumed second-sequence slot:

- The accumulated-bitmap reference and an identifier obtained through the slot determine the target payload-word address.
- The update expression reads the slot’s record reference again and reads an identifier through that reference to determine the mask bit.
- The selected accumulated payload word is updated by bitwise OR with that mask.

Thus this pass separately reads both the temporary slot’s record reference and the referenced identifier for word selection and bit selection. It does not retain one record reference for both purposes.

The target-word address is established before the later mask-producing access. The supplied expression does not establish a finer ordering between the payload-value read and every read used to obtain the mask. Neither agreement between the two record references nor agreement between the two identifier values is guaranteed without stable memory.

With stable slots and records, each occurrence inserts the bit for its identifier. Repeated identifiers are logically idempotent under stable, noninterfering storage, but each occurrence still executes its own reads and write.

This pass has no separate direct conditional-bitmap update. Overlap can still affect conditional storage.

### Persistence and ordering

Each node’s first sequence precedes that node’s second sequence. A first-sequence bit test therefore does not see an insertion made only later by that node’s second sequence.

The visible bit-insertion operations do not themselves remove an earlier conditional bit. Persistence is not unconditional: a later dependency can clear or replace conditional storage, and overlapping storage can introduce other effects. Claims that a bit “remains set” require the absence of such interference.

### Final payload copy

After traversal terminates, the function reads the conditional reference, then the copied reference, then the copied bitmap’s header.

Let \(h\) be that header’s unsigned 32-bit bit pattern. The copy count is

\[
N=\left((h+31)\bmod 2^{32}\right)\mathbin{\mathrm{>>}}5.
\]

The addition is 32-bit unsigned arithmetic and the shift is unsigned.

For \(0\leq h\leq\texttt{0xffffffe0}\), this equals \(\lceil h/32\rceil\). For `0xffffffe1` through `0xffffffff`, addition wraps and the count is zero.

The function copies payload words in increasing index order. Each iteration reads one conditional payload word and writes the corresponding copied payload word. The header is not copied, and the final word is copied in full without masking unused high bits.

The copy count comes from the destination header, not the source header. The references and header used for this phase are captured before its loop rather than reread on every iteration.

This is a forward word-by-word copy. It is not guaranteed to preserve the original source contents under overlap: an earlier destination write may change a later source word.

## Side effects

Established direct effects are:

- Four calls to F-106b019354f2 and four result stores.
- Two enumeration calls per processed node.
- Conditional-payload writes for first-sequence entries whose accumulated test is zero.
- Accumulated-payload writes for consumed second-sequence entries.
- Copied-payload writes for the computed final extent.

Enumeration dependencies receive addresses through which they may write temporary storage. Such writes are possible dependency effects, not established writes on every invocation.

There are no explicit direct operations to clear bits, alter headers, rewrite list links, or release referenced objects. This statement concerns the designated targets of operations: aliasing can cause a payload write to overlap a header, link, state field, or other object.

No ownership transfer, allocation guarantee, retention rule, or eventual release responsibility is established. In particular, the absence of a direct release does not establish that dependencies preserve ownership or refrain from releasing memory.

There is no visible error return, bounds check, cycle detection, allocation-failure check, rollback, or transactional guarantee. Invalid accesses or nontermination may follow already-observable calls and writes.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless a case says otherwise, assume valid accesses, distinct nonoverlapping bitmaps, stable slots and records, zero initial payloads, well-formed endpoints, terminating traversal, and no dependency mutations beyond providing the stated results.

### Empty traversal with unused results

With a zero head, all four initialization calls and stores still occur, but neither enumeration dependency is called.

If the copied header is zero, no payload access occurs. On this path, the accumulated, conditional, and fourth initialization results need not be dereferenceable. The copied reference must still support its header read.

### Same identifier in both sequences

If one node’s first and second sequences each contain identifier 5:

- The first pass finds the accumulated bit absent and inserts bit 5 into conditional storage.
- The second pass inserts bit 5 into accumulated storage.
- Both retain that bit under the stated noninterference assumptions.
- The bit reaches copied storage if its word lies within the final copy extent.

This distinguishes first-sequence-before-second-sequence behavior from the reverse ordering.

### Earlier accumulation suppresses a later insertion

If an earlier node’s second sequence inserts bit 5, a later node’s first-sequence occurrence of identifier 5 finds that bit set and performs no conditional-payload write for that occurrence.

Reversing those node roles can produce a different conditional result.

### First-pass identifier changes

Suppose one first-sequence slot retains the same record reference, but its two identifier reads yield 32 and then 5. The selected location is payload word 1, bit 5—not the ordinary location of either identifier considered as one stable snapshot.

The accumulated test and any conditional insertion use that combined location.

### Second-pass slot changes

Suppose a second-sequence slot first references a record whose identifier is 32, then references another record whose identifier is 5 when read again. The target is accumulated payload word 1, with bit 5 inserted.

This case requires valid storage for both reached records. It illustrates access behavior without asserting that concurrent mutation is supported or synchronized.

### Intervening clearing

A first pass may insert conditional bit 5, after which the second enumeration dependency may clear that storage. The later direct insertion of accumulated bit 5 does not restore the conditional bit. Unconditional persistence would therefore be an incorrect guarantee.

### Boundaries and final copy

Stable identifiers 31 and 32 select, respectively, payload word 0 bit 31 and payload word 1 bit 0.

A copied header of 33 causes two complete words to be copied, including bits above the nominal 33-bit extent. A header of `0xffffffff` causes zero payload copies.

If an enumeration returns the temporary beginning, that sequence consumes no entries. The other enumeration still occurs in its prescribed order.
