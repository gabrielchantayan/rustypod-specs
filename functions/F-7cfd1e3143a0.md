## Behavior

### Initial access

The first relevant memory operation is the read of the pointer field at object offset 4. This occurs before the function decides whether scanning is possible.

The local count starts at zero.

If the loaded pointer is null:

- No byte is read through that pointer.
- F-d3922c7fe0ec is not called.
- F-491a7a9bcafa is not called.
- The function returns zero.

The null-pointer branch is therefore an empty-sequence path, not validation of the object argument.

### Scanning order

For a nonnull initial cursor, each attempted iteration begins by reading the byte at the current cursor.

If that byte is zero, scanning stops immediately. The zero byte is not passed to F-d3922c7fe0ec by this function.

If that byte is nonzero, the function calls F-d3922c7fe0ec with the address of the local cursor. The dependency may change that cursor before returning.

After the dependency returns, its integer result is compared with the comparison value:

- If equal, the count increases by one and scanning attempts another iteration.
- If unequal, scanning stops without incrementing the count for that call.

The dependency result is not itself tested as a termination marker. A result of zero counts as a match when the comparison value is zero, provided the call was reached after a nonzero byte check.

The next byte read, after a successful match, uses the cursor value left by F-d3922c7fe0ec. There is no visible independent cursor increment.

### Consequences of dependency-controlled advancement

The count measures successful comparisons. It does not establish how much storage was traversed.

One successful call may advance over multiple bytes, leave the cursor unchanged, or move it in some other way. Those possibilities are not constrained by the available dependency contract.

In particular:

- If the dependency leaves the cursor unchanged and repeatedly returns the comparison value, the function has no independent means of making progress.
- If the dependency changes the cursor on a nonmatching call, that change has already occurred when scanning stops.
- A nonmatching call is not undone.
- If a matching call leaves the cursor null, the next loop condition attempts a byte read through that null cursor. There is no repeated null check.
- If a nonmatching call leaves the cursor null, this function performs no subsequent cursor-byte read before leaving the scan.

The object’s pointer field is loaded only once by the visible function. Later changes to that field do not directly refresh the local cursor. A dependency could nevertheless access the object or related state through other means; its effects are unknown.

### Completion operation

After scanning stops normally, the function tests whether the count is strictly greater than zero.

For a positive count, it calls F-491a7a9bcafa with:

1. The original object argument.
2. Integer zero.

This call occurs once on that path, after the terminal byte check or nonmatching dependency result.

For a zero count, the call is skipped.

Under ordinary representable counting, this means the completion dependency runs precisely when at least one matching result was counted. That equivalence must not be extended through an unspecified overflow condition.

The function then returns the count. There is no visible adjustment based on the completion dependency’s result.

The established counting contract therefore covers executions in which the count remains representable. Beyond that range, the source-level arithmetic semantics and actual executable behavior are not established here. A wrapping negative return, skipped completion call, or any other overflow outcome must not be promised.
