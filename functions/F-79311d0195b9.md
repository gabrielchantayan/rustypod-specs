# F-79311d0195b9

## Purpose

F-79311d0195b9 obtains one 24-byte record from a mutable storage state and partially clears that record. It prefers a record reachable through a reuse list, otherwise consumes the next unused record in the current storage region. When that region is exhausted, it requests a new region and a 12-byte descriptor through F-871e64ddc6de.

The selected record is not returned. Its selection is reflected in state mutations and writes to its storage.

The organization resembles a record pool with a reuse list and linked allocation descriptors. That interpretation is inferred intent. The established behavior is the selection, allocation, linking, cursor movement, and partial clearing described below.

## Interface

### Input and representation

The function accepts one address identifying a mutable state structure. It has no explicit return value.

The visible representation uses four consecutive 32-bit state fields:

| Byte offset | Descriptive role | Interpretation |
|---|---|---|
| 0 | Descriptor head | Address of the most recently linked allocation descriptor, or zero |
| 4 | Reuse head | Address of a reusable record, or zero |
| 8 | Unused cursor | Address of the next record available from the current region |
| 12 | Region end | Address used as the exhaustion boundary |

These role names describe the observed access pattern; they do not establish a public type definition.

An allocation descriptor occupies 12 requested bytes:

| Byte offset | Contents written or read |
|---|---|
| 0 | Link to the descriptor head observed after the allocation calls |
| 4 | 32-bit record capacity |
| 8 | Address returned for the record-storage allocation |

Each record has a 24-byte stride. A record selected from the reuse list contains its next-record address in the 32-bit field at offset 12.

The supplied representation carries addresses in 32-bit fields. Capacity calculations use unsigned 32-bit arithmetic. No wider arithmetic, pointer representation, or portability guarantee is established.

### Preconditions

For an ordinary successful execution:

- The state address must permit all state reads and writes required by the selected branch.
- A nonzero reuse head must identify storage permitting a 32-bit read at offset 12 and the record writes described below.
- When the unused cursor differs from the region end, it must identify writable storage for the selected record. The function does not verify that the cursor is below the end or that a full record remains.
- When growth consults a nonzero descriptor head, that address must permit a 32-bit capacity read at offset 4.
- Successful allocation results must provide usable descriptor and record storage.

The function does not validate these conditions. Its behavior on invalid addresses, inaccessible storage, malformed reuse links, or unusable allocation results is not defined by this contract beyond the visible unchecked accesses.

### Output

There is no explicit returned record address, status code, or success indicator. Successful completion leaves state and storage modified as specified below.

## Behavior

### 1. Prefer the reuse list

The first observed state read obtains the reuse head.

If it is nonzero, that address becomes the selected record. The function then:

1. Reads the 32-bit value at selected-record offset 12.
2. Writes that value into the state's reuse-head field.
3. Performs the selected-record clearing sequence.

This branch does not explicitly read the unused cursor, region end, descriptor head, or capacity. It does not call F-871e64ddc6de.

The reuse successor is captured before the selected record's offset-12 field is cleared. Thus a nonzero successor can become the new reuse head even though that field in the selected record subsequently becomes zero.

No validation establishes that the successor is another record, that the list is acyclic, or that the selected record is distinct from the state structure.

### 2. Otherwise use the unused cursor

If the initially read reuse head is zero, the function reads the unused cursor and compares it with the region end.

If the addresses differ, the cursor address becomes the selected record. The function writes selected-record address plus 24 into the state's unused-cursor field, then performs the clearing sequence.

Exhaustion is tested by equality only. There is no ordering comparison, remaining-byte calculation, alignment check, or bounds check. A cursor beyond the end still follows this branch if the two addresses are unequal.

### 3. Grow when cursor equals end

If the reuse head is zero and the unused cursor equals the region end, the function computes a new capacity.

It first reads the descriptor head:

- If the head is zero, the new capacity is 32 records.
- Otherwise, it reads the unsigned 32-bit capacity at descriptor offset 4 and derives two candidates:
  - The old capacity plus 32.
  - The old capacity plus its value shifted right by one bit, plus its value shifted right by three bits.

Each addition is unsigned 32-bit arithmetic. Each right shift operates on the original unsigned capacity. The second candidate is selected when the first candidate is less than or equal to it; otherwise, the first candidate is selected.

Without wraparound, this chooses the larger of growth by 32 records and growth by approximately 62.5 percent. The fractional terms are separately truncated before addition. This is descriptive intent only: the actual rule is the unsigned calculation and comparison above, including wraparound.

The function next makes two calls, in this order:

| Call | First argument | Second argument |
|---|---|---|
| First | 12 | 0 |
| Second | New capacity multiplied by 24 | 0 |

Both calls target F-871e64ddc6de. The multiplication supplied to the second call is unsigned 32-bit arithmetic and can wrap.

The first result is retained as the descriptor address. The second result is used as the record-storage address. No result is checked for zero or another failure indication before use.

After the second call returns, the explicit mutation order is:

1. Write the second result to descriptor offset 8.
2. Read the state's descriptor-head field and write that value to descriptor offset 0.
3. Write the computed capacity to descriptor offset 4.
4. Publish the descriptor address in the state's descriptor-head field.
5. Read descriptor offset 8 to obtain the selected-record address.
6. Write the selected-record address plus the capacity-times-24 extent into the state's region-end field.
7. Write the selected-record address plus 24 into the state's unused-cursor field.
8. Perform the selected-record clearing sequence.

The head linked into the new descriptor is read after both dependency calls. It is not necessarily the same head used earlier to decide the capacity. Nothing supplied establishes that either dependency call preserves the state or other memory reachable by the function.

Likewise, after the calls, the function does not re-evaluate reuse availability or repeat the original cursor/end comparison.

### 4. Partially clear the selected record

Every normally completing branch reaches the same ordered writes:

1. Write a 32-bit zero at record offset 4.
2. Write a 32-bit zero at record offset 8.
3. Write a 32-bit zero at record offset 12.
4. Write a single zero byte at record offset 0.

These writes clear bytes 4 through 15 and byte 0. The function does not explicitly clear bytes 1 through 3 or bytes 16 through 23.

The record is therefore not fully initialized to zero. Any previous contents of the untouched bytes remain unless other effects, including aliasing or dependency behavior, change them.

## Side effects

### State changes

Under ordinary nonoverlapping storage:

- **Reuse selection:** advances the reuse head to the selected record's saved successor.
- **Cursor selection:** advances the unused cursor by 24.
- **Growth:** links a new descriptor, replaces the descriptor head, establishes a new region end, and advances the new region's unused cursor past its first record.

On the cursor and growth paths, the function itself does not write the reuse-head field. On the reuse path, it does not explicitly update the descriptor head, unused cursor, or region end.

These distinctions describe direct accesses, not unconditional final-value guarantees. If state, descriptors, and records overlap, an explicitly addressed write may also alter another logical field.

### Allocation, ownership, and lifetime

Only the growth path invokes F-871e64ddc6de. The visible function performs no release operation and no rollback.

The new descriptor retains both a link to an earlier descriptor head and the record-storage address. This supports the interpretation that descriptors track allocated regions, but no ownership-transfer, reclamation, or lifetime rules are established.

The selected record's lifetime is also unspecified. This function removes or consumes it from an available source but supplies no explicit handle to its caller.

### Failure and concurrency

There is no visible local error return, allocation-result check, recovery branch, synchronization, or transactional protection.

If a dependency fails to return, no subsequent behavior is established. If it returns an unusable address, the visible function proceeds toward unchecked accesses. The supplied evidence does not establish a particular fault, exception, or process outcome.

The mutation sequence is not atomic. Concurrent or reentrant access to the same state requires external guarantees not provided here.

## Acceptance examples

These examples are conditional on valid writable storage, nonoverlap, and dependency behavior as stated in each example. They are static acceptance criteria, not executed tests.

### Reuse takes precedence

Given a nonzero reuse head whose record contains successor address **B** at offset 12:

- That record is selected even if the unused cursor also points to available storage.
- The reuse head becomes **B** before clearing.
- No dependency call occurs.
- The selected record receives the four clearing writes in their specified order.
- Its successor field ends as zero, while the state's reuse head retains **B**.

### Available cursor storage

Given a zero reuse head, cursor **P**, and a different region end:

- **P** is selected.
- The unused cursor becomes **P + 24** before clearing.
- No descriptor allocation occurs.
- Untouched record bytes are not required to become zero.

This criterion does not require **P** to be below the end. Memory validity remains a separate precondition.

### Initial growth

Given a zero reuse head, equal cursor and end, and a zero descriptor head, with dependency calls returning distinct usable storage and not changing the state:

- Capacity is 32.
- The requests are 12 bytes followed by 768 bytes, each with second argument zero.
- The new descriptor's link is zero and its capacity is 32.
- The first record of the new storage is selected.
- The region end is 768 bytes beyond the storage address.
- The cursor is 24 bytes beyond that address.

### Existing-capacity growth

With the same growth conditions and an existing capacity of 32, the two candidates are 64 and 52. Capacity 64 is selected, producing a 1,536-byte storage request.

With an existing capacity of 64, the candidates are 96 and 104. Capacity 104 is selected, producing a 2,496-byte storage request.

### Head changes during dependency calls

If the capacity was computed from one descriptor head but a dependency changes the state's head before returning, the new descriptor must link to the head read after both calls. It need not link to the descriptor used for the capacity calculation.

### Partial clearing

If a selected record initially contains nonzero bytes throughout, successful clearing requires zero at byte 0 and throughout bytes 4–15. It does not require zero at bytes 1–3 or 16–23.
