# F-90254983f139

## Purpose

F-90254983f139 dispatches an event against a receiver object. Depending on the event classification and, for one event class, an embedded-object identity, it:

- Invokes a receiver-specific operation.
- Updates a receiver field.
- Performs one or two indirect notifications.
- Offers the event to another object obtained through the receiver.
- Returns a handled indicator or a dependency’s result.

The established behavior is dispatch and state manipulation. The business meanings of the events, embedded objects, notification arguments, and receiver fields are not established.

This contract describes static evidence only. No runtime tests have been performed. Descriptive names below identify roles within this contract, not confirmed application concepts.

## Interface

### Inputs

The function accepts two arguments:

1. **Receiver:** an address used as the base of an object with a dispatch-table pointer, embedded objects, and mutable fields.
2. **Event:** an address used to read an event discriminator and passed to extraction or fallback operations.

The supplied representation uses 32-bit integer values and four-byte pointer/table entries. The offsets below follow that representation. The native calling convention and a complete object-layout declaration are unavailable.

### Configuration values

Several global values are unresolved. This contract names them by role:

- **Primary boundary:** used first for event equality, then for signed ordering.
- **Secondary boundary:** used for event equality and a subsequent signed ordering decision.
- **Entry notification value:** captured before reading the event discriminator.
- **Decrement notification first value** and **decrement notification second value**.
- **First paired-notification second value**.
- **Second paired-notification second value**.

These names do not imply immutable configuration. The function accesses global storage, and dependencies are not established to preserve it.

### Output

The return value is represented as a signed 32-bit integer:

- Most recognized local paths return `1`.
- F-e23b7384348d can supply any nonzero result directly.
- The fallback operation can supply any result directly.
- Failure to obtain a fallback object returns `0`.

Consequently, the interface is not limited to Boolean results. A negative dependency result can be returned unchanged.

### Preconditions

For defined normal execution, each address actually accessed must refer to suitable readable or writable storage. Indirect-call tables and invoked entries must be valid.

The function does not visibly validate:

- The receiver or event address.
- Extraction results before accessing offset `0x008`.
- Indirect-call table pointers.
- Indirect-call entries.

The only explicit null check concerns the fallback object returned through the receiver. Behavior after another invalid address, invalid call target, or dependency failure is not established as a recoverable error.

## Behavior

### Dispatch precedence

The entry notification value is captured first. The event discriminator is then read once for the local dispatch decisions.

The dispatch hierarchy matters because the two boundary values are unknown:

1. Equality with the primary boundary takes precedence over every other event interpretation.
2. Events signed-less-than the primary boundary enter the lower partition.
3. All remaining events enter the upper partition.

Within the lower partition:

1. Equality with the secondary boundary takes precedence.
2. Otherwise, events signed-greater-than-or-equal-to the secondary boundary enter a special-event check.
3. Only events below the secondary boundary reach the `0x0F` and `0x16` checks.

Thus, a numeric event described below is recognized only if the earlier boundary decisions route it to that check. The unknown boundaries prevent an unconditional flat event-number table.

### Primary-boundary event

If the discriminator equals the primary boundary, F-1f2e67c575ed is invoked with the receiver. Its result is ignored, and the function returns `1`.

### Lower partition: secondary-boundary event

If the discriminator is below the primary boundary and equals the secondary boundary, F-13b43f762d0e is invoked with the receiver. Its result is ignored, and the function returns `1`.

### Lower partition: special-event check

For an event below the primary boundary, unequal to the secondary boundary, and not below the secondary boundary:

- `0x80009` invokes F-23f93d0ccdf0 with the receiver and returns `1`.
- Otherwise, the function subtracts `0x80000` from the discriminator and checks whether the result is `10`. A matching result invokes the same dependency and returns `1`.
- Nonmatching events proceed to fallback.

For ordinary non-overflowing signed arithmetic, the second comparison recognizes `0x8000A`.

The subtraction uses an integer-width expression, not a pointer calculation. Its behavior for an overflowing signed subtraction is not established. Because the boundary values are unknown, the evidence does not prove that all possible values reaching this expression are overflow-safe.

### Lower partition: event `0x0F`

This path is reached only below both boundaries and after failing secondary-boundary equality.

F-682adfd5a561 is called with the event and selector `0xD00`. The returned address is then read at offset `0x008` to obtain an identity address.

The function compares that address against receiver-relative embedded-object addresses. These are exact address comparisons, not content comparisons.

| Identity address | Action |
|---|---|
| Receiver + `0x4A0` | Counter/decrement path described below |
| Receiver + `0x77C` | Invoke F-9424d07bff77 with the receiver |
| Receiver + `0x7A8` | Write zero to the byte at receiver + `0x885` |
| Receiver + `0x7D4` | Invoke F-27eec3099149 with the receiver |
| Receiver + `0x800` | Invoke F-6810bb156327 with the receiver |
| Receiver + `0x82C` | Invoke F-817f866b3fef with the receiver |
| Receiver + `0x858` | Invoke F-ae258cae6e8b with the receiver |
| Any other address | No further visible action |

Every normally completing row returns `1`. An unrecognized identity does not trigger fallback.

#### Counter/decrement path

When the identity equals receiver + `0x4A0`:

1. Read the four-byte field at receiver + `0x49C`.
2. If it is zero, return `1` without changing it or invoking the subsequent operations.
3. Otherwise, subtract one and write the updated value to the same field.
4. Invoke F-ec4cfa552cce with receiver + `0x4A0`.
5. After that dependency returns, resolve the receiver’s indirect-call entry at table byte offset `0x58`.
6. Obtain the decrement notification first value, then the decrement notification second value.
7. Invoke the resolved entry with the receiver and those two values.
8. Return `1`.

The zero check is not a positivity check. Negative nonzero field values also enter the decrement path. The source does not establish defined signed-overflow behavior when decrementing the minimum signed 32-bit value.

The field update occurs before F-ec4cfa552cce. That dependency can therefore observe the decremented field, subject to any behavior internal to the dependency. The later indirect target is resolved after the dependency returns; preservation of the receiver’s dispatch table is not assumed.

### Lower partition: event `0x16`

This path is also restricted to events below both boundaries.

1. Invoke F-682adfd5a561 with the event and selector `0xF00`.
2. Read a four-byte value at offset `0x008` from the returned address.
3. Invoke F-e23b7384348d with the receiver and that value.
4. If its result is nonzero, return that exact result.
5. If its result is zero, proceed to fallback.

The function does not interpret a nonzero result as success versus failure; it only distinguishes zero from nonzero.

Other events in this portion of the lower partition proceed directly to fallback.

### Upper partition

For events not signed-less-than the primary boundary, after primary-boundary equality has already been excluded:

| Discriminator | Action |
|---|---|
| `0x8000C` | Invoke F-91f7df9150bd with the receiver; return `1` |
| `0x8000D` | Perform the paired notifications below; return `1` |
| `0x8000E` | Invoke F-03060a50e787 with the receiver; return `1` |
| `0x80012` | Invoke F-1f2e67c575ed with the receiver; return `1` |
| Any other value | Proceed to fallback |

#### Paired notifications

For the reachable `0x8000D` path:

1. Resolve the receiver’s indirect-call entry at table byte offset `0x58`.
2. Invoke it with the receiver, a fresh read of the global supplying the entry notification value, and the first paired-notification second value.
3. After that call returns, resolve the receiver’s table entry at byte offset `0x58` again.
4. Obtain the second paired-notification second value.
5. Invoke the newly resolved entry with the receiver, the entry notification value captured before event dispatch, and the second paired-notification second value.
6. Return `1`.

The first notification’s first value is freshly obtained; the second notification’s first value is the entry-time capture. These may differ if intervening behavior changes the relevant global.

The second call target is also freshly resolved. It need not equal the first call target if the first call changes receiver state. Both indirect return values are ignored.

### Fallback

Fallback first invokes an indirect entry through the receiver’s table at byte offset `0xCC`. The supplied representation does not establish explicit arguments for that call.

- If the returned object address is null, return `0`.
- Otherwise, read that object’s indirect-call table and invoke its entry at byte offset `0x30`, explicitly passing the returned object and the original event.
- Return that invocation’s result unchanged.

Fallback does not repeat the local event-discriminator read. If earlier dependencies modify the event, the forwarded event is still the original address, with whatever state it has when the fallback operation receives it.

## Side effects

The directly visible writes are limited to:

- A four-byte decrement at receiver + `0x49C`, on the matching nonzero counter path.
- A one-byte zero write at receiver + `0x885`, on its matching identity path.

The byte write does not establish any update to adjacent bytes.

All dependency calls and indirect calls may have additional effects. Their preservation of receiver fields, globals, event storage, memory ownership, and dispatch tables is unknown.

No direct allocation, release, reference-count operation, or ownership transfer is established. In particular:

- Passing an embedded-object address to F-ec4cfa552cce does not establish destruction or release.
- The extraction result is not visibly released here.
- The fallback object is not visibly retained or released here.

No rollback is visible. If a dependency fails to return normally after a direct write, this function provides no established restoration behavior.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Each assumes valid storage, valid indirect targets, and normally returning dependencies unless stated otherwise.

1. **Primary-boundary precedence.**  
   If the event equals the primary boundary, F-1f2e67c575ed is called and the result is `1`, even if that numeric value would otherwise resemble another recognized event.

2. **Unknown identity is consumed.**  
   If `0x0F` reaches its extraction path and the extracted address matches none of the listed embedded-object addresses, the function returns `1` without fallback.

3. **Zero counter avoids notification.**  
   If the extracted identity is receiver + `0x4A0` and the field at `0x49C` is zero, the result is `1`; neither F-ec4cfa552cce nor the subsequent notification is invoked.

4. **Nonzero counter changes before the dependency.**  
   With the same identity and an initial field value of `3`, the field is written as `2` before F-ec4cfa552cce is invoked. A later dependency may change it again, so `2` is not an unconditional final-state guarantee.

5. **Single-byte clearing.**  
   If the extracted identity is receiver + `0x7A8`, the byte at `0x885` becomes zero and the result is `1`.

6. **Nonzero handler result propagates.**  
   If reachable event `0x16` produces a handler result of `-7`, the function returns `-7` without fallback.

7. **Zero handler result permits fallback.**  
   If that handler returns zero and fallback-object acquisition returns null, the final result is `0`.

8. **Fallback result is not normalized.**  
   If fallback obtains an object whose event operation returns `42`, the final result is `42`.

9. **Paired calls observe different resolution times.**  
   If reachable event `0x8000D` causes the first notification to replace the receiver’s table entry, the second notification uses the entry resolved after that replacement. Its first notification argument still uses the entry-time captured value.

## Uncertainties

**Documented only:**

- Concrete boundary and notification values.
- Business meanings of event classes, selectors, fields, and embedded objects.
- Complete receiver, event, and extraction-result layouts.
- Exact calling conventions, especially the fallback-object acquisition call.
- Dependency side effects, ownership rules, and failure behavior.
- Signed-overflow behavior for subtraction and decrement edge cases.
- Whether the apparent globals can change asynchronously or have special access semantics.
- Runtime reachability of numeric cases under the unknown boundary values.

**Inferred intent:** the function resembles an event dispatcher, with embedded-object identities selecting actions and a fallback object handling otherwise unconsumed events. This interpretation is not needed to establish the listed reads, writes, calls, and returns.
