# F-7e83af7e8039

## Purpose

F-7e83af7e8039 advances a stateful operation through initialization, item processing, completion notification, and finalization. It supports two execution modes:

- **Blocking mode:** continues internally until the state byte is observed as 3 at an outer-loop boundary.
- **Incremental mode:** returns after one outer-loop pass, reporting whether that boundary observes state 3. An item-processing pass can nevertheless perform multiple dependency calls before yielding.

These descriptions express the visible control flow, not a guarantee of progress. Dependencies may fail to return, alter shared state, or provide results that prevent termination.

The apparent intent is a staged operation with periodically reported progress. The meaning of the processed items, the progress scale, and the surrounding subsystem are not established.

## Behavior

### 1. Entry ordering and effective mode

The following actions occur before dispatching on the state:

1. Copy the auxiliary argument into a local 32-bit slot.
2. Call F-3d42232ff214 and retain its 32-bit result as a processing handle.
3. Call F-8f4035bf2a29 with the value 0x21.
4. Read and retain one global 32-bit value, used later as the discriminator comparison target and as an extra argument to the initial preparation call.
5. Read the context state byte. If it is zero, replace the effective mode with zero for the remainder of the invocation.

The state used for the override is read **after** both entry calls. The relevant state is therefore not necessarily the state present when the caller entered the routine.

The comparison target is captured once. Later dependency changes to its backing global do not change the retained value used by this invocation.

The state is then read again for dispatch. If it changes between the override read and the dispatch read, the effective mode still reflects the earlier read.

### 2. State 0: preparation

When a dispatch read observes state 0:

1. Call F-ac88c15e3e35 with the context and the captured comparison target.
2. Call F-8a4e638db1bd with the context, the value 3, and the effective mode.
3. Write state 1.

The second dependency’s result is ignored on this path.

This branch does not immediately open or advance work. It proceeds to the outer-loop boundary. In the ordinary case where the earlier override also observed state 0, the effective mode is blocking and the routine proceeds to another iteration.

The state-1 write occurs after both dependencies return and overwrites any state-byte change they made.

### 3. States 1 and 3: opening or advancing work

Both state 1 and state 3 enter the same processing path. State 3 is therefore **not an unconditional no-op terminal state on entry**.

First, read the active-work field at +0x10C.

If it is nonzero, skip opening and the associated resets, and proceed directly to item advancement.

If it is zero:

1. Call F-88e8ca916d2a with:
   - the retained processing handle;
   - a 32-bit value read from a separate global at this point;
   - the address of context offset +0x110;
   - the address of the local auxiliary slot.
2. Write its 32-bit result to +0x10C.
3. Write zero to +0x114.
4. Write zero to +0x11C.
5. Write zero to +0x120.
6. Write state 1.
7. Re-read +0x10C.

The reset writes occur even when the opening result is zero. They occur after the opening dependency returns, so they replace any values it placed in those fields.

If the re-read finds no active work, proceed directly to completion notification. Otherwise, advance an item.

### 4. Item advancement

For each advance:

1. Read the 32-bit discriminator at +0x110 and compare it with the captured comparison target.
2. If they differ, call F-ac88c15e3e35. This call is visibly presented with only the context argument.
3. Read the counter at +0x114, increment it by one, and write the result back.
4. Call F-64f05dadf1ac with the retained processing handle, the address of +0x110, and the address of the local auxiliary slot.
5. Write the returned 32-bit value to +0x10C.

The counter increment occurs after the optional discriminator-related call and before the advance dependency. It therefore uses any counter value left by that optional call. The advance dependency can subsequently modify the counter again.

In blocking mode, return to the active-work check without performing the incremental progress calculation. Continue advancing while the field remains nonzero. On observing zero, proceed to completion notification.

In incremental mode:

1. Read the current counter after the advance call.
2. Call F-d7be9cfb4000 with that counter and 3.
3. Inspect a secondary result associated with that call.
4. If the secondary result is nonzero, return to the active-work check.
5. If it is zero, calculate and publish progress.

Thus, an incremental invocation does not necessarily advance exactly three items, or any fixed number of items. Its stopping point depends on the current counter and an incompletely established secondary-result convention.

### 5. Progress publication

When the secondary result is zero:

1. Form a 32-bit product from the retained counter value and a global 32-bit factor read for this calculation.
2. Call F-d7be9cfb4000 with that product and the current 32-bit value at +0x118.
3. Retain the primary result as the progress value.
4. Call F-93fd250aa9bf.
5. Call F-b63ebee7ff72 with that result, the value 5, and the progress value.
6. Re-read +0x10C.

If active work remains, proceed to the outer-loop boundary. If not, perform completion notification first.

The counter used in the product is the value captured before the first arithmetic call. The final active-work check occurs after both progress-related dependencies, so it can observe their side effects.

### 6. Completion notification

Whenever the processing path observes no active work at the designated checks:

1. Call F-93fd250aa9bf.
2. Call F-79160ed9e5ba with its result and the value 6.
3. Write state 2.
4. Proceed to the outer-loop boundary.

Progress publication and completion notification can occur in the same pass. In that case, the value-5 call precedes the value-6 call, and each obtains its own result from a separate invocation of F-93fd250aa9bf.

The state-2 write occurs after the notification dependency returns.

### 7. State 2: finalization

When dispatch observes state 2:

1. Call F-8a4e638db1bd with the context, zero, and the effective mode.
2. If the result is zero, perform no further direct state write and proceed to the outer-loop boundary.
3. If the result is nonzero:
   - call F-c4233718c9d6;
   - call F-ae93e1613907;
   - write state 3;
   - proceed to the outer-loop boundary.

A zero result does not prove that state remains 2: the dependency may have modified it. The boundary reads the actual state byte.

### 8. Invalid states

A dispatch state other than 0, 1, 2, or 3 invokes F-a817d8d58c10.

The supplied representation marks this dependency as non-returning. No recoverable error result or normal output write is established for this path. Behavior if that non-return assumption is false is undocumented.

### 9. Outer-loop boundary and normal return

At each boundary:

- In incremental mode, read the state and return, writing 1 if it equals 3 and 0 otherwise.
- In blocking mode, read the state and return only if it equals 3. Otherwise, dispatch another iteration.

On every normal return:

1. Write exactly one byte, 0 or 1, through the completion-output pointer.
2. Call F-85722f62e20a with 0x21 and a value read from another global.
3. Return.

The output reflects the boundary read before the final dependency call. That call may alter state or other memory afterward. Normal return does not independently guarantee that the context still contains state 3.

## Side effects

Direct context writes are limited to the state byte, active-work field, counter, and the two reset fields identified above. Other changes may be made by dependencies.

No explicit allocation, deallocation, ownership transfer, or handle release is visible. In particular:

- A nonzero active-work result is treated as active, not proven to be an owned pointer.
- Replacing that field does not itself establish release of its previous contents.
- The retained processing handle is passed to processing dependencies, but its ownership is unknown.
- The entry and exit calls sharing 0x21 appear paired, but their purpose and balancing obligations are not established.

No rollback is visible. If a dependency fails to return, earlier writes and calls have already occurred. The final output write and exit call are not guaranteed on such paths.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests.

1. **Initial-state override:** If the post-entry override read observes state 0, even a nonzero requested mode becomes blocking. Assuming preparation and processing eventually reach successful finalization, the invocation returns with output 1 rather than yielding immediately after initialization.

2. **Opening no work:** Given incremental mode, dispatch state 1, and zero active work, if opening returns zero and no subsequent side effect reactivates work, the counter and both reset fields become zero, completion selector 6 is sent, state becomes 2, and output is 0.

3. **Existing work:** Given state 1 and nonzero active work, the opening dependency and opening resets are skipped. The existing counter is incremented before the first advance call.

4. **Incremental continuation:** If an advance leaves work active and the arithmetic secondary result is nonzero, another active-work check occurs rather than an immediate return. No fixed batch size is guaranteed without the arithmetic dependency’s contract.

5. **Progress followed by completion:** If the secondary result is zero and the post-progress active-work read is zero, selector 5 is sent before selector 6. State is then written to 2, and incremental execution returns output 0.

6. **Finalization deferred:** Given incremental mode and dispatch state 2, if the finalization gate returns zero and leaves state 2 unchanged, neither finalization action runs and output is 0.

7. **Finalization accepted:** If that gate returns nonzero and both actions return, they run in their specified order, state is written to 3, and the boundary selects output 1.

8. **Entry in state 3:** Given state 3 and zero active work, opening is attempted. If it returns zero, completion notification changes state to 2. Entry in state 3 alone therefore does not guarantee output 1.

9. **Invalid state:** If dispatch observes an unsupported byte value, the invalid-state dependency is invoked instead of a normal completion path.
