# F-474b7e2941e6

## Purpose

F-474b7e2941e6 obtains a node, initializes part of its value, increments container bookkeeping, stores the node into a caller-selected attachment location, performs color-dependent structural repair, and writes the obtained node address to an output slot.

The layout and repair pattern are consistent with red-black-tree insertion. That is inferred intent, not an independently established guarantee. The function does not search for an insertion position, check ordering, reject duplicates, or establish that the supplied attachment node belongs to the container.

Normal completion does not alone establish container reachability of the obtained node. Reachability additionally requires appropriate caller-provided structure and dependency behavior.

## Interface

The function has five inputs and no explicit status return:

| Input | Observed interpretation |
|---|---|
| Result slot | Address receiving the originally obtained node address as one 32-bit word on normal completion. |
| Container | Address of mutable bookkeeping and a header pointer. |
| Attachment selector | 32-bit integer; zero permits comparison-based selection, while any nonzero value forces first-link attachment unless header attachment already selects it. |
| Attachment node | Address into which the selected child-link write is made; it may equal the container’s header. |
| Source value | Address supplying one byte directly and a subobject beginning four bytes later through a dependency. |

The supplied representation uses 32-bit address and integer storage and 8-bit color/value accesses. It does not establish behavior for wider pointers.

“Left,” “right,” “minimum,” “maximum,” “red,” and “black” are plausible semantic interpretations, not additional established properties. This contract uses first/second links and numeric colors instead.

For repair decisions, zero is the active color. Every nonzero byte takes the opposite-color branch; values other than one are not rejected. Explicit color writes are exactly zero or one.

### Preconditions and arithmetic limits

Normal completion requires valid storage for every direct and dependency-mediated access. This includes the result word, container fields, selected attachment link, obtained node, and all links followed during repair. Word-access alignment must satisfy the target.

The function does not validate these requirements. It also does not validate tree membership, acyclicity, ordering, header consistency, or suitable initial node color and child links.

The count update is represented as signed 32-bit addition. Behavior at signed overflow is not established; wrapping, saturation, and recovery are not promised. Address-offset calculations likewise do not establish portable overflow or invalid-pointer behavior.

No general non-aliasing contract is supplied. Aliasing among the source, result slot, container, header, attachment node, and obtained node can make the exact access order consequential.

## Behavior

### Node acquisition and partial value initialization

The first dependency call is F-547af65833e6 with the container address. Its returned address is retained as the obtained node address and is the value ultimately written to the result slot.

The function tests whether the obtained address plus 16 is nonzero. This is not a test that the obtained address itself is nonzero.

When the derived address is nonzero:

1. The first source byte is read and written to obtained node +16.
2. F-4e8353c41904 is called with destination obtained node +20 and source value +4.

The first-byte write precedes the dependency call. No direct copy of source bytes +1 through +3 is shown. The dependency’s data extent and construction, copying, or ownership semantics are unknown.

When the derived-address test is false, both initialization operations are skipped. Insertion work nevertheless continues.

A null acquisition result is not handled as a clean failure. Under ordinary address-offset reasoning, null plus 16 is nonzero, leading to an attempted first-byte store at that offset. Such a result is outside the valid-storage preconditions.

### Count update and attachment selection

After initialization, including any normal return from F-4e8353c41904, the function reads container +20, adds one, and writes the result back.

It then loads the current header address from container +16. First-link attachment is selected if the attachment node equals that loaded header or if the selector is nonzero.

Otherwise, the function enters the comparison route. Before calling the comparison dependency, it sets two retained auxiliary argument values to zero. These values otherwise retain the original selector and attachment-node address, respectively. Their later use is described under Dependencies.

F-e2cfac22dfa4 receives, in order:

1. Container +25.
2. The original source-value address.
3. Attachment node +16.

A nonzero result selects first-link attachment. Zero selects second-link attachment. The function does not require a result restricted to zero and one.

The comparison sees the original source address, not obtained node +16. The count increment and any value initialization have already occurred. Dependencies may have changed the source or container before this call; preservation is not assumed.

### Attachment and endpoint updates

On the first-link path, the function first stores the obtained node address at attachment node +8. It then reloads the container’s header address.

If the attachment node differs from this reloaded header, the function reads header +8 and replaces it with the obtained node only if it equals the attachment node.

If the attachment node equals this reloaded header, the function:

1. Writes the obtained node to that header’s +4 root link.
2. Reloads the container’s header address again.
3. Writes the obtained node to the newly selected header’s +12 endpoint link, without an endpoint-equality condition.

With a stable header and header attachment, the effective write order is header +8, header +4, then header +12.

On the second-link path, the function first stores the obtained node at attachment node +12. It reloads the header address, reads that header’s +12 endpoint, and replaces the endpoint only if it equals the attachment node.

After either path, the function writes the attachment-node address into obtained node +4 as its parent.

These are separate ordered writes, not an atomic publication. The selected attachment-node write does not prove that this node is reachable from the container. Moreover, later dependency calls may alter relevant links.

### Repair-loop entry and stopping conditions

The repair cursor initially identifies the obtained node.

At the beginning of each iteration, the function reloads the header address and reads its +4 root link. If that root equals the repair cursor, the loop stops without reading the cursor’s parent color in that iteration.

Otherwise, it reads the cursor’s parent link and that parent’s color byte. Any nonzero color stops the loop. For a zero-colored parent, it reads the parent’s parent link as the grandparent address and reads the grandparent’s first child.

The repair branch depends on whether the parent equals that first child. The alternative branch does not separately verify that the parent equals the grandparent’s second child.

### Parent is the grandparent’s first child

The function reads the grandparent’s second child as the opposite child.

If the opposite child is non-null and has color zero, the function performs these operations in order:

1. Writes one to the captured parent’s color.
2. Writes one to the captured opposite child’s color.
3. Resolves the cursor’s parent and grandparent links and writes zero to that grandparent’s color.
4. Resolves the cursor’s parent and grandparent links again and advances the cursor to that grandparent.

It then repeats the root check. No structural dependency is called in this recoloring case.

If the opposite child is null or has nonzero color, the function checks whether the cursor equals the parent’s second child. If so, it calls F-9a4773035256 with the container and captured parent, then assigns that captured parent as the repair cursor.

It next:

1. Reads the cursor’s current parent and writes one to that parent’s color.
2. Resolves the cursor’s parent chain again and writes zero to the resulting grandparent’s color.
3. Resolves the grandparent again and calls F-960cfae00cac with the container and that address.

This occurrence of F-960cfae00cac displays two arguments. The loop then repeats.

### Parent is not the grandparent’s first child

The opposite child is the already-read grandparent’s first child.

If this child is non-null and has color zero, the same recoloring and upward-cursor sequence applies.

Otherwise, the function checks whether the cursor equals the parent’s first child. If so, it calls F-960cfae00cac at a distinct, six-argument call site, then assigns the previously captured parent as the repair cursor. The six supplied values are specified below.

It next:

1. Reads the cursor’s current parent and writes one to that parent’s color.
2. Resolves the parent chain again and writes zero to the resulting grandparent’s color.
3. Resolves the grandparent again and calls F-9a4773035256 with the container and that address.

The loop then repeats.

Repeated parent-chain resolutions are actual repeated reads. A dependency’s returned state, or an earlier aliased write, can change what later reads resolve. A pre-call parent chain is not authoritative after a dependency returns.

### Finalization

After the loop stops, the function reloads the container’s header address, reads its root link, and writes one to the addressed root’s color byte.

Only afterward does it write the originally obtained node address to the result slot. The returned address is not necessarily the root or final repair cursor.

There is no explicit success code, failure code, or rollback path.

## Side effects

Direct mutations comprise:

- A conditional first-value-byte write.
- The count-like field increment.
- A selected attachment-link write.
- Conditional endpoint updates and the header-attachment root update.
- The obtained node’s parent-link write.
- Repair-related color writes.
- A final root-color write.
- The final result-slot write.

Every dependency may have additional effects not established here. In particular, no dependency is assumed to preserve globals, container fields, source bytes, node links, allocation state, or ownership.

The function itself does not directly initialize the obtained node’s color or child links. Suitable starting state must come from caller invariants, acquisition behavior, or other established conditions.

Storing the obtained address into the supplied attachment node makes it reachable through that particular link at that point, subject to aliasing and subsequent changes. Reachability from the container requires that the attachment location belongs to the container’s reachable structure, or that appropriate header updates establish reachability, and that dependencies do not undo the relevant links. Normal completion alone is insufficient.

No allocation ownership, source ownership, destruction duty, or lifetime transfer follows solely from these stores. There is no explicit release, destruction, logging, synchronization, or transactional recovery in the supplied body.

A dependency fault or nonlocal exit may leave partial state. The count changes before comparison; attachment and parent initialization precede structural repair calls.

2. Captured parent address.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid storage, defined arithmetic, a stable header, suitable initial node state, valid repair links, and dependencies that return normally without unmentioned interference.

### Stable-header attachment

When the attachment node equals the header:

- Comparison is skipped, regardless of selector.
- The count increments before attachment.
- Header +8, +4, and +12 receive the obtained node in that order.
- The obtained node’s parent becomes the header.
- The initial repair root check stops the loop.
- The root color becomes one before the result-slot write.

### Nonzero selector

For a non-header attachment node and selector −1:

- Comparison is skipped because the selector is nonzero.
- Attachment node +8 receives the obtained node.
- Header +8 changes only if its inspected value equals the attachment node.

Positive selectors follow the same selection rule.

### Comparison-selected attachment

For a non-header attachment node and selector zero:

- Comparison runs after initialization and count increment.
- Result zero selects attachment node +12.
- Result seven selects attachment node +8.
- The retained fifth and sixth arguments for any later six-argument repair call are both zero in either case.

### Recoloring

For a non-root cursor with a zero-colored parent and non-null, zero-colored opposite child:

- Parent and opposite child receive color one.
- A freshly resolved grandparent receives color zero.
- The cursor advances through another parent-chain read.
- No structural dependency is called in that iteration.

### Six-argument call with null opposite child

Assume the mirrored structural branch reaches the six-argument call, the opposite child is null, and the captured grandparent address is 0x12345000.

The third argument is null and the fourth argument is the 32-bit value 0x12345000. It is not a color value in this case.

### Six-argument call with nonzero-colored opposite child

Under the same call-reaching conditions, but with a non-null opposite child whose inspected color is 200:

- The third argument is that child’s address.
- The fourth argument is unsigned 32-bit 200.

With color zero, recoloring occurs instead; that iteration does not reach this structural call.

### Nonzero parent color and disconnected attachment

Assume a valid container root distinct from the obtained node, and a supplied attachment node with color two that is not reachable from the container. Assume no endpoint equality causes an endpoint update.

After attachment, repair stops at the nonzero parent color. The existing container root receives color one and the result slot receives the obtained node. Completion does not make the disconnected attachment reachable from the container.
