# F-a441e10ff512

## Purpose

F-a441e10ff512 conditionally detaches a referenced node from a linked structure, performs color-dependent structural repair, passes the detached node’s payload address to a dependency, publishes the node’s address in a container-maintained chain, and decrements a count. It writes one 32-bit result word to caller-provided storage.

A preliminary dependency controls whether removal occurs. When that dependency returns nonzero, the function instead outputs the container’s current header word and performs none of the direct removal-path mutations.

The links, cached extrema, and color operations suggest tree erasure with red/black-style repair. That interpretation is inferred intent. Ordering, balance, dependency semantics, and allocation ownership are not established by this body.

## Behavior

### Preliminary decision and result preparation

The initial observable reads are the reference word, followed by the container’s header word. Copies of these words become two temporary arguments to F-16fc12967f5e.

If that dependency returns nonzero, the function rereads container offset +16 and writes that value to result storage. It does not directly unlink a node, repair colors, call F-4b957c7aaf84 or F-8a5aadac202f, update the chain, or decrement the count. This restriction concerns this function’s direct actions, not effects performed by F-16fc12967f5e.

If the result is zero, F-4b957c7aaf84 receives the address of the first temporary word. The function then rereads reference storage to obtain the target node address. Consequently, the removal target need not equal the initial reference snapshot if a dependency changes the referenced storage.

The first temporary is retained for the final output. No comparison or reference-advancement semantics are independently established.

### Detachment and replacement

The target’s left-child link is inspected first. Its right-child link distinguishes the remaining cases.

#### Target without children

The target’s parent becomes the repair position.

When that parent equals the current header address, the direct header writes occur in this order:

1. Rightmost becomes the parent/header address.
2. Leftmost becomes that address.
3. Root becomes zero.

Otherwise, the parent’s left-child word is compared with the target. A match selects the left link; a nonmatch selects the right link without separately validating that it contains the target.

The selected link is cleared by four successive byte writes in increasing address order: offsets +8 through +11 for the left link, or +12 through +15 for the right link. These are not established as one atomic word write.

The corresponding cached extreme is then inspected: leftmost for a cleared left link, rightmost for a cleared right link. If it equals the target, it is replaced with the parent.

#### Target with exactly one child

The sole child becomes the replacement and the repair position.

The child’s parent word is written from the target’s parent before the incoming structural link is changed. The function then:

- Replaces the header’s root word if it equals the target.
- Otherwise replaces the target parent’s left link if that link equals the target.
- Otherwise replaces the parent’s right link, without validating that link.

Cached extrema change only when their current values equal the target.

For a cached-leftmost target:

- If the target’s right child is absent, leftmost becomes the target’s parent.
- Otherwise, leftmost becomes the terminal node reached by following left links from the replacement.

For a cached-rightmost target:

- If the target’s left child is absent, rightmost becomes the target’s parent.
- Otherwise, rightmost becomes the terminal node reached by following right links from the replacement.

The original target remains the node selected for payload processing and chain publication.

#### Target with two children

The replacement is selected by entering the target’s right subtree and following left links until a node with no left child is reached. Under the tree interpretation, this is the successor. Its right child, if present, is the initial repair position.

Relocation preserves the following direct-write order:

1. The target’s left child receives the replacement as parent.
2. The replacement receives the target’s left-child link.
3. The replacement’s former position is handled.
4. The target’s incoming root or parent-child link is replaced.
5. The replacement receives the target’s parent.
6. The replacement and target exchange color bytes.

Handling the former position depends on placement:

- **Immediate right-child replacement:** its right child, when present, receives the replacement as parent. Its right-child link is otherwise retained.
- **Deeper replacement:** its right child, when present, receives its former parent. That former parent’s left link is then replaced with the right-child address, including zero when absent. The replacement receives the target’s right-child link, and that subtree root receives the replacement as parent.

The incoming-link selection uses the same root-first, then parent-left-match, otherwise-parent-right rule as the one-child case.

If the replacement has no right child, the replacement itself becomes the repair position. Otherwise, its right child remains the repair position.

The original target is still retired. Following the color exchange, its color is the replacement’s former color. No payload copying between nodes is directly performed, and this branch does not directly update cached extrema.

### Color-dependent repair

Repair is entered only when the repair position differs from the header and the retired node’s color byte is nonzero. The header comparison precedes the retired-color read; equality skips that read and the repair block.

Within repair, each iteration first compares the repair position with the root obtained through the current container header. If they match, the loop body is skipped. Otherwise, iteration continues only if the repair position’s color equals exactly one.

Thus, nonzero retired color controls entry, but exactly-one repair-position color controls continued iteration.

Each iteration reads the repair position’s parent and tests whether the position equals that parent’s left child:

- A match selects the parent’s right child as sibling.
- A nonmatch selects the parent’s left child, without verifying right-child membership.

For the descriptions below, the **nearer child** is the sibling’s child on the repair position’s side; the **farther child** is its opposite child.

#### Zero-colored sibling

When a present sibling has color zero:

1. The sibling is colored one.
2. The parent is colored zero.
3. The orientation-specific dependency is called.
4. The repair position’s parent and the sibling link are reread.

The established calls are:

| Orientation | Dependency and visible arguments |
|---|---|
| Position matches parent’s left child | F-ebd170a93754 receives container and parent. |
| Position does not match parent’s left child | F-6b3ab84173ed receives container and parent. |

The parent argument is read from the repair position’s parent field for the call. These calls do not establish rotation semantics or preservation of other state.

#### Missing sibling and upward propagation

If the selected sibling is absent, either initially or after the zero-colored-sibling call, the current repair position is colored zero and repair moves to the parent. The root/color conditions are then reevaluated.

For child-color decisions, an absent sibling child satisfies the same relevant condition as a child whose color is exactly one. Other nonzero colors are not automatically treated as one.

If both sibling children are absent or colored one, the sibling is colored zero and repair moves to the repair position’s parent.

#### Nearer-child preparation

When the both-children condition does not apply, but the farther child is absent or colored one:

1. The nearer child is colored one when its link is nonzero.
2. The sibling is colored zero.
3. The preparation dependency is called.
4. The sibling is reread through the repair position’s current parent.

#### Concluding restructuring

With a sibling available for the concluding case, the function:

1. Copies the parent’s color to the sibling.
2. Colors the parent one.
3. Colors the sibling’s farther child one when present.
4. Calls the concluding dependency.
5. Leaves the loop.

The calls are:

| Orientation | Dependency and visible arguments |
|---|---|
| Position matches parent’s left child | F-ebd170a93754 receives container and parent. |
| Position does not match parent’s left child | F-6b3ab84173ed receives container and parent. |

The parent argument is read from the repair position’s parent field.

Every normal exit from an entered repair block writes one to the current repair position’s color. Paths that bypass the block do not perform this common final write.

### Payload call, chain publication, count, and output

After structural processing:

1. The current chain head is read from container offset +4.
2. That word is written to the retired node’s offset +12.
3. F-8a5aadac202f receives the address at retired-node offset +16.
4. After it returns, the retained retired-node address is stored at container offset +4.
5. The count at container offset +20 is read, decremented by one, and written back.
6. The retained result temporary is written to result storage.

The node-link write precedes the payload call. Chain-head publication, count adjustment, and output follow it.

There is no subsequent explicit dereference or write through the retired-node address after F-8a5aadac202f returns. Storing that address into the container does not establish that its allocation remains live or writable.

The count decrement uses the value present after the payload dependency returns, not an entry snapshot. It has no zero check or saturation. Zero becomes negative one under the supplied signed 32-bit arithmetic. Subtraction from the minimum signed 32-bit value is outside the representable range; its behavior is not established here.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless stated otherwise, they assume accessible storage, coherent links, no relevant aliasing, returning dependencies, representable arithmetic, and no dependency mutations beyond those specified.

### Bypass observes the current header

If F-16fc12967f5e returns nonzero and changes the container header word, the output must contain the changed header word. Neither F-4b957c7aaf84 nor F-8a5aadac202f is called, and no direct removal-path writes occur.

### Emptying a single-node structure

For a childless target whose parent equals the header:

- Header rightmost and leftmost become the header address, in that order.
- Root becomes zero afterward.
- Repair is skipped.
- The target receives the prior chain head at offset +12 before payload processing.
- Chain publication, count decrement, and output follow the payload call.

### Root with one right child

The child’s parent changes before the root field. If the target is cached leftmost, the new leftmost is obtained by following left links from the replacement. The original target, not the child, is retired.

### Deeper replacement

For a two-child target with a deeper successor, the successor’s former parent receives its right child as the left link, including zero when absent. A present right child first receives that former parent. The successor takes the target’s subtrees and incoming position, the color bytes are exchanged, and the original target is retired.

### Repair boundaries and helper identity

A zero retired color skips repair. Any nonzero retired color enters it when the repair position differs from the header. If that position is already the root, iteration is skipped but final coloring writes one.

When the position matches its parent’s left child, a zero-colored sibling requires F-ebd170a93754 with container and parent. Nearer-child preparation requires F-6b3ab84173ed with only container visibly supplied. The concluding case requires F-ebd170a93754 with container and parent. The nonmatching orientation uses the opposite dependency at each corresponding site.

### Payload mutation and lifetime boundary

If F-8a5aadac202f changes the count from seven to three, the subsequent direct decrement produces two.

If that dependency invalidates the retired allocation but otherwise permits execution to continue, the remaining explicit operations still store the retained address in the container, update the count, and write output without explicitly dereferencing that node. This does not establish that later chain traversal is valid.
