# F-32201b880080

## Purpose

F-32201b880080 processes catalog and schema state for one database selected from a connection’s database array. Its visible actions include catalog processing, optional catalog-object marking, storage access, metadata-dependent schema updates, conditional query execution, and status-dependent completion marking.

“Schema initialization” is inferred intent. The established behavior is the sequence of calls, reads, writes, branches, and return values described below. Dependency implementations are unavailable.

The catalog name is `sqlite_temp_master` for selector 1 and `sqlite_master` for every other selector.

## Interface

### Arguments and result

| Item | Representation | Visible use |
|---|---|---|
| Connection | 32-bit address-like value | Identifies mutable connection state |
| Database selector | Signed 32-bit integer | Selects a database entry |
| Diagnostic argument | Opaque 32-bit value | Included in callback context and supplied to diagnostic reporting |
| Return value | 32-bit status | Selected according to the paths below |

There is no visible null check, selector-bounds check, or validation of nested addresses. Safe use requires every accessed object to be valid at the time of access, including after intervening dependency calls. Invalid addressing and out-of-range selector behavior are not specified.

### Visible object layout

These offsets describe the supplied representation, not a portable ABI.

| Connection offset | Width | Role |
|---|---:|---|
| `+0x08` | 32 bits | Database-array address |
| `+0x0c` | 32 bits | Flags tested or modified with `0x00008000` and `0x00040000` |
| `+0x1e` | 8 bits | Failure indicator |
| `+0x2c` | 32 bits | Result of an encoding-related dependency |
| `+0xe0` | 32 bits | State temporarily replaced during query execution |

Each database entry occupies `0x18` bytes.

| Entry offset | Width | Role |
|---|---:|---|
| `+0x00` | 32 bits | Input to catalog lookup and query construction |
| `+0x04` | 32 bits | Storage handle |
| `+0x14` | 32 bits | Schema-state address |

| Schema offset | Width | Role |
|---|---:|---|
| `+0x00` | 32 bits | First metadata word |
| `+0x58` | 8 bits | Format value |
| `+0x59` | 8 bits | Encoding-related value |
| `+0x5a` | 16 bits | Flags modified with masks `0x0001` and `0x0004` |
| `+0x5c` | 32 bits | Normalized third metadata word |

A nonzero catalog-lookup result is treated as an object address; its byte at `+0x34` is written with 1.

The callback context begins with three 32-bit fields initialized to the connection, selector, and diagnostic argument. An adjacent 32-bit status slot is subsequently read, but no initialization of that slot is visible before the initial callback.

### Retained entry versus fresh-array access

After catalog lookup and optional object marking, the function reads the connection’s database-array address and computes the selected entry address. That **retained entry address** is used throughout the storage-backed path.

Retaining the entry address does not retain its storage handle or schema address. Those fields are reread at their respective uses.

Other operations instead reload the connection’s database-array address and select an entry from that current array:

- Temporary-database completion marking on the missing-storage path.
- Schema flag `0x0004` when the fifth metadata word is zero.
- Primary-schema encoding reads and writes.
- Query-construction input from the selected entry’s first word.
- Schema flag `0x0001` at ordinary completion.

Consequently, metadata writes and completion flags can affect different schema objects if a dependency changes the array address or entry contents. The function does not reconcile those objects.

## Behavior

### 1. Initial catalog processing

The selector determines the catalog name and an associated opaque constant. A descriptor contains the selected name, another opaque value, the selected constant, and a following zero field.

F-0a6598ebb6d2 receives the callback context, count 3, descriptor address, and zero.

If its return is nonzero:

- Catalog lookup, storage access, allocation, and metadata processing are skipped.
- The eventual returned status comes from the adjacent context status slot, not directly from the dependency’s return.
- The final status rule described below still applies.

If its return is zero, F-4e77314e8c36 receives the connection, catalog name, and first word of the selected entry obtained from the then-current database array. A nonzero result is marked by writing 1 to its byte at `+0x34`; a zero result does not itself cause failure.

Only after this call and marking does the function establish the retained entry address.

### 2. Missing storage and allocation

The storage-handle field of the retained entry is tested.

If zero:

- Selector 1 causes schema flag `0x0001` to be added through a **fresh database-array lookup of entry 1**.
- Other selectors receive no corresponding flag write.
- The function immediately returns 0.

This return bypasses failure-indicator checking, final status classification, allocation, and storage cleanup.

For a nonzero handle, F-1c177d5ba9f6 is asked for a `0x60`-byte work object. If the result is zero, the function writes 1 to the connection failure byte and returns 7. It does not perform the storage-operation or work-cleanup sequence.

The handle tested before allocation is not captured for later calls. After successful allocation:

1. The retained entry’s handle field is reread for F-0b4658e20c99.
2. It is reread again for F-80f420262fea, whose remaining arguments are 1, 0, 0, and the work address.

Either dependency can therefore receive a different handle from the one originally tested, including zero if an intervening call changed the field. There is no repeated nonzero check.

### 3. Storage status and metadata destinations

F-80f420262fea determines the next path:

- **Status 0:** perform indexed metadata calls.
- **Status `0x10`:** invoke an unmapped external dependency with the metadata-area address and size `0x28`, then enter metadata processing with query suppression enabled.
- **Any other status:** obtain a diagnostic through F-d5aed6d90713, report it through F-2cb24bca4183 with the diagnostic argument and a trailing zero, then clean up with that status.

For status zero, F-70fe47664dff is called with indices 1 through 10 in ascending order. The destination for index 1 is the metadata-area base; each subsequent destination advances by four bytes, through base plus `0x24`. The retained entry’s handle field is reread separately for every call.

Each return status is checked before another metadata call. The first nonzero status stops the sequence, is converted and reported as a diagnostic, and proceeds to cleanup without schema metadata processing.

**A zero return does not establish that a destination was initialized.** The visible evidence establishes destination addresses, indices, and checked statuses, not the dependency’s write extent or initialization guarantee. It does not establish that a call writes exactly one word, writes only its supplied destination, or writes anything on success.

Subsequent processing interprets this region as ten consecutive 32-bit words. Only the first, second, third, and fifth are visibly used for decisions or schema values here. The supplied local declarations do not, by themselves, establish a runtime buffer overflow.

The special `0x10` dependency likewise has unknown write behavior. Its size argument is not evidence that it clears the area.

### 4. Metadata-dependent writes

After all ten metadata calls return zero, or after the special external operation, processing occurs in this order:

1. Read the retained entry’s schema address and write the first metadata word to schema offset `+0x00`.
2. Branch on the fifth metadata word.
3. If the encoding branch permits continuation, copy the current primary encoding byte to the schema reached through the retained entry.
4. Normalize and store the third metadata word.
5. Reread the retained entry’s handle for F-50de58a8a319.
6. Reread the retained entry’s schema address for format writes and validation.

These writes are not rolled back after later failures.

#### Fifth metadata word

If the fifth word is zero, schema flag `0x0004` is added through a **fresh lookup of the selected entry in the current array**. Processing then continues.

If the fifth word is nonzero:

- For selector 0, the current array’s primary-schema address is read, and the low eight bits of the word are written to its encoding byte. F-4a95613e1504 receives the connection, 1, `BINARY`, 6, and 0. Its result is stored at connection offset `+0x2c`.
- For every other selector, the complete 32-bit fifth word must equal the zero-extended encoding byte from the current primary schema. Matching only its low byte is insufficient.

A mismatch reports an opaque diagnostic through F-2cb24bca4183, sets status 1, and proceeds to cleanup. It skips the encoding copy, normalization, format handling, and query path.

On continuation, the primary encoding byte is read through a fresh database-array lookup and copied to the schema reached through the retained entry. For selector 0, this read occurs after F-4a95613e1504; it need not observe the object or value written before that call.

#### Third metadata word

The third word is interpreted using a signed 32-bit negativity test:

- Zero becomes 2000.
- A nonzero value with no sign bit remains unchanged.
- A value with its sign bit set is negated using the represented unsigned 32-bit word arithmetic.

Thus the represented normalization of `0x80000000` remains `0x80000000`; it does not become a representable positive signed value. This describes the supplied word-level representation, not independently inspected machine instructions.

The normalized word is written to offset `+0x5c` of the schema currently referenced by the retained entry.

### 5. Format processing

After F-50de58a8a319 returns, the second metadata word’s low eight bits are written to the retained entry’s currently referenced schema at `+0x58`.

- Low byte zero is replaced with 1.
- Low bytes 1 through 4 are retained.
- A low byte above 4 reports `unsupported file format`, sets status 1, and proceeds to cleanup.

The unsupported byte is written before rejection.

Only after this validation, selector 0 additionally tests the **entire second word as signed 32-bit**. If it exceeds 3, connection flag `0x00008000` is cleared. The full-word comparison and byte-sized validation are distinct.

### 6. Query and completion

The special `0x10` path skips query construction, execution, and the post-query dependency, and sets the intermediate status to zero.

Otherwise, F-1983453691c7 receives the connection, a query template, the first word of the selected entry from a **fresh database-array lookup**, and the catalog name. The visible template begins by selecting `name`, `rootpage`, and `sql`; its complete text is unavailable.

The resulting query value is used without a visible zero-result check:

1. Save connection field `+0xe0`, after query construction.
2. Write zero to that field.
3. Invoke F-f2daf800ed06 with the connection, query value, opaque callback value, callback context, and zero.
4. Restore the saved field on normal return.
5. Replace execution status 4 with the context status slot.
6. Pass the query value to F-94cb53877c15.
7. If the effective status is zero, call F-f727355bee54 with the connection and selector.

Construction-time changes to `+0xe0` are included in the saved value. Execution-time changes are overwritten by restoration on normal return. Nonlocal exits are not specified.

Next, both the ordinary query path and the special `0x10` path check the connection failure byte:

- If nonzero, status becomes 7 and F-aacdb1821b51 receives the connection and zero.
- A nonzero status is retained unless the subsequently read connection flags contain `0x00040000`.
- If that mask is present, the error is replaced with zero.
- A zero or overridden status causes schema flag `0x0001` to be added through a **fresh lookup of the selected entry in the current database array**.

Encoding mismatch, unsupported format, ordinary storage failure, and metadata-call failure bypass this completion override.

### 7. Cleanup and final status

After successful work allocation, normal cleanup is:

1. F-2106ab1fda38 with the work address.
2. F-94cb53877c15 with that address.
3. Reread the retained entry’s storage-handle field.
4. F-96dd78c4ca33 with that newly read handle.

The cleanup handle need not equal any earlier handle. In particular, the read occurs after both work-cleanup dependencies.

The final status is preserved across these cleanup calls. Status 7 or `0x0c0a` causes the connection failure byte to be set to 1 before return. Other statuses are returned without this final write. The missing-storage return bypasses this classification.

## Side effects

Direct writes include catalog marking; schema metadata, encoding, format, and flags; connection encoding-related state; connection flag clearing; temporary query-state replacement; and failure-byte setting.

Schema flag updates are 16-bit read-modify-write operations preserving other bits. There is no visible transaction or rollback encompassing the metadata updates.

The work allocation is followed by finalization and release requests on the visible normal cleanup paths. The constructed query is also passed to the release dependency. These calls do not establish complete ownership contracts: retention, transfer, nested-resource handling, and actual release behavior remain unknown.

No general dependency-preservation guarantee is established. Changes to the database-array pointer, retained entry fields, schema contents, or connection flags can affect subsequent operations exactly where those values are reread.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless a mutation is specified, dependencies are assumed to return normally and leave relevant state valid and unchanged.

1. **Temporary database without storage.** With initial processing successful, selector 1, and retained-entry handle zero, the current array’s entry-1 schema receives flag `0x0001`. Return is 0 even if the connection failure byte was already nonzero.

2. **Allocation failure.** With a nonzero tested handle and allocation result zero, the failure byte becomes 1 and return is 7. No storage operation or work cleanup occurs.

3. **Array replacement during allocation.** If allocation replaces the connection’s array pointer, storage access and first-metadata writes still use the retained entry. A zero-fifth-word flag write and later completion flag write use the replacement array.

4. **Handle changes between calls.** If allocation changes the retained entry’s handle from A to B, F-0b4658e20c99 receives B. If that call changes it to C, F-80f420262fea receives C. A later cleanup receives whatever handle is present after work finalization and release.

5. **Third metadata call fails.** If calls for indices 1 and 2 return zero and index 3 returns nonzero, indices 4–10 are not requested. The diagnostic and cleanup occur; schema metadata processing does not. No conclusion follows about which destinations the successful calls initialized.

6. **Full-word encoding mismatch.** With a non-primary selector, primary encoding byte 1, and fifth metadata word 257, comparison fails. The first schema metadata write has already occurred; encoding copying and format processing do not occur.

7. **Unsupported format.** With encoding accepted and second-word low byte 5, schema format byte 5 is written before reporting the error. No query is constructed.

8. **Different comparison widths.** For selector 0 and second metadata word 256, the format byte becomes 1 and flag `0x00008000` is cleared. For word `0xffffffff`, low-byte validation rejects the format before the full-word flag comparison.

9. **Query substitution and override.** Execution status 4 is replaced by the context status. If that effective status is nonzero and completion observes flag `0x00040000`, it becomes zero and the current array’s selected schema receives flag `0x0001`.

10. **Special storage status.** Status `0x10` invokes the external metadata operation and suppresses querying. Metadata-derived outcomes remain conditional on the area’s actual contents; zero-filled metadata cannot be assumed.
