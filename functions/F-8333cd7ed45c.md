# F-8333cd7ed45c

## Purpose

The established behavior is defined by call order, four-byte field accesses, shared-state reads, and one unconditional record write on the normal path. The available evidence does not establish the application-level meaning of the record, its status values, or the dependency operations.

This contract describes normal execution through the supplied static representation. It does not establish memory safety for arbitrary inputs or the behavior of unavailable callees.

## Behavior

### 1. Initial dependency call

The function reads four bytes at input offset `0xB0` and passes that value as the sole explicit argument to F-936a8728139d.

This occurs before the record address at input offset `0xB4` is read. The first dependency may therefore affect the record selected by this invocation, whether by modifying the input object or through other shared state.

The return value of F-936a8728139d, if any, is not visibly used.

### 2. Record selection and intervening calls

After F-936a8728139d returns, the function reads the four-byte record address at input offset `0xB4`. That selected address is retained for subsequent record accesses.

The function then invokes:

1. F-da2d75c0df8d with no explicit arguments.
2. F-338d16f9ce72 with the current root-reference value as its sole explicit argument.

These calls precede the status comparison. Neither call’s return value is visibly used.

If either dependency later changes the input object’s record-address field, that change does not redirect this invocation’s record accesses: selection has already occurred. However, the selected record’s lifetime and contents are not protected by any visible mechanism. A callee that invalidates the retained address can make later accesses invalid.

The root reference used as the argument to F-338d16f9ce72 is read for that call. It is not the necessarily same value used during the final pointer traversal, because the shared value is read again later.

### 3. Conditional record processing

After F-338d16f9ce72 returns, the function compares:

- the four-byte status at selected-record offset `0x20`; and
- the shared comparison word.

The comparison therefore observes state available after the preceding dependencies have run, rather than a status snapshot taken on entry.

If the values are equal, the function invokes F-77781c8e0ff9 with these three explicit arguments:

| Argument position | Value |
|---|---|
| First | Four-byte value at selected-record offset `0x28` |
| Second | Current shared conditional argument |
| Third | Retained selected-record address |

The record field at `0x28` is not read by the visible function when the comparison does not match.

The exact evaluation order of the two comparison operands, and of the argument-value reads within the conditional call, is not established. The branch relationship and ordering relative to completed calls are established.

The conditional call is not a loop. Even if F-77781c8e0ff9 changes the status or comparison word, the function does not visibly repeat the comparison or invoke that dependency a second time.

### 4. Status replacement

Once the conditional call has returned, or immediately after a nonmatching comparison, the function writes the four-byte replacement word to selected-record offset `0x20`.

This write occurs on both branches of the comparison, provided execution reaches it.

The replacement is not taken from a dependency return value. Its exact byte pattern is not established by the supplied material.

If F-77781c8e0ff9 writes a different value to the status field, this subsequent write replaces that value, assuming the selected record remains valid. The function does not visibly preserve the old status or provide a rollback path.

### 5. Final pointer traversal and callback gate

After replacing the status, the function reads the current root reference and accesses the cell it identifies. The four-byte contents of that cell are interpreted as an object address.

There is no visible null check on the root reference before this cell access.

The remaining behavior depends on the object address:

- **Zero object address:** the function does not dereference a gate object and does not invoke the callback.
- **Nonzero object address:** the function reads four bytes at that object’s start.
  - A zero gate word suppresses the callback.
  - A nonzero gate word permits the indirect callback invocation.

The gate word is **not** the callback destination. The indirect call uses the separately stored callback target.

No explicit arguments are shown for that callback. The evidence does not establish the full callback ABI, implicit execution context, or whether the callback can inspect state through other means.

If the callback returns normally, the function returns without another visible record access or status write. If the gate fails, the function returns without invoking the callback.

The normal sequence depends on every invoked dependency returning control. If a dependency faults, terminates execution, transfers control elsewhere, or otherwise fails to return, subsequent operations are not guaranteed to occur.
