# F-0ebe5075a506

## Purpose

F-0ebe5075a506 builds a forward table of 16-bit identifiers from one of three predefined sources or from an external encoding. A nonzero option requests an additional reverse table associating identifiers with forward-table indices.

Established behavior includes output-field updates, reference reads, allocation requests, external reads, table writes, optional reverse construction, status checks, and cleanup. Character-set mapping is inferred intent; identifier meanings and dependency ownership contracts are not established.

This contract describes the supplied static representation. No runtime tests have been performed.

## Interface

### Inputs

The function receives six inputs, in order:

1. **Output-state address:** points to five consecutive 32-bit fields.
2. **Entry count N:** unsigned 32-bit count of forward entries.
3. **Context address:** supplied to external-reading operations. A 32-bit value at context byte offset 28 is captured at entry for allocation and cleanup.
4. **Base value:** 32-bit operand used in external metadata.
5. **Selector:** unsigned 32-bit value. Values 0–2 select predefined sources; all other values select external decoding.
6. **Reverse-map flag:** zero disables reverse construction; any nonzero value enables it.

The original context address and the value captured from context offset 28 are distinct dependency inputs. In particular, external format-0 finalization receives the original context address, not the captured value.

### Output-state layout

| Byte offset | Width | Meaning |
|---|---:|---|
| 0 | 32 bits | External format |
| 4 | 32 bits | Predefined selector or external metadata |
| 8 | 32 bits | Forward-table address |
| 12 | 32 bits | Reverse-table address |
| 16 | 32 bits | Reverse entry count |

Stored addresses have a visible 32-bit representation. Table elements occupy 16 bits. Visible address-offset arithmetic uses the 32-bit domain without bounds or overflow validation.

### Return value

The visible 64-bit return combines:

- **Low 32 bits:** final status bit pattern.
- **High 32 bits:** an auxiliary value initially equal to N.

The high word becomes zero immediately before forward allocation on accepted predefined paths and external paths that reach allocation. Reverse construction also sets it to zero before reverse allocation.

Consequently:

- Rejected predefined counts retain N in the high word.
- External setup or initial-format-reader failures occurring before allocation retain N.
- Paths reaching forward allocation return a zero high word, including later detected failures.
- Unsupported-format rejection occurs after allocation and returns a zero high word.
- Ordinary successful completion returns both words zero.

Explicit count and unsupported-format rejection assign status 3 after the diagnostic returns. Other status values originate from dependencies or their side effects. The ABI meaning of the combined return beyond this composition is **documented_only**.

### Preconditions and ownership

All reached memory accesses and dependency arguments require suitable accessible storage. The function neither validates addresses nor independently checks allocation capacity.

The forward and reverse fields are not unconditionally initialized at entry. Cleanup can therefore receive addresses that predate this invocation. Existing addresses overwritten during construction are not visibly released first.

Successful completion performs no release. Caller ownership of constructed storage is plausible intent, not an established contract. Allocation, release, null handling, and zero-length-operation semantics remain unresolved.

Aliasing among output fields, context, table storage, global references, and dependency-accessible state can alter subsequent behavior. Ordinary content predictions require noninterference assumptions.

## Behavior

### Entry and captured context state

The function reads the 32-bit value at context offset 28, initializes status to zero, and initializes the return high word to N.

All allocation and cleanup calls use that captured value. They do not reread context offset 28. External setup, reading, preparation, and finalization use the original context address where their arguments are established.

### Predefined sources

For selectors 0–2, the selector is stored at output offset 4. The corresponding diagnostic reference is then read from its global reference location before the count is checked.

| Selector | Accepted N |
|---|---|
| 0 | 0–229 |
| 1 | 0–166 |
| 2 | 0–87 |

An excessive count causes F-4457a9a44a68 to receive the captured diagnostic reference. If it returns, the high word is set to N, status becomes 3, and cleanup begins.

For an accepted count, the observable sequence is:

1. Set the high word to zero.
2. Request allocation through F-6dd003795db7, supplying the captured context-derived value, element size 2, zero, N, zero, and the status address.
3. Store the returned address in the forward field.
4. Read the selected predefined-data reference from its global location.
5. Check status.
6. On zero status, request copying of twice N bytes from that captured data reference to the captured allocation result.

The data-reference read occurs even when allocation reports failure. Allocation-side changes to that global reference therefore affect the captured source. The copy destination is the returned allocation address, not a reload of the forward field.

Copy length is formed by a 32-bit left shift by one. Accepted predefined counts prevent overflow. N = 0 still reaches allocation and, on zero status, a zero-byte copy request.

There is no direct format-field initialization on these paths. After copying, reverse-map selection occurs without an intervening status check.

### External setup and initial format

For selectors at least 3, the function stores base plus selector at output offset 4 using 32-bit arithmetic without overflow validation.

F-e40a3ceddab2 receives the original context address; its return replaces status. On zero status, F-6fa39a8df0d4 receives the context address and status address. Its low eight return bits, zero-extended, are stored in the format field before status is checked.

Thus a failed format read still updates the format field. The metadata sum is not an explicit argument to the setup dependency; seeking or indirect consumption of that sum is not established.

On zero status, the high word becomes zero and forward allocation uses the argument structure described above. Its returned address is stored before checking status.

After successful allocation, a 16-bit zero is written directly through the captured allocation result. This write occurs even when N = 0; successful zero-entry allocation does not itself establish that the write is safe.

Only afterward is the format field reloaded. Allocation-side changes to that field can therefore change format selection. Values 0, 1, and 2 are accepted. Any other current value causes a diagnostic using an embedded reference and, if the diagnostic returns, status 3 and cleanup. Allocation and the initial zero write precede this rejection.

### External format 0

For N = 0, this mode performs no preparation, element reads, or finalization. The earlier unconditional zero write has already occurred.

For nonzero N:

- F-d036abe1e536 receives the original context address and the 32-bit byte count twice N minus one entry, meaning twice the quantity N − 1.
- Its return replaces status. Nonzero status immediately leads to cleanup.
- Forward indices 1 through N − 1 are filled from F-7efb5338f0fa, which receives the original context address.
- After all element reads and stores, F-9787e15c337d receives the original context address—the third function input. Its return is ignored.

For each element, the reader executes before the forward-address field is read for the destination store. A reader that replaces that field can redirect the same iteration’s write. The captured allocation result is not the retained decoding destination.

For N = 1, preparation receives zero bytes, no element reads occur, and finalization still receives the original context address. Preparation-size arithmetic is 32-bit and can wrap for large N.

No explicit status address is passed to the element reader, and no per-element status check occurs. The ignored finalizer return does not establish status preservation: dependencies could retain access to status storage previously supplied elsewhere.

### External range decoding

A current format of 1 or 2 at initial selection enters range decoding at forward index 1. No ranges are read for N = 0 or N = 1.

Each range begins with F-8f49ed59b67e receiving the original context address and status address. Its low 16 return bits supply the starting identifier. Status is checked before proceeding.

The format field is then reloaded:

- If it equals exactly 2, F-8f49ed59b67e supplies a run length reduced to 16 bits. The arguments to this second invocation are not established by the supplied representation.
- Every other current value selects F-6fa39a8df0d4 with the original context address and status address. Its low eight return bits supply the run length.

Status is checked again before writing any entries for that range. This reader selection is not another supported-format validation: a dependency-installed value such as 0 or 9 selects the byte reader rather than triggering a diagnostic.

A run length describes up to one more entry than its numeric value. Zero therefore describes one entry. Maximum encoded capacities are 256 entries through the byte reader and 65,536 through the 16-bit reader.

Identifiers increase in the 16-bit storage domain, wrapping from 65,535 to zero. Writes stop when N forward entries have been accounted for, even if a range has unused capacity. Such truncation is not rejected.

Each destination uses the forward-address field rather than the original allocation result. This mode has no format-0 preparation or finalization.

### Optional reverse construction

Following predefined copying or completed external decoding, the reverse-map flag is examined without first rechecking status.

If enabled, all N forward entries are scanned as unsigned 16-bit identifiers through the forward-address field. The maximum starts at zero, including for an empty scan.

The reverse count is the maximum plus one, with bit 16 cleared:

- Maximum 0–65,534 gives maximum plus one.
- Maximum 65,535 gives zero.
- An empty scan gives one.

The function resets the high word to zero, requests reverse allocation with element size 2 and the computed count, stores the returned address, and checks status.

On zero status, the clearing primitive receives the captured reverse allocation result and twice the reverse count in bytes. Population then accesses forward and reverse storage through their output fields after clearing returns. The visible expression does not establish a separate ordering between those two address-field reads within an iteration.

Population proceeds in increasing forward-index order. Each forward identifier selects a reverse slot, which receives the low 16 bits of that forward index. With stable storage, duplicate identifiers leave the greatest matching index modulo 65,536.

After population, the computed reverse count is stored at output offset 16. If clearing has its apparent semantics, untouched reverse slots remain zero; zero cannot distinguish absence from a mapping to forward index zero.

A maximum identifier of 65,535 creates a boundary hazard: reverse allocation requests zero entries and clearing requests zero bytes, yet population still includes a write to reverse slot 65,535. No local check prevents it.

### Deferred status check

The ordinary final status check occurs only after optional reverse construction.

A status change during copying or format-0 finalization does not itself prevent reverse scanning and allocation. The reverse allocator receives the existing status address without an explicit reset; whether it preserves or replaces an error is unknown.

Likewise, a clearing-side status change does not prevent reverse population or the reverse-count store. Those operations precede the final check.

Zero status completes normally. Nonzero status enters cleanup.

### Error cleanup

On each detected error, the visible order is:

1. Read the current forward address and pass it, with the captured context-derived value, to F-bf7242c98d06.
2. Clear the forward field.
3. Read the current reverse address and pass it with the same captured context-derived value to F-bf7242c98d06.
4. Clear the reverse field.
5. Clear the format field.
6. Clear the metadata field.
7. Clear the forward field again.

The reverse cleanup argument reflects state after the first cleanup call and the forward-field clear. It is not captured at cleanup entry.

Both cleanup calls occur even when this invocation allocated neither object. The reverse-count field is not explicitly cleared.

Cleanup neither rechecks status nor explicitly replaces it. Dependency effects on escaped status storage can therefore affect the returned low word.

## Side effects

Direct output initialization is path-dependent:

- Predefined success does not directly set the format field.
- Success without reverse construction does not directly set the reverse address or count.
- Error cleanup clears the first four fields but leaves reverse count unchanged by direct stores.
- Dependencies may modify state accessible to them.

Other effects include global-reference reads, allocation requests, copying and clearing requests, external operations, diagnostic calls, initial and partial table writes, and paired cleanup calls.

Failures may occur after addresses have been replaced or tables partially populated. No local mechanism handles invalid memory access, nonreturning dependencies, or failures not represented by checked status.

## Acceptance examples

These are conditional static predictions, not executed tests. Unless varied explicitly, assume normal dependency return, adequate nonaliasing storage, successful reads and allocations, apparent copy/clear semantics, and preservation of relevant state except for stated effects.

1. **Predefined boundary:** Selector 0 with N = 229 reads its diagnostic reference, allocates, stores the forward address, reads the data reference, and copies 458 bytes. N = 230 instead diagnoses and cleans up, returning low word 3 and high word 230 if cleanup preserves status.

2. **Failed allocation reference read:** Accepted selector 1 with N = 166 still reads its predefined-data reference after storing the allocation result when allocation reports an error. It does not copy. The high word is zero.

3. **Format-0 completion:** With N = 3 and element results 7 and 12, forward entries become 0, 7, 12. Preparation receives four bytes. After both stores, F-9787e15c337d receives the original context address; its return does not replace status.

4. **Single-entry format 0:** N = 1 causes zero-byte preparation and no element reads. Finalization still receives the original context address. N = 0 instead skips preparation and finalization but not the initial zero write.

5. **Redirected destination:** If the first format-0 element reader replaces the forward field with another valid table address, its returned value is written at index 1 of that replacement table. The initial zero was written through the captured allocation result.

6. **Inclusive, truncated range:** Format 1, N = 4, start 20, and run length 2 produce 0, 20, 21, 22. With N = 3, start 50, and run length 10, only 0, 50, 51 are produced.

7. **Dynamic reader choice:** Initial format 2 enters range mode. If the starting-identifier dependency changes format to 9 without error, the byte reader supplies the run length. That later value alone causes no unsupported-format diagnostic.

8. **Reverse duplicate:** Forward entries 0, 4, 4 yield reverse count 5 and reverse slot 4 equal to 2. Unassigned slots remain zero under the clearing assumption.

9. **Unsupported-format timing:** Format 3 preserved through successful allocation causes the initial zero write before diagnosis. Allocation failure prevents that write. Allocation changing format to 0 changes the subsequent selection.

10. **Deferred error:** If format-0 finalization changes escaped status to nonzero, reverse scanning and allocation are still attempted when requested. An allocator preserving that error leads to cleanup at its status check.

11. **Reverse boundaries:** Empty predefined construction with reverse mapping computes count one. A forward maximum of 65,535 computes count zero but still leads to population writes if execution proceeds; safe completion is not established by a zero-entry allocation.
