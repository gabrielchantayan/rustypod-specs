# F-15cb46d648eb

## Purpose

F-15cb46d648eb prepares a caller-supplied state using a nonempty byte sequence and a fourth argument forwarded to initialization dependencies. Its established behavior includes:

- Optionally reducing an input whose length, interpreted as signed 32-bit, exceeds 64.
- Constructing two 64-byte blocks using byte transformations and padding.
- Storing one block at state offset `0x68`.
- Initializing the state and submitting the other block to a dependency.

The block size, two XOR constants, and optional reduction suggest a keyed digest preparation operation. That interpretation is inferred intent, not an established algorithm identity. The dependency implementations and the meaning of their byte representations are unavailable.

A null input pointer or zero input length causes an immediate return without state writes or dependency calls.

## Interface

The function has four inputs and no meaningful return value.

| Input | Representation | Role |
|---|---|---|
| Input length | Unsigned 32-bit integer | Byte count; also subjected to a signed 32-bit comparison |
| State address | 32-bit integer used as an address | Base address passed to dependencies and used for direct writes |
| Input address | Byte pointer | Source of input bytes; null is explicitly accepted |
| Initialization argument | Opaque 32-bit value | Forwarded unchanged to initialization calls |

The input is length-delimited. No terminator is sought, and zero-valued bytes do not end processing.

### State layout directly accessed

The function directly writes a 64-byte region beginning at state offset `0x68`:

| Relative offsets | Direct use |
|---|---|
| `0x00`–`0x67` | No direct access established; dependencies receive the state base |
| `0x68`–`0xA7` | 64-byte block, written before the final state initialization call |

Thus, ordinary nonwrapping address use requires writable storage through offset `0xA7`, or at least 168 bytes from the state base. This is only the minimum established by direct writes. Dependencies may require more storage.

The state address is not checked for nullness, alignment, validity, or available capacity.

### Temporary storage

The supplied representation exposes:

- A 65-byte local array, whose last 64 bytes form a temporary block. Its first byte is not accessed by the shown operations.
- A 96-byte scratch region passed to dependencies on the reduction path.
- A separate 32-bit local word read after those dependency calls.
- A 20-byte temporary output region used as the effective input on the reduction path.

The 32-bit word lies 96 bytes after the scratch-region base in the supplied layout. No direct assignment to that word is shown. Its connection to dependency state is unresolved.

All these regions are local to the invocation. The function performs no explicit allocation or release.

## Behavior

### 1. Early return

The following cases return without any dependency calls or direct state writes:

- The input address is null, regardless of length.
- The input length is zero, provided the input address is nonnull.

Length one is processed normally. The guard does not impose a general upper bound.

### 2. Conditional input reduction

For a nonnull input with nonzero length, reduction occurs only when the original length, interpreted as a signed 32-bit integer, is greater than 64.

Accordingly:

| Original unsigned length | Reduction selected? |
|---|---|
| `1`–`64` | No |
| `65`–`0x7FFFFFFF` | Yes |
| `0x80000000`–`0xFFFFFFFF` | No |

The reduction path performs these operations in order:

1. Invoke F-ed485a8933da with the scratch-region address and the initialization argument.
2. Invoke F-74d7981315b3 with the original input address, scratch-region address, and original unsigned length.
3. Invoke F-0b6f5f32b71e with the 20-byte temporary output address and scratch-region address.
4. Use that temporary output address as the effective input address.
5. Read the separate 32-bit local word and use its low 16 bits as the effective input length.

The effective length is therefore not explicitly set to 20, 64, or a known digest size. The existence of a 20-byte output region does not prove how much F-0b6f5f32b71e writes or what value the later length read produces.

No dependency return value controls this path. There is no shown recovery if a dependency fails to initialize the scratch data, produce output, or establish the subsequently read word.

Without reduction, the effective address and length remain the original input address and unsigned length.

### 3. Initialize the two blocks

After optional reduction, the function performs two complete initialization passes:

1. Write byte `0xEC` to all 64 bytes of the temporary block, in ascending index order.
2. Write byte `0xEC` to state offsets `0x68` through `0xA7`, in ascending index order.

The first pass completes before the second begins. Both complete before any direct copy from the effective input.

Consequently, overlap between the original input and the state block can change input bytes before they are copied. The directional copying described below does not protect against these earlier initialization writes.

### 4. Copy the effective input into both blocks

The function first copies the effective input to the temporary block, then separately copies it to the state block. It does not derive the state block by copying the temporary block.

Each stored byte is calculated using an arithmetic expression equivalent, after truncation to eight bits, to the source byte itself:

\[
((-75x+36)(-99)-20)\bmod256=x.
\]

This follows because the expression reduces to \(7425x-3584\), where \(7425\equiv1\pmod{256}\) and \(3584\equiv0\pmod{256}\).

Each copy independently selects its direction from the numeric source and destination addresses:

- If the destination address is lower than the effective input address, bytes are copied in ascending index order.
- Otherwise, bytes are copied in descending index order.
- Equal source and destination addresses use descending order.

The direction is selected by address ordering, not by an explicit overlap test.

The entire first copy completes before the second copy begins. The second copy reads the effective input again. It does not necessarily see the same values if the first copy or earlier block initialization changed overlapping storage.

There is no bound check against 64. An effective length exceeding 64 makes the copy operations write beyond their intended block regions. On the reduction path, an effective length exceeding 20 also makes them read beyond the declared temporary output region.

### 5. Transform all 64 bytes

For each byte index from 0 through 63, the function transforms the temporary-block byte first, then the corresponding state-block byte.

Define two eight-bit mappings:

\[
E(x)=(36-75x)\bmod256,
\qquad
D(y)=(-99y-20)\bmod256.
\]

These satisfy \(D(E(x))=x\). The final block mappings are:

\[
T_{\mathrm{temporary}}(x)=D(E(x)\mathbin{\mathrm{XOR}}0x36),
\]

\[
T_{\mathrm{state}}(x)=D(E(x)\mathbin{\mathrm{XOR}}0x5C).
\]

The XOR operates on the intermediate arithmetic value before the final multiplication and addition. The mappings above describe its stored-byte result because only the low eight bits survive.

These are not generally equivalent to directly XORing stored input bytes with `0x36` or `0x5C`.

Relevant values are:

| Byte before transformation | Temporary-block result | State-block result |
|---|---|---|
| `0xEC`, the padding byte | `0x0A` | `0x58` |
| `0x00` | `0xF6` | `0x84` |

The displayed loop update includes a mask clearing bit 16 of the index. For the established range 0 through 63, that mask has no effect: exactly 64 iterations occur.

### 6. Initialize and submit

After both blocks have been transformed:

1. Invoke F-ed485a8933da with the state address and the initialization argument.
2. Invoke F-74d7981315b3 with the temporary-block address, state address, and length 64.
3. Return.

The transformed state block exists before the initialization call. Its survival through initialization, submission, and return is not established. Neither dependency may be assumed to preserve it.

There is no F-0b6f5f32b71e call on the main state after the 64-byte submission.

## Side effects

### Direct memory effects

On a normal, unreduced path with effective length at most 64 and disjoint valid storage:

- The source bytes are read twice during copying.
- State offsets `0x68`–`0xA7` receive padding writes.
- The first effective-length bytes of that state region receive copy writes.
- Every byte of that state region receives a transformation write.
- The remaining direct writes affect local temporary storage.

Dependencies can add reads, writes, global changes, and other effects. Their effects are not characterized by this function alone.

### Ownership and lifetime

The function does not explicitly take ownership of the input or state storage, and it does not explicitly free either one.

Dependencies receive addresses of local storage:

- Reduction calls receive scratch and temporary-output addresses.
- The final submission receives the temporary-block address.

For use after this function returns to be valid, dependencies must not retain and later dereference these local addresses. Whether they retain, release, or otherwise manage passed storage is unknown; no ownership guarantees are established here.

### Errors and unsafe inputs

No explicit error status, exception handling, capacity check, or dependency-failure handling is present.

The null-input check does not make the state address optional for nonempty input. High-bit-set lengths bypass reduction and remain large unsigned copy counts. Such values can cause extensive out-of-bounds access; they are not safely reduced or rejected.

On the reduction path, safe deterministic execution depends on otherwise unestablished behavior: dependencies must produce readable output and establish a usable effective length. A value no greater than 20 is necessary to keep subsequent reads within the declared output region. A value no greater than 64 is necessary to keep direct copy writes within each block.

No synchronization or atomic access is established.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless otherwise stated, assume valid disjoint storage and dependencies that return normally without modifying the relevant source bytes.

### Null input

With a null input address and any length:

- No dependency is called.
- No direct state write occurs.
- The function returns without accessing the state address.

### Zero-length input

With a nonnull input address and length zero, the outcome is the same. No empty block is submitted.

### One zero byte

With length one and a source byte of `0x00`:

- No reduction dependency sequence occurs.
- Immediately before final state initialization, the temporary block contains `0xF6` followed by 63 bytes of `0x0A`.
- At that same point, the state block contains `0x84` followed by 63 bytes of `0x58`.
- State initialization is followed by submission of the temporary block with length 64.

The state block’s contents at return remain dependency-dependent.

### Exactly 64 bytes

With length 64:

- Reduction is not selected.
- All 64 input bytes are copied into each block before transformation.
- No padding position remains within either block.
- The final submission count is 64.

### Length 65 with an established reduction result

If the reduction dependencies produce 20 readable bytes and establish a low-16-bit length value of 20:

- The reduction calls consume the original address and count 65.
- Those 20 output bytes become the effective input.
- Each block has 20 copied positions and 44 padding positions before transformation.
- The original input is not directly copied into the blocks.

The stated dependency results are required conditions, not facts proved by this function.

### Reduction producing zero effective length

If reduction establishes an effective length of zero:

- Both copy operations perform no byte accesses.
- The temporary block becomes 64 bytes of `0x0A`.
- The state block becomes 64 bytes of `0x58` before state initialization.
- Final initialization and the 64-byte submission still occur.

This differs from an original length of zero, which returns immediately.

### High-bit-set length

With a nonnull input and length `0x80000000`, reduction is not selected. The copy count remains `0x80000000`. Acceptance must not treat this as a safe long-input case.

## Uncertainties

The following remain **documented_only**:

- The cryptographic or noncryptographic algorithm represented by the dependencies.
- Whether input and state bytes use an encoded representation.
- The complete state and scratch-context layouts.
- How the separately read length word becomes initialized.
- Whether reduction output fits within 20 bytes.
- Whether dependencies preserve the transformed state block.
- Whether dependencies retain pointers, manage ownership, access globals, or report failures externally.
- Whether production callers exclude high-bit-set lengths and overlapping storage.
- Behavior after invalid memory access or other violated storage preconditions.

The two block constants support an inference of paired keyed-processing blocks. They do not justify promising a named hash, MAC, digest size, or interoperable output format.

## Evidence

Established evidence consists solely of static inspection of the supplied function representation: guards, integer operations, direct memory accesses, local storage declarations, dependency arguments, and call order.

The byte identities and transformation examples follow from modulo-256 arithmetic. The signed-length boundary follows from the explicit signed comparison, distinct from the unsigned copy bounds.

No dependency implementation was available. No runtime tests have been performed. The acceptance examples state expected behavior under their explicit conditions; they are not observations of an executing program.
