# F-d988be290708

## Purpose

F-d988be290708 acquires one 20-byte slot from a caller-supplied pool state and partially resets that slot. It prefers a slot from a linked availability list. If that list is empty, it takes the next slot from a contiguous region, allocating and linking a new region when the region cursor equals its end marker.

The function has no explicit return value and does not write the selected slot address to a dedicated output field. Its directly observable results are changes to pool metadata, possible allocation requests, and writes to the selected slot.

“Pool,” “availability list,” and “slot” describe the structure suggested by the accesses. The supplied evidence establishes the mechanism, not the larger application’s ownership or lifecycle policy.

## Interface

### Input and result

The sole argument is an address of mutable control storage. Under the 32-bit representation shown by the supplied source, that storage contains four consecutive 4-byte fields:

| Byte offset | Field | Observed role |
|---|---|---|
| 0 | Block head | Address of the current block descriptor, or zero |
| 4 | Available head | Address of a reusable slot, or zero |
| 8 | Region cursor | Address of the next slot in the active contiguous region |
| 12 | Region end | Address compared with the region cursor to decide whether another block is needed |

The function returns no value. In particular, there is no established returned pointer to the acquired slot.

The control address is not checked for zero. The function assumes that every address it actually reads or writes is valid for the relevant access.

### Block descriptor layout

A newly allocated block descriptor occupies 12 bytes:

| Byte offset | Width | Meaning established by accesses |
|---|---:|---|
| 0 | 4 bytes | Link to the block head read while constructing the descriptor |
| 4 | 4 bytes | Capacity, measured in 20-byte slots |
| 8 | 4 bytes | Address returned by the payload allocation |

For an existing nonzero block head, only its capacity field is read during capacity selection.

### Slot layout

Each slot occupies 20 bytes. This function accesses only the following portions:

| Byte offset | Width | Behavior |
|---|---:|---|
| 0 | 1 byte | Set to zero |
| 4 | 4 bytes | Set to zero |
| 8 | 4 bytes | Set to zero |
| 12 | 4 bytes | Read as a next-slot address on the availability-list path, then set to zero |

Bytes 1–3 and 16–19 are not explicitly written. A contract that describes the entire slot as cleared would therefore be incorrect.

### Representation and preconditions

The source represents addresses through 4-byte integer fields and uses 32-bit unsigned arithmetic for capacity calculations. The observable layout described here consequently assumes the 32-bit address representation reflected by that source. A native 64-bit reinterpretation is not established.

For ordinary valid pool operation:

- The control fields must be readable, and fields changed on the selected path must be writable.
- A nonzero available-head address must identify storage supporting the next-link read and all slot reset writes.
- A cursor used directly must identify storage supporting all slot reset writes.
- A nonzero block head used during growth must identify a readable capacity field.
- Allocation results used as descriptor or payload addresses must support the subsequent accesses.

No validation enforces these preconditions.

## Behavior

### Selection priority

The available-head field is read first.

If it is nonzero, that address becomes the selected slot. The function reads the 4-byte value at slot offset 12 and stores it into the control structure’s available-head field. This removes the selected slot from the front of the list.

On this path, the function does not consult the region cursor, region end, or block head. It does not allocate and does not advance the region cursor. A nonempty availability list therefore takes precedence even if the region cursor equals the region end.

If the available-head field is zero, the function instead reads the region cursor and compares it with the region end.

### Taking a slot from an existing region

When the cursor and end differ, the original cursor address becomes the selected slot. The region cursor is advanced by exactly 20 bytes before the slot reset writes occur.

The comparison is equality only. There is no range check, alignment check, or check that a complete 20-byte slot remains before the end. A cursor beyond the end, or a cursor whose remaining region is shorter than one slot, is not rejected by this function.

### Choosing a new block capacity

When the cursor equals the end, the function chooses a new capacity.

If the block-head value is zero at the capacity decision, the new capacity is 32 slots.

Otherwise, the function reads the 32-bit unsigned capacity at offset 4 of the existing block descriptor. Let that value be \(c\). It forms two candidates:

- An additive candidate: \(c + 32\).
- A proportional candidate: \(c + \lfloor c/2 \rfloor + \lfloor c/8 \rfloor\).

Each candidate is computed with 32-bit unsigned arithmetic. Addition wraps modulo \(2^{32}\). The proportional candidate is selected when the additive candidate is less than or equal to it under unsigned comparison; otherwise, the additive candidate is selected. Equivalently, the selected capacity is the unsigned maximum of the two already-wrapped candidates.

Without overflow, this provides an increase of at least 32 slots and eventually favors approximately 1.625 times the prior capacity. That growth interpretation does not hold across wraparound.

No minimum, maximum, or overflow check follows the calculation.

### Allocating and publishing a new block

The growth path calls F-871e64ddc6de twice, in this order:

1. With arguments 12 and zero, obtaining the descriptor address.
2. With arguments equal to the new capacity multiplied by 20, and zero, obtaining the payload address.

The payload-size multiplication is also 32-bit unsigned arithmetic. A large capacity can therefore produce a wrapped request size, including zero.

Both dependency calls occur before this function initializes the descriptor or publishes the new block head. After they return, the function performs the following operations in the evidenced order:

1. Stores the payload allocation result at descriptor offset 8.
2. Reads the control structure’s then-current block head and stores it at descriptor offset 0.
3. Stores the selected capacity at descriptor offset 4.
4. Stores the descriptor address into the control structure’s block-head field.
5. Reads the payload address back from descriptor offset 8.
6. Stores the payload address plus the wrapped capacity-times-20 extent into the region-end field.
7. Stores the payload address plus 20 bytes into the region-cursor field.

The payload base becomes the selected slot. Thus, creating a block also consumes its first slot immediately.

The head stored into the new descriptor is read after both dependency calls. It must not be assumed to equal the head previously examined for capacity selection if the dependency can mutate shared state. Similarly, the payload address used for selection is read from the initialized descriptor rather than treated as an independently guaranteed immutable value.

### Resetting the selected slot

After selection and any relevant metadata updates, the function writes to the selected slot in this order:

1. A 4-byte zero at offset 4.
2. A 4-byte zero at offset 8.
3. A 4-byte zero at offset 12.
4. A one-byte zero at offset 0.

On the availability-list path, the old next-link value is read and published as the new available head before the selected slot’s offset-12 field is cleared.

On the contiguous-region paths, the cursor is advanced before any slot reset write.

These are the explicit access sequences established by the supplied representation. They do not establish atomicity, synchronization, or a machine-level memory-ordering guarantee.

## Side effects

### Direct state changes

The normal direct effects depend on the selected path:

| Path | Control changes | Other writes |
|---|---|---|
| Nonempty availability list | Available head replaced with selected slot’s old next link | Partial reset of selected slot |
| Existing region has unequal cursor and end | Cursor advanced by 20 bytes | Partial reset of selected slot |
| New block required | Block head, region end, and region cursor updated | Descriptor initialization and partial reset of first payload slot |

The function makes no direct write to the available-head field on either region path.

These distinctions assume the control structure, descriptor, and slot storage do not overlap. The function contains no alias checks. Overlapping storage can cause a descriptor or slot write to alter other state, changing the subsequent effects of the access sequence.

### Allocation and ownership

The function records each new descriptor in a linked block chain and records its payload address in that descriptor. It does not explicitly free an old descriptor, a payload region, or a selected slot.

This establishes retention of addresses in pool metadata, not a complete ownership contract. The following are unknown:

- Whether F-871e64ddc6de transfers ownership.
- Whether it returns fresh, distinct, suitably aligned storage.
- Whether it initializes memory.
- Which component eventually releases descriptors or payloads.
- Whether another operation recovers or exposes the selected slot address.

The selected slot’s old contents are overwritten only at the listed offsets. The function performs no explicit destruction or release of resources that those fields might previously have represented.

### Errors and partial progress

There is no explicit failure result, allocation-result check, rollback, or cleanup path.

If an allocation returns an unusable address, the function proceeds with stores or pointer use based on that result. The precise external outcome is not established; successful completion must not be promised.

If the second allocation fails after the first succeeds, the function contains no explicit release of the first result. Whether either dependency call can fail, throw, terminate, or perform its own cleanup remains unknown.

Metadata updates precede slot resetting. An interruption or invalid access during resetting can therefore leave a slot already removed from the availability list, or a cursor already advanced, without all reset writes having completed.

## Dependencies

### F-871e64ddc6de

This is the only explicit called dependency.

On a growth operation, it is called exactly twice by this function: first for a 12-byte descriptor, then for a capacity-dependent payload extent. Both calls receive zero as their second argument.

Its results are used as addresses. The descriptor result is subsequently written as three 4-byte fields; the payload result supplies the selected slot and region boundaries.

The meaning of the second argument, failure conventions, alignment, allocation lifetime, and effects on shared or global state are not established. No guarantee that it preserves the input control structure or other reachable memory may be inferred.

No dependency call occurs when the function selects an available-list slot or consumes a slot from an existing region.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless otherwise stated, they assume valid, nonoverlapping storage, ordinary 32-bit addresses without address wraparound, and dependency behavior that does not independently modify the described state.

### Available slot takes precedence

Given a nonzero available head identifying slot A, with slot A’s offset-12 field identifying slot B:

- The available head becomes B.
- A’s fields at offsets 4, 8, and 12 become four-byte zeros.
- A’s byte at offset 0 becomes zero.
- A’s bytes 1–3 and 16–19 retain their prior values.
- The region cursor, region end, and block head receive no direct writes.
- F-871e64ddc6de is not called.

This remains the selected path if the region cursor equals the region end.

### Existing region supplies one slot

Given a zero available head and a region cursor 40 bytes before the end:

- The original cursor is the selected slot.
- The cursor becomes its original value plus 20.
- The selected slot receives only the specified reset writes.
- No allocation occurs, and the block head and region end receive no direct writes.

### First block allocation

Given a zero available head, equal cursor and end, and a zero block head:

- The selected capacity is 32.
- The dependency requests are 12 bytes followed by 640 bytes, each with a zero second argument.
- The new descriptor records a zero predecessor, capacity 32, and the returned payload address.
- The block head becomes the descriptor address.
- The region end becomes payload base plus 640.
- The region cursor becomes payload base plus 20.
- The slot at the payload base receives the specified reset writes.

### Additive and proportional growth

Given a growth operation whose previous capacity is 32, the additive candidate is 64 and the proportional candidate is 52. The selected capacity is 64, and the payload request is 1,280 bytes.

Given a previous capacity of 64, the candidates are 96 and 104. The selected capacity is 104, and the payload request is 2,080 bytes.

### Unsigned wraparound affects selection

Given a growth operation whose previous capacity is \(2^{32}-1\):

- The additive candidate wraps to 31.
- The proportional candidate wraps to 2,684,354,557.
- The proportional candidate wins the unsigned comparison.
- Multiplying that capacity by 20 wraps to a payload request of 2,147,483,588 bytes.

The function does not reject this calculation. This is an arithmetic example, not evidence that such a request can succeed or that the resulting pool is safe to use.

### Equality is not a bounds check

Given a zero available head and a cursor greater than the end, the function does not grow the pool merely because the cursor is out of range. Because the addresses differ, it selects the cursor, advances it by 20, and attempts the reset writes.
