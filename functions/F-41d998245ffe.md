## Behavior

The following ordering is established by the supplied representation. It is not a claim that the underlying machine code, compiler memory model, or external observers have been independently verified.

### 1. Initial context updates and first snapshot

The function performs these accesses in order:

1. Writes the low byte of the fourth explicit argument to Context A at `0x15`.
2. Writes the 32-bit address value of Context B to Context B at `0x54`.
3. Writes the low byte of the Context C address to Context B at `0x11`.
4. Writes the second explicit argument to Context A at `0x11`.
5. Reads a 32-bit word from Context A at `0x64`. This captured value is the **context snapshot**.
6. Writes the incoming byte to Context B at `0x09`.
7. Reads a 32-bit address from Context C at `0x04`. This captured address identifies the **linked region**.

The context snapshot is the value read at step 5, after the preceding four stores. Overlap between contexts can therefore affect it.

### 2. Linked-region updates

Using the captured linked-region address, the function then:

1. Writes the low byte of the Context B address to the linked region at `0x09`.
2. Reads a 32-bit word from the linked region at `0x50`. This is the **linked snapshot**.
3. Writes the low byte of the context snapshot to the linked region at `0x11`.
4. Again writes the low byte of the Context B address to the linked region at `0x09`.
5. Writes the full 32-bit context snapshot to Context B at `0x14`.
6. Writes the low byte of the linked-region address to Context B at `0x0D`.
7. Writes the low byte of the linked snapshot to the first byte of the linked region.

The two writes to linked-region offset `0x09` are separate accesses. The intervening read and write must not be discarded from the behavioral account merely because the repeated byte values match.

### 3. Additional address capture and fixed-value writes

Next, in order:

1. Reads a 32-bit value from Context C at `0x74`. This is the **character displacement**.
2. Reads a 32-bit address from Context C at `0x14`. This identifies the **parent region**.
3. Writes the 32-bit address value of the linked region to the linked region at `0x54`.
4. Reads a 32-bit address from the parent region at `0x04`. This identifies the **child region**.
5. Writes the byte value decimal 100, hexadecimal `0x64`, to the child region at `0x10`.
6. Writes the 32-bit value decimal 100 to Context B at `0x54`.
7. Writes the 32-bit value decimal 100 to the child region at `0x40`.
8. Writes the low byte of the context snapshot to Context B at `0x0D`.
9. Writes the low byte of the child-region address to the parent region at `0x09`.
10. Writes the full 32-bit context snapshot to Context B at `0x24`.
11. Writes the low byte of the Context B address to the parent region at `0x11`.

Absent interfering overlap, Context B’s `0x54` field changes from a self-address value to decimal 100. Its `0x0D` byte similarly changes from the low byte of the linked-region address to the low byte of the context snapshot.

Those intermediate stores remain observable if execution faults later or the memory has externally visible write semantics.

### 4. Halfword stores and character-derived address

The function then:

1. Reads G1.
2. Reads a 32-bit value from Context B at `0x74`. This is the **table displacement**.
3. Writes the low halfword of the table displacement to the address formed by adding Context B and the table displacement.
4. Writes the low halfword of the captured G1 value to the address formed by multiplying the child-region address by two.
5. Reads a character-sized value from the address formed by adding Context B and the character displacement, then converts it to a 32-bit unsigned value. This is the **character-derived value**.
6. Writes the low halfword of the table displacement to the address formed by adding the captured G1 value and the table displacement.
7. Repeats the halfword write from step 3.
8. Writes the 32-bit value `0x45` to the address formed by adding `0x45` to the character-derived value.

Multiplication of the child-region address by two constructs an address. It is not represented as an indexed access relative to an independently supplied array base.

The character read uses plain-character interpretation rather than an explicitly unsigned-byte interpretation. Consequently, the 32-bit character-derived value depends on the unresolved signedness of that character type when the stored byte has its top bit set.

### 5. Final writes and indirect transfer

Finally, the function:

1. Reads G2.
2. Reads G3.
3. Reads a 32-bit word from Context B at `0x44`. This is the **final context snapshot**.
4. Writes the byte value `0x44` to the address formed by adding `0x44` to the character-derived value.
5. Writes the captured 32-bit G3 value to the address formed by multiplying the captured G2 value by two.
6. Writes the low halfword of the captured G2 value to the address formed by adding the fourth explicit argument and the captured G2 value.
7. Invokes the unresolved indirect dependency with these arguments, in order:
   - The character-derived value combined with `0x44` by bitwise OR.
   - The captured G2 value.
   - The final context snapshot.

The first indirect argument uses bitwise OR, not addition. The adjacent memory destinations use addition.

The final context snapshot is read before the last three stores. If one of those stores aliases Context B at `0x44`, the third indirect argument remains the previously captured word.

A third store of `0x1234` targets captured G1 plus the same displacement. These are three ordered stores, even if two or all three destinations coincide.

### Addition versus bitwise OR

If the character-derived value is `0x04`, then:

- The 32-bit `0x45` store targets address `0x49`.
- The byte `0x44` store targets address `0x48`.
- The first indirect argument is `0x44`, because `0x04` OR `0x44` is `0x44`.

An implementation substituting addition for the final OR would produce a different argument.

### Character signedness boundary

For a character byte of `0x7F`, both common signed-character and unsigned-character interpretations produce `0x0000007F`.

For `0xFF`:

- An unsigned-character interpretation produces `0x000000FF`.
- A signed 8-bit interpretation, converted to 32-bit unsigned, produces `0xFFFFFFFF`.

The supplied evidence does not select between those interpretations. Resulting address arithmetic must also be interpreted under the applicable execution model.

### Captured argument survives a later overwrite
