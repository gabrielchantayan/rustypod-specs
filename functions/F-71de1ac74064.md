# F-71de1ac74064

## Purpose

F-71de1ac74064 initializes selected fields of a caller-supplied object, chooses a storage-initialization path, and conditionally initializes two embedded components.

The established behavior is a partial, branch-dependent initialization—not a guarantee that the entire object becomes valid. Several paths return after writing only the initial fields. Allocation-like failures are handled differently depending on the selected mode. Every ordinary return supplies the original object address; the return value does not distinguish success, rejection, unsupported mode, or allocation-like failure.

The apparent intent is to initialize an object with dimensions, a format or mode, and either internally obtained or externally supplied storage. Those semantic labels are inferred. The field writes, branch conditions, argument values, and call order below are established by the supplied static evidence.

## Behavior

### 1. Initial writes and unconditional dependency call

Before validating the mode or external values, the function performs this sequence:

1. Reads one 32-bit value from a global location.
2. Writes 1 at destination offset `0x04`.
3. Writes the captured global value at `0x00`.
4. Writes the mode byte at `0x08`.
5. Writes the second extent at `0x14`.
6. Writes the first extent at `0x0C`.
7. Writes the configuration at `0x10`.
8. Writes the storage-option byte at `0x18`.
9. Writes the 32-bit extent product at `0x1C`.
10. Writes byte 0 at `0x20`.
11. Writes byte 0 at `0x3C`.
12. Writes byte 1 at `0x3D`.
13. Calls F-1780a335331b without explicit arguments.

The return from F-1780a335331b is retained as a context-like value for later calls.

The function then reads the mode byte from the destination. Dispatch therefore uses the stored byte as it exists **after** F-1780a335331b returns, not necessarily the original mode argument.

No evidence establishes that this dependency preserves globals, destination contents, or other reachable state. Subsequent field reads must be understood accordingly.

### 2. Modes 0 and 1

These modes share one path.

Acceptance requires:

- The low bit of the stored configuration at `0x10` is zero.
- The low bit of the stored first extent at `0x0C` is zero.
- The low bit of the stored second extent at `0x14` is zero.
- All four external-value arguments are zero.

The field checks are conditional and ordered: configuration first, then first extent only if configuration is even, then second extent only if both preceding values are even. The implementation does not unconditionally read all three fields for this check.

These conditions enforce low-bit parity only. They do not establish positivity, nonzero dimensions, valid configuration ranges, or absence of arithmetic overflow.

On rejection, the function returns immediately without its own writes to `0x24`, `0x28`, `0x2C`, or `0x38`, and without calling the two embedded-component dependencies.

On acceptance, it:

1. Writes byte 1 at `0x3C`.
2. Writes 0 at `0x24`.
3. Enters common finalization.

There is no primary storage request on this path.

### 3. Modes 2 and 3 with no primary external value

If the primary external value is zero, all three additional external values must also be zero. Any nonzero additional value causes an immediate return.

When all four external values are zero:

1. Byte `0x20` is set to 1.
2. The function reads byte `0x3C`.
3. It reads byte `0x18`.
4. It reads the stored product at `0x1C`.
5. It forms a request quantity:
   - Mode 2: product shifted left by one bit.
   - Mode 3: product shifted left by two bits.
6. It calls F-e20da8d344de with, in order:
   - The context-like result from F-1780a335331b.
   - The request quantity.
   - The sampled byte from `0x18`.
   - The sampled byte from `0x3C`.
   - The original configuration argument.
7. It stores the returned 32-bit value at `0x24`.

A zero return from this request causes an immediate return. Common finalization is skipped. Byte `0x20` remains set by this function, and the primary slot has explicitly been written as zero.

A nonzero return proceeds to common finalization. The zero test concerns the dependency’s returned value, not a later reread of `0x24`.

### 4. Mode 4 with no primary external value

The external-value rejection rule is the same as for modes 2 and 3: all three additional external values must be zero when the primary value is zero.

On acceptance:

1. Byte `0x20` is set to 1.
2. F-e20da8d344de is called with the context-like result, the stored product shifted left by one bit, the stored byte at `0x18`, the stored byte at `0x3C`, and the original configuration argument.
3. The return value is stored at `0x24`.
4. Common finalization is entered unconditionally.

Unlike modes 2 and 3, **mode 4 does not reject a zero primary-request result**. This distinction is established behavior, not an error to normalize away.

The evidence establishes the argument values for this call but does not independently establish an ordering among evaluation of its field-valued arguments.

- A nonzero additional value causes an immediate return.
- Otherwise, the primary external value is written at `0x24`, and common finalization follows.

This function does not validate alignment, length, accessibility, or compatibility of the external value. It does not directly access storage through that value.

This path does not itself set byte `0x20` to 1; that byte was initially cleared. A dependency may nevertheless have modified it.

## Side effects

The destination is modified before any branch can reject the request. There is no visible transactional behavior or restoration of its previous contents.

Early returns leave branch-dependent partial state. Fields not written on a selected path retain their prior contents unless a dependency changes them. In particular, an unsupported mode or rejected external-value combination does not cause this function to clear a preexisting primary slot.

The function makes no explicit release call and does not visibly dispose of a preexisting primary value before replacing it. Reinitializing an already populated object therefore has no established resource-safety guarantee.

The meaning of bytes `0x20` and `0x3C` resembles storage-management metadata, but ownership is not proven. Neither setting a byte nor accepting an external value establishes who must eventually release the associated resource.
