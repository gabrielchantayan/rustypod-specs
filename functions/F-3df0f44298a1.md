# F-3df0f44298a1

## Purpose

F-3df0f44298a1 prepares object state using three shared resource entries, conditionally creates an auxiliary object, and selects between two processing paths. Accepted processing records two unsigned 16-bit quantities and calculates their enclosing multiples of 16. Handled failure invokes an indirect target associated with the object.

The operation is not transactional. Object mutations, shared-resource publication, dependency effects, and input-state updates can precede failure. No explicit rollback is present.

“Resource,” “auxiliary object,” “recognized input,” and “extent” are descriptive labels. Their application-level meanings are inferred, not established.

### Return value

Normal return produces a 64-bit bit pattern:

- The lower 32 bits are `0` after accepted processing, or `0xFFFFFFFF` after handled failure.
- The upper 32 bits initially equal the original input-state address.
- On the recognized-input path, a global 32-bit value replaces that upper half at a specific point in the byte-initialization sequence.

The replacement is the value read at that point, not necessarily an immutable constant. Its numeric value is not supplied.

A failure before that read retains the original input-state address in the upper half. A recognized-path failure after it retains the captured global value. The failure target’s return value does not determine either explicit return half.

## Behavior

### Entry and shared-resource acquisition

The function first clears bit 0 of a global 32-bit status word at offset `0x314` within a global region. Other bits are preserved by this read-modify-write operation; atomicity is not established.

It then captures the shared-resource record address, clears object words `0xD0` and `0xD4` in that order, and saves local copies of the input-state address and the third and fourth arguments. The lower return half initially denotes failure.

The shared-resource record has three 32-bit slots. They are inspected in this order:

| Shared-record offset | Construction size argument | Object destination |
|---|---:|---:|
| `0x08` | `0x400` | `0xD8` |
| `0x0C` | `0x20000` | `0xDC` |
| `0x10` | `0x20000` | `0xE0` |

For each slot:

- If its current value is nonzero, construction and the corresponding object-field assignment are skipped.
- If zero, F-8157a180d901 receives `0x10`. Its result is passed to F-9b3ee6b2bfa6 together with the listed size and `3`.
- The result of F-9b3ee6b2bfa6 is stored in the shared slot **before** its 32-bit word at offset `0x04` is read.
- Bit 31 of that word is cleared. The resulting value is written to the corresponding object destination.
- A zero masked value immediately enters handled failure. Later shared slots are not processed.

There is no intervening null check before the read at result offset `0x04`. An invalid returned address is not converted by this body into a defined handled failure.

The captured shared-record address remains the base used for this acquisition sequence. Dependency calls are not assumed to preserve the record’s contents; later slots are inspected when reached.

Existing shared entries do not refresh object resource fields. Consequently, cached shared resources can coexist with zero object fields.

### Captured clear target and object-field validation

After acquisition reaches the end without an immediate masked-value failure, the function **loads a global pointer identifying a four-word clear target**.

This pointer capture occurs **before** validation begins at object offset `0xD8`.

The object fields are then checked with short-circuit reads:

1. Read `0xD8`; if zero, fail without reading the remaining validation fields.
2. If nonzero, read `0xDC`; if zero, fail without reading `0xE0`.
3. If both preceding values are nonzero, read `0xE0`; zero causes failure.

On successful validation:

1. Clear object word `0xF0`.
2. Through the **previously captured pointer**, clear four consecutive 32-bit words at relative offsets `0`, `4`, `8`, and `12`, in that order.
3. Call an unidentified external dependency with `0x40000`, `0`, and `1`.

The external result is not checked.

The capture is not deferred until after the `0xF0` write. If that write aliases the global pointer’s storage, it does not change the already selected clear target. A validation failure occurs after pointer capture but before any of these five clearing writes.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Dependencies must return normally with the stated results; unrelated interference is excluded unless expressly described.

1. **Aligned acceptance.** Captured quantities `32` and `48` produce originals `32` and `48`, extents `32` and `48`, counts `2` and `3`, and lower return half zero.

2. **Boundary rounding.** Quantities `17` and `65535` produce extents `32` and `65536`, counts `2` and `4096`, and unchanged original copies. Quantities both zero produce zero in all six output fields.

3. **Cached resource without object value.** A nonzero first shared slot does not populate object `0xD8`. If that object field remains zero, validation fails. Later missing resources can already have been constructed, and the four-word target pointer has been captured, but neither `0xF0` nor the four-word target is cleared.

4. **Immediate masked failure.** If a newly constructed resource’s inspected word is `0x80000000`, its object-associated value becomes zero and failure occurs immediately. Later slots and the four-word target-pointer capture are not reached.

5. **Captured clear target under aliasing.** Suppose acquisition succeeds, validation passes, and the global pointer storage aliases object `0xF0`. Clearing `0xF0` changes that storage, but the four clearing writes still use the target captured before validation.

6. **Captured auxiliary argument under aliasing.** Suppose auxiliary construction is required and object `0x08` aliases the global-value storage. The global value is read after F-c6bf6c2a3ff7 returns and before the object store. F-9d7922b16667 receives that captured value even though publication changes the aliased storage.

7. **Recognized-path failures.** A nonzero F-4574f685dc0e result causes failure after byte initialization and upper-half replacement, without this function’s input advancement. A zero parser result followed by a nonzero F-2c401d78984a result causes failure after advancement, without explicit reversal.

8. **Alternate-path distinction.** F-4090b43c3bda results `0` and `2` accept processing; result `1` fails. The upper return half remains the original input-state address.
