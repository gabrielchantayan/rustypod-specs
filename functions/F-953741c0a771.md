# F-953741c0a771

## Purpose

F-953741c0a771 performs an operation on an object, beginning with an indirectly dispatched lookup of an associated record. When that lookup succeeds, it changes a record field, notifies the object using values read from two global locations, and obtains a candidate from F-fd8692810e8b.

A zero candidate causes an explicit clear of an object field, a call to F-f2b8332efb8a, and a zero return. A nonzero candidate leads to temporary-data preparation, an explicit candidate-field write, and an unsigned comparison that selects one of two terminal calls. The selected call’s result is returned.

The application-level meanings of the record state, candidate, temporary data, and comparison quantities are not established. In particular, adding 60 does not establish a unit such as seconds, frames, or entries.

## Behavior

### Associated-record lookup

The function obtains dispatch information from the object and invokes the entry at byte offset 0xC0, passing the object.

If the returned 32-bit address-like value is zero, the function returns zero immediately. On this path, it performs no explicit record-state write, notification-global reads, notification call, candidate acquisition, or candidate-field write.

Effects of the lookup dependency itself remain possible.

A nonzero lookup result is used as the associated-record address.

### Record-state transition

The function reads the 32-bit field at associated-record offset 0x14.

If that field is nonzero, the replacement is zero. The visible logic does not read offset 0x1C on this branch.

If the field is zero, the function reads the 32-bit field at offset 0x1C:

- The bit pattern 0xFFFFFFFF, interpreted as signed −1 for the comparison, selects replacement 8.
- Every other 32-bit pattern selects replacement 4.

The selected replacement is written to offset 0x14.

This is not a Boolean toggle. Any nonzero initial state becomes zero, including values other than 4 and 8. An initial zero becomes either 4 or 8.

### Notification and global reads

After the record-state write, the function prepares and invokes the notification through dispatch-table offset 0x58. Its arguments, in argument-position order, are:

1. The object.
2. The value read from global location 0x08109CA8.
3. The value read from global location 0x08109CA4.

These are reads from global storage, not established fixed constants. Their values are not established as snapshots taken before the initial lookup or record update. Effects of the initial lookup, and any aliasing relevant to the record-state write, may affect what the notification receives.

The supplied representation establishes that these reads and notification dispatch-target evaluation occur after the record-state write and before invocation of the notification. It does **not** establish an evaluation order:

- Between the two global reads.
- Between either global read and evaluation of the notification’s dispatch target.

Argument positions are established even though evaluation order is not. The value from 0x08109CA8 occupies the first non-object argument position regardless of which global is read first.

The notification’s return value is not used by the visible logic. After it returns, the function calls F-fd8692810e8b without explicit arguments.

### Zero-candidate path

If F-fd8692810e8b returns zero, the function:

1. Writes zero to the 32-bit field at object offset 0xC4.
2. Calls F-f2b8332efb8a with argument 3.
3. Returns zero.

The return value of F-f2b8332efb8a is not forwarded.

The record-state write, notification-global reads, and notification invocation have already occurred. No explicit rollback is present. The candidate-field clear precedes F-f2b8332efb8a, but does not establish the field’s final value if that dependency modifies it.

The threshold is the first F-b8274406a146 result’s 32-bit bit pattern plus 60, reduced modulo 2³². The unsigned addition wraps rather than saturating or signaling an explicit error.

### Comparison and terminal call

After the candidate-field write, the function calls F-b8274406a146 again. This invocation receives the address of the 12-byte temporary area as its sole explicit argument shown.

The second result is interpreted as an unsigned 32-bit value and compared against the unsigned threshold derived from the first result:

- If the second result is strictly less than the threshold, the function calls F-910df819391b with arguments 1 and the address of the four-byte temporary region preceding the packed word.
- Otherwise, including equality, it obtains object dispatch information and invokes the entry at byte offset 0xE8 with the object and argument 2.

The selected call’s 32-bit result is returned.

The packed word is four bytes after the pointer supplied to F-910df819391b. This adjacency does not establish that the dependency consumes the packed word, treats the storage as a larger structure, or requires any particular contents in the preceding four bytes.

## Side effects

### Direct reads and writes

On a successful associated-record lookup, the visible logic performs a 32-bit record-state write before preparing the notification.

Notification preparation reads global locations 0x08109CA8 and 0x08109CA4. These reads are part of the function’s behavior even though the globals’ values and declarations are unavailable. The function contains no explicit write directly targeting either global location. Aliased writes and dependency effects are not excluded.

After candidate acquisition, the function explicitly writes object offset 0xC4:

- Zero on the zero-candidate path, before F-f2b8332efb8a.
- The acquired nonzero candidate after temporary preparation, before the second F-b8274406a146 call.

The function also stores the packed temporary word locally.

These are ordered write events, not unconditional guarantees about memory contents at return. Later dependencies may modify the same storage.

### Dispatch and external effects

Later object-dispatched calls obtain dispatch information again rather than relying exclusively on the initial lookup’s target. Changes to the object or its dispatch information may therefore affect later targets.

The notification’s global arguments are likewise obtained for that notification, after the state update. No global-preservation assumption is justified for the preceding lookup dependency.

All dependencies may have effects beyond those evident from their arguments. No purity, synchronization, reentrancy, or global-preservation guarantee is established.

### Ownership and lifetime

No explicit allocation, release, reference-count adjustment, or ownership transfer is visible.

Writing the candidate to offset 0xC4 retains its 32-bit value at that point in execution. It does not establish ownership of any resource represented by that value.

Temporary addresses refer to invocation-local storage. Whether a dependency copies the data, retains an address, or releases an associated resource is unknown. No safe post-return use of those local addresses can be inferred.

## Acceptance examples

These examples are conditional specification cases, not observed executions. They assume valid storage, callable targets, normal dependency returns, and the stated dependency outputs.

### Missing associated record

If the initial lookup returns zero:

- The function returns zero.
- No notification-global read or later dependency call is performed by the visible continuation.
- No explicit record-state or candidate-field write occurs.

Effects inside the lookup remain possible.

### State selection

| Initial state at 0x14 | Field at 0x1C | Explicit replacement |
|---|---|---|
| 0 | 0xFFFFFFFF | 8 |
| 0 | Any other 32-bit pattern | 4 |
| 4 | Not read on this branch | 0 |
| 8 | Not read on this branch | 0 |
| Any other nonzero pattern | Not read on this branch | 0 |

The replacement write precedes notification preparation.

### Notification argument sources and ordering

Suppose the notification’s read from 0x08109CA8 produces value A and its read from 0x08109CA4 produces value B. The notification receives the object, A, and B in that argument order.

If the initial lookup changes either global before returning, that earlier value cannot be substituted for the value subsequently read for notification. Likewise, a record-state write that aliases relevant global storage cannot be ignored.

Either relative order of the two global reads is compatible with the supplied representation. Either read may also occur before or after notification dispatch-target evaluation, provided all occur after the record-state write and before notification invocation. A check requiring one such evaluation order would impose an unsupported restriction.

### Zero candidate

If the record exists and F-fd8692810e8b returns zero:

- State processing and notification occur first.
- Object offset 0xC4 is explicitly cleared.
- F-f2b8332efb8a is called with 3.
- The function returns zero regardless of that dependency’s ordinary return value.

The candidate field remains zero at return only if subsequent effects do not change it.

### Strict comparison boundary

If the first F-b8274406a146 result is 100, the threshold is 160:

- A second result of 159 selects F-910df819391b.
- A second result of 160 selects dispatch slot 0xE8 with argument 2.
- A second result of 161 also selects slot 0xE8.

The candidate has already been explicitly stored in all three cases.

### Unsigned wraparound

If the first result has bit pattern 0xFFFFFFF0, adding 60 modulo 2³² produces threshold 44:

- A second unsigned result of 43 selects F-910df819391b.
- A result of 44 selects slot 0xE8.
- A result of 0xFFFFFFFF also selects slot 0xE8.

If the threshold wraps to zero, no unsigned 32-bit operand satisfies the strict-less-than condition.

### Packed temporary bytes

If the three bytes read after the second F-dee541b2a059 call are 0x12, 0x34, and 0x56, the packed word is 0x00123456.

This establishes byte significance only, not the word’s application meaning or whether F-910df819391b reads it.
