# F-95715cbe2fd3

## Purpose

F-95715cbe2fd3 searches a linked collection for the first entry matching a selector and a dependency-defined comparison. It then either clears selected fields in that entry or assigns a supplied 32-bit value to an existing or newly obtained entry.

A zero assignment value selects the clearing operation. Any nonzero assignment value selects the assignment operation; it is not merely a Boolean enable flag.

The function returns a 32-bit status:

- **1:** the selected path completed, including a clearing request for which no matching entry exists.
- **0:** an assignment requires increasing the collection count, but the unsigned capacity check rejects that increase.

These return meanings assume that dependency calls return and all required memory accesses complete. The visible function does not convert invalid memory accesses or dependency failures into status values.

Terms such as “collection,” “entry,” “count,” and “capacity” describe the apparent roles of fields. Allocation, ownership, and the broader meaning of entry state are not established.

## Interface

The function accepts four inputs:

| Input | Representation | Visible use |
|---|---|---|
| Collection address | Address represented by a 32-bit value in the supplied representation | Locates the list head, count, and capacity fields |
| Selector | Unsigned 32-bit value | Passed unchanged to F-ab6062dd4d3b and, when needed, F-ca2677f280e0; compared against an entry’s unsigned byte field |
| Comparison argument | Opaque 32-bit value | Passed unchanged to the indirect comparison dependency and, when needed, F-ca2677f280e0 |
| Assignment value | 32-bit value | Zero selects clearing; any other bit pattern is stored in the selected entry |

There is no explicit output parameter. Results are conveyed through the return value, direct memory writes, and dependency effects.

### Preconditions

The collection address must support the reads and writes required by the selected path. Every traversed entry must support its tag and next-link reads; a matched entry must also support the applicable state and assignment accesses.

If an entry passes the tag test, the object returned by F-ab6062dd4d3b must support the indirect call described below. The function does not visibly validate that object.

For normal termination, traversal must eventually encounter a matching entry or a zero link, and all invoked dependencies must return. A cycle without a match can cause unbounded traversal.

## Behavior

### 1. Resolve comparison support

The function first calls **F-ab6062dd4d3b**, passing the complete unsigned 32-bit selector.

This call occurs before the list head is read, even when the collection will prove empty or the operation will ultimately be a no-op.

The returned value is treated as an object address. When comparison is needed, the function reads a 32-bit table address from the beginning of that object, then obtains an indirect call target from table offset `0x04`.

The indirect comparison receives:

1. The returned object address.
2. The current entry address plus `0x08`.
3. The opaque comparison argument.

Its result is interpreted only as zero or nonzero. Nonzero means that the current entry matches.

No stable opaque ID is supplied for this indirect target. Its identity and complete behavior remain documented_only.

### 2. Search for the first match

After F-ab6062dd4d3b returns, the function reads the collection’s head field at `0x10`.

For each nonzero current entry:

1. Read its unsigned 8-bit selector tag at `0xC8`.
2. Compare that tag, numerically, with the complete unsigned 32-bit selector.
3. If the values differ, do not invoke the indirect comparison for that entry.
4. If they are equal, invoke the indirect comparison. A nonzero result selects the current entry.
5. If the tag differs or the comparison returns zero, read the current entry’s next link at `0x04` and continue.

The first qualifying entry is selected. Later entries are not inspected by the visible traversal.

The selector comparison does **not** truncate the input selector to eight bits. Consequently, selectors greater than 255 cannot match an entry’s tag through this search. Such selectors are nevertheless passed unchanged to F-ab6062dd4d3b and may later be passed to F-ca2677f280e0.

Dependency mutations matter to ordering:

- Changes made by F-ab6062dd4d3b before it returns can affect the subsequently read list head.
- If an indirect comparison returns zero, the next link is read afterward; dependency changes to that link can affect traversal.
- If an indirect comparison returns nonzero, the current entry is accepted without rereading its tag.

The visible function does not protect against dependencies invalidating memory that it subsequently uses.

### 3. Clear when the assignment value is zero

If the assignment value is zero and no entry matched, the function returns **1** without performing its own field writes.

If an entry matched, the function performs these direct writes in order:

1. Read the collection count at `0x20`, subtract one, and store the 32-bit result back there.
2. Store an 8-bit zero into the entry’s tag at `0xC8`.
3. Store a 32-bit zero into the entry’s assignment field at `0xBC`.
4. Store a 32-bit zero into the entry’s state field at `0xC4`.
5. Return **1**.

There is no test of the matched entry’s state before decrementing the count. In particular, the decrement is not conditional on state bit `2`.

There is also no nonzero-count check. The visible 32-bit update produces `0xFFFFFFFF` when decrementing a zero bit pattern; no underflow error is returned.

Clearing does not directly unlink the entry, alter the list head, change its next link, or release memory. Setting the tag to zero also does not establish that the entry becomes unsearchable: selector zero can pass the tag comparison.

### 4. Assign when no entry matched

For a nonzero assignment value with no matching entry, the function reads the collection capacity and count and compares them as unsigned 32-bit values.

If capacity is less than or equal to count, it returns **0**. It does not directly increment the count or call F-ca2677f280e0 on this path.

Otherwise:

1. Increment the collection count by one and store the 32-bit result.
2. Call **F-ca2677f280e0** with the collection address, full selector, opaque comparison argument, and a fourth argument of zero.
3. Treat its return value as the selected entry address.
4. Store the supplied nonzero assignment value at entry offset `0xBC`.
5. Store the exact 32-bit value `2` at entry offset `0xC4`.
6. Return **1**.

The count increment precedes F-ca2677f280e0. The function contains no visible rollback if that dependency fails, does not return, or returns an unusable address.

The returned address is not checked for zero before the two entry writes.

The caller does not directly initialize the returned entry’s tag or linkage. Any such initialization is a dependency behavior, not an established effect of this function’s own writes.

### 5. Assign when an entry matched

For a nonzero assignment value with a matching entry, the function reads the entry state at `0xC4`.

If state bit `2` is already set:

- Skip the capacity check.
- Do not directly change the count.
- Store the assignment value at `0xBC`.
- Replace the complete state field with `2`.
- Return **1**.

If state bit `2` is clear:

- Compare capacity and count as unsigned 32-bit values.
- Return **0** if capacity is less than or equal to count.
- Otherwise increment the count, store the assignment value, replace the complete state field with `2`, and return **1**.

The final state write is a replacement, not a bitwise addition. Any other bits previously present in the state field are cleared.

F-ca2677f280e0 is not called when traversal found a matching entry.

### Arithmetic and access ordering

Capacity decisions use unsigned ordering. For example, a count bit pattern of `0xFFFFFFFF` is greater than a capacity of `0x7FFFFFFF`.

A count increment is performed only after observing count less than capacity. For those observed unsigned values, incrementing count cannot wrap past `0xFFFFFFFF`.

The clear path has no corresponding bound check.

The supplied representation establishes the ordering of calls and stores described above. It does not establish a portable relative order for the capacity and count operand reads within their comparison.

No atomicity, synchronization, or protection from concurrent mutation is visible.

## Side effects

The function’s direct writes are limited to:

- The collection count at `0x20`.
- A selected entry’s tag at `0xC8`, on clearing only.
- A selected entry’s assignment field at `0xBC`.
- A selected entry’s state field at `0xC4`.

It does not directly write the collection’s head, capacity, or an entry’s next link.

These limits do not constrain dependency side effects. F-ab6062dd4d3b, the indirect comparison, and F-ca2677f280e0 may have effects that are not described by the supplied evidence. In particular, a return value of **0**, or a successful no-match clear, does not prove that the call was globally side-effect-free.

No direct allocation or deallocation operation is visible. Ownership transfer, reference counting, and lifetime guarantees are not established. The function neither visibly releases the comparison-support object nor releases an entry when clearing it.

## Acceptance examples

These examples are conditional on valid memory, terminating dependencies, and no dependency mutations except where explicitly stated. They specify behavior derived from static evidence; they are not runtime test results.

### Empty collection, clear request

Given a zero head and assignment value zero:

- F-ab6062dd4d3b is still called before the head is read.
- No indirect comparison or F-ca2677f280e0 call occurs.
- The function performs no direct field writes.
- The result is **1**.

### Existing match, clear request

Given a matching entry, count 5, and assignment value zero:

- Count becomes 4.
- The entry tag, assignment field, and state field become zero, in that write order after the count update.
- The entry is not directly unlinked.
- The result is **1**, regardless of its previous state bits.

### Existing match, already counted state

Given a matching entry with state `0x12`, count equal to capacity, and assignment value `0xFFFFFFFF`:

- Capacity does not block the operation because state bit `2` is set.
- Count is not directly changed.
- The assignment field becomes `0xFFFFFFFF`.
- State becomes exactly `2`, clearing bit `0x10`.
- The result is **1**.

### Existing match requiring a count increase

Given a matching entry with state `0x10`, count 3, capacity 4, and a nonzero assignment:

- Count becomes 4.
- F-ca2677f280e0 is not called.
- The assignment is stored and state becomes `2`.
- The result is **1**.

With count 4 and capacity 4 instead, the result is **0**, with no direct count, assignment, or state write.

### Missing match with available capacity

Given no match, count 2, capacity 3, and a nonzero assignment:

- Count is stored as 3 before F-ca2677f280e0 is called.
- That dependency receives the original selector and comparison argument, plus a final zero argument.
- Its returned entry receives the assignment and then state `2`.
- The result is **1** if those accesses complete.

### Wide selector

Given selector `0x101` and an entry tag of `0x01`:

- That entry fails the tag test.
- Its indirect comparison is not called.
- The input selector is not narrowed to `0x01`.
- If no match exists and assignment is permitted, F-ca2677f280e0 receives `0x101`.

### First matching entry wins

Given two entries that would both pass the tag and comparison tests:

- The first is selected.
- The second is not compared or directly modified by this function.
- Dependency side effects remain outside that guarantee.

### Clearing with count zero

Given a matching entry, count zero, and assignment value zero:

- The function does not reject the operation for underflow.
- The 32-bit count becomes `0xFFFFFFFF`.
- The selected entry’s three cleared fields become zero.
- The result is **1** if execution completes.
