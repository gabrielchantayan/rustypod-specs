# F-983b1880ceb6

## Purpose

F-983b1880ceb6 obtains a node, copies a supplied 32-bit value into it under an unusual address guard, increments a container count, attaches the node at a caller-selected position, performs color-based repair, colors the current root 1, and writes the obtained node’s address to an output slot.

**Established static evidence:** attachment uses a supplied parent, a placement-control argument, and, conditionally, a comparison dependency. Repair follows parent and grandparent links, changes color bytes, and invokes two structural dependencies.

**Inferred intent:** the structure is a red-black tree with a header containing root and extremum links. Color 0 behaves as red and color 1 as black. The structural dependencies appear to implement opposite-direction rotations. These interpretations do not establish their implementations or guarantees.

The function does not search for a position, check for duplicate values, or reject an occupied child link. It relies on the caller and dependencies for a suitable insertion position and node initialization.

## Interface

The visible interface has five inputs and no explicit return value.

| Input | Representation | Role |
|---|---|---|
| Output slot | Address of writable 4-byte storage | Receives the originally obtained node address after repair and final root coloring. |
| Container | 32-bit address carried in an integer-width argument | Provides the header reference, count, and comparison-state address. |
| Placement control | 32-bit integer | Any nonzero value forces attachment through the parent’s offset-8 link. |
| Parent | 32-bit address carried in an integer-width argument | Identifies the initial attachment parent, possibly the header. |
| Value source | Address of readable 4-byte storage | Supplies the copied value and, when comparison occurs, an operand address. |

Visible address fields and value transfers are 4 bytes wide. Color reads and writes are 1 byte wide. This establishes a 32-bit address and word representation, not a portable 64-bit interface. Byte order and required alignment are not independently established.

### Preconditions and ownership

Normal completion requires valid storage for every access reached on the selected path:

- The container must expose the accessed header and count fields.
- The parent must permit the selected child-link write.
- The obtained node must permit its parent-link write and any reached value or color accesses.
- Traversed ancestors must provide readable links and writable colors where used.
- The final header root must identify writable color storage.
- The output slot must permit a 4-byte write.
- The value source must permit a 4-byte read when the copy guard succeeds. Comparison can impose additional requirements.

Null opposite-side children are explicitly handled during repair. There is no general protection against null parents, grandparents, headers, or roots.

No direct release operation appears. Linking a node and exposing its address do not establish who owns its allocation, who must eventually dispose of it, or whether any dependency allocates or releases memory.

## Behavior

### Acquisition, value transfer, and count

The first dependency call is F-2c6eb1a3a169 with the container. Its returned address is retained as the node identity ultimately written to the output slot. The repair cursor may move, but this saved identity does not change.

The function next tests whether the obtained node address plus 16 is nonzero. If so, it reads one 4-byte value from the value source and writes it at node offset 16.

This guard is not a null-node check. A zero node address does not itself make the derived address zero. A zero acquisition result therefore does not select a supported allocation-failure path. Conversely, a derived address that evaluates to zero suppresses only the value transfer; subsequent insertion work still proceeds. Exact behavior at address-arithmetic boundaries is documented_only.

After the guarded copy, the function reads the 4-byte count, adds one, and writes it back. This precedes comparison and all initial attachment writes. No capacity check, overflow check, failure result, or compensating decrement is visible. The count is represented as a 32-bit integer, but defined wraparound at signed overflow cannot be promised from the supplied representation.

### Attachment selection

The function reads the container’s header address. It selects the offset-8 attachment path without comparison when either:

- The supplied parent equals that header; or
- Placement control is nonzero.

Otherwise, F-2c6a49ccf2ab receives:

1. The container address plus 25.
2. The original value-source address.
3. The supplied parent address plus 16.

A nonzero result selects offset 8; zero selects offset 12. Negative and positive nonzero results are not distinguished.

The comparator receives addresses rather than copied operands. Its value-source argument is not the newly stored node-value address. No second value copy follows comparison.

The header-parent decision is not restarted after comparison. Later header reads can nevertheless observe a changed header if the dependency changes container state.

### Offset-8 attachment

The first link write stores the new node address at the supplied parent’s offset 8. The header address is then reread.

If this reread header differs from the supplied parent, the function reads that header’s offset-8 field. It replaces the field with the new node address only when the existing value equals the supplied parent.

If the reread header equals the supplied parent:

1. Its offset-4 root field receives the new node address.
2. The container’s header address is reread.
3. That header’s offset-12 field receives the new node address unconditionally.

With a stable header equal to the parent, header offsets 8, 4, and 12 therefore all become the new node address.

### Offset-12 attachment

The first link write stores the new node address at the supplied parent’s offset 12. The function then rereads the header address and reads that header’s offset-12 field.

That header field is replaced only if its existing value equals the supplied parent.

Neither attachment path checks that the selected parent link was empty. An existing subtree reference can be overwritten.

### Parent assignment and repair entry

After attachment and header maintenance, the new node’s offset-4 parent link is written with the supplied parent. The repair cursor initially identifies the new node.

At each loop entry, the function rereads the header and its root link. If the root equals the cursor, repair stops without reading the cursor’s parent color.

Otherwise, the cursor’s parent address is read, followed by that parent’s color byte. Any nonzero color stops repair, including values other than 1.

For a zero-color parent, the function reads its parent as the grandparent, then the grandparent’s offset-8 child. Equality between that child and the current parent selects the first structural case. Inequality selects the second; the function does not additionally verify that the parent is the grandparent’s offset-12 child.

### Parent equals the grandparent’s offset-8 child

The grandparent’s offset-12 child becomes the opposite-side node.

If it is nonnull and has color 0, the function:

1. Colors the saved parent 1.
2. Colors the saved opposite-side node 1.
3. Follows the cursor’s current parent and grandparent links and colors that grandparent 0.
4. Follows the cursor’s parent and grandparent links again and moves the cursor to the resulting grandparent.

The loop then repeats. No structural dependency is called in this branch.

If the opposite-side node is null or has nonzero color, the function checks whether the cursor equals the saved parent’s offset-12 child.

- If equal, it calls F-bf05f6f01092 with the container and saved parent, then sets the cursor to that saved parent address.
- If unequal, both that call and the cursor assignment are skipped.

Using the resulting cursor, it then colors the reached parent 1, colors the reached grandparent 0, and calls F-030a3110641a with the container and a freshly reached grandparent address. The loop repeats; the dependency call is not followed by an unconditional exit.

### Parent does not equal the grandparent’s offset-8 child

The grandparent’s offset-8 child is the opposite-side node.

If it is nonnull and has color 0, the same ordered recoloring and upward cursor movement described above occurs.

Otherwise, the function checks whether the cursor equals the saved parent’s offset-8 child.

- **If equal:** F-030a3110641a is called at the saved parent with the additional visible arguments described under Dependencies. Immediately after that call returns, the cursor becomes the saved parent address.
- **If unequal:** the parent-level call and cursor assignment are both skipped. The cursor remains unchanged.

Only after this conditional step does the function:

1. Follow the resulting cursor’s parent link and color that parent 1.
2. Follow that cursor’s parent and grandparent links and color that grandparent 0.
3. Follow those ancestor links again and call F-bf05f6f01092 with the container and the reached grandparent.

Thus, in the non-triangle case, recoloring and the final dependency argument are derived from the **unchanged cursor**, not from a cursor unconditionally moved to the saved parent. This distinction determines both the nodes recolored and the structural call’s target.

### Completion

When repair stops, the function rereads the header, reads its root link, and writes color 1 to that root. It then writes the originally obtained node address to the output slot.

The output write is the last explicit operation. No explicit success value, error value, or rollback path is visible. Normal termination is not established for malformed structures or arbitrary dependency behavior.

## Side effects

Direct writes can affect:

- The obtained node’s 4-byte value.
- The container’s 4-byte count.
- The supplied parent’s selected child link.
- Header root and extremum links.
- The obtained node’s parent link.
- Ancestor, opposite-side, and root color bytes.
- The caller’s 4-byte output slot.

There are no visible direct writes to the comparison-state object or padding.

Read order matters because the function does not retain one immutable structural snapshot. Header references are reread during attachment, loop tests, and completion. Ancestor links are reread for successive recolorings, upward movement, and dependency arguments. After a structural dependency returns, the function uses links then reachable from the selected cursor; it does not assume they still match pre-call links.

Dependency preservation guarantees are unknown. Calls may affect container state, input storage, globals, or memory ownership. The contract does not treat such effects as absent.

Input overlap is not checked. For example:

- If the output slot aliases a tree field, the final output write can overwrite that field.
- If the value source aliases the count, the initial copy precedes the increment, while comparison occurs afterward.
- If color bytes overlap link storage in an invalid layout, recoloring can affect subsequent address reads.

These observations do not establish aliasing as supported use.

A fault or nonlocal exit can leave partial changes. In particular, comparison occurs after the guarded value copy and count increment, but before initial attachment. No cleanup or restoration is visible.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. They assume valid storage, ordinary nonoverlapping layouts, normally returning dependencies, and no unmentioned interference.

1. **Header-parent insertion.** With a stable header supplied as parent, comparison is skipped. Header offsets 8, 4, and 12 become the obtained node address. The node’s parent becomes the header. The root comparison ends repair, final coloring sets the node to 1, and output receives its address.

2. **Forced offset-8 attachment.** With a non-header parent and nonzero placement control, offset 8 is selected without comparison. The header’s offset-8 link changes only if it previously equals that parent.

3. **Comparison-selected offset-12 attachment.** With zero placement control, a non-header parent, and comparison result zero, the parent’s offset-12 link receives the node. The header’s offset-12 link changes only if its prior value equals that parent.

4. **Noncanonical nonzero color.** If the cursor is not root and its parent color is 7, repair stops at that test. Final root coloring and the output write still occur.

5. **Zero-color opposite-side node.** For a zero-color parent and nonnull zero-color opposite-side node, both saved nodes become color 1. The cursor-reached grandparent becomes 0, the cursor moves upward through reread links, and that iteration makes no structural call.

6. **Second-case triangle.** Suppose the parent differs from the grandparent’s offset-8 child, the opposite-side node is null or nonzero-colored, and the cursor equals the parent’s offset-8 child. The parent-level F-030a3110641a call occurs. Only after it returns does the cursor become the saved parent; subsequent ancestor targets derive from that cursor and the resulting links.

7. **Second-case non-triangle.** Under the same opposite-side conditions, suppose the cursor does not equal the parent’s offset-8 child. No parent-level F-030a3110641a call occurs and the cursor does not move. With stable links, the original parent is colored 1, the original grandparent is colored 0, and F-bf05f6f01092 receives that grandparent—not an ancestor obtained by first moving the cursor to the parent.

8. **Null opposite-side child.** A null opposite-side child selects structural repair without a color read through that null address. Valid ancestor storage remains required.

9. **Comparison exits nonlocally.** The guarded value transfer and count increment have already occurred. This function has not yet performed initial attachment or final output.

10. **Zero acquisition result.** Zero does not produce an ordinary failure return. The derived-address guard does not reject it, and subsequent accesses can fail.
