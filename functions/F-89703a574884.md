# F-89703a574884

## Purpose

F-89703a574884 advances allocation-related state in a caller-supplied descriptor. It has two distinct paths:

- If a linked-entry head is nonzero, replace that head with the first word stored at the referenced entry, then return.
- Otherwise, advance a sequential cursor by 16 bytes, creating and linking a new backing block first when the cursor equals its endpoint.

**Inferred intent:** the descriptor appears to support fixed-size, 16-byte entries, with a reusable-entry chain and a chain of backing blocks. This interpretation explains the structure but is not necessary to establish the observable behavior.

The function does not return an entry address. Its visible result is mutation of the descriptor and, on the block-creation path, initialization of a newly obtained block header. Whether surrounding code treats the operation as reserving, consuming, or committing an entry is unknown.

## Interface

### Inputs

The function accepts:

1. A pointer to a mutable descriptor containing at least four consecutive 32-bit words.
2. A 32-bit integer mode value.

Only the distinction between zero and nonzero matters for the mode. Positive and negative nonzero values select the same behavior.

The supplied representation uses 32-bit words for integers and stored addresses. The layout below describes that representation; it is not a portable layout for an arbitrary host pointer width.

### Descriptor layout

| Byte offset | Width | Meaning in this contract |
|---|---:|---|
| 0 | 32 bits | Backing-block head: address of the most recently linked block header, or zero |
| 4 | 32 bits | Linked-entry head: address of an entry whose first word contains a successor address, or zero |
| 8 | 32 bits | Sequential cursor |
| 12 | 32 bits | Sequential endpoint |

The backing-block head and linked-entry head are independent fields. A nonzero linked-entry head takes precedence over every cursor, endpoint, block-capacity, and mode consideration.

### Block-header layout

When a new block is created, the function initializes a 12-byte header:

| Byte offset | Width | Value written |
|---|---:|---|
| 0 | 32 bits | Backing-block head read from the descriptor during publication |
| 4 | 32 bits | Selected entry capacity |
| 8 | 32 bits | Address returned by the payload acquisition |

For an existing block, only the capacity word at offset 4 is used to calculate ordinary-mode growth.

### Output

There is no explicit return value.

Normal return means that either:

- the linked-entry head has been replaced by its successor; or
- the sequential cursor has been advanced by 16 bytes, potentially after a new block was acquired and published.

There is no explicit success indicator, error code, or failure callback.

### Memory preconditions

For defined, ordinary execution:

- The descriptor must designate readable and writable storage for its four words.
- A nonzero linked-entry head must designate a readable 32-bit successor word.
- On ordinary-mode growth, a nonzero backing-block head must designate a readable capacity word at header offset 4.
- Storage returned for a new header must permit the subsequent three 32-bit header writes.
- Returned addresses and descriptor state must support the arithmetic and accesses described below.

The function does not validate these conditions. Alignment requirements, address validity, allocation failure behavior, and the execution environment’s handling of invalid accesses are not established by the supplied evidence.

## Behavior

### 1. Linked-entry path

The function first examines the descriptor’s linked-entry head.

If that value is nonzero:

1. Read the first 32-bit word at the referenced entry.
2. Store that word into the descriptor’s linked-entry-head field.
3. Return immediately.

On this path, the function does not call F-871e64ddc6de, compare the cursor with the endpoint, inspect an existing block’s capacity, or explicitly change the cursor.

The removed entry is not cleared, returned to the caller, or explicitly released. Its successor may itself be zero or any other 32-bit value; no successor validation occurs.

These field-level effects assume ordinary, non-overlapping storage. If the referenced successor word aliases part of the descriptor, its value is read before the head replacement is written. The function contains no protection against such aliasing.

### 2. Existing sequential space

When the linked-entry head is zero, the function compares the cursor and endpoint for exact equality.

If they differ, it skips block creation and adds 16 to the cursor.

There is no ordering comparison. Consequently:

- A cursor below the endpoint advances by 16.
- A cursor above the endpoint also advances by 16.
- A cursor less than 16 bytes short of the endpoint still advances by 16.
- The function does not establish that an entire entry fits before advancing.

On this path, the mode and backing-block head do not affect the operation.

### 3. Capacity selection when cursor equals endpoint

If the linked-entry head is zero and the cursor equals the endpoint, the function selects a capacity before making either dependency call.

#### Nonzero mode

The selected capacity is exactly one entry.

The existing backing-block head and its capacity are not consulted for this selection.

#### Zero mode with no existing backing block

If the backing-block head is zero, the selected capacity is 32 entries.

#### Zero mode with an existing backing block

Read the existing head block’s 32-bit unsigned capacity, called \(c\) here for mathematical exposition.

Compute two unsigned 32-bit candidates:

\[
a = (c + 32) \bmod 2^{32}
\]

\[
b =
\left(
c + \left\lfloor c/2 \right\rfloor
  + \left\lfloor c/8 \right\rfloor
\right) \bmod 2^{32}
\]

The selected capacity is the larger candidate under an unsigned comparison:

\[
n = \max_{\mathrm{unsigned}}(a,b)
\]

Equality selects a numerically identical result, so there is no distinct externally visible tie behavior.

The shifts supplying the fractional terms operate on the unsigned capacity. The rounding is performed separately for the halves and eighths; this is not, in general, interchangeable with one rounded multiplication by a combined growth factor.

**Inferred intent:** absent overflow, this policy grows by at least 32 entries and otherwise approximately 62.5%. That interpretation must not replace the actual wrapped arithmetic for large capacities.

### 4. Acquisition order and requested sizes

With the selected capacity fixed, the function calls F-871e64ddc6de twice, in this order:

1. First argument: 12. Second argument: zero.
2. First argument: the selected capacity shifted left by four bits in unsigned 32-bit arithmetic. Second argument: zero.

The first result is used as the new header address. The second result is used as the payload address.

The requested payload size is therefore:

\[
s = (16n) \bmod 2^{32}
\]

There is no overflow check. A large capacity can produce a small or zero payload-size request even though the capacity recorded in the header remains large.

Both calls occur before the function’s explicit initialization of the new header and before its explicit publication of the new backing-block head. In particular, the header returned by the first call has not yet been initialized by this function when the second call occurs.

No conclusion is established about what either call does to shared state, existing memory, or the other allocation. The post-call operations below must therefore not be described as using an immutable snapshot of all descriptor fields.

### 5. Header initialization and publication

After the second dependency call returns, the function performs these explicit operations in order:

1. Write the payload result into the new header’s word at offset 8.
2. Read the descriptor’s backing-block head and write it into the new header’s word at offset 0.
3. Write the selected capacity into the new header’s word at offset 4.
4. Write the new header address into the descriptor’s backing-block-head field.
5. Read the payload-address word from the new header.
6. Store that address into the descriptor’s cursor field.
7. Store that address plus the wrapped 32-bit payload-size expression into the descriptor’s endpoint field.
8. Advance the descriptor’s cursor by 16 bytes.

The old-head value stored in the new header is read after both dependency calls. It is not necessarily the value previously inspected during capacity selection.

Similarly, the payload address used to initialize the cursor is read back from the header rather than treated solely as a retained dependency result. Under ordinary disjoint-storage assumptions the values coincide. If returned storage aliases the descriptor or other relevant storage, the ordered writes and reads can interact; the evidence does not establish a general non-aliasing guarantee.

### 6. State on normal completion

Assuming successful dependency returns, disjoint storage, no intervening mutation, and nonproblematic address arithmetic, the block-creation path leaves:

- the new header linked ahead of the previous backing-block head;
- the selected capacity recorded in that header;
- the payload address recorded in that header;
- the cursor at payload start plus 16 bytes;
- the endpoint at payload start plus the requested payload extent;
- the linked-entry head unchanged at zero.

For a one-entry block without arithmetic wrap, cursor and endpoint are equal immediately after completion. The next invocation with no linked entry available therefore takes the block-creation path again.

The final cursor increment uses an integer-typed value in the supplied representation. Its behavior at signed-overflow boundaries is not established as a portable language-level guarantee. A faithful low-level implementation must resolve the target arithmetic semantics rather than silently impose a new checked-arithmetic policy.

## Side effects

- initialize a 12-byte block header;
- replace the backing-block head;

It does not explicitly initialize payload contents, unlink an old backing block, release storage, clear a consumed linked entry, or write an application result into a 16-byte entry.

## Acceptance examples

These are conditional contract examples, not runtime observations. Unless stated otherwise, they assume valid disjoint storage, normally returning dependencies, no concurrent or dependency-induced descriptor mutation, and representable address arithmetic.

1. **Linked entry overrides exhaustion.**  
   Given a nonzero linked-entry head whose first word is zero, and equal cursor and endpoint, the function sets the linked-entry head to zero and returns. It makes no dependency calls and does not advance the cursor.

2. **Nonzero successor is retained without traversal.**  
   Given a linked-entry head whose successor word contains another entry address, the function installs that address as the new head. It does not inspect the new head’s successor during this invocation.

3. **Unequal cursor and endpoint avoid acquisition.**  
   Given a zero linked-entry head, cursor `0x1000`, and endpoint `0x1100`, the cursor becomes `0x1010`. No dependency call occurs, regardless of mode.

4. **An already excessive cursor is not rejected.**  
   Given cursor `0x1200`, endpoint `0x1100`, and zero linked-entry head, the cursor becomes `0x1210`. The function does not repair or reject the ordering.

5. **Initial ordinary-mode block.**  
   Given zero mode, no backing block, and equal cursor and endpoint, the function requests 12 bytes and then 512 bytes. If the returned addresses are header \(H\) and payload \(P\), the header records previous head zero, capacity 32, and payload \(P\). The descriptor records head \(H\), cursor \(P+16\), and endpoint \(P+512\).

6. **Ordinary additive growth.**  
   Given an existing capacity of 32, zero mode, and an exhausted sequential range, the candidates are 64 and 52. Capacity 64 is selected, and the payload request is 1,024 bytes.

7. **Ordinary proportional growth.**  
   Given existing capacity 64 under the same conditions, the candidates are 96 and 104. Capacity 104 is selected, and the payload request is 1,664 bytes.

8. **Nonzero mode disregards existing capacity.**  
   Given any nonzero mode and an exhausted sequential range with no linked entry, the function requests a one-entry block: 12 bytes followed by 16 bytes. With ordinary arithmetic, final cursor equals final endpoint.

9. **Payload-size overflow is not rejected.**  
   Given zero mode and existing unsigned capacity `0x80000000`, the growth candidates are `0x80000020` and `0xD0000000`. The selected capacity is `0xD0000000`, while the shifted payload request is zero. Subsequent behavior depends on the dependency’s zero-size result and address semantics; no oversized-capacity error is reported by this function.
