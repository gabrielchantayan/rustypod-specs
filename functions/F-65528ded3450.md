# F-65528ded3450

## Purpose

F-65528ded3450 coordinates a change from a currently reported associated object to a requested associated object.

The established behavior is an ordered sequence: query the current association, compare object addresses, optionally notify the old object, store the requested address through an owner-held storage reference, and optionally notify the requested object. If the queried address already equals the requested address, the function returns without performing the store or either notification.

“Association,” “owner,” and “notification” are descriptive terms, not established domain semantics. The visible operations suggest a relationship transfer, but do not establish ownership transfer, reference counting, destruction, or consistency enforcement.

## Interface

### Inputs

The function accepts two pointer-valued arguments:

- **Owner:** an address used for an initial indirect dispatch and, on the change path, to locate writable association storage.
- **Requested object:** the address to install, or a null pointer to request removal without a replacement notification.

The owner is also passed as an argument to both possible notification calls.

No explicit return value is exposed. The meaningful outputs are memory effects, dependency effects, and whether control returns normally.

### Visible representation

The supplied representation supports the following layout contract:

| Object or storage | Location | Use |
|---|---:|---|
| Owner | First machine word | Dispatch-table address for the query |
| Owner dispatch table | Byte offset `0x1c` | Query call target |
| Owner | Byte offset `0x0c` | Address of association storage |
| Association storage | Byte offset `0x04` | Destination for the requested-object pointer |
| Queried old object | First machine word | Dispatch-table address for old-object notification |
| Old-object dispatch table | Byte offset `0x3c` | Old-object notification target |
| Requested object | First machine word | Dispatch-table address for new-object notification |
| Requested-object dispatch table | Byte offset `0x38` | New-object notification target |

These offsets describe only the fields accessed here. They do not establish complete object sizes, inheritance, type identities, or the meaning of adjacent fields.

The representation uses 32-bit integer words. Consequently, the owner’s fourth word is at byte offset `0x0c`, and the association destination is four bytes beyond the address stored there. Pointer-bearing words and dispatch-table entries are represented as 32-bit values in this source view. The actual binary ABI, alignment requirements, and calling convention are not independently established.

The offsets are byte displacements. The storage destination is not four pointer elements beyond its base, and the dispatch offsets are not entry counts.

### Preconditions

For defined operation, the following must hold on each path that reaches the corresponding access:

- The owner permits the initial dispatch-table read.
- The query dispatch entry is readable and callable with the owner as its argument.
- A nonnull queried old object that differs from the requested object permits its notification dispatch.
- On the change path, the owner’s storage-reference field is readable and identifies storage with a writable pointer-sized destination at byte offset `0x04`.
- A nonnull requested object on the change path permits its notification dispatch after the destination has been written.

The function contains no explicit validation of these conditions. A null requested object is supported; a null owner is not a supported sentinel in the visible behavior.

## Behavior

### 1. Query the current association

The function first reads the owner’s dispatch-table address, obtains the target at byte offset `0x1c`, and invokes that target with the owner.

The result is interpreted as an object pointer. This document calls it the **queried old object**.

The query occurs even when the requested object is null. It also occurs when the requested object will compare equal to the result. Thus, “no change” does not mean “no external call” or “no possible side effects.”

Nothing establishes that the query is pure, that it reads the same field this function later writes, or that its returned pointer remains live without further guarantees.

### 2. Compare addresses and possibly return

The queried old-object pointer is compared directly with the requested-object pointer.

If they are equal, the function returns immediately. In that case:

- No old-object notification is initiated.
- The owner’s association-storage reference is not read by the subsequent change path.
- No association-store operation is performed by this function.
- No new-object notification is initiated.

This applies when both pointers are null as well as when both identify the same nonnull address. The comparison is pointer identity, not content equality.

Any side effects already performed by the query remain possible.

### 3. Notify the old object when present

If the addresses differ and the queried old object is nonnull, the function:

- Reads that object’s dispatch-table address.
- Obtains the target at byte offset `0x3c`.
- Invokes it with the queried old object as receiver and the owner as the additional argument.

This notification completes, assuming normal return, before this function reads the owner’s association-storage reference for its explicit store.

The query result is not refreshed after this notification. There is no second equality check, even if the notification changes the owner or its reported association.

No claim is made that the notification releases memory, adjusts a reference count, disconnects a relationship, or leaves either argument unchanged.

### 4. Store the requested-object pointer

After the optional old-object notification, the function reads the storage-reference word at owner byte offset `0x0c`. It writes the requested-object pointer at byte offset `0x04` within that referenced storage.

The timing of this read is significant. If an earlier dependency changes the owner’s storage reference, the visible sequence uses the reference available when this step is reached, rather than a reference captured before notification.

This is one explicit pointer store. No companion field update, clearing of the previous destination, allocation, deallocation, or rollback is visible.

For a null request, the stored value is null. For a nonnull request, the stored value is the requested pointer.

### 5. Notify the requested object when present

If the requested-object pointer is null, the function returns after the store.

Otherwise, it reads the requested object’s dispatch-table address, obtains the target at byte offset `0x38`, and invokes it with the requested object as receiver and the owner as the additional argument.

This dispatch occurs after the explicit association store. Its target is resolved at that point, not before the old-object notification or before the store.

The visible representation treats the final indirect transfer as a call, but includes a recovery warning about its control-flow form. The supported behavioral contract is a final notification after the store; the precise machine-level call-versus-tail-transfer mechanism is not independently established.

### Ordering and reentrancy

Assuming all dependencies return normally, the observable outer sequence is:

1. Query dispatch.
2. Address comparison.
3. Optional old-object notification dispatch.
4. Association-storage reference read.
5. Requested-pointer store.
6. Optional requested-object notification dispatch.

Each dependency may perform additional operations internally. Those operations are not specified here.

There is no visible reentrancy guard, locking, transactional boundary, or post-notification validation. If a dependency reenters this function, changes dispatch tables, redirects storage, or mutates shared state, the outer invocation continues according to its already obtained query result and the later reads described above.

The final stored state is not guaranteed to equal the requested pointer when the function returns: the final notification may modify that state.

## Side effects

### Direct effects

On the unequal-pointer path, the function directly writes the requested pointer into the association destination selected after the optional old-object notification.

On the equal-pointer path, no explicit store is performed by this function.

The owner, old object, requested object, and storage can have additional side effects through dependency calls. Those effects are unknown rather than assumed absent.

### Ownership and lifetime

No direct allocation or deallocation is visible. No explicit retain, release, destruction, or ownership-transfer operation is established.

Correct execution requires each object and dispatch structure to remain usable until its relevant access. In particular:

- The owner must remain usable after the query and after any old-object notification when the change path continues.
- A nonnull queried old object must remain dispatchable until its notification begins.
- A nonnull requested object must remain dispatchable after the association store.

The function provides no visible protection against a dependency invalidating memory needed later.

Aliasing is not explicitly rejected. However, if the association destination overlaps an owner field, dispatch structure, or object memory, the write may affect later accesses. For a nonnull request, the requested object’s dispatch information is read after that write. The contract does not silently assume disjoint storage.

### Errors and exceptional exits

There is no explicit error result, null-owner check, dispatch-target validation, storage validation, or rollback path.

If an access is invalid, a target cannot be called, or a dependency does not return normally, the resulting failure behavior depends on the execution environment and dependency. It is not specified by the supplied evidence.

If the final notification fails after the store, the store has already occurred. No restoration of the previous association is visible.

## Acceptance examples

These examples are conditional on valid memory and normal dependency returns. They describe required observations, not executed tests.

### Same nonnull object

Given that the query returns the exact requested address:

- The query is invoked.
- Neither notification is invoked by this function.
- No association-storage read or store follows the equality check.

An acceptance observer must still allow query-side effects.

### Both pointers null

Given a null request and a null query result:

- The query occurs.
- The function returns through the equality path.
- No explicit null store occurs.

This differs from removal of a nonnull association.

### Remove an existing object

Given a null request and a nonnull query result:

- The old-object notification occurs first.
- The owner’s storage reference is then read.
- Null is stored into the selected destination.
- No new-object notification occurs.

### Install into an empty association

Given a nonnull request and a null query result:

- No old-object notification occurs.
- The requested pointer is stored.
- The requested object is notified afterward.

At the start of the final notification, this function has completed its explicit store.

### Replace one object with another

Given distinct nonnull old and requested addresses:

- The old object receives its notification with the owner.
- The requested pointer is then stored.
- The requested object receives its notification with the same owner.

There is no intermediate null store in the visible sequence.

### Old notification redirects storage

Given that the old-object notification changes the owner’s storage reference from one valid region to another:

- The subsequent explicit store targets the latter region.
- The function does not separately update the earlier region.

This follows from the storage-reference read occurring after the notification.

### Final notification changes the association again

Given that the requested-object notification replaces the stored association:

- The function does not restore the original request afterward.
- Return-time association state may differ from the requested pointer.

Acceptance must not require a postcondition that the visible function does not enforce.
