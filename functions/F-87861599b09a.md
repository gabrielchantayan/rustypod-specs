# F-87861599b09a

## Purpose

F-87861599b09a modifies a three-word storage descriptor and constructs or assigns a four-byte element associated with a supplied source slot.

The structure and dependency usage suggest an append operation on a contiguous collection of reference-counted, string-like values. That interpretation is **inferred intent**, not an established semantic guarantee. In particular:

- The return value differs between ordinary insertion and storage replacement.
- One storage-full path contains a backward traversal that does not terminate within the expected live range under ordinary unchanged-descriptor conditions.
- Allocation failure, dependency exceptions, ownership transfer, and rollback are not established.

This contract describes the visible operations and their ordering without replacing those irregularities with conventional container behavior.

## Interface

### Inputs

The function receives two addresses:

1. **Descriptor address.** Points to at least three readable and writable four-byte words:
   - Offset **0**: storage-start address.
   - Offset **4**: current-end address.
   - Offset **8**: storage-limit address.

2. **Source-slot address.** Points to a readable four-byte word containing a payload address.

These names describe the apparent roles of the fields. No validation establishes that they form a valid ordered range.

The visible representation uses 32-bit words, addresses, and unsigned arithmetic. Element-address steps are four bytes. It is not a native 64-bit pointer layout.

### Payload-relative fields

On paths that inspect the source directly, the payload address obtained from the source slot must support these reads:

| Relative offset | Width | Visible use |
|---|---:|---|
| −12 bytes | 32 bits | Compared with the all-ones value, interpreted as −1 |
| −4 bytes | 32 bits | Supplied to construction, assignment, or transfer dependencies |

The field at −4 is plausibly a payload length, but its unit and meaning are not independently established.

### Output

The return value is an address-sized, 32-bit value:

- On the ordinary non-full path: the captured original current-end address, including a possible zero result.
- On the special full-storage path, if it reaches its return: the captured original current-end address.
- On storage replacement: the newly computed storage-limit address, **not** the inserted element’s address.

There is no explicit status code, allocation-failure result convention, or error object.

### Preconditions

For defined successful execution, every address actually read or written must be valid for that operation, and every dependency must accept the arguments supplied to it. This includes payload metadata, construction destinations, and ranges passed to dependencies.

The function does not enforce non-nullness, alignment, range ordering, available capacity, arithmetic safety, or source independence. Stronger container invariants and aliasing restrictions remain documented_only.

## Behavior

### 1. Initial dispatch

The function first captures the descriptor’s current-end address, then compares that captured address with the storage-limit field.

- If they differ, it takes the ordinary non-full path.
- If they are equal, it consults two dependencies and chooses one of two full-storage paths.

Equality alone controls this first choice. A malformed descriptor whose current end lies beyond its limit still takes the non-full path if the addresses differ.

### 2. Ordinary non-full path

The function first writes the captured current-end address plus four bytes into the descriptor’s current-end field.

This publication occurs **before source metadata is read or element construction is completed**.

If the captured destination address is zero, the function immediately returns zero. It does not read the source slot on this branch. In the 32-bit address model, the descriptor’s current-end field has nevertheless been changed to address 4.

For a nonzero destination, it reads the payload address from the source slot and tests the metadata word at payload minus 12.

#### Metadata is −1

The function:

1. Reads the four-byte quantity at payload minus 4.
2. Calls F-fe78e25e82ff with the destination slot and that quantity supplied twice.
3. Adds 12 bytes to the returned address.
4. Stores that adjusted address in the destination slot.
5. Calls an unmapped transfer dependency with:
   - The adjusted returned address.
   - The payload address freshly reread from the source slot.
   - The previously captured quantity.

The destination write precedes the transfer call. The transfer’s source is not necessarily the payload address used for the initial metadata inspection.

The apparent intent is private construction followed by payload copying. Actual allocation, termination, copy semantics, and handling of overlapping addresses are not established.

#### Metadata is not −1

The function:

1. Stores the previously read payload address in the destination slot.
2. Calls F-54e9fd6505cf with payload minus 12.

This includes metadata values other than a conventional positive reference count. The visible distinction is only “exactly −1” versus “anything else.”

The apparent intent is shared ownership with a reference-count adjustment. The dependency’s actual ownership effect is unknown.

### 3. Full-storage decision

When the captured current-end and storage-limit addresses are equal, the function calls:

1. F-2aa59d7a08b5 with no explicit argument visible.
2. F-e02ac27bd77d with the descriptor address.

Both results are treated as unsigned 32-bit quantities.

If the second result is strictly less than the first, the function takes the special in-place path. Equality selects storage replacement.

These results may represent capacity and size, but that interpretation is inferred. Neither purity nor preservation of the descriptor or global state is established.

### 4. Special in-place path

The function rereads the descriptor’s current-end field and advances that field by four bytes.

If this reread address is nonzero, F-f4fd698ba468 is called with:

- The reread end address as destination.
- The address four bytes before it as source.

This call is skipped when the reread address is zero. The subsequent traversal is **not** skipped.

#### Backward traversal

The traversal compares the original captured end address with an address four bytes before a separate cursor initialized from the reread end.

While they differ, it moves another cursor backward by four bytes, calls F-4fcc06b56813 on that address, and moves the comparison cursor backward by four bytes.

This direction and termination condition are consequential:

- If the earlier dependencies leave the end field unchanged, both cursors begin at the originally captured end.
- The first dependency call in the traversal is then at original end minus four bytes.
- Subsequent calls proceed toward lower addresses.
- The comparison does not become equal after processing one preceding element; it moves farther from the captured end.

Consequently, this path is not established as a bounded one-element shift. With a finite ordinary allocation, it traverses outside that allocation unless execution is interrupted or another unstated condition applies.

In a purely wrapping 32-bit address model, unchanged initial addresses would require **1,073,741,823 traversal calls** before the comparison becomes equal. This is an arithmetic illustration, not a claim of valid execution: intervening invalid memory access or dependency failure can prevent reaching that point.

#### Assignment after the traversal

Only if the traversal finishes does the function read the source payload and inspect metadata at payload minus 12.

If metadata is −1:

- When the original captured destination address equals the source-slot address, no assignment dependency is called.
- Otherwise F-5aa61f6c87d1 is called with:
  - The original captured destination slot.
  - Zero.
  - The metadata quantity read from the destination’s existing payload at offset −4.
  - The source payload address.
  - The metadata quantity read from the source payload at offset −4.
  - Three additional values whose origins are not established by the supplied material.

If metadata is not −1, the order is:

1. Call F-54e9fd6505cf on source payload minus 12.
2. Call F-8a5aadac202f on the original captured destination slot.
3. Reread the source slot and store its current word into that destination.

The source reread occurs after both dependency calls. No guarantee establishes that its contents remain unchanged.

The function then returns the original captured destination address.

### 5. Storage replacement

This path calls F-e02ac27bd77d a second time. It does not reuse the earlier comparison result.

Let the new unsigned 32-bit result be the growth metric. The requested element count is the unsigned maximum of:

- Growth metric plus 32.
- Growth metric plus its right-shift-by-one value plus its right-shift-by-three value.

Every addition is 32-bit and may wrap before the unsigned comparison. The second expression approximates 1.625 times the metric only where arithmetic does not overflow and truncation is accounted for.

The requested allocation quantity is this count shifted left by two bits, also subject to 32-bit truncation. F-871e64ddc6de receives that quantity and zero.

No result check intervenes before the returned address is used.

#### Construction in replacement storage

The following operations occur in order:

1. F-a4bd713d4b27 receives the descriptor’s current storage start, the originally captured end, the allocation result, and the descriptor address.
2. An insertion destination is computed by:
   - Subtracting the descriptor’s then-current storage start from the originally captured end.
   - Clearing the lowest two bits.
   - Adding the allocation result.
3. If that destination is nonzero, F-f4fd698ba468 receives it and the source-slot address.
4. F-a4bd713d4b27 is called again with:
   - The originally captured end.
   - The descriptor’s then-current current end.
   - A freshly recomputed destination offset, plus four bytes.
   - The descriptor address.

The first and second destination calculations separately read the descriptor’s storage-start field. Dependency-induced changes can therefore make them differ. Even if the source range appears empty under normal container invariants, the second F-a4bd713d4b27 call is still made.

#### Old-storage processing and descriptor replacement

Next, the function:

1. Calls F-e02ac27bd77d with the descriptor and captures a 32-bit result.
2. Calls F-f19cd7a3a483 with the descriptor and its then-current start and end.
3. Captures the descriptor’s storage-start field after that call.
4. Calls F-2aa59d7a08b5, this time with the descriptor address.
5. Calls F-ff1bdc376dcd with the captured storage-start address, the preceding dependency result, and zero.
6. Writes the allocation result into the descriptor’s storage-start field.
7. Writes allocation result plus four times the result captured in step 1, plus four, into the current-end field.
8. Writes allocation result plus four times the requested element count into the storage-limit field.
9. Returns that new storage-limit address.

The explicit final descriptor stores occur in start, current-end, limit order. There is no established atomic publication or rollback.

## Side effects

### Descriptor and element writes

The ordinary and special in-place paths advance the current-end field before completing element work.

The replacement path performs construction-related dependency calls and old-storage processing before its final three descriptor writes. Dependencies may also modify the descriptor; preservation is not assumed.

Direct element writes are four-byte stores of payload addresses. The replacement path’s inserted element is handled through F-f4fd698ba468 rather than a visible direct store.

### Ownership

The call patterns suggest sharing, private copying, element destruction, range destruction, allocation, and storage release. Those interpretations do not establish the underlying ownership contracts.

In particular, the supplied body does not prove:

- That a returned allocation is owned by this function.
- That old storage is actually released.
- That a source survives construction or destruction dependencies.
- That metadata adjustments are atomic or overflow-safe.
- That a failing dependency leaves ownership unchanged.

### Aliasing

There is no general source snapshot.

If the source slot aliases a destination, the ordinary −1 branch can overwrite the source-slot word before rereading it for transfer. The transfer then receives the newly stored payload address rather than necessarily receiving the original payload.

If the source slot lies inside old storage during replacement, dependency behavior determines whether it remains readable until element construction. The function supplies no separate preservation mechanism.

### Errors

No explicit error recovery is visible. Null allocation results, malformed payloads, invalid ranges, arithmetic overflow, and dependency failures have no locally implemented recovery path.

If execution stops after an early end-field update, the descriptor may describe an element whose construction did not complete. Strong exception safety is not established.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests.

1. **Non-full, shareable source.** Given a valid nonzero destination and source metadata other than −1, the current-end field advances first, the destination receives the original source payload address, and F-54e9fd6505cf is then called. The return is the original end.

2. **Non-full, private source.** Given metadata −1 and quantity 7, F-fe78e25e82ff receives the destination, 7, and 7. Its result plus 12 is stored before the transfer dependency receives quantity 7 and a freshly read source payload.

3. **Zero destination with unequal limit.** Given end zero and a different limit, the current-end field becomes 4 and the function returns zero without reading the source.

4. **Equality in the full-storage comparison.** Equal unsigned dependency results select replacement, not the special in-place path.

5. **Growth without overflow.** If the second growth-metric call returns 64, the two candidates are 96 and 104. The allocation dependency receives 416 and zero. If subsequent dependencies leave the relevant metric at 64, the final end is allocation result plus 260; the returned limit is allocation result plus 416.

6. **Growth with overflow.** A growth metric of 4,294,967,280 produces candidates 16 and 2,684,354,534 after 32-bit wrapping. The larger candidate’s left shift yields allocation quantity 2,147,483,544. Checked or unbounded arithmetic would not reproduce this behavior.

7. **Unchanged-end special path.** If the preliminary dependencies do not change the full descriptor, observing a single bounded backward operation followed immediately by assignment would contradict the visible traversal.

8. **Replacement return value.** A consumer must not interpret the replacement result as the inserted slot: the returned address is the new storage limit.
