# F-44d1c5b1902d

## Purpose

F-44d1c5b1902d traverses a linked structure, optionally checks a candidate, and either reports the candidate or delegates to F-45446d5e82b1. It communicates its result through a four-byte word and a following one-byte disposition in caller-provided storage.

**Established static behavior:**

- Search comparisons select between two links.
- A container control byte determines whether candidate checking occurs.
- Disposition zero identifies the candidate-reporting path.
- Disposition one identifies a path on which F-45446d5e82b1 returned.

Disposition one does not establish successful insertion, allocation, or a valid returned handle. The reported word is copied from a local slot after the dependency returns; that dependency is not established to write the slot.

**Inferred intent:** the links and navigation resemble an ordered tree with a header, parent links, and predecessor selection. Candidate checking may implement a duplicate-key policy. These interpretations do not establish ordering laws, structural invariants, ownership, or dependency behavior.

### Storage and completion requirements

For an ordinary completion with a determinate result:

1. The result word is written at offset `0x00`.
2. The disposition byte is written at offset `0x04`.

The word write precedes the byte write. No direct result write targets subsequent bytes.

The caller must supply writable result storage and valid storage for every dereference reached on the selected path. Null traversal pointers terminate search, but there is no general null protection for headers, candidates, parent links, or navigation intermediates.

Some insertion paths expose a local slot that this function has not initialized. If the dependency does not establish its contents, normal dependency return alone does not guarantee a determinate result word.

## Behavior

### Search initialization

The remembered comparison outcome initially has the nonzero value one.

Initialization performs distinct reads in this order:

1. Read the container’s header pointer.
2. Read that header’s offset-`0x04` field as the initial traversal pointer.
3. Read the container’s header pointer again and retain this second value as the terminal anchor.

The initial traversal pointer and anchor therefore need not originate from the same observed header value if those reads differ.

### Search traversal

For each non-null traversal node:

1. Zero a four-byte early-insertion slot.
2. Zero a separate four-byte final-insertion slot.
3. Call F-685cd10e4a2e with the comparison-context address, supplied operand, and current-node offset-`0x10` address, in that order.
4. Retain the current node as the terminal anchor.
5. Read the next traversal pointer from offset `0x0c` when the comparison returned zero, or offset `0x08` when it returned nonzero.

Both slots are zeroed on every visited node, before that node’s comparison call. Neither is initialized by this loop when the initial traversal pointer is null.

The selected link is read after the dependency returns. Dependency effects on the node can therefore affect the next traversal step.

Search ends when the selected traversal pointer is null. The terminal anchor is the last visited node, or the second header value if no node was visited. The remembered comparison is the last search result, or its initial nonzero value for empty traversal.

Positive and negative nonzero results select the same link. No signed ordering distinction is made.

### Control-byte decision

After search ends, the function reads the container byte at offset `0x18`.

- A nonzero value selects final insertion directly.
- Zero selects candidate checking.

The control byte is not captured before search. Effects of search dependencies may influence its subsequently observed value.

### Candidate preparation and boundary processing

Candidate checking initially stores the terminal anchor in a writable local candidate slot.

If the remembered search comparison is zero, boundary processing and navigation are skipped. Candidate extraction follows.

If the remembered comparison is nonzero:

1. Read the container’s header pointer again.
2. Read that header’s offset-`0x08` word.
3. Store this boundary word in the final-insertion slot, replacing any earlier zero.
4. Call F-6183894e2484 with the candidate-slot address and final-insertion-slot address.

A nonzero helper result selects early insertion. A zero helper result selects navigation using the candidate slot’s contents after the call.

The helper can modify both exposed slots. It is not established to preserve either value, or to avoid retaining their addresses. Later calls can therefore affect these still-live slots through retained addresses; preservation after helper return must not be assumed.

Early insertion uses the separately retained terminal anchor, not the helper-visible candidate slot.

### Marker-dependent navigation

Navigation first reads the candidate’s one-byte marker.

If the marker is zero:

- Read the candidate’s offset-`0x04` link.
- Read the linked object’s offset-`0x04` field.
- Compare that second pointer with the candidate.

If the pointers match, replace the candidate with its offset-`0x0c` link and skip ordinary navigation.

A nonzero marker, or a zero marker with a nonmatching two-link check, selects ordinary navigation. The intermediate pointer in the two-link check is not checked for null.

### Ordinary navigation and repeated reads

Ordinary navigation reads the candidate’s offset-`0x08` field twice:

- The first read saves a possible next pointer.
- The second read selects climbing when null or descent when non-null.

Descent uses the value from the first read, not the second. The reads must not be collapsed into one observation.

**Climbing:** first read the candidate’s parent-like link. For each parent examined, read its offset-`0x08` link and compare it with the preceding candidate. Replace the candidate with that parent regardless of the comparison result. Equality continues climbing through the parent’s offset-`0x04` link; inequality ends climbing.

Thus, at termination, the candidate is the first encountered parent whose observed offset-`0x08` link did not equal the preceding candidate.

**Descent:** replace the candidate with the saved next pointer. Read the new candidate’s offset-`0x0c` field twice. The first read saves the pointer for a possible next iteration; the second determines whether another iteration occurs.

- A null second read stops descent at the current candidate.
- A non-null second read continues using the first read’s saved value.

If paired reads disagree, a non-null decision can cause a later dereference of a saved null pointer. No recovery is established.

With stable links, this resembles descending through offset `0x08` and then following offset `0x0c` to its end, or climbing parents when offset `0x08` is null. That simplification is conditional on the repeated observations agreeing.

There are no explicit cycle checks or general parent-chain null checks.

### Candidate extraction and comparison

After candidate selection, the function clears a separate four-byte local scratch location. No subsequent direct read or dependency argument uses that scratch value in the supplied representation.

It then:

1. Calls F-4d250808fcd1 with the candidate value read for that call.
2. Calls F-685cd10e4a2e with the comparison-context address, the extraction result, and the supplied operand.

The extraction result is four bytes. The final comparison reverses the operand roles used during search.

A zero final comparison selects candidate reporting. A nonzero result selects final insertion.

On candidate reporting, the function reads the candidate slot for the result-word write, then writes disposition zero. F-45446d5e82b1 is not called.

When the candidate slot was exposed to the boundary helper, its preservation across extraction and comparison is not established. Consequently, the reported candidate is the slot’s value at the output read, not necessarily the value previously passed to extraction.

Zero comparison is not independently established to mean equality or key equivalence.

### Insertion paths

Both insertion paths call F-45446d5e82b1 with these arguments:

1. Address of the selected four-byte local slot.
2. Container address.
3. Literal zero.
4. Retained terminal anchor.
5. Supplied operand.

The paths use distinct slots:

| Path | Slot supplied | Contents established before intervening effects |
|---|---|---|
| Early insertion after nonzero helper return, with a visited node | Early-insertion slot | Zeroed during the last search iteration. |
| Early insertion with empty traversal | Early-insertion slot | Not initialized here. |
| Final insertion without boundary processing, with a visited node | Final-insertion slot | Zeroed during the last search iteration. |
| Direct final insertion with empty traversal and nonzero control byte | Final-insertion slot | Not initialized here. |
| Final insertion after boundary processing | Final-insertion slot | Loaded with the boundary word, then exposed to the helper. Its eventual contents may reflect helper writes **and modifications after helper return**, including during extraction or final comparison through a retained address. |

The boundary-processing row also applies to empty traversal if navigation and comparison reach final insertion.

F-45446d5e82b1 is not established to write its slot. After it returns, the function reads the selected slot and writes that word to the result destination, followed by disposition one.

The reported insertion word is therefore the slot’s value at the post-call read. In particular, knowing its value when the boundary helper returned is insufficient to predict final output without conditions covering intervening operations.

Disposition staging uses one byte of the early-insertion slot. On early insertion, that byte is overwritten only after the slot’s full word has been copied to the result. Candidate reporting and final insertion also stage their disposition there before the final byte write.

Neither insertion path repeats search or validates the terminal anchor after dependency calls.

## Side effects

Direct external writes target the result word and disposition byte. Other direct writes update local storage, including dependency-visible slots.

The function does not directly allocate, release, rebalance, update a count, or write structural links. Dependencies may have such effects; their bodies are not supplied.

No explicit error result, rollback, exception handling, or recovery path is established. Invalid addresses, inconsistent links, cycles, dependency failure or nonreturn, and reads from uninitialized slots have no established handled outcome.

### Ownership and escaped addresses

No ownership transfer, retention permission, or release obligation is established for the operand, container, nodes, candidate, or result word.

Passing local addresses to dependencies does not establish that those addresses remain valid after this function returns. It also does not prove that dependencies refrain from retaining them while the function is active. ### Aliasing and synchronization

No stable snapshot, locking protocol, or concurrent-mutation safety is established. Distinct reads establish order, not permission to mutate the structure concurrently.

## Acceptance examples

These are conditional static acceptance cases. They are not executed tests.

### Initialized final slot remains zero

Given one visited node, a null selected child, and a subsequently observed nonzero control byte, final insertion uses the final-insertion slot zeroed during that visit.

If no intervening operation changes the slot and F-45446d5e82b1 leaves it unchanged, the result is word zero and disposition one. This says nothing about insertion success.

### Candidate reporting without navigation

Given a zero control byte and a last search comparison of zero, boundary processing and navigation are skipped.

If extraction returns normally and the final comparison returns zero, the function reports the candidate with disposition zero. No insertion dependency is called.

### Boundary-derived slot survives to final insertion

Suppose the helper leaves the final-insertion slot containing `0x2468ace0` and returns zero. Suppose navigation is valid and the final comparison is nonzero.

The expected result is `0x2468ace0` with disposition one **only if no intervening operation changes that slot**, including extraction and final comparison, and the insertion dependency also leaves it unchanged.

Equivalently, if the slot contains `0x2468ace0` immediately before insertion and remains unchanged through the post-call read, that is the reported word.

### Intervening modification changes the reported word

Suppose the helper leaves `0x2468ace0` in the final-insertion slot but retains its address. If an intervening dependency changes the slot through that retained address to `0x13579bdf`, the final comparison selects insertion, and the slot remains unchanged through the insertion call and subsequent read, the result is `0x13579bdf` with disposition one.

The helper-return value alone does not determine the result word.

### Early insertion uses the separate slot

Given at least one visited node and a nonzero boundary-helper return, early insertion uses the early-insertion slot, not the helper’s boundary-containing slot.

If the early slot remains zero through the post-insertion read, the result is zero with disposition one. Helper changes to the candidate do not replace the separately retained terminal anchor supplied to insertion.

### Empty traversal

An initially null traversal pointer bypasses both per-node zero initializations.

- Nonzero control selects final insertion with a slot not initialized here.
- Zero control and nonzero helper return select early insertion with a slot not initialized here.
- Boundary processing initializes the final-insertion slot with a boundary word, but does not initialize the early-insertion slot.

A non-writing insertion dependency does not establish a determinate result for either uninitialized-slot case.

### Repeated reads disagree

If ordinary navigation first reads pointer A at offset `0x08` and then reads non-null pointer B, descent uses A.

If descent first reads pointer A at offset `0x0c` and then reads null, it stops at the current candidate without moving to A.

These outcomes depend on read order, not stable-tree assumptions.

### Non-Boolean comparison results

Search results of negative one and positive one both select offset `0x08`. Either sign of nonzero final comparison selects insertion.
