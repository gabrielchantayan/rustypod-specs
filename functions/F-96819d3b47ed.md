# F-96819d3b47ed

## Purpose

F-96819d3b47ed obtains a candidate object through one of two paths: a direct request to a dependency, or retrieval from a context-associated record with conditional creation. A nonzero candidate may then receive four ordered dependency calls and a one-byte state update. A zero candidate instead causes a one-byte failure indication in a separate caller-supplied record.

This is a source-facing behavioral contract based on static evidence only. “Object,” “context,” “associated record,” and “initialization” are descriptive terms, not established type or ownership declarations. In particular, the dependency called with the value 100 is not proven to allocate memory, and the dependencies surrounding access to the associated record are not proven to acquire or release a lock.

## Interface

### Inputs and result

The visible interface has two 32-bit integer-shaped inputs and a 32-bit integer-shaped result. Some of these values are used as addresses.

- **Status-record address:** Used only when the eventual candidate value is zero. In that case, the function writes the byte value 1 at offset 30 from this address.
- **Context value:** Zero selects direct acquisition. Nonzero is passed to two dependencies and is also treated as an address from which a 32-bit associated-record address is read at offset 4.
- **Result:** The selected candidate value, returned without an explicit success-code translation. Zero is the visible failure result; a nonzero result is also used as an object address.

No argument validation, bounds checking, address validation, or explicit error object is visible.

### Relevant layouts

Offsets are byte offsets. The following describes only fields directly accessed by this function, not complete types or dependency requirements.

|---|---:|---:|---|

The global state directly read by this function consists of one 32-bit word. Its meaning and the meaning of the associated-record field at offset 60 are not established.

### Preconditions

For normal completion, every executed memory access must be valid, and every invoked dependency must return normally.

A nonzero context requires a readable 32-bit field at offset 4 and a usable associated-record address from that field. Depending on the cached value, the associated record must permit reads at offset 56 and writes at offsets 56 and 60.

A nonzero selected candidate requires a readable byte at offset 88. If that byte is zero, the candidate must also support the dependency operations and the final write at offset 89.

The status-record address need not be dereferenced on a nonzero-result path. Conversely, the function does not protect a zero-result path against an invalid status-record address.

No alignment, address-overflow, or concurrent-access guarantees can be established from the supplied evidence.

## Behavior

### Entry snapshot

The function first reads the global 32-bit word and retains that value for possible later use. This read precedes branch-specific dependency calls.

The captured value is not refreshed if a dependency changes the global word. It is written to the associated record only on the context path when the cached candidate was observed to be zero. On other paths, the initial global read still occurs, but this function does not subsequently use the captured value in a visible write.

### Direct acquisition

When the context value is zero:

1. F-1c177d5ba9f6 is called with the integer value 100.
2. Its 32-bit result becomes the selected candidate.

No context field or associated-record field is accessed on this path. There is no visible cache write, metadata write, retry, or balancing call associated with the acquisition.

The value 100 is established as a dependency argument. Its interpretation as an allocation size or any other quantity is unknown.

### Context-associated acquisition

When the context value is nonzero, the following ordering applies:

1. The associated-record address is read from context offset 4 and retained.
2. F-0b4658e20c99 is called with the original context value.
3. The 32-bit cached candidate at offset 56 of the retained associated record is read.
4. If that cached value is zero:
   - F-1c177d5ba9f6 is called with 100.
   - Its result is written to associated-record offset 56, including when that result is zero.
   - The entry-time global snapshot is written to associated-record offset 60.
5. F-96dd78c4ca33 is called with the original context value.
6. The candidate at offset 56 of the retained associated record is read again. This last read determines the selected candidate.

The associated-record address is captured before F-0b4658e20c99. A change to context offset 4 during that call does not redirect this invocation’s later explicit accesses to another record.

The final cache read occurs after F-96dd78c4ca33. Consequently, the selected candidate need not equal either the earlier cached value or the result of F-1c177d5ba9f6. A dependency or another actor could change the retained record’s cache before the final read.

If the first cache read is nonzero, this function neither calls F-1c177d5ba9f6 nor writes the captured global word to offset 60. F-96dd78c4ca33 still runs, and the cache is still reread afterward.

### Zero candidate

If the selected candidate is zero, the function writes the byte value 1 at status-record offset 30, then returns zero.

This function does not clear that status byte on success. A previously set status indication can therefore remain set after a successful invocation unless some other actor changes it.

On the context path, a zero candidate is determined by the final cache read—not solely by the acquisition dependency’s return value.

### Nonzero candidate

For a nonzero candidate, the function reads the byte at candidate offset 88.

If the byte is nonzero, the function returns the candidate without making any initialization dependency calls and without explicitly writing candidate offset 89.

If the byte is zero, it calls F-c247d7bfe027 four times, in this order:

| Call | First argument | Second argument | Third argument |
|---|---|---:|---:|
| 1 | Candidate address + 4 | 3 | 0 |
| 2 | Candidate address + 24 | 3 | 0 |
| 3 | Candidate address + 44 | 3 | 0 |
| 4 | Candidate address + 64 | 3 | 1 |

After all four calls return normally, it writes the byte value 1 at candidate offset 89 and returns the candidate.

The four calls use the same selected candidate as their address base. This function does not reread the associated-record cache between them. Changes to that cache therefore do not redirect these calls or change the retained return value.

No return value from F-c247d7bfe027 is checked. There is no visible conditional stop between calls based on a dependency-reported status.

The guard at offset 88 is not explicitly written by this function. The final write targets the distinct byte at offset 89. Thus, this function’s own final write does not establish that a later invocation will skip initialization.

## Side effects

### Explicit memory effects

The function directly performs the following conditional writes:

- Zero selected candidate: status-record offset 30 receives byte value 1.
- Initially empty context cache: associated-record offset 56 receives the acquisition result, followed by offset 60 receiving the captured global word.
- Nonzero candidate with zero initialization guard: candidate offset 89 receives byte value 1 after the four initialization calls.

No other direct writes are visible. Dependencies may have additional effects; none are excluded by this contract.

These writes are not specified as a transaction. For example, on the context path, both associated-record writes occur before the final context dependency call and before the candidate guard is inspected.

### Aliasing and concurrency

No non-aliasing guarantee is established among the status record, context, associated record, candidate, or global storage. The write order matters if valid caller-supplied regions overlap.

The names and placement of F-0b4658e20c99 and F-96dd78c4ca33 may suggest an access protocol, but synchronization is not established. This contract does not promise atomic cache creation, exclusive initialization, memory ordering, or race freedom.

The final cache read occurs after F-96dd78c4ca33 returns. Any proposed synchronization interpretation must account for that ordering rather than assuming the selected candidate was captured beforehand.

### Ownership and failure handling

No explicit release, deallocation, reference-count adjustment, or ownership transfer is visible.

The caller’s ownership obligations for a returned candidate are unknown. The acquisition dependency’s result is stored in the cache without any visible cleanup if the cache later changes. This is not evidence of either a leak or correct ownership management without the dependencies’ contracts.

There is no visible recovery from invalid addresses, interrupted execution, or a dependency that does not return normally. Partial side effects may already have occurred in those cases.

## Acceptance examples

These examples are conditional specifications, not runtime observations. They assume valid executed accesses and normally returning dependencies.

### Direct zero result

Given a zero context and an F-1c177d5ba9f6 result of zero:

- The acquisition call receives 100.
- Status-record offset 30 is written with byte value 1.
- No initialization call occurs.
- The returned value is zero.

### Direct candidate with a nonzero guard

Given a zero context, a nonzero acquisition result, and a nonzero byte at candidate offset 88 when inspected:

- No F-c247d7bfe027 call occurs.
- This function does not write candidate offset 89.
- The candidate is returned.
- This function does not clear or otherwise write the status byte.

### Candidate requiring initialization

Given a selected nonzero candidate whose offset-88 byte is zero:

- The four dependency calls occur in the listed order, with the listed addresses and integer arguments.
- Candidate offset 89 is written with 1 only after the fourth call returns.
- The selected candidate is returned.

Even if a dependency changes the guard byte during these calls, this function does not recheck it or skip the remaining calls on that basis.

### Context with an existing candidate

Given a nonzero context, a retained associated record whose initial cache read is nonzero, and no intervening cache mutation:

- The two context dependencies are called in order.
- No acquisition call occurs.
- Associated-record offset 60 is not explicitly written.
- The final cache read selects the existing candidate for guard handling.

### Empty cache with failed acquisition

Given an initially zero cache, a zero acquisition result, and no later cache mutation:

- Zero is written to the cache.
- The entry-time global snapshot is written to offset 60 despite acquisition returning zero.
- F-96dd78c4ca33 is called before the cache is reread.
- The final zero selection causes the status-byte write and a zero return.

### Cache changed by the final context dependency

Given that F-96dd78c4ca33 changes the retained record’s cache to another valid nonzero candidate:

- The changed candidate is selected by the final read.
- Its guard controls initialization.
- That changed candidate is returned, regardless of the earlier cached or acquired value.

### Global changed during acquisition

Given an initially empty cache and a dependency that changes the global word after entry:

- The metadata write uses the entry-time snapshot.
- The changed global value is not reread for that write.
