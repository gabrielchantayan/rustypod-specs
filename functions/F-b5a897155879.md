## Behavior

### 1. Check that the header fits

The first check compares End against Start plus two bytes.

- If End is strictly before that address, the function returns `3`.
- Equality is accepted.
- No header byte is read on the rejecting path.

This establishes a minimum extent of two bytes under the ordinary, non-wrapping interpretation of the addresses. It does not validate Start or End as actual memory addresses.

### 2. Read the count and check the declared extent

After the first check succeeds, the function reads the two header bytes and forms the unsigned 16-bit record count.

The first record begins two bytes after Start. The required endpoint is that first-record address plus four times the count.

- If End is strictly before the required endpoint, the function returns `3`.
- Equality is accepted.
- An End beyond the required endpoint is also accepted.

Consequently, the function does not require the supplied extent to contain only the declared sequence. Extra trailing bytes do not become additional records.

The count multiplication itself has a maximum result of 262,140 bytes. Including the header, the maximum declared sequence size is 262,142 bytes. These values fit within 32-bit integer arithmetic; this does not establish that adding them to an arbitrary pointer cannot wrap or become invalid.

On rejection at this stage, the header has been read, but no record bytes have been read by this function and no dependency invocation has occurred.

### 3. Handle an empty sequence

A count of zero causes a successful return of `0` after the extent checks.

No record bytes are read, and F-9ed95c690cc1 is not invoked. A two-byte extent is sufficient for this case.

### 4. Process records in order

For a nonzero count, records are processed from the first record to the last without skipping or reordering.

For each record, the function obtains:

1. Its two-byte big-endian identifier.
2. Its unsigned byte at offset 2.
3. Its unsigned byte at offset 3.

It invokes F-9ed95c690cc1 with these four arguments:

| Dependency argument | Value |
|---|---|
| 1 | Original Context |
| 2 | Current record’s unsigned 16-bit identifier, represented numerically |
| 3 | First base plus the unsigned byte at record offset 2 |
| 4 | Second base plus the unsigned byte at record offset 3 |

The additions use the unsigned 32-bit arithmetic implied by the explicit unsigned conversion of each adjustment. Thus, at that arithmetic stage, addition wraps modulo \(2^{32}\); there is no visible overflow rejection, saturation, or clamping.

The dependency’s formal parameter types are not supplied. Whether it interprets an adjusted 32-bit pattern as signed or unsigned is therefore unknown.

The first identifier byte is read before the other three record bytes. The supplied representation does not establish a relative read order among the second identifier byte and the two adjustment bytes, which appear as argument expressions. All four record bytes are obtained before the dependency invocation begins.

### 5. Stop or continue according to the dependency result

After each dependency invocation:

- A zero result allows processing to continue with the next record.
- A nonzero result is returned immediately.

There is no retry, error translation, or visible rollback.

If a dependency fails for a particular record, no later record is processed or read by this function. Earlier successful dependency invocations have already occurred; their effects are not reversed by any visible action here.

If all declared records return zero, the function returns `0`.

### Snapshot and mutation boundaries

The count is read once before record processing. The function does not reread the header after a dependency invocation.

Record contents are not copied into a complete preliminary snapshot. A record’s bytes are read when that record is reached. Therefore, if a dependency modifies bytes belonging to a later record, later processing can observe those modified bytes.

Modifying the header after processing begins does not change the already captured count. Likewise, the extent check is not repeated between records.

These observations describe the function’s own access pattern. They do not establish that the dependency is permitted to mutate the input, that concurrent mutation is safe, or that arbitrary dependency behavior cannot invalidate later reads.
