# F-1e77f5f5600b

## Purpose

F-1e77f5f5600b dispatches an operation to objects supplied by an external iteration mechanism. It supports two modes:

- **Record-backed dispatch:** obtain an initial record through a lookup, then supply successive record-payload addresses to successive objects.
- **Null-payload dispatch:** omit the lookup and supply zero as the payload argument to every produced object.

An optional context controls mode selection and, when present, supplies the lookup selector. Without that context, the function uses record-backed dispatch and obtains the selector from the primary object.

These are descriptions of established accesses and calls. The application-level meanings of the objects, records, selector, and dispatched operation are unknown.

## Behavior

### Local storage and preliminary dependency

Before any dependency call, the function copies the optional-context value, opaque word, and initial object-slot value into local storage.

The address of the context copy is later supplied as the iteration-state address. The object-slot address is supplied separately to advancement. The excerpt presents these as neighboring local storage, but does not establish a complete iterator-state layout or the memory extent dependencies may access.

F-4120116224e1 is then called once, unconditionally, before the explicit primary-object and context-field accesses.

Its result is represented as an unsigned 32-bit value. That result does not determine either dispatch mode:

- With a present context, a flag read replaces it.
- With an absent context, record-backed dispatch is selected independently of the result.

The call remains observable. In particular, its effects on global storage cannot be discarded or assumed absent.

### Selector and flag access order

After the preliminary call, the function determines whether the context is absent.

When context is present, the explicit accesses occur in this order:

1. Read the flag word at context offset `0x58`.
2. Read the fallback selector at primary-object offset `0x44`.
3. Write the first flag value to primary-object offset `0xA4`.
4. Read the replacement selector at context offset `0x08`.
5. Read the flag word at context offset `0x58` again.

The replacement selector is selected for lookup. The first flag value supplies the copied word; the second supplies the mode bit.

The two flag reads are distinct. Equality between their results is not guaranteed by the visible body. Address overlap can also make access order significant: the primary-object write precedes both the context-selector read and the second flag read.

When context is absent:

- No context fields are read.
- No explicit write occurs at primary-object offset `0xA4`.
- The selector is read from primary-object offset `0x44`.

The primary selector read is not omitted merely because a present context supplies a replacement.

### Mode selection and global argument read

Record-backed dispatch is selected when either:

- Context is absent; or
- Bit zero of the second context flag read is clear.

Null-payload dispatch is selected only when context is present and bit zero of its second flag read is set. Other flag bits do not affect this branch, although the entire first flag word is copied.

Only on the record-backed path, after the selector and flag accesses above, the function reads global storage to obtain the first lookup argument. It then calls F-8967e4fb3bba with that value and the selected four-byte selector.

This global value is **not captured at entry**. The read follows F-4120116224e1 and all applicable selector/flag accesses. If the preliminary dependency changes that global, the lookup argument comes from the later read, subject to any further changes before that read. The excerpt provides no invariant-global guarantee.

The null-payload path performs neither this explicit global read nor the lookup.

### Lookup result and record representation

The lookup result is represented by a **signed 32-bit integer**. Zero causes immediate return. A nonzero result becomes the current-record accumulator, also represented by a signed 32-bit integer.

A lookup miss occurs before iterator initialization. Consequently, it causes no advancement, callback, or finalization. Earlier effects remain observable, including any flag copy and effects of the preliminary dependency or lookup.

The nonzero test does not reject negative signed results. Whether such a value denotes usable storage is not established.

The accumulator is an address-like integer representation, not an established native-width pointer. Payload arguments and record-field addresses are formed through integer expressions involving this accumulator.

### Record-backed iteration

After a nonzero lookup result, F-8ca21d3a8cca receives:

- The local iteration-state address.
- The address formed from the primary-object value plus `0xA8`.

F-b38a3aba0e18 then repeatedly receives the state address and local object-slot address. Its result is represented as a signed 32-bit integer. Zero ends iteration; any nonzero result triggers dispatch using the slot’s current value.

For each such result:

- The function reads the produced object’s dispatch-table reference and resolves the callback at table offset `0xDC`.
- The callback receives the object and a payload argument formed by adding eight to the current signed 32-bit record accumulator.
- After the callback returns, the function reads the signed 32-bit displacement from the address formed by adding four to that accumulator.
- The accumulator is updated using the displacement, the current accumulator, and an additional four-byte offset.

For representable, usable calculations, the next-record relation is:

\[
R_{\text{next}} = d + R + 4
\]

Here \(R\) and \(d\) are signed 32-bit integer representations. The displacement is relative to its field at record offset four, not to the payload at offset eight.

This equation describes the address relation; it does not establish unbounded arithmetic, native-pointer arithmetic, or defined wraparound. The visible update combines the signed displacement with the accumulator and then adds four. Intermediate arithmetic limits matter.

The displacement is loaded **after** the callback. A valid callback mutation of that field can therefore affect the next record. Conversely, a callback that makes the displacement storage unreadable prevents the visible path from completing normally.

The update occurs after every completed callback, including the last one before a subsequent advancement returns zero. There is no explicit record terminator, record-count limit, or validation that records match the number of produced objects. The updated accumulator is not checked for zero.

### Null-payload iteration and finalization

Null-payload mode initializes and advances iteration through the same dependencies and argument forms.

Each nonzero advancement result triggers the resolved object callback with the current object and a zero second argument. This path performs no explicit record-displacement load or record-accumulator update.

In either mode, once an initialized iterator reports zero, F-d0d3f100effc is called once with the iteration-state address. This includes immediate completion on the first advancement.

No exceptional-exit cleanup mechanism is visible. Faults, nonreturning calls, and nonlocal exits do not have an established finalization guarantee.

## Side effects

### Direct and delegated effects

The only explicit store to a primary-object field is the four-byte flag copy at offset `0xA4`, conditional on context presence. It precedes mode selection, the global argument read, lookup, and initialization. A lookup miss does not undo it.

The function also initializes local storage and updates the local record accumulator. Iteration dependencies receive local addresses and may modify accessible storage according to contracts not supplied here.

Additional effects are delegated to every dependency and callback. None is established to preserve globals, avoid allocation or release, or leave objects and records unchanged.

The explicit global load occurs only when preparing the record-backed lookup. No direct global store is visible in this body; this does not constrain indirect global writes.

Negative displacement values are not rejected. Records may move backward or repeat. No overflow, address-range, record-boundary, or null-result check protects the updated accumulator.

The function reports no errors to its caller. Lookup zero and advancement zero have established control-flow meanings; their broader meanings are unknown. Negative advancement results are treated as nonzero, not as a distinct error class.

## Acceptance examples

These are conditional static expectations, not executed tests. Record-address examples require valid storage and representable intermediate signed 32-bit calculations.

### Absent context and lookup miss

Given absent context and lookup result zero:

- The preliminary dependency runs.
- The primary selector is read.
- Global storage is read afterward to supply the lookup’s first argument.
- No flag copy, iterator initialization, advancement, callback, or finalization occurs.

### Preliminary dependency changes the global

Suppose the lookup-argument global initially contains value \(A\), and F-4120116224e1 changes it to \(B\). If record-backed mode is selected and no intervening effect changes that storage, the lookup receives \(B\), not an entry-time copy of \(A\).

If null-payload mode is selected instead, this function does not explicitly read that global for lookup and does not call the lookup dependency.

### Present context, clear mode bit, lookup miss

Given a present context whose second flag read has bit zero clear:

- The first flag value is copied to the primary object.
- The context selector replaces the primary selector.
- The global argument is read after those accesses.
- A zero lookup result returns without iterator initialization.
- The copied flag value remains unless another effect changes it.

### Set mode bit and two produced objects

Given a present context whose second flag read has bit zero set, and two nonzero advancement results followed by zero:

- No lookup or lookup-argument global read occurs.
- Each produced object receives one callback with a zero second argument.
- No record displacement is explicitly loaded.
- Finalization follows the terminating advancement.

### Successful lookup and empty iteration

Given record-backed mode, a nonzero lookup result, and immediate advancement result zero:

- Initialization and finalization each occur once.
- No callback or record-displacement load occurs.

### Two record-backed callbacks

Suppose the initial accumulator is \(R\), and the first post-callback displacement read yields \(d\).

If two objects are produced:

- The first callback receives the argument represented by \(R+8\).
- The next accumulator is represented by \((d+R)+4\).
- The second callback receives that next accumulator plus eight.
- The second record’s displacement is read and another update is performed before the terminating advancement.

These expectations require every relevant intermediate calculation to remain within the established signed 32-bit representation and every reached address to be usable. They assert no wraparound behavior.

### Repeated record and differing flag reads

A displacement of \(-4\) leaves the accumulator unchanged when the arithmetic is representable. A following produced object therefore receives the same payload argument; the function has no repeated-record rejection.

Separately, if the first flag read has bit zero clear but the second has it set, the first value is copied while null-payload mode is selected. This does not establish that unsynchronized concurrent modification is valid.
