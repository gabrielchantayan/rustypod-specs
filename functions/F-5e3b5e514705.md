# F-5e3b5e514705

## Purpose

F-5e3b5e514705 coordinates work using two descriptor slots, alternating source submissions with status inspection and consumer calls. It calculates chunk quantities, submits descriptors at advancing positions, and reports a selected local status through caller-provided storage.

The established contract is the ordering of calls, memory accesses, arithmetic, branching, and status propagation below. An asynchronous, double-buffered transfer is inferred intent; the dependency implementations do not establish that interpretation.

The function has no explicit return value. Its direct result is two consecutive 16-bit output fields. Source operations and consumer calls may already have taken effect on an error path. No rollback is visible.

### Status and descriptor storage

The function maintains two local statuses, designated **A** and **B** in this contract. Each has two 16-bit fields. A belongs to the first slot; B belongs to the second.

Two distinct local 16-byte descriptor buffers are observable:

- A dedicated buffer used only for the initial first-slot submission.
- One shared scratch buffer used for every subsequent submission and for both consumer paths.

Each snapshot consists of four 32-bit reads from the selected context descriptor, in increasing address order, with corresponding local writes. These are shallow copies; ownership of referenced resources is not established.

Fresh snapshots do **not** imply distinct backing storage. A dependency retaining a pointer to the shared scratch buffer can observe later overwrites during this invocation.

## Behavior

### Initial calculation and initialization

Before any dependency call, the function reads the unsigned 32-bit context word at `0x34`.

- Below `65,536`, the chunk limit is that value shifted right by one bit.
- At or above `65,536`, the limit is `32,768`.

The limit is therefore between zero and `32,768`, inclusive. It remains fixed for this invocation even if the context word later changes.

The function invokes the source operation at dispatch offset `0x24`. The supplied representation shows no explicit call arguments; an implicit receiver convention is unresolved.

Its 32-bit result is multiplied by the quantity multiplier and assigned to an unsigned 32-bit remaining-quantity value. The multiplication is expressed using signed operands before that assignment. There is no overflow check or rejection of negative operands. Exact behavior outside the signed representable range is documented_only; modulo multiplication must not be assumed from this representation alone.

F-603a53835f04 is then called on status A, followed by status B, each time with three zero arguments. The contents produced by those calls are dependency-defined.

The first chunk is the unsigned minimum of the fixed limit and the initial remaining quantity.

### Initial first-slot submission

The function obtains a source receiver from the context and invokes its query operation at dispatch offset `0x24`. F-d7be9cfb4000 receives the first chunk and that fresh query result. Only the low 16 bits of its result are retained for submission.

After conversion, the first descriptor is copied into the dedicated initial descriptor buffer. The source operation at dispatch offset `0x08` receives:

- The cached source receiver.
- The dedicated descriptor-buffer address.
- The initial position.
- The narrowed 16-bit conversion result.
- The context address at `0x54`.
- Status A’s address.

The receiver is cached before the query and conversion. Replacing the context’s source pointer during either intervening call does not replace that receiver for this submission. This does not imply that the receiver’s own dispatch table or state remains unchanged.

The initial submission occurs even when the remaining quantity or chunk limit is zero.

A nonzero submission return causes F-7f008c1060db to receive status A and arguments `0x22`, zero, zero. Status A is then selected for output. No slot synchronization, status inspection, or consumer call occurs on this path.

A zero return enters alternating processing.

### First-slot phase

If the remaining quantity is zero on entry, status A is selected immediately. Thus a successful initial submission for a zero total is not followed by synchronization or inspection.

Otherwise, the function:

1. Subtracts the first-slot chunk from the unsigned remaining quantity.
2. Performs a fresh source query and conversion of that chunk.
3. Advances the position using the full 32-bit conversion result.
4. Calculates the second-slot chunk as the unsigned minimum of the limit and the remaining quantity.

If quantity remains, the second slot is submitted **before** first-slot synchronization. This submission obtains a fresh source receiver, queries and converts again, narrows the submission quantity to 16 bits, and copies the second descriptor into the shared scratch buffer. It passes the advanced position, the context address at `0x58`, and status B.

If this second-slot submission returns nonzero, F-fceaba74ea88 is called on the first-slot address, and status B is selected. There is no first-slot inspection or consumption, and no explicit `0x22` update for this submission failure.

Otherwise, including when no second submission was needed, the function synchronizes the first slot through F-fceaba74ea88 and inspects status A through F-ec61551795ee.

A zero inspection result suppresses the first-slot consumer call. If remaining quantity is nonzero, the second slot is synchronized before status A is selected.

A nonzero result permits consumption. The function copies the current first descriptor into the shared scratch buffer and calls the consumer operation with:

- The consumer receiver.
- The original first-slot chunk as a 32-bit quantity.
- The shared descriptor-buffer address.

If a second slot was submitted, this copy overwrites the scratch storage supplied to that submission **before the second slot is synchronized**.

The consumer result must equal the requested 32-bit quantity exactly. Any unequal result invokes F-7f008c1060db on status A with `0x22`, zero, zero. If quantity remains, the second slot is synchronized; status A is then selected.

After an exact consumer result, zero remaining quantity selects status A. Otherwise, processing advances to the second-slot phase.

### Second-slot phase

The function subtracts the second-slot chunk from the remaining quantity, performs a fresh source query and conversion for that chunk, advances the position, and calculates the next first-slot chunk.

If quantity remains, it submits the next first slot before synchronizing the second. This submission uses a fresh receiver and conversion, the shared scratch buffer containing a new first-descriptor snapshot, the advanced position, the address at `0x54`, and status A.

A nonzero return from this later first-slot submission selects status A immediately. The second slot is **not visibly synchronized** on this exit, and no explicit `0x22` update is made.

Otherwise, the function synchronizes the second slot and inspects status B.

- A zero inspection result selects status B immediately. A newly submitted first slot is **not** synchronized on this path.
- A nonzero result permits consumption using the second-slot chunk and a fresh second-descriptor snapshot in the shared scratch buffer.

When a new first slot has been submitted, that second-descriptor copy overwrites its submitted descriptor storage **before first-slot synchronization**.

An unequal consumer result updates status B through F-7f008c1060db with `0x22`, zero, zero. If remaining quantity is nonzero, the first slot is synchronized before status B is selected.

An exact consumer result returns to the first-slot phase. If the remaining quantity is now zero, that phase selects **status A**, not B. Consequently, an ordinary exact-completion path returns A even when the last consumed chunk used the second slot.

### Arithmetic and progress

The remaining quantity is decremented before synchronization and consumption of the corresponding chunk. It is not a count of successfully delivered quantity.

Submission conversion and position-advance conversion use separate fresh queries. The function does not require their results to agree:

- Submission uses only the low 16 bits.
- Position advancement uses the full 32-bit conversion result.

Position addition has no overflow check. Its behavior at signed 32-bit overflow remains documented_only.

A zero chunk limit with nonzero remaining quantity prevents numerical progress. If the dependency results continue permitting processing, the function can continue alternating zero-sized chunks indefinitely. No zero-progress guard is visible.

Statuses A and B are initialized once, not explicitly reset before slot reuse. Reuse semantics belong to the dependencies.

### Output and finalization

When A is selected, the function writes A’s first 16-bit field, then A’s second field, to consecutive output fields.

When B is selected, the order is:

1. Write B’s first field to the first output field.
2. Copy B’s second field into A’s local second field.
3. Write that local field to the second output field.

Thus selecting B also modifies A’s local representation before finalization.

After either output path, F-9b718979506d is called on B and then A. No further explicit output write follows those calls, although dependency effects are unknown.

The field copies do not establish an ownership transfer or guarantee that copied values remain meaningful after finalization.

## Side effects

Visible effects include dependency calls, local status and descriptor writes, final output writes, and passing mutable local and context-derived addresses to dependencies. The function does not directly modify context descriptor words.

Descriptor-buffer reuse creates an intra-invocation retention hazard. In particular:

- A second-slot submission can retain the shared buffer and subsequently observe first-descriptor contents written for first-slot consumption.
- A later first-slot submission can retain that same buffer and subsequently observe second-descriptor contents written for second-slot consumption.
- Further submissions and consumer calls continue reusing the same address.

Keeping the function active is therefore insufficient to guarantee stable submitted descriptor contents. Safe pointer retention requires an unavailable dependency contract governing when descriptors are copied, read, or no longer needed—not merely a lifetime guarantee until function return.

The initial submission’s buffer is separate and is not overwritten by these explicit scratch-buffer copies. Its retention requirements and any dependency-driven mutations remain unknown.

Some exits leave an operation without a visible corresponding synchronization. Neither cancellation nor safe completion is established. No explicit allocation, deallocation, rollback, or exception handling appears in the function; dependencies may nevertheless perform such operations.

## Acceptance examples

These are conditional static criteria, not executed tests. Numerical examples assume the stated totals are obtained without unresolved overflow.

1. **Capacity boundary.** Capacity values `65,535`, `65,536`, and `100,000` yield limits `32,767`, `32,768`, and `32,768`. Later capacity mutations do not change the saved limit.

2. **Zero total.** The initial first-slot submission still occurs after conversion of a zero chunk. If it returns zero, A is copied out without synchronization, inspection, or consumption. Finalization still occurs in B-then-A order.

3. **Two chunks and scratch identity.** With limit four, total eight, successful submissions, permitting inspections, and exact consumer results, the second submission precedes first-slot synchronization. Its descriptor address is the shared scratch address, distinct from the initial submission’s buffer. First-slot consumption overwrites that shared buffer before second-slot synchronization. Normal completion outputs A.

4. **Three chunks and reverse overwrite.** With limit four and total ten, quantities are four, four, and two. The third submission uses the shared buffer and precedes second-slot synchronization. Second-slot consumption then overwrites that buffer with the second descriptor before first-slot synchronization.

5. **Initial versus later submission failures.** Initial submission failure explicitly updates A with `0x22`. Second-slot submission failure synchronizes the first slot and selects B without that update. A later first-slot submission failure selects A without synchronizing the second slot.

6. **Second-slot inspection rejection.** If the next first slot has already been submitted and inspection of B returns zero, B is selected without synchronizing that newly submitted first slot.

7. **Consumer mismatch.** For a requested quantity of four, returns of three and five both cause the active status’s `0x22` update. There is no retry or partial-progress interpretation.

8. **Context extent.** No direct function access reaches beyond context byte `0x4f`. Slot-address formation and dependency calls still require separately valid pointer and storage contracts; neither safety nor a four-byte access at `0x58` follows from this direct-access bound.

9. **No progress.** Capacity zero or one produces a zero limit. With nonzero total and continuously permitting dependency results, successful zero-quantity processing need not terminate.
