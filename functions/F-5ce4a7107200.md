# F-5ce4a7107200

## Purpose

F-5ce4a7107200 conditionally processes a range represented by two opaque endpoint arguments against a state object. It has a special path that invokes a bulk-processing dependency and resets sentinel-related state. Otherwise, it repeatedly advances the first endpoint and invokes a per-element dependency until an endpoint comparison returns exactly one.

**Established static behavior:** the function writes an initial sentinel reference to a caller-provided output slot, performs endpoint comparisons, selects either the bulk-reset path or the iterative path, and returns a packed 64-bit value.

**Inferred intent:** the sentinel links, state field, advance operation, and per-element dependency are consistent with range erasure from a linked or tree-like container. That interpretation does not establish the container type, ordering rules, allocation policy, or destruction semantics.

This contract specifies the visible reads, writes, calls, and return construction. It does not attribute unobserved behavior to dependencies.

## Interface

### Arguments

The function accepts four arguments:

1. **Output-slot address.** An address at which the function writes a 32-bit reference. This address is also retained as the initial value of the low return component.
2. **State address.** A 32-bit address identifying an object with accessible fields at byte offsets 16 and 20.
3. **First-endpoint address.** An address passed to comparison and advance dependencies. On each iterative pass, its first 32-bit word is read directly.
4. **Second-endpoint token.** A 32-bit value passed unchanged as an argument to comparison dependencies. Its interpretation, including whether it denotes an address, is not established locally.

All addresses and stored references in the supplied representation are 32 bits. The function returns 64 bits.

### Local in/out cells

The function uses temporary 32-bit cells whose addresses are passed to dependencies:

- A comparison cell initialized from sentinel offset 8.
- A comparison cell initialized from the current sentinel reference.
- A result cell initially containing the state address.
- A candidate cell initially containing the output-slot address and subsequently replaced by each captured endpoint word.

The first two cells are separate from the state fields used to initialize them. A dependency may modify the cells it receives; no immutability guarantee is established.

### Return value

The return is a concatenation of two 32-bit bit patterns:

- **High 32 bits:** the current result cell on the iterative path; the freshly loaded sentinel reference on the bulk-reset path.
- **Low 32 bits:** the current candidate cell.

The construction preserves the component bit patterns. It is not arithmetic addition with sign extension.

On an iterative path with no iterations, the high component remains the original state address and the low component remains the original output-slot address, even though the output slot has already been assigned a sentinel reference. The returned pair must therefore not be assumed to duplicate the output slot.

### Preconditions

The function performs no explicit null, bounds, alignment, ownership, or structural validation.

For a defined execution, every direct access and every dependency access must be valid when performed. At minimum:

- The output slot must be writable for four bytes.
- The state fields used by the selected path must be readable or writable as appropriate.
- Sentinel-derived fields must be accessible whenever read or written.
- The first endpoint must expose a readable four-byte word whenever the loop body executes.
- Dependency-specific argument requirements must hold.

A zero state field at offset 20 does not prevent the initial sentinel accesses.

No non-aliasing requirement is explicitly checked. The ordinary descriptions below assume distinct state, output, and endpoint storage. With aliasing, earlier writes may change later reads, including the first endpoint’s contents or the state’s sentinel reference. Such effects are not prevented by the function.

## Behavior

### 1. Initial output and boundary comparison

The function first reads the reference at state offset 16 and writes that reference to the output slot.

It then reads state offset 16 again and reads the four-byte field at offset 8 of that referenced object. This value initializes the first local comparison cell.

Before calling a dependency, it initializes the result cell with the state address and the candidate cell with the output-slot address.

It calls **F-4cec57b703f5** with:

- The first-endpoint address.
- The address of the first local comparison cell.

The comparison result is treated as a 32-bit integer:

- Zero skips the remaining special-path checks.
- Any nonzero value proceeds to the second special-path comparison.

The initial output write occurs before this call. The sentinel reference used to initialize the comparison cell is obtained by a separate load, rather than by reusing the value already written to the output slot.

### 2. Second special-path comparison

If the first result is nonzero, the function reloads the reference at state offset 16 into a second local comparison cell.

It calls **F-4cec57b703f5** with:

- The second-endpoint token.
- The address of that second local comparison cell.

If this result is zero, the function proceeds to the iterative path without reading state offset 20 for the special-path decision.

If the result is nonzero, it reads the 32-bit field at state offset 20:

- Zero proceeds to the iterative path.
- Any nonzero bit pattern selects the bulk-reset path.

The field is not checked for positivity. A value whose signed interpretation is negative still satisfies the nonzero condition.

The special path therefore requires three conditions: a nonzero first comparison, a nonzero second comparison, and a nonzero state field. The comparisons are not required to return exactly one here.

### 3. Bulk-reset path

The function reloads the sentinel reference from state offset 16, reads the field at sentinel offset 4, and calls **F-0949893ba6a1** with:

- The state address.
- That field’s 32-bit value.

The dependency’s return value is not used.

After the call returns normally, the function performs these writes in order:

1. Assign the current sentinel reference to the field at sentinel offset 8.
2. Write zero to the field at sentinel offset 4.
3. Assign the current sentinel reference to the field at sentinel offset 12.
4. Write zero to state offset 20.

The sentinel reference is reloaded for these operations. The function does not preserve and universally reuse the sentinel value that existed before the dependency call. If the dependency changes state offset 16, subsequent operations use the changed reference.

Within a single assignment, the supplied representation does not establish an ordering between separate operand reads. The ordering of the four completed writes above is established.

Finally, the function reloads state offset 16, writes that reference to the output slot, and returns it as the high 32-bit component. The low component is the candidate cell, which has not entered the per-element processing path and still contains the original output-slot address.

This path does not call the endpoint-advance dependency or the per-element dependency.

### 4. Iterative path

The function repeatedly calls **F-4cec57b703f5** with the original first-endpoint address and original second-endpoint token.

Here the termination condition is narrower than on the special path:

- A result of exactly one terminates the loop.
- Every other result, including zero and other nonzero values, executes an iteration.

For each iteration, the observable sequence is:

1. Read the first 32-bit word at the first-endpoint address and retain its bit pattern.
2. Call **F-8f8f82c1972b** with the first-endpoint address.
3. Assign the retained word to the candidate cell.
4. Call **F-0fb9b308b3a3** with the address of the result cell, the state address, and the address of the candidate cell.
5. Read the result cell and write its value to the output slot.
6. Perform the next loop comparison.

Thus, endpoint advancement is requested before per-element processing. The candidate passed to per-element processing is the word captured before advancement, not a fresh read of the advanced endpoint.

The result and candidate cells are passed by address. The per-element dependency may change either. The function ignores its ordinary return value and uses the cells instead.

The result cell is initialized only once, with the state address. It is not reset between iterations. The candidate cell is overwritten with the newly captured endpoint word before each per-element call.

When a loop comparison returns exactly one, the function returns the current result and candidate cells as the high and low halves respectively. It performs no additional output-slot write on loop termination.

### 5. Completion and failure boundaries

There is no explicit success code, error code, rollback, iteration bound, or recovery branch.

If a dependency does not return, subsequent operations do not occur. If a dependency changes state or endpoint storage, later operations observe those changes through the reads described above.

Termination is not guaranteed locally. In particular, a comparison that continually returns a nonzero value other than one does not terminate the loop.

## Side effects

### Direct writes

The function directly writes:

- The output slot during initialization.
- The output slot after every completed per-element dependency call.
- The output slot once more at completion of the bulk-reset path.
- Sentinel fields at offsets 8, 4, and 12, and the state field at offset 20, on the bulk-reset path.

It does not directly write endpoint storage. Endpoint mutation may occur through dependencies.

### Dependency-mediated effects

Dependency calls may modify endpoint storage, the state object, reachable objects, globals, or local cells whose addresses they receive. Their implementations are not supplied here.

The function contains no explicit allocation or deallocation operation. The bulk and per-element dependencies may release resources, but that is **documented_only**, not established.

No ownership transfer is proven merely by passing an address or reference. Conversely, callers must not assume a referenced object remains live after a dependency call.

The temporary cells are local to this invocation. Whether dependencies retain their addresses is unknown; this function provides no evidence of a valid lifetime beyond its return.

## Acceptance examples

The following are conditional static examples, not executed tests. Except where stated otherwise, assume valid, disjoint storage and dependencies that return normally without unrelated mutations.

### Immediate loop termination

Suppose the first special-path comparison returns zero and the first loop comparison returns one.

Expected behavior:

- The output slot receives the initial sentinel reference.
- Neither advancement nor per-element processing occurs.
- The return’s high half is the original state address.
- The return’s low half is the original output-slot address.
- No sentinel-reset writes occur.

### Bulk processing with a noncanonical comparison result

Suppose the first comparison returns two, the second returns negative one, and state offset 20 contains a nonzero value.

Expected behavior:

- Both comparison results satisfy the special-path nonzero tests.
- The bulk dependency is called.
- Sentinel reset writes occur in the specified order.
- The output slot receives the final sentinel reference.
- No loop comparison or per-element processing occurs.

This distinguishes special-path truth testing from the loop’s exact-one termination rule.

### Zero state field

Suppose both special-path comparisons return one, but state offset 20 is zero.

Expected behavior:

- The bulk dependency is not called.
- No direct sentinel-reset writes occur.
- Execution enters the loop and obtains a fresh comparison result.
- The earlier comparison results do not themselves terminate iteration.

### One processed element

Suppose the special path is not selected. The first loop comparison returns zero, the first endpoint initially contains reference A, and the advance dependency changes that endpoint to reference B.

Suppose the per-element dependency writes reference R into the result cell and reference C into the candidate cell. The next comparison returns one.

Expected behavior:

- The candidate supplied to the per-element dependency initially contains A, not B.
- The output slot is assigned R after that dependency returns.
- The return has R in its high half and C in its low half.

### Non-one loop result

Suppose a loop comparison returns two.

Expected behavior: the function executes an iteration. Treating this result as terminal merely because it is nonzero would violate the observed behavior.

### Sentinel replacement during bulk processing

Suppose the bulk dependency changes state offset 16 to another valid sentinel reference.

Expected behavior: subsequent reset operations and the final output assignment reload that field and use the replacement reference. Reusing the original sentinel throughout would not preserve the observed reads.
