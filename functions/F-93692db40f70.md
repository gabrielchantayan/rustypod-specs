# F-93692db40f70

## Purpose

F-93692db40f70 conditionally records an identifier and replaces a per-entry state word with a requested five-bit value. When the full stored word changes, it emits events for changed positions among bits 0–4, then performs downstream notifications.

Acceptance requires both:

- An indirect query result equals the supplied identifier at full 32-bit width.
- The requested state has no bits set above bit 4.

These checks do not guard every write equally. A matching identifier causes a one-byte write before state validity is checked.

The function returns a 32-bit status: **0** when both checks pass, including an unchanged state, or **4** when either check fails. Dependency return values do not change this status.

This contract describes static evidence only. It does not establish dependency success, global preservation, memory ownership, or application-level meanings for the notifications.

## Interface

### Inputs

| Input | Representation | Role |
|---|---|---|
| Entry selector | Signed 32-bit integer | Selects an identifier byte and a state record. |
| Identifier | Signed 32-bit integer | Compared with the indirect query result; its low eight bits are stored on equality. |
| Requested state | Unsigned 32-bit integer | Accepted only in the inclusive range 0–31. |

The function performs no explicit selector bounds check. Negative selectors are not rejected merely because they are negative.

The requested state is validated, not truncated. For example, 32 and `0xffffffff` are rejected even though their low five bits could be interpreted independently.

### Return value

- **0:** Identifier equality and five-bit validation both succeeded.
- **4:** Identifier equality failed, or the requested state was outside 0–31.

These are normal-return results. Invalid memory accesses, invalid indirect targets, or dependencies that do not return normally are not translated into status 4.

### Referenced storage and layouts

The visible address-and-word model is 32-bit.

| Storage role | Addressing or layout |
|---|---|
| Identifier-byte region | A global base plus the entry selector, addressing one byte. |
| State-record region | A global base plus a global stride factor multiplied by the selector and by four. |
| State field | One 32-bit word at byte offset `0x80` from the selected record. |
| Notification value | A global 32-bit word. |
| Notification context | A globally stored address designating an object with a 32-bit handle at byte offset `0x14`. |

No bounds or overflow check accompanies either selected address. The state field physically occupies a full 32-bit word; only the requested replacement is restricted to five bits.

The source does not establish byte order, alignment guarantees, region sizes, or a portable result for overflowing address arithmetic. The multiplication by four is established; any higher-level meaning of the stride is not.

### Preconditions

Each executed operation requires valid accessible storage or a valid callable target:

- The provider result must permit reading its first 32-bit word as a dispatch-table address.
- That table must provide a callable entry at byte offset `0x110`.
- Identifier equality requires the selected identifier byte to be writable.
- Acceptance requires the selected state word to be readable.
- A changed state requires that word to be writable.
- Executed notification paths require the applicable context objects and handle fields to remain accessible.

The function does not check these preconditions. It also does not establish that its separately described storage roles are disjoint.

## Behavior

### 1. Obtain an object and query it

The function first calls **F-cdd33263ee89**, with no visible arguments.

It reads a dispatch-table address from the first word of the returned object. It invokes the callable entry at byte offset `0x110` in that table, supplying:

1. The returned object address.
2. The integer 1.

The resulting 32-bit value is compared with the supplied identifier at full width.

If they differ, the function returns 4 without an explicit identifier-byte write, selected-state access, event call, or downstream notification. Effects of the provider and indirect query are still possible.

### 2. Store the identifier byte, then validate the requested state

On equality, the function writes the identifier’s low eight bits to the selected identifier byte.

This write precedes validation of the requested state. An invalid requested state therefore does not undo or prevent the identifier-byte write.

The function then rejects any requested state with one or more of bits 5–31 set. Such a request returns 4 without entering the state-update path.

Otherwise, the normal-return status is 0.

There is no visible restriction requiring the identifier itself to fit in one byte. A query result and identifier of 257 compare equal, and the stored byte is 1.

### 3. Compare the full stored word and install a replacement

For an accepted request, the function calculates the record address and reads the 32-bit state word at offset `0x80`.

It compares old and requested states through their full-width exclusive-or difference.

If that difference is zero:

- The identifier-byte write has already happened.
- The state word is not rewritten.
- No event or downstream notification is issued.
- The function returns 0.

If the difference is nonzero, the function writes the entire requested 32-bit value to the state field before issuing any event.

There is no rollback around subsequent calls. A dependency may therefore observe the replacement already installed.

The original record address is retained for the later state reread; changing the global record base or stride during a dependency does not redirect that reread.

### 4. Scan changed positions 0–4

After a nonzero full-word difference, the function scans low-order bit positions in ascending order, beginning at position 0.

For each examined position whose old and requested bits differ, it calls **F-c6c589453fa8** with:

1. Integer 2.
2. Integer 1.
3. An address to reused temporary payload storage.
4. Byte count 12.

The payload construction has this layout:

| Byte offset | Width | Assigned value |
|---|---:|---|
| 0 | 4 bytes | Word value 1 |
| 4 | 4 bytes | Current zero-based bit position |
| 8 | 1 byte | Requested value of that bit, either 0 or 1 |
| 9–11 | 3 bytes | No assignment established by the visible construction |

The advertised length is 12 bytes, but only the first nine bytes receive visible assignments for an event. The final three bytes must not be specified as zero or as semantically irrelevant padding.

Each event reports the new bit value, not the old value. Event order is strictly increasing by bit position.

The scan stops when no unexamined difference bits remain or after examining position 4. It never emits an event for position 5 or above. A nonzero difference always causes at least one scan iteration.

The old state is not validated as five-bit data. A high-order old bit can therefore trigger a full-word replacement and downstream notifications without producing any low-five-bit event.

### 5. Capture notification globals during the scan

On every executed scan iteration, after any event for that position, the function reads:

1. The global notification-context address.
2. The global notification value.

These reads also occur on iterations that issue no event.

The address and value retained from the final executed iteration are used by the conditional second notification. Because an event dependency can change globals, these retained values need not equal their entry-time values.

The scan uses the already computed difference and requested-bit progression. It does not reread the selected state to decide which bit events to emit.

### 6. Perform the first downstream notification

After the scan, the function:

1. Freshly reads the global notification value into a temporary 32-bit word.
2. Writes 137, hexadecimal `0x89`, into another temporary 32-bit word.
3. Obtains the handle at offset `0x14` through the current global notification-context address.
4. Calls **F-704f99fd5e22**.

The call arguments are:

1. That handle.
2. The entry selector.
3. The address of the temporary containing the freshly read notification value.
4. The address of the temporary containing 137.
5. Integer 0.

This call occurs for every accepted nonzero full-word difference, including replacement with zero and changes confined to old high-order bits.

Its notification value is freshly read after the scan, rather than taken from the value retained during the final scan iteration. Its context lookup likewise uses the current global address rather than the retained address.

### 7. Reread the state and conditionally perform the second notification

After **F-704f99fd5e22** returns, the function rereads the 32-bit state word at the originally calculated record address.

If that word is zero, it omits both the following payload-storage write and the second notification.

If the word is nonzero, it performs these operations in order:

1. Writes the 32-bit value **200**, hexadecimal `0xc8`, to the first word of the reused event-payload storage.
2. Reads the handle at offset `0x14` through the context address retained during the final scan iteration.
3. Calls **F-43ce968102ca** with that handle, the entry selector, the retained notification value, integer 137, and integer 0.

The value 200 is **not a direct argument** to this call. The call also receives no explicit payload pointer. Nevertheless, the write cannot be discarded from the behavioral contract: an earlier event dependency received that storage address, its retention behavior is unknown, and the storage remains live during this later call.

The write of 200 also occurs when this path is reached without any earlier bit event.

The second call is controlled by the reread state, not simply by whether the requested replacement was nonzero. Dependencies can alter that condition after the replacement.

Its context address and notification value come from the final scan iteration. The handle itself is read after the first downstream notification, so changes to the retained context object’s handle can affect it.

The function returns 0 if control returns normally.

## Side effects

### Explicit writes

The visible function can write:

- One identifier byte on every full-width identifier match.
- One full 32-bit state replacement on an accepted full-word change.
- Event payload fields before each bit-event call.
- Two temporary notification words before **F-704f99fd5e22**.
- The 32-bit value 200 to the event payload’s first word when the post-notification state reread is nonzero.

The final payload write changes the same first word that held 1 for an event. It does not construct another 12-byte event payload or issue another event.

No allocation, deallocation, or persistent ownership transfer is visible.

### Temporary storage and retention

All event calls use the same temporary payload storage. A dependency must not be assumed to receive an independent allocation for each event.

The payload storage remains live through the later conditional notification. If an earlier dependency retains its address and that address is accessed during **F-43ce968102ca**, the first word can expose the later value 200, subject to intervening dependency effects.

This is a possible observation, not proof that a dependency actually retains or reads the address. No ownership or retention contract is supplied. In particular, the source does not establish a right to dereference invocation-local storage after the invocation ends.

The two temporary words passed to **F-704f99fd5e22** likewise have no established retention, copying, or ownership contract.

### Dependency effects, errors, and reentrancy

The function supplies no synchronization, transaction boundary, reentrancy guard, or rollback. Dependencies must not be assumed to preserve globals, selected state, context contents, or temporary arguments.

There are no visible null checks, dependency-error branches, or exception-recovery paths. Faults or non-returning dependencies can prevent the specified normal return. Status 4 is a rejection result, not a general error-recovery result.

## Acceptance examples

These are conditional examples, not executed tests. Unless stated otherwise, assume valid, nonoverlapping relevant storage, normal dependency returns, and no dependency mutation of the relevant state, globals, or temporary storage.

1. **Identifier mismatch**  
   A query result of 6 and identifier of 7 yield status 4. No explicit identifier-byte write, state update, event, or downstream notification occurs.

2. **Matching identifier with invalid state**  
   A query and identifier both equal to 257, with requested state 32, cause byte value 1 to be stored. The function returns 4 without entering the state-update path.

3. **Accepted unchanged state**  
   Replacing stored state 5 with 5 returns 0 after the identifier-byte write. There is no state rewrite, event, downstream notification, or payload write of 200.

4. **Three changed bits**  
   Replacing 2 with 5 writes state 5 first. Events follow for positions 0, 1, and 2, carrying 1, 0, and 1 respectively. After the first downstream notification, the nonzero state reread causes the payload’s first word to become 200 before the second notification.

5. **Clearing the state**  
   Replacing 5 with 0 emits events for positions 0 and 2, both carrying 0. The first downstream notification occurs. If the state remains zero, neither the write of 200 nor the second notification occurs.

6. **High-order difference with zero replacement**  
   Replacing `0x80000000` with 0 overwrites the full word and emits no low-five-bit event. The first downstream notification occurs. If the word remains zero, the later payload write and second notification are omitted.

7. **High-order difference with nonzero replacement**  
   Replacing `0x80000001` with 1 emits no bit event because bits 0–4 are unchanged. The first downstream notification occurs, followed by the payload first-word write of 200 and the second notification if the word remains 1. No earlier event need have exposed the payload address.

8. **Dependency changes the final condition**  
   A nonzero request does not guarantee the second notification. If a dependency makes the selected word zero before its final reread, the write of 200 and second call are omitted. Conversely, a zero request can reach both if a dependency makes the word nonzero.

9. **Retained payload address and context**  
   Suppose an event dependency retains the payload address, and the state remains nonzero after the first downstream notification. During the second notification, access through that retained address can observe first-word value 200. If the first notification also replaces the global context address, the second still reads its handle through the context address retained during the final scan iteration.
