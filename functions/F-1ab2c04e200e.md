# F-1ab2c04e200e

## Purpose

F-1ab2c04e200e traverses a linked, tagged structure and appends selected node addresses to a record collection held by a caller-supplied context.

A node whose tag equals the supplied selector is treated as a traversal node: its child link is processed recursively, then traversal continues through its continuation link. A node whose tag differs from the selector is appended as a single record, after which that invocation returns. A null node ends an invocation without appending.

The function can expand the collection’s backing storage. An unsuccessful expansion sets an error byte reachable through the context and returns zero from that invocation. Recursive return values are not checked, so a failure in a descendant does not necessarily stop an ancestor’s traversal or determine its return value.

The return value is deliberately described as a raw 32-bit result. Depending on the path, it represents the context address, a previous record count, or zero. It is not a uniform success indicator.

## Interface

### Inputs

The function receives three values:

| Input | Representation | Meaning |
|---|---|---|
| Collection context | Address in the supplied 32-bit memory model | Mutable collection metadata and embedded storage |
| Current node | Address, possibly zero | Starting point for this invocation |
| Selector | Unsigned 32-bit integer | Value compared with each node’s unsigned 8-bit tag |

The source accesses addresses and context fields as 32-bit quantities. Node tags and the failure flag are 8-bit quantities; one record field is written as a 16-bit quantity.

The widths below describe the supplied representation, not a portable host-language layout. Byte order is not established.

### Context layout

Offsets are byte offsets from the context address.

| Offset | Width | Observed role |
|---|---:|---|
| +0 | 32 bits | Address used to reach the error-reporting object |
| +4 | 32 bits | Not accessed by this function |
| +8 | 32 bits | Current record count |
| +12 | 32 bits | Recorded capacity |
| +16 | 32 bits | Backing-storage address |
| +20 | 32 bits | Not accessed by this function |
| +24 onward | Unspecified extent | Embedded-storage address used when deciding whether to release the previous backing storage |

The extent of the embedded storage is unknown. Its address is established by the comparison against the context address plus 24; that comparison alone does not establish its usable capacity.

### Node layout

| Offset | Width | Observed role |
|---|---:|---|
| +0 | 8 bits | Tag |
| +8 | 32 bits | Child address, accessed only for a matching tag |
| +12 | 32 bits | Continuation address, accessed only for a matching tag |

Other node bytes are not directly accessed.

### Appended-record layout

Each record occupies 40 bytes. The function initializes only these fields:

| Record offset | Width | Written value |
|---|---:|---|
| +0 | 32 bits | Address of the selected node |
| +4 | 16 bits | All bits set: 0xffff |
| +12 | 8 bits | Zero |
| +16 | 32 bits | Context address |

The remaining record bytes are not initialized by the explicit record writes. Their values are not specified.

### Return value

The raw result is:

- The context address when traversal reaches a null current node.
- Zero when this invocation’s storage acquisition fails.
- The record count immediately before an append when this invocation appends a node.

Consequently, appending the first record returns zero despite completing the append. A nonzero result does not prove that recursive processing had no failures.

### Preconditions for defined use

Every address actually accessed must identify suitably accessible memory for the relevant width and operation. In particular:

- A nonnull current node must permit reading its tag.
- A matching node must also permit reading its two links.
- A nonmatching node requires a readable and writable context and a writable destination record.
- The expansion-failure path requires the error-reporting pointer chain to be valid.
- Any previous storage passed to a dependency must satisfy that dependency’s requirements.

A null current node is handled before any context dereference. That path can therefore return a zero or otherwise unusable context address unchanged.

No validation establishes count/capacity consistency, storage bounds, acyclicity, address arithmetic safety, or allocator compatibility.

## Behavior

### Traversal and selection

At the beginning of each iteration, the function checks whether the current node address is zero. If so, it returns the context address immediately.

Otherwise, it reads the node’s unsigned 8-bit tag and compares its numerical value with the complete unsigned 32-bit selector. The selector is not truncated to eight bits. A selector greater than 255 therefore cannot match any tag.

For a matching tag:

1. The child address at node offset +8 is read.
2. F-1ab2c04e200e is called recursively with the same context and selector and that child address.
3. The recursive result is discarded.
4. After the recursive call returns, the continuation address at offset +12 of the matching node is read.
5. Processing continues with that address.

The continuation is not read before the recursive call. If recursive processing or a dependency changes it, the later read can observe that change.

For a nonmatching tag, traversal stops and that node is appended. Neither its child nor its continuation link is read by the explicit traversal logic.

This gives child-before-continuation ordering for matching nodes. It does not enumerate every descendant of every selected node: a nonmatching node terminates its invocation’s traversal after being appended.

There is no visited-node tracking, recursion-depth limit, or iteration limit. Matching-link cycles can cause nontermination or exhaustion of execution resources.

### Capacity decision

Before appending, the function compares capacity with count using signed 32-bit interpretations:

- If signed capacity is greater than signed count, it proceeds directly to append.
- If signed capacity is less than or equal to signed count, it attempts expansion.

The signed interpretation is material. For example, a capacity with its highest bit set is treated as negative in this comparison, even though the same stored bits subsequently participate in size arithmetic.

### Expansion

The function saves the current backing-storage address and calls F-391e3d30e634 with a size derived from the capacity:

- Requested size: capacity multiplied by 80 bytes.
- Existing-record transfer size: count multiplied by 40 bytes.

The supplied 32-bit operations provide no explicit overflow checks. Products can lose high bits; no larger mathematical result is established by the source.

The acquisition result is written into the context’s backing-storage field before it is checked for zero.

If the result is zero:

1. The function reads the address stored at context offset +0.
2. It reads a further 32-bit address from offset +0 of that object.
3. It writes the byte value 1 at offset +30 from the second address.
4. It restores the previously saved backing-storage address.
5. It returns zero.

There is no explicit count or capacity update on this failure path. The temporary zero in the backing-storage field precedes the error-byte write and the subsequent restoration.

If acquisition returns nonzero:

1. X-01 is called with the acquired address, the saved previous address, and the transfer size.
2. If the previous address differs from context address plus 24, F-94cb53877c15 is called with that previous address.
3. The capacity field is doubled with a 32-bit left shift.
4. Appending proceeds.

The function performs no explicit check of a result from X-01 or F-94cb53877c15. It also does not independently verify that the acquired region is large enough for the transfer or subsequent append.

For an ordinary positive capacity \(C\), doubling produces \(2C\) records of 40 bytes each, matching the requested \(80C\) bytes. This consistency is an inferred design intent, not a guarantee for overflowed, negative-interpreted, zero, or otherwise inconsistent metadata.

Dependency calls occur between metadata accesses. Later reads of count, capacity, and backing storage must not be assumed to reproduce earlier values if a dependency can mutate the context. In particular, the capacity doubled after transfer and possible release is the value present then.

### Record append

After any successful expansion, or immediately when expansion is unnecessary, the function:

1. Reads the current 32-bit count.
2. Computes a record address from the current backing-storage address plus count multiplied by 40.
3. Writes count plus one to the context’s count field.
4. Writes the selected node address at record offset +0.
5. Writes zero at record offset +12 as an 8-bit value.
6. Writes the context address at record offset +16.
7. Writes 0xffff at record offset +4 as a 16-bit value.
8. Returns the count captured before the increment.

The count is therefore published before the record fields are initialized. The writes are not established as atomic or synchronized.

Record-address arithmetic and count increment have no explicit overflow protection. Under inconsistent metadata, wraparound or an invalid destination is possible.

These steps describe the explicit access order. If context, node, error-reporting objects, and backing storage overlap, earlier writes can affect later accesses. No non-aliasing guarantee is established.

## Side effects

The function can change:

- The context’s record count.
- The context’s recorded capacity.
- The context’s backing-storage address.
- The explicitly initialized fields of appended records.
- The error byte reached through the context’s two-address chain.
- Memory and external state affected by dependencies.

Recursive processing can append multiple records before an outer invocation returns. Such changes are not rolled back if a later append fails.

The function stores node addresses; it does not explicitly copy node contents, retain nodes through a separate operation, or release nodes.

The previous backing-storage address is passed to F-94cb53877c15 unless it equals the embedded-storage address. This establishes a release-like call and an embedded-storage exemption, but not the callee’s actual ownership semantics. The caller’s obligations for node lifetime, context lifetime, and final collection disposal remain unknown.

No error byte is explicitly cleared. Successful processing can therefore leave an earlier failure indication intact.

## Acceptance examples

These are conditional static acceptance cases, not results of executed tests. Unless stated otherwise, memory is valid, relevant objects do not overlap, arithmetic does not overflow, and dependencies do not unexpectedly mutate the context.

### Null starting node

Given a null current node, the result equals the supplied context address. No context or node memory is explicitly accessed, and no dependency is called.

### First append without expansion

Given count 0, capacity 1, valid backing storage, and a node whose tag differs from the selector:

- Count becomes 1.
- The first record receives the four specified field values.
- No growth dependency is called.
- The raw result is zero.

This case distinguishes a successful first append from interpreting every zero result as failure.

### Selector wider than the tag

Given selector 256 and a nonnull node, the node cannot match regardless of its 8-bit tag. Subject to storage success, it is appended directly. Its child and continuation links are not read by the traversal logic.

### Child-before-continuation ordering

Given a matching root whose child and continuation each identify nonmatching nodes, with room for two records:

- The child node is appended first.
- The continuation node is appended second.
- Neither nonmatching node’s own links are traversed.
- If the initial count is zero, the outer invocation returns 1, the pre-append count for its continuation node.

### Matching node with no links

Given a matching node with null child and continuation addresses:

- The child invocation returns the context address.
- The outer invocation subsequently reaches its null continuation and also returns the context address.
- No record is appended.

### Ordinary expansion

Given count 2, capacity 2, a valid existing two-record buffer, and successful acquisition:

- The acquisition request is 160 bytes.
- X-01 receives a transfer size of 80 bytes.
- The previous address is passed to F-94cb53877c15 only if it differs from context plus 24.
- Capacity becomes 4.
- The new record is placed at byte offset 80 in the resulting backing storage.
- Count becomes 3 and the raw result is 2.

### Acquisition failure

Given a node requiring append and metadata requiring expansion, if F-391e3d30e634 returns zero:

- The error byte is written to 1 before backing-storage restoration.
- The saved backing address is restored.
- No new record is explicitly initialized.
- That invocation returns zero.

### Recursive failure does not stop the ancestor

Given a matching parent whose child invocation encounters acquisition failure, the parent still reads and processes its continuation after the child returns. A later append can succeed if the dependency outcome permits it. The parent’s final result can then be nonzero while the error byte remains 1.

### Signed capacity comparison

Given count 0 and capacity bits 0x80000000, the signed comparison selects expansion rather than the direct-append path. No safe-size or successful-allocation conclusion follows: the size arithmetic is unchecked.

## Uncertainties

The following remain **documented_only**:

- Complete context, node, and record schemas, including padding and unused fields.
- Embedded-storage extent and initial metadata invariants.
- Target byte order and alignment requirements.
- Exact dependency implementations and their effects on memory, globals, and ownership.
- Whether X-01 guarantees the intended preservation of existing records.
- Intended interpretation of the mixed return-value conventions.
- Valid selector domain, beyond its observed unsigned 32-bit representation.
- Whether cycles, overlapping objects, inconsistent metadata, or extreme counts are excluded by callers.
- Concurrency, signal-handler visibility, atomicity, and reentrancy requirements.
- Behavior after inaccessible-memory accesses, exhausted recursion resources, or violations of a dependency’s requirements.
- Whether the supplied source representation omits behavior relevant to these cases.

Zero capacity is not repaired explicitly. An expansion request based on zero remains zero, and doubling zero remains zero. If acquisition nevertheless returns a nonzero address, the function proceeds toward an append without establishing usable storage.
