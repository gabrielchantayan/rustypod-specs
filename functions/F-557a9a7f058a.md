# F-557a9a7f058a

## Purpose

F-557a9a7f058a performs an ordered reset of selected fields in a caller-supplied memory region, invokes two dependencies using four stored 32-bit values, and conditionally updates a stored range-ending address.

Established behavior consists of:

- Clearing one leading byte.
- Passing three stored values to F-097ecc469c2a, in order.
- Passing a fourth stored value to F-58ba61416cc9, then clearing its field.
- Clearing six regularly spaced 16-bit fields.
- Comparing two stored range addresses and, if they differ, traversing addresses in two-byte steps before updating the ending field.

Neither range loop executes a dereference through a range cursor. This is not a guarantee that bytes belonging to the range remain unaccessed: the range may overlap the supplied header, whose fields are read and written independently of the range traversal. Dependencies may also access overlapping memory through aliases.

“Reset,” “cleanup,” and “emptying a range” are inferred intent, not established object or ownership semantics. The dependency calls are not established deallocations.

## Behavior

### Leading reset and dependency calls

The first direct effect is an 8-bit zero store at `H + 0x00`.

The function then calls F-097ecc469c2a three times:

1. With the 32-bit value read from `H + 0x04`.
2. With the 32-bit value read from `H + 0x08`.
3. With the 32-bit value read from `H + 0x0C`.

Each argument is read for its own call, after the preceding call returns. The function does not capture all three arguments before beginning the calls.

Next, it reads the 32-bit value at `H + 0x10` and calls F-58ba61416cc9 with that value. After normal return, it writes a 32-bit zero to `H + 0x10`.

Consequences of this ordering include:

- An earlier dependency can change a later argument through an alias before that argument is read.
- The fourth argument need not equal the value present at function entry.
- A dependency-written value at `H + 0x10` is overwritten by the subsequent zero store, provided execution reaches that store.
- The leading byte is not cleared again after any dependency call.
- The fields at `0x04`, `0x08`, and `0x0C` are not directly cleared.

No dependency result is inspected. A zero-valued argument does not suppress its call. No local recovery branch handles a dependency that fails to return normally.

If any of these header addresses also identify range bytes, the corresponding header access is also an access to those range bytes. The access remains present regardless of the absence of range-cursor dereferences later.

### Six 16-bit resets

After clearing `H + 0x10`, the function performs six individual 16-bit zero stores, in this order:

`0x1A`, `0x26`, `0x32`, `0x3E`, `0x4A`, `0x56`.

All four dependency calls precede these stores. There is no bulk clearing of the intervening bytes.

These stores can modify range bytes if the range overlaps their header locations.

### Capturing the range addresses

After the six resets, the function reads the 32-bit address at `H + 0x68`, then the 32-bit address at `H + 0x6C`. Denote the saved values by **B** and **E**, respectively.

They are therefore values observed after all dependency calls and reset stores, not necessarily the values present on entry.

If **B** equals **E**, the function returns without a store to `H + 0x6C`. This early return skips only the remaining range-processing phase.

### Unequal-range processing

When **B** and **E** differ, a represented copy loop is encountered first. Its source cursor and stopping address are both initialized from the same saved ending address. Its entry condition is therefore false. It executes no iterations and performs no source or destination dereference.

A second loop starts its cursor at **B**. It compares that cursor with the current 32-bit address read from `H + 0x6C`. After each unequal comparison, it advances the cursor by two bytes and repeats.

This loop has the following established properties:

- The ending field is reread for each comparison.
- The saved **E** is not a fixed stopping value for this loop.
- No payload address is dereferenced through the cursor.
- There is no dependency call inside the loop.
- There is no explicit iteration limit or malformed-range error.

The repeated reads of `H + 0x6C` are still header reads. If that field lies within the range, those reads also access range bytes. Thus “address-only traversal” describes the cursor’s use, not a blanket absence of accesses to memory numerically within the range.

If the ending field remains stable and the distance is a valid, even, forward byte distance, the cursor reaches **E** in two-byte steps. An odd distance does not become acceptable merely because the later arithmetic masks off one bit. Completion for malformed, wrapping, or externally changing ranges is not generally established.

### Final ending-field update

After the traversal terminates, the function reads `H + 0x6C` again. Call this newly read 32-bit value **R**.

The stored result is:

**R − ((E − B) masked with `0xFFFFFFFE`)**, at 32-bit width.

The mask clears the least significant bit of the saved-address difference. The calculation uses byte-address differences; it does not divide by two or multiply by an element size. The final stored bit pattern follows 32-bit subtraction, including reduction to 32 bits where applicable.

For a stable range whose valid byte distance is even, **R = E**, and the resulting ending address is **B**. This does not justify replacing the behavior generally with an unconditional assignment of **B**: the actual update uses saved addresses and a fresh ending-field read.

The final write is to the header ending field. If that field overlaps the range, the write also changes range bytes.

## Side effects

### Direct accesses and writes

On a normally completed invocation, the direct writes occur in this order:

1. An 8-bit zero at `H + 0x00`.
2. A 32-bit zero at `H + 0x10`, after F-58ba61416cc9 returns.
3. Six ordered 16-bit zeros at the listed offsets.
4. A 32-bit result at `H + 0x6C`, only when **B ≠ E** and the traversal completes.

The function does not directly store to `H + 0x68`, and neither range loop executes a range-cursor dereference.

These are address-specific guarantees, not guarantees about a disjoint payload region. Header reads and writes can access payload bytes through overlap. For example, if **H = B**, the leading byte clear writes the first byte at the range beginning.

### Dependency effects and ownership

The dependency bodies are unavailable. Their calls may have additional effects, including changes to the header, range bytes, unrelated memory, or global state. They may invoke callbacks or fail to return normally.

The function contains no explicit allocation. It does not establish whether any argument transfers ownership, identifies owned memory, or is released by a dependency.

Neither the lack of executed range-cursor dereferences nor the local absence of allocation proves that range storage is unchanged, retained, or released across the complete invocation.

### Partial completion and repetition

There is no rollback. If a dependency does not return normally, an access fails, or the traversal fails to terminate, earlier effects are not undone by this body.

Repeated invocation is not established as safe or idempotent. The three fields at `0x04`, `0x08`, and `0x0C` are passed again unless otherwise changed. The field at `0x10` is passed as zero on a later invocation if it remains cleared. Dependency effects may make repetition materially different.
