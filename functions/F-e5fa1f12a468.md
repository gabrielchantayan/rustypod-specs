# F-e5fa1f12a468

## Purpose

F-e5fa1f12a468 obtains a node address from a dependency, conditionally copies an eight-byte payload into that node, increments a tree-associated count, writes attachment links, performs color-based structural repair, and finally writes the originally obtained address to a caller-supplied result slot.

The visible operations are consistent with red–black tree insertion using a header containing a root link and cached extrema. That is inferred intent. The body does not establish node initialization, dependency correctness, preservation of tree invariants, or continued reachability or lifetime of the published node.

This contract describes static evidence from the supplied representation. No runtime tests have been performed.

## Behavior

### Node acquisition and payload transfer

The first dependency call is F-16423b2a3bda with the tree address. Its returned address is retained for attachment and eventual publication.

The function tests whether that address plus 16 is nonzero. If so, it performs these transfers in order:

1. Read four bytes from the payload address and write them at node offset +16.
2. Read four bytes from payload offset +4 and write them at node offset +20.

The second source read occurs after the first destination write. If storage overlaps, the first write can affect the second value copied.

The condition is not a null check on the returned node address. A null result does not select an error path: under ordinary numeric address interpretation, the copy would target addresses 16 and 20. Later attachment and repair operations also require usable node storage.

Under wrapping 32-bit address arithmetic, an obtained address of `0xfffffff0` would make the tested sum zero and skip the payload transfers. The underlying pointer-arithmetic semantics are unresolved; this is not an established supported sentinel.

The body does not visibly initialize the obtained node’s color or child links.

### Count update

After the payload-transfer stage, the function reads the four-byte count at tree offset +20, adds one, and writes the result back.

This precedes comparison, attachment, repair, and publication. There is no visible overflow guard, capacity check, or rollback. Under wrapping 32-bit arithmetic, `0xffffffff` would become zero. Whether that wrap is defined by the original execution environment remains **documented_only**.

If a later operation fails to complete normally, the count may already have changed.

### Attachment selection

The function reads the header address at tree offset +16. Left attachment is selected without comparison when either:

- The supplied parent equals that header address; or
- The attachment override is nonzero.

The header equality is evaluated before the override condition in the supplied representation.

Otherwise, F-bcefa5957e76 receives:

- The address at tree offset +25;
- The original payload address;
- The address at parent offset +16.

Any nonzero result selects left attachment. Zero selects right attachment. There is no visible positive-versus-negative distinction or duplicate-rejection branch.

Comparison occurs after acquisition, payload copying, and count increment. It receives the original payload address, not the copied payload address. Its side effects are unknown; subsequent header reads must not be assumed to return the header observed before the call.

### Left attachment

The function first writes the obtained node address at supplied-parent offset +8. It then rereads the header address from the tree.

If that header differs from the supplied parent, it reads the header’s +8 link. That link is overwritten with the obtained node address only if its inspected value equals the supplied parent.

If the reread header equals the supplied parent:

1. The header’s +4 link is written with the obtained node address.
2. The header address is read again from the tree.
3. That newly read header’s +12 link is written with the obtained node address.

Under the conventional interpretation, the nonheader case can update the cached minimum, while the header-parent case establishes minimum, root, and maximum links. There is no separate emptiness check. These writes occur even if preexisting links would make such an attachment destructive.

Repeated header reads matter when storage aliases or earlier writes change the header-reference field.

### Right attachment

The function writes the obtained node address at supplied-parent offset +12.

It then reads the current header address and inspects that header’s +12 link. If the inspected link equals the supplied parent, it overwrites the link with the obtained node address.

This is consistent with maintaining a maximum-like cache. It does not prove that the cache was valid beforehand or remains valid afterward.

### Parent-link assignment

After the attachment and cache writes, the function writes the supplied parent address at obtained-node offset +4.

No local check establishes that the selected child link was empty, the parent belongs to the tree, or the attachment respects the comparison relation.

### Repair loop

Repair begins with the obtained node as the repair position.

At each loop test, the function rereads the tree’s header and that header’s +4 root-like link. If the repair position equals that link, repair ends.

Otherwise, it reads the repair position’s parent. A nonzero parent color ends repair. A zero parent color leads to inspection of the grandparent and its left link.

#### Parent equals the grandparent’s left link

The uncle is read from the grandparent’s +12 link.

If the uncle is nonnull and its color is zero, the function:

1. Writes 1 to the parent’s color.
2. Writes 1 to the uncle’s color.
3. Follows parent links from the current repair position and writes 0 to the resulting grandparent’s color.
4. Follows those parent links again to obtain the next repair position.

The next loop test then occurs. The parent-link traversals are repeated rather than guaranteed to reuse a previously captured grandparent address. Interfering aliases can therefore affect the sequence.

If the uncle is null or has nonzero color:

- When the repair position equals the parent’s +12 link, F-a72107f22654 is called with the tree and that parent. After return, the repair position becomes the saved parent address.
- The function follows the current repair position’s parent link and writes 1 to that parent’s color.
- It follows parent links again and writes 0 to the resulting grandparent’s color.
- It again obtains a grandparent through the current links and calls F-8050e778e362 with the tree and that address.

The loop is subsequently reevaluated. This branch does not explicitly terminate repair after the dependency call.

#### Parent does not equal the grandparent’s left link

The uncle considered in this branch is the grandparent’s +8 link.

A nonnull uncle with color zero takes the same recoloring-and-propagation sequence described above.

Otherwise:

- If the repair position equals the parent’s +8 link, F-8050e778e362 is called using the tree, saved parent, and additional argument expressions described under Dependencies. The repair position then becomes the saved parent address.
- The current repair position’s parent is colored 1.
- A grandparent reached through freshly read parent links is colored 0.
- F-a72107f22654 is called with the tree and the grandparent obtained through the then-current links.

This branch is selected by inequality with the grandparent’s left link. It does not separately verify that the parent equals the grandparent’s right link.

The apparent symmetry is consistent with red–black insertion repair, but correctness depends on link structure, initialization, and dependency behavior not established here.

### Final coloring and publication

After repair ends, the function rereads the header and its +4 root-like link, then writes exactly 1 to the color byte at that linked address.

Only afterward does it write the originally obtained node address to the result slot. The published address is not the possibly advanced repair position or necessarily the current root.

Publication establishes an address value, not a postcondition of reachability, allocation lifetime, or payload integrity. Unknown dependencies may have changed links or lifetime, and an aliased result slot may itself overwrite tree state.

There is no explicit status return, local recovery path, or rollback.

## Acceptance examples

These are conditional static expectations, not executed tests. Ordinary examples assume accessible, noninterfering storage, stable relevant state except for intended changes, and dependencies implementing the inferred initialization and rotation roles.

1. **Attachment through the header.**  
   If the supplied parent equals the header, comparison is bypassed even with a zero override. With stable header references, header offsets +8, +4, and +12 receive the obtained address in that order. The node’s parent receives the header address. If the root-like link still names the obtained node at the loop test, repair ends immediately, that node is colored 1, and its address is published.

2. **Forced left attachment.**  
   For an ordinary parent and any nonzero override, comparison is not called. Parent offset +8 receives the obtained address. The inspected header +8 cache is updated only when it equals that parent.

3. **Zero comparison result.**  
   With a zero override and nonheader parent, a zero comparison result selects parent offset +12. The inspected header +12 cache changes only when it names that parent. Zero alone does not establish payload equality.

4. **Noncanonical black-like color.**  
   If the repair position is not root and its parent color is 7, repair stops without locally rejecting that color. The final root-like target is still colored exactly 1.

5. **Red-like uncle propagation.**  
   With a zero-colored parent and selected nonnull zero-colored uncle, parent and uncle are colored 1, a grandparent reached through parent links is colored 0, and repair proceeds upward. Higher repair depends on the subsequently read structure.

6. **Left-side inner repair.**  
   With a red-like left parent, absent or black-like right uncle, and repair position on the parent’s right, F-a72107f22654 is called first on the parent. Recoloring and F-8050e778e362 then use the links available after that call.

7. **Failure during comparison.**  
   If comparison does not return normally, acquisition, the conditional payload transfers, and count update have already occurred. The function has not yet performed its own attachment or result-publication writes. Dependency side effects remain unrestricted.

8. **Publication without a reachability guarantee.**
