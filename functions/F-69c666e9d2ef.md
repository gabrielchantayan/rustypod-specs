# F-69c666e9d2ef

## Purpose

F-69c666e9d2ef searches an indexed, fixed-stride region by repeatedly invoking a caller-supplied comparison callback. It returns the computed address of a candidate for which the callback returns zero, or the integer value zero when the search interval becomes empty.

The established behavior is an interval-halving search controlled entirely by callback results. Interpreting it as a lookup in a sorted array is inferred intent: the function itself neither checks ordering nor reads record contents.

A nonzero result identifies the candidate address used in a successful callback invocation. It does not establish that the candidate remains valid, that its contents are unchanged, or that ownership has transferred. A successful candidate whose address is zero is indistinguishable in the return value from an unsuccessful search.

## Interface

The function receives five arguments, in this order:

| Position | Role | Source-visible representation |
|---|---|---|
| 1 | Search token passed to the callback | One 32-bit value; its meaning is unspecified |
| 2 | Base used to calculate candidate addresses | Signed integer, treated here as 32 bits |
| 3 | Initial number of indexed candidates | Signed integer, treated here as 32 bits |
| 4 | Stride between candidate addresses | Signed integer, treated here as 32 bits |
| 5 | Indirect comparison callback | Callable address |

The function returns an integer, treated here as 32 bits. Its two possible meanings are a successful candidate address and the zero sentinel.

The callback receives:

1. The first argument’s 32-bit value, unchanged by the search function.
2. The computed candidate address for the current index.

The callback supplies an integer result interpreted by sign:

- Negative: continue with smaller indices.
- Zero: stop and return the candidate address supplied to this invocation.
- Positive: continue with larger indices.

The magnitude of a nonzero result is irrelevant. The callback need not restrict its results to negative one, zero, and positive one.

The supplied material explicitly identifies the first argument as four bytes. The other integer widths follow the apparent 32-bit representation, but no independent ABI declaration is supplied. Exact calling convention, pointer representation, and behavior outside representable signed arithmetic remain documented_only.

For the intended address-based use, the caller must provide a compatible callable target and candidate addresses that the callback can safely use. The search function performs no callback validation, region validation, or bounds validation against an allocation.

## Behavior

### Search interval and initial state

The function maintains an inclusive interval of candidate indices.

Its initial lower bound is zero. Its initial upper bound is the supplied count minus one. This subtraction occurs before the first interval-emptiness check.

When subtraction is representable:

- A positive count starts with indices zero through count minus one.
- A zero count produces an empty interval.
- A negative count also produces an empty interval.

For an initially empty interval, the function returns zero without calculating a candidate address or invoking the callback.

The most-negative signed count requires a separate qualification: subtracting one is not representable in a signed 32-bit integer. The supplied representation does not establish a portable result for that input. It must not be grouped unconditionally with ordinary negative counts.

### Selecting a candidate

Before each callback invocation, the function checks whether the upper bound is less than the lower bound. If so, it returns zero.

Otherwise, it selects the midpoint by adding the two bounds and shifting the sum right by one bit. For a nonnegative, representable sum, this selects the lower of the two central indices when the interval has an even number of candidates.

This is not an overflow-avoiding midpoint calculation. The bounds are added before division by two. A valid count alone does not ensure that this addition remains representable throughout the search.

The candidate address is calculated by multiplying the stride by the selected index, then adding the base. No record size, alignment adjustment, padding rule, pointer dereference, or content comparison is imposed by this function.

Thus, the candidate layout is an arithmetic sequence of addresses:

- Index zero uses the base.
- Index one uses the base plus one stride.
- Each subsequent index adds another stride.

The stride is not checked for positivity or nonzero size. A zero stride makes all selected indices produce the same address. A negative stride makes increasing indices move toward lower addresses, provided the calculations remain representable.

### Callback dispatch and branch order

For each nonempty interval, the observable sequence is:

1. Select the midpoint index.
2. Calculate its candidate address.
3. Invoke the callback with the search token and that address.
4. Interpret the returned integer by sign.
5. Either return the calculated address or narrow the interval.

A negative callback result sets the upper bound to one less than the selected index. The lower bound is retained.

A positive callback result sets the lower bound to one more than the selected index. The upper bound is retained.

A zero callback result ends the search immediately. The returned value is the candidate address calculated before that callback invocation. There is no second comparison, candidate-address recalculation, record copy, or post-callback validation.

After a nonzero result, the next interval-emptiness check occurs before any further callback invocation.

### Meaning of ordering

For a conventional lookup, the callback must make its signs consistent with index order:

- A negative result must indicate that any desired match lies at a smaller index.
- A positive result must indicate that any desired match lies at a larger index.
- Zero must indicate an acceptable match.

These conditions concern increasing indices, not necessarily increasing memory addresses. With a negative stride, index order and address order run in opposite directions.

The function does not verify these conditions. An inconsistent callback can cause it to discard indices containing an acceptable match and return zero. The function does not perform a recovery scan.

If several candidates would compare equal, the first midpoint that produces zero is returned. There is no guarantee of the lowest index, highest index, first address, or last address among equal candidates.

### Termination and arithmetic limits

With representable arithmetic and a normally returning callback, every nonzero result excludes the selected index and strictly reduces the remaining interval. The search therefore terminates after a logarithmic number of callback invocations.

That guarantee is conditional. In particular:

- The initial count decrement must be representable.
- Each midpoint-bound addition must be representable.
- Each stride multiplication must be representable.
- Each base-plus-offset addition must be representable.
- The callback must return normally.

For positive counts no greater than 1,073,741,824, the sum of two in-range bounds is representable as a signed 32-bit integer. This is a sufficient bound for midpoint arithmetic, not a check performed by the function and not a guarantee that address arithmetic is safe.

No defined wrapping-address behavior is established by the supplied representation. Overflow must not be silently treated as intentional modular pointer arithmetic.

## Side effects

The function performs no explicit reads or writes of candidate contents. It computes candidate addresses and exposes them to the callback.

Its visible direct effects are callback invocations and its eventual return value. Its search bounds and temporary candidate calculations are internal state.

There is no explicit allocation, release, record relocation, record copying, or ownership transfer in the supplied body. This does not establish that a complete call is allocation-free or side-effect-free: the callback’s behavior is unspecified.

In particular, no preservation guarantee is available for:

- Global state.
- Memory reachable through the search token.
- Candidate storage.
- Other memory accessible to the callback.
- Resources owned by the caller or callback.

If the callback changes candidate contents, later invocations observe whatever state the callback and surrounding execution make available. The function provides no snapshot, locking, rollback, or consistency check.

If a callback releases or invalidates the successful candidate’s storage and then returns zero, the function still returns the previously calculated address. The supplied body does not check its continued validity.

No explicit error-reporting mechanism distinguishes invalid arguments, inconsistent ordering, arithmetic failure, callback failure, and ordinary absence of a match. The zero return is the empty-interval result, not a general validated error status.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, they assume compatible 32-bit representations, representable arithmetic, and normally returning callbacks.

### Empty candidate set

Given a count of zero, the function returns zero without invoking the callback.

The base, stride, search token, and callback target are not used to perform a candidate call on this path.

### Ordinary negative count

Given a count of negative one, the initialized interval is empty. The function returns zero without invoking the callback.

This example does not extend to the most-negative signed integer, whose initial decrement is outside the representable signed range.

### One candidate

Given a count of one, the only selected index is zero, so the callback receives the base address.

- If the callback returns zero, the function returns the base.
- If the callback returns any negative or positive integer, the remaining interval becomes empty and the function returns zero.

The stride does not affect the candidate address in this case because the selected index is zero.

### Three-step successful search

Given base 4096, count seven, and stride eight:

1. The first selected index is three, producing address 4120.
2. If that callback result is positive, the next interval contains indices four through six. Its selected index is five, producing address 4136.
3. If that result is negative, the next interval contains only index four, producing address 4128.
4. If that result is zero, the function returns 4128.

The callback receives the same search-token value at every step.

### Even-sized initial interval

Given a count of four, the first selected index is one, not two. A zero result at that invocation returns the address for index one without examining the other three candidates.

### Non-unit comparison results

For the same interval and candidate, a callback result of negative seven chooses the same next interval as negative one. A result of positive twenty-three chooses the same next interval as positive one.

### Zero stride

Given a count of four and stride zero, every callback receives the base address.

If every callback returns a positive value, the selected indices are one, two, and three. After those three invocations, the function returns zero. Repeated callback addresses are not deduplicated.

### Negative stride

Given base 8192, count three, and stride negative sixteen, the first selected index is one and its candidate address is 8176.

A positive result searches larger indices, even though those indices correspond to lower addresses.

### Duplicate acceptable candidates

Given five candidates for which every callback invocation would return zero, the function returns the address for index two after one invocation. It does not search for the first equal candidate.

### Zero-address success

Given one candidate whose base is zero, a callback result of zero causes the function to return zero as a successful candidate address.

A caller observing only the returned integer cannot distinguish this case from an exhausted search.

- **Callback implementation:** no concrete dependency ID or implementation is available.
- **Ownership:** no evidence establishes that the callback preserves, owns, retains, or releases any argument-associated memory.
- **Concurrent mutation:** no synchronization or stable-view guarantee is shown.

- **Intended record format:** there is no field layout beyond fixed-stride candidate addressing.
- **Intended comparison relation:** sorted lookup is inferred from interval selection, not enforced by the function.
