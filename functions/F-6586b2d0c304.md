# F-6586b2d0c304

## Purpose

F-6586b2d0c304 is a non-returning state-management loop over 61 indexed entries. It maintains entry activity and countdown state, processes acquired records, updates two shared state words, and emits notifications.

The established behavior includes:

- Clearing all 61 activity bytes on entry.
- Repeatedly acquiring a record, measuring an interval, obtaining an external state value, and aging active entries.
- Dispatching record kinds 0 through 6 when acquisition status permits.
- Selecting the **greatest** finite countdown among active entries, unless any active entry has the distinguished countdown value −1.
- Publishing whether any entry is active.
- Selecting between two notification mechanisms according to a field in the acquired record.
- Passing each non-null acquired record to a final dependency before the next iteration.

An inferred purpose is coordinated activity or timeout management. The meanings of individual entries, record kinds, notification routing constants, and shared state words are not established.

## Interface

### Invocation and termination

The function takes no explicit arguments and has no normal return path. Its inputs and outputs are supplied through global references, dependency calls, acquired records, and memory writes.

There is no explicit shutdown condition, error return, or exception-handling path.

### Memory model and widths

The supplied representation supports the following working layout:

| Object | Layout |
|---|---|
| Activity region | 61 one-byte entries, indexed 0 through 60 |
| Countdown region | 61 signed 32-bit entries, each at byte offset `4 × index` |
| Shared state | At least two adjacent 32-bit words |
| Acquired record | At least 36 accessible bytes when the relevant fields are used |
| Direct-notification payload | 16 bytes, initialized to zero |
| Allocated notification | Requested size 20 bytes |

The arithmetic and signed comparisons are described using 32-bit integer values. Pointer operations and four-byte fields are consistent with a 32-bit environment. Exact ABI and signed-overflow behavior are not independently established.

The two shared words are:

1. **Selected index:** zero is the “none selected” sentinel.
2. **Activity summary:** read as a fallback state and later written as zero or one.

The record fields used by this function are:

| Byte offset | Width | Use |
|---|---:|---|
| 16 | 1 byte | Record kind |
| 20 | 4 bytes | Entry index |
| 24 | 4 bytes | Countdown supplied by kind 2 |
| 28 | 4 bytes | Response field written by kinds 0 and 1 |
| 32 | 4 bytes | Nonzero selects direct notification |

No other record fields are explicitly accessed.

### Required memory preconditions

For defined operation:

- All three global memory references must identify accessible regions of the sizes above.
- An index used for an activity or countdown access must be valid for those regions.
- Any selected index promoted into activity must also be valid.
- An acquired record dispatched with successful status must be non-null and sufficiently accessible.
- The allocation dependency must provide at least 20 writable bytes before the function initializes the allocated notification.

The function does not enforce these conditions. In particular, it does not range-check signed record indices or selected indices.

Index zero is valid for table access but cannot represent a persistent selection: zero also means “none selected.”

## Behavior

### Initialization

The activity-region reference is captured before clearing begins. The function writes zero to activity entries 0 through 60, in ascending order.

During each clearing iteration, after the byte write, it reloads the references for shared state and countdown storage. The references obtained during the final clearing iteration are retained for subsequent loop operations.

Initialization does **not** clear countdown storage or either shared word.

The initial acquisition interval is −1.

### Acquisition and interval measurement

Each iteration starts with a zero-valued activity-aggregation flag.

The function first calls the interval dependency with a pointer to a four-byte scratch area and ignores its return value.

It then chooses an acquisition operation:

- If the previous aggregate interval is less than one, it calls the two-argument acquisition dependency with arguments 1 and 0. After that call, it explicitly sets acquisition status to zero.
- Otherwise, it calls the timed acquisition dependency with arguments 1, 0, the previous aggregate interval, and a pointer to acquisition status.

The returned value is treated as a record pointer.

The interval dependency is then called again with the same scratch area. This second return value becomes the interval used to age entries. If acquisition status equals 5, the function adds 10 to that value.

This addition is not clamped or checked. The source does not establish behavior if signed arithmetic exceeds its representable range.

A positive aggregate interval therefore affects the next acquisition call; it is not itself the interval subtracted from entries. Aging uses the subsequent interval-dependency result.

### External state and selected-entry promotion

The state dependency receives a pointer to a local 32-bit word. After it returns:

1. If that word is zero, the function replaces it with the current activity-summary word.
2. If the resulting value is nonzero, the function reads the selected-index word.
3. If both the resulting state and selected index are nonzero, the function performs these writes in order:
   - Set the selected entry’s activity byte to one.
   - Set its countdown to −1.
   - Clear the selected-index word to zero.

Thus a nonzero selected index can become indefinitely active before aging and record dispatch occur.

A zero value returned by the state dependency is not necessarily treated as inactive: a nonzero shared activity summary overrides that zero through fallback.

### Aging active entries

Entries are visited in ascending order, from 0 through 60.

For each entry:

- The activity byte is read first.
- If it is zero, the countdown is not read or changed.
- If it is nonzero, the countdown is read.
- A countdown of −1 is left unchanged.
- Any other countdown is compared, as a signed value, with the measured interval.

For a non-distinguished countdown:

- If the countdown is less than the measured interval, the result is zero.
- Otherwise, the measured interval is subtracted from the countdown.
- If the result is zero, the activity byte is cleared. The selected-index word is then read; if it equals this entry’s index, it is cleared.
- The resulting countdown is written after those activity and selection updates.

Equality therefore expires an entry as well as an interval larger than its countdown.

Negative countdowns other than −1 and negative measured intervals are not rejected. Their treatment follows the same signed comparisons and subtraction, subject to the unresolved arithmetic-overflow model.

### Record dispatch

If acquisition status is nonzero, record dispatch is skipped entirely. Later aggregation, notification selection, and non-null record handoff still occur.

With zero status, the function reads the record index at offset 20 before reading and dispatching the kind byte at offset 16. There is no preceding null check.

#### Kind 0: unconditional indefinite activation

The function:

1. Sets the indexed activity byte to one.
2. Sets its countdown to −1.
3. Writes one to the record response field at offset 28.

#### Kind 1: conditional indefinite activation

If the effective external state obtained earlier is nonzero, behavior is identical to kind 0.

Otherwise, the function writes zero to the response field and does not modify that entry’s activity or countdown through this dispatch branch.

Earlier promotion or aging may already have changed table state.

#### Kind 2: replace countdown and cancel selection

The countdown value at offset 24 is read.

- If that value is zero, the indexed activity byte is cleared.
- If the indexed entry equals the current selected index, the selected-index word is cleared, regardless of the supplied countdown.
- The supplied countdown is written to the countdown table.

A nonzero supplied countdown does **not** activate an inactive entry. This branch can therefore leave a nonzero or −1 countdown stored under a zero activity byte.

#### Kind 3: select only when unselected

The selected-index word is read. If it is zero, the record’s index is stored there. Otherwise it remains unchanged.

This branch does not directly activate the entry. Selecting index zero leaves the shared word at its “none selected” value.

#### Kind 4: direct notification and exceptional loop tail

The function replaces the low 16 bits of its local state word with 2, retaining the upper 16 bits. It then initializes a separate 16-byte payload to zero and invokes the direct-notification dependency with arguments 4, the payload pointer, 5, and 58.

After that call, it:

1. Resets the next acquisition interval to −1.
2. Writes zero to the activity-summary word.
3. Skips normal aggregation and normal notification selection.
4. Passes a non-null acquired record to the final record dependency.
5. Starts the next iteration.

This branch does **not** clear the activity table. Active entries can remain present while the activity summary is explicitly zero.

#### Kinds 5 and 6: extra direct notification

Kind 5 replaces the low 16 bits of the local state word with 3. Kind 6 replaces them with 4.

Each then sends the same all-zero 16-byte direct-notification payload, using arguments 4, payload pointer, 5, and 58.

Both continue into normal aggregation and normal notification selection. Consequently, either kind can produce two notification calls in one iteration.

The locally assigned values 2, 3, and 4 are not explicitly stored into the zeroed payload.

#### Other kinds

Other kind values perform no dispatch-specific writes and continue to normal aggregation.

### Normal aggregation

Except for kind 4, the function scans activity entries in ascending order.

It begins with:

- “Any active” equal to zero.
- Candidate next interval equal to −1.

For each nonzero activity byte, it reads the associated countdown:

- The first active entry sets “any active” to one and supplies the candidate interval.
- Later active entries replace the candidate when their countdown is greater.
- A countdown of −1 replaces the candidate regardless of its prior value.
- As soon as the candidate is −1, the scan stops.

For ordinary nonnegative finite countdowns, this selects the **maximum**, not the minimum. An active −1 countdown dominates every finite countdown.

If there are no active entries, the candidate remains −1.

The activity-summary word is then written with “any active,” as either zero or one.

### Normal notification and iteration completion

If the record pointer is non-null, the function reads its four-byte field at offset 32.

When that field is nonzero:

- The low 16 bits of the local state word are replaced with 1 if any entry is active, or 2 otherwise.
- A separate 16-byte payload is zeroed.
- The direct-notification dependency is called with arguments 4, payload pointer, 5, and 58.
- The acquired record is passed to the final record dependency.

Otherwise, including when the record pointer is null:

- The allocation dependency is called for 20 bytes.
- Byte 16 is written as 1 if any entry is active, or 2 otherwise.
- Byte 17 is written as 1.
- Four 32-bit zero stores initialize bytes 0 through 15.
- Bytes 18 and 19 are not initialized by this function.
- The allocated pointer is passed to the allocated-notification dependency with arguments 4, pointer, 5, and 58.
- Any non-null acquired record is passed to the final record dependency.

The next iteration uses the aggregate candidate interval computed before notification.

## Side effects

Explicit effects include:

- Initial activity-table clearing.
- Activity, countdown, and selection updates.
- Activity-summary writes.
- Record response writes for kinds 0 and 1.
- Notification payload construction and dependency calls.
- Repeated 20-byte allocation requests on the allocated-notification path.

No allocated notification is explicitly freed by this function. Transfer of ownership, copying, retention, and release by notification dependencies are unknown.

Likewise, the final record dependency is called once for each non-null acquired record that reaches the loop tail, but its ownership semantics are not established. Calling it a release operation would exceed the evidence.

Dependency calls may change global contents or storage. The function does not refresh its retained table and shared-state references during the main loop. No guarantee that dependencies preserve their contents is supplied.

There are no explicit checks for acquisition failure, allocation failure, invalid indices, arithmetic overflow, or downstream notification failure.

## Acceptance examples

These examples are conditional on valid memory, the stated dependency results, and no additional dependency side effects.

1. **Entry clearing:** On invocation, all 61 activity bytes become zero. Preexisting countdowns and shared words are not explicitly reset during initialization.

2. **Expiration at equality:** An active entry with countdown 7 and measured interval 7 becomes inactive with countdown zero. If it is selected when expiration checks selection, the selected-index word becomes zero.

3. **Distinguished countdown:** An active entry with countdown −1 survives aging unchanged. Normal aggregation selects −1 and stops scanning when it encounters that entry.

4. **Maximum finite interval:** If the surviving active countdowns are 4 and 12, with no active −1, normal aggregation selects 12. The next iteration uses timed acquisition with interval 12.

5. **State fallback:** If the state dependency writes zero but the activity-summary word is one, effective state is nonzero. A nonzero selected index is promoted to activity with countdown −1, then selection is cleared.

6. **Conditional activation rejected:** For kind 1 with effective state zero, response becomes zero. Dispatch itself does not activate the indexed entry.

7. **Countdown without activation:** For kind 2 targeting an inactive entry with supplied countdown 9, the countdown becomes 9 while the activity byte remains zero.

8. **Kind 4 bypass:** If aging leaves active entries and kind 4 is dispatched, those activity bytes remain set, but the activity summary is written zero and the next acquisition interval becomes −1. Normal notification is skipped.

9. **Two notifications:** Kind 5 or 6 produces one direct notification during dispatch and then one normal notification through the record-selected path.

10. **Nonzero acquisition status:** With nonzero status and a non-null record, kind dispatch is skipped. Offset 32 can still select direct notification, and the record still reaches F-E06.

11. **Allocated payload boundary:** On the allocated-notification path, bytes 0–15 are zero, byte 16 reflects aggregate activity, and byte 17 is one. No value is guaranteed for bytes 18–19.
