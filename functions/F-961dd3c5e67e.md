# F-961dd3c5e67e

## Purpose

F-961dd3c5e67e constructs a compact, tagged output record from one of two sources:

- A nonzero 32-bit field in an input object produces a record containing that field and a fixed one-byte marker.
- A zero input field selects a shared-state path. That path may invoke three dependencies before copying selected fields from a shared record.

The established behavior is selection, conditional dependency invocation, and partial initialization of a 16-byte output region. The meanings of the tags, the input field, and the shared fields are not established.

The dependency sequence resembles guarded initialization, but that is inferred intent rather than a proven synchronization or initialization contract.

## Interface

### Arguments

The function accepts two arguments:

| Argument | Interpretation established by the source |
|---|---|
| Output address | Address of a writable record accessed through 32-bit words, with one additional byte-sized write. |
| Input address | Address of an object whose 32-bit field at byte offset 4 is read. No other input-object field is directly accessed. |

The input address is represented by a 32-bit integer in the supplied source and used as an address. The output argument is a pointer to 32-bit storage. This contract describes that source-level, 32-bit address model; it does not establish portability to a different pointer width.

There is no explicit return value and no returned success or failure status.

### Output layout

The function directly writes the following fields, relative to the output address:

| Byte offset | Width | Nonzero-input branch | Zero-input branch |
|---|---:|---|---|
| 0 | 4 bytes | Nonzero-branch tag | Shared-state tag |
| 4 | 1 byte | Exactly 1 | Byte read from shared-record offset 4 |
| 5–7 | 3 bytes | No direct write | No direct write |
| 8 | 4 bytes | Initially captured input field | Word read from shared-record offset 8 |
| 12 | 4 bytes | Exactly 0 | Word read from shared-record offset 12 |

The branch tags are two separately referenced symbolic values. Their numeric values, equality or inequality, and semantic interpretation are not supplied.

The minimum output extent needed for the direct stores is 16 bytes. This is not a claim that all 16 bytes are initialized: bytes 5–7 are omitted from the direct writes.

### External state

The function refers to these externally supplied values:

- A base address used to read a 32-bit flag word at byte offset 24.
- An argument value passed to F-b255b26284e6 and, when applicable, F-d08d3ca17b81.
- A shared-record address passed to F-b07efd113d9d and later used to read output data.
- The two branch-specific tag values.

Their concrete addresses, numeric values, storage ownership, and initialization rules are not established.

### Preconditions

For ordinary completion, each memory access actually reached must be valid under the execution environment:

- The input must permit a 4-byte read at offset 4.
- The output must permit the specified stores through byte offset 15.
- On the zero-input path, the flag source must permit a 4-byte read at offset 24.
- After any dependency calls, the shared-record address used for copying must permit reads at offsets 4, 8, and 12, with widths of 1, 4, and 4 bytes respectively.

The source expresses word-sized accesses but establishes neither alignment checks nor support for misaligned addresses. Native byte order applies to the multi-byte reads and writes; no byte-order conversion is shown.

## Behavior

### Initial selection

The function first reads the 32-bit field at input offset 4. It tests that captured value for equality to zero.

Only zero versus nonzero matters. A value with its high bit set takes the nonzero branch just as any other nonzero bit pattern does. No range restriction, normalization, arithmetic transformation, or interpretation as an address is applied to the captured field.

The input field is not reread after branch selection. Later changes to that field, including changes made by dependencies, do not change the selected branch.

### Nonzero-input branch

When the captured input field is nonzero, the function performs these direct output writes in order:

1. Write the nonzero-branch tag as a 32-bit value at output offset 0.
2. Write the byte value 1 at output offset 4.
3. Write the captured 32-bit input field at output offset 8.
4. Write a 32-bit zero at output offset 12.

It then returns.

This branch does not directly inspect the flag word or shared record and invokes none of the three named dependencies. The captured input bit pattern is preserved in the payload word, including for values interpreted as negative by a signed 32-bit interpretation.

### Zero-input branch: conditional calls

When the captured input field is zero, the function reads the 32-bit flag word at offset 24 from the external flag base and tests bit 0.

- If bit 0 is set, the dependency sequence is skipped.
- If bit 0 is clear, F-b255b26284e6 is called with the external dependency argument.

Only the low bit participates in the flag decision. Other bits do not independently enable or suppress the dependency sequence.

The result of F-b255b26284e6 is tested as a 32-bit zero/nonzero result:

- A zero result skips both remaining calls.
- Any nonzero result causes F-b07efd113d9d to be called first, followed by F-d08d3ca17b81.

F-b07efd113d9d receives the shared-record address available for that call. F-d08d3ca17b81 receives the external dependency argument available for its call. Neither call’s result is used.

There is no visible retry, loop, or second flag test. In particular, the function does not itself recheck bit 0 after F-b255b26284e6 succeeds. Any additional checking belongs to the dependencies, if it exists.

The dependency argument is referenced separately for the first and last calls. Likewise, the shared-record address is referenced for F-b07efd113d9d and again for the subsequent copy. If a dependency changes those external values, the source does not guarantee that later references produce the earlier values.

### Zero-input branch: shared-record copy

The shared-record copy occurs after the conditional sequence, including when all calls were skipped. There is no explicit failure exit before that copy.

The source orders the direct operations as follows:

1. Capture the shared-record address to use for the copy.
2. Write the shared-state tag at output offset 0.
3. Read one byte from shared-record offset 4, then write that byte at output offset 4.
4. Read the 32-bit word at shared-record offset 12 and retain its value.
5. Read the 32-bit word at shared-record offset 8, then write it at output offset 8.
6. Write the retained word at output offset 12.
7. Return.

The word at shared-record offset 12 is therefore read before the word at offset 8, although output offset 8 is written first. The operation is not established to be an atomic snapshot of the shared record.

The shared-record base used by this copy is captured before the output tag write. Changes to the external shared-record address after that capture do not redirect these particular field reads.

### Aliasing and observation

No explicit non-aliasing restriction is shown. Nevertheless, a simple interpretation as an independent record copy requires that destination writes not alter subsequent source reads.

For example, the tag store occurs before the shared byte and word reads. If the output overlaps those shared fields, an earlier output write may change a later observed source value. Similarly, the output byte store precedes both shared word reads.

The nonzero branch captures its input payload before writing output, so overlap between the output and the input field does not cause that payload to be reread.

The ordering above describes the supplied source’s direct operations. It does not establish hardware memory barriers, atomic publication, or synchronization guarantees for concurrent observers.

## Side effects

### Direct memory effects

On an ordinary return, each branch has directly performed:

- One 32-bit tag store.
- One byte-sized marker store.
- Two 32-bit payload stores.

The direct stores cover 13 bytes within a 16-byte extent. The function does not directly write output bytes 5–7.

Preservation of those three bytes is conditional on the absence of other writers, dependency side effects, and aliases that cause other storage to coincide with them. The omission of direct stores is established; unconditional preservation across arbitrary dependency behavior is not.

The function directly reads, but does not directly modify, the input field, flag word, or shared-record fields, except where output aliasing makes a destination write affect that storage.

### Dependency effects

On the zero-input path, dependencies may run before the function’s direct output construction begins. Their effects are not defined by the supplied body.

The function does not save and restore external state around those calls. It must not be assumed that dependencies:

- Preserve global values.
- Preserve the output buffer.
- Initialize the shared record.
- Acquire or release a particular synchronization object.
- Allocate, retain, transfer, or release memory.
- Return normally under every condition.

### Ownership and lifetime

No direct allocation, deallocation, reference-count update, or ownership transfer is shown. Shared words are copied as 32-bit values. Their interpretation as integers, addresses, handles, or ownership-bearing references is unknown.

The caller supplies the output storage. The function itself does not establish that any address-like payload remains valid after return.

### Errors and partial completion

There are no explicit null checks, bounds checks, error codes, or recovery paths.

A zero result from F-b255b26284e6 does not cause an error return; it causes the function to proceed to the shared-record copy without the other two calls. Whether that result represents failure, unnecessary work, or some other condition is unknown.

If a dependency does not return normally, the later direct output construction is not reached. If a memory access fails partway through construction, earlier stores may already have occurred. No rollback is shown.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Unless stated otherwise, assume valid memory, ordinary dependency returns, stable relevant state during the copy, and no interfering aliases or writers.

### Nonzero input

Given an input field with bit pattern `0x12345678`:

- No named dependency is called.
- Output offset 0 receives the nonzero-branch tag.
- Output offset 4 receives byte value 1.
- Output offset 8 receives `0x12345678`.
- Output offset 12 receives zero.
- Bytes 5–7 retain their previous values under the stated assumptions.

The same branch must be selected for `0xFFFFFFFF`; the copied payload remains `0xFFFFFFFF`, not a normalized Boolean.

### Zero input with flag bit set

Given a zero input field and a flag word of `0x00000001`:

- None of the dependencies is called.
- The shared-state tag and selected shared fields are copied to the output.

A flag word of `0xFFFFFFFD` has the same call-suppression effect because its low bit is also set.

### Zero input with a zero dependency result

Given a zero input field, a flag word of `0x00000002`, and a zero result from F-b255b26284e6:

- F-b255b26284e6 is called once.
- F-b07efd113d9d and F-d08d3ca17b81 are not called.
- The shared-record copy still occurs.

The set second-lowest flag bit does not alter this decision.

### Zero input with a nonzero dependency result

Given a zero input field, clear flag bit 0, and result `0xFFFFFFFF` from F-b255b26284e6:

- All three dependencies are invoked in the specified order.
- The result qualifies as nonzero despite its signed interpretation.
- The shared-record address used for copying is obtained after the dependency sequence.

If F-b07efd113d9d changes the external shared-record address, the later copy uses the subsequently obtained address, not necessarily the address supplied to that dependency.

### Shared-field ordering

Given stable shared fields containing byte `0x7E`, word `0x11223344` at offset 8, and word `0xAABBCCDD` at offset 12:

- Output offset 4 becomes `0x7E`.
- Output offset 8 becomes `0x11223344`.
- Output offset 12 becomes `0xAABBCCDD`.

The required source-level read order is byte at offset 4, word at offset 12, then word at offset 8. An overlapping or concurrently changing source must not be treated as though all three fields were captured simultaneously.

The field widths, offsets, call conditions, and source-level access order above follow from that body. Domain meanings, synchronization semantics, ownership rules, and dependency internals do not.
