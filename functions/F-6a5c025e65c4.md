# F-6a5c025e65c4

## Purpose

F-6a5c025e65c4 prepares a destination byte range through one of two paths, invokes a transformation interface, overwrites the first four destination bytes with spaces, and installs the destination as the active parser range.

A state byte selects either:

- Searching an existing source buffer for `eexec` and choosing a payload-processing interface from classifications of its first four bytes.
- Sizing and replaying a sequence of matching records through stream-related dependencies.

The marker and diagnostics suggest preparation of a font private dictionary. Allocation, copying, hexadecimal decoding, stream positioning, and record transfer are **inferred intent**, not established dependency contracts.

The established contract covers this function’s field accesses, explicit writes, calls, branching, and status handling. Successful dependency statuses alone do not establish correct destination contents.

## Interface

The function accepts a mutable state address and a service-table address. Its return representation is an unsigned 32-bit status.

### State layout

Offsets are byte offsets from the state address. Addresses and ordinary scalar fields occupy 32 bits in the supplied representation.

The service table contains a 32-bit nested-table address at `0x04`. The nested table’s `0x18` entry supplies a payload-processing interface. The original table’s `0x10` entry supplies the final transformation interface.

### Preconditions

All accessed state fields, selected indirect targets, and dereferenced storage must be valid. The function establishes no null-address checks.

Safe execution additionally requires suitable accessible ranges, representable arithmetic, sufficient destination capacity, and appropriate callback behavior. In particular:

- The source scan can read before establishing that the logical source is nonempty.
- Payload classification can read four bytes without checking payload length.
- Finalization always writes four destination bytes.
- Parser callbacks must provide valid positions and any necessary progress.
- No protection against overlap or aliasing with state storage is established.

### Results

Three local format-failure paths explicitly assign status `3` after issuing diagnostics: missing marker acceptance, invalid marker termination, and zero-count record sizing.

Other explicit error exits propagate dependency statuses. Those statuses may have **any nonzero value, including `3`**. Therefore, observing `3` does not establish that local diagnostics occurred.

Normal finalization returns the local status slot. Replay explicitly resets that slot to zero before finalization; the ordinary source path also reaches finalization with zero. These statements do not establish preservation against dependencies that can modify previously exposed output storage.

A replay record-reader error is discarded. A zero result therefore does not prove complete replay, valid contents, or a valid dictionary.

## Behavior

### Entry and state capture

The function captures the stream context at `0x48`, then the allocation context at `0x10`, and initializes its local status to zero before selecting a path.

Subsequent changes to these context fields do not replace the captured arguments. Most other state fields are read when needed rather than captured for the whole operation.

### Source-buffer candidate search

The initial scan address is the source address. The initial end address is source address plus source count.

Each scan iteration reads the current byte before checking whether the incremented scan address remains below the end. A zero-length source is not rejected before that first read.

A raw candidate requires:

- The current byte to be `e`.
- The address nine bytes beyond it to be strictly below the current scan end.
- The next four inspected bytes to complete `eexec`.

The remaining marker bytes are inspected conditionally, stopping when a preceding requirement fails. The nine-byte condition is stricter than merely fitting the five-byte marker. Equality with the end rejects the candidate.

For a raw candidate, the function rereads the source base, writes the candidate’s nine-byte-ahead address into parser limit, and then writes that source base into parser current. It traverses parser positions below the retained temporary bound.

At a position beginning with `e`, F-fca51b715561 receives that position, a fixed marker-string address, and `5`. A zero result accepts the position. This establishes neither token delimitation nor comparison semantics beyond the observed acceptance rule.

If the position is not accepted, the function:

1. Calls the parser interface at `0x20`.
2. Reads parser status at `0x0C`; nonzero ends the inner traversal.
3. Otherwise calls the parser interface at `0x1C`.
4. Rereads parser current for the next iteration.

No independent progress or cursor-bounds enforcement is present.

After an unsuccessful inner traversal, the function recomputes source end from the then-current source fields. Raw scanning resumes at the retained nine-byte-ahead address of the original candidate, skipping intervening candidate starts. This resumed scan again performs its byte read before the loop’s end test.

Exhaustion invokes the two local diagnostics for missing marker acceptance and returns `3`. Earlier parser changes remain.

### Accepted marker and payload boundary

Upon acceptance, parser limit is restored to the then-current source address plus source count. The function calls the parser interface at `0x20` and reads parser current afterward.

The byte at that position determines the payload boundary:

- Carriage return advances the payload start by one byte, or by two if the following byte is line feed.
- Line feed advances the payload start by one byte.
- Any other byte causes two diagnostics and local status `3`.

No parser-status check intervenes between this callback and the byte inspection. The function itself does not skip spaces or tabs here. A carriage return causes inspection of the following byte without a separate bounds check.

Payload length is the current source count minus the displacement from the current source base to the computed payload start. These source fields are read after the callback. No explicit range or overflow check validates the subtraction.

### Source-path destination acquisition

If byte `0x5D` is zero, the function performs these writes in order:

1. Set byte `0x5E` to one.
2. Store computed payload length at `0x58`.
3. Store source base at `0x54`.
4. Clear source address at `0x4C`.
5. Clear source count at `0x50`.

Destination therefore references the source base, not payload start. This is an observable reference transfer, not proof of ownership transfer or release obligations.

If byte `0x5D` is nonzero, F-3ce007b692cc receives, in order:

1. The captured allocation context.
2. Computed payload length plus one.
3. The local status-output address.

The returned address is stored at `0x54` before the status is tested. A nonzero status returns immediately; otherwise payload length is stored at `0x58`.

There is no independent null-result check. This branch does not explicitly clear the reuse flag.

### Payload classification and processing

F-3a66152d0947 receives successive payload bytes at offsets zero through three, in that order. Classification stops at the first zero result.

If any attempted classification returns zero, F-000000000005 receives the current destination address, retained payload-start address, and retained payload length. Its return value is ignored.

If all four classifications return nonzero:

1. Parser current is set to payload start.
2. F-000000000003 receives state, current destination address, current destination count, a 32-bit output-count address, and zero.
3. Its return value is ignored.
4. Its output count is stored at `0x58`.
5. A zero byte is written at the then-current destination address plus that output count.

The output-count storage is not explicitly initialized before this call. Meaningful use requires the dependency to supply it.

Hexadecimal classification and decoding are inferred roles. The observed calls do not establish validation of the complete payload, output capacity compliance, or correct output bytes. A short payload can still undergo all four reads if every classification result is nonzero.

### Record sizing

F-b03b1199772e receives the captured stream context. Its result is retained. Only after that call does the function capture the global record-selection value. It then clears destination count.

F-680428c8d305 receives the stream context and addresses for a 32-bit tag and a 32-bit length-like output. Its return becomes the local status.

A nonzero reader status during sizing returns directly, without destination acquisition or local format diagnostics.

For a zero reader status, the tag’s low 16 bits are compared with the captured selection value. The selection value itself is not explicitly masked.

For each matching record, the function adds the current length output to the then-current destination count and calls F-d8528f8db63b with the captured stream context. A nonzero result from that call returns immediately.

A successful nonmatching record ends sizing. The function tests the destination count as it then exists:

- Zero causes two diagnostics and local status `3`.
- Nonzero starts replay preparation.

This is not a separately protected total. Dependencies may affect state unless their own contracts prohibit it.

### Replay preparation

F-e40a3ceddab2 receives the captured stream context and the result retained from F-b03b1199772e. A nonzero status returns immediately.

After that successful call, F-3ce007b692cc receives these arguments in exactly this order:

1. The captured allocation context.
2. The destination count freshly read from `0x58`.
3. The local status-output address.

There is no separately retained sizing total used for this request. Changes to destination count by F-e40a3ceddab2 affect the requested size. No extra byte is requested.

The returned address is stored at `0x54` before acquisition status is tested. Nonzero returns immediately. On zero status, destination count is cleared and replay begins.

### Record replay

Replay calls F-680428c8d305 again using the captured stream context and the tag/length output addresses.

A zero reader status with a matching low-16-bit tag causes F-0c21b5cad025 to receive:

1. Captured stream context.
2. Current destination address plus current destination count.
3. Current length output.

A nonzero transfer status returns immediately.

After a zero transfer status, the function rereads destination count and the length output, adds those post-call values, and stores the result at `0x58`. It does not necessarily add the length originally passed to the dependency.

A nonmatching tag or nonzero reader status ends replay. The function explicitly resets local status to zero and enters finalization. It neither propagates that reader error nor compares replay count with the requested acquisition size.

### Common finalization

F-000000000004 receives the current destination address, current destination count, and a global transformation value read for this call. Its return value is ignored.

Afterward, the function writes `0x20` to destination-relative offsets zero, one, two, and three, in order. Destination is read from state for these writes, rather than being retained from before the callback.

The function then reads destination again and writes:

1. Parser base to that address.
2. Parser current to that same address.
3. Parser limit to that address plus the then-current destination count.

The four space writes are unconditional even when count is below four. Aliasing with state storage can affect subsequent field reads; disjointness is not checked.

## Side effects

Direct effects include parser-range changes, count changes, replacement of the destination reference, source-reference clearing, setting the reuse flag, an optional zero terminator, and four final space writes.

Each local format failure calls F-4457a9a44a68 twice: first with a context message, then with the reason-specific message. Propagated dependency errors do not trigger those local diagnostic calls merely because their value is `3`.

No explicit release operation appears. Existing destination references can be overwritten without release. Failed acquisition can leave its returned address installed. Later failure can leave partial state or dependency-produced data.

There is no rollback. Failure does not imply unchanged parser fields, source references, destination storage, globals, or stream position. Opaque dependencies may have additional effects.

## Acceptance examples

These are conditional static examples, not executed tests.

1. **Marker boundary.** A raw `eexec` whose nine-byte-ahead address equals source end is rejected as a candidate, even though all five marker bytes fit.

2. **Termination.** If marker acceptance occurs and F-000000000001 leaves parser current on line feed, payload begins one byte later. Leaving it on a space causes local diagnostics and status `3`.

3. **Reference reuse.** With acquisition selector zero, destination becomes source base, source address and count are cleared, and reuse flag becomes one before classification.

4. **Short-circuit classification.** If the second classification returns zero, offsets two and three are not classified. F-000000000005 is selected; copied contents remain conditional on its actual contract.

5. **Decoded count.** If all four classifications are nonzero and F-000000000003 supplies count 12, the function stores 12 and writes a zero at the post-callback destination plus 12. A final 12-byte parser range additionally requires relevant state to remain preserved through finalization.

6. **Ordinary two-record replay.** Suppose sizing yields matching lengths 8 and 12, then a nonmatching tag. If dependencies preserve the relevant count, restoration preserves 20, and acquisition succeeds, the acquisition call receives allocation context first, size 20 second, and status-output address third. Preserved replay outputs can then produce count 20; actual concatenation additionally requires the transfer dependency’s content contract.

7. **Changed acquisition size.** If sizing leaves count 20 but successful restoration changes it to 24, the acquisition request uses 24, not 20.

8. **Post-transfer rereads.** If transfer receives length 8 but returns zero after changing destination count to 3 and the length output to 5, the subsequent stored count is 8.

9. **Reader-error asymmetry.** A replay reader error is discarded and finalization follows. The same error during sizing is returned.

10. **Propagated status `3`.** If F-d8528f8db63b returns `3`, this function returns `3` without issuing its local format diagnostics. Thus the status value alone cannot distinguish local format failure from dependency failure.

The payload length and record length-like output have signed-looking representations; tags and returned status use unsigned 32-bit representations. No explicit checks protect payload subtraction, size-plus-one, count accumulation, destination offsets, or parser-limit addition.

The contract does not treat negative-looking lengths, high-bit values, overflow, or invalid pointer arithmetic as safely accepted. Exact exceptional arithmetic behavior is unresolved; nonnegative lengths and valid ranges are not enforced by this function.
