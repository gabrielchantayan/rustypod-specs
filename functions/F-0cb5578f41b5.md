# F-0cb5578f41b5

## Purpose

F-0cb5578f41b5 is a state-dependent wrapper around F-3222fac04966. It either returns zero without invoking the dependency or returns a scaled result from the most recent dependency invocation.

The decision to invoke, continue, or return is controlled by arithmetic involving shared state. The wrapper can invoke the dependency with either two zero words or the two supplied input words in reversed order. Which argument pair is used depends on whether a zero-valued dispatch has occurred before the invocation.

This is a behavioral description based exclusively on the supplied static representation. The application-level meaning of the shared state, scaling factors, inputs, and dependency result is unknown.

## Interface

### Inputs

The function accepts two opaque 32-bit words, referred to here as the **first input** and **second input**.

The wrapper does not interpret either input as an address, dereference it, validate it, or perform arithmetic on it. It retains and forwards their bit patterns. If an input represents a pointer, handle, or resource identifier, its meaning and validity requirements belong to the dependency’s contract, which is unavailable.

### Output

The function returns an integer:

- Zero if execution reaches a return without completing a dependency invocation.
- Otherwise, the product of two captured scaling factors and the integer result of the most recent completed invocation of F-3222fac04966.

The supplied representation uses ordinary integer types for the return, dispatch arithmetic, scaling factors, and dependency result. A 32-bit integer model is consistent with the representation but is not independently established by an ABI or instruction listing.

Overflow behavior is not established. Examples below use small values for which the relevant arithmetic is representable.

## Behavior

### Entry capture

The observable shared-state reads shown by the supplied representation occur in this order:

1. Read and retain the second scaling factor.
2. Read and retain the first scaling factor.
3. Read the base-state value and form a **post-call operand** by adding one.
4. Read the base-state value again and form a **post-zero operand** by adding two.
5. Read the base-state value a third time and use it as the **initial operand**.

The three base-state reads must not be collapsed into a single snapshot in this contract. If the storage changes between reads, the initial operand and the two continuation operands need not derive from the same value.

Before dispatch begins:

- The pending return value is zero.
- The retained argument pair consists of two zero words.
- The current dispatch operand is the initial operand.

The scaling factors and both continuation operands remain captured values. They are not explicitly refreshed after dependency calls.

### Dispatch evaluation and argument selection

Each dispatch evaluation has the following behavior:

- Preserve the current retained argument pair as the candidate pair for a possible dependency invocation.
- Add a newly read dispatch offset to the current dispatch operand, producing the dispatch value.
- Prepare the post-zero operand as the next current operand.
- Replace the retained argument pair with the original first and second inputs.

The dispatch value then determines the transition.

#### Dispatch value zero

A zero dispatch value causes another dispatch evaluation immediately.

There is no dependency invocation and no change to the pending return value.

The next evaluation uses the captured post-zero operand. Its candidate argument pair is now the original input pair. Repeated zero dispatches continue to use that same post-zero operand and keep the original inputs as the retained pair.

The offset is read again on every repetition. A zero dispatch is therefore not, by itself, proof that the next dispatch is also zero.

#### Dispatch value two

A dispatch value of two invokes F-3222fac04966.

The dependency receives the candidate pair in reversed order:

- First dependency argument: the candidate pair’s second word.
- Second dependency argument: the candidate pair’s first word.

After the dependency returns normally:

- The pending return value is replaced by the product of the captured first scaling factor, captured second scaling factor, and returned integer.
- The next dispatch uses the captured post-call operand.
- The retained argument pair is restored to the candidate pair used for this invocation.
- Execution resumes dispatch evaluation.

The result is replaced, not accumulated. A later dependency invocation can overwrite an earlier nonzero result with zero or another value.

The dependency is still invoked when either captured scaling factor is zero. There is no visible shortcut that skips the call because the eventual product would be zero.

#### Any other dispatch value

Any dispatch value other than zero or two ends the function and returns the pending return value.

One has no unique externally visible treatment: it returns in the same way as every other nonzero value except two.

No dependency invocation occurs on this exit transition.

### Argument-pair invariant

Initially, the candidate pair is two zero words. A dependency invocation reached before any zero dispatch therefore receives two zero words, regardless of the supplied inputs.

A zero dispatch changes the retained pair to the supplied inputs. Every later dependency invocation receives the second input followed by the first input.

A dependency invocation preserves the pair it used for subsequent processing. It does not itself switch from the zero pair to the input pair.

Consequently, within this wrapper, the dependency can receive only:

- Two zero words; or
- The original input words in reversed order.

The wrapper does not construct a mixed pair containing one original input and one zero word. These alternatives may, of course, be indistinguishable when the actual input words are zero.

### Stable-state special case

Suppose all three base-state reads yield the same integer, the offset remains unchanged throughout execution, and arithmetic is representable.

Let the initial dispatch sum be the common base value plus the offset.

- If that sum is neither zero nor two, the function returns zero without a dependency invocation.
- If that sum is zero, the next dispatch is two. The dependency receives the reversed original inputs. The following dispatch is one, so the function returns the scaled result.
- If that sum is two, the dependency receives two zero words. The following dispatch is three, so the function returns the scaled result.

Under these conditions there is at most one dependency invocation and at most three dispatch evaluations.

This bounded behavior does not extend to changing offsets or inconsistent entry-time base-state reads.

## Side effects

No explicit shared-memory write, input-memory write, allocation, release, or direct input dereference is visible in the wrapper.

The absence of explicit wrapper writes does not imply that the function is free of side effects. F-3222fac04966 may modify shared storage, perform I/O, allocate or release resources, or have other externally visible effects. None of those behaviors can be established from this body.

### Effects across a dependency call

Changes made by the dependency have different consequences depending on the storage affected:

- Changes to the dispatch offset can affect the immediately following dispatch.
- Changes to the shared scaling-factor locations do not refresh the factors already captured by the wrapper.
- Changes to the base-state location do not refresh the already captured initial or continuation operands.

No assumption is made that the dependency preserves any global storage.

### Ownership

The wrapper visibly forwards words by value and performs no explicit ownership transfer operation.

That does not establish a borrowing contract. If either word identifies a resource, the dependency could retain, mutate, consume, or release it. Ownership and lifetime obligations are documented_only pending the dependency contract.

### Errors and non-return

A dependency result that an application might interpret as an error is still used as an integer scaling operand. It is not visibly recognized as an error code.

Invalid reads, arithmetic overflow, dependency failure, dependency non-return, and exceptions or faults are not handled in the supplied body. Their actual outcomes depend on execution details not provided here.
