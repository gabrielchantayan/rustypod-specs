# F-0cd52eaf0204

## Purpose

F-0cd52eaf0204 searches a table of inclusive unsigned 32-bit ranges and produces a 32-bit value derived from a matching range.

It supports two behaviors:

- **Lookup mode:** search for the caller-supplied key and return the range-derived value, or zero when no range matches.
- **Advancing mode:** increment the supplied key modulo \(2^{32}\), search for that target, and either publish a matching value or prepare context state for F-008865c7563b to resolve a position. On successful completion, replace the caller’s key with the context’s resulting key.

The static evidence establishes these operations, but not the application-level meaning of the table, keys, or returned values. “Advancing” describes the observed increment-and-resolution behavior; it does not establish that every successful result is a numerical successor.

Zero is both a possible arithmetic result and the function’s failure/no-result return value. The return value alone does not distinguish those cases.

## Interface

### Inputs

The function takes three arguments:

1. **Context address.** An address used to locate a table reference and mutable state fields.
2. **Caller-key address.** An address of a readable unsigned 32-bit scalar. Successful advancing-mode completion also writes this scalar.
3. **Mode selector.** A signed integer tested only for equality with zero. Zero selects lookup mode; every nonzero value selects advancing mode.

The supplied representation uses 32-bit integer values and integer-based address calculations. This contract describes that 32-bit representation; it does not establish behavior for a port with wider integers or addresses.

### Context layout

Offsets are byte offsets from the context address.

| Offset | Width | Observed role |
|---|---:|---|
| `0x10` | 32 bits | Table address, loaded on entry |
| `0x18` | 8 bits | Activity/status flag, written as 1 before advancing-mode resolution and checked after the dependency call |
| `0x1c` | 32 bits | Working/result key |
| `0x20` | 32 bits | Working/result value |
| `0x24` | 32 bits | Selected or candidate record index |

The table address is loaded once for this invocation. Later changes to the context’s table-address field do not change the table address already used by the search.

Context fields and the caller-key scalar use native scalar loads and stores. The table fields below are instead decoded explicitly from individual bytes.

### Table layout

Offsets are byte offsets from the loaded table address.

| Offset | Width | Meaning |
|---|---:|---|
| `0x0c` | 4 bytes | Record count, unsigned big-endian |
| `0x10 + 12 × index` | 4 bytes | Inclusive lower bound, unsigned big-endian |
| `0x14 + 12 × index` | 4 bytes | Inclusive upper bound, unsigned big-endian |
| `0x18 + 12 × index` | 4 bytes | Mapping base, unsigned big-endian |

Each record occupies 12 bytes. The first record’s lower bound begins at table offset `0x10`.

No table length, allocation size, format version, or ownership metadata is checked.

### Output

The function returns a signed 32-bit integer. A matching record produces the 32-bit pattern

\[
(\text{mapping base} + \text{target} - \text{lower bound}) \bmod 2^{32}.
\]

That pattern is returned through the signed integer result. For example, the bit pattern `0xffffffff` corresponds to signed −1 under the represented 32-bit model. A negative return is not separately classified as an error.

In advancing mode, a dependency-resolved nonzero context result can also become the return value.

### Preconditions

For defined, useful execution:

- The context fields read or written along the selected path must be accessible.
- The caller-key address must be readable even when the table count is zero.
- On a successful advancing path, the caller-key address must also be writable.
- Every table byte reached by the search must be readable.
- Address arithmetic must resolve to valid accessible storage.
- If F-008865c7563b is called, its own preconditions must hold.

The routine performs no explicit validation of these conditions.

## Behavior

### Initial reads and empty table

The function first loads the table address from context offset `0x10`, then reads the caller’s unsigned 32-bit key, then decodes the table count.

If the count is zero, it returns zero immediately. This path does not increment the key, write context state, call the dependency, or write the caller-key scalar.

Thus, an empty table does not make an invalid caller-key address safe: the key is read before the empty-table return.

### Target selection

In lookup mode, the search target is the original caller key.

In advancing mode, the target is the original caller key plus one, modulo \(2^{32}\). An original key of `0xffffffff` therefore produces target zero. There is no overflow rejection or saturation.

The increment is initially local to the invocation; it is not immediately written back to the caller.

### Range search

The search begins with a half-open index interval covering the record count. It repeatedly selects a midpoint using unsigned 32-bit addition followed by a right shift.

For each probed record:

1. Decode its lower bound.
2. If the target is below that lower bound, move the upper search boundary to the probed index.
3. Decode that record’s upper bound even when the target was already found to be below its lower bound.
4. If the target is below the lower bound, continue without testing that record for membership.
5. Otherwise, if the target is at most the upper bound, treat the record as a match.
6. Otherwise, move the lower search boundary past the probed record.

Membership comparisons are unsigned and both range endpoints are inclusive.

Only a matching record’s mapping base is decoded. A match produces the modular arithmetic result described in the interface and ends the search.

If the search interval becomes empty, the function retains the index and upper bound from the last probe. The retained index initially equals the count, and the retained upper bound initially equals `0xffffffff`.

The midpoint is not computed with an overflow-avoiding difference. Its boundary sum can wrap modulo \(2^{32}\). Consequently, arbitrary large counts do not carry a general guarantee of in-bounds probing, progress, or termination.

### Lookup-mode completion

Lookup mode returns the computed value when a record matches, including when that value is zero.

If the search exhausts its interval without a match, lookup mode returns zero.

There are no context writes, caller-key writes, or dependency calls on any lookup-mode path.

### Advancing-mode candidate selection

After a match or an exhausted search, advancing mode uses the retained record index and upper bound.

If the retained upper bound is less than the target:

- Increment the retained index modulo \(2^{32}\).
- If the incremented index equals the table count, return zero immediately.

Otherwise, retain the index unchanged.

This equality test is the explicit end-of-table rejection. It is not a general bounds check. When the retained upper bound is not less than the target, the function does not perform that increment or equality test.

For a conventional ascending, nonoverlapping table with safe arithmetic, this logic can retain a matching record or select the following record when the target lies in a gap. What the dependency does with that candidate remains undocumented.

### Advancing-mode state publication

Unless the preceding end-of-table check returned zero, the function writes context fields in this order:

1. Store 1 in the one-byte flag at `0x18`.
2. Store the selected index at `0x24`.
3. Store the incremented target at `0x1c`.

It then branches on the locally computed mapping value.

**Nonzero computed mapping value**

The function writes that value to context offset `0x20`. It does not call F-008865c7563b.

It then reads context offset `0x1c`, writes that value through the caller-key address, and returns the computed value.

**Zero computed mapping value**

This branch covers both an exhausted search with no match and a matching record whose arithmetic result is zero.

The function calls F-008865c7563b with the context address. The dependency’s direct return value is ignored.

After the dependency returns:

1. Read the flag at `0x18`. If it is zero, return zero.
2. Otherwise, read the 32-bit result at `0x20`. If it is zero, return zero.
3. Otherwise, read the key at `0x1c`, write it through the caller-key address, and return the result read from `0x20`.

The dependency can therefore affect success, the returned value, and the caller’s resulting key. This function does not itself establish that the dependency preserves any other memory.

## Side effects

### Direct writes

Lookup mode performs no direct writes.

Advancing mode can write the flag, selected index, working key, result value, and caller-key scalar. The caller-key write occurs only after either:

- A nonzero directly computed result has been stored in the context; or
- The dependency has returned with a nonzero flag and nonzero context result.

An advancing call that returns zero may nevertheless have changed context state. In particular, dependency-related failure occurs after the flag, index, and target have already been published. There is no rollback.

The zero-count return and the end-of-table rejection occur before any direct context writes.

### Read/write ordering

The observable field-level order is significant:

- Initial table-address load precedes the caller-key read, which precedes count decoding.
- Each probed lower bound is decoded before that record’s upper bound.
- The upper bound is decoded even on the below-lower-bound branch.
- The mapping base is decoded only after a membership match.
- Advancing-mode publication orders flag, index, then key.
- After the dependency, the flag is checked before the result is read; the key is read only after both checks succeed.
- The caller-key store is last among this function’s direct writes.

The representation does not establish an exact evaluation order among the individual byte loads used within one big-endian field expression.

### Aliasing

No non-aliasing check is present.

If the caller-key address overlaps context or table storage, stores can affect subsequent observations or final state. In particular, the key copied to the caller is read from context offset `0x1c` at completion; it is not necessarily the original locally incremented target.

The dependency may introduce additional alias-visible effects. Ordinary use should provide distinct, valid storage unless such interactions are deliberately supported elsewhere.

### Ownership

The function directly allocates and releases no memory. It uses caller-provided addresses and a table address obtained from the context.

No ownership transfer is established. The dependency’s allocation, release, retention, and global-state behavior are unknown.

## Dependencies

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Except where stated otherwise, assume valid nonoverlapping storage, safe address arithmetic, and an ascending nonoverlapping table.

1. **Empty table**
   
   With count zero, either mode returns zero. The caller key is still read. No direct write or dependency call occurs.

2. **Inclusive range endpoints**
   
   For one record covering keys 10 through 12 with mapping base 100, lookup mode returns 100 for key 10 and 102 for key 12. Both endpoints match.

3. **Lookup miss**
   
   For that same record, lookup mode with key 9 or 13 returns zero without modifying context or caller storage.

4. **Direct advancing match**
   
   With caller key 10 and a nonzero mode selector, the target is 11. The function publishes flag 1, index 0, and key 11; stores result 101; writes 11 to the caller key; and returns 101. It does not call the dependency.

5. **Advance beyond the final range**
   
   For that single record, caller key 12 in advancing mode produces target 13. The candidate index increments to the count, so the function returns zero before writing context or caller storage.

6. **Gap resolved by the dependency**
   
   Suppose records cover 10–12 and 20–22. Caller key 12 in advancing mode produces target 13. The search selects candidate index 1 and publishes target 13.
   
   If the dependency leaves the flag nonzero, sets the context key to 20, and sets the context result to 500, the function writes 20 to the caller key and returns 500. Those dependency changes are conditions, not established dependency behavior.

7. **Arithmetic zero triggers dependency resolution**
   
   A record covering key 10 with mapping base zero yields zero for target 10. Lookup mode returns zero directly. Advancing mode reaching target 10 calls the dependency despite having found a matching record.

8. **Dependency failure preserves published state**
   
   If the dependency clears the flag, the function returns zero without its final caller-key write. The earlier context stores remain, subject to any dependency changes. The result field is not read after the zero flag check.

9. **Unsigned key wrap**
   
   Caller key `0xffffffff` in advancing mode produces target zero. If a record covers zero with mapping base 7, the direct-success path returns 7 and writes zero to the caller key.

10. **Signed return representation**
    
    A matching target whose modular mapping result is `0xffffffff` yields signed −1. Because this result is nonzero, advancing mode uses the direct-result path rather than invoking the dependency.
