# F-08ef66001117

## Purpose

F-08ef66001117 conditionally reconfigures a caller-supplied object around a supplied or newly obtained storage value, then clears six object fields.

The established behavior has three outcomes:

- A dynamically dispatched gate reports a nonzero status: return null without proceeding.
- The gate permits continuation, but the requested extent is nonpositive and the supplied storage value is nonzero: return null without invoking subsequent dependencies.
- Otherwise: perform the applicable configuration operations, clear six fields in a defined order, and return the original object address.

The interpretation of this operation as buffer replacement or reset is **inferred intent**. The supplied evidence establishes field accesses, dependency calls, arguments, and ordering; it does not establish the object’s complete type, storage ownership rules, or dependency implementations.

## Interface

### Inputs

The function receives three arguments:

1. **Object address.** A pointer to a mutable object represented by an array of 32-bit words in the supplied evidence.
2. **Storage value.** A 32-bit integer used as an opaque storage value. Zero is distinguished from every nonzero value. Its use as an address is inferred from the surrounding operations, not established by its declared integer type.
3. **Extent.** A signed 32-bit integer. Values greater than zero select the configuration path; zero and negative values select the nonpositive-extent path.

No explicit null-object check, object-size check, storage-capacity check, alignment check, or storage-address validation is present.

### Result

The result is either:

- Null, on either explicit rejection path; or
- The exact object address supplied by the caller, after the final direct field writes.

Returning the object address is not evidence that a storage-acquisition dependency succeeded. The function does not check that dependency’s returned storage value before installing it.

## Behavior

### 1. Invoke the initial gate

Before checking either the storage value or extent, the function:

1. Reads the object’s first 32-bit word.
2. Uses that value to locate a 32-bit dispatch entry at offset `+0x34`.
3. Clears the entry’s low two bits.
4. Invokes the resulting callable with the object address as its sole explicit argument.

The returned value is represented as 64 bits in the evidence. Its low 32 bits are interpreted as the status used by this function.

If those low 32 bits are nonzero, the function immediately returns null. It does not directly read the flags word, invoke any later dependency, replace the storage or extent fields, or perform the six final clear operations.

The callback itself may have side effects. Consequently, this rejection is not established to leave the object or global state unchanged.

If the low 32 bits are zero, execution continues. A nonzero upper half alone does not reject the request.

### 2. Sample the flags word

After a successful gate, the function reads the 32-bit word at object offset `+0x10` and retains its value for a later bit-0 decision.

This read occurs before the extent branch, including on the path that subsequently rejects a nonzero storage value paired with a nonpositive extent.

The retained value is a snapshot. Later dependency changes to the flags field do not change the bit-0 decision made from this sample.

### 3. Handle a nonpositive extent

For an extent less than one:

- If the storage value is nonzero, return null immediately.
- If the storage value is zero, invoke F-128bc7e093a3 with the object address and a 32-bit selector value of `1`, then perform the final clear sequence.

This path does not directly install a storage value, directly replace the extent field, invoke F-fab3799b3190, invoke F-cf4f89824645, or invoke F-58ba61416cc9.

In particular, zero and negative extents are treated identically for this branch decision. No negative extent is passed to the storage-acquisition dependency.

The lack of direct replacement writes does not imply that the storage and extent fields remain unchanged: F-128bc7e093a3 may modify them.

### 4. Handle a positive extent

For an extent greater than zero, the function first records whether the original storage argument was zero.

#### Obtain a storage value when none was supplied

If the original storage value was zero, the function invokes F-fab3799b3190 with:

- The positive signed 32-bit extent; and
- The upper 32 bits of the initial gate’s 64-bit return, passed through the signed integer conversion shown by the evidence.

The dependency’s returned value becomes the replacement storage value.

There is no local failure check. A zero result is still eligible for installation, and it does not change the recorded fact that the original storage argument was zero.

The upper return half is not independently validated or normalized. Its meaning is unknown. In particular, it must not be assumed to be zero merely because the gate’s low-half status was zero. Exact signed-conversion semantics for an upper-half value outside the signed 32-bit range depend on the represented implementation.

If the original storage value was nonzero, F-fab3799b3190 is not called.

#### Invoke the preparation dependency

Next, invoke F-cf4f89824645 with:

- The object address; and
- A Boolean indicating whether the original storage argument was zero.

This Boolean reflects the original argument, not the replacement storage value, the flags snapshot, or the success of any acquisition.

#### Conditionally pass the current storage field to another dependency

If bit 0 of the earlier flags snapshot is set, the function reads the object’s storage field at `+0x08` and passes that current value to F-58ba61416cc9.

The timing is significant:

- The flags snapshot predates any call to F-fab3799b3190 or F-cf4f89824645.
- The storage-field read occurs after those applicable calls.
- Therefore, the call decision uses an earlier flags value, while its argument uses the storage field’s later value.

The function does not additionally test that storage-field value for zero.

F-58ba61416cc9 may be a release operation, but that interpretation is not established. Its exact effect and ownership contract remain unknown.

#### Install the replacement fields

After the conditional call returns, or immediately if the sampled bit was clear, the function directly writes:

1. The replacement storage value to `+0x08`.
2. The positive extent to `+0x0C`.

It then invokes F-128bc7e093a3 with the object address and a 32-bit selector value of `0`.

F-128bc7e093a3 runs after these writes and may change either field again. Thus the function’s direct installation order is established, but the final values of those fields cannot be guaranteed without that dependency’s contract.

### 5. Clear final fields and return

After F-128bc7e093a3 returns on either successful branch, the function directly writes 32-bit zero values in this order:

1. `+0x14`
2. `+0x18`
3. `+0x1C`
4. `+0x24`
5. `+0x20`
6. `+0x28`

It then returns the original object address.

These are the final direct object writes shown. Their ordering is an ordering in the supplied static evidence, not a claim of atomicity, synchronization, or hardware-level visibility to concurrent observers.

## Side effects

### Direct state changes

On the positive-extent path, the function directly replaces the storage and extent fields before calling F-128bc7e093a3.

On either successful path, it subsequently clears the six listed fields. On both explicit rejection paths, it performs none of these direct field writes.

There is no direct write to the flags word in this function.

## Acceptance examples

The following are conditional static acceptance cases, not executed tests. Unless stated otherwise, required accesses are valid and invoked dependencies return normally.

### Gate rejection

Given any storage and extent, if the gate’s low 32 return bits are nonzero:

- The result is null.
- No subsequent dependency is invoked.
- No flags read or direct configuration/final-clear write follows.
- Effects already caused by the gate remain possible.

### Nonpositive extent with supplied storage

Given a zero gate status, nonzero storage, and extent `0` or a negative signed 32-bit value:

- The flags word is read.
- The result is null.
- None of the four named dependencies is invoked.
- No direct storage, extent, or final-clear write occurs.

### Nonpositive extent without supplied storage

Given a zero gate status, zero storage, and a nonpositive extent:

- F-128bc7e093a3 receives selector `1`.
- The six fields are cleared in the specified order.
- The original object address is returned.
- No direct storage or extent replacement is required.

### Positive extent with supplied storage

Given a zero gate status, nonzero storage, and positive extent:

- F-fab3799b3190 is skipped.
- F-cf4f89824645 receives false.
- The conditional F-58ba61416cc9 call follows the sampled flags bit.
- Storage is written before extent.
- F-128bc7e093a3 receives selector `0`.
- Final clearing follows that call.

### Acquisition returning zero

Given zero original storage, positive extent, and F-fab3799b3190 returning zero:

- F-cf4f89824645 still receives true.
- The conditional old-storage operation still occurs if the sampled flags bit requires it.
- Zero is directly installed in the storage field.
- The function continues to finalization rather than returning null for acquisition failure.

### Intervening mutation

If the sampled flags bit is set and F-cf4f89824645 changes the storage field, F-58ba61416cc9 receives the changed field value.

If the sampled bit is clear and F-cf4f89824645 sets that bit in memory, F-58ba61416cc9 is nevertheless skipped.

### Upper-half gate data

A gate return with low 32 bits zero and upper 32 bits nonzero permits continuation. For zero original storage and positive extent, the acquisition dependency receives the upper-half-derived argument; for supplied storage, that upper half is not otherwise consumed here.
