# F-ea6b4f7a8762

## Purpose

F-ea6b4f7a8762 conditionally drives two ordered processing phases through dependency F-df2c7f3bb9d4. When an external gate byte is nonzero, it repeatedly invokes the dependency with selector 0 while a first record’s signed counter is positive. It then repeatedly invokes the same dependency with selector 1 while a second record’s signed counter is positive.

The established behavior is counter-controlled repetition, not a guarantee that either counter decreases. This function contains no direct counter update, timeout, iteration limit, or recovery path. Completion depends on the initial counters and on changes made by the dependency or other actors.

A plausible intent is to drain two classes of pending work in order. That interpretation is not required by the evidence: the meanings of the gate, counters, records, and selectors remain unknown.

## Interface

**Entry and result**

- No explicit arguments are accepted.
- No result value is returned.
- Relevant inputs are obtained from external state and memory reached through that state.
- The function has no visible error-reporting result.

**External state**

The contract uses these descriptive names:

| Name | Role |
|---|---|
| Gate reference | An external value identifying the byte that enables processing. |
| First-record reference | An external address-like value captured once at entry. |
| Second-record reference | An external address-like value read at every first-phase condition evaluation. |
| First counter | A signed integer field at byte offset 64 from the captured first-record address. |
| Second counter | A signed integer field at byte offset 64 from the second-record address retained when the first phase ends. |

The gate is tested as one byte. Zero disables processing; every nonzero byte value enables it. The test is not restricted to the value one.

Both counter accesses are represented as signed `int` accesses. Their comparison is strictly greater than zero. Consequently, zero and negative values terminate or bypass their respective phases.

The supplied representation does not independently establish the target ABI. A 32-bit signed counter layout is consistent with it, but the physical width of `int`, the address width, byte order, and alignment requirements require target confirmation. These are layout qualifications, not permission to reinterpret the comparison as unsigned.

**Memory preconditions**

For ordinary completion:

- The external references that are evaluated must be readable.
- The gate reference must identify a readable byte.
- Whenever a counter is evaluated, the corresponding captured record address plus byte offset 64 must identify a valid signed integer field.
- Those record addresses must remain usable for every subsequent access through them.
- Each invoked dependency call must return normally for this function to continue.

A zero gate avoids all counter-field accesses. It does not avoid the initial read of the first-record reference.

No null check, record-size check, lifetime check, alignment check, or address-overflow check is visible.

## Behavior

### Entry and gate decision

The first-record reference is read and retained before the gate byte is evaluated. This captures the record address for the entire first phase.

The gate reference is then used to read the gate byte.

If that byte is zero, the function returns immediately. In this case:

- Neither counter is read.
- The second-record reference is not read.
- F-df2c7f3bb9d4 is not called.

If the byte is nonzero, processing continues. The gate is not tested again during this invocation. A later change to the gate therefore does not, by itself, stop either phase.

### First phase

Each first-phase condition evaluation has two ordered operations:

1. Read and retain the current second-record reference.
2. Read the signed counter at byte offset 64 from the first-record address captured at entry.

This ordering applies to the initial condition evaluation, every evaluation following a returning selector-0 call, and the final evaluation that ends the phase.

If the first counter is positive, F-df2c7f3bb9d4 is called with selector 0. After a normal return, the first-phase condition is evaluated again.

If the first counter is zero or negative, no selector-0 call is made for that evaluation, and execution proceeds to the second phase.

The first-record reference is not refreshed. If the dependency changes that external reference, later first-counter reads still use the address captured at entry. Changes to the counter stored at that captured address can affect the next condition evaluation.

In contrast, the second-record reference is refreshed on every first-phase condition evaluation. A selector-0 call that changes this external reference can therefore affect which record is ultimately used by the second phase.

The function does not itself decrement the first counter. A positive counter that remains positive can cause unbounded repetition. In that case the second phase is never reached.

### Transition between phases

The second phase uses the second-record address retained during the final first-phase condition evaluation—the evaluation that observed a nonpositive first counter.

This remains true when the first counter is nonpositive on its first read. Even though no selector-0 call occurs, the second-record reference has already been read and retained before that first counter read.

The retained second-record address is selected before the first counter is read on that final evaluation. It is not a fresh reference read performed at the start of the second phase.

### Second phase

The function reads the signed counter at byte offset 64 from the retained second-record address.

If that counter is positive, F-df2c7f3bb9d4 is called with selector 1. After a normal return, the counter at the same retained address is read again.

If the counter is zero or negative, the function returns.

The second-record reference is not refreshed during this phase. A selector-1 call that changes the external reference does not redirect later counter reads in the current invocation. A change to the counter in the retained record can affect the next evaluation.

The first counter is not revisited once the second phase begins. If a selector-1 call makes the first counter positive again, this invocation does not return to selector-0 processing.

As in the first phase, this function performs no direct counter decrement. A persistently positive second counter can cause unbounded selector-1 calls.

### Ordering guarantees and limits

For a normally returning invocation:

- Every selector-0 call precedes every selector-1 call.
- Either class of call may be absent.
- No selector-0 call occurs after selector-1 processing has begun.
- Each call requires a preceding positive counter observation for its phase.
- The final nonpositive counter observation for a phase does not produce a call.

These are statements about the control and access order represented by the supplied static evidence. They do not establish atomicity, synchronization, hardware memory barriers, or the behavior of concurrent unsynchronized mutation.

## Side effects

The function contains no direct memory writes in the supplied representation. Its explicit memory operations are reads of external references, the gate byte, and the two counter fields.

Its direct action beyond those reads is invoking F-df2c7f3bb9d4. Those calls may have externally visible effects, but their nature is not supplied.

In particular, this contract does not assume that the dependency:

- Decrements either counter.
- Preserves the gate or either external record reference.
- Preserves either record’s contents or lifetime.
- Acquires, transfers, or releases ownership.
- Avoids callbacks, reentrancy, blocking, or abnormal termination.

No allocation, release, ownership transfer, or resource cleanup is explicit in F-ea6b4f7a8762 itself. Record addresses are retained for later access, but retention is not evidence of ownership or a lifetime guarantee.

If the dependency invalidates a retained record address, the next counter access may be invalid. There is no visible revalidation or recovery.

Invalid memory accesses and dependency failures have no specified local handling. The evidence supplies neither a defined error value nor an exception or fault handler. It does not establish a portable outcome for such cases.

## Acceptance examples

These examples are conditional acceptance criteria derived from the static behavior. They are not reports of executed tests.

### Disabled gate

Given a readable gate byte equal to zero:

- The first-record reference is read before the gate decision.
- No counter field is accessed.
- The second-record reference is not read.
- No dependency call occurs.
- The function returns.

This does not require either record address to be dereferenceable, because neither record is accessed on this path.

### Enabled gate with no positive counters

Given a nonzero gate and valid records whose counters are both nonpositive:

- The second-record reference is read.
- The first counter is read and causes the first phase to end without a call.
- The retained second record’s counter is read and causes return without a call.

A negative signed counter behaves like zero for phase continuation. It is not treated as a large unsigned amount of work.

### Finite processing under an explicit dependency assumption

Suppose the first counter starts at two and the second counter starts at one. Further suppose that each selector-0 call reduces the first counter by exactly one, each selector-1 call reduces the second counter by exactly one, and all relevant references and other state remain stable.

The call sequence is two selector-0 calls followed by one selector-1 call. The function then returns after observing the second counter as zero.

The exact call counts depend on those added assumptions, not on the counters’ initial values alone.

### Second-record replacement during the first phase

Suppose a selector-0 call changes the external second-record reference to another valid record and makes the captured first counter nonpositive.

On the next first-phase condition evaluation, the replacement second-record reference is captured before the first counter is read. The second phase therefore uses the replacement record.

### Record-reference replacement during the second phase

Suppose a selector-1 call changes the external second-record reference while the retained record remains valid.

The next second-counter read still targets the retained record. The new external reference is not consulted again during this invocation.

Likewise, changing the first-record reference during selector-0 processing does not redirect first-counter reads away from the record captured at entry.

### Gate changes after entry

Suppose the initial gate is nonzero and a dependency call later clears it.

The function does not retest the gate. Processing continues according to the active phase’s counter.

### No progress

Suppose the first counter remains positive indefinitely and selector-0 calls keep returning.

The function continues selector-0 processing indefinitely. It does not reach selector 1, report an error, or stop because a call limit was reached.
