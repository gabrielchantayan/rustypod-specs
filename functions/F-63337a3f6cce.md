# F-63337a3f6cce

## Purpose

F-63337a3f6cce destructively processes linked records while updating a head field in a separate state object. For each processed record, it replaces the record’s offset-12 field with the current head value, then replaces the head with the record’s address.

Under finite-tree and nonoverlap conditions, processing order is the offset-12 subtree, the current record, then the offset-8 subtree. The resulting offset-12 links connect records in reverse processing order. The first-processed record receives the original head value as its link.

Copying the original head value does not establish preservation of a chain previously reachable from it. If the original head identifies a processed record, processing can create a cycle. Preservation of an existing tail requires additional conditions on the storage containing that tail’s links.

Destructive tree-to-chain conversion is **inferred intent**. The established behavior is the ordered access and mutation described below. Record semantics, ordering keys, and downstream use are not established.

## Interface

### Inputs and partial layouts

The function accepts two 32-bit quantities interpreted as addresses:

- **State address:** identifies storage whose four-byte field at byte offset 4 contains the head value.
- **Starting-record address:** identifies the initial record. Zero means there is no starting record.

The accessed layouts are partial:

| Storage | Byte offset | Transfer width | Role |
|---|---:|---:|---|
| State | 4 | 4 bytes | Read and replace the head |
| Record | 8 | 4 bytes | Read the continuation after recursive processing |
| Record | 12 | 4 bytes | Read the recursive link, then replace it with a head value |

These accesses do not establish complete object sizes, other fields, alignment, packing, or byte order.

Zero is the only value explicitly treated as an absent record. Other values are used as record addresses without validation.

### Output

The function has no return value. Its results are changes to caller-supplied storage.

It does not separately return a status, record count, original head, or final head.

### Widths and arithmetic

The supplied representation establishes 32-bit inputs and four-byte field transfers. The link and head transfers preserve the entire four-byte quantity; no masking, tagging, truncation to a narrower width, or numeric transformation is shown.

Address calculations add fixed byte offsets of 4, 8, or 12. There is no index scaling or record-count arithmetic.

The representation does not establish portable behavior for address overflow, invalid integer-valued addresses, or misalignment. Valid use requires every executed field-address calculation to identify accessible storage without depending on unresolved arithmetic or address-conversion behavior.

### Preconditions for normal completion

For all accesses actually executed:

- Record offset-8 and offset-12 reads must address four readable bytes.
- Record offset-12 writes must address four writable bytes.
- State offset-4 reads and writes must address four readable and writable bytes.
- Storage must remain valid through its last access.
- The traversal induced by values read during execution must terminate within available resources.
- External mutation must not invalidate those conditions.

A zero starting-record address requires no accessible state storage because the function performs no field access on that path.

A finite tree of distinct records, with all accessed record fields mutually nonoverlapping and the state-head field disjoint from them, supports the ordinary traversal interpretation. These structural conditions are not checked. They do not, by themselves, guarantee preservation of a chain identified by the original head.

## Behavior

### Empty input

When the starting-record address is zero, the function returns immediately.

It does not read the head, inspect a record field, or write any caller-supplied field. The state address is not dereferenced or validated.

### Ordered processing of a nonzero record

For each nonzero current record, the established order is:

1. Read the record’s four-byte offset-12 link.
2. Invoke F-63337a3f6cce recursively with the same state address and that link value as the starting record.
3. After the recursive invocation returns, read and retain the current record’s four-byte offset-8 continuation.
4. Read the four-byte state head.
5. Write that head value into the current record’s offset-12 field.
6. Write the current record address into the state’s offset-4 field.
7. Continue within the current invocation using the retained continuation.

A zero continuation ends that invocation’s processing.

This order has several observable consequences:

- Recursive processing completes before the enclosing record’s continuation or head is read.
- The enclosing prepend uses the head present after recursion, not necessarily the head present at entry.
- The continuation is read after recursion, so recursive mutations can affect its value when storage aliases.
- The continuation is retained before either prepend write. Those writes cannot retroactively change the retained value used for the next iteration.
- The record-link write precedes the state-head write. If their destinations overlap, the second write can alter bytes written by the first.

The function does not snapshot the initial head or the reachable record structure before processing.

### Ordinary finite-tree result

Assume:

- A finite tree of distinct records.
- Mutually nonoverlapping accessed record fields.
- A state-head field disjoint from those record fields.
- Valid storage throughout execution.
- No external mutation.

Under these conditions:

- Offset 12 selects the subtree processed before the current record.
- Offset 8 selects the subtree processed after the current record.
- Every reachable record is processed once.
- Offset-8 fields retain their original values.
- Offset-12 fields are replaced with chain links.
- The final head identifies the last-processed record.
- Each processed record links to its immediate predecessor in processing order, except the first-processed record, which links to the original head value.

For a nonempty traversal of N records, following exactly N offset-12 links from the final head reaches the original head value. This is a finite-prefix guarantee. It does not establish that traversal terminates afterward or that all addresses encountered afterward are distinct.

Copying a head value into a record link does **not itself dereference the address represented by that value**. Record accesses at that address can nevertheless occur if it is supplied as the starting record or is subsequently reached through traversal. In particular, the starting-record argument may equal the original head without any record link first leading to it.

### Attachment value versus preserved tail

The original head is used as an attachment value, not automatically traversed as an existing tail.

Three cases must be distinguished:

- **Opaque attachment:** the original head is copied into the first-processed record’s link. The copied value need not identify readable storage if no executed traversal access uses it as a record address.
- **Preserved tail:** if the original head identifies a valid chain, and every offset-12 field in that chain is disjoint from every executed write range, those links remain unchanged.
- **Overlapping attachment:** if existing tail-link storage overlaps an executed write, preservation is not established. An original head that identifies a processed record can produce a cycle.

Relevant write ranges include both processed-record offset-12 fields and the state-head field. Disjointness is a byte-range property, not merely inequality of object addresses.

Given valid lifetimes, a valid original chain, link-storage disjointness, and no external mutation, the reverse-processing prefix is attached to the unchanged tail. Without those conditions, only the copied attachment value is guaranteed. Overlap does not necessarily change a value in every case, but unchanged-tail behavior cannot be assumed.

### Sharing, overlap, and cycles

The function maintains no visited-record set.

A repeated visit to a record can encounter an offset-12 value installed during an earlier visit rather than its original recursive link. Shared records therefore do not automatically behave like independently processed tree nodes.

Aliasing can also change continuation values before they are read, alter the head used by later records, or cause a head write to modify record storage. Such cases must be evaluated using the actual ordered accesses, not the finite-tree result.

An offset-12 self-link causes repeated recursive descent before that record’s prepend occurs, provided no intervening mutation changes the link. Other cycles can cause unbounded recursion, unbounded iteration, repeated mutation, or results unlike a simple chain.

No explicit cycle-detection error is produced.

### Resource behavior

Offset-12 traversal creates recursive invocations. Offset-8 traversal continues within the current invocation.

For a finite tree, simultaneous recursion depends on the active nesting of offset-12 calls, including calls made from records reached through offset-8 continuations. Calls with a zero record return immediately, but are still recursive calls in the supplied body.

There is no explicit recursion-depth limit, maximum-record count, cancellation check, or resource-exhaustion recovery.

## Side effects

### Writes

Each completed prepend performs two four-byte writes, in this order:

1. Store the recently read head into the current record’s offset-12 field.
2. Store the current record address into the state’s offset-4 field.

The original offset-12 traversal link is not restored.

No explicit write targets a record’s offset-8 field. Such a field can nevertheless change if its bytes overlap a write destination. The same applies to other storage that aliases a destination, including links in a preexisting chain.

No additional explicit writes appear in the supplied body.

### Ownership and lifetime

No allocation, deallocation, reference-count change, or ownership-transfer protocol is shown.

Storing an address does not establish ownership, retain the referenced storage, or extend its lifetime. Callers must provide valid storage for accesses during execution. Any later consumer of the resulting links independently requires the referenced storage to remain valid.

### Errors and partial progress

There is no explicit validation, error result, rollback, or recovery path.

Failure during recursive processing can prevent the enclosing record’s prepend while leaving earlier mutations in place. Failure after the record-link write but before the head write can leave those two fields inconsistent with a completed prepend.

The manifestation of invalid memory access, arithmetic failure, or resource exhaustion is environment-dependent and unresolved. Transactional or all-or-nothing behavior is not established.

## Acceptance examples

These are conditional expectations derived from static evidence, not executed tests. Unless stated otherwise, accessed fields are disjoint, storage remains valid, execution completes, and there is no external mutation.

### Empty starting record

Given a zero starting-record address:

- No record or state field is accessed.
- The function returns without mutation.
- The state address need not identify accessible storage for this execution.

### One record with an opaque attachment

Given record A with both traversal links zero and initial head H:

- A’s offset-12 field becomes H.
- The final head becomes A.
- A’s offset-8 field remains zero.
- The stored value H is not used as a record address during this execution.

This example establishes copying, not that H identifies a valid chain.

### Two records connected through offset 12

Given A’s offset-12 link points to B, all other traversal links are zero, and the initial head is zero:

- Processing order is B, then A.
- Final head is A.
- Final offset-12 links form A → B → zero.

### Two records connected through offset 8

Given A’s offset-8 link points to B, both offset-12 links and B’s offset-8 link are zero, and the initial head is zero:

- Processing order is A, then B.
- Final head is B.
- Final offset-12 links form B → A → zero.
- A’s offset-8 link still points to B.

### Root with two descendants

Given root R with offset 12 pointing to B and offset 8 pointing to A, both descendants having zero traversal links, and initial head H:

- Processing order is B, R, A.
- Final head is A.
- The resulting offset-12 prefix is A → R → B → H.

This prefix makes no claim about traversal after H is reached.

### Preserved disjoint tail

Given an original chain T → U → zero and a single processed record A with zero traversal links:

- If the original tail’s link fields are disjoint from A’s offset-12 field and the state-head field, those tail links remain unchanged.
- With initial head T, the resulting chain is A → T → U → zero.

### Starting record equals the original head

Given a single record A with both traversal links initially zero, a separate state-head field initially containing A, and starting-record address A:

- A is accessed because it is the starting record, not because traversal first reaches it through another record.
- Its offset-12 link is read as zero, so recursive processing returns without field accesses.
- Its retained continuation is zero.
- The head read yields A.
- A’s offset-12 field becomes A.
- The final head remains A.

The original chain A → zero becomes a self-cycle. The attachment-value guarantee still holds: one offset-12 link from the final head reaches the original head value A.

### State head overlaps a record link

Given that the state-head field occupies exactly A’s offset-12 field, with both of A’s traversal links initially zero:

- Recursive processing receives zero.
- The retained continuation is zero.
- The head read yields zero.
- The record-link write stores zero in the shared field.
- The state-head write then stores A in that same field.

The final shared field contains A, making A’s offset-12 link point to itself. The ordinary nonoverlapping-tree result does not apply.

### Recursive self-link

Given A’s offset-12 link points to A, with no intervening mutation:

- Recursive descent repeats before A’s prepend.
- Normal completion is not established.
- No explicit cycle error is reported.
