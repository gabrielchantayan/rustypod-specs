# F-221b3a8e8ac1

## Purpose

The established behavior is integer-address arithmetic and conditional indirect dispatch. An enclosing-object/interior-address relationship is plausible intent, but the supplied representation does not establish an object type, allocation layout, lifecycle operation, or ownership protocol.

The associated-pointer field is evaluated once for a null test and, on the non-null branch, evaluated again to obtain the pointer used for dispatch resolution. These are distinct source-level evaluations. Their values are equal only if the field remains stable under the applicable execution model. This does not establish a particular number of physical machine loads.

Neither the named dependency nor the runtime-selected callable has an established allocation, destruction, release, or notification meaning.

## Behavior

### 1. Invoke the named dependency

The function evaluates the input plus 80 and invokes F-0347c6cd67d1 with that value.

There is one visible invocation of this dependency. It precedes the function’s explicit associated-memory reads. If argument evaluation or the dependency does not complete normally, the subsequent local behavior is not reached.

The dependency’s returned integer becomes the retained reference value for:

- Locating the associated-pointer field.
- Computing the final return value.

The dependency is not required by this function to return its argument. Therefore, the initial +80 and final −80 must not be treated as generally cancelling.

No contract for the dependency’s memory effects, global effects, resource effects, or ownership behavior is supplied.

### 2. Evaluate the associated-pointer field for the condition

After the dependency returns, the function evaluates the pointer-valued field at the address represented by the dependency result minus four.

This first field evaluation is unconditional on the visible continuation path. In particular, the dependency result itself is not checked for zero before forming and accessing the field location.

The value obtained by this first evaluation controls the branch:

- A null pointer skips the entire indirect-dispatch expression.
- A non-null pointer enters that expression.

The condition tests the contents of the associated field, not the dependency result.

If the first value is null, there is no second source-level evaluation of this field, no base-value read, and no callable-entry read on that path.

### 3. Evaluate the field again on the non-null branch

When the first value is non-null, the function evaluates the same associated-pointer field a second time. The address of the field is again derived from the retained dependency result minus four.

The value obtained by this second evaluation supplies the address for the following integer read. It is not specified as a cached copy of the value used in the condition.

This distinction limits what the null test proves:

- It establishes that the first observed pointer value was non-null.
- It does not independently establish that the second observed pointer value is non-null.
- It does not establish that the second value identifies readable memory.
- It does not establish that the two observed values are equal.

No visible call or explicit store by this function intervenes between these two source-level field evaluations. That fact is not a synchronization guarantee or a substitute for a field-stability requirement. Whether concurrent or externally induced changes are possible and have defined semantics depends on the execution environment.

The representation establishes two source-level evaluations on this branch, not two verified physical machine loads. Optimization and the target memory model are outside the supplied evidence.

### 4. Resolve and invoke the callable

The function uses the pointer obtained from the second field evaluation to read a signed integer base value.

It then adds four to that base value, interprets the resulting integer-represented address as a location containing a callable pointer, reads that callable pointer, and invokes it.

The resolution has three distinct memory relationships:

- The associated field contains the pointer obtained by the second field evaluation.
- That pointer designates the integer base value.
- The address represented by the base plus four designates the callable-pointer entry.

No additional null check is visible for the second associated-pointer value, the loaded integer base, or the callable pointer.

The call representation supplies no explicit arguments. It does not independently establish the machine calling convention, implicit receiver state, or other register-based call context.
