# F-36c0d5ef5423

## Purpose

F-36c0d5ef5423 conditionally dispatches an operation on an object obtained through an initial indirect call.

The established behavior is a two-stage sequence:

1. Resolve and invoke a function through a table associated with the input object.
2. If that invocation returns a non-null object address, resolve and invoke a function through that returned object’s table, passing the returned address and an integer zero.

A null result from the first invocation ends processing without the second invocation.

This structure is consistent with obtaining an associated object and requesting an operation on it. That interpretation is inferred intent only. The evidence does not establish the objects’ domain, the meaning of either operation, or whether the second call modifies, resets, releases, or destroys anything.

## Interface

### Input

The function accepts one address, interpreted as pointing to an object whose first field is a dispatch-table address.

For the initial dispatch to proceed normally:

- The input address must permit reading its first address-bearing field.
- The resulting table address must permit reading a function address at byte offset 252, hexadecimal 0xFC.
- That function address must identify a callable target compatible with the actual calling convention.

There is no explicit check for a null input, a null table address, or a null function address.

The supplied representation uses an integer-pointer type for the input and an integer-sized load for the table address. This supports a 32-bit address-bearing layout, but does not independently establish a complete platform ABI. The byte offsets are established; pointer width, argument placement, and related ABI details require confirmation outside this evidence.

### Output

No caller-visible return value is specified. The function either:

- Returns after the first call produces a null address; or
- Invokes the second target and then returns if that target returns normally.

The result of the second invocation, if any, is not used.

### Intermediate result

The first indirect call produces a value interpreted as an object address. Only equality with null is tested.

For a non-null result, normal continuation requires:

- The returned address to permit reading its first address-bearing field.
- That field to identify a dispatch table with a readable function-address entry at byte offset 160, hexadecimal 0xA0.
- The selected function to be callable with the returned object address and integer zero under the actual ABI.

Non-nullness alone does not establish validity, alignment, lifetime, or ownership.

## Behavior

### Initial dispatch

The function first reads the dispatch-table address from the beginning of the input object. It then reads the callable address stored at byte offset 252 within that table and invokes the selected target.

The supplied representation shows no explicit arguments for this first invocation. It therefore does not establish that the input object is passed as an explicit receiver. An implicit receiver or other ABI-carried context remains unknown.

Both dispatch-resolution reads occur before the first call. There is no other explicitly represented memory access or call between them.

The returned value is interpreted as an object address and checked against null.

### Null-result branch

If the first invocation returns null, F-36c0d5ef5423 returns immediately.

On this branch:

- No returned object is dereferenced.
- No dispatch entry at offset 160 is read.
- No second target is invoked.
- No local cleanup or compensating operation is represented.

The first invocation has already occurred and may have produced side effects. Returning early does not imply that the overall operation had no effect.

### Non-null-result branch

If the first invocation returns a non-null address, the function reads the dispatch-table address from the beginning of that returned object.

It then reads the callable address at byte offset 160 within that table and invokes the selected target with two explicit arguments, in this order:

1. The returned object address.
2. Integer zero.

After that invocation returns normally, F-36c0d5ef5423 returns. No further operation on either object is represented.

The returned object may be the input object, a different object, or an alias into other storage. There is no identity comparison or branch based on the relationship between the two addresses.

### Layout and arithmetic

Both dispatch offsets are byte offsets:

| Dispatch | Table entry byte offset | Explicit arguments |
|---|---:|---|
| Initial | 252 / 0xFC | None represented |
| Conditional second | 160 / 0xA0 | Returned object address, integer zero |

These offsets are not counts of entries. Under a four-byte-entry layout, they correspond to zero-based entries 63 and 40, respectively. Those entry numbers are conditional layout interpretations, not independently established interface requirements.

No loop, count calculation, sign-dependent branch, or data-dependent offset calculation is represented. The only explicit branch tests the first result for null. Integer zero has no signedness ambiguity at the value level; its argument width and extension behavior remain ABI-dependent.

### Ordering across calls

The second object’s table address and callable entry are read after the first invocation returns. They are not resolved in advance.

Consequently, the first target may affect the state used by the second dispatch. For example, it may return an object whose current dispatch table differs from an earlier state. The wrapper uses the table address read after the return.

No preservation of globals, input-object contents, or other shared state by the first target is established. After the first call, the wrapper does not explicitly reread the original input merely to resolve the second dispatch; it uses the returned address.

## Acceptance examples

These are conditional contract examples, not executed tests. Each assumes valid storage and callable targets unless explicitly stated otherwise.

### First target returns null

Given an input whose offset-252 entry selects a normally returning target that produces null:

- The initial target is invoked once.
- The wrapper returns without reading a returned object.
- No second target is invoked.

Any side effects of the initial target remain outside the wrapper’s null-result handling.

### First target returns a distinct valid object

Given an initial target that returns a valid object different from the input:

- The second dispatch is resolved from the returned object, not the input.
- Its table entry at byte offset 160 is selected.
- The selected target receives the returned object address followed by integer zero.
- The wrapper returns if that target returns normally.

### First target returns the input object

Given an initial target that returns the input address:

- The result is treated as non-null.
- The wrapper reads the table address from that object after the initial call.
- The offset-160 target is invoked with the same object address and zero.

There is no special handling for address equality.

### Initial call changes dispatch state

Given an initial target that changes the returned object’s table address before returning:

- The second dispatch uses the table address subsequently read from the returned object.
- It does not use a table address captured before the initial invocation.

This example assumes that the changed object and table remain valid through dispatch.

### First target returns invalid non-null storage

Given a non-null result that cannot support the required header read:

- The null branch is not taken.
- The wrapper attempts the second dispatch-resolution sequence.
- No graceful rejection or error return is established.

### Second target returns a value

Given a second target that returns normally with a value:

- The wrapper does not inspect or forward that value.
- No additional wrapper action is represented before return.
