# F-0d56c9347cca

## Purpose

F-0d56c9347cca conditionally adjusts a candidate index in a caller-supplied state object, waits for candidate-associated readiness when necessary, and commits an index and an associated 32-bit value.

The established behavior is numeric and structural. Interpreting the indices as positions, the associated values as timestamps, or the processing dependency as a loader is inferred intent, not an established interface guarantee.

There are three mode classes:

- **Mode 2:** return success without committing state.
- **Mode 0:** enforce an initial upper-bound check and, under qualifying conditions, move toward larger indices.
- **Every other mode:** under qualifying conditions, move toward smaller indices.

Both ordinary completion and mode-2 bypass return `0`. Several early exits return `3`. The meanings of these codes beyond their observed control-flow roles are unknown.

## Interface

### Inputs and result

The function accepts:

1. A state-object address represented by a 32-bit input.
2. A 32-bit mode, tested for equality with `0` and `2`.

It returns a 32-bit value, limited by the supplied evidence to `0` or `3`.

The state address is not checked for nullness, alignment, or accessible extent. The initial candidate-index read occurs even in mode 2.

### Referenced state layout

Offsets below are byte offsets from the state address. All scalar fields and array elements shown are 32 bits. Comparisons use signed interpretation unless explicitly described otherwise.

| Offset | Role established by use |
|---|---|
| `0x40` | Address of a separate object whose first 32-bit word supplies a count |
| `0x58` | Limit used during readiness processing |
| `0x9c` | Value supplied as the low word of a dependency argument, with a sign-derived high word |
| `0xa8` | Low word used to construct a scaled two-word argument |
| `0xac` | High word used to construct that scaled argument |
| `0x21c` | Stored candidate index |
| `0x220` | Current comparison value and eventual destination for a selected array value |
| `0x228` | Address of a readiness array |
| `0x22c` | Address of an associated-value array |

Both arrays are accessed at a byte displacement of four times the candidate index. A readiness element equal to zero means processing must continue before that candidate can be evaluated. Any nonzero readiness element is accepted.

The count, limit, array addresses, and comparison value are read from state as execution proceeds. They are not all captured at entry.

### Memory and arithmetic preconditions

For defined, usable operation:

- The state object must support all accesses reached on the selected path.
- The count address and array addresses must be valid whenever dereferenced.
- Every array element actually accessed must be accessible, including elements reached after dependency calls.
- Arithmetic used for indexing and signed comparisons must have a defined interpretation on the execution platform.
- Dependencies must meet whatever validity requirements apply to their arguments.

The function does not establish these conditions itself. In particular, it does not reliably guard against an empty collection, a negative count, or an inaccessible array element.

## Behavior

### Entry and bypass

The stored candidate index is read first. A separate local 32-bit working value is initialized to zero.

If the mode is `2`, the function returns `0`. It performs no direct state write and calls neither dependency. This is not a memory-free bypass: reading the stored index still requires a valid state address.

For mode `0`, the function next reads the count through the address at `0x40`. If the candidate is at least count minus one, it returns `3`.

This check precedes normalization of negative candidates. For example, with a count of zero and candidate `-1`, mode `0` returns `3` rather than normalizing the candidate.

Other modes do not perform this initial rejection.

### Candidate normalization and immediate stopping

For all non-bypass paths that survive the initial check:

- A negative candidate becomes zero and proceeds directly to commitment.
- A nonnegative candidate enters candidate evaluation.

At the start of evaluation, the count is read. If the candidate is at least that count, the function proceeds toward commitment without consulting readiness.

If that first comparison does not stop evaluation, the current comparison value at `0x220` is read. A zero value also stops evaluation before any readiness-array access.

These stopping paths apply an upper adjustment before commitment: the count is read again, and a candidate greater than count minus one is replaced by count minus one. When replacement is required, the expression producing the replacement reads the count again.

Consequently, this is not an atomic clamp against a single captured count. A count that changes between reads can affect the test and replacement differently.

A negative candidate normalized directly to zero does not pass through this upper adjustment.

### Readiness processing

If evaluation continues, the function reads the readiness element for the candidate.

A nonzero element skips readiness processing. A zero element causes a call to **F-1e0edc6e0bc9** to initialize the local working value.

The first two arguments are two 32-bit words constructed as follows:

- The value at `0xa8` is interpreted as unsigned and multiplied by `1000`, producing a 64-bit product.
- The low 32 bits of that product form the first argument.
- The high 32 bits of that product are added to the value at `0xac` multiplied by `1000`, forming the second argument subject to 32-bit arithmetic constraints.

The remaining two arguments come from the value at `0x9c`: one read supplies the value, and another supplies its sign-derived high word through a right shift by 31. If the field remains stable and the shift is arithmetic, these form a sign-extended two-word value. The supplied evidence does not establish a dependency-level interpretation such as division, time conversion, or unit normalization.

F-1e0edc6e0bc9’s 32-bit result replaces the local working value.

The readiness element is then checked again. Thus, initialization can be followed by zero calls to the second dependency if readiness has become nonzero.

While readiness remains zero:

1. A proposed working value is formed by adding `10000` to the current working value.
2. The limit at `0x58` is compared with that proposal.
3. If the limit is less than or equal to the proposal, the proposal is instead formed by adding `1000` to the previous working value.
4. The chosen proposal becomes the working value.
5. **F-616a3e217b7c** is called with the state address, the address of the local working value, and a third argument of zero.
6. A nonzero dependency result causes immediate return of `3`.
7. Otherwise, the limit is read again. If it is less than or equal to the possibly dependency-modified working value, the function returns `3`.
8. Otherwise, readiness is checked again.

The two increments are alternatives, not cumulative additions. The smaller increment is selected when the larger proposal reaches or exceeds the limit. The smaller proposal is not checked against the limit until after the dependency call.

There is no iteration bound. Termination depends on readiness, dependency results, limit comparisons, and any mutations performed by dependencies or external actors.

### Candidate-value comparison and movement

Once readiness is nonzero, the function reads:

1. The current comparison value at `0x220`.
2. The associated-value array address and the candidate’s element.

It computes a branch-selected difference: the larger signed value minus the smaller signed value. When representable, this is their nonnegative absolute difference.

A difference of at least `2000` stops movement. A candidate less than `1` also stops movement. These stops lead through the upper adjustment described above and then to commitment.

A candidate whose difference is at most `1999` and whose index is positive undergoes another count check:

- If the candidate is at least count minus one, movement stops and commitment follows the upper adjustment.
- Otherwise, mode determines the next action.

For a nonzero mode other than the already-bypassed mode `2`, the candidate decreases by one and evaluation restarts.

For mode `0`, another count read occurs:

- If that read says the count is less than or equal to the candidate, evaluation repeats at the same candidate.
- Otherwise, the candidate increases by one and evaluation restarts.

With a stable count, the earlier upper-end check means the mode-0 repeat-at-the-same-candidate case is not normally reached. It remains part of the observed behavior when count reads differ.

### Commitment

Commitment has the following direct read/write order:

1. Write the selected candidate to `0x21c`.
2. Read the associated-value array address and selected element.
3. Write that element to `0x220`.
4. If the selected element is zero and mode is `0`, read the count.
5. If the selected candidate is less than count minus one, overwrite `0x21c` with candidate plus one.

The optional final increment does **not** refresh `0x220`. The final stored index can therefore identify the next element while the stored value still comes from the preceding selected element.

The function then returns `0`.

## Side effects

Direct persistent writes are confined to `0x21c` and `0x220`, including the optional second index write. Readiness, count, limit, and array contents are not directly written by this function.

Early returns of `3` occur before these direct commitment writes. This does not guarantee that state is unchanged: F-616a3e217b7c receives the state address and may already have modified it. Neither dependency is established to preserve globals or other accessible state.

The local working value is writable by F-616a3e217b7c. Its address refers to function-local storage. The evidence establishes neither permission to retain that address beyond the call nor any ownership transfer.

No allocation, release, or ownership transfer is directly visible. Nothing establishes whether either dependency allocates, releases, retains, or otherwise affects memory.

The function offers no rollback. A failure after dependency activity preserves whatever effects that activity produced.

## Acceptance examples

These are conditional static acceptance cases, not results of runtime tests. Unless otherwise stated, referenced memory is valid, arithmetic is representable, counts remain stable, and dependencies do not introduce unmentioned changes.

1. **Mode-2 bypass**  
   Given mode `2`, the function reads the stored index and returns `0`. Neither dependency is called, and neither commitment field is directly written.

2. **Mode-0 upper-end rejection**  
   Given count `5`, stored index `4`, and mode `0`, the function returns `3` before readiness or associated-value access.

3. **Negative-index normalization**  
   Given count `5`, stored index `-3`, and mode `1`, the selected index becomes `0`. The function commits index `0` and associated element `0` without checking readiness.

4. **Initial zero comparison value**  
   Given count `5`, index `2`, mode `1`, and comparison value zero, readiness is not read. Index `2` and its associated value are committed.

5. **Threshold boundary**  
   Given count `5`, index `2`, mode `1`, ready candidates, comparison value `10000`, and associated value `8000`, the difference is `2000`; movement stops at index `2`. With associated value `8001`, the difference is `1999`, so evaluation continues at index `1`.

6. **Forward movement**  
   Given count `5`, mode `0`, index `1`, ready entries, and a difference below `2000` at index `1`, evaluation advances to index `2`. Subsequent behavior depends on the values and readiness encountered there.

7. **Dependency failure**  
   Given a zero readiness element, if F-616a3e217b7c returns nonzero on its first call, the function returns `3`. It performs no direct commitment writes, but dependency effects are not rolled back.

8. **Limit equality**  
   If F-616a3e217b7c returns zero and leaves the working value equal to the subsequently read limit, the function returns `3`; equality is sufficient.

9. **Final index/value mismatch by design**  
   Given count `5`, mode `0`, selected index `2`, selected associated value zero, and a comparison difference large enough to stop movement, commitment first stores index `2` and value zero. It then changes only the index to `3` and returns `0`.

10. **Empty-count hazard**  
    Given count zero, mode `1`, and a nonnegative initial index, upper adjustment can produce index `-1`, followed by an associated-value access at that index. No safe empty-collection result is established.

## Uncertainties

The following are **documented_only**, not behavior to invent:

- Domain meanings and units of the count, comparison values, limit, and working value.
- Dependency semantics beyond their visible argument and return usage.
- Dependency effects on memory, globals, ownership, and termination.
- Synchronization, atomicity, and support for concurrent mutation.
- Overflow behavior for signed additions, subtractions, multiplication, count-minus-one calculations, and index-address calculations.
- Whether right shift of a negative signed value is guaranteed to be arithmetic by the original execution environment.
- Argument-expression evaluation order where multiple field reads appear within one call.
- Valid behavior for malformed pointers, inaccessible elements, negative counts, and empty arrays.

The unsigned low-word multiplication has an explicit 64-bit intermediate. Other arithmetic is expressed using 32-bit quantities. In particular, subtracting two signed values can overflow even when intended as an absolute difference. The `2000` threshold interpretation is established for representable differences; it must not be extended to overflowing cases without additional platform evidence.
