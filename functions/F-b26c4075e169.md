# F-b26c4075e169

## Purpose

F-b26c4075e169 obtains a main-object pointer, writes several initialization fields, conditionally obtains and publishes a companion pointer, invokes operations through dispatch tables, and returns the original main-object pointer.

“Main object,” “companion,” and “dispatch table” describe the observed access patterns. Their application-level meanings are not established.

The conditional creation path depends on a shared-pointer slot at byte offset 100 in a context. Crucially, the function reads the context-pointer global twice:

- The first value is retained for subsequent publication and for the argument supplied to a main-object operation.
- The second value identifies the context whose shared-pointer slot controls the branch.

These values are not established to be identical. Interpreting the function as initializing a single shared context requires an explicit stability assumption.

The apparent intent is object initialization with lazy establishment of a shared companion. The established contract is narrower: it specifies local reads, writes, calls, and their ordering, without guaranteeing successful construction, ownership transfer, or thread-safe initialization.

## Interface

| Position | Represented width | Visible use |
|---|---:|---|
| First | 32 bits | No explicit use. |
| Second | 32 bits | Written to main-object byte offset 48. |
| Third | 32 bits | Written to main-object byte offset 52. |

The second and third inputs are represented as signed integers, but the function performs no arithmetic, comparison, range check, or explicit conversion on them. Their 32-bit representations are written unchanged.

The first input is not explicitly forwarded to another operation. Its API meaning and any significance outside the visible body are **documented_only**.

### Output

On normal completion, the function returns the same main-object pointer supplied by F-ff4dff756de0.

The return value is not an explicitly computed success indicator. There is no local alternative return for a null dependency result, invalid context, or failed indirect operation.

Returning the same pointer does not establish that the pointed-to storage remains valid: that also depends on the intervening dependencies.

The visible body does not validate its addresses. Normal completion requires, at minimum:

- The main-object result permits the stated writes through byte offset 55.
- The context obtained by the second context-global read permits reading four bytes at offset 100.
- The context retained from the first read permits the later four-byte read at offset 100 and, when the creation branch executes, a four-byte write there.
- On the creation path, the companion result permits a four-byte write at offset zero.
- Each dispatch-table address permits reading its selected four-byte target slot.
- Each selected target is callable using the represented invocation.

Address additions must designate valid locations in the represented execution environment. The body supplies no bounds checking or overflow recovery. Complete allocation sizes, alignment rules, and behavior for invalid address arithmetic are **documented_only**.

## Behavior

### 1. Obtain and initialize the main object

The first explicit call is to F-ff4dff756de0, with no explicit arguments shown. Its result is retained as the main-object pointer and ultimately used as the return value.

The following direct effects occur in order:

1. Read the main dispatch-table global and write that four-byte value to main-object offset zero.
2. Write the single byte one at offset 40.
3. Write four-byte zero at offset 44.
4. Write the second input’s 32-bit representation at offset 48.
5. Write the third input’s 32-bit representation at offset 52.

These operations precede both context-global reads.

These are initialization-time writes, not unconditional guarantees of final contents. Subsequent dependencies, or aliasing among the accessed locations, may change those fields.

### 2. Read the context global twice and choose the branch

After the main-object writes, the function performs two distinct reads of the context-pointer global:

1. It reads the global and retains that pointer value.
2. It reads the global again and uses this second pointer value to read the four-byte shared-pointer slot at offset 100.

The shared-pointer value read through the second context pointer is compared with zero:

- Zero enters the companion-creation branch.
- Any nonzero 32-bit value skips that branch.

The second context pointer controls branch selection only. The retained first context pointer is used for the later publication and the later shared-slot argument read.

There is no visible dependency call between the two context-global reads. Nevertheless, the supplied representation contains two reads, not one read reused twice. Equality of their results requires a stability assumption; the contract does not silently supply one. Whether a particular execution can expose different values depends on the execution environment and its memory-access rules.

After these two reads, the body does not explicitly reload the context-pointer global. Later changes to that global do not, by themselves, replace the retained pointer used for subsequent slot accesses.

### 3. Conditionally obtain and publish the companion

If the slot read through the second context pointer is zero, the function performs these operations in order:

1. Call F-8157a180d901 with the numeric argument eight.
2. Call F-b45f9214930f with no explicit arguments shown and retain its result as the companion pointer.
3. Read the companion dispatch-table global and retain that table value for the companion indirect call.
4. Read the companion dispatch-table global again and write this second value to companion offset zero.
5. Write the companion pointer to offset 100 of the context retained from the first context-global read.
6. Read the target at byte offset 24 of the retained companion-table value and invoke it with no explicit arguments shown.

The two companion-table global reads are distinct. The table value used to select the indirect target comes from the first read. The value installed in the companion comes from the second read. They coincide only if those reads obtain the same value.

The indirect call is therefore not specified as a fresh dispatch through the companion’s installed table. Nor does the supplied invocation establish an explicit companion-pointer argument or a particular hidden calling convention.

Publication precedes the companion indirect call. At that call’s entry, the publication write has already occurred, subject to any intervening aliasing effects. This ordering does not prove that the companion is fully initialized or safe for other users.

The function does not check the retained context’s slot before publication. In particular:

- A zero slot in the second context can trigger a write to an already nonzero slot in the retained first context.
- Changes to either slot during the direct dependency calls do not cause the branch decision to be reevaluated.
- Publication does not explicitly release or otherwise dispose of a value previously present in the destination slot.

The value eight is established only as an argument to F-8157a180d901. Its interpretation as a size, alignment, or resource request is unknown. No result from that call is explicitly consumed. The companion pointer comes from F-b45f9214930f.

### 4. Invoke the first main-object operation

After either branch, the function obtains:

- The main object’s current dispatch-table pointer and the target at its byte offset 84.
- A fresh four-byte value from offset 100 of the retained first context.

It calls that target with two explicit arguments:

1. The main-object pointer.
2. The freshly read shared-slot value.

The shared-slot argument is not the value used for branch selection unless the relevant contexts and slot contents happen to coincide.

On the creation path, it is also not unconditionally the pointer just published. The companion indirect operation may have changed the retained context’s slot, including clearing it to zero.

The dispatch lookup uses the main object’s current table, not necessarily the value written during initial setup. Intervening dependencies may have changed it.

Both the dispatch target and shared-slot argument are obtained before the call. The supplied expression does not establish a finer ordering between those operand reads.

### 5. Invoke the second main-object operation

After the first main-object operation returns, the function again reads the main object’s current dispatch-table pointer. It selects the target at byte offset 92 and calls it with:

1. The main-object pointer.
2. The integer value one.

A table change made by the preceding operation can affect this target selection.

No visible return value from either main-object operation is consumed.

### 6. Return

After the second main-object operation returns, the function returns the originally retained main-object pointer.

There is no explicit release, rollback, context restoration, or clearing of the published slot.

## Side effects

The direct memory effects are:

- Five main-object writes with the widths and order specified above.
- On the creation path, a four-byte companion-table write.
- On that same path, a four-byte publication into the context retained from the first global read.

The function also invokes three named direct dependencies and up to three unresolved indirect targets. Their additional effects are unknown.

No explicit error-status check, exception handler, or rollback mechanism is visible. If a dependency fails to return normally, later operations and the final return are not established to occur. Earlier writes may already have happened.

Ownership is **documented_only**. The body neither establishes that either returned dependency pointer is newly allocated nor establishes borrowing, reference counting, or lifetime transfer. Unknown callees must not be assumed to preserve globals or to retain, own, or release any object.

Synchronization and reentrancy guarantees are **documented_only**. No explicit lock, atomic initialization protocol, or initialization-in-progress marker appears. A shared-slot zero test followed by later publication is not evidence of once-only initialization.

Aliasing restrictions are also unknown. The main object, companion, contexts, globals, and dispatch tables are not proven disjoint. Statements about untouched bytes or unchanged slot contents therefore require the absence of overlapping writes and dependency mutations.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless stated otherwise, storage and targets are valid, dependencies return normally, and no additional mutation or aliasing changes the locations being discussed.

### Stable context with an existing companion

If both context-global reads obtain the same pointer and that context’s slot tests nonzero:

- Neither creation-path direct dependency is called.
- The main-object initialization writes precede the two context-global reads.
- The offset-84 operation receives a fresh slot value from that same context.
- The offset-92 operation follows with one.
- The original main-object pointer is returned.

This example explicitly assumes context-pointer stability; it is not the unconditional branch contract.

### Different contexts, second slot nonzero

Suppose the first context-global read obtains context A, whose slot is zero, while the second obtains context B, whose slot is nonzero.

Then:

- Companion creation is skipped because B’s slot controls the branch.
- The offset-84 operation receives A’s freshly read slot value, zero under the stated conditions.
- There is no local fallback creation attempt for A.

A contract that branches on A’s slot would reject behavior supported by the source.

### Different contexts, second slot zero

Suppose the first read obtains context A, whose slot already contains a pointer, while the second obtains context B, whose slot is zero.

Then:

- The creation path executes.
- The new companion is published into A’s slot, overwriting its previous value.
- The publication does not directly target B’s slot.
- No explicit release of A’s previous pointer occurs.
- If the companion operation leaves A’s slot unchanged, the offset-84 operation receives the newly published pointer.

### Mutation after publication

If the companion indirect operation replaces the retained context’s shared slot, the offset-84 operation receives the replacement.

If it clears that slot, the operation receives zero. There is no second zero check or creation attempt.

### Distinct companion-table reads

If the first companion-table global read yields table T and the second yields table U, the companion receives U at offset zero, while the companion indirect target is selected from T at offset 24.

This criterion applies only where the execution environment permits the reads to differ; it does not assert that such a difference occurs.

### Main dispatch mutation and input preservation

If the offset-84 operation changes the main object’s table and returns, the offset-92 target is selected from the changed table.

An all-ones second input is written as the all-ones 32-bit representation at offset 48; the same rule applies independently to the third input at offset 52. The byte write at offset 40 leaves bytes 41–43 unchanged unless another overlapping write or dependency changes them.

### Invalid main-object result

If F-ff4dff756de0 returns null, the function does not explicitly select a clean failure return. The next visible operation attempts the dispatch-table write through that result. Fault behavior is outside the established normal-completion contract.
