# F-b146e4b90359

## Purpose

F-b146e4b90359 computes a length-like integer from a bounded, zero-terminated sequence of unsigned 16-bit values. Each nonzero value contributes one, two, or three units according to its numeric range. The returned result includes one additional unit, even when no input values are processed.

The contribution thresholds match the byte lengths of independently encoding values below 0x10000 using a UTF-8-like scheme. That interpretation is **inferred intent**, not an established encoding guarantee. The function does not generate encoded bytes, validate Unicode scalar values, or combine surrogate pairs.

The established behavior is a numeric calculation over individual 16-bit values, stopped by either a zero value or the supplied processing limit.

## Interface

The function accepts two inputs:

- **Sequence address:** A nullable pointer to unsigned 16-bit elements. A non-null address must support every read the function actually reaches.
- **Processing limit:** A signed integer restricting the number of nonzero elements that may contribute to the result.

It returns a signed integer containing the accumulated contributions plus one, subject to the arithmetic-representability limitations described below.

The sequence is not returned, modified, copied into another buffer, or retained by any visible operation. There is no output-buffer argument.

### Widths and representation

The supplied representation identifies sequence elements as unsigned 16-bit quantities. Their numeric range is therefore 0 through 65535, inclusive. Adjacent elements are read by advancing one 16-bit element at a time, not one byte at a time.

The limit, accumulator, and return value use the same signed integer type. The supplied material does not independently establish the ABI or its integer width. A 32-bit signed integer interpretation is plausible, but remains an assumption rather than a portable guarantee of this contract. The overflow discussion therefore states both the general representability requirement and its consequences if the integer width is 32 bits.

The function receives typed element values, not a byte-stream format. It performs no explicit byte-order conversion. Mapping raw bytes to those values depends on the execution environment.

### Preconditions

For a non-null sequence address and a positive limit:

- Each element reached before stopping must be readable.
- The address must satisfy the execution environment’s requirements for reading unsigned 16-bit elements.
- Storage must remain valid during the call.

The caller need not provide readable storage for the full limit if an earlier readable zero element stops processing. Conversely, without an earlier zero, the caller must provide all elements the positive limit allows the function to read.

A null sequence address requires no readable storage, regardless of the limit.

## Behavior

### Empty and disabled cases

The accumulated contribution begins at zero.

If the sequence address is null, no sequence element is read. The function returns one for every limit, including positive, zero, and negative limits.

If the sequence address is non-null but the limit is zero or negative, no sequence element is read. The function again returns one. A negative limit is not converted to an unsigned count and does not request a large traversal.

### Traversal and stopping

For a non-null sequence address with a positive limit, elements are examined in increasing address order.

Each reached element is read before its value is classified. A value of zero stops traversal immediately and contributes nothing. No later element is read.

A nonzero value contributes according to this table:

| Element value | Contribution |
|---|---:|
| 0x0001 through 0x007F | 1 |
| 0x0080 through 0x07FF | 2 |
| 0x0800 through 0xFFFF | 3 |

After a nonzero element contributes, traversal advances to the next element and the remaining limit decreases by one.

At most the initial positive limit’s number of elements is read. If that many nonzero elements are processed, traversal stops without reading the following element. A zero immediately beyond the allowed span is therefore neither read nor required.

If a zero is encountered within the allowed span, that zero is itself a read element, although it adds nothing and stops processing before any traversal beyond it.

### Result

For all executions within the arithmetic and memory preconditions, the result is one plus the sum of the contributions of the processed nonzero elements.

The additional one is unconditional. It does not depend on whether:

- The sequence address is null.
- The limit allows any reads.
- A zero element is encountered.
- Processing stops because the limit is exhausted.

The apparent purpose of the additional unit is space for an encoded terminator. That purpose is inferred. No terminator, output buffer, or encoded representation is actually written.

### Treatment of character-like values

All nonzero values are classified numerically. There are no exceptions for reserved code points, noncharacters, or surrogate values.

In particular:

- Every value from 0xD800 through 0xDFFF contributes three.
- A high-surrogate/low-surrogate pair contributes six in total.
- An isolated surrogate also contributes three.
- Zero always terminates traversal; it cannot contribute an embedded encoded zero.

Thus, this function must not be specified as a validating UTF-16-to-UTF-8 size calculation. Such a calculation could combine a surrogate pair into a single supplementary character or reject isolated surrogates; neither behavior occurs here.

### Arithmetic boundaries

Every processed nonzero element adds a positive amount. The final addition of one must also be representable.

For a signed integer type with maximum value *M*, a defined result requires the accumulated contribution to be at most *M* − 1. Merely keeping the accumulation at *M* is insufficient because the return calculation adds one.

If the signed integer type is 32 bits, its maximum is 2,147,483,647. Under that assumption:

- At most 2,147,483,646 one-unit contributions fit with the final additional unit.
- At most 1,073,741,823 two-unit contributions fit.
- At most 715,827,882 three-unit contributions fit.

Mixed sequences require checking their actual contribution sum. These arithmetic bounds do not establish that such large memory regions are accessible.

No overflow check, saturation, or explicit failure result is visible. Wrapping behavior must not be promised from the supplied evidence.
