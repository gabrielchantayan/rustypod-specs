# F-64e4b5213ed5

## Purpose

F-64e4b5213ed5 performs a service-dependent setup of a caller-supplied object. It first invokes an external operation on that object, then looks up a service through a second object. A null lookup result produces two diagnostic calls and return value 7. A nonnull result is stored in the destination, a subordinate setup function is invoked, and several destination fields are populated before return value 0.

The apparent intent is initialization of a decoder-like object using a PostScript-related naming or character-map service. That interpretation comes from labels associated with the lookup and diagnostic arguments. It is not necessary to the behavioral contract, and the supplied evidence does not establish the literal contents of those strings.

This contract distinguishes visible operations from unknown dependency behavior. In particular, the first external operation is not established to clear memory, and the subordinate setup function is not established to succeed merely because this function returns 0.

### Result

- **7:** the service lookup returned zero and both diagnostic calls returned.
- **0:** the lookup returned nonzero and the remaining calls, reads, and writes completed.

No other ordinary return value is selected by the visible function. A dependency that faults, throws, terminates execution, or otherwise fails to return may prevent either result.

Return value 0 does not establish that F-091a82f7a774 reported success. Its result, if any, is not used in the visible control flow.

## Behavior

### Initial external operation

Before the lookup or any explicit destination-field write, the function invokes an external dependency with:

1. A1;
2. `0x5E0`.

The dependency’s opaque function ID and semantics are unavailable. Its return value is not used.

This operation is unconditional. Consequently, the function is not established to leave the destination unchanged when service lookup later fails. Describing this operation as zero-initialization, allocation, release, or a guaranteed 1504-byte write would exceed the evidence.

After this call returns, the function reads the 32-bit value at A2 plus `0x60`. It passes that value and a fixed string address to F-c79a29304dfd.

The source-context read occurs after the initial external operation. If that operation changes the memory at A2 plus `0x60`, including through aliasing, the lookup receives the changed value.

### Null-service path

If F-c79a29304dfd returns zero:

1. F-4457a9a44a68 is called with one fixed diagnostic string address.
2. F-4457a9a44a68 is called again with a different fixed diagnostic string address.
3. The function returns 7.

The order of the two diagnostic calls is fixed.

This path does not invoke F-091a82f7a774. It does not perform the explicit destination-field writes of the nonnull-service path, read the global table pointer, or read A2 plus `0x10`.

These exclusions apply only to the visible operations of F-64e4b5213ed5. They do not constrain writes, reads, or other effects performed internally by the initial external operation, the lookup, or either diagnostic call.

There is no visible rollback or cleanup on this path.

## Side effects

The function directly writes caller-addressed memory and invokes dependencies that may have additional effects.

The explicit service-result write occurs before F-091a82f7a774, so that dependency can observe the stored value if it accesses that field. The later explicit stores occur after the dependency returns. The visible function neither restores dependency-modified state generally nor guarantees preservation of globals.

The null-service path makes two diagnostic calls. Their destination, formatting behavior, buffering, and failure behavior are unknown. The supplied labels suggest an initialization-related message followed by a missing-module message, but literal output is not established.

There is no explicit allocation, deallocation, reference-count adjustment, or ownership transfer in the visible body. Storing the service value and the three table words does not itself prove acquisition of ownership or a future release obligation. Dependencies may manage resources internally; that remains undocumented.

## Acceptance examples

These are conditional acceptance cases derived from static evidence. They are not executed tests.

### Byte-width argument

If A8 is `0xA5`, the explicit store at destination `0x5CC` writes the single byte `0xA5`. Acceptance must not require a 32-bit store there or any particular value in the following three bytes.

### Subordinate setup changes the source field or global pointer

Assume F-091a82f7a774 changes the source field at A2 plus `0x10` or replaces the global table pointer before returning.

The subsequent operations must use the field and pointer as read after that call. Entry-time snapshots would not satisfy the visible ordering.

### Table overlaps destination

If the write at destination `0x5D4` overlaps table storage, the values subsequently stored at `0x5D8` and `0x5DC` must still be the entries already read from table offsets `4` and `8`. Re-reading those entries after the first table-derived write could change observable behavior.
