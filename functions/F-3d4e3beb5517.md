# F-3d4e3beb5517

## Purpose

F-3d4e3beb5517 performs an unconditional indirect operation on a caller-supplied object, optionally performs a second indirect operation on that same object, and then writes the integer value one through a global destination reference.

The established behavior is an ordered sequence of dispatches followed by a store. Object destruction, resource release, state reset, and completion signaling are possible interpretations, but none is established by the supplied evidence. In particular, the interface does not establish whether the object remains usable after either indirect operation.

This contract describes the visible body and its dependency boundaries. Effects inside the indirect callees remain unknown.

## Interface

### Inputs

The function accepts two inputs:

- **Object reference.** A pointer to an object whose leading integer-sized field supplies the address used for indirect dispatch.
- **Conditional flag.** A by-value integer. Zero suppresses the second indirect operation; every nonzero value selects it.

The object reference is supplied unchanged as the first argument to both indirect operations. The second operation additionally receives an integer zero. The conditional flag itself is not forwarded to either operation.

There are no explicit length, capacity, ownership, allocator, or error-reporting arguments.

### Output

The function has no explicit return value. On the visible normal-return path, it completes the selected indirect operations and performs the final global store.

There is no returned success indicator, dependency result, or previous global value. Any return value produced by an indirect callee is unused by the visible body.

### Representation and widths

The supplied representation declares the leading object field and conditional flag using the integer type `int`. It does not independently establish the target ABI, integer width, pointer width, alignment requirements, or byte order. A concrete integration contract must obtain those facts elsewhere.

The dispatch accesses use byte offsets:

| Dispatch | Offset from the table address obtained from the object | Arguments |
|---|---:|---|
| First, unconditional | 0x20, or 32 bytes | Object reference |
| Second, conditional | 0x34, or 52 bytes | Object reference, integer zero |

These are byte displacements, not established table indices. Converting them into entry numbers would require a confirmed entry layout and pointer width.

The first field is rendered as an integer but is used to locate a callable table entry. The evidence does not establish how that representation relates to native pointer width. It would be unsafe to infer a portable object layout from this representation alone.

The final destination receives integer one. Its storage width and declared type are not present in the supplied fragment; a one-byte or four-byte store must not be asserted as established behavior.

## Behavior

### Required order

On a path where each dependency returns normally and all memory accesses are valid, the function performs these actions in order:

1. Reads the dispatch-address field at the beginning of the supplied object.
2. Resolves a callable target at byte offset 0x20 from that address.
3. Invokes that target with the object reference.
4. After that invocation returns, uses the conditional flag to decide whether to perform the second dispatch.
5. If the flag is nonzero, rereads the dispatch-address field from the same object, resolves the target at byte offset 0x34, and invokes it with the object reference and integer zero.
6. After all selected invocations return, writes integer one through the global destination reference.
7. Returns without an explicit value.

This is the logical access and call order represented by the supplied body. It is not a claim about individual machine instructions, compiler scheduling, or synchronization between threads.

### Dispatch state is read again

When selected, the second dispatch obtains its table address after the first callee returns. The function does not visibly retain the first table address for use by the second dispatch.

Consequently, a first callee that changes the object’s leading dispatch-address field can affect the second target. A consumer must not assume that the two targets come from the same table.

The object reference itself remains the same argument value across both calls. Passing the same reference does not establish that the referenced storage or its contents remain valid.

### Flag interpretation

The flag is tested for zero versus nonzero, not for equality to one.

Accordingly:

- Zero selects only the first dispatch.
- A positive nonzero value selects both dispatches.
- A negative value, if representable by the actual integer type, also selects both dispatches.

There is no visible range check, normalization, or rejection of particular nonzero values.

### Final store

The final store occurs only after the first callee and, when selected, the second callee return normally.

The stored value is exactly integer one. The visible body does not read the prior destination value, combine it with one, or condition the write on that prior value.

The destination is obtained through a global reference at the final operation. The body does not visibly snapshot that destination before calling dependencies. Therefore, the contract cannot assume that a destination established before entry remains the one written afterward: a dependency may change global state.

There is no visible readback after the store.

### Preconditions and invalid execution

For the visible operations to complete normally:

- The object reference must permit the leading-field read.
- The first resolved table location must permit retrieval of a valid callable target.
- That target must be callable with the supplied object argument under the actual ABI.
- If the flag is nonzero, the object and its current dispatch representation must remain valid for the second lookup after the first call.
- The second target must accept the object reference and integer-zero argument under the actual ABI.
- At the final store, the global destination reference must designate writable storage suitable for the actual store.

The function contains no visible null checks or validity checks for these accesses. It provides no defined fallback, error return, or recovery path for invalid pointers, invalid callable targets, or incompatible call signatures.

If a dependency does not return normally, the remaining visible sequence is not reached through the normal path. The fragment does not establish exception handling, nonlocal-transfer handling, or recovery behavior.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence, not executed tests.

### Zero flag

Given a valid object, a normally returning F-indirect-20, and a writable final destination:

- Invoke F-indirect-20 with the supplied object reference.
- Do not resolve or invoke F-indirect-34.
- Write integer one through the global destination reference.
- Return without an explicit value.

An unusable second dispatch entry alone does not prevent this path, because the visible body does not access that entry.

### Nonzero flag

Given valid dispatch state, normally returning callees, and a writable final destination:

- Invoke F-indirect-20 first.
- Resolve and invoke F-indirect-34 afterward.
- Pass the same object reference and an additional integer zero to F-indirect-34.
- Perform the final store only after both invocations return.

This selection applies equally to one, other positive nonzero values, and representable negative values.

### First callee changes the table address

Given that F-indirect-20 replaces the object’s leading dispatch-address field with another valid table address, and the flag is nonzero:

- Resolve F-indirect-34 using the replacement address.
- Do not require the original table’s second entry to be used.

### Dependency changes the global destination

Given that a selected dependency redirects the global destination reference to different valid writable storage:

- The final operation uses the destination reference present when that operation executes.
- This body does not require a write to the former destination.

### Destination already contains one

Given otherwise valid execution and a destination already containing one:

- The final assignment is still performed.
- There is no visible equality check that skips it.

### First callee does not return normally

If F-indirect-20 terminates execution or transfers control away without returning through the ordinary path, that path does not proceed to the second dispatch or final store. Effects caused independently by the callee remain outside this contract.
