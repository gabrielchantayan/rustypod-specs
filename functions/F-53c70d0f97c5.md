# F-53c70d0f97c5

## Purpose

F-53c70d0f97c5 conditionally forwards 32-bit values from an input record to destinations within an associated object. It may then perform an indexed counter decrement and entry update.

The established sequence is:

1. Test an object flag that can bypass all dependency calls.
2. Perform eleven ordered forwarding calls.
3. Inspect a secondary-record flag.
4. If enabled, perform three additional forwarding calls and evaluate an eligibility gate.
5. If eligible, accept a zero index without bookkeeping, or process a valid positive index.

“Object,” “forwarding,” “counter,” and “entry” describe observable structure, not established application semantics. In particular, the source does not establish resource ownership, reference counting, or release behavior.

The result is pointer-shaped but can represent a flag byte, a secondary-record address, zero, or a rejection sentinel. It is not uniformly a dereferenceable address.

## Behavior

### Entry bypass

The function first captures the object address from input offset `0x00`, then reads the flag byte at object offset `0x21`.

If bit `0x02` is set, it reads the same byte again and returns the second value, zero-extended. Neither dependency is called, and this function performs no direct store on this path.

The flag test and returned value are separate source-level reads. With stable memory, the returned byte has bit `0x02` set. If the byte changes between reads, the returned value need not equal the tested value.

Otherwise, execution continues with the captured object address.

### Initial forwarding

F-808c5d99c3bd is called eleven times in this order:

| Call | First argument: object-relative destination address | Second argument: input value at byte offset |
|---|---|---|
| 1 | `0xc0` | `0x28` |
| 2 | `0x118` | `0x2c` |
| 3 | `0x118` | `0x3c` |
| 4 | `0x170` | `0x30` |
| 5 | `0x1c8` | `0x34` |
| 6 | `0x220` | `0x38` |
| 7 | `0x278` | `0x40` |
| 8 | `0x2d0` | `0x44` |
| 9 | `0x328` | `0x48` |
| 10 | `0x380` | `0x4c` |
| 11 | `0x3d8` | `0x50` |

Calls two and three both occur and use the same destination address. Neither replaces the other.

Each input value is read for its corresponding call. There is no initial snapshot of all eleven values. An earlier dependency call can therefore affect a later argument if it modifies reachable input memory.

Dependency results do not control this sequence. No returned failure status is checked.

### Secondary-record decision

After the eleven calls, the function reads the secondary-record address from input offset `0x10`, then reads that record’s flag byte.

If bit `0x01` is clear, it returns the captured secondary-record address. There is no secondary-index read, eligibility call, or direct bookkeeping store on this path.

If bit `0x01` is set, three further calls to F-808c5d99c3bd occur:

| Order | Object-relative destination | Source of the 32-bit value |
|---|---|---|
| First | `0x7a0` | Offset `0x08` of the captured secondary record |
| Second | `0x7f8` | Offset `0x04` of the secondary record addressed by a fresh input-offset-`0x10` read |
| Third | `0x850` | Offset `0x0c` of the secondary record addressed by another fresh input-offset-`0x10` read |

After these calls, the function reloads the secondary-record address again and captures the signed index at its offset `0x10`.

Only the first additional value is tied to the record whose flag was tested. Dependency-induced pointer changes can cause subsequent values and the index to come from different records.

### Eligibility gate

After capturing the index, the function calls F-0aff6a5050f5 without explicit arguments.

The gate is evaluated in this order:

- A zero dependency result causes rejection immediately.
- Otherwise, the object’s mode word at `0x8d8` is read. A nonzero mode causes rejection.
- Only for zero mode is the option word at `0x8ac` read. Option bit `0x40` causes rejection.

Rejection returns `0xffffffce`.

All fourteen forwarding calls precede this gate. Rejection does not undo their effects.

The index is captured before F-0aff6a5050f5, whereas mode and option are read afterward. Changes made by that dependency can affect eligibility, but do not replace the captured index.

When the gate succeeds, the captured option value also controls counter processing later. The option word is not reread for that decision.

### Index validation

With the gate satisfied:

- Index zero returns zero without reading the upper bound or either table holder and without any direct bookkeeping store.
- A negative index returns `0xffffffce` without reading the upper bound.
- A positive index causes a signed upper-bound read at object offset `0x8c4`. An index greater than that bound returns `0xffffffce`.
- A positive index no greater than the bound proceeds to table processing.

Consequently, an upper bound of zero or less permits no positive index, but does not prevent the separate zero-index success path.

### Counter processing

For a valid positive index, captured option bit `0x01` determines whether the counter table is used.

If the bit is clear, counter processing is skipped and the entry update is selected directly.

If the bit is set, the function obtains the counter-table base through the holder addressed at object offset `0x8b4`. It selects the 32-bit counter at mathematical displacement `4 × (index − 1)`, reads it, subtracts one, stores the decremented value, and tests that computed result for equality to zero.

The decrement store precedes the decision about entry updating:

- A zero result selects the entry update.
- A nonzero result skips the explicit entry-update stores and returns zero.

Skipping those stores does not guarantee that the accumulator or entry memory is unchanged. The counter store may alias either target or other subsequently relevant memory.

### Entry update

When selected, the entry update obtains the entry-table base through the holder addressed at object offset `0x8b0`. It selects the eight-byte entry at mathematical displacement `8 × (index − 1)`.

The function reads the accumulator and the selected entry’s second word, adds them, and stores the sum to object offset `0x8dc`. It then stores `0x80000001` to the selected entry’s first word and returns zero.

The accumulator store precedes the marker store. The relative evaluation order of the two addition-operand reads is not established.

The selected entry address has already been computed when the accumulator is stored. An accumulator store that overlaps a holder does not redirect the following marker store. Conversely, if the selected entry’s first word overlaps the accumulator, the later marker store overwrites the accumulator’s earlier sum.

No existing marker is tested. With otherwise unchanged, disjoint storage, repeated accepted updates can repeatedly add the same contribution.

The mathematical table displacements describe element selection where arithmetic is representable; they do not establish unrestricted address-range or overflow semantics.

## Side effects

The function’s explicit stores are limited to:

1. The selected counter, if counter processing is enabled for a valid positive index.
2. The accumulator, if entry updating is selected.
3. The selected entry’s first word, after the accumulator store.

These describe store destinations, not mutually independent storage regions. Aliasing may make any such store modify memory also serving another role.

For example, a counter store can change an entry-table holder before that holder is read. A marker store can overwrite the newly stored accumulator value. A skipped entry-update branch proves the absence of its explicit stores, not preservation of memory those stores would have targeted.

Dependencies may perform additional reads, writes, allocations, releases, or other effects. Their preservation of input records, object fields, holders, tables, and globals is not established.

There is no direct allocation or release operation in this function and no rollback. This does not establish borrowing, ownership transfer, retained references, or lifetime guarantees.

No synchronization or atomic-update mechanism is shown.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests.

Unless a case states otherwise, dependencies return normally without modifying the example’s relevant memory, no external changes occur, reached addresses are valid, and arithmetic is representable. These assumptions alone do **not** exclude aliasing. Cases asserting independent final field values additionally require the stated disjoint storage.

1. **Entry bypass.** With object flag `0x06` unchanged between reads, the result is `0x00000006`. Neither dependency is called.

2. **Secondary processing disabled.** With entry bypass clear and secondary flag `0x00`, eleven forwarding calls occur. The result is the secondary-record address captured after those calls.

3. **Repeated destination.** Calls two and three both target object offset `0x118`, receiving input values from offsets `0x2c` and `0x3c`, respectively.

4. **Eligibility dependency rejects.** With secondary processing enabled and F-0aff6a5050f5 returning zero, fourteen forwarding calls precede result `0xffffffce`. The mode and option words are not read by the gate, and no direct bookkeeping store occurs.

5. **Zero index.** With the gate satisfied and index zero, the result is zero. The upper bound and both table holders are not read by index handling.

6. **Negative index and upper boundary.** With the gate satisfied, index `-1` rejects without an upper-bound read. With upper bound three, index three proceeds to table processing; index four rejects.

7. **Direct entry update with disjoint fields.** Let index two be valid, option bits `0x40` and `0x01` be clear, the accumulator be 100, and entry two’s second word be seven. Require the accumulator and selected eight-byte entry to occupy disjoint storage. The accumulator finishes at 107, the entry’s first word finishes at `0x80000001`, and its second word remains seven. No counter-table lookup occurs.

8. **Counter reaches zero with disjoint fields.** Let counter processing be enabled, the index be valid, and the selected counter start at one. Require the selected counter, accumulator, selected entry, and address-bearing storage used for these lookups to be disjoint. The counter becomes zero, then the accumulator and marker stores occur in that order.

9. **Counter remains nonzero with disjoint fields.** Under the preceding disjoint-storage conditions, a selected counter of two becomes one. No explicit entry-update store occurs. Because the counter is disjoint from the accumulator and entry, and no other actor modifies them, those memory regions remain unchanged.

10. **Counter aliases the accumulator.** Let the selected counter occupy exactly the accumulator’s four bytes and initially contain two. With a valid index and counter processing enabled, the decrement stores one there. The entry-update branch is skipped, but the accumulator’s memory has nevertheless changed from two to one.

11. **Marker aliases the accumulator.** Let direct entry updating be selected, and let the selected entry’s first word occupy exactly the accumulator’s four bytes. Let its second word be seven and the accumulator initially be 100, with other relevant storage disjoint. The accumulator store first writes 107. The subsequent marker store overwrites those same four bytes with `0x80000001`; 107 is not their final value.
