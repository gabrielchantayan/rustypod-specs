# F-0c335b11b4ca

## Purpose

F-0c335b11b4ca validates request-related state, selects a handler for original selectors 0–8, and, after handler success, coordinates response-related dependency calls. Original selector 7 can select an iterative fragmentation path; other selectors use a single-message path.

The body establishes argument construction, read ordering, arithmetic, branches, direct state writes, and handling of dependency results. It does **not** establish that the external transfer-like dependency copies memory, that sequence-related calls encode bytes, that transport-like calls submit data, or that the final output-address call releases storage.

“Header,” “payload,” “capacity,” and “fragment” describe apparent roles. They do not establish a protocol or dependency implementation. All conclusions below are static; no runtime tests have been performed.

## Interface

### Inputs and accessed layout

The function accepts two 32-bit values used as addresses:

- **Owner address:** Used in handler-address adjustment and passed unchanged to F-5ca71e377766.
- **Context address:** Used for request access, validation, response-related calls, and explicit error-state writes.

| Context byte offset | Width | Established use |
|---|---|---|
| 0 | 32 bits | Read after handler success; treated as a connection-related value. |
| 8 | 32-bit address | Read initially as the request address. |
| 12 | 32 bits | Read initially; its low 16 bits must equal 7. |
| 16 | 16 bits | Written with `0x0012` on either explicit fragment-path failure. |

The request selector is an unsigned byte at request offset 0. The request address plus 1 is passed to F-c25a2fcc75b5; the request address plus 5 is passed to F-64e2dfdd4a5d. Their results supply a 32-bit field and a 16-bit field respectively. Their actual read extents, byte orders, and transformations are unknown.

The selector is read **before** the explicit null-request check. Metadata equal to 7 does not independently establish that seven request bytes are accessible.

### Handler-visible working record

A stack-resident record is passed by address to the selected handler.

| Relative offset | Width | Preparation or subsequent use |
|---|---|---|
| 0 | 32 bits | Result of F-c25a2fcc75b5; later compared against an unsigned limit. |
| 4 | 16 bits | Result of F-64e2dfdd4a5d. |
| 6 | 8 bits | Header-length field, initially 1. |

The address at offset 7 is supplied as the second argument of header transfer-like calls. Initial preparation does not initialize a complete multi-byte header.

A separate auxiliary-object slot is initialized to null. The body contains no explicit assignment making it nonnull. Whether the handler can legitimately populate it through the supplied record address or another reachable reference is unresolved.

### Return values and preconditions

The result is a 32-bit integer:

- **4:** Initial result; retained for unsupported selectors or a failed unsigned limit comparison.
- **Nonzero handler result:** Retained without response construction.
- **0:** Retained after handler success unless an explicit later error changes it.
- **2:** Immediate return for a zero connection-related value; also selected when F-256e8a77aa59 returns nonzero.
- **3:** Immediate return for a zero output-address result; also selected when F-cd7e1905512f returns zero.

These values overlap possible handler results and do not uniquely identify execution paths.

Some conditions invoke nonreturning F-a817d8d58c10 instead of returning.

All directly accessed structures must be valid for their actual accesses. Dependencies may impose additional requirements. The capacity-like value does not establish output allocation size: the output-address supplier receives no explicit capacity argument.

## Behavior

### Initial observations and validation

The function initializes its result to 4, reads the request address and metadata, reads the selector byte, and initializes the auxiliary slot to null.

Validation short-circuits in this order:

1. A zero request address rejects, if execution reaches that check after the preceding selector read.
2. F-5f5f14cedda3 receives the context. A signed result greater than 2 rejects.
3. The previously read metadata must have low 16 bits equal to 7.

Every rejection invokes F-a817d8d58c10. Negative validation-helper results pass this comparison. Metadata upper bits are ignored; metadata is not reread after the helper.

Original selectors 9–255 reach common exit with result 4 after validation, without field decoding or handler dispatch.

### Dispatch sampling and selection

For selectors 0–8, the function reads a pointer-valued global and selects an eight-byte table entry using eight times the original selector. It loads a 32-bit callable representation and a 32-bit control word.

Both values are sampled **before** either field decoder, F-b7af80e829ec, or the indirect limit query. Changes to the global or entry during those calls do not replace the cached values.

The function then:

- Calls F-c25a2fcc75b5 with request address plus 1.
- Calls F-64e2dfdd4a5d with request address plus 5.
- Initializes header length to 1 and response selector to the original selector.
- Calls F-b7af80e829ec.
- Uses its returned object to invoke a method at method-table byte offset `0xEC`.

The limit-query result is interpreted as unsigned 32 bits. Dispatch requires the working record’s 32-bit field, observed after that query, to be strictly less than the limit. Equality or a greater value leaves result 4.

The cached control word, interpreted as signed 32 bits and arithmetically shifted right once, supplies the owner displacement. Address calculations use the represented 32-bit address model.

- If control bit 0 is clear, the cached callable is used directly.
- If control bit 0 is set, the callable representation’s bottom two bits are cleared. The resulting value is used as a byte offset from a table address read through the adjusted owner; the callable address is loaded there.

Thus the entry pair is cached early, while indirect resolution reads the adjusted owner’s dispatch structure later.

The handler receives the adjusted owner and working-record address. Its result replaces the current result. A nonzero result reaches common exit without response construction.

### Setup following handler success

After a zero handler result:

1. The connection-related value is read at context offset 0.
2. If zero, the function immediately returns 2.
3. F-1a836ac93559 receives that value and 3. Its unsigned 32-bit result is retained as capacity.
4. F-fab3799b3190 is called. Its result is retained as the output address.
5. If the auxiliary slot is nonnull, F-cec639934d47 receives its current value. The slot is then observed again to read the current object’s 32-bit field at offset 4. That field is passed to F-8810f53aaa0b; the low 16 bits of its result become the retained payload length.
6. If the output address is zero, the function immediately returns 3.

Payload length starts at zero. Auxiliary processing occurs before the zero-output check. There is no second null check between F-cec639934d47 and the object-field read. Consequently, valid behavior requires that subsequent read to remain valid; the earlier check alone does not guarantee it.

Neither immediate return performs common-exit auxiliary processing. The retained payload length is not recalculated merely because the auxiliary slot later changes.

### Repeated header-length observations

The header-length field is an unsigned byte in escaped working storage, not one immutable value. Distinct observations govern:

- The response-path comparison.
- The fragmentation-entry equality check.
- Each fragment’s capacity subtraction.
- Each header transfer-like call’s third argument.
- Arithmetic after each such call returns.

No dependency-preservation contract is supplied. The post-call length may therefore differ from the count passed to the preceding call. Within a response iteration, the post-call value is retained for subsequent address and length calculations; later calls do not cause an explicit reread for those calculations.

### Single-message path

This path applies unless the original selector is 7 and capacity is less than the header-length-plus-retained-payload-length sum observed at path selection.

The function calls F-D01 with:

1. Output address.
2. Working-record address plus 7.
3. The currently observed header-length byte, promoted for the call.

F-D01’s result is unused. Its implementation is absent; these arguments do not establish a memory copy.

After the call, header length is reread and retained.

If the auxiliary slot is null, no payload-address lookup, payload transfer-like call, or F-5ca71e377766 call occurs. The outgoing length is the post-call header length, without an additional mask.

If the slot is nonnull, capacity is compared against post-call header length plus retained payload length. When that sum exceeds capacity:

- Capacity must be strictly greater than the post-call header length.
- Otherwise F-a817d8d58c10 is invoked.
- Payload length becomes the low 16 bits of capacity minus that header length.

Next, F-44362605ab79 receives the current auxiliary object. F-D01 receives output address plus retained header length, the returned address, and selected payload length. F-5ca71e377766 then receives the original owner, that same output-relative address, and selected payload length.

The outgoing length becomes the header-plus-payload sum masked with `0xFFFEFFFF`. This clears bit 16; it is not a general conversion to 16 bits.

F-dece790ddc92 receives:

1. Context.
2. Retained connection-related value.
3. Zero.
4. 3.
5. `0x13`.
6. Output address.
7. Outgoing length.

Its result is unused. The initial F-D01 invocation precedes the auxiliary-dependent capacity rejection. No corresponding rejection is present on the null-auxiliary branch.

### Selector-7 fragmentation

Fragmentation requires original selector 7 and insufficient capacity at path selection. Entry rereads header length and requires exactly 4, then requires a nonnull auxiliary slot. Failure invokes F-a817d8d58c10.

Payload offset and sequence begin at zero. While offset is less than retained payload length, each iteration:

1. Reads header length and subtracts it from capacity using unsigned 32-bit arithmetic.
2. Compares the result with remaining payload length.
3. Selects the smaller quantity as slice length. If capacity-derived space is smaller, directly writes flag 1; otherwise writes flag 3 and selects the entire remainder.
4. Calls F-3a7a47316439 with working-record address plus 9 and the current sequence.
5. Calls F-D01 with output address, working-record address plus 7, and a newly observed header length.
6. Rereads header length and retains that post-call value.
7. Checks the auxiliary slot again.

F-3a7a47316439’s arguments suggest a sequence-encoding role, but no write, encoding, or write extent is established.

On the per-iteration nonnull branch, F-44362605ab79 receives the current auxiliary object. F-D01 then receives:

- Output address plus retained post-call header length.
- Returned address plus payload offset.
- Selected slice length.

The length subsequently passed to F-cd7e1905512f is the low 16 bits of retained header length plus slice length.

On the null branch, both calls are skipped. The length passed onward is the retained header length without the low-16-bit mask. Entry-time nonnullness does not eliminate this later branch. Once the nonnull branch is selected, no additional null check intervenes before the F-D01 call.

F-cd7e1905512f receives the retained connection-related value, zero, 3, `0x13`, output address, and calculated length.

- A zero result selects function result 3.
- Otherwise F-256e8a77aa59 receives that result and zero. A nonzero return selects function result 2.

Either failure writes 16-bit `0x0012` at context offset 16, skips the normal completion call, and proceeds to the output-address finalizer and common exit. These branches establish return-value handling, not whether construction or submission actually occurred.

After both calls indicate continuation, sequence advances by one and is masked with `0xFFFEFFFF`; payload offset advances by slice length. Offset advances even on a null-auxiliary iteration with no payload transfer-like call.

There is no capacity-versus-header guard before subtraction. A smaller capacity produces unsigned underflow. Equal capacity can select zero bytes and prevent offset progress.

After loop completion, F-dece790ddc92 receives context, zero, zero, `0xFFFFFFFF`, zero, zero, and zero. If retained payload length is zero, no iteration precedes this call.

### Finalization and common exit

After either normal response path or either explicit fragment failure, F-58ba61416cc9 receives the output address. Its result is unused. A release role is inferred; actual release or ownership transfer is unknown.

Common exit checks the current auxiliary slot. If nonnull, an indirect method at the object’s method-table byte offset 4 is invoked. The displayed invocation supplies no established explicit argument list or ownership contract.

The retained result is then returned. Zero-connection and zero-output immediate returns bypass common exit. Cleanup after nonreturning rejection is not established.

## Side effects

Established direct writes are limited to local preparation, fragment flags, local arithmetic state, and the two fragment-error status writes. The body does not directly establish output-buffer writes: output-related addresses and counts are passed to dependencies.

Under a separately assumed memory-copy contract for F-D01, its calls would place header and payload bytes at the supplied destinations. Without that assumption, byte placement, written extent, overlap handling, and even whether any memory is accessed remain unknown.

The body contains no explicit request-byte write or success-path context-status reset. Unknown dependency effects prevent a general preservation guarantee.

No ownership transfer is established for the output address or auxiliary object. F-58ba61416cc9 and the auxiliary exit method may have cleanup-like roles, but whether either releases anything is unknown. Later auxiliary observations need not identify the same object as earlier ones.

## Acceptance examples

These are conditional static expectations, not executed tests. Accessed storage must be valid. Unless varied, dependencies preserve relevant state and return normally.

1. **Validation and unsupported selector:** Selector 9 with passing validation returns 4 without decoding or dispatch. Metadata `0xABCD0007` passes; low bits `0x0008` reject. Unsupported selectors do not bypass validation.

2. **Cached dispatch:** A decoder changing the selected dispatch entry does not replace the cached callable/control pair. Indirect resolution still reads the adjusted owner’s table later.

3. **Limit boundary:** A working 32-bit value equal to the unsigned limit does not dispatch. A value strictly below it does.

4. **Early outcomes:** Handler result 6 returns through common exit without output acquisition. Handler success followed by zero connection returns 2 immediately. Zero output returns 3 only after the conditional auxiliary-length processing.

5. **Ordinary truncation arguments:** With non-7 selector, stable header length 1, payload length 20, nonnull auxiliary object, and capacity 8, the payload F-D01 call receives output address plus 1 and count 7. F-5ca71e377766 receives that address and 7; outgoing length is 8. Seven payload bytes are placed there **only if F-D01 has the assumed memory-copy contract**.

6. **Different header observations:** Suppose the header F-D01 call receives count 1, changes header length to 3, and capacity is 8 with retained payload length 20. The payload call receives output address plus 3 and count 5; outgoing length is 8. With memory-copy behavior and no other relevant writes, the two intervening output bytes are untouched by these calls. Without those assumptions, their contents are unknown.

7. **Rejection ordering:** With nonnull auxiliary object, post-call header length 4, positive payload length, and capacity 4 on the single-message path, rejection occurs after the header F-D01 invocation. A preceding memory write is not established.

8. **Stable fragmentation arguments:** Selector 7, header length 4, payload length 10, capacity 8, and continuing dependencies produce slice lengths 4, 4, 2; flag writes 1, 1, 3; sequence arguments 0, 1, 2; and F-cd7e1905512f length arguments 8, 8, 6. Encoded bytes and actual submission remain unknown.

9. **Auxiliary disappearance:** If the first fragment’s header F-D01 call makes the auxiliary slot null while retaining header length 4, that iteration skips payload lookup and its F-D01 call, passes length 4 onward, and advances offset by 4 after successful continuation results.

10. **Three length samples:** Capacity 8 and subtraction-time header length 4 select four bytes from ten remaining. If F-3a7a47316439 changes header length to 6, the header F-D01 count is 6. If that call changes it to 5, the nonnull payload branch uses destination offset 5 and onward length 9.

11. **Fragment errors:** F-cd7e1905512f returning zero selects result 3. F-256e8a77aa59 returning nonzero selects result 2. Both write status `0x0012`, skip normal completion, and invoke F-58ba61416cc9 before common exit. Neither proves storage release.

12. **No progress:** Selector 7, stable header length 4, positive payload length, and capacity 4 select zero-length slices. With indefinitely continuing dependencies and unchanged state, the loop does not terminate.
