# F-e9d6f8628430

## Purpose

F-e9d6f8628430 conditionally writes five fields into caller-provided, indexed storage. Eligibility depends on selector recognition, a quantity in the range 2–4, and a nonnegative override. If eligibility fails, the function may latch a nonzero status into the first word of that storage, preserving an existing nonzero status.

“Selector,” “quantity,” “override,” “payload,” “record,” and “status” are descriptive roles, not established application-level meanings. The comparisons, arithmetic, access conditions, and write sequence below are established by static evidence. No runtime tests have been performed.

The function has no explicit return value.

## Interface

### Arguments and representation

| Argument | Role |
|---|---|
| State pointer | Base of storage read and potentially written by the function. |
| Quantity | Integer tested for membership in 2–4, unless an initial selector rejection replaces its working value with 1280. |
| Selector | Integer compared with 5120 and configuration-dependent values. |
| Override | Signed integer: negative prevents record updates; zero requests derivation; positive supplies the stored value directly. |
| Payload | Integer copied into the first field written on success. |

This contract uses the represented **32-bit integer model**:

- Integer arguments and state fields are 32-bit words.
- A word occupies four bytes.
- The override comparison is signed.
- The quantity test uses unsigned 32-bit subtraction.
- Stored arguments retain their 32-bit values.

The original ABI, pointer width, byte order, and physical access requirements are not independently established.

Two external words are read:

- **Selector base**, used to construct retained candidates and in subsequent direct comparisons.
- **Default status**, read only if the second selector-recognition decision succeeds.

Neither external word is explicitly written by the function. Aliasing with state storage is not excluded.

## Behavior

### 1. External-read schedule and selector preparation

The function begins with **two separate, unconditional selector-base reads**, in this source-level order:

1. Read the selector base and form a retained plus-10 candidate.
2. Read the selector base again and form a retained plus-4 candidate.

These reads occur even when the selector is 5120, the quantity is invalid, or the override is negative. They need not observe the same value. The two retained candidates therefore need not be four and ten greater than one common base.

The additions have the overflow qualification described under Uncertainties. They are not specified here as wrapping operations.

After candidate preparation, external reads occur as follows:

| Stage | Condition for external read | Read |
|---|---|---|
| First recognition | Selector is not 5120 | Selector base, for a direct comparison |
| Second recognition | Selector is not 5120 | Selector base again, independently of the first recognition |
| Before quantity test | Second recognition succeeds | Default status |
| Successful value derivation | Override is zero and selector is not 5120 | Selector base again, for derivation |

The second recognition occurs even if the first rejected the selector. Each recognition performs its conditional direct-base read before comparisons with either retained offset candidate. Thus matching a retained candidate does not eliminate that direct-base read.

A call performs two to five source-level selector-base reads. It performs at most one default-status read. These are source-established execution conditions; uncertainty about hardware access ordering does not remove them.

### 2. First recognition and working quantity

The first recognition compares the selector, in short-circuit order, against:

1. Fixed value 5120, hexadecimal `0x1400`.
2. A freshly read direct selector base.
3. The retained plus-10 candidate.
4. The retained plus-4 candidate.

The direct-base read is skipped only when the fixed comparison succeeds. Later candidate comparisons are skipped once an earlier comparison succeeds.

If none matches, the working quantity becomes 1280, hexadecimal `0x500`. Otherwise, the working quantity remains the supplied quantity. This replacement affects only internal computation; it does not write to caller argument storage.

### 3. Second recognition and eligibility

The second recognition independently repeats the same comparison precedence:

1. Fixed value 5120.
2. Another freshly read direct selector base.
3. The retained plus-10 candidate.
4. The retained plus-4 candidate.

It does not reuse the first recognition result or its direct-base observation.

If this recognition fails, neither the default status nor the quantity and override eligibility tests are evaluated. The failure-status candidate is the current working quantity.

If this recognition succeeds:

1. Read the external default status and retain it as the failure-status candidate.
2. Test whether unsigned 32-bit working quantity minus 2 is less than 3.
3. Only if that test succeeds, test whether the signed override is nonnegative.

The quantity condition accepts exactly 2, 3, and 4. It rejects zero, one, all negative 32-bit quantities, and every other positive quantity.

The default-status read precedes the quantity test and occurs even if the call subsequently succeeds. It also occurs if the first recognition rejected the selector but the second recognizes it. In that case, the working quantity is already 1280, so the quantity test fails.

A successful record update therefore requires:

- First recognition retained the supplied quantity.
- Second recognition succeeds.
- The supplied quantity is 2, 3, or 4.
- The override is nonnegative.

Under stable configuration, both recognition decisions agree. The recognized set then consists of 5120, the selector base, base plus 10, and base plus 4.

### 4. Derived or overridden value

A strictly positive override supplies the stored value directly. No derivation-time selector-base read occurs.

For a zero override:

- If the selector is 5120, the stored value is the accepted quantity. No derivation-time selector-base read occurs.
- Otherwise, the function reads the selector base again.
  - If the selector matches that observation, the stored value is quantity multiplied by 2.
  - Otherwise, it compares with the retained plus-4 candidate and then the retained plus-10 candidate. A match produces quantity multiplied by 4.
  - If neither retained candidate matches, the stored value is zero.

The fixed-selector case takes precedence over every configured match. The fresh direct-base comparison takes precedence over retained candidate matches. Offset comparisons during derivation use plus-4 before plus-10, unlike the recognition decisions.

For accepted quantities, scaling produces only 2–16, so these shifts do not overflow the stated 32-bit model.

The zero fallback is reachable in the represented control flow if recognition succeeded through an earlier direct-base observation but the derivation-time base differs. It is not an ordinary selector category under stable configuration.

### 5. Successful write sequence

After determining the stored value, the function performs five assignments in this order:

| Order | Index handling | Destination and value |
|---:|---|---|
| 1 | Read word 148 | Store payload at word 110 + 8 × index |
| 2 | Read word 148 again | Store derived or overridden value at word 115 + 8 × index |
| 3 | Read word 148 again | Store selector at word 109 + 8 × index |
| 4 | Read word 148 again | Store accepted quantity at word 108 + 8 × index |
| 5 | Read word 148 again | Copy word 694 to word 111 + 8 × index |

The source word for the fifth assignment is read at that assignment, after the preceding four assignments. It is not an entry-time snapshot.

The representation establishes assignment order but not the relative machine-level order of the final assignment’s source-word read and destination-index read.

After the fifth assignment, the function returns without executing status latching.

### 6. Failure and status latching

The complete failure-candidate rule is:

| Recognition outcome | Failure-status candidate |
|---|---|
| Second recognition fails | Working quantity: supplied quantity if first recognition succeeded, otherwise 1280 |
| Second recognition succeeds, but quantity or override fails | Previously read default status |

Under stable configuration, this simplifies to:

- Unrecognized selector: candidate 1280.
- Recognized selector with invalid quantity or negative override: candidate is the default status.

For any failure candidate:

- If zero, return without reading or writing state word 0.
- If nonzero, read state word 0.
- If that word is zero, write the candidate there.
- Otherwise, preserve the existing word.

Any nonzero 32-bit value qualifies, including a negative signed value. There is no separate error return and no indication of whether a status write occurred.

## Side effects

An ordinary successful call performs five word stores. An unsuccessful call performs no record-field assignments and at most one status-word store.

There is no explicit index advancement, status clearing, external-configuration update, allocation, deallocation, callback, or dependent function call. These statements do not imply that computed destinations cannot overlap other meaningful state.

Two concrete overlaps matter:

- **Initial index 5:** the fourth store reaches word 148 and replaces the index with the accepted quantity. The fifth store uses that replacement.
- **Index 73:** the first store reaches word 694 and overwrites the later copy source with the payload.

Other overlaps must follow the same ordered assignments. A successful store could affect the status word or externally meaningful storage if the actual address arrangement permits it; success does not promise those locations remain unchanged through aliasing.

The state remains caller-provided storage. No independent record allocation or nonaliasing guarantee is established.

There is no rollback or transactional protection. Inaccessible memory, invalid address arithmetic, or unsupported concurrent execution has no documented recoverable behavior. Partial writes are not ruled out.

## Acceptance examples

These are conditional static acceptance examples, not observed executions. Unless stated otherwise, assume the represented 32-bit model, accessible addresses, valid arithmetic, stable configuration, and no interference.

### Fixed selector and zero override

Given selector 5120, quantity 3, override zero, payload 91, index zero, and source word 27:

1. Word 110 becomes 91.
2. Word 115 becomes 3.
3. Word 109 becomes 5120.
4. Word 108 becomes 3.
5. Word 111 becomes 27.

There are exactly two selector-base reads, both during preparation. Neither recognition reads the direct base, and derivation does not read it. The default status is still read before the successful quantity test.

### Base and offset selectors

Given selector base 1000, quantity 4, and override zero:

- Selector 1000 stores derived value 8.
- Selector 1004 or 1010 stores derived value 16.

Each case performs five selector-base reads: two preparation reads, one per recognition, and one during derivation.

### Positive override

Given a recognized nonfixed selector, quantity 2, and override 17, the stored value is 17. There are four selector-base reads: two preparation reads and one per recognition. There is no derivation-time base read.

### Boundary rejection and status preservation

Given a recognized selector, nonnegative override, default status 77, and initial status zero:

- Quantities 2 and 4 permit record updates.
- Quantities 1, 5, and −1 produce no record-field assignments and latch 77.

Given quantity 3 and override −1, the result is also failure with candidate 77. An existing status 12 remains 12.

### Zero failure candidate

Given a recognized selector, invalid quantity, and default status zero, the default status is read, but state word 0 is neither read nor written through the status-latching path. No record-field assignment occurs.

### Stable unrecognized selector

Given selector base 1000 and selector 1001, both recognitions reject. The working quantity becomes 1280, and that is the failure candidate regardless of supplied quantity or override. The default status is not read.

### Independent preparation observations

Suppose the plus-10 preparation read observes 1000 and the plus-4 preparation read observes 2000. The retained candidates are 1010 and 2004, not 1010 and 1004. A selector of 2004 can match the retained plus-4 candidate even if subsequent direct-base reads observe other values.

### First rejection followed by recognition

Suppose the retained candidates are 1010 and 1004, the selector is 2000, the first recognition reads base 1000, and the second reads base 2000.

The first rejection replaces the working quantity with 1280. The second recognition succeeds and reads the default status. The quantity test then fails. No record update occurs; the failure candidate is the observed default status, not 1280.

### First recognition followed by rejection

Suppose the retained candidates are 1010 and 1004, the selector is 2000, the first recognition reads base 2000, and the second reads base 3000.

The supplied quantity remains unchanged, but the second recognition fails. The default status is not read. A supplied quantity of 3 becomes the failure candidate; a supplied quantity of zero causes no status-word access.

### Derivation-time mismatch

Suppose selector 2000 is recognized through direct-base observations in both recognitions, quantity is 3, override is zero, and the retained candidates are 1010 and 1004. If the derivation-time base read observes 3000, the stored derived value is zero. All five successful assignments still occur.

### Selector collision and state overlap

With stable base 5120, selector 5120, quantity 4, and zero override, the stored value is 4, not 8.

With initial index 5 and accepted quantity 2, the fourth store writes 2 into word 148. The final copy targets word 127, not word 151.

With index 73 and payload 99, the first store writes 99 into word 694. If the index remains unchanged, the final copy writes 99 into word 695.
