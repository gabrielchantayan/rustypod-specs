# F-e090cd2f418c

## Purpose

F-e090cd2f418c obtains a dispatch object from receiver-associated state and submits that object to a selected dispatch route.

The visible route priority is:

1. Direct dispatch when a receiver-associated value is strictly positive under signed 32-bit comparison.
2. Iterator-backed dispatch when the direct route is not selected.
3. Linked-handler dispatch if iteration is unavailable or finishes without a nonzero handler result.

A nonzero dispatch result stops the applicable search. Negative results count as nonzero; results are not normalized to a Boolean. A non-null dispatch object receives a final virtual callback after normally returning dispatch processing.

These role names describe observed use, not established application types. The supplied representation has an unresolved execution-context transition before fallback processing. Fallback behavior below is therefore conditional on reaching that processing with a valid context.

### Preconditions and failures

The receiver is dereferenced without a null check. Every reached memory access requires valid readable storage, and every reached indirect call requires a valid table and callable entry.

A successful earlier pointer check does not validate a separately reread pointer. In particular, direct-route selection checks one read of receiver `+0x04` but dereferences an address obtained by a second read.

No explicit recovery is visible for invalid addresses, inaccessible tables, malformed iteration output, nonreturning dependencies, or failures inside callbacks. The function establishes no exception-safe or nonlocal-exit cleanup guarantee.

## Behavior

### Initial gate and dispatch-object acquisition

The first visible operation reads the receiver’s 32-bit field at `+0xA4`.

If that read yields zero, the function returns zero immediately. It does not acquire a dispatch object, inspect routing state, invoke fallback providers, or perform a final callback.

Otherwise, acquisition proceeds in this order:

1. Call F-f2ddcdbfb0c6 without visible arguments.
2. Call F-c5a232e4455b with the preceding result and the 32-bit constant `0x0000000C`.
3. Read receiver `+0xA4` again.
4. Call F-2ed0781c3d25 with the result of F-c5a232e4455b, the later receiver-field value, and the receiver address.

The second field read is distinct from the initial gate. Intervening dependencies may change the field; the later value, including zero, is supplied to F-2ed0781c3d25 without another gate.

The result of F-2ed0781c3d25 is the dispatch-object reference. A null result does not itself stop processing.

### Direct-route selection: two receiver-field reads

After acquisition, routing is determined through the following ordered observations:

1. Read receiver `+0x04` and test that value for zero.
2. If that first value is zero, do not perform the second receiver-field read or the nested routing-field read; select fallback.
3. If the first value is nonzero, read receiver `+0x04` again.
4. Use the second value as the address of the routing object and read its 32-bit field at `+0x04`.
5. Interpret the nested value as signed 32-bit and select direct dispatch only when it is greater than zero.

The first routing-object reference is not retained for the dereference. If the field changes between the two reads, the second address controls the nested read. There is no separate null check on that second address. If it becomes zero, the representation still attempts the read at offset `+0x04` from that address; fallback is not established as a safe response.

Nested values from `0x00000001` through `0x7FFFFFFF` select direct dispatch. Zero and values from `0x80000000` through `0xFFFFFFFF` do not.

On the direct route:

- Call F-c7f4370906ef with the receiver, dispatch object, 32-bit one, and 32-bit zero.
- Retain its 32-bit result.
- If the dispatch object is non-null, invoke its virtual entry at table offset `+0x04`.
- Return the retained result.

A zero direct result does not trigger fallback.

### Fallback entry and representation limitation

When direct dispatch is not selected, the routing candidate is explicitly cleared to null.

At this transition, the supplied representation also replaces its apparent receiver and stack context using values not established by the four arguments. This prevents a complete callable-interface account of fallback entry. The subsequent operations remain describable as static control and data flow, conditional on a valid execution context.

The fallback result accumulator begins at zero.

### Linked-handler traversal

If iterator processing does not produce a nonzero result, call F-3fdd14ecd250 again and read the returned object’s 32-bit field at `+0x28` as the initial linked-handler reference.

This is a new provider call. Its result need not identify the same object as the earlier provider result. The initial linked-handler reference is captured before the filtering callback.

Filtering is selected once:

- A null dispatch object disables filtering.
- Otherwise, invoke the dispatch object’s virtual entry at `+0x14`.
- Only the low 32 bits of its represented 64-bit result select filtering: zero disables it; nonzero enables it.

This selector call occurs even if the captured initial linked-handler reference is null. The upper return word does not supply an additional eligibility condition.

For each non-null handler, while the accumulated result is zero:

**Filtering disabled:** Invoke the handler’s virtual entry at `+0x30`, passing the handler and dispatch object.

**Filtering enabled:**

1. Read the handler’s 32-bit field at `+0x0C` as an associated-object address.
2. Read the associated object’s 32-bit field at `+0x0C`.
3. If that nested field is zero, invoke the handler’s `+0x30` entry.
4. Otherwise, call F-35b8bd5fa9e0 with the dispatch object.
5. A nonzero dependency result permits the handler call; zero skips it and leaves the accumulated result zero.

The associated-object address is not checked for null before its nested field is read. A later traversal check does not protect this earlier dereference.

Any nonzero handler result stops traversal immediately. There is no subsequent traversal-gate read or successor call for that result.

After a zero handler result or an eligibility skip:

1. Read the current handler’s `+0x0C` field.
2. If it is zero, stop traversal.
3. Otherwise, invoke that handler’s virtual entry at `+0x1C`.
4. Use the low 32 bits of the represented 64-bit return as the next handler reference.

With filtering enabled, the post-dispatch traversal read is a separate read from the earlier associated-object read. A dependency or handler callback may have changed the field. With filtering disabled, the earlier filtering-related read does not occur.

No visible cycle detection, iteration limit, or fallback retry bounds traversal.

Thus each visible normal completion path after acquisition makes one explicit final callback for a non-null dispatch object. The initial zero-gate path and null dispatch-object paths make none. This describes calls made directly by this function, not additional calls dependencies might perform internally.

## Acceptance examples

These are conditional static criteria, not executed tests. Normal-path examples require valid reached memory, callable entries, normally returning dependencies, and a valid fallback context where applicable.

1. **Disabled initial gate.** An initial receiver `+0xA4` value of zero produces zero without dependency calls.

2. **Changed construction input.** If an acquisition dependency changes receiver `+0xA4` from nonzero to zero before its second read, F-2ed0781c3d25 receives zero as that input.

3. **Routing reference changes.** If the first receiver `+0x04` read identifies one non-null object and the second identifies another, the second object’s `+0x04` field controls routing. The first object’s nested field is not read.

4. **Routing reference becomes null.** If the first receiver `+0x04` read is nonzero and the second is zero, no second null check protects the nested read. A clean fallback result is not guaranteed.

5. **Direct result is final.** A nested value of `0x7FFFFFFF` selects direct dispatch. If F-c7f4370906ef returns zero, zero is returned without fallback; a non-null dispatch object still receives its final callback.

6. **Signed routing boundary.** A nested value of `0x80000000` does not select direct dispatch. Fallback behavior remains conditional on the unresolved entry context.

7. **Iteration source changes after its gate.** If the first provider `+0x2C` read is nonzero but the second is zero, F-538044b67754 receives zero and `0xFFFFFFFE`. The function does not recheck that source before initialization. What the dependency does with zero is unknown.

8. **First nonzero iterator result wins.** Candidate results zero followed by negative seven cause both candidates to be called, iteration to be concluded, linked traversal to be skipped, and negative seven to be returned.

9. **Exhaustion uses a fresh provider call.** After all-zero candidate dispatch and iterator exhaustion, F-944b595e25e9 precedes the later F-3fdd14ecd250 call. Linked traversal uses that later result’s `+0x28` field.

10. **Filtering skip still permits advancement.** With filtering enabled, a nonzero associated-object field and zero F-35b8bd5fa9e0 result suppress the handler call. A later nonzero handler `+0x0C` read permits successor acquisition.

11. **Handler mutation stops traversal.** If a called handler returns zero and changes its `+0x0C` field to zero, the subsequent read stops traversal without a successor call.

12. **Null dispatch object.** Null is still passed to selected dispatch operations. Linked filtering is disabled, and no dispatch-object final callback occurs.
