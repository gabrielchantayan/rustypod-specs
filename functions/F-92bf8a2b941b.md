# F-92bf8a2b941b

## Purpose

F-92bf8a2b941b writes a variable-length byte representation of an integer into caller-supplied storage, including an explicit zero byte.

The established behavior resembles UTF-8 encoding for some input ranges, but **this function must not be specified as a general Unicode-to-UTF-8 encoder**:

- Values in the surrogate range are not rejected.
- Inputs with bit 31 set follow a two-byte output path rather than the apparent out-of-range path.
- For inputs from 0x10000 through 0x10FFFF, the visible writes omit destination offset 2 and put bits 6–11 of the input at offset 1.
- Several paths transfer control to an unresolved indirect target after making their visible writes.

This contract distinguishes the function’s explicit stores from any behavior of that unresolved target. For paths involving that target, the supplied evidence does not establish the destination’s final contents at eventual return.

## Interface

### Inputs

The function accepts:

1. **Destination:** a pointer to writable byte storage.
2. **Value:** a 32-bit unsigned integer bit pattern.

Bytes are eight bits. Destination offsets in this document are byte offsets from the supplied pointer. Multibyte integer endianness does not affect the output description: the visible output operations are individual byte stores.

The supplied representation uses both unsigned comparisons and signed interpretations of the same input. For the signed comparisons described here, bit patterns 0x80000000 through 0xFFFFFFFF are interpreted as negative 32-bit integers.

### Output

There is no explicit return value, byte count, status code, or error object.

For paths without an unresolved transfer, the output is the destination modification described below. For paths with an unresolved transfer, only the stores preceding that transfer are established.

An explicit zero store is not necessarily the first zero in the resulting storage:

- Input zero produces two consecutive zero bytes.
- In the four-byte-like path, destination offset 2 is not written and may already contain zero.

Consequently, neither an output length nor a valid zero-terminated encoding can be inferred universally from the apparent encoding width.

### Storage preconditions

The destination must permit all stores on the selected path:

| Input range, using unsigned notation | Storage required by explicit stores |
|---|---|
| 0x00000000–0x0000007F | Writable offsets 0–1 |
| 0x00000080–0x000007FF | Writable offsets 0–2 |
| 0x00000800–0x0000FFFF | Writable offsets 0–3 |
| 0x00010000–0x0010FFFF | Writable offsets 0, 1, 3, and 4; an ordinary contiguous buffer must extend through offset 4 |
| 0x00110000–0x7FFFFFFF | Writable offset 0 |
| 0x80000000–0xFFFFFFFF | Writable offsets 0–2 |

These requirements cover only the explicit stores. They do not establish sufficient storage or other preconditions for the unresolved indirect target.

The visible function does not check destination validity, nullness, capacity, address-range overflow, or write permissions. Invalid storage is outside the established successful-operation preconditions.

## Behavior

### Arithmetic conventions

All ranges below describe the original 32-bit input bit pattern.

A **low-six-bit payload** means input bits 0–5, yielding a value from 0x00 through 0x3F.

A **next-six-bit payload** means input bits 6–11, also yielding a value from 0x00 through 0x3F.

A continuation-style byte is formed by combining such a payload with 0x80. Its resulting range is 0x80–0xBF.

Byte conversion retains the low eight bits. The shift-and-mask expression used to obtain the next-six-bit payload is evaluated as 32-bit unsigned arithmetic; the left shift discards bits beyond that width. Its resulting payload is input bits 6–11, not bits 12–17.

### 1. Inputs from 0x00000000 through 0x0000007F

The function performs these stores in order:

1. Store the input value at destination offset 0.
2. Store zero at destination offset 1.

It then returns without the unresolved indirect transfer.

Input zero is accepted by this path and produces zero at both offsets. There is no special distinction between a zero input and other values in this range beyond the byte stored.

### 2. Inputs from 0x00000080 through 0x000007FF

The function performs these stores in order:

1. At offset 0, store 0xC0 combined with the input shifted right by six bits.
2. At offset 1, store 0x80 combined with the low-six-bit payload.
3. At offset 2, store zero.

It then returns without the unresolved indirect transfer.

For this range, the first byte lies between 0xC2 and 0xDF. The result matches the corresponding ordinary two-byte UTF-8 encoding followed by a zero byte.

### 3. Inputs from 0x00000800 through 0x0000FFFF

The function performs these stores in order:

1. At offset 0, store 0xE0 combined with the input shifted right by twelve bits.
2. At offset 1, store 0x80 combined with the next-six-bit payload.
3. At offset 2, store 0x80 combined with the low-six-bit payload.
4. At offset 3, store zero.

It then invokes the unresolved indirect target.

The visible byte construction includes the entire range 0xD800–0xDFFF. No scalar-value validity check excludes those values. An acceptance rule requiring their rejection would contradict the visible branches.

The stores themselves have the familiar three-byte UTF-8 shape. Their persistence after the indirect transfer is not established.

### 4. Inputs from 0x00010000 through 0x0010FFFF

The function performs these stores in order:

1. At offset 0, store 0xF0 combined with the input shifted right by eighteen bits.
2. At offset 1, store 0x80 combined with the next-six-bit payload.
3. At offset 3, store 0x80 combined with the low-six-bit payload.
4. At offset 4, store zero.

It then invokes the unresolved indirect target.

**There is no visible store to offset 2.** Immediately before the indirect transfer, that byte retains its prior value, provided no external actor has modified it.

The byte at offset 1 uses input bits 6–11. It does not use bits 12–17, which would be expected at that position in ordinary four-byte UTF-8.

These are observable properties of the supplied body. They must not be silently repaired in this contract by inserting a missing store, moving a store, or assuming that the unresolved target completes an encoding.

### 5. Inputs from 0x00110000 through 0x7FFFFFFF

The function stores zero at destination offset 0 and then invokes the unresolved indirect target.

No other destination store is visible before that transfer. In particular, there is no visible clearing of the remainder of the buffer, status reporting, or replacement-character encoding.

The zero store may indicate intended empty-string output for out-of-range positive values, but that interpretation is not an independently established error-reporting contract.

### 6. Inputs from 0x80000000 through 0xFFFFFFFF

These inputs do not take the preceding out-of-range path.

The initial comparison against 0x80 is unsigned, so these inputs bypass the single-byte path. Later comparisons interpret the original input as signed. Because these bit patterns are negative under that interpretation, they select the two-byte-style output path.

The function performs these stores in order:

1. At offset 0, store a byte whose upper two bits are set and whose lower six bits are input bits 6–11.
2. At offset 1, store 0x80 combined with input bits 0–5.
3. At offset 2, store zero.

It then returns without the unresolved indirect transfer.

Thus the first output byte can range from 0xC0 through 0xFF. These results are not guaranteed to be valid UTF-8.

The supplied signed right shift acts on a negative intermediate in this range. The stored low byte is nevertheless characterized by the bit rule above: the sign-filled high bits do not affect the low-byte result.

## Side effects

### Explicit memory accesses

The visible body does not read existing destination bytes. It derives its output from the input value and performs the ordered stores specified above.

Untouched offsets retain their previous contents up to the unresolved transfer, subject to external modification. This is particularly significant for offset 2 in the four-byte-like path.

There is no visible buffer-wide initialization or clearing operation.

### Ownership and lifetime

The visible body does not allocate, resize, release, or visibly retain the destination storage. The caller supplies storage and must keep it valid for the explicit stores.

No ownership or lifetime guarantee is established for the unresolved target. In particular, the evidence does not prove that it preserves the allocation, avoids retaining pointers, or leaves memory untouched.

### Other state and failures

No explicit global-state access, I/O operation, synchronization operation, or error-reporting operation appears in the visible body.

That absence does not constrain the unresolved target. Its effects on globals, memory, control flow, and external state remain unknown.

The function has no visible recovery path for an invalid destination or a failed store. The evidence also does not establish whether the indirect target returns normally, fails, or transfers control elsewhere.

The listed store order describes the supplied body’s explicit sequencing. It is not a concurrency guarantee for unsynchronized observers.

Additional conditional acceptance criteria:

- If offsets 0–5 initially contain A5 and the input is 0x00010000, the explicit stores leave them as F0 80 A5 80 00 A5 immediately before the unresolved transfer.
- If offset 2 initially contains zero on that same path, it remains zero before transfer. An observer treating the buffer as a zero-terminated string would encounter that zero before offset 4.

- A final-buffer assertion for an indirect-transfer path is acceptable only under a separately established condition that the target returns and preserves the relevant bytes.
- An implementation that rejects every unsigned value above 0x10FFFF would not match the established behavior for inputs with bit 31 set.

## Uncertainties

### Inferred intent

The prefix bytes, six-bit payloads, thresholds, and terminators suggest an intended UTF-8-related conversion. This is an inference, not a substitute for the observed behavior.

The missing offset-2 store and unusual offset-1 payload on the four-byte-like path may reflect incomplete recovery or behavior supplied elsewhere. Neither explanation is established.

### Documented-only unknowns

The following remain **documented_only**:

- The identity and behavior of the unresolved indirect target.
- Final destination contents after that target executes.
- Overall return and failure behavior on paths involving that target.
- Any additional storage, ownership, or global-state requirements imposed by it.
- Whether the supplied representation captures all original control flow accurately.

No runtime execution, instrumentation, or tests have been performed. The acceptance examples are derived expectations, not observed results.

## Evidence

The contract is based solely on static inspection of the supplied function representation.

Established static evidence includes:

- A byte-addressed destination and a 32-bit unsigned input representation.
- An initial unsigned threshold of 0x80.
- Subsequent signed comparisons at 0x800, 0x10000, and 0x110000.
- Explicit byte stores and their order on each visible path.
- No explicit store to destination offset 2 on the four-byte-like path.
- Extraction of input bits 6–11 for its offset-1 byte.
- Explicit zero stores at the documented offsets.
- Direct returns for the single-byte, ordinary two-byte, and signed-negative input paths.
- Unresolved indirect transfers after the other visible store sequences.

No claim about dependency preservation, completed four-byte encoding, or successful runtime operation is supported beyond that evidence.
