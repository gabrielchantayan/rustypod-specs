# F-0c6c499426e0

## Purpose

F-0c6c499426e0 obtains three values through indirect calls and writes a four-byte result record. The first value selects a category, the second supplies selection flags, and the third controls whether classification is enabled.

The established behavior is a fixed classification and encoding operation. The meanings of the categories, flag bits, output tags, and shared values are not established. Any interpretation as a device event, command, or protocol message would be inferred intent rather than part of this contract.

## Interface

### Inputs

The function receives two arguments:

1. **Context address.** An address used to locate an indirectly dispatched dependency.
2. **Output address.** An address at which the function writes a four-byte record.

The recovered interface represents the context address using a 32-bit integer-shaped argument. Its behavioral role is an address, not an ordinary numeric quantity. No range validation or address sanitization is present.

Under the supplied address model, dispatch uses this layout:

| Location | Role |
|---|---|
| Context address + 4 bytes | Pointer to a dispatch-bearing object |
| First pointer-sized field of that object | Pointer to a dispatch table |
| Dispatch table + 0x78 bytes | First callable entry |
| Dispatch table + 0x74 bytes | Second callable entry |
| Dispatch table + 0x70 bytes | Third callable entry |

The offsets are byte offsets, not entry indices.

The three returned values are interpreted as follows:

| Call order | Returned value | Interpretation |
|---|---|---|
| First | Category | Signed 32-bit integer |

The supplied representation shows no explicit arguments at these call sites. It does not establish the complete calling convention, hidden arguments, or dependency signatures.

### Output

The payload is written as one 16-bit field. Its byte order is not established by the supplied evidence. A consumer must not assume a particular ordering of the two payload bytes solely from this contract.

The function neither reads the previous record contents nor preserves any part of the four-byte record on normal completion.

## Behavior

### 1. Obtain the three dependency results

The function performs the three indirect calls in this order:

1. Dispatch at table offset 0x78, obtaining the category.
2. Dispatch at table offset 0x74, obtaining the selection flags.
3. Dispatch at table offset 0x70, obtaining the enable flags.

All three calls occur before the function makes any explicit write to the output record. A disabled result does not bypass either of the first two calls.

Each call expression resolves its dispatch chain from the context. The evidence does not establish a single retained object or table pointer reused across all three calls. Consequently, an earlier dependency may affect the target of a later call by changing reachable dispatch state.

Once obtained, the returned category and flag values are retained for classification. The function does not call a dependency again to refresh them.

### 2. Apply the enable gate

Only bit 0 of the enable flags controls this gate.

If bit 0 is clear, the function writes:

- Result tag: 0.
- Result subtype: 0.
- Payload: 0.

It then returns without entering enabled classification.

All other enable-flag bits are irrelevant to the function’s own decision. For example, an enable-flags value of 2 is disabled, while a value of 3 is enabled.

The disabled path does not explicitly read either shared value described below.

### 3. Read the baseline payload

If enable bit 0 is set, the function obtains a shared value and converts it to a 16-bit quantity. This document calls that quantity the **baseline payload**.

The baseline payload is obtained before the category is classified. This read therefore occurs even when the category will ultimately produce a zero payload or a fixed literal payload.

The shared object’s declared width, update mechanism, and semantic meaning are unknown. The established property is the 16-bit value used by this function. If the underlying value is wider, conversion retains its low 16 bits.

### 4. Classify the category

Two category sets receive flag-sensitive treatment:

| Category set | Signed decimal values | Hexadecimal values |
|---|---|---|
| Shared-payload set | 48, 52, 53, 202 | 0x30, 0x34, 0x35, 0xCA |
| Fixed-payload set | 32, 36, 37, 200 | 0x20, 0x24, 0x25, 0xC8 |

Every other signed 32-bit category is unsupported for this classification. This includes negative values, 0, and values immediately adjacent to the listed values unless separately listed.

For an unsupported category, the enabled result is:

- Result tag: 2.
- Result subtype: 3.
- Payload: 0.

Selection flags do not alter that result.

For a category in the shared-payload set, the function additionally reads another shared value and converts it to a 16-bit quantity. This document calls it the **alternate payload**. The alternate payload is read before testing the selection flags for that category.

Consequently, the alternate-payload read occurs even if the selected result will use the baseline payload, 0x1000, or zero instead. Categories in the fixed-payload set do not explicitly read the alternate payload.

### 5. Select the enabled result

For either recognized category set, four selection bits matter. Their priority, from highest to lowest, is:

1. 0x40.
2. 0x80.
3. 0x10.
4. 0x04.

The first present bit in that order determines the result. All other selection bits are ignored.

| Highest-priority applicable bit | Result subtype | Shared-payload set: payload | Fixed-payload set: payload |
|---|---:|---|---|
| 0x40 | 3 | Alternate payload | 0x1100 |
| 0x80 | 11 | 0x1000 | 0x1000 |
| 0x10 | 11 | Baseline payload | Baseline payload |
| 0x04 | 3 | Alternate payload | 0x1100 |
| None | 3 | 0 | 0 |

Every enabled result has result tag 2.

Important consequences of the priority rule include:

- 0x40 overrides 0x80, 0x10, and 0x04.
- Without 0x40, 0x80 overrides 0x10 and 0x04.
- Without 0x40 or 0x80, 0x10 overrides 0x04.
- A selection value with none of these four bits produces subtype 3 and payload zero, even if unrelated bits are set.

This is a priority selection, not an accumulation or combination of payloads.

### 6. Write the result

On every normal path, the function explicitly writes the record in this order:

1. One byte at output offset 0.
2. One byte at output offset 1.
3. One 16-bit field at output offset 2.

There is no explicit output write before the dependency calls or between those calls.

All required shared-value reads precede these output writes. If output storage aliases a shared value or dispatch-related storage, the explicit writes may modify that storage, but the function performs no further explicit classification reads after writing begins.

The record is not shown as an atomic four-byte update. No guarantee is established that another observer can see only a complete old or complete new record.
