# F-96f2113e6c12

## Purpose

F-96f2113e6c12 performs a gated, ordered teardown of an object, followed on the normal path by allocation-accounting updates and a final allocation-related operation.

The established behavior is a sequence of dependency calls and direct memory updates. Describing the function as a destructor or deallocator is inferred intent: the supplied evidence does not establish the ownership rules or complete effects of its dependencies.

The function has three materially different outcomes:

- An initial dependency returns zero, and the function returns immediately.
- Teardown reaches a nonzero terminal-state field, invokes two dependencies, and does not return according to the supplied annotation.
- Teardown proceeds through object-wide processing and, for a nonzero object address with acceptable allocation metadata, updates accounting and invokes final allocation-related dependencies.

No runtime tests have been performed.

## Interface

### Input and result

The function accepts one 32-bit value used as an object base address. It returns no explicit value.

The supplied representation uses:

- 32-bit object addresses, integer fields, and accounting words.
- Unsigned 16-bit allocation classification fields.
- One 64-bit dependency result, interpreted as two independent 32-bit components.

This contract describes those represented widths. The original type declarations and calling convention are not available.

A zero object address is **not** generally accepted as a null-safe input. The only explicit zero-address check occurs after substantial teardown work. If the initial gate allows execution, earlier calls and an unconditional read at object offset `0x9D0` already use the supplied address.

## Behavior

### 1. Initial gate

The first operation is a call to F-cd52fcefba54 with no explicit arguments.

If its result is zero, the function returns immediately. No subsequent dependency call or direct object access is shown on that path.

If the result is nonzero, teardown proceeds. The gate’s side effects, if any, remain possible even on the immediate-return path.

### 2. First traversal

F-f00a43009ecb receives the object base and supplies the initial traversal value.

While the current value is nonzero, each iteration:

- Calls F-86e96ca6f077 with the current value to obtain the next value.
- Calls F-169ef81f8355 with the current value.
- Continues using the previously obtained next value.

Thus, the next value is obtained **before** the current element is processed by F-169ef81f8355. The traversal does not derive its successor by rereading the current element after that call.

A zero initial value skips the traversal. There is no visible cycle detection, iteration bound, or error-result handling. A cyclic or otherwise nonterminating successor sequence can prevent all subsequent teardown phases from being reached.

### 3. Object and component processing

After the first traversal ends, the function calls F-6fe983b82266 with the object base.

It then calls F-1dc7fdb390e6 exactly 22 times, provided each call returns:

1. With the address at offset `0x34`.
2. With the address at offset `0x8C`.
3. With each of the twenty addresses beginning at `0xE4`, advancing by `0x58`, through `0x76C`.

These calls are unconditional once this phase is reached. No component-presence checks are shown.

Their ordering is observable. The evidence does not establish whether these calls initialize, clear, destroy, release, or otherwise modify the addressed components.

### 4. Second traversal

F-3d9e13a03861 receives the object base and supplies a second initial traversal value.

For each nonzero current value:

- F-bcb367eab8e4 receives that value and returns a 64-bit result.
- The upper 32 bits of the result are passed as a 32-bit value to F-c200511f3bf0.
- The lower 32 bits become the next traversal value after that call returns.

The two components are therefore used differently: the upper half is a dependency argument, and the lower half controls continuation.

The upper half is passed even if it is zero. A zero lower half ends traversal only after the corresponding upper-half call has occurred.

As with the first traversal, no cycle check, iteration limit, or explicit error handling is shown.

### 5. Terminal-state branch

After the second traversal, the function reads the 32-bit field at offset `0x9D0`.

If it is nonzero:

1. F-a600efb7b035 is called with no explicit arguments.
2. F-feee9156a257 receives the previously read field value.

The supplied source annotation identifies the second call as non-returning. On that interpretation, this path does not perform the later field checks, object-wide processing, global-context capture, or accounting updates.

The field value is read before F-a600efb7b035 and passed afterward. The function does not explicitly reread the field between those calls.

### 6. Conditional calls and object-wide processing

If the terminal-state field was zero, the function reads the field at offset `0x2C`. A nonzero value causes a call to F-2ff42e8572a4 with no explicit arguments.

It then reads the field at offset `0x30`. A nonzero value causes a second call to the same dependency, again with no explicit arguments.

The second field is read after any call caused by the first field. Consequently, the second decision can reflect changes made by that earlier call. Neither field value is shown as an explicit argument.

The function next calls:

- F-2fd8826557a4 with no explicit arguments.

The numeric size argument does not, by itself, establish that the first dependency clears, copies, or releases exactly that many bytes.

### 7. Global-context capture and allocation validation

After those calls, the function reads a 32-bit context address from a global pointer slot.

If the object base is zero, it skips the remaining allocation-accounting block and returns. This late check does not make the earlier phases safe for a zero address.

For a nonzero object base, the function examines the 32-bit word at offset `−8`:

- If the word is zero, it calls F-a817d8d58c10.
- Otherwise, it tests bit 0; if that bit is set, it calls F-a817d8d58c10.

The supplied annotation marks this dependency as non-returning.

The zero test and bit test are separate reads in the supplied representation, with the second conditional on the first read being nonzero. Treating them as a single stable snapshot requires an additional memory-stability assumption.

No other prefix bits are rejected by this validation. In particular, bit 1 and the two highest bits are not independently grounds for rejection.

### 8. Accounting updates and final operation

For metadata that passes validation, F-c0fc6d033caa receives the captured context address.

After that call returns, the function:

2. Reads the prefix word and masks it with `0x3FFFFFFC`, producing an accounting quantity.
3. Subtracts that quantity from the 32-bit word at context offset `0x224 + 4 × first index`.
4. Subtracts the same quantity from the word at context offset `0x30C`.
5. Reads the unsigned 16-bit index at object offset `−2`.
6. Subtracts the same quantity from the word at context offset `0xE0 + 4 × second index`.
7. Subtracts the same quantity from the word at context offset `0x220`.
8. Calls F-09dcb55e8e0a with no explicit arguments.
9. Decrements by one the word at context offset `0x310 + 4 × that result`.
10. Decrements by one the word at context offset `0x390`.
11. Rereads the prefix word, masks it with `0x3FFFFFFC`, and subtracts that newly obtained quantity from the word at context offset `0x08`.
12. Calls F-cc6c9b4a0f68 with the captured context address and the address of the prefix word.

## Side effects

### Direct writes and arithmetic

All explicit memory writes are in the final context-accounting phase. Earlier memory effects occur through dependencies and cannot be characterized from this function alone.

The accounting operations are 32-bit word updates. There is no visible underflow check or saturation. At the represented machine-word level, subtraction and decrement retain the low 32 bits of the result.

The accounting mask retains bits 2 through 29. Its result is a multiple of four between zero and `0x3FFFFFFC`, inclusive. A nonzero prefix can therefore pass validation while producing a zero accounting quantity.

Each 16-bit index is zero-extended before multiplication by four. Its scaled contribution ranges from zero through `0x3FFFC`. No table-bound checks are shown.

The result of F-09dcb55e8e0a is used in another scaled address calculation without visible range validation. Its permitted range and signedness contract are unknown.

If computed accounting addresses alias one another, updates occur sequentially and can accumulate on the same word. The function does not enforce table separation.

### Ownership and synchronization

The dependency sequence is consistent with resource teardown and allocator bookkeeping, but does not prove:

- Ownership of either traversal’s elements.
- Whether any dependency releases the object or its prefix.
- Whether the final dependency pair frees storage.
- Whether F-c0fc6d033caa and F-e586bff64fb7 implement locking.
- Whether no-explicit-argument dependencies preserve globals or allocation metadata.

The captured context address is reused after subsequent calls rather than reloaded from the global pointer slot. This establishes local address reuse, not context validity or immutability.

### Errors and partial progress

There is no recoverable error return, rollback, or explicit retry.

If execution terminates or a dependency fails partway through, earlier calls and writes have already occurred. In particular, prefix validation happens after both traversals and the object-wide processing phase; invalid allocation metadata does not prevent those earlier effects.

## Acceptance examples

These are conditional acceptance criteria, not executed tests.

1. **Gate denies continuation.** If F-cd52fcefba54 returns zero, accept only an immediate return with no later call or direct object access by this function.

2. **First traversal ordering.** If its initial value is A, A’s successor is B, and B’s successor is zero, require successor lookup for A, processing of A, successor lookup for B, and processing of B, in that order.

3. **Empty traversals.** If both initial traversal values are zero, neither per-element processing dependency is called. Object and component processing still occurs between the two traversal initializations.

4. **Packed terminal element.** If a second-traversal result has lower half zero and upper half X, require one call to F-c200511f3bf0 with X before traversal ends. This also applies when X is zero.

5. **Terminal-state selection.** If the field at `0x9D0` is nonzero when read, require F-a600efb7b035 followed by F-feee9156a257 with that saved value. Under the non-returning annotation, no later phase occurs.

6. **Conditional-field mutation.** If the field at `0x2C` is nonzero and its resulting dependency call changes the field at `0x30` to zero, the second conditional call is omitted, assuming no intervening change.

7. **Rejected prefix.** A zero prefix or one with bit 0 set selects F-a817d8d58c10 before accounting updates, although earlier teardown has already occurred.

8. **Zero accounting quantity.** A stable prefix value of `2` passes validation but masks to zero. The five quantity-based subtractions leave their target words unchanged, while the two count decrements still occur.

9. **Stable ordinary accounting.** With a stable prefix of `0x102`, the masked quantity is `0x100`. Assuming valid, distinct targets and no interfering dependency mutations, the five quantity-based targets each decrease by `0x100`, and the two count targets each decrease by one.

10. **Reread-sensitive total.** If F-09dcb55e8e0a changes the prefix’s masked quantity, the later subtraction at context offset `0x08` uses the changed quantity; the earlier four subtractions retain the previously captured quantity.
