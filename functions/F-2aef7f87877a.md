# F-2aef7f87877a

## Purpose

F-2aef7f87877a expands a sequence of 16-bit elements into adjacent duplicate pairs within a destination object. It also writes the requested element count to a separate 32-bit output location before processing any elements.

For a source sequence of three distinct elements, the destination payload receives the first element twice, then the second twice, then the third twice. The payload begins 48 bytes after the supplied destination base.

This is a sequential memory transformation, not necessarily a transformation of a snapshot of the original source. If the output locations overlap the source, earlier writes can affect later source reads.

The supplied static representation establishes the memory operations and control flow described below. It does not establish the application-level meaning of the elements, the destination object’s complete layout, or the ownership of any participating allocation.

## Behavior

### Initial count publication

Before reading the first source element or writing the destination payload, the function stores the supplied 32-bit element count at the count-output address.

This write occurs even when the element count is zero. It is not a completion report: it precedes all payload processing and is not reduced if execution later encounters an invalid address.

The destination payload’s starting address is derived as the destination base plus 48 bytes. Deriving that address does not itself read or write the destination header.

### Sequential expansion

The function processes source positions in increasing order, beginning at position zero and stopping before the supplied count.

For each position:

1. It reads one 16-bit element from the corresponding source position.
2. It writes that captured element to the next destination slot.
3. It writes the same captured element to the immediately following destination slot.

It then proceeds to the next source position and next pair of destination slots.

The source advances by two bytes per processed element. The destination advances by four bytes per processed element.

The two writes for a position use the same previously read element. There is no second source read between them. Consequently, if the first destination write changes the source location just read, the second destination write still duplicates the captured value rather than fetching a replacement.

There is no terminator condition based on element contents. Zero-valued elements, all-one bit patterns, and repeated elements are processed exactly like other 16-bit values.

### Completion

On normal completion:

- The function has performed exactly \(N\) logical 16-bit source reads.
- It has performed exactly \(2N\) logical 16-bit destination stores.
- It has performed one logical 32-bit count store.
- It returns without a result value.

There is no appended terminator, separate destination-length field, completion flag, or additional status write in the supplied evidence.

### Zero count

For a zero count, the count-output location receives zero and no source element or destination payload slot is accessed.

This does not make every argument universally valid. In particular, the count-output address must still support its store. The supplied representation also forms the destination payload address, but the target language and machine rules governing unusual integer-address inputs are not independently established.

### Overlap and aliasing

The initial count write participates in aliasing behavior. If the count-output location overlaps source bytes, the source reads observe memory after that write, subject to the execution environment’s memory semantics and byte order.

Destination writes can likewise change source elements that have not yet been read. The function does not protect against that effect by making a complete preliminary copy or by traversing backward.

If the count-output location overlaps destination payload bytes, a later payload write can overwrite part or all of the stored count. The guarantee is that the count store occurs first, not that its value remains intact at return.

The count used to control traversal is the supplied argument. Overwriting the memory at the count-output address does not instruct the function to reload that location or change the requested iteration count.

### Integer boundaries

The count and traversal index are represented as unsigned 32-bit quantities. The comparison is unsigned.

At the maximum count, 4,294,967,295, the index reaches that value only after processing the preceding position, at which point the comparison ends traversal. The loop’s stopping rule does not itself require an index increment from the maximum value back to zero.

Address calculations are a separate constraint. A maximum-count request would mathematically describe 8,589,934,590 source bytes and 17,179,869,180 destination payload bytes. Those extents cannot be assumed representable or accessible merely because the count is representable.

The supplied source-position calculation multiplies a 32-bit unsigned index by two. Its unsigned arithmetic has a 32-bit wrap boundary. Therefore, callers must not extrapolate the ordinary contiguous-layout description to arbitrarily large counts without accounting for target address arithmetic. The exact native pointer behavior and destination-address overflow behavior remain undocumented here.

## Side effects

The explicit memory effects are limited to:

- One 32-bit write through the count-output address.
- A sequence of 16-bit source reads.
- A sequence of paired 16-bit writes beginning at destination offset 48.

Under non-overlapping, valid-buffer conditions, the function does not write the 48-byte destination prefix. If the count-output location aliases that prefix, however, the initial count store can modify it.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed test results.

### Distinct elements in disjoint buffers

Given three readable source elements with 16-bit values 0x1234, 0xABCD, and 0x0000, sufficient disjoint destination storage, and a separate writable count-output location:

- The count-output location is first written with 3.
- The six destination elements beginning at byte offset 48 are 0x1234, 0x1234, 0xABCD, 0xABCD, 0x0000, and 0x0000.
- The destination prefix is unchanged.
- No seventh payload element is written.

The values describe 16-bit elements; their byte representation depends on target byte order.

### Empty input

Given a count of zero and a valid count-output location:

- The count-output location is written with zero.
- No source element is read.
- No destination payload element is written.

This example does not establish that an arbitrary destination-base integer is valid under every possible execution model.

### Single-element input

Given a count of one and a source element of 0xFFFF:

- The count-output location receives 1.
- Destination slots beginning at byte offsets 48 and 50 both receive 0xFFFF.
- No source element at the next source position is read.

### Source coincides with payload start

Assume valid, suitably aligned storage; the source begins exactly at the destination payload start; the count-output location is disjoint; and the initial first two source elements are distinct values A and B.

For a count of two:

- The first source read captures A.
- The first pair of writes produces A, A, overwriting the original second source element.
- The next source read therefore captures A, not the original B.
- The four output elements are A, A, A, A.

This distinguishes the established sequential behavior from snapshot-based duplication.

### Count-output location inside the payload

Assume one source element, valid storage, and a count-output location spanning exactly the first two 16-bit destination slots.

The initial 32-bit store writes the count value 1. The subsequent two payload stores overwrite those same bytes with two copies of the source element. The final contents of that location need not represent the integer 1.
