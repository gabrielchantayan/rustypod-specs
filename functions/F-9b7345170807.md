# F-9b7345170807

## Purpose

F-9b7345170807 processes an ordered collection of objects associated with a supplied owner. For each object, it first asks whether that object is applicable to a corresponding input word. Applicable objects are then evaluated with the owner, input word, and an additional caller-supplied word.

Processing stops when an evaluation returns exactly **1** or **2**. That value becomes the function’s result. If every entry is processed without either result, the function returns **0**.

The function also conditionally emits diagnostics. Diagnostic eligibility is checked separately for each processed entry, after either the applicability check or the evaluation. A terminal evaluation result does not bypass this diagnostic step.

“Owner,” “object,” “applicability,” and “evaluation” are descriptive roles inferred from the call structure. Their domain-specific meaning is not established.

## Interface

### Inputs

The function has three arguments:

| Argument | Established use |
|---|---|
| Owner address | Identifies storage containing a diagnostic-related word at byte offset **+8** and a collection-related field at byte offset **+32**. It is also passed to the evaluation callback and diagnostic-gating dependency. |
| Context word | An opaque **32-bit** value passed unchanged to each evaluation callback. This function does not dereference or interpret it. |
| Input-base reference | An address of a **32-bit word** containing the base address of a corresponding input-word sequence. The reference is dereferenced again for each processed entry. |

The supplied representation uses four-byte words, four-byte collection entries, and four-byte input entries. Addresses are carried through those words in the recovered interface. This establishes a 32-bit data-layout model for this contract; it does not independently establish a source-language ABI or a portable representation on wider machines.

The owner is not itself treated as the collection base. The collection base is loaded from the owner’s **+32** field.

### Output

The normal return value is a 32-bit integer with one of three values:

- **0:** The captured entry count was exhausted without an evaluation result of 1 or 2.
- **1:** An evaluation callback returned exactly 1.
- **2:** An evaluation callback returned exactly 2.

Other evaluation results do not propagate to the caller. They allow processing to continue.

There is no explicit output buffer and no explicit error result distinct from these values. In particular, **0 does not prove that every object was applicable, that every evaluation succeeded, or that diagnostics were disabled**.

### Preconditions

For execution to complete normally, every memory access actually reached must be valid, and each invoked dependency must support the arguments supplied to it.

Depending on the path, this includes valid owner storage, collection entries, input-reference storage, input words, object storage, dispatch tables, and callable dispatch entries.

The function performs no visible null checks, bounds validation, dispatch validation, or recovery from invalid memory. An empty captured count avoids collection-entry, input-reference, and object accesses, but does not avoid the initial count dependency call.

## Behavior

### Count acquisition and iteration bounds

The first external action is a call to **F-0c14ee61f55d**, receiving the address of the owner’s **+32** field.

Its result is captured as an unsigned 32-bit count. The entry index begins at zero. Before processing each entry, the function compares the index with that captured count using unsigned ordering. If the index is greater than or equal to the count, it returns 0.

The count dependency is called only once. This function does not refresh the count after callbacks or diagnostic calls, even if those calls modify the collection or related owner state.

The count controls iteration but does not establish that either the collection or the input sequence has enough accessible entries.

### Per-entry reads

For each index below the captured count, the function performs the following ordered accesses before invoking the applicability callback:

1. It reads the collection base from the owner’s **+32** field.
2. It reads the object address at the current four-byte collection position.
3. It reads the input-sequence base through the input-base reference.
4. It reads the 32-bit input word at the corresponding four-byte input position.
5. It obtains and invokes the object’s applicability callback through dispatch-table offset **+20**.

The object address and input word are retained for the current entry. They are not fetched again from their respective sequences before evaluation.

The collection base and input-sequence base are nevertheless reloaded on each new iteration. Changes made during an earlier callback can therefore affect which object or input word is used at a later index.

### Applicability decision

The applicability callback receives:

- The selected object address.
- The selected 32-bit input word.

Its return is interpreted as zero versus nonzero, not as a strict Boolean encoding.

If it returns **zero**, the evaluation callback is not invoked. The function proceeds to the diagnostic-gating step for an inapplicable entry, then advances to the next index.

If it returns **any nonzero value**, including a negative integer representation, the function invokes the evaluation callback through dispatch-table offset **+24**.

### Evaluation

The evaluation callback receives, in order:

- The selected object address.
- The owner address.
- The selected 32-bit input word.
- The caller-supplied context word.

The input word is the value captured before the applicability call. An applicability callback that changes the input sequence does not thereby change the current entry’s evaluation argument.

The evaluation callback’s 32-bit result is retained across subsequent diagnostic-related calls. The function does not classify it until those calls finish.

Exactly **1** and **2** are terminal. Every other result permits advancement to the next index.

### Diagnostic gating and emission

Each entry that reaches the end of either the inapplicable branch or the evaluation call invokes **F-b8fd684a82f2** with the owner address.

This happens:

- After an applicability result of zero, without evaluation.
- After every completed evaluation, regardless of its result.
- Before returning a terminal evaluation result.

If the gating dependency returns zero, this function makes no diagnostic-value callback or diagnostic-emission call for that entry.

If it returns nonzero, the function:

1. Invokes the selected object’s callback at dispatch-table offset **+8**, passing the object address.
2. Retains that callback’s opaque 32-bit result.
3. Reads the word at owner offset **+8**.
4. Calls **F-395ef1af5853** with that owner field, a branch-specific fixed diagnostic template, and the opaque diagnostic value.

There are two distinct template selections: one for an inapplicable entry and one for an evaluated entry. The supplied evidence does not expose their complete byte strings, so this contract does not specify exact diagnostic wording or formatting.

The diagnostic-value callback’s result is not established to be a string, borrowed pointer, owned allocation, or numeric identifier. Only its forwarding to the diagnostic dependency is established.

Neither the gating result nor a diagnostic-related return value changes which evaluation result is ultimately returned by this function. Their side effects, failure behavior, or failure to return can still affect whether execution reaches that return.

### Advancement and termination

After an inapplicable entry, or an evaluation result other than 1 or 2, the unsigned index increases by one and iteration continues.

The count and index use 32-bit unsigned comparisons. No signed interpretation of the captured count limits iteration. A high-bit-set count is therefore not treated as negative.

Under ordinary progress, the index does not need to wrap: even for the maximum unsigned count, the index can reach that count and terminate at the next bounds comparison. This does **not** make the indexed memory accesses safe. Four-byte index scaling and base-address addition can exceed valid storage, and the function has no visible guard against that condition.

## Side effects

### Direct effects

The visible body reads owner fields, collection entries, the input-base reference, input words, and dispatch information.

It contains no explicit store to caller-provided memory and no explicit allocation or deallocation. Its direct local state consists of the captured count, current index, current object address, input word, callback results, and diagnostic value.

These facts do not establish that the overall operation is read-only.

### Dependency-mediated effects

All invoked dependencies and callbacks may have effects not established here. In particular, this contract does not assume that they:

- Preserve owner fields or global state.
- Preserve collection contents or the input-base reference.
- Preserve object storage or dispatch tables.
- Avoid allocating, retaining, or releasing memory.
- Return normally.

The visible function continues to use the selected object address after applicability, evaluation, and diagnostic-gating calls. It does not establish a lifetime safeguard around that address. Safe use therefore requires a compatible lifetime contract from those dependencies.

Dispatch information is obtained for each reached callback invocation; the function does not visibly capture one immutable dispatch table for the entire entry. A dependency that changes the object’s dispatch state may affect later callbacks on the same selected object, provided the subsequent accesses remain valid.

The diagnostic destination word is read only after the diagnostic-value callback returns. A change to owner offset **+8** made by that callback can therefore affect the destination argument used for the current diagnostic.

### Ownership

The visible function does not explicitly take ownership of the owner, collection, input sequence, objects, or context word. Nor does it explicitly release them.

Passing an address or value to a dependency does not establish whether that dependency retains it. Ownership transfer, retention, reference counting, and diagnostic-value cleanup remain unspecified.

## Acceptance examples

These are conditional behavioral requirements derived from static evidence, not reports of executed tests. Unless otherwise stated, all accessed memory is valid and every dependency returns normally.

1. **Empty collection.**  
   If F-0c14ee61f55d returns zero, the function returns 0. No collection entry, input-base reference, or object dispatch is accessed by the visible body. The count dependency has still been called.

2. **Inapplicable entry with diagnostics disabled.**  
   For a captured count of one, if applicability returns zero and F-b8fd684a82f2 returns zero, evaluation is skipped, no diagnostic-value callback runs, and the function returns 0 after advancing past the entry.

3. **Noncanonical applicability value.**  
   If applicability returns a negative value, evaluation still runs because the applicability decision is nonzero versus zero.

4. **Terminal result 1 with diagnostics enabled.**  
   If evaluation returns 1 and the gate is nonzero, the diagnostic-value callback and F-395ef1af5853 run before the function returns 1. No later entry is processed.

5. **Terminal result 2 with diagnostics disabled.**  
   If evaluation returns 2 and the gate is zero, the function returns 2 after the gating call, without invoking the diagnostic-value callback.

6. **Nonterminal evaluation result.**  
   If evaluation returns 3, zero, or a negative value, processing continues after the diagnostic step. Those values are not returned merely because they came from evaluation.

7. **First terminal result wins.**  
   If an earlier entry evaluates to 2 and a later entry would evaluate to 1, the later entry is not reached. The result is 2, subject to the earlier entry’s diagnostic sequence completing.

8. **Current input is captured before applicability.**  
   If applicability changes the current input-sequence word, evaluation still receives the previously read word. A later iteration reloads the input base and reads its own indexed word.

9. **Mutable bases with a fixed count.**  
   If a callback replaces the collection base or input base, the next iteration uses the replacement base. The original captured count still governs iteration; shortening either allocation does not trigger a new bounds check.

10. **Diagnostic destination changes during value production.**  
    If the diagnostic-value callback changes owner offset +8, the subsequent diagnostic call receives the changed field value, because that field is read afterward.
