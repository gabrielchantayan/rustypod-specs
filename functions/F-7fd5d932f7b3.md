# F-7fd5d932f7b3

## Purpose

F-7fd5d932f7b3 performs ordered updates to shared accounting state, processes caller-supplied addresses in chunks of at most 20 bytes, XORs working bytes into a shared pool, and finally XORs 20 working bytes into a selected shared region.

The visible structure suggests a pool-mixing operation. That interpretation does not establish cryptographic properties, entropy accounting, synchronization, or the semantics of any dependency.

A central limitation is that the initial external invocation is **not an established copy operation**. The supplied representation establishes its three arguments, but not its effects. Consequently, the initial contents of the local working region—and results depending on those contents—remain conditional on that dependency’s unknown contract.

All behavior below is based on static evidence. No runtime tests have been performed.

## Behavior

### 1. Establish the fixed identity condition

The function first captures the current state pointer and reads its offset-16 word.

If that word is zero, the identity condition is false and no identity query occurs.

Otherwise, the following operations occur in order:

1. F-890414d1fd99 receives `(5, 19, 0, 0)`.
2. F-7eadd9e17dc6 is called without explicit arguments.
3. Its result is compared with offset 20 of the initially captured state object.
4. F-890414d1fd99 receives `(6, 19, 0, 0)`.

The offset-20 read follows the identity query; it is not an entry-time snapshot. The state object used for this comparison remains the initially captured object even if a dependency changes the global state selection.

If the resulting identity condition is false, F-890414d1fd99 then receives `(9, 18, 0, 0)`.

The condition is retained for later notification decisions. It is not recomputed after subsequent state changes. The numeric calls are event-like; their synchronization meaning is unknown.

### 2. Capture state values and invoke the unmapped dependency

After the initial notifications, the function reloads the global state pointer. Through this newly captured pointer, it reads, in order:

1. Offset 28 into the first metadata word.
2. Offset 4 into the local pool cursor.
3. Offset 32 into both the second metadata word and a value retained for shared-state accounting.

It then invokes an unmapped external dependency with three explicit arguments:

1. The local 20-byte working-region address.
2. The currently selected shared-region address.
3. The integer 20.

This establishes an invocation and argument values only. It does **not** establish a 20-byte copy, the direction or extent of memory accesses, initialization of the working region, preservation of the shared region, or preservation of globals.

The working region must therefore not be described as a shared-value snapshot. The state values captured before this invocation remain the values used by the subsequent explicit arithmetic, subject to any memory mutation actually performed by dependencies.

### 3. Update position-related state

The captured cursor and signed byte count are added using the represented 32-bit arithmetic. The resulting value is written to offset 4 of the state object captured in step 2.

The wrap bound is then loaded.

The source’s overflow-aware subtraction conditions select the following signed threshold behavior:

- If the resulting position is at least 1023, F-870c4fcf7295 receives that position and the loaded wrap bound. A secondary result channel is written to offset 4 of the captured state object. The previously loaded wrap bound is written to offset 0 of that same object.
- Otherwise, offset 0 is read through the current global state pointer. If this extent-like value is signed-less-than 1023 and signed-less-than the new position, the new position is written to offset 0 through the global state selection.

The intermediate constant 768 does not establish an additional observable boundary.

The original captured cursor remains the starting cursor for direct pool writes; this accounting step does not replace it with the updated position or the dependency’s secondary result.

The distinction between captured and globally reselected state matters. The unmapped dependency may have changed the global state pointer before these operations.

### 4. Update the offset-32 field

F-870c4fcf7295 receives the original signed byte count and 20.

Its represented 64-bit result is divided into two 32-bit components:

- The low component contributes directly to the update.
- An additional one contributes if the high component, interpreted as signed, is greater than zero.

The low component, that conditional increment, and the earlier offset-32 value are added. The resulting 32-bit value is written to offset 32 of the captured state object.

This does not establish division, remainder, or a rounded-up chunk count. Those interpretations require the dependency’s contract.

If the identity condition is false, F-890414d1fd99 then receives only the two explicit arguments `(10, 18)`. Additional arguments must not be invented from other invocations of that dependency.

### 6. Process chunks

A signed progress value starts at zero. An iteration occurs while progress is signed-less-than the original byte count.

The chunk size is the smaller of 20 and the represented difference between the byte count and progress. For ordinary nonoverflowing positive counts, chunks are 20 bytes except for a possible shorter last chunk.

Zero and negative byte counts skip all iterations.

Each iteration performs these operations in order:

1. Call F-764a7398631d.
2. Call F-e3ef981e414f with the context address, the preceding result, and zero.
3. Call F-2cfb687bb8ab with the context address, working-region address, and explicit length 20.
4. Perform the pool-related submissions described below.
5. Call F-2cfb687bb8ab with the context address, current input address, and chunk size.
6. Call F-2cfb687bb8ab with the context address, metadata address, and explicit length 8.
7. Call F-0b1e8b902739 with the context address, working-region address, and zero.
8. Reload the wrap bound.
9. Increment the second local metadata word by one.
10. Advance the input address by the chunk size.
11. Perform the direct pool XOR operations.
12. Increase signed progress by **20**, including after a short final chunk.

The progress increment differs from the input-address increment. This matters at extreme counts where signed progress arithmetic can overflow.

The explicit metadata increment is local, not a shared offset-32 write. No explicit operation changes its first word after capture. Dependencies receiving its address may have additional, unknown effects.

#### Pool-related submissions

The function forms the represented 32-bit result of cursor plus chunk size minus 1023.

If that result is signed-positive:

- F-2cfb687bb8ab receives the context address, captured pool base plus cursor, and an explicit length equal to chunk size minus that positive result.
- After that invocation, the next pool address is loaded from the then-current global pool base.

Otherwise, the next pool address is captured pool base plus cursor.

The function then calls F-2cfb687bb8ab with **only two explicit arguments**: context address and selected pool address.

No explicit length is established for this final pool submission. Its byte consumption, calling convention, and any implicit argument state are unknown. It must not be specified as consuming the entire chunk or the remainder of a split chunk.

#### Direct pool XOR operations

For each working-byte index from zero through chunk size minus one:

- The pool byte at captured pool base plus current cursor and the corresponding working byte are read.
- Their XOR is written to that pool address.
- The cursor is incremented.
- If the incremented cursor is signed-greater-than-or-equal-to the wrap bound loaded for this iteration, the cursor is reset to zero.

Both operand reads precede their corresponding write; their relative evaluation order is not independently established.

The wrap check follows the access and increment. An invalid starting cursor is not normalized before the first access. Direct writes use the captured pool base, even when a pool-related dependency submission used a newly selected global base.

### 7. Finish context processing and fold back working bytes

If the identity condition is false, F-890414d1fd99 next receives only `(9, 18)` as explicit arguments.

The global shared-region base is then loaded once. Exactly 20 bytewise XOR updates follow, in increasing offset order:

- Read the current destination byte and corresponding working byte.
- Write their XOR to the destination byte.

The working bytes are the bytes present at this stage. They are not established to equal the entry shared bytes, nor is the final destination established to be the region supplied to the unmapped dependency.

Each update uses the bytes available when that update executes. No separate 20-byte destination snapshot or overlap protection is visible.

### 8. Apply the accounting contribution

After the fold-back, offset 8 is read through the current global state pointer.

If its signed value is less than 32, the original accounting contribution is added and the resulting 32-bit value is written back. Otherwise, no explicit write to this field occurs.

This is a pre-update threshold, not saturation. It allows crossing above 32 and allows decreases from values below 32.

If the identity condition is false, the final visible invocation is F-890414d1fd99 with `(10, 18, 0, 0)`.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume normal dependency returns and valid accesses.

1. **Identity match.** With nonzero offset 16 and a query result equal to the captured object’s offset-20 value at comparison time, the two category-19 notifications occur. All category-18 notifications are omitted. Processing and accounting still occur.

2. **Twenty-one input bytes.** Under nonoverflowing arithmetic, there are chunks of 20 and 1. Input submissions use those respective lengths; working-region submissions each use 20; metadata submissions each use 8. Progress advances to 20 and then 40.

3. **Zero count without a copy assumption.** No chunks execute. The unmapped invocation, position and offset-32 accounting, context initialization and finalization, final 20-byte XOR, and contribution handling still occur. The final shared bytes cannot be determined from the initial shared bytes alone.

4. **Conditional zero-valued fold-back.** For zero count, suppose the unmapped dependency actually copies the initial 20 shared bytes into the working region. If subsequent operations preserve those working bytes, the final selected destination contains the same respective bytes when consumed, and aliasing does not disturb later operands, each final XOR writes zero. These are additional assumptions, not established dependency behavior.

5. **Negative count.** A negative count skips chunks but still participates in position arithmetic and the F-870c4fcf7295 invocation with 20. Rejection and no-op behavior are not established.

6. **Pool crossing.** With cursor 1020 and chunk size 5, ordinary arithmetic produces a split quantity of 2. The explicit pool submission has length 3; the following two-argument submission uses the global pool base selected after that call. Its consumed length remains unknown. With wrap bound 1023, direct writes target positions 1020, 1021, 1022, 0, and 1.

7. **Contribution threshold.** With offset 8 equal to 31 and contribution 5, the explicit update writes 36, absent intervening mutation. With offset 8 equal to 32, even a negative contribution is not applied.

8. **Position threshold.** Captured position 1000 and count 23 produce 1023 and select the arithmetic-dependency branch. The final offset-4 value depends on its secondary result.
