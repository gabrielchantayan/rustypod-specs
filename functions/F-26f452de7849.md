# F-26f452de7849

## Purpose

F-26f452de7849 conditionally copies 32-bit values from two fixed-length record tables into locations obtained through destination-specific dependencies.

A shared byte controls entry. An invocation that observes a nonzero byte returns immediately. An invocation that observes zero writes 1 to that byte before invoking setup or examining either destination.

The first table contains 3,920 records; the second contains 22. Each phase runs only when a 32-bit field at byte offset 20 of its initially examined destination is zero. Admission applies to the entire phase, not separately to each destination subsequently used: every iteration reloads the phase’s destination reference, and a dependency can redirect that reference without triggering another admission check.

One-time initialization of associative structures is **inferred intent**, not an established type or ownership contract. The established behavior is the gating, ordered reads and calls, reference reloads, and 32-bit stores described below.

## Interface

### Arguments and result

The function accepts four 32-bit arguments and has no specified return value.

| Argument | Established use |
|---|---|
| 1 | No direct use in the supplied body |
| 2 | No direct use in the supplied body |
| 3 | Copied into a local 32-bit work word after setup returns |
| 4 | Copied into the first word of local auxiliary storage after setup returns |

Arguments 1 and 2 are not explicitly forwarded to dependencies.

The work word is passed by address to the preparation, destination, and post-store dependencies. Auxiliary storage is passed by address only to the preparation dependency. Its visible layout is two consecutive 32-bit words, totaling eight bytes. Only its first word is explicitly initialized by this function; the second has no established initial value.

These storage layouts do not establish the representation of an object, key, allocator, or ownership token.

### External state and layouts

The function accesses:

- A reference to the entry-gate byte.
- A first-table base designation.
- A second-table base designation.
- A mutable first-destination reference.
- A mutable second-destination reference.

Each destination admission check reads a 32-bit field at byte offset 20 from the destination reference loaded for that check. The semantic meaning of this field is unknown.

Each table uses eight-byte records:

| Record-relative offset | Width | Established use |
|---|---:|---|
| 0 | 32 bits | Passed by value to F-9b9c1c7483f4 |
| 4 | 32 bits | Captured after preparation and later written through a destination-dependency result |

No independent byte order is established. Interpretation follows the execution environment.

### Preconditions for normal completion

For every operation actually reached, successful execution requires:

- A readable gate byte, and permission to write it on the active path.
- A valid destination reference and readable offset-20 field for each admission check.
- Accessible table fields for every processed record.
- Destination references acceptable to their respective dependencies on every iteration, including references changed after phase admission.
- A returned address valid for the immediate 32-bit store.
- Valid storage, arguments, and execution conditions for all dependency calls.
- Address arithmetic that reaches the intended accessible storage without invalid overflow or wrapping.

The function does not enforce these conditions. In particular, it does not validate a reloaded destination reference or check the returned store address before using it.

A nonzero entry gate avoids the body’s destination, table, and dependency operations.

## Behavior

### Entry gate and setup

The function first reads the gate byte.

If the byte is nonzero, it returns without directly writing the gate, calling dependencies, checking destination fields, or reading table records.

If the byte is zero, the following order is established:

1. Write the byte value 1 to the gate.
2. Call F-3fb30196f4e0 without explicit arguments.
3. Capture the first table base.
4. Initialize the work word from argument 3.
5. Initialize the first auxiliary word from argument 4.
6. Begin the first destination admission check.

The gate write precedes setup. It is therefore not evidence that setup or population has completed. The body contains no compensating gate reset if later execution fails.

No atomic test-and-set, lock, or other synchronization mechanism is established.

### First-phase admission

After setup and local initialization, the function loads the first-destination reference and reads the 32-bit field at byte offset 20 of the referenced destination.

- A nonzero field skips the first phase.
- A zero field admits processing of all 3,920 first-table records, assuming continued normal execution.

The admitted records are visited in ascending index order, from 0 through 3,919.

The destination reference used for this admission check is **not cached as the destination for the loop**. Each iteration obtains a fresh first-destination reference later in its processing sequence.

The admission field is not rechecked during the phase. A change to the field, or redirection of the destination reference, does not itself shorten the loop.

### Second-phase admission

After the first phase completes or is skipped, the function:

1. Captures the second table base.
2. Loads the second-destination reference.
3. Reads that destination’s 32-bit field at byte offset 20.

A nonzero field skips the second phase. A zero field admits all 22 second-table records, visited in ascending index order from 0 through 21.

As in the first phase, the reference used for admission is not retained as the loop’s destination reference. Each second-phase iteration reloads the second-destination reference.

The second admission decision is made after all first-phase activity. First-phase dependency effects can therefore change the second table base, the second-destination reference, or its admission field before those values are obtained.

### Per-record ordering

Both phases use the following observable sequence. The first phase uses F-71ccb26f9d97 as its destination dependency; the second uses F-2e3a666c8de6.

1. Read the current record’s first 32-bit field from the phase’s captured table base.
2. Call F-9b9c1c7483f4 with the work-word address, that field’s value, and the auxiliary-storage address.
3. After preparation returns, read the current record’s second 32-bit field and retain its value.
4. Reload the phase-specific destination reference.
5. Call the phase-specific destination dependency with that reloaded reference and the work-word address.
6. Store the retained second-field value as one 32-bit value through the returned address.
7. Call F-8a5aadac202f with the work-word address.
8. Advance to the next record.

The destination-reference reload occurs **after both preparation and the second-field read**. It does not reuse the reference obtained for admission or for a preceding iteration.

Consequences include:

- F-9b9c1c7483f4 can redirect the current iteration by changing the applicable destination reference before returning.
- The newly selected destination’s offset-20 field is not checked before its destination dependency is called.
- A destination dependency or F-8a5aadac202f can change the destination reference used by later iterations.
- Changing a destination reference during the destination dependency does not change the reference already supplied to that call.
- Changing the current record’s second field during preparation can affect the subsequently captured value.
- Changing that field during the destination dependency does not replace the value already retained for the pending store.
- The store occurs before F-8a5aadac202f.
- F-8a5aadac202f must return before the next record’s first-field read is reached.

The function performs no explicit success check between these operations.

### Persistent local storage

The work word and first auxiliary word are initialized once per admitted invocation, not once per record or once per phase.

Dependencies may modify storage passed by address. The body does not restore argument 3 or argument 4 before later iterations or before the second phase. Thus, later calls receive the storage state left by earlier calls.

The second auxiliary word is not explicitly initialized at any point in the body. Whether a dependency reads or writes it, and whether an initial value is required, remain unresolved.

### Widths and bounds

The loop index is a 32-bit unsigned quantity. It starts at zero and advances by one after each completed record sequence.

| Property | First phase | Second phase |
|---|---:|---:|
| Record count | 3,920 | 22 |
| Last index | 3,919 | 21 |
| Last record-start offset | 31,352 bytes | 168 bytes |
| Last second-field offset | 31,356 bytes | 172 bytes |
| Complete contiguous record span | 31,360 bytes | 176 bytes |

The first bound is 3,920, not 3,919; the latter is the last processed index. Both loops are entered only after a successful zero admission test, and both have nonzero fixed counts.

The maximum record-offset calculation is 31,356 bytes, well within a 32-bit unsigned range. This does not prove that adding an offset to an arbitrary base produces a valid address. The supplied representation uses a 32-bit table-base intermediate; platform address interpretation and base-plus-offset validity remain execution preconditions.

Admission distinguishes only a zero 32-bit field from a nonzero field. It does not otherwise interpret signedness, count, capacity, or status.

## Side effects

### Direct effects

On an invocation admitted by the gate, the body directly:

- Writes 1 to the gate byte.
- Initializes the work word and the first auxiliary word.
- Captures each table base at its specified phase boundary.
- Loads destination references for admission and again for every processed record.
- Reads the admission fields and table fields.
- Performs one 32-bit store through each completed destination-dependency result.

If both phases complete, there are 3,942 destination stores. These need not target distinct addresses, objects, or even the same destination throughout a phase.

### Captured bases versus reloaded destinations

Each table base is captured once for its phase. Changes to the external table-base designation after capture do not redirect later records in that phase. Changes to the contents of the captured table can still affect later reads.

Destination references behave differently: they are reloaded for every iteration after preparation and after the second-field read. Their values are not frozen by phase admission.

This distinction remains relevant even when all dependency calls return normally.

### Dependency effects, ownership, and lifetime

No dependency is established to preserve globals, table contents, destination references, the gate, or local storage supplied by address.

The local storage lasts for the invocation. The body does not establish whether dependencies retain its addresses, nor any lifetime guarantee that would make later use of retained addresses safe.

F-8a5aadac202f is called after each completed store, but cleanup or deallocation is only inferred intent. The destination dependencies might retrieve, create, or otherwise provide storage; their implementations and ownership rules are unknown.

The caller performs no separate release of the returned destination addresses and no explicit rollback of completed stores.

### Failure and interruption

There is no explicit error result, recovery branch, or null-result check in the supplied body.

If a dependency does not return, later operations are not reached. If an access faults or a dependency transfers control abnormally, completion and recovery semantics are not established here.

The direct gate write has already occurred before any dependency call. The body does not undo it after failure, although dependencies or other actors may independently change the gate.

## Acceptance examples

The following are conditional predictions from static evidence. No runtime tests have been performed.

### Nonzero gate

Given any nonzero gate byte, the invocation returns without a setup call, destination admission check, table-record read, or direct destination store.

### Both phases skipped

Given a zero gate, normally returning setup, and nonzero admission fields at their respective examination times:

- The gate is written to 1 before setup.
- Setup runs once.
- Neither phase performs record processing.
- No preparation, destination, or post-store dependency is called.

### First phase only

Given a zero gate, a zero first admission field, and a nonzero second admission field at its later examination, normal execution processes first-table records 0 through 3,919 and no second-table records.

### Both phases complete

Given zero admission fields at their respective checks and valid, normally completing operations, all 3,920 first-table sequences precede all 22 second-table sequences.

Preparation and post-store dependencies each run 3,942 times. F-71ccb26f9d97 runs 3,920 times; F-2e3a666c8de6 runs 22 times.

### Preparation redirects the current destination

Suppose a phase is admitted using destination A. During preparation for one record, F-9b9c1c7483f4 changes that phase’s destination reference to destination B.

After preparation returns, the function reads the record’s second field, reloads the destination reference, and calls the applicable destination dependency with B. This occurs even if B’s offset-20 field is nonzero. B receives no new admission check.

### A destination change affects the next iteration

Suppose the destination dependency receives A, then changes the external destination reference to B while returning a valid store address.

The current store uses the returned address. On the next iteration, B is used if the reference remains B through preparation and the subsequent second-field read. The phase continues without another admission-field check.

### Admission changes do not stop an admitted phase

If the checked admission field becomes nonzero during the first iteration, the remaining records are still processed, provided execution continues normally. The loop does not recheck that field.

### Mutation between phases

If first-phase processing changes the second-destination reference, the second admission check uses the then-current reference. If its offset-20 field is nonzero, the second phase is skipped.

### Current-record value changes

If preparation changes the current record’s second field, the following read can observe the changed value. If the destination dependency changes that field afterward, the pending store still uses the previously retained value.

### Re-entry or incomplete setup

If a dependency re-enters this function while the gate remains 1, the nested invocation returns immediately.

If setup does not return, no table population is reached and this body performs no compensating gate reset.

## Uncertainties

The following remain **documented_only**:

- Semantic types and names of the gate, tables, destinations, and admission fields.
- Complete contracts for all dependencies.
- Required representation, initialization, and extent of storage accessed through the work-word address.
- Whether dependencies access the second auxiliary word or require it to be initialized.
- Allocation, ownership transfer, destruction, and address-retention behavior.
- Duplicate-record behavior and whether destination results alias.
- Aliasing among table storage, destinations, reference storage, the gate, and other externally accessible memory.
- Platform byte order, alignment constraints, address representation, and fault handling.
- Concurrency safety and memory visibility.
- Exceptional control flow and state after interrupted execution.

No unresolved dependency behavior is assumed to preserve globals or release memory. Uncertainty about these matters does not weaken the established destination-reference reload ordering.

## Evidence

The supplied static body establishes the gate access, four 32-bit arguments, setup order, local storage layout, phase-specific base captures, zero-tested 32-bit fields at offset 20, eight-byte record stride, fixed loop bounds, dependency calls, and immediate 32-bit stores.

It also establishes separate destination-reference reads for admission and for every record. Each per-record reload follows preparation and the second-field read; there is no intervening admission check for the reloaded destination.

The record spans and total of 3,942 sequences are arithmetic consequences of the fixed widths and bounds.

One-time initialization, associative-container operations, and temporary cleanup are inferred intent only. No dependency implementations or runtime observations establish those interpretations. No runtime tests have been performed.
