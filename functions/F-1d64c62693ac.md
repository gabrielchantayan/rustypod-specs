# F-1d64c62693ac

## Purpose

F-1d64c62693ac dispatches an object and a record through an ordered set of conditional calls. It returns a 32-bit status determined by the first status-producing callback that returns nonzero, or zero when processing completes without such a result.

The dispatch contract has four roles: preliminary notification, interception, main processing, and final processing. Preliminary notification does not contribute to the returned status. Interception can prevent main processing. Main processing can prevent final processing.

The record is not treated as an immutable description of the entire operation. Decisions made after a dependency returns use newly read state. A dependency can therefore change later routing by modifying the record, nested data, or the object’s dispatch-table address.

“Notification,” “interception,” and “processing” describe observable roles, not established application semantics. In particular, a nonzero result is not known to mean success, failure, or acceptance.

## Interface

### Arguments and result

The function accepts:

- **An object address**, used to obtain dispatch targets and two additional state values.
- **A record address**, used to obtain a discriminator and a field whose interpretation depends on that discriminator.

Every indirect callback receives these two original addresses, in that order. Changes to the contents of either object do not change the address arguments supplied to subsequent callbacks.

The direct dependency F-4fd087f2325e receives the original object address and a character-converted object-state value. It does not receive the record address as an explicit argument.

The return value is a represented 32-bit integer. Nonzero callback results are propagated without Boolean normalization or other visible transformation. Zero is returned if all reached status-producing callbacks return zero.

### Validity requirements

Every reached memory access must be valid when it occurs. In particular:

- A reached discriminator read requires readable record storage at offset `0x04`.
- A discriminator of `0x16` requires a readable address-valued field at record offset `0x08` and a readable subtype at offset `0x04` of the addressed storage.
- A selected callback requires a readable current dispatch-table address, a readable selected slot, and a compatible callable target.
- Dependencies that return normally must leave any storage needed by later processing valid if that processing is reached.

There are no explicit null, bounds, alignment, or callback-validity checks. This contract does not assign a controlled error result to invalid memory or incompatible call targets.

## Behavior

### Routing and completion rules

The following table defines the routing conditions. Each condition concerns state read for that particular role, not necessarily the state present at entry.

| Role | Eligibility | Effect on continuation |
|---|---|---|
| Preliminary notification | Discriminator `0x16` and subtype satisfying the arithmetic condition described below. | Calls F-4fd087f2325e; no result is consumed. |
| Interception | Discriminator `0x16` and subtype zero. | A nonzero callback result completes the function immediately; zero permits main processing. |
| Main processing | Always reached unless interception has already returned nonzero. | Exactly one main callback runs. A nonzero result completes the function immediately; zero permits evaluation of final processing. |
| Final processing | After a zero main result, discriminator `0x0F` and equal record/object comparison operands. | Calls the final callback and completes with its result. If ineligible, completes with zero. |

Roles occur only in the order shown. Normal execution can make between one and four dependency calls: one main callback is mandatory unless a nonzero interception result ends processing first. No path reaches final processing without a completed main call returning zero.

### Preliminary notification condition

The preliminary decision reads the record discriminator. If it equals `0x16`, the decision also reads the nested-data address and subtype.

The represented arithmetic subtracts `0x2500` from the subtype and compares the result with `2`. The matching subtype is `0x2502` under ordinary nonoverflowing 32-bit evaluation, and also under 32-bit modular evaluation. The matching case itself does not require overflow. The supplied evidence does not settle arithmetic-overflow treatment for other subtype values.

When notification is selected, the integer at object offset `0x104` is loaded and converted to the represented character type before being passed to F-4fd087f2325e. This is an integer load followed by conversion, not evidence of a direct byte read from that offset. Character width, signedness, and argument-extension rules are unresolved.

No returned value from F-4fd087f2325e affects routing or status directly. Its mutations can still affect all subsequent decisions.

### Interception and main selection

Interception uses a fresh discriminator read after preliminary notification, including when notification was not selected. Its nested-data address and subtype are read only if this discriminator is `0x16`.

A zero subtype selects interception. If interception returns zero, main selection does not reuse that subtype: it reads the discriminator again and, when appropriate, the current nested-data address and subtype.

Main selection uses slot `0x10C` precisely when its discriminator is `0x16` and its subtype is `0x2A`. All other main-selection conditions use slot `0x110`. A main-selection discriminator other than `0x16` causes no nested-data read.

For each selected indirect call, the target comes from the object’s dispatch table as read for that call. There is no single dispatch-table snapshot retained for the whole operation.

### Final eligibility and status

Final eligibility is evaluated only after a main callback returns zero. It begins with another discriminator read.

For discriminator values other than `0x0F`, final processing is ineligible. In that case, this decision does not read either the record comparison operand or the object comparison operand.

For discriminator `0x0F`, the record value at offset `0x08` is read before the object value at offset `0x50`. Equality selects the final callback; inequality completes with zero. The record value is compared directly and is not dereferenced as an address for this decision.

If selected, the final callback receives the original object and record addresses. Its nonzero result is returned unchanged; its zero result leads to zero. There is no later dispatch or visible cleanup.

### Observable read ordering

The established read dependencies are:

- Each routing decision reads its discriminator before any discriminator-dependent record or nested-data read.
- A nested-data decision reads the address from the record before reading the subtype through that address.
- Notification reads the object-state value only after its discriminator and subtype condition matches.
- An indirect call obtains the current object dispatch-table address and selected table entry after its routing condition is established.
- Final equality reads the record operand before the object operand.
- A nonzero interception or main result prevents all reads belonging to later roles.

Dependencies separate the routing decisions. No assumption of state preservation bridges those calls. For example, notification may enable interception; interception returning zero may select the special main slot; a main callback returning zero may enable final processing.

These are access-order properties of the supplied static representation. They do not establish synchronization or hardware memory-order guarantees.

## Side effects

The function body has no explicit memory writes, allocation, release, or ownership-transfer operation. Its direct effects are memory reads, dependency calls, and selection of a returned status.

The absence of direct writes does not imply purity. A dependency may modify the object, record, nested data, dispatch tables, unrelated memory, or global state. The caller cannot infer preservation from a zero result.

No dependency ownership contract is available:

- Passing an address does not establish ownership transfer.
- Returning normally does not establish that referenced storage remains alive.
- Returning nonzero does not imply rollback.
- The function performs no visible compensating action after a call.

If a dependency invalidates storage required by a later reached read, the function provides no demonstrated protection. An immediate nonzero result avoids later reads but does not establish that any earlier side effects are reversed.

No atomicity, locking, concurrent-update safety, or volatile-memory semantics are established.
