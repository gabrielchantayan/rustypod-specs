# F-86a7d82434e3

## Purpose

F-86a7d82434e3 conditionally processes three pairs of 32-bit input values for one of two dimension selections. It obtains one result from each pair, searches a collection of fixed-stride records for a record matching any of those results, obtains a record if no match is found, and applies the three results to the selected record.

A nonzero status already present in the context prevents all further work. On an active invocation, a failure reported by a dependency stops the operation and is written into that status field after an error-reporting call. The function has no explicit return value.

The apparent intent is to register a related group of three items in a dimension-specific collection. That interpretation is inferred from the operation’s structure; the established contract is the sequence of reads, dependency calls, branching, and status writes below. The meanings of the pair values, generated results, and collection records are not established.

## Interface

### Inputs and result

The function receives three arguments:

1. **Context reference.** A reference to a memory object containing 32-bit fields, an inspected byte, and dimension-dependent subobjects.
2. **Dimension selector.** An unsigned 32-bit value.
3. **Input reference.** A reference to three consecutive pairs of 32-bit words, requiring 24 readable bytes if all three pairs are processed.

The function returns no explicit result. Observable outcomes are dependency calls, any changes those dependencies make, and the function’s own conditional write to the context status field.

### Established context locations

Offsets are byte offsets from the beginning of the context. Each listed word occupies four bytes.

| Offset | Established use |
|---|---|
| 0 | A 32-bit value captured once and passed to several dependencies. Its type and ownership meaning are unknown. |
| 4 | A 32-bit status field. Zero permits processing; nonzero causes immediate return. |
| 12 | A single byte tested for equality with 1. Other bytes at this location are not part of that test. |
| 16 + 36 × dimension | Address passed to F-062e6c77d9d0 while processing each pair. |
| 40 + 36 × dimension | A 32-bit collection count, and the starting address of a subobject passed to F-5e2345d8f7b1. |
| 48 + 36 × dimension | A 32-bit value used as the initial candidate-record address. |

After dimension normalization, the dimension is either 0 or 1. The corresponding address arguments are therefore:

| Dimension | Pair-processing address | Collection-subobject address | Candidate-address field |
|---|---:|---:|---:|
| 0 | 16 | 40 | 48 |
| 1 | 52 | 76 | 84 |

These locations do not establish complete structure boundaries or prove that the named regions are independent objects.

### Preconditions and validity requirements

The context must permit the initial 32-bit read at offset 4. If that value is nonzero, this function does not itself inspect the remaining context or dereference the input reference.

For active processing, all subsequently accessed context locations must be readable. If an error is recorded, offset 4 must also be writable. The input reference must permit reading each pair actually reached.

Dependencies impose additional, undocumented validity requirements on the addresses and values supplied to them. In particular, this function does not validate the candidate address, collection size, or dependency output values.

The function has three temporary 32-bit result slots and a temporary 32-bit candidate-address slot. A successful pair-processing call is expected to produce the result used later from its designated slot. This output behavior is a dependency precondition, not something this function independently verifies.

## Behavior

### 1. Existing-status gate

The first established operation is a read of the 32-bit status at context offset 4.

- If the status is nonzero, the function returns immediately.
- It does not normalize the dimension, inspect the mode byte, read input pairs, or call any dependency on that path.
- It does not clear or replace the existing status.

If the status is zero, the function captures the 32-bit value at context offset 0. Later calls that receive this captured value use that saved value; the function does not refresh it from the context.

### 2. Dimension normalization

The dimension comparison is unsigned.

- Values 0 and 1 are accepted unchanged.
- Every value greater than 1 causes a call to F-4457a9a44a68 with a dimension-related diagnostic argument.
- After that call returns normally, the dimension used by the remaining operation is 1.

An invalid dimension does not by itself set an error status or terminate processing. It selects the second dimension after reporting the diagnostic.

The saved context value is captured before this diagnostic call. The mode byte and dimension-dependent collection fields are read afterward. Consequently, changes made during the diagnostic call can affect later reads, but cannot change the already captured value.

### 3. Mode gate

The function reads the single byte at context offset 12 and compares it with exactly 1.

If it is not 1:

1. F-4457a9a44a68 is called with a mode-related diagnostic argument whose content is not supplied.
2. The function selects error value 6.
3. It follows the common failure-reporting path.

No input pair is processed on this path. No other byte value is accepted as an alternative enabled mode.

### 4. Processing the three input pairs

When the mode byte equals 1, the function makes up to three ordered calls to F-062e6c77d9d0.

Each call receives:

- The dimension-selected address at context offset 16 + 36 × dimension.
- The first word of the current pair.
- The second word of that pair.
- The saved 32-bit context value.
- The address of the corresponding temporary result slot.

Pairs are taken in input order: bytes 0–7, then 8–15, then 16–23. Both words of a pair are supplied by value. The exact evaluation order of the two word reads within a call is not established by the supplied material.

A return value of zero permits the next stage. A nonzero return value stops pair processing immediately and becomes the error selected for the common failure path.

Thus:

- Failure on the first pair prevents processing of the second and third.
- Failure on the second prevents processing of the third.
- Collection search begins only after all three calls return zero.

No rollback is visible. Effects of earlier successful calls, or partial effects of the failing call, are not reversed by this function.

### 5. Searching candidate records

After all three pair-processing calls succeed, the function reads the initial candidate address from context offset 48 + 36 × dimension. It then reads the collection count from offset 40 + 36 × dimension.

These collection reads occur after pair processing. If a dependency changed those fields, the search uses their later values.

For each candidate, the function calls F-cc8b1f257eed against the three temporary results in order:

1. Candidate and first result.
2. Candidate and second result, only if the first comparison returned zero.
3. Candidate and third result, only if the preceding comparisons both returned zero.

Any nonzero comparison result selects the current candidate immediately. Such a result is a **match indication**, not an error to be written to the context.

If all three comparisons return zero, the candidate address advances by 16 bytes, and the remaining count decreases by one. The next iteration uses the advanced address without rereading the context’s candidate-address field.

For an ordinary nonnegative count:

- Zero skips comparisons entirely.
- A positive count allows at most that many candidates.
- A match stops the search at the first matching candidate.
- If every candidate fails to match, the temporary candidate address ends one 16-byte stride beyond the final candidate.

The search count and advancing candidate address are local values. Changes that dependencies make to the corresponding context fields do not automatically refresh those local values.

### 6. Obtaining a record when the search finds none

If the search does not select an existing candidate, the function calls F-5e2345d8f7b1 with:

- The address at context offset 40 + 36 × dimension.
- The saved 32-bit context value.
- The address of the temporary candidate-address slot.

A zero return permits the application stage to use the candidate-address slot’s value after the call. A nonzero return skips application and becomes the selected error.

The dependency may therefore replace the temporary candidate address. Allocation, collection insertion, and ownership transfer are plausible purposes, but are not established by this caller alone.

A successful search bypasses F-5e2345d8f7b1 entirely.

### 7. Applying results to the selected record

Once a candidate has been selected or obtained, F-277c3b9f6f6a is invoked in result order.

The first invocation receives the candidate address, first result, and saved context value. If it returns zero, the second invocation receives the candidate address, second result, and saved context value.

Only if both return zero is the third invocation reached. The supplied representation explicitly shows only the candidate address and third result for that call. Whether a third argument exists in the actual calling convention, and what it would contain, is not established. The contract does not assume the third invocation receives the saved context value.

A nonzero result from any reached invocation stops further application and becomes the selected error. If the final reached invocation returns zero, the function returns normally without an explicit status write.

There is no visible removal, rollback, or compensation for an earlier successful application.

### 8. Common failure reporting

All selected errors converge on one sequence:

1. Call F-4457a9a44a68 with an operation-failure diagnostic argument.
2. After that call returns normally, write the selected 32-bit error value to context offset 4.
3. Return.

The error is either:

- 6 for an unsupported mode byte; or
- A nonzero return from F-062e6c77d9d0, F-5e2345d8f7b1, or F-277c3b9f6f6a.

The diagnostic precedes the status write. A diagnostic observer must not assume this function has already stored the selected error when that reporting call begins.

The function does not recheck the status field after any dependency call. A dependency’s modification of that field therefore does not independently stop processing. On a failure path, the final explicit store replaces whatever value is present there at that time.

## Side effects

The only direct write to caller-visible context memory established in the supplied body is the failure-path write at offset 4.

Other observable effects occur through dependencies:

- Diagnostic reporting.
- Processing of input pairs against a dimension-selected subobject.
- Candidate comparisons.
- Possible acquisition or modification of a collection record.
- Ordered application of up to three generated results.

No direct write through the input reference is shown. This does not prove input immutability if it aliases the context or storage accessible to a dependency.

Successful completion does not explicitly clear the status. Although active processing starts with a zero status, the final status cannot be guaranteed to remain zero without contracts establishing that the intervening dependencies preserve it.

No explicit release operation is shown for generated results or candidate records. Ownership, cleanup responsibility, and lifetime rules remain undocumented. Neither successful return nor failure return proves that dependency-created resources have been released.

There is no visible synchronization, exception handler, or recovery path for invalid memory access. All normal-return sequences described here are conditional on the invoked dependencies returning normally and required memory remaining valid.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence, not executed tests.

1. **Preexisting error:** With status 9, the function returns without dependency calls and without reading input pairs. An otherwise invalid dimension has no effect on this path.

2. **Unsigned out-of-range dimension:** With status zero and dimension 4,294,967,295, the dimension diagnostic occurs. Subsequent dimension-dependent addresses use dimension 1, provided the diagnostic returns normally.

3. **Unsupported mode:** With status zero and mode byte 2, the mode diagnostic occurs, followed by the operation-failure diagnostic, followed by a status write of 6. No pair-processing call occurs.

4. **Second pair failure:** If the first pair-processing call returns zero and the second returns a nonzero value E, the third pair is not processed. No candidate comparisons or application calls occur. After failure reporting, status is E.

5. **First candidate matches the second result:** The first comparison returns zero and the second returns nonzero. The third comparison is skipped, no later candidate is inspected, and F-5e2345d8f7b1 is skipped.

6. **Empty collection:** With count zero, no comparison occurs. F-5e2345d8f7b1 receives the candidate-address slot initialized from the context field. If it returns zero, application uses that slot’s resulting value.

7. **Two candidates, no matches:** With count two and all six comparisons returning zero, candidate addresses are examined at the initial address and initial address plus 16. The obtain-record call follows with the temporary address advanced by 32 bytes.

8. **Application stops midway:** If the first application returns zero and the second returns E, the third is skipped. Failure reporting precedes the status write. No rollback of the first application is visible.

9. **All application calls succeed:** If every required prior stage succeeds and all three application calls return zero, the function returns without its own status write. A zero final status additionally requires that dependencies have not changed it.

## Uncertainties

The following remain **documented_only**:

- Semantic types, units, signedness, and permitted ranges of the input-pair values and generated results.
- The meaning of the saved context word and whether it denotes a resource-management object.
- Full context and record layouts, alignment requirements, and byte order.
- The actual signature and calling-convention behavior of the third F-277c3b9f6f6a invocation.
- Dependency effects on globals, context memory, aliased input memory, ownership, and resource lifetime.
- Exact diagnostic contents and whether reporting may terminate or otherwise fail to return.
- Safe behavior for malformed collection counts or invalid candidate addresses.

The search count is represented as a signed 32-bit quantity, but termination tests it for zero rather than positivity. A negative value is not rejected or treated as an empty collection. Such a value enters the loop. Repeated decrement can reach signed overflow, and candidate advancement can exceed valid address space. No safe traversal or termination guarantee is established for malformed counts or address arithmetic overflow.

For dimensions 0 and 1, the stated dimension-dependent offsets are small and do not overflow 32-bit offset arithmetic. This does not establish that adding them to a supplied context address is valid.
