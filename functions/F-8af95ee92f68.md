# F-8af95ee92f68

## Purpose

F-8af95ee92f68 performs a gated, two-stage query. Each stage obtains a value from a dependency, prepares an eight-byte temporary context, and attempts to extract a four-byte value from that context. A successful extraction permits a query using a stage-specific selector.

The first stage is a gate: its extraction and its query with selector `0x1180` must both report nonzero before the second stage begins. The second stage obtains its input independently, extracts a value, and queries it with selector `0x1700`. The four-byte result of that final query becomes the function’s result.

All other normal return paths produce zero. Context cleanup occurs before every normal return, in reverse preparation order when both contexts have been prepared.

This describes the established call structure, not the application meaning of the values or selectors. Interpreting the function as a capability check, state check, or property lookup would require additional evidence.

## Interface

**Explicit inputs:** None.

**Output:** One four-byte result.

- Zero is returned when an extraction reports zero or the first-stage query reports zero.
- If the final query is reached, its complete four-byte result is returned unchanged.
- The final result is not normalized to a Boolean. A nonzero result other than one remains distinguishable from one.

**Implicit inputs:** State accessed by the dependencies. The function invokes the value-supplying dependency separately for each stage; it does not explicitly pass the first supplied value into the second stage.

**Temporary storage:**

| Storage | Extent | Observable use |
|---|---:|---|
| First context | 8 bytes | Passed to preparation, extraction, and cleanup dependencies. |
| Second context | 8 bytes | Used only after the first-stage gate succeeds; passed to the same three dependencies. |
| Shared extraction output | 4 bytes | Its address is supplied to both extraction attempts. Its value is read for a query only after the corresponding extraction reports nonzero. |

The storage regions are distinct. Their internal layouts, alignment requirements, and semantic types are not established by the supplied evidence.

The function does not explicitly initialize the shared extraction output before either extraction. Successful extraction therefore needs to establish a usable output value for the intended behavior. Whether that guarantee actually belongs to the extraction dependency is unknown.

All descriptions of completed calls and returns below assume the dependencies return normally.

## Behavior

### First-stage acquisition and extraction

The function first calls F-583dc5fa4d66 with no explicit arguments. It passes the resulting four-byte value, together with the address of the first context, to F-8ca21d3a8cca.

After that preparation call returns, the function calls F-b38a3aba0e18 with:

- The address of the first context.
- The address of the shared four-byte extraction output.

The extraction result is tested for zero.

If it is zero, no selector query occurs. The function calls F-d0d3f100effc on the first context and returns zero.

If it is nonzero, the function reads the shared extraction output and passes that value to F-682adfd5a561 with selector `0x1180`, decimal 4480.

### First-stage gate

The result of the `0x1180` query is tested for zero.

If it is zero, the second stage is skipped. The first context is cleaned up through F-d0d3f100effc, and the function returns zero.

Any nonzero result opens the gate. The particular nonzero value is not forwarded to the second stage or returned directly.

The extraction status and gate-query status are used solely as zero-versus-nonzero conditions. No ordering comparison, magnitude test, or special treatment of a high-bit-set result is established.

### Second-stage acquisition and extraction

After the gate succeeds, the function calls F-583dc5fa4d66 again. It supplies this second result to F-8ca21d3a8cca together with the address of the second context.

This is a fresh dependency invocation, not reuse of the first acquisition result. The two acquisition results may be equal or different. The function itself imposes no equality requirement.

The first context has not yet been cleaned up when the second context is prepared.

The function next calls F-b38a3aba0e18 with the second context and the same shared extraction-output address used in the first stage.

If this extraction reports zero:

1. No `0x1700` query occurs.
2. The second context is cleaned up.
3. The first context is cleaned up.
4. The function returns zero.

Any output write performed by a failed extraction is not consumed by a selector query on this path.

### Final query and result

If the second extraction reports nonzero, the function reads the shared extraction output and calls F-682adfd5a561 with that value and selector `0x1700`, decimal 5888.

The function then retains the query’s four-byte result while calling cleanup on the second context, followed by cleanup on the first context. It returns the retained result.

There is no branch on the final query result. Zero and nonzero final-query results both receive the same cleanup sequence.

### Widths and arithmetic

The supplied representation establishes four-byte acquired values, extraction output, query result, and function result. Extraction and first-query statuses are tested at the represented four-byte width.

Both selectors are positive constants that fit within 16 bits and within a 32-bit argument. The wrapper performs no arithmetic on them, so there is no selector overflow, truncation, increment, or offset calculation to specify.

The function performs no explicit arithmetic on extracted values. Whether a four-byte value denotes an address, handle, identifier, or numeric quantity remains unknown.

## Side effects

The wrapper’s explicit storage interaction consists of passing addresses of its temporary regions to dependencies and subsequently reading extraction output after a nonzero extraction status. The contents written by the dependencies are not visible in the supplied evidence.

The first context receives one preparation call and one cleanup call on every normal path. The second receives one preparation call and one cleanup call only if the first-stage gate succeeds.

When both contexts exist, cleanup is ordered:

1. Second context.
2. First context.

This order is observable to the dependencies. The first context remains uncleaned throughout the second acquisition, second preparation, second extraction, and any final query.

On normal paths:

| Dependency operation | Number of calls |
|---|---:|
| Acquire value | One or two |
| Prepare context | One or two |
| Extract value | One or two |
| Selector query | Zero, one, or two |
| Clean up context | One or two |

A cleanup call is made even when extraction from that context reports failure. No preparation result is checked before extraction or cleanup.

**Ownership limits:** The function supplies temporary storage to its dependencies. This establishes an ordered usage interval, not a complete ownership contract. It does not establish whether preparation allocates resources, whether cleanup releases resources, whether extraction produces a borrowed value, or whether any dependency retains an address.

No explicit heap allocation, deallocation, external I/O, or global-state access appears in the wrapper. Dependencies may nevertheless perform such operations. In particular, there is no basis for assuming the first query preserves state observed by the second acquisition.

No local recovery from a dependency that fails to return normally is established. The normal-path cleanup guarantees must not be extended to exceptions, faults, process termination, or nonlocal control transfers without further evidence.

## Acceptance examples

These are conditional acceptance criteria derived from the supplied static evidence, not executed tests. They assume valid dependency interactions and normal returns.

### First extraction fails

Given a first extraction status of zero:

- Acquisition, first-context preparation, and first extraction occur.
- No selector query or second acquisition occurs.
- The first context is cleaned up once.
- The result is zero.

This holds regardless of whether the failed extraction changed the output storage.

### First query rejects the gate

Given a nonzero first extraction status and a zero result from the `0x1180` query:

- That query receives the output value present after the first extraction.
- No second context is prepared.
- The first context is cleaned up once.
- The result is zero.

### Second extraction fails

Given nonzero first extraction and gate-query results, followed by a zero second extraction status:

- Acquisition occurs twice.
- Both contexts are prepared.
- The `0x1180` query occurs, but the `0x1700` query does not.
- Cleanup occurs for the second context before the first.
- The result is zero.

### Final result is preserved

Given both successful extractions and a successful first-stage gate:

- If the final query returns zero, the function returns zero.
- If it returns one, the function returns one.
- If it returns the four-byte value `0x80000005`, the function returns that same four-byte value.

In each case, both cleanup calls occur before return. These examples distinguish raw-result propagation from Boolean normalization.

### Acquisitions produce different values

If the second acquisition supplies a different value from the first, the second preparation receives the second value. The function does not substitute the first value.

### Extraction output changes between stages

If successful extractions produce different output values, the `0x1180` query receives the first extracted value and the `0x1700` query receives the second. The shared output location does not imply equality between those values.
