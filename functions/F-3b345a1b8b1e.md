# F-3b345a1b8b1e

## Purpose

F-3b345a1b8b1e has an evidenced prefix consisting of two ordered memory stores:

1. Store the first argument into the location designated by the second argument.
2. Store the first argument’s low-order 16 bits into a location 52 bytes beyond the address represented by that same first argument.

The supplied representation then ends at an invalid-instruction boundary. It does not establish a normal return, subsequent execution, or a complete application-level purpose.

This contract describes that visible prefix, its prerequisites, and its limits. It does not treat the first argument as a verified object pointer or the second argument as a verified output buffer. Those interpretations would require evidence not supplied here.

## Interface

**Identifier:** F-3b345a1b8b1e.

**Arguments:**

- **Address-value argument:** An integer used both as data and as the basis for a memory address. Its full represented value supplies the first store. Its low-order portion supplies the second store.
- **Destination argument:** A pointer to storage receiving the address-value argument.

**Result:** The supplied representation declares no returned value. That declaration does not establish that execution returns normally; the visible control flow instead reaches an invalid-instruction boundary.

**Width model:** The representation uses an integer-sized first argument and first store, and a short-integer-sized second store. The operational descriptions and examples below use the conventional recovered model of a 32-bit first argument, a 32-bit first store, and a 16-bit second store. These widths are supported by the displayed types but are not independently verified against a target ABI or machine instructions. Pointer width is not established.

Under that model:

- The first store occupies four consecutive bytes.
- The second store occupies two consecutive bytes.
- The second store carries the low 16 bits of the address-value argument.
- The second destination is derived using a displacement of 52 bytes, not 52 integer elements.

**Prerequisites for completing both stores:**

- The destination argument must designate writable storage covering the first store’s full width.
- The address-value argument must produce a usable effective address after the 52-byte displacement.
- That effective address must designate writable storage covering the second store’s full width.
- Both destinations must satisfy any alignment and memory-access requirements imposed by the target environment.

No visible validation enforces these prerequisites. They are conditions for successful execution of the visible prefix, not advertised checks performed by the function.

There is no established non-aliasing requirement. The two destinations can coincide or overlap if the execution environment permits the corresponding accesses.

## Behavior

### First store

The first observable operation in the supplied representation writes the address-value argument into storage designated by the destination argument.

This is a direct write of the argument’s represented integer value. The function does not visibly read the destination’s previous contents, combine those contents with the argument, or dereference the address-value argument to obtain the value being stored.

Under the 32-bit model, all four bytes of the destination are replaced. Their byte order depends on the target’s endianness, which is not established.

### Second store

After the first store, the function writes a narrowed version of the address-value argument to the address obtained by adding 52 bytes to that argument’s address representation.

Under the 32-bit/16-bit model, the stored bit pattern is the argument’s low 16 bits. This is not a store of the displaced address’s low 16 bits. The displacement determines the destination only; it does not change the value selected for storage.

The second store does not visibly depend on the contents written by the first store. In particular, the visible representation does not reload the argument through the destination pointer before calculating the second destination.

The representation contains signed integer arithmetic for the displacement calculation. Its behavior at signed overflow, and the exact relationship between that expression and target address arithmetic, are not established. A portable contract must therefore not promise wraparound at the address-space boundary.

### Store ordering and overlap

The represented order is first store, then second store.

If the destination ranges overlap, the second store occurs later and can replace bytes written by the first store. There is no visible temporary output buffer, overlap check, or compensating rewrite.

For example, when the destination argument designates exactly the second store’s address, the first store writes four bytes there and the second store subsequently rewrites the first two addressed bytes with the narrowed value. The final byte pattern depends on endianness.

This ordering describes the visible execution sequence. It does not establish atomicity, inter-thread visibility, memory barriers, or suitability for memory-mapped devices. Another observer is not guaranteed to see either store as one indivisible event.

### End of established control flow

After the two stores, the supplied representation reaches a boundary identified as invalid instruction data.

The evidence does not establish that this boundary is an intentional trap in the original program. It could reflect an execution-time invalid instruction, an incomplete recovery, or another limitation of the supplied representation. No one explanation is selected as contractual behavior.

Accordingly:

- Normal return is not established.
- A particular exception or signal is not established.
- Execution of later instructions is not established.
- Rollback of either completed store is not established.
- Cleanup, recovery, and error reporting are not established.

The visible prefix is the supported behavioral unit. Completion of that prefix must not be described as successful completion of the whole function.

## Side effects

The established side effects are the two ordered stores, conditional on execution reaching and completing each access.

The function performs no visible reads of pre-existing destination contents. Address calculations and argument use do not themselves establish reads from memory addressed by the first argument.

No allocation, deallocation, ownership transfer, reference-count change, or resource acquisition is visible. The contract therefore requires accessible storage for the relevant accesses but does not assign ownership of that storage to the function.

The second destination is not established as a field within a valid object. The 52-byte displacement alone does not prove an object layout, a minimum allocation size, or the meaning of the stored value.

If an access fails, the evidence supplies no handled error result. In an environment where a failed access interrupts execution:

- Failure of the first store prevents the ordinary sequential path from reaching the second.
- Failure of the second store may leave the first store’s effect in place.
- Partial effects of a faulting store depend on the target’s memory semantics and are not established here.

There is no basis for claiming that globals, unrelated memory, or process state remain unchanged after the unresolved control-flow boundary.

## Acceptance examples

These examples are conditional predictions from the visible representation, not runtime observations. They assume 32-bit and 16-bit store widths, valid writable addresses, permitted alignment, and displacement arithmetic that does not encounter an unresolved boundary case.

### Distinct writable destinations

Given an address-value argument of `0x00123456` and a separate writable four-byte destination:

- The first destination receives the 32-bit pattern `0x00123456`.
- The second destination is address `0x0012348A`.
- That second destination receives the 16-bit pattern `0x3456`.
- The first store precedes the second.
- No normal-return expectation follows from these stores.

The second value is not `0x348A`; the displacement affects the address, not the stored argument value.

### Exact overlap on a little-endian target

Given an address-value argument of `0x00123456`, with the destination argument designating address `0x0012348A`:

- The first store produces addressed bytes `56 34 12 00`.
- The later second store writes bytes `56 34` over the first two addressed bytes.
- After both stores, the four addressed bytes are still `56 34 12 00`.

The unchanged final bytes do not mean the second write was absent.

### Exact overlap on a big-endian target

With the same argument values on a big-endian target:

- The first store produces addressed bytes `00 12 34 56`.
- The second store writes bytes `34 56` over the first two addressed bytes.
- After both stores, the four addressed bytes are `34 56 34 56`.

This difference is why a byte-level contract cannot select an endianness without further evidence.

### Invalid second destination

If the first destination is writable but the derived second destination is inaccessible, an environment that faults on the second write may expose the completed first write before interrupting execution. The visible representation provides no rollback.

### Unusable first destination

If the destination argument cannot support the first write, the function has no visible validation path that substitutes another destination or reports an ordinary error value. Whether the attempted write faults, and its exact effects, depend on the environment.

## Evidence

**Established static evidence:** The supplied representation contains an integer-valued argument, a pointer-valued argument, a store of the former through the latter, and a later short-width store at a 52-byte displacement from the former. The value selected for the second store is the narrowed original argument. The representation then stops at an invalid-instruction boundary.

**Conditional interpretation:** The numerical widths and byte examples use the conventional 32-bit integer and 16-bit short model. Target execution properties have not been independently established.

**Inferred intent:** No application-level purpose is sufficiently supported to make it contractual.

**Runtime evidence:** No runtime tests have been performed. The acceptance examples describe conditional outcomes, not observed executions.
