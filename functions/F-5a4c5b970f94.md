# F-5a4c5b970f94

## Purpose

F-5a4c5b970f94 attempts to obtain three bytes from a stream-like object, construct a big-endian numeric result, and advance the object's position by three.

It supports direct access through a stored base address and indirect access through an object-supplied callback. Locally detected failures produce a status write and two diagnostic calls. A zero return value alone does not distinguish failure from successful decoding of zero.

The conventional unsigned 24-bit interpretation is established when the first byte is below 128. For other first-byte values, character signedness and signed-shift behavior remain unresolved.

This contract describes static evidence only. Dependency behavior, object invariants, and actual execution outcomes are not established. No runtime tests have been performed.

## Interface

### Arguments and result

| Input | Role | Established representation |
|---|---|---|
| Stream object | Supplies the backing address, limit, position, and optional callback | Pointer to storage accessed through 32-bit fields |
| Status destination | Receives initial zero and, on local failure, decimal 85 | Pointer to a writable 32-bit word |
| Third argument | No ordinary-path use is visible; replaced on the null-stream assertion path | Opaque 32-bit value |
| Fourth argument | Initializes callback scratch storage | Opaque 32-bit value |

The result is an unsigned 32-bit quantity. Local failure returns zero if both diagnostic calls return normally.

The original status-destination argument remains the destination for status writes. On the null-stream path, the assertion's second argument instead comes from global storage; it is not established to equal the status destination.

### Relevant stream layout

| Byte offset | Width | Observed use |
|---|---|---|
| 0 | 32 bits | Base address used in direct mode |
| 4 | 32 bits | Limit used in the availability comparison |
| 8 | 32 bits | Current position |
| 20 | 32 bits | Optional callback address |

Fields at offsets 12 and 16 are not directly accessed. The full object layout is unknown.

“Position” and “limit” describe their observed roles. Their units, validity constraints, and object-wide semantics are inferred rather than independently established.

### Callback interface

The indirect dependency receives four arguments in this order:

1. The stream-object pointer.
2. The position captured before the availability comparison.
3. A pointer to four bytes of local scratch storage.
4. A requested count of exactly three.

The scratch word is initialized from the fourth input argument before the callback runs. Only its first three bytes are consumed on successful decoding.

The callback's returned value must equal exactly three. Any other value takes the local failure path. There is no retry, partial-result decoding, or acceptance of a larger reported count.

### Preconditions

For an ordinary successful invocation:

- The stream object must be nonnull and accessible at the relevant offsets.
- The status destination must permit a 32-bit write.
- A selected callback must be callable with the observed interface.
- In direct mode, a nonnull computed data address must permit three consecutive byte reads.
- Address formation and position arithmetic must have valid behavior in the execution environment.

The status destination is not checked for null. A null stream is not made safe merely by invoking the assertion dependency.

No non-aliasing condition is established. Aliasing among the status destination, stream fields, and backing bytes can affect the result because status initialization precedes stream-field and data reads.

## Behavior

### Entry and null-stream assertion

The function initializes four bytes of local scratch storage from the fourth argument.

When the stream pointer is null, the static representation establishes this preparation order:

1. Select the fixed assertion-format address for the assertion's first argument.
2. Read one global storage location to obtain the assertion's third argument, replacing the incoming third argument.
3. Read a different global storage location to obtain the assertion's second argument.
4. Invoke F-540af0155702 with the format address, the second value read, and the first value read, in that argument order.

Both global reads occur before the assertion call and before status initialization. Their order is third-argument value first, second-argument value second.

Only the assertion-format address is visibly fixed. The two other arguments are values obtained from global storage. Their contents, initialization, mutability, and semantic meanings are not established. They must not be treated as fixed metadata or constants.

There is no explicit return after F-540af0155702. If it returns normally, the function writes zero to the original status destination and then attempts to read the position through the null stream pointer. A clean failure return is therefore not established for a null stream.

If either global read or the assertion dependency prevents continuation, the subsequent status initialization is not reached. Whether the assertion terminates, raises an exception, or returns is unknown.

### Status initialization and availability

After the null-stream handling, the function:

1. Writes a 32-bit zero to the original status destination.
2. Reads the position at offset 8.
3. Reads the limit at offset 4.
4. Tests whether the captured position plus two, evaluated as unsigned 32-bit arithmetic, is strictly less than the unsigned 32-bit limit.

The addition wraps modulo \(2^{32}\). This is not an overflow-safe general test that three bytes remain.

Under ordinary nonwrapping bounded-stream conditions, position zero and limit three pass; position one and limit three fail. With position bit pattern `0xFFFFFFFE`, adding two produces zero, so every nonzero unsigned limit passes.

If the comparison fails, no callback-field inspection or direct data read is performed. Execution enters the local failure path.

### Direct access

After a passing comparison, a zero callback field selects direct access.

The data address is formed from the base field and the previously captured position. The function does not allocate a buffer, seek, or invoke a separate reader.

If the resulting address is nonnull, three bytes are used for decoding. If it is null, the byte reads are skipped and the result remains zero. That null-address case still follows the success path: the wrapper performs its position update without setting status 85 or calling the failure diagnostics.

The field comparison does not establish that the computed address is readable. Address formation also has separate unresolved arithmetic and pointer-validity requirements; the visible null check is not a general memory-safety check.

### Indirect access

A nonzero callback field selects the object-supplied indirect dependency.

It receives the captured position, not a newly read position. Its destination is the scratch storage initialized from the fourth argument.

If it returns exactly three, the function decodes the first three scratch bytes. Otherwise, it enters the local failure path without decoding them.

The wrapper does not clear scratch storage to a fixed byte pattern. If the callback reports three without replacing every consumed byte, remaining bytes depend on the fourth argument's in-memory representation. The representation's byte order is not established here.

A return value of three does not establish that the callback:

- Wrote all three bytes.
- Preserved the stream fields or status destination.
- Preserved global state.
- Kept the object or its backing storage alive.
- Refrained from retaining the scratch pointer.

Those properties require an independent callback contract.

### Result construction

Let \(b_0\), \(b_1\), and \(b_2\) denote the three bytes at increasing addresses.

When \(b_0 < 128\), the established result is:

\[
65536b_0 + 256b_1 + b_2
\]

The second and third bytes are explicitly interpreted as unsigned eight-bit values. The first is accessed through a plain character representation, converted to an integer, and shifted left by 16 bits.

For first-byte values from 128 through 255, a single portable result is not established. Unsigned-character interpretation gives the conventional unsigned 24-bit result. Signed-character interpretation can produce a negative intermediate and raises signed-left-shift concerns. Neither character signedness nor a definitive target-level result for those cases is supplied.

The expression does not establish a reliable relative order for the individual byte reads. Decoding completes before the success-path position update.

### Successful position update

On the success path, including direct access with a null computed data address, the function rereads the position, adds three, stores the result, and returns the decoded value.

This is a fresh read. It is not necessarily the position captured for the comparison or supplied to the callback. If a successful callback changes the position from five to twenty, the wrapper subsequently stores twenty-three.

The final addition is represented as signed-integer arithmetic. Portable wrapping behavior at signed overflow is not established, unlike the explicitly unsigned availability calculation.

The wrapper does not restore status to zero after the callback or after updating the position. Aliasing or dependency side effects may therefore make the final status differ from zero.

### Local failure

Local failure occurs when:

- The availability comparison fails; or
- The callback's result differs from three.

The wrapper then:

1. Writes decimal 85, hexadecimal `0x55`, to the original status destination.
2. Calls F-4457a9a44a68 with a fixed operation-identifying diagnostic.
3. Calls F-4457a9a44a68 again with a fixed position/size diagnostic and freshly obtained position and limit values.
4. Returns zero if both calls return normally.

The position and limit for the second call are read after the first diagnostic returns. They can therefore differ from the values used in the availability comparison. Their relative argument-evaluation order is not established.

There is no wrapper-performed success increment on this path and no rollback of callback, status-aliasing, or diagnostic effects. The diagnostics are not established to preserve status 85.

## Side effects

### Reads and writes

The wrapper directly performs:

- A four-byte local scratch initialization.
- Two ordered global reads on the null-stream path, before the assertion call and before any status write.
- A 32-bit zero write to the status destination.
- Stream-field reads for comparison and access selection.
- Three byte reads when decoding a nonnull data pointer.
- A fresh position read and position write on success.
- A 32-bit write of 85 on local failure.
- Fresh position and limit reads between the first and second failure diagnostics.

The two null-path global reads supply argument values; they are not direct writes to global storage. Dependency calls may have additional effects that are not established.

### Aliasing

If the status destination aliases the position field, initial status clearing changes the position before the comparison. If it aliases the limit field, the limit becomes zero before that comparison.

If it aliases backing bytes, those bytes can change before decoding. If it aliases the position on a successful path, the position update can overwrite the status word after initialization.

On failure, the status write can itself alter fields subsequently reported by diagnostics. These cases are not isolated or rejected.

### Ownership and lifetime

No allocation, deallocation, or ownership transfer is directly visible in the wrapper.

The callback receives a pointer to storage local to this invocation. No usable lifetime after return is established. The wrapper supplies no evidence that dependencies refrain from retaining pointers, releasing objects, or changing ownership.
