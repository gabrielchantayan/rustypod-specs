# F-c5640ca5b487

## Purpose

F-c5640ca5b487 attempts to acquire four bytes from a stream-like state object, interpret them as an unsigned little-endian 32-bit value, and advance the object’s current position by four.

Acquisition uses either a backing-memory address or a state-provided callback. A rejected bounds check or a callback result other than exactly four leads to two diagnostic calls, a status write of `0x55`, and a zero return, provided the diagnostic calls return normally.

The operation is not transactional. It clears the status output before checking bounds, permits dependencies to affect accessible state, and performs no visible rollback. A zero return can represent either successful decoding or detected failure.

A null state pointer takes an assertion-related path. Before calling that dependency, the function reads two global locations in a defined order. Their contents are not established constants.

## Behavior

### Initialization and null-state handling

The function initializes four bytes of invocation-local storage from the fourth argument. The initial acquisition destination points to that storage.

For a null state pointer, the observable sequence is:

1. Read the third-argument global.
2. Read the second-argument global.
3. Call F-540af0155702 with a fixed assertion-related message, the second global’s value as the second argument, and the first global’s value as the third argument.
4. If the dependency returns normally, write zero through the original status-output pointer.
5. Attempt to read the position through the null state pointer.

The two global reads precede the dependency call; the dependency cannot retroactively change the values already obtained for that invocation. The body does not establish an atomic snapshot across the reads or any protection against external mutation between them.

The substituted second call argument does not redirect subsequent status writes. Those writes still use the original status-output pointer.

There is no explicit return after F-540af0155702. Null state therefore is not an established recoverable error that returns zero with status `0x55`. Termination at the dependency, a later fault, or other platform-dependent consequences remain unresolved.

### Initial status write and bounds check

For an ordinary non-null state, the first externally directed write is a 32-bit zero to the status output. The function then reads the position at offset `+8` and the extent at offset `+4`.

The bounds condition accepts exactly when:

**The unsigned 32-bit value of position plus three is strictly less than the unsigned 32-bit extent.**

The addition in this comparison wraps modulo `2³²`. It is not an overflow-checked calculation.

Without wraparound, the condition requires all four requested byte positions to lie below the extent. Near the upper end of the 32-bit range, wraparound can instead admit a request that a mathematical, non-wrapping bounds check would reject.

A rejected condition skips acquisition and enters the detected-failure sequence. The callback field and backing data are not needed for that path.

The initial status write precedes these state reads. If the output aliases the position field, for example, bounds checking sees the zero just written rather than the previous position.

### Acquisition-mode selection

After bounds acceptance, the function inspects the callback field at offset `+20`.

- Zero selects direct-memory acquisition.
- Nonzero selects callback acquisition.

The position supplied to either acquisition path is the position captured for the bounds check. Later callback changes do not alter that already captured input.

### Direct-memory acquisition

In direct mode, the acquisition address is formed from the backing-address representation at offset `+0` and the captured position.

The function does not copy the requested bytes into its temporary storage. If the computed address is non-null, it reads four bytes and assigns them the following significance:

| Byte position | Contribution to the result |
|---|---|
| First | Bits 0–7 |
| Second | Bits 8–15 |
| Third | Bits 16–23 |
| Fourth | Bits 24–31 |

Each byte is treated as unsigned. Equivalently, the value is the first byte plus 256 times the second, 65,536 times the third, and 16,777,216 times the fourth.

The supplied expression establishes byte significance, not a guaranteed temporal order among the four individual loads. No behavior for volatile or concurrently changing backing storage is established.

If the computed address is null, all four byte loads are skipped. The result remains zero, and execution still follows the success path, including position advancement. This case does not itself produce status `0x55`.

The wrapping bounds addition does not establish wrapping address arithmetic. Portable behavior for overflowing backing-address-plus-position arithmetic is unresolved, and bounds acceptance alone does not prove address validity.

### Callback acquisition

The state-provided callback receives these four arguments:

1. The state object pointer.
2. The position captured before invocation.
3. A pointer to the initialized four-byte temporary destination.
4. The requested count, four.

The caller accepts only a return value exactly equal to four. Zero, partial counts, larger counts, and negative values under the visible 32-bit result interpretation all enter detected failure.

After an accepted result, the function decodes the temporary destination using the same unsigned little-endian weighting as direct mode. It does not independently verify that the callback wrote all four bytes. Untouched bytes retain their initial contents from the fourth argument.

The numeric fourth argument’s representation in those bytes depends on the platform. No platform-independent initialization byte order is established.

The callback receives the state pointer and may have access to other shared storage. The caller imposes no visible preservation requirement on state, status storage, globals, or memory lifetime. Callback-side changes are not rolled back if the callback later returns an unacceptable count.

### Success advancement and return

After decoding, or after skipping decoding because the computed direct address is null, the function reads the position field again, adds four, and writes the result to offset `+8`.

This updates the **then-current position**, not necessarily the position used for bounds checking or callback input. If a callback changes the position to 100 and returns four, the caller subsequently stores 104, assuming no further mutation or invalid access intervenes.

The visible update uses a 32-bit position field and an addition represented as signed arithmetic. A portable result for signed overflow is not established. The unsigned wraparound rule from the bounds test must not be applied automatically to this update.

The function returns the decoded value without clearing the status output again. A callback-induced status change can survive success. A success-time position write can also overwrite the status output if those locations alias.

### Detected failure

Bounds rejection or a callback result other than four produces this sequence:

1. Call F-4457a9a44a68 with a fixed operation-related diagnostic message.
2. Read the state’s current position and extent for a second call to F-4457a9a44a68 using a fixed invalid-I/O diagnostic format.
3. Write the 32-bit value `0x55` to the original status-output location.
4. Return zero.

The position and extent used by the second diagnostic are obtained after the first diagnostic call. They need not equal the values used for the bounds check. No relative ordering between those two diagnostic argument reads is established.

The function performs no explicit position advancement on detected failure. That does not guarantee an unchanged position: the callback or diagnostics may already have changed it.

If either diagnostic does not return normally, the final status write and return are not guaranteed.

## Acceptance examples

These are conditional static expectations, not runtime observations. Unless stated otherwise, accessed memory is valid, status does not alias relevant storage, arithmetic does not overflow outside the defined unsigned bounds calculation, and dependencies return normally without additional mutation.

1. **Ordinary direct success.** Position is 2, extent is 6, and the four requested bytes are `78 56 34 12`. The return is `0x12345678`, status remains zero, and position becomes 6.

2. **Insufficient extent.** Position is 2 and extent is 5. Position plus three equals the extent, so the strict comparison rejects the request. Acquisition is skipped, both diagnostics run, status becomes `0x55`, and the return is zero.

3. **Successful zero.** Four acquired zero bytes produce a zero return, zero status, and advancement by four. The return value alone does not distinguish this from failure.

4. **Partial callback result.** Bounds accept, but the callback returns three. The caller enters detected failure without decoding a successful result. Callback-side changes remain; no rollback occurs.

5. **Callback changes position.** The callback receives position 8, supplies bytes `01 00 00 00`, changes the position to 100, and returns four. The return is 1 and the final position is 104.

6. **Callback leaves bytes untouched.** A callback returning four without writing the destination causes the initialized bytes to be decoded. The result depends on the fourth argument’s byte representation.

7. **Null computed direct address.** If accepted bounds and direct-address formation yield null, the return is zero, no data bytes are read, and the current position advances by four. Status remains zero under the baseline assumptions.

8. **Wrapping bounds calculation.** Position `0xFFFFFFFE` and extent 2 pass because adding three modulo `2³²` yields 1. This establishes bounds acceptance only, not valid direct access or portable success advancement.

9. **Status aliases position.** The initial status write sets the position to zero. If acquisition then succeeds without other mutation, the position update stores four into that same location. The caller consequently observes four there, not a preserved success-status zero.

10. **Null state with readable globals.** Suppose the first global read yields value A and the second yields value B. F-540af0155702 receives the fixed message, B, and A, in that argument order. Both global reads precede any status write. If the dependency returns, the function clears the original status destination and then attempts a null-state position read; no successful return or recoverable-error status is established.

11. **First diagnostic changes state.** If the first diagnostic changes position and extent, the second diagnostic receives the subsequently read values rather than necessarily reporting the rejected request’s original values.
