# F-1cd488469071

## Purpose

F-1cd488469071 performs an ordered, per-coordinate transformation involving three objects: a destination, a source, and a third object supplying an auxiliary byte. For each visited coordinate, it requests source data, destination data, and auxiliary data; invokes a transformation dependency; and submits the result to a destination-writing dependency.

The apparent intent is a masked or weighted image operation. That interpretation is **inferred**, not established: the supplied evidence does not define the data format, the transformation, or the meaning of the auxiliary byte.

The traversal bounds are established by the visible arithmetic, including unusual adjustments when the third region is smaller than the source region. Those adjustments must not be replaced by conventional rectangle intersection or minimum-width clipping.

For descriptive purposes:

These names describe how the values participate in the arithmetic. They do not establish a public rectangle type, coordinate system, pixel format, or object class.

The representation uses 32-bit integer quantities and signed comparisons. The source does not independently establish behavior for signed arithmetic overflow. The arithmetic contract below is therefore unambiguous when intermediate values are representable; overflow cases remain documented_only.

## Behavior

### 1. Establish translated coordinates

Before any dependency call, the function reads the input values and object offsets to establish:

- Source start:
  - `Sx` = source left + source horizontal offset.
  - `Sy` = source top + source vertical offset.
- Source end:
  - `Ex` = source right + source horizontal offset.
  - `Ey` = source bottom + source vertical offset.
- Destination start:
  - `Dx` = destination x + destination horizontal offset.
  - `Dy` = destination y + destination vertical offset.
- Auxiliary start:
  - `Ax` = auxiliary left + auxiliary horizontal offset.
  - `Ay` = auxiliary top + auxiliary vertical offset.

The visible sequence establishes the source start and end first, then the destination start, then the auxiliary start.

Object offset fields are referenced separately for the corresponding expressions. The evidence does not justify treating repeated references as one atomic snapshot, nor does it establish operand-level load order within an individual arithmetic expression.

There are no dependency calls during this setup phase.

### 2. Derive the vertical extent

The function computes an auxiliary vertical span:

`AH = (auxiliary bottom + auxiliary vertical offset) − Ay`

It compares this span with the initial source height, `Ey − Sy`, using a signed comparison.

- If `AH` is strictly smaller, the source end value is replaced with `AH − Ay`.
- Otherwise, the source end remains `Ey`.

The final traversal height is the resulting end value minus `Sy`.

Equivalently, without overflow:

| Condition | Final height `H` |
|---|---|
| `AH < Ey − Sy` | `AH − Ay − Sy` |
| Otherwise | `Ey − Sy` |

The adjustment subtracts translated start coordinates; it is not simply a minimum of two heights.

### 3. Derive the horizontal extent

Next, the function computes an auxiliary horizontal span:

`AW = (auxiliary right + auxiliary horizontal offset) − Ax`

It compares that span with the initial source width, `Ex − Sx`, using a signed comparison.

- If `AW` is strictly smaller, the source end value is replaced with `AW − Ax`.
- Otherwise, the source end remains `Ex`.

The final traversal width is the resulting end value minus `Sx`.

Equivalently, without overflow:

| Condition | Final width `W` |
|---|---|
| `AW < Ex − Sx` | `AW − Ax − Sx` |
| Otherwise | `Ex − Sx` |

Vertical adjustment occurs before horizontal adjustment. Both adjustments occur before traversal begins.

No destination extent is supplied or checked. There is no explicit intersection against destination bounds.

### 4. Traverse columns before rows

The outer traversal advances a horizontal index from zero while it is less than `W`. For each horizontal index, the inner traversal advances a vertical index from zero while it is less than `H`.

Thus, the operation visits a whole column before advancing to the next column.

When both extents are positive and arithmetic remains defined, the visited index pairs are:

- `(0, 0)` through `(0, H − 1)`;
- then `(1, 0)` through `(1, H − 1)`;
- continuing through column `W − 1`.

If `W` is nonpositive, no traversal body executes. If `W` is positive but `H` is nonpositive, the outer traversal advances without executing a per-coordinate body. In either case, no dependencies are called.

The extents and translated starts are calculated once. They are not recalculated after dependency calls.

## Side effects

### Direct effects

The visible body reads object fields and input arrays and writes its own temporary storage. It contains no explicit allocation, deallocation, or direct write into the supplied objects or input arrays.

The intended externally visible update is delegated to F-50245a09539e. The function itself does not establish what that dependency writes.

### Dependency-mediated effects

Dependencies receive addresses derived from the supplied objects and addresses of temporary storage. Their effects are not constrained by the visible body.

In particular:

- Object fields at `0x1c` are reread at their respective call sites.
- A dependency mutation of such a field can affect a later call in the same iteration.
- Changes to source, destination, or auxiliary content may affect later reads.
- Dependencies may affect global state; preservation is not established.
- The region beginning at destination offset `0x34` may be read or modified by the writer, but its contents and extent are unknown.

The caller does not restore state after a dependency call.

### Aliasing and ownership

There is no alias check. Source, destination, and auxiliary objects or their backing data may overlap unless prohibited by an external contract.

The function does not snapshot an entire region. Each read occurs at its place in the column-major sequence. A destination write can therefore influence a later read if storage aliases.

No ownership transfer of input objects is explicitly performed. Temporary storage is reused across iterations. Whether dependencies retain, release, or otherwise assume ownership of supplied addresses is unknown; the function provides no visible handling for retained scratch addresses.

### Errors

There is no explicit error branch, bounds check, rollback, or partial-completion report. If a dependency fails, faults, or does not return, the visible body supplies no recovery behavior. Prior dependency effects may already have occurred.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed tests. Arithmetic is assumed representable, and dependencies are assumed to return normally. Where call counts are specified, they assume dependencies do not disrupt the traversal state.

### Ordinary two-column, three-row traversal

Suppose all object coordinate offsets are zero:

- Source region: `[0, 0, 2, 3]`.
- Destination position: `[10, 20]`.
- Auxiliary region: `[0, 0, 2, 3]`.

The effective width is two and height is three. Six iterations occur, producing thirty dependency calls.

Destination coordinates are processed in this order:

`(10,20), (10,21), (10,22), (11,20), (11,21), (11,22)`.

Within every iteration, source read precedes destination read, auxiliary read, transformation, and destination write. Dependency coordinate arguments place the vertical coordinate before the horizontal coordinate.

### Smaller auxiliary span with zero starts

With zero offsets, a source region `[0,0,5,4]` and auxiliary region `[0,0,2,3]` produce width two and height three.

In this particular case, the unusual adjustment agrees with conventional minimum-span clipping because the translated starts are zero.

### Smaller auxiliary width with nonzero starts

With zero offsets:

- Source region: `[10,0,15,1]`.
- Auxiliary region: `[2,0,5,1]`.

The initial source width is five and auxiliary width is three. Because three is smaller than five, the adjusted source horizontal end becomes `3 − 2 = 1`. Subtracting the source start produces width `1 − 10 = −9`.

No dependency calls occur. Treating the effective width as three would not match the supplied behavior.

### Equal spans do not trigger adjustment

With zero offsets:

- Source horizontal bounds: `[10,15]`.
- Auxiliary horizontal bounds: `[2,7]`.

Both spans are five. The strict comparison is false, so the width remains five. Nonzero starts alone do not activate the unusual adjustment.

### Destination address can change between read and write

Suppose a dependency changes the destination field at `0x1c` after the destination read but before the destination write.

The writer receives the newly read field value plus four. Reusing the destination-read address would not preserve the visible behavior.

### Auxiliary byte requires a dependency guarantee

If F-bc8f2568ff72 writes a defined value to the byte two positions after the auxiliary scratch address, that byte is supplied to F-86dd6fb1ad71.

If it writes only the first two bytes, the supplied evidence establishes no initialized value for the consumed byte. A deterministic output cannot be required for that case from this evidence alone.
