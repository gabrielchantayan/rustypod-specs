# F-64e6624e7275

## Purpose

F-64e6624e7275 searches a linked sequence of memory-block records, selects the first record large enough for a requested size, removes it from that sequence, optionally splits it, and invokes a finalization dependency on the selected allocation record.

The structure and operations suggest an allocator operating on an existing free-block structure. That interpretation is **inferred intent**, not a complete established API contract. In particular:

- The supplied interface has no explicit return value.
- A payload address is computed internally, but the supplied evidence does not establish that it is returned to the caller.
- The dependencies’ allocation, ownership, accounting, and global-state behavior is unknown.
- Failure to find a suitable record does not invoke the explicit failure dependency.

The established behavior is the sequence of reads, writes, comparisons, and dependency calls described below.

## Interface

### Inputs

1. **Context address**

   A pointer to writable storage containing 32-bit words and an embedded block record. The function directly accesses:

   | Byte offset | Direct use |
   |---|---|
   | 0 | Accounting word, reduced by the selected record’s masked size |
   | 8 | Accounting word, increased after finalization by the final record’s then-current masked size |
   | 208 | First record header examined |
   | 212 | Link used to advance from that first record when it is too small |
   | 216 | Backward-link field if that first record is selected |

   Offset 208 is the address of an embedded record, **not** a location from which an initial record pointer is loaded.

2. **Requested size**

   An unsigned 32-bit value. The entry check requires its low two bits to be zero. This is expressed through a subtract-and-mask operation, but it does **not** enforce a minimum size of eight.

   Zero, four, and every other multiple of four pass this entry check.

3. **Opaque auxiliary value**

   A 32-bit value forwarded unchanged to F-d344ca23a883. This function does not otherwise interpret it.

### Record layout

The function treats each traversed record as having these 32-bit words:

| Byte offset | Meaning used here |
|---|---|
| 0 | Header containing a size field and other bits |
| 4 | Forward link |
| 8 | Backward link while the record is linked |

The size field is the header masked with `0x3ffffffc`: bits 2 through 29 contribute to the size. Bits 0, 1, 30, and 31 do not.

The nominal payload address is eight bytes after the record address. Its required alignment is eight bytes.

The function also accesses a boundary word at the selected record address plus its masked size. The evidence establishes checks and updates to that word, but not its complete format.

### Outputs

There is no explicit return value in the supplied interface.

On a successful selection path, an internal candidate address becomes the final record address plus eight. On a no-match path, that candidate remains null. The function checks this candidate for eight-byte alignment before returning.

Neither an externally returned payload pointer nor a caller-visible null failure result is established.

### Preconditions

For defined ordinary operation, the context and every accessed record, link target, boundary word, and newly formed record location must designate suitable readable or writable storage.

The function does not validate:

- A null context.
- Record containment within an arena.

Arbitrary aliasing can make earlier writes affect later reads. Conventional list and arena invariants are therefore practical preconditions for the ordinary interpretation, rather than invariants proved by this function.

## Behavior

### 1. Request validation

The internal candidate address starts as null.

The function checks whether the low two bits of the 32-bit result of requested size minus eight are zero. Because eight is divisible by four, this accepts exactly requests divisible by four.

A failing request immediately invokes F-a817d8d58c10. No context or record access precedes that call.

This check does not round the request.

### 2. First-fit traversal

For an accepted request, traversal begins at context address plus 208.

For each non-null record:

1. Read its header.
2. Extract its size with `0x3ffffffc`.
3. Compare the requested size against that extracted size as unsigned values.
4. Select the record if the request is less than or equal to its size.
5. Otherwise, read its forward link and continue there.

The first sufficient record wins. There is no best-fit search or continuation after a selected record fails an integrity check.

If traversal reaches a null link without selecting a record, the candidate remains null. Its alignment check succeeds, and the function returns without invoking either record-management dependency.

There is no cycle detection or iteration limit.

### 3. Selected-record validation

Before modifying a selected record, the function requires its nominal payload address, record address plus eight, to be eight-byte aligned.

It then computes the boundary address using the selected record’s masked size and reads the 32-bit boundary word. That word must satisfy both conditions:

- Bit 1 is set.
- Bit 0 is clear.

Failure of either the payload alignment check or the boundary-bit check invokes F-a817d8d58c10.

No selected-record mutation has occurred at these failure points.

### 4. Boundary update and unlinking

After validation, the function clears bit 1 in the boundary word and writes it back. All other bits of that word are preserved by this operation.

It then removes the selected record from its linked structure:

1. Read the selected record’s backward link.
2. If that link is non-null, read the selected record’s forward link and write it to offset 4 of the backward-linked record.
3. Examine the selected record’s forward link.
4. If non-null, write the selected record’s current backward link to offset 8 of the forward-linked record.

The boundary write occurs before either neighboring-link write. The backward neighbor is updated before the forward neighbor.

These operations do not use a guaranteed immutable snapshot of all link fields. Later operations use fields read after earlier writes. Aliasing or malformed self-links can therefore change the values observed later in the sequence.

There is no separate head-pointer update. Any head-management behavior must arise from the embedded record, the links, or dependencies outside the visible behavior.

### 5. Header and accounting update

The function next reads the selected record’s header and clears bit 0 in that header.

It reduces the context word at offset 0 by the masked size of the header read for this update. The accounting operation has 32-bit arithmetic behavior; no underflow check is performed.

It then reads the selected header again and extracts its masked size for the split decision. This later read is significant if storage aliases earlier write destinations.

### 6. Split decision

A split is attempted only when the selected masked size is strictly greater than:

**the requested size plus 19, evaluated at 32-bit width, then masked with `0x3ffffffc`.**

The comparison is unsigned. Equality means no split.

This expression is not an unrestricted mathematical request-plus-margin test. The mask removes high bits as well as the low two bits. Near the upper boundary of the size field, the threshold can become small.

For ordinary small requests:

- A request of 32 has a threshold of 48.
- A request of 48 has a threshold of 64.
- A request of 36 has a threshold of 52.

If the selected size does not exceed the threshold, the original selected record proceeds directly to finalization.

### 7. Split construction and checks

When splitting is attempted, the function subtracts the requested size from the selected record’s **full current header**, at 32-bit width. This is not subtraction from only the masked size.

The resulting raw remainder must be divisible by eight.

The visible logic also checks four-byte divisibility of a temporary value. On a path where the remainder is divisible by eight, that temporary is the remainder minus four, so this additional check necessarily succeeds.

Importantly, the raw remainder is written into the original record header **before** the function acts on a failing split-validity result.

If the remainder is acceptable, a new record address is formed as:

**original selected record address plus the remainder masked with `0x3ffffffc`.**

The new record’s nominal payload address, eight bytes later, must be eight-byte aligned.

Failure of the remainder or new-address alignment checks invokes F-a817d8d58c10. At that point, earlier boundary, link, header, and accounting changes have already occurred. There is no visible rollback.

On a valid split:

1. Write the requested size as the new record’s header.
2. Invoke F-cc6c9b4a0f68 with the context and original selected record.
3. Make the new record the record passed to finalization.

Thus the remainder occupies the lower-address original record, while the requested-size record is placed at the higher address.

The function does not directly initialize the new record’s link words.

### 8. Finalization and final accounting

Whether split or unsplit, the function invokes F-d344ca23a883 with:

- The context.
- The final record address.
- The opaque auxiliary value.

After that call returns, the function reads the final record’s current header, extracts its masked size, and adds that size to the context word at offset 8.

This size is read **after** finalization. It must not be assumed to equal the requested size, the original selected size, or the header written during splitting.

The context counter is also used after the dependency has run; dependency changes to it affect the final result. The visible code establishes that both operand reads precede the accounting write, but not a meaningful externally guaranteed order between those operand reads.

The candidate address then becomes the final record address plus eight. If this address is eight-byte aligned, the function returns. Otherwise, it invokes F-a817d8d58c10.

There is no additional boundary check after finalization.

## Side effects

Direct mutations, in order along a selected-record path, are:

1. Clear boundary-word bit 1.
2. Update the backward neighbor’s forward link, when present.
3. Update the forward neighbor’s backward link, when present.
4. Clear selected-header bit 0.
5. Subtract the selected masked size from context offset 0.
6. On a split attempt, replace the original header with the raw remainder.
7. On a valid split, write the requested size into the new record header.
8. Invoke the split dependency, when applicable.
9. Invoke the finalization dependency.
10. Add the final record’s post-finalization masked size to context offset 8.

No direct payload clearing or payload copying is shown.

The link word at offset 8 overlaps the beginning of the nominal payload region. Its use as a backward link is established for linked records; the function does not establish what happens to its contents after allocation.

The two context accounting updates use 32-bit arithmetic without explicit saturation or range checks.

No ownership transfer can be fully specified from this function alone. It removes a record from a linked structure and delegates further processing, but does not itself establish who owns backing storage, whether a dependency releases storage, or whether the final record remains accessible after finalization.

No synchronization is visible. Thread safety, interrupt safety, and reentrancy are not established.

## Acceptance examples

These examples are conditional contracts. Unless stated otherwise, assume valid non-overlapping storage, consistent links, eight-byte-aligned record addresses, and returning dependencies that leave the fields relevant to the example accessible.

### Misaligned request

A request of 10 fails the entry check.

Expected behavior: invoke F-a817d8d58c10 without reading the context or any record.

### No sufficient record

A request of 128 traverses records whose masked sizes are 32 and 64, followed by a null link.

Expected behavior: examine both headers in order, follow both forward links, and return without direct record writes or calls to either record-management dependency. No externally returned null value is established.

### Selection without splitting

A request of 48 selects a record with masked size 64 and header bit 0 initially set.

The split threshold is 64, so equality prevents splitting.

Expected behavior: validate the payload and boundary, clear boundary bit 1, unlink the record, clear header bit 0, subtract 64 from context offset 0, and invoke F-d344ca23a883 on the original record.

If finalization leaves the masked size at 64, add 64 to context offset 8. F-cc6c9b4a0f68 is not called.

### Successful split

A request of 32 selects a record whose header becomes exactly 64 after bit 0 is cleared.

The threshold is 48, so splitting occurs. The raw remainder is 32.

Expected behavior: write 32 into the original header, place a new header containing 32 at original record address plus 32, invoke F-cc6c9b4a0f68 on the original record, then invoke F-d344ca23a883 on the new record.

If the dependencies preserve the new masked size, the final accounting addition is 32.

### Split failure after mutation

A request of 36 selects a record whose header becomes exactly 64 after clearing bit 0.

The threshold is 52, so a split is attempted. The raw remainder is 28, which is not divisible by eight.

Expected behavior: perform the boundary update, unlinking, initial header update, and accounting subtraction; then write 28 into the original header and invoke F-a817d8d58c10. Neither returning dependency is called.

### Zero request

A request of zero passes entry validation.

If it selects a record whose cleared header is exactly 64, the split threshold is 16 and the remainder is 64. With valid storage and alignment, the function writes a zero-sized new header at original record address plus 64 and proceeds through both returning dependencies.

Whether those dependencies accept that record is unknown. This function does not reject zero itself.
