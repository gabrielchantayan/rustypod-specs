# F-1b066d20d1be

## Purpose

F-1b066d20d1be temporarily records an association between two supplied objects, publishes a token into a container, and invokes an operation selected by a two-component bound. It returns a 32-bit status.

**Established static behavior:** the function performs selected pointer and field checks, optionally invokes a preliminary dependency, increments an association count, establishes or checks cross-references, publishes a token, evaluates the bound, and performs result-dependent cleanup.

**Inferred intent:** the association, token, and bound resemble coordination for a timed synchronization operation. This interpretation does not establish locking, waiting, execution-context identity, physical time units, or ownership semantics.

The function is not transactional. An association-mismatch return leaves the count increment in place. Dependency effects are not generally reversed. Normalization must finish before the function checks whether the bound is strictly later; failure to progress there prevents the subsequent operation and cleanup.

No argument-disjointness or concurrency contract is supplied. Aliasing and dependency-induced mutations can affect later reads. The behavior described below assumes accesses remain valid; invalid memory access is not converted into a documented status.

## Behavior

### 1. Entry checks and preliminary call

Initial rejection is short-circuited in this order:

1. Null primary pointer.
2. Null secondary pointer.
3. Secondary marker unequal to the required external marker.
4. Null bound pointer.

Any such rejection returns **26** without calling a dependency. Thus a secondary-marker read can occur before a null bound is rejected, whereas a null primary prevents that read.

After these checks, the primary marker is compared with another external marker. Equality selects F-ce244e3d86dc, called with the primary object and zero. A nonzero result is returned immediately. A zero result permits further processing.

This preliminary call precedes minor-range and identity validation. Its effects are not rolled back if either later check fails.

### 2. Identity acquisition and two distinct normalization reads

F-196812b4b122 is called, and its 32-bit result is retained for the identity comparison.

The normalization global is then read into a saved unsigned 32-bit value. This saved value is used later by the borrowing loop.

A separate read of the same global supplies the unsigned limit used to validate the bound’s minor component. If that minor component is greater than or equal to this **validation-read value**, the function returns **26**.

The source includes a non-null guard around this range check, although ordinary entry validation has already required a non-null bound.

Only after range validation does the function compare the secondary identity field with the retained F-196812b4b122 result. Inequality returns **5**.

Consequences of the two-read sequence:

- Validation is not against the saved borrowing increment.
- Equality between the two values requires an external stability assumption.
- A zero validation-read value rejects every unsigned minor component.
- A zero saved increment is not necessarily rejected: a later, positive validation-read value can allow processing to continue.
- Later dependencies do not cause the saved increment to be refreshed.

### 3. Association accounting

The primary count is read, incremented, and written before association compatibility is resolved.

When the incremented count equals one:

1. The supplied secondary address is written to the primary association field.
2. The primary address is written to the supplied secondary back-reference.

Otherwise, the stored primary association must equal the supplied secondary address. A mismatch returns **26** immediately.

That mismatch return retains the increment. It performs no compensating decrement, token preparation, token removal, or final reference clearing.

There is no explicit count-range check. An ordinary initial count of zero establishes the cross-references; behavior at signed-overflow boundaries is not established as wrapping.

### 4. Token preparation and container publication

F-e495954a1b5a receives the address of the three-word temporary region. The function subsequently uses its first word as the token; the dependency’s full initialization contract is unknown.

After this call, the primary container address is captured. F-341a4429b84a receives that captured address.

F-81769f9c2572 is then called with the same captured container if either:

- F-341a4429b84a returns nonzero; or
- it returns zero and the container fields at +16 and +24 compare equal.

The field comparison is skipped when the preceding result is nonzero. There is no visible failure-status check after F-81769f9c2572.

Publication then uses the captured container:

1. Its +16 field is interpreted as an insertion address.
2. If nonzero, the token’s first 32-bit word is written through that address.
3. The +16 field is advanced by four bytes.
4. The 32-bit field at +32 is incremented by one.

A zero insertion address skips only the indirect token store. Pointer-field advancement and count advancement still occur. Under ordinary arithmetic, a zero insertion field therefore becomes four.

F-40a859542b3f is then called with the primary association field as read at that time. Its result is ignored.

### 5. Current-value query and normalization

On the ordinary validated path, F-3ad269318332 receives:

- the primary field at +16, read at call time;
- the address of a local unsigned 32-bit output component.

A neighboring signed 32-bit local component is also consumed afterward. The visible call does not separately pass its address or establish its initialization. Subsequent pair calculations therefore require an unavailable output-layout contract.

A nonzero query result becomes the pending return status and selects failure cleanup.

For a zero query result, the function forms two differences:

- supplied major minus returned major, using unsigned 32-bit subtraction, then assigned to signed 32-bit storage;
- supplied minor minus the neighboring current minor, likewise using unsigned 32-bit subtraction, then assigned to signed 32-bit storage.

While the stored minor difference is negative, each iteration decreases the signed major difference by one and adds the saved unsigned normalization increment to the minor difference. The latter addition uses unsigned arithmetic before assignment back to signed storage.

This is repeated borrowing, not division. No explicit overflow check, iteration limit, or nonprogress check is present.

If the saved increment is zero and the initial stored minor difference is negative, adding the increment cannot change that minor difference. The major difference continues to be decremented while execution remains defined. The source does not establish successful normalization, a timeout status, or cleanup for this case. Signed major overflow prevents an unconditional language-level claim of infinite looping.

### 6. Strict-future decision and operation

Only after normalization finishes does the function compare the bound with the returned current pair.

The bound qualifies as strictly later when:

- its unsigned major component is greater than the current unsigned major component; or
- the major components are equal and the current signed minor component is less than the supplied minor component converted to signed 32-bit.

Otherwise the pending result becomes **64**.

Bound fields are read again during this comparison rather than taken from a single saved pair. Without input stability, the values compared need not be the values used for subtraction.

A qualifying bound selects F-eda20b604f7c, called with the temporary region and the address of the signed major difference. The minor difference occupies neighboring local storage, but the dependency’s access to a two-component difference is not established by the visible call alone.

The function also contains a later null-bound branch selecting F-c1fb734a0a68 with the temporary region. Entry rejects null and no visible assignment changes the bound pointer. This branch does not establish a supported null-bound interface.

### 7. Result-dependent cleanup

A zero operation result selects this order:

1. F-9ccc36b3b385 receives the temporary region.
2. F-4bbc81f24830 receives the primary association field, read afterward.
3. The result of F-4bbc81f24830 becomes the pending return value.

There is no explicit F-b00a3b0e2b77 call on this path, even if F-4bbc81f24830 returns nonzero.

A nonzero operation result, nonzero current-value query result, or status **64** selects this order:

1. F-4bbc81f24830 receives the currently stored primary association; its result is ignored.
2. F-b00a3b0e2b77 receives the primary container field, read at this point, and the temporary region’s first word.
3. F-9ccc36b3b385 receives the temporary region.

The earlier nonzero status remains pending. The removal container can differ from the captured insertion container if an intervening dependency changes the primary object. The token supplied for removal is also read at removal time.

### 8. Final association cleanup

Both completed cleanup paths then read the current primary count, decrement it, and write it back.

If the resulting count equals zero:

1. The primary association field is cleared.
2. The supplied secondary object’s back-reference is cleared.

The function then returns the pending status.

This uses the count present during cleanup, not a saved entry count. Dependencies can therefore affect the final count and whether references are cleared. The secondary object cleared is the supplied one, not an object obtained by following the current association field.

## Acceptance examples

These are conditional static expectations, not executed tests. Arithmetic examples assume representable signed values, stable inputs except where stated, and valid dependency output contracts.

1. **Null bound.** With valid object pointers and the required secondary marker, returns **26** without dependency calls. The secondary marker is read before null-bound rejection.

2. **Validation uses the second global read.** Suppose the saved increment is 1,000, the validation read is 500, and the supplied minor is 500. The function returns **26**, despite the minor being below the saved increment. Association accounting has not begun.

3. **Different values can permit validation.** Suppose the saved increment is 500, the validation read is 1,000, and the supplied minor is 700. Range validation passes. Any later borrowing uses 500, not 1,000. Identity validation can still reject the request.

4. **Zero validation limit.** A second global read of zero rejects every unsigned supplied minor, regardless of the saved increment.

5. **Zero saved increment with successful validation.** Suppose the saved increment is zero, the second read is 1,000, the current pair is `(10, 900)`, and the bound is `(11, 100)`. Range validation passes. If execution reaches normalization, the minor difference is −800 and never changes through addition of the saved increment. No successful normalization or subsequent cleanup is established; the major decrement eventually encounters the signed-arithmetic limitation.

6. **Association mismatch.** With initial count one and a different stored association, the function writes count two and returns **26**. The increment remains; no token is prepared.

7. **Ordinary borrowing.** With both global reads equal to 1,000, current pair `(10, 900)`, and bound `(11, 100)`, normalization yields `(0, 200)`. The strict-future comparison succeeds and F-eda20b604f7c is called.

8. **Equal bound.** For equal ordinary-range pairs, normalization finishes and status **64** is selected. Cleanup calls F-4bbc81f24830, F-b00a3b0e2b77, and F-9ccc36b3b385 in that order. The first dependency’s result does not replace **64**.

9. **Zero operation followed by status seven.** If the operation returns zero and F-4bbc81f24830 returns seven, the final result is seven after count cleanup. F-9ccc36b3b385 precedes that association call; explicit token removal is not called.

10. **Zero insertion address.** If the insertion field remains zero after container preparation, the token store is skipped, the field becomes four under ordinary arithmetic, and the container count increments.

## Uncertainties

- **documented_only — global stability:** equality between the saved increment and validation limit is not established. A zero saved increment can survive validation.
- **documented_only — normalization termination:** zero saved increments can prevent minor-difference progress. Other values require signed-conversion and arithmetic-domain analysis; the unsigned range check does not guarantee a positive signed increment or termination.
- **documented_only — current-pair output:** initialization of the neighboring current minor requires an unavailable dependency or ABI contract.
- **documented_only — difference layout:** passing the major-difference address does not independently establish the operation dependency’s complete input layout.
- **documented_only — arithmetic extremes:** out-of-range unsigned-to-signed conversions and signed count, pointer-field, or major-difference overflow have no explicit handling. Signed wrapping is not assumed.
- **documented_only — mutation and aliasing:** repeated reads can observe changed values. Argument overlap and dependency effects are unrestricted by the available contract.
- **documented_only — ownership and lifetimes:** resource ownership, token consumption, release, and retained-address validity are unknown.
- **documented_only — later null branch:** no ordinary validated route to it is established.
- **Inferred intent only:** object markers, execution-context identity, synchronization, and time semantics are interpretations, not established requirements.
