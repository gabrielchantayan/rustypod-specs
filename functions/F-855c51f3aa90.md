# F-855c51f3aa90

## Purpose

F-855c51f3aa90 obtains a result object using a fixed 68-byte request, records a one-byte discriminator and two supplied 32-bit values, conditionally establishes additional object state, invokes a final processing dependency, and returns the acquired address.

Two mutually exclusive initialization routes are visible:

- An explicit two-word input supplies four 32-bit fields in the result.
- Without that input, the routine may combine information from two referenced objects and propagate a flagged four-byte value from them.

If acquisition fails, the routine invokes a dependency once for each supplied reference value, in argument order, and returns a null pointer if both calls return.

“Acquisition,” “combination,” and “final processing” describe the roles of the calls in this routine. Their underlying allocation, ownership, and semantic guarantees are not established.

## Behavior

### 1. Acquisition and failure handling

The first operation is a call to F-f053f140662a with the acquisition context and the value 0x44, equivalent to 68.

The returned pointer is tested against null.

If it is null:

1. F-841dc33ee157 is called with the first reference.
2. After that call returns, F-841dc33ee157 is called with the second reference.
3. After the second call returns, the routine returns null.

Neither cleanup call is conditional on its reference being nonzero. If the two references are equal, the same value is passed twice. There is no visible deduplication or alternate handling for that case.

No result-object initialization, explicit-pair read, combination call, or final processing call occurs on this path.

### 2. Common successful initialization

For a non-null acquired address, the following direct writes occur in this order:

1. The discriminator is written as one byte at offset 0.
2. The four-byte all-one pattern is written at offset 48.
3. The first reference is written as four bytes at offset 8.
4. The second reference is written as four bytes at offset 12.

These stores precede the choice between explicit-pair initialization and reference-based initialization.

The all-one pattern is established as a bit pattern. Its possible interpretation as a sentinel, signed negative value, index, or other domain value is not established.

### 3. Explicit-pair route

If the explicit-pair pointer is non-null, the routine:

1. Reads the first 32-bit word from the pair.
2. Reads the second 32-bit word from the pair.
3. Writes the first captured word at result offset 20.
4. Writes the second captured word at result offset 24.
5. Writes the first captured word at result offset 28.
6. Writes the second captured word at result offset 32.

Both input reads occur before these four result writes. The duplicated words are taken from those captured values, not from fresh reads between stores.

This route performs no direct reference flag inspection and makes no call to F-50fff3996655. Nonzero reference inputs are still recorded at offsets 8 and 12, but they are not directly dereferenced by this route.

The common successful initialization occurs before the pair is read. Consequently, if input and result storage overlap, those earlier stores can affect the pair values subsequently observed. No non-aliasing guarantee is supplied.

### 4. Reference-based route

This route is selected only when the explicit-pair pointer is null.

If the first reference is zero, the routine performs no combination call and no reference flag inspection. A nonzero second reference alone does not activate either operation.

If the first reference is nonzero, processing proceeds as follows.

#### Optional combination and second-reference propagation

When the second reference is also nonzero, F-50fff3996655 is called with three arguments:

- The result address;
- The first reference advanced by 28 bytes;
- The second reference advanced by 28 bytes.

The call’s return value is not used.

After that call returns, the routine reads the second reference’s two-byte flags at offset 2 and tests bit 0x0100. It does not use a flag value captured before the call.

If the bit is set:

1. The current two-byte flags at result offset 2 are read and written back with bit 0x0100 set.
2. The four-byte value at second-reference offset 4 is read and written to result offset 4.

Other result flag bits are preserved by this direct read-modify-write. A clear source bit does not cause the result bit to be cleared.

When the second reference is zero, both this combination call and this second-reference flag handling are skipped.

#### First-reference propagation

Still within the nonzero-first-reference branch, the routine next reads the first reference’s two-byte flags at offset 2 and tests bit 0x0100.

If set:

1. The current result flags at offset 2 are updated to include bit 0x0100.
2. The first reference’s four-byte value at offset 4 is copied to result offset 4.

This occurs after any second-reference propagation. If both propagation branches execute, the first reference supplies the last direct write to result offset 4.

The first-reference flags are read at this later point. They are not snapshotted before the combination call or before the preceding result writes. A dependency’s mutations, or aliasing between result and referenced storage, can therefore influence the observed values.

### 5. Final processing and return

Every successful-acquisition route reaches a call to F-895c599e0ca7 with the result address.

After that call returns, the routine returns the acquired address. It performs no further visible object reads or writes.

The directly initialized fields describe state before this call. Without a contract for F-895c599e0ca7, their values cannot be guaranteed at the time the caller receives the pointer.

## Side effects

### Memory effects

The routine directly writes the result fields described above. Its direct reference-object accesses are reads, except where referenced storage aliases the result.

The explicit pair is read, not directly written. That does not establish that its storage remains unchanged: result aliasing or dependency effects could change it.

There is no visible whole-object clearing operation. In the absence of dependency guarantees:

- The result flags at offset 2 may retain existing bits.
- The value at offset 4 is not directly established unless a propagation branch executes.
- Offsets 20, 24, 28, and 32 are directly established only on the explicit-pair route.
- Other bytes retain whatever state acquisition and dependencies provide.

### Ownership and lifetime

The failure path’s two calls suggest reference-release or cleanup intent, but that intent is inferred rather than established. The routine does not itself show either reference being freed.

On success, both reference values are recorded in the result. The visible body does not establish whether this transfers ownership, retains ownership, increments a count, or merely stores borrowed references.

There is no explicit deallocation of the acquired result in this body. That observation does not prove the final dependency preserves its lifetime. Returned-pointer validity and caller disposal obligations remain unknown.

### Errors and nonlocal effects

The only explicit failure check is the null acquisition result. No status from the other dependencies is checked.

There is no visible validation of pointer alignment, accessible extent, reference consistency, or aliasing. No recovery path is shown for invalid memory access or a dependency that does not return normally.

Dependencies may have additional memory, global-state, or resource effects. Their absence cannot be inferred from this routine.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Acquisition failure with zero references.**  
   If F-f053f140662a returns null and both references are zero, F-841dc33ee157 must still receive zero twice, in sequence. If both calls return, the result is null.

2. **Acquisition failure with identical references.**  
   If both reference inputs contain the same nonzero value, failure still produces two calls with that value. Any safety of repeated processing is a dependency precondition, not a guarantee here.

3. **Explicit pair overrides reference-based initialization.**  
   Given successful acquisition and a non-null pair containing two readable words, those words are captured and duplicated at offsets 20/28 and 24/32. F-50fff3996655 is not called, and reference flags are not directly inspected. If the final dependency preserves those fields, the caller observes those duplicated values.

4. **Second reference alone does not propagate.**  
   With a null explicit pair, zero first reference, and nonzero second reference, neither reference flag field is directly read. No combination call occurs, even if the second object would have bit 0x0100 set.

5. **First reference alone can propagate.**  
   With a null pair, nonzero first reference, and zero second reference, the combination call is skipped. If the first reference’s flags contain bit 0x0100 when read, the result bit is set and its four-byte value is copied.

6. **Both flagged references, distinct stable storage.**  
   Assume null pair, both references nonzero, readable disjoint objects, and no relevant mutation by F-50fff3996655. If both source flag bits are set, the second value is copied first and the first value overwrites it. The pre-final-call value at result offset 4 is therefore the first source value.

7. **Post-combination flags control propagation.**  
   If F-50fff3996655 changes the second reference’s flag bit, the subsequent test uses that changed state. A pre-call flag snapshot is not an acceptable substitute.

8. **No clearing on absent flags.**  
   If neither inspected source has the bit set, the routine does not directly clear the result bit or initialize offset 4. Any stronger outcome requires a dependency contract.
