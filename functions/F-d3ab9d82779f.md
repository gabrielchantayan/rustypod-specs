# F-d3ab9d82779f

## Purpose

F-d3ab9d82779f constructs a sequence of eight-byte records from an unsigned 32-bit candidate range. For each candidate, a caller-supplied callback determines whether to request a value. A requested value is retained only if at least one of its lower 31 bits is set. Each retained record contains the complete value and its original candidate index.

The routine initializes two fields in caller-provided state, requests storage, conditionally requests a smaller capacity, and submits a nonempty result to an ordering-like dependency. It returns a 64-bit result assembled from two 32-bit components.

**Established static behavior:** record selection, record layout, state-field accesses, dependency-call conditions, and return packing are visible.

**Inferred intent:** the dependencies appear to manage storage, supply values, perform empty-result cleanup, and order records. These roles do not establish their ownership, error, or preservation contracts.

The final argument to the ordering-like dependency is obtained by reading a global location while preparing that call. It is not established to be an immutable comparator constant. Earlier callbacks and dependencies may affect the value subsequently read.

### Record layout

Each record occupies eight bytes:

| Record offset | Width | Contents |
|---|---:|---|
| 0 | 4 bytes | Complete retrieved unsigned value. |

Before the ordering-like call, records are appended in increasing candidate-index order. That call may change their order or contents; its implementation is unavailable. Native byte order is not independently established.

### Return value

The returned 64-bit bit pattern has:

- **Lower 32 bits:** the mutable status slot’s contents at return.
- **Upper 32 bits:** zero unless the nonempty path makes the second storage request. On that path, the upper half contains the storage-address bit pattern saved after enumeration and supplied to that request.

The status slot initially contains the callback address. Storage requests receive the slot’s address and may modify it. The routine itself can set the slot to zero or to the numeric bit pattern 6.

Neither half is an independently established success flag. The upper half is not a count, and its address-like value carries no established ownership or liveness guarantee.

### Preconditions

The routine does not validate the state address, callback address, storage results, alignment, capacity, or overlap.

For ordinary record construction:

- The state must permit the two four-byte field accesses.
- Storage used by the write cursor must accommodate every retained record.
- The callback must be callable whenever enumeration reaches it.
- Address arithmetic must support the accessed range and the subsequent signed count derivation.

A null callback is not explicitly rejected. If enumeration reaches a callback invocation, the supplied address is invoked regardless of validity.

## Behavior

### Entry and initial storage request

The routine first writes zero to the count field, then zero to the storage field. It initializes the upper return component to zero and the mutable status slot to the supplied callback address.

It calls F-6dd003795db7 with these ordered arguments:

1. Resource context.
2. Element width 8.
3. Zero.
4. Candidate count.
5. Zero.
6. Address of the mutable status slot.

The returned address becomes the record-write cursor and is written to the storage field. The routine then tests the status slot.

If the slot is nonzero, it skips enumeration, count derivation, empty-result handling, the second storage request, ordering, and the final count-field write. It returns with the upper half zero and the lower half taken from the slot.

The routine’s initial count-field write is zero, but the initial dependency cannot be assumed to preserve that field through aliases or other reachable state.

The initial storage request occurs even when the candidate count is zero. No explicit multiplication of the candidate count by eight is performed locally; width and capacity are separate dependency arguments.

### Candidate enumeration and retention

Enumeration occurs only when the status slot is zero after the initial request.

Candidates are visited from index zero while the unsigned index is less than the candidate count. For each candidate:

- The selection callback is invoked with callback context and index.
- A zero callback result causes the candidate to be skipped without a value-dependency call.
- A nonzero result causes F-95ac13ec38f8 to be called without explicit arguments.
- Its result is treated as an unsigned 32-bit value.
- The value is retained only if its lower 31 bits are not all zero.

Thus, both `0x00000000` and `0x80000000` are rejected. All other 32-bit values pass this value filter.

For a retained value, the routine writes the complete value at the current cursor, writes the candidate index four bytes later, and advances the cursor by eight bytes. The high bit is preserved in the stored value.

The cursor is not reloaded from the state field for each record. Changes to the state’s storage field therefore do not redirect subsequent record appends, although they can affect later count derivation and dependency arguments.

There is no per-record update of the state’s count field.

For candidate count `0xffffffff`, the final visited index is `0xfffffffe`; the loop exits when the index reaches the bound. This establishes the enumeration boundary, not the feasibility of the corresponding storage or execution.

### Deriving the count

After enumeration, the routine rereads the storage field. It subtracts that address from the final cursor using the visible signed 32-bit address representations, then applies a signed right shift by three. The resulting bit pattern is used as an unsigned 32-bit count.

Under valid contiguous storage, an unchanged storage field, and representable arithmetic, the result equals the number of records appended.

That interpretation is conditional. There is no separately maintained retained-record counter. An intervening change to the storage field can make the derived count differ from the actual number of writes. Out-of-range signed subtraction and negative signed-shift behavior are not specified as portable mathematical division.

### Zero derived count

If the derived count is zero, the routine:

1. Calls F-bf7242c98d06 with the resource context.
2. Writes zero to the storage field.
3. Tests the mutable status slot.
4. If the slot is zero, replaces it with the numeric bit pattern 6.
5. Writes zero to the count field.

No ordering-like call occurs, and the global location used for its fourth argument is not read by this path.

The empty-result dependency receives no explicit storage address. Whether it releases anything, and how it identifies resources, are unknown.

The status check occurs after that dependency returns. A nonzero slot left at that point is preserved rather than replaced with 6.

### Nonzero derived count and optional second request

For a nonzero count, the routine compares the derived unsigned count with the original candidate count shifted right by one.

The second storage request occurs only when:

**derived count < floor(candidate count / 2)**

Equality does not trigger it. A zero derived count follows the separate empty-result branch.

The second F-6dd003795db7 call receives:

1. Resource context.
2. Element width 8.
3. Original candidate count.
4. Derived count.
5. Storage address saved after enumeration.
6. Address of the same mutable status slot.

After this call, the routine writes the returned address to the storage field, unconditionally clears the status slot, and sets the upper return component to the saved pre-request address.

There is no local failure check before replacing the storage field. Any status written by this second request is discarded. The routine does not implement a fallback to the prior address.

### Ordering-like call and final publication

Every nonzero derived count reaches F-4d426a8054f4 with:

1. A value read from the state’s storage field while preparing the call.
2. The derived count.
3. Record width 8.
4. A value read from a global location while preparing the call.

The global read occurs after enumeration and after any second storage request. It is not an entry-time snapshot. Earlier callback invocations, value requests, or storage requests may change that global and thereby affect the fourth argument.

No relative evaluation order is established between the global read and the storage-field read used for the first argument. Both supply arguments to the ordering-like call; neither is specified here as occurring first.

The global’s contents may be comparator-related, but their type, meaning, mutability, and validity requirements are not established. The routine does not establish an ascending order, descending order, tie-breaking rule, or stability guarantee.

After F-4d426a8054f4 returns, the routine writes the derived count to the count field. It does not subsequently restore or rewrite the storage field. Finally, it returns the packed result.

## Side effects

### Direct memory effects

The routine directly:

- Clears the count field, then the storage field.
- Stores the initial storage result.
- Appends records using value-then-index writes.
- Rereads the storage field for count derivation.
- Either clears the storage field on an empty result or may replace it after a second request.
- On a nonempty result, reads the storage field and a global location to prepare the ordering-like call.
- Publishes the derived count after empty-result handling or ordering.

It does not directly write the global supplying the fourth ordering argument.

These operations are interleaved with external calls. The count field is not a reliable progress indicator during enumeration or ordering.

### Ownership and lifetime

No complete ownership contract is established.

The routine overwrites the incoming storage field without first reading or explicitly releasing its prior value. An existing live allocation therefore requires an external contract; this routine alone does not account for it.

The storage dependency may allocate, resize, reuse, or otherwise provide storage. The empty-result dependency may release context-associated resources. Both are inferred roles.

The address returned in the upper half may cease to identify live storage after the second request. Returning it does not authorize dereferencing or releasing it.

### Interference and errors

Unknown callees cannot be assumed to preserve globals, aliased state, record contents, or resource ownership. In particular, they may affect the global value later supplied to F-4d426a8054f4.

The status-slot address is exposed to storage requests. Whether it is retained or accessed by later calls is unknown; consequently, later external calls cannot be assumed incapable of changing the eventual lower return component through such an alias.

No synchronization, rollback, exception handling, explicit allocation-size validation, or invalid-address recovery is visible. The second request’s status is explicitly cleared rather than acted upon.

## Acceptance examples

These examples assume valid storage, representable ordinary address arithmetic, and no external interference except where expressly described.

### Initial status blocks processing

If the initial request returns address A and leaves a nonzero status S:

- A is written to the storage field.
- No callback, value request, empty-result call, or ordering-like call occurs.
- The ordering-operand global is not read.
- The return has upper half zero and lower half S.
- There is no final count-field write after the initial request.

### Empty input

For candidate count zero, if the initial request clears the status slot and preserves the storage field after its assignment:

- The initial request still occurs.
- No callback or value request occurs.
- The derived count is zero.
- F-bf7242c98d06 is called.
- The storage and count fields are subsequently written as zero.
- If cleanup leaves the status zero, the return has upper half zero and lower half 6.

### Selection and high-bit filtering

For three candidates:

- Index 0: callback returns zero.
- Index 1: callback returns nonzero; the value is `0x80000000`.
- Index 2: callback returns nonzero; the value is `0x80000005`.

There are two value requests and one appended record: value `0x80000005`, index 2.

The derived count is 1. Since half the original count rounded down is also 1, no second storage request occurs. The nonempty ordering-like call still occurs.

### Strict capacity threshold

For candidate count 8:

- Derived count 3 triggers the second request.
- Derived count 4 does not.
- Derived count zero follows empty-result handling instead.

If the second request receives saved address A and returns B, B is written to the storage field and A supplies the upper return half. Ordering receives the storage-field value read during its own call preparation, not an independently guaranteed copy of B.

### Global operand reflects earlier changes

Suppose the global initially contains operand X. If an earlier callback or storage request changes it to Y, and it remains Y until call preparation, F-4d426a8054f4 receives Y as its fourth argument.

This example requires no assumption that X or Y is a callable comparator. It also establishes no read order between that global and the storage field.

### Second-request status is discarded

If the second storage request writes nonzero status S, the routine clears the slot before ordering. If no later call changes it, the returned lower half is zero.

This behavior does not establish that the returned storage is usable.
