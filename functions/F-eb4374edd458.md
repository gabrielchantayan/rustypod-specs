# F-eb4374edd458

## Purpose

F-eb4374edd458 performs three ordered indirect invocations using a supplied receiver and an associated object reachable through that receiver. It also captures a 32-bit value between the first and second invocations and supplies that captured value to the third invocation.

The established behavior is dispatch and argument preparation. The available evidence does not establish what the invoked operations accomplish. In particular, it does not justify describing this function as initialization, rendering, allocation, cleanup, or event delivery.

This contract distinguishes:

- **Established static evidence:** operations represented in the supplied recovered source.
- **Inferred intent:** plausible interpretations that are not requirements.
- **Documented-only unknowns:** details that cannot be resolved from the supplied material.

No runtime tests have been performed.

## Behavior

### First indirect invocation

The function obtains an associated-object address from receiver offset `0x378`. Through that object’s first word, it locates a dispatch table and selects the target at table byte offset `0x0D4`.

The invocation has three represented arguments, in this order:

1. The associated-object address.
2. The adjustment-source value minus `0x61`, equivalent to subtracting decimal 97.
3. The literal `0x6000`, equivalent to decimal 24,576.

The representation contains separate accesses to the associated-object field for target lookup and for the first argument. It does not establish a single retained field value shared by both uses. Nor does it establish a left-to-right order among the reads used to prepare this invocation.

The subtraction is not shown as a bounded, checked, or saturating operation. Its exact signedness and overflow semantics are not established by the recovered expression. For values where ordinary subtraction is unambiguous and representable, the argument is the source value less 97. Boundary behavior requires ABI or instruction-level evidence before a wraparound rule can be made unconditional.

After this invocation returns normally, the function proceeds to the primary-value capture. Its return value, if any, is discarded.

### Primary-value capture

The function reads the primary-value cell and retains a four-byte value for later use.

This capture occurs:

- After the first indirect invocation returns.
- Before the second indirect invocation.
- Before the third invocation uses the captured value.

The capture therefore includes any change the first callee has already made to that cell, subject to the execution model’s visibility rules.

The later use is not represented as a fresh read of the primary-value cell. A change made by the second callee does not, by itself, replace the retained four-byte value.

### Second indirect invocation

The function uses the entry receiver’s current dispatch-table reference to select a target at byte offset `0x058`.

The recovered representation supplies five arguments, in this order:

1. The entry receiver.
2. A separately obtained value from the primary-value cell.
3. The value from the secondary-value cell.
4. A code-pointer value obtained through receiver dispatch-table offset `0x058`.
5. The unresolved entry-state-dependent value.

The fourth argument is itself a dispatch-table target value. It is not the return value of another invocation.

The target used for this invocation and the target value passed as its fourth argument are represented by separate lookup expressions. If the relevant receiver and dispatch-table contents remain unchanged during argument preparation, they identify the same target. Without a stability assumption, their equality is not guaranteed by an explicit snapshot.

Likewise, the primary-value argument is distinct from the earlier retained value. In a stable execution, the two reads produce equal values. The visible behavior nevertheless contains two read events, not a single capture reused for both purposes.

The supplied material does not determine the evaluation order among the target lookup and individual argument reads. It therefore does not establish whether the primary-value read occurs before the secondary-value read or before either dispatch lookup.

The fifth argument cannot be assigned a semantic meaning from the available evidence. The function visibly supplies it, but the source of its meaningful value, its required width under the real ABI, and whether the callee consumes it remain documented-only unknowns.

After a normal return, the function proceeds to the final invocation. No returned value is visibly consumed.

### Third indirect invocation

The function again resolves a target through the entry receiver’s dispatch table at byte offset `0x058`.

This lookup occurs after the second invocation. It is not represented as reuse of a previously saved target. A second callee that changes the receiver’s dispatch-table reference or the relevant table entry can therefore affect the third target, provided the resulting state remains valid.

The third invocation has three represented arguments:

1. The entry receiver.
2. The four-byte primary value retained before the second invocation.
3. The value from the final-value cell.

The final-value read belongs to preparation of this third invocation, after the second invocation has returned. It can consequently observe a change made by the second callee.

The recovered evidence flags this final transfer as having uncertain indirect-control-flow reconstruction. It presents the transfer as a call followed by return. The three represented argument values and fresh dispatch lookup are supported by the supplied representation; the exact original branch form and full ABI-level argument state are not independently established.
