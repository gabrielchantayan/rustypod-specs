# F-98a9aa5e9e94

## Purpose

F-98a9aa5e9e94 captures a selected integer element as a two-field result: the element’s address and the value read from that address.

Selection uses two fields in a caller-supplied descriptor: a base address and an element index. The function computes an address at a four-byte stride, reads one integer there, and then writes the address and captured value into caller-provided output storage.

The established behavior is an address-and-value capture, not a reference that automatically tracks subsequent changes. The function does not allocate storage, copy an array, validate an index, or call another function.

Interpreting the descriptor as an array descriptor is reasonable inferred intent. No array length, element count, allocation boundary, or ownership metadata is consulted.

## Behavior

### Address selection

The function reads the base-address field and the index field from the descriptor. Both values are needed before it can determine the selected address.

The available evidence does not establish which of these two descriptor reads occurs first. A consumer must not depend on one field being read before the other, especially if the descriptor is concurrently modified or mapped to storage with read side effects.

Selection uses an index scale of exactly four bytes. There is no additional displacement after that scaling, no lower-bound adjustment, and no bounds check.

An index of zero selects the base address itself. A positive index selects a higher address when the arithmetic is valid. A negative index can select a lower address when the arithmetic and resulting memory access are valid. The function does not explicitly reject negative indices.

### Value capture and output ordering

After selecting the address, the function reads the integer stored there. That read completes, in the source-level ordering, before either output assignment.

It then performs two ordered output assignments:

1. Store the selected address, converted to an integer, in the first output slot.
2. Store the previously captured integer in the second output slot.

The second assignment uses the captured value. It does not reread the selected element after writing the address field.

This ordering matters when output storage overlaps the selected element or the descriptor. The address calculation and selected-element read precede output modification. Thus, under a valid execution model that permits the overlap, an output write cannot retroactively change the address already selected or the value already captured.

The first output store precedes the second in the source-level behavior. The evidence does not promise an atomic two-field update or a synchronization protocol through which another execution context can safely observe the pair.

### Completion and failure

On normal completion, both output fields have been written and control returns without an explicit result value.

There is no explicit error return, exception construction, diagnostic, fallback value, or cleanup operation. Null addresses, inaccessible storage, unsuitable alignment, invalid arithmetic, and unrepresentable address conversions are not checked locally.

Consequently, this contract provides no successful-result guarantee for invalid inputs. Exact failure behavior is target-dependent and is not established by the supplied evidence.

In particular, arithmetic must not silently be specified as wrapping. Multiplying the index by four and adding it to the base are expressed through integer arithmetic before the selected integer is read. Overflow behavior and address interpretation require the original execution model. Descriptor-field address formation also requires valid arithmetic for adding offsets 20 and 24 to the descriptor address.
