# F-317ac8669bcd

## Purpose

F-317ac8669bcd coordinates an ordered sequence of dependency calls, preserves the result of its principal operation, and conditionally copies a 16-bit field from a supplied object into a field of an object obtained from another dependency.

The established behavior has three parts:

- Obtain an opaque value and pass it, the supplied object address, and a zero argument to a preparation dependency.
- Invoke the principal dependency with both original arguments, preserving its result for return.
- Perform conditional follow-up work, including a possible 16-bit field transfer.

The names “preparation,” “principal,” and “follow-up” describe call position, not established subsystem semantics. The supplied evidence does not establish the objects’ types, the fields’ meanings, or whether the second argument represents a Boolean flag, mode, count, or another value.

## Behavior

### Ordered dependency calls

On an execution that reaches each successive operation normally, the initial sequence is unconditional:

1. Call F-fdd8589eca2d with no explicit arguments.
2. Pass its returned value to F-3e5212464798 as the first argument, followed by the original object address and a zero-valued third argument.
3. Call F-a3c410f12096 with the original object address and original control value.
4. Preserve the result of F-a3c410f12096 for the eventual return.

The first result from F-fdd8589eca2d is not directly dereferenced by this function. Its suitability for F-3e5212464798 is a dependency-level precondition whose details are unknown.

The result of F-3e5212464798 is not used by the visible caller.

### Control-dependent follow-up

If the control value is nonzero, call F-5c5958cfd5fe with no explicit arguments after F-a3c410f12096 returns.

If the control value is zero, omit that call.

This decision does not depend on the principal result. Any meaning assigned to that result by F-a3c410f12096 does not alter the caller’s visible control flow.

### Conditional field transfer

After the preceding calls, evaluate the transfer conditions in the following order:

1. Read the 16-bit field at the supplied object address plus `0xE6`.
2. Determine whether that value is nonzero.
3. Only if it is nonzero, evaluate whether the original control value is nonzero.
4. Only if both conditions hold, call F-fdd8589eca2d again.
5. Read the 16-bit field at that newly returned address plus `0x80`.
6. Only if that destination-check field is zero, call F-fdd8589eca2d once more and perform the transfer.

The first source-field read occurs even when the control value is zero. Zero control therefore suppresses the optional dependency call and the transfer, but does not make the supplied object’s field unnecessary or inaccessible-safe.

When the transfer occurs, its destination is the address returned by the final F-fdd8589eca2d call plus `0x80`. Its value is a fresh 16-bit read from the supplied object address plus `0xE6`, performed after that final dependency call returns.

The transfer copies the 16-bit representation without a visible arithmetic transformation. The earlier comparisons test only zero versus nonzero; interpreting a tested field as signed does not change that distinction.

### Repeated lookups and fresh reads

The repeated F-fdd8589eca2d calls must not be collapsed into a single lookup in this contract:

- The initial result is used as an argument to F-3e5212464798.
- A later result supplies the address of the destination field being checked.
- A final result, when obtained, supplies the address of the field being written.

There is no established guarantee that these results are equal.

Consequently, the function can check a zero field in one object and write a field in another object. The field at the actual write destination is not separately checked for zero.

Likewise, the source field is read separately for eligibility and for the copied value. The copied value need not equal the value that initially passed the nonzero test. If an intervening dependency changes that field to zero, the visible transfer can write zero.

All successful paths then return the preserved principal result.

- One 16-bit source-field read after the principal call and, for nonzero control, after F-5c5958cfd5fe.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Each assumes all reached calls return normally and all reached memory accesses are valid.

### Zero control still requires the source read

- The initial lookup, F-3e5212464798, and F-a3c410f12096 occur in that order.
- F-5c5958cfd5fe is omitted.
- The source field at offset `0xE6` is read.
- No destination lookup, destination-check read, or direct destination write follows.
- The preserved principal result is returned.

This holds whether the source field is zero or nonzero.

### Nonzero control and zero source

- F-5c5958cfd5fe occurs before the source read.
- No later lookup or destination access occurs.
- The principal result is returned unchanged.

### Nonzero destination-check field

- The destination-check field is read.
- The third lookup is omitted.
- No direct write occurs.

### Stable objects permit the expected transfer

- The later lookup is performed twice.
- The final destination field receives the 16-bit value `0x1234`.
- The function returns the principal result, not the copied value.

### The checked and written objects can differ

- The zero test is performed on A.
- The write targets B.
- B’s previous field value does not control whether the write occurs.

### A source mutation changes the transferred value

Suppose the source eligibility read is nonzero, but the final lookup changes the source field to zero before returning:

- The transfer path remains selected.
- The fresh source read supplies zero.
- Zero is written to the final destination.

### Principal-result contents do not gate follow-up
