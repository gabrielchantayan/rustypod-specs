# F-9d39dcd3197c

## Purpose

F-9d39dcd3197c selects a slot associated with an object, conditionally processes that slot’s inclusive range, and chooses between an indirect notification sequence and a continuation sequence.

**Established static behavior:** selection depends on mode, slot counters, and lookup results. Processing can decrement or clear a counter. Notification is restricted to the requested slot and gated by a character-sized completion value. Continuation uses an object field that can be populated through a dependency.

**Inferred intent:** the counters appear to track remaining processing opportunities; the notification sequence appears to signal completion; the continuation sequence appears to arrange further work. These meanings are not established contracts of the called functions. In particular, the dependency receiving 44 may be an allocator, but allocation and ownership are not established.

## Interface

The function accepts four inputs and has no specified return value.

| Input | Representation | Visible role |
|---|---|---|
| Object | Pointer to storage accessed through 32-bit words and one byte write | Supplies dispatch information, slot state, completion state, and a continuation value. |
| Requested slot | Signed 32-bit integer | Initial selected slot and identity against which notification eligibility is tested. |
| Mode | Signed 32-bit integer | Zero enables alternate-slot search; any nonzero value resets the requested counter to ten. |
| Continuation argument | Opaque 32-bit value | Saved on entry and supplied unchanged to F-6904f7699031 if that call is reached. |

The supplied representation uses four-byte words and pointer-like values. The following layout describes accesses, not a complete object type.

| Byte offset | Access and meaning |
|---|---|
| `0x00` | Four-byte dispatch-table reference. |
| `0xE8` | A 32-bit word converted to a character-sized value for the completion check; its first addressed byte is written separately. |
| `0x1C0` | Four-byte continuation value. |
| `0x1C4 + 4 × slot` | Signed 32-bit counter. |
| `0x2C + 24 × slot` | Signed 32-bit range start. |
| `0x30 + 24 × slot` | Signed 32-bit range end. |

The indirect notification entry is at byte offset `0x58` within the referenced dispatch table.

Additional storage consists of:

- An external table of four-byte entries indexed by the selected slot.
- Three external four-byte notification values, designated here as **shared**, **first-specific**, and **second-specific**.
- A 40-byte temporary area passed to the processing dependency.
- A four-byte temporary status area whose first byte controls traversal.

Neither temporary area is visibly initialized by this function before use.

### Preconditions

There is no visible validation. Required accessibility includes the object fields selected by the supplied index, lookup-result storage, referenced resource fields, external table entries, and dispatch entries. Dependencies may impose further requirements.

The alternate search covers slots zero through three, but this does not establish that requested slots are restricted to those values. A different requested slot can be used directly for addressing and lookup.

Address calculations and signed arithmetic must have defined behavior under the actual execution model. Behavior for invalid addresses, unrepresentable calculations, or dependency contract violations is not established.

## Behavior

### 1. Slot selection and final lookup

The selected slot initially equals the requested slot.

When mode is zero, examine candidates zero, one, two, and three in order:

1. Read the candidate’s counter.
2. Only if that counter is nonzero and the candidate differs from the requested slot, call F-0260b20d4c56 with the object and candidate.
3. Select the first candidate whose lookup result is nonzero, then stop searching.

The counter test is nonzero, not positive: negative counters qualify. The counter read precedes the requested-slot exclusion in the supplied expression, so the requested candidate’s counter is still read when encountered. Candidate indices pass through a character-sized conversion before lookup; values zero through three are unaffected.

If no candidate is selected, retain the requested slot.

When mode is nonzero, omit the alternate search and write ten to the requested slot’s counter. The requested slot remains selected.

After either route, call F-0260b20d4c56 with the object and selected slot. This final lookup is separate from any successful search lookup. Its result is not required to match the earlier result.

### 2. Resource preparation and the processing gate

If the final lookup is zero, proceed to the **ordinary counter decision** described below. No resource access or counter decrement occurs on this route.

For a nonzero final lookup, retain that lookup result as a reference to a four-byte resource value:

1. Read its first word to locate a resource, then inspect the signed 32-bit field at resource offset `0x14`.
2. If that field is nonzero, call F-01a3521ad08a without visible arguments.
3. Read the selected counter. If it equals ten, call F-9c31c3e85ab1 with the then-current first word of the lookup result and the value one.
4. Read the selected counter again to determine whether it is positive.

The two preparation dependencies may run even when no range processing follows. Resource words and counters used after a dependency are read from storage as specified; dependency preservation is not assumed.

If the final positivity check finds a nonpositive counter, proceed **directly to the slot-identity decision**. There is no additional counter read or ordinary positivity check on this route.

If it finds a positive counter, enter range processing.

### 3. Range processing

Decrease the positive selected counter by one, then read the selected range start as the current signed 32-bit position. A single decrement from a positive signed 32-bit value is representable.

Before each processing call, compare the current position with the currently read range end. Continue only while the position is less than or equal to that end.

For each position, call F-fbe427d8956f with:

- The current first word of the retained lookup result.
- The 40-byte temporary area.
- The current position.
- The four-byte external table entry for the selected slot.
- The four-byte temporary status area.

The resource word and external table entry are obtained for each call, rather than captured once for the traversal. The supplied representation does not establish an order among the argument reads within an individual call.

After the call, inspect the first status byte.

#### Zero status byte

Read the selected range start again and compare the current position with that start plus three.

- If the current position is strictly greater than the newly read start plus three, write zero to the selected counter and proceed **directly to the slot-identity decision**.
- Otherwise, stop traversal and proceed to the **ordinary counter decision**.

This threshold is based on position relative to the reread start, not on the number of successful processing calls. With an unchanged start and representable arithmetic, an offset of three does not clear the counter; an offset of four does.

#### Nonzero status byte

Read the range end and compare it with the current position. Then increment the position by one. If the comparison found equality, write zero to the selected counter.

Return to the loop condition, which reads the range end again. Clearing the counter does not itself terminate traversal, and the loop does not recheck counter positivity.

For an unchanged end and a representable increment, processing the endpoint makes the next loop condition false. A dependency-induced change to the range end can change this outcome.

If the initial start exceeds the end, no processing call occurs. The counter decrement has nevertheless already occurred.

### 4. Ordinary counter decision and slot identity

The **ordinary counter decision** is reached only:

- After a zero final lookup.
- After ordinary traversal exit, including a zero-status stop that did not explicitly clear the counter.

It reads the selected counter:

- Positive: take the continuation path.
- Zero or negative: proceed to the slot-identity decision.

Two routes bypass this read entirely:

- A nonzero final lookup followed by a nonpositive post-preparation counter check.
- A zero status that explicitly clears the counter because the position exceeds the threshold.

At the **slot-identity decision**:

- Selected slot different from requested slot: take the continuation path.
- Selected slot equal to requested slot: inspect the completion value and potentially notify.

Thus, this invocation does not issue the requested-slot notification sequence merely because an alternate slot has finished.

### 5. Completion check and notification

Read the 32-bit word at object offset `0xE8` and convert it to a character-sized value.

If the converted value is nonzero, return without either notification call or the continuation sequence.

Otherwise:

1. Write one to the single byte at object offset `0xE8`.
2. Read the external shared notification value into a saved local value.
3. Perform the first indirect notification.
4. Perform the second indirect notification.
5. Return, subject to the uncertain transfer representation noted under **Evidence**.

Both notifications receive the object followed by two four-byte arguments. Their value sources differ:

| Notification | Argument after the object | Final argument |
|---|---|---|
| First | A separate global read of the shared value, not the saved local | First-specific external value |
| Second | The saved shared value captured before the first call | Second-specific external value, read after the first call |

The first call is therefore not specified as receiving the captured shared value. In a stable environment, its separate read and the saved read produce the same bits; that equality is not guaranteed by the visible read structure.

Each notification resolves the dispatch-table reference from the object and obtains the entry at offset `0x58` anew. The first notification can therefore affect the second target. The second-specific value is also obtained after the first call. No relative order is established among a call’s target resolution and argument reads beyond the explicit saved read and call sequencing.

The completion value is not rechecked between notifications. Its byte write precedes both calls.

### 6. Continuation sequence

Read the four-byte continuation value at object offset `0x1C0`.

If it is nonzero, skip setup. If it is zero:

1. Call F-8157a180d901 with the numeric argument 44, equivalently `0x2C`.
2. Store its returned four-byte value in the continuation field.
3. Test that returned value for zero.
4. On zero, call F-a817d8d58c10, represented as nonreturning.
5. On nonzero, call F-861a66c91b48 with the object, the returned value, zero, and zero.

The established contract is a call receiving 44 and a stored, zero-tested result. It does not establish a 44-byte allocation, a pointer result, or ownership acquisition.

After existing-value reuse or successful setup:

1. Read the current continuation field and call F-6904f7699031 with it and the saved fourth input.
2. Read the continuation field again and call F-ec4cfa552cce with that value.
3. Return.

The setup dependency can change the field before the first final call, and F-6904f7699031 can change it before the second. Neither final call is guaranteed to receive the originally returned setup value.

## Side effects

Direct writes by this function are:

- A requested-counter reset to ten in nonzero mode.
- A selected-counter decrement before range traversal.
- Selected-counter clearing at the specified status threshold or endpoint.
- A one-byte completion-state write before notification.
- Storage of the result from F-8157a180d901, including a zero result.

Additional effects may arise from every dependency and indirect notification.

This function contains no explicit rollback. The ordering establishes that its writes happen before the subsequent calls described above. It does **not** establish that those values remain observable after a later dependency fails, does not return, or otherwise changes control flow: that dependency may overwrite the same storage first.

No release operation is visible. Whether any dependency allocates, retains, transfers, or releases storage is unknown. Passing a resource value or continuation value does not itself establish ownership transfer.

The temporary areas belong to this invocation. No supported retention lifetime beyond the invocation is established. Dependency retention of their addresses would require an external lifetime contract.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, dependencies return normally, relevant storage remains unchanged except for this function’s writes, and arithmetic is representable.

1. **Reset and complete an inclusive range.**  
   Nonzero mode writes ten to the requested counter. A nonzero final lookup leads to the counter-ten dependency. The counter becomes nine before traversal. Nonzero status through the unchanged endpoint clears the counter. Ordinary exit reaches the counter decision, then requested-slot completion handling. An unset completion value causes its byte write and both notifications.

2. **Alternate selection requires another lookup.**  
   Candidate zero differs from the requested slot, has a nonzero counter, and produces a nonzero search lookup. It is selected, but a separate final lookup still occurs. If that final lookup returns zero, no resource dereference follows.

3. **Nonpositive counter takes the direct identity route.**  
   The final lookup is nonzero and the post-preparation positivity check reads zero or a negative value. There is no decrement, traversal, or additional ordinary counter read. Matching slots lead directly to completion handling; different slots lead to continuation.

4. **Early zero status retains the decremented counter.**  
   A counter of two becomes one. With an unchanged start of twenty, zero status at position twenty-three stops traversal without clearing the counter. The ordinary counter decision reads one and selects continuation.

5. **Later zero status bypasses the ordinary counter decision.**  
   With start twenty, zero status at position twenty-four clears the counter and goes directly to slot identity. Matching slots reach completion handling; alternate slots reach continuation.

6. **Reversed range still decrements.**  
   A counter of one becomes zero before an initially reversed range is checked. No processing call occurs. Ordinary exit reads the zero counter and reaches slot identity.

7. **Absent resource with positive counter.**  
   A zero final lookup and positive selected counter cause continuation without decrementing the counter.

8. **Notification uses distinct reads.**  
   The shared value is captured before the first notification, while that first call uses a separate shared-value read. If the first notification changes the shared global, the second notification still uses the saved value. Changes to the dispatch table or second-specific value can affect the second call.

9. **Zero setup result.**  
   A zero continuation field causes F-8157a180d901 to receive 44. If it returns zero, zero is stored before F-a817d8d58c10 is invoked. Assuming that dependency is nonreturning, no normal continuation calls follow. This establishes setup failure handling, not allocation failure semantics.

10. **Continuation field changes between calls.**  
    If F-6904f7699031 changes the continuation field, F-ec4cfa552cce receives the newly read value, not necessarily its predecessor’s argument.

## Uncertainties

The following remain **documented_only**:

- Valid requested-slot bounds, full object extent, and external table bounds.
- Resource types and the meanings of external notification values.
- Dependency mutation, errors, retention, ownership, and reentrancy.
- Whether F-8157a180d901 allocates anything, what 44 means to it, and whether its result denotes storage.
- Whether F-a817d8d58c10 is actually nonreturning; no fallback contract is supplied if that representation is wrong.
- Whether each processing call initializes the first status byte. Without such a write, the supplied representation does not establish a reliable status outcome.
- Character signedness and target byte order. Conversion of a word to a character-sized value and writing its first addressed byte must not be assumed universally equivalent.
- Overflow behavior for start plus three, position increment, and slot-derived arithmetic. No wrapping, saturation, or bounds enforcement is established.
- Concurrent access and synchronization. No synchronization is visible.
- Exact machine-level transfer semantics of the second notification.

## Evidence

This contract is based only on the supplied static representation and opaque dependency mapping. No runtime tests have been performed.

Established evidence comprises access widths, offsets, branches, comparisons, call arguments, explicitly repeated reads, and ordering across calls. In particular, the nonpositive post-preparation route bypasses the ordinary counter decision; notification uses a saved shared-value read plus a separate first-call read; and the setup dependency’s argument and result handling do not establish allocation semantics.

“Completion,” “continuation,” “resource preparation,” and “remaining processing opportunities” describe inferred roles rather than verified dependency meanings.

The second indirect notification is represented as an invocation followed by return, but its recovered transfer form is explicitly uncertain. The notification sequence above follows that representation without claiming independently verified machine-level control flow.
