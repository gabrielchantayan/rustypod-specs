# F-0c21b5cad025

## Purpose

F-0c21b5cad025 attempts a transfer from an object’s current position into a caller-supplied destination. It selects either a memory-backed transfer operation or an object-provided callback.

The function returns a 32-bit status:

- **0:** the transfer count used by the function is greater than or equal to the requested count.
- **0x55:** the initial position is outside the permitted starting range, or the transfer count is less than the request.

A short transfer is not transactional. The function updates the position before reporting the short-transfer error and performs no direct rollback of destination changes.

“Object,” “position,” “size,” and “transfer count” describe roles inferred from the operations. They do not establish a complete stream abstraction, allocation model, or external API contract.

All conclusions below derive from static evidence. No runtime tests have been performed.

## Interface

### Arguments

The function accepts three arguments:

1. **Object reference:** a pointer to storage accessed as 32-bit words.
2. **Destination value:** a 32-bit value passed unchanged to the transfer dependency. Its apparent role is an address, but the external primitive’s interpretation is not supplied.
3. **Requested count:** an unsigned 32-bit quantity.

The accessed object fields are:

| Word index | Byte offset in the supplied representation | Role |
|---|---:|---|
| 0 | 0 | Backing-base value used in memory-backed source-address arithmetic |
| 1 | 4 | Size or limit |
| 2 | 8 | Current position |
| 5 | 20 | Callback selector and invocation target |

Words 3 and 4 are not directly accessed. These offsets describe the supplied four-byte-word representation, not a complete public structure definition.

The object words have signed 32-bit storage in the supplied representation. The position, size comparisons, available-count arithmetic, source-address arithmetic, and transfer-count comparisons use unsigned 32-bit values. A high-bit-set field must not automatically be interpreted as a negative size or position.

### Result

The result is a 32-bit status, not a byte count. No separate transferred-count output is supplied.

After a transfer dependency returns normally, the function directly writes an updated position. That write reflects the count used by this function; it does not independently verify destination changes.

### Preconditions and unchecked conditions

The object must support the accesses taken on the selected path. There is no explicit null-object check.

Memory-backed operation requires whatever address validity, capacity, alignment, and overlap conditions the external transfer primitive imposes. Callback operation requires a valid callable target at the **second** access to word 5, with a compatible calling interface.

The function does not explicitly validate:

- Destination validity or capacity.
- Backing allocation extent.
- Source-address representability as valid memory.
- Source and destination overlap.
- Callback target validity or stability between accesses.
- Whether the callback result accurately describes transferred bytes.

These are necessary execution conditions where applicable, not checks performed by this function.

## Behavior

### 1. Capture and validate the initial position

The function first reads word 2 and retains its value as an unsigned 32-bit initial position. It then reads word 1 and compares that size value with the captured position using unsigned ordering.

If the captured position is greater than or equal to the size:

1. F-4457a9a44a68 is invoked with a diagnostic-format argument and the captured position.
2. The function returns **0x55**, provided the diagnostic call returns normally.

On this path, the function does not directly access the callback field, invoke either transfer mode, or write the position field.

The request does not affect this check. Consequently:

- A position exactly equal to the size is rejected.
- A position greater than the size is rejected.
- Size zero and position zero are rejected.
- A zero-byte request does not bypass rejection.

The diagnostic dependency’s effects are unknown. Absence of a direct position write does not establish that the position, other object fields, globals, or memory remain unchanged.

### 2. Test the transfer mode

For a valid starting position, the function reads word 5 to test whether it is null.

- A null value selects memory-backed operation.
- A non-null value selects callback operation.

This first access is a selector test, not an established capture of the callback target for later reuse.

On the callback path, word 5 is accessed **again** to obtain the invocation target. Without field stability, the value used for the call need not equal the value used for the null test. In particular, the non-null test does not establish that the later invocation target is still non-null or callable.

On the memory-backed path, no second callback-field access is shown. A later change to word 5 does not cause this function to reconsider its selected branch.

### 3. Memory-backed operation

After the null callback test, the function reads word 1 again and computes the available count by subtracting the captured initial position.

Both operands participate as unsigned 32-bit quantities. The subtraction therefore produces a result modulo 2³². With a stable size field, the successful initial check ensures a positive available count. If the second size value differs, that earlier check does not constrain the subtraction to a positive, non-wrapped remainder.

The selected transfer count is the unsigned minimum of:

- The requested count.
- The available count computed from the second size access.

The function reads word 0 to form the source value. Although that backing-base word has signed storage, adding it to the unsigned captured position converts it to unsigned 32-bit form. The resulting source value is:

**backing-base bit value + captured initial position, modulo 2³².**

This wrapping arithmetic is established. Whether the resulting 32-bit value denotes valid memory, and how the external primitive interprets it, remain separate unknowns.

The external memory-transfer dependency receives three arguments in this order:

1. Original destination value.
2. Computed 32-bit source value.
3. Selected transfer count.

Its return value, if any, is ignored. The selected count becomes the count used for the position update and final status comparison. The function does not obtain or validate an actual-progress count from this dependency.

A zero request still reaches the primitive with a selected count of zero. There is no zero-count shortcut around the invocation. Whether the primitive permits particular source and destination values for that invocation is not established.

### 4. Callback operation

After a non-null first access to word 5, the function reads word 5 again and invokes the target obtained from that second access.

The arguments are:

1. Original object reference.
2. Captured initial position.
3. Original destination value.
4. Full requested count.

The request is not reduced to the declared remaining size. The initial range check restricts only the starting position.

The callback result is used as an unsigned 32-bit transfer count. No separate error channel is examined. The function does not reject or clamp a result that:

- Exceeds the requested count.
- Exceeds the declared remaining size.
- Produces an ending position beyond the declared size.
- Causes the position addition to wrap.

If a callback-specific convention uses a negative signed result as an error indication, a corresponding high unsigned count may instead be accepted here. Such a convention is not handled explicitly.

The returned count does not prove how many destination bytes changed. Callback memory effects, ownership rules, and failure conventions remain unknown.

### 5. Update the position

After either transfer dependency returns normally, the function writes word 2 using:

**captured initial position + transfer count, modulo 2³².**

For memory-backed operation, the count is the selected count passed to the primitive. For callback operation, it is the callback’s result interpreted as unsigned 32-bit.

The function does not reread the position before this calculation. A position written by the callback or memory-transfer dependency is therefore superseded by this direct write if execution reaches it.

This write occurs before the short-transfer comparison and before either short-transfer diagnostic.

### 6. Determine the final status

The function compares the transfer count with the requested count using unsigned ordering.

If the count is less than the request:

1. F-4457a9a44a68 is invoked with a diagnostic-format argument alone.
2. F-4457a9a44a68 is invoked with another diagnostic-format argument, followed by the requested count and transfer count.
3. The function returns **0x55**, assuming both calls return normally.

Otherwise, it returns **0** without a direct diagnostic invocation.

Success does not require equality. An excessive callback count is accepted and used in full in the position calculation.

No direct position write follows the short-transfer diagnostics. Thus, the arithmetic update is established as this function’s own write, but it is not an unconditional final-state guarantee if diagnostics can modify relevant memory.

## Side effects

### Object and destination state

The only explicit field assignment is the post-transfer write to word 2. It occurs on successful and short-transfer paths, but not on the initial-range-rejection path.

Transfer dependencies may produce additional object effects. In particular:

- A callback receives the original object reference.
- A destination that aliases object storage could allow a transfer dependency to alter object fields.
- A dependency-written position is overwritten by the function’s later position update if that update is reached.
- Other dependency changes are not explicitly undone.

Memory-backed destination effects depend on the external primitive. Callback destination effects depend on the callback. Neither mode supplies independent evidence that the reported count matches actual destination modification.

There is no direct rollback after a short transfer.

### Diagnostics

Direct diagnostic invocations occur:

- Once after initial-range rejection.
- Twice, in order, after a short transfer.
- Not on the ordinary success path.

Exact output text, output destination, formatting behavior, and diagnostic failure behavior are not established.

### Ownership and lifetime

No direct allocation or release operation is shown. No ownership transfer is explicitly expressed by the visible interface.

This does not establish that dependencies preserve allocations, retain no references, or release no memory. Their ownership and lifetime effects are **documented_only** unknowns.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, object fields remain stable during the relevant reads, dependencies return normally, and dependencies do not alter the final state being described.

### Exact memory-backed transfer

Given size 100, position 20, a null callback field, and request 30:

- The selected count is 30.
- The primitive receives the backing-base value plus 20, reduced modulo 2³², as its source value.
- The function writes position 50 and returns 0.
- No diagnostic call occurs.

### Memory-backed short transfer

Given size 100, position 90, a null callback field, and request 20:

- The selected count is 10.
- The function invokes the primitive, then writes position 100.
- It invokes both short-transfer diagnostics in order and returns 0x55.
- It performs no direct destination rollback.

### Zero request within and outside the starting range

Given size 100, position 40, a null callback field, and request zero, the primitive is still invoked with count zero. The function then writes position 40 and returns 0.

Given size 100, position 100, and request zero, the function instead invokes the initial-range diagnostic and returns 0x55 without a direct position write or transfer invocation.

### Callback request exceeds the remaining size

Given size 100, position 90, request 50, and a stable callable callback reporting 50:

- The callback receives request 50, not 10.
- The function writes position 140.
- It returns 0.

No ending-position bound is enforced.

### Callback reports a short count

Given size 100, position 20, request 8, and a callback reporting 3:

- The function writes position 23 even if the callback wrote another position.
- Both short-transfer diagnostics follow that write.
- The function returns 0x55.

### Callback over-reports and the position wraps

Given size 100, position 10, request 1, and callback result 4,294,967,295:

- The result exceeds the request under unsigned ordering.
- The position addition wraps to 9.
- The function returns 0.

This accepts the reported count; it does not verify an actual transfer of that extent.

### Source-value arithmetic wraps

Given a backing-base word with bit value 4,294,967,280, size 100, position 32, a null callback field, and request 1:

- The computed source value is 16.
- The selected count is 1.
- If the primitive returns normally, the function writes position 33 and returns 0.

The arithmetic is defined by the supplied unsigned 32-bit expression. Validity of source value 16 as memory is not established.

### Callback field differs between accesses

If the selector access is non-null but the invocation-target access yields another valid compatible callback, that second target is invoked.

If the second access instead yields null or an invalid target, the earlier null test provides no protection. The supplied function establishes no successful-return or error-status outcome for that invalid invocation.

### Size differs between accesses

Suppose the initial size read yields 100, the captured position is 90, the callback selector is null, the second size read yields 80, and the request is 20.

The initial check passes. The available-count subtraction yields 4,294,967,286 modulo 2³², so the selected count is 20 rather than a bounded remainder of the first size. If the primitive returns normally, the function writes position 110 and returns 0.

This is an arithmetic consequence under the stated differing reads, not a concurrency guarantee.
