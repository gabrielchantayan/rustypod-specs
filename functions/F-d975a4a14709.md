# F-d975a4a14709

## Purpose

F-d975a4a14709 applies a dependency-gated state update for an unsigned candidate value.

Candidates below 2 produce no direct state access and no dependency invocation. Other candidates are submitted to F-2b2cf4a4fe41. A nonzero result from that dependency enables two local operations:

- Replace an unsigned field with the candidate when the candidate lies inclusively between two observed unsigned field values.
- Increase a signed field by one when that field is nonzero, independently of whether the replacement occurred.

These are established operational properties, not application-level meanings. The available evidence does not identify what the candidate represents, why the dependency gates the update, or what the signed field counts.

The contract below describes normally completing execution. Invalid storage, unrepresentable arithmetic, and abnormal dependency behavior have no established recovery contract.

## Behavior

### Eligibility and dependency gate

An unsigned candidate of 0 or 1 makes the invocation locally inert: the function returns without calling the dependency or directly accessing the listed object fields. This path contains no address validation.

For every other candidate, F-2b2cf4a4fe41 is invoked once with the state address, candidate, and zero, in that argument order. No listed field is directly accessed by F-d975a4a14709 before that invocation returns.

A zero dependency result ends local processing. This guarantees no subsequent direct field access by this function; it does **not** guarantee that the object or any external state remains unchanged, because the dependency has already executed.

Every nonzero dependency result enables the local updates. Its sign and magnitude do not otherwise affect local behavior. The evidence does not establish that zero means failure or that nonzero means success.

### Conditional replacement

The candidate replaces the upper field exactly when both inclusive comparisons hold at the relevant reads:

- The observed lower value is no greater than the candidate.
- The candidate is no greater than the observed upper value.

The lower comparison is decisive for whether the upper comparison field is accessed. When the lower value exceeds the candidate, there is no direct upper-field read for this decision and no upper-field write.

When the lower comparison passes but the upper comparison fails, the upper field is read but not written.

When both comparisons pass, the upper-field assignment is required. Equality does not suppress it: a candidate already equal to the upper value still causes a write of that same value. Equality with the lower value is also accepted.

The lower field is never directly modified by this function.

All comparison values come from storage after the dependency returns. There is no preserved pre-call field snapshot. A dependency mutation can therefore change a previously acceptable candidate into an unacceptable one, or the reverse.

With stable storage, a performed replacement cannot increase the observed unsigned upper value, because the write is conditional on the candidate being no greater than that value. This is a local property of the comparison and assignment, not a synchronization guarantee.

### Conditional increment

The counter operation is independent of the replacement decision. Once a nonzero dependency result has enabled local processing, normal completion of the comparison and possible replacement is followed by counter handling.

A zero counter is left unwritten. A nonzero counter is increased by one and written back. Negative values are eligible; there is no positivity requirement.

For stable storage and representable arithmetic:

| Observed counter | Required resulting counter |
|---:|---:|
| 0 | 0, without a counter write |
| −2 | −1 |
| −1 | 0 |
| 1 | 2 |
| 2,147,483,646 | 2,147,483,647 |

The zero test and the value used for addition are distinct logical reads in the supplied expression. A contract for asynchronously changing storage cannot assume they observe the same value. The ordinary examples in this document assume they do.

There is no saturation, overflow check, or special handling for the largest signed value. Under the 32-bit interpretation, adding one to 2,147,483,647 is not representable as a signed value of the same width. The execution model needed to determine the outcome is not supplied; wraparound is not promised.

## Side effects

### Direct memory effects and ordering

Only the upper field and counter field are possible direct write destinations. Each has at most one direct write per invocation in the supplied body.

The observable local dependencies impose the following ordering:

- Dependency execution precedes every local object-field access.
- The lower observation precedes any upper observation.
- An upper observation, when reached, precedes any upper replacement.
- The bound-related accesses finish before the counter zero test.
- A nonzero counter test precedes the counter value acquisition for addition and the resulting write.

Consequently, failure during an earlier access can prevent later accesses. For example, counter handling is not guaranteed after a fault during an upper-field write.

This ordering describes the supplied expression-level behavior. It does not establish a machine-instruction trace, volatile-access contract, memory barrier, atomic operation, or inter-thread ordering guarantee.

### Ownership, lifetime, and external state

The body contains no explicit allocation, release, reference-management operation, or direct global-state access.

Those absences apply only to the visible local behavior. The dependency may have effects on object storage, globals, external systems, ownership, or lifetime. None are established or excluded by its call site.

On a nonzero dependency-result path, the required object storage must remain valid for the later local accesses. The function does not reacquire the object or check whether the dependency invalidated it.

### Errors and partial effects

There is no explicit error result, validation failure report, rollback, or retry.

The function does not validate:

- Address validity or accessible extent.
- Alignment or memory permissions.
- Consistency of the lower and upper fields.
- Continued lifetime after the dependency returns.
- Safety of the signed increment.
- Representability of address calculations.

Effects that have already occurred are not explicitly undone if a later operation fails. In particular, the dependency may already have changed state before a local access fails, and an upper-field replacement may precede a counter-related failure.
