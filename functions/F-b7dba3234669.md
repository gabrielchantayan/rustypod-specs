# F-b7dba3234669

## Purpose

F-b7dba3234669 looks up an exact, nonempty byte sequence in a packed, globally selected table and returns an associated 16-bit value.

**Established behavior:** Lookup first selects a root record using binary search, then consumes the remaining input through either adjacent-byte continuation records or lists of child-record offsets. Success requires the record reached after the final input byte to carry a terminal-value marker.

The return value is zero both for lookup failure and for a successful match whose stored value is zero. The interface provides no separate success indicator.

**Inferred intent:** The representation is a compact trie with compressed single-successor paths. This interpretation explains the layout but does not establish how tables are constructed, validated, or owned.

## Behavior

### Table layout

All table offsets are measured in bytes from the globally selected table base. Two-byte offsets and terminal values are interpreted high byte first, independently of the host’s native byte order.

The root directory has this layout:

| Position relative to table base | Meaning |
|---|---|
| 0 | No semantic use established by this function. |
| 1 | Unsigned 8-bit root-entry count. |
| 2 onward | Root-record offsets, two bytes per entry. |

A count of zero causes lookup to return zero without reading an input byte or a root entry.

Each root offset is an unsigned 16-bit quantity. No special meaning or rejection is assigned to offset zero.

Every record begins with a header byte:

- Bits 0–6 contain the record’s input label.
- Bit 7 selects the record form.

The forms are:

| Header bit 7 | Record form |
|---|---|
| Set | Adjacent continuation: the successor record begins exactly one byte after this record’s header. |
| Clear | Branch-capable record: the following byte is a descriptor containing a child count and terminal marker. |

For a branch-capable record, the descriptor immediately follows the header:

- Bits 0–6 contain a child count from 0 through 127.
- Bit 7 marks the presence of a terminal value.

The remainder of this form is laid out as follows:

| Terminal marker | Terminal value | Beginning of child-offset list |
|---|---|---|
| Clear | Absent | Two bytes after the record header. |
| Set | Two bytes immediately after the descriptor | Four bytes after the record header. |

Each child-offset entry occupies two bytes and refers to a record relative to the table base.

An adjacent-continuation record has no separately interpreted descriptor, value, or child list. Its next byte is itself the next record header. That successor can be either record form.

### Initial guard and root selection

The initial guard precedes table access. A null Start returns zero without requiring an End comparison to be evaluated. Otherwise, End must compare greater than Start.

After the guard, the function reads the root-entry count. It searches the half-open root-index interval beginning at zero and ending at that count.

For each candidate:

1. The candidate index is the floor of the average of the current lower and upper bounds.
2. Its two-byte directory entry selects a record.
3. The record’s low seven header bits are compared with the first input byte.
4. Equality selects that record.
5. A smaller record label moves the lower bound past the candidate.
6. A larger record label moves the upper bound to the candidate.

An empty search interval returns zero.

The root count limits indices to 0 through 254. The search-bound arithmetic therefore cannot overflow the represented 32-bit intermediates. With the maximum root count of 255, the last root-directory entry occupies table-relative positions 510 and 511.

Root binary search requires the directory to be ordered by record labels if it is to find every present root. The function does not check this ordering. It also does not reject duplicate root labels or search alternative equal-label roots if the selected root later fails.

The first input byte is compared in full against a seven-bit record label; the input byte is not masked. A first byte greater than `0x7f` cannot match any root.

### Consuming later input bytes

After a root match, traversal starts with the second input byte. For every remaining byte, the function reads that byte and advances its input position before resolving the next record.

If the current record is an **adjacent-continuation record**, the successor is the byte immediately following the current header. The successor’s low seven header bits must equal the consumed input byte. A mismatch returns zero immediately.

If the current record is a **branch-capable record**, the descriptor determines the child count and whether the two terminal-value bytes must be skipped before the child list. The function scans the child offsets in stored order:

- Each entry selects a child record.
- The child header’s low seven bits are compared with the consumed input byte.
- The first matching child becomes the current record.
- Exhausting the declared child count without a match returns zero.

A zero child count causes immediate failure when another input byte must be consumed; no child-offset entry is read in that case.

Child lists are scanned linearly and need not be sorted. If multiple children have the same label, only the first matching child is selected. There is no backtracking to later equal-label entries if the chosen path subsequently fails.

As with the first byte, every later input byte is compared without masking. Consequently, an input byte from `0x80` through `0xff` cannot match a record label.

A terminal value on an intermediate branch-capable record does not stop traversal. The function skips over it to reach that record’s child list when input remains.

### Final acceptance

Once all input bytes have been consumed, the current record is checked in this order:

1. An adjacent-continuation record is rejected.
2. A branch-capable record without the terminal marker is rejected.
3. A branch-capable record with the terminal marker supplies the two-byte return value.

This is exact-match behavior, not longest-prefix behavior. An earlier terminal record is not remembered as a fallback, and an available successor is not followed without consuming another input byte.

For a one-byte input, the selected root itself must satisfy these terminal conditions.

### Read ordering and arithmetic boundaries

The established logical access sequence is:

- Initial pointer guard.
- Root count.
- Candidate root offsets, candidate headers, and first-byte comparisons during binary search.
- For each later byte: input-byte read, current-record inspection, then successor or child-list reads.
- Final record-form check, terminal-marker check, then terminal-value retrieval.

A final adjacent-continuation record is rejected without inspecting the following byte as a descriptor. A final nonterminal branch-capable record is rejected without reading a terminal value.

The two bytes of an offset or value are both required, but the supplied expressions do not establish a portable evaluation order between those two byte reads. Likewise, repeated source-level header or input expressions do not guarantee a particular number of physical memory reads.

Offsets are zero-extended before addition to the table base. They range from 0 through 65,535. Those additions, directory access, adjacent-record advancement, and input-pointer advancement have no explicit overflow or capacity checks.

There is no explicit iteration over a table path without consuming input: every successful traversal transition consumes one more byte. Cyclic child offsets therefore do not, by themselves, create an unbounded traversal for a finite valid input range.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not observed runtime results.

1. **Initial rejection.** If Start is null, the result is zero without accessing the table. If Start and End are equal, the result is also zero without accessing the table.

2. **Empty root directory.** Given a valid nonempty input range and a table whose root count is zero, lookup returns zero without reading an input byte or directory entry.

3. **Single-byte terminal match.** Given a matching root label, a branch-capable root with the terminal marker set, and value bytes `0x12, 0x34`, a one-byte input returns `0x1234`. Its child count does not affect this result.

4. **Prefix without a value.** Given a matching root that is branch-capable but lacks the terminal marker, a one-byte input returns zero even if that root has children.

5. **Input ends within an adjacent chain.** If the final matched record has its header’s high bit set, lookup returns zero. Bytes beyond that header are not interpreted as a terminal descriptor merely because input has ended.

6. **Adjacent-chain success.** Given an adjacent-continuation root whose immediately following record matches the second input byte and is terminal with value `0xabcd`, the corresponding two-byte input returns `0xabcd`.

7. **Intermediate terminal value is skipped.** Given a terminal root with one child, a two-byte lookup reads the child offset after the root’s two value bytes. If the child matches and is terminal, the child’s value is returned rather than the root’s value.

8. **No longest-prefix fallback.** Given a terminal root and a second input byte that matches no child, the result is zero, not the root’s stored value.

9. **No children with input remaining.** Given a matched branch-capable record with child count zero and another input byte remaining, lookup returns zero without reading a child offset.

10. **Duplicate child labels.** If two child entries have the requested label, the first is selected. A later failure along that selection does not cause lookup to try the second entry.

11. **Full-byte comparison.** An otherwise valid input containing `0x80` cannot match the seven-bit label `0x00`; the input is not reduced modulo 128.

12. **Zero-valued terminal.** A complete terminal match with stored value bytes `0x00, 0x00` returns zero and is indistinguishable through this interface from a failed lookup.
