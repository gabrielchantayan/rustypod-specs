# F-5569dd87c920

## Purpose

F-5569dd87c920 coordinates a position-dependent input operation, context accounting, optional verification, identifier-based object selection, and delivery through dependent operations and an optional callback.

The established behavior is orchestration: the function reads context fields, invokes dependencies, updates a two-word counter, applies rejection and filtering conditions, and conditionally processes a selected object. The meanings of the input format, identifier, counter, and object payload are not established.

**Inferred intent:** this resembles processing a framed item whose identifier selects a destination, with optional integrity verification and an alternate delivery path. These interpretations are not requirements. The contract below uses neutral terms.

## Interface

The function accepts five arguments:

| Argument | Width and interpretation |
|---|---|
| Context | A 32-bit address of mutable structured storage. |
| Input handle | An opaque 32-bit value passed to dependencies. |
| Position low word | An unsigned 32-bit value. |
| Position high word | A 32-bit value participating in position arithmetic. |
| Verification flag | A 32-bit value; zero disables the optional verification path, any nonzero value enables it. |

The result is a 32-bit status. Established result sources are:

- A nonzero result propagated from an input or preparation dependency.
- The fixed value **101**, hexadecimal **0x65**, for specified rejection conditions.
- Zero for several successful or deliberately skipped paths.
- The result of the alternate-delivery dependency, when that dependency runs and no later explicit rejection supersedes it.

There is no established universal interpretation of nonzero statuses beyond the branches described below.

## Behavior

### 1. Capture and initial input operation

The function first reads and retains the 32-bit value at context offset 0xe4. Later changes to that field do not replace this captured buffer value.

It also creates local 32-bit copies of the context address, input handle, and both position words.

It calls **F-7d053eed75bd** with five observed arguments, in this order:

1. Input handle.
2. Input handle again.
3. Position low word.
4. Position high word.
5. Address of a local 32-bit identifier output.

If this call returns nonzero, that value is returned immediately. No explicit accounting update or subsequent dependency call occurs.

Successful execution requires the identifier output to be defined before it is consumed. The available evidence does not independently establish the dependency’s output guarantee.

The function then computes an auxiliary high word: the original position high word plus one if adding four to the original low word would carry. The carry condition is an unsigned comparison against **0xfffffffb**.

Next it calls **F-779a651c5cc8** with:

1. The saved input handle.
2. The captured buffer.
3. The value currently read at context offset 0x40.

After this call, it captures the identifier output for early validation. If the dependency returned nonzero, its result is returned immediately.

The extent passed to this dependency is not necessarily the extent used below: offset 0x40 is read again after the call.

### 2. First accounting update

The function reads the current extent and the accounting low word.

All arithmetic described here is at 32-bit word width. Low-word results wrap modulo \(2^{32}\). Carries are unsigned carry-outs.

Let the current extent be \(E\). It first forms:

\[
D = (E + 4) \bmod 2^{32}.
\]

It then:

1. Writes the accounting low word plus \(D\), modulo \(2^{32}\), to offset 0x98.
2. Reads the accounting high word and writes back that word plus:
   - zero if bit 31 of \(D\) is clear, or negative one if bit 31 is set; and
   - the unsigned carry from the low-word addition.

This is addition of the **sign-extended wrapped 32-bit value \(D\)** to the two-word counter. It is not unconditionally an unsigned addition of the mathematical value \(E+4\).

The low-word write precedes the high-word update. Both writes occur before identifier rejection and upper-bound filtering. No rollback is shown.

### 3. Identifier rejection and filtering

The function returns **101** if the live identifier output is zero.

Otherwise, it calls **F-870c4fcf7295** with:

1. **0x40000000**.
2. The extent captured for the accounting update.

If that dependency’s result, increased by one using 32-bit unsigned arithmetic, equals the identifier captured after F-779a651c5cc8, the function returns **101**.

The operation performed by F-870c4fcf7295 is unknown. No division, capacity, or format interpretation is required by this contract.

Next, the function reads context offset 0x24. If that unsigned value is less than the captured identifier, it returns **zero**. This path retains the accounting changes but skips optional verification, object lookup, alternate delivery, and object processing.

Equality with the upper bound does not trigger this early return.

### 4. Optional verification

This stage runs only when the verification flag is nonzero and earlier checks have passed.

Using the original position words and the extent captured during the first accounting update, the function derives a new position. Its low word is the wrapped sum of the original low word, extent, and four.

Its high word is the original high word plus:

- The sign extension of the 32-bit extent: zero or negative one.
- The unsigned carry from adding the original low word and extent.
- The unsigned carry from adding four to that wrapped sum.

Thus the position calculation treats the extent as a signed 32-bit displacement, followed by an increment of four.

It calls **F-7d053eed75bd** again, now with six observed arguments:

1. The saved input handle.
2. The derived high word.
3. The derived low word.
4. The derived high word again.
5. Address of a separate local 32-bit verification output.
6. The auxiliary high word computed from the original position plus four.

The differing argument counts and unusual argument arrangement are part of the static evidence. Their ABI-level meaning is unresolved.

If this call returns nonzero, its result is returned immediately. The first accounting update remains, but the additional increment below does not occur.

After a zero result, the function adds four to the accounting value:

1. It reads and writes the low word at offset 0x98.
2. It reads and writes the high word at offset 0x9c, adding the carry from the low-word increment.

It then calls **F-01aa528e5c81** with the context address and captured buffer. If the returned 32-bit value differs from the verification output, the function returns **101**. Both accounting updates remain committed.

There is no established integrity algorithm or interpretation of the verification output.

### 5. Object selection and alternate delivery

The provisional final status is initialized to zero.

The function calls **F-c1f06f89d6d7** with the context address and the live identifier output, obtaining either zero or a selected-object address.

Only after this call does it read the unsigned mode byte at context offset 0x0e.

If the mode is greater than three:

- A nonzero object whose byte at offset 0x1e is nonzero proceeds directly to object processing.
- Otherwise, the function reads the pointer at context offset 0x6c and dereferences its first 32-bit word.
- If that word is nonzero, it calls **F-87fe98a22e06** with that pointer, the captured buffer, and a freshly read extent.
- The result of F-87fe98a22e06 becomes the provisional final status.
- If no object was selected, the function returns that status immediately.
- If an object was selected, it calls **F-d0d75bd453b2** with the object address, ignores the result, and proceeds to object processing using the same address.

If the mode is at most three, or the alternate gate word is zero, alternate delivery does not occur.

After the applicable branches, a zero object address causes a zero return unless alternate delivery already returned its result.

No ownership or lifetime effect may be inferred for F-d0d75bd453b2. In particular, this function subsequently reads the selected object; valid continuation requires that the dependency’s actual contract permit that use.

### 6. Object processing and callback

For a nonzero selected object, the function reads its 32-bit value at offset 0x34.

It invokes an unmapped external operation with three observed arguments:

1. The object data value.
2. The captured buffer.
3. A freshly read extent.

The external operation’s result is not used.

After that operation returns, the function reads the callback address at context offset 0xc8. If nonzero, it invokes the callback with:

1. The selected-object address.
2. Another freshly read extent.

The callback’s result is not used.

Finally, if the live identifier output equals one, the function invokes the same unmapped external operation with two observed arguments:

1. The address at context offset 0xe8.
2. The object data value plus **0x18**, using 32-bit address arithmetic.

This final call uses the previously captured object data value, even though the preceding external operation or callback could have changed the object.

The function returns the provisional final status: zero unless F-87fe98a22e06 supplied another value.

## Acceptance examples

These are conditional static expectations, not runtime test results. They assume valid reachable memory and the stipulated dependency behavior.

1. **Initial failure:** If the first F-7d053eed75bd call returns status 7, the function returns 7. No explicit accounting write occurs.

2. **Preparation failure:** If the initial call succeeds and F-779a651c5cc8 returns 9, the function returns 9 without the first accounting update.

3. **Zero identifier:** If successful preparation leaves the identifier zero, the function updates accounting and then returns 101. F-870c4fcf7295 is not called.

4. **Reserved identifier:** If the nonzero captured identifier equals the 32-bit wrapped value of F-870c4fcf7295’s result plus one, the function returns 101 after accounting.

5. **Filtered identifier:** If earlier rejection checks pass and the upper bound is 8 while the captured identifier is 9, the result is zero. Verification and lookup are skipped despite a nonzero verification flag.

6. **Boundary inclusion:** An identifier equal to the upper bound remains eligible for verification and lookup.

7. **Signed accounting increment:** If the captured extent is **0x7ffffffc**, its wrapped sum with four is **0x80000000**. With an initially zero counter, the first accounting update yields low word **0x80000000** and high word **0xffffffff**.

8. **Verification mismatch:** If optional input succeeds but F-01aa528e5c81 returns a different value, the result is 101. The first increment and the additional four-unit increment remain.

9. **No object, ordinary mode:** With mode at most three and a zero lookup result, the function returns zero without dereferencing the alternate-delivery pointer.

10. **No object, alternate delivery:** With mode greater than three, a zero lookup result, and a nonzero gate word, the function returns F-87fe98a22e06’s result directly.

11. **Object bypass:** With mode greater than three and a nonzero object flag at offset 0x1e, alternate delivery and F-d0d75bd453b2 are skipped. Object processing still occurs.

12. **Alternate error with object:** If alternate delivery returns 12 and an object exists, F-d0d75bd453b2 and subsequent object processing still occur. The final status remains 12.

13. **Callback-visible extent change:** If the three-argument external operation changes context offset 0x40, the callback receives the newly read value, not an earlier captured extent.

14. **Identifier-one ordering:** When the identifier is one and an object exists, the two-argument external operation occurs after the callback, using the previously captured object data value plus 0x18.
