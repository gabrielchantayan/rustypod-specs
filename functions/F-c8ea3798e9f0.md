# F-c8ea3798e9f0

## Purpose

F-c8ea3798e9f0 reads an object reference from an input context and, when that reference is non-null, exports two header words followed by three-word records into caller-supplied storage. It then invokes an unresolved indirect dependency with a zero-valued argument and returns that dependency’s result.

A null object reference instead produces the 32-bit return value 6, without accessing the output or invoking the dependency.

The record-export pattern is consistent with copying a record identifier and the first and last words of associated storage. That interpretation is **inferred intent**. The supplied evidence establishes addresses and transfers, not domain meanings or valid sequence boundaries.

The explicit output writes are not a guarantee of output contents on return. The unresolved dependency executes afterward and may modify or release the output before returning normally.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

### Inputs and representation

The function accepts:

1. **Context address:** used to read an object reference at byte offset 524, hexadecimal 0x20C.
2. **Output address:** used as the beginning of a sequence of 32-bit output words.

The represented accesses use 8-bit bytes, 32-bit data words, a 32-bit unsigned record index, and 32-bit address-bearing object fields. The context reference occupies a pointer slot in the supplied representation. Portability to other pointer widths or address spaces is not established.

Neither input supplies a capacity, allocation size, ownership annotation, or validity indicator. The context address is not checked before the object-reference read.

### Context layout

| Byte offset | Access | Established use |
|---|---|---|
| 0x20C | Object-reference read | Selects the object used by subsequent explicit accesses |

The object reference is loaded once. The visible processing does not reload this context slot during the export.

### Object layout

Let \(i\) denote the zero-based record index. The following offsets describe nominal addresses before any address-arithmetic limitations:

| Byte offset | Access width | Established use |
|---|---|---|
| 0 | 32 bits | Second exported header word |
| 4 | 32 bits | First exported header word; repeatedly read unsigned loop bound |
| \(8 + 4i\) | 32 bits | First word of output record \(i\) |
| \(88 + 12i\) | 8 bits | Count-like value used in the second referenced address |
| \(92 + 12i\) | 32 bits | Address-bearing field used for both referenced-word transfers |

The count-like field consists of one byte, not the surrounding 32-bit word. Its numerical range is 0 through 255.

The record-indexed regions have different strides. Nothing establishes that they are separate allocations or disjoint logical arrays. Their nominal address ranges can overlap at sufficiently large indices.

### Explicit output-write layout

For a stable loop bound \(N\), valid representable addresses, sufficient output capacity, stable source fields, and non-overlapping output, the function’s **explicit writes before the indirect call** have this layout:

| Output byte offset | Value explicitly written |
|---|---|

The nominal explicit-write footprint is \(2 + 3N\) words, or \(8 + 12N\) bytes. This is a mathematical capacity expression, not a checked allocation or size calculation performed by the function. It does not cover any additional memory accesses the dependency might perform.

This table describes the export phase, not a postcondition on normal return. Without a preservation guarantee from the dependency, output contents and output-storage validity on return are **documented_only**.

### Result

- Null loaded object reference: returns the 32-bit value 6.
- Non-null reference, followed by completed export and a normally returning dependency: returns the dependency’s 32-bit result unchanged.

The function does not return an output length. Passing zero to the dependency does not establish a zero result or a success status.

## Behavior

### Object selection and null handling

The first established memory access reads the object reference from the context at byte offset 0x20C.

If that reference is null:

- The function returns 6.
- No output access occurs.
- No object field is read.
- The indirect dependency is not invoked.

This is the only explicit validation branch. An invalid context address is not treated as equivalent to a readable context containing a null object reference.

For a non-null reference, subsequent explicit object accesses use the loaded reference. Changing the context slot later does not itself redirect those accesses.

### Header transfers

The function performs two sequential transfers:

1. Reads the object word at byte offset 4 and writes it to output byte offset 0.
2. Reads the object word at byte offset 0 and writes it to output byte offset 4.

These transfers do not form an atomic snapshot. The second source read occurs after the first output write. If that write overlaps the second source location, the second transfer observes the modified value.

Both header writes precede the first loop-bound comparison. Therefore, output aliasing can change the bound before any record is processed.

### Loop-bound behavior

The record index starts at zero. Each condition evaluation compares that index against the current object word at byte offset 4, interpreted as an unsigned 32-bit value.

The bound is not retained solely from the first header transfer. It is read again for successive loop decisions.

Consequences include:

- A bound of zero at the first comparison skips all record transfers.
- A bound with its high bit set is a large unsigned value, not a negative count.
- The first exported header word need not equal the number of records eventually processed.
- Output writes that overlap the bound can change later loop decisions.
- A stable maximum unsigned bound does not by itself require index wrap: the loop can stop when the index reaches that bound. Memory validity remains a separate requirement.

These observations describe the represented access pattern. They do not establish thread safety or defined behavior under unsynchronized concurrent mutation.

### Record transfers

Each iteration performs three output transfers in the following order.

**First word:** reads the object word at nominal byte offset \(8 + 4i\), then writes it to output byte offset \(8 + 12i\).

**Second word:** reads the address-bearing object field at nominal byte offset \(92 + 12i\), reads a 32-bit word through that address, then writes the result to output byte offset \(12 + 12i\).

**Third word:** obtains the address-bearing field again and reads the count-like byte at nominal object byte offset \(88 + 12i\). It reads a 32-bit word at the resulting address:

\[
\text{base} + 4L_i - 4
\]

It then writes that word to output byte offset \(16 + 12i\).

The address field is used in separate expressions for the second and third transfers. There is no guaranteed once-per-record snapshot. If the second output write overlaps that field, the third transfer can use a different base address. Earlier output writes can likewise change the count-like byte before it is read.

Statement order establishes the order of the three transfers. The evidence does not establish a finer ordering between independent operand reads within the third transfer, such as whether the base field or count byte is read first.

After the third write, the index increases by one and the loop condition is evaluated again.

### Widths and address calculations

The count byte is converted to an unsigned value before multiplication by four. Its scaled value ranges from 0 through 1,020, so that multiplication alone cannot overflow a 32-bit unsigned value.

The resulting nominal displacement from the base is:

| Count-like byte | Nominal displacement |
|---|---:|
| 0 | −4 bytes |
| 1 | 0 bytes |
| 2 | 4 bytes |
| 255 | 1,016 bytes |

For zero, the represented 32-bit arithmetic adds the equivalent of minus four. Where that calculation denotes a valid preceding address, the read is four bytes before the base. It is not an empty-record case.

Index expressions involving multiplication by three and addition are unsigned 32-bit expressions in the supplied representation. Their values can wrap for sufficiently large indices. The byte-offset tables and capacity formula are ordinary mathematical descriptions valid where the corresponding address calculations remain representable and valid; they do not promise unbounded linear traversal.

The exact execution-environment consequences of pointer-address overflow, crossing allocation boundaries, or invalid addresses remain **documented_only**. No range or overflow checks are visible.

### Indirect dependency

Once the loop terminates, the function invokes F-indirect-unknown with one explicit zero-valued argument.

If the dependency returns normally, its result is returned directly. No further explicit output writes appear in the visible body.

Normal return does not establish that the dependency preserved the exported words, the object, the context, referenced storage, globals, or ownership. It may overwrite output after the export phase. Consequently, even successful completion does not establish the output layout as the final returned state.

## Side effects

The directly established writes target the caller-supplied output addresses. The function directly reads the context, object fields, and referenced words.

There are no visible allocation, release, or ownership-transfer operations in the resolved export phase. That observation does not establish ownership behavior for F-indirect-unknown.

The export is incremental, without rollback. If an access or the final call cannot complete, preceding writes may already have occurred.

No separate explicit writes to the context or object appear. Output aliasing can nevertheless modify either, including fields needed by later transfers. There is no overlap check.

Safe completion of the explicit export requires valid memory access for every executed operation, including:

- The context’s object-reference slot.
- Both non-null-path header transfers.
- Every loop-bound read.
- All executed record-field and referenced-word reads.
- Every output write.

Alignment requirements, fault handling, and memory permissions depend on the execution environment. The function contains no explicit mechanism converting access failures into return value 6 or another defined status.

The final call adds unresolved side effects. No guarantee is established that caller-owned memory remains allocated or unchanged after that call.

- Output storage is not accessed.

- The explicit pre-call output sequence is 1, 41, 7, 10, 30.
- The export operations read the first and third referenced words, not the middle word.
- The dependency determines the return value.

The dependency may independently read the middle referenced word; its reads are unresolved.

### Count-like byte equal to one

For a record with count byte 1 and unchanged base field:

- Both referenced transfers address the base word.
- Stable contents at that location produce matching second and third record words.
- Two reads are represented; there is no guaranteed single-read snapshot.

### Count-like byte equal to zero

For a record with count byte 0:

- The second record word comes from the base.
- The third comes from the represented base-minus-four address.
- If that address is invalid, no normal-return guarantee exists.
- Zero does not suppress either read or select a default value.

### Header aliasing

If output begins at object byte offset 0, the first header write replaces object word 0 with the previously read bound. The second header transfer then reads that replacement and writes it at object byte offset 4.

Thus, both explicit header values equal the original bound, assuming those accesses are otherwise valid. This behavior differs from a two-word snapshot.
