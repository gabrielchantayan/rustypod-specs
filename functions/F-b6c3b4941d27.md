# F-b6c3b4941d27

## Purpose

F-b6c3b4941d27 conditionally produces a two-word reference containing a calculated entry address and the original object address.

The function selects an unsigned bound from a shared table using object-associated metadata and a global datum containing the table’s base address. If the requested unsigned index is strictly below that bound, it writes the reference to caller-provided output storage and returns 0. Otherwise, it returns 9 without accessing storage through the output argument and without performing any stores.

The entry-address calculation uses a 12-byte stride. The calculated address is not dereferenced to inspect the selected entry. This does not imply that the same physical address cannot be accessed independently as an input field or output location.

**Inferred intent:** the two output words represent an indexed entry associated with its containing object. This interpretation does not establish ownership, entry type, allocation extent, or address lifetime.

## Interface

The function has three explicit inputs and a 32-bit result.

| Input | Representation and role |
|---|---|
| Object address | A 32-bit address-bearing value. Locates metadata and, on success, the entry-storage base. Also becomes the second output word. |
| Requested index | An unsigned 32-bit integer used for the bounds comparison and entry-address calculation. |
| Output address | Identifies storage for two consecutive 32-bit words, written only on success. |

A global datum containing the shared-table base address is an additional implicit input. The datum and the table it addresses are separate storage dependencies.

| Result | Meaning on normal completion |
|---|---|
| 0 | The index is strictly below the selected bound, and both output stores have completed. |
| 9 | The index is equal to or greater than the selected bound. No access through the output argument and no stores occur. |

Result 0 does not certify that the calculated entry address is usable or that the backing allocation contains the indexed entry. Result 9 is the observed bounds-rejection result, not a general memory-error result.

### Observed storage layout

All offsets and strides below are in bytes.

| Location | Operation |
|---|---|
| Global base-holding datum | Read the shared-table base address. |
| Object address + 0x50 | Read a 32-bit metadata address. |

The global datum contains a base address; it is not itself the selected table record or bound word. Obtaining the base and reading the bound are distinct accesses.

The table-record stride and entry-address stride are both 12 bytes. Their equality does not establish a common record type or shared allocation.

Byte order and alignment requirements are not established by the supplied representation.

### Preconditions for normal completion

Every input location actually read must be accessible at the required width. This includes the global datum, the object’s metadata-address field, the metadata selector, and the selected table-bound word.

Success additionally requires the entry-storage-base field to be readable and both output words to be writable.

The calculated entry address need not be readable merely because it is returned: the function does not dereference it as an entry. If that address also coincides with a required input or output location, accessibility requirements still apply to that independent access.

No explicit null-pointer, selector-range, allocation-size, or alignment validation appears.

Rejection does not require output storage to be writable. However, storage designated by the output address may also be required input storage through aliasing. In that case, the relevant input reads must still succeed.

## Behavior

### Bound selection

The function obtains the shared-table base from the global datum. It also follows the object’s field at offset 0x50 to metadata and reads the selector at metadata offset 0x10.

The selector chooses a table record with a 12-byte stride. The unsigned bound is read at offset 4 within that record.

The established ordering constraints are:

- Reading the metadata address precedes reading the selector through that address.
- Obtaining both the global base value and the selector precedes reading the selected bound.
- Reading the bound precedes the comparison.
- A successful comparison precedes the success-path entry-base read and output stores.

The relative evaluation order between the global-datum read and the metadata-address or selector reads is not established. The contract therefore imposes no order among those independent reads beyond their dependencies.

There is no explicit validation that the selector names a valid table record. In particular, no explicit rejection of a negative selector appears.

### Unsigned comparison

The requested index and selected bound are compared as unsigned 32-bit values.

- An index strictly below the bound takes the success path.
- An index equal to or greater than the bound takes the rejection path.

Equality is rejected. A zero bound rejects every possible index, assuming the bound-selection reads complete.

An index with its high bit set remains an unsigned value for this comparison. It is not rejected solely because interpreting the same bit pattern as signed would produce a negative value.

### Rejection

On rejection, the function returns 9.

The body performs no access through the output argument and no stores. It also does not perform the success-only read of the entry-storage-base field through object offset 0x54.

These are access-path guarantees, not guarantees that particular physical addresses remain unread. For example:

- The output address may equal the metadata-selector address, causing the first output word’s storage to be read as the selector.
- An output word may coincide with the selected table-bound word.
- The storage at object offset 0x54 may also be reached through another required input address.

Such aliases do not introduce an output-argument access or a success-path entry-base read. They do mean that categorical claims of “no access to output storage” or “no read of that physical address” would be too strong.

Because the function performs no stores on rejection, it leaves output contents unchanged by this invocation. Changes caused by other actors are not excluded.

The body does not show input-access failures being converted into result 9.

### Success

After the comparison succeeds, the observable memory operations occur in this order:

1. Read the entry-storage base through object offset 0x54.
2. Write the original object address at output offset 4.
3. Write the calculated entry address at output offset 0.

The function then returns 0.

The calculated entry address is the entry-storage base plus 12 times the requested index, with the arithmetic-width behavior described below.

The logical output layout is therefore:

| Output word | Value |
|---|---|
| First, at offset 0 | Calculated entry address |
| Second, at offset 4 | Original object address |

The write order is the reverse of this layout order: the second word is written first.

There is no dereference of the calculated address to inspect, copy, initialize, or validate an entry. Required input reads or output stores may nevertheless touch the same physical storage if addresses overlap.

### Arithmetic widths

The index is unsigned 32-bit. Its multiplication by 12 and addition to the entry-storage base use 32-bit unsigned arithmetic in the supplied representation. The stored entry-address word is the mathematical sum reduced modulo \(2^{32}\).

No explicit multiplication-overflow or addition-overflow check appears. Passing the bounds comparison does not prove that:

- Multiplication by 12 avoids wraparound.
- Adding the entry-storage base avoids wraparound.
- The resulting address lies within an allocation.
- The selected entry is accessible or complete.

Table selection has a separate arithmetic issue: its selector is represented as signed, and its multiplication by 12 is not established to have portable unsigned wraparound semantics. Overflowing signed table-offset arithmetic remains documented_only.

The supplied representation also does not establish portable behavior for every overflowing or invalid address calculation involved in locating fields. Those cases are not assigned a fabricated recovery result.

### Aliasing and partial updates

No explicit non-aliasing restriction appears.

On success, output stores may overwrite the object, metadata, shared table, or global base-holding datum if the addresses overlap. They may also overwrite storage that happens to coincide with the calculated entry address.

Before either output store, this invocation has already obtained its bound and read its entry-storage base. The visible body does not reread those values after the first store. Consequently, overwriting an input field through output aliasing does not cause a new lookup or alter the already-consumed values for this invocation. It may affect later invocations or other consumers.

The two stores are not shown as an atomic pair. If execution stops after the store at output offset 4 but before the store at offset 0 completes, a partial update may be observable. No rollback or defined error return for that situation is established.

On normal rejection, the body performs no stores and no access through the output argument. Required input reads can still access storage overlapping either output word.

There is no separate direct assignment to the global base-holding datum, object fields, metadata, or table. Successful output aliasing can nevertheless modify any of those regions.

No locking, retry, or snapshot-validation operation appears. The body does not establish that the global base, metadata selector, bound, and entry-storage base form a coherent snapshot under concurrent mutation.
