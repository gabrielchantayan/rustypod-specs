# F-1a1c220ba66e

## Purpose

F-1a1c220ba66e performs an extended sequence of indirect invocations and fixed-width transformations, then mutates absolute-address and indirectly addressed memory before a final unresolved dispatch.

The supplied representation does not establish a domain-level purpose. Character-like constants, repeated writes, and linked-address accesses do not establish formatting, serialization, allocation, construction, or cleanup.

This contract distinguishes:

- **Established static evidence:** explicitly represented argument uses, transformations, memory accesses, value captures, and ordering.
- **[INFERENCE]:** conclusions requiring an additional machine-arithmetic assumption.
- **documented_only:** unresolved behavior that must not be replaced by an invented guarantee.

The operation is not established to be pure, transactional, memory-safe for arbitrary inputs, or fully determined by its explicit arguments.

## Interface

### Explicit arguments

| Position | Represented width | Established use |
|---|---|---|
| First | 32-bit opaque value | No explicit use in the represented body |
| Second | 32-bit opaque value | No explicit use in the represented body |
| Third | 32-bit unsigned value | Supplies shifted and masked arguments to early indirect invocations |
| Fourth | 32-bit signed value | Supplies two equal values obtained by shifting left seven bits |

The third argument supplies both a 24-bit-left-shifted value and its low eight bits shifted left five bits.

**[INFERENCE]** With 32-bit bit-vector arithmetic, those expressions depend only on the third argument’s low byte. The second expression ranges from 0 to 8,160.

“No explicit use” of the first two arguments does not guarantee observational independence. Unknown invocation conventions may expose incoming machine state.

### Implicit inputs

Execution additionally depends on:

- Incoming control-link state used to form the first indirect target.
- Results and secondary machine outputs of unresolved invocations.
- A shared 32-bit address-base value read at absolute address 0x087FBBBC.
- Absolute low-address memory and computed-address memory.
- An unresolved final dispatch target.

The explicit arguments are therefore not a complete executable interface.

### Outputs

No explicit return value is represented. Outputs are invocation effects, ordered memory accesses, mutations, and the final dispatch.

The final target receives four represented arguments:

These are captured values, not descriptions of memory to reload at dispatch time. Their capture points and subsequent mutations are specified below.

## Behavior

### Indirect-invocation phase

The operation starts with three indirect invocations having no explicit arguments in the representation. The first target depends on incoming control-link state plus displacement 0xFFE. Subsequent targets are formed from embedded continuation-like values and the same displacement.

These initial invocations precede the fourth argument’s explicit use. An early invocation receives its seven-bit-left-shifted value twice. Later invocations receive the third argument’s transformed values.

The remaining invocation phase repeatedly consumes:

- Shifted 32-bit results.
- Masked low-order fields.
- Logical right shifts of unsigned quantities.
- Low and high 32-bit portions of represented 64-bit results.
- Secondary machine outputs with incomplete producer contracts.
- Explicit zero arguments.
- Equal values repeated in multiple argument positions.

No represented conditional branch checks a result for failure. Zero may participate in subsequent transformations or address generation.

An invocation without explicit represented arguments is not necessarily input-free. A represented 64-bit result establishes consumption of two 32-bit portions, not a resolved public return convention.

The dependencies remain unresolved. Their invocations cannot be replaced by arithmetic alone merely because some transformed arguments appear redundant.

### Widths and arithmetic

Direct accesses distinguish bytes, 16-bit halfwords, and 32-bit words. Represented 64-bit invocation results are split before subsequent 32-bit processing.

Masks select fields including 24, 22, 20, 19, 17, 14, 13, and 11 low-order bits. Some transformations additionally select 18-bit and 21-bit fields. A selected field need not survive a later left shift intact.

**[INFERENCE]** Under 32-bit bit-vector arithmetic, multiplication and left shifts retain only the low 32 bits. Intermediate truncation matters: a later right shift does not restore discarded bits.

Exact behavior for signed-overflow cases, address overflow, and the late variable-count signed right shift is **documented_only**. Arbitrary-precision arithmetic is not supported by the evidence.

For describing memory dependencies, this contract uses the following descriptive labels. They identify captured values or derived addresses, not object types:

| Label | Meaning |
|---|---|
| Tall base | An invocation result multiplied by 2²⁵ |
| Small selector | A result shifted left eight bits, masked with 0x7FFF, then logically shifted right six bits |
| Small base | Twice the small selector |
| Saved word | The word captured through the absolute-0x05-derived base at offset 0x54 |
| Scaled base | Four times the saved word |
| Adjusted base | The scaled base minus 0x96 |
| Working base | Four times the adjusted base |
| Shared base | The captured word read at absolute address 0x087FBBBC |
| Late anchor | Twice a link value obtained before the constant-write region |

**[INFERENCE]** With 32-bit bit-vector arithmetic, the tall base has 25 low zero bits. The small selector is a multiple of four from 0 through 508; the small base is a multiple of eight from 0 through 1,016. These constraints do not establish address validity.

### Initial mutation and absolute address 0x05

The final paired invocation result supplies a high-result-based word store at offset 0x14 and a low-result-based word store at offset 0x54 of a 256-scaled address. The latter store contains the tall base. It occurs between two byte writes to another computed address at offset 0x09.

The tall-base offset 0x14 is cleared before reading its offset-0x05 byte. A clear through the small base intervenes before that byte is zero-extended into a word store at tall-base offset 0x34. The tall-base offset 0x14 is then read, followed by another small-base clear and two identical byte writes at small-base offset 0x15.

The word read after the clear is not necessarily zero: intervening computed-address stores may alias it.

The first meaningful absolute-address group then proceeds as follows:

- The byte at absolute address 0x05 is read and zero-extended into an address base.
- Absolute address 0x01 receives the low byte of the small base.
- Offset 0x15 of the base obtained from absolute 0x05 receives the low byte of the small selector.
- Tall-base offset 0x11 receives a transformed invocation value’s low byte.
- A word store through the previously read tall-base offset-0x14 value writes that transformed value at offset 0x54.
- Tall-base offset 0x11 is cleared.
- The word at offset 0x54 of the absolute-0x05-derived base is captured as the saved word, then replaced with the earlier tall-base offset-0x14 value.

The absolute-0x05 byte capture remains the address base for these accesses even if absolute 0x01 or another intervening write changes overlapping memory. Conversely, the offset-0x54 word capture occurs after the intervening indirect stores and must reflect the memory at its actual read point.

### Linked updates and absolute addresses 0x54 and 0x15

Subsequent updates follow words at offsets 0x74 and 0x54, perform repeated self-valued stores, and write bytes at offsets 0x09 and 0x15.

A word loaded from tall-base offset 0x74 becomes a destination base. Another destination is reached through small-base offset 0x74. The representation reads the latter field for both address construction and stored-value construction; no independent stability guarantee is supplied.

The saved word is written to its own offset 0x24 twice, interleaved with byte and word updates through another link.

The absolute-0x54 write occurs after a word update at small-base offset 0x14 and before that field is replaced twice with the saved word. Absolute 0x54 receives the saved word shifted left one bit as a 32-bit word.

The scaled base then supplies two identical byte writes at small-base offset 0x15. Absolute address 0x15 subsequently receives the low byte of the small base. A word write through scaled-base offset 0x54 follows that absolute byte write.

These absolute stores are distinct from computed-address accesses that happen to use the same numeric offset. Their resulting alias interactions are unresolved, but their order is explicit.

Further accesses:

- Store the scaled base at small-base offset 0x34.
- Read small-base offset 0x74 and double the captured word.
- Update offsets 0x44, 0x54, 0x14, and 0x0D through scaled or linked bases.
- Read a byte at offset 0x05, zero-extend it, and use that value as the base for a word read at offset 0x74.
- Read offsets 0x64 and 0x04 to obtain further addresses.
- Read an offset-0x05 byte again after intervening writes.

The repeated byte reads cannot be merged without an established non-aliasing, stable-memory assumption.

The later offset-0x74 link supplies the late anchor by doubling its captured value.

### Constant writes and shared-base capture

One link produces three distinct stores of 0x3A:

- A byte at four times the link.
- A halfword at eight times the link.
- A word at four times the link plus 0x20.

No string or character-array layout is established.

At working-base offset 0x20, four word writes occur in order: 0x20, 0x2F, a zero-extended byte read from working-base offset 0x04, and 0x20 again.

After these writes, the shared base is captured by a 32-bit read at absolute address 0x087FBBBC. Only then does absolute address 0x60 receive the 32-bit value 0x20.

This capture order matters if the absolute-0x60 store or later computed stores alias the shared-base storage. The repeated region uses the captured base; it does not repeatedly reload absolute 0x087FBBBC.

The first repeated-update group stores four times the link through an eight-times-saved-word destination at offset 0x54, writes the working base’s low byte at shared-base offset 0x19, writes the shared base’s low byte at working-base offset 0x11, and writes eight times the saved word at shared-base offset 0x34.

The following fixed repeated groups use eight times the adjusted base for both the offset-0x54 destination base and the shared-base offset-0x34 value. The byte writes retain their captured values. Each group’s word store precedes its two byte stores and concluding offset-0x34 word store.

The final group completes its offset-0x34 update before the late reads begin. This is a fixed straight-line repeated region, not an established input-controlled loop. Reducing it to final memory contents would discard represented access events.

### Late absolute-global group and fresh reads at 0x67

After the repeated region, the operation captures a 32-bit word at absolute address 0xA9. It next captures a word at offset 0x74 of the four-times-link address used earlier.

Absolute address 0x3A then receives the low byte of eight times the adjusted base plus 0x30.

The following captures occur after that absolute byte write:

- The word at late-anchor offset 0x14, retained as the final dispatch’s third argument.
- The word at working-base offset 0x04, retained for a later shared-base offset-0x74 store.

Before absolute 0x67 is written, indirect mutations write the working base’s low byte at late-anchor offset 0x0D, write 0x6C at working-base offset 0x08, write the shared base’s low byte at working-base offsets 0x0D and 0x09, and store the late anchor itself at its offset 0x54.

Absolute address 0x67 then receives the low byte of the captured absolute-0xA9 word.

A word read at late-anchor offset 0x44 intervenes before absolute address 0x21 receives a byte read from absolute 0x67. The captured offset-0x44 word subsequently supplies:

- A byte write at working-base offset 0x10.
- A word write at shared-base offset 0x54.
- A shifted byte write at late-anchor offset 0x01.

The shift uses the captured word as signed and selects its count from the working base’s low eight bits. Counts outside the ordinary 32-bit range remain **documented_only**.

The shared-base offset 0x54 is then overwritten with the working base. A word read at working-base offset 0x40 precedes stores of the earlier offset-0x04 capture at shared-base offset 0x74 and the offset-0x40 capture at working-base offset 0x10. Shared-base offset 0x44 receives the late anchor.

There are then two additional, distinct reads of absolute 0x67:

1. The first supplies a byte store at working-base offset 0x09. It follows the shared-base updates above.
2. The second supplies another byte store at working-base offset 0x09. Between these reads, late-anchor offset 0x09 receives the working base’s low byte, working-base offset 0x44 receives the captured absolute-0xA9 word, and working-base offset 0x54 is read as another address.

The writes between the original absolute-0x67 assignment, the absolute-0x21 copy, and these later reads can alias absolute 0x67. Consequently, neither later read may be replaced with the originally captured absolute-0xA9 low byte.

### Final captures, mutations, and dispatch

The address read from working-base offset 0x54 receives a byte at offset 0x0D derived from the earlier four-times-link offset-0x74 capture. Late-anchor offset 0x54 is then overwritten with the previously captured third dispatch argument.

Next, the word at working-base offset 0x14 is captured. Subsequent updates write:

- The earlier link-derived byte at late-anchor offset 0x11.
- The low byte of the working-base offset-0x54 address at working-base offset 0x09.
- That address as a word at working-base offset 0x44.

The final argument construction then has these temporal requirements:

- A word read at late-anchor offset 0x04 establishes the **dispatch base**.
- A halfword store of 0x65 occurs at twice the dispatch base.
- The second dispatch argument is captured from dispatch-base offset 0x64, after the halfword store.
- The earlier working-base offset-0x14 capture supplies a byte store at offset 0x11 of the address obtained from working-base offset 0x54.
- That same address receives the 32-bit constant decimal 100 at offset 0x54.
- The fourth dispatch argument is captured from dispatch-base offset 0x74.

The fourth capture is **not** immediately before dispatch. It is followed by:

- A word read at late-anchor offset 0x64, producing a final link.
- A byte write at late-anchor offset 0x09 containing the dispatch base’s low byte.
- A word write at final-link offset 0x54 containing the captured second argument.
- A word write at twice the captured second argument containing the final link.

Only then does the final invocation receive 0x72, the captured second argument, the earlier captured third argument, and the captured fourth argument.

Intervening writes do not cause those arguments to be reloaded. The second argument also determines the final doubled-address store destination. No restoration follows the final invocation in the representation.

## Acceptance examples

These are conditional static expectations, not executed tests.

1. **Third-argument extraction.** Under 32-bit bit-vector arithmetic, 0x000000AB and 0x123456AB both produce 0xAB000000 for the 24-bit left shift and 0x1560 for the low-byte-times-32 expression. Whole-function equivalence does not follow.

2. **Fourth-argument duplication.** A fourth argument of 1 supplies 0x80 in both relevant argument positions. Overflow-producing signed inputs remain documented_only.

3. **Byte zero-extension.** An early tall-base offset-0x05 read of 0xFE supplies the word value 254 at offset 0x34, not a negative sign-extended value.

4. **Clear with aliasing.** A cleared word reads back as zero only if intervening writes do not overlap it and memory remains stable.

5. **Captured shared base.** If the read at absolute 0x087FBBBC yields 0x1000, later repeated accesses use that captured base even if the following absolute-0x60 store aliases its storage.

6. **Fresh absolute-0x67 reads.** If absolute 0x67 initially receives 0xAA, but an intervening aliasing store changes it to 0xBB before a later read, the corresponding working-base offset-0x09 store uses 0xBB. The original 0xAA capture is not a substitute.

7. **Captured dispatch arguments.** If the second argument is captured as 0x2000, the final doubled-address word store targets 0x4000, subject to the address model. Later overwriting its original offset-0x64 storage does not change the represented dispatch argument.

8. **Fourth-argument retention.** If the fourth capture yields a particular word, a subsequent aliasing final-link store does not cause that argument to be reloaded.

9. **Nonreturning dispatch.** If F-U002 does not return, this operation need not return. Prior mutations are not specified to be undone.
