# F-499802108227

## Purpose

F-499802108227 conditionally searches a context-associated collection, dispatches the first nonzero match, and then processes a descriptor’s entries and allocation-accounting metadata.

Search admission depends on a state byte and a prerequisite dependency. For a nonnull descriptor, cleanup and accounting proceed independently of whether search was skipped, succeeded, or reported no match, provided the intervening dependencies return normally.

Earlier calls and accounting writes occur before allocation-header validation. No rollback is visible in this function. The nonreturning failure dependency’s effects are unknown, including whether it changes previously affected state before terminating.

“Search,” “descriptor,” “cleanup,” and “allocation” describe inferred roles. They do not establish domain types, ownership, or dependency semantics.

## Interface

### Arguments and result

The function accepts three arguments:

| Argument | Representation | Observed use |
|---|---|---|
| Context handle | Address of a 32-bit word | The word supplies a state-object address; the handle is also passed to dependencies |
| Descriptor | Address interpreted as structured storage and an allocation payload | Supplies search values, cleanup entries, and allocation-prefix access |
| Diagnostic suppression | 32-bit integer | Zero permits the unmatched diagnostic; any nonzero value suppresses it |

The context word is read immediately, before descriptor-null checking or any dependency call. The captured state-object address remains the search-state address even if the prerequisite changes the context word.

There is no explicit return value. Normal completion returns control to the caller; dependency termination or invalid memory access can prevent completion.

The representation uses 32-bit addresses and ordinary words, signed 16-bit descriptor counts, and unsigned 16-bit allocator selectors. Endianness and alignment requirements are not established.

### State and record layouts

The captured state-object address supports these accesses:

| Byte offset | Width | Interpretation |
|---|---:|---|
| +4 | Signed 32 bits | Search count, reread at each traversal test |
| +8 | 32 bits | Search-record array address |
| +30 | 8 bits | Nonzero inhibits search |

Search records have a 24-byte stride:

| Record-relative offset | Width | Use |
|---|---:|---|
| +0 | 32 bits | First filter argument |
| +20 | 32 bits | Address value to which 44 bytes are added for matching |

### Descriptor layout

| Byte offset | Width | Use |
|---|---:|---|
| +0 | Signed 16 bits | Cleanup-entry count |
| +8 | 32 bits | Search filter and first cleanup-entry field |
| +12 | 32 bits | Search value and second cleanup-entry field |

Cleanup entries begin at descriptor offset +8 and have a 48-byte stride. Their accessed 32-bit fields are at entry-relative offsets +0, +4, +8, +12, +16, +28, and +32.

Search reads descriptor offsets +12 and +8 regardless of the cleanup count. A zero or negative cleanup count does not eliminate those search accesses.

### Preconditions

Every reached memory access requires suitable readable or writable storage. This includes the context word, state object, selected records, descriptor, allocation prefixes, global-pointer storage, accounting objects, and selected allocator counters.

A null descriptor avoids direct descriptor accesses only if search is skipped. The descriptor-null check follows the search phase.

Array capacity must cover the actual record selection, not merely an assumed zero-based prefix: a search count of one selects record index one.

No visible validation establishes selector bounds, pointer validity, allocation size consistency, synchronization, or safe handling of malformed metadata.

## Behavior

### 1. Search admission

After capturing the state-object address, the function reads its byte at +30.

- A nonzero byte skips search, including the prerequisite dependency.
- A zero byte causes F-10ba02f1ed27 to receive the context handle.
- Only a zero prerequisite result admits search.

Skipped search produces neither dispatch nor an unmatched diagnostic here. Execution continues to descriptor cleanup.

The prerequisite may mutate memory or globals. Subsequent search accesses nevertheless use the initially captured state-object address.

### 2. Search preparation

An admitted search performs these operations in order:

1. Read the 32-bit search value at descriptor offset +12.
2. Read the 32-bit filter at descriptor offset +8.
3. Call F-1cb585febd84 with the captured search value.
4. Retain its 32-bit result for matching.

The search value and filter are captured once. Later changes to the descriptor do not refresh them.

### 3. Candidate traversal

The traversal counter starts at zero. Before each candidate, it is compared as a signed 32-bit value with the freshly read signed count at state offset +4. An initially nonpositive count admits no candidates.

The selected record indices are 1, 0, 2, 3, and onward. Thus, with a stable count of four, traversal examines records in that order; with a stable count of one, it examines only record one.

For each selected record:

1. A captured filter of zero bypasses F-e6db2171781a.
2. Otherwise, that dependency receives the record’s field at +0 and the captured filter.
3. A nonzero filter result skips matching for this candidate.
4. With filtering bypassed or a zero filter result, the function reads the record’s address field at +20 and adds 44 bytes.
5. F-a09bb08bf954 receives that resulting address, the captured search value, and the preparation result.
6. A zero match result permits traversal to continue. The first nonzero result ends traversal immediately.

The array address at state offset +8 is loaded for individual record accesses. If filtering calls a dependency, the subsequent match-related access can use a different array address. No preservation of the array address, records, count, or globals is established.

### 4. Dispatch and unmatched handling

The first nonzero match result is passed to F-cb1bc0706bec together with the context handle. No subsequent candidate is examined.

If admitted traversal ends without a nonzero result:

- Zero diagnostic suppression causes F-2022b0f73f3b to receive the context handle and a fixed diagnostic reference.
- Nonzero suppression omits that call.

This includes admitted searches whose initial count is nonpositive.

The diagnostic’s exact text and formatting are not established. An unmatched-target report is inferred intent.

If the invoked dependency returns, execution continues to cleanup. There is no separate returned success or failure status.

### 5. Descriptor-entry processing

A null descriptor returns after search handling.

For a nonnull descriptor, entries are traversed from descriptor offset +8 with a 48-byte stride. At each loop-condition evaluation, the function first captures the accounting-global address and then reads the descriptor’s signed 16-bit count. This includes the final condition evaluation that ends traversal.

A nonpositive initial count produces no entry calls. Otherwise, each entry is processed in this order:

| Order | Dependency | Entry-relative field |
|---:|---|---:|
| 1 | F-94cb53877c15 | +0 |
| 2 | F-94cb53877c15 | +4 |
| 3 | F-94cb53877c15 | +8 |
| 4 | F-da1a289a3277 | +12 |
| 5 | F-6c7ac9769d41 | +16 |
| 6 | F-841dc33ee157 | +28 |
| 7 | F-11bd3a21366b | +32 |

Each field is read when its call is reached. Earlier callbacks can therefore affect later field values and subsequent count tests.

The first F-94cb53877c15 call is presented with a second, context-related argument; the following two calls are presented with only the field argument. For the first entry, the context-related argument is the original context handle. For subsequent entries, an unresolved secondary return-register value is propagated into that position. Its meaning and the complete calling convention remain unknown.

The function retains the accounting-global address captured by the final loop-condition evaluation for a later high-word write.

### 6. Allocation identification and accounting

For the nonnull descriptor, the function reads a 32-bit displacement at descriptor offset −4. Subtracting that displacement from the descriptor address produces the derived allocation address.

It then reads a 32-bit accounting amount at derived-address offset −8.

Accounting uses words at offsets +56 and +60, but its pointer evaluations must be distinguished. In order, the function:

1. Evaluates the accounting-global pointer and reads the low word at +56.
2. Evaluates that global pointer again and forms a high-word source pointer at +60, without yet reading that word.
3. Evaluates the global pointer again and writes the low-word subtraction result at +56.
4. Reads the high word through the source pointer formed in step 2.
5. Writes the adjusted high word at +60 through the address cached by the final cleanup-loop condition.

These pointer evaluations are not established to identify the same object. In particular, the high-word source read occurs after the low-word write; aliasing must not be ruled out.

The low result is the captured low word minus the captured amount, modulo 2³². The high adjustment subtracts:

- The amount’s arithmetic sign extension: zero when its top bit is clear, or negative one when set.
- An unsigned borrow, equal to one when the captured low word is less than the amount, otherwise zero.

The high result is also 32-bit modular arithmetic.

Under an explicit stable-address assumption, this implements subtraction of a sign-extended 32-bit amount from a two-word value. It is not generally subtraction of a zero-extended unsigned amount. Without address stability, it must be understood as the distinct reads and writes above, not as one coherent two-word update.

Next, F-2fd8826557a4 is called. After it returns, the function reads an allocator-context address through a separate global pointer.

Only then does it compare the derived allocation address with numeric address eight. Equality skips the remaining allocation processing. It does not skip the preceding prefix reads, accounting writes, dependency call, or allocator-context read.

### 7. Header validation and allocator updates

For a derived allocation address other than eight, the header address is sixteen bytes before that address.

The function first reads the 32-bit header to test for zero. If that read is nonzero, it reads the header again to test bit zero. A zero first read, or bit zero set in the second read, invokes F-a817d8d58c10, represented as nonreturning.

Validation therefore precedes the following allocator updates but follows global accounting.

If validation passes, the observable sequence is:

1. Call F-c0fc6d033caa with the captured allocator-context address.
2. Read the unsigned 16-bit selector at derived-address offset −12.
3. Compute the allocator-relative address using four times that selector.
4. Only then reread the allocation header and mask it with `0x3ffffffc` to obtain the size used for the next four subtractions.
5. Subtract that size from the 32-bit counter at allocator offset +548 plus four times the first selector.
6. Subtract the same size from allocator offset +780.
7. Read the unsigned 16-bit selector at derived-address offset −10 and form its allocator-relative address.
8. Subtract the same size from allocator offset +224 plus four times the second selector.
9. Subtract the same size from allocator offset +544.
10. Call F-09dcb55e8e0a and use its result to select the counter at allocator offset +784 plus four times that result.
11. Decrement that counter, then decrement the counter at allocator offset +912.
12. Reread the allocation header, mask it with `0x3ffffffc`, and subtract this newly obtained size from allocator offset +8.
13. Call F-cc6c9b4a0f68 with the allocator context and header address.
14. Call F-e586bff64fb7 with the allocator context.

The allocator-context address is captured before header validation and retained across these calls.

The post-F-c0fc6d033caa header read and the later header read are not revalidated. They can differ from the validation reads and from each other if intervening effects change the header.

All described counter updates are 32-bit modular operations. No visible checks prevent underflow or an out-of-range selector or dependency-supplied index. Address computations use the supplied 32-bit representation; this contract does not establish portable behavior for invalid or overflowing addresses.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Each assumes valid storage and normal dependency returns unless stated otherwise.

1. **Inhibited search with null descriptor.** A nonzero inhibition byte prevents the prerequisite call. The subsequent null check returns without descriptor cleanup or accounting.

2. **Admitted search with null descriptor.** A zero inhibition byte and zero prerequisite result lead to a read at descriptor offset +12 before any descriptor-null check. Null is not a valid descriptor for this path.

3. **Record order.** With a stable count of three, stable records, and no successful match, selected indices are 1, 0, 2. With count one, only index one is selected.

4. **Disabled filtering.** A captured filter of zero produces no F-e6db2171781a calls. Each reached candidate proceeds directly to matching.

5. **First match wins.** A nonzero result from matching record one is dispatched once. Record zero and later records are not examined; no unmatched diagnostic is requested.

6. **Suppressed miss.** An admitted search with no match and nonzero suppression makes no diagnostic call. A nonnull descriptor still reaches entry processing and accounting.

7. **Nonpositive entry count.** No entry callbacks occur, but the accounting-global address is still captured at the terminating condition. Allocation-prefix reads and accounting follow.

8. **Stable accounting with borrow.** Assuming every accounting address identifies the same object, amount one, low word zero, and high word five produce low `0xffffffff` and high four.

9. **Stable accounting with a negative signed amount.** Under the same stability assumption, amount `0xffffffff`, low zero, and high five produce low one and high five.

10. **Distinct accounting locations.** If the separate evaluations identify distinct objects, the low destination receives the result computed from the first low source. The high source is read after that write, and the high destination remains the object cached at the final cleanup condition. No single-object two-word result is required.

11. **Post-call header change.** If F-c0fc6d033caa changes the first selector and header, the function reads the changed selector and computes its allocator-relative address before reading the changed header size. That size is not revalidated.

12. **Invalid header.** A zero initial header read invokes the nonreturning failure dependency after accounting and F-2fd8826557a4. Ordinary allocator-counter updates are not subsequently reached. The failure dependency’s own state changes remain unknown.

13. **Derived address eight.** Header validation and allocator updates are skipped, but earlier prefix accesses and accounting still occur. This comparison does not make otherwise invalid prefix storage acceptable.
