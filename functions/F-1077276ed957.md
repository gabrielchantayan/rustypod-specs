# F-1077276ed957

## Purpose

F-1077276ed957 conditionally handles an event through a small set of command-specific actions, then optionally forwards the event through a secondary receiver.

The established behavior has two stages:

1. Examine event flags and type; when eligible, classify the event and select one of four recognized actions.
2. Unless an earlier path returns, inspect an object-state bit and, when enabled, construct or obtain an intermediate object and dispatch it to a receiver.

The return value is an unsigned 32-bit value. Some paths return exactly 1; others return a dependency’s result, a captured state bit, or 0. A nonzero result may indicate that an event was handled, but that interpretation is inferred rather than established.

## Interface

### Inputs

The function accepts two address-valued arguments:

- **Primary object:** a pointer to an object containing state words, a receiver reference, and a dispatch-table pointer.
- **Event:** an address identifying an event record.

The supplied representation uses 32-bit words and addresses. The event argument is represented as a 32-bit integer but is used as an address. No validation, null handling, or bounds checking is established for either input.

### Additional object layouts

A non-null intermediate object is subsequently accessed through its dispatch-table address at byte offset +0x00. The entry at table byte offset +0x04 is invoked with that intermediate object.

These offsets are byte offsets, not dispatch-slot numbers.

### Output and preconditions

The output is a 32-bit unsigned result. Results obtained from dependencies or dispatch calls are not normalized to a Boolean.

Execution requires that every address actually dereferenced along the selected path be valid and appropriately laid out. In particular:

- The primary object must support every state or dispatch read reached.
- A fallback receiver must be valid when fallback dispatch is enabled.
- A non-null intermediate object must support its post-dispatch callback.

There is no explicit recovery path for invalid addresses, missing dispatch entries, or dependency failures.

## Behavior

### 1. Determine eligibility for command-specific handling

The function first reads the event’s 32-bit flags word at +0x10.

The flags condition succeeds when either:

- All bits selected by 0xFF000000 are zero; or
- Bit 0x01000000 is set.

The lower 24 bits do not affect this decision.

The expression is short-circuited. When the first flags read has a zero high byte, no second flags read is needed. When that test fails, the function reads the flags word again to test 0x01000000. Consequently, this is not necessarily a single-snapshot predicate when the backing storage can change between reads.

Only after the flags condition succeeds does the function read the event type at +0x04. Type 13 is accepted immediately. Otherwise, the type is read again and compared with 7.

For stable event storage, command-specific eligibility is therefore:

- The flags high byte is zero or has its least-significant bit set; and
- The type is 13 or 7.

If eligibility fails, command-specific classification is skipped and execution proceeds to the fallback stage.

### 2. Classify an eligible event

For an eligible event, F-11c1b7e655b3 is called with the event address.

Its returned classification is compared with 16, 87, 88, and 111. No other classification receives command-specific handling.

Classification values are compared exactly. There is no range matching or truncation to an 8-bit command value.

### 3. Process classification 16

F-3582bc2328c6 is called with:

- The primary object.
- A 32-bit value read from a fixed data location referenced by this function.

The contents and meaning of that fixed value are unknown.

If the dependency returns a nonzero 32-bit value, the function returns that value unchanged. The fallback state bit is not inspected on this path.

If the dependency returns zero, execution proceeds to the fallback stage. A zero result therefore permits another dispatch rather than necessarily determining the final return value.

### 4. Process classification 87

The function invokes the primary object’s dispatch-table entry at byte offset +0x1AC with:

- The primary object.
- The integer 1.

After that call returns normally, F-1077276ed957 returns exactly 1. The dispatched call’s return value does not determine the function’s result, and fallback processing does not occur.

### 5. Process classification 88

F-b9205949e132 is called with the primary object.

After that call returns normally, F-1077276ed957 returns exactly 1. Any dependency result is ignored, and fallback processing does not occur.

### 6. Process classification 111

This path first reads the primary-object word at +0x124 and captures bit 0x00000008 as either 0 or 1. The capture is an unsigned mask followed by a three-bit right shift; no other bits contribute.

The function then:

1. Calls F-b3f4a7a52609 with the primary object.
2. Invokes the primary object’s dispatch-table entry at byte offset +0x17C, passing the primary object and the dependency’s 32-bit result.

Both calls occur regardless of whether the captured bit was zero or one.

If the captured bit was one, the function returns exactly 1 after the dispatch call completes.

If the captured bit was zero, execution proceeds to the fallback stage.

The decision uses the earlier capture, not a reread of +0x124. Changes made to that word by either call do not alter this particular return decision. Other state changes may affect the fallback stage.

### 7. Process an unrecognized classification

Any classification other than 16, 87, 88, or 111 proceeds directly to fallback processing.

### 8. Perform optional fallback dispatch

The fallback stage is reached after an eligibility failure, an unrecognized classification, a zero result for classification 16, or a zero captured bit for classification 111.

The default result at this stage is zero.

The function reads the primary-object word at +0x48 and tests 0x08000000. This read occurs after any preceding command-specific calls. It is not a state snapshot taken at entry.

If the bit is clear, the function returns zero without invoking the fallback dependencies.

If the bit is set, the function performs the following ordered operations:

1. Call F-f2ddcdbfb0c6 without arguments.
2. Pass its 32-bit result and the integer 16 to F-c5a232e4455b.
3. Pass that result, the event address, and the primary object to F-589860a89654.
4. Treat the result of F-589860a89654 as an intermediate-object pointer.
5. Invoke the fallback receiver’s dispatch-table entry at byte offset +0x30, passing the receiver and the intermediate-object pointer.
6. Save the receiver call’s 32-bit result.
7. If the intermediate-object pointer is non-null, invoke its dispatch-table entry at byte offset +0x04.
8. Return the saved receiver result.

The receiver call occurs even if the intermediate-object pointer is null. Null suppresses only the subsequent intermediate-object callback.

The receiver reference is obtained from the primary object’s +0x38 field as part of preparing the receiver dispatch, after the three preceding dependency calls. It must not be treated as a reference captured at function entry. The expression does not establish a portable ordering among every individual dispatch-table and receiver-argument load; validity and consistency of that field remain preconditions.

The intermediate-object callback’s return value is ignored. The saved receiver result remains the return value if that callback completes normally.

No ownership transfer to the receiver is established. No reference-counting rule is established. The function’s unconditional post-dispatch access to a non-null intermediate object requires that the object remain suitable for that access.

There is no explicit cleanup path if a dependency or dispatch call fails to return normally.

## Acceptance examples

These are conditional contract examples, not runtime test results. Unless stated otherwise, inputs remain stable between repeated reads and all invoked calls return normally.

1. **Flags reject command-specific handling.**  
   With flags 0x02000000, the high byte is nonzero and 0x01000000 is clear. Classification is skipped regardless of event type. If the fallback-enable bit is clear, the result is 0.

2. **Other high-byte bits do not necessarily reject eligibility.**  
   With flags 0x03000000 and type 7, the flags condition succeeds because 0x01000000 is set. Classification occurs.

3. **Event type still gates classification.**  
   With flags 0 and type 8, classification does not occur. An enabled fallback still runs.

4. **Classification 16 preserves a non-Boolean result.**  
   If F-3582bc2328c6 returns 0x80000002, the function returns 0x80000002 unchanged and does not inspect the fallback-enable bit.

5. **Classification 16 can continue into fallback.**  
   If F-3582bc2328c6 returns 0 and the subsequently observed fallback-enable bit is set, the fallback chain runs. Its receiver result determines the return value.

6. **Classification 87 has a fixed result.**  
   The +0x1AC dispatch entry receives the primary object and 1. After it returns, the function returns 1 even if the callback returned zero or changed the fallback-enable bit.

7. **Classification 111 uses a captured bit.**  
   If +0x124 initially contains bit 0x00000008, both classification-specific calls execute and the function then returns 1, even if those calls clear that bit.

8. **A later bit set does not replace the capture.**  
   If the captured bit was zero but the +0x17C callback sets it, execution still reaches fallback. The later read of +0x48 independently decides whether forwarding occurs.

9. **Null intermediate result still reaches the receiver.**  
   If F-589860a89654 returns null, the receiver is called with null. No intermediate-object callback follows. The receiver result is returned unchanged.

10. **Non-null intermediate result is followed by its callback.**  
    If the receiver returns 9 and the intermediate pointer is non-null, the +0x04 callback runs before the function returns 9. Its own return value does not replace 9.
