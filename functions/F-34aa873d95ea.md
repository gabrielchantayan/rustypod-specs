# F-34aa873d95ea

## Purpose

F-34aa873d95ea performs a bounded, first-match lookup over a table of fixed-stride records. It compares a supplied unsigned key against a 16-bit field in each record and returns the 32-bit value associated with the earliest matching record. If no record matches, it returns zero.

The established behavior is an ordered lookup, not a uniqueness check. Duplicate keys are permitted by the visible operation; later duplicates do not affect the result once an earlier match has been found.

The apparent intent is to retrieve a value associated with a compact numeric identifier. The meaning of that identifier and whether the returned value represents an integer, address, handle, or another four-byte representation are not established.

The caller does not supply the table base, its size, or a record count as explicit arguments.

**Output**

The returned representation has no established signedness or higher-level type beyond its four-byte width. Zero is not a separate status channel: a successful match can also return zero.

## Behavior

### Search range and order

The lookup begins with record index zero and examines records in ascending index order. There are exactly 205 eligible indices: zero through 204 inclusive.

For each examined record, the function first reads its unsigned 16-bit key at record-relative offset 10. It compares that key numerically with the entire unsigned 32-bit input.

If the values are equal, the function reads the four-byte value at record-relative offset 4 and returns it immediately. It does not inspect any later record.

If the values are unequal, the search proceeds to the next record. After a mismatch at index 204, the function returns zero.

The table is therefore not terminated by a sentinel key, a zero value, or an empty-looking record. Its search bound is fixed independently of record contents.

### Comparison width

The stored key ranges from 0 through 65,535. Its comparison with the input preserves that unsigned numeric value.

The input is not truncated to 16 bits. Consequently:

- Inputs from 0 through 65,535 can match stored keys.
- Inputs from 65,536 through 4,294,967,295 cannot match any stored key.
- A large input does not match a key merely because its low 16 bits equal that key.

There is no visible early rejection for an input above 65,535. Such an input still follows the bounded search and reads all 205 key fields, provided those reads complete normally.

### Read ordering and early return

The established table-field read order is:

1. Read the current record’s key.
2. If it matches, read that record’s associated value and return.
3. Otherwise, advance to the next record’s key.

Although the associated value is located at a lower byte offset than the key, the lookup examines the key before fetching the value.

For an ordinary stable table:

- A match at index zero entails one key-field read and one value-field read.
- A match at index 204 entails 205 key-field reads and one value-field read.
- No match entails 205 key-field reads and no value-field read.

These counts describe the visible table-field accesses. They are not a claim about processor bus transactions, compiler-generated loads, or the number of reads used to obtain the table base.

### Arithmetic and bounds

Record addressing uses a 20-byte stride. The last searched record begins at offset 4,080 from the table base.

The relevant final-record offsets are:

- Value field: offsets 4,084 through 4,087.
- Key field: offsets 4,090 through 4,091.

The unsigned 32-bit search index starts at zero and advances by one after a mismatch. Its greatest value before leaving the search is 205. Neither that increment nor the record-offset multiplication approaches 32-bit overflow.

This bounded arithmetic does not establish that adding an offset to the externally supplied table base is safe. Address validity remains a memory precondition.

### Return-value ambiguity

A matching record whose associated value is zero produces the same returned bit pattern as a failed lookup.

The function exposes no additional result indicating:

- Whether a match occurred.
- Which record matched.
- How many records were examined.
- Whether duplicate keys exist.

Consumers cannot distinguish a zero-valued match from absence using the return value alone.
