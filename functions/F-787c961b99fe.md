# F-787c961b99fe

## Purpose

F-787c961b99fe acquires three nonzero resource values, publishes them and two endpoint values into a caller-provided record, and delegates final initialization. Its 32-bit return value reports success as 1 and failure as 0.

Publication is **not transactional**. A failed invocation can leave resource values and endpoint values in the record even after those resources have been submitted for cleanup. The return value alone does not establish that the record is unchanged, usable, or safe to release.

The apparent purpose is construction of a record associated with an inclusive range and a collection of fixed-size entries. That interpretation is inferred from the size calculations; the domain meanings of the record and resources are not established.

This contract is based on static evidence only. No runtime tests have been performed.

### Result and error boundary

The represented return width is 32 bits:

- **1** means all three acquisition results were nonzero and the final initializer returned nonzero.
- **0** means an acquisition returned zero or the final initializer returned zero, with the applicable cleanup calls completed normally.

A nonzero initializer result is normalized to 1; its original magnitude or sign is not returned.

These guarantees assume normally returning dependencies, valid memory accesses, and defined arithmetic. There is no visible mechanism that converts an arithmetic fault, invalid access, or nonreturning dependency into a zero result.

## Behavior

### Size requests and arithmetic domain

The first requested size is twice the inclusive difference between the full-width endpoints:

**2 × (second endpoint − first endpoint + 1)**

The subtraction precedes addition of one, which precedes multiplication by two. The endpoint values used here are the signed 32-bit arguments, not their eventual 16-bit record representations.

The second requested size is:

**20 × entry count**

This second calculation is reached only after the first acquisition has returned nonzero and its result has been published.

There is no explicit rejection of reversed endpoints, negative operands, zero requests, out-of-range endpoint conversions, or arithmetic overflow. The constants describe size requests passed to a dependency; whether that dependency measures them in bytes is not established here.

For a portable, non-overflowing signed 32-bit interpretation:

- Each intermediate endpoint calculation must fit the signed 32-bit range.
- A positive first request requires an inclusive endpoint count from 1 through 1,073,741,823.
- A nonnegative entry count must not exceed 107,374,182 for multiplication by 20 to remain representable.

These are arithmetic preconditions, not checks performed by the function. They also do not establish that the acquisition dependency accepts the resulting sizes.

Behavior outside the representable arithmetic domain is documented_only. The function text does not establish whether a particular executable wraps, traps, or exhibits another consequence.

### Acquisition and publication guarantees

The first two resource values come from F-638beded7699. Both requests carry the additional value 45. Zero is treated as failure; every nonzero result is accepted without further validation.

The first resource is published at offset 4 before the second acquisition is attempted. The second resource is published at offset 8 before either of the dependencies associated with the third acquisition is called.

The third acquisition has a preparation dependency: F-8157a180d901 receives 184 before F-a891c2749310 is invoked without explicit arguments. No result from the preparation dependency is tested. Its normal return is sufficient for execution to continue; it has no separately checked failure outcome.

A nonzero result from F-a891c2749310 is published at offset 16. Only after this publication are the endpoint fields written, first at offset 0 and then at offset 2.

**offset 4, offset 8, offset 16, offset 0, offset 2.**

That order applies to the stores that are reached. An acquisition failure prevents the later publications and final initialization.

## Side effects

### Record state

Publication is incremental and overwrites existing field contents without preserving them. There is no direct rollback, clearing, or restoration.

After second-acquisition failure, offset 4 still contains the first published result unless a dependency has changed it. After third-acquisition failure, the same limitation applies to offsets 4 and 8. After initializer failure, all five fields have been written, and none is explicitly restored.

These are guarantees about this function’s writes, not guaranteed final record contents. Dependencies may mutate reachable memory, and the final initializer receives the record pointer directly.

Bytes 12–15 are not directly initialized. The function also performs no direct initialization or inspection of the contents addressed or represented by the acquired resource values.

### Resource retention and ownership

On success, this function makes no explicit cleanup calls. This establishes retention by the visible function, not an ownership-transfer policy. The eventual release responsibility is unknown.

On failure after acquisition, the function submits the acquired nonzero results for cleanup in acquisition order, not reverse order. It does not check whether another dependency has already released them.

No dependency is assumed to preserve globals, leave the record unchanged, retain resources, or refrain from releasing them. For example, if the final initializer releases a resource and then returns zero, this function still submits the retained result for cleanup. The validity of that interaction requires an external ownership contract.

### Other state and failure effects

F-8157a180d901 may alter state that affects F-a891c2749310, but that relationship is not established beyond call order. Its effects are not explicitly undone after later failure.

Effects of the final initializer are likewise not reversed. The visible failure handling addresses only the three acquired result values.

There is no directly established diagnostic output, stored error code, or error classification beyond the binary return value. Dependencies may have additional effects.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless otherwise specified, they assume valid reached memory accesses, representable arithmetic, and normally returning dependencies.

### Successful construction

For endpoints 10 and 12 and entry count 3, the acquisition size requests are 6 and 60, each accompanied by 45.

If both requests return nonzero, the preparation dependency receives 184. If the third acquisition also returns nonzero, its result and the endpoint values are published before final initialization. An initializer result of 7 produces a function result of 1. No explicit cleanup occurs.

The request values are established; interpreting them as byte counts requires the acquisition dependency’s contract.

### Initial acquisition failure

If the first acquisition returns zero, the function returns zero without directly reading or writing the record. There is no second acquisition, preparation call, third acquisition, final initialization, or cleanup submission.

This does not establish that the first dependency has no side effects.

### Second acquisition failure

If the first acquisition returns a nonzero resource and the second returns zero, only the first resource has been directly published. Cleanup receives that retained resource and 45, and the function returns zero.

No endpoint field is directly written. The published first-resource field is not cleared.

### Third acquisition failure

If both initial acquisitions succeed but the third returns zero, preparation has already occurred. Both initial resource fields have been written, but neither endpoint nor the third-resource field has been directly written.

Cleanup receives the first resource and then the second. There is no explicit reversal of preparation effects.

### Initializer failure with record mutation

Suppose all acquisitions succeed and the initializer changes the record’s first-resource field before returning zero.

Cleanup still receives the originally retained first resource, followed by the retained second and third resources. The replacement record value does not become the cleanup operand. The function does not restore the overwritten field.

### Repeated resource representation

Suppose the first and second acquisitions return the same nonzero value, and the third acquisition fails.

The visible failure behavior requires two cleanup calls with that value and 45. This example is valid only if the dependency contracts permit those results and repeated submissions; the function itself does not prevent them.

### Narrowed endpoints

For endpoints 65,536 and 65,537, the first size request is 4 because allocation arithmetic uses the full-width endpoints.

If the target’s signed 16-bit conversion retains the low 16 bits, publication produces endpoint bit patterns 0 and 1. That conversion rule is a condition of this example, not independently established portable behavior for out-of-range endpoints.

### Zero-sized and boundary requests

Endpoints 5 and 4 produce a first request of zero without arithmetic overflow. The function still invokes the acquisition dependency; continuation depends on its result.

An entry count of zero similarly produces a zero second request when that stage is reached.

An entry count of 107,374,182 produces 2,147,483,640. Increasing that count by one exceeds the positive signed 32-bit range after multiplication by 20; no executable outcome for that overflow is specified here.
