# F-78f2b8a816ac

## Purpose

F-78f2b8a816ac performs an in-place, word-oriented multiply-and-accumulate operation. It traverses a source sequence, multiplies each decoded source word by a 32-bit unsigned scalar, adds the product into a destination sequence starting at a supplied word position, and propagates carry toward higher positions.

The operation uses shared configuration words to interpret sequence lengths and to transform stored payload words. Their values are not supplied. Consequently, ordinary unsigned multiword arithmetic is an **inferred intent**, not an unconditional description of every possible configuration.

The established behavior includes several important qualifications:

- The destination’s initial interpreted length determines whether an existing payload word contributes to an addition.
- Writes are not bounded by that length.
- Source payload reads remain live throughout traversal; overlapping source and destination storage can affect subsequent calculations.
- The destination header may be updated after arithmetic finishes, including when no payload word was processed.
- Successful completion returns zero. No explicit error-return path is present.

## Interface

### Arguments

The function receives four arguments:

1. **Destination descriptor address.** Refers to a descriptor containing at least:
   - At byte offset 0: a 32-bit header interpreted through signed arithmetic.
   - At byte offset 4: a 32-bit payload address.

   The header and payload are writable where the operation requires writes.

2. **Starting destination position.** A signed 32-bit word index. Each advance increases the position by one, and each payload address is formed using a four-byte word stride.

3. **Source descriptor address.** Refers to a descriptor with the same two visible fields:
   - At byte offset 0: a 32-bit header.
   - At byte offset 4: a 32-bit payload address.

   Source payload words are read, not explicitly written through the source descriptor. Aliasing can nevertheless make destination writes modify source storage.

4. **Multiplier.** An unsigned 32-bit scalar.

The visible layout uses 32-bit stored addresses and four-byte payload words. It does not establish byte order, required alignment, or the complete descriptor layout.

### Shared configuration

Four shared 32-bit words participate in the operation. This contract names them by role:

| Role | Use |
|---|---|
| Length interpretation factor | Multiplies descriptor headers before length comparisons |
| Header encoding factor | Multiplies the ending destination position when updating the destination header |
| Payload decoding factor | Multiplies stored source and destination words before arithmetic |
| Payload encoding factor | Multiplies computed result words before storage |

These role names do not establish that either pair of factors consists of inverses, that their values are nonzero, or that they remain stable under external modification.

### Return value and ownership

On every visible normal-return path, the function returns a 32-bit zero.

No allocation, release, ownership transfer, or payload-address replacement is visible. The caller must provide accessible storage for every actual read and write. The function contains no capacity argument and performs no visible capacity check.

Header multiplication, magnitude formation, position increments, and address calculations also involve 32-bit values, but the supplied representation does not establish a portable signed-overflow policy. A conservative acceptance domain therefore requires that:

## Behavior

### Initial interpretation

The source header is read first and multiplied by the length interpretation factor. If the resulting signed value is negative, it is negated. This establishes the source traversal count.

The destination header is then read and treated in the same way, establishing the destination’s original interpreted length.

Both values are computed before payload processing. The source traversal count is not recomputed as destination writes occur. The original destination length likewise remains the threshold for deciding whether destination payload contributes to subsequent additions.

The carry starts at zero.

For signed products other than the minimum signed 32-bit value, this construction produces a nonnegative magnitude. The exceptional minimum value is addressed under uncertainties.

### Source traversal

The function processes source positions in increasing order, starting at zero and stopping at the previously established source count. The destination position starts at the supplied signed position and advances once for each processed source word.

For each source position:

1. **Select the existing destination contribution.**

   If the current signed destination position is less than the original destination length, the function reads that destination payload word and multiplies it by the payload decoding factor. The resulting 32-bit word contributes to the addition.

   Otherwise, the contribution is zero, and the destination payload word is not read for this purpose.

   This condition does not test that the position is nonnegative. A negative starting position can therefore cause accesses before the nominal payload base.

2. **Read and decode the source word.**

   The source payload word at the current source position is read and multiplied by the payload decoding factor. Its resulting 32-bit bit pattern is treated as unsigned.

3. **Form a full-width product.**

   The decoded source word is multiplied by the unsigned scalar to obtain a 64-bit unsigned product.

4. **Add the product, destination contribution, and incoming carry.**

   Let \(B = 2^{32}\). Let \(p\) be the full product, \(d\) the selected destination contribution, and \(c\) the incoming carry.

   The result word is:

   \[
   r = (p + d + c) \bmod B.
   \]

   The outgoing carry is formed from the high 32 bits of \(p\), plus the unsigned carry from adding \(d\) to the low product word, plus the unsigned carry from adding the incoming carry to that intermediate low word.

   These are word carries, not signed-overflow indicators. For unsigned 32-bit inputs, the total \(p+d+c\) fits within 64 bits.

5. **Encode and write the result.**

   The low result word is multiplied by the payload encoding factor, and the resulting 32-bit word is written to the current destination position.

6. **Advance the destination position.**

   The position increases by one.

The destination contribution is evaluated before the source product, and the destination write occurs after both contributions have been obtained. The supplied representation does not establish a complete machine-level order among all shared-factor and pointer-field reads within individual expressions.

A zero scalar does not skip traversal. Source words are still read, qualifying destination words are still read, and result words are still written.

### Carry propagation

After source traversal, processing continues while carry is nonzero.

At each carry position:

- If the position is less than the original destination length, the corresponding destination word is read and decoded.
- Otherwise, the destination contribution is zero; no existing payload value at that position contributes.
- The incoming carry and destination contribution are added as unsigned 32-bit words.
- The low word is multiplied by the payload encoding factor and written.
- The next carry is the unsigned carry-out of that addition.
- The destination position increases by one.

After the first propagation addition, carry is either zero or one.

At a position at or beyond the original destination length, the contribution is zero, so the incoming carry is stored and the carry becomes zero. Subject to valid position arithmetic, this ends propagation.

Existing storage beyond the original length is therefore ignored, not incorporated. Its previous contents can be overwritten.

### Final header update

After all payload work, the destination header is read again. The function multiplies that current header by the length interpretation factor and compares the signed result directly with the ending destination position.

Unlike the initial length calculation, this final comparison does **not** take a magnitude.

If the interpreted current header is less than the ending position, the function writes the ending position multiplied by the header encoding factor into the destination header. Otherwise, it leaves that header unchanged.

Consequences include:

- The update decision uses the current header, not necessarily the initially read value.
- A negative interpreted header can trigger an update even when its magnitude already covered all processed positions.
- The header can change without any payload access if the source traversal is empty and the supplied starting position satisfies the final comparison.
- There is no visible trimming of zero-valued high words.

The function then returns zero.

## Side effects

### Writes

The visible write targets are:

- Consecutive destination payload positions reached during source traversal.
- Additional consecutive destination payload positions required by carry propagation.
- The destination header, conditionally, after payload processing.

The function does not explicitly modify either descriptor’s payload-address field.

### Reads and aliasing

The function does not snapshot the source payload. Each source word is read when its traversal step is reached.

If an earlier destination write overlaps a source word that will be read later, the later operation can consume the modified value. The result is not guaranteed to equal multiplication of the original source sequence.

Payload-address fields are referenced during processing rather than visibly copied into a single immutable base for the entire operation. If destination writes overlap descriptor fields, later accesses may therefore be affected. Safe, ordinary sequence use should keep descriptors outside payload write regions.

No non-aliasing precondition is enforced by the function itself.

### Failures and partial mutation

There are no visible checks for null pointers, invalid payload addresses, insufficient capacity, malformed descriptors, or negative starting positions.

An invalid access or other execution-environment failure can occur after earlier writes have completed. No rollback is visible. Zero is a normal completion result, not evidence that input validation or capacity checks occurred.

No synchronization is visible. Concurrent modification of descriptors, payloads, or shared configuration is outside the established deterministic acceptance domain.

## Acceptance examples

These examples are conditional contracts, not runtime observations. Unless stated otherwise, all four shared factors equal one, storage is valid and sufficiently large, descriptors do not overlap payloads, and position arithmetic is representable. Sequences list words in traversal order.

### Multiply and accumulate within the existing destination

Given:

- Source header: 2; source payload: \([3,4]\).
- Destination header: 3; destination payload: \([10,20,30]\).
- Starting position: 1.
- Scalar: 2.

The destination becomes \([10,26,38]\). The ending position is 3, so the destination header remains 3. The function returns zero.

### Full-width multiplication and carry extension

Given:

- Source header: 1; source payload: \([B-1]\).
- Destination header: 0.
- Starting position: 0.
- Scalar: \(B-1\).

The product is \(B^2-2B+1\). The function writes 1 at position 0 and \(B-2\) at position 1, then updates the destination header to 2 and returns zero.

The original contents of those destination positions do not contribute.

### Carry through existing maximum words

Given:

- Source header: 1; source payload: \([1]\).
- Destination header: 3; destination payload: \([B-1,B-1,7]\).
- Starting position: 0.
- Scalar: 1.

The destination becomes \([0,0,8]\). Carry stops at position 2. The header remains 3.

### Zero scalar still processes storage

Given:

- Source header: 2.
- Destination header: 0.
- Starting position: 0.
- Scalar: 0.

Both source words are read. Zero is written at destination positions 0 and 1 regardless of their previous contents. The destination header becomes 2.

This behavior does not permit an implementation to omit the source accesses merely because the multiplier is zero.

### Empty source can update the header

Given:

- Source header: 0.
- Destination header: 2.
- Starting position: 5.

No payload words are accessed, but the destination header becomes 5. Payload positions between the old length and that position are not initialized.

### A negative header is not preserved by magnitude

Given:

- Source header: 0.
- Destination header: −4.
- Starting position: 0.

The initial destination magnitude is 4. Nevertheless, the final comparison uses −4 directly, so the destination header is replaced with 0.

### Overlap changes a later source read

Suppose the source payload occupies a shared array beginning at position 0, with initial words \([2,3,0]\). The source header is 2. The destination uses the same payload base, has header 0, starts at position 1, and the scalar is 2.

The first step reads source word 2 and writes 4 at shared position 1. The second step then reads that modified source word 4 and writes 8 at position 2. The final shared array is \([2,4,8]\), and the destination header becomes 3.

This differs from processing an immutable source snapshot.
