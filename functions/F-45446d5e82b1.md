# F-45446d5e82b1

## Purpose

F-45446d5e82b1 obtains a node, conditionally copies two payload bytes into it, increments a container count, attaches the node at a supplied position, performs color-based structural repair, and publishes the obtained node’s address through an output slot.

The structure and repair pattern suggest red-black-tree insertion. That is **inferred intent**, not an independently established data-structure contract. The established behavior consists of the accesses, branch conditions, writes, and dependency calls described below.

The function does not search for an insertion position, reject duplicates, check whether an attachment link is occupied, or visibly initialize the obtained node’s color and child links. Successful use requires compatible caller-supplied structure and dependency behavior.

## Behavior

### Acquisition, copying, and count mutation

The first action is a call to F-4a68b66a4199 with the container address. The returned address is retained as the obtained node address.

The function tests whether that address plus 16 is nonzero. If so, it performs these separate byte accesses in order:

1. Read the first source byte.
2. Write it to obtained-node offset 16.
3. Read the second source byte.
4. Write it to obtained-node offset 17.

This is not an established snapshot or atomic two-byte copy. The first write can affect the second read if the locations overlap.

The test is not a conventional null-result check. A null obtained-node address is not explicitly rejected, and later node accesses occur even if copying is skipped. Defined behavior for invalid or wrapping address arithmetic is not established.

After the copy decision, the function reads the four-byte count at container offset 20, adds one, and writes the result back. This precedes attachment selection and comparison. No overflow check or rollback is visible. The source presents the count operation as signed 32-bit arithmetic; a defined wraparound result at the maximum signed value is not established.

### Selecting an attachment branch

The function reads the header address from container offset 16.

The first attachment branch is selected without comparison if either:

- The supplied attachment parent equals that header address; or
- The placement selector is nonzero.

Otherwise, F-685cd10e4a2e is called with these three addresses, in argument order:

1. Container plus 25;
2. The original value source;
3. Attachment parent plus 16.

A nonzero result selects the first branch; zero selects the second.

The comparison receives the original source address, not the copied payload address. Its read extent, relation, and side effects are unknown. Consequently, copied bytes and comparison inputs need not agree if earlier writes or dependency effects modify overlapping storage.

### First attachment branch

The following order is significant:

1. Write the obtained node address to attachment-parent offset 8.
2. Reload the header address from container offset 16.
3. Compare the supplied attachment parent with this newly loaded header.

If they differ, the function selects offset 8 of that newly loaded header as an endpoint slot. It reads the slot and replaces it with the obtained node address only if its value equals the attachment parent.

If they are equal:

1. Write the obtained node address to offset 4 of the header loaded in step 2.
2. **Reload the header address again from container offset 16.**
3. Unconditionally write the obtained node address to offset 12 of this latest header.

The root write and final endpoint write therefore need not target the same header object. In particular, the root-field write can overlap the container’s header-reference slot and change the target of the final write. The unconditional final endpoint write does not first compare that endpoint with the attachment parent.

Under stable, non-overlapping storage, attachment through the header writes its first endpoint, root, and second endpoint in that order. That familiar interpretation does not replace the reload-sensitive behavior above.

### Second attachment branch

The function:

1. Writes the obtained node address to attachment-parent offset 12.
2. Reloads the header address from container offset 16.
3. Selects offset 12 of that header.
4. Reads the selected endpoint slot.
5. Replaces that slot with the obtained node address only if its value equals the attachment parent.

Neither attachment branch checks whether the overwritten child link was empty.

### Parent assignment and repair entry

After attachment and any endpoint update, the supplied attachment-parent address is written to obtained-node offset 4.

The obtained node becomes the active node for repair. The function does not directly initialize its color or either child link. Required initialization may be provided by F-4a68b66a4199, but that dependency contract is unavailable.

### Repair-loop entry and orientation

At each loop condition, the function reloads the container’s header address and reads that header’s root address. If the active node equals the root, the loop ends.

Otherwise, it reads the active node’s parent address and the parent’s color byte. A nonzero parent color ends the loop without reading a grandparent for that iteration.

For a zero-colored parent, it reads the parent’s parent address and that grandparent’s first child. The iteration then uses one of two orientations:

- If the saved parent equals the grandparent’s first child, the opposite child is read from the grandparent’s second-child field.
- Otherwise, the already-read first child is the opposite child. The function does not verify that the parent equals the grandparent’s second child.

For the remainder of that iteration, references to the **saved parent** and **saved opposite child** mean the addresses already read for orientation. Later parent-chain evaluations are separate reads, not synonyms for those saved addresses.

### Recoloring and ascent

In either orientation, a nonnull opposite child with color zero selects recoloring:

1. Write color 1 to the saved parent.
2. Write color 1 to the saved opposite child.
3. Read the active node’s parent link, then that parent’s parent link; write color 0 at the resulting address.
4. **Read the active node’s parent link and that parent’s parent link again**, after the color-0 write. Use the resulting address as the next active node.
5. Repeat the loop.

The first two writes use saved addresses even if the first write changes link storage through aliasing. The two subsequent chain evaluations are distinct. A color write that overlaps link bytes can change the node selected for recoloring or ascent. The next active node is not necessarily the address just colored zero.

### Transformation path: parent in the first-child position

If the opposite child is null or has nonzero color:

- Read the saved parent’s second-child link.
- If it equals the active node, call F-bd7d3aa9e3fb with the container and saved parent. After return, set the active node to the saved parent address.

Then perform all of the following, including when no preliminary call occurred:

1. Read the current active node’s parent link and write color 1 at that address.
2. **Reread** the active node’s parent link, read that parent’s parent link, and write color 0 at the resulting address.
3. **Reread both links again** and call F-7e485a919ef1 with the container and the newly obtained address.

The loop then repeats. The function does not explicitly end repair immediately after this transformation call.

### Transformation path: other orientation

If the opposite child is null or has nonzero color:

- Read the saved parent’s first-child link.
- If it equals the active node, invoke F-7e485a919ef1 in the six-argument form described under Dependencies. After return, set the active node to the saved parent address.

It then follows the same three-stage rereading discipline:

1. Read the current active node’s parent link and write color 1 there.
2. Reread the parent link and then its parent link; write color 0 at the resulting address.
3. Reread both links again; call F-bd7d3aa9e3fb with the container and this latest result.

The loop repeats.

These rereads occur across direct byte writes as well as dependency calls. Even without dependency side effects, aliasing can make the successive chain results differ.

### Completion

After repair ends, the function reloads the header address, reads its root address, and writes color 1 to that root.

It then writes the originally obtained node address to the four-byte output slot. This is independent of which node became active during repair.

There is no visible explicit error return, release, or rollback.

## Side effects

Direct mutations include:

- Up to two payload bytes;
- The container count;
- One attachment-parent child link;
- Conditional header endpoint updates and, on one path, a root update;
- The obtained node’s parent link;
- Color bytes reached during repair and completion;
- The final output slot.

Through aliasing, these writes can also modify other logical fields. In particular, direct color writes can alter later pointer-chain reads, and the root-field write can alter the header reference used by the immediately following endpoint write.

The principal order is acquisition, payload copying, count increment, optional comparison, attachment and endpoint handling, parent assignment, repair, final root recoloring, output publication.

No synchronization or atomic multi-field update is visible. Intermediate states include an incremented count before attachment and a child link installed before the new node’s parent link is written.

Dependency side effects are not bounded by this body. No dependency is assumed to preserve globals, structural fields, source storage, or ownership. If a dependency does not return normally, this body supplies no recovery requirement.

## Acceptance examples

These are conditional static expectations, not executed tests. Each assumes accessible storage, defined arithmetic, and dependency behavior compatible with the stated scenario.

1. **Stable header attachment.**  
   If the attachment parent equals a stable header, the copy guard succeeds, storage does not overlap, and dependencies preserve the relevant fields, comparison is bypassed. The count increases once. Header offsets 8, 4, and 12 receive the obtained address in that order. Its parent becomes the header. It is already the root, so no repair transformation is called. Its color becomes 1 before output publication.

2. **Header-reference alias during root installation.**  
   Suppose execution reaches the equal-parent case after the first header reload, and that header’s offset 4 overlaps the container’s header-reference slot. Writing the obtained address there changes the reference subsequently reloaded. The unconditional endpoint write then targets offset 12 of the newly referenced object, not necessarily offset 12 of the earlier header. This expectation concerns that execution prefix; successful repair afterward requires valid resulting links.

3. **Forced first attachment.**  
   With a nonzero placement selector, comparison is bypassed. The parent’s first child is overwritten. If the subsequent header reload differs from the parent, its first endpoint is replaced only when that endpoint equals the parent.

4. **Comparison-selected second attachment.**  
   With selector zero, parent unequal to the initially read header, and comparison result zero, the parent’s second child is overwritten. The second endpoint of the subsequently loaded header changes only if it equals the parent.

5. **Nonzero parent color.**  
   If the active node is not the current root and its parent color is nonzero, repair stops before reading that iteration’s grandparent. Completion still reloads the header and root and writes root color 1.

6. **Recoloring without overlapping links.**  
   With zero-colored parent and opposite child, and no relevant overlap, both become 1, their grandparent becomes 0, and repair continues from that grandparent without a transformation call for that iteration.

7. **Recoloring with link overlap.**  
   If the color-0 write changes a link used by the immediately following ascent, the next active node is selected by rereading the modified chain. Reusing the pre-write grandparent is not equivalent. The same rule applies between transformation-path color writes and the final dependency argument read.

8. **Overlapping payload copy.**  
   If the first destination byte is the second source byte, the second read observes the first write. A snapshot-copy result is not required.

9. **Interrupted completion.**  
   If a later inaccessible address or nonreturning dependency prevents completion, the body provides no restoration of the count or earlier writes and no guarantee that the output was published.
