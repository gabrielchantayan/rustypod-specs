# F-05077d384bfe

## Purpose

F-05077d384bfe conditionally acquires or replaces a resource associated with a caller-supplied state record, optionally takes a preservation-related path, performs conditional external actions, and makes the record’s active resource equal to its replacement resource.

The established behavior is a sequence of field accesses, dependency calls, and state updates. Resource allocation, resizing, release, and content preservation are plausible interpretations of the dependencies, but their implementations are not supplied. In particular, the available evidence does not establish that bytes are copied, that storage is freed, or that an existing resource survives a failed replacement.

On normal completion, the function returns either:

- **0** when the replacement-resource field read during finalization is nonzero.
- **7** when that field is zero.

These are local status decisions, not direct propagation of dependency return codes.

## Interface

### Inputs

The function accepts three 32-bit arguments:

| Argument | Interpretation established by use |
|---|---|
| State-record address | Address used to access the fields listed below. |
| Requested value | Signed 32-bit value compared against a dependency result and, when acquisition is required, passed to an acquisition dependency after applying a minimum. |
| Preservation selector | Zero disables the preservation-related paths; any nonzero value enables them. It is not restricted to the value 1. |

The requested value is plausibly a size or capacity request. Its unit is not established.

### State-record layout

Offsets are byte offsets from the state-record address. These field names are descriptive labels for this contract, not evidence of source-level types.

| Offset | Width | Contract label | Observed use |
|---|---:|---|---|
| `0x10` | 32 bits | Context | First explicit argument to either acquisition dependency. |
| `0x14` | 32 bits | Active resource | Compared with the replacement resource; passed to the callback; ultimately overwritten with the replacement resource. |
| `0x1c` | 16 bits | Flags | Tested for bit `0x0040`, conditionally overwritten with 1, and finally masked. |
| `0x20` | 32 bits | Callback target | Conditionally used as an indirect call target; cleared during finalization. |
| `0x24` | 32 bits | Replacement resource | Controls acquisition, receives acquisition results, and supplies the final active resource and status decision. |

The resource values are treated as 32-bit words. Zero is a distinguished value. Their representation as addresses, handles, or another token type is not established.

The callback target is used as a callable address when the relevant flag is set and the target is nonzero. The surrounding interface is therefore consistent with a 32-bit address model. No 64-bit resource field is established.

## Behavior

### 1. Decide whether acquisition is required

The function first reads the replacement-resource field.

If that value is zero, acquisition is required immediately. F-53620d05c48c is not called on this path.

If that value is nonzero, the function calls F-53620d05c48c with no explicit arguments shown in the available evidence. It interprets the low 32 bits of the result as a signed integer and compares that value with the signed requested value.

Acquisition is required exactly when the comparison result is strictly less than the request. Equality does not require acquisition.

The initial nonzero replacement-resource value is not shown as an explicit argument to F-53620d05c48c. Its relationship to the dependency’s result is therefore unknown.

When acquisition is not required, the function does not normalize the requested value and does not call either acquisition dependency. It proceeds to the preservation-related conditional action.

### 2. Normalize the request only on an acquisition path

When acquisition is required, every signed requested value below 33 is replaced with 32. Values of 33 or greater remain unchanged.

Consequences include:

- Negative requests become 32.
- Requests of 0 through 31 become 32.
- A request of 32 remains 32.
- A request of 33 remains 33.

There is no rounding to a larger boundary, multiplication, or addition to the request in the supplied behavior. No local arithmetic overflow is introduced by this normalization.

### 3. Choose an acquisition path

After normalization, the function chooses between two paths.

#### Preservation-selected, equal-resource path

This path is taken when both conditions hold:

1. The preservation selector is nonzero.
2. The active-resource and replacement-resource fields compare equal as 32-bit values at this decision point.

Equality includes the case where both values are zero.

The function calls F-814e6ca769cc with three explicit arguments:

1. The current context field.
2. The current active-resource field.
3. The normalized request.

The low 32 bits of its result become the new resource value. The function writes that value:

1. First to the replacement-resource field.
2. Then to the active-resource field.

If the value is zero, the function additionally overwrites the entire 16-bit flags field with `0x0001`. This is not a bitwise addition of an error flag: all previous flag bits are discarded.

This path then proceeds directly to callback processing. It bypasses the later preservation-related external action, regardless of whether the dependency succeeded or failed.

A nonzero result does not cause a corresponding local flags overwrite.

#### All other acquisition cases

For every other acquisition case, the function:

1. Reads the replacement-resource field and passes that word to F-94cb53877c15.
2. After that dependency returns, reads the context field.
3. Calls F-83e6016208ce with the context and normalized request.
4. Writes the low 32 bits of its result to the replacement-resource field.

F-94cb53877c15 is called even when the replacement-resource field supplied to it is zero.

The context read for F-83e6016208ce occurs after F-94cb53877c15 returns. A change to that field by the earlier dependency can therefore affect the subsequent call.

This path does not immediately overwrite the active-resource field. It also does not locally overwrite the flags with 1 when acquisition returns zero. It proceeds to the preservation-related conditional action.

### 4. Perform a conditional external action

This stage is reached after either:

- No acquisition was required; or
- The second acquisition path completed.

It is skipped after the preservation-selected, equal-resource acquisition path.

When the preservation selector is zero, this stage makes no external call.

When the selector is nonzero, the function reads the active-resource field. If that value is nonzero, it reads the replacement-resource field. It invokes D-01 only when both values are nonzero and unequal.

The supplied evidence does not reliably establish D-01’s arguments, transfer length, or memory effects. The surrounding branch is consistent with an operation between distinct resources, but this contract does not assert a copy, move, release, or ownership transfer.

The exact established invocation condition is:

- Preservation selected.
- Active resource nonzero.
- Replacement resource nonzero.
- Active resource different from replacement resource.

A zero replacement result suppresses this call.

### 5. Process the optional callback

All normally returning paths converge on callback processing.

The function reads the 16-bit flags field and tests bit `0x0040`.

- If the bit is clear, it does not read the callback target for invocation.
- If the bit is set, it reads the callback-target field.
- If that target is also nonzero, it calls the target with one explicit 32-bit argument: the active-resource field read for that call.

The active resource passed to the callback depends on the preceding path:

- On the preservation-selected, equal-resource acquisition path, it has already been overwritten with the acquisition result.
- On the other acquisition path, it has not yet been locally overwritten.
- On the no-acquisition path, it remains whatever the record contains at callback time.

The callback return value is not used for the final status.

The callback is not assumed to preserve the record, globals, or resource ownership. In particular, it may change the replacement-resource field before finalization reads that field.

On a zero result from F-814e6ca769cc, the preceding flags overwrite to `0x0001` clears bit `0x0040`. In ordinary execution without intervening asynchronous mutation, this suppresses callback invocation on that failure path.

### 6. Finalize the record and select the result

After callback processing, the function performs these ordered operations:

1. Reads the replacement-resource field.
2. Writes that same 32-bit value to the active-resource field.
3. Selects status 7 if the captured value is zero, otherwise status 0.
4. Reads the current 16-bit flags field and writes it back ANDed with `0xfe7f`.
5. Writes zero to the 32-bit callback-target field.
6. Returns the selected status.

The mask clears bits `0x0080` and `0x0100`. It preserves all other flag bits, including callback-enable bit `0x0040`.

Thus, normal completion can leave the callback-enable bit set while the callback target has been cleared.

Status selection is based on the replacement-resource value read after the callback, not necessarily on an earlier acquisition result. Likewise, the final flags mask uses the flags present after callback processing.

## Side effects

### Direct record writes

The function may write:

- Replacement resource during acquisition.
- Active resource immediately after F-814e6ca769cc returns.
- Flags to exactly `0x0001` after a zero result from that dependency.
- Active resource again during finalization.
- Flags during finalization.
- Callback target to zero during finalization.

On every normally completed path, finalization writes the active-resource, flags, and callback-target fields. No direct write to the context field is shown.

### External effects and ownership

Dependency calls and the indirect callback can have effects beyond these direct writes. Their implementations are unavailable, so this contract does not restrict their global or memory effects.

Specifically, the evidence does not establish:

- Whether F-94cb53877c15 frees or otherwise invalidates its argument.
- Whether F-814e6ca769cc preserves an old resource on failure.
- Whether F-83e6016208ce returns fresh, shared, or externally owned storage.
- Whether D-01 modifies either resource.
- Whether the callback releases, retains, replaces, or merely observes its argument.

No rollback is shown. On the second acquisition path, F-94cb53877c15 runs before acquisition, and a zero acquisition result is still stored and later made active. Any stronger guarantee that the prior resource remains usable is undocumented.

## Acceptance examples

These examples are conditional static acceptance cases, not executed tests. Except where stated otherwise, dependencies return normally and do not mutate the record beyond returning their stated results.

1. **Zero replacement and negative request, preservation disabled.**  
   Given replacement zero, request −1, and selector zero, F-53620d05c48c is skipped. F-94cb53877c15 receives zero. F-83e6016208ce receives request 32. Its result becomes the replacement resource.

2. **Zero resources with preservation selected.**  
   Given both resource fields zero and a nonzero selector, acquisition uses F-814e6ca769cc because zero equals zero. F-94cb53877c15 and F-83e6016208ce are not called.

3. **Equality does not trigger acquisition.**  
   Given an initially nonzero replacement and a low-word signed result of 64 from F-53620d05c48c, request 64 does not cause acquisition. Request 65 does.

4. **Signed comparison governs the threshold.**  
   A low-word result of `0xffffffff` is interpreted as −1. Against request 1, it requires acquisition; the acquisition request becomes 32.

5. **Failed equal-resource acquisition.**  
   Given equal resource fields, a nonzero selector, and a zero result from F-814e6ca769cc, both resource fields become zero and flags become exactly 1. D-01 is skipped, the callback is suppressed, and normal completion returns 7.

6. **Distinct nonzero resources without acquisition.**  
   Given no acquisition requirement, a nonzero selector, and distinct nonzero resource fields at the conditional-action stage, D-01 is invoked. Its unknown semantics must not be replaced by an assumed byte-copy requirement.

7. **Callback changes the final outcome.**  
   Given an enabled nonzero callback target, if the callback changes replacement from nonzero to zero, finalization writes zero to active and returns 7. Changing replacement from zero to nonzero instead causes finalization to return 0.

8. **Final flags and callback target.**  
   Given flags `0x01c0` at the final masking step, the stored flags become `0x0040`. The callback-target field is nevertheless cleared to zero.
