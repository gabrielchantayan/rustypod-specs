# F-892aa643a358

## Purpose

F-892aa643a358 selects two 16-bit values and writes them to two caller-supplied destinations. An unsigned selector below 14 selects a record from a table addressed through a global base value. A selector of 14 or greater produces the pair `(1, 1)` without reading that global base value or accessing the table.

The global base is read on the in-range branch before the selected record address is calculated. The supplied body does not establish that this base is constant across invocations. Within one invocation, the selected address is retained across the first output write; the second table field is not located through another global-base lookup.

There is no explicit return value or status result. The observable results are the memory reads and the ordered writes through the destination pointers.

The apparent intent is selection among fourteen pairs with a uniform fallback. The application-level meaning of those pairs is not established.

## Behavior

### Branch selection

The selector is compared with 14 using unsigned ordering.

For values 0 through 13, the function reads the global base value and uses the selected table record. For every other representable value, it writes the fallback pair.

The fallback does not clamp to record 13, wrap the selector, calculate an out-of-range record offset, or report an error.

If a caller converts a negative value to the unsigned selector type before the call, the function operates on the resulting unsigned value. There is no separate negative-input case.

### Global base and record layout

On the in-range branch, the function reads a global value that supplies the table base. It then calculates the selected record address using an offset of four bytes times the selector.

The global value is not established to be a constant, an immutable pointer, or a fixed address across invocations. Different calls may therefore select records relative to different bases if the global value changes between calls.

Each selected record has this layout:

| Byte offset within record | Content |
|---|---|
| 0 | First 16-bit field |
| 2 | Second 16-bit field |

The first field begins at offset `4 × selector` from the base read for that invocation. The second begins at offset `4 × selector + 2`.

For selector 13, the record starts at offset 52 and its second field starts at offset 54. That second field occupies offsets 54 and 55. Supporting every in-range selector therefore requires readable field storage covering the corresponding 56-byte table region. The source does not prove that such a backing region actually exists.

The branch limits the multiplication operand to at most 13, so the largest record offset is 52. This multiplication does not overflow a 32-bit unsigned integer, or any unsigned representation capable of representing the source’s ordinary small integer values. This bounded offset does not establish that adding it to the global base produces a valid address. The base representation, address width, and applicable address-arithmetic rules remain unresolved.

### Ordered operations on the in-range branch

The source-established access order is:

1. Read the global base value.
2. Calculate the selected record address from that value and the selector.
3. Read the record’s first 16-bit field.
4. Write the value read to the first destination.
5. Read the record’s second 16-bit field using the already selected record address.
6. Write that value to the second destination.

The second table read occurs after the first output write. The function does not read both fields into a snapshot before writing caller-provided storage.

Consequently, a valid first-destination write that modifies the selected second field can change the value subsequently read and delivered to the second destination.

The selected address is retained across that first write. There is no second global-base lookup. If a permitted destination write changes the global base storage, this body still addresses the second field relative to the previously selected record, not relative to the newly stored base value. Such overlap is only meaningful where the underlying storage and access rules permit it.

### Ordered operations on the fallback branch

For a selector of 14 or greater, the function:

1. Writes the 16-bit value 1 to the first destination.
2. Writes the 16-bit value 1 to the second destination.

This branch does not read the global base value and does not read table fields. Accessibility of the global base and table is therefore not a memory-access precondition for this branch.

### Aliasing and incomplete execution

If both destinations designate the same valid 16-bit unit outside the relevant table storage, the second write replaces the first. On the in-range branch, the final value is the value obtained by the second table read. On the fallback branch, it is 1.

If the destinations also overlap table storage, the same ordered accesses apply, but the first write may affect the later read. The final result must be derived from that order rather than from the table’s initial pair alone.

Partially overlapping destinations receive no special handling. Where such accesses are valid, final byte contents depend on their overlap, written values, and byte representation.

There is no explicit error handling or rollback. The body provides no transactional guarantee if a later access fails after an earlier write. The precise consequences of invalid accesses are not established.

## Side effects

On either branch, the first destination is written before the second destination. These are the only explicit memory writes in the body.

On the in-range branch, the explicit data reads include the global base value and two 16-bit table fields. The global-base read precedes record-address calculation. The first output write separates the two table-field reads.

On the fallback branch, there is no global-base or table-field read.

Destination writes may alter table storage, global-base storage, or other state if the supplied addresses designate such storage and the accesses are valid. The function therefore cannot be described as preserving all global state.

The body contains no explicit callable dependency, allocation, deallocation, I/O operation, synchronization operation, or persistent storage of an output pointer. It establishes neither atomicity nor a coherent snapshot in the presence of concurrent modification.

These statements describe source-level accesses and their expressed order. Exact machine-access widths, fault behavior, compiler transformations, and hardware visibility to other observers are not independently established.

## Acceptance examples

These examples are conditional expectations derived from static evidence. No runtime tests have been performed.

### First record

Given selector 0, a readable global base identifying a record containing `(7, 9)`, and valid destinations disjoint from the table:

- The global base is read.
- The first field is read as 7 and written to the first destination.
- The second field is then read as 9 and written to the second destination.

### Last in-range selector

Given selector 13 and suitable storage, the function reads the global base and accesses fields beginning at offsets 52 and 54 relative to that base. It does not use the fallback.

### First out-of-range selector

Given selector 14 and valid destinations, the function writes 1 to the first destination and then 1 to the second. It does not read the global base or table, even if those locations are inaccessible.

### Large unsigned selector

Under a 32-bit selector interpretation, selector `0xFFFFFFFF` takes the fallback branch. It does not read the global base or multiply that selector to locate a record.

### Changed base between calls

Suppose two valid table regions contain different pairs at the same selected index. If the global base identifies the first region for one call and the second region for a later call, each in-range invocation uses the base value it reads for itself. There is no established cross-invocation caching of the selected address.

### Identical destinations

Given a selected record containing `(7, 9)` and both destinations designating the same valid 16-bit unit outside the table, that unit receives 7 and then 9. Its final value is 9.

### First destination overlaps the second field

Given a writable selected record initially containing `(7, 9)`, with the first destination exactly designating its second field and the second destination elsewhere:

- The first field is read as 7.
- The first write changes the second field to 7.
- The subsequent second-field read obtains 7.
- The second destination receives 7.

This distinguishes the behavior from reading both fields before either output write.

### First write changes the global base

If a first-destination write validly changes global-base storage, the second field is still read from the record selected before that write. No fresh global-base lookup occurs. This expectation is conditional on the overlap and representation being valid; the source does not establish that such an arrangement is permitted on the actual platform.
