# F-01a5e215a7b3

## Purpose

F-01a5e215a7b3 conditionally updates a destination descriptor from a source descriptor and returns the destination address. Identical descriptor addresses cause an immediate no-op.

The established behavior has three nontrivial paths:

- Request replacement storage when a destination query is less than a source query.
- Reuse existing storage, process an existing prefix, and process an additional suffix.
- Reuse existing storage, process the source range, and process a remaining destination range.

**Inferred intent:** this resembles assignment between sequence-like objects whose elements occupy eight bytes. Several dependency calls resemble size queries, a capacity query, allocation, element assignment, element construction, element destruction, and storage release. Those interpretations are not established dependency contracts.

A significant observable detail must not be normalized into conventional container behavior: on the final reuse path, this function writes the same computed address to both the second and third destination words. On the prefix-plus-suffix path, it does not directly write the third destination word.

## Interface

### Arguments and result

The function accepts four arguments:

| Argument | Established use |
|---|---|
| Destination descriptor address | Compared with the source address; passed to dependencies; read and written as described below; returned unchanged as an address. |
| Source descriptor address | Compared with the destination address; passed to dependencies; its first two words supply range endpoints. |
| First unsigned scalar | Copied into temporary storage on a non-self call, but overwritten before any value derived from it affects a dependency argument, descriptor write, or return value. |
| Second unsigned scalar | Likewise copied and then overwritten before any externally visible use. |

The last two arguments therefore have no established effect on normal externally visible behavior.

The return value is always the original destination address **if the function returns normally**. There is no separate success flag or error result.

### Descriptor layout

The visible accesses use consecutive four-byte words:

| Byte offset | Established use |
|---|---|
| 0 | Read as a base-like address; replaced on the replacement-storage path. |
| 4 | Read as a range endpoint; updated on every non-self path that completes normally. |
| 8 | Written on the replacement-storage path and the final reuse path. Not directly accessed on the prefix-plus-suffix path. |

The first two source words are read directly. No source word is directly written by this function.

**Inferred intent:** the three destination words are a storage beginning, a logical end, and a storage limit. Dependencies, not this body, determine whether that interpretation is correct.

### Widths and arithmetic

The supplied representation uses 32-bit scalar words. Count comparisons in branch selection and growth calculation are unsigned.

Count-to-byte conversion uses a stride of eight:

- Allocation size is the selected count shifted left by three.
- Endpoint calculations add a count multiplied by eight to a base-like word.

Unsigned growth calculations have 32-bit wraparound semantics in the supplied representation. They are not checked arithmetic. Address-like values and some query results are also carried through signed integer representations. The supplied text does not establish a portable host-language interpretation of signed overflow or integer-to-pointer behavior.

For ordinary, non-wrapping acceptance cases, all counts, byte sizes, and resulting addresses must remain representable in the target execution model.

### Preconditions

For a non-self call to complete safely:

- All direct descriptor accesses must be valid.
- Dependencies must accept the descriptors and range-like arguments supplied on the selected path.
- Any returned storage or address-like value subsequently used must be usable for those operations.
- Descriptor state must satisfy whatever invariants the dependencies require.

The function does not establish or check those conditions.

For a self call, the body only compares and returns the address. It performs no descriptor dereference or dependency call.

## Behavior

### 1. Identity check and initial observations

If destination and source addresses are identical, return the destination address immediately.

Otherwise, the function obtains, in this order:

1. A source value from F-a08e2acc116b.
2. A destination value from F-3c5c967c9f05.

It compares these as unsigned 32-bit values. If the destination value is smaller, execution takes the replacement-storage path. Otherwise, it takes one of the reuse paths.

These are separate calls. Later calls to either dependency are fresh observations, not reuse of these results.

### 2. Replacement-storage path

This path begins when the initial destination value from F-3c5c967c9f05 is less than the initial source value from F-a08e2acc116b.

The function then:

1. Calls F-a08e2acc116b on the source again.
2. Calls F-a08e2acc116b on the destination.
3. Computes a requested count from these new results.
4. Requests storage through F-871e64ddc6de.
5. Processes the source range into the returned storage through F-5a4cc0640626.
6. Processes the then-current destination range through F-1b16f6af8dff.
7. Calls F-3c5c967c9f05 on the destination and then calls F-ff1bdc376dcd using a previously captured destination base-like value.
8. Installs the returned storage address into destination offset 0.
9. Queries the source again, then updates destination offset 4.
10. Updates destination offset 8 using the selected allocation count.

#### Requested count

Let:

- \(s\) be the second source result from F-a08e2acc116b.
- \(d\) be the destination result obtained immediately afterward.

Two unsigned 32-bit candidates are calculated:

- \(a = d + 32\).
- \(b = d + \lfloor d/2 \rfloor + \lfloor d/8 \rfloor\).

The additions wrap at 32 bits. The function selects the unsigned maximum of \(a\), \(b\), and \(s\). Call the selected result \(r\).

Thus the apparent growth policy is based on the queried destination size-like value, not on the initial destination capacity-like value. Because arithmetic is unchecked, the mathematical growth interpretation only applies when the additions do not wrap.

#### Dependency arguments and ordering

F-871e64ddc6de receives:

- The low 32 bits of \(r \times 8\).
- A literal zero.

Its return value is treated as the new base-like value. There is no visible failure check.

F-5a4cc0640626 then receives:

- The source word at offset 0.
- The source word at offset 4.
- The returned storage value.
- The destination descriptor address.

After that call returns, F-1b16f6af8dff receives the destination descriptor and its then-current words at offsets 0 and 4. The old destination range is therefore not necessarily the range visible before F-5a4cc0640626.

After F-1b16f6af8dff returns, the function captures destination offset 0. It then calls F-3c5c967c9f05 on the destination. F-ff1bdc376dcd receives the captured base-like value, that query result, and zero.

Only after F-ff1bdc376dcd returns does the function directly install the new base-like value.

#### Final descriptor writes

The direct writes occur in this order:

1. Destination offset 0 receives the stored result of F-871e64ddc6de.
2. F-a08e2acc116b is called on the source.
3. Destination offset 4 receives the destination base-like value read after that query, plus eight times the query result.
4. Destination offset 8 receives the destination base-like value plus eight times \(r\).

The selected count \(r\) is retained across the dependency calls. The source count used for the final endpoint is queried anew; it is not necessarily the count used to select \(r\).

### 3. Reuse-path selection

If replacement storage is not selected, the function calls:

1. F-a08e2acc116b on the destination.
2. F-a08e2acc116b on the source.

If the first result is unsigned-less-than the second, it takes the prefix-plus-suffix path. Otherwise, it takes the final reuse path.

The initial capacity-like comparison alone does not determine which reuse path follows.

### 4. Prefix-plus-suffix path

The function queries F-a08e2acc116b on the destination once more. Let this result be \(p\). It need not equal the destination result used in the preceding comparison.

It calls F-01edb2194553 with:

- The source base-like word.
- The source base-like word plus \(8p\).
- The destination base-like word.

The return value is ignored.

Next, it calls F-a08e2acc116b on the source. Using that result and a subsequently read destination base-like word, it writes destination offset 4 to the computed endpoint.

Only after that endpoint write does it call F-5a4cc0640626 with:

- The then-current source base-like word plus \(8p\).
- The then-current source word at offset 4.
- The then-current destination base-like word plus \(8p\).
- The destination descriptor address.

The function then returns immediately.

There is no direct write to destination offset 8 on this path. That is not a guarantee that the word is unchanged: dependencies may alter it.

**Observable ordering requirement:** the destination endpoint is published before the final F-5a4cc0640626 call. It is not delayed until that call succeeds.

### 5. Final reuse path

This path is selected when the destination result is not unsigned-less-than the source result in the reuse-path comparison.

F-01edb2194553 receives:

- The source word at offset 0.
- The source word at offset 4.
- The destination word at offset 0.

Its returned 32-bit value is retained and passed as the second argument to F-1b16f6af8dff. That dependency also receives the destination descriptor address and the destination word at offset 4, read after F-01edb2194553 returns.

The function then calls F-a08e2acc116b on the source and computes an address-like value from the subsequently read destination base-like word plus eight times that result.

It writes that single computed value first to destination offset 4 and then to destination offset 8.

Consequently, on ordinary stable-descriptor interpretations, the two endpoint-like words become equal even if the storage previously had spare capacity. The contract must preserve this write rather than substitute conventional capacity-preserving assignment behavior.

## Side effects

### Direct effects

Apart from temporary computations, direct externally visible writes are limited to destination descriptor words:

| Path | Direct writes, in order |
|---|---|
| Self | None |
| Replacement storage | Offset 0, offset 4, offset 8 |
| Prefix plus suffix | Offset 4 |
| Final reuse | Offset 4, offset 8 |

No direct element-memory writes appear in this body; such effects are delegated.

### Indirect effects and ownership

Dependencies receive descriptor addresses, range-like values, and storage-like values. Their effects on memory, global state, allocation state, or descriptor contents are unknown.

The call sequence is consistent with acquiring new storage, populating it, processing old elements, and releasing old storage. That is inferred intent, not proof of ownership transfer or release semantics. In particular:

- The allocation-like dependency’s return is not checked.
- The release-like dependency receives a queried count-like value, not an explicitly computed byte size.
- No guarantee establishes that a dependency preserves either descriptor.
- Distinct descriptor addresses do not establish disjoint underlying storage.
- No explicit overlap handling or alias validation is visible.

### Failure behavior

There are no explicit error returns, rollback operations, null checks, overflow checks, or allocation-failure branches.

If a dependency fails by a mechanism outside the visible body, subsequent behavior depends on that mechanism. Partial effects are possible. For example, the prefix-plus-suffix path writes the destination endpoint before its final range-processing call.

The body establishes sequencing between completed calls and later accesses. It does not establish a total order among argument-expression reads within a single call.

## Acceptance examples

These are conditional static examples, not executed tests. Except for the identity example, assume valid non-overlapping storage, non-wrapping arithmetic, stable query meanings, and dependencies that preserve descriptor fields unless the scenario explicitly relies on this function’s direct writes.

### Identical descriptor addresses

If both descriptor arguments are the same address, the function returns that address without dependency calls or descriptor access. The two scalar arguments do not affect this result.

This also describes two identical null addresses at the body level; it does not assert that an external interface permits null arguments.

### Replacement with the minimum increment

Suppose the source size-like value is consistently 10, the destination capacity-like value is 5, and the destination size-like value is 4.

Replacement is selected. The growth candidates are 36 and 6, so the selected count is 36. The allocation-like request is 288 bytes and zero.

On normal completion, if the returned base is \(B\), the destination words become:

- Offset 0: \(B\).
- Offset 4: \(B + 80\).
- Offset 8: \(B + 288\).

### Replacement governed by the source count

Suppose the source size-like value is 100, destination capacity-like value is 5, and destination size-like value is 4.

The selected count is 100, not 36. The allocation-like request is 800 bytes. Under the stated assumptions, the final endpoint-like words both equal \(B + 800\).

### Prefix and suffix within existing storage

Suppose destination capacity is 12, destination size is consistently 3, and source size is consistently 5.

The prefix call covers the first 24 source bytes. The destination endpoint is then written as its base plus 40. The suffix call covers the source range beginning 24 bytes after its base and uses the destination address 24 bytes after its base.

No direct third-word write follows.

### Source no longer than destination

Suppose destination capacity is 12, destination size is 7, and source size is 3.

The full source range is passed to F-01edb2194553. Its returned value is forwarded to F-1b16f6af8dff. After those calls, both destination endpoint-like words are directly set to the destination base plus 24.

### Empty source

If source size is zero and the final reuse path is selected, both endpoint-like words are set to the destination base under stable-query assumptions. The dependency calls still occur; the function does not directly skip them because the source is empty.

## Uncertainties

The following are **documented_only**:

- Whether the query dependencies actually mean size and capacity.
- Element representation, alignment, construction, assignment, and destruction semantics.
- Allocation ownership, failure signaling, and release units.
- Whether dependencies mutate either descriptor or global state.
- Behavior with distinct descriptors sharing storage.
- Behavior on invalid ranges, insufficient storage, or inconsistent query results.
- Target-specific overflow and address behavior outside representable, non-wrapping cases.
- Whether the final third-word overwrite is intentional.
- Exception, termination, fault, or other nonlocal-exit behavior.

Repeated queries cannot be treated as interchangeable without additional dependency guarantees. A changing source count may affect branch selection, requested storage, and the final endpoint differently; the body performs no consistency check.

## Evidence

Established static evidence consists solely of the supplied function body and dependency-ID mapping:

- An address-equality guard precedes all descriptor accesses and dependency calls.
- Descriptor accesses use four-byte word positions; range arithmetic uses an eight-byte stride.
- Replacement selection, growth arithmetic, dependency order, and direct writes are visible.
- The replacement path re-queries the source after installing the new base.
- The prefix-plus-suffix path writes the endpoint before processing the suffix and returns without a direct third-word write.
- The final reuse path writes the same computed value to both endpoint-like words.
- No explicit validation, failure handling, or rollback is present.

Container terminology and dependency roles beyond their visible arguments and uses are inferred intent. No runtime tests have been performed.
