# F-3ae6baf96671

## Purpose

The first callback receives the function’s input unchanged. A nonzero result from that callback stops further processing. The second callback is eligible only when the input is zero and the first callback either is absent or returns zero. Its argument is a 32-bit value read from the originally captured shared object.

This is an evidence-bounded behavioral contract. The supplied static representation establishes control flow, offsets, zero tests, and callback arguments. It does not establish the application meaning of the shared object, the callbacks, or their results. No runtime tests have been performed.

## Behavior

### Initial dependency and shared-base capture

F-bafc2e4b678f is called first, without an explicit argument.

After that call returns, the supplied representation captures the outer-object address from the shared global slot. It then checks the dependency’s result:

- A nonzero result causes immediate return.
- A zero result permits dispatch processing.

Consequently, the captured outer address reflects shared state after F-bafc2e4b678f returns, not necessarily shared state at function entry. The dependency must not be assumed to preserve that state.

The supplied representation places the shared-base capture before the nonzero-result return. That ordering is part of the available static evidence; it is not evidence that an optimized binary necessarily performs an externally observable ordinary-memory load on that otherwise terminating path.

### Initial dispatch-object check

When the dependency result is zero, the function reads the dispatch-object address at offset 4 through the shared global base.

If that address is zero, the function returns immediately. Neither callback is invoked, even when the input is zero.

This check establishes only that the address read at that point was nonzero. It does not establish that the outer object exists, that the dispatch object is valid, or that a later read of the field will produce the same address.

### First callback

After the initial dispatch-object check passes, the function obtains the first callback address from offset 32 of the dispatch object selected through the shared global base.

The supplied representation expresses another traversal through the global base and the outer object’s offset-4 field for this lookup. It does not explicitly retain the dispatch-object address from the preceding null check.

If the first callback address is zero, no first callback occurs, and execution continues to the input test.

If the first callback address is nonzero:

1. The callback is invoked with the original 32-bit input value.
2. The callback’s result is tested for zero.
3. A nonzero result causes immediate return.
4. A zero result permits execution to continue.

This callback can therefore prevent the final callback by returning any nonzero value. The function assigns no further local meaning to positive, negative, or otherwise distinct nonzero results.

The first callback is eligible for both zero and nonzero input. In particular, the nonzero-input early return happens **after** the first callback opportunity, not before it.

### Input gate

Once the first callback is absent or has returned zero:

- A nonzero input causes immediate return.
- A zero input permits the final callback lookup.

Thus, for nonzero input, at most the first callback can be invoked. A zero input does not guarantee the final callback: earlier gates and the final callback’s own null check still apply.

### Final callback

The final lookup uses the outer-object address captured after F-bafc2e4b678f returned. It does not simply repeat the global-base lookup used for the first callback.

From that captured outer object, the function rereads the dispatch-object address at offset 4 and obtains the final callback address at offset 8 of the resulting dispatch object.

There is no new null check on this dispatch-object address. If an earlier callback has changed the captured outer object’s offset-4 field to zero, the original successful check does not protect this later access.

If the final callback address is zero, the function returns without reading the final argument for a call.

If the final callback address is nonzero:

- The function reads the 32-bit value at offset 8 of the captured outer object.
- It invokes the final callback with that value.
- It performs no further represented local work.

The argument is not established to be a pointer, handle, integer count, or owned resource. Its raw 32-bit value is forwarded without local interpretation.

### State changes between callback stages

The captured outer address and the outer object’s contents have different persistence properties:

- The outer address used by the final stage is captured before the first callback.
- The dispatch-object address used by the final stage is read after the first callback.
- The final callback argument is also read after the first callback, and only when that callback is present.

Therefore, changing the shared global slot during the first callback does not, by itself, redirect the final stage to the newly installed outer object. Changing the captured outer object’s fields can affect the final stage.

No callback is required by the evidence to preserve the global slot, the captured outer object, either dispatch object, or their lifetimes.
