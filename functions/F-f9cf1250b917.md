## Interface

### Inputs and address model

The function accepts:

- An owner address represented by a 32-bit argument.
- An unsigned 32-bit request.

For a nonzero request, the function reads a 32-bit state-object address at owner offset `0x0C`. Subsequent state accesses use that captured address; the owner’s state-object field is not reread.

A zero request returns without dereferencing the owner. Otherwise, the caller must provide storage valid for every access reached by the execution. The representation establishes a 32-bit address model, not a portable interface for wider addresses.

- Bits 0–31: the current 32-bit status-slot bit pattern.

## Behavior

### Arithmetic and comparison rules

Each count component is read as signed 16-bit and extended before addition. The sum of either pair lies between −65,536 and 65,534 and fits in signed 32 bits.

The primary requirement combines the primary-count sum with the unsigned request, producing a 32-bit unsigned result with modular arithmetic. The initial gate interprets both that result and primary capacity as signed 32-bit values. Subsequent capacity comparisons are unsigned.

The primary target is the recomputed primary requirement plus seven, modulo \(2^{32}\), with the lowest three bits cleared. The secondary target is a separately reread secondary-count sum plus three in unsigned 32-bit arithmetic, with the lowest two bits cleared.

These operations act as upward alignment to multiples of eight and four only when the additions do not wrap. The function does not reject negative counts, wrapped arithmetic, zero targets, or capacities with their top bit set.

### Initial gate

A zero request immediately returns the all-zero 64-bit result.

For a nonzero request, the function captures the state-object address and reads the primary-count components and primary capacity for the initial comparison. If the signed interpretation of the primary requirement is less than or equal to the signed interpretation of primary capacity, it returns zero status with the original request in the high half.

This gate does not consider secondary capacity. Insufficient secondary capacity alone cannot cause work when the primary signed comparison permits an early return.

The evidence establishes the comparison’s inputs, but not a total ordering among independent operand reads within that expression.

### Slow-path captures

After the initial gate requires further work, the function captures the context at `0x00`, initializes its local 32-bit status slot to zero, captures primary capacity, and rereads both primary-count components to recompute the primary requirement using the original request.

It also records that no primary growth has yet completed.

The primary capacity and count reads here are distinct from the initial-gate reads. There is no coherent-snapshot or synchronization guarantee. The captured context, captured old primary capacity, and recomputed primary requirement govern the primary calls even if dependencies subsequently modify the state object.

### Primary processing

Primary processing occurs only if the captured primary capacity is unsigned-less-than the recomputed primary requirement. Otherwise, it is skipped, even though the signed initial comparison required entry into the slow path.

When primary processing is required, the function first loads the first primary-buffer value from `0x18` into the return carrier. It then calculates the aligned primary target.

The first F-6dd003795db7 call receives the captured context, size-like argument 8, captured old primary capacity, aligned target, loaded buffer value, and the status-slot address. Its 32-bit return value is stored at `0x18` before status is inspected. Nonzero status immediately ends processing.

After a zero-status first call, the second primary-buffer value is loaded from `0x1C` into the carrier. The next call uses size-like argument 1 and the same captured context, old capacity, target, and status-slot address. Its return value is stored at `0x1C` before another status check.

Only after both calls pass their checks does the function read the flag byte at `0x10`. A nonzero byte causes the optional primary-buffer value at `0x28` to be loaded into the carrier and passed to another call, this time with size-like argument 8. That return value is stored at `0x28` before its status check.

Thus, earlier calls can affect the later flag or buffer values if their side effects reach those fields. Those values are not all captured before the first call.

After every applicable primary call has completed with zero status, the function records completed primary growth and writes the aligned target to primary capacity at `0x04`. No primary-capacity commit occurs before that point.

### Secondary processing and distinct rereads

Secondary processing is reached only if no earlier status check terminated execution. Its comparison uses secondary capacity at `0x08` and the unsigned conversion of the signed secondary-count sum read from `0x14` and `0x34`.

If secondary capacity is not unsigned-less-than that sum, no secondary call occurs.

If the comparison selects secondary growth, the following statement-level order is established:

- The secondary-buffer value at `0x20` is loaded into the return carrier.
- Both secondary-count fields are read again to calculate the aligned target.
- Secondary capacity at `0x08` is read again for the dependency’s old-capacity argument.
- F-6dd003795db7 is called.

The target is therefore not necessarily derived from the count values that selected the branch. Likewise, the old-capacity argument is not necessarily the capacity value used in the comparison. No dependency call occurs between these reads, but the function provides no synchronization that would make them a single snapshot.

The call receives the captured context, size-like argument 2, the reread secondary capacity, the target derived from the reread counts, the previously loaded secondary-buffer value, and the status-slot address.

Its return value is stored at `0x20` before status is checked. A nonzero status ends execution without this function committing secondary capacity. On zero status, it writes the calculated target to `0x08`.

A negative comparison-time count sum becomes a large unsigned requirement. A negative target-time sum participates in the separate unsigned alignment calculation. Neither condition is diagnosed.

## Side effects

### Direct state changes

Each reached F-6dd003795db7 call causes its returned 32-bit value to be assigned to the corresponding buffer field before the function tests status.

Primary capacity is directly assigned only after all applicable primary calls pass their status checks. Secondary capacity is directly assigned only after the secondary call passes its check.

The local status slot is initialized once, before buffer processing. The same slot is supplied to every reached buffer call; it is not explicitly reset between calls.

### Partial updates

The operation is not transactional.

- First-primary failure leaves that call’s returned value assigned at `0x18`, without a primary-capacity commit.
- Second-primary failure leaves both primary-buffer assignments in place, without a primary-capacity commit.
- Optional-primary failure leaves all three primary-buffer assignments in place, without a primary-capacity commit.
- Secondary failure after primary success leaves primary capacity committed and the secondary-buffer assignment performed, but does not commit secondary capacity or invoke final processing.

These are this function’s own effects. Dependencies may themselves change capacities or other state. No preservation guarantee for those fields follows from the caller.

There is no visible rollback, retry, compensating operation, explicit release, logging, or locking.

The status-slot address refers to local storage. Whether F-6dd003795db7 retains that address is unknown; safe use after this function returns cannot be inferred.
