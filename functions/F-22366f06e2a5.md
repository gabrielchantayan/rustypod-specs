# F-22366f06e2a5

## Purpose

F-22366f06e2a5 performs an ordered initialization-and-transfer operation between two caller-supplied object addresses. It invokes two dependencies with a captured source-associated value, invokes another dependency on two pairs of embedded addresses, and then updates selected destination words from the source.

The operation is not a whole-object copy. It passes a displacement into the first dependency, adds that displacement to two source-derived arguments, and applies a displacement scaled by 983,040 to two later destination fields. One destination word is explicitly cleared, and five trailing words are transferred without arithmetic.

These structural effects are established by the supplied representation. Descriptions such as “clone,” “position adjustment,” “animation setup,” or “reference attachment” would be inferred intent, not established behavior. In particular, the numeric constant 1000 and the scaled displacement have no established units.

## Interface

### Inputs

The function accepts four arguments:

| Argument | Interpretation established by the representation |
|---|---|
| Destination | Object base address, represented as an integer. Used to form dependency arguments and direct memory addresses. |
| Source | Object base address, represented as an integer. Used for direct reads and embedded-address dependency arguments. |
| Displacement | Integer used unchanged as a dependency argument, added to two source words, and multiplied by 983,040 for two later updates. |
| Auxiliary value | Opaque four-byte value forwarded unchanged to the first dependency. |

The source representation uses integer address values and four-byte memory accesses. A 32-bit execution model is strongly indicated, but the supplied material does not independently establish the target ABI, byte order, alignment rules, or pointer representation. Those platform details remain documented_only.

The field operations below describe four-byte words, not a portable externally serialized format. No signedness or semantic type is established for words that are merely transferred.

### Result

There is no explicit return value. Dependency return values, if any, are not inspected or propagated.

There is no explicit status result, validation result, or error translation.

### Required accessible storage

For the function’s own direct accesses, the following locations must be accessible at the time of access:

- Source offset `0x128`, containing an address-like word.
- Offset `0x1C` from the address initially obtained from source offset `0x128`.
- Source offsets `0x12C`, `0x130`, `0x00C`, `0x140`, `0x164`, `0x188`, `0x1AC`, `0x1D0`, and `0x1F4`.
- Destination offset `0x128`, read after the first dependency returns.
- Writable destination offsets `0x00C`, `0x010`, `0x140`, `0x164`, `0x188`, `0x1AC`, `0x1D0`, and `0x1F4`.

The highest directly accessed object word begins at `0x1F4` and occupies four bytes. This does not establish that every intervening byte is accessed, nor that an allocation of exactly `0x1F8` bytes is sufficient for the dependencies.

The dependencies additionally receive addresses at source and destination offsets `0x008` and `0x050`. Their required storage extents are unknown.

No null, bounds, alignment, overlap, lifetime, or ownership checks are visible. Validity must account for changes made by preceding dependency calls, not just entry-state validity.

## Behavior

### 1. Capture a source-associated value

The function first reads the address-like word at source offset `0x128`. From that referenced storage, it reads the four-byte word at offset `0x1C`.

The second word becomes the captured value used in both of the next two dependency calls. It is not fetched again between those calls.

Consequently, mutation of the source offset `0x128`, the referenced storage, or its offset `0x1C` during the first dependency does not change the value supplied to the second dependency. Whether the captured value remains valid after such mutation is a separate dependency and lifetime question.

### 2. Invoke F-7cb8ec6f6858

The first dependency receives six arguments in this positional order:

1. Destination base address.
2. The captured value.
3. The word at source offset `0x130`, plus the displacement.
4. The word at source offset `0x12C`, plus the displacement.
5. The displacement itself.
6. The auxiliary four-byte value.

Both source-word additions are evaluated before the dependency is entered. Their relative memory-read order is not established by the supplied call expression. The contract therefore does not impose an order between the reads at `0x130` and `0x12C`.

The captured value is obtained before these argument reads. No initial snapshot of the later source fields is made.

### 3. Invoke F-eef117f98f87

After the first dependency returns, the function reads the current four-byte word at destination offset `0x128`.

It then calls F-eef117f98f87 with:

1. That newly read destination word.
2. The previously captured value.
3. The integer constant 1000.
4. Zero.
5. Zero.
6. Zero.

The destination word is deliberately described as current: it is read after F-7cb8ec6f6858, so a change made by that dependency can affect this call.

There is no visible validation or conditional branch between the dependency calls.

### 4. Invoke F-470fed045f43 twice

After F-eef117f98f87 returns, the function makes two calls to F-470fed045f43:

| Call order | First argument | Second argument |
|---|---|---|
| First | Destination plus `0x008` | Source plus `0x008` |
| Second | Destination plus `0x050` | Source plus `0x050` |

These are address arguments, not direct four-byte field transfers by F-22366f06e2a5.

The call order is established. The helper’s transfer extent, direction, overlap handling, and other effects are not established merely by its argument positions. It must not be assumed to implement a plain memory copy.

In particular, destination offset `0x00C` is four bytes after the first destination address passed to this dependency. Whether the dependency accesses that word is unknown. The later direct write to `0x00C` occurs after both calls.

### 5. Perform ordered direct field updates

Only after all four dependency calls return does the function perform its explicit destination writes:

| Order | Source read | Destination write |
|---|---|---|
| 1 | Word at source `0x00C` | Source value plus displacement × 983,040, at destination `0x00C` |
| 2 | None | Four-byte zero at destination `0x010` |
| 3 | Word at source `0x140` | Source value plus displacement × 983,040, at destination `0x140` |
| 4 | Word at source `0x164` | Same four-byte value at destination `0x164` |
| 5 | Word at source `0x188` | Same four-byte value at destination `0x188` |
| 6 | Word at source `0x1AC` | Same four-byte value at destination `0x1AC` |
| 7 | Word at source `0x1D0` | Same four-byte value at destination `0x1D0` |
| 8 | Word at source `0x1F4` | Same four-byte value at destination `0x1F4` |

Each source word is read for its individual assignment, after all preceding calls and assignments. These values are not necessarily the values present when the function was entered.

The constant 983,040 is hexadecimal `0x000F0000`. It is an integer scaling factor in the supplied representation; no fixed-point format or physical unit is established.

### Arithmetic boundaries

The representation treats the displacement and arithmetic source words as integer values. The apparent word width is 32 bits.

For signed 32-bit arithmetic, the product of the displacement and 983,040 is representable when the displacement lies from −2184 through 2184, inclusive. This range alone does not guarantee that either final addition is representable. The additions to source offsets `0x130` and `0x12C` also have their own overflow boundaries.

Overflow behavior is not established by the supplied representation. In particular, the contract does not assert that overflow traps, saturates, or wraps modulo \(2^{32}\). A wrapping interpretation would require additional target-level evidence. Acceptance examples below use representable arithmetic.

### Aliasing and changing source state

No non-aliasing requirement or alias rejection appears in the function.

If source and destination are identical, the same ordered calls and accesses still apply. For the final direct-update phase, each arithmetic field is read and then replaced, while the five unmodified-transfer fields are read and written at their existing addresses.

If source and destination partially overlap, an earlier destination write can change a later source read. There is no visible temporary snapshot protecting against this. Dependency effects can likewise change later reads.

Accordingly, the contract specifies access order rather than promising entry-state copying or general overlap safety.

## Side effects

The function directly writes eight destination words, in the order listed above. It directly reads the source-associated address chain, the first dependency’s source arguments, the destination-associated word for the second dependency, and the source words used in the final updates.

It additionally invokes dependencies four times. Their effects are not bounded by the direct-write list. They may affect later observations if they modify reachable storage or global state.

No direct allocation, deallocation, reference-count adjustment, locking, logging, or external I/O is visible in this function. That observation does not rule out any of those effects inside dependencies.

Ownership is unspecified:

- Forwarding a value does not establish ownership transfer.
- Reading a value does not establish that it is retained.
- Reusing the captured value does not establish that a dependency preserves its lifetime.
- The function does not visibly release the captured value or either object, but dependencies may have ownership-related effects.

The function provides no visible rollback. If execution fails or does not return during a dependency or memory access, earlier effects may already have occurred. Atomicity and concurrent-access safety are not established.

## Acceptance examples

These examples are conditional contracts, not reports of executed tests.

### Representable displacement and stable source

Assume all dependencies return normally, storage is valid, and dependency effects leave the relevant source words unchanged.

For a displacement of 2:

- Source `0x130` equal to 40 produces the third argument 42 for F-7cb8ec6f6858.
- Source `0x12C` equal to 70 produces the fourth argument 72.
- Source `0x00C` equal to 100 produces destination `0x00C` equal to 1,966,180.
- Source `0x140` equal to −50 produces destination `0x140` equal to 1,966,030.
- Destination `0x010` becomes zero.
- Each of the five trailing transfer fields receives its corresponding source word.

The calls must occur before those direct writes.

### Zero displacement

With displacement zero and valid, stable source storage:

- The two adjusted arguments equal their source words.
- The direct updates at `0x00C` and `0x140` equal the source words read at those steps.
- Destination `0x010` is still cleared.
- All dependencies are still called.

Zero displacement does not select a shortcut.

### First dependency changes destination-associated state

Suppose F-7cb8ec6f6858 replaces destination offset `0x128` before returning.

F-eef117f98f87 receives the replacement value as its first argument, not the destination word that existed on entry. Its second argument remains the initially captured source-associated value.

### A dependency changes a later source field

Suppose a dependency changes source offset `0x164` and returns normally, without a subsequent operation changing that location again.

The later direct transfer uses the changed word. Using a value snapshotted before the dependency calls would not match the observed access structure.

### Identical source and destination

If both object addresses are identical and the dependencies support those arguments, the final direct phase reads each arithmetic field immediately before updating it, clears offset `0x010`, and performs the five same-location transfers.

This example does not assert that the dependencies support self-aliasing; their acceptance conditions remain unknown.

### Invalid initial address chain

If source offset `0x128` cannot be read, or the resulting address does not permit the read at offset `0x1C`, there is no visible guard or explicit error result.

The environment determines the consequence of the invalid access. The specification does not invent a recoverable failure return.

## Evidence
