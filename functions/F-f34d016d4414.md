# F-f34d016d4414

## Purpose

F-f34d016d4414 consumes a zero-terminated byte sequence, decodes selected one-, two-, and three-byte character encodings, passes each decoded value to F-0ec8efa9c769, and writes the dependency’s 16-bit result to consecutive output positions.

The accepted byte patterns resemble a subset of UTF-8, but this routine is not a strict UTF-8 validator. It accepts overlong encodings and encoded surrogate values, rejects four-byte encodings, and replaces a literal single-byte colon with a slash before invoking the dependency. Equivalent values obtained through multibyte decoding do not receive that replacement.

The routine reports a 32-bit status and, on successful termination, stores a 16-bit output-unit count. Output capacity enforcement is asymmetric: a capacity comparison occurs for multibyte characters, but not for single-byte characters. Consequently, the capacity argument is not a general memory-safety bound.

These are static observations. No runtime tests have been performed.

## Interface

The routine has four inputs:

| Input | Established role |
|---|---|
| Source address | Address of bytes to consume. A zero byte encountered at a character boundary terminates processing. |
| Capacity argument | Signed 32-bit integer used to construct an output-end address for multibyte capacity checks. |
| Destination address | Beginning of consecutive 16-bit output writes. |
| Count address | Address receiving a 16-bit zero initially and a 16-bit output count on success. |

The return value is 32 bits:

| Value | Meaning established by local control flow |
|---|---|
| `0x00000000` | A zero byte was encountered at a character boundary; the success count was stored. |
| `0x00000016` | An unsupported leading byte or an invalid continuation byte was encountered. |
| `0x00000037` | A syntactically accepted multibyte character reached an output position at or beyond the computed end address. |

The last two meanings describe the branches selecting those values, not externally established error names.

### Required memory conditions

The routine performs no null-pointer checks, source-length checks, or alignment checks.

For execution without invalid memory accesses:

- The count address must permit a 16-bit write immediately upon entry.
- The source must remain readable for every byte the routine examines, including continuation bytes.
- Every actual destination write must have two writable bytes available, regardless of the capacity argument.
- Destination addresses must satisfy the execution environment’s requirements for 16-bit stores.
- Calls to F-0ec8efa9c769 must satisfy that dependency’s unknown preconditions.

A source terminator does not protect against every read beyond a logical string boundary. A zero byte examined as a required continuation byte is invalid continuation data, not successful termination.

No allocation, ownership transfer, or release is explicit in this routine. The caller supplies the storage. The dependency’s ownership and memory effects are not established.

## Behavior

### Entry and termination

The first explicit memory operation is a 16-bit zero write through the count address. This precedes the first source-byte read.

The output cursor initially identifies the destination address. Processing then examines source bytes at character boundaries.

If the next leading byte is zero:

- No dependency call occurs for that byte.
- No output terminator is written.
- A 16-bit count derived from the output cursor’s byte displacement is stored through the count address.
- The routine returns success.

For ordinary, nonwrapping address arithmetic, each successful output advances the cursor by two bytes, so the stored count represents the number of 16-bit output units, not a byte count.

The displayed count calculation multiplies the 32-bit byte displacement by `0x8000`, takes the upper 16 bits of the resulting 32-bit value, and stores 16 bits. Under modulo-32-bit arithmetic and two-byte cursor increments, this yields the output-unit count modulo `65536`. It does not report overflow or saturate. Address-wrap and overflow behavior outside the ordinary valid-buffer case require execution-model evidence not supplied here.

### Single-byte input

Any nonzero leading byte below `0x80` is accepted as a one-byte character.

Its numeric value is passed to F-0ec8efa9c769, with one exception: a literal byte `0x3A` is changed to the value `0x2F` before the call.

There is no destination-capacity comparison on this path. This applies both to ordinary single-byte values and to the colon replacement.

For example, a zero capacity argument does not prevent a nonempty single-byte source from causing output writes.

### Two-byte input

Leading bytes from `0xC0` through `0xDF` select a two-byte sequence.

The second byte must be in the range `0x80` through `0xBF`. If it is not, the routine returns `0x16` without calling the dependency or writing an output unit for that sequence.

For accepted sequences, the decoded value combines:

- The low five bits of the leading byte as the high portion.
- The low six bits of the second byte as the low portion.

This yields a value from `0` through `0x7FF`.

No shortest-form restriction is enforced. In particular, `0xC0` and `0xC1` are accepted leading bytes when followed by a valid continuation byte. A two-byte sequence may therefore decode to zero or to a value also representable by one byte.

Decoded zero is processed as a value and sent to the dependency. It is not source termination.

### Three-byte input

Leading bytes from `0xE0` through `0xEF` select a three-byte sequence.

The second byte is read and checked first. It must be in `0x80` through `0xBF`. If it fails, the routine returns `0x16` without reading the third byte on this path.

Only after the second byte passes is the third byte read and checked against the same range. Failure returns `0x16`.

For accepted sequences, the decoded value combines the low four bits of the leading byte and the low six bits of each continuation byte. The result lies between `0` and `0xFFFF`.

The displayed arithmetic includes a mask after constructing the upper portion. For the supported three-byte input range, that intermediate fits in the low 16 bits, which the mask retains. It therefore does not impose an additional validity restriction.

There are no checks excluding:

- Values below `0x800`, including overlong representations of zero.
- Surrogate values from `0xD800` through `0xDFFF`.
- Noncharacter values.

### Unsupported leading bytes

Nonzero leading bytes in either of these ranges return `0x16`:

- `0x80` through `0xBF`.
- `0xF0` through `0xFF`.

For such a leading byte, the routine does not read a continuation byte or call the dependency.

Thus a valid four-byte UTF-8 sequence is rejected at its first byte.

### Capacity comparison

After a two- or three-byte sequence has been decoded and its required continuation bytes validated, the routine compares the current output cursor with an end address constructed by adding the capacity argument to the destination address.

If the cursor is at or beyond that end address, it returns `0x37`. Otherwise, processing proceeds to the dependency call and output write.

Important consequences:

- The capacity is applied as a byte displacement, not as a count of 16-bit slots.
- Input validation precedes the capacity comparison.
- Only the start address of the next output unit is checked.
- The comparison does not establish that both bytes of the next store fit.
- Single-byte input bypasses this comparison entirely.

For example, a capacity of one byte permits the first multibyte character’s two-byte output store because its starting cursor is still below the end address.

The intended meaning of negative capacities is unknown. Under an ordinary nonwrapping address interpretation, a negative capacity places the end address below the destination, making an initial valid multibyte character fail the comparison. Pointer wrapping or invalid pointer construction is outside that conditional interpretation.

### Dependency call and output commit

For each accepted character that passes any applicable capacity check:

1. The decoded or substituted value is passed to F-0ec8efa9c769.
2. The dependency’s 16-bit result is written at the current output cursor.
3. The cursor advances by two bytes.

Supported decoded values require at most 16 bits, although the displayed argument computation uses a 32-bit value.

The dependency’s result is not validated. A zero result, if returned, is written as an ordinary output unit and does not terminate conversion.

There is no rollback on a later error. Earlier explicit output writes remain unless affected by aliasing or dependency side effects.

## Side effects

The routine explicitly performs:

- An initial 16-bit zero write to the count address.
- Ordered source-byte reads.
- One call to F-0ec8efa9c769 per accepted character that reaches conversion.
- One 16-bit destination write per completed dependency call.
- A final 16-bit count write only on successful source termination.

It does not explicitly write a destination terminator.

On either error return, the routine makes no final count update. With disjoint buffers and a dependency that does not modify the count storage, the count therefore remains zero even if earlier characters produced output. Without those conditions, zero cannot be guaranteed: the initial count write may be overwritten through aliasing or dependency effects.

Aliasing matters throughout:

- Count storage overlapping the source can change the source before its first read.
- Destination writes overlapping unread source can alter subsequent decoding.
- Count storage overlapping the destination can overwrite an output unit at entry or successful termination.
- Dependency side effects may change memory subsequently observed by the routine.

No nonaliasing validation is present. A contract requiring stable source contents and independently meaningful output and count values must require disjoint storage or separately establish safe overlap conditions.

The byte order of each 16-bit store is not established by the supplied routine alone.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, assume readable source bytes, writable suitably aligned destination storage, disjoint count storage, nonwrapping address arithmetic, and a dependency that returns normally without modifying those buffers.

1. **Empty source**

   Source begins with `00`. Expected: success, count zero, no dependency call, and no destination write.

2. **Literal colon**

   Source is `3A 00`. Expected: one dependency call with `0x2F`, one output unit containing its result, count one, and success.

3. **Overlong colon**

   Source is `C0 BA 00`, with sufficient applicable capacity. Expected: one dependency call with `0x3A`, not `0x2F`. The literal-colon substitution does not apply to multibyte decoding.

4. **Encoded zero followed by termination**

   Source is `C0 80 00`, with sufficient applicable capacity. Expected: one dependency call with zero, one output unit, then success with count one. The decoded zero does not terminate conversion.

5. **Surrogate value**

   Source is `ED A0 80 00`, with sufficient applicable capacity. Expected: the value `0xD800` reaches the dependency. The routine does not reject it as a surrogate.

6. **Invalid second byte of a three-byte sequence**

   Source begins `E1 41`. Expected: `0x16`, no dependency call for that sequence, and no third-byte read on that path.

7. **Unsupported four-byte sequence**

   Source begins `F0 90 80 80`. Expected: `0x16` upon the leading byte, without continuation-byte reads for that sequence.

8. **Malformed sequence takes precedence over capacity failure**

   Capacity is zero and source begins `C2 41`. Expected: `0x16`, not `0x37`, because continuation validation occurs first.

9. **Valid multibyte sequence with zero capacity**

   Capacity is zero and source begins `C2 80`. Expected: both bytes are read, validation succeeds, then `0x37` is returned without a dependency call or output write for that sequence.

10. **One-byte capacity does not contain a two-byte write**

    Capacity is one and source is `C2 80 00`. If the actual allocation has at least two writable bytes, expected: one output unit and success with count one. The declared byte limit does not prevent the second byte of that store.

11. **Single-byte input ignores capacity**

    Capacity is zero and source is `41 00`. If actual destination storage is writable, expected: a dependency call with `0x41`, one output unit, and success.

12. **Partial output before error**

    Source is `41 80`. Expected: one completed output unit for the first byte, followed by `0x16`. The count remains zero under the stated disjointness and dependency assumptions.
