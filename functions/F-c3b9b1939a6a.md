# F-c3b9b1939a6a

## Purpose

F-c3b9b1939a6a converts pairs of 32-bit source words into individual 32-bit destination words. Each source word contributes a 16-bit value: five bits selected from source bits 19–23, six bits selected from bits 10–15, and five bits selected from bits 3–7. The first source word supplies the destination’s low half; the second supplies its high half.

The function processes a caller-specified number of rows. Within each row, it processes source words in pairs until the number of source positions covered is at least the supplied width. A positive odd width therefore consumes one additional source word and produces a complete final pair. There is no partial-pair handling.

**Inferred intent:** the selected bit fields are consistent with converting a packed 24-bit color representation, carried in 32-bit words, into paired RGB565 values. Channel names, color space, and the role of the ignored high byte are not established by the supplied material.

## Behavior

### Dimension handling

If height is zero or negative, the function returns without processing any rows or accessing either pointed-to region.

If height is positive, the function processes rows in ascending order.

At the start of each row, the covered-source-position count is reset to zero. The source and destination positions are **not** reset. They continue from the positions reached by the preceding row.

If width is zero or negative, the row performs no source reads, destination writes, or pointer advances. Positive height still controls the internal row iteration, but this produces no buffer change.

For positive width, every row processes at least one pair. Each pair advances the covered-position count by two. Processing that row stops when this count is no longer less than width.

Consequently:

- Widths 1 and 2 each process one pair per row.
- Widths 3 and 4 each process two pairs per row.
- More generally, adjacent positive odd and even widths share the same pair count.
- A positive odd width does not suppress, mask, or preserve half of the final destination word.

### Per-source-word conversion

For each 32-bit source value, the resulting 16-bit value has this layout:

| Result bits | Source bits | Width |
|---|---|---:|
| 0–4 | 3–7 | 5 bits |
| 5–10 | 10–15 | 6 bits |
| 11–15 | 19–23 | 5 bits |

The following source bits do not affect the result:

- Bits 0–2.
- Bits 8–9.
- Bits 16–18.
- Bits 24–31.

This is bit selection and placement, not rounding, saturation, scaling, or blending. Discarded low bits do not contribute a rounding increment. All 16 result bits are supplied by the selected fields.

Calling the conversion of a source value \(x\) its packed value \(P(x)\), its numerical definition is:

\[
P(x)=
\left(\left\lfloor x/2^{19}\right\rfloor\bmod 32\right)2^{11}
+
\left(\left\lfloor x/2^{10}\right\rfloor\bmod 64\right)2^5
+
\left(\left\lfloor x/2^3\right\rfloor\bmod 32\right).
\]

The fields do not overlap, so this addition is equivalent to combining the fields bitwise.

### Pair packing

For each pair, let \(a\) be the first source word and \(b\) the immediately following source word. The destination value is:

\[
P(a)+2^{16}P(b).
\]

Thus:

- Destination bits 0–15 contain the first converted source word.
- Destination bits 16–31 contain the second converted source word.
- Every destination bit is replaced.
- The previous destination value is not read or preserved.

The highest packed result bit is bit 31. Under the 32-bit unsigned model, the packing operations fit within the destination word without losing any selected source bit.

### Access order and progression

Each pair has the following memory-access order in the supplied representation:

1. Read the first source word.
2. Read the second source word.
3. Write one complete destination word.

Both source values are obtained before the destination write for that pair.

The next pair starts two source words later and one destination word later. These are contiguous word positions; there is no separate byte stride, row pitch, padding adjustment, or row-start lookup.

For nonoverlapping valid buffers, destination word \(k\), counting from zero, is formed from source words \(2k\) and \(2k+1\). This continues across row boundaries.

For odd widths, each row consumes the rounded-up, even number of source words. For example, width 3 consumes four source words per row. The second row therefore begins at source word 4, not source word 3.

The access order above describes the supplied operation sequence. It is not a guarantee of atomicity, synchronization, or processor-level bus transaction order.

### Byte order

The numerical layout is fixed: first result in the low 16 bits, second result in the high 16 bits.

The corresponding byte sequence depends on the target’s byte order. On a little-endian target, the first result occupies the lower-addressed two bytes of the destination word. On a big-endian target, the second result occupies those bytes. No explicit byte-order conversion is present.

## Side effects

For valid positive dimensions, the function writes exactly one 32-bit destination word per processed pair. With nonoverlapping buffers, it performs two source-word reads and one destination-word write per pair.

There are no explicit source writes. If the buffers overlap, destination writes can nevertheless modify storage that is also part of the source region.

### Overlap

No overlap check or temporary copy of the whole input exists.

Both words of the current pair are read before its output word is written. However, a destination write can overwrite source words needed by a later pair. Any such later read observes the memory then available, rather than an automatically preserved original input.

Accordingly, the pairwise output formula over the **original** input is guaranteed only when writes do not alter source values before their reads. Disjoint valid buffers satisfy that condition. In-place conversion starting at the same address also avoids overwriting future source pairs under the stated access sequence.

Arbitrary overlap must be evaluated against the actual read/write progression; it is not a general snapshot conversion.

## Acceptance examples

These examples are conditional expectations derived from static inspection. They have not been executed.

### Nonpositive height

Given height 0 or a negative height, with any width:

- No source word is read.
- No destination word is written.
- No output status is produced.

Pointer readability and writability are not exercised on this path.

### Nonpositive width

Given positive height and width 0 or a negative width:

- No source or destination word is accessed.
- Destination contents remain unchanged.
- Neither buffer position advances.

### Two distinct packed values

Given width 2, height 1, and two source words:

- First source: `0x00FF0000`.
- Second source: `0x000000FF`.

The first converts to `0xF800`; the second converts to `0x001F`. The single destination word must be `0x001FF800`.

This distinguishes the two half-word positions and confirms that the selected high and low source-byte fields occupy different result fields.

### Full selected-field coverage

Given width 2, height 1, and both source words equal to `0x00FFFFFF`, the destination word must be `0xFFFFFFFF`.

Changing either source word’s bits 24–31 alone must not change its packed result.

### Discarded low bits

Given width 2, height 1, and both source words equal to `0x00070307`, the destination word must be zero. Every set bit in those values falls outside the selected fields.

### Odd-width consumption

Given width 3, height 2, adequate nonoverlapping storage, and source words numbered 0 through 7:

- Destination words 0 and 1 use source pairs 0–1 and 2–3.
- Destination words 2 and 3 use source pairs 4–5 and 6–7.
- Eight source words are read and four destination words are written.

There is no three-word row stride and no discarded second half of a final pair.

### Current-pair overlap

Given width 2, height 1, and identical source and destination starting addresses with sufficient valid storage, the first two source words are read before the first word is overwritten. That output therefore reflects both original source values.

This example does not establish safety for every other overlap arrangement.
