# F-7392db945a55

## Purpose

F-7392db945a55 performs three ordered cell writes through parallel table structures, then modifies a bit in a row-associated 32-bit word.

The supplied column and row serve two distinct roles:

- Their original values are written as cell metadata.
- Separate, mutable four-byte copies select destinations and determine the bit mask.

Dependencies receive the addresses of the mutable coordinate copies before the table operations. The coordinates are subsequently read again for successive selections; they are not established as a single frozen destination. In particular, a table write that overlaps an exposed coordinate copy can change the destination of a later write.

**Established static behavior:** five ordered dependency calls, three ordered cell writes, and a row-word read/modify/write. The descriptor fields and working coordinates are consulted at the stages described below.

**Inferred intent:** place a value at adjusted coordinates, retain its original coordinates, and maintain a per-column condition in a row word. This interpretation does not establish the meaning of the stored value or the dependencies.

## Interface

The function accepts five inputs and has no explicit return value.

| Input | Width and interpretation | Use |
|---|---|---|
| Context | Opaque 32-bit value | Passed unchanged to four dependencies; not directly dereferenced by this function |
| Cell value | Opaque 32-bit value | Copied into the first selected cell |
| Original column | Unsigned 32-bit integer | Initializes the working column and supplies the second cell’s stored value |
| Original row | Signed 32-bit integer | Initializes the working row and supplies the third cell’s stored value |
| Mode | Signed 32-bit integer | Exactly 2 selects bit setting; every other value selects bit clearing |

The working column is an unsigned four-byte object. The working row is a signed four-byte object. Their addresses are passed separately to dependencies. Changes to these copies affect later selections, but do not replace the original argument values used for the metadata writes.

### Descriptor and storage layout

F-bb9feedb0740 supplies a descriptor address. Four consecutive four-byte fields are accessed:

| Byte offset | Interpretation |
|---|---|
| 0 | Address of the first table’s array of row addresses |
| 4 | Address of the second table’s array of row addresses |
| 8 | Address of the third table’s array of row addresses |
| 12 | Address of an array of 32-bit row words |

For each table, the working row selects a four-byte row-address entry. That entry supplies the row-storage address, and the working column selects a four-byte cell within that row.

The row-word array has no intermediate row-address lookup: the working row selects a four-byte word directly.

This establishes only the accessed layout. It does not establish complete object types, dimensions, allocation extents, byte order, alignment guarantees, or non-aliasing.

## Behavior

2. F-32d7a58b928b with the context and the address of the working row.
3. F-d1db756204ac with the context and the address of the working column.
4. F-58820ea3065a with the context.

The explicit pointer arguments identify direct access to the working coordinates, not exclusive access. For example, a dependency receiving the working row’s address could retain that address and make it available to a later dependency. The supplied body does not establish that any dependency preserves globals, descriptor contents, or previously exposed storage.

### Three ordered cell writes

After the dependencies return, the function performs these writes in sequence:

| Order | Selected structure | Four-byte value written |
|---|---|---|
| First | First table | Cell value |
| Second | Second table | Original unsigned column |
| Third | Third table | Original signed row |

Each destination selection uses its own descriptor-field access, row-address lookup, and reads of the working coordinates. The three destinations are not established by one initial coordinate snapshot.

For each write:

- The relevant descriptor field supplies the table’s row-address-array base.
- The working row selects a row-address entry using four-byte scaling.
- The selected row address and the working column, also scaled by four, identify the destination cell.
- The designated value is written there.

The supplied body establishes the order of the completed writes. It does not establish a finer relative evaluation order among all reads used to calculate one destination.

The original column and row determine the metadata values regardless of changes to their working copies. Conversely, those metadata values do not force later destination selections to use the original coordinates.

### Coordinate and structural aliasing

Earlier writes can affect later selections when storage overlaps. Relevant overlap includes:

- A table destination overlapping a descriptor field.
- A table destination overlapping a row-address entry.
- Two table destinations overlapping each other.
- A table destination overlapping either exposed working coordinate.
- A table destination overlapping a row word later accessed.

Thus, “all three tables are updated at the coordinates left by the dependencies” is valid only under an explicit stable-coordinate assumption. The function itself does not establish that assumption.

If the first destination overlaps the working column, the first write changes the column used by the second and third selections and by the subsequent mask calculation. The first write still targets the address calculated before that write; it does not retroactively change its own destination.

Likewise, overwriting the working row can redirect later row-address lookups and the row-word operation. Changes to descriptor fields or row-address entries can redirect later accesses independently of coordinate changes.

### Row-word operation

After the third cell write, the function performs these stages:

1. It reads descriptor offset 12 and uses the working row to locate and read a 32-bit row word.
2. It reads the working column and uses its low eight bits as the shift count for a left shift of integer 1.
3. It combines the captured word with that mask:
   - Mode exactly 2: bitwise OR.
   - Every other mode: bitwise AND with the 32-bit complement of the mask.
4. It accesses descriptor offset 12 again and reads the working row again to select the destination of the final four-byte write.

The mask is formed from the working column at the mask-calculation stage, not necessarily the column used by any cell write.

The final row-word destination is calculated again. The body does not establish a retained row-word address shared by the read and write. If the descriptor field or working row changes between those stages, the function can write the modified captured word to a different address. The stored result still derives from the previously read word and previously calculated mask.

With stable storage and a valid single-bit mask, setting or clearing preserves every other bit. An already-set bit remains set; an already-clear bit remains clear. These cases do not suppress the final write.

### Widths and arithmetic

Descriptor fields, row-address entries, cells, and row words are all accessed in four-byte units.

The working column is unsigned 32-bit. Its cell-address contribution uses the column multiplied by four with unsigned 32-bit arithmetic; the low-eight-bit reduction applies only to the shift count. A column of 256 therefore does not mean cell column 0, even though its mask shift count is 0.

The working row is signed 32-bit and is multiplied by four for row selection. No negative-row rejection or signed-overflow check is visible. A negative row can select storage before an array base if the execution environment and storage layout permit that access; the function does not promise such storage exists.

The mask’s shift count lies between 0 and 255. This is not a reduction modulo 32.

Under ordinary 32-bit signed-integer shift rules:

- Counts 0 through 30 produce unambiguous representable single-bit masks.
- Count 31 raises the signed-left-shift representability issue for the integer literal 1.
- Counts 32 through 255 are outside the width of the shifted integer.

A portable acceptance condition for the displayed mask operation is therefore a low-eight-bit column value from 0 through 30. No target-specific behavior is promised outside that range. In particular, column 32 is not specified to select bit 0.

Unsigned scaling has 32-bit modular arithmetic, but this alone does not establish usable wrapped addresses. Exact address-conversion behavior, signed-overflow consequences, and target address wraparound remain unresolved.

## Side effects

### Direct memory effects

The visible sequence includes:

- Initialization of two four-byte working coordinate objects.
- Exposure of their addresses to dependencies.
- Descriptor and row-address reads for the cell selections.
- Three ordered four-byte cell writes.
- A four-byte row-word read.
- A four-byte row-word write after mask computation and mode selection.

Coordinate reads occur throughout destination selection and mask formation. The working coordinates can therefore carry state changes from earlier aliased writes into later operations.

No explicit allocation, deallocation, reference-count adjustment, or ownership transfer appears in this function. The cell value is copied as a four-byte quantity. Whether it represents an owned resource is unknown.

Dependencies may have additional memory-management or global-state effects. Their calls must not be treated as ownership-neutral without further evidence.

The working coordinate addresses refer to local storage. Their exposure permits access during this invocation, including alias arrangements affecting later operations. It does not establish that dereferencing retained addresses after the function returns is valid.

### Errors, partial effects, and concurrency

There is no explicit error result, null check, bounds check, rollback, or recovery path.

If a dependency does not return normally, subsequent operations are not reached. If a later access fails, earlier dependency effects and completed writes may already have occurred.

No synchronization is visible. The row-word update is a separate read and write, not an established atomic operation. Concurrent changes can be lost. Concurrent mutation also cannot be assumed to provide defined behavior merely because the body contains later reads.

## Acceptance examples

These examples are conditional deductions from static evidence, not executed tests. Except where aliasing is expressly introduced, assume returning dependencies, valid non-overlapping storage, stable working coordinates after the dependencies, no intervening mutation, and defined arithmetic.

### Unchanged coordinates and bit setting

Given original column 3, original row 4, mode 2, and unchanged working coordinates:

- The first table receives the cell value at row 4, column 3.
- The second table receives unsigned 3 there.
- The third table receives signed 4 there.
- Row word 4 is ORed with hexadecimal 00000008.

An initial row word of hexadecimal 00000020 becomes hexadecimal 00000028.

### Adjusted destination with original metadata

Given original column 3 and original row 4, suppose the dependency sequence leaves working column 6 and working row 1.

If those working copies remain unchanged throughout the accesses:

- All three cell writes target row 1, column 6.
- The second table stores 3.
- The third table stores 4.
- The row-word operation targets row 1 and uses mask hexadecimal 00000040.

Without the stated stability assumption, the shared destination is not guaranteed.

### First cell write changes the working column

Given original column 0, original row 4, cell value 1, and mode 2, suppose:

- Dependencies leave working column 0 and working row 4.
- The first table’s selected cell at row 4, column 0 is exactly the working column’s four-byte storage.
- All later selected storage is otherwise valid and does not further alter the coordinates or addressing structures.

Then:

- The first write stores 1 into the working column’s storage.
- The second write selects row 4, column 1 and stores original column 0.
- The third write selects row 4, column 1 and stores original row 4.
- The mask uses shift count 1, producing hexadecimal 00000002.

If row word 4 initially contains hexadecimal 00000010, the final value is hexadecimal 00000012. The first write used column 0; later selections used column 1.

### Clearing for every other mode

With stable working column 2 and a selected row word of hexadecimal 0000000F, any mode other than 2 produces hexadecimal 0000000B.

Modes 0, 1, 3, and negative signed values all take this clearing branch.

### Unchanged bit does not suppress writes

If mode is 2 and the selected bit is already set, the function still performs the three cell writes and the final row-word write. Equal old and new row-word values do not cause an early return.

### Descriptor mutation during dependencies

If a dependency changes the retained descriptor’s first base field before returning, the first table selection uses that changed field. The base was not captured when the descriptor address was obtained.

### Shift boundary

With working column 32, the mask shift count is 32. No particular resulting mask or successful completion is promised. Interpreting this as bit 0 requires additional target-specific evidence.
