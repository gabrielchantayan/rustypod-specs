# F-2a04b18fd4a3

## Purpose

F-2a04b18fd4a3 selects an entry from shared storage using a 32-bit index, examines its ownership state, and follows one of three paths:

- For an initially zero owner, update the entry and return zero.
- For a nonzero owner that subsequently compares equal to the current identity, update the entry and return ten.
- Otherwise, submit a local request to F-c81f7910921f and return the request’s resulting status.

“Owner,” “identity,” “activity,” and “nesting” describe apparent field roles. They do not establish a complete locking, acquisition, waiting, or resource-management protocol.

This contract distinguishes established static behavior from inferred intent and unresolved target-dependent behavior. No runtime tests have been performed.

## Interface

| Auxiliary value | 32 bits | Copied unchanged into the delegated request. |
| Result | 32 bits | Zero on the initially unowned path; ten on the matching-owner path; request status after delegation otherwise. |

There is no explicit index validation, negative-index rejection, overflow check, or table-bound check. Negative indexing is not established as supported behavior.

The auxiliary value is not directly interpreted or dereferenced. Its meaning and signedness are unknown.

### Shared state and entry layout

The function uses a shared table base and a shared pointer to a 32-bit identity value. Entries have a 32-byte stride.

The access widths are distinct from the apparent logical field widths:

| Entry offset | Direct read | Direct write | Description |
|---:|---:|---:|---|
| 0 | 32 bits | 32 bits on initial claim | Owner value. |
| 4 | **32 bits on matching ownership** | **16 bits** on either direct-update path | Nesting-related storage. The matching path converts the 32-bit read to a signed 16-bit value before incrementing. |
| 24 | 32 bits | 32 bits on either direct-update path | Activity counter. |

The matching-owner read at offset 4 covers bytes **4–7**, including bytes 6–7. The corresponding write covers only bytes **4–5**. Bytes 6–7 are therefore read but not directly written by that update.

Bytes 8–23 and 28–31 are not directly accessed through the entry pointer. This does not exclude indirect access through an aliasing identity pointer or effects of dependencies.

Byte order is unresolved. Consequently, the low 16 value bits of the 32-bit read at offset 4 are not established to correspond to the 16-bit object written at that same address.

### Preconditions and failure boundary

Ordinary completion requires:

- Valid storage for the selected entry accesses.
- A readable shared identity-pointer location.
- Readable 32-bit identity storage wherever the executed path dereferences that pointer.
- Normally returning dependencies.
- Address and arithmetic behavior that permits the selected accesses.

In particular, matching ownership requires a readable **four-byte region at entry offsets 4–7**, even though only two bytes are written there. Readable storage limited to offsets 4–5 is insufficient for that path.

Alignment requirements, valid index range, and table extent are **documented_only**. No explicit error result handles invalid memory, invalid indexing, arithmetic failure, or dependency nonreturn.

## Behavior

### Entry selection and initial call

The function calculates the selected entry address from the shared table base and 32 times the index before invoking **F-opaque-01**.

After that dependency returns, the function obtains and retains the shared identity pointer. It then reads the selected entry’s 32-bit owner value.

The ordering establishes that:

- Entry selection uses the table base obtained before F-opaque-01.
- Owner inspection occurs after F-opaque-01.
- The retained identity pointer is obtained after F-opaque-01.
- Retaining that pointer does not capture the identity value to which it points.

No dependency-preservation guarantee is available. F-opaque-01 may affect shared state; this function nevertheless continues using its already-selected entry address.

### Initially zero owner

If the first owner read is zero, the function performs these operations in order:

1. Reads the 32-bit activity counter at offset 24 and writes its incremented value.
2. Reads the 32-bit identity through the retained pointer and writes it to the owner at offset 0.
3. Writes one to the 16-bit region at offset 4.
4. Invokes **F-opaque-02**.
5. Establishes and returns a 32-bit result of zero.

There is no direct nesting read on this path. In particular, the function does not perform the matching path’s four-byte read at offset 4.

There is no check that the installed identity is nonzero. A zero identity leaves the owner zero despite the counter and nesting writes.

The identity-value read occurs after the activity update. If the identity storage aliases the activity counter, the owner assignment can therefore observe the updated value. The function does not provide an unconditional identity snapshot at entry.

The result is established after F-opaque-02 returns. Ordinary memory changes by that dependency do not change the direct result of zero, although they may change the entry’s eventual state.

### Matching owner after an initially nonzero read

If the first owner read is nonzero, the function makes a separate ownership comparison. It reads the owner again and compares it with the 32-bit identity obtained through the shared identity pointer referenced for this comparison.

This comparison is not established to reuse the retained pointer from the initial capture. The relative order of the operand reads within the comparison is unresolved.

The two owner observations are separate. Without a stability guarantee, the second owner value need not equal the first or remain nonzero.

When the comparison matches, the function performs these operations in order:

1. Reads and increments the 32-bit activity counter at offset 24.
2. Reads a **32-bit signed word** at offset 4.
3. Converts that word to a **signed 16-bit value**.
4. Increments the converted value using the wider integer arithmetic represented by the supplied material.
5. Stores the result as a **signed 16-bit value** at offset 4.
6. Invokes F-opaque-02.
7. Establishes and returns a 32-bit result of ten.

The read at offset 4 and the write at offset 4 have different widths. This behavior must not be replaced in the contract by an unconditional “read and increment a 16-bit field.”

No direct owner write occurs on this path.

### Nesting conversion and arithmetic limits

For a 32-bit word numerically within −32,768 through 32,767, conversion to signed 16 bits preserves its value.

For a 32-bit word outside that range, the initial signed narrowing is implementation-dependent. The supplied representation does not establish a portable low-bit truncation rule.

After a successfully produced signed 16-bit value, adding one yields a value between −32,767 and 32,768. Those values fit the represented 32-bit arithmetic width. The addition itself therefore does not require signed 32-bit overflow.

The final signed 16-bit store is exact when the incremented value is within −32,768 through 32,767. If the converted value was 32,767, the increment produces 32,768, and the final narrowing is again implementation-dependent.

Two independent limitations prevent an unconditional modulo-\(2^{16}\) field-increment contract:

- Signed out-of-range narrowing is not established to retain the low 16 bits.
- Unknown byte order prevents equating the low 16 bits of the four-byte read with the two-byte object written at the same starting address.

Accordingly, an existing two-byte value of 65,535 does **not**, by itself, establish that this path writes zero.

### Different-owner delegation

If the initial owner read is nonzero and the later comparison is unequal, the function invokes F-opaque-02 before constructing the delegated request.

The request has this layout under the represented 32-bit pointer model:

| Request offset | Width | Value before delegation |
|---:|---:|---|

| 4 | 32 bits | Zero; subsequently used as the returned status |
| 8 | 32 bits | Original entry index |
| 12 | 32 bits | One |
| 16 | 32 bits | Original auxiliary value |
| 20 | 32-bit pointer | Address of a local 32-byte buffer |

The described request region occupies 24 bytes. Its initialization order is:

1. Buffer pointer at offset 20.
2. Status zero at offset 4.
3. Constant 14 at offset 0.
4. Constant one at offset 12.
5. Index at offset 8.
6. Auxiliary value at offset 16.

The function passes the address of the request’s first field to **F-c81f7910921f**.

The local 32-byte buffer is not initialized before that call. Its incoming contents are not established as zero, meaningful data, or a defined serialized object.

After the dependency returns, the function reads and returns the 32-bit status at request offset 4. The dependency’s direct return value is unused.

This path performs no direct entry-field update before delegation. Dependencies may nevertheless modify the entry or other shared state.

### Activity and address arithmetic

The activity counter uses represented signed 32-bit arithmetic. For values whose increment is representable, the direct update stores the value plus one. Incrementing the maximum signed 32-bit value has no established portable result; no saturation, explicit overflow error, or guaranteed wraparound is shown.

The index multiplication and entry-address addition are unchecked. Their behavior at arithmetic boundaries is unresolved. The 32-byte stride does not establish a supported wraparound indexing policy.

## Side effects

### Direct writes and call placement

The initially zero-owner path writes activity, owner, and then the two-byte nesting region.

The matching-owner path writes activity and then the two-byte nesting region. Before the second write, it reads four bytes at offset 4.

The delegated path initializes local request storage after F-opaque-02 and returns the resulting status after F-c81f7910921f.

Each normally completed path invokes F-opaque-01 once and F-opaque-02 once. On the direct paths, F-opaque-02 follows the entry updates. On the delegated path, it precedes request initialization.

These statements describe direct operations and their ordering, not guaranteed final shared-state values after unknown dependency effects.

### Storage lifetime and ownership

The request and 32-byte buffer are local to the invocation. No heap allocation, explicit deallocation, or explicit ownership transfer is visible.

Their addresses are made available to F-c81f7910921f. No lifetime beyond this invocation is promised. Whether that dependency retains pointers, accesses the buffer synchronously, or requires additional lifetime guarantees remains unknown.

The auxiliary value is only copied by this function. That does not constrain how the receiving dependency interprets it or whether that dependency allocates, releases, or accesses memory.

### Synchronization and exceptional execution

The placement of F-opaque-01 and F-opaque-02 suggests paired synchronization, but their contracts are unavailable. This function alone does not establish mutual exclusion, atomic updates, memory barriers, or stable shared-state observations.

No recovery or guaranteed cleanup is shown for a fault or nonreturning dependency. Execution interrupted before F-opaque-02 is not guaranteed to invoke it later.

## Acceptance examples

These are conditional deductions, not executed tests. Unless a case states otherwise, it assumes valid storage, normally returning dependencies, no relevant aliasing, and no dependency or concurrent changes to the described state.

### Initial claim

Given an initial owner of zero, activity of seven, and a retained identity pointer referring to 42:

- Activity is written as eight.
- Owner is written as 42.
- The two-byte nesting region is written as one without a preceding nesting read.
- F-opaque-02 follows these writes.
- The result is zero.

### Matching ownership with representable conversion

Given matching ownership, activity seven, and a **32-bit word read at offset 4 numerically equal to three**:

- Activity is written as eight.
- Conversion to signed 16 bits preserves three.
- Increment and final conversion produce a two-byte stored value of four.
- Bytes 6–7 participate in the read but are not directly written.
- No direct owner write occurs.
- The result is ten.

This example does not assert that the previous two-byte object at offset 4 necessarily represented three.

### Conditional 65,535-to-zero transition

Assume additionally:

- Little-endian integer storage, so the low 16 bits of the four-byte read correspond to the two-byte region at offset 4.
- Out-of-range conversion to signed 16 bits retains those low bits and interprets an all-ones result as −1.

If the two-byte region contains the all-ones pattern, the initial conversion then produces −1, increment produces zero, and the final store writes zero.

Without those additional assumptions, that transition is **documented_only**, not an acceptance requirement.

### Final narrowing boundary

Given matching ownership and a 32-bit word at offset 4 numerically equal to 32,767, the initial signed 16-bit conversion is exact and the increment produces 32,768. The final signed 16-bit result is implementation-dependent. The contract does not require wraparound to −32,768.

### Delegated status

Given an initially nonzero owner and an unequal ownership comparison:

- F-opaque-02 runs before request construction.
- F-c81f7910921f receives the stated request layout and the local-buffer pointer.
- If it writes 23 to request offset 4, the function returns 23.
- If it leaves that field unchanged, the function returns zero.

Neither result independently establishes ownership acquisition.

### Zero identity and pointer replacement

For an initially zero owner and an identity read of zero, the function still increments activity, writes owner zero, writes nesting one, and returns zero.

If the shared identity pointer changes after its initial capture, the zero-owner path uses the retained pointer. The nonzero-owner comparison instead references the shared pointer for that comparison. These accesses cannot be specified as one unconditional identity snapshot.
