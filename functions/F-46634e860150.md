# F-46634e860150

## Purpose

F-46634e860150 writes a two-byte count header and, for each element of a positive-count input, a two-byte position entry into storage identified by a mutable state record. It also invokes dependencies to obtain an initial payload position and to process each element using a destination address, a source-address value, and a length.

Construction of a serialized collection of byte sequences is **inferred intent**, not an established dependency contract. The established behavior consists of the accesses, arithmetic, calls, and state changes described below. Actual payload transfer is unresolved.

The function performs no explicit validation of addresses, array extents, capacity, count, overlap, arithmetic range, or dependency results.

## Behavior

### Initial length scan

For a positive count, the function first reads that many unsigned 16-bit lengths in increasing element order. For zero or negative counts, it performs no scan reads.

The accumulator starts at signed 32-bit zero. Each update converts its current value to unsigned 32 bits, adds the zero-extended length modulo \(2^{32}\), and assigns the result back to signed 32-bit storage.

An unsigned result no greater than 2,147,483,647 retains its numerical value. A larger result introduces a target-dependent unsigned-to-signed conversion. This is not signed-addition overflow, and the evidence does not establish a particular negative result.

The function neither bounds nor validates the total. Individual scanned lengths are not retained for later element processing.

All scan reads precede the metadata reads and explicit writes described next.

### Metadata capture and count-header address formation

After the scan, the function reads, in order:

1. The signed 32-bit buffer-base value at state offset 0x44.
2. The unsigned 16-bit table position at offset 0x0E, zero-extended to unsigned 32 bits.
3. The unsigned eight-bit displacement at offset 0x08, zero-extended to unsigned 32 bits.

The buffer base and initial table position are retained. Later changes to those state fields do not redirect subsequent explicit writes.

Count-header address formation has two distinct arithmetic stages:

- The captured signed buffer base is converted to unsigned 32 bits and added to the zero-extended displacement **modulo \(2^{32}\)**.
- That unsigned result is assigned to a signed 32-bit header-position temporary.

If the unsigned result exceeds 2,147,483,647, this assignment introduces another target-dependent unsigned-to-signed conversion, independent of those in the length total and payload-position updates.

The two header-byte addresses are then formed by adding **3** and **4**, respectively, to that signed temporary. These are signed 32-bit address expressions. Either addition can exceed the signed range independently of whether the preceding unsigned addition and conversion were unproblematic.

Thus, “buffer base plus displacement plus 3 and 4” is only a shorthand. It is not an unconditional mathematical-address guarantee: the unsigned intermediate, its signed conversion, and the two signed additions must be considered separately.

### Count-header writes

For every count, including zero and negative counts, the function writes:

- Count bits 8–15 at the first header-byte address.
- Count bits 0–7 at the second header-byte address.

The first store precedes the second. Both precede any dependency call.

Only the low 16 count bits are serialized. The loops still use the full signed 32-bit count, not the serialized halfword.

These stores may affect later reads if their destinations overlap state or input arrays. Their addresses remain subject to the arithmetic qualifications above.

### Initial payload position and state adjustment

For any nonzero count, the function calls F-cec90b5dcee3 with the state address and the signed accumulator from the initial scan. Its signed 32-bit result becomes the current payload position.

No result value is checked for negativity, invalid range, or a failure sentinel. For a negative count, this call receives an initial total of zero.

After the dependency returns, the function reads the signed halfword at state offset 0x12 and writes an adjusted halfword there. Consequently, any dependency change to this field participates in the adjustment.

The count is first narrowed to a signed halfword. That value is multiplied by −2 and added to the signed-halfword field value using promoted signed arithmetic. Those promoted operations fit within signed 32-bit range. Narrowing the count and storing the result remain target-qualified where values are not representable.

At the represented low-halfword level, the adjustment is:

\[
\text{new field} \equiv \text{old field}-2\,\text{count}\pmod{65,536}.
\]

This describes the low-halfword effect, not a portable guarantee for every out-of-range signed conversion.

The call and adjustment occur for all nonzero counts. Both are skipped for count zero.

### Positive-count element processing

Elements are processed in increasing index order.

For each reached element, the function first writes a two-byte table entry containing bits 8–15 and then bits 0–7 of the current payload position. These stores precede the reads used to prepare F-U1’s source-address and length arguments.

It then reads the element’s four-byte source-address value and unsigned 16-bit length and calls F-U1 with:

- A destination formed from the captured buffer base and current payload position.
- The source-address value.
- The zero-extended length.

Both argument-value reads precede the call; their relative order is not established.

The destination expression adds two signed 32-bit operands. If their mathematical sum falls outside the signed range, the evidence does not establish the resulting behavior. This is separate from the unsigned arithmetic used for table addresses and payload advancement.

After F-U1 returns, the function advances the unsigned table position by two modulo \(2^{32}\). It then rereads the same length entry and advances the payload position using that post-call value.

Payload advancement converts the signed position to unsigned 32 bits, adds the zero-extended length modulo \(2^{32}\), and assigns the result back to signed 32-bit storage. Results above 2,147,483,647 introduce a target-dependent conversion rather than signed-addition overflow.

The table position starts as a zero-extended halfword but thereafter remains unsigned 32-bit storage. It does not wrap at 65,536. Table-address calculations, including the second byte’s additional displacement of one, use unsigned 32-bit arithmetic.

Table entries retain only 16 position bits. F-U1’s destination uses the full signed position, subject to the separate signed-addition constraint.

A zero-length element still receives a table entry and an F-U1 call. With an unchanged post-call length of zero, its payload-position increment is zero.

### Final count write

After the nonzero-count branch, the function writes the narrowed count to state offset 0x14 using a native halfword store.

This is the final explicit write. It occurs for positive, zero, and negative counts, provided execution reaches it normally. Out-of-range signed narrowing is target-qualified; the represented low-halfword value is the count’s low 16 bits.

Neither the final payload position nor the advanced table position is explicitly stored back into the state.

## Side effects

### Writes and partial progress

On normal completion, explicit writes comprise:

- Two header-byte stores.
- One offset-0x12 halfword adjustment for a nonzero count.
- Two table-byte stores per positive-count element.
- One final count-halfword store.

Dependencies can add other effects.

The operation is not atomic. Earlier writes may remain visible if a later access fails or a dependency does not return normally. No rollback or cleanup path is shown. The final count store is not a documented commit mechanism.

### Aliasing and repeated reads

There is no overlap check or input snapshot.

The initial scanned lengths, call-time lengths, and post-call lengths used for advancement may differ:

- Header writes can change inputs subsequently read.
- Table writes can change the current element’s source-address entry or length before argument preparation.
- F-cec90b5dcee3 can change either array before element processing.

Source-address entries are not read during the initial scan. Each is read only when its element is processed.

The retained buffer base is unaffected by later changes to the state’s buffer-base field. This does not prove that the retained storage remains valid.
