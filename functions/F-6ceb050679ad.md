# F-6ceb050679ad

## Purpose

F-6ceb050679ad conditionally clears an object’s leading word and, except for a distinguished object, updates bookkeeping associated with an adjacent allocation header before passing that header to a dependency.

The established behavior is a sequence of conditional calls, memory writes, and 32-bit accounting updates. Its apparent intent is an object-release path with allocator accounting. That interpretation does **not** establish that storage is freed, that synchronization is acquired or released, or that any dependency preserves global state.

There are three principal outcomes:

- A null input or an input whose leading word is zero produces no calls or writes by this function.
- A nonzero leading word is passed through an external operation and then cleared. If the input matches the distinguished object, processing stops there.
- Any other such input proceeds through header validation, accounting updates, and two final dependency calls.

This contract distinguishes behavior visible in the supplied static material from dependency semantics that remain undocumented.

## Interface

### Input and return

The function accepts one pointer, referred to here as the **object pointer**.

- Null is explicitly accepted.
- For a nonnull pointer, the function initially reads a 32-bit word at byte offset 0.
- If that word is nonzero, the function subsequently writes zero to the same location.
- For the ordinary bookkeeping path, the pointer must also support access to metadata preceding it.

The function has no specified return value. It returns normally on the inactive and distinguished-object paths. On the ordinary path, normal return depends on the called dependencies returning.

### Represented widths and layout

The supplied material represents 32-bit words and addresses, with two unsigned 16-bit metadata fields. The contract below uses that represented 32-bit model; it does not imply portability to another pointer width or byte order.

| Location relative to the object pointer | Width | Role |
|---|---:|---|
| −8 bytes | 32 bits | Header word: validation flags and masked accounting amount |
| −4 bytes | 16 bits, unsigned | First accounting selector |
| −2 bytes | 16 bits, unsigned | Second accounting selector |
| 0 bytes | 32 bits | Leading object word inspected and cleared |

The two selectors are separate halfword reads at the stated addresses. Their relationship to a combined 32-bit value is not specified independently of the target’s byte order.

The bookkeeping context is obtained indirectly through a global pointer slot. The distinguished object is obtained from a separate global pointer slot. Their initialization and ownership are unknown.

### Preconditions for defined access

A nonnull input must point to a readable leading word. If that word is nonzero, the location must also be writable and acceptable to the external dependency.

For the ordinary bookkeeping path, further requirements apply:

- The preceding metadata must be readable with the represented access widths.
- The global context reference and all computed context locations must be valid.
- The selector values and the index returned by F-09dcb55e8e0a must select valid bookkeeping locations.
- Dependencies must accept the values passed to them.
- Concurrent or dependency-induced mutations must not make later accesses invalid.

The function performs no general pointer, bounds, alignment, or counter-capacity validation.

## Behavior

### 1. Inactive-input handling

For a null object pointer, the function returns without reading object memory, calling dependencies, or writing bookkeeping state.

For a nonnull pointer, it reads the leading 32-bit word once for the initial activity decision. If that value is zero, it returns without calling dependencies or examining preceding metadata.

Consequently, invalid or unavailable metadata is irrelevant to this function’s inactive-input path, provided the leading-word read itself is valid.

### 2. External operation and leading-word clear

If the initial leading word is nonzero, the function invokes **F-opaque-01**, the locally labeled external dependency, with:

1. the integer value 1; and
2. the object pointer.

After that dependency returns, the function writes zero to the leading word.

The value tested before the call is not tested again. A dependency modification to the leading word therefore does not suppress the subsequent zero write.

The function next compares the object pointer with the distinguished-object pointer obtained from its global slot. If they match, it returns immediately.

This comparison occurs after the external call and zero write. The distinguished pointer must not be treated as an entry-time snapshot: dependency effects or aliasing may affect the value observed at the comparison.

The distinguished-object path does not validate the preceding header, obtain the bookkeeping context, or perform the accounting updates described below.

### 3. Preparation and context capture

For a nondistinguished object, the function calls F-2fd8826557a4 with no explicit arguments.

After that call returns, it reads the bookkeeping-context pointer from its global slot and retains that context value for the remaining operations.

There is no visible null-context check. Later changes to the global context slot do not replace the retained context value, although dependencies may still modify the memory addressed by that context.

### 4. Header validation

The function treats the address eight bytes before the object pointer as the allocation-header address.

It rejects the header when either:

- a 32-bit header read is zero; or
- if the first read is nonzero, a further header read has bit 0 set.

Rejection invokes F-a817d8d58c10. The supplied material identifies this call as nonreturning; no recovery behavior after that call is established.

The checks are not a single immutable header snapshot. With stable memory, they are equivalent to requiring a nonzero header with bit 0 clear. With mutable memory, the two checks may observe different values.

The leading object word has already been cleared before validation. Failure therefore does not preserve the object’s original leading word and does not constitute an all-or-nothing operation.

### 5. Context entry and first four accounting updates

After successful validation, the function calls F-c0fc6d033caa with the retained context value.

No synchronization or memory-preservation guarantee is established for this dependency. The following metadata reads occur after it returns:

1. Read the unsigned 16-bit selector at object offset −4.
2. Form the first counter address at context offset `0x224 + 4 × selector`.
3. Read the header word and mask it with `0x3ffffffc` to obtain the accounting amount.

The function then performs these four read-modify-write updates in order:

| Order | Context-relative location | Update |
|---:|---|---|
| 1 | `0x224 + 4 × first selector` | Subtract the captured accounting amount |
| 2 | `0x30c` | Subtract the same captured amount |
| 3 | `0xe0 + 4 × second selector` | Subtract the same captured amount |
| 4 | `0x220` | Subtract the same captured amount |

The second selector is read from object offset −2 after the first two counter updates and before the third.

The mask removes bits 0–1 and bits 30–31. The resulting amount is a multiple of four, ranging from zero through `0x3ffffffc`, inclusive. A header can pass validation while producing a zero accounting amount.

The first four updates reuse the one captured amount. They do not independently reread the header for each subtraction.

### 6. Count updates and final amount update

After the first four accounting updates, the function calls F-09dcb55e8e0a with no explicit arguments.

Its result is used as an index into context-relative storage. The following updates occur in order:

1. Decrement the 32-bit word at context offset `0x310 + 4 × returned index` by one.
2. Decrement the 32-bit word at context offset `0x390` by one.
3. Reread the header at object offset −8, mask it with `0x3ffffffc`, and subtract that newly observed amount from the 32-bit word at context offset `0x08`.

No index-range check is visible.

The last amount subtraction is distinct from the earlier four: it uses a fresh header read after F-09dcb55e8e0a returns. If that dependency changes the header, the final subtraction can differ from the earlier four subtractions. The header is not revalidated at this point.

### 7. Final dependency calls

After all seven bookkeeping updates, the function calls:

1. F-cc6c9b4a0f68 with the retained context and the allocation-header address;
2. F-e586bff64fb7 with the retained context.

The function then returns if both calls return.

No explicit object or header access follows the first of these final calls. That sequencing does not, by itself, establish which dependency frees memory or which party owns the storage.

### Arithmetic and overlapping locations

Accounting words are updated as 32-bit values. No saturation, underflow check, overflow check, or diagnostic is present. In the represented machine-width behavior, arithmetic wraps modulo \(2^{32}\).

Counter addresses use a four-byte index scale. Both metadata selectors are zero-extended from 16 bits before address formation. The index returned by F-09dcb55e8e0a has no visible range restriction.

The counter locations must not automatically be treated as disjoint. A selected location can coincide with a fixed bookkeeping offset or another selected location. If it does, the ordered read-modify-write operations accumulate on that location; they are not simultaneous updates from a common snapshot.

## Side effects

Direct effects attributable to this function are:

- One leading-word zero write on every active path, before the distinguished-object decision.
- No direct bookkeeping writes on the inactive or distinguished-object paths.
- Seven ordered 32-bit bookkeeping updates on the ordinary path, assuming validation succeeds and intervening dependencies return.
- Invocation of the rejection dependency for a zero or bit-0-set header at validation.

Dependencies may produce additional effects. Their effects are not limited by the explicit argument lists: the supplied material provides no guarantee that they preserve globals, object metadata, context memory, or allocation state.

The bookkeeping operations are separate reads and writes, not an established atomic transaction. There is no visible rollback after an invalid access, nonreturning dependency, or other interruption.

Repeated calls have conditional behavior. If the first completed call leaves the leading word zero, a later call returns through the inactive path. This does not prove general idempotence, because dependencies, concurrent actors, or aliasing may change that word.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

### Null input

Given a null object pointer, the function returns without object reads, dependency calls, or direct writes.

### Inactive object

Given a valid leading word equal to zero, the function reads that word and returns. It does not access the preceding header, even if that metadata would fail validation.

### Distinguished active object

Given an initially nonzero leading word, suppose F-opaque-01 returns and the subsequent distinguished-pointer comparison matches the object pointer.

The required sequence is:

- external call with 1 and the object pointer;
- leading-word write of zero;
- return without bookkeeping preparation or header validation.

### Invalid ordinary header

Given an active, nondistinguished object and a stable zero header, the function clears the leading word, calls F-2fd8826557a4, captures the context, and invokes F-a817d8d58c10.

No accounting update precedes rejection. The leading word remains subject to the already completed zero write; rollback is not provided.

A stable header of `0x00000005` likewise reaches rejection because bit 0 is set.

### Ordinary subtraction

Assume valid, stable, nonoverlapping storage; a stable header of `0x00000022`; valid selectors and returned index; and dependencies that return without changing the relevant values.

The accounting amount is `0x20`. The four initial amount counters and the final counter at context offset `0x08` each decrease by 32. The indexed count and the count at `0x390` each decrease by one. The final two dependency calls occur afterward, in their specified order.

### Accepted zero accounting amount

A stable header of `0x00000002` is nonzero with bit 0 clear, but its masked amount is zero.

The amount-update writes leave their numeric values unchanged unless overlapping effects intervene. The two count decrements still occur.

### Header mutation during index selection

Suppose the first captured masked amount is 32, but F-09dcb55e8e0a changes the header so its masked amount becomes 64.

Subject to otherwise valid memory, the first four amount counters decrease by 32, while the final amount counter decreases by 64. The function does not enforce consistency between those amounts.

### Counter underflow

If a count word is zero before its decrement, the resulting 32-bit value is `0xffffffff`. No underflow error is reported by the visible function.

## Uncertainties

**Inferred intent:** The negative-offset metadata, amount counters, count decrements, and final header handoff suggest allocation-release bookkeeping. This interpretation does not define dependency behavior.

**Documented-only unknowns:**

- The meaning and initialization of the distinguished-object and context globals.
- The external operation’s purpose.
- The ownership and lifetime of the object, header, and context.
- Whether any dependency implements locking or memory release.
- Valid selector ranges and the valid returned-index domain.
- Whether overlapping counter locations are intended or forbidden by an external invariant.
- Target byte order, concurrency rules, and memory-ordering guarantees.
- The rejection mechanism and failure behavior of other dependencies.
- Guarantees against arithmetic wraparound or invalid computed addresses.

These unknowns are not replaced with allocator, synchronization, or ownership assumptions.
