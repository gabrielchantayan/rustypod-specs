# F-598db5dd0432

## Purpose

F-598db5dd0432 coordinates a count-based transfer into a caller-supplied destination. It chooses between a direct backend operation and a staged operation according to whether the destination address is aligned to a 32-byte boundary.

The established behavior includes:

- Treating a zero count as a successful no-op.
- Rejecting count bit patterns that are negative when interpreted as signed 32-bit values.
- Calling a preliminary dependency before either transfer path.
- Using intermediate storage for destinations whose low five address bits are nonzero.
- Bracketing the aligned path with two synchronization-like dependency calls.
- Translating selected backend results and status flags into fixed 32-bit return values.

“Transfer,” “element size,” “intermediate storage,” and “synchronization” describe apparent roles. The supplied evidence establishes the calls and data flow, but not the complete semantics of the dependencies.

## Interface

The function accepts four arguments:

| Argument | Representation | Observed role |
|---|---|---|
| Object | Pointer to an object represented through 32-bit words | Supplies dispatch tables, a backend reference, an intermediate-buffer reference, and a synchronization-like token |
| Position | 32-bit integer | Passed to transfer dependencies; advanced by a number of elements on the staged path |
| Destination | Unsigned 32-bit address value | Determines alignment and is passed to dependencies as an output address |
| Count | Unsigned 32-bit value | Number of requested elements, subject to a signed-range gate |

The return value is an unsigned 32-bit status word. Several results have negative signed interpretations:

| Return bits | Signed interpretation |
|---|---:|
| `0x00000000` | 0 |
| `0xFFFFFFF6` | −10 |
| `0xFFFFFFE3` | −29 |
| `0xFFFFFFDF` | −33 |
| `0xFFFFFFF5` | −11 |
| `0xFFFFFFFE` | −2 |
| `0xFFFFFFF9` | −7 |

The staged path can additionally return whatever bit patterns F-fe1e63264848 produces, including the bitwise OR of two such results. Its return domain is therefore not limited to the table.

### Object layout used by this function

Offsets are byte offsets within the observed 32-bit layout:

| Offset | Access |
|---|---|
| `+0x00` | Read as a dispatch-table pointer |
| `+0x04` | Read as a backend-object pointer |
| `+0x08` | Read as a pointer to a location containing a 32-bit intermediate-buffer value |
| `+0x10` | Read as a token passed to the synchronization-like dependencies |

The object dispatch table has a function entry at `+0x2C`. It is called with the object argument and its result is used as an element size.

The backend dispatch table has entries at:

- `+0x04`: direct transfer operation.
- `+0x18`: conditional preparation operation.
- `+0x74`: status-bit operation.

The source-level evidence shows no explicit arguments for the latter two backend operations. An implicit receiver or hidden calling-convention argument is not established.

### Preconditions

For each path actually reached, referenced object fields, dispatch-table entries, intermediate-buffer storage, and destination ranges must be usable by the corresponding operation. The wrapper does not explicitly validate these properties.

The zero-count and signed-negative-count exits occur before object dereferences.

No independent requirement that count fit in 16 bits is enforced. On the direct path, the backend receives only the low 16 bits even though the preceding size-related operation uses the full accepted count.

## Behavior

### 1. Count gates

A zero count returns zero immediately. No dependencies are called and no object fields are read.

For any nonzero count whose signed 32-bit interpretation is negative, the function returns `0xFFFFFFF6` immediately. Thus count values from `0x80000000` through `0xFFFFFFFF` are rejected before preliminary validation or synchronization.

All remaining counts lie between 1 and `0x7FFFFFFF`, inclusive.

### 2. Preliminary dependency

For every accepted positive count, the function calls F-25748144b48d with arguments in this order:

1. Object.
2. Destination.
3. Position.

Count is not passed.

A nonzero result causes an immediate return of zero. That result is not propagated, translated, or distinguished from successful completion by this wrapper. Neither transfer path is entered.

A zero result allows processing to continue. The destination’s low five bits then select the path.

### 3. Unaligned destination: staged path

A destination is unaligned for this function when its address has any of the low five bits set.

First, F-88991d522e6f is called with the object. Its result is not used.

#### Optional bulk portion

For a count greater than one, the function performs a bulk portion covering count minus one elements:

1. It obtains an element-size value through the object dispatch entry at `+0x2C`, passing the object.
2. It calls F-3cb5472b4a81 with the original destination address. No requested size or count is explicitly passed to this dependency.
3. It calls F-fe1e63264848 with the object, original position, the value returned by F-3cb5472b4a81, and count minus one.
4. It saves that transfer result.
5. It calls the external copy-like dependency with the original destination, the intermediate value returned by F-3cb5472b4a81, and the product of count minus one and the previously obtained element size.
6. It advances the position by count minus one and the destination by that same byte-size product.

The copy-like call is made regardless of the transfer result. A nonzero result from F-fe1e63264848 neither suppresses copying nor prevents the final portion.

The copy-like dependency’s return value is ignored.

For a count of one, this entire bulk portion is skipped. The accumulated bulk status remains zero, and position and destination remain unchanged.

#### Final single-element portion

After the optional bulk portion:

1. The function reads the pointer at object offset `+0x08`.
2. It reads the 32-bit value stored at that pointer.
3. It calls F-fe1e63264848 with the object, current position, that stored value, and a count of one.
4. It obtains an element-size value through a fresh call to the object dispatch entry at `+0x2C`.
5. It calls the external copy-like dependency with the current destination, the previously loaded intermediate-buffer value, and this freshly obtained size.
6. It returns the bitwise OR of the final transfer status and the saved bulk status.

The final copy-like call also occurs regardless of the final transfer status.

The element size is not necessarily stable across the two portions. The bulk portion uses the size obtained before its intermediate-storage dependency and transfer. The final portion obtains a new size after its transfer. No equality check or normalization joins these values.

Similarly, the intermediate-buffer value for the final portion is loaded only after the optional bulk transfer and copy. Mutations made by earlier dependencies can therefore affect which value is loaded.

No explicit synchronization-token calls occur on this path.

### 4. Aligned destination: direct path

A destination is aligned for this function when its low five bits are zero.

The function reads the value at object offset `+0x10`, retains that value locally, and passes it to F-4a19e3742733.

It then performs the following operations in order:

1. It reads the backend reference at object offset `+0x04` and passes it to F-d7da32d44f8e.
2. If that dependency returns zero, it resolves the backend dispatch entry at `+0x18` and calls it with no explicit arguments.
3. It calls the object dispatch entry at `+0x2C`, passing the object, to obtain an element-size value.
4. It calls F-20810a394e6a with the destination and the product of the full count and that size.
5. It resolves the backend dispatch entry at `+0x04` and invokes it with the backend object, destination, position, and the low 16 bits of count.

The backend reference is obtained from the object as needed; the function does not establish that dependencies leave it unchanged. In particular, the backend observed before preparation need not be assumed identical to the one observed for the transfer.

The result of F-20810a394e6a is ignored.

#### Direct-result translation

A zero direct-transfer result produces a return value of zero after F-fd58bea73663 is called.

Nonzero results are translated as follows:

| Direct-transfer result | Additional behavior | Return |
|---|---|---|
| 3 | No status query | `0xFFFFFFE3` |
| 10 | No status query | `0xFFFFFFDF` |
| 8 | Query backend status bits | See below |
| Any other nonzero value | No status query | `0xFFFFFFF9` |

For result 8, the function invokes the backend dispatch entry at `+0x74` with no explicit arguments. The returned status word is interpreted with this precedence:

1. If bit `0x40` is set, return `0xFFFFFFF5`.
2. Otherwise, if bit `0x80` is set, return `0xFFFFFFF9`; bits `0x10` and `0x04` do not change that result.
3. Otherwise, if bit `0x10` is set, return `0xFFFFFFF6`.
4. Otherwise, if bit `0x04` is set, return `0xFFFFFFFE`.
5. Otherwise, return `0xFFFFFFF9`.

Before each ordinary return from the direct path, the function calls F-fd58bea73663 with the exact token captured before F-4a19e3742733. It does not reload the token from the object.

This pairing describes normal control flow only. Recovery from a dependency that faults, does not return, or performs a nonlocal exit is not shown.

### 5. Widths and arithmetic

The alignment test examines five bits of the 32-bit destination address.

The position advances in element units on the staged path. The destination advances by an element-count-times-size product.

The direct path preserves a significant width mismatch:

- The size-related dependency receives full accepted count multiplied by element size.
- The backend transfer receives count masked to 16 bits.

For example, an accepted count of 65,536 becomes a backend count of zero.

No explicit checks protect multiplication, position addition, or address addition from overflow. The supplied representation mixes signed 32-bit intermediate values with unsigned address and count values. Exact behavior on overflowing signed intermediates is documented_only; this contract does not assert portable signed wraparound. Acceptance examples involving arithmetic assume representable products and valid ranges unless stated otherwise.

## Side effects

The function directly reads object fields and dispatch-table entries. It contains no explicit stores to object fields.

Any writes to the destination, intermediate storage, object, globals, or synchronization state occur through dependencies. The apparent copy calls support the interpretation that destination memory is modified, but their exact behavior is not independently provided.

Observable call ordering is significant:

- Preliminary validation precedes either path.
- Staged transfers precede their associated copy-like calls.
- The final staged size query follows the final transfer.
- Direct-path preparation precedes the size-related call and backend transfer.
- Direct error translation precedes the matching synchronization-like completion call.

No explicit release operation is shown for the value returned by F-3cb5472b4a81. This is not evidence of either a leak or retained ownership: the dependency’s allocation and ownership semantics are unknown.

The intermediate-buffer value read through object offset `+0x08` is not explicitly freed, replaced, or cleared.

Unknown dependencies must not be assumed to preserve global state, object contents, dispatch tables, backend references, or memory ownership.

## Acceptance examples

These are conditional static acceptance cases, not runtime test results.

1. **Zero count with unusable object or destination.**  
   Given count zero, the function returns zero without dereferencing either value or calling dependencies.

2. **Signed-negative count pattern.**  
   Given count `0x80000000`, the function returns `0xFFFFFFF6` before preliminary validation, regardless of destination alignment.

3. **Preliminary nonzero result.**  
   Given positive count and a nonzero result from F-25748144b48d, the function returns zero without entering either transfer path.

4. **One unaligned element.**  
   Given an unaligned destination and count one, the bulk intermediate-storage dependency is not called. After the staged-path initialization, exactly one staged transfer is requested. The final size query and copy-like call still occur if that transfer returns a nonzero status. The wrapper returns that transfer status.

5. **Multiple unaligned elements with two errors.**  
   Given count four, element size eight, and stable usable intermediate storage, the bulk transfer requests three elements and its copy-like call receives size 24. The final transfer uses position increased by three and destination increased by 24. If the transfer statuses are `0x02` and `0x08`, the wrapper returns `0x0A`; neither copy-like call is suppressed.

6. **Changing staged element size.**  
   Given count two, a first size result of eight and final size result of sixteen, the destination advances by eight after the bulk portion, while the final copy-like call receives size sixteen. The wrapper does not reconcile the differing sizes.

7. **Direct backend count truncation.**  
   Given an aligned destination, count 65,536, size one, and safe arithmetic, F-20810a394e6a receives size 65,536 while the backend receives count zero. No separate range error is produced by this wrapper.

8. **Status precedence.**  
   Given direct result 8 and status `0xD4`, bit `0x40` wins and the return is `0xFFFFFFF5`. With status `0x94`, bit `0x80` suppresses the lower-priority interpretations and the return is `0xFFFFFFF9`. With status `0x14`, the return is `0xFFFFFFF6`.

9. **Token changes during direct work.**  
   If a dependency changes the object’s token field after its initial capture, the completion dependency still receives the originally captured token.
