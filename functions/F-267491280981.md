# F-267491280981

## Purpose

F-267491280981 performs an in-place relinking of a parent-linked, two-child structure. It promotes the node referenced by the second argument’s field at byte offset 8, moves the promoted node’s field at byte offset 12 into the vacated position, and reconnects the surrounding parent or root link.

The established behavior is a sequence of 32-bit memory reads and writes. Interpreting this operation as a binary-tree rotation is inferred intent. In particular, interpreting offset 8 as a left-child link and offset 12 as a right-child link makes this a right rotation. The supplied evidence does not establish those left/right labels, ordering invariants, balancing rules, or the larger data structure.

The function returns no value and reports no explicit success or failure status.

### Arguments

The function accepts two 32-bit integer-valued arguments that are used as addresses:

- **Container address:** Used to find an indirect root-link location.
- **Pivot address:** Identifies the node whose offset-8 link will be promoted.

The representation uses four-byte memory values for the relevant addresses and links. The evidence supports a 32-bit address-bearing representation; it does not establish host portability, byte order, or behavior when wider addresses are supplied through some external interface.

## Behavior

### Observable access sequence

The ordering below is part of the established behavior. It matters because several fields are read more than once and some writes precede the root-versus-parent decision.

1. **Select the promoted node.**  
   Read four bytes at pivot offset 8 and retain that value as the promoted-node address.

2. **Replace the pivot’s offset-8 child.**  
   Read four bytes at promoted-node offset 12, then write that value to pivot offset 8.

3. **Conditionally repair the transferred child’s parent.**  
   Read promoted-node offset 12 again and compare the value with zero.
   - If zero, perform no transferred-child parent write.
   - If nonzero, read promoted-node offset 12 once more and use that newly read address as the destination object. Write the pivot address to that object’s offset-4 field.

   The value copied into the pivot’s child field, the value tested for zero, and the address used for the parent write are therefore separate observations. They coincide under stable, ordinary memory, but the function does not take a single retained snapshot of this link.

4. **Give the promoted node the pivot’s current parent link.**  
   Read pivot offset 4 and write that four-byte value to promoted-node offset 4.

5. **Locate and inspect the root link.**  
   Read the anchor address from container offset 16. Read the four-byte link at anchor offset 4 and compare it with the pivot address.

6. **Reconnect the promoted node through the root or parent.**
   - If the inspected root link equals the pivot address, write the promoted-node address to that same root-link location.
   - Otherwise, read pivot offset 4 again to obtain the old-parent address. Read old-parent offset 12:
     - If that field equals the pivot address, write the promoted-node address to old-parent offset 12.
     - Otherwise, write the promoted-node address to old-parent offset 8.

   The fallback does not first verify that old-parent offset 8 contains the pivot.

7. **Attach the pivot beneath the promoted node.**  
   Write the pivot address to promoted-node offset 12.

8. **Finish the pivot’s parent link.**  
   Write the promoted-node address to pivot offset 4.

There are no explicit dependency calls in the supplied body.

### Result under stable, non-overlapping conditions

When the structure satisfies the stated preconditions and relevant memory does not change independently:

- The promoted node replaces the pivot at the root link or at the selected old-parent child link.
- The promoted node’s parent becomes the pivot’s former parent.
- The pivot becomes the promoted node’s offset-12 child.
- The pivot’s parent becomes the promoted node.
- The promoted node’s former offset-12 child becomes the pivot’s offset-8 child.
- If that transferred child is nonzero, its parent becomes the pivot.

The pivot’s offset-12 child and the promoted node’s offset-8 child are not directly modified. Neither the container’s anchor-address field nor the old parent’s unselected child field is directly modified.

These final-state statements assume distinct, non-overlapping fields. With aliasing, an explicitly targeted write can also change another named role, and subsequent reads follow the actual modified memory rather than a preserved conceptual structure.

### Root selection and malformed relationships

The root branch is selected solely by equality between the root-link value and the pivot address. It is not selected by a null parent, a sentinel parent, or another property of the pivot.

In the non-root branch, equality at old-parent offset 12 takes precedence. If both parent child fields contain the pivot, only offset 12 is replaced. If neither contains the pivot, offset 8 is nevertheless overwritten.

## Side effects

The function mutates existing storage in place.

On a successful ordinary path, it performs:

- One write to pivot offset 8.
- Zero or one write to a transferred child’s offset-4 parent field.
- One write to promoted-node offset 4.
- One write to either the anchor’s offset-4 link or one old-parent child field.
- One write to promoted-node offset 12.
- One write to pivot offset 4.

Thus the visible body contains five writes when the transferred-child condition is zero, or six when it is nonzero.
