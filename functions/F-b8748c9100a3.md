# F-b8748c9100a3

## Purpose

This contract describes a memory-effecting operation whose visible behavior consists of fourteen transfer windows, preparation of activation-local state, and a sequence of dependency calls. An application-level objective, object model, and successful completion condition are not established.

The central requirement is **preservation of value provenance and access order under possible aliasing**. A retained value is not interchangeable with a later acquisition from the same address. Publications, partial-width writes, and control-address replacements can affect subsequent acquisitions.

All established claims below concern the supplied static representation. They are conditional on meaningful execution of the represented accesses and arithmetic. Two byte payloads have no preceding definitions. The contract neither assigns them values nor guarantees a valid execution prefix under semantics in which their use invalidates execution.

No explicit result value is established. Physical argument placement, calling convention, caller visibility of argument-storage changes, and eventual return are **documented_only**.

### Memory and arithmetic model

Offsets are in bytes. A byte, halfword, or word access has width 8, 16, or 32 bits respectively. Offsets do not establish object boundaries or allocation sizes.

Address-bearing halfwords are signed 16-bit values promoted for address arithmetic. Character signedness is unresolved. A character used as an address base can therefore have different promoted values under different applicable character models.

The representation uses 32-bit integer arithmetic, including multiplication, doubling, and left shifts. No universal wrapping rule is established. Multiplication by two and left shift by one must not be treated as having identical validity conditions. Narrowing behavior, endianness, alignment, integer-to-address conversion, and arithmetic overflow semantics are **documented_only**.

Valid storage, accessible addresses, and valid arithmetic are preconditions, not conditions checked by this operation.

### Descriptive roles

The **control address** can be replaced during processing. Each transfer window also has a **selected address** and a **retained transfer word**.

Where acquired, **control metadata** means the word from control offset 0x44. The **displacement** is a signed halfword acquired at the address formed by adding control and the selected address. Some accesses use this displacement alone as an address base.

An **anchor** is established in window 4. An **earlier association** comes from that window’s selected offset 0x74; a **later association** comes from window 8’s selected offset 0x64. These roles imply neither ownership nor lifetime guarantees.

## Behavior

### Transfer and publication invariants

Every window has the following common constraints:

- The retained transfer is acquired from transfer-source offset 0x44 before control is published at control offset 0x54.
- The selected address comes from the window’s external word location after that publication.
- A second represented acquisition from the same external location supplies the word published at publication-destination offset 0x44.
- That publication precedes storage of the retained transfer at selected offset 0x14.
- The window’s initial control-byte write occurs after this transfer storage.

The two external value occurrences are distinct in the representation. Their equality is not required. This establishes neither volatility nor two guaranteed physical transactions.

Cross-window address relationships are:

| Window | Transfer-source base | Publication-destination base |
|---|---|---|
| 1 | Incoming source | Incoming destination |
| 2 | Window 1 selected address | Window 1 control metadata |
| 3–5 | Previous selected address | Previous fresh selected-offset-0x14 word |
| 6 | Window 5 selected address | Window 5 control metadata |
| 7 | Window 6 redirect | Window 6 control metadata |
| 8–10 | Previous selected address | Previous promoted character |
| 11 | Window 10 redirect | Window 10 control metadata |
| 12 | Window 11 redirect | Window 11 control metadata |
| 13–14 | Previous selected address | Previous control metadata |

“Fresh” identifies a later acquisition, not reuse of the value previously stored there. The incoming destination is not established to equal argument 1.

### Initial routing and anchor relationships

Window 1 acquires control metadata before its displacement. Its remaining byte destinations are selected offsets 0x01 and 0x0d, followed by metadata-address offset 0x09. Their respective payloads are the selected-address character conversion, the additional incoming byte, and the selected-address character conversion. These effects precede a halfword write of converted metadata at selected address plus displacement.

Windows 2–4 establish routing addresses through word acquisitions at **displacement offset 0x44**. Control is not added again to these addresses.

Their later control-byte payloads originate in word-width acquisitions:

| Window | Word source for later control byte |
|---|---|
| 2 | Argument-1 offset 0x64 |
| 3 | Previous routing-result offset 0x64 |
| 4 | Previous routing-result offset 0x64 |

Window 2 retains its displacement, routing result, and fresh selected-offset-0x14 word before acquiring its later byte source. Its concluding halfword uses that fresh selected word at selected address plus displacement.

Window 3 retains its later byte-source word before acquiring control metadata and displacement. Between displacement acquisition and routing acquisition, control is published at transfer-address offset 0x54, the retained byte is written at control offset 0x11, and the selected address is published at metadata-address offset 0x44, in that order. The routing acquisition and fresh selected-offset-0x14 acquisition separate this byte write from another write of the same retained byte. The fresh selected word supplies the concluding halfword at selected address plus displacement.

Window 4’s routing result becomes the anchor. Anchor establishment precedes acquisition of its fresh selected-offset-0x14 word and later byte-source word. After the later control-byte write, anchor offset 0x04 supplies a retained word before selected offset 0x74 supplies the earlier association. The retained anchor word is published at control offset 0x54.

Window 4 has a distinct concluding destination: selected address plus **twice the initial control address**, rather than selected address plus displacement. Its halfword payload is the fresh selected-offset-0x14 word converted to 16 bits.

### Control replacement and redirects

Window 5 retains an anchor-offset-0x64 word before acquiring control metadata and displacement. The earlier association is published at anchor offset 0x54 before a fresh selected-offset-0x14 word replaces control. Replacement-control offset 0x0d receives the selected-address conversion. The concluding halfword still uses the earlier metadata and displacement, at selected address plus displacement.

Window 6 similarly retains metadata and displacement before republishing the earlier association at anchor offset 0x54 and replacing control from a fresh selected-offset-0x14 word. Replacement-control offset 0x0d receives the selected-address conversion before transfer-address offset 0x14 supplies a redirect. The anchor is then published at earlier-association offset 0x54. The concluding halfword carries converted retained metadata at redirect plus retained displacement.

Replacement does not refresh retained operands. In particular, neither window’s concluding metadata comes from the replacement control.

### Character-dependent addresses and association updates

Windows 7–9 acquire their displacement before acquiring a character at displacement plus retained transfer. Each retained character supplies both the concluding halfword payload and the next window’s publication-destination base. Each concluding halfword targets selected address plus displacement.

Their additional effects are:

| Window | Established effects before the concluding halfword |
|---|---|
| 7 | Selected offset 0x1d receives the earlier-association character conversion. |
| 8 | A fresh anchor-offset-0x64 word is published at displacement offset 0x54; character-derived offset 0x0d receives a transfer conversion; selected offset 0x64 then supplies the later association. |
| 9 | Anchor offset 0x01 receives a selected-address conversion; selected offset 0x0d receives a transfer conversion; selected offset 0x44 receives the later association as a word; character-derived offset 0x0d receives a selected-address conversion. |

Window 9 also retains an anchor-offset-0x64 word before displacement and character acquisition. Its concluding halfword precedes window 10’s fresh transfer acquisition from selected offset 0x44. Consequently, that transfer need not equal the association previously published there.

### Later redirects and association publication

Window 10 acquires another anchor-offset-0x64 word before control metadata and displacement. Transfer-address offset 0x74 supplies its redirect before control is replaced from old-control offset 0x14. Metadata-address offset 0x0d receives the redirect conversion; the concluding halfword uses redirect plus displacement and converted retained metadata.

Window 11 acquires metadata before displacement. Transfer-address offset 0x15 then receives the selected-address conversion, and selected offset 0x44 receives the retained transfer. Metadata-address offset 0x74 supplies the next redirect after those writes. The concluding halfword again uses redirect plus displacement and converted metadata.

Windows 12 and 13 replace control from a word acquired at **displacement offset 0x14**. This address is not relative to old control or the selected address.

Both windows have the same post-replacement ordering constraints: metadata self-publication at metadata-address offset 0x54 precedes publication of the later association at selected address plus retained transfer. That publication precedes storage of metadata at selected offset 0x14. A fresh later-association-offset-0x44 word then supplies the byte at selected offset 0x0d, before replacement-control offset 0x0d receives a metadata conversion. The concluding halfword places converted metadata at selected address plus displacement.

Window 12 acquires an anchor-offset-0x64 word before metadata and displacement. Window 13 independently acquires another such anchor word at the corresponding point.

Window 13 has three additional effects between displacement acquisition and control replacement: control publication at transfer-address offset 0x54, an **unresolved byte** write at control offset 0x11, and selected-address publication at metadata-address offset 0x44. The later conversion used for window 14’s initial byte does not define this earlier unresolved payload.

### Product-dependent addressing

Window 14 retains control metadata before acquiring its signed displacement. In this window the displacement also acts as an arithmetic factor.

The product-dependent values have these relationships:

| Role | Derivation |
|---|---|
| Region address | Three chained word acquisitions, starting at factor-times-metadata offset 0x44, continuing at resulting-address offset 0x74, then resulting-address offset 0x14 |
| Saved address | Word from region offset 0x14 |
| Intermediate product | Factor multiplied by the word from saved-address offset 0x14 |
| Payload word | Word from intermediate-product offset 0x74 |
| Main base | Factor multiplied by the intermediate product |
| Further operand | Word from factor-times-main-base offset 0x44 |
| Final destination | Fresh word from anchor offset 0x14 |

Region offset 0x14 is read before being overwritten by control shifted left one bit. The saved address remains the basis of the subsequent multiplicand acquisition. The payload is not the multiplicand used to form the main base.

There are five word publications of the factor at factor-address offset 0x54:

- The first two precede region acquisition. A control-address byte conversion at selected offset 0x11 separates them; another such byte write follows the second.
- The third follows multiplicand acquisition and precedes a saved-address conversion at selected offset 0x11.
- The fourth follows payload acquisition and main-base formation, before a second **unresolved byte** is written at selected offset 0x11.
- The fifth follows the main-base byte update described below.

After the unresolved selected-byte write, a word is acquired at main-base offset 0x44, followed by a word at anchor offset 0x74. Selected offset 0x64 receives the payload word before selected offset 0x09 receives a conversion of the first main-base word.

A fresh main-base-offset-0x44 acquisition supplies the byte written at main-base offset 0x11. The selected-offset-0x09 write lies between the two acquisitions and can change the second value through overlap.

Following the fifth factor publication, twice-main-base offset 0x11 receives an 8-bit payload conversion. This does not define the earlier unresolved byte.

The further operand is acquired before the final destination. Payload-address offset 0x01 subsequently receives the retained anchor-offset-0x74 conversion. Final-destination offsets 0x11 and 0x09 then receive conversions of the further operand and twice the main base, respectively.

## Acceptance examples

These are conditional criteria, not executed tests. They assume valid storage, arithmetic, conversions, and applicable execution semantics.

1. **Retained transfer:** If control self-publication overlaps the transfer source, the transfer payload remains the word acquired before that publication.

2. **Independent acquisitions:** If a window’s external location yields different values at its two represented acquisitions, selection uses the first and publication uses the second.

3. **Width-sensitive source:** If argument-1 offset 0x64 contains 0x123456ab and narrowing retains the low eight bits, window 2 writes 0xab. Substituting a byte-width acquisition does not satisfy the established source-width relationship.

4. **Signed address contribution:** Halfword bits 0xffff contribute −1 as displacement. Character bits 0xff can contribute −1 or 255, depending on the unresolved character model.

5. **Displacement-only routing:** A displacement of 0x20 places the routing acquisition at address 0x64, not control plus 0x64.

6. **Exceptional destination:** Initial control 0x100 and window-4 selected address 0x2000 give a concluding destination of 0x2200, independently of that window’s displacement.

7. **Replacement provenance:** Window 5’s concluding halfword retains pre-replacement metadata and displacement even if replacement-control storage contains different values.

8. **Overlap-sensitive transfer:** A write overlapping window 9’s selected offset 0x44 before window 10’s acquisition can change the next transfer despite the earlier association publication.

9. **Product distinction:** Factor 3 and multiplicand 5 give intermediate product 15 and main base 45. The word at address 15 plus 0x74 supplies the payload; it does not replace 15 in the main-base calculation.

10. **Repeated-read sensitivity:** If selected offset 0x09 overlaps main-base offset 0x44, the two acquisitions from the latter address may differ.

11. **Prepared values:** Anchor 0x1234 yields two represented copies of 0x12340 and four of 0x123400 when the shifts are valid. Contiguous storage does not follow.

12. **Call boundary:** A returning F-unknown-01 may alter the external operand subsequently passed to F-cdec09f5d432. A non-returning call prevents subsequent represented effects from being reached.

13. **Undefined payloads:** Neither later byte definition establishes a value for its earlier unresolved use.
