# F-6b22f19305b0

## Purpose

F-6b22f19305b0 returns one byte while updating shared, byte-oriented state. A zero initialization marker selects a preparation path that obtains 256 external bytes, constructs and mixes a 256-entry table, and marks the captured state initialized. The function then performs an output-generating transition in the same invocation. A nonzero marker bypasses preparation and selects that transition directly.

The established behavior is a stateful byte generator. Its identity table, mixing exchanges, and output selection resemble an RC4-style construction. That resemblance is inferred intent, not evidence of compatibility, cryptographic security, randomness, or any particular provider quality.

The global state pointer is accessed more than once during entry and cold-state preparation. Stable-pointer execution selects one storage region throughout, but the source does not express all these accesses through a single captured pointer.

## Interface

### Explicit interface

The function takes no explicit arguments and returns a character-sized value representing one output byte.

All 256 byte patterns are possible return patterns. The evidence does not establish whether callers interpret patterns 128–255 as negative character values, or how the return value is extended by the target calling convention.

There is no separate success indicator, checked completion status, or reserved error byte.

### Implicit state and entry reads

The implicit input is a global pointer to state storage. The source-level entry sequence is:

1. Read the global pointer and retain that address as the captured state.
2. Separately read the global pointer again and read the initialization marker through that second pointer value.

The marker test does not explicitly dereference the captured pointer. When the global pointer remains stable, both reads select the same storage. If it changes between these reads, the marker can be read from storage different from the storage retained for later updates.

On the zero-marker path, the first state write also uses the global pointer directly: it clears offset 2 through another evaluation of that pointer. The following write clears offset 1 through the captured pointer. After this direct global-pointer clear, the remaining direct state accesses use the captured address.

These are source-level distinctions. The evidence does not establish exact machine-load counts or atomicity.

### State layout

Each storage region used for the full generator state has this layout:

| Byte offset | Width | Role |
|---|---:|---|
| 0 | 1 byte | Initialization marker |
| 1 | 1 byte | First generator index |
| 2 | 1 byte | Second generator index; also the initialization mixing accumulator |
| 3–258 | 256 bytes | Table entries numbered 0–255 |

The captured state requires at least 259 accessible bytes, writable for the duration of normal execution. The marker-test pointer must permit reading offset 0. On the cold path, the pointer used for the initial offset-2 clear must permit that write.

With a stable global pointer, these requirements apply to one region. Without stability, the accessed regions need not be identical.

A zero marker selects initialization. Every nonzero marker selects the existing-state path; a value other than one is not rejected or normalized on that path.

The function checks neither storage validity nor allocation size, ownership, exclusivity, or table contents.

### Widths and arithmetic

The state indices, provider bytes, table entries, and output are eight-bit quantities in the supplied representation. Index updates and table-selection sums retain their low eight bits.

Consequences include:

- Advancing an index of 255 produces zero.
- The mixing accumulator wraps modulo 256.
- Output-transition index addition wraps modulo 256.
- Every explicitly byte-reduced table index is between 0 and 255, selecting state offsets 3–258.

The two initialization traversals use integer counters that visit 0–255 and terminate when the incremented value reaches 256. Their control counters do not wrap at eight bits.

Exact native integer width and character signedness are not established. The byte-level description specifies the low-eight-bit behavior represented by the supplied source, not a portable character-language ABI.

## Behavior

### Entry and path selection

The function captures the global pointer before separately obtaining the pointer used to read the marker.

If the marker read through the second pointer is nonzero, the function skips both dependency calls, all table initialization, and the marker write. It performs one output transition on the captured state.

If that marker is zero, the function performs cold-state preparation and then one output transition on the captured state.

There is no second marker check. In particular, when the entry pointer reads select different regions:

- A nonzero marker in the marker-test region can bypass initialization even if the captured state’s marker is zero.
- A zero marker in the marker-test region can trigger initialization even if the captured state’s marker is nonzero.

No existing table is validated. A nonzero marker does not establish that the captured table is a permutation or that its indices were previously initialized.

### Cold-state clearing and external calls

On the zero-marker path, the following operations occur in order:

1. Write zero to offset 2 through the global pointer evaluated for that write.
2. Write zero to offset 1 through the captured pointer.
3. Call F-2e88c9fc2422 without explicit arguments.
4. Obtain an indirect call target from byte displacement 60 relative to the returned value.
5. Invoke that target with the returned value as its first argument, integer value 256 as its second argument, and the address of a local 256-byte destination as its third argument.

If the global pointer is stable through the initial clearing operations, both captured indices are zero before F-2e88c9fc2422 is called. If the pointer used for the offset-2 write differs from the captured pointer, that write need not clear the captured second index.

The local destination is not initialized by this function before the indirect call. The indirect operation’s return value is ignored. No byte count, status, retry, or fallback is checked.

Both external calls finish before table construction begins. Neither captured index is reset after those calls. Consequently, dependency modifications to the captured first or second index can affect initialization and generation.

After these calls, changing the global pointer does not redirect the remaining direct state accesses in this invocation. Those accesses use the previously captured address.

### Table construction

The function writes the identity table into the captured state in ascending order:

- Table entry 0 receives byte 0.
- Each following entry receives its own index.
- Table entry 255 receives byte 255.

These 256 writes overwrite any earlier dependency changes to the captured table. They do not restore the indices, undo changes to other memory, or restore the global pointer.

### Table mixing

Mixing makes exactly 256 visits, in ascending table-index order from 0 through 255. Each visit uses the corresponding byte from the local provider destination.

At each visit, the next accumulator is the low eight bits of the sum of:

- The current table value at the visited index.
- The provider byte at that same index.
- The current captured second-index byte.

The function writes the new accumulator to offset 2 before exchanging table entries. It then reads the accumulator-selected table entry, writes the visited entry’s value into the accumulator-selected entry, and writes the saved value into the visited entry.

Thus the exchange writes the accumulator-selected location first and the visited location second. If both indices are equal, the two writes address the same entry and preserve its value under stable, isolated execution.

The initial mixing accumulator is whatever the captured second-index byte contains when mixing starts. It is zero only if the earlier clear reached that storage and no dependency or other actor subsequently changed it.

With stable, isolated storage, the identity fill followed by these exchanges preserves a permutation of all 256 byte values.

The final mixing accumulator remains stored at offset 2. It is not reset before output generation.

After mixing completes, the function writes one to the captured state’s marker. It then immediately performs the ordinary output transition.

### Output-generating transition

Every normally completing invocation performs exactly one such transition.

First, the function reads the captured first index, adds one modulo 256, and writes the advanced index back to offset 1. It reads and retains the table value selected by that advanced index.

Next, it reads the captured second index and writes the low eight bits of the sum of that index and the retained table value back to offset 2.

The table exchange then has these observable data accesses:

1. Read the table entry selected by the byte-reduced sum of the previously read second index and retained table value.
2. Write that value into the table entry selected by the advanced first index.
3. Reread the stored second-index byte.
4. Write the retained table value into the entry selected by that reread index.

For isolated execution, the computed sum and the reread second index select the same entry. The exchange therefore swaps the entries selected by the updated first and second indices. Its first write is to the first-index-selected entry; its second write is to the second-index-selected entry.

If those indices coincide, both writes target the same entry and preserve its value.

Output selection follows the exchange:

- Reread the stored first-index byte.
- Read the table value selected by that byte.
- Add that value to the retained pre-exchange table value and reduce the sum to eight bits.
- Read and return the table byte selected by that sum.

Under isolated execution, this is equivalent to selecting the output by the sum of the two post-exchange entries at the updated indices. The explicit rereads mean the source does not establish a single atomic snapshot of the transition.

### Completion and abnormal execution

Successful completion leaves the updated indices and table in captured storage and returns one byte.

There is no explicit error handling or rollback. If a dependency does not return normally, the initial clearing writes have already occurred. If execution stops later, partial table construction, mixing, marker changes, or output-transition writes can remain.

Invalid pointers, an invalid indirect target, insufficient destination contents, or invalid state storage have no established fallback result.

## Side effects

### Direct state changes

On the existing-state path, the function writes:

- The captured first index.
- The captured second index.
- Two selected table locations, possibly the same location twice.

It does not directly write the marker on that path.

On the cold path, it additionally:

- Clears offset 2 through the global pointer used at that point.
- Clears captured offset 1.
- Fills all 256 captured table entries.
- Performs 256 mixing exchanges and accumulator writes.
- Writes one to the captured marker.
- Performs the output transition.

For stable pointers and dependencies that leave the captured indices untouched, a successful cold invocation ends with first index one. Its second index reflects both mixing and the subsequent output transition.

### Ownership and external effects

No explicit allocation, deallocation, release, or ownership transfer appears in this function. This does not imply that either dependency avoids those effects.

The provider destination has invocation-local lifetime. The function neither returns its address nor stores it in the generator state. Whether the indirect operation retains the address is unknown; no permission for later use is established.

The local provider bytes are not explicitly erased before return.

Dependency effects on globals, captured storage, unrelated storage, object lifetime, or memory ownership are unknown.

### Concurrency and reentrancy

No synchronization is visible. The pointer acquisition, marker test, initial clearing, mixing exchanges, and output exchange are separate operations.

Deterministic ordinary behavior requires valid, stable storage and absence of interfering writes during the relevant operations. Reentrant use of the same state is not shown to be safe. The external calls are not established to preserve globals or prevent reentrancy.

The separately expressed pointer reads identify distinct access paths; they do not establish defined behavior for otherwise unsupported concurrent mutation.
