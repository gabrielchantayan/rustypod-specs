# F-7464b1422118

## Purpose

F-7464b1422118 checks a caller-supplied value against information obtained through a context-associated identifier. It supports two distinct execution routes:

- An optional context-provided callback that receives all six inputs and bypasses the built-in processing.
- A built-in route that acquires a working handle, obtains data, and performs either a fixed-size comparison or a parsed type-and-content comparison.

The established behavior is not a simple Boolean predicate. Its 64-bit return value carries two independently constructed 32-bit words. Some paths that do not complete a comparison return the same word pair as a completed comparison failure would not: for example, a nonpositive data-processing result returns upper word 1 and lower word 0 without an explicit local error report.

The apparent intent is to check a typed signature or similar stored value. That interpretation is inferred from the comparison structure and diagnostic context; it is not needed to define the observable contract.

## Interface

### Inputs

The function accepts six machine-word arguments. The supplied representation uses 32-bit integers, pointers, and opaque words.

| Position | Contract name | Established use |
|---|---|---|
| 1 | Requested kind | A 32-bit value used for type matching, callback forwarding, and special-case selection. The value `0x72` selects the fixed-size route. |
| 2 | Expected value | An opaque 32-bit word forwarded to the callback and used as an address-like comparison operand by the built-in route. |
| 3 | Expected size | A signed 32-bit value used as a requested size, parsed-size comparison value, and comparison length. |
| 4 | Processing argument | A 32-bit value forwarded to the callback and to the data-processing dependency. Its broader meaning is unknown. |
| 5 | Expected identifier | A 32-bit value compared with the context-derived identifier, passed to acquisition and cleanup dependencies, and used as the callback route’s upper return word. |
| 6 | Context | An address-like 32-bit value used by the identifier dependency and for direct field reads. |

For readability, these contract names describe roles, not recovered source identifiers.

### Return representation

Treat the result as a 64-bit bit pattern with:

- **Lower word:** bits 0–31.
- **Upper word:** bits 32–63.

The word pair is more reliable than interpreting the result as a signed integer or a single success flag.

| Exit condition | Upper word | Lower word |
|---|---:|---:|
| Context identifier mismatch | 0 | 0 |
| Callback route | Expected identifier, unchanged as 32 bits | Callback’s 32-bit result |
| Acquired handle is zero | 0 | 0 |
| Requested kind is `0x72`, but expected size is not 36 | 0 | 0 |
| Data-processing result is zero or negative | 1 | 0 |
| Parser returns a null result | 1 | 0 |
| Fixed-size comparison matches | 1 | 1 |
| Fixed-size route has an unacceptable result size or comparison mismatch | 0 | 0 |
| Parsed kind, size, and content are accepted | 1 | 1 |
| Parsed kind, size, or content is rejected | 0 | 0 |

Dependencies may have additional side effects or failure conventions. The table describes the explicit local control flow when each invoked dependency returns normally.

### Memory preconditions

The function does not locally validate all addresses it uses. Defined completion requires suitable readable memory for every path actually taken:

- The context must support the context-derived identifier operation and the applicable direct field reads.
- If the callback-selection flag is set, the callback-table pointer and callback slot must be readable.
- A nonnull parsed result must expose the pointer layout described below.
- Comparison operands must satisfy the requirements of F-7f14f1ab6851 for the supplied length.

There is no established general null-input rejection, bounds check, or recovery from invalid memory.

## Behavior

### 1. Context identifier gate

The first dependency invocation is F-d7cb69444a05 with the context.

Its 32-bit result is compared with the expected identifier. A mismatch causes:

1. An invocation of F-4fc89ec41a6d with the two visible arguments `4` and `0x77`.
2. An immediate return with both result words zero.

This route performs no subsequent local callback-table read, acquisition, processing, parsing, or cleanup.

### 2. Optional callback dispatch

After the identifier matches, the function reads a 32-bit flags field at byte offset `0x3c` from the context.

If bit `0x40` is set, it:

1. Reads a pointer at context byte offset `8`.
2. Reads a callback pointer at byte offset `0x30` within that pointed-to object.

The table pointer is not locally checked for null before reading its callback slot.

If the callback-selection bit is set and the callback pointer is nonzero, the callback is invoked with all six original arguments in their original order. The function immediately returns the callback result as the lower 32-bit word and the original expected identifier as the upper 32-bit word.

No built-in acquisition, comparison, error reporting, or cleanup follows this callback invocation. Callback behavior, including ownership and global-state changes, is unknown.

If the flag is clear, the callback-table fields are not read by this local dispatch logic. If the flag is set but the callback slot is zero, processing continues through the built-in route.

### 3. Working-handle acquisition

The built-in route calls F-43da6b23bd44 with:

1. Expected identifier.
2. Zero.
3. Zero.

Its 32-bit result is retained as the original working handle.

If that handle is zero, the function reports an error through F-4fc89ec41a6d using the two visible arguments `4` and `0x77`. It then executes the normal final cleanup sequence, including passing the zero handle to both cleanup dependencies, and returns both words zero.

A nonzero handle enables further processing.

### 4. Fixed-size input restriction

For requested kind `0x72`, the expected size must equal `0x24`, or 36.

This check occurs **after** acquiring a nonzero handle and **before** invoking the data-processing dependency. If the expected size is not 36, the function reports the two-argument error and immediately returns zero in both words.

That immediate return bypasses both final cleanup calls. This is established local behavior. Whether it leaks or otherwise mishandles a resource cannot be determined without the acquisition dependency’s ownership contract.

Other requested kinds do not receive this local expected-size restriction.

### 5. Data processing

The function calls F-98fabf52a553 with six arguments, in this order:

1. Expected identifier.
2. Original processing argument.
3. Original working handle.
4. Context.
5. Constant `1`.
6. Original expected size.

The returned value is interpreted as a signed 32-bit quantity.

If it is less than 1, the function performs final cleanup and returns upper word 1, lower word 0. No explicit local error-reporting call occurs on this branch.

A positive result selects the next stage:

- Requested kind `0x72`: fixed-size comparison.
- Any other requested kind: parsing and typed comparison.

### 6. Fixed-size comparison

For kind `0x72`, the positive processing result must equal 36.

If it does, F-7f14f1ab6851 is invoked with:

1. Original working handle.
2. Expected value.
3. Length 36.

A zero comparison result is accepted and produces upper word 1, lower word 1 after final cleanup.

A nonzero comparison result is rejected. A positive processing result other than 36 is also rejected, without performing the comparison. Both rejection cases invoke F-4fc89ec41a6d with the two visible arguments `4` and `0x77`, then perform final cleanup and return both words zero.

The comparison operand order is significant: the working handle is first and the expected value second.

### 7. Parsing

For other requested kinds, the function initializes a local 32-bit cursor-like slot with the original working handle. It then calls F-86ceda4d173f with:

1. Zero.
2. The address of that local slot.
3. The positive processing result.

The parser can modify the slot through the supplied address. Subsequent final cleanup nevertheless uses the original working handle, not the slot’s potentially modified value.

A null parser result causes final cleanup and returns upper word 1, lower word 0. No local error report or parsed-result cleanup occurs on this path.

For a nonnull result, the directly accessed layout is:

| Location | Interpretation established by subsequent reads |
|---|---|
| Parsed-result offset 0 | A 32-bit pointer to an object whose first 32-bit word is passed to the kind-decoding dependency |
| Parsed-result offset 4 | A 32-bit pointer to a descriptor |
| Descriptor offset 0 | A 32-bit size value |
| Descriptor offset 8 | A 32-bit address-like value used as the content comparison operand |

No other descriptor fields are established by this function.

### 8. Parsed kind acceptance

The function reads the first word of the object referenced by the parsed result’s first pointer and passes that word to F-2eb743f270d1.

The returned 32-bit kind is accepted if it equals the requested kind.

Two unequal pairs are also accepted for continued checking:

- Requested kind 4 and decoded kind 8.
- Requested kind 3 and decoded kind 7.

For either exceptional pair, F-395ef1af5853 is invoked with a global diagnostic destination and a fixed signature-related warning message. Size and content checks happen afterward; the warning does not itself make the overall check succeed.

Any other kind mismatch invokes F-4fc89ec41a6d with the three visible arguments `4`, `0x77`, and decimal `100`. It then proceeds to parsed-result cleanup and final cleanup, returning both words zero.

### 9. Parsed size and content acceptance

After an accepted kind, the descriptor’s size word must equal the original expected size.

A size mismatch reports an error through F-4fc89ec41a6d with arguments `4`, `0x77`, and `0x68`. No content comparison is performed.

If the sizes match, F-7f14f1ab6851 is invoked with:

1. Expected value.
2. The descriptor’s word at byte offset 8.
3. Expected size.

This operand order is the reverse of the role ordering in the fixed-size route: the caller’s expected value is first.

A zero comparison result produces upper word 1, lower word 1. A nonzero result reports the same `0x68` error and produces both words zero.

The function does not independently reject zero or negative expected sizes on this parsed route. Whether such a size can reach comparison depends on the processing result and parsed descriptor. The comparison dependency’s interpretation of the length remains unknown.

### 10. Cleanup order

For every nonnull parsed result, F-22d7c8927afa is invoked with that result after kind, size, and content handling, including rejection paths.

Normal final cleanup then invokes:

1. F-80308ee0e93f with the original working handle and expected identifier.
2. F-5990a26eaaa3 with the original working handle.

The return value is produced afterward. Neither cleanup dependency’s return value is used.

## Side effects

Established local effects are dependency calls, reads of context and parsed-result memory, and initialization of a stack-local slot whose address is passed to the parser.

Important sequencing guarantees include:

- Identifier validation precedes callback selection and handle acquisition.
- Handle acquisition precedes the fixed-size expected-size restriction.
- The exceptional-kind warning precedes descriptor size and content reads.
- Parsed-result cleanup precedes both working-handle cleanup calls.
- Final cleanup uses the original acquired handle even if parsing changes its cursor slot.

No direct write to caller-owned memory is visible in the supplied body. Dependencies can write memory, change globals, report errors, or transfer ownership; their contracts are not supplied. In particular, the parser receives a writable local address, and the callback receives the original inputs without isolation.

The two cleanup-like dependencies and the parsed-result dependency are named by their observed call positions, not by a proven memory-release contract. Exactly-once local invocation on a path does not prove exactly-once resource release.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. All invoked dependencies are assumed to return normally, and all accessed memory is assumed valid.

1. **Identifier mismatch.** If the context-derived identifier differs from the expected identifier, the two-argument error call occurs and the result is `(upper 0, lower 0)`. No acquisition occurs.

2. **Callback selected.** If identifiers match, flag `0x40` is set, and the callback slot is nonzero, a callback result of `0xabcdef01` with expected identifier 9 produces `(upper 9, lower 0xabcdef01)`. No built-in cleanup follows.

3. **Zero acquired handle.** With no selected callback and acquisition returning zero, the error call is followed by F-80308ee0e93f with zero and the expected identifier, then F-5990a26eaaa3 with zero.

4. **Invalid fixed-size request.** Requested kind `0x72`, expected size 35, and a nonzero acquired handle cause immediate error and `(0, 0)`. Neither processing nor final cleanup occurs.

5. **Nonpositive processing result.** A processing result of zero or a negative signed 32-bit value produces `(1, 0)` after final cleanup, without a local comparison or local error report.

6. **Successful fixed-size comparison.** Kind `0x72`, expected size 36, processing result 36, and comparison result zero produce `(1, 1)` after final cleanup.

7. **Null parse result.** On a non-fixed-size route with a positive processing result, a null parser result produces `(1, 0)`. No parsed-result cleanup call occurs.

8. **Compatible kind with later rejection.** Requested kind 4 and decoded kind 8 emit the warning. If the descriptor size then differs from the expected size, error detail `0x68` is reported, both cleanup stages occur, and the result is `(0, 0)`.

9. **Unsupported kind mismatch.** Requested kind 4 and decoded kind 7 report error detail 100. Descriptor size and content are not checked. The parsed result and original handle still receive their respective cleanup calls.

10. **Successful parsed comparison.** An accepted kind, equal descriptor size, and zero comparison result produce `(1, 1)`, with parsed-result cleanup before working-handle cleanup.
