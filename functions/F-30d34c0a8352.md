# F-30d34c0a8352

## Purpose

F-30d34c0a8352 performs two consecutive, independently initialized descents through a linked structure. Each descent invokes F-3a00e7887b9d at every visited node, follows one of two links according to whether that dependency returns zero, and maintains an address-valued candidate. After both descents finish, it writes the two candidates to adjacent output slots.

The two descents differ in dependency argument order, branch selection, and candidate-update conditions. A candidate update records the **selected child address**, not the address of the node just examined. A selected null child can therefore replace a previously non-null candidate.

The structure resembles a sentinel-based binary search structure, but its ordering, balance, key representation, and abstract search operation are not established. This contract specifies the observable traversal and output behavior without assuming that the results represent bounds, matches, predecessors, or successors.

## Interface

| Input | Role established by the supplied representation |

These results are address-valued 32-bit words in the supplied representation. A result can be a header address, a node address, or zero. It is not necessarily the address of a node at which the dependency was called.

## Behavior

### First descent

Initialization has two distinct context-field reads:

1. Read the header reference at context offset `+0x10`, then read the root reference at offset `+0x04` of that header.
2. Read the header reference at context offset `+0x10` again and retain it as the first candidate.

The root and initial candidate therefore come from separately evaluated reads. With stable memory, they refer to the same header’s structure. The function does not explicitly capture one header reference for both purposes.

For each nonzero current node, invoke F-3a00e7887b9d with these five arguments, in order:

1. Context address plus `0x19`.
2. Current node address plus `0x10`.
3. Third input.
4. Fourth input.
5. Zero.

Only zero versus nonzero dependency return values matter:

- **Zero return:** Read the current node’s link at `+0x08`. Continue from that child and replace the first candidate with that same child address.
- **Nonzero return:** Read the current node’s link at `+0x0C`. Continue from that child without changing the first candidate.

The selected child link is read after the dependency returns. A dependency mutation to that link can therefore affect the next node and, on the zero-return branch, the candidate.

The descent ends when its current node becomes zero. There is no dependency call for a zero node.

Consequences include:

- If the initial root is zero, the first candidate remains the header reference obtained by the separate initialization read.
- If all dependency returns are nonzero, the first candidate remains its initial header reference.
- A zero-return branch selecting a null `+0x08` child sets the first candidate to zero.
- A nonzero candidate retained at termination need not be the last node visited.

### Second descent

After the first descent ends, the function initializes a new traversal from the context:

1. Read the header reference at context offset `+0x10`, then read that header’s root reference at `+0x04`.
2. Read the context’s header-reference field again and retain it as the second candidate.

Neither the root nor the header reference is reused from the first descent. Changes made during the first descent can affect the second descent’s starting state.

For each nonzero current node, invoke F-3a00e7887b9d with these arguments:

1. Context address plus `0x19`.
2. Third input.
3. Current node address plus `0x10`.
4. Fourth input.
5. Zero.

The second and third dependency arguments are reversed relative to the first descent.

Branch behavior is also different:

- **Zero return:** Read the current node’s link at `+0x0C` and continue from that child. Leave the second candidate unchanged.
- **Nonzero return:** Read the current node’s link at `+0x08`. Continue from that child and replace the second candidate with that same child address.

Again, the link read occurs after the dependency call. The descent ends at a zero current-node address.

Consequences include:

- An initially empty second descent leaves its candidate equal to its initialization-time header reference.
- If every dependency return is zero, the second candidate remains that header reference.
- A nonzero-return branch selecting a null `+0x08` child sets the second candidate to zero.
- Any nonzero return has the same branch effect; positive and negative results are not distinguished.

### Output publication

Only after both descents terminate does the function perform its explicit output stores:

1. Write the first candidate at output offset `+0x00`.
2. Write the second candidate at output offset `+0x04`.

There is no explicit output initialization before traversal, no per-node output update, and no failure status.

If traversal does not terminate or a dependency call does not return, the final stores are not reached. If the first output store succeeds and the second fails, the shown behavior provides no rollback or atomicity guarantee.

These are the source-level read, call, and write dependencies visible in the supplied representation, not a claim about instruction-level ordering or cross-thread synchronization.

## Side effects

The function’s own explicit memory writes are limited to the two output slots. Its traversal state and candidate values are otherwise maintained internally.

F-3a00e7887b9d is called once per visited nonzero node. Its side effects are unknown. In particular, this contract does not assume that it:

- Preserves the context’s header reference.
- Preserves roots or child links.
- Preserves node-associated data.
- Avoids modifying output storage or global state.
- Preserves object lifetime.
- Allocates or releases memory.
- Returns normally.

No direct allocation, release, reference-count adjustment, or ownership transfer appears in F-30d34c0a8352. Returning an address through an output slot does not by itself establish ownership or validity duration.

Output aliasing is not explicitly rejected. Because this function’s own stores occur after both descents, an output store cannot alter one of its earlier link reads. However, aliased output storage may overwrite context or structure fields at the end, and the dependency may modify aliased storage earlier. No general alias-safety guarantee is established.

There is no cycle detection or traversal bound. A cycle, dependency-driven rewiring, or repeated selection of non-null nodes can prevent completion.

## Acceptance examples

These examples are conditional requirements derived from the supplied static behavior. They are not runtime results.

Unless stated otherwise, assume stable accessible storage, a nonzero header address **H**, normal dependency returns, and no dependency side effects.

### Empty structure

If the header’s root is zero during both initializations:

- Neither descent calls the dependency.
- Both candidates remain **H**.
- The output is **(H, H)**, written first slot before second.

An empty root therefore does not inherently produce two zero results.

### Single node with zero returns

Let the root be node **A**, with both child links zero. Suppose the dependency returns zero in each descent.

- First descent follows **A**’s `+0x08` link and replaces its candidate with zero.
- Second descent follows **A**’s `+0x0C` link and retains **H**.
- Output: **(0, H)**.

### Single node with nonzero returns

Use the same structure, but let both dependency calls return any nonzero value.

- First descent follows the null `+0x0C` link and retains **H**.
- Second descent follows the null `+0x08` link and replaces its candidate with zero.
- Output: **(H, 0)**.

### Retaining a child candidate

Let **A**’s `+0x08` child be **B**, and let **B**’s `+0x0C` child be zero.

For the first descent, suppose the call at **A** returns zero and the call at **B** returns nonzero.

- The first transition records **B** as the candidate.
- The second transition terminates through the null `+0x0C` child without updating the candidate.
- The first output is **B**.

This distinguishes recording a selected child from recording the node whose call triggered the update.

### Replacing a candidate with zero

Let **A**’s `+0x08` child be **B**, and let **B**’s `+0x08` child be zero. If the first descent receives zero at both nodes:

- Its candidate first becomes **B**.
- Its candidate then becomes zero.
- Its final result is zero, not **A**, **B**, or **H**.

The second descent has the same candidate-replacement pattern when both returns are nonzero.

### Argument-order-sensitive results

At a node **A**, the first descent passes **A** plus `0x10` before the third input. The second descent passes the third input before **A** plus `0x10`.

Acceptance must permit different dependency results for those calls. Neither result can be inferred from the other without a separate dependency contract.

### Dependency mutation before link selection

Suppose a dependency call changes the current node’s `+0x08` link from **B** to **C** and then returns zero during the first descent.

The subsequent link read selects **C**, and the first candidate becomes **C**. Using a pre-call cached value of **B** would not match the shown ordering.

### Changed header between descents

Suppose the first descent’s dependency activity changes the context’s header reference from **H** to another valid header **J**. If **J** has a zero root and remains stable during second-descent initialization:

- The second descent performs no dependency calls.
- Its result is **J**.
- It does not reuse **H** or the first descent’s root.
