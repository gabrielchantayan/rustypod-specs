# F-82b71a47b6b5

## Purpose

F-82b71a47b6b5 performs two successive, comparison-directed traversals of a linked structure and writes two 32-bit address-like results to caller-provided storage.

Both traversals begin from a root reached through a structure header. They use the same dependency, F-685cd10e4a2e, but reverse the order of its second and third arguments. Each traversal maintains a result initialized to the header address. On selected branches, that result is replaced by the address of the child just entered—not by the address of the node whose payload was compared.

The layout and paired traversals suggest an ordered-tree search. That interpretation is inferred intent, not an established contract for ordering, bounds, equality, or ranges. In particular, the visible result updates do not justify describing the outputs as conventional lower-bound or upper-bound iterators.

## Interface

### Inputs

The function accepts three inputs:

1. **Output storage address.** An address at which two consecutive 32-bit result words will be written.
2. **Structure base address.** An address used to locate the header pointer and to derive the first argument passed to F-685cd10e4a2e.
3. **Query word.** An opaque 32-bit value forwarded unchanged to F-685cd10e4a2e.

The query word is not directly dereferenced or interpreted by this function. Whether it represents an address, scalar value, handle, or another encoding is unknown.

### Visible layout

The structure address at +0x19 and node address at +0x10 are formed without a direct read of the pointed-to data by this function. Their required readable or writable extents depend on F-685cd10e4a2e.

### Widths and return behavior

The visible words, link values, saved results, and dependency result are 32 bits. The function treats zero link values as traversal termination.

Only zero versus nonzero matters for the dependency result. There is no visible distinction between positive and negative nonzero results.

The function has no explicit return value. Its direct outputs are the two stores to output storage, together with any effects of dependency calls.

## Behavior

### First traversal initialization

The function first reads the header address from structure offset +0x10, then reads the root address from that header’s offset +0x04.

It subsequently reads the header address from structure offset +0x10 again and saves this second value as the first traversal result.

These are distinct structure-field reads. The visible sequence does not obtain the root and initial saved result from one retained header value. In ordinary stable storage they agree; concurrent or externally induced changes are not constrained by the supplied body.

If the root is zero, the first traversal makes no dependency calls. Its result remains the header value obtained by the second structure-field read.

### First traversal steps

For each nonzero current node, the function calls F-685cd10e4a2e with these arguments, in order:

1. Structure base address plus 0x19.
2. Current node address plus 0x10.
3. The unchanged query word.

After the dependency returns:

- **Zero result:** read link A from the current node, enter that child, and replace the saved first result with the child address just read.
- **Nonzero result:** read link B from the current node and enter that child, leaving the saved first result unchanged.

The selected child field is read after the dependency returns. If the dependency changes that field, the traversal uses the value subsequently read, not a pre-call snapshot.

A zero selected child terminates the traversal at its next loop condition. In particular, taking the zero-result branch when link A is zero explicitly sets the saved first result to zero.

The node payload is supplied by address. The visible body does not copy it into local storage before calling the dependency.

### Second traversal initialization

Only after the first traversal ends does the function initialize the second traversal.

It again reads the header address from structure offset +0x10 and then the root address at header offset +0x04. It separately rereads the structure’s header field and saves that value as the second traversal result.

The second traversal therefore does not reuse the first traversal’s root or initial header snapshot. Changes caused by earlier dependency calls can affect the second traversal’s starting state.

If this newly read root is zero, the second traversal makes no dependency calls and retains its initialized result.

### Second traversal steps

For each nonzero current node, the function calls F-685cd10e4a2e with:

1. Structure base address plus 0x19.
2. The unchanged query word.
3. Current node address plus 0x10.

The query and payload argument positions are reversed relative to the first traversal.

After the dependency returns:

- **Zero result:** read link B and enter that child, leaving the saved second result unchanged.
- **Nonzero result:** read link A, enter that child, and replace the saved second result with the child address just read.

Again, the selected child field is read after the call. Taking the nonzero-result branch with a zero link A sets the saved second result to zero.

There is no established relationship between the dependency’s results for the two argument orders. Antisymmetry, strict ordering, equality behavior, purity, and determinism are not established.

### Completion and result selection

After both traversals finish, the function writes:

1. The saved first result to output offset +0x00.
2. The saved second result to output offset +0x04.

Neither output word is written before the second traversal finishes. The stores occur in the stated order; they are not presented as an atomic pair.

For a normally terminating traversal:

- The first result is the last link-A child address read on a **zero** dependency result during the first traversal, or its initialized header value if no such branch occurred.
- The second result is the last link-A child address read on a **nonzero** dependency result during the second traversal, or its initialized header value if no such branch occurred.

Any result-update branch replaces the earlier saved value completely. A later update to zero is not prevented by an earlier nonzero candidate.

## Acceptance examples

These examples are conditional static scenarios, not executed tests. Unless stated otherwise, assume stable memory, normal dependency returns, valid accesses, and no dependency-induced mutations.

### Empty structure

The structure’s header field identifies header H, and H’s root field is zero.

Both traversals skip their dependency calls. The output is H in the first word and H in the second word.

The function still performs both traversal initializations before writing either output word.

### Single node with zero-result calls

The root is node N, both links of N are zero, and both dependency calls return zero.

- The first traversal reads link A, saves zero, and terminates.
- The second traversal reads link B and terminates without replacing its initialized header result.

The output is zero followed by H.

### Single node with nonzero-result calls

The root is N, both links are zero, and both dependency calls return nonzero.

- The first traversal follows link B without changing its saved result.
- The second traversal follows link A and saves zero.

The output is H followed by zero.

A negative nonzero result has the same branch effect as a positive nonzero result.

### A saved result need not be the final visited node

During the first traversal, suppose a zero result at node N selects a nonzero link-A child M. The saved first result becomes M.

If a later nonzero result at M selects a zero link B, the traversal terminates with M still saved. The update at N stored its child M, not N.

The analogous second-traversal case uses a nonzero result to select and save M, followed by a zero result at M selecting a zero link B.

### A terminal update can erase a previous candidate

During the first traversal, suppose an earlier zero-result branch saved nonzero child M. If a subsequent zero-result branch reads zero from link A, the final first result becomes zero.

For the second traversal, the same replacement occurs on a subsequent nonzero-result branch reading a zero link A.

### Mutation between traversals

Suppose a first-traversal dependency call changes the structure’s header field to another valid header H2 before the first traversal ends, and that field remains H2.

The second traversal reads its root through H2 and initializes its result from H2. It does not restart using the original header merely because the first traversal used it.

### Mutation during a comparison

Suppose a dependency call changes the current node’s selected child link and returns normally, leaving that field valid.

The next traversal step uses the changed child value because the link read follows the call. No earlier child snapshot is visible.
