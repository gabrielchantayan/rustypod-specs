# F-739b66c266c2

## Purpose

F-739b66c266c2 advances a cursor over one token-like unit in a byte-oriented input range. Its directly implemented behavior distinguishes single-byte structural delimiters, doubled angle delimiters, slash-prefixed names, ordinary tokens, and angle-bracketed hexadecimal content. Parenthesized content and initial input skipping are delegated to dependencies.

The routine reports selected malformed input by invoking a diagnostic dependency and assigning the 32-bit value 3 to a state field. It has no explicit return value.

The apparent intent is token skipping for a PostScript-like syntax. That interpretation is inferred from the recognized characters and diagnostic descriptions; it is not a guarantee of complete language conformance. In particular, the visible handling of exhausted hexadecimal input does not consistently report a missing closing delimiter.

## Interface

### Inputs

The routine accepts three arguments:

1. **State-record address.** The visible representation uses 32-bit slots:
   - Byte offset 0: current input cursor, represented in a 32-bit slot.
   - Byte offset 4: an uninterpreted slot not directly accessed.
   - Byte offset 8: input-limit address, represented in a 32-bit slot.
   - Byte offset 12: status/error field, written with the 32-bit value 3 on specified error paths.

   The input limit is treated as an exclusive upper bound: a cursor at the limit is not dereferenced by the routine’s own guarded input reads.

2. **An uninterpreted 32-bit argument.** The visible body neither reads nor forwards its value.

3. **A byte-pointer argument.** Its value is initially copied to temporary storage but is not dereferenced or used to determine observable behavior. The only path that subsequently uses that temporary storage replaces its value first.

The representation establishes 32-bit record slots. The correspondence between those slots and native pointer values depends on the original execution environment; portability to a different pointer width is not established.

### Outputs

There is no explicit return value. Results are communicated through:

- A final write to the state record’s current-cursor slot.
- A possible earlier cursor write during hexadecimal-content processing.
- A possible assignment of 3 to the status field.
- Calls to dependencies, including a diagnostic dependency.

The routine does not directly produce a token object, token length, decoded string, or decoded hexadecimal bytes.

### Preconditions and validity limits

For defined, meaningful use:

- The state record must permit the indicated 32-bit reads and writes.
- Cursor and limit addresses must support the comparisons and address arithmetic performed by the routine.
- Every byte directly read must be accessible.
- Dependencies must accept the temporary cursor-address and limit arguments supplied to them.
- Any cursor movement performed by dependencies must leave subsequent direct reads valid.

The routine does not validate these conditions. It also contains a path that advances one byte beyond an exhausted limit; callers must not assume that its resulting cursor always remains within the original input range.

No non-aliasing guarantee is visible. If input storage overlaps the state record, direct state writes can affect subsequent input reads. Conventional use with a separate state record and input buffer avoids that interaction.

## Behavior

### Entry and initial dependency call

The routine first reads the current cursor from state offset 0, then reads the limit from offset 8. It invokes F-1fe3b1afff2c with:

- The address of temporary cursor storage.
- The captured limit.

Subsequent classification uses the cursor left in that temporary storage.

The routine does not reread the state record’s cursor after this call. Except for the hexadecimal path described below, it also continues using the previously captured limit rather than rereading offset 8.

If the resulting cursor is at or beyond that limit, the routine performs no direct input-byte read. It writes that cursor to state offset 0 and returns. It does not clamp the cursor to the limit.

The name and implementation of F-1fe3b1afff2c are unavailable as behavioral evidence. Its role as a whitespace or comment skipper is plausible but not established here.

### Single-byte structural delimiters

If the first classified byte is one of:

- `[` — hexadecimal 5B
- `]` — hexadecimal 5D
- `{` — hexadecimal 7B
- `}` — hexadecimal 7D

the routine advances the cursor by one byte and commits it to the state record.

It does not inspect matching delimiters, nesting, or surrounding syntax on these paths.

### Parenthesized content

If the classified byte is `(`, hexadecimal 28, the routine calls F-03e9c84a7328 with the address of its temporary cursor and the captured limit.

After that call, it commits the resulting cursor without further direct validation. Its own body does not:

- Search for a closing parenthesis.
- Interpret escapes.
- Track nesting.
- Assign an error specifically for this branch.

Any such behavior belongs to the dependency and remains unknown.

### Opening angle bracket

If the classified byte is `<`, hexadecimal 3C, the routine first tests whether a following byte is still below the captured limit.

If that following byte is also `<`, it advances by two bytes and commits the result. The pair `<<` is therefore consumed as a unit without scanning its contents.

Otherwise, it enters the hexadecimal-content path.

#### Hexadecimal-content path

This path first writes the address of the opening `<` to state offset 0. This is an observable intermediate state write, distinct from the final cursor commit.

It then initializes a separate scan cursor to the opening delimiter and rereads the limit from state offset 8. This reread occurs after the intermediate cursor write. The newly read limit governs this scan and is subsequently retained across its dependency calls.

Each scan iteration:

- Advances the scan cursor by one byte.
- Stops immediately if the advanced cursor is at or beyond the scan limit.
- Otherwise invokes F-1fe3b1afff2c with the scan cursor by reference and the scan limit.
- Stops if the resulting cursor is at or beyond that limit.
- Otherwise reads the byte at that cursor and determines whether it is an ASCII hexadecimal digit.

Recognized hexadecimal digits are exactly:

- `0` through `9`
- `A` through `F`
- `a` through `f`

The digit classification uses unsigned 32-bit arithmetic. A byte is zero-extended before subtraction; values below a tested lower bound wrap in the unsigned domain and fail that range test. There is no locale-dependent classification, sign extension, digit decoding, or enforcement of an even digit count.

A recognized digit causes another iteration. A non-digit ends the scan at that byte.

After scanning:

- If the cursor is below the scan limit and points to `>`, hexadecimal 3E, the routine commits the address immediately after that byte.
- If the cursor is below the scan limit and points to any other byte, it invokes F-4457a9a44a68 with a diagnostic describing a missing closing delimiter. It then writes 3 to the status field and commits the offending byte’s address. The offending byte is not consumed.
- If the cursor is at or beyond the scan limit, the routine does not issue this diagnostic or directly assign 3. Instead, it commits one byte beyond the scan cursor.

The last case is an important established behavior, not a proposed interpretation: exhaustion follows the same final cursor advancement as successful closing-delimiter recognition. If scanning stops exactly at the limit, the resulting cursor is one byte beyond the limit, assuming that address arithmetic is representable.

### Closing angle bracket

If the classified byte is `>`, the routine advances once and checks the next position.

- If that position is below the captured limit and contains another `>`, it advances once more and commits the cursor after `>>`.
- Otherwise, it invokes F-4457a9a44a68 with an unexpected-closing-angle diagnostic, writes 3 to the status field, and commits the position immediately after the first `>`.

For a single `>` at the end of the range, the committed cursor is the limit. For `>X`, the error leaves the cursor at `X`; that byte is not consumed.

### Slash-prefixed and ordinary tokens

A leading `/`, hexadecimal 2F, is consumed before the shared scanning loop checks the next byte.

For other bytes not already handled, scanning begins at the classified byte itself.

The shared scanner stops at the limit or at any of these bytes:

| Category | Bytes |
|---|---|
| Whitespace-like separators | space 20, carriage return 0D, line feed 0A, tab 09, form feed 0C, NUL 00 |
| Delimiters | `/`, `(`, `<`, `>`, `[`, `]`, `{`, `}`, `%` |

These stopping bytes are not consumed by this scanner. Percent therefore stops ordinary-token scanning, but comment consumption is not directly implemented here.

A right parenthesis `)`, hexadecimal 29, is handled separately. Encountering it during shared scanning invokes F-4457a9a44a68 with an unexpected-right-parenthesis diagnostic, writes 3 to the status field, and commits the cursor at that right parenthesis. It remains unconsumed.

All other bytes advance the scan by one byte, including byte values above hexadecimal 7F and control bytes not explicitly listed.

Consequences include:

- A slash-prefixed token consumes its initial slash but stops before a subsequent slash.
- An ordinary token ending at a right parenthesis reports an error during the same invocation, rather than merely stopping normally.
- If the initial dependency leaves the cursor at a non-consuming separator such as `%`, this routine can return without advancing it.
- There is no general forward-progress guarantee.

### Final commit

All visible returning paths converge on a write of the selected cursor to state offset 0.

There is no unconditional status initialization. Successful paths do not directly clear a pre-existing error value.

## Side effects

### Direct state effects

The routine directly:

- Reads state offsets 0 and 8 on entry.
- Writes state offset 0 before scanning single-angle hexadecimal content.
- Rereads state offset 8 on that path.
- Writes state offset 12 with the 32-bit value 3 after each diagnostic call made by this routine.
- Writes state offset 0 on every visible return.

It does not directly access the slot at offset 4 or write the limit slot.

The status assignment follows the diagnostic call, and the final cursor write follows that assignment. A diagnostic dependency can therefore observe state before this routine’s error value and final cursor are installed. In the hexadecimal error case, it can observe the earlier cursor write at the opening `<`.

### Input and ownership

The visible body performs byte reads but no direct writes through an input cursor. It does not directly allocate, release, or transfer ownership of memory.

Dependencies may have additional effects. Their ownership behavior, global-state effects, and ability to modify aliased state are unknown. They must not be assumed to preserve state-record fields, preserve globals, or leave memory ownership unchanged.

The routine itself does not provide rollback if a dependency changes state.

## Acceptance examples

These are conditional static acceptance examples, not runtime test results. Unless specified otherwise:

- Input and state storage do not overlap.
- The limit is immediately after the displayed input.
- F-1fe3b1afff2c returns the supplied cursor unchanged.
- Diagnostic calls return without additional relevant state changes.
- Address arithmetic is valid.

1. **Empty range.** With cursor equal to limit, the routine invokes F-1fe3b1afff2c, performs no direct input-byte read, and commits the returned cursor. It makes no direct status assignment.

2. **Single structural delimiter.** For `[abc`, it consumes only `[`. The final cursor points to `a`.

3. **Doubled opening angle.** For `<<abc`, it consumes exactly `<<`. It does not inspect `a` as hexadecimal content.

4. **Valid hexadecimal content.** For `<0aF>rest`, it commits the cursor at `r` without directly assigning an error.

5. **Empty hexadecimal content.** For `<>x`, it consumes `<>` and leaves the cursor at `x`.

6. **Odd hexadecimal count.** For `<A>`, it consumes the complete input without an odd-digit-count error. No even-count requirement is visible.

7. **Invalid hexadecimal byte.** For `<0G>`, it reports the missing-closing-delimiter category, writes status 3, and leaves the cursor at `G`.

8. **Exhausted hexadecimal content.** For `<AB`, it reaches the limit without a closing `>`, performs no direct error assignment, and commits a cursor one byte beyond the limit.

9. **Opening angle alone.** For `<`, it likewise commits one byte beyond the limit without this routine issuing a diagnostic.

10. **Whitespace depends on the dependency.** For `<A B>`, an unchanged-cursor F-1fe3b1afff2c causes an error at the space. If that dependency instead moves the cursor from the space to `B`, scanning can continue and consume the closing `>`.

11. **Doubled closing angle.** For `>>x`, it consumes `>>` and leaves the cursor at `x`.

12. **Single closing angle.** For `>x`, it reports an unexpected closing angle, writes status 3, and leaves the cursor at `x`.

13. **Ordinary token.** For `abc def`, it leaves the cursor at the space without consuming it.

14. **Slash-prefixed token.** For `/name/next`, it consumes `/name` and leaves the cursor at the second slash. For `//`, it consumes only the first slash.

15. **Unexpected right parenthesis.** For `abc)`, it reports an unexpected right parenthesis, writes status 3, and leaves the cursor at `)`.

16. **Delegated parenthesized content.** For input beginning with `(`, if F-03e9c84a7328 returns a particular cursor, that cursor is committed without additional validation by this routine.

17. **Existing status survives direct success.** If status initially contains 3 and input is `[`, the routine does not directly clear it. Its final value still depends on any dependency side effects.
