# F-ffb5c1023f20

## Purpose

F-ffb5c1023f20 validates a byte-oriented block and, if its checks pass, invokes an external dependency with a pointer to the remaining payload and its computed length. After that dependency returns normally, the function returns the payload length.

Recognized rejection paths invoke F-4fc89ec41a6d with a numeric reason and then return −1.

For ordinary, defined arithmetic and stable readable memory, the accepted block contains, in order:

- An initial byte equal to `0x01`.
- At least eight consecutive `0xFF` padding bytes.
- A `0x00` separator.
- Zero or more payload bytes, with their computed length no greater than the second argument.

Before examining the block, the function also requires the fifth argument’s pointer value to match a pointer-shaped value derived from the fourth argument plus one.

**Inferred intent:** the byte structure resembles type-1 padding. The supplied evidence does not establish a protocol, a cryptographic operation, or a caller-level security guarantee. The external acceptance call suggests a transfer operation, but its implementation is unavailable.

## Interface

The function takes five positional arguments and returns a signed integer.

| Position | Role established by the supplied body |
|---|---|
| First | An opaque 32-bit word passed unchanged to the acceptance dependency. |
| Second | A signed integer upper limit for the computed payload length. |
| Third | A pointer to the candidate block’s first byte. |
| Fourth | A signed integer extent used in the initial comparison, scan bound, and payload-length calculation. |
| Fifth | A byte-pointer-typed value used in the initial pointer-value comparison. Its incoming value is never dereferenced. |

The supplied representation explicitly identifies the first argument as a four-byte word and the input elements as bytes. This contract treats bytes as eight bits and uses the apparent signed 32-bit integer model when discussing numerical boundaries. The complete ABI, pointer width, integer-to-pointer conversion rules, and overflow behavior are not independently established.

The following terms describe the behavior:

- **Extent:** the fourth argument.
- **Scan bound:** extent minus one, evaluated only after both the initial comparison and the first-byte check succeed.
- **Padding count:** the number of consecutive `0xFF` bytes traversed after the initial byte.
- **Payload length:** the scan bound minus the sum of the padding count and one. For defined arithmetic on an accepted layout, this equals extent minus padding count minus two.

The fifth argument does not identify a second buffer to scan. After its value passes the initial comparison, traversal is based on the third argument.

### Results

- **Accepted block:** returns the computed payload length after F-external-01 returns normally.
- **Recognized rejection:** returns −1 after F-4fc89ec41a6d returns normally.

Neither dependency’s return value is inspected. Failure to return normally prevents the corresponding normal result.

### Path-dependent preconditions

The obligations below apply only when execution reaches the relevant operation:

1. **On every path**, extent plus one must have a defined result under the applicable arithmetic model, and its conversion to the pointer-shaped comparison value must be meaningful.
2. **Only if the initial pointer-value comparison succeeds**, the third argument must permit the first-byte read and formation of the address one byte beyond it.
3. **Only if that comparison succeeds and the first byte equals `0x01`**, extent minus one must have a defined result.
4. **Only when the resulting scan bound is positive**, the addresses actually examined by the scan must be readable, and the performed pointer advances must be valid.
5. **Only on the acceptance path**, the payload-length arithmetic and the external dependency’s argument requirements must hold.

In particular, extent minus one is not evaluated on an initial comparison failure or a wrong-first-byte rejection. Its arithmetic precondition must not be imposed on those paths.

The function contains no explicit null-pointer check, allocation-size check, or independent verification that the candidate storage covers the supplied extent.

## Behavior

### Initial pointer-value comparison

The first operation relevant to acceptance derives a pointer-shaped value from extent plus one and compares it with the incoming fifth argument.

If those values differ, the function selects rejection reason `0x6A`. It does not read the block, form the traversal address from the third argument, or compute extent minus one.

If they match, the function reads the byte at the third argument and forms a traversal address one byte beyond that address. It then checks whether the first byte represents `0x01`.

A first byte other than `0x01` also selects reason `0x6A`. This path performs no scan and does not compute extent minus one. The traversal-address formation has already occurred.

The observed byte is converted through an unsigned integer to a pointer-shaped value for the comparison. Describing the condition as “first byte equals `0x01`” uses the ordinary target interpretation evident in the supplied representation; unusual conversion behavior remains outside the established ABI evidence.

### Bounded padding scan

Only after both initial checks pass does the function compute extent minus one and initialize the padding count to zero.

When the scan bound is positive, the function examines successive byte positions starting immediately after the initial byte:

- A byte equal to `0xFF` extends the padding run. Traversal advances by one byte, and the padding count increases by one.
- A byte equal to `0x00` ends the scan. Traversal advances past the separator, while the padding count remains the number of preceding `0xFF` bytes.
- A byte equal to neither value causes immediate rejection with reason `0x66`.

The scan examines no more positions than the scan bound permits. Under an ordinary positive extent, the last permitted position is the final byte within that extent.

An unexpected nonzero byte takes precedence over the minimum-padding check. For example, three padding bytes followed by `0x7E` produce `0x66`, not `0x67`.

After the scan:

1. If the padding count equals the scan bound, the function rejects with `0x71`. For a positive bound, this means every permitted scan position contained `0xFF`; no separator was found.
2. Otherwise, if the padding count is less than eight, the function rejects with `0x67`.
3. Otherwise, it proceeds to the payload-length check.

A separator in the final permitted position is not scan exhaustion: it is examined while the padding count is still below the bound. Such a separator can yield an accepted empty payload.

### Payload-length calculation and limit

After a separator following at least eight padding bytes, the function computes the payload length by subtracting the padding count plus one from the scan bound.

For a valid ordinary layout:

**Payload length = extent − padding count − 2**

The two fixed bytes are the initial `0x01` and the separator. The calculation uses the declared extent, not a separate measurement of accessible payload storage.

The function compares the computed length with the second argument using a signed comparison:

- A length greater than the limit selects reason `0x6D`.
- A length less than or equal to the limit proceeds to the acceptance dependency.

There is no separate requirement that the limit be nonnegative. On ordinary accepted layouts the payload length is nonnegative, so a negative limit rejects even an empty payload.

The function does not inspect payload contents and does not require a positive payload length.

### Acceptance call

|---|---|

| Second | The traversal pointer immediately after the separator |
| Third | The computed payload length |
| Fourth | The scan bound |
| Fifth | The original extent |

The function then returns the computed payload length if the dependency returns normally. It does not condition that result on the dependency’s return value.

This establishes invocation with the specified arguments, not successful copying or delivery. The dependency’s actual operation is unresolved.

### Zero and negative scan bounds

These cases are reached only after the initial comparison succeeds and the first byte is accepted.

- **Extent one:** the scan bound is zero. No scan byte is read. The initial padding count equals the bound, so the function selects `0x71`.
- **Extent zero or a negative extent for which the subtraction is defined:** the scan bound is negative. No scan byte is read. The initial zero count does not equal the negative bound, but is less than eight, so the function selects `0x67`.

These are not safe empty-input operations: they still require the first-byte read and traversal-address formation.

Under a nonwrapping signed 32-bit interpretation, extent equal to the minimum signed value cannot reach this analysis with defined extent-minus-one arithmetic. That limitation does not apply to earlier rejection paths, which do not perform the subtraction.

## Side effects

### Direct memory access

The directly visible access order is:

1. Compute and compare the initial pointer-shaped values without reading candidate bytes.
2. If the comparison succeeds, read the first candidate byte and form the next-byte address.
3. If the first-byte check also succeeds, compute the scan bound.
4. If the bound permits scanning, examine bytes in increasing address order until a separator, an unexpected byte, or exhaustion.
5. Perform no direct payload-byte reads after the separator.

The scan’s non-`0xFF` branch separately tests the same position for zero. The supplied body therefore does not establish a single physical read per position. The ordinary byte-sequence behavior assumes stable memory; concurrent mutation, volatile access, and device-backed storage are unresolved.

The function makes no explicit writes to caller-provided storage. Its traversal changes do not update the caller’s pointer object.

## Acceptance examples

These are conditional static examples, not executed tests. Unless specified otherwise, they assume stable readable memory, defined arithmetic and pointer operations, a matching fifth argument, and dependencies that return normally.

1. **Four-byte payload accepted.**  
   Extent is 14. The block contains `0x01`, eight `0xFF` bytes, `0x00`, and four payload bytes. The limit is four. F-external-01 receives the payload pointer, length four, scan bound 13, and extent 14, together with the unchanged first argument. The function returns four.

2. **Empty payload accepted.**  
   Extent is ten. The block consists of `0x01`, eight `0xFF` bytes, and a final separator. With limit zero, the dependency is called with length zero and a pointer immediately after the separator. The function returns zero.

3. **Initial mismatch avoids all candidate reads.**  
   The fifth argument differs from the derived pointer-shaped value. The function reports `0x6A` and returns −1 without reading candidate storage or computing extent minus one.

4. **Wrong header avoids scan-bound arithmetic.**  
   The initial comparison succeeds, but the first byte is `0x02`. The function reads that byte and forms the next-byte address, then reports `0x6A`. It performs no scan and does not compute extent minus one.

5. **Minimum signed extent with an initial mismatch.**  
   Assume nonwrapping signed 32-bit arithmetic and a meaningful conversion of extent plus one. Extent is −2,147,483,648, and the initial comparison fails. Extent plus one is representable. The function reports `0x6A`; the overflowing extent-minus-one subtraction is never evaluated.

6. **Minimum signed extent with a wrong first byte.**  
   Under the same arithmetic assumptions, the comparison succeeds and readable candidate storage begins with `0x02`. With valid next-byte address formation, the function reports `0x6A` without evaluating extent minus one. If the first byte were instead `0x01`, that subtraction would be reached, and this contract would not guarantee a normal rejection result.

7. **Unexpected byte wins over short padding.**  
   Within the scan bound, three `0xFF` bytes are followed by `0x7E`. The function reports `0x66`, not `0x67`.

8. **Early separator.**  
   Extent is nine, with `0x01`, seven `0xFF` bytes, and `0x00`. The function reports `0x67`.

9. **No separator.**  
   Extent is ten, with `0x01` followed by nine `0xFF` bytes. The function reports `0x71` without searching beyond the scan bound.

10. **Payload exceeds the limit.**  
    The valid 14-byte block from example 1 is supplied with limit three. The function reports `0x6D` and does not invoke F-external-01.

11. **Negative limit rejects an empty payload.**  
    The valid empty-payload block from example 2 is supplied with limit −1. The signed comparison rejects zero as greater than −1, producing `0x6D`.

12. **Nonpositive bounds still require a header read.**  
    With a matching initial comparison and first byte `0x01`, extent one produces `0x71`; extent zero produces `0x67`. Neither case reads a scan byte.
