# F-3d0cbc9c0022

## Purpose

F-3d0cbc9c0022 conditionally decodes a four-byte word from an object and writes the result to caller-provided storage. A dependency supplies a position within the object. The function checks two bytes near that position, decodes a length, and uses an unsigned 32-bit comparison to decide whether to perform the extraction.

The function is not an independently safe buffer reader. It does not establish the object’s allocation size, validate the selected position against that size, or exclude arithmetic wraparound.

The apparent intent is to read a word at a caller-specified offset within a payload following a 20-byte header. “Header,” “payload,” and “length” are descriptive interpretations of the offsets and arithmetic, not independently established format semantics.

## Interface

The function takes four positional inputs and returns a 32-bit value.

| Input | Visible role |
|---|---|
| Output address | Destination for one decoded 32-bit word. Must be nonnull to pass initial admission. |
| Opaque argument | A 32-bit value with no visible use. It is not forwarded to the dependency. |
| Requested offset | A signed 32-bit input. Its bit pattern participates in unsigned 32-bit range arithmetic. Negative values are not explicitly rejected. |
| Object-state address | Address of a cell containing a 32-bit object base or address-like value. The address and the cell’s initially observed contents must both be nonzero. |

The supplied representation establishes a four-byte result and 32-bit arithmetic operands. It carries the object base through an integer-valued cell. Exact machine ABI, physical pointer width, alignment requirements, and the portability of integer-to-address conversions remain **documented_only**.

### Return values

There are five visible return paths:

| Path | Return value |
|---|---|
| Initial admission fails | Value read from the external input-rejection status location |
| Dependency returns zero | Value read from the external selector-rejection status location |
| Either checked header byte fails | Value read from the external header-rejection status location |
| Length comparison fails | Value read from the external range-rejection status location |
| Extraction completes | Literal zero |

The four external status locations have unknown contents. Their values need not be distinct, stable, or nonzero. A returned zero therefore does not, by itself, establish that an output store occurred.

### Preconditions for defined access

The function does not prove the validity of the memory it accesses. Each reached path requires:

- A readable object-state cell when its address is nonnull.
- Readable backing memory at every reached header, length, and extraction address.
- A destination valid for a four-byte store when extraction succeeds.
- Whatever additional state F-e81ed1edd673 requires.

Nonnull addresses do not establish these conditions. Nor does a nonzero dependency result establish that the selected position is within an allocation.

No ownership transfer is established by the visible interface.

## Behavior

### Initial admission

Admission uses short-circuit checks in this order:

1. Check whether the object-state address is null.
2. If nonnull, read the state cell and check whether its contents are zero.
3. If the preceding checks pass, check whether the output address is null.

Any failure returns the input-rejection status. F-e81ed1edd673 is not called on these paths, and this function performs no output store.

This ordering is observable. A null output address does not prevent the earlier state-cell read. A null object-state address does prevent that cell from being dereferenced.

The opaque argument affects none of the visible checks, calls, memory accesses, or return selections.

### Position selection

After admission, the function calls F-e81ed1edd673 exactly once, passing the object-state address.

The return is interpreted as an unsigned 32-bit position:

- **Zero is rejected**, returning the selector-rejection status.
- **One is accepted** for subsequent processing.
- Every value from two through hexadecimal `FFFFFFFF` is also accepted for subsequent processing.

For a result of one, the intermediate admission value becomes zero, which selects the same continuation as larger results. There is no rejection of position one.

Acceptance at this stage means only that processing continues. It does not guarantee successful extraction.

For every accepted position, the function reads the object-state cell again. This post-call value supplies the base for subsequent object accesses; the initially checked base is not reused. There is no second nonzero check.

Consequently:

- A dependency-provided replacement base is used.
- A dependency-provided zero base is not rejected before the later address-based reads.
- The dependency’s preservation of backing memory, output storage, or external status storage cannot be assumed.

When the dependency returns zero, the post-call state-cell read and all header accesses are skipped.

### Byte decoding and layout

For a stored byte \(x\), define:

\[
d(x) = 23x \bmod 256.
\]

Four bytes at consecutive increasing addresses form a decoded 32-bit word with the first byte contributing the most significant eight bits:

\[
W = 2^{24}d(x_0) + 2^{16}d(x_1) + 2^8d(x_2) + d(x_3).
\]

This is the observed bit-pattern construction. It describes decoding independently of the machine’s native byte order. It does not establish that all signed-looking operations in the supplied representation are portable language arithmetic.

Let the selected origin be the post-call base plus the accepted position. The visible layout relative to that origin is:

| Relative offset | Use |
|---|---|
| 0–3 | Four encoded bytes decoded as a 32-bit length |
| 14 | Checked byte, examined second |
| 15 | Checked byte, examined first |
| 20 plus requested offset | Start of the four encoded extraction bytes |

No other header bytes are directly checked by this function.

These offsets do not establish a minimum allocation size. The function reaches the checked bytes before decoding or comparing the length.

### Header checks

The byte at relative offset 15 is read first. Its product with 23, narrowed to one byte, must be zero.

If it is nonzero, the function returns the header-rejection status immediately. Relative offset 14 and the length bytes are not read on that path.

If the first check passes, the byte at relative offset 14 is read and checked by the same rule. Failure returns the same header-rejection status without reading the length bytes.

Because 23 is relatively prime to 256, multiplication by 23 is invertible modulo 256. Thus each checked byte passes exactly when its stored byte is zero. No nonzero byte is converted to zero by this check.

### Length decoding and comparison

Only after both header checks pass does the function read the four bytes at relative offsets zero through three and decode them as the length.

The range decision compares two unsigned 32-bit quantities:

- Requested offset plus four, reduced modulo \(2^{32}\).
- Decoded length minus 20, reduced modulo \(2^{32}\).

Extraction is permitted when the first quantity is less than or equal to the second. Otherwise, the function returns the range-rejection status without a direct output store.

This comparison is not an overflow-safe proof that four bytes lie within a payload:

- A decoded length below 20 makes the subtraction wrap to a large unsigned value.
- A sufficiently large offset bit pattern makes addition of four wrap.
- Negative requested offsets are not separately rejected.
- Neither the selected position nor the object’s actual allocation size is validated.
- No check establishes that the resulting addresses are readable.

For ordinary nonnegative offsets without wraparound and decoded lengths of at least 20, the comparison matches “four bytes fit after the requested offset within the length minus 20.” Outside those conditions, the unsigned arithmetic remains controlling.

### Extraction and return

After a successful comparison, the function combines the accepted position, the 20-byte displacement, and the requested offset to form the extraction displacement. The position participates as an unsigned 32-bit value, so the displacement has the corresponding 32-bit arithmetic result.

Four bytes beginning at the resulting address are decoded by the same rule as the length. The function stores the complete decoded 32-bit word through the output address, then returns literal zero.

All four extraction bytes contribute to the value before the output store. The supplied expression does not establish a left-to-right order among those reads. Likewise, it does not establish a left-to-right order among the four length-byte reads.

The visible output operation is a single word assignment. Hardware atomicity, access decomposition, and fault behavior are not established.

The exact treatment of signed-looking final address arithmetic and integer-to-address conversion is **documented_only**. The 32-bit displacement calculation does not itself establish valid addressing.

## Side effects

### Direct effects and ordering

On a fully successful path, the visible sequence is:

1. Read the initial object-state cell during admission.
2. Call F-e81ed1edd673.
3. Read the object-state cell again.
4. Read and check relative byte 15.
5. Read and check relative byte 14.
6. Read and decode the four length bytes.
7. Perform the unsigned comparison.
8. Read and decode the four extraction bytes.
9. Store one 32-bit output word.
10. Return literal zero.

A rejection stops this sequence at the relevant condition and reads the corresponding external status value for return. Earlier rejection prevents later object reads.

The function directly performs no allocation, release, state-cell update, or backing-object update other than changes possible through an aliased output store.

### Dependency effects

The dependency’s contract is unavailable. Its call may affect memory or globals; preservation must not be assumed.

In particular, “no direct output store on rejection” does not mean output storage is necessarily unchanged. The dependency may have modified it before a later rejection. External rejection statuses may also have changed before they are read.

The visible body neither establishes nor transfers ownership. It does not establish that the dependency retains, releases, or preserves any supplied storage.

### Aliasing and concurrency

No non-aliasing condition is checked. If the output overlaps the state cell, backing object, or other writable storage, the final successful store may modify that storage.

The source bytes have already supplied the decoded word before the output assignment. The function does not promise rollback if execution faults or if a dependency has already caused effects.

No synchronization, concurrency guarantee, or reentrancy guarantee is visible. Concurrent changes to the state cell, backing bytes, or status locations are not specified.

## Acceptance examples

These are conditional deductions from static evidence, not executed tests. Except where an example concerns initial rejection, assume valid reached storage, no interfering concurrent changes, and a dependency returning the stated position.

1. **Null object-state address.**  
   The input-rejection status is returned. The state cell is not dereferenced, and the dependency is not called.

2. **Zero initial base.**  
   A nonnull state cell containing zero causes input rejection. The dependency is not called.

3. **Null output after a usable initial cell.**  
   The state cell is read before the null output is rejected. No dependency call occurs.

4. **Zero selected position.**  
   If the dependency returns zero, the selector-rejection status is returned. There is no post-call state-cell read and no header read.

5. **Position one can succeed.**  
   Suppose the dependency returns one and leaves a valid base. At the selected origin, both checked bytes are zero, the length bytes are hexadecimal `00 00 00 A8`, and the requested offset is zero. The length decodes to 24, so the comparison is four less than or equal to four. If the extraction bytes at relative offsets 20–23 are `00 00 00 A7`, the function stores one and returns zero. Position one is not rejected.

6. **Larger accepted position.**  
   The same conditions with dependency result two also store one and return zero, using the origin two bytes beyond the post-call base.

7. **First checked byte rejects.**  
   With any nonzero position, a stored byte of one at relative offset 15 produces a narrowed decoded value of 23. Header rejection occurs without reading relative offset 14 or the length bytes.

8. **Second checked byte rejects.**  
   If relative offset 15 is zero but relative offset 14 is nonzero, the first check passes and the second causes header rejection. The length bytes are not read.

9. **Ordinary range rejection.**  
   With decoded length 24 and requested offset one, the compared quantities are five and four. The range-rejection status is returned without a direct output store.

10. **Length underflow permits the comparison.**  
    With decoded length zero and requested offset zero, subtraction produces hexadecimal `FFFFFFEC`. Four is less than that value, so extraction proceeds if all required addresses are valid.

11. **Negative offset can pass.**  
    Requested offset negative four has bit pattern `FFFFFFFC`; adding four gives zero. With decoded length 24, the comparison passes. Under the represented address arithmetic, extraction begins 16 bytes after the selected origin, not 20. Address validity remains a separate precondition.

12. **Dependency replaces the base.**  
    For any nonzero dependency result, including one, subsequent accesses use the reloaded base. If the replacement is zero, there is no second null rejection; subsequent address validity is unresolved.
