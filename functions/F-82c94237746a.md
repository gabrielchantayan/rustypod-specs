# F-82c94237746a

## Purpose

F-82c94237746a consumes one word from an index-linked collection of four-byte words. It reads the word selected by a stored head index, decodes its successor, updates the head, decrements a stored count, and clears the selected word.

When the count is zero on entry, the function first invokes two dependencies, copies existing words into a replacement region, initializes additional successor links, and publishes replacement storage before performing the same consumption operation.

The interpretation as a free-entry pool is inferred from the links and count changes. The established behavior is the memory-access and dependency-call sequence below. The function does not return the consumed index or its address.

## Interface

**Input:** an address identifying a mutable record containing at least four consecutive 32-bit fields.

**Output:** no explicit return value. Observable results consist of memory mutations and, on the zero-count branch, dependency calls.

| Byte offset | Width | Contract name | Operational role |
|---|---:|---|---|
| 0 | 32 bits | Storage address | Base address used for backing-word accesses |
| 4 | 32 bits | Available count | Controls growth and is decremented during consumption |
| 8 | 32 bits | Capacity | Supplies growth arithmetic, copy bounds, and publication values |
| 12 | 32 bits | Head index | Selects the backing word to consume |

These names describe observed roles, not a verified external type or invariant. The count is not checked against the capacity, head, or link structure.

The storage address is held in a 32-bit field. The supplied representation does not establish compatibility with a wider native pointer model. Each backing word occupies four bytes; byte order is not established independently.

A consumed word is decoded as follows:

- `0xFFFFFFFF` produces a head value of `0xFFFFFFFF`.
- Every other word produces its unsigned value shifted right by one bit.
- The low bit is discarded without validation.

Thus an even word is accepted by the decoder, and a zero word produces successor index zero.

### Preconditions and ordinary-use assumptions

The function performs no explicit input validation. Successful bounded execution requires accessible memory for every reached read and write, dependencies that return sufficiently usable results, and arithmetic compatible with the execution model.

The ordinary pool interpretation additionally requires:

- A writable record with the stated layout.
- A valid selected-word address.
- On growth, a positive captured capacity and representable size, doubling, and address calculations.
- A replacement region large enough for every destination access.
- Dependencies that preserve the record except where an example explicitly states otherwise.
- No concurrent interference.
- A memory arrangement that prevents writes from unexpectedly changing record fields or unread backing words.

Record/backing-storage nonaliasing is not enforced. It is an explicit condition for the ordinary acceptance examples below, not an inherent property of the input.

## Behavior

### Entry decision

The function reads the available-count field and tests whether it equals zero.

- Zero selects the growth sequence.
- Any nonzero value skips growth and proceeds directly to consumption.

There is no positivity check. A negative nonzero count follows the nongrowth branch. Its later decrement remains subject to the arithmetic limitations described under Uncertainties.

### Growth: captured values and first dependency

The function reads and retains the capacity before calling either dependency. It computes a retained doubled capacity as twice that captured value.

It then calls **F-fab3799b3190**, passing the captured capacity shifted left by three bits. For positive values within the representable range, this requests eight times the captured capacity in bytes: enough for twice that many four-byte words.

The returned 32-bit value is retained as the replacement-storage address. There is no check for null, an error encoding, alignment, ownership, or sufficient allocation size.

The captured capacity, doubled capacity, and retained replacement address are distinct from later record-field reads. Dependency mutations do not cause these retained values to be recaptured.

### Growth: copying

The copy traversal starts at index zero and uses an unsigned 32-bit index.

Before each iteration, the index is compared with a fresh read of the capacity field, interpreted as unsigned. For an admitted index:

1. A four-byte word is read from the current storage address at that index.
2. Its unchanged 32-bit contents are written to the same index in the retained replacement region.

The storage-address field is used as it exists for that iteration; it is not an entry-time snapshot. The index then advances by one.

Consequences include:

- Changes made by F-fab3799b3190 can affect both the copy bound and the source region.
- A destination write that aliases the record can affect subsequent iterations.
- Overlap with unread source words can change later copied values.
- A negative capacity bit pattern is treated as a large unsigned copy bound, not as a negative bound that automatically skips copying.

With a stable record and disjoint regions, exactly the captured-capacity number of words is copied.

### Growth: successor initialization

After copying, the function reads the capacity field again to obtain the starting index for successor initialization. This is not necessarily the captured capacity.

The unsigned index advances while it is less than the retained doubled capacity minus one, with that subtraction evaluated in the unsigned comparison domain.

At each visited index, the function writes a successor encoding whose value is twice the next index, with the low bit set. The index arithmetic for this encoding is unsigned 32-bit arithmetic. Within the ordinary representable index range, the word therefore encodes the following index.

With stable ordinary inputs, this initializes indices from the captured capacity through the doubled capacity minus two.

The function then writes `0xFFFFFFFF` at the retained replacement address plus eight times the **captured** capacity minus four bytes. Under ordinary positive, nonoverflowing arithmetic, this is the last word of the doubled region. The location is not derived from a fresh capacity read.

### Growth: second dependency and publication

After all replacement initialization writes, the function reads the current storage-address field and passes it to **F-58ba61416cc9**.

That argument need not equal the entry storage address or every source address used during copying. Earlier dependency effects or aliasing writes can change the field.

If the dependency returns, publication occurs in this order:

1. Store the retained replacement address in the storage-address field.
2. Read the current capacity field and store that value in the head-index field.
3. Read the capacity field again and store the retained doubled capacity minus that value in the available-count field.
4. Store the retained doubled capacity in the capacity field.

Both capacity reads occur after F-58ba61416cc9 returns. The function does not restore or validate the original capacity.

With a stable record, publication establishes the captured capacity as the head and as the available count, and establishes twice the captured capacity as the new capacity. Consumption then occurs immediately; growth is not a standalone return path.

### Common consumption

Both branches perform the following sequence:

1. Form a selected-word address from the current storage-address field plus four times the current head index.
2. Read the 32-bit word at that address.
3. Decode its successor, preserving `0xFFFFFFFF` specially and otherwise using an unsigned right shift by one.
4. Write the decoded successor into the head-index field.
5. Read and decrement the available-count field by one.
6. Write zero to the previously selected address.

The selected address is retained through the record updates. The final clear does not use the updated head to select a different word.

This order is significant when storage aliases the record. The final clear can overwrite the newly written head, the decremented count, the capacity, or the storage-address field. Consequently, the decoded successor need not remain the final head, and fields not otherwise assigned on the nongrowth branch need not remain unchanged.

With ordinary disjoint storage after growth:

- Final capacity is twice the captured capacity.
- Final available count is the captured capacity minus one.
- The first added word is zero.
- For captured capacity greater than one, the final head is the captured capacity plus one.
- For captured capacity one, the final head is `0xFFFFFFFF`.

## Side effects

### Memory writes

Every normally completed call performs the head update, count decrement, and selected-word clear. These are ordered writes, not a guarantee that each written value survives later overlapping writes.

The growth branch additionally writes:

- Copied words into replacement storage.
- Successor encodings into the added region.
- A terminal marker.
- The replacement storage address, provisional head, available count, and doubled capacity into the record.

The old backing region is read during copying. It can also be affected through overlap or dependency behavior.

### Ownership and lifetime

The call pattern suggests allocation followed by release, but those ownership roles are not established by this body alone.

The contract does not assume that:

- F-fab3799b3190 returns newly owned or distinct memory.
- Its result is disjoint from the record or existing storage.
- F-58ba61416cc9 releases its argument.
- Either dependency preserves the record, globals, or unrelated memory.
- Either dependency transfers ownership in a particular direction.

After successful publication, the record contains the retained replacement address. This establishes a stored address, not a proven ownership transfer.

### Errors and partial execution

There is no explicit error result, bounds check, allocation-failure check, rollback, or recovery path.

Invalid addresses can prevent completion at the first affected read or write. A dependency that fails or does not return prevents subsequent operations. Completed earlier writes are not undone.

During growth, replacement writes precede publication. During consumption, the head and count updates precede the final clear. A failure between these operations can leave partially changed state.

No synchronization is visible. Concurrent safety is not established.

## Acceptance examples

These are conditional static acceptance cases, not runtime test results.

Unless an example explicitly introduces overlap, all examples require:

- The entire record and backing storage to be disjoint.
- On growth, replacement storage to be disjoint from both the record and old backing storage.
- Valid, sufficiently sized and aligned memory for all reached accesses.
- Representable ordinary arithmetic and no concurrent interference.
- Normally returning dependencies with no relevant mutations except those expressly stated.

These nonaliasing conditions are necessary for the stated ordinary final-field values.

### Ordinary successor

Given a nonzero available count of 2, head index 3, and backing word 3 containing 9:

- Neither dependency is called.
- The decoded successor is 4.
- Final head is 4.
- Final available count is 1.
- Word 3 becomes zero.
- Storage address and capacity remain unchanged.

### Terminal word

Given available count 1 and a selected word containing `0xFFFFFFFF`:

- Final head is `0xFFFFFFFF`, not `0x7FFFFFFF`.
- Final available count is zero.
- The selected word becomes zero.

### Even successor encoding

Given a nonzero available count and selected word 8:

- The successor written to the head is 4.
- The count is decremented.
- The selected word becomes zero.
- No explicit error is reported for the clear low bit.

This does not establish that index 4 is valid for a later call.

### Growth from capacity three

Given count zero, capacity 3, and F-fab3799b3190 returning usable disjoint replacement storage:

- The first dependency receives 24.
- Old words 0 through 2 are copied unchanged.
- Replacement words 3, 4, and 5 are initialized to 9, 11, and `0xFFFFFFFF`.
- F-58ba61416cc9 receives the old storage address.
- Publication is followed immediately by consumption of word 3.
- Final capacity is 6, count is 2, head is 4, and word 3 is zero.
- Words 4 and 5 retain 11 and `0xFFFFFFFF`.

### Growth from capacity one

Given count zero and capacity 1 under the same ordinary conditions:

- The first dependency receives 8.
- Old word 0 is copied.
- Replacement word 1 receives the terminal marker and is then consumed.
- Final capacity is 2, count is zero, head is `0xFFFFFFFF`, and word 1 is zero.

### Capacity mutation by the second dependency

Suppose captured capacity is 3 and replacement initialization completes as above, but F-58ba61416cc9 changes capacity to 2 before returning.

Then:

- The retained doubled capacity remains 6.
- Publication sets head to 2 and count to 4, then capacity to 6.
- Consumption selects replacement word 2.
- Final count is 3.
- Final head is decoded from the copied contents of word 2, with the terminal-marker exception.

This is an observable reread case, not a recommended dependency contract.

### Selected word overlaps capacity

This example replaces the ordinary record/storage disjointness condition with explicit overlap. All reached memory remains accessible, and arithmetic remains representable.

Let storage begin four bytes before the record. Set capacity to 9, count to 2, and head to 3. Backing word 3 then occupies the capacity field and contains 9.

Expected sequence and result:

- Growth is skipped.
- The selected word decodes to successor 4.
- Head is written as 4.
- Count becomes 1.
- The final selected-word clear overwrites capacity with zero.
- Final head is 4, count is 1, and capacity is zero.

Capacity is not preserved merely because the nongrowth branch contains no separate capacity assignment.

### Selected word overlaps head

Again permit explicit overlap while requiring valid accesses. Let storage begin at the record address, with capacity 4, count 1, and head 3. Backing word 3 is then the head field itself and initially contains 3.

Expected behavior:

- The selected word decodes to 1, which is first written to the head.
- Count becomes zero.
- The retained selected address still identifies the head field.
- The final clear overwrites the head with zero.

The final head is zero, not the decoded successor 1.

## Uncertainties

**documented_only — Arithmetic model.** The representation establishes 32-bit fields, unsigned loop comparisons, unsigned successor decoding, and unsigned successor-encoding arithmetic. It does not independently establish universal wrapping semantics for signed doubling, left shifts, count arithmetic, or address expressions. Their behavior outside representable ranges is not generalized here.

**documented_only — Zero and negative capacity.** Neither is rejected. With captured capacity zero, the unsigned successor-loop limit becomes `0xFFFFFFFF`; growth is not a harmless empty initialization. The terminal displacement also lies four bytes before the retained replacement address under ordinary arithmetic. Negative capacities can produce large unsigned traversal bounds. Safe completion is not established for these inputs.

**documented_only — Extreme positive values.** Size calculations, doubling, terminal placement, or selected-address formation may exceed the supported range. No explicit maximum capacity or head is supplied.

**documented_only — Aliasing.** There is no enforced nonaliasing guarantee. Overlap can alter record values, future source reads, loop bounds, or the final state. The overlapping acceptance cases establish specific consequences, not a general guarantee of usable overlapping operation.

**documented_only — External contracts.** Dependency ownership, failure behavior, preservation guarantees, caller invariants, byte order, and concurrency rules remain unresolved.

**Inferred intent.** The structure appears to manage available entries through encoded successor links. This does not establish payload semantics or external lifecycle rules.
