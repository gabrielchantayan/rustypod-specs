# F-83c236f76838

## Purpose

F-83c236f76838 updates two 32-bit values held in a target record, derives a classification from those values, and conditionally places the record at the head of an indexed chain.

The established behavior is narrower than a general-purpose “move record” operation. The function does not visibly unlink an already-linked record, validate the classification against a table size, or report success or failure. Its direct insertion work is gated by both the classification and one bit in the target record.

Names such as “classification,” “chain,” and “membership bit” describe the apparent role of the accesses. Their broader application meaning is inferred, not established.

A normally completing call produces its result through record, table, and dependency side effects, not through a return value.

## Behavior

### Initial external-state capture and dependency calls

The function first captures the address of the external 32-bit cell. It reads that cell and invokes F-03b9616af95f with:

1. The cell’s current 32-bit contents.
2. The target argument.

It then invokes F-2609ef4ae406 twice, in this order:

1. With the first value.
2. With the second value.

These calls occur before this function tests either of the target’s existing value fields. Consequently, effects of these dependencies can influence the subsequent field tests.

The captured cell address is retained across the calls. The function does not later fetch a replacement address from the external pointer location. If a dependency redirects that external pointer, the later read still uses the originally captured cell address. If a dependency changes the contents of that original cell, however, the later read observes those contents.

### Conditional processing of existing values

After the initial three dependency calls:

1. The function reads the 32-bit field at target offset `0x1c`.
2. If that read is nonzero, it invokes F-029930293dcb with no explicit arguments.
3. It then reads the 32-bit field at target offset `0x18`.
4. If that read is nonzero, it invokes F-029930293dcb again, also with no explicit arguments.

The tests are not taken from an entry-time snapshot. In particular, the first conditional call can affect the value observed by the second test.

The existing nonzero field contents are not explicitly passed to F-029930293dcb. It is therefore not established that this dependency releases those values, decrements their reference counts, or even operates on them. Any such interpretation requires additional evidence.

Zero suppresses the corresponding conditional call. Nonzero causes the call regardless of whether the old field equals the incoming replacement value.

### Value replacement and classification

After both conditional tests and their possible calls, the function performs these direct writes in order:

1. Stores the first value at target offset `0x1c`.
2. Stores the second value at target offset `0x18`.

It then invokes F-fb6e215aa4fd with the second value first and the first value second. This argument order is significant and differs from the order of the two earlier F-2609ef4ae406 calls.

The classification dependency returns a 32-bit integer result. The function stores that result plus one in the 32-bit field at target offset `0x08`.

The classification call occurs after the value-field writes. It can therefore observe those writes if it has access to the target through other state. Its effects are not assumed to preserve the target, the external cell, or any other shared memory.

After the classification call and the write at `0x08`, the function reads the originally captured external cell again. This second value supplies the base address for any ensuing table access.

### Index derivation and insertion gate

The function reads target offset `0x08` and subtracts one to derive a 32-bit candidate index. It considers the candidate’s signed 32-bit interpretation.

- If the candidate is negative, insertion is skipped.
- If the candidate is nonnegative, the function reads the byte at target offset `0x14`. Insertion occurs only if bit 0 is clear.
- If the candidate is nonnegative and bit 0 is set, insertion is skipped.

For a negative candidate, the gate does not require a read of the byte at `0x14`. The later external-cell read has nevertheless already happened.

For ordinary nonoverflowing arithmetic, the derived candidate equals the classification dependency’s result. A negative classification therefore suppresses insertion. The signed maximum classification has an arithmetic qualification described under **Uncertainties**.

Insertion being skipped does not undo earlier work. The dependency calls, replacement-value writes, classification call, classification-field write, and later external-cell read have already occurred.

### Insertion writes

When the candidate is nonnegative and bit 0 is clear, the function accesses a 32-bit table entry at:

**table base + 4 × candidate index**

There is no visible bounds check.

The direct operations occur in this order:

1. Write zero to target offset `0x0c`.
2. Read the selected table entry and store its 32-bit value at target offset `0x10`.
3. Write the target address into the selected table entry.
4. Read the byte at target offset `0x14` and write it back with bit 0 set.
5. Read target offset `0x10`.
6. If that field is nonzero, use the address held there and write the target address at offset `0x0c` of that record.

In an ordinary nonaliasing layout, this makes the target the new head, records the former head as its next record, and updates the former head’s backward link.

That structural interpretation does not add checks absent from the supplied material. There is no direct check that the old head differs from the target, that the target’s links were clear, or that the table entry belongs to a compatible structure.

The old-head condition is checked through the target’s stored `0x10` field after the intervening writes. It is not specified as an immutable copy of the earlier table read. Overlapping memory can therefore affect the result.

## Side effects

Directly established writes are:

- Replacement of both 32-bit value fields.
- Replacement of the 32-bit classification field.
- On insertion, clearing the target’s backward-link field.
- On insertion, replacing the target’s forward-link field.
- On insertion, replacing one table entry with the target address.
- On insertion, setting bit 0 in the target’s flag byte.
- On insertion with a nonzero stored successor, replacing that successor’s backward-link field.

For the flag update itself, bits 1–7 are preserved from the byte read at that moment. This is not a guarantee that dependencies preserve those bits.

The function has no visible direct allocation, deallocation, or explicit transfer of ownership. Dependency names and call placement do not establish ownership semantics. In particular, no guarantee can be made that incoming values remain owned by the caller, become owned by the target, or receive balanced retain/release operations.

There is no visible error result, rollback path, or recovery path. If a dependency does not return normally, later operations are not established to occur. Invalid target, table, or successor addresses can cause invalid memory accesses; the platform-specific outcome is not established.

The function is not shown to provide synchronization, atomic insertion, or protection against concurrent modification.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless stated otherwise, dependencies return normally, preserve relevant memory beyond their specified return, and all addressed storage is valid and nonoverlapping.

### Insertion into an empty entry

Given a classification result of 3, a clear bit 0 at target offset `0x14`, and a zero table entry at index 3:

- The first and second values replace fields `0x1c` and `0x18`, respectively.
- Field `0x08` becomes 4.
- Field `0x0c` becomes zero.
- Field `0x10` becomes zero.
- Table entry 3 becomes the target address.
- Bit 0 becomes set.
- No successor backward-link write occurs.

### Insertion before an existing head

Given a classification result of 2, a clear membership bit, and a nonzero valid table head at index 2:

- The target’s forward link becomes that previous head.
- The table entry becomes the target address.
- The previous head’s field at `0x0c` becomes the target address.
- The target’s own field at `0x0c` is zero.

### Membership bit already set

Given a classification result of 5 and bit 0 already set when the gate reads it:

- The value fields are still replaced.
- Field `0x08` becomes 6.
- The external cell is still reread.
- No direct insertion writes occur.

This case does not establish that the record is moved to entry 5 or that any existing linkage is corrected.

### Negative classification

Given a classification result of −1:

- Field `0x08` becomes zero.
- The derived candidate is −1.
- Insertion is skipped without the gate reading the flag byte.

Other negative results likewise suppress insertion under the ordinary arithmetic interpretation, but need not produce zero in field `0x08`.

### Sequential cleanup conditions

If the field at `0x1c` is nonzero after the initial dependency calls, the first conditional F-029930293dcb invocation occurs.

If that invocation changes field `0x18` to zero, the second invocation is omitted. An entry-time nonzero value at `0x18` does not override the later zero read.

### External cell changes

If a dependency changes the contents of the originally captured cell from one table base to another, insertion uses the later contents.

If it instead redirects the external pointer to a different cell while leaving the original cell intact, insertion still uses the original cell’s later contents.
