# F-94ed37fbe922

## Purpose

F-94ed37fbe922 accepts three 32-bit inputs, performs an extensive ordered sequence of indirect dependency invocations and bit-field transformations, then performs direct memory reads and writes before a final unresolved indirect transfer.

**Established static evidence:** the supplied representation exposes argument forwarding, arithmetic widths, dependency-result consumption, mixed-width memory accesses, repeated writes, and a final four-argument transfer. It does not establish a recognizable application-level operation.

**Inferred intent:** the repeated shifts and masks may participate in packed-state processing. The later offset-based accesses may manipulate interconnected state. Neither interpretation establishes a data format, object model, serialization protocol, or ownership scheme.

**Contract boundary:** this document specifies supported observable constraints and explicitly records unresolved behavior. It is not a complete executable replacement specification. Dependency identities, hidden calling-convention state, and uncertain control-flow recovery prevent an unconditional input-to-output contract.

## Behavior

### Execution ordering

The visible body has three broad phases:

1. A long, straight-line sequence of indirect invocations and arithmetic preparation.
2. Direct memory mutation, including repeated stores and reads through previously obtained values.
3. A final unresolved indirect transfer with four explicit arguments.

No explicit input-validation branch, local retry loop, or local error-return branch is shown. This does not establish that dependencies return normally, terminate, or have no internal branches.

Each reached dependency invocation is an ordering boundary. An invocation whose return value is unused remains potentially observable. Identical-looking calls cannot be merged, omitted, or reordered merely because their visible arguments match.

A displayed invocation with no explicit arguments does not establish a truly argument-free ABI. Additional machine state may be significant.

### Dependency-driven transformations

The initial invocation receives all three explicit inputs and zero. Subsequent invocations consume a mixture of:

- Newly returned 32-bit values.
- Low and high 32-bit portions of represented 64-bit results.
- Shifted copies of earlier results.
- Explicit zero arguments.
- Secondary result state whose producer and ABI role are incompletely established.

A recurring transformation shifts a returned low word left by eight bits before passing it onward. Other calls receive an unchanged high word alongside transformed low-word data. Some invocations receive the same transformed value in multiple argument positions.

The third explicit input is separately shifted left by five bits and passed as a second argument early in this phase. There is no visible range check before this transformation.

Later transformations use masks of 24, 22, 20, 19, 18, 17, 14, 13, 12, and 11 bits, among others. Their presence establishes local field extraction, not a common record layout or externally defined field meaning.

### Width and arithmetic constraints

The representation uses 8-bit, 16-bit, 32-bit, and 64-bit quantities.

For an established unsigned 32-bit operation:

- Left shifts retain the low 32 result bits.
- Right shifts introduce zero bits.
- Masking before shifting limits which original bits can contribute.
- Intermediate truncation must be preserved.

For example, masking a 32-bit quantity to its lowest 20 bits, shifting right by ten, and then shifting left by six yields a ten-bit field placed at bit positions 6 through 15. It does not retain the original upper bits.

The represented 64-bit results are repeatedly split into low and high 32-bit portions. A logical shift of a 64-bit result by 34, 36, or 44 bits corresponds to shifting its high word right by 2, 4, or 12 bits respectively. These operations do not establish memory byte order.

Many other shifts and multiplications are represented on signed 32-bit values. Their exact overflow and negative-input behavior cannot be made portable from the supplied evidence alone. Where examples below use low-32-bit arithmetic, that interpretation is explicitly conditional.

A late variable-count right shift uses the low eight bits of an address-derived quantity as its count. Counts outside the ordinary 32-bit range, and right shifts of negative represented values, are **documented_only** pending machine-level semantics.

### Beginning of direct memory mutation

The first direct-memory operations use values retained from the last dependency invocations. The following descriptive labels are mathematical references, not asserted object identities:

- **Packed base:** a retained 32-bit result shifted left by 25 bits.
- **Narrow base:** twice a nine-bit extracted quantity.
- **Shifted base:** a retained result shifted left by eight bits.
- **Link base:** another retained result shifted left by 25 bits.
- **Final pair:** the low and high words of the last represented 64-bit dependency result.

The nine-bit quantity is obtained by shifting a result left by eight, retaining its lowest 15 bits, and logically shifting right by six. Under 32-bit bit-vector interpretation, it is a multiple of four from 0 through 508. Consequently, the narrow base is a multiple of eight from 0 through 1016.

The opening observable order includes:

- A 32-bit store of the link base at the final pair’s high word plus offset 0x14.
- A byte store at the link base plus offset 9, containing the low byte of that high word.
- A 32-bit store of the packed base at the final pair’s low word multiplied by 256, plus offset 0x54.
- Another byte store to the same link-base offset 9, now containing the low byte of the link base.
- A 32-bit zero store at the packed base plus offset 0x14, followed by a byte read at offset 5.
- A 32-bit zero store at the narrow base plus offset 0x14.
- A 32-bit store of the zero-extended byte read to the packed base plus offset 0x34.
- A 32-bit reread at the packed base plus offset 0x14.
- Another 32-bit zero store at the narrow base plus offset 0x14.
- Two byte stores at the narrow base plus offset 0x15, both using the low byte of that reread value.

These are distinct accesses. Their actual interaction depends on address overlap, memory semantics, and intervening environmental changes. An earlier zero store does not justify replacing a subsequent read with a constant without those conditions.

- 32-bit stores whose value equals their destination base.
- Reads at offset 0x74 whose results become bases for further accesses.
- Reads through addresses derived from a previously loaded byte.

A later region writes the numeric value 0x3A using three different widths: one byte, two bytes, and four bytes, at separately derived destinations. Those accesses are not interchangeable.

Another destination at offset 0x20 receives, in order, four 32-bit stores: 0x20, 0x2F, a zero-extended byte read from offset 4 of the same base, and 0x20 again. The byte read occurs after the first two stores and before the third.

A long repeated-store region follows. Each repeated group writes a 32-bit derived value at offset 0x54 of a scaled base, writes one byte at offset 0x19 of a globally obtained base, writes one byte at offset 0x11 of another base, and then writes a 32-bit scaled value at offset 0x34 of the globally obtained base. Repetition is visible; no loop-control or termination policy is established by those repeated groups. Their exact multiplicity is not promoted here to a verified acceptance criterion.

The visible tail includes:

- Byte writes at offsets 9, 0x0D, 0x10, and 0x11.

The final unresolved transfer receives, in order:

2. A value obtained through an offset-0x64 read.
3. A retained value read earlier at offset 0x14.
4. A later value read at offset 0x74.

## Acceptance examples

These examples are conditional static obligations, not executed tests.

### Input forwarding

Given any three 32-bit input patterns, if execution reaches F-U001, its four explicit arguments are those patterns in original order followed by zero. No visible preprocessing alters the first three arguments.

### Unsigned field extraction

Given an established unsigned 32-bit value of 0xFFFFFFFF, retaining the lowest 20 bits, shifting right by ten, then shifting left by six produces 0x0000FFC0. Retaining upper input bits would violate that local transformation.

### Intermediate truncation

Under 32-bit bit-vector semantics, shifting a value left by 28 bits and subsequently shifting that intermediate left by another 28 bits produces zero. Treating the combined operation as an unbounded 56-bit shift would not preserve the intermediate width.

### Byte-store truncation

If a byte destination receives the low byte of 0x123456AB, its stored byte is 0xAB. This does not authorize replacing the access with a 32-bit store.

### Repeated stores

If the narrow-base destination is observable memory and execution reaches both identical byte stores at offset 0x15, both accesses occur. Recording only the final byte value is insufficient to establish equivalent behavior.

### Conditional final value

If the four offset-0x20 stores target ordinary writable memory, no aliasing operation changes that location afterward, and execution completes those stores, the last of those four stores leaves the 32-bit value 0x20 there. This says nothing about the function’s ultimate final memory state.

### Invalid-address behavior

If a computed destination is inaccessible, no explicit local validation or rollback is promised. A successful return or unchanged memory state is not an acceptance requirement for that case.

### Terminal arguments

If execution reaches F-U003, its first explicit argument is 0x72. Replacing retained earlier reads with fresh reads is not equivalent unless intervening-write and aliasing conditions establish equivalence.
