# F-6ef0016a253f

## Purpose

F-6ef0016a253f searches an object-associated pointer collection for an entry whose 32-bit unsigned key equals the requested key. If the collection search finds no match, it checks one separate fallback entry.

The operation is conditional on an initial dependency returning a nonzero result and on the requested key being nonzero. It can invoke another dependency to populate or otherwise modify the collection reference when that reference is initially null.

The established result is either an entry address or zero. Zero does not distinguish a disabled lookup, an excluded zero key, an unavailable collection, or an unsuccessful search.

The collection search uses midpoint narrowing followed by an ascending scan of the final interval. Its apparent intent is lookup in an ascending-key collection, but the supplied evidence contains no validation of ordering, entry validity, or storage bounds.

## Interface

### Inputs

The function takes two arguments:

- **Object address:** an address represented by a 32-bit signed integer in the supplied representation. The function uses this value as a base address, not as an ordinary numeric identifier.
- **Requested key:** a 32-bit unsigned integer. Equality and ordering against entry keys use unsigned comparisons. Zero is excluded from lookup, although the initial dependency is still called for that input.

No explicit length, allocation size, ownership flag, or error-output argument is supplied.

### Result

The result is a 32-bit address-bearing value, represented as a signed integer:

- A nonzero result identifies an entry selected by the lookup.
- Zero indicates that no entry was returned.

A result with its high bit set is not inherently an error: the represented value is used as an address. The evidence provides no separate status code.

## Behavior

### 1. Initial eligibility check

The function first calls F-3b037d560480 with no explicit arguments.

Only after that call returns does it evaluate whether the result is nonzero and the requested key is nonzero.

If the dependency returns zero, the function returns zero without reading the collection or fallback fields. If the dependency returns nonzero but the requested key is zero, it likewise returns zero without those field reads.

Consequently:

- The dependency is called even for a zero requested key.
- Object validity is not examined by this function before that call.
- A zero key cannot match either an array entry or the fallback entry.

The dependency’s meaning is unknown. Describing it as an eligibility check reflects how its result controls this function, not an established description of its internal purpose.

### 2. Collection acquisition

For an eligible lookup, the function reads the object’s collection reference at offset `0x234`.

If that reference is nonzero, it does not call F-616f7d92d3b9.

If that reference is zero, it calls F-616f7d92d3b9 with:

1. The object address.
2. The integer value `4`.

The dependency’s return value is ignored. After the call, the function rereads the collection reference from the object.

If the reference is still zero, the function returns zero. In particular, it does **not** check the fallback entry in this case, even if that fallback might contain a matching key.

Once the collection-presence condition succeeds, the function reads the collection reference again and uses that newly read value as the collection base. Thus the presence-check read and the search-base read are distinct. The supplied evidence does not establish synchronization or protection against changes between them.

A population or initialization role for F-616f7d92d3b9 is inferred from this call pattern. Its actual operation, allocation behavior, failure modes, and interpretation of `4` are unknown.

### 3. Search bounds

The function reads the collection’s signed 32-bit count at offset `0x0C`. It establishes a lower index of zero and an upper index equal to the count minus one.

For ordinary nonnegative counts:

- A zero count produces an empty interval, so no array entry is read.
- A count of one sends the sole entry directly to the final scan.
- A count of two sends both entries directly to the final scan.

The subtraction is not a saturating or validated operation. Extremely negative counts, oversized counts, and counts inconsistent with allocated storage are outside the established safe-input conditions.

### 4. Midpoint narrowing

While the difference between the upper and lower indices exceeds one, the function selects the midpoint using signed integer addition and division by two.

At each selected midpoint, it:

1. Reads the entry reference from the indexed collection slot.
2. Reads that entry’s unsigned key at offset `0x10`.
3. Compares the key with the requested key.

If the keys are equal, the function reads the same indexed pointer slot again and returns the address obtained by that second slot read. It does not reuse the first pointer value for this return.

If the requested key is smaller under unsigned comparison, the midpoint becomes the upper bound. Otherwise, the midpoint becomes the lower bound.

The midpoint itself remains within the retained interval; the bounds do not advance to one position beyond it. The loop therefore stops with at most two candidate indices under ordinary valid bounds.

For a stable, correctly sorted collection, this narrowing retains the region where a match can exist. For an unsorted collection, a matching entry can be discarded from consideration. The function neither detects nor reports that condition.

### 5. Final interval scan

After midpoint narrowing, the function examines the remaining interval in ascending index order, including both bounds.

For each position, it reads the entry reference and then that entry’s unsigned key. On equality, it immediately returns the entry reference already read for that comparison.

This differs from a midpoint match: the final scan does not reread the pointer slot to obtain its return value.

Duplicate keys are not rejected. Which duplicate is returned depends on the search path:

- A matching midpoint is returned immediately.
- If no midpoint matched, the first matching position in the final ascending scan is returned.

There is no general guarantee that the result is the first or last duplicate in the collection.

### 6. Fallback lookup

Only after an available collection has been searched without returning an entry does the function read the fallback reference at object offset `0x40`.

If the reference is zero, it returns zero without reading an entry key.

If the reference is nonzero, it reads that entry’s unsigned key at offset `0x10`:

- Equality returns the fallback address already read.
- Inequality returns zero.

An empty collection can therefore lead to a successful fallback lookup. An absent collection cannot.

The fallback is subordinate to the collection: a collection match returns before the fallback reference is read.

## Acceptance examples

These are conditional consequences of the static evidence, not executed tests. Unless stated otherwise, storage is valid and stable, arithmetic is representable, and the initial dependency returns nonzero.

1. **Initial dependency denies lookup.**  
   If F-3b037d560480 returns zero, the result is zero. Neither object field is read, and F-616f7d92d3b9 is not called.

2. **Requested key is zero.**  
   The initial dependency is still called. The function returns zero without consulting collection or fallback entries, even if an entry has key zero.

3. **Collection remains unavailable.**  
   If the initial collection reference is zero, F-616f7d92d3b9 receives the object address and `4`. If the subsequent reference read is also zero, the result is zero. A matching fallback does not change this result because it is not inspected.

4. **Population makes an empty collection available.**  
   If the optional dependency leaves a valid collection with count zero, the function reads no array entries. A nonnull fallback whose key matches is returned.

5. **Single-entry match.**  
   With count one and a matching entry at index zero, that entry is returned by the final scan. The fallback reference is not read.

6. **Two-entry match.**  
   With ascending keys `10` and `20`, requesting `20` examines index zero and then index one, returning the latter. No midpoint iteration occurs.

7. **Immediate midpoint match.**  
   With ascending keys `10`, `20`, and `30`, requesting `20` selects index one as the midpoint. The key is compared, then the pointer slot at index one is reread for the result.

8. **Duplicate selection is not first-match selection.**  
   With five entries all keyed `7`, requesting `7` returns the entry read from midpoint index two, not necessarily index zero.

9. **Unsigned ordering matters.**  
   With keys `1`, `2147483648`, and `4294967295` in that order, requesting `4294967295` narrows toward the higher indices and returns the final entry. Treating the keys as signed would impose a different ordering and is not this function’s comparison rule.

10. **Fallback after array miss.**  
    With ascending array keys `10`, `20`, and `30`, a request for `25` finds no array match. A fallback keyed `25` is then returned; a null fallback or a fallback with another key produces zero.

11. **Array takes precedence.**  
    If both an array entry and the fallback match, the array result is returned without reading the fallback reference.

12. **Unsorted collection can miss an existing key.**  
    With array keys `30`, `20`, and `10`, requesting `30` examines the middle key and retains the upper-index region, excluding index zero. If the fallback does not match, the result is zero despite the matching array entry.
