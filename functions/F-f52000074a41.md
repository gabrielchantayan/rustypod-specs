# F-f52000074a41

## Purpose

F-f52000074a41 checks compatibility between two record references, obtains a value through local storage, prepares a destination record, transfers selected fields, updates a source field, conditionally changes context state, and delegates the remaining operation to F-a51e4d3e8ef4.

The observable return is a 32-bit status:

- Zero is returned only after F-a51e4d3e8ef4 returns zero.
- Two local rejection gates return `0x24` directly: a source-only restriction and an existing-destination compatibility check.
- Nonzero statuses from checked dependencies are propagated after common failure handling. Those statuses can also equal `0x24`.

Consequently, the numeric return value `0x24` alone does not identify a local compatibility rejection or establish whether cleanup occurred.

Failure handling is asymmetric. Local rejection bypasses common failure handling. A checked dependency failure invokes two cleanup-position calls and clears three outputs. Earlier changes are not explicitly rolled back.

“Acquire,” “prepare,” “transfer,” and “cleanup” describe apparent roles. Application meaning, resource ownership, and dependency internals remain unestablished.

### Local storage

Two distinct local regions matter:

- A 32-bit acquisition result location whose address is passed to F-80c2f77a86cc.
- A separate four-byte scratch region whose address is passed to F-a51e4d3e8ef4.

The acquisition result location is not an immutable snapshot. Its contents are read at several later points separated by dependency calls. No supplied dependency contract establishes that its address is not retained or that its contents remain stable.

Neither region is visibly initialized before its respective first dependency call. The caller relies on acquisition producing usable contents when it reports success. The scratch contents are not subsequently inspected by this function.

### Preconditions

No explicit null, bounds, alignment, or access-permission checks are present.

Defined execution requires readable source and destination reference locations at entry, a usable captured source address, and valid storage for every access reached on the selected path. A successful destination-acquisition call must leave a usable destination address for subsequent operations; the function does not check that requirement.

An initially zero destination address is explicitly accommodated. A zero source address is not.

Offsets and address-like values are represented in a 32-bit setting. The supplied body does not establish valid behavior for address overflow, inaccessible storage, different pointer widths, or violated dependency requirements. It also does not establish byte order for multibyte memory operations.

## Behavior

### Entry capture and source-only rejection

The function performs these entry reads in order:

1. Capture the record address contained in the source reference.
2. Read the source discriminator at offset `9`, widening it as unsigned.
3. Capture the record address contained in the destination reference.

If the captured source discriminator is `1`, the function reads the source marker at offset `8`. A marker other than the all-ones byte causes immediate return of `0x24`.

That rejection invokes no dependency and performs no direct write. Outputs are not cleared. The destination reference has already been read, even though destination compatibility has not yet been checked.

The captured source discriminator is retained for initial compatibility checking. Later discriminator reads are separate accesses and need not observe the same byte.

### Existing-destination compatibility

An initially zero destination address skips this stage.

For an initially nonzero destination, the function calls F-4055be9c3f18 with the captured destination address. Compatibility is evaluated with short-circuiting:

- If the returned 32-bit value differs from the requested value, reject.
- Otherwise, read the destination discriminator at offset `9`. If it differs from the captured source discriminator, reject.
- Otherwise, read and compare the destination and source markers at offset `8`. If they differ, reject.

The relative evaluation order of the two marker reads is **not established**. Both occur only after the discriminator comparison succeeds.

Each rejection returns `0x24` without common failure handling or direct output clearing. F-4055be9c3f18 has already run, so these paths cannot be described as free of all indirect effects.

The captured destination address remains the address used throughout this check. The destination reference is not reloaded between comparisons.

### Acquisition

After validation passes, F-80c2f77a86cc receives the context and the address of the local 32-bit acquisition result location.

A nonzero return enters common failure handling with that status. The function does not read the acquisition result on that failure path.

A zero return permits subsequent processing. The visible caller assumes usable contents are then present, but initialization and continued stability are not independently guaranteed by the supplied evidence.

### Preparation for an initially existing destination

This stage is selected using the destination address captured at entry, not a later reference value.

If that captured address is nonzero:

1. Read the then-current acquisition result and pass that 32-bit value, followed by the captured destination address, to F-946cac4b59bc. Its return is not checked.
2. Call F-f7c5b7585b2d with context, destination reference, zero, and `0x100`, in that order.
3. If F-f7c5b7585b2d returns nonzero, enter common failure handling.

The first helper receives the originally captured destination address even if an earlier dependency has changed the destination reference.

Dependencies in this stage may have effects not visible in their return values. In particular, the acquisition result is not assumed unchanged after these calls.

### Destination acquisition and reload

F-b00cf3174ef8 receives:

- Context.
- A fresh read of the then-current acquisition result.
- Destination reference.

This acquisition-result read occurs after any existing-destination preparation calls. It is not specified to equal the value passed during that preparation.

A nonzero status enters common failure handling. On zero, the function reloads the destination address from the destination reference. Subsequent destination operations use this reloaded address, without further reloading that reference.

There is no explicit nonzero or validity check on the reloaded address.

### Record updates

After destination acquisition succeeds, the following operations occur in order:

1. Pass the requested value and reloaded destination address to F-946cac4b59bc.
2. Call F-4055be9c3f18 with the captured source address plus `4`.
3. Pass that returned 32-bit value and the reloaded destination address plus `4` to F-946cac4b59bc.
4. Read the current source marker at offset `8` and write that byte to destination offset `8`.
5. Read the current source discriminator at offset `9` and write that byte to destination offset `9`.
6. Read the then-current acquisition result and pass it, followed by the captured source address plus `4`, to F-946cac4b59bc.

The source-field read therefore precedes the later request to write the acquisition result into that source field. The destination receives the helper-returned value, not necessarily a raw memory copy.

The source-byte copies use reads made at this stage. They do not reuse validation snapshots. No dependency contract establishes that earlier calls preserve these bytes.

The acquisition result used for the source-field update can differ from either earlier use. Its read occurs after destination acquisition, destination field-helper calls, and the two byte-copy operations.

No bulk record copy is present, and no direct copying of other record locations is established.

### Conditional context updates

Next, the function reads the destination marker at offset `8`.

If the marker is not the all-ones byte, the context-update branch is skipped. If it is all ones, the function calls F-4055be9c3f18 with the reloaded destination address plus `4`.

Only if that helper returns zero does the function:

1. Read the then-current acquisition result and store it as 32 bits at context offset `0x14`.
2. Read the 32-bit context field at offset `0x2c`, OR it with mask `1`, and write the 32-bit result back.

The context store does not necessarily use the same value as the earlier source-field update. The intervening F-946cac4b59bc call and conditional F-4055be9c3f18 call do not have established preservation guarantees for the escaped acquisition result location.

The flags operation sets bit zero while preserving the other bits from that particular read. It is not established as atomic.

Both context writes precede final delegation. No visible rollback restores them after a later failure.

### Final delegation

F-a51e4d3e8ef4 receives these eleven arguments in order:

1. Context.
2. Reloaded destination address.
3. Captured source address.
4. Forwarded argument 5.
5. Forwarded argument 6.
6. Forwarded argument 7.
7. Forwarded argument 8.
8. First output address.
9. Second output address.
10. Address of the local four-byte scratch region.
11. Third output address.

A zero return causes immediate return of zero. There is no subsequent cleanup call or direct output write.

A nonzero return enters common failure handling with that status.

### Common failure handling

Every nonzero checked status from acquisition onward follows this sequence:

1. Call F-b0f922796692 with context and destination reference.
2. Call F-b0f922796692 with context and source reference.
3. Store a 16-bit zero to the first output.
4. Store a 32-bit zero to the second output.
5. Store a 16-bit zero to the third output.
6. Return the status that selected this path.

The cleanup-position calls’ results are ignored. Both calls occur even when acquisition failed before destination preparation or acquisition was attempted.

This sequence assumes calls and memory accesses return normally. Faults, exceptions, and nonlocal control transfers are not handled in the visible body.

## Side effects

Direct caller-visible writes consist of:

- Destination marker and discriminator bytes after successful destination acquisition.
- Conditional 32-bit context writes at offsets `0x14` and `0x2c`.
- Output clearing on common failure, using widths of 16, 32, and 16 bits in that order.

Dependencies receive record addresses, reference locations, context, outputs, and local-storage addresses. Their additional memory and global-state effects are unknown. The function also requests helper-managed field writes, but the exact resulting representation is not established.

No explicit transaction, undo sequence, or ownership transfer is established. In particular:

- F-b0f922796692 is not proven to free, release, null, or decrement anything.
- No separately identifiable release of acquisition-result contents is visible.
- Passing a reference does not establish that its contents remain unchanged.
- Passing local storage does not establish that a dependency avoids retaining its address.

Local storage has only the lifetime of this invocation. No valid post-return use of either local address is established.

Aliasing is not checked or rejected. If references, records, context, or outputs overlap, the operation sequence still applies, but independent-object interpretations may fail. The two cleanup-position calls still occur when the reference arguments designate the same location. Overlapping outputs are cleared in first–second–third order.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume valid reached accesses and normally returning dependencies.

1. **Source-only rejection.** With source discriminator `1` and marker `0`, return `0x24`. No dependency is called and no direct write occurs.

2. **All-ones source marker.** With source discriminator `1` and marker `0xff`, the source-only gate passes. Later compatibility checks or dependencies can still fail.

3. **Requested-value mismatch.** For an initially nonzero destination, if its first helper result differs from the requested value, return `0x24` without reading its discriminator or performing marker comparison. Common failure handling is skipped.

4. **Discriminator mismatch.** If the requested value matches but destination discriminator differs from the captured source discriminator, return `0x24`. Neither marker is read for the compatibility comparison.

5. **Marker comparison.** After the requested value and discriminator match, unequal marker bytes cause local rejection. Either marker may be read first; an acceptance trace must not require destination-before-source ordering.

6. **Dependency status `0x24`.** If validation passes and F-80c2f77a86cc returns `0x24`, call F-b0f922796692 for destination and source, clear all three outputs at their specified widths, and return `0x24`. This has the same numeric result as local rejection but different side effects.

7. **Initially absent destination.** An initially zero destination skips existing-destination validation and preparation. Successful acquisition is still followed by F-b00cf3174ef8 and a destination-reference reload.

8. **Changing acquisition storage.** Suppose an initially existing destination is accepted, acquisition leaves value A, and later dependency effects change the live result location to B before destination acquisition. The preparation helper receives A, while F-b00cf3174ef8 receives B. If the location later contains C at the source-field update and D at the conditional context store, those operations use C and D respectively. This example is conditional on such dependency effects; it does not assert they occur.

9. **Conditional context update.** If the destination marker reads as `0xff` and its offset-`4` helper result is zero, store the acquisition-result contents observed at that point to context offset `0x14`, then set bit zero at offset `0x2c`, before final delegation.

10. **Late failure.** A nonzero final-delegation status triggers cleanup and output clearing. The visible body does not restore earlier record or context state.

11. **Final success.** If all checked dependencies return zero, return zero after final delegation, without subsequent cleanup or direct output clearing.
