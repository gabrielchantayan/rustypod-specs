# F-fb875b7a8097

## Purpose

F-fb875b7a8097 initializes a destination object, recognizes an input using up to two signature checks, obtains a region descriptor, and selects one of two region-acquisition paths.

One path derives a region address from input fields. The other requests a region address from a dependency and then attempts a transfer. Successful acquisition publishes start, current, and end addresses in the destination. Failure conditionally invokes cleanup and clears the stored region address.

**Established behavior:** initialization order, signature-status branching, descriptor selection, acquisition branching, metadata writes, range publication, cleanup gating, and packed return composition.

**Inferred intent:** the signature labels and rejection diagnostic suggest Type 1 font processing. The acquisition paths and cleanup flag suggest different storage-ownership arrangements. Neither inference establishes format validity, ownership transfer, or lifetime obligations.

## Interface

The initializer context must allow a 32-bit pointer read at byte offset `+0x04`. The referenced object must allow a callable-address read from its first 32-bit slot. The resolved callback receives the destination, two zero-valued arguments, and the original resource token. Its return value is not inspected.

Normal completion requires valid memory accesses and normally returning dependency calls on the executed path. The callback may require more destination storage or stronger object invariants than the visible direct accesses establish.

## Behavior

### Initialization

The indirect initialization callback runs before direct destination initialization.

After its normal return, the function performs these writes in order:

1. Store the input address at destination `+0x48`.
2. Clear the 32-bit extent at `+0x50`.
3. Clear the 32-bit region address at `+0x4C`.
4. Clear the 32-bit field at `+0x58`.
5. Clear the 32-bit field at `+0x54`.
6. Clear the byte at `+0x5C`.
7. Clear the byte at `+0x5D`.
8. Clear the byte at `+0x5E`.

It does not directly clear the published start, current, or end fields at this stage.

### Signature checks

The first F-35285c1570df call receives the input, the first embedded signature operand, and comparison-size argument 14.

- Status zero proceeds to preparation.
- Status exactly 2 selects a second signature check.
- Any other status proceeds directly to failure handling.

The second check receives the input, a different embedded signature operand, and comparison-size argument 10.

- Status zero proceeds to preparation.
- Any nonzero status triggers the diagnostic decision and then failure handling.

For the diagnostic decision, the function obtains the current globally referenced diagnostic-state base and reads the signed 32-bit field at base `+0x84`.

- Values below 2 suppress the diagnostic call.
- Values at least 2 cause F-4457a9a44a68 to receive the embedded Type 1 font rejection diagnostic.

The diagnostic return value is ignored. The failed second-check status is not explicitly replaced by that return value.

Neither a successful signature check nor the supplied size argument establishes complete format validation. Exact signature bytes and the comparison dependency’s interpretation of its arguments remain unresolved.

### Preparation and description

After either signature succeeds, F-e40a3ceddab2 receives the input and zero.

A nonzero result proceeds to failure handling. A zero result permits F-680428c8d305 to run with:

- The input.
- Writable access to the token copy.
- Writable access to the descriptor.

A nonzero description result proceeds to failure handling. Descriptor changes already made are not directly rolled back and remain relevant to the upper return half.

On a zero description result, marker recognition uses only the token copy’s low 16 bits. The pattern `0x8001`, interpreted as signed 16-bit `−32767`, selects the marker case.

For the marker case:

- Write byte value 1 at destination `+0x5C`.
- Retain the descriptor supplied by description.

For every other low-16-bit pattern:

1. Call F-e40a3ceddab2 again with the input and zero.
2. On nonzero status, proceed to failure handling.
3. On zero status, read the current 32-bit input field at `+0x04` and replace the descriptor with it.

The token copy’s high 16 bits do not affect marker selection. Modification of this copy does not replace the original token used for allocation and cleanup.

### Acquisition-mode selection

After description and any fallback processing, the function reads the current 32-bit input field at `+0x14`.

The timing is significant: earlier dependencies may have changed the input selector or the fields subsequently used for acquisition.

### Input-derived-address path

When the selector is zero:

1. Add the 32-bit input fields at `+0x00` and `+0x08`.
2. Store the resulting 32-bit address at destination `+0x4C`.
3. Store the descriptor at destination `+0x50`.
4. Write byte value 1 at destination `+0x5D`.
5. Call F-d8528f8db63b with the input.

A zero result proceeds to range publication. A nonzero result proceeds to failure handling.

Neither allocation nor transfer is called on this path. The acquisition flag is set before F-d8528f8db63b runs, but failure handling later reads the current flag. The branch alone does not guarantee that cleanup will be skipped if a dependency changes that flag.

The relative read order of the two address-addition operands is not independently established.

### Allocation-and-transfer path

When the selector is nonzero, the status slot already contains zero: either description succeeded and selected the marker case, or fallback preparation succeeded.

The function then:

1. Calls F-3ce007b692cc with the original resource token, the descriptor, and writable access to the zero-valued status slot.
2. Stores the returned 32-bit region value at destination `+0x4C`.
3. Tests the status slot’s contents after the call.
4. Proceeds to failure handling if the slot is nonzero.
5. Otherwise calls F-0c21b5cad025 with the input, the returned region value, and the descriptor.
6. Uses the transfer result as the status.
7. On nonzero transfer status, proceeds to failure handling.
8. On zero transfer status, stores the descriptor at destination `+0x50` and proceeds to range publication.

The allocation dependency’s output guarantees are unknown. In particular:

- The caller supplies a zero-valued status slot; it does not require a visible dependency write before considering transfer.
- Normal return without modifying that slot causes transfer to be attempted.
- A nonzero region return does not independently establish success.
- A zero region return does not independently establish failure.
- The returned region value is stored before the status test, including when the slot is nonzero.

No independent null-address check appears before transfer. The extent is not directly installed on this path until transfer succeeds.

### Range publication

After successful acquisition, the function reads the current region address at destination `+0x4C`. It then performs these 32-bit writes in order:

1. Write that address at `+0x04`.
2. Write that address at `+0x00`.
3. Write that address plus the current extent at `+0x50` to `+0x08`.

Thus publication uses destination metadata after the preceding dependencies have run. It need not publish an unchanged copy of the address originally calculated or returned.

Both the input-derived address addition and the end-address addition use 32-bit results. No overflow check is visible. The represented arithmetic wraps modulo \(2^{32}\); this does not establish that a wrapped result describes valid memory.

### Failure handling

Failure handling reads the current byte at destination `+0x5D`.

If it is zero:

1. Read the current region address at destination `+0x4C`.
2. Call F-bf7242c98d06 with the original resource token and that address.
3. After normal return, clear the 32-bit region-address field.

If the flag is nonzero, both the cleanup call and the clearing write are skipped.

There is no nonzero-address guard. With otherwise unchanged initialized state, an early failure passes region value zero to cleanup.

Failure handling does not directly clear the extent, marker flag, stored input address, or published range. It is not a transactional rollback. Dependencies may affect the cleanup decision or the address passed to cleanup.

### Marker-selected input-derived region

### Zero region with unchanged status

### Diagnostic-state timing and signedness

Assume the first check returns 2. During the second check, the globally referenced diagnostic-state base changes, and the check returns 7.

The diagnostic decision uses the new base. A signed field value of 2 permits the diagnostic call; values 1, 0, and `−1` suppress it. Bit pattern `0xFFFFFFFF` is interpreted as `−1`, not a large unsigned value.

All these cases proceed to failure handling. With unchanged initialized metadata, cleanup receives zero and the return low half remains 7.

### Other failure boundaries

If the first signature check returns 7, there is no second check, diagnostic-state access, preparation, description, or acquisition. With unchanged initialized state, cleanup receives zero; the upper return half remains the input-address bit pattern.

If F-d8528f8db63b fails while leaving the acquisition flag set, cleanup and publication are skipped, and installed region metadata remains.

If allocation permits transfer but transfer fails while the flag remains zero, cleanup receives the stored region address. The allocated path has not yet directly installed its extent.

### Wrapped end address
