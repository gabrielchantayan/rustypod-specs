# F-00af20be5d65

## Purpose

F-00af20be5d65 coordinates an alignment-dependent, chunked operation over two unsigned address-like values and an unsigned requested length. It selects configuration values, reads external capacity state, obtains two control values through a setup dependency, and issues two dependency calls for each chunk. After normal loop termination, it calls a final dependency and returns zero.

The visible operations establish how configuration, chunk lengths, address progression, and call sequencing are determined. They do not establish that data is copied, that any call waits for completion, or that the final call releases a resource.

**Inferred intent:** alignment-aware transfer coordination. The direction, units, completion guarantees, and underlying operation remain dependency-level questions.

## Interface

### Inputs

The function accepts three unsigned 32-bit values:

| Input | Established role |
|---|---|
| First address value | Supplied as the second address argument to the chunk dependency; increased by each chunk length. |
| Second address value | Supplied as the first address argument to the chunk dependency; increased by each chunk length. |
| Requested length | Participates in alignment selection and grouping selection, controls loop entry, and is reduced by each chunk length. On normal termination, the chunk lengths sum to this initial value. |

The sum is expressed in the requested length’s own units. The supplied evidence does not establish that those units are bytes or that the input counts chunks.

The two addresses are integer values at this interface. The function does not directly dereference them. Their interpretation as memory addresses, device locations, or another addressing scheme is unresolved.

There is no visible rejection of zero addresses, inaccessible locations, overlapping regions, invalid ranges, or wrapping address arithmetic.

### Output and failure reporting

The function returns a 32-bit zero whenever execution reaches its return.

No dependency result is used to select a branch, stop processing, or change that return value. Consequently, zero is not established as proof of successful setup, successful processing, completion, or release.

A dependency that fails to return prevents subsequent actions. A zero retained capacity can also prevent termination for a nonempty request.

### Control-slot storage

Before setup, the function initializes two separate invocation-local, writable 32-bit slots:

1. The primary slot is set to zero.
2. The secondary slot is set to `0xffffffff`.

Setup receives the primary slot’s address followed by the secondary slot’s address. Their relative placement, spacing, and padding are not established interface properties.

The slots remain local to this invocation. Passing their addresses does not establish ownership transfer, permission for use after return, or that setup will replace either initial value.

### Arithmetic and conversion rules

The input values, remaining length, retained capacity, chunk lengths, and address progression are treated as unsigned 32-bit quantities.

- Address addition wraps modulo \(2^{32}\).
- Capacity comparison is unsigned.
- Chunk subtraction cannot underflow when the selected chunk is the unsigned minimum of capacity and remaining length.
- Length normalization uses unsigned right shifts.
- The widest-mode capacity is the 32-bit result of shifting the base capacity left by two; high bits do not survive in the retained value.
- The primary control argument is the primary slot masked with `0xff`, giving a value from 0 through 255.
- The secondary control argument is obtained by conversion to a plain character-sized value, followed by conversion to a signed integer argument.

The secondary conversion is not equivalent to the explicit primary mask without target-specific assumptions. The supplied evidence does not independently establish plain-character width, signedness, or every out-of-range conversion detail. Under an eight-bit signed-character interpretation that preserves the low byte, values with that byte from `0x80` through `0xff` become negative. Under an eight-bit unsigned-character interpretation, the corresponding arguments are 128 through 255.

## Behavior

### Alignment and normalization

The function combines both address values and the requested length with bitwise OR. Wider-mode eligibility therefore depends on all three inputs, not just the addresses.

The modes have the following precedence:

| Condition | Width selector | Normalized length |
|---|---:|---:|
| Both addresses and requested length are divisible by four | 2 | Requested length divided by four |
| All three are divisible by two, but the preceding condition is false | 1 | Requested length divided by two |
| Otherwise | 0 | Requested length unchanged |

The divisions are exact because each mode’s alignment condition includes the requested length.

The normalized length is used for grouping selection. It does not replace the original requested length as the total amount processed by the loop.

An odd address forces width selector 0 regardless of the other inputs. An odd requested length likewise forces width selector 0 even when both addresses are divisible by four.

### External-capacity reads and retained value

Two external capacity objects are relevant: the **base capacity** and the **alternate capacity**. The reads performed must be distinguished from the value ultimately retained:

| Mode | Reads performed, in order | Retained chunk capacity |
|---|---|---|
| Width selector 2 | Base capacity | Base value shifted left by two, retained as 32 bits |
| Width selector 1 | Base capacity, then alternate capacity | Alternate value |
| Width selector 0 | Base capacity | Base value |

In particular, the middle mode does **not** read only the alternate capacity. It first reads the base capacity and then replaces that retained value with the subsequently read alternate capacity. Although the base value does not determine middle-mode chunk lengths, its read is part of the visible operation sequence.

These reads occur after control-slot initialization and before setup. Grouping selection also precedes setup.

There is no visible capacity reread inside the loop. A later dependency changing an external capacity object does not, by itself, change the retained chunk limit for this invocation.

The concrete capacity values, declared storage widths, mutability, access properties, and units are not established. The visible function uses the selected result as an unsigned 32-bit limit in the same numerical units as the remaining length. The supplied representation establishes the read sequence, not any additional hardware or concurrency guarantees for those reads.

### Grouping selection

Grouping is selected from the normalized length:

- A value divisible by eight selects 7.
- Otherwise, a value divisible by four selects 3.
- Otherwise, the selector is 0.

Zero selects 7.

These values are configuration arguments. The function does not establish that they are literal group sizes, chunk lengths, or counts of operations.

### Setup

F-cbaa20924752 is called exactly once before the loop, including for a zero requested length.

Its arguments, in order, are:

1. `0x1c`.
2. Width selector.
3. Grouping selector.
4. `0x1c`.
5. The same width selector.
6. The same grouping selector.
7. Address of the primary control slot.
8. Address of the secondary control slot.

The repeated configuration triplets are identical. Their relationship to a particular endpoint is not established beyond their argument positions.

The function does not inspect a setup result. Later calls derive control arguments from whatever values remain in the slots, including the initial values if setup leaves them unchanged.

### Per-chunk processing

The loop executes while the remaining length is nonzero. Each iteration selects the unsigned minimum of the remaining length and retained capacity as its chunk length.

The established sequence for an iteration is:

1. F-ff7e5dd1f1c9 receives the current second address, current first address, chunk length, converted primary control, and converted secondary control.
2. After that call returns, F-dbb1e1e8544e receives the converted primary and secondary controls.
3. After that call returns, the second address is increased by the chunk length.
4. The first address is increased by the chunk length.
5. The remaining length is reduced by the chunk length.

Thus both per-chunk calls precede address advancement and length reduction. F-dbb1e1e8544e is called once for each chunk call, even when the selected chunk length is zero.

The control arguments are derived separately for each dependency invocation. The function makes no explicit control-slot writes after initialization, but setup receives addresses through which the slots can be accessed. The evidence does not establish that setup declines to retain those addresses or that later dependencies cannot modify the slots through retained access. A slot change between calls can therefore affect later control arguments.

The representation does not establish the evaluation order of separate argument expressions within one call.

No result from either per-chunk dependency changes the visible loop decisions. If both calls return normally, the local address and length updates proceed.

### Termination and final call

After the remaining length reaches zero, F-4cf587a7e13d is called with the converted primary and secondary controls. If it returns, F-00af20be5d65 returns zero.

For an initially zero length:

- Alignment, capacity reads, grouping selection, and setup still occur.
- Neither per-chunk dependency is called.
- The final dependency is called.
- The return is reached if setup and the final dependency return normally.

The final call is a normal-path action. No exception-safe or unconditional cleanup guarantee is established.

### Progress and boundary behavior

For a positive retained capacity, every entered iteration selects a positive chunk no greater than the remaining length. If dependencies return normally, the remaining length reaches zero. The chunk lengths then sum exactly to the initial requested length, without wraparound in that sum.

For zero retained capacity and nonzero remaining length:

- Every chunk length is zero.
- Both per-chunk dependencies are called repeatedly.
- Neither address advances.
- The remaining length stays unchanged.
- The final call and return are not reached while execution continues this way.

A zero capacity can result from a stored zero or from the widest-mode shift discarding high bits. For example, a base value of `0x40000000`, if available from its external storage, yields a retained widest-mode capacity of zero.

Chunk lengths are not rounded to a width or grouping boundary. A capacity incompatible with the selected width can produce chunks that advance initially aligned addresses to unaligned values. Whether external configuration prevents this is unresolved.

Address wraparound is independent of length progress. The function can complete its numerical length accounting while one or both address values wrap.

## Acceptance examples

These are conditional consequences of the static representation, not executed tests. Completing examples assume normally returning dependencies. Unless stated otherwise, control slots remain stable after setup.

### Widest mode and two chunks

For first address `0x1000`, second address `0x2000`, and requested length 32:

- Width selector is 2.
- Normalized length is 8.
- Grouping selector is 7.
- Only the base capacity is read.
- If its value is 4, retained capacity is 16.

The chunk calls receive:

| Call | First address argument | Second address argument | Length |
|---|---:|---:|---:|
| 1 | `0x2000` | `0x1000` | 16 |
| 2 | `0x2010` | `0x1010` | 16 |

Each is followed by F-dbb1e1e8544e. The final call follows the second pair. The chunk lengths sum to 32 in the requested length’s units.

### Middle mode preserves both reads

For first address `0x1002`, second address `0x2000`, and requested length 16:

- Width selector is 1.
- Normalized length is 8.
- Grouping selector is 7.
- The base capacity is read first.
- The alternate capacity is read second and supplies the retained limit.

If the alternate value is 6, chunk lengths are 6, 6, and 4. The earlier base value does not determine those lengths. Its read must not be omitted from the specified sequence.

### Odd requested length

For addresses `0x1000` and `0x2000` with requested length 9, width selector is 0, normalized length is 9, and grouping selector is 0. Only the base capacity is read. A base value of 4 produces lengths 4, 4, and 1.

### Grouping uses normalized length

For addresses `0x1000` and `0x2000` with requested length 16, width selector is 2 and normalized length is 4. Grouping selector is 3, not 7.

### Empty request still reads capacity

For first address `0x1002`, second address `0x2000`, and length zero, width selector is 1 and grouping selector is 7. The base read precedes the alternate read. Setup and the final call occur; neither per-chunk call occurs. Zero is returned if both dependencies return.

### Zero retained capacity

For any nonzero request with retained capacity zero, both per-chunk calls repeat with unchanged addresses and zero chunk length. No numerical progress occurs.

In widest mode, a base value of `0x40000000` produces this case through the 32-bit shift result.

### Address wraparound

For first address `0xfffffffc`, second address `0x1000`, requested length 8, and widest-mode retained capacity 4:

- The first chunk receives address arguments `0x1000` and `0xfffffffc`.
- The second receives `0x1004` and `0x00000000`.

This establishes integer progression, not validity of either operation.

### Control conversion and rereading

A primary slot value of `0x123456ab` produces primary control 171.

For secondary slot `0x123456ff`, an eight-bit signed-character interpretation preserving the low byte produces −1; an eight-bit unsigned-character interpretation produces 255.

If a dependency changes the primary slot from `0x123456ab` to `0x12345602` before the companion call, that later call receives primary control 2 rather than the preceding call’s 171.
