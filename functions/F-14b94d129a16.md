# F-14b94d129a16

## Purpose

F-14b94d129a16 constructs a result comprising a 40-byte header followed by 40-byte record slots. It selects caller-provided storage or obtains storage through F-83e6016208ce, decodes an input prefix and subsequent entry values, and delegates record construction to F-6c89f049f346.

Two input positions serve different roles:

- The **encoded-entry position** locates encoded entry values.
- The **data position** locates data passed to the record-building dependency.

The decoded prefix supplies both the upper bound for the encoded-entry position and the initial data position. The positions subsequently advance independently.

These are structural descriptions. A particular file format, encoding, or record meaning is not established.

## Interface

### Inputs

The function accepts five arguments:

| Argument | Representation and use |
|---|---|
| Context address | Address of at least three consecutive 32-bit words |
| Stopping threshold | Signed 32-bit value conditionally enabling the stopping predicate |
| Input address | Address of input bytes; no separate input length is supplied |
| Caller-storage address | Candidate result storage |
| Caller-storage size | Signed 32-bit value used in storage selection |

The accessed context fields are:

| Byte offset | Width | Use |
|---|---:|---|
| 0 | 32 bits | Argument to F-83e6016208ce and value copied into each initialized record |
| 4 | 32 bits | Low eight bits copied into each initialized record |
| 8 | Signed 32 bits | Storage-size calculation and initial record-limit calculation |

The supplied representation uses 32-bit integers and addresses, 16-bit halfwords, and 8-bit bytes. Layouts below describe that representation, not a portable layout for wider addresses.

The caller-storage size is neither an input-read bound nor an independently enforced per-record output bound.

### Return value

The function returns:

- The caller-storage address when that storage is selected.
- The nonnull address returned by F-83e6016208ce when dependency-provided storage is selected.
- Null if F-83e6016208ce returns null.

There is no separate status for exhausting the encoded-entry range, reaching the record limit, or stopping through the predicate.

### Result layout

The header occupies 40 bytes. Record storage begins immediately afterward.

| Header byte offset | Width | Assignment |
|---|---:|---|
| 0 | 32 bits | Context address |
| 4 | 16 bits | Initially a record limit; finally the completed-record count |
| 6 | 8 bits | Zero for caller storage; one for dependency-provided storage |
| 7 | 8 bits | One |
| 8 | 32 bits | Result address plus 40 bytes |
| 12–39 | 28 bytes | No explicit initialization by this function |

The byte values at offsets 6 and 7 do not establish ownership, release obligations, or validity semantics.

Before each record-building call, the function initializes these record fields:

| Record byte offset | Width | Assignment |
|---|---:|---|
| 16 | 32 bits | Current context word at offset 0 |
| 28 | 16 bits | Zero |
| 31 | 8 bits | Low eight bits of the current context word at offset 4 |
| 36 | 32 bits | Zero |

Other record bytes are not explicitly initialized here. F-6c89f049f346 may write additional fields or overwrite the listed values.

### Preconditions

All locations actually accessed must be readable or writable as appropriate, including accesses performed by dependencies. Required alignment must hold for the target’s word and halfword accesses.

The selected output storage must accommodate every header and record write that occurs. The storage-selection calculation does not prove this: capacity supplied by the allocation dependency is unknown, and the record limit can be affected by aliasing or dependency writes.

No input-length validation, address validation, non-aliasing requirement, or capacity validation is visible. Dependencies must leave execution able to continue using the addresses subsequently accessed; the function does not establish that they do so.

## Behavior

### 1. Calculate the requirement and select storage

The function first reads the signed 32-bit context quantity at offset 8. It adds two and then multiplies the result by 40, producing the calculated requirement.

The storage-selection condition has an additional arithmetic operation that is significant:

1. Subtract the signed caller-storage size from the signed calculated requirement.
2. Compare that subtraction result with zero.
3. If it is zero, select caller storage without evaluating the following less-than comparison.
4. Otherwise, compare the calculated requirement with the caller-storage size using a signed less-than comparison.
5. Select caller storage if that comparison succeeds; otherwise call F-83e6016208ce.

Thus, the condition is not unconditionally equivalent to a mathematical “requirement less than or equal to size” rule. That simplification is valid only where the requirement’s addition and multiplication **and the condition’s initial signed subtraction** are representable.

Overflow behavior for any of those signed 32-bit operations is unestablished. In particular, a representable requirement does not establish a defined storage-selection result. If the context quantity is −2 and the supplied size is −2,147,483,648, the requirement is zero, but subtracting the size from that requirement exceeds the signed 32-bit range. No branch outcome is established for that case under the supplied representation.

When caller storage is selected, the function writes zero to its byte at offset 6.

Otherwise, the function reads context word 0 and passes it as the sole visible argument to F-83e6016208ce. The calculated requirement is not passed to that dependency.

- A null dependency result causes an immediate null return.
- A nonnull result becomes the selected output address, and its byte at offset 6 is set to one.

The dependency’s allocation size, storage policy, initialization, and ownership rules are unknown. On allocation failure, this function performs no explicit header or record writes; dependency side effects remain possible.

### 2. Initialize the header

After writing the storage-selection byte, the function performs these operations in order:

1. Store the context address at result offset 0.
2. Read the context quantity at offset 8 again and write its value plus one, narrowed to 16 bits, at result offset 4.
3. Write one at result offset 7.
4. Establish the first record-slot address as result base plus 40 bytes.
5. Store that address at result offset 8.

The initial limit has the low-16-bit result of adding one to the context quantity. It is subsequently read as an unsigned 16-bit value. For example, a quantity of 65,535 yields an initial limit of zero.

This context read occurs after any allocation call and after earlier header writes. It need not observe the value used for the storage requirement: a dependency or overlapping storage may have changed it.

### 3. Decode the prefix

After header initialization, the function examines the first input byte.

- If the byte is below 128, its unsigned value becomes the decoded prefix and the encoded-entry position becomes one.
- Otherwise, F-887200f76f20 receives the input address and an address for a 32-bit decoded result. Its return value becomes the encoded-entry position.

On the direct-byte path, the byte is read for the comparison and again to obtain its value. No stability guarantee is established for externally mutable memory.

The data position is initialized to the decoded prefix. The prefix therefore acts both as an unsigned encoded-entry boundary and as the initial data offset.

There is no visible validity or success check on the decoder’s returned position or decoded value.

### 4. Admit and decode an entry

The completed-record count starts at zero. An iteration is admitted only while:

1. The unsigned encoded-entry position is less than the decoded prefix.
2. The completed-record count is less than the unsigned 16-bit value currently stored at header offset 4.

The encoded-position comparison precedes the limit comparison. If the first comparison fails, the second need not be evaluated. The header limit is read during loop-condition evaluation rather than being an immutable cached limit.

For an admitted iteration, the byte at the encoded-entry position is examined:

- A byte below 128 supplies the entry value directly, with advancement of one. The direct path reads the byte again for its value.
- Otherwise, F-887200f76f20 receives that input address and an address for a 32-bit decoded entry value. Its return supplies the advancement.

The advancement is added to the unsigned 32-bit encoded-entry position before the stopping decision.

This is not a checked length calculation. Zero advancement can leave the position unchanged. A return with a negative signed representation participates in unsigned arithmetic, and the addition can wrap modulo \(2^{32}\).

There is no post-decode check that the new position remains within the prefix boundary. The admitted entry can still reach construction after advancing to or beyond that boundary.

### 5. Apply the conditional stop

The current data position is interpreted as signed 32-bit for comparison with the stopping threshold.

Only if the threshold is less than or equal to that signed value does the function call F-445198130f42 with the decoded entry value.

- A positive signed return stops traversal.
- Zero or a negative return permits construction.
- If the threshold comparison fails, the predicate is not called and construction proceeds.

This stopping decision follows entry decoding and encoded-position advancement, but precedes the four explicit record-initialization writes.

An entry rejected by the predicate is not counted. The threshold is therefore not an unconditional maximum data position.

For data positions whose unsigned value exceeds the signed 32-bit maximum, the exact unsigned-to-signed conversion behavior is not independently established by the supplied evidence.

### 6. Initialize and construct a record

For an entry that passes the stopping decision, the function performs these operations in order:

1. Read context word 4 and write its low eight bits to record offset 31.
2. Read context word 0 and write it to record offset 16.
3. Write a zero halfword at record offset 28.
4. Write a zero word at record offset 36.

It then calls F-6c89f049f346 with:

- Input address plus the current data position.
- The decoded entry value.
- The current record-slot address.

The dependency’s signed 32-bit return is added to the unsigned 32-bit data position. The addition uses unsigned arithmetic and may wrap. No local check rejects zero, negative, or unusually large returns.

The record-slot address then advances by 40 bytes, and the completed-record count increases by one. The next iteration reevaluates the loop conditions.

A builder return that might signify an error under some unknown dependency convention is not treated as a local error: the record is still counted.

### 7. Finalize

After ordinary loop termination or a positive predicate result, the function stores the completed-record count, narrowed to 16 bits, at header offset 4 and returns the result address.

That field no longer exposes the initial limit. Neither input position is returned separately.

## Side effects

### Observable ordering and aliasing

The established ordering is:

1. Read the context quantity and evaluate storage-selection arithmetic and comparisons.
2. If required, read context word 0 and call the allocation dependency.
3. Write the selected storage’s byte at offset 6.
4. Initialize the remaining identified header fields.
5. Read or decode the prefix.
6. For each admitted entry: decode it, advance the encoded-entry position, conditionally call the predicate, initialize its record, call the builder, advance the data position, advance the record address, and increment the count.
7. Replace the header limit with the completed-record count.

This ordering matters when addresses overlap. Header writes precede the first input-byte read. The storage-selection byte precedes the second read of the context quantity. Within each record, the offset-31 byte write precedes the read and write associated with context word 0.

Consequently, overlapping input, context, header, or record storage can affect later reads. The function neither prevents such overlap nor guarantees useful behavior for every overlapping arrangement.

Dependencies are not assumed to preserve globals, input bytes, context fields, header fields, record contents, or other reachable memory.

### Ownership and lifetime

The function contains no explicit release operation for the input, context, caller storage, selected output storage, or record-associated data.

The result stores the context address. Whether later consumers dereference it, and therefore how long it must remain valid after return, is not established.

Selecting dependency-provided storage and setting offset 6 to one does not prove an ownership transfer or identify a matching release operation. Dependencies’ own memory-management effects are unknown.

### Errors and partial progress

A null allocation result is the only explicit failure return.

No separate local handling is visible for malformed encodings, truncated input, insufficient output storage, invalid addresses, unsuitable dependency returns, or arithmetic overflow.

A predicate-triggered stop returns the partially populated result normally. Earlier writes and dependency effects are not rolled back. The rejected entry has no explicit record initialization, although dependencies may independently have modified the same storage.

## Acceptance examples

These examples are conditional static consequences, not executed tests. Unless otherwise stated, accessed memory is valid, storage is sufficient, relevant values remain stable, and dependencies do not otherwise change the described state.

### Exact calculated size

With context quantity 2 and caller-storage size 160:

- The addition produces 4, multiplication produces 160, and initial subtraction produces zero.
- All three arithmetic operations are representable.
- Caller storage is selected without evaluating the signed less-than alternative.
- F-83e6016208ce is not called.
- Header offset 6 becomes zero, and the initial limit is three.

### Smaller caller storage and allocation failure

With context quantity 2, supplied size 159, and a null return from F-83e6016208ce:

- The requirement is 160.
- The initial subtraction produces one.
- The signed comparison of 160 with 159 fails.
- The allocation dependency is called, and the function returns null.
- This function performs no explicit result-header or record writes.

### Representable requirement but overflowing condition subtraction

With context quantity −2 and supplied size −2,147,483,648:

- The requirement’s addition and multiplication produce zero without overflow.
- The condition first attempts to subtract −2,147,483,648 from zero.
- That mathematical result is outside the signed 32-bit range.

No storage-selection branch, allocation call, or returned result is established for this case. It must not be classified solely by a mathematical comparison between zero and the supplied size.

### Empty traversal

With a direct prefix of zero, the encoded-entry position starts at one and fails the unsigned boundary comparison. No entry decoder, predicate, or record builder is called. The final count is zero.

A direct prefix of one likewise admits no iteration because the initial position equals the boundary.

### Two direct entries

Assume prefix 3, following entry bytes 7 and 8, a stable limit of at least two, threshold 100, and builder returns of 2 and 3.

The builder receives input plus 3 with entry 7, then input plus 5 with entry 8. The predicate is not called because data positions 3 and 5 are below the threshold.

The final count is two. The encoded-entry position reaches three and ends traversal.

### Predicate rejects the first entry

With prefix 3, threshold 3, a limit permitting entry admission, and a positive first predicate return:

- The entry is decoded and the encoded-entry position advances.
- None of the four explicit record-initialization writes occurs for that entry.
- The record builder is not called.
- The final count is zero.

### Initial-limit truncation

With context quantity 65,535 and supplied size 2,621,480, the requirement arithmetic is representable and the selection subtraction is zero. The initial limit becomes zero.

The prefix is still decoded, but no record iteration occurs unless an intervening effect changes the header limit. The final count is zero.

### Zero builder advancement

If a constructed record’s builder returns zero, the record is counted and the record address advances by 40 bytes. The data position remains unchanged, so a later builder call may receive the same data address.
