# F-61e691d947b4

## Purpose

F-61e691d947b4 selects one 24-byte record from either a reusable-record chain or a sequential record region, creating a new region when the current region is exhausted. It then clears selected fields in the chosen record.

The selection is internal: the function has no explicit return value and does not publish the selected record through a separate output parameter. Its externally visible results are changes to the caller-supplied state, writes to the selected record, and, when necessary, two calls to F-871e64ddc6de.

“Reusable record,” “region,” and “capacity” describe the apparent roles of the observed fields. They are inferred intent, not evidence of a complete allocation, lifetime, or ownership protocol.

## Interface

### Input and result

The function accepts one address identifying a mutable state object. The visible representation contains four consecutive 32-bit words:

| Byte offset | Role in this contract |
|---|---|
| 0 | Address of the current region descriptor, or zero |
| 4 | Address of the first reusable record, or zero |
| 8 | Sequential selection cursor |
| 12 | Sequential region endpoint |

Addresses are represented using 32-bit words in the supplied evidence. Record fields and descriptor fields described as words are also 32 bits wide. The evidence does not establish a portable interface for wider addresses.

The function returns no explicit result. There is no visible success flag, selected-record address, or error code.

### Record representation

A selected record occupies a nominal 24-byte slot. This function accesses only the following parts:

| Byte offset | Access |
|---|---|
| 0 | One-byte write of zero |
| 4 | Four-byte write of zero |
| 8 | Four-byte write of zero |
| 12 | Four-byte read when selecting a reusable record; four-byte write of zero afterward |

Bytes 1–3 and 16–23 are not initialized by the function. The record must therefore not be treated as wholly cleared.

For a reusable record, the word at offset 12 supplies the address of the next reusable record before that word is cleared.

### Region descriptor representation

A region descriptor occupies 12 bytes:

| Byte offset | Role |
|---|---|
| 0 | Address of the preceding descriptor |
| 4 | Region capacity, measured in 24-byte records |
| 8 | Address supplied for the region’s record storage |

An existing descriptor’s capacity is read only when sequential storage is exhausted and a new region is needed. A new descriptor is populated after both dependency calls have returned.

### Preconditions for normal completion

The state object must support the required four-byte reads and writes. Every nonzero record or descriptor address that is dereferenced must identify appropriately accessible storage.

On the reusable-record path, the selected record must support reading its word at offset 12 and all four initialization writes.

On the sequential path, a cursor unequal to the endpoint is taken as sufficient reason to use the cursor. The function does not independently establish that the cursor lies inside a valid region, that a full record remains, or that cursor advancement is safe.

On the region-creation path, normal completion requires usable results from both dependency calls and storage sufficient for subsequent writes. The function contains no visible checks enforcing these conditions.

Alignment, address validity, non-overlap, and allocation-success requirements are obligations of the surrounding environment rather than validated input conditions.

## Behavior

### Selection priority

The reusable-record chain has priority over sequential storage.

The function first reads the reusable-record address at state offset 4. If it is nonzero, that address becomes the selected record. The sequential cursor, endpoint, and descriptor capacity do not participate in selection on this path.

If the reusable-record address is zero, the function reads the sequential cursor and compares it with the endpoint. Equality triggers creation of a new region. Any inequality selects the existing cursor without a bounds or ordering check.

### Selecting a reusable record

For a nonzero reusable-record address:

1. The function reads the four-byte successor address at offset 12 of that record.
2. It writes that successor address to state offset 4.
3. It initializes the selected record as described below.

The chain update occurs before any of the record-clearing writes. In particular, the successor is read before its storage location is zeroed.

There is no chain traversal. A successor of zero, a self-reference, or another unusual address is copied into the state without validation. Such values affect later behavior, but this invocation does not inspect the successor record.

Absent aliasing, the descriptor address, sequential cursor, and endpoint remain unchanged on this path.

### Selecting an existing sequential slot

If the reusable-record address is zero and the cursor differs from the endpoint:

1. The current cursor becomes the selected record address.
2. State offset 8 is updated to the selected address plus 24 bytes.
3. The selected record is initialized.

The cursor update precedes record initialization.

The comparison is equality-only. A cursor numerically beyond the endpoint, misaligned to the nominal stride, or close enough to an address boundary to wrap is not rejected by this function. Such inputs do not become valid merely because the function accepts the comparison outcome.

### Choosing a new region’s capacity

If the cursor equals the endpoint, the function reads the current descriptor address.

If that address is zero, the requested capacity is 32 records.

Otherwise, it reads the existing descriptor’s 32-bit capacity and computes two unsigned candidates:

- The old capacity plus 32.
- The old capacity plus its unsigned right-shift-by-one value plus its unsigned right-shift-by-three value.

The larger unsigned candidate is selected. Each shift discards the shifted-out bits. The additions use 32-bit arithmetic, including wraparound.

For ordinary non-overflowing capacities, the second candidate approximates 1.625 times the old capacity, with the two fractional contributions truncated separately. The comparison therefore normally chooses between an additional 32 records and this proportional increase.

That growth interpretation is not a guarantee near the 32-bit limit. Wrapped values are compared as unsigned 32-bit quantities, and there is no overflow rejection or requirement that the resulting capacity exceed the old capacity.

### Creating and publishing a new region

After choosing the capacity, the function calls F-871e64ddc6de twice, in this order:

| Call | First argument | Second argument |
|---|---:|---:|
| First | 12 | 0 |
| Second | Chosen capacity multiplied by 24, using 32-bit arithmetic | 0 |

The first result is used as the new descriptor address. The second result is used as the record-storage address.

The size multiplication can wrap. The function does not check that the resulting request represents enough bytes for the nominal capacity.

After both calls return, the function performs these state changes in order:

1. It writes the second call’s result to the new descriptor at offset 8.
2. It reads the current descriptor address from state offset 0 and writes that value to the new descriptor at offset 0.
3. It writes the chosen capacity to the new descriptor at offset 4.
4. It writes the new descriptor address to state offset 0.
5. It reads the storage address back from the new descriptor at offset 8 and uses that address as the selected record.
6. It writes the storage address plus the 32-bit capacity-times-24 result to state offset 12.
7. It writes the selected record address plus 24 to state offset 8.
8. It initializes the selected record.

The previous-descriptor link is therefore based on a state read made after both dependency calls. It is not necessarily the same descriptor address used earlier to choose capacity. Equating those values requires an additional assumption that the dependency calls do not alter the state.

No old descriptor or region is released by visible behavior. The descriptor link preserves the state’s then-current descriptor address.

### Initializing the selected record

All selection paths converge on the same four writes, in this order:

1. Four zero bytes at record offset 4.
2. Four zero bytes at record offset 8.
3. Four zero bytes at record offset 12.
4. One zero byte at record offset 0.

These are distinct writes, not evidence of a single atomic initialization. No stronger synchronization or publication guarantee is established.

The selected record’s other bytes are untouched by these explicit writes. In particular, clearing the first byte does not establish that the complete four-byte word beginning at offset 0 is zero.

## Side effects

### Caller state

Depending on the path, the function changes:

- The reusable-record head, when a reusable record is selected.
- The sequential cursor, when a sequential record is selected.
- The descriptor address and endpoint, when a new region is created.

The function does not visibly reset the reusable-record head while creating a region. Entry to that path follows an observed zero head, but unknown dependency side effects must not be silently excluded.

### Memory and ownership

The function writes to the selected record and, on the growth path, to a newly returned descriptor.

There is no visible release operation, rollback, or ownership-transfer notification. The state retains a descriptor address, descriptors retain preceding-descriptor addresses, and each new descriptor retains its storage address. These relationships do not establish who must eventually release either object or which operation would do so.

F-871e64ddc6de’s own memory and global-state effects are unknown. The explicit writes described here do not bound that dependency’s effects.

### Failure behavior

There is no visible recoverable-error path.

A zero or unusable first dependency result is subsequently used as a descriptor address after the second call returns. A zero or unusable second result is stored as the storage address and later used for record initialization. The precise platform-level outcome is not established.

If a dependency does not return normally, subsequent steps are not reached. No cleanup for the first result is visible if the second call fails or does not return.

Invalid addresses, unsuitable alignment, overlapping objects, and insufficient storage likewise have no explicit detection or recovery.

### Aliasing

The ordinary field descriptions assume the state, descriptor, and record storage do not overlap in ways that interfere with the listed accesses.

The function does not verify this assumption. If they do overlap, record clearing can overwrite state or descriptor fields already updated earlier in the invocation. The ordered accesses remain the available behavioral evidence; preservation claims for unrelated fields are conditional on noninterference.

## Dependencies

### F-871e64ddc6de

This is the only explicit dependency.

It is called only when the reusable-record head is zero and the sequential cursor equals the endpoint. In that case it is called twice: first with a size-like argument of 12, then with the wrapped 32-bit product of capacity and 24. Both calls receive zero as their second argument.

Established caller behavior:

- The first result is treated as a writable descriptor address.
- The second result is treated as a record-storage address.
- Neither result is checked before use.
- Both calls finish before descriptor initialization begins.

Inferred intent: the dependency supplies storage.

Unknowns include allocation semantics, alignment, initialization, failure signaling, ownership, release requirements, exceptions or nonlocal exits, and effects on globals or caller-accessible memory. The zero second argument has no established meaning beyond its value.

## Acceptance examples

These are conditional examples derived from static evidence, not executed tests. Unless stated otherwise, they assume valid non-overlapping storage, ordinary dependency returns, and no dependency interference with caller state.

### Reusable record takes precedence

Given a nonzero reusable-record head, even if the sequential cursor equals the endpoint:

- The current head is selected.
- Its offset-12 successor becomes the new head.
- F-871e64ddc6de is not called.
- The sequential cursor and endpoint are unchanged.
- The selected record receives the four ordered initialization writes.

### A reusable record can terminate the chain

Given a reusable record whose offset-12 word is zero, selection writes zero to the reusable-record head before clearing the record. The next invocation therefore cannot obtain another record from that chain unless something else updates the head.

### Existing sequential storage is consumed

Given a zero reusable-record head and a cursor different from the endpoint:

- The old cursor identifies the selected record.
- The cursor advances by 24 bytes.
- No descriptor capacity is read and no dependency call occurs.
- Bytes 1–3 and 16–23 of the selected record retain their previous values, absent other interference.

### Initial region creation

Given a zero reusable-record head, equal cursor and endpoint, and a zero descriptor address:

- Capacity is 32.
- Dependency arguments are first `(12, 0)`, then `(768, 0)`.
- The new descriptor links to zero if state offset 0 remains zero through the calls.
- The endpoint becomes storage base plus 768.
- The cursor becomes storage base plus 24.
- The record at the storage base is initialized.

### Minimum-increment growth

Given an exhausted region with capacity 32:

- The additive candidate is 64.
- The proportional candidate is 52.
- Capacity 64 is chosen.
- The second dependency request is 1,536 bytes.

### Proportional growth

Given an exhausted region with capacity 64:

- The additive candidate is 96.
- The proportional candidate is 104.
- Capacity 104 is chosen.
- The second dependency request is 2,496 bytes.

### Dependency mutation affects the descriptor link

If the dependency calls change state offset 0 to another descriptor address, and execution otherwise remains valid, the new descriptor links to that later address. Capacity may still have been computed from the descriptor observed before the calls.

### Invalid cursor ordering is not rejected

Given a zero reusable-record head and a cursor numerically beyond the endpoint, the function takes the existing-sequential-slot path because the addresses are unequal. It attempts cursor advancement and record initialization. This illustrates the missing bounds check, not a guarantee of valid execution.
