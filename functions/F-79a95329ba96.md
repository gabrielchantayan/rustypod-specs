# F-79a95329ba96

## Purpose

F-79a95329ba96 writes two caller-supplied four-byte values into storage addressed relative to a caller-supplied base. The first value is written at byte offset 8; the second is written at byte offset 12.

The established behavior is a pair of stores, not a complete object initialization operation. The supplied evidence does not establish the meaning of either destination field, the type or lifetime of the surrounding storage, or any invariant relating the two values.

## Behavior

### Normal execution

The function performs these observable memory operations in source order:

1. A four-byte store of the first value to the address formed from the base plus 8 bytes.
2. A four-byte store of the second value to the address formed from the base plus 12 bytes.

It then returns without a value.

There is no explicit read of either destination’s previous contents. Existing values do not select a branch, affect the replacement values, or suppress either store. There is no explicit read of other memory relative to the base.

For a valid ordinary-memory invocation, and in the absence of concurrent modification, successful completion leaves the first destination containing the first supplied value and the second destination containing the second supplied value. The earlier contents of those regions are overwritten.

The two destination regions are contiguous and nonoverlapping under ordinary, nonwrapping address arithmetic. The evidence contains no operation that combines them into a single eight-byte assignment. Consequently, the contract does not promise that the pair becomes visible as one indivisible update.

### Address formation and widths

Each destination is formed independently from the same base, using byte offsets 8 and 12. Neither displacement is scaled by an element size.

The stores are four bytes wide. The evidence does not show an eight-byte store, a bytewise copy loop, or a store whose width depends on an input.

The base is presented in an integer form before its derived addresses are used as destinations. This does not establish portable address arithmetic at the limits of the address space. In particular, the evidence does not justify choosing between wrapping arithmetic, signed-overflow behavior, or an implementation-specific integer-to-address interpretation.

The successful-use contract therefore requires that both destination addresses be meaningfully representable and valid in the target execution environment. Inputs near an address-space boundary have no independently established successful behavior.
