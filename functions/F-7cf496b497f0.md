# F-7cf496b497f0

## Purpose

F-7cf496b497f0 converts a bounded sequence of unsigned 16-bit input units into a variable-length byte representation and returns the number of **nonzero input units processed**.

Each nonzero input unit produces one, two, or three bytes according to its numeric value. The byte patterns match UTF-8 encoding for values outside the surrogate range. Surrogate-valued input units are encoded individually rather than paired or rejected. Consequently, the output is not necessarily well-formed UTF-8 when the input contains UTF-16 surrogate units.

Processing stops at either:

- Exhaustion of the supplied input-unit limit; or
- The first zero-valued input unit.

A zero input unit is written as a zero output byte, but is excluded from the return value. Exhausting the limit does **not** append a zero byte.

The established behavior is a bounded code-unit conversion, not a destination-capacity-aware encoder and not a complete UTF-16-to-UTF-8 conversion.

## Interface

The function has three inputs and a signed integer result.

| Input | Representation | Meaning |
|---|---|---|
| Destination | Pointer to writable 8-bit byte storage | Beginning of the output region |
| Source | Pointer to readable unsigned 16-bit units | Beginning of the input sequence |
| Limit | Signed integer | Maximum number of nonzero input units that may be processed before stopping; also bounds the number of source units inspected |

The result is the number of nonzero input units processed before termination. It is neither the output-byte count nor an error status.

### Widths and interpretation

The supplied representation identifies destination elements as 8-bit bytes and source elements as unsigned 16-bit units. Each source read therefore yields a value from 0 through 65,535.

The signed limit and result are represented by the integer type in the supplied material. Their exact ABI width is not independently established here; a 32-bit signed representation is consistent with that material but remains an ABI assumption. The observable contract does not require signed arithmetic to wrap: for a positive limit, the result increases only as far as that initial limit, and the remaining limit decreases only to zero.

Source units are read as native unsigned 16-bit values, not assembled from two explicitly ordered bytes. The source byte order and alignment requirements therefore depend on the execution environment. Output consists of individual bytes and has the byte order specified below.

### Storage requirements

For a positive limit, the caller must provide:

- A readable source unit at every position actually inspected.
- Writable destination storage for every byte actually emitted.
- Valid pointer arithmetic and any alignment required by the underlying environment.

No destination capacity is supplied or checked.

For disjoint, stable source and destination storage, reserving three destination bytes per permitted input unit is sufficient for every possible input sequence. A tighter allocation may be sufficient when the caller knows the input values and stopping position.

For a zero or negative limit, the function returns zero before reading source storage or writing destination storage. Pointer dereference validity is therefore unnecessary on that path.

There is no explicit non-overlap check. Non-overlapping storage is the straightforward precondition for interpreting the result as conversion of the source sequence as it existed at entry. With overlapping storage, output writes can alter source units that have not yet been read.

## Behavior

### Entry and stopping rules

The processed-unit count begins at zero.

Before each source read, the function checks whether the remaining limit is less than one. If so, it returns the current count without another source read or destination write.

Otherwise, it reads the current unsigned 16-bit source unit and selects an encoding based on that value.

For a nonzero unit:

1. Its complete one-, two-, or three-byte encoding is written.
2. The processed-unit count increases by one.
3. The remaining limit decreases by one.
4. The source position advances by one 16-bit unit.
5. The destination position advances by the number of bytes just written.

For a zero unit:

- One zero byte is written at the current destination position.
- The function immediately returns the current count.
- The zero unit is not included in that count.
- No following source unit is inspected.

Thus, a positive limit of \(N\) permits inspection of at most \(N\) source units. If all inspected units are nonzero, exactly \(N\) units are converted and the return value is \(N\).

### Byte encoding

Let \(u\) be the unsigned numeric value of the current source unit.

| Input range | Bytes emitted, in increasing destination-address order |
|---|---|
| 0 through 127 | One byte equal to \(u\) |
| 128 through 2,047 | First byte: `C0` combined with the upper five bits of \(u\). Second byte: `80` combined with the lower six bits |
| 2,048 through 65,535 | First byte: `E0` combined with the upper four bits of \(u\). Second byte: `80` combined with bits 6–11. Third byte: `80` combined with bits 0–5 |

All byte constants in this table are hexadecimal. “Combined” means bitwise OR. The extracted value bits occupy positions not already set by the corresponding prefix.

Equivalently, the nontrivial byte values are:

- Two-byte encoding:
  - \(192 + \lfloor u / 64 \rfloor\)
  - \(128 + (u \bmod 64)\)
- Three-byte encoding:
  - \(224 + \lfloor u / 4096 \rfloor\)
  - \(128 + (\lfloor u / 64 \rfloor \bmod 64)\)
  - \(128 + (u \bmod 64)\)

These calculations stay within the range of an unsigned byte. The input is unsigned, so there is no sign extension of values at or above 32,768.

The branch boundaries are exact:

- 127 uses one byte.
- 128 uses two bytes.
- 2,047 uses two bytes.
- 2,048 uses three bytes.
- 65,535 uses three bytes.

No four-byte encoding is produced.

### Zero handling and output termination

Zero is handled within the one-byte case. It is written before termination is reported by returning.

This creates two distinct completion modes:

- **Zero encountered:** Output includes a zero byte after all preceding converted units.
- **Limit exhausted:** Output ends immediately after the last converted unit, without an added zero byte.

A zero unit immediately beyond the permitted input range is not inspected and does not cause an output terminator to be written.

The caller cannot determine the stopping reason from the return value alone in every case. In particular, zero is returned both for a nonpositive limit and for a positive limit whose first source unit is zero, although their destination effects differ.

### Return value and output size

For a positive initial limit \(N\), the return value lies between zero and \(N\), inclusive.

If the function returns \(k\) because a zero was encountered, the output size is:

\[
1 + \sum_{i=0}^{k-1} L(u_i)
\]

where \(L\) is the one-, two-, or three-byte length determined by the ranges above. In this case, \(k < N\).

If the function returns because the limit was exhausted, the output size is:

\[
\sum_{i=0}^{N-1} L(u_i)
\]

No output size is separately returned or stored for the caller.

### Surrogates and other special values

The function performs no surrogate-pair recognition.

Each input value from `D800` through `DFFF` receives its own three-byte encoding. A high surrogate followed by a low surrogate therefore produces six bytes, counts as two input units, and is not combined into a supplementary Unicode scalar value.

There is no special treatment for:

- Byte-order marks.
- Unicode noncharacters.
- Isolated surrogates.
- Paired surrogates.
- Values with the high bit set.
- Any zero-free sequence that reaches the limit.

A source unit with value `FEFF`, for example, is encoded as three bytes rather than consumed as an instruction to change byte order.

## Side effects

### Reads and writes

At the level of the supplied representation, each active iteration reads the current 16-bit input value before writing its output bytes.

For a multi-byte encoding, output writes proceed from the lowest destination address to the highest:

- Two-byte case: leading byte, then continuation byte.
- Three-byte case: leading byte, middle continuation byte, then final continuation byte.

The next source unit is not read until the current unit’s output has been written.

These are source-level sequencing facts. They do not independently establish bus transaction widths, synchronization behavior, atomicity, or a memory-mapped I/O contract.

The function does not intentionally write to source storage. Nevertheless, aliased destination storage can overwrite source bytes, including bytes belonging to future source units. Because subsequent source values are read during processing rather than snapshotted at entry, such writes can change later output or cause an earlier zero-based stop.

### State and ownership

The function:

- Writes only through the destination pointer in the supplied body.
- Does not allocate, free, acquire, or transfer ownership of storage.
- Does not retain either supplied pointer.
- Does not expose its advanced pointer positions.
- Does not reference global state.
- Does not invoke another function.

Caller ownership of source and destination storage is unchanged.

### Errors and partial completion

There is no explicit validation, error return, or recovery path for:

- Insufficient destination storage.
- Inaccessible source storage.
- Invalid pointers on a path that dereferences them.
- Misaligned source storage where alignment is required.
- Overlap that changes future input.
- Malformed UTF-16 or invalid Unicode scalar values.

A negative limit is not reported as an error; it produces the same no-access return path as a zero limit.

If an external memory fault occurs during execution, earlier writes may already have happened. The function provides no rollback mechanism. The platform’s fault delivery and recovery semantics are outside the established contract.

## Uncertainties

### Established static evidence

The supplied representation directly supports:

- The limit check before each source read.
- The three encoding ranges and byte formulas.
- Writing zero before returning on a zero input unit.
- Excluding that zero unit from the return count.
- The lack of an appended terminator on limit exhaustion.
- Sequential source processing and forward destination writes.
- The absence of explicit capacity checks, allocation, global references, and function calls.

### Inferred intent

The output patterns strongly suggest an intended UTF-8-like encoding of 16-bit input units. Treating the source as a zero-terminated wide-character sequence is also consistent with the stopping behavior.

Those interpretations do not establish full UTF-16 support, Unicode scalar validation, a particular platform-wide character type, or a destination-size convention.
