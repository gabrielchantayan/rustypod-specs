# F-84cf36eb7469

## Purpose

F-84cf36eb7469 allocates and initializes an object, then conditionally prepends it to a list associated with a supplied parent. Initialization includes a second, fixed-size allocation, a flag-controlled dependency, and an optional indirect initializer.

The visible operation has three distinct outcomes:

- A missing parent or associated context causes an explicit status assignment of 6.
- Failure reported by the first allocation causes an explicit zero write to a supplied output cell.
- After the first allocation succeeds, the final initialization decision selects either publication or two cleanup calls. This failure path does not explicitly clear the output cell.

Publication and return must be distinguished. Publication writes establish list and output-cell values at that point in execution, subject to aliasing. An optional diagnostic dependency runs afterward and has no supplied preservation contract.

The returned value is a 64-bit composition of the original output-cell address and a final read of primary-status storage. That storage escapes to the first allocation dependency. Consequently, the returned status need not identify the publication or cleanup branch unless subsequent mutation of the escaped storage is excluded.

“Parent,” “context,” “class record,” and “object” describe inferred structural roles, not established ownership or type contracts.

## Interface

### Inputs

The supplied representation exposes four 32-bit inputs:

| Input | Meaning and constraints |
|---|---|
| Parent address | Zero selects the invalid-parent path. Otherwise, storage relative to this address is accessed without validation. |
| Output-cell address | Optional address of a writable 32-bit cell. Zero suppresses explicit output-cell writes. Its original bits become the upper return half. |
| Initial helper-status value | Copied to temporary helper-status storage on the valid-context path. An explicit zero assignment replaces it before that storage is passed to a dependency. |
| Initial primary-status value | Copied to temporary primary-status storage before the first allocation. The allocation receives this storage by address; whether its initial contents matter is unknown. |

The representation uses 32-bit address-like values and four-byte fields. Nonzero addresses are not checked for accessibility, alignment, extent, or identity.

### Return

The 64-bit result contains:

- Bits 63–32: the original output-cell address bits.
- Bits 31–0: the primary-status bits read for return.

The lower half is not sign-extended. For example, primary status with bit pattern `0xFFFFFFFF` occupies only the lower 32 bits.

The return composition is established. Interpreting its lower half as a stable construction outcome requires additional assumptions:

- The first allocation can retain the primary-status address.
- Subsequent dependencies can potentially modify that storage.
- The exit diagnostic receives a status value read before its invocation; the return reads primary status afterward.

Therefore, zero in the lower return half does not unconditionally prove that publication occurred. Conversely, publication does not unconditionally imply a zero lower return half.

## Behavior

### Validation and captured state

The function first captures the diagnostic-state address from a global location.

If the parent is nonzero, it reads the parent’s context address at +0x60. A zero parent or zero context selects the invalid-input path: primary status is assigned 6, neither diagnostic call is executed, and the composite result is returned. There is no explicit output-cell write on this path.

For a nonzero parent and context, the function captures, in order:

1. The allocation-context value at context +0x08.
2. The class-record address at context +0x14.

It initializes the two temporary statuses from the third and fourth inputs.

### Entry diagnostic and first allocation

The entry diagnostic condition rereads the global diagnostic-state address. It reads that state’s verbosity at +0x1C as a signed 32-bit integer. If the value exceeds 3, F-4457a9a44a68 receives an entry-message argument.

This address selection differs from the exit diagnostic, which uses the address captured at function entry. Negative signed verbosity values do not satisfy the threshold.

After the optional entry call, the function reads the requested size from +0x2C of the previously captured class record. It calls F-3ce007b692cc with:

- The initially captured allocation-context value.
- That 32-bit size.
- The address of primary-status storage.

The returned address-like value is treated as the main object. The subsequent decision uses primary status, not an independent null-result check.

If primary status is nonzero at this decision:

- A nonzero output-cell address receives a four-byte zero.
- No shown cleanup dependency is called.
- Execution proceeds to the exit diagnostic check.

A nonzero object address returned alongside an error status is not explicitly released on this branch. The status observed here need not remain unchanged through the exit diagnostic.

### Initialization after first-allocation success

If primary status is zero at the first allocation decision, the function first writes the parent address to object +0x04. It then rereads the context address from parent +0x60.

From this reread context it captures, in order:

1. The class-record address at +0x14.
2. The allocation-context value at +0x08.

It assigns zero to helper-status storage and copies context +0x04 to object +0x00.

The first and second allocation phases can therefore use different contexts. Neither the entry diagnostic nor the first allocation has a supplied contract preventing it from changing the parent’s context.

The captured addresses are not revalidated. If an intervening dependency invalidates them, the supplied representation establishes no recovery behavior.

### Auxiliary allocation and conditional initialization

The function calls F-3ce007b692cc again with:

- The later allocation-context value.
- Size `0x28`, exactly 40 bytes.
- The address of helper-status storage, initialized to zero.

If helper status is nonzero afterward, the returned auxiliary address is not explicitly written to object +0x9C. The flag-controlled helper and indirect initializer are skipped.

If helper status is zero, the auxiliary result is written to object +0x9C without an independent null check. The function then reads the descriptor address from the reread context’s +0x00 field and reads the descriptor’s flags word.

When mask 0x200 is set, F-f752365621f4 is skipped. When it is clear, that dependency receives the later allocation-context value and auxiliary result; its 32-bit return value is assigned to helper status.

Only mask 0x200 controls this branch. Other flag bits do not affect the shown decision.

If the preceding initialization conditions remain successful, the function examines the initializer pointer at +0x40 of the later captured class record:

- Zero permits continuation without an initializer call.
- Nonzero causes an indirect call with the main-object address as the sole shown argument. Its return value replaces helper status.

The representation shows a pointer read for the nonzero check and another for invocation. Target stability between those reads is not established.

### Publication or cleanup

After initialization, the function copies helper status into primary status. The publication-versus-cleanup decision tests helper status.

When that decision observes zero, the explicit publication accesses occur in this order:

1. Read the parent’s current list head at +0x54.
2. Write that value to object +0x08.
3. Write the object address to parent +0x54.
4. If the output-cell address is nonzero, write the object address there.

The head used is the value present after initialization, not a value captured at entry.

When the decision observes nonzero helper status, the function instead calls:

1. F-83ef5b3ae552 with the main-object address.
2. F-bf7242c98d06 with the **initially captured** allocation-context value and main-object address.

This branch has no explicit list-publication write or output-cell write. The final release call uses the initial allocation context even if auxiliary allocation used a different one.

The primary-status copy records helper status at that assignment. It does not protect that value from subsequent writes through the escaped primary-status address, including writes during cleanup.

### Exit diagnostic and return

All valid-context paths reach an exit diagnostic check after allocation failure, publication, or cleanup.

The check reads signed verbosity at +0x1C through the diagnostic-state address captured at function entry. If verbosity exceeds 3, F-4457a9a44a68 receives an exit-message argument and the primary-status value read for that call.

The function subsequently reads primary status for the lower return half. A diagnostic dependency that modifies retained primary-status storage can make the logged argument and returned status differ.

The same dependency can modify published structures or the output cell. The visible function performs no restoration after the exit call.

## Side effects

### Explicit writes

Depending on the selected path, explicit writes affect:

- Main-object fields at +0x00, +0x04, +0x08, and +0x9C.
- Parent +0x54 during publication.
- A supplied output cell: zero on first-allocation failure, or the object address during publication.
- Temporary primary- and helper-status storage.

No explicit allocation-wide zeroing is shown.

“No explicit output-cell write” does not guarantee unchanged contents. Dependencies or writes through overlapping addresses can affect the same storage.

### Publication, reachability, and ownership

With disjoint valid storage, the publication writes establish a link from the parent to the new object, a next link containing the previous head, and, when supplied, an output reference to the object.

Those are publication-time effects, not unconditional return-time guarantees. They persist to return only if subsequent activity, including the exit diagnostic, preserves the relevant storage. Aliasing can also alter the apparent final structure during publication itself.

The list insertion suggests a parent-associated ownership relationship, but exclusive ownership, reference counting, destruction obligations, and lifetime guarantees are not established.

On later initialization failure, cleanup and release are requested in the shown order. The supplied material does not establish whether auxiliary storage is released, whether either dependency has already reclaimed storage, or whether partial initialization is safe for cleanup.

### Escaped status storage

Both allocation calls receive addresses of temporary status storage. No supplied dependency contract forbids retaining those addresses or using them during later calls while the storage remains live.

For primary status, this directly affects observable results:

- Later initialization calls can modify it, although the explicit helper-to-primary copy subsequently overwrites its then-current value.
- Cleanup calls occur after that copy and can change the value used by the exit diagnostic or return.
- The exit diagnostic can change the value after receiving its status argument but before the final return read.

No behavior after the temporary storage’s lifetime is established.

### Aliasing and synchronization

Aliasing is not rejected. If the output cell aliases object +0x08, for example, the final output write replaces the saved old-head value with the object’s own address.

No synchronization, atomic list insertion, callback-target stability, or concurrent-access guarantee is shown. The ordered accesses described here do not establish safety against independent concurrent mutation.

## Acceptance examples

These are conditional static expectations, not executed tests. Except where an example states otherwise, assume valid disjoint storage, normal dependency returns, and no dependency mutations beyond the specified results. In particular, assume escaped status storage and published structures are preserved after the relevant assignments.

1. **Zero parent.** With a zero parent and an output cell containing a sentinel, the lower return half is 6 and the upper half is the original output-cell address. No explicit output-cell write or diagnostic call occurs.

2. **Missing context.** A nonzero parent with zero at +0x60 selects status 6 without allocation, cleanup, or diagnostic calls.

3. **First allocation reports failure.** If the first allocation writes status 17, a supplied output cell receives zero. No shown object cleanup follows, regardless of the returned address. With no later status mutation, the lower return half is 17.

4. **Auxiliary allocation reports failure.** If the second allocation writes status 23, its result is not explicitly stored at object +0x9C. Cleanup and release occur in that order. No explicit output-cell update occurs. With status preservation, the lower return half is 23.

5. **Flag-controlled helper fails.** With successful auxiliary allocation and mask 0x200 clear, a helper return of 9 skips the indirect initializer and selects cleanup. With no later status mutation, the lower return half is 9.

6. **Flag bypass and absent initializer.** If both allocations succeed, mask 0x200 is set, and the initializer pointer is zero, neither initialization helper is invoked. The publication branch executes.

7. **Successful prepend.** If the parent head immediately before publication is H, the writes store H into object +0x08, then the object address into the parent head, then into a supplied output cell. These values remain at return only under the preservation assumptions.

8. **No output cell.** A zero output-cell address suppresses output writes but not publication. The upper return half is zero.

9. **Cleanup changes returned status.** Suppose initialization yields status 9 and selects cleanup. If a cleanup dependency writes zero through a retained primary-status address, and no later operation changes it, the lower return half is zero despite no explicit publication.

10. **Diagnostic argument differs from return.** Suppose the exit diagnostic receives status 9. If it then writes 12 through a retained primary-status address, the lower return half is 12, not 9.

11. **Publication does not ensure return-time reachability.** Suppose publication occurs, then the enabled exit diagnostic replaces the parent’s head and output-cell contents. The publication writes still occurred; their values are not guaranteed at return.

12. **Signed diagnostic threshold.** Verbosity 3 suppresses a diagnostic; 4 enables it. A negative signed value suppresses it. Entry and exit may differ because they select diagnostic-state addresses differently.
