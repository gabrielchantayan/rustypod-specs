# F-14322dc15216

## Purpose

F-14322dc15216 selects a starting object by following one link under a per-object continuation condition, then invokes F-fa89c050ea53 along two linked sequences.

The established behavior is structural:

1. Select an object using the 32-bit fields at byte offsets +0x134 and +0x130.
2. Visit that object and its successors through the field at +0x138.
3. Return to the selected object as an anchor, then visit its successors through the field at +0x134, excluding the anchor from this second sequence.

The links used during visitation are read after dependency calls. Consequently, the call sequence can depend on changes made by F-fa89c050ea53. This is not a snapshot traversal.

A possible intent is to process related objects in two directions or across two kinds of links. That interpretation is inferred, not established. The evidence does not identify a container type, link names, an ownership policy, or the operation performed on each visited object.

The argument is therefore a pointer to an address-bearing slot, not directly the object address. The slot is read once at entry. There is no visible write to the slot and no later reread of it.

## Behavior

### 1. Read the initial object

The function reads the input slot and retains its value as the initial object address.

There is no null check on the input pointer. There is also no check that the initial object address is nonzero before selection begins.

### 2. Select the anchor

Selection begins at the initial object. At each selection step, the current object becomes the prospective anchor.

The function first reads the word at current object +0x134:

- If that read is zero, selection stops at the current object. The field at +0x130 is not read for that step.
- If that read is nonzero, the function reads current object +0x134 again to obtain the candidate next address. It then reads current object +0x130.

If the +0x130 condition is zero, selection stops at the current object. The candidate next address is not selected.

If the +0x130 condition is nonzero, selection continues at the candidate next address, and that object becomes the prospective anchor on the next step.

Thus, a nonzero link alone is insufficient to advance. Advancement requires both a nonzero first link read and a nonzero continuation condition at the object being left.

The two reads of +0x134 are distinct in the supplied operation sequence. Under stable memory, they return the same value. If an external agent can change that field between reads, the evidence does not justify treating the first nonzero value as the address actually followed. No dependency calls occur during selection.

Selection does not invoke F-fa89c050ea53 on objects that it passes over.

### 3. Visit the +0x138 sequence

After selection, the function starts the first visitation sequence at the selected anchor.

For each nonzero current address:

1. F-fa89c050ea53 is called with that address.
2. After the call returns, the function reads the word at that same object’s +0x138 field.
3. That newly read value determines the next object.

A zero next address ends this sequence. The function does not call the dependency with the terminating zero address.

The selected anchor is included in this sequence. Links are not prefetched before the callback. A callback that changes the current object’s +0x138 field can therefore change which object is visited next.

The retained anchor address is separate from the advancing first-sequence address. Reaching the end of this sequence does not replace the anchor with its final object.

### 4. Visit the +0x134 sequence

After the first sequence has finished, the function reads selected anchor +0x134.

- If that value is zero, the second sequence is empty.
- Otherwise, the function calls F-fa89c050ea53 with that nonzero address.

For every object visited in this second sequence, the function reads that object’s +0x134 field only after the dependency call returns. A nonzero result supplies the next callback argument; a zero result terminates traversal.

The anchor is not automatically visited again at the start of this sequence. The sequence begins with the anchor’s then-current +0x134 successor. A cycle or an overlapping link structure can nevertheless cause the anchor, or any previously visited object, to be visited again.

The anchor’s +0x134 value is not preserved from selection. The read starting this sequence occurs after all first-sequence callbacks. Any relevant mutation during those calls can affect the second sequence.

### 5. Return

The function returns after the second sequence reaches a zero link.

There is no visited-object set, duplicate suppression, traversal bound, cycle detection, error result, or visible recovery path.

## Side effects

### Direct effects

The visible body performs reads and dependency calls. It contains no explicit writes to the input slot, object fields, or global storage. It contains no direct allocation or release operation.

The ordering of dependency calls is established: every callback in the first sequence occurs before any callback in the second sequence. Each callback completes before the function reads that visited object’s next-link field.

The field-read order described above reflects the supplied representation. The evidence alone does not establish machine-level memory transactions, volatile semantics, atomicity, or concurrent-access guarantees.

### Dependency-mediated effects

F-fa89c050ea53 may have effects not shown in the supplied evidence. This contract does not assume that it preserves globals, leaves links unchanged, or preserves object lifetime.

The function passes object addresses to the dependency, but no ownership transfer is established. In particular, the post-call field reads prevent safely assuming that the callback can release the current object without further lifetime guarantees. If it releases or invalidates that object, the subsequent link read may access invalid storage.

The selected anchor has an additional lifetime requirement: it must survive the entire first sequence because its +0x134 field is read afterward.

### Failure and nontermination

Invalid pointers, inaccessible field storage, or invalid addresses produced by links have no visible handling. The exact failure mechanism is environment-dependent.

Cycles can prevent return:

- Selection can loop through objects whose selection links and continuation conditions keep allowing advancement.
- The first sequence can loop through +0x138 links.
- The second sequence can loop through +0x134 links.

A dependency call that does not return also prevents further traversal. No independent timeout or cancellation mechanism is visible.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, all named objects and fields are readable, relevant storage remains stable, and F-fa89c050ea53 returns without changing links or object lifetimes.

### Single object

Given initial object A with A’s +0x134 and +0x138 fields both zero:

- Selection stops at A without reading A’s +0x130 field.
- The callback receives A once.
- The first sequence stops at A’s zero +0x138 link.
- The second sequence is empty because A’s +0x134 link is zero.

Expected callback order: A.

### A nonzero link with a zero continuation condition

Given A’s +0x134 link points to B, A’s +0x130 condition is zero, A’s +0x138 link points to C, C’s +0x138 link is zero, and B’s +0x134 link is zero:

- Selection stops at A, not B.
- The first sequence visits A and C.
- The second sequence visits B.

Expected callback order: A, C, B. B’s +0x130 field does not control this second-sequence traversal.

### Selection advances before visitation

Given A links to B through +0x134 and A’s +0x130 condition is nonzero; B links to C through +0x134 but B’s +0x130 condition is zero; and B’s +0x138 and C’s +0x134 links are zero:

- Selection advances from A to B, then stops.
- The first sequence visits B.
- The second sequence visits C.
- A receives no callback merely because selection passed through it.

Expected callback order: B, C.

### Callback changes the first sequence

Suppose A is selected and initially has +0x138 pointing to B. During the callback for A, the dependency changes that field to C and leaves A readable.

The next first-sequence object is C, not B. The original link value is not retained for visitation.

### Callback changes the second-sequence start

Suppose A is selected with +0x134 initially pointing to B. During the first sequence, a callback changes A’s +0x134 field to zero and leaves A readable.

After the first sequence ends, the second sequence is empty. The earlier selection-time link to B does not force a visit to B.

### Overlapping sequences produce repeated calls

Given A is selected, A’s +0x138 and +0x134 fields both point to B, B’s +0x138 field is zero, and B’s +0x134 field is zero:

Expected callback order: A, B, B.

The two visits to B are not merged.

### No empty-input convention

A readable input slot containing zero does not cause an immediate successful return. Selection attempts a field read using that zero base address. The resulting behavior depends on the execution environment; it is not a supported empty-list case established by this evidence.
