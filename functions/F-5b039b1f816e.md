# F-5b039b1f816e

## Purpose

F-5b039b1f816e conditionally submits an operation using an object-associated value and a caller-supplied 32-bit selector. It first checks an external prerequisite, then validates the selector’s low byte. An accepted selector causes an entry-side dependency call, a submission call, an optional continuation call, and an exit-side dependency call.

The established result paths are:

- Return 11 when the prerequisite dependency returns zero.
- Return 9 when the prerequisite succeeds but selector validation fails.
- Return 28 when submission returns zero.
- Otherwise, return the continuation dependency’s 32-bit result unchanged.

These numbers are established values, not established semantic error names. The evidence does not identify the operation being submitted, the object’s concrete type, or the meaning of the continuation result.

The entry-side and exit-side calls surround submission and continuation. Their placement suggests a paired protection or lifecycle mechanism, but their identities and effects are unknown. This contract therefore does not assert that they acquire and release a lock.

## Behavior

### Prerequisite check and precedence

The function preserves the supplied selector in local 32-bit writable storage and invokes F-5a5d7959eb80 without explicit arguments.

If that dependency returns zero, the function returns 11. It does not proceed to selector rejection, object-relative access, submission, continuation, or either surrounding dependency call.

Any nonzero prerequisite result allows selector validation to proceed. The sign and magnitude of that result otherwise have no visible significance.

This ordering establishes precedence: prerequisite failure wins over an invalid selector. A caller cannot distinguish selector validity from the result 11 alone.

### Selector acceptance

Selector acceptance is determined entirely by the least significant eight bits:

- Bits 4 through 7 must all be zero.
- The least significant eight-bit value must be less than 4.

Together, these conditions mean that the low byte must be exactly 0, 1, 2, or 3.

The upper 24 bits are unrestricted by this function. They are neither cleared nor rejected before submission. For example, a selector with hexadecimal value 0xA5B60002 passes this validation despite being much greater than 3 as a complete 32-bit unsigned value.

If validation fails, the function returns 9. No entry-side call, object-field read, submission, continuation, or exit-side call occurs on that path.

The evidence contains two component checks, but it does not expose a distinct externally visible operation between them. Their combined acceptance set is the relevant contract.

### Entry-side call and object-field read

After selector acceptance, the function invokes the entry-side dependency with the address at object offset 0x2D8.

Only after that call returns does the function read the 32-bit value at object offset 0x2D0 for use in submission. This ordering matters if the entry-side dependency modifies the object or affects which value is observable at that location.

The entry-side dependency’s return value is not used by this function to choose a branch or result. There is no visible local handling of entry failure.

It would be incorrect to replace this ordering with a read of the object field before the entry-side call unless preservation of the field were independently established.

### Submission

The function next invokes F-cd7e1905512f with seven arguments, in this order:

1. The 32-bit value read from object offset 0x2D0 after the entry-side call.
2. Numeric value 0.
3. Numeric value 7.
4. Numeric value 8.
5. The address of the local 32-bit selector copy.
6. Numeric value 1.
7. The original object-address input.

The fifth argument points to the full 32-bit copy, not merely to an independently normalized low-byte value. Consequently, the upper 24 bits remain present in the supplied storage.

The semantic meanings of the constants 0, 7, 8, and 1 are unknown. In particular, the argument value 1 is not sufficient evidence that exactly one byte is read or written through the selector pointer.

Submission is tested only for zero versus nonzero:

- A zero result selects return value 28 and skips continuation.
- A nonzero result is passed to continuation.

No positivity, numeric range, or resource-validity check is visible. A nonzero result with its high bit set follows the continuation path.

The submission dependency receives writable selector storage. The caller-visible input is supplied by value, so writing through that pointer does not directly overwrite the caller’s original selector variable. Such a write may affect what submission itself observes, but this function performs no visible selector read or revalidation after submission returns.

### Continuation

For a nonzero submission result, the function invokes F-a0388036d124 with four arguments:

1. The original object-address input.
2. The submission result.
3. Numeric value 1.
4. Numeric value 200.

The function adopts the continuation’s 32-bit return value as its own pending result.

The meaning and units of 200 are not established. It must not be specified as a duration, retry count, or size without additional evidence.

Continuation results receive no local classification. Zero, values matching the function’s own selected results, and all other representable 32-bit values are forwarded alike.

### Exit-side call and return

After either a zero submission result or a normally returning continuation call, the function invokes the exit-side dependency with the address at object offset 0x2D8.

The exit-side dependency’s return value does not visibly replace the pending result. The function then returns:

- 28 following zero submission; or
- The continuation result following nonzero submission.

Thus every accepted-selector path that reaches submission and returns normally includes the exit-side call. The evidence does not establish guaranteed cleanup after a dependency that does not return normally. There is no visible exception handler or alternate cleanup route.
