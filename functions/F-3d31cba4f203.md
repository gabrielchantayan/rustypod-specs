# F-3d31cba4f203

## Purpose

F-3d31cba4f203 performs two stages of dependency-driven selection and, if both stages complete, clears bit 4 of one addressed byte and sets bit 4 of another.

The first stage ordinarily advances when its predicate returns nonzero, but it also advances without evaluating that predicate when retrieval returns any 32-bit value other than 0 or 1. The second stage requires a nonzero retrieval result, a nonzero result from a different predicate, and bit 0 set in a subsequently read byte.

The two marker operations use the selection destinations’ **then-current values when the operations are reached**. A value supplied by an earlier retrieval is not unconditionally preserved: retrieval receives the destination’s address, and the source does not rule out retention or later mutation through that address.

Both normal completion paths invoke F-d0d3f100effc. The function then returns the 32-bit value 0 for retrieval-driven failure or 1 after executing the marker updates.

“Selection,” “predicate,” and “finalization” describe visible call-site roles. They do not establish domain semantics, ownership, traversal order, or resource-management behavior.

## Interface

The function receives four 32-bit arguments and returns a 32-bit result.

| Input | Established use |
|---|---|
| First argument | Initializes the second-stage selection destination and is separately passed by value to F-8ca21d3a8cca. |
| Second argument | Initializes the first-stage selection destination. |
| Third argument | Initializes the first word of local state storage. |
| Fourth argument | Initializes the immediately following word of that state storage. |

The two initialized state words occupy eight consecutive bytes beginning at the state address passed to dependencies. This establishes the initialized prefix, not the complete extent or abstract type expected by those dependencies. Byte order is not established by the supplied function body.

Each selection destination holds a 32-bit value. F-b38a3aba0e18 receives the address of one destination at a time and can replace its contents. Selected values are later used as address-like values, with a byte displacement of 24 to reach a flag byte.

There are no direct caller-supplied output parameters. Nevertheless, the function writes through addresses derived from selection values, and dependencies may have additional effects.

### Normal results

- **0:** A retrieval returned zero, finalization was invoked, and finalization returned normally. Neither explicit marker write was executed.
- **1:** Both explicit marker writes were executed, finalization was invoked, and finalization returned normally.

These results do not certify that dependencies succeeded internally, that the same object remained selected throughout a stage, or that the written marker values persisted through finalization.

### Preconditions

Normal execution requires that:

- Reached dependencies accept their arguments and the supplied local-storage addresses.
- Every directly accessed address identifies a readable flag byte.
- Both marker-update targets support the required byte reads and writes.
- Each address calculation using a 32-bit selected value and displacement 24 is valid for the execution environment.

The function contains no visible null check, bounds check, overflow check, or memory-fault recovery. The supplied representation does not establish a portable overflow rule for these address calculations; wrapping must not be assumed as an accepted behavior.

## Behavior

### Initialization and exposure of local storage

Before calling a dependency, the function initializes both selection destinations and the two adjacent state words from the arguments.

It then calls F-8ca21d3a8cca with:

- The state address.
- The first argument by value.

No branch depends on this call’s result.

All retrieval calls use the same state address. First-stage retrieval calls receive the first-stage destination’s address; second-stage calls receive the separate second-stage destination’s address.

Passing a destination address exposes mutable local storage. The source provides no nonretention guarantee. A dependency may retain such an address and use it during a later call while the storage remains live. Consequently, the contract distinguishes:

- The value read from a destination to form a predicate argument.
- The value present in that destination after the predicate returns.
- The value present when a later flag access occurs.

Those values coincide only under an applicable preservation assumption.

### First-stage search

The function calls F-b38a3aba0e18 with the state address and the first-stage destination’s address.

Its 32-bit return value determines the next action:

| Retrieval result | Action |
|---|---|
| Exactly 0 | Proceed to failure finalization. |
| Exactly 1 | Invoke F-87ad59f6eb14. |
| Any other value | Advance to the second stage without invoking the first-stage predicate for this retrieval. |

When invoked, F-87ad59f6eb14 receives the first-stage destination’s value as read for that call:

- A zero predicate result causes another first-stage retrieval.
- A nonzero predicate result advances to the second stage.

Thus a first-stage retrieval result of 2, or the all-ones 32-bit pattern, bypasses the first-stage predicate and advances. The possible signed interpretation of such a result does not change its inequality to 0 and 1.

The function does not directly inspect a selected flag byte during this stage.

Retrieval is not visibly required to write the destination for any particular status. If it leaves the destination unchanged, the existing value remains until some operation changes it. That existing value might originate from the second argument, a previous retrieval, or another dependency’s mutation.

**No first-stage value is latched for the later marker-clear operation.** On the ordinary acceptance path, the first-stage predicate runs after retrieval. Further dependency calls occur throughout the second stage. Any of these calls may affect the exposed first-stage destination if the dependencies have retained access to it.

Accordingly, the marker-clear target is determined from the first-stage destination’s value when the clear operation is reached—not unconditionally from its value immediately after the last first-stage retrieval or from the value passed to F-87ad59f6eb14.

### Second-stage search

After a nonzero first-stage exit, the function calls F-b38a3aba0e18 with the same state address and the second-stage destination’s address.

The status rule differs from the first stage:

- Zero causes failure finalization.
- Every nonzero value causes a call to F-f86ec6aaf357.

F-f86ec6aaf357 receives the second-stage destination’s value as read for its argument. Its result controls qualification:

- If zero, repeat second-stage retrieval without a direct qualification-byte read.
- If nonzero, read the byte at displacement 24 from the second-stage destination’s then-current value.
- If bit 0 of that byte is clear, repeat retrieval.
- If bit 0 is set, proceed to the marker updates.

The qualification-byte read occurs **after** the predicate returns. The function does not preserve a separate copy of the predicate’s argument for this access. If the predicate changes the second-stage destination through a retained address, the qualification read can therefore address a different object from the one whose value was passed to the predicate.

Likewise, the predicate may change the addressed flag byte itself. Qualification observes the byte read afterward, not a pre-predicate snapshot.

Only bit 0 controls this byte-level qualification. Bits 1–7 do not affect this decision.

### Marker updates and access order

After successful qualification, the function performs two byte read-modify-write operations in this order:

1. At displacement 24 from the first-stage destination’s then-current value, read a byte and write it with bit 4 cleared.
2. At displacement 24 from the second-stage destination’s then-current value, read a byte and write it with bit 4 set.

Each store is one byte wide. Clearing bit 4 preserves bits 0–3 and 5–7 of the byte read for that operation. Setting bit 4 preserves those same other bits.

The second marker operation uses a fresh byte read; it does not reuse the earlier qualification byte.

No dependency call occurs between successful qualification and these two operations, or between the two operations. That does not establish atomicity, synchronization, or freedom from external interference. If aliasing allows an earlier write to alter a selection destination or another later-accessed location, no separate target-stability guarantee is provided.

The two marker targets need not differ. If both operations address the same byte and no other mutation intervenes, the clear occurs first and the set leaves bit 4 set.

There is no equality check, distinct-object requirement, transaction, or rollback.

### Finalization, return, and termination

On a retrieval result of zero in either stage, the function calls F-d0d3f100effc with the state address and returns 0 after that call returns.

On success, it performs both marker updates, calls F-d0d3f100effc with the state address, and returns 1 after that call returns.

The finalizer’s result is not used. Its effects are unknown. In particular, return value 1 establishes execution of the writes, not their persistence after finalization.

No iteration limit is visible. Either search can continue indefinitely if dependencies keep producing retry conditions. Finalization is not reached while such a search continues.

## Side effects

### Directly established effects

The function:

- Initializes local state and selection storage.
- Exposes the state address to initialization, retrieval, and finalization.
- Exposes each selection destination’s address to retrieval during its respective stage.
- Conditionally reads a qualification flag byte.
- On success, clears one flag byte’s bit 4 and then sets another flag byte’s bit 4.
- Invokes finalization before either normal return.

A zero-status failure path performs neither explicit marker write. Earlier dependency effects may still have occurred.

### Ownership and lifetime

No allocation, release, ownership transfer, or reference-count operation is directly established.

The local addresses remain addresses of live local storage during the function’s execution. This does not prohibit dependencies from retaining them or using them during subsequent calls. Nor does it establish any valid lifetime for accessing that storage after the function returns.

F-d0d3f100effc’s call-site role supports the descriptive term “finalization,” but does not prove that it releases memory or any other resource.

### Errors and partial effects

The only explicit failure branch is driven by a zero retrieval result.

There is no visible recovery for invalid memory, dependency faults, nonlocal exits, or failure after the first marker write. Finalization is established on normal success and zero-status failure paths, not on arbitrary abnormal exits.

No dependency is established to preserve globals, selected objects, state storage, or previously exposed destination storage.

## Acceptance examples

These are conditional static expectations, not execution reports. Unless an example states otherwise, assume valid addresses, normal dependency returns, no concurrent interference, and no dependency changes beyond those described.

1. **Immediate first-stage failure.**  
   The first retrieval returns 0. Finalization runs, followed by return value 0. Neither predicate nor either direct marker write is reached.

2. **First-stage retry.**  
   Retrieval returns 1 and F-87ad59f6eb14 returns 0. Another first-stage retrieval follows.

3. **First-stage predicate bypass.**  
   Retrieval returns 2. F-87ad59f6eb14 is skipped and second-stage retrieval begins. The all-ones 32-bit result has the same control-flow effect.

4. **Stable ordinary success.**  
   First-stage retrieval returns 1 and its predicate returns nonzero. Second-stage retrieval and its predicate return nonzero, and qualification reads bit 0 set. If both destinations remain unchanged through their marker operations, the first selected byte has bit 4 cleared and the second has bit 4 set. Finalization then runs and the function returns 1.

5. **First-stage predicate changes the later clear target.**  
   Retrieval places address A in the first-stage destination and returns 1. F-87ad59f6eb14 receives A, changes that destination to valid address B through retained access, and returns nonzero. If no subsequent operation changes the destination, successful completion clears bit 4 at B plus 24, not A plus 24.

6. **Second-stage activity changes the first-stage destination.**  
   The first stage completes with address A in its destination. During second-stage processing, a dependency changes that exposed destination to B. If it remains B until the marker clear, the clear targets B plus 24. Acceptance of A earlier does not fix the later target.

7. **Predicate argument and qualification target differ.**  
   Second-stage retrieval places A in its destination. Its predicate receives A, changes the destination to B, and returns nonzero. Qualification reads B plus 24. If that byte’s bit 0 is clear, retrieval repeats even if the corresponding byte at A has bit 0 set.

8. **Second-stage predicate rejection.**  
   Retrieval returns nonzero but F-f86ec6aaf357 returns 0. No direct qualification-byte read occurs for that iteration.

9. **Flag rejection.**  
   The predicate returns nonzero and qualification reads hexadecimal 10. Bit 4 is set, but bit 0 is clear; retrieval repeats.

10. **Second-stage failure.**  
    After the first stage completes, second-stage retrieval returns 0. Finalization runs and the function returns 0 without either explicit marker write.

11. **Distinct stable targets.**  
    Immediately before their respective marker operations, the first byte is hexadecimal B7 and the second is hexadecimal 05. The writes produce A7 and 15. Persistence after return additionally requires that finalization leave them unchanged.

12. **Aliased stable targets.**  
    Both destinations identify the same flag byte, initially hexadecimal 01. With no intervening mutation, the marker operations write 01 and then 11.

13. **Unbounded rejection.**  
    First-stage retrieval repeatedly returns 1 and its predicate repeatedly returns 0. The function continues searching without reaching finalization or a normal return.

## Uncertainties

The following remain **documented_only**:

- Argument and object domain meanings.
- Complete state layout and dependency-accessed extent.
- Traversal ordering, consumption, duplication, and progress guarantees.
- Whether retrieval writes its destination for each status.
- Whether dependencies retain destination addresses and later mutate them.
- Preservation of selection destinations, selected memory, state, or globals across calls.
- Intended meanings of statuses other than 0 and 1.
- Whether predicate-bypassing first-stage advancement is intentional.
- Allocation, release, ownership, and post-return retention behavior.
- Domain meanings of bits 0 and 4.
- Concurrency, atomicity, and interrupt-safety guarantees.
- Address-overflow behavior and abnormal-exit handling.

An inferred intent is to transfer a marker between eligible objects. That interpretation is not established behavior: mutable destinations can redirect later accesses, and the first-stage predicate is bypassed for some statuses.

## Evidence

This contract uses only the supplied static function body and opaque dependency mapping. No runtime tests have been performed.

Established evidence includes the 32-bit argument and result widths, adjacent state initialization, exposed destination addresses, asymmetric retrieval-status comparisons, predicate call order, post-predicate qualification read, displacement of 24 bytes, ordered byte-level marker operations, finalization paths, and normal return constants.

The later marker-clear operation refers to the first-stage destination again; it does not use an independently preserved copy of the last retrieval output or predicate argument. Preservation of an earlier value is therefore conditional on intervening operations leaving that destination unchanged. The second-stage predicate argument and later qualification access likewise use the destination at separate points.

Dependency internals and runtime guarantees are unavailable. Their possible effects remain explicit unknowns rather than preservation or ownership assumptions.
