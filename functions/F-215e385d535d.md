# F-215e385d535d

## Purpose

F-215e385d535d replaces two 32-bit fields in a selected record associated with a context obtained from another function. Before replacement, it conditionally invokes a no-argument dependency according to the record’s existing first field and the least significant bit of its existing second field.

The established behavior is conditional invocation followed by ordered field replacement. Interpreting the first field as a resource reference, the second as ownership flags, or the dependency as a release operation is inferred intent, not an established contract. In particular, the visible operation does not pass the existing first-field value to that dependency.

## Behavior

### Context acquisition and selection

The function first calls F-035afcc6e793. No selector or selected-field access is visible before that call returns.

It then reads the 32-bit selector at context offset 0x144. That value is captured for this invocation. The function substitutes 15 locally when the captured value is zero; it does not visibly write 15 back to the selector location.

Selection uses the resulting index with a scale of four bytes. The selected first-field address is the context base plus the scaled index plus 0x44. The selected second-field address is the context base plus the same scaled index plus 0x84.

No second context lookup or selector read is visible later in the function.

### Inspection of existing state

The function reads the selected first field as a 32-bit quantity and tests whether it is zero.

- If it is zero, the existing second field is not read by the visible body. The conditional dependency is not invoked.
- If it is nonzero, the function reads the selected second field as a 32-bit quantity and examines bit 0.

Only the existing second field’s least significant bit affects the decision. Its other bits do not participate in the visible condition. The replacement second value does not affect this invocation’s decision.

### Conditional dependency and replacement

1. The selected first field was nonzero when inspected.
2. Bit 0 of the subsequently read selected second field was set.

The invocation has no explicit arguments. Neither replacement input nor the previously read first-field value is visibly passed to it.

If that dependency returns normally, the function writes a 32-bit zero to the previously selected first-field address. It then writes the replacement first value to that same address, followed by the replacement second value to the selected second-field address.

When the conditional dependency is not invoked, the intermediate zero write is omitted. The function still writes the replacement first value and then the replacement second value.

Thus, the visible access order is:

| Condition | Ordered operations after selection |
|---|---|
| Existing first field is zero | Read first field; write replacement first value; write replacement second value |
| Existing first field is nonzero and existing bit 0 is clear | Read first field; read second field; write replacement first value; write replacement second value |
| Existing first field is nonzero and existing bit 0 is set | Read first field; read second field; call F-5990a26eaaa3; write zero to first field; write replacement first value; write replacement second value |

The function exposes no explicit status result, error translation, rollback, or recovery branch. If a dependency does not return, subsequent operations are not reached. ## Side effects

**Direct writes.** Every normally completed invocation performs the two replacement writes. The conditional-call path additionally performs an intervening zero write to the first field.

That zero write occurs after F-5990a26eaaa3 returns, not before it is called. Consequently, the visible body does not clear the first field as a pre-call guard. The zero is also not necessarily the final first-field state: the replacement first value is written immediately afterward in the visible sequence.

**Dependency effects.** Either dependency may have effects not exposed here. The contract does not assume that they preserve globals, leave the context untouched, avoid reentrancy, or refrain from allocating or releasing memory.

**Retained destination.** After the conditional call returns, the function uses the destination selected before that call. It does not visibly reacquire the context, reread the selector, or reconsider the condition. A dependency changing the selector or some global current-context reference therefore does not, by itself, redirect the remaining visible writes.

This retained destination is a lifetime requirement, not proof of safety: if the dependency invalidates that storage, the later writes may no longer be valid.

**Ownership.** No ownership transfer or memory-release guarantee can be assigned to either replacement input from the visible body alone. It stores their bit patterns. The conditional dependency may be associated with disposal, but its purpose and ownership effects remain unknown.

**Concurrency.** No lock, atomic update protocol, memory barrier, or transaction is visible. The ordered writes do not establish that another observer sees the pair replaced indivisibly. Physical observability of intermediate states depends on the execution environment and memory model.
