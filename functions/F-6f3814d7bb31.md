# F-6f3814d7bb31

## Purpose

F-6f3814d7bb31 obtains a record through F-08f20a63bf27, associates that record with a supplied owner, updates the owner’s linkage fields, and writes two caller-supplied bytes into the record.

The established behavior is a fixed sequence of memory accesses and one dependency call. The field arrangement is consistent with appending a record to a linked collection, but that interpretation is inferred intent, not an established collection invariant. In particular, this function does not initialize the returned record’s leading link field, verify that the owner’s existing links are consistent, or inspect a dependency failure indicator.

## Behavior

### 1. Obtain the dependency argument

Before invoking F-08f20a63bf27, the function follows a three-read chain:

1. Read a 32-bit address from owner offset 4.
2. Read a 32-bit address from offset 4 of that intermediate object.
3. Read a 32-bit value from the resulting argument cell.

The third value is the single visible argument to F-08f20a63bf27.

This chain does not pass the owner address directly. It also does not pass the address of the argument cell unless that happens to equal the value stored in the cell.

Each read depends on the preceding result. The supplied behavior contains no null checks or bounds checks between these reads.

### 2. Invoke the dependency

F-08f20a63bf27 is called once on a normally progressing execution.

Its result is treated as a 32-bit record address. The caller neither tests that result nor performs a visible fallback before using it.

The dependency’s memory effects are unknown. In particular, the owner’s linkage fields must not be assumed to retain their entry values across this call.

### 3. Associate the returned record with the owner

After the dependency returns, the function writes the owner address as a 32-bit value at returned-record offset 4.

This write precedes the branch-selector read. Consequently, if this destination aliases the owner’s branch-selector field, the branch sees the effect of this write. A specification that always selects the branch from the owner’s entry state would not reproduce the established ordering.

### 4. Choose and perform the linkage update

The function reads the 32-bit value at owner offset 12 and retains whether it is nonzero.

If the sampled value is nonzero:

- Read a 32-bit address from owner offset 16.
- Write the returned record address as a 32-bit value at offset 0 of that address.

If the sampled value is zero, neither of these branch-specific accesses occurs.

The branch decision depends only on the zero/nonzero status of the value sampled at this point. It is not based on owner offset 16, and it is not recomputed after subsequent writes.

### 5. Replace the owner’s trailing-address field

The function writes the returned record address as a 32-bit value at owner offset 16 on both branches.

On the nonzero branch, the preceding indirect link write therefore uses the address read before this replacement. It does not obtain its destination from the newly stored value.

### 6. Initialize the owner’s leading-address field when selected

If the previously sampled branch selector was zero, the function writes the returned record address as a 32-bit value at owner offset 12.

If that selector was nonzero, this conditional write is omitted.

The decision remains the one sampled in step 4. Intervening writes do not cause a second test.

### 7. Store the record bytes

After the linkage updates, the function performs two one-byte writes in order:

1. First record byte to returned-record offset 8.
2. Second record byte to returned-record offset 9.

These are separate byte writes. No surrounding bytes are explicitly cleared, initialized, or copied by these operations.

The function then returns without an explicit value.

### Ordinary non-overlapping interpretation

When all relevant objects and fields are distinct, the dependency returns a valid record, and the dependency does not otherwise modify the owner:

- A zero value at owner offset 12 results in both owner offsets 12 and 16 containing the returned record address.
- A nonzero value at owner offset 12 leaves that field unchanged, writes the returned record address into the leading word of the object addressed by the old owner-offset-16 value, and replaces owner offset 16 with the returned record address.
- Returned-record offset 4 contains the owner address, and offsets 8 and 9 contain the supplied bytes.

These postconditions require the stated non-overlap assumptions. They are not unconditional final-memory guarantees for arbitrarily overlapping storage.
