# F-486dc725426a

## Purpose

F-486dc725426a conditionally removes a node from a linked, color-balanced tree representation, places the detached node on a container-maintained singly linked list, decrements a 32-bit count, and writes a 32-bit result to caller-provided storage.

The link layout, successor selection, rotations, and color repair strongly suggest a red-black-tree erasure operation. That interpretation is **inferred intent**, not a substitute for the established behavior. In particular, this function contains explicit repair paths that must not be replaced by a generic tree-deletion algorithm without establishing equivalence.

The function has no explicit return value. Its externally visible results are memory writes and dependency calls.

## Interface

The interface has three inputs:

| Input | Representation | Required access |
|---|---|---|
| Result storage | Address of a 32-bit word | Written once on normal completion |
| Container | Address represented by a 32-bit machine value | Selected fields read and written |
| Node-reference storage | Address of a 32-bit word containing a node address | Read initially and read again after a dependency call on the removal path |

All offsets below are byte offsets. The supplied representation uses four-byte link and address fields and one-byte color fields.

### Container layout

| Offset | Width | Observed role |
|---|---:|---|
| +4 | 32 bits | Head of a list receiving the detached node |
| +16 | 32 bits | Address of a tree header |
| +20 | 32 bits | Count decremented after removal |

No behavior is established for the other container bytes.

### Header and node layout

Both the header and ordinary nodes expose link fields at the following offsets:

| Offset | Width | Ordinary-node role | Header role |
|---|---:|---|---|
| +0 | 8 bits | Color | Not ordinarily used by this function as a color |
| +4 | 32 bits | Parent | Root |
| +8 | 32 bits | Left child | Cached leftmost node |
| +12 | 32 bits | Right child | Cached rightmost node |

A null child address denotes an absent child. The header address is distinct from a null address.

Color value 0 is treated as red and value 1 as black in the repair logic. Other byte values do not receive consistently equivalent treatment: the initial repair gate accepts any nonzero removed-node color, whereas the repair loop continues only while the current node’s color is exactly 1.

On removal, the detached node’s +12 field becomes a next-list link. Its former right-child role therefore ceases at that point.

### Preconditions

For defined successful use:

- All input addresses and all subsequently dereferenced links must be valid for the indicated access widths.
- The container must provide a readable header address at +16.
- On the removal path, the node-reference word reread after the preparatory dependency must identify a removable ordinary node.
- Parent/child links and header caches must satisfy the relationships used by the selected branch.
- Child-chain traversals must terminate.
- Dependencies must return normally and leave memory usable for the subsequent accesses actually performed.

The function does not validate these conditions. It does not establish that a requested node belongs to the supplied container.

Aliasing between result storage, node-reference storage, the container, and node fields is not expressly rejected. Its consequences follow the access order below; nonaliasing is the safe calling precondition.

## Behavior

### 1. Initial decision and result preparation

The function first reads the node-reference word into temporary 32-bit storage. It then reads the container’s header address into separate temporary 32-bit storage.

It calls F-be1b50af3623 with the addresses of those two temporary words.

If that dependency returns a nonzero result:

1. The function rereads the header address from container offset +16.
2. That freshly read address becomes the result value.
3. The result word is written.
4. The function returns without performing its own tree removal, list insertion, or count decrement.

This branch is not side-effect-free: F-be1b50af3623 has already run. Its effects are unknown.

If the dependency returns zero, the function calls F-8abb04e87ea7 with the address of the first temporary word. That word subsequently supplies the final result, subject to any modification by this dependency.

After this call, the removal target is obtained by rereading the caller’s node-reference word. It is **not** taken from the temporary result word. Consequently, the value prepared for output and the node actually removed are distinct data flows.

Neither dependency’s name or interface establishes that the output represents a successor, an iterator, or the removed node.

### 2. Structural removal

The function reads the target’s left-child link, then selects among leaf removal, single-child replacement, and successor transplantation.

#### Leaf target

When both child links are null, the target’s parent is read.

If that parent equals the container’s current header address, the function performs these writes in order:

1. Header rightmost becomes the header address.
2. Header leftmost becomes the header address.
3. Header root becomes null.

Otherwise, it determines whether the target is its parent’s left child. It clears the corresponding child link. In this leaf branch, the selected four-byte link is cleared through four individual byte writes in increasing byte-offset order.

It then checks the corresponding header extremum:

- Removing a left child checks the cached leftmost link.
- Removing the other child checks the cached rightmost link.

If that cache equals the target, it is replaced by the target’s parent.

The target’s parent becomes the current repair node. The original target remains the node eventually inserted into the detached-node list.

#### Target with exactly one child

The existing child replaces the target.

The function first writes the child’s parent link to the target’s parent. It then replaces either the header root or the appropriate parent child link with the child.

Cached extrema are handled afterward, in this order:

1. If the target was cached as leftmost, the replacement is either the target’s parent or the leftmost node reached from the replacement child. The choice depends on whether the target’s right link is null.
2. If the target was cached as rightmost, the replacement is either the target’s parent or the rightmost node reached from the replacement child. The choice depends on whether the target’s left link is null.

The replacement child becomes the current repair node. The original target remains the node to be added to the detached-node list.

#### Target with two children

The function finds the leftmost node in the target’s right subtree. This is the structural successor. Its right child, which may be null, is the replacement for its former position.

The transplant proceeds in this observable order:

1. The target’s left child has its parent changed to the successor.
2. The successor’s left link is assigned the target’s left link.
3. The successor is detached from its old position when necessary.
4. The target’s root or parent link is redirected to the successor.
5. The successor’s parent is assigned the target’s former parent.
6. The target and successor exchange color bytes.

There are two detachment cases:

- **Successor is the target’s immediate right child:** a nonnull successor right child has its parent set to the successor. The successor’s existing right link is retained.
- **Successor is deeper in the right subtree:** a nonnull successor right child has its parent set to the successor’s former parent. That former parent’s left link is replaced by the child, including null when absent. The successor receives the target’s right subtree, and that subtree’s root has its parent set to the successor.

If the successor’s former right child is null, the successor itself becomes the current repair node. Otherwise, that child becomes the current repair node.

The original target—not the successor—is ultimately added to the detached-node list. Its post-exchange color is the successor’s original color.

No explicit cached-leftmost or cached-rightmost update appears in this two-child branch.

### 3. Color and balance repair

Repair is entered only when:

- The current repair node differs from the current header address; and
- The detached target’s current color byte is nonzero.

If either condition fails, no repair color write is performed.

Once repair is entered, the loop first checks whether the current node is the root or has a color other than exactly 1. Either condition ends the loop. On every exit through the repair completion path, the current node’s color is written as 1.

For a nonroot current node whose color is exactly 1, the function reads its parent and determines whether it is the left child. The opposite child is the sibling.

#### Current node is a left child

The sibling is the parent’s right child.

- If the sibling is null, the current node is colored 0 and repair moves to the parent.
- If the sibling is color 0, it is colored 1, the parent is colored 0, and F-afe6bf6f53c9 is called with the container and parent. The parent and sibling links are then reread.
- If both sibling children are null or color 1, the sibling is colored 0 and repair moves to the current node’s parent.
- Otherwise, if the sibling’s right child is null or color 1, the sibling’s left child is colored 1 when present, the sibling is colored 0, and F-051feb68d086 is called. The sibling is then reread through the current node’s parent.
- With a remaining nonnull sibling, the sibling receives the parent’s color, the parent becomes color 1, and the sibling’s right child becomes color 1 when present. F-afe6bf6f53c9 is called with the container and parent, and repair finishes.

If the sibling becomes null after the intermediate F-051feb68d086 call, repair finishes without the subsequent sibling and parent color assignments.

#### Current node is not a left child

The sibling is the parent’s left child. The behavior is mirrored:

- A null sibling causes the current node to become color 0 and repair to move to the parent.
- A color-0 sibling becomes color 1; the parent becomes color 0; F-051feb68d086 is called with the container and parent; parent and sibling links are reread.
- Two null-or-color-1 sibling children cause the sibling to become color 0 and repair to move upward.
- If the sibling’s left child is null or color 1, its right child becomes color 1 when present, the sibling becomes color 0, and F-afe6bf6f53c9 is called. The sibling is reread.
- With a remaining nonnull sibling, it receives the parent’s color, the parent becomes color 1, and the sibling’s left child becomes color 1 when present. F-051feb68d086 is called with the container and parent, and repair finishes.

A sibling becoming null after the intermediate call similarly ends repair.

These descriptions identify the dependency calls and surrounding writes. They do not assert the internal effects of either dependency.

### 4. Detached-node list, count, and output

After structural removal and any repair, the function:

1. Reads the container’s list head at +4 and writes it to the detached target’s +12 field.
2. Writes the detached target’s address to container +4.
3. Reads the 32-bit count at +20 and stores that value minus one.
4. Writes the prepared temporary result to caller-provided result storage.

Only the detached node’s +12 field is repurposed for the list. Its parent, left link, and color are not generally cleared.

The count update has 32-bit storage. No zero-count guard exists. A zero starting count therefore produces the all-ones 32-bit stored pattern under the represented machine arithmetic. No source-language guarantee about signed overflow is established.

## Side effects

Established direct side effects include:

- Tree root, parent, and child-link writes.
- Cached-extremum updates.
- One-byte color writes.
- Insertion of the detached target at the head of the container’s +4 list.
- A single count decrement on the removal path.
- A final result-word write on either normally returning path.

The function makes no direct allocation or memory-release call visible in the supplied body. List insertion alone does not establish memory ownership transfer, destruction, or reclamation policy.

Effects of dependencies on globals, caller storage, allocation state, or other memory are unknown. In particular, the first two calls occur before the target is reread, so dependency-visible changes can affect which node is subsequently removed.

There is no explicit error code, rollback, or recovery path. Invalid links can cause invalid accesses or nontermination. If a dependency does not return normally, this function provides no visible mechanism to complete or undo earlier writes.

No atomicity, synchronization, or concurrent-reader safety is established. Intermediate tree states are observable if another agent can access the same memory during execution.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless specified otherwise, they assume valid, nonaliasing storage, normal dependency returns, and no dependency side effects beyond those explicitly stipulated.

1. **Nonzero initial decision.**  
   If F-be1b50af3623 returns nonzero, the output must equal the header address reread after that call. F-8abb04e87ea7 must not be called. This function must not directly decrement the count or insert a node into the detached list.

2. **Only node in the tree.**  
   If the target is a leaf whose parent is the header, removal must set both extremum caches to the header and the root to null. The header is the repair node, so repair is skipped. The old list head becomes the target’s +12 link, the target becomes the new list head, and the count decreases once.

3. **Leaf attached on the left.**  
   If a nonroot leaf is its parent’s left child, the parent’s left link must be cleared. A matching leftmost cache must become the parent. The rightmost cache is not independently updated by this leaf branch.

4. **Single right-child replacement.**  
   If the target has only a right child, that child must receive the target’s parent and replace the target in the root or parent link. If the target was cached as leftmost, the cache must become the leftmost descendant of the replacement child.

5. **Deep successor without a right child.**  
   For a two-child target whose successor lies below the immediate right child and has no right child, the successor’s former parent must receive a null left link. The successor replaces the target structurally, but the original target is the node added to the detached list. Repair initially uses the successor, not a null child.

6. **Prepared output differs from removed node.**  
   If F-8abb04e87ea7 changes its temporary word to a distinct 32-bit value while leaving the caller’s node-reference word unchanged, removal must still use the caller’s referenced node. The distinct prepared value must be written as output.

7. **Color-zero detached target.**  
   If the detached target’s color at the repair gate is 0, repair must be skipped, even if the replacement node is not the header. List insertion and count decrement must still occur.

8. **Zero count.**  
   If removal reaches the count update with a stored count of zero, no underflow error is reported; the stored 32-bit result is all ones.
