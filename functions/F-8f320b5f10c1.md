# F-8f320b5f10c1

## Purpose

F-8f320b5f10c1 performs a conditional indirect operation followed by an unconditional indirect operation on the same receiver.

The condition is a one-byte field in a separate input object. If that byte equals 2, the function invokes a receiver-associated target with two additional integer arguments, 6 and 0. After that invocation returns normally—or immediately when the condition is false—the function dispatches another receiver-associated target with only the receiver argument.

This is an observable dispatch contract, not a determination of the operations’ application-level meaning. The available evidence does not establish whether either target performs notification, cleanup, state transition, destruction, or another action.

## Interface

### Inputs

The recovered interface has two explicit inputs:

| Input | Role | Required accessible layout |
|---|---|---|
| Selector object | Supplies the condition byte | A readable byte at displacement 0x2EC, or 748 bytes, from its base address |
| Receiver | Supplies the dispatch-table address and is passed to both indirect targets | A readable address-bearing field at displacement zero; readable target entries in the selected table |

The selector object is represented as an integer in the supplied recovered interface but is used as an address. The receiver is represented as a pointer to an integer-sized field, and that field is used as a dispatch-table address. These representations do not establish the original declared types.

The relevant dispatch-table entries are at byte displacements:

- 0x5C, or 92 bytes, for the conditional operation.
- 0x128, or 296 bytes, for the subsequent operation.

These are byte offsets, not entry indexes. Interpreting them as indexes would require a separately established entry width.

The recovered representation is consistent with a 32-bit address model. However, the excerpt alone does not independently establish the machine ABI, pointer width, alignment requirements, or original integer declarations. The required field relationships and byte displacements are established more directly than those type details.

### Output

There is no explicit result value in the recovered interface. Any return values produced by the indirect targets are unused by this function.

Normal completion means the final indirect target has completed and control has returned to the caller, subject to the control-transfer uncertainty described below. Normal completion does not imply that the receiver remains usable or that either input object retains its previous state.

## Behavior

### Condition evaluation

The first visible data access reads the selector object’s byte at offset 0x2EC.

Only equality with the byte value 2 selects the conditional operation. This is an exact comparison, not a nonzero test or a bit test. Signedness of a one-byte character interpretation does not change whether the value 2 matches.

Other contents of the selector object do not participate in the visible decision. The condition byte is not read again by this function after the initial comparison.

### Conditional operation

When the selector byte equals 2, the function:

1. Reads the receiver’s leading dispatch-table address.
2. Resolves the target at byte offset 0x5C in that table.
3. Invokes that target with the receiver, followed by integer arguments 6 and 0.

The argument values and their order are established. Their semantic meanings are not.

The available representation shows ordinary integer arguments, but does not supply independent ABI evidence for their physical argument widths or register and stack placement. Both values are exactly representable by the recovered integer type.

If this target returns normally, processing continues to the subsequent operation. Its return value does not select another branch.

When the selector byte is not 2, this conditional dispatch is skipped. In particular, the visible function does not need to read the 0x5C entry on that path.

### Subsequent operation

On every path that reaches this stage, the function resolves and invokes the target at byte offset 0x128 in the receiver’s dispatch table. The receiver is its only explicit argument.

The receiver’s leading dispatch-table field is accessed for this operation after the conditional invocation, if that invocation occurred. The contract therefore does not treat the initial table address as permanently cached across the conditional call.

This ordering matters if the conditional target changes the receiver’s leading field or changes the later target entry. The subsequent dispatch uses the information available when that later dispatch is resolved, not necessarily the table or target that existed before the conditional call.

The two invocations receive the same receiver address value. The visible function does not replace its receiver argument with a pointer returned by the conditional target.

### Completion and interruptions

If both applicable targets return normally, the visible function performs no further substantive operation after the subsequent dispatch.

There is no visible local handling for a fault, exception, nonlocal transfer, or target that does not return. If the conditional target does not return normally, the excerpt does not establish that the subsequent operation occurs. Likewise, invocation of the subsequent target does not guarantee eventual return to this function’s caller.

The recovered representation contains an explicit warning about the final indirect transfer. It supports the existence and target location of that transfer more strongly than it establishes whether the original machine operation was an ordinary call or a tail-style transfer.

## Side effects

The visible body contains no direct stores to either input object and no explicit allocation, release, reference-count update, global write, or I/O operation.

That statement is limited to the visible body. Both indirect targets may have side effects that are not described by the supplied excerpt. In particular, this contract does not assume that they:

- Preserve global state.
- Preserve the receiver’s contents or dispatch table.
- Preserve the selector object.
- Retain or release ownership of any object.
- Avoid allocation, deallocation, callbacks, or external I/O.

The visible function establishes no ownership transfer on its own. Passing the receiver to a target is observable, but is not enough to determine whether that target borrows, retains, consumes, or destroys it.

There is also no established non-aliasing requirement between the selector object and receiver. If they overlap, the initial selector read still precedes either dispatch. A later mutation of the selector byte does not cause the already-selected conditional operation to be reconsidered.

No synchronization is visible. Behavior under concurrent mutation of the selector, receiver, dispatch table, or target entries is not specified by this excerpt.

## Acceptance examples

These examples are conditional static expectations, not reports of executed tests.

### Selector equals 2

Given valid accessible objects, a selector byte of 2, and targets that return normally:

- F-000000000001 is invoked first with the receiver, 6, and 0.
- F-000000000002 is invoked afterward with the receiver alone.
- Neither target’s return value becomes an explicit result of F-8f320b5f10c1.

### Selector does not equal 2

Given the same validity assumptions and a selector byte such as 0, 1, 3, or 255:

- The conditional target is not invoked by this function.
- The subsequent target is still invoked.
- The value 255 does not match 2 regardless of whether the byte is interpreted as signed or unsigned.

### Conditional target changes the dispatch table

Suppose the selector byte is 2 and F-000000000001 returns normally after replacing the receiver’s leading table address with another valid table address.

The subsequent target is resolved through that updated table. An implementation that retains the original table address for the second dispatch would not preserve the visible behavior in this case.

The same principle applies if the table address remains unchanged but the target at offset 0x128 is modified before the later resolution.

### Conditional target changes the selector byte

Suppose F-000000000001 changes the selector byte from 2 to another value and returns normally.

The subsequent operation still occurs. There is no second selector test and no repetition of the conditional operation.

### Conditional target invalidates the receiver

Suppose F-000000000001 releases the receiver’s storage and returns without leaving valid storage for the subsequent dispatch.

The excerpt supplies no protective check or defined error result. Successful completion cannot be required under these conditions; the later receiver access no longer satisfies the stated preconditions.

### Conditional target does not return

If F-000000000001 terminates execution or otherwise transfers control without returning, the subsequent invocation is not guaranteed. “Unconditional” describes the later operation on paths that reach it, not a guarantee across interruption.
