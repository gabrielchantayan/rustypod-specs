# F-80f83c943539

## Purpose

F-80f83c943539 traverses a linked structure using a two-word request, subjects a resulting selection to dependency-mediated checks, and conditionally updates an associated byte. An update is followed by receiver acquisition and two ordered indirect notifications.

The 32-bit result distinguishes final rejection from final acceptance:

- **0:** the final selection check returned nonzero.
- **1:** the final selection check returned zero, and all subsequent operations returned normally.

Acceptance does not necessarily mean that a byte changed. An accepted selection whose byte already equals the original second argument also returns 1.

**Inferred intent:** an ordered lookup followed by an attribute update and notifications. Neither an ordering relation nor the domain meanings of the byte and notifications are established.

## Interface

### Inputs and result

| Item | Established behavior |
|---|---|
| First argument | A 32-bit opaque value copied into the first word of a local request record. The current contents of that word are later supplied to each notification. |
| Second argument | An unsigned 32-bit value copied into the second request word. Independently, the original argument supplies the full-width comparison value and the low eight bits written on a mismatch. |
| Result | A 32-bit value, either 0 or 1 on normal completion. |

The function does not directly dereference the first argument. Dependencies receive the request record by address and may interpret or modify either word.

The second argument is not constrained to the byte range by the function. Values above 255 remain significant during comparison.

## Behavior

### 1. Read the global context three times

Initialization performs three distinct reads of the global context value, with different uses:

1. The first global read is saved as the context address used by subsequent explicit context-relative operations.
2. The second global read supplies a context whose +0x10 field is read. The resulting address is then read at +0x04 to obtain the initial traversal node.
3. The third global read supplies a context whose +0x10 field is read to obtain the initial candidate.

The second and third initialization accesses are **not** accesses through the saved context address. If the global changes between reads, the saved context, the context supplying the traversal root, and the context supplying the initial candidate can all differ.

After these reads, the function initializes the local request record with the first argument followed by the second argument, each occupying 32 bits.

Later explicit context-relative operations use the saved context address. The function does not refresh that saved address from the global. This fixes the address used for those operations, not the contents of the object at that address.

### 2. Traverse the links

For each nonzero traversal-node address, F-bcefa5957e76 receives, in order:

1. Saved context address plus 0x19.
2. Current node address plus 0x10.
3. Address of the local request record.

The function observes only whether the return value is zero:

- **Zero:** read the node’s +0x08 link. Set both the traversal node and the candidate to that link value.
- **Nonzero:** read the node’s +0x0C link. Set only the traversal node to that value.

A zero-result step therefore records the **destination link**, not the node just examined. A zero +0x08 link sets the candidate to zero and ends traversal.

The link read occurs after the dependency returns. Dependency-mediated changes to the node can therefore affect the link followed.

No less-than, greater-than, equality, predecessor, or successor semantics are established for these branches.

### 3. Check the candidate

Once traversal ends:

1. Read saved context +0x10 into a local boundary-like word.
2. Copy the candidate into a separate local word.
3. Call F-f063d8ade9f7 with the candidate-word address first and the boundary-word address second.

Both operands are addresses of local 32-bit words. Their contents cannot be assumed preserved by the call.

If the check returns nonzero, proceed to fallback selection without calling F-539f08165386 or making the additional comparison below.

If the check returns zero:

1. Call F-539f08165386 with the current candidate-word value.
2. Call F-bcefa5957e76 with saved context +0x19, the request-record address, and the returned value, in that order.
3. Retain the candidate only if this comparison also returns zero.

This comparison reverses the request record’s operand position relative to traversal: the request is second here and third during traversal.

The retained selection is taken from the candidate word when selection is copied. It is not guaranteed to equal the candidate originally supplied to the first check. Mutation through exposed local addresses is not ruled out.

### 4. Select a value and perform the decisive check

If both candidate-stage checks returned zero, use the current candidate-word value.

Otherwise, read saved context +0x10 again and use that fresh value as the fallback.

Then:

1. Copy the chosen value into a selected-value word.
2. Separately read saved context +0x10 into another boundary-like word.
3. Call F-f063d8ade9f7 with the selected-word address first and this boundary-word address second.

A fallback read and the following boundary read are distinct. The function does not independently require that their values match.

The final dependency result determines the branch:

- **Nonzero:** return 0. Do not directly access the associated byte, acquire a receiver, or issue either notification.
- **Zero:** continue using the selected word’s current value, including any modification by the dependency.

Fallback is not intrinsically rejection. It can reach byte handling if the final check returns zero. Likewise, a candidate retained by earlier checks can still be rejected here.

### 5. Compare and conditionally write the associated byte

For an accepted selection:

1. Read the associated-object address from selected node +0x14.
2. Read the unsigned byte at associated object +0x64.
3. Compare its numeric value with the original unsigned 32-bit second argument.

The comparison uses the byte’s value in the range 0–255 against the full argument. It does not truncate the argument before comparison.

If equal, return 1 without a direct byte write, receiver acquisition, or either notification.

If unequal:

1. Read the associated-object address again from selected node +0x14.
2. Write the original second argument’s low eight bits at associated object +0x64.
3. Acquire a notification receiver.
4. Issue the two notifications.
5. Return 1 if both calls return normally.

The write is exactly one byte. Its value is the original second argument modulo 256. No increment, saturation, or range rejection occurs.

The associated-object pointer is read separately for comparison and writing. If the field changes between those accesses, the object compared and the object written can differ.

Every argument above 255 necessarily mismatches the byte. Such an argument triggers the write-and-notify path after acceptance even when its low eight bits already equal the stored byte.

### 6. Acquire the receiver and notify

After the byte write, call F-9d0ecc5f6adf and use its result as the receiver for both notifications.

The notifications occur in this order:

1. Read notification token A from its global storage location after receiver acquisition. Invoke the receiver’s dispatch-table entry at +0x58 with the receiver, token A, and the current first request word.
2. After the first notification returns, read notification token B from its separate global storage location. Invoke the receiver’s dispatch-table entry at +0x58 with the same receiver value, token B, and the current first request word.

Neither token is captured at function entry or before receiver acquisition. Receiver acquisition may affect either token’s subsequently observed value. The first notification may affect the value read for token B.

The receiver’s dispatch-table pointer and callable entry are evaluated for each notification. The second target need not equal the first if relevant storage changes.

The first request word is also evaluated separately for each call. It need not equal the original first argument, nor need its two observed values match.

The supplied evidence does not establish an evaluation order among the dispatch lookup, token read, and request-word read within a single notification expression. It does establish the call boundaries above: acquisition precedes the first notification’s token read, and the first notification’s return precedes the second notification’s token read.

Notification return values do not determine the function result.

## Side effects

### Direct effects

The only explicit write to externally reachable object data is the conditional eight-bit write at associated object +0x64.

Other direct writes initialize or update local request and selection-related words. Several of those local addresses are exposed to dependencies.

Observable reads include:

- Three separate initialization reads of the global context.
- Context fields, node links, and selection-related fields.
- The associated-object pointer, read again on the write path.
- Separately timed reads of global notification tokens.
- Dispatch information and the first request word for each notification.

### Dependency-mediated effects

No supplied dependency contract establishes preservation of globals, pointed-to data, or exposed locals. Dependencies may affect later reads. This contract does not assume purity, non-reentrancy, allocation behavior, or absence of retained pointers.

A return of 0 does not imply no side effects: traversal and selection dependencies have already executed.

### Ownership and lifetime

The function contains no explicit allocation, release, ownership transfer, or reference-count adjustment.

Local storage has no lifetime extension supplied by this function. Whether a dependency retains an exposed local address is unknown.

Ownership of the selected object, associated object, extracted value, and receiver is unresolved. The same receiver value is reused for the second notification without an explicit retain, reacquisition, or validity check.

### Failure behavior

There is no explicit exception handling, rollback, retry, or synchronization.

If receiver acquisition or either notification fails to return normally, the byte write has already occurred. If the first notification does not return, the second notification is not reached.

Invalid addresses, invalid call targets, nonterminating traversal, or nonreturning dependencies can prevent normal completion. No additional error result is established.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Required accesses and calls are assumed valid unless the example specifically concerns failure.

1. **Different initialization contexts.**  
   If the three initial global reads yield three different context addresses, the first supplies the saved context, the second supplies the route to the initial traversal node, and the third supplies the initial candidate. Later explicit context-relative accesses use the first address.

2. **Accepted, unchanged byte.**  
   If the final check returns zero, the second argument is 7, and the associated byte is 7, return 1 without writing the byte, acquiring a receiver, or notifying.

3. **Accepted byte update.**  
   With final acceptance, stable associated-object addressing, argument 9, and stored byte 7, write byte 9 before receiver acquisition. If subsequent calls return, notify with token A, then token B, and return 1.

4. **Full-width mismatch despite equal low byte.**  
   With final acceptance, argument 263, and stored byte 7, write byte 7 and perform both notifications. The comparison is 7 against 263; only the write truncates.

5. **Final rejection.**  
   Any nonzero final check result produces 0 without direct associated-byte access or receiver acquisition.

6. **Candidate becomes null.**  
   A zero traversal comparison followed by a null +0x08 link leaves a null candidate. The visited node is not retained as the candidate.

7. **Early candidate rejection.**  
   A nonzero candidate check skips F-539f08165386 and the additional comparison. Selection uses a fresh saved-context +0x10 read.

8. **Fallback can be accepted.**  
   A fallback selection followed by a zero final check proceeds to byte handling, subject to valid dereferences.

9. **Receiver acquisition changes token A.**  
   If acquisition changes token A’s global storage before returning, the first notification uses the subsequently read value, not an entry-time snapshot.

10. **First notification changes token B.**  
    If the first notification changes token B’s global storage and returns, the second notification uses the value read afterward.

11. **Failure after mutation.**  
    If the first notification does not return normally, the byte has already been written and the second notification has not occurred. No rollback is provided.
