# F-5265e28451fc

## Purpose

F-5265e28451fc obtains a signed integer result through one of two paths selected by a dependency:

- A record-lookup path recognizes a fixed set of 21 record codes, selects one of 20 packed-byte entries, and converts three bytes into a signed 16-bit result.
- A structure-lookup path reads a signed 16-bit value from an optional secondary structure, falling back to a value in a primary structure when the secondary structure is absent or its value is zero.

Before selecting either path, the function invokes an indirect operation on its input object. A zero result from that operation causes an immediate return of −1.

These are established behaviors of the supplied static representation. The application-level meaning of the object, record codes, packed bytes, and returned values is not established. In particular, −1 is not an unambiguous error indicator: successful data conversion or structure lookup can also produce −1.

## Interface

### Input and representation

The function accepts one object address and returns an integer. The supplied representation uses 32-bit integer and address fields, 16-bit signed values, and 8-bit unsigned bytes. An independent ABI description was not supplied; the layouts below describe the represented interface.

Relevant input-object fields are:

| Byte offset | Width | Interpretation |
|---|---:|---|
| 0 | 32 bits | Address of a dispatch structure |
| 8 | 32 bits | Address of a state structure, used only on the structure-lookup path |

The dispatch structure contains an indirect callable entry at byte offset 8. The function calls that entry with the original object address as its explicit argument.

For dependency references, this contract assigns the opaque, specification-local ID **F-unknown-01** to that indirect callable. Its identity is not supplied, and the label does not imply a known implementation.

The state structure has two relevant address fields:

| Byte offset | Width | Interpretation |
|---|---:|---|
| 0 | 32 bits | Primary-structure address |
| 16 | 32 bits | Optional secondary-structure address |

The secondary structure supplies a signed 16-bit field at byte offset 40. The primary structure supplies a signed 16-bit field at byte offset 2312.

### Preconditions

The function performs no explicit null or bounds checks before reading the input object's dispatch address or calling its indirect entry. The object, dispatch structure, and callable entry must therefore be valid for those operations.

Additional validity requirements are path-dependent:

- The structure-lookup path requires the state-structure address to be readable. Its secondary-structure field may be zero.
- A nonzero secondary-structure address must permit a signed 16-bit read at offset 40.
- When fallback is required, the primary-structure address must permit a signed 16-bit read at offset 2312.
- The record-lookup path requires the dependency-selected record address and, for recognized codes, the selected three packed bytes to be readable.

No validation of these requirements is visible. Invalid addresses, invalid callable entries, and out-of-range record indices have no defined recovery behavior in the supplied evidence.

### Output

Every normally completed path returns either:

- −1 from an explicit rejection;
- a signed 16-bit field extended to the integer return width; or
- a computed value narrowed to signed 16-bit form and extended to the integer return width.

Consequently, every established normal return lies within −32768 through 32767. No separate status or output parameter distinguishes a rejected lookup from a legitimate result of −1.

## Behavior

### 1. Initial indirect operation

The function reads the dispatch-structure address from the input object, obtains the callable entry at dispatch offset 8, and invokes F-unknown-01 with the input object.

If its integer result is zero, the function immediately returns −1. It makes no subsequent dependency calls and performs neither result-lookup path.

If the result is nonzero, including a negative result, the function passes that result as the explicit argument to F-7e4f952e879e. It does not inspect that dependency's return value.

The function then calls F-03337e233941. Its result controls the remaining behavior:

- Zero selects the record-lookup path.
- Any nonzero value selects the structure-lookup path.

No other distinction among selector results is visible.

### 2. Record-lookup path

This path first calls F-7e4f952e879e again. Unlike the earlier invocation, the supplied representation shows no explicit argument for this call. This difference must not be resolved by assuming that the first argument is reused, cleared, or otherwise determined.

Next, the function calls F-6ae9471e3481 and uses its integer result as a record index.

Records have a stride of 12 bytes. The code field is a 32-bit integer at byte offset 8 within the selected record. Its address is formed from the then-current shared record-table base, the index multiplied by 12, and the field offset of 8.

There is no visible index-range check. Negative indices are not explicitly rejected. The evidence does not establish a record count, a signed-overflow policy for index scaling, or valid access behavior for addresses outside the table. Valid address formation and readable selected storage are therefore preconditions, not guaranteed outcomes.

### 3. Packed-byte conversion

For a recognized code, the function reads the first three bytes of the selected entry as unsigned values. The entries begin four bytes apart, but the fourth byte is not used by this function.

Let \(x\), \(y\), and \(z\) denote the first, second, and third byte values, each in the range 0 through 255. The decoded mathematical value before narrowing is:

\[
D = 1024(x - 96) + 32y + z - 3168
\]

Equivalently:

\[
D = 1024x + 32y + z - 101472
\]

The result is the signed 16-bit interpretation of the low 16 bits of \(D\), extended to the integer return width. Values outside the signed 16-bit range are not clamped or explicitly rejected.

Before narrowing, the possible mathematical range is −101472 through 168063. Computing that intermediate value does not itself require more than a signed 32-bit integer. The represented final multiply-and-shift operation expresses low-half extraction and sign extension; treating that expression as portable signed arithmetic in an arbitrary implementation language would require separate care.

No byte validation is visible. In particular, the function does not require any byte to be printable, alphabetic, nonzero, or within a narrower encoding range.

The supplied representation establishes which three byte positions contribute to the result, but not a strict temporal order among those byte reads.

### 4. Structure-lookup path

After a nonzero result from F-03337e233941, the function reads the input object's state-structure address, then the secondary-structure address at state offset 16.

If the secondary-structure address is nonzero, it reads the signed 16-bit field at secondary offset 40 and extends it to the integer return width.

- A nonzero value is returned directly.
- A zero value triggers fallback.

If the secondary-structure address is zero, fallback occurs without reading a secondary value.

For fallback, the function reads the input object's state-structure address again, obtains the primary-structure address at state offset 0, and reads the signed 16-bit field at primary offset 2312. That field is returned without further interpretation.

Thus, zero has different control significance at the two locations:

- A zero secondary value means “use the primary value.”
- A zero primary value is a valid final result.

A negative secondary value, including −1, is nonzero and suppresses fallback. No dependency call occurs between the secondary lookup and the fallback lookup.

## Side effects

The visible body performs no direct stores to the object, its referenced structures, the record table, or the packed-byte region. It does not explicitly allocate or release memory.

Dependency calls may have side effects. Their implementations and contracts were not supplied, so this contract does not assume that they:

- preserve shared state;
- preserve the input object's contents;
- retain or release any referenced resource;
- leave table selection or packed-byte contents unchanged; or
- return normally in every case.

The ordering of calls and subsequent reads is therefore significant:

1. F-unknown-01 runs before any call to a mapped dependency.
2. A nonzero indirect result is passed to the first invocation of F-7e4f952e879e.
3. F-03337e233941 runs after that invocation.
4. On the record path, the second invocation of F-7e4f952e879e and the call to F-6ae9471e3481 precede record selection.
5. On the structure path, state fields are read after F-03337e233941 returns.

An implementation must not substitute pre-call snapshots for these later reads without an independently established preservation guarantee.

The function exposes no explicit ownership transfer of its own. This does not establish that ownership is unchanged by its callees. It also provides no visible synchronization or coherent snapshot guarantee for concurrently changing data.

## Acceptance examples

These examples are conditional contract checks, not executed tests. They assume valid addresses, normally returning dependencies, and the stated values at the relevant read points.

### Early rejection

If F-unknown-01 returns zero:

- The result is −1.
- F-7e4f952e879e, F-03337e233941, and F-6ae9471e3481 are not called.
- No state-field or record lookup occurs.

### Nonzero selector and preferred secondary value

If F-unknown-01 returns a nonzero value, F-03337e233941 returns nonzero, and the secondary structure contains −12:

- The result is −12.
- The primary value is not read.
- F-6ae9471e3481 is not called.

The same rule applies to a secondary value of −1; it is returned as data rather than treated as a reason to fall back.

### Secondary fallback

If the structure path is selected and the secondary address is zero, a primary field of 245 produces 245.

If the secondary address is valid but its field is zero, a primary field of −300 produces −300.

If fallback reads a primary field of zero, the result is zero. There is no further fallback or rejection.

### Shared packed entry

If the record path selects code 0x6078 or code 0x6079, both codes select entry 19. With identical bytes observed there, both produce the same return value.

### Unrecognized record code

If the selected record code is 0x6069:

- The result is −1.
- The record-path dependency calls have already occurred.
- No packed entry is selected for decoding.

Being numerically between recognized codes does not make the code acceptable.
