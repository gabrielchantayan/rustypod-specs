# F-1e6fb4590882

## Purpose

F-1e6fb4590882 assembles temporary parameter records and coordinates two unconditional dependency operations, followed by an optional third operation.

A 32-bit mode selects the unconditional operation sequence. Three separate observations of a status byte affect two record-field selections and the decision to perform the optional operation. The function also reads global template sources, table entries, selectors, and request values.

**Established static evidence:** the supplied body establishes argument forwarding, branch conditions, dependency-call order, explicit 32-bit writes, and the timing of reads relative to calls.

**Inferred intent:** the transfer dependency appears to populate records from templates. F-8157a180d901 appears to obtain storage that the subsequent dependencies initialize. Neither interpretation establishes allocation units, ownership, successful construction, or record-retention rules.

The contract distinguishes a value explicitly written during preparation from a value present when a consumer receives the record. Intervening dependencies are not assumed to preserve exposed temporary storage.

## Behavior

### Record and source terminology

The following labels describe roles within this contract:

- **First record:** initially supplied with Template A.
- **Second record:** initially supplied with Template B.
- **Common record:** initially supplied with Template C.
- **Extended record:** supplied from the common record on the nonzero-mode path.
- **Optional record:** supplied with Template D when the final status test permits it.
- **Shared table base:** a global address-like value used for table lookup and to locate Template B.
- **Default selector** and **mode-one selector:** global 32-bit values used while preparing the common record.
- **Extension word:** a global 32-bit value used while preparing the extended record.
- **Extended request:** a global 32-bit argument supplied to F-8157a180d901.
- **Final word source:** an address-like global through which a 32-bit value is read.

**D-1** is a document-local opaque identifier for the external transfer dependency. No published function ID for it was supplied.

Every D-1 invocation supplies a destination address, a source address, and the count 104. Its implementation is unavailable. Statements about inherited template bytes are therefore conditional on D-1 performing the apparent byte transfer.

All record offsets below are byte offsets. Explicit field writes are 32 bits wide.

### 1. Prepare the first record

The function calls D-1 with the first record as destination, Template A as source, and count 104.

After D-1 returns, it captures the then-current shared table base for a later lookup.

It then reads the status byte. The selected table index is:

- 1 if status bit 0 is set and mode equals 1;
- 0 otherwise.

Using the shared table base read for this first lookup, the function reads the 32-bit entry at displacement four times the selected index. It writes that word at offset 72 of the first record.

The captured base and the base used by this lookup are distinct observations in the visible sequence. Their values are not required to remain equal under external mutation.

### 2. Prepare the second record

The function calls D-1 with:

- The second record as destination.
- A source located 224 bytes after the shared table base read for this call.
- Count 104.

After D-1 returns, the function reads the status byte again and applies the same index rule.

This lookup uses the base captured after the first D-1 call, not a fresh global-base read. The selected 32-bit entry is written at offset 72 of the second record.

Consequences:

- The two status observations can select different entries.
- The second record’s source address and its table-entry lookup can derive from different base values.
- A dependency-induced change to the global base does not replace the already captured base used for the second lookup.
- Capturing an address does not freeze the contents at that address.

Both first and second records are prepared regardless of which one the mode-selected consumer will receive.

### 3. Prepare the common record

The function reads the default selector. If mode equals 1, it also reads the mode-one selector and uses that value instead.

It then calls D-1 with the common record as destination, Template C as source, and count 104. After D-1 returns, it writes the previously selected 32-bit value at offset 64 of the common record.

The selector is obtained before this D-1 call and written afterward. A change to the selector’s global source during the call does not itself cause a reload.

This establishes the write, not indefinite preservation of the written value. D-1 has received the common record’s address. Its pointer-retention and shared-state behavior are unknown.

### 4. Perform the mode-selected pair of operations

#### Mode equals 0

The call sequence is:

1. F-8157a180d901 with request 560.
2. F-60fe53f7ab39 with that result, zero, both context words, and the first record.
3. F-8157a180d901 with request 544.
4. F-7f6becd152e6 with that result, zero, both context words, and the common record.

Each call must return before the next listed call is reached.

Both earlier table selections use index 0 because mode is not 1. The function has written the default selector at common-record offset 64 before this sequence begins.

It does **not** establish that F-7f6becd152e6 observes that selector unchanged. Between the write and consumer entry, both F-8157a180d901 calls and F-60fe53f7ab39 execute. The common-record address has already been exposed to D-1, so indirect mutation cannot be excluded.

#### Mode is nonzero

This branch includes mode 1 and all other nonzero 32-bit values.

First:

1. Call F-8157a180d901 with request 560.
2. Call F-60fe53f7ab39 with that result, zero, both context words, and the second record.

After F-60fe53f7ab39 returns, call D-1 with the extended record as destination, the common record as source, and count 104.

Under the byte-transfer interpretation, this transfers the common record’s contents as supplied by that operation. In particular, the extended record’s offset-64 bytes come from the common record’s **then-current** offset-64 bytes. They are not unconditionally the selector originally written there: F-8157a180d901 and F-60fe53f7ab39 have intervened, and the common-record address was already exposed to D-1.

After this transfer returns, the function performs these 32-bit writes in order:

| Extended-record offset | Written value |
|---:|---|
| 48 | 0 |
| 104 | 30 |
| 108 | Extension word read during this preparation |
| 112 | 2 |
| 116 | 25 |
| 120 | 5 |

The extension word is read after the offset-104 write and used for the offset-108 write.

The last five fields lie beyond the 104-byte transfer range. The explicit layout therefore extends through byte 123, requiring 124 bytes of temporary storage for the described preparation.

Next:

1. Read the extended request and call F-8157a180d901 with it.
2. Call F-4a73b9be0f3a with that result, zero, both context words, and the extended record.

The six writes are established events. Their values at F-4a73b9be0f3a entry are not unconditional guarantees: the intervening F-8157a180d901 call may affect storage whose address D-1 has received.

Likewise, even if the extended transfer obtains the originally selected common-record selector, that alone does not establish preservation through consumer entry.

### 5. Decide and perform the optional operation

After the selected pair of operations returns, the function reads the status byte a third time.

If bit 0 is clear, no optional operation is performed.

If bit 0 is set:

1. Call D-1 with the optional record as destination, Template D as source, and count 104.
2. Read the address-like final word source and the 32-bit value it references.
3. Write that value at offset 100 of the optional record.
4. Call F-8157a180d901 with request 560.
5. Call F-60fe53f7ab39 with that result, zero, both context words, and the optional record.

The final status observation is independent of both earlier observations. Earlier clear observations do not prevent this operation; earlier set observations do not require it.

The offset-100 write occurs after the Template D transfer and before the final F-8157a180d901 call. Its continued presence at consumer entry requires preservation across that call. There is no further visible status test during the optional sequence.

### Temporary storage and aliasing

The function’s explicit stores target temporary parameter storage belonging to this invocation. Calls may have additional effects not established here.

The optional record starts 20 bytes into the extended record’s storage. Its 104-byte transfer range overlaps extended-record bytes 20 through 123. The optional record’s offset-100 field is the same storage as the extended record’s offset-120 field.

Thus, optional preparation reuses storage previously passed to F-4a73b9be0f3a on the nonzero path. Under the byte-transfer interpretation, it can overwrite that earlier record’s contents.

No temporary record is explicitly cleared on return. No visible mechanism extends its lifetime beyond the invocation. A consumer that retains a record address may encounter later mutation within the invocation and expired storage afterward.

These facts do not establish that consumers retain pointers, copy records, or finish all reads synchronously. Those contracts remain unknown.

### Preservation boundaries

No dependency is assumed to preserve:

- Global values or pointed-to data.
- Previously exposed temporary records.
- Status memory.
- Table contents.
- Other dependencies’ state.

A prepared field can therefore be specified unconditionally as an actual write at a particular point, but not as an unchanged consumer-visible value across intervening calls.

There is no direct call between each F-8157a180d901 return and its associated consumer invocation. This does not negate mutations performed during that preceding call.

### Results, ownership, and errors

Every F-8157a180d901 result is forwarded without inspection. A zero result is still passed to the associated consumer if execution continues normally.

There is no explicit release, rollback, or failure cleanup. This is not proof of a leak: the result’s meaning and ownership rules are unavailable.

If any reached operation faults, terminates, throws, or fails to return, later operations are not reached through the visible normal sequence. The function supplies no local handling for those outcomes.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests.

Assertions about writes below describe events performed by F-1e6fb4590882. Assertions about record contents at consumer entry require the additional preservation conditions explicitly stated.

### Mode 0, all three status observations clear

Given valid accessed memory and normally returning dependencies:

- Both table lookups select index 0.
- The function writes the selected default selector at common-record offset 64.
- Request 560 precedes F-60fe53f7ab39 with the first-record address.
- Request 544 precedes F-7f6becd152e6 with the common-record address.
- No optional request or consumer call occurs.

If every intervening dependency and other actor preserves the common record’s offset-64 bytes after the selector write, F-7f6becd152e6 receives those bytes containing the selected default value. Without that condition, the write remains required but the consumer-entry value is unresolved.

### Mode 1, all three status observations set

Given a stable table base and stable table contents during both lookups:

- Both offset-72 writes use table entry 1.
- The common-record offset-64 write uses the mode-one selector read before the Template C transfer.
- Request 560 precedes F-60fe53f7ab39 with the second-record address.
- The common-to-extended D-1 call occurs after that consumer returns.
- The six extended-record field writes occur in the documented order.
- The extended request precedes F-4a73b9be0f3a with the extended-record address.
- The optional sequence occurs.

Under faithful byte-transfer semantics, the extended record obtains the common record’s offset-64 bytes as transferred. To require those bytes to equal the originally selected mode-one value, additionally require preservation of the common-record field from its write through the extended transfer.

To require F-4a73b9be0f3a to observe that selector and the six explicitly written fields, additionally require preservation of the corresponding extended-record bytes through consumer entry, including across the intervening F-8157a180d901 call.

### Mode 2, all three status observations set

Mode 2 takes the nonzero branch without mode-one selection:

- Both table lookups select index 0.
- The common-record offset-64 write uses the default selector.
- F-4a73b9be0f3a is the second unconditional consumer.
- The optional operation occurs.

The extended record is not unconditionally guaranteed to retain the original default selector. That conclusion requires both faithful transfer and preservation of the common selector through transfer. Observing it at consumer entry additionally requires preservation of the extended field afterward.

All other nonzero values except 1 have this branch classification, including negative signed 32-bit values.

### Intervening mutation of the common selector

Suppose mode is 1 and the function writes the selected mode-one value at common-record offset 64. An intervening dependency then changes those bytes before the common-to-extended transfer.

Under faithful byte-transfer semantics, the extended transfer obtains the changed bytes, not necessarily the original selector. The function performs no selector rewrite in the extended record.

### Status changes between observations

With mode 1, a clear first observation and set second observation select entries 0 and 1 respectively. If the third observation is clear, the optional operation is omitted.

Conversely, a status bit becoming set only before the third observation permits the optional operation even if both earlier lookups selected entry 0.

### Zero request result

If F-8157a180d901 returns zero and control continues, the associated consumer receives zero as its first argument. A zero-triggered early return or skipped consumer call is not supported.
