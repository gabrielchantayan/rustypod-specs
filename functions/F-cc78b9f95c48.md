# F-cc78b9f95c48

## Purpose

F-cc78b9f95c48 constructs a table of per-record sequence boundaries using metadata and a stream. For each processed record, it decodes offsets, requests a contiguous payload allocation, reads payload bytes, and constructs an array of boundary addresses. A nonnegative record-control field enables one indirect callback per sequence.

The interpretation as variable-length byte sequences is **inferred intent**. The established behavior is the sequence of memory accesses, dependency calls, status checks, and boundary calculations described below. The payload format and callback semantics are unknown.

A checked failure during record processing triggers cleanup over the context’s then-current table and record count, not merely over completed records. Safe cleanup therefore depends on initialization and dependency behavior not established here.

## Interface

### Input and result

The input is a 32-bit address of a mutable context. The result is a 32-bit signed status.

- Zero means the explicitly checked allocation and stream operations reported success.
- A nonzero result comes from an allocation status output or a checked stream operation. No local error-code translation is visible.
- There is no explicit validation of the context, metadata, stream, callback object, decoded offsets, or allocation contents.
- Unchecked operations can have effects or failures not represented by the returned status.

### Context layout

Offsets are in bytes. Addresses and fields occupy 32 bits.

| Offset | Interpretation | Access pattern |
|---|---|---|
| 100 | Memory-management context | Captured at entry. |
| 136 | Callback-bearing object address | Captured at entry. |
| 300 | Record count | Passed as a word to initial allocation; repeatedly read as signed for processing and cleanup. |
| 304 | Metadata-array address | Read when selecting each record. |
| 308 | Base stream offset | Read separately for each seek. |
| 316 | Output-table address | Overwritten after initial allocation; reread during failure cleanup. |
| 328 | Stream-object address | Captured at entry. |

Metadata records have a 252-byte stride:

| Record offset | Width and interpretation |
|---|---|
| 4 | Signed 32-bit callback control. |
| 240 | Unsigned 32-bit sequence count, called **N** below. |
| 244 | 32-bit offset-table location relative to the base stream offset. |
| 248 | 32-bit encoded-width field. |

The captured callback-bearing object contains a callable address at byte offset 16. That callable address is reread for each invocation.

### Output representation

Each output-table entry occupies eight bytes:

| Entry offset | Meaning |
|---|---|
| 0 | 32-bit sequence count, written after callback processing. |
| 4 | 32-bit address of an array requested to contain N + 1 four-byte boundary addresses. |

Boundary element zero receives the payload allocation’s returned address. Elements one through N are constructed from adjacent decoded-offset differences. Element N is a terminal boundary, not an additional callback item.

Normal processing retains a local address derived from the initial table allocation and advances it by eight bytes after each record. Changing context offset 316 does **not** redirect those normal-path entry writes. Failure cleanup instead obtains its addresses through the context.

Consequently, successful return leaves the output allocations reachable through context offset 316 only if dependencies and callbacks preserve the relevant table address and allocation structure.

## Behavior

### Initial allocation

Entry captures occur in this order: memory-management context, stream address, then callback-bearing object address. Temporary offset storage starts with a null address and zero capacity.

F-6dd003795db7 receives the captured memory-management context, element width eight, old count zero, the context’s record-count word, a null existing allocation, and an address for a 32-bit status output.

The returned table address is written to context offset 316 **before** checking status. The function also retains that address locally for normal record processing.

If the status is nonzero:

- Record processing and table cleanup are skipped.
- The temporary-storage release call still occurs with a null address.
- The allocation status is returned.

The previous value of context offset 316 is overwritten without a visible release. A nonnull address returned with initial allocation failure is neither cleared nor released by this branch.

### Record selection and temporary capacity

After successful initial allocation, processing begins at record index zero. Each loop condition rereads the context record count and compares it with the signed index. A signed nonpositive count therefore prevents record processing, but only after that count word has already been supplied to the allocator.

For each selected record, the function computes its address from the current metadata-array base and the 252-byte stride. It captures the signed callback control and unsigned N. Subsequent metadata-array-base changes do not relocate this already selected record.

The required offset count is N + 1, evaluated with 32-bit unsigned arithmetic. If temporary capacity is smaller, F-6dd003795db7 is called with:

- Element width four.
- The previous capacity and existing temporary address.
- Requested capacity equal to N + 4, wrapped to 32 bits and then rounded down by clearing its low two bits.
- The status-output address.

The returned address replaces the temporary address before status is checked. Failure enters table cleanup. Success commits the requested capacity.

Without arithmetic wrap, this rounds N + 1 upward to a multiple of four and reuses storage without shrinking it. That property does not hold across wrap. For N = 4,294,967,292, the required count is 4,294,967,293 but the requested rounded capacity is zero. Existing capacity four therefore causes a resize request from four elements to zero. The allocator’s response and ownership effects remain unknown.

### Offset-table acquisition and decoding

The function calls F-e40a3ceddab2 with the captured stream and a seek target formed from the currently read context base offset plus the selected record’s offset-table location.

Only if positioning succeeds does it call F-d036abe1e536. The acquisition byte count is the record’s full 32-bit width field multiplied by the previously computed N + 1. This is a 32-bit calculation, not an explicitly widened size calculation.

Either nonzero status enters table cleanup. No acquisition-finalization call is made on these checked failure branches.

After successful acquisition:

1. A 32-bit address is read from stream offset 32 into a local cursor.
2. F-d8b79fc4b172 is called for indices zero through N inclusive.
3. Each call receives the cursor’s address and the low eight bits of the selected record’s width field.
4. Each returned 32-bit value is stored in the corresponding temporary-offset element.
5. F-9787e15c337d is called after decoding finishes; its result is not checked.

The width field is read for acquisition sizing and read again for each decoder call. It is not a single captured width value. Even without mutation, the acquisition uses all 32 bits while the decoder receives only eight. No consistency check is visible.

For N = 4,294,967,295, the unsigned inclusive decoding loop cannot terminate by exceeding N: its index wraps to zero. No safe memory behavior is established for that case.

### Pointer-array allocation and payload read

After acquisition finalization, the function reads the last decoded offset and then the first decoded offset. Those saved values supply the endpoint difference used for payload-allocation size and payload-read size.

It requests a new pointer array through F-6dd003795db7, using element width four, old count zero, count N + 1, and a null existing address. The returned address is written into the current locally addressed output entry before its status is checked.

If successful, F-3ce007b692cc is called with the captured memory-management context, the saved last-minus-first difference, and the status-output address. Its returned address is written to boundary element zero before that status is checked.

If payload allocation succeeds:

- F-e40a3ceddab2 is called using the currently read context base offset plus the **then-current first temporary offset**.
- If positioning succeeds, F-0c21b5cad025 receives the stream, the address then stored in boundary element zero, and the difference computed from the saved endpoints.

This distinction matters if a dependency mutates accessible state: the payload seek rereads the first offset after the allocation calls, while the payload size comes from the earlier endpoint reads.

A nonzero status from pointer-array allocation, payload allocation, payload positioning, or payload reading enters cleanup. No local check establishes ordered offsets, representable subtraction, stream bounds, or a destination large enough for later boundary construction.

### Boundary construction and callbacks

Following a successful payload read, boundary elements one through N are written in ascending order. Each is the preceding boundary address plus the difference between the corresponding adjacent temporary offsets.

With stable, nondecreasing offsets and representable arithmetic, these addresses delimit the sequences inside the payload. Those conditions are not enforced.

Every boundary-loop condition evaluation reads an unnamed 32-bit global callback argument, including the final unsuccessful evaluation. The value read on that final evaluation is retained for the callback phase. This read also occurs when N is zero. The global is not reread between callbacks.

If the captured signed control is nonnegative, callbacks run for indices zero through N − 1 in ascending order. Each receives:

1. The address read from the corresponding boundary element.
2. The difference between the next and current temporary offsets.
3. The retained global argument.

The callable address is read from offset 16 of the captured callback-bearing object for each invocation. No callback return value is checked. Sequence addresses and lengths are read as the invocations occur; they are not all captured before the first callback.

After the callback phase, the function writes the captured N into the current output entry’s count field, advances its local entry address by eight bytes, and checks the next record index against the context count.

Thus, the current record’s count is not committed before its callbacks.

### Checked-failure cleanup

A checked processing failure first tests whether context offset 316 is nonnull. If it is null, table cleanup is skipped.

Otherwise, cleanup iterates from index zero using a signed comparison against the record count reread from the context. For each index:

1. Read the pointer-array address through the context’s current table address.
2. **Only if that initially read pointer-array address is nonnull:**
   - Pass its first word to F-bf7242c98d06 as the payload address.
   - Reread the table and pointer-array addresses through the context.
   - Write zero into the reread pointer array’s first word.
3. Pass the pointer-array address currently obtained through the context to F-bf7242c98d06, including when it is null.
4. Reread the table address through the context and clear that entry’s pointer-array field.

The first-word clear in step 2 is conditional on the address read **before** the payload-release call. The reread pointer-array address is **not checked again**. Dependency mutation can therefore turn that write into an invalid access or redirect it to different storage.

The table’s nonnull guard is likewise not repeated before each subsequent context-based access. Cleanup does not retain one immutable table snapshot.

After the entry loop, the function passes the current context table address to F-bf7242c98d06 and then clears context offset 316.

Cleanup covers the then-current record count, including entries never successfully processed. It does not clear count words before releasing the table.

### Final release and return

Every visible normal-return path calls F-bf7242c98d06 with the current temporary-offset address, including null. The stored status is then returned.

No rollback of stream position, payload writes, callback effects, or other dependency mutations is visible.

## Side effects

### Storage and ownership

The function requests storage for the output table, temporary offsets, per-record boundary arrays, and payload blocks. Visible cleanup treats boundary element zero as the payload allocation address; later boundary elements are not individually released.

The temporary storage is submitted for release on every normal return. This establishes a release request, not the release dependency’s actual ownership behavior.

No explicit bulk initialization of the output table or newly allocated boundary arrays is visible. Failure cleanup can therefore encounter:

- Unprocessed table entries.
- A pointer array whose payload allocation was never attempted.
- Addresses returned by failed allocations.

Safe cleanup requires suitable allocator initialization and failure guarantees, or equivalent state supplied by dependencies. Those guarantees are unknown.

Normal entry writes continue through the retained initial-table address even if a dependency changes context offset 316. Cleanup follows the context instead. This can separate the storage being constructed from the storage later traversed or exposed to the caller. Unconditional success-path reachability or complete failure-path reclamation is therefore not established.

### Stream and external state

Per-record stream operations occur in this order: offset-table positioning, acquisition, decoding, acquisition finalization, payload positioning, payload read. Failures stop that sequence at the checked operation.

The original stream position is not restored. Partial-read contents and failure-position behavior depend on the stream dependencies.

Callbacks may affect payloads, output entries, metadata, context fields, globals, or other accessible state. Neither callbacks nor other dependencies are assumed to preserve globals or release—or retain—any particular allocation.

### Wrapped capacity request

With current temporary capacity four and N = 4,294,967,292, the capacity comparison requests a resize from four to zero. A successful status commits capacity zero. This is not a guarantee of adequate storage for the subsequent decoding; actual allocator behavior and execution safety remain unresolved.

### Null cleanup entry

If a processing failure enters cleanup and an entry’s initially read pointer-array address is null, the payload release and first-word clear are skipped. The pointer-array release is still called with the address then read through the context, and the entry field is cleared.

If that address remains null, no boundary-element dereference occurs for this entry.

### Mutation during payload release

If an initially nonnull cleanup pointer-array address causes a payload-release call, and that dependency changes the context-based pointer-array address to null, the following first-word clear still proceeds through the reread null address. No second nonnull check protects it. Safe completion cannot be claimed under that mutation.

### Changed table field during normal processing

If a callback replaces context offset 316 but leaves the original table valid, the current count write and subsequent normal entry writes still target the retained original table address. The replacement does not redirect construction. A later checked failure instead consults the replacement context value for cleanup.
