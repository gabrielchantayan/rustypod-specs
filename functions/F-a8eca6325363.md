# F-a8eca6325363

## Purpose

F-a8eca6325363 creates and initializes a context, invokes a loading dependency, conditionally reconciles result dimensions and metrics, optionally requests a buffer adjustment and writes a terminating zero byte, and conditionally publishes the current result address. A nonzero context subsequently receives two ordered cleanup calls.

“Loading,” “metrics,” “buffer adjustment,” and “cleanup” describe inferred roles. The established behavior consists of the accesses, conditions, assignments, and calls below. Dependency names do not establish allocation, preservation, ownership, or successful release.

The returned 32-bit status and the caller’s output slot are separate outputs. Publication can be skipped. When publication occurs, cleanup follows it, so publication alone does not establish that the published object remains valid.

The pointer slot is not the caller’s output storage.

## Behavior

### Creation and initialization

The function initializes the status and pointer slots, then invokes F-3ce007b692cc with these arguments, in order:

1. Allocation handle.
2. Global opaque value.
3. Status-slot address.
4. Caller’s output-slot address.
5. Input handle.
6. Allocation handle again.

The returned context address is captured and retained throughout the function.

A nonzero status skips initialization, loading, processing, and publication. A nonzero returned context still reaches cleanup.

With zero status:

1. A zero options argument is replaced by the global default address.
2. The selected address is written to context `+0x24`.
3. A **16-bit** value `0x7FFF` is written at context `+0x0C`.
4. The allocation handle is written to the globally selected context location.
5. Zero is written to `+0x2028`, `+0x202C`, `+0x2030`, and `+0x2034`, in that order.
6. The allocation handle is written to `+0x2034`.

The initial write at `+0x0C` is not a 32-bit initialization. The zeroing and subsequent overwrite of `+0x2034` are distinct writes.

### Loading and diagnostic state

F-d84a3ea80626 receives the input handle, another global opaque value, the captured context address, and the pointer-slot address. Its returned status replaces the status slot.

The global diagnostic-state base is then captured, even if loading returned a nonzero status. Nonzero loading status bypasses result processing and publication.

Each later level-gated diagnostic independently reads the signed 32-bit level at captured base `+0xDC` and requires a value greater than 1. Replacing the global base does not replace this captured address; changing the storage at the captured address can affect later gates.

The loading-status gate is not repeated after diagnostics.

### Initial result processing

The current result address is captured from context `+0x20`. Zero skips this initial processing block.

For a nonzero captured result:

1. Its discriminator at `+0x1C` is compared with 8.
2. If different, its 16-bit width at `+0x04` is copied to its `+0x20`. Both accesses use the captured address.
3. Its count sum is compared with context `+0x04`. Each count expression obtains its result address from context `+0x20`, rather than using the earlier capture.
4. On mismatch, a fresh diagnostic-level check can cause F-4457a9a44a68 to receive a global message.
5. After that optional call, context `+0x20` is reread and the selected result’s 16-bit marker is set to 1.

The count operands are signed 32-bit values. Their addition precedes comparison with the unsigned 32-bit expected count; the comparison therefore involves unsigned conversion. Signed addition overflow is not given a portable outcome by this contract.

A diagnostic can redirect the marker write. No new null check protects its destination. Count mismatch does not directly assign status. The width copy does not itself set the marker.

### Reconciliation gates

The current options address is read from context `+0x24`, and its first 32-bit word is tested. This is not necessarily the address or contents selected during initialization.

If that word is nonzero:

1. A new result address is captured from context `+0x20`.
2. Its first count at `+0x34` is read.
3. Only when that count is zero is its second count at `+0x40` read.
4. Reconciliation proceeds if either inspected count is nonzero.

Both count reads use this new capture. The gate tests individual counts, not their sum. The captured result also supplies the width operand for the first metric comparison.

### Ordered metric reconciliation

The order is width, horizontal origin, upper metric, lower metric, height, then the flag-`0x1000` diagnostic.

For each mismatching metric, a fresh level check can invoke F-4457a9a44a68 before correction. Corrective expressions reread context values and destination result addresses; they do not reuse comparison operands as immutable snapshots.

**Width.** The maximum and minimum are each obtained by reading a 32-bit unsigned context element at `+0x10` and `+0x0C`, respectively, and converting it to signed 16 bits. Their promoted difference is compared with the zero-extended 16-bit width from the reconciliation-gate result capture.

On mismatch, after any diagnostic, both 32-bit context elements are read and converted again. The difference is narrowed to 16 bits and written to `+0x04` of a result selected by rereading context `+0x20`. Another result-pointer read selects the marker destination.

**Horizontal origin.** A newly selected result’s signed 16-bit origin is compared with the effective minimum obtained from a **32-bit** context read at `+0x0C` followed by signed-16-bit conversion.

On mismatch, the correction repeats that context read and conversion, writes the resulting 16-bit value to a freshly selected result’s `+0x08`, and separately selects the marker destination.

**Upper metric.** A newly selected result’s signed 16-bit value at `+0x0C` is compared with an **explicit signed 16-bit read** at context `+0x12`.

On mismatch, the 16-bit contents at context `+0x12` are read again and copied to a freshly selected result’s `+0x0C`. A separate result-pointer read selects the marker destination.

**Lower metric.** A newly selected result’s signed 16-bit value at `+0x0E` is compared with a 32-bit unsigned context read at `+0x14`, converted to signed 16 bits.

On mismatch, after any diagnostic:

1. Context `+0x14` is read as a 32-bit unsigned element and converted again; its effective 16-bit value is copied to a currently selected result’s `+0x0E`.
2. Another 32-bit read and signed-16-bit conversion at context `+0x14` supplies the value whose negation is narrowed to 16 bits and written to a currently selected result’s `+0x0A`.
3. Another result-pointer read selects the marker destination.

These are separate reads and writes. Aliasing can make the first write affect the next read. A matching lower metric does not independently repair `+0x0A`.

**Height.** An explicit signed 16-bit read at context `+0x12` is added to the effective lower metric derived from a 32-bit unsigned read at `+0x14` and signed-16-bit conversion. The promoted sum is compared with a newly selected result’s zero-extended 16-bit height.

On mismatch, those differently sized context expressions are evaluated again. The recomputed sum is narrowed to 16 bits and written to a freshly selected result’s `+0x06`. **No marker write accompanies this correction.**

Signed-16-bit differences range from −65535 to 65535; sums range from −65536 to 65534. These promoted calculations fit signed 32 bits. The dimension comparisons convert the signed computed quantity to unsigned 32 bits; a negative result cannot equal a zero-extended 16-bit dimension.

Finally, context flag `0x1000` causes a level-gated diagnostic. This check remains inside both reconciliation gates.

### Flag-controlled diagnostic

If set:

1. The first global message value is read.
2. Context flags are read again to test `0x20`.
3. When `0x20` is clear, an alternative global message is read and selected instead.
4. F-4457a9a44a68 receives the selected message and current pointer-slot contents.

The first message read occurs even when replaced. This diagnostic has no level gate.

### Missing result, resizing, and termination

If zero, status becomes 3 only if it is currently zero. Publication then follows.

2. The value 1.
3. Captured length.
4. Captured length plus 1.
5. Buffer address from captured result `+0x54`.

2. The returned buffer address is stored at that result’s `+0x54`, even on reported failure.
3. Nonzero status skips termination and publication.
4. Otherwise, context `+0x20` and the selected result’s length are read again.

## Side effects

There is no entry-time output initialization. Creation failure, loading failure, and resize failure omit the final publication write, but dependencies may already have modified caller-visible storage.

Dependencies may mutate reachable objects, globals, or previously exposed local slots. Their apparent diagnostic or cleanup roles impose no preservation guarantee. Explicit captures remain captured; explicit reloads observe the storage then present.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, assume valid non-overlapping storage, stable unrelated state, representable arithmetic, and preservation of status after the specified assignments.

1. **Ordinary publication.** Loading succeeds with a nonzero result, matching counts, reconciliation disabled, flag `0x01` clear, and zero length. A mode other than 8 still causes the width copy. The current result is published, cleanup is called, and zero is returned.

2. **Missing result.** The final pre-buffer result capture is zero and status is zero. Status becomes 3. If the result field remains zero, publication writes zero. Returning 3 additionally requires cleanup to preserve status.

3. **Loading failure.** A nonzero loading return skips processing and publication. A nonzero context still receives both cleanup calls. The output is not guaranteed unchanged because creation received its address.

4. **Expression width versus metric width.** A 32-bit minimum element with numeric value `0x1234FFFE` yields effective minimum −2; a maximum element `0x56780005` yields effective maximum 5. Their width difference is 7. The source expressions remain 32-bit reads despite the signed-16-bit metric interpretation. This example does not determine other overlapping fields or physical load widths.

5. **Initialization width.** Initialization writes 16 bits at `+0x0C`; it does not initialize the whole 32-bit element later used by minimum expressions. Validity of subsequent 32-bit expression accesses remains required.

6. **Diagnostic redirects correction.** A width mismatch enables a diagnostic that changes the effective maximum from 10 to 12, leaves minimum zero, and switches the result address. Correction rereads the 32-bit metric elements and writes width 12 to the replacement result, then separately selects the marker destination.

7. **Height-only correction.** Upper and effective lower metrics are 8 and 2. All other compared metrics match, but height is 9. Height becomes 10 without a marker write. A matching lower metric leaves an inconsistent negated-lower field unrepaired.

8. **Individual-count gate.** Counts 1 and −1 enable reconciliation when options permit it, although their sum is zero.

9. **Resize redirects result.** Resizing receives length 4 from one result, returns address B with zero status, and redirects the current result to another object with length 7. B is stored in the replacement object, and termination writes at B plus 7, assuming sufficient storage.

10. **Resize failure.** A nonzero resize status still permits storing the returned address through the refreshed result pointer. Termination and publication are skipped.

11. **Boundary dimensions.** Effective maximum 32767 minus minimum −32768 equals 65535 and can match unsigned width 65535. A negative difference cannot match; correction narrows it to 16 bits.
