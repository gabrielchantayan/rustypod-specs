# F-3669943b6ca4

## Purpose

F-3669943b6ca4 searches a table of fixed-size records using an unsigned key derived from a caller-supplied cursor. On success, it replaces the cursor with the selected record’s key and returns that record’s 16-bit payload plus one. On failure, it writes zero to the cursor and returns zero.

For a stable table whose keys are ordered nondecreasingly, and whose indexing arithmetic does not overflow, the selected key is the smallest key greater than or equal to the cursor’s incremented value. The cursor increment uses 32-bit unsigned arithmetic, so an incoming cursor of 4,294,967,295 produces a search target of zero.

The apparent intent is ordered enumeration of keyed records. That interpretation is inferred; the established behavior is a binary search followed, when necessary, by a candidate lookup. There is no independent validation that the table is ordered, that its storage is valid, or that the caller is using the cursor for enumeration.

## Interface

The function accepts two arguments:

- **Object address:** identifies a memory region containing a table count and table address.
- **Cursor address:** identifies a readable and writable 32-bit unsigned value. Its initial value determines the search target; its final value reports the selected key or zero.

It returns an integer with the following established values on normal completion:

- **0:** no candidate was selected.
- **1 through 65,536:** the selected record’s unsigned 16-bit payload, increased by one.

These ranges are disjoint. A selected record whose key is zero is therefore distinguishable from failure by the return value.

## Behavior

### Initial observations

The explicit memory-read order begins with:

1. Reading the table address from object offset +20.
2. Reading the incoming cursor.
3. Reading the initial record count from object offset +16.

The search target is the incoming cursor plus one, reduced modulo 2³². Thus, an incoming cursor of zero searches for a key at least one; an incoming cursor of 4,294,967,295 searches for a key at least zero.

The table address is retained after its initial read. It is not explicitly reloaded later in the call.

### Search and selection

The search initially considers record indices from zero through one less than the initial count. Keys and index comparisons use unsigned values.

A midpoint record is examined during each search iteration. Its key determines the next action:

- An exact match selects that record immediately.
- A key below the target eliminates that midpoint and the lower portion of the current search interval.
- A key above the target excludes that midpoint and the higher portion while retaining its index as the upper boundary.

Under stable, ordered, non-overflowing conditions, the interval narrows either to an exact match or to the insertion position for the target.

An exact match does not trigger a further search for an earlier equal key. Consequently, duplicate keys do not imply selection of the first duplicate. The selected duplicate is the one encountered by the midpoint search.

If no exact match is found, the function explicitly reads the count field again. It then compares the candidate index against this newly read count:

- If the candidate index is below the newly read count, the candidate record is selected.
- Otherwise, the function reports failure.

This second count read is observable and conditional. Exact-match selection bypasses it. The second count is not used to restart or expand the search.

For an unchanged sorted table, the candidate selected after a nonmatching search is the first record whose key exceeds the target. Combined with the exact-match path, this gives a selected key greater than or equal to the target.

### Result construction

For an exact match:

- The output key is the target value, already known to equal the examined key.
- The selected record’s payload is read.
- The cursor is written with the output key.
- The return value is the payload plus one.

For a candidate selected after the search:

- The candidate’s key is read.
- Its payload is read.
- The cursor is written with that key.
- The return value is the payload plus one.

For failure:

- No selected-record payload is read.
- The cursor is written with zero.
- The return value is zero.

Payload arithmetic does not wrap at 16 bits. The unsigned 16-bit payload is promoted before addition, so a payload of 65,535 produces a return value of 65,536.

### Arithmetic boundaries

The target increment is explicitly unsigned and wraps at 32 bits.

The midpoint is computed by adding the two unsigned 32-bit search boundaries and then shifting right by one. It is not expressed as a subtraction-based, overflow-avoiding midpoint. If the boundary sum exceeds 4,294,967,295, it wraps before the shift.

Accordingly, ordinary binary-search correctness is conditional on avoiding midpoint overflow. With extreme counts or indices, the midpoint need not remain within the intended interval, and the usual progress argument no longer applies. Termination and selection of the mathematical lower bound are not established for those cases.

Record addressing uses the eight-byte stride. The supplied material does not establish safe behavior when stride multiplication or address addition exceeds the usable address range.

### Empty and mutable tables

With a stable count of zero:

- No table key or payload is read.
- The count is still read initially and again during candidate validation.
- The cursor is set to zero.
- The return value is zero.

The initial table-address read still occurs even though the table is empty.

If the count changes between its two reads, the final candidate check uses the newer value but the completed search reflects the initial value and the keys observed during that search. For example, an initially empty table can reach a candidate read at index zero if the later count is positive. Such observations do not establish synchronization support or define behavior under a language-level data race.

## Side effects

The only explicit write is a single 32-bit store through the cursor address on normal completion.

There are no explicit writes to the object or table, and no allocation, release, ownership transfer, logging, callback, or external function invocation is shown.

The cursor write occurs after all explicit table reads required by the selected path. This matters if the cursor aliases other storage:

- If it overlaps the count field, the final store can change the object’s count.
- If it overlaps the table-address field, the final store can change that field, though the search has already used the captured address.
- If it overlaps a record, the final store can modify table contents after selection and payload retrieval.

These are consequences of the destination store, not evidence that such aliasing is intended. Non-overlapping storage is the safe ordinary-use precondition.

There is no rollback mechanism. Invalid addresses, inaccessible storage, unsuitable alignment, or incompatible concurrent modification have no specified error mapping. In particular, a return value of zero is an ordinary search failure, not a documented memory-error indication.
