# F-9070b5548263

## Purpose

F-9070b5548263 updates two link destinations using two address-valued words read from a selected record. Each destination is either a neighboring record’s link field or a field in an endpoint record.

The apparent purpose is to unlink a record from a doubly linked sequence. This interpretation is consistent with the accesses but is not independently established by type definitions or callers. The directly established behavior is narrower: capture two links, choose two destinations by testing those captured links for zero, and perform two ordered writes.

The function does not search for the selected record, verify sequence membership, check reciprocal links, clear the selected record as a separate operation, or release its storage. Whether unlinking constitutes an ownership transfer under caller conventions is unknown.

## Interface

### Inputs and layout

The function takes two address-valued arguments:

| Argument | Operational role | Apparent layout |
|---|---|---|
| Endpoint-record address | Supplies destinations when a captured link is zero | First endpoint at byte offset 0; last endpoint at byte offset 4 |
| Selected-record address | Supplies the two links used for all decisions and stored values | Predecessor link at byte offset 0; successor link at byte offset 4 |

“Predecessor,” “successor,” “first,” and “last” describe the inferred sequence roles. The operation itself depends only on the stored values and their positions.

The supplied representation is consistent with two adjacent 32-bit link words and a 32-bit address model. It includes an explicit four-byte displacement for the nonzero-predecessor destination. This contract uses that apparent model when describing widths and offsets; the original ABI, pointer width, integer representation, and alignment requirements are not independently supplied.

Zero is the absence marker for either captured link. A nonzero link is used as an address without a membership, range, or positivity check. In particular, the predecessor is tested for equality to zero, not for being greater than zero.

### Output

There is no explicit return value, status code, or returned record address. Normal completion is expressed entirely by the memory writes below.

The absence of a returned pointer does not establish an ownership policy.

### Preconditions for normal completion

The selected record must support reading both link fields. Destination requirements then depend on the captured links:

| Captured condition | Required writable destination |
|---|---|
| Predecessor is zero | Endpoint record at offset 0 |
| Predecessor is nonzero | Captured predecessor address plus four bytes |
| Successor is zero | Endpoint record at offset 4 |
| Successor is nonzero | Captured successor address at offset 0 |

When both links are nonzero, the endpoint-record argument is not dereferenced by this body. Its storage need not be accessed for that branch combination; this does not establish that an arbitrary argument value is valid under every possible ABI.

These requirements concern accessible storage, not sequence correctness. Preserving an ordinary doubly linked sequence additionally requires suitable caller-maintained relationships among the selected record, neighbors, and endpoints. The function does not verify those relationships.

## Behavior

### Capturing the selected record’s links

The function first reads the predecessor link from the selected record’s first field. It then reads the successor link from the selected record’s second field.

Both reads precede either write. The captured values supply all later branch decisions and stored values. The function does not reload either link after making the first update.

Consequently, an update that overlaps the selected record cannot change which second destination is selected or which captured predecessor value is written there.

### First write: forward link or first endpoint

The captured predecessor selects the first destination:

- If it is zero, the function writes the captured successor to the endpoint record’s first field.
- Otherwise, the function writes the captured successor to the field four bytes beyond the captured predecessor address.

Under the sequence interpretation, this either advances the first endpoint or changes the predecessor’s successor to bypass the selected record.

The previous destination value is not read or compared with the selected-record address. An inconsistent forward link is overwritten rather than rejected.

### Second write: backward link or last endpoint

After the first write, the captured successor selects the second destination:

- If it is zero, the function writes the captured predecessor to the endpoint record’s second field.
- Otherwise, the function writes the captured predecessor to the field at the captured successor address.

Under the sequence interpretation, this either retreats the last endpoint or changes the successor’s predecessor to bypass the selected record.

The previous value at this destination is also neither read nor validated.

### Ordinary sequence cases

For valid, nonoverlapping records with the apparent layout:

| Captured predecessor | Captured successor | First write | Second write |
|---|---|---|---|
| Zero | Zero | First endpoint becomes zero | Last endpoint becomes zero |
| Zero | Nonzero | First endpoint becomes successor | Successor’s predecessor becomes zero |
| Nonzero | Zero | Predecessor’s successor becomes zero | Last endpoint becomes predecessor |
| Nonzero | Nonzero | Predecessor’s successor becomes successor | Successor’s predecessor becomes predecessor |

These cases correspond, respectively, to removing a singleton, first record, last record, or interior record from an ordinary doubly linked sequence.

In such a nonoverlapping arrangement, the selected record retains both original links. There is no dedicated operation that marks it detached, resets its fields, or records that removal has occurred.

### Aliasing and overlapping destinations

The function contains no disjointness check. Its observable rule remains: read both selected links, perform the first chosen write, then perform the second chosen write.

If a destination overlaps a selected-record field, that field can change despite the absence of a dedicated clearing step. The already captured links still determine the remaining action.

If both writes address the same word, the second write determines that word’s final value after normal completion. The first write nevertheless occurs earlier in the body’s access sequence.

These rules describe the supplied operation where the accesses are valid under the execution environment. They do not establish that overlapping records form a meaningful sequence or that every possible overlap has defined behavior under the original language and ABI.

### Address arithmetic and boundaries

The only explicit field displacement beyond the base address is four bytes. There is no traversal, count calculation, allocation-size calculation, or payload arithmetic.

No overflow or address-validity check precedes the predecessor-relative write. The supplied evidence does not establish portable behavior when adding four crosses an integer or address-space boundary. The apparent 32-bit representation must not be interpreted as a guarantee of defined modulo-address wraparound.

A nonzero stored value is treated as an address, not validated as a legitimate record. Normal-completion examples therefore require representable, accessible destinations and valid field addressing.

## Side effects

On normal completion, the body specifies two link reads followed by two link writes. Branches change the write destinations, not the number of writes.

For a well-formed, nonoverlapping sequence, the writes affect only:

- The predecessor’s successor field or the first endpoint.
- The successor’s predecessor field or the last endpoint.

There is no separate payload update, length update, allocation, deallocation, logging operation, or synchronization operation in the supplied body. Aliasing can make one of the selected destinations overlap storage that a caller regards as another kind of field; the body does not prevent that.

The body performs no deallocation and invokes no ownership-management dependency. Whether unlinking constitutes an ownership transfer under caller conventions is unknown. The evidence does not determine who may subsequently retain, reuse, or release the selected record or its associated storage.

The operation provides no transactional mechanism. The first write precedes the second, and no restoration path is present. If execution stops or a later access fails after the first write, the body supplies no rollback. The precise fault, exception, or termination behavior is environment-dependent and remains unspecified here.

No lock, atomic sequence-update primitive, or concurrency protocol is shown. The body’s stated access order does not establish word-store atomicity, visibility ordering for other execution agents, or a consistent intermediate sequence state for concurrent observers.

## Acceptance examples

These are conditional consequences of static inspection, not executed tests. Unless stated otherwise, each example assumes the apparent four-byte link model, valid accesses, nonoverlapping records, and no concurrent mutation.

### Interior record

The selected record contains distinct, nonzero predecessor and successor addresses. The predecessor’s second field and successor’s first field initially refer to the selected record.

Expected behavior:

1. Both selected-record links are read.
2. The predecessor’s second field is written with the successor address.
3. The successor’s first field is written with the predecessor address.

The endpoint record is not accessed. The selected record retains its original links.

### First record with a successor

The selected record contains a zero predecessor and a nonzero successor.

The first endpoint is written with the captured successor. The successor’s first field is then written with zero. The last endpoint is untouched, provided it does not alias either destination.

The selected record retains its original links under the nonoverlap assumption.

### Last record with a predecessor

The selected record contains a nonzero predecessor and a zero successor.

The predecessor’s second field is written with zero. The last endpoint is then written with the captured predecessor. The first endpoint is untouched under the nonoverlap assumption.

### Singleton, including inconsistent endpoints

Both selected-record links are zero.

The first endpoint is written with zero, followed by the last endpoint being written with zero. These writes occur even if the endpoints did not previously refer to the selected record. There is no singleton-membership check.

### Interior case without endpoint dereferencing

Both captured links are nonzero, and both neighbor destinations are valid.

The two neighbor updates occur without a read or write through the endpoint-record argument. This demonstrates branch-dependent storage access, not a general promise that the endpoint argument is optional in other cases.

### Inconsistent reciprocal link

The captured predecessor is nonzero, but its second field contains an unrelated address.

That field is still overwritten with the captured successor. No comparison, rejection, search, or corrective traversal occurs.

### Repeated invocation

An interior removal completes with distinct records, leaving the selected record’s captured links unchanged.

If a later invocation reads the same link values and the destinations remain valid, it writes those neighbor links again. This is not an “already removed” check. Any intervening changes at the destinations can be overwritten.

### Self-referential record

Both selected-record links contain the selected-record address, and both selected fields are writable.

The second field is written with the selected-record address first. The first field is then written with that address. The endpoint record is not accessed.

The self-links remain in place. The function does not recognize this as a special circular-sequence case.

### Both destinations are one word

The captured predecessor and successor are nonzero, and the successor address equals the predecessor address plus four bytes. Assume this addressing is valid.

The first write places the successor address at that shared destination. The second write places the predecessor address at the same destination. Its final value is the captured predecessor.

This outcome follows from write order; it is not evidence of a valid sequence arrangement.

### Ownership interpretation

An otherwise valid unlink operation completes.

Acceptance requires the specified writes and absence of an explicit deallocation or ownership-management call. It does not require that ownership remain unchanged or transfer to any particular party. Either policy would need evidence from caller conventions outside this body.
