# F-4a68b66a4199

## Purpose

F-4a68b66a4199 selects one 20-byte record from a caller-supplied storage state and clears selected fields in that record. It prefers a record reachable through a reuse-list pointer. If that pointer is null, it consumes the next record from a contiguous range, allocating a new range when the next-record pointer equals the range-end pointer.

The function returns no value. The selected record’s address is not explicitly returned or stored in a separate output field. Observable results are changes to the storage state, allocation requests when necessary, and writes into the selected record.

A record pool with a reuse list and linked allocation blocks is the inferred intent. Record semantics, allocation ownership, and the way a caller subsequently identifies the selected record are not established.

## Interface

### Input and result

The sole argument is a pointer to a mutable state object containing at least four consecutive 32-bit fields:

| Byte offset | Contract name | Observed use |
|---|---|---|
| 0 | Block head | Address of the current allocation descriptor, or zero |
| 4 | Reuse head | Address of a reusable record, or zero |
| 8 | Next record | Address of the next unused record in the current range |
| 12 | Range end | Address used to detect exhaustion of that range |

The contract names describe observed roles, not application-defined types.

There is no explicit result value and no explicit error result. The function does not validate the argument before reading its field at byte offset 4.

### Allocation-descriptor layout

When a new block is needed, the function requests 12 bytes for a descriptor and writes three 32-bit fields:

| Byte offset | Stored value |
|---|---|
| 0 | Block-head value read from the state after both allocation calls return |
| 4 | Newly calculated record capacity |
| 8 | Address returned by the backing-storage allocation |

An existing descriptor contributes only its capacity field at byte offset 4 to this invocation’s capacity calculation. This function does not traverse the descriptor chain.

### Record layout

Records have a stride of 20 bytes. The selected record is modified as follows:

| Byte offset | Width | Operation |
|---|---:|---|
| 0 | 1 byte | Store zero |
| 1–3 | 3 bytes | No direct write |
| 4 | 4 bytes | Store zero |
| 8 | 4 bytes | Store zero |
| 12 | 4 bytes | Store zero |
| 16–19 | 4 bytes | No direct write |

On the reuse path, the 32-bit field at byte offset 12 is read as the next reuse-list address before being cleared.

This is partial initialization, not a full 20-byte clear.

### Widths and validity requirements

The supplied representation uses 32-bit state fields, addresses, descriptor fields, and capacity arithmetic. Capacity calculations and allocation-byte-count multiplication use unsigned 32-bit values.

For defined, ordinary operation:

- The state must be readable and writable for all fields accessed on the chosen path.
- A selected record must support the indicated byte and 32-bit accesses.
- A nonzero block head used during growth must permit reading its 32-bit capacity field.
- Allocation results must support the subsequent descriptor and backing-storage accesses.
- Record, descriptor, and state storage must not overlap in ways that invalidate the described structures.

No checks enforce these conditions. Alignment requirements and the consequences of invalid addresses are not established independently of the execution environment.

## Behavior

### 1. Select the reuse path when possible

The first state-field read obtains the reuse head.

If that address is nonzero:

1. Select the record at that address.
2. Read the 32-bit address at record byte offset 12.
3. Write that address into the state’s reuse-head field.
4. Perform the record-clearing writes described below.

This branch does not call the allocation dependency. It does not directly read or update the block head, next-record pointer, or range-end pointer.

There is no traversal beyond the selected record’s single link. No check establishes that the link is valid, distinct from the selected record, or acyclic.

In particular, a self-linked record leaves the reuse head pointing to that same record, after which the record’s link is cleared. The function does not reject or repair that condition.

### 2. Otherwise inspect the contiguous range

If the initial reuse head is zero, the function reads the next-record pointer and compares it with the range-end pointer.

If the addresses differ:

1. Select the address read from the next-record field.
2. Store that address plus 20 into the next-record field.
3. Perform the record-clearing writes.

The exhaustion check is equality only. It does not establish that the next-record pointer is below the range end, lies inside a valid allocation, or has 20 writable bytes remaining.

Consequently, unequal null, reversed, misaligned, or out-of-range pointers are not rejected by this function.

### 3. Calculate capacity when the range is exhausted

If the next-record pointer equals the range-end pointer, the function calculates a new capacity.

If the block head is zero, the capacity is 32 records.

Otherwise, let the unsigned 32-bit capacity read from the existing head descriptor be \(c\). Calculate:

- \(g = c + \lfloor c/2 \rfloor + \lfloor c/8 \rfloor\), reduced modulo \(2^{32}\).
- \(m = c + 32\), reduced modulo \(2^{32}\).

The new capacity is the larger of \(g\) and \(m\), using unsigned comparison.

Without overflow, this chooses the larger of an additive increase of 32 records and an approximately 1.625-fold capacity. With overflow, the wrapped values determine the choice; neither monotonic growth nor sufficient allocation size is guaranteed.

An existing descriptor with capacity zero yields a new capacity of 32. It is not treated as an error.

### 4. Allocate and publish a new block

After calculating capacity, the function performs these operations in order:

1. Call F-871e64ddc6de with arguments 12 and zero.
2. Call F-871e64ddc6de with the unsigned 32-bit product of capacity and 20, and zero.
3. Store the second call’s returned address into byte offset 8 of the first call’s returned descriptor.
4. Read the state’s current block head and store it into byte offset 0 of that descriptor.
5. Store the calculated capacity into descriptor byte offset 4.
6. Store the descriptor address into the state’s block-head field.
7. Read the backing-storage address from descriptor byte offset 8.
8. Store that address plus the capacity-times-20 byte count into the state’s range-end field.
9. Store the backing-storage address plus 20 into the state’s next-record field.
10. Clear the selected record at the backing-storage address.

The backing-storage allocation argument is \((20 \times \text{capacity}) \bmod 2^{32}\). There is no multiplication-overflow check.

The descriptor’s previous-head link uses a state read performed after both dependency calls. It is not guaranteed to equal the head used earlier to calculate capacity. If a dependency changes that state, growth sizing and descriptor linkage can reflect different head values.

Similarly, publication does not precede initialization of the descriptor’s three fields: all three are written before the state’s block head is replaced.

The old range is not freed. No old records are copied into the new range. The function does not directly change the reuse-head field on this branch.

### 5. Clear the selected record

After the applicable state updates, the function performs these stores in this order:

1. Zero the 32-bit field at record byte offset 4.
2. Zero the 32-bit field at record byte offset 8.
3. Zero the 32-bit field at record byte offset 12.
4. Zero the single byte at record byte offset 0.

There is no direct write to bytes 1–3 or 16–19.

State advancement therefore precedes record initialization. The operation has no visible rollback path if an access fails after the state has already changed.

## Side effects

### Direct memory effects

For nonoverlapping, valid storage:

- **Reuse path:** update the reuse head and partially clear one record.
- **Available-range path:** advance the next-record pointer by 20 and partially clear one record.
- **New-block path:** initialize a descriptor, replace the block head, replace the range end, advance the next-record pointer into the new range, and partially clear the first record.

Other state fields are not directly written on those respective paths. This does not constrain indirect writes by F-871e64ddc6de or effects caused by overlapping storage.

There are no explicit synchronization operations. Concurrent mutation of the state, descriptors, or records is not handled by the visible behavior.

### Allocation and ownership

Only the exhausted-range path invokes F-871e64ddc6de, twice.

The new descriptor is linked into the state, and the backing-storage address is retained in that descriptor. This establishes retention of those addresses, not a complete ownership contract.

No release operation appears. Nothing establishes:

- Who must eventually release descriptors or record storage.
- Whether the dependency returns newly owned, shared, pooled, or otherwise managed storage.
- Whether either dependency call modifies unrelated memory or globals.
- Whether the dependency guarantees distinct, suitably aligned regions.

### Errors and interrupted execution

Allocation results are not checked.

If the first allocation returns a null address normally, the second allocation call still occurs before the first descriptor write is attempted. If the backing-storage allocation returns null normally, that value is stored in the descriptor, state publication proceeds, and the function subsequently attempts record initialization through that address.

No explicit recovery, cleanup, status reporting, or transactional rollback is present. Dependency failure signaling and invalid-memory-access behavior remain environment-dependent.

## Acceptance examples

These examples are conditional on valid writable storage, appropriate access alignment, and no interfering mutation unless explicitly stated. They are derived expectations, not executed tests.

### Reusing a linked record

Given a nonzero reuse head naming record A, with record A’s field at byte offset 12 naming record B:

- No allocation call occurs.
- The reuse head becomes B before A is cleared.
- A’s 32-bit fields at offsets 4, 8, and 12 become zero, followed by its byte at offset 0.
- A’s bytes 1–3 and 16–19 retain their prior contents.
- The block head, next-record pointer, and range end receive no direct writes.

A zero link makes the reuse head zero.

### Consuming an available contiguous record

Given a zero reuse head and a next-record address P unequal to the range end:

- No allocation call occurs.
- The selected record is at P.
- The next-record field becomes P plus 20 before the record-clearing stores.
- The block head and range end receive no direct writes.
- Only the specified 13 record bytes are directly cleared.

This expectation does not certify that P is inside the range; equality is the sole range check.

### Creating the first block

Given a zero reuse head, equal next-record and range-end pointers, and a zero block head:

- The capacity is 32.
- Dependency requests are 12 bytes followed by 640 bytes, both with second argument zero.
- With no dependency mutation of the state, the descriptor’s previous-head field is zero.
- The descriptor records capacity 32 and the returned backing-storage address.
- The new next-record pointer is the backing-storage address plus 20.
- The new range end is the backing-storage address plus 640.
- The first record is partially cleared.

### Choosing between growth candidates

Given exhaustion and an existing head capacity of 32, the candidates are 52 and 64. The chosen capacity is 64, producing a 1,280-byte backing-storage request.

Given an existing head capacity of 64, the candidates are 104 and 96. The chosen capacity is 104, producing a 2,080-byte request.

### Wrapped byte-count multiplication

Given exhaustion and an existing capacity of 268,435,456:

- The proportional candidate is 436,207,616.
- The additive candidate is 268,435,488.
- The chosen capacity is 436,207,616.
- Its 20-byte-record product wraps to a backing-storage request of 134,217,728 bytes.

The descriptor still records 436,207,616 records. No overflow error is reported or checked.

### Dependency mutation of the block head

If either allocation call changes the state’s block head and both calls return normally, the new descriptor’s previous-head field receives the head read after those calls. The capacity remains the value calculated before the calls.

This distinguishes the timing of the two observations; it does not establish that such mutation is supported or safe.
