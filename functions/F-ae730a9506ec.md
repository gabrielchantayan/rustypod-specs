# F-ae730a9506ec

## Purpose

F-ae730a9506ec installs an object pointer into an indexed pointer collection. It conditionally initializes the incoming object, conditionally assigns an index through caller-provided storage, requests collection growth when needed, releases one reference from the object currently occupying the selected slot, acquires one reference to the incoming object, and replaces the slot.

The established behavior is the sequence of reads, writes, and calls described below. Terms such as “initialization,” “reference count,” and “release” describe inferred roles of fields and callbacks, not independently verified lifecycle guarantees.

The function does not establish that insertion succeeds safely for malformed objects, invalid indices, failed growth, or callbacks that invalidate storage. It contains no explicit validation, error return, rollback, or synchronization.

## Interface

The function accepts four arguments:

1. **Collection handle:** a pointer to a word containing the address of a collection descriptor.
2. **Incoming object:** a pointer to an object with accessible fields at byte offsets 0, 8, and 12.
3. **Index cell:** a pointer to an unsigned 32-bit index.
4. **Auxiliary value:** an opaque 32-bit value copied into temporary storage on entry.

There is no explicit result value. No return-register contents are specified.

The pointer-slot array has a four-byte stride. Pointer-bearing fields are represented as four-byte words in the supplied material. This contract describes that representation; it does not establish portability to an ABI with different pointer widths or layouts.

Both indirect callback addresses are obtained by clearing the low two bits of their respective stored dispatch words. Those bits do not participate in the resulting call target. Their meaning is unknown.

### Preconditions for a defined, memory-safe execution

Every address actually dereferenced must identify appropriately accessible storage. This includes addresses reached after callbacks, because some handles and fields are reread after those calls.

Additional requirements include:

- The incoming object is non-null and remains valid through its final count increment.
- The collection handle, descriptor, and selected slot remain usable at their respective access points.
- Any non-null occupying object has an accessible count field.
- Every invoked indirect target is callable using the observed argument list and calling convention.
- If growth is requested, subsequent slot access must be valid when the growth dependency returns.
- Count arithmetic and address calculations must remain valid for the execution environment.

These are requirements for safe use, not checks performed by this function.

The function does not establish that the collection handle, incoming object, index cell, shared counter, or their reachable storage are disjoint. Unusual aliasing can affect later reads. The access order below takes precedence over conclusions that assume independent storage.

## Behavior

### 1. Capture the auxiliary value

On entry, the fourth argument is copied into a temporary 32-bit word.

If growth is subsequently requested, that word is overwritten with zero before its address is passed to the growth dependency. Thus the supplied auxiliary value is not the initial value seen by that dependency.

If no growth is requested, no use of this temporary is visible in the supplied body.

### 2. Conditionally allocate an index and initialize the incoming object

The function reads bit 0 of the incoming object’s flags word at offset 8.

If the bit is already set, the entire initialization branch is skipped:

- The index cell is not checked for zero in this branch.
- The shared counter is not accessed.
- The initialization callback is not called.
- The flags word is not updated by this branch.

If the bit is clear, the function first reads the index cell.

When the index is zero, it performs these operations in order:

1. Read a shared unsigned 32-bit counter.
2. Add one using unsigned 32-bit arithmetic.
3. Write that incremented value to the shared counter.
4. Write the same computed value to the index cell.

When the index is nonzero, the counter update and index assignment are skipped.

Next, the function resolves the incoming object’s initialization callback through the dispatch word at offset 8, clears the low two address bits, and invokes the resulting target with two explicit arguments:

1. The incoming object pointer.
2. The collection handle.

After the callback returns, the function reads the incoming object’s flags word again, sets bit 0, and writes the resulting word back.

This read-modify-write uses the flags value present after the callback. Changes made by the callback to other flag bits are therefore retained, provided the object storage remains valid.

The callback may alter the index cell, shared state, or collection state through available aliases or other means. No preservation guarantee is established.

### 3. Select the effective index and conditionally request growth

After the initialization branch, the function reads the index cell and saves that unsigned 32-bit value as the effective index for the rest of this invocation.

Consequently:

- The effective index can differ from the value assigned before the initialization callback.
- Once captured, subsequent changes to the index cell do not change the index used for this insertion.

The function then reads the current collection descriptor through the collection handle and reads the unsigned bound at descriptor offset 12.

If the bound is less than or equal to the effective index, it:

1. Writes zero into the temporary auxiliary word.
2. Calls F-992b83e9731d with:
   - The address of the descriptor field at offset 8.
   - The effective index plus one, computed as an unsigned 32-bit value.
   - The address of the temporary zero-valued word.

The first argument identifies the descriptor’s slot-array pointer field, not the slot-array allocation itself and not the collection handle.

The call’s result is not inspected. The function does not recheck the bound afterward and does not independently establish that the requested slot exists.

If the bound is greater than the effective index, no growth call occurs.

### 4. Read the occupying pointer and release one reference

After any growth call, the function rereads the collection descriptor through the handle and obtains its slot-array address. It reads the pointer at the effective index, using a four-byte slot stride.

If that pointer is null, no occupying-object count update or release callback occurs.

If it is non-null, the function:

1. Reads the occupying object’s count-like field at offset 12.
2. Computes one less.
3. Writes the decremented value back.
4. Tests whether that computed decremented value is zero.

Only when the computed result is zero does the function resolve and call the occupying object’s release callback. Resolution uses the object’s dispatch word at offset 4 with its low two bits cleared.

This callback has **no explicit arguments** in the supplied representation. The contract must not add an object argument or assume an implicit receiver.

The count decrement is visible before the callback is invoked. The slot has not yet been overwritten by this function at that point. The callback therefore executes during a transitional state in which the selected slot can still contain the outgoing pointer.

The callback’s identity, actual destruction behavior, and memory ownership obligations are unknown.

### 5. Acquire the incoming reference and install the pointer

After the outgoing-object handling completes, the function reads the incoming object’s count-like field, increments it by one, and writes it back.

It then rereads the collection descriptor through the handle and rereads the slot-array pointer from descriptor offset 8. Finally, it writes the incoming object pointer into the slot selected by the saved effective index.

The final destination is therefore resolved after a possible outgoing release callback. If that callback changes the handle or slot-array pointer, the final write can target different storage from the earlier slot read.

The final slot write occurs after the incoming count increment. There is no subsequent operation in the supplied body.

## Side effects

### Direct writes

Depending on the executed branches, the function directly writes:

- The shared counter.
- The caller’s index cell.
- Bit 0 of the incoming object’s flags word, while preserving the other bits as reread after initialization.
- The occupying object’s count-like field.
- The incoming object’s count-like field.
- The selected collection slot.
- A temporary word whose address is supplied to F-992b83e9731d.

No direct allocation or deallocation operation appears in this function. Allocation, relocation, destruction, or deallocation may occur in dependencies, but none is established by this body alone.

### Ownership and lifetime

The decrement/increment pattern supports an inference that the collection holds a counted reference to each installed object. Under that interpretation, replacement releases the outgoing reference before acquiring the incoming reference.

This ordering matters when the occupying and incoming pointers are equal. There is no identity check and no early return for self-replacement. An object whose count is one is decremented to zero and receives its release callback before the later increment of the same object storage.

If that callback frees or invalidates the object, the later increment is unsafe. The function does not prevent that outcome.

The temporary word passed to F-992b83e9731d has invocation-local lifetime. No evidence establishes whether the dependency retains its address. Safe use requires that any retention or deferred access respect that lifetime.

### Errors, interruption, and concurrency

No status return or error-handling branch is visible for either indirect callback or F-992b83e9731d. Partial updates are not rolled back.

For example, index assignment precedes initialization, and the outgoing count decrement precedes its release callback. If a dependency does not return normally, earlier effects may already have occurred.

There are no visible locks or atomic read-modify-write operations. The body does not establish safe concurrent counter allocation, reference-count updates, or collection mutation.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, assume valid storage, nonoverflowing count arithmetic, and dependencies that return normally without changing relevant state.

1. **Already initialized, empty in-range slot.**  
   With flag bit 0 set, index 3, bound 4, a null slot 3, and incoming count 5, the function skips counter assignment, initialization, growth, and outgoing release. It changes the incoming count to 6 and stores the incoming pointer in slot 3.

2. **First initialization with an unassigned index.**  
   With flag bit 0 clear, index zero, and shared counter 9, the counter is written as 10 before the index cell is written as 10. Initialization then runs. After it returns, bit 0 is set. If the callback leaves the index unchanged, insertion proceeds at index 10.

3. **Initialization changes the effective index.**  
   If initialization changes the index cell from 10 to 2, the later bound comparison and slot accesses use index 2.

4. **Growth at the boundary.**  
   An effective index of 7 and bound of 7 trigger F-992b83e9731d with requested value 8. A bound of 8 does not. The pointed-to auxiliary word is zero regardless of the fourth argument’s entry value.

5. **Replacing an object with multiple references.**  
   If the selected slot holds an object with count 3, that count becomes 2 without a release callback. The incoming count is then incremented and the slot replaced.

6. **Replacing an object with its final counted reference.**  
   If the occupying count is 1, it is written as zero before the release callback. Only after that callback returns does the incoming increment occur.

7. **Self-replacement.**  
   With the same object already in the slot and count 2, the function decrements to 1 and later increments to 2. With count 1, it invokes release between the decrement and increment; safety depends on what that callback does.

8. **Counter wraparound.**  
   With an uninitialized object, zero index, and shared counter 4,294,967,295, the counter and index are both written as zero. No retry or reservation of a nonzero value follows.

9. **Maximum effective index.**  
   An effective index of 4,294,967,295 triggers growth for every representable unsigned 32-bit bound, but the requested value wraps to zero. The function still proceeds toward indexed access. A successful or safe outcome is not established.
