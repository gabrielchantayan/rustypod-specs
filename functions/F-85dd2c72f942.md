# F-85dd2c72f942

## Purpose

F-85dd2c72f942 obtains an event wrapper, examines its event pointer, conditionally updates associated state, and queues every nonempty event. A nonempty event also causes a separate notification to be constructed and submitted. Both empty and nonempty paths finish with a conditional indirect call controlled by a fresh state read.

**Established static behavior:** the supplied representation establishes the field accesses, conditional updates, dependency-call sequence, queue-record write, and final-dispatch conditions described below.

**Inferred intent:** the wrapper appears to carry pending work, while several helpers appear to coordinate access and signal work availability. These interpretations do not establish synchronization, ownership transfer, or release obligations.

The external comparison boundary is observed separately for equality and, if equality fails, for signed less-than. Dispatch is therefore not generally a three-way comparison against one stable value.

## Interface

### Invocation and result

The routine accepts one 32-bit address-like argument and has no explicit return value.

The argument identifies storage containing a four-byte state-object pointer at byte offset `+0x04`. This pointer is read after the initial wrapper-construction calls. The resulting state address is retained throughout the invocation; the pointer in the input object is not reloaded.

Observable results consist of direct memory writes, dependency calls, and possible indirect dispatch. No explicit status or error value is returned.

The contract does not assume that dependencies preserve globals, state fields, or object lifetimes. In particular, construction occurs before the state pointer is loaded, and the initial state helper runs before the wrapper’s event pointer is read.

## Behavior

### Initial construction and state access

The routine first calls F-0a77364c41cc with `12`. It supplies the returned value, the initial descriptor, and one zero argument to F-afb630a7107c. The latter result is treated as the initial-wrapper pointer.

It then reads the state pointer from input offset `+0x04`, calls F-338d16f9ce72 with state address `+0x10c`, and reads the event pointer from wrapper offset `+0x08`.

The wrapper-field read is unconditional. A later wrapper null check does not make a null construction result a supported condition.

### Empty event

When the event pointer is zero, the routine checks whether the wrapper pointer is nonzero. If so, it reads the wrapper’s dispatch-table pointer and invokes the target at table offset `+0x04`, explicitly supplying the wrapper pointer.

It then proceeds directly to common final dispatch. This path performs no event-specific field update, queue-record allocation, queue insertion, or notification construction.

The wrapper operation resembles release or destruction, but its actual ownership and lifetime effects are unknown.

### Nonempty-event dispatch and separate boundary reads

For a nonzero event pointer, the routine reads the signed 32-bit discriminator once from event offset `+0x04`. That retained discriminator is used throughout dispatch.

The external boundary is accessed as follows:

1. The routine reads the boundary for an equality comparison.
2. If the discriminator equals that first observed boundary value, it writes `1` to state offset `+0x140`. There is no second boundary comparison on this path.
3. Otherwise, it reads the boundary again for a signed less-than comparison.
4. If the discriminator is less than that second observed value, it selects the lower-case group.
5. Otherwise, it selects the remaining-case group.

Thus:

- The lower group requires failed equality against the **first** observed boundary and successful signed less-than against the **second**.
- The remaining group requires failed equality against the **first** observed boundary and failed signed less-than against the **second**.

The remaining group does **not** require the discriminator to be greater than either observed boundary. It can equal the second boundary after differing from the first, or be less than the first boundary while not less than the second.

Only under an additional boundary-stability assumption do these paths reduce to equality, signed less-than, and signed greater-than against one value. The supplied evidence does not establish that stability.

### Lower-case group

The following cases are considered only after entry into the lower group.

| Discriminator | Direct behavior |
|---|---|
| `0x6600000d` | Write zero to `+0x144`, then zero to `+0x140` |
| `0x66000014` | Optionally initialize the count, then increment it |
| `0x66000015` | Optionally initialize the count, then conditionally decrement it |
| `0x66000017` | Write zero to `+0x144`, then zero to `+0x140` |

For either count-adjustment case, the routine first reads `+0x144` and compares it with signed `-1`. If equal, it:

- Calls F-87be4aa684d1.
- Reads the returned object’s dispatch-table pointer.
- Invokes the target at table offset `+0x16c`, with no explicit arguments visible.
- Writes the returned four-byte value to `+0x144`.

This sentinel check occurs once. A query result of `-1` does not trigger another query during the same event.

For increment, the routine reads the count after optional initialization, adds one, and stores the result.

For decrement, it reads the count after optional initialization and tests whether it is signed-positive. If positive, it reads the field again for the subtraction and stores one less. A nonpositive test result causes no decrement store. The test and calculation are separate reads; the contract does not silently replace them with one captured count.

The arithmetic operates on a 32-bit field. There is no explicit saturation, overflow check, or error branch. Ordinary representable results are established. Exact overflow behavior, including incrementing `2,147,483,647`, remains **documented_only**; the supplied representation does not establish a portable signed-overflow rule. Likewise, a positive decrement test alone does not establish the later calculation operand if external mutation is possible.

### Remaining-case group

These cases are considered only when the initial equality comparison and subsequent signed less-than comparison both fail.

| Discriminator | Direct behavior |
|---|---|
| `0x6600001a` | Write zero to `+0x140` |
| `0x6600001b` | Conditionally exchange mode values `1` and `2` |
| `0x66000024` | Copy an indirectly referenced four-byte payload into `+0x148` |

For the mode-transition case, the routine reads `+0x140`. If the value is `-1`, it calls F-87be4aa684d1 and invokes the returned object’s target at dispatch-table offset `+0x18c`, with no explicit arguments visible. That result supplies the transition decision. Otherwise, the directly read mode supplies the decision.

A decision of `1` causes a write of `2`; a decision of `2` causes a write of `1`. Any other decision causes no direct mode write.

The query result is not unconditionally cached in the mode field. Dependencies may themselves change the field, but those changes are not direct writes established for this routine.

For the payload case, the routine reads the pointer at event offset `+0x0c`, reads four bytes through that pointer, and writes those bytes to state offset `+0x148`. It copies the value, not the pointer. No explicit validation or release of the payload storage is visible.

A numeric constant associated with one group is not considered in the other group. Equality with the first observed boundary takes precedence over every numeric case.

### Common final dispatch

The pointed-to first word is a condition, not the callable target itself. This final decision uses state observed after preceding dependency calls, not a snapshot from entry.

## Side effects

### Direct writes

The routine’s explicit write destinations are:

- State `+0x140`: zero, one, or two.
- State `+0x144`: zero, a query result, or an arithmetic result.
- State `+0x148`: four payload bytes.
- Queue record `+0x04`: the initial-wrapper pointer.

These are destination descriptions, not a guarantee that distinct logical objects cannot alias. Dependencies may perform additional writes or invalidate storage.

### Observable ordering

Initial construction precedes the input’s state-pointer read. The first state helper precedes the wrapper event-pointer read.

For nonempty events, discriminator selection and event-specific writes precede queue processing. The first boundary read precedes the optional second read; successful first-read equality excludes the second read. Queue insertion precedes the `+0x134` helper, which precedes the `+0x12c` completion helper. Notification construction and submission follow that sequence.

Final state inspection follows all preceding operations on the selected path.

## Acceptance examples

These are conditional static examples, not executed tests. All reached storage and targets are assumed valid, and all invoked dependencies are assumed to return normally. Examples describing numeric field outcomes also assume no interfering mutation or aliasing that changes those outcomes.

For examples stated as “below” or “above” the boundary, the boundary is explicitly assumed stable across both comparisons.

1. **Empty event.** An event pointer of zero causes the wrapper-table operation. No queue record or notification is requested. Common final dispatch remains applicable.

2. **First-read equality.** If the discriminator equals the first observed boundary, the routine writes `1` to `+0x140` and does not read the boundary for less-than. Queueing and notification follow. This example requires no boundary-stability assumption.

3. **Stable-boundary reset.** With a stable boundary greater than `0x6600000d`, that discriminator causes zero to be written first to `+0x144`, then to `+0x140`.

4. **Stable-boundary increment.** With a stable boundary greater than `0x66000014` and count `7`, no count query occurs and the arithmetic store is `8`.

5. **Count initialization.** Under the same boundary condition, count `-1` and query result `9` produce a store of `9` followed by a store of `10`. A query result of `-1` instead produces those respective stores as `-1` and `0`, without repeating initialization.

6. **Nonpositive decrement.** With a stable boundary greater than `0x66000015`, count zero causes no count write. Count `-1` with query result `-3` causes the initialization store of `-3`, but no decrement store.

7. **Mode query.** With a stable boundary less than `0x6600001b` and mode `-1`, query result `2` causes a direct mode write of `1`. Query result `4` causes no direct mode write.

8. **Payload copy.** With a stable boundary less than `0x66000024`, a payload pointer addressing `0x12345678` causes those four value bytes to be copied to `+0x148`, rather than storing the pointer.

9. **Changing boundary reaches the remaining group.** Let the discriminator be `0x6600001a`. If the equality read observes `0x6600001b` and the less-than read observes `0x6600001a`, both comparisons fail. The remaining group writes zero to `+0x140`, even though the discriminator is less than the first observed boundary and equal to the second.

10. **Unmatched event.** A nonzero event matching neither first-read equality nor a case in its selected group performs no direct event-specific write, but still queues and notifies.

11. **Fresh final state.** If a preceding dependency leaves state `+0x10c` zero, final dispatch is skipped. If it leaves a valid nonzero pointer whose first word is nonzero, the external callable is invoked.
