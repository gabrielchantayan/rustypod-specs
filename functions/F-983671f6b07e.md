# F-983671f6b07e

## Purpose

F-983671f6b07e reports the one-based position of the earliest eligible entry for which a comparison dependency returns zero. A separate dependency is invoked before any search, whenever the object argument is nonzero.

A return of zero means that no successful comparison was observed. It does not distinguish a missing object, a missing search argument, a nonpositive traversal bound, or a completed search without a match.

“Object,” “entry,” “preparation,” and “comparison” describe inferred roles. The established contract concerns integer-valued arguments, object-relative reads, dependency calls, and the returned position. No particular collection type or equality relation is established.

## Interface

### Arguments and result

| Item | Contract |
|---|---|
| Object argument | Integer-valued address carrier. Zero prevents both dependency calls and all direct memory reads. A nonzero value is passed to F-266f529b8bb5 and, if traversal occurs, identifies the object representation. |
| Search argument | Integer-valued comparison operand. Zero prevents traversal but does not prevent preparation of a nonzero object. Otherwise, it is supplied unchanged as the second operand to U-1. |
| Result | Integer-valued position. Zero indicates no observed successful comparison; a positive result identifies the successful entry’s one-based physical position. |

The search argument is not directly dereferenced by this function. Whether it represents an address, scalar, handle, or some other value depends on U-1.

There is no separate status channel, output buffer, or error object.

### Relevant memory layout

Only the following parts of the object representation are directly used:

| Object-relative byte offset | Role |
|---|---|
| 52 | Signed integer traversal bound. |
| 60 | Integer-valued address of entry storage. |

Entry locations are separated by four bytes. The value obtained from an entry is treated as an integer-valued comparison operand. Zero denotes an entry that must not be passed to U-1.

The supplied representation supports a four-byte-slot, 32-bit-integer interpretation. It does not independently establish the target ABI, address width, or arithmetic rules. Numerical limits stated for signed 32-bit arithmetic below are therefore conditional on that interpretation. The four-byte displacement between successive entry accesses is established independently of those numerical limits.

No element payload is directly inspected beyond the integer value read from its slot.

### Validity requirements

A normally completing search requires readable storage at every location actually reached. In particular:

- The object must remain suitable for each required field read.
- Each admitted entry location must be readable.
- Every nonzero entry passed to U-1, together with the search argument, must satisfy U-1’s requirements.
- Address calculations must be valid under the execution environment’s arithmetic and addressing rules.
- Dependencies must return normally for execution to proceed beyond their calls.

These are path-dependent requirements, not checks performed by the function. A nonpositive bound, for example, avoids the storage-address and entry reads entirely. Conversely, a positive bound provides no evidence that enough entry storage exists.

## Behavior

### Preparation and search eligibility

A zero object argument produces zero without invoking either dependency.

A nonzero object argument causes exactly one invocation of F-266f529b8bb5, provided execution reaches and completes that call normally. The dependency receives the object argument; its return value has no role in the result or subsequent search decision.

The search argument is relevant to traversal only after preparation. Consequently, a nonzero object paired with a zero search argument still invokes F-266f529b8bb5. On normal return from that dependency, the function returns zero without directly reading either object field or any entry.

Preparation is therefore not conditional on whether a search will occur. Its effects, if any, remain observable even on the zero-search-argument path.

### Candidate selection and result meaning

When traversal is enabled, candidates are considered in increasing physical position, beginning with the first slot. Eligibility is determined by a signed comparison between the current zero-based position and the current bound.

A zero or negative initial bound admits no candidate. For an admitted position, the entry location is determined using the storage-address field and a displacement of four bytes per preceding position.

A zero entry occupies a position but does not cause a comparison call. A nonzero entry is passed to U-1 as its first operand, with the original search argument as its second operand.

Only a zero result from U-1 establishes success. Positive and negative nonzero results both allow the search to continue. The function does not interpret a negative result as an error or assign an ordering meaning to its sign.

The successful return identifies the physical position, including any preceding zero entries. It is not the number of calls to U-1. The first successful comparison ends the function immediately; later positions are not inspected.

If traversal reaches a position that is not below the current bound without having observed success, the result is zero.

### Observable read and call ordering

Preparation precedes every direct read of the traversal representation. There is no object-field snapshot before F-266f529b8bb5.

Within traversal, admission of a candidate depends on a bound read that precedes that candidate’s storage-address and entry reads. The storage address is obtained only for an admitted position. Its read precedes the corresponding entry read, which in turn precedes any U-1 call for that entry.

The bound and storage address are not retained as a fixed snapshot for the whole search. After an unsuccessful comparison, the next candidate is subject to a fresh bound read. If admitted, it uses a fresh storage-address read.

These ordering properties have observable consequences when dependencies mutate state:

- Preparation can determine the field values seen by the first candidate.
- A failed comparison can shorten, extend, or otherwise alter the bound used for later candidates.
- A failed comparison can redirect later entry reads to different storage.
- Replacing storage does not restart the search or revisit earlier positions.
- A successful comparison causes no subsequent bound or storage-address read.

The entry operand for a comparison has already been obtained before U-1 runs. Changing that slot during the call does not cause the current position to be reread or compared again.

These guarantees describe the represented accesses and dependency interactions. They do not establish a concurrent-memory model, volatile-access semantics, or synchronization with unrelated execution contexts.

### Arithmetic limits

The traversal bound is signed. The entry displacement is four times the zero-based position, and success returns that position plus one.

Under a signed 32-bit interpretation, the largest possible admitted position is 2,147,483,646: it must be strictly below a bound no greater than 2,147,483,647. A successful result can therefore reach 2,147,483,647 without overflowing that integer model. Advancing from the largest admitted position to the next bound check also fits.

Entry-address arithmetic has a separate constraint. The mathematical displacement fits a signed 32-bit integer through position 536,870,911. At position 536,870,912, the displacement is 2,147,483,648 and no longer fits that signed range. Adding even a representable displacement to the storage address can independently exceed the permitted address domain.

The supplied evidence does not determine whether an out-of-range calculation wraps, traps, or lacks defined behavior. This contract promises neither a zero result nor safe termination in those circumstances.

### Failure behavior

No local error-handling path is established for unreadable memory, invalid operands to dependencies, arithmetic faults, or abnormal dependency exits.

Zero is a normal search outcome, not a general failure conversion. If preparation or comparison fails to return normally, a normal result from F-983671f6b07e is not established.

## Side effects

The function contains no explicit writes to the object or entry storage. Its direct externally relevant operations are conditional dependency calls, memory reads, and delivery of the result.

No direct allocation, deallocation, ownership transfer, reference-count adjustment, or cleanup operation is visible.

That absence does not establish that the overall invocation is read-only. Neither dependency is known to preserve:

- Object fields or entry contents.
- Global state.
- Storage addresses or allocation lifetimes.
- Resources associated with the supplied arguments.

F-266f529b8bb5 may affect the representation subsequently searched. U-1 may affect later traversal or produce externally visible effects even when its return value rejects the current entry.

Passing an argument to either dependency does not establish whether associated memory is borrowed, retained, consumed, or released. If a dependency invalidates storage that a later access requires, this function provides no visible safeguard.

No locking, snapshot isolation, rollback, or explicit recovery mechanism is established. Repeated field reads are not evidence of thread safety or reentrancy.

## Acceptance examples

The following are conditional acceptance scenarios, not executed tests. Unless stated otherwise, they assume readable storage, valid arithmetic, normal dependency returns, and stable relevant state.

### Zero object

For a zero object argument, the result is zero regardless of the search argument.

Neither dependency is invoked. There are no direct object-field or entry reads.

### Zero search argument

For a nonzero object argument and zero search argument, F-266f529b8bb5 receives the object argument once.

If that call returns normally, the result is zero. The function performs no direct traversal-field or entry reads, and U-1 is not invoked. Any preparation effects are neither suppressed nor undone.

### Empty or negative bound

With both arguments nonzero, suppose preparation leaves the bound at zero or a negative value.

The result is zero after the initial bound read. The storage-address field and entry storage are not read, and U-1 is not invoked.

### Sparse positions

Suppose the stable bound is three. The first entry is zero; the second is nonzero and receives a nonzero comparison result; the third is nonzero and receives a zero comparison result.

The result is **3**, with two U-1 calls. The skipped zero entry still contributes to the returned position.

### Nonzero comparison results

Suppose two admitted nonzero entries produce comparison results of negative one and positive one, respectively, and the next position is outside the bound.

The result is **0**. Neither comparison result causes success, and the negative value is not treated as a locally handled error.

### Earliest successful position

Suppose the first entry is nonzero and U-1 returns zero for it.

The result is **1**. No later entry is read, and no subsequent traversal-bound read occurs.

### Preparation changes the representation

Suppose F-266f529b8bb5 replaces the storage address and changes the bound before returning.

Any subsequent traversal uses the resulting fields. There is no earlier direct snapshot whose values override those changes.

### Failed comparison reduces the bound

Suppose the first comparison returns nonzero and changes the bound to one.

The next position is not admitted. The result is **0**, without reading a second entry or rereading the storage-address field for that position.

### Failed comparison replaces storage

Suppose the first comparison returns nonzero, installs replacement entry storage, and leaves a bound that admits the second position.

The next entry is taken from the second position of the replacement storage. The first position in the replacement storage is not revisited.

### Successful comparison changes the object

Suppose U-1 changes the bound or storage address while returning zero.

The current one-based position is returned immediately. It is not revalidated against the modified object.
