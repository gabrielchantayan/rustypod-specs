# F-646805e2d5b7

## Purpose

F-646805e2d5b7 conditionally removes a node from a pointer-linked, color-marked structure. On the removal path, it reconnects links, conditionally performs color repair, invokes a removal-related dependency, decrements a count-like field, and writes a 32-bit result to caller-provided storage.

The structure resembles a red-black tree with a header containing root and extremal links. That is **inferred intent**, not an established external contract. The behavior below follows the supplied static evidence, including cursor choices and dependency-call arguments that must not be replaced with conventional tree-erasure behavior.

The result is not established to identify the removed node, its successor, or success. On the removal path, it is the value of a dependency-exposed local word **at the final assignment**.

## Interface

The function accepts three inputs and has no explicit return value:

| Input | Established role |
|---|---|
| Result destination | Address receiving one 32-bit word on normal completion. |
| Container address | Base address for a header-pointer field and a count-like field. |
| Node-reference address | Address of a 32-bit word read initially and reread to obtain the removal target. |

Represented pointers and pointer fields are 32 bits. Color accesses are one byte. The contract therefore requires an execution environment in which these represented addresses are meaningful; it is not an address-width-independent interface.

## Behavior

### Initial reads and branch selection

The function first reads the node-reference word into a local 32-bit result word. It next reads the container’s header pointer into a separate local 32-bit word. F-8e016e73ddbc receives the addresses of those two local words.

These are addresses of local copies, not the original node-reference address or the address of the container’s header field. Mutating a local copy does not, by itself, update the corresponding original field.

If F-8e016e73ddbc returns nonzero, the function rereads the container’s header pointer, assigns that value to the local result word, writes the word to the result destination, and completes. There are no direct structural writes, count decrement, or removal-related calls on this branch. Effects of the comparison dependency are not excluded.

If it returns zero, F-de786f046894 receives the address of the local result word. After that call, the function rereads the original node-reference word and uses this newly read value as the removal target.

Consequences:

- The target need not equal the initial node-reference value.
- Neither local-word mutation nor the initial header copy determines subsequent structural accesses.
- The local result word’s address is exposed to both initial dependencies. Either may retain that address or make it reachable by later dependencies.
- No preservation guarantee spans later calls. The removal-path output is the local word’s value at the final assignment, including any indirect modifications made before then.

### Target classification

The target’s left-child link is examined first.

- If it is null, the right-child link distinguishes a leaf from a single-right-child target.
- If it is nonnull and the right-child link is null, the left child is the replacement.
- If both children are nonnull, the leftmost node of the right subtree is selected for transplantation.

The original target remains the node supplied to the removal-related dependency.

### Leaf removal

For a leaf, the target’s parent is obtained.

If the parent equals the current header pointer, direct structural writes occur in this order:

1. Set the header’s rightmost link to the parent, which equals that header.
2. Set the header’s leftmost link to the same value.
3. Set the header’s root link to zero.

The container’s header field is reread for these field accesses; the behavior is not defined using one permanently cached header.

Otherwise, the parent’s left-child link is compared with the target. A match selects the left-child field for clearing; a mismatch selects the right-child field without requiring a separate right-link match.

Clearing consists of four individual zero-byte writes in increasing byte-address order. It is not represented as one 32-bit store.

The function then examines one header extremal link: leftmost for the left-child case, rightmost otherwise. If that link equals the target, it is replaced by the parent. The other extremal link is not checked in this leaf branch.

The parent becomes the repair cursor. The cursor is not a representation of the detached null-child position.

### Single-child removal

The nonnull child becomes the replacement and repair cursor. Structural operations proceed in this order:

1. Write the target’s parent into the replacement’s parent field.
2. Read the current header’s root link.
3. If that link equals the target, replace it with the child.
4. Otherwise, inspect the target parent’s left link. Replace that link on a match; otherwise replace the parent’s right link.
5. Inspect and conditionally update the header’s leftmost link.
6. Inspect and conditionally update the header’s rightmost link.

If the leftmost link identifies the target, it becomes:

- The target’s parent when the target’s right child is null.
- Otherwise, the leftmost node reached by following left links from the replacement.

If the rightmost link identifies the target, it becomes:

- The target’s parent when the target’s left child is null.
- Otherwise, the rightmost node reached by following right links from the replacement.

These operations reconnect nodes; they do not copy a payload. The detached original target remains the removal-call argument.

### Two-child removal

The function follows left links from the target’s right child until it reaches a node without a left child. This selected node is called the successor here. Its right child, possibly null, is initially selected as the repair cursor.

Transplantation begins by writing the successor into the target left child’s parent field, then writing the target’s left-child link into the successor’s left field.

If the successor is the target’s immediate right child, a nonnull successor right child has its parent set to the successor.

Otherwise, the following operations occur in order:

1. If the successor’s right child is nonnull, set that child’s parent to the successor’s former parent.
2. Replace the successor’s former parent’s left link with that right child, including zero when absent.
3. Set the successor’s right link to the target’s right child.
4. Set that right child’s parent to the successor.

Next, the target is replaced in the header root or its parent’s selected child link. Selection is root-first, then parent-left match, otherwise parent-right. The successor’s parent is then set to the target’s parent.

The function saves the successor’s old color byte. If the successor’s original right child was null, the successor itself becomes the repair cursor. It then writes the target’s color into the successor and the saved successor color into the detached target.

Thus:

- The successor is moved structurally; there is no observed payload copy.
- The detached target’s color becomes the successor’s original color.
- That detached color controls repair eligibility.
- A null successor right child produces a successor cursor, not a null cursor.
- This branch performs no explicit extremal-header updates.

### Repair eligibility and termination

After structural removal, the function rereads the header pointer.

If the repair cursor equals that header, repair is skipped without reading the detached node’s color for eligibility. Otherwise, the detached node’s color is inspected:

- Zero skips repair.
- Any nonzero byte enters repair.

Once entered, the repair loop continues only if the cursor is not the root obtained through the current header and the cursor’s color is exactly 1. Root equality is tested before the cursor-color condition.

The entry test and continuation test differ. A color of 2 is nonzero but is not equal to 1.

Every normal exit from an entered repair section writes 1 to the current cursor’s color. No such final repair write occurs when repair is skipped entirely.

### Repair transformations

The function determines whether the cursor equals its parent’s left child. If not, it uses the opposite branch without separately establishing that the cursor equals the right child.

For description, the sibling’s **inner child** is the child nearer the cursor; its **outer child** is the other child.

For a left-child cursor, the sibling is the parent’s right child:

- If absent, the cursor is recolored to 0, the cursor moves to the parent, and eligibility for another loop iteration is checked.
- If its color is zero, the sibling is recolored to 1, the parent to 0, and F-967e83193b72 is called with the container and parent. The cursor’s parent and sibling are reread. An absent reread sibling takes the upward-movement case.
- If both sibling children are absent or have color exactly 1, the sibling is recolored to 0 and the cursor moves to its parent.

## Side effects

Direct writes can affect:

- Root, parent, child, and extremal links.
- Individual bytes of a cleared parent child field.
- Node colors during transplantation and repair.
- The count-like field.
- The caller’s result destination.

No direct allocation, payload access, or release operation is shown. Whether F-fc81232f2e53 destroys or releases the target is unknown. This function does not directly access the target after that call.

The operation is nontransactional. Structural writes precede repair, the removal dependency, count update, and output assignment. No rollback is established.

The function repeatedly reads the container’s header field and rereads links after selected repair calls. Unknown dependencies must not be assumed to preserve globals, container state, node storage, or exposed local words.

There are no alias checks. In particular, the final output store can overwrite a count or link field if the result destination aliases it. Any alias-sensitive obligation must account for actual read/write order rather than assume independent storage.

## Acceptance examples

These are conditional static obligations, not executed tests. Structural examples assume suitable storage and no dependency effects that invalidate their stated conditions.

1. **Early completion.** If F-8e016e73ddbc returns nonzero after changing the container’s header field, output must receive the subsequently reread header value. No direct removal or count decrement occurs.

2. **Conditionally stable result.** If comparison selects removal, F-de786f046894 writes a particular word, and no later activity changes that local word, normal completion must output that word. Its meaning need not be a successor.

3. **Later result mutation.** If an initial dependency exposes the result-word address to a later dependency, and that later dependency validly changes the word before final assignment, output must receive the later value. Preservation of the earlier value is not required.

4. **Single-node tree.** With a leaf target whose parent equals the header, structural writes set rightmost and leftmost to the header, then root to zero. If the cursor still equals the reread header, repair is skipped. The removal call precedes count decrement.

5. **Zero-colored nonroot leaf.** The selected parent child field is cleared using four ordered byte stores. The selected extremal link moves to the parent if it identifies the target. Detached color zero suppresses repair.

6. **Single-child replacement.** The child’s parent is updated before root or parent-child redirection. The original target, not the child, is passed to F-fc81232f2e53.

7. **Successor with no right child.** Two-child removal transplants the successor and exchanges the two color bytes. The successor becomes the repair cursor. No null-position cursor may be substituted.

8. **Noncanonical color.** Detached color 2 permits repair entry when the cursor differs from the header. Cursor color 2 fails the exact-1 continuation condition and is then written to 1.

9. **Dependency-modified count.** If F-fc81232f2e53 sets the count to 10 and returns normally, with no relevant alias interference, the direct count update stores 9.

10. **Output/count alias.** If the result destination aliases the count field, the final result store follows and may overwrite the decremented count. An unconditional final-count guarantee is unsupported for that alias.
