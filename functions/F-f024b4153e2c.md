# F-f024b4153e2c

## Purpose

F-f024b4153e2c conditionally removes a supplied node from a forward-linked container, clears the node’s container association, updates container bookkeeping, and may invoke a node-associated indirect function.

The established behavior includes a predecessor shortcut: a stored container field is accepted as the predecessor when its forward link equals the supplied node. This shortcut is not independently checked against the container’s head.

The usual successful result is the removed node’s forward-link value. Zero also represents several other outcomes, including rejection, an unsuccessful search, and successful removal of a final node. The return value is therefore not a success indicator.

The interpretation as a container-removal operation is inferred intent. The field accesses, branch conditions, writes, indirect invocation, and returned value described below are established static behavior.

## Interface

### Inputs

The function accepts two machine-level arguments:

- **Container address:** a 32-bit value used as the base address of a mutable container record.
- **Node address:** a pointer to a mutable node record, or zero.

The supplied representation uses 32-bit integers, 32-bit pointer-bearing fields, and four-byte field spacing. This contract describes that representation; it does not establish portability to a different pointer width.

A zero node address is explicitly supported. A zero container address is not generally supported: with a nonzero node, the function eventually accesses container-relative storage if the node’s association check passes.

### Container layout

The following fields are accessed, at byte offsets from the container address:

| Offset | Width | Behavioral role |
|---|---:|---|
| +4 | 32 bits | Head node address |
| +8 | 32 bits | Tail-associated node address |
| +12 | 32 bits | Stored predecessor address |
| +16 | 32 bits | Count-like integer |

No meaning is established for bytes before offset +4 or for other container fields.

“Head,” “tail-associated,” “stored predecessor,” and “count-like” describe how this function uses the fields. They do not establish invariants maintained by other operations.

### Node layout

The following node fields are accessed:

| Offset | Width | Behavioral role |
|---|---:|---|
| +0 | 32 bits | Address of a dispatch table |
| +4 | 32 bits | Forward-link address |
| +8 | 32 bits | Flags; only bit 0 is tested |
| +12 | 32 bits | Associated container address |

When the indirect invocation is selected, a function address is obtained from byte offset +4 in the dispatch table addressed by the node’s first field.

### Output

The return value is a 32-bit value. On an ordinary successful unlink, it is the removed node’s forward link, sampled during the unlink operation.

Zero is returned when:

- The supplied node address is zero.
- The node’s associated-container field differs from the container argument.
- A required predecessor search reaches the end without locating the node.
- A successful unlink samples a zero forward link.

The function supplies no separate status or diagnostic.

### Preconditions for ordinary list behavior

For the normal removal interpretation:

- Accessed container, node, and dispatch storage must be valid for the relevant reads or writes.
- Container and node records must not overlap in ways that alias distinct logical fields.
- Traversed forward links must address readable node records or be zero.
- A search must eventually find the target or reach zero if termination is required.
- The stored predecessor must either be zero or identify readable storage; when its forward link matches the target, the function trusts that relationship.
- If the indirect invocation is selected, both the dispatch table and the function address at its +4 slot must be valid.

These are conditions for defined, interpretable execution, not validations performed by the function.

## Behavior

### 1. Initial rejection

The function initializes its prospective return value to zero.

If the supplied node address is zero, it immediately returns zero. It does not access the container or node storage.

Otherwise, it reads the node’s associated-container field at +12 and compares that 32-bit value with the container argument. A mismatch causes an immediate zero return.

These two rejection paths perform no explicit writes and no indirect invocation.

A matching association is necessary to proceed, but it does not prove that the node is reachable from the head.

### 2. Stored-predecessor shortcut

After the association matches, the function reads the container’s stored predecessor at +12.

- If it is zero, the shortcut cannot be used.
- If it is nonzero, the function reads that record’s forward link at +4.
- If that forward link equals the supplied node address, predecessor discovery is skipped.

A matching stored predecessor is accepted without checking whether it belongs to the container’s forward chain. In particular, the head field is not consulted on this shortcut.

If the stored predecessor is zero or its forward link does not match, the function proceeds to head handling or traversal.

### 3. Head handling

When predecessor discovery is required, the function reads the container head.

If the head equals the supplied node:

1. The stored predecessor field is written to zero.
2. The target’s forward link is read and retained as the return value.
3. The head is replaced with that retained value.
4. The count-like field is read, decremented by one, and written back.
5. The target’s associated-container field is cleared to zero.

With ordinary non-overlapping records and no external mutation, the later predecessor-based unlink is skipped because the stored predecessor is now zero. The head-removal path therefore decrements the count once.

The function does not clear the removed node’s forward link.

### 4. Predecessor search

If the head differs from the target, the function searches forward from the head.

For each nonzero candidate predecessor, its forward link is examined:

- If the link equals the target, that candidate is selected.
- Otherwise, traversal continues at that link.

When a predecessor is found, its address is written into the container’s stored-predecessor field. The target’s associated-container field is then cleared to zero.

If traversal reaches zero without finding a predecessor, the function discards its working target reference and proceeds to the common finishing checks. Under ordinary non-overlapping storage:

- The return value remains zero.
- The target’s associated-container field remains unchanged.
- The container fields remain unchanged.
- The indirect invocation is skipped.

There is no cycle detection. A reachable cycle that never produces a forward link equal to the target can prevent return.

### 5. Predecessor-based unlink

After the target association has been cleared, the function checks whether both the container’s current stored predecessor and the working target reference are nonzero.

If both are nonzero:

1. The target’s forward link is read and retained as the return value.
2. That value is written into the current stored predecessor’s forward-link field.
3. The count-like field is read, decremented by one, and written back.

This path covers both a trusted stored-predecessor shortcut and a predecessor located by traversal.

The predecessor field is retained after this unlink; it is not cleared merely because it was used.

The ordering differs from head removal:

- For head removal, head replacement and count decrement occur before clearing the target association.
- For predecessor-based removal, clearing the target association occurs before forward-link replacement and count decrement.

### 6. Tail-associated field update

The function next reads the container’s tail-associated field.

If it is nonzero and equals the working target reference, it is replaced with the retained return value.

Consequently, under normal list invariants, removing a final node whose forward link is zero writes zero into this field. The function does **not** replace it with the predecessor.

If the removed node has a nonzero forward link and the tail-associated field nevertheless equals that node, the field becomes that nonzero forward link. There is no consistency check requiring a tail-associated node to have a zero forward link.

### 7. Conditional indirect invocation

After structural and bookkeeping updates, the function examines the working target:

- A zero working target suppresses the invocation.
- For a nonzero target, bit 0 of its flags field is tested.
- If bit 0 is clear, no invocation occurs.
- If bit 0 is set, the function calls F-INDIRECT-01 with the target address as its argument.

The condition tests bit 0 only. Other flag bits do not select or suppress this invocation.

The dispatch-table address and function slot are read when the call is made. The indirect function’s return value is not used.

There are no further explicit container or node writes after the call. If the call returns normally, F-f024b4153e2c returns the retained 32-bit result. If the call does not return, this function does not reach its normal return.

## Side effects

### Explicit memory changes

On ordinary successful removal, the function:

- Clears the target’s associated-container field.
- Replaces either the head or a predecessor’s forward link.
- Decrements the container’s count-like field.
- Writes the stored predecessor when head removal or traversal requires it.
- Conditionally replaces the tail-associated field.

It does not explicitly:

- Clear the removed node’s forward link.
- Modify the node’s flags.
- Replace the node’s dispatch-table address.
- Allocate memory.
- Directly release memory.
- Repair other container invariants.

### Arithmetic

The count operation is a decrement of a 32-bit integer field. There is no lower-bound check, saturation, or validation that the original count is positive.

For example, a stored count of zero is decremented to −1 when interpreted as a signed 32-bit integer. Behavior at the minimum signed value depends on the underlying arithmetic semantics; the supplied representation does not establish a portable overflow rule.

### Ownership and lifetime

Clearing the association is an explicit state change, not proof that storage ownership transfers to any particular party.

The flag-selected call may affect lifetime, but its implementation is unavailable. It must not be assumed to release the node, preserve it, preserve container state, or leave other memory unchanged.

The retained return value is sampled before that call. Even if it denotes a successor address, this function does not establish that the addressed object remains live after the call.

### Failure and concurrency

There is no explicit error recovery or rollback. Invalid addresses, invalid dispatch data, or arithmetic behavior outside the established representation have no specified recovery path.

No locking or atomic protocol is shown. The ordinary transition descriptions assume no concurrent or reentrant mutation during the pre-call reads and writes. The function rereads several fields rather than operating on an immutable snapshot.

## Acceptance examples

The following are conditional contract examples, not executed tests. Unless stated otherwise, records are valid and non-overlapping, the chain is finite, no external mutation occurs, and target flag bit 0 is clear.

### Null target

Given any container argument and a zero node address:

- The result is zero.
- No container access is required.
- No write or indirect invocation occurs.

### Association mismatch

Given a nonzero target whose associated-container field differs from the supplied container address:

- The result is zero.
- No container fields are read.
- The target association remains unchanged.

### Head removal

Given a chain A → B → zero, head A, count 2, and a zero stored predecessor, removing A:

- Returns B.
- Changes the head to B.
- Leaves the stored predecessor zero.
- Changes the count to 1.
- Clears A’s association.
- Leaves A’s forward link equal to B.
- Leaves a tail-associated field containing B unchanged.

### Interior removal by search

Given A → B → C → zero, head A, count 3, and no matching stored-predecessor shortcut, removing B:

- Stores A as the predecessor.
- Clears B’s association.
- Changes A’s forward link to C.
- Changes the count to 2.
- Returns C.
- Leaves B’s forward link equal to C.

### Final-node removal

Given A → B → zero, count 2, tail-associated field B, and a usable predecessor A, removing B:

- Changes A’s forward link to zero.
- Clears B’s association.
- Changes the count to 1.
- Changes the tail-associated field to zero, not A.
- Returns zero despite successful removal.

### Matching association, unreachable node

Given a target associated with the container but absent from its finite chain, and no matching stored-predecessor shortcut:

- The search reaches zero.
- The result is zero.
- The target association is not cleared.
- The container is not explicitly changed.
- No indirect invocation occurs, even if the target’s flag bit 0 is set.

### Shortcut outside the head chain

Given a stored predecessor P whose forward link equals target B, even though P is not reachable from the head:

- The shortcut is accepted.
- No head-chain membership search occurs.
- B’s association is cleared.
- P’s forward link becomes B’s forward link.
- The count is decremented.

This illustrates the absence of membership validation, not a valid-container invariant.

### Flag-selected invocation

Given an otherwise successful removal with target flag bit 0 set:

- The indirect function is invoked once with the target address.
- Association clearing, unlinking, count decrement, and any tail-associated update precede the call.
- The retained successor value is returned only if the call returns normally.
- Final memory state cannot be determined without the callee’s contract.
