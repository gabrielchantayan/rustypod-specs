# F-870ebb745467

## Purpose

F-870ebb745467 performs an ordered reset of selected fields in a caller-supplied object, with two intervening calls to F-bf7242c98d06.

The established behavior is narrower than a destructor or resource-release contract: it obtains one 32-bit value through an indirect reference, passes that value and an object field to the dependency, clears five fields, calls the dependency again using a different object field, and clears four more fields plus one byte.

The pattern suggests cleanup of two related groups of state. That purpose is **inferred intent**, not proof that either dependency call releases memory, that the cleared fields represent owned resources, or that the complete object becomes reusable.

This contract describes the supplied static evidence. No runtime tests have been performed.

## Behavior

### 1. Obtain the shared dependency argument

Before either dependency call, the function reads the 32-bit reference at object offset `0xC4`, then reads a 32-bit value through that reference.

The resulting value is retained for both dependency calls. It is not recomputed between calls.

This distinction is observable: if the first dependency call changes the object’s `0xC4` field or changes the referenced storage, those changes do not select a new first argument for the second call.

No null or zero test precedes this indirect read. A zero reference is not an established no-op case.

### 2. Perform the first dependency call

The function reads the 32-bit field at offset `0xB0` and invokes F-bf7242c98d06 with:

1. The previously obtained 32-bit value.
2. The value read from `0xB0`.

The call is unconditional on the straight-line path. In particular, a zero value at `0xB0` does not cause the call to be skipped.

The function itself has not yet cleared any of the listed object fields when this call begins. This does not constrain changes made by other actors or by the dependency itself.

### 3. Clear the first group

After the first dependency call returns normally, the function performs these 32-bit zero writes in order:

1. Offset `0xB0`.
2. Offset `0xB4`.
3. Offset `0xAC`.
4. Offset `0xA4`.
5. Offset `0xA8`.

Each write covers four bytes. The order is part of the observed access sequence; it is not increasing address order.

These writes overwrite the respective fields regardless of what F-bf7242c98d06 may have written there during the first call. There is no conditional clearing based on their values.

### 4. Read the second argument and call again

Only after the five preceding writes does the function read the 32-bit field at offset `0xC0`.

It then invokes F-bf7242c98d06 with:

1. The same retained 32-bit value used in the first call.
2. The value just read from `0xC0`.

Consequently, the second argument is not necessarily the entry value of `0xC0`. A change made by the first dependency call can affect it. The function does not save this field before making the first call.

This second call is also unconditional on the ordinary path. A zero value at `0xC0` does not suppress it.

### 5. Clear the remaining group and final byte

After the second dependency call returns normally, the function performs these writes in order:

1. A 32-bit zero at offset `0xC0`.
2. A 32-bit zero at offset `0xBC`.
3. A 32-bit zero at offset `0xB8`.
4. A 32-bit zero at offset `0xC4`.
5. An 8-bit zero at offset `0xC8`.

The final write affects only one byte. It must not be widened into a four-byte clear that also overwrites offsets `0xC9` through `0xCB`.

After that byte write, the function returns without an explicit result.

### Completion and interruption

There is no explicit branch, loop, retry, rollback, or error-reporting path.

The sequence is not transactional. If an access fails or a dependency call does not return normally, the supplied evidence does not establish completion of the remaining operations. Earlier effects may already have occurred.

After normal completion, the fields cleared following the second call have received their final zero writes. The first group has also received zero writes, but a dependency that modifies those fields during the second call can leave them nonzero: the function does not clear the first group again.
