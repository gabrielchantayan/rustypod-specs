# F-a3d697b6b735

## Purpose

F-a3d697b6b735 requests a 120-byte workspace, initializes three regions within it, performs initial processing and three ordered preparation calls, and invokes one operation selected by a 32-bit mode. An option can enable two additional, ordered processing calls. After successful allocation, every normal-return path passes the workspace base to a cleanup dependency.

The result is a 64-bit concatenation of a path-dependent high word and a status low word. The application-level meaning of the operations is not established.

The low-word statuses are:

| Status | Meaning |
|---|---|
| 0 | Allocation succeeded, the mode was supported, initial processing, all three preparations, the selected operation, and any enabled follow-up operations returned zero, and cleanup returned normally. |
| 1 | A processing dependency returned nonzero, or the mode was unsupported; cleanup subsequently returned normally. |
| 4 | Allocation returned null. No cleanup call occurs. |

These rules distinguish dependency categories. Allocation succeeds by returning a **nonnull address**, not by returning zero. Processing dependencies succeed by returning **zero**. Cleanup’s return value, if any, is ignored; its normal return is necessary for this function to return after successful allocation.

## Interface

### Arguments

The function accepts seven arguments:

| Position | Role | Width and interpretation |
|---|---|---|
| 1 | Mode | Unsigned 32-bit selector. |
| 2 | Operand A | 32-bit value forwarded to selected operations and used as the initial high result word. |
| 3 | Operand B | 32-bit value forwarded to preparation, selected operations, and follow-up operations. |
| 4 | Option | 32-bit value forwarded during preparation. Exactly 1 enables follow-up processing. |
| 5 | Configuration address | Address represented in 32 bits. A 32-bit field at byte offset 12 is read at specified stages. |
| 6 | Context address | Address represented in 32 bits. A 32-bit field at byte offset 64 is read for each preparation call. |
| 7 | Input-array address | Address of three consecutive 32-bit entries, accessed individually as preparation progresses. |

The supplied representation uses signed 32-bit types for several arguments. Their observed uses do not introduce signed ordering decisions: Operand A and Operand B are forwarded as 32-bit values; Option is compared for equality with 1; the address arguments participate in memory accesses. Mode selection uses unsigned comparisons and equality.

Processing results are tested for zero versus nonzero. A processing result with its high bit set is still a failure. This zero/nonzero rule does not apply to allocation or cleanup.

### Result

The function returns a 64-bit bit pattern:

- Bits 0–31 contain status 0, 1, or 4.
- Bits 32–63 contain the high word selected by the reached path.

The words are concatenated. Neither word is sign-extended into the other.

### Memory preconditions

If allocation returns null, the function performs no explicit dereference of the caller-supplied addresses and invokes none of the processing or cleanup dependencies.

After allocation succeeds, the initial-processing dependency receives the context, input-array, and configuration addresses. Its requirements for those addresses are unknown.

If execution reaches preparation, the function itself requires valid 32-bit reads from:

- Configuration address plus 12, before each reached preparation.
- Context address plus 64, for each reached preparation.
- Input-array address plus 0, 4, or 8, for the corresponding preparation.

Every supported dispatch branch additionally reads the configuration field at offset 12. Unsupported modes do not perform that additional dispatch-stage read.

Validity is required at the time of each access, including after earlier dependency calls. No null checks, bounds checks, or explicit recovery for invalid memory appear in the body.

Successful workspace initialization requires a writable allocation supporting the stated layout and representable internal addresses. The observed representation uses 32-bit address fields and 4-byte words. A wider-pointer ABI, address-overflow behavior, alignment requirements, and byte order are not established.

## Behavior

### Workspace allocation and initialization

F-d33f6d597e5d receives a request for 120 bytes.

If it returns null, the function returns status 4 with Operand A in the high word. Nothing else is called.

For a nonnull result, the function initializes the allocation as follows. Offsets are byte offsets from the returned workspace base.

| Write order | Offset | Width | Value |
|---|---:|---:|---|
| 1 | 0 | 4 bytes | Workspace base plus 12 |
| 2 | 12 | 4 bytes | Zero |
| 3 | 16 | 4 bytes | Workspace base plus 20 |
| 4 | 4 | 4 bytes | Workspace base plus 48 |
| 5 | 48 | 4 bytes | Zero |
| 6 | 52 | 4 bytes | Workspace base plus 56 |
| 7 | 8 | 4 bytes | Workspace base plus 84 |
| 8 | 84 | 4 bytes | Zero |
| 9 | 88 | 4 bytes | Workspace base plus 92 |

The first 12 bytes form a three-word header. Its entries initially point to three regions beginning at offsets 12, 48, and 84. Each region is 36 bytes apart from the next. Each receives a zero first word and a second word pointing eight bytes beyond that region’s start.

The internal-pointer writes obtain their destination and stored pointer value through reads of the corresponding header entry. No dependency call occurs between these initialization operations. The source does not establish a relative evaluation order between the header reads used for an individual internal-pointer assignment.

Only these nine words are explicitly initialized. The remaining 28 bytes of each region are not explicitly cleared or assigned by this function.

### Initial processing

After initialization, F-46045e04216b receives these arguments, in order:

1. Context address.
2. Input-array address.
3. Configuration address.

A zero result permits preparation. Any nonzero 32-bit result selects status 1, skips preparation, dispatch, and follow-up processing, and proceeds to cleanup.

On this failure path, the high result word remains Operand A.

### Three ordered preparations

F-43d17b9e9ea1 is called for input entries 0, 1, and 2, in that order, stopping at the first nonzero result.

Each call receives:

1. The corresponding 32-bit input-array entry.
2. Context address.
3. The current workspace header entry at offset 0, 4, or 8.
4. The current 32-bit field at Context address plus 64.
5. The 32-bit field freshly loaded from Configuration address plus 12.
6. Operand B.
7. Option.

For each preparation, the configuration-field load occurs before evaluation of that call’s remaining memory-based arguments. The relative order of the input-entry read, workspace-header read, and context-field read within the call’s argument evaluation is not established.

The three calls do not share one snapshot of these memory values. In particular:

- Each preparation has its own configuration-field load.
- Each reads its corresponding input entry when that preparation is reached.
- Each reads its corresponding workspace header entry rather than reconstructing the originally initialized pointer.
- Each reads the context field again.

Earlier dependencies may therefore affect later argument values. The body provides no guarantee that they preserve the configuration, context, input entries, or workspace header.

When a preparation returns nonzero:

- Later preparations are skipped.
- No mode-selected operation runs.
- Neither follow-up operation runs.
- Status becomes 1.
- The high result word is the configuration snapshot loaded before that failed preparation.
- Execution proceeds to cleanup.

When all three return zero, execution reaches mode selection.

### Mode-selected operation

Supported modes and their ordered argument lists are:

| Mode | Dependency | Arguments |
|---|---|---|
| 0, 1, 7 | F-b127cc91530e | 4; Operand A; 2; freshly read configuration field at +12; Context address; Operand B; workspace base |
| 2, 3, 6 | F-818a5ad7fd72 | Workspace base; Operand B; 4; Context address; freshly read configuration field at +12; Operand A |

Mode 4 also performs a fresh configuration-field read immediately before its selected call, even though that value is not passed to the dependency. The value becomes the high result word.

For modes 2, 3, and 6, the dispatch configuration read likewise occurs before the selected call and supplies both a call argument and the high word.

Modes 0, 1, and 7 select Context address as the high word. Mode 5 selects Operand B as the high word; its configuration read supplies a dependency argument but does not replace that high word.

Every other unsigned 32-bit mode is unsupported. Unsupported modes are rejected only after allocation, initial processing, and all three preparations have succeeded. No selected dependency is called, and no additional dispatch-stage configuration read occurs. Status becomes 1.

A selected dependency must return zero to permit further processing. Any nonzero result produces status 1 and skips both follow-ups.

### Optional follow-up processing

Following a supported selected operation that returns zero:

- If Option differs from 1, status becomes 0 without follow-up calls.
- If Option equals 1, F-519283beb223 is called with Operand B, Context address, and Configuration address, in that order.
- Only a zero result from F-519283beb223 permits F-62704de676b4, with the same ordered arguments.

A nonzero result from either follow-up produces status 1. Both must return zero for status 0 when follow-up processing is enabled.

Neither follow-up’s result replaces the high word. Subsequent memory changes by these dependencies also do not refresh a configuration snapshot already selected as the high word.

### Cleanup and return

Every normal-return path after successful allocation calls F-5e3309c9d083 exactly once with the original workspace base. This includes initial-processing failure, preparation failure, unsupported mode, selected-operation failure, follow-up failure, and success.

The cleanup return value, if any, is not examined and does not alter either result word. The function returns only if cleanup returns normally.

The call establishes that the workspace is passed to a cleanup dependency. It does not establish that the dependency releases the allocation, releases nested resources, or preserves any other memory.

## Side effects

The function’s explicit stores are the nine workspace writes listed above. Its explicit memory reads include workspace header reads during initialization and preparation, input-array entries, context fields, and configuration fields.

Dependencies may have additional effects. Their bodies are unavailable, so the contract does not assume that they:

- Preserve global state or caller-owned memory.
- Preserve workspace contents or header pointers.
- Avoid allocating, retaining, or releasing memory.
- Leave earlier work unchanged when returning failure.
- Preserve addresses needed by later accesses.

Individual workspace-region pointers are passed to preparations. The workspace base is passed to selected operations and cleanup. No workspace pointer is explicitly returned to the caller, but dependency retention of such pointers is unresolved.

Failure short-circuits later processing; it does not establish rollback. Cleanup is the only call common to all normal-return paths after successful allocation.

## Acceptance examples

The following are conditional expectations derived from static evidence, not executed tests. Unless otherwise stated, reached dependencies return normally and required memory accesses are valid.

1. **Allocation failure.** If Operand A is `0x89ABCDEF` and allocation returns null, the result is `0x89ABCDEF00000004`. No processing or cleanup dependency is called.

2. **Initial-processing failure.** If allocation succeeds and F-46045e04216b returns 2, no preparation, dispatch, or follow-up occurs. Cleanup receives the workspace base. The result has Operand A as its high word and 1 as its low word, not 2.

3. **Second-preparation failure.** If initial processing and the first preparation succeed, the second preparation’s configuration snapshot is `0x12345678`, and that preparation returns nonzero, the result after cleanup is `0x1234567800000001`. The third preparation and all later processing are skipped.

4. **Unsupported mode.** If Mode is 8 and initial processing and all preparations return zero, all three preparations occur before rejection. No selected operation or follow-up runs. The high word is the snapshot preceding the third preparation, even if that preparation subsequently changes the configuration field.

5. **Successful processing with cleanup’s result ignored.** If Mode is 7, Option is 0, allocation succeeds, and all reached processing calls return zero, the low word is 0 and the high word is Context address. Cleanup must return normally. Any return value it produces, including a nonzero value, does not convert this outcome to status 1.

6. **Mode 4’s otherwise unused read.** If preparation succeeds, Mode is 4, and the dispatch-stage configuration read yields 9, a zero selected-operation result with Option unequal to 1 leads to `0x0000000900000000` after cleanup. The configuration read is required despite not supplying a selected-operation argument.

7. **Follow-up short-circuit.** If a supported selected operation succeeds and Option is 1, a nonzero result from F-519283beb223 prevents F-62704de676b4 from running. Cleanup still occurs and the low word is 1.

8. **Mode 5 preserves Operand B as high word.** If Mode is 5 and Operand B is `0xFFFFFFFF`, the high word is `0xFFFFFFFF` after dispatch, including when dispatch or a follow-up fails. A low-word failure produces `0xFFFFFFFF00000001`.

9. **Fresh preparation reads.** If an earlier returning dependency changes the configuration field from 3 to 5 before the next preparation’s load, that preparation receives 5. The function cannot be described as using a single configuration snapshot for the entire operation.

10. **Nonbinary option.** If Option is 2, its value is forwarded to each reached preparation, but it does not enable either follow-up. With otherwise successful processing and a supported mode, the low word is 0.
