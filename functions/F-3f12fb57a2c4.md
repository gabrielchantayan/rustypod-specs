# F-3f12fb57a2c4

## Purpose

F-3f12fb57a2c4 selects one of three operations on a resolved object using a one-byte selector in an input record. It forwards the record’s leading 32-bit value and a caller-supplied auxiliary object to the selected operation.

Selectors outside the supported set take a separate path involving a fixed-address shared data region and the auxiliary object. Depending on the first byte of that region, this path either invokes an auxiliary-object operation directly or requests a destination and conditionally invokes an indirect transfer operation.

This is a source-facing behavioral contract. The dispatch structure, offsets, explicit arguments, and local control flow are established by static evidence. The meanings of the selected operations, the shared data, and the destination request are not established. In particular, interpreting the unsupported-selector path as producing a diagnostic string is inferred intent, not a guaranteed semantic result.

## Interface

### Inputs

The function accepts three arguments:

1. **Context address.** An address-like value represented by a 32-bit integer in the supplied representation. Supported-selector paths pass this value plus 40 bytes to F-7d964f24a044. This function does not directly dereference the context address.
2. **Record address.** A pointer to a record containing:
   - At byte offset 0: a four-byte value forwarded without visible transformation.
   - At byte offset 4: a one-byte selector.
3. **Auxiliary-object address.** A pointer forwarded unchanged on supported-selector paths. On unsupported-selector paths, the function treats its first machine word as an address of an indirect-operation table.

The record’s remaining layout is unknown. There is no evidence that the bytes after the selector are padding, additional fields, or readable storage. The selector is read as one byte, not as a four-byte field.

The leading record value is an opaque 32-bit quantity. Its interpretation as an integer, pointer, identifier, handle, or bit field is not established.

### Indirect-object layouts

For objects used in this function, the supplied representation uses the first machine word as an operation-table address. The relevant table entries are identified by byte offsets:

| Object | Table offset | Use |
|---|---:|---|
| Resolved object | 356 | Selector 2 |

These are byte offsets, not operation indices. The supplied representation uses 32-bit address and value forms. No different-width ABI behavior is established.

### Output

There is no explicit return value.

Results returned by the three supported-selector operations, the auxiliary operation at offset 12, and the final indirect transfer operation are not used locally. The result of the auxiliary operation at offset 8 determines whether the final transfer operation is invoked.

There is no local success flag, status translation, or explicit error return.

### Preconditions

For execution to complete through the accesses shown:

- The selector byte at record offset 4 must be readable.
- On supported-selector paths, the record’s leading four bytes must be readable after F-7d964f24a044 returns.
- The resolver’s result must support the first-word and selected table-entry reads.
- On unsupported-selector paths, the shared region’s first byte must be readable.
- The auxiliary object must support the table lookup required by the chosen unsupported-selector branch.
- Every invoked indirect target must be callable with the arguments supplied.

These requirements are not validated locally. A supported selector does not cause this function itself to dereference the auxiliary object, although the selected operation receives it and may do so.

## Behavior

### 1. Read and classify the selector

The first explicit memory read obtains the byte at record offset 4.

Exactly three values are supported: 0, 1, and 2. Every other byte value takes the unsupported-selector path. Whether the implementation treats a plain byte-sized character as signed does not change this classification.

The selector is retained locally. It is not read again after a dependency call.

### 2. Supported selectors

For any supported selector, the function performs the following sequence:

1. Calls F-7d964f24a044 with the context address plus 40 bytes.
2. Retains the returned object address.
3. Reads the four-byte value at record offset 0.
4. Reads the returned object’s first word as an operation-table address.
5. Reads the selected target from that table.
6. Invokes that target with the resolved object address, the captured four-byte record value, and the original auxiliary-object address.
7. Returns if the invoked operation returns normally.

The selector-to-slot mapping is:

| Selector | Selected table offset |
|---:|---:|
| 0 | 360 bytes |
| 1 | 364 bytes |
| 2 | 356 bytes |

The slot order is not numerically ascending with selector value. A contract that maps selector 0 to offset 356 would be incorrect.

The ordering around F-7d964f24a044 is significant. The selector is captured before that call, but the record’s leading four-byte value is read afterward. If the resolver changes that leading value through an alias, the changed value is forwarded. If it changes the selector byte, the previously captured selector still determines the slot.

The object’s operation-table address is also read after the resolver returns. The function does not obtain an earlier table address or verify that the returned object is nonzero.

On these paths, the function contains no direct access to the shared-data region and no direct invocation of the auxiliary object’s offset-8 or offset-12 operations. Called dependencies may nevertheless perform such accesses or calls; their behavior is unknown.

### 3. Unsupported selector with a zero shared byte

For any unsupported selector, the function next reads the first byte of a fixed-address shared data region.

If this byte is zero, it:

1. Reads the auxiliary object’s first word as an operation-table address.
2. Reads the target at table byte offset 12.
3. Invokes that target with the auxiliary-object address as its sole explicit argument.
4. Returns if the operation returns normally.

This branch does not call F-7d964f24a044 or F-5cb57bbb2e0e. It does not directly read the record’s leading four-byte value.

The meaning of the offset-12 operation is unknown. Calling it a reset, clear, release, or error operation would add semantics not established by the supplied evidence.

### 4. Unsupported selector with a nonzero shared byte

If the shared region’s first byte is nonzero, the function:

1. Calls F-5cb57bbb2e0e with the shared region’s base address.
2. Adds one to its returned 32-bit integer.
3. Reads the auxiliary object’s current operation-table address.
4. Reads the target at table byte offset 8.
5. Invokes that target with:
   - The auxiliary-object address.
   - The incremented integer.
   - A zero-valued third argument.
6. Examines the returned 32-bit value.
7. If that value is nonzero, reads the final transfer target from a fixed-address shared function-pointer location and invokes it with the returned value and the shared region’s base address.
8. Returns if the applicable calls return normally.

If the offset-8 operation returns zero, the final transfer operation is skipped. No retry, alternate operation, or local error report follows.

The function does not recheck the shared region’s first byte after F-5cb57bbb2e0e returns. It also does not capture the region’s contents for later use. The final transfer operation receives the same base address, but the bytes stored there may have changed during intervening calls.

The auxiliary-object table lookup occurs after F-5cb57bbb2e0e returns. The final transfer-target lookup occurs after the offset-8 operation returns. Consequently, this function uses the table and transfer target present at those later lookup points; it does not establish that either remains unchanged across dependency calls.

### 5. Arithmetic boundaries

For representable results, these additions have the stated values. Behavior at a signed-integer boundary, or where address arithmetic does not produce a usable address, is not established by the supplied representation. This contract does not assume wraparound, saturation, or rejection.

The zero passed to the offset-8 operation is established only as a zero-valued explicit argument. Its interpretation as a flag, mode, pointer, or reserved value is unknown.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not reports of executed tests.

1. **Selector 0.** Given valid objects and normally returning dependencies, the resolver receives context plus 40, and the resolved object’s offset-360 operation receives the resolved object, the subsequently read 32-bit record value, and the auxiliary object.

2. **Selector 1.** Under the same validity conditions, the selected operation comes from offset 364, not offset 360 or 356.

3. **Selector 2.** Under the same validity conditions, the selected operation comes from offset 356.

4. **Resolver changes the record.** If the initial selector is 0 and the resolver changes both record fields, offset 360 remains selected, while the newly stored leading four-byte value is forwarded.

5. **Unsupported selector and zero shared byte.** For selector 3 and an initially zero shared byte, only the auxiliary offset-12 operation is directly invoked. Neither named dependency is called by this function.

6. **Unsupported selector and nonzero request result.** Suppose the shared byte is initially nonzero, F-5cb57bbb2e0e returns 7, and the offset-8 operation returns a nonzero value. The request receives 8 and zero as its second and third explicit arguments. The final transfer receives that nonzero result and the shared region’s address.

7. **Zero request result.** With the same initial branch conditions, if the offset-8 operation returns zero, the final transfer is not invoked.

8. **Shared data changes during a call.** If F-5cb57bbb2e0e changes the shared region’s first byte to zero, execution still proceeds to the offset-8 operation. The initial nonzero decision is not reconsidered.

9. **Different unsupported byte values.** Any byte other than 0, 1, or 2 follows the same unsupported-selector decision structure. There is no separate branch for a negative interpretation of a high-bit-set byte.
