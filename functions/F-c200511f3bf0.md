# F-c200511f3bf0

## Purpose

F-c200511f3bf0 performs a staged teardown of a non-null object: it conditionally processes an associated handle, invokes two object-related dependencies, decrements an owner-associated count, and then updates allocation-accounting state before handing the allocation header to another dependency.

A null object is an immediate no-op.

The teardown and accounting sequence is established by the supplied static evidence. Interpreting the final stages as memory release, the accounting context as an allocator, or particular dependencies as locking operations is inferred intent, not an established dependency contract.

This function does not establish that arbitrary non-null inputs are safe. It dereferences the object and invokes several dependencies before checking the allocation-header condition.

## Interface

### Inputs

The interface has two inputs:

- **Object address:** a 32-bit address-like value. Zero is accepted and causes immediate return. A nonzero value identifies the object body and must support all accesses described below.
- **Auxiliary value:** an uninterpreted 32-bit value. It is forwarded to F-b0e62816dde2 only when the handle field is not the sentinel value.

No return value is exposed.

A global reference supplies the accounting-context address. The function reads that reference after F-2fd8826557a4 returns. The address is retained for the remaining accounting operations; subsequent changes to the global reference do not redirect those operations.

### Preconditions for normal completion

For the non-null path:

- Object, prefix, owner, global-reference storage, and all accessed accounting locations must be readable or writable as appropriate.
- Dependencies must accept their arguments and return normally where continuation is expected.
- The allocation header must satisfy the observed validity condition at the point where it is checked.
- Both 16-bit indices and the index returned by F-09dcb55e8e0a must select valid accounting storage.
- The caller must satisfy any concurrency, ownership, or lifetime requirements imposed by dependencies. Those requirements are not supplied.

There is no local bounds validation for any accounting index.

## Behavior

### 1. Null handling and owner capture

If the object address is zero, the function returns without reading the auxiliary value from pointed-to storage, accessing the global accounting reference, invoking a dependency, or writing memory.

For a nonzero object, the function first reads the 32-bit owner address from object offset +4. It retains this address across subsequent calls. If a dependency later changes the object's owner field, the retained owner address still determines the later owner operations.

### 2. Conditional handle processing

The function reads the 32-bit handle field at object offset +364.

If that value is the all-ones bit pattern, conventionally signed −1, both handle-related calls are skipped. Zero is not the sentinel and does not skip them.

Otherwise, the function invokes F-b0e62816dde2 with four arguments:

1. A value read from the handle field.
2. The auxiliary input.
3. The 32-bit field at object offset +368.
4. The 32-bit field at object offset +372.

The source does not establish a portable relative order among the field reads used to prepare this call. It also does not establish that the handle read for the condition and the handle read for the call must observe the same value if storage can change between them.

After F-b0e62816dde2 returns, the function reads the handle field again and passes that newly read value to F-ec29e3fd7593. It does not necessarily pass the handle previously supplied to F-b0e62816dde2.

There is no local write that resets the handle to the sentinel. The function does not recheck the sentinel before invoking F-ec29e3fd7593. Consequently, if F-b0e62816dde2 changes the field to the sentinel, that sentinel is still passed to F-ec29e3fd7593.

### 3. Object-related cleanup and owner accounting

After the conditional handle stage, the following operations occur in order:

1. F-1dc7fdb390e6 receives the address at object offset +16.
2. F-8d6903442911 receives the retained owner address plus 32, followed by the object address.
3. The 32-bit word at retained owner offset +28 is read, decremented by one, and written back.
4. F-2fd8826557a4 is invoked without explicit arguments.
5. The global reference supplying the accounting-context address is read.

The owner count is read after F-8d6903442911 returns. Any dependency-caused change to that count before this read affects the decrement.

These operations precede the allocation-header validity check. Failure of that later check does not undo the earlier calls or the owner-count write.

### 4. Header check

The function examines the 32-bit header word at object offset −8.

The header is rejected if either:

- It is zero; or
- Its least significant bit is set.

On rejection, F-a817d8d58c10 is invoked. The supplied evidence marks this dependency as non-returning. No accounting-context entry call, allocation-accounting writes, or final header handoff follows on that path.

The zero test and low-bit test are represented as separate reads. If the zero test succeeds, the low-bit test is not needed. No synchronization protecting those initial reads is established by the supplied evidence.

The function does not reject a header merely because its masked accounting size is zero. A nonzero even header can pass validation while producing a zero size after masking.

### 5. First accounting updates

After the header passes the check, F-c0fc6d033caa is called with the retained accounting-context address.

Only after that call returns does the function derive the values for the first accounting updates:

1. Read the unsigned 16-bit index at object offset −4.
2. Read the 32-bit header and retain its value masked with `0x3ffffffc`.

The mask keeps bits 2 through 29. It clears the low two bits and the high two bits. The resulting accounting quantity ranges from zero through 1,073,741,820, in multiples of four.

Using this retained quantity, the function performs four read-modify-write subtractions in this order:

| Order | Accounting-context location |
|---:|---|
| 1 | +548 plus four times the first unsigned 16-bit index |
| 2 | +780 |
| 3 | +224 plus four times the second unsigned 16-bit index |
| 4 | +544 |

The second index is read from object offset −2 after the write at context offset +780, before its indexed subtraction.

All four subtractions use the same retained masked quantity. They do not each reload the header.

The pre-call validation does not establish the value of the later masked header read: F-c0fc6d033caa is an opaque dependency and is not assumed to preserve the prefix.

### 6. Remaining accounting updates

After those four writes, the function calls F-09dcb55e8e0a with no explicit arguments. Its return value selects another accounting location.

The function then performs these operations in order:

1. Decrement the 32-bit word at context offset +784 plus four times the returned index.
2. Decrement the 32-bit word at context offset +912.
3. Reload the header word at object offset −8, mask it with `0x3ffffffc`, and subtract this newly derived quantity from the 32-bit word at context offset +8.
4. Invoke F-cc6c9b4a0f68 with the retained context address and the allocation-prefix address at object offset −8.
5. Invoke F-e586bff64fb7 with the retained context address.
6. Return.

The subtraction at context offset +8 can therefore use a different quantity from the first four subtractions. In particular, F-09dcb55e8e0a could change the header or accounting state; its behavior is unknown.

There is no visible object or header access after F-cc6c9b4a0f68 returns. The subsequent dependency receives only the retained context address.

### 7. Widths, arithmetic, and aliasing

Both prefix indices are explicitly unsigned 16-bit quantities, ranging from 0 through 65,535. Their four-byte scaling ranges from zero through 262,140 before adding the context address and table offset.

Accounting words and counts are 32 bits. No underflow, overflow, saturation, or nonnegative-count check is present. A faithful 32-bit machine-level interpretation retains the low 32 bits of subtraction results. The supplied source representation mixes signed and unsigned arithmetic, so portable language-level signed-overflow guarantees are not established.

The returned index from F-09dcb55e8e0a has no visible nonnegative or range check. Its valid range and the behavior of extreme address calculations remain external requirements.

The visible address expressions do not prove that all accounting locations are distinct. If indexed locations alias fixed locations, each ordered read-modify-write still occurs; effects must not be collapsed into independent conceptual counters.

## Side effects

Established direct writes are:

- One owner-count decrement.
- Four size-based accounting subtractions using a retained masked header value.
- Two accounting-count decrements.
- One further size-based subtraction using a freshly read masked header value.

The null path performs none of these writes. The rejected-header path performs the owner-count decrement, but none of the allocation-accounting writes.

Dependencies may have additional effects. Nothing supplied establishes that they preserve object fields, global references, prefix storage, counters, or unrelated memory.

There is no visible rollback, error return, retry, or compensation. If a dependency does not return, the already completed prefix of effects remains the only locally established behavior.

Ownership transfer is not explicitly documented. F-cc6c9b4a0f68 receives the allocation-prefix address and may be associated with release, but actual deallocation, retention, reuse, or ownership transfer is documented_only. Callers cannot derive permission to reuse or access the object after return from this body alone.

## Acceptance examples

These examples are conditional static expectations, not runtime test results.

1. **Null object.** With object address zero and any auxiliary value, expect immediate return, no dependency calls, and no direct memory writes.

2. **Sentinel handle.** With a valid non-null object whose handle remains all ones during the initial check, expect neither F-b0e62816dde2 nor F-ec29e3fd7593. The embedded-region, owner, and allocation-accounting stages still proceed.

3. **Zero handle.** With a handle of zero and otherwise valid storage, expect both handle-related calls. Zero is not treated as absence.

4. **Handle changed by the first call.** If F-b0e62816dde2 changes the handle from 7 to 12 and returns, expect F-ec29e3fd7593 to receive 12. If it changes the handle to all ones, expect that value to be forwarded without another sentinel check.

5. **Rejected header after earlier teardown.** With a header that remains zero until validation, expect the object-related calls and owner decrement first, then F-a817d8d58c10. Expect no subsequent allocation-accounting updates.

6. **Stable size accounting.** Assume the header remains `0x00000024`, all dependencies return normally, selected locations are valid and nonaliasing, and dependencies do not modify the relevant counters. The masked quantity is 36. Expect subtraction of 36 at each of the first four accounting locations and at context offset +8, plus the three separate count decrements: one owner count and two context counts.

7. **Valid header with zero masked quantity.** A stable header of 2 is nonzero and even, so it passes the check. Its masked quantity is zero. Under otherwise valid conditions, expect the size-based read-modify-write operations to subtract zero, while all three count decrements still occur.

8. **Header changes during index selection.** If the first retained masked quantity is 36 and F-09dcb55e8e0a changes the header to yield 64, expect the first four size subtractions to use 36 and the later subtraction at context offset +8 to use 64.
