# F-d920a917d399

## Purpose

F-d920a917d399 scans a prefix of a byte sequence, constructs an arithmetic payload represented by two 32-bit words, and writes that payload to caller-provided storage. It returns a 32-bit address difference identifying the consumed prefix, not a conversion-success flag.

The recognized structure comprises leading classified bytes, one optional sign, a significand with an optional decimal point, and an optional exponent introduced by literal `e` or `E`. Recognition depends on both literal comparisons and a supplied classification table. Incomplete forms can be consumed without rejection.

Decimal-to-floating-point conversion is inferred intent. The supplied static evidence establishes scanning rules, dependency-call order, word layout, and final sign-bit transformation. It does not establish arithmetic constants, numeric representation, dependency mathematics, or the effective operands on the negative-exponent application path.

## Interface

### Inputs

**Input address**

- Identifies a sequence of 8-bit bytes without an accompanying length.
- Must support every byte read reached by scanning, including reads of stopping bytes that remain unconsumed.
- Supplies unsigned byte values for classification-table indexing.
- Does not inherently designate a zero-terminated string. A zero byte stops scanning only if the applicable classification and literal tests make it stop.

**Output address**

- Identifies storage writable as two consecutive 32-bit words, eight bytes total.
- Receives the accumulator’s low word first.
- Receives its high word second, conditionally XORed with `0x80000000` when a leading minus was consumed.
- Has no established alignment requirement or within-word byte order in the supplied evidence.

### Result

The returned value is the final scanning address minus the original input address, after conversion of both addresses to 32-bit integers.

For representable, nonwrapping address differences, this is the consumed-byte count. It includes skipped leading bytes and consumed signs, literal zeros, decimal points, exponent markers, and digits.

A zero return does not prevent output writes. A positive return does not establish that any digit was accumulated or that the consumed text is a conventional number. Portable behavior for unrepresentable address conversions or overflowing differences is **documented_only**.

### Preconditions and failure boundary

Normal completion requires readable input, readable classification storage, writable output, and normal return from every invoked dependency. F-2a4c402ba617 must return an object from which a usable table address can be read. The table must support indexing by every encountered unsigned byte value.

There are no explicit null, length, capacity, or arithmetic-overflow checks. No local recovery mechanism is established for inaccessible memory, dependency failure, or arithmetic exceptions.

## Behavior

### Classification and literal syntax

Before obtaining classification information, the routine reads two global 32-bit words to initialize its accumulator.

It calls F-2a4c402ba617 once, reads a table address from the returned object, and retains that address. Later classification operations use the retained address, not a copied table.

Two classification predicates are distinct:

| Use | Required classification entry |
|---|---|
| Leading skipping | Low bit set |
| Significand and exponent digits | Entire byte exactly `0x20` |

An entry of `0x21` permits leading skipping but does not qualify as a digit. No independent ASCII digit-range check accompanies digit recognition.

Literal syntax uses these byte values:

| Syntax | Value |
|---|---:|
| Plus | `0x2B` |
| Minus | `0x2D` |
| Decimal point | `0x2E` |
| Zero | `0x30` |
| Uppercase exponent marker | `0x45` |
| Lowercase exponent marker | `0x65` |

Classification can prevent literal syntax from being reached. For example, a leading minus whose entry has its low bit set can be skipped instead of recorded as a sign. A decimal point or exponent marker classified exactly `0x20` can be consumed by a digit loop before its literal role is tested.

For significand conversion, an accepted byte contributes its unsigned value minus 48: a value from −48 through 207. The table therefore determines whether nondecimal bytes reach numeric dependencies.

### Leading prefix

The routine skips consecutive bytes whose classification entries have the low bit set. It then consumes at most one literal plus or minus. Only a consumed minus at this position records final negativity.

Next, it consumes consecutive literal zero bytes. This happens whether or not a sign was present. These zeros:

- Do not require digit classification.
- Do not invoke arithmetic dependencies.
- Do not increase the significand digit counter.

Leading classification-based skipping is not resumed after a sign.

### Integer significand

The significand digit counter starts at zero and has 32-bit signed storage. There is no integer-phase digit limit.

At the start of every integer-loop test, the routine reloads a global two-word scale seed. This includes the terminating test. The seed from that terminating test supplies the initial fractional scale if a decimal point follows.

For each byte classified exactly `0x20`, the arithmetic calls occur in this order:

1. F-b3a54d881220 receives the unsigned byte value minus 48 and returns a two-word payload.
2. F-c4b34006a13c receives the current accumulator and a global two-word scaling operand.
3. F-1b22d7e17791 receives that result and the converted-byte payload.

The resulting payload replaces the accumulator. The scanning address advances by one byte, and the digit counter increases.

Multiplication by ten followed by addition is inferred intent, not an established contract of these dependencies. The global scaling operand is read at its uses; it is not established as a function-wide constant snapshot.

### Decimal point and fractional significand

After integer scanning stops, a literal decimal point is consumed if present. Neither preceding nor following digits are required.

If the digit counter is zero, literal zeros immediately after the point are consumed first. Each such zero invokes F-c4b34006a13c to update the fractional scale using the global scaling operand. These zeros do not increase the digit counter and do not require digit classification.

The routine then scans bytes classified exactly `0x20`.

When the signed digit counter is less than 18, an accepted byte causes:

1. Conversion through F-b3a54d881220.
2. Accumulator combination through F-c4b34006a13c.
3. Accumulator combination through F-1b22d7e17791.
4. Fractional-scale combination through F-c4b34006a13c.
5. An increment of the digit counter.

When the counter is at least 18, the accepted byte is consumed without those arithmetic calls and without a counter increment.

Thus, absent counter overflow:

- Eighteen counted integer digits leave no fractional accumulation capacity.
- Seventeen counted integer digits permit one accumulated fractional digit.
- Skipped leading integer zeros do not consume capacity.
- Initial literal fractional zeros can update the scale without consuming capacity.
- Excess fractional digits still contribute to the consumed prefix.

At each fractional-loop test, the accumulator and scale high words are captured before classification. These captured components supply the corresponding arithmetic operations. On the terminating test, the captured high words accompany the current low words in a call to F-596e18a33aec. Its result replaces the accumulator.

That final fractional-combination call occurs whenever a decimal point was consumed, including a bare point. No local rounding decision examines discarded fractional digits.

### Exponent scanning

After significand processing, the global two-word scale seed is reloaded, even if no exponent marker follows.

A literal `e` or `E` then starts exponent processing. The marker is consumed, followed by one optional literal plus or minus. No exponent digit is required. Neither the marker nor its sign is rolled back when digits are absent.

Consecutive bytes classified exactly `0x20` update a 32-bit exponent accumulator by multiplication by ten and addition of the unsigned byte value minus 48. There is no separate ASCII-range validation, saturation, or overflow status.

The exponent sign is recorded separately. A minus selects the negative-exponent application path; it does not negate the magnitude during scanning.

The accumulation expression mixes signed multiplication with unsigned byte-derived arithmetic and assignment back to signed 32-bit storage. Overflowing or out-of-range cases must not be modeled as unbounded nonnegative arithmetic.

### Exponent scale construction and application

The stored exponent controls these stages in order:

| Signed threshold | Scale update | Exponent reduction |
|---:|---|---:|
| At least 64 | F-c4b34006a13c with a dedicated global operand pair | 64 |
| At least 16 | F-c4b34006a13c with a second dedicated pair | 16 |
| At least 4 | F-c4b34006a13c with a third dedicated pair | 4 |
| At least 1 | F-c4b34006a13c with the significand scaling operand | 1 |

Each stage repeats until its threshold is no longer met, before proceeding to the next stage. Signed negative stored values satisfy none of these thresholds.

The operand pairs are inferred to represent decimal powers corresponding to the reductions. Their actual values are not supplied. The ordered dependency calls are established regardless of that interpretation.

For a nonnegative exponent sign, F-c4b34006a13c explicitly receives the significand accumulator and constructed exponent scale. Its result becomes the accumulator.

For a negative exponent sign, F-596e18a33aec supplies the replacement accumulator. Its effective operands on this path are not established by the supplied representation. Division by the exponent scale is inferred intent and remains **documented_only**.

An exponent marker with no digits still reaches exponent application using the seed-derived scale. It is not rejected as incomplete.

### Publication and return

After all scanning and arithmetic:

1. The accumulator high word is captured before either output store.
2. The low word is stored at the output address.
3. Exactly one high word is stored at the next 32-bit output position.
4. The consumed-address difference is returned.

The second store contains either the captured high word or that word XORed with `0x80000000`, depending on the recorded leading sign.

There is no preliminary unmodified high-word store and no subsequent in-place sign update. The high word is not reread from output storage after the low-word store.

XOR toggles bit 31 rather than setting it. If that bit was already set, a leading minus clears it. Binary64 sign inversion is only a conditional numeric interpretation.

## Acceptance examples

### Complete baseline classification profile

Except for explicitly identified classification overrides, every example below assumes this complete, stable table profile:

| Input byte | Classification entry |
|---|---:|
| ASCII `0` through `9` | `0x20` |
| ASCII space, `0x20` | `0x01` |
| Every other byte | `0x00` |

In particular, `x`, `X`, `t`, all other letters including `e` and `E`, decimal points, signs, and punctuation are **not** digit-classified. Signs, decimal points, and exponent markers also do not qualify for leading skipping. Consequently:

- Decimal points terminate significand digit scanning and can reach literal point recognition.
- Exponent markers terminate significand digit scanning and can reach literal exponent recognition.
- Letter and punctuation terminators cannot be accidentally accumulated as digits.
- Initial syntax bytes survive leading skipping.

Each displayed input is followed by an accessible zero byte. Under this profile, that byte is a stopping byte, not a digit or skipped leading byte. Relevant memory remains stable, dependencies return normally, and address differences are representable. Numerical payload values remain conditional on the missing arithmetic contracts.

Additional boundary cases under the same profile:

- **Fractional capacity exhausted:** `123456789012345678.9!` consumes 20 bytes. The fractional `9` is consumed without numeric accumulation.
- **One position remaining:** `12345678901234567.89!` accumulates `8`, consumes `9` without numeric updates, and stops before `!`.
- **Literal fractional zeros:** `0.0001!` skips the integer zero without counting it, performs three fractional-scale updates for the following zeros, then accumulates `1`.
- **Exponent ordering:** `1e85!` performs one 64-unit update, one 16-unit update, one 4-unit update, and one 1-unit update, followed by exponent application.

### Classification-sensitive cases

These cases override only the specified baseline table entry:

- With the entry for `x` changed to `0x20`, `123x!` consumes four bytes. The `x` contributes 120 − 48 = 72 through F-b3a54d881220. A three-byte expectation would be incorrect.
- With the entry for `e` changed to `0x20`, `1e2!` consumes its first three bytes as integer significand digits. No exponent-processing path is entered.
- With the entry for the point changed to `0x20`, `1.2!` consumes the point as a significand digit with contribution −2. No fractional-combination call is required.
- With the entry for minus changed to `0x01`, `-1!` skips the minus during leading skipping. It does not record a negative leading sign.
- With the entry for `x` changed to `0x21`, `x1!` skips `x` at entry, whereas `1x!` stops before `x`.

### Output transformation

If the final accumulator has low word `0x12345678` and high word `0x01234567`, a recorded leading minus produces stores of `0x12345678` and then `0x81234567`.

If the high word instead is `0x81234567`, the second store is `0x01234567`. These are conditional word-transformation examples, not established numeric conversion results.
