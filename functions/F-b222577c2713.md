# F-b222577c2713

## Purpose

F-b222577c2713 selects an object through an indexed table and, for either of two recognized requests, writes a 32-bit control field within that object. One request returns immediately after writing zero. The other writes one, performs a bounded sequence of readback checks, and returns a status determined by a separate final read.

**Established behavior:** the function manipulates the field at object-relative byte offset `0x400`. It returns one of three 8-bit status values: `0`, `1`, or `3`.

**Inferred intent:** the field may represent an enabled/disabled state, and the readback sequence may be intended to confirm that a request has taken effect. Neither interpretation establishes what the field controls, whether another actor changes it, or whether a successful return indicates any activity beyond the observed field value.

This contract describes normal completion under valid memory-access preconditions. It does not establish fault recovery, thread safety, device behavior, or progress by another execution context.

## Interface

### Inputs

The function has two explicit inputs:

| Input | Width and interpretation | Role |
|---|---|---|
| Entry index | Signed 16-bit integer | Selects an entry in a table using a byte stride of `0x18c`, or 396 bytes. |
| Request | Signed 32-bit integer | Selects the behavior: `0`, `1`, or any other value. |

The interface does not expose a table length, object size, timeout, allocator, callback, or output buffer.

The index is used as a signed value. Negative indices are not rejected or converted into unsigned indices by the displayed behavior. No bounds check is present.

### Implicit inputs and layout

The function uses a globally supplied table base. For the selected entry:

- The entry address is the table base plus the signed index multiplied by 396.
- The first 32-bit word at that entry supplies the object address.
- Recognized requests access a 32-bit field at byte offset `0x400`, or 1024 bytes, from that object address.

Only the first word of the selected entry is shown as being used. The 396-byte stride does not establish the meaning of any other entry bytes.

The object address is loaded before the request is classified. Consequently, even an unsupported request requires access to the selected table entry, although it does not require access to the object's control field.

### Output

The result is an 8-bit value:

| Result | Established meaning |
|---|---|
| `0` | Request zero completed its write, or request one's final field read equaled one. |
| `1` | The request was neither zero nor one. |
| `3` | Request one's final field read did not equal one. |

These are exact values, not a Boolean result. In particular, `0` does not have the same evidentiary meaning for both recognized requests: request zero has no readback check.

### Preconditions

For defined, normally completing execution:

- The table-base source and selected entry must be readable.
- Address calculation must resolve to the intended entry within the execution environment's address model.
- For requests zero and one, the loaded object address must permit a 32-bit write at offset `0x400`.
- For request one, that field must also permit the subsequent 32-bit reads.
- Memory alignment and access rules must be satisfied by the relevant addresses.

The function does not verify these conditions. A null, stale, inaccessible, misaligned, or otherwise unsuitable address is not converted into one of the documented return statuses.

## Behavior

### Common entry resolution

Before choosing a request branch, the function obtains the object address from the indexed table entry.

The index is multiplied by 396. Across the signed 16-bit input range, this product ranges from −12,976,128 through 12,975,732 and fits within a signed 32-bit integer. That fact does not prove that adding the displacement to the table base produces a valid address. The applicable address-arithmetic and overflow rules remain an execution-environment prerequisite.

The loaded object address is retained for the rest of the invocation. The displayed behavior does not reload the table entry during polling. If another actor subsequently changes the table base or selected entry, there is no explicit re-resolution of the target object.

### Request zero

For a request equal to zero:

1. The function writes the full 32-bit value zero to the selected object's field at offset `0x400`.
2. It returns the 8-bit value zero.

There is no field read before or after this write. The previous field value is not inspected, preserved, or returned.

A zero return therefore establishes only that execution reached the return after the write. It does not establish that the field still contains zero when the caller receives the result, that another actor accepted the value, or that any related state changed.

### Request one

For a request equal to one, the function first writes the full 32-bit value one to the selected field.

It then performs a bounded readback loop:

- Each iteration reads the field and compares the full 32-bit value with one.
- A read equal to one ends the loop immediately.
- A read not equal to one consumes one position in a fixed countdown.
- If no loop read equals one, the loop ends after eleven loop reads.

The maximum is **eleven**, not ten. The countdown starts at ten, and the loop continues through the iteration whose countdown value on entry is zero.

After the loop ends, the function always performs one additional field read. This final read alone determines the return value:

- Final value equal to one: return `0`.
- Final value not equal to one: return `3`.

Thus, on normally completing request-one paths, the displayed behavior contains:

- Exactly one 32-bit field write.
- Between one and eleven loop reads.
- Exactly one additional final read.
- Between two and twelve field reads in total.

The final read is not reused from the loop condition. This distinction matters if the field can change between accesses:

- A loop read equal to one does not guarantee a zero return.
- Exhausting all eleven loop reads without observing one does not guarantee a return of three.

There is no delay, sleep, scheduler yield, retry of the write, or additional request submission in the displayed sequence. The bound limits the number of loop reads, not elapsed time.

### Other requests

For every request other than zero or one, the function returns the 8-bit value one.

It does not read or write the object field on this branch. However, the common table-entry read has already occurred. An unsupported request is therefore not a safe mechanism for probing an invalid index or bypassing an invalid table entry.

The function does not distinguish among unsupported negative values, unsupported positive values, or other 32-bit bit patterns interpreted as signed request values.

## Side effects

### Memory-access ordering

At the level of the displayed operations, the relevant ordering is:

| Request | Ordered accesses |
|---|---|
| Zero | Resolve table base; read selected entry's object address; write field as zero. |
| One | Resolve table base; read selected entry's object address; write field as one; perform loop reads; perform final read. |
| Other | Resolve table base; read selected entry's object address. |

The field operations are full 32-bit accesses. There is no displayed byte-sized update, bit mask, read-modify-write operation, or preservation of unrelated bits within that word.

If the table entry and object field happen to alias, the entry read still precedes the field write. No non-aliasing guarantee is established.

### State and ownership

The only explicit memory write is to the selected object's control field for a recognized request.

The function does not explicitly:

- Allocate, free, retain, or release memory.
- Replace the table base or table entry.
- Transfer ownership of the selected object.
- Restore the previous field value.
- Undo a write when readback fails.
- Modify another object field.

A return of three leaves the request-one write unrolled back. The final field contents are whatever the memory environment provides; the function performs no subsequent corrective write.

No callee ownership or global-preservation assumptions are needed because the supplied function body contains no calls.

### Concurrency and external effects

The repeated reads may be intended to observe externally changing state, but the supplied representation does not establish volatile access, atomic access, memory barriers, cache policy, or synchronization.

Accordingly, the access sequence above is a description of the displayed operations, not a guarantee of physical bus transactions, cross-thread visibility, or device ordering.

Any special effects of reading or writing memory-mapped storage are unknown. The function itself contains no explicit mechanism for handling such effects.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence. They are not reports of executed tests. Counts refer to the displayed field-access sequence.

1. **Immediate zero write.**  
   Given a valid selected entry and writable field, request zero writes the 32-bit value zero and returns `0`. There are no field readback operations, regardless of the initial field value.

2. **Ordinary successful readback.**  
   Given request one and a field that retains the written value, the function writes one, observes one on the first loop read, observes one on the final read, and returns `0`. There are two field reads.

3. **Persistent mismatch.**  
   Given request one, if all eleven loop reads and the final read produce values other than one, the function returns `3`. It performs twelve field reads and does not repeat or reverse its initial write.

4. **Success appearing only at the final read.**  
   If all eleven loop reads differ from one but the separate final read equals one, the return is `0`. Countdown exhaustion does not override the final comparison.

5. **Success disappearing before the final read.**  
   If the first loop read equals one but the final read is zero, the return is `3`. Early loop termination does not latch success.

6. **Late loop success.**  
   If the first ten loop reads differ from one and the eleventh equals one, the loop terminates at that point. The twelfth total field read remains necessary and determines the result.

7. **Exact-value comparison.**  
   If the final field value is two, negative one, or any other 32-bit value unequal to one, request one returns `3`. A merely nonzero value is insufficient.

8. **Unsupported request with a readable entry.**  
   Given a readable selected entry, request two returns `1` without dereferencing the object field. The loaded object address need not identify accessible object storage for that branch.

9. **Negative index with suitable surrounding storage.**  
   Index negative one selects an entry 396 bytes before the table base. It is not rejected. Normal completion still depends on the selected address and any required object-field accesses being valid.

10. **Invalid entry access.**  
    An unsupported request does not avoid the initial entry read. If that read cannot complete, no documented normal-return status is established.
