# F-21c22c475387

## Purpose

F-21c22c475387 conditionally retrieves a 32-bit value from a collection-like structure associated with a caller-supplied object.

Its observable outcomes are asymmetric:

- An index rejected by the initial validation produces a 32-bit zero output and a zero return value.
- An index accepted by the initial validation but rejected by a later validation produces return bits `0xFFFFFFCE`, without a direct output write by this function.
- An index accepted by both validations produces the selected 32-bit value and a zero return value.

The two validations involve separate calls to F-255ea5022a24. They must not be treated as one check or assumed to return the same result. The associated structure pointer is also read twice on the path that reaches the second validation, allowing the two stages to use different pointer values.

This contract describes the supplied static representation. No runtime tests have been performed.

## Interface

### Inputs

The function has three inputs:

| Input | Represented width and role |
|---|---|
| Object address | A 32-bit integer used as the base address for an object field at byte offset `0x40`. |
| Index | A 32-bit unsigned quantity, additionally examined through a signed 32-bit interpretation. |
| Output address | An address at which the function may store one 32-bit value. |

The signed interpretation of the index is nonnegative exactly when its bit pattern lies between `0x00000000` and `0x7FFFFFFF`, inclusive. Index values from `0x80000000` through `0xFFFFFFFF` are rejected before the object is accessed or the dependency is called.

No null-pointer checks, alignment checks, allocation-size checks, or memory-access recovery are visible.

### Output and return representation

The output location is written with exactly one 32-bit value on either successful return path:

- Zero when the initial validation rejects the index.
- The selected record value when both validations accept the index.

The return value is a 32-bit quantity:

| Return bits | Meaning established by the supplied representation |
|---|---|
| `0x00000000` | Initial rejection with zero output, or successful retrieval. |
| `0xFFFFFFCE` | Initial acceptance followed by rejection at the later validation. |

`0xFFFFFFCE` has signed 32-bit interpretation −50. Its association with a named error category is unknown.

There is no separate return code distinguishing an initial rejection from retrieval of a stored zero value.

### Required memory layout

The following offsets and widths are established:

| Location | Use |
|---|---|
| Object address plus `0x40` | Read as a 32-bit address of an associated structure. |
| Associated structure address plus `0xE58` | Its address is supplied to the first dependency call. On the retrieval path, its contents are later read as a 32-bit record-storage address. |
| Record-storage address plus index × `0xC` plus `0x8` | Read as the selected 32-bit output value. |

The record addressing implies a 12-byte stride and a selected field at byte offset 8 within each indexed record. It does not establish the meanings of the other eight bytes, allocation ownership, or the complete representation of the collection-like structure.

The first dependency call receives the address of the associated structure’s `0xE58` field, not the record-storage address contained in that field.

### Preconditions

Preconditions depend on the path actually taken:

- If the index’s signed interpretation is negative, only the output location must be writable for the explicit operations shown.
- If that interpretation is nonnegative, the object’s field at offset `0x40` must be readable, and the resulting address calculation must be suitable for the first dependency call.
- If the first dependency result accepts the index, the object’s field at offset `0x40` must be readable again.
- If the later validation also accepts the index, the saved associated structure’s field at offset `0xE58` and the selected record field must be readable, and the output location must be writable.

These are requirements for ordinary completion, not validations performed by the function. Dependency-specific preconditions remain unknown.

## Behavior

### Initial eligibility and validation

The function first examines the index through its signed 32-bit interpretation.

If that interpretation is negative:

- It does not explicitly read the object.
- It does not call F-255ea5022a24.
- It writes a 32-bit zero to the output location.
- It returns zero.

For an index with nonnegative signed interpretation, the function:

1. Reads the 32-bit associated structure address from the object at offset `0x40`.
2. Forms the address at offset `0xE58` within that structure.
3. Calls F-255ea5022a24 with that computed address as the one explicitly supplied argument.
4. Uses the returned value as a 32-bit unsigned bound.

The index is accepted at this stage only if it is strictly less than that bound under unsigned comparison. Equality is rejection.

On rejection, the function writes a 32-bit zero to the output location and returns zero. It does not perform the second object-field read or the second dependency call.

A dependency result of zero therefore rejects every index that reaches this comparison.

### Reload before the later validation

After initial acceptance, the function reads the object’s field at offset `0x40` again and saves the newly read associated structure address.

This second read occurs after the first dependency call. Consequently, if that call changes the object’s field, the saved address can differ from the address used to prepare the first call.

The supplied representation includes another signed-nonnegative test of the same index. Because the index is an unchanged by-value input and reaching this point already required that condition, this repeated test introduces no additional reachable rejection case under ordinary execution of the represented function.

The function then calls F-255ea5022a24 again. This call has no explicit argument in the supplied representation.

The second call must not be specified as receiving either the earlier field address or the newly saved structure address. Its actual interface, any implicit context, and its relationship to the first call are unresolved.

### Later validation and retrieval

The second dependency result is also used as a 32-bit unsigned bound. Retrieval requires the index to be strictly less than this result.

If the index is equal to or greater than the second bound, the function returns `0xFFFFFFCE`. There is no explicit output write on this path.

If the index is less than the second bound:

- The function reads the 32-bit record-storage address from offset `0xE58` of the associated structure saved before the second call.
- It locates the selected field using a 12-byte record stride and an additional offset of 8 bytes.
- It reads the selected 32-bit value.
- It writes that value to the output location.
- It returns zero.

The function does not reload the object’s field at offset `0x40` after the second dependency call. A change to that object field during the second call does not replace the saved associated structure address.

However, the record-storage address is read after the second call. Changes by that call to the saved structure’s field at offset `0xE58` can therefore affect the eventual read.

### Integer arithmetic and limits

Both bounds comparisons are unsigned 32-bit comparisons. The signed index test is an additional restriction; a large unsigned bound does not admit an index whose high bit is set.

The indexed byte displacement uses the index multiplied by 12. In the represented 32-bit unsigned arithmetic, this multiplication wraps modulo \(2^{32}\). The function contains no explicit overflow check.

The largest index for which multiplication by 12 alone does not exceed `0xFFFFFFFF` is `0x15555555`. Adding the 8-byte field offset, and adding the record-storage base address, can introduce further address overflow.

Accordingly, successful comparisons do not independently establish memory safety. The bounds must be consistent with the actual allocation, and the target execution environment must support the resulting addresses. Exact fault behavior and the treatment of invalid address arithmetic are not established by the supplied representation.

## Side effects

### Explicit memory access order

On the complete retrieval path, the relevant order is:

1. Read the object’s associated structure address.
2. Call F-255ea5022a24 using an address derived from that read.
3. Compare the index with the first result.
4. Read the object’s associated structure address again.
5. Call F-255ea5022a24 with no explicit argument shown.
6. Compare the index with the second result.
7. Read the record-storage address from the saved structure.
8. Read the selected 32-bit record field.
9. Write the 32-bit output value.

A failing comparison stops the later explicit accesses as described above. This is the order established by the representation, not a claim about processor-level bus transactions or concurrent-memory guarantees.

### Direct writes and dependency effects

The only explicit write performed by F-21c22c475387 is to the output location. It directly performs no allocation, release, or ownership transfer.

The dependencies’ effects are unknown. In particular:

- A dependency may change reachable memory or global state.
- The absence of an explicit output write on the `0xFFFFFFCE` path does not guarantee that the output’s value is unchanged if a dependency can reach it.
- A dependency may invalidate memory that a later explicit read requires.
- No assumption is justified that either dependency call preserves a collection, its backing storage, or a global context.

No output ownership is transferred merely because a 32-bit value is copied. The selected value’s interpretation—integer, address, handle, or other bit pattern—is unknown.

### Aliasing

No non-aliasing requirement or check is shown. The output location may overlap an object field, the saved structure, or record storage, provided the accesses remain valid.

On retrieval, the selected value is read before the explicit output store. If source and output are the same 32-bit location, the function reads and then writes that value.

If the output aliases the object’s field at offset `0x40`, the final store can replace that field. No subsequent explicit object read occurs. Similar aliasing can overwrite collection metadata or record data; the representation does not prevent it.

## Dependencies

## Acceptance examples

These are conditional consequences of the static representation, not executed tests. Each assumes that all reached dependency calls complete and all reached memory accesses are valid.

### High-bit index

Given index `0xFFFFFFFF`:

- No dependency call occurs.
- No explicit object read occurs.
- The output receives zero.
- The return value is zero.

An invalid object address does not itself prevent this path, because the object is not accessed. The output must still be writable.

### First-bound equality

Given index 3 and first dependency result 3:

- The index is rejected because the comparison is strict.
- The second dependency call does not occur.
- The output receives zero.
- The return value is zero.

### Later-bound equality

Given index 3, first result 4, and second result 3:

- The first validation accepts.
- The object’s associated structure address is read again.
- The later validation rejects.
- The return bits are `0xFFFFFFCE`.
- The function performs no explicit output store.

If dependencies leave an existing output sentinel untouched, that sentinel remains. Without that condition, preservation is not guaranteed.

### Successful retrieval

Given index 2, first result 5, and second result 3:

- Both validations accept.
- The selected field is 32 bytes from the record-storage base: two 12-byte strides plus 8 bytes.
- If that field contains `0x89ABCDEF`, the output receives exactly those bits.
- The return value is zero.

### Structure change during the first call

Suppose the object initially refers to structure A, and the first dependency call changes it to structure B while returning an accepting bound.

The first call receives an address derived from A. The second object read saves B. If the later validation accepts, retrieval uses B’s field at offset `0xE58`, as read after the second call.

### Structure change during the second call

Suppose the saved associated structure is B, and the second dependency call changes the object to refer to C.

If validation accepts, retrieval still uses B. If that same dependency changes B’s record-storage field, the subsequent read observes that field’s value at the time of the read, subject to the target memory model.

### Unsigned bound versus signed eligibility

Given index `0x80000000` and any possible dependency results, the index is rejected before any call occurs.

Given index `0x7FFFFFFF`, a returned bound of `0x80000000` accepts that comparison. Retrieval still requires the other validation and valid address arithmetic; the comparison alone does not make the large indexed access safe.
