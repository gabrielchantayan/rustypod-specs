# F-7b9683882e71

## Purpose

F-7b9683882e71 creates and conditionally initializes a dynamically obtained object, then publishes either its address or a null address through a caller-supplied output location.

The function requests 116 bytes of storage and invokes an initialization dependency on an address 24 bytes into that storage. A zero initialization result enables three additional four-byte field writes. A nonzero initialization result causes the allocation address to be passed to a cleanup dependency, after which a null address is published.

The apparent intent is to construct an object containing an embedded component and a small header. That interpretation is inferred. The established behavior is the allocation request, dependency calls, conditional writes, publication, and status propagation described below.

| Output location | An address at which the function publishes the resulting object address or null. A null output-location address is explicitly rejected. Any nonnull address must support the final output store for execution to complete normally. |

The recovered interface uses four-byte object words and a four-byte output slot carrying an address. This contract describes that recovered 32-bit address representation; it does not establish portability to an ABI with wider pointers.

The caller’s existing output-slot contents are not read by the function. In particular, an existing object address in that slot is not passed to cleanup before replacement.

## Behavior

### 1. Validate the output-location address

If the output-location address is null, the function returns −50 immediately.

On this path, the function makes none of the three dependency calls, performs no output store, and does not perform the success-path global read or object-field writes.

This check concerns the address of the output slot, not the address currently stored in it.

### 2. Request storage

For a nonnull output-location address, the function calls F-858f5b8d5984 with the size value 116.

No separate clearing operation is shown. The function does not itself establish the contents of the returned storage before invoking the initializer.

If this dependency returns null:

- The initializer is not called.
- The cleanup dependency is not called.
- The function writes a null address to the output slot.
- The function returns −108.

The output is therefore explicitly replaced with null on allocation failure, assuming the output store completes.

### 3. Invoke initialization

If the allocation result is nonnull, the function calls F-891c06385ffa with three arguments, in this order:

1. The allocation address advanced by 24 bytes.
2. Zero.
3. A reference to statically addressed data.

The supplied source associates the third argument with a text-like symbol, but does not provide its bytes or the dependency’s parameter contract. Its exact content, encoding, mutability, and purpose remain unknown.

Initialization occurs before the function’s three explicit object-field writes. Consequently, those fields are not established by this function before the initializer runs.

### 4. Handle successful initialization

If F-891c06385ffa returns zero, the function performs these direct accesses in order:

1. Reads a four-byte value from a global location and writes it at allocation offset 0.
2. Writes the four-byte value 1 at allocation offset 4.
3. Writes the payload value at allocation offset 12.
4. Writes the allocation address to the caller’s output slot.
5. Returns zero.

The global value is read after the initializer returns. It is not captured before allocation or initialization. If either dependency changes that global location, the later read observes the value then present, subject to the execution environment’s memory semantics.

The meanings of the global-derived field and the constant-one field are not established. A dispatch header and an initial reference count are possible interpretations, not contractual facts.

### 5. Handle unsuccessful initialization

If F-891c06385ffa returns any nonzero status:

1. The function calls F-1137792fba7d with the allocation base address.
2. It selects null as the address to publish.
3. It writes null to the output slot.
4. It returns the initializer’s nonzero status.

The cleanup argument is the allocation base, not the address at offset 24.

The function performs none of its three success-path object-field writes on this branch. Any object changes already made by allocation or initialization are dependency effects.

The cleanup result, if any, does not determine the function’s returned status. Normal completion of this path nevertheless requires the cleanup call to return normally.

## Side effects

### Publication and output replacement

On every normal-return path with a nonnull output-location address, the function performs one direct output-slot store:

- Allocation address after successful initialization.
- Null after allocation failure or initialization failure.

The function does not proactively clear the output slot before invoking dependencies. Its direct publication occurs only after the applicable allocation, initialization, cleanup, and field-write operations.

This ordering does not guarantee that the output slot remains unchanged during those calls. Dependency effects and aliasing are not characterized.

Overwriting a preexisting output value does not itself dispose of the object previously referenced there. Callers must account for any prior ownership independently.

### Allocation and ownership

On successful initialization, F-7b9683882e71 does not call F-1137792fba7d before publishing the allocation address.

On initialization failure, it passes the allocation address to F-1137792fba7d and does not publish that address.

These observations suggest a creation-and-handoff convention, but they do not establish:

- That F-858f5b8d5984 uses a particular allocator or returns uniquely owned storage.
- That F-891c06385ffa retains no references or acquires no additional resources.
- That F-1137792fba7d releases all storage or nested resources.
- Which operation a successful caller must eventually use for disposal.

Those ownership rules require dependency contracts.

### Aliasing and access failures

No overlap checks are present. If the output slot aliases the allocated object, its final store occurs after the success-path field writes and may overwrite one of them. The function provides no invariant protecting the header from such overlap.

A nonnull but unwritable output location is not converted into a defined status error. The final store may fail according to the execution environment. There is no shown recovery or compensating cleanup for a publication failure.

Likewise, the function assumes that returned storage and all dependency-required addresses are valid for the operations performed. Faults, nonlocal exits, or abnormal dependency termination are not mapped to the documented return values.

### Global state

The function directly reads one global four-byte value on the successful initialization path. No direct global write is shown.

This is not a guarantee that globals remain unchanged: all three dependencies may have effects not visible in the supplied body. No synchronization or concurrency guarantees are established.
