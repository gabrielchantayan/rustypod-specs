# F-600a7e8b5f6d

## Purpose

F-600a7e8b5f6d is a four-input routine that returns a 64-bit value. Its visible structure initializes two 64-bit working values from four shared 32-bit words, invokes a predicate-like dependency, and conditionally repeats two transformations before checking again.

The established behavior is an ordered call-and-update loop. The available evidence does **not** establish that the transformations are addition, that the working values represent integers rather than encoded values, or that the predicate performs a particular comparison.

The loop decision is especially important: it uses a carry-state indication whose connection to the preceding dependency call is not explicitly represented in the supplied material. Consequently, termination cannot be specified as an ordinary comparison of the visible arguments.

An inferred intent is repeated accumulation while advancing a candidate toward some boundary. That interpretation is not part of the established contract.

## Behavior

### Initialization

The routine first constructs the initial 64-bit candidate from the candidate high and low words. It then constructs the initial 64-bit accumulator from the accumulator high and low words.

The order between these two constructions is visible: candidate construction precedes accumulator construction. The evidence does not establish an observable order between the two individual word reads within either construction. It also does not establish an atomic 64-bit snapshot.

Both initial constructions occur before the first dependency call.

For each constructed value, the high word supplies bits 32–63 and the low word supplies bits 0–31. This is bit assembly, not an established arithmetic addition.

### Check phase

Before each check call, the routine extracts the current candidate’s upper 32 bits. It calls F-c6bfc9d0fb36 with five 32-bit arguments in this order:

1. The first input.
2. The second input.
3. The current candidate’s low 32 bits.
4. The current candidate’s high 32 bits.
5. The fourth input.

The third input is absent from this argument list.

The candidate halves are passed as 32-bit quantities. Some source-level expressions use signed 32-bit forms, but the visible use does not establish a signed numeric domain. In particular, a high-bit-set half is not evidence that the complete candidate is negative.

The call occurs before every loop decision, including the decision that exits the routine. There is therefore at least one check call on every normal execution reaching the loop.

### Exit decision

After the check call, the routine tests a carry-state indication:

- A set indication exits the loop.
- A clear indication enters the update phase.

There is no visible use of an ordinary return value from F-c6bfc9d0fb36 to make this decision.

The supplied representation exposes this indication without an explicit assignment tying it to the call. The contract therefore preserves the branch direction but leaves the origin of the tested state unresolved. It is not established whether F-c6bfc9d0fb36 produces the relevant processor flag, whether some other instruction determines it, or whether it represents state entering the routine.

No threshold relation, equality condition, signedness, or inclusive/exclusive boundary can be inferred reliably from this branch alone.

### Update phase

When the tested indication is clear, two calls occur in a fixed sequence.

First, F-1b22d7e17791 receives four 32-bit arguments:

1. The current accumulator’s low word.
2. The current accumulator’s high word.
3. A read of the shared accumulator low word.
4. A read of the shared accumulator high word.

Its complete 64-bit result replaces the accumulator.

Second, F-c4b34006a13c receives four 32-bit arguments:

1. The current candidate’s low word.
2. The candidate high word extracted before the preceding check call.
3. A read of the shared candidate low word.
4. A read of the shared candidate high word.

Its complete 64-bit result replaces the candidate.

The next check uses this replacement candidate.

The shared operands used during updates are not established as cached copies of the initialization words. They are read again for the corresponding calls. A dependency that changes shared state can therefore affect subsequent argument values.

In particular:

- Changes made by the check dependency can affect the accumulator transformation’s shared-word operands.
- Changes made by the accumulator transformation can affect the candidate transformation’s shared-word operands.
- Changes made by the candidate transformation can affect later iterations’ shared-word operands.

The candidate halves passed to the candidate transformation remain derived from the working candidate for that iteration, including the high half extracted before the check. They are distinct from the shared candidate-word operands read for that transformation.

Within each pair of shared-word argument reads, evaluation order and atomicity are not established.

### Return and termination

When a check’s tested indication is set, the routine returns the current accumulator without invoking either transformation for that check.

For a normal return after exactly \(n\) completed update phases:

- F-c6bfc9d0fb36 has been called \(n+1\) times.
- F-1b22d7e17791 has been called \(n\) times.
- F-c4b34006a13c has been called \(n\) times.
- The accumulator transformation always precedes the candidate transformation within an update phase.

No iteration limit, timeout, cancellation check, or fallback return is visible. Normal termination requires that the dependencies return and that a check eventually produces a set tested indication. Neither property is established for arbitrary inputs.
