# F-4fa4ec01302c

## Purpose

F-4fa4ec01302c selects one 20-byte record from a reusable-record list or from a block-backed sequential allocation area, then clears selected fields of that record.

The established behavior is a state mutation, not a value-returning allocation interface: the function has no explicit return value and does not explicitly publish the selected record through an output parameter. Selection is observable through changes to the supplied state, writes to record storage, and any dependency calls.

A pool-like record allocator is the inferred intent. The source establishes the selection, growth, linking, and initialization operations, but does not establish the surrounding ownership protocol or how a caller subsequently identifies or uses the selected record.

## Interface

### Argument and result

The function accepts one pointer to mutable state. The represented interface uses 32-bit integers and 32-bit pointer values stored in integer-sized fields.

The state contains at least four consecutive 4-byte fields:

| Byte offset | Contract name | Observed role |
|---|---|---|
| 0 | Block head | Pointer to the most recently linked block descriptor, or zero. |
| 4 | Reuse head | Pointer to the next reusable record, or zero. |
| 8 | Sequential cursor | Pointer to the next sequential record position. |
| 12 | Sequential end | Boundary compared with the sequential cursor to decide whether another block is needed. |

The function returns without an explicit result. No selected-record pointer is assigned to a separate caller-provided output location.

### Block descriptor layout

A block descriptor occupies 12 bytes:

| Byte offset | Width | Observed role |
|---|---:|---|
| 0 | 4 bytes | Link to the preceding block descriptor. |
| 4 | 4 bytes | Unsigned 32-bit record capacity. |
| 8 | 4 bytes | Pointer to the block’s record storage. |

When growth is required, a descriptor and its record storage are obtained through two separate calls to F-871e64ddc6de.

### Record layout relevant to this function

Each sequential record occupies 20 bytes. Only the following record locations are accessed:

| Byte offset | Width | Access |
|---|---:|---|
| 0 | 1 byte | Set to zero during initialization. |
| 4 | 4 bytes | Set to zero during initialization. |
| 8 | 4 bytes | Set to zero during initialization. |
| 12 | 4 bytes | Read as a reuse-list link when selecting a reusable record; subsequently set to zero. |

Bytes 1–3 and 16–19 are not explicitly initialized by this function. A successful call therefore does not establish that the entire record is zero-filled.

### Preconditions for ordinary completion

The supplied state must support the reads and writes required by the selected branch. A nonzero reuse head must identify storage supporting a 4-byte link read at offset 12 and all initialization writes.

When selecting from the sequential area without growth, the cursor must identify a writable record. The function checks only whether the cursor equals the end; it does not verify ordering, alignment, remaining byte count, or membership in an allocated block.

When growth uses an existing block head, that head must support a 4-byte capacity read at offset 4.

On the growth path, the dependency results must provide usable descriptor and record storage for subsequent accesses. The function does not validate either result. Appropriate alignment and address validity are required by the execution environment; the source supplies no mechanism for establishing them.

Distinct, nonoverlapping state, descriptors, and record storage are sufficient for the ordinary structural interpretation described below. The function performs no overlap checks. If these objects alias, earlier writes can affect later reads, and the ordered accesses—not an abstract independent-object model—determine the result.

## Behavior

### Selection priority

The reuse head is read first.

If it is nonzero, its record is selected immediately. The sequential cursor, sequential end, and block capacity do not participate in that selection. No dependency call is made on this branch.

If the reuse head is zero, the sequential cursor becomes the candidate record address. That address is compared for equality with the sequential end:

- Unequal addresses select the current cursor without allocating another block.
- Equal addresses trigger block growth before a record is selected.

There is no relational bounds check. A cursor numerically above the end, below valid storage, or too close to the end still follows the unequal-address branch.

### Reusable-record branch

The 4-byte value at offset 12 of the selected record is read and assigned to the state’s reuse head.

This removes the selected record from the front of the represented reuse chain before record initialization occurs. The value read is not validated as a pointer. A zero link leaves the reuse head empty; any other bit pattern becomes the new head.

Under nonoverlapping storage and absent external interference, the block head, sequential cursor, and sequential end are unchanged on this branch.

The selected record then receives the common initialization writes described below.

### Sequential selection without growth

If the reuse head is zero and the cursor differs from the end, the current cursor is selected.

Before initializing the record, the state’s sequential cursor is advanced by 20 bytes from the selected address. The end and block head are not explicitly changed.

The function does not check whether that increment reaches, crosses, or wraps past the represented end. Valid pool state must provide the required space independently.

### Capacity calculation on growth

Growth occurs only when the reuse head is zero and the cursor equals the end.

If the block head is zero, the new capacity is 32 records.

Otherwise, the function reads the existing head descriptor’s unsigned 32-bit capacity. Two unsigned 32-bit candidate capacities are formed:

- The old capacity plus 32.
- The old capacity plus its logical right shift by one bit plus its logical right shift by three bits.

All additions use 32-bit unsigned arithmetic. Overflow wraps modulo \(2^{32}\). The comparison is unsigned and is applied to the resulting wrapped values.

The new capacity is the larger of the two wrapped candidates. Equality selects the second candidate, with no difference in the resulting capacity.

For values that do not overflow, the second candidate approximates 1.625 times the old capacity, with each shifted contribution truncated independently. This growth interpretation does not imply overflow protection: for large capacities, wrapping can produce a capacity smaller than the old capacity.

### Allocation and publication on growth

After computing the capacity, the function performs the following dependency calls in order:

1. F-871e64ddc6de with arguments 12 and zero.
2. F-871e64ddc6de with arguments equal to the new capacity multiplied by 20, and zero.

The multiplication is performed at 32-bit unsigned width. The second request can therefore wrap to a smaller size, including zero. No overflow check precedes the call.

The first result is used as the descriptor address. The second result is used as the record-storage address. After both calls return, the function performs these operations in order:

1. Stores the record-storage address in the descriptor at offset 8.
2. Reads the state’s then-current block head and stores it as the descriptor’s preceding-block link.
3. Stores the computed capacity in the descriptor at offset 4.
4. Publishes the descriptor address as the state’s block head.
5. Reads the descriptor’s record-storage field.
6. Sets the state’s sequential end to that address plus the 32-bit product of capacity and 20.
7. Sets the state’s sequential cursor to 20 bytes after the selected record address.

The record selected by this branch is the start of the new record-storage area, as obtained through the descriptor read.

The timing of the old-head read matters. The previous block link is taken from state after both dependency calls, not from a saved pre-call head. Neither dependency call may be assumed to preserve the supplied state, globals, or related memory.

For ordinary disjoint allocations and unchanged state during the calls, the new descriptor links to the former head, the end marks the end of the new storage, and the cursor points to its second record position.

### Common record initialization

After the branch-specific state changes, the selected record receives these writes in this order:

1. A 4-byte zero at offset 4.
2. A 4-byte zero at offset 8.
3. A 4-byte zero at offset 12.
4. A 1-byte zero at offset 0.

The function then returns.

These are not a whole-record clear. In particular, the final byte write does not establish zero values for the other three bytes of a 4-byte word beginning at offset 0.

The ordering also means that the reuse-head update or cursor advancement precedes initialization. No rollback is present if an access fails partway through the operation.

## Side effects

The function may mutate:

- The state’s reuse head when selecting a reusable record.
- The state’s sequential cursor when selecting a sequential record.
- The state’s block head and sequential end when growing.
- All three fields of a newly obtained block descriptor.
- Thirteen bytes of the selected record, through three 4-byte stores and one 1-byte store.

No other writes are explicit in this function. F-871e64ddc6de may have additional effects that are not specified by the available evidence.

The function does not explicitly release records, descriptors, or storage. Linking a new descriptor into state establishes reachability, but does not establish a complete ownership or destruction policy. There is no basis for assigning eventual release responsibility to this function, its caller, or the dependency.

The state update and record initialization are not presented as a transaction. No synchronization operation is visible. Concurrent use of shared state is outside the established contract.

## Acceptance examples

These are conditional consequences of the static evidence, not executed tests. Unless stated otherwise, addresses are valid and nonoverlapping, arithmetic does not wrap, dependency calls return normally with suitable storage, and the calls do not modify the supplied state.

### Reuse takes priority

Given a nonzero reuse head whose offset-12 link identifies another record, the function selects the original head and replaces the state’s reuse head with that link.

This remains true if the sequential cursor equals the end. Growth is not attempted while a reusable record is available. The selected record’s fields are cleared in the stated order, including clearing its former link at offset 12.

### Existing sequential space

Given a zero reuse head and a cursor unequal to the end, the original cursor is selected and the cursor advances by 20 bytes.

If the original cursor is exactly 20 bytes before the end, the resulting cursor equals the end. No allocation occurs during this call; the equality affects a later call if the reuse head remains zero.

### First block

Given a zero reuse head, equal cursor and end, and a zero block head, the requested capacity is 32 records.

The dependency requests are 12 bytes followed by 640 bytes. The new descriptor’s previous-block link is zero. Its storage begins with the selected record, the cursor advances 20 bytes into that storage, and the end is set 640 bytes after its start.

### Growth from capacity 32

Given growth from an existing capacity of 32, the two capacity candidates are 64 and 52. The new capacity is 64, and the second dependency request is 1,280 bytes.

### Growth from capacity 64

Given growth from an existing capacity of 64, the candidates are 96 and 104. The new capacity is 104, and the second dependency request is 2,080 bytes.

### Wrapped capacity arithmetic

Given an existing unsigned capacity of 4,294,967,295, the two wrapped candidates are 31 and 2,684,354,557. The latter is selected.

Multiplication by 20 wraps to 2,147,483,588 bytes. This example establishes the arithmetic behavior only; it does not assert that the resulting state or storage request is operationally safe.

### Partial initialization

Given a selected record whose bytes 1–3 and 16–19 contain nonzero data, those bytes remain unchanged if no aliasing or dependency effect alters them.

Offsets 4–15 become zero, and byte 0 becomes zero. Treating the result as a fully zeroed 20-byte record would violate this contract.

### Dependency changes the block head

If either dependency changes the state’s block head and both calls return normally, the descriptor’s previous-block link is read from the post-call state. It need not equal the head used earlier to obtain the capacity.
