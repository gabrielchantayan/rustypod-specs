# F-85a78df759d4

## Purpose

F-85a78df759d4 constructs a context using an explicit descriptor or a shared default descriptor. Its complete success path obtains backing and context values, acquires an external handle, configures the context, performs external setup and completion calls, and publishes the context address through a caller-provided output location.

The established behavior consists of checks, memory accesses, dependency calls, status handling, and their ordering. “Allocation,” “configuration,” and “completion” describe inferred dependency roles; their full semantics are not established.

Success returns zero. Locally generated failures return `0x1A` or `0x27`. A nonzero configuration status is returned unchanged.

## Interface

### Inputs and result

The interface has four logical inputs:

| Input | Representation | Direct requirements and use |
|---|---|---|
| Output location | Address of a writable 32-bit slot | Must be non-null; receives the context address only after the complete success sequence |
| Optional descriptor | 32-bit address | Null selects the shared-default path; non-null selects the supplied descriptor |
| Required value | 32-bit integer | Must be nonzero; stored in the context after configuration succeeds |
| Associated value | Opaque 32-bit value | Stored beside the required value; zero is accepted |

The return value is a 32-bit status.

Addresses, integer fields, and opaque values are represented by four-byte slots in the supplied representation. This contract does not establish behavior for a wider-pointer ABI.

| Status | Established meaning |
|---|---|
| `0` | Both final dependency calls returned normally, and the context address was written to the output location |
| `0x1A` | A required input or descriptor-marker check failed, or configuration returned this status |
| `0x27` | Context allocation, external acquisition, or external setup failed, or configuration returned this status |

## Behavior

### Initial capture and mandatory-input checks

Before rejecting either mandatory input, the function reads the shared-default pointer and retains that address as the initially selected descriptor.

It then checks the output location and required value. If the output location is null or the required value is zero, it returns `0x1A`.

On this rejection path, the initial shared-pointer read has occurred, but no descriptor-marker dereference, dependency call, or direct output write is shown.

### Descriptor selection and distinct shared-pointer reads

For a non-null descriptor input:

1. The supplied descriptor replaces the initially captured address as the selected descriptor.
2. Its marker at `0x00` is compared with the acceptance marker.
3. A mismatch returns `0x1A`.

The shared-default initializer is not called on this explicit-descriptor path.

For a null descriptor input, the initially captured address remains selected. However, the first marker check does **not** necessarily dereference that captured address:

1. The shared-default pointer is read again.
2. The marker at the address obtained by this separate read is compared with the acceptance marker.
3. If the marker differs, the shared-default pointer is read once more to supply the argument to F-ad9fef0b9720.
4. No result from F-ad9fef0b9720 is tested.

Thus, the default path involves two shared-pointer reads when initialization is skipped, and three when initialization is attempted. Without an established stability or synchronization guarantee, the captured descriptor, the descriptor initially inspected, and the initialization target need not be the same object.

After either selection path, the function reads `0x00` from the **selected descriptor** and compares it with the readiness marker. A mismatch returns `0x1A`.

On the default path, this readiness check uses the address captured before mandatory-input validation, not a replacement address loaded after initialization. Later descriptor reads and the configuration call also use that captured address. Updating the shared-default pointer does not by itself retarget those operations.

The representation establishes these separate pointer accesses and the sequencing around the initializer call. It does not establish a finer ordering among operands within an individual comparison expression.

### Backing-value selection

After the readiness check succeeds, the function captures the 32-bit value at selected-descriptor offset `0x10`.

It next reads the flags at `0x04` and tests mask `0x08`:

- If the bit is set, the value at `0x0C` becomes the backing value. No backing allocation is requested.
- If the bit is clear, the function reads `0x14`, adds it to the captured `0x10` value, and passes the sum to F-d33f6d597e5d. That dependency’s result becomes the backing value.

A zero backing value is accepted locally in either branch. In particular, a zero result from the computed-size allocation does not terminate construction.

The addition is represented as signed 32-bit integer arithmetic. No check for negative operands, overflow, or an unsuitable allocation size is shown. Behavior outside the signed representable range is unresolved; neither wraparound, saturation, widening, nor rejection is established.

The backing-selection decision and the value captured from `0x10` are retained across subsequent calls. Later descriptor mutations do not cause this function to reread those fields for the same decisions.

### Context allocation and external acquisition

The function next calls F-d33f6d597e5d with `0x238`.

If this returns zero:

- External acquisition is not attempted.
- If the backing value came from the computed-size allocation and is nonzero, it is passed to F-5e3309c9d083.
- The function returns `0x27`.

If the context result is nonzero, the function calls F-000000000001 with no shown arguments.

If acquisition returns zero:

1. The context value is passed to F-5e3309c9d083.
2. A nonzero backing value obtained from the computed-size allocation is then passed to F-5e3309c9d083.
3. The function returns `0x27`.

An existing backing value selected by flag `0x08` is not passed to that dependency on either early-failure path.

If acquisition returns nonzero, the function performs these direct four-byte context writes in order:

1. Acquisition result to `0x18C`.
2. Backing value to `0x208`.
3. Captured descriptor value to `0x20C`.

### Configuration and input installation

F-9bf13f8f02d7 receives the context address and selected descriptor address.

If it returns nonzero, that exact status is returned. The function performs no subsequent direct context stores, external setup, completion calls, or output publication. No local cleanup call is shown on this path.

If configuration returns zero, the function writes:

1. The required value to context offset `0x1F8`.
2. The associated value to `0x1FC`.

It then reads the four-byte value at `0x220` and passes it to F-141a6af56ef5.

The representation does not establish how `0x220` became valid. Successful configuration is not evidence that every context field was initialized.

### External setup

After F-141a6af56ef5 returns, F-000000000002 receives five arguments:

1. The current value at context offset `0x18C`.
2. The result of F-141a6af56ef5.
3. The current value at context offset `0x208`.
4. The current value at context offset `0x20C`.
5. A separately referenced global 32-bit value.

The context fields and global argument are obtained for this call after the transformation call. They are not promised to equal earlier values: preceding dependencies may have modified accessible state.

The expression does not establish an individual evaluation order among all setup arguments.

A nonzero setup result is converted to `0x27`; its particular value is not propagated. No local cleanup, final completion call, or output publication follows.

### Completion and publication

If external setup returns zero:

1. The current handle at `0x18C` is read and passed with the context address to F-80e21062e235.
2. After that call returns, the handle at `0x18C` is read again.
3. The reread handle is passed to F-000000000003.
4. After that call returns, the context address is written to the output location.
5. The function returns zero.

Neither final dependency’s result is tested. Their returning normally is sufficient for execution to reach publication; no independent success indication is required.

The two final calls need not receive the same handle because the field is reread between them.

## Side effects

### Output visibility and aliasing

The only direct write to the output slot occurs after both final calls return.

Every earlier return leaves that slot unwritten **by this function’s publication operation**. This is not an unconditional preservation guarantee: dependencies may modify aliased storage, and other direct context stores could affect the slot if storage overlaps.

Dependencies receive the context before the output slot is populated.

### Shared state and descriptors

The function directly reads the shared-default pointer multiple times under the conditions described above. It does not directly write that pointer or descriptor fields.

F-ad9fef0b9720 receives the address from the conditional third pointer read. Its effects on the shared pointer, the captured descriptor, the initialization target, and other state are unknown. Initialization of one object does not establish readiness of a different captured object.

F-9bf13f8f02d7 receives the selected descriptor address. Descriptor immutability across dependency calls is not established.

### Resource handling

The directly shown release-like calls are confined to context-allocation failure and external-acquisition failure.

After successful external acquisition, no direct resource-release call is shown, including on configuration or setup failure. That fact does not prove a leak: dependency ownership transfers and internal cleanup are unknown.

Likewise, release-like terminology does not establish that F-5e3309c9d083 actually frees memory. What is established is which values are passed to it and in what order.

On success, the caller receives the context address. The eventual destruction operation and ownership of associated backing and external resources are not established.

## Acceptance examples

These examples are conditional consequences of static evidence, not runtime observations. Calls are assumed to return normally unless stated otherwise.

1. **Mandatory-input rejection.** A null output location or zero required value produces `0x1A`. The initial shared-pointer capture occurs, but no descriptor marker is dereferenced and no dependency is called.

2. **Explicit descriptor rejection.** An explicit descriptor failing the acceptance check produces `0x1A` without default initialization. If it passes acceptance but fails readiness, the same status results.

3. **Distinct stable markers.** If the two marker values differ and neither the explicit descriptor marker nor either comparison value changes, an explicit descriptor cannot pass both comparisons.

4. **Stable default pointer.** If all default-pointer reads yield the same address and its first marker fails acceptance, F-ad9fef0b9720 receives that address. Construction proceeds past validation only if the subsequent readiness read matches the readiness marker. The initializer’s untested result is irrelevant to that branch decision.

5. **Different default-pointer read results.** Suppose the initial capture identifies one descriptor, the initial marker dereference identifies another, and the initializer argument identifies a third. If the second descriptor fails acceptance, initialization is called on the third. Readiness is nevertheless checked on the first, and configuration later receives the first. A ready third descriptor does not compensate for a non-ready first descriptor.

6. **Initialization skipped on another object’s marker.** If the second pointer read identifies a descriptor matching acceptance, initialization is skipped even if the captured descriptor differs. A failing readiness marker on the captured descriptor then produces `0x1A`.

7. **Existing zero backing value.** With flag `0x08` set and `0x0C` equal to zero, zero is selected without backing allocation. Context-allocation failure returns `0x27` without a release-like call for that backing value.

8. **Computed allocation returns zero.** With flag `0x08` clear, a zero backing-allocation result does not prevent context allocation or external acquisition. Later success can publish a context into which zero was initially stored at `0x208`.

9. **Acquisition failure.** After nonzero context allocation, zero external acquisition causes the context to be passed to F-5e3309c9d083 first, followed by nonzero internally requested backing. The result is `0x27`, without publication.

10. **Configuration failure.** A nonzero configuration result is returned unchanged. The required and associated inputs are not subsequently stored by this function, and no local cleanup call follows.

11. **Setup failure.** Any nonzero external-setup result becomes `0x27`. Neither final call nor output publication occurs.

12. **Handle mutation and publication.** If F-80e21062e235 changes `0x18C`, F-000000000003 receives the changed handle. If both calls return normally, publication follows them and the return status is zero, regardless of their untested results.
