# F-8685dec604a9

## Purpose

F-8685dec604a9 conditionally updates a keyed entry in a context. It normalizes a category-and-flag argument, checks whether an existing entry blocks replacement, optionally performs callback-driven cleanup over three records, and requests a destination for four field writes.

Established outcomes are:

- Result `1` for an unsupported normalized category.
- Result `5` when an existing entry has a nonzero occupancy-like field and a context guard is nonzero.
- Result `0` after the destination request, including when that request returns null.

These results identify control-flow outcomes, not independently verified dependency success. In particular, result `0` does not prove that an entry was written.

“Entry,” “replacement,” and “cleanup” describe inferred roles. They do not establish ownership, allocation, release, or application-level semantics.

## Interface

### Arguments and result

The supplied interface uses six 32-bit arguments and a 32-bit result.

| Position | Role |
|---|---|
| 1 | Context address, passed to dependencies and used for context-relative accesses. |
| 2 | Opaque key-designating value, passed unchanged to key-related and lookup dependencies. |
| 3 | Unsigned category-and-flag word. Bit 3 is separated from the category and retained for a possible destination write. |
| 4 | Opaque value written to destination offset `+0x08`. |
| 5 | Opaque value written to destination offset `+0x0C`. An existing value at this offset controls entry into replacement handling. |
| 6 | Opaque value written to destination offset `+0x10`. During cleanup, a nonzero value at this offset is used as a callback address. |

The explicit results are `0`, `1`, and `5`. The status-reporting dependency’s return value does not determine these results.

The global diagnostic value is not established to be immutable, a string, or a pointer. It is distinct from the named diagnostic reference used for result `1`.

### Preconditions

Fault-free execution requires all actually accessed storage to remain valid for the relevant access width. Any invoked callback must be callable with the observed single-argument interface, and storage used after a callback must remain valid if execution is to continue normally.

These requirements are path-dependent. For example, unsupported categories bypass direct context-field and record-field accesses, but the status-reporting dependency may impose its own requirements.

The function does not visibly validate context addresses, key representations, callback addresses, backing-storage extent, alignment, or object lifetime. No synchronization or reentrancy guarantee is established.

## Behavior

### Category normalization

The function first clears bit 3 of the full 32-bit third argument. It does not first truncate that argument to a byte.

If the resulting value is exactly `4`, it reads the selector byte:

- Zero selects effective category `3`.
- Any nonzero byte selects effective category `2`.

No selector-byte read is established for other normalized values.

The effective category is accepted only when every bit above bit 1 is zero. Thus the accepted effective categories are exactly `0`, `1`, `2`, and `3`.

Consequently:

- Third arguments `0` through `3` are accepted directly.
- Third arguments `8` through `11` select the same respective categories while retaining bit 3 for installation.
- Third arguments `4` and `12` use the selector-dependent mapping.
- Other bits remain significant during validation. For example, `0x100` is invalid despite having a zero low byte.

### Unsupported category

For an unsupported category, the function calls F-a061acf353ed with:

1. The context.
2. Status `1`.
3. A named diagnostic reference associated with the unsupported-category case.

It then returns `1`.

This path performs no key-related call, entry lookup, cleanup preparation, scan, or destination write. It does not evaluate the separate global diagnostic value used by the result-`5` branch.

The named reference’s exact text, storage characteristics, and ownership are not established here.

### Initial lookup

For an accepted category, the function calls F-1cb585febd84 with the second argument. Its returned 32-bit value is then passed to F-4a95613e1504 together with:

1. The context.
2. The effective category, restricted to its low eight bits.
3. The original second argument.
4. The newly returned key-related value.
5. Mode `0`.

If the lookup result is null, no entry field is read through it.

If it is non-null, the function reads its 32-bit field at `+0x0C`. A zero field bypasses replacement handling. A nonzero field enters that handling.

### Replacement guard and result `5`

On the occupied-entry path, the function next reads the context’s 32-bit guard at `+0x90`.

If the guard is nonzero, the function evaluates the global diagnostic value and calls F-a061acf353ed with the context, status `5`, and that evaluated value. It then returns `5`.

The established ordering on this branch is:

1. Initial call to F-1cb585febd84.
2. Initial call to F-4a95613e1504.
3. Read of the returned entry’s `+0x0C` field.
4. Read of the context guard.
5. Evaluation of the global diagnostic value for the reporting call.
6. Reporting call and explicit return of `5`.

The diagnostic argument is therefore not a fixed reference captured before the initial dependencies. Those dependencies may change the global value before it is evaluated. Its representation, ownership, diagnostic meaning, and immutability are not established.

This branch does not call F-ad6543e399ad, perform the cleanup scan, or request a destination. No direct record writes precede this return, although earlier dependencies and the reporting call may have side effects.

If the guard is zero, the function calls F-ad6543e399ad with the context and ignores its result.

### Eligibility for cleanup

After F-ad6543e399ad returns, the function reads the initial entry’s category byte at `+0x04`. It promotes that byte, clears bit 3, and compares the result with the effective category.

This is a fresh read after the dependency call, not a comparison against a saved category byte. A mutation by that dependency can therefore change whether cleanup is entered.

If the comparison fails, the function skips the scan and proceeds to the destination request.

If it succeeds, the function:

- Calls F-1cb585febd84 again with the second argument.
- Calls F-a09bb08bf954 with the context-relative address `+0x128`, the second argument, and the fresh key-related result.
- Uses the returned address as the base of the three-record scan.

There is no null check on this scan-base result before record access.

### Three-record scan

The scan visits records at offsets `0`, `0x14`, and `0x28` from the returned base, in that order.

At each record, it compares the record’s raw category byte at `+0x04` with the initial entry’s raw category byte at `+0x04`. This comparison includes bit 3 and all other bits in the byte. It is not the masked comparison used to decide whether to enter the scan.

For each matching record:

1. The callback field at `+0x10` is tested for zero.
2. If nonzero, the designated callback is invoked with the record’s 32-bit `+0x08` value.
3. After the callback returns, or immediately if no callback is present, the record’s 32-bit `+0x0C` field is written with zero.

The prior `+0x0C` value does not control this operation. A matching record with zero `+0x0C` can still have its callback invoked. A matching record without a callback still receives the zero write.

For a nonmatching record, this function does not invoke its callback or clear its `+0x0C` field.

The scan does not directly clear the category byte, payload field, or callback field.

The initial entry’s category byte participates in each iteration’s comparison; it is not snapshotted for the entire scan. A callback that changes it can alter subsequent matching decisions. Later records are likewise examined when reached. No dependency or callback is assumed to preserve record contents or pointer validity.

If a callback fails to return normally, neither the subsequent clear nor later processing is guaranteed.

### Destination request and installation

Every accepted-category path that does not return `5` performs a fresh call to F-1cb585febd84 after any replacement handling.

The function then calls F-4a95613e1504 using the same argument roles as the initial lookup, but with the fresh key-related result and mode `1`.

The destination is not assumed to equal the initial entry or any scanned record.

For a non-null destination, the function performs these direct writes in order:

| Order | Destination offset | Width | Value |
|---:|---|---:|---|
| 1 | `+0x0C` | 32 bits | Argument 5 |
| 2 | `+0x08` | 32 bits | Argument 4 |
| 3 | `+0x10` | 32 bits | Argument 6 |
| 4 | `+0x04` | 8 bits | Effective category combined with bit 3 from the original third argument |

The resulting category byte is one of `0`–`3` or `8`–`11`. Selector-dependent input stores category `2` or `3`, never category `4`.

If the destination is null, all four writes are skipped. This condition does not produce a separate error result.

Finally, the function calls F-a061acf353ed with the context, status `0`, and diagnostic value zero, then returns `0`. The reporting call follows all destination writes and may itself alter caller-observable state.

## Side effects

Direct effects are limited to the described global, context, and record reads; cleanup clears; and destination writes.

The result-`5` diagnostic evaluation is a conditional global read. It occurs only after the initial dependencies and occupied-entry guard checks. It must not be treated as an immutable diagnostic constant or conflated with the unsupported-category reference.

The installation sequence writes the occupancy-like field first. No atomic publication, transaction, memory barrier, or rollback is visible. Cleanup can modify records before the destination request; a null destination does not restore those records.

Dependencies and callbacks may cause additional effects. Their preservation of globals, records, allocations, or returned addresses is not established.

No direct allocation, deallocation, reference-count adjustment, or copying of pointed-to payload contents is visible. Storing a 32-bit value does not establish ownership transfer. Callback invocation does not establish destruction or memory release.

The callback receives the `+0x08` value, not the `+0x0C` value, and receives no explicit context argument in the observed invocation.

## Acceptance examples

These are conditional static acceptance cases, not runtime tests. Unless otherwise stated, dependencies return normally, accessed memory remains valid, and incidental mutations do not change the stated conditions.

1. **Preserved flag.** With argument 3 equal to `10`, lookup category arguments are `2`. A non-null destination receives category byte `10`.

2. **Selector-dependent input.** With argument 3 equal to `12`, a zero selector byte produces effective category `3` and stored byte `11`. A nonzero selector produces category `2` and stored byte `10`.

3. **Full-width rejection.** Argument 3 equal to `0x100` produces status and result `1`, with the unsupported-category diagnostic reference. There are no key-related or lookup calls.

4. **Late global diagnostic read.** Suppose an accepted input reaches an occupied initial entry and a nonzero context guard. If the initial key-related or lookup dependency changes the global diagnostic value from `A` to `B`, and it remains `B` until evaluation, the status-`5` call receives `B`, not an entry-time snapshot of `A`.

5. **Unoccupied entry bypasses the guard.** If the initial entry’s `+0x0C` is zero, this function does not read the context guard or the result-`5` diagnostic global. A nonzero guard does not itself block installation on this path.

6. **Flag-sensitive cleanup.** With effective category `2` and initial raw byte `10`, scanned raw bytes `2`, `10`, and `10` cause only the latter two records to match, provided the comparison state remains unchanged.

7. **No callback still clears.** A matching record with zero callback field receives zero at `+0x0C`. Its payload and callback fields are not directly cleared.

8. **Callback precedes clear.** A matching record’s callback receives its `+0x08` value before the function clears `+0x0C`. If the callback changes that field and returns normally, the subsequent zero write overwrites its change.

9. **Missing destination.** A null mode-`1` result skips installation but still produces status and result `0`. Earlier cleanup is not undone.

10. **Zero installed occupancy-like value.** Argument 5 may be zero. A non-null destination still receives all four writes in the specified order.
