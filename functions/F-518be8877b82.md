# F-518be8877b82

## Purpose

F-518be8877b82 configures a state object from a supplied data address, length, representation selector, and storage-policy value. A null data address selects a separate reset-like operation. A non-null address selects either a reserve-and-transfer path or a direct-address installation path.

The established behavior is the control flow, argument construction, state accesses, and status mapping described below. Interpreting the data as text, the storage-policy value as ownership information, or the reserve-and-transfer path as creating an independent copy is inferred intent. Those interpretations depend on callees whose implementations are not supplied.

The function returns a 32-bit status. Its explicit return values are:

- **0:** normal completion, including completion of the null-data branch.
- **7:** a nonzero result from either of two checked dependencies.

A zero return does not independently establish that every dependency succeeded: several dependency results are ignored.

## Behavior

### 1. Null data address

If the data address is zero, the function calls **F-05ca8baffd5f** with the state address and then returns 0.

On this branch, the function itself:

- Does not inspect the data contents.
- Does not process the length, selector, or storage-policy value.
- Does not perform any of the fixed-offset state accesses listed above.
- Does not inspect the dependency’s result.

Calling this branch a reset or clear is inferred intent. Its actual effects, including any release of memory, are documented_only.

### 2. Initial flags and effective length

For a non-null data address, the function constructs an initial 16-bit flag value:

- Original selector zero: `0x0010`.
- Any other original selector: `0x0002`.

If the supplied length is nonnegative, it becomes the effective length unchanged. No terminator is examined.

If the supplied length is negative, the effective length starts at zero and is determined by a scan:

- **Original selector exactly one:** read one byte at each successive offset until a zero byte is encountered. The effective length is the offset of that byte.
- **Every other original selector:** examine candidate pairs at offsets 0, 2, 4, and so on. A pair terminates the scan only when both bytes are zero. The effective length is the offset of that pair.

For the pair scan, reads are short-circuited: the first byte is read first; the second byte is read only when the first is zero. A nonzero first byte advances the scan without reading the second byte at that candidate position.

After either scan terminates, flag bit `0x0020` is added.

Consequences:

- The effective length excludes the terminator.
- Every negative input length requests scanning; there is no special distinction between −1 and other negative lengths.
- The pair scan produces an even effective length if its arithmetic remains representable.
- A supplied nonnegative length may be odd, regardless of selector.
- Selector zero uses the pair scan, despite being normalized to one later.
- Unknown selector values use the pair scan rather than being rejected.

A caller using a negative length must provide readable memory through a reachable terminating byte or pair, subject to the actual short-circuit read order. There is no scan bound.

### 3. Storage-policy value exactly −1

This path computes a transfer count from the effective length.

- With a nonnegative supplied length, the count equals that length.
- With a scanned length and original selector one, the count is effective length plus one.
- With a scanned length and any other original selector, the count is effective length plus two.

Thus, a scan includes its terminating byte or pair in the transfer count, while the length eventually stored in the state excludes it. An explicitly supplied length does not cause any extra terminator bytes to be requested.

The function then:

1. Calls **F-05077d384bfe** with the state address, transfer count, and zero.
2. If that dependency returns nonzero, returns 7 immediately.
3. Otherwise, reads the 32-bit value at state offset `0x14`.
4. Invokes an unmapped external dependency with that value as the destination-like argument, the supplied data address as the source-like argument, and the transfer count as the third argument.
5. Continues to metadata installation without checking the external dependency’s result.

The destination field is read **after** F-05077d384bfe returns. It is not captured before that call.

This path does not directly write the supplied data address into `0x14`, and it does not directly write `0x20`. Either dependency may nevertheless modify those or other fields.

The call shape suggests allocation or reservation followed by a byte transfer. Actual allocation, copying, overlap behavior, and memory ownership remain dependency-defined.

### 4. Storage-policy value other than −1

This path first calls **F-74b5a05d0094** with the state address. Its result is not checked.

After that call returns, the function:

1. Selects an additional flag:
   - Storage-policy value zero: `0x0080`.
   - Any other value: `0x0040`.
2. Writes the complete 32-bit storage-policy value to state offset `0x20`.
3. Adds the selected flag to the current flags.
4. Writes the supplied data address to state offset `0x14`.

Negative values other than −1 therefore take this path and receive flag `0x0040`. They are not rejected or converted.

The preceding dependency may be intended to release or detach prior storage, but that is not established. In particular, it cannot be assumed to preserve globals, leave other state fields unchanged, or avoid affecting memory reachable through the supplied data address.

### 5. Common metadata installation

After either non-null storage path completes without an early return, the function normalizes the selector:

- Original selector zero becomes one.
- Every other selector remains unchanged.

It then performs these direct state writes in this order:

1. Effective length to `0x18`, as 32 bits.
2. Constructed flags to `0x1c`, as 16 bits.
3. Low eight bits of the normalized selector to `0x1f`.
4. Tag to `0x1e`, as eight bits:
   - 4 when the original selector was zero.
   - 3 otherwise.

The write to `0x1f` precedes the write to `0x1e`, despite the latter having a lower address.

The selector is compared at full width before being narrowed for storage. Consequently, a value whose low byte is one is not necessarily treated as selector one.

### 6. Conditional final dependency

After the metadata writes:

- If the full-width normalized selector equals one, no final dependency is called.
- Otherwise, the function calls **F-7bf2492c1b76** with the state address.

A nonzero result from this dependency produces status 7. A zero result produces status 0.

Original selectors zero and one both skip this dependency. Every other original selector reaches it.

The dependency runs after all common metadata writes and may change them. Therefore, the direct writes above specify the values installed before the call, not unconditional final-state guarantees.

## Side effects

### Ordering and partial updates

The observable sequence is:

1. Null-address decision.
2. For non-null data, any requested terminator scan.
3. The selected storage-path dependency and accesses.
4. Common metadata writes.
5. Any required final dependency.
6. Status return.

If F-05077d384bfe returns nonzero, the function performs no subsequent transfer invocation or common metadata writes. That dependency may already have changed state; no rollback is attempted.

If F-7bf2492c1b76 returns nonzero, common metadata has already been written. Its own mutations may also have occurred. Status 7 does not imply preservation of the entry state.

### Memory access and aliasing

The wrapper’s direct data-buffer reads occur only during negative-length scanning. A nonnegative length does not cause direct source-buffer reads before the selected dependencies.

There is no explicit non-aliasing check among the state, source, and destination regions. Aliasing is not automatically invalidated by this wrapper, but dependencies and ordered writes may affect its outcome. In particular:

- A scan occurs before either storage-path dependency.
- A cleanup-like dependency can run before the supplied address is installed.
- The transfer destination is obtained from potentially modified state.
- The external transfer dependency’s overlap guarantees are unknown.

### Ownership

No ownership contract is established solely by the flags or storage-policy value. The wrapper does not itself free memory. Any allocation, release, reference-count update, or ownership transfer belongs to dependency behavior and is documented_only.

### Arithmetic and faults

The effective length and transfer count are represented as signed 32-bit quantities in the supplied representation. Repeated scan increments and terminator-count additions can exceed that range. Address additions can also exceed the usable address space.

There are no explicit overflow checks or bounded-read checks. Wrapping, trapping, fault handling, and successful behavior outside representable, accessible ranges are not established.

No exception-handling or memory-fault recovery behavior is shown.
