# F-531eddc58a54

## Purpose

F-531eddc58a54 obtains a candidate 32-bit value, resolves an associated record, rejects a candidate already present in that record’s slot array, and attempts to place the candidate into the first zero-valued slot.

The established behavior is **replacement of an existing zero slot**, not general append behavior. If the searched range contains no zero slot, the function returns −1 without directly inserting the candidate. This remains true if a preceding dependency call changes the record but leaves the subsequently searched range without a zero.

On successful insertion, the function increments the record’s field at offset 0x38. It does not directly increment the scan-bound field at offset 0x34. Their apparent relationship may suggest bookkeeping intent, but their semantic names and invariants are not established.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

### Invocation and result

The function accepts no explicit arguments and returns a signed 32-bit integer.

Possible results are:

- **−1:** candidate acquisition returned zero, duplicate detection found the candidate, or the later slot search found no zero.
- **A nonnegative slot index:** the later search found a zero-valued slot. Under ordinary, stable-memory execution, the function increments the field at offset 0x38 and writes the candidate into that slot before returning its index.

There is no distinct result for duplicate rejection versus lack of an available zero slot. Dependency failures other than the explicitly checked zero candidate have no defined error conversion in the supplied evidence.

### Relevant widths and record layout

The supplied representation uses 32-bit integer values, four-byte slot entries, and 32-bit address-like values. A compatible record has the following relevant fields:

| Byte offset | Width | Established use |
|---|---:|---|
| 0x30 | 4 bytes | Address of the slot array |
| 0x34 | 4 bytes | Signed bound used by both scans |
| 0x38 | 4 bytes | Compared with the scan bound before a dependency call; incremented before an insertion |

Offsets are relative to the record address returned by F-ecd921e533b1. No other record fields are directly accessed by this function.

Each slot occupies four bytes. Slot index zero is at the array address, index one is four bytes later, and subsequent entries follow the same spacing. Zero is the sentinel searched for as an available slot. A candidate of zero is rejected before any record lookup.

The meanings “capacity,” “length,” and “occupied count” are not established for either numeric field. This contract therefore calls them the **scan bound** and the **0x38 field**.

## Behavior

### 1. Acquire the candidate

The function first calls F-8157a180d901 with the constant 0x48, decimal 72. Its four-byte result is passed as the first argument to F-bb27b9d7a176; the second and third arguments are both zero.

The returned candidate is tested against zero:

- If zero, the function immediately returns −1.
- Otherwise, the function continues with that exact 32-bit candidate value.

The constant 72 is an established argument, not proof of an allocation size or object layout. Neither the first result nor the candidate has an established ownership model.

### 2. Resolve the record and reject duplicates

The nonzero candidate is passed to F-ecd921e533b1. The result supplies the record address used for the remainder of the function.

The function scans slots in ascending index order, beginning at zero. Each iteration compares the index against the signed value read from the record’s scan-bound field at offset 0x34.

For every index admitted by that comparison, the function obtains the array address from offset 0x30 and reads the corresponding four-byte slot. If that slot equals the candidate, the function immediately returns −1.

Important consequences:

- Duplicate detection occurs before the possible call to F-2f110feb3696.
- A duplicate causes no direct field or slot write by this function.
- A zero or negative scan bound permits no slot reads in this scan.
- The scan-bound field is consulted again for successive loop conditions; it is not initially captured as a fixed bound for this scan.
- The array-address field is used again for successive slot accesses; the function does not establish a permanent array-base snapshot for the scan.

Under stable record contents, duplicate detection covers precisely the slots whose indices are nonnegative and strictly less than the scan bound.

### 3. Conditionally call the record-management dependency

After duplicate detection completes without a match, the function compares the 0x38 field with the scan-bound field.

If they are equal, it calls F-2f110feb3696 with the address of the record’s field at offset 0x30. The argument is therefore an address **inside the record**, not the slot-array address stored in that field.

If the fields are unequal, this dependency is not called.

The dependency’s return value is not used. There is no explicit success check.

This call may change the array-address field, either adjacent numeric field, other memory, or external state. No preservation or allocation behavior is established. The subsequent search uses the record’s contents after this call rather than assuming that the earlier values remain unchanged.

The duplicate scan is not repeated after the call. Consequently, any property established by that earlier scan applies to the earlier observed contents, not necessarily to dependency-modified contents.

### 4. Search for the first zero slot

The function reads the scan-bound field into a local 32-bit value after the optional dependency call. This captured bound governs the entire second scan.

Starting at index zero, it examines each slot below that signed bound and stops at the first slot equal to zero. The array address is obtained from the record’s offset-0x30 field for each examined slot.

If no zero is found, the search result becomes −1. In particular:

- A captured bound of zero or a negative value produces −1 without examining slots.
- A positive bound with no zero-valued entries produces −1.
- Space outside the captured range is not searched.
- A dependency that merely makes additional storage available does not by itself cause insertion; the second search must actually encounter a zero inside its captured range.

Unlike the duplicate scan, later changes to the scan-bound field do not alter this second scan’s captured limit. Changes to the array-address field can still affect later slot accesses.

### 5. Update bookkeeping and insert

For a zero slot found by ordinary execution, the selected index is nonnegative and strictly less than the captured bound. The function then performs these direct writes in order:

1. Read the current 0x38 field, add one, and write the result back to that field.
2. Read the array address from offset 0x30.
3. Write the candidate into the selected four-byte slot.

The scan-bound field is not directly modified.

Index zero is a valid insertion result. Although the supplied control flow contains a separate equality distinction, it does not exclude index zero when a zero slot was actually found within a positive range.

The insertion logic also excludes an index equal to the captured bound. The shown search cannot ordinarily produce such an index as a successful result: it examines only indices strictly below the bound.

If the search result is −1, neither direct write occurs.

Finally, the function returns the selected index or −1.

## Side effects

### Direct memory effects

The only direct writes established for this function are the increment of the 0x38 field and the subsequent candidate store into a selected zero slot.

The order matters. The function is not shown to provide transactional or atomic insertion. If the slot write cannot complete after the bookkeeping write, the earlier update is not explicitly rolled back.

There is no direct write to the scan-bound field and no direct clearing of any slot.

### Dependency effects

Every execution calls F-8157a180d901 and F-bb27b9d7a176. A nonzero candidate also causes a call to F-ecd921e533b1. F-2f110feb3696 is called only after successful duplicate screening and only when the two record fields compare equal.

These calls may have effects even when the final result is −1. A −1 result does not imply unchanged global state, no allocation, or no resource acquisition.

### Ownership and lifetime

The evidence contains no explicit release, destruction, or rollback call.

In particular, if candidate acquisition succeeds but duplicate detection or slot search later fails, this function does not visibly release the candidate or the earlier four-byte result. Whether that is correct, leaking, reference-neutral, or managed elsewhere is unknown.

No ownership transfer may be inferred solely from the candidate being stored in a slot.

### Concurrency and observability

No synchronization is visible. There is no established atomicity across the duplicate scan, optional dependency call, zero-slot search, bookkeeping update, and insertion.

The duplicate scan rereads its bound, whereas the zero-slot search captures its bound once. Both searches use the array-address field repeatedly. Concurrent or externally induced mutation can therefore produce observations different from a single consistent record snapshot.

Relative ordering between the two field reads used by the equality comparison is not established here. The phase ordering and final bookkeeping-before-slot-write ordering are established.
