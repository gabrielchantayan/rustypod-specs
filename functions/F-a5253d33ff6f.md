# F-a5253d33ff6f

## Purpose

F-a5253d33ff6f conditionally invokes an operation selected through a caller-supplied object. An optional callback can authorize or veto that operation and, after the operation completes, replace its result.

The established behavior has three principal paths:

- A null object produces zero without invoking a dependency.
- A nonnull object whose initial descriptor or operation entry is null triggers a diagnostic dependency and then produces −2, provided that dependency returns normally.
- An initially valid object proceeds through optional pre-operation notification, operation dispatch, and optional post-operation notification.

Interpreting the callback as an interceptor, and its event values as pre-operation and post-operation notifications, is inferred intent. The actual contract rests on the arguments, branching conditions, reads, and return-value selection described below.

## Behavior

### 1. Null-object handling

If the object is null, the function returns zero.

This path does not read an object field and does not invoke the diagnostic dependency, callback, or operation.

### 2. Initial operation availability check

For a nonnull object, the function first reads the descriptor reference at object offset 0.

- If the descriptor is null, the initial operation availability check fails without reading a descriptor field.
- If the descriptor is nonnull, the function reads the operation entry at descriptor offset 24.
- If that entry is null, the initial operation availability check fails.

On failure, the function invokes F-4fc89ec41a6d with five arguments, in this order:

1. 32
2. 103
3. 121
4. 0
5. 0

The dependency’s ordinary return value is not used. If it returns normally, F-a5253d33ff6f returns −2.

The callback field is not read on this failure path. A callback cannot repair an initially missing descriptor or operation entry through this invocation because it is never called in that case.

If F-4fc89ec41a6d fails to return normally, the evidence does not establish a subsequent −2 return.

### 3. Callback capture

After the initial descriptor and operation-entry checks succeed, the function reads the callback reference at object offset 4.

This reference is captured for the remainder of the invocation. The function does not visibly reread the object’s callback field before deciding whether to perform the post-operation call.

Consequently:

- A null captured callback means neither callback phase occurs.
- A nonnull captured callback is the target for both phases that are reached.
- A callback’s modification of the object’s callback field does not, by itself, replace the captured target for the current invocation.

The captured target must remain callable for any later invocation of it. The wrapper does not visibly retain, reference-count, or otherwise protect it.

### 4. Optional pre-operation callback

When the captured callback is nonnull, it is invoked with six arguments in the following order:

| Position | Value |
|---|---|
| 1 | Object |
| 2 | 6 |
| 3 | C |
| 4 | A |
| 5 | B |
| 6 | 1 |

The callback result is tested as a signed integer.

- A result less than 1 is returned immediately.
- A result of 1 or greater allows operation dispatch.

Thus zero and every negative signed result veto the operation. A positive result authorizes dispatch, but its magnitude is not forwarded to the operation.

A veto also suppresses the post-operation callback. Any side effects already performed by the pre-operation callback remain; no rollback is visible.

### 5. Operation selection and invocation

Before invoking the operation, the function reads the descriptor reference from the object again, then reads the operation entry at offset 24 of that descriptor.

The operation target used for dispatch is therefore selected by these later reads, not by reuse of the target obtained during the initial availability check.

There is no second null check on this dispatch path. In particular, a pre-operation callback may change the object’s descriptor or its operation entry, but the wrapper does not validate those replacements before attempting dispatch.

The operation receives six arguments:

| Position | No callback captured | Callback captured and authorization granted |
|---|---|---|
| 1 | Object | Object |
| 2 | A | A |
| 3 | B | B |
| 4 | C | C |
| 5 | B | B |
| 6 | C | 1 |

The fifth argument duplicates B in both cases. The sixth argument depends only on whether a nonnull callback was captured and the pre-operation phase authorized dispatch. It does not equal the positive authorization result unless that result happens to be 1.

The operation’s signed 32-bit result becomes the provisional result.

With no captured callback, that provisional result is returned directly. There is no sign check or special handling of an operation result of zero or a negative value.

### 6. Optional post-operation callback

If a nonnull callback was captured and the operation returns normally, the function invokes that same captured callback with:

| Position | Value |
|---|---|
| 1 | Object |
| 2 | 134 |
| 3 | C |
| 4 | A |
| 5 | B |
| 6 | Operation result |

This call occurs regardless of whether the operation result is positive, zero, or negative.

The post-operation callback’s result becomes the function’s final result without an additional condition or transformation. It may preserve, replace, or reverse the apparent success or failure represented by the operation result; the wrapper imposes no policy on that replacement.

If the operation does not return normally, the evidence does not establish that the post-operation callback runs.

## Side effects

### Direct effects

The wrapper visibly reads:

1. The initial descriptor reference, for a nonnull object.
2. The initial operation entry, if that descriptor is nonnull.
3. The callback reference, only after initial validation succeeds.
4. The descriptor reference again, if dispatch is reached.
5. The corresponding operation entry again, immediately for dispatch selection.

The supplied body contains no explicit stores to object fields, descriptor fields, global state, or caller-provided buffers.

The ordering above describes the supplied execution model. It is not an atomicity, synchronization, or inter-thread visibility guarantee.

### Effects through invoked functions

The diagnostic dependency, callback, and operation may have effects not described by this wrapper. The evidence does not establish that any of them:

Likewise, a post-operation callback still receives the original object argument even if the operation has changed or released the referenced storage. Safe use requires compatible callee lifetime behavior; that behavior is not established here.

No locking, retry, exception handling, or rollback is visible.

## Acceptance examples

These examples are conditional specifications, not observed runtime results. They assume readable storage, callable targets, and normal return from each invoked function unless stated otherwise.

1. **Null object.** With a null object and arbitrary A, B, and C, the result is zero. No dependency is invoked.

2. **Missing descriptor.** With a nonnull object whose descriptor reference is null, F-4fc89ec41a6d receives 32, 103, 121, 0, 0. If it returns normally, the wrapper returns −2. The callback field is not consulted.

3. **Missing operation.** With a readable nonnull descriptor whose operation entry is null, the same diagnostic invocation and −2 result occur. A nonnull callback field does not change this path.

4. **No callback.** Suppose initial validation succeeds, the callback is null, and A, B, and C are 10, 20, and 30. The dispatch-time operation receives the object followed by 10, 20, 30, 20, and 30. If it returns −9, the wrapper returns −9.

5. **Zero veto.** Suppose the callback receives the pre-operation invocation and returns zero. The wrapper returns zero without invoking the operation or post-operation callback.

6. **Negative veto.** If the pre-operation callback returns −7, the wrapper returns −7. No later operation-entry reread for dispatch is reached.

7. **Positive authorization.** With A, B, and C equal to 10, 20, and 30, a pre-operation callback result of 5 authorizes dispatch. The operation receives the object followed by 10, 20, 30, 20, and 1—not a sixth argument of 5.

8. **Result replacement.** If the operation returns −9 after authorization, the post-operation callback receives −9 as its sixth argument. If that callback returns 12, the wrapper returns 12.

9. **Descriptor replacement.** If the pre-operation callback installs a different valid descriptor and returns positively, dispatch uses the replacement descriptor’s operation entry. The originally checked operation is not necessarily invoked.

10. **Callback-field replacement.** If the pre-operation callback changes the object’s callback field, the post-operation invocation still targets the originally captured callback, provided that target remains callable.

11. **Invalidation after authorization.** If the pre-operation callback clears the descriptor or operation entry and returns positively, no defined error result is established. The wrapper attempts dispatch without repeating validation.
