# F-d1087040d66b

## Purpose

F-d1087040d66b searches a fixed-size table for the first record whose 32-bit key equals the supplied key. When a match is found, it clears two fields in that record and returns a 32-bit success indicator. If no record matches, it returns zero without writing to the table.

The established operation is a selective field reset, not removal of an entire record. The matching key remains unchanged. Consequently, a later invocation with the same key can find the same record and report success again.

An inferred intent is to deactivate or reset a keyed entry. The meanings of the cleared fields are not established, so “deactivation,” “release,” and “deletion” are not contractual descriptions.

## Interface

### Input

The function accepts one 32-bit integer key.

Matching uses equality between that argument and a 32-bit field read from each candidate record. No range restriction, special sentinel, or rejection of zero or negative keys is shown. Equality does not introduce an ordering interpretation: matching depends on equal 32-bit values, not whether either value is positive or negative.

### Result

The function returns a 32-bit value:

- **1:** A matching record was found, and the two specified clearing writes completed before normal return.
- **0:** The search completed without finding a matching record.

Success indicates that a key was found and the writes were performed. It does not establish that either cleared field previously held a nonzero value.

There is no separate result for an already-cleared record. There is also no explicit result for invalid memory, inaccessible storage, or an interruption during access.

### Table layout

The function obtains its table base from global state. The table contains ten candidate records, each with a stride of 12 bytes.

| Offset within each record | Width | Contractual use |
|---|---:|---|
| 0–3 | 32 bits | Key, read for comparison |
| 4–7 | 32 bits | Field set to zero after a match |
| 8 | 8 bits | Field set to zero after a match |
| 9–11 | 24 bits total | Not directly read or written |

Record indices run from 0 through 9. The key of record \(i\) begins at byte offset \(12i\) from the table base.

The interpretation of bytes 9–11 is unknown. They may be padding or additional data; this function does not establish either interpretation.

### Preconditions for normal completion

The global table-base state must be readable. Every key field reached by the search must support a valid 32-bit read. If a matching record is reached, its byte at offset 8 and its 32-bit field at offset 4 must support the specified writes.

The routine performs no explicit pointer, capacity, alignment, or access-permission validation. A valid complete table occupies 120 bytes, although an early successful search does not require this function to access later records.

Stable table-base state and stable keys during the call are sufficient conditions for the ordinary first-match behavior described below. No synchronization mechanism is shown.

## Behavior

### Search order and stopping condition

The search begins at record 0 and proceeds in increasing index order.

For each candidate, the function reads the 32-bit key at offset 0 and compares it with the input. A nonmatching candidate causes the search to advance to the next record. A matching candidate stops the search immediately.

At most ten candidate keys are examined. Record 9 is the final candidate; record 10 is never examined during ordinary execution.

Under stable table state:

- A match at index \(i\) requires examination of exactly \(i+1\) key fields.
- A search with no match examines all ten key fields.
- Duplicate keys do not cause multiple records to be reset. Only the first matching record is selected.

The source representation contains an additional index-bound check after a match. The surrounding loop limits the index to 0 through 9, so that check cannot reject an ordinary match. It provides no additional reachable result under the displayed control flow.

### Successful match

After selecting the matching record, the function performs these observable writes in this order:

1. It writes an 8-bit zero at record offset 8.
2. It writes a 32-bit zero at record offset 4.

It then returns 1.

The ordering matters: this is not one atomic update of both fields. An observer capable of seeing intermediate state could observe the byte field cleared before the 32-bit field is cleared.

The key at offset 0 is not overwritten. Bytes 9–11 are not overwritten. No subsequent record is examined after the match.

Writing zero is unconditional once a valid match is selected. The function does not first inspect either destination field, and it does not skip the write because the destination already contains zero.

### Unsuccessful search

If none of the ten keys matches, the function returns 0.

On this path, it performs no explicit table writes. It does not clear any candidate merely because a record appears unused, empty, or previously reset. Only key equality selects a record.

### Widths and arithmetic

The search index is represented as an unsigned 32-bit quantity. Its ordinary reachable values are 0 through 10, with 10 used only to terminate the search.

The record stride is 12 bytes. For examined records, the stride multiplication therefore ranges from 0 through 108 and does not overflow a 32-bit quantity.

The largest key access begins at table offset 108 and occupies offsets 108–111. For a match in the final record, the word clear occupies offsets 112–115, and the byte clear targets offset 116. Bytes 117–119 remain untouched.

These bounded offsets do not make an arbitrary base address safe. The function does not detect an invalid base, insufficient backing storage, or an address calculation that is invalid in the execution environment.

Both clearing values are zero, so their resulting bytes do not depend on byte order. The representation used to interpret nonzero keys remains environment-dependent.

## Side effects

The only explicit table modifications are the two clearing writes for a selected record.

For a normal successful invocation, the function:

- Preserves the selected record’s key.
- Clears exactly the fields at offsets 8 and 4–7.
- Leaves the selected record’s remaining bytes untouched.
- Does not modify other records.
- Does not explicitly modify the global table-base state.

There is no visible allocation, deallocation, external call, logging, callback, or ownership transfer.

In particular, the 32-bit field at offset 4 is not established to be a pointer. Even if another component interprets it as one, this function merely overwrites its storage with zero; it does not visibly release any associated resource.

The function provides no rollback. If execution is interrupted after the byte clear but before completion of the word clear, the source does not establish restoration of the earlier byte value. Fault delivery and partial completion of a failing memory access are properties of the execution environment, not error-handling behavior implemented here.

Concurrent mutation is not coordinated. The function does not establish that the key remains equal to the input between comparison and modification.

## Dependencies

There are no visible function-call dependencies. No additional opaque function IDs are required to describe the operation.

The routine depends on:

- Global state supplying the table base.

The source representation references the global table-base value during key lookup and again when forming the address for the successful update. It does not establish a single immutable base snapshot spanning the entire call.

Accordingly, without a stable-base precondition, the record whose key was compared is not guaranteed to be the same storage subsequently modified. Exact machine-level load counts and ordering beyond the represented operations are not established here.

## Acceptance examples

These examples are conditional behavioral criteria, not executed tests. Unless stated otherwise, assume valid memory, a stable table base, no concurrent modification, and normal completion.

### First record matches

Given that record 0’s key equals the input:

- The result is 1.
- Record 0’s byte at offset 8 becomes zero before its 32-bit field at offset 4 is cleared.
- Record 0’s key and bytes 9–11 remain unchanged.
- No later candidate key is examined.

### Last record matches

Given that records 0–8 do not match and record 9 does:

- All ten keys are examined in increasing record order.
- Only record 9 receives the two clearing writes.
- The result is 1.

### No record matches

Given that all ten keys differ from the input:

- All ten keys are examined.
- The result is 0.
- No table bytes are explicitly written.

### Duplicate keys

Given matching keys in records 2 and 7, with no earlier match:

- Record 2 receives the clearing writes.
- Record 7 is not examined or modified by this call.
- The result is 1.

### Repeated invocation

Given a stable matching key and an initial successful call:

- A second call with the same key finds the same first matching record.
- It performs the same two writes, even though their destinations are already zero.
- It returns 1 again.

This follows because clearing does not change the key.

### Zero or negative key

Given an input of zero, or any negative 32-bit value:

- A record with an equal 32-bit key is handled by the same matching rule.
- No special rejection or alternative reset behavior applies.

### Existing cleared fields

Given a matching record whose two destination fields already contain zero:

- The result is still 1.
- The writes still occur in the specified order.
- Success does not imply a change in stored values.
