# F-91e520893aef

## Purpose

F-91e520893aef attempts to resolve an ordering-term list against a sequence of query components. Each successfully resolved term is rewritten in place as a zero-based result-column reference and marked resolved.

The function returns a 32-bit status:

- **0:** no ordering list exists, or every ordering term is marked resolved at the final check.
- **1:** a term-count limit is exceeded, a dependency reports a negative result, a required result-list pointer is null, a returned column position exceeds the available result count, or a term remains unresolved after traversal.

These outcomes describe the visible control flow. They do not establish that dependencies performed no additional work or that a successful return implies an otherwise error-free surrounding context.

**Inferred intent:** the traversal and rewriting implement ordering-term resolution across a compound query. That interpretation is consistent with the diagnostic references and record structure, but the contract below relies on observed accesses rather than assumed language semantics.

## Interface

### Arguments

The function accepts four arguments:

1. **Resolution-context pointer.** Points to a record whose first 32-bit word supplies a context address. The same argument is passed to the resolver and diagnostic dependencies.
2. **Starting query-record pointer.** Supplies the ordering-list pointer and the starting point for component traversal.
3. **Opaque 32-bit value.** Passed to the initial limit diagnostic and copied into each successfully rewritten expression.
4. **Opaque 32-bit value.** Passed to the initial limit diagnostic. No other direct use is visible.

No ownership transfer of either top-level record is established.

### Representation and layouts

The supplied representation uses 32-bit words and addresses, one-byte flags, and byte offsets. Counts, limits, resolver results, and column-position comparisons are treated as signed 32-bit integers. Endianness is not established.

Only the following fields are relevant to the visible behavior; the function does not establish complete structure definitions.

| Record | Byte offset | Width | Observed role |
|---|---:|---:|---|
| Resolution-context record | 0 | 32 bits | Context address |
| Context | 30 | 8 bits | Gate controlling whether the resolver is called |
| Context | 88 | 32 bits | Maximum permitted ordering-term count |
| Query record | 0 | 32 bits | Result-list address |
| Query record | 28 | 32 bits | Ordering-list address, read from the starting query record |
| Query record | 32 | 32 bits | Link followed to find the initial component to process |
| Query record | 36 | 32 bits | Link followed between processed components |
| Ordering list | 0 | 32 bits | Term count |
| Ordering list | 12 | 32 bits | Term-entry array address |
| Result list | 0 | 32 bits | Available result-column count |

Each term entry occupies **12 bytes**:

| Entry offset | Width | Observed role |
|---|---:|---|
| 0 | 32 bits | Expression address |
| 10 | 8 bits | Resolution marker: zero means unresolved; nonzero means resolved |

Successful resolution writes the following expression fields:

| Expression offset | Width | Written value |
|---|---:|---|
| 0 | 8 bits | `0x95` |
| 36 | 32 bits | Third argument |
| 48 | 32 bits | `0xFFFFFFFF` |
| 40 | 32 bits | Resolved one-based column position minus one |
| 60 | 32 bits | Zero |

The listed expression writes occur in that order, not in ascending address order.

### Preconditions

For defined operation, all accessed records and arrays must remain valid for the accesses made. In particular:

- The starting query-record pointer must permit reading its ordering-list field, even when that field is null.
- If an ordering list exists, the resolution-context pointer and its referenced context must be valid.
- Positive term counts require a readable term-entry array and writable marker bytes.
- Expressions that resolve successfully must permit all five expression writes listed above.
- Traversed query records must permit the relevant link and result-list accesses.
- Address calculations for term entries must remain valid for the target execution model.

The function contains no visible protection against malformed pointers, cyclic links, undersized records, or invalid array extents.

## Behavior

### 1. Optional-list handling and limit check

The function first reads the ordering-list address from the starting query record.

If that address is null, it returns **0** immediately. It does not visibly read the context address, inspect component links, call dependencies, or modify records on this path.

Otherwise, it reads and retains the context address from the resolution-context record. It compares the context’s signed limit with the ordering list’s signed term count.

If the limit is less than the count:

- F-2022b0f73f3b is called with the resolution-context pointer, a diagnostic reference indicating excessive ordering terms, and the third and fourth arguments.
- The function returns **1**.
- No term-marker initialization has occurred.

Equality is permitted.

### 2. Marker initialization

For every term indexed from zero up to, but not including, the term count, the function writes zero to the entry’s marker byte.

Previously resolved markers are therefore discarded. The function does not restore the associated expression contents before attempting resolution again.

The count and entry-array address are accessed through the ordering-list record rather than established as immutable metadata. Normal fixed-count behavior requires those fields to remain stable.

### 3. Choosing the first component

Starting at the supplied query record, the function follows links at byte offset 32 until it reaches a record whose offset-32 link is null. That terminal record is processed first.

At least the starting record’s offset-32 link is examined whenever the ordering-list pointer is nonnull and the limit check passes.

There is no visible cycle detection or traversal bound. A cycle can prevent this phase from terminating.

### 4. Processing unresolved terms

Components are processed from the selected terminal record through their offset-36 links. Within a component, terms are considered in increasing index order.

A term with a nonzero marker is skipped. For a zero-marker term:

1. The function captures that term’s expression address.
2. It calls F-1a5398bcc6b3 with the retained context address and the captured expression address.
3. It reads the one-byte context field at offset 30 **after** that call.
4. If the byte is zero, it calls F-343f48b6323a with:
   - the resolution-context pointer;
   - the current query component;
   - the value returned by F-1a5398bcc6b3;
   - the one-based ordering-term position;
   - the integer value 1;
   - the integer value 0.
5. Whether or not the resolver was called, it calls F-841dc33ee157 with the value returned by F-1a5398bcc6b3.
6. It then interprets the resolver result, or the retained negative default when the resolver was skipped.

F-841dc33ee157 is thus called before the function handles a negative resolver result, checks the component’s result-list pointer, validates the returned position, or rewrites the original expression.

There is no visible null check on the value returned by F-1a5398bcc6b3 before passing it to the other dependencies.

### 5. Interpreting a resolution attempt

The attempt result has three behavioral classes.

**Negative result**

The function immediately returns **1** after the F-841dc33ee157 call.

When the context gate is nonzero, the resolver is skipped and the default negative result produces this failure path. This function does not issue its own diagnostic on that path.

**Nonnegative result**

The function reads the current component’s result-list pointer after the dependency calls.

- A null result-list pointer produces an immediate return of **1**, without a direct diagnostic call.
- If the signed result count is less than the attempt result, F-2022b0f73f3b is called with an out-of-range diagnostic reference, the one-based term position, and the available result count. The function then returns **1**.

This upper-bound comparison also applies to a result of zero. Consequently, a zero attempt result with a negative result count takes the out-of-range path rather than remaining unresolved.

**Zero result after passing the upper-bound check**

The term remains unresolved. Its expression is not directly rewritten, and processing is allowed to continue to another component after the current component has been scanned.

**Positive result after passing the upper-bound check**

The function writes the five expression fields specified in the interface, using the expression address captured before the dependency calls. It then writes 1 to the term entry’s marker byte.

The positive one-based result becomes a zero-based stored column index. Since the result is positive and signed 32-bit, subtracting one is within the signed 32-bit range.

### 6. Continuing or stopping component traversal

The function scans every term in the current component unless an immediate failure occurs.

It proceeds to another component only when at least one attempted term in the current component returned zero after passing validation. Already resolved terms are not attempted again.

The next component address is read from the current component’s offset-36 field at the end of a normally completed component scan. That link read occurs even if all terms are now resolved and the next component will not be processed.

The two link directions are not validated as inverses. The function does not prove that offset-36 traversal visits exactly the records encountered during offset-32 traversal, nor that a component belongs to the same logical query.

### 7. Final unresolved-term check

After component processing stops, the function scans term markers in increasing index order.

At the first zero marker, it calls F-2022b0f73f3b with a diagnostic reference indicating that the ordering term does not match, together with that term’s one-based position. It returns **1** immediately.

If no zero marker is found, it returns **0**.

For a stable zero or negative term count that passes the initial limit comparison, all term loops are skipped. The function still performs the initial component-link traversal and a component-end offset-36 link read, then returns **0**. This is observed loop behavior, not evidence that negative counts are valid input.

## Side effects

### Direct mutations

The function directly modifies:

- Every term marker during initialization.
- Selected fields of expressions that resolve to valid positive positions.
- The marker of each successfully rewritten term.

It does not visibly modify the query links, result-list pointers, result counts, or context gate itself. Dependencies may do so; their preservation behavior is not established.

### Failure is not transactional

There is no rollback.

A failure can leave:

- All original term markers cleared.
- Earlier terms rewritten and marked resolved.
- Later terms unresolved.
- Any dependency-produced changes intact.

The function does not restore earlier expression contents or markers when a later term fails.

### Dependency-visible ordering and ownership

Every attempted unresolved term produces one F-1a5398bcc6b3 call and one subsequent F-841dc33ee157 call on its returned value. The resolver call, when enabled, occurs between them.

The names and signatures alone do not establish allocation, cloning, ownership transfer, or release semantics. In particular:

- It is not established that F-1a5398bcc6b3 returns a distinct object.
- It is not established that F-841dc33ee157 releases memory.
- It is not established that dependencies preserve the original expression, term array, query records, context fields, or other shared state.
- The captured expression must remain usable for any subsequent rewrite, regardless of what the intervening dependencies do.

## Acceptance examples

These are conditional acceptance cases derived from static behavior, not executed tests. Unless stated otherwise, records are valid, counts and links remain stable, the context gate is zero, and dependencies introduce no mutations that alter the described flow.

1. **Absent ordering list.**  
   A null ordering-list field produces status **0**, with no dependency calls or direct writes.

2. **Limit exceeded.**  
   A limit of 2 and term count of 3 produces the excessive-term diagnostic call and status **1**. Existing marker bytes remain unchanged.

3. **Exact limit and successful positions.**  
   With limit 2, count 2, result count 4, and resolver results 4 and 1, both terms resolve. Their stored column indices become 3 and 0. Both receive the third argument at expression offset 36 and a marker of 1. Status is **0**.

4. **Resolution across components.**  
   For two unresolved terms, suppose the first processed component returns 0 for the first term and 2 for the second. The second term is rewritten immediately. If the next component returns 1 for the first term, only that unresolved term is attempted there. Both markers end at 1 and status is **0**.

5. **Positive position beyond the result count.**  
   A resolver result of 4 with result count 3 produces an out-of-range diagnostic and status **1**, after F-841dc33ee157 has been called. That attempt does not directly rewrite its expression.

6. **Resolver disabled by the context gate.**  
   If the gate is nonzero after F-1a5398bcc6b3 returns, F-343f48b6323a is not called. F-841dc33ee157 is called, followed by status **1**.

7. **Null result list after a zero result.**  
   A resolver result of 0 does not bypass result-list validation. A null result-list pointer produces status **1** rather than continuing to another component.

8. **Exhausted components.**  
   If a term repeatedly returns 0 and the offset-36 chain ends, the final scan reports the first still-unresolved term by one-based position and returns **1**.

9. **Partial failure.**  
   If the first term resolves and the second returns a negative result, status is **1**, but the first term’s rewritten fields and marker remain committed.

10. **Empty list.**  
    With count 0 and a nonnegative limit, there are no term dependency calls or marker writes. Component-link traversal still occurs. With valid terminating links, status is **0**.
