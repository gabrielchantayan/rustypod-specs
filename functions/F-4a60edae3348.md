# F-4a60edae3348

## Purpose

F-4a60edae3348 adds one 16-bit value to a descriptor-managed sequence, either by using an available slot or by entering a capacity-management path.

The ordinary interpretation is an append operation on contiguous 16-bit elements. That interpretation is supported by the descriptor layout, two-byte cursor movement, and allocation-growth calculation. It is not a complete description of all observable behavior: the capacity-management path calls dependencies whose effects are unknown, and its non-growing alternative contains a backward-copy loop that is problematic when the saved insertion position remains equal to the descriptor’s end.

This contract describes the visible operations without assuming that dependencies are pure, preserve descriptor fields, copy ranges successfully, or implement conventional ownership rules.

## Interface

**Inputs**

- A pointer to a writable descriptor containing at least three consecutive 32-bit fields.
- A pointer identifying a source value occupying 16 bits.

The descriptor fields are interpreted as follows:

| Byte offset | Width | Role |
|---|---:|---|
| 0 | 32 bits | Storage-base address |
| 4 | 32 bits | Logical-end address |
| 8 | 32 bits | Storage-limit address |

The visible representation uses 32-bit addresses. Elements occupy two bytes. End and limit are address values, not element counts.

**Output**

There is no explicit return value. Results are communicated through descriptor updates, writes to element storage, and dependency effects.

**Ordinary representation preconditions**

For conventional sequence behavior, the descriptor should describe a contiguous, two-byte-aligned region in which:

- Base does not follow logical end.
- Logical end does not follow storage limit.
- Both occupied length and capacity are multiples of two bytes.
- Logical elements occupy the half-open range from base to logical end.
- Unused storage occupies the half-open range from logical end to storage limit.

These conditions are inferred representation requirements, not validated conditions. The function does not check them.

The source must be readable whenever a path actually dereferences it. The descriptor must remain valid for each field access. Destination storage must be writable wherever an element write occurs. Dependencies can change which addresses are subsequently accessed.

The source is not visibly consumed or released. Aliasing between the source, descriptor, and storage is not prohibited by a check, but it can affect the value read and the resulting state.

## Behavior

### 1. Entry decision and available-slot path

The function first obtains the descriptor’s logical-end address and compares it with the storage-limit address. The saved logical end is also the insertion position used later in this invocation.

If these addresses differ, the function:

1. Stores the saved end address plus two bytes into the descriptor’s logical-end field.
2. If the saved end address is nonzero, reads the 16-bit source value and writes it at that saved address.
3. Returns.

The descriptor update precedes the source read and element write. Consequently, a source that aliases bytes of the logical-end field can observe the updated field rather than its entry value.

Only equality is tested. This path does not establish that end is below limit or that two writable bytes remain. A malformed descriptor whose end exceeds its limit still takes this path.

If the saved end is zero and differs from the limit, the descriptor end is advanced to address two, but neither the source nor the destination is dereferenced on this path. This is a visible null-destination guard, not a general allocation or validity check.

No dependency is called on the available-slot path.

### 2. Decision when entry end equals limit

When the entry logical end equals the entry storage limit, the function saves the descriptor’s base and limit before calling F-421ee22ef2f3 with the descriptor.

A capacity-like comparison value is derived from the saved addresses:

- Subtract saved base from saved limit using the represented 32-bit arithmetic.
- Apply the signed right shift by one represented in the supplied evidence.
- Interpret that result as unsigned for comparison with the dependency’s 32-bit unsigned result.

For an ordinary valid descriptor with a nonnegative, even byte span, this is the storage capacity in 16-bit elements. That ordinary interpretation must not be extended to negative, misaligned, or overflowing spans.

If the saved capacity-like value is less than or equal to the dependency result, execution takes the growth path. Otherwise, it takes the non-growing backward-copy path.

The comparison uses address fields captured before the dependency call. Later operations can use descriptor fields read after that call. Changes made by the dependency therefore need not affect these two parts consistently.

### 3. Growth path

#### Capacity selection

F-421ee22ef2f3 is called again. Its second result is independently obtained; it is not assumed to equal the first.

Treating this second result as an unsigned 32-bit quantity, the function calculates two candidate element counts:

- The result plus 32.
- The result plus its unsigned right shift by one, plus its unsigned right shift by three.

Each addition follows 32-bit unsigned arithmetic. The selected count is the unsigned maximum of the two candidates.

For ordinary non-overflowing values, the second candidate is the result plus one-half and one-eighth, with each fractional contribution rounded down independently. It is not generally identical to multiplying by 13 and then dividing by 8.

The selected count is shifted left by one to obtain the allocation request in bytes. That shift is also 32-bit arithmetic. There is no overflow or maximum-capacity check.

#### Allocation and transfer sequence

The function calls F-871e64ddc6de with:

- The calculated byte count.
- A second argument equal to zero.

The returned 32-bit value is used as the new storage address. No success test is performed.

An unresolved range dependency is then called with four arguments:

- The descriptor’s base as read after allocation returns.
- The insertion position saved at entry.
- The returned new storage address.
- The descriptor pointer.

The identity and semantics of this dependency are not supplied. In particular, calling it a copy, move, construction, or relocation operation would exceed the established evidence.

After it returns, the function computes a destination address by subtracting the descriptor’s then-current base from the saved insertion position, clearing the low bit of that difference, and adding the new storage address.

If this computed address is nonzero, the function reads the 16-bit source value and writes it there. If the address is zero, both the source read and this write are skipped.

The low-bit clearing is a mask on a byte difference. For a valid two-byte-aligned sequence it leaves the difference unchanged; for malformed or changed state it rounds that represented difference down to an even value. It does not validate the address.

The unresolved range dependency is called a second time with:

- The insertion position saved at entry.
- The descriptor’s current logical end.
- A destination recomputed from the saved insertion position, the descriptor’s current base, and the new storage address, then advanced by two bytes.
- The descriptor pointer.

The second destination is not specified to reuse the address from the preceding element write. The expression is evaluated again after that write, so aliasing or dependency-induced descriptor changes can matter.

#### Retirement and descriptor replacement

After the second range call, the function calls F-421ee22ef2f3 a third time and saves its result for the final logical-end calculation.

It then reads the descriptor’s current base and performs an empty traversal:

- The traversal address begins at that base.
- Each step adds two bytes.
- Termination requires equality with the descriptor’s logical end.

The traversal contains no element read, element write, destructor call, or dependency call. Its visible significance is control flow and repeated consultation of the logical-end field. If the end cannot be reached by two-byte increments in the represented address space, the traversal does not terminate.

F-ff1bdc376dcd is then called with:

- The base captured immediately before the traversal.
- The current storage-limit-minus-that-base difference, shifted right by one.
- A third argument equal to zero.

No return value is used.

Only after that call returns does the function replace the descriptor fields, in this order:

1. Base becomes the new storage address.
2. Logical end becomes the new storage address plus twice the saved third result of F-421ee22ef2f3, plus two bytes.
3. Storage limit becomes the new storage address plus twice the selected capacity.

These final address calculations are represented through 32-bit quantities. The evidence supplies no checked-overflow behavior.

Under conventional, non-mutating dependency behavior, this sequence is consistent with transferring existing elements, appending the source element, retiring old storage, and publishing the replacement storage. Those dependency semantics remain conditional.

### 4. Non-growing backward-copy path

This path is reached only when the first dependency result is strictly smaller, in unsigned comparison, than the saved capacity-like value.

The function rereads the descriptor’s logical end. It then:

1. Advances that field by two bytes.
2. If the reread old end is nonzero, copies the 16-bit element immediately before that old end into the old-end slot.
3. Initializes a backward source position to one element before the reread old end.
4. Until that backward source position equals the insertion position saved at entry, moves both copy positions backward by one element and copies the 16-bit source element to the destination.
5. After the loop terminates, reads the supplied source value and writes it at the saved insertion position.

The initial end update occurs before any element copy. The initial predecessor copy is guarded by a nonzero destination test; the loop’s copies and final source write are not.

If the current descriptor end has become greater than the saved insertion position by a positive whole number of elements, and all affected storage is valid, this sequence shifts that suffix right by one element and writes the new value at the insertion position.

There is a critical contrary case: if the dependency leaves the end unchanged, the saved insertion position equals the reread old end. The loop starts one element before that position and decrements farther before each loop copy. It does not terminate immediately and is not a conventional empty-suffix append. There is no lower-bound check; termination would require eventual address equality, potentially through address wraparound, while intervening accesses can be invalid.

The evidence therefore does not justify describing this branch as safe for an unchanged, full descriptor whose helper result merely happens to be smaller than capacity.

## Side effects

**Descriptor writes**

- Available-slot path: logical end only.
- Growth path: dependencies may make unknown changes; the function itself ultimately overwrites base, end, and limit in that order.
- Non-growing path: logical end is advanced before element movement.

There is no rollback mechanism in the visible body.

**Storage writes**

The function writes 16-bit elements. Growth can additionally cause dependency-defined writes. No element-level destruction is visible in the empty traversal.

**Ownership**

The growth path passes a storage address and an element-count-like value to F-ff1bdc376dcd before publishing the replacement descriptor. This suggests retirement of old storage, but actual release behavior is unknown.

The function does not itself establish whether the allocator grants ownership, whether range operations transfer ownership, or whether the retirement dependency invalidates the supplied address. No ownership guarantee may be inferred solely from the call sequence.

**Failure and partial state**

There is no explicit status result, allocation-failure branch, exception handler, or compensating cleanup.

A failure during an element access can occur after logical end has already changed. A dependency failure or non-return can leave any preceding allocation, transfer, or mutation in effect. A zero allocation result is used in subsequent address arithmetic and dependency calls rather than rejected.

No direct global access is visible, but dependency effects on globals are unknown. Atomicity, synchronization, and concurrent-use safety are not established.

## Acceptance examples

These examples are conditional consequences of the visible behavior, not runtime observations.

1. **One available slot.** Base is address 4096, end is 4100, limit is 4104, and the source holds `0x1234`. With valid non-aliasing storage, end becomes 4102 and the element at address 4100 becomes `0x1234`. Base and limit remain unchanged. No dependency is called.

2. **Null available-slot destination.** End is zero and limit is two. The function sets end to two and returns without reading the source. This example does not assert that such a descriptor is a valid sequence.

3. **Conventional growth from four elements.** Base is 4096, end and limit are 4104. Assume all three calls to F-421ee22ef2f3 return four without modifying state; allocation returns 8192; range operations perform the expected transfers without descriptor mutation; retirement returns normally. The selected capacity is 36 elements and the allocation request is 72 bytes. The source element is written at 8200. Final base, end, and limit are 8192, 8202, and 8264.

4. **Rounding at a small growth basis.** If the second helper result is seven, the two candidates are 39 and 10, so the selected capacity is 39. The proportional candidate is 10, not 11.

5. **Unsigned growth overflow.** If the second helper result is `0xFFFFFFFF`, the plus-32 candidate wraps to 31 and the other candidate becomes `0x9FFFFFFD`. The selected element count is `0x9FFFFFFD`; its doubled byte request wraps to `0x3FFFFFFA`. The function has no visible rejection of this result.

6. **Backward insertion after dependency mutation.** Entry end equals limit at 4104. Suppose the first helper makes the current descriptor end 4108 and returns a value below the previously captured capacity. With sufficient writable storage, the branch shifts elements at 4104 and 4106 to 4106 and 4108, writes the supplied value at 4104, and leaves end at 4110.

7. **Backward branch without end mutation.** Entry end equals limit, and the first helper returns less than captured capacity while leaving end unchanged. The backward loop does not represent a zero-element shift. Acceptance must not require normal successful append for this case without additional dependency invariants.

## Evidence

The established evidence is the supplied static function body and its private dependency-to-opaque-ID mapping.

That evidence directly supports the three-field layout, 16-bit element operations, branch comparisons, dependency-call sequence, growth arithmetic, conditional destination guards, backward movement, empty traversal, and final descriptor-write order.
