# F-820d34f1a0c3

## Purpose

F-820d34f1a0c3 transforms a value stored as an array of 32-bit words by discarding low-order bits, writes the result to a destination object, and removes high zero words from the destination’s recorded active count.

**Established static behavior:** For nonnegative shifts and suitable counts, lower-indexed words supply lower-order bits. The transformation uses logical shifts of unsigned 32-bit words. Identical source and destination objects are supported, subject to storage validity.

**Inferred intent:** The objects resemble multiprecision integer containers, and the transformation resembles a magnitude right shift. The fourth object field is copied on the distinct-object path, but its meaning is not established. Its presence does not establish signed arithmetic-shift semantics.

The mathematical interpretation is conditional. A dependency can change the source count after the initial branch decisions. The resulting provisional destination count can be negative even when both the original and replacement source counts are nonnegative. Such executions have specific storage effects described below; they are not ordinary magnitude shifts.

The function also accesses storage outside the recorded result range. In particular, the word-aligned path copies an extra source word when the provisional count is nonnegative, then writes an additional zero.

## Interface

### Arguments and layout

The function receives:

1. A destination-object address.
2. A source-object address.
3. A signed 32-bit shift amount.

Each object exposes four consecutive 32-bit fields:

| Byte offset | Width | Observed role |
|---|---:|---|
| 0 | 32 bits | Word-storage address |
| 4 | 32 bits | Signed active-word count |
| 8 | 32 bits | Signed capacity-related value |
| 12 | 32 bits | Metadata copied for distinct objects |

Storage consists of 32-bit words spaced four bytes apart. The stored addresses and address calculations belong to the represented 32-bit environment. This layout is not a native-pointer layout guarantee for other environments.

The capacity-related field is compared with a requested word count. Neither its allocation units nor its exact relationship to physically accessible storage is established.

### Result

The function returns a 32-bit value:

- **1:** Normal completion, including normal return from the clearing dependency, the identical-object zero-shift fast path, and transformation paths that retain a negative count.
- **0:** The capacity dependency returns null on the distinct-object path.

The clearing dependency’s return value is ignored. Return 1 does not independently certify successful clearing, a nonnegative result count, adequate allocation, or satisfaction of an external object invariant.

### Conditions for the bounded descriptions

The storage and count descriptions below assume:

- Valid readable object fields and writable destination fields.
- Representable signed count calculations, including the capacity request and the aligned loop’s count-plus-one calculation.
- Valid address calculations and readable or writable storage for every access actually performed.
- For unequal object addresses, disjoint complete 16-byte object records.
- All accessed storage disjoint from both object records.
- Either disjoint source and destination storage, identical-object storage, or an independently established overlap arrangement that cannot corrupt a source word before its read.
- No concurrent modification of the objects or accessed storage.
- Dependencies returning normally leave the subsequently accessed state satisfying these conditions.

These are conditions on callers and dependency effects, not validations performed by this function.

For the ordinary magnitude-shift interpretation, additionally require a nonnegative shift and a source count at the transformation-stage reread that is at least the whole-word displacement. An initially sufficient count does **not** establish that later condition.

The negative-provisional-count behavior below does not require that additional count condition. It still requires representable calculations and validity of its actual accesses.

## Behavior

### Shift decomposition and initial clearing decision

The signed shift amount is separated into:

- A whole-word displacement equivalent to division by 32 with truncation toward zero.
- A signed remainder modulo 32, stored in an unsigned 32-bit quantity.

For nonnegative shifts, the displacement is nonnegative and the remainder lies between 0 and 31.

Before the object-identity fast path, the function checks the source count. If it is strictly less than the displacement, or is zero, the function calls **F-d4e7c5a40239** with the destination and zero.

If that dependency returns normally, this function returns 1. It does not inspect the dependency’s result or proceed to metadata copying, capacity handling, transformation, or normalization.

Equality with a positive source count does not select clearing. A positive count exactly equal to the displacement can therefore reach transformation with a provisional count of zero.

### Identity and capacity handling

If clearing was not selected and the object addresses are identical:

- A zero shift returns 1 immediately.
- Any other shift proceeds without metadata copying or capacity handling.

The identical-object zero-shift path does not normalize the count, inspect storage words, or write a trailing zero.

For distinct objects, the observable order is:

1. Read the source metadata field and assign it to the destination metadata field.
2. Compare the destination capacity-related field with the source count minus the displacement, plus one.
3. If the capacity-related value is smaller, call **F-08bc2fc94856** with the destination and that requested count.
4. If the dependency returns null, return 0.

The metadata assignment precedes any capacity call and is not rolled back on failure. Dependency-side changes are likewise not rolled back.

A nonnull dependency result permits continuation; it does not replace the original destination argument.

The function does not reapply the initial clearing decision after the capacity call. In particular, a dependency can reduce the source count below the displacement, including to zero, and execution still proceeds to transformation.

### Establishing transformation state

After identity and capacity handling, the function:

1. Reads the source storage address and forms a source position displaced by four bytes per whole-word displacement.
2. Rereads the source count and subtracts the displacement.
3. Writes that difference into the destination count field.
4. Performs the storage transformation.

Call this difference the **provisional count**, denoted *n* below.

The source position is established before the destination count assignment. The count used here is the later source-count read, not a saved value from the initial clearing or capacity decisions.

A successful capacity call does not imply *n* is nonnegative. For example, a displacement of two words and a post-call source count of zero produce *n* = −2. This does not select clearing.

### Word-aligned transformation

When the remainder is zero, the destination storage address is read after the provisional count assignment.

For **n ≥ 0**:

- Displaced source words 0 through *n*, inclusive, are copied to destination words 0 through *n*.
- Copying proceeds in increasing index order.
- Each source word is read before its corresponding destination write.
- Destination word *n* + 1 is then written as zero.

This copies *n* + 1 words, not *n* words.

If the source count remains unchanged at *L*, the final copied source word is source word *L*: the word immediately beyond the recorded active range.

The destination therefore requires *n* + 2 writable words. A distinct-object capacity request computed from the same unchanged count is only *n* + 1. The dependency contract supplied here does not establish that this request guarantees the additional writable word.

For **n < 0**:

- No source word is read by the copying loop.
- No copied-word write occurs.
- Destination word 0 is written as zero.

For negative *n*, the explicit zero is **not** placed at word *n* + 1. The destination write position has not advanced because the copying loop performs no iterations.

For **n = 0**, one source word is still copied to destination word 0, followed by zero at destination word 1.

### Non-word-aligned transformation

For a remainder from 1 through 31, the function first reads the word at the displaced source position. It then reads the destination storage address.

For **n > 0**:

- Exactly *n* source words are read.
- Each output except the last combines the current source word shifted logically right by the remainder with the next source word shifted left by 32 minus the remainder.
- The next source word is read before the corresponding destination write.
- The final output is the final source word shifted logically right by the remainder.
- Destination word *n* is written as zero after the transformed words.

All word shifts and bitwise combinations operate on unsigned 32-bit values.

For **n ≤ 0**:

- The first displaced source word is still read.
- Its logically right-shifted value is written to destination word 0.
- Destination word 1 is written as zero.
- No additional source word is read.

Thus zero or negative recorded counts do not suppress this path’s first source read or shifted-word write.

### Normalization

After the transformed-word writes and explicit zero write, the function reads the destination count.

If that count is positive, it forms a traversal position from the destination storage address and count, then scans downward through the recorded active words:

- Encountering a nonzero word returns 1 immediately.
- Encountering zero causes another destination-count read and a decrementing count write.
- Reaching count zero completes with return 1.

Under the record/storage separation conditions, normalization changes only the count. It does not clear every excluded word or move the previously written trailing zero.

If the count is zero or negative, normalization performs no storage scan and no count decrement.

Consequently, under those separation conditions, a negative provisional count remains negative on return. The aligned and nonaligned negative-count paths both return 1 after their respective storage writes.

## Side effects

### Destination state

Depending on the selected path, the function may:

- Delegate destination changes to F-d4e7c5a40239.
- Copy the source metadata field.
- Permit F-08bc2fc94856 to mutate accessible state.
- Write the provisional count before transforming any word.
- Write transformed words, an aligned boundary copy, and an explicit zero.
- Decrease a positive count during normalization.
- Return with a negative count unchanged after transformation.

A distinct-object zero shift is not equivalent to the identical-object fast path. It can copy metadata, request capacity, copy a boundary word, write an additional zero, and normalize.

### Source preservation and overlap

Unequal object addresses do not establish disjoint records or storage.

With disjoint records and accessed storage disjoint from both records, this function’s own destination writes do not modify the distinct source record. This statement does not constrain dependency behavior or guarantee preservation of overlapping source storage.

If the records overlap, metadata copying or count assignment can directly modify source fields. For example, when the source record begins four bytes after the destination record, the destination metadata field occupies the source capacity-related field.

Storage overlapping either record can cause transformed-word writes to alter fields that are read later. Count-field writes can also alter storage. The function performs no general overlap check.

With valid separated records and storage, identical-object forward traversal supports the ordinary in-place right shift. Other storage overlaps require separate analysis of whether earlier destination writes affect later source reads.

### Ownership and failures

No direct allocation or release operation appears in this function. Dependencies may manage storage, but ownership transfer, old-storage lifetime, alias preservation, release behavior, and global effects are not established.

There is no explicit rejection of negative shifts, negative counts, null addresses, insufficient storage, inconsistent capacities, harmful overlap, or overflowing arithmetic. Invalid accesses and unsupported arithmetic are not converted into defined error returns.

The explicit null-result capacity failure is partial, not atomic: metadata copying has already occurred, and dependency mutations may also have occurred.

## Acceptance examples

These are conditional static criteria, not executed tests. Arrays list words from lowest to highest index. Except where stated otherwise, assume representable arithmetic, valid separated records, adequate actual storage, a nonnegative shift, and dependencies preserving the stated source state.

### Cross-word combination

For active source words `[0x00000001, 0x00000001]`, count 2, and shift 1:

- The provisional count is 2.
- Destination words 0 and 1 become `0x80000000` and zero.
- Destination word 2 is written as zero.
- Normalization reduces the count to 1.
- The return value is 1.

### Aligned boundary copy

For source count 2, active words `[0x11223344, 0x55667788]`, source boundary word `0xA5A5A5A5`, and shift 32:

- The provisional count is 1.
- Destination words 0 and 1 become `0x55667788` and `0xA5A5A5A5`.
- Destination word 2 is written as zero.
- The final count is 1 and the return value is 1.

Three destination words must be writable, although a capacity request based on the unchanged source count is two.

### Displacement equal to count

For source count 1 and shift 32:

- Clearing is not selected.
- The provisional count is zero.
- The source boundary word is copied into destination word 0.
- Destination word 1 is written as zero.
- Normalization does not inspect word 0.

For shift 33, destination word 0 instead receives the boundary word logically shifted right by one. Destination word 1 is still zeroed, and the recorded count remains zero.

### Dependency reduces the count: aligned case

Suppose the objects are distinct, the initial source count is 3, the shift is 64, and the destination capacity-related value is below 2.

If F-08bc2fc94856 returns nonnull after setting the source count to zero, while leaving the required records and destination storage valid:

- The initial clearing decision is not repeated.
- The provisional count becomes −2 and is written to the destination.
- The displaced source position is formed, but the aligned loop reads no source words.
- Destination word 0 is written as zero.
- No zero write occurs at destination word −1.
- Normalization is skipped.
- The final count is −2 and the return value is 1.

### Dependency reduces the count: nonaligned case

Under the preceding conditions, use shift 65 and make the displaced source word readable with value `0x80000003`.

After the dependency reduces the source count to zero:

- The provisional count is −2.
- The displaced word is read despite that negative count.
- Destination word 0 becomes `0x40000001`.
- Destination word 1 is written as zero.
- Normalization is skipped.
- The final count is −2 and the return value is 1.

### Clearing and identity precedence

For source count 1 and shift 64, the clearing dependency receives the destination and zero. Metadata copying and capacity handling are bypassed.

For identical objects with count zero and shift zero, clearing still takes precedence.

For identical objects with positive count and shift zero, the function instead returns 1 without copying, normalization, metadata assignment, or explicit zero writing.

### Capacity failure

For distinct objects whose required capacity call returns null:

- Metadata has already been copied.
- This function returns 0 before its provisional-count assignment and transformation writes.
- Dependency-side mutations remain possible.

### Overlapping records

If the source record begins four bytes after the destination record, a source metadata value of `0x13579BDF` is written into the source capacity-related field by the destination metadata assignment.

This establishes a direct source-field mutation, not an eventual shifted result or return value. Subsequent behavior depends on the remaining overlapping state.

## Uncertainties

The following remain **documented_only**:

- The metadata field’s semantic meaning.
- Physical allocation sizes and spare-word conventions.
- Whether source boundary words are normally zero.
- The reason for the aligned extra-word copy.
- Whether the capacity dependency provides storage beyond its numeric request.
- Dependency effects on records, storage, globals, ownership, and aliases.
- General outcomes for overlapping records or storage intersecting records.
- Outcomes involving invalid addresses or overflowing calculations.
- Portable results for negative shifts.

Negative provisional counts are not inherently unresolved: their aligned and nonaligned storage effects are specified above when the stated access and arithmetic conditions hold. What remains unresolved is whether external object contracts permit those returned states.

For a negative shift, a negative signed remainder becomes a large unsigned 32-bit value. The shift-count expressions retain only their low eight bits, which does not guarantee a count below 32. The supplied static representation does not establish portable results for oversized shift counts. A negative displacement may also form a source position before the nominal storage base. No opposite-direction shift behavior is promised.
