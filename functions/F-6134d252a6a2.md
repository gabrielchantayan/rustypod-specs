## Behavior

### Entry comparison and unchanged-value path

The function first reads the selected field and compares its integer value with the requested value.

If they are equal:

- The function returns normally.
- Neither dependency is called.
- No direct field writes occur.
- The first and second result fields are not read or validated.

Consequently, matching selected and requested values are sufficient to suppress refresh, even when either result field is stale, uninitialized, or inconsistent according to some external domain rule. Such a rule is not implemented here.

This path still requires the initial read. It is not safe for an invalid storage reference merely because the caller expects the values to match.

### Update path and observable ordering

If the entry comparison is unequal, the direct operations and dependency calls have the following order:

1. The requested value is written to the selected field.
2. F-cb3a86d90510 is called with the requested value.
3. After that dependency returns, its integer result is written to the first result field.
4. The selected field is read again.
5. F-34aa873d95ea is called with the value obtained by that fresh read.
6. After that dependency returns, its integer result is written to the second result field.
7. The function returns normally.

This ordering establishes several important distinctions.

**The first dependency receives the requested value, not a fresh field read.** Its argument does not depend on whether the selected field subsequently changes.

**The second dependency receives a freshly read selected value.** That value need not equal the original request. F-cb3a86d90510 could affect the selected field through shared state, reentrancy, or another alias if the surrounding program allows such access.

**The first result is stored before the second dependency runs.** A second dependency that can observe the same storage may therefore observe that completed store, subject to the actual execution and memory model.

**Each result is stored after its producing call returns.** If a dependency modifies its corresponding destination field during the call and then returns normally while leaving the destination valid, the wrapper’s subsequent result store supersedes that modification at that field. This does not imply that other dependency effects are undone.

### Normal completion guarantees

If all accesses are valid and both dependencies return normally:

- The first result field receives the result returned by F-cb3a86d90510.
- The second result field receives the result returned by F-34aa873d95ea.
- The function performs no further direct write after storing the second result.

The first result field is not guaranteed to retain its stored result at function exit: the second dependency runs afterward and might modify it. Likewise, the selected field is not guaranteed to retain the requested value if a dependency can modify it.

Under the additional assumption that neither dependency changes the caller’s storage and there are no interfering accesses, normal completion leaves the selected field equal to the requested value and the two result fields equal to their respective dependency results.
