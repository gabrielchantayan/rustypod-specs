# F-91f4b2cc2046

## Purpose

F-91f4b2cc2046 routes a supplied object through either an explicitly selected recipient or a fallback sequence of recipients. On normally returning paths, it invokes a final operation on the supplied object when that object is non-null.

The two routing modes have different result contracts:

- **Explicit-recipient mode:** selects one of two operations using an identity comparison and returns exactly **1**, irrespective of the selected operation’s return value.
- **Fallback mode:** visits an optional preliminary collection, then potentially follows a recipient chain. It returns the first nonzero handling result, or zero if no attempted recipient produces one.

“Recipient,” “supplied object,” “handling,” and “final operation” are descriptive roles, not established application-level types. In particular, the final operation might release a reference or perform another lifecycle action, but its ownership meaning is not established.

This contract describes the supplied static representation. It does not establish runtime validity, concurrency safety, or the internal behavior of dependencies.

## Interface

### Input record

The function accepts one 32-bit address identifying an input record. Two 32-bit pointer fields are read, in this order:

| Byte offset | Role |
|---|---|
| +12 | Explicit-recipient pointer |
| +16 | Supplied-object pointer |

Both values are captured before dependency calls. The function does not subsequently reload these fields from the input record.

The input-record address is not checked for null or validity. Both fields must be readable for defined execution of the represented accesses.

### Return value

The return value is a 32-bit integer:

- Explicit-recipient mode returns 1 after its selected operation and any applicable final object operation return normally.
- Fallback mode returns a recipient callback’s exact nonzero 32-bit result, or zero.
- Nonzero results are not normalized to 1 in fallback mode. Negative values qualify as nonzero and are returned unchanged.
- Dependency failures, invalid accesses, and nonlocal exits have no separately represented error return.

### Object layout and indirect calls

The representation uses 32-bit pointers and four-byte table entries. Each object used for indirect dispatch has an operation-table pointer at byte offset 0.

The following operation-table byte offsets are observable:

|---|---:|---|---|

| Supplied object | +28 | Supplied object | Ignored |

### Other relevant layouts

An explicit recipient exposes a readable 32-bit identity field at byte offset +16.

A context obtained through F-3fdd14ecd250 exposes:

- A 32-bit chain-head pointer at +40.
- A 32-bit preliminary-collection reference at +44.

A chain recipient exposes a 32-bit associated pointer at +12. When filtering mode is active, a 32-bit field at offset +12 within that associated object is read as a zero/nonzero flag.

The function also reserves 20 bytes of local iterator storage. Its internal layout is not established.

## Behavior

### 1. Capture the input pointers

The explicit-recipient pointer is read first, followed by the supplied-object pointer.

A non-null explicit recipient selects explicit-recipient mode. A null explicit recipient selects fallback mode. There is no fallback after an explicit-recipient operation has been selected.

### 2. Explicit-recipient mode

The function reads the explicit recipient’s 32-bit identity field at +16, then calls F-f4c5ae40135d with no explicit arguments.

The identity field is sampled **before** that dependency runs. Changes to the field during the call do not change the already captured comparison operand.

The two 32-bit values are compared for equality:

- **Equal:** invoke the explicit recipient’s table operation at +48, passing the explicit recipient and the captured supplied-object pointer.
- **Unequal:** invoke the supplied object’s table operation at +28, passing that object.

The unequal case does not check whether the supplied object is null before dereferencing it for dispatch. A null supplied object therefore does not have an established normally returning behavior on this path.

After the selected operation returns, a non-null supplied object receives its table operation at +4. The function then returns exactly 1.

Consequences:

- The selected operation’s result cannot cause fallback routing.
- A zero result from the explicit recipient’s operation does not change the final return value.
- A null supplied object can be passed to the explicit recipient in the equal case. Whether that callback accepts null is unknown.
- The final operation is looked up after the selected operation returns. No supplied-object operation table is cached across those calls.

### 3. Preliminary collection in fallback mode

The handling result begins at zero.

The function calls F-3fdd14ecd250 and reads the returned context’s field at +44. A zero field skips preliminary collection processing.

For a nonzero field:

1. The context field at +44 is read again for iterator initialization.
2. F-538044b67754 receives the local iterator storage, the reread collection reference, and the 32-bit value `0xFFFFFFFE`, equivalent to signed −2.
3. F-6e4651b532dc is called with the iterator storage and an output slot for a recipient pointer.
4. A zero return from F-6e4651b532dc ends enumeration.
5. A nonzero return causes dispatch to the yielded recipient’s table operation at +52, passing that recipient and the captured supplied-object pointer.
6. A zero recipient result requests another enumeration step. A nonzero recipient result stops enumeration.

There is no explicit null check on a yielded recipient before its operation table is accessed.

F-944b595e25e9 receives the iterator storage on both normal enumeration exits:

- Enumeration reports zero.
- A recipient reports nonzero.

If a recipient reported nonzero, that exact result is retained, iterator cleanup runs, and chain routing is skipped.

If enumeration reports zero, iterator cleanup runs before chain setup. The cleanup operation’s return value is not used.

This function does not distinguish “enumeration exhausted” from any dependency-specific error that F-6e4651b532dc might also represent with zero.

### 4. Chain setup

If preliminary routing did not produce a nonzero result, the function calls F-3fdd14ecd250 again and reads the returned context’s chain-head field at +40.

This is a fresh context acquisition. The function does not assume it returns the context used for preliminary collection processing.

The chain head is captured **before** any supplied-object classification callback:

- If the supplied object is null, filtering mode is inactive.
- Otherwise, its table operation at +20 is invoked.
- Filtering mode is active exactly when the low 32 bits of that operation’s represented 64-bit result are nonzero.

The high 32 bits of this represented return do not affect a dispatch decision, the final result, or chain selection in the supplied representation. Likewise, an internal upper-half seed used on the null-object path has no established externally meaningful effect.

Even a null chain head does not suppress the supplied-object classification call when the supplied object is non-null.

### 5. Chain traversal

Traversal stops when the current recipient is null or a handling result is nonzero.

For each non-null current recipient:

**When filtering mode is inactive:**

- Invoke the recipient’s table operation at +48 with the recipient and supplied object.
- Do not perform the associated-object flag read or call F-35b8bd5fa9e0 for this eligibility decision.

**When filtering mode is active:**

- Read the recipient’s associated pointer at +12.
- Read the 32-bit flag at offset +12 within that associated object.
- If the flag is zero, invoke the recipient’s +48 operation without calling F-35b8bd5fa9e0.
- If the flag is nonzero, call F-35b8bd5fa9e0 with the supplied object.
  - A nonzero result permits the recipient’s +48 operation.
  - A zero result skips that operation and leaves the handling result zero.

The associated pointer is not checked for null before the nested flag read in active filtering mode. The later null check described below does not protect this earlier access.

A nonzero result from the +48 operation terminates traversal immediately. Otherwise:

- Read the current recipient’s associated pointer at +12 again.
- If it is null, terminate traversal with zero.
- If it is non-null, invoke the current recipient’s table operation at +28.
- Treat the low 32 bits of that represented 64-bit return as the next-recipient pointer, and continue.

The second associated-pointer read occurs after any eligibility dependency and recipient callback. It is not necessarily equal to an earlier read. Callback-driven mutation can therefore affect whether traversal advances.

The high 32 bits returned by the chain-advance operation do not affect subsequent observable decisions in the represented logic.

There is no cycle detection or iteration limit. A chain that repeatedly yields eligible or skipped recipients without producing a nonzero result or reaching a stopping condition can fail to terminate.

### 6. Final supplied-object operation

After normal fallback completion, the captured supplied-object pointer is tested for null.

If non-null, its table operation at +4 is invoked once. The retained handling result is then returned unchanged.

This final operation also occurs after a preliminary recipient succeeds; success skips the chain, not finalization.

There is no represented exception or fault cleanup mechanism. An abnormal exit from an earlier dependency or invalid memory access need not reach iterator cleanup or this final operation.

## Side effects

The function’s explicit memory writes are confined to local iterator storage and the local output slot supplied to enumeration. It does not explicitly clear, replace, or write the input record’s two pointer fields.

External effects occur through dependency calls and indirect operations. Those effects are unknown unless separately specified. In particular:

- Dependencies may mutate contexts, objects, operation tables, collections, or globals.
- A fresh context acquisition after collection processing may observe such mutations.
- Chain setup retains the head read before supplied-object classification, even if classification changes the context’s head field.
- Dispatch tables and chain fields read after callbacks may reflect callback mutations.
- Skipping a recipient’s handling operation does not mean there are no side effects: eligibility checking and chain advancement can still call dependencies.

Ownership is not established. The final +4 operation is consistent with a lifecycle action, but calling it a release, destructor, or deallocation would exceed the evidence. No allocation is explicitly visible in this function, and dependencies must not be assumed either to allocate or not to allocate.

For valid continued execution, each object must remain usable for every later read or call that the function performs on it. This is especially relevant when callbacks can affect lifetime.

## Acceptance examples

These are conditional acceptance cases derived from the static representation, not executed tests. Each assumes valid addresses, compatible operation tables, and normally returning dependencies unless stated otherwise.

1. **Matching explicit recipient:** Its captured identity equals F-f4c5ae40135d’s result. Its +48 operation receives the supplied object and returns zero. For a non-null supplied object, +4 follows. The function returns 1; no fallback collection or chain is consulted.

2. **Mismatching explicit recipient:** The identities differ and the supplied object is valid and non-null. The supplied object receives +28, then +4. The explicit recipient’s +48 operation is not called. The function returns 1.

3. **Null object with matching explicit recipient:** The recipient’s +48 operation receives null. If it returns normally, no final object operation occurs and the function returns 1. The corresponding mismatch case has no valid null-object dispatch contract.

4. **Preliminary success:** Preliminary recipients return zero, then −7. Enumeration stops at −7, iterator cleanup runs, chain setup is skipped, and a non-null supplied object receives +4. The function returns −7.

5. **Preliminary exhaustion followed by an empty chain:** Enumeration ends with zero and cleanup runs. A fresh context supplies a null chain head. A non-null supplied object still receives +20, then +4. The result is zero.

6. **Inactive filtering:** The supplied object’s +20 operation has a zero low word, or the supplied object is null. A chain recipient receives +48 without a nested eligibility-flag read. If it returns zero and its associated pointer is null at the later check, traversal ends with zero.

7. **Active filtering, zero flag:** The nested flag is readable and zero. F-35b8bd5fa9e0 is not called. The recipient’s +48 operation runs, and a nonzero result is returned after finalization.

8. **Active filtering, nonzero flag, rejected eligibility:** F-35b8bd5fa9e0 returns zero. The current recipient’s +48 operation is skipped. If the later associated-pointer read is non-null, +28 obtains the next recipient.

9. **Callback changes traversal state:** A recipient’s +48 operation returns zero and changes its associated pointer to null. The subsequent read observes null, so its +28 operation is not invoked.

10. **Active filtering with a null associated pointer:** The representation attempts the nested flag read before any protecting null check. Graceful skipping or a zero return is not an acceptance requirement; behavior depends on the invalid access.
