# F-7a0c4836ae1b

## Purpose

F-7a0c4836ae1b searches a fixed-stride byte-record table for a numeric key and, on a match, writes two decoded numeric fields to caller-provided output locations.

The record layout is selected by three flag bits. All multibyte record fields are decoded most-significant byte first. The search compares decoded keys with the full target value; it does not truncate the target to the stored key width.

The established behavior includes an important limitation: the search does not necessarily terminate when a key is absent. In particular, its lower search boundary is set to the midpoint rather than the position after the midpoint. A search can therefore repeat the same record indefinitely. This contract describes that behavior rather than substituting a conventional binary search.

## Interface

The function accepts seven arguments in this order:

| Position | Meaning | Representation |
|---|---|---|
| 1 | Base address of the record table | Integer-valued address in the supplied interface |
| 2 | Address used as the table-end bound | Byte pointer |
| 3 | Initial number of searchable records | Unsigned 32-bit value |
| 4 | Record-format flags | Unsigned 32-bit value |
| 5 | Target key | Unsigned 32-bit value |
| 6 | Destination for the final record field | Pointer to a writable unsigned 32-bit value |
| 7 | Destination for the middle record field | Pointer to a writable unsigned 32-bit value |

There is no returned status value.

The widths and arithmetic below describe the represented 32-bit execution model. The supplied material does not independently establish portable behavior on other integer or pointer models.

### Record layout

Every record consists of three adjacent fields, without intervening padding:

| Field | Flag controlling width | Flag clear | Flag set |
|---|---|---:|---:|
| Key | Bit 0 | 1 byte | 2 bytes |
| Middle field | Bit 1 | 1 byte | 2 bytes |
| Final field | Bit 2 | 2 bytes | 3 bytes |

Thus the record stride is four bytes plus one byte for each set bit among bits 0, 1, and 2. Its possible values are four through seven bytes.

The fields appear in key, middle-field, final-field order. Their byte offsets depend on the selected widths. Each decoded value is zero-extended to an unsigned 32-bit value.

Bits above bit 2 do not affect the layout, comparisons, or search transitions.

### Preconditions for defined memory access

The caller must provide writable storage for both output destinations whenever execution reaches an output write. A zero record count does not remove this requirement.

For a visited record, the bytes actually read must be accessible. The end-bound check alone does not establish this: it checks the computed end of a record against one address, but does not verify the base address, mapped memory, address wraparound, or output-pointer validity.

For an ordinary table interpretation, the following additional conditions are needed:

- Record-address arithmetic must identify the intended records without wraparound.
- The table and its end bound must support meaningful address comparison in the execution environment.
- The visited records must use the selected layout.
- Keys must be in ascending numeric order for the search direction to have its conventional meaning.

Sortedness is an inferred requirement for useful searching, not a condition validated by the function. Even with sorted input, unsuccessful searches are not guaranteed to terminate.

## Behavior

### Layout selection

The function determines the stride solely from the low three flag bits. A clear bit selects the narrower corresponding field; a set bit adds one byte to that field.

There is no format-validation error and no rejection of additional flag bits.

### Search interval and midpoint

The initial lower boundary is zero. The initial upper boundary is the supplied record count. The function continues searching while the lower boundary is strictly less than the upper boundary.

On each iteration, it computes the midpoint by adding those two unsigned 32-bit boundaries and shifting the result right by one bit. The addition wraps modulo \(2^{32}\) before the shift. Consequently, for sufficiently large boundaries, this is not necessarily the mathematical midpoint of the interval.

The record address is formed from the table base plus the stride multiplied by that midpoint. In the represented 32-bit arithmetic, multiplication and address formation can wrap. There is no overflow detection.

### Bound check before record reads

Before reading a candidate key, the function compares the supplied end-bound address with the address immediately following the entire candidate record.

- If the bound is below that record-end address, the search stops and takes the failure-output path.
- If the bound equals that record-end address, the record passes this check.
- Otherwise, the record also passes.

The comparison occurs before any field of that candidate record is read. A failed check does not trigger a search of an earlier record, even if an earlier record would be fully within the bound.

For conventional use, the bound can be understood as an exclusive end address: a record ending exactly there is permitted. The function does not independently establish that convention or validate the surrounding allocation.

### Key decoding and comparison

After the bound check passes, the function reads the candidate key:

- A one-byte key has range 0 through 255.
- A two-byte key has range 0 through 65,535 and is decoded most-significant byte first.

The decoded key is compared as an unsigned value against the complete 32-bit target.

There is no target-range validation. A target above the representable key range does not produce an immediate error or a guaranteed clean miss.

### Successful match

When the decoded key equals the target, the function performs these observable operations in order:

1. Reads and decodes the middle field.
2. Writes that value as a 32-bit value to argument 7.
3. Reads and decodes the final field.
4. Writes that value as a 32-bit value to argument 6.
5. Returns.

The middle field is either one byte or two most-significant-byte-first bytes. The final field is either two or three most-significant-byte-first bytes. A three-byte final field has maximum value 16,777,215.

The supplied expressions establish which bytes participate in each decoded value, but do not establish a portable order among individual byte reads within a multibyte expression. They do establish the middle-output write before final-field decoding.

The function does not continue searching for another equal key. With duplicate keys, the matching record is whichever equal-key record the search first visits.

### Search transition after a mismatch

If the candidate key is greater than the target, the upper boundary becomes the midpoint.

If the candidate key is less than the target, the lower boundary becomes the midpoint. It does **not** become the midpoint plus one.

This distinction is observable. With an ordinary, nonwrapping interval whose width is one, the midpoint equals the lower boundary. If that record’s key is below the target, neither boundary changes. Assuming stable readable memory and no external interruption, the same candidate is read indefinitely, with no output writes.

The same stalled state can be reached from a larger interval. Accordingly, neither an absent key nor a target outside the key width implies a terminating failure.

### Failure-output path

Two conditions lead to failure outputs:

- The search loop finishes because the lower boundary is no longer below the upper boundary.
- A candidate record fails the end-bound check.

The function then writes:

1. Zero to argument 7.
2. Zero to argument 6.

It returns without a separate success indicator.

A successful record whose middle and final fields are both zero produces the same output values as this failure path. The interface therefore cannot distinguish those outcomes from output values alone.

With an initial count of zero, the failure-output path is taken immediately, without reading table bytes.

## Side effects

### Reads and writes

The function reads candidate key bytes while searching. It reads the middle and final fields only after finding an equal key.

On a terminating path, it writes both 32-bit output destinations, in argument-7-then-argument-6 order. A nonterminating search may repeatedly read a key without writing either output.

No direct table write appears in the supplied behavior. However, output destinations are not checked for overlap with the table.

### Aliasing

The two outputs are not required by the visible interface to be distinct, and no alias check is performed.

If arguments 6 and 7 designate the same valid 32-bit location:

- On success, the final-field value is the value left there, because it is written last.
- On failure, zero is left there.

If argument 7 overlaps bytes of the matched record’s final field, its write occurs before those bytes are read. The final result can therefore reflect the modified bytes rather than the record’s original contents. The function does not take a snapshot of the complete record before producing outputs.

Other overlapping or partially overlapping arrangements depend on the execution environment’s alignment and aliasing rules. They must not be treated as safe merely because no explicit overlap rejection is present.

### Ownership and external state

The function contains no visible allocation, release, ownership transfer, or call to another function. The interface provides no ownership-transfer mechanism.

No direct global-state access is shown. This does not establish isolation from externally shared memory: the table and output storage may themselves refer to shared state.

There is no explicit exception, fault recovery, cancellation, or error-reporting mechanism. Invalid memory access and nontermination are not converted into a status result.

## Acceptance examples

These examples are conditional static expectations, not results of runtime testing. Unless otherwise stated, assume valid output storage, stable table contents, meaningful address comparisons, and no arithmetic wraparound.

### Empty table

Given a record count of zero, the function reads no table bytes. It writes zero to argument 7, then zero to argument 6, and returns.

This remains the expected control flow even if the base and end-bound arguments do not describe a usable table, provided merely supplying those arguments does not itself violate the execution environment.

### Narrow-layout match

With the low three flag bits clear, each record contains a one-byte key, a one-byte middle field, and a two-byte final field.

For a one-record table containing key 42, middle field 127, and final-field bytes representing 4,660 in most-significant-byte-first order, a target of 42 produces:

- Argument 7: 127.
- Argument 6: 4,660.

The middle output is written before the final field is read.

### Widest-layout match

With bits 0, 1, and 2 set, the stride is seven bytes. A matching record may contain a two-byte key, a two-byte middle field, and a three-byte final field.

For a target of 4,660 and a matching record whose remaining fields represent 43,981 and 660,510, those values are written to arguments 7 and 6 respectively. Setting additional higher flag bits does not change this result or the layout.

### Exact bound versus short bound

For a candidate beginning at a valid record address:

- A bound exactly one stride beyond that address permits the record read.
- A bound one byte earlier causes the failure-output path before reading that candidate’s key.

The second case writes both outputs as zero rather than trying a smaller candidate.

### Terminating miss below the first key

For a one-record table whose key is 10, target 9 first visits record zero. Since the key exceeds the target, the upper boundary becomes zero. The function then writes both failure outputs and returns.

### Nonterminating miss above a sole key

For the same one-record table, target 11 visits record zero. Since 10 is below 11, the lower boundary is set to zero again. With stable memory, this repeats indefinitely.

Neither output is written during the repeating search.

### Existing key can remain unreachable in an unsorted table

For three records with keys 9, 1, and 5, target 9 first visits the middle record. Its key is below the target, so searching proceeds into the upper portion. It can subsequently stall on key 5 without ever visiting the matching first record.

This illustrates that the function neither checks ordering nor performs a fallback scan.

### Shared output destination

For a successful record with middle field 7 and final field 300, if both output arguments designate the same valid 32-bit storage location outside the table, the final stored value is 300.

### Indistinguishable zero results

A matching record with both result fields zero and a terminating unsuccessful search both leave zero in each separate output location. There is no return value distinguishing them.

## Uncertainties

### Established static evidence

The supplied body establishes the flag-selected widths, field order, most-significant-byte-first decoding, search transitions, candidate-bound check, output order, and absence of visible function calls.

It also establishes that the lower-bound update lacks a one-record advance. Nontermination under the stated stable-memory conditions follows from that transition.

### Inferred intent

The table appears intended to be searched by ascending key using a binary-search-like procedure. The address bound appears intended to prevent reads of incomplete records. Neither inferred intention justifies changing the actual transition or treating the bound check as complete memory-safety validation.

The meanings of the middle and final fields are unknown. They must not be described as offsets, lengths, identifiers, or owned resources without additional evidence.
