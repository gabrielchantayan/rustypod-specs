# F-3e5212464798

## Purpose

F-3e5212464798 conditionally reduces a per-key 32-bit count, invokes a backend operation when the count reaches zero or an override is supplied, and may tear down an empty backend.

This description separates three levels of confidence:

- **Established static behavior:** argument gating, field accesses, dependency calls, branches, count updates, and cleanup ordering described below.
- **Inferred intent:** the data structure resembles a keyed tree of reference counts, and two receiver callbacks resemble entry/exit synchronization. Neither interpretation establishes the contracts of the dependencies.
- **Unknown behavior:** comparison semantics, callback side effects, allocation ownership, exception behavior, and the exact semantics of teardown helpers.

The traversal must be preserved as observed, even where it differs from a conventional tree search. In particular, one comparison outcome assigns the candidate to a child link rather than to the node just examined.

No runtime tests have been performed.

## Interface

The function accepts three arguments and has no explicit return value.

| Argument | Established role |
|---|---|
| Receiver | Pointer to an object whose first three fields are accessed as 32-bit words. Its first word supplies a virtual dispatch table, its second a backend pointer, and its third an auxiliary structure pointer. |
| Key | 32-bit value. Zero causes immediate return. A local, addressable copy is supplied to several dependencies. |
| Override | 32-bit value interpreted only as zero versus nonzero. A nonzero value permits the backend operation after a nonzero count is decremented, even if that decrement does not produce zero. |

The original override argument controls the override branch. It is not passed to the backend operation. Its sign and magnitude otherwise have no established significance.

### Preconditions

When the key is zero, the function returns without dereferencing the receiver. Otherwise, reading the receiver’s backend field must be valid.

When both the key and initial backend pointer are nonzero, execution requires valid receiver dispatch data and a valid entry callback. Later pointer validity depends on the state after callbacks and helpers return. The function does not independently validate those pointers, dispatch entries, or node addresses.

A zero backend immediately after the entry callback bypasses all auxiliary-structure access. Otherwise, the auxiliary structure and every traversed or selected object must support the accesses described here.

## Behavior

### 1. Initial gating and entry

The function first tests the original key argument.

- If the key is zero, it returns immediately.
- If the key is nonzero, it reads the receiver’s backend field.
- If that backend field is zero, it returns immediately.

Neither early-return path invokes the entry callback or exit callback.

After these gates, the function prepares an addressable 32-bit copy of the key and invokes the receiver’s entry callback at dispatch offset +8. The callback’s result is retained.

The backend field is then read again. The function does not assume that the entry callback preserved it.

- If the backend is now zero, lookup and count handling are skipped. Execution proceeds to the common cleanup decision.
- If the backend remains nonzero, lookup begins using the receiver’s auxiliary structure pointer as read after entry.

A later replacement of the receiver’s auxiliary field does not, by itself, change the auxiliary address already captured for this lookup.

### 2. Traversal

The initial traversal node is read through the auxiliary structure’s header pointer, from header offset +4. The candidate is initialized from another read of the auxiliary header field.

While the current traversal node is nonzero:

1. F-a073c1bc0f3f is invoked with:
   - the captured auxiliary address plus 25;
   - the current node address plus 16;
   - the address of the local key copy.
2. If the result is zero, the node’s +8 link becomes both the next traversal node and the candidate.
3. If the result is nonzero, the node’s +12 link becomes the next traversal node, while the candidate is unchanged.

Only zero versus nonzero is examined. No ordering relation, sign convention, or equality semantics is established for this comparison helper.

The zero-result case is significant: **the candidate becomes the +8 child value, including zero, not the current node**. Consequently, an ordinary leaf traversal can leave a zero candidate. No local validation repairs or substitutes for that value.

The local key copy is exposed by address. The visible function does not write it after initialization, but dependencies may do so. Later comparisons and the backend operation use the then-current contents of that same copy, not necessarily the original key.

### 3. Candidate selection

After traversal, the function takes a fresh snapshot of the auxiliary header field.

F-3ee46ff4f2dc receives addresses of the candidate storage and that header snapshot. Its result is tested as zero versus nonzero.

- A nonzero result selects a freshly read header value as the fallback.
- A zero result causes F-f8ae48a15441 to be called with the then-current candidate value.

The result of F-f8ae48a15441 is passed to F-a073c1bc0f3f as its third operand. For this comparison:

- the context remains the captured auxiliary address plus 25;
- the second operand is the address of the local key copy;
- the third operand is the opaque value returned by F-f8ae48a15441.

If that comparison returns nonzero, a freshly read header value is selected. If it returns zero, the then-current candidate value is selected.

F-f8ae48a15441 is plausibly an accessor for the candidate’s key, and F-3ee46ff4f2dc plausibly compares iterator-like values. These interpretations are not prerequisites for the established branch behavior.

The selected value is copied into separate storage. A fresh header snapshot is obtained, and F-3ee46ff4f2dc is called again with addresses of the selected-value storage and this snapshot.

Because these helpers receive addresses, their contracts matter: the function does not establish that they leave either addressed value unchanged.

### 4. Count handling and backend operation

The result of the second F-3ee46ff4f2dc call determines whether the function proceeds:

- Nonzero: skip count handling and backend teardown; invoke the exit callback.
- Zero: inspect the 32-bit field at offset +20 of the then-current selected value.

If that field is zero, the function invokes the exit callback without a decrement, backend key operation, or teardown check.

If the field is nonzero:

1. The count is read for subtraction.
2. One is subtracted.
3. The result is written back to offset +20.
4. If the result is nonzero and the original override argument is zero, execution proceeds directly to the exit callback.
5. Otherwise, the backend key operation at dispatch offset +40 is invoked.

The backend key operation is dispatched through the receiver’s backend field as read at that point. It receives the backend and the address of the local key copy. The function does not reuse the backend pointer from the initial gate.

After the backend key operation returns, the selected node’s count is unconditionally written to zero. This write occurs even if the operation returned the special status −1.

The backend operation’s result becomes the status used for the common cleanup decision.

### 5. Common cleanup decision

The common cleanup decision is reached in two cases:

- the entry callback returned and the receiver’s backend was then zero; or
- the backend key operation was invoked and returned.

It is not reached on the ordinary lookup-rejection, zero-count, or nonzero-count-without-override paths.

The status is the entry callback’s result in the first case and the backend key operation’s result in the second.

Cleanup proceeds only if all of the following hold:

1. The status is not −1, represented by the 32-bit all-ones value.
2. A subsequent read of the receiver’s backend field is nonzero.
3. The 32-bit field at offset +4 of that backend is zero.

If any condition fails, the function proceeds to the exit callback.

If all conditions hold:

1. F-c719314a16bb is called with the receiver.
2. The receiver’s backend field is read again.
3. If it is nonzero, that backend’s cleanup callback at dispatch offset +4 is invoked. No explicit arguments are shown for this call.
4. The receiver’s backend field is written to zero.
5. The receiver’s auxiliary field is read.
6. If it is nonzero, F-c8eefdf96f4b is invoked, followed, if it returns, by F-feee9156a257.
7. If the auxiliary field was zero, it is written to zero and execution continues to the exit callback.

F-feee9156a257 is marked non-returning in the supplied static material. Under that designation, the nonzero-auxiliary branch does not reach the final auxiliary-field write or exit callback. F-c8eefdf96f4b may itself fail to return; its behavior is unspecified.

### 6. Exit

Every ordinary path after the entry callback invokes the receiver’s exit callback at dispatch offset +12 exactly once, except paths interrupted by non-returning dependency behavior or faults.

Dispatch uses the receiver’s table as read at exit time. The function does not establish that the entry callback and exit callback use the same table value.

## Side effects

Direct writes established by the visible body are limited to:

- private argument and iterator-like storage;
- the selected node’s 32-bit count;
- the receiver’s backend field during teardown;
- the receiver’s auxiliary field on the returning, zero-auxiliary teardown path.

Observable count ordering is:

- decrement and store before a possible backend key operation;
- unconditional zero store after that operation returns.

Thus, during the backend operation, the count has already been decremented but has not yet received the explicit post-operation zero write.

Observable teardown ordering is:

- receiver teardown helper;
- optional backend cleanup callback;
- backend field cleared;
- auxiliary field tested;
- optional auxiliary-related dependency calls;
- exit callback only if execution reaches it.

No allocation, deallocation, ownership transfer, or successful resource release is directly established. The cleanup-looking operations are opaque dependencies. Their names or positions do not prove that they free anything.

No synchronization guarantee is established. Entry/exit callback pairing suggests a guarded operation, but their implementation and behavior on interruption are unknown.

## Acceptance examples

These examples are conditional static acceptance cases, not executed tests. Except where stated otherwise, callbacks return normally, preserve relevant storage, and all accessed addresses are valid.

1. **Zero key with an unusable receiver address.**  
   The function returns without reading the receiver or invoking any dependency.

2. **Nonzero key with a zero initial backend.**  
   The backend field is read, then the function returns. Neither receiver callback is invoked.

3. **Selected count equals three; override is zero.**  
   If selection succeeds, the count becomes two. No backend key operation or teardown check occurs. The exit callback is invoked.

4. **Selected count equals one; override is zero.**  
   Successful selection decrements the count to zero and invokes the backend key operation. After its return, the count is written to zero again. Teardown eligibility depends on its status and the subsequently observed backend state.

5. **Selected count equals three; override is nonzero.**  
   Successful selection stores two before calling the backend key operation. After that operation returns, the count is forced to zero.

6. **Selected count is already zero; override is nonzero.**  
   No decrement or backend key operation occurs. The override does not bypass the zero-count guard.

7. **Backend key operation returns −1.**  
   The post-operation zero count write still occurs. Backend teardown is skipped, and the exit callback is invoked.

8. **Traversal comparison returns zero at a node whose +8 link is zero.**  
   Traversal ends with a zero candidate. Subsequent behavior depends on F-3ee46ff4f2dc and, if reached, F-f8ae48a15441. The function must not be specified as retaining the node just examined.

9. **Eligible teardown with a zero auxiliary field.**  
   F-c719314a16bb runs; any surviving backend receives its cleanup callback; the backend field is cleared; the auxiliary field receives zero; the exit callback runs.

10. **Eligible teardown with a nonzero auxiliary field.**  
    After clearing the backend field, the function calls F-c8eefdf96f4b and then, if it returns, the designated non-returning F-feee9156a257. It does not normally reach the exit callback.
