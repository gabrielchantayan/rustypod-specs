# F-8f668f38ee82

## Purpose

F-8f668f38ee82 obtains a block address and updates an object containing two four-word descriptors and an address table.

Its three paths are:

- Initialize the table and both descriptors when F-4959bfd499df returns nonzero.
- Insert a block address at the next slot when the second descriptor’s slot differs from the calculated last table slot.
- Allocate a replacement table, copy a range of entries, invoke a release-like dependency, and rebuild both descriptors when those slot addresses are equal.

Replacement does not imply growth. The replacement allocation request is eight times a retained active count, and the final capacity is twice that count. Neither is guaranteed to exceed the corresponding previous value.

The layout suggests a segmented container with beginning and ending descriptors. That interpretation is inferred intent, not established type information.

The return value is a 64-bit concatenation of two words from a mutable working descriptor, not an explicit success indicator.

## Interface

### Arguments and working descriptor

The function receives:

1. An address of a mutable object accessed through 32-bit words.
2. A 32-bit value.
3. A 32-bit value.
4. A 32-bit value.

Before any dependency call, it initializes a four-word working descriptor:

| Working word | Initial value |
|---|---|
| 0 | Object address converted to a 32-bit value |
| 1 | Second argument |
| 2 | Third argument |

These words are snapshots, not references to object fields. F-ea2d02694b71 receives their storage address and can modify them. The function does not independently reset them between calls.

The address conversions and stored addresses require a compatible 32-bit address representation for usable execution.

### Object layout

Offsets are measured in bytes from the original object address.

| Offset | Width | Direct use |
|---|---:|---|
| 0–15 | Four 32-bit words | First descriptor |
| 16–31 | Four 32-bit words | Second descriptor |
| 32–35 | One 32-bit word | No direct access |
| 36–39 | One 32-bit word | Table base address |

The fourth word of each descriptor is treated as a table-slot address: offset 12 in the first descriptor and offset 28 in the second.

The first word of the first descriptor is passed to F-ea2d02694b71 during replacement. The function does not otherwise establish the meanings of the first three descriptor words.

“No direct access” does not guarantee preservation of offset 32: dependencies may affect object or shared memory.

### Return value

On normal return, working word 0 supplies bits 0–31 and working word 1 supplies bits 32–63. This is bit-pattern concatenation, not sign extension.

The returned words are those present after the selected path’s final F-ea2d02694b71 call. Working words 2 and 3 are not returned.

### Preconditions and arithmetic domain

No explicit validation is present. A usable execution requires writable object storage, valid and suitably aligned table addresses, sufficient allocation extents, and dependency behavior compatible with all subsequent accesses.

All table entries and descriptor words are 32 bits. Table entries are spaced four bytes apart; block-position calculations use twelve-byte spacing.

Unsigned shifts and masks operate on 32-bit values. Unsigned multiplication wraps at that width. Some other expressions are represented as signed 32-bit arithmetic, including the initial block-size multiplication and slot-distance subtraction. Their overflow behavior is not independently established. The contract does not extend ordinary address formulas to overflowing signed expressions by silently assuming mathematical integers or universal wraparound.

Allocation failure, invalid metadata, address wraparound, and dependency failure are not explicitly handled.

## Behavior

### Common prefix

After initializing the working descriptor, the function:

1. Calls F-478e80b97aec.
2. Calls F-871e64ddc6de with twelve times that result and a second argument of zero.
3. Retains its result as the new block address.
4. Calls F-4959bfd499df with the original object address.
5. Selects initialization for a nonzero result; otherwise examines the existing table.

Thus, the block-address-producing call occurs before the predicate and on every path.

The function itself does not initialize the block’s contents. Describing this dependency as an allocator reflects how its result is used, not a verified allocation contract.

### Initialization

When the predicate returns nonzero, the following order applies:

1. Call F-478e80b97aec again.
2. Store that result in the capacity field.
3. Call F-871e64ddc6de with that result shifted left by two bits and a second argument of zero.
4. Store the returned address in the table-base field.
5. Store the new block address at the returned table address plus four times the unsigned half of the then-current capacity.
6. Call F-478e80b97aec a third time.
7. Call F-ea2d02694b71 with the working descriptor address, the new block address plus twelve times the unsigned half of the third count result, and the then-current table base plus four times the unsigned half of the then-current capacity.
8. Write working words 0 through 3 into the first descriptor, in increasing word order.
9. Copy first-descriptor words 0 through 3 into the second descriptor, in increasing word order.
10. Return the packed working words.

The three count results are separate observations. Equality is not established.

The first result controls the block request. The second controls the table request and is initially written as capacity. The third controls the block-relative position supplied to descriptor construction.

The table-slot store uses the retained allocation result as its base and rereads capacity after the allocation call. The later descriptor call reads table base and capacity after the third count call. If those dependencies modify the fields, the insertion and descriptor slot addresses can differ.

Under valid ordinary memory without aliasing interference or concurrent mutation, both descriptors contain the same four words after the explicit copy.

### Existing-table branch selection

For a zero predicate result, the function reads the second descriptor’s fourth word and compares it with:

\[
\text{table base} + 4 \times \text{capacity} - 4.
\]

Inequality selects the next-slot path; equality selects replacement.

This comparison is not a bounds check. Inequality does not prove that the current slot lies inside the table or that its successor is writable. No separate handling exists for zero capacity or malformed slot addresses.

### Next-slot path

The function:

1. Writes the retained current slot address plus four into the second descriptor’s fourth word.
2. Stores the new block address at that retained successor address.
3. Calls F-ea2d02694b71 with the working descriptor address, the new block address without an offset, and a fresh read of the second descriptor’s fourth word.
4. Writes all four working words into the second descriptor, in increasing word order.
5. Returns the packed working words.

The preliminary descriptor-slot update precedes the table write and dependency call. The final descriptor copy overwrites that slot field with working word 3.

This path directly changes neither the first descriptor nor table-base or capacity fields. Dependency effects remain possible.

### Replacement: retained arithmetic

Before requesting replacement storage, the function retains:

- A signed slot distance obtained by subtracting the first descriptor’s slot address from the previously read second-descriptor slot address, then arithmetically shifting right by two.
- A 32-bit unsigned active count obtained from that distance plus one.

For aligned, nonnegative distances without overflow, the active count is the inclusive number of entries between the two slots. That interpretation is conditional, not validation.

The replacement request is eight times the retained active count, calculated as a 32-bit unsigned value, with zero as the second argument.

A retained destination offset is calculated by doubling the unsigned active count and clearing the lowest two bits. In the ordinary nonoverflowing domain:

\[
\text{destination offset}
=4\left\lfloor\frac{\text{active count}}{2}\right\rfloor.
\]

The actual mask and fixed-width arithmetic remain significant outside that domain.

### Replacement: copy range and release

After the replacement allocation call returns, the function rereads:

- The second descriptor’s slot address, retained as the copy endpoint.
- The first descriptor’s slot address, used as the copy start.

These reads occur **after** the allocation dependency. The retained distance and active count were computed **before** it. A dependency-induced change to either slot field can therefore make the copied range differ from the retained count.

The destination begins at the replacement allocation address plus the retained destination offset.

Successive 32-bit entries are copied toward increasing addresses. Each source entry is read before its corresponding destination write. Copying stops when the source address equals four bytes beyond the retained copy endpoint.

The loop uses address equality, not the retained active count. It can copy zero entries when the initial source already equals the termination address. Malformed addresses are not safely rejected. Overlap-safe behavior is not established.

After copying, the function calls F-ff1bdc376dcd with the object’s then-current table base, its then-current capacity, and zero. These arguments need not equal values observed before allocation.

### Replacement: insertion and reconstruction

After the release-like call returns:

1. Store the retained replacement allocation address in the table-base field.
2. Store the new block address at an insertion slot calculated from that retained allocation address and retained arithmetic.
3. Call F-ea2d02694b71 to rebuild the first descriptor.
4. Copy all four working words into the first descriptor in increasing word order.
5. Call F-ea2d02694b71 to rebuild the second descriptor.
6. Copy all four working words into the second descriptor in increasing word order.
7. Store twice the retained unsigned active count in the capacity field.
8. Return the packed working words.

The insertion slot’s index relative to the replacement allocation is:

\[
\text{slot distance}
+\left((\text{active count}\mathbin{\&}\texttt{7FFFFFFF})\mathbin{\gg}1\right)
+1,
\]

using the represented 32-bit arithmetic. The resulting index is scaled by four.

In the ordinary nonnegative, nonoverflowing case, this selects the slot immediately after a range of the **retained active count** beginning at the retained destination offset. It is immediately after the entries actually copied only when the reread copy bounds produce that same range.

The first reconstruction call receives:

- The working descriptor address.
- The then-current first-descriptor word 0.
- The then-current table base plus the retained destination offset.

The second reconstruction call receives:

- The same working descriptor address.
- The retained new block address.
- The then-current table base plus the retained destination offset, plus four times the retained slot distance, plus four.

The working descriptor is not reset between these calls. The second call therefore receives working storage containing the first call’s results.

The insertion uses the retained replacement allocation address. Reconstruction uses fresh table-base reads. Changes by dependencies can make their addresses diverge.

The final capacity write occurs after both reconstruction calls. Neither call is guaranteed to observe the final capacity.

## Side effects

### Direct memory effects

Depending on the path, direct writes include table entries, descriptor words, table base, and capacity. Replacement also copies table-entry values into the replacement allocation.

Descriptor updates consist of four separate 32-bit writes, not an atomic descriptor assignment. No synchronization is established.

During replacement, copying finishes before F-ff1bdc376dcd is called. The function installs the replacement table base only after that call returns.

### Allocation and ownership

The function makes:

- One block-address-producing call on every path.
- One additional table-address-producing call during initialization or replacement.
- One release-like call during replacement.

There is no explicit release of the new block.

Replacement copies entry values, not the blocks they may reference. It performs no explicit per-entry release.

Ownership transfer cannot be established merely from address stores. Allocation units, ownership obligations, and release semantics depend on the opaque callees. In particular, F-ff1bdc376dcd receives the recorded capacity, not an explicitly byte-scaled table size.

### Errors and partial state

There is no explicit null-result check, rollback, exception boundary, or error status.

If a dependency fails or does not return, earlier allocations and writes may already have occurred. No transactional guarantee or recovery behavior is established.

## Acceptance examples

These are conditional static scenarios, not executed tests. Each assumes valid addresses, adequate storage, and returning dependencies. Field-preservation assumptions are stated where needed.

### Stable initialization

If all three count calls return eight and dependencies preserve the relevant object fields:

- The block request is 96.
- The table request is 32.
- Capacity is written as eight before the table allocation call.
- The block address is inserted at table slot four.
- Descriptor construction receives a block position 48 bytes after the block base and the address of table slot four.
- Both descriptors receive the resulting working words.

### Distinct initialization counts

If the count results are eight, ten, and six, with relevant fields otherwise preserved:

- The block request is 96.
- The table request is 40.
- Insertion uses table slot five.
- Descriptor construction uses a block position 36 bytes after the block base.

Reusing one count result for all three purposes would not match this behavior.

### Next-slot insertion

If capacity is eight and the second descriptor identifies table slot three, with valid ordinary metadata and no interfering field changes:

- Slot three differs from the calculated last slot, seven.
- The descriptor-slot field is advanced to slot four before the block address is written there.
- Descriptor construction receives the block base.
- The resulting working words replace the second descriptor.
- No direct replacement-table or capacity write occurs.

### Replacement with preserved copy bounds

Suppose capacity is eight, the first descriptor identifies slot four, and the second identifies slot seven. Assume dependencies preserve the relevant slot fields, first-descriptor data, table-base fields, and copied storage until the function updates them.

Then:

- Retained slot distance is three; active count is four.
- The replacement request is 32.
- The destination offset is eight bytes.
- Four entries are copied into replacement slots two through five.
- Release-like processing occurs after copying.
- The new block address is inserted at replacement slot six.
- Reconstruction uses replacement slot two for the first descriptor and slot six for the second.
- Final capacity is eight, written after both reconstruction calls.

This replaces the table without increasing recorded capacity.

### Replacement with allocation-time bound mutation

Use the same initial metadata, but let the replacement allocation dependency change only the first descriptor’s slot address from old slot four to old slot six. Assume all subsequent relevant fields and storage remain stable.

Then:

- Retained distance remains three and active count remains four.
- The replacement request remains 32.
- Fresh copy bounds select old slots six through seven.
- Those two entries are copied into replacement slots two and three.
- Insertion still targets replacement slot six.
- Insertion is **not** immediately after the copied entries.
- Final capacity remains eight.

This distinguishes retained sizing and insertion arithmetic from post-allocation copy bounds.

### Return packing

If the final working words 0 and 1 contain `89ABCDEF` and `01234567`, respectively, the returned 64-bit pattern is `0123456789ABCDEF`.
