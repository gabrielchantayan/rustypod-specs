# F-10c913f72506

## Purpose

F-10c913f72506 writes two individual bytes in a destination object, conditionally calls F-151ab4bfe553 for an embedded address, and performs three ordered indirect dispatches through the destination’s dispatch table.

The established contract concerns memory accesses, argument values, and call ordering. The supplied static representation does not establish the application meanings of the fields or operations. Descriptions such as “copy,” “reset,” “enable,” or “notify” would add unsupported semantics.

A shared external 32-bit storage location is read twice directly: once to retain a value for the third dispatch, and separately to supply the first dispatch’s second argument. Those two argument values are equal only if the two reads produce equal values.

This document distinguishes established static evidence, inferred intent, and unresolved behavior marked **documented_only**. No runtime tests have been performed.

## Behavior

### Initial byte write

The first direct mutation writes the supplied eight-bit value at destination offset 36.

This precedes the source-address comparison, any helper invocation, and all dispatches. It writes one byte, not a four-byte field. No visible validation precedes this mutation.

### Address comparison and optional helper

The source reference is compared with destination plus 40.

- Equal addresses skip F-151ab4bfe553.
- Unequal addresses cause a 32-bit read at source offset 4, followed by the helper invocation.

This is an address-equality condition. Equal contents at distinct addresses do not suppress the helper. The condition does not implement a general overlap check.

When called, F-151ab4bfe553 receives:

1. Destination plus 40.
2. The 32-bit value read at source plus 4.

No copy semantics, ownership transfer, allocation, release, or preservation guarantee follows merely from these arguments.

If the helper does not return normally, the subsequent zero write, shared-storage reads, and dispatches are not established as occurring.

### Later byte write

After the helper returns normally, or immediately after the equal-address branch skips it, the function writes zero to the single byte at destination offset 48.

If the helper wrote this byte, the direct zero write follows and replaces the helper’s value. Later dispatches may change the byte again; zero is not an unconditional final-state guarantee.

### Retained shared-storage read

After the zero write, the function reads shared storage as a 32-bit value and retains that value for the third dispatch.

An optional helper call precedes this read. Therefore, changes made by the helper to shared storage can affect the retained value.

This read is distinct from the subsequent read used for the first dispatch. The retained value is not explicitly used as the first dispatch’s second argument.

### First dispatch

The first dispatch receives:

1. The destination reference.
2. A separately obtained 32-bit value from shared storage.
3. The 32-bit literal 644, hexadecimal 0x284.

Its target is resolved through the destination’s dispatch-table field and the entry at table offset 88.

The shared-storage read supplying this call is separate from the earlier retention read. The representation does not justify combining them into one read or requiring their results to match.

The retention read precedes preparation of the first call. Within that call’s preparation, the precise ordering of the shared-storage argument read relative to dispatch-table and target-resolution reads is not established. This contract does not impose such an ordering.

If the two shared-storage reads both yield the same value, the first and third dispatches receive equal second arguments. Otherwise, they receive different second arguments: the first receives the later read’s value, while the third receives the retained earlier value.

### Second dispatch

After normal return from the first dispatch, the second dispatch receives:

1. The destination reference.
2. The value from second-dispatch operand storage.
3. The value from second-dispatch selector storage.

These external operands are obtained for this call after the first dispatch. The first dispatch may have changed their storage; preservation is not assumed.

The destination’s dispatch-table field and the selected table entry are consulted again. The second target need not be the first target.

The representation does not establish a precise ordering among the operand reads and target-resolution reads within preparation of this call.

### Third dispatch

1. The destination reference.
2. The value retained by the earlier shared-storage read.
3. The value from third-dispatch selector storage.

The third selector is obtained for this dispatch after the second dispatch. Either earlier dispatch may have changed its storage.

The target is resolved again through the destination’s current dispatch-table field and table offset 88. It may differ from both earlier targets.

The visible third-dispatch expression does not reread shared storage. Changes to that storage after retention do not, by themselves, change the retained argument. This is not a guarantee that callees preserve other state or that execution remains valid after arbitrary callee behavior.

### Helper does not return

### Byte-width boundary
