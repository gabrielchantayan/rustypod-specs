# F-e7b5b40d1609

## Purpose

F-e7b5b40d1609 normalizes a requested signed value against two fields in a caller-supplied object, compares that value with an embedded component’s reported value, and conditionally updates the object’s stored current value. When the stored value changes, it performs mode-dependent dependency calls and indirect notifications.

The established behavior is an ordered sequence of field accesses and calls. The meanings of the value, bounds, modes, and notification arguments are not established. Describing the operation as a selection update or the indirect calls as notifications is inferred intent, not an additional behavioral guarantee.

The operation is not transactional. A dependency can be called before an unchanged-value return, and the new current value is stored before later processing.

## Interface

### Inputs and result

The function takes:

- An object address.
- A requested value, interpreted as a signed 32-bit integer.

There is no explicit return value and no explicit error result.

The visible representation uses four-byte object words. The relevant layout is:

| Byte offset from object | Visible use |
|---|---|
| `0x000` | Reference to a dispatch table |
| `0x018` | A word whose low eight bits select the mode |
| `0x01C` | Start of an embedded component passed to two dependencies |
| `0x8B8` | Stored current value, accessed as a 32-bit word |
| `0x8BC` | Lower comparison bound, interpreted as signed 32-bit |
| `0x8C0` | Upper comparison bound, interpreted as signed 32-bit |

The indirect callable is obtained from byte offset `0x58` within the dispatch table referenced by the object’s first word.

These are access locations, not evidence that the surrounding object has no other fields. The visible routine performs no null, alignment, object-size, or dispatch-target validation.

### Preconditions

For a path to complete normally:

- Every object field accessed on that path must be readable.
- The current-value field must be writable when its value changes.
- Dependencies must accept the object or embedded-component address supplied to them.
- Each indirect call must resolve to a valid callable with a compatible calling convention.
- The object must remain usable for subsequent accesses after returning dependency calls.

The source does not establish that dependencies preserve object contents, dispatch tables, global argument storage, or object lifetime. Those requirements cannot be silently attributed to the dependencies.

### Opaque notification values

The source exposes several four-byte global values without establishing their meanings. This contract distinguishes them by use:

- **A:** an argument value captured immediately after storing a changed current value.
- **B:** a second argument value captured immediately after A.
- **P:** the third argument of the nonzero-result mode-2 callback.
- **C** and **D:** respectively the second and third arguments of the first callback in the shared notification tail.
- **E:** the third argument of the last callback in that shared tail.
- **Q1**, **Q2**, **Q3**, and **Q4:** successive third-argument values used by the mode-3 notification sequence.

These names identify distinct source storage locations, not necessarily distinct contents. Their numeric values, external meanings, and mutability are unknown. They must not be treated as known string addresses, event numbers, or immutable constants.

## Behavior

### 1. Normalize the requested value

The function first reads the upper comparison bound.

- If the upper bound is strictly less than the requested value, the normalized value becomes that upper bound. The lower bound is not read on this branch.
- Otherwise, the function reads the lower comparison bound.
  - If the requested value is strictly less than the lower bound, the normalized value becomes that lower bound.
  - Otherwise, the requested value is retained.

Both comparisons are signed 32-bit comparisons. Equality with either bound does not itself cause replacement.

This is an upper-first conditional selection, not an unconditional guarantee that the result lies in a valid interval. No relationship between the bounds is checked. If the lower bound exceeds the upper bound, the result still follows the branch order above.

No arithmetic increment, decrement, saturation calculation, or range-width calculation is visible.

### 2. Query the embedded component

The function calls F-56fd8d6069bf with the address at object offset `0x01C`.

It compares that call’s returned value with the normalized value. If they differ, it calls F-9c31c3e85ab1 with:

1. The same embedded-component address.
2. The integer value `1`.

The second dependency’s result does not control the visible continuation.

This comparison does not set the normalized value to the returned value. Nor does the visible code write the normalized value into the embedded component.

Both calls occur before the stored-current-value equality check. Therefore, an eventual unchanged-value return does not imply that the function made no calls or produced no side effects.

### 3. Compare and store the current value

After the component-related calls, the function reads the current-value field at `0x8B8`.

- If it equals the normalized value, the function returns immediately.
- Otherwise, the function writes the normalized value to that field.

Because this equality check occurs after the dependencies, it observes the field as it exists after those calls, not necessarily as it existed at entry.

After the write, the function captures A and then B from their respective global storage locations. These captured values are reused later even if subsequent dependencies change their backing storage.

The function then examines the low eight bits of the mode word.

### 4. Initial mode 2 processing

If the first mode examination yields `2`, the function calls F-bfda5fbfe0b0 with:

1. The object address.
2. The address of a local 40-byte scratch region.
3. The current-value field, read again at this point.
4. The integer value `3`.

The scratch region is not visibly initialized before this call. No scratch contents are subsequently inspected by this function.

The dependency’s return is tested only for zero versus nonzero.

**Zero result:**

1. Call F-97a072757e44 with the object address.
2. Read the current-value field again.
3. Call F-52cae007644e with the object address and that freshly read value.

The value supplied to F-52cae007644e need not equal the normalized request if earlier calls changed the field.

**Nonzero result:**

Invoke the object’s indirect callable with:

1. The object address.
2. Captured A.
3. P, read for this call.

No rollback of the stored current value is visible on either result.

After either branch completes, the function reads the mode again:

- If it is still `2`, proceed to the shared notification tail.
- Otherwise, perform the mode-1/mode-3 decision below.

A mode change caused by a dependency therefore affects the remaining notification sequence.

### 5. Mode-1/mode-3 decision

This decision is reached either when the initial mode was not `2`, or when mode-2 processing returned with a mode other than `2`.

The function examines the low eight mode bits:

- Mode `1`: execute the shared notification tail.
- Otherwise, examine the mode for `3`.
  - Mode `3`: execute the mode-3 sequence.
  - Any other value: return.

The visible access sequence contains separate mode examinations rather than one entry-time mode snapshot.

For an initial mode outside `1`, `2`, and `3`, the current-value write still occurs when needed. Only the later mode-specific calls are omitted.

### 6. Shared notification tail

This tail is used for mode `1` and for mode-2 processing that leaves the mode equal to `2`.

It makes two indirect calls, in order:

1. Object address, C, D.
2. Object address, captured B, E.

C, D, and E are obtained from their global storage when the corresponding call is prepared. The first call can therefore affect the global value later obtained as E.

The indirect callable is resolved again for the second call. The first call can change which callable receives the second invocation.

There is no mode recheck between these two calls.

### 7. Mode-3 sequence

The function makes four indirect calls, in order:

1. Object address, captured A, Q1.
2. Object address, captured A, Q2.
3. Object address, captured A, Q3.
4. Object address, captured B, Q4.

Each Q value is obtained for its associated call. Earlier calls can change storage used by later calls. Captured A and B are not refreshed.

The dispatch table and callable are resolved separately for each invocation. No mode check interrupts this four-call sequence once it has been entered.

For the final indirect call in either notification sequence, the callable is obtained before the final third-argument global value is read. The supplied source does not establish a complete machine-level ordering among all argument-expression reads in the other calls.

## Side effects

The only direct persistent write visible in this function is the changed current value at object offset `0x8B8`.

Other observable effects include:

- Calls involving the embedded component, even when the current value is ultimately unchanged.
- Mode-specific dependency calls after the current-value write.
- Indirect calls with the ordered argument combinations described above.
- Reads of object state and global argument storage after dependencies have had an opportunity to change them.

No explicit heap allocation, release, ownership transfer, lock operation, or rollback is visible.

The 40-byte scratch region has local-call lifetime. Its address is passed to F-bfda5fbfe0b0, but the source does not establish whether that dependency writes it, retains its address, or accesses its initial contents. Retention would not make the region’s lifetime extend beyond this invocation.

The function does not establish that an indirect call is merely informational. Such calls may change state used by later operations. If a dependency does not return normally, the source provides no recovery path or guarantee that the remaining calls occur.

## Acceptance examples

These are conditional static acceptance examples, not reports of executed tests. Unless stated otherwise, assume valid object storage, returning dependencies, and no dependency changes to relevant state.

1. **Request above the upper bound.**  
   Upper bound `20`, lower bound `10`, request `25`: the normalized value is `20`. The lower-bound read is skipped. Subsequent comparisons and any write use `20`.

2. **Request below the lower bound.**  
   Upper bound `20`, lower bound `10`, request `5`: the normalized value is `10`.

3. **Boundary equality.**  
   With bounds `10` and `20`, requests `10` and `20` remain unchanged by normalization. Whether later calls occur depends on the component result, stored current value, and mode.

4. **Inverted bounds expose branch priority.**  
   Upper bound `10`, lower bound `20`, request `15`: the result is `10`, because the upper-bound branch wins without reading the lower bound. With the same bounds and request `5`, the result is `20`.

5. **Unchanged current value with component mismatch.**  
   The normalized value is `12`, the component query returns `7`, and the current field is `12` after component-related calls. F-9c31c3e85ab1 is called with the embedded address and `1`; the function then returns without mode-specific processing.

6. **Changed value in mode 1.**  
   The current field differs from the normalized value, and mode is `1`. The field is written first. The two indirect calls then receive `(object, C, D)` and `(object, captured B, E)`, in that order.

7. **Mode 2, zero result, mode preserved.**  
   F-bfda5fbfe0b0 returns zero and mode remains `2`. F-97a072757e44 precedes F-52cae007644e, followed by the two shared-tail indirect calls.

8. **Fresh current-value read matters.**  
   During the preceding example, F-97a072757e44 changes the current field to `99`. F-52cae007644e receives `99`, not the earlier normalized value.

9. **Mode 2 changes to mode 3.**  
   After the zero/nonzero-result branch, the reread mode is `3`. The function executes the four-call mode-3 sequence instead of the shared tail. Any earlier nonzero-result callback has already occurred and is not undone.

10. **Unsupported mode after a change.**  
    The current value changes and mode is `4`. The function retains the current-value write but performs no mode-specific dependency or indirect calls.

11. **Captured versus refreshed arguments.**  
    A mode-3 callback changes the storage backing A and Q2. The second mode-3 callback still uses captured A, but obtains Q2 from its storage when preparing that second call.
