# F-6b944f57518d

## Purpose

F-6b944f57518d recognizes a backlight-related command and conditionally dispatches its action. Recognized actions are:

- Select one of eight backlight settings.
- Save the current backlight selection.
- Cancel the backlight interaction.
- Show the backlight settings.

Recognition and permission to act are separate. A recognized command returns the recognized result even when a mode comparison suppresses its action. An unrecognized command returns the unrecognized result.

The supplied static evidence establishes dispatch behavior, a direct settings write, and dependency calls. It does not establish the numerical backlight values, the command-comparison algorithm, or the effects of the save, cancel, and show operations.

## Interface

### Inputs

The function accepts three arguments:

| Argument | Established representation | Use |
|---|---|---|
| Receiver | Pointer to an object whose initial field can be interpreted as a dispatch-table address | Forwarded to save and show dependencies; used for indirect cancel dispatch |
| Command token | 32-bit opaque value | Passed unchanged as the first argument of each command comparison |
| Mode | 32-bit integer | Compared with a captured shared mode value; also forwarded to save and show dependencies |

The command token is not directly dereferenced in the visible body. Its admissible representation is determined by the comparison dependency. Although the command labels suggest text matching, the supplied evidence does not establish that the token is a string pointer or specify encoding, termination, case sensitivity, or comparison length.

### Return value

The normal return value is a 32-bit quantity:

- **1:** A command was recognized, whether or not its action was enabled.
- **0:** None of the command comparisons reported a match.

These results do not describe success or failure of saving, displaying settings, or cancelling. Return values from invoked action dependencies are not used.

The return contract applies when every required dependency returns normally and every required memory access is valid. No visible mechanism handles dependency failure, invalid memory, or nonlocal control transfer.

### Shared data and layouts

The visible body uses the following conceptual shared locations:

- A 32-bit mode value used to suppress actions.
- A base address for a settings record.
- Eight separate 32-bit setting-value sources, one for each selection command.

For a permitted selection, the function writes exactly one 32-bit value at byte offset **+4** from the captured settings-record base address. No other field of that record is directly accessed by the visible body.

For a permitted cancel operation:

1. The receiver’s initial field supplies a dispatch-table address.
2. A callable entry is obtained at byte offset **0xB8** from that address.
3. That entry is invoked with the receiver and the integer value **0x10**.

The evidence supports the byte offsets and the 32-bit setting write. It does not provide a complete receiver structure, settings-record structure, or dispatch-table declaration. Treating the dispatch entry as a particular numbered method would require an additional assumption about entry width.

### Preconditions

Preconditions are path-dependent:

- Every comparison that is reached must accept the supplied command token and its command descriptor.
- Every shared source read by the selected comparison path must be readable.
- A permitted selection requires a valid destination for the 32-bit write at settings-base +4.
- A permitted cancel requires a readable receiver header, a readable callable entry at dispatch-table offset 0xB8, and a compatible callable target.
- Save and show require whatever additional preconditions their dependencies impose.

A null receiver is not explicitly rejected. The visible body does not dereference it for a selection, an unrecognized command, or a recognized command whose action is suppressed. This observation is not a general guarantee that null is accepted by other reached dependencies.

## Behavior

### 1. Initial comparison and shared-state capture

The function first invokes the command-comparison dependency for the selection descriptor labelled **SetBacklight_AlwaysOff**.

After that comparison returns, the function reads shared data in this order:

1. The mode value used for suppression.
2. The settings-record base address.
3. The setting value associated with AlwaysOff.

The mode value and settings-record base are retained for subsequent use. They are not visibly refreshed after later command comparisons.

This timing is significant. The first comparison occurs before these shared reads. Later comparisons occur after the captures and may have effects of their own, but the visible body continues using the captured mode and settings base.

The AlwaysOff setting-value source is read even when the initial comparison reports no match.

### 2. Selection recognition

Selection descriptors are tested in the following order:

| Priority | Descriptor label | Value selected if matched |
|---|---|---|
| 1 | SetBacklight_AlwaysOff | Its associated 32-bit setting value |
| 2 | SetBacklight_2sec | Its associated 32-bit setting value |
| 3 | SetBacklight_5sec | Its associated 32-bit setting value |
| 4 | SetBacklight_10sec | Its associated 32-bit setting value |
| 5 | SetBacklight_15sec | Its associated 32-bit setting value |
| 6 | SetBacklight_20sec | Its associated 32-bit setting value |
| 7 | SetBacklight_30sec | Its associated 32-bit setting value |
| 8 | SetBacklight_AlwaysOn | Its associated 32-bit setting value |

A comparison result of zero means match for dispatch purposes. Any nonzero result means this descriptor did not match.

Recognition short-circuits at the first match. No lower-priority selection descriptor or action descriptor is compared after a selection match.

For each selection after AlwaysOff, the function:

- Performs that descriptor’s comparison.
- Reads that descriptor’s 32-bit setting-value source.
- Uses the comparison result to determine whether selection recognition stops.

Consequently, a reached selection’s setting-value source is read even when its comparison does not match. Setting-value reads are not deferred until a successful match.

The descriptor labels suggest durations and always-on/off states. The actual setting values are not supplied. They must not be assumed to equal 2, 5, 10, 15, 20, or 30, or to use any particular time unit or enumeration.

### 3. Selection action

Once a selection descriptor matches:

- If the input mode differs from the captured shared mode value, the function writes the selected 32-bit setting value to settings-base +4.
- If the two mode values are equal, it performs no direct settings write.

The function then normally returns 1.

The mode check does not control whether comparisons or setting-value reads occur. Those operations precede action suppression.

There is no visible validation, conversion, range check, or read-before-write of the destination field. There is also no explicit save call, display refresh, cancellation callback, or hardware operation in the selection branch.

### 4. Save recognition and dispatch

Only if all eight selection comparisons fail does the function compare the token with the descriptor labelled **SaveBacklight**.

If this comparison matches:

- When the input mode differs from the captured shared mode value, F-c37966403d77 is called with the receiver and the original input mode.
- When the values are equal, that call is suppressed.

The command token and selected setting value are not supplied as explicit arguments to this dependency.

After normal completion of this branch, the function returns 1. The dependency’s return value, if any, does not change that result.

### 5. Cancel recognition and dispatch

Only if SaveBacklight also fails does the function compare against **CancelBacklight**.

If this comparison matches:

- When the input mode differs from the captured shared mode value, the function obtains the indirect callable from the receiver’s dispatch table at byte offset 0xB8 and invokes it with the receiver and 0x10.
- When the values are equal, the receiver-based dispatch is suppressed.

The argument 0x10 is an established literal value. Its meaning as an event, operation, or status code is not established.

After normal completion of this branch, the function returns 1.

### 6. Show recognition and dispatch

Only if CancelBacklight also fails does the function compare against **ShowSetting_Backlight**.

If this comparison matches:

- When the input mode differs from the captured shared mode value, F-88e35d3d97ca is called with the receiver and the original input mode.
- When the values are equal, the call is suppressed.

The function then normally returns 1.

If this final comparison does not match, the function returns 0.

### 7. Precedence and comparison counts

The visible dispatch order is fixed. If the comparison dependency could report matches for more than one descriptor, the earliest reached match wins.

Assuming all reached comparisons return normally:

- AlwaysOff recognition requires one comparison.
- AlwaysOn recognition requires eight comparisons.
- Save recognition requires nine comparisons.
- Cancel recognition requires ten comparisons.
- Show recognition, or complete nonrecognition, requires eleven comparisons.

These counts describe calls to the comparison dependency, not the number of token reads performed within that dependency.

### 8. Widths and arithmetic

Mode suppression is an equality test between 32-bit integer values. No ordering or arithmetic interpretation is involved, so signedness does not affect the equality decision.

Selected setting values are copied as 32-bit quantities without visible transformation.

The visible address calculations are fixed byte offsets of +4 and +0xB8. The body does not perform duration conversion, multiplication, incrementing, or accumulation. It supplies no overflow or address-validity checks for those offsets. Valid accessible destinations and dispatch entries remain caller or environment preconditions.

## Side effects

### Directly established effects

The visible body can:

- Read shared mode, settings-base, and setting-value sources.
- Invoke the comparison dependency between one and eleven times.
- Perform one 32-bit settings-field write for a permitted selection.
- Invoke one save dependency, one show dependency, or one indirect cancel target for the corresponding permitted action.

Only one action branch is taken. In particular, selecting a value does not fall through to save or show.

### Dependency effects

No preservation contract is supplied for any dependency. The comparison dependency may have externally observable effects or modify shared data. Save, show, and cancel may likewise modify state, perform I/O, or alter object lifetime.

The direct-effect list therefore must not be interpreted as a whole-program side-effect limit.

If a later comparison modifies the shared mode value or settings-base source, the function still uses its earlier captured values. A setting value for a later selection, however, is read after that selection’s comparison returns.

### Ownership and lifetime

The visible body performs no explicit allocation, deallocation, reference-count update, or ownership transfer.

Passing the receiver to a dependency does not establish that the dependency borrows it, retains it, or destroys it. Those lifetime rules are documented_only pending dependency contracts.

The function does not visibly access the receiver after a save, show, or cancel call returns. This does not by itself establish that releasing the receiver inside those calls is permitted.

### Errors

There is no explicit error result other than command nonrecognition. In particular:

- A suppressed recognized action still returns 1.
- A save or show dependency’s result is not inspected.
- The indirect cancel result is not inspected.
- Invalid pointers and inaccessible shared locations have no visible recovery path.
- No rollback is visible.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests.

### Permitted 5-second-labelled selection

Given that:

- AlwaysOff and 2sec comparisons return nonzero;
- the 5sec comparison returns zero;
- the captured shared mode differs from the input mode;
- the relevant reads and destination write are valid;

the function must compare those three descriptors in order, read each reached selection’s value source at its specified point, write the 5sec-associated 32-bit value to the captured settings-base +4, and return 1.

It must not compare 10sec or invoke save, show, or cancel.

### Suppressed selection

Given an AlwaysOn match and equality between the input mode and captured shared mode, the function must return 1 without its direct settings write.

All eight selection comparisons and their associated value-source reads still occur. This example does not require comparison dependencies to be side-effect-free.

### Save after all selections fail

No CancelBacklight or ShowSetting_Backlight comparison occurs.

### Cancel with action suppressed

Given that the first ten comparisons identify CancelBacklight and the mode values are equal, the function must return 1 without performing the visible receiver dispatch-table lookup or indirect cancel call.

This establishes no validity guarantee for the receiver on other paths.

### Permitted cancel

Given a CancelBacklight match, unequal mode values, and valid dispatch data, the selected indirect target must receive the receiver and 0x10. Normal completion produces return value 1 regardless of an otherwise returned callback value.

### Show and nonrecognition

If only ShowSetting_Backlight matches and the modes differ, F-88e35d3d97ca must receive the receiver and input mode.

If all eleven comparisons return nonzero, the function must return 0 and perform no visible action-branch write or action call.

### Shared-state mutation during recognition

If a comparison after the initial shared-data capture changes the shared mode source, action suppression must still use the captured mode value.

Likewise, changing the settings-base source during a later comparison does not redirect the direct selection write. Conversely, changing a later selection’s value source during its own comparison can affect the value subsequently read for that selection.
