# F-913f697b827b

## Purpose

F-913f697b827b performs an ordered update-and-dispatch operation on caller-supplied storage. It:

- Writes the low eight bits of an input value into the storage.
- Captures two unsigned 32-bit values and independently limits each to a maximum of 28.
- Invokes a first dependency with existing state, the storage address, and the original scalar inputs.
- Overwrites two state bytes after that dependency returns.
- Captures two additional bytes and passes them, together with the limited values and two addresses within the storage, to a second dependency.
- Returns the two captured bytes packed into a 64-bit result.

These operations are established by the supplied static representation. Their application-level meaning is unknown. In particular, describing the bytes as flags, handles, coordinates, channels, or resource identifiers would be unsupported.

The two dependency identifiers used below are report-local opaque identifiers. Their behavior and externally assigned identities were not supplied.

## Behavior

### 1. Initial byte update

The function first writes the low eight bits of the update value to offset 14.

This write precedes the direct reads of the two leading words. There is no validation or dependency call before it.

The original 32-bit update value remains available for the first dependency. Writing its low byte does not replace that argument with the truncated value.

### 2. Capture and limit the leading values

The function reads the unsigned 32-bit word at offset 0. Values from 0 through 27 are retained; values greater than 27 become 28.

It then reads and transforms the unsigned 32-bit word at offset 4 in the same way.

Consequently, each captured value is in the range 0–28. An input of 28 remains numerically 28, although it follows the greater-than-27 case. Large unsigned values, including values whose highest bit is set, also become 28.

These are captured values. Later modifications of the corresponding storage words by a dependency do not cause the function to reread or recompute them.

### 3. Invoke the first dependency

The first dependency, F-000000000001, receives eight arguments in this positional order:

1. The byte read from offset 15.
2. A value obtained by reading the 32-bit word at offset 16, narrowing it to a plain character, and converting that character to the integer type.
3. Auxiliary value A.
4. Auxiliary value B.
5. The original storage address.
6. The original 32-bit update value.
7. Auxiliary value A again.
8. Auxiliary value B again.

The byte at offset 15 and the word at offset 16 are read before control enters this dependency. Their relative evaluation order is not established by the supplied representation.

The second argument has a signedness uncertainty. On an eight-bit signed-character target, a narrowed byte with its high bit set may become a negative integer. On an unsigned-character target, it is in the range 0–255. The target’s actual character-conversion rules are not supplied.

The dependency’s return value is not used. No branch on a status or error result is shown.

Because the dependency receives the storage address, the later behavior cannot assume that the initial byte update or any other storage content survived the call unchanged.

### 4. Perform post-call byte writes

If the first dependency returns normally, the function writes:

1. Zero to offset 15.
2. 255 to offset 16.

These are separate eight-bit writes in the stated order.

The second write changes only the byte at offset 16. It is not a 32-bit assignment to the word beginning there, and it does not directly overwrite offsets 17–19.

These writes occur after the first dependency’s effects. They are not guaranteed final values, because the second dependency subsequently receives addresses to both bytes.

### 5. Capture the return components

The function next reads:

1. The byte at offset 14.
2. The byte at offset 13.

Each is interpreted as unsigned and widened to 32 bits.

These reads occur after the first dependency and the two explicit byte writes. Thus:

- The captured offset-14 value can differ from the low byte initially written there if the first dependency changed it.
- The captured offset-13 value reflects any change made by the first dependency before it returned.
- Neither captured value is refreshed after the second dependency.

### 6. Invoke the second dependency

The second dependency, F-000000000002, receives eight arguments:

1. The first limited value, restricted to its low eight bits.
2. The captured offset-14 byte, widened to 32 bits.
3. The captured offset-13 byte, widened to 32 bits.
4. The second limited value, restricted to its low eight bits.
5. The same captured offset-14 value.
6. The same captured offset-13 value.
7. The address of offset 15.
8. The address of offset 16.

The low-eight-bit restrictions on the limited values do not alter their numeric values: each is already between 0 and 28.

The last two arguments designate adjacent byte locations within the original storage. The dependency can potentially modify those locations. No assumption is made about its actual access widths, other accesses, retention of the addresses, or ownership behavior.

Its return value is ignored.

### 7. Return the packed captures

After the second dependency returns normally, F-913f697b827b returns the packed offset-13 and offset-14 captures described in the interface.

Changes made by the second dependency to those storage bytes do not change the already-captured return components.

There is no explicit success indicator, failure indicator, or alternate return path in the supplied representation.

## Side effects

### Direct memory effects

On an execution that reaches every step, the direct writes are exactly:

1. Offset 14 receives the low eight bits of the update value.
2. Offset 15 receives zero after the first dependency returns.
3. Offset 16 receives 255 immediately afterward.

The function does not directly write back either limited leading value.

These writes are not transactional. No rollback is shown if a later read, write, or dependency invocation fails to complete.

### Dependency-mediated effects

Both dependencies execute before normal return. Their side effects are unknown.

The first receives the original storage address. The second receives two addresses within that storage. Either may also have effects on global state or other resources that cannot be determined from this function.

The function itself shows no allocation, release, ownership transfer, or explicit lifetime management. That absence does not establish that the dependencies refrain from allocating, freeing, retaining pointers, or changing global state.

### Ordering and concurrency

The behavioral order above describes the explicit operation sequence supported by the static representation. It does not establish atomicity, inter-thread synchronization, hardware memory barriers, or safe concurrent access.

Argument positions are established. Evaluation order among separate reads used as arguments to the first dependency is not.
