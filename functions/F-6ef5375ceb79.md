# F-6ef5375ceb79

## Purpose

F-6ef5375ceb79 invokes an operation selected through a primary object, supplies local storage and an interior address of that object to a preparation dependency, and repeatedly requests a candidate reference. Each nonzero request result causes an operation selected through the current candidate. A zero result ends the repetition and causes a final dependency call.

The established contract is the ordering of calls, the addresses supplied to dependencies, and the use of each request result. A traversal or object-processing interpretation is plausible but not established. The relationship between the primary object and candidate objects is unknown.

This specification describes the supplied static representation. No runtime tests have been performed.

## Interface

### Arguments

The function accepts four arguments in this order:

| Position | Representation | Established role |
|---|---|---|
| First | Reference to integer-addressable object storage | Supplies the initial dispatch base and the base for an interior address. |
| Second | Opaque 32-bit word | Initially copied into the first word of local context storage. |
| Third | Opaque 32-bit word | Initially copied into the next word of local context storage. |
| Fourth | Reference to integer-addressable object storage | Initially copied into a local candidate-reference slot. |

The two opaque words have no established numeric interpretation, signedness, pointer meaning, or ownership significance. Their initial copies retain all 32 bits.

The fourth argument is a candidate reference value, not the address of a caller-owned output slot. The function creates its own slot containing that reference. A dependency's replacement of this local slot does not itself replace a caller-held copy of the argument. Mutations to an object reached through the reference may still be externally visible.

### Result

The function has no explicit return value. It does not directly report:

- Whether any candidate operation occurred.
- How many request calls occurred.
- The final candidate reference.
- A dependency status or error code.

Observable results arise through calls and changes to memory or other state accessible to their targets.

### Widths and layout

The supplied representation establishes two consecutive four-byte local context words, followed by a local candidate-reference slot. The address of the first context word is supplied to all three identified dependencies. The candidate slot's address is also supplied separately to F-b38a3aba0e18.

This arrangement does not establish the complete size or permitted access extent of a context accepted by those dependencies. In particular, an access through the context address may reach the candidate slot; independence between the two is not established.

Object dispatch uses the following layout:

- The beginning of the primary object supplies a dispatch-base value.
- A callable entry is selected at byte displacement 152, or 0x98, from that base.
- Candidate dispatch uses the same displacement from the candidate object's own dispatch base.
- The interior address supplied during preparation is ten integer elements beyond the primary object reference. Under the apparent four-byte integer model, that is byte displacement 40, or 0x28.

The interior argument is an address, not the value stored at that address. The displacement is not ten bytes.

The representation is consistent with a 32-bit object model, but a complete target ABI is not independently supplied. Pointer width, function-pointer representation, alignment requirements, and arithmetic behavior outside valid address ranges remain unresolved. Ordinary execution requires address computations and accesses to be valid under the actual execution model; this contract does not prescribe portable wraparound behavior.

### Preconditions for ordinary completion

The function does not visibly validate its inputs. Ordinary completion requires:

- Readable object and dispatch storage at every dispatch actually attempted.
- Compatible callable targets at the selected entries.
- A suitable primary-object interior address for the preparation dependency's actual accesses.
- Valid local-storage accesses by dependencies.
- Normal return from every invoked target.
- An eventual zero result from F-b38a3aba0e18.

A candidate need not be dereferenceable merely because it is stored in the slot. The wrapper dereferences it only following a nonzero request result. Dependencies may impose additional requirements not visible here.

## Behavior

### Initial local state

Before the first external call, the function initializes local storage in this order:

1. The first context word receives the second argument.
2. The second context word receives the third argument.
3. The candidate-reference slot receives the fourth argument.

These are initial values, not invariants across subsequent calls. The function does not visibly restore them before preparation or iteration.

The initial candidate copy therefore does not establish which reference will be present when the first request begins. In particular, F-8ca21d3a8cca subsequently receives the context address, and its unknown access extent may include the candidate slot.

### Primary-object operation

The first external call is selected through the primary object:

- The object's leading dispatch-base value is read.
- The callable entry at byte displacement 152 from that base is read.
- The selected target is invoked with the primary object reference as an explicit argument.

The function does not inspect or propagate a result from this call.

The operation's semantic meaning is unknown. The shared dispatch displacement does not identify it as destruction, cleanup, visitation, notification, or any other particular operation.

This call precedes preparation. Any changes it makes to accessible object storage or shared state can therefore affect what later dependencies observe. Its normal return does not independently guarantee that the primary object remains valid.

### Preparation

After the primary-object call returns, F-8ca21d3a8cca receives:

1. The address of the first local context word.
2. The primary-object interior address ten integer elements beyond the original object reference.

The function does not visibly read or copy the interior contents before passing this address. Preparation therefore receives access to the storage as it exists after the initial operation, rather than a snapshot taken before that operation.

No result from F-8ca21d3a8cca controls subsequent execution. If it returns normally, the function proceeds to the first request.

The dependency may modify storage accessible through its arguments. The wrapper does not establish the extent of such modification. Consequently, neither the initial context-word values nor the initial candidate value may be assumed to survive preparation unchanged.

### Request and candidate operation

Every request invokes F-b38a3aba0e18 with:

1. The same local-context address supplied during preparation.
2. The address of the local candidate-reference slot.

The request's integer result is tested only for equality with zero.

**Zero:** iteration ends immediately. The function does not perform a candidate-directed operation for that request, even if the request replaced the candidate slot.

**Nonzero:** the function obtains the candidate reference from the slot after the request returns, selects the callable entry through that candidate's leading dispatch base at byte displacement 152, and invokes it.

The supplied representation shows no explicit arguments for this candidate-directed call. It therefore does not establish that the candidate reference is passed as an explicit argument. Hidden arguments, register-based conventions, and an incomplete recovered call signature remain unresolved.

A negative result, if representable by the request's result type, is nonzero and takes the candidate-operation branch. The wrapper does not distinguish success, failure, or other status categories within the nonzero range.

The candidate slot is not reset between requests. If a request leaves it unchanged and returns nonzero, dispatch uses the reference that was present immediately before that request. For the first request, that reference is not necessarily the initial fourth argument: preparation may already have changed the slot.

After the candidate operation returns, the next external call is another request. The wrapper does not inspect the candidate operation's result, maintain a visible count, or impose a count-based limit.

Each nonzero request causes a fresh selection through the current candidate and its current dispatch storage. The wrapper does not visibly cache one dispatch target for all candidates.

### Finishing and return

The first zero request result is followed by a call to F-d0d3f100effc with the same local-context address.

After that call returns, the function returns without an explicit value.

Finishing occurs on the ordinary zero-result path even if no candidate operation occurred. It is not established as an exception-safe cleanup action. A fault, exception, nonlocal transfer, or nonreturning callee can prevent the finishing call.

## Side effects

### Direct effects

The visible wrapper directly initializes the two local context words and the local candidate-reference slot. It supplies addresses of that storage to dependencies.

No direct write to a primary-object or candidate-object field is visible in the wrapper. Object mutation may nevertheless occur inside any selected target or dependency.

Replacing the local candidate reference changes which object a subsequent nonzero request dispatches through. It does not itself alter the caller's reference variable or establish an ownership transfer.

### Delegated effects and ownership

The effects of each callee are unknown beyond how its result is consumed here. No dependency is established to preserve globals, object fields, dispatch structures, or another dependency's inputs.

The wrapper does not visibly allocate or release memory. That does not imply that its callees avoid allocation or release. In particular:

- The initial operation is not proven to preserve the primary object for preparation.
- Preparation is not proven to preserve the candidate slot.
- A request is not proven to leave context words unchanged.
- Candidate operations are not proven to preserve objects or shared state used by later requests.
- Finishing is not proven to release any particular resource.

Addresses into local storage are supplied to dependencies. The visible function provides no persistent replacement storage and no demonstrated lifetime extension. Whether a dependency retains such an address is unknown; valid use after this function returns is not established.

### Ordering

For normal completion after a finite number of candidate operations, the external-call order is:

1. The primary-object operation.
2. F-8ca21d3a8cca.
3. At least one F-b38a3aba0e18 request, with one candidate operation immediately after each nonzero result.
4. F-d0d3f100effc after the first zero result.

There may be zero candidate operations, but there is always at least one request after preparation returns normally.

These are synchronous ordering properties of the wrapper. They do not establish atomicity, synchronization, or behavior under concurrent mutation.

## Acceptance examples

These are conditional requirements derived from static evidence, not executed tests. Unless stated otherwise, they assume valid accesses, compatible targets, and normal returns.

### Immediate termination

If the first request returns zero, the call order is the primary-object operation, preparation, one request, and finishing. No candidate operation occurs.

This remains true if preparation or the request changes the candidate slot. The wrapper does not dispatch a candidate on the zero-result branch.

### Two nonzero requests

If requests return nonzero, nonzero, and then zero, exactly two candidate operations occur. Each uses the reference present after its corresponding request returns. Finishing follows the third request.

The references need not be distinct, and neither is required to equal the initial fourth argument.

### First request leaves the slot unchanged

If the first request returns nonzero without modifying the slot, the candidate operation uses whatever reference occupied the slot immediately before that request.

For the operation to use the initial fourth argument, an additional condition is required: the slot must still contain that initial reference immediately before the first request. The initial assignment alone is insufficient.

### Preparation replaces the candidate

Suppose preparation changes the candidate slot from the initial reference to a different valid reference. If the first request leaves the slot unchanged and returns nonzero, the operation is selected through the replacement reference.

The function does not restore or prefer the initial candidate.

### Replacement on a terminating request

If a request writes a different candidate reference and returns zero, no candidate operation follows that request. Finishing receives the context address next.

Whether finishing subsequently accesses the candidate slot is unknown.

### Negative request result

If a request returns a negative nonzero integer and leaves a valid candidate in the slot, one candidate operation occurs before the next request. There is no separate negative-result error branch.

### Primary operation changes interior data

If the initial operation changes storage at the interior address later supplied to preparation, preparation receives that address after the change. The wrapper provides no earlier snapshot of its contents.

### Invalid candidate after a nonzero result

If a request returns nonzero with a null or otherwise invalid candidate reference in the slot, the wrapper attempts dispatch without a visible validity check. A safe skip, defined error result, and guaranteed finishing are not established.

### No terminating request

If every request returns nonzero and all selected operations return normally, repetition continues without a visible count limit. Finishing is not reached along that execution.

## Evidence

The supplied static representation establishes four inputs, no explicit return value, initial copies into local storage, and an initial object-selected call through displacement 152 with an explicit object argument.

It then shows preparation receiving the context address and the primary-object interior address, repeated requests receiving both the context address and candidate-slot address, and candidate dispatch following only nonzero results. The candidate call has no explicit arguments in the supplied representation. Finishing follows ordinary zero-result termination.

The candidate slot's initial value is established only at initialization. Because preparation receives an address into adjacent local storage and its access extent is unknown, static evidence does not establish that the initial candidate survives until the first request. The acceptance conditions above preserve that distinction.

No runtime tests, dynamic observations, independent dependency contracts, or complete ABI evidence were provided.
