## Behavior

### Initial writes and shared-state capture

The operation first writes 0x3A at three locations associated with the entry base: as a byte at that base, as a halfword at twice that base, and as a word at offset 0x20.

It then targets the word at primary-base offset 0x20. That location receives, in order:

1. 0x20.
2. 0x2F.
3. The zero-extended byte read from primary-base offset 0x04.
4. 0x20 again.

The byte read occurs after the first two writes. It is not an entry-time snapshot. Aliasing or device semantics can therefore affect the byte obtained.

Only after this sequence does the operation read the shared base from its shared cell. Earlier writes can affect that read if their address ranges overlap the cell.

A shared location at absolute address 0x60 is then assigned 0x20. The supplied material does not independently establish that destination’s access width. Its width must remain **documented_only** rather than being inferred solely from the numeric value.

### Repeated relationship updates

The next phase repeatedly writes a small set of address relationships and low-byte projections.

The first relationship update uses the doubled link:

- The word at doubled-link offset 0x54 receives the doubled context.
- The byte at shared-base offset 0x19 receives the low byte of the primary base.
- The byte at primary-base offset 0x11 receives the low byte of the shared base.
- The word at shared-base offset 0x34 receives the doubled link.

Subsequent relationship updates use the secondary base instead of the doubled link. Each complete repeated unit writes the doubled context to secondary-base offset 0x54, then updates the same two byte locations, then stores the secondary base at shared-base offset 0x34.

The phase ends with another update of the two byte locations and the shared-base word. These are repeated writes to fixed derived addresses, not evidence of traversal through successive elements.

The exact repetition count is **documented_only** in this contract. The supplied material visibly contains extensive explicit repetition; no runtime-dependent loop bound is established. This contract does not authorize collapsing the repeated accesses into a single update when access multiplicity is observable.

The shared base and the two low-byte projections are retained values during this phase. Overwriting the shared cell later in the phase would not, by itself, cause the base to be reloaded.

### Captured values and context updates

After the repeated phase, the operation captures a 32-bit value from absolute address 0xA9 and a word from doubled-context offset 0x74.

It next writes one byte at absolute address 0x3A. That byte is the low eight bits of eight times the adjusted input plus 0x30.

Before the following context writes, it captures:

- A word from context-base offset 0x14, later used both for restoration and as an outgoing argument.
- A word from primary-base offset 0x04, distinct from the earlier byte read at that address.

It then establishes several byte fields: the low byte of the primary base at context-base offset 0x0D, 0x6C at primary-base offset 0x08, and the low byte of the shared base at primary-base offsets 0x0D and 0x09. The word at context-base offset 0x54 receives the context base itself.

The low byte of the captured value from absolute address 0xA9 is written to absolute address 0x67.

The operation subsequently reads a word at context-base offset 0x44. This read occurs after the preceding writes, so overlap can change its result. The byte at absolute address 0x67 is then copied to absolute address 0x21.

The newly read context word supplies:

- Its low byte to primary-base offset 0x10.
- Its full value to shared-base offset 0x54.
- A shifted, byte-narrowed value to context-base offset 0x01.

The shift count is the low byte of the primary base. The supplied expression represents a signed right shift. Behavior for counts of 32 or greater, and the exact negative-value shift semantics, are not established.

The word at shared-base offset 0x54 is then overwritten with the primary base. The preceding write remains part of the visible access sequence.
