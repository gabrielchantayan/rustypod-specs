# F-6848c4d5f0a2

## Purpose

F-6848c4d5f0a2 conditionally obtains an indexed value from a supplied receiver, transfers selected parts of that value into a separately initialized temporary, and passes the latter temporary to another operation on the receiver.

The established selection rule accepts either:

- An unsigned 32-bit index strictly less than a value returned by the receiver.
- The distinguished index `0xFFFFFFFF`, regardless of that returned value.

On normal completion, the function returns the 32-bit value `0` for an accepted index and `9` for any other index.

**Inferred intent:** the receiver appears to expose a collection-like interface, with operations resembling a size query, indexed value retrieval, and consumption or application of the retrieved value. These meanings are not established by the available evidence. In particular, the distinguished index must not be described as “last item,” “current item,” or “no selection” without an additional contract.

## Interface

### Inputs

| Input | Established representation | Use |
|---|---|---|
| First argument | One 32-bit value | Not inspected or forwarded by the visible function body. |
| Receiver | Pointer to an object whose initial field supplies a dispatch-table address | Used for three possible indirect calls. |
| Index | Unsigned 32-bit integer | Compared with the query result and, when accepted, forwarded unchanged to the retrieval operation. |

The first argument has no visible influence on the branch, dependency arguments, or returned status. This does not establish anything about obligations imposed by an external calling convention.

### Output

The function returns one 32-bit status:

- `0`: the acceptance branch reached its status assignment after the receiver’s final operation returned normally.
- `9`: the index failed the acceptance condition.

Both values are returned only after the final cleanup dependency returns normally.

These statuses do not independently prove success of any dependency. The body does not inspect a success or failure result from initialization, transfer, cleanup, retrieval, or the final receiver operation.

### Receiver requirements

The receiver must support an initial pointer read and the indirect calls selected through byte offsets in its dispatch table:

| Dispatch-table byte offset | Visible call interface |
|---|---|
| `0x118` | Receives the receiver; supplies a value used as an unsigned 32-bit query result. |
| `0x14C` | Receives an output-storage address, the receiver, and the unchanged 32-bit index. Called only for an accepted index. |
| `0x4C` | Receives the receiver and the address of the initialized temporary. Called only for an accepted index. |

These offsets identify table locations, not stable identities for the selected functions. No opaque dependency IDs were supplied for the indirect targets.

There is no visible null check, dispatch-table validation, or target validation. Valid storage, compatible call interfaces, and sufficient receiver lifetime are preconditions for defined normal execution.

### Temporary storage

Two groups of local storage are visible:

1. A **working temporary**, initialized before the acceptance decision and cleaned up before every normal return.
2. A **retrieved temporary**, supplied to the retrieval operation and cleaned up only on the accepted path.

For each group, the visible layout comprises:

| Relative byte offset | Visible region |
|---|---|
| `+0` | A 4-byte leading region whose address is passed as the temporary’s base. |
| `+4` | An 8-byte region whose address participates in the transfer dependency call. |
| `+12` | A 4-byte trailing field. |

The regions form a visible 16-byte local footprint for each temporary. This does **not** establish a public object type, alignment contract, or complete callee access footprint. In particular, the transfer dependency receives interior addresses; the evidence does not establish that it reads or writes exactly eight bytes.

## Behavior

### Initialization and query

The function establishes a fallback result of `9`, then calls F-b02b795a8319 with the base address of the working temporary.

Only after initialization returns does it read the receiver’s dispatch-table address and call the target at byte offset `0x118`. The query is performed even when the index is the distinguished value `0xFFFFFFFF`; there is no sentinel shortcut around initialization or the query.

The query result is used as an unsigned 32-bit value. The function accepts the index if either:

- The index is strictly less than that result under unsigned comparison.
- The index equals `0xFFFFFFFF`.

There is no arithmetic on the index: no increment, decrement, sign conversion, offset calculation, or replacement of the distinguished value is visible.

### Rejected index

For an index that is neither below the query result nor equal to `0xFFFFFFFF`:

- The retrieval operation is not called.
- F-46f0b3cb316e is not called.
- No trailing-field transfer occurs.
- The receiver operation at offset `0x4C` is not called.
- F-ee5919ca4be6 is called with the working temporary’s base.
- The function returns `9` if cleanup returns normally.

Rejection therefore does not mean “no effects.” Initialization, the receiver query, and working-temporary cleanup have already occurred.

### Accepted index

For an accepted index, the following operations occur in order:

1. The receiver’s dispatch table is read again, and the target at offset `0x14C` is invoked with the retrieved temporary’s base, the receiver, and the original index.
2. F-46f0b3cb316e is called with two interior addresses: the working temporary at `+4`, followed by the retrieved temporary at `+4`.
3. After that dependency returns, the 32-bit trailing field at `+12` is read from the retrieved temporary and written to the working temporary’s corresponding field.
4. F-ee5919ca4be6 is called with the retrieved temporary’s base.
5. The receiver’s dispatch table is read again, and the target at offset `0x4C` is invoked with the receiver and the working temporary’s base.
6. The result is set to `0`.
7. F-ee5919ca4be6 is called with the working temporary’s base.
8. The function returns `0` if this final cleanup returns normally.

This establishes a partial transfer rather than a visible whole-object copy. The leading region of the working temporary is not explicitly copied from the retrieved temporary. Its interior region is passed to a dependency, while its trailing 32-bit field is assigned directly.

The trailing-field read occurs **after** F-46f0b3cb316e returns. If that dependency changes the retrieved temporary’s trailing field through an alias or other reachable state, the subsequent direct assignment uses the field’s value at that later point.

The retrieved temporary is cleaned up **before** the final receiver operation. The working temporary remains available through that receiver operation and is cleaned up afterward.

### Dispatch and mutable state

Each receiver operation uses a fresh dispatch-table read at its own call site. The function does not visibly cache one dispatch-table address for all three calls.

Consequently, a dependency that changes the receiver’s dispatch-table pointer can affect a later call. A behavioral model must not silently assume that the initial query fixes the retrieval or final-operation target.

Likewise, the acceptance comparison uses the query result already obtained. There is no second query before retrieval, and no revalidation after transfer or cleanup.

### Abnormal completion

No explicit recovery path, rollback, or dependency-result validation appears in the body.

If a dependency fails to return normally, the evidence does not establish that later cleanup occurs or that a status is returned. In particular:

- A failure during retrieval does not visibly trigger working-temporary cleanup.
- A failure during the transfer dependency does not visibly trigger either cleanup.
- A failure during retrieved-temporary cleanup prevents the visible sequence from reaching the final receiver operation.
- A failure during final working-temporary cleanup prevents normal return, even if the result has already been set to `0`.

Runtime exception handling, nonlocal exits, and platform-specific unwinding are unknown.

## Side effects

### Established effects

The body visibly performs:

- Initialization of the working temporary through a dependency.
- At least one indirect receiver call on every normal invocation.
- Conditional retrieval into local storage.
- Conditional invocation of the interior-address transfer dependency.
- One conditional 32-bit read and corresponding 32-bit write between trailing fields.
- Conditional cleanup of the retrieved temporary.
- A conditional final receiver operation.
- Cleanup of the working temporary before every normal return.

The relative order of these effects is part of the contract. In particular, retrieved-temporary cleanup must precede the final receiver operation, and working-temporary cleanup must follow it.

### Ownership and lifetime limits

Passing a temporary’s base to F-ee5919ca4be6 establishes a cleanup call, not a proven ownership model. The evidence does not identify which allocations, references, handles, or other resources the dependency releases.

Similarly, passing the working temporary to the final receiver operation does not establish whether that operation copies data, retains a reference, consumes resources, or merely observes the value.

The local storage ceases to be available after the function returns. Safe retention of any pointer into it requires an additional dependency contract; it cannot be inferred here.

No assumption may be made that dependencies preserve global state, preserve the receiver, or avoid aliases to the temporaries. The body’s direct writes are narrow, but dependency-mediated effects are not bounded by the available evidence.

## Acceptance examples

These are conditional contract examples, not observed executions. Unless stated otherwise, they assume valid receiver storage, compatible dependencies, usable temporary contents, and normal return from every invoked dependency.

### Ordinary accepted index

If the query returns `5` and the index is `4`, the function takes the accepted path.

Expected ordering: working initialization, query, retrieval with index `4`, interior transfer, trailing-field transfer, retrieved cleanup, final receiver operation, working cleanup. The returned status is `0`.

### Exact upper boundary

If the query returns `5` and the index is `5`, the index is rejected.

Only initialization, query, and working cleanup occur. The returned status is `9`.

### Empty range

If the query returns `0` and the index is `0`, the index is rejected. Equality is insufficient for acceptance.

The returned status is `9`, following working cleanup.

### Distinguished index with empty range

If the query returns `0` and the index is `0xFFFFFFFF`, the index is accepted despite the empty ordinary range.

The query still occurs, and retrieval receives `0xFFFFFFFF` unchanged. The function does not translate it into a valid ordinary index. The returned status is `0` if the complete accepted sequence returns normally.

### Unsigned high-bit boundary

If the query returns `0x80000000`:

- Index `0x7FFFFFFF` is accepted.
- Index `0x80000000` is rejected.

This comparison must not be implemented as a signed 32-bit comparison.

### Maximum query result

If the query returns `0xFFFFFFFF`, every possible 32-bit index is accepted: all smaller values satisfy the unsigned comparison, and `0xFFFFFFFF` satisfies the distinguished-index condition.

### Transfer-dependent trailing value

If the retrieved trailing field initially contains one 32-bit value, but F-46f0b3cb316e changes it before returning, the later direct transfer uses the changed value.

An implementation that captures this trailing field before calling the dependency would change the established ordering.

### Changed dispatch table

If retrieved-temporary cleanup changes the receiver’s dispatch-table pointer, the final receiver call selects offset `0x4C` through the table read afterward.

Reusing a table address captured before cleanup is not equivalent under that condition.
