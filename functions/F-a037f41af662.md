# F-a037f41af662

## Purpose

F-a037f41af662 performs a conditional two-object setup, followed by a notification and a terminal-state check on an associated record.

When the associated-record field is nonzero after the entry dependency returns, the function obtains two resources, creates two corresponding objects, configures them, copies two saved state words, and marks the setup active. Regardless of whether that setup runs, it invokes a notification dependency.

After notification, the function checks the associated-record field again. If it finds a record, it writes a one-byte marker into that record and rereads the association. If both the pre-write and post-write association values are nonzero, it invokes two dependencies, the second of which is represented as nonreturning. Otherwise, it clears five receiver fields and returns a 64-bit value.

The meanings of the created objects, resource identifiers, notification constants, and terminal operation are not established. Descriptions such as “object,” “resource,” and “active” identify structural roles, not independently verified application semantics.

- Lower 32 bits: `4`.
- Upper 32 bits: the auxiliary input word if conditional setup was skipped, or `4` if setup completed and execution subsequently reached the normal return.

Thus, the setup-skipped return has the bit pattern formed by placing the auxiliary word above the low word `4`. A returning setup path has the bit pattern `0x0000000400000004`.

These are bit-level descriptions, not signed numeric interpretations. No byte-order assumption is needed to describe the two halves.

The return shape is established by the supplied representation; its correspondence to a public calling convention remains unverified.

## Behavior

### 1. Entry processing and setup decision

The function first invokes F-ecc1f4c34dbc. The visible call supplies no explicit arguments and consumes no result.

Only after that call does it inspect the four-byte associated-record field at receiver offset `0x1B8`. Therefore, setup is selected using the state after this dependency returns, not necessarily the state at function entry.

If the field is zero, all two-object setup is skipped. Execution proceeds directly to notification.

If it is nonzero, the function reads the one-byte category at receiver offset `0x1C4`:

- Categories `1` through `6` establish a setup flag of one.
- Categories `0` and `7` through `12` establish a setup flag of zero.
- All other byte values leave that flag without a function-established value in the supplied representation.

The default-category case must not be treated as equivalent to either zero or one. Its downstream flag value is documented_only.

### 2. Obtain the temporary pair

On the setup path, the function replaces the temporary pair with:

1. The four-byte word at associated-record offset `0x30`.
2. The four-byte word at associated-record offset `0x34`.

The associated-record field is accessed for these loads rather than represented as a single permanently retained record address. There is no intervening dependency call between the two pair loads.

No numeric interpretation, scaling, addition, or conversion of these words is visible. They are subsequently exposed as adjacent four-byte values through a temporary address.

If it is zero, the marker write is skipped and normal cleanup follows.

1. Write the byte value one at offset `0x60` of that record.

2. Receiver offset `0x1B8`.

4. Receiver offset `0x1C0`.
5. Receiver offset `0x1E0`.

## Side effects

The function directly writes resource results, object results, copied state, an active marker, the associated record’s one-byte marker, and the five cleanup fields.

It does not visibly clear the resource fields, object fields, copied-state destinations, or active marker during normal cleanup. A successful setup followed by a returning cleanup can therefore leave those setup results present while clearing the association and saved input fields.

Every dependency may have additional effects. No preservation of globals, receiver fields, associated records, or temporary data is assumed without a separate dependency contract.

Two allocation-like requests are visible on the setup path. There is no explicit release operation whose argument identifies either allocation. Neither transfer of ownership to F-b07a62920ca7 nor release by either terminal dependency is established.

The temporary-pair address is valid as function-local storage during the visible calls. Any retention of that address beyond its lifetime requires dependency behavior not supplied here.

No explicit error result, rollback, retry, or partial-setup cleanup exists in the visible behavior. A dependency that fails to return prevents subsequent operations. A dependency that returns an invalid dereferenced address may lead to an invalid access; the source provides no recovery branch.
