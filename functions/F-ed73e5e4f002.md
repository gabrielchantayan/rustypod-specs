# F-ed73e5e4f002

## Purpose

F-ed73e5e4f002 conditionally updates context-relative accounting and passes an input address’s preceding metadata to a dependency.

For a nonzero input, the established behavior consists of an initial dependency call, context capture, metadata validation, accounting updates, and final dependency calls. A zero input returns without those effects.

The metadata layout, size-like mask, and accounting operations suggest allocation management. That is **inferred intent**, not evidence that the function frees storage, transfers ownership, or acquires and releases a lock.

This contract describes source-level behavior. It does not impose a total order on operand reads where the supplied expression leaves their relative order unspecified, and it does not assign wrapping behavior to signed overflow.

## Interface

### Input and result

The function accepts one signed integer carrying an address, called **P** below. The supplied representation uses a 32-bit integer/address model, with 32-bit signed and unsigned accounting words and unsigned 16-bit metadata selectors.

- P equal to zero selects the immediate-return path.
- Nonzero P is used to locate metadata immediately before the supplied address.
- The function has no result value or returned status.

The integer-to-pointer interpretation, platform byte order, alignment requirements, and validity of the resulting addresses are not established independently by the supplied material.

### Metadata layout

For nonzero P, the function uses the following locations:

| Offset from P | Access width | Established use |
|---|---:|---|
| −8 bytes | 32 bits, unsigned | Validation word and source of accounting amounts |
| −4 bytes | 16 bits, unsigned | First amount-counter selector |
| −2 bytes | 16 bits, unsigned | Second amount-counter selector |

An accounting amount is obtained by masking the metadata word with **0x3FFFFFFC**. This retains bits 2 through 29. The amount ranges from zero through 0x3FFFFFFC, in multiples of four.

The metadata address passed to a final dependency is P−8, not P.

### Captured context and accounting locations

After the initial dependency returns, the function reads a global context reference and retains its value, called **B** below. Subsequent context-relative accesses use this captured value rather than reloading the global reference.

| Location relative to B | Stored width | Update |
|---|---:|---|
| 0x224 + 4 × first metadata selector | 32 bits | Subtract the first captured amount |
| 0x30C | 32 bits | Subtract the first captured amount |
| 0x0E0 + 4 × second metadata selector | 32 bits | Subtract the first captured amount |
| 0x220 | 32 bits | Subtract the first captured amount |
| 0x310 + 4 × dependency result | 32 bits, signed access | Decrement by one |
| 0x390 | 32 bits, signed access | Decrement by one |
| 0x008 | 32 bits | Subtract a freshly read, masked amount |

These formulas identify accesses. They do not establish array bounds, object sizes, or distinctness between locations.

### Preconditions for ordinary, defined completion

The function does not explicitly check pointer validity, selector bounds, context validity, or arithmetic safety. Ordinary, defined completion requires:

- Metadata and accounting locations to be valid for their respective accesses.
- All evaluated signed address calculations and signed decrements to remain representable.
- Any implementation-dependent integer conversions and pointer interpretations to produce the intended locations.
- Dependencies to return where continued execution requires it.
- Dependency effects not to invalidate storage that will subsequently be accessed.

These are caller/environment requirements, not conditions enforced by the function.

## Behavior

### Null handling

When P is zero, the function returns immediately.

It does not call a dependency, capture the global context reference, access metadata, or update accounting on this path.

### Initial call and context capture

For nonzero P, the function first calls **F-2fd8826557a4** without explicit arguments. After that call returns, it reads the global context reference and captures B.

The ordering is significant: changes to the global reference made by this dependency can affect which context is selected. Later changes to that reference do not redirect the function’s remaining context-relative accesses, which use B.

### Metadata validation

The function forms the metadata address P−8 and checks its unsigned 32-bit word.

Validation selects the failure branch when:

- The first word evaluation yields zero; or
- The first evaluation is nonzero and a subsequent evaluation has bit 0 set.

The zero check short-circuits the bit check. At the source-expression level, a nonzero first result leads to a second evaluation of the same metadata location. This is not a guarantee of two separate physical memory transactions or a synchronization mechanism.

If the evaluations observe different values, the predicate uses those respective observations. In particular, a nonzero first result followed by a zero second result does not select failure.

The failure branch calls **F-a817d8d58c10** without explicit arguments. No direct accounting write has occurred at that point.

The supplied representation marks this dependency as non-returning. Its implementation and termination mechanism are unavailable. The displayed body has no explicit recovery branch or return following this call; if the dependency returned despite that designation, execution would reach the subsequent accounting path.

Validation does not require a nonzero masked amount. It does not reject bit 1, bit 30, or bit 31 merely because those bits are set.

### Pre-accounting call

After validation succeeds, the function calls **F-c0fc6d033caa(B)**.

Neither metadata selector nor the amount used for the first four accounting updates has yet been captured. A dependency-induced metadata change can therefore affect those later values. There is no subsequent repetition of the validation predicate.

The call’s placement is consistent with a state-entry or synchronization operation, but neither role is established.

### First four accounting updates

After the pre-accounting dependency returns, the function:

1. Reads the unsigned 16-bit selector at P−4 and forms the corresponding first selected address.
2. Reads the unsigned word at P−8 and captures its value masked with 0x3FFFFFFC.
3. Updates the first selected accounting word by subtracting that captured amount.
4. Updates the word at B+0x30C by subtracting the same amount.
5. Reads the unsigned 16-bit selector at P−2 and forms the corresponding second selected address.
6. Updates the second selected accounting word by subtracting the same amount.
7. Updates the word at B+0x220 by subtracting the same amount.

Each update reads the current accounting word and writes the subtraction result. The first amount capture is reused for all four subtractions; those updates do not independently reload the metadata amount.

Both metadata selectors range from zero through 65,535, so their unsigned multiplication by four ranges from zero through 262,140. No bounds check accompanies either selection.

The later selector is read after the first two accounting writes. If those writes alias its storage, that ordering matters.

### Count selection and decrements

The function next calls **F-09dcb55e8e0a** without explicit arguments.

Its signed integer result selects the count location described by B + 0x310 + four times the result. There is no explicit nonnegative check or range check.

The function then performs two ordered signed-word updates:

- Read the selected count, decrement it by one, and write it back.
- Read the count at B+0x390, decrement it by one, and write it back.

The dependency runs after the first four amount-based writes and before both count updates. It may affect metadata or accounting memory; no preservation contract is supplied.

These decrements use signed arithmetic. Their overflow behavior must not be inferred from the unsigned amount-based subtractions.

### Final amount-based update

After both count decrements, the function evaluates:

- The current signed accounting word at B+0x008.
- A fresh unsigned metadata word at P−8, masked with 0x3FFFFFFC.

The relative order of these two operand reads is **unspecified by the supplied subtraction expression**. Both supply values for the final subtraction, and both occur before its result is written to B+0x008.

The accounting operand is converted to unsigned for this subtraction. The result is stored as an unsigned 32-bit word.

The newly obtained amount need not equal the earlier captured amount. The selector dependency and intervening accounting writes occur between the two captures, and relevant storage may alias.

### Final calls and return

After the final accounting write, the function calls, in order:

1. **F-cc6c9b4a0f68(B, P−8)**
2. **F-e586bff64fb7(B)**

The second call is reached only if the first returns normally. No direct metadata access is shown after the metadata-taking call.

After the final dependency returns, the function returns without a result value.

## Side effects

### Direct writes and ordering

A completed non-null accounting path performs seven direct 32-bit accounting writes:

- Four subtractions using one captured amount.
- Two signed decrements.
- One subtraction using a later metadata evaluation.

There is no direct assignment to the global context reference or an explicitly designated metadata field. Computed accounting locations may nevertheless alias metadata or other storage; the access formulas do not prevent that.

The source establishes ordering between the successive accounting updates and dependency calls. It does **not** establish a universal total order for every operand read. In particular, neither operand read of the final subtraction is specified to precede the other.

No transaction, atomic read-modify-write primitive, or rollback is shown. Earlier effects are not explicitly reversed if later execution fails.

### Unsigned amount arithmetic

For each amount-based subtraction, the accounting value is read through a signed 32-bit type, but the masked amount is unsigned. The subtraction therefore operates in the unsigned 32-bit domain and stores an unsigned result.

On an otherwise defined execution, these five subtraction results are reduced modulo 2³². For example, subtracting 64 from a stored zero produces 0xFFFFFFC0.

This rule describes the subtraction, not the safety or validity of the address used to access its operands.

### Signed counts and address arithmetic

The two count decrements operate on signed 32-bit values.

- Decrementing zero yields −1 without signed overflow.
- Decrementing −2,147,483,648 exceeds the signed range.

The supplied source does not establish a wrapping result for the latter case. Signed overflow has no defined wrapping behavior in the source language; the resulting machine behavior is **documented_only** without additional evidence.

Address construction also mixes signed and unsigned operations:

- Metadata offsets from P use signed arithmetic.
- Fixed context offsets and dependency-derived count-address calculations include signed arithmetic.
- The metadata-selector multiplication and its addition to the context value use unsigned arithmetic, followed by storage into a signed intermediate and a signed offset addition.

The unsigned intermediate calculations have unsigned arithmetic semantics. An unsigned value outside the signed range is not guaranteed to convert to the intended signed address representation. Subsequent signed additions can also overflow.

Consequently, this contract does not guarantee that arbitrary address calculations wrap modulo 2³² or that wrapped addresses are usable.

### Aliasing, ownership, and lifetime

Accounting locations are not proven distinct. Where permitted aliasing exists and execution remains defined, later ordered accesses use the memory state left by preceding writes and dependency effects. The two final operand reads remain unordered relative to one another.

Passing P−8 to F-cc6c9b4a0f68 does not, by itself, establish release, retention, or ownership transfer. Whether P remains usable after return is unknown.

No dependency is assumed to preserve globals, metadata, context contents, or storage lifetime merely because its implementation is absent.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, assume valid distinct locations, stable metadata, representable signed calculations, suitable address conversions, and returning non-failure dependencies that do not mutate relevant memory.

### Zero input

For P equal to zero, the function returns with no dependency call, context read, metadata access, or accounting write.

### Zero metadata

For nonzero P whose first validation read yields zero:

- The initial dependency has run and B has been captured.
- F-a817d8d58c10 is called.
- No direct accounting write precedes that call.
- Normal return is not established by the supplied non-returning designation.

### Bit-0 rejection

With stable metadata 0x00000005, the nonzero check succeeds but the bit check selects failure. The pre-accounting dependency and accounting writes have not yet occurred.

### Accepted zero amount

With stable metadata 0x00000002:

- Validation succeeds.
- Both amount captures yield zero.
- All five amount-based writes still occur, storing the corresponding subtraction results.
- Both signed counts are decremented.
- The final dependencies are reached if execution continues normally.

### Stable nonzero amount

With stable metadata 0x00000042, both captured amounts are 64.

A distinct amount counter initially containing 100 becomes 36. Each of the five amount counters is reduced by 64 under unsigned arithmetic, and each count is decremented by one.

### Metadata changed by the selector dependency

Suppose the first captured amount is 64 and F-09dcb55e8e0a changes the masked metadata amount to 128.

The first four subtractions use 64. The final subtraction uses 128, assuming no further relevant mutation. Validation is not repeated.

This example does not require either final operand read to occur first.

### Unsigned subtraction versus signed decrement

A distinct amount counter containing zero becomes 0xFFFFFFC0 when its amount is 64.

A distinct signed count containing zero becomes −1 when decremented. In the represented 32-bit model its stored bit pattern is 0xFFFFFFFF; this is a representable signed result, not evidence of signed-overflow wrapping.

### Signed minimum count

If a decremented count contains −2,147,483,648, the source-level signed decrement overflows.

No specific stored result, final dependency sequence, or normal completion is guaranteed for that execution by this contract.

### Context reference changes

If the initial dependency changes the global context reference before returning, the changed reference is captured.

If a later dependency changes that global reference, subsequent direct context-relative accesses still use the previously captured B, provided that captured context remains valid.
