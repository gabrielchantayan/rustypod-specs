# F-5285a4e19423

## Purpose

F-5285a4e19423 conditionally returns a 16-bit value from storage associated with a caller-supplied object.

The function first selects and invokes an indirect dependency through the object’s dispatch structure. A zero dependency result produces a 16-bit zero return without any subsequent wrapper access to the object. A nonzero dependency result causes the function to read an associated-storage address from the object and return the 16-bit value at displacement 122 from that address.

This is a conditional-access contract. Describing the dependency as a validity, readiness, or availability check is inferred intent, not established behavior. In particular, a nonzero dependency result does not establish that the subsequent memory accesses are safe.

## Interface

**Input:** One object address.

The address is used to select an indirect callable target and is passed unchanged as the dependency’s visible argument. On the nonzero-result path, it is also used after the invocation to obtain an associated-storage address.

**Output:** One 16-bit value:

- Zero if the dependency returns zero.
- The bit pattern read from associated storage if the dependency returns nonzero.

The evidence does not establish a signed interpretation for the returned 16-bit pattern. It also does not establish how a caller widens that result. A nonzero stored value is not normalized to one.

### Represented layout

| Location | Established use |
|---|---|
| Beginning of the input object | Contains the representation used to obtain the dispatch-structure address |
| Displacement 8 from the dispatch-structure address | Contains the indirect callable target |
| Third integer-sized slot of the input object | Contains the representation used to obtain the associated-storage address |
| Displacement 122 from the associated-storage address | Begins the returned 16-bit value |

The third integer-sized slot has displacement twice the represented integer size. Under a 32-bit integer layout, that displacement is 8 bytes. This object-field displacement and the dispatch-entry displacement of 8 are separate locations in separate structures.

The supplied representation uses integer-sized storage in address calculations. It does not independently establish the complete target ABI, native pointer width, byte order, or alignment rules. Treating these representations as usable addresses is a platform prerequisite, not a portable serialization contract.

The result and associated-value access are 16 bits wide. Under an eight-bit-byte model, the value occupies bytes at offsets 122 and 123.

### Preconditions are path-specific

For target selection, the object’s initial dispatch-address field and the selected dispatch entry must be readable when accessed. The selected target must support the invocation.

The wrapper does **not** require the dispatch structure to remain readable after target selection. It does **not** require the input object to remain readable after a dependency that returns zero.

If the dependency returns nonzero, the object’s associated-address field must be readable when the wrapper subsequently accesses it. The resulting value location must then support the 16-bit read. Additional lifetime and argument requirements during the invocation belong to the unknown dependency contract.

## Behavior

### Target selection and invocation

The wrapper performs these observable operations in order:

1. Reads the dispatch-address representation from the beginning of the input object.
2. Reads the callable target at displacement 8 from that dispatch address.
3. Invokes the selected target with the original input object address as its visible argument.
4. Uses the dependency’s returned integer result to choose between the two return paths.

There is one indirect invocation along the shown normal control flow. No earlier branch bypasses that invocation. No retry, alternate target, or second invocation is shown.

Target selection is complete before the invocation begins. A dependency change to the object’s dispatch-address field or to the dispatch entry cannot change the target already selected for this invocation. The wrapper does not reload either location afterward.

The dispatch structure is storage used to select the callable target; its continued existence is distinct from the ability to execute that target. The wrapper places no further read requirement on the dispatch structure during or after the invocation. Whether the dependency itself needs that structure remains unknown.

### Zero-result path

If the dependency returns integer zero, the function returns the 16-bit zero pattern.

After the dependency returns zero, the wrapper performs no further access to:

- The input object.
- The dispatch structure.
- The associated-address field.
- The associated value.

Consequently, normal wrapper completion on this path does not depend on the input object remaining allocated or readable after the invocation. The dependency may invalidate or release the input object and still return zero, provided its own execution completes normally and its unknown contract permits that behavior.

This does not establish that the dependency avoids accessing the object or associated storage. The access restriction describes only the wrapper’s behavior after the call.

### Nonzero-result path

If the dependency returns any nonzero integer result, the wrapper:

- Reads the associated-address representation from the object’s third integer-sized slot.
- Forms the address at displacement 122 from that represented address.
- Reads and returns the 16-bit value at that location.

The zero comparison applies to the dependency’s integer result, not to the eventual 16-bit return value. There is no shown truncation of the dependency result to 16 bits before the branch. Any representable nonzero result selects the value-read path, including a negative result if the dependency’s result interpretation permits one.

A stored zero is returned unchanged. Therefore, a public return value of zero does not distinguish the zero-result path from a nonzero-result path that reads a stored zero.

### Post-call state determines the associated read

The associated-address field is read only after the dependency returns nonzero. The wrapper does not obtain a pre-call snapshot of that field.

If the dependency replaces the associated address and returns nonzero, the wrapper uses the replacement. If it modifies the selected value, the wrapper reads that location after the modification, assuming no subsequent interfering change.

These observations are not safety guarantees. If the dependency leaves the object unreadable, the nonzero path has no shown protection before reading its associated-address field. If the field is readable but identifies unusable storage, no validation precedes the value read.

### Address arithmetic and access boundaries

The dispatch-entry calculation uses displacement 8. The associated-value calculation uses displacement 122. The associated-address field is selected by integer-slot indexing, so its byte displacement depends on the represented integer width.

No explicit range check, null check, overflow check, address normalization, or alignment adjustment appears. Successful execution requires the computed addresses to be usable under the target environment.

The evidence does not establish defined behavior for integer overflow or an unusable integer-to-address interpretation. In particular, it does not support promising modular address wraparound as a recovery mechanism.

The ordering above describes the supplied control flow. It does not establish atomic accesses, volatile semantics, synchronization, or a cross-thread memory-order guarantee.

## Side effects

The wrapper contains no explicit write to the input object, dispatch structure, associated storage, or global storage. It selects a target, invokes it, conditionally reads a value, and returns a scalar result.

The complete operation is not established as side-effect-free. The dependency may modify or release memory, alter globals, perform external operations, or otherwise change state. No preservation guarantee for globals or other memory follows from the wrapper’s lack of explicit stores.

### Lifetime and ownership

No explicit allocation, release, ownership transfer, reference-count change, or cleanup operation appears in the wrapper. Returning a 16-bit value does not return an address or establish a borrowed-memory relationship.

The wrapper’s own access requirements are limited to the times and paths on which it reads memory:

- The initial object field must be readable when the dispatch address is obtained.
- The selected dispatch entry must be readable when the callable target is obtained.
- Neither location is reaccessed by the wrapper merely to carry out or complete the invocation.
- After a zero result, no object or dispatch-storage readability is required by the wrapper.
- After a nonzero result, the associated-address field must be readable for its post-call read.
- The selected value location must support the subsequent 16-bit read.

The dependency may release or invalidate the dispatch structure during invocation without preventing wrapper completion merely because that structure no longer exists. This remains conditional on normal dependency completion and the validity of the already selected callable target.

Likewise, the dependency may release or invalidate the input object and return zero without causing any subsequent wrapper access to that object. A nonzero result instead leads to a post-call object read; no lifetime repair or validation is shown.

The dependency’s own lifetime, ownership, and release rules remain unresolved.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence, not executed tests.

1. **Zero dependency result with a surviving object.**  
   Given valid target selection and a normally returning dependency, a zero result must produce a 16-bit zero. No associated-address or associated-value read occurs afterward.

2. **Zero dependency result after object release.**  
   Given successful target selection and a dependency that releases the input object and then returns zero normally, the wrapper must return zero without another object access. Whether that release is permitted during the dependency’s execution depends on its unknown contract.

3. **Dispatch structure released during invocation.**  
   Given a callable target already obtained from the dispatch entry, the dependency may release the dispatch structure without the wrapper subsequently reading it. If the dependency returns nonzero, normal completion still requires readable post-call associated-address and value locations; dispatch-storage survival is not an additional wrapper requirement.

4. **Nonzero dependency result with a nonzero stored value.**  
   Given readable post-call storage containing the 16-bit pattern 0x1234 at displacement 122, the function must return 0x1234. The target environment determines how that pattern is represented by bytes.

5. **Nonzero dependency result with a stored zero.**  
   The wrapper must perform the associated reads and return zero. Return value alone cannot distinguish this case from dependency zero.

6. **Associated address replaced during invocation.**  
   If the dependency replaces the associated-address field with another valid address and returns nonzero, the returned value must come from the replacement storage, not a pre-call address snapshot.

7. **Stored value modified during invocation.**  
   If the dependency modifies the selected value and returns nonzero, the wrapper reads the post-call value, assuming no further modification interferes.

8. **Unusable associated storage with dependency zero.**  
   If target selection and dependency execution complete normally, unusable associated storage does not prevent wrapper return through the zero branch. This makes no claim about dependency-internal accesses.

9. **Unreadable object after dependency nonzero.**  
   If the dependency leaves the associated-address field unreadable and returns nonzero, no successful return is guaranteed. The wrapper attempts the post-call field read without a shown safeguard.

10. **Readable object but unusable associated value.**  
    If the dependency returns nonzero and the associated-address field is readable but identifies an unusable value location, no fallback-to-zero behavior is specified.
