# F-378877c2d100

## Purpose

F-378877c2d100 repeatedly examines a control block’s first 32-bit word. When that word represents a nonzero record address, the function assigns the selected record’s first word to the control block’s first word, then invokes F-ff1bdc376dcd twice. When an examination finds zero, the function clears three additional control-block words and returns.

**Established static behavior:** the head assignment precedes both dependency calls. It does not necessarily remove the selected record from the first position. A self-linked record assigns its own address back to the head, and dependency effects can subsequently change that field.

**Inferred intent:** the access pattern resembles clearing a linked collection while disposing of a resource associated with each record and then disposing of the record itself. Resource release, memory deallocation, and ownership transfer are not established by the supplied evidence.

Traversal uses the control block’s current head on every iteration. It is not restricted to records reachable at entry.

## Behavior

### Selecting a record and updating the head

Each loop check reads the control block’s first 32-bit word.

If the value is zero, the function performs no record access or dependency call for that check and proceeds to finalization.

Otherwise, the value selects the record for the current iteration. The function retains that address, reads the selected record’s first 32-bit word, and assigns the value read to the control block’s head.

This is a head assignment, not an unconditional detachment:

- A zero record link installs zero.
- A link to another record installs that address.
- A self-link reinstalls the selected record’s own address.
- An arbitrary nonzero link is installed without local validation.

Even when the control block and selected record do not overlap, the head can therefore still name the selected record immediately after the assignment.

There are no stores addressed through the retained record pointer. However, the head store can modify selected-record storage if its destination overlaps that storage. Such a modification can affect the argument-field reads that follow.

### First dependency invocation

After the head assignment, the function obtains the selected record’s words at offsets 8 and 4 and calls F-ff1bdc376dcd with:

| Argument position | Value |
|---|---|
| First | 32-bit value read from selected-record offset 8 |
| Second | 32-bit value read from selected-record offset 4 |
| Third | Zero |

The head assignment precedes the argument-field reads used for this call. Therefore, if the head store overlaps either argument field, the call uses the value available after that store, not necessarily the value present at function entry or at record selection.

The supplied representation does not establish the relative evaluation order of the two argument-field reads. A contract requiring one of those reads to precede the other would exceed the evidence.

### Second dependency invocation

If the first invocation returns normally, the function calls F-ff1bdc376dcd again with:

| Argument position | Value |
|---|---|
| First | Retained selected-record address |
| Second | One |
| Third | Zero |

The address comes from the record selected for the current iteration. It is not replaced by rereading the control-block head after the first call.

No explicit record-field read occurs between the first invocation’s return and the second invocation. This does not establish that the first invocation may safely release the selected record: the second invocation’s requirements for the supplied address remain unknown.

Dependency return values are not used. There is no result-dependent branch, retry, or local error report.

### Continuing traversal

After both invocations return normally, the function rereads the control-block head at the next loop check.

The next selected record consequently depends on the state left by both invocations, not solely on the link installed before them. For example:

- A dependency can replace a nonzero head with zero, causing the next check to end traversal.
- A dependency can install a different valid record address, causing that record to be selected next.
- A dependency can restore an earlier address, potentially causing repeated processing.
- A dependency can invalidate storage that a later local operation attempts to access.

The function contains no visible protection against these effects. It also does not preserve a private copy of the remaining chain for later traversal.

### Finalization

After a loop check observes zero, the function performs three ordered 32-bit stores:

1. Zero to control-block offset 4.
2. Zero to control-block offset 8.
3. Zero to control-block offset 12.

No dependency invocation intervenes between these stores in the visible body.

There is no separate final store of zero to control-block offset 0. The zero head is a value observed by the terminating check, not a value unconditionally installed by finalization.

The three stores are not an atomic all-fields reset. If the control block overlaps record storage, they can also change fields in that storage. An initially empty control block still receives all three stores.
