# F-22f5795a2978

## Purpose

F-22f5795a2978 transforms selected groups of four input bytes into groups of three output bytes, using a shared byte-translation table. It first removes a table-defined leading class and a limited table-defined trailing class. It then requires the remaining input length to be divisible by four.

The operation resembles a radix-64 decoder, but that interpretation is **inferred intent**, not the established contract. The supplied evidence does not identify the table contents, a character alphabet, or a standard encoding. In particular, successful translation accepts table values from 0 through 127, rather than restricting them to six bits.

Success returns the number of output bytes written. Rejection returns −1. Rejection is not transactional: output from earlier accepted groups remains written.

## Interface

The function has three arguments:

| Argument | Interpretation |
|---|---|
| Destination | Pointer to writable bytes receiving the transformed output. |
| Source | Pointer to input bytes, also read during boundary classification. |
| Length | Unsigned 32-bit quantity describing the initial input extent, subject to the signed comparisons described below. |

The result is a signed 32-bit integer in the supplied representation.

The source and destination elements are eight-bit bytes. Every table index is formed by retaining only the low seven bits of an input byte, so indices range from 0 through 127.

A shared reference identifies the translation table. The function captures this reference at entry for use during group transformation. Boundary classification instead uses the shared reference as it is read during those checks.

### Caller obligations

For ordinary successful use, the caller must provide:

- Readable source storage for the supplied input extent.
- Readable source storage at any additional position inspected by the leading-boundary check, including the position immediately after an entirely stripped input.
- A valid table reference and readable entries for every index encountered.
- Writable destination storage for three bytes per accepted four-byte group.
- Pointer arithmetic and storage extents that remain valid throughout execution.

The function receives no destination capacity and performs no destination-bounds check.

A zero length does **not** eliminate the source-read requirement: the leading-boundary condition classifies the current source byte before testing whether the remaining length is positive.

No ownership transfer, allocation, deallocation, or retention of either caller pointer is visible. The function changes only its local copies of the pointers.

## Behavior

### 1. Capture the transformation table reference

Before examining the boundaries, the function captures the current shared table reference. This captured reference is used for all subsequent four-byte group transformations.

The distinction between the captured reference and the reference read during trimming is established by the supplied body. Whether an external actor can safely change the shared reference during execution is not established.

### 2. Remove the leading class

The function repeatedly classifies the current source byte:

- Read the current input byte.
- Mask it to its low seven bits.
- Read the corresponding entry through the shared table reference.
- Interpret that table entry as a signed eight-bit value for this comparison.

An entry whose byte representation is `0xE0` qualifies for leading removal. The function advances the source by one byte and decrements the remaining length only if the remaining length, interpreted as signed 32-bit, is strictly positive.

The classification precedes that length test. Consequences include:

- With an initial length of zero, one source byte and its table entry are still read.
- If every byte of a positive-length input is removed, the next condition evaluation reads and classifies the byte immediately after that input.
- A length with its high bit set does not cause leading removal, but the initial classification still occurs.

Only table value `0xE0` is removed at this stage. Other values in the trailing-removal class are not interchangeable with it.

### 3. Remove the trailing class, stopping at three bytes

After leading removal, the function examines trailing bytes while the remaining length, interpreted as signed 32-bit, exceeds three.

For each such examination, it reads the last byte of the current remaining span, masks it to seven bits, and looks up its table value through the shared table reference.

A trailing byte qualifies for removal exactly when its table value is one of:

- `0xE0`, `0xE1`, `0xE2`, `0xE3`
- `0xF0`, `0xF1`, `0xF2`, `0xF3`

Each qualifying byte reduces the remaining length by one. The source start does not move during this stage.

Trailing removal stops when either:

- The last byte does not belong to that class; or
- The remaining signed length is three or less.

Therefore, trailing removal does not strip a span all the way to zero. For example, four trailing-class bytes remaining after the leading stage are reduced to three, not zero.

There is no recognition here of a standard padding syntax or a permissible padding count.

### 4. Check divisibility

The remaining unsigned length must have its low two bits clear.

If it is not divisible by four, the function returns −1 without transforming any group and without writing destination bytes.

This check occurs after boundary reads and removal. It does not prevent the earlier reads.

If the remaining length is zero, the function returns zero without writing output.

### 5. Translate and validate each four-byte group

For a positive, divisible-by-four remaining length, the function processes groups from the adjusted source start toward the end.

For each group, all four input bytes are translated through the captured table reference, with each input byte masked to seven bits.

The supplied body establishes this access sequence:

1. Read the first raw input byte.
2. Read and translate the second input byte.
3. Translate the saved first input byte.
4. Read and translate the third input byte.
5. Read and translate the fourth input byte.

All four translations precede group validation. An invalid first translation therefore does not prevent the later translations in that group from being read.

A group is rejected if any translated byte has its high bit set. Equivalently, all four translated values must lie between 0 and 127 inclusive.

On rejection:

- Return −1.
- Write no output bytes for that group.
- Preserve any output already written for earlier groups.
- Do not process subsequent groups.

There is no separate validation that accepted values fit within six bits.

### 6. Emit three bytes for an accepted group

Let \(a,b,c,d\) denote the four translated values in input order. These are explanatory mathematical names, not additional interface state.

The three output bytes are:

\[
\begin{aligned}
o_0 &= \operatorname{low8}\big((a \ll 2)\mathbin{\mathrm{OR}}(b \gg 4)\big),\\
o_1 &= \operatorname{low8}\big((b \ll 4)\mathbin{\mathrm{OR}}(c \gg 2)\big),\\
o_2 &= \operatorname{low8}\big((c \ll 6)\mathbin{\mathrm{OR}}d\big).
\end{aligned}
\]

Here, \(\operatorname{low8}\) retains only the low eight bits. The shifts and intermediate combinations are represented using 32-bit arithmetic in the supplied body.

The destination writes occur in order:

1. First output byte.
2. Second output byte.
3. Third output byte.

The next group starts four input bytes later and writes three destination bytes later.

Because values 64 through 127 are accepted, high bits can affect adjacent packed fields or be discarded by narrowing. The behavior must not be replaced with a transformation that first masks translated values to six bits.

### 7. Return the output count

After all groups are accepted, return three times the number of processed groups.

For an ordinary positive signed length, if the post-trimming length is \(n\), successful output size is \(3n/4\).

The largest positive signed length divisible by four is 2,147,483,644. Its corresponding output count is 1,610,612,733, which fits in signed 32-bit storage. The group-progress and output-count arithmetic therefore do not overflow within that positive-length processing range, assuming valid storage and pointer arithmetic.

### High-bit length behavior

Lengths from `0x80000000` through `0xFFFFFFFF` are treated as nonpositive by the signed loop comparisons.

After the initial leading-classification read:

- Neither removal loop consumes bytes.
- If the length is divisible by four, the group loop exits immediately and the result is zero.
- Otherwise, the result is −1.

Thus a high-bit length is not processed as a large positive input extent. This is established behavior of the supplied representation, not evidence of an intentional supported input range.

## Side effects

### Destination mutation

Only accepted groups write destination bytes. A later error does not undo earlier writes.

On any normal return of −1, the return value alone does not report how many bytes were already written.

No output terminator is appended. No destination bytes beyond the accepted three-byte groups are explicitly initialized or cleared.

### Source and shared state

The function performs no explicit writes through the source pointer and no explicit updates to the shared table reference.

That does not establish source immutability when storage overlaps. Destination writes can modify source storage, table storage, or the shared-reference storage if the caller arranges such aliasing.

All four bytes of a group are translated before that group writes output. However, output from an earlier group can affect later reads if the corresponding storage overlaps. No general arbitrary-overlap guarantee is established.

Boundary classification completes before output writes begin. Accordingly, destination aliasing cannot retroactively change which boundaries were removed, although it can affect later group transformation reads.

### Errors and memory validity

The only explicit failure result is −1 for:

- A remaining length not divisible by four.
- A translated group containing a high-bit-set table value.

There is no explicit handling for null pointers, unreadable memory, insufficient output capacity, or invalid table references. A defined return or recovery behavior for those conditions is not established.

## Dependencies

The operation depends on shared data:

The table’s initialization, complete contents, lifetime, mutability, and synchronization rules are not supplied. No assumption is made about an unseen initializer or other external function preserving globals or owning memory.

## Acceptance examples

These examples are conditional static predictions, not executed tests. Unless stated otherwise, assume valid disjoint buffers, sufficient destination capacity, a valid stable table, and no external mutation.

### Empty input still reads

Given length zero and a readable current source byte with a readable indexed table entry:

- The leading check reads and classifies that byte.
- No bytes are removed or written.
- The result is zero.

An unreadable source does not become valid merely because the length is zero.

### Entirely removable leading input

Given length two, both included bytes mapping to `0xE0`, and a readable byte immediately afterward:

- Both included bytes are removed.
- The following byte is also classified during the next condition evaluation.
- The result is zero.
- The destination remains unchanged.

### Three trailing-class bytes are retained for rejection

Given three input bytes, none mapping to `0xE0` at the leading boundary, and all mapping to `0xF0`:

- Leading removal does not advance.
- Trailing removal does not run because the length is not greater than three.
- The result is −1 because three is not divisible by four.
- No output is written.

### One removable trailing byte after a valid group

Given five bytes whose first four translate to 0, 1, 2, and 3, and whose fifth maps to `0xF0`:

- The fifth byte is removed.
- The remaining four-byte group is accepted.
- Output is `0x00`, `0x10`, `0x83`.
- The result is three.

### Low-seven-bit input equivalence

If two source spans differ only in the high bits of their input bytes, and all other conditions remain identical, they access identical table indices. They therefore receive identical trimming and transformation decisions.

### Accepted seven-bit translations

Given a four-byte group whose translated values are all 64:

- The group is accepted.
- Output is `0x04`, `0x10`, `0x40`.
- The result is three.

A decoder that rejects these translations or masks them to zero before packing would not preserve this behavior.

### Partial output before rejection

Given eight bytes, no trimming, a valid first group, and a second group containing a translation of `0x80`:

- Three output bytes from the first group are written.
- All four translations of the second group are read.
- No output from the second group is written.
- The result is −1.

### High-bit lengths

Given a readable initial classification location:

- Length `0x80000000` returns zero without output.
- Length `0x80000001` returns −1 without output.

Neither case processes input groups.

## Uncertainties

The following remain **documented_only**:

- The concrete input alphabet and complete table contents.
- Whether the leading class represents whitespace.
- Whether the trailing class represents padding, whitespace, another delimiter class, or a mixture.
- Whether callers intentionally rely on high-bit lengths or seven-bit translated values.
- The actual destination capacity available at call sites.
- Any supported overlap policy beyond the established read-before-write behavior within a group.
- Whether the shared reference can change during execution under a defined synchronization model.
- Platform-specific behavior for invalid memory accesses.

The radix-64 interpretation is inferred intent only. It does not justify adding alphabet checks, canonical-padding checks, six-bit masking, or transactional output.
