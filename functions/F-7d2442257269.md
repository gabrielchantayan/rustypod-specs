# F-7d2442257269

## Purpose

F-7d2442257269 obtains an object pointer, writes an initial 32-bit value into that object, publishes the pointer through shared storage, conditionally initializes another shared field, and performs ordered operations over two resource entries and three initialization entries.

On ordinary completion, it clears the 32-bit object field at byte offset 0x2D0 and returns the originally obtained pointer.

“Object,” “context,” “resource,” and “initialization” describe observable roles, not established application types or semantics. The evidence establishes memory accesses, call arguments, sequencing, and control flow. It does not establish allocation contracts, ownership, or the purpose of the surrounding subsystem.

## Interface

### Explicit inputs and output

The function has no explicit parameters.

Its ordinary output is the pointer returned by F-ff29814bf4cc at the beginning of execution. That pointer is retained independently of the shared field through which it is subsequently published.

There is no visible recoverable error result. A resource-creation result equal to signed 32-bit −1 causes a call to F-a817d8d58c10, whose call site is marked non-returning.

## Behavior

### 1. Obtain, initialize, and publish the object

The function first calls F-ff29814bf4cc without explicit arguments and retains its returned pointer.

It then captures the shared-state base and performs two direct writes in order:

1. Write the configured 32-bit initial value at object offset 0.
2. Store the retained object pointer at shared-state offset 0x30.

The shared-state base remains the captured address for the subsequent shared-field accesses. Later changes to the storage supplying that base do not themselves redirect those accesses.

Publication precedes the conditional initialization, resource processing, entry processing, and final object-field clear. The function therefore exposes the pointer before completing its remaining work; safe external observation of that partially initialized state is not established.

### 2. Conditionally update shared-state offset 0x5C

The function reads the 32-bit field at shared-state offset 0x5C.

If the value is nonzero, it skips this branch.

If the value is zero, it:

1. Calls F-8157a180d901 with integer argument 28.
2. Calls F-72538fc0941d without explicit arguments.
3. Stores the 32-bit result of F-72538fc0941d at shared-state offset 0x5C.

No explicit result from the first call is passed to the second. An allocation-and-construction relationship is therefore not established.

The field is not checked again after either call. The final store occurs even if a dependency has changed that field in the meantime. A zero result is stored without rejection or immediate retry.

### 3. Initialize context, capture snapshots, and retain resource inputs

The function calls F-U1 and passes an address four bytes beyond its result to F-379efa3ca9d1. The other arguments are zero and a configured 32-bit value.

It then performs this ordered sequence:

1. Call F-U1 again; its returned value is not consumed by this function.
2. Read the first 32-bit snapshot through its configured source address.
3. Store that snapshot at shared-state offset 0x28.
4. Call F-U1 a third time; its returned value is again not consumed.
5. Capture the resource-result table base.
6. Capture the common 32-bit resource-creation argument.
7. Read the second 32-bit snapshot through its configured source address.
8. Store that snapshot at shared-state offset 0x2C.

The apparently unused F-U1 calls are observable dependency calls. They precede their respective snapshot reads and cannot be treated as side-effect-free.

The resource-table base is captured **before** the common creation argument, and **both captures precede** the second snapshot read and offset-0x2C store. This ordering is significant even without an intervening dependency call: if that store aliases storage supplying either captured input, the resource loop still uses the values captured before the store. It does not reload them afterward.

The resource-table base and common argument remain retained throughout both resource iterations.

### 4. Process resource indices zero and one

For each resource index, in ascending order, the function:

1. Calls F-U2.
2. Calls F-c930571cdede with the F-U2 result, the retained common argument, the retained object pointer, and zero.
3. Stores the 32-bit creation result in the retained resource table at the current index.
4. Compares that creation result with signed 32-bit −1.
5. If equal, calls F-a817d8d58c10.
6. Otherwise, calls F-U2 again.
7. Reads the current resource-table entry.
8. Calls F-23aadb16b673 with the second F-U2 result and the table-read value.
9. Calls F-352a899fb784 with the retained object pointer, the current index, and zero.
10. Captures the current byte-region base.
11. Captures the current word-clearing-table base.
12. Advances the index, retaining only its low eight bits, and continues while it is below two.

The failure comparison uses the creation result, not a subsequent table read. The sentinel is the 32-bit pattern corresponding to −1; no other result value is explicitly rejected.

The result-table store precedes the failure check. On the annotated failure path, the table already contains −1 when F-a817d8d58c10 is invoked.

On the successful path, the value supplied to F-23aadb16b673 is reread after the second F-U2 call. It may differ from the creation result if that dependency changes the entry. A change to the shared storage supplying the resource-table base does not redirect this read: the table base was retained before the loop.

The byte-region and word-clearing-table bases are captured after F-352a899fb784 in each successful iteration. The captures from index one are the ones used in the subsequent entry loop.

### 5. Process entry indices zero, one, and two

After completing the resource loop, the function reads the byte-region base once more and derives an address three bytes before that freshly read base.

This is a separate capture from the byte-region base retained at the end of resource index one.

For each entry index, in ascending order, the function:

1. Calls F-ca1c4e2f14bb with the retained object pointer, index, and one.
2. Calls F-U1.
3. Calls F-39405f5827ef with the returned context address plus four and the index.
4. Writes one zero byte at the fresh byte-region base minus three, plus the index.
5. Writes one zero byte at the retained byte-region base plus the index.
6. Writes one 32-bit zero at the retained word-clearing-table base plus four times the index.
7. Calls F-88707f7d96dd with the retained object pointer and index.

The three direct stores are separate ordered operations between F-39405f5827ef and F-88707f7d96dd. They are not one bulk clear.

Neither byte destination base nor the word-table base is refreshed inside this loop. Dependency changes to the storage supplying those bases do not redirect later direct clears.

If the fresh and retained byte-region bases are equal, the byte stores cover offsets −3 through −1 and 0 through 2 around that common base. Equality is not guaranteed; the regions may be separate or overlap.

### 6. Complete and return

After all three entry iterations, the function writes a 32-bit zero at object offset 0x2D0 and returns the originally retained object pointer.

It does not obtain the return pointer by rereading shared-state offset 0x30. Changing that shared field alone does not change the returned pointer.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests.

### Nonzero conditional field

Given valid storage, successful resource results, returning dependencies, and a nonzero value at shared offset 0x5C when checked:

- Neither conditional dependency is called.
- Resource indices zero and one and entry indices zero through two are processed.
- The final direct object write clears offset 0x2D0.
- The originally obtained pointer is returned.

### Zero conditional result

Given a zero checked field and a zero result from F-72538fc0941d:

- F-8157a180d901 receives 28 before F-72538fc0941d is called.
- Zero is stored at offset 0x5C.
- Processing continues without an immediate retry or rejection.

### Snapshot-store aliasing with captured resource inputs

Suppose, immediately after the third F-U1 call, the resource-table source contains address A and the common-argument source contains value K.

The function captures A first, then K, then reads and stores the second snapshot. If the offset-0x2C store changes either source through aliasing, the resource loop nevertheless uses A and K. If those destinations also alias resource entries or other accessed storage, their additional effects remain governed by the subsequent ordered accesses.

### Failure at resource index zero

If the first creation result is −1:

- Resource-table entry zero receives −1.
- F-a817d8d58c10 is called before any association for that index.
- Under the non-returning annotation, no second resource iteration, entry processing, final object clear, or ordinary return follows.

### Failure at resource index one

If index zero succeeds and index one returns −1:

- Index zero completes its association, F-352a899fb784 call, and base captures.
- Entry one receives −1 before the error call.
- No association for index one or subsequent entry loop follows under the annotation.

### Table mutation during provider execution

If the second F-U2 call for an index replaces that index’s resource-table value, F-23aadb16b673 receives the replacement value. The earlier failure decision still concerns the original creation result.

### Distinct byte-base captures

If the retained byte-region base is A and the fresh post-resource-loop base is B, entry index j clears one byte at B−3+j, then one byte at A+j, then its retained word-table entry.

Across the three iterations, the byte destinations are B−3 through B−1 and A through A+2. Adjacency is not required.
