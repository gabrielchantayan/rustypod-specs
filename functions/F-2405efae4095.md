# F-2405efae4095

## Purpose

F-2405efae4095 is represented as a non-returning dispatch sequence that reads a selector byte, clears the byte at a selector-derived address, and repeatedly invokes indirect dependencies.

The visible behavior includes:

- Extracting an unsigned value from incoming execution context.
- Performing one selector-based byte clear before any dependency call.
- Making two initialization calls.
- Repeating ten calls in a fixed order, with another selector-based clear between the fifth and sixth calls.
- Transforming selected call results into subsequent arguments.
- Changing the target of the first call site in the repeated sequence after its first invocation.

No application-level purpose is established. The cleared byte is not identified as a flag, lock, status field, or device register. Likewise, the call sequence is not established to implement scheduling, polling, communication, or another particular service.

The supplied representation reports invalid instruction data and removal of unreachable regions. This contract describes the visible path, subject to that control-flow limitation.

### Width and arithmetic model

The representation distinguishes byte accesses, signed integers, and unsigned integers. It does not supply authoritative type definitions or an ABI.

### Memory interface and layout

Each direct memory operation uses a one-byte selector and a one-byte destination:

- Selector address: index input multiplied by 1,024, plus one.

- Destination address: selector value plus 17.

Under either ordinary unbounded integer arithmetic or 32-bit wrapping address arithmetic, the selector address is congruent to one modulo 1,024. No address from 17 through 272 has that property. The selector address therefore cannot numerically equal a destination address under either model.

No multi-byte record layout is involved in the explicit accesses. The representation establishes neither alignment requirements for call targets nor the memory mapping behind these numerical addresses.

## Behavior

### Dependency notation

F-U01 through F-U12 are opaque, site-based dependency labels assigned for this contract. They do not identify independently established functions.

In particular, F-U03 denotes one call site with two visible target values. Its first and later invocations must not be assumed to reach the same function or have identical behavior.

### Initialization

The visible initialization proceeds in this order:

1. Extract the packed-word input shifted right by 20 bits.
2. Read the selector byte at the index-derived address.
3. Write zero to the byte at the selector value plus 17.
4. Invoke F-U01 at the dispatch-base input plus `0xF74`, passing twice the extracted value.
5. Establish `0x08832789` as the initial target base for F-U03.
6. Invoke F-U02 at numerical target `0x08833785` and retain its result.

The initial extracted value ranges from 0 through 4,095 under the 32-bit model. F-U01 therefore receives an even value from 0 through 8,190. This particular left shift loses no set bits.

F-U01’s result is not explicitly consumed. F-U02’s result becomes the first argument of the first F-U03 invocation without the two-bit shift used for later iterations.

F-U03’s initial target is its initial base plus `0xFFE`:

- Initial base: `0x08832789`.
- First target: `0x08833787`.

This target selection is independent of the result returned by F-U02 in the displayed data flow.

### Repeated sequence

Each complete iteration contains the following operations:

| Order | Operation | Explicit result use |
|---|---|---|
| 1 | Invoke F-U03 with the carried argument and the working unsigned value shifted right by eight bits. | Result not consumed. |
| 2 | Invoke F-U04. | Result not consumed. |
| 3 | Invoke F-U05. | Result not consumed. |
| 4 | Invoke F-U06. | Result not consumed. |
| 5 | Invoke F-U07. | Result retained for F-U08. |
| 6 | Read the selector byte again, then write zero to the newly selected destination byte. | No returned value. |
| 7 | Invoke F-U08 with the F-U07 result shifted left by two bits. | Result not consumed. |
| 8 | Invoke F-U09. | Result not consumed. |
| 9 | Invoke F-U10. | Result not consumed. |
| 10 | Invoke F-U11. | Result not consumed. |
| 11 | Invoke F-U12. | Result determines the next iteration’s argument state. |

Except for F-U03 and F-U08, these iteration calls have no explicit arguments in the representation. This does not establish that they ignore implicit register inputs, shared memory, or processor state.

The selector read and zero store occur after F-U07 returns and before F-U08 is invoked. The selector is not visibly cached between clear operations.

### Changing F-U03 target

During the first iteration, after F-U11 and before F-U12, the carried target base for F-U03 is replaced with `0x088327C7`.

Consequently:

| Invocation of F-U03 | Carried base | Numerical target after adding `0xFFE` |
|---|---|---|
| First | `0x08832789` | `0x08833787` |
| Second and subsequent | `0x088327C7` | `0x088337C5` |

Each later iteration reestablishes the latter base before its F-U12 call. The displayed loop does not restore the initial base.

This is a target transition, not merely an argument transition. A consumer reproducing the visible behavior must distinguish it even if both targets accept the same apparent argument shape. Their actual interfaces and effects remain unknown.

### Argument state between iterations

Let the result of a completed F-U12 invocation be the source for the next iteration’s argument state.

Under wrapping 32-bit word semantics:

- The next first argument to F-U03 is that result shifted left by two bits, retaining the low 32 bits.
- The next unsigned working value is that result shifted left by 26 bits, retaining the low 32 bits.
- F-U03 receives the working value shifted right logically by eight bits as its second argument.

These relationships mean:

- The next first argument preserves only the low 30 bits of the result, positioned in bits 2 through 31.
- The working value preserves only the low six bits, positioned in bits 26 through 31.
- The next second argument is the low six bits of the result multiplied by 262,144.

The second argument therefore has different origins across the target transition:

- At the first target, it is the top four bits of the original packed-word input: a value from 0 through 15.
- At the later target, it is a value from 0 through 16,515,072 in increments of 262,144.

The F-U07 result feeds F-U08 within the same iteration. It is not the explicitly shown source of the next iteration’s argument state.

### Continuation and counts

The visible back edge is unconditional. If all accesses and calls complete normally, execution repeats indefinitely.

After completion of exactly \(n\) iterations, the visible path has performed:

## Side effects

### Direct memory effects

Each clear consists of a selector-byte read followed by a zero-byte store to the selected numerical address. No read of the previous destination value is visible.

The store is performed regardless of whether the destination already contains zero. Repeated stores may be independently observable, particularly if the environment maps these addresses to devices.

The numerical non-overlap established above means a clear cannot directly overwrite its own selector by numerical address equality under the stated arithmetic models. Physical aliasing through an unspecified memory mapping is not established.

Dependencies or other actors may nevertheless change the selector between reads. The next clear then uses the newly observed selector value.

No atomicity guarantee, barrier, synchronization protocol, or concurrent-access policy is established.

## Acceptance examples

These are conditional consequences of static evidence, not runtime observations. They require all preceding accesses and calls to complete normally. Examples involving overflowing signed expressions additionally require the stated wrapping word interpretation.

### Initial extraction and first target

For packed-word input `0xABCDEF12`:

- The initial extracted value is `0xABC`.
- F-U01 receives `0x1578`.
- The first F-U03 invocation targets `0x08833787`.
- Its second argument is `0xA`.
- Its first argument is the F-U02 result, without a two-bit shift.

The initialization byte clear precedes F-U01.

### Target and argument transition

Suppose F-U02 returns 3 and the first F-U12 returns 65.

- The first F-U03 call targets `0x08833787` and receives 3 as its first argument.
- The second F-U03 call targets `0x088337C5`.
- Under wrapping 32-bit semantics, the second call receives 260 as its first argument and 262,144 as its second argument.
- A third F-U03 invocation, if reached, again targets `0x088337C5`; its arguments depend on the second F-U12 result.

Keeping the first target for all iterations would not satisfy the displayed behavior. Neither would assuming that the target change makes the two dependencies behaviorally interchangeable.

### Selector changes

Suppose the initial selector read yields 5, and a later F-U07 invocation leaves the selector byte containing 9.

- The initialization clear targets numerical address 22.
- That iteration’s clear targets numerical address 26.
- The later selector read and store occur after F-U07 and before F-U08.

Reusing the initial selector value would violate the visible read sequence.

### Selector extremes and non-overlap

A selector value of zero selects address 17; a selector value of 255 selects address 272.

For an index input of zero, the selector address is one. A zero store to address 17 or 272 does not numerically overwrite that selector.

More generally, the selector address remains congruent to one modulo 1,024 under the stated wrapping model, excluding equality with every possible destination address.

These numerical properties do not prove that any access is permitted.

### F-U07 result transformation

If F-U07 returns 7:

- The selector read and zero store occur before F-U08.
- F-U08 receives 28.
- The next iteration’s F-U03 arguments still depend on F-U12, not this F-U07 result.
