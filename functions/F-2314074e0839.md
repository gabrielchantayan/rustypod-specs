# F-2314074e0839

## Purpose

F-2314074e0839 conditionally updates a 16-bit destination word using an 8-bit weight, a 16-bit source word, and a caller-supplied callback.

The established behavior is a masked, three-field interpolation followed by callback conversion. The fields occupy bits 11–15, 5–10, and 0–4. This layout is consistent with RGB565, but color semantics and the purpose of the callback are inferred intent, not established requirements.

A zero weight produces an immediate return without accessing the source, callback, or destination. For every other representable weight, the function invokes the callback twice and eventually stores the low 16 bits of the second callback result into the destination, provided both calls return normally.

The supplied representation also contains a branch for weight 256. That branch is unreachable under the stated 8-bit weight load. It must not be treated as an available full-replacement operation.

## Interface

### Inputs

The function receives four arguments:

| Position | Contract role | Observed use |
|---|---|---|
| 1 | Weight address | Read once as an unsigned 8-bit value. |
| 2 | Source-word address | Read as an unsigned 16-bit value on the reachable nonzero path, after the first callback returns. |
| 3 | Callback entry point | Invoked indirectly; identified in this document as F-CB-01. |
| 4 | Destination-word address | Read as a 16-bit word before the first callback, then written as a 16-bit word after the second callback. |

F-CB-01 is a specification-local opaque dependency label. No concrete callback identity is established by the supplied dependency map.

### Output

The function has no explicit return value. Its direct output, when the nonzero path completes normally, is one 16-bit destination write.

The zero-weight path performs no destination write.

### Widths and interpretation

The arithmetic described by the supplied representation uses:

- An unsigned 8-bit weight, widened to 32 bits.
- A 16-bit unsigned source value, widened to 32 bits.
- A 16-bit destination word passed to the first callback.
- A first callback result consumed as a 32-bit unsigned value.

The callback’s actual machine-level calling convention, declared parameter type, and declared return type are not established. This contract describes the values consumed and produced at this call site, rather than asserting a complete callback ABI.

## Behavior

### Zero-weight path

The first observable memory operation established by the body is the one-byte weight read.

If that value is zero, the function returns immediately. It does not:

- Read the source word.
- Read the destination word.
- Invoke F-CB-01.
- Write the destination.

Consequently, source, destination, and callback validity are not requirements of this path. This does not relax the requirement that the weight itself be readable.

### Reachable nonzero path

For weights 1 through 255, the established order is:

1. Read the destination word.
2. Invoke F-CB-01 with that destination value.
3. Receive the first callback result.
4. Read the source word.
5. Compute the three masked field results.
6. Invoke F-CB-01 with their packed combination.
7. Receive the second callback result.
8. Store its low 16 bits into the destination.

The weight is not reread. A callback modification to the weight’s storage therefore cannot change the weight already selected for this invocation.

The source is deliberately not described as a snapshot taken at entry. Its value is obtained after the first callback completes. A callback that changes source storage can affect the interpolation in the same invocation.

Likewise, the final store is not conditional on the destination retaining its earlier value. If the callbacks modify destination storage and the second call returns normally, the function still performs its final 16-bit store.

### Field calculation

Let:

- \(w\) be the captured weight.
- \(S\) be the source word read after the first callback.
- \(B\) be the first callback result.
- \(M\) be one of the masks \(0xF800\), \(0x07E0\), or \(0x001F\).

Each field is calculated independently using:

\[
D_M=(S\mathbin{\&}M)-(B\mathbin{\&}M)
\]

\[
Q_M=\operatorname{trunc}_{0}\left(\frac{wD_M}{256}\right)
\]

\[
R_M=\big((B\mathbin{\&}M)+Q_M\big)\mathbin{\&}M
\]

Here, \(\operatorname{trunc}_{0}\) means truncation toward zero, including for negative values.

The second callback receives:

\[
P=R_{0xF800}\mathbin{|}R_{0x07E0}\mathbin{|}R_{0x001F}
\]

The masks partition the low 16 bits, so \(P\) lies between 0 and 65535 inclusive. Bits above bit 15 in the first callback result do not participate in this calculation.

The mask operation occurs after adding the scaled difference. This matters: the function operates on values in their packed bit positions, rather than first reducing all three fields to small, right-aligned channel numbers.

In particular, truncation toward zero is not the only quantization step. Remasking discards bits below each field’s position. A small downward adjustment to a high-position field can therefore move that field down by one encoded level even when a corresponding small upward adjustment would leave it unchanged.

### Arithmetic bounds

The largest field magnitude is \(0xF800=63488\). With the maximum reachable weight of 255, the largest product magnitude is:

\[
63488\times255=16189440
\]

This fits in a signed 32-bit integer. The other two field products are smaller.

Although the supplied arithmetic includes unsigned subtraction and multiplication before signed interpretation, the bounded values support the signed-difference description above under the represented 32-bit integer semantics. Negative products are adjusted before the final right shift so that the effective division by 256 truncates toward zero rather than toward negative infinity.

The mask removes any unwanted bits after each field adjustment. There is no separately established saturation or clamping operation.

### Unreachable 256 branch

The supplied representation includes a separate branch that would read the source, invoke F-CB-01 once with it, and store the low 16 bits of that callback result into the destination.

Its condition compares the captured weight with 256. An unsigned one-byte read can produce only 0 through 255, so this branch cannot be selected through the stated interface.

Whether that branch reflects an inaccurate recovered type, obsolete logic, or another origin is unknown. This contract does not widen the weight to make it reachable.

## Side effects

### Direct memory effects

On a normal zero-weight return, the only direct memory access established by the body is the weight read.

On a normal nonzero return, the function directly performs:

- One weight-byte read.
- One destination-word read.
- One source-word read.
- One destination-word write.

There are no additional explicit stores, allocations, releases, or global accesses in the supplied body.

This statement applies only to the function’s own operations. It does not constrain F-CB-01.

### Callback effects and ownership

F-CB-01 may have additional effects that are not described by the supplied evidence. In particular, this contract does not assume that it:

- Preserves global state.
- Preserves source or destination contents.
- Preserves storage lifetime.

The function does not explicitly transfer ownership of any supplied storage. It passes scalar values to the callback, not the source or destination addresses as explicit arguments. This does not establish that the callback cannot access that storage through other means.

No rollback is implemented. If callback activity occurs and a later operation fails or does not complete, the supplied body provides no mechanism to reverse earlier effects.

### Aliasing

No disjointness check or explicit non-aliasing requirement is present.

For example, source and destination may identify the same word if the required accesses remain valid. The first callback still receives the earlier destination read, while the source read occurs afterward and may observe callback modifications.

If the final destination store overlaps the weight byte, it may change the weight stored in memory, but it does not change the weight already used in this invocation.

The precise consequences of arbitrary partial overlap depend on the memory layout, byte order, and validity rules of the execution environment.

### Errors and abnormal completion

There is no explicit error result or internal recovery path.

Invalid memory access, an invalid callback target, callback non-return, or callback-driven invalidation of later-accessed storage can prevent normal completion. The exact platform response is documented_only.

If the second callback does not return normally, the final destination store is not reached. Callback side effects may already have occurred.

## Acceptance examples

These examples are conditional behavioral expectations, not recorded runtime results. Numeric examples assume ordinary 32-bit arithmetic as represented, valid storage, normal callback returns, and no unmentioned concurrent changes.

### Zero weight suppresses all later access

Given a readable weight byte containing zero, the function returns after reading that byte.

It must not invoke F-CB-01 or access source or destination storage, even if the other arguments would be unusable on the nonzero path.

### Identity callback, upward half-weight adjustment

Given:

- Weight 128.
- Source word \(0xFFFF\).
- Destination word \(0x0000\).
- F-CB-01 returns its input unchanged.

The first callback receives \(0x0000\). The second receives \(0x7BEF\), and the destination becomes \(0x7BEF\).

This result includes the post-adjustment masks; it is not simply the unmasked half of the packed source word.

### Maximum representable weight is not full replacement

With the same source, destination, and identity callback, but weight 255, the second callback receives \(0xF7DE\).

The destination becomes \(0xF7DE\), not \(0xFFFF\). A caller cannot request the separate 256 branch by storing a single-byte weight.

### Downward low-field adjustment truncates toward zero

Given weight 1, source \(0x0000\), destination \(0x0001\), and an identity callback, the low-field product is \(-1\).

Division by 256 truncates to zero. The second callback receives \(0x0001\), and the destination remains \(0x0001\).

### High-position remasking can expose a one-level decrease

Given weight 1, source \(0x0000\), destination \(0xF800\), and an identity callback, the high-field adjustment is \(-248\).

Adding that adjustment gives \(0xF708\), which becomes \(0xF000\) after applying the high-field mask. The second callback therefore receives \(0xF000\).

### Source changes during the first callback are observable

Suppose the first callback changes the source word before returning.

The calculation uses the source value read after that change, not the value present when the function was entered. The captured weight and the destination value already passed to the first callback are unaffected by that later source read.

### Final callback controls stored representation

If the second callback returns a value whose low 16 bits are \(0x1234\), the final destination word is \(0x1234\), regardless of the packed argument supplied to that call.

Any higher return bits are discarded by the observed store path.

## Uncertainties

### Inferred intent

The masks strongly suggest a 5/6/5 packed representation, plausibly RGB565. The weight and division by 256 suggest interpolation between a callback-derived destination representation and the source.

Neither interpretation establishes color space, channel names, gamma behavior, or conversion semantics.

### Documented-only unknowns

The following remain unresolved:

- The callback’s concrete identity, ABI, and semantic contract.
- Whether callback state changes are intentional or incidental.
- The execution environment’s byte order and alignment requirements.
- The validity and lifetime guarantees attached to the supplied addresses.
- Concurrency, volatile-access, and synchronization guarantees.
- The origin of the unreachable 256 comparison.

The unreachable branch does not justify assuming a wider weight interface. Conversely, the supplied type evidence alone cannot explain why that branch exists.
