# F-638b5c73be41

## Purpose

F-638b5c73be41 processes a nonzero object reference through two dependencies, conditionally updating link and endpoint storage between the calls. Its normal return value is the first dependency’s 32-bit result.

Established behavior:

- A zero object reference returns zero without calling either dependency or accessing link or endpoint state.
- A nonzero reference is passed to F-ff91b5d6bcbb before any object-link or endpoint inspection.
- Local updates require two observed zero object links and an observed head different from the object reference.
- A separate, subsequent head read selects the update branch.
- F-b56a17d0278a follows skipped or completed local updates on every normally progressing nonzero-reference path.
- The second dependency’s result is ignored.

The arrangement suggests appending an apparently detached object to a doubly linked sequence. That is **inferred intent**, not an established guarantee of membership, valid endpoints, or list consistency.

Storage separation is not established. Every write described below identifies an addressing role; it can also affect other roles whose storage overlaps the destination, including through partial overlap.

## Behavior

### Zero-reference path

A zero second input produces a zero return.

On this path, the visible body:

- Calls neither dependency.
- Reads neither object link.
- Does not capture the global endpoint pointer.
- Accesses no endpoint contents.
- Performs no link or endpoint write.

The remaining inputs do not alter this behavior.

### First dependency

For a nonzero object reference, F-ff91b5d6bcbb is called with five ordered arguments:

1. The object reference.
2. The value one.
3. The third input.
4. The fourth input.
5. The fourth input again.

Its 32-bit result is retained for the eventual return.

All link and endpoint inspection follows this call. Consequently, eligibility is determined from state encountered after the dependency returns, not from entry state. The dependency may change the object, endpoint contents, global pointer, ownership, or allocation lifetime; the supplied evidence does not establish otherwise.

### Pointer capture and eligibility

After the first dependency returns, the global endpoint pointer is captured before either object link is inspected.

The function then performs short-circuit inspection:

1. Read the current object’s first link.
2. If that observed value is zero, read its second link.
3. If both observed values are zero, read the endpoint head through the global pointer and compare it with the object reference.

A nonzero first link prevents the second-link read and endpoint-content inspection. A nonzero second link prevents endpoint-content inspection. The earlier global-pointer capture still occurs in either case.

If the compared head equals the object reference, updates are skipped.

Eligibility therefore requires three observations:

- First link equals zero.
- Second link equals zero.
- Compared head differs from the object reference.

These are ordered observations, not an atomic snapshot. They are not a complete membership test: there is no traversal, reachability check, or examination of other objects.

### Branch selection

After eligibility succeeds, the head is read again through the global pointer. This separate read determines whether the zero-head or nonzero-head branch executes.

The earlier head comparison and this later zero test must not be collapsed into a single contractual observation. With stable storage they agree about the head’s value; stability is not established by this function.

### Zero-head branch

If the branch-selection head read is zero, writes occur in this order:

1. Store the current object reference into the head addressed through the global pointer.
2. Store the current object reference into the tail addressed through the captured endpoint pointer.

The old tail is neither read nor validated.

With a stable global pointer, the writes address the head and tail of the same endpoint record. If those complete write ranges are disjoint from both current-object link ranges, the wrapper leaves those links unchanged.

Without that separation, endpoint writes can modify the object links. For example, an endpoint record beginning at the current object’s offset 336 places its head and tail exactly over the object’s first and second links. If both initially contain zero, this branch writes the object reference into both links.

### Nonzero-head branch

If the branch-selection head read is nonzero, the function reads the endpoint tail through the global pointer and retains that value.

It then writes, in order:

1. The recorded tail value into the current object’s first link.
2. The current object reference into the recorded tail’s second link.
3. The current object reference into the endpoint tail through the captured pointer.

The recorded tail is not checked for:

- Zero or invalid addressing.
- Reachability from the head.
- Equality with the current object.
- A clear second link.
- Full or partial overlap with other relevant storage.

The retained tail value determines the second write’s destination even if the first write changes storage from which that tail was read.

If the tail equals the current object, the first two writes set both current-object links to the object reference.

A distinct tail does not guarantee preservation of the current object’s second link. Its second-link destination can partially overlap that link. Preservation requires the current second link’s entire four-byte range to be disjoint from every wrapper write destination, not merely a distinct tail reference or mutually disjoint write destinations.

There is no explicitly addressed head assignment in this branch. Nevertheless, a link write or the final tail write can modify head storage if their ranges overlap it.

### Final dependency and return

After updates are skipped or all selected writes complete, F-b56a17d0278a receives:

1. The current object reference.
2. The 32-bit pattern `0xFFFFFFFF`.
3. Zero.
4. Zero.
5. Zero.

No semantic meaning is established for `0xFFFFFFFF`; the evidence does not identify it as a mask, operation code, or signed sentinel.

The dependency’s result is ignored. If it returns normally, F-638b5c73be41 returns the saved result of F-ff91b5d6bcbb.

The final dependency can have unspecified effects on the object, endpoints, global pointer, and storage lifetime. State immediately after wrapper writes is therefore distinct from state at the function’s return.

## Side effects

### Explicit writes and overlapping storage

The wrapper selects at most these destinations:

- Endpoint head through the global pointer, only in the zero-head branch.
- Current object’s first link, only in the nonzero-head branch.
- Recorded tail’s second link, only in the nonzero-head branch.
- Endpoint tail through the captured pointer, after either update branch.

These destinations do not bound the semantic fields affected. Full or partial overlap can change other fields.

Preservation of any field requires its entire storage range to avoid every reached wrapper write range, or a separate value-specific argument demonstrating preservation. Merely assigning different object references to the roles is insufficient.

Examples of permitted overlap include:

- The recorded tail equaling the current object.
- Endpoint fields occupying current-object link storage.
- A recorded-tail link overlapping the head.
- A recorded-tail link overlapping only part of the current object’s second link.
- A write overlapping global-pointer storage.

Writes do not retroactively change the captured endpoint-pointer value or retained tail value. Later accesses expressed through the global pointer may, however, be affected by changes to its storage. Exact partial-overlap effects depend on platform representation and byte order.

If eligibility fails, the wrapper performs no link or endpoint write. Both dependencies can still have effects.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless stated otherwise, assume normal dependency returns, valid reached accesses, and stable state during wrapper processing. State assertions concern the wrapper’s effects before the final dependency.

### Zero reference

For a zero second input:

- Return zero.
- Call neither dependency.
- Access no object or endpoint state.

### Detached object with a zero head

Suppose both object links and the endpoint head are zero after the first dependency. The global pointer remains stable, and both endpoint write ranges are disjoint from both object-link ranges.

The wrapper writes the object reference to head, then tail. Both links remain zero. A nonzero old tail does not prevent this because the old tail is not read.

### Endpoint record occupying the object links

Suppose the endpoint record begins at the current object’s offset 336 and both fields are initially zero.

Eligibility succeeds. The head write sets the first object link to the object reference; the tail write then sets the second link to that reference.

### Detached object with an ordinary nonempty sequence

Suppose:

- Both current-object links are zero.
- Head is nonzero and differs from the object.
- Tail identifies a distinct valid object.
- The complete endpoint-field ranges and the two link-write ranges are mutually disjoint.
- The current object’s entire second-link range is disjoint from every wrapper write range.

The wrapper writes the old tail to the current first link, the object reference to the old tail’s second link, and the object reference to endpoint tail, in that order.

Head and the current object’s second link remain unchanged by these writes. The final disjointness condition is necessary for the second-link preservation claim.

### Distinct tail with a partially overlapping second link

Suppose the recorded tail reference is one byte above the current object reference, with valid arithmetic and a platform permitting the reached accesses. Both current links initially contain zero; head is nonzero and different from the object; endpoint storage is disjoint from the relevant object storage.

The recorded tail’s second-link write begins at current-object offset 341 and occupies offsets 341 through 344. It overlaps three bytes of the current object’s second link at offsets 340 through 343, while remaining disjoint from the first-link destination at offsets 336 through 339.

The wrapper performs the normal nonzero-head writes. The current object’s second link is not guaranteed to remain zero. Its resulting value depends on byte order and the stored reference’s byte representation.

Thus a distinct tail and mutually disjoint write destinations do not establish preservation of an additional, partially overlapping field.

### Recorded tail equals the current object

Suppose both current links are zero, head is nonzero and differs from the object, tail equals the object, and endpoint storage is disjoint from both links.

The wrapper sets both current links to the object reference, then assigns that reference to endpoint tail. No distinct-tail check prevents self-links.

### Recorded-tail link overlaps head

Suppose eligibility succeeds, head is nonzero, and the recorded tail’s second-link destination exactly occupies head storage. Other destinations do not interfere.

The second nonzero-head write changes head to the current object reference despite the absence of an explicitly addressed head assignment in this branch.

### Ineligible object

If the first link is nonzero, neither the second link nor endpoint contents are inspected. If the first link is zero and the second is nonzero, endpoint contents are not inspected.

If both links are zero but the compared head equals the object, updates are also skipped.

All three cases still capture the endpoint pointer and call the final dependency.

### First dependency returns zero

If the first dependency returns zero and leaves eligible, accessible state, wrapper updates still proceed. The final dependency is called. Normal completion returns zero.
