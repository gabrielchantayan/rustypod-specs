# F-4a4de87a7e05

## Purpose

F-4a4de87a7e05 conditionally processes one of 32 indexed regions associated with a caller-supplied base address.

For an accepted index, it invokes a preparatory dependency, inspects an object reference and an associated 32-bit counter, and conditionally decrements that counter. When the decrement produces zero, it clears the stored object reference and a one-byte field, then invokes an indirect callback obtained through the previously captured object. A second dependency runs afterward on the normal-return path.

For an index outside the accepted range, the function returns the original first argument without making either dependency call or accessing the described fields.

A reference-counted release operation is a plausible interpretation of the counter transition and callback. That interpretation is **inferred intent**, not an established ownership contract. The available evidence does not identify the resource, prove that the callback destroys it, or establish what either direct dependency does.

## Interface

### Inputs

The function has two inputs:

| Input | Representation | Established use |
|---|---|---|
| Base value | 32-bit integer, used as an address | Locates indexed fields and a shared dependency argument; returned unchanged for an out-of-range index |
| Index | Unsigned 32-bit integer | Selects one of 32 accepted indexed regions |

The accepted index range is **0 through 31 inclusive**. Because the index is unsigned, a caller-provided bit pattern corresponding to a negative signed integer is interpreted as a large positive index and rejected.

### Addressing and field layout

For an accepted index, define the **selected origin** as the base address plus 20 times the index. The 20-byte stride is established; it does not establish a complete, independently allocated 20-byte record type.

The function uses these locations:

| Location | Width or interpretation | Use |
|---|---|---|
| Base + 652 bytes, hexadecimal 0x28C | 32-bit value | First argument to F-f0216cff9365 |
| Selected origin + 4 bytes | Object pointer in the represented address model | Read after F-f0216cff9365; conditionally cleared |
| Selected origin + 8 bytes | One byte | Cleared only on a decrement-to-zero transition |
| Selected origin + 12 bytes | Address passed to dependencies | Passed first to F-f0216cff9365 and later to F-1333331b2da1 |
| Selected origin + 20 bytes | Signed 32-bit counter | Conditionally read, decremented, and written |

The counter is at offset 20, not within offsets 0 through 19 of a stride-sized region. For example, the counter for index 0 is located at the selected origin for index 1. Consumers must not infer that all fields used by one invocation lie strictly inside one 20-byte record.

The largest selected-origin displacement is 620 bytes, hexadecimal 0x26C, for index 31. Its counter is at base + 640 bytes, hexadecimal 0x280. The shared 32-bit value at base + 652 bytes is a separate access.

### Return value

On normal completion:

- An index greater than 31 returns the original base value.
- An accepted index returns zero.

The return value does not report whether an object was present, whether the counter changed, whether the callback ran, or whether a dependency reported a failure through its own return value.

### Preconditions

For an accepted index, the relevant addresses must be valid for the accesses and dependency operations actually reached.

In particular:

- The shared 32-bit value and selected object-pointer field must be readable.
- The counter must be readable when the captured object pointer is nonnull.
- A taken decrement path requires a writable counter.
- A decrement-to-zero path requires writable object-pointer and byte fields, a readable dispatch structure reached through the captured object, and a callable dispatch entry.
- Both direct dependencies must accept the supplied arguments.

No validation of these conditions is visible. The invalid-index path does not impose these memory-access requirements because it exits before the corresponding accesses.

## Behavior

### Index rejection

The unsigned range check occurs before any field access or dependency call.

If the index exceeds 31, processing ends immediately with the unchanged base value. The function does not clamp the index, calculate a fallback selection, clear state, or call a dependency.

### Preparatory dependency

For an accepted index, the function determines the selected origin and invokes F-f0216cff9365 with:

1. The 32-bit value read from base + 652 bytes.
2. The address at selected origin + 12 bytes.

The first argument is a loaded value. The second is an address; the function does not itself load the contents at that address to form this argument.

This dependency completes before the selected object pointer is read. Consequently, mutations made by F-f0216cff9365 to the object-pointer field or counter can affect the subsequent decision. There is no visible snapshot of either field before that call.

The dependency’s return value is not used.

### Object and counter inspection

After F-f0216cff9365 returns, the function reads and retains the object pointer from selected origin + 4 bytes.

If that pointer is null:

- The counter condition is not evaluated by this function.
- No local counter decrement occurs.
- The local object-clear and byte-clear operations do not occur.
- The indirect callback is not invoked.
- Processing continues to F-1333331b2da1.

If the captured pointer is nonnull, the function reads the signed 32-bit counter at selected origin + 20 bytes.

A zero counter suppresses the decrement and callback path. A nonzero counter enables that path. There is no positivity check: negative counter values are also nonzero.

On the enabled path, the counter is read again to calculate its value minus one. Thus, the supplied representation contains a nonzero-test read followed by a separate decrement-value read. No dependency call intervenes between those reads. Concurrent or asynchronous mutation is not given a synchronization contract.

### Decrement without a zero transition

If subtracting one produces a nonzero result, the function writes that result to the counter field.

It does not, on this path, clear the stored object pointer, clear the byte at offset 8, or invoke the indirect callback.

For example, a counter of 2 becomes 1. Subject to representable signed arithmetic, a counter of −1 becomes −2 rather than being rejected or normalized.

### Decrement to zero

If subtracting one produces zero, the function performs these actions in order:

1. Writes a 32-bit zero to the object-pointer field at selected origin + 4 bytes.
2. Writes a one-byte zero to selected origin + 8 bytes.
3. Resolves and invokes the indirect callback through the object pointer captured before these writes.
4. After the callback returns, writes the saved decrement result, zero, to the counter field.

The callback is obtained by reading a dispatch-table address from the beginning of the captured object and selecting the function entry at byte offset 4 in that table.

The visible call supplies no explicit arguments. An implicit receiver, register-based arguments, or other calling-convention details are not established by this evidence.

The ordering is significant:

- The stored object reference is cleared before callback dispatch and invocation.
- The byte field is also cleared before callback dispatch and invocation.
- This function’s counter write happens after the callback returns.
- The callback target is resolved through the retained object pointer, not by rereading the now-cleared object-pointer field.
- No post-callback object-pointer check occurs.

If the callback changes the counter field, the function’s subsequent write overwrites that change with its saved result. If the callback changes the stored object pointer or byte field, this function does not subsequently clear those fields a second time.

The function does not establish that the counter is zero during the callback. In ordinary non-aliasing execution without other mutations, a transition from 1 leaves the counter holding 1 until the callback returns.

### Final dependency and completion

After the conditional object/counter processing, F-1333331b2da1 receives the address at selected origin + 12 bytes.

This call occurs on every accepted-index path that reaches it normally, including paths with:

- A null object pointer.
- A zero counter.
- A nonzero decrement result.
- A decrement-to-zero callback that returns normally.

Its return value is not used. After it returns, F-4a4de87a7e05 returns zero.

There is no visible exception handling, fault recovery, rollback, or guaranteed-finalization mechanism. If an earlier dependency or callback does not return normally, reaching the final dependency is not established.

## Side effects

The function’s own explicit writes are limited to:

- A 32-bit zero in the selected object-pointer field on a decrement-to-zero transition.
- A one-byte zero at selected origin + 8 bytes on that same transition.
- The decremented 32-bit counter whenever the decrement path is taken.

These are not limits on total execution effects. F-f0216cff9365, F-1333331b2da1, and the indirect callback may have additional effects not described by the supplied evidence.

The function visibly performs no allocation. It also contains no direct, independently identified deallocation operation. Clearing a pointer does not prove that the referenced storage has been freed, and invoking the callback does not establish its ownership semantics.

No synchronization primitive is established. The counter update is represented as separate reads, arithmetic, and a write, not as an atomic reference-count operation. Thread safety, interrupt safety, and reentrancy are therefore not promised.

Aliasing can affect execution. In particular, callback dispatch occurs after the two clearing writes. If either cleared location aliases the captured object’s dispatch data, dispatch may observe the modified data. The evidence contains no alias check or protective copy of the dispatch target before those writes.

Dependencies are not assumed to preserve global state, selected-region contents, object lifetime, or memory ownership.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless stated otherwise, assume valid non-overlapping memory, representable arithmetic, normally returning dependencies, and no dependency mutation of the described fields.

1. **Index 32 is rejected.**  
   With any base value, index 32 returns that base value unchanged. Neither direct dependency runs, and none of the described fields is accessed.

2. **Maximum unsigned index is rejected.**  
   Index 4,294,967,295 follows the rejection path. It is not treated as an accepted negative index.

3. **Index 31 uses the final accepted selection.**  
   Its selected origin is base + 620 bytes. The dependency address is base + 632 bytes, and the counter is at base + 640 bytes. Normal completion returns zero.

4. **Null object suppresses counter processing.**  
   If the object-pointer field is null after F-f0216cff9365 returns, this function does not read the counter for its condition, decrement it, clear the byte field, or invoke the callback. F-1333331b2da1 still runs.

5. **Non-null object with zero counter is left unchanged locally.**  
   The function does not clear the object pointer or byte field and does not write a decremented counter. Both direct dependencies run.

6. **Counter 2 becomes 1.**  
   With a nonnull object, the counter is written as 1. No indirect callback runs, and the object-pointer and byte fields receive no local write.

7. **Counter 1 triggers ordered clearing and callback.**  
   The object-pointer field becomes zero first, then the byte field becomes zero. The callback is resolved through the captured object and invoked. If it leaves the counter unchanged, it encounters a counter still equal to 1. After it returns, the function writes zero to the counter and invokes F-1333331b2da1.

8. **A callback counter write does not replace the saved result.**  
   In the preceding transition, if the callback writes 9 to the same counter field and returns, the subsequent local write replaces 9 with zero.

9. **Preparatory changes affect the branch.**  
   If F-f0216cff9365 changes a previously nonnull stored object pointer to null, the later pointer read sees null under the stated sequential-memory assumptions. The decrement path is skipped.

10. **Negative counters are not rejected.**  
    With a nonnull object and counter −1, the result is −2. The callback does not run. A counter at the minimum signed 32-bit value is excluded from this example because its subtraction semantics require additional evidence.
