# F-77a65db9996d

## Purpose

F-77a65db9996d handles selector `0xA9` locally and delegates every other selector to F-971e9510f21c.

For selector `0xA9`, it compares the low eight bits of an incoming 32-bit value with a byte in the supplied object. Equality suppresses all updates and calls. Inequality causes a one-byte update, one indirect operation, and then four further indirect operations with identifiers `0xAA`, `0xAC`, `0xB5`, and `0xB6`, in that order.

The changed-byte path accesses shared 32-bit storage twice after the first indirect operation returns. The earlier access supplies a retained value used by the final three calls. The later access supplies the argument to the `0xAA` call. The representation does not establish that these accesses must observe identical values.

The distinguished-selector path returns the 32-bit value `1` on normal completion. The delegated path returns the result of F-971e9510f21c.

Interpreting the stored byte as a cache or the later calls as notifications is inferred intent, not an established behavioral guarantee.

## Behavior

### Selector routing

The selector comparison concerns the complete 32-bit value. A selector of `0x000001A9` therefore takes the delegated path despite sharing its low byte with `0xA9`.

On the delegated path, F-971e9510f21c receives all five original inputs in their original positions. Its result becomes this function’s result.

This path performs no local object-byte comparison, byte write, shared-storage access, or object-dispatched operation.

### Distinguished selector with an equal byte

For selector `0xA9`, the function reads the byte at object offset `0x4C8` and compares its unsigned value with the incoming value restricted to its low eight bits.

If equal:

- No direct write occurs.
- No indirect operation occurs.
- The shared storage is not accessed.
- F-971e9510f21c is not invoked.
- The function returns `1`.

The upper 24 bits of the incoming value do not affect this comparison. An incoming value whose low byte matches the stored byte takes this path regardless of its upper bits.

### Distinguished selector with a different byte

If the compared bytes differ, the following actions occur in order.

**1. Update the object byte.**

The function stores the incoming low eight bits at object offset `0x4C8`.

This write precedes all indirect operations. A subsequent callback that reads this location can observe the update, subject to any intervening mutation. The function does not defer the write pending callback success.

**2. Invoke the operation selected through dispatch offset `0x074`.**

The operation receives five arguments, in this order:

1. The original object address.
2. The four-byte value read from object offset `0x040`.
3. A callable address read through dispatch-table offset `0x074`.
4. The original auxiliary value.
5. The complete original 32-bit incoming value.

The last argument is not narrowed to a byte.

The call target and the third argument are obtained through the same dispatch offset, but the representation contains separate accesses for those roles. It does not establish an ordering among all reads used to prepare this call, or guarantee matching observations if dispatch state changes between accesses.

The operation’s result does not select a different local path. Subsequent actions require that the operation return normally.

**3. Read and retain the shared value.**

After the first operation returns, the function reads the shared 32-bit storage and retains the resulting value for later use.

This retained value supplies the second argument to the calls identified by `0xAC`, `0xB5`, and `0xB6`.

**4. Read the shared value again and issue the `0xAA` call.**

The function separately accesses the same shared storage to supply the second argument to the first operation selected through dispatch offset `0x058`.

That call receives:

1. The original object address.
2. The value from this second shared-storage access.
3. Identifier `0xAA`, decimal `170`.

The second shared-storage access follows the retained-value access. Both follow the return of the operation at `0x074` and precede invocation of the `0xAA` operation.

The relative order of the second shared-storage access and reads used to resolve that call’s dispatch target is not established. No equality between the two shared-storage observations is guaranteed without additional stability or synchronization assumptions.

**5. Issue the remaining three calls using the retained value.**

After the `0xAA` call returns, the function invokes the operation selected through offset `0x058` three more times:

| Order within the four-call sequence | Second argument | Third argument |
|---|---|---|
| Second | Retained value from the earlier shared-storage access | `0xAC`, decimal `172` |
| Third | The same retained value | `0xB5`, decimal `181` |
| Fourth | The same retained value | `0xB6`, decimal `182` |

The first argument is the original object address for every call.

Each call must return normally before the next begins. Returned values are not used to decide whether to issue the next call.

The dispatch target is obtained through the object separately for each invocation. The function does not retain one `0x058` target for the whole sequence. A callback that changes dispatch state can therefore affect the target of a later invocation, provided subsequent accesses remain valid.

There is no further shared-storage read in this sequence. In particular, changes to that storage during the `0xAA` call do not refresh the retained argument used by the final three calls.

**6. Return `1`.**

After all operations return normally, the function returns `1`. It does not reread the object byte or check whether callbacks preserved its write.

## Side effects

### Direct reads and writes

The equal-byte path directly reads only the comparison byte among the object and shared locations described here.

On a normally completed changed-byte path, the representation establishes:

- A comparison-byte read.
- A one-byte write at object offset `0x4C8`.
- A four-byte read at object offset `0x040`.
- Dispatch-table address and entry accesses needed for the indirect calls, including the callable-address argument to the first operation.
- Two accesses to the same shared 32-bit storage after the first indirect operation returns.

The first shared access supplies the retained value for `0xAC`, `0xB5`, and `0xB6`; the second supplies the `0xAA` argument. These are source-facing accesses, not a claim about the precise number of machine load instructions.

The original object address is reused after callbacks. If a callback invalidates storage needed later, normal completion is not established.
