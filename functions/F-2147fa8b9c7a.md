# F-2147fa8b9c7a

## Purpose

F-2147fa8b9c7a classifies an input token and, for five recognized classification values, invokes one operation obtained from a receiver’s dispatch table. It returns a 32-bit recognition indicator rather than the result of that operation.

Two recognized values request a fixed argument of one. Another forwards a 32-bit value obtained through the receiver’s associated state. The remaining two enter a calendar-like adjustment path: the function obtains a record, constructs a neighboring month/year candidate, queries a helper for both records, and selects an argument for the final dispatched operation.

The calendar interpretation is inferred from the handling of month values 1 and 12 and the accompanying 16-bit field adjustment. The record’s actual type, the meaning of the helper results, and the effects of the dispatched operations are not established.

## Interface

### Inputs

The function accepts:

- **Receiver:** a pointer to storage whose first 32-bit word supplies a dispatch-table address. A second receiver field, at byte offset `0xEC`, supplies an associated-state address.
- **Token:** a 32-bit value passed to F-11c1b7e655b3 for classification. This function does not otherwise establish the token’s representation or ownership.

The exposed operations use a 32-bit address and word model. The receiver and associated-state offsets are byte offsets, not element indices.

The following storage is required only when the selected path accesses it:

| Location | Use |
|---|---|
| Receiver offset `0x00` | Dispatch-table address |
| Receiver offset `0xEC` | Associated-state address |
| Associated state offset `0xE8` | 32-bit value passed onward |
| Dispatch table offset `0x160` | Indirect operation for classification `0x6F` |
| Dispatch table offset `0x16C` | Indirect operation for classification `0x57` or the negative adjustment direction |
| Dispatch table offset `0x170` | Indirect operation for classification `0x58` or the positive adjustment direction |

### Output

On normal completion:

- Returns **0** when the initial classification is not one of `0x57`, `0x58`, `0x59`, `0x5A`, or `0x6F`.
- Returns **1** after invoking the selected indirect operation for a recognized classification.

The return value of the indirect operation is ignored. A return of one establishes that the function reached and returned from that invocation; it does not establish that the operation succeeded according to any external definition.

No explicit error result exists for invalid addresses, invalid record contents, helper failures, or an invalid function pointer.

### Preconditions and ownership

All storage actually read or written must be valid for the corresponding access. Selected dispatch entries must identify callable operations compatible with a receiver argument and a 32-bit second argument.

The function creates two temporary record regions for the adjustment path. It neither explicitly allocates nor explicitly releases heap storage. It does not directly acquire or release ownership of the receiver, token, or associated state.

The dependencies’ ownership behavior is unknown. In particular, this contract does not assume that a dependency preserves global state, avoids retaining a pointer, or refrains from releasing memory.

## Behavior

### Initial classification and routing

The first action is a call to F-11c1b7e655b3 with the token.

Its 32-bit result determines the route:

| Initial classification | Route |
|---|---|
| `0x57` | Dispatch through offset `0x16C` with argument 1 |
| `0x58` | Dispatch through offset `0x170` with argument 1 |
| `0x59` | Enter the adjustment path |
| `0x5A` | Enter the adjustment path |
| `0x6F` | Dispatch through offset `0x160` with an associated-state value |
| Any other value | Return 0 without a dispatched operation |

For an unsupported classification, the function performs no direct receiver dereference. The classifier itself may have effects; returning zero does not imply that the entire call was side-effect free.

For classifications `0x57` and `0x58`, the function reads the receiver’s dispatch-table address and the selected entry, invokes that entry with the receiver and one, then returns one.

For classification `0x6F`, the observable order is:

1. Read the associated-state address from receiver offset `0xEC`.
2. Read the 32-bit argument from associated-state offset `0xE8`.
3. Read the receiver’s dispatch-table address and its entry at offset `0x160`.
4. Invoke the entry with the receiver and the captured argument.
5. Return one.

No record helper is called on these three direct-dispatch routes.

### Direction selection on the adjustment path

An initial classification of either `0x59` or `0x5A` causes a **second** call to F-11c1b7e655b3 with the original token.

The second result, not the first, determines the direction:

- Exactly `0x59`: direction is −1.
- Any other result: direction is +1.

The second result is not required to remain within the initially recognized set. For example, an initial `0x59` followed by an unrelated second result still takes the positive adjustment route.

This repeated classification is observable. A contract that substitutes the initial result for the second call would not preserve the established behavior.

### Record acquisition and layout

After selecting the direction, the function reads the associated-state value at offset `0xE8`, through the receiver’s field at offset `0xEC`. It passes that 32-bit value and a pointer to a temporary record to F-a062a6eb1219.

The function subsequently consumes three consecutive 32-bit words from that record, a total of 12 bytes. It copies those words into a second temporary record before calling F-8cfb43901820.

The relevant layout is:

| Record byte offset | Width | Established use |
|---|---:|---|
| `0–2` | 3 bytes | Copied; not individually interpreted here |
| `3` | 8 bits | Read later as an unsigned comparison threshold |
| `4` | 8 bits | Adjusted field, with special handling for values 1 and 12 |
| `5` | 8 bits | Preserved during the direct adjustment |
| `6–7` | 16 bits | Decremented or incremented at the special boundaries |
| `8–11` | 32 bits | Copied; not individually interpreted here |

The byte ordering implied by the extraction and reconstruction places the adjusted 8-bit field in the low byte of the middle word and the 16-bit field in that word’s upper half.

F-a062a6eb1219’s own initialization guarantee is unknown. The caller nevertheless uses all 12 bytes. Fully initialized output is therefore a required dependency condition for defined, meaningful processing of this path, not an independently established property of that dependency.

### Candidate adjustment

Only the copied candidate is directly adjusted. The original record is retained separately for the first helper query.

For direction −1:

- If candidate byte `4` equals 1, set it to 12 and decrement the 16-bit field at bytes `6–7`.
- Otherwise, decrease candidate byte `4` by one and leave the 16-bit field unchanged.

For direction +1:

- If candidate byte `4` equals 12, set it to 1 and increment the 16-bit field at bytes `6–7`.
- Otherwise, increase candidate byte `4` by one and leave the 16-bit field unchanged.

Candidate byte `5` and all other bytes are preserved by these direct adjustments.

There is no general validity check or normalization. Values outside 1 through 12 do not cause an error or receive calendar-specific repair.

The adjusted byte remains eight bits, and the companion field remains sixteen bits. Thus, the stored field representations are width-limited: a boundary decrement from a 16-bit zero produces all one bits, and an increment from all one bits produces zero. Whether those representations denote signed years, unsigned years, or something else is unknown.

### Helper queries and argument selection

After constructing the candidate, the function calls F-8cfb43901820 in this order:

1. With a pointer to the original record.
2. With a pointer to the adjusted candidate.

Each result is retained as a character-width value and then promoted for comparison or dispatch. The effective narrow width is eight bits. Signed interpretation of values with the top bit set is not independently established; ordinary small positive results are unambiguous.

After both helper calls, the function reads original-record byte `3` as an **unsigned** eight-bit threshold. This timing matters: the threshold is not captured before the helper calls.

Let:

- **O** be the promoted result of the original-record query.
- **C** be the promoted result of the candidate-record query.
- **T** be the unsigned value, from 0 through 255, read from original-record byte `3` after both calls.

The selected argument is:

| Direction | Condition | Selected argument |
|---|---|---|
| −1 | C < T | O |
| −1 | C ≥ T | C |
| +1 | C < T | C |
| +1 | C ≥ T | O |

Equality follows the greater-than-or-equal branch. The function does not directly compare O with C, so this selection must not be reduced to a general minimum or maximum operation.

The selected character-derived value becomes the 32-bit second argument of the final indirect call.

### Final adjustment dispatch

For direction −1, the function selects dispatch-table offset `0x16C`. For direction +1, it selects offset `0x170`.

The receiver’s dispatch-table address and the selected entry are read **after** both record-helper calls and the argument-selection work. The function does not preserve an earlier table entry across those calls.

The selected entry receives the receiver and the selected argument. After that call returns normally, F-2147fa8b9c7a returns one.

## Side effects

Directly established effects are:

- One token-classifier call on every path.
- A second token-classifier call only on the adjustment path.
- Reads of receiver, associated-state, and dispatch-table storage as required by the route.
- Creation, copying, and adjustment of temporary record storage on the adjustment path.
- Two ordered calls to F-8cfb43901820 on that path.
- Exactly one final indirect invocation for each recognized initial classification.

The function contains no direct write to receiver fields or associated-state fields. This does not establish that those objects remain unchanged: dependencies and indirect operations may mutate accessible storage.

Both record-helper calls receive pointers, not immutable snapshots. The first helper may change the original record before the second call. Either helper may have additional effects not visible in this body. The later threshold read must use the then-current original-record byte `3`; it cannot safely be replaced with the byte’s earlier value without additional dependency guarantees.

There is no explicit rollback. If a dependency or indirect operation fails to return normally, the final recognition return is not established, and earlier effects are not undone.

## Acceptance examples

These are conditional behavioral examples, not executed tests.

1. **Unsupported classification.**  
   If the first classifier call returns `0x56` and returns normally, the function returns zero. It performs no direct receiver read, record query, or indirect invocation.

2. **Fixed negative-side entry.**  
   If the first classification is `0x57` and the selected entry is callable, the entry at offset `0x16C` receives the receiver and 32-bit value one. The function returns one after that call returns.

3. **Associated-state forwarding.**  
   If the first classification is `0x6F` and the associated-state value is `0x12345678`, the entry at offset `0x160` receives that value unchanged as its second argument. No record construction occurs.

4. **Second classification controls direction.**  
   If the first result is `0x59` but the second is `0x5A`, the candidate is adjusted in the positive direction and final dispatch uses offset `0x170`. Conversely, an initial `0x5A` followed by `0x59` selects the negative direction and offset `0x16C`.

5. **Negative boundary adjustment.**  
   If direction is −1 and the acquired record has byte `4` equal to 1 and its 16-bit companion equal to 2026, the candidate supplied to its helper has byte `4` equal to 12 and companion value 2025. Other candidate bytes remain copied unless affected by intervening dependency behavior.

6. **Positive boundary adjustment.**  
   If direction is +1, byte `4` is 12, and the companion field is 2026, the candidate uses byte value 1 and companion value 2027.

7. **Selection below the threshold.**  
   Assuming helper results O = 31 and C = 28, and the post-call threshold T = 30, negative direction dispatches argument 31; positive direction dispatches argument 28.

8. **Equality is not “below.”**  
   With O = 31, C = 30, and T = 30, negative direction dispatches 30; positive direction dispatches 31.

9. **Threshold mutation is observable.**  
   If original byte `3` initially contains 30 but helper activity changes it to 27 before the comparison, C = 28 is compared against 27, not 30.

10. **No general month validation.**  
    If direction is +1 and candidate byte `4` starts at 13, the direct adjustment produces 14 without changing the companion field. Calendar validity is not enforced here.

## Uncertainties

The following remain **documented_only**:

- The token’s semantic type and the names or meanings of the five recognized classifications.
- Whether the receiver is a language-level object and whether its first word is formally a virtual dispatch table.
- The actual record type. Month/year and day-related interpretations are inferred, not proven.
- Whether F-a062a6eb1219 initializes every consumed byte or reports failures through an unexamined mechanism.
- Whether either helper mutates records, receiver state, dispatch entries, globals, or ownership.
- The signed interpretation of character-width helper results outside the ordinary positive range.
- The meanings and valid ranges of the two dispatch arguments.
- Whether callees retain temporary-record pointers. Their usable lifetime cannot be assumed to extend beyond this invocation.
- Fault, exception, nonlocal-exit, or concurrency behavior beyond the visible sequence of operations.

## Evidence

The established behavior derives solely from static inspection of the supplied function body: classification branches, receiver-relative accesses, temporary-record transfers, width-limited field adjustments, dependency-call order, strict comparison, dispatch-entry selection, and fixed recognition returns.

The calendar interpretation is inferred from the paired 1-to-12 and 12-to-1 transitions with a neighboring 16-bit decrement or increment. No dependency implementation or independent type definition was provided to confirm it.

No runtime tests have been performed. The acceptance examples state consequences conditional on the specified dependency results and valid accesses; they are not observations of execution.
