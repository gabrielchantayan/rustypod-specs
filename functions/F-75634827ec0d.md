# F-75634827ec0d

## Purpose

F-75634827ec0d marks a supplied object with a one-byte value and conditionally performs a sequence of dependent calls.

The established behavior is:

- Write the byte value `1` at object-relative offset `0x884`.
- Return immediately if the 32-bit field at offset `0x738` equals signed `-1`.
- Otherwise, invoke F-a47f88e3d6eb, invoke an operation through a related object, and invoke two operations through the supplied object.

The meaning of the flag, selector, related object, and later operations is not established. In particular, the source does not establish that this is initialization, cleanup, cancellation, notification, or resource release.

This contract describes the visible source-level operations and their dependencies. It does not establish the behavior of unavailable callees or reconstruct an uncertain machine-level calling convention.

## Behavior

### Initial state change and sentinel decision

The first visible operation writes the byte value `1` at supplied-object offset `0x884`.

Only after that write does the function read the 32-bit selector at offset `0x738` and compare it with `-1`.

If the selector equals `-1`, execution returns without calling any dependency. The flag write is not undone.

If the selector differs from `-1`, execution continues along the active path. There is no visible second sentinel decision.

### Preliminary dependency call

The function invokes F-a47f88e3d6eb with:

1. The supplied object address.
2. The 32-bit value read from supplied-object offset `0x734`.

The return value, if any, is not visibly used.

No preservation properties are established for this dependency. It may affect fields, global state, dispatch tables, or memory lifetime. Later reads must therefore be understood as occurring after this call, rather than as using an immutable entry-state snapshot.

In particular, the selector used by the next operation is read again after F-a47f88e3d6eb returns.

### Related-object operation

After the preliminary call, the function selects an operation through the related object:

- The related-object address comes from supplied-object offset `0x88C`.
- The related object’s first word supplies its dispatch-table address.
- The target comes from byte offset `0x84` in that table.

The visible call supplies:

1. The related-object address.
2. The current 32-bit value at supplied-object offset `0x738`.

The returned value is not visibly used.

If the preliminary call changes the selector to `-1`, that value is passed to this operation. The function does not return early at this point merely because the selector has become the sentinel.

The relative evaluation order of separate reads within this indirect-call expression is not established. The source supports the inter-call ordering and the fact that these accesses occur after F-a47f88e3d6eb; it does not support a stronger instruction-by-instruction order among all argument and target reads.

### Retaining global A

After the related-object operation returns, the function reads global A into four-byte retained storage.

That retained value is later supplied to the second supplied-object operation. It is a value captured at this point, not a fresh read of global A immediately before the second operation.

### First supplied-object operation

The function selects an operation through the supplied object’s dispatch table at byte offset `0x58`.

The visible call expression supplies five arguments:

1. The supplied object address.
2. A read of global A.
3. A read of global B.
4. An operation address obtained through the supplied object’s dispatch-table slot at `0x58`.
5. The incoming register value whose origin is not established.

The read of global A for this call is separate from the earlier read retained for the later call. Under stable memory conditions, the two reads have the same value. The source alone does not establish that equality under asynchronous changes or special memory behavior.

The operation address used as an argument and the operation address used as the call target are separately expressed lookups of the same slot. They normally agree if the object and table remain stable, but the source does not prove unconditional equality or a precise relative load order.

No return value is visibly consumed.

### Second supplied-object operation

After the first supplied-object operation returns, the function again selects a target through the supplied object’s dispatch-table slot at byte offset `0x58`.

This final visible call supplies three arguments:

1. The supplied object address.
2. The retained four-byte value of global A captured before the preceding operation.
3. A read of global C performed for this final call.

The target is selected again after the preceding call. If that call changes the supplied object’s dispatch-table address or the table entry, the final call can select a different target.

Likewise, global C is not visibly captured before the preceding call. A change made by that call can affect the value supplied to the final operation.

If the final call returns normally, F-75634827ec0d returns.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

### Sentinel at entry

Given a valid supplied object whose selector is `0xFFFFFFFF`:

- The byte at `0x884` is written to `1`.
- The function returns.
- No dependency is invoked.
- Neither dispatch table nor the related-object field needs to be read.

A null related-object field does not by itself invalidate this path, provided the initial write and selector read remain valid.

### Any other selector

Given a selector of zero, a positive value, or a negative value other than `-1`, and assuming all dependencies return normally:

- The initial byte write occurs.
- F-a47f88e3d6eb is invoked.
- The related-object operation is invoked.
- The two supplied-object operations follow in that order.

No further visible range check restricts the selector.

### Selector changes during the preliminary call

Given an entry selector of `7`, if F-a47f88e3d6eb changes it to `-1`:

- The active path continues.
- The related-object operation receives `-1`.
- The later supplied-object operations are not skipped by a repeated sentinel check.

### Global A changes during the first supplied-object operation

Assume global A is stable at value A₀ from its retained read through preparation of the first supplied-object call. If that call changes global A to A₁:

- The first supplied-object call receives A₀.
- The final call still receives retained value A₀.
- The function does not visibly reread global A for the final call.

### Dispatch changes during the first supplied-object operation

If that operation installs a different valid supplied-object dispatch table, the final call uses the target selected through the new table’s `0x58` slot. It is not required to reuse the earlier target.

### Surrounding bytes remain intact

If no dependency changes the surrounding memory, the initial store changes only the byte at `0x884`. Adjacent bytes are not cleared or otherwise assigned by that store.
