# F-b3d17d4376ff

## Purpose

F-b3d17d4376ff conditionally initializes a shared service value, obtains an associated record for its input, and requests and submits descriptors referring to that record.

The established behavior is not transactional:

- An initial service-field test determines whether to call an initializer.
- That test and subsequent service-field accesses need not use the same base address.
- A nonzero record address and successful mandatory descriptor request enable the main path.
- Up to three optional descriptors are requested.
- Present descriptors are initialized and submitted in ascending kind order.
- Nonzero submission results trigger another dependency call but do not directly abort processing.
- The main path masks a record flags word and returns another record field.

“Service,” “record,” “descriptor,” “request,” and “submission” are descriptive labels. Their application-level meanings are not established. A registration or lifecycle-management interpretation is **inferred intent**, not a verified API contract.

## Behavior

### Entry and service initialization

The function first reads the base-pointer global and retains that value as the captured base. It then initializes four private descriptor slots to zero.

It separately reads the base-pointer global again and uses this second value as the test base. It reads the service field at test base plus 4.

If that field is nonzero, initialization is skipped. This does not establish that the field at captured base plus 4 is nonzero: the two global reads may have supplied different bases.

If the tested field is zero:

1. The initializer-argument-1 global supplies the first argument to F-d7ef2d5b2803.
2. The distinct initializer-argument-2 global supplies its second argument.
3. The initializer is called.
4. Its 32-bit result is written to captured base plus 4.
5. A zero initializer result causes an immediate zero return.

The numbered argument positions do not imply an ordering between the two argument-global reads.

The initializer-result write occurs even when the result is zero. Its destination remains the captured base, regardless of changes the initializer may make to the base-pointer global.

If the captured and test bases differ, the field that triggered initialization is not necessarily overwritten. Conversely, a skipped initialization does not validate or repair the captured-base field used later.

The zero-result branch tests the initializer’s returned value, not a fresh read of the destination field. No record lookup occurs on that branch.

No synchronization or atomic once-only initialization protocol is visible.

### Record acquisition and mandatory descriptor request

After initialization is skipped or returns nonzero, F-55d1d3164b96 receives the original input unchanged.

A zero result selects the failure exit. A nonzero result is retained as the associated-record address.

For a nonzero record, the function requests the mandatory kind-3 descriptor by calling F-43da6b23bd44 with `(8, 0, 0)`.

If this request returns zero, the function takes the failure exit. It does not evaluate optional-descriptor conditions, submit descriptors, perform the final flags update, or return the record’s result field.

### Optional descriptor requests

After successful kind-3 allocation, optional requests are considered in order 0, 1, then 2.

**Kind 0:** The function first reads the record field at offset 12. If nonzero, it reads the input-addressed field at offset 16 and retains that value for this decision. If the first record read was zero, the retained decision value is zero and no input-addressed read occurs.

The function then reads the record field at offset 12 again. Kind 0 is requested only when this second record read and the retained input-field value are both nonzero.

Consequently:

- A zero first record read suppresses kind 0 even if the second read becomes nonzero.
- A nonzero first read can cause the input read even if the second record read becomes zero.
- The input field is not reread for the final kind-0 decision.

**Kind 1:** A nonzero read of the record field at offset 0 enables its request.

**Kind 2:** A nonzero read of the record field at offset 4 enables its request.

Each enabled request passes `(8, 0, 0)` to F-43da6b23bd44. A zero optional result leaves that descriptor absent and does not abort processing.

These conditions are evaluated at their respective execution points. They are not a combined snapshot. In particular, kind-1 and kind-2 conditions can observe changes made by earlier descriptor-request calls. No dependency is assumed to preserve the record or globals.

### Descriptor writes and submission

Only after all request decisions does the function process descriptors, in ascending kind order: 0, 1, 2, 3.

For each nonzero descriptor slot, the observable sequence is:

1. Write its kind into the four-byte field at descriptor offset 0.
2. Write the associated-record address into the four-byte field at descriptor offset 4.
3. Read the service value at captured base plus 4.
4. Call F-dbd019788d3d with that service value as argument 1 and the descriptor address as argument 2.
5. If the submission result is nonzero, call F-5990a26eaaa3 with no explicit argument shown.

Zero descriptor slots are skipped.

The mandatory kind-3 descriptor is requested first but processed last. Optional descriptors can therefore be submitted before it.

Each submission receives a fresh service-field read from the captured base. The function does not reread the base-pointer global for submission. A dependency changing the captured-base field can affect later submissions; changing only the base-pointer global does not retarget them.

No nonzero-service check precedes submission. A submission can receive zero if that is the value read at this stage.

A nonzero submission result does not directly stop iteration, select the failure exit, suppress the flags update, or replace the eventual return value. Continued execution remains conditional on F-5990a26eaaa3 returning and subsequent storage remaining valid.

### Final record update and return

After descriptor processing, the function reads the 32-bit record flags field at offset 20 and writes back its bitwise AND with **0xFFFFFFF2**.

This clears exactly bits 0, 2, and 3. Bit 1 and bits 4 through 31 retain their values from this final flags read.

The function then reads the record’s four-byte field at offset 8 and returns it. Neither flags nor the result field are snapshotted before dependency calls.

This is an ordinary visible read-and-write sequence, not an established atomic update.

### Failure exit after record acquisition

The failure exit examines the four descriptor slots in ascending order and contains a no-explicit-argument F-5990a26eaaa3 call for each nonzero slot.

Under the supplied control flow, every slot is zero on entry to this exit:

- A zero record result precedes all descriptor requests.
- A zero mandatory request leaves kind 3 absent and prevents optional requests.

Thus, no descriptor-related dependency call is reached through this failure-exit loop under the visible paths.

If the retained record address is nonzero, the function calls F-5990a26eaaa3 with that address as an explicit argument. It then returns zero. No direct flags-mask write occurs on this exit.

## Side effects

### Direct writes

Externally addressed writes performed directly by this function are:

- The initializer result at captured base plus 4, whenever initialization is attempted.
- Two four-byte fields in every present descriptor, immediately before its submission.
- The masked flags word at record offset 20 on the main path.

The private descriptor slots are internal bookkeeping.

No rollback is shown. Initialization can remain effective after record lookup or mandatory allocation fails. Optional request failures permit a partial descriptor set.

### Ownership, aliasing, and lifetime

- A zero submission result does not prove acceptance or ownership transfer.
