# F-7834b08494a4

## Purpose

F-7834b08494a4 conditionally reuses an existing entry or installs a new entry associated with a supplied 32-bit value and length. It returns a status and, on specified successful paths, publishes a one-based entry identifier.

Established behavior includes admission checks, optional lookup, descriptor acquisition, storage-adjustment requests, entry installation, and conditional counter increments. A successful admitted zero-length call performs no lookup or insertion.

The arrangement suggests duplicate detection, reference counting, and variable-length storage. Those are inferred purposes, not guarantees about ownership, transfer direction, synchronization, or dependency implementations.

## Behavior

### Admission and empty input

The observable sequence is:

1. Clear the supplied result cell, if nonzero.
2. Call F-0aff6a5050f5 with the state.
3. If that call returns zero, return −50.
4. Read +0x30. If nonzero, return −50 without reading flags for admission.
5. Read +0x04. If bit 6 is set, return −50.
6. Capture bit 0 for subsequent reuse and insertion-counting decisions.
7. If length is zero, return zero.

Thus empty input still undergoes admission and the initial dependency call. No lookup or insertion follows on its successful path. The output remains zero only if neither aliasing nor dependency effects change it.

The captured bit-0 decision is not refreshed later, even if dependencies or aliased writes change the flags.

### Existing-entry lookup

Lookup requires captured bit 0 to be set, a nonzero descriptor handle at +0x08, and a nonzero data handle at +0x10. These checks do not validate reachable arrays or the counter handle.

When eligible, the function calls F-efaaaab570a3, then reads current flag bit 2.

With bit 2 clear, it reads and caches the data base, counter base, and descriptor base, in that order. It scans descriptors from index zero upward. Each loop-bound evaluation compares the index against the current +0x1C interpreted as signed 32-bit; the count is not captured once for the entire search.

For each descriptor:

- F-88337f8f5d95 receives its address.
- Only a nonzero result permits reading and comparing its second word with the input length.
- Only equal lengths permit calling F-UNMAPPED-01 with the original source value, cached data base plus the descriptor’s first word, and input length.
- A nonzero comparison result is a match.

On the first match, the corresponding counter at the cached counter base is incremented, the index plus one is written to the result cell, F-2a517f9b9ef3 is called, and zero is returned. Later descriptors are not inspected.

The descriptor pointer advances by eight bytes between attempts. Cached bases are not refreshed across the per-descriptor dependencies, even though those dependencies’ mutation guarantees are unknown.

With current bit 2 set, F-849b785f50ce instead receives all four original arguments. A nonzero return means handled success: the function calls F-2a517f9b9ef3 and returns zero. It does not itself publish an identifier or increment a counter on that branch.

If either lookup route reports no match, F-2a517f9b9ef3 runs before insertion. The entry/exit pairing suggests synchronization, but no locking contract is established.

### Free-descriptor acquisition and identifier derivation

Every insertion-loop iteration begins with F-30a0e9a392e7 receiving the state and zero.

If the free head is nonzero, the function obtains the current descriptor base and reads the head for address calculation. The selected descriptor address is the base plus eight times the head, minus eight, using 32-bit arithmetic.

It reads the selected descriptor’s second word and writes that value to +0x20, popping the head. Only after this read and write does it test whether the computed descriptor address is zero. A zero address therefore does not avoid the preceding link access or undo the head update; it leads to descriptor growth.

For a nonzero descriptor address, the published identifier is derived rather than simply copied from the earlier head:

- The descriptor base is read again, after the free-head write.
- The 32-bit difference between the retained descriptor address and this freshly read base is interpreted as signed.
- That signed difference is shifted right arithmetically by three.
- One is added to obtain the 32-bit identifier.

The fresh base can differ if the head write aliases relevant storage. Even with a stable base, a difference whose high bit is set receives signed, not unsigned, division-like treatment. Equality with the original head therefore requires suitable valid-address, arithmetic, and nonaliasing assumptions.

The function then calls F-ec8cbc7f302e with the state. Its returned 32-bit value is retained as the data offset.

### Data-space adjustment

After F-ec8cbc7f302e, the current +0x24 is compared with the input length, both interpreted as signed 32-bit. Only a strictly smaller available-byte value triggers growth.

For growth:

- Read +0x28.
- Retain the unsigned maximum of that value and the unsigned input length as the requested increment.
- If the old +0x28 is below 0x20000 unsigned, replace +0x28 with twice that old value.
- Call F-7eff13797b9b with the address of +0x10 and the retained increment.

The request uses the old policy value’s maximum, not a newly doubled value or a policy value changed by the dependency.

After this call, whether it succeeds or fails, the descriptor address is recomputed from the current descriptor base and the saved derived identifier.

On nonzero adjustment status, the function writes 0x80000000 to that descriptor’s first word, writes the current free head to its second word, sets the head to the saved identifier, and returns the status. These writes use the saved derived identifier, not a separately retained original head. They do not restore +0x28 or undo dependency effects.

On successful adjustment, the retained increment is added to the then-current +0x24.

Without data growth, the descriptor address retained before F-ec8cbc7f302e is used without recomputation.

### Entry installation

F-70a021fc7c24 receives the original source value, current data base plus the retained data offset, and original length. Its return value is not checked. Which argument is a transfer destination is not established here.

After it returns, the function performs these writes in order:

1. Subtract length from the current +0x24.
2. Write length to the retained descriptor’s second word.
3. Write the retained offset to its first word.
4. Write the derived identifier to the result cell.

If captured bit 0 is clear, it returns zero.

Otherwise, it reads the current counter base and increments the counter selected by the derived identifier. It then reads current flag bit 2. If set, F-4cffcc8d6e9b receives the state and original source value. Its result is not interpreted. The function returns zero.

Output aliasing can therefore affect state consulted after publication, including the counter handle and final flag check.

### Descriptor-storage growth

Growth occurs when the head was zero or a popped descriptor address was zero.

First, +0x2C is compared with 0x1000 unsigned. If smaller, that field is doubled. The descriptor-adjustment request then reads +0x2C and passes eight times that value to F-7eff13797b9b, together with the address of +0x08.

A nonzero result is returned immediately. The policy update, if any, is not reversed.

If captured bit 0 is set, the counter-adjustment request independently rereads +0x2C after the descriptor dependency returns. F-7eff13797b9b receives the address of +0x0C and four times this newly read value. It need not use the quantity used for the descriptor request.

If the counter request fails, the rollback request independently rereads +0x2C after that failed call. F-7eff13797b9b receives the address of +0x08 and negative eight times this latest value. Its return is ignored; the counter-request failure is returned. This is not necessarily an inverse of the earlier descriptor request.

After all required requests succeed, initialization uses current state, not a preallocation snapshot:

- The start address uses the descriptor base and +0x1C read after the allocation calls.
- A zero-based initialization index is compared unsigned against a fresh +0x2C read on each loop evaluation.
- Each visited descriptor’s first word receives 0x80000000.
- Starting with the second visited descriptor, the preceding descriptor’s second word receives the currently read +0x1C plus the initialization index plus one.
- The descriptor pointer advances eight bytes per iteration.

No final-link terminator is explicitly written. No counter values are explicitly initialized.

After initialization, the free head is written as the then-current +0x1C plus one. The count update subsequently rereads +0x1C and +0x2C and writes their sum to +0x1C. In particular, it does not use a count captured before allocation, and the free-head write can matter if state aliases storage.

The insertion loop repeats. No iteration limit, zero-growth rejection, or consistency check links requested byte sizes to the quantities later used for initialization.

## Side effects

Direct writes can affect the result cell, growth-policy fields, available-byte accounting, free head, descriptor count, descriptors, and counters. Dependencies can additionally affect state, handles, backing storage, and globals; their preservation guarantees are unknown.

Success and failure are not transactional. Output clearing, head removal, policy changes, allocation effects, and dependency mutations can survive failure. The explicit recovery paths are limited to reinserting a selected descriptor after data-adjustment failure and requesting descriptor shrinkage after counter-adjustment failure.

No explicit source release or ownership transfer is established. Storage adjustment receives handle-field addresses and may replace handles, but allocation, relocation, and release semantics remain documented_only.

Address retention is significant:

- Linear search retains bases across dependency calls.
- Insertion retains its descriptor address across F-ec8cbc7f302e unless data growth occurs.
- Data adjustment refreshes the descriptor address afterward.
- The transfer dependency runs before writes through that retained address.
- Descriptor initialization obtains its start after allocation dependencies but does not recompute that pointer on each iteration.

Correct operation therefore depends on storage-validity and mutation constraints not supplied by this function alone.

## Acceptance examples

These are conditional static cases, not executed tests. Unless stated otherwise, assume accessible backing storage, nonaliasing state and output, stable relevant fields, and dependencies that return normally.

1. **Initial rejection.** If F-0aff6a5050f5 returns zero, a supplied result cell has already been cleared, and the function returns −50 without local lookup or insertion.

2. **Admitted empty input.** With a nonzero gate result, +0x30 zero, bit 6 clear, and length zero, the result is zero. No entry is selected; no lookup or insertion dependency runs.

3. **First linear match.** With eligible reuse and bit 2 clear, if descriptor three is the first qualifying comparison match, counter three increases by one, identifier 3 is published, the lookup-exit dependency runs, and no insertion follows.

4. **Alternate handled success.** If F-849b785f50ce returns nonzero, the enclosing function returns zero after the lookup-exit call. Its own body supplies no identifier or counter update on this path.

5. **Ordinary identifier recovery.** With a stable base, head 3, and a valid descriptor address 16 bytes above that base, the fresh-base difference is 16; arithmetic shifting by three and adding one produces identifier 3. Without those assumptions, equality with the original head is not guaranteed. A signed difference of −8 instead produces identifier zero.

6. **Data-adjustment failure.** If data adjustment fails after a descriptor is popped, the descriptor recomputed from the saved identifier and current base is marked free and pushed onto the then-current head. The adjustment status propagates; earlier effects remain.

7. **Independent growth requests.** Suppose +0x2C starts at 4. Local doubling makes the descriptor request 64 bytes. If that dependency changes +0x2C to 12, the counter request is 48 bytes. If the failing counter dependency changes it to 20, rollback requests −160 bytes, not −64. The counter failure remains the returned status regardless of rollback’s result.

8. **Post-allocation initialization.** Suppose successful descriptor and counter requests leave +0x1C at 20 and +0x2C at 2, with sufficient backing storage. Initialization starts at descriptor index 20, marks indices 20 and 21 free, links the first to identifier 22, and leaves the second link unwritten. The free head becomes 21 and the count becomes 22. Earlier request quantities do not replace these current-state reads.

9. **Uncounted insertion.** With captured bit 0 clear, valid free storage, sufficient signed space, and a returning transfer dependency, installation publishes the derived identifier without incrementing a counter or calling the final indexing dependency.

## Uncertainties

The following remain documented_only:

- Dependency semantics, ownership rules, preservation guarantees, and relocation behavior.
- Valid state construction, allocation extents, counter initialization, and free-chain termination.
- Transfer direction, overlap behavior, and required source lifetime.
- Synchronization and concurrent-access guarantees.
- Fault behavior for invalid addresses and null result cells on publishing paths.
- Alternate lookup’s output and counting guarantees.
- Coordination between the offset dependency and available-byte accounting.

Arithmetic hazards are visible but not locally resolved. Lengths at or above 0x80000000 are negative in the signed space comparison. Address differences used for identifier recovery also receive signed interpretation and arithmetic shifting. Growth products, doubling, counter increments, address calculations, and accounting updates have no explicit overflow guards.

Zero descriptor growth can initialize nothing yet still set the free head to current count plus one. Large growth values can wrap byte requests. Dependency changes can make descriptor, counter, rollback, and initialization quantities disagree. The final newly initialized free link is unwritten. None of these cases has a locally established safe outcome.
