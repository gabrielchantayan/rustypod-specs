# F-f36b2c975917

## Purpose

F-f36b2c975917 conditionally unlinks a selected node from a pointer-linked structure, adjusts links and color metadata, prepends the selected node to a container-associated chain, decrements a 32-bit count, and writes a 32-bit result to caller-provided storage.

The representation is consistent with deletion from a header-based red/black tree. Tree terminology describes inferred roles; it does not establish ordering invariants or a balancing guarantee. The contract preserves the visible repair-cursor choices and dependency calls rather than substituting a conventional deletion algorithm.

An initial dependency can bypass structural processing. That path still performs the final output store. If output storage aliases a structural field, that store can modify the structure despite the bypass.

| Argument | Established use |
|---|---|
| Output storage | Writable address receiving one 32-bit word at completion. Its existing contents are not directly read. |
| Container address | Address supplying the chain head, header reference, and count described below. |
| Selection storage | Readable address supplying a 32-bit value initially and, on the removal path, supplying the selected-node address through a later read. |

There is no explicit return value. Results consist of memory effects, dependency effects, and the final output word.

References occupy 32-bit words in the supplied representation. Null is represented by zero. Color accesses are one byte. All offsets below are byte offsets; byte order is not established.

### Node and header layout

| Offset | Width | Node role |
|---|---:|---|
| +0 | 8 bits | Color or repair-state byte |

For the header, +4 supplies the root reference, +8 the cached leftmost reference, and +12 the cached rightmost reference.

Color 0 takes branches conventionally associated with red. Color 1 takes branches associated with black. The repair-entry condition accepts any nonzero removed-node color, whereas loop continuation and black-child tests require exactly 1. Other byte values therefore do not behave uniformly as black.

### Preconditions and aliasing

Defined completion requires every access actually reached to address valid storage of the corresponding width. There is no explicit validation of pointers, node membership, topology, colors, count, or dependency results beyond the initial zero/nonzero decision.

Traversed child and parent paths must terminate for completion. Dependencies must leave subsequent accesses valid; their preservation of memory or global state is not established.

Output and selection storage are not required to be distinct by any visible check. Their aliasing is compatible with reading selection before the final output store. Broader aliasing can change behavior:

- Earlier structural writes can affect later reads of overlapping fields.
- Repeated header reads need not yield the same reference.
- The final output store can overwrite a count, chain link, color-containing word, header reference, or node link if addresses overlap.

The structural descriptions below specify ordered operations, not unconditional final-state guarantees under arbitrary aliasing.

## Behavior

### Initial decision and retained result

The function first reads selection storage into a temporary 32-bit result cell, then reads the container’s header reference into a second temporary cell. F-3ee46ff4f2dc receives the addresses of both cells.

If its result is nonzero, the function rereads the container’s header reference, puts that value into the result cell, and writes the result cell to output storage. It skips the explicit unlinking, repair, chaining, and count-decrement operations. Dependency effects and output aliasing can still change structural state.

If its result is zero, F-0a8f01d26159 receives the result cell’s address. Selection storage is then read again, and this later value identifies the selected node.

Structural processing does not directly assign another value to the result cell. Nevertheless, its final contents are not determined solely by the first two calls: a later dependency could modify it through an address retained by an earlier dependency. Output receives the cell’s value at the final store.

### Structural case selection

The selected node’s left-child reference is examined before its right-child reference.

- With no left child and no right child, the node is a leaf.
- With exactly one nonnull child, that child is the replacement.
- With two nonnull children, left-child links are followed from the right child until a node with no left child is reached. This is the structural successor. Its right child, possibly null, is the replacement at its former position.

No payload, key comparison, or ordering check participates. Some child references are read both for assignment and for a subsequent condition; no single-read or snapshot guarantee is established.

The originally selected node is the node ultimately placed on the chain in every removal case.

### Leaf removal

The selected leaf’s parent becomes the repair cursor.

If that parent equals the current header, the function performs these writes in order:

1. Header rightmost reference becomes the parent/header reference.
2. Header leftmost reference becomes that same reference.
3. Header root reference becomes zero.

The header reference is obtained again for the individual header accesses rather than treated as an immutable snapshot.

Otherwise, the parent’s left-child reference is compared with the selected node. If equal, that left-child field is cleared; otherwise the parent’s right-child field is cleared. Each clear consists of four consecutive zero-byte writes in increasing address order.

Only the corresponding cached extreme is then checked: leftmost for the left-child branch, rightmost for the other branch. If it equals the selected node, it is replaced with the parent. Both extremes are not recomputed.

### Replacement by the only child

For a selected node with exactly one nonnull child:

1. The replacement’s parent receives the selected node’s parent reference.
2. If the header’s root reference equals the selected node, that root field receives the replacement.
3. Otherwise, the selected node’s parent has its left link replaced if that link equals the selected node; its right link is replaced otherwise.
4. Cached extremes are checked and conditionally updated.

The leftmost-cache check precedes the rightmost-cache check.

If the leftmost cache equals the selected node:

- When the selected node’s right child is null, the cache receives the selected node’s parent.
- Otherwise, left-child links are followed through the replacement subtree, and the terminal node becomes the cache.

If the rightmost cache equals the selected node:

- When the selected node’s left child is null, the cache receives the selected node’s parent.
- Otherwise, right-child links are followed through the replacement subtree, and the terminal node becomes the cache.

These are conditional operations on cached metadata, not an unconditional reconstruction of extremes. The replacement child becomes the repair cursor.

### Successor relocation

For a node with two children, the successor is moved into the selected node’s structural position. No payload copy is visible.

First, the selected node’s left child receives the successor as parent. The successor’s left-child field then receives the selected node’s left-child reference.

If the successor was the selected node’s immediate right child, a nonnull successor right child receives the successor as parent. The successor’s right-child field is otherwise retained.

If the successor was deeper in the right subtree, the following occurs in order:

1. A nonnull successor right child receives the successor’s former parent.
2. The successor’s former parent has its left-child field replaced with that child, including zero when absent.
3. The successor’s right-child field receives the selected node’s right-child reference.
4. That right child receives the successor as parent.

Next, the selected node’s incoming root or parent link is replaced with the successor. The root field is used when it equals the selected node; otherwise the parent’s left link is used when it equals the selected node, and its right link is used otherwise. The successor’s parent field then receives the selected node’s parent reference.

The successor’s color is saved, the successor receives the selected node’s color, and the selected node receives the saved color. Thus the selected node’s color used for repair entry is its post-exchange color.

The repair cursor is the successor’s original right child if nonnull. Otherwise it is the successor itself, even when the successor came from deeper in the subtree. No explicit cached-extreme update occurs in this two-child branch.

### Repair entry and completion

Repair is entered only when the cursor differs from the current header and the selected node’s current color is nonzero. If the cursor equals the header, the selected node’s color need not be read for this decision.

Once entered, repair reaches a shared completion point that writes color 1 to the current cursor. At each loop check:

- If the cursor equals the current root, repair completes.
- Otherwise, if the cursor’s color is not exactly 1, repair completes.
- Otherwise, sibling processing continues.

The root reference is read through the current container header at each loop check.

### Sibling processing and rotations

The cursor’s parent is read. If the parent’s left link equals the cursor, the sibling is the parent’s right child. Otherwise the sibling is the parent’s left child; membership in that right-child field is not separately verified.

For a left-child cursor, the sibling’s left child is the inward child and its right child is the outward child. The meanings are mirrored for the opposite orientation.

A sibling of color 0 is first changed to 1, and the cursor’s parent is changed to 0. A red-sibling rotation-like call follows:

### Chaining, decrement, and output

After structural processing and any repair, the function:

1. Reads the container’s current chain head and writes it into the selected node’s +12 field.
2. Writes the selected-node reference into the container’s chain-head field.
3. Reads the 32-bit count, applies a decrement by one, and writes the 32-bit result back.
4. Writes the result temporary’s current 32-bit value to output storage.

There is no zero-count check, saturation, or rejection branch. Modulo-32-bit arithmetic would map zero to 4,294,967,295, but the representation does not establish the original implementation’s language-level signed-overflow guarantees.

Each later access can observe earlier overlapping writes. In particular, the output store can overwrite an otherwise completed structural or count update.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless an example concerns aliasing, final-state claims require nonoverlapping output storage and no other overlapping access or dependency effect that overwrites the stated result.

1. **Bypass with a changed header.** If F-3ee46ff4f2dc returns nonzero after changing the container’s header reference, output receives the header reference read after that call. F-0a8f01d26159 is not called. Explicit structural processing is skipped, but an aliased output store can still alter structural state.

2. **Selection changes before removal.** If an initial dependency changes selection storage, removal uses the value read after F-0a8f01d26159, not necessarily the initially captured value.

3. **Result-cell preservation.** If the first two dependencies leave a particular value in the result cell and all subsequent dependencies preserve it, the final output store writes that value. Without preservation, the criterion is instead that output receives the cell’s value at the final write.

4. **Single-node structure.** For a selected leaf whose parent is the header, the explicit header writes set rightmost and leftmost to the header, then clear the root. With the aliasing and preservation conditions above, those values remain after completion; the selected node becomes chain head and the count is decremented.

5. **One-child root.** With consistent links, replacing a selected root having one child writes that child into the root field and assigns it the selected node’s parent. Subject to subsequent effects, the child remains root while the originally selected node becomes chain head.

6. **Two-child relocation.** The leftmost node of the right subtree is structurally relocated rather than copied as payload. Its color is exchanged with the selected node’s color before repair entry. If its original right child is null, the successor itself is the repair cursor.

7. **Missing sibling before preliminary processing.** If initial sibling selection yields null, the current cursor is written with color 0 and repair advances to the already read parent. The same transition uses the reread parent when the sibling becomes null after a red-sibling call.

8. **Missing sibling after preliminary processing.** If a preliminary rotation-like call leaves the reread sibling null, repair does not color the cursor 0 or ascend. It writes color 1 to the current cursor at shared completion, then proceeds to chaining.

9. **Repair skipped for zero color.** If the selected node’s color is 0 at repair entry, that phase performs no direct recoloring or rotation-like call. The earlier relocation phase may already have exchanged colors.

10. **Chain and count boundary.** With nonoverlapping fields and preserved storage, the selected node’s +12 receives the chain head current at chaining, before the container head changes. A zero count does not reject removal; it reaches the same 32-bit decrement operation, subject to the arithmetic uncertainty stated above.

11. **Output aliases the count.** If output storage is exactly the count field and execution completes, the final output store overwrites the decrement result. A final count of “previous count minus one” is therefore not an unconditional postcondition.
