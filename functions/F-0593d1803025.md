# F-0593d1803025

## Purpose

F-0593d1803025 obtains one 32-byte slot from a caller-supplied pool and partially initializes that slot. It prefers a slot from a reusable-slot chain. If that chain is empty, it consumes the next slot in the current backing region, obtaining a new region when the current cursor equals its limit.

The function has no explicit return value. Its observable results are changes to pool bookkeeping, initialization writes to the selected slot, and, when growth is required, two calls to F-871e64ddc6de.

“Pool,” “reusable-slot chain,” and “backing region” describe the apparent roles of the supplied fields. The field accesses and updates are established static evidence; a larger allocation or ownership protocol is not established.

## Interface

### Input and result

The sole explicit input is an address identifying writable pool state. The visible representation uses four consecutive 32-bit fields:

| Byte offset | Width | Role in this function |
|---|---:|---|
| 0 | 32 bits | Address of the current backing-region header, or zero |
| 4 | 32 bits | Address of the first reusable slot, or zero |
| 8 | 32 bits | Cursor identifying the next unconsumed slot |
| 12 | 32 bits | End address used to detect exhaustion |

The function returns no explicit result, including no pointer to the selected slot and no status code.

Address-bearing fields are represented as 32-bit values in the supplied material. This establishes the visible layout, not portability to a wider-address environment.

### Backing-region header

A newly obtained header occupies 12 bytes:

| Byte offset | Width | Value written |
|---|---:|---|
| 0 | 32 bits | Pool header address read when this header is linked |
| 4 | 32 bits | Selected slot capacity |
| 8 | 32 bits | Address returned for backing storage |

When calculating growth from an existing header, the function reads only its capacity field, at offset 4. It does not inspect that header’s backing-storage address or previous-header link.

### Slot layout used here

Each slot has a stride of 32 bytes. The function accesses only these portions of a selected slot:

| Byte offset | Width | Use |
|---|---:|---|
| 0 | 8 bits | Written as zero |
| 4 | 32 bits | Written as zero |
| 8 | 32 bits | Written as zero |
| 12 | 32 bits | Read as a reusable-chain link on the reuse path, then written as zero |

Bytes 1–3 and 16–31 are not explicitly written by this function. Full-slot clearing is not part of the contract.

### Preconditions for normal completion

The pool-state address must support the indicated reads and writes. Any nonzero reusable-slot address must support reading its link and performing the initialization writes.

When a slot is taken from the cursor, that cursor must identify storage adequate for those writes. Equality with the end address is the only exhaustion check: the function does not validate ordering, alignment, remaining byte count, or region membership.

On growth, F-871e64ddc6de must return usable storage for a 12-byte header and for the requested backing-storage size. The function does not check either result.

These are conditions needed for normal execution, not validations performed by the function.

## Behavior

### 1. Prefer a reusable slot

The function first reads the reusable-slot field at pool offset 4.

If it is nonzero:

1. That address becomes the selected slot.
2. The function reads a 32-bit link from selected-slot offset 12.
3. It writes that link into the pool’s reusable-slot field.
4. It performs the slot-initialization writes described below.

The cursor, end address, and backing-region header are not directly accessed on this path. No dependency call occurs.

The link is consumed before it is cleared. A self-link or other malformed chain is not detected. The function processes only one chain element; it does not traverse or validate the remainder.

### 2. Use the current cursor when no reusable slot exists

If the reusable-slot field is zero, the function reads the cursor from pool offset 8, then compares it with the end address at offset 12.

If they are unequal, the cursor becomes the selected slot. The function writes an address 32 bytes beyond that slot into the cursor field, then initializes the slot.

There is no test that the cursor precedes the end address. A cursor beyond the end, or one less than 32 bytes before it, still follows this path if the addresses are unequal. Whether such a state permits valid memory accesses depends on the surrounding storage; this function does not make it safe.

### 3. Grow when cursor and end are equal

If the cursor equals the end address, the function selects a new capacity.

With a zero backing-region header address, the capacity is 32 slots.

With a nonzero header address, it reads that header’s 32-bit unsigned capacity, denoted here by \(c\), and calculates:

- Additive candidate: \(a = c + 32\).
- Fractional-growth candidate: \(g = c + (c \mathbin{\gg} 1) + (c \mathbin{\gg} 3)\).

Both candidates use 32-bit unsigned arithmetic. The shifts are unsigned right shifts, and additions wrap modulo \(2^{32}\). The selected capacity is \(g\) when \(a \leq g\) under an unsigned comparison; otherwise it is \(a\).

For values whose additions do not overflow, this chooses the larger of an increase of 32 slots and growth by approximately five eighths of the previous capacity. That interpretation does not override the actual wrapping arithmetic.

The function then performs these operations in order:

1. Calls F-871e64ddc6de with arguments 12 and zero, retaining its result as the new header address.
2. Calls F-871e64ddc6de with arguments equal to the selected capacity shifted left by five bits, and zero, retaining its result as the backing-storage address.
3. Writes the backing-storage address into new-header offset 8.
4. Reads the pool’s header field and writes that value into new-header offset 0.
5. Writes the selected capacity into new-header offset 4.
6. Writes the new header address into pool offset 0.
7. Reads the backing-storage address from new-header offset 8 and uses it as the selected-slot address.
8. Writes the address calculated as selected-slot address plus capacity times 32 into the pool’s end field.
9. Writes selected-slot address plus 32 into the pool’s cursor field.
10. Performs the slot-initialization writes.

The backing-storage request is a 32-bit left shift. Its size is therefore the low 32 bits of capacity times 32, not an unbounded mathematical product. The visible end-address calculation likewise provides no overflow protection.

The header linked at step 4 is read **after both dependency calls**. It is not necessarily the same header whose capacity was read before those calls. If a dependency can modify the pool through other accessible state, those modifications may affect the link written into the new header. The supplied material does not establish dependency purity.

Similarly, publication of the new header occurs before the pool’s end and cursor fields are updated. The operation is not visibly transactional.

### 4. Initialize the selected slot

After either selection path and its bookkeeping updates, the function writes:

1. A 32-bit zero at selected-slot offset 4.
2. A 32-bit zero at selected-slot offset 8.
3. A 32-bit zero at selected-slot offset 12.
4. An 8-bit zero at selected-slot offset 0.

This order is part of the visible access sequence. In particular, pool bookkeeping is updated before these writes, and the byte at offset 0 is cleared last.

No further work is shown. The function neither returns the selected address nor explicitly stores it into a separate output field.

## Side effects

### Pool-state mutation

For ordinary, non-overlapping storage:

- Reuse updates only the reusable-slot field.
- Cursor consumption without growth updates only the cursor field.
- Growth updates the header, end, and cursor fields.
- Every successful path performs the same selected-slot initialization writes.

Those field summaries assume the selected slot, pool state, and headers do not overlap. The function contains no overlap checks. Aliasing could make a slot write overwrite bookkeeping or make earlier header writes affect later reads.

### Allocation and lifetime

Growth makes two dependency calls. No explicit release operation appears on any path. Existing headers are linked rather than explicitly freed.

The visible linkage is consistent with retaining earlier regions, but it does not establish who owns them, how their slots are reclaimed, or which operation eventually releases them. Neither the zero second argument nor the dependency’s allocation-like use proves a particular lifetime policy.

### Errors and partial updates

There is no explicit failure return, null-result handling, overflow handling, rollback, or state validation.

If the first dependency result is unusable, the second call still precedes the first write through the header address. If the second result is unusable, it is still recorded and used to calculate pool addresses before slot initialization is attempted.

An invalid memory access may interrupt execution after earlier writes have occurred. The function provides no visible recovery guarantee. Dependency-internal error reporting or non-returning failure behavior remains unknown.

### Concurrency

No lock, atomic operation, or synchronization protocol is visible. Shared concurrent access would require external guarantees not established here. The ordered writes do not constitute an atomic pool transition.

## Acceptance examples

These are conditional static expectations, not results of executed tests.

### Reusing a slot

Given a nonzero reusable-slot address whose offset-12 link identifies a second slot:

- The pool’s reusable-slot field becomes the second-slot address.
- The original first slot receives the four initialization writes.
- The original first slot’s link becomes zero.
- No dependency call occurs.
- With disjoint storage, the header, cursor, and end fields remain unchanged.

If the stored link is zero, the reusable-slot chain becomes empty.

### Consuming an existing region

Given an empty reusable chain and a cursor unequal to the end address:

- The previous cursor address identifies the selected slot.
- The new cursor is 32 bytes beyond that address.
- The selected slot receives the specified partial initialization.
- No dependency call occurs.

This expectation does not imply that an unequal cursor is valid. Storage validity remains a precondition.

### Creating the first region

Given an empty reusable chain, equal cursor and end addresses, and a zero header field:

- Capacity is 32 slots.
- Dependency request sizes are 12 bytes and 1,024 bytes, in that order.
- If the header field remains zero through the calls, the new header’s link is zero.
- The new end is 1,024 bytes beyond the returned backing address.
- The new cursor is 32 bytes beyond that address.
- The first slot receives the initialization writes.

The backing region is not otherwise explicitly cleared.

### Growing from 32 slots

- The fractional-growth candidate is 52.
- Selected capacity is 64.
- The backing-storage request is 2,048 bytes.

### Growing from 128 slots
