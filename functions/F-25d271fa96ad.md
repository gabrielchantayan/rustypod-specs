# F-25d271fa96ad

## Purpose

F-25d271fa96ad constructs a multilevel decoding table from an indexed sequence of symbol code lengths. For accepted nonempty input, it also writes the nonzero-length symbol indices into workspace, ordered first by length and then by original index.

Established behavior includes:

- Counting lengths in sixteen unsigned 16-bit counters.
- Rejecting oversubscribed distributions and most incomplete nonempty distributions.
- Selecting a root-table width bounded by the detected nonzero lengths.
- Writing four-byte decoding records and links to subsidiary tables.
- Enforcing a mode-one footprint limit of fewer than 1,456 records.
- Advancing a table cursor and reporting the selected width on success.

The structure is consistent with canonical prefix-code decoding using least-significant-bit-first table indices. This is **inferred intent**, not an established association with any particular format.

Storage addresses are supplied through arguments. The function writes through those addresses, but the body does not establish ownership of the workspace, table storage, or reference cells. Their ownership and external lifetime arrangements are **documented_only**.

## Interface

The function accepts six arguments and returns a 32-bit result. The supplied body uses a 32-bit address model.

| Argument | Representation and role |
|---|---|
| Mode | Signed 32-bit selector. Zero, one, and all other values select different symbol interpretations. |
| Length sequence | Address of unsigned 16-bit lengths, indexed by symbol number. |
| Symbol count | Unsigned 32-bit number of length elements to inspect. |
| Table-cursor reference | Address of a writable 32-bit address cell identifying table storage. |
| Root-width reference | Address of a writable unsigned 32-bit requested-width cell; receives the selected width on success. |
| Workspace | Address of caller-provided writable storage for unsigned 16-bit symbol indices. |

“Caller-provided” describes how storage is supplied, not who owns it. No ownership transfer or external lifetime policy is established by the body. No allocation or release operation is visible.

### Results

| Raw result | Established meaning |
|---|---|
| `0x00000000` | Success; the cursor and root-width references have been updated. |
| `0xffffffff` | Oversubscribed distribution or disallowed incomplete nonempty distribution. |
| `0x00000001` | Mode-one table footprint reaches or exceeds 1,456 records. |

These are not general memory-safety results. Invalid addresses, insufficient storage, invalid lengths, and representational overflow are not explicitly reported.

### Record layout

Each decoding record occupies four bytes.

| Byte offset | Width | Meaning |
|---|---|---|
| 0 | 8 bits | Operation, or subsidiary-table width |
| 1 | 8 bits | Bits consumed at this decoding level |
| 2 | 16 bits | Symbol index, mapped value, or subsidiary-table offset |

Combined writes to the first two bytes have little-endian interpretation.

Record classes are:

- **Direct symbol:** operation zero; value is the unsigned 16-bit symbol index.
- **Mapped symbol:** operation and value come from selected lookup origins.
- **Distinguished terminal:** operation `0x60`; value zero.
- **Invalid entry:** operation `0x40`; value zero.
- **Subsidiary link:** operation is the subsidiary width, consumed bits equal the root width, and value identifies the subsidiary base as a record offset from the root base.

### Preconditions and representation

For the ordinary behavior described below:

- Length storage must be readable for the supplied count.
- Reference cells, workspace, and table storage must be accessible for their respective reads and writes.
- Lengths must be in 0–15. Larger values index outside the fixed counting storage; no explicit bounds check rejects them.
- Storage must not overlap in ways that let writes change inputs, reference cells, workspace entries, or lookup elements still needed.
- Address calculations and backing storage must remain valid.
- Inputs and reference cells must remain stable unless a separate-read scenario is explicitly being considered.
- Mapped lookup elements must be readable at every accessed address.

Counters, workspace positions, and stored symbol indices are 16-bit quantities. A counter wraps modulo 65,536. Cumulative positions also narrow to 16 bits, and symbol indices above 65,535 are truncated when stored. These conditions have no dedicated error result.

Workspace normally requires one 16-bit entry per nonzero-length symbol. Table storage must accommodate the root and all subsidiary tables. There is no capacity argument. The mode-one limit does not establish that the supplied storage is sufficiently large.

## Behavior

### Counting and width selection

The function clears sixteen private 16-bit counters, then scans the length sequence in increasing symbol-index order. Each length selects a counter to increment.

Length-zero entries are counted but do not occupy code space or appear in the sorted workspace.

The maximum nonzero length is found by inspecting counters from length 15 downward. This examines stored counter values, not an independent count of nonzero input elements. Counter wrap can therefore conceal an actual length population.

The root-width reference is read once to capture a provisional request and again for comparison with the detected maximum. If the second value exceeds that maximum, the provisional width becomes the maximum.

For nonempty input, the function finds the smallest length whose counter is nonzero and raises the provisional width to that minimum if needed. With a stable reference and ordinary nonwrapped counts, the result is the requested width clamped to the inclusive minimum–maximum interval.

No width-reference write occurs during selection.

### Empty-distribution path

If the detected maximum is zero, the function bypasses code-space validation, sorting, mode-dependent lookup setup, and footprint checks.

It writes two consecutive invalid records, each with operation `0x40`, consumed-bit count 1, and value zero.

For each record, the observable order is:

1. Read the current address from the cursor reference.
2. Advance that reference by four bytes.
3. Write the combined operation/consumed-bit halfword at the captured address.
4. Write the zero value halfword.

After both records, it writes 1 to the root-width reference and returns zero. The cursor advances by eight bytes overall.

This path applies to zero symbols and, without counter wrap, to an all-zero length sequence. It does not access workspace or either mode-dependent global pointer cell. The incoming width does not affect the result, although the width reference is read before the empty decision.

### Nonempty validation

Validation maintains a signed 32-bit available-prefix count. Starting from one, each depth from 1 through 15 doubles the available count and subtracts the stored count at that depth.

A negative result immediately returns `0xffffffff`.

After depth 15:

- Zero remaining space is accepted.
- Positive remaining space is rejected in mode zero.
- Positive remaining space is rejected in every mode if the detected maximum length is not 1.

For ordinary nonwrapped counts, the only accepted incomplete nonempty distribution is a single length-one symbol in a nonzero mode.

These rejection paths precede workspace writes, mode-dependent global pointer reads, and decoding-table writes. Under the nonaliasing preconditions, both output references and the supplied output storage remain unchanged.

The validation arithmetic fits within signed 32-bit range for the fifteen inspected depths and 16-bit counter values. This does not make wrapped counters faithful representations of the input.

### Stable workspace ordering

After successful validation, the function forms 16-bit cumulative starting positions for lengths 1 through 15.

It scans the input again in increasing symbol-index order. Each nonzero-length symbol index is narrowed to 16 bits and written at the next workspace position for its length.

With representable counts and indices, the resulting order is:

1. Increasing code length.
2. Increasing original symbol index within each length.

Later construction reads lengths through the symbol indices recovered from workspace. Consequently, truncation of an original index can affect both symbol identity and subsequent length selection.

### Mode setup and global reads

Mode setup occurs after workspace population and before the initial footprint check.

| Mode | Signed threshold | Value origin | Operation origin |
|---|---:|---|---|
| Zero | 19 | Workspace address | Workspace address |
| One | 256 | First read of the mode-one pointer cell | Second read of that cell, plus 62 bytes |
| Any other value | −1 | First read of the other-mode pointer cell | Second read of that cell, plus 64 bytes |

For each nonzero mode category, the selected global pointer cell is read twice. The first read establishes the value origin; the second independently establishes the operation origin.

The operation origin is therefore not necessarily a displacement from the captured value origin. Such a relationship requires equal results from the two pointer-cell reads. No synchronization or consistency check is visible.

Both reads occur even if the root footprint subsequently causes immediate mode-one rejection. That rejection avoids mapped lookup-element reads, not mode setup.

Mode zero uses workspace as both origins and reads neither global pointer cell.

### Symbol interpretation

Each unsigned 16-bit workspace index is compared against the selected signed threshold:

- Below the threshold: direct record.
- Equal to the threshold: distinguished terminal record.
- Above the threshold: mapped record.

Thus:

- Mode zero treats indices 0–18 as direct and 19 as terminal.
- Mode one treats indices 0–255 as direct and 256 as terminal.
- Every other mode maps every possible unsigned 16-bit index, because every such index exceeds −1.

For a mapped symbol, the function first reads a 16-bit operation element at the operation origin plus twice the symbol index. Only its low eight bits are retained. It then reads a 16-bit value element at the value origin plus twice the symbol index.

The two captured origins are reused; later pointer-cell changes do not refresh them.

Mode-zero indices above 19 also take this mapped branch, using workspace-relative accesses. Whether those indices are intended inputs, and whether sufficient workspace-relative lookup storage exists, are **documented_only**.

### Root and subsidiary tables

The root contains \(2^r\) records, where \(r\) is the selected root width. With stable, valid inputs, \(r\) lies in 1–15. The initial root base is read from the cursor reference after mode setup.

Symbols are consumed in workspace order. Code advancement follows canonical ordering with reversed-bit numerical progression for table indexing.

For each symbol:

- The consumed-bit field is its code length minus the root bits already accounted for at the active subsidiary level.
- The record is replicated into all matching positions of the active table.
- Replicas are written in descending table-index order.
- Each replica receives its operation/consumed-bit halfword before its value halfword.

When a longer code enters a root prefix not represented by the active subsidiary table, a new subsidiary table is placed immediately after the active table.

Its initial width is the current code length minus the root width. Remaining length counts can cause this width to increase, stopping when projected occupancy is sufficient or the maximum length is reached.

The subsidiary size is added to the total footprint before the corresponding root link is installed.

Link writes occur in this order:

1. Subsidiary-width operation byte.
2. Root-width consumed-bit byte.
3. Unsigned 16-bit record-offset field.

The link-writing expressions reread the cursor reference to locate the root, including when calculating the offset. Stable reference storage is therefore required for these accesses to agree with the initially captured root base.

For a nonnegative, four-byte-aligned displacement, the link value represents the displacement divided by four, reduced to the 16-bit field. Larger offsets are not explicitly rejected. Address and intermediate arithmetic must satisfy the stated representability preconditions for a usable link.

### Mode-one footprint limit

Only mode one enforces the 1,456-record threshold. The permitted footprint is strictly less than 1,456.

If the root alone requires at least 1,456 records, the function returns `0x00000001` after:

- Successful validation.
- Workspace population.
- Both mode-one pointer-cell reads.
- Reading the initial table base.

It has not yet processed a workspace symbol for table construction or written a decoding record. No mapped lookup element is read on this root-only rejection path.

Each proposed subsidiary table is added to the total before the same threshold check. A total of exactly 1,456 fails.

On subsidiary-related failure, earlier table writes remain. The newly proposed subsidiary link is not installed after the failing check. Both output references remain uncommitted, assuming nonaliasing storage.

Other modes have no corresponding footprint restriction.

### Invalid filling and success

After the final symbol, any remaining code-space positions are filled with invalid records: operation `0x40`, value zero, and a consumed-bit count appropriate to the active table level.

If filling leaves the active subsidiary prefix for an unserved root prefix, it returns to the root table. Each invalid record receives the operation/consumed-bit halfword before the zero value halfword.

For ordinary accepted input, the incomplete case is a single length-one symbol in a nonzero mode. Its root contains one symbol record and one invalid record.

On nonempty success, the function:

1. Reads the cursor reference and advances it by four times the total record count.
2. Writes the selected root width.
3. Returns zero.

Unlike the empty path, nonempty construction leaves cursor advancement until completion.

## Side effects

Established external effects are reads from supplied lengths, reference cells, workspace, selected global pointer cells, and any required lookup elements; writes to workspace and table storage; and successful updates to both output references.

Construction is not transactional. A late footprint failure can leave sorted workspace and partially written table storage despite unchanged output references. No rollback is visible.

The supplied body contains no external function call, allocation, release, I/O operation, or global pointer-cell write.

These observations do not establish who owns any supplied storage, how it was obtained, whether ownership changes under an external convention, or how long it remains valid outside the invocation. Those arrangements are **documented_only**. The accesses require storage to remain accessible when used.

Concurrent mutation is not made safe by visible synchronization. In particular, separate global reads can capture different lookup bases, and repeated reference reads can observe different addresses.

## Acceptance examples

These are conditional static deductions, not executed tests. They assume valid, adequately sized, nonoverlapping storage, stable inputs unless stated otherwise, and representable arithmetic.

### Empty input

With zero symbols, any mode, and any requested width:

- Return zero.
- Write two invalid records consuming one bit each.
- Advance the cursor twice by four bytes, each update preceding its corresponding record writes.
- Set root width to 1.
- Leave workspace untouched.
- Read neither mode-dependent pointer cell.

The same applies to all-zero lengths without relevant counter wrap.

### Complete one-bit alphabet

With mode zero and lengths `[1, 1]`:

- Select width 1.
- Write workspace indices 0 and 1.
- Produce two direct records consuming one bit each.
- Advance the cursor by eight bytes and return zero.
- Read neither global pointer cell.

### Oversubscription

With three length-one symbols, every mode returns `0xffffffff` before workspace or table writes and before mode-dependent pointer reads. Both output references remain unchanged.

### Incomplete singleton

With a single symbol at index zero of length 1:

- Mode zero rejects without output writes.
- Mode one reads its selected pointer cell twice and succeeds with a direct symbol record and an invalid record.
- Other modes read their selected cell twice and require mapped operation and value elements for symbol zero.

Mode one performs its two pointer-cell reads even though this example needs no mapped element.

A single symbol of length 2 is rejected in every mode.

### Subsidiary table

With mode zero, lengths `[1, 2, 2]`, and requested width 1:

- Select root width 1.
- Build a two-record root followed by a two-record subsidiary.
- Root index 0 identifies symbol 0.
- Root index 1 links to record offset 2.
- Subsidiary indices 0 and 1 identify symbols 1 and 2, each consuming one additional bit.
- Advance the cursor by sixteen bytes and return zero.

### Root-only footprint failure

With mode one, 2,048 symbols all of length 11, and requested width 11:

- Accept the complete code space and populate workspace.
- Read the selected pointer cell twice and read the initial table base.
- Return `0x00000001` because the root requires 2,048 records.
- Write no decoding records and leave both output references unchanged.
- Read no mapped lookup elements.

### Distinct pointer-read results

If the mode-one pointer-cell reads yield addresses \(A\) and then \(B\), the value origin is \(A\), and the operation origin is \(B+62\) bytes.

For other nonzero modes, the adjustment is 64 bytes. This establishes the separate-read dependency, not supported concurrent-mutation semantics.
