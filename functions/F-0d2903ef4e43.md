# F-0d2903ef4e43

## Purpose

F-0d2903ef4e43 scans integer-indexed positions on both sides of an anchor, counts positions that qualify under a mutable selection mode, and conditionally copies their associated 32-bit values into indexed destination records. Copying is restricted to an inclusive interval; counting qualifying positions is not.

The backward scan includes the anchor. The forward scan begins immediately after it. Each direction has a separate requested count and reports a boundary through a caller-provided output address.

For a nonzero interval extent, the function invokes F-3878194a6aa9 after both boundary outputs have been written. A zero extent suppresses scanning, output writes, and that final call, but does not suppress the initial state reads.

This is a source-derived behavioral contract. No runtime tests have been performed. Names such as “selection,” “record,” and “boundary” describe observed roles, not independently established application semantics.

## Interface

The function has no explicit return value and accepts eight arguments:

| Argument | Role |
|---|---|
| State address | Base address of the state fields and embedded dependency contexts described below. |
| Anchor | Initial integer position for the backward scan; the forward scan starts at anchor plus one. |
| Backward count | Number of qualifying positions to consume while moving toward decreasing positions. |
| Forward count | Number of qualifying positions to consume while moving toward increasing positions. |
| Interval start | Inclusive lower bound for positions eligible for copying. |
| Interval extent | Used to compute the inclusive upper bound; zero also disables almost all work. |
| Backward-output address | Receives the backward boundary when the extent is nonzero. |
| Forward-output address | Receives the forward boundary when the extent is nonzero. |

The supplied representation uses 32-bit integer values and four-byte value transfers. Counts, position comparisons, and the test for a positive remaining count use signed integer interpretation. Exact behavior when arithmetic exceeds the signed 32-bit range is not established here.

The state address exposes these relevant byte offsets:

| Offset | Observed use |
|---|---|
| `+0x2b4` | A 32-bit integer participating in the destination-index baseline. |
| `+0x2cc` | A second 32-bit integer, subtracted from the first. |
| `+0x2d8` | Address of a context passed to F-a08df428c8af. |
| `+0x2f0` | One-byte mode flag: zero enables qualification calls; nonzero bypasses them. |
| `+0x2f4` | Address of a context passed to F-56a66efac853. |

F-a08df428c8af supplies an address used as a destination record. Within that record, this function accesses:

- Offset `+0`: a four-byte value, overwritten with the result of a value-retrieval dispatch.
- Offset `+8`: a single byte, set to zero before that dispatch.

No record stride, total record size, allocation policy, or meaning of the other bytes is established.

A returned object from F-56a66efac853 is used for indirect dispatch through a table referenced by its first word. This function uses table byte offsets `+0x18` and `+0x0c`. The supplied evidence does not assign independent opaque function IDs to those indirect targets.

### Preconditions

For a normally returning execution:

- The initial two state fields must be readable, even when the interval extent is zero.
- Every subsequently reached field access, output write, dependency-context access, and destination-record write must address valid memory.
- F-56a66efac853 must return an object supporting the reached indirect dispatch.
- F-a08df428c8af must return a record address permitting the reached writes.
- Each requested positive scan count must eventually encounter enough qualifying positions for termination.
- Position, interval-bound, and destination-index arithmetic must remain in a range with established execution semantics.

These are execution requirements, not validations performed by this function. No null checks, record-bound checks, or failure-status checks are visible.

## Behavior

### Entry and extent gate

Before checking the interval extent, the function reads the two 32-bit baseline fields and obtains their difference:

**initial destination index = field at `+0x2b4` − field at `+0x2cc`.**

Both reads precede the extent decision. Their relative machine-level ordering is not established by the supplied representation.

If the interval extent is zero, the function returns without:

- Reading the mode flag for a scan.
- Calling any listed dependency.
- Writing either output.
- Writing any destination record.

If the extent is nonzero, the inclusive interval upper bound is calculated as:

**interval start + interval extent − 1.**

The implementation does not reject negative extents or normalize a reversed interval. Subject to arithmetic remaining defined, a negative extent produces an upper bound below the start and therefore admits no positions for copying. Scanning and finalization still proceed.

### Qualification rule

Each candidate position has its mode byte checked when that candidate is visited.

- If the byte is nonzero, the candidate qualifies without a qualification dispatch.
- If the byte is zero, F-56a66efac853 is called with the context address at state offset `+0x2f4`. The returned object's table entry at byte offset `+0x18` is invoked with that object and the candidate position.
- Any nonzero result qualifies. Zero rejects the candidate.

The mode is not captured once for the whole operation. Later candidates can observe changes made by dependency calls or other permitted state changes.

A rejected candidate changes only scan progression within this function: it does not consume the requested count, advance the destination index, or trigger a destination-record copy.

### Backward scan

The backward scan begins at the anchor with the initial destination index.

While the remaining backward count is positive, it visits the current candidate:

1. Qualification is determined using the rule above.
2. A qualifying candidate inside the inclusive copy interval triggers the record update described below.
3. Every qualifying candidate, whether inside or outside the interval, consumes one backward count and decreases the destination index by one.
4. The candidate position decreases by one after every completed visit, including rejected visits.

Consequently, destination indices track qualifying positions rather than all examined positions or only copied positions.

When the backward scan ends, the function writes the current candidate position plus one to the backward-output address.

For a positive count that completes normally, this is the last qualifying position consumed by the backward scan. When the initial backward count is zero or negative, there are no backward visits, and the reported boundary is anchor plus one.

The backward-output write precedes all forward scanning and the forward-output write.

### Forward baseline and scan

A forward count equal to zero skips baseline recomputation and forward scanning.

A forward count that is nonzero causes both baseline fields to be read again, producing:

**forward destination index = current field at `+0x2b4` − current field at `+0x2cc` + 1.**

This recomputation occurs even for a negative forward count, although such a count causes no forward candidate visits. It occurs after the backward-output write and can therefore observe changes caused by earlier dependency calls or by aliasing of that output with state.

For a positive forward count, scanning begins at anchor plus one. Each visited candidate follows the same qualification and interval rules as the backward scan, except that:

- Candidate positions increase.
- Each qualifying candidate increases the destination index by one.
- Each qualifying candidate consumes one forward count.

Rejected candidates advance the position without consuming a count or destination index.

The forward-output value is the last visited position when a positive forward scan completes. Because completion requires consuming a qualifying position, this is also its final qualifying position.

If the forward count is zero or negative, the forward-output value is the original anchor. No forward candidate is visited.

### Record update

A record update occurs only when a candidate both qualifies and lies between the interval start and computed upper bound, inclusive.

For each such candidate, the observable sequence is:

1. Call F-a08df428c8af with the context address at state offset `+0x2d8` and the current destination index.
2. Write zero to the byte at offset `+8` of the returned record.
3. Call F-56a66efac853 with the context address at state offset `+0x2f4`.
4. Invoke the returned object's table entry at byte offset `+0x0c`, passing that object and the candidate position.
5. Write the resulting four-byte value to record offset `+0`.

For a candidate that needed a qualification dispatch, the object used for value retrieval is obtained through a separate F-56a66efac853 call. Object identity or consistency across the two calls is not guaranteed.

The record address obtained in step 1 remains the address used in step 5. There is no visible reacquisition after the value-retrieval call. Correct execution therefore requires that address to remain writable through the intervening calls.

The byte at offset `+8` is cleared before value retrieval, not after it. An indirect call that can access the record may observe or alter that byte. This function performs no later write to that byte for the same update.

### Completion

After the forward phase, the function writes the forward-output value.

It then calls F-3878194a6aa9 with:

- The state address.
- The original interval start.
- The original interval extent.

That call occurs whenever the extent is nonzero and execution reaches completion, including when both counts are nonpositive or no candidate lies in the copy interval.

## Side effects

Direct writes are limited to:

- The two caller-provided output locations.
- Record offset `+8`, one byte per copy operation.
- Record offset `+0`, four bytes per copy operation.

The function does not visibly allocate or release memory. It does not establish ownership transfer for any argument, returned object, or destination record. Allocation, retention, invalidation, or release performed inside dependencies remains unknown.

Aliasing is not prevented:

- If both output addresses identify the same storage, the forward-output write occurs last and replaces the backward-output value before finalization.
- If an output aliases state, its write can affect later state reads or dependency behavior.
- If returned records overlap, later writes may replace earlier updates.
- Finalization may further alter outputs or records if it can access them.

Dependencies may mutate globals or reachable state. Their absence of side effects must not be assumed. In particular, repeated mode reads, repeated baseline reads, and repeated object acquisition are behaviorally significant.

There is no visible rollback. A dependency failure or invalid memory access can occur after earlier record or output writes have already happened. The representation provides no explicit error result or recovery path.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Unless stated otherwise, assume valid nonoverlapping memory, stable dependencies, no arithmetic overflow, and a constant baseline difference of 10.

### Zero extent

With extent zero and either output initially containing a sentinel:

- The initial baseline fields are read.
- Both sentinels remain unchanged by this function.
- No dependency is called.

This differs from a nonzero extent with zero counts.

### All candidates qualify

Use anchor 20, backward count 3, forward count 2, interval start 18, extent 5, and a nonzero mode byte.

Expected copy operations, in order:

| Candidate | Destination index |
|---|---:|
| 20 | 10 |
| 19 | 9 |
| 18 | 8 |
| 21 | 11 |
| 22 | 12 |

The backward output receives 18; the forward output receives 22. No qualification dispatch occurs. Each copy still performs object acquisition and value retrieval. Finalization receives interval start 18 and extent 5.

### Rejected candidates do not consume counts

Use anchor 10, backward count 2, forward count 2, interval `[8, 13]`, and a zero mode byte. Suppose qualification results are:

- Backward: 10 qualifies, 9 rejects, 8 qualifies.
- Forward: 11 rejects, 12 qualifies, 13 qualifies.

Expected copies are 10 at destination 10, 8 at destination 9, 12 at destination 11, and 13 at destination 12.

The outputs are 8 and 13. Candidates 9 and 11 cause qualification calls but no record-access or value-retrieval calls.

### Qualified positions outside the interval still count

Use anchor 10, backward count 2, forward count zero, interval start 9, extent 1, and a nonzero mode byte.

Candidate 10 qualifies and consumes destination index 10 without copying. Candidate 9 qualifies and copies to destination index 9.

The outputs are 9 and 10, respectively. Finalization still occurs.

### Nonpositive counts

With nonzero extent, anchor 7, backward count −2, and forward count −1:

- Neither scan visits a candidate.
- The backward output receives 8.
- The baseline fields are reread because the forward count is nonzero.
- The forward output receives 7.
- Finalization occurs.

If the forward count were zero instead, the baseline reread would not occur.

### Changed baseline between scans

Suppose the initial difference is 10, but a backward-phase dependency changes it to 30. With a positive forward count, the first qualifying forward candidate uses destination index 31, provided no later relevant mutation intervenes before the reread.

The forward baseline is not derived from the destination index left by the backward scan.

## Uncertainties

The following remain **documented_only**:

- Overflow and underflow semantics for interval bounds, position movement, and destination-index arithmetic.
- Valid position and destination-index ranges.
- Whether qualification eventually succeeds often enough for termination.
- Meaning and valid values of copied four-byte data.
- Meaning of the cleared record byte.
- Allocation, ownership, lifetime, and stability guarantees of dependency results.
- Effects of all dependency calls on global or reachable state.
- Failure, exception, or nonlocal-exit behavior of indirect calls.
- Whether aliasing or concurrent mutation is supported by the surrounding system.
- Application meaning of the two baseline fields and finalization operation.

Interpreting the destination structure as a cache, or finalization as a refresh or notification, would be inferred intent rather than established behavior.
