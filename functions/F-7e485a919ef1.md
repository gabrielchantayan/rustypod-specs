# F-7e485a919ef1

## Purpose

F-7e485a919ef1 performs a local pointer-link transformation consistent with a right rotation in a parent-linked binary tree.

The operation promotes the node referenced by a selected node’s left link. It reconnects the promoted node to the selected node’s former parent, moves the promoted node’s right subtree into the selected node’s left position, and makes the selected node the promoted node’s right child.

That interpretation is inferred from the link arrangement. The established behavior is a specific ordered sequence of 32-bit reads and writes. The function does not compare keys, inspect payloads, maintain balancing metadata, allocate memory, or release memory.

## Interface

### Inputs and result

The function takes two address-bearing inputs:

- **Context**: identifies an object containing a reference at byte offset 16 to another object that contains a distinguished node-reference slot at byte offset 4.
- **Pivot**: identifies the node whose left-linked node is to be promoted.

The function has no explicit return value. Its result is expressed through modifications to referenced memory.

The available representation uses 32-bit integer values for address-bearing inputs and 32-bit memory accesses for all observed fields. A compatible implementation must preserve those field widths. The evidence does not establish a portable native-pointer interface or behavior for addresses outside the represented address domain.

### Preconditions for the tree-rotation interpretation

For the intended structural result:

- The context and pivot must identify accessible objects with the relevant fields.
- The pivot’s left link must identify a valid, nonzero node. This node is the **promoted node**.
- The context’s root-holder reference must identify an accessible object.
- If the promoted node’s right link is nonzero, it must identify a node with a writable parent field. This node is the **transferred subtree root**.
- If the distinguished root slot does not identify the pivot, the pivot’s parent reference must identify a node with accessible child fields.
- In that non-root case, the parent must reference the pivot through the expected child relationship.
- The link fields must not overlap in a way that makes earlier writes unexpectedly change later reads.
- The relevant fields must remain stable except for this operation’s own writes.

## Behavior

### Ordered observable accesses

The order below is established by the supplied representation. Several fields are read more than once; they must not be treated as one cached observation when describing behavior under overlapping storage or external modification.

1. **Select the promoted node.**  
   Read the pivot’s left-child field at offset 8. Retain that 32-bit value as the promoted-node reference.

2. **Replace the pivot’s left link.**  
   Read the promoted node’s right-child field at offset 12. Write that value into the pivot’s left-child field.

3. **Conditionally repair the transferred subtree’s parent link.**  
   Read the promoted node’s right-child field again and test whether it is zero.

   - If it is zero, perform no transferred-subtree parent write.
   - If it is nonzero, read that same right-child field once more to obtain the destination reference, then write the pivot reference into the destination node’s parent field at offset 4.

   Thus, the value copied into the pivot’s left link, the value tested for zero, and the value used to locate the parent-field write come from separate reads.

4. **Assign the promoted node’s prospective parent.**  
   Read the pivot’s parent field at offset 4. Write that value into the promoted node’s parent field.

5. **Locate and inspect the distinguished root slot.**  
   Read the context field at offset 16. Use the resulting reference to locate the root-holder field at offset 4. Read that field and compare its 32-bit value with the pivot reference.

6. **Reconnect the promoted node above the pivot.**

   - **Root path:** If the distinguished root slot equals the pivot reference, write the promoted-node reference into that same slot. Do not inspect the former parent’s child fields.
   - **Non-root path:** Otherwise, read the pivot’s parent field again. From that parent, read the right-child field at offset 12.
     - If the right-child field equals the pivot reference, replace that right-child field with the promoted-node reference.
     - Otherwise, replace the parent’s left-child field at offset 8 with the promoted-node reference.

   The fallback branch does not verify that the parent’s left-child field actually references the pivot.

7. **Attach the pivot beneath the promoted node.**  
   Write the pivot reference into the promoted node’s right-child field.

8. **Finish the pivot’s parent link.**  
   Write the promoted-node reference into the pivot’s parent field.

The function then returns without a result value.

### Result for a stable, well-formed local tree

Let:

- **P** be the pivot;
- **L** be P’s original left child, the promoted node;
- **T** be L’s original right child, possibly zero;
- **A** be P’s original parent.

Under the stated structural and stability preconditions, completion establishes:

| Relationship | Final value |
|---|---|
| P’s left child | T |
| T’s parent, when T is nonzero | P |
| L’s parent | A |
| L’s right child | P |
| P’s parent | L |

Additionally:

- If the distinguished root slot originally identified P when tested, it is updated to L.
- Otherwise, the selected child link of A is updated to L: the right link if it equals P, and the left link otherwise.

The pivot’s right-child field and the promoted node’s left-child field are not directly written. Payloads and other metadata are not directly accessed.

When the relevant node fields are distinct, this is the usual local shape change of a right rotation. If the surrounding structure is an ordered binary tree, preservation of its ordering depends on the original subtree relationships. The function does not establish or check ordering.

### Root handling

The root decision is made by comparing the distinguished slot with the pivot reference. It is not made by checking whether the pivot’s parent reference is zero.

Consequently:

- A pivot with a nonzero parent reference can still take the root path if the distinguished slot identifies it.
- The promoted node receives the pivot’s parent value even on the root path.
- A pivot with a zero parent reference does not automatically take the root path. If the distinguished slot does not identify it, the function proceeds to use the parent reference in the non-root path.

No special root-parent convention is established. A null parent, sentinel parent, or another convention would have to be supplied by the surrounding system.

## Side effects

### Writes

On the ordinary distinct-object path, the operation performs:

- One write to the pivot’s left link.
- One optional write to the transferred subtree root’s parent link.
- One write to the promoted node’s parent link.
- One write to either the distinguished root slot or a former parent’s child link.
- One write to the promoted node’s right link.
- One write to the pivot’s parent link.

This is five 32-bit writes when the transferred subtree is absent and six when it is present.

The count does not imply that all destination locations are distinct under malformed or overlapping inputs.
