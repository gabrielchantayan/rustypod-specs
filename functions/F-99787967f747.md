# F-99787967f747

## Purpose

F-99787967f747 conditionally updates an associated handle using a request and records obtained through an object’s virtual interface.

The established selection behavior is:

- A particular object-state value suppresses all request processing.
- Otherwise, a nonzero request field enables an initial candidate comparison.
- If that comparison does not succeed, or the request field was zero, the function examines the request through a separate predicate.
- A nonzero predicate result selects the 32-bit value `0xFFFFFFFF`.
- A zero predicate result causes an ordered search of object-provided records. The first record whose comparison returns exactly zero selects its zero-based position.
- Exhausting the search does not invoke the final update dependency.

The apparent intent is to reconcile a requested value with an object’s available entries, with a special “no selection” value. That interpretation is inferred. The meanings of the request, records, associated handle, and sentinel are not established by the supplied source.

## Behavior

### 1. Outer setup and state gate

The first operation is F-f3d840047ba4 on an eight-byte local storage region.

After that call returns, the function examines the low eight bits of the object field at offset `0x44`.

- If they equal `2`, request processing is skipped. F-036034b4c0cc is invoked on the outer local storage, and the function returns.
- Otherwise, the function separately examines the same field for equality with `1`.
- If that second examination yields `1`, F-0f9731535d65 is invoked on the outer local storage before processing continues.
- Any other value continues without that additional call.

The two state tests are distinct evaluations in the supplied representation. They should not be specified as a guaranteed single snapshot.

No signedness interpretation of other eight-bit values changes the two equality cases.

### 2. Processing setup

For every path not suppressed by state `2`, the function:

1. Reads the associated handle at object offset `0x40`.
2. Passes that value to F-e2a44a932446.
3. Invokes F-b02b795a8319 on local record storage.
4. Reads the 32-bit request field at offset `0x0C`.

The associated handle passed to this setup call is not cached for the later update. A later update uses another read of object offset `0x40`.

The local record storage has a leading four-byte region, followed by an eight-byte field region and a four-byte scalar region. The source shows initialization and eventual teardown at the leading region, but does not establish the semantic record type.

### 3. Optional initial candidate

If the request field at offset `0x0C` is nonzero, the function attempts an initial comparison before testing the request predicate or searching.

It invokes the virtual entry at table offset `0x238` with local result storage and the object argument. Unlike search iterations, this call has **no explicit position argument** in the supplied call representation.

The returned local record occupies a representation containing a leading four-byte region, an adjacent eight-byte field region, and an adjacent four-byte scalar region. The function then performs these operations in order:

1. Invokes F-46f0b3cb316e with the persistent record’s eight-byte field region as destination and the returned record’s corresponding field region as source.
2. Copies the returned record’s 32-bit scalar into the persistent record’s scalar region.
3. Invokes F-ee5919ca4be6 on the returned record’s leading region.
4. Invokes F-b9acea4b06ad to prepare an eight-byte temporary from the persistent record’s field region.
5. Invokes F-44362605ab79 on that temporary, obtaining a 32-bit opaque result.
6. Invokes F-b9acea4b06ad to prepare a second eight-byte temporary from request offset `0x04`.
7. Invokes F-4a902fecdea3 with the request-derived temporary and the opaque result.
8. Invokes F-289ec4311c64 on the request-derived temporary.
9. Invokes F-289ec4311c64 on the record-derived temporary.

Only a comparison result of exactly zero is accepted. A result of `1` or any unsigned 32-bit result greater than `1` is rejected. Although the source expresses this using subtraction and a range test, it does not accept “any nonzero” or “any nonpositive” result.

If accepted:

- The request field at offset `0x0C` is read again.
- The associated handle at object offset `0x40` is read again.
- F-3ada95d6312c is invoked with that handle and the reread request value.
- Processing proceeds to teardown without invoking the request predicate or record count.

Consequently, the value submitted to the update dependency is not necessarily the original nonzero request value. The function does not enforce stability across intervening calls.

If rejected, processing continues with the fallback path below.

### 4. Request predicate

This stage is reached when the request field was initially zero or when the initial candidate was rejected.

The function:

1. Invokes F-b9acea4b06ad to prepare an eight-byte temporary from request offset `0x04`.
2. Invokes F-6d70e45e29c9 on that temporary.
3. Invokes F-289ec4311c64 on that temporary.
4. Tests the saved predicate result for zero.

Any nonzero predicate result takes the sentinel path:

- The associated handle is reread from object offset `0x40`.
- F-3ada95d6312c is invoked with that handle and the 32-bit bit pattern `0xFFFFFFFF`.

The record-count virtual entry is not invoked on this path.

A zero predicate result starts the ordered search.

### 5. Ordered search

The function calls the virtual entry at table offset `0x12C` with the object argument. Its result is treated as an unsigned 32-bit count and retained as the loop bound.

The function examines positions in ascending order, starting at zero and stopping before the retained count.

For each position:

1. The virtual entry at offset `0x238` is invoked with local result storage, the object argument, and the current unsigned 32-bit position.
2. The record field transfer, scalar copy, returned-record teardown, temporary preparation, comparison, and temporary teardown occur in the same order described for the initial candidate.
3. A comparison result of exactly zero terminates the search.
4. Any other result advances to the next position.

On the first accepted record, the associated handle is reread and F-3ada95d6312c is invoked with that handle and the accepted position.

If the count is zero, no record is requested. If every comparison fails, the function performs no update call.

The count is obtained once. The function does not refresh it after record retrievals or comparisons, even if callees change the object’s underlying collection.

The unsigned loop covers positions from zero through count minus one. Even for a count of `0xFFFFFFFF`, the last examined position is `0xFFFFFFFE`; normal loop termination does not require wrapping the position through zero.

### 6. Teardown

For every normally returning processing path:

1. F-ee5919ca4be6 is invoked on the persistent record storage.
2. F-036034b4c0cc is invoked on the outer local storage.
3. The function returns without a value.

When an update occurs, it precedes both of these teardown calls.

The state-`2` path skips persistent-record initialization and teardown and invokes only the outer teardown after the state check.

## Side effects

### Direct memory activity

The function directly:

- Reads the object’s state, associated handle, and virtual-table reference as needed.
- Reads the request’s 32-bit field.
- Supplies the address at request offset `0x04` to dependencies.
- Reads fields from returned record storage.
- Copies one 32-bit scalar between local record regions.
- Maintains local temporary objects and loop state.

No direct write to the input object or request is shown.

The eight-byte record field is transferred by F-46f0b3cb316e, not by an established raw eight-byte copy. Its aliasing, allocation, reference-counting, and ownership behavior remain unknown.

### Calls and ownership boundaries

Temporary wrappers are explicitly passed to F-289ec4311c64 after their last use. Returned records and the persistent record are passed to F-ee5919ca4be6 at the points described above.

These call pairings establish observable sequencing. They do **not** establish that the dependencies allocate, release, retain, or transfer ownership of any particular resource.

Across multiple record comparisons, the persistent record’s field destination is reused. The caller does not invoke whole-record teardown between iterations; any replacement semantics needed by that field must come from the field-transfer dependency’s contract.

No supplied evidence establishes that any dependency preserves globals, input fields, backing records, or associated handles.

### Errors and abnormal exits

There is no explicit error reporting, rollback, retry, or recovery path.

The source does not establish behavior if a dependency fails, throws, terminates, corrupts storage, or does not return. In particular, the normal teardown sequence must not be generalized into a guarantee of cleanup during abnormal unwinding.

## Acceptance examples

These are conditional contract examples, not executed tests. Each assumes valid storage and normally returning dependencies. Input stability is assumed only where stated.

1. **Suppressed processing.**  
   The first state examination yields `2`. The outer setup and teardown occur. No associated-handle setup, request access, virtual call, persistent-record initialization, or update occurs.

2. **Additional outer operation.**  
   The first state examination is not `2`, and the second yields `1`. F-0f9731535d65 occurs before F-e2a44a932446. Subsequent behavior follows the request branches normally.

3. **Accepted initial candidate.**  
   The request field is nonzero and the initial comparison returns zero. The update receives the request field’s value as reread after temporary teardown. Neither the predicate nor the count virtual call occurs.

4. **Changed request during initial comparison.**  
   The request field is initially `7`, the initial comparison succeeds, and an intervening dependency changes that field to `9`. Provided no other relevant changes occur, the update receives `9`, not `7`.

5. **Rejected initial candidate followed by sentinel.**  
   The initial comparison returns `1`, and the subsequent predicate returns a nonzero value. The update receives `0xFFFFFFFF`; no search count is requested.

6. **First matching position wins.**  
   The predicate returns zero and the retained count is four. Position zero compares unequal, position one returns comparison result zero. The update receives `1`; positions two and three are not requested.

7. **Comparison is exact-zero only.**  
   A comparison returns the bit pattern `0xFFFFFFFF`. It is rejected, not treated as a negative match result. In a search, processing advances to the next position if one remains.

8. **Empty or exhausted search.**  
   The predicate returns zero. A count of zero, or a positive count with no zero comparison result, causes normal teardown without any update call.

9. **Handle changes before update.**  
   The setup dependency receives one handle value, but a later dependency changes object offset `0x40` before selection completes. The update receives the later value read from that field.
