# F-a5ba8c521633

## Purpose

F-a5ba8c521633 processes a pair of 32-bit input values against mutable state. It conditionally invokes dependencies to select or change a processing mode, delegates mode-specific work, and records the original input pair when processing succeeds or no mode-specific processing applies.

Two recognized modes use different representations of the second input:

- Mode 1 passes the second input and associated state fields without sign transformation.
- Mode 2 passes negated representations of the second input and selected state fields, with those selected fields also exchanged in argument order.

The function returns a 64-bit result containing a status in its low 32 bits and a path-dependent value in its high 32 bits. The high half is not a uniform second status code.

Names such as “mode,” “stored pair,” and “processing” describe observed roles. The supplied evidence does not establish an application domain or a geometric interpretation.

## Interface

### Inputs

The function receives three arguments:

1. **State address:** a 32-bit address identifying an accessible mutable state object.
2. **First input:** a 32-bit unsigned value.
3. **Second input:** a 32-bit unsigned value whose bit pattern is also interpreted as a signed 32-bit integer for ordering decisions.

The state address must permit access to the fields required by the selected path. No null, extent, alignment, or lifetime checks are visible.

### State layout

|---|---:|---|
| `0x48` | 32 bits | Stored first value; passed to the processing dependency and replaced on successful completion |

### Return value

The return is a 64-bit bit pattern:

- **Low 32 bits:** `0` for successful completion or a path that requires no recognized-mode processing; `1` when an invoked dependency returns a nonzero result.
- **High 32 bits:** a path-dependent payload.

| Path reached | High 32 bits |
|---|---|
| A mode-selection or transition dependency fails before processing | Original first input |
| Mode-1 processing is invoked | Original second input |
| Mode-2 processing is invoked | 32-bit negation of the original second input |
| No recognized processing mode is present after preliminary work | Original first input |

The high half for a processing path is retained whether its processing dependency succeeds or fails. Its sign bit can be set; callers must treat it as a 32-bit payload rather than infer the sign of the complete 64-bit result.

## Behavior

### 1. Initial mode and signed comparison

The function first reads the mode byte at offset `0x68`. Its initial mode controls which preliminary actions, if any, occur.

All comparisons between the second input and the stored second value use **signed 32-bit ordering**. Thus, an input bit pattern of `0xFFFFFFFF` compares as `−1`, not as a large positive unsigned value.

The preliminary decision is:

| Initial mode | Signed relation of second input to stored second value | Preliminary actions |
|---|---|---|
| `0` | Greater | Invoke F-dbf79ec942b4 with selector `1` |
| `0` | Less | Invoke F-dbf79ec942b4 with selector `2` |
| `0` | Equal | None |
| `1` | Less | Invoke F-ecde43d0a2b1; if successful, invoke F-dbf79ec942b4 with selector `2` |
| `1` | Equal or greater | None |
| `2` | Greater | Invoke F-ecde43d0a2b1; if successful, invoke F-dbf79ec942b4 with selector `1` |
| `2` | Equal or less | None |
| Any other byte value | Any | None |

Both preliminary dependencies receive the state address. F-dbf79ec942b4 additionally receives the indicated 32-bit selector.

For either preliminary dependency:

- Zero permits continuation.
- Any nonzero result terminates this function immediately.
- The terminating result has low half `1` and high half equal to the original first input.
- This function does not perform its final stored-pair writes on that failure path.

If F-ecde43d0a2b1 succeeds on a path requiring a subsequent selector call, that selector is determined by the already-selected branch. The comparison is not repeated after the dependency returns, even if it changed the stored second value.

Dependency-side modifications are not rolled back.

### 2. Mode is read again after preliminary work

Processing dispatch uses the state’s mode byte after the preliminary actions, not merely the initial mode snapshot.

Consequently:

- A successful selector call is not itself proof that a particular mode is active.
- A dependency can affect the subsequent dispatch by modifying the mode byte.
- Values consumed by processing are read from state after the preliminary calls.

If the resulting mode is neither `1` nor `2`, no processing dependency is invoked. The function proceeds to the successful stored-pair update and returns with the original first input in the high half.

An unrecognized mode is therefore not, by itself, an error.

### 3. Mode-1 processing

When the processing mode is `1`, the function invokes F-06e4777924ae with these seven positional arguments:

1. State address.
2. Current 32-bit value at offset `0x48`.
3. Current 32-bit value at offset `0x4C`.
4. Original first input.
5. Original second input.
6. Current 32-bit value at offset `0x50`.
7. Current 32-bit value at offset `0x54`.

The high-half return payload for this path becomes the original second input.

A nonzero dependency result returns status `1` without this function’s final stored-pair update. A zero result proceeds to that update.

No mode-2 flag-transition correction is performed on this path, even if the dependency changes the mode or flag.

### 4. Mode-2 processing

When the processing mode is `2`, the function first samples the byte at offset `0x5A`.

It then invokes F-06e4777924ae with:

1. State address.
2. Current 32-bit value at offset `0x48`.
3. Negation of the current 32-bit value at offset `0x4C`.
4. Original first input.
5. Negation of the original second input.
6. Negation of the current 32-bit value at offset `0x54`.
7. Negation of the current 32-bit value at offset `0x50`.

The final two state-derived arguments are both **negated and exchanged** relative to mode 1.

The high-half return payload becomes the 32-bit negation of the original second input.

After the processing dependency returns, the function checks for this flag transition:

- The sampled flag was nonzero.
- The current flag at offset `0x5A` is zero.

If both conditions hold, the function:

- Reads the current secondary-object address from offset `0x5C`.
- Reads the 32-bit field at secondary offset `0x14`.
- Replaces that field with its negated value.

This correction occurs **before** the function acts on the processing dependency’s success or failure result. It can therefore occur even when the function subsequently returns status `1`.

The secondary address used is obtained after the dependency returns. The evidence does not support substituting a pre-call pointer snapshot.

If the initial sampled flag is zero, the correction is skipped regardless of its later value. If the sampled flag is nonzero but remains nonzero, the correction is also skipped. The condition is not limited to an initial flag value of exactly `1`.

### 5. Successful stored-pair update

When preliminary actions and any processing call have succeeded—or when no recognized processing mode applies—the function writes:

1. Original first input to offset `0x48`.
2. Original second input to offset `0x4C`.

These are the original inputs, not the transformed processing arguments and not values subsequently found in state.

The writes occur in that order. The function then returns status `0` with the path-dependent high-half payload.

### Arithmetic boundaries

For a 32-bit negation interpreted by its resulting bit pattern:
