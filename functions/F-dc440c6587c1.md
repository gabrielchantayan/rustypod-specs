# F-dc440c6587c1

## Purpose

F-dc440c6587c1 conditionally records a buffer in a four-slot state object and submits that buffer in batches of at most ten 12-byte records. Before submitting a batch, it writes the byte value `0xFD` at offset 4 within every record in that batch.

An external query and a byte in an external table control whether processing is enabled. When disabled, the function returns `-1` without accessing the supplied state object or record buffer through its own visible operations.

When enabled, the function waits for the next slot to appear empty, invokes an entry dependency, advances the current-slot field, records the original buffer address and record count, and submits successive batches. Processing stops at the first nonzero submission result. A final dependency is invoked after processing, including after an empty submission or a submission failure.

The apparent intent is a four-slot queued submission mechanism with entry and exit operations around registration and submission. Queue semantics, synchronization, and ownership transfer are inferred intent, not established contracts of the dependencies.

## Interface

The function accepts four arguments and returns a 32-bit signed integer:

| Argument | Width and interpretation |
|---|---|
| State address | A 32-bit address used as the base of a mutable state object. |
| Context value | An opaque 32-bit value passed unchanged to the wait/progress dependency and each submission call. |
| Record count | An unsigned 32-bit count of 12-byte records. |
| Buffer address | A 32-bit address identifying the first record. Its bit pattern is also stored in a selected state slot. |

These are descriptive argument names, not source identifiers.

The visible state layout is:

| Offset from state address | Size | Visible use |
|---|---:|---|
| `0x0C`, `0x10`, `0x14`, `0x18` | 4 bytes each | Four buffer-address slots. A zero value is treated as empty during the wait phase. |
| `0x1C`, `0x20`, `0x24`, `0x28` | 4 bytes each | Four associated record-count slots. |
| `0x2C` | 4 bytes | Current-slot field, read using both signed and unsigned interpretations at different points. |
| `0x34` | 4 bytes | Opaque value read immediately before each submission call. |

No other state fields are directly accessed by the visible body. Dependencies may access additional fields.

Each record has a stride of 12 bytes. Only the byte at record-relative offset 4 is directly modified. The other eleven bytes are not directly written by this function.

The external table consists of entries with a stride of 24 bytes. A single unsigned byte at entry-relative offset 19 is consulted.

For ordinary intended operation, the caller must provide:

- A valid state object with accessible fields at the offsets above.
- A current-slot value in the range zero through three whenever it is used.
- For a positive record count, a writable buffer covering the corresponding 12-byte records.
- A valid external table entry for any non-sentinel query result.
- Address calculations that remain valid in the target execution environment.

The visible function does not validate these requirements. A zero record count avoids direct buffer writes and submission calls, but does not avoid state access on the enabled path.

## Behavior

### 1. Determine whether processing is enabled

The function first calls F-36a285714182 without arguments.

Its result is interpreted as an unsigned 32-bit value:

- If it equals `0xFFFFFFFF`, processing is disabled. No table byte is read.
- Otherwise, the function reads the unsigned byte at offset 19 of the table entry selected by that result, using a 24-byte entry stride.
- A zero table byte disables processing.
- Any nonzero table byte enables processing.

When processing is disabled, the function returns `-1`. It does not directly read or write the state object or record buffer on this path. F-36a285714182 may nevertheless have side effects; none are excluded by the available evidence.

The query result is not visibly range-checked before indexing the table.

### 2. Wait for an apparently empty next slot

On the enabled path, the function repeatedly reads the current-slot field and computes a candidate next slot.

During this phase, the current-slot field and candidate are interpreted as signed 32-bit values. The candidate is one greater than the current value. If the candidate is greater than three under signed comparison, it is replaced with zero.

The function then reads the corresponding buffer-address slot:

- If the slot contains zero, the wait phase ends.
- If it contains a nonzero value, the function calls F-2d9d714aef44 with the state address and context value, then repeats the check.

The dependency’s return value is not used. The current-slot field and candidate slot are read again after each call; the function does not simply poll a previously chosen slot.

There is no visible timeout, retry bound, cancellation check, or error branch for this phase. If the candidate slot never becomes zero and the dependency continues returning normally, the function can remain in this loop indefinitely.

For a valid current-slot value, the candidate sequence is the usual next slot modulo four: zero leads to one, one to two, two to three, and three to zero. Malformed negative values do not have the same guarantee.

### 3. Invoke the entry dependency and advance the slot

After observing an empty candidate slot, the function calls F-338d16f9ce72 with the state address.

It then reads the current-slot field again. The slot inspected before this call is not retained as the destination. Consequently, changes made by F-338d16f9ce72 can affect which slot receives the new registration.

The advance operation has an observable write sequence:

1. Compute the current-slot value plus one and write that 32-bit result to offset `0x2C`.
2. Compare that result with three as an unsigned 32-bit value.
3. If it exceeds three, write zero to offset `0x2C`.

Thus a normal transition from three to zero first writes four and then writes zero. The function does not combine those writes into a single visible assignment in the supplied representation.

The wait-phase candidate calculation and this advance operation use different comparison interpretations. Their equivalence is established for valid slot values zero through three, not for arbitrary 32-bit values.

### 4. Register the original buffer and count

After advancing the slot, the function:

1. Reads the current-slot field and writes the original buffer address into that slot’s buffer-address field.
2. Reads the current-slot field again and writes the original unsigned record count into the corresponding count field.

The buffer address is stored before the count. The two destination indices are obtained through separate reads of the current-slot field. The visible body contains no dependency call between these writes, but it does not establish a concurrency model that would make the pair atomic.

The count stored here is the original count, not the size of the first batch or the number of records eventually accepted.

No further empty-slot check is performed after F-338d16f9ce72. The visible body therefore does not independently guarantee that the slot selected after that call is still empty.

### 5. Mark and submit batches

If the original count is zero, no record-marking or submission iteration occurs.

For a positive remaining count, each iteration selects a batch size equal to the smaller of the remaining count and ten.

Before calling the submission dependency, the function writes `0xFD` to byte offset 4 in each record of the selected batch. These byte writes occur in ascending record order, starting at the current buffer position. All marker writes for the batch precede its submission call.

It then reads the 32-bit field at state offset `0x34` and calls F-5a8daf08d253 with five arguments, in this order:

1. The value just read from state offset `0x34`.
2. The original context value.
3. The current batch’s buffer address.
4. The batch size, from one through ten.
5. A boolean indicating whether the remaining count is at most ten.

The final boolean is based on the count remaining before that call. It is true for the last planned batch, including a batch of exactly ten. It is false when additional records would remain after a successful current batch.

The state field at offset `0x34` is read afresh for every submission. Its value is not cached across calls.

If the submission result is nonzero:

- That result becomes the function’s eventual return value.
- No subsequent batch is marked or submitted.
- The current batch’s marker writes remain performed.
- The visible function does not undo its slot registration or previous writes.

If the submission result is zero:

- The local buffer position advances by 12 times the batch size.
- The local remaining count decreases by the batch size.
- Processing continues if records remain.

For a successful iteration, batch-size multiplication is at most 120, and the unsigned subtraction cannot underflow because the batch size never exceeds the remaining count. These bounds do not establish that the complete buffer address range is valid.

### 6. Invoke the exit dependency and return

After the batch loop, the function calls F-1333331b2da1 with the state address.

This call occurs on every enabled path that reaches this point, including:

- An original count of zero.
- Completion of every batch with zero submission results.
- Early termination after a nonzero submission result.

Its return value is not used.

The function then returns:

- `-1` when processing was disabled.
- `0` when processing was enabled and no submission returned nonzero, including the zero-count case.
- Otherwise, the exact 32-bit result of the first nonzero submission result, interpreted as the function’s signed return value.

A return value of `-1` is therefore not necessarily unique to the disabled path: the submission dependency could also return that bit pattern.

## Side effects

Direct visible side effects on an enabled path are:

- Updating the current-slot field, potentially with two successive writes.
- Storing the original buffer address and original record count in slot fields.
- Writing `0xFD` into selected record bytes before each submission attempt.
- Calling the wait/progress, entry, submission, and exit dependencies in the order described.

The function does not directly clear a registered slot, revise its stored count after a partial submission, release the buffer, or restore marker bytes. Dependencies may perform such actions, but the supplied body does not establish that they do.

Ownership is not settled by storing the address or calling the submission dependency. The evidence does not establish copying, borrowing duration, ownership transfer, retention, or release responsibility.

No atomic operations, memory-order guarantees, or explicit error recovery are visible. The apparent entry/exit pairing does not by itself prove a lock protocol.

If a dependency fails to return normally, subsequent operations, including the exit dependency, are not established to occur. There is no visible exception or fault cleanup mechanism.

## Acceptance examples

These examples are conditional on valid addresses, normal dependency returns, and no unspecified mutation except where explicitly described. They are acceptance criteria derived from static evidence, not observed test results.

### Disabled by sentinel

If F-36a285714182 returns `0xFFFFFFFF`, the function returns `-1`. It does not read the table entry byte and does not directly access the supplied state or buffer.

### Disabled by table byte

If the query returns a valid selector and the selected byte is zero, the function returns `-1` after that byte read. No wait/progress, entry, submission, or exit call follows.

### Empty submission

Suppose processing is enabled, the current slot is zero, and slot one is empty. With count zero, the function invokes the entry dependency, advances the current slot to one, stores the buffer address and zero count in slot one, and invokes the exit dependency. It performs no record-marker writes and makes no submission call. It returns zero.

### Exact ten-record batch

With ten records and an available destination slot, all ten marker bytes are written before one submission call. The batch size is ten and the final-batch boolean is true. If submission returns zero, the exit dependency follows and the function returns zero.

### Twenty-one records

With 21 records and all submissions returning zero, the attempted batch sizes are ten, ten, and one. Their final-batch booleans are false, false, and true. Their buffer positions are the original address, that address plus 120 bytes, and that address plus 240 bytes.

The slot registration stores count 21, not ten or one.

### Failure in the second batch

For 25 records, suppose the first submission returns zero and the second returns a nonzero result. The function marks and submits the first ten records, then marks and submits the next ten. It does not mark or submit the final five records. It calls the exit dependency and returns the second submission’s result.

The visible body does not roll back the original registration of 25 records.

### Occupied next slot

If the current slot is three and slot zero is nonzero, the function calls F-2d9d714aef44. If that dependency clears slot zero without changing the current slot, the next check ends the wait.

After the entry dependency, assuming no state change, the current-slot field is written first as four and then as zero before registration.

### Entry dependency changes the current slot

Suppose the wait phase observes an empty slot one while the current slot is zero. If the entry dependency changes the current slot to two, registration advances from two to three. The function does not insist on using the previously observed slot one.
