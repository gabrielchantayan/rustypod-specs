# F-51a9703516d3

## Purpose

F-51a9703516d3 searches a counted sequence of 32-bit values for the first value equal to a supplied target. Under ordinary, stable storage conditions, it removes that occurrence by shifting subsequent values one position toward the beginning, decreases the logical count by one, and returns the removed value.

A return value of zero is ambiguous. It can mean that no matching value was found, that a later removal check rejected the operation, or that the removed value itself was zero. There is no separate status output.

This purpose describes the ordinary effect of the supplied static representation. It does not establish that the storage is a particular container type, that values are pointers, or that removal transfers ownership of any resource.

## Interface

### Inputs

The function receives two arguments:

1. **Descriptor address.** An address identifying a two-field descriptor:
   - At byte offset 0: a signed 32-bit logical element count.
   - At byte offset 4: a 32-bit address representation locating the backing sequence.

2. **Target value.** A 32-bit value to compare with sequence elements.

The represented interface uses a 32-bit layout. The descriptor’s second field is interpreted as an address, not as an inline element or an offset relative to the descriptor. The evidence does not establish how this representation would be adapted to an environment with wider pointers.

### Backing sequence layout

Elements occupy consecutive four-byte slots. The element at logical index zero begins at the backing address; each following element begins four bytes later.

The descriptor contains no visible capacity field. This function neither checks an allocation size nor changes capacity.

The search compares each loaded 32-bit element with the target for equality. Equality does not depend on interpreting the element as a positive or negative integer. The count and index comparisons, however, are signed in the supplied representation.

### Output

The function returns one 32-bit value:

- Zero when search ends without finding a match.
- Zero when the post-search removal checks do not permit removal.
- The value reread from the selected slot when removal proceeds.

The return is an opaque 32-bit result. No ownership transfer, reference-count effect, or interpretation as an address is established.

### Preconditions for ordinary removal semantics

The ordinary behavior described below requires:

- A readable descriptor address from function entry onward.
- A backing address readable for every element actually inspected.
- Writable descriptor count storage if removal proceeds.
- Readable and writable backing storage for every slot participating in a shift.
- Address and index arithmetic that validly identify the intended four-byte slots.
- Stable descriptor and sequence contents during the operation, apart from the function’s own writes.
- No overlap between descriptor fields and shifted sequence storage if conventional container behavior is required.

These conditions are not comprehensively checked. In particular, a null descriptor is not a supported empty-sequence representation: the function accesses the count before reaching its later null checks.

## Behavior

### Search

The search begins at index zero and proceeds in increasing index order.

Before examining each candidate, the function reads the descriptor’s current count. If the signed count is less than or equal to the current index, it immediately returns zero.

Consequences include:

- A zero count returns zero without accessing the backing-address field or any element.
- A negative count also returns zero without accessing the backing-address field or any element.
- Under stable conditions, a positive count permits inspection of indices zero through count minus one.
- The search count is not a single entry-time snapshot. A new count read controls each candidate inspection.

For each permitted index, the function reads the backing-address field and loads the corresponding four-byte element. It compares that element with the target.

A mismatch advances the index by one and repeats the count check. A match ends the search immediately. Later equal values are not considered.

The search performs no explicit writes.

### Post-search checks

After finding a match, the function checks whether the descriptor address is non-null and, if so, reads the count again. This count becomes the fixed bound used by the removal checks and shift loop.

The removal checks require:

- A non-null descriptor.
- A nonzero newly read count.
- A nonnegative selected index.
- A selected index strictly below the newly read count.

Although the represented checks include a less-than-or-equal comparison, a separate equality rejection excludes an index equal to the count. The resulting accepted range is therefore from zero through the newly read count minus one.

If these checks reject removal, the function returns zero. It has not yet written either the descriptor or the sequence.

Under stable, ordinary inputs, a match found by the search already satisfies these checks. Their distinct effect matters when the count changes between search and removal, or when considering behavior outside the ordinary arithmetic assumptions. They do not make the initial descriptor access safe for a null argument.

### Capturing the return value

Once removal is accepted, the function reads the backing-address field again and rereads the selected slot. It retains this second element value for return.

The value used for the successful search comparison is not retained as the return value. With stable storage, the two values are equal. If the selected slot or backing address changes between these accesses, the returned value need not equal the target.

This saved return value is captured before any shifting writes.

### Shifting

If the selected index is the final index according to the removal-time count snapshot, no element movement occurs.

Otherwise, the function processes destination indices in increasing order, beginning at the selected index and ending at the snapshot count minus two. For each destination, it copies the four-byte value from the immediately following slot into that destination.

Thus, under stable, non-overlapping conditions:

- Elements preceding the selected index remain unchanged.
- Each later logical element moves left by one slot.
- Relative order among the remaining logical elements is preserved.
- The final physical slot is not cleared.
- No slot beyond the original logical end is accessed by this shift.

The removal-time count snapshot controls the number of copies. The function does not reread the descriptor count to determine the shift-loop bound.

The backing-address field is accessed again for the source and destination address expressions during shifting. The supplied representation does not justify assuming a single backing address cached for the entire operation. Nor does it establish a total order between the address-field reads used to form a particular copy’s source and destination. The source value must be obtained before that copy’s destination write.

### Count update and return

After shifting, or immediately after capturing the return value when no shift is necessary, the function reads the descriptor count again, subtracts one, and writes the result to the descriptor count field.

The value decremented is therefore the count present at this final read, not necessarily the earlier removal-time snapshot.

With stable, non-overlapping storage, the final count is the original positive count minus one. If the count changes through interference or storage aliasing, the final write can differ from that ordinary result.

The function then returns the previously captured 32-bit element value.

## Side effects

### Ordinary successful removal

A successful removal changes:

- The selected slot and following destination slots, when shifting is required.
- The descriptor count, reduced by one under stable conditions.

It does not explicitly change the backing-address field, allocate storage, resize an allocation, release storage, clear the vacated tail slot, or invoke element cleanup.

For a tail removal, the only explicit storage write is the count update. The removed value remains in its physical slot outside the shortened logical sequence.

For a non-tail removal, the old final element remains duplicated in the final physical slot after its value has been copied left. That slot is outside the new logical sequence.

### Unsuccessful operation

An unsuccessful search performs reads but no explicit writes.

Rejection by the post-search removal checks likewise performs no explicit writes.

### Ownership and aliasing

No ownership policy is established for either the backing allocation or values stored within it. In particular, returning an element does not prove that the caller acquires responsibility for releasing anything.

Descriptor/sequence aliasing is not rejected. If a shift destination overlaps a descriptor field, a shift can change later address calculations or the count used by the final decrement. Conventional sequence-removal semantics are not promised for such layouts.

The function provides no visible locking, atomic access protocol, or synchronization. Its repeated reads do not establish safe concurrent mutation.

### Invalid memory and partial effects

There is no explicit recovery path for invalid descriptor storage, invalid backing addresses, inaccessible element slots, or unwritable destinations.

If an execution environment faults during a shift, earlier copies may already have occurred while the count has not yet been updated. The supplied evidence establishes no rollback behavior and no specific fault-delivery mechanism.

## Acceptance examples

These examples are conditional on valid four-byte storage, representable address calculations, stable inputs, and no overlap between descriptor fields and the backing sequence unless stated otherwise. They are specification examples, not reports of executed tests.

1. **Empty sequence.**  
   Given count zero, the result is zero and the count remains zero. No backing element or backing-address-field read is required by the visible path.

2. **Negative count.**  
   Given count negative three, the initial signed count check ends the operation. The result is zero, the count remains negative three, and no backing element is inspected.

3. **Missing target.**  
   Given logical elements 7, 12, and 19, count three, and target 8, the function returns zero. All three elements and the count remain unchanged.

4. **First of duplicate matches.**  
   Given logical elements 4, 9, 4, and 6, count four, and target 4, the function returns 4. The new logical sequence is 9, 4, and 6, with count three. The final physical slot still contains 6.

5. **Middle removal.**  
   Given logical elements 10, 20, and 30, count three, and target 20, the function returns 20. The new logical sequence is 10 and 30, with count two. Physical backing contents are 10, 30, and 30.

6. **Tail removal.**  
   Given logical elements 10, 20, and 30, count three, and target 30, the function returns 30 and writes count two. No element shift occurs; the physical slot containing 30 is not cleared.

7. **Single-element removal.**  
   Given one logical element with value 25 and target 25, the function returns 25 and writes count zero. The backing slot retains 25.

8. **Successful removal of zero.**  
   Given logical elements 5, 0, and 8 and target zero, the function returns zero, writes count two, and leaves the logical sequence 5 and 8. The return alone cannot distinguish this success from a missing target.

9. **Count change before removal checks.**  
   If search selects index two but the removal-time count read yields two, removal is rejected and the function returns zero without explicit writes. This is a conditional consequence of the visible checks, not a guarantee that concurrent mutation is supported.

10. **Value change between matching and capture.**  
    If a slot matches the target during search but holds a different value when reread for removal, the saved return value is that later value. This example describes the separate reads; it does not establish a valid concurrent-access protocol.

### Inferred intent

That intent does not justify adding bounds validation, tail clearing, resource release, or a separate success indicator. None is present in the supplied evidence.
