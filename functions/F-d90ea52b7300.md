# F-d90ea52b7300

## Purpose

F-d90ea52b7300 selects an object and invokes an operation on the first candidate whose eligibility callback returns a nonzero value. It considers the supplied object first. If that object is ineligible, it follows a linked sequence, using F-682adfd5a561 to obtain a candidate from each subsequent sequence node.

The established behavior is selection and dispatch, not a defined business operation. “Eligibility,” “candidate,” and “sequence node” describe their roles in this function; they do not establish the application meaning of the objects.

The function performs no explicit allocation, deallocation, or object-field write. Its callbacks and resolver may have effects that are not established here.

## Interface

### Inputs

The recovered interface has six arguments:

| Position | Contract |
|---|---|
| 1 | An object address, used immediately for indirect callback lookup and later as the initial traversal anchor. |
| 2 | An opaque 32-bit value forwarded to the selected operation and to eligibility callbacks for resolved candidates. |
| 3 | An opaque 32-bit value forwarded in the same circumstances as argument 2. |
| 4 | An opaque 32-bit value forwarded in the same circumstances as argument 2. A copy captured before the first callback is also supplied as an additional argument to later eligibility callbacks. |
| 5 | An opaque 32-bit value supplied to eligibility callbacks for resolved candidates, but not explicitly supplied to the initial eligibility callback or selected operation. |
| 6 | An opaque 32-bit value supplied in the same circumstances as argument 5. |

The supplied representation uses 32-bit object words, pointer-sized fields, callback addresses, and callback-result storage. This is a contract for that represented layout, not a claim that the layout is portable to an arbitrary host.

Arguments 2–6 are opaque bit patterns. Their interpretation as integers, addresses, handles, flags, or other values is not established.

### Required object layout

Every object used for eligibility or operation dispatch must support:

- A 32-bit callback-table address at byte offset 0.
- An eligibility callback address at byte offset 132, hexadecimal 0x84, within that table.
- An operation callback address at byte offset 116, hexadecimal 0x74, within that table.

Every traversal anchor whose successor is examined must support:

- A 32-bit successor address at byte offset 20, hexadecimal 0x14, from the anchor’s base.

The traversal anchor and a candidate returned by F-682adfd5a561 are distinct roles. They may refer to the same object, but equality is not required by the visible behavior.

### Output

No return value is defined by the recovered interface.

There are two normal completion paths:

1. A candidate is eligible, its operation is invoked, and this function completes without examining another node.
2. A successor read produces a null address, and this function completes without invoking an operation.

There is no explicit status, selected-object result, or error code returned to the caller.

### Preconditions

For defined execution of the visible accesses:

- The initial object address must be nonnull and readable at the required fields.
- Each callback table and callback entry used must be readable and callable under the applicable ABI.
- Each nonnull traversal anchor must remain valid whenever its successor is read.
- Every nonnull candidate returned by F-682adfd5a561 must support the callback layout.
- Dependencies must return normally for execution to proceed beyond their calls.

The function does not validate these conditions.

## Behavior

### Initial eligibility check

Before invoking any dependency, the function preserves a 32-bit copy of argument 4.

It then reads the initial object’s callback-table address, obtains the entry at table offset 132, and invokes that entry with the initial object as its only explicitly shown argument.

The callback’s result is consumed as a 32-bit integer and compared with zero:

- Zero means continue searching.
- Any nonzero value means select this object.

There is no requirement that success equal one. A result whose signed interpretation is negative is still nonzero and selects the object.

The initial eligibility call differs from later eligibility calls: arguments 2–6 and the saved copy of argument 4 are not explicitly supplied to it. The visible evidence does not establish a uniform callback signature or the significance of this asymmetry.

### Dispatch when the initial object is eligible

If the initial eligibility result is nonzero, the selected object is the initial object.

After eligibility returns, the function reads that selected object’s callback-table address and obtains the operation entry at table offset 116. It invokes the operation with four explicitly shown arguments, in order:

1. Selected-object address.
2. Original argument 2.
3. Original argument 3.
4. Original argument 4.

It then completes. It does not read the initial object’s successor or invoke F-682adfd5a561 on this path.

The operation lookup occurs after the eligibility callback. If that callback changes the selected object’s table address or operation entry, dispatch uses the subsequently read state rather than an earlier cached operation address.

### Traversal after an ineligible candidate

If the initial eligibility result is zero, traversal begins with the initial object as the anchor.

For each traversal step:

- The function reads the current anchor’s successor at byte offset 20.
- That successor becomes the new traversal anchor.
- If the successor is null, the function completes.
- Otherwise, it invokes F-682adfd5a561 with the new anchor and the value 6.

A null result from F-682adfd5a561 causes the node to be skipped without an eligibility call. Traversal proceeds by reading that node’s successor.

A nonnull result becomes a candidate. The function reads the candidate’s callback table and invokes its eligibility entry at table offset 132 with seven explicitly shown arguments:

| Position | Value |
|---|---|
| 1 | Candidate address returned by F-682adfd5a561 |
| 2 | Original argument 2 |
| 3 | Original argument 3 |
| 4 | Original argument 4 |
| 5 | Original argument 5 |
| 6 | Original argument 6 |
| 7 | The 32-bit copy of argument 4 captured before the initial eligibility call |

Thus, the fourth and seventh values carry the same original argument-4 bit pattern. The purpose of this duplication is not established.

If this eligibility result is nonzero, the candidate is selected and its operation is invoked as described above: candidate address followed by original arguments 2, 3, and 4. Arguments 5 and 6, and the additional saved copy, are not explicitly forwarded to that operation.

If the eligibility result is zero, traversal resumes from the sequence node that produced the candidate—not from the candidate address. In particular, a candidate’s own successor is irrelevant unless the candidate and sequence node happen to be the same address.

### Search order and termination

The effective selection order is:

1. The initial object.
2. A nonnull resolved candidate from the initial object’s successor.
3. A nonnull resolved candidate from each later successor, in link order.

Nodes whose resolver result is null contribute no candidate.

The function stops at the first nonzero eligibility result. It invokes at most one operation per invocation.

A null successor ends the search. A null resolver result does not end it.

There is no visible cycle detection, visited-node tracking, iteration limit, or duplicate-candidate suppression. Consequently:

- A cycle can cause nontermination.
- A repeated candidate can be checked multiple times.
- A changing resolver result or changing eligibility result can affect a later visit.
- A cyclic sequence can still terminate by finding an eligible candidate.

There is no visible counter arithmetic, buffer-length arithmetic, or accumulation whose overflow requires a separate rule. The relevant offsets are fixed byte offsets; invalid address formation or inaccessible memory is not handled explicitly.

## Side effects

### Reads and their ordering

The visible ordering is:

1. Capture argument 4 by value.
2. Read the initial object’s callback information and invoke initial eligibility.
3. If eligible, read operation callback information and invoke the operation.
4. Otherwise, read the current anchor’s successor.
5. For a nonnull successor, invoke F-682adfd5a561.
6. For a nonnull resolver result, read candidate callback information and invoke eligibility.
7. Either dispatch the eligible candidate or continue from the sequence anchor.

These are control-flow and dependency-order guarantees. They do not specify machine-level atomicity, memory barriers, or synchronization with concurrent modification.

The next successor read occurs after the relevant dependencies return. Changes made by a dependency to the current sequence anchor can therefore affect subsequent traversal. The function does not visibly snapshot the linked sequence.

### Writes, ownership, and lifetime

No direct object-field or global write is visible in this function. Its local traversal state changes as the search advances.

There is no explicit allocation, retain, release, destruction, or ownership-transfer operation. That absence does not establish that dependencies preserve ownership or lifetime.

In particular, this contract does not assume that F-682adfd5a561 or either indirect callback:

- Preserves globals.
- Leaves object fields unchanged.
- Returns borrowed rather than owned storage.
- Keeps an input object alive.
- Avoids allocation or release.
- Is reentrant or thread-safe.

If a dependency invalidates an object that this function subsequently accesses, the visible implementation provides no lifetime recovery mechanism.

### Errors and abnormal execution

The function explicitly accommodates null successor addresses and null resolver results. It does not explicitly accommodate a null initial object, null callback table, null callback entry, or malformed nonnull candidate.

There is no visible exception handler, retry, rollback, diagnostic emission, or cleanup path. Dependency failures, abnormal control transfer, and inaccessible memory are outside the established normal-completion behavior.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests.

### Initial object succeeds

Given a valid initial object whose eligibility callback returns a nonzero 32-bit value:

- Its operation is invoked once with the initial object and original arguments 2–4.
- F-682adfd5a561 is not invoked.
- No successor is read by this function.
- An eligibility result such as −1 is accepted just as a result of 1 is.

### Initial object fails and the sequence ends

Given an initial eligibility result of zero and a null successor field:

- The successor field is read after eligibility returns.
- No resolver call occurs.
- No operation is invoked.
- The function completes without a defined result value.

### A resolver miss is skipped

Given an ineligible initial object, a first successor whose resolver result is null, and a second successor whose resolver returns a valid candidate:

- The resolver is called on the first successor with 6.
- No eligibility callback is invoked for the null result.
- The first successor’s link determines the next anchor.
- The second resolved candidate is then checked.

A null resolver result alone must not terminate the search.

### A resolved candidate differs from its sequence node

Given a sequence node that resolves to a different-address candidate whose eligibility result is zero:

- Eligibility is invoked on the candidate.
- The next traversal link is read from the sequence node.
- The candidate’s successor field is not used merely because it was the checked candidate.

### Later eligibility succeeds

Given a resolved candidate with nonzero eligibility:

- Its eligibility call receives the candidate, original arguments 2–6, and an additional copy of original argument 4.
- Its operation receives only the candidate and original arguments 2–4.
- No later successor or candidate is examined.

### Eligibility changes dispatch state

Given an eligibility callback that returns nonzero after replacing the candidate’s callback-table address with another valid table:

- Operation lookup uses the table read after eligibility returns.
- The operation entry from the earlier table is not required to be used.

### A cycle never produces success

Given a reachable cycle, normally returning dependencies, and no nonzero eligibility result:

- The visible behavior supplies no guaranteed termination.
- Returning merely because a node or candidate was previously visited would add behavior absent from this contract.
