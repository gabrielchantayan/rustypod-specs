# F-b09db3398a5a

## Purpose

F-b09db3398a5a searches a sequence of variable-stride records within a memory-backed object. It obtains an origin offset through F-e81ed1edd673, begins examining records 20 bytes after that origin, and returns the offset of the first record whose two decoded identifiers match the requested values.

An optional output receives the matching record’s one-based traversal ordinal, represented in 16 bits. The returned offset is relative to a captured base address, not a direct memory address.

The visible behavior is a first-match search. The interpretation of the object as a container and its entries as records is inferred intent; the actual traversal, decoding, comparison, and return rules are established by the supplied static evidence.

The “first” and “second” identifier names describe comparison order and record layout, not argument order.

The supplied representation uses 32-bit integer and address-bearing values and a 16-bit short value. Exact machine-level pointer semantics and exceptional arithmetic behavior are not independently verified.

### Outputs

- On a match, the current record offset is returned.
- Otherwise, zero is returned if the search terminates normally.
- No separate error code distinguishes an unavailable object, a zero dependency result, an exhausted search, or a successful match whose offset happens to be zero after arithmetic wraparound.

If the ordinal destination is non-null and a match occurs, the function writes exactly one 16-bit value there before returning.

The function performs no explicit write to the ordinal destination on an ordinary no-match return. This does not guarantee that the dependency or an aliased external operation leaves that storage unchanged.

## Behavior

### Four-byte decoding rule

Every decoded field consists of four bytes in increasing address order. Each byte is multiplied by 23 independently, and only the low eight bits of that byte’s product contribute to the result. The four resulting bytes are assembled in most-significant-byte-first order.

For bytes \(b_0,b_1,b_2,b_3\), the decoded 32-bit value is:

\[
D =
((23b_0)\bmod256)\,2^{24}
+
((23b_1)\bmod256)\,2^{16}
+
((23b_2)\bmod256)\,2^{8}
+
((23b_3)\bmod256).
\]

This is **not** equivalent to assembling the original four bytes into an integer and multiplying that integer by 23. Carries do not propagate between byte positions.

For example:

- Bytes 0, 0, 0, 1 decode to 23.
- Bytes 0, 0, 0, 12 decode to 20, because \(12\times23=276\), whose low byte is 20.
- Bytes 0, 0, 1, 12 decode to 5908, not 6164.

The rule specifies the value obtained from a stable four-byte field. The source does not establish the chronological order of individual byte reads within a decoding expression.

### Entry checks and dependency call

The traversal ordinal is initially zero.

The function first checks whether the object reference is null. If it is null, the function returns zero without dereferencing that reference or invoking F-e81ed1edd673.

Otherwise, it reads the cell addressed by the object reference. If that value is zero, the function returns zero without invoking the dependency.

If both checks succeed, F-e81ed1edd673 is invoked with:

1. The original object reference.
2. The opaque lookup argument.

A zero result from the dependency causes an immediate zero return.

For a nonzero dependency result, the function reads the object-reference cell again and captures that value as the base address for traversal. This second read matters: the dependency is not known to preserve the cell.

The captured base is not checked again for zero. The initial nonzero-base check therefore does not establish that the post-call base is valid.

### Origin, boundary, and first candidate

The dependency’s nonzero result is used as an origin offset.

The first candidate record offset is the origin plus 20 bytes.

At the start of every loop iteration, including the first, the function decodes the four-byte field at the captured base plus the origin. It adds that decoded value to the origin to obtain the current upper boundary.

A candidate is examined only when its unsigned 32-bit offset is strictly less than that boundary.

Consequences:

- A candidate equal to the boundary is not examined.
- The origin’s four-byte field is read again for every loop-condition evaluation.
- The decoded boundary value is not cached for the entire traversal.
- Only the candidate’s starting offset is compared with the boundary. The function does not check whether the candidate’s fields or full stride fit before that boundary.

The displayed arithmetic is 32-bit. Where candidate offsets or unsigned boundary calculations overflow, their resulting 32-bit values govern the unsigned comparison; there is no visible overflow check. The source representation also contains signed intermediate expressions, so an independent language-level guarantee for every overflowing expression is not established.

### Per-candidate processing

For each admitted candidate, the function first advances the traversal ordinal by one, retaining it in 16-bit storage.

It then decodes the four-byte field at candidate-relative offset 4 and compares it against the requested first identifier.

If that comparison fails:

- The identifier field at candidate-relative offset 8 is not evaluated.
- The candidate is treated as a non-match.

If the first identifier matches, the function decodes the field at candidate-relative offset 8 and compares it against the requested second identifier.

A match requires exact equality of both decoded 32-bit values.

The relevant memory layout is:

| Location | Size | Use |
|---|---:|---|
| Origin + 0 | 4 bytes | Decoded extent used to form the loop boundary |
| Origin + 4 through origin + 19 | 16 bytes | Not directly read as header fields by this function |
| Candidate + 0 | 4 bytes | Decoded stride, read only after a non-match |
| Candidate + 4 | 4 bytes | First identifier, compared first |
| Candidate + 8 | 4 bytes | Second identifier, read only if the first matches |
| Other candidate-relative bytes | Unspecified | No direct interpretation established |

The gap in the header is not validated or interpreted here. Later traversal may reach overlapping or otherwise unusual locations because record positions are determined solely by decoded strides.

### Successful match

On the first candidate satisfying both comparisons:

1. If the ordinal destination is non-null, the current 16-bit ordinal is written there.
2. The current candidate offset is returned immediately.

The candidate’s stride field is not needed or decoded on this successful path.

A null ordinal destination suppresses only the write. It does not suppress matching or change the returned offset.

### Advancing after a non-match

After a candidate fails either comparison, the function decodes the four-byte stride at candidate-relative offset 0.

That decoded stride is added to the current candidate offset. The resulting candidate is subjected to the next loop-condition evaluation, which rereads the origin’s extent field.

There is no check that a stride is:

- Nonzero.
- At least 12 bytes.
- Aligned.
- Confined to the stated extent.
- Consistent with a record’s physical size.

A zero stride leaves the candidate offset unchanged. With stable memory and an unchanged failing match condition, this causes repeated examination of the same candidate rather than a normal failure return.

A positive decoded stride can wrap the 32-bit candidate offset. Consequently, “positive stride” alone does not establish monotonic traversal or termination.

### Exhaustion

If a loop-condition evaluation finds that the candidate is not strictly below the boundary, the function returns zero.

The ordinal destination is not written by this function on that path, even if records were previously examined.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, assume valid readable storage, a stable captured base, non-overflowing offsets, stable field contents, and a dependency result of origin \(O\).

1. **Null object reference**

   The result is zero. The dependency is not called, and this function performs no ordinal write.

2. **Initially zero base cell**

   A valid object reference whose cell initially contains zero produces a zero result without a dependency call.

3. **Dependency declines the lookup**

   If the initial checks pass but F-e81ed1edd673 returns zero, the result is zero. There are no subsequent header or record reads by this function.

4. **Boundary excludes the first candidate**

   If the extent bytes at the origin are 0, 0, 0, 12, the decoded extent is 20. The first candidate is \(O+20\), exactly equal to the boundary. No candidate is examined, and the result is zero.

5. **First candidate matches**

   Let the extent decode to 23. At \(O+20\), let the first identifier decode to 46 and the second to 69. With requested identifiers 46 and 69 in their respective argument positions, the result is \(O+20\). A non-null ordinal destination receives the 16-bit value 1. The stride field need not be read.

6. **First identifier fails**

   With a candidate admitted by the boundary, suppose its first decoded identifier differs from the requested first identifier. Its second identifier is not read. Its stride is decoded to determine the next candidate.

7. **Second candidate matches**

   Let the extent decode to 46, the first candidate’s stride decode to 23, and only the second candidate match. Candidate starts are \(O+20\) and \(O+43\). The result is \(O+43\), and the ordinal output is 2.

   This also demonstrates that an admitted record may have identifier bytes beyond the nominal boundary \(O+46\). Such bytes must still be readable; the function does not reject that layout.

8. **One non-match followed by exhaustion**

   Let the extent and first stride both decode to 23, and let the first candidate fail. The next candidate is \(O+43\), which is not below \(O+23\). The result is zero, and the ordinal destination is not explicitly written.

9. **Zero-stride non-match**

   If an admitted candidate fails and its stride decodes to zero, stable memory causes the same candidate to be revisited indefinitely. A zero return is not guaranteed.

10. **Ordinal exceeds its signed positive range**

    If traversal reaches a match on visit 32768, the retained 16-bit ordinal has bit pattern 0x8000 under the evident narrowing behavior. A signed 16-bit consumer interprets that pattern as −32768 on a two’s-complement target. The function does not reject the visit count or widen the output.
