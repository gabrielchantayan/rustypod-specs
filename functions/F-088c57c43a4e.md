# F-088c57c43a4e

## Purpose

F-088c57c43a4e searches a linked hierarchy for the first eligible node whose stored integer key equals a requested key.

The search is ordered: it considers the starting node before its descendants, and it considers descendants in the order defined by their sibling links. Eligibility is also a traversal gate. A node whose eligibility bit is clear is neither compared with the requested key nor searched for descendants.

The result is the address of the first matching node, represented by the function’s integer return type, or zero when the explored hierarchy contains no match.

“Node,” “key,” “child,” and “sibling” are descriptive interpretations of the accesses shown. No external type declaration or application-level meaning is supplied.

## Interface

The function takes two values:

- **Starting address:** an integer used as the base address of a node.
- **Requested key:** an integer compared for exact equality with a field in eligible nodes.

It returns:

- The starting address or a recursively reached node address when that node is eligible and its key matches.
- Zero when the search completes without finding such a node.

## Behavior

### Eligibility gates both matching and descent

At entry to each invocation, the function reads the flag byte at offset `0x1D` from that invocation’s starting address.

If its low bit is clear, that invocation returns zero immediately. In particular, it does not:

- Read that node’s key.
- Read its first-child field.
- Visit descendants through that node.

A matching key in an ineligible node therefore cannot produce a successful result.

If the low bit is set, the function reads the integer key at offset `0x14` and compares it with the requested key. Equality returns that node’s address immediately.

The comparison is equality only. There is no ordering comparison, range check, string interpretation, or key transformation. For any concrete ABI, keys must be compared in the integer representation actually used by that ABI.

### Child traversal

An eligible node whose key does not match causes a read of its first-child address at offset `0x20`.

A zero first-child address ends that invocation’s search with a zero result.

For a nonzero child address, the function recursively invokes F-088c57c43a4e with that address and the unchanged requested key. A nonzero recursive result is returned immediately and unchanged.

Only when that recursive invocation returns zero does the enclosing invocation read the just-visited child’s sibling field at offset `0x08`. A nonzero sibling address becomes the next recursive search root. A zero sibling address ends the child-list traversal.

This distinction matters: rejecting a child because its eligibility bit is clear prunes that child’s descendants, but does not prevent the parent’s traversal from continuing to the child’s next sibling.

The sibling field of the initial starting node is not followed by that invocation. Sibling traversal belongs to the parent’s child-list processing, not to the recursive search of an individual node.

### Search order and early termination

The resulting order is depth-first, node-before-descendants, with sibling order determined by the stored links.

For duplicate matching keys:

1. An eligible starting node wins over every descendant.
2. Within its child list, a match anywhere in an earlier child’s searched subtree wins over a match in a later child.
3. Within each subtree, the same rules apply recursively.

After a match, later siblings and unexplored descendants are not visited. In particular, the successful child’s sibling field is not read by the enclosing traversal.

### Read sequencing

The conditional read sequence established by the supplied representation is:

1. Read the current node’s flag byte.
2. If eligible, read its key.
3. If eligible and nonmatching, read its first-child address.
4. Recursively search a nonzero child.
5. Only after that search returns zero, read that child’s next-sibling address.
6. Repeat child processing until a match or a zero sibling link.

A sibling address is therefore obtained after the corresponding recursive search, not prefetched before it. A node’s sibling field is not required by its own recursive invocation; it is required by the enclosing invocation if that recursive search fails.

These are source-level sequencing facts. They do not independently establish machine-instruction ordering, volatile semantics, or a supported concurrent-mutation model.

## Acceptance examples

These examples are conditional on valid field representations, readable addresses, stable relevant memory, and sufficient execution resources.

### Ineligible starting node

Given a starting node whose flag low bit is clear, the result is zero.

This remains true even if its key would equal the requested key or its first-child field would identify a matching descendant. Neither field participates in this invocation’s decision.

### Immediate match

Given an eligible starting node with a matching key, the result is exactly that starting address.

The first-child field and the starting node’s sibling field are not read. A malformed unused child link does not affect this represented path.

### Empty eligible node

Given an eligible starting node with a nonmatching key and a zero first-child address, the result is zero.

Its sibling field is irrelevant to this invocation, even if nonzero.

### Earlier subtree wins

Given an eligible, nonmatching starting node with two children, suppose the first child’s searched subtree contains an eligible match and the second child also matches.

The result is the match from the first child’s subtree. The second child is not searched. The first child’s sibling field is not read after the successful recursive result.

### Pruned child followed by a matching sibling

Given an eligible, nonmatching starting node whose first child is ineligible, suppose that child’s sibling link identifies an eligible matching node.

The first recursive search returns zero without inspecting the ineligible child’s key or descendants. The parent then reads that child’s sibling link and finds the matching sibling.

### Starting-node sibling is outside the search

Given an eligible, nonmatching starting node with no children, suppose its sibling field points to an eligible matching node.

The result is zero. Searching that sibling would require an enclosing traversal or a separate invocation.

### Exhausted finite hierarchy

Given a finite, acyclic reachable hierarchy with no eligible matching node, the result is zero after all child lists reachable through eligible nodes are exhausted.

Descendants behind an ineligible node are excluded from that search.

### Cyclic links

Given an eligible, nonmatching node whose first-child field points back to itself, recursive descent does not reach a normal no-match completion through the represented logic.

A sibling cycle can likewise prevent completion when each recursive search returns zero and the enclosing list repeatedly revisits nodes. There is no defined cycle-error result. A match encountered before repetition can still terminate the search.
