# F-f22232d382e6

## Purpose

F-f22232d382e6 conditionally acts on a writable integer slot and a proposed replacement value. It compares the existing slot value with the proposal, leaves an equal value unchanged, and writes a differing proposal when the existing value is zero.

A differing, nonzero existing value takes a separate dependency path. That path transforms the existing value through F-2f51066133e0 and passes an adjusted result to F-feee9156a257. The supplied representation marks the latter call as non-returning. Consequently, replacement of a differing nonzero value is **not established as a normally completing update**.

The address-like adjustments suggest a relationship between an exposed value and associated storage or metadata. That interpretation is inferred intent, not an ownership or allocation contract. The established behavior is the comparison, conditional write, arithmetic, and dependency-call ordering described below.

## Interface

### Inputs

The function receives two arguments:

- **Slot reference:** a pointer to an integer object. The function reads that object on entry and, on one path, writes it.
- **Proposed value:** an integer passed by value. No reference to the caller’s original proposed-value storage is exposed by this interface.

The supplied representation uses `int` for both the slot element and the proposed value. This contract treats those values as signed 32-bit integers under the recovered-width interpretation. The text alone does not independently establish the target ABI or pointer width; those limitations are recorded under Uncertainties.

The slot is one integer object. No additional fields, adjacent elements, header layout, or containing-object layout are established.

### Preconditions

The slot reference must permit the initial integer read. The function performs no explicit null check, alignment check, bounds check, or lifetime check before that access.

If the existing value is zero and the proposal differs, the slot must also permit an integer write. A read-only slot can therefore satisfy the direct memory requirements of an equality path but not of the zero-to-nonzero update path.

For a differing nonzero existing value, the dependency arguments must satisfy whatever requirements F-2f51066133e0 and F-feee9156a257 impose. Those requirements are unavailable here. In particular, a nonzero value is not proved valid merely because this function accepts it into that branch.

No thread-safety, atomicity, or synchronization precondition is supplied. Concurrent access requires an external contract.

### Outputs and completion

The function has no return value.

Normal return is directly established for:

- An existing value equal to the proposed value.
- An existing value of zero with a differing proposed value, after the slot write.

For a differing nonzero existing value, execution reaches a call represented as non-returning, provided the preceding dependency returns and argument evaluation completes. The mechanism of non-return is unknown.

There is no explicit status result, error code, or failure-reporting object.

## Behavior

### Initial observation and equality

The first direct memory operation is a read of the integer designated by the slot reference. The resulting value supplies both the comparison and, when applicable, the later arithmetic. There is no explicit second read of the slot.

If the captured value equals the proposed value, the function returns immediately:

- It performs no direct slot write.
- It calls neither dependency.
- It does not perform the four-unit argument adjustments.

This includes equality at zero and equality at any nonzero representable value. In particular, equal nonzero inputs do not trigger the dependency path.

### Differing value with a zero existing value

If the captured existing value is zero and differs from the proposal, the function writes the proposed value into the slot and returns normally.

Because equality was already excluded, this path necessarily writes a nonzero proposal. The visible behavior is one initial read followed by one write to the same integer object, with no intervening dependency call.

There is no visible validation or normalization of the proposed value before this write. Subject to the integer representation and a valid writable slot, a negative proposal follows this same path as a positive proposal.

### Differing value with a nonzero existing value

If the captured existing value is nonzero and differs from the proposal, the function proceeds in this order:

1. It forms an integer argument by adding four to the captured existing value.
2. It invokes F-2f51066133e0 with that argument.
3. If that call returns, it takes the returned integer and forms a second argument by subtracting four.
4. It invokes F-feee9156a257 with the second argument.

The supplied representation classifies the final invocation as non-returning. Under that control-flow model, this path does not reach the direct slot assignment or a normal return.

The proposed value is not passed to either dependency. It determines whether this branch is entered, but it is not used in either dependency argument.

The slot reference is also not explicitly passed to either dependency. This does **not** establish that the slot remains unchanged: either dependency could have access to it through other state or aliases. Nor does it establish that unrelated state is preserved.

### Integer arithmetic

Both adjustments are integer arithmetic, not typed pointer traversal:

- The first adds the numeric constant four to the captured existing value.
- The second subtracts the numeric constant four from the first dependency’s returned value.

There is no visible dereference of either adjusted value in this function. No scaling by an element size is shown.

Under signed 32-bit arithmetic, the first adjustment is representable when the existing value is at most 2,147,483,643. The second adjustment is representable when the returned value is at least −2,147,483,644. Other bounds follow from each operand already being a signed 32-bit value.

The representation does not establish portable behavior for signed overflow. This contract therefore does not assume wrapping, trapping, saturation, or rejection at those boundaries. Boundary cases requiring overflow are documented-only until the target arithmetic semantics are established.
