# F-6f4f01b9e22a

## Purpose

F-6f4f01b9e22a attempts to register a descriptor-backed instance with a manager. It validates two pointers and a compatibility field, searches for an existing matching registration, optionally requests removal of that registration, allocates and initializes an instance, performs flag-controlled setup, and appends the instance to the manager’s registration array.

The operation is not transactional. Removal of an older registration precedes replacement allocation. A selected-instance reference or auxiliary-list insertion can precede later failure. The function contains no direct rollback for those changes.

“Registration,” “removal,” and “allocation” describe inferred roles. The established contract below concerns visible accesses, calls, branches, and status propagation. Dependency implementations and runtime behavior are unavailable.

## Interface

### Arguments and result

The function accepts four 32-bit arguments:

1. **Manager pointer:** nullable pointer to mutable manager storage.
2. **Descriptor pointer:** nullable pointer to descriptor storage.
3. **Auxiliary status seed:** initial 32-bit contents of the status location supplied to the auxiliary allocation dependency.
4. **Initial main status seed:** written to the main status location before searching. Every visible terminating path overwrites this seed.

Pointers and accessed scalar fields have 32-bit representations. Offsets below are byte offsets.

The represented result is 64 bits:

| Bits | Contents |
|---|---|
| 63–32 | Original descriptor argument’s 32-bit pointer representation |
| 31–0 | Main status contents at return |

The upper half is not the allocated instance pointer. It retains the original descriptor argument on both success and failure. Whether this representation matches an independently documented external ABI is unresolved.

### Manager storage

| Offset | Observed use |
|---|---|
| +0 | Context supplied to allocation and release dependencies |
| +24 | Registration count |
| +28 onward | Array of 32-bit instance pointers |
| +156 | Address supplied as an auxiliary-list anchor |
| +168 | Selected-instance reference |

Searching and the capacity check interpret the count as unsigned 32-bit. The capacity check admits counts from zero through 31 and rejects counts of 32 or greater.

### Descriptor storage

| Offset | Observed use |
|---|---|
| +0 | Flags |
| +4 | Main allocation size or parameter |
| +8 | Matching key |
| +12 | Revision-like value, compared as signed 32-bit |
| +16 | Compatibility field, checked using signed ordering |
| +24 | Optional registration callback |
| +36 | Auxiliary tag |
| +40 | Value copied after successful special initialization |
| +56 | Pointer to an auxiliary operation table |

The operation table provides an optional initializer at +4, a copied value at +16, and a cleanup callback at +20.

### Instance and auxiliary-record storage

| Instance offset | Observed use |
|---|---|
| +0 | Current descriptor pointer |
| +4 | Manager pointer |
| +8 | Retained main-allocation context |

The separate auxiliary allocation requests 12 bytes. This function directly writes only its instance-pointer field at +8 before passing the record to dependencies.

### Preconditions

Beyond checking the manager and descriptor for null, the function relies on valid storage for every accessed object, array entry, nested pointer, and callback. It does not validate allocation sizes against the fields it subsequently accesses.

A zero allocation status permits immediate use of the returned pointer. No independent null-result check is visible. Cleanup can inspect fields that this function has not initialized on the failing path; safe contents must come from an external allocation or object-state contract.

## Behavior

### Initial validation

Validation occurs in this order:

1. A null manager produces status `0x21`.
2. A nonnull manager with a null descriptor produces status `6`.
3. Otherwise, the descriptor compatibility field is checked.

The compatibility check rejects exactly those field values greater than `0x00020002` under signed 32-bit interpretation, producing status `4`. It establishes no lower bound. Zero, `0x00020000`, `0x00020001`, `0x00020002`, and negative signed values pass this check.

These failures occur before registration searching.

### Matching and possible replacement

After validation, the auxiliary and main status locations receive the third and fourth arguments, respectively.

The function searches registrations in ascending index order. Each loop condition rereads the manager’s count and compares the index with it as unsigned 32-bit. For each entry, it obtains that instance’s descriptor and invokes F-U01 with the existing descriptor’s key followed by the incoming descriptor’s key.

A zero comparison result identifies a match. The function then reads the incoming and existing revisions:

- If the incoming revision is less than or equal to the existing revision under signed 32-bit ordering, status becomes `5` and the function returns.
- Otherwise, F-f8ea4f8029b1 receives the manager and existing instance. Searching ends after this call.

The existing instance pointer is the entry selected before F-U01; its descriptor is accessed again for the revision comparison after that call. No preservation of descriptor contents by F-U01 is established.

Only the first matching entry is handled. F-f8ea4f8029b1’s return value is ignored. Whether it changes the count, compacts the array, destroys storage, or removes other references is unknown.

### Capacity and main allocation

After searching, the function retains the manager context from +0 and sets the main status to zero. It then rereads the count. An unsigned count greater than 31 produces status `0x30`.

Otherwise, F-3ce007b692cc receives:

- The retained context.
- The incoming descriptor’s value at +4.
- The address of the main status location.

A nonzero main status after the call causes immediate return. The returned pointer is not released on that branch.

With zero status, the returned instance receives these writes in order:

1. Manager pointer at +4.
2. Retained context at +8.
3. Original descriptor pointer at +0.

The original descriptor’s flags are then read to determine whether auxiliary setup is required.

### Auxiliary setup: flag `0x2`

If flag `0x2` is clear, auxiliary setup is skipped.

If it is set, the function rereads the manager context and calls F-3ce007b692cc with that context, a 12-byte request, and the auxiliary status address. Unlike the main allocation status, this status is not reset to zero before allocation: it initially contains the third argument.

After the allocation call, the function reads a global discriminator. Subsequent changes to that global do not change this retained comparison value.

If the auxiliary status is nonzero immediately after allocation, the function does not prepare, link, notify, or release the returned auxiliary pointer. It proceeds to status transfer as described below.

If the auxiliary status is zero:

1. The instance’s current descriptor pointer is retained for this setup and written to instance +20.
2. Its tag at descriptor +36 is copied to instance +24.
3. The tag is compared with the retained discriminator.

If the tag differs, the special initializer is skipped. If it matches, the operation table is accessed and its initializer pointer is checked. A null initializer is also skipped.

A nonnull initializer, F-U03, receives the context retained for auxiliary allocation and the address of instance +60. Its returned 32-bit value replaces the auxiliary status.

There are then two distinct paths:

- **Initializer failure:** A nonzero F-U03 result bypasses the instance +64 and +68 copies, the auxiliary-record +8 write, list insertion, and notification. The function proceeds directly to releasing the auxiliary record.
- **Initializer success or omission:** A zero F-U03 result first causes operation-table +16 to be copied to instance +64, followed by descriptor +40 to instance +68. If initialization was skipped, these two copies do not occur. Both cases then reach record preparation and linking.

The successful-initializer copies use the descriptor pointer retained before the callback, but reread its operation-table pointer and copied fields after the callback. They do not use guaranteed pre-callback snapshots.

Record preparation writes the instance pointer to auxiliary-record +8. F-24b3b16470f4 then receives the manager’s anchor address at +156 and the record. F-114548cdf489 subsequently receives the manager. Their return values are ignored.

After notification, the auxiliary status is checked again:

- Zero bypasses auxiliary-record release.
- Nonzero reaches auxiliary-record release.

Thus, release is reached either directly after a nonzero special-initializer result or after linking and notification leave the auxiliary status nonzero. F-bf7242c98d06 receives the retained auxiliary-allocation context and the auxiliary record.

After that call, the function reads the **then-current auxiliary status**, copies it to the main status, and branches on the auxiliary status value. It does not restore or preserve the initializer’s error value. Because the auxiliary status address has escaped to the allocator, the supplied representation does not establish that release or another dependency cannot modify it.

A zero value at this transfer continues into common setup. A nonzero value enters instance cleanup. In particular, an initializer failure followed by a release that changes the auxiliary status to zero can continue without the skipped copies or list operations having occurred.

### Common setup and registration callback

Common setup reads flags through the instance’s current descriptor pointer.

If flag `0x4` is set, manager +168 is immediately assigned the new instance. This occurs before resource setup and the registration callback.

If flag `0x1` is set, the current descriptor pointer is written to instance +20. The flags are then examined for `0x200`:

- With `0x200` set, resource initialization is skipped.
- With `0x200` clear, F-f752365621f4 receives the retained main-allocation context and the address of instance +36. Its returned status replaces the main status. A nonzero result enters cleanup.

With flag `0x1` clear, neither that descriptor-saving write nor resource initialization occurs.

If setup permits continuation, the optional registration callback is read from +24 of the **original descriptor argument**, not necessarily the descriptor currently stored in the instance. A null callback is skipped. Otherwise, F-U02 receives the instance; its returned status replaces the main status. Nonzero enters cleanup, while zero permits commit.

### Commit

The function reads the manager’s current count, writes the count incremented by one, and then writes the instance pointer into the array slot selected by the old count. The direct write order is therefore **count first, array entry second**.

There is no capacity recheck after allocation, initialization, or callbacks. Safe indexing requires those calls to leave an appropriate count. The represented fields are 32 bits; no overflow handling or enlarged-count storage is visible.

Commit is reached through the stated control-flow checks, not a final independent validation of the main status. If a dependency changes escaped status storage on a path that does not subsequently overwrite or test it, commit and a nonzero returned status are not excluded by this representation.

### Cleanup after setup failure

After a post-allocation failure, cleanup:

1. Reads flags through the instance’s current descriptor. If `0x1` is set and `0x200` is clear, F-12625f941422 receives the value at instance +36.
2. Rereads the current descriptor’s flags. If `0x2` is set and instance +60 is nonzero, invokes F-U04 from operation-table +20 through the descriptor saved at instance +20.
3. Calls F-bf7242c98d06 with the retained main-allocation context and the instance.

Resource cleanup is flag-based, not based on whether initialization was attempted or succeeded. An auxiliary failure can therefore trigger resource cleanup before resource initialization.

F-U04 has no visible explicit arguments, no visible null check, and an ignored return value. The cleanup operation-table lookup follows the saved descriptor, which flag `0x1` setup may have overwritten.

The function returns the main status contents remaining after cleanup calls. Their preservation of escaped status storage is not established.

## Side effects

Direct writes can affect allocated instance storage, auxiliary-record +8, manager +168, manager count, and a registration-array entry.

Indirect effects are possible through every dependency. The function provides no synchronization or reentrancy guard.

Visible cleanup does not directly:

- Restore an older registration.
- Clear manager +168.
- Unlink an auxiliary record already passed to the list dependency.
- Release descriptor storage.

Consequently, a later failure may leave a selected-instance reference or list entry referring to storage passed to a release dependency. Whether dependencies prevent such outcomes is unknown.

Successful setup retains descriptor pointers rather than copying the complete descriptor. Descriptor lifetime requirements therefore extend beyond this call unless an external contract establishes otherwise.

Main storage is retained on commit and passed to a release dependency on setup failure. Auxiliary storage may be linked, released, or left untouched depending on status transitions. These observations do not establish ownership transfer, deallocation, or callback-created resource lifetimes.

## Acceptance examples

These are conditional static examples, not executed tests.

1. **Null precedence:** With both pointers null, the result is status `0x21` with upper half zero. Status `6` requires a nonnull manager and null descriptor.

2. **Compatibility boundary:** Compatibility `0x00020003` produces status `4` before searching. `0x00020002`, zero, and `0xffffffff` pass this check.

3. **Signed revision:** For a first matching registration with revision zero, incoming revision `0xffffffff` means signed −1 and produces status `5`. Removal is not reached.

4. **Replacement before failure:** A newer matching revision reaches F-f8ea4f8029b1 before capacity checking and allocation. A subsequent allocation error does not cause direct restoration of the older registration.

5. **Capacity:** With stable manager state and no match, count 31 permits allocation; count 32 produces `0x30`.

6. **Ordinary commit:** With setup flags clear, no registration callback, successful allocation, and no dependency mutation, count is incremented before the new array entry is written. Returned status is zero; the upper half contains the original descriptor pointer.

7. **Initializer failure without status mutation:** If auxiliary allocation reports zero and F-U03 returns nonzero, the +64/+68 copies, record +8 write, list insertion, and notification are skipped. The record is released. If release leaves auxiliary status unchanged, that error is copied to the main status and instance cleanup follows.

8. **Initializer failure with status mutation:** Under the preceding conditions, if release changes auxiliary status to zero through accessible escaped storage, zero is copied to the main status and common setup follows. The skipped initialization copies and linking are not retried.

9. **Skipped initializer:** With auxiliary allocation status zero and a nonmatching tag, the special initializer and +64/+68 copies are skipped, but record preparation, linking, and notification are reached.

10. **Post-link status change:** If notification leaves auxiliary status nonzero, the record is released after linking. The subsequent branch uses the status remaining after release, not necessarily the value observed after notification.

11. **Early cleanup:** With flags `0x1` and `0x2` set and `0x200` clear, an auxiliary failure that remains nonzero reaches F-12625f941422 before resource initialization has run.

12. **Selected reference:** With flag `0x4` set and a failing registration callback, manager +168 is written before cleanup. This function contains no subsequent direct clearing write.
