# F-d92bc662c47a

## Purpose

F-d92bc662c47a searches a linked sequence associated with a supplied key, ranks eligible records by two attributes, and either returns an existing record, creates and registers a new record, or returns null.

Creation is controlled by a separate input. When creation is disabled, an existing match is necessary but not sufficient for a non-null result: the selected record must also have a non-null pointer in at least one of two additional fields. When creation is enabled, a record with the maximum possible match score is reused; otherwise, the function attempts to create a record.

These are established structural behaviors. The application meanings of the key, attributes, two additional pointer fields, and context flag are unknown. Terms such as “record,” “match,” and “registration” describe observed roles, not verified domain semantics.

## Interface

### Inputs

The function accepts six arguments:

| Argument | Observed representation | Role |
|---|---|---|
| Context address | 32-bit address-bearing value | Supplies a dependency receiver at byte offset 276 and a writable flag at byte offset 30. It is also passed directly to the allocation dependency. |
| Key source | 32-bit opaque value | Passed unchanged to the lookup and external transfer dependencies. The transfer operation makes a readable source-address interpretation likely, but its complete contract is unavailable. |
| Key length | Signed 32-bit integer | Passed to lookup and registration, used to calculate allocation size, and used to locate a terminating zero byte. |
| Requested primary attribute | Signed 32-bit integer | Clamped upward to −1, used in eligibility and scoring, and narrowed to 16 bits when creating a record. |
| Requested secondary attribute | Unsigned 32-bit integer | Compared at full width with a stored unsigned byte and narrowed to a byte when creating a record. |
| Creation control | Signed 32-bit integer | Zero disables creation; every nonzero value enables it. Its magnitude and sign otherwise have no observed effect. |

### Output

The result is a record pointer or null.

A non-null result is either an existing selected record or the newly allocated record. The function does not return either of the two additional pointer fields it examines before a successful return.

Null can mean:

- No eligible record was found while creation was disabled.
- An existing selected record failed the final pointer-field gate while creation was disabled.
- The allocation dependency returned null.
- The registration dependency returned the newly allocated record’s own address, triggering a failure path.

No distinct error code is returned for these cases.

## Behavior

### 1. Normalize the requested primary attribute

Any requested primary attribute below −1 is replaced by −1. Values of −1 and above are unchanged.

This normalization occurs at signed 32-bit width. There is no corresponding range clamp to the signed 16-bit range of the stored record attribute.

### 2. Obtain the candidate sequence

The function calls F-a09bb08bf954 with:

1. The context address plus 276 bytes.
2. The key source.
3. The key length.

The returned pointer becomes both the traversal starting point and a saved initial head. The saved initial head is later written into a newly allocated record if creation occurs.

A null lookup result is treated as an empty sequence. The function may nevertheless create a record when creation is enabled.

### 3. Traverse and rank candidates

For each non-null candidate, the function first reads its signed 16-bit primary attribute.

A candidate is eligible if at least one of the following holds:

- Its primary attribute is −1.
- Its primary attribute equals the normalized request.
- The normalized request is −1.

An ineligible candidate is not scored, and its secondary attribute is not read by the visible logic.

For an eligible candidate, the function reads the unsigned byte at offset 2 and computes a score:

| Condition | Score contribution |
|---|---:|
| Stored primary equals the normalized request, or the normalized request is −1 | Base score 4 |
| Otherwise, the stored primary is −1 | Base score 1 |
| Stored secondary equals the full 32-bit requested secondary | Add 2 |
| Otherwise, the stored and requested secondary values are 2 and 3, in either order | Add 1 |
| Otherwise | Add 0 |

Possible scores are 1 through 6.

A candidate replaces the current selection only if its score is strictly greater than the best score so far. Equal-score candidates do not replace an earlier selection. Consequently, traversal order determines ties.

After processing each candidate, the function reads the 32-bit link at offset 12 and continues from that pointer. It traverses the entire sequence even after finding a score of 6; there is no early exit at the maximum score.

There is no observed cycle detection or traversal limit. A cyclic sequence can prevent termination.

### 4. Decide whether to reuse or create

After the traversal reaches null:

- If creation is disabled:
  - No selection means an immediate null return.
  - Otherwise, the selected existing record proceeds to the final pointer-field gate.
- If creation is enabled:
  - A best score of 6 causes reuse of the selected existing record.
  - A best score below 6 causes an allocation attempt, even if a weaker eligible record exists.

The visible signed-subtraction and overflow test implements this decision. Because the best score remains in the range 0 through 6, the decision reduces to the threshold above without an ambiguous overflow case.

A failed creation attempt does not fall back to a weaker existing selection.

### 5. Allocate and initialize a new record

When creation is required, the function calls F-f053f140662a with:

1. The original context address.
2. The key length plus 32.

A null allocation result immediately produces a null return.

For a non-null allocation result, the visible initialization order is:

1. Write the low 16 bits of the normalized primary request at offset 0.
2. Write the saved initial lookup pointer at offset 12.
3. Write the low 8 bits of the requested secondary attribute at offset 2.
4. Invoke the unmapped external transfer dependency with the record address plus 28, the original key source, and the original key length.
5. Write a zero byte at record address plus 28 plus key length.
6. Call F-30162766ee7c with the context address plus 276, the record address plus 28, the original key length, and the new record pointer.

The external transfer dependency is consistent with copying key bytes, but its exact access pattern, overlap handling, length interpretation, and error behavior are not established.

The explicit zero-byte write follows that call. It is not conditional on a visible transfer status.

### 6. Handle the registration result

The result from F-30162766ee7c is compared with the newly allocated record’s address.

If they are equal, the function:

1. Writes the byte value 1 at context offset 30.
2. Calls F-94cb53877c15 with the new record.
3. Returns null.

The meaning of this equality condition is unknown. It is observably treated as failure, but should not be renamed “duplicate,” “collision,” or “insertion failure” without additional evidence.

If the registration result differs from the new record’s address, processing continues with the new record. This includes a null registration result. The returned value is not otherwise used to choose the final result.

### 7. Apply the final pointer-field gate

For either a reused or newly created record, the function:

1. Reads the pointer at offset 20.
2. Reads the pointer at offset 16 only if the first pointer is null.

It then returns:

- The selected record if either pointer is non-null.
- The selected record if creation is enabled, even when both pointers are null.
- Null if both pointers are null and creation is disabled.

The pointer-field reads still occur when creation is enabled, despite their values not changing the successful return decision.

### Writes

The visible function writes:

- A zero byte after the key destination region.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. They assume readable, finite candidate sequences and dependency behavior consistent with the stated scenario.

### First equal-scoring candidate wins

With creation disabled, suppose two eligible records each score 5. The first remains selected. If its field at offset 20 is non-null, the function returns that first record even if the second has different pointer fields.

### Primary wildcard has lower priority for a specific request

For a normalized primary request of 7 and secondary request of 2:

- A record with primary −1 and secondary 2 scores 3.
- A record with primary 7 and secondary 3 scores 5.
- A record with primary 7 and secondary 2 scores 6.

The last record wins regardless of the order of these three records.

### A wildcard request gives every candidate the higher base score

For primary request −1 and secondary request 2, any stored primary value is eligible. A record with secondary 2 scores 6; secondary 3 scores 5; any other secondary scores 4.

A request below −1 has this same ranking behavior because it is normalized to −1.

### Creation replaces a weaker selection

With creation enabled and a best existing score of 5, the function attempts allocation. If allocation returns null, the result is null, not the existing score-5 record.

### Maximum score avoids allocation

With creation enabled and a best score of 6, the function reuses the first score-6 record. It still completes traversal and reads the final pointer fields. Both fields may be null without preventing the record’s return.

### Existing selection can still yield null

With creation disabled, an eligible selected record whose fields at offsets 20 and 16 are both null produces null. No allocation is attempted.

### Registration identity triggers the flagged failure path

If registration returns the exact newly allocated record address, the context byte at offset 30 is set to 1 before F-94cb53877c15 is called, and the function returns null.

If registration instead returns null, that identity test does not trigger. Subject to valid subsequent reads and normal dependency returns, creation-enabled execution returns the new record.

### Full-width comparison differs from stored truncation

A secondary request of 258 does not equal a stored byte of 2 during scoring, and it does not activate the special request-value-2 pairing rule. If a record is created, however, its stored secondary byte becomes 2.

Similarly, a primary request of 65535 is not normalized to −1 and does not equal a stored signed primary of −1. On creation, its low 16 bits are stored, yielding the signed 16-bit representation −1.

### Zero-length key

For key length zero, the allocation-size argument is 32, the transfer dependency is still called with length zero, and the explicit terminator is written at offset 28. Whether the source may be null depends on the lookup and transfer dependencies.

## Uncertainties

The supplied body establishes selection order, scoring, strict tie handling, the creation threshold, visible field accesses, dependency argument order, and the registration identity failure path.

### Inferred intent

The layout and calls suggest a keyed record store with wildcard-compatible attributes and inline key storage. The allocation request provides four bytes beyond the 28-byte prefix plus the key length; the explicit terminator uses one of those bytes for ordinary nonnegative lengths. Neither a string-key abstraction nor the purpose of the remaining capacity is established.
