# F-40aaef3d8070

## Purpose

F-40aaef3d8070 derives a candidate from an object-held base and a signed displacement, applies an ordered bound selection, consults an embedded component, and conditionally replaces the object’s current value.

If the current value differs from the candidate after the embedded-component calls, the function commits the candidate and performs mode-dependent processing. Depending on mode and dependency results, that processing includes additional dependencies and ordered indirect calls.

An unchanged current value suppresses the commit and subsequent mode processing, but does not suppress the preceding embedded-component calls.

“Base,” “bound,” “current value,” and “notification” describe observable roles. Their application-level meanings are not established.

## Interface

### Inputs and output

The function receives:

- An object address.
- A signed 32-bit displacement.

It returns no value. Observable results consist of memory accesses, a conditional object-field write, dependency calls, indirect calls, and any effects of those calls.

The represented object layout is:

| Byte offset | Width or representation | Role |
|---|---|---|
| `0x00` | 32-bit pointer-like word | Locates an indirect dispatch table |
| `0x18` | 32-bit word | Mode storage; comparisons use its low eight bits |

| `0x8BC` | Signed 32-bit integer | Initial base and later lower comparison bound |

The indirect target is obtained from the table entry at byte offset `0x58`. Each indirect call receives the object followed by two opaque 32-bit arguments. Any return value is unused.

These widths and offsets describe the supplied representation. A complete independently verified ABI, including pointer representation and alignment, is unavailable.

## Behavior

### Candidate calculation and ordered bound selection

The function first reads the base field and adds the displacement. It then reads the upper-bound field and compares that bound with the candidate using signed ordering.

The selection has two mutually exclusive adjustment paths:

- If the upper bound is strictly less than the candidate, the candidate becomes the upper bound. The lower-bound read and comparison are skipped.
- Otherwise, the function reads the base field again. If the candidate is strictly less than that newly read base, the candidate becomes that base.
- If neither comparison requires replacement, the candidate is retained.

This is not an unconditional application of both bounds. In particular, selecting the upper bound does not lead to a later lower-bound correction.

With stable fields and a base no greater than the upper bound, the behavior matches an inclusive clamp. With inverted bounds, the ordered selection remains authoritative. A candidate above the upper bound becomes that upper bound even when the result is below the base.

The base used for addition and the base used for the lower comparison are separate reads. The latter is reached only when the upper comparison does not select the upper bound.

### Embedded-component processing

After candidate selection, the function calls F-56fd8d6069bf with the embedded-component address at object offset `0x1C`.

It compares the returned integer with the retained candidate:

- Equal: no further embedded-component call.
- Unequal: call F-9c31c3e85ab1 with the same embedded-component address and the integer `1`.

The candidate is not recomputed after either call. Changes to the base or upper-bound fields by those dependencies therefore do not alter this invocation’s selected candidate.

These calls precede the current-value equality check. Their occurrence does not depend on whether the current value already matched the candidate at entry.

### Current-value comparison and commit

After the embedded-component processing, the function reads the current-value field at `0x8B8`.

If that value equals the candidate, the function returns immediately. No direct current-value write, shared-argument capture, mode processing, or indirect notification follows.

Otherwise, the function writes the candidate to the current-value field and continues.

This equality check observes the value after the preceding dependencies return. Either dependency can therefore cause or prevent the early return by changing the current-value field.

There is exactly one explicit object-field write in the supplied body: this conditional 32-bit commit. Later callees may change the field again; the function does not restore its candidate afterward.

### Shared notification-argument capture

After the commit, the function reads two distinct global locations in this order:

1. A **primary argument**.
2. A **final argument**.

Both are opaque 32-bit values retained for later use.

The primary argument is used by the mode-2 nonzero-result notification and the first three mode-3 notifications. The final argument is used by the last call of either notification sequence.

Subsequent changes to these globals do not replace the already captured arguments. Other notification arguments are loaded later, as described below.

### Initial mode-2 processing

The first mode test occurs after the commit and shared-argument capture. It compares the low eight bits of the mode field with `2`.

If equal, the function calls F-bfda5fbfe0b0 with:

1. The object.
2. The address of a 40-byte local workspace.
3. A fresh read of the current-value field.
4. The integer `3`.

The function does not explicitly initialize the workspace before this call and does not inspect its contents afterward.

A zero result selects this ordered pair of calls:

1. F-97a072757e44 with the object.
2. F-52cae007644e with the object and a current-value read performed after F-97a072757e44 returns.

The second call is not cancelled if F-97a072757e44 changes the mode. Its value argument can differ from the candidate and from the value previously supplied to F-bfda5fbfe0b0.

A nonzero result instead selects one indirect call with:

- The object.
- The captured primary argument.
- A mode-2-specific payload loaded from its global location.

After either alternative, the function reads the mode again. If its low eight bits equal `2`, it proceeds to the common two-call notification sequence. Otherwise, it proceeds to the mode-1/mode-3 selection.

### Mode-1/mode-3 selection

This selection is reached either because the initial mode test did not match `2`, or because mode-2 processing completed with a subsequent mode read not equal to `2`.

The function reads the mode and compares its low eight bits with `1`.

- If equal, it selects the common two-call sequence.
- Otherwise, it reads the mode again and compares its low eight bits with `3`.
- If that comparison succeeds, it selects the mode-3 four-call sequence.
- Otherwise, it returns without further calls.

These are distinct mode reads, not one retained mode value. Consequently, an initial mode-2 path can later select mode `1` or mode `3`.

Once either notification sequence is selected, no further mode test interrupts that sequence.

### Common two-call notification sequence

The sequence is:

| Call | First non-object argument | Second non-object argument |
|---|---|---|
| First | Common-call argument, loaded for this call | Common-call payload, loaded for this call |
| Second | Previously captured final argument | Final common payload |

The first call uses two global sources separate from the sources of the captured primary and final arguments.

After the first indirect call returns, the final call has an explicitly established staging order:

1. Resolve the dispatch table through the object and capture its `0x58` target.
2. Load the final common payload from its global location.
3. Invoke the captured target with the object, captured final argument, and loaded payload.

Thus, the first call can affect both the target and payload used by the second call. Target capture precedes the final payload load; these operations are not unordered parts of one call expression.

### Mode-3 four-call notification sequence

The sequence is:

| Call | First non-object argument | Second non-object argument |
|---|---|---|
| First | Captured primary argument | First mode-3 payload |
| Second | Captured primary argument | Second mode-3 payload |
| Third | Captured primary argument | Third mode-3 payload |
| Fourth | Captured final argument | Fourth mode-3 payload |

Each payload has a separate global source. Payloads are loaded when their respective calls are reached, rather than all being captured before the sequence.

The dispatch target is resolved anew for each call. Earlier calls can therefore affect later targets by changing the object’s table reference or the relevant table entry.

After the third indirect call returns, the fourth call has this explicit staging:

1. Resolve and capture the dispatch target.
2. Load the fourth mode-3 payload from its global location.
3. Invoke that captured target with the object, captured final argument, and loaded payload.

The fourth payload load therefore follows both the third call’s return and the final target capture.

No rollback, exception handler, or error-reporting return value is shown. If a callee fails to return normally, completion of later operations is not established. A committed current value is not visibly undone.

## Acceptance examples

These are conditional static deductions, not executed tests. Unless an example states otherwise, arithmetic is representable, fields and globals remain stable except for the direct commit, dependencies return normally, and dispatch targets are valid.

### Unchanged current value still permits reconciliation

For base `100`, upper bound `200`, displacement `20`, and current value `120`, the candidate is `120`.

F-56fd8d6069bf is still called. If its result differs from `120`, F-9c31c3e85ab1 follows with `1`. If the current value remains `120`, execution then returns without a direct write or mode processing.

### Bounds and equality

For base `100` and upper bound `200`:

- Displacement `150` selects `200`.
- Displacement `−50` selects `100`.
- Displacement `100` retains `200`.
- Displacement `0` retains `100`.

The bound comparisons are strict; equality alone does not trigger replacement.

### Inverted bounds

For base `100`, upper bound `50`, and displacement `0`, the initial candidate is `100`. The upper comparison selects `50`, and the lower comparison is skipped. The final candidate is `50`.

### Reconciliation changes the commit decision

If the candidate is `120` and an embedded-component dependency changes the current value to `120`, the subsequent equality check returns early even if the current value differed at entry.

Conversely, if the current value initially equals `120` but a dependency changes it away from `120`, the function commits `120` and proceeds to mode processing.

### Initial mode 1

If a commit occurs, the first mode test observes `1`, and mode remains `1` through the subsequent selection, the common two-call sequence executes.

F-bfda5fbfe0b0, F-97a072757e44, and F-52cae007644e are not called on this path. This exclusion depends on the initial mode test not selecting mode `2`; later selection of mode `1` alone is insufficient.

### Mode 2 transitions to mode 1

If the first mode test observes `2`, F-bfda5fbfe0b0 is called before any later mode-1 selection.

If it returns zero, F-97a072757e44 and F-52cae007644e also occur. If subsequent mode reads select `1`, the common two-call sequence follows those dependencies.

If it returns nonzero instead, the mode-2-specific indirect call occurs before the common sequence. That path has three indirect calls.

### Mode 2, zero result, retained mode

If mode remains `2` and F-bfda5fbfe0b0 returns zero, the order is F-bfda5fbfe0b0, F-97a072757e44, F-52cae007644e, then the common sequence.

If F-97a072757e44 changes the current value from `120` to `125`, F-52cae007644e receives `125`.

### Mode 2 transitions to mode 3

If F-bfda5fbfe0b0 returns nonzero and subsequent selection observes mode `3`, the mode-2-specific indirect call precedes all four mode-3 calls: five indirect calls in total.

### Notification mutations and final-call staging

If the first mode-3 call changes the primary-argument global, calls two and three still use the captured primary argument. If it changes the second payload’s global, the second call loads that changed payload.

If the third mode-3 call changes the dispatch entry and fourth payload global, the final stage captures the resulting target first, loads the resulting payload second, and invokes the captured target third.

The corresponding order holds after the first common-sequence call: capture final target, load final common payload, invoke captured target.

Changing mode during a selected notification sequence does not cancel its remaining calls.

### Other stable modes

If a commit occurs and all mode reads observe a value other than `1`, `2`, or `3`, the commit remains effective, but no mode-specific dependency or indirect notification follows.
