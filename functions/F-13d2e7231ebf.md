# F-13d2e7231ebf

## Purpose

F-13d2e7231ebf conditionally clears a 32-bit field in an indexed table entry and, when requested, obtains and stores a replacement. It also issues dependency calls describing the removal and replacement, invokes an indirect operation on a temporary object, and returns a signed 32-bit status.

The update is **nontransactional**. Clearing precedes replacement acquisition. Storing a replacement precedes indirect dispatch, replacement classification, and final notification. A nonzero returned status does not imply that the entry is unchanged, and no rollback is visible.

Replacement classification uses the current value field of an addressable message buffer **after indirect dispatch**, not an immutable copy of the acquired replacement. That buffer is also used for the removal message. If its address was previously supplied to a dependency, retention and later mutation are unresolved. Consequently, the stored replacement and the subsequently classified or reported value need not agree.

“Removal,” “replacement,” and “notification” describe observable sequencing. Resource ownership and protocol meaning are not established.

## Interface

### Arguments

| Argument | Representation | Established use |
|---|---|---|
| First argument | Opaque 32-bit value | Neither inspected nor forwarded by the visible body. |
| Group selector | Signed 32-bit integer | Participates in entry-address calculation; forwarded to validation and notifications. |
| Entry selector | Signed 32-bit integer | Participates in entry-address calculation. |
| Replacement request | Signed 32-bit integer | Zero disables validation and replacement. Every nonzero value enables both. |

The visible body does not reject negative selectors or negative nonzero replacement requests.

### Result

The function returns a signed 32-bit status:

| Condition | Status effect |
|---|---|
| No status-changing condition occurs | Remains `0`. |
| Validation returns nonzero | That result is returned after cleanup; the table-update portion is skipped. |
| Initially read entry value is `1` or `2` | Sets status to `18`. |
| Replacement message’s current unsigned value field is below `3` after indirect dispatch | Sets status to `18`. |
| Final replacement notification returns nonzero | Sets status to `2`, overriding an earlier `18`. |

An otherwise acceptable replacement does not reset an earlier `18` to zero. The removal notification’s return does not affect the status.

### Table addressing and field layout

Four global quantities supply:

- A table base.
- A stride factor.
- A context address.
- A notification word.

The selected entry address is the table base plus:

- Four times the stride factor times the group selector.
- Twelve times the entry selector.

The accessed entry field is an unsigned 32-bit word at byte offset `8`. The twelve-byte entry indexing scale does not establish the meanings of the other bytes, table dimensions, or valid selector ranges.

The recovered address operands and operations are 32-bit. Behavior outside the valid address range, including overflow interpretation, remains documented_only; this contract does not impose portable mathematical or signed-overflow semantics.

### Temporary storage and message layout

A temporary object is initialized before branching and cleaned up on every shown normal exit. On the replacement path, its first 32-bit word supplies a dispatch-table address. The indirect target is taken from byte offset `12` in that table.

One addressable twelve-byte message region is reused for removal and replacement:

| Byte range | Explicitly established content |
|---|---|
| `0` | One-byte value `5` when prepared. |
| `1`–`3` | Not explicitly initialized by this body. |
| `4`–`7` | Unsigned 32-bit value field. |
| `8` | One-byte removal indicator `0` or replacement indicator `1`. |
| `9`–`11` | Not explicitly initialized by this body. |

These are preparation-time assignments, not guarantees against subsequent dependency mutation. Native byte order is not established.

### Preconditions

Normal completion requires valid storage and callable dependencies for every reached operation. In particular:

- The selected entry field must be readable and writable.
- The captured context address must permit a 32-bit read at offset `20` whenever a notification is reached.
- Temporary initialization must establish the state required by dispatch and cleanup.
- The replacement-path indirect target must be callable.

No visible bounds, null-address, alignment, or dispatch-validity check enforces these requirements.

## Behavior

### Initialization and validation

F-7a117b899bf6 receives the temporary-object address first. Its result is not inspected. Initialization occurs even for removal-only requests and validation failures.

For a zero replacement request, validation is skipped and status starts at zero.

For a nonzero replacement request, F-eef328c1181f receives the group selector and replacement request. A nonzero signed 32-bit result becomes the return status: the function proceeds directly to cleanup without performing its subsequent global captures or table accesses.

A zero validation result permits the update path to continue with status zero. Because validation precedes the global captures, any changes it makes to those globals can affect the update.

### Capturing state and reading the entry

The function then:

1. Captures the global notification word.
2. Captures the global context address.
3. Computes the selected entry address from the table globals and selectors.
4. Reads the unsigned 32-bit field at entry offset `8`.

The context address, notification word, and computed entry address are retained. They are not explicitly refreshed from their globals after later calls. The relative order of individual global reads within the address expression is not established.

Capturing the context address does not capture its contents: the context word at offset `20` is read separately at each notification.

### Processing an existing nonzero value

An initially read value of zero skips this phase entirely.

For a nonzero value:

- Values `1` and `2` set status to `18`.
- The message region is prepared with byte `0` equal to `5`, byte `8` equal to `0`, and its 32-bit value field equal to the initially read entry value.
- If that initially read unsigned value is at least `3`, F-c6c589453fa8 receives `2`, `0`, the message address, and length `12`.
- The entry field is then written with zero.
- Two addressable 32-bit words are prepared, containing `136` and a copy of the captured notification word.
- F-704f99fd5e22 receives, in order:
  1. A fresh 32-bit read from offset `20` of the captured context.
  2. The group selector.
  3. The address of the notification-word copy.
  4. The address of the word containing `136`.
  5. Zero.

The removal notification’s return is ignored.

The optional message call precedes the explicit clear; the removal notification follows it. Absent independent mutation, the message call therefore occurs while the old value is still installed, and the removal notification occurs after the field is zero.

Values `1` and `2` suppress only the message call. They do not suppress clearing or the removal notification.

The notification-word argument passed by address is a separate copy. A write through that pointer is not, by itself, a write to the separately captured word later passed by value.

### Acquiring and storing a replacement

A zero replacement request skips the entire replacement phase.

Otherwise, F-5449900ee365 receives the replacement request. Its result is assigned to the message region’s unsigned 32-bit value field. The body then reads that field and stores the value into the selected entry’s offset-`8` field.

At this point, the acquired value has been installed by the visible body. The function next writes message byte `8` to `1` and message byte `0` to `5`, then invokes the temporary object’s indirect operation with:

1. The temporary-object address.
2. The selected entry address.

No replacement message is sent before this dispatch.

### Classifying the current message value

After indirect dispatch returns, the function reads the message region’s current unsigned 32-bit value field:

- A value below `3` sets status to `18` and suppresses the replacement message call.
- A value at least `3` causes F-c6c589453fa8 to receive `2`, `0`, the same message-region address, and length `12`.

This comparison is not an entry reread. It is also not guaranteed to classify the originally acquired value.

If the removal phase called F-c6c589453fa8, that dependency has already received a pointer to this same message storage. Its pointer-retention behavior is unknown. An intervening dependency could use such retained access to change the message value before classification, without changing the entry.

Thus, acquiring and storing `9` does not unconditionally require the replacement message path. If dispatch causes the retained message value to become `2`, the comparison sets status `18` and no replacement message is sent, even if the entry remains `9`.

Under an explicit assumption that the message value is not changed between acquisition assignment and classification, classification uses the acquired value. Without that assumption, the post-dispatch message value controls.

If a replacement message call occurs, it receives the message region as it then exists. Earlier assignments of the tag and indicator do not prove those bytes remain unchanged after a dependency capable of accessing the region.

Changing only the entry during dispatch does not change the message value through any visible operation: the body does not reload the entry.

### Final notification and cleanup

The replacement phase always reaches F-43ce968102ca after classification, provided preceding calls return normally. Its arguments are:

1. A fresh 32-bit read from offset `20` of the captured context.
2. The group selector.
3. The captured notification word, by value.
4. `136`.
5. Zero.
6. `200`.

A nonzero result sets status to `2`; zero leaves the current status unchanged.

Neither low-value classification nor a nonzero final-notification result causes a visible rollback.

Finally, F-ec22bd8215d3 receives the temporary-object address, and the selected status is returned. Cleanup occurs on all explicitly shown normal exits, including validation rejection. This does not establish cleanup after faults, exceptions, nonreturning calls, or other nonlocal exits.

## Side effects

### Direct writes

The visible body can write the selected entry field twice:

- Zero, when the initially read value was nonzero.
- The acquired replacement, when replacement was requested and validation succeeded.

Dependency calls occur between these writes. The replacement need not remain installed if a dependency independently modifies the entry.

No direct writes to the other entry fields or the four globals are visible. Their preservation across calls is not established.

### Observable ordering

When both the existing value and the post-dispatch message value are at least `3`, and replacement is requested, the normal sequence is:

1. Initialize temporary object.
2. Validate.
3. Capture globals and read entry.
4. Send removal message.
5. Clear entry.
6. Issue removal notification.
7. Acquire replacement.
8. Assign acquired value to message field and store it in the entry.
9. Prepare replacement indicator and tag.
10. Invoke indirect dispatch.
11. Read and classify the current message value.
12. Send replacement message.
13. Issue final notification.
14. Clean up.

Conditional omissions preserve the order of remaining operations.

### Aliasing, ownership, and lifetime

The removal and replacement messages use the same temporary region. A removal message call therefore exposes storage later reused for acquisition, replacement preparation, and classification.

The temporary object and notification argument words are also addressable temporary storage. Passing these addresses establishes neither ownership transfer nor a promise that dependencies copy, preserve, or release anything.

Whether a dependency retains a pointer is unknown. This uncertainty matters during the function as well as after return. No lifetime extension beyond the function’s temporary storage is established.

The visible body supplies no synchronization or transactional protection.

- An initially read entry value of `0x80000000` qualifies for the removal message because the comparison is unsigned.

- If dispatch changes only the entry after storing `9`, and leaves the message region unchanged, classification and the replacement message still use message value `9`.
- Replacing the context global after capture does not redirect later explicit context reads. Changing offset `20` within the captured context can change the later notification argument.

## Evidence

Established behavior follows from the supplied static body’s branches, explicit byte and 32-bit accesses, unsigned comparisons, call arguments, address displacements, and normal cleanup path.

In particular, the replacement result is assigned to the addressable message value field, then stored in the entry. Indirect dispatch intervenes before a later comparison reads that message field. The same message address can already have been supplied during removal. These facts establish the distinction between the acquired-value store and the post-dispatch classification; they do not establish that retained-pointer mutation actually occurs.

No runtime tests, execution traces, or implementation-level verification have been performed.
