# F-f7426a02ebb4

## Purpose

F-f7426a02ebb4 conditionally updates a shared state object using a three-byte unsigned value obtained through a caller-supplied object. It first validates a descriptor and a separate selector, then checks the decoded value against a global comparison value and two fixed sets of permitted values. On acceptance, it invokes three dependencies, with two state-field writes between the first and second calls.

The numeric values resemble common audio sampling rates. That is **inferred intent**, not an established interface meaning. The contract below therefore calls the decoded quantity the **candidate value**.

The function returns the 32-bit value zero after the accepted path completes normally. Explicit rejection returns the 32-bit bit pattern `0xFFFFFFFF`. No other ordinary return value is visible in the supplied evidence.

## Interface

### Inputs

The function has three inputs in the supplied representation:

1. **Object address:** a 32-bit integer used as the address of a readable object. Its field at byte offset `0x18` holds a pointer to the candidate-value bytes.
2. **Descriptor address:** a 32-bit unsigned value initially used as an address. The function accesses a 16-bit field beginning at byte offset `2`, and conditionally a byte at offset `1`.
3. **Selector:** a 32-bit signed integer compared for exact equality with `3`.

Although the second input is later replaced internally by a decoded byte, its initial use is as an address, not as a scalar descriptor value.

## Behavior

### 1. Capture the state reference and inspect the descriptor

The function first reads the shared-state reference and retains that address for later operations. This happens before descriptor validation, including on paths that subsequently reject the request.

It then reads the descriptor’s 16-bit field at offset `2`. It shifts that unsigned value right by eight bits and requires the result to equal `1`. Consequently, the numeric field must be in the inclusive range `0x0100` through `0x01FF`; its lower eight bits do not affect this check.

This is a native 16-bit load. The evidence does not justify equating its upper byte with a particular descriptor byte address without a target byte-order assumption.

Only if that check succeeds does the function read the descriptor byte at offset `1`. That byte must equal `1`. If the 16-bit check fails, the offset-`1` byte is not read.

The selector must also equal `3`. Failure of any of these conditions returns `0xFFFFFFFF` before reading the caller object’s candidate pointer or invoking any dependency.

A selector other than `3` does not avoid the earlier descriptor accesses. Descriptor inspection precedes the combined rejection decision.

### 2. Obtain and decode the candidate

After the descriptor and selector checks pass, the function reads a pointer from the caller object at offset `0x18`.

It obtains three bytes from that pointer and constructs the candidate as:

- byte at offset `0`: bits `7:0`;
- byte at offset `1`: bits `15:8`;
- byte at offset `2`: bits `23:16`.

Thus the candidate is explicitly little-endian regardless of the byte order used for native multi-byte accesses elsewhere. Its range is `0` through `16,777,215`, inclusive. It is zero-extended to 32 bits; no sign extension or scaling is applied.

The source expression establishes the three byte contributions, but not a reliable relative execution order among the three individual byte reads. Their ordering must not be used as a device-I/O or synchronization guarantee.

### 3. Validate the candidate

A candidate equal to the global comparison value is accepted without any fixed-set membership check.

When unequal, the function compares the candidate and comparison value as **signed 32-bit integers**:

- If the candidate is smaller, it is accepted only if it belongs to the lower set: **8,000; 11,025; 12,000; 16,000**.
- Otherwise, it is accepted only if it belongs to the upper set: **24,000; 32,000; 44,100; 48,000**.

A failed membership check returns `0xFFFFFFFF` before any dependency invocation or direct state-field write.

Every candidate is below `2²⁴`, so its signed 32-bit interpretation is always nonnegative and numerically unchanged. The comparison value is not constrained in the supplied evidence. If its high bit is set, its signed interpretation is negative, and every possible candidate takes the upper-set branch after failing equality.

For a comparison value that remains stable throughout validation, acceptance is exactly the union of:

- equality with that comparison value;
- membership in the lower set while signed-smaller than it;
- membership in the upper set while signed-larger than it.

The fixed sets are therefore **not** an unconditional whitelist. A listed value can be rejected if the comparison value places it on the opposite branch. Conversely, equality can accept a value outside both sets.

The evidence contains separate uses of the comparison global. It does not establish a single captured snapshot or synchronization against concurrent changes. The stable-value rule above is conditional on stability.

### 4. Execute the accepted-path effects

After validation succeeds, the function performs these operations in order:

1. Reads the shared-state reference again, reads the 32-bit field at offset `0x0C` from that currently referenced object, and passes the field value to **F-338d16f9ce72**.
2. After that call returns normally, writes 32-bit zero to offset `0x14` of the state object captured at entry.
3. Writes the candidate as a 32-bit unsigned value to offset `0x10` of that captured object.
4. Reads the 32-bit field at offset `0x0C` from the captured object and passes it to **F-1333331b2da1**.
5. After that call returns normally, reads the 32-bit field at offset `0x04` from the captured object and calls **F-5602e6ff7e58** with that value and the integer constant `0x81`.
6. After the third call returns normally, returns zero.

The first dependency’s state object is selected through a fresh global read. Subsequent direct accesses use the address captured at entry. If those addresses differ, the first dependency argument can come from a different object than the object receiving the two writes and supplying the later arguments.

The later field reads are not snapshots taken before the dependencies run. Changes made by an earlier dependency can affect the arguments supplied to a later one.

## Side effects

The only explicit writes by this function are, on the accepted path:

1. A 32-bit zero at captured-state offset `0x14`.
2. A 32-bit candidate value at captured-state offset `0x10`.

That order is established. The first dependency executes before either write; the second executes after both writes.

No direct writes to the descriptor, caller object, or candidate byte sequence are shown. No direct update of the shared-state reference or comparison global is shown.

On an explicit rejection path, the function performs no direct writes and calls none of the three dependencies. It can still have performed reads, including the initial shared-state-reference read and descriptor reads.

## Acceptance examples

These are conditional contract examples, not runtime observations. Unless stated otherwise, assume valid accessible memory, stable comparison and state-reference globals, descriptor checks passing, selector `3`, and normally returning dependencies.

### Descriptor rejection

If the native 16-bit descriptor field equals `0x0200`, the result is `0xFFFFFFFF`. The descriptor byte at offset `1` is not read, and neither the caller-object pointer nor any dependency is reached.

If that field equals `0x01AB`, its check passes. An offset-`1` byte of `2` still causes rejection.

If both descriptor checks pass but the selector is `4`, the function rejects without reading the candidate pointer. The descriptor has already been inspected.

### Explicit byte decoding

Candidate bytes `0x44`, `0xAC`, `0x00` at offsets `0`, `1`, and `2` decode to `44,100`. They do not decode to a native-endian 16-bit field or a sign-extended quantity.

If the comparison value is `22,050`, this candidate is above it and belongs to the upper set, so the accepted-path effects occur.

### Equality bypasses fixed-set membership

With a stable comparison value of `12,345`, bytes encoding `12,345` are accepted even though that number belongs to neither fixed set.

With a stable comparison value of zero, an all-zero candidate is likewise accepted by equality.

### Branch-dependent membership

With comparison value `22,050`:

- `8,000` is accepted through the lower set.
- `48,000` is accepted through the upper set.
- `20,000` is rejected.

With comparison value `7,000`, candidate `8,000` is rejected: it reaches the upper-set branch, which does not contain `8,000`.

With comparison value `50,000`, candidate `48,000` is rejected: it reaches the lower-set branch, which does not contain `48,000`.

### Signed comparison boundary

With comparison bit pattern `0xFFFFFFFF`, equality is impossible for a 24-bit candidate. Its signed interpretation is negative, so all candidates reach the upper-set branch. Candidate `24,000` is accepted; candidate `16,000` is rejected.

### Accepted-path state visibility

For an accepted candidate of `32,000`, the first dependency is called before the function writes zero to captured-state offset `0x14` and `32,000` to offset `0x10`. The second dependency follows those writes.

If the first dependency changes the captured object’s offset-`0x0C` field and returns normally, the second dependency receives the field’s subsequently read value, not a saved earlier value.
