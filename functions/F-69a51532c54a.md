# F-69a51532c54a

## Purpose

F-69a51532c54a processes two selector bytes captured from shared storage. Each selector determines a callback descriptor and, if further processing is enabled, a metadata entry. A callback returning zero enables a status-consistency check and payload validation. Nonzero validation enables an external operation; returning from that operation adds the selector’s bit to a 32-bit accumulated mask.

After both selectors have been processed, a nonzero mask is passed with the original input to F-55b77747959b. That dependency supplies the function’s result. If no bits are accumulated, the result is zero.

These are established control-flow relationships. Describing the selectors as events, the payload as a message, or the external operation as publication would be inferred intent, not an interface guarantee.

## Interface

### Input and result

The function accepts one 32-bit input used as an address-like context value. Selector-specific receiver addresses are derived from it using signed displacement arithmetic. The original, unadjusted input is retained for the final call to F-55b77747959b.

The function returns a 32-bit quantity:

- Zero when the accumulated mask remains zero.
- The result of F-55b77747959b when the accumulated mask is nonzero.

No separate local error result is assigned for a nonzero callback result, zero validation result, or status mismatch. Those outcomes affect control flow instead.

The function does not check whether the input or derived addresses are valid, aligned, mapped, or associated with suitable objects. Valid shared storage, descriptors, receiver memory, metadata, and callable targets are execution preconditions. The supplied representation does not establish behavior for invalid accesses or address arithmetic outside the target’s supported range.

### Selector snapshot

One 32-bit value is copied from memory reached through a shared selector-storage pointer. The function processes only the first two bytes of that local copy, in increasing address order.

Thus:

- Both selectors belong to the same four-byte capture.
- Shared selector storage is not reread for the second iteration.
- The other two captured bytes do not select work.
- The relationship between these bytes and the numerical high or low portions of the captured word depends on target byte order.

The capture is not shown to be atomic or synchronized with concurrent writers.

The descriptor-table base is read during each iteration. It is not captured once for both selectors.

## Behavior

### Capture and iteration

Before processing selectors, the function captures the metadata-table base, initializes its result and 32-bit mask to zero, and copies the four-byte selector value into local storage.

The metadata-table base and captured selector bytes remain fixed within the invocation. This does not make the metadata entries immutable: dependencies may modify memory reached through the captured base.

Processing proceeds in captured-byte order: first byte, then second byte. Both positions are processed under ordinary returning execution, including when their selector values are equal. A successful contribution from the first selector does not end processing early.

The iteration position advances with an eight-bit mask. Starting at zero and continuing while below two produces exactly two iterations.

### Receiver calculation and dispatch ordering

The current selector is interpreted as signed eight-bit for descriptor indexing, using an eight-byte stride from the descriptor-table base read for that iteration. Both descriptor words are loaded before receiver-based indirect dispatch.

The second descriptor word serves two purposes:

- Its least significant bit selects direct or indirect dispatch.
- Interpreted as signed 32-bit and shifted arithmetically right by one, it supplies the displacement added to the original input to form the receiver address.

The response initialization is deliberately split around callback target resolution. After computing the adjusted receiver, the function writes status value 1 at response offset 0. Only then does it perform any indirect dispatch reads through the receiver.

For direct dispatch, the first descriptor word supplies the callback address, and no receiver-based lookup is performed.

For indirect dispatch, the function reads a 32-bit value from the adjusted receiver. It clears the low two bits of the first descriptor word, adds that masked value to the receiver-derived value, and reads the callback address from the resulting location.

After the callback address has been resolved, the function writes the original selector byte at response offset 1 and invokes the callback.

Consequently, the observable ordering is:

- Receiver computation precedes status initialization.
- Status initialization precedes both receiver-based reads used for indirect dispatch.
- Callback target resolution precedes selector initialization.
- Both response initializations precede the callback.

An indirect dispatch access can therefore fail after response offset 0 has been set to 1 but before response offset 1 has been initialized for the current iteration. Descriptor accesses occur earlier and can fail before either current-iteration initialization. On the second iteration, offset 1 may still contain a value left by the first iteration until the new selector write occurs.

“Virtual dispatch” is a possible interpretation of the indirect form, but no particular language object model is required by the established behavior.

### Callback invocation and result

The resolved callback receives two arguments:

- The adjusted receiver address.
- The response-storage address at offset 0.

Its 32-bit result is tested only for equality to zero.

A nonzero result skips status checking, validation, and the external operation for that selector. Processing then advances to the next captured selector, if any.

A zero result enables status checking. The callback may have modified the response, including status and payload. Modifying response offset 1 does not change the selector retained by the function: subsequent metadata indexing and bit selection still use the original captured byte.

The payload region is not cleared before either callback. Bytes not initialized by a dependency have no established usable contents. Reuse of the same response region also means later processing may encounter bytes left by earlier processing.

### Status consistency

After a zero callback result, the function locates a metadata entry using the signed eight-bit selector and a 12-byte stride from the metadata-table base captured at entry.

The observed metadata fields are:

| Offset | Width | Use |
|---|---:|---|
| 4 | 32 bits | First argument to validation and the external operation |
| 8 | 1 byte | Expected value for response status minus one |

The status comparison does not perform wrapping eight-bit subtraction. The response status byte is promoted for subtraction, and the result is compared as an unsigned 32-bit quantity against the metadata byte.

Established boundary cases are:

- Status 1 matches metadata byte 0.
- Status 255 matches metadata byte 254.
- Status 0 produces comparison value 4,294,967,295 and matches no metadata byte.
- Metadata byte 255 cannot match any possible response status byte.

On mismatch, the function calls F-a817d8d58c10 without explicit arguments. The supplied static annotation marks this dependency as non-returning. Normal continuation after a mismatch is therefore not established.

If that annotation is inaccurate and the dependency returns normally, the visible continuation proceeds to validation. There is no explicit local return or alternate branch after the mismatch call. Because the dependency implementation is unavailable, no preservation of metadata, payload, or other state may be assumed in that case.

### Validation and external operation

When execution reaches validation, the function reads the 32-bit metadata field at offset 4 and passes it, together with the payload address, to F-7f14f1ab6851.

A zero validation result skips the external operation and leaves the mask unchanged.

A nonzero result enables an external operation whose opaque function ID is unavailable in the supplied dependency map. That operation receives the same payload address but a fresh read of the metadata field at offset 4.

The two metadata reads are distinct. If validation changes the field, the external operation receives the later value. If validation changes the payload, the external operation receives the payload in its modified state; there is no intervening restoration or copy.

After the external operation returns, the function adds the selector’s bit to the 32-bit mask using bitwise OR. The operation’s return value is not tested. Returning from the operation, rather than any observed success result, is what permits the mask update.

The bit position uses the original selector byte interpreted as unsigned, unlike signed table indexing. For selector values 0 through 31, the corresponding position in a 32-bit mask is identifiable. Exact target shift semantics and language-level guarantees at the high-bit boundary are not supplied. Counts of 32 or greater must not be assumed to wrap, mask, saturate, or be rejected.

If the external operation does not return, its bit contribution and all later processing are not reached.

### Final dispatch

Once both iterations complete, a nonzero mask causes exactly one call to F-55b77747959b with the original input and accumulated mask. Its 32-bit result is returned without further interpretation.

A zero mask suppresses that call and leaves the function’s result zero.

Repeated selectors can cause repeated callbacks, validations, and external operations. Their bit contributions combine by OR; repeated contributions do not create a count.

## Acceptance examples

These are conditional static expectations, not executed tests.

1. **Both callbacks return nonzero.**  
   With valid dispatch inputs and both callbacks returning normally, both are invoked in captured-selector order. Neither iteration checks status or invokes validation or the external operation. The final dependency is not called, and the function returns zero.

2. **Indirect dispatch fails during receiver access.**  
   Suppose descriptor reads and receiver computation complete, indirect dispatch is selected, and the receiver read fails. Status has already been set to 1. The current selector has not yet been written to response offset 1, and the callback has not been invoked.

3. **Indirect target read fails.**  
   Suppose the receiver read succeeds but the subsequent callback-address read fails. Status initialization has occurred, but current-iteration selector initialization and callback invocation have not.

4. **Matching status with zero validation.**  
   A callback returns zero with status 1, and the metadata comparison byte is 0. Validation is reached. If validation returns zero, that iteration performs no external operation and contributes no bit.

5. **Two distinct contributions.**  
   Captured selectors are 2 and 5. Both callbacks return zero, both status checks match, both validations return nonzero, and both external operations return. F-55b77747959b receives the original input and mask 36. Its result becomes the function result.

6. **Duplicate contributions.**  
   Both selectors are 3, and both iterations return from the external operation. The callback and enabled dependencies execute twice. The final mask is 8, not 16.

7. **Status boundaries.**  
   Status 255 matches metadata byte 254. Status 0 matches no metadata byte, and metadata byte 255 matches no status. A mismatch calls F-a817d8d58c10 before validation.

8. **Validation changes metadata or payload.**  
   Validation receives the initially read metadata argument, modifies that field or the payload, and returns nonzero. The external operation receives the reread field and the current payload, not preserved copies.

9. **Callback changes the response selector.**  
   A callback overwrites response offset 1. Metadata selection and any bit contribution still use the original captured selector.

10. **High-bit selector.**  
    A selector byte of 255 indexes both tables as −1. If processing reaches the bit update, the shift count is 255. Its result remains documented_only; no wrapped bit position is promised.
