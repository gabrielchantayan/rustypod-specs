## Behavior

### Initialization

Before making any dependency call, the function:

1. Reads the 32-bit state address at offset 0x1c from the object identified by the first argument.
2. Reads the 32-bit value at offset 0x08 from that state address.
3. Places the latter value in a local current-position cell.
4. Initializes a separate local bookkeeping cell from the third argument.

The initial state address is not itself retained as the authoritative value for every later probe. The field at offset 0x1c is read again at the start of the first iteration and every subsequent iteration.

Initialization therefore requires both the outer object field and the state-relative field to be readable before any dependency has an opportunity to validate them.

### Probe and termination

At the beginning of each iteration, the function reads the first argument’s field at offset 0x1c again and stores its 32-bit contents in a local state-snapshot cell.

It then calls F-d5d901ed9cd8 with:

- the address of the local current-position cell; and
- the address of the local state-snapshot cell.

Both arguments are addresses of local storage, rather than copies of the values alone. The dependency can therefore affect the values subsequently observed through those cells.

After the probe returns:

- A result of exactly 1 ends the function immediately.
- Any other result continues the iteration.

In particular, zero, negative values, and positive values other than 1 are not recognized as stop results. The function does not implement a general “nonzero means finished” rule or a separate error-result branch.

On the terminating path, it does not read the current position’s offset-0x14 field, call the action dependency, or call the advancement dependency. Initialization and that iteration’s fresh state-field read have already occurred.

### Action

When the probe result is not 1, the function uses the current-position value as it exists **after the probe returns**.

It reads four bytes at offset 0x14 from that position and calls F-c90084728f7b with:

- the value just read; and
- the original second argument’s 32-bit value.

Consequently, a probe that changes the current-position cell changes which position supplies the action argument.

The action dependency’s return value does not control any explicit branch or assignment in this function. Its effects are otherwise unspecified. In particular, the contract does not assume that it preserves shared state, retains no references, or leaves objects alive.

### Advancement and bookkeeping

After the action returns, the function reads the current-position cell again and saves that value locally. This read is distinct from the earlier use of the position to obtain the action argument.

The function then calls F-2b3097eaee8e with the address of the current-position cell. The dependency can replace the current-position value through that address.

After advancement returns, the function stores the pre-advancement saved value into the bookkeeping cell that was initially populated from the third argument. It then starts the next iteration.

No explicit subsequent read of that bookkeeping cell is shown. It is not passed directly to any dependency.

The distinction between the two current-position observations matters: if the action can modify that cell through an alias previously obtained by a dependency, the value saved before advancement need not be the position used for the action’s field read. The evidence does not establish that such aliasing occurs, but it also does not justify assuming preservation.

### Repeated-state behavior

The function maintains its current position across iterations, subject to dependency modifications. It does not reload that position from the state-relative offset 0x08 on each iteration.

Conversely, the outer object’s offset-0x1c field is reloaded before every probe. A dependency-induced change to that field can therefore affect the next probe without automatically resetting the current-position cell.

There is no local iteration limit, cycle detector, null-position check, or progress check. If probes continue returning values other than 1 and all operations continue returning normally, the loop continues.
