# F-eaf6a501584f

## Purpose

The visible operation is an ordered sequence of word stores, byte-addressed accesses, and indirect calls. It accepts a 32-bit payload and an integer selector, also consumes inherited machine state, and derives later memory addresses and byte values from call results.

The established behavior is mechanical rather than semantic: two indexed word stores occur before four byte stores interleaved with 36 calls. The available evidence does not establish that these accesses implement a particular device protocol, data structure, allocator, or application operation.

The recovered sequence ends at an invalid-instruction boundary. Successful return, a return value, and behavior beyond that boundary are not established.

This contract distinguishes:

- **Static evidence:** operations and ordering directly represented in the supplied material.
- **Inferred intent:** possible interpretation, not an acceptance requirement.
- **Documented-only unknowns:** behavior that cannot be established without additional implementation or platform evidence.

All descriptions are conditional on execution reaching the relevant operation.

### Width and arithmetic conventions

The recovered representation uses 32-bit words and 8-bit bytes. Byte reads are unsigned: they produce values from 0 through 255. A byte write retains the low eight bits of its supplied value.

Unsigned shifts and products described below are 32-bit operations. In particular:

- Shifting the inherited unsigned word right by three is logical.
- Multiplying that word by `0x80000` retains the low 32 bits.
- Multiplying an unsigned call result by eight retains the low 32 bits.
- Unsigned left shifts by two retain the low 32 bits.

Some address and call-argument expressions instead involve recovered signed integers. Their behavior on overflow, or on left-shifting negative values, cannot be settled from this material. Where useful, examples explicitly assume ordinary wrapping 32-bit machine arithmetic; that assumption is not an unconditional language-level guarantee.

This does not guarantee the address retained the original payload until then: intervening calls may also modify it.

### Payload extraction

If the first payload is `0x12345678`, its first byte store writes `0xE0`, while its second byte store writes `0x23`.

F-000000000013 receives `0x48D159E0`, not `0xE0`.

If the second payload is `0xABCDEF01`, its two byte stores write `0x04` and `0xBC`.

### Repeated source reads

If the first two reads from the original byte-source address return `0x20` and `0x30`, the corresponding stores target `0x31` and `0x41`.

Caching the first read and using `0x31` for both stores would not match the represented behavior.

### Cached argument survives aliasing

Suppose the inherited unsigned word is zero. The original byte-source address is then `0x01`.

If the third read returns `0xF0`, the third store targets `0x101`, and F-000000000025 receives `0x000000F0`. That argument is the retained source value regardless of later memory changes.

### Unsigned address multiplication

For inherited unsigned word `0x00002000`, multiplication by `0x80000` produces zero after 32-bit truncation. The original byte-source address is therefore `0x01`.

A wider, nontruncating multiplication would produce a different access and would not match this unsigned 32-bit expression.

### Interrupted execution
