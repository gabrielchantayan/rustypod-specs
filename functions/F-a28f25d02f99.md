# F-a28f25d02f99

## Purpose

F-a28f25d02f99 dispatches an input record through an ordered sequence of conditional calls associated with a receiver:

1. An optional notification.
2. An optional handler for a zero secondary discriminator.
3. One of two general handlers.
4. An optional receiver-matching handler.

Every result-bearing handler short-circuits the sequence when it returns nonzero. That exact integer becomes the function’s result. If all invoked result-bearing handlers return zero, the function returns zero. The notification’s result does not control continuation.

This establishes dispatch behavior, not application semantics. Describing a nonzero result as “handled,” assigning application-specific meanings to discriminator values, or identifying the receiver’s object class would be **inferred intent**, not established evidence.

### Path-dependent preconditions

Every location actually accessed must remain readable at the time of access. Each selected dispatch entry must be readable and identify a callable dependency compatible with the supplied arguments and observed result use.

The requirements are stage-specific:

- The record discriminator must be readable at entry and at each later stage that is reached.
- In **each of the first three stages only**, observing discriminator `0x16` causes a read of the payload address at record offset `0x08`, followed by a read of the secondary discriminator at payload offset `0x04`. Those locations must be usable for that stage.
- The notification requires receiver offset `0x108` to be readable only when its selection condition succeeds.
- A selected indirect handler requires the current receiver dispatch-table address and the selected entry to be usable.
- In the final stage, discriminator `0x0F` requires the integer values at record offset `0x08` and receiver offset `0x50` to be readable.
- In the final stage, discriminator `0x16` does **not** cause any payload-address or payload-content read. It therefore imposes no remaining payload-validity requirement.

Validity is not an entry-to-exit blanket requirement for every field. For example, a general handler may invalidate the payload, leave or set the record discriminator to `0x16`, and return zero. Provided the record discriminator remains readable, the remaining function body returns zero without accessing that payload.

The function contains no visible validation or recovery path for violated memory or callability requirements.

## Behavior

### Initial notification stage

The function first reads the primary discriminator at record offset `0x04`.

If it is not `0x16`, this stage does not read record offset `0x08` or any payload field.

If it is `0x16`, the function reads the payload address from record offset `0x08`, then reads the integer secondary discriminator at payload offset `0x04`. It subtracts `0x2500` and compares the result with `2`.

Under ordinary defined integer arithmetic, secondary discriminator `0x2502` satisfies that comparison. Computing its difference does not overflow. The supplied material does not establish a signed-overflow policy for other secondary values whose subtraction falls outside the integer range; the condition must not be generalized into a portable arithmetic guarantee for those cases.

When the condition succeeds:

1. The integer at receiver offset `0x108` is read.
2. That value is converted to a character type.
3. **F-opaque-A** is called with the receiver and the converted value.

The conversion occurs after the integer read. It does not demonstrate that the stored field is character-sized.

No subsequent branch depends on F-opaque-A’s result. If it returns normally, processing continues. The supplied evidence does not establish whether the dependency has a meaningful return value.

### Zero-secondary handler stage

The function reads the primary discriminator again after the notification stage, including after any notification call.

When this newly observed discriminator is `0x16`, it rereads the payload address and secondary discriminator. If the secondary discriminator is zero, the function resolves **F-opaque-B** from the current receiver dispatch table at offset `0x124` and calls it with the receiver and the original record address.

- A nonzero result is returned unchanged immediately.
- A zero result allows processing to continue.
- If the selection condition is false, the call is skipped.

This stage does not reuse the initial primary or secondary discriminator.

For unchanged data, the notification condition and the zero-secondary condition are mutually exclusive. Both calls can nevertheless occur in one invocation if F-opaque-A changes data used by this stage.

### General-handler stage

Unless F-opaque-B has returned nonzero, the function reads the primary discriminator again.

For discriminator `0x16`, it reads the current payload address and then the current secondary discriminator:

- Secondary discriminator `0x2A` selects **F-opaque-C**, using dispatch-table offset `0x10C`.
- Every other secondary value selects **F-opaque-D**, using dispatch-table offset `0x110`.

A primary discriminator other than `0x16` selects F-opaque-D without a payload read at this stage.

The selected dependency is called with the receiver and the original record address. Exactly one of F-opaque-C and F-opaque-D is invoked whenever this stage is reached.

A nonzero result is returned unchanged. A zero result permits the final stage.

### Final receiver-matching stage

After the selected general handler returns zero, the function reads the primary discriminator again.

If it is `0x0F`, the function reads, in the represented order:

1. The integer at record offset `0x08`.
2. The integer at receiver offset `0x50`.

If those values are equal, the function resolves **F-opaque-E** from the current receiver dispatch table at offset `0xE0` and calls it with the receiver and the original record address.

A nonzero result from F-opaque-E is returned unchanged. A zero result falls through to the function’s zero return.

If the primary discriminator is not `0x0F`, the function returns zero without reading either comparison field for this stage. In particular, observing `0x16` here does not cause the function to interpret record offset `0x08` as a payload address, read that address, or dereference a payload.

### Sequencing and mutation

Each stage obtains its selection data from memory when that stage executes. There is no retained entry-time snapshot governing the whole dispatch sequence.

A dependency that returns normally may therefore affect later selection by changing:

- The primary discriminator.
- The payload address or comparison value at record offset `0x08`.
- The payload’s secondary discriminator.
- Receiver comparison or notification fields.
- The receiver’s dispatch-table address or entries.

Dispatch targets are obtained at their respective call stages rather than all being selected before the first call. Later stages do not restore earlier values.

The selection conditions preceding a dependency call have already been evaluated when that call begins. Mutations by that dependency affect subsequent reads, not the completed selection that caused the call.

These are logical ordering observations from the supplied representation. They are not guarantees about machine-instruction scheduling, volatile accesses, atomicity, or behavior under concurrent mutation.

## Side effects

The visible body contains no explicit writes to caller-visible receiver, record, payload, or global storage. Its direct operations consist of reads, integer operations, comparisons, control flow, and dependency calls.

The calls themselves are observable effects. Additional effects inside dependencies are unknown.

The possible call order is:

1. F-opaque-A, conditionally.
2. F-opaque-B, conditionally.
3. Exactly one of F-opaque-C or F-opaque-D, unless F-opaque-B returned nonzero.
4. F-opaque-E, conditionally, only after a zero general-handler result.

At most four dependency calls occur on a normally returning path. There is no visible loop or retry.

### Ownership and lifetime

No explicit allocation, release, retention, ownership transfer, or object copy appears in this function. Passing an address to a dependency does not establish whether that dependency borrows, modifies, retains, or releases the referenced storage.

Continued execution requires only storage used by the remaining path to remain valid. For example:

- A nonzero result from F-opaque-B prevents all later general-selection and final-stage reads.
- A nonzero general-handler result prevents every final-stage read.
- A zero general-handler result requires another readable record discriminator.
- A final discriminator of `0x16` requires no remaining payload access.
- A final discriminator of `0x0F` requires the two comparison-field reads and, if they match, a usable receiver dispatch path.

The function performs no lifetime check before these later accesses.

### Errors and abnormal completion

Invalid memory, invalid call targets, dependency traps, exceptions, and dependencies that do not return have no visible recovery mechanism here. Zero is a normal fall-through result, not proof that nothing happened.

## Acceptance examples

These examples are conditional consequences of static evidence, not executed tests. Unless an example specifies mutation, assume valid reached memory and dependencies that leave relevant data unchanged.

### Ordinary record

For a primary discriminator other than `0x16` or `0x0F`:

- F-opaque-A and F-opaque-B are skipped.
- F-opaque-D is called without any payload read.
- If it returns zero, the function returns zero without calling F-opaque-E.

### Zero secondary discriminator

For primary discriminator `0x16` and secondary discriminator zero:

- F-opaque-A is skipped.
- F-opaque-B is called.
- If it returns `-7`, the function returns `-7` without selecting a general handler or performing final-stage reads.
- If it returns zero, F-opaque-D is called next.

### Special general selection

For primary discriminator `0x16` and secondary discriminator `0x2A`:

- F-opaque-A and F-opaque-B are skipped.
- F-opaque-C is selected instead of F-opaque-D.
- If it returns `9`, the function returns `9` without reading the final discriminator.

### Notification and continuation

For primary discriminator `0x16`, secondary discriminator `0x2502`, and receiver field `0x108` equal to `65`:

- F-opaque-A receives the receiver and character-converted value `65`.
- Its result does not stop dispatch.
- With relevant data unchanged, F-opaque-B is skipped and F-opaque-D is called.
- If F-opaque-D returns zero, the final stage sees `0x16` and returns zero without another payload read.

### Matching receiver

For primary discriminator `0x0F`, equal record and receiver comparison values, and a zero result from F-opaque-D:

- The final stage reads the comparison values and calls F-opaque-E.
- A result of `-3` from F-opaque-E becomes the function’s result unchanged.
- A zero result produces a zero function result.

If the comparison values differ, F-opaque-E is skipped.

### Notification changes later selection

Suppose the initial primary discriminator is `0x16` and the initial secondary discriminator is `0x2502`. If F-opaque-A changes the secondary discriminator to zero and returns normally, the second stage observes the new value and calls F-opaque-B.

If F-opaque-B then changes the secondary discriminator to `0x2A` and returns zero, the general stage selects F-opaque-C. Earlier observations do not override those rereads.

### General handler establishes a final match

If the selected general handler changes the primary discriminator to `0x0F`, establishes equal comparison values, and returns zero, the final stage calls F-opaque-E, regardless of which primary discriminator originally selected the general handler.

### Payload becomes invalid after general dispatch

Suppose the selected general handler invalidates the payload, sets or leaves the primary discriminator at `0x16`, and returns zero. Assume the record discriminator remains readable.

The final stage reads that discriminator and returns zero. It does not read record offset `0x08`, dereference the invalid payload, or read receiver offset `0x50`.

This example does not relax payload validity for earlier stages that observe `0x16`; those stages actually access it.
