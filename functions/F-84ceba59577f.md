# F-84ceba59577f

## Purpose

F-84ceba59577f obtains a candidate record from F-3317362fe54d, conditionally stores a caller-supplied 32-bit value in that record, performs ordered link updates through a previously selected anchor, and increments a 32-bit field in a separately saved state object.

The link updates are consistent with inserting a record immediately before an anchor in a doubly linked structure. That is inferred intent. The established behavior is the sequence of reads and writes described below; neither a complete list type nor a list-validity invariant is established.

The function reads the same global address-holding location three times before calling its dependency. Those reads have different uses. Their observed addresses are equal only if the global retains the same value across the reads. In particular, the object receiving the final increment is not necessarily the object from which the anchor was selected or the object passed to the dependency.

There is no explicit result, error-reporting branch, rollback, or visible ownership operation.

## Behavior

### Global observations and anchor selection

The visible order is:

1. Read the global and retain the resulting saved state address.
2. Read the global again to obtain the anchor-selection base.
3. Read the four-byte address field at anchor-selection base +16 and retain it as the saved anchor.
4. Read the global a third time to obtain the dependency state argument.
5. Call F-3317362fe54d.

The second read is not specified as reuse of the first. The third read is not specified as reuse of either earlier value.

If the global remains unchanged across all three observations, the saved state address, anchor-selection base, and dependency state argument are equal. If it changes, the function can select an anchor from one object, pass another address to the dependency, and eventually increment a field in the object identified by the first read.

The function does not reread the anchor-selection field after the dependency returns. It also does not reread the global to choose the target of the final increment.

The visible read order does not establish a synchronization contract or guarantee that concurrent mutation is supported.

### Dependency invocation

F-3317362fe54d receives five arguments, in this order:

1. The dependency state argument obtained by the third global read.
2. Zero.
3. The third explicit input.
4. The fourth explicit input.
5. The third explicit input again.

The returned value is treated as the candidate address.

No guarantee is established that the dependency preserves the global, any of the three observed objects, the saved anchor, or the candidate. Changes made by the dependency can affect later field reads. They do not, by themselves, replace the saved state address or saved anchor address retained by this function.

For example, changing the anchor-selection object’s +16 field during the call does not redirect the subsequent link operations. Invalidating the already selected anchor can instead prevent normal completion.

### Conditional payload store

After the dependency returns, the function tests whether the address two four-byte elements beyond the candidate is nonzero. This corresponds to an eight-byte displacement in the represented layout.

If that derived address is nonzero, the function stores the first input at candidate +8. If it is zero, only that store is skipped. The subsequent link writes and final increment remain on the visible execution path.

This is not a test that the candidate itself is nonzero:

- Under ordinary numeric address interpretation, a zero candidate gives a derived address of eight and therefore does not bypass the payload store.
- Under a wrapping 32-bit address interpretation, a candidate address of `0xFFFFFFF8` gives a zero derived address.

The latter observation is conditional on wrapping address arithmetic. It is not an established safe special case: the function still attempts subsequent accesses at candidate +0 and +4.

The intended purpose of the condition is unknown. It does not provide a visible allocation-failure return path.

### Ordered link operations

After the conditional payload store, the function performs these operations in order:

1. Write the saved anchor address to candidate +0.
2. Read the four-byte value at saved anchor +4, then write that value to candidate +4.
3. Read saved anchor +4 again, then write the candidate address to offset +0 of the object identified by this second read.
4. Write the candidate address to saved anchor +4.

The two reads of saved anchor +4 are separate observations. The function does not establish that they return the same value.

With stable, non-overlapping storage, both reads identify the same predecessor. Under that condition, the updates have the conventional insertion interpretation:

- Candidate +0 points to the anchor.
- Candidate +4 points to the former predecessor.
- The former predecessor’s +0 points to the candidate.
- Anchor +4 points to the candidate.

With overlapping storage, earlier writes can change later read targets or values. In particular, the payload store, the candidate +0 store, or the candidate +4 store may alter saved anchor +4 if the corresponding addresses overlap it. External mutation can also make the two anchor-field observations differ.

There is no visible traversal, link-consistency check, duplicate-membership check, or validation that the candidate is separate from existing records.

### Final state-field increment

After all link writes, the function reads the four-byte field at saved state address +20, adds one, and writes the result to the same field.

Only the address captured by the first global read selects this target. The anchor-selection base and dependency state argument do not replace it, even when either differs from the saved state address.

The value being incremented is read at this late point, not captured before the dependency call. Therefore:

- A dependency write to that field can change the value subsequently incremented.
- An overlapping link or payload write can change that value.
- A later change to the global does not redirect the increment.
- If execution stops before this operation, the increment is not performed.

The represented addition is a signed 32-bit integer addition. When the value read is within the range for which adding one is representable, the stored value is exactly that value plus one. The supplied evidence does not establish wrapping or another defined outcome at signed overflow. Overflow behavior remains documented_only.
