# F-7265777c1e19

## Purpose

F-7265777c1e19 performs an in-place rearrangement of pointer-linked records. Under a conventional binary-tree interpretation, it is a left rotation: a selected node’s right child is promoted, the selected node becomes that child’s left child, and the promoted child’s former left subtree is transferred to the selected node’s right side.

The structural interpretation is inferred intent. The established behavior is a sequence of 32-bit memory reads and writes, including a conditional update to an externally referenced slot. The function does not validate that its inputs form a tree.

The operation returns no result. Its observable result is the modified linkage in caller-supplied memory.

## Interface

### Inputs

The function accepts two machine-level arguments represented as 32-bit integers and used as addresses:

- **Context address:** identifies a record containing a 32-bit address at byte offset `0x10`.
- **Selected-node address:** identifies the record whose links will be rearranged.

The context’s field at `0x10` identifies another record. This contract calls that record the **anchor**. The anchor’s field at `0x04` is compared with the selected-node address and may be replaced with the promoted-node address.

The following field names are descriptive labels, not established source-level type declarations:

| Record | Byte offset | Width | Role in this operation |
|---|---:|---:|---|
| Context | `0x10` | 32 bits | Address of the anchor |
| Anchor | `0x04` | 32 bits | Distinguished node slot, inferred to be a root link |
| Node | `0x04` | 32 bits | Parent link |
| Node | `0x08` | 32 bits | Left link |
| Node | `0x0c` | 32 bits | Right link |

These are field-access requirements, not complete record layouts. No meaning is established for other offsets.

### Output

There is no return value or explicit status channel. The function neither reports validation failures nor indicates whether the selected node was found in a structurally valid tree.

### Required memory conditions

For the ordinary rotation interpretation:

- The context and selected-node addresses must identify accessible storage for the fields used.
- The selected node’s right link must identify an accessible, non-null promoted node.
- The promoted node must have readable left-link storage and writable parent-link and left-link storage.
- The anchor address read from the context must identify accessible storage at offset `0x04`.
- If the promoted node’s left link is nonzero when tested, the corresponding record must have writable parent-link storage.
- If the anchor’s distinguished slot does not equal the selected-node address, the selected node’s parent link must identify a record with a readable left link and a writable child slot.

No checks enforce these conditions.

A valid tree rotation additionally requires structurally consistent links, appropriate separation between records and fields, and no concurrent mutation of the participating links. Those are preconditions for the inferred tree semantics, not conditions verified by the function.

## Behavior

### Structural result for an ordinary, stable tree

Let the selected node be **S**, its original right child be **P**, and P’s original left child be **T**. Let S’s original parent be **A**.

For non-overlapping records whose links remain stable except for this operation, the resulting relationships are:

- S’s right link becomes T.
- If T is non-null, T’s parent link becomes S.
- P’s parent link becomes A.
- The incoming reference that previously selected S is redirected to P:
  - If the anchor’s distinguished slot equals S, that slot becomes P.
  - Otherwise, if A’s left link equals S, A’s left link becomes P.
  - Otherwise, A’s right link becomes P.
- P’s left link becomes S.
- S’s parent link becomes P.

In the final branch above, the function does **not** verify that A’s right link previously equalled S. The right slot is the unconditional fallback after the distinguished-slot and left-slot comparisons fail.

The operation does not itself change S’s left link or P’s right link. It does not inspect node payloads, ordering keys, heights, colors, counts, or balance factors.

### Observable access ordering

The function makes ordinary field accesses rather than presenting an atomic structural update. Their order matters for aliased storage, concurrent observers, and failures during access.

**Transfer of the promoted node’s left link comes first.** The function reads S’s right link to obtain P. It then reads P’s left link and writes that value into S’s right link. Only after that write does it read P’s left link again to decide whether a transferred child needs a parent-link update.

If this later read is nonzero, P’s left link is read again to obtain the address used for that parent-link write. The function writes S into the addressed record’s parent field. Thus, the pointer copied into S’s right link, the pointer tested for nonzero, and the pointer used as the write destination are not necessarily one captured value.

For stable, non-overlapping records these reads agree. Without that condition, the function provides no guarantee that they agree. In particular, the nonzero test does not independently validate the value obtained by the subsequent read.

**The promoted node’s parent is assigned before the incoming reference is redirected.** The function reads S’s parent link and copies it into P’s parent link. It next reads the context’s anchor address and examines the anchor’s distinguished slot.

If that slot equals S, the slot is replaced with P. Otherwise, the function reads S’s parent link again, inspects that parent record’s left link, and replaces either its left or its right link as described above. The parent address used for this branch is therefore not necessarily the same value previously copied into P’s parent field.

The context’s anchor address is consulted after the subtree-transfer writes and after P’s parent-link write. It is not established that the function captures all inputs before modifying memory.

**The final two writes complete the ordinary rotation.** P’s left link is set to S, followed by S’s parent link being set to P. These occur after the incoming reference has been redirected.

Consequently, the operation exposes intermediate linkage states. For example, the incoming reference can already identify P before P’s left link has been changed to S. No transactional or atomic-update behavior is established.

### Branch selection and precedence

The anchor comparison has precedence over the parent-child comparison. When the distinguished slot equals S, the function updates that slot without examining the old parent’s child links.

This distinction allows the distinguished-slot branch to operate without dereferencing S’s original parent address. The original parent value is still read from S and copied to P. It may be a null value or a sentinel address; the function does not interpret it further in that branch.

For a non-distinguished node:

- A matching left link selects the parent’s left slot.
- Every other left-link value selects the parent’s right slot.
- There is no search for S elsewhere in the structure.
- There is no consistency check between the selected node’s parent link and the parent’s existing children.

### Null links and malformed structures

A null transferred subtree is explicitly accommodated: when P’s left link is zero at the conditional test, the transferred-child parent update is skipped.

A null promoted node is not accommodated. S’s right-link value is used to access a left-link field without a preceding null check.

Likewise, a null anchor is not handled as an empty-tree indication. The function uses the anchor address to access its distinguished slot.

Cycles, self-links, shared subtrees, inconsistent parent links, and overlapping record storage are not rejected. They can cause the actual access sequence to diverge from the ordinary rotation result because an earlier write can change a field read later.

### Width and address arithmetic

Every explicit field access is four bytes wide. The displayed interface and link fields support a 32-bit address model; they do not establish a native-width, 64-bit pointer interface.

Field addresses are formed using fixed byte displacements: `0x04`, `0x08`, `0x0c`, and `0x10`. There are no element counts, loops, variable-length copies, or size calculations.

The function provides no explicit address-overflow checks. Exact behavior when an address-plus-offset exceeds the valid address range, is misaligned, or identifies inaccessible memory depends on the execution environment. Such cases are not supported normal-operation inputs.

## Side effects

Under the stable, non-overlapping tree preconditions, the function writes:

- S’s right link.
- T’s parent link, only when T is non-null.
- P’s parent link.
- Exactly one incoming-reference slot: the anchor’s distinguished slot, A’s left link, or A’s right link.
- P’s left link.
- S’s parent link.

The function therefore performs five four-byte writes when T is null and six when T is non-null. These counts describe write operations, not necessarily distinct memory locations if the caller supplies aliases.

There is no explicit allocation, deallocation, payload copy, or external call. Existing records are relinked; the function does not create or destroy nodes. No broader ownership transfer or lifetime policy is established.

There is no explicit synchronization, rollback, logging, or error handling. If an access fails after earlier writes, those earlier modifications have already occurred in the displayed sequence. Recovery behavior is unknown.

For ordinary distinct records, fields not listed as write targets remain untouched by the function. If storage overlaps, a write to one designated field can also alter memory serving another role.

## Acceptance examples

The following are conditional acceptance criteria derived from static evidence. They are not runtime test results.

### Distinguished node with a transferred subtree

Assume distinct, stable records with:

- The anchor’s distinguished slot equal to S.
- S’s right link equal to P.
- P’s left link equal to non-null T.
- S’s parent link equal to A.

On normal completion:

- The distinguished slot identifies P.
- P’s parent link equals A.
- P’s left link identifies S.
- S’s parent link identifies P.
- S’s right link identifies T.
- T’s parent link identifies S.

The old parent’s child slots are not inspected or updated through the non-distinguished branch.

### Non-distinguished left child

Assume the distinguished slot does not equal S and A’s left link equals S. With the remaining ordinary tree preconditions satisfied, A’s left link becomes P. A’s right link is not selected for the incoming-reference write.

The subtree transfer and final S/P parent-child relationship are otherwise the same as in the distinguished-node case.

### Non-distinguished right-side fallback

Assume the distinguished slot does not equal S and A’s left link does not equal S. The function writes P into A’s right link.

This remains the specified branch behavior even if A’s right link did not previously identify S. Acceptance as a valid tree rotation requires the caller to provide the missing structural consistency.

### Empty transferred subtree

Assume P’s left link is zero throughout the relevant reads. S’s right link becomes zero, and no transferred-child parent write occurs. The incoming reference is redirected, P becomes S’s parent, and S becomes P’s left child.

### Distinguished node with a null parent value

Assume the distinguished slot equals S and S’s parent field contains zero. With valid S, P, and anchor storage, zero is copied into P’s parent field. The function does not dereference that zero parent value in this branch.

### Missing promoted node

If S’s right link is zero, the input does not satisfy the required accessible-promoted-node condition. No successful no-op, error return, or preserved-state result is promised.

### Aliased records

If S and P designate the same storage, the ordinary rotation postconditions are not an appropriate acceptance oracle. Earlier writes affect later field reads. Such input must either be excluded by the caller’s structural contract or analyzed using the documented access ordering.
