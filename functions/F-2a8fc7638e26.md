# F-2a8fc7638e26

## Purpose

F-2a8fc7638e26 coordinates a multiprecision-style transformation followed by one of four output-decoding operations. It imports an input value, checks it against a bound held in an operation object, conditionally applies preparatory and finishing transformations, invokes an operation callback, exports the intermediate result to temporary storage, and passes that storage to the selected decoder.

The multiprecision and cryptographic interpretation is inferred from the call structure. The established contract is the sequence of calls, field accesses, branch conditions, resource handling, and returned values described below. The mathematical meaning of the transformation and the formats accepted by the four decoders are not established.

The ordinary failure result is signed 32-bit −1. A decoder’s negative result is returned unchanged after an error-reporting call and cleanup. Some failures invoke the error dependency; others do not.

## Interface

The function accepts five arguments and returns a signed 32-bit result.

| Argument | Representation and role |
|---|---|
| Input extent | Signed 32-bit quantity. Passed to the input-import dependency and compared, as signed, with the computed temporary-buffer extent. |
| Input reference | Opaque 32-bit value passed unchanged to the input-import dependency. Pointer validity and readable extent are requirements of that dependency. |
| Output reference | Opaque 32-bit value passed unchanged to the selected decoder. Destination layout and capacity requirements are not established here. |
| Operation-object reference | A 32-bit address used for direct field reads and passed to several dependencies and one callback variant. |
| Mode | Signed 32-bit selector. Exactly 1, 2, 3, and 4 select decoding operations. Other values are rejected only if execution reaches decoder selection. |

The input extent, input reference, and output reference are retained as argument values. The function does not copy the caller’s input or output storage merely by retaining those values.

The operation object has the following accessed layout. Offsets are byte offsets; each directly accessed field is 32 bits wide.

| Offset | Observed use |
|---|---|
| +8 | Reference to a callback table. |
| +16 | Opaque bound or modulus-like value; supplied to sizing, comparison, and one callback variant. |

## Behavior

### Initialization and context acquisition

The function begins with:

- Result set to −1.
- Temporary-buffer reference and extent set to zero.
- Selected state reference set to zero.
- A flag recording ownership of replacement state cleared.

It initializes the input work object first and the result work object second, using F-163f35978c12 for each. It then calls F-2a7d78c39bfc to obtain an opaque context.

A zero context skips all sizing and transformation work. Both work objects are still cleaned up, and the function returns −1. This path makes no explicit call to the error-reporting dependency.

### Temporary-buffer sizing and allocation

With a nonzero context, the function reads the operation-object field at +16 and passes its value to F-ae3bc1bfd2a8. The signed 32-bit result determines the temporary-buffer extent.

For values where the intermediate signed additions are representable, the extent is the signed result of dividing the sizing result plus seven by eight, with truncation toward zero. Thus:

- Sizing results 0, 1, 8, and 9 produce extents 0, 1, 1, and 2.
- A sizing result of −8 produces extent 0, not −1.
- A sizing result of −15 produces extent −1.

The displayed arithmetic includes sign adjustment before a right shift. It does not establish a portable overflow rule when the signed additions overflow. Ordinary nonnegative sizing results with a representable addition have the familiar ceiling-by-eight behavior.

The function calls F-43da6b23bd44 with the computed extent followed by two zero arguments. This call occurs before checking whether the extent is smaller than the input extent.

If the allocation result is zero, or the computed extent is signed-less-than the input extent, the function invokes F-4fc89ec41a6d with arguments 4 and 101, then proceeds to cleanup if that dependency returns. The result remains −1.

Negative input extents and negative computed extents receive no separate local rejection. Their eventual treatment depends on this signed comparison and on downstream dependencies.

### Input import and bound comparison

After allocation and the extent check succeed, F-3eaa60da10c7 receives:

1. The input reference.
2. The input extent.
3. The input work object.

A zero return stops processing without an explicit error-reporting call.

A nonzero return leads to F-c0985d8666ae, receiving the input work object and a freshly read operation-object field at +16. A return greater than or equal to zero invokes the error dependency with 4 and 101 and stops processing.

A negative comparison result permits further processing. Interpreting this as requiring an input value strictly below a bound is reasonable, but the comparator’s numeric semantics are not independently supplied.

### State acquisition and optional preparation

The function next reads flags at +60. If bit 0x80 is clear, it reads the state reference at +80. Only when that reference is zero does it call F-8bb113c5b25d with the operation object and context.

A zero result from that call stops processing without an explicit error report. A nonzero result does not itself become the selected state: the function subsequently reads operation-object offset +80 again.

It then rereads flags at +60:

- If bit 0x80 is clear, the selected state must be nonzero. A zero state invokes the error dependency and stops processing.
- If bit 0x80 is set, a zero selected state is permitted, and preparation is skipped.
- A nonzero selected state enters the same preparation path regardless of bit 0x80.

For a nonzero selected state, F-7eadd9e17dc6 is called. Its result is compared with the 32-bit field at state offset +16, read after that call.

If the values differ, F-22a808773769 receives the operation object and context. Its return replaces the selected state reference:

- Zero stops processing without an explicit error report.
- Nonzero is recorded as replacement state requiring later cleanup by F-3eadc90e0ec1.

The function then calls F-3959199a1859 with the input work object, selected state, and context. A zero result stops processing without an explicit error report.

No claim is made that these calls preserve the operation object, callback table, flags, or global state. Later reads occur at their stated points and may observe changes.

### Main callback selection and invocation

The function reads flags at +60 again. Bit 0x20 selects between two callback forms:

- If bit 0x20 is set, use the callback-table entry at +20.
- Otherwise, inspect the five operation-object fields at +28, +32, +36, +40, and +44 in that order. Reading stops at the first zero field.
- If all five fields are nonzero, use the entry at +20.
- If any inspected field is zero, use the entry at +24.

The +20 callback receives three arguments, in this order:

1. Result work object.
2. Input work object.
3. Operation-object reference.

The +24 callback receives six arguments:

1. Result work object.
2. Input work object.
3. Operation-object field at +24.
4. Operation-object field at +16.
5. Context.
6. Zero.

The exact relative evaluation order of the callback-table read and the operand-field reads within this latter call is not established. All are needed for that invocation.

A zero callback return stops processing without an explicit error-reporting call.

### Cleanup

On ordinary control-flow paths where dependencies return, cleanup occurs in this order:

1. If a context was acquired, call F-87ceecb12e6c with that context.
2. Clean up the input work object using F-12979315a90f.
3. Clean up the result work object using F-12979315a90f.
4. If replacement state was successfully acquired and recorded, call F-3eadc90e0ec1 with that state.
5. If the temporary-buffer reference is nonzero, call F-80308ee0e93f with the buffer and computed extent.
6. Call F-5990a26eaaa3 with that buffer.
7. Return the saved result.

A nonzero buffer is processed in this sequence even when the extent check failed immediately after allocation. A zero buffer is neither processed nor released by these final two calls.

The behavior of F-80308ee0e93f is opaque; calling it does not by itself establish that every allocated byte is erased.

## Side effects

The function directly initializes its own bookkeeping and performs the listed object-field reads. Input interpretation, work-object mutation, output writes, allocation, error-state changes, and possible operation-object mutation occur through dependencies.

The output reference is passed only to the selected decoder. That does not prove that earlier dependencies cannot reach or modify the same storage through aliases or global state. A decoder failure does not imply that output storage remains unchanged; there is no local rollback.

The function explicitly arranges cleanup for a nonzero context, its two work objects, the temporary buffer, and successfully acquired replacement state. State read directly from the operation object is not passed to the replacement-state cleanup dependency merely because it was used.

No explicit release is performed on the caller’s input reference, output reference, or operation-object reference. Dependency ownership and retention rules are not available. In particular, this function’s cleanup sequence does not establish that unknown callees neither retain nor release passed references.

No synchronization, reentrancy protection, or atomic object snapshot is present in the supplied body. Flags and other operation-object fields are reread at different stages.

## Acceptance examples

These are conditional acceptance criteria derived from static control flow, not executed tests. They assume dependencies return normally and that supplied references satisfy the dependencies’ requirements.

1. **Context unavailable.** If context acquisition returns zero, both work objects are initialized and subsequently cleaned up. No allocation, callback, decoder, or explicit error call occurs. The return is −1.

2. **Buffer too small after successful allocation.** If the sizing result is 17, the computed extent is 3. With input extent 4 and a nonzero allocation result, the error dependency receives 4 and 101. Import is not called. Cleanup includes processing and releasing the allocated buffer with extent 3.

3. **Equality rejected by comparison.** If import succeeds and comparison returns zero, preparation, callbacks, export, and decoding do not occur. The explicit error call occurs, followed by cleanup and return −1.

4. **State-free path.** If bit 0x80 is set when relevant flags are read and the selected state is zero, no state setup, state preparation, or state finishing call is required. Successful callback execution can proceed directly to export.

5. **Replacement state.** If selected state is nonzero and its +16 field differs from the value returned by F-7eadd9e17dc6, a nonzero replacement returned by F-22a808773769 is used for preparation and, if reached, finishing. It is cleaned up after both work objects, even if preparation or the callback fails.

6. **Short-circuit callback selection.** With bit 0x20 clear and the field at +28 zero, selection does not require reads of +32 through +44. The +24 callback form is used.

7. **Flag-selected callback.** With bit 0x20 set, the +20 callback form is used without checking the five nonzero-status fields.

8. **Negative decoder result.** If mode 2 reaches its decoder and that decoder returns −7, the error dependency is called, cleanup runs, and the function returns −7 rather than normalizing it to −1.

9. **Late unsupported-mode rejection.** If mode is 5 and all preceding stages succeed, export occurs before the error call. No decoder is called, and the return is −1.

10. **Early failure masks unsupported mode.** If mode is 5 but input import returns zero, the unsupported-mode check is never reached. There is no explicit error call on that path.

These unknowns do not justify adding local validation, assuming rollback, or treating dependency names as ownership guarantees.
