# F-1f7e737c20e5

## Purpose

F-1f7e737c20e5 performs an unconditional sequence of memory updates using implicit entry-state values, then transfers control through an unresolved indirect target. Its observable interface consists primarily of memory reads, byte and word writes, and the arguments supplied at that final transfer.

The supplied static evidence does not establish a higher-level purpose. In particular, repeated writes do not establish that the function initializes a collection: most repeated operations address the same locations.

This contract distinguishes:

- **Established static evidence:** accesses, widths, ordering, and data dependencies visible in the supplied representation.
- **Inferred intent:** possible interpretations that are not acceptance requirements.
- **documented_only:** behavior that cannot be resolved from the supplied evidence.

No runtime tests have been performed.

## Behavior

### Initial state publication

The primary-base word at offset `0x20` receives `0x20` before the anchor is loaded. The fixed word at `0x60` then receives `0x20`.

This ordering matters if the first destination overlaps the anchor’s source. The anchor is the value read after that first write, not necessarily the value present at function entry. After capture, subsequent uses of the anchor do not visibly reload its source.

A doubled secondary-base value supplies the word payload for the following repeated publication sequence.

### Repeated publication sequence

The opening publication uses the initial selector. It writes the doubled secondary-base value to the word starting at twice the initial selector plus `0x54`. It then publishes three associated values, in this order:

1. The primary base’s low byte at anchor offset `0x19`.
2. The anchor’s low byte at primary-base offset `0x11`.
3. Twice the initial selector at anchor offset `0x34`.

The subsequent repeated publications use the primary base instead of the initial selector. Each has the same ordered footprint:

| Position within a publication | Destination | Width | Value |
|---:|---|---:|---|
| 1 | Twice primary base plus `0x54` | Word | Doubled secondary base |
| 2 | Anchor plus `0x19` | Byte | Low byte of primary base |
| 3 | Primary base plus `0x11` | Byte | Low byte of anchor |
| 4 | Anchor plus `0x34` | Word | Doubled primary base |

The supplied representation contains a fixed, explicitly repeated sequence, not a data-dependent loop. There is no visible increment of the primary base, secondary base, anchor, or repeated destination.

Repeated writes are part of the represented access trace. A final-state-only implementation is not automatically equivalent where writes are externally observable or destinations overlap. The exact repetition count is **documented_only** in this contract; no numerical count is asserted.

### Capture and byte-field updates

After the repeated publications, the function captures:

- A word from fixed address `0xA9`.
- A word from twice the secondary base plus `0x74`.

It next writes a byte to fixed address `0x3A`. The stored byte is the low eight bits of twice the primary base’s low byte plus `0x30`. This is not established as digit formatting: the expression is not limited to decimal-digit results.

The function then captures a word from secondary-base offset `0x14` and a word from primary-base offset `0x04`.

The next update group has the following order:

- Secondary-base offset `0x0D` receives the primary base’s low byte.
- Primary-base offset `0x08` receives `0x6C`.
- Primary-base offsets `0x0D` and then `0x09` receive the anchor’s low byte.
- Secondary-base offset `0x54` receives the secondary base itself as a word.
- Fixed byte `0x67` receives the low byte of the previously captured word from `0xA9`.

These captured values must be distinguished from later memory contents. Subsequent writes can change their original storage without changing the already captured payloads.

### Link and word-field updates

A word is next read from secondary-base offset `0x44`; call this the **captured link word**.

The byte at `0x67` is propagated to fixed address `0x21`. Primary-base offset `0x10` receives the captured link word’s low byte, and anchor offset `0x54` receives the entire captured link word.

Secondary-base offset `0x01` then receives a byte derived by right-shifting the captured link word. The shift count comes from the primary base’s low byte. Signed-shift behavior and counts outside the 32-bit operand width require the qualifications under **Uncertainties**.

Anchor offset `0x54` is subsequently overwritten with the full primary-base value. Thus, when these accesses complete, its earlier captured-link write is not the last write to that location.

The function next captures a word from primary-base offset `0x40`. It stores the earlier primary-base-offset-`0x04` capture at anchor offset `0x74`, then writes the newly captured word across primary-base offsets `0x10` through `0x13`.

That full-word write overlaps the earlier byte writes at primary-base offsets `0x10` and `0x11`. Under ordinary memory semantics, the later word determines their resulting bytes; the byte values depend on target endianness.

The remaining updates in this group occur in this order:

| Destination | Width | Value source |
|---|---:|---|
| Anchor plus `0x44` | Word | Secondary base |
| Primary base plus `0x09` | Byte | Read of fixed byte `0x67` |
| Secondary base plus `0x09` | Byte | Low byte of primary base |
| Primary base plus `0x44` | Word | Captured word from fixed address `0xA9` |

### Derived-base updates

The word at primary-base offset `0x54` is now read and used as a new address base, called the **derived base**.

The next operations preserve these ordering constraints:

- Primary-base offset `0x09` again receives a read of fixed byte `0x67`.
- Derived-base offset `0x0D` receives the low byte of the earlier capture from twice the secondary base plus `0x74`.
- Secondary-base offset `0x54` receives the earlier captured word from secondary-base offset `0x14`.
- A word is captured from primary-base offset `0x14`.
- Secondary-base offset `0x11` receives the same byte used at derived-base offset `0x0D`.
- Primary-base offset `0x09` receives the derived base’s low byte.
- Primary-base offset `0x44` receives the full derived base.

The secondary-base word at offset `0x54` therefore has at least two distinct writes: the secondary base itself earlier, followed by a previously captured payload. Likewise, primary-base offset `0x44` receives the fixed-address capture before receiving the derived base.

### Final linkage and indirect transfer

A word read from secondary-base offset `0x04` supplies another base, called the **terminal base**.

The function writes the halfword value `0x0065` at twice the terminal base. This is a 16-bit write, not a word write.

A word from terminal-base offset `0x64` supplies a **terminal link**. The earlier capture from primary-base offset `0x14` contributes its low byte to derived-base offset `0x11`. Derived-base offset `0x54` then receives the word value 100 decimal, equivalent to `0x64`.

The final read-and-write group obtains:

- A word from terminal-base offset `0x74`, used as the fourth outgoing argument.
- A word from secondary-base offset `0x64`, called the **terminal destination**.

Secondary-base offset `0x09` receives the terminal base’s low byte. Terminal-destination offset `0x54` receives the terminal link. A word at twice the terminal link then receives the terminal destination.

Only after these writes does the unresolved indirect invocation occur. Its four visible arguments, in order, are:

1. `0x72`.
2. The terminal link.
3. The earlier captured word from secondary-base offset `0x14`.
4. The word captured from terminal-base offset `0x74`.

No visible condition suppresses this invocation once execution reaches it.

## Acceptance examples

### Ordinary disjoint storage

Assume all accesses are valid, all described regions are disjoint except for explicit same-base overlaps, arithmetic is representable, and the dependency has not yet executed.

At the indirect-transfer boundary:

- Primary-base offset `0x20` and fixed word `0x60` contain `0x20`.
- Anchor offset `0x34` contains twice the primary base.
- Anchor offset `0x54` contains the primary base, not the captured link word.
- Secondary-base offset `0x54` contains its earlier offset-`0x14` capture.
- Derived-base offset `0x54` contains 100 decimal.

These are boundary observations, not guaranteed post-return values after an unknown dependency executes.

### Low-byte truncation

If the primary base’s low byte is `0xF0`, the byte written at fixed address `0x3A` is `0x10`: twice `0xF0` plus `0x30` is `0x210`, whose low byte is `0x10`.

This example accepts byte truncation; it does not establish signed-overflow behavior elsewhere.

### Overlapping byte and word fields

Assume primary-base offset `0x40` supplies the word `0x11223344`. The later full-word store places that word at primary-base offset `0x10`, replacing the earlier byte-level contents across four bytes.

On a little-endian target, offsets `0x10` and `0x11` become `0x44` and `0x33`. On a big-endian target, they become `0x11` and `0x22`. Endianness is a condition of the example, not an established property.

### Safe shift case

If the captured link word is nonnegative and the primary base’s low byte is zero, secondary-base offset `0x01` receives the captured link word’s low byte. No assumption about oversized shift counts is required.

### Observable intermediate writes

If anchor offset `0x54` is monitored externally, observing only the final primary-base value is insufficient to establish trace equivalence. The preceding write of the captured link word must also be accounted for.
