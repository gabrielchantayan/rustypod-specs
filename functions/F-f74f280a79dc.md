# F-f74f280a79dc

## Purpose

F-f74f280a79dc derives one 32-bit result per input coordinate from a context-associated collection of lookup tables, then passes the resulting sequence to F-7913ee9e1fa0.

The established selection behavior is:

- An exact coordinate match selects the corresponding stored value.
- A coordinate preceding the first encountered breakpoint selects the first stored value.
- A coordinate exceeding all breakpoints selects the last stored value.
- A coordinate between encountered breakpoints invokes F-8f41f510c86c with three differences and uses that dependency’s return value directly.

Interpolation is an inferred purpose of the difference-based call, not an established numerical contract. In particular, this function does **not** visibly add the lower endpoint’s stored value to the dependency’s result.

If the context has no associated collection, or the collection’s count does not match the supplied count, the function returns the 32-bit value 6 without invoking either dependency.

## Interface

### Inputs

The function accepts three machine-word arguments:

1. **Context address.** A 32-bit address used to locate a collection pointer at byte offset `0x20C`.
2. **Requested count.** A 32-bit value compared for equality with the collection’s 32-bit count field.
3. **Coordinate-array address.** The base address of consecutive 32-bit signed coordinates, one per processed table.

Although the address arguments appear in integer-typed positions in the supplied representation, they are used as addresses. Their validity, alignment requirements, and address-space restrictions are caller-side prerequisites; this function does not check them.

The requested count is not independently checked for positivity or bounded by the local result capacity.

### Referenced layout

All offsets are byte offsets.

| Object | Location | Established use |
|---|---|---|
| Context | `0x20C` | 32-bit pointer to the collection |
| Collection | `0x04` | 32-bit count |
| Table descriptor for position *j* | `0x58 + 12 × j` | Unsigned 8-bit breakpoint count |
| Same descriptor | `0x5C + 12 × j` | 32-bit pointer to a breakpoint array |
| Same descriptor | `0x60 + 12 × j` | 32-bit pointer to a stored-value array |
| Coordinate array | `4 × j` | Signed 32-bit input coordinate |
| Breakpoint array | `4 × k` | Signed 32-bit breakpoint |
| Stored-value array | `4 × k` | 32-bit stored value |

The descriptor stride is 12 bytes. Only nine bytes of each descriptor have established meaning here: one count byte and two four-byte pointers. The intervening three bytes have no observed use in this function.

The implementation provides temporary storage for **16 consecutive 32-bit results**, totaling 64 bytes. This storage is not initialized wholesale.

### Output

The return value is a 32-bit word:

- `6` on the two initial rejection paths.
- Otherwise, exactly the return value of F-7913ee9e1fa0.

The meaning of `6` as an application-level status is unknown. It is not established that a successful dependency call cannot also return `6`.

## Behavior

### Admission and collection selection

The function first reads the collection pointer from the context at offset `0x20C`.

If that pointer is zero, processing stops and the function returns `6`. The requested count and coordinate-array contents do not cause further reads on this path.

If the pointer is nonzero, the function reads the collection’s count at offset `0x04`. A mismatch with the requested count also returns `6`.

This equality compares the 32-bit count representations. It is not a signed-positive-count validation. A requested count whose signed interpretation is negative can still match the stored bits.

The selected collection address is retained for subsequent processing. The function does not visibly reload the collection pointer from the context during the loop.

### Processing extent

Table positions are processed in increasing order, beginning with zero.

The loop compares its position against the collection count using an **unsigned 32-bit comparison**. The collection count is read again for loop continuation; processing is not visibly governed by an immutable copy of the count that passed the initial check.

Consequently, a mutation of the collection count during a dependency call can affect later iteration decisions. The initial equality check is not repeated.

For stable, valid inputs with a count between zero and 16 inclusive, the function produces that many temporary results. Counts greater than 16 are not rejected and can cause writes beyond the established temporary storage.

A stable zero count is accepted when the requested count is also zero. No coordinate or descriptor is processed, and F-7913ee9e1fa0 is still invoked with the address of the uninitialized temporary result storage.

### Per-table reads

For each table position, the function obtains:

1. The breakpoint-array pointer from that table’s descriptor.
2. The stored-value-array pointer from that descriptor.
3. The corresponding signed 32-bit coordinate from the coordinate array.

It then scans breakpoint positions from zero upward. The descriptor’s unsigned 8-bit breakpoint count controls the scan; the supplied representation reads this field as part of scan continuation rather than copying it once into a fixed table length.

The coordinate is read once for that table. The breakpoint and value pointers are also obtained before the scan and are not visibly reloaded from the descriptor during it.

The scan uses signed 32-bit comparisons between the coordinate and breakpoints.

### Exact match

At each visited breakpoint, equality is checked before the “coordinate is smaller” condition.

If a breakpoint equals the coordinate:

- The function reads the stored value at the same position.
- That 32-bit word becomes the table’s result.
- No difference-based dependency call occurs for that table.
- No later breakpoint is examined for that table.

With duplicate breakpoint values, the first matching entry reached by the scan wins. There is no search for a later duplicate.

### Below-range selection

If the coordinate is smaller than the first breakpoint, the first stored value becomes the result.

The same first-value selection also occurs when the breakpoint count is zero. In that case, no breakpoint is read, but the function still dereferences the stored-value pointer at position zero.

Therefore, a zero breakpoint count does **not** make a table inert or safe with a null value pointer. The function has no empty-table error return.

### Above-range selection

If the scan exhausts a nonempty table without finding equality or an earlier larger breakpoint, the function selects the stored value at the last position, using the descriptor’s breakpoint count minus one.

For a stable, strictly increasing table, this is the ordinary upper-end clamp.

The descriptor’s count is read for this last-position calculation. Its value is not established to be a frozen copy of the count used by earlier scan steps.

### Between-breakpoint selection

When the scan encounters a breakpoint greater than the coordinate after already passing at least one smaller breakpoint, the function uses the most recently passed position as the lower endpoint and the current position as the upper endpoint.

It calls F-8f41f510c86c with three 32-bit arguments, in this order:

1. Coordinate minus lower breakpoint.
2. Upper stored value minus lower stored value.
3. Upper breakpoint minus lower breakpoint.

For this path, the lower breakpoint is read again after the scan. The upper breakpoint is also read again to form the third argument. Stored values are read from the retained value-array pointer.

The dependency’s return word is the complete result for this table. There is no visible addition of the lower stored value, no local rounding adjustment, and no local saturation step afterward.

The relative ordering of all memory reads used to construct these three arguments is not fully established by the supplied representation. The semantic argument order is established.

### Result accumulation and final call

After selecting or computing a table result, the function writes that word into the corresponding position of its temporary result storage.

Results are produced in increasing table order. Each result write occurs after that table’s reads and any F-8f41f510c86c call, and before the next loop-continuation decision.

After the loop, the function calls F-7913ee9e1fa0 with:

1. The original context argument.
2. The original requested-count argument.
3. The address of the temporary result storage.

The final call receives the original requested count even if mutations to the collection count changed how many loop iterations occurred.

Its return value is returned unchanged.
