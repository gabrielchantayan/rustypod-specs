# F-9a7ac0159191

## Purpose

F-9a7ac0159191 conditionally refreshes fields in a shared record using a value obtained from an indirect callback, then returns a 32-bit field from that record.

The refresh decision uses the first callback result. If refresh is required, the function calls the callback again and uses the **second result** for the update and subsequent calculations.

Two distinct reads of the shared record-pointer word occur after the first callback:

- The first supplies the **retained record address**, used for subsequent direct writes and the final return-field read.
- The second supplies the **comparison record address**, used to locate the cached field for the refresh decision.

These addresses coincide if the shared pointer remains stable across the two reads. That stability is not established.

The calculations include bounded doubling and a conditional call to F-d7be9cfb4000. The domain meanings of the callback result, configuration words, and record fields are unknown. Interpreting the calculation as selecting a scale or capacity is inferred intent, not an established contract.

## Interface

### Explicit input and dispatch layout

The function accepts one 32-bit address-bearing input. The supplied representation accesses the following chain:

| Location | Required content |
|---|---|
| Input address plus `0x1C` | A 32-bit object pointer |
| Beginning of that object | A 32-bit dispatch-table pointer |
| Dispatch-table address plus `0xA0` | An indirect callable entry |

The chain is resolved separately for each callback invocation. The second invocation need not reach the same callable if the intervening execution changes any part of the chain.

No explicit arguments to the indirect callable appear in the supplied representation. Its actual calling convention, implicit receiver, and register-carried context are unresolved.

### Shared inputs

Four shared 32-bit words participate:

| Descriptive name | Access |
|---|---|
| Initial bound | Read before the first callback; retained privately for the doubling calculation |
| Record pointer | Read twice after the first callback: first for the retained record, then independently for the comparison record |
| Cutoff | Read only on the refresh path, after doubling |
| Multiplier | Read only on the refresh path, after the cutoff comparison, in the selected branch |

These names describe use, not domain meaning.

The retained record requires accessible 32-bit fields at these byte offsets:

| Offset | Role |
|---|---|
| `+0x04` | Factor field, ultimately read for the return value |
| `+0x08` | Derived-result field |
| `+0x24` | Cached callback-value field |

The comparison record requires an accessible 32-bit cached field at `+0x24`. This function does not otherwise access that record by virtue of its role as the comparison record. If both record addresses coincide, these roles refer to the same storage.

### Widths and preconditions

The supplied representation uses 32-bit addresses, pointer values, callback results, record fields, arithmetic operands, and return values.

Accessible storage, suitable alignment, valid address calculations, and callable dispatch entries are prerequisites. On a refresh, the retained record’s three listed fields must be writable. No explicit validation of these prerequisites appears.

The retained record and dispatch objects must remain valid for every access that actually occurs, including accesses after dependency calls. The function supplies no lifetime protection.

### Output

The return value is the 32-bit contents of the retained record’s factor field, read at the end of execution.

Without refresh, the return is the existing factor of the retained record—not necessarily the factor of the comparison record.

On a refresh without interfering writes, the computed factor is one of `1`, `2`, `4`, `8`, `16`, or `32`. A later dependency-induced change to that field can change the final return.

There is no separate success flag or explicit error result.

## Behavior

### Initial observation and record selection

The function first reads the shared initial-bound word into a private working value. Later changes to that shared word do not replace this snapshot.

It resolves the input’s dispatch chain and invokes the indirect callback. The first 32-bit callback result controls only the refresh decision.

After that callback returns, the function performs these distinct accesses in order:

1. Reads the shared record-pointer word and retains that address.
2. Reads the same shared record-pointer word again to obtain the comparison record address.
3. Reads the cached field at `+0x24` from the comparison record.
4. Compares that cached value with the first callback result.

Both pointer reads occur after the first callback. A change made by that callback can therefore affect both reads. A change between the two reads can cause them to select different records.

The comparison tests equality of the complete 32-bit values. Signed interpretation does not affect the equality result.

### No-refresh path

If the first callback result equals the comparison record’s cached value:

- There is no second callback invocation.
- There are no direct record writes.
- The cutoff and multiplier are not read.
- F-d7be9cfb4000 is not invoked.
- The function reads and returns the factor field of the retained record.

This path neither examines the retained record’s cached field nor validates its relationship to its factor or derived-result fields, unless the two record addresses happen to coincide.

Consequently, equality against one record can suppress refresh while returning an unrelated existing factor from another record. The function does not normalize arbitrary factor values on this path.

### Refresh value and destination

If the first callback result differs from the comparison record’s cached value, the function resolves the dispatch chain again and invokes the callback a second time.

The second callback result is not required to match the first. It is also not compared with either record’s cached field before the refresh proceeds.

The retained address from the **first** record-pointer read remains the destination for subsequent direct writes and the final factor read. The comparison address from the **second** pointer read does not replace it. Later changes to the shared record-pointer word likewise do not redirect those accesses.

After the second callback returns, the function:

1. Writes the second callback result to the retained record’s cached field at `+0x24`.
2. Writes `1` to the retained record’s factor field at `+0x04`.
3. Performs the doubling calculation.
4. Updates the retained record’s derived-result field at `+0x08`.
5. Reads and returns the retained record’s factor field.

A mismatch against the comparison record’s cached value is sufficient to trigger all refresh work. Refresh still occurs if the second result equals the value previously read from the comparison record’s cached field. If the records differ, that value need not equal the retained record’s previous cached value.

### Doubling calculation

The second callback result and the working bound are compared using unsigned 32-bit ordering.

The working bound starts from the initial-bound snapshot. The factor has just been written as `1`.

At each comparison point:

- If the second result is less than or equal to the working bound, doubling stops.
- Otherwise, the working bound is shifted left by one bit within its 32-bit width.
- The retained record’s factor is read, shifted left by one bit, and written back.
- A further bound comparison occurs only if that newly calculated factor is unsigned-less-than `32`.

Without interfering writes, the factor progresses through powers of two and there are at most five doublings. Once it reaches `32`, the calculation stops without another comparison against the newly doubled bound.

Factor `32` therefore does not establish that the bound reached or exceeded the second callback result.

The bound does not saturate. Bits shifted beyond its 32-bit width are discarded. An initial bound of zero remains zero.

The factor is repeatedly stored in the record, rather than held only as a private final result. Its initialization and intermediate doubled values are direct writes. The ordinary five-doubling limit relies on the initialized factor not being altered by outside interference; no synchronization or concurrent-interference contract is established.

### Derived-result update

After doubling, the function reads the shared cutoff. It compares the second callback result with that cutoff using unsigned 32-bit ordering.

If the second result is **strictly less** than the cutoff:

1. The function reads the multiplier.
2. It multiplies the multiplier by the second result, retaining the low 32 bits.
3. It calls F-d7be9cfb4000 with that 32-bit product as the single explicit argument.
4. It stores the dependency’s complete 32-bit return value in the retained record’s derived-result field.
5. If the returned value is zero, it writes `1` to the same field.

The zero check concerns the dependency’s returned value. A zero return produces two ordered direct writes: zero, then one.

If the second result is **greater than or equal to** the cutoff:

1. The function reads the multiplier.
2. It writes that word directly to the retained record’s derived-result field.

This branch does not invoke F-d7be9cfb4000 and does not replace a zero multiplier with one.

Finally, the function reads the retained record’s factor field and returns it. This read occurs after any call to F-d7be9cfb4000 and after the derived-result writes.

## Side effects

### Direct memory effects

The function shows no direct writes to the four shared configuration words.

On a refresh, direct record writes target the retained address and occur in this order:

1. Cached field receives the second callback result.
2. Factor field receives `1`.
3. Factor field receives each successive doubled value, if doubling occurs.
4. Derived-result field receives either the multiplier or the dependency result.
5. A zero dependency result is followed by a write of `1` to the derived-result field.

There is no direct write targeted through the comparison address merely because that address supplied the refresh comparison. The comparison record can nevertheless be affected if it coincides with or aliases written storage.

The operation is not transactional. Cached and factor fields have already been changed before a possible call to F-d7be9cfb4000. No rollback is shown if a later access or call fails to complete.

### Dependency effects, ownership, and concurrency

The indirect callback executes once or twice on a normally completing execution. F-d7be9cfb4000 executes at most once.

Neither dependency is established to preserve globals, record contents, dispatch structures, or object lifetimes. The function continues to use its retained record address after dependency calls; a dependency changing the shared pointer does not update that retained address.

No direct allocation, deallocation, ownership transfer, or release operation is shown. The dependency result must not be treated as an owned pointer solely because it is stored in a record field. The function does not release the previous derived-result value before overwriting it.

No locks, atomic-access protocol, or inter-thread ordering guarantee are established. The access order described here is the order expressed by the supplied representation, not a guarantee of visibility to concurrent observers.

Aliasing can affect later reads. For example, a record write that aliases the cutoff or multiplier storage can change the subsequently read configuration value. Independent-storage assumptions must not be imposed on such a case.

## Acceptance examples

These are conditional static acceptance cases, not runtime observations. Except where a change is expressly specified, assume valid distinct storage, normally returning dependencies, and no changes to relevant state during execution.

### Stable pointer and cached equality

Both record-pointer reads yield record A. The first callback returns `7`, A’s cached field is `7`, and A’s factor is `19`.

The function calls the callback once, performs no direct record writes, and returns `19`. The existing factor need not be a power of two.

### Different records on the two pointer reads: no refresh

The first pointer read yields A; the second yields B. The first callback returns `7`. B’s cached value is `7`, while A’s cached value is `99`. A’s factor is `19` and B’s factor is `3`.

The comparison against B suppresses refresh. The function returns `19` from A. It does not compare A’s cached value or return B’s factor.

### Different records on the two pointer reads: refresh

The first pointer read yields A; the second yields B. The first callback returns `7`, A’s cached value is `7`, and B’s cached value is `8`. The second callback returns `8`, and the initial bound is `10`.

Refresh occurs because the first result differs from B’s cached value. A’s cached field is written with `8`, A’s factor becomes `1`, and A receives the derived-result update. The second result equaling B’s previously compared cached value does not cancel refresh. Under these distinct-storage assumptions, B receives no direct writes.

### The second callback controls calculations

Both pointer reads yield A. A’s cached value is `10`; the first result is `11`; the second result is `10`; the initial bound is `10`.

Refresh occurs. A’s cached field is written with `10`, its factor remains `1`, and the derived-result branch uses `10`, not `11`.

### Ordinary doubling

With an initial bound of `10` and a refresh result of `21`, the compared bounds are `10`, `20`, and `40`. Factor writes are `1`, `2`, and `4`.

Absent later interference, the return is `4`.

### Cap, zero, and wraparound

With initial bound `1` and refresh result `100`, the factor reaches `32` while the working bound is only `32`. The calculation stops anyway.

With initial bound zero and a positive refresh result, the bound remains zero and the factor reaches `32`.

With initial bound `0x80000000` and refresh result `0xFFFFFFFF`, the first doubling wraps the bound to zero. The factor ultimately reaches `32`.

### Strict cutoff and zero handling

If the refresh result equals the cutoff, the direct-multiplier branch is taken. F-d7be9cfb4000 is not called. A zero multiplier is stored as zero.

If the refresh result is `2`, the cutoff is greater than `2`, and the multiplier is `0x80000000`, the dependency receives zero because the product is truncated to 32 bits. If it returns zero, the derived-result field receives zero and then one.

### Dependency changes the eventual return

Suppose doubling leaves the retained record’s factor at `4`. F-d7be9cfb4000 then changes that field to `9` while preserving the record’s validity.

The final return is `9`, because the factor is read after the dependency call.
