# F-8050e778e362

## Purpose

F-8050e778e362 modifies a small set of 32-bit links associated with a supplied node and a control object. It returns no value.

**Inferred intent:** For coherent binary-tree links, the operation is a right rotation around the supplied node. The node referenced by its offset-8 link is promoted; the promoted node’s offset-12 subtree becomes the supplied node’s offset-8 subtree; and the surrounding root or parent link is redirected to the promoted node.

**Established behavior:** The function performs the ordered memory accesses described below. It does not verify that the objects form a tree, that parent and child links agree, or that the link identifying the promoted node is nonzero.

### Terms

- **Pivot:** The object identified by the second argument.
- **Promoted node:** The address read from the pivot’s offset-8 field at the beginning of the operation. This address is retained for subsequent accesses.
- **Transfer node:** Under stable, non-overlapping storage, the object initially referenced by the promoted node’s offset-12 field.
- **Root slot:** The four-byte location at offset 4 from the root-holder address obtained through the control object.
- **Former parent:** Under ordinary tree-layout assumptions, the object initially referenced by the pivot’s offset-4 field.

Only the promoted-node address is captured at entry. The transfer link and pivot parent-like link are read later, including repeated reads. These terms must not be interpreted as implying a snapshot of all initial relationships.

## Behavior

### Ordered accesses

The following order is established at the supplied body’s statement level. It does not establish machine-instruction ordering, atomicity, or an evaluation order between subexpressions within one statement.

1. **Capture the promoted-node address.**  
   Read the pivot’s four-byte field at offset 8. Retain this address for the rest of the operation.

2. **Replace the pivot’s first child-like link.**  
   Read the promoted node’s offset-12 field and write that four-byte value to the pivot’s offset-8 field.

3. **Conditionally update the transfer node’s parent-like link.**  
   Read the promoted node’s offset-12 field again and compare the value with zero.

   - If zero, perform no transfer-parent write.
   - If nonzero, read the same field again to obtain a destination object address, then write the pivot address to that object’s offset-4 field.

   Including the read in the preceding step, the promoted node’s offset-12 field is read twice when the zero branch is taken and three times when the nonzero branch is taken. The function does not retain one transfer-link value for all these uses.

4. **Set the promoted node’s parent-like link.**  
   Read the pivot’s offset-4 field and write its four-byte value to the promoted node’s offset-4 field.

5. **Locate and inspect the root slot.**  
   Read the control object’s offset-16 field to obtain the root-holder address. Derive the root-slot address by adding byte offset 4, then read that slot and compare its value with the pivot address.

   This lookup occurs after the preceding child-link and parent-link writes. The selected root-slot address is retained for the root-path write.

6. **Redirect one surrounding link.**

   - **Root path:** If the root slot equals the pivot address, write the promoted-node address into that root slot. Do not inspect the former parent’s child fields.
   - **Non-root path:** Read the pivot’s offset-4 field again to obtain a parent address, then read that parent’s offset-12 field.
     - If the inspected value equals the pivot address, write the promoted-node address to that parent’s offset-12 field.
     - Otherwise, write the promoted-node address to that parent’s offset-8 field.

   The fallback does not read or validate the parent’s offset-8 value before replacing it.

7. **Attach the pivot beneath the promoted node.**  
   Write the pivot address to the promoted node’s offset-12 field.

8. **Finish the pivot’s parent-like link.**  
   Write the promoted-node address to the pivot’s offset-4 field. Return without a value.

The link comparisons are equality comparisons against zero or the pivot address. There is no key comparison, traversal loop, or arithmetic on node payloads.

### Result for coherent tree storage

If the objects are stable, distinct, accessible, and coherently linked, successful completion produces these relationships:

| Relationship | Final value |
|---|---|
| Pivot’s first child | Promoted node’s former second child |
| Transfer node’s parent, when present | Pivot |
| Promoted node’s parent | Pivot’s former parent |
| Root or selected former-parent child link | Promoted node |
| Promoted node’s second child | Pivot |
| Pivot’s parent | Promoted node |

Under these assumptions, the promoted node’s first child and the pivot’s second child remain unchanged. No direct write targets the control object’s offset-16 field.

The function does not require the root pivot’s parent-like value to be zero. On the root path, it copies that value to the promoted node without dereferencing it as a parent address.

### Aliasing and intermediate state

The simplified rotation result is conditional on the layout assumptions. It is not an unconditional postcondition for overlapping or self-referential objects.

Earlier writes can change later reads when fields overlap. In particular:

- The repeated promoted-node offset-12 reads need not observe the same value.
- The pivot’s offset-4 field is read for the promoted-parent update and read again on the non-root path.
- The control field and root slot are inspected only after the initial link writes.

Consequently, the branch decision about transfer-parent repair depends on its own read, not necessarily on the value previously copied into the pivot’s offset-8 field. Likewise, the destination used by the optional transfer-parent write comes from a further read, not from the value used for the zero comparison.

This is an in-place update, not a transaction. Intermediate relationships can violate tree invariants. The surrounding link is redirected before the final two writes complete the pivot–promoted relationship.

## Side effects

### Memory mutation and write counts

A normally completed invocation performs **five unconditional four-byte writes, plus one optional four-byte transfer-parent write**.

| Write | Destination | Condition |
|---|---|---|
| First-child replacement | Pivot, offset 8 | Always |
| Transfer-parent repair | Object selected by the repeated transfer-link read, offset 4 | Transfer-link comparison is nonzero |
| Promoted-parent assignment | Promoted node, offset 4 | Always |
| Surrounding-link replacement | Root slot, parent offset 12, or parent offset 8 | Exactly one destination on every completed invocation |
| Promoted second-child assignment | Promoted node, offset 12 | Always |
| Pivot parent assignment | Pivot, offset 4 | Always |

Therefore:

- **Zero-transfer branch:** Five four-byte writes.
- **Nonzero-transfer branch:** Six four-byte writes.

These counts describe writes in the supplied body, not the number of distinct memory locations modified. Aliasing can make destinations coincide. A write still occurs when its value equals the destination’s existing value.

All written values are supplied object addresses or values read from existing link fields. The body contains no allocation, deallocation, payload copy, reference-count adjustment, or ownership-management call. It does not establish ownership of any object or reclaim storage disconnected by malformed input.

### Errors and partial completion

There is no explicit validation failure, error return, or rollback.

An inaccessible address can prevent completion. The environment’s fault mechanism is unknown. Earlier writes may already have occurred before a later access fails.

A zero transfer link is explicitly handled by skipping the transfer-parent write. A zero promoted-node address is not handled before the offset-12 access. A zero pivot parent-like value does not require dereferencing on the root path, but it is used as an address on the non-root path.

There is no established synchronization, memory barrier, atomic grouping, or concurrent-access protocol.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence. They have not been executed. Except where stated otherwise, assume stable, non-overlapping, accessible storage and normal completion.

### Root pivot with a transfer node

Given a root slot referring to the pivot, a pivot offset-8 link referring to the promoted node, and a nonzero promoted-node offset-12 link referring to a transfer node:

- The root slot ends referring to the promoted node.
- The promoted node’s parent-like field receives the pivot’s former parent-like value.
- The pivot’s first-child field ends referring to the transfer node.
- The transfer node’s parent-like field ends referring to the pivot.
- The promoted node’s second-child field ends referring to the pivot.
- The pivot’s parent-like field ends referring to the promoted node.

No former-parent child field is inspected. This path performs six four-byte writes.

### Root pivot without a transfer node

Given a root slot referring to the pivot and a stable zero promoted-node offset-12 field:

- The pivot’s offset-8 field becomes zero.
- No transfer-parent destination is accessed.
- The root and final parent/child links are updated as above.

This path performs five four-byte writes.

### Non-root pivot in the parent’s second-child slot

Given a root slot not referring to the pivot and a parent offset-12 field equal to the pivot address, the surrounding-link update replaces that offset-12 field with the promoted-node address.

The parent’s offset-8 field is not directly written on this branch.

### Non-root fallback

Given a root slot not referring to the pivot and a parent offset-12 field not equal to the pivot address, the surrounding-link update writes the promoted-node address to the parent’s offset-8 field.

This occurs even if that offset-8 field did not previously refer to the pivot. There is no rejection of the inconsistent structure and no guarantee of preserving the displaced link’s reachability.

### Root with a zero parent-like value

Given a root slot referring to the pivot and a zero pivot offset-4 value, the promoted node receives zero in its parent-like field. The root path does not dereference that zero value as a parent address.

### Invalid promoted-node link

Given a zero or inaccessible pivot offset-8 value, the function attempts the promoted-node offset-12 read without first validating that address.

A successful rotation or defined error result is not promised. The behavior of the failing access remains environment-dependent.
