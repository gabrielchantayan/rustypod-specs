# F-3f754031ddf9

## Purpose

F-3f754031ddf9 scans a byte sequence and accumulates an integer using a selected radix, an external byte-classification table, and an external byte-to-value table. It optionally stores the position at which scanning stopped.

The routine recognizes an initial ASCII minus sign and an ASCII hexadecimal prefix. It does not implement general whitespace handling, positive-sign handling, radix autodetection, or explicit overflow reporting.

The classification tables and value table are not supplied. Consequently, the routine’s control flow is established, but conventional numeric parsing behavior is conditional on those tables containing conventional entries.

## Interface

The routine has four inputs and one integer return value:

| Input | Contract |
|---|---|
| Input address | Address of a readable byte sequence, or null. Each scanned element is an unsigned 8-bit byte. No length is supplied. |
| Optional stopping-position destination | Null, or writable storage for one input address. The supplied representation uses a four-byte destination slot. |
| Requested radix | An integer selector. Values 8 and 16 are distinguished; every other value selects decimal behavior unless a hexadecimal prefix overrides it. |
| Auxiliary unsigned value | Replaced with the first input byte whenever the input address is non-null. When the input address is null, this value does not affect the result. It has no independent parsing role. |

The return is an integer accumulator, optionally negated.

The supplied representation indicates a 32-bit interface: a four-byte output slot, unsigned integer operations, and integer accumulation. Exact original type declarations and overflow semantics are not independently established. The widths and overflow limitations described below must therefore be read with that qualification.

### Preconditions

For an invocation that enters scanning:

- The input must remain readable through all prefix inspection and scanning reads.
- The input must eventually reach a byte rejected by the selected classification table if the routine is to terminate normally.
- Every external table location accessed must be readable.
- A non-null stopping-position destination must support a four-byte address write under the calling environment’s alignment and access rules.
- The routine supplies no bounds checking. A conventional null-terminated string is sufficient only if the relevant classification table rejects the zero byte.

A null input address is explicitly supported. An empty input sequence is also handled specially, provided its first zero byte is readable.

No ownership is transferred. The routine does not allocate or release memory.

## Behavior

### 1. Entry checks

When the input address is non-null, the routine reads its first byte and uses that unsigned byte in place of the auxiliary unsigned argument.

If the input address is null, it returns zero immediately. It does not access the input, initialize the stopping-position destination, or consult parsing tables.

If the first input byte is zero, it also returns zero immediately. In this case, the stopping-position destination is left unchanged even when non-null.

This creates an important distinction between an empty input and a nonempty input that yields no accepted digits: only the latter reaches the stopping-position write.

### 2. Initial radix and classification selection

For a non-null input whose initial byte is nonzero, the routine selects a radix and a classification-table base:

- Requested radix 8 selects radix 8 and the octal-associated classification table.
- Requested radix 16 selects radix 16 and the hexadecimal-associated classification table.
- Any other requested radix selects radix 10 and the decimal-associated classification table.

There is no error for an unsupported radix selector. Negative selectors, zero, and other unsupported values all follow the decimal-selection path.

The supplied representation shows an ordered sequence of external table-reference reads:

1. The octal-associated reference is read first.
2. If the requested radix is not 8, the hexadecimal-associated reference is read.
3. If the requested radix is neither 8 nor 16, the decimal-associated reference is read.

Thus, the representation includes reads of table references that may subsequently be replaced. It does not establish that an optimizing implementation performs a distinct physical memory transaction for every such read.

### 3. Initial minus sign

If the original first byte is ASCII `-`, the scan position advances by one byte.

The sign decision remains based on that original byte. A minus sign encountered later receives no special sign treatment.

There is no corresponding explicit handling of ASCII `+`. Whether that byte can participate in accumulation depends entirely on the selected classification and value tables.

The routine does not require any accepted digit after a minus sign before continuing with prefix inspection and scanning.

### 4. Hexadecimal prefix override

At the position following the optional minus sign, the routine checks for ASCII `0` followed by either lowercase `x` or uppercase `X`.

When that pair is present:

- The effective radix becomes 16.
- The hexadecimal-associated classification reference is read and selected.
- The scan position advances by two bytes.

This override applies regardless of the requested radix. In particular, a requested radix of 8 does not prevent hexadecimal-prefix recognition.

The second prefix byte is inspected only when the first byte at the current position is ASCII `0`. Prefix inspection does not itself verify that any accepted digit follows the prefix.

A leading zero without a following `x` or `X` does not trigger octal autodetection. It remains part of the sequence offered to the selected classification table.

### 5. Classification and accumulation

The accumulator starts at zero after sign and prefix processing.

At each scan position, the routine reads one unsigned byte. That byte selects a bit in the chosen classification table:

- The byte’s upper five bits select a table-byte offset from 0 through 31.
- Its lower three bits select one of eight bits within that table byte.
- A set bit means the input byte is accepted.
- A clear bit ends scanning without consuming that byte.

A full classification bitmap therefore covers all 256 possible input-byte values using 32 bytes. The routine does not first restrict the input to ASCII, digits, or printable characters.

For an accepted byte, the routine:

1. Advances the scan position by one byte.
2. Obtains an unsigned 8-bit mapped value from the external value table, indexed by the accepted input byte.
3. Updates the accumulator according to

   $$
   A_{\text{next}} = rA_{\text{current}} + v
   $$

   where $r$ is the effective radix and $v$ is the mapped value.

The value-table base is obtained through an external reference in each accepted-byte iteration. Unlike the selected classification-table base, it is not visibly captured once before the loop in the supplied representation.

The routine performs no independent validation that the mapped value is less than the effective radix. A classification table can therefore admit a byte whose mapped value is outside the conventional digit range, and the routine still applies the same accumulation rule.

### 6. Stopping-position output and sign application

Once classification rejects the current byte, the routine writes the current scan address to the optional destination, if that destination is non-null.

This address identifies the first rejected byte after any consumed sign and prefix. It does not necessarily identify the first unconsumed byte of the original input when no numeric digit was accepted: the sign and prefix may already have been consumed.

The output write occurs before final sign application.

If the original first byte was ASCII `-`, the accumulator is negated. The resulting integer is returned. Otherwise, the accumulator is returned without negation.

There is no separate success flag, digit count, overflow flag, or error code.

### 7. Arithmetic boundaries

Mapped values are unsigned bytes, so each lies between 0 and 255. The effective radix is always 8, 10, or 16.

The supplied representation uses integer multiplication, addition, and final negation without explicit range checks or a wider accumulator. It establishes neither saturation nor a checked-overflow result.

For inputs whose intermediate accumulation and final sign application are representable, the arithmetic rule above defines the result directly.

For larger inputs, exact behavior is **documented_only**. A 32-bit machine implementation may wrap intermediate results, but the supplied representation alone is insufficient to make wraparound a portable contract. Negation at the most-negative signed value has the same unresolved arithmetic-boundary issue.

## Side effects

The only explicit write is the optional stopping-position write. It occurs only after entry into the nonempty-input parsing path and termination of the classification loop.

The routine does not explicitly modify:

- The input bytes.
- The classification tables.
- The value table.
- The global references used to locate those tables.

A caller can nevertheless arrange aliasing between the output destination and other storage. The routine performs no visible alias check. If the destination overlaps writable input or table-related storage, the final address write can alter that storage. Scanning has already ended when that write occurs.

There are no visible function calls, allocations, releases, logging operations, or explicit error notifications.

Invalid input memory, invalid table references, an invalid output destination, or an unterminated accepted-byte run can lead to an invalid memory access or failure to return. The routine has no visible mechanism for translating such conditions into a controlled return value.

The description of reads and writes here is their logical order in the supplied representation, not a guarantee about instruction-level load counts, memory atomicity, or synchronization. Concurrent mutation and volatile-memory behavior are not established.

## Acceptance examples

These examples are conditional specifications derived from the visible behavior. They are not runtime test results.

### Unconditional entry behavior

- **Null input:** Return zero. Leave a supplied stopping-position slot unchanged. The auxiliary unsigned value has no effect.
- **Input beginning with a zero byte:** Return zero and leave the stopping-position slot unchanged, regardless of requested radix.
- **Non-null input:** Changing only the auxiliary unsigned argument does not change parsing, because the first input byte replaces it.

### Conventional numeric tables

Assume the selected tables accept the usual digits for each radix, reject the delimiter and zero byte, and map numeric characters to their conventional values.

| Input | Requested radix | Expected result | Stored stopping position |
|---|---:|---:|---|
| `123!` | 10 | 123 | The `!` byte |
| `17!` | 8 | 15 | The `!` byte |
| `19!` | 8 | 1 | The `9` byte |
| `ff!` | 16 | 255 | The `!` byte |
| `077!` | 10 | 77 | The `!` byte |
| `12!` | 3 | 12 | The `!` byte |
| `-12!` | 10 | −12 | The `!` byte |
| `0x10!` | 8 | 16 | The `!` byte |
| `-0X10!` | 10 | −16 | The `!` byte |

These results require the stated classifications and mappings. For example, acceptance of lowercase hexadecimal letters is not independently established.

### No accepted digit after structural consumption

Assume the effective table rejects the zero byte and ASCII `!`.

- Input `!` returns zero and stores the address of `!`.
- Input `-!` returns zero and stores the address of `!`, after the consumed sign.
- Input `0x!` returns zero and stores the address of `!`, after the consumed prefix.
- Input `-0X!` returns zero and stores the address of `!`, after both structural components.
- Input consisting only of `-` followed by a zero byte returns zero and stores the zero byte’s address.
- Input consisting only of `0x` followed by a zero byte returns zero and stores the zero byte’s address.

These differ from an initially empty input, which does not write the output slot.

### Table-defined behavior beyond conventional parsing

If the effective table accepts a particular byte and maps it to 200, that accepted byte contributes 200 even in radix 8. The routine does not reject it merely because 200 exceeds the radix.

If a classification table accepts the zero byte, encountering a zero byte during scanning does not terminate the loop. The routine advances past it and continues reading. Only the initial zero-byte check is unconditional.

- Exact membership of each classification bitmap.
- Exact byte-to-value mappings.
- Defined behavior when accumulation or negation exceeds the signed integer range.
- Exact original pointer and integer declarations beyond the supplied 32-bit representation.

The likely intent is a compact signed integer parser with decimal, octal, and hexadecimal modes. That intent does not establish standard-library compatibility. In particular, output handling for empty input, unconditional prefix consumption, table-driven termination, and absence of range reporting must remain explicit parts of this contract.
