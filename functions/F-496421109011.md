# F-496421109011

## Purpose

F-496421109011 performs a sequence of memory updates derived from its arguments, incoming execution context, and pointer values read from memory. The recovered path then enters an unconditional loop issuing a coprocessor operation.

The established behavior is memory mutation followed by repeated coprocessor interaction. A normal return, a completion notification, and a recoverable error result are not present in the supplied static evidence.

An initialization, reset, or device-control purpose is plausible but **inferred**, not established. The evidence does not identify the affected memory as ordinary RAM, device registers, object storage, or a combination of these.

This contract describes the recovered path conditionally. The supplied material reports invalid instruction data and removed unreachable regions, so it does not establish that the recovered path accurately represents every executable instruction or every possible entry condition.

## Behavior

### Preconditions for the complete recovered path

Successful progression to the loop requires every accessed address to support its indicated access at the moment that access occurs. The function contains no visible null checks, bounds checks, alignment checks, or pointer validation.

Pointer values obtained from memory are used directly in subsequent address calculations. Their validity is an environmental precondition, not something this function establishes.

Overlapping memory regions are not excluded. Earlier writes can therefore affect later pointer reads, data reads, or writes.

### Ordered memory operations

The following order is established by the recovered path. Each numbered item completes before the next item on that path. Within a pointer-dependent item, the pointer read necessarily precedes the access using that pointer. No stronger ordering is asserted for independent subexpressions inside one item.

1. **Store the incoming base value into a field relative to itself.**

   A 32-bit value is written at an address `0x50` bytes beyond the implicit incoming base. The stored value is that base value itself.

   This resembles a self-reference field, but that interpretation is not established.

2. **Clear the explicit byte destination.**

   A zero byte is written through the second argument. No prior contents of that byte are read by the recovered operation.

3. **Copy one byte from a wider read within a third-argument-derived region.**

   Form a region address by multiplying the third argument by `0x400`.

   Read a 32-bit value at offset `0x64` within that region. Write the low eight bits of the value to offset `0x03` within the same region.

   The source access is a 32-bit read, not a byte read. A device mapping or access boundary can therefore make it observably different from reading a single byte.

4. **Clear a byte through a context-selected pointer.**

   Mask the separate implicit selector to its low 22 bits, multiply that result by `0x10`, and add `0x3C`.

   Read a 32-bit pointer from the resulting address. Write a zero byte at offset `0x02` from that pointer.

   The selector table's layout beyond this pointer read is not established.

5. **Clear a 32-bit field through the fixed-address pointer.**

   Read the 32-bit pointer stored at `0x00000060`. Write a 32-bit zero at offset `0x2C` from the resulting pointer.

   This pointer read occurs after the preceding writes. The contract does not treat it as an immutable global or cache its entry-time value.

6. **Clear a byte at a scaled address.**

   Multiply the third argument by `0x100000` and write a zero byte at the resulting address.

   Under 32-bit arithmetic, this address depends only on the low 12 bits of the third argument.

7. **Write a derived byte through a two-stage pointer lookup.**

   First form a lookup address by masking the third argument to its low 12 bits, multiplying by `0x100`, and adding `0x68`.

   Read a 32-bit pointer at that address. Read a 32-bit value at offset `0x60` from the pointer.

   Logically shift that second value right by two bits, then add `0x04`. The result is used directly as the byte destination address.

   The byte written is the low eight bits of the address formed by multiplying the third argument by `0x100000` and adding `0x9E`. Under the stated 32-bit model, those low eight bits are always `0x9E`.

   The shift is a logical shift of an unsigned 32-bit value. Before the final addition, its range is `0x00000000` through `0x3FFFFFFF`; afterward, the destination lies from `0x00000004` through `0x40000003`, inclusive.

8. **Clear a final derived byte.**

   Take the address formed in the preceding item from the scaled third argument plus `0x9E`, multiply it by `0x400`, and subtract `0x5E`. Write a zero byte there.

   Under 32-bit arithmetic, the destination is:

   \[
   \bigl((\text{third argument} \bmod 4)\times \texttt{0x40000000}\bigr)
   + \texttt{0x000277A2}.
   \]

   Thus, only the low two bits of the third argument affect this final destination.

### Coprocessor loop

After the final byte write, the recovered path enters a loop with no visible exit.

The first iteration derives an unsigned 32-bit value from the same multiplied address used in the final memory operation, but subtracts `0x68` rather than `0x5E`. It logically shifts that result right by 11 bits.

Before issuing the coprocessor operation, the loop's retained arithmetic state is set to zero. Consequently:

- The first operation receives the computed shifted value.
- Every subsequent operation receives zero in that operand position.
- The first computed value is not repeatedly submitted.

Each invocation uses the fixed selector tuple `(8, 5, 4)`, the iteration-dependent operand, and the two incoming coprocessor-related values.

The evidence identifies the operation as a coprocessor transfer but does not establish its architectural effect. It must not be renamed as a flush, barrier, sleep, reset, or other specific action without additional evidence.

There are no explicit ordinary-memory accesses in the visible loop body. That does not establish that the coprocessor operation lacks memory effects.

An implementation that substitutes a byte read for the specified 32-bit read is not established as equivalent, even if it produces the same byte in ordinary little-endian RAM.

### Pointer-derived byte destination

If the second-stage 32-bit value in the two-stage lookup is `0x00000100`, its logical right shift by two produces `0x40`. The destination byte address is therefore `0x44`, and the byte written there is `0x9E`.

That address must still be writable. A small numerical address is not evidence of validity.

### Zero third argument is not rejected
