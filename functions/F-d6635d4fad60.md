# F-d6635d4fad60

## Purpose

F-d6635d4fad60 performs an in-place structural rearrangement of pointer-linked records. Under the conventional tree interpretation of the accessed fields, the operation is a **right rotation** around a supplied node: its left child is promoted, the promoted child’s right subtree is transferred to the supplied node, and the surrounding parent or root link is updated.

That tree interpretation is inferred from the relationships among the reads and writes. The established behavior is a fixed sequence of 32-bit field accesses and conditional link updates. The routine does not validate a tree, compare keys, establish ordering, update balancing metadata, or report whether its inputs describe a valid structure.

No runtime tests have been performed. The contract below distinguishes the directly supported field behavior from the structural assumptions needed to interpret it as a valid rotation.

## Interface

The function accepts two arguments and returns no value:

- **Context address:** identifies a record containing a 32-bit address-bearing field at byte offset 16.
- **Node address:** identifies the node to be demoted by the rearrangement.

The supplied representation uses 32-bit argument values and 4-byte field accesses. Values used as addresses must therefore be valid in the applicable 32-bit address representation. A wider-pointer ABI, implicit pointer widening, or support for addresses outside that representation is not established.

The relevant layouts are:

| Record | Byte offset | Width | Operational role |
|---|---:|---:|---|
| Context | 16 | 4 bytes | Address of a separate anchor record |
| Anchor | 4 | 4 bytes | Link compared against the supplied node; conditionally replaced |
| Node-like record | 4 | 4 bytes | Parent-like link |
| Node-like record | 8 | 4 bytes | Left-child-like link |
| Node-like record | 12 | 4 bytes | Right-child-like link |

These role names describe the inferred tree layout, not a separately established public type definition. No record size, packing rule, field meaning outside these offsets, or byte order is established by the supplied material.

For discussion, the following names identify records rather than implementation variables:

- **Target:** the supplied node.
- **Pivot:** the record named by the target’s initial field at offset 8.
- **Transfer subtree:** the record named by the pivot’s field at offset 12, when that field is nonzero.
- **Anchor:** the record reached through the context’s field at offset 16.
- **Former parent:** the record named by the target’s field at offset 4 when that field is consulted.

There is no explicit success result, error result, callback, ownership token, or returned replacement-root address. A root replacement, when applicable, is communicated by modifying the anchor.

## Behavior

### Required memory conditions

For defined execution in the intended environment, every address dereferenced along the selected branch must designate accessible storage for the relevant 4-byte operation. Alignment requirements depend on the execution environment and are not established here.

In particular:

- The target must permit reads and writes at the offsets used.
- The initial pivot address must permit the pivot accesses.
- The context must permit a read at offset 16.
- The resulting anchor address must permit a read at offset 4 and, on the root branch, a write there.
- A nonzero transfer-subtree address must permit a write at offset 4.
- On a non-root branch, the former-parent address must permit a read at offset 12 and a write at either offset 12 or offset 8.

Zero is explicitly checked only for the pivot’s offset-12 link. The routine does not guard against a zero target, zero pivot, zero anchor, or invalid former parent.

A conventional, nondegenerate tree rotation additionally assumes consistent parent/child links and distinct records wherever their fields are intended to have separate structural roles. Those assumptions are not checked.

### Ordered field effects

The following order is material. Some fields are read more than once; replacing those accesses with a single conceptual snapshot would not describe all aliasing or externally modified cases.

1. **Select the pivot.**  
   Read the target’s 4-byte field at offset 8. Its value selects the pivot for the remainder of the operation.

2. **Replace the target’s left link.**  
   Read the pivot’s field at offset 12 and write that 4-byte value into the target’s field at offset 8.

3. **Conditionally repair the transferred record’s parent link.**  
   Read the pivot’s field at offset 12 again and compare it with zero. If nonzero, read that field again to obtain a destination address, then write the target address into the destination record’s field at offset 4.

   For stable, nonoverlapping records, these accesses all identify the same transfer subtree. The behavior does not establish an atomic snapshot across the repeated reads.

4. **Give the pivot the target’s parent link.**  
   Read the target’s field at offset 4 and write that value into the pivot’s field at offset 4.

5. **Locate and inspect the anchor link.**  
   Read the context’s field at offset 16 to obtain the anchor address. Read the anchor’s field at offset 4 and compare its value with the target address.

6. **Reconnect the surrounding structure.**
   - If the anchor’s field at offset 4 equals the target address, write the pivot address into that anchor field.
   - Otherwise, read the target’s field at offset 4 again to obtain the former-parent address. Read that record’s field at offset 12.
     - If this field equals the target address, replace it with the pivot address.
     - Otherwise, write the pivot address into the former parent’s field at offset 8.

   The final alternative does **not** check that the former parent’s offset-8 field previously named the target.

7. **Make the target the pivot’s right child.**  
   Write the target address into the pivot’s field at offset 12.

8. **Make the pivot the target’s parent.**  
   Write the pivot address into the target’s field at offset 4.

The function then returns without a value.

### Structural result under ordinary tree assumptions

For stable memory, nonoverlapping records, and internally consistent tree links:

- The pivot replaces the target in the target’s former position.
- The pivot’s former right subtree becomes the target’s left subtree.
- A nonempty transferred subtree has its parent link changed to the target.
- The pivot inherits the target’s former parent link.
- The target becomes the pivot’s right child.
- The target’s parent link becomes the pivot.
- The anchor’s root-like link changes only when it initially identifies the target.

The target’s right-child field and the pivot’s left-child field are not directly written. No payload or balancing field is directly accessed.

If the underlying structure is a correctly ordered binary search tree, this arrangement has the usual right-rotation interpretation. Preservation of any particular ordering relation is conditional on that structure and is not independently checked.

### Widths and arithmetic

Address calculations use fixed byte offsets of 4, 8, 12, and 16. There is no element-count calculation, key arithmetic, allocation-size calculation, or loop. The routine provides no explicit address-overflow check. Behavior for addresses whose field calculations are not valid in the execution environment is not established as a supported case.

## Side effects

The operation mutates caller-provided storage directly. In an ordinary nonoverlapping execution, the possible write locations are:

- Target, offset 8.
- Transfer subtree, offset 4, only when the tested link is nonzero.
- Pivot, offset 4.
- Exactly one surrounding link: anchor offset 4, former-parent offset 12, or former-parent offset 8.
- Pivot, offset 12.
- Target, offset 4.

Thus the ordinary execution performs five writes when the transfer link is zero and six when it is nonzero.

There is no explicit allocation, deallocation, ownership transfer, reference-count adjustment, or external call. The operation rearranges links; it does not establish that any record may be released afterward. Storage lifetime remains a caller responsibility.

No explicit lock, atomic transaction, rollback mechanism, or error recovery appears. Intermediate states are not a complete rotation: the target’s left link changes before the surrounding link is repaired, and the final parent link is written last. Callers requiring isolation must arrange it outside this operation.

Invalid memory access is not converted into a reported failure. Any platform-level fault behavior is outside this contract. If execution fails after earlier writes, no rollback is established.

Aliasing can cause a listed write to affect a later read or make multiple logical fields share storage. The simple tree postconditions and ordinary write-location interpretation therefore require the stated nonoverlap assumptions. The ordered accesses remain the basis for analyzing unusual layouts.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Unless stated otherwise, records are distinct, memory is stable, and all required accesses are valid.

### Root rotation without a transferred subtree

Given that the anchor’s offset-4 field names the target, the target’s offset-8 field names the pivot, and the pivot’s offset-12 field is zero:

- The target’s offset-8 field becomes zero.
- No transfer-subtree parent write occurs.
- The anchor’s offset-4 field becomes the pivot address.
- The pivot receives the target’s former parent link.
- The pivot’s offset-12 field becomes the target address.
- The target’s offset-4 field becomes the pivot address.

### Root rotation with a transferred subtree

Given the same root relationship, but with a nonzero pivot offset-12 link naming an accessible transfer subtree:

- The target’s offset-8 field becomes that subtree address.
- The subtree’s offset-4 field becomes the target address.
- The remaining root and parent-link changes match the preceding example.

The subtree is retained and reparented; it is not freed.

### Target is the former parent’s right child

Given that the anchor does not name the target and the former parent’s offset-12 field does:

- The former parent’s offset-12 field becomes the pivot address.
- The former parent’s offset-8 field is not directly written by this branch.
- The final target/pivot relationship is the same as in the root examples.

### Non-root fallback branch

Given that the anchor does not name the target and the former parent’s offset-12 field also does not:

- The former parent’s offset-8 field is overwritten with the pivot address.

This occurs even if that field did not previously name the target. An inconsistent structure is not rejected or repaired generally.

### Missing pivot

Given a zero target offset-8 field, the routine still attempts to access the selected pivot’s offset-12 field. No clean rejection, no-op result, or error return is established. This is outside the ordinary valid-rotation preconditions.
