# F-a709b42a5ce0

## Purpose

F-a709b42a5ce0 computes a prospective 32-bit state value from an object’s state field and a signed adjustment. It conditionally requests an adjustment through an object-dispatched operation, then stores the prospective value in the state field.

The established behavior is a state update combined with conditional calls. Interpreting the state as a logical length, the queried value as capacity, and the first queried value as an allocation quantum is plausible but not established. This contract uses the neutral terms **state**, **extent**, and **quantum**.

Two behaviors are especially important:

- On the growth path, a zero result from the first adjustment call causes a second adjustment call whose argument is the prospective state itself, not the previously requested increase.
- Every normally completing path stores the prospective state, regardless of the adjustment calls’ results. There is no explicit rollback or error return.

The arithmetic loop and external calls can prevent normal completion. The final state store is not reached in those cases.

## Interface

### Inputs and result

The function takes:

1. An object address, represented as a pointer to integer-sized storage.
2. A signed integer adjustment.

It returns no value.

The supplied representation uses signed and unsigned integer types consistent with a 32-bit execution model. The behavioral descriptions below use:

- **U32**: an unsigned 32-bit value, from 0 through 4,294,967,295.
- **S32**: a signed 32-bit interpretation, from −2,147,483,648 through 2,147,483,647.
- **Modulo-32 arithmetic**: retaining the low 32 bits of an arithmetic result.

The source does not independently establish the compilation ABI. In particular, overflow of the initial signed addition is not given a portable source-language meaning. Cases that require that overflow are documented separately rather than assigned an unconditional result.

### Object layout

Under the represented 32-bit layout:

| Byte offset | Required content or access |
|---|---|
| `0x00` | A dispatch-table address held in the first object word. |
| `0x04` | A signed 32-bit state field, read during calculation and branch selection and written on normal completion. |

The dispatch table is accessed at these byte offsets:

| Table offset | Role |
|---|---|
| `0x70` | Obtain the quantum. |

The offsets identify dispatch locations, not necessarily distinct implementations. The object’s table address and the selected entry are resolved at each relevant call site; a method address is not retained across the whole function.

For normal completion, the object must remain valid for the accesses actually performed. Its dispatch-table entries must be callable with the shown argument shapes. The state field must be readable and writable.

No null check, object-type check, table-bound check, or memory-access recovery is present.

These are access preconditions, not validation performed by this function. External operations must also return normally for execution to reach subsequent steps. No ownership, memory-preservation, or global-state-preservation guarantee is implied for those operations.

## Behavior

### 1. Obtain the quantum

The first external operation resolves the entry at dispatch-table offset `0x70` and calls it with the object address as its sole explicit argument.

Its result is retained as a U32 quantum.

This call occurs before the state value used to compute the prospective state is read. Therefore, any state change made by this call can affect the calculation.

### 2. Compute the prospective state

After the quantum call returns, the function reads the state field at object offset `0x04` and adds the signed adjustment. The result is retained as a U32 prospective state.

For inputs whose signed addition is representable, the result is established directly. A negative representable sum becomes its corresponding unsigned bit pattern when retained as U32.

The displayed addition has signed operands. The supplied evidence does not establish portable behavior when that addition exceeds the S32 range. A modulo-32 interpretation of those overflow cases would require additional machine-level or compilation evidence.

The prospective state is retained for the rest of the function. Later changes to the object’s state do not cause it to be recomputed.

### 3. Obtain the extent

The function resolves the entry at dispatch-table offset `0xa0` and calls it with the object address.

The returned value is retained as a U32 extent.

This lookup happens after the prospective-state calculation. If the earlier quantum call changed the dispatch table, that change can affect this call. The extent call may itself change object or global state; the function provides no protection against such changes.

### 4. Select a branch using a fresh state read

After the extent call returns, the state field is read again.

The function compares that freshly read S32 state against the S32 interpretation of the prospective state:

- If the fresh state is strictly smaller, it follows the growth path.
- Otherwise, it follows the non-growth path.

This is a signed comparison. Subsequent extent and quantum comparisons use unsigned arithmetic.

Consequently, the branch is not determined solely by whether the original adjustment was positive or negative. A dependency may change the state between the two reads. A prospective state with its high bit set also has a negative S32 interpretation.

### 5. Growth path

A candidate extent starts at the retained extent.

While the candidate is unsigned-less-than the prospective state, the function adds the retained quantum to the candidate using U32 arithmetic. The loop has no external calls and no explicit object accesses. Its additions can wrap.

Once the candidate is no longer below the prospective state:

- If the candidate equals the original retained extent, no adjustment call is made.
- Otherwise, the function resolves the entry at dispatch-table offset `0xc0` and calls it with:
  - the object address;
  - the U32 difference between candidate and original extent.

The return from this first adjustment call is tested as an integer:

- A nonzero result leads directly to the final state store.
- A zero result causes another lookup of the entry at `0xc0`, followed by a second call with the object address and the prospective state itself as the second argument.

The second call’s result is ignored.

The second argument in this fallback call is not a recomputed delta. It is the retained prospective state, even if the first call changed the object’s state, extent-related storage, or dispatch table.

The loop is repeated unsigned addition, not an established mathematical ceiling operation for all inputs. With a nonzero quantum, wraparound can change both its result and termination behavior. With a zero quantum and an initial extent below the prospective state, the loop cannot progress.

### 6. Non-growth path

The function computes the U32 difference between the retained extent and prospective state.

If that difference is unsigned-less-than the quantum, no adjustment request is made.

Otherwise, it calls F-d7be9cfb4000 with:

1. The U32 difference.
2. The retained U32 quantum.

The helper’s result is retained as a signed integer. The function multiplies that result by the unsigned quantum, then negates the product in unsigned arithmetic. Thus, in the 32-bit model, the adjustment argument is the low-32-bit additive inverse of the product.

After the helper returns, the function resolves the entry at dispatch-table offset `0xc0` and calls it with the object address and that adjustment argument.

The adjustment call’s result is ignored. There is no second attempt on this path.

The helper’s implementation is unavailable. In particular, this contract does not assume it computes integer division, returns a nonnegative value, or handles a zero second argument.

### 7. Commit the prospective state

Every normally completing path writes the retained prospective state into the field at object offset `0x04`.

This write occurs after all adjustment calls selected by the path. It overwrites any intervening value left in that field by a dependency.

There is no explicit final extent query, validation, rollback, or success indication. If a call does not return, a memory access fails, or the growth loop does not terminate, this final write is not reached.

## Side effects

### Direct memory effects

The function’s explicit object accesses include:

1. Reading the dispatch information needed for the quantum call.
2. Reading the state used to calculate the prospective state.
3. Reading the dispatch information needed for the extent call.
4. Reading the state again for branch selection.
5. Reading dispatch information for each adjustment call that is actually selected.
6. Writing the prospective state at normal completion.

Dispatch reads for an adjustment occur after any preceding call on that path has returned. In particular, the fallback adjustment entry is looked up after the first adjustment returns zero. The non-growth adjustment entry is looked up after F-d7be9cfb4000 returns.

The function makes no explicit allocation, deallocation, buffer copy, or ownership transfer. Such effects may occur inside dependencies.

### Retained values and mutable state

The quantum, extent, and prospective state remain the values already obtained; they are not refreshed after adjustment calls.

By contrast, the branch-selection state and later dispatch entries are read when needed. This distinction is observable if a dependency mutates the object.

No assumption is made that dependencies preserve global state, retain or release memory, or leave the object alive. Normal completion requires that their actual effects permit all subsequent accesses.

### Errors and completion

There is no explicit error-reporting channel.

A nonzero first growth-adjustment result suppresses the second call. A zero result selects the second call. These are established control-flow meanings; they do not prove that nonzero means success or zero means failure.

Results from the fallback growth adjustment and the non-growth adjustment do not affect the final store.

## Acceptance examples

These are conditional static examples, not runtime-test results. Unless stated otherwise, assume the dependencies return normally, the relevant storage remains valid, dependencies do not change the state or dispatch table, and the initial signed addition is representable.

### Growth requiring two quantum increments

Initial state: 10. Adjustment: 15. Quantum: 8. Extent: 16.

The prospective state is 25. The signed comparison selects growth. The candidate progresses from 16 to 24 to 32.

The first adjustment argument is 16, the difference between 32 and 16.

- If that call returns nonzero, there is no second adjustment call.
- If it returns zero, the second adjustment argument is 25.

Normal completion stores 25 in either case.

### Growth with sufficient retained extent

Initial state: 10. Adjustment: 5. Quantum: 8. Extent: 20.

The prospective state is 15, and growth is selected. The candidate starts above the prospective state, so it remains equal to the original extent. No adjustment call occurs. The final state is 15.

### Non-growth below the threshold

Initial state: 20. Adjustment: −2. Quantum: 8. Extent: 24.

The prospective state is 18. The non-growth difference is 6, which is below 8. Neither the helper nor an adjustment operation is called. The final state is 18.

### Non-growth with a specified helper result

Initial state: 20. Adjustment: −8. Quantum: 8. Extent: 40.

The prospective state is 12. The helper receives 28 and 8.

If F-d7be9cfb4000 returns 3, the adjustment argument is 4,294,967,272: the U32 representation of −24. The adjustment result is ignored, and normal completion stores 12.

This example specifies the helper result as a condition; it does not assert division semantics.

### State mutation changes branch selection

Suppose the state read after the quantum call is 10 and the adjustment is 5. The retained prospective state is therefore 15.

If the extent call changes the state to 30, the later signed comparison selects the non-growth path. Normal completion still stores 15.

### Unsigned subtraction wraps on the non-growth path

Initial state: 10. Adjustment: 0. Quantum: 8. Extent: 5.

The prospective state is 10. Equality selects non-growth. The U32 difference is 4,294,967,291, not a negative value. The helper is called with that difference and 8.

There is no explicit rejection of an extent smaller than the prospective state.

### Zero quantum prevents growth-loop progress

Initial state: 1. Adjustment: 1. Quantum: 0. Extent: 1.

The prospective state is 2, and growth is selected. The candidate remains 1 indefinitely. No adjustment call or final state store is reached.

### Inferred intent

The pattern resembles quantum-based growth and reduction of backing storage followed by a logical-state update. The helper’s arguments resemble a quotient calculation. These interpretations are not acceptance requirements.
