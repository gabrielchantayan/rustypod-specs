# F-fb78cb06a857

## Purpose

F-fb78cb06a857 resolves a packed request to a buffer address, loading a 512-byte cache slot when the required mapping is absent. A nonzero third argument additionally sets an associated bitmap bit after the lookup or load succeeds.

Two distinct cache-management paths are selected by a signed 16-bit field in the supplied context:

- A value of 8 selects a 32-bit tagged-entry path.
- Every other value selects a byte-mapping path with sequential slot allocation followed by eviction scanning.

“Cache,” “slot,” and “dirty bitmap” describe the apparent roles of the observed structures. The established behavior is the addressing, comparisons, dependency calls, and writes specified below; the broader storage protocol is not established.

The routine returns a computed buffer address on its success path and zero on several explicit failure paths. It has no separate error code and does not generally roll back allocation or eviction state after failure.

## Interface

### Arguments and result

| Item | Width and interpretation |
|---|---|
| First argument | 32-bit context address. The context must expose the fields and variable-length regions accessed by the selected path. |
| Second argument | Unsigned 32-bit packed request. Its interpretation depends on the context’s mode field. |
| Third argument | 32-bit value tested only for zero versus nonzero. Nonzero requests a bitmap update after success. |
| Result | 32-bit value carrying a computed buffer address, or zero on an explicit failure path. |

The returned address refers into a buffer selected through the context. No buffer allocation or release is directly visible in this routine. A successful return does not establish transfer of ownership, exclusivity, or any particular lifetime.

Zero is not structurally reserved by the address calculation. If a computed successful buffer address is zero, the result is indistinguishable from the explicit failure result.

### Preconditions

For defined, returning behavior:

- The context and every selected entry, bitmap byte, and buffer address must be accessible with the required access width.
- Derived addresses and base-plus-index values must be meaningful in the target’s 32-bit execution environment.
- Dependencies must meet whatever validity and termination requirements their implementations impose.
- If byte-mapping eviction is entered, the scan must eventually encounter a nonzero mapping at an index of at least one for termination to be guaranteed.

There are no visible checks for null context addresses, buffer bounds, malformed slot identifiers, or unavailable eviction candidates.

## Behavior

### 1. Capture mode and decode the request

The routine first reads the signed 16-bit mode field. That captured value determines the path for the rest of the invocation; the routine does not reread it to select a different path after a dependency call.

For modes other than 8, the decoded request index consists of bits 8 through 23 of the packed request, interpreted as an unsigned 16-bit value. Both the lowest eight bits and the highest eight bits are discarded.

For mode 8:

1. The decoded request index is the unsigned packed request shifted right by seven, giving a value from zero through `0x01ffffff`.
2. F-d7be9cfb4000 is called with that index and the 16-bit value read at offset `0x90`.
3. Its 64-bit result is split into two 32-bit words.
4. The low word, with bit 31 forced to one, becomes the expected tag.
5. The high word becomes the tagged-entry index and later bitmap index.

The meaning of those two returned words is otherwise unknown. In particular, interpreting them as quotient and remainder is not an established contract.

Only after this mode-8 dependency call does the routine read the 32-bit request bound at offset `0x1e0`. In other modes, the bound check occurs without that dependency call.

If the decoded request index is greater than or equal to the bound, the routine returns zero. There is no bitmap update. In mode 8, any effects of F-d7be9cfb4000 have already occurred.

### 2. Mode 8: tagged-entry lookup

The buffer address is calculated from the buffer-pool base and the low seven bits of the dependency-derived entry index:

- Slot number: entry index masked with `0x7f`.
- Byte displacement: slot number multiplied by 512.
- Buffer address: pool base plus that displacement.

The tagged entry is a 32-bit value at offset `0xb8` plus four times the full entry index. The entry index is not masked for this table access.

If the stored tag equals the expected tag, the routine uses the computed buffer address without calling either F-5306c1e4a5ff or F-a63889a8554d.

If the tag differs:

1. F-5306c1e4a5ff is called with the context address.
2. A zero result causes an immediate zero return. The routine itself has not replaced the tag.
3. A nonzero result is followed by writing the expected tag to the selected entry.
4. F-a63889a8554d is called with the arguments specified under Dependencies.
5. A zero result from that dependency causes the selected tag entry to be cleared to zero, followed by a zero return.
6. A nonzero result proceeds to the optional bitmap update and returns the previously computed buffer address.

The expected tag is installed before the data-related dependency is called. No synchronization or protection against observers seeing this intermediate state is established.

The pool-derived buffer address is computed before F-5306c1e4a5ff. If that dependency changes the pool-base field, this invocation still uses its already computed address.

### 3. Other modes: existing byte mapping

For a decoded request index of zero, a nonzero 32-bit value at offset `0xb4` is sufficient to treat the mapping as present. In that case, the mapping byte need not be tested for presence, but it is still read to select the buffer slot.

Otherwise, the byte at offset `0xb8` plus the decoded request index determines presence:

- Nonzero means an existing mapping.
- Zero means an absent mapping.

For an existing mapping, the low seven bits of the mapping byte select the 512-byte buffer slot. The upper bit does not affect the returned address. Neither cache-management dependency is called on this path.

Thus, request index zero can be considered present with a zero mapping byte and return slot zero, provided the special validity field is nonzero.

### 4. Other modes: assign a missing mapping

For an absent mapping, the routine reads the unsigned 16-bit allocation counter and compares it for equality with the unsigned 16-bit threshold.

#### Counter differs from threshold

The old counter value becomes the slot identifier for the new mapping. The allocation counter is incremented and stored back as 16 bits.

This is an equality decision, not a less-than capacity check. A counter greater than the threshold still takes this allocation path. Incrementing `0xffff` stores zero.

The slot identifier retained for address calculation is the full old 16-bit counter. Its low eight bits are stored in the byte mapping; its low seven bits select the buffer slot.

#### Counter equals threshold

The routine calls F-5306c1e4a5ff with the context address. A zero return immediately returns zero.

After a nonzero return, eviction scanning proceeds using the then-current cursor and bound fields:

1. A zero cursor is changed to one.
2. A cursor greater than or equal to the current request bound is changed to one.
3. Beginning at the cursor, request indices are examined in increasing order while below the bound.
4. The first nonzero mapping byte is selected.
5. That byte is saved as the replacement slot identifier.
6. The selected old mapping byte is cleared.
7. The cursor is set to the selected index plus one, truncated to 16 bits.

If no nonzero mapping is found in the scanned range, the cursor is reset to one and scanning repeats. Index zero is never an eviction candidate.

There is no visible exhausted-cache return. If no eligible nonzero mapping becomes available, this path may loop indefinitely. Bounds of zero or one leave no eligible index to inspect.

The allocation counter is not incremented by this eviction path.

### 5. Other modes: load the newly assigned mapping

After either allocation or eviction:

1. The selected slot identifier’s low eight bits are written into the requested mapping byte.
2. The buffer address is calculated using the selected identifier’s low seven bits and a 512-byte stride.
3. F-a63889a8554d is called.

If the dependency returns zero, the requested mapping byte is cleared and the routine returns zero. Other changes are not rolled back:

- A sequential counter increment remains.
- An evicted mapping remains cleared.
- An advanced eviction cursor remains advanced.
- Dependency side effects are not undone.

If the dependency returns nonzero, the routine writes the 32-bit value one at offset `0xb4`. This write occurs after every successful new byte-mapping load, not only a load for request index zero.

An existing-map hit does not perform this validity write.

### 6. Optional bitmap update and return

Every successful path reaches the same final decision.

If the third argument is nonzero, one bitmap bit is set by a byte read-modify-write:

- In mode 8, the relevant index is the high 32-bit word returned by F-d7be9cfb4000.
- In every other mode, it is the decoded request index.
- The byte displacement from offset `0x92` is the index masked with `0x7ffff`, then shifted right by three.
- The selected bit is determined by the index’s low three bits.

The existing byte is ORed with that bit, preserving its other bits. Indices differing by a multiple of `0x80000` therefore select the same bitmap location and bit.

A zero third argument causes no bitmap access on this final path. Explicit failure returns do not perform this update. The routine then returns the selected buffer address.

## Side effects

Direct writes are limited to the selected tag entry, byte mappings, cursor, allocation counter, special validity field, and optional bitmap byte, as described above.

The ordering has externally relevant consequences:

- A mode-8 tag is installed before F-a63889a8554d runs and cleared if that call reports failure.
- A byte mapping is installed before that dependency runs and cleared if it reports failure.
- An eviction victim is cleared before its slot identifier is assigned to the requested mapping.
- Successful new byte-mapping loads set the special validity field before the optional bitmap update.
- The final bitmap update is not atomic by anything established in the evidence.

All dependency side effects remain unknown. No dependency may be assumed to preserve context fields, other globals, buffer contents, or memory ownership. Fields read after a call can therefore reflect changes made during that call, whereas already computed indices, tags, and addresses remain the values captured earlier.

There is no visible allocation, deallocation, exception handling, or comprehensive failure rollback.

## Dependencies

### F-d7be9cfb4000

- Called only for mode 8.
- Called before the decoded-index bounds check.
- Receives the decoded request index and a 16-bit context value from offset `0x90`.
- Produces a 64-bit result used as two 32-bit words.
- Its arithmetic meaning, errors, and side effects are documented_only.

### F-5306c1e4a5ff

- Receives the context address.
- Called on a mode-8 tag mismatch or when the byte-mapping allocation counter equals its threshold.
- Zero is treated as failure; any nonzero result permits further processing.
- Its apparent preparation or flush role is inferred intent, not an established guarantee.
- Context mutations, external I/O, and ownership effects are documented_only.

### F-a63889a8554d

Receives five arguments, in order:

1. The 16-bit context value read at offset `0x78`.
2. The 32-bit base read at offset `0x80`, plus the decoded request index.
3. The selected buffer address.
4. The constant one.
5. The constant zero.

The first two context values are read for the call after any preceding F-5306c1e4a5ff invocation.

Zero is treated as failure; any nonzero value is treated as success. Although its use suggests a one-unit transfer into a cache buffer, transfer direction, unit meaning, completion guarantees, partial effects, and ownership behavior are not established.

## Acceptance examples

These are conditional static examples, not executed tests. They assume valid addresses and that dependencies have no additional mutations except those explicitly stated.

1. **Non-mode-8 decoding.** A packed request of `0xab1234ff` decodes to index `0x1234`. Changing only its highest or lowest byte leaves that index unchanged.

2. **Mode-8 rejection still invokes a dependency.** If the packed request decodes to index five and the bound read afterward is five, F-d7be9cfb4000 has already been called. The routine returns zero without a tagged-entry lookup or final bitmap update.

3. **Tagged hit.** Suppose F-d7be9cfb4000 returns high word three and low word `0x42`. A stored tag of `0x80000042` matches. The returned address is the pool base plus `0x600`; neither miss-handling dependency is called.

4. **Tagged load failure.** On a tag mismatch, suppose F-5306c1e4a5ff returns nonzero and F-a63889a8554d returns zero. The expected tag is written before the latter call, then cleared. The result is zero, with no final bitmap update.

5. **Special index-zero hit.** In a non-8 mode, index zero with a nonzero special validity field and a zero mapping byte is an existing mapping. It returns the pool base without loading a new mapping.

6. **Allocation failure preserves the increment.** With an absent mapping, counter two, and threshold four, the counter becomes three and mapping byte two is installed. If F-a63889a8554d returns zero, the mapping becomes zero again, but the counter remains three.

7. **Eviction preserves the full mapping byte.** If the first eligible victim contains `0x85`, that victim byte is cleared and `0x85` is assigned to the requested mapping. The buffer address uses slot five. Failure of the subsequent dependency clears the new mapping but does not restore the victim.

8. **No eviction candidate.** If the counter equals its threshold, preparation succeeds, and all mappings at indices one through bound-minus-one remain zero, the routine does not have an established terminating result. It repeatedly rescans.

9. **Bitmap update.** With relevant index ten and a nonzero third argument, bit two of the byte at context offset `0x93` is set. Other bits are preserved. A zero third argument leaves that byte untouched by the final step.

## Uncertainties

The following remain documented_only:

- Native endianness, alignment requirements, and concrete context allocation size.
- Valid ranges linking entry indices, mapping capacity, bitmap capacity, and buffer-pool size.
- The semantic meaning of the mode value, allocation threshold, tag words, and mapping-byte high bit.
- Whether F-5306c1e4a5ff guarantees a nonzero eviction candidate or performs a flush.
- Dependency error details, partial I/O, reentrancy, global mutations, and ownership effects.
- Whether external invariants prevent counter truncation, bitmap aliasing, overlapping layout regions, invalid derived addresses, or nonterminating eviction.
- How callers distinguish an actual zero buffer address from failure.

No protective behavior is inferred for these cases beyond the explicit operations described.
