# F-9d237a026cd7

## Purpose

F-9d237a026cd7 resolves an input description, collects bytes accepted by a classification dependency, invokes processing and result-selection dependencies, and conditionally transfers a selected result into caller-managed storage.

Its 32-bit return value is:

- **0:** the explicit result-publication path was not completed.
- **1:** the result-transfer operation returned normally and the function subsequently wrote the output-size slot.

A return of 1 does not establish successful allocation, valid transferred contents, or persistence of output state through cleanup. Allocation results and transfer results are not checked, and subsequent cleanup dependencies have unknown effects.

“Input,” “processing,” “selection,” and “allocation” describe apparent roles inferred from call-site use. The established behavior is the control flow, memory accesses, arithmetic, and dependency interactions below.

## Behavior

The resolver receives, in order:

1. Argument 2.
2. The initial descriptor.
3. An address for the signed offset.
4. An address for the unsigned required-count word.

The required-count address is therefore exposed to a dependency. The function does not subsequently capture one immutable target: it rereads that storage throughout collection.

### Allocation and live-count collection

F-fab3799b3190 receives the required-count word’s value **at allocation time**. Its returned address becomes the filtered-storage base. No allocation-failure check follows.

The accepted-byte counter starts at zero. Collection depends on repeated unsigned comparisons against the **current** required-count word:

- Before each prospective read, the current required count is compared with the accepted counter.
- After classification accepts a candidate, the current required count is checked again before storing.
- After collection exits, the current required count is checked again to decide whether processing is allowed.

These accesses need not observe the allocation-time value.

When the pre-read comparison finds that the accepted counter is at least the current required count, collection exits without another read. Otherwise, F-8737e491f1cd receives the reader-like temporary, request amount **0x400** or 1,024, candidate-region address, and scratch-count address.

A nonzero read result exits collection without inspecting candidates from that call. A zero result enters candidate inspection.

Candidates are visited in increasing byte-offset order while the unsigned candidate index is below the current scratch count. The count is tested repeatedly, not captured once per read. Its address is exposed to the read dependency, and it is not explicitly reset before each read.

For each visited candidate:

- Its 8-bit value is read and passed to F-c181a51d2f48.
- The returned value is interpreted as unsigned.
- A value of **64 or greater** rejects the candidate.
- A value **below 64** triggers another comparison against the current required count.
- If the accepted counter is already at least that count, candidate inspection stops without storing this candidate.
- Otherwise, the candidate byte is read again, stored at the filtered base plus the accepted counter, and the counter advances by one.

The stored value is the second byte read, not the classifier result. Classification may change the candidate region between those reads; the function does not enforce equality.

After candidate inspection, execution returns to the pre-read comparison. Rejected candidates can therefore still be classified after the accepted counter has reached an earlier count. A subsequent classifier call can change the exposed required count and affect whether another read occurs.

### Completion and progress conditions

After collection exits, processing is attempted exactly when the accepted counter is at least the required-count value observed by the processing gate.

Consequences requiring a **stable required count** include:

- A count of zero at allocation and throughout collection causes no reads.
- Once the counter reaches that stable count, no further read is initiated.
- A read failure while the counter remains below that count prevents processing.
- Repeated successful reads with zero candidates cannot make accepted-byte progress.

Without stability, the behavior differs:

- An allocation requested with zero can be followed by reads if the exposed count increases before the pre-read comparison.
- Reaching a previously observed target does not prevent later reads if a subsequent classifier call raises the count.
- A nonzero read result can still be followed by processing if the required count has become no greater than the accepted counter by the processing gate.
- A reduced count can make previously collected bytes sufficient without further acceptance.

There is no explicit timeout, retry limit, or no-progress failure. Increasing the count does not resize filtered storage. Safe storage capacity must cover actual stores, not merely the allocation-time count.

The external transfer operation receives:

- The descriptor’s source-address field at offset 0x2c.

After the transfer returns normally, the function writes the **initially calculated** size to the output-size slot and sets its return flag to one. Descriptor mutation can therefore make allocation size, transfer length, and published size disagree.

## Side effects

### Explicit output effects

The explicit output-publication path can release an old address before obtaining a replacement. No rollback or allocation-result validation is visible.

When replacing storage, the output-address slot is written before transfer. The output-size slot is written afterward. A matching size paired with a zero address still reaches transfer without allocation.

These are explicit accesses, not guarantees that dependencies leave caller state unchanged. Aliasing can also make a publication write affect later reads or the eventual size write affect transferred bytes.

### Ownership and memory requirements

The old output address must be acceptable to F-8349c252c168 with tag 27 whenever the replacement branch releases it. The replacement is published to the caller, but its eventual ownership protocol is not independently established.

Filtered storage is passed to F-58ba61416cc9 after collection or processing. This establishes a disposal-shaped call, not proof of deallocation or exclusive ownership. Processing dependencies may retain references; their contracts are unavailable.

Safe execution requires adequate candidate storage, filtered-storage capacity for every actual store, valid descriptor fields, a readable transfer source, and a writable destination spanning the actual transfer length. No visible checks enforce these requirements.

The 1,024-byte read request does not establish scratch capacity or constrain the reported count. Overlap semantics, address-arithmetic validity, count mutation, extent overflow, and aliases remain caller/dependency constraints rather than checked errors.

## Acceptance examples

These are conditional static criteria, not executed tests. Unless an example specifies mutation, relevant storage is assumed stable across dependencies; required memory is assumed valid.

1. **Resolution failure.** Zero resolution status leads to initial-descriptor cleanup and return 0. Neither bracket call nor explicit output-slot access occurs.

2. **Positioning failure.** Nonzero positioning status prevents filtered allocation. The closing-global value is loaded for bracket closure, followed by reader cleanup and descriptor cleanup.

3. **Original-byte filtering.** For a stable target of two, three stable candidates classified as 63, 64, and 0 produce the first and third candidate bytes in order. Classification results are not stored.

4. **Stable zero count.** A count remaining zero through allocation, collection, and the processing gate causes allocation with zero, no reads, and an attempted processing path.

5. **Zero allocation followed by reads.** If allocation receives zero but changes the exposed required count to one, the next comparison requests input. This does not resize storage; a valid subsequent store requires adequate writable backing despite the zero request.

6. **Target reached, then raised.** With initial count one, the first candidate is accepted. Classification of a later rejected candidate changes the count to two. If that remains the count, another read is attempted after candidate inspection. Adequate filtered capacity is a separate precondition.

7. **Read failure with changed count.** One byte has been accepted toward a count of two. The next read returns nonzero but reduces the count to one. The processing gate passes despite that read status. If the count remains two instead, processing is skipped.

8. **Output reuse and replacement.** A stable extent of 100 yields size 128. Prior size 128 bypasses tagged release/allocation; prior size 64 invokes allocation of 128 and first releases a nonzero old address. Transfer precedes publication of size 128.

9. **Extent mutation.** Initial extent 100 yields allocation/comparison size 128. If an intervening dependency changes the extent to 200, the later transfer length is 228, while the final size write remains 128. No mismatch check prevents this.

10. **Global timing.** A change to the initialization global during F-5b24edfb22c0 affects the subsequently stored initialization value. A change to the distinct closing global during filtered-storage disposal affects the later bracket-closing argument.

11. **No-progress reads.** With a stable positive required count, repeated zero-status reads reporting zero candidates neither advance acceptance nor trigger an explicit no-progress error.
