# F-3d13a864bc0b

## Purpose

F-3d13a864bc0b performs an ordered sequence of memory reads, mixed-width writes, address calculations, and an unresolved indirect invocation.

The established behavior is memory mutation followed by indirect dispatch. No higher-level purpose—such as initialization, parsing, destruction, or collection maintenance—is established. Constants that correspond to printable characters do not establish text processing.

Access order is material. Addresses are repeatedly loaded from writable memory, and no separation between objects, fields, or globals is established. A store can therefore change a later address selection. Repeated writes and read/write-back pairs remain part of the contract even when they appear redundant.

## Interface

| First argument | 32 bits | Stored as four bytes and separately narrowed to one byte. |
| Second argument | 32 bits | No explicit use in the supplied body. |
| Third argument | 32-bit address-bearing value | Used immediately for a self-reference store at offset `0x54`. |
| Fourth argument | 32 bits | Stored as one byte and as four bytes in the state root. |

The second argument’s absence from explicit expressions does not resolve the indirect invocation’s machine-level calling convention.

### Ambient inputs and terminology

Two incoming address-bearing machine values have no visible initialization:

- **Context root:** supplies an early address through offset `0x14`.
- **State root:** supplies the initial and working objects and receives early mutations.

The **initial object** is the address captured from state-root `0x14` near entry. The **working object** is a later capture of that same field. These names identify captured values, not types; the values need not be equal.

Other object names below similarly identify specific captures. A later reload is identified explicitly and must not be replaced by an earlier capture.

Three external four-byte values are called **global alpha**, **global beta**, and **global gamma**, in their eventual read order.

### Result and preconditions

No explicit result value is established. If the terminal indirect invocation returns normally, the visible body returns without further explicit memory accesses.

Successful completion requires every executed access to address valid storage for its width and the execution environment’s alignment requirements. Address formation includes ordinary offsets, subtraction, addition of independently obtained values, doubling, and a byte-derived integer.

No explicit null, bounds, alignment, arithmetic-overflow, ownership, or accessibility checks are present. No recoverable error result or rollback is established.

## Behavior

### Width and ordering conventions

Unless explicitly identified as a byte or two-byte access, every memory read and write described below is **four bytes**. Address-bearing captures are also four bytes in the supplied representation.

A low-byte store retains eight bits; a low-sixteen-bit store retains sixteen bits. The terminal plain-character conversion has a separate signedness uncertainty described below.

The following account is chronological. Captures survive later changes to their source storage. Reloads use memory at their actual position in the sequence. Nested traversals read the outer address before reading the selected field.

### 1. Entry and initial-object mutations

The first store writes the third argument to its own offset `0x54`. The function then reads context-root `0x14`, obtaining an entry destination. It writes the fourth argument’s low byte to state-root `0x11`, reads state-root `0x14`, and writes that read’s low byte to entry-destination `0x15`.

Only afterward does it capture the initial object from state-root `0x14`, followed by an **early state value** from state-root `0x64`.

The first argument is written to initial-object `0x10`. Next comes a state-root self-reference store at `0x44`, followed by the first argument’s low byte at initial-object `0x14`. State-root `0x54` then receives the fourth argument.

The function captures state-root `0x74` as an **early state link**. State-root byte `0x09` receives the low byte of the state-root address **before** initial-object `0x54` receives that link. Initial-object `0x10` receives `0x6e`; state-root `0x44` again receives its own address; initial-object `0x20` receives `0x6e`.

A fresh state-root `0x64` read supplies a **refreshed state value**. Its low byte goes to initial-object `0x09`. Initial-object `0x74` is then read as the **linked object**, whose `0x54` is captured for later write-back.

The ensuing byte stores occur in this order: initial-object `0x1c` receives `0x79`; state-root `0x11` receives the refreshed value’s low byte; state-root `0x09` receives the early value’s low byte; initial-object `0x1c` receives `0x68`; state-root `0x11` again receives the refreshed value’s low byte; linked-object `0x11` receives the state-root address’s low byte.

A new state-root `0x74` read establishes the **later state link**. Initial-object `0x10` receives its captured `0x50` value. Linked-object `0x54` receives its previously captured value as an actual write-back. Initial-object byte `0x00` receives the captured `0x50` value’s low byte, and byte `0x09` receives the state-root address’s low byte.

## Acceptance examples

These are conditional acceptance requirements, not executed tests.

1. **Entry ordering:** An access trace must place the first-argument store to initial-object `0x10` before the state-root `0x44` self-reference, and that self-reference before the byte store to initial-object `0x14`. State-root byte `0x09` must precede initial-object `0x54`.

2. **Separated repeated store:** The two initial-object byte `0x00` stores must remain separated by the intervening accesses, including working-object selection, linked-object byte `0x11`, and initial-object `0x44`.

3. **Distinct destinations:** If the subtraction anchor and old working link differ, the subtraction-relative store uses the former, while the four-byte `0x64` store at offset `0x30` uses the latter.

4. **Reload-sensitive traversal:** If an intervening store changes a field before a specified reload, traversal uses the reloaded value. This applies to state-root `0x14`, branch-object `0x14`, working-object `0x64`, and dispatch-side `0x04`.

5. **Mixed-width interleaving:** The constant-update target receives four-byte `0x66` at `0x10`, then the working-object `0x44` store occurs, then the target receives byte `0x66`. A single replacement write does not satisfy this access sequence.

6. **Delayed store:** Dispatch-side `0x04` is captured before the consecutive working-object byte `0x0d` writes. Its target’s `0x30` store occurs after those writes and after replacement data reaches working-object `0x64`.

7. **Final capture boundary:** Both continuation-field captures precede the final-object `0x54` self-reference. Leaf-parent `0x04` is read afterward. Aliasing must not move the self-reference across either boundary.

8. **Terminal conversion:** For byte `0x80`, unsigned plain-character interpretation yields byte-derived value `0x00000080`, write addresses `0x000000c5` and `0x000000c4`, and first dispatch argument `0x000000c4`. Signed interpretation with sign extension yields `0xffffff80`; under a wrapping 32-bit address model, the corresponding values are `0xffffffc5`, `0xffffffc4`, and `0xffffffc4`. These are alternative environmental cases, not an established platform choice.
