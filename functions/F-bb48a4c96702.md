# F-bb48a4c96702

## Purpose

F-bb48a4c96702 coordinates a requested change to an externally managed current selection or state. It compares the requested 32-bit value with a value obtained through object dispatch, skips most processing when they match, and otherwise invokes a transition sequence. Depending on two additional inputs, it may then create and submit a history-related object and perform further state processing.

The selection, history, and flag terminology describes inferred roles, not established application semantics. The established contract is the ordering of calls, comparisons, direct memory writes, and conditional exits described below.

The routine has no explicit result value. Its observable results are dependency calls, indirect method calls, and up to two direct memory writes. Some calls occur even when the requested selection already matches the current value.

## Interface

### Inputs and result

The routine accepts three 32-bit integer inputs:

| Input | Contract |
|---|---|
| Requested value | Compared for equality with a global discriminator and with a value returned through indirect dispatch. Forwarded unchanged to the transition method. |
| Second control | Tested only for equality with zero. |
| Third control | Tested only for inequality with zero. |

The second and third controls are not restricted to canonical Boolean values. Any nonzero representation satisfies their respective nonzero tests. Their signedness does not affect the decisions made here.

There is no explicit return value or defined success indicator.

### External state and object layouts

The routine accesses three distinct global roles:

- **Special discriminator:** a 32-bit value compared with the requested value at entry.
- **Initial state value:** a 32-bit value read after the first call to F-5c5958cfd5fe and passed to F-e2d95185a0cc.
- **Final destination base:** an address read only if execution reaches the final direct store. The store targets four bytes after this base.

Their initial values, storage relationships, synchronization, and mutability are not established. They must not be assumed immutable across dependency calls.

The visible operations use a 32-bit address and dispatch-entry model. Relevant byte offsets are:

| Location | Visible use |
|---|---|
| Address returned by F-fdd8589eca2d, plus `0x80` | Store the 16-bit value 6. |
| First word of an object used for dispatch | Obtain a dispatch-table address. |
| Table offset `0x14` on the primary object | Call a method with the primary object as explicit argument; receive a secondary object address. |
| Table offset `0x68` on the secondary object | Call a method with no explicit arguments in the supplied representation; receive the current 32-bit value. |
| Table offset `0x1DC` on the service object | Call a method with the service object as explicit argument. |
| Table offset `0x50` on the primary object | Call a method with the primary object, requested value, and zero. |
| Table offset `0x04` on the primary object | Call a method with the primary object and a constructed 32-bit value. |
| Table offset `0x19C` on a newly acquired service object | Call a method with that service object as explicit argument. |
| Final destination base, plus `0x04` | Store a computed 32-bit value. |

Offsets are byte offsets, not entry indices. The absence of an explicit argument on the secondary-object query is significant; this contract does not add a receiver argument absent from the evidence.

### Preconditions

Every address actually dereferenced on the selected execution path must be valid for the corresponding read, write, or indirect call. This includes object headers, dispatch tables, method entries, the conditional 16-bit destination, and the conditional final 32-bit destination.

The routine performs no visible null checks, allocation-failure checks, dispatch validation, or address-range validation.

## Behavior

### 1. Entry-specific update

First, the routine reads the special discriminator and compares it with the requested value.

If they match:

1. Call F-fdd8589eca2d with no explicit arguments.
2. Add `0x80` bytes to its returned address.
3. Write the 16-bit value 6 at that location.

If they do not match, neither the call nor the write occurs.

This processing precedes the current-value query. Consequently, an otherwise redundant request can still produce this call and write.

### 2. Acquire objects and query the current value

Next, in order:

1. Call F-17fe47085641 with no explicit arguments and retain its returned service-object address.
2. Call F-76b1c50b12f7 with no explicit arguments and retain its returned primary-object address.
3. Read the primary object's dispatch-table pointer and its entry at byte offset `0x14`.
4. Invoke that entry with the primary object as explicit argument and retain the returned secondary-object address.
5. Read the secondary object's dispatch-table pointer and its entry at byte offset `0x68`.
6. Invoke that entry with no explicit arguments shown in the evidence.

Compare the resulting 32-bit value with the requested value. If equal, return immediately.

This exit occurs before either call to the state-setting dependency, before the transition method, before allocation, and before the final direct store. It does not undo the entry-specific write or any side effects of the calls already made.

### 3. Perform the transition sequence

When the queried value differs from the requested value:

1. Call F-5c5958cfd5fe and retain its 32-bit result as the first saved value.
2. Read the global initial state value.
3. Call F-e2d95185a0cc with that global value.
4. Dispatch through offset `0x1DC` on the previously retained service object, passing that object.
5. Dispatch through offset `0x50` on the previously retained primary object, passing that object, the requested value, and a 32-bit zero.
6. Call F-e2d95185a0cc with the first saved value bitwise-ORed with `0x00004000`.

The OR sets bit 14 and preserves the remaining 31 bits. It is not an arithmetic addition.

The value used in step 6 comes from the earlier F-5c5958cfd5fe result, not a fresh query. Changes made by intervening calls do not change that retained argument.

The dispatch-table pointers and entries for these calls are read at their respective call sites. The routine retains the original object addresses but does not establish that their contents remain unchanged across calls.

### 4. Apply the optional-processing gate

After the transition sequence, return immediately if both conditions hold:

- The second control is zero.
- The third control is nonzero.

All other combinations continue. In particular:

| Second control | Third control | Continue to history-related processing? |
|---|---|---|
| Zero | Zero | Yes |
| Zero | Nonzero | No |
| Nonzero | Zero | Yes |
| Nonzero | Nonzero | Yes |

This gate never suppresses the preceding transition sequence.

### 5. Construct and submit a history-related value

If processing continues:

1. Call F-8157a180d901 with `0x78`, decimal 120.
2. Pass its returned 32-bit value to F-1e30c9d0c388, together with the address of the fixed string “CntrlHistoryFn”.
3. Retain the 32-bit result of F-1e30c9d0c388.
4. Dispatch through offset `0x04` on the retained primary object, passing that object and the construction result.

The constant 120 is established as an argument. Interpreting it as an allocation size is inferred from the call pattern, not proven by this routine alone.

No validation separates these calls. If the first dependency returns zero or another failure representation, that value is still passed to F-1e30c9d0c388 if execution returns normally. Likewise, the construction result is submitted without a visible validity check.

### 6. Perform final state processing

After submission:

1. Call F-17fe47085641 again and retain the returned service-object address.
2. Call F-5c5958cfd5fe again and retain its 32-bit result as the second saved value.
3. Call F-e2d95185a0cc with `0x00000010`.
4. Dispatch through offset `0x19C` on the newly acquired service object, passing that object.
5. Call F-d2bc4a2e390c with two identical 32-bit arguments, both equal to the second saved value.
6. Interpret the returned result as an unsigned 64-bit quantity.

The second service-object acquisition is not interchangeable with the first. The routine uses the address returned by the second acquisition for this dispatch, even if it differs from the earlier address.

No post-call read is used to replace the second saved value before it is passed twice to F-d2bc4a2e390c.

### 7. Conditionally write the final word

Divide the 64-bit result conceptually into:

- **Lower word:** bits 0–31.
- **Upper word:** bits 32–63.

Return without a direct final store when both conditions hold:

- The lower word is nonzero.
- Bit 46 of the complete result is clear.

The lower-word comparison is represented as a signed 32-bit conversion followed by a comparison with zero. For this decision, only whether those 32 bits are all zero matters.

In every other case, read the final destination base and write the following 32-bit value at base plus `0x04`:

**The upper word, with bit 14 cleared.**

Equivalently, the stored value is the upper word masked with `0xFFFFBFFF`. Bit 14 of the upper word is bit 46 of the original 64-bit result.

Thus:

- A zero lower word always permits the store.
- A nonzero lower word permits the store only when bit 46 is set.
- Whenever the store occurs, the tested upper-word bit is cleared in the stored value.
- The lower word contributes only to the store decision, not to the stored data.

The upper word is obtained by an unsigned 64-bit right shift of 32 bits. There is no sign extension in this operation.

## Side effects

The routine directly performs only these visible memory writes:

1. A conditional 16-bit write of 6 at the address returned by F-fdd8589eca2d plus `0x80`.
2. A conditional 32-bit write at the final destination base plus `0x04`.

These are ordinary width-specific stores. Byte order and atomicity guarantees are not established.

All other mutations are delegated to dependencies or indirect methods. Their effects may include changes to globals or object contents, but this routine does not establish their extent.

No explicit release, destructor call, rollback, or error cleanup appears. The routine does not establish ownership of the value returned by F-8157a180d901, the value returned by F-1e30c9d0c388, or any object acquired through dependencies. Submission through the primary object's method must not be assumed to transfer ownership.

The state-setting calls are not evidence of a general save-and-restore guarantee. The first saved value is modified by setting bit 14 before being passed back. Later, the routine passes the constant `0x10` and does not visibly restore the second saved value through F-e2d95185a0cc. Effects of subsequent dependencies remain unknown.

No explicit error result is produced. If a dependency does not return normally, later operations described here are not established to occur.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. They assume all reached calls return normally and all reached accesses are valid.

### Already-current request

If the secondary-object query returns the requested value:

- The routine returns after that comparison.
- No transition, allocation, history submission, or final processing occurs.
- If the requested value also matched the entry discriminator, the earlier 16-bit write of 6 has already occurred.

### Transition without history-related processing

If the current value differs, the second control is zero, and the third control is any nonzero value:

- The complete transition sequence occurs.
- Its last F-e2d95185a0cc argument is the first saved value with bit 14 set.
- No allocation/construction calls occur.
- No second service acquisition or final direct store occurs.

### Noncanonical control values

If the current value differs and both controls are nonzero, history-related processing proceeds. The controls need not equal 1.

### Final result with zero lower word

If F-d2bc4a2e390c returns `0x1234567800000000`, the lower word is zero. The routine stores `0x12341678` at the final destination base plus `0x04`.

### Final result rejected by the gate

If the result is `0x0000000000000001`, the lower word is nonzero and bit 46 is clear. The routine returns without the final direct store.

### Final result accepted through bit 46

If the result is `0x0000400000000001`, the lower word is nonzero but bit 46 is set. The routine stores zero: the upper word is `0x00004000`, and clearing its bit 14 produces zero.

### Changed service identity

If the two calls to F-17fe47085641 return different addresses, the `0x1DC` dispatch uses the first address and the `0x19C` dispatch uses the second. The routine does not force them to identify the same object.
