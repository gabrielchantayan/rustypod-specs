# F-97743e35a521

## Purpose

F-97743e35a521 initializes two address-like cursors, then repeatedly invokes a two-stage processing pipeline. The first stage receives the first cursor by reference and a four-byte scratch region. The second stage receives the second cursor by reference and the same scratch region. After each group of iterations, the function applies separate row-transition adjustments to both cursors.

The established behavior is the initialization, dependency-call ordering, loop control, and cursor adjustments. A two-dimensional transfer or conversion is inferred intent, not an established data-format contract. The visible function does not itself read a source element, write a destination element, or establish that either cursor advances by an element width during a dependency call.

This contract distinguishes:

- **Established static evidence:** behavior directly represented in the supplied function.
- **Inferred intent:** plausible interpretation of the scaling factors and loop structure.
- **documented_only:** behavior requiring dependency implementations, machine-level details, or runtime evidence that is not available.

## Behavior

### Initialization order

The function first saves arguments 1 through 4 in local storage. Argument 3 is copied as an opaque four-byte quantity.

It then makes two initialization calls to F-082b668da333, in this order:

1. The first call receives argument 2 shifted left by one bit, followed by argument 15.
2. The second call receives argument 9 shifted left by two bits, followed by argument 16.

Call the returned integer values the **first stride** and **second stride**. “Stride” is a descriptive name; the dependency’s actual computation and units are unknown.

Both initialization calls complete before either cursor is initialized.

The cursor initializations are then performed in this order:

1. First cursor = first stride × argument 5 + saved argument 4 × 2 + saved argument 1.
2. Second cursor = argument 12 × second stride + argument 11 × 4 + argument 8.

Thus the scaling factors two and four apply to the respective horizontal-offset-like inputs. Nothing in this function verifies that the resulting values designate accessible storage.

### Processing order

The inner counter is initialized from argument 6.

The function enters the outer loop without first testing argument 7. It likewise enters the inner loop without first testing the inner counter.

Each inner iteration performs these actions in order:

1. Calls F-a0d7716b0f77 with:
   - The address of the shared four-byte transfer scratch region.
   - The address of the first-stage-only four-byte scratch region.
   - The address of the first-cursor slot.
2. Calls F-94989df6c6d2 with:
   - The address of the second-stage-only four-byte scratch region.
   - The address of the second-cursor slot.
   - The address of the shared transfer scratch region.
3. Decrements the inner counter.
4. Repeats the inner iteration if the decremented counter is nonzero.

The second stage therefore runs only after the first stage returns normally. It receives the same transfer-region address that the first stage received.

The visible function does not inspect, validate, copy, or clear that region between the two calls. It also does not establish that the first stage writes all four bytes, that the second stage reads them, or that the second stage leaves them unchanged.

Both cursor slots are passed by address. The row-transition calculations use their values after the processing calls, including any mutations those calls perform.

### Row transition and termination

After the inner loop finishes, the function:

1. Decrements the outer counter.
2. Adds first stride − 2 × argument 6 to the current first cursor.
3. Adds second stride − 4 × argument 6 to the current second cursor.
4. Resets the inner counter to argument 6.
5. Repeats the outer loop if the decremented outer counter is nonzero.

These cursor adjustments occur even after the final processing row. The function does not skip the last row transition.

For positive, representable counts, and assuming all calls and arithmetic complete normally:

- Argument 7 determines the number of outer iterations.
- Argument 6 determines the number of paired processing calls per outer iteration.
- Each processing dependency is called argument 6 × argument 7 times.
- The two initialization calls occur once each, not once per row.

The multiplication in that call-count statement is mathematical notation, not an additional multiplication performed by the function.

## Acceptance examples

These are conditional static acceptance scenarios, not runtime test results.

### One element, one row

Given arguments 6 and 7 both equal to one, normal dependency returns, and valid arithmetic:

- F-082b668da333 is called twice.
- F-a0d7716b0f77 is called once.
- F-94989df6c6d2 is called once, after the first processing call.
- Both cursor row adjustments occur.
- The function returns without a value.

An implementation that skips row adjustment on the last row would not preserve the visible operation sequence.

### Two elements, three rows

Given argument 6 equal to two and argument 7 equal to three:

- There are six processing-call pairs.
- Within every pair, F-a0d7716b0f77 precedes F-94989df6c6d2.
- Each row contains two pairs before its cursor adjustments.
- Each row adds first stride − 4 to the current first cursor.
- Each row adds second stride − 8 to the current second cursor.

Those adjustments apply to the dependency-mutated cursor values, not independently reconstructed row-start values.

### Conditional conventional element advancement

Suppose independently established dependency contracts guarantee that every first-stage call advances the first cursor by two bytes and every second-stage call advances the second cursor by four bytes.

For a positive inner count, and ignoring overflow, a complete row then advances the first cursor by exactly first stride and the second cursor by exactly second stride.

This explains the apparent row-stride intent. It is not a guarantee of F-97743e35a521 without those dependency contracts.

### Shared scratch contents

If the first stage writes a particular four-byte transfer value and no other effect changes that region before the second stage observes it, the second stage receives that same storage containing that value.

The wrapper provides ordering and address identity. It does not itself guarantee complete initialization or define how the second stage interprets those bytes.

### Zero count

With argument 6 equal to zero, the first processing pair still occurs before the counter is decremented or tested.

With argument 7 equal to zero and a positive inner count, the first complete inner loop still occurs before the outer counter is decremented or tested.

Neither case may be accepted as a guaranteed no-op.
