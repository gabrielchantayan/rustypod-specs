# F-b08da5548c1d

## Purpose

F-b08da5548c1d writes a fixed 16-byte record into caller-supplied storage and returns the smaller of an unsigned 32-bit input and 16.

The record contains one byte read from the supplied context, fixed byte values, and two bytes obtained in connection with two indirect calls. The meaning of the record and the semantic roles of those two bytes are not established.

The third argument limits the returned value, not the number of bytes written. Even an input of zero leads to all 16 explicit byte writes if execution completes normally.

## Interface

### Inputs

**Context address**

An address interpreted through a recovered 32-bit layout:

- At byte offset 0, a 32-bit field supplies an object address for indirect dispatch.
- At byte offset 24, one byte supplies the first byte of the output record.
- At the referenced object address, a further 32-bit field supplies a dispatch-table address.
- At byte offset 36 within that table, a callable address supplies the indirect-call target.

These are observed access requirements, not a complete definition of the context, object, or dispatch table. Their total sizes and other fields are unknown.

**Destination address**

An address to writable byte storage. Normal completion requires at least 16 writable bytes beginning at this address, independently of the third argument.

There is no destination-size check, null check, or explicit overlap check.

**Unsigned limit**

A 32-bit unsigned integer used only to determine the returned value. Its range is 0 through 4,294,967,295.

This value is not consulted to decide whether individual destination bytes may be written.

### Output

The return value is an unsigned 32-bit integer:

- For an input from 0 through 16 inclusive, the returned value equals the input.
- For an input greater than 16, the returned value is 16.

The function also performs the destination writes and indirect calls described below.

No explicit error result is defined. Faults, abnormal transfers of control, and failures originating in indirect callees are not converted into a documented status value.

### Preconditions for normal completion

The following conditions are required by the observed accesses:

- The context byte at offset 24 is readable when the initial read occurs.
- The destination supports all 16 byte writes.
- Each indirect-dispatch pointer chain is readable and valid at the time it is evaluated.
- Each resolved call target is callable under the actual execution environment.
- Both indirect calls return normally if completion and a return value are expected.

The calling convention, implicit call inputs, alignment requirements, and additional callee-specific preconditions are not established by the supplied evidence.

## Behavior

### Record layout

The function explicitly writes the following bytes, using offsets relative to the destination address:

| Offset | Explicitly written value |
|---|---|
| 0 | Byte read from context offset 24 |
| 1 | 0xB0 |
| 2 | 0x00 |
| 3 | 0x0C |
| 4 | 0x00 |
| 5 | 0x00 |
| 6 | Byte obtained from an auxiliary output associated with the first indirect call; exact ABI origin is unresolved |
| 7 | Byte-valued result of the second indirect call |
| 8–15 | 0x00 at each offset |

The constants are individual byte values. They do not establish an integer byte order or a multibyte field interpretation.

The read at context offset 24 selects the byte at that address. It must not be described as selecting the least-significant byte of a larger integer without additional evidence about byte order and the context field.

### Ordered operations

The following order is established for the function’s own accesses and calls:

1. Read the byte at context offset 24 and write that value to destination offset 0.
2. Write destination offsets 1 through 5, in ascending order, with the fixed values shown in the table.
3. Resolve and perform the first indirect call.
4. Write the first call’s associated auxiliary byte to destination offset 6.
5. Resolve and perform the second indirect call.
6. Write the second call’s byte-valued result to destination offset 7.
7. Write zeros to destination offsets 8 through 14, in ascending order.
8. Determine whether the unsigned limit exceeds 16 and cap the return value at 16 if necessary.
9. Write zero to destination offset 15.
10. Return the resulting unsigned value.

Both indirect calls are attempted regardless of the unsigned limit, provided execution reaches them. There is no special path for limits of zero, values below 16, or values above 16.

### Indirect-dispatch resolution

Each call independently resolves its target through the context’s first field, the referenced object’s first field, and dispatch-table byte offset 36.

The second call is not established to reuse a previously resolved target. Its pointer chain is evaluated after the write to destination offset 6. Consequently:

- The two calls can resolve to different targets if relevant memory changes.
- The first callee can affect the second target by modifying dispatch-related state.
- Destination overlap with the dispatch-related storage can affect either call.
- A pointer chain valid for the first call need not remain valid for the second.

The representation shows no explicit call arguments. This does not establish that the actual call ABI supplies no implicit inputs.

### Integer widths and arithmetic

The limit comparison is unsigned and 32-bit. There is no signed-negative input case in this interface.

The cap operation involves comparison with 16 and selection of either the original value or 16. It does not require addition or subtraction and therefore does not introduce arithmetic wraparound.

The largest destination offset explicitly written is 15. All 16 writes are unconditional with respect to the limit.

### Aliasing and intervening mutation

No non-overlap requirement is checked.

The initial context byte is read before the first destination write. Later dispatch reads occur after destination offsets 0 through 5 have been written. Therefore, if destination storage overlaps context or dispatch-related storage, the function’s own writes can change what later dispatch reads observe.

The first call occurs before the write to offset 6. The second call occurs after that write and before the write to offset 7. Both callees may modify memory unless their contracts independently prohibit it.

The record-layout table specifies this function’s explicit writes, not an unconditional guarantee that every listed byte still has that value at return. For example, either callee could overwrite an earlier destination byte. Under non-overlap and a callee contract that excludes such mutation, the completed record has exactly the listed layout.

## Side effects

### Destination writes

The function explicitly performs 16 one-byte writes covering offsets 0 through 15.

There is no rollback. If execution stops during an indirect call or a later access, earlier writes may remain visible. In particular:

- Before the first call begins, offsets 0 through 5 have been written.
- Before the second call begins, offset 6 has also been written.
- Offsets 7 through 15 are written only after the second call returns.

The function does not explicitly access destination offsets beyond 15. This statement does not constrain memory accesses performed by callees.

### Calls and external state

On a normal complete execution, the function makes exactly two indirect calls through the specified dispatch slot.

Those calls may have side effects not visible in the supplied evidence, including changes to context data, destination storage, dispatch state, global state, or resource ownership. Their behavior cannot be treated as pure.

### Ownership and lifetime

No allocation, deallocation, retention, or ownership transfer is explicitly performed by this function’s visible operations.

That observation does not establish the ownership behavior of either indirect callee. In particular, the evidence does not show that callees preserve the lifetime of the context, destination, object, or dispatch table. Continued execution requires those resources to remain valid for every subsequent access.

### Failure behavior

There is no explicit validation, recovery path, or error reporting.

Invalid pointers, insufficient writable storage, incompatible call targets, or callee failures may prevent normal completion. The exact resulting fault or control transfer depends on the execution environment and callee behavior; it is not specified here.

- The second call produces a byte-valued result of 0x72.

| Offsets | Values |

The return value depends separately on the unsigned limit.

### Zero limit

Under the preceding conditions, a limit of 0 returns 0.

The function still makes both indirect calls and writes all 16 destination bytes. A zero limit does not make a null or undersized destination acceptable.

### Limit below the record size

A limit of 7 returns 7 while still writing offsets 0 through 15.

An implementation that writes only seven bytes would not match the observed behavior.

### Boundary and large limits

A limit of 16 returns 16.

A limit of 17 also returns 16. The maximum 32-bit unsigned input, 4,294,967,295, returns 16 rather than being interpreted as a negative value.

### Dispatch changes after the first invocation

Suppose the first invocation changes the pointer chain so that the same dispatch-table offset now resolves to a different valid target.

The second invocation must use the newly observed chain. It is not required to call the first target again.

### First invocation does not return

If the first invocation does not return normally, offsets 0 through 5 have already been explicitly written. This function has not yet explicitly written offsets 6 through 15 and does not deliver its normal return value.

Any further effects depend on the callee and execution environment.

### Insufficient destination storage

A limit of 4 paired with only four writable destination bytes does not satisfy the normal-completion preconditions. The returned cap is not a bound on memory access.
