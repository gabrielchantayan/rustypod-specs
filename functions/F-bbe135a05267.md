# F-bbe135a05267

## Purpose

F-bbe135a05267 conditionally appends a requested amount of source data to a mutable buffer record. It can append without changing capacity, reduce the amount when growth is disabled, or select a new capacity and request replacement storage. Some paths change state and return without appending.

**Established behavior:** ordered entry gates, signed comparisons, wrapping 32-bit arithmetic, widened growth comparisons, capacity changes before allocation, and dependency calls whose effects are not established.

**Inferred intent:** a bounded, optionally growable accumulator that normally leaves one capacity unit beyond the accumulated data. This interpretation does not establish memory safety, ownership, or string termination. The function itself does not write a terminator.

## Interface

### Inputs and result

The function receives three inputs:

1. **State address:** identifies the mutable record described below.
2. **Source value:** a 32-bit value passed to the length-discovery dependency and the final transfer dependency. Its use suggests an address, but its complete type and validity requirements are unresolved.
3. **Requested amount:** a 32-bit word. A negative signed interpretation requests length discovery rather than directly specifying an amount.

There is no explicit return value. Observable results consist of memory accesses, direct state changes, dependency calls, and any effects of those calls.

### Record layout

Offsets are byte offsets from the state address.

| Offset | Width | Contract name | Established use |
|---|---:|---|---|
| 0 | 32 bits | Reference address | Compared with the current buffer address after allocation failure. |
| 4 | 32 bits | Current buffer address | Supplies transfer addresses; replaced on allocation success or cleared on one failure path. |
| 8 | 32 bits | Used amount | Supplies transfer lengths and append offsets; updated after the final transfer. |
| 12 | 32 bits | Capacity | Controls the initial decision and is changed before allocation. |
| 16 | 32 bits | Maximum capacity | Constrains capacity selection when growth is enabled. |
| 20 | 32-bit read | Entry status word | Read at entry and narrowed to an 8-bit character value for a nonzero test. |
| 20 | 8-bit write | Allocation-failure marker | Written with 1 when allocation returns zero. |
| 21 | 8-bit read | Growth-enabled byte | Zero selects truncation; nonzero selects growth handling. |
| 22 | 8-bit read/write | Limit byte | Tested first at entry; written with 1 on specified capacity-limit paths. |

The entry status word spans offsets 20–23 and overlaps the three named byte fields. The represented accesses therefore require a record extent of at least **24 bytes** when all such accesses are reachable. An invocation rejected by the first gate reads only the byte at offset 22.

The entry status operation is a represented **32-bit read followed by narrowing**, not an independently established byte read at offset 20. The narrowed value consists of the word’s low-order eight bits:

- With little-endian layout, those bits correspond to offset 20.
- With big-endian layout, they correspond to offset 23.

Byte order is not established by the supplied material. Consequently, the allocation-failure marker cannot unconditionally be identified with the value tested by the second entry gate.

### Preconditions and numeric model

No explicit null, bounds, overlap, or record-consistency checks are visible.

Every reached access must be valid at its represented width. In particular, passing the first entry gate requires the subsequent 32-bit status read to be valid; accessibility of offset 20 alone is insufficient.

Amounts and represented addresses are 32-bit values. Wrapping additions and subtractions are modulo \(2^{32}\). Signed 32-bit interpretation ranges from \(-2^{31}\) to \(2^{31}-1\).

The widened comparisons described below operate on sums of signed 32-bit interpretations without discarding the high-order information. They must not be replaced by signed comparisons of wrapped 32-bit sums.

Source, destination, alignment, overlap, and transfer-length requirements depend on unavailable dependency contracts. The function does not establish those requirements itself.

## Behavior

### Entry gates

The function first reads the limit byte at offset 22.

- If nonzero, it returns immediately.
- If zero, it reads the entry status word at offset 20, narrows the word to an 8-bit character value, and returns if that value is nonzero.

The first test short-circuits the second. Neither dependency calls nor direct state writes precede these gates.

### Effective amount

After both gates permit continuation, a requested amount with a negative signed 32-bit interpretation causes a call to F-1cb585febd84 with the source value. The dependency’s 32-bit result replaces the requested amount.

This substitution occurs once. A replacement result with its sign bit set does not trigger another discovery call.

If the effective amount is zero, the function returns without a capacity check or direct state write. Effects already performed by F-1cb585febd84 are not undone.

The entry gates are not rechecked after length discovery. Subsequent state reads therefore observe whatever state exists after that call, even if the dependency changed fields involved in entry gating.

### Initial capacity decision

For a nonzero effective amount, the function reads and retains capacity. It also reads the used amount and forms the wrapping 32-bit sum of used amount and effective amount.

If signed capacity is **strictly greater** than the signed interpretation of that wrapped sum, the function proceeds directly to the final append.

Otherwise, including equality, it reads the growth-enabled byte and enters capacity handling.

This decision is neither an unsigned bounds check nor a widened signed sum comparison. Overflow in the wrapped sum can select direct append despite a much larger mathematical sum.

### Growth disabled

When the growth-enabled byte is zero, the function rereads the used amount and replaces the effective amount with:

\[
(\text{retained capacity}-\text{current used amount}-1)\bmod 2^{32}.
\]

It then writes 1 to the limit byte.

If the replacement amount is less than 1 under signed 32-bit interpretation, the function returns. Otherwise, it proceeds to the final append with that replacement amount.

For ordinary nonnegative, consistent fields, this leaves one capacity unit unused. For arbitrary bit patterns, the wrapping calculation and signed test govern; the function does not guarantee safe truncation.

The limit byte is set even when the replacement amount causes immediate return.

### Growth enabled

The function first forms a wrapping increment:

\[
I=(\text{effective amount}+1)\bmod 2^{32}.
\]

It then considers the widened signed sum:

\[
G=\operatorname{signed32}(\text{retained capacity})
+\operatorname{signed32}(I).
\]

The increment wraps **before** its signed interpretation is used. Thus \(G\) is not necessarily the mathematical value of signed capacity plus the original amount plus one.

The function reads maximum capacity and compares its signed 32-bit interpretation with \(G\).

#### Candidate no greater than maximum

If signed maximum capacity is greater than or equal to \(G\), the function stores the low 32 bits of \(G\) into capacity.

For small nonnegative values, this selects old capacity plus effective amount plus one. It grows from capacity, not from used amount.

#### Candidate greater than maximum

Otherwise, the function rereads maximum capacity and stores that word into capacity. It then rereads used amount and compares the widened sum

\[
\operatorname{signed32}(\text{used amount})
+\operatorname{signed32}(\text{effective amount})
\]

against the signed interpretation of the selected maximum.

If the widened sum is **greater than or equal to** that maximum:

1. F-059e33c80433 is called with the state address.
2. The limit byte is written with 1.
3. The function returns without allocation or final append.

Capacity has already been written before this call. Equality is rejected on this fallback path.

If the widened sum is strictly below the selected maximum, allocation proceeds.

### Allocation

After either accepted growth calculation, the function reads capacity and passes that word to F-391e3d30e634.

The result is tested only for zero. No additional result validation is visible.

#### Zero result

The function:

1. Writes a single byte containing 1 at offset 20.
2. Reads and compares the current buffer address and reference address.
3. Returns if those values are equal.
4. Otherwise calls F-94cb53877c15 with no explicit arguments shown.
5. Stores zero into the current buffer address and returns.

The marker write precedes the address comparison and optional call. It is not a full-word status write.

There is no explicit capacity rollback or used-amount write on this path. This does not establish preservation across dependency calls.

Under little-endian layout, the marker inhibits a later invocation through the narrowed status test if it remains unchanged. Without established byte order, that consequence is not unconditional.

#### Nonzero result

The allocation result is retained as the replacement address. The function then:

1. Calls the external transfer dependency with the replacement address as destination, the current buffer address as source, and the current used amount as amount.
2. Calls F-059e33c80433 with the state address.
3. Stores the retained replacement address into the current buffer address.
4. Proceeds to the final append.

The existing-data transfer is invoked even when its amount is zero.

Publication of the replacement address occurs after F-059e33c80433 returns. The function does not restore used amount or other fields after that call. The final append uses the state then present.

### Final append and usage update

The final transfer dependency receives:

- A destination formed by wrapping 32-bit addition of the current buffer address and current used amount.
- The original source value.
- The effective amount, including any discovery or truncation replacement.

After the transfer returns, the function **rereads used amount**, adds the effective amount modulo \(2^{32}\), and stores the result at offset 8.

The final value therefore depends on the used amount **after the transfer**, not necessarily the value used to form the destination. Destination aliasing with the record or other dependency effects can change that field before the reread.

Any transfer result is ignored. No terminating-byte write follows.

The supplied representation does not establish evaluation order between independent record reads used to prepare a single call, or between the two reads in the failure-path address comparison. The ordering between calls and direct writes described above is established.

## Side effects

### Direct writes

Depending on the selected path, the function directly writes:

- Capacity, before allocation or fallback rejection.
- The limit byte, before a truncated append or after the fallback-rejection call.
- One byte at offset 20, after a zero allocation result.
- The current buffer address, after successful replacement or the unequal-address failure call.
- Used amount, after the final transfer returns.

There is no direct full-word write to the entry status word. Byte writes at offsets 20 and 22 modify overlapping storage, but their effects on the narrowed entry value depend on byte order.

The function does not explicitly clear either marker.

### Partial completion

The operation is not transactional:

- Capacity can change without a successful allocation.
- The limit byte can be set without a transfer.
- Existing-data transfer occurs before F-059e33c80433.
- Replacement publication occurs after that call.
- Final transfer occurs before the used-amount update.

No rollback, synchronization, or abnormal-return recovery is visible. If a dependency does not return normally, subsequent operations on that path are not established as occurring.

### Ownership and aliasing

A nonzero allocation result is used as a transfer destination and later stored in the record. Its lifetime, allocation family, and release obligations remain unknown.

The reference-address comparison does not establish ownership. Neither F-059e33c80433 nor F-94cb53877c15 may be assumed to release storage.

Dependencies may affect record fields, source memory, destination memory, or globals unless their separate contracts say otherwise. Ordinary transfer behavior also does not imply record preservation when transferred storage aliases the record.

## Acceptance examples

These examples are conditional static deductions, not observed executions. Unless an example specifies otherwise, both entry gates permit continuation and all reached accesses are valid. Transfer behavior and state preservation are conditions stated for the relevant examples, not guarantees supplied by this function.

1. **First gate stops further access.**  
   A nonzero limit byte causes return without reading the entry status word or calling a dependency.

2. **Second gate requires the represented word read.**  
   With a zero limit byte and nonzero low-order eight bits in the entry status word, entry stops before length discovery. The represented access spans offsets 20–23.

3. **Marker interpretation depends on byte order.**  
   Suppose offset 20 contains 1 and offsets 21–23 contain zero. The first gate passes. Little-endian interpretation makes the narrowed status value 1 and stops entry; big-endian interpretation makes it zero and permits continuation.

4. **Length discovery returns zero.**  
   An initially negative request causes F-1cb585febd84 to be called. If its result is zero, no capacity check, transfer, or direct state write follows. Any effects of that dependency remain.

5. **Direct append with conditional final usage.**  
   Capacity 16, used amount 4, and request 3 select direct append. The transfer receives current buffer plus 4, the source value, and amount 3. **If the final transfer leaves used amount equal to 4**, including no overwrite through destination aliasing, the stored used amount becomes 7. Otherwise, it becomes the post-transfer used amount plus 3 modulo \(2^{32}\).

6. **Boundary truncation with conditional final usage.**  
   Capacity 10, used amount 7, request 3, and disabled growth enter capacity handling on equality. The replacement amount is 2 and the limit byte is set to 1 before transfer. **If that transfer leaves used amount equal to 7**, the final stored value is 9. Otherwise, the update uses the value present after transfer and adds 2 modulo \(2^{32}\).

7. **No transferable room.**  
   Capacity 10, used amount 9, request 1, and disabled growth produce replacement amount zero. The limit byte becomes 1, and no transfer or direct used-amount update occurs.

8. **Growth based on capacity.**  
   Capacity 10, used amount 8, request 4, enabled growth, and maximum 20 select capacity 15. If allocation succeeds without changing the relevant fields, the existing-data transfer receives amount 8. F-059e33c80433 follows, then replacement publication, then the final append. If used amount remains 8 through those dependencies and the final transfer, final usage is 12.

9. **Fallback accepts strictly below maximum.**  
   Capacity 10, used amount 8, request 4, enabled growth, and maximum 13 select capacity 13. Allocation proceeds because the widened used-plus-request sum is 12, strictly below 13.

10. **Fallback rejects equality.**  
    With those values but maximum 12, capacity is written as 12, F-059e33c80433 is called, and the limit byte is then set to 1. No allocation or final append follows. Other state after the call remains dependent on its effects.

11. **Allocation failure branches.**  
    A zero allocation result writes one byte containing 1 at offset 20. Equal current and reference addresses cause return without a direct current-address write. Unequal addresses cause F-94cb53877c15 followed, if it returns, by a zero current-address write.

12. **Wrapped initial sum selects direct append.**  
    Capacity \(2^{31}-1\), used amount \(2^{31}-2\), and request 4 produce a negative signed interpretation of the wrapped proposed usage. Direct append is selected. This arithmetic result does not prove that the destination is valid.

13. **Final transfer changes usage.**  
    Suppose a direct append uses effective amount 3 and the transfer leaves the used-amount word equal to 100, through aliasing or another effect. The subsequent reread and update store 103, regardless of the used amount originally used to form the destination.

## Evidence

The supplied static representation establishes the branches, access widths, arithmetic distinctions, dependency arguments, call ordering, and direct writes described above.

In particular:

- Entry uses an ordered byte test followed by a represented 32-bit status read and narrowing.
- Allocation failure writes only one byte at offset 20.
- The initial capacity decision uses a wrapped sum interpreted as signed.
- Growth selection and fallback rejection use widened signed sums.
- The final used-amount update rereads the field after transfer, so numeric final-usage examples require preservation of that field through the transfer.

The supplied dependency mapping establishes the listed opaque function IDs, not their implementations. No opaque ID was supplied for the external transfer dependency.

No runtime tests have been performed. All acceptance examples are conditional deductions from static evidence.
