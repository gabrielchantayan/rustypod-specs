# F-a836e5479ebf

## Purpose

F-a836e5479ebf maintains a sequence of fixed-size records associated with a caller-supplied state object. For a nonnegative first key, it searches records in ascending index order for a matching pair of keys. It updates the first matching record’s flag, or requests storage for one additional record and appends a new record when no match is found.

A matching record retains its existing keys and payload. Its flag becomes a canonical Boolean representing the logical OR of its previous low-byte flag and the full incoming flag argument.

A negative first key causes an immediate return without accessing the state object.

The apparent intent is a keyed accumulation operation with a sticky enabled flag and an associated payload. That interpretation is inferred; the search order, update rules, allocation request, and failure writes are established by the supplied static representation.

## Interface

### Inputs

The function receives five arguments:

1. **State address:** an address used to access a state object containing a context reference, a record count, and a record-storage address.
2. **First key:** a signed 32-bit integer. Negative values disable the operation.
3. **Second key:** a 32-bit integer compared for equality.
4. **Incoming flag:** a 32-bit integer. Its treatment differs between insertion and an existing-record update.
5. **Payload:** a 32-bit value stored only when a record is appended.

The supplied representation uses 32-bit integer slots and stores addresses in such slots. The layout below describes that represented address model, not a portable native-pointer interface for a wider platform.

### State layout

Offsets are byte offsets from the state address.

| Offset | Width | Meaning |
|---|---:|---|
| `0x000` | 4 bytes | Context address passed to F-814e6ca769cc and used as the base for the failure-status write |
| `0x13C` | 4 bytes | Signed record count |
| `0x140` | 4 bytes | Record-storage address |

Other state bytes have no direct use in the supplied function. This does not establish that the dependency leaves them unchanged.

When reporting storage-request failure, the function writes one byte with value `1` at offset `0x1E` from the context address read from the state.

### Record layout

Each record occupies 16 bytes.

| Record-relative offset | Width used by the operation | Meaning |
|---|---:|---|
| `0x00` | 4 bytes | First key |
| `0x04` | 4 bytes | Second key |
| `0x08` | 1 byte written | Flag |
| `0x09`–`0x0B` | No direct writes | Unspecified intervening bytes |
| `0x0C` | 4 bytes | Payload |

On an existing-record update, the supplied expression accesses the 32-bit slot beginning at offset `0x08` and converts it to a character value before testing it. The resulting Boolean is written to the byte at offset `0x08`. Consequently, the represented read extent and write extent are not identical. Exact machine-level access width requires evidence beyond the supplied representation.

### Output

There is no return value and no explicit success or failure result.

Observable outcomes are expressed through:

- A changed flag in an existing record.
- A replaced record-storage address and increased count.
- Newly written record fields.
- A zero record-storage address, zero count, and context failure byte on a zero dependency result.

### Preconditions

For a negative first key, the state address need not designate accessible storage because the early return occurs before state access.

For a nonnegative first key, safe execution requires accessible state fields and valid addresses for whichever branch is reached. In particular:

- A positive count requires readable records for the indices searched.
- A matching record requires writable flag storage.
- A successful storage request requires writable space for the selected appended record.
- A failed request requires a writable byte at the current context address plus `0x1E`.
- Count, byte-size, and address calculations must remain within the supported arithmetic and address ranges.

The function does not validate these conditions. Nonnegative counts and disjoint state, context, and record storage are useful caller invariants, but they are not enforced by the function.

## Behavior

### 1. Negative-key rejection

The first key is tested as a signed value.

If it is negative, the function returns immediately. It does not search records, call F-814e6ca769cc, read the payload, or access the state through its address.

No analogous rejection is applied to the second key, incoming flag, or payload.

### 2. Ordered search

For a nonnegative first key, the search begins at record index zero.

Before each record inspection, the function reads the current signed count and compares it with the current index. If the count is less than or equal to that index, it enters the storage-growth path.

Otherwise, it reads the current record-storage address and locates the record at a displacement of 16 bytes times the index.

Comparison order is significant:

1. Read and compare the record’s first key.
2. Only if the first key matches, read and compare the second key.
3. If both keys match, stop searching.
4. Otherwise, increase the index by one and repeat.

The payload and flag do not participate in key matching.

If duplicate key pairs already exist, only the earliest matching record is updated. Later duplicates are not inspected after that match.

The count and storage address are not captured as immutable entry snapshots: the source expressions access them during traversal. This observation does not establish thread safety or defined behavior under concurrent mutation.

### 3. Existing-record update

For the first matching record, the new flag is the logical OR of:

- Whether the existing flag value, after conversion from its containing 32-bit slot to a character value, is nonzero.
- Whether the full incoming 32-bit flag argument is nonzero.

The byte written is canonical Boolean `0` or `1`.

Consequences include:

- A true flag cannot be cleared by supplying zero.
- A noncanonical existing nonzero flag is normalized to `1`.
- An incoming nonzero value makes the updated flag `1`, even if its low eight bits are zero.
- A false existing flag and zero incoming flag produce `0`.

The function performs the flag assignment even when the resulting logical value is unchanged.

It does not directly rewrite either key, the payload, the count, or the storage-address field on this path. The incoming payload is ignored for a matching record.

### 4. Storage-growth request

When the current count is less than or equal to the search index, the function calls F-814e6ca769cc with three arguments:

1. The context value read from state offset `0x000`.
2. The storage-address value read from state offset `0x140`.
3. A requested byte size calculated as 16 times the current count plus one record.

The size calculation adds one to the count before multiplying by 16. No capacity field, spare-capacity check, or geometric growth policy is visible.

The language-level representation does not establish the evaluation order of the three argument expressions. All are evaluated for the call, but their individual read order must not be inferred.

The dependency’s returned 32-bit value is written to the state’s storage-address field before the function handles success or failure. A zero result therefore replaces the previous storage address with zero.

### 5. Nonzero dependency result

For a nonzero dependency result, the function reads the count again after the call. It uses this post-call count as the insertion index, writes that count plus one back to the count field, and then writes the new record.

The direct write order is:

1. Store the returned storage address in the state.
2. Store the incremented count in the state.
3. Store the first key in the selected record.
4. Store the second key.
5. Store the incoming flag converted to a one-byte character value.
6. Store the payload.

The new record’s flag is not Boolean-normalized on insertion. Under the represented eight-bit byte model, it retains the incoming argument’s low eight bits.

The function does not initialize the three bytes between the flag and payload.

The post-call count matters: the function does not necessarily append at the count used to calculate the requested size if the dependency changes the count. No preservation guarantee for that field is supplied.

There is also a publication-order limitation: the count is increased before the record fields are initialized. The function therefore does not establish an invariant that every record below the published count is fully initialized throughout the operation.

### 6. Zero dependency result

For a zero dependency result, the direct sequence is:

1. Store zero in the state’s storage-address field.
2. Store zero in the count field.
3. Read the context address from the state.
4. Write the byte value `1` at context-relative offset `0x1E`.
5. Return.

The context address used for the final write is read after the dependency returns. It need not equal the context value passed into that call if the dependency modifies the state.

The function does not restore the previous storage address, preserve the old count, explicitly release storage, or clear former record bytes.

## Side effects

The negative-key path has no direct memory side effects.

The matching-record path directly writes only the selected flag byte. Under ordinary nonaliasing storage, the record’s keys, intervening bytes, and payload remain unchanged.

The append path directly replaces the storage-address field, increases the count, and writes 13 bytes of record fields across a 16-byte record. It does not initialize every byte of that record.

The failure path directly clears the storage-address and count fields and sets the context failure byte to `1`. No direct write clears that failure byte on later success or on a matching-record update.

F-814e6ca769cc may have additional side effects. Its allocation behavior, preservation guarantees, error reporting, and effects on global or caller-reachable state are unknown.

Ownership is not established by this function. In particular:

- Passing an existing storage address to the dependency does not prove transfer of ownership.
- A nonzero result does not prove that the previous address was freed or that previous records were copied.
- A zero result does not prove that previous storage was freed or retained.
- Replacing the state’s address with zero may discard its only visible reference, but whether that creates a leak depends on the dependency’s contract.

Overlapping state, context, and record regions can make a nominal field write affect later reads. No nonaliasing check prevents that situation. Acceptance examples below assume disjoint regions unless stated otherwise.

## Acceptance examples

These examples describe conditional expected behavior from static evidence. They are not runtime test results.

### Negative first key

Given a first key of `-1`, the function returns without dereferencing the state address and without calling F-814e6ca769cc. This remains true even if the state address is unusable.

### First matching duplicate only

Given three valid records where records zero and two have the requested key pair, only record zero’s flag is updated. Record two’s flag and both records’ payloads remain unchanged by the function’s direct writes.

### First-key mismatch skips second-key access

Given an inspected record whose first key differs from the requested first key, its second key is not read for comparison on that iteration. The next iteration begins after the index increases.

### Matching record with zero incoming flag

Given a matching record whose existing flag byte is `0x7F` and an incoming flag of zero, the flag becomes `1`. The existing payload remains unchanged, regardless of the supplied payload.

Given instead an existing zero flag and incoming zero, the flag is written as zero.

### Insertion and update treat `256` differently

Given an ordinary successful append with incoming flag `256`, the inserted flag byte is zero.

Given an existing matching record with a zero flag and incoming flag `256`, the updated flag byte is `1`, because the update tests the full incoming argument for nonzero.

### Successful append after two records

Given a count of two, no matching keys, and a dependency that leaves the state count unchanged and returns suitable storage preserving the earlier records:

- The requested size is 48 bytes.
- The count becomes three.
- The new record begins 32 bytes after the returned storage address.
- Its two keys and payload equal the supplied values.
- Its flag receives the incoming value’s low byte.
- Its three intervening bytes are not initialized by this function.

Preservation of the first two records in this example is a dependency assumption, not a guarantee established here.

### Failed growth

Given a reachable growth path and a zero dependency result, the storage-address field becomes zero, the count becomes zero, and the context failure byte becomes `1`. The previous address is not restored.

### Dependency changes the count

Given a dependency that returns nonzero and changes the count before returning, insertion uses that changed count. Acceptance requires adequate writable storage at the resulting location; the original size request alone does not establish that safety.
