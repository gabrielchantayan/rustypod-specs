# F-eee1239b9042

## Purpose

F-eee1239b9042 conditionally copies a source record’s first 32-bit field and a bounded number of associated 32-bit payload units into an existing destination.

The copy count is derived from the signed product of the source’s first field and a shared multiplier. For ordinary representable arithmetic, the count is the absolute value of that product. A count greater than 28 is rejected before any destination write. An accepted operation copies payload units in descending index order.

This is not an allocation, capacity-management, or general-purpose overlap-safe copying interface. It uses addresses already stored in the records. Its bounded-copy interpretation depends on valid arithmetic and valid memory supplied by the caller.

The interpretation of the first field as a logical length, and of the multiplier as a unit-conversion factor, is inferred intent rather than an established interface definition.

## Interface

### Arguments

The function takes two record addresses, in this order:

1. **Destination record address.**
2. **Source record address.**

The visible layout of each record is:

| Byte offset | Width | Observed use |
|---|---:|---|
| 0 | 32 bits | Signed input to count calculation; copied from source to destination on accepted, non-identical-record operations. |
| 4 | 32 bits | Address-bearing field used as the base of the associated payload storage. |

Each payload unit occupies four bytes. Index zero begins at the payload base, and consecutive units are separated by four bytes.

The recovered representation uses 32-bit integer slots for these fields. The second slot is used as an address, not as a value copied into the destination record. Its encoding, byte order, and portability to other address widths are not established.

### Shared input

A shared 32-bit value supplies the multiplier for the initial count calculation.

The function visibly reads this value but does not explicitly write it. Its meaning, initialization, allowed range, and synchronization requirements are unknown.

### Return value

The result occupies 32 bits:

- **1:** The computed magnitude exceeds 28.
- **0:** The magnitude is accepted, including when the record addresses are identical or the accepted count is zero.

These statuses do not report memory-access failures. A successful return is not a capacity guarantee and does not establish that the record or payload contents satisfy any external invariant.

- On an accepted operation with distinct record addresses, the source first field must remain readable and the destination first field must be writable.
- For a positive count, the payload-base fields must be readable when used.
- Every selected source payload unit must be readable, and every selected destination payload unit must be writable.

The function does not visibly check these preconditions.

## Behavior

### 1. Derive the count and decide acceptance

The function reads the source’s first 32-bit field and the shared multiplier, then forms their signed product.

The supplied representation establishes both inputs to the multiplication but does not establish their relative machine-level load order.

For a product that is representable as a signed 32-bit value and whose absolute value is also representable:

- A nonnegative product supplies the magnitude directly.
- A negative product supplies its negation as the magnitude.
- A magnitude greater than 28 produces return value 1.
- A magnitude from 0 through 28 is accepted.

Rejection occurs before the record-address identity check and before any explicit write.

Consequently, passing the same record address twice does not unconditionally succeed. The source field and multiplier are still read, and an excessive magnitude still returns 1.

Arithmetic overflow and the most-negative signed value require separate treatment; they are not silently covered by the ordinary magnitude rule.

### 2. Handle identical record addresses

After acceptance, the function compares the source and destination record addresses.

If they are identical, it returns 0 without executing the record-field copy or the payload-copy loop.

Identity here concerns the record addresses themselves. Distinct records containing equal payload addresses do not take this shortcut.

### 3. Copy the first record field

For accepted operations with distinct record addresses, the function reads the source’s first field again and writes that value into the destination’s first field.

This is a fresh read, not necessarily the value used in the original multiplication. The loop count has already been selected and is not recomputed from this second read.

Under stable-memory conditions, the value written is simply the source’s original first field. If the source field changes between reads, the copied field and the selected payload count can describe different states.

The destination’s payload-base field is not explicitly replaced with the source’s payload-base field.

### 4. Copy payload units in descending order

For an accepted positive count \(n\), with distinct record addresses, the payload transfers occur in this order:

\(n-1,\ n-2,\ \ldots,\ 1,\ 0\).

For each index:

- The source payload-base field supplies the source address base.
- The destination payload-base field supplies the destination address base.
- The source unit at the base plus four times the index is read.
- Its 32-bit value is written to the corresponding destination address.

Each source payload read precedes its corresponding destination payload write. The representation does not establish the relative machine-level ordering of the two payload-base reads.

Each indexed transfer is expressed using the records’ payload-base fields. The supplied evidence does not establish that both bases are captured once before the loop. Accordingly, stable bases must not be assumed when a payload write can overlap either record or when another agent can modify the fields.

For a zero count, the first-field copy still occurs, but no payload unit is accessed by the loop.

After the accepted copy path completes, the function returns 0.

### Bounds of the ordinary path

With representable count arithmetic, the accepted payload count is at most 28 units, or 112 bytes.

This bound describes the selected payload transfers, not the allocation size, available capacity, or total possible memory effects under aliasing. The function does not inspect a capacity field or prove that either payload allocation has 112 bytes available.

## Side effects

### Explicit reads

The visible operation may read:

- The source first field for count calculation.
- The shared multiplier for count calculation.
- The source first field again for an accepted, non-identical-record copy.
- The payload-base fields during positive-count copying.
- One 32-bit source payload unit per selected index.

Rejected operations and accepted identical-record operations do not execute the payload-copy path.

### Explicit writes

For accepted operations with distinct record addresses, the function writes:

- The destination first field once.
- One 32-bit destination payload unit per selected index.

For a stable positive count \(n\), this is one record-field write followed by \(n\) descending payload writes.

There are no explicit writes before the rejection decision. There are no explicit writes on the identical-record shortcut.

These statements describe ordinary memory accesses. Device-specific effects of reading or writing memory-mapped addresses are outside the available evidence.

### Aliasing and overlap

The descending order is observable when payload regions overlap.

If source and destination payloads are stable, contiguous regions, descending order can preserve original source values when the destination begins at a higher address within the source region. It does not generally preserve them when the destination begins at a lower address: an earlier high-index write can change a source unit that a later iteration has not yet read.

Distinct records may contain the same payload base. In that case, the function still executes the selected reads and writes; it does not skip them based on payload-address equality.

Record/payload aliasing can have additional effects:

- The first-field write can alter memory subsequently used as payload data.
- A payload write can alter a record field used by later iterations.
- A payload write can alter the shared multiplier if those addresses alias, although the multiplier is not visibly reread for this operation.

Thus, preservation of fields other than the destination first field requires an appropriate non-aliasing assumption. The lack of an explicit assignment to a field is not proof that aliased payload writes cannot modify it.

Expected behavior:

- Select six payload units.
- Write −3, not 3, into the destination first field.
- Copy the same six indices in descending order.
- Return 0.

The magnitude determines the transfer count; the original signed field is copied.

### Inclusive boundary

A representable product of either 28 or −28 is accepted.

Expected behavior: copy 28 payload units, from index 27 down to index 0, and return 0.

A representable product of either 29 or −29 is rejected.

Expected behavior: return 1 without any explicit destination write.

### Zero multiplier

The multiplier is zero, and the source first field contains an otherwise valid 32-bit signed value.

Expected behavior for distinct record addresses:

- Select zero payload units.
- Copy the source first field into the destination first field.
- Perform no payload transfer.
- Return 0.

A nonzero source field does not itself require a nonzero payload transfer.

### Identical record addresses

Both arguments designate the same record.

- If the computed magnitude is 28 or less, return 0 without explicit writes.
- If it exceeds 28, return 1 without explicit writes.

The source first field and multiplier are still required for the decision.

### Overlap that demonstrates descending order

The source payload contains four consecutive units A, B, C, D. The destination begins one unit below the source, and the selected count is three.

The index-2 transfer first writes C into the location originally containing B. The index-1 transfer then reads that modified location and writes C into the location originally containing A. The index-0 transfer reads that modified location and writes C into the lowest destination location.

Expected destination contents are C, C, C, rather than the original A, B, C. This example distinguishes the observed descending loop from an overlap-safe copy guarantee.
