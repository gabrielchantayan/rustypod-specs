# F-d378005cb920

## Purpose

F-d378005cb920 selects between two behaviors using a zero-versus-nonzero mode:

- **Zero mode:** performs a lookup. If the result is nonzero, passes an interior object address to a dependency, then sets the addressed byte to one.
- **Nonzero mode:** clears that byte, invokes preparation, refreshes an object field, and checks a guard. A zero guard permits further record processing, conditional linked-structure insertion, and a final conditional indirect call.

Scheduling, timer activation, and coordination are **inferred intent**, not established semantics. The established contract consists of accesses, calls, branch conditions, arithmetic, and ordered writes.

The function has no explicit return value. Observable outcomes include memory changes, dependency effects, calls reached or skipped, and whether execution returns.

### Object layout

All offsets are byte offsets from the supplied object address.

| Offset | Width | Established use |
|---|---:|---|
| `0x28` | 4 bytes | Lookup argument in zero mode. |
| `0xEC` | 4 bytes | First word of the embedded record; receives its successor address during insertion. Its address is passed to record processing. |
| `0xF0` | 4 bytes | Interval-like input; zero suppresses insertion. |
| `0xF4` | 4 bytes | Arithmetic result used as a comparison key. |
| `0x104` | 4 bytes | Copy of shared insertion metadata. |

The embedded record starts at `0xEC`. Traversed records are accessed through:

- A four-byte successor word at record offset zero.
- A comparison-key address at record offset eight.

The comparison dependency’s access width is not established merely by receiving that key address.

An explicit one-byte write affects only the addressed byte. A dependency receiving that address is not established to have the same access bounds.

### Shared state

The function accesses shared storage serving these roles:

- Lookup selector.
- Refresh value.
- Entry-side argument, subsequently reloaded and used as a pointer to an address-bearing cell.
- Address of a list-head cell.
- Insertion metadata.
- Exit-side argument.
- Indirect dispatch target.

It also calls an unresolved value-producing dependency for deadline-like arithmetic.

These roles are not evidence of disjoint storage. Shared cells, their pointees, object fields, and records may alias unless additional caller constraints exclude that configuration.

### Preconditions

Each reached memory access requires valid storage of the accessed width. Each reached call requires a valid target and satisfaction of that dependency’s unknown calling requirements. Storage must remain valid despite earlier dependency calls.

The function performs no explicit address validation. Normal completion additionally requires invoked dependencies to return and any traversal to terminate.

A coherent resulting list requires stronger conditions than valid individual accesses; those conditions are stated under **Side effects**. They are not enforced by this function.

## Behavior

### Zero mode

The function obtains the four-byte object value at `0x28` and the shared lookup selector, then calls F-682adfd5a561 with those two arguments. The representation does not establish a relative evaluation order between the two argument reads.

If the result is zero, the function returns without an explicit object write.

If the result is nonzero, it calls F-7e83af7e8039 with:

- The lookup result.
- Zero.
- The address at object offset `0x118`.

After that call returns, it writes one to the byte at `0x118` and returns. This explicit write replaces any value the dependency left at that byte, provided the storage remains valid. If the dependency does not return, the write is not reached.

Neither zero-mode outcome reaches nonzero-mode preparation, record insertion, exit processing, or final dispatch.

### Nonzero-mode preparation and guard

For any nonzero mode, the observable sequence is:

1. Write zero to the byte at object offset `0x118`.
2. Call F-936a8728139d without explicit arguments.
3. Read the shared refresh value and write it as four bytes at object offset `0x10C`.
4. Read the four-byte guard at object offset `0x108`.

A nonzero guard causes immediate return. Clearing the flag, preparation, and refresh have already occurred. Entry processing, record processing, exit processing, and final dispatch are skipped.

The decisive guard value is its value when read, not necessarily its entry value. Preparation or aliased writes may affect that observation.

### Processing after a zero guard

If the observed guard is zero, the function:

1. Calls F-338d16f9ce72 with the then-current shared entry-side argument.
2. Calls F-add44d4e9aaa with the embedded record address at object offset `0xEC`.
3. Reads the four-byte interval-like value at object offset `0xF0`.

Both dependencies precede the interval read. Their effects may therefore determine whether insertion is attempted.

If the interval is zero, the function skips the arithmetic-producing call, explicit deadline and metadata writes, traversal, and insertion writes. It proceeds to exit processing.

This is a statement about operations omitted by this body, not a guarantee that those fields retain their entry values: dependencies may modify them.

### Arithmetic and metadata

For a nonzero interval, the function calls the unresolved value producer without explicit arguments. It then captures the shared address of the list-head cell.

Using the interval already read, it computes:

\[
\text{result}=\text{produced value}+1000\times\text{interval}
\]

It writes the result to the four-byte field at object offset `0xF4`. It does not reload the interval after the value-producing call.

Next, it reads shared insertion metadata and writes four bytes at object offset `0x104`. Only afterward does it read the current head through the captured head-cell address.

This order matters under aliasing:

- The head-cell address is captured before the deadline and metadata writes.
- The head stored at that address is read after those writes.
- The metadata is read after the deadline write.
- Later changes to the shared source of the head-cell address do not, by themselves, replace the captured address.

The representation uses signed 32-bit intermediates for the arithmetic and a four-byte destination. It does not establish saturation, checked arithmetic, an error result, or a portable overflow rule. Modulo-\(2^{32}\) overflow behavior requires an additional machine-semantics assumption.

Multiplication by 1000 fits signed 32-bit arithmetic for intervals from −2,147,483 through 2,147,483 inclusive. The subsequent addition must also fit. Negative nonzero intervals are not explicitly rejected.

### Traversal

The initial current record is the head value read through the captured head-cell address. Initially, there is no predecessor.

For each nonnull current record, the function calls F-0d70d6f9010c with:

- The address eight bytes into that record.
- The address of the new record’s key at object offset `0xF4`.

A nonzero result stops traversal at the current record. The function distinguishes only zero from nonzero; negative results do not have a separate interpretation.

A zero result continues traversal. After that comparison returns, the function reads the current record’s first four-byte word as the next-record address and remembers the current record as predecessor. Thus, a comparison dependency can affect the successor that is subsequently read.

A null current record stops traversal without a comparison call.

No ordering direction or equality policy follows from this control flow alone. No cycle detection, duplicate-record check, or local traversal limit is visible.

### Ordered insertion writes

After traversal stops, the function performs these writes in order:

1. If no predecessor was recorded, write the embedded record address through the captured head-cell address. Otherwise, write that address into the predecessor’s first four-byte word.
2. Write the four-byte value one at object offset `0x108`.
3. Write the stopping record address, possibly zero, into the embedded record’s first word at object offset `0xEC`.

These are the unconditional insertion-write obligations for an execution that reaches them. They do **not** establish that the first destination still contains the embedded record address afterward: the later writes may overlap it.

For example, if the captured head-cell address equals object offset `0xEC` and its initial word is zero, traversal sees an empty list. The first insertion write places the embedded record’s own address in that word. The final insertion write replaces the same word with zero. The final head is therefore zero, not the embedded record address.

The representation provides no explicit atomic publication, memory barrier, or protection against observation between writes.

### Exit processing and dispatch

After either a zero interval or completed insertion, the function calls F-5bcae2eff9a7 with the shared exit-side argument.

After that call returns, it reloads the shared entry-side pointer and reads an address through it. Call this result the candidate address.

- A zero candidate suppresses further candidate access and dispatch.
- A nonzero candidate causes a four-byte read from its first word.
- A zero first word suppresses dispatch.
- A nonzero candidate with a nonzero first word causes a call through the shared indirect target, without explicit arguments.

The entry-side pointer must itself support the first dereference; there is no preceding null check for that pointer. The null check applies to the candidate obtained through it.

The candidate’s first word controls whether dispatch occurs. It is not used as the dispatch target. The exit-side dependency precedes these reads and can affect their outcome. Normal return after dispatch depends on the indirect target’s behavior.

## Side effects

### Explicit memory effects

Depending on the path, the function explicitly writes the flag, refresh, deadline, metadata, guard, embedded successor, and either the captured head cell or a predecessor link.

These are addressed writes, not guarantees of independently preserved final fields. Aliasing can cause one write to replace another write’s result or alter a later read.

There is no explicit allocation, deallocation, reference-count update, or ownership-transfer operation in the supplied body. Dependencies may perform such operations; their behavior is unknown.

### Conditional list postconditions

Ordinary linked-list outcomes require additional caller and dependency assumptions. A sufficient set is:

- The captured head cell, enclosing object, and each existing record occupy mutually nonoverlapping storage.
- The embedded record is not already among the existing records.
- The existing successor chain is valid and finite.
- Relevant head, link, key, and object storage remains valid.
- Dependencies and concurrent agents do not change the relevant structure or insertion fields during the operation, apart from the explicit writes described here.
- The comparisons yield the stopping position used by the claimed outcome.

Under those assumptions, insertion connects the head or predecessor to the embedded record, connects the embedded record to the stopping record, and sets the guard to one. The unchanged prefix of the original chain keeps a non-head insertion reachable.

Without such assumptions, only the ordered accesses and writes are established. Neither reachability nor a well-formed resulting list is guaranteed.

### Ownership, lifetime, and concurrency

Passing an interior flag address or embedded record address does not establish whether a dependency retains it, requires exclusivity, or releases associated storage.

If a valid linked structure retains the embedded record’s address, continued safe use of that structure requires the enclosing object to remain alive while reachable. This is a conditional lifetime requirement, not proof that insertion always leaves the record reachable or transfers ownership.

The entry-side and exit-side calls may suggest coordination, but no lock, unlock, exclusion, or reentrancy guarantee is established.

There is no explicit local handling for invalid memory, arithmetic overflow, corrupted links, a null indirect target, dependency failure, or nontermination.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, calls return normally, arithmetic is representable, accesses remain valid, and dependencies and concurrent agents do not alter the memory relevant to the example.

1. **Unsuccessful zero-mode lookup.**  
   A zero result from F-682adfd5a561 causes return without F-7e83af7e8039 and without an explicit flag write.

2. **Successful zero-mode lookup.**  
   A nonzero lookup result is passed to F-7e83af7e8039 with zero and the flag address. After that call returns, the explicit byte write sets the flag to one.

3. **Nonzero guard after preparation.**  
   The function clears the flag, calls preparation, and refreshes `0x10C`. If the subsequently read guard is nonzero, it returns without entry processing, record processing, exit processing, or dispatch.

4. **Zero interval after record processing.**  
   With a zero observed guard and zero interval, the body performs no deadline, metadata, guard, or link write associated with insertion. It still reaches exit processing and the dispatch condition.

5. **Empty, nonaliasing list.**  
   Under the sufficient list assumptions in **Side effects**, an initially zero head receives the embedded record address. The guard becomes one and the embedded successor becomes zero. No comparison is called.

6. **Insertion before the head.**  
   Under those same assumptions, a nonzero first comparison causes the head to become the embedded record address and the embedded successor to become the former head.

7. **Insertion after a prefix.**  
   Under those same assumptions, zero comparisons for two records followed by a nonzero comparison for the third cause the second record’s successor to become the embedded record address. The embedded successor becomes the third record, and the unchanged prefix preserves reachability.

8. **Aliased head and embedded successor.**  
   Let the captured head-cell address equal object offset `0xEC`, with that word zero when read and with a nonzero interval. The insertion writes the embedded record address to that word, writes one to the guard, then writes zero to that same word. The final head is zero. No dependency mutation is needed for this outcome.

9. **Representable arithmetic.**  
   An interval of 2 and produced value of 300 yield a stored arithmetic result of 2300.

10. **Dispatch gating.**  
    After exit processing, a zero candidate suppresses dispatch. A nonzero candidate whose first word is zero also suppresses dispatch. A nonzero candidate with a nonzero first word reaches the shared indirect target, assuming that target is valid.
