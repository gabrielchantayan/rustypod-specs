# F-772735a0d0b9

## Purpose

F-772735a0d0b9 searches a word-oriented collection for a supplied value, rejects an existing match, and otherwise attempts to replace the first zero-valued slot in a bounded prefix.

The behavior is not an ordinary append operation:

- An existing match returns −1 without invoking a dependency or writing collection state.
- Equality between two header fields triggers F-926b44f5ac05 before the search for a zero slot.
- A successful replacement increments the third header field, not the field that bounds the search.
- Failure to find a zero slot also returns −1.
- The function itself does not extend the searchable prefix.

The names “collection,” “slot,” and “search bound” describe observable structure. An interpretation in terms of allocation capacity, occupancy, or growth is inferred intent, not an established contract.

## Interface

### Inputs

The function takes two arguments:

1. **Header reference.** A writable reference to a structure containing at least three consecutive integer fields.
2. **Candidate value.** An integer compared against existing elements and, on successful replacement, written into an element slot.

The header has the following observed layout:

| Field position | Nominal byte offset | Observed role |
|---|---:|---|
| First | 0 | Integer-held base address of element storage |
| Second | 4 | Signed bound for both searches |
| Third | 8 | Equality-trigger field, incremented on successful replacement |

Element addresses are formed from the stored base address plus four times the element index. Thus, element spacing is explicitly four bytes.

The offsets in the header table assume four-byte integers. The supplied representation is consistent with a 32-bit layout, but it does not independently establish the execution ABI. A faithful implementation must resolve integer width, pointer width, alignment, and integer-to-pointer conversion rules rather than assume that a host-native integer or pointer has the required representation.

For the 32-bit interpretation:

- Header fields and candidate values are 32-bit integers.
- Search bounds and indices use signed comparisons.
- The failure result is signed −1.
- Element positions are separated by four bytes.
- The first header field must represent a usable storage address under the target’s address-conversion rules.

### Output

The function returns an integer:

- **−1** if the candidate is found during the initial search.
- **−1** if no zero-valued slot is found during the later search.
- **A nonnegative index** if a zero-valued slot is found and the replacement path completes.

These two failure cases are not distinguishable through the return value alone. They may be distinguishable through dependency effects: only the second case can follow a call to F-926b44f5ac05.

No separate success flag, updated count, or storage address is returned.

### Preconditions and ownership

For defined execution, all header and element accesses actually performed must address valid, appropriately aligned memory. Header fields must be readable, and fields or slots reached by writes must be writable.

The supplied representation does not establish ownership of the header or storage. This function contains no explicit allocation or release operation. F-926b44f5ac05 receives the header reference and may have effects that are not visible here; its memory-management behavior must not be assumed.

No null-reference check, storage-length validation, or arithmetic-overflow check is present.

## Behavior

### 1. Search for an existing candidate

The function begins at index zero and visits increasing indices while the index is strictly less than the signed value of the second header field.

For every visited index, it obtains the element-storage base address from the first header field, reads the element at the corresponding four-byte displacement, and compares that element with the candidate.

On the first equality:

- It returns −1 immediately.
- It does not invoke F-926b44f5ac05.
- It performs no explicit header or element writes.

The second header field is consulted as the loop proceeds; it is not initially captured as one fixed bound for this first search. The storage base is likewise obtained from the header for individual element accesses. This describes the supplied expression-level behavior, not a guarantee of machine-level reloads or synchronization.

A zero candidate receives no exemption from duplicate rejection. If any visited element is zero, a zero candidate is rejected at that point.

If the second header field is zero or negative, the initial search performs no element reads.

### 2. Conditionally invoke the dependency

After the initial search finishes without finding the candidate, the function compares the third header field with the second header field.

If they are equal, it calls F-926b44f5ac05 with the same header reference. If they differ, it proceeds without calling that dependency.

This condition is exact equality. A third field greater than the search bound does not trigger the call merely because it exceeds the bound.

The dependency’s return value is not used. No explicit result check follows the call.

The call occurs before searching for a zero slot. Consequently, equality triggers the dependency even when a zero slot already exists in the searchable prefix. The initial search looked for the candidate, not for a reusable slot.

No preservation of header fields, storage contents, allocation identity, or globals by F-926b44f5ac05 is established. The subsequent behavior must be understood using whatever accessible state exists when the dependency returns normally.

If the dependency does not return normally, this function has no demonstrated recovery or rollback path.

### 3. Capture the later search bound

After the optional dependency call, the function reads the second header field and retains that value as the bound for the zero-slot search.

This distinction matters:

- The first search consults the header’s second field as it proceeds.
- The later search uses a captured bound.
- Changes made by the dependency to the second field can therefore affect the later search.
- A negative captured bound causes the later search to inspect no elements.

There is no second duplicate search after the dependency returns. If the dependency introduces the candidate into storage, the function does not re-establish uniqueness before replacement.

### 4. Find the first zero slot

Starting at index zero, the function searches the prefix bounded by the captured value. It visits indices in ascending order and stops at the first element equal to zero.

For each visited position, the element address is derived from the base address held in the first header field and the four-byte index displacement.

If no zero is found, the function selects −1 as its result and performs no explicit replacement or header increment.

This includes a zero-length or negative-length later search. Any effects already produced by F-926b44f5ac05 remain; the function does not undo them.

A zero at an index equal to the captured bound is outside the search. A zero beyond the bound is likewise irrelevant, regardless of the third header field.

### 5. Update state on a found slot

A normally found slot has an index satisfying:

- The index is nonnegative.
- The index is strictly less than the captured bound.

For every such result, the function performs these explicit writes in this order:

1. Read the current third header field, add one, and write the result back to that field.
2. Obtain the storage base from the first header field.
3. Write the candidate into the found element slot.
4. Return the found index.

Index zero is a successful replacement position. It is not rejected by the later conditions.

The second header field is not explicitly modified by this function. Successful replacement therefore does not itself increase the searchable prefix.

The increment precedes the element write. There is no demonstrated transactional guarantee that both updates either happen together or are rolled back together.

### Arithmetic boundaries

The third-field increment has no overflow guard. Under a signed 32-bit interpretation, incrementing 2,147,483,647 exceeds the representable signed range. The supplied representation does not establish wrapping, saturation, or a defined error result for that case.

Element addressing includes multiplication by four and addition to an integer-held address. Both intermediate arithmetic and the resulting memory access must be valid under the target model. In a signed 32-bit arithmetic interpretation, a large positive index can make the multiplication unrepresentable before memory bounds are considered.

Ordinary positive search bounds do not, by themselves, require the loop index to advance beyond that bound. This does not eliminate the separate risks in displacement arithmetic, address construction, or the third-field increment.

## Side effects

### Explicit effects

Without a dependency call, the explicit effects are limited to:

- Reading the header and visited elements.
- Incrementing the third header field on successful replacement.
- Writing the candidate into the first zero slot found by the later search.

On immediate duplicate rejection, there are no explicit writes.

On failure to find a zero slot, there are no explicit writes by this function after the optional dependency call.

### Dependency effects

F-926b44f5ac05 may alter state before the zero-slot search. Its effects, including any allocation, release, relocation, header mutation, element mutation, or global-state changes, are unknown from the supplied evidence.

The function does not restore pre-call state when the later search fails.

### Aliasing and observation

No non-aliasing guarantee is supplied. If element storage overlaps the header, an element write can also change a header field. In such a layout, the statement that the function does not explicitly assign the second field does not imply that its underlying bytes remain unchanged.

Likewise, the third-field increment can affect memory subsequently observed through an aliased address. A replacement implementation must not assume independent header and element storage without an external precondition.

No locking, atomic update, or concurrent-access protocol is shown. The logical ordering described here is not a thread-safety guarantee or a specification of atomic machine operations.

- Elements: [12, 0, 0].

With a search bound of 2, third field of 5, elements [12, 25], and candidate 37:

- The dependency is skipped.
- The later search finds no zero.

Initial state:

- Search bound: 2.
- Third field: 2.
- Elements: [12, 0].
- Candidate: 25.

The function calls F-926b44f5ac05 even though a zero exists.

If that dependency returns normally and leaves this state unchanged, the function subsequently increments the third field to 3, writes 25 at index 1, and returns 1. Without a dependency postcondition, that final outcome cannot be guaranteed.

### Zero candidate is rejected when zero already exists

With searchable elements [12, 0] and candidate zero, the initial search returns −1 at index 1. No dependency call or replacement occurs.

A zero candidate can reach the replacement path only under different state conditions, such as a dependency introducing a zero after the initial search. If that occurs, writing zero back to the found slot still increments the third field and returns its index.

### Dependency introduces a duplicate

Suppose the initial search finds no candidate and equality triggers F-926b44f5ac05. If the dependency returns with captured-bound elements [25, 0] for candidate 25, the later search does not reject the newly introduced duplicate. Subject to valid arithmetic, it increments the third field, writes 25 at index 1, and returns 1.

- The dependency is skipped.
- The function returns −1 without explicit writes.

If both fields instead equal −2, the dependency is called, and the later result depends on its effects.
