# F-3222fac04966

## Purpose

F-3222fac04966 is a configuration-driven routine that can obtain a 32-bit value through F-57eae45cc059, publish that value to caller-provided storage, and return a 64-bit value containing two independently maintained 32-bit words.

None of those actions is unconditional. Configuration determines the initial operation, subsequent transitions, arithmetic operands, and termination. The supplied static evidence does not establish a normal execution sequence, a mandatory dependency call, a mandatory destination write, or guaranteed return.

Its established contract is therefore a parameterized state machine, not simply “call a helper and return its result.”

## Interface

### Inputs

| Input | Representation | Established use |
|---|---|---|
| Destination | Pointer to a 32-bit object | Saved at entry; becomes the active destination only through input activation. |
| Auxiliary value | Uninterpreted 32-bit word | Becomes the active auxiliary value through input activation; otherwise the dependency receives zero. |

The destination is not dereferenced at entry. Supplying null therefore does not itself cause an immediate memory access. A later destination-write operation nevertheless attempts a store through the active destination without checking it.

Whenever that store executes, the active destination must designate writable storage for one 32-bit object. Alignment requirements, address validation, and invalid-access recovery are not established.

### Return value

A returning execution produces a 64-bit concatenation:

- Bits 63–32: the current internal result cell.
- Bits 31–0: the current captured return-low word.

Equivalently, interpreting both halves as unsigned words, the value is the result cell multiplied by \(2^{32}\), combined with the return-low word. There is no sign extension between the halves. This numerical description does not depend on memory byte order.

Both halves initially equal zero. They subsequently change independently:

- The result cell can be cleared or modified through the dependency.
- The return-low word changes only during product capture.

A destination store does not itself change either half. The destination can consequently retain an earlier result even when the returned high half has subsequently changed.

### Per-invocation state

Each invocation begins with:

- A zero result cell.
- A null active destination.
- A zero active auxiliary value.
- A zero working word.
- A zero factor word.
- A zero return-low word.
- Saved caller inputs.

No persistent state in these values is established.

## Behavior

### Widths and arithmetic interpretation

The supplied representation uses 32-bit arithmetic words and a 64-bit return. The behavioral descriptions below use low-32-bit multiplication, addition, subtraction, and complement as a word-level model.

Unsigned arithmetic supports that modular interpretation directly. Some expressions in the supplied representation instead involve signed operands, including portions of state arithmetic and the multiplication used immediately after the dependency returns. The representation alone does not prove that overflowing signed expressions have defined wrapping behavior under a particular source-language interpretation.

Accordingly, examples involving overflow are conditional on the low-32-bit execution model. Exact machine behavior for those cases is **documented_only**, not runtime-confirmed.

The factor’s high-bit test also depends on signed right-shift behavior. The two-target interpretation below assumes an arithmetic right shift of a signed 32-bit word by 31 positions.

### Entry and dispatch

Entry configuration references occur in this order:

1. The multiplier is read and saved.
2. A base reference supplies the saved base-minus-six target.
3. Another base reference supplies the saved base-minus-one target.
4. A third base reference supplies the initial current state.

These are three source-level references to base configuration, not evidence of one shared snapshot. If configuration can change between evaluations, the three resulting values need not correspond to the same base value. Whether generated execution performs separate physical loads is not established.

At every dispatch, the current state is added to the dispatch offset. The resulting selector chooses an operation. Dispatch repeats without a visible iteration bound until the return operation is selected.

### Operations

| Selector | Established behavior |
|---|---|
| **0 — product capture** | Multiply the saved multiplier by the current factor word and place the low 32 bits in the working word. Read the capture target and install it as the next state. Copy the working word into the return-low word. |
| **1, and every selector outside 0–7 — destination decision** | Clear the result cell, then evaluate the destination-dependent transition described below. |
| **2 — dependency invocation** | Call F-57eae45cc059 with the address of the existing result cell and the active auxiliary value. Process its return value as described below. |
| **3 — destination write** | Store the result cell through the active destination as one 32-bit object. Then install the saved base-minus-one target. No null check occurs in this operation. |
| **4 — seed** | Read the seed word into the factor word. Continue at the saved base-minus-six target. |
| **5 — transform** | Multiply the transform coefficient, saved multiplier, and previous working word. Place the low 32 bits in the working word and copy that word into the factor word. Continue at the saved base-minus-six target. |
| **6 — input activation** | Read and install the activation target, then install the saved destination and original auxiliary input as the active inputs. |
| **7 — return** | Return the current result cell and return-low word as the specified 64-bit concatenation. |

An unrecognized selector performs the same operation as selector 1. It is not an explicit invalid-selector error.

### Destination-dependent transition

The result cell is cleared before the destination-dependent transition expression is evaluated.

That expression contains **two source-level references** to destination-target configuration:

- One reference belongs to the null-destination contribution. Two is added to that referenced value, and the result is multiplied by an indicator that is one for a null active destination and zero otherwise.
- The other reference belongs to the nonnull-destination contribution. That referenced value is multiplied by an indicator that is one for a nonnull active destination and zero otherwise.

The contributions are added to obtain the next state.

Thus:

- With a null active destination, the first reference contributes its value plus two; the second reference occurs in a term multiplied by zero.
- With a nonnull active destination, the second reference contributes its value; the first reference occurs in a term multiplied by zero.

This is not specified as choosing between branches that each contain only one configuration reference. Nor is it specified as taking one destination-target snapshot and reusing it. If both references obtain the same value, the transition simplifies numerically to “destination target plus two for null, destination target otherwise.”

The expression does not establish a physical-load count, an evaluation order between those references, or an atomic snapshot. Multiplication by zero also does not, by itself, prove that a physical read occurs or is omitted. For a literal signed-source interpretation, overflow in the addition of two remains a separate uncertainty even when that contribution is subsequently multiplied by zero.

### Dependency invocation and result processing

The dependency receives the address of the current result cell. This operation does not clear the cell first. Its incoming value may therefore be its initial zero, a previous dependency-written value, or a value retained across other operations.

After the dependency returns:

1. Its 32-bit return value is multiplied by the status coefficient to produce the working word.
2. Two word products are formed: saved multiplier times working word, and working word times mask coefficient.
3. The factor word becomes the bitwise complement of the bitwise OR of those products.
4. A selection indicator is derived from the factor’s signed right shift by 31 and negation.
5. The next state is formed by adding a saved-target contribution and a negative-mask-target contribution.

Under arithmetic right shift, the indicator is zero when the factor’s high bit is clear and one when it is set. The resulting contributions are:

| Factor high bit | Saved base-minus-one contribution | Negative-mask-target contribution |
|---|---|---|
| Clear | Saved target multiplied by one | Configuration value multiplied by zero |
| Set | Saved target multiplied by zero | Configuration value multiplied by one |

The transition expression therefore **references negative-mask-target configuration even when the factor’s high bit is clear**. In that case its term contributes zero to the next-state value. This separates the expression’s configuration references from the target that determines the numerical result.

No physical load on the zero-contribution path is guaranteed by this observation. Optimization, configuration storage properties, and actual load behavior are unresolved.

The status coefficient, mask coefficient, and negative-mask target are referenced after the dependency returns. The dependency is not assumed to preserve their values.

This processing is not a direct comparison of the dependency return value against zero. In particular, a zero dependency result produces a zero working word and an all-one factor word, selecting the negative-mask-target contribution under the stated shift interpretation.

The dependency’s return value does not directly become either returned half. Its separately writable result cell supplies the high half; product capture supplies the low half.

### Repetition and ordering

Configuration can cause operations to repeat or occur in unusual orders:

- Before input activation, the dependency receives auxiliary value zero.
- Before input activation, destination decisions treat the active destination as null, regardless of the caller’s pointer.
- Product capture can occur before input activation or before a dependency call.
- Later transforms and dependency calls change the working word without changing an already captured return-low word.
- Destination decisions clear the result cell but do not clear the return-low word.
- Destination writes occur before their following state transition.
- Multiple dependency calls, multiple destination stores, repeated resets, and nontermination are compatible with the supplied representation.

No established invariant requires activation before a destination write or a dependency call.

## Acceptance examples

These are conditional static examples, not observed executions. Each assumes configuration produces the stated sequence, accesses are valid unless an invalid-access case is being described, and arithmetic follows the stated word model.

1. **Immediate return.**  
   If the initial selector is 7, the routine returns zero. It neither calls the dependency nor writes the caller’s destination.

2. **Dependency call before activation, retaining a captured low word.**  
   Suppose selector 2 executes before input activation, with the return-low word currently equal to \(L\). The dependency receives auxiliary zero. If it writes \(H\), and return follows without another result-cell modification or product capture, the returned value is \(H \times 2^{32} + L\). Only if \(L=0\)—for example, because no product capture has occurred—is the result just \(H \times 2^{32}\).

3. **Earlier product capture survives the dependency call.**  
   If product capture establishes return-low word 15 before activation, a subsequent pre-activation dependency call writes 9, and return follows without changing either returned half, the result is `0x000000090000000F`.

4. **Activated destination publication.**  
   If activation installs a valid destination, a dependency call writes \(H\), and destination write follows before any reset, the destination receives \(H\). This does not itself change the return-low word.

5. **Reset after publication.**  
   If the preceding publication is followed by a destination decision and then return without further cell modification, the destination retains \(H\), while the returned high half is zero.

6. **Product capture with truncation.**  
   With saved multiplier 3 and factor `0x80000001`, product capture produces return-low word `0x80000003`. With a zero result cell at return, the returned value is `0x0000000080000003`.

7. **Zero dependency return.**  
   A dependency return of zero produces factor `0xFFFFFFFF`. Under arithmetic right shift, the negative-mask-target contribution determines the next state. Any dependency-written cell value remains independent of this calculation.

8. **Clear factor high bit.**  
   If result processing produces factor `0x7FFFFFFF`, the saved base-minus-one target determines the next-state value. The transition expression still references negative-mask-target configuration in a zero-multiplied term; this example makes no claim about a physical load.

9. **Two destination-target references.**  
   If the active destination is null, the null-destination reference contributes its value plus two, while the separate nonnull-destination reference belongs to a zero-multiplied term. If both references yield 40, the next state is 42. A single shared read is not an acceptance requirement.

10. **Nonnull input not yet active.**  
    A destination decision before activation uses the null-destination contribution even if the caller supplied a nonnull pointer.

11. **Null write path.**  
    If destination write is selected while the active destination is null, the routine attempts the store. No documented error result replaces that access.

12. **Default dispatch.**  
    A selector outside 0–7 clears the result cell and evaluates the destination-dependent transition; it does not immediately return an invalid-selector error.
