# F-389707b2b41e

## Purpose

F-389707b2b41e performs a lookup against state associated with a supplied object. It returns an existing entry’s associated 32-bit value when the lookup result differs from a separately obtained boundary value. When those values are equal, it obtains a new 32-bit value from a dependency, constructs a three-word record, submits that record through two further dependencies, and returns the newly obtained value.

This lookup-or-create interpretation is **inferred intent**. The established behavior is a sequence of calls, address calculations, equality testing, memory reads, and record construction. In particular, the available evidence does not establish that creation succeeds, that insertion occurs, or that the returned word is a pointer.

All behavior below is based on static evidence. No runtime tests have been performed.

## Interface

### Inputs

The function receives four machine-level inputs:

| Input | Established representation | Use |
|---|---|---|
| Object address | 32-bit address-bearing value | Supplies fields at byte offsets +4 and +76. |
| Auxiliary word | Opaque 32-bit value | Passed to the initial dependency. |
| First payload word | Opaque 32-bit value | Passed initially by value, then copied into addressable local storage. |
| Second payload word | Opaque 32-bit value | Passed initially by value and stored adjacent to the first payload word. |

These names describe roles, not established semantic types. The payload words could contain integers, handles, addresses, or another representation.

The first payload word has its address passed to a dependency. Consequently, later uses must distinguish the original input from the value remaining in that storage after the call. The second payload word occupies the next four bytes in the displayed layout. Whether a dependency is permitted to access that adjacent word is undocumented.

### Output

The function returns one opaque 32-bit word:

- On the existing-entry branch, the word read eight bytes before the selected node address.
- On the creation branch, the result returned by F-f50b25aae42a.

There is no separate status return. Zero has no established special meaning for the function’s final result.

## Behavior

### 1. Capture the initial state address

The function reads the object field at +76 and retains that state address for the initial lookup sequence.

It also places the payload inputs in local storage. Subsequent dependency calls may make the first payload word, and potentially its neighboring storage, externally accessible through an address argument.

The saved initial state address and later reloads of the object’s state field are distinct. The function does not consistently reuse a single state-field snapshot throughout its execution.

### 2. Produce the initial lookup value

From the saved state address, the function reads the 32-bit field at +4 and adds it to that state address.

It calls F-58cc241cfb6b with:

1. The calculated address.
2. The original auxiliary word.
3. The original first payload word.
4. The original second payload word.

Its 32-bit result is then passed to F-d7be9cfb4000 together with the field at +24 of the saved state.

A machine-level auxiliary result observed after F-d7be9cfb4000 supplies the slot index for the next step. The displayed call does not express this value as an ordinary returned value. Its exact ABI meaning is undocumented.

It would be plausible to interpret this dependency as computing a bucket index, but the evidence does not establish division, remainder, signedness rules, or any particular transformation.

### 3. Select a candidate through a slot

After F-d7be9cfb4000 returns, the function reads the slot-base field at +20 of the saved state. It calculates a slot address by adding four times the auxiliary index to that base.

It calls F-16846337587d with:

1. The saved state address.
2. The calculated slot address.
3. The address of the local first payload word.

The result is treated as a 32-bit candidate node address or sentinel-like value.

If this result is nonzero, the function retains that result as the candidate. It does not itself dereference the initially calculated slot to obtain the candidate on this path.

If this result is zero, the function instead:

1. Reads the slot-base field at +20 of the saved state again.
2. Reads the index-like field at +24 of that state again.
3. Calculates a fallback slot address using a four-byte stride.
4. Reads one 32-bit word from the fallback slot.
5. Uses that word as the candidate.

The fallback word is not checked for zero before later processing.

These are fresh field reads after F-16846337587d. Changes made by dependencies to the saved state’s fields can therefore affect the fallback location.

### 4. Obtain a boundary value

The function reloads the object field at +76 and passes the resulting state word to F-d6fd6932ce90, along with an address into local output storage.

After this call, it reads a 32-bit word adjacent to the beginning of that output storage and treats it as the boundary value.

The displayed local layout is consistent with an eight-byte output object whose second word contains this boundary value. However, the displayed declaration identifies only the first four-byte region as the explicit output buffer. A dependency contract or lower-level layout evidence is needed to establish the full output extent.

The function compares the candidate and boundary values for exact 32-bit equality. This is not an ordering comparison or a test for nonzero.

### 5. Return the existing associated value when unequal

If the candidate differs from the boundary, the function reads four bytes at candidate address minus eight and returns that word.

This branch does not call F-f50b25aae42a, F-283d1c3e26b7, or F-0f1ba805a3b8.

There is no explicit validation that the candidate denotes readable storage. In particular, a zero fallback candidate that differs from the boundary still leads to the candidate-minus-eight access.

### 6. Obtain and submit a new value when equal

If the candidate equals the boundary, the function calls F-f50b25aae42a with:

1. The current object field at +4.
2. The boundary word.
3. The current first payload word.
4. The current second payload word.

It saves the returned 32-bit word.

After that call, it assembles the three-word record described in the interface: current payload words followed by the saved result. Thus, the payload contents used in the record are loaded after F-f50b25aae42a returns. They must not be assumed to equal earlier values if a dependency can access them through a retained alias.

It then reloads the object field at +76 and calls F-283d1c3e26b7 with:

1. An address to local output storage.
2. That freshly loaded state word.
3. An address to the three-word record.

Afterward, it calls F-0f1ba805a3b8 with a second local output-storage address and the output-storage address supplied to F-283d1c3e26b7.

Neither of these calls contributes a checked success status to the function’s return decision. On normal completion, the function returns the word previously obtained from F-f50b25aae42a, not a field reread from the record or either later output area.

### Arithmetic and access constraints

Field accesses and slot elements are 32 bits wide. Slot displacement uses multiplication by four; it is not a byte-sized or eight-byte-sized table stride.

The state-relative address, slot-address calculations, and candidate-minus-eight access have no visible overflow, range, or alignment checks. The established operations are 32-bit address-bearing calculations; the evidence does not establish portable behavior for overflow or invalid addresses.

The order above establishes call sequencing and reads separated by calls. It does not establish an evaluation order between independent argument-field reads within one call, or between independent operands of a single address expression.

## Side effects

### Direct effects

The function directly writes its own local storage, including:

- Payload copies.
- Lookup and boundary bookkeeping.
- The three-word creation record.
- Storage passed as output destinations to dependencies.

No direct store to the supplied object, associated state, slot table, or selected node is visible in the function body.

That does **not** make the operation externally read-only. Dependencies receive addresses or values that may permit mutation.

### Dependency-mediated effects

Potential externally visible effects include changes to the object, associated state, table contents, payload storage exposed by address, and other dependency-accessible state. Their actual scope is undocumented.

The function’s rereads matter:

- F-d7be9cfb4000 precedes the slot-base read used for initial selection.
- F-16846337587d precedes fallback field rereads.
- The boundary call uses a freshly loaded object state field.
- The creation-submission call uses another freshly loaded object state field.
- The object field at +4 is read only when creation is selected.

These operations can observe different state across one invocation. No locking, retry, snapshot consistency, or concurrency guarantee is established.

### Ownership and lifetime

The function contains no explicit allocation or deallocation operation. Dependency names and argument shapes are insufficient to establish allocation or ownership transfer.

Addresses passed for payload, record, and output storage refer to storage local to the invocation. That storage does not remain valid after return. Whether dependencies copy its contents, retain addresses, or release referenced resources is undocumented. Safe composition requires dependency behavior compatible with these lifetimes; the available evidence does not prove it.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. They assume dependencies return normally and all referenced accesses are valid.

### Existing candidate

Suppose F-16846337587d returns a nonzero candidate, F-d6fd6932ce90 supplies a different boundary, and the 32-bit word eight bytes before the candidate is 37.

The function returns 37. It does not execute the three creation-branch calls.

### Fallback selects an existing entry

Suppose F-16846337587d returns zero. After that call, the saved state’s slot base is B and its +24 field is N. The word at B + 4N is candidate C, C differs from the boundary, and the word at C − 8 is 91.

The function returns 91. The original auxiliary index does not select the fallback slot.

### Nonzero candidate equals the boundary

Suppose F-16846337587d returns a nonzero word equal to the boundary.

The creation branch executes. A nonzero candidate alone does not establish an existing entry.

If F-f50b25aae42a returns 52, the function submits a record ending in 52, performs the final dependency call, and returns 52 on normal completion.

### Fallback selects the boundary

Suppose the initial candidate is zero and the fallback-slot word equals the boundary.

The same creation sequence executes. Selection of that branch does not depend on whether equality arose from the direct candidate or fallback.

### Payload modification during lookup

Suppose the original first payload is 10, and F-16846337587d changes its addressable storage to 12. If creation is selected and that storage remains unchanged until use, F-f50b25aae42a receives 12, not 10.

The initial F-58cc241cfb6b call still received the original value 10.

### State replacement during dependencies

Suppose the object’s +76 field initially names state A, then a dependency changes it to state B before the boundary call.

The initial lookup continues using saved state A. The boundary call receives B. A later change to state C before creation submission causes F-283d1c3e26b7 to receive C. No automatic reconciliation is visible.

### Zero creation result

Suppose the creation dependency returns zero and all subsequent calls complete normally.

The function still performs both remaining creation-branch calls and returns zero. It contains no explicit zero-result error branch.

## Uncertainties

- Semantic types of all opaque words and address-bearing fields.
- Full object, state, slot-table, node, and output-object layouts.
- Exact ABI source and validity of the auxiliary slot index.
- Boundary-output initialization and required output extent.
- Behavior for null pointers, invalid alignment, arithmetic overflow, inaccessible memory, or an out-of-range index.
- Behavior when the +24 state field is zero.
- Dependency failure signaling, nonlocal exits, and exceptions.
- Whether the creation sequence actually inserts or preserves an entry.
- Ownership, allocation, destruction, and retained-reference rules.
- Concurrency safety and invariants spanning different state snapshots.

The apparent lookup-or-create design is useful explanatory intent, but it does not resolve these uncertainties.
