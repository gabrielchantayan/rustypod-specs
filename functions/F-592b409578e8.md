# F-592b409578e8

## Purpose

F-592b409578e8 returns a byte-string pointer associated with a caller-supplied object. It first checks a cached pointer. When that pointer is null, it searches a record table for one of two eligible record classes, prefers one class over the other, and attempts to construct a terminated byte string from the selected record.

The preferred class is interpreted as two-byte units and filtered to printable seven-bit bytes. The fallback class is copied as raw bytes and receives an additional zero terminator.

These descriptions express the behavior visible in the supplied static evidence. The semantic meaning of the object, record classes, selector constant, and backing data is not established. In particular, this is not evidence of a general-purpose text decoder.

## Interface

### Input and result

The sole input is a 32-bit address identifying a mutable object. The function returns a byte pointer, represented as a 32-bit value in the supplied representation.

There is no explicit status return. A null result can mean that no eligible record exists or that a selected-record operation failed. Conversely, the visible control flow does not guarantee that every non-null result denotes a successfully constructed string: an allocation dependency’s nonzero status does not cause its returned pointer to be cleared.

No validation of the input address, table bounds, stream state, or dependency outputs is visible.

## Behavior

### 1. Cache check

The function first reads the pointer at object offset `0x294`.

If this pointer is non-null, the function returns that exact pointer immediately. It does not scan records, call dependencies, validate the cached bytes, or explicitly modify the object.

If the pointer is null, the function proceeds to selection.

### 2. Record selection

The function scans records in increasing index order, beginning with index zero. The loop condition reads the object’s unsigned 16-bit record count on each iteration. The table base is read when locating each scanned record.

A record is eligible for either class only if:

- Its 16-bit field at offset `0x06` equals 6.
- Its 16-bit field at offset `0x08` is nonzero.

Among eligible records, a **preferred-class record** satisfies all of the following:

- Primary selector equals 3.
- Secondary selector, interpreted as unsigned 16-bit, equals 1.
- Tertiary selector, interpreted as unsigned 16-bit, equals the global selector value.

An eligible **fallback-class record** satisfies:

- Primary selector equals 1.
- Secondary selector equals zero.
- Tertiary selector equals zero.

Other selector combinations do not qualify.

Each newly encountered match replaces the remembered index for its class. Consequently:

- The last preferred-class match wins.
- The last fallback-class match wins.
- Any preferred-class match takes precedence over every fallback-class match, regardless of their relative positions.

Selection completes before any allocation or stream operation occurs. The selected record address is then computed using a fresh read of the table-base field.

If neither class has a match, the result remains null. The function writes null to the cache field and returns null.

A failure while processing a preferred-class match does not cause the function to try a fallback-class record or an earlier preferred-class record. Likewise, failure of the selected fallback record does not cause another candidate to be tried.

### 3. Fallback-class construction

For the selected fallback record, the function reads its unsigned 16-bit length and captures the object’s allocation context.

It initializes a 32-bit status slot to zero and invokes F-3ce007b692cc with:

- The captured allocation context.
- The length plus one.
- The address of the status slot.

The returned pointer becomes the prospective result.

If the status slot is nonzero after the call, this path performs no explicit stream operation, termination write, record invalidation, or release. The returned pointer—whether null or non-null—is subsequently written to the cache and returned.

If the status is zero:

1. The function reads the stream-like field at object offset `0x168`.
2. It invokes F-e40a3ceddab2 using that value and the selected record’s current 32-bit position field.
3. Only if positioning returns zero does it invoke F-0c21b5cad025, passing the same stream value, the allocated pointer, and the previously captured length.
4. If both operations return zero, it writes a zero byte at output offset equal to that captured length.

The raw data is not filtered. Embedded zero bytes remain present. The extra terminator does not imply that all copied bytes will be visible to a consumer that stops at the first zero.

If positioning or raw reading returns nonzero, the function performs the following explicit actions in this order:

1. Writes zero to the selected record’s 32-bit position field.
2. Writes zero to its 16-bit length field.
3. Reads its ancillary resource field and passes that value, with the captured allocation context, to F-bf7242c98d06.
4. Writes zero to the ancillary resource field.
5. Passes the allocated output pointer and the captured allocation context to F-bf7242c98d06.
6. Sets the prospective result to null.

The raw-read dependency is not called when positioning fails.

### 4. Preferred-class construction

For the selected preferred record, the function captures the allocation context and initializes the status slot to zero.

It reads the unsigned 16-bit length to calculate a pair count: the length shifted right by one, equivalent to rounding half the length downward. It separately reads the length for an allocation request of length plus one.

If F-3ce007b692cc reports a nonzero status, the function retains its returned pointer as the prospective result. It performs no explicit stream operation, output termination, or cleanup before caching and returning that pointer.

If allocation reports zero status:

1. The function reads the stream-like object from object offset `0x168`.
2. It invokes F-e40a3ceddab2 with that object and the selected record’s current position field.
3. Only if positioning returns zero does it invoke F-d036abe1e536 with the stream object and the selected record’s then-current 16-bit length.
4. Only if both calls return zero does it read the buffer pointer at stream offset `0x20` and construct output.

Construction examines exactly the previously calculated number of consecutive two-byte units. For each unit:

- The first byte must be zero.
- The second byte must be greater than `0x1F` and less than `0x80`.
- If both conditions hold, the second byte is appended to the output.
- Otherwise, that unit contributes no output byte.

The second input byte is consulted by the visible condition only when the first byte is zero. The input position advances by two bytes regardless of whether a byte is emitted. Output is compacted: rejected units do not produce placeholders.

Accepted bytes are exactly `0x20` through `0x7F`, inclusive. Thus space is retained, and `0x7F` is also retained despite not ordinarily being considered printable text.

After examining all complete pairs, the function writes a zero byte immediately after the emitted bytes. It then calls F-9787e15c337d with the stream object. The return value of that call is not inspected.

An odd trailing input byte is not examined by the conversion loop. A length of one therefore produces an empty terminated output if the preceding dependencies succeed.

If positioning or buffer preparation returns nonzero, the explicit failure actions occur in this order:

1. Pass the allocated output pointer and captured allocation context to F-bf7242c98d06.
2. Write zero to the selected record’s 16-bit length field.
3. Write zero to its 32-bit position field.
4. Read the ancillary resource field and pass it, with the captured allocation context, to F-bf7242c98d06.
5. Write zero to the ancillary resource field.
6. Set the prospective result to null.

F-d036abe1e536 is not called if positioning fails. F-9787e15c337d is called only after successful conversion and termination, not on these failure paths.

### 5. Cache publication and arithmetic

Every path that entered with a null cache eventually writes the prospective result to object offset `0x294`, then returns that same pointer value.

A null cached result does not suppress future work: another invocation with a null cache scans again. A non-null cached result bypasses all later work.

Lengths are zero-extended from 16 bits before the allocation-size addition. The largest requested allocation is therefore 65,536 bytes; the addition does not wrap at 16 bits.

The preferred pair count is at most 32,767. Under stable record contents, its output contains at most that many retained bytes plus one terminator. The fallback path can copy up to 65,535 bytes and append one terminator.

The scan index and record-address arithmetic use 32-bit quantities. No explicit address-overflow or bounds check is present.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid accessible memory, stable relevant fields, successful dependencies, and a valid allocation result.

1. **Existing cache.** A non-null cache is returned unchanged. No dependency is called.

2. **Empty table.** With a null cache and record count zero, no record is examined. Null is written to the cache and returned.

3. **Last-match precedence.** If fallback matches occur at indices 1 and 8, and preferred matches at indices 2 and 5, index 5 is selected. Index 8 does not override preferred-class priority.

4. **Ineligible zero length.** A record with otherwise matching selectors but length zero is ignored. No allocation is attempted for it.

5. **Raw bytes with embedded zero.** A fallback record of length three yielding bytes `41 00 42` produces storage containing `41 00 42 00`. The embedded zero is preserved.

6. **Preferred filtering boundaries.** Six pairs `00 1F`, `00 20`, `00 7E`, `00 7F`, `00 80`, and `01 41` produce output bytes `20 7E 7F 00`. The first, fifth, and sixth pairs are discarded.

7. **Odd preferred length.** Length three causes one complete pair to be examined. If that pair is `00 41`, output is `41 00`; the third input byte is ignored by conversion.

8. **Allocation status failure.** If allocation returns a nonzero status and pointer P, P is cached and returned without an explicit terminator write or release. This holds even if P is non-null. If P is null, null is cached.

9. **Preferred positioning failure.** Buffer preparation and completion are not called. The output-release call precedes explicit record clearing; the final result and cache are null. No fallback candidate is attempted.

10. **Repeated call after invalidation.** Following a stream-operation failure, the selected record’s explicitly cleared length makes it ineligible on a later scan, provided no intervening action changes that field. Another record may then be selected.
