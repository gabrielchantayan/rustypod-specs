# F-ea211170ad1a

## Purpose

F-ea211170ad1a fills caller-supplied storage with a 72-byte sequence and returns the smaller of an unsigned input count and 72.

The first output byte is copied from the byte at a supplied source base plus 24. The remaining 71 bytes have fixed values.

Construction is unconditional. The count limits only the returned number; it does not limit reads, writes, or destination capacity requirements. A count of zero still causes the source read and all 72 destination assignments.

The fixed sequence may be a template or structured record. That interpretation is inferred intent, not an established format or protocol requirement.

## Interface

### Inputs

| Input | Role | Successful-execution requirement |
|---|---|---|
| Source base | Signed integer used as an address base | Adding 24 must produce a usable address representation, and the byte at that address must be readable. |
| Destination | Pointer to byte-addressable storage | All 72 bytes at destination offsets 0 through 71 must be writable, regardless of count. |
| Count | Unsigned integer controlling the reported result | Any value representable by the input type is accepted by the visible comparison logic. |

The source base is represented as an integer rather than a typed source pointer. The supplied evidence does not establish the calling environment’s rules for converting addresses to this representation.

There is no visible requirement that source and destination storage be disjoint. Overlap affects which existing byte supplies the first output byte, as described under **Behavior**.

Destination accesses are byte-sized. No additional alignment requirement is visible, although address validity remains an environmental prerequisite.

### Return value

On normal completion:

\[
\text{return value}=\min(\text{count},72)
\]

The return type is unsigned.

- Counts from 0 through 72 are returned unchanged.
- Counts above 72 return 72.
- Every successful invocation assigns the complete 72-byte destination region.

The result is not a measurement of how many bytes were actually assigned. In particular, a result below 72 does not imply a correspondingly smaller memory footprint.

### Widths and arithmetic

The observable layout comprises 72 consecutive byte-sized storage locations. The values in this contract describe their eight-bit patterns, including values above `0x7F`; no character encoding is implied.

The source base has a signed integer representation. The count, result, and loop-control values have unsigned integer representations. Exact integer widths and the target ABI are **documented_only**: the supplied material does not include the relevant type definitions or an ABI declaration. A 32-bit interpretation is consistent with the material but is not independently established here.

The count is only compared with 72 and, when larger, replaced with 72. No count addition, subtraction, multiplication, or narrowing is visible.

The loop-control arithmetic remains within 0 through 64. Its eight-bit mask therefore does not cause wraparound during this operation.

## Behavior

### Preconditions

The successful-execution contract requires:

1. A valid source-address calculation.
2. A readable byte at the resulting source address.
3. Writable destination storage covering offsets 0 through 71.
4. Storage lifetimes and access permissions sufficient for the complete operation.
5. No conflicting external access that invalidates the stated memory behavior.

The function performs no visible validation of these conditions. It does not check for null addresses, verify storage size, or use the count to authorize or suppress destination writes.

If a caller treats count as a destination capacity, the caller must still provide at least 72 writable bytes. A smaller count does not make a smaller allocation sufficient.

### Observable construction order

The supplied representation establishes the following logical memory-access order:

1. Read one byte from source base plus 24.
2. Store that value at destination offset 0.
3. Assign the fixed bytes at destination offsets 1 through 7, in increasing offset order.
4. Assign the fixed sequence at destination offsets 8 through 71, in increasing offset order.
5. Apply the count bound and return the result.

The initial source value is read once. There is no later source read.

This order describes the supplied operation sequence, not a guarantee of separate machine instructions, atomicity, synchronization, memory barriers, or device-visible ordering. Those properties are not established.

### Destination layout

Let \(S\) be the byte obtained by the initial source read.

| Destination offset | Length | Contents after normal completion |
|---|---:|---|
| 0 | 1 byte | \(S\) |
| 1–2 | 2 bytes | `0x00`, `0x00` |
| 3 | 1 byte | `0x44` |
| 4 | 1 byte | `0x00` |
| 5 | 1 byte | `0x80` |
| 6 | 1 byte | `0x83` |
| 7 | 1 byte | `0xB0` |
| 8–71 | 64 bytes | Consecutive values `0xC0` through `0xFF`, inclusive |

For the final region:

\[
\text{destination}[8+k]=192+k,\qquad 0\leq k<64
\]

Consequently:

- Offset 8 contains `0xC0`.
- Offset 9 contains `0xC1`.
- Offset 70 contains `0xFE`.
- Offset 71 contains `0xFF`.

Exactly 64 bytes belong to the final region. Together with the first eight assignments, this produces a 72-byte footprint.

The tail construction uses negative intermediate arithmetic values before byte storage. Its established output is the byte-pattern sequence above; those intermediate values do not make the output a sequence of textual characters or impose a signed-byte interpretation on consumers.

### Count independence

The complete destination construction precedes count handling.

There is no zero-count shortcut, short-output mode, or count-dependent loop bound. Count values 0, 5, 72, and values greater than 72 all produce the same destination contents when the source byte and memory conditions are the same.

Only the result differs:

| Count range | Result | Destination bytes assigned |
|---|---:|---:|
| 0–71 | Original count | 72 |
| 72 | 72 | 72 |
| Greater than 72 | 72 | 72 |

The comparison is strictly against values greater than 72. Equality does not select a different construction path.

### Aliasing and preservation of the initial source value

No non-overlap restriction is visible.

When the source location lies inside the destination region, its previous value is read before any destination assignment. That captured value supplies destination offset 0 even if a later write replaces the source location.

For ordinary valid memory without external interference:

- If the source location is destination offset 0, the initial value is read and then written back to that offset.
- If the source location is destination offset 1 through 71, its initial value is copied to offset 0 before the corresponding fixed-value write replaces it.
- The function does not reread the source after any overwrite.

These cases do not require preservation of the source location’s final contents. They require preservation only of the initially read value for the first destination assignment.

## Side effects

### Memory mutation

On normal completion, every destination byte at offsets 0 through 71 is assigned. No explicit destination write occurs outside that region.

No reads are performed through the destination pointer. The initial source read can read a destination byte’s previous contents when the source location aliases the destination.

Thus, previous destination contents normally have no influence on the result, but one previous destination byte can determine output offset 0 through source aliasing. The remaining 71 output bytes are fixed.

The source location is directly read, not directly written through the source address. It can nevertheless be modified by a destination write when the two regions overlap.

### Ownership and lifetime

No allocation, deallocation, ownership transfer, or address retention is visible. The function uses caller-provided storage for the duration of the operation.

The evidence does not establish any extension of storage lifetime or any mechanism for obtaining additional destination capacity. The caller remains responsible for supplying valid storage.

### Errors and partial effects

There is no explicit error result, validation failure branch, or recovery mechanism. The returned count is not a success status and does not report completed writes.

Invalid source or destination accesses fall outside the successful-execution contract. The supplied material does not determine whether such an access causes a trap, process termination, or another environment-specific outcome.

If execution stops during construction, earlier writes may remain visible. No rollback is present. Neither the final 72-byte layout nor a normal return is promised after an invalid access.

### Other state

This does not make the referenced storage private: caller-supplied addresses may designate shared memory or other externally observable storage. Concurrency and special-memory behavior remain environmental concerns.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence. They are not reports of executed tests.

### Large count with separate storage

Given valid, non-overlapping source and destination storage, source byte `0x5A`, and count 100:

- The result is 72.
- Destination offset 0 becomes `0x5A`.
- Offsets 1 through 7 become `00 00 44 00 80 83 B0`.
- Offsets 8 through 71 become `C0` through `FF` in ascending order.
- The function performs no explicit write at destination offset 72.

### Boundary count

Given valid storage and count 72:

- The result is 72.
- All 72 destination bytes are assigned.
- Construction is identical to the count-100 example for the same source byte.

For count 71 under the same memory conditions, the result is 71, but offset 71 is still assigned `0xFF`.

### Short count with sufficient storage

Given 72 writable destination bytes and count 5:

- The result is 5.
- All 72 bytes are assigned.
- Destination offsets 5 through 71 are not preserved merely because they lie beyond the returned count.

The result cannot be used to infer that only five bytes were touched.

### Zero count

Given valid source and destination storage and count 0:

- The source byte is read.
- All 72 destination bytes are assigned.
- The result is 0.

A zero count does not make a null or inaccessible destination acceptable.

### Source aliases a tail byte

Given that the source address equals destination offset 8 and that this byte initially contains `0x2A`:

- The initial source read reads that destination byte’s previous contents.
- Destination offset 0 becomes `0x2A`.
- Destination offset 8 later becomes `0xC0`.
- No later source read changes the value already selected for offset 0.

These outcomes assume valid ordinary memory and no external mutation.

### Source aliases a header byte

Given that the source address equals destination offset 3 and that this byte initially contains `0x7E`:

- Destination offset 0 becomes `0x7E`.
- Destination offset 3 subsequently becomes `0x44`.

The fixed header assignment does not retroactively change the captured source value.

### Source aliases destination offset 0

Given that the source address equals destination offset 0:

- Its initial byte is read and written back at offset 0.
- The other 71 bytes are assigned their fixed values.

### Insufficient destination storage

A destination with only five writable bytes fails the preconditions even when count is 5.

There is no established successful result for this case. The operation is not truncated to five bytes; its construction requires writes through offset 71.
