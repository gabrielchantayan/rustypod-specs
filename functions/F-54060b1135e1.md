# F-54060b1135e1

## Purpose

F-54060b1135e1 performs an ordered preparation-and-status sequence on caller-supplied storage. For a non-null storage address, it invokes one dependency, writes two supplied 32-bit values into the storage, and invokes a second dependency with an interior address. If the second dependency returns zero, it copies a value from a global location into the first 32-bit slot of the storage. It returns the second dependency’s status unchanged.

A null storage address is rejected with −50 before either dependency is called.

This is a behavioral contract for the visible function body, not a guarantee about its dependencies. In particular, the evidence does not establish that the first dependency clears memory, that the second dependency initializes an object, or that either dependency preserves the supplied values.

## Interface

### Inputs

The function accepts three arguments:

| Argument | Visible interpretation |
|---|---|
| Storage address | Nullable pointer to storage addressed in 4-byte units. |
| First supplied value | An opaque 32-bit value written at byte offset 48 from the storage address. |
| Second supplied value | An opaque 32-bit value written at byte offset 52 from the storage address. |

The supplied values have no established signedness or semantic meaning. They may represent integers, flags, addresses, or other 32-bit payloads; the visible function does not distinguish among these interpretations or validate their contents.

For a non-null address, the directly visible accesses involve these locations:

| Byte offset | Width | Visible use |
|---|---:|---|
| 0 | 4 bytes | Written only when the second dependency returns zero. |
| 12 | Address only at this level | Passed to the second dependency as an interior storage address. |
| 48 | 4 bytes | Receives the first supplied value before the second dependency call. |
| 52 | 4 bytes | Receives the second supplied value before the second dependency call. |

The first dependency receives the original storage address and the numeric argument 56. The meaning of that numeric argument is not established by its call site.

### Output

The function returns an integer status:

- −50 when the storage address is null.
- Otherwise, exactly the status returned by F-d66002da6765.

Zero has a specific local consequence: it permits the final write at offset 0. Any nonzero status suppresses that write, without distinguishing positive from negative results.

The supplied representation uses a signed integer return type in an apparently 32-bit environment. A 32-bit signed status interpretation is consistent with that evidence; the source excerpt alone is not a complete ABI specification.

### Preconditions for defined execution

A null address requires no backing storage because this function does not dereference it.

For a non-null address, the caller must provide storage suitable for the direct 4-byte accesses and the interior-address calculation described above. A writable 56-byte region covers the function’s own possible writes, but does **not** establish sufficient storage for either dependency: their access requirements are unknown.

Alignment requirements, dependency-specific storage requirements, permitted aliasing, and concurrent-access constraints are documented_only. No visible checks enforce them.

## Behavior

### Null-address path

If the storage address is null, the function returns −50 immediately.

On this path, the visible body:

- Does not call F-c67cb20988a1.
- Does not call F-d66002da6765.
- Does not read or write the caller’s storage.
- Does not read the global value used by the successful non-null path.

The two supplied values do not affect this result.

### Non-null preparation

For a non-null address, the first externally visible action in the body is a call to F-c67cb20988a1 with:

1. The original storage address.
2. The numeric value 56.

The function neither captures nor checks a result from that call. The dependency’s return type and any significance of its result are not established here.

If the dependency returns normally, the function performs two 4-byte stores in this order:

1. The first supplied value is written at offset 48.
2. The second supplied value is written at offset 52.

Consequently, changes that the first dependency makes to those locations are overwritten by these direct stores. This does not imply that any other changes made by the dependency are undone.

There is no visible validation between the dependency’s return and these writes.

### Status-producing dependency call

After both supplied-value stores, the function calls F-d66002da6765 with four arguments, in this argument-position order:

1. The numeric value 4.
2. Zero.
3. Zero.
4. An address 12 bytes beyond the original storage address.

The fourth argument is an interior address, not a copied storage block and not the original base address.

The visible contract does not establish what the first three arguments mean. In particular, the value 4 must not be described as a byte count, a mode, or a resource type without additional evidence.

F-d66002da6765 is reached only after both supplied-value stores have occurred. Subject to its own access behavior, it can therefore observe the stored values. It may also alter those locations or other state; preservation is not established.

The function captures this dependency’s integer status and uses it both to choose the final-write branch and as its return value.

### Zero-status completion

If F-d66002da6765 returns zero, the function reads a 32-bit value from a designated global location and writes that value into the first 4-byte slot of the caller’s storage.

This global read occurs after the second dependency has returned. The function does not visibly cache the global value before either dependency call. Thus, if either dependency changes that global location, the final write uses the value present at the later read, not necessarily the value present on entry.

After the offset-0 store, the function returns zero.

The offset-0 write does not restore the supplied values at offsets 48 and 52. If the second dependency changed them, those changes remain unless an independently established alias relationship produces another effect.

### Nonzero-status completion

If F-d66002da6765 returns any nonzero status, the function returns that status without performing its conditional global read or offset-0 store.

This is not a rollback path. The first dependency has already run, both supplied-value stores have already occurred, and the second dependency may already have produced side effects.

A nonzero result therefore does not establish that the storage is unchanged or that offset 0 retains its entry value. It establishes only that this function omits its final direct write to offset 0.

### Arithmetic and representation

The storage layout follows 4-byte indexing:

- Three units correspond to the interior-address displacement of 12 bytes.
- Twelve units correspond to the first supplied-value offset of 48 bytes.
- Thirteen units correspond to the second supplied-value offset of 52 bytes.

There is no visible arithmetic on either supplied value. Each is stored as a 32-bit payload.

The function performs no visible range, alignment, or pointer-overflow validation. Invalid non-null addresses do not have a defined error status in this contract.

## Side effects

The direct effects of a normally returning non-null invocation are:

- One call to F-c67cb20988a1.
- A 4-byte write at offset 48.
- A 4-byte write at offset 52.
- One call to F-d66002da6765.
- On zero status only, a global 32-bit read followed by a 4-byte write at offset 0.

This ordering is material. There is no transaction, rollback, retry, or compensating call in the visible body.

No direct allocation, release, or ownership-transfer operation appears in the function. Passing the storage address to dependencies does not, by itself, prove that they borrow it only for the duration of the call. Whether either dependency retains an address, allocates resources, releases resources, or changes global state is documented_only.

The function does not visibly release the supplied storage before returning. Its continued usability nevertheless depends on the dependencies’ unknown contracts.

The ordering above describes the visible source-level sequence. It is not a guarantee of atomicity, cross-thread synchronization, or observation by an unsynchronized concurrent reader.

## Acceptance examples

These examples are conditional acceptance criteria, not executed tests.

1. **Null storage**

   Given a null storage address and arbitrary supplied values, the result must be −50. Neither dependency may be called by this function, and its conditional global read must not occur.

2. **Zero status with preserving dependencies**

   Given valid storage, a normally returning first dependency, and a second dependency that returns zero without changing offsets 48 or 52, the supplied values must occupy those offsets on return. Offset 0 must contain the global value read after the second dependency returns. The result must be zero.

3. **Nonzero status**

   If the second dependency returns −7, the result must be −7. The function must not perform its conditional global read or offset-0 store. No unchanged-storage guarantee follows.

4. **First dependency changes the supplied-value locations**

   If the first dependency writes arbitrary data at offsets 48 and 52 and returns normally, the function must overwrite those locations with the two supplied values before calling the second dependency.

5. **Second dependency changes the supplied-value locations**

   If the second dependency changes either supplied-value location and returns normally, this function must not restore the earlier supplied value. This applies to both zero and nonzero status.

6. **Global value changes during a dependency call**

   If a dependency changes the designated global value and the second dependency returns zero, the final offset-0 store must use the value present when the global is subsequently read.

7. **Positive nonzero status**

   If the second dependency returns 1, the function must return 1 and omit the final direct offset-0 store. Positive statuses are not treated as zero.

**Inferred intent:** the sequence resembles preparation of caller-owned structured storage followed by installation of a header-like value on success. That interpretation is not required for conformance.
