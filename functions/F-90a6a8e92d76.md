# F-90a6a8e92d76

## Purpose

F-90a6a8e92d76 traverses contours represented by coordinate records, point tags, and inclusive contour-end indices. It reports each contour through callbacks for an initial position, straight segments, one-control-point curves, and two-control-point curves.

The established behavior includes coordinate transformation, insertion of implicit midpoint endpoints, contour closure, selective tag validation, and immediate propagation of callback errors. It does not include rendering, allocation, or comprehensive input validation.

The apparent intent is decomposition of an outline containing straight, quadratic, and cubic segments. That interpretation explains the callback shapes and tag handling; the observable contract is the callback sequence described below, including acceptance of some tag combinations that a stricter outline format might reject.

## Interface

The function accepts three arguments:

1. **Outline descriptor:** a pointer to a structure containing contour metadata and point data.
2. **Callback descriptor:** a pointer to four callback addresses and two transformation parameters.
3. **Context:** an opaque 32-bit value forwarded to each invoked callback.

It returns a 32-bit integer status:

- **0:** traversal completed successfully, including the case where the signed contour count is nonpositive.
- **6:** either descriptor pointer is null.
- **20:** an encountered tag sequence is rejected by this function.
- **Any nonzero callback result:** returned immediately and unchanged.

A callback can itself return 6 or 20; the return value alone does not identify the source of an error.

### Outline descriptor layout

The supplied representation establishes the following byte offsets:

| Offset | Field | Interpretation |
|---|---|---|
| 0 | Contour count | Signed 16-bit integer |
| 4 | Coordinate-array address | 32-bit address |
| 8 | Tag-array address | 32-bit address |
| 12 | Contour-end-array address | 32-bit address |

Other descriptor bytes are not interpreted by the shown function.

Each coordinate record occupies 8 bytes: a signed 32-bit x coordinate followed by a signed 32-bit y coordinate.

Each tag occupies one byte. Only its two least significant bits affect classification:

| Low two bits | Meaning used during traversal |
|---|---|
| 0 | One-control-point-curve control |
| 1 | Explicit endpoint |
| 2 | Two-control-point-curve control |
| 3 | Context-dependent treatment described below |

Contour-end entries are signed 16-bit point indices. Each identifies the inclusive final point of a contour. The first contour starts at point index 0; a subsequent contour starts one point after the preceding contour’s original end index.

There is no visible point-count field or bounds check.

### Callback descriptor layout

| Offset | Field |
|---|---|
| 0 | Callback F-000000000001 |
| 4 | Callback F-000000000002 |
| 8 | Callback F-000000000003 |
| 12 | Callback F-000000000004 |
| 16 | 32-bit shift parameter |
| 20 | Signed 32-bit coordinate offset |

The callback IDs here are document-local opaque labels for unresolved indirect dependencies, not established identities of external functions.

Callback point arguments address pairs of signed 32-bit coordinates:

| Dependency | Arguments, in order | Apparent role |
|---|---|---|
| F-000000000001 | Initial point, context | Begin contour |
| F-000000000002 | Endpoint, context | Straight segment |
| F-000000000003 | Control point, endpoint, context | One-control-point curve |
| F-000000000004 | First control, second control, endpoint, context | Two-control-point curve |

Each callback result is tested as a 32-bit integer.

### Preconditions

For safe traversal, callers must provide readable descriptors, accessible arrays, valid contour indices, and callable callback addresses for every operation reached. The function does not validate these conditions.

Contour ranges must support the pointer arithmetic used by the traversal. In particular, a contour beginning with tag 0 causes traversal state to be positioned one coordinate record and one tag before that contour’s first point. For a first contour starting at index 0, the supplied representation does not establish portable language-level validity for forming those preceding pointers, even though the ensuing traversal advances back into the contour before reading its first control.

The arithmetic restrictions and callback-mutation assumptions needed for an unambiguous geometric interpretation are documented under **Uncertainties**.

## Behavior

### Entry and transformation

If either descriptor pointer is null, the function returns 6 without reading descriptor fields or invoking callbacks.

Otherwise, it reads and retains the shift parameter and coordinate offset before testing whether any contour exists. A nonpositive contour count therefore still requires a readable callback descriptor through offset 23.

For every coordinate component that it transforms, the function left-shifts the 32-bit component using the low eight bits of the retained shift parameter, then subtracts the retained offset. The same operation applies independently to x and y.

Implicit midpoint coordinates are computed from already-transformed coordinates. Division by two is signed division, truncating toward zero when the sum is representable. Thus an odd negative sum rounds toward zero, not toward negative infinity.

The supplied text does not establish portable results for overflowing arithmetic or out-of-range shifts.

### Contour selection and initial position

The contour ordinal begins at zero. Before each contour, it is compared with the currently read signed contour count.

For each selected contour, the function:

1. Reads that contour’s signed end index.
2. Obtains the first and last coordinate records using the coordinate-array address.
3. Transforms the first point, then the last point.
4. Examines the first point’s tag.

These coordinate reads occur before rejection of an initial tag 2. For the initial transforms, the component-read order shown is first x, first y, last y, last x.

The initial position and effective traversal range depend on the first tag:

- **Tag 2:** return 20 without a contour-start callback.
- **Tag 1 or 3:** use the transformed first point as the initial position. The effective final point remains the original last point.
- **Tag 0 with final tag 1:** use the transformed last point as the initial position. Exclude that final record from the effective traversal range, because it supplies the contour’s starting position.
- **Tag 0 with any other final tag:** use the componentwise midpoint of the transformed first and last points as the initial position. Keep the original last point in the effective traversal range.

For either tag-0 case, traversal is arranged so that the original first point is processed as the next control point.

The function invokes F-000000000001 with the chosen initial position. A nonzero result ends the entire operation immediately.

### Straight segments and normal closure

After a successful callback, traversal checks whether the current point has reached or passed the effective final point.

If so, it invokes F-000000000002 with the saved initial position to close the contour. It does not suppress that call when the current position already equals the initial position.

Otherwise, it examines the next point’s low tag bits:

- **1:** transform the point and invoke F-000000000002 with it.
- **0:** enter one-control-point-curve processing.
- **2 or 3:** enter two-control-point-curve processing.

After a successful straight-segment callback, traversal resumes from the endpoint just consumed.

A contour containing a single explicit endpoint consequently produces a contour-start callback followed by a straight-segment callback to the same position.

### One-control-point curves

The first tag-0 point becomes the current control point.

If that control is already at the effective contour end, the function invokes F-000000000003 with that control and the saved initial position. Success completes the contour without a separate straight closure callback.

Otherwise, the next coordinate record is transformed before its tag is used to decide among these cases:

- **Tag 1:** invoke F-000000000003 with the current control and that explicit endpoint. Resume ordinary traversal at the endpoint.
- **Tag 0:** compute the componentwise midpoint between the current control and the next control. Invoke F-000000000003 with the current control and that midpoint. After success, make the next control current and continue.
- **Tag 2 or 3:** return 20. The invalid point has already had its coordinates read and transformed, but it is not reported through a callback.

Thus consecutive tag-0 controls introduce implicit endpoints between them. If the chain reaches the effective contour end as a control, its final curve endpoint is the saved initial position.

Any earlier successful callbacks remain observable if a later point causes rejection.

### Two-control-point curves

When the next point has tag 2 or 3, the function requires:

- space within the effective contour range for two control records; and
- low tag bits exactly 2 on the second control.

Failure returns 20 before transforming those controls for this segment.

The first control may therefore have low bits 2 **or 3**. The second must have low bits 2.

After validation, both controls are transformed. The following record, if it remains within the effective range, is used as the endpoint. Its tag is not inspected.

The function invokes F-000000000004 with:

1. the transformed first control;
2. the transformed second control;
3. either the transformed following record or the saved initial position.

If there is no following record within the range, the curve closes directly to the initial position. Successful completion of that callback completes the contour without a separate straight closure callback.

If there is a following record, traversal resumes there. If that record is exactly the effective last point, normal closure subsequently emits F-000000000002 to the initial position.

### Completion and error precedence

On successful contour completion, the next starting index is the original signed contour-end index plus one, not the possibly shortened effective endpoint. The contour ordinal is incremented and the contour-count condition is evaluated again.

The first encountered nonzero callback result or detected tag error terminates traversal. There is no rollback, compensating callback, or processing of later contours.

## Side effects

The function’s own visible writes are to temporary local storage. It contains no direct writes to the outline descriptor, callback descriptor, coordinate array, tag array, or contour-end array.

It passes addresses of temporary coordinate pairs to callbacks. These addresses are not ownership transfers. Consumers must not rely on their contents remaining valid after the callback returns; temporary storage is reused and ceases to exist when the function returns.

No allocation or release operation is visible in this function. That does not establish that callbacks allocate nothing, release nothing, preserve global state, or leave caller-owned memory unchanged.

Callback addresses are obtained from the callback descriptor at their invocation sites. In contrast, the shift and offset are retained from entry. Callback-driven descriptor changes can therefore affect later callback dispatch without changing the retained transformation parameters.

The contour count is read again at contour boundaries. Array addresses are also read during subsequent contour setup. Mutation by callbacks can affect later traversal; no snapshot, lock, or reentrancy protection is visible.

Temporary point arguments are not established as immutable by the supplied signatures. A callback that writes through one can alter saved coordinates used later, especially the saved initial position. The geometric descriptions above assume callbacks do not modify point arguments or traversal inputs.

## Dependencies

- **F-000000000001:** receives the chosen initial position. Its nonzero result stops traversal before segment processing.
- **F-000000000002:** receives explicit straight endpoints and normal closure endpoints. Its nonzero result stops traversal immediately.
- **F-000000000003:** receives a control and endpoint, including implicit midpoint endpoints and direct closure endpoints. Its nonzero result stops traversal immediately.
- **F-000000000004:** receives two controls and an endpoint, possibly the initial position. Its nonzero result stops traversal immediately.

All receive the same supplied context value. The function does not dereference that value.

Callback implementations, calling-convention details beyond the shown arguments, memory ownership behavior, and global-state effects are unresolved.

## Acceptance examples

These are conditional static examples, not runtime observations. Except where specified otherwise, assume valid accessible storage, shift zero, offset zero, representable arithmetic, unchanged inputs, and callbacks that return zero without modifying point arguments.

1. **Null descriptor:** either descriptor pointer is null. Expected result: 6, with no callbacks.

2. **No contours:** contour count is zero or negative, with a readable callback descriptor. Expected result: 0, with no point-array reads and no callbacks. Transformation parameters are still read.

3. **Single endpoint:** one contour contains only point (4, 7), tag 1. Expected calls: F-000000000001 at (4, 7), then F-000000000002 at (4, 7). Expected result: 0.

4. **Ordinary closed chain:** points A, B, C all have tag 1. Expected calls: initial A, straight B, straight C, straight A.

5. **Initial tag 3:** a single-point contour has tag 3. It is treated like an initial endpoint: initial-position callback followed by straight closure. Changing its low tag bits to 2 instead yields 20 with no callbacks, after the initial coordinate reads.

6. **Leading control, explicit final endpoint:** points are (0, 4) with tag 0 and (8, 0) with tag 1. Expected calls: initial (8, 0), then F-000000000003 with control (0, 4) and endpoint (8, 0). No separate straight closure follows.

7. **All-control contour:** points are (0, 0) and (4, 4), both tag 0. The initial point is (2, 2). Expected curves use the first control to endpoint (2, 2), then the second control to endpoint (2, 2). No separate straight closure follows.

8. **Negative midpoint rounding:** initial and final controls are (−1, −1) and (0, 0), both tag 0. Their implicit initial midpoint is (0, 0), because signed division of −1 by 2 truncates toward zero.

9. **Rejected mixed curve:** after an explicit initial endpoint, a tag-0 control is followed by a tag-2 point. The initial callback occurs; the later point’s coordinates are read; then result 20 is returned without a curve callback for that pair.

10. **Cubic endpoint tag is ignored:** a contour contains an explicit initial endpoint, two tag-2 controls, and a final record whose tag is 0. Expected calls include F-000000000004 using that final record as endpoint, followed by straight closure. Its tag 0 does not start a one-control-point curve.

11. **Tag-3 first cubic control:** replace the first control’s tag in the preceding example with 3. The same segment remains accepted. Replacing the second control’s tag with 3 causes result 20 before that segment’s callback.

12. **Callback error:** any invoked callback returns −9. Expected result: −9, with no subsequent callback or contour processing. Earlier effects are retained.

13. **Tag high bits:** changing a tag from 1 to 129 does not change its classification; both have low bits 1.

## Uncertainties

The following are **documented_only**:

- Exact results of signed left shifts involving negative values, excessive counts, or overflowing results. The visible expression masks the shift parameter to eight bits; a further five-bit mask is not established here.
- Exact results when coordinate subtraction or midpoint addition overflows signed 32-bit range.
- Behavior for inaccessible memory, null array addresses, invalid callback addresses, reversed contour ranges, negative end indices, or out-of-bounds indices. No controlled error result is established.
- Portable validity of pointer formation before a contour’s first record and pointer comparisons on malformed ranges.
- Behavior when callbacks modify temporary point arguments, descriptors, arrays, or shared state. Some subsequent reads are visible, but the function provides no coherent mutation protocol.
- Concrete identities and semantics of the four callback implementations.
- Whether external format rules impose stricter tag or contour requirements than this function enforces.
- Concurrency, reentrancy, nonlocal exits, and callback exception behavior.

**Inferred intent:** the four callback shapes and control-point handling indicate outline decomposition into initial-position, straight, quadratic, and cubic operations. Those names do not establish stricter validation than the visible branches perform.
