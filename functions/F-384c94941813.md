# F-384c94941813

## Purpose

F-384c94941813 conditionally replaces a pointer-valued field in a caller-supplied memory region. When the existing pointer differs from the replacement and is non-null, the function invokes an indirect operation associated with the existing pointee before storing the replacement.

The observable distinction is between three cases:

- The existing and replacement pointer values are equal: no indirect invocation and no field write.
- The existing pointer is null and the replacement differs: the replacement is stored without an indirect invocation.
- The existing pointer is non-null and the replacement differs: the indirect operation is invoked first; the replacement is stored only if that operation returns normally.

This resembles replacement of an associated resource with a cleanup hook for the previous resource. That interpretation is **inferred intent**, not an established ownership contract. The available evidence does not identify the indirect operation as a destructor, release operation, reference-count adjustment, or notification.

## Interface

### Inputs

The function has two represented inputs:

1. **Container address.** An address used to locate a pointer-valued field at byte offset **0x4C**, or **76 decimal**.
2. **Replacement pointer.** A pointer value compared with the current field value and, when different, written into that field.

The first input is represented as an integer in the supplied material but is used as a memory address. Its apparent integer type does not establish that arbitrary integers are valid inputs.

The replacement may be null. This function does not dereference the replacement merely because it is supplied or stored.

### Widths and layout

The supplied representation supports the following **32-bit layout interpretation**:

| Location | Represented contents |
|---|---|
| Container address + 0x4C | Current pointer, occupying one 32-bit pointer-sized slot |
| Address held by a non-null current pointer | A 32-bit pointer-sized value used as a dispatch-table address |
| Dispatch-table address + 0x04 | An indirect callable address in a 32-bit pointer-sized slot |

The offsets are byte offsets, not element counts. In particular, the callable address is obtained from four bytes beyond the dispatch-table address, not four entries beyond it.

The underlying executable’s complete ABI and pointer-width declaration are not supplied. These layouts therefore describe the represented 32-bit model; they must not be silently widened to a 64-bit layout.

There is no evidenced length, count, allocation-size, or reference-count arithmetic. The relevant address computations are addition of 76 to the container address and addition of four to the dispatch-table address. Validity across address-space boundaries is not established.

### Output

The function has no specified return value. Its observable result consists of:

- Whether an indirect operation is invoked.
- Whether the selected field is written.
- Any effects of the indirect operation.
- Whether execution returns normally.

### Preconditions

For normal execution:

- The field at the container address plus 0x4C must be readable.
- On a path that stores a replacement, that field must also be writable when the store occurs.
- If a differing, non-null current pointer triggers dispatch, the current pointee’s first pointer-sized slot and the selected dispatch-table slot must be readable.
- The retrieved callable address must be valid for the actual calling convention.
- Any additional preconditions imposed by that indirect operation must hold.

No checks establish these conditions. Null is not accepted specially as a container address: the function still attempts to access the field at the fixed offset.

## Behavior

### Initial observation and equality decision

The function first reads the current pointer from the selected container field. It compares that captured pointer value with the replacement pointer.

The comparison is pointer-value equality in the represented execution model. There is no comparison of pointed-to contents, resource identity beyond pointer equality, or allocation metadata.

If the values are equal, the function returns without invoking the indirect operation and without writing the field. This includes the case where both values are null.

The absence of a write on this path is part of the contract. It is not merely equivalent final field contents: an observer capable of detecting writes must not be promised an idempotent store.

### Replacement when the current pointer is null

If the values differ and the captured current pointer is null, the function stores the replacement into the selected field and returns.

Because equality was already rejected, the replacement is necessarily non-null on this particular path.

No dispatch-table access occurs through the null current pointer. No indirect operation is invoked by this function on that path.

### Replacement when the current pointer is non-null

If the values differ and the captured current pointer is non-null, the function:

1. Reads a dispatch-table address from the beginning of the current pointee.
2. Reads a callable address from byte offset 0x04 in that table.
3. Invokes that callable.
4. After a normal return, stores the original replacement argument into the container field.
5. Returns.

This sequence describes the order of operations visible in the supplied representation. It does not establish processor memory-ordering guarantees.

There is no evidenced check that the dispatch-table address or callable address is non-null. A non-null current pointer alone does not guarantee safe dispatch.

### State across the indirect invocation

The function does not itself store the replacement before invoking the indirect operation. Thus, absent intervening modification, the selected field still contains the previous pointer when dispatch begins.

The indirect operation is not known to preserve that field, the container, other memory, or global state. Consequently, the contract must not require that the field remain unchanged during the invocation.

On normal return, the outer function stores its replacement argument without rereading the field or repeating the equality decision. If the indirect operation has changed the field, that change is overwritten by this final store, provided the container remains valid and writable.

The dispatch is based on the initially captured current pointer. A later change to the container field does not cause this invocation to select a different pointee.

### Completion and failure boundaries

The replacement store occurs only after a normal return from the indirect invocation.

If that invocation does not return, control does not reach the replacement store. If it faults or otherwise transfers control away, the supplied evidence establishes no rollback, recovery, or guaranteed final field value.

An invalid initial field access or invalid dispatch-related access likewise has no specified recovery behavior. No explicit status return, validation failure, or error-reporting mechanism is present.

## Side effects

### Direct memory effects

On an equal-pointer path, the function directly reads the container field but does not write it.

On a differing-pointer path with a null current value, it directly reads and then writes the field.

On a differing-pointer path with a non-null current value, it additionally reads the current pointee’s initial dispatch-table pointer and the table’s callable slot. Its own field write follows the indirect invocation.

These are the accesses established by the function body. They do not include memory accesses performed by the callee.

### Ownership and lifetime

No direct allocation, deallocation, copying of pointed-to data, or reference-count modification is established.

The function does not visibly acquire ownership of the replacement, validate it, or invoke an operation through it. Storing a pointer does not, by itself, establish ownership transfer.

Likewise, invoking an operation through the old pointee does not prove that the old pointee is released. Its post-call validity and ownership remain unknown.

The container must remain usable until the final store on a returning dispatch path. If the indirect operation invalidates the container, the outer function has no evidenced safeguard against the subsequent write.

### Concurrency and reentrancy

No lock, atomic exchange, compare-and-swap, or memory barrier is established. The read, comparison, optional invocation, and write must not be treated as a single atomic replacement.

If reentrant execution or another actor changes the field after the initial read, this function does not detect that change before its final store. Safe concurrent use requires constraints not supplied here.

## Acceptance examples

The following are conditional acceptance criteria derived from static evidence, not reports of executed tests. Each assumes valid memory and a compatible dispatch target where applicable.

### Equal non-null pointers

Given that the field contains a non-null pointer P and the replacement is P:

- The field is read.
- No indirect operation is invoked.
- The function performs no field write.
- The field remains P unless some external actor changes it.

### Both pointers null

Given that the field is null and the replacement is null:

- Equality ends the operation.
- No dispatch-table access occurs.
- No field write occurs.

### Null current pointer and non-null replacement

Given a null field and replacement Q, where Q is non-null:

- No indirect operation is invoked.
- Q is stored in the field.
- This function does not dereference Q.

### Non-null current pointer and null replacement

Given that the field contains P, where P is non-null, and the replacement is null:

- The callable selected through P is invoked.
- The function itself has not yet cleared the field when that invocation begins.
- If the invocation returns normally and the field remains writable, null is stored afterward.

This example does not imply that P is destroyed.

### Different non-null pointers

Given field value P and replacement Q, with P and Q distinct and non-null:

- Dispatch uses P’s associated table, not Q’s.
- Q is stored only after the selected operation returns normally.
- No operation through Q is established.

### Callee modifies the field

Given distinct P and Q, suppose the selected operation changes the field to R and returns normally while leaving the container valid:

- The outer invocation does not reconsider its original comparison.
- Its final store replaces R with Q.

### Callee never returns

Given a differing, non-null current pointer, suppose the selected operation never returns:

- The outer invocation never reaches its replacement store.
- The final field value cannot be determined without knowing the callee’s effects.
