# F-647f70d31437

## Purpose

F-647f70d31437 scans an accepted prefix of a byte sequence and optionally constructs a signed, multiple-precision integer from that prefix.

Acceptance and numeric conversion are distinct:

- An external classification table determines which bytes belong to the prefix.
- Explicit hexadecimal conversion determines the value contributed by each accepted byte.
- An accepted byte outside the hexadecimal digit ranges contributes a zero nibble; it does not cause a conversion error.

An initial minus byte is handled separately, before classification. It contributes to the returned count and sets the object’s sign flag, but is not itself submitted to the classification predicate.

The return value normally reports the number of accepted bytes, including that optional initial minus. Object-allocation or storage-growth failure instead returns zero. Zero therefore does not distinguish failure from a successfully processed prefix containing no accepted bytes.

The interpretation as a signed hexadecimal multiple-precision conversion is inferred from the digit mapping and object updates. The classification table’s actual accepted alphabet is not established.

## Interface

### Arguments and return value

The function accepts:

1. **An optional destination-slot pointer.** When nonnull, it identifies a readable and writable slot containing an integer-object pointer. The slot may initially contain null. A null destination-slot pointer selects scanning without object construction.
2. **An input-byte pointer.** Null is explicitly accepted. Otherwise, it must identify sufficiently readable storage for scanning and, when constructing an object, conversion.

The return is a signed 32-bit integer in the supplied representation. Accepted-byte counts and word indices use signed 32-bit arithmetic. Magnitude accumulation uses unsigned 32-bit arithmetic.

There is no input-length argument, end-pointer result, or separate error indicator.

### Observed object layout

The listing uses four-byte object slots and stores addresses in 32-bit slots.

| Byte offset | Observed meaning |
|---|---|
| 0 | Address of magnitude-word storage |
| 4 | Signed 32-bit significant-word count |
| 8 | Signed 32-bit storage capacity, compared in words |
| 12 | Sign flag, written as zero or one |

Magnitude words are unsigned 32-bit values stored least-significant word first. This describes numerical word order, not a portable byte serialization.

No other object fields are directly accessed by this function. Dependencies may access additional fields.

### Preconditions for defined successful operation

Except for the explicit null-input case:

- The input must remain readable through the first rejected byte.
- The classification dependency must supply a readable descriptor and table covering every encountered unsigned-byte index.
- Scanning must eventually encounter a rejected byte.
- A supplied destination slot must be readable and writable.
- A selected object must support the observed field accesses and dependency calls.
- Successful capacity handling must leave the selected object with enough writable magnitude storage.
- Counts, intermediate arithmetic, and address calculations must remain representable.

Input stability is additionally required for a single consistent interpretation of scanning and conversion. The function does not enforce that stability.

## Behavior

### Initial input handling

A null input pointer returns zero immediately. The destination slot is not read or written, and no dependency is called.

For nonnull input, the function reads the original first byte. If it is zero, the function returns zero with the same absence of destination access and dependency calls.

For every other initial byte:

- If it is `0x2D`, the function records sign one and advances the input position by one byte.
- Otherwise, it records sign zero and leaves the input position unchanged.

The initial minus is consumed unconditionally. Its classification-table entry is irrelevant to this decision.

There is no separate recognition of a plus sign, whitespace, or a hexadecimal-prefix marker. Any such byte reached by scanning is governed by the classification predicate.

### Prefix scanning

F-2a4c402ba617 is called once after initial-byte handling, including in scan-only mode. Its result is treated as a descriptor whose first 32-bit slot supplies the classification-table address. There is no explicit null-result check.

Each candidate input byte is used as an unsigned index from 0 through 255. For stable memory, let the classification byte be \(c\). The candidate is accepted exactly when:

\[
\bigl(c \mathbin{\mathrm{xor}} (c \ll 2)\bigr) \mathbin{\mathrm{and}} 0x80 \ne 0.
\]

Thus classification bits 7 and 5 must differ. Setting both bits does not satisfy the predicate.

The predicate contains two input-byte reads and two classification-entry reads. The supplied expression does not establish an ordering between its two operands. Treating the result as a predicate over one classification byte assumes stable input, descriptor, and table contents.

Scanning proceeds from left to right until rejection. The rejected byte is read but not counted.

There is no explicit zero-byte check inside this scan. A zero byte encountered after initial handling terminates scanning only if its classification rejects it. In particular, after an initial minus, the following zero byte reaches the classification mechanism.

Let:

- \(n\) be the number of accepted bytes after optional-minus handling;
- \(s\) be one if an initial minus was consumed, otherwise zero.

The nominal return count is \(n+s\), calculated before object construction.

### Scan-only mode

If the destination-slot pointer is null, the function returns the nominal count after scanning.

It does not call the object-creation, existing-object, growth, or cleanup dependencies. It does not perform numeric conversion or write object fields.

This does not establish that the classification dependency itself is allocation-free or free of other side effects.

### Object selection

With a nonnull destination-slot pointer, the function reads the slot after scanning.

If the slot contains null, it calls F-7d962cda8fd4. A null result causes an immediate zero return. A nonnull result becomes the selected object.

If the slot contains a nonnull object pointer, it calls F-d4e7c5a40239 with that object and zero. The result is ignored. Subsequent operations continue using the originally selected object pointer.

Calling the latter dependency a “reset” is inferred intent only. This caller does not establish which fields it changes, whether it allocates, or whether it preserves storage or globals.

### Capacity comparison and growth

For nonnegative \(n\) without arithmetic overflow, the signed capacity field is compared against:

\[
\left\lceil \frac{n}{8} \right\rceil.
\]

If capacity is smaller, F-08bc2fc94856 is called with the selected object and:

\[
\left\lfloor \frac{n}{8} \right\rfloor + 1
\]

as the requested word count.

The comparison threshold and growth request are deliberately distinct descriptions of the observed operations. For eight accepted bytes, the comparison threshold is one word, but a necessary growth call requests two words. For nine accepted bytes, both values are two words.

For zero accepted bytes, the comparison threshold is zero. A negative signed capacity therefore triggers a growth request of one word, even though conversion will generate no words.

The growth result is used only as a null/non-null status. Its address is not adopted. All later object access and final publication use the originally selected object pointer. Compatible successful growth must therefore leave that original object usable with sufficient storage.

On a null growth result, the function rereads the destination slot:

- If the slot is currently nonnull, it returns zero without calling cleanup.
- If the slot is currently null, it calls F-2642535311f0 on the selected object and then returns zero.

Cleanup selection depends on the slot’s value at that moment, not on a retained allocation-origin flag. Unknown dependency effects must not be assumed to preserve the slot.

### Arithmetic limits

The ordinary capacity formulas apply only in the non-overflowing range. The comparison calculation forms four times \(n\), adds 31, and uses a sign-adjusted right shift corresponding to truncating signed division by 32. The growth request similarly derives from four times \(n\), followed by a division-like operation and addition of one.

For signed 32-bit arithmetic, \(0 \le n \le 536{,}870{,}904\) keeps both the multiplication and comparison’s addition within the nonnegative signed range. This bound does not independently establish that input, storage, or address calculations are valid.

There is no explicit overflow-detection path. The positive-count formulas must not be extrapolated to overflowing intermediates as though arbitrary-precision arithmetic were used.

### Magnitude conversion

Conversion begins only after successful object selection and capacity handling. It rereads the accepted bytes; it does not retain a copy from scanning.

The accepted region is divided into groups of at most eight bytes, starting at the rightmost end:

1. The rightmost group is converted and stored at magnitude-word index zero.
2. Each next group lies immediately to its left and is stored at the next higher word index.
3. Within each group, bytes are read from left to right.

Each byte contributes one nibble:

| Byte range | Contribution |
|---|---|
| `0` through `9` | 0 through 9 |
| `a` through `f` | 10 through 15 |
| `A` through `F` | 10 through 15 |
| Any other byte | 0 |

A group’s value is formed by repeatedly shifting the unsigned 32-bit accumulator left four bits and incorporating the next nibble. At most eight nibbles contribute to a word.

A classification-accepted nonhexadecimal byte therefore occupies a digit position with value zero. It is neither skipped nor reported as invalid.

Because scanning and conversion are separate passes, input changes between them can change the resulting magnitude without changing the already computed count. Dependency calls occur between these passes and are not established to preserve the input.

### Normalization and publication

After conversion, the function writes the generated word count to the significant-word-count field.

If any words were generated, it examines them from the highest generated index downward. For each zero high word, it decrements the significant-word count. It stops at the first nonzero word or when the significant count reaches zero.

Consequences:

- Leading zero digits do not remain as significant high words.
- An all-zero magnitude has zero significant words.
- Generated zero words remain written even when excluded by normalization.
- Storage beyond the generated words is not directly cleared here.

The sign flag is then written independently of the normalized magnitude. An initial minus produces sign one even for zero magnitude.

Finally, the selected object pointer is written to the destination slot, and the nominal count is returned.

No rollback is performed on failure. In particular, an existing object may already have been changed by F-d4e7c5a40239 before a growth failure.

## Side effects

The established direct-access and call order is:

1. Read the original first input byte, unless the input pointer is null.
2. Return early for a zero original first byte; otherwise determine optional-minus handling.
3. Call the classification dependency.
4. Read candidate input bytes and classification entries until rejection.
5. Compute the nominal return count.
6. If constructing an object, read the destination slot.
7. Call either the object-creation dependency or the existing-object dependency.
8. Read the selected object’s capacity and conditionally call growth.
9. On growth failure, reread the destination slot and conditionally call cleanup.
10. On success, reread accepted input bytes and write magnitude words from low word index upward.
11. Store the generated word count, then read high words and reduce that count as needed.
12. Write the sign flag.
13. Publish the selected object pointer through the destination slot.

Dependency effects are additional to this sequence and remain unknown.

The function contains no explicit writes to input bytes or named global state. This does not establish that dependencies preserve either. Likewise, aliasing between input, destination, object fields, and magnitude storage is not validated.

Successful publication makes the selected object reachable through the destination slot. The actual ownership, allocation, and release contracts of the dependencies are not established. This caller alone does not prove leak freedom or that the cleanup call frees memory.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless an example specifies otherwise, assume stable input and classification data, hexadecimal digits accepted, the shown terminator rejected, representable arithmetic, valid objects, and successful compatible dependencies.

1. **Null input with an existing destination.**  
   Returns zero without reading the destination slot or calling any dependency.

2. **Original first byte is zero.**  
   Returns zero without classification or object access, regardless of how the table would classify zero.

3. **Scan-only input `-1a!`.**  
   Returns three. The minus counts without classification; `1` and `a` are accepted; `!` is read but excluded.

4. **Conversion of `123456789!`.**  
   Returns nine. Magnitude words are `0x23456789` at index zero and `0x00000001` at index one. Significant-word count is two; sign is zero.

5. **Conversion of `-00000000!`.**  
   Returns nine. A zero word is written, significant-word count normalizes to zero, and sign is one.

6. **Rejected ordinary initial byte.**  
   Suppose the original first byte is nonzero, is not `0x2D`, and is rejected by the classification predicate. The nominal return is zero. With a destination and successful compatible dependencies, construction still occurs, producing zero significant words and sign zero. This case is not the initial-empty early return.

7. **Initial minus followed by zero.**  
   For bytes `[0x2D, 0x00]`, with zero rejected, returns one. With a destination, successful construction stores zero significant words and sign one. This remains true even if the classification table also rejects `0x2D`, because the original minus is never classified.

8. **Accepted nonhexadecimal byte.**  
   If `G` is accepted in `1G!`, returns two and constructs magnitude `0x10`. The accepted `G` contributes a zero nibble.

9. **Eight accepted digits and capacity zero.**  
   The comparison threshold is one word, so growth is called. Its request is two words. Compatible success is followed by one generated magnitude word.

10. **Allocation failure after scanning.**  
    If the destination slot contains null and F-7d962cda8fd4 returns null, returns zero rather than the nominal count.

11. **Growth failure with a currently nonnull slot.**  
    Returns zero without F-2642535311f0. An earlier existing-object call may already have modified the object.

12. **Growth failure with a currently null slot.**  
    Calls F-2642535311f0 on the selected object and returns zero. Actual memory release is not established.
