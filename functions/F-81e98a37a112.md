# F-81e98a37a112

## Purpose

F-81e98a37a112 performs a conditionally enabled indirect operation on an object. An optional callback can reject the operation before dispatch and replace its externally returned result after dispatch. A positive target result also contributes to a mutable field in the object.

The contract distinguishes three independent decisions:

- Whether an initial dispatch configuration is present.
- Whether an installed callback permits continuation and the object subsequently permits dispatch.
- Whether the target result requires an accounting update.

Initial configuration failure and disabled dispatch produce different fixed diagnostic requests, but both lead to a return value of −2 if the diagnostic dependency returns normally. A callback can terminate processing with any nonpositive result. Following dispatch, the returned value comes from either the target or the concluding callback.

“Enable,” “accounting,” “diagnostic,” and callback-phase names describe observed roles. Their application-level meanings are inferred, not established.

## Interface

### Arguments and result

The interface has four arguments:

| Position | Contract role |
|---|---|
| First | Nullable address of a mutable dispatch object. |
| Second | Opaque 32-bit input, forwarded unchanged to the target and any callback invocations. |
| Third | Opaque 32-bit input, forwarded unchanged and additionally used in the target argument layout when no callback is installed. |
| Fourth | Opaque 32-bit input, forwarded to the target only when no callback is installed. |

The result is a signed 32-bit integer. Zero and negative values are distinguished from positive values in callback continuation and accounting decisions.

The opaque inputs have no established signedness or application interpretation. Their forwarding preserves their 32-bit values; it does not establish that they are numbers, addresses, lengths, or handles.

### Object layout

The supplied representation supports four-byte integer and address-bearing fields:

| Object-relative byte offset | Width | Established role |
|---|---:|---|
| +0 | 32 bits | Address of a dispatch record. |
| +4 | 32 bits | Optional callback address; zero denotes absence. |
| +12 | 32 bits | Dispatch-enable field; zero disables dispatch. |
| +48 | 32 bits | Accounting field, conditionally updated after dispatch. |

Within the dispatch record, the four-byte field at byte offset +12 contains a target address.

The object’s +12 field and the record’s +12 field are distinct storage locations with different roles. No meanings are established for intervening storage. Access to the accounting field requires storage through byte offset +51, but this does not establish the object’s complete size.

These offsets describe the supplied representation, not a portable layout for another pointer width or ABI.

### Memory and execution preconditions

A null first argument is explicitly supported as an error case. For a nonnull object, ordinary execution requires every field reached on the selected path to be readable. Accounting additionally requires writable storage when the target returns positively.

Nonzero addresses are not validated for allocation bounds, alignment, executability, or continued lifetime. A checked address being nonzero does not establish that dereferencing or calling it is safe.

## Behavior

### Initial rejection

An initially eligible configuration consists of a nonnull object, a nonzero dispatch-record address in its +0 field, and a nonzero target address in that record’s +12 field.

The initial accesses are guarded: a null object is not dereferenced, and a zero record address is not dereferenced to obtain a target.

| Argument position | Value |
|---|---:|

| Second | 111 |
| Third | 121 |
| Fourth | 0 |

Normal return from that dependency is followed by return −2. The dependency’s return value does not determine this result.

On this route, F-81e98a37a112 does not directly consult the callback, enable, or accounting fields. It performs no direct write to the object. These restrictions do not constrain effects caused by the diagnostic dependency.

Initial eligibility is a presence check, not a retained dispatch selection. The record and target used later can differ from those observed during this check.

### Callback participation and continuation

Following initial eligibility, the callback address is obtained from the object’s +4 field. That selected address is retained for this invocation.

A zero address means no preliminary or concluding callback is performed. A nonzero address selects the preliminary callback interface:

| Argument position | Value |
|---|---|
| First | Object address |
| Second | 2 |
| Third | Original second input |
| Fourth | Original third input |
| Fifth | 0 |
| Sixth | 1 |

The signed callback result determines whether processing continues:

| Preliminary result | Required outcome |
|---|---|
| Zero or negative | Return that result unchanged. No subsequent enable check, target dispatch, accounting update, concluding callback, or diagnostic request occurs in this function. |
| Positive | Continue to the enable decision. The magnitude of the positive result has no further established use. |

In particular, a preliminary result of zero rejects continuation. A result greater than one does not become a target argument.

Selection of the callback is stable within the invocation: changing the object’s callback field later does not redirect the concluding call. Continued validity of the retained address is nevertheless a precondition for that call.

### Enablement and disabled outcome

The enable field is consulted only after initial eligibility and, if applicable, successful preliminary callback completion.

Zero selects a diagnostic request to F-4fc89ec41a6d with arguments 32, 111, 120, 0, 0. If that dependency returns normally, the function returns −2.

Any nonzero enable value permits dispatch, including a value whose signed interpretation is negative. The enable condition is not restricted to one.

A successful preliminary callback followed by disabled dispatch does not receive a concluding callback. Callback participation therefore does not guarantee paired invocations.

Because the enable read follows the preliminary callback, that callback’s modifications to the field affect the decision.

### Target interface

Enabled dispatch resolves the record and target again through the object. The earlier presence check does not protect these later accesses: there is no second explicit null or zero rejection before the indirect call.

The target receives six arguments:

| Position | Callback absent | Preliminary callback returned positively |
|---|---|---|
| First | Object address | Object address |
| Second | Original second input | Original second input |
| Third | Original third input | Original third input |
| Fourth | Target-address value obtained through the record | Target-address value obtained through the record |
| Fifth | Original third input | 0 |
| Sixth | Original fourth input | 1 |

Thus, without a callback, the third input occupies both the third and fifth target positions. With a callback, the target’s final two arguments are fixed at zero and one; the original fourth input is not forwarded.

The fourth target argument is address-shaped data. Its purpose is unknown. Target selection and construction of this argument involve repeated reads through the dispatch configuration. Their relative expression-level evaluation order is not established. If the configuration changes between those reads, the evidence does not guarantee that the fourth argument equals the address actually called.

A preliminary callback may replace the dispatch record or target used by the later call. It may also invalidate them; no recovery for that condition is established.

### Accounting and returned result

The target produces a signed 32-bit result.

A positive result causes the accounting field to be read after target completion, increased by that result, and written back. A zero or negative result causes no direct accounting read or write by this function.

For a mathematically representable signed 32-bit sum, the update is ordinary addition. The existing field need not be nonnegative. No overflow check, saturation behavior, wider accumulation, or overflow-specific error route is visible. Behavior outside the signed 32-bit range remains unresolved.

The accounting value used is the value present when read after the target returns. A target-side modification therefore participates in the addition.

Without a retained callback, the function returns the target result unchanged.

With a retained callback, the concluding invocation uses:

| Argument position | Value |
|---|---|
| First | Object address |
| Second | 130 |
| Third | Original second input |
| Fourth | Original third input |
| Fifth | 0 |
| Sixth | Target result |

This invocation occurs after any accounting update. Its signed 32-bit result becomes the function result without another sign-based decision.

Accounting depends on the target result, not the concluding result. A positive target result followed by a negative concluding result still triggers the accounting update. There is no direct rollback. Conversely, a positive concluding result does not cause accounting when the target result was nonpositive.

## Side effects

The sole established direct persistent write is the conditional update at object offset +48. The function does not directly replace the callback, dispatch record, target, or enable field.

Observable access and call ordering includes these constraints:

- Initial configuration checks precede callback selection.
- Preliminary callback completion precedes the enable read.
- The enable decision precedes target dispatch.
- Target completion precedes any accounting access.
- Accounting completion precedes the concluding callback.
- Each explicit rejection request precedes return −2, provided its dependency returns normally.

These are path-dependent constraints, not synchronization guarantees.

The function contains no explicit allocation, release, ownership transfer, locking, or rollback mechanism. This does not establish that its dependencies lack such effects. No dependency may be assumed to preserve globals, the object, its record, or reachable memory.

In particular, preliminary callback effects can influence dispatch; target effects can influence accounting; concluding callback effects can alter state after accounting. Diagnostic effects remain possible even though its result is ignored.

If an invoked dependency does not return normally, the subsequent return values and effects described for normal completion are not guaranteed.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless stated otherwise, each case assumes readable and writable storage as required, valid callable addresses, normally returning dependencies, and no unmentioned mutations.

1. **Null object.** F-4fc89ec41a6d receives 32, 111, 121, 0, 0. The function returns −2 without dereferencing the object.

2. **Absent record or target.** A zero record field, or a readable record containing a zero target field, selects the same initial diagnostic request. An installed callback is not consulted.

3. **Preliminary rejection.** A preliminary callback returning −7 causes immediate return −7. The enable field is not subsequently read. Returning zero likewise terminates immediately with zero.

4. **Callback disables dispatch.** An initially eligible object has a preliminary callback that returns positively but leaves enable zero. The request is 32, 111, 120, 0, 0, followed by return −2. No concluding callback occurs.

5. **Nonzero enable.** With no callback and enable represented as −1, dispatch remains permitted. The field is tested for zero, not positivity.

6. **Dispatch without callback.** With third input 9 and fourth input 12, the target receives 9 in its third and fifth positions and 12 in its sixth. A target result of 4 and post-target accounting value of 20 produce accounting 24 and return 4.

7. **Dispatch with callback.** A preliminary result of 8 permits continuation but does not change the target’s fixed final arguments, zero and one. If the target returns 4 and accounting is 20 when read, accounting becomes 24 before the concluding callback. A concluding result of −9 becomes the function result.

8. **Nonpositive target result.** A target result of −3 causes no direct accounting access. With a retained callback, the concluding callback receives −3 in its sixth position. Its result is returned, even if positive.

9. **Target changes accounting.** If the target sets accounting to 100 and returns 3, the function’s subsequent update produces 103. The pre-dispatch accounting value does not determine that addition.

10. **Negative accounting value.** Accounting −5 and target result 2 produce −3. Positive target results trigger addition even when the resulting accounting value remains negative.

11. **Dispatch replacement.** If the preliminary callback installs another valid record and leaves dispatch enabled, the later call resolves through that replacement rather than using a retained initial target.

12. **Callback replacement.** If the preliminary callback replaces the callback field, the concluding invocation still uses the previously retained address, provided that address remains callable.

13. **Overflow boundary.** Accounting at the maximum signed 32-bit value and target result 1 reaches arithmetic without a visible overflow guard. No wrapped, saturated, or diagnostic outcome is specified by this contract.
