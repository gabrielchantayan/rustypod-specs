# F-197b84b9ae41

## Purpose

F-197b84b9ae41 copies source bytes into a supplied destination and, for selected modes, expands those bytes into additional 16-byte blocks.

The signed selector determines the behavior:

- **0 or 2:** copy a 16-byte seed, then generate blocks using substitution, XOR chaining, and an evolving byte-valued constant.
- **3:** copy a 32-byte seed, then generate blocks using alternating transformations, XOR chaining, and an evolving byte-valued constant.
- **Every other value:** copy blocks without transformation.

The third argument is an **inclusive final destination-block index**, not a byte count or an unconditional number of generated blocks. The expansion modes copy their complete seeds even when this index is negative.

The transformations suggest cryptographic key expansion. That is inferred intent only. The evidence does not establish a named algorithm, particular table contents, permitted key sizes, or a required number of rounds.

## Interface

The function accepts four arguments and returns no value.

| Position | Meaning | Represented width |
|---|---|---|
| First | Source byte address | 32-bit integer-valued address |
| Second | Selector | Signed 32-bit integer |
| Third | Inclusive final block index | Signed 32-bit integer |
| Fourth | Destination byte address | 32-bit integer-valued address |

There is no explicit success result or error result.

A **block** comprises 16 consecutive bytes. Destination block zero begins at the supplied destination address. Each block contains four consecutive four-byte groups. Indices and offsets are zero-based.

Memory loads and stores carrying seed data, generated data, and table entries are eight bits wide. Table indices derived from loaded bytes are unsigned values from 0 through 255. The evolving constant is held in a 32-bit unsigned temporary, but its value is initially 1 and subsequently comes from zero-extending an eight-bit table entry. Constant injection uses its low eight bits.

### Global table-address inputs

Before selector dispatch, the function performs two ordered source-level evaluations of the same global value:

1. The **first evaluation** supplies the saved **constant-transition table base**.
2. The **second evaluation**, reduced by 512 bytes, supplies the saved **substitution table base**.

These are distinct evaluations with distinct roles. If the first observes address value \(G_1\) and the second observes address value \(G_2\), the saved bases are:

\[
C = G_1,\qquad A = G_2 - 512.
\]

Only when both evaluations observe the same value are the saved substitution and transition bases necessarily 512 bytes apart. The evidence does not establish that the two evaluations form an atomic snapshot.

Both evaluations precede seed copying and occur even on the copy-only path. Subsequent table-entry accesses use the saved bases; the function does not explicitly reevaluate the global while generating blocks.

This source-level ordering does not establish the exact number or form of machine-level global loads.

### Preconditions and storage extents

For execution within the ordinary finite-address interpretation:

- Every source byte must be readable when its read occurs.
- Every destination byte must be writable when its store occurs.
- Each table entry actually accessed must be readable.
- Table-base subtraction, address calculations, and loop progression must remain within the supported execution model.
- Deterministic results require sufficiently stable relevant memory, including any global values and table entries being observed.

The function performs no validation of these conditions.

With disjoint storage, a nonnegative final index \(N\), and representable addressing:

| Selector | Source extent read | Destination extent written |
|---|---:|---:|
| 0 or 2 | 16 bytes | \(16(N+1)\) bytes |
| 3 | 32 bytes | \(16\max(2,N+1)\) bytes |
| Other | \(16(N+1)\) bytes | \(16(N+1)\) bytes |

For negative \(N\), selectors 0 and 2 still copy 16 bytes, selector 3 still copies 32 bytes, and other selectors perform no source-to-destination byte transfers.

These are mathematical extents, not assurances that their sizes or final addresses fit within 32 bits.

No ownership policy is established for the supplied storage.

## Behavior

### Memory interpretation and ordering

Let \(B_j[k]\) denote byte offset \(k\) within destination block \(j\), with \(0 \leq k < 16\).

Let:

- \(S[x]\) denote the byte at saved substitution base \(A\), offset \(x\).
- \(T[x]\) denote the byte at saved constant-transition base \(C\), offset \(x\).

These symbols identify memory locations, not snapshots. A later read can observe an earlier destination write if the corresponding storage overlaps.

The ordering described below is established at the source-operation level. For an assignment that combines independent reads, their relative evaluation order is not established. In particular, the contract does not require that the substitution-table read precede the historical-block XOR-operand read, or vice versa. The value used to index a table must, however, be obtained before that indexed table entry can be selected.

All source bytes used for seeding or copying are read as execution reaches them. Neither source nor tables are copied into an independent snapshot.

### Selectors 0 and 2

Both selectors select the same behavior.

#### Seed

Source offsets 0 through 15 are copied to the corresponding destination offsets in ascending order. Each source-byte read and corresponding destination-byte store complete before the next byte transfer.

This seed copy is unconditional with respect to the final index. It occurs before any expansion-block comparison can prevent generation.

The evolving constant starts at 1 without an initial transition-table lookup.

#### First four bytes of each generated block

Blocks \(j=1\) through \(j=N\) are generated in increasing order. If \(N<1\), none are generated.

For each block, offsets 0, 1, 2, and 3 are written in ascending order, initially according to:

\[
B_j[k]
=
S\!\left[B_{j-1}\!\left[12+((k+1)\bmod 4)\right]\right]
\mathbin{\mathrm{XOR}}
B_{j-1}[k],
\qquad 0\leq k<4.
\]

The substitution inputs therefore come from the preceding block’s offsets **13, 14, 15, and 12**, respectively.

After all four initial stores, the function reads the newly written byte at offset zero, XORs it with the current constant, and stores it back. This is a separate read-modify-write, not merely a formula for a single combined store.

#### Remaining bytes and constant transition

The remaining bytes satisfy:

\[
B_j[4g+k]
=
B_j[4(g-1)+k]
\mathbin{\mathrm{XOR}}
B_{j-1}[4g+k],
\quad
1\leq g\leq3,\quad 0\leq k<4.
\]

The store order traverses groups for each byte position:

**4, 8, 12, 5, 9, 13, 6, 10, 14, 7, 11, 15.**

Consequently, each newly written group byte is available to the following group’s computation for that byte position.

After all twelve stores, the function reads \(T[r]\), where \(r\) is the current constant, and replaces the constant with the zero-extended result.

This transition read occurs after **every** generated block, including the last requested block. It is not eliminated because the new constant will go unused.

### Selector 3

#### Seed

The function copies 32 source bytes into destination blocks zero and one, interleaving the two halves.

For each offset from 0 through 15, it completes the transfer for that offset in the first half, then completes the transfer for the corresponding offset in the second half.

The destination store order is:

**0, 16, 1, 17, 2, 18, …, 15, 31.**

The source-byte reads follow the corresponding transfer order. In particular, the second-half read for an offset occurs after the first-half store for that offset. Overlapping storage can therefore behave differently from an ascending 32-byte copy.

The complete seed copy occurs regardless of the final index. The evolving constant starts at 1.

#### Even-numbered generated blocks

Blocks \(j=2\) through \(j=N\) are generated in increasing order. If \(N<2\), only the seed is copied.

For even \(j\), the first four bytes are initially:

\[
B_j[k]
=
S\!\left[B_{j-1}\!\left[12+((k+1)\bmod4)\right]\right]
\mathbin{\mathrm{XOR}}
B_{j-2}[k],
\qquad 0\leq k<4.
\]

These stores occur in increasing offset order. Substitution uses the immediately preceding block, but the other XOR operand comes from **two blocks earlier**.

The function then separately reads, modifies, and rewrites byte zero using the current constant.

Immediately after that read-modify-write, it reads \(T[r]\) and replaces the constant. This transition occurs **before** generating offsets 4 through 15. It also occurs when this even block is the last requested block.

#### Odd-numbered generated blocks

For odd \(j\), the first four bytes are:

\[
B_j[k]
=
S[B_{j-1}[12+k]]
\mathbin{\mathrm{XOR}}
B_{j-2}[k],
\qquad 0\leq k<4.
\]

The substitution inputs use offsets **12, 13, 14, and 15**, without rotation. The four stores occur in increasing offset order.

Odd generated blocks neither inject the constant nor perform a transition-table lookup.

#### Remaining bytes for either parity

For both even and odd generated blocks:

\[
B_j[4g+k]
=
B_j[4(g-1)+k]
\mathbin{\mathrm{XOR}}
B_{j-2}[4g+k],
\quad
1\leq g\leq3,\quad 0\leq k<4.
\]

The store order is:

**4, 8, 12, 5, 9, 13, 6, 10, 14, 7, 11, 15.**

### Every other selector

All selector values other than 0, 2, and 3 select block copying. There is no unsupported-selector error.

For nonnegative \(N\), source blocks zero through \(N\), inclusive, are copied to the corresponding destination blocks. Blocks are processed in increasing order, with each block’s bytes transferred in increasing offset order.

With nonoverflowing addressing, this is a forward byte copy of \(16(N+1)\) bytes. It does not guarantee snapshot-copy behavior under overlap.

For negative \(N\), the copy loop performs no source or destination byte accesses.

No substitution or constant-transition **entry** is read on this path. The two initial global evaluations and associated table-base setup still precede dispatch.

### Integer boundaries

The final-index comparisons are signed 32-bit comparisons.

Selectors 0 and 2 and the copy-only path use signed block counters. Selector 3 uses an unsigned 32-bit block counter, interpreted as signed for its comparison with the final index. Its block-offset multiplication is consequently represented using unsigned arithmetic, unlike the signed-counter paths.

A final index of \(2^{31}-1\) is not a supported ordinary finite-buffer case:

- Signed-counter paths would need to increment past the largest signed value to finish.
- In selector 3, every signed interpretation of the unsigned counter is at most that final index, so the comparison supplies no normal upper-bound exit.

Address calculations can exceed representable or accessible ranges at much smaller indices. No general portable wrapping-address contract follows from the supplied representation.

## Side effects

Direct visible side effects are byte stores into destination-addressed memory. Expansion also reads previously written destination bytes.

There is no visible allocation, release, explicit ownership-transfer operation, callback, or retention of either supplied address after return. Those observations do **not** establish who owns the storage or what caller-level ownership obligations apply.

There is no explicit global write. Destination aliasing can nevertheless modify source storage, table storage, or the global location indirectly. Such aliasing is not checked or prevented.

Because the table bases are saved before seed copying, a later destination write that changes the global location does not explicitly refresh either base. Writes overlapping table entries can still change values obtained by later table reads.

For valid finite executions:

- Selectors 0 and 2 with \(N<1\) write only the 16-byte seed region.
- Selector 3 with \(N<2\) writes only the 32-byte seed region.
- Other selectors with negative \(N\) write nothing.
- Each constant-injecting block writes its byte zero twice.

The function has no bounds checks, address validation, rollback, output clearing, or error-reporting mechanism. An invalid access may occur after earlier stores have modified memory. Fault delivery and recovery are not defined by this evidence.

## Acceptance examples

These are conditional static deductions, not observed runtime results. Unless an example states otherwise, assume stable tables, disjoint storage, valid addresses, ordinary byte memory, and representable arithmetic.

1. **Two global evaluations with distinct values.** If the first global evaluation observes \(P\) and the second observes \(Q\), transition lookups use base \(P\), while substitution lookups use base \(Q-512\). The bases need not be 512 bytes apart. This condition describes the source-level mapping; it does not assert that a particular machine execution exposes two independently changing loads.

2. **Stable global.** If both initial evaluations observe \(P\), the transition base is \(P\) and the substitution base is \(P-512\). Later explicit table accesses use those saved bases.

3. **Equivalent selectors.** Selectors 0 and 2, with identical initial memory and arguments otherwise, have identical byte-transfer and expansion behavior.

4. **One-block seed only.** Selector 0 with final index −1 or 0 copies exactly the first 16 source bytes. It performs no table-entry lookup and leaves destination offsets beyond 15 untouched. The initial global evaluations still occur.

5. **Two-block seed only.** Selector 3 with final index 1 copies 32 bytes in order **0, 16, 1, 17, …, 15, 31**. It generates no further block and performs no table-entry lookup.

6. **Negative copy-only bound.** Selector 1 with final index −1 performs no source or destination byte transfer. It still performs initial table-address setup.

7. **Inclusive copy bound.** Selector 4 with final index 1 copies 32 bytes: blocks zero and one.

8. **First one-seed expansion block.** If the 16-byte seed is zero and \(S[0]=a\), selector 2 with final index 1 produces every four-byte group of block one as:
   \[
   (a\mathbin{\mathrm{XOR}}1,\ a,\ a,\ a).
   \]
   After all generated-byte stores, it reads \(T[1]\), even though no further block is requested.

9. **First two-seed expansion block.** If all 32 seed bytes are zero and \(S[0]=a\), selector 3 with final index 2 produces that same pattern in every group of block two. Its \(T[1]\) read occurs after the byte-zero read-modify-write but before stores to offsets 4 through 15.

10. **Zero constant.** If \(T[1]=0\), the next constant-injecting block uses zero. Its byte-zero read-modify-write still occurs even though XOR with zero leaves the numeric value unchanged. In selector 3, an intervening odd block neither injects nor advances that constant.

11. **Destructive forward overlap.** On the copy-only path, let destination be source plus one byte and final index be zero. Each store overwrites the next source position before its read. All 16 destination bytes become the original first source byte; snapshot-copy behavior would not satisfy this case.
