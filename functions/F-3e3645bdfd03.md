# F-3e3645bdfd03

## Purpose

F-3e3645bdfd03 processes a counted input fragment in one of two ways:

- Recognize a zero-tagged initialization header, validate its format and dimensions, allocate a destination region, and install destination metadata.
- Treat the fragment as continuation data for a destination whose current position is below its recorded end.

When data remains after the selected header, the function delegates its processing to F-f1ce972db28c and returns that dependency’s result.

This is an independent contract derived from static evidence. The apparent roles of dimensions, row stride, and destination storage are inferred from their use; their domain-specific meaning is not independently established.

## Interface

### Arguments and result

The function receives two 32-bit address-like arguments:

1. **State address:** identifies a writable state structure.
2. **Fragment descriptor address:** identifies a structure containing a data address and a byte count.

It returns a 32-bit result:

- **4** for locally detected rejection or allocation failure.
- **0** after successful initialization from an exactly 11-byte fragment, without invoking the data-processing dependency.
- The result of F-f1ce972db28c whenever processing is delegated.

No distinct local error codes distinguish malformed initialization, unsupported format, invalid dimensions, mismatched stride, unavailable destination space, or allocation failure.

### Preconditions

The caller must provide valid addresses for all accesses reached on the selected path. In particular:

- The descriptor fields must be readable even when the count is below three.
- A fragment reaching discriminator decoding must satisfy that dependency’s access requirements.
- Initialization requires writable state fields, a valid global context, and a callable indirect query operation.
- The indirect query must produce usable 32-bit dimension limits.

No local pointer validation, exception recovery, or memory-access fault handling is visible.

## Behavior

### Initial reads and branch selection

The function first reads the unsigned 16-bit count, then the 32-bit fragment address.

If the count is less than three, it returns 4. It does not decode fragment bytes or explicitly read or write the state fields on this path.

For every count of at least three, it invokes F-64e2dfdd4a5d at the fragment start. This occurs even for fragments too short to qualify as initialization headers.

Initialization is selected only when both conditions hold:

- The low 32-bit discriminator result is zero.
- The count is greater than ten.

Every other case follows the continuation path. Consequently, a zero discriminator with a count from three through ten is not automatically rejected as a short initialization header.

### Initialization parsing and format selection

Initialization performs these operations in order:

1. Read the format byte at offset +2.
2. Decode the first dimension through F-64e2dfdd4a5d at offset +3.
3. Decode the second dimension through F-64e2dfdd4a5d at offset +5.
4. Decode the declared stride through F-c25a2fcc75b5 at offset +7.
5. Determine the effective format factor.
6. Invoke an indirect global-context query to obtain two dimension limits.

The effective format factor is:

- **2** for format code 1.
- **16** for format code 2 or 3, but only if a byte at global-context offset +1 is nonzero.
- **0** otherwise.

The global flag is read only for format code 2 or 3. Format code 1 does not require that flag.

The query is reached even when the effective factor is zero or either decoded dimension is zero. Thus, invalid initialization headers can still cause observable dependency calls before returning 4.

### Initialization validation

After the query, the function rejects the header unless all of these conditions hold:

- The effective format factor is nonzero.
- Both decoded dimensions are nonzero.
- The first dimension is no greater than the first queried limit under signed 32-bit comparison.
- The second dimension is no greater than the second queried limit under signed 32-bit comparison.
- The declared unsigned stride equals the computed stride.

The second dimension comparison is reached only if the first dimension is within its limit. Stride validation is reached only if both dimension comparisons succeed.

The signed limit comparisons are supported by explicit overflow-aware comparison logic. They are not equivalent to simply testing a potentially wrapped signed subtraction.

The computed stride is:

\[
\left(
\left(
(\text{first dimension}\times\text{format factor}+31)
\bmod 2^{32}
\right)
\mathbin{\gg}3
\right)
\mathbin{\&}\texttt{0xfffffffc}
\]

The right shift is logical. Multiplication and addition are reduced to 32 bits before the shift and mask.

For ordinary positive, nonoverflowing dimensions, this computes a four-byte-aligned row size from the dimension and format factor. That interpretation must not replace the stated wrapping arithmetic for boundary cases.

There is no explicit positivity check beyond rejecting zero. Negative decoded dimensions can therefore pass the visible signed comparisons if the dependency’s result range permits them and the remaining conditions hold.

### Allocation and replacement

After successful validation, the function computes the allocation size as the low 32 bits of:

\[
\text{second dimension}\times\text{declared stride}
\]

It passes that 32-bit value to F-d33f6d597e5d. No explicit multiplication-overflow check or zero-size rejection is present.

If the allocation result is zero, the function returns 4. It has not yet explicitly read the previous allocation field or installed new state.

For a nonzero allocation result:

1. Read the state field at +0x318.
2. If that field is nonzero, invoke F-5e3309c9d083.
3. Install the new allocation and metadata.

The visible call to F-5e3309c9d083 supplies no explicit arguments. It is therefore not established that it releases the previous value, that it accesses a particular state object, or that its behavior is equivalent to a conventional deallocator.

### State installation order

The explicit writes occur in this order:

| Order | Offset | Value written |
|---:|---|---|
| 1 | +0x318 | New allocation result, 32 bits |
| 2 | +0x308 | Parsed format, 8 bits |
| 3 | +0x30a | Low 16 bits of first dimension |
| 4 | +0x30c | Low 16 bits of second dimension |
| 5 | +0x31c | New allocation result, 32 bits |
| 6 | +0x310 | Total allocation size, 32 bits |
| 7 | +0x320 | Allocation result plus total size, reduced to 32 bits |
| 8 | +0x314 | Declared stride, 32 bits |

The dimensions used for validation and allocation are not first narrowed to the stored 16-bit widths.

There is no explicit clearing of the allocated region, copying of fragment data, or advancement of the current position during installation.

For an exactly 11-byte initialization fragment, the function returns 0 after these writes.

For a longer initialization fragment, it invokes F-f1ce972db28c with:

- The original state address.
- The fragment address advanced by 11 bytes.
- The original count minus 11.

Its return value becomes the function’s return value. The installed state is not visibly rolled back if that result indicates an error.

### Continuation path

The continuation path reads the 32-bit current-position field at +0x31c.

- If it is zero, return 4 without reading the end field.
- Otherwise, read the 32-bit end field at +0x320.
- Return 4 if the end is less than or equal to the current position under unsigned comparison.

If the current position is nonzero and strictly below the end, invoke F-f1ce972db28c with:

- The original state address.
- The fragment address advanced by two bytes.
- The original count minus two.

The function returns that dependency’s result unchanged.

There is no local check that the remaining fragment fits in the destination space. Any such enforcement must come from the dependency or an external invariant.

## Side effects

The function performs explicit state writes only after successful initialization validation and a nonzero allocation result. Continuation processing performs no explicit local state writes before delegation.

Dependency side effects remain possible on paths that ultimately return 4:

- The initial discriminator decoder runs before initialization versus continuation is decided.
- Initialization decoders and the global-context query run before format and dimension rejection.
- The allocation dependency runs before allocation failure is reported.

After allocation succeeds, old-storage handling occurs before new metadata is installed. The writes are sequential, not visibly transactional or synchronized. Concurrent observers could see partially installed metadata unless callers provide exclusion.

No direct write to fragment bytes is visible. Called dependencies are not established to preserve input memory, state, globals, or ownership.

## Acceptance examples

These are conditional static acceptance examples, not executed tests.

1. **Count below the minimum:** With count 2 and readable descriptor fields, return 4 after reading the count and data address. Do not invoke the discriminator decoder.

2. **Short zero-tagged continuation:** With count 10, discriminator result zero, nonzero current position, and unsigned end greater than current position, invoke F-f1ce972db28c at fragment offset +2 with count 8. Do not attempt initialization.

3. **Unsupported initialization format:** With count 11, discriminator zero, and format code 4, decode both dimensions and the stride and invoke the limit query, then return 4 without allocating or explicitly installing state.

4. **Disabled conditional format:** With format code 2 and the global flag byte zero, use effective factor zero. The limit query still occurs before rejection.

5. **Successful header-only initialization:** Suppose format code 1 produces dimensions 16 and 2, the queried limits admit both, and the declared stride is 4. The stride equation yields 4 and the allocation size is 8. If allocation returns a nonzero value, install the metadata and return 0 for count 11. The recorded end is the allocation result plus 8 modulo \(2^{32}\).

6. **Initialization with data:** Under the same successful header conditions but count 15, install metadata and invoke F-f1ce972db28c at offset +11 with count 4. Return its result, including an error result, without visible rollback.

7. **Stride mismatch:** For first dimension 16 and effective factor 2, a declared stride other than 4 fails validation. Do not invoke allocation.

8. **Exhausted continuation destination:** If current position equals end, return 4. The comparison is unsigned and equality does not permit delegation.

9. **Allocation failure:** If validation succeeds but F-d33f6d597e5d returns zero, return 4 without explicitly reading the old allocation field, invoking old-storage handling, or installing metadata.

10. **Wrapping allocation size:** If accepted decoded values produce a product exceeding 32 bits, pass only its low 32 bits to the allocator. Do not introduce an overflow rejection absent another dependency’s contract.
