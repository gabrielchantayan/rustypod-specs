# F-3df8cda06292

## Purpose

F-3df8cda06292 fills caller-supplied memory with blocks of byte lookup results. Each block contains 16 rows of 256 bytes. Entries are selected from a shared byte lookup region by XORing a key byte with the entry’s column number.

The lowest-addressed block receives an additional per-row XOR using bytes from the beginning of the key region. Higher blocks do not receive that additional XOR.

The established behavior is a memory transformation, not a validated cryptographic interface. A cryptographic purpose, a particular substitution table, and a requirement that the row selectors form a permutation are not established by the supplied evidence.

## Interface

The function accepts three integer-represented arguments and returns no value:

| Argument | Role |
|---|---|
| Count | Signed loop-control input. Determines how many higher blocks are written before the mandatory lowest block. |
| Key address | Base address for byte reads used to select and modify lookup results. |
| Destination address | Base address for byte writes. |

The supplied representation uses signed integers for the arguments and row control, unsigned integers for column control and XOR-derived indices, and byte-sized memory accesses for key material, lookup results, and output. The behavioral layout below uses 32-bit integer words and 8-bit bytes, consistent with that representation. Native pointer width, calling convention, alignment behavior, and signed-overflow semantics require target confirmation.

There is also an implicit shared input: an address-bearing global value. At entry, the function obtains:

- A lookup base from that global value.
- A selector-table base by evaluating that global value again and subtracting 384 bytes.

The two evaluations are distinct in the supplied representation. With a stable global value, the selector table begins 384 bytes before the lookup base. Concurrent mutation could cause the captured bases not to have that relationship; no synchronization is shown.

The relevant memory layouts are:

| Region | Layout |
|---|---|
| Lookup region | 256 byte entries, addressed by indices 0 through 255. |
| Selector table | 16 entries, each a signed 32-bit integer, spaced four bytes apart. |
| Output row | 256 bytes. |
| Output block | 16 consecutive rows, totaling 4,096 bytes. |

A selector entry is used as a byte displacement into the key region. It is not scaled after being loaded. The function neither checks that selectors are distinct nor constrains them to the interval 0 through 15.

For an ordinary successful invocation, all memory accesses actually reached must be valid, including the signed-word selector reads and any negatively displaced key reads. Address arithmetic must also have defined meaning for the actual target.

## Behavior

### Output extent and traversal

If Count is greater than one, the function processes higher blocks using descending round numbers: Count, Count minus one, and so on through two.

For round number \(r\), it writes output block \(r-1\), where block zero begins at Destination address. Within each block:

1. Rows are visited from zero through 15.
2. Within each row, columns are visited from zero through 255.
3. Each column produces one byte store.

After all higher blocks, the function always writes block zero. Thus, for positive Count:

- Count equal to one writes one block.
- Count equal to two writes two blocks.
- Count equal to three writes three blocks.
- In general, Count blocks are written, provided all arithmetic and accesses remain valid.

Zero and negative counts do **not** request an empty operation. They skip the higher-block phase but still write the entire 4,096-byte block zero.

For a count that completes without arithmetic or memory failure, the number of byte stores is:

\[
4096 \times \max(1,\text{Count})
\]

This is a mathematical description of the work, not a guarantee that every representable positive count permits valid address calculations.

### Higher-block transformation

For each higher-block round \(r\), row \(j\), and column \(x\):

- \(r\) descends from Count through two.
- \(j\) ranges from zero through 15.
- \(x\) ranges from zero through 255.

The function reads selector entry \(j\). Using that signed displacement, it reads a key byte at:

\[
\text{Key address} + 16r + \text{selector}[j]
\]

It XORs that byte with \(x\). Since both operands are in the range zero through 255, the resulting lookup index is also in that range.

The byte read from the lookup region at that index is written to:

\[
\text{Destination address} + 4096(r-1) + 256j + x
\]

For stable, nonoverlapping inputs, the resulting relationship is:

\[
\text{output}[r-1,j,x]
=
\text{lookup}\bigl[\text{key}[16r+\text{selector}[j]] \mathbin{\mathrm{XOR}} x\bigr]
\]

That formula describes entry values only under the stated stability conditions. It must not be interpreted as permission to snapshot or cache mutable inputs.

### Lowest-block transformation

Block zero is written after every higher block.

For row \(j\) and column \(x\), the selected key byte comes from:

\[
\text{Key address} + 16 + \text{selector}[j]
\]

The resulting lookup byte is additionally XORed with the byte at:

\[
\text{Key address} + j
\]

The destination byte is at:

\[
\text{Destination address} + 256j + x
\]

For stable, nonoverlapping inputs:

\[
\text{output}[0,j,x]
=
\text{lookup}\bigl[\text{key}[16+\text{selector}[j]] \mathbin{\mathrm{XOR}} x\bigr]
\mathbin{\mathrm{XOR}}
\text{key}[j]
\]

The final XOR remains byte-sized because both operands are byte values. There is no accumulation, carry, or dependence on a previous output value.

### Reads, writes, and aliasing

The supplied representation places selector and key reads inside the innermost loop. They are not fetched once per row.

For each higher-block output byte, the represented data-access dependency chain is:

1. Read the row’s signed selector word.
2. Read the selected key byte.
3. Read the indexed lookup byte.
4. Store the output byte.

For each lowest-block output byte, the function performs that same selection chain and also reads the row’s additional XOR byte from the beginning of the key region. Both byte operands must be available before the store. The supplied expression does not establish whether the additional XOR-byte read occurs before or after the lookup-selection chain.

The function does not snapshot the selector table, lookup bytes, or key bytes. Consequently:

- A destination store that overlaps a later key read can affect later results.
- A destination store that overlaps the selector table can change subsequent selector values and therefore subsequent read addresses.
- A destination store that overlaps the lookup region can change later lookup results.
- Processing the highest requested block first can affect later, lower blocks when regions overlap.
- Stores within a row can affect later columns when inputs and output overlap.

The captured base addresses remain the function’s bases after entry. Changing the address-bearing global later does not, in the supplied representation, cause the function to reacquire those bases. Changing memory reachable through those bases is a separate matter and can affect later reads.

These are observations about the represented access structure. Exact machine-level access order, compiler transformations, and guarantees for concurrent or externally observable memory require target evidence.

### Integer and address boundaries

The column counter covers exactly 256 values: zero through 255. Its conversion for the loop comparison is safe over the values reached by that loop. The row counter covers exactly 16 values.

The signed Count is decremented only while it is greater than one. Accordingly, the loop-control decrement itself does not underflow for zero or negative inputs.

Address arithmetic is a separate risk:

- Higher-round addressing multiplies the round number by 4,096.
- Key addressing multiplies it by 16.
- Selector values can be negative or large.
- Base-address addition can overflow independently of those products.

The higher-block destination calculation is represented as forming an address using \(4096r\), the row displacement, and the column, and then subtracting 4,096 for the store. The mathematical destination is block \(r-1\), but definedness of intermediate calculations cannot be inferred solely from the final mathematical address.

No range checks, overflow checks, or checked pointer operations appear. A portable contract must therefore make valid target arithmetic a precondition rather than promise wrapping behavior.

## Side effects

The function writes destination bytes in the order described above. With distinct, stable input regions and valid arithmetic, its explicit stores affect only the requested output blocks.

It performs no explicit:

- Allocation or deallocation.
- Ownership transfer.
- File, device, or network operation.
- Callback or subordinate function call.
- Status reporting.
- Write to the address-bearing global.

The caller retains responsibility for the supplied storage. The function neither acquires ownership of the key region nor releases the destination region.

If destination aliases input storage, the function’s ordinary output writes also modify that aliased storage. This includes the possibility of modifying the selector table, lookup region, key bytes, or even the storage containing the global address value. There is no overlap detection or protection.

No explicit error path is present. Invalid memory, invalid alignment on a target that requires alignment, or invalid arithmetic may prevent completion. The evidence does not establish a particular fault type, recovery behavior, rollback, or error return. A failure after some stores can leave a partially written destination.

## Acceptance examples

These examples are conditional static expectations. No runtime tests have been performed.

### One-block invocation

Given Count equal to one, stable disjoint memory, and selector entry \(j\) equal to \(j\):

- Only block zero is written.
- Row \(j\) uses the selected key byte at displacement \(16+j\).
- Every result in that row is additionally XORed with the key byte at displacement \(j\).
- Exactly 4,096 byte stores occur.
- No higher block is written.

### Two-block invocation

Given Count equal to two and valid stable inputs:

- Block one is completely written before block zero.
- Block one uses selected key bytes at displacements \(32+\text{selector}[j]\).
- Block one receives no additional XOR from the first 16 key bytes.
- Block zero uses the distinct lowest-block transformation.
- Exactly 8,192 byte stores occur.

### Nonpositive count

Given Count equal to zero or a negative value, and otherwise valid inputs:

- No higher-block round executes.
- Block zero is still fully written.
- The operation is not a no-op.
- Key and selector memory must still be readable.

### Identity lookup region

Given lookup entry \(x\) contains byte value \(x\), stable disjoint regions, and a selected key byte equal to hexadecimal 3C:

- In a higher-block row, column 00 produces 3C.
- Column 3C produces 00.
- Column FF produces C3.

For block zero, if the row’s additional XOR byte is hexadecimal A5, the corresponding results are 99, A5, and 66.

### Repeated selectors

Given two rows have equal selector entries and all input regions remain stable:

- Their higher-block rows are identical within the same round.
- Their block-zero rows need not be identical because their additional XOR bytes are read from different row-indexed key positions.
- The function does not reject repeated selectors.

### Aliased key and output

Given an earlier destination store overwrites a key byte that a later column will read, the later result must be assessed using the modified memory state represented by that execution, not an assumed entry-time key snapshot.

An acceptance check that expects snapshot semantics would therefore assert behavior not established by the supplied evidence.
