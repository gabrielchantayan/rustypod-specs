# F-da96b149d58f

## Purpose

F-da96b149d58f performs an ordered startup sequence, creates and configures two objects through dependencies, and then enters an unbounded wait-for-interrupt loop.

The established behavior is the sequence of memory accesses and dependency invocations described below. The meanings of “startup,” “object,” and “configure” are inferred from the overall pattern, not established service contracts. In particular, the supplied evidence does not establish that either object is a thread, that a buffer request allocates heap memory, or that a configuration call transfers ownership.

There is no normal return path in the supplied representation. Reaching the final phase produces repeated wait-for-interrupt operations, not a completion result.

## Interface

The function has no explicit parameters and no declared return value. It nevertheless consumes implicit machine state:

- Four incoming 32-bit values: the link-register value, the values associated with registers r5 and r4, and the incoming r3 value.
- A primary frame-top pointer obtained from a global location.
- A fallback frame-top pointer obtained from another global location when the primary pointer is null.

The visible interface uses 32-bit words. Object handles, pointer-like dependency results, lengths, constants, and the saved incoming values occupy 32-bit quantities in the supplied representation. This does not establish signedness or semantic type for every word.

### Selected frame storage

Let the selected frame top be the primary pointer when nonnull, or the fallback pointer otherwise. The function requires writable storage for the 16 bytes immediately preceding that address.

The four word-sized slots are:

| Offset from selected frame top | Initial value written |
|---|---|

## Behavior

It then writes the incoming link-register, r5, r4, and r3 values to the four slots described in the interface.

There is no visible fallback-pointer validation. If both pointers are null, the function still attempts the writes below the selected null address. This is not an explicit error-return path.

The source representation does not establish how many physical reads of the primary global occur, or whether those reads have volatile semantics. The established selection rule is primary-if-nonnull, fallback otherwise.

## Side effects

4. The first outgoing value at frame offset −16.
5. The second outgoing value at that same frame offset.

No non-aliasing guarantees are supplied. If frame storage, publication storage, global data, or dependency-managed memory overlap, the writes and subsequent reads can affect one another. The contract does not silently assume disjoint storage.

### Ownership and lifetime

There is no visible release operation for either result. This does not prove a leak: ownership could remain with F-U03, transfer to another dependency, or follow an undocumented protocol.

Likewise, the function does not visibly restore the saved incoming words or release object handles. Its nonreturning final phase makes conventional return-time cleanup inapplicable on the shown path.

### Errors and partial progress

The only visible conditional decision concerns the initial zero/nonzero result. Later results are consumed without visible success checks. A null object result, unusable buffer result, nonreturning dependency, or invalid memory access can prevent the final wait phase.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests.

1. **Primary frame selection.** Given a nonnull, usable primary frame pointer, the four initial writes use its preceding 16 bytes. A different fallback value does not change the selected base.

2. **Fallback selection.** Given a null primary pointer and a usable fallback pointer, the same layout and write order apply relative to the fallback. A null fallback is not converted into a controlled error result.

3. **Initial branch.** A zero result from F-a3aed6337812 skips F-40ce7199841c. Any nonzero result causes exactly one visible invocation before the fixed-address write, provided it returns.

4. **Nonoverflowing field sum.** If the fields at offsets 0xE4 and 0xE0 contain 12 and 20, F-U01 receives 32. This example does not define overflowing cases.

5. **First-handle reread.** If the first acquisition publishes handle H and F-U03 changes the publication word to J, the first configuration call receives J. If configuration then changes the word to K, the following F-7aad9d988c5b receives K.

6. **Different configuration arguments.** With returning dependencies and usable results, the first configuration receives mode-like value zero and size 768; the second receives 64 and size 2,048. The second handle is not explicitly published to the first handle’s global location.

7. **Final continuation.** If all preceding operations return and the second F-7aad9d988c5b returns R, every subsequent visible loop iteration performs the wait operation with R. No normal return follows.
