# F-7a20c3ac79f3

## Purpose

F-7a20c3ac79f3 routes two 32-bit input values through one of two mutually exclusive paths:

- When the first input produces a nonzero result from a designated dependency, the function checks the second input against two table entries and may clear a byte in a caller-supplied object.
- Otherwise, it classifies the second input and selects one of two indirect operations obtained through that object.

This is an established description of the visible control flow. The meanings of the inputs, table entries, object byte, and indirect operations are not established. In particular, interpreting the byte as an enabled flag or the dependency results as equality tests would require additional evidence.

The function has no specified return value. Its observable effects consist of dependency calls, indirect dispatch, the reads needed to select those operations, and zero, one, or two explicit byte writes.

## Behavior

### Initial selection

Before the initial dependency call, the function retains the shared lookup base for possible later use. It also obtains the 32-bit entry at offset `0x80` from the shared lookup address for that call.

It invokes F-a1e68ae27737 with:

1. The first input.
2. The retrieved `0x80` entry.

Only the distinction between zero and nonzero controls subsequent behavior. A negative result, if representable in the dependency’s result type, takes the same branch as any other nonzero result.

The supplied representation uses both a retained base and a shared-base reference around this initial lookup. It does not justify a claim about an exact machine-level count of shared-base loads or behavior under concurrent modification. The established sequencing is that the retained base exists before the dependency call and is available afterward.

### Initial result is nonzero: two ordered checks

This path always performs two calls to F-a1e68ae27737, assuming earlier operations return normally.

First, the function reads the 32-bit entry at offset `0x88` from the retained lookup base. It passes the second input and that entry to F-a1e68ae27737.

- A nonzero result causes a one-byte write of zero at object offset `0x18`.
- A zero result causes no explicit object write at this point.

Next, the function reads the 32-bit entry at offset `0x84` from the same retained base. It passes the second input and that entry to F-a1e68ae27737.

- A nonzero result causes another one-byte write of zero at object offset `0x18`.
- A zero result causes no explicit object write at this point.

The function then returns without entering the dispatch path.

The checks do not short-circuit. A nonzero result from the `0x88` check does not suppress the `0x84` lookup or call. If both results are nonzero, the function performs two explicit byte writes, not one combined write.

The intervening dependency call matters. If the first check causes a byte clear, that write occurs before the second check. The second check can therefore observe the cleared byte if it has some independent means of reaching the object. It may also modify that byte. Consequently, an earlier clear does not by itself guarantee that the byte remains zero when the function returns.

The later lookup entries are read when their respective calls are prepared; they are not both snapshotted before the checks. Changes to the retained table’s contents by an earlier dependency can affect a later entry read. Conversely, changing the shared base does not redirect these later reads away from the already retained base.

### Initial result is zero: classification and dispatch

This path makes no further calls to F-a1e68ae27737. It instead invokes F-d5d68dc4e17c with the second input.

After that dependency returns, the function obtains the dispatch-table address from the object’s first 32-bit field.

- If the dependency result is nonzero, the function selects the indirect target at dispatch-table offset `0x24`.
- If the dependency result is zero, the function selects the indirect target at dispatch-table offset `0x20`.

The `0x20` operation is shown with two explicit arguments: the object address and the first input, in that order.

The `0x24` operation is shown without explicit arguments. Because the supplied representation identifies indirect-call recovery as uncertain, this does not establish that the actual operation has a zero-argument ABI or that no receiver is conveyed implicitly. Its argument contract remains unresolved.

The object’s dispatch-table field is read after F-d5d68dc4e17c returns. A dependency-induced change to that field can therefore affect the selected target.

This function makes no explicit write to the object’s `0x18` byte on the dispatch path. Dependencies and indirect operations may nevertheless write there or elsewhere; their behavior is not supplied.
