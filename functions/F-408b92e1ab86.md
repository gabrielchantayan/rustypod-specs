# F-408b92e1ab86

## Purpose

F-408b92e1ab86 updates a counter within a caller-supplied object, checks that counter against a dependency-provided value, and then conditionally updates ownership and nesting state in an embedded subobject.

The established behavior has two ordered phases:

1. Invoke an entry dependency, decrement a nonzero 32-bit counter, invoke a notification dependency when that decrement reaches zero, and check consistency.
2. Optionally invoke a header-dependent dependency, compare an embedded owner value with a dependency-provided identity, and either report an owner mismatch, retain nested ownership, or clear ownership and invoke a final dependency.

The apparent intent is a synchronized release operation involving a reference-like counter and an owner-tracked, possibly recursive synchronization object. That interpretation is inferred, not established. In particular, the supplied material does not establish that the entry dependency acquires a lock, that the notification dependency wakes waiters, or that the final dependency releases a lock.

The ordering below is part of the contract. The function performs its first-phase operations before checking whether the embedded-subobject address is null, and it performs those operations even when the eventual result is an error.

## Interface

### Inputs and result

The interface exposes four 32-bit input words and returns a 32-bit integer result.

- **Object address:** The first input is used as the base address for all direct field accesses and for several dependency arguments.
- **Second input word:** No explicit use is visible.
- **Third and fourth input words:** Forwarded unchanged to F-621dae46a146 if that dependency is invoked. They have no other visible use.
- **Additional unmodeled value:** The invocation of F-621dae46a146 also receives an additional word whose origin is not established by the declared interface. Its value must not be inferred from any of the four declared inputs.

The result can be:

## Behavior

### 1. Entry operation and counter update

The function first invokes an unresolved dependency with the address at object `+0x180`. Its result is not used as a visible branch condition. Subsequent steps require that this invocation return normally.

It then reads the 32-bit counter at `+0x1c0`.

- If the value is zero, it leaves the counter unchanged and does not invoke the notification dependency.
- If the value is nonzero, it writes the value decreased by one back to `+0x1c0`.
- If the decreased value is zero, it invokes a second unresolved dependency with the address at object `+0x19c`.

For ordinary representable arithmetic, the notification occurs exactly when the initially read counter is `1`. A counter already equal to zero does not cause notification.

No lower-bound validation is visible. Negative counter values are not rejected before subtraction. The exact extreme-value overflow semantics of the displayed signed 32-bit subtraction require machine-level confirmation; the contract does not replace that uncertainty with an assumed saturating or checked operation.

### 2. Consistency check

After any notification invocation has returned, the function calls F-1e90bf079919 with the object address.

It then reads the current counter at `+0x1c0` and compares that value with the dependency’s result. This comparison uses a fresh field read, not merely the value computed before calling the dependency.

If the values differ, the function invokes F-a817d8d58c10. The supplied static material marks this invocation as non-returning. No normal result from F-408b92e1ab86 is established for this mismatch path.

This ordering matters if either preceding dependency changes the counter:

- A notification dependency can affect what F-1e90bf079919 observes.
- F-1e90bf079919 can affect the counter subsequently compared with its result.
- The function does not require the final comparison value to equal the value written during the decrement step.

No rollback of the counter update is visible before the mismatch handler is invoked.

### 3. Computed-address check

After a successful consistency comparison, the function computes the embedded-subobject address at object `+0x180`.

If that computed address is null, it returns `26`.

This is not an early object-validation guard. The entry dependency, counter processing, and consistency check have already occurred. The same embedded address was also passed to the entry dependency before this check.

Under wrapping 32-bit address arithmetic, an object-address bit pattern of `0xfffffe80` would produce a null address after adding `0x180`. This is an arithmetic observation, not a guarantee that execution with that input is valid or can reach this return: earlier address formation, memory accesses, and dependency behavior remain prerequisites.

### 4. Header-dependent invocation

For a non-null embedded address, the function reads the 32-bit header at `+0x180` and compares it with an external marker value.

- If they differ, it skips F-621dae46a146.
- If they match, it invokes F-621dae46a146 with five visible argument positions:
  1. the embedded-subobject address;
  2. zero;
  3. the third declared input word;
  4. the fourth declared input word;
  5. the additional unmodeled word.

If F-621dae46a146 returns a nonzero value, F-408b92e1ab86 immediately returns that value.

If the dependency returns zero, processing continues. Its zero result does not establish that it left the object unchanged. Subsequent field accesses observe whatever state exists after the dependency returns.

### 5. Flags snapshot and owner comparison

The function reads the unsigned 16-bit flags field at `+0x18e` and retains that value for the later nesting decision.

It then invokes F-196812b4b122 without explicit arguments. After that invocation returns, it reads the 32-bit owner field at `+0x184` and compares it with the dependency’s result.

If the values differ:

- the function returns `5`;
- it does not directly read or modify the nesting counter in this phase;
- it does not directly clear the owner;
- it does not invoke F-259d2fe281b0.

Earlier writes and dependency effects remain in place. In particular, an owner mismatch does not undo the first-phase counter decrement.

The flags and owner are intentionally described at different observation points. The flags snapshot precedes F-196812b4b122; the owner read follows it. If that dependency changes the flags, the nesting decision still uses the earlier snapshot.

### 6. Nested retention or final release

If the owner comparison succeeds, the function examines bits 4 and 5 of the captured flags value.

Nested-release handling applies exactly when those bits encode binary `10`: bit 5 is set and bit 4 is clear. Other flags bits do not affect this decision.

**When that flag condition is true:**

1. Read the signed 16-bit nesting counter at `+0x192`.
2. Subtract one and store the result in the same 16-bit field.
3. If the stored 16-bit result is nonzero, return `0` without directly clearing the owner or invoking F-259d2fe281b0.
4. If the result is zero, proceed to final release.

**When that flag condition is false:**

- Do not perform the nesting-counter decrement.
- Proceed directly to final release, regardless of the counter’s previous value.

Final release has this order:

1. Write 16-bit zero to the nesting counter at `+0x192`.
2. Write 32-bit zero to the owner field at `+0x184`.
3. Invoke F-259d2fe281b0 with the address at object `+0x194`.
4. Return that dependency’s result.

When nested handling decrements `1` to zero, the nesting field is written twice: once with the decrement result and once by the final-release clearing operation.

The owner and nesting fields are cleared before F-259d2fe281b0 is invoked. There is no visible restoration if it returns a nonzero result. The dependency itself may modify those fields; the function does not re-read or restore them afterward.

These statements concern writes performed by this function. They do not imply that dependencies preserve or restore any field.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Each assumes valid reached memory accesses, normally returning dependencies except where specified, and a successful consistency comparison unless otherwise stated.

1. **Counter already zero.**  
   Starting with the first-phase counter at `0`, the function performs no direct write to that counter and does not invoke F-unresolved-02. It still invokes F-1e90bf079919 and checks the current counter.

2. **Transition from one to zero.**  
   Starting with the counter at `1`, the function writes `0`, invokes F-unresolved-02, then invokes F-1e90bf079919. If the latter returns the subsequently observed counter value, execution continues.

3. **Consistency mismatch.**  
   If F-1e90bf079919 returns `4` but the subsequent counter read is `3`, F-a817d8d58c10 is invoked. No normal return value is established, and the later header and owner processing is not reached.

4. **Header dependency rejects continuation.**  
   If the header equals the external marker and F-621dae46a146 returns `17`, the function returns `17` without performing the later flags read, identity invocation, or direct owner and nesting writes.

5. **Owner mismatch.**  
   If the owner read after F-196812b4b122 differs from its result, the function returns `5`. A prior first-phase decrement remains observable unless a dependency changed it.

6. **Nested ownership retained.**  
   With matching owner, captured flags satisfying the nested condition, and nesting counter `2`, the function writes nesting counter `1` and returns `0`. It does not directly clear the owner or invoke F-259d2fe281b0.

7. **Last nested release.**  
   With the same flags and matching owner but nesting counter `1`, the function writes nesting zero, writes nesting zero again, clears the owner, and invokes F-259d2fe281b0. Its result is returned.

8. **Zero nesting counter is not rejected.**  
   With nested handling selected and nesting counter `0`, subtraction produces `-1`, a nonzero 16-bit result. The function returns `0` without directly clearing the owner or invoking F-259d2fe281b0.

9. **Non-nested flags bypass decrement.**  
   With matching owner and captured flags not selecting nested handling, the function clears nesting and owner regardless of the prior nesting value, then returns F-259d2fe281b0’s result.

10. **Flags change during identity lookup.**  
    If the captured flags select nested handling but F-196812b4b122 subsequently changes the flags to a non-nested value, the function still follows nested handling, provided the owner comparison succeeds.
