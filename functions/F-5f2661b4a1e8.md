# F-5f2661b4a1e8

## Purpose

F-5f2661b4a1e8 selects between two operations on a receiver:

- A fallback dispatch through the receiver’s method-table entry at byte offset 12.
- A preparation-and-transfer operation that obtains a length-like value, requests a destination through the method-table entry at byte offset 8, conditionally transfers bytes, and writes a terminating zero byte.

The third input controls this selection but is not itself invoked on the preparation-and-transfer path. On the fallback path, it is replaced by the receiver’s selected method-table entry before the indirect invocation.

The established behavior is the branch selection, dependency invocation order, argument relationships, null-result handling, and final byte store described below. Interpreting the operation as copying a terminated string is plausible intent, not an established contract: the length-producing dependency and external transfer dependency have not been supplied.

## Behavior

### 1. Select the path

Fallback is selected if any of these conditions holds:

1. The source token is zero.
2. The dispatch token is null.
3. The dispatch token, when the source token is nonzero, converts to a negative signed integer.

Otherwise, preparation and transfer is selected.

Under the recovered 32-bit interpretation, preparation and transfer therefore requires both:

- A nonzero source token.
- A dispatch-token value in the positive signed range, from `0x00000001` through `0x7fffffff`.

The magnitude or sign of a nonzero source token does not otherwise affect this decision. In particular, a negative source token does not by itself select fallback.

The original dispatch token is not called on either visible path. Its value selects the path; fallback resolves a replacement target from the receiver.

### 2. Fallback dispatch

The fallback path performs the following observable operations in order:

1. Read the method-table address from the receiver’s first word.
2. Read the callable entry at byte offset 12 in that table.
3. Invoke F-000000000002 with the original receiver as the one explicitly recovered argument.
4. Return if that invocation returns normally.

The fallback path does not visibly:

- Invoke F-af561b6ad9f2.
- Read the entry at byte offset 8.
- Invoke F-000000000003.
- Perform the final zero-byte store used by the other path.

Those exclusions concern direct operations in this function. The fallback dependency’s own effects are unknown.

The supplied representation includes adjustments involving unrecovered register state before the indirect fallback invocation. Those adjustments do not change the explicitly recovered receiver argument. They prevent this contract from guaranteeing that the fallback target observes no additional register-carried inputs. The complete fallback calling convention is documented_only.

### 3. Obtain a length-like value

On the preparation-and-transfer path, invoke F-af561b6ad9f2 with the source token.

Its result is retained as a signed integer-sized value. This contract calls it the **extent**.

No direct validation follows. In particular, the function does not visibly reject:

- An extent of zero.
- A negative extent.
- An extent too large for an eventual destination.
- A value whose later decrement or address arithmetic exceeds the signed range.

The dependency’s result must not be silently redefined as a guaranteed valid string length. Such a guarantee would require its separate contract.

This call precedes the visible read of the receiver’s method-table address on this path. Consequently, dispatch uses the table read after F-af561b6ad9f2 returns. No assumption is made that this dependency preserves receiver-reachable memory or global state.

### 4. Request a destination

After obtaining the extent:

1. Read the method-table address from the receiver’s first word.
2. Read the callable entry at byte offset 8.
3. Invoke F-000000000001 with three explicitly recovered arguments, in order:
   - The receiver.
   - The extent.
   - Integer zero.

The third argument is a literal zero. Its semantic role is unknown.

The method’s result is retained as an integer-sized value and compared with zero.

- If the result is zero, return immediately.
- If the result is nonzero, use that numeric value as the destination address for subsequent operations.

There is no visible secondary success test, bounds check, or alignment check. A nonzero result is sufficient to continue, even if its signed interpretation is negative.

The zero-result branch does not establish why the method failed or declined to provide a destination. The function supplies no explicit error code or diagnostic for this condition.

### 5. Invoke transfer and terminate

For a nonzero destination result:

1. Invoke F-000000000003 with:
   - The destination value.
   - The original source token.
   - The extent minus one.
2. After that invocation returns normally, write a single zero byte at the address obtained by adding the extent minus one to the retained destination value.
3. Return.

The transfer’s return value is not used.

The final byte store is unconditional once this point is reached. It is not conditional on an explicit transfer-success result. If the transfer dependency returns normally after doing less than expected, the visible function still performs the terminator store.

The final address is derived from the retained destination and extent, rather than from a replacement destination returned by the transfer. There is no visible reread of the receiver’s table or re-request for storage.

### Arithmetic boundaries

For an extent of at least one, assuming representable arithmetic and valid storage:

- The transfer count is one less than the extent.
- The terminator is written at destination offset one less than the extent.
- An extent of one requests a zero-count transfer and then writes zero at the destination’s first byte.

An extent of zero is not treated as an empty successful case. The visible arithmetic produces a decrement of one below zero. In a conventional 32-bit interpretation, that yields a third-argument word of `0xffffffff`, and the final offset is negative one. Whether the transfer dependency interprets that word as signed or unsigned is unknown.

For negative extents, the supplied function does not establish a valid destination region or transfer count.

The recovered expressions use signed integer-sized intermediates. The representation alone does not establish a portable rule for signed overflow. In particular:

- Decrementing the minimum signed value is outside the signed range.
- Destination-plus-extent arithmetic may exceed that range.
- A bit-level machine result must not be promoted into a guaranteed portable arithmetic contract without additional evidence.

Safe ordinary use therefore requires an extent and destination for which the dependency arguments and final address calculation have the intended machine-level meaning, and for which the final byte is writable.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests.

### Zero source selects fallback

Given a valid receiver and source token zero, any dispatch-token value selects F-000000000002 through table offset 12. The receiver is the explicitly recovered argument.

### Null or signed-negative dispatch token selects fallback
