# F-0b7676808c91

## Purpose

F-0b7676808c91 processes a requested index against an object’s backing source and current index window. It performs an initial notification, marks an attempt flag, rejects certain indices, and then adjusts or replaces the current window before conditionally presenting an associated entry.

The established behavior is an ordered sequence of object-field accesses and dependency calls. “Window,” “selection,” and “presentation” are descriptive interpretations of that sequence, not established application-level types.

The function has no explicit return value or error result. Several paths return after partially updating the object. A normal return does not establish that an entry was presented.

## Interface

### Inputs

The recovered interface has five arguments:

1. **Object reference.** A writable object with the fields and dispatch structure described below.
2. **Requested index.** A 32-bit unsigned value. Some decisions reinterpret its bits as a signed 32-bit integer.
3. **First auxiliary value.** A 32-bit integer. Its original value is stored in the object and passed to a presentation callback. It also initializes the first word of temporary storage.
4. **Second auxiliary value.** A 32-bit integer. It initializes the second word of temporary storage and, if presentation proceeds, is stored in the object and passed to another callback.
5. **Optional-action flag.** A 32-bit integer tested for zero versus nonzero. Its magnitude and sign otherwise have no visible significance.

The source model uses four-byte words and 32-bit addresses. Byte fields must not be treated as four-byte fields.

## Behavior

### 1. Initial notification and preliminary rejection

The function first initializes two consecutive four-byte temporary words from the two auxiliary arguments. It then invokes the object operation at dispatch offset `+0xe0`, with the object as an explicit argument.

After that operation returns, it writes byte value `1` to object offset `+0x66`.

It next interprets the requested index as signed 32-bit:

- If negative, it returns immediately.
- Otherwise, it obtains a 32-bit value from the backing-source operation at dispatch offset `+0x08`.
- It compares that returned value and the requested index as unsigned values. If the returned value is less than or equal to the requested index, it returns.

Thus, every request with bit 31 set is rejected before the backing-source count-like operation is called. Such requests still cause the initial object callback and the attempt-flag write.

The backing-source call has no explicit arguments in the supplied call expression. An explicit receiver argument must not be invented for it.

The returned value appears to be a count or upper bound, but that interpretation is inferred. The established acceptance condition at this stage is:

- the requested index is signed-nonnegative; and
- the requested index is unsigned-less-than the returned value.

### 2. Clearing an existing active association

After preliminary acceptance, the function writes byte value `1` to `+0x15`.

It reads the signed word at `+0x40`. If that value is nonnegative, it performs this sequence:

1. Captures the presentation-object reference from `+0x1c`.
2. Invokes the main object’s operation at dispatch offset `+0xd8`, passing the main object.
3. Passes that operation’s four-byte result to the captured presentation object’s operation at dispatch offset `+0x14`, with the captured object as the explicit receiver.
4. Writes signed value `−1` to the main object’s `+0x40` field.

The captured reference matters: changes to `+0x1c` during the main-object callback do not redirect this particular subsequent call.

If the original `+0x40` value is negative, all four actions are skipped.

The function then stores the requested index at `+0x60` and the original first auxiliary argument at `+0x5c`. These stores precede window adjustment and do not imply eventual presentation.

### 3. First window classification

The function examines the current span at `+0x2c`.

If the span is zero, it writes byte value `0` to `+0x44` and uses the nonwrapping membership rule below.

If the span is nonzero, it:

1. Calls the backing-source operation at dispatch offset `+0x08` again.
2. Reads and retains the current start from `+0x20`.
3. Calls F-d7be9cfb4000 with:
   - the 32-bit expression “span plus retained start minus one”; and
   - the returned backing-source value.
4. Stores that dependency’s secondary result at `+0x24`.

The ordinary primary return value is not used. The supplied evidence does not establish the dependency’s arithmetic semantics; in particular, it does not prove that this operation computes a remainder.

The endpoint is compared as signed against the retained start:

- If the endpoint is greater than or equal to that start, the function writes `0` to `+0x44` and uses nonwrapping membership.
- If the endpoint is less than that start, it writes `1` to `+0x44` and uses wrapping membership.

For a nonwrapping classification, the requested index is considered inside when both signed comparisons hold:

- requested index is at least the currently read start; and
- requested index is less than the 32-bit sum of the currently read start and span.

For a wrapping classification, the requested index is considered inside when either signed comparison holds:

- requested index is at least the retained start; or
- requested index is at most the dependency-supplied endpoint.

The nonwrapping rule uses an exclusive upper bound. The wrapping rule includes the endpoint.

### 4. Adjusting or replacing the window

If the first classification considers the request inside:

- If the current start equals the requested index, no adjustment callback is made.
- Otherwise, the function computes the 32-bit difference “requested index minus current start.”
- If that difference is signed-negative, it calls the backing-source operation at dispatch offset `+0x08` again and adds the returned value to the difference.
- It invokes the main object’s operation at dispatch offset `+0xd4`, passing the object, the resulting difference, and zero.

This path does not directly assign a new start.

If the first classification considers the request outside, the function instead:

1. Invokes the main object’s operation at dispatch offset `+0xd4`, passing the object, `0x7fffffff`, and zero.
2. Writes the requested index to `+0x20`.
3. Invokes the main object’s operation at dispatch offset `+0xd0`, passing the object.

The maximum signed 32-bit value is therefore a distinguished argument on this path. Its meaning inside the callback is unknown.

### 5. Reclassification after callbacks

The function does not rely solely on the first membership decision. After the adjustment or replacement path, it classifies the window again using the then-current object state.

For a nonzero span, it repeats the backing-source call and F-d7be9cfb4000 call, stores the new secondary result at `+0x24`, and compares that endpoint with a start retained before the dependency call.

If the endpoint is signed-less-than that retained start:

- It writes `1` to `+0x44`.
- It returns if the requested index is strictly between the endpoint and retained start.
- Otherwise, it proceeds to entry lookup.

In every other case, including a zero span:

- It writes `0` to `+0x44`.
- It returns if the requested index is signed-less-than the current start.
- It returns if the current 32-bit start-plus-span value is signed-less-than-or-equal-to the requested index.
- Otherwise, it proceeds to entry lookup.

A first-stage acceptance therefore does not guarantee entry lookup. Callback effects or different dependency results can cause the second classification to reject the request.

### 6. Entry lookup and presentation

After second-stage membership succeeds, the function performs these operations in order:

1. Calls F-5cd5fa633bae with the address of embedded storage at `+0x28` and the 32-bit difference “requested index minus current start.”
2. Stores the requested index at `+0x40`.
3. Reads a four-byte value from offset `+0x08` of the returned entry.
4. Invokes the current presentation object’s operation at dispatch offset `+0x10`, passing that object and the entry value.
5. Calls F-b9acea4b06ad with the address of the two-word temporary storage and the entry reference.
6. Writes one opaque four-byte static value through the address returned by that dependency.
7. Invokes the current presentation object’s operation at dispatch offset `+0x1c`, passing that object, the temporary-storage address, and the original first auxiliary argument.
8. Stores the original second auxiliary argument at `+0x48`.
9. Invokes the current presentation object’s operation at dispatch offset `+0x3c`, passing that object and the original second auxiliary argument.

Presentation references are obtained as execution reaches the respective calls; a single immutable presentation reference is not established for this sequence.

If the optional-action flag is nonzero, the function additionally:

1. Invokes the presentation operation at dispatch offset `+0x20`, with no explicit arguments in the supplied call expression.
2. Invokes the current presentation operation at dispatch offset `+0x34`, passing the presentation object, zero, and one.

Finally, regardless of the optional-action flag:

- It replaces the first temporary word with a second opaque four-byte static value.
- It calls F-22abefe7f288 with the temporary-storage address.
- It returns.

## Side effects

The routine directly modifies the object flags, request fields, active index, endpoint, and possibly window start described above. It also writes through the address returned by F-b9acea4b06ad.

All invoked operations may have additional effects. Their effects on globals, object fields, referenced storage, ownership, and external resources are not established here.

There is no visible explicit allocation or direct deallocation. The temporary storage is local to this invocation. Passing its address does not establish that a dependency may retain it beyond the call, nor does the final helper prove any particular ownership or destruction convention.

Early returns retain preceding writes and callback effects. There is no rollback, exception handler, status conversion, or visible cleanup path for a dependency that fails to return normally.

The function’s order is significant. For example, `+0x40` is set to the requested index before the presentation payload callback, and `+0x48` is updated only after the temporary-object presentation callback.

## Acceptance examples

These are conditional contract examples, not executed tests. Unless stated otherwise, dependencies return normally, preserve relevant fields, and arithmetic stays within signed range.

1. **Signed-negative request.** A requested index of `0xffffffff` causes the initial notification and attempt-byte write, then returns. No backing-source bound call follows.

2. **Request equal to the bound.** For request `10` and preliminary backing-source result `10`, execution returns after the attempt-byte write. The function does not directly set the accepted flag or request fields.

3. **Existing active association.** With a valid request and initial active index `4`, the main-object `+0xd8` operation precedes presentation `+0x14`. The active index is then set to `−1`, before request fields are stored.

4. **Inside a nonwrapping interval.** With start `10`, span `5`, endpoint result `14`, and request `12`, the first classification accepts. The movement callback receives `2` and zero. If state and endpoint remain unchanged, lookup receives relative index `2`.

5. **At the nonwrapping upper boundary.** Under the preceding interval conditions, request `15` is outside. The function sends the sentinel adjustment, writes start `15`, and invokes the replacement callback. Final acceptance depends on reclassification.

6. **Inside a wrapped interval.** With start `8`, span `4`, endpoint result `1`, request `0`, and a later backing-source result of `10`, the initial difference is `−8`, then becomes `2`. The movement callback receives `2`. The endpoint result is a condition of this example, not a claim about F-d7be9cfb4000.

7. **Inside the wrapped gap.** With retained start `8`, endpoint `1`, and request `5`, wrapping membership fails. If the second classification has those same values, it returns without lookup.

8. **Zero span that remains zero.** If callbacks preserve span zero and avoid overflow, the second nonwrapping check cannot accept any index. Earlier notification, association clearing, request storage, or window replacement may nevertheless have occurred.

9. **Optional actions.** After successful presentation, a zero optional-action flag skips dispatch offsets `+0x20` and `+0x34`. Any nonzero flag executes both, in order, before the final temporary-storage helper.

## Uncertainties

The following remain **documented_only**:

- The arithmetic operation and secondary-result convention of F-d7be9cfb4000.
- The exact signed-overflow semantics of the original executable. Additions and subtractions are 32-bit expressions; they must not be silently widened or assigned unbounded mathematical behavior.
- Whether negative relative indices reaching F-5cd5fa633bae are valid. The wrapped path does not independently normalize the final lookup difference.
- The meanings of the two opaque static values written during temporary-storage handling.
- The full temporary object layout, retention rules, and ownership effects.
- Hidden calling-convention inputs to calls shown without explicit arguments.
- Dependency failure behavior, reentrancy, thread safety, and synchronization requirements.

Callbacks and helpers must not be assumed to preserve fields simply because the surrounding logic resembles a conventional window-selection implementation.
