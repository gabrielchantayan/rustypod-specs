# F-c3853890e662

## Purpose

F-c3853890e662 conditionally updates a one-byte selector in a supplied state record. A prerequisite dependency runs before any direct record access. If processing proceeds, the function either accepts an already-matching selector, rejects a differing nonzero selector, or attempts four indirect calls before committing the requested selector.

The established behavior is:

- A zero prerequisite result returns 6 before any direct record read.
- A request equal to the current selector returns 0 without table access or indirect calls.
- A differing request is rejected with 2 when a subsequent selector read is nonzero.
- Otherwise, two table entries are loaded. Either entry being null produces 1.
- With both objects nonnull, four indirect calls are attempted in a fixed order. The first zero result ends processing with 4.
- Four nonzero results cause the request’s low eight bits to be written to the selector, followed by return 0.

“State transition,” “preparation,” and “activation” are possible interpretations, not established meanings. The contract does not assign application semantics to the selector, objects, or indirect methods.

## Behavior

### Prerequisite precedence

F-ac0ea219f7ca is called first, with no explicit arguments.

If its result is zero, the function returns 6 immediately. It does not directly read the selector, compare the request, or access the table.

Any nonzero result permits processing to continue. No further distinction among nonzero prerequisite results is made.

The prerequisite’s effects are unknown. In particular, subsequent reads observe whatever state exists after that dependency returns, not necessarily the state present at function entry.

### Selector comparison and eligibility

After the prerequisite returns nonzero, the function reads the selector byte, zero-extends it, and compares it with the full unsigned 32-bit request.

Equality produces return 0. This path does not directly rewrite the selector, read the table, or invoke an object method.

If the comparison differs, the function reads the selector again. A nonzero value produces return 2. A zero value permits object selection.

Under stable memory:

- Selector zero and request zero return 0 at the equality comparison.
- Any matching nonzero selector also returns 0.
- A differing request from a nonzero selector returns 2.
- A nonzero request from selector zero reaches object selection.

The request is not narrowed for comparison. Request 256 therefore differs from selector zero; request 257 differs from selector one.

These are separate selector reads, not one saved selector snapshot. If externally visible mutation intervenes, the first and second reads can differ. The source establishes no synchronization or atomic multi-access snapshot.

### Object selection and null handling

The function obtains two object pointers in this order:

1. An entry indexed by another read of the selector byte.
2. An entry indexed by the full unsigned 32-bit request.

Each entry address uses a table base plus four times the corresponding index. The record’s table-address field is read separately for these selections. A single shared table-base snapshot is not retained.

Under stable memory, the first index is zero because the preceding selector test required zero. The function nevertheless reads the selector again; it does not substitute a constant index. With intervening mutation, that read may select another entry. Likewise, changes between the two table-address reads may cause the entries to come from different table bases.

Both object-pointer loads occur before the null decision. A null first object does not prevent the requested-entry load. Consequently, an invalid second entry address is not protected by a null first entry.

After both loads complete, either pointer being null causes return 1. No object method is invoked on that path.

When both pointers are nonnull, their values are retained for the subsequent call sequence. Later table-entry changes do not cause object reselection. The two retained pointers may refer to the same object; no distinctness check is present.

### Ordered indirect calls

With both selected pointers nonnull, the function attempts:

| Order | Receiver | Dispatch-table byte offset | Opaque dependency |
|---:|---|---:|---|
| 1 | First selected object | 36 | F-indirect-01 |
| 2 | First selected object | 40 | F-indirect-02 |
| 3 | Requested-entry object | 20 | F-indirect-03 |
| 4 | Requested-entry object | 24 | F-indirect-04 |

Each call receives its receiver address as the sole explicit argument.

The receiver’s dispatch-table pointer and the specified target slot are read when that call is reached. Targets for all four calls are not captured in advance. An earlier dependency’s changes to object dispatch data can therefore affect a later dispatch.

Each returned 32-bit integer is tested only for zero versus nonzero:

- Zero stops the sequence and produces return 4.
- Nonzero permits the next step.
- A negative value under the represented signed interpretation counts as nonzero.

The calls are short-circuited. Failure of the first prevents the remaining three; failure of the second prevents the last two; failure of the third prevents the fourth.

There is no rollback or compensating call. Effects of already-completed dependencies are not undone.

### Final selector write

After all four indirect calls return nonzero, the function writes the low eight bits of the original request to byte offset zero of the supplied record, then returns 0.

Before this write, it does not recheck the prerequisite, selector, table address, selected entries, or object identity. A dependency’s intervening selector change can therefore be overwritten by the final assignment.

Table selection and storage use different widths:

- Requested-entry selection uses the full 32-bit request.
- The final selector stores only the low eight bits.

A request greater than 255 is not rejected solely because it cannot be represented in one byte. Successful processing can select an entry using a wider value and commit a different numerical selector.

### Integer and address arithmetic

The selector is an unsigned eight-bit value. Its comparison and table-index use zero-extension.

The request is unsigned and 32 bits. Table entries have a four-byte stride, with no explicit bounds or overflow check.

In the represented 32-bit address arithmetic, multiplying the index by four and adding the table base can wrap modulo \(2^{32}\). Such wrapping does not establish that the resulting address belongs to a valid allocation or corresponds to an intended logical table entry.

No valid request range, table length, or allocation boundary is supplied.
