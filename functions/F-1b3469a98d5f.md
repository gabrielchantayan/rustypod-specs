# F-1b3469a98d5f

## Purpose

F-1b3469a98d5f selects one slot from a caller-supplied storage state and clears selected fields within that slot. The slot stride is 24 bytes. Selection follows this precedence:

1. Remove the first slot from a reusable-slot chain, if that chain is nonempty.
2. Otherwise, consume the current allocation cursor if it differs from the recorded end address.
3. Otherwise, obtain a new block header and slot-storage region, link the header into the state, and consume the region’s first slot.

The function has no explicit return value and does not return the selected slot’s address. Its established outputs are memory writes to the state, selected slot, and, on the allocation path, a new block header.

A pooled-storage allocator with partial slot initialization is the inferred intent. The meanings of the initialized slot fields and the mechanism by which a caller subsequently identifies the selected slot are not established.

## Interface

### Argument and result

The sole argument is the address of a mutable state record containing at least four consecutive 32-bit fields.

There is no explicit result, status code, or error indication. Successful completion is observable through the writes described below.

The supplied representation uses 32-bit address-bearing fields and unsigned 32-bit capacity arithmetic. This contract describes that representation; it does not establish a corresponding layout for a different address width.

### State layout

| Byte offset | Width | Role |
|---|---:|---|
| 0 | 4 bytes | Current block-header address, or zero |
| 4 | 4 bytes | First reusable-slot address, or zero |
| 8 | 4 bytes | Current allocation cursor |
| 12 | 4 bytes | Recorded end address |

The function detects exhaustion solely by comparing the cursor and end address for equality. It does not establish that either belongs to the current block.

### New block-header layout

| Byte offset | Width | Value established during construction |
|---|---:|---|
| 0 | 4 bytes | Previous block-header address |
| 4 | 4 bytes | Selected capacity, in slots |
| 8 | 4 bytes | Slot-storage address returned by the dependency |

Header storage and slot storage are obtained through separate calls. The header accesses span 12 bytes.

### Selected-slot layout

The slot stride is 24 bytes, but only the following locations are explicitly accessed:

| Byte offset | Width | Access |
|---|---:|---|
| 0 | 1 byte | Written with zero |
| 4 | 4 bytes | Written with zero |
| 8 | 4 bytes | Written with zero |
| 12 | 4 bytes | Read as a successor address on the reuse path; subsequently written with zero |

Bytes 1–3 and 16–23 are not explicitly accessed. The function does not perform a whole-slot clear.

### Preconditions for successful completion

The state must support the specified reads and writes. Each selected address must support the accesses made through it:

- A nonzero reusable-slot head must be readable at offset 12 and writable at offsets 0, 4, 8, and 12, with the widths listed above.
- An unequal cursor and end pair must leave the cursor usable for the slot writes, even if their numerical ordering is unexpected.
- A nonzero current block-header address used for growth must permit reading its capacity at offset 4.
- Dependency results must permit the header and slot accesses subsequently performed.
- Size and address calculations must produce storage suitable for those accesses.

These conditions are not checked. Alignment requirements and the consequences of invalid accesses remain platform-dependent unknowns.

Disjoint state, header, and slot storage is a precondition for the ordinary pool interpretation, not a condition enforced by the function. With overlapping storage, the ordered accesses below determine the effects.

## Behavior

### Reuse has priority

The function first reads the reusable-slot head at state offset 4.

If that address is nonzero, it selects the referenced slot. It reads a 32-bit successor address from selected-slot offset 12 and writes that successor to state offset 4. Only after this chain update does it perform the slot-clearing writes.

Consequently, the successor is captured before its location is cleared. No chain traversal, membership check, cycle detection, or successor validation occurs.

This path does not inspect the cursor, end address, or existing capacity. It makes no dependency calls and performs no direct writes to the state’s block-header, cursor, or end fields. Overlapping memory can nevertheless cause those locations to change through slot writes.

### Consume the cursor when it differs from the end

When the reusable-slot head is zero, the function reads the cursor and compares it with the recorded end address.

If they are unequal, the old cursor is the selected slot address. The function stores the selected address plus 24 into the cursor field, then partially clears the selected slot.

This branch does not check whether:

- The cursor is below the end.
- At least 24 bytes remain.
- The cursor is aligned to a slot boundary.
- The cursor belongs to the block referenced by the state.

A cursor numerically greater than the end still takes this branch. There is no explicit allocation on this path.

### Obtain a new block when cursor equals end

If the reusable-slot head is zero and the cursor equals the end address, the function computes a capacity and makes two dependency calls.

#### Capacity calculation

If the current block-header address is zero when examined, the selected capacity is 32 slots.

Otherwise, the function reads the existing header’s unsigned 32-bit capacity. It forms two candidates:

- The existing capacity plus 32.
- The existing capacity plus its logical right shift by one, plus its logical right shift by three.

The selected capacity is the unsigned maximum of these candidates. Equality yields their common value.

All candidate additions are unsigned 32-bit operations. Values wrap modulo \(2^{32}\), and the comparison uses the wrapped results. The two shifted terms are computed from the original capacity; they represent separately truncated division by two and eight.

The requested slot-storage size is the selected capacity multiplied by 24, also with unsigned 32-bit wrapping. There is no overflow rejection or correction that restores a minimum capacity after wrapping.

For nonwrapping values, the inferred growth policy is the greater of an additional 32 slots and an increase of approximately 62.5%. That description does not replace the exact wrapped arithmetic.

#### Dependency interaction

The function calls F-871e64ddc6de twice, in this order:

1. First argument 12; second argument zero. The result is used as the new header address.
2. First argument equal to the selected capacity multiplied by 24, reduced to 32 bits; second argument zero. The result is used as the slot-storage address.

The first result is retained across the second call. There are no explicit header-initialization writes between the calls and no explicit validation of either result.

The selected capacity is computed before either call. A dependency-side change to an existing header’s capacity does not cause recalculation.

#### Header construction and state publication

After both calls return, the function performs these explicit memory accesses in order:

1. Write the slot-storage result to new-header offset 8.
2. Read state offset 0 and write that value to new-header offset 0.
3. Write the selected capacity to new-header offset 4.
4. Write the new-header address to state offset 0.
5. Read the slot-storage address from new-header offset 8; this read determines the selected slot address.
6. Write the selected slot address plus the wrapped capacity-times-24 value to state offset 12.
7. Write the selected slot address plus 24 to state offset 8.

The previous-header link therefore comes from a state read after both dependency calls, not from a value saved before them. Dependency mutation of the state can affect that link.

The selected slot address is read back from the header after the header address is published. It is not merely assumed to remain equal to the second dependency result under arbitrary aliasing.

The new current-header address is published before the end and cursor updates. No transactional publication, rollback, or synchronization is visible.

### Partially clear the selected slot

Every selection path ends with the same explicit writes, in this order:

1. Four-byte zero at slot offset 4.
2. Four-byte zero at slot offset 8.
3. Four-byte zero at slot offset 12.
4. One-byte zero at slot offset 0.

The first byte is cleared last. The reusable-head or cursor update precedes these writes.

Under nonoverlapping-storage assumptions, bytes 1–3 and 16–23 retain their prior values. The function itself writes thirteen bytes within the selected slot, not all twenty-four.

If execution is interrupted or an access fails after earlier writes, the function contains no explicit restoration mechanism. The supplied evidence does not establish whether or how such failures are exposed.

## Side effects

Direct writes can affect:

- The reusable-slot head when a slot is reused.
- The cursor whenever the reusable-slot head was zero.
- The current-header and end fields when a new block is obtained.
- All three fields of the newly constructed header.
- The selected slot’s fields at offsets 4, 8, and 12, and its byte at offset 0.

These describe access locations, not necessarily distinct storage. Aliasing can make a header or slot write affect the state or another header field.

F-871e64ddc6de may have additional effects that are not established by this function. In particular, it must not be assumed to preserve the state, existing headers, globals, or other reachable memory.

No explicit release, destruction, reference-count adjustment, or ownership transfer operation appears. Linking the previous header into the new header establishes a stored relationship, not a complete ownership or reclamation contract.

There are no explicit locks, atomic operations, diagnostics, or error returns. The stated access order describes the supplied function’s explicit operations; it is not a cross-thread visibility guarantee.

## Acceptance examples

These are conditional deductions from static evidence, not executed tests. Unless an example states otherwise, assume valid disjoint storage, usable dependency results, and no dependency mutations beyond providing storage.

### Reusable storage wins over exhaustion

Given a nonzero reusable-slot head and equal cursor and end addresses:

- The head slot is selected.
- Its 32-bit successor at offset 12 replaces the reusable-slot head before clearing begins.
- No dependency call occurs.
- The function makes no direct change to the current-header, cursor, or end fields.
- The selected slot receives the four ordered clearing writes.

A self-linked head is not rejected. If its successor equals its own address, the head remains that address even though the selected slot’s successor field is subsequently cleared.

### Unequal cursor and end consume the cursor

Given a zero reusable-slot head and unequal cursor and end addresses:

- The old cursor selects the slot.
- The cursor becomes that address plus 24.
- No dependency call occurs.
- Only the specified slot fields are cleared.

A cursor greater than the end has the same branch outcome. Successful completion still requires writable selected storage.

### Initial block

Given a zero reusable-slot head, equal cursor and end addresses, and a zero current-header address:

- Capacity is 32.
- Dependency requests are 12 and 768, in that order, each with second argument zero.
- The new header records capacity 32 and the returned storage address.
- Its previous-header link is zero if the dependency leaves state offset 0 unchanged.
- The end becomes the selected storage address plus 768.
- The cursor becomes that address plus 24.
- The first slot is partially cleared.

Address validity remains a separate precondition.

### Wrapped growth arithmetic

For an existing capacity of 4,294,967,280:

- The right-shift-by-one term is 2,147,483,640.
- The right-shift-by-three term is 536,870,910.
- Adding 32 to the existing capacity wraps to 16.
- Adding the existing capacity and both shifted terms produces 6,979,321,830 before reduction, which wraps to 2,684,354,534.
- Unsigned comparison selects 2,684,354,534.
- Multiplying that selected capacity by 24 produces 64,424,508,816 before reduction, which wraps to 4,294,966,672.

The second dependency call therefore receives 4,294,966,672 as its first argument. This arithmetic example does not establish allocation success or a usable address range.

### Dependency mutation affects the previous-header link

If either dependency changes state offset 0 before construction, and no intervening aliasing write changes it again, the new header records the value read after both calls.

That value need not equal the header address used earlier to choose capacity. Capacity remains the value calculated before the calls.

### Partial initialization preserves other bytes

Given distinguishable prior slot contents and disjoint storage, bytes 1–3 and 16–23 remain unchanged. A result requiring every slot byte to be zero would not satisfy this contract.
