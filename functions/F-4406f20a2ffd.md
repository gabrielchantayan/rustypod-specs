# F-4406f20a2ffd

## Purpose

F-4406f20a2ffd conditionally submits a two-byte request through shared state and returns a packed 64-bit result.

The established behavior is:

- Query a gate dependency.
- If the gate returns zero, return status `0x53` together with the original second input’s pointer representation.
- Otherwise, require an unsigned selector in the range 1 through 3.
- Obtain an object for an entry/exit pair of dependency calls.
- Construct a 16-bit request value from the selector’s low eight bits and the second input’s pointer representation’s low eight bits.
- Store that value in the initial two-byte portion of a local 32-bit word and submit that portion.
- Convert a zero submission result to status `0x1C`; otherwise obtain the status from a downstream dependency.
- Invoke the exit dependency before returning normally.

Two separate reads of a global pointer location determine which pointer cells supply the entry/exit object and the submission object. These reads must not be collapsed into one: the cells themselves can differ if the global pointer location changes between reads.

The request’s numeric construction is established. Its physical byte order is not independently established. Under a little-endian assumption, the submitted bytes are the selector byte followed by the pointer-representation byte.

“Request submission” describes the call-site structure. Synchronization is inferred intent for the entry/exit pair, not an established dependency contract.

## Interface

### Inputs

The supplied representation exposes four inputs:

| Position | Representation | Direct use |
|---|---|---|
| First | Unsigned 32-bit integer | Active-path selector; accepted values are exactly 1, 2, and 3 |
| Second | Pointer represented in 32 bits, nominally pointing to 32-bit words | Original inactive-path high return word; its low eight address bits also contribute to the active request |
| Third | Uninterpreted 32-bit value | Passed unchanged as the third argument to F-799b69a6c06d |
| Fourth | Uninterpreted 32-bit value | Initial contents of a local 32-bit word, partially overwritten on the active path |

This function does not directly dereference the second input. The active request incorporates bits of its pointer representation, not bytes from the memory it might designate.

The selector is validated only when the gate returns nonzero. No local validation is visible for the other inputs.

### Output

The result is a 64-bit numeric concatenation:

| Result bits | Meaning |
|---|---|
| 31–0 | 32-bit status |
| 63–32 | 32-bit selected pointer representation |

The status is:

- `0x00000053` when the gate returns zero;
- `0x0000001C` when submission returns zero;
- the complete 32-bit return value of F-799b69a6c06d when submission returns nonzero.

The selected pointer is:

- the original second input on the inactive path;
- the address of the local 32-bit request word on every normally returning active path.

This numeric field placement does not depend on the physical byte order of a stored 64-bit result.

The active-path high word exposes an address of automatic local storage. It is not evidence of an allocated result buffer, transferred ownership, or a lifetime extending beyond the invocation.

### Preconditions and validity

Normal completion on the active path requires valid shared-memory accesses and valid dependency calls. In particular:

- The selector must be 1, 2, or 3.
- The cell obtained through the second global-pointer read must support reading the entry/exit object address.
- The cell captured through the first global-pointer read must support reading the submission object address after entry returns.
- The submission object must support a 32-bit read at byte offset `0x2D4`.
- The derived entry/exit argument must be valid for those dependencies.
- Every reached dependency must return normally, except the invalid-selector dependency represented as non-returning.

No null, bounds, alignment, or address-overflow checks are visible.

The inactive path still reads the global pointer location after the gate returns, but it does not dereference the captured cell.

## Behavior

### Initialization and gate

Before calling the gate, the function establishes:

- status `0x53`;
- a selected pointer equal to the second input;
- a local 32-bit word initialized from the fourth input.

It calls F-4adf9cc89b33 without explicit arguments.

After that dependency returns, the function reads a global pointer location and retains the resulting pointer-cell address. This is the **first global-pointer read**. It occurs before the branch on the gate result.

The gate must not be assumed to preserve global state. The captured cell address is the value obtained after the gate has returned.

### Inactive path

If the gate result is zero, the function returns immediately through the normal result construction:

- status remains `0x53`;
- the high result word remains the original second input;
- the selector is not validated;
- the captured cell is not dereferenced;
- no second global-pointer read occurs;
- no entry, submission, downstream-processing, or exit call occurs.

The local copy of the fourth input does not contribute to the returned value.

### Active-path validation

If the gate result is nonzero, the selector must satisfy both of these conditions:

- it is not zero;
- it is not greater than 3 in unsigned 32-bit comparison.

Thus only 1, 2, and 3 proceed.

Any other bit pattern invokes F-a817d8d58c10 without explicit arguments. The supplied representation marks this call as non-returning. No normal result is established for that path, and no entry or submission occurs before it.

In particular, `0xFFFFFFFF` is rejected; it is not treated as a permitted negative selector.

### Entry object acquisition: the second global-pointer read

After successful validation, the function reads the global pointer location again. This is the **second global-pointer read**.

It dereferences the cell obtained from this second read to obtain a 32-bit object address. That object address is retained for both entry and exit.

The function then calls F-unmapped-01 with the retained object address plus byte offset `0x2D8`. Its return value is ignored.

The distinction between the two global reads is observable in the access structure:

| Use | Source |
|---|---|
| Retained entry/exit object | Dereference of the cell obtained by the second global-pointer read |
| Submission object | Later dereference of the cell captured by the first global-pointer read |

If the global pointer location changes between those reads, entry/exit and submission can use different cells. Even when both reads obtain the same cell, that cell’s stored object address can change before submission reads it.

No atomic snapshot, locking guarantee, or permission for such mutation is established.

### Request construction

After entry returns, the selected pointer becomes the address of the local 32-bit word.

The function forms a 16-bit value with:

| Numeric bit range | Source |
|---|---|
| 7–0 | Low eight bits of the selector |
| 15–8 | Low eight bits of the second input’s pointer representation |

Equivalently, the value is the selector byte plus 256 times the pointer-representation byte. Both components are eight bits, so this construction fits in 16 bits without overflow.

That 16-bit value is written into the local word’s initial two-byte portion. The remaining two bytes retain their initialized contents at this point.

The established storage facts and endian-dependent consequences are:

| Property | Contract |
|---|---|
| Submission address | Start of the local 32-bit word |
| Declared submission length | Two bytes |
| Initial two-byte portion | Contains the constructed 16-bit value in the target’s representation |
| Remaining two-byte portion | Unchanged by this function’s request-construction write |
| Little-endian consequence | Offset 0 contains the selector byte; offset 1 contains the pointer-representation byte; the fourth input’s upper numeric 16 bits remain |
| Endianness without additional evidence | documented_only |

It would therefore be incorrect to state unconditionally that this write replaces the local word’s numeric low 16 bits, or that the selector occupies its first physical byte.

The preserved two bytes are outside the declared submission length. Whether the submission dependency accesses beyond that length is unknown.

### Submission object acquisition and call

After entry returns and the request is constructed, the function dereferences the cell captured by the **first** global-pointer read.

It reads a 32-bit handle at byte offset `0x2D4` from the resulting object address. This step does not obtain a fresh cell address from the global pointer location.

F-cd7e1905512f receives six ordered arguments:

1. The 32-bit handle read from object offset `0x2D4`.
2. Zero.
3. One.
4. `0x0B`.
5. The address of the local request word.
6. Two.

The request storage exists during this call. No allocation or explicit ownership transfer is visible.

### Status selection

The submission result is tested for equality with zero.

If it is zero:

- status becomes `0x1C`;
- F-799b69a6c06d is not called.

If it is nonzero, F-799b69a6c06d receives:

1. The submission result, preserving its 32-bit representation.
2. Zero.
3. The original third input.

Its complete 32-bit return value becomes the status.

There is no positive-versus-negative distinction in this branch. A submission result such as `0x80000001` takes the downstream-processing path.

### Exit and normal return

After either status-selection branch completes, F-unmapped-02 receives the retained entry/exit object address plus `0x2D8`.

The function does not reload either the global pointer location or the entry/exit object from a cell for this call. Changes to those locations do not change the retained address used for exit.

The exit return value is ignored. If exit returns normally, the function returns the selected pointer in bits 63–32 and the status in bits 31–0.

No visible cleanup mechanism ensures exit is invoked if entry, submission, or downstream processing faults or fails to return normally.

## Side effects

### Direct memory accesses

The function directly writes only its local request storage:

- initialization from the fourth input;
- active-path replacement of its initial two-byte portion.

It performs no visible direct write through the second input, to the global pointer location, to either captured cell, or to the shared-object fields.

Its shared-memory read ordering is:

1. Gate returns.
2. First global-pointer read captures the submission cell address.
3. For a valid active selector, second global-pointer read obtains the entry/exit cell address.
4. That second cell is dereferenced for the retained object address.
5. Entry is called.
6. The first captured cell is dereferenced for the submission object address.
7. The handle at submission-object offset `0x2D4` is read.

This ordering describes the represented function; it does not establish inter-thread synchronization or atomicity.

### Dependency-mediated effects

All dependency side effects remain unspecified unless established at this call site. They may modify global state or other accessible memory.

F-cd7e1905512f receives the local request address. A read-only contract is not established, so it may modify the request storage. The function does not inspect its contents afterward.

No assumption is made that a dependency copies, retains, owns, or releases the supplied storage.

### Lifetime and ownership

No allocation or explicit release is visible. The local request address is exposed to submission and in the active-path return value, but the function provides no lifetime-extension mechanism.

Safe retention or later dereference would require an external contract not supplied here.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Memory validity and stated dependency outcomes are premises.

### Inactive gate bypasses invalid-selector handling

Given a zero gate result, selector `0xFFFFFFFF`, and second-input pointer representation `0x123456AB`, the result is:

`0x123456AB00000053`

The first global-pointer read occurs. There is no cell dereference, second global-pointer read, invalid-selector call, entry, submission, downstream processing, or exit.

### Active gate rejects the boundary values

Given a nonzero gate result:

- Selector 1 or 3 passes validation.
- Selector 0 or 4 invokes F-a817d8d58c10.
- Selector `0xFFFFFFFF` also invokes F-a817d8d58c10.

For rejected values, the first global-pointer read has already occurred, but the second global-pointer read and entry have not.

### Numeric request construction and conditional byte order

Given selector 2, second-input pointer representation `0x123456AB`, and fourth input `0xCDEF9876`, the constructed 16-bit value is `0xAB02`.

Under an explicit little-endian assumption, immediately before submission the local word has low-address-to-high-address bytes:

`02 AB EF CD`

The declared payload is then `02 AB`.

Under a conventional big-endian representation, the same initial-two-byte write would instead yield:

`AB 02 98 76`

The declared payload would then be `AB 02`.

These alternatives illustrate why the numeric construction does not establish an unconditional physical byte sequence. Memory contents at address `0x123456AB` are not directly read in either case.

### Different cells from the two global reads

Suppose the first global-pointer read captures cell A. Before the second read, the global pointer location changes to cell B.

If cell B supplies object B and cell A later supplies object A:

- Entry receives object B plus `0x2D8`.
- Submission reads the handle from object A plus `0x2D4`.
- Exit receives object B plus `0x2D8`.

This case describes the access structure, not whether such mutation is permitted.

### Same cell, changed object

Suppose both global-pointer reads obtain the same cell, initially containing object A. Entry then changes that cell to contain object B.

Submission reads the handle from object B plus `0x2D4`, while exit still receives object A plus `0x2D8`.

### Submission status branches

For a valid active selector and normally returning entry and exit:

- A zero submission result produces low return word `0x1C` and skips downstream processing.
- Submission result `0x80000001` invokes F-799b69a6c06d with that bit pattern, zero, and the original third input.
- If downstream processing returns `0x11223344`, the low return word is `0x11223344`.

In both branches, the high return word is the local request address, not the original second input.
