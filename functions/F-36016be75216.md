# F-36016be75216

## Purpose

F-36016be75216 invokes one dependency with two writable, invocation-local 32-bit values. It returns zero when that dependency reports zero. When the dependency reports any nonzero value, it returns the arithmetic negation of a sum formed by narrowing the two local values to different widths.

The third and fourth inputs supply the initial local values. The first and second inputs have no explicit use in the supplied body.

This is a source-facing behavioral contract based on static evidence only. It does not establish the application-level meaning of the inputs, the dependency’s status, or the returned number. In particular, the dependency’s nonzero result selects a calculation; it is not established to mean application-level success.

## Interface

### Inputs

The interface has four positional inputs, each represented as a 32-bit value:

| Position | Established use |
|---|---|
| First | No explicit read or forwarding in the supplied body. |
| Second | No explicit read or forwarding in the supplied body. |
| Third | Copied into a writable 32-bit local cell passed as the dependency’s second argument. |
| Fourth | Copied into a separate writable 32-bit local cell passed as the dependency’s first argument. |

The wrapper itself does not dereference any input as a pointer. An input’s bit pattern can therefore be described without assigning it pointer, handle, or numeric semantics. The dependency might impose additional meaning on the third and fourth values, but that meaning is not available here.

The third and fourth inputs are passed onward indirectly, through addresses of local copies. The dependency does not receive addresses of the caller’s original input storage through these arguments.

### Output

The recovered interface returns an integer. Under the apparent 32-bit integer model, the result is:

- Zero when F-59067e4d309c returns zero.
- Otherwise, the negative of the sum of:
  - The post-call value of the fourth-input cell narrowed to a signed 16-bit value and promoted to the integer arithmetic width.
  - The post-call value of the third-input cell narrowed to an 8-bit `char` value and promoted to the integer arithmetic width.

The interpretation of the 8-bit term requires a qualification: the supplied representation uses plain `char`, not an explicitly signed or unsigned character type. Signed 8-bit behavior is a natural reading, but the target’s plain-character signedness is not independently established. Conditional expectations for both interpretations appear below.

A zero result does not uniquely identify the dependency’s zero-status branch. The nonzero-status branch can also calculate zero.

## Behavior

### Local preparation

Before invoking the dependency, the wrapper establishes:

1. A candidate return value of zero.
2. A 32-bit local copy of the third input.
3. A separate 32-bit local copy of the fourth input.

The supplied body places the third-input copy before the fourth-input copy. Both copies are initialized before the dependency is called.

These are full-width copies. No 16-bit or 8-bit narrowing occurs before the call. The dependency therefore receives writable cells containing the complete original 32-bit input patterns, not merely the portions later used by the result calculation.

The exact stack addresses, distance between the cells, alignment beyond that needed by the recovered access types, and surrounding stack layout are not specified.

### Dependency invocation

There is one explicit invocation of F-59067e4d309c:

- Its first argument identifies the local cell initialized from the fourth input.
- Its second argument identifies the local cell initialized from the third input.

This reversal relative to the input positions is behaviorally significant.

The dependency may modify either cell. The wrapper’s later calculation uses the values present after the dependency returns, rather than retaining separate copies of their initial contents.

The wrapper compares the dependency’s returned integer against zero. It does not require a particular nonzero value, distinguish positive from negative values, or incorporate the status magnitude into the result.

### Zero-status branch

If the dependency returns zero, the wrapper returns zero.

In this branch, the wrapper performs no explicit post-call value read from either local cell for result calculation. Consequently, dependency modifications to those cells do not affect this branch’s return value.

This does not imply that the call had no effects. Any effects performed by the dependency remain outside the wrapper’s result-selection logic.

### Nonzero-status branch

If the dependency returns a nonzero value, the wrapper calculates the result from the post-call cell contents.

The fourth-input cell contributes a signed 16-bit term. Under the ordinary fixed-width interpretation, only its low-order 16 bits determine this term:

- Bit patterns from 0 through 32,767 represent nonnegative values.
- Bit patterns from 32,768 through 65,535 represent values from −32,768 through −1.

The third-input cell contributes an 8-bit character term. Only its low-order eight bits determine this term under the same fixed-width interpretation:

- With signed character interpretation, the range is −128 through 127.
- With unsigned character interpretation, the range is 0 through 255.

The two narrowed terms are promoted before addition. The wrapper negates their sum and returns the resulting integer.

The supplied expression does not establish a left-to-right order between the two post-call operand reads. Both belong after the dependency call and only to the nonzero-status branch. A contract must not require one of these reads to precede the other.

### Arithmetic limits

With a signed 8-bit character term:

- The sum ranges from −32,896 through 32,894.
- The returned negation ranges from −32,894 through 32,896.

With an unsigned 8-bit character term:

- The sum ranges from −32,768 through 33,022.
- The returned negation ranges from −33,022 through 32,768.

Neither interpretation can overflow a signed 32-bit integer during the addition or negation. In particular, the wrapper does not negate the minimum signed 32-bit value.

The operation is not equivalent to adding the original 32-bit values and then narrowing. Each operand is narrowed separately before the addition.

Its only explicit transfer of writable storage to another function is the pair of cell addresses passed to F-59067e4d309c. The cells are distinct; their argument positions must not be treated as aliases.

No explicit heap allocation, deallocation, global-variable access, file operation, device access, or caller-buffer write appears in the wrapper. This is a statement about the wrapper body, not a guarantee about the dependency.

No ownership transfer is established. The cells have invocation-local lifetime, and the wrapper provides no mechanism that extends their validity beyond its return. Whether the dependency retains these addresses is unknown; this contract does not promise that retained addresses remain usable.

The wrapper contains no explicit handling for dependency exceptions, abnormal termination, nonreturning behavior, or memory corruption. Its normal-return contract applies only when the dependency returns normally and execution remains valid.

## Acceptance examples

These examples are conditional contracts, not reports of executed tests. Unless otherwise stated, they use the conventional fixed-width narrowing described above.

### Zero status overrides cell contents

Given any initial inputs and any post-call contents of the two cells, if F-59067e4d309c returns zero, F-36016be75216 returns zero.

This remains true if the dependency changes both cells before returning.

### Unchanged small positive values

Given a third input of 5 and a fourth input of 7, if the dependency leaves both cells unchanged and returns any nonzero integer, the wrapper returns −12.

The result is the same for dependency statuses 1 and −1.

### Mutation uses the reversed argument mapping

Suppose the dependency writes 9 to its first cell argument and 4 to its second cell argument, then returns nonzero.

The first argument supplies the signed 16-bit term; the second supplies the character term. The wrapper returns −13, irrespective of the original third and fourth inputs.

### Signed 16-bit interpretation

If the post-call fourth-input cell has low-order 16 bits equal to hexadecimal FFFF, and the third-input cell has low-order eight bits equal to zero, a nonzero dependency status produces a return value of 1.

The signed 16-bit term is −1, not 65,535.

### High-order bits do not contribute

If the post-call fourth-input cell contains hexadecimal 12340002 and the third-input cell contains hexadecimal ABCD0003, a nonzero status produces −5.

The higher bits do not contribute to either narrowed term.

### Character signedness distinguishes outcomes

If the fourth-input cell contributes zero and the third-input cell has low-order eight bits equal to hexadecimal FF:

- Signed 8-bit character interpretation produces 1.
- Unsigned 8-bit character interpretation produces −255.

The supplied evidence does not independently resolve this target-level distinction.

### Nonzero status can still produce zero

If the fourth-input cell contributes −1 and the character term contributes 1, any nonzero dependency status produces zero.

A consumer must not treat the wrapper’s zero result as proof that the dependency returned zero.
