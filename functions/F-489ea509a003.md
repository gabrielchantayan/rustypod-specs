# F-489ea509a003

## Purpose

F-489ea509a003 prepares one fixed-size record for use within a caller-supplied allocation state. It selects the record from a reusable-record chain when that chain is nonempty. Otherwise, it consumes a record from a contiguous allocation region, obtaining a new region when the current region is exhausted.

The selected record is partially cleared. The function has no explicit return value and does not explicitly publish the selected record’s address through a dedicated output field.

An inferred interpretation is a record-pool acquisition or preparation operation. The observable contract is narrower: update allocation bookkeeping, select a 24-byte record, and clear specified fields. The intended way for a caller to identify or use that record is not established by the supplied evidence.

## Interface

The function accepts one pointer to mutable state. The supplied representation uses four consecutive 32-bit words:

| Byte offset | Role established by accesses |
|---|---|
| +0 | Pointer to the most recently linked allocation descriptor, or zero |
| +4 | Pointer to the first reusable record, or zero |
| +8 | Pointer to the next unused record in the current region |
| +12 | Pointer marking the end of the current region |

These are descriptive roles, not declarations of a broader type contract. The state occupies at least 16 accessible bytes.

The function has no explicit result value. Its outputs are memory writes and any effects of dependency calls.

### Allocation descriptor layout

A newly obtained descriptor occupies 12 bytes:

| Byte offset | Width | Value installed |
|---|---:|---|
| +0 | 32 bits | Allocation-descriptor head read from the input state after both allocation calls |
| +4 | 32 bits | Chosen record capacity |
| +8 | 32 bits | Address returned for the record region |

When a prior descriptor exists, its field at offset +4 supplies the capacity used for growth calculations. No other field of that prior descriptor is read directly by this function.

### Record layout

Each record has a stride of 24 bytes. The function accesses these portions:

| Byte offset | Width | Use |
|---|---:|---|
| +0 | 1 byte | Cleared after record selection |
| +4 | 32 bits | Cleared after record selection |
| +8 | 32 bits | Cleared after record selection |
| +12 | 32 bits | Read as the next reusable-record pointer when applicable, then cleared |

For a normally disjoint record, bytes +1 through +3 and +16 through +23 are not written by this function. Their values are not initialized or validated here.

## Behavior

### Selection precedence

The reusable-record head at state offset +4 is read first.

If it is nonzero, that record is selected immediately. The current-region cursor, end pointer, and descriptor capacity do not participate in this path.

Only when the reusable-record head is zero does the function read the current-region cursor at state offset +8 and compare it for equality with the end pointer at offset +12.

The exhaustion decision is equality only. There is no ordering comparison and no validation that the cursor lies within the current region.

### Reusing a record

When the reusable-record head is nonzero:

1. The 32-bit value at selected-record offset +12 is read.
2. That value is written to state offset +4 as the new reusable-record head.
3. The selected record is partially cleared in the order specified below.

The next-link read occurs before that same record field is cleared. Thus the state receives the old next-link value, not the zero subsequently installed into the selected record.

No allocation dependency is called on this path. The function makes no direct write to the descriptor head, current-region cursor, or region end.

### Consuming an existing region

When the reusable-record head is zero and the current-region cursor differs from the end pointer:

- The current cursor is the selected record address.
- State offset +8 is advanced by 24 bytes.
- The selected record is partially cleared.

This path does not inspect a capacity or call the allocation dependency. It advances the cursor even if the supplied cursor/end pair is inconsistent with a valid 24-byte-record region.

### Obtaining a new region

When the reusable-record head is zero and the current-region cursor equals the end pointer, the function chooses a capacity and makes two dependency calls.

If the descriptor-head field is zero, the chosen capacity is 32 records.

Otherwise, it reads a 32-bit unsigned capacity from offset +4 of the existing descriptor. Let that capacity be \(c\). It forms two unsigned 32-bit candidates:

- \(c + 32\)
- \(c + \lfloor c/2 \rfloor + \lfloor c/8 \rfloor\)

Each addition follows 32-bit unsigned arithmetic. The comparison uses the resulting wrapped unsigned values. The larger candidate is selected; equality selects the fractional-growth candidate, without changing the resulting numeric capacity.

The first dependency call requests 12 bytes and passes zero as its second argument. Its result is retained as the new descriptor address.

The second call requests the chosen capacity multiplied by 24, with that multiplication evaluated in 32-bit arithmetic, and again passes zero as its second argument. Its result is retained as the record-region address.

The descriptor is then populated and linked. The direct operations occur in this order:

1. Write the record-region address to descriptor offset +8.
2. Read the descriptor-head field from state offset +0 and write that value to descriptor offset +0.
3. Write the chosen capacity to descriptor offset +4.
4. Write the new descriptor address to state offset +0.
5. Read the record-region address back from descriptor offset +8.
6. Write that address plus the 32-bit capacity-times-24 displacement to state offset +12.
7. Write the selected record address plus 24 bytes to state offset +8.
8. Partially clear the selected record.

The selected record on this path is the record-region address read back in step 5.

The descriptor-head read in step 2 is a fresh read after both dependency calls. It is not necessarily the same value used earlier to decide the capacity. The contract therefore does not assume that the dependency preserves the input state or any globally reachable storage.

### Record clearing

After any successful selection path, direct writes to the selected record occur in this order:

1. A 32-bit zero at offset +4.
2. A 32-bit zero at offset +8.
3. A 32-bit zero at offset +12.
4. A one-byte zero at offset +0.

The operation is not a full 24-byte clear. In particular, the final one-byte write does not imply that the entire first 32-bit word becomes zero.

### Arithmetic boundaries

The represented addresses and stored pointer fields are 32 bits wide. Capacity calculations are unsigned 32-bit calculations.

Consequently:

- Capacity growth is not saturating arithmetic.
- The computed capacity need not exceed the old capacity after overflow.
- The requested region size can wrap independently of whether the capacity calculation wrapped.
- No check ensures that the region request can hold the stated number of 24-byte records.
- Cursor and end-address construction have no explicit overflow checks.

The exact consequences of an invalid or wrapped address depend on the execution environment and are not established here.

## Side effects

### Direct memory effects

On the reusable-record path, the function writes the state’s reusable-record head and the selected record’s cleared fields.

On the existing-region path, it writes the current-region cursor and the selected record’s cleared fields.

On the new-region path, it writes all three fields of a new descriptor, the state’s descriptor head, region end, current-region cursor, and the selected record’s cleared fields.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Successful cases assume valid, disjoint storage, valid address arithmetic, and normally returning dependency calls with suitable storage.

### Reusable record takes precedence

Given a nonzero reusable-record head whose next-link field contains another record address:

- The reusable-record head becomes that next-link address.
- The selected record’s fields at +4, +8, and +12 become 32-bit zero.
- Its byte at +0 becomes zero.
- Its untouched bytes retain their prior contents.
- No dependency call occurs.
- The function makes no direct change to the region cursor or end, even if those fields compare equal.

### Existing region advances by one record

Given a zero reusable-record head, cursor address \(p\), and an end pointer different from \(p\):

- The cursor becomes \(p + 24\).
- The record at \(p\) receives the specified partial clear.
- The descriptor head and end pointer receive no direct writes.
- No dependency call occurs.

The equality-only exhaustion rule also applies when the cursor is beyond the end. Such a state is not repaired or rejected.

### First region uses 32 records

Given a zero reusable-record head, equal cursor and end pointers, and a zero descriptor head:

- The dependency requests are 12 bytes and then 768 bytes, both with second argument zero.
- If their results are descriptor address \(h\) and region address \(b\), and the dependency leaves the state unchanged, the new descriptor contains a zero predecessor, capacity 32, and region address \(b\).
- The state’s descriptor head becomes \(h\).
- Its end becomes \(b + 768\).
- Its cursor becomes \(b + 24\).
- The record at \(b\) is partially cleared.

### Growth changes which candidate dominates

With an existing capacity of 32, the candidates are 64 and 52, so the selected capacity is 64 and the region request is 1,536 bytes.

With an existing capacity of 64, the candidates are 96 and 104, so the selected capacity is 104 and the region request is 2,496 bytes.

These cases distinguish the additive minimum-growth candidate from the fractional-growth candidate.

### Overflow is not rejected

For an existing capacity of 4,294,967,295:

- The additive candidate wraps to 31.
- The fractional-growth candidate wraps to 2,684,354,557.
- The latter is selected.
- Multiplication by 24 produces a wrapped request size of 4,294,967,224 bytes.

The function contains no rejection or correction for this result. Successful completion still depends on usable returned storage and valid address operations.

### Dependency effects can change the linked predecessor

If either dependency changes the state’s descriptor-head field before descriptor linking, the new descriptor’s predecessor is the head value read after both calls. The earlier capacity decision remains based on the value read before those calls.
