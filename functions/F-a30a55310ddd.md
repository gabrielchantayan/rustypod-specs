# F-a30a55310ddd

## Purpose

F-a30a55310ddd resolves an unsigned selector through a table of two-byte entries, obtains a target pointer through an indirect dependency, and searches candidate pointers in increasing index order.

A candidate qualifies only if it is non-null, its first byte equals the target’s first byte, and a comparison dependency returns zero. The function returns the qualifying candidate’s index.

A zero return is ambiguous. It can mean:

- The selector was rejected.
- No qualifying candidate was found.
- The candidate at index zero qualified.

The apparent intent is a name or string lookup. That interpretation is **inferred**, not established. The available evidence establishes byte filtering and a comparison call, but not string termination, encoding, or complete comparison semantics.

## Interface

### Inputs and recovered widths

The function takes two inputs:

- **Context address:** represented by a signed integer, but used to locate context fields.
- **Selector:** an unsigned integer.

This contract uses the recovered **32-bit integer and address model**: signed and unsigned integers occupy four bytes, candidate-pointer slots occupy four bytes, and address arithmetic involving an unsigned operand follows unsigned 32-bit rules. Original ABI metadata is unavailable, so confirmation of the recovered model remains documented_only.

The observed context layout is:

| Byte offset | Field use | Observed width |
|---|---|---|
| +16 | Lookup-table base address, loaded as a signed integer | Four bytes |
| +20 | Indirect callable address for F-000000000001 | Four bytes in the recovered model |
| +24 | Unsigned candidate count | Four bytes |
| +28 | Candidate-array base address, loaded as a signed integer | Four bytes |

These are observed field locations, not a complete context definition.

Only selectors below 256 enter the lookup path. Selectors from 256 through 4,294,967,295 return zero without accessing the context.

### Output

The output is an unsigned 32-bit value in the recovered model:

- Zero for a rejected selector.
- Zero when traversal ends without a qualifying candidate.
- The index of the first qualifying candidate encountered, including zero.

There is no separate success flag or established diagnostic result.

### Preconditions for normal completion

For an accepted selector, normal completion requires that all accesses and calls actually reached are valid. In particular:

- The context fields used by the path must be readable.
- The selected two-byte table entry must be readable at the calculated address.
- The indirect callable address must identify a usable dependency.
- Each reached candidate slot must support a four-byte pointer read.
- Each examined non-null candidate must have a readable first byte.
- The retained target must have a readable first byte whenever a non-null candidate reaches the byte comparison.
- Both dependencies’ additional requirements must hold when called.

The function does not explicitly validate these conditions. Arithmetic wraparound is defined separately below; it does not establish that the resulting address is usable.

## Behavior

### Selector gate

The selector comparison precedes every context access.

If the selector is at least 256, the function returns zero. Neither dependency is invoked, and no valid context storage is required for this path.

Selectors from zero through 255 proceed to target resolution.

### Target resolution

The function loads the table base from context offset +16 and selects a two-byte entry using twice the selector as the displacement.

Under the recovered 32-bit model:

- The selector is unsigned.
- Multiplication by two therefore uses unsigned 32-bit arithmetic.
- Because the accepted selector is at most 255, the displacement is between zero and 510, with no multiplication wraparound.
- Adding that displacement to the loaded table base uses unsigned 32-bit arithmetic. The loaded signed base is converted to its unsigned 32-bit value for this addition.
- The resulting entry address is the sum **modulo 2³²**.

Thus, the bounded displacement does not prevent the address addition from wrapping. A table base numerically near the end of the address space can produce a selected address near zero.

The function reads two bytes at the resulting entry address. A conventional contiguous table containing all 256 entries would occupy 512 bytes, but this function neither verifies such an extent nor requires unselected entries to be read.

The selected two-byte value is passed to F-000000000001. Its callable address comes from context offset +20. The returned value is retained as the target pointer.

The raw 16-bit table value is established. Its signed interpretation, argument extension, and semantic meaning are not established.

The callable-address and table-related reads precede the indirect call. The supplied expression does not establish a finer relative ordering among those reads.

F-000000000001 is called before the first candidate-count read. It is therefore called even when the count subsequently observed is zero. The function does not reject a null target at this stage.

### Candidate traversal

Traversal starts at index zero.

Each traversal decision first reads the unsigned count at context offset +24 and compares the current index against it. If the index is not strictly less than the count, traversal ends and the function returns zero.

If the index is below the observed count, the function:

1. Reads the candidate-array base from context offset +28.
2. Calculates the slot address using the current index.
3. Reads a candidate pointer from that slot.
4. Rejects a null candidate without reading the target’s first byte or calling F-000000000002.
5. For a non-null candidate, compares its first byte with the retained target’s first byte.
6. Rejects unequal first bytes without calling F-000000000002.
7. For equal first bytes, calls F-000000000002 with the candidate pointer first and target pointer second.
8. Returns the current index if that call returns zero.
9. Otherwise advances the index and repeats the bound check.

The relative order of the candidate-byte and target-byte reads is not established. Both occur before the comparison call when that call is reached.

Only zero versus nonzero matters for the comparison result. Positive and negative nonzero results both reject the candidate.

A successful comparison ends traversal immediately. No later bound check or candidate-slot access occurs.

### Candidate address arithmetic

Candidate slot calculations have established unsigned arithmetic behavior; they are not merely unspecified overflow cases.

Under the recovered 32-bit model, for each reached index:

- Multiplication of the unsigned index by four is performed modulo 2³².
- The loaded candidate-array base is converted to an unsigned 32-bit value for addition.
- Adding the slot displacement to that base is also performed modulo 2³².
- The resulting 32-bit value is used as the candidate-slot address.

Consequently:

- Index 0x40000000 produces a slot displacement of zero.
- Index 0x40000001 produces a slot displacement of four.
- For an unchanged base, indices differing by 0x40000000 calculate the same slot address.
- A non-wrapping multiplication can still be followed by a wrapping base addition.

Traversal remains ordered by the unsigned index, but the calculated addresses need not be distinct or numerically increasing. No extent check or wraparound rejection is visible.

These rules establish the calculated address, not the validity of dereferencing it. Whether storage exists there, whether a four-byte access is supported, and what happens on an invalid access remain undocumented.

### Index limits and termination

The index advances through unsigned 32-bit addition after each rejection.

The largest index that can satisfy the strict bound against any unsigned 32-bit count is 4,294,967,294. If that index is rejected, the next index is 4,294,967,295, which cannot be less than any representable count. Traversal then ends before another candidate access.

Therefore, the index cannot wrap back to zero through this traversal, and 4,294,967,295 cannot be returned as a successful index. This does not prevent the separate slot-address calculations from wrapping much earlier.

Subject to valid accesses and returning dependencies, there is no additional retry or restart mechanism.

### Live state and retained values

The collection is not captured as an entry-time snapshot:

- The count is read for every traversal decision.
- The candidate-array base is read for each candidate access that passes its bound check.
- The target pointer is obtained once and retained.
- The candidate pointer obtained for the current index is used for that candidate’s byte check and comparison call.

F-000000000001 can therefore affect the first observed count and candidate-array base. A rejecting F-000000000002 call can affect subsequent count checks and candidate accesses.

Retaining the target pointer does not freeze the target bytes. The first target byte is read again for each non-null candidate reaching the filter.

“First qualifying candidate” means the first qualifying index encountered under the values actually read during execution. It does not necessarily mean the first match in the collection as it existed on entry.

No synchronization or general concurrent-access guarantee is established.

## Side effects

The function itself performs no explicit writes to context fields, candidate slots, candidate bytes, or target bytes.

Its explicit operations include memory reads and dependency calls. It must not be treated as pure:

- F-000000000001 may change accessible state before traversal.
- F-000000000002 may change accessible state during traversal.
- Either dependency may have other observable effects.
- Neither dependency is established to preserve globals, context storage, candidate storage, or target storage.

There is no explicit allocation, release, ownership transfer, or reference-count operation in this function. The function itself does not free the target or candidates. This does not establish that dependencies leave ownership or lifetimes unchanged.

The first-byte filter constrains observable dependency calls. Even if F-000000000002 would accept two pointers with different first bytes, it is not called for that candidate.

There is no explicit handling for an unusable address, dependency failure, exception, or non-returning dependency. No particular failure result or recovery behavior is established.

## Dependencies

The following opaque IDs distinguish the observed dependency roles without claiming externally verified identities.

### F-000000000001

- **Dispatch:** Indirect, through context offset +20.
- **Input:** The selected two-byte table value.
- **Output use:** Retained as a pointer to byte-addressable target storage.
- **Invocation:** Once on an accepted-selector path that reaches and returns from resolution; never on a rejected-selector path.
- **Ordering:** Invoked before any candidate-count check.
- **Unknowns:** Meaning, argument extension, nullability, ownership, storage lifetime, side effects, and failure behavior.

A null result does not itself cause a return. It becomes relevant if a non-null candidate requires a target-byte read.

### F-000000000002

- **Dispatch:** Fixed comparison dependency.
- **Inputs:** Current candidate pointer first; retained target pointer second.
- **Output use:** Zero accepts the candidate; every nonzero value rejects it.
- **Eligibility:** Called only for non-null candidates whose first byte equals the target’s first byte.
- **Unknowns:** Comparison semantics, extent of reads, termination requirements, encoding, ownership effects, side effects, and failure behavior.

Neither dependency is assumed to preserve state or keep memory valid for subsequent accesses.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed tests. Except where an example concerns arithmetic alone, all reached accesses and calls must satisfy their validity requirements.

1. **Rejected selector**  
   With selector 256, return zero without reading context storage or calling either dependency. The context address need not be usable.

2. **Empty collection after resolution**  
   With an accepted selector and a count observed as zero after F-000000000001 returns, call that dependency once, read no candidate slot, call no comparison dependency, and return zero.

3. **Resolution changes the collection**  
   If F-000000000001 changes the count or candidate-array base, traversal uses the values subsequently read from the context, not their entry-time values.

4. **Null candidate**  
   With a stable count of one and a null pointer in slot zero, do not read the target’s first byte or invoke F-000000000002. Return zero after the next bound check.

5. **Different first bytes**  
   With non-null, readable pointers whose first bytes differ, reject the candidate without invoking F-000000000002. Continue if the next index remains below the next observed count.

6. **Equal first bytes, rejected comparison**  
   With equal first bytes and a nonzero comparison result, continue traversal. A negative result has the same rejection effect as a positive result.

7. **Successful later position**  
   With a stable count of four, rejected candidates at indices zero and one, and a qualifying candidate at index two, return two without accessing slot three.

8. **Successful position zero**  
   With a qualifying candidate at index zero, return zero immediately. The result alone does not distinguish this success from failure.

9. **Count reduced during comparison**  
   If comparison at index zero returns nonzero and changes the count to one, the next bound check terminates traversal. Slot one is not accessed.

10. **Candidate-array base changed during comparison**  
    If a rejecting comparison changes the base, the next candidate-slot calculation uses the newly read base.

11. **Null target with only null candidates**  
    If resolution returns null and every visited candidate is null, this function does not dereference the target. A later non-null candidate would require a target-byte read; there is no established null-target fallback.

12. **Wrapped candidate displacement**  
    If execution reaches index 0x40000000 and the observed count is greater than that index, the slot displacement is zero. The candidate slot is read at the currently loaded base, subject to address validity. The index is not rejected merely because multiplication wraps.

13. **Wrapped candidate-base addition**  
    A loaded base with unsigned value 0xFFFFFFFC and index two calculates slot address 0x00000004. This arithmetic result does not establish that address 0x00000004 is readable.

14. **Wrapped table-base addition**  
    A table base with unsigned value 0xFFFFFFF0 and selector eight calculates entry address zero: the displacement is 16 and the addition wraps modulo 2³². The function attempts the two-byte read there; normal completion depends on that address being usable.

## Uncertainties

The following remain **documented_only**:

- Independent ABI confirmation of integer widths, pointer representation, and calling conventions.
- Byte order and interpretation of the selected two-byte table value.
- Argument extension applied when passing that value to F-000000000001.
- Semantic meaning and allocated extent of the table and collection.
- Whether target and candidates represent strings, fixed-size records, or another format.
- Dependency identities beyond the opaque roles specified here.
- Ownership, storage lifetimes, and dependency allocation or release behavior.
- Consequences of invalid reads, invalid callable addresses, dependency failure, or non-return.
- Rules governing external mutation and synchronization.
- Validity and consequences of dereferencing an address produced by modular arithmetic.

The unsigned multiplication and base-addition rules are **established within the recovered 32-bit model**, not unresolved address-overflow behavior. Their results must be distinguished from the unknown usability of the resulting addresses.

The context-field offsets are established. This contract does not generalize the unsigned table and candidate calculations into a claim that every context-address calculation has the same unsigned arithmetic semantics.
