# F-d1bb3c5047e2

## Purpose

F-d1bb3c5047e2 conditionally removes a selected node from a pointer-linked structure, repairs selected links and color bytes, prepends the removed node to a container-associated chain, and decrements a 32-bit count-like field. A caller-provided output cell receives a locally held position value.

A preliminary dependency can bypass removal. On that path, the output receives the container’s header pointer as read after the dependency returns.

The structure resembles a red-black tree with a header and cached extremal pointers. That interpretation is inferred intent. The established contract consists of the accesses, branch conditions, mutations, and dependency interactions below; it does not establish balanced-tree correctness.

## Behavior

### Preliminary decision and position handling

The function first reads the selection cell into a local 32-bit position cell. It then reads the container’s header pointer into a separate local 32-bit cell. F-d5d901ed9cd8 receives the addresses of both local cells.

A nonzero dependency result bypasses removal. The function rereads the container’s header pointer, replaces the local position with that value, and assigns it to the output cell. There are no direct tree, chain, color, or count mutations on this path. Effects of F-d5d901ed9cd8 remain possible.

A zero result permits the removal path. F-2b3097eaee8e receives the address of the local position cell. After that call returns, the selected-node address is reread from the caller’s selection cell.

Thus:

- The initial selection value need not identify the node subsequently removed.
- The node to remove comes from the selection cell after both preliminary calls.
- The output comes from the local position cell at the final assignment.
- Neither preliminary dependency’s effects can be disregarded when specifying the subsequent topology or count.

The second local cell is not subsequently used as a stable header snapshot. Header-dependent operations read the container’s header field again.

### Structural removal cases

The selected node’s left link is inspected first. Its right link is then used to distinguish the remaining cases.

**Leaf.** With both children absent, the selected node’s parent becomes the retained repair position.

If that parent equals the then-current header, the direct stores set the header’s rightmost cache to the header address, then its leftmost cache to the header address, then its root field to zero.

Otherwise, the parent’s left link is compared with the selected node. A match causes the left link to be cleared; a nonmatch causes the right link to be cleared. Each clear consists of four single-byte zero stores in increasing address order. The corresponding header cache is then checked: leftmost for the matching-left branch, rightmost for the other branch. If that cache identifies the selected node, it is replaced with the parent.

The nonmatching branch does not independently verify that the parent’s right link identifies the selected node.

**Exactly one child.** The existing child is the replacement and retained repair position. Its parent field is first assigned the selected node’s parent. The current root field is then checked. If it identifies the selected node, it is replaced with the child. Otherwise, the selected node’s parent link is updated: left if that link matches the selected node, right otherwise.

The cached leftmost pointer is checked before the cached rightmost pointer:

- If the selected node is cached as leftmost and its right link is absent, leftmost becomes its parent. Otherwise, leftmost becomes the leftmost node reachable from the replacement.
- If the selected node is cached as rightmost and its left link is absent, rightmost becomes its parent. Otherwise, rightmost becomes the rightmost node reachable from the replacement.

These are the observed conditions, including their behavior on inconsistent caches; they are not replaced by a general “recompute extrema” rule.

**Two children.** The successor candidate is found by starting at the selected node’s right child and following left links until the current node has no left child. The candidate’s right child is its possible replacement at its former location.

The candidate is moved structurally into the selected node’s position. No payload copy is directly performed. The mutation order is significant:

- The selected node’s left child receives the candidate as parent, and the candidate receives the selected node’s left link.
- If the candidate is the immediate right child, a nonnull replacement receives the candidate as parent.
- Otherwise, a nonnull replacement receives the candidate’s former parent; that former parent’s left link receives the replacement; the candidate receives the selected node’s right link; and that right child receives the candidate as parent.
- The root or selected node’s parent link is redirected to the candidate, using the same left-match/right-fallback distinction.
- The candidate receives the selected node’s parent.
- The candidate’s color is saved, the candidate receives the selected node’s color, and the selected node receives the saved color.

If the candidate’s former replacement is null, the relocated candidate itself becomes the retained repair position. Otherwise, that replacement is retained. The null case must not be interpreted as retaining the candidate’s former parent.

The original selected node remains the node destined for the chain. In the two-child case, its color after the exchange controls repair entry. There is no direct extremal-cache update in this structural branch.

### Repair entry and termination

After structural removal, the header pointer is reread. Repair is entered only if the retained repair position differs from that header and the removed node’s current color is nonzero. The removed-node color is not needed when the position equals the header.

If repair is skipped, there is no final repair-position blackening.

Within entered repair, each iteration first checks the position against the root obtained through the current container header. Equality ends the loop without needing the position’s color for that condition. Otherwise, a position color other than exactly 1 also ends the loop.

Every normal exit from entered repair writes color 1 to the current repair position.

### Repair cases and dependency mapping

For a nonroot position colored exactly 1, the parent is read. Equality with the parent’s left link selects the left-side branch. A nonmatch selects the mirrored branch without a separate right-link membership check.

“Near child” means the sibling child toward the repair position; “far child” means the other child.

| Repair-position side | Sibling | Near child | Far child |
|---|---|---|---|
| Parent’s left child | Parent’s right child | Sibling’s left child | Sibling’s right child |
| Mirrored branch | Parent’s left child | Sibling’s right child | Sibling’s left child |

The established call-site mapping is:

| Case | Left-side branch | Mirrored branch |
|---|---|---|
| Sibling color is 0 | F-a3d85cb09a50(container, parent) | F-d202fbc49f1c(container, parent) |
| Near-child adjustment | F-d202fbc49f1c(container), one explicit argument | F-a3d85cb09a50(container), one explicit argument |
| Final balancing | F-a3d85cb09a50(container, parent) | F-d202fbc49f1c(container, parent) |

These are explicit call-site distinctions, not claims about complete dependency signatures.

**Missing sibling.** The current repair position is colored 0, and repair continues at the retained parent. If a sibling disappears after the zero-colored-sibling call, this path uses the parent reloaded after that call.

**Sibling color 0.** The sibling is colored 1, then the parent is colored 0. The corresponding two-argument call above occurs. The parent is then reloaded through the repair position’s parent field, and the sibling is reloaded through that parent. A null sibling takes the missing-sibling path.

**Both sibling children absent or exactly color 1.** The near child is considered first. Only if it is absent or exactly color 1 is the far child examined for this combined condition. When both qualify, the sibling is colored 0 and repair continues at the position’s parent, read again from the position.

**Far child absent or exactly color 1, without the preceding combined condition.** The nonnull near child is colored 1, then the sibling is colored 0. The corresponding one-explicit-argument near-child call occurs. The sibling is subsequently reloaded through the repair position’s then-current parent. If it is null, repair exits to the final position-blackening store.

**Final balancing.** The sibling receives the current parent’s color. The parent is then colored 1, followed by the nonnull far child. The corresponding final two-argument call occurs, and repair exits to position blackening.

Far-child fields and colors are read again where the later decisions require them; they are not universally cached from the combined-child test. Dependencies may change the memory used by subsequent reloads. No conventional rotation postcondition is substituted for those actual reads.

### Chain insertion, decrement, and output

After structural work and any entered repair, the direct operations occur in this order:

1. The current container chain head is read and stored into the removed node’s +12 field.
2. The removed node’s address is stored as the container chain head.
3. The current 32-bit count-like field is read, decremented, and stored.
4. The current local position-cell value is assigned to the output cell.

The decrement is a 32-bit operation with no zero check or saturation. A value of zero at the decrement produces the all-ones 32-bit pattern. No checked-underflow result or error status is established.

The output is not unconditionally the value present immediately after F-2b3097eaee8e. Later dependencies may affect accessible state, including escaped local-cell storage. The contract fixes the output’s observation point at the final assignment.

## Acceptance examples

These are conditional static scenarios, not executed tests. They assume accessible, nonoverlapping storage, no external concurrent mutation, and normal dependency returns. Conditions on topology apply when the function reads that topology after the preliminary calls, not merely at entry. Count and chain assumptions apply at their respective final reads.

### Preliminary bypass

If F-d5d901ed9cd8 returns nonzero and the container’s header field contains address H when reread:

- The output assignment stores H.
- F-2b3097eaee8e is not called.
- This function performs no direct tree, chain, color, or count updates.

The preliminary dependency may itself have changed those fields.

### Removing the sole node

After both preliminary calls, suppose the selection reread identifies node N, both child reads yield zero, N’s parent and the current header are H, and the count is one when decremented.

The direct stores set H’s rightmost cache to H, then its leftmost cache to H, then its root to zero. Repair is skipped because the retained position is H. N is prepended to the chain, and the count becomes zero. The output receives the local position value at the final assignment.

Entry-time topology and count alone do not establish this outcome: either preliminary dependency could alter them before observation.

### Removing a root with only a right child

After the preliminary calls, suppose N is the root, its parent is H, its left child is absent, and its sole right child R is a leaf. Let leftmost be N, rightmost be R, and N’s color be 0.

R receives parent H and becomes the root. Leftmost becomes R; rightmost remains R. Repair is skipped because N’s color is zero. N becomes the chain head. The count is decremented from its value at that later read.

### Two children with a null successor replacement

After the preliminary calls, suppose root N has left child L and right child R; R’s left child S has no children. Let N’s color be 0, S’s color be 1, and the links consistently identify these relationships.

S is detached by clearing R’s left link and is moved to the root with children L and R and parent H. N receives color 1; S initially receives color 0. Because S’s former replacement is null, S itself is the repair position. Entered repair immediately recognizes S as root and writes color 1 to S, without a repair dependency call. The original N is chained.

### Repair call orientation

At a repair iteration where the position is the parent’s left child and the sibling is color 0, the sibling becomes 1 and the parent becomes 0 before F-a3d85cb09a50(container, parent) is called.

The mirrored case calls F-d202fbc49f1c(container, parent). A later near-child adjustment instead uses the one-explicit-argument call shown in the mapping table. No post-call topology is accepted without an additional dependency-effect condition.

### Late count and output observations
