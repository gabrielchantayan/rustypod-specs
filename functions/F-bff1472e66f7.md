# F-bff1472e66f7

## Purpose

F-bff1472e66f7 obtains a candidate associated with a context. Context fields determine whether it delegates acquisition or attempts construction. A successful delegated result is published directly. Successful construction includes two allocation-like requests, initialization, insertion into a context-held linked structure, and publication.

The visible behavior establishes:

- Short-circuit selection between delegation and construction.
- Conditional capacity adjustment.
- Unsigned, modulo-\(2^{32}\) computation of the first construction request size.
- Cleanup of the first allocation-like result when the second request fails.
- A maintenance call after every construction allocation attempt.
- Explicit object-field, context-field, and output-slot writes.
- Separate handling of delegated status `5`, other nonzero delegated statuses, and local construction failure.

“Acquisition,” “allocation,” “capacity,” and “maintenance” are inferred roles. They do not establish dependency semantics or ownership rules.

## Interface

### Inputs

The supplied representation exposes four arguments:

1. **Context address:** a 32-bit address used for the field accesses below.
2. **Output-slot address:** an address receiving one 32-bit candidate address on the common success path.
3. **Opaque 32-bit value:** not directly used by the visible body.
4. **Initial candidate address:** a pointer-shaped value copied into a local candidate slot.

The initial candidate is not directly dereferenced. Delegation receives the address of the local slot and can replace its contents. Construction replaces the slot with the first allocation-like result.

No direct argument validation is visible. The context must support every access reached on the selected path. The output slot must support a 32-bit write if publication is reached.

### Return value

The result is represented as a 32-bit integer:

| Condition | Result |
|---|---|
| Common success path | `0` |
| Local construction failure | `7` |
| Delegated status other than `0` or `5` | That status, unchanged |
| Delegated status `5` | Value read from a separate stored location whose contents are not supplied |

The special status-`5` return is not established as success or failure. Its value may coincide numerically with another return category without following that category’s publication behavior.

## Behavior

### 1. Establish the candidate and select a path

The initial candidate address is copied into a local slot. This is not a write to the caller’s output slot.

Construction is selected if any of the following holds:

1. The signed 32-bit value at `0x44` is less than the signed 32-bit value at `0x4c`.
2. The word at `0x7c` is zero.
3. The byte at `0x14` is nonzero.
4. The word at `0x84` is zero and the byte at `0x16` is nonzero.

Evaluation short-circuits in that order. Thus:

- The comparison is evaluated first.
- `0x7c` is consulted only if the comparison is false.
- `0x14` is consulted only if both preceding conditions are false.
- `0x84` is consulted only if the first three conditions are false.
- `0x16` is consulted only if evaluation reaches the last condition and `0x84` is zero.

The supplied expression does not establish the relative order of the two reads within the first comparison.

Delegation is selected only when every construction condition is false.

### 2. Delegated acquisition

F-26ff4a9b1180 receives the context address and the address of the local candidate slot. The dependency can replace the candidate.

Its returned status controls completion:

- **`5`:** read and return the separate stored value immediately, without direct output publication.
- **Other nonzero value:** return that status immediately, without direct output publication.
- **`0`:** write the current candidate to the output slot and return `0`.

There is no candidate-validity or nonnull check after delegated success. A dependency that returns `0` with a null candidate causes null to be published.

The dependency’s effects on the context, global state, resources, or aliased storage are not established.

### 3. Construction capacity decision

The function reads the signed 32-bit capacity value at `0xcc`, then compares the signed value at `0x44` against it.

If the value at `0x44` is strictly less than capacity, construction proceeds without adjustment.

Otherwise, the requested capacity is:

- `256` if the old capacity is signed-less-than `256`.
- The old capacity shifted left by one bit otherwise.

F-7aaf25e11a19 receives the context and that request. Its return value is ignored.

The function then rereads `0xcc`:

- Zero causes return `7`.
- Any nonzero value permits construction.

There is no repeated comparison against `0x44`. A nonzero post-call capacity permits construction even if it remains equal to or below the counter, including when it is negative under signed interpretation.

The early return caused by a zero capacity occurs before the decrement, allocation-like requests, and maintenance call described next.

### 4. Decrement and compute the first request size

The function first reads, decrements, and writes the 32-bit field at `0xe0`.

It then computes and retains the first request size using the base field at `0x3c` and an unsigned-byte read of `0x14`. These are fresh reads after any capacity-adjustment call. Their relative evaluation order is not established.

Let:

- \(B_u\) be the base field converted to an unsigned 32-bit value.
- \(f\) be the unsigned byte, from `0` through `255`.

The unsigned expression result is:

\[
R = (B_u + 20f + 60) \bmod 2^{32}.
\]

The explicit unsigned conversion of the byte makes the multiplication and both additions unsigned 32-bit operations. The base participates through unsigned conversion. Consequently, this expression has defined modulo-\(2^{32}\) arithmetic; it is not part of the unresolved signed-overflow behavior of the counter updates or capacity shift.

The product \(20f\) ranges from `0` through `5100` and cannot itself overflow 32 bits. The additions can wrap. The byte is not normalized to a Boolean: `2` contributes `40`, while `255` contributes `5100`.

The result is stored in a signed 32-bit temporary. If \(R\) is at most `0x7fffffff`, it is representable there. If its high bit is set, the supplied evidence does not establish the signed-conversion convention or how the receiving dependency interprets the resulting argument. This uncertainty concerns storage and consumption of the result, not whether the preceding unsigned arithmetic wraps.

The retained value is used for the first allocation-like call and, if construction succeeds, for initialization. It is not recomputed after intervening calls.

### 5. Attempt the allocation sequence

F-391e3d30e634 is called with the retained first request size. Its result replaces the candidate.

If that result is null, the second request is skipped.

If it is nonnull, the function reads the 32-bit field at context offset `0x40` and calls F-391e3d30e634 again with that value. This read occurs after the first call; changes made by that call can affect the second request argument.

If the second result is zero:

1. F-94cb53877c15 receives the first result.
2. The local candidate is set to null after that call returns.

The function then calls F-b93e3fe564f6 with the context in all three allocation outcomes:

- First request failed.
- First request succeeded and second request failed.
- Both requests succeeded.

No assumption is made that this maintenance dependency preserves the context or either resource.

### 6. Reject or complete construction

After maintenance returns, a null candidate causes return `7`.

A nonnull candidate is passed, together with the retained first request size, to an initialization dependency for which no opaque ID was supplied. Its memory effects and return semantics are unknown. In particular, zero-initialization is not established.

After that call returns, the function performs these operations in order:

1. Write the context address at object offset `0x00`.
2. Write the second allocation-like result at object offset `0x34`.
3. Read context offset `0x88` and write that head address at object offset `0x18`.
4. Write the candidate address to context offset `0x88`.
5. Read, increment, and write the 32-bit field at context offset `0x44`.
6. Write the candidate address to the output slot.
7. Return `0`.

The head used for insertion is the value present after initialization, not a snapshot from before allocation or maintenance. Similarly, the increment uses the counter value present at that late point.

## Acceptance examples

These are conditional static examples, not executed tests. They assume normal dependency returns and valid storage for every reached access. Examples requiring stable fields explicitly exclude intervening changes to those fields.

### Delegated success, including null

The first request therefore receives the representable retained value `44`. No signed-overflow uncertainty applies to this calculation.

This example does not establish safe successful construction: the explicit object writes require storage through offset `0x37`, which a literal 44-byte allocation would not provide.

### High-bit arithmetic result

### Allocation failures

If the first request returns null, the second request is skipped, maintenance still runs, and the function returns `7` without direct publication.

If only the second request returns zero, cleanup of the first result precedes maintenance. The function then returns `7` without initialization or insertion. Neither case explicitly restores the earlier decrement.
