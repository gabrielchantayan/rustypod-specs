# F-29d0725269fe

## Purpose

The supplied static representation describes a state-mutating execution fragment that interleaves indirect calls with byte and 32-bit memory accesses. Its visible work includes copying low bytes from word-sized fields, updating small-address byte locations, storing scaled values into word-sized fields, and passing transformed values to unresolved dependencies.

A higher-level purpose is not established. In particular, the representation does not establish that this is a complete callable routine, an object-management operation, a serializer, or an allocator.

The visible path ends at an invalid-instruction boundary, not at a normal return. This contract therefore describes the ordered effects of the represented fragment, conditional on reaching each effect. It does not promise successful completion or a recoverable error result.

### Width and arithmetic model

The visible representation distinguishes:

- 8-bit byte loads and stores.
- 32-bit word loads, stores, addresses, and most intermediate quantities.
- 64-bit call results subsequently split into low and high 32-bit halves.

Byte loads used in address calculations are zero-extended. Byte stores retain only the low eight bits of the supplied value.

Unsigned right shifts are logical. Important masks include:

- `0x7fffffff`: removes bit 31.
- `0x3fffffff`: retains the low 30 bits.
- `0x07ffffff`: retains the low 27 bits.
- `0x1ff`: retains nine bits.

Left shifts and scaling must not be interpreted as arbitrary-precision arithmetic. Several expressions are represented using signed 32-bit intermediates, including multiplication by four and left shifts. Exact overflow behavior requires instruction-level evidence. Examples below either avoid overflow or explicitly condition their conclusions on a 32-bit bit-vector interpretation.

## Behavior

### Interpretation of ordering

The supplied representation presents one straight-line path, without visible loops or conditional branches. Its effects are described below in their represented order.

Calls between memory operations are observable boundaries. A later load must not be replaced by a previously loaded value merely because its address expression looks unchanged. An unresolved dependency may modify memory, globals, external state, or control flow.

For clarity, **byte-selected destination** means the following address relationship: load one unsigned byte from a specified address, then use that byte’s numeric value plus `0x11` as a destination address. This is not a pointer-sized load and not an offset within the original record.

### Entry propagation and initial byte updates

Before the first call, the fragment reads a 32-bit word at record base `+0x74` and writes its low byte to record base `+1`.

The first dependency receives four explicit 32-bit values, in order:

1. Twice the incoming seed.
2. The second explicit argument.
3. The incoming seed logically shifted right by two.
4. The incoming record base.

A following dependency supplies a 64-bit result. Another call receives its low half, its high half, its low half again, and the incoming seed with bit 31 removed and then shifted right by one.

After additional calls, a returned word is scaled by four to form another base. The fragment reads the word at that base `+0x74`, copies its low byte to base `+1`, and passes the scaled base to a dependency.

The fragment next reads the byte at twice the incoming seed plus one. It writes zero to the corresponding byte-selected destination. A dependency then receives a secondary-register value whose provenance is not fully represented.

A later returned word becomes a retained **carrier base** and is passed to another dependency. After more calls, the fragment reloads the byte at twice the incoming seed plus one and writes the high byte of the doubled seed to the newly selected destination. The two destination selections are independent loads; intervening dependencies may change the selector.

### Carrier traversal and word-to-byte copying

A later result is scaled by four to form a **working base**. The fragment then:

- Reads a 32-bit **carrier word** from carrier base `+4`.
- Loads the byte at carrier word `+1`.
- Clears the destination selected by that byte.
- Calls a dependency with the working base repeated three times.

After further calls, it reads a byte at `(carrier word logically shifted right by two) +1`. This byte becomes a retained **small base**. The fragment clears small base `+0x11`, then calls a dependency with a newly returned word shifted left by two.

Next, two 32-bit words are read in order:

1. A **packed word** from working base `+4`.
2. A **linked word** from small base `+0x74`.

The linked word’s low byte is written to small base `+1`. The next four-argument call receives the linked word, the working base shifted left by 19 twice, and a recent dependency result shifted left by two.

A later call receives a fresh result and the linked word logically shifted right by two.

### Packed-field writes and scaled records

Another returned word is multiplied by four to form a **copy base**. The fragment reads copy base `+0x74`, saves the full 32-bit value, and writes its low byte to copy base `+1`. A dependency receives the copy base.

After intervening calls, the saved full word is written at an address formed from a secondary-register value multiplied by four, plus `0x14`. That secondary-register value is also passed to a dependency.

The earlier packed word is logically shifted right by 22, producing a value in the range 0 through 1023. Two uses follow:

- Its low nine bits are shifted left by 21 and supplied twice to a dependency, after another dependency result.
- The full shifted value is shifted left by 23 and stored at four times a later returned word, plus `0x14`.

These expressions have different bit-selection behavior. Under 32-bit truncation, the second expression retains only the low nine bits in the stored result.

A subsequent dependency result supplies a **record index**. Before masking that index, the fragment stores four times the index at 16 times the index plus `0x14`.

It then retains the index’s low 30 bits as the **masked index**, computes the masked index shifted right by two for later use, and passes the masked index to a dependency.

After further calls, the masked index is stored at four times a returned **slot index**, plus `0x14`. Four times that slot index is passed to the next dependency.

### Paired writes around the `+0x34` field

A later 32-bit result supplies a **link value**. Eight times the slot index becomes a **pair base**.

The fragment writes:

- The pair base’s low byte to linked word `+1`.
- The link value shifted left by two to pair base `+0x34`.

The shifted link value is then passed to a dependency.

The low 30 bits of the link value form a **link base**. After another call sequence yields a 64-bit result, the fragment writes:

- The pair base’s low byte to link base `+1`.
- The result’s high 32-bit half to pair base `+0x34`.

The result’s low half shifted left by two is passed to the next dependency. The second `+0x34` store is a distinct observable write; it does not erase the observability of the earlier store.

### Small-address markers and scaled payload fields

Sixteen times the slot index becomes a **payload base**. The fragment writes:

- The payload base’s low byte to `((link value masked to 30 bits) logically shifted right by 20) +0x11`.
- The low byte of four times the earlier record index to payload base `+0x0d`.

A recent result shifted left by two is passed twice to a dependency. Another dependency supplies a word that is forwarded together with its logical right shift by three.

After intervening calls, the fragment writes the payload base’s low byte directly to absolute address `0x11`, then repeats the payload base `+0x0d` store.

Following another call sequence, it writes:

- Four times the earlier record index as a 32-bit word at link base `+0x14`.
- The low byte of twice the link base at link base `+0x0d`.

A newly returned **payload value** supplies:

- A new base equal to payload value multiplied by 32.
- A word value equal to payload value shifted left by seven.
- A small selector equal to the low 27 bits of payload value, shifted right by 17.

After three more calls, a fresh result is available. The fragment stores the shifted payload word at new base `+0x14` and the low byte of the fresh result shifted left by two at new base `+0x0d`. That shifted result is passed to a dependency.

After another group of calls:

- The low byte of twice the earlier masked-index-right-shift result is written at small selector `+7`.
- The byte at new base `+1` is loaded, and the small selector’s low byte is written to its byte-selected destination.
- The fresh result shifted left by 21 is passed three times to a dependency.

### Selector snapshot and absolute byte marker

A later dependency returns a **status word**, which is forwarded to another dependency. After further calls, the fragment snapshots the byte at new base `+1` and clears its byte-selected destination.

This snapshot is retained across subsequent calls. It is not reloaded for the following uses.

The fragment then writes:

- The low byte of status word logically shifted right by three to new base `+0x0d`.
- The saved selector byte to absolute address `0x0d`.

A dependency receives twice the saved selector, `0x98`, and `0x260`. Subsequent calls include one receiving a secondary-register value logically shifted right by three, and another receiving a returned word shifted left by two.

The low byte derived from the status word is then written at twice the saved selector plus `0x0d`. Absolute address `0x0d` is overwritten with `0xc0` before the next dependency call.

### Final word propagation and repeated destination clears

A later result is shifted left by two and stored at twice the saved selector plus `0x24`. The fragment reads a 32-bit **tail base** from twice the saved selector plus `0x74`.

A four-argument dependency receives:

1. The tail base.
2. The tail base shifted left by one.
3. The preceding result shifted left by five.
4. The tail base with bit 31 cleared, then logically shifted right by two.

After more calls, the preceding result shifted left by five is stored at tail base `+0x24`. The word at tail base `+0x74` is then loaded and passed to a dependency.

A subsequent 64-bit result supplies:

- A low half shifted left by two, retained as a **tail payload**.
- A high half used to select a destination at four times that half plus `0x14`.

The status word logically shifted right by three is written to that destination. A dependency receives the tail payload three times and the high half logically shifted right by three.

Another 64-bit result is passed onward as low half, high half, low half again, and high half logically shifted right by three. A later returned word selects a destination at four times that word plus `0x14`, where the tail payload is stored.

A final returned **tail value** drives the remaining byte effects:

- Its left shift by two is reduced to a byte and written to the destination selected by a fresh byte load from tail base `+1`.
- After calls, the selector at tail base `+1` is loaded again. Its destination receives the low byte of the tail value masked to 30 bits and logically shifted right by 20.
- A byte is loaded at 1024 times the tail value shifted left by two, plus one. Its selected destination is cleared.
- A dependency receives the tail value shifted left by five twice, the tail value shifted left by two, and another result shifted left by two.
- After further calls, the large scaled selector address is read again and its selected destination is cleared again.
- A final sequence of indirect calls precedes the invalid-instruction boundary.

Neither repeated clear can be removed from the behavioral description: intervening dependencies may change the selector or observe the earlier write.

## Side effects

All visible stores are immediate memory effects. There is no visible transaction, rollback, synchronization primitive, or deferred commit.

The fragment performs partial-byte updates alongside full-word updates. Fields sharing storage, overlapping computed addresses, and aliases between nominal bases can therefore affect later behavior. Distinct descriptive names do not imply distinct allocations.

The direct stores to absolute addresses `0x0d` and `0x11` are part of the represented behavior. Whether those addresses denote ordinary storage, device state, aliases, or invalid memory is unknown.

No explicit allocation, release, ownership transfer, or reference-count operation is established. Values are passed to unresolved dependencies, but neither their numeric form nor their use as addresses proves ownership. Dependencies must not be assumed to preserve globals, preserve pointed-to storage, or refrain from releasing memory.

## Acceptance examples

These are conditional static examples, not executed tests.

1. **Initial low-byte copy.** If the initial word at record base `+0x74` is `0x123456ab`, the first visible store writes `0xab` to record base `+1`, before the first dependency executes.

2. **Byte-selected destination.** If a selector load returns `0x80`, its destination is address `0x91`. It is not the selector’s source address plus `0x11`.

3. **Changed selector across calls.** If the first doubled-seed selector load returns 2 and the later load returns 5, the initial clear targets `0x13` and the later high-byte write targets `0x16`.

4. **Nine-bit packed result.** If the packed word shifted right by 22 equals `0x200`, the explicitly nine-bit-masked argument is zero. Under 32-bit truncation, shifting the unmasked `0x200` left by 23 also produces zero. A wider-integer implementation would not be equivalent.

5. **Snapshot retention.** If the saved selector is 7, the later three-argument call receives 14, `0x98`, and `0x260`. A dependency changing the original selector memory does not change that retained value.

6. **Absolute marker order.** If execution reaches both absolute-address stores without intervening failure, address `0x0d` first receives the saved selector byte and later receives `0xc0`. This does not establish its final value after subsequent dependencies execute.

7. **Split-result placement.** For a paired 64-bit result with low half 3 and high half `0x11223344`, the corresponding pair-base `+0x34` store writes `0x11223344`, while the next shifted argument is 12.

8. **Inaccessible destination.** If a required destination is unmapped, no visible check converts that condition into a defined error return. Any fault behavior depends on the execution environment.
