# F-1f3366eda5f7

## Purpose

F-1f3366eda5f7 conditionally issues up to two adjustment requests through an object’s indirect dispatch table, then returns a packed pair of 32-bit values.

The adjustment calculations are consistent with centering an object’s nonzero horizontal and vertical spans inside bounds obtained from an associated record. That geometric interpretation is inferred intent. The established behavior is narrower: field tests, arithmetic on stored 32-bit values, and indirect calls with one computed adjustment argument at a time. The supplied evidence does not establish what those calls actually do.

The return value is not a success indicator. Its two components are selected before any adjustment call:

- Without an enabled, nonzero associated-record reference, the components are the incoming object reference and the second argument.
- With such a reference, the components come from two fields in that record.

No runtime tests have been performed.

## Interface

### Inputs

1. **Object reference.** A reference to storage containing 32-bit fields and an indirect dispatch-table reference.
2. **Secondary value.** A 32-bit integer. It supplies the upper half of the return value only when the associated-record path is not selected.

No null check, bounds check, object-type check, or dispatch-target validation is visible.

### Output

The function returns a 64-bit bit pattern formed by concatenating two 32-bit components:

| Component | Associated-record path not selected | Associated-record path selected |
|---|---|---|
| Bits 31–0 | Incoming object-reference representation | Record field at byte offset `0x80` |
| Bits 63–32 | Incoming secondary value | Record field at byte offset `0x84` |

The concatenation describes bit significance, not byte order in memory. Signed-looking component values retain their 32-bit representations; the function does not numerically add them together or report adjustment-call results.

The source presentation treats object and record references as fitting in 32-bit quantities. A 32-bit pointer model is therefore strongly indicated, but the target ABI is not independently supplied. Porting this behavior to wider pointers requires an explicit representation decision rather than assuming pointer widening preserves the contract.

## Behavior

### Path selection and return-component capture

The function first reads the object flags at `0x48` and tests bit `0x100`. Other bits do not affect this decision.

If that bit is clear:

- The associated-record field is not needed.
- Neither adjustment branch is entered.
- The return value contains the incoming object-reference representation in its lower half and the secondary value in its upper half.

If the bit is set, the associated-record reference at `0x34` is read. A zero reference produces the same return selection and absence of adjustment calls as the disabled case.

For a nonzero reference, the function captures record fields in this order:

1. Field `0x80`, retained as the lower return component and the vertical container origin.
2. Field `0x84`, retained as the upper return component and the horizontal container origin.
3. Field `0x88`, retained as the vertical container ending bound.

These captures precede both adjustment branches. In particular, the vertical ending bound is read even when later object fields suppress every adjustment.

After this selection, the incoming secondary value does not participate in either adjustment calculation or the returned components.

### Horizontal adjustment

Horizontal processing occurs before vertical processing.

The function reads the object’s horizontal suppression field at `0x5c`. A nonzero value suppresses the entire horizontal request, including reads of horizontal flags and bounds.

When the suppression field is zero, the function reads horizontal flags at `0x60`. If bit `0x40` is clear, no horizontal bounds are needed and no horizontal call occurs.

When that bit is set, the function reads:

1. The object’s horizontal starting bound at `0x84`.
2. The object’s horizontal ending bound at `0x8c`.

The horizontal span is their 32-bit difference, ending bound minus starting bound. If its bit pattern is zero, no horizontal call occurs. There is no requirement that the span be positive.

For a nonzero span, the associated record’s right bound at `0x8c` is read. The horizontal adjustment is:

\[
\text{saved left}
+\operatorname{half}(\text{record right}-\text{saved left})
-\operatorname{half}(\text{object horizontal span})
-\text{object horizontal start}
\]

Here, \(\operatorname{half}\) denotes signed division by two, truncating toward zero in the supplied expression.

The indirect dependency is then invoked with three presented arguments:

1. The original object reference.
2. The computed horizontal adjustment.
3. Zero.

A computed adjustment of zero does **not** suppress the call. Eligibility depends on the suppression field, flag bit, and nonzero span, not on whether movement would be necessary under the inferred geometric interpretation.

### Vertical adjustment

Vertical processing follows the horizontal branch, including any horizontal callback.

The function reads the object’s vertical suppression field at `0x50`. If nonzero, vertical processing stops.

Otherwise, it reads vertical flags at `0x54`. If bit `0x40` is clear, no vertical bounds or callback are needed.

With the bit set, it reads:

1. The object’s vertical starting bound at `0x80`.
2. The object’s vertical ending bound at `0x88`.

Their 32-bit difference is the vertical span. A zero span suppresses the vertical call; a nonzero span, including a negative signed interpretation, permits it.

The vertical adjustment is:

\[
\text{saved top}
+\operatorname{half}(\text{saved bottom}-\text{saved top})
-\operatorname{half}(\text{object vertical span})
-\text{object vertical start}
\]

The indirect dependency is invoked with:

1. The original object reference.
2. Zero.
3. The computed vertical adjustment.

The dispatch table and callable entry are resolved for this invocation; the function does not establish a single immutable target shared by both calls.

### Arithmetic boundaries

The field arithmetic is presented as 32-bit arithmetic, not widened 64-bit geometry. Span differences are first held as 32-bit unsigned quantities, tested for zero, and then interpreted as signed 32-bit values for division.

Consequences include:

- A span with its high bit set is not treated as a large positive magnitude during division.
- Negative odd values divide toward zero rather than toward negative infinity.
- Halving the container span and object span separately can differ from halving their difference.
- There is no visible clamp, normalization, positive-size check, or saturation.

Overflow behavior beyond the supplied source presentation is `documented_only`. The evidence does not independently establish target-instruction behavior for every overflowing signed intermediate. Examples below avoid that ambiguity.

## Acceptance examples

These are conditional acceptance cases derived from the static evidence, not executed tests. Callback examples assume valid storage and normal callback return.

### Disabled association

Given an object-reference representation of `0x00001000`, a secondary value of `0x12345678`, and bit `0x100` clear at object offset `0x48`:

- No associated-record dereference or adjustment call is required.
- The return bit pattern is `0x1234567800001000`.

### Enabled association with a zero reference

Given bit `0x100` set but a zero associated-record reference:

- Neither adjustment branch runs.
- The return components remain the incoming object reference and secondary value.
- There is no fallback lookup.

### Captured return pair despite suppression

Given a valid enabled record whose `0x80`, `0x84`, and `0x88` fields contain 20, 10, and 220, with both object suppression fields nonzero:

- Those three record fields are still captured.
- No adjustment call occurs.
- The return bit pattern is `0x0000000a00000014`.
- The record’s right-bound field is not needed by either adjustment calculation.

### Both adjustments eligible

Suppose the captured container bounds are left 10, top 20, right 110, and bottom 220. Both suppression fields are zero and both relevant flag bits are set.

With object horizontal bounds 30 and 50, the horizontal span is 20 and the requested horizontal adjustment is:

\[
10 + 100/2 - 20/2 - 30 = 20
\]

The first call receives the object, 20, and zero.

If that callback leaves the subsequently read vertical fields unchanged, and those fields contain bounds 40 and 80, the vertical span is 40. The requested vertical adjustment is:

\[
20 + 200/2 - 40/2 - 40 = 60
\]

The second call receives the object, zero, and 60. The packed return remains the saved pair, not either adjustment.

### Zero span versus zero adjustment

With horizontal eligibility flags satisfied:

- Equal horizontal start and end bounds suppress the horizontal call.
- A nonzero span that produces an adjustment of zero still causes a call with both numeric adjustment arguments zero.

Thus, observing zero-valued adjustment arguments does not establish which axis caused the call.

### State change between axes

If the horizontal callback sets the vertical suppression field to a nonzero value, the subsequent vertical check suppresses the vertical call.

If it instead changes the record’s top or bottom, those changes do not replace the already captured top and bottom used by this invocation.

### Signed odd span

For a vertical container from 0 to 10 and object bounds from 4 to 1, the object span is −3. With vertical eligibility satisfied:

\[
0 + 10/2 - (-3)/2 - 4 = 2
\]

The result uses \((-3)/2=-1\), not −2. Reversed bounds are not explicitly rejected.
