# F-5719df83e333

## Purpose

F-5719df83e333 writes an incoming integer through a destination pointer stored in a caller-provided record, and updates a 16-bit field in that record to indicate whether the incoming integer is nonzero.

For ordinary, nonoverlapping storage, the resulting relationship is:

- The indirect destination contains the incoming integer.
- The record’s leading field contains zero if the incoming integer is zero, or one otherwise.

The order of operations is part of the contract: the leading field is cleared **before** the embedded destination pointer is read, and the nonzero indicator is written **after** the indirect destination write. Aliasing can therefore change the outcome from the simple relationship above.

This describes the supplied static evidence. No runtime tests have been performed.

## Interface

### Inputs

The function has two inputs:

1. **Incoming integer.** An integer value used both for a zero comparison and as the value written to the indirect destination.
2. **Record address.** A caller-supplied address identifying writable storage with the layout described below.

There is no explicit length, destination capacity, ownership indicator, or error-output argument.

### Record layout

Offsets are measured in bytes from the supplied record address.

| Offset | Field | Access |
|---|---|---|
| 0 | Two-byte indicator | Always written with zero; subsequently written with one on the nonzero branch |
| 2 | Two-byte intervening region | No explicit access |
| 4 | Embedded pointer to the integer destination | Read after the initial indicator write |

The pointer field begins at offset 4 because its location is two two-byte units beyond the record base.

The intervening region is not established to be padding, a reserved field, or an independent application field. Only its position and lack of explicit access are established.

### Widths and representation

The leading field is exactly two bytes, corresponding to the 16-bit indicator represented in the supplied material. Its assigned numeric values are zero and one.

The incoming integer and indirect destination use the same integer type in the supplied representation. Their exact bit width is not independently specified. A 32-bit integer interpretation is plausible, but must remain conditional rather than a portability guarantee.

Likewise, the embedded pointer’s width is not established. Its **offset** is fixed by the shown address calculation; its storage size and alignment requirements depend on the target execution model.

Under a 32-bit-integer, 32-bit-pointer interpretation:

- The indicator occupies bytes 0–1.
- The intervening region occupies bytes 2–3.
- The embedded pointer occupies bytes 4–7.
- The indirect destination receives a four-byte integer write.

These sizes beyond the indicator are conditional acceptance assumptions, not additional established facts.

### Return and ownership

The function returns no result value. It does not return either input or the indirect destination address.

No allocation, deallocation, ownership transfer, or retained pointer is explicitly present. The caller must supply storage suitable for the accesses made during the call. The function does not establish how that storage was obtained or who must eventually release it.

## Behavior

### Ordered operations

The statically established access sequence is:

1. Write numeric zero to the two-byte indicator at record offset 0.
2. Compare the incoming integer with zero.
3. Read the embedded destination pointer from record offset 4.
4. Write an integer to the destination identified by that pointer:
   - For a zero input, write zero.
   - For a nonzero input, write the incoming integer unchanged.
5. On the nonzero branch only, write numeric one to the two-byte indicator.

No explicit read of the indicator’s original value occurs. The function does not preserve that original value.

The embedded pointer is not obtained before the initial indicator write. This matters if the write affects how the pointer field is subsequently observed, whether through an unusual storage arrangement, mapped-memory behavior, or another execution environment feature.

This ordering describes the supplied operation sequence. It does not establish machine-level atomicity, synchronization semantics, or observable access granularity for concurrent observers.

### Zero input

For a zero input, the function first clears the indicator, then writes zero to the indirect destination. There is no final indicator write.

With valid, ordinary, nonoverlapping storage, both the indicator and the indirect destination therefore contain zero when the function returns.

The indirect write still occurs when the input is zero. Zero is not treated as a request to skip destination access, and a zero input does not make an invalid embedded pointer safe.

### Nonzero input

For any nonzero input, the function first clears the indicator, writes the incoming integer through the embedded pointer, and finally sets the indicator to one.

The zero comparison is the only visible classification of the incoming value. There is no positive-only restriction, range test, normalization, clamping, or rejection of negative values.

Consequently, any representable negative input follows the same branch as a positive nonzero input. The destination receives that input value, while the indicator receives one rather than a copy of the input.

### Aliasing

No non-aliasing requirement or overlap check is explicitly present. Final-state claims must account for overlapping writes.

If the indirect destination overlaps the indicator:

- On the zero branch, the indirect integer write occurs last and may overwrite bytes written by the initial indicator clear.
- On the nonzero branch, the final two-byte indicator write occurs last and may overwrite part or all of the integer representation just stored.

Thus, “the destination equals the incoming integer on return” is guaranteed only under an appropriate nonoverlap assumption.

If the indirect destination overlaps the embedded pointer field, the destination write can modify that stored pointer. The supplied operation sequence does not read the embedded pointer again afterward. The current indirect write uses the pointer obtained before that write, but a subsequent call can observe the modified pointer.

Whether a particular overlapping arrangement is valid depends on the target’s alignment, storage, and access rules. The function supplies no mechanism for making otherwise invalid overlap safe.

### Preconditions and failures

For normal completion, the caller must provide:

- A record address supporting the two-byte indicator write.
- Accessible storage for reading a pointer at offset 4.
- A resulting destination pointer supporting an integer write of the required width.
- Alignment and access permissions appropriate to the target.
- Storage whose lifetime covers all accesses.

There are no explicit null checks, bounds checks, pointer-validity checks, or recovery branches.

The function provides no structured error return. An invalid access may prevent completion; its precise manifestation is outside the supplied evidence.

If destination access fails after the initial indicator write, the earlier clear has already occurred in the shown sequence. On a nonzero call, the final assignment of one has not yet occurred. This is an ordering observation, not a guarantee about fault delivery, persistence, or recovery in a particular runtime.

## Side effects

The explicit memory effects are limited to:

- One initial two-byte write to the record indicator.
- One read of the embedded destination pointer.
- One integer write through that pointer.
- One additional two-byte indicator write for nonzero input.

There is no explicit write to the intervening two-byte region or to the embedded pointer field itself. Either can nevertheless be affected if the indirect destination overlaps it.

There is no explicit access to global state, no external call, and no explicit allocation or release operation. The supplied record and destination could themselves refer to globally reachable or specially mapped storage; the interface does not restrict their provenance.

The function does not provide transactional behavior. In particular, the indicator clear precedes the destination update rather than being committed together with it. The final value of one on the nonzero branch follows the destination write, but this alone does not establish a thread-safe publication protocol.

## Acceptance examples

These are conditional behavioral examples, not executed tests. Unless stated otherwise, they assume valid ordinary storage, no overlap, and a destination capable of representing the input.

### Zero clears both outputs

Given an incoming value of zero, an indicator initially containing a nonzero value, and an indirect destination initially containing any integer:

- The indicator is cleared first.
- The destination is written with zero.
- The function returns without a final indicator update.
- Both locations contain zero afterward.

### Positive nonzero input

Given an incoming value of 7:

- The indicator is first written with zero.
- The destination is written with 7.
- The indicator is then written with one.
- The final indicator is one, not 7.

### Negative nonzero input

Given a representable incoming value of −3:

- The nonzero branch is taken.
- The destination receives −3 without an explicitly shown transformation.
- The indicator finishes at one.

This example does not require a particular negative-integer byte representation.

### Repeated calls

Given stable, valid, nonoverlapping storage, a call with 7 followed by a call with zero leaves the destination at zero and the indicator at zero.

The earlier nonzero state does not cause an early return or prevent the second destination write.

### Destination failure

Given a writable indicator but an embedded pointer that cannot support the destination write:

- The shown sequence clears the indicator before attempting that write.
- No successful return or structured error result is promised.
- On a nonzero input, the final indicator assignment is not reached in that sequence if the destination access interrupts execution.

The exact failure mechanism is documented_only.

### Overlap under a specific representation

Assume a valid little-endian environment with four-byte integers, and an indirect destination beginning exactly at the indicator address. For an incoming value of 2:

- The integer write places 2 at the overlapping destination.
- The later two-byte indicator write replaces its low two bytes with the representation of one.
- The final four-byte destination representation corresponds to 1, not 2.

This example demonstrates why the nonoverlapping final-state contract must not be applied to overlapping storage. Its representation and access-validity assumptions are essential.
