## Behavior

### 1. Capture the count and request storage

The function first reads the count from object offset +8. It computes an entry count equal to that captured count plus one, then forms a byte-size argument equal to four times the entry count.

It invokes F-871e64ddc6de once, with seven arguments in this order:

1. The computed byte size.
2. A zero-valued argument.
3. The original third argument.
4. The original fourth argument.
5. The object address plus one byte.
6. A zero-valued argument.
7. A zero-valued argument.

The fifth argument is a one-byte address increment. It is not the address of the field at offset +4, nor is it a four-byte entry increment.

The call's return value is used as the storage base address. The visible body contains no explicit success test before initialization and no retry, alternate storage path, or explicit release.

The count is captured before the call. There is no visible reload from object offset +8 afterward. If the dependency changes that field and returns normally, subsequent initialization still uses the captured count.

### 2. Initialize the storage in ascending entry order

Starting at the returned base address, the function traverses four-byte entries toward the endpoint located one entry beyond the captured count.

For ordinary nonnegative counts and valid arithmetic, it visits exactly the captured count plus one entries, in ascending address order.

At each visited address:

- If the address is nonzero, the function writes a 32-bit zero.
- If the address is zero, it skips that write.
- Traversal advances by four bytes.

This address-zero check applies to each visited entry. It is not a general allocation-failure check. A zero returned base does not cause an early return: if traversal continues to address four, the function attempts a write there.

The traversal stops on address equality with its computed endpoint. The evidence does not show a less-than bounds check. Consequently, negative counts, wrapped arithmetic, or invalid address calculations must not be treated as a safe empty-range case.

For a valid ordinary request, this stage also zeroes the final entry. That entry is subsequently overwritten with its own address.

### 3. Publish the final-entry address

The function computes the final-entry address as the returned base plus four times the captured count.

It then writes this address into the object's four-byte field at offset +12.

This publication happens after all zero-initialization writes and before the final entry receives its self-address. The function does not wait until all storage initialization is complete before publishing this field.

### 4. Write the self-address

The function writes the final-entry address into the four-byte entry located at that same address.

For an ordinary valid call, the resulting region contains:

- A number of zero entries equal to the captured count.
- One final entry containing its own address.

This write is unconditional in the visible body. Unlike writes in the earlier traversal, it has no address-zero guard.

### 5. Publish the storage base

Finally, the function writes the returned base address into the object's field at offset +4 and returns without an explicit value.

For a successful, non-overlapping call, the order of visible writes is therefore:

1. Zero entries in ascending address order.
2. Publish the final-entry address at object offset +12.
3. Store that address into the final entry itself.
4. Publish the storage base at object offset +4.

This ordering is part of the established behavior. No rollback is visible if an intervening write fails.

- Zero writes over the traversed storage addresses, subject to the per-address zero check.
