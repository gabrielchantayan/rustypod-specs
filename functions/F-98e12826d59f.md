# F-98e12826d59f

## Purpose

F-98e12826d59f conditionally accepts a requested inclusive range, invokes a fixed sequence of dependencies on a context object, and reconciles a one-byte context field with a requested unsigned value. It reports completion through both a 32-bit return value and a caller-provided byte.

The established behavior is procedural. The supplied evidence does not establish what the context represents, what the range selects, or what the dependency calls accomplish. Names such as “range,” “requested value,” and “notification” below describe observable roles, not a recovered application-level purpose.

The only explicit rejection occurs when both range endpoints are specified and the computed inclusive span does not match a context field. Otherwise, if all dependency calls return normally and memory accesses succeed, the function writes a completion byte of 1 and returns 1.

## Interface

### Inputs and output

The function takes six arguments, in this order:

| Position | Contract name | Representation and role |
|---|---|---|
| 1 | Context | Pointer to a mutable, word-addressed context containing a dispatch-table reference and fields described below. |
| 2 | Signed selector | Signed 32-bit scalar. Governs part of the later byte-update decision. Its magnitude is otherwise not used in that decision. |
| 3 | Completion destination | Pointer to a writable byte. Receives 0 on entry and 1 upon normal completion of the accepted path. |
| 4 | Requested value | Unsigned 32-bit scalar. Compared in full against a zero-extended context byte; stored into that field only after truncation to eight bits. |
| 5 | First endpoint | Signed 32-bit scalar. The value −1 is a sentinel. |
| 6 | Last endpoint | Signed 32-bit scalar. The value −1 is a sentinel. |

The return value is a 32-bit value:

- **0:** explicit range-consistency rejection.
- **1:** the accepted path reached its final completion write.

There is no demonstrated return value for dependency failure, invalid memory, or other abnormal termination.

### Context layout

The following byte offsets are relative to the supplied context address:

| Offset | Width | Observed use |
|---|---:|---|
| 0 | One dispatch-table reference, represented as a 32-bit word in the supplied evidence | Read to resolve three indirect calls. |
| 4 | 32 bits | Read and passed as the first argument to F-60e7318a3858. |
| 28 | 8 bits | Read as an unsigned byte; conditionally overwritten with the low eight bits of the requested value. |
| 32 | 32 bits | Read as the expected span when both endpoints differ from −1. |

The evidence shows no direct access to the other bytes within these words or intervening storage. In particular, the write at offset 28 is a one-byte write, not a replacement of the entire word beginning there.

The observed dispatch-table entries are at byte offsets 8, 16, and 48. These offsets are established; a complete object layout, runtime type, and ABI are not.

### Preconditions

For a normally completing accepted call:

- The completion destination must be writable.
- The context must support all context reads and writes reached on that path.
- Each reached dispatch-table entry must resolve to a callable dependency compatible with its observed arguments.
- Dependency-specific preconditions must hold. They are not recoverable from this function alone.

For explicit rejection, the function still requires a writable completion destination and, when both endpoints are specified, a readable expected-span field.

No null checks, bounds checks on memory accesses, overlap checks, or ownership checks are shown.

## Behavior

### 1. Clear the completion byte

The first observable memory operation is a write of 0 to the completion destination.

This precedes range validation and every dependency call. Consequently, an explicitly rejected request still modifies the completion destination.

The supplied evidence does not prohibit aliasing between this destination and the context. If they overlap, the initial byte write can affect subsequent context reads, including validation or dispatch resolution.

### 2. Validate only a fully specified range

Range validation is enabled only when **both** endpoints differ from −1.

When enabled:

1. The function reads the 32-bit expected-span field at context offset 32.
2. It computes the inclusive span represented by last endpoint minus first endpoint plus one.
3. It compares the computed 32-bit result with the expected span.
4. On mismatch, it immediately returns 0.

There are no dependency calls on this rejection path. The function does not itself overwrite the context byte at offset 28 on that path, except for any overlap caused by the initial completion-byte write.

When either endpoint is −1, the expected-span comparison is bypassed. Both original endpoint values are nevertheless passed to F-70e13ef9fc28 later.

The function does not independently reject reversed endpoints, negative endpoints other than the sentinel, or a nonpositive span. Such inputs are subject only to the observed equality check when validation is enabled.

The span calculation uses 32-bit signed operands in the supplied representation. The evidence does not establish the handling of arithmetic overflow. Non-overflowing calculations are specified directly; overflowing cases remain documented_only.

### 3. Invoke the accepted-path dependencies

After validation succeeds or is bypassed, the following calls occur in order:

1. **F-indirect-08**, resolved through the context’s dispatch-table reference at table byte offset 8, receives the context.
2. **F-60e7318a3858** receives the current 32-bit field at context offset 4 and the scalar value 1.
3. **F-70e13ef9fc28** receives the context, first endpoint, and last endpoint.
4. **F-indirect-30**, resolved at table byte offset 48, receives the context and the current 32-bit fields at context offsets 40 and 44.

The indirect labels above are document-local opaque dependency labels, not recovered function identities.

These calls are sequenced, but dependency side effects are not constrained by the evidence. In particular:

- The offset-4 argument is read after F-indirect-08 returns.
- The offset-40 and offset-44 arguments are read after F-70e13ef9fc28 returns.
- Each indirect call resolves through the context’s dispatch-table reference at its own call site. The function does not establish that the reference remains unchanged across earlier calls.
- The relative order of the individual argument-field reads and dispatch-reference read within a single call setup is not established.
- No dependency return value is inspected.

Later behavior therefore depends on the context state left by these dependencies, not necessarily on its entry state.

### 4. Decide whether to write the context byte and notify

After F-indirect-30 returns, the function reads the unsigned byte at context offset 28 and compares it with the full unsigned 32-bit requested value.

An update consists of both:

1. Writing the low eight bits of the requested value to context offset 28.
2. Calling **F-indirect-10**, resolved at dispatch-table byte offset 16, with the context and scalar value 0.

If the current byte differs from the full requested value, the update always occurs.

If they compare equal, the signed selector determines whether the update is still required:

| Signed selector | Requested value, given full equality with the byte | Update and call F-indirect-10? |
|---|---|---|
| Negative | 0 | No |
| Negative | Nonzero | Yes |
| Zero | Any equal value | No |
| Positive | 0 | Yes |
| Positive | Nonzero | No |

Thus equality of the stored byte is not, by itself, sufficient to suppress the write and callback.

The comparison and store have different widths. A requested value greater than 255 cannot compare equal to the zero-extended byte. It always takes the update path, even when its low eight bits already match the stored byte.

The one-byte store precedes F-indirect-10. That dependency may observe the stored byte, subject to its own behavior. No later restoration of that field is shown.

### 5. Report completion

After the conditional update path finishes, or after it is skipped, the function:

1. Writes 1 to the completion destination.
2. Returns the 32-bit value 1.

The completion byte is therefore a completion indicator for this function’s normal accepted path, not evidence that opaque dependencies reported success. Their results are not checked.

If the completion destination aliases context storage, this final write can modify context state after all dependency calls. If it aliases the byte at offset 28, for example, the final directly imposed value of that byte is 1 rather than necessarily the requested low byte.

## Side effects

### Direct effects

The function directly performs:

- An unconditional entry write of 0 to the completion destination.
- A conditional one-byte write at context offset 28.
- A completion write of 1 on the normally completed accepted path.

The range check itself performs no direct context write beyond possible effects of aliasing with the completion destination.

### Dependency effects

Every accepted path invokes four dependencies before deciding whether a fifth call is necessary. Those dependencies may modify context storage, dispatch references, external state, or memory reachable through arguments. Their effects are unknown here.

The evidence does not justify assuming that dependencies:

- Preserve global state or context fields.
- Retain or release any particular allocation.
- Leave the completion destination unchanged.
- Return normally.
- Signal errors through their return values.

### Ownership and lifetime

No direct allocation, deallocation, reference-count operation, or explicit ownership transfer is visible.

This absence does not establish that the dependencies perform none. The caller must supply storage and dependency state that remain usable for all accesses actually reached. No ownership guarantee is inferred for any passed value.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless otherwise stated, assume valid memory, no aliasing, normally returning dependencies, and dependencies that do not modify the fields relevant to the stated outcome.

### Fully specified range rejected

Given first endpoint 4, last endpoint 7, and expected span 5:

- The computed inclusive span is 4.
- The completion destination receives 0.
- The function returns 0.
- No dependency is called.
- No direct write is made to the context byte at offset 28.

### Fully specified range accepted

Given first endpoint 4, last endpoint 7, and expected span 4:

- Range validation passes.
- The first four dependencies run in the specified order.
- The later byte decision determines whether F-indirect-10 is called.
- On normal completion, the completion destination is 1 and the return value is 1.

### One sentinel bypasses validation

Given first endpoint −1 and last endpoint 7:

- No expected-span comparison is performed.
- F-70e13ef9fc28 receives −1 and 7 unchanged.
- The accepted-path sequence proceeds regardless of the expected-span field’s value.

The same validation bypass applies when only the last endpoint is −1 or when both endpoints are −1.

### Reversed endpoints can pass

Given first endpoint 5, last endpoint 3, and expected span −1:

- The inclusive calculation produces −1 without overflow.
- The equality check passes.
- The function does not reject merely because the endpoints are reversed.

This establishes only this function’s behavior; F-70e13ef9fc28 may impose additional behavior that is unknown here.

### Equal byte with positive selector and zero request

Given a positive signed selector, requested value 0, and current byte 0 after F-indirect-30:

- The function still writes 0 to the context byte.
- It calls F-indirect-10.
- It then reports completion.

### Equal byte with negative selector and nonzero request

Given a negative signed selector, requested value 9, and current byte 9:

- The byte is rewritten with 9.
- F-indirect-10 is called despite equality.

### Equal byte with zero selector

Given signed selector 0 and current byte equal to the requested value:

- No byte write occurs at the update stage.
- F-indirect-10 is skipped.
- The completion write and return value are still 1.

### Truncation does not make the comparison equal

Given requested value 256 and current byte 0:

- The full-width comparison is unequal.
- The function writes 0, the low eight bits of 256.
- F-indirect-10 is called for any signed selector.

### Dependency changes the byte before comparison

If F-indirect-30 changes the context byte, the decision uses that changed byte. It does not use a saved entry value.

### Completion destination aliases the context byte

If the completion destination is exactly context offset 28:

- The entry write first sets that byte to 0.
- The later decision uses the byte as it exists after the first four dependencies.
- Any update write precedes F-indirect-10.
- The final completion write sets the byte to 1 on normal completion.

This aliasing case does not establish that dependencies tolerate such overlap.
