# F-96b09b4480d9

## Purpose

F-96b09b4480d9 updates three consecutive one-byte fields in an indexed record. Two requested field combinations are accepted. Every other combination is normalized to three zero bytes.

For an accepted combination, the function additionally writes a derived one-byte value through a caller-supplied output pointer. For a rejected combination, it does not access that output pointer.

The record-selection check rejects signed indices greater than 2 through a dependency annotated as non-returning. It does not reject negative indices.

**Established behavior:** selection, normalization, byte values, write order, and conditional output access are directly supported by the supplied static representation.

**Inferred intent:** the three fields may represent a mode, an associated option, and a derived encoding. Their application meaning is not established; this contract uses positional descriptions instead.

The function accesses these locations relative to the selected record:

| Byte offset | Size | Meaning in this contract |
|---|---|---|

No other record fields are explicitly accessed. The 276-byte stride does not establish the total allocation size, the number of allocated records, or the purpose of the intervening bytes.

## Behavior

### 1. Upper-bound check

The function first compares the record index with 2 using a signed comparison.

- An index greater than 2 invokes F-a817d8d58c10.
- An index equal to 2 passes this check.
- Zero, one, and every negative signed index also pass this check.

The dependency is annotated as non-returning. Under that annotation, the function does not proceed to read the record base or perform its own record or output writes on this path.

This is an upper-bound check only. It must not be described as validating membership in the set {0, 1, 2}.

### 2. Requested-field classification

For indices that pass the check, the function classifies the requested fields using their full integer values.

| Requested first field | Requested second field | Classification | Stored first byte | Stored second byte | Derived byte |
|---|---|---|---|---|---|
| 1 | 0 | Accepted | 1 | 0 | 16, hexadecimal 0x10 |
| 2 | 0 | Accepted | 2 | 0 | 20, hexadecimal 0x14 |
| Any other combination | Any | Rejected and normalized | 0 | 0 | 0 |

In the final row, “any other combination” includes either accepted first-field value paired with a nonzero second field.

Classification occurs before byte storage. Values are not first truncated to eight bits for comparison. Consequently, a first-field request whose low byte is 1 but whose full integer value is not 1 is rejected.

Rejected requests are not left unchanged. Their selected record fields are explicitly overwritten with zeros.

### 3. Base acquisition and address calculation

After classification, the function reads the record base from external storage and computes the selected record address using the index and 276-byte stride.

The visible path contains one acquisition of that base. The three record destinations derive from the resulting address; the base is not visibly reloaded between stores.

The representation supports a 32-bit interpretation of the integer arithmetic. It does not establish a portable rule for signed overflow or out-of-object pointer arithmetic. In particular:

- Negative indices produce a negative mathematical displacement from the base.
- Sufficiently large-magnitude negative indices can exceed the signed 32-bit range when multiplied by 276.
- Passing the upper-bound check therefore does not establish that address calculation or memory access is valid.

Normal acceptance examples below assume representable address calculation and valid destination memory. Overflow behavior is documented as unknown rather than assigned an unsupported wrapping rule.

### 4. Ordered record writes

The function performs three separate one-byte stores in this order:

1. Normalized first field at record offset 16.
2. Normalized second field at record offset 17.
3. Derived byte at record offset 18.

For accepted requests, these stores produce either **1, 0, 16** or **2, 0, 20**.

For rejected requests, they produce **0, 0, 0**.

There is no visible read of the previous contents of these fields. The operation does not preserve old field values when a request is rejected.

The sequence is not a single atomic record update. The supplied representation does not provide synchronization or transactional rollback.

### 5. Conditional output write

After all three record stores:

- For an accepted request, the function stores the derived byte at the output location.
- For a rejected request, the function does not dereference the output pointer.

The output store is one byte wide and contains 16 or 20. The function does not read the previous output byte.

A rejected request does not write zero to the output location. Any existing byte there remains unchanged unless another write, including an aliasing record write, affects the same address.

### 6. Return

After the applicable stores, the function returns without an explicit value.

There is no visible success/error return channel. The internal distinction between accepted and rejected requests controls only the conditional output store.

### Aliasing

No non-aliasing requirement is checked or established.

If the output location aliases a record field, the output store occurs last and can change the final field contents:

- Aliasing offset 16 replaces the previously stored first field with the derived byte.
- Aliasing offset 17 replaces zero with the derived byte.
- Aliasing offset 18 writes the same derived byte again.

Thus, the three-byte values in the classification table describe the record immediately after its three stores. They describe the final record state only when a later output store does not overwrite a relevant byte.

For rejected requests, the output pointer itself is not used. However, an output object that aliases the three record destinations can still change because those record destinations are written independently.

### Ownership and lifetime

The dependency’s effects on ownership, memory lifetime, and global state are unknown. Its non-returning annotation does not imply that it is side-effect-free.

### Errors and interrupted execution
