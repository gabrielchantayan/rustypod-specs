# F-b167ca983b59

## Purpose

F-b167ca983b59 maintains two keyed values within a receiver, synchronizes a packed representation of the first value through an embedded dispatch interface, and conditionally establishes an association involving the second value.

The established behavior distinguishes three cases:

- The key is reported absent from the first keyed component: invoke insertion-oriented dependencies for both values, submit a packed entry, notify the receiver, and check the association.
- The key is reported present and both retrieved values equal the requested values: return without further calls.
- The key is reported present and either retrieved value differs: invoke update-oriented dependencies for both values, conditionally replace a packed entry, notify the receiver, and check the association only if the second value changed.

The interpretation of the components as keyed stores and the final operation as association establishment is inferred intent. The concrete contract is the call sequence, argument values, comparisons, and branch behavior below. The internals of the dependencies are not established.

## Behavior

### 1. Probe the first keyed component

The function initializes a 32-bit output cell to zero, then calls **F-d6f1e679078e** with:

1. the first component at receiver byte offset 24;
2. the full 32-bit key;
3. the address of that output cell.

After the call returns, it captures the output cell as the previous first value.

The call’s return value controls the main branch:

- Exactly zero selects the absent-key path.
- Any nonzero value selects the present-key path.

No particular nonzero success code is required. If the dependency leaves the output cell untouched, the captured first value is zero because of the explicit initialization. Whether leaving it untouched is permitted by the dependency’s own contract is unknown.

The function also constructs the requested packed word:

**requested packed word = low 16 bits of key | (low 16 bits of requested first value shifted into bits 16–31).**

This is a 32-bit bit-pattern description. It does not require an unbounded mathematical shift or a language-level signed-overflow interpretation.

### 2. Absent-key path

When the first lookup returns zero, the following calls occur in order:

1. **F-9c3a6bed907e**, with the first component, full key, and requested first value.
2. **F-9c3a6bed907e**, with the second component, full key, and requested second value.
3. The packed-entry submission method, with the embedded component at receiver byte offset 104 and the address of a 32-bit cell containing the requested packed word.
4. The receiver notification method, with the receiver, opaque context, and full key.
5. The association check described below.

There is no second-component lookup on this path. Thus, this function does not independently establish that the key is absent from the second component before invoking its insertion-oriented dependency.

Neither keyed mutation’s return value is inspected. The packed-entry submission’s result is also unused. Notification and the association check are not conditional on a reported mutation success.

### 3. Present-key path: retrieve the second value

When the first lookup returns nonzero, the function calls **F-d6f1e679078e** again with:

1. the second component at receiver byte offset 64;
2. the full key;
3. the address of the same output cell used by the first lookup.

The cell is **not reset** before this call. Immediately before the second lookup, it contains whatever the first lookup left there.

The second lookup’s return value is not used to determine presence, success, or any subsequent branch. Instead, the function captures the output cell after that call as the previous second value.

Consequently, if the second lookup does not write the cell, the previous second value used by this function equals the previous first value. This is an established consequence of cell reuse, not a guarantee about how the dependency behaves.

### 4. Present-key path: unchanged values

If both comparisons hold—

- previous first value equals requested first value; and
- previous second value equals requested second value—

the function returns immediately.

This return occurs after both lookups. It skips:

- both update-oriented calls;
- packed-entry lookup and replacement;
- receiver notification;
- association checking and establishment.

The function performs no further explicit mutation on this branch, but the lookups’ own side effects are unknown.

### 5. Present-key path: update both keyed components

If either value differs, the function calls, in order:

1. **F-8a277506598f**, with the first component, full key, and requested first value.
2. **F-8a277506598f**, with the second component, full key, and requested second value.

Both calls occur even when only one value changed. Their return values are not inspected.

The decisions that follow use the previous values captured before these update calls. The function does not re-read either keyed value afterward.

### 6. Conditionally replace the packed entry

If the previous first value differs from the requested first value, the function constructs a previous packed word:

**previous packed word = low 16 bits of key | (low 16 bits of previous first value shifted into bits 16–31).**

It then calls the packed-entry lookup method with:

1. the embedded component at receiver byte offset 104;
2. the address of a 32-bit cell containing that previous packed word.

The lookup returns a 32-bit integer locator.

- If the locator is exactly −1, no replacement call occurs.
- For every other locator, including other negative values, the function calls the packed-entry replacement method with the embedded component, the returned locator unchanged, and the address of a separate cell containing the requested packed word.

A lookup miss does not cause an insertion, rollback, or early return. The function proceeds to receiver notification.

If the first value did not change, neither packed-entry lookup nor replacement occurs.

### 7. Notify after a nontrivial present-key update

After both update calls and any packed-entry work, the function calls the receiver notification method with:

1. the receiver;
2. the opaque context;
3. the full key.

The dispatch pointer is obtained at the notification call site. No cached dispatch-table identity is established across earlier dependency calls.

After notification returns:

- If the captured previous second value equals the requested second value, the function returns.
- Otherwise, it proceeds to the association check.

Thus, a first-value-only change causes notification but no association check.

### 8. Check and conditionally establish the association

This step is reached:

- unconditionally after the absent-key path’s notification; or
- after a present-key update when the second value changed.

The function calls **F-c7ba4c901230** with the requested second value first and the receiver second.

- A zero result causes a call to **F-8f9bd59e3ec5** with the same arguments in the same order.
- Any nonzero result skips that call.

The establishment call’s result is not inspected. No final verification follows it.

## Side effects

### Explicit call ordering

All described dependency calls are sequential. In particular:

- Both keyed mutations precede packed-entry submission or replacement.
- Packed-entry work precedes notification.
- Notification precedes any association check.
- The association-establishment call, when needed, follows the association check.

There is no transaction or rollback mechanism in the visible function. A missing packed entry, ignored dependency result, or later failure does not undo earlier work.

### Receiver and dispatch access

The function passes interior addresses of the receiver to dependencies. It does not visibly copy or replace the receiver itself.

Dispatch-table pointers are read at their respective call sites. If an earlier dependency changes relevant receiver state and returns normally, a later dispatch lookup can observe that changed state. The supplied evidence does not establish that dependencies preserve receiver fields, dispatch tables, global state, or external state.

### Temporary storage and ownership

The function supplies writable addresses for:

- the reused keyed-lookup output cell;
- packed-word cells used by submission, lookup, and replacement.

These are temporary cells associated with the invocation. The supplied function contains no explicit allocation, deallocation, ownership transfer, or retention protocol.

Whether a callee copies a packed word, retains its address, or manages other memory is unknown. Safe post-return use of these temporary addresses is not established.

### Failure behavior

There are no explicit checks for invalid receiver pointers, invalid dispatch pointers, missing methods, or component-operation errors.

The two checked sentinel conventions are:

- zero versus nonzero for the first keyed lookup and association check;
- exactly −1 versus all other values for packed-entry lookup.

The second keyed lookup’s return value and the mutation methods’ results do not alter control flow. Behavior when a dependency faults, fails to return normally, or violates memory requirements is not defined by this evidence.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Each assumes valid memory and dependencies that return normally.

1. **Absent first key.**  
   If the first lookup returns zero, both insertion-oriented calls occur, followed by packed submission, notification, and association checking. This remains the sequence even if the first lookup writes a nonzero output value.

2. **Present and unchanged.**  
   If the first lookup returns nonzero and writes 12, the second lookup writes 34, and the requested values are 12 and 34, only the two lookups occur.

3. **Only the first value changes.**  
   With previous values 12 and 34 and requested values 13 and 34, both update-oriented calls occur. Packed lookup uses the encoding of the key and 12. A locator other than −1 triggers replacement with the encoding of the key and 13. Notification follows; no association check occurs.

4. **Only the second value changes.**  
   With previous values 12 and 34 and requested values 12 and 35, both update-oriented calls occur. No packed lookup or replacement occurs. Notification precedes the association check for 35.

5. **Packed lookup misses.**  
   If the first value changes but packed lookup returns −1, replacement is skipped. Notification still occurs, followed by association checking only if the second value changed.

6. **Nonstandard negative locator.**  
   A packed lookup result of −2 is forwarded to replacement. It is not treated as the −1 miss sentinel.

7. **Full-width key versus packed key.**  
   For key `0x12345678` and requested first value `0x00009ABC`, the packed word is `0x9ABC5678`. Keyed dependencies and notification still receive `0x12345678`.

8. **Different first values with identical packed representation.**  
   A change from `0x00000001` to `0x00010001` is a full-width value change. It triggers packed lookup and, if found, replacement, although both packed words are identical for the same key.

9. **Second lookup leaves the output untouched.**  
   If the first lookup writes 7 and the second lookup does not write its output cell, this function uses 7 as both previous values regardless of the second lookup’s return value.

10. **Association check succeeds by nonzero result.**  
    Any nonzero association-check result skips establishment. Exactly zero causes one establishment call.
