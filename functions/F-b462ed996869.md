# F-b462ed996869

## Purpose

F-b462ed996869 constructs a 16-byte record from three 32-bit inputs and passes that record to a dependency together with a shared context reference. A non-null submission result may trigger an indirect callback before being passed to a final dependency.

The normal return value is a 32-bit value of either 0 or 1. These values do not directly express whether submission returned an object:

- A null submission result can lead to either return value.
- A return of 0 can occur after allocation, record construction, and submission.
- A return of 1 does not establish ownership transfer, callback execution, or successful completion of any domain-level operation.

Registration or scheduling is a possible interpretation of the record and comparison. That is inferred intent, not an established requirement.

No local error object, diagnostic, or distinct error code is produced. Dependency failures, invalid memory accesses, and exceptional control transfers are outside the established normal-return behavior.

### Shared-state representation

The supplied representation uses 32-bit words and pointer-bearing values, with four-byte field spacing. Two fields of a shared block are used:

| Byte offset | Established role |
|---|---|
| 0 | Context reference. |
| 8 | Optional handle used to gate comparison work and, later, as a resolver argument. |

There are **two separate initial evaluations of the global block pointer**:

1. The routine evaluates the global pointer and retains that block address for later use.
2. It separately evaluates the global pointer again and reads the context reference at offset 0 through this second evaluation.

The second evaluation supplies the initial readiness-condition dereference. It is not a dereference through the retained address.

No dependency call occurs between these two evaluations. The representation nevertheless does not justify merging them into a single evaluation or assuming that both necessarily identify the same block. Whether external mutation can produce a difference under the actual execution and synchronization model is unknown.

After this initial readiness-condition read, the routine’s context and handle accesses use the **retained block address**, not a newly acquired global block pointer. Retaining that address does not snapshot the block’s fields.

### Memory-validity preconditions

Normal execution requires each reached access to be valid:

- The block selected by the **second initial global-pointer evaluation** must permit a 32-bit read at offset 0 for the readiness test.
- The retained block must permit its later context and handle reads when those paths are reached. It need not be dereferenced if readiness fails or allocation returns null.
- A non-null allocation result must permit four consecutive 32-bit writes covering 16 bytes.
- If submission returns null, the context reference then read from the retained block must permit a 32-bit read at offset 92.
- A non-null submission result must remain suitable for every object-field access and dependency use reached on that path.
- A reached resolver result must permit loading a callable target at byte offset 8, and that target must be callable with the three supplied arguments.

These are access requirements, not locally enforced validations. In particular, readiness success does not establish that the context subsequently read from the retained block is nonzero or valid.

## Behavior

### Initial readiness decision

The routine first retains one evaluation of the global block pointer. It then separately evaluates that global pointer and reads the context reference through the second evaluation.

If the readiness-condition context reference is nonzero, F-ea867029bc2c is skipped and execution proceeds to allocation.

If that context reference is zero, F-ea867029bc2c is called without arguments:

- A zero result causes an immediate return of 0.
- Any nonzero result permits allocation.

The result is not required to equal 1. No further context validation occurs before allocation.

The block used for the readiness-condition read and the retained block have different roles. A nonzero context observed for readiness does not establish the value later obtained from the retained block. A readiness dependency may also modify shared state, but no dependency call explains any difference between the two initial pointer evaluations: both evaluations precede that dependency.

### Allocation and record construction

After readiness succeeds, F-43da6b23bd44 is called with three ordered arguments:

1. 16.
2. Zero.
3. Zero.

A null result causes a return of 0. Submission is not reached.

A non-null result is treated as writable storage for a 16-byte record. Four 32-bit stores occur in increasing offset order:

| Byte offset | Stored word value |
|---|---|
| 0 | Second input masked with `0xFFFF7FFF`. |
| 4 | Second input masked with `0x00008000`. |
| 8 | First input, unchanged. |
| 12 | Third input, unchanged. |

The first field preserves every bit of the second input except bit 15. The second field contains only bit 15, so its value is either zero or `0x00008000`, not a normalized Boolean 1.

The two fields neither truncate the second input to 16 bits nor discard its upper bits. There is no arithmetic addition or signed conversion in this partition.

These requirements describe word values and byte offsets. They do not establish a portable serialized byte order.

### Submission

After all four stores, the routine reads the context reference at offset 0 of the retained block. F-dbd019788d3d is then called with these ordered arguments:

1. The context reference just read.
2. The allocated record address.

This context reference is not necessarily the context observed by the readiness condition. Even if both initial pointer evaluations selected the same block, intervening dependencies may have changed its contents.

Submission’s result is treated as either null or an object pointer. The evidence does not establish whether a non-null object is distinct from the allocated record or other referenced storage.

### Null submission result

If submission returns null, the routine rereads the context reference from offset 0 of the retained block. Through that reference, it reads a 32-bit field at byte offset `0x5C`, which is 92.

- A nonzero field produces return value 0.
- A zero field produces return value 1.

The reference used for this inspection is read **after submission**. It may differ from the reference passed to submission.

Neither the comparison dependency, the resolver, the indirect callback, nor F-5990a26eaaa3 is reached on this path. No local release of the allocated record is visible.

The offset-92 access is a fixed-offset field read, not a bounds check. No explicit check establishes that the reread context is nonzero or that this field is accessible.

### Non-null submission result

If submission returns an object, the routine reads the optional handle at offset 8 of the retained block.

If that handle is zero, comparison and callback processing are skipped.

If that handle is nonzero:

1. F-10b760faca36 is called without arguments.
2. After that call returns, the object’s 32-bit field at offset 0 is read.
3. That field is compared with the dependency result using signed 32-bit strict less-than.

The comparison therefore interprets the operands as signed values. It is not unsigned ordering and does not subtract the operands. Equality does not select the callback path.

If the comparison is false, the resolver and callback are skipped.

If the comparison is true, the routine rereads the handle from offset 8 of the retained block and passes that value to F-6bbddce1b930. There is no second nonzero test. The resolver may therefore receive zero if the handle changed after the earlier gate.

The resolver’s result is used to load a callable target at byte offset 8. No explicit null check is made for the resolver result or the loaded target.

The indirect target is invoked with three ordered argument positions:

| Argument position | Value source |
|---|---|
| First | Object’s 32-bit field at offset 8. |
| Second | Object’s 32-bit field at offset 0. |
| Third | Object’s 32-bit field at offset 12. |

These object fields are read after the resolver returns. In particular, the callback’s second argument is a fresh field read, not necessarily the value used in the comparison. The representation establishes argument positions but not the relative order of these individual argument-field loads.

The indirect callback’s result is unused.

After optional callback processing, F-5990a26eaaa3 is called with the non-null submission object. This occurs whether the handle gate failed, the comparison failed, or the callback completed normally. Once the final dependency returns, the routine returns 1.

## Side effects

### Direct memory effects

The four stores into the allocated record are the only explicit direct writes shown. There is no explicit assignment to the global block pointer, retained block fields, or submission object fields.

This does not imply that those locations remain unchanged. Dependencies and the indirect callback may modify accessible state. Their implementations are unavailable.

If storage aliases other referenced memory, the stores may affect later reads through that alias. No non-aliasing guarantee is established.

### Observable ordering

For operations reached on a normally progressing path, the following order is established:

- Retaining the first global-pointer evaluation precedes the separate readiness-condition evaluation and dereference.
- Any readiness dependency call follows that initial dereference and precedes allocation.
- Allocation precedes the four ordered record stores.
- All record stores precede the context read used for submission.
- Submission precedes the null-result inspection or non-null-result handle gate.
- On the comparison path, F-10b760faca36 precedes the object-field read used in the signed comparison.
- A successful comparison precedes the handle reread and resolver call.
- The resolver returns before the callback argument fields are read and the callback is invoked.
- A normally returning callback precedes F-5990a26eaaa3.
- F-5990a26eaaa3 precedes the normal return of 1 on the non-null path.

No callback-field snapshot may be substituted for the post-resolver reads. Likewise, entry-time block fields may not replace later rereads.

## Acceptance examples

These are conditional expectations from static evidence, not executed tests. Unless specified otherwise, all reached accesses are valid and all invoked dependencies return normally.

1. **Readiness failure.** The second initial global-pointer evaluation selects a block whose context is zero, and F-ea867029bc2c returns zero. The result is 0. Allocation is not reached, and the retained block is not subsequently dereferenced.

2. **Distinct initial selections.** Suppose the first evaluation retains block A and the second selects block B. If B’s context is nonzero, readiness is skipped. After successful allocation and construction, submission receives A’s then-current context, not B’s context. This is conditional on the execution environment permitting the two evaluations to differ; no intervening dependency is involved.

3. **Noncanonical readiness success.** The readiness-condition context is zero and F-ea867029bc2c returns 7. Allocation is reached. The routine does not require return value 1 or revalidate the retained block’s context before allocation.

4. **Allocation failure.** Readiness succeeds and F-43da6b23bd44 returns null. The result is 0. No record stores or submission occur.

5. **Record partition.** For first input `0x11223344`, second input `0x1234ABCD`, and third input `0x55667788`, the stored words in offset order are `0x12342BCD`, `0x00008000`, `0x11223344`, and `0x55667788`.

6. **High-bit preservation.** A second input of `0xFFFFFFFF` produces first and second record fields of `0xFFFF7FFF` and `0x00008000`. A second input of `0x80000000` produces `0x80000000` and zero.

7. **Null submission result.** Submission returns null. A zero field at offset 92 of the subsequently selected context produces 1; a nonzero field produces 0. Neither case reaches F-5990a26eaaa3.

8. **Context mutation during submission.** Submission changes the context field of the retained block and returns null. The offset-92 inspection uses the changed context reference, provided the resulting access is valid.

9. **Zero handle.** Submission returns an object and the handle is zero when tested. Comparison, resolver, and callback are skipped. F-5990a26eaaa3 receives the object, followed by return value 1.

10. **Strict signed comparison.** With a nonzero handle, equal signed comparison operands suppress the callback. An object field of `0xFFFFFFFF` and dependency result zero select it because signed −1 is less than zero. An object field of `0x7FFFFFFF` and result `0x80000000` do not select it.

11. **Handle and argument mutation.** If F-10b760faca36 changes the handle to zero and the comparison succeeds, the resolver receives zero. If the resolver changes accessible object fields before returning a valid target location, callback arguments reflect the later field reads, not pre-resolver snapshots.
