# F-66dcb2746b93

## Purpose

F-66dcb2746b93 runs a synchronous processing loop using a context, its current handle, a shared stop indicator, and four shared records. It waits, selects among prioritized processing paths, and records eligible completions. It terminates when an activity check returns zero or the captured stop-byte location contains a nonzero value.

The only explicit normal return is the 32-bit value zero. Dependency results control processing but are not returned to the caller.

**[INFERENCE]** The routine coordinates ongoing work and deferred completions. Two recurring context callbacks may delimit protected regions, but their synchronization meaning is not established.

Continued activity without a stop request need not terminate. No iteration limit is visible.

### Separately captured shared addresses

1. The first read captures the base used for all subsequent stop-byte accesses, at captured base plus `0x01`.
2. The retry latch is initialized to false.
3. The second read supplies the value to which `0x28` is added to obtain the record-table address.
4. The local 32-bit result slot is initialized from the fourth argument.

The two root reads must not be treated as one snapshot. If the root global changes between them, the stop-byte base and the table address can refer to different root objects. Stability against concurrent mutation is not established.

Neither captured address is subsequently refreshed. Later changes to the root global do not redirect this invocation’s stop-byte or table accesses.

## Behavior

### Entry and waiting

After the entry initialization described above, the routine calls F-16cb6bd1e676 with the current context handle and the integer `2000`. The units and meaning of `2000` are unknown.

A result equal to `-6` causes an activity check through F-d355b89833b7, using a freshly read handle:

- If activity is nonzero, F-da058fcbda4c receives another freshly read handle. Its result is then passed to F-68392d180ba3 together with the address of context offset `0x60`. Waiting repeats.
- If activity is zero, the wait loop ends.
- Any wait result other than `-6` ends the wait loop without that wait-condition activity check.

The function does not read the stop byte before its initial wait. A wait result other than `-6`, including any apparent error value, is not directly returned or separately reported.

### Dispatch entry and termination

After waiting, and after processing paths that return directly to dispatch, the routine calls F-d355b89833b7 with the current handle.

If that result is zero, termination is selected without first reading the stop byte. Otherwise, the stop byte at the first captured base plus `0x01` is read; nonzero selects termination.

Termination has this observable order:

1. Call F-0c9f3e959e1b with the context.
2. Read the stop byte at the same captured location.
3. If this post-callback value is nonzero, clear the byte.
4. Return 32-bit zero.

The post-callback read occurs even when inactivity selected termination. Cleanup can affect whether the explicit clear is performed. A change to the root global during cleanup does not change the location read or cleared.

## Side effects

The function’s explicit persistent writes are:

- Conditional clearing of the captured stop byte after the termination callback.
- Conditional clearing of context offset `0x60` after a nonzero gate result.
- Pending-byte clears, 32-bit completion-result stores, and eight-bit status stores for final-pass completions.

The two shared addresses remain fixed for the invocation, but their contents are not snapshotted. Record flags are evaluated as each position is reached. Dependencies can affect later records or subsequent passes. The passes need not select disjoint records if flags change between them.

The handle is repeatedly loaded from context offset `0x34`, rather than cached for the invocation. Changes by dependencies can affect later calls. The representation does not establish a relative evaluation order between multiple memory-derived arguments within a single call.

The result slot is initialized only once. It is not reset between queries, passes, retries, or dispatch iterations. If a query leaves it unchanged, subsequent consumers can receive a previous query’s value or the fourth argument. This does not establish that any particular status leaves the slot unchanged.

No dependency is assumed to preserve the context, shared storage, root global, or result slot where accessible. Explicit “no update” paths describe this function’s own actions, not an absence of dependency side effects.

No rollback or recovery is visible if a dependency fails to return normally.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, dependencies return normally and leave relevant storage unchanged.

1. **Different roots at entry.** If the first root read yields address A and the second yields address B, stop accesses use A plus `0x01`, while record accesses use B plus `0x28` and record offsets. Equality of A and B is not required by the visible control flow. Both locations must remain valid.

2. **Root replaced after capture.** If the root global later changes to C, this invocation still uses its original stop-byte base and separately captured table address. Cleanup changing the global does not redirect the final stop-byte clear.

3. **Initial stop request.** A nonzero captured stop byte does not bypass the initial wait. Once dispatch is reached, nonzero activity followed by that nonzero byte selects termination.

4. **Inactive handle.** Zero dispatch activity skips the pre-cleanup stop-byte read, invokes F-0c9f3e959e1b, then checks the captured stop byte and clears it if needed before returning zero.

5. **Cleanup changes the stop byte.** If termination is selected and cleanup clears the captured byte, no explicit clear follows. If cleanup leaves or makes it nonzero, the function clears it.

6. **Repeated wait.** Wait status `-6` followed by nonzero activity causes F-da058fcbda4c, then F-68392d180ba3, then another wait. Wait status `-3` does not receive this handling.

7. **Priority.** A nonzero highest-priority predicate causes its three handlers in order and returns to dispatch. No lower-priority predicate is evaluated on that iteration.

8. **Retry latch.** A nonzero completion gate leaves the latch true. Later zero work predicates still permit a cycle if higher-priority paths do not intercept it. A fully completed cycle clears the latch after its final hook.

9. **Identifier mutation.** A participating first-pass record initially has identifier `0x12`. If its query changes that field to `0x34` and returns a status other than `-3`, dispatch receives `0x34`.

10. **Mode distinction.** Zero mode queries `0x80`, then `0x00`; nonzero mode queries `0x00`, then `0x80`. In nonzero mode, a first status of `-3` suppresses both the result-consuming callback and the paired identifier calls, but not the second query.

11. **Completion ordering and truncation.** An eligible record queried with status `0x123` and result-slot value `0x89ABCDEF` has its pending byte cleared, result field written with `0x89ABCDEF`, and status byte written with `0x23` before its associated value is read for F-5bcae2eff9a7.

12. **Excluded completion and carryover.** A final-pass status of `-3` causes no direct completion update. If queries leave the result slot unchanged, later consumers receive its seeded or previously written value; no automatic zeroing intervenes.
