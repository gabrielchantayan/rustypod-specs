# F-269e394bb002

## Purpose

F-269e394bb002 maps two signed integer components to an angle-like signed integer. Axis constants and quadrant transformations suggest a scale of 128 units per quarter turn and 512 units per full turn, with the first component horizontal and the second vertical.

The established behavior is an integer transformation, not a mathematical accuracy guarantee. Axes and equal-magnitude diagonals have direct results. Other ordinary inputs invoke F-73d099a86adb and use its result to select one unsigned byte from lookup storage.

The angle interpretation and approximation intent are inferred. The dependency’s formula, the table’s contents, and correspondence to any particular trigonometric function are not established.

## Behavior

### Entry read and axis precedence

The global lookup-base value is captured before input-dependent early returns. Capturing the base does not read a table entry.

The second component is tested first:

| Condition | Returned value |
|---|---:|
| Second component is zero and first component is negative | 256 |
| Second component is zero and first component is zero or positive | 0 |

Thus the zero vector returns 0, and the negative horizontal axis returns positive 256.

If the second component is nonzero but the first component is zero:

| Condition | Returned value |
|---|---:|
| Second component is positive | 128 |
| Second component is negative | −128 |

Every axis path returns without invoking F-73d099a86adb or reading a lookup byte. The entry-time base read still occurs.

### Quadrant reduction

When both inputs are nonzero, the function reduces their direction while maintaining a signed angular offset.

The offset starts at zero. If the first component is negative, the offset becomes 256 and both components are negated. The resulting second component is then examined. If it is negative, the offset is decreased by 128, and the pair is rotated: the reduced first component becomes the negation of that second component, while the reduced second component becomes the normalized first component.

When these negations are representable, the reduced components are positive:

| Original signs | Reduced pair | Signed offset |
|---|---|---:|
| First positive, second positive | First magnitude, second magnitude | 0 |
| First negative, second positive | Second magnitude, first magnitude | 128 |
| First negative, second negative | First magnitude, second magnitude | 256 |
| First positive, second negative | Second magnitude, first magnitude | −128 |

These transformations affect local values only. The caller’s input storage is not written.

For a non-axis input containing −2,147,483,648 under the 32-bit interpretation, normalization requires a negation that lacks a representable signed result. Ordinary magnitude-based reasoning does not cover that case.

### Reduced-zero guard

After reduction, the function checks whether at least one reduced component is nonzero. If both are zero, it returns 0 without calling the dependency or reading a table entry.

This branch is explicit but unreachable from the preceding nonzero-input path under ordinary representable arithmetic. Its existence does not define recovery behavior for overflowing negation.

### Equal reduced components

Equal reduced components cause a signed increment of 64 to the offset. There is no dependency call or lookup-byte read.

The final upper-bound adjustment still applies:

| Original nonzero inputs | Result |
|---|---:|
| Both positive with equal magnitudes | 64 |
| First negative, second positive with equal magnitudes | 192 |
| Both negative with equal magnitudes | −192 |
| First positive, second negative with equal magnitudes | −64 |

These diagonal results use signed arithmetic and do not depend on the lookup path’s unsigned-to-signed conversion behavior, provided normalization is representable.

### Unequal reduced components

For unequal reduced components, F-73d099a86adb is called exactly once, with the smaller reduced component first and the larger second.

The comparison also selects the interpretation of the lookup byte:

| Reduced-component relationship | Contribution selection |
|---|---|
| Second is less than first | Use the byte directly |
| First is less than second | Use 128 minus the byte |

After the dependency returns, its signed result is shifted right by eight bit positions. That shifted value is used as the byte displacement from the base captured at entry.

For a nonnegative dependency result, the shift gives its integer quotient on division by 256. The supplied representation does not resolve the right-shift rule for negative signed results.

The function then reads exactly one unsigned byte. It performs no visible displacement mask, bounds check, negative-displacement rejection, or table-value validation.

### Contribution formation and unsigned addition

The two lookup branches differ in how they form the contribution, but **both subsequently add an unsigned contribution to the signed offset using unsigned arithmetic**.

In the direct branch, the byte is converted to an unsigned integer. Its value remains between 0 and 255.

In the complementary branch:

1. The unsigned byte is promoted to a signed integer.
2. The subtraction of the promoted byte from signed 128 occurs in signed arithmetic.
3. That signed result, ranging from −127 through 128, is converted to the unsigned contribution.

Thus the subtraction itself is not unsigned subtraction. A byte greater than 128 produces a representable negative signed difference, which is then converted modulo 4,294,967,296 under the 32-bit interpretation.

In either branch, adding the unsigned contribution to the signed offset converts the offset to unsigned and performs unsigned addition. The unsigned sum is then assigned back to the signed accumulator.

If that sum is at most 2,147,483,647, its signed value is determined. If it exceeds that limit, the signed result requires the execution environment’s out-of-range unsigned-to-signed conversion behavior.

This qualification applies **even when every table byte is between 0 and 128**. In particular, a signed offset of −128 can produce a large unsigned sum before assignment back to signed.

For example, a contribution of 109 combined with offset −128 produces unsigned sum 4,294,967,277. The signed accumulator becomes −19 only under a conversion rule that interprets that unsigned value as the corresponding 32-bit two’s-complement signed value.

Table values within 0 through 128 therefore do not, by themselves, make all lookup-derived signed results conversion-independent.

### Final upper-bound adjustment

After a diagonal increment or lookup accumulation, the signed accumulator is compared with 256:

- If it is strictly greater than 256, 512 is subtracted once.
- Otherwise, it is returned unchanged.

Exactly 256 is retained. There is no repeated modular reduction and no corresponding correction below −256.

On lookup paths, this comparison occurs **after** the unsigned sum has been converted back to signed. If that conversion is unresolved, the comparison and final result can also be unresolved.

Some negative results do not require an out-of-range conversion. For example, offset 256 plus direct contribution 19 produces representable signed value 275, after which the signed final adjustment produces −237.

Under representable normalization, table bytes restricted to 0 through 128, and conventional 32-bit two’s-complement unsigned-to-signed conversion, the results lie from −255 through 256 inclusive. This range is conditional; the function neither checks the table restriction nor establishes the conversion rule.
