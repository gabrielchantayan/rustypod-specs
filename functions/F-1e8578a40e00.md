# F-1e8578a40e00

## Purpose

F-1e8578a40e00 examines one tag-and-length item at a supplied offset within an addressable byte region. When its publication conditions hold, it writes the complete tag octet, a content length, the calculated content address, and a cursor positioned at the calculated content end.

The function reads the tag and length header. It does not inspect, copy, or recursively parse the content bytes.

**Inferred intent:** this resembles parsing a single-octet-tag, definite-length TLV item. That interpretation does not establish compliance with a named encoding standard. The function does not enforce minimal length encodings or validate content semantics.

**Established qualification:** malformed long-form headers are rejected through a status check that depends on an external error value. If that value is zero when sampled, some malformed headers can reach publication. Returning zero therefore does not, by itself, establish either header validity or output publication.

## Interface

The function takes six arguments and returns an integer status.

| Position | Role | Contract |
|---|---|---|
| 1 | Region base address | Origin for header-byte reads and the calculated content address. |
| 2 | Region bound | Unsigned upper bound for offsets measured from the region base, not a remaining-byte count relative to the initial cursor. |
| 3 | Content-length output | Receives the unsigned content length on publication. |
| 4 | Content-address output | Receives the calculated address immediately after the parsed or retained header on publication. |
| 5 | Cursor input/output | Supplies the initial unsigned item offset; receives the calculated content-end offset on publication. |
| 6 | Tag output | Receives the complete tag octet, zero-extended to the unsigned output width, on publication. |

### Widths and representation

The supplied representation distinguishes byte values, unsigned integer scalars, and signed integer scalars. It represents the region base and content-address output using integer-valued addresses.

This contract uses a **conditional 32-bit scalar model** for numerical examples:

- Bytes contain eight bits.
- Unsigned lengths, offsets, bounds, and tag-output slots contain 32 bits.
- Unsigned addition and shifting produce results modulo \(2^{32}\).
- The return status and content-address slot use the represented signed integer type.

The supplied material does not independently establish the original ABI, type definitions, native pointer width, or integer-to-address conversion rules. The 32-bit examples are conditional arithmetic consequences, not independent ABI verification.

The content-length encoding supports:

- A short-form octet containing a value from 0 through 127.
- A long-form prefix selecting one through four following length octets, interpreted most-significant octet first.

### Storage, ownership, and lifetime

The cursor location must be readable before any bounds decision is made. Every header-byte address actually accessed must be readable. Each output location reached during publication must be writable.

The declared bound does not prove that these storage requirements hold. In particular, unchecked unsigned additions can wrap and allow comparisons to pass without establishing a valid memory extent.

The body performs no allocation, release, content copy, or explicit ownership-management operation. **Ownership of the input storage and the lifetime contract of the resulting address are unknown caller/environment properties.** Supplying an address does not establish that the supplier owns the storage. Calculating and returning an address into that storage does not establish ownership transfer, a borrowing agreement, retention rights, or a guaranteed lifetime.

No null-address, alignment, output-overlap, or input/output-overlap checks are present.

## Behavior

### Initial cursor and tag access

The function first reads the unsigned initial offset from the cursor location.

It compares the region bound with the initial offset plus one. If the bound is smaller, it returns the external error value without reading the tag or writing outputs.

If that comparison passes, it reads one tag octet at the region base plus the initial offset. It rejects the tag when its low five bits equal 31. This rejection returns the external error value and performs no output stores.

No other tag bits are validated. Consequently:

- Low-five-bit values from 0 through 30 are eligible.
- The extended tag-number form indicated by low-five-bit value 31 is not parsed.
- Upper tag bits are retained in the published tag value.
- No content interpretation is selected by tag class or construction bits.

The function then calculates an offset two bytes after the initial offset. If the bound is smaller than this calculated offset, it returns the external error value without reading the length octet or writing outputs.

These preliminary comparisons use additions without separate overflow checks. Under the conditional 32-bit model, their operands can wrap before comparison.

### Short-form length

After the second preliminary comparison passes, the function reads the length-prefix octet immediately after the tag.

When its high bit is clear:

- The entire octet is the content length, from 0 through 127.
- The content offset is two bytes after the initial offset.
- The prospective success status is zero.
- No additional length octets are read.

Publication still depends on the final content-extent comparison.

A zero length is eligible. The calculated content address can therefore denote the end of the declared region, without requiring a content-byte read.

### Long-form length

When the length-prefix high bit is set, its low seven bits specify a following-length-octet count.

The function reads the external error value into its prospective status before validating that count. A long-form length is decoded only when all of the following conditions hold:

1. The count is nonzero.
2. The count is no greater than four.
3. The calculated offset after the additional length octets is no greater than the region bound.

The third condition also uses unchecked unsigned addition. A passing comparison is therefore not an independent guarantee of accessible header storage when arithmetic wraps.

For a valid count and passing header comparison, the function reads exactly the selected number of length octets in ascending logical offset order. It combines them most-significant octet first, advances the content offset past them, and sets the prospective status to zero.

Under the conditional 32-bit model:

| Following length octets | Decoded length |
|---|---:|
| `00` | 0 |
| `80` | 128 |
| `01 00` | 256 |
| `FF FF FF FF` | 4,294,967,295 |

There is no minimality check. Leading zero octets, long-form encodings of values below 128, and long-form zero lengths can pass.

The function does not implement indefinite-length parsing. A zero count is not a request to search for a terminator. Counts greater than four are not decoded.

### Invalid long-form headers and status-dependent continuation

If the long-form count or header-range validation fails, no following length octets are read.

The function then tests the prospective status previously loaded from external error storage:

- If that sampled value is nonzero, publication is disabled.
- If that sampled value is zero, execution remains eligible for the final extent check.

In the zero-status case, the candidate content length is still the complete length-prefix octet, including its high bit. The content offset remains two bytes after the initial offset.

Examples:

- An invalid prefix `80` leaves candidate length 128.
- An invalid prefix `85` leaves candidate length 133.
- A prefix requesting an otherwise supported count also retains its complete prefix value if its header-range comparison fails.

This behavior is not a decoded interpretation of those malformed headers. It is a consequence of the retained candidate length and the sampled zero status.

If publication is disabled, or the subsequent final comparison fails, the final return reads the external error value again. The final returned value is therefore not necessarily the earlier sample if the environment can change that storage. Its volatility and synchronization properties are not supplied.

### Final content extent

An eligible path publishes only if the calculated content offset plus the candidate content length is no greater than the region bound.

There is no separate addition-overflow check. Under the conditional 32-bit model, the comparison uses the wrapped unsigned sum rather than an unbounded mathematical end offset.

Consequences include:

- A mathematically excessive content extent can pass.
- A calculated end can be numerically smaller than the content offset.
- Successful publication does not prove that the described content bytes are accessible.
- No content-byte reads occur during this check.

### Publication and return

When publication is allowed, the function performs these stores in order:

1. The cursor receives the calculated content-end offset.
2. The tag output receives the complete tag octet.
3. The content-length output receives the decoded or retained candidate length.
4. The content-address output receives the region base plus the content offset.

It then returns zero.

When publication is not allowed, the function returns the external error value and performs none of these output stores.

A zero return is ambiguous if the external error value can be zero: both publication and rejection without publication can return zero.

There is no explicit recovery from invalid memory accesses. If an output store faults after an earlier store has completed, the body provides no rollback mechanism and does not translate that fault into its normal status return.

## Side effects

The explicit writes in the supplied body are the four ordered publication stores. No function calls, allocations, releases, or direct content-copy operations appear.

All header reads required for the selected path occur before publication starts. The function does not reread the cursor, tag, or length header after writing outputs.

Output overlap is not excluded:

- If the cursor and content-length output share the same scalar location, the later length store replaces the earlier cursor value.
- If another output overlaps the content-address destination, the final address store can replace earlier output bytes.
- Partial overlap depends on the target’s scalar layout and memory-access rules.

Output destinations may also overlap the input region. In that case publication can alter region bytes, even though the parsing operations themselves only read them. Such writes do not change the header values already captured for the current invocation.

The external error storage is explicitly read, not explicitly assigned. That observation does not establish immutability or exclude an output address aliasing that storage.

There are no diagnostics, callbacks, structured error records, or explicit exception-handling operations in the supplied body.

## Acceptance examples

These are conditional consequences of static inspection, not runtime test results. Except where stated otherwise, assume an initial cursor of zero, distinct valid output locations, readable header addresses, stable external error storage, and nonwrapping address calculations. Byte sequences describe region prefixes, not necessarily complete allocations.

1. **Short-form content**

   With prefix `04 03 AA BB CC` and bound 5, publication occurs. The return is zero, tag is 4, length is 3, content address is base plus 2, and cursor becomes 5. The three content bytes are not read.

2. **Empty content**

   With prefix `04 00` and bound 2, publication occurs with length zero, content address base plus 2, and cursor 2. The function does not dereference the calculated content address.

3. **Nonzero initial cursor**

   With initial cursor 2, a tag `04` at offset 2, length `01` at offset 3, and bound 5, publication produces content offset 4 and cursor 5. The bound is an absolute offset bound from the base, not a count of bytes remaining after offset 2.

4. **Trailing bytes**

   With prefix `04 01 AA BB` and bound 4, publication sets cursor 3. The byte at offset 3 is neither inspected nor included in the item’s calculated extent.

5. **Nonminimal long form**

   With prefix `04 82 00 01 AA` and bound 5, publication produces length 1, content offset 4, and cursor 5. Neither the leading zero nor the unnecessary long form causes rejection.

6. **Upper tag bits retained**

   With prefix `A4 00` and bound 2, publication produces tag 164 and length zero. Upper tag bits do not select a different length parser.

7. **Unsupported extended tag**

   With prefix `1F 00` and bound 2, the function returns the external error value without publication. If that value is zero, the return is zero but the outputs remain unchanged.

8. **Insufficient declared content extent**

   With prefix `04 03 AA` and bound 3, the final comparison fails. No output stores occur; the function returns the external error value.

9. **Invalid count with nonzero external error**

   With second octet `80` or `85` and a sampled nonzero external error value, publication is disabled. No following length octets are read.

10. **Invalid count with zero external error**

    With prefix `04 80`, bound 130, and sampled external error value zero, publication occurs with length 128, content offset 2, cursor 130, and return zero. This is not indefinite-length decoding. No content bytes are inspected.

11. **Unsupported five-octet count with zero external error**

    With prefix `04 85`, bound 135, and sampled external error value zero, publication occurs with retained length 133 and cursor 135. The function does not read five length octets.

12. **Wrapped content end**

    Under the 32-bit unsigned model, prefix `04 84 FF FF FF FF` with bound 6 decodes length 4,294,967,295 and content offset 6. Their sum wraps to 5, so publication occurs with cursor 5 and content address base plus 6. This does not establish accessibility of the described content extent.
