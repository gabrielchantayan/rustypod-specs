# F-46e7f9a196d3

## Purpose

F-46e7f9a196d3 creates and attaches a node to a tree-like container, performs color-based structural repair, forces the resulting root’s color byte to 1, and returns the new node address through an output slot.

The visible structure is consistent with red-black-tree insertion: nodes contain parent and child links, repair uses recoloring and paired rotation-like dependencies, and a header tracks the root and two extremal nodes. This interpretation is inferred intent. The established contract is the sequence of accesses, decisions, dependency calls, and writes below; complete red-black-tree correctness depends on initialization and dependency behavior not supplied here.

The caller supplies the intended parent and an attachment override. This function does not search for an insertion position, reject duplicates, or establish that the supplied position respects an ordering relation.

### Preconditions for ordinary successful use

The output slot, container fields, proposed parent links, source field at +4, and all nodes reached during repair must support the accesses described below. Objects and dependency-produced addresses must be suitably aligned for the target’s 4-byte accesses.

The supplied parent must represent a valid attachment position. Existing links must support parent/grandparent traversal and repair. The visible routine provides no structural validation, cycle detection, capacity check, or duplicate-key check.

These are conditions for the intended tree operation, not checks performed by the function. Aliasing is not rejected. An output slot that overlaps container or node storage may overwrite that storage at the final step.

## Behavior

### 1. Obtain a node and process its payload

The first dependency call is F-3affa7926e3f, with the container address as its sole visible argument. Its result is retained as the new node address.

The function forms the address 0x10 bytes beyond that result. If the formed address is nonzero, it:

1. Calls F-f4fd698ba468 with the formed address and the source-value address.
2. Copies the 4-byte field at source offset +4 into the 4-byte field at offset +4 from that dependency’s result.

The payload dependency’s return value is therefore used as a destination base. The visible code does not establish that this result equals the new node’s payload address.

The nonzero check applies to the **formed payload address**, not directly to the new node address. It is not a conventional node-allocation failure check: a zero node result would ordinarily produce a nonzero payload address of 0x10. No early error return is visible.

The payload call precedes the direct source-field copy. Both precede the counter increment. The relative evaluation order of the source-field read and evaluation of the destination address is not independently established.

### 2. Increment the container counter

After payload processing, the function reads the 4-byte field at container offset +0x14, adds one, and writes it back.

The increment precedes the attachment decision, comparison call, link writes, and balancing. No overflow check or rollback is visible.

The representation establishes a 32-bit counter update. Portable signed-overflow semantics are not established by this listing. For a normal-use contract, the counter must remain in its valid representable range; behavior at the signed maximum remains documented_only rather than being assigned an unsupported overflow policy.

### 3. Select the attachment side

The function takes the left-attachment path without comparison if either condition holds:

- The proposed parent equals the header currently obtained from container offset +0x10.
- The attachment override is nonzero.

Otherwise, it calls F-31a0b2b5649a with:

1. The container address plus 0x19.
2. The source-value address.
3. The proposed parent address plus 0x10.

A nonzero result selects left attachment. A zero result selects right attachment.

Only zero versus nonzero is tested. A conventional negative/zero/positive comparator contract is not established, and must not be substituted for this predicate.

Before making this comparison call, the function also sets two auxiliary values to zero. If comparison is bypassed, those values instead retain the attachment override and proposed parent address. They are exposed only through one repair dependency call described below.

### 4. Attach the new node and update header links

For left attachment:

- Write the new node address into the proposed parent’s left-child field at +0x08.
- Reload the header address from the container.
- If this header equals the proposed parent:
  - Write the new node address into the header’s root field at +0x04.
  - Reload the header address again and write the new node address into its +0x0c field.
- Otherwise, inspect the reloaded header’s +0x08 field. Replace it with the new node address only if it equals the proposed parent.

Thus, when the proposed parent is a stable header, this path initializes all three header links: +0x08, +0x04, and +0x0c, in that order.

For right attachment:

- Write the new node address into the proposed parent’s right-child field at +0x0c.
- Reload the header address from the container.
- Replace the header’s +0x0c field with the new node address only if its existing value equals the proposed parent.

After the side-specific writes, write the proposed parent address into the new node’s parent field at +0x04.

The header reloads matter. In particular, a comparison dependency that changes the container’s header can affect later header maintenance. The function does not visibly preserve one immutable header value across the operation.

### 5. Repair color and structure

Repair begins with the new node as the current repair node.

At each iteration, the function first reloads the root through the container’s current header. If the current repair node equals that root, repair ends. Otherwise, it reads the current node’s parent. If the parent’s color byte is nonzero, repair ends.

When the parent is red, the function obtains the grandparent and inspects the grandparent’s left-child link.

**Parent is the grandparent’s left child**

The uncle is the grandparent’s right child.

- If the uncle exists and its color byte is zero:
  - Set the parent’s color to 1.
  - Set the uncle’s color to 1.
  - Set the current node’s grandparent color to 0.
  - Continue repair with that grandparent as the current node.
- Otherwise:
  - If the current node is its parent’s right child, call F-bff5bbe8ab77 with the container and parent. Then use the former parent as the current repair node.
  - Set the current node’s parent color to 1.
  - Set that parent’s parent color to 0.
  - Call F-3008804f5ed8 with the container and the grandparent obtained through the then-current links.

**Parent is not the grandparent’s left child**

The function uses the grandparent’s left child as the uncle. It does not separately validate that the parent equals the grandparent’s right child.

- If the uncle exists and its color byte is zero, perform the same parent/uncle/grandparent recoloring and upward continuation.
- Otherwise:
  - If the current node is its parent’s left child, call F-3008804f5ed8, then use the former parent as the current repair node.
  - Set the current node’s parent color to 1.
  - Set that parent’s parent color to 0.
  - Call F-bff5bbe8ab77 with the container and the grandparent obtained through the then-current links.

The inner F-3008804f5ed8 call in this mirrored case is shown with six arguments. After the container and parent, it receives:

- The uncle address.
- The grandparent address if the uncle is absent; otherwise, the uncle’s nonzero color byte widened to a 32-bit value.
- The first auxiliary value established during attachment selection.
- The second auxiliary value established during attachment selection.

Other calls to that dependency show only two arguments. Whether the additional arguments are semantically consumed is unknown.

Repair uses links read after dependency calls. Its correctness therefore depends on what those dependencies actually change; it cannot be specified as though they preserve all container fields or links.

### 6. Finalize and publish the result

After repair ends, the function:

1. Reloads the header and root through the container.
2. Writes color byte 1 into that root.
3. Writes the original new node address into the caller’s 4-byte output slot.

The published address is the created node, not the final repair node or necessarily the root.

There is no success flag. Normal completion is indicated only by reaching the final output write.

## Acceptance examples

These examples are conditional static expectations, not runtime test results.

1. **First insertion with a stable header.**  
   Given the header as proposed parent, valid initialized node storage, and dependencies that leave the header stable, comparison is skipped. The header’s left, root, and right links become the new node address. The new node’s parent becomes the header. Repair immediately recognizes the new root, writes its color to 1, and publishes its address.

2. **Forced left attachment.**  
   Given a non-header parent and any nonzero override, comparison is skipped and the parent’s left link is replaced. The header’s left-extremal link changes only if it previously equaled that parent. The function does not check whether this replacement overwrites an existing subtree.

3. **Predicate-selected right attachment.**  
   Given a non-header parent, zero override, and comparison result zero, the parent’s right link is replaced. If the header’s right-extremal link equals that parent, it advances to the new node; otherwise it is left unchanged.

4. **Nonzero is not a comparator sign convention.**  
   Under the same conditions, a comparison result represented as either positive or negative selects left attachment because both are nonzero.

5. **Black parent.**  
   Given a non-root insertion whose parent color is nonzero, repair performs no rotation-like dependency call and no uncle inspection. Finalization still writes 1 to the root color before publishing the node.

6. **Red parent and red uncle.**  
   Given a valid grandparent and an existing uncle with color zero, repair writes parent color 1, uncle color 1, and grandparent color 0, then continues from the grandparent.

7. **No ordinary null-allocation recovery.**  
   If node acquisition returns zero, the visible payload-address check does not provide a normal failure return. Successful handling of such a result is not an acceptance requirement established by this function.
