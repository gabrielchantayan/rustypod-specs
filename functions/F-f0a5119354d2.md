# F-f0a5119354d2

## Purpose

F-f0a5119354d2 prepares a shared descriptor and two fields in a caller-supplied structure, waits for a control interface to become available, issues one control write and two record-dependent command pairs, and finally updates a shared selector.

The established behavior is a sequence of memory reads, memory writes, and busy waits. Interpreting these operations as configuring a device or switching buffers is inferred intent, not an established interface guarantee. In particular, a command write is not evidence that the device has completed the commanded operation.

The function has no explicit return value, error result, timeout, allocation, or dependency call.

## Interface

### Arguments

The function accepts two address-bearing arguments:

- **Input A:** a structure supplying two 32-bit values, at byte offsets `0x14` and `0x18`.
- **Input B:** a writable structure supplying a 32-bit value at offset `0x0C`, receiving values at offsets `0x10` and `0x24`, and supplying two record indicators at offsets `0x00` and `0x14`.

The available source represents these arguments as integer values used in address calculations. It does not establish a public pointer type, calling convention, alignment contract, or address-space mapping.

For ordinary non-overlapping structures, the accessed extents are:

| Region | Required accessed bytes |
|---|---|
| Input A | `0x14`–`0x1B`, read |
| Input B | `0x00`–`0x03`, `0x0C`–`0x13`, `0x14`–`0x17`, and `0x24`–`0x27`, with the read/write roles described below |

These extents describe accesses, not validated buffer lengths. The function performs no bounds or address validation.

## Behavior

### 1. Initial shared-state and descriptor updates

The function first captures a shared-state base address for later selector access. It then writes a single zero byte through the shared-state global address.

It next obtains the shared descriptor base and performs these descriptor writes in order:

1. Reads the 32-bit value at Input B offset `0x0C` and stores it at descriptor offset `0x18`.
2. Reads Input B offset `0x0C` again, adds `0x200`, and stores the result at descriptor offset `0x1C`.
3. Stores the 32-bit value `3` at descriptor offset `0x0C`.
4. Reads Input A offset `0x14` and stores that value at descriptor offset `0x2C`.
5. Reads Input A offset `0x18` and stores that value at descriptor offset `0x3C`.

The two reads of Input B offset `0x0C` are distinct. The second result is not derived from a retained copy of the first. Consequently, under aliasing or externally changing memory, the descriptor fields at `0x18` and `0x1C` need not differ by `0x200`.

There is also a base-binding distinction: the destination base for the first descriptor-field write is obtained through the global binding again, while the later descriptor writes use the previously captured descriptor base. With stable global bindings these identify the same region. If those bindings can change during execution, a single-descriptor interpretation is not guaranteed.

### 2. Selector-dependent Input B updates

After all five descriptor writes, the function reads the 32-bit selector at offset `0x58` of the captured shared-state region.

It chooses a value according to the entire selector:

- If the selector is exactly zero, it reads Input A offset `0x14`.
- Otherwise, it reads Input A offset `0x18`.

This is a new read from Input A, not reuse of the value previously written into the descriptor.

The function then:

1. Stores the chosen value at Input B offset `0x10`.
2. Stores the chosen value plus `8` at Input B offset `0x24`.

The choice is a zero-versus-nonzero decision. It is not a test of only the selector’s low bit.

### 3. Control-interface wait and write

The function repeatedly reads the 32-bit control status at offset `0x14` until bit mask `0x00010000` is clear.

- Other status bits do not affect this wait.
- An initially clear bit permits progress after the first status read.
- A permanently set bit causes an unbounded busy wait.
- The control-interface global base is consulted repeatedly during this polling phase.

After the condition is satisfied, the function writes the following 32-bit value to control-interface offset `0x0C`:

\[
(\text{captured selector} \ll 30)\ \mathbin{\mathrm{OR}}\ 0x00000080
\]

The shift is a 32-bit unsigned shift. Only the selector’s lowest two bits contribute to the shifted result. Bits above those two are discarded.

This write uses the selector captured before the wait. The selector is not reread when the wait ends. The control destination is addressed through the global control-interface binding at the write.

### 4. Two ordered record commands

After the control write, the function captures the shared command value and then the command-interface base. It processes exactly two records, in increasing index order.

The record indicators are 32-bit reads from:

- First record: Input B offset `0x00`.
- Second record: Input B offset `0x14`.

Thus, the indicator positions have a stride of `0x14` bytes. The function does not copy either record or inspect any additional record field.

For each record:

1. It reads that record’s indicator.
2. It normalizes the indicator to zero if the entire 32-bit value is zero, or one otherwise.
3. It repeatedly reads command-interface status at offset `0x11808` until bit mask `0x00000002` is clear.
4. It writes the captured shared command value OR-combined with the normalized indicator shifted left by 19 to offset `0x11800`.
5. It writes `0x31` OR-combined with the normalized indicator shifted left by 3 to offset `0x10C`.

The second record’s indicator is not read until both writes for the first record have occurred.

For a zero indicator, the second write is `0x31`. For any nonzero indicator, it is `0x39`. For the first write, a nonzero indicator adds bit `0x00080000` by OR; a zero indicator does not clear that bit if the captured shared command value already contains it.

Each record has its own status wait. There is no additional wait between its two writes, and no completion wait after the second record’s final write.

### 5. Final selector update

After both record command pairs, the function writes the captured selector XOR `1` to offset `0x58` of the captured shared-state region.

This flips only bit zero:

- `0` becomes `1`.
- `1` becomes `0`.
- `2` becomes `3`.
- `3` becomes `2`.

The function does not normalize the selector to a Boolean. It also does not reread the shared selector before writing, so this operation can overwrite an intervening update by another actor.

The function then returns without an explicit result.

## Side effects

### Observable ordering

The shown sequence imposes the following logical access order:

1. One-byte shared-state clear.
2. Five descriptor writes.
3. Selector read and two Input B writes.
4. Control-status polling.
5. One control write.
6. Capture of the shared command value and command-interface base.
7. First record read, status polling, and two command writes.
8. Second record read, status polling, and two command writes.
9. Final selector write.

These are source-visible access-order facts. The available evidence does not establish processor barriers, device-bus ordering, atomicity, or compiler treatment of the polling locations.

### Partial effects and nontermination

There is no rollback.

If control-status polling never finishes, the initial shared-state clear, descriptor writes, and Input B writes have already occurred. No record commands or final selector write have occurred.

If a record-status wait never finishes:

- The control write has already occurred.
- That record’s indicator has already been read.
- Earlier record commands, if any, remain issued.
- The final selector write has not occurred.

An invalid access has no defined error-reporting path in the supplied evidence. The function does not return a failure status or attempt recovery.

### Aliasing and external mutation

No non-aliasing guarantee is present. The listed reads and writes must therefore be understood in sequence, rather than as a transformation of an immutable entry snapshot.

For example:

- A descriptor write may affect a later Input A or Input B read if regions overlap.
- The descriptor copy of an Input A field and the later selected value may differ.
- The command value is captured only after the control write.
- Both record commands use the same captured command value and command-interface base.
- The final selector value is based on the earlier selector read, regardless of intervening memory changes.

The consequences of overlapping hardware registers, changing global bindings, or concurrent access cannot be reduced to ordinary disjoint-memory examples without additional preconditions.

## Acceptance examples

The following are conditional static acceptance cases, not runtime test results. Unless stated otherwise, they assume stable global bindings, disjoint ordinary data regions, valid accesses, no concurrent mutation, and status bits that permit progress.

### Zero selector

Given:

- Selector `0`.
- Input A values `0x1000` at `0x14` and `0x2000` at `0x18`.
- Input B value `0x3000` at `0x0C`.

Required effects include:

- Descriptor `0x18` receives `0x3000`.
- Descriptor `0x1C` receives `0x3200`.
- Descriptor `0x0C` receives `3`.
- Descriptor `0x2C` and `0x3C` receive `0x1000` and `0x2000`.
- Input B `0x10` receives `0x1000`; `0x24` receives `0x1008`.
- The control write is `0x00000080`.
- After both record command pairs, the selector becomes `1`.

### Nonzero selector beyond the Boolean range

Given selector `2` and the same Input A values:

- Input B receives `0x2000` and `0x2008`.
- The control write is `0x80000080`.
- The final selector is `3`.

This distinguishes the nonzero selection rule from a low-bit selection rule.

### Record indicator normalization

Given a captured shared command value of `0x20`, first indicator zero, and second indicator `0x80000000`, the command-interface writes are:

| Record | Offset `0x11800` | Offset `0x10C` |
|---|---:|---:|
| First | `0x00000020` | `0x31` |
| Second | `0x00080020` | `0x39` |

The second indicator’s magnitude and sign interpretation do not matter; it is nonzero.

### OR preserves an already-set command bit

Given a captured command value of `0x00080020`, either indicator value produces `0x00080020` at offset `0x11800`. A zero indicator does not clear bit 19.

### Busy waits expose partial progress

If control-status bit `0x00010000` stays set indefinitely, the descriptor and Input B updates still precede the stalled wait. The control write, both record command pairs, and final selector update do not occur.

If only the second record’s wait remains busy indefinitely, the first record’s command pair has occurred, but the second pair and final selector update have not.
