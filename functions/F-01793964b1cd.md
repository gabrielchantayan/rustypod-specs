# F-01793964b1cd

## Purpose

F-01793964b1cd selects and invokes an external target, then attempts a sequence of memory publications, clears, and shared-state updates. Its observable behavior depends on the invocation result, two explicit inputs, ambient values, and shared storage that may overlap.

The contract is an ordered-effects contract, not a success protocol. The available evidence establishes no validation, rollback, ordinary return value, or confirmed normal return. A calculable destination does not establish that the destination is writable or that execution reaches its associated write.

**Established static evidence:** One dynamically selected invocation precedes all described continuation effects. The continuation includes fixed-width indirect writes and assignments to shared storage of unresolved width.

**Inferred intent:** Some shared-state updates may prepare control-related state. No guarantee of handler installation, executable-object publication, or successful subsequent control transfer follows.

**Verification status:** Static analysis only. No runtime tests have been performed.

| Third | Unsigned 32-bit request value. Used as publication data and in destination and shift calculations. |

No relationship between the unused positions and the continuation is established. Their significance outside the represented behavior, argument transport, and the complete entry convention are **documented_only**.

### Ambient inputs and dependency result

An unsigned 32-bit ambient dispatch basis selects the external invocation target. A separate opaque four-byte ambient payload supplies publication data after that invocation.

The origins, availability, and preservation of these values are **documented_only**. In particular, the payload must not be assumed unchanged by the invocation.

The selected dependency, **F-D01**, receives one explicit argument with numerical value zero. A returning invocation supplies an opaque eight-byte result. The continuation uses:

- A signed 32-bit conversion of that result.
- The upper 32 bits of its unsigned 64-bit interpretation.
- A signed 16-bit conversion of the result.

These interpretations are independent. None establishes allocation success, pointer ownership, or a relationship between two memory regions.

### Shared storage

### Outputs and ownership

There is no explicit allocation or release in the continuation. Address publication alone establishes neither ownership transfer nor permission to retain, execute, modify, or release the designated object. F-D01’s resource and ownership behavior is unknown.

## Behavior

### Dispatch and continuation eligibility

The numerical target is selected by clearing the lowest two bits of the dispatch basis and increasing the resulting unsigned 32-bit value by 3,280. The addition wraps modulo 4,294,967,296. Dispatch bases differing only in their lowest two bits select the same numerical target.

Invocation additionally requires an applicable address interpretation, an executable target, and a compatible calling interface. These requirements are not validated by the visible behavior.

If F-D01 does not return, the continuation is not reached. If it returns, no preservation of shared storage, ambient payload, memory mappings, or resources may be assumed without a separate dependency contract.

### Publication obligations

Before shared-state preparation, the continuation attempts the following publications:

| Publication | Destination | Data and width |
|---|---|---|
| Request publication | Signed 32-bit conversion of the dependency result, increased by 100 | Request value, four bytes |
| Payload publication | Upper 32 bits of the dependency result’s unsigned 64-bit interpretation | Ambient payload, four bytes |
| Shift-derived publication | Request-derived shifted value, increased by 12 | Signed 16-bit conversion of that shifted value, two bytes |
| Result-derived publication | Request increased by 42 with unsigned 32-bit arithmetic | Signed 16-bit conversion of the dependency result, two bytes |

The request-derived shifted value is obtained from the signed 32-bit conversion of the request, shifted right by a count equal to the request’s lowest eight bits.

The ordering has observable consequences:

- The request publication precedes evaluation of the request-derived shift.
- That shift is evaluated before the payload publication.
- The payload publication precedes the shift-derived publication.
- The shift-derived publication precedes the result-derived publication.

Consequently, an invalid shift cannot be bypassed merely because the payload destination is independently calculable. Likewise, knowing the result-derived destination does not establish that its write occurs.

The table describes numerical destination relationships. It supplies no pointer provenance, storage lifetime, accessibility, or alignment guarantee.

### Arithmetic and conversion boundaries

The request and selector are unsigned 32-bit values. Their unsigned additions and subtractions wrap modulo 4,294,967,296.

The request-derived shift has a 32-bit signed operand and a count between zero and 255. Counts of 32 or greater have no established shifted result. Hardware-specific masking of the count is not guaranteed.

For requests from zero through 2,147,483,647, conversion to signed 32-bit form is representable. When the count is below 32, the operand is nonnegative and the right-shift result is determined. Within this subset, increasing the shifted value by 12 also remains representable. In particular, a zero count requires the request’s lowest byte to be zero, excluding values immediately below the signed maximum that could otherwise make this addition overflow.

Requests above 2,147,483,647 require an applicable out-of-range conversion rule. If that conversion produces a negative value, negative right-shift behavior also matters. Both rules are **documented_only**.

The request publication has a separate boundary: increasing a signed 32-bit result conversion greater than 2,147,483,547 by 100 exceeds the signed 32-bit range. Unsigned wraparound is not an established substitute.

Signed 16-bit values from −32,768 through 32,767 are representable. Conversions outside that interval are **documented_only**; unconditional low-bit truncation is not guaranteed.

### Clearing and shared-state preparation

After the four publications, the selector controls a one-byte zero write. Its upper six bits provide a value from zero through 63. Subtracting 208 using unsigned 32-bit arithmetic produces a numerical destination in the inclusive range 0xFFFFFF30 through 0xFFFFFF6F. The selector’s lower 26 bits do not affect this destination.

A four-byte zero write follows. Its destination is derived from the contents of the clearing basis with displacement 12—not from the address of the storage holding that basis. Whether this displacement denotes twelve bytes depends on the unavailable declaration.

Only after both clears does the shared-state preparation occur:

- Primary state receives the state source.
- The first reset slot receives zero, followed by the second reset slot.
- The control slot receives numerical value 4,294,967,200.

These assignments do not establish four-byte storage widths. In particular, the control assignment does not independently establish a stored signed value of −96.

### Marker, state, and reference publication

Following preparation, a four-byte marker with numerical value 1,200 is written at a destination derived from a new observation of the state source with displacement 16.

The first reference slot then receives the designated object’s address. After that assignment, a four-byte state publication uses:

- Primary state with displacement 20 as its destination.
- Primary state shifted right by 29 as its data.

The second reference slot receives the designated object’s address after this state publication.

The primary-state shift has no explicit conversion establishing a signed 32-bit operand. Its operand type, promotions, width, signedness, and treatment of negative values depend on the unavailable declaration. The rules established for the request-derived shift must not be imported into this separate operation.

The displacement units for both state-related destinations remain **documented_only**.

### Observation order and overlap

The represented ordering must be preserved wherever overlap makes it observable:

- The selector-controlled clear precedes consumption of the clearing basis. It may therefore alter the basis used for the next clear.
- The state source is consumed once for initialization and again for the marker destination. The later observation is not guaranteed to equal the earlier one.
- Reset and control assignments intervene between those observations and may change the later value through overlap.
- The first reference assignment precedes consumption of primary state for its publication and may change that state.
- The state publication precedes the second reference assignment and may overwrite the first reference slot.

Primary state participates in both the destination and the data of one publication. The evidence does not establish a single captured snapshot, the relative evaluation order of those uses, or an exact number of physical reads.

Earlier indirect writes may also modify storage consumed later. Reusing an earlier observation requires independently established equivalence under the actual layout and execution environment.

### Preconditions, errors, and termination

Every reached access requires an appropriate address interpretation, live storage, sufficient extent, required alignment, and applicable permissions.

No visible check converts invalid access, invalid arithmetic, or dependency failure into a recoverable result. There is no explicit error report or rollback. A failing operation must not be modeled as a successful no-op, and partial visibility of a faulting write is not established.

The represented control flow terminates at an unresolved instruction boundary. Neither normal return nor a particular trap, exception, or additional ordinary invocation is established.

## Acceptance examples

These are conditional deductions, not executed tests. Each assumes execution reaches the relevant operation and that all preceding arithmetic, conversion, and access requirements are satisfied.

### Dispatch equivalence

Dispatch bases from 0xFFFFFFF0 through 0xFFFFFFF3 select numerical target 0x00000CC0 after unsigned wraparound. Selecting different targets solely because their lowest two bits differ would violate the selection rule.

This does not establish that the selected target is executable.

### Independent result uses

For a dependency result of 4,096:

- The request publication destination is 4,196.
- The payload publication destination is zero.
- The result-derived two-byte publication carries signed value 4,096.

Using 4,196 as the payload destination would incorrectly merge separate result interpretations. A write at address zero still requires valid writable storage there.

### Shift boundary

Request 256 gives count zero and shifted value 256. The shift-derived destination is 268, its two-byte data is signed value 256, and the result-derived destination is 298.

Request 288 gives count 32. No shifted result is established. Treating it as a zero-count shift, or guaranteeing the later payload publication, adds unsupported behavior.

### Conversion and overflow are distinct

A dependency result of 32,768 gives request-publication destination 32,868, but its signed 16-bit conversion remains **documented_only**.

A result of 2,147,483,647 has a representable signed 32-bit conversion, but increasing that conversion by 100 exceeds the signed range. No wrapped destination is guaranteed.

### A destination does not guarantee execution

Request 0xFFFFFFF0 gives result-derived destination 0x0000001A through unsigned wraparound.

Earlier processing nevertheless involves an out-of-range signed conversion and shift count 240. The calculable destination does not establish that its publication occurs.

### Selector and clearing-basis interpretation

Selector zero gives byte-clear destination 0xFFFFFF30. Selector 0xFC000000 gives 0xFFFFFF6F. Changing only the lower 26 bits leaves the destination unchanged.

If the clearing basis contains 0x00005000 when consumed, and displacement is byte-based, the four-byte clear targets 0x0000500C. Clearing relative to the address of the basis-holding storage would be different behavior.

### Distinct shared observations

Assume compatible declarations and byte-based displacement. If initialization consumes state-source value 0x00003000 but the marker calculation later observes 0x00004000, the marker destination is 0x00004010.

For a stable unsigned 32-bit primary state of 0x80000000, its right shift by 29 yields 4. For signed 32-bit primary state −2,147,483,648 under arithmetic negative right shift, it yields −4. The available declarations do not select either case.
