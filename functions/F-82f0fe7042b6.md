# F-82f0fe7042b6

## Purpose

F-82f0fe7042b6 obtains two 32-bit values from a shared service, passes those values and a caller-supplied 32-bit argument to an object-initialization dependency, and dispatches the resulting 32-bit value to one of two destinations.

The destination is selected by whether the third argument is null:

- When null, dispatch uses the first argument and a function-table entry at byte offset `0x1C4`.
- When non-null, dispatch uses the third argument and a function-table entry at byte offset `0x5C`.

Both branches request `0x14` bytes of storage and invoke the same initialization dependency before resolving the destination’s dispatch entry.

This is an established description of the visible operations, not a claim about application-level meaning. Interpreting the allocated storage as a newly created object and the final dispatch as attaching or registering it is plausible intent, but not established.

## Behavior

### 1. Capture the shared base and perform the first service query

Before the first service callback, the function retains the current shared base address for later use.

The first callback is resolved through the shared service receiver at byte offset `0x18`. Its callable entry is read from byte offset `0x78` in that receiver’s function table.

The callback receives:

1. The service receiver.
2. The caller’s unchanged 32-bit value.

Its 32-bit result is retained as the first query result.

This callback is completed before the second service callback is invoked. There is no visible validation of its return value and no visible conditional branch based on that value.

The first callback’s receiver access is expressed through the shared global location, whereas the subsequent query uses the retained base address. The evidence does not justify a stronger atomicity or concurrency guarantee for these reads.

### 2. Reload the service receiver and perform the second query

After the first callback returns, the function obtains a service receiver from byte offset `0x18` of the previously retained base address.

It does not simply reuse a service-receiver pointer captured before the first callback. Consequently, a change to that field during the first callback can affect the receiver used by the second callback.

The second callback is resolved through byte offset `0x7C` of the function table belonging to this subsequently obtained receiver.

It receives:

1. That service receiver.
2. The same unchanged caller value.

Its 32-bit result is retained as the second query result.

The second query is not visibly skipped for null destinations, unusual query results, or any particular caller value. Both query results are passed onward without visible interpretation.

The retained base address matters independently of the global location. If the first callback changes only the global base pointer, the later service lookup still uses the retained base. If it changes the service-receiver field inside the retained base, the later lookup can observe that field change. These statements describe the explicit data dependencies; validity of the affected memory remains a precondition.

### 3. Select the destination branch

The branch determines which destination and table offset are used later. It does not change the allocation request, initialization dependency, or order of the two service queries.
