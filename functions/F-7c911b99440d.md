# F-7c911b99440d

## Purpose

The supplied static representation does not establish a higher-level purpose. In particular, it does not justify describing this operation as object initialization, list manipulation, serialization, string construction, or resource management. Several stores resemble link updates, but the same regions also receive small constants and truncated addresses.

The contract is therefore a low-level memory-effect contract. Intermediate writes, repeated reads, overlapping access widths, and the final indirect transfer are behaviorally significant. A simplified “final object contents” description would not preserve the supplied behavior.

### Entry effects

The first observable effects are the two byte writes at control offset `0x09`: second byte first, first byte second.

Only afterward does the routine read the source word at offset `0x74`, followed by the companion word at offset `0x14`. It forms a value by adding `0x20` to the latter word.

It then reads an address from control offset `0x64` and writes the working address as a four-byte value to offset `0x14` of that destination. The low byte of the companion-derived sum is written to companion offset `0x11`.

These writes occur before the routine traverses the working region.

### Initial working-region traversal

Working offset `0x44` is read twice in succession. One result is retained as data; the other is used as an address. These are distinct reads in the supplied sequence, even though ordinary unchanged memory would return equal words.

The routine also reads a byte from the address obtained by doubling the unsigned control value. That byte is converted through the represented character type, shifted right by a count taken from the control value’s low eight bits, and narrowed to a byte.

The result is written to:

- Offset `0x08` of the address obtained from working offset `0x44`.
- Working offset `0x11`.

Between those stores, the earlier word from working offset `0x44` is copied to working offset `0x74`.

The companion-derived sum is written as a four-byte value to companion offset `0x54`; the previously captured source word immediately replaces it there. The sum’s low byte is subsequently written to companion offset `0x19`.

The working address is written to offset `0x44` of the region reached through working offset `0x44`. The companion-derived sum is also written to offset `0x74` of the original region reached through companion offset `0x14`.

These effects are address-sensitive. They do not establish independent objects or a conventional linked structure.

- Stores the first global word’s low sixteen bits at twice a previously captured address.

- Repeats the earlier halfword store at the first summed destination.

It then reads the second global word, the third global word, and a current offset-`0x44` word, in that order. Following those reads, it:

- Writes byte `0x44` at offset `0x44` of the character-derived base.
- Writes the third global word as four bytes at twice the second global word.

The four-byte store at base plus `0x45` is potentially unaligned. The required machine behavior for such an access is not established.

Finally, the unresolved target is invoked with:

2. The second global word.
3. The word read from the current offset-`0x44` field.

The OR operation is not addition and does not necessarily produce the address used by the preceding byte store.

## Acceptance examples

These are conditional acceptance criteria, not executed tests.

### Entry write ordering

Given a writable control byte and an observer capable of recording accesses, the first two writes must target control offset `0x09`, carrying the second byte and then the first byte.

If the source read subsequently faults, the routine has already attempted both writes. An implementation that validates the source before those stores changes the visible ordering.

### Narrowing a captured word

If the source word captured at offset `0x74` is `0x123456AB`, a later byte store explicitly derived from that captured word carries `0xAB`. A four-byte copy of that word carries the entire `0x123456AB`.

This does not require the source memory to remain unchanged after the capture.

### Mixed-width replacement

Where the routine writes four-byte `0x74` after writing byte `0x74` at the same offset-`0x10` destination, the later operation replaces four bytes, not merely the original byte.

The byte arrangement of those four bytes is target-endian-dependent.

### Aliased link fields

If an earlier destination overlaps a link field read later, the later traversal uses the field value present at that later read. Continuing through an entry-time snapshot is not equivalent.

Whether a particular alias arrangement permits the entire routine to complete is a separate precondition.

### Final invocation arguments

If the character-derived value is `0x20` and the final three computed stores succeed, the first indirect argument is `0x64`, because `0x20` OR `0x44` equals `0x64`.

The immediately preceding byte store instead targets address `0x64` by adding offset `0x44` to base `0x20`; equality in this example is incidental, not a general identity between OR and addition.

### Failure before invocation

If a final halfword destination is unwritable and the machine traps on that store, the indirect invocation is not reached. The visible body provides no recovery or rollback path.
