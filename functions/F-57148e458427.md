## Behavior

### Common prefix and dispatch

The function first reads source offset 0 and writes that observed byte to destination offset 4. It then reads source offset 0 again and selects a branch using this second observation.

These are two reads in the supplied representation, with one byte write between them and no intervening dependency call.

For ordinary byte-addressed storage without external mutation or access-triggered side effects, both observations agree:

- If destination offset 4 is the same address as source offset 0, the write puts the first observed tag value back at that address.
- Otherwise, the write does not modify source offset 0.

Consequently, ordinary storage aliasing alone cannot make the recorded tag differ from the dispatched tag. Intervening external mutation could do so. Behavior involving memory-access side effects is unresolved; no device-memory or similar access contract is supplied.

The function does not snapshot the source payload. The branch descriptions below use the second tag observation, and later payload reads remain susceptible to effects of earlier writes or dependencies.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not runtime test results. Unless stated otherwise, assume valid, ordinary, disjoint storage without intervening external mutation, and normal return from reached dependencies.

1. **Tag-only path.** With source tag `0x05`, destination offset 4 receives `0x05`. No dependency is invoked, and no other destination byte is explicitly written.

2. **Aliased tag location remains consistent.** If destination offset 4 aliases source offset 0 and the first observed tag is `0x03`, the intervening write puts `0x03` back at that address. The second observation is also `0x03`. Ordinary aliasing does not select a different branch.

3. **External tag mutation.** If an external actor changes source offset 0 from `0x05` to `0x03` after the tag write but before the second read, destination offset 4 records the first observation while dispatch follows `0x03`. This is a conditional access-order example, not a synchronization guarantee.

4. **Ordered transfer without overlap.** With tag `0x03` and source offsets 1 through 3 containing `0xA1`, `0xB2`, and `0xC3`, destination offsets 6 through 8 receive those values, respectively, in ascending write order.

5. **Overlap changes a later payload read, not the tag.** Let the destination base be four bytes before the source base, with valid writable overlapping storage. For tag `0x00`, destination offset 4 aliases source offset 0, so the tag remains `0x00`. If source offsets 1 and 2 initially contain `0xA1` and `0xB2`, the first transfer writes `0xA1` to destination offset 6, which aliases source offset 2. The second transfer consequently reads `0xA1`, not the original `0xB2`, and writes it to destination offset 7.

6. **Status after preparation.** For tag `0x04`, a nonzero source byte at offset 1 when read after F-EXT-01 prevents F-EXT-02 and causes an explicit zero write at destination offset 71. The status before preparation does not determine this condition.

7. **Full-width forwarding and narrowing.** For tag `0x04`, a zero status and auxiliary value `0x00000102` cause F-EXT-02 to receive the full value. After normal return, destination offset 71 receives `0x02`. Safe handling of that argument by the dependency is not established.

8. **Preparation address and current indirect target.** Tag `0x10` prepares destination plus 6; tag `0x12` prepares destination plus 7. Both tags pass destination plus 6 to that operation.

9. **Trailing spaces only.** For tag `0x14` or `0x1E`, assume zero status and that destination offsets 7 through 14 contain, after F-EXT-02, `A`, space, `B`, space, space, `C`, space, space. The scan zeroes offsets 14 and 13, stops at offset 12, and leaves the earlier spaces untouched.
