# F-5166d0f0eac3

## Purpose

F-5166d0f0eac3 rewires a linked structure by promoting the node referenced through a selected node’s offset-12 link. The selected node becomes the promoted node’s offset-8 child. Any node previously occupying that offset-8 child position is transferred to the selected node’s offset-12 position.

Under the inferred interpretation that offset 4 is a parent link, offset 8 is a left-child link, and offset 12 is a right-child link, this is a **left rotation**. That interpretation describes the apparent intent; the established behavior is the sequence of four-byte memory accesses and link replacements specified below.

The operation also reconnects the promoted node to the selected node’s former attachment point. That attachment point is either a distinguished root slot or one of the former parent’s child slots.

There is no validation, allocation, deallocation, callback, or reported success status in the supplied body.

## Interface

The operation accepts two arguments:

- **Context address:** identifies an object with a four-byte field at offset 16. That field supplies the address of a root-holder object.
- **Selected-node address:** identifies the node to move downward in the local structure.

The supplied representation declares both arguments as integer-valued parameters. Their use as memory addresses is established by the accesses, but the original public type declarations and calling convention are unknown.

The operation returns no value.

### Referenced layout

All listed fields are accessed as four-byte quantities. Offsets are measured in bytes from the corresponding object address.

| Object | Offset | Established use |
|---|---:|---|
| Context | 16 | Address of the root holder |
| Root holder | 4 | Distinguished root-node address |
| Selected node and related nodes | 4 | Parent-like link |
| Selected node and related nodes | 8 | Left-child-like link |
| Selected node and related nodes | 12 | Right-child-like link |

These accesses do not establish complete object sizes, alignment requirements, field declarations, or the meaning of any other bytes.

For the behavioral description:

- The **promoted node** is the address initially read from the selected node’s offset-12 field.
- The **transfer node** is the node referenced by the promoted node’s offset-8 field, when that reference is nonzero.
- The **former parent** is the address obtained from the selected node’s offset-4 field when that field is read.
- The **root slot** is the four-byte field at offset 4 of the root holder obtained through the context’s offset-16 field.

These are descriptive roles, not additional inputs.

### Preconditions for the intended structural operation

A successful ordinary rotation requires:

- A readable selected-node offset-12 field containing a usable promoted-node address.
- Readable and writable promoted-node link fields.
- Readable and writable selected-node link fields.
- A readable context offset-16 field and accessible root slot.
- If the transfer link is nonzero, a writable offset-4 field at its target.
- If the selected node is not the distinguished root, accessible former-parent child fields.

A zero promoted-node address is not accepted as an empty subtree: the operation proceeds directly to accesses relative to that address.

A zero transfer-node address is explicitly supported. It suppresses only the write to the transfer node’s parent-like field.

These are caller obligations inferred from the accesses, not checks performed by the operation.

## Behavior

### Transfer of the promoted node’s inner subtree

The operation first reads the selected node’s offset-12 field and retains that address as the promoted node for the remainder of the operation.

It reads the promoted node’s offset-8 field and writes that four-byte value into the selected node’s offset-12 field. Thus, the selected node relinquishes its direct link to the promoted node before the promoted node is connected at its new attachment point.

After that write, the operation reads the promoted node’s offset-8 field again to decide whether a parent-link update is needed. If this later value is nonzero, the field is read again to obtain the target address, and the selected-node address is written to that target’s offset-4 field.

The repeated reads are significant. The initial transfer value, the value tested for zero, and the value used as the parent-update target are not specified as one cached value. With stable, non-overlapping ordinary memory, they agree. Aliasing, external modification, or memory with read side effects can make them differ.

### Establishing the promoted node’s upward link

After the transfer-node parent update, if any, the operation reads the selected node’s offset-4 field and copies that value into the promoted node’s offset-4 field.

This read occurs after the earlier writes. Consequently, the promoted node receives the selected node’s parent-like value as it exists at this point, not necessarily its value on entry under unusual aliasing or interference.

For an ordinary well-formed structure, this gives the promoted node the selected node’s former parent.

### Reconnecting the external attachment point

The operation next reads the context’s offset-16 field to locate the root holder. It reads the root slot and compares its four-byte value with the selected-node address.

If they are equal, the promoted-node address replaces the selected-node address in the root slot. The former parent’s child fields are not inspected through the non-root path.

If they are unequal, the operation reads the selected node’s offset-4 field again to locate its parent-like object. It then reads that object’s offset-8 field:

- If the field equals the selected-node address, it is replaced with the promoted-node address.
- Otherwise, the object’s offset-12 field is overwritten with the promoted-node address.

The second case does **not** verify that the offset-12 field previously referenced the selected node. “Not the left child” is treated as sufficient reason to replace the right-child-like link. Malformed linkage can therefore overwrite an unrelated link rather than producing an error.

The former-parent address used on this path is obtained by a separate read from the selected node. It is not required by the supplied body to equal the value previously copied into the promoted node.

### Completing the local relationship

After reconnecting the external attachment point, the operation writes the selected-node address into the promoted node’s offset-8 field.

It then writes the promoted-node address into the selected node’s offset-4 field. This is the final explicit memory write.

For a stable, well-formed, non-overlapping structure, the completed relationships are:

- The promoted node occupies the selected node’s former root or parent-child attachment.
- The promoted node’s parent-like link is the selected node’s former parent-like link.
- The promoted node’s offset-8 link references the selected node.
- The selected node’s parent-like link references the promoted node.
- The selected node’s offset-12 link references the former offset-8 child of the promoted node.
- A nonzero transferred child has its parent-like link changed to the selected node.

The selected node’s offset-8 field and the promoted node’s offset-12 field are not directly written.

## Side effects

All explicit state changes are memory writes to link fields or the root slot. There is no separate global-variable access shown, although supplied addresses may refer to globally reachable storage.

For ordinary valid inputs, the explicit writes occur in this order:

1. Replacement of the selected node’s offset-12 link.
2. Conditional replacement of the transfer node’s offset-4 link.
3. Replacement of the promoted node’s offset-4 link.
4. Replacement of the root slot or one former-parent child link.
5. Replacement of the promoted node’s offset-8 link.
6. Replacement of the selected node’s offset-4 link.

These are four-byte writes. The operation is not shown to make the combined transformation atomic. Intermediate states can contain inconsistent upward and downward links.

No locking, synchronization, memory barriers, transactional protection, or rollback is present in the supplied body. Concurrent access requires an external contract that is not provided here.

No memory is explicitly allocated or released. No ownership transfer, reference-count change, payload movement, or object-lifetime transition is established. The operation changes reachability through the described fields; that alone does not establish ownership semantics.

Invalid addresses or inaccessible fields have no defined recovery path in the supplied body. A failure after an earlier write may leave a partially modified structure. The exact fault mechanism and any process-level handling remain unknown.

## Acceptance examples

These examples are conditional contracts for ordinary stable memory with distinct node-field locations. They are not runtime observations.

### Selected node is the distinguished root

Given a root slot referencing the selected node, a selected offset-12 link referencing the promoted node, and a promoted offset-8 link referencing a transfer node:

- The root slot ends referencing the promoted node.
- The promoted node receives the selected node’s former parent-like link.
- The promoted node’s offset-8 link references the selected node.
- The selected node’s offset-4 link references the promoted node.
- The selected node’s offset-12 link references the transfer node.
- The transfer node’s offset-4 link references the selected node.

This case does not require dereferencing the selected node’s former parent through the non-root branch. A zero or sentinel parent-like value is copied without special treatment.

### Selected node is a left child

Given that the root slot does not reference the selected node and the former parent’s offset-8 field does reference it, the former parent’s offset-8 field is replaced with the promoted-node address.

The former parent’s offset-12 field is not directly written by this branch.

### Selected node is not recorded as a left child

Given that the root slot does not reference the selected node and the former parent’s offset-8 field contains some other value, the former parent’s offset-12 field is replaced with the promoted-node address.

This happens even if that offset-12 field also contains some other node. Acceptance of this example means reproducing the unconditional overwrite behavior, not asserting that the input was structurally valid.

### Empty transfer subtree

Given a zero promoted offset-8 link that remains zero across its reads:

- The selected node’s offset-12 field becomes zero.
- No transfer-node parent field is written.
- The external attachment and final selected/promoted relationship changes still occur.

### Missing promoted node

Given a zero selected offset-12 link, the operation attempts an access at offset 8 relative to that zero value. It does not return a clean “nothing to rotate” result.

The resulting execution outcome is environment-dependent and is documented_only.

### Parent field affected by aliasing

If an earlier write changes storage later read as the selected node’s parent-like field, the later access uses the changed value. An implementation that snapshots every input link on entry would not necessarily preserve the supplied behavior.

The semantic validity of overlapping node objects is unknown; the observable access order is nevertheless relevant.
