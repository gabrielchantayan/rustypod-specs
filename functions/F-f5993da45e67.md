# F-f5993da45e67

## Purpose

F-f5993da45e67 performs a local link transformation consistent with a left rotation in a parent-linked binary tree. It promotes the target node’s right child, moves that child’s left subtree to the target’s right side, and makes the target the promoted node’s left child. It also redirects either the tree’s root link or the former parent’s child link.

The link transformation is established by the supplied static evidence. Its interpretation as a binary-tree rotation is inferred intent: no type declarations, tree invariants, ordering rules, or surrounding operations are available.

The operation has no explicit validation, allocation, deallocation, callback, or recovery path. Successful use requires accessible records and suitable link relationships before entry.

## Interface

### Inputs

The operation accepts two address-bearing inputs:

- **Container reference:** identifies a record containing a reference at byte offset `0x10`.
- **Target reference:** identifies the node whose right child will be promoted.

The reference at container offset `0x10` identifies an **anchor record**. The four-byte field at anchor offset `0x04` is treated as the root link.

The target’s right-link value at entry identifies the **promoted node**. This value is captured once and remains the promoted-node reference throughout the operation.

## Behavior

### Ordered field accesses

The sequence below describes the logical field accesses visible in the supplied representation. It does not establish hardware-level access counts, atomicity, compiler barriers, or a concurrency memory model.

1. **Select the promoted node.**  
   Read the target’s right link and retain that value as the promoted-node reference.

2. **Replace the target’s right link.**  
   Read the promoted node’s left link and write that value into the target’s right-link field.

3. **Repair the transferred child’s parent link when present.**  
   Read the promoted node’s left link again and compare it with zero. If nonzero, read that link again to select the destination record, then write the target reference into that record’s parent field.

   The condition and destination are based on repeated reads, not explicitly on the value copied in step 2. With stable, non-overlapping records, all these reads identify the same transferred child.

4. **Give the promoted node the target’s current parent.**  
   Read the target’s parent link and write it into the promoted node’s parent field.

5. **Locate and inspect the root link.**  
   Read the container’s anchor reference, locate the anchor’s root-link field, and read it for comparison with the target reference.

6. **Redirect the incoming link to the promoted node.**
   - If the root link equals the target reference, write the promoted-node reference into that root-link field.
   - Otherwise, read the target’s parent link again. Read that parent’s left link.
     - If the left link equals the target reference, replace it with the promoted-node reference.
     - Otherwise, replace the parent’s right link with the promoted-node reference.

   The final alternative does not verify that the parent’s right link actually identifies the target.

7. **Attach the target below the promoted node.**  
   Write the target reference into the promoted node’s left-link field.

8. **Update the target’s parent link.**  
   Write the promoted-node reference into the target’s parent field.

There are five writes on every ordinarily completing path, plus one write when the transferred child is nonzero.

### Result for a coherent tree

Assuming distinct, stable records and valid initial relationships:

- The target’s former right child becomes the replacement for the target in its former position.
- The promoted node’s former left child becomes the target’s right child.
- If that transferred child exists, its parent becomes the target.
- The promoted node’s parent becomes the target’s former parent.
- The target becomes the promoted node’s left child.
- The target’s parent becomes the promoted node.
- The root link changes only when it identifies the target.
- Otherwise, one child link of the target’s former parent changes.

The target’s left-link field and the promoted node’s right-link field are not directly written. Payloads, keys, counts, colors, heights, and balancing metadata are not explicitly accessed.

A root promotion copies the target’s existing parent value into the promoted node’s parent field. It does not independently assign zero or an anchor reference. Any root-parent convention must already be represented by the target’s parent value.

### Branch precedence and malformed relationships

Root identity is tested before the former parent’s child links are inspected. If the root link identifies the target, the parent-child replacement branch is skipped.

For a non-root target, the parent’s left link takes precedence. If both child links identify the target, only the left link is replaced. If neither identifies the target, the right link is nevertheless overwritten.
