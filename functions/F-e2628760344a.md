# F-e2628760344a

## Purpose

F-e2628760344a copies two metadata fields from a source record to a destination record. For recognized destination modes, it also obtains and stores a dependency result, selects a payload address and count, conditionally updates destination state, and invokes an unknown indirect target.

Actual payload transfer is **not established**. The indirect target receives arguments consistent with a transfer operation, but its implementation and effects are unknown.

Destination mode 1 has an additional transition: when the computed unsigned count exceeds 128, the function traverses a list belonging to a globally selected object, conditionally invokes a dependency, clears fields in qualifying entries, and changes the destination to mode 2 with an address inside that object.

These are static effects of the supplied representation. Application-level meanings of the records, modes, payload, and state fields remain unknown.

## Interface

The function accepts two address-bearing inputs:

- **Source address:** identifies metadata, a region passed to a dependency, and a region supplied to the final indirect target.
- **Destination address:** identifies metadata, a mode, state fields, and either inline storage or an address field.

The supplied representation uses 32-bit address-bearing values and 32-bit stored addresses. This contract does not imply native-width pointers on other architectures.

No explicit result value is produced. Observable outcomes consist of memory accesses, writes, dependency invocations, and any effects of those dependencies. There is no explicit success flag, error code, or returned count.

## Behavior

### Initial writes and mode selection

The function first reads four bytes at source offset `0x04` and writes them to destination offset `0x1c`. It then reads two bytes at source offset `0x08` and writes them to destination offset `0x20`.

These are ordered read/write pairs, not a snapshot or atomic record update. In particular, an overlapping first write can affect the second source read.

Only afterward does the function read the destination’s signed 16-bit mode at offset `0x22`.

- Modes 0, 1, and 2 continue.
- Every other signed 16-bit mode returns after the metadata writes.

An unsupported mode performs no dependency invocation, count calculation, final state comparison, or final indirect-target lookup.

Mode dispatch occurs once. Later changes to the stored mode do not restart dispatch or select another branch.

### Common dependency call

Each recognized mode invokes F-4055be9c3f18 once with the address `source + 0x1e`. Its 32-bit result is then written to destination offset `0x24`.

Count reads occur after this call and result write. The function therefore uses the source count as it exists at that later time, not necessarily its entry value.

No preservation guarantee is established for the dependency. It may affect source or destination storage, globals, or other memory according to its unknown contract.

### Mode 0

The selected payload destination is `destination + 0x28`.

The count is the unsigned byte read at source offset `0x22`, plus one, retained as an unsigned 16-bit value. Its possible values are 1 through 256.

There is no 128-byte threshold check, global-object lookup, or list traversal in this branch. The function does not directly change the destination mode.

The maximum count is therefore 256 even though mode 1 transitions when its count exceeds 128. This does not establish that the destination has 256 bytes of inline capacity.

### Mode 1: count and threshold

The initial selected payload destination is `destination + 0x28`.

The function reads a signed 16-bit value from source offset `0x22`, adds one, multiplies by two, and retains the result as an unsigned 16-bit count.

The retained unsigned count determines the branch:

- **At most 128:** retain the inline destination; perform no global traversal or direct mode update.
- **Greater than 128:** perform the global-object transition below.

The threshold is not applied to the signed source value or to the unretained arithmetic result.

### Mode 1: global-object transition

The function obtains a global-object address through a global pointer location. This selection occurs after F-4055be9c3f18 has returned, its result has been stored, and the count has been computed.

The selected object’s list head is a 32-bit address read at object offset `0x04`. A null head skips entry processing.

For each visited nonnull entry:

1. Read its signed 16-bit selector at offset `0x22`.
2. If the selector is not 2, perform none of the qualifying-entry actions.
3. If the selector is 2, read the next-entry address at offset `0x00` to determine whether it is nonzero.
4. If that address is nonzero, invoke F-6ceb9cf500c4 with the selected global-object address and current entry address.
5. For a qualifying entry, after the conditional call, write four zero bytes at entry offset `0x08`.
6. Then write four zero bytes at entry offset `0x18`.
7. Advance using the next-entry address read from the current entry after its processing.

A qualifying terminal entry skips the dependency call but still receives both zero writes. A nonqualifying entry is still followed through its next-entry field.

The address tested before a qualifying-entry call is not saved for traversal. If the dependency changes the current entry’s next field, the post-call value controls advancement. The function continues accessing the current entry after the dependency returns; valid execution therefore requires those accesses to remain possible. The call itself does not establish continued lifetime.

No cycle detection or iteration bound is visible.

When traversal reaches null:

- Select the payload destination as the originally selected global-object address plus `0x10`.
- Write the destination’s 16-bit mode at offset `0x22` as 2.
- Write the selected payload address as four bytes at destination offset `0x28`.

The global-object pointer location is not reread during traversal or for this final address calculation. A callback changing that location does not change the object address already selected by this invocation.

### Mode 2

After the common dependency result is stored, the function reads the payload destination as a 32-bit address from destination offset `0x28`.

It then reads the signed 16-bit source count at offset `0x22` and applies the same arithmetic and unsigned 16-bit retention as mode 1.

There is no threshold check or list traversal. A count greater than 128 does not cause another transition.

The address read occurs after F-4055be9c3f18 returns. Changes that dependency makes to destination offset `0x28` can therefore determine the selected address.

### Count arithmetic

For modes 1 and 2, the signed arithmetic before retention ranges from −65,534 through 65,536. These values fit within signed 32-bit arithmetic.

Retention to unsigned 16 bits produces an even count from 0 through 65,534.

| Signed source value | Retained unsigned count |
|---:|---:|
| −32,768 | 2 |
| −2 | 65,534 |
| −1 | 0 |
| 0 | 2 |
| 63 | 128 |
| 64 | 130 |
| 32,767 | 0 |

Negative values are not rejected. Both −1 and 32,767 produce zero. A source value of −2 takes the mode-1 transition because the retained count is 65,534.

These widths describe the selected count’s value. The supplied representation does not independently establish the final target’s machine-level argument-slot width or full calling convention.

### Final comparison and late target lookup

After address/count selection and any completed traversal, the function reads destination offsets `0x24` and `0x18` as 32-bit values and compares them. The representation establishes both reads before the conditional write, but does not establish a required relative read order between these two operands.

If the values differ, write `0xffffffff` at destination offset `0x14`. If they match, make no direct write there.

The comparison rereads offset `0x24`; it does not use a protected copy of the earlier dependency result. Dependency effects or intervening aliasing writes can affect the comparison.

**After the comparison and any resulting write to offset `0x14`, the function reads the callable target through a global pointer location.** It then invokes that target with:

- The selected payload destination address.
- The address `source + 0x22`.
- The retained unsigned count.

The final target is not established as fixed or captured before earlier dependencies execute. Changes to its global pointer location by F-4055be9c3f18, a traversal callback, or another applicable memory effect can affect which target is invoked.

The invocation occurs even when the count is zero. Neither byte-copy behavior nor zero-count access behavior follows from the invocation alone.

## Side effects

Direct writes consist of:

- The two initial metadata updates.
- Destination offset `0x24` for recognized modes.
- Destination offset `0x14` when the final compared values differ.
- Destination offsets `0x22` and `0x28` during the mode-1 transition.
- Offsets `0x08` and `0x18` of qualifying list entries visited during that transition.

Direct global reads include the transition’s global-object selection and the final callable-target lookup. These occur at different stages. The former is retained through traversal; the latter occurs only at the final invocation stage.

Dependencies may perform additional writes, allocations, releases, or other effects. None of those effects can be excluded from this representation.

No direct allocation, release, reference-count update, or explicit ownership-transfer operation is visible. Clearing entry fields does not prove destruction or release. Storing an address inside a global object does not establish ownership, exclusive access, capacity, or lifetime.

There is no visible rollback. A fault or nonreturning dependency may leave metadata, dependency results, entry fields, or transition state partially updated.

Aliasing is neither prohibited nor specially handled. Earlier writes can affect later reads when source, destination, entries, or global locations overlap. Conversely, selected values already retained by the function are not automatically refreshed from memory. The ordered behavior must not be replaced by an entry-time snapshot model.

No explicit exception, invalid-pointer, failed-call, or capacity-recovery path is established.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid storage, returning dependencies, and no mutation or aliasing beyond that described.

1. **Unsupported mode:** Mode 3 causes the two metadata writes followed by return. Neither dependency is called, and the final target’s global location is not read.

2. **Mode-0 minimum:** With mode 0 and source byte 0, the final invocation receives `destination + 0x28`, `source + 0x22`, and count 1.

3. **Mode-0 maximum:** With source byte 255, count 256 is selected without a threshold check or traversal. Actual target behavior remains unknown.

4. **Mode-1 boundary:** Signed source value 63 produces count 128. The inline destination remains selected, with no direct mode change.

5. **Mode-1 transition with empty list:** Signed source value 64 produces count 130. A null list head causes no entry processing, but mode 2 and the global-object interior address are still stored.

6. **Qualifying terminal entry:** Selector 2 with a null next field causes no F-6ceb9cf500c4 call. Entry offsets `0x08` and `0x18` are cleared in that order.

7. **Callback-modified next entry:** If the callback changes the current entry’s next field while keeping required storage accessible, traversal follows the field read afterward.

8. **Zero-count mode 2:** Signed source value −1 still leads to the final invocation with count 0 and the selected address. No conclusion follows about whether the target accesses either supplied region.

9. **Wrapped negative count:** In mode 1, source value −2 produces count 65,534 and takes the transition path.

10. **Conditional state marking:** Unequal final comparison values cause `0xffffffff` at destination offset `0x14`. Equal values leave its existing contents unchanged by this function.

11. **Late target replacement:** If an earlier dependency changes the final-target global location and it remains unchanged thereafter, the final invocation uses that replacement, not an entry-time target.

12. **Comparison before target lookup:** If destination offset `0x14` aliases the final-target pointer storage, and the comparison differs, the late lookup observes the pointer contents resulting from that write. Successful invocation is conditional on those contents identifying a valid callable target.
