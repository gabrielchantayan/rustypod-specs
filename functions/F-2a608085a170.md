# F-2a608085a170

## Purpose

F-2a608085a170 conditionally returns an address derived from a caller-supplied base and an unsigned selector. It consults a two-byte table entry for selectors below 65,536 and returns zero for selectors outside that range.

The selector has two distinct interpretations:

- For selectors from 0 through 255, the selector chooses an entry whose entire two-byte value must be zero. Success returns the address immediately following a 512-byte table.
- For selectors from 256 through 65,535, the selector’s upper byte chooses an entry. The entry supplies an eight-byte-aligned displacement, which must be nonzero. Success returns the address following the table plus that displacement.

The lower selector byte is ignored in the second case.

This is an address-selection operation, not an allocation, copy, or validation of the returned storage. The apparent use as a lookup into grouped data is inferred intent; no particular data format or consumer behavior is established.

## Interface

### Inputs

**Base**

A signed integer used as an address-like value. All table accesses and returned addresses are derived from it.

The supplied representation uses an integer rather than a typed pointer. It establishes neither the allocation size nor the ownership of the referenced storage.

**Selector**

An unsigned integer. Its behavior is divided into three ranges:

| Selector range | Table entry selected | Success condition |
|---|---|---|
| 0–255 | Entry indexed by the selector | Entire entry equals zero |
| 256–65,535 | Entry indexed by the upper selector byte | Entry with its lowest three bits cleared is nonzero |
| 65,536 and above | None | Always returns zero |

The representation is consistent with a 32-bit integer interface. However, the supplied material does not independently establish the target ABI or language integer widths. The address examples below assume a 32-bit address representation and avoid overflow.

### Output

The result is a signed integer carrying either:

- zero, used as the rejection result; or
- a computed address derived from the base.

No separate status, length, ownership token, or diagnostic is returned.

Zero is not proven to be exclusive to rejection: if permitted address arithmetic produces address zero, a successful calculation could be numerically indistinguishable from rejection. Behavior at arithmetic overflow or address wraparound is not established.

### Relevant memory layout

The function interprets memory relative to the base as follows:

| Relative byte offsets | Interpretation by this function |
|---|---|
| 0–5 | Not read |
| 6–517 | 256 consecutive two-byte entries |
| 518 onward | Address region used as the origin for successful results; not read by this function |

The first entry begins at base plus 6. Entry 255 occupies relative offsets 516 and 517. The result origin is base plus 518, equivalently base plus hexadecimal `0x206`.

Each selected entry is interpreted in big-endian byte order: the byte at the lower address is the high byte, and the next byte is the low byte. This interpretation does not depend on the processor’s native byte order.

Only the selected two-byte entry must be read by the displayed operation. A complete 518-byte object is not itself accessed or validated.

## Behavior

### Selector outside the accepted range

When the selector is at least 65,536, the function returns zero.

On this path:

- It does not read memory through the base.
- It does not inspect any table entry.
- It does not compute a useful result address from the base.

Consequently, an otherwise unusable base does not cause a displayed table access on this path.

### Selectors from 0 through 255

The function first forms the result origin at base plus 518.

It selects the two-byte entry at:

- base plus 6;
- plus twice the selector.

The two bytes form an unsigned value from 0 through 65,535, with the lower-address byte contributing the upper eight bits.

If this value is nonzero, the function returns zero.

If this value is zero, the function returns the result origin, base plus 518.

All 16 entry bits participate in this decision. In particular, an entry whose only set bits are among its lowest three bits still causes rejection. Those bits are not discarded on this path.

Selectors in this range therefore choose a presence-or-absence condition, not an address displacement. Distinct selectors can return the same result address when their respective entries are zero.

### Selectors from 256 through 65,535

The function first forms the same result origin, base plus 518.

It selects an entry using the selector shifted right by eight bits. Because this branch is restricted to selectors below 65,536 and excludes those below 256, the resulting index is from 1 through 255.

The selected entry begins at base plus 6 plus twice that index. Its two bytes are interpreted as an unsigned big-endian value.

The lowest three bits of that value are cleared. The resulting displacement:

- is between 0 and 65,528 inclusive;
- is a multiple of eight;
- cannot acquire high set bits from sign extension, because the entry is formed from two bytes rather than interpreted as a signed 16-bit quantity.

The function adds this displacement to the result origin. It then compares the resulting address with the result origin:

- If they are equal, it returns zero.
- Otherwise, it returns the resulting address.

For ordinary nonoverflowing address arithmetic, this equality test rejects exactly a zero displacement. Thus entry values 0 through 7 all reject on this path. Any entry value of at least 8 produces a nonzero displacement.

The lower eight bits of the selector have no effect in this branch. Every selector from hexadecimal `0x1200` through `0x12FF`, for example, uses entry 18 and follows the same calculation, assuming stable table contents.

### Arithmetic boundaries

The table-index calculations are bounded by the selector checks. Their relative access offsets range from 6 through 517.

The largest successful relative address calculation is:

- 518 bytes to the result origin;
- plus 65,528 bytes of displacement;
- totaling 66,046 bytes from the base, or hexadecimal `0x101FE`.

These are bounds on computed offsets, not proof that the corresponding addresses are valid or backed by an allocation.

The supplied representation uses signed integer arithmetic for address-like calculations. It does not establish whether an overflowing calculation wraps, traps, or is governed by some other execution rule. A portable contract therefore requires the relevant address calculations to be representable and usable on the actual target. No overflow handling is visible.

## Side effects

### Reads

For every selector below 65,536, the displayed behavior reads the two bytes of one selected table entry.

The entry’s lower-address byte supplies the high-order byte of the interpreted value. The higher-address byte supplies the low-order byte. This establishes byte significance, but not a guaranteed temporal ordering between the two physical loads.

There is no displayed retry, synchronization, or atomic two-byte snapshot. Concurrent modification could therefore affect the observed entry value; the supplied material does not define a consistency guarantee.

The function does not read:

- the first six bytes at the base;
- unselected table entries;
- the storage addressed by its result.

### Writes and state changes

No memory writes, global-state changes, allocation, release, or resource transfer are displayed.

The function does not initialize the returned storage or mark it as consumed. It does not update the table after a successful lookup.

### Ownership and validity

The returned integer is a derived address, not evidence of a newly allocated object. No ownership transfer or permission to free the address is established.

The caller remains responsible for providing readable selected-entry bytes when a table-reading path is taken. If the result is later dereferenced, the caller or consumer must separately establish the validity, extent, alignment, and access permissions of that storage.

Although the displacement is eight-byte-aligned, the returned address is not necessarily aligned to eight bytes: its alignment also depends on the base plus 518.

### Errors

The only explicit rejection result is zero.

Invalid memory, inaccessible addresses, or arithmetic faults have no displayed recovery path or error translation. Their concrete manifestation depends on the execution environment and is documented_only.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not results of executed tests. Unless stated otherwise, assume a base of hexadecimal `0x00100000`, readable entry bytes, stable memory, and representable arithmetic. The result origin is then `0x00100206`.

1. **Small selector with a zero entry**

   Selector 5 selects relative offsets 16 and 17. If both bytes are zero, the result is `0x00100206`.

2. **Small selector with a low flag-like bit set**

   Selector 5 with entry bytes `0x00` and `0x01` returns zero. The lowest three bits are not ignored in this selector range.

3. **Big-endian interpretation**

   Selector `0x0100` selects entry 1 at relative offsets 8 and 9. Bytes `0x01` and `0x00` represent 256, so the result is `0x00100306`.

   Reversing those bytes gives entry value 1, whose cleared displacement is zero; that case returns zero.

4. **Discarding low displacement bits**

   Selector `0x1200` selects entry 18 at relative offsets 42 and 43. Entry value hexadecimal `0x0013` produces displacement `0x0010`, so the result is `0x00100216`.

   Entry values `0x0010` through `0x0017` produce that same displacement.

5. **Ignored lower selector byte**

   With unchanged entry 18, selectors `0x1200`, `0x1234`, and `0x12FF` produce the same result. None selects a distinct entry based on its lower byte.

6. **Zero-displacement rejection**

   Selector `0x0100` with an entry value from 0 through 7 returns zero. Entry value 8 instead returns `0x0010020E`.

7. **Branch boundary changes entry selection**

   Selector `0x00FF` selects entry 255 and requires the entire entry to be zero.

   Selector `0x0100` selects entry 1 and requires a nonzero displacement after clearing its lowest three bits. The boundary does not advance from entry 255 to an entry 256.

8. **Largest in-range selector and displacement**

   Selector `0xFFFF` selects entry 255. Entry bytes `0xFF` and `0xFF` produce displacement `0xFFF8`, yielding result `0x001101FE`.

9. **Out-of-range selector**

   Selector `0x10000` returns zero without accessing the table. This remains the displayed behavior even if the base would be invalid for a memory read.

## Uncertainties

### Inferred intent

The table may encode absent direct entries and offsets to secondary data. The clearing of three low bits suggests those bits may carry metadata. Neither interpretation is required for the observed behavior.

The six-byte prefix may be a header, but the function never examines it. Its content and meaning are unknown.

### Documented_only

The following are not established:

- Exact target ABI, integer width, and signed-overflow semantics.
- Valid base-address range and enclosing allocation size.
- Semantic meaning of table entries or their lowest three bits.
- Type, size, lifetime, and ownership of the storage at a successful result.
- Whether address zero can be a valid computed result.
- Required synchronization for concurrent table updates.
- Behavior of memory-mapped or otherwise side-effectful table storage.
- Guaranteed ordering or atomicity of the two byte reads.
- Calling-context restrictions beyond the memory and arithmetic requirements described above.

No runtime tests have been performed.
