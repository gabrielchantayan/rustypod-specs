# F-a2904fc24bd6

## Purpose

F-a2904fc24bd6 examines a byte sequence until it encounters an ordinary-position zero byte, exhausts a supplied byte budget, or detects one of a limited set of structural failures.

Its established behavior is a **bounded byte-pattern check**, not complete UTF-8 validation. It recognizes certain two-byte and three-byte patterns, but also accepts other high-bit-set bytes by consuming three bytes without checking either following byte. Consequently, success does not establish that the examined bytes represent valid Unicode text.

The apparent intent is to check a zero-terminated or length-bounded multibyte string. That intent is inferred from the byte masks and stopping conditions; it is not a substitute for the acceptance rules below.

## Interface

The recovered interface has three inputs and one return value:

| Item | Representation | Contract |
|---|---|---|
| Starting address | Pointer to 8-bit bytes | Identifies the first byte to examine. The function reads through this address but does not write through it. |
| Byte budget | Signed 32-bit integer | For nonnegative values, limits the number of bytes available to the scan. Zero succeeds without reading memory. Negative values are not handled as invalid input and do not have a generally safe bounded-scan interpretation. |
| Auxiliary value | Unsigned 32-bit integer | Has no influence on the returned result or memory-read sequence in the established control flow. |
| Result | 32-bit scalar | Returns exactly `1` for the function’s success conditions and exactly `0` for its detected structural failures. |

Pointer width is not established by the supplied material. Bytes are zero-extended when used in the unsigned bit-mask comparisons.

For a straightforward, memory-safe use with a nonnegative budget, the starting address should designate a readable region containing at least that many bytes. A smaller readable region can suffice if execution returns before reaching its end, but that depends on the actual bytes and the read ordering described below.

There is no output buffer, consumed-length result, or error-position result. Advancing the scan changes only local state; it does not update the caller’s pointer or budget.

A zero budget does not require a readable starting address because no byte is accessed on that path.

## Behavior

### Scan boundaries and stopping conditions

At each ordinary scan position, the function first reduces its local remaining budget by one.

If that reduction produces `−1`, the function returns `1` without reading the byte at the current position. For a nonnegative starting budget, this is the exhaustion case: all permitted bytes have already been consumed.

Otherwise, the function reads the current byte. If it is zero, the function returns `1` immediately. This zero-byte success applies only when the byte is being read as the first byte of a scan unit. Zero bytes used as following bytes of a multibyte unit do not automatically terminate the scan.

A nonzero byte with its high bit clear—values `01` through `7F` hexadecimal—is accepted as a one-byte unit. The scan then continues at the next byte with one byte deducted from the budget.

A byte with its high bit set enters the multibyte handling described below.

For nonnegative budgets, exact exhaustion after an accepted unit succeeds on the next scan iteration without an additional memory read. A terminating zero is therefore not required for success.

### Two-byte units

A first byte in the inclusive range `C0`–`DF` selects the two-byte rule.

The function requires at least one byte after that first byte within the budget. If the first byte used the last available byte, it returns `0` before reading a second byte.

When a second byte is available, the function reads it and accepts the pair only if that byte is in the inclusive range `80`–`BF`. Equivalently, its two highest bits must be binary `10`.

On acceptance, the scan continues after the pair, with two bytes consumed from the budget.

This rule includes first bytes `C0` and `C1`. There is no additional restriction preventing overlong encodings. The function does not decode the pair into a code point.

### Three-byte units beginning with `E0`–`EF`

A first byte in the inclusive range `E0`–`EF` selects a three-byte unit whose two following bytes are checked.

The function requires two additional bytes within the budget:

- With only the first byte available, it returns `0` without reading a second byte.
- With exactly two bytes available, it reads the second byte, then returns `0` without reading a third byte.
- With at least three bytes available, it reads the second byte and then the third byte.

After both following bytes have been read, the function checks the second byte first. It must be in `80`–`BF`. If that check succeeds, the third byte must also be in `80`–`BF`.

The read of the third byte therefore occurs **before** rejection of an invalid second byte. A caller cannot rely on an invalid second byte to prevent the third-byte read.

If both checks succeed, the scan continues after the three-byte unit with three bytes consumed.

There are no first-byte-specific restrictions on the following bytes. In particular:

- `E0` does not impose a higher lower bound on the second byte.
- `ED` does not impose a restriction excluding surrogate encodings.
- No decoded value is computed or checked.

### Other high-bit-set first bytes

A first byte in either range `80`–`BF` or `F0`–`FF` follows a different three-byte path.

The function still requires and reads two following bytes:

- With one byte available, it returns `0` before a second-byte read.
- With two bytes available, it reads the second byte and returns `0` before a third-byte read.
- With at least three bytes available, it reads both following bytes and continues after all three bytes.

For this class, **neither following byte is checked**. Their values may be zero, ASCII, continuation-shaped, or any other byte value.

Thus, a continuation-shaped byte can be accepted as a first byte if two more bytes are available. Likewise, a byte that normally introduces a four-byte UTF-8 sequence is treated here as the start of an unchecked three-byte unit. Any fourth byte is subsequently processed as a new first byte.

This is established behavior, not an inferred extension of UTF-8 rules.

### Byte-budget accounting

For nonnegative initial budgets, accepted units consume:

| First-byte class | Bytes consumed |
|---|---:|
| `01`–`7F` | 1 |
| `C0`–`DF`, with a valid following byte | 2 |
| `E0`–`EF`, with two valid following bytes | 3 |
| `80`–`BF` or `F0`–`FF`, with two available following bytes | 3 |

An ordinary-position `00` returns success immediately after its read. No later byte is read.

The budget counts bytes, not characters or Unicode scalar values. Under the nonnegative-budget precondition, the function does not read beyond the supplied budget. Its checks do not, however, establish that the supplied address actually refers to a readable region.

### Auxiliary input

The auxiliary 32-bit input has no externally observable influence in the supplied control flow.

When the budget is zero, the function returns success without needing the auxiliary value. When the budget is nonzero, the first-byte read replaces that value before any byte classification. Later local reuse of the same storage does not make the original input relevant.

There is no evidence that this input carries decoding state between calls.

## Side effects

The function performs byte reads from the supplied region. No memory writes, global-state accesses, allocations, releases, callbacks, or external calls are visible in the supplied body.

The relative order of explicit byte accesses is:

1. Read the current first byte, unless exhaustion has already caused success.
2. For a high-bit-set first byte, read the second byte only if the budget permits it.
3. For a first byte outside `C0`–`DF`, read the third byte only if the budget permits it.
4. Apply the relevant continuation checks, or skip them for the unchecked three-byte class.
5. Continue at the next scan position if the unit is accepted.

For the checked three-byte class, both following-byte reads precede the first continuation check. For the unchecked class, both reads occur even though their values do not affect acceptance.

The function does not take ownership of the input region and does not release it. No pointer is retained in visible persistent state. The caller remains responsible for the region’s lifetime and readability throughout execution.

The only reported failures are returns of `0` for insufficient bytes after a high-bit-set first byte or for failed continuation checks. Invalid addresses and inaccessible memory do not have an explicit recovery path or specified return value.

No concurrency guarantees are established. If another actor changes the input during execution, the supplied material does not define a stable-snapshot interpretation.

## Uncertainties

### Established static behavior

The supplied body establishes the byte classes, checks, read order, local budget updates, and return constants described above. It also establishes the absence of visible calls and writes.

The recovered interface indicates an 8-bit byte element, a signed 32-bit budget, an unsigned 32-bit auxiliary input, and a 32-bit result. It does not establish pointer width, an external declaration, or a broader calling convention.

### Inferred intent

The high-bit and continuation masks suggest a multibyte-text check resembling part of UTF-8 validation.

That interpretation must not strengthen the contract. Successful return does not establish canonical encoding, valid scalar values, valid four-byte encoding, or even continuation-shaped following bytes for every high-bit-set first byte.

### documented_only: negative budgets and arithmetic extremes

Negative budgets are not explicitly rejected. The exhaustion comparison recognizes the transition from zero to `−1`, rather than testing whether the budget is nonpositive.

For negative budgets, zero bytes and structural failures can still cause a return, but the budget does not provide the normal forward bound. The supplied body performs signed subtractions by one, two, or three; inputs near the minimum signed 32-bit value can cross the signed representable range.

The material does not settle the intended language-level overflow semantics or provide an independent machine-level overflow contract. A portable specification must therefore not promise wraparound behavior, eventual exhaustion, or memory safety for negative budgets.

### documented_only: invalid memory and unstable inputs

There is no established contract for null or invalid addresses when a read is required, address arithmetic outside the underlying region, concurrent mutation, or memory-mapped read side effects.

The explicit read ordering is documented, but no additional processor-level speculation or device-ordering guarantees are established.
