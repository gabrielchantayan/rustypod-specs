# F-4251abd1b83c

## Purpose

**Established static evidence:** The visible body contains eleven stores, six reads supplying retained values, and one indirect transfer. ## Behavior

### Widths, conversions, and address calculations

Each byte access covers one byte, each two-byte access covers 16 bits, and each four-byte access covers 32 bits. Narrow stores use the source’s low 8 or low 16 bits. A signed two-byte interpretation does not change the low-16-bit pattern being stored.

The full 32-bit loaded offset participates in address formation. Truncating it for a two-byte store does not truncate the corresponding address component.

The selected byte is read with a plain-character interpretation and then converted to an unsigned 32-bit value. Its result depends on plain-character signedness:

- If plain characters are unsigned, the derived value is between `0` and `255`.
- If plain characters are signed, bytes below `0x80` produce the same result, while bytes with the high bit set are interpreted as negative character values before unsigned conversion.

For example, the byte `0xFF` produces either `0x000000FF` or `0xFFFFFFFF`. That distinction affects the later address calculations and the first explicit transfer argument.

Address expressions are not widened or checked by any visible operation. Two categories must be distinguished:

- Additions and doubling represented with signed 32-bit operands have no established overflow or address-wrapping contract. They must not be silently treated as checked arithmetic or universally modulo arithmetic.
- Additions to the byte-derived unsigned 32-bit value use unsigned arithmetic in the supplied representation. Under that width model, those additions reduce modulo \(2^{32}\). Whether the resulting value identifies an accessible address is a separate, unresolved platform question.

The first transfer argument uses bitwise OR with `0x44`, not addition.

### Aliasing and retained values

No non-aliasing guarantee is established. An earlier store may modify a shared-word location, a later base-relative field, or the selected byte. Consequently, reads must be understood at their stated positions, not as a snapshot of entry memory.

The first shared word and the offset at hidden-base offset `0x74` are read after the first three stores. If those stores overlap either source, the later read uses the resulting contents.

The selected byte is read after the first base-plus-offset store and the doubled-index store, but before the first-shared-word-plus-offset store and the repeated base-plus-offset store. Overlap can therefore affect the byte-derived value.

The second shared word is read only after the four-byte constant store. The shared payload and third transfer argument are read after that second shared-word read.

Once a value has been retained, later stores do not cause an implicit reload. In particular:

- Both base-plus-offset stores use the same retained offset.
- The second transfer argument uses the retained second shared word.
- The payload store uses the retained payload.
- The third transfer argument uses the value read before the final three stores.

The repeated two-byte store remains part of the behavior even when its address and data match an earlier store. Intervening accesses and device-backed memory may make the repetition observable.

### Bitwise OR rather than addition

The constant-store addresses are separately formed by addition: `0x89` for the four-byte store and `0x88` for the later byte store.

### High-bit selected byte

If the selected byte is `0xFF`:

- With unsigned plain characters, the derived value is `0x000000FF`; the constant-store addresses are `0x144` and `0x143`, and the first transfer argument is `0x000000FF`.
- With signed plain characters and the represented 32-bit unsigned arithmetic, the derived value is `0xFFFFFFFF`; the constant-store addresses reduce to `0x44` and `0x43`, and the first transfer argument is `0xFFFFFFFF`.

These alternatives remain conditional on character signedness and accessible resulting addresses.

### Read before overwrite

### Shared-state aliasing
