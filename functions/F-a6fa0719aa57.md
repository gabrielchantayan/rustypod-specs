# F-a6fa0719aa57

## Purpose

F-a6fa0719aa57 consumes a one-byte request from shared storage. Two request values select an operation involving a temporary 104-byte workspace, a bounded polling sequence, and three final dependency calls. Every other request value causes an immediate return after the request byte has been cleared.

The established behavior is the byte consumption, argument selection, call ordering, polling bound, and memory accesses described below. Interpreting these actions as a request/acknowledgment protocol is inferred intent, not an established external contract. In particular, the supplied material does not establish that the operation succeeds when the polled byte becomes nonzero, or fails when polling reaches its bound.

## Interface

### Inputs and shared storage

The function has no explicit parameters.

Its implicit input is a global pointer to byte-addressable storage. This document calls the pointer value captured at entry the **captured base**. Two offsets are relevant:

| Offset from the captured base | Width | Observed role |
|---|---:|---|
| 0 | One byte | Request value, read and then cleared |
| 2 | One byte | Status value, cleared before polling and then repeatedly read |

No direct access to offset 1 is shown. The complete object layout, object size, allocation origin, and meaning of other bytes are unknown.

At entry, the function captures the global pointer, reads the request byte through the global pointer, and clears the request byte through the global pointer. No dependency call intervenes among those actions. Subsequent explicit status accesses use the captured base.

Consequently, when the global pointer is stable during these entry actions, the consumed request and the later status byte belong to the same storage object. Concurrent changes to the global pointer are outside the established contract; the supplied material does not establish an atomic snapshot.

## Behavior

### Request consumption and selection

The function first captures the global pointer, reads the request byte, and writes zero to the request location. It then selects behavior using the value read before that clear.

| Consumed request | Selected operation argument | Subsequent behavior |
|---:|---:|---|
| 1 | 2 | Execute the recognized-request path |
| 2 | 1 | Execute the recognized-request path |
| Any other byte value | None | Return immediately |

Clearing the request is unconditional: an unrecognized request is also consumed.

The selected operation argument is represented as a four-byte value in the supplied material. Its only possible values are 1 and 2. The original request is supplied separately to F-7dee43db055e as a third argument. For both recognized inputs, that original value is positive under either signed or unsigned interpretation of the one-byte request.

No arithmetic transformation of an arbitrary request is performed. The mapping applies only to the two recognized values.

### Recognized-request preparation

After selecting the operation argument, the function calls F-eeb1a6b9fb4d with the workspace address.

It then calls F-7dee43db055e with these ordered arguments:

1. The same workspace address.
2. The selected four-byte operation value.
3. The original request value, either 1 or 2.

Any return values from these calls are not explicitly tested or used by this function.

Only after both calls return does the function write zero to the status byte at captured-base offset 2. This ordering is significant: a status value established before this clear, including one written by either dependency, is not preserved by the explicit status write.

The function does not refresh its captured base after either dependency. A dependency’s alteration of the global pointer therefore does not, by itself, redirect the subsequent explicit status accesses.

That observation does not imply that dependencies preserve the captured object, its allocation, or any other global state. Those are separate unknowns.

### Bounded polling

After clearing the status byte, the function performs at least one call to a further dependency with the numeric argument 1000.

The supplied dependency map does not identify this callee. This contract gives it the document-local opaque ID **F-000000000001** solely to describe its call sites. That identifier is not a provenance claim or a mapping supplied by the publisher.

Each polling iteration has this observable order:

1. Call F-000000000001 with argument 1000.
2. After that call returns, read the one-byte status at captured-base offset 2.
3. If the byte is nonzero, leave polling.
4. Otherwise, advance the local zero-observation count and continue only while fewer than ten zero observations have occurred.

There is no explicit status read between clearing the byte and the first call to F-000000000001.

The polling limits are therefore:

- Minimum: one dependency call and one status read.
- Maximum: ten dependency calls and ten status reads.
- A nonzero value at any scheduled status read ends polling.
- Ten consecutive zero-valued reads end polling at the bound.

Every nonzero byte value has the same polling effect. The function does not distinguish among different nonzero values.

The counter starts at zero and advances only after a zero observation. Its reachable values are 0 through 10, so this bounded counting does not approach integer overflow. The supplied representation uses an integer counter and a four-byte operation value; no truncation affects the reachable operation values or counter values.

The argument 1000 is established. Its unit, interpretation, and relationship to elapsed time are not. The polling count does not establish a real-time timeout: any dependency may take an unknown duration or fail to return.

### Final calls and return

Once polling ends, either through a nonzero observation or through ten zero observations, the function makes these calls in order:

1. F-c66c8af92610, with no explicit arguments.
2. F-58eeb14d0e92, with no explicit arguments.
3. F-1473dc32d2e4, with the workspace address.

It then returns.

These calls are not conditional on which polling exit occurred. No explicit error branch, success branch, result conversion, retry of the selected operation, or additional status clear follows polling.

This ordering applies when preceding calls return normally. If a dependency does not return normally, the supplied material does not establish execution of later calls or recovery behavior.

## Side effects

### Direct writes

The function explicitly performs:

- One request-byte clear on every invocation that reaches that access.
- One status-byte clear on each recognized-request invocation.

It makes no other explicit writes to the shared object. In particular, it does not explicitly clear the status byte after observing a nonzero value.

This is not a guarantee about the status byte’s value at return. Dependencies and external actors may change it, including during the final calls.

### Direct reads

The function explicitly reads:

- The request byte before clearing it.
- The status byte once after each polling dependency call.

For an unrecognized request, no status read or status clear is performed by this function.

The polling condition uses the value obtained at each scheduled read. A transient nonzero status that disappears before that read is not guaranteed to be detected.

### Dependency effects and ownership

The function gives dependencies access to the local workspace and permits their execution between shared-memory actions. The supplied material does not establish whether those dependencies:

- Allocate or release resources.
- Read or modify globals.
- Read or modify the captured shared object.
- Retain pointers.
- Block, invoke callbacks, or perform external I/O.
- Report errors through mechanisms not inspected here.

F-1473dc32d2e4’s position at the end of the workspace-using sequence is compatible with a finalization role, but its actual behavior and resource ownership obligations remain undocumented. No allocation, release, or ownership transfer should be inferred solely from call order.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence, not executed tests. Unless stated otherwise, assume valid storage, a stable global pointer during entry, and dependencies that return normally.

### Unrecognized request

Given a request byte of 0, 3, or any value other than 1 or 2:

- The request byte is written to zero.
- The function returns without calling any listed dependency.
- The function does not directly read or write offset 2.

A consumer must not interpret an unchanged nonzero request as the expected rejection behavior; rejection still consumes the byte.

### Request value 1

Given a request byte of 1:

- The request is cleared.
- F-eeb1a6b9fb4d receives the workspace.
- F-7dee43db055e receives that workspace, operation value 2, and original request value 1.
- The status clear and polling occur afterward.
- The three final dependencies execute in the specified order.

### Request value 2

Given a request byte of 2, the same sequence applies, except F-7dee43db055e receives operation value 1 and original request value 2.

### Nonzero first observation

If the status read after the first F-000000000001 call returns any nonzero byte:

- Exactly one polling dependency call occurs.
- Exactly one status read occurs.
- The final dependency sequence follows.
- No second polling call occurs.

### Ten zero observations

If all ten scheduled status reads return zero:

- Exactly ten polling dependency calls occur, each with argument 1000.
- There is no eleventh polling call or read.
- The final dependency sequence still executes.
- No explicit failure result is produced.

### Status set before the explicit clear

If a preparation dependency writes a nonzero value to captured-base offset 2, and that storage remains valid:

- The function subsequently overwrites that value with zero.
- Polling does not bypass its first dependency call because of the earlier write.

This makes an acknowledgment produced only before the explicit clear insufficient for early polling termination.

### Global pointer redirected by a dependency

If a preparation dependency changes the global pointer to a different object while leaving the captured object valid:

- The explicit status clear and reads still address offset 2 of the captured object.
- They do not follow the replacement global pointer.

### Transient status

If an external actor briefly writes a nonzero status but restores zero before the next scheduled read, that iteration may observe zero and continue. The contract does not promise event capture.
