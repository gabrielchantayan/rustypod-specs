# F-d1a3481e68e2

## Purpose

F-d1a3481e68e2 compares two records using a primary 32-bit unsigned key and a secondary 24-bit unsigned key. For stable record contents, the comparison is lexicographic: the primary key determines the result unless both primary keys are equal, in which case the secondary keys determine it.

The result occupies 32 bits and has one of three bit patterns:

- `0xFFFFFFFF`: the first record orders before the second.
- `0x00000000`: the compared keys are equal.
- `0x00000001`: the first record orders after the second.

The first result represents −1 when interpreted as a signed 32-bit integer. The supplied evidence establishes its bit pattern, not the caller’s signed interpretation.

This is a comparison of selected fields, not a bytewise comparison of entire records. Differences outside those fields do not affect the result under stable-memory conditions.

## Behavior

### Key construction and arithmetic

Each secondary key is assembled from three unsigned bytes. Each byte is widened before it is shifted or combined:

- The offset-8 byte contributes a value between `0x00000000` and `0x00FF0000`.
- The offset-9 byte contributes a value between `0x00000000` and `0x0000FF00`.
- The offset-10 byte contributes a value between `0x00000000` and `0x000000FF`.

These bit ranges do not overlap. Their combination produces a value between zero and `0x00FFFFFF`, inclusive. There is no sign extension, and construction does not overflow 32 bits.

Each primary key uses two complete 16-bit quantities. Their concatenation produces a value between zero and `0xFFFFFFFF`, inclusive. Comparison is unsigned: a primary key of `0x80000000` orders after `0x7FFFFFFF`.

The function does not subtract one key from another. Its ordering therefore does not depend on signed subtraction overflow or on the magnitude of the difference.

### Observable access phases

The source establishes the following phase order:

1. Read and assemble the first record’s secondary key.
2. Read and assemble the second record’s secondary key.
3. Read the primary-key fields for an unsigned less-than comparison.
4. If that comparison does not select an immediate return, read the primary-key fields again for an unsigned less-than-or-equal comparison.
5. If the second primary comparison permits it, compare the already assembled secondary values.

The source does not establish a left-to-right ordering among the individual reads within a single key-construction expression or comparison expression. In particular, the field layout must not be treated as proof that the individual byte reads occur in ascending address order.

Both secondary keys are obtained before any primary-key decision. Their values are subsequently reused; the function does not explicitly reread the secondary bytes when resolving a primary tie.

Each primary comparison expression contains new accesses to the two 16-bit fields of each record. Thus, at the source level:

- An immediate less-than result requires one primary-key comparison.
- All other paths reach a second primary-key comparison.

These are source-level access facts. The evidence is not sufficient to promise a particular optimized machine-load count or an instruction-by-instruction bus-access sequence.

### Decision rules for stable records

When the accessed fields remain unchanged during execution, the result is:

| Relationship | Return bit pattern |
|---|---|
| First primary key is smaller | `0xFFFFFFFF` |
| First primary key is larger | `0x00000001` |
| Primary keys equal; first secondary key is smaller | `0xFFFFFFFF` |
| Primary keys equal; first secondary key is larger | `0x00000001` |
| Both keys equal | `0x00000000` |

The primary key dominates the secondary key. A larger secondary key cannot make a record order after another record whose primary key is larger.

Equality means equality of the two extracted keys only. It does not establish equality of the record addresses, unused bytes, padding, or any additional fields.

### Changing contents and repeated reads

A stable snapshot is not explicitly created. The primary fields appear in two distinct comparison expressions, while the secondary values are captured earlier.

At the source level, the first primary comparison returns `0xFFFFFFFF` if the values observed there satisfy unsigned less-than. Otherwise, execution reaches a second primary comparison. If the values observed by that second comparison satisfy less-than-or-equal, the previously captured secondary values decide the result. If they do not, the result is `0x00000001`.

Consequently, when external changes are observable between primary comparisons, reaching the secondary comparison does not necessarily imply that the primary values were equal in either observation. The ordinary lexicographic contract requires stable input fields or an external mechanism that provides equivalent stability.

The evidence supplies no synchronization, atomic snapshot, or concurrent-mutation guarantee. It also does not establish that ordinary-memory concurrent modification is valid under the surrounding execution environment.
