# F-4b53288e056a

## Purpose

F-4b53288e056a performs an in-place rearrangement of linked records. Under conventional binary-tree layout and consistency assumptions, the rearrangement is a **left rotation**: a selected node’s right child takes its place, and the selected node becomes that child’s left child.

The tree interpretation is inferred intent. The established behavior is a specific sequence of four-byte field reads and writes. The function does not validate that the records form a tree, that reciprocal links agree, or that the replacement node exists.

No runtime tests have been performed. The contract below distinguishes the directly visible memory behavior from the structural interpretation that applies to well-formed inputs.

## Behavior

### Ordered memory effects

The order below is part of the contract. Repeated reads are significant: the function does not take a complete snapshot of the participating records before modifying them.

#### 1. Select the replacement and transfer its left link

The function first reads X’s field at offset `0x0c` and retains that value as Y.

It then reads Y’s field at offset `0x08` and writes the resulting four-byte value into X’s field at offset `0x0c`.

Y’s field at offset `0x08` is read again to determine whether it is zero. If this second read is nonzero, the same field is read once more to obtain an address, and X is written into that addressed record’s field at offset `0x04`.

Consequences:

- X’s right-link field is written before the zero test.
- The transferred-child value is not captured once and reused for all purposes.
- A zero transferred-child value skips the corresponding upward-link write.
- There is no check that Y itself is nonzero before accessing Y’s fields.

With stable, non-overlapping records, this transfers Y’s former left child to become X’s right child and updates that child’s parent to X.

#### 2. Transfer X’s upward link to Y

After the optional transferred-child update, the function reads X’s field at offset `0x04` and writes that value into Y’s field at offset `0x04`.

This copies X’s upward link as it exists at this point in execution, not necessarily its entry value under arbitrary aliasing.

#### 3. Locate and inspect the root reference

The function next reads the context’s field at offset `0x10`, obtains H, and identifies the four-byte field at H plus `0x04`.

It reads that field and compares its value with X.

This root-bearing location is resolved only after the preceding writes. If the context or its referenced storage overlaps previously modified fields, those writes can affect which location is inspected.

#### 4. Replace the incoming reference to X

If the root-bearing field equals X, the function writes Y to that same field. It does not examine an ordinary parent’s child links on this branch.

Otherwise, it reads X’s field at offset `0x04` again and obtains P. It then reads P’s field at offset `0x08`:

- If that field equals X, it writes Y to P’s field at offset `0x08`.
- Otherwise, it writes Y to P’s field at offset `0x0c`.

The fallback does **not** verify that P’s field at offset `0x0c` previously contained X. A malformed structure can therefore cause an unrelated right-link value to be overwritten.

Root-field equality takes precedence over the ordinary-parent path.

#### 5. Complete the local linkage

Finally, the function writes X into Y’s field at offset `0x08`, then writes Y into X’s field at offset `0x04`.

These are the last two explicit writes, in that order.

### Structural result for well-formed, stable records

Assume the relevant records do not overlap, no external actor changes them during execution, and the initial relationships are:

- X has parent P and right child Y.
- Y has left child B.
- The incoming root or parent link correctly identifies X.

After completion:

- Y replaces X in the appropriate root or parent link.
- Y’s parent becomes X’s former parent.
- Y’s left child becomes X.
- X’s parent becomes Y.
- X’s right child becomes B.
- If B is nonzero, B’s parent becomes X.

The function does not explicitly write X’s left-child field or Y’s right-child field. For distinct, non-overlapping records, those fields remain unchanged.

### Aliasing and concurrent modification

The ordered memory effects, rather than the simplified rotation description, govern overlapping or self-referential records.

For example, X’s parent field is read once for assignment to Y’s parent and may be read again later to locate P. The intervening write to Y’s parent can affect the later read if the records alias. Likewise, the repeated reads of Y’s left-link field need not observe the same value if an earlier write overlaps that field.

No locking, atomic-update protocol, retry, or consistency recheck is visible. The evidence does not establish supported concurrent use or a memory-ordering guarantee.

## Side effects

Depending on the branch and transferred-child value, explicit writes target:

- X at offset `0x0c`.
- The transferred child at offset `0x04`, if the tested link is nonzero.

- Either H at offset `0x04`, P at offset `0x08`, or P at offset `0x0c`.
- Y at offset `0x08`.

## Acceptance examples

These examples are conditional expectations derived from the static evidence, not executed test results. Unless stated otherwise, participating records are distinct, accessible, stable during execution, and have consistent links.

### Root rotation with a transferred child

Initially, H’s root field contains X. X’s right link contains Y, Y’s left link contains a nonzero B, and X’s parent field contains P.

Expected final relationships:

- H’s root field contains Y.
- Y’s parent field contains P.
- Y’s left link contains X.
- X’s parent field contains Y.
- X’s right link contains B.
- B’s parent field contains X.

The value P is copied as stored. It need not be zero: the function does not normalize the new root’s parent to any particular value.

### Non-root rotation where X is a left child

Initially, H’s root field does not contain X, X’s parent field contains P, and P’s left link contains X.

The function replaces P’s left link with Y. For distinct records, P’s right link and H’s root field remain unchanged. The local X–Y–B relationships change as described above.

### Non-root rotation where X is a right child

Initially, H’s root field does not contain X, P’s left link does not contain X, and P’s right link contains X.

The function replaces P’s right link with Y. It does not need to read that right link before writing it.

### Empty transferred subtree

Initially, Y’s left link is zero and remains stable through the relevant reads.

X’s right link becomes zero. No upward-link write is attempted through that zero value. The remaining linkage changes still occur.

This conditional zero handling applies to the transferred child, not to Y itself.

### Inconsistent parent linkage

Initially, H’s root field does not contain X, X’s parent field contains P, and neither of P’s child links contains X.

Provided all accesses remain valid, the function still writes Y into P’s right-link field and completes the remaining writes. It neither rejects nor reports the inconsistency.

### Missing replacement node

Initially, X’s right-link field contains zero.

The function attempts to read the field at offset `0x08` relative to that value. It does not return early as an empty-subtree operation. Successful execution is not guaranteed; the exact consequence depends on address mapping and memory-access behavior.
