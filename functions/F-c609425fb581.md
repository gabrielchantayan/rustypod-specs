# F-c609425fb581

## Purpose

F-c609425fb581 performs two indirect calls associated with a supplied object and, if both calls return normally, produces a four-byte status determined solely by whether a second input equals zero.

The established call order is:

1. Invoke the target obtained from the object’s dispatch structure at byte offset 16.
2. Select the eventual status from the integer input.
3. Invoke the target obtained from the object’s dispatch structure at byte offset 12.
4. Return the selected status.

The dispatch structure is read separately for each invocation. The second target is therefore not necessarily obtained from the same dispatch structure as the first.

No purpose such as locking, unlocking, validation, destruction, or reference counting is established. Those interpretations would require evidence about the indirect targets.

## Interface

### Inputs

**Object reference**

The first input is a pointer to storage whose initial integer-sized field supplies an address used for indirect dispatch.

The supplied representation uses a 32-bit integer model for this field. At each dispatch, the function:

- Reads the address-bearing field at the beginning of the object.
- Uses that value as the base of a dispatch structure.
- Reads a callable target at a fixed byte displacement from that base.
- Passes the original object pointer as the sole explicit argument to the target.

The first displacement is 16 bytes; the second is 12 bytes. These are byte offsets, not entry numbers. The source does not independently specify the native width or encoding of a callable target.

The object’s complete size, alignment requirements, field meanings, and allocation mechanism are unknown. Only the initial address-bearing field and the two dispatch locations are relevant to the visible behavior.

**Selector**

The second input is an integer value, modeled as 32 bits in the supplied representation. Only equality with zero matters.

- Zero selects a result of `0x00000000`.
- Every nonzero value selects a result of `0xFFFFFFFF`.

There is no range check, normalization, or distinction between positive and negative nonzero values.

### Output

On normal completion, the function returns a four-byte value:

| Selector | Returned bit pattern |
|---|---|
| Zero | `0x00000000` |
| Nonzero | `0xFFFFFFFF` |

The all-ones result may be interpreted as unsigned 4,294,967,295 or signed −1 by a caller’s type system. Neither interpretation is established as the semantic meaning of the result. In particular, the source does not establish which result represents success.

No output parameter or returned object is visible.

### Preconditions

For ordinary completion:

- The object pointer must support the initial address-field read.
- The first dispatch lookup must identify a callable target.
- That target must accept the supplied object pointer under the actual calling convention and return control normally.
- After that call, the same object pointer must still support the second address-field read.
- The resulting dispatch structure must support the lookup at byte offset 12.
- The second target must likewise be callable and return normally.

These are access and control-flow requirements, not enforced validation rules. The function contains no explicit null checks or recovery path.

## Behavior

### First dispatch

The function initializes its prospective return value to the four-byte all-ones pattern.

It then reads the initial address-bearing field from the object, obtains a callable target at byte offset 16 from the resulting base, and invokes that target with the object pointer.

This invocation occurs for every selector value, including zero. A zero selector does not bypass either indirect call.

Any ordinary return value produced by this first target is ignored. The wrapper does not use it to select its result or decide whether the second invocation should occur.

### Result selection

After the first invocation returns normally, the function tests whether the selector equals zero.

If the selector is zero, the prospective return value becomes four-byte zero. Otherwise, it remains four-byte all ones.

This is a test of the argument value supplied to this invocation. The function does not reread a selector from caller-owned storage. There is no arithmetic on the selector and no magnitude-dependent behavior.

### Second dispatch

After selecting the result, the function reads the object’s initial address-bearing field again. It uses the newly read value to obtain the target at byte offset 12 and invokes that target with the same object pointer.

The second dispatch must not be specified as using a cached copy of the first dispatch base. If the first target changes the object’s initial field and leaves a valid replacement dispatch structure, that replacement controls the second lookup.

Likewise, the second target entry is read after the first invocation. An implementation cannot assume that a target entry observed before the first invocation remains applicable afterward.

The second target’s ordinary return value is ignored. After that target returns normally, the wrapper returns the previously selected four-byte status.

### Failure and interrupted execution

No explicit failure branch surrounds either invocation or either dispatch lookup.

If a lookup cannot be completed, a target is invalid, or a target does not return normally, the source does not establish a normal wrapper result. There is no visible translation of such conditions into either status pattern.

The second invocation is not shown as an unconditional cleanup action across exceptional or nonlocal exits. Its execution is established only after the first invocation returns normally.

## Side effects

The wrapper’s directly visible object interactions are reads and indirect invocations. No explicit write to object storage, dispatch storage, or global storage appears.

The required observable order is:

1. Read the object’s initial address-bearing field.
2. Read the target at dispatch-base byte offset 16.
3. Invoke that target with the object pointer.
4. Select the result using the selector.
5. Read the object’s initial address-bearing field again.
6. Read the target at the newly obtained base plus 12 bytes.
7. Invoke that target with the object pointer.
8. Return the selected result.

Result initialization and selection are internal state changes; the source does not expose them as writes to caller-accessible memory.

The indirect targets may have additional effects. Their behavior is unknown, so this contract does not assume that they preserve globals, object contents, dispatch entries, external resources, or memory ownership.

No allocation, release, ownership transfer, reference-count adjustment, or resource acquisition is directly visible in the wrapper. This does not establish that the complete invocation is free of those effects: either indirect target could perform them.

In particular, if the first target releases or invalidates the object, the wrapper still attempts its second lookup through the original object pointer. There is no visible replacement-object mechanism or lifetime check.

## Acceptance examples

These examples are conditional expectations derived from static evidence, not executed tests.

### Zero selector with ordinary dependencies

Given a readable object, valid dispatch entries, and two targets that return normally:

- The offset-16 target is invoked first.
- The offset-12 target is invoked second.
- Both receive the original object pointer.
- The result is `0x00000000`.

### Positive or negative nonzero selector

Under the same validity and normal-return conditions, a selector of 1, −1, or any other nonzero representable value produces `0xFFFFFFFF`.

The number and order of indirect invocations remain unchanged.

### Changed dispatch base

Suppose the first target replaces the object’s initial dispatch-base field with another valid base and returns normally.

The second target must be obtained at byte offset 12 from that replacement base. Calling the offset-12 target from a previously cached base would not match the established behavior.

### Dependency-reported status

Suppose either indirect target returns an ordinary value conventionally understood elsewhere as an error.

Provided execution returns normally and all subsequent accesses remain valid, that value does not alter this wrapper’s result. The selector still determines the returned bit pattern.

### First target does not return

If the first target does not return normally, normal execution does not reach result selection, the second invocation, or the wrapper’s return. No recovery status is established.

### Invalidated object

If the first target invalidates the object, no safe normal-completion outcome is guaranteed. The visible behavior still requires another read through the original pointer; it does not include a lifetime check.
