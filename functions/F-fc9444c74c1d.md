# F-fc9444c74c1d

## Purpose

F-fc9444c74c1d modifies an owner’s selector-activity field, obtains and stores a four-byte metadata value through two dependencies, and then either updates a lookup-selected entry or allocates, initializes, and links a new entry.

The established contract is the sequence of represented memory accesses, dependency calls, branch decisions, and return-value construction. The apparent intent is to track selector activity and maintain a selector-ordered list. That interpretation does not establish lookup semantics, initializer behavior, ownership, or unconditional list ordering.

The supplied representation exposes a 64-bit result assembled differently on the update and insertion paths. Whether that result is an intentional public interface remains unresolved.

## Behavior

### Activity recording

The first represented operation reads the owner’s four-byte activity field, combines it with a selector-derived mask using bitwise OR, and writes the result to the same field.

The mask is obtained by right-shifting the unsigned 32-bit value `0x80000000`. The shift count is the selector’s low eight bits.

For counts from 0 through 31:

- Count 0 selects bit 31.
- Count 1 selects bit 30.
- Count 31 selects bit 0.
- Other counts in that interval select the corresponding descending bit.

The OR preserves previously set bits in the value read by this operation. The operation does not explicitly clear any bit.

For counts from 32 through 255, the resulting mask is **documented_only**. The supplied representation does not establish a portable result for these oversized shifts. Neither a zero result nor a modulo-32 shift may be assumed.

Only the mask calculation reduces the selector to its low eight bits. Subsequent lookup, initialization, and insertion comparisons use the full unsigned 32-bit selector.

### Metadata preparation and replacement

After the activity write, the function copies the original fourth argument into a temporary four-byte object.

It calls F-c082dad756a2 with that temporary’s address. After that call returns, it calls F-11922d899a44 with the same address. The four-byte result of the second call is then stored at owner offset +12.

The temporary is not restored between the calls. Consequently, the second dependency receives its contents as left by the first dependency.

The original fourth argument remains the value forwarded later to update or initialization and used in the insertion-path return. Changes to the temporary do not themselves replace that argument.

No semantic interpretation of the stored metadata is established. In particular, the evidence does not identify it as a timestamp, checksum, counter, or token.

### Lookup and branch selection

After writing the metadata, the function calls F-c8e46dcc735a with:

1. The owner address.
2. The full selector.

A nonzero result selects the update path. Zero selects allocation and insertion.

The function does not independently compare the returned entry’s key, check its structure, or validate its ownership. List contents alone do not determine which path executes; the lookup dependency’s result does.

### Front insertion

The initializer-returned entry is linked at the front when either:

- The observed head is zero; or
- The full unsigned selector is strictly less than the unsigned one-byte key at the observed head.

When the head is zero, no head-key read is needed.

The represented write order is:

1. Store the observed head address in the new entry’s next field.
2. Store the new entry address in the owner’s head field.

The function then returns the insertion-path result.

Equality with the head’s key does not select front insertion.

### Traversal and non-front insertion

Otherwise, traversal begins at the observed nonzero head.

For each current entry, the function reads its next field. A zero next address selects that current entry as the insertion predecessor.

For a nonzero next address, the function reads the next entry’s unsigned one-byte key. It advances to that entry when its key is less than or equal to the full selector. It stops before that entry when its key is strictly greater.

After selecting a predecessor, the function reads the predecessor’s next field again. This final read supplies the successor value used for the splice; it is not merely assumed to equal an earlier read.

The represented writes then occur in this order:

1. Store the new entry address in the predecessor’s next field.
2. Store the just-read successor address in the new entry’s next field.

These are two successive writes in the supplied representation. This does **not** establish target memory ordering, concurrent visibility, or an opportunity for reentrant observation between the writes. Those guarantees remain unknown.

The function then returns the insertion-path result.

For a stable, acyclic list already sorted by unsigned byte key, with valid distinct entry storage and no interfering mutation, the insertion point follows the encountered entries whose keys are less than or equal to the selector. Existing equal-key entries are therefore traversed before insertion.

For a selector greater than 255, every possible byte key is less than the selector. Under the same structural assumptions, traversal reaches the tail. This conclusion concerns insertion only; any preceding oversized-shift behavior remains unresolved.

## Side effects

The directly represented sequence is:

1. Read and rewrite the owner’s activity field.
2. Invoke both metadata dependencies.
3. Replace the owner’s metadata field.
4. Invoke lookup.
5. Invoke update, or allocate, initialize, and perform insertion reads and writes.

Activity and metadata writes occur before branch selection. They are not conditional on creation of a new entry.

No rollback is represented. Earlier writes may remain if a later dependency does not return normally or a later memory access fails. The supplied evidence does not establish how such failures manifest.

The function contains no explicit:

- Deallocation.
- Locking, atomic operation, or memory barrier.
- Validation of entry pointers or list acyclicity.
- Allocation- or initialization-failure recovery.
- Write to an entry’s key.

These absences describe this function’s direct behavior, not the dependencies’ behavior.

Linking the initializer-returned address makes that address reachable through the list under ordinary valid, nonaliasing list assumptions. It does not establish allocation ownership, transfer rules, eventual release responsibility, or whether a dependency retains or releases supplied storage.

Both metadata dependencies receive the address of invocation-local temporary storage. Its lifetime is limited to this invocation. Dependency retention of that address is unknown; safe use after the temporary’s lifetime cannot be assumed.

No dependency is assumed to preserve global state, owner fields, existing entries, or allocation contents. Aliasing between the initializer-returned entry and existing owner or entry storage is not checked. Ordinary insertion guarantees require suitable nonaliasing storage.
