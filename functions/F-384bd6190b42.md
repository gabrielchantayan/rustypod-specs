# F-384bd6190b42

## Purpose

F-384bd6190b42 selects and returns a node using an input object's related-object identity, a category mask, and two ordered fallback lists.

The function first considers a candidate obtained through the input object or its related object. It accepts that candidate only when its association refers to the same related object and its category matches the effective mask. Otherwise, it searches the first fallback list, then the second if necessary.

The selected path determines which dependencies are called:

- An accepted initial candidate is passed to one dependency together with a value read from that candidate.
- A fallback result is passed to two dependencies in a fixed order.
- Reaching the second fallback list also causes an additional dependency call, including when no node is found.

These are established control-flow properties. Interpreting the dependencies as registration, list movement, activation, or ownership operations would be inferred intent, not established behavior.

## Behavior

### Initial reads and effective mask

The first established memory read fetches the related-object reference from input-object offset +4. This happens before candidate selection and before any dependency call.

A zero input mask is converted to `0xFFFFFFFF`. Every nonzero mask remains unchanged. Consequently, zero does not mean “select no categories.”

The initial candidate is then read:

- If the saved related-object reference is null, from input-object offset +8.
- Otherwise, from related-object offset +8.

Only one of these candidate locations is read. A nonnull related-object reference takes precedence even if its candidate field is null; there is no subsequent attempt to use the input object's own candidate field.

### Initial-candidate validation

For a nonnull initial candidate, the function reads its association reference at node offset +16 before deciding whether to use fallback selection.

The initial candidate is accepted only if all of the following hold:

1. The candidate is nonnull.
2. Its association reference is nonnull.
3. The association's field at +4 equals the related-object reference saved from the input object.
4. Its category matches the effective mask.

The validation conditions are short-circuited:

- A null candidate prevents association and category reads.
- A null association prevents the association-field and category reads.
- An association mismatch prevents the category read.

A null saved related-object reference is not inherently disqualifying. An initial candidate obtained from input-object offset +8 can be accepted if its nonnull association contains a null reference at +4 and its category matches.

On acceptance, the function reads the candidate's 32-bit field at +8 and calls F-cbaaedb97720 with:

1. That field value.
2. The candidate pointer.

It then returns that candidate, provided the dependency returns normally. It does not search either fallback list or call the fallback dependencies on this path.

### Category matching and integer boundaries

For categories from 0 through 31 inclusive, the mask test selects the corresponding bit of the 32-bit effective mask. A node matches when that bit is set.

The category byte is interpreted as signed, so its represented range is −128 through 127. The supplied expression shifts a value of one by that signed category. It does not explicitly validate the category or mask the shift count.

Accordingly:

- Categories 0 through 30 support an ordinary, unambiguous bit-selection interpretation.
- Category 31 has the intended bit-31 interpretation, but the signedness of the left operand introduces a source-language arithmetic qualification. The supplied material does not independently establish the executable's exact shift semantics.
- Negative categories and categories 32 through 127 have no portable shift result established by this evidence.

This contract does not invent wrapping, saturation, rejection, or modulo-32 behavior for unsupported shift counts. An effective all-ones mask does not remove that uncertainty because the shift still has to be evaluated.

### First fallback list

If any initial-candidate condition fails, the function reads the first list head from context offset +500.

It examines nodes in forward-link order. For each nonnull node, it reads the category byte at +12 and tests the effective mask. If the node matches, traversal stops immediately. Otherwise, the next-node reference at +0 is read and traversal continues.

The first matching node wins. This path does not examine its association field or compare any related-object identity.

When a match is found in this first list:

- The second list head is not read.
- F-ba08d17401b3 is not called.
- The common fallback calls described below occur.

### Second fallback list

If the first list reaches null without a match, the function reads the second list head from context offset +508.

It traverses this list using the same category test and next-link order, stopping at the first match or at null.

After this search, it calls F-ba08d17401b3 with:

1. The context value.
2. The selected node, or null if neither list matched.

This call is unconditional once selection reaches the second-list path. It also occurs when the second list was initially empty.

The selected result is not recomputed after this dependency returns.

### Common fallback calls and return

After either fallback search path, the function calls:

1. F-58820f51cfa6 with the address at context +496 and the selected node.
2. F-514f645f8582 with the address at context +504 and the same selected node.

Both calls occur even when the selected node is null, provided earlier calls return normally.

The function then returns the selected node. Dependency return values do not replace the selected result. There is no node-field reread between these two calls or before returning.

The pointer returned is therefore the value selected before these calls. Whether it still refers to a live or usable object depends on dependency behavior that is not supplied.
