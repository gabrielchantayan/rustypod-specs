# F-1baa81057c41

## Purpose

F-1baa81057c41 conditionally scans a receiver’s indexed entries. It stops normally when scanning is disabled or when every examined entry has a zero leading word. On the first entry whose leading word is nonzero, it invokes F-1d611dd012c9 and, if that invocation returns, invokes F-feee9156a257.

The observable distinction is **zero versus nonzero**, not any particular interpretation of the entry. The evidence does not establish that a nonzero entry represents an error, an allocated object, a pending operation, or another domain-specific condition.

The scan is performed through an indirect callable selected from a receiver-associated dispatch structure. Consequently, entry lookup can itself have observable effects. This contract does not assume that lookup is pure or that any dependency preserves receiver state, global state, or storage lifetimes.

## Interface

**Input:** one pointer to a receiver-like memory object.

**Output:** no explicit return value. A normal return conveys no separately encoded status.

The supplied representation uses signed integer words and address-bearing values consistent with a 32-bit target. The layout below therefore uses four-byte integer words and byte offsets derived from that model. Exact machine types, pointer width, calling convention, endianness, and physical load widths are not independently established.

| Receiver location | Observed use |
|---|---|
| Offset 0 | Address-bearing word used to locate a dispatch structure |
| Offset 4 | Signed scan bound, captured once after the enable check |
| Offset 16 | Integer word converted to a character-sized value for the enable check |

Within the dispatch structure, the callable is selected at **byte offset 64**. It is invoked with the receiver and the current signed index. Its result is treated as a pointer to an integer word; that leading word is read and compared with zero.

For a 32-bit integer model, the bound and index have the signed range −2,147,483,648 through 2,147,483,647. The enable decision concerns a character conversion, not a comparison of the entire offset-16 integer with zero. Under an eight-bit truncating character conversion, only its low eight bits determine whether scanning is enabled.

### Preconditions

The following storage and callability requirements are conditional on the path taken:

- The receiver must permit the enable-field access at offset 16.
- If the converted enable value is nonzero, the receiver must also permit the bound read at offset 4.
- If the captured bound is positive, every attempted lookup requires a readable dispatch address at receiver offset 0, a valid callable at dispatch offset 64, and a valid call under the actual calling convention.
- Every lookup result that returns normally must identify readable storage for at least the leading integer word. There is no null-result check before that read.
- Storage and callable validity must hold when each access occurs, including after any earlier dependency has run.

No validation, recovery, or error result is shown for violations of these requirements. Their consequences are outside the defined normal behavior of this contract.

## Behavior

### Enable gate

The first observed decision is whether the receiver’s offset-16 value becomes zero when converted to the character-sized type.

If it does, the function returns immediately. It does not read the scan bound, resolve the dispatch callable, inspect an entry, or invoke either named dependency on this path.

This is not necessarily equivalent to testing the full integer field for zero. Under an eight-bit truncating conversion, a nonzero integer such as 256 converts to zero and disables scanning. Character signedness does not change a zero-versus-nonzero test when the same eight bits are retained; the conversion’s exact target semantics remain a platform dependency.

### Bound capture and empty scans

If scanning is enabled, the signed bound at receiver offset 4 is read once and retained for the scan.

The first candidate index is zero. Before each lookup, the function compares that index with the captured bound. If the index is greater than or equal to the bound, the function returns normally.

Accordingly:

- A zero bound produces no lookups.
- A negative bound also produces no lookups.
- A positive bound permits indices beginning at zero and ending, at most, at one less than the captured bound.

Changes to the receiver’s stored bound after its initial read do not change this invocation’s captured limit. The enable field is likewise not rechecked during scanning.

### Indexed lookup and entry inspection

For each eligible index, observable accesses occur in this order:

1. Read the receiver’s dispatch address.
2. Resolve the indirect callable at byte offset 64 within that dispatch structure.
3. Invoke that callable with the receiver and current index.
4. After the callable returns, read the leading integer word through its returned pointer.
5. Decide whether that word is zero.

The dispatch lookup is repeated for each attempted entry. The function does not establish a single cached callable for the whole scan. A lookup that changes the receiver’s dispatch address can therefore affect the next iteration, provided the resulting state remains valid.

If the returned entry’s leading word is zero, the index advances by one and the bound comparison is repeated. If the word is nonzero, scanning stops immediately. No later index is requested by this function.

The word’s sign and magnitude do not affect this branch: negative and positive nonzero values have the same effect.

### Exhaustion and index arithmetic

If all requested entries have zero leading words, the function returns when the index reaches the captured bound.

For a positive signed 32-bit bound, index progression does not require signed overflow. Even at the maximum bound, the final possible zero-result lookup uses index 2,147,483,646. Advancing that index produces 2,147,483,647, which is representable and causes the next comparison to terminate the scan.

A negative bound is not reinterpreted as a large unsigned count.

### First nonzero entry

After observing the first nonzero leading word, the function invokes F-1d611dd012c9 with no explicit arguments in the supplied representation.

If that invocation returns normally, the function then invokes F-feee9156a257, also with no explicit arguments shown. No return value from F-1d611dd012c9 is tested or used to choose whether to make this second call.

The supplied evidence marks F-feee9156a257 as non-returning. This supports an expected non-returning terminal path but does not independently establish that dependency’s implementation. No normal continuation after its invocation is established here.

The entry pointer and the observed nonzero word are not explicitly passed to either named dependency. Those dependencies may nevertheless observe receiver-related or global state through mechanisms not shown.

## Side effects

The function itself contains no explicit writes to receiver fields, entry storage, or globals. Its direct operations consist of reads, local index progression, and calls.

That does **not** establish that the overall operation is read-only:

- Each indexed lookup may mutate the receiver, entries, globals, dispatch state, or memory ownership.
- F-1d611dd012c9 may have arbitrary effects not specified here.
- F-feee9156a257 may terminate execution or otherwise transfer control without returning; its precise mechanism is unknown.

There is no explicit allocation, deallocation, ownership transfer, or release in the function’s own visible operations. The receiver and returned entry pointers are used as access paths. No ownership guarantee for either pointer can be inferred from that use.

In particular, the contract does not assume that lookup preserves the receiver, that its returned pointer remains valid beyond the required immediate read, or that either named dependency preserves any previously observed state. No synchronization, atomicity, or concurrent-mutation guarantee is established.
