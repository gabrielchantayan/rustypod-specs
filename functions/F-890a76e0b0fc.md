# F-890a76e0b0fc

## Purpose

F-890a76e0b0fc searches an externally stored table of inclusive unsigned ranges. For the first qualifying record reached by the search, it translates the query by preserving its offset from that record’s lower bound and adding that offset to the record’s translation base.

The search is order-sensitive. It stops with a zero result when it encounters a lower bound greater than the query, even if a later record could contain the query. It also returns zero when no record qualifies before the declared record count is exhausted.

The established behavior is a range lookup with an affine translation. The broader meaning of the ranges and translated values is unknown. Interpreting the table as an address map, character map, or other domain-specific mapping would be inferred intent, not an established contract.

## Interface

### Inputs

The function has two inputs:

1. **Context address.** An address-like input used to locate a table base through a field at byte offset `0x10`.
2. **Query.** An unsigned 32-bit value, compared against unsigned 32-bit range endpoints.

The supplied representation uses an integer-shaped first parameter rather than a typed context pointer. Its semantic role is nevertheless an address: the function dereferences a field relative to it.

### Result

The function returns an integer represented as a 32-bit result in the supplied source model:

- Zero when the search stops without selecting a record.
- The translated 32-bit value when a record is selected.

Zero is not an unambiguous failure indicator. A selected record can also produce zero.

The successful translation uses unsigned 32-bit arithmetic:

**translation base + query − lower bound, modulo 2³².**

Although the declared return type is signed, the translation expression is unsigned. Results above `0x7fffffff` therefore require care at the interface boundary. The unsigned result bits are established; their exact interpretation by a particular signed-return ABI is not established independently of the supplied representation.

### Memory layout

All offsets below are byte offsets.

| Location | Size | Meaning |
|---|---:|---|
| Context + `0x10` | One integer-sized address field | Base address of the backing storage |
| Backing storage + `0x200c` | 4 bytes | Unsigned record count, big-endian |
| Backing storage + `0x2010` | 12 bytes per record | First record, followed immediately by subsequent records |

Each record has this layout:

| Offset within record | Size | Meaning |
|---|---:|---|
| `0x00` | 4 bytes | Inclusive unsigned lower bound, big-endian |
| `0x04` | 4 bytes | Inclusive unsigned upper bound, big-endian |
| `0x08` | 4 bytes | Unsigned translation base, big-endian |

A big-endian field assigns its first byte to bits 31–24 and its fourth byte to bits 7–0. These fields are assembled from individual byte accesses; they are not read as native-endian 32-bit table words.

The context’s address field is different: it is accessed as an integer-sized field, not decoded byte by byte as big-endian data. Its native representation, alignment requirements, and exact address-width interpretation depend on the execution environment.

### Preconditions

For a defined, successful execution:

- The context-relative address field must be readable.
- The backing storage’s count field must be readable.
- Every table field actually reached by the search must be readable.
- The address calculations needed to reach those fields must be valid in the target environment.
- The backing storage must remain valid for the duration of its use.

There is no supplied length parameter. The function does not verify that the declared count fits within the available allocation.

A stable table is required for deterministic behavior. The function supplies no synchronization or coherent-snapshot mechanism for concurrent modifications.

## Behavior

### Initial reads

The function first reads the backing-storage address from the context-relative field. It then obtains the record count from the four bytes at backing-storage offset `0x200c`.

That count controls the entire search. It is not reloaded between records. Likewise, the backing-storage address is obtained once rather than reloaded from the context for each record.

The first record starts at backing-storage offset `0x2010`, immediately after the count field.

If the decoded count is zero, the function returns zero without reading a record’s bounds or translation base. A zero count does not eliminate the prerequisite that the context address field and count field be readable.

### Record selection

Records are considered in their stored order, with a stride of 12 bytes.

For each record reached while the remaining count is nonzero:

- The lower bound is decoded first.
- If the unsigned query is less than that lower bound, the search terminates immediately with zero.
- Otherwise, the upper bound is decoded.
- If the unsigned query is less than or equal to the upper bound, the record is selected.
- If the query is greater than the upper bound, the search continues to the next record, consuming one record from the remaining count.

Consequently, a selected record satisfies both inclusive inequalities:

**lower bound ≤ query ≤ upper bound.**

A record’s translation base is needed only after that record has been selected. Nonmatching records do not have their translation bases read by the supplied behavior.

If every declared record is rejected because its upper bound is below the query, the function returns zero after exhausting the count. It does not read an additional record to determine that the count has reached zero.

### Translation

For a selected record, the function decodes the translation base and computes:

**translation base + (query − lower bound), reduced modulo 2³².**

The offset from the lower bound is nonnegative because the earlier unsigned comparison has already established that the query is not below it. The final translated value can nevertheless wrap around the 32-bit range.

There is no saturation, overflow rejection, or reserved-result filtering. In particular, a mathematically positive sum that reaches `0x100000000` produces the 32-bit value zero.

The function returns immediately after translating a selected record. It does not examine later records for a better match, conflicting mapping, or overlapping range.

### Ordering and malformed records

The early termination on a lower bound greater than the query is consistent with an intended table ordered by nondecreasing lower bounds. Such ordering is not checked.

The exact behavior remains order-sensitive when that intended property is absent:

- A later matching record can be hidden by an earlier record whose lower bound exceeds the query.
- Among overlapping records reached by the search, the first qualifying record wins.
- No duplicate or overlap error is reported.

A record with an upper bound below its lower bound cannot match an unsigned query:

- A query below its lower bound causes immediate termination.
- A query at or above its lower bound necessarily exceeds its upper bound, so the search continues.

The function does not classify such a record as invalid or emit an explicit error.

## Side effects

No memory writes, allocation, deallocation, callbacks, logging, or external function calls are present in the supplied body.

The function does not explicitly change the context, backing storage, count field, or records. Advancement through the records and reduction of the remaining count are internal execution state only.

The observable memory-access dependencies are:

1. Read the backing-storage address.
2. Read and decode the count.
3. For each reached record, read its lower bound.
4. Read its upper bound only if the query is not below the lower bound.
5. Read its translation base only if the query is also not above the upper bound.

This describes the field-level control dependencies established by the source. It does not establish an exact temporal order among the four individual byte reads used to assemble one field. Nor does it establish processor-level speculation, bus transactions, or compiler-generated access details.

No ownership transfer is expressed. The function neither retains the input addresses nor explicitly releases the referenced storage. The caller remains responsible for supplying valid storage during the operation; ownership outside this function is unknown.

## Acceptance examples

These are conditional behavioral examples derived from the supplied source. They are not runtime test results. Each assumes valid, stable memory and the stated decoded field values.

### Empty table

With count zero, the result is zero. No record fields are read, even if bytes following the count happen to resemble a valid range.

### Inclusive endpoints and interior translation

For one record with lower bound 100, upper bound 109, and translation base 1000:

| Query | Result |
|---:|---:|
| 99 | 0 |
| 100 | 1000 |
| 104 | 1004 |
| 109 | 1009 |
| 110 | 0 |

For query 99, the lower-bound comparison terminates the search without requiring the upper bound or translation base.

For query 110, the upper bound is read, but the translation base is not needed.

### Continuing past an earlier range

With two records:

- First: lower 10, upper 19, translation base 100.
- Second: lower 30, upper 39, translation base 200.

Query 35 skips the first record and returns 205 from the second.

Query 25 skips the first record, then returns zero upon seeing the second record’s lower bound. The second record’s upper bound and translation base are not needed.

### Early termination in an unsorted table

With two records:

- First: lower 100, upper 199, translation base 1000.
- Second: lower 10, upper 20, translation base 2000.

Query 15 returns zero upon examining the first lower bound. It does not reach the second record, despite that record containing the query.

### Overlap precedence

With two records:

- First: lower 10, upper 30, translation base 100.
- Second: lower 20, upper 40, translation base 500.

Query 25 returns 115 from the first record. The second record is not examined.

### Unsigned comparison

For a record whose lower and upper bounds are both `0x80000000`, a query of `0x80000000` selects that record and returns its translation base.

The query is not treated as a negative number during range selection.

### Wrapping and zero ambiguity

For a record with lower bound 100, upper bound 101, and translation base `0xffffffff`:

- Query 100 produces the result bits `0xffffffff`.
- Query 101 produces zero through unsigned wraparound.

The latter zero is a successful translation, indistinguishable from an unsuccessful lookup through the result alone.

### Reversed bounds

For a record with lower bound 20 and upper bound 10:

- Query 15 causes immediate zero termination.
- Query 25 rejects the record and continues if more declared records remain.

Neither case produces a validation error.

- Whether callers guarantee ordered, nonoverlapping, well-formed ranges.
- Whether zero has a domain-level sentinel meaning despite also being a possible translation.
- The native representation and alignment of the context’s address field.
- The exact signed-return interpretation of unsigned results above `0x7fffffff` on the target ABI.
- Behavior when address arithmetic overflows, storage is inaccessible, or the count exceeds the available records.
- Concurrent mutation behavior, including whether separately read bytes can come from different updates.
- Exact instruction-level read ordering and hardware effects for special memory regions.

The function supplies no explicit recovery path for invalid memory. Such conditions must not be described as ordinary zero-return errors.

The apparent expectation of ordered ranges is **inferred intent**. The actual early-termination rule is established independently of that intent.
