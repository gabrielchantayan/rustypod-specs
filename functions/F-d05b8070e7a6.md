# F-d05b8070e7a6

## Purpose

F-d05b8070e7a6 scans a stream-backed directory in entry order, selects the first entry whose 32-bit tag equals a requested tag, and constructs an array of adjusted values from the selected entry’s records.

The visible behavior establishes these distinctions:

- The context word is captured once, before any dependency call.
- The diagnostic configuration base is loaded afresh for each completely read directory entry.
- The matched count is published before matched-data positioning and allocation.
- The array address is published only on successful completion.
- Movement results are stored but not independently checked.
- A checked record-read failure causes a release call, followed by a reread of the shared status slot for the return value.
- Directory exhaustion returns the literal status `1`.

“Directory,” “record,” “positioning,” and “allocation” describe inferred intent. The masks, arithmetic, direct accesses, dependency calls, and branch conditions below are established static behavior. Dependency semantics not supplied by the source remain documented_only.

## Interface

The function accepts seven arguments and returns a signed 32-bit status.

| Position | Input or output | Representation and use |
|---|---|---|
| 1 | Context reference | Address of a readable four-byte word, captured at entry and supplied to allocation and release dependencies. |
| 2 | Stream token | Opaque 32-bit value supplied to positioning, reading, and movement dependencies. |
| 3 | Directory base | Signed 32-bit input used for initial positioning and matched-data address arithmetic. |
| 4 | Value adjustment | Signed 32-bit input added to extracted values through unsigned 32-bit arithmetic. |
| 5 | Requested tag | Unsigned 32-bit comparison value. |
| 6 | Array output | Address of a writable four-byte slot receiving the allocation-address representation on success. |
| 7 | Count output | Address of a writable signed 32-bit slot, also reread during allocation and population. |

The returned allocation address is represented by a 32-bit value. Each array element occupies four bytes. A wider-address implementation would require an explicit representation decision; the output slot cannot simply be treated as a wider native pointer.

### Preconditions

Defined execution of the visible accesses requires:

- A valid initial four-byte read through the context reference.
- Valid four-byte writes to each output slot reached by execution.
- A readable global configuration-base location and a readable signed 32-bit field at displacement `0x34` from the base loaded for each diagnostic check.
- A successful allocation result that supports all element stores actually reached.
- Dependencies that accept the supplied stream token, context value, and other arguments.

There are no visible null, alignment, capacity, or address-range checks.

No non-aliasing guarantee is established. Output slots, context storage, and allocated storage must be considered according to their actual overlap and access order. In particular, the count output is mutable control state, not merely a final result.

Descriptions of unchanged outputs below assume non-overlapping storage and no dependency-induced mutation unless explicitly stated otherwise.

## Behavior

### 1. Capture context and position initially

The first visible access reads the four-byte context word. That captured value is used by subsequent allocation and release calls; the context reference is not reread for those purposes.

The function calls F-e40a3ceddab2 with the stream token and directory base. Its return value is stored in a shared signed 32-bit status slot.

- A nonzero status terminates the function with that status.
- Zero permits directory processing.

The context read therefore occurs even when initial positioning fails.

### 2. Determine the directory scan bound

F-8f49ed59b67e receives the stream token and the address of the shared status slot.

A nonzero status after that call terminates processing. Otherwise, the low 16 bits of the returned word determine the scan bound:

**Entry count = low 16 bits + 1.**

The bound ranges from 1 through 65,536. The addition occurs after masking and does not wrap at 16 bits. In particular, `0xffff` means 65,536 entries, not zero.

Entries are visited in order. A selected match ends directory scanning permanently, whether processing that match succeeds or fails.

### 3. Read a complete directory entry

For each entry, the function calls:

1. F-10d2ce969adf to obtain the candidate tag.
2. F-8f49ed59b67e to obtain the encoded record count.
3. F-8f49ed59b67e to obtain the relative-offset word.

Each call receives the stream token and the same shared status-slot address. The status is read and checked immediately after each call. A nonzero value terminates processing before the next operation for that entry.

All three reads precede the tag comparison. A nonmatching tag does not permit the remaining entry reads to be skipped.

The caller establishes 32-bit returned-word handling, but not the number of stream bytes consumed or their byte order.

### 4. Consult the current diagnostic configuration

After the three entry reads have completed with checked zero statuses, the function performs this configuration access sequence:

1. Load the current configuration-base value from a global location.
2. Read the signed 32-bit field at byte displacement `0x34` from that loaded base.
3. Compare that field with `1`.

This sequence occurs separately for every completely read entry. The configuration base is not captured at function entry. Earlier dependency calls may change the global base, the field reached through it, or both.

If the field is greater than `1`, F-4457a9a44a68 receives a fixed diagnostic-format argument followed by four values derived from the candidate tag. Those values are the tag’s bytes in most-significant-to-least-significant order, each in the range 0–255.

The diagnostic call precedes tag matching, so both matching and nonmatching complete entries can trigger it. Its return value is not checked. Its rendering, destination, and effects on external state are not established.

### 5. Select a match and publish its count

A candidate tag unequal to the requested tag causes scanning to continue.

For an equal tag, the function directly writes the count output:

**Published count = low 16 bits of the encoded record count + 1.**

This direct write produces a value from 1 through 65,536.

Next, F-e40a3ceddab2 receives the stream token and the directory base plus the low 16 bits of the relative-offset word. The masked offset participates as an unsigned 32-bit value, so this addition wraps modulo \(2^{32}\).

The positioning result is stored in the shared status slot and checked. A nonzero status is returned without an allocation call.

The function performs no rollback write to the count output. However, the positioning dependency may mutate output-reachable memory. The direct count write is unconditional on this path; persistence of that value across the dependency call is not.

### 6. Request storage

After successful matched-data positioning, F-6dd003795db7 receives, in order:

1. The captured context word.
2. The literal `4`.
3. The literal `0`.
4. The current signed value read from the count output.
5. The literal `0`.
6. The shared status-slot address.

The count is reread after positioning; it is not necessarily the value originally published.

The argument pattern suggests storage for four-byte elements. The formal meanings of the arguments and the allocation capacity guarantee are not established.

If the status after allocation is nonzero, the function returns it without calling F-bf7242c98d06. Any nonzero address returned alongside that error receives no local cleanup.

If status is zero, the returned 32-bit value becomes the array base without a separate null or validity check.

With an unchanged count and the inferred four-byte-element interpretation, the required extent is 4 through 262,144 bytes. The function does not itself calculate or validate a byte capacity.

### 7. Populate the array using the live count

The signed element index starts at zero. Before every element, including the first, the function rereads the signed count output.

If the current count is less than or equal to the index, the function writes the allocation-address representation to the array output and returns literal zero. This completion path does not check the shared status slot.

Otherwise, the observable sequence is:

1. Call F-d8528f8db63b with the stream token and `2`, storing its result in the status slot.
2. Call that dependency again with the stream token and `2`, overwriting the slot.
3. Call F-10d2ce969adf with the stream token and the status-slot address.
4. Read and check the status slot.
5. If it is zero, store the adjusted element.
6. Call F-d8528f8db63b with the stream token and `4`, storing its result in the slot.
7. Increment the element index and return to the live-count check.

Each stored value is:

**Element = (record word masked to 24 bits + adjustment) modulo \(2^{32}\).**

The record word’s high byte is discarded. A negative signed adjustment participates through its unsigned 32-bit representation. No arithmetic-overflow status is generated for this value calculation.

Stores use successive four-byte displacements from the allocation base. Their byte order is the environment’s native 32-bit store order, which is not established here.

Under a stable, originally published count, the index remains within the range required for at most 65,536 stores, and the displacement multiplication remains small enough for signed 32-bit arithmetic. Arbitrary count mutation can invalidate that bound or the allocated capacity. The supplied material does not establish safe behavior after signed address-arithmetic overflow or invalid memory access.

### 8. Movement results are not independently enforced

The two movement-by-2 calls and the movement-by-4 call have no dedicated error branches:

- The first movement result is overwritten by the second.
- The second result is present in the status slot when the record-reading dependency is called.
- The record-reading dependency may replace or preserve that incoming value; its contract is unknown.
- The movement-by-4 result is not checked before the next count comparison.

Consequently, a nonzero movement result does not by itself establish a failure return.

After the final required element, a nonzero movement-by-4 result can be followed by array publication and return zero, provided the next live-count comparison indicates completion.

### 9. Handle a checked record-read failure

If the status checked after a record read is nonzero, no element is stored for that iteration and no following movement-by-4 call occurs.

The function calls F-bf7242c98d06 with the captured context word and allocation address. **After that call returns, the function rereads the shared status slot and returns its current contents.**

The checked read-error value is not separately preserved for return. Although the release call does not directly receive the status-slot address as an argument, earlier dependencies have received that address. Without their contracts, the release dependency cannot be assumed unable to affect the slot through retained state or other access.

Therefore:

- The release call is triggered by a nonzero checked status.
- Equality between that checked status and the eventual return value requires preservation of the slot across release.
- A post-release value of zero would be returned as zero, without array publication by this routine.

Previously stored elements are not rolled back. Their subsequent accessibility depends on the release dependency’s actual semantics.

### 10. Exhaust the directory

If every declared entry is processed without a match or checked error, the function assigns and returns literal `1`.

This path performs no direct write to either output slot. It does not restore the original stream position. The value `1` is not established as a globally unique “not found” code; dependencies may also return it.

## Side effects

### Direct memory writes

The function directly writes:

- The shared status slot throughout processing.
- The matched count to the count output.
- Four-byte result elements after successful checked record reads.
- The allocation address to the array output only at population completion.

Neither output is cleared at entry or on error.

Under non-overlapping storage and no dependency-induced output mutation:

| Outcome | Count output | Array output |
|---|---|---|
| Initial positioning failure, directory-read failure before selection, or no match | Unchanged | Unchanged |
| Matched-data positioning failure | Matched count retained | Unchanged |
| Allocation-status failure | Matched count retained | Unchanged |
| Checked record-read failure | Matched count retained | Unchanged |
| Population completion | Matched count retained | Allocation address published |

Without those assumptions, this table describes direct-write intent, not guaranteed final memory contents. In particular, no rollback write follows the count publication.

### External state and ownership

Stream dependencies may alter stream position or other stream state. No restoration is visible.

The global diagnostic base is consulted anew for each complete entry. Dependencies are not assumed to preserve it, its referenced field, output-reachable memory, or the exposed status slot.

On population completion, the allocation address is exposed to the caller and no release call occurs. On checked record-read failure, the address is passed once to F-bf7242c98d06.

These call patterns do not establish allocation ownership transfer, successful disposal, or a caller-side deallocation obligation. Those contracts remain documented_only.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Initial failure.** If initial positioning returns `7`, the function returns `7` without directory reads or allocation. The context word has already been captured.

2. **Directory bounds.** With zero checked statuses, a directory-bound word whose low 16 bits are zero permits one entry examination. Low bits `0xffff` permit 65,536 examinations unless selection or error terminates scanning earlier.

3. **Nonmatching entries still require complete reads.** If the candidate tag differs but the encoded-count read reports `9`, the function returns `9` before reading the relative-offset field or consulting diagnostics.

4. **Configuration base can change between entries.** Suppose the first complete entry observes one global configuration base. If a dependency subsequently changes that global to another valid base, the next complete entry uses the new base for its `0x34` field read. A signed field value of `2` triggers diagnostics; `1` or a negative value does not.

5. **Count publication precedes positioning failure.** A matching encoded count with low 16 bits `4` causes a direct write of `5`. If matched-data positioning returns `6`, the function returns `6` without allocation or a rollback write. The final count remains `5` only if that dependency and other intervening effects do not mutate the count storage.

6. **Relative-position wrap.** A directory-base bit pattern of `0xfffffff0` plus a masked offset of `0x0030` produces positioning-argument bits `0x00000020`, without a local overflow error.

7. **Value masking and adjustment.** A record word `0xab123456` and adjustment `0x20` produce `0x00123476`. With adjustment `−1`, the result is `0x00123455`.

8. **Failure return is determined after release.** Suppose two elements have been stored and the next checked record status is `9`. The function calls release once and performs no direct array-output publication. If release preserves the status slot, the return is `9`. If it changes the slot to `12`, the return is `12`; if it changes the slot to zero, the return is zero without array publication.

9. **Final movement error can be ignored.** If the final required read succeeds, its element is stored, and movement-by-4 returns nonzero, an unchanged count still leads to address publication and return zero.

10. **First duplicate wins.** If multiple entries have the requested tag, only the first is selected. Failure while processing it does not resume scanning for another match.

11. **The live count can end population immediately.** If allocation completes with zero status but the count output has become zero or negative, the first bound comparison publishes the allocation address and returns zero without record movement or reading. This does not establish that such count mutation is valid under the allocator’s unknown contract.
