# F-c4462b7eb2a2

## Purpose

The established behavior is a traversal driven by an ambient address, followed by three 32-bit destination writes, one 16-bit write, an unresolved call, and a breakpoint-like operation.

The traversal advances to a linked address before testing whether to continue. Consequently, the record used after traversal is the successor of the record whose flag terminates the loop—not that terminating record itself.

The apparent intent may be to select a record, publish three words into an address derived from that record, update another derived location, and transfer control to a low-level operation. That interpretation is inferred, not established. The evidence does not identify the records, destination memory, flag meaning, or operational purpose.

The available representation contains warnings about invalid instruction data and removed unreachable material. This contract therefore describes the visible behavior without claiming that the recovered control flow is complete or executable as presented.

## Behavior

### 1. Traverse using a successor-first decision

The loop executes at least once.

For each iteration, let the current record be the address held at the start of that iteration. The visible memory-read order is:

1. Read the 32-bit link at the current record’s offset +16 and make that address the traversal address for the next stage.
2. Read the 32-bit flag word at the original current record’s offset +8.
3. Continue if bit 21 of that flag word is one.

Bit numbering is zero-based. The tested mask is hexadecimal 00200000. Other flag bits have no visible effect on this decision.

When bit 21 is zero, traversal stops with the traversal address already replaced by the link just read. That successor becomes the selected record.

Consequences:

- The initial record is never selected merely because its own flag is clear.
- A terminating record must still have a readable link field.
- A clear flag does not prevent the link read from occurring.
- There is no visible null check, cycle detection, traversal bound, or link validation.
- A cycle whose examined records all have bit 21 set can continue indefinitely.
- A self-link with a clear flag selects that same address after the mandatory iteration.

### 2. Capture selected-record fields

After traversal, the visible sequence reads:

1. The selected record’s 32-bit field at +12, called the **encoded word** in this contract.
2. The selected record’s 32-bit field at +16, called the **captured link word**.

These reads are distinct from earlier traversal accesses. In particular, the captured link word is read from the selected record, which need not be the record whose clear flag ended the loop.

The captured link word is retained as a value for a later store. The visible body does not dereference it during this phase.

### 3. Derive the three-word destination

The destination address is calculated by logically shifting the encoded word right by four bits and multiplying the result by 8192.

Under the recovered 32-bit unsigned model, multiplication wraps modulo 2³². Thus:

- Encoded-word bits 0–3 do not affect this destination.
- Bits 4–22 determine destination bits 13–31.
- Bits 23–31 are discarded by overflow.
- The resulting base address is aligned to 8192 bytes arithmetically; that fact does not establish that the address is mapped or writable.
- Distinct encoded words can produce the same destination.

Treating the multiplication as an unbounded integer calculation would change the behavior and is not the contract described here.

### 4. Write three consecutive words

The visible write order is:

| Destination offset | Width | Value |
|---|---:|---|
| +0 | 32 bits | Word read from the selected record at +4 |
| +4 | 32 bits | Ambient 32-bit word |
| +8 | 32 bits | Previously captured link word |

The selected record’s +4 field is read after the encoded word and captured link word have been captured, and before the first destination store.

No non-aliasing guarantee is established. If these writes overlap record fields:

- The encoded word and captured link word used by this invocation remain the values already captured.
- The first payload value is the value obtained by the selected-record +4 read before its destination store.
- The stores can affect memory that later execution, another observer, or the unresolved call may access.

The visible order is not a claim of atomic publication, transactional behavior, or synchronization between processors or devices.

### 5. Write a derived halfword

Let the **reduced word** be the encoded word logically shifted right by eight bits. It ranges from zero through hexadecimal 00FFFFFF.

After the three word stores, a 16-bit value is written at the address equal to the reduced word plus ten bytes.

The stored value is the low 16 bits of the reduced word shifted left by twelve bits. Equivalently, it contains:

- Encoded-word bits 8–11 in halfword bits 12–15.
- Zero in halfword bits 0–11.

The possible stored bit patterns are therefore hexadecimal 0000, 1000, 2000, through F000.

The derived halfword address ranges from hexadecimal 0000000A through 01000009. This addition does not overflow a 32-bit unsigned quantity.

The address need not be even. No alignment adjustment or pre-access alignment check is visible. Byte order determines the two byte values placed in memory and is not established by the supplied evidence.

This halfword store occurs after all three word stores. If it overlaps any of them, its written bytes take precedence in the visible sequential execution.

### 6. Invoke the unresolved dependency

After the halfword store, the function invokes an unresolved target with four visible arguments:

| Argument | Value |
|---|---|
| First | Reduced word shifted left by 24 bits, truncated to 32 bits |
| Second | Same value as the first argument |
| Third | Ambient 32-bit word |
| Fourth | Hexadecimal 010E8000 |

The first two arguments depend only on encoded-word bits 8–15. Those eight bits become the most significant byte; the lower 24 bits are zero.

No result from this call is visibly consumed. The evidence does not establish whether the target returns, changes memory, alters global state, consumes resources, or transfers control elsewhere.

### 7. Execute the terminal operations if reached

If the unresolved call returns to the visible continuation, a breakpoint-like operation is issued with immediate hexadecimal B4.

The recovered representation then indicates a terminal invalid-data condition. It does not establish a normal return, a specific operating-system signal, a particular exception handler, or what a debugger might do after the breakpoint.

If the unresolved call does not return, neither later operation is reached.

## Acceptance examples

These are conditional expectations derived from static evidence. They are not reports of executed tests.

### Immediate flag termination still selects the successor

Suppose record A has bit 21 clear and its +16 link contains address B.

Expected behavior:

- Read A’s link before reading A’s flag.
- Stop after the first flag decision.
- Use B’s +12, +16, and +4 fields for subsequent processing.
- Do not use A as the selected record unless B equals A.

### Multiple iterations preserve the predecessor distinction

Suppose A links to B and has bit 21 set. B links to C and has bit 21 clear.

Expected behavior:

- Read A’s link, then A’s flag.
- Read B’s link, then B’s flag.
- Select C.
- Do not require C’s +8 flag word to be read during this traversal.

### High bits wrap out of the first destination

Suppose the encoded word is hexadecimal 00800000.

Expected calculations:

- Shifting right by four and multiplying by 8192 produces zero modulo 2³².
- The three-word destination base is therefore address zero.

Expected behavior:

- It is not reloaded from the now-modified selected record.
