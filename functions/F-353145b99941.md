# F-353145b99941

## Purpose

F-353145b99941 dispatches an event-like record against a receiver-like object. It applies an optional preliminary notification, attempts a type-specific handler when eligible, and then follows a shared fallback sequence until a handler returns a nonzero result or the sequence is exhausted.

The established behavior is dispatch and result propagation. Names such as “event,” “receiver,” “type,” and “subtype” describe structural roles only; they do not establish a particular framework or application meaning.

A nonzero handler result stops dispatch and is returned unchanged. Zero permits the next applicable stage. The preliminary notification is an exception: its return value, if any, does not participate in dispatch.

## Interface

### Inputs and result

The function accepts two inputs:

- **Receiver:** an address providing access to receiver fields and a table of callable entries.
- **Event:** an address providing access to a discriminator and conditionally accessed payload fields.

It returns an integer result. The supplied representation uses 32-bit integer words and four-byte address-bearing fields. This contract describes that represented layout; the original ABI, exact declared types, and character signedness are not independently established.

The caller-visible result is:

- The exact nonzero result of the first result-bearing invocation that returns nonzero.
- Otherwise, zero.

Negative nonzero results are not distinguished from positive nonzero results for control flow. There is no normalization to a Boolean value.

### Referenced layout

Offsets below are byte offsets from the indicated base. Except for the character conversion described separately, fields are represented as 32-bit words.

| Base | Offset | Role |
|---|---:|---|
| Receiver | `0x00` | Address of a callable-entry table |
| Receiver | `0x50` | Value compared with an event field in the final fallback stage |
| Receiver | `0xC0` | Value compared with an event field during type-specific dispatch |
| Receiver | `0xF8` | Word converted to a character-sized argument for the preliminary notification |
| Event | `0x04` | Primary discriminator |
| Event | `0x08` | Either an address of a secondary record or a comparison value, depending on the current discriminator |
| Event | `0x0C` | Selector used for discriminator `0x13` |
| Secondary record | `0x04` | Secondary discriminator, reached through the event field at `0x08` |

The event field at `0x08` has two distinct structural uses. For discriminator `0x16`, it is dereferenced as an address. For discriminator `0x0F`, it is compared as a word value without being dereferenced by this function.

The following callable-table slots are used:

| Table byte offset | Dispatch role |
|---:|---|
| `0x14C` | Initial handler for a matching discriminator-`0x0F` event |
| `0x124` | Shared-path handler for discriminator `0x16`, secondary discriminator zero |
| `0x10C` | Main shared-path handler for discriminator `0x16`, secondary discriminator `0x2A` |
| `0x110` | Main shared-path handler for every other case |
| `0x0E0` | Final handler for a matching discriminator-`0x0F` event |

All table-dispatched handlers receive the receiver and event addresses.

### Preconditions

Every field actually reached must be readable, and every selected callable entry must be callable under the applicable ABI. The function performs no explicit null, bounds, alignment, table-length, or pointer-validity checks.

These requirements are path-dependent:

- The event discriminator is always read.
- A secondary-record address is dereferenced only when a discriminator read at that stage equals `0x16`.
- The event selector at `0x0C` is read only during initial type-specific dispatch for discriminator `0x13`.
- Receiver fields at `0xC0` and `0x50` are read only on their respective discriminator-`0x0F` paths.
- Receiver field `0xF8` is read only when the preliminary notification condition matches.
- Callable-table accesses occur only when their corresponding handler is invoked.

The receiver and event may be mutated by dependencies. Validity must therefore hold at each subsequent access, not merely at entry.

## Behavior

### 1. Preliminary notification

The function first reads the event discriminator at `0x04`.

If it equals `0x16`, the function reads the secondary-record address from event offset `0x08`, then reads the secondary discriminator at that record’s offset `0x04`.

If that secondary discriminator equals `0x2502`, the function:

1. Reads the receiver word at `0xF8`.
2. Converts that word to a character-sized value.
3. Invokes F-fa9d474c64ca with the receiver and the converted value.

No result from this invocation is inspected. It does not directly cause an early return.

The exact signed interpretation of the converted character argument is not established. The source establishes a conversion from a word to a character type, rather than forwarding the entire word unchanged.

After this stage, the event discriminator is read again. The initial discriminator and secondary discriminator are not treated as stable across the preliminary invocation.

### 2. Initial type-specific dispatch

Using the newly read event discriminator, the function selects at most one initial result-bearing handler.

#### Discriminator `0x27`

Invoke F-54014c626648 with the receiver and event.

#### Discriminator `0x13`

Read the selector at event offset `0x0C`.

- If the selector equals `0x7681`, invoke F-b5d0e10d98f4.
- Otherwise, read the selector at `0x0C` again. If this second value equals `0x7682`, invoke F-4fcdc0742c81.
- Otherwise, do not invoke an initial handler.

The second selector comparison is represented through subtraction by `0x7600` and comparison with `0x82`. Under the represented 32-bit word arithmetic, this selects `0x7682`; it does not select an interval or require a separate upper-bit test.

The second selector read is observable independently of the first. If the selector can change between reads, dispatch follows the values actually observed. Such changes require an external memory or concurrency model not supplied here.

#### Discriminator `0x0F`

Read the event word at `0x08`, then the receiver word at `0xC0`.

If they are equal, resolve and invoke the receiver-table handler at `0x14C`. Otherwise, do not invoke an initial handler.

#### Other discriminators

Do not invoke an initial handler.

#### Initial-handler result

For any initial handler that is invoked:

- A nonzero result is returned immediately and unchanged.
- A zero result enters the shared fallback sequence.

If no initial handler applies, the function enters that same shared sequence.

A handler that changes the event to a different type does not cause initial dispatch to restart. Its changes can affect later fallback stages.

### 3. Shared zero-secondary handler

Read the event discriminator again.

If it equals `0x16`, read the secondary-record address at event offset `0x08`, then the secondary discriminator at record offset `0x04`.

If the secondary discriminator is zero, resolve and invoke the receiver-table handler at `0x124`.

- A nonzero result is returned immediately.
- A zero result continues to the next stage.

If the discriminator is not `0x16`, or its secondary discriminator is not zero, this handler is skipped.

### 4. Main shared-path handler

Read the event discriminator again.

If it equals `0x16`, read the secondary-record address and then its secondary discriminator again. Select:

- Table slot `0x10C` if the secondary discriminator equals `0x2A`.
- Table slot `0x110` otherwise.

If the discriminator is not `0x16`, select table slot `0x110` without reading a secondary record.

Resolve and invoke the selected handler with the receiver and event.

- A nonzero result is returned immediately.
- A zero result continues to the final stage.

Exactly one of these two main shared-path handlers is invoked whenever execution reaches this stage. They are alternatives, not consecutive fallback handlers.

The discriminator, secondary-record address, secondary discriminator, and receiver table are obtained at this stage rather than preserved from earlier stages. In particular, a zero-returning handler at `0x124` can change which main shared-path handler is selected.

### 5. Final matching handler

Read the event discriminator again.

If it equals `0x0F`, read the event word at `0x08`, then the receiver word at `0x50`.

If those values are equal, resolve and invoke the receiver-table handler at `0x0E0`.

- A nonzero result is returned unchanged.
- A zero result produces the function’s final zero result.

If the discriminator or comparison does not match, return zero without this invocation.

The receiver comparison field here is `0x50`, not `0xC0`. The two discriminator-`0x0F` gates are independent and occur at different points in dispatch.

## Side effects

### Direct effects

The function directly performs field reads, callable-table reads, and dependency invocations. No direct write to receiver storage, event storage, secondary-record storage, or global storage is present in the supplied body.

No direct allocation, deallocation, ownership transfer, or reference-count adjustment is present.

### Dependency-mediated effects

All invoked dependencies may have effects not shown here, including mutation of:

- The receiver and its callable-table address.
- The event discriminator or payload fields.
- A secondary record.
- Global state or other reachable objects.

No preservation guarantee for these objects or globals can be inferred.

Consequently, replacing repeated reads with entry-time snapshots would not preserve the established behavior when an intervening dependency mutates relevant storage. Each later stage uses the fields read at that stage.

For each table invocation, the receiver’s table address is read and the selected entry is loaded. The function does not retain one table address for all dispatch stages.

### Read and call ordering

The observable order is:

1. Initial discriminator read and, conditionally, secondary-record reads.
2. Conditional receiver-character read and preliminary notification.
3. A fresh discriminator read and initial-dispatch reads.
4. An optional initial handler.
5. Fresh reads for the zero-secondary shared handler.
6. An optional handler at `0x124`.
7. Fresh reads selecting one main shared-path handler.
8. That main handler.
9. Fresh reads for the final comparison.
10. An optional handler at `0x0E0`.

Any nonzero result-bearing handler prevents all later stages from executing.

### Errors and ownership

No explicit error object, status translation, recovery path, or cleanup path is established. A dependency’s nonzero value is propagated without interpreting whether it denotes success, failure, or another dispatch outcome.

Invalid memory or an invalid callable entry is not converted into a defined integer error by this body. The resulting behavior depends on the execution environment.

The supplied body does not establish ownership of either argument. It also does not establish whether a dependency retains, releases, or invalidates supplied objects. If a dependency returns normally and execution continues, subsequent accesses require those objects to remain valid.

## Acceptance examples

These are conditional contract examples, not reports of execution. Unless stated otherwise, invoked dependencies return normally, preserve the relevant fields, and all accessed storage is valid.

1. **Initial handler terminates dispatch.**  
   With discriminator `0x27`, F-54014c626648 returns `7`. The function returns `7`; no shared-path handler is invoked.

2. **Negative results also terminate dispatch.**  
   With discriminator `0x13` and selector `0x7681`, F-b5d0e10d98f4 returns `-3`. The function returns `-3` unchanged.

3. **Second selector selects a distinct handler.**  
   With discriminator `0x13`, both selector reads returning `0x7682`, F-4fcdc0742c81 is invoked. If it returns zero, the main shared-path handler is subsequently selected from current event state.

4. **An unmatched selector does not terminate dispatch.**  
   With discriminator `0x13` and both selector reads returning `0x7683`, neither selector-specific handler is invoked. With unchanged fields, the main shared-path handler is the entry at `0x110`.

5. **Preliminary notification does not consume the event.**  
   With discriminator `0x16` and secondary discriminator `0x2502`, F-fa9d474c64ca receives the receiver and character-converted receiver field. With unchanged fields, dispatch later invokes the main entry at `0x110`, regardless of any return value produced by the preliminary dependency.

6. **Preliminary mutation affects initial dispatch.**  
   If that preliminary dependency changes the event discriminator to `0x27`, the following fresh read selects F-54014c626648. The function does not continue treating the event as necessarily having discriminator `0x16`.

7. **Zero-secondary handling precedes the main handler.**  
   With discriminator `0x16` and secondary discriminator zero, the entry at `0x124` is invoked first. If it returns zero and fields remain unchanged, the main entry is `0x110`. If it returns nonzero, no main handler is invoked.

8. **A zero-returning handler may redirect later selection.**  
   If the entry at `0x124` changes the secondary discriminator from zero to `0x2A` and returns zero, the main entry selected by subsequent reads is `0x10C`.

9. **The special main entry is exclusive.**  
   With discriminator `0x16` and secondary discriminator `0x2A`, the main entry is `0x10C`. A zero result from it does not trigger the alternative entry at `0x110`.

10. **The two equality gates are independent.**  
    With discriminator `0x0F`, event word `0x08` unequal to receiver field `0xC0` but equal to receiver field `0x50`, the initial entry at `0x14C` is skipped. If the main entry at `0x110` returns zero, the final entry at `0x0E0` is invoked.

11. **Exhaustion returns zero.**  
    If every invoked result-bearing handler returns zero, the function returns zero after the last applicable stage. Skipped handlers do not contribute a result.
