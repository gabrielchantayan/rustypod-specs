# F-b73bd82d3437

## Purpose

F-b73bd82d3437 constructs selected fields of a caller-provided output record. A 32-bit field in the input selects either direct construction from that field or construction from shared fallback data.

A nonzero input field selects direct construction without dependency calls. A zero input field selects fallback handling. On that path, a shared status bit and a dependency’s zero/nonzero result determine whether two additional dependencies run before the fallback data is read.

The two paths obtain their output markers from different global source designations. **Different source designations do not establish different runtime values.** Both marker values are 32 bits; their numeric values, equality, and semantic meanings are unknown. Marker equality would not change branch selection or the remaining field operations.

Record construction and conditional calls are established behavior. “Lazy initialization,” “locking,” and similar interpretations are possible intent, not established dependency semantics.

## Interface

The function takes two arguments:

- **Output address:** the base address of caller-provided writable storage.
- **Input address:** an address used to read a 32-bit field at byte offset 8.

There is no explicit return value. Observable results consist of memory writes, conditional dependency calls, and any effects of those dependencies.

The supplied representation uses 32-bit address-bearing values. The input argument is represented as an integer but used as an address. The evidence does not establish support for wider addresses or checked address arithmetic.

### Shared inputs

## Behavior

### Initial selection

The initial record access reads the 32-bit input field at offset 8. Its captured value controls the entire direct-versus-fallback decision.

Later modification of the input field does not cause reconsideration. In particular, a dependency reached after a zero input cannot switch execution to direct construction by changing that field.

### Direct construction

For nonzero captured input, the observable field operations occur in this order:

1. Obtain the 32-bit value supplied by the direct-marker designation and write it to output offset 0.
2. Write the single byte 1 to output offset 4.
3. Write the captured input value to output offset 8.
4. Write a 32-bit zero to output offset 12.

The function then returns.

No dependency is called. Neither the status field nor the fallback record is read on this path. The input value undergoes no visible arithmetic, normalization, saturation, or range conversion.

The marker write is a value obtained from its global designation, not evidence that the designation’s address is being stored.

### Fallback dependency gate

For zero captured input, the function obtains the status-structure address and reads its 32-bit field at offset 28. Only bit 0 is tested.

If bit 0 is set, all three dependencies are skipped.

If bit 0 is clear, F-b255b26284e6 is called with the shared argument value evaluated for that call:

- A zero result skips both remaining dependencies.
- A nonzero result causes F-b07efd113d9d to run, followed by F-d08d3ca17b81.

F-b07efd113d9d receives the shared fallback-record address evaluated for its call. F-d08d3ca17b81 receives the shared argument value evaluated for its later call.

The tested prerequisite result is a 32-bit integer. Only zero versus nonzero matters; a negative signed interpretation is not handled as a distinct case. No result from either subsequent dependency is used.

The status bit is not read again after the gate. Changes to it during a dependency do not introduce another check or cancel the remaining calls.

Shared values are not established as immutable across calls. Consequently:

- F-b255b26284e6 may affect which fallback address is subsequently passed to F-b07efd113d9d.
- Earlier dependencies may affect the shared argument later passed to F-d08d3ca17b81.
- The later argument need not equal the argument previously passed to F-b255b26284e6.

These are consequences of evaluation order, not claims that any dependency actually performs such mutations.

### Fallback construction

After the gate and any normally returning dependencies, the function reads and retains the shared fallback-record address for output construction. This address is obtained after the calls, rather than preserved from before them.

The following field operations then occur in order:

1. Obtain the 32-bit value supplied by the fallback-marker designation and write it to output offset 0.
2. Read the fallback byte at offset 4 and write it to output offset 4.
3. Read and retain the fallback 32-bit word at offset 12.
4. Read the fallback 32-bit word at offset 8 and write it to output offset 8.
5. Write the retained word to output offset 12.

The function then returns.

The fallback byte is copied without normalization. Any 8-bit value is permitted by the visible operation.

The offset-12 word is read before the offset-8 word, even though output offset 8 is written before output offset 12. This is not an atomic record snapshot.

The fallback address retained for this construction is not reloaded between these field operations. A later change to the shared location holding that address does not, by itself, redirect the remaining reads. Changes to memory at the retained address can still affect reads that have not yet occurred.

### Aliasing and interference

No explicit non-aliasing check or restriction appears in the function. This does not prove that every overlapping arrangement is intended or valid. For otherwise valid overlapping accesses, the stated ordering matters.

On the direct path, the input value is already captured before output writes begin. Overwriting its original storage does not change the value later written at output offset 8.

On the fallback path:

- The output marker is written before any fallback data field is read.
- The output-byte write precedes both fallback-word reads.
- The fallback offset-12 word is retained before the output-offset-8 write.

Thus, an overlapping earlier write may change a later source read. Conversely, changing the original offset-12 storage after that word has been retained does not refresh the final value written to output offset 12.

The ordinary output table assumes noninterfering storage. With overlap, its entries must be interpreted through the ordered accesses rather than as a simultaneous copy of original contents.

No synchronization, atomicity, or coherent-snapshot guarantee is established. The source alone does not define platform behavior for concurrent races or memory-mapped access effects.

Those direct writes may also modify shared or source storage if the output aliases it. The absence of an explicit assignment to a global designation is not a guarantee that aliased global storage remains unchanged.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless an example states otherwise, assume valid, stable, nonoverlapping storage and normally returning dependencies.

### Nonzero input

With input field 37:

- No dependency is called.
- Output offset 0 receives the current direct-marker value.
- Output offset 4 receives byte 1.
- Output offset 8 receives the 32-bit value 37.
- Output offset 12 receives zero.
- Output bytes 5–7 remain unchanged.

The status field and fallback contents do not affect this path.

### High-bit-set input

With input pattern 0x80000000, direct construction is selected and output offset 8 receives exactly that pattern. No dependency is called. Its signed interpretation does not select fallback handling.

### Equal marker values

If both marker designations supply 0x12345678:

- A direct execution writes 0x12345678 at output offset 0.
- A fallback execution also writes 0x12345678 there.
- Each execution still follows its own gate and payload operations.

A consumer cannot rely on the marker alone to distinguish these paths unless some external contract establishes distinguishable values.

### Set status bit

With zero input and status bit 0 set, no dependency is called. The fallback fields are copied in the specified order. Other status bits do not affect this gate.

### Clear status bit and zero prerequisite result

With zero input, clear status bit 0, and a zero result from F-b255b26284e6:

- Only F-b255b26284e6 is called.
- Fallback construction still occurs.
- Its effects are not undone before the later shared reads.

If that dependency replaces the shared fallback address with another valid address, construction uses the replacement.

### Clear status bit and nonzero prerequisite result

With zero input, clear status bit 0, and a nonzero prerequisite result, the dependency order is F-b255b26284e6, F-b07efd113d9d, then F-d08d3ca17b81. Fallback construction follows.

A change to the status bit during these calls causes no recheck. Changes to fallback data or its shared address may affect construction.

### Byte boundary

With fallback byte 0xA5, output offset 4 receives exactly 0xA5. The assignment does not clear or replace bytes 5–7. Under the stated noninterference assumptions, those bytes retain their prior contents.

### Retained word under overlap

Suppose output offset 8 overlaps the fallback word at offset 12, with all accesses otherwise valid. The function reads and retains that fallback word before writing output offset 8. The final output-offset-12 write uses the retained value, even if the intervening write changes its original storage.

This example does not establish that arbitrary overlapping layouts are supported by the platform.
