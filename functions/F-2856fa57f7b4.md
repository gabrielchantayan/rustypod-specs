# F-2856fa57f7b4

## Purpose

F-2856fa57f7b4 coordinates a sequence of handlers for a context and an object. It first attempts one of several specialized handlers, then a callback selected from the context’s dispatch table, and finally a conditional callback associated with a context-relative identity match.

The established result convention is:

- A nonzero result from an invoked handler or callback ends processing immediately and is returned unchanged.
- A zero result permits the next applicable stage.
- If no invoked stage returns nonzero, the function returns zero.

“Handled,” “declined,” and “identity match” are useful interpretations of this control flow, not established domain meanings. No particular object model, diagnostic policy, or resource-management protocol is established.

## Interface

### Inputs

The function takes two arguments:

1. **Context reference.** An address of storage whose first word supplies a dispatch-table address. A later conditional stage also accesses a word at context byte offset `0x50`.
2. **Object reference.** An address of storage with a discriminator at byte offset `0x04` and a conditionally accessed word at byte offset `0x08`.

Both original argument values are passed, in the same order, to every selected specialized handler and indirect callback. The classification dependency receives only the original object reference.

The exposed representation uses 32-bit integer words and address-bearing fields. Offsets below are byte offsets. The interface description establishes these accessed slots, not the full sizes or definitions of either structure.

| Storage | Offset | Established use |
|---|---:|---|
| Context | `0x00` | Dispatch-table address |
| Context | `0x50` | Value compared with the object’s `0x08` word during the final conditional stage |
| Object | `0x04` | Discriminator used throughout dispatch |
| Object | `0x08` | Nested-object address or comparison value, depending on the discriminator |
| Nested object | `0x04` | Discriminator used to choose between two callbacks |
| Dispatch table | `0x0E0` | Final conditional callback entry |
| Dispatch table | `0x10C` | Callback entry for one nested-discriminator case |
| Dispatch table | `0x110` | Callback entry for all other cases at that stage |

For the dispatch table, these are byte displacements to function-pointer slots, not ordinal method numbers.

### Output

The output is a 32-bit integer. Zero means that no executed stage produced a nonzero result. Any nonzero result is forwarded without conversion, normalization, or interpretation. Negative results are therefore propagated just as positive results are.

### Preconditions

All storage actually accessed along the executed path must be valid for the corresponding reads. In particular:

- The object discriminator must be readable whenever dispatch reaches a discriminator check.
- The context’s dispatch-table address and the selected callback slot must be readable when a callback is selected.
- A nested-object address used for the nested-discriminator case must support a read at byte offset `0x04`.
- Every selected indirect callback must be a valid callable target compatible with the two-argument invocation and integer result convention.
- Context offset `0x50` and object offset `0x08` must be readable if the final comparison is reached with the required discriminator.

There is no explicit null check, bounds check, callback validation, or recovery path for invalid storage. Fault behavior for invalid inputs is not specified by this contract.

## Behavior

### 1. Specialized-handler selection

The function evaluates the following alternatives in order. The order and repeated reads are observable when a dependency changes the object.

1. Read the object discriminator. If it is `0x15`, invoke **F-91c1e0ac85c5** with the context and object.
2. Otherwise, read the discriminator again. If it is `0x0D`, invoke **F-468ee00d626a** with the object. If that result is exactly `0x6F`, invoke **F-52454889933b** with the context and object.
3. If the preceding alternative was not selected, read the discriminator again. If it is `0x0D`, invoke **F-468ee00d626a** again. If this invocation returns exactly `0x6E`, invoke **F-d2aaf6b6aced** with the context and object.
4. If the preceding alternative was not selected, read the discriminator again. If it is `0x0D`, invoke **F-468ee00d626a** again. If this invocation returns exactly `0x10`, invoke **F-d9f17153a5ae** with the context and object.
5. If none of these alternatives selects a specialized handler, proceed directly to the general callback stage.

The classifier result is not cached across alternatives. The classifier can be invoked zero, one, two, or three times during this stage. Each invocation belongs to a distinct comparison and may return a different value.

The discriminator is also reread before each later classification opportunity. A classifier that changes the discriminator can therefore prevent or enable later classifier invocations.

At most one specialized handler is invoked by this stage. Once a specialized handler is selected:

- A nonzero result is returned immediately.
- A zero result proceeds to the general callback stage.
- A zero result does **not** resume the remaining specialized alternatives, even if the handler changed the discriminator or classifier-visible state.

The classifier’s result is used only for selection. An unmatched nonzero classifier result is not returned as the function’s result.

### 2. General callback selection

On reaching this stage, the function reads the current object discriminator anew. This read occurs after any specialized handler has returned zero.

If the current discriminator is `0x16`:

1. Read the object word at byte offset `0x08` as a nested-object address.
2. Read the nested object’s discriminator at byte offset `0x04`.
3. Select the callback at dispatch-table byte offset `0x10C` if that nested discriminator is `0x2A`.
4. Otherwise select the callback at dispatch-table byte offset `0x110`.

For every current object discriminator other than `0x16`, select the callback at dispatch-table byte offset `0x110` without performing the nested-object reads.

After the discriminator and any nested discriminator have been examined, the function reads the context’s dispatch-table address and the selected callback entry. It then invokes that callback with the original context and object arguments.

Consequences:

- A specialized handler can change which general callback is selected.
- The context’s dispatch-table address is obtained after the specialized stage; it is not a table snapshot captured on entry.
- The nested-object word is not needed for callback selection when the current discriminator is not `0x16`.
- Exactly one of the two general callback slots is selected and invoked on an ordinary execution reaching this stage.

If the callback returns nonzero, return that exact result immediately. Otherwise proceed to the final conditional stage.

### 3. Final conditional callback

After the general callback returns zero, read the object discriminator again.

If it is not `0x0F`, return zero without performing the final comparison or callback lookup.

If it is `0x0F`:

1. Read the object word at byte offset `0x08`.
2. Read the context word at byte offset `0x50`.
3. Compare those two 32-bit values for equality.
4. If they differ, return zero.
5. If they are equal, read the context’s dispatch-table address anew, obtain its callback at byte offset `0x0E0`, and invoke it with the original context and object arguments.

Return the final callback’s result if it is nonzero. If it is zero, return zero.

The comparison is exact word equality, not a nested-object discriminator check. Whether the compared words represent addresses, handles, identifiers, or another value class is not established.

Because this stage rereads both the object discriminator and, when needed, the dispatch-table address, changes made by the general callback affect final-stage eligibility and callback selection.

### Integer and address behavior

All discriminator comparisons and the final equality comparison operate on the represented 32-bit words. Signed ordering, arithmetic overflow, and numeric range checks are not involved.

The visible address calculations use fixed byte displacements. The function does not compute an allocation size, increment a counter, or perform variable-length indexing. These observations do not establish behavior for invalid addresses or address-space wraparound.

## Side effects

That does not make the overall operation read-only. Every called dependency or callback may have side effects not described here. In particular, this contract does not assume that a callee:

- Preserves either input object or the dispatch-table address.
- Preserves globals or other shared state.
- Leaves the object discriminator unchanged.
- Retains, transfers, or releases ownership in any particular way.
- Returns normally.

The caller must arrange that storage needed after a returning dependency remains valid. A dependency that invalidates storage subsequently read can prevent defined completion; the function supplies no visible ownership safeguard.

Aliasing between the context, object, nested object, and other referenced storage is not prohibited by a visible check. It must not be treated as harmless: callee mutations to aliased storage can affect subsequent reads.

## Acceptance examples

These are conditional, static acceptance cases, not executed tests. Each assumes valid storage and normally returning callees unless stated otherwise.

1. **Immediate specialized result.** If the initial discriminator is `0x15` and F-91c1e0ac85c5 returns `-7`, the result is `-7`. No classifier or indirect callback is invoked afterward.

2. **First classifier match.** If the initial discriminator is not `0x15`, the next read is `0x0D`, and the classifier returns `0x6F`, F-52454889933b is selected. Even if that handler returns zero, neither later specialized handler is attempted.

3. **Repeated classification matters.** With a discriminator remaining `0x0D`, suppose successive classifier results are `0x00`, `0x6F`, and `0x10`. The first comparison fails, the second comparison also fails because it requires `0x6E`, and the third selects F-d9f17153a5ae. The second result does not retroactively select F-52454889933b.

4. **Classifier mutation suppresses later calls.** Suppose the first classifier invocation returns an unmatched value and changes the discriminator from `0x0D` to `0x16`. If it remains `0x16`, the later classification opportunities do not call the classifier. General callback selection then examines the nested-object discriminator.

5. **Nested callback selection.** On reaching general dispatch with discriminator `0x16`, a valid nested-object address, and nested discriminator `0x2A`, the callback at offset `0x10C` is invoked. A different nested discriminator selects offset `0x110`.

6. **Non-nested general dispatch.** On reaching general dispatch with discriminator `0x0F`, offset `0x110` is selected without reading the object’s `0x08` word for that selection. A nonzero callback result prevents the later comparison.

7. **Final-stage state comes from after the callback.** Suppose the general callback returns zero and changes the discriminator to `0x0F`. If the subsequently read object `0x08` word equals the subsequently read context `0x50` word, the final callback is invoked even if the discriminator was different before the general callback.

8. **Changed dispatch table is honored.** If the general callback returns zero, leaves a qualifying final comparison, and changes the context’s dispatch-table address, the final callback is obtained from that new table.

9. **No final match.** If the general callback returns zero and the final discriminator is `0x0F` but the two compared words differ, the result is zero and the callback at offset `0x0E0` is not read or invoked.
