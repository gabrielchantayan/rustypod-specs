# F-9549e5a07150

## Purpose

F-9549e5a07150 searches the end of a byte sequence for an uppercase hexadecimal field introduced by `#`, optionally ignoring a short alphanumeric extension. It returns the field’s numeric value and writes the marker’s byte offset to a caller-provided output location.

The function is not a general string parser. It does not search arbitrarily past invalid characters, accept lowercase hexadecimal digits, or stop at a zero byte. Its effective input boundary is supplied explicitly or obtained from F-1cb585febd84.

The apparent intent is to extract a hexadecimal identifier from a name-like sequence. That interpretation is inferred; the established behavior is byte-oriented scanning and conversion.

A return value of zero does not distinguish failure from successful conversion of a zero-valued field. The output offset provides additional information, but it is written before conversion finishes and therefore is not itself a success flag.

## Interface

The function has three inputs:

| Input | Role |
|---|---|
| Base address | Address of the first byte of the candidate sequence. A zero address suppresses scanning. |
| Extent | Unsigned length or boundary value. Zero requests a value from F-1cb585febd84, provided the base address is nonzero. |
| Offset output | Address of a writable unsigned integer receiving an initial zero and, on some paths, the offset of a qualifying `#`. |

The return is a signed integer containing the converted value, or zero on a rejection path.

### Width model

### Preconditions

The offset output must be writable even when the base address is zero or the extent is too short to scan. It is written before either condition is checked.

For a nonzero base address, the caller must make all bytes actually reached by the scans readable. An allocation containing only the stated extent is not sufficient for every large-extent case: the suffix scan uses the full extent, while the subsequent search narrows its index to 16 bits.

No zero terminator is required by the visible scanning logic. A zero byte is an ordinary byte that fails the relevant character tests.

There is no visible allocation, ownership transfer, or release. The implementation of F-1cb585febd84 is unavailable, so its ownership and memory effects are not established.

## Behavior

### 1. Initial output write and boundary selection

The first observable action is a write of zero to the offset output.

If the base address is zero, the function then returns zero. It does not invoke F-1cb585febd84 or read sequence bytes.

If the base address is nonzero and the supplied extent is zero, the function calls F-1cb585febd84 without visible explicit arguments. Its result becomes the effective extent. No input-length measurement is otherwise visible.

An effective extent of 27 or less produces a zero return without any explicit sequence-byte read by this function.

These early-exit statements do not establish that the offset output remains zero after an unknown dependency call. The dependency may have effects not shown here.

### 2. Optional extension recognition

For an effective extent greater than 27, the function begins at the final byte, at offset one less than the extent, and reads backward.

It recognizes an ignorable terminal extension only when:

- The terminal run contains between one and five bytes, inclusive.
- Every byte in that run is an ASCII letter or decimal digit.
- A literal `.` immediately precedes the run.

Both uppercase and lowercase letters are permitted in this extension.

When those conditions hold, the extension and its preceding dot are excluded from the subsequent hexadecimal search. The adjusted boundary is therefore the original extent minus the extension length minus one.

If the backward scan encounters a non-alphanumeric byte other than `.`, or encounters a sixth alphanumeric byte, extension recognition fails. The original extent remains the boundary for the subsequent search.

A terminal dot also fails extension recognition because the run after it is empty. Failure to recognize an extension is not an immediate function failure; the next phase still runs against the unadjusted boundary.

This phase reads at most six bytes. With an extent greater than 27, it does not need to cross the beginning of the stated sequence.

### 3. Backward hexadecimal search

The selected boundary serves two distinct purposes:

- Its full 32-bit value remains the endpoint used later by conversion.
- Its low 16 bits determine where the backward search begins.

Before each search read, the current index is narrowed to signed 16 bits, decremented by one, narrowed again, and sign-extended for the nonnegative check. If that result is negative, the function returns zero without reading at that index.

For boundaries from 28 through 32768, inclusive, the first search read is at boundary minus one. Larger boundaries do not retain this ordinary relationship:

| Selected boundary | First search action |
|---|---|
| 32768 | Read offset 32767 |
| 32769 | Return zero without a search-byte read |
| 65536 | Return zero without a search-byte read |
| 65537 | Read offset 0 |

These examples describe this phase only. The preceding extension probe still reads near the full effective extent.

At each nonnegative search index:

- A decimal digit permits the backward search to continue.
- An uppercase letter `A` through `F` permits it to continue.
- A `#` selects the candidate marker.
- Every other byte causes a zero return.

Thus, the search stops at the first byte outside the hexadecimal alphabet unless that byte is `#`. It does not skip punctuation, whitespace, lowercase letters, embedded zero bytes, or other invalid bytes to find an earlier marker.

For ordinary boundaries, the selected marker is the `#` immediately before the terminal run of uppercase hexadecimal digits.

### 4. Marker qualification and offset publication

On finding `#`, the function computes the unsigned difference between the selected boundary and the marker offset.

If that difference is less than three, it returns zero without publishing the marker offset. For an ordinary, nonwrapped boundary, this requires at least two bytes after `#`.

Otherwise, it writes the marker offset to the output location.

This write occurs before the function rereads and converts the bytes following the marker. A later conversion failure does not undo it.

For ordinary, disjoint, stable input, the backward search has already checked the field’s character set. The second pass nevertheless performs its own checks. Those checks matter if memory changes between reads, if the output aliases the sequence, or if a large boundary causes the backward search and conversion range to differ.

### 5. Forward conversion

After publishing the marker offset, the function rereads bytes in increasing-address order, starting immediately after `#`.

The intended conversion endpoint is the selected boundary. On each iteration, the byte address advances before the count-versus-boundary check; the byte itself is read only if that check permits another digit.

Accepted digit bytes are:

- `0` through `9`, contributing values zero through nine.
- `A` through `F`, contributing values ten through fifteen.

Each accepted digit multiplies the accumulated value by sixteen and adds the digit value.

Any other byte returns zero immediately. The previously published marker offset remains unless some external or aliasing effect changes it.

There is no explicit maximum digit count or overflow rejection. Leading zeroes are accepted. Lowercase hexadecimal letters are rejected.

The conversion counter also has a signed 16-bit narrowing step. After processing 32768 digits, its next stored unsigned representation is `0xFFFF8000`, rather than the ordinary count 32768. That value is compared with the unsigned required digit count before another byte is read.

For ordinary selected boundaries no greater than 32768, this counter limit is not reached. For large extents, conversion can have nonstandard termination behavior. In particular, the search may find a marker at a low offset while conversion uses a much larger full-width endpoint. The function must not be specified as a conventional unrestricted-length hexadecimal parser.

## Side effects

The visible write order is:

1. Store zero through the offset output.
2. Optionally call F-1cb585febd84.
3. Read bytes backward for extension recognition.
4. Read bytes backward for the hexadecimal search.
5. If a marker passes the distance check, store its offset.
6. Read bytes forward for conversion.

No explicit sequence write occurs except where the offset output aliases sequence storage.

Aliasing is not checked. Its consequences are observable:

- The initial zero store can change bytes that will later be scanned.
- The marker-offset store can change bytes that conversion will subsequently reread.
- A marker can be found and published, followed by a zero return caused by the output write corrupting the candidate field.

Accordingly, non-overlapping input and output is a useful caller precondition for ordinary parsing behavior, but it is not enforced by the function.

No explicit global read or write appears in the supplied function body. That does not imply that F-1cb585febd84 preserves global state, input storage, or the offset output.

Invalid addresses and unreadable storage are not converted into a structured error. No visible null check protects the output pointer, and no visible bounds-validation mechanism protects the byte reads.

## Acceptance examples

These examples are conditional predictions from static evidence, not runtime test results. Unless stated otherwise, they assume valid addresses, stable non-overlapping input and output, an explicit nonzero extent, and values small enough to avoid signed accumulator overflow.

1. **Null base address.**  
   With a writable output and a zero base address, the output is set to zero and the return is zero. The extent does not cause a dependency call on this path.

2. **Short input.**  
   A nonzero base address and extent 27 produce zero without explicit sequence-byte reads. A candidate ending in `#AB` is still ignored if the entire stated extent is at most 27.

3. **Uppercase hexadecimal field.**  
   A sequence consisting of 28 `x` bytes followed by `#1A`, with extent 31, returns 26 and writes offset 28. The prefix is not inspected after the marker is found.

4. **Recognized extension.**  
   A sequence consisting of 28 `x` bytes followed by `#1A.txt`, with extent 35, also returns 26 and writes offset 28. The terminal three-letter extension and its dot are excluded before the hexadecimal search.

5. **Five-character extension.**  
   Replacing that extension with `.a1B2c` still permits recognition. Extension letters need not be uppercase and need not be hexadecimal.

6. **Six-character extension.**  
   A terminal `.abcdef` is not stripped. The backward hexadecimal search then encounters the final lowercase `f` and returns zero without publishing the marker.

7. **Empty extension.**  
   A terminal `#1A.` does not strip the dot. The hexadecimal search rejects the final dot.

8. **Too few digits.**  
   A sequence consisting of 28 `x` bytes followed by `#A` returns zero and leaves the output at its initial zero. The marker-to-boundary distance is two, below the required three.

9. **Successful zero value.**  
   A sequence consisting of 28 `x` bytes followed by `#00` returns zero but writes offset 28. This is a successful conversion whose return value matches the failure value.

10. **Invalid lowercase digit.**  
    A sequence ending in `#aF` reaches uppercase `F`, then rejects lowercase `a`. It does not continue backward to the marker.

11. **Nearest invalid separator.**  
    A sequence ending in `#12-AB` returns zero at `-`. It does not recover the earlier `#`.

12. **Narrowed search boundary.**  
    With selected boundary 32769, the first backward-search index is negative after signed 16-bit narrowing. The search returns zero even if the readable bytes near the full boundary contain a valid-looking field.

13. **Aliased output and field.**  
    If publishing the marker offset overwrites a digit with an invalid byte, the later forward pass returns zero. The earlier backward validation does not guarantee success.
