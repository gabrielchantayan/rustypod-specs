# F-40a81407b15f

## Purpose

F-40a81407b15f validates two pointer arguments and a three-valued selector, invokes a construction-like dependency, examines a status field in its result, and either publishes that result through an output pointer or invokes an indirect operation followed by status translation.

The established contract is structural. It does not identify the application-level meaning of the input, selector values, returned object, or translated status.

The return value is a 64-bit composite with independently meaningful upper and lower 32-bit portions. It must not be interpreted as an ordinary sign-extended status code:

- Rejected entry arguments produce a lower portion of `0xFFFFFFCE` and preserve the second argument as the upper portion.
- An accepted returned status produces a lower portion of zero and an upper portion of `0x00000400`.
- A rejected returned status produces a lower portion supplied by a translation dependency and an upper portion of `0x00000400`.

**Inferred intent:** the function appears to construct or open an object, tolerate a special status in two selector modes, and dispose of an unsuccessful result. These interpretations do not establish allocation, ownership, or cleanup guarantees.

## Interface

### Inputs

The function has four arguments, in order:

1. **Input pointer.** A pointer treated as addressing a 16-bit element followed immediately by additional input beginning two bytes later. A null value is rejected. On a valid-selector path, the first 16-bit element is read, and the address two bytes beyond the pointer is passed to a dependency.
2. **Upper-return input.** An opaque 32-bit value. It is used only to form the direct return value for rejected entry arguments. It is not passed to any dependency in the supplied evidence.
3. **Selector.** A 32-bit integer. Exactly the values 1, 2, and 3 are accepted.
4. **Output-slot pointer.** A pointer to a writable 32-bit slot. A null value is rejected. On an accepted-status path, the returned object pointer is stored in this slot as a 32-bit value.

Neither a length nor an independently supplied bound accompanies the input pointer. No string termination, encoding, alignment, or readable extent for the data after the initial two bytes is established.

### Return layout

The return is a 64-bit value with the following logical layout:

| Bits | Meaning |
|---|---|
| 63–32 | Entry-rejection context or fixed value `0x00000400` |
| 31–0 | Direct rejection value, zero, or translated result |

The three return forms are:

| Path | Upper 32 bits | Lower 32 bits |
|---|---:|---:|
| Null input pointer, null output-slot pointer, or unsupported selector | Second argument | `0xFFFFFFCE` |
| Accepted returned status | `0x00000400` | `0x00000000` |

The lower-bit pattern `0xFFFFFFCE` represents −50 when interpreted as a signed 32-bit integer. Its placement in the lower portion does not make the complete 64-bit return equal to −50.

## Behavior

### 1. Reject invalid entry arguments

The function first tests the input pointer and output-slot pointer for null.

If either is null, it immediately returns the entry-rejection composite. It does not directly dereference either pointer, write the output slot, or invoke any dependency.

If both pointers are non-null, the selector is classified:

- Selector 1 selects mode 1.
- Selector 2 selects mode 0.
- Selector 3 selects mode 0.
- Every other selector value immediately returns the same entry-rejection composite.

Thus unsupported selectors are rejected before the first direct input-data read or dependency invocation. Non-null pointers alone do not establish readable or writable storage, but rejection does not require such storage to be accessed.

### 2. Obtain an intermediate value

For an accepted selector, F-8157a180d901 is invoked with the single numeric argument `0x54`, or 84 decimal.

Its returned 32-bit value becomes the first argument to the next dependency. This function does not check it for null, zero, or any other failure representation.

**Inferred intent:** the argument 84 may be a requested object size. The evidence does not establish that F-8157a180d901 is an allocator or that its result conveys ownership.

### 3. Invoke the construction-like dependency

After F-8157a180d901 returns, F-3fc3239fa339 is invoked with seven arguments in this order:

| Position | Value |
|---|---|
| 1 | The value returned by F-8157a180d901 |
| 2 | The input pointer advanced by two bytes |
| 3 | Mode 1 for selector 1; mode 0 for selectors 2 and 3 |
| 4 | A value derived from the initial 16-bit input element by narrowing through a character type and converting to a 32-bit integer |
| 5 | `0x400`, or 1024 decimal |
| 6 | 1 |
| 7 | 0 |

The direct input read supplying argument 4 occurs after the first dependency returns and before F-3fc3239fa339 is entered. Consequently, the relevant input contents are those present after the first dependency has run. No guarantee that earlier contents remain unchanged is established.

The narrowing operation retains the low eight value bits of the 16-bit element on the represented byte-width model. The resulting 32-bit integer depends on whether the character conversion is signed:

- Values from `0x00` through `0x7F` give the corresponding nonnegative integer.
- Values from `0x80` through `0xFF` give −128 through −1 if the character type is signed.
- Those same values give 128 through 255 if the character type is unsigned.

The supplied evidence does not independently settle that character-type property. Nor does it establish which memory byte supplies the low eight value bits without a target byte-order assumption.

The second argument advances by two bytes regardless of the narrowed value. The function itself does not interpret or scan the trailing input.

### 4. Read and classify the returned status

F-3fc3239fa339 returns a pointer treated as an object address. The function immediately reads a 32-bit status at byte offset 28 from that address.

There is no null-result check before this read. A null result therefore does not lead to a defined graceful failure return in the shown behavior.

The status acceptance rule is:

| Selector | Mode | Accepted status values |
|---|---:|---|
| 1 | 1 | 0 |
| 2 | 0 | 0 or 7 |
| 3 | 0 | 0 or 7 |

Every other 32-bit status value is rejected. There is no range check, sign-based classification, or normalization before this decision.

Selectors 2 and 3 have identical behavior within this function. Their original values are not separately passed to the construction-like dependency.

### 5. Publish an accepted result

For an accepted status, the returned object pointer is stored into the caller’s output slot as one 32-bit value.

The function then returns `0x0000040000000000`: upper portion 1024, lower portion zero.

No indirect object operation or status-translation call occurs on this path.

The store occurs after the status read and acceptance decision. No non-aliasing requirement is checked. If the output slot aliases storage used by the input or returned object, the store can overwrite that storage after the decision has already been made.

### 6. Process a rejected result

For a rejected status, the function retains the status value already read.

It then conditionally performs an indirect call if the returned object pointer is non-null. The call target is obtained through:

1. A 32-bit dispatch-table pointer at byte offset 0 of the object.
2. A callable entry at byte offset 4 of that table.

This later null check does not protect the preceding status read.

After the indirect call returns, F-5cecf2e46c23 is invoked with the retained status value. The status is not reread from the object.

If translation returns normally, its 32-bit result becomes the lower portion of the function’s return; the upper portion is 1024.

The function performs no direct store to the caller’s output slot on this path. This does not guarantee that the slot remains unchanged: dependencies may affect aliased or globally reachable memory.

A translated result of zero is not overridden. If translation returns zero, the complete return bits match those of an accepted-status path, despite the absence of the direct output-slot publication.

## Acceptance examples

These examples are conditional consequences of the supplied static evidence, not executed tests.

1. **Null input pointer.** With any selector and any output-slot pointer, a null input pointer produces lower bits `0xFFFFFFCE` and upper bits equal to the second argument. No dependency is invoked.

2. **Unsupported selector.** With both pointers non-null and selector 4, the function returns the entry-rejection composite without directly reading the input contents or writing the output slot.

3. **Selector 1, status zero.** Assuming all accesses and dependencies complete normally, status 0 causes the returned object address to be written to the output slot. The return is `0x0000040000000000`.

4. **Selector 1, status seven.** Status 7 is rejected. The indirect operation precedes translation of 7. The function itself does not publish the object.

5. **Selector 2 or 3, status seven.** Status 7 is accepted. The object is published, and neither the indirect operation nor translation is invoked.

6. **Negative status.** A status with the 32-bit pattern `0xFFFFFFFF` is rejected for all accepted selectors. Its retained value is supplied to translation after the indirect operation returns.

7. **Status changed during the indirect operation.** If the initially read status is 9 and the indirect operation changes the object’s status to 0, translation still receives 9. There is no second status read.

8. **Zero translation result.** If a rejected status translates to zero, the returned bits equal the accepted-status return. The function still performs no direct output publication on that rejected path.

9. **Null construction-like result.** A null result reaches the status read before any null guard. No specific error return, translation call, or recoverable outcome is established.

10. **High-bit input character.** For a first 16-bit input value of `0x0180`, the narrowed eight-bit value is `0x80`. Argument 4 is −128 under signed character conversion or 128 under unsigned conversion. The trailing-input address remains two bytes beyond the initial pointer.
