# F-50f346be9118

## Purpose

F-50f346be9118 performs an ordered lookup over a table of 205 fixed-size records. It returns a 16-bit field from the first record that satisfies three conditions, evaluated in this order:

1. A stored unsigned 16-bit field equals the third input.
2. F-a9106d0ae91a, called with another 16-bit field, returns a value equal to the first input.
3. F-3159305e8693, called with the prospective result field, returns exactly the Boolean normalization of the second input.

If no record qualifies, the function returns the 16-bit value zero.

This is a description of established static behavior. The business meaning of the fields, the table’s ownership, and the dependencies’ internal behavior are not established. In particular, zero is not proven to be reserved for lookup failure.

## Interface

### Inputs

The function takes three inputs:

| Input | Established representation | Role |
|---|---|---|
| First input | Signed 32-bit integer | Required result from F-a9106d0ae91a. |
| Second input | Signed 32-bit integer | Boolean selector: zero selects a required dependency result of zero; any nonzero value selects a required result of one. |
| Third input | Unsigned 32-bit integer | Compared directly against a zero-extended unsigned 16-bit record field. |

The first input is not normalized to a Boolean. Its complete 32-bit value participates in the comparison.

The second input’s sign and magnitude do not distinguish requests. For example, positive one, negative one, and any other nonzero representable value all select the same required result, one.

The third input is not reduced to 16 bits. Values greater than 65,535 cannot equal any value read from the corresponding 16-bit field.

### Output

The output is a 16-bit quantity:

- On a match, it is read from the selected record at byte offset 10.
- On exhaustion, it is zero.

The output’s signed interpretation and semantic type are not established. Consumers should treat the established result as a 16-bit bit pattern unless a separate interface contract assigns further meaning.

A returned zero does not distinguish exhaustion from a successful match whose final result-field read yields zero.

### Table layout

A global table-base value is read once when the function begins. Records are addressed relative to that captured base.

The search covers exactly 205 candidate positions, numbered 0 through 204 inclusive. Each record occupies 20 bytes. Only these fields are directly accessed:

| Byte offset within record | Width | Established use |
|---|---:|---|
| 8 | 16 bits, unsigned | Compared against the third input. |
| 10 | 16 bits | Argument to F-3159305e8693 and, on success, the returned field. |
| 16 | 16 bits | Argument to F-a9106d0ae91a. |

Offsets refer to byte positions, not field indices. No meaning is established for the other bytes.

The last candidate starts 4,080 bytes after the captured base. The highest directly accessed field occupies bytes 4,096 and 4,097 relative to that base.

## Behavior

### Search order and stopping rule

The function captures the global table base and begins with candidate 0. It examines candidates in increasing index order.

For each candidate, it evaluates the three conditions below with short-circuit behavior. Failure of any condition advances to the next candidate without evaluating the remaining conditions for the failed candidate.

The first candidate that passes all three conditions ends the search immediately. Later records are not examined.

If candidate 204 fails, the function returns zero. Candidate 205 is never examined. A success at candidate 204 returns that candidate’s result field normally.

### First condition: stored key

The function reads the unsigned 16-bit field at offset 8 and compares its zero-extended value with the third input.

If the values differ:

- Neither dependency is called for that candidate.
- The fields at offsets 16 and 10 are not directly read for that candidate.
- The search advances.

Because the third input is unsigned 32-bit, a value above 65,535 fails this condition for every candidate. There is no wraparound or low-16-bit matching.

### Second condition: first dependency result

If the first condition succeeds, the function reads the 16-bit field at offset 16 and supplies it to F-a9106d0ae91a.

The dependency’s returned 32-bit integer is compared with the first input. If they differ, the search advances without calling F-3159305e8693 for that candidate.

The comparison requires equality of the complete returned integer and the first input. It is not a truth-value comparison.

The field at offset 10 is read only after F-a9106d0ae91a returns a matching result. Consequently, any changes that dependency makes to the result field can affect the next condition.

### Third condition: exact Boolean-valued result

If the first two conditions succeed, the function reads the 16-bit field at offset 10 and passes that value to F-3159305e8693.

Its result is observed as an unsigned 32-bit value and compared against:

- Zero, when the second input is zero.
- One, when the second input is nonzero.

This is exact equality. A dependency result of two, for example, fails for both possible selector states. The function does not interpret an arbitrary nonzero dependency result as true.

If the comparison fails, the search advances to the next record.

### Successful return and repeated read

After F-3159305e8693 returns the required value, the function reads the selected record’s field at offset 10 again and returns that newly read 16-bit value.

It does not return a saved copy of the argument previously passed to F-3159305e8693.

This distinction is observable if the dependency changes the selected record. A field value used as the dependency argument may differ from the field value ultimately returned.

No earlier condition is rechecked after the dependency calls. In particular:

- The offset-8 field is not rechecked after either dependency runs.
- The offset-16 field is not reread for another F-a9106d0ae91a call.
- The final offset-10 value is not submitted to F-3159305e8693 again.

Thus, success records the outcomes of sequential observations, not proof that all predicates hold simultaneously for a final immutable record state.

### Captured base and live contents

The table base is captured once. Replacing the global base during a dependency call does not redirect the remaining search or the final return read.

The table contents, however, are not copied or snapshotted. Each field read observes memory at the point it occurs, subject to the execution environment’s memory semantics.

Consequences include:

- A dependency can affect later reads within the current record.
- A dependency can affect records not yet examined.
- Already rejected records are not revisited.
- If the captured table is released or invalidated during a dependency call, subsequent direct reads may no longer be valid.

No guarantee that either dependency preserves globals, table storage, or record contents is established.

## Side effects

The function itself visibly performs table reads and dependency calls. It contains no direct table writes, allocation, release, or ownership transfer.

This does not make the complete operation side-effect-free. Either dependency may have effects not described by the supplied evidence.

The direct operation order for a candidate that reaches success is:

1. Read the offset-8 field.
2. Read the offset-16 field.
3. Call F-a9106d0ae91a.
4. Read the offset-10 field.
5. Call F-3159305e8693.
6. Read the offset-10 field again.
7. Return that last value.

A failure at an earlier condition omits the later operations for that candidate.

Across the complete search:

- Each dependency is called at most once per candidate.
- F-a9106d0ae91a is called at most 205 times.
- F-3159305e8693 is called at most 205 times.
- Every F-3159305e8693 call is preceded, for the same candidate, by an F-a9106d0ae91a call that returned the requested first-input value.
- No dependency calls occur after the first successful candidate.

The final scalar result is not an established owning handle, borrowed pointer, or resource-transfer token. Such an interpretation requires an external contract.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not results of executed tests. Unless a case says otherwise, assume readable storage, normally returning dependencies, and no mutation during the call.

### First eligible candidate wins

Suppose candidates 4 and 9 both have:

- An offset-8 value equal to the third input.
- An F-a9106d0ae91a result equal to the first input.
- An F-3159305e8693 result equal to the normalized second input.

If candidates 0 through 3 fail, the function returns candidate 4’s offset-10 field. Candidate 9 is not examined.

### Key mismatch suppresses calls

Suppose the third input is 12 and a candidate’s offset-8 field is 13.

That candidate causes neither dependency to be called, regardless of its other fields.

### Oversized third input does not truncate

Suppose the third input is 65,536 and every candidate’s offset-8 field is zero.

All 205 candidates fail the first condition. The function returns zero without calling either dependency. It must not treat 65,536 as a request for key zero.

### First dependency mismatch suppresses the second

Suppose a candidate’s offset-8 field matches, the first input is −3, and F-a9106d0ae91a returns 3.

That candidate fails. F-3159305e8693 is not called for it.

### Nonzero selectors are equivalent

Suppose a candidate reaches the third condition and F-3159305e8693 returns one.

The candidate passes that condition when the second input is one, −1, or any other nonzero 32-bit integer. It fails that condition when the second input is zero.

### A non-Boolean dependency result is rejected

Suppose F-3159305e8693 returns two.

The candidate fails regardless of whether the second input is zero or nonzero.

### Successful return observes dependency mutation

Suppose a candidate reaches the third condition with an offset-10 value of 7. F-3159305e8693 receives 7, changes that same field to 11, and returns the required selector value.

The function returns 11, not 7.

### A changed global base does not redirect the search

Suppose F-a9106d0ae91a replaces the global table base but leaves the originally captured table valid.

The current candidate’s subsequent offset-10 read, and any later candidate accesses, still use the original base.

### Zero remains ambiguous

Suppose a qualifying candidate’s final offset-10 read yields zero.

The returned value is zero, just as it is when all 205 candidates fail. The return value alone does not distinguish these outcomes.

### Last candidate remains eligible

Suppose candidates 0 through 203 fail and candidate 204 passes.

The function returns candidate 204’s final offset-10 value. If candidate 204 instead fails, the function returns zero without accessing candidate 205.
