# F-9de7e03cc883

## Purpose

F-9de7e03cc883 scans callback-supplied input, constructs bounded decimal representations, and delegates conversion. Ordinary completion may store either two 32-bit result words or one 32-bit scratch word after a narrowing dependency has been called. Destination storage can be suppressed.

The function also offers selected prefixes to two delegated parsers. A delegated result other than `-3` ends the invocation immediately.

Established behavior includes field-width accounting, lookahead, selective progress reporting, representation-capacity checks, decimal-adjustment tracking, and indirect destination writes. Floating-point conversion, special-value parsing, and hexadecimal parsing are inferred intent. Their complete semantics are not established here.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

### Arguments

The function receives four arguments:

1. An opaque 32-bit value, saved but not otherwise used on the visible path.
2. An opaque 32-bit input context, passed to input callbacks and delegated parsers.
3. A pointer to a writable 32-bit progress integer.
4. A pointer to a mutable control record.

### Control record

| Byte offset | Access width | Established role |
|---|---:|---|
| 0 | 32 bits | Mutable cursor into a sequence of 32-bit destination addresses |
| 4 | 32 bits | Flags, copied at entry |
| 8 | 32 bits | Signed field width, copied at entry |
| 12–20 | — | No direct access established |
| 24 | 32 bits | Fetch callback address |
| 28 | 32 bits | Retraction callback address |
| 32 | 32 bits | Leading-input predicate callback address |

Each callback address is read from the live record and masked with `0xfffffffc` before invocation. Its low two bits do not contribute to the target.

Fetch receives the input context and supplies a 32-bit value. Recognized values include ASCII characters and the sentinel `0xffffffff`.

Retraction receives the input context; its return value is ignored.

The leading-input predicate receives no explicit argument. Its relationship to the most recently fetched input is unresolved.

### Returns

| Condition | Return |
|---|---|
| Initial skipping ends on `0xffffffff` | Signed 32-bit `-1` |
| Ordinary finalization finds no digit accepted in the currently required phase | Signed 32-bit `-2` |
| A delegated parser returns anything except `-3` | That result, unchanged |
| Ordinary completion reaches its successful return | Accumulated signed 32-bit count |

A delegated `-3` requests local continuation; it is not returned as an ordinary local scanning failure.

Success here means that the scanner’s current digit requirement was satisfied and execution reached its successful return. No conversion status is locally checked.

### Preconditions and arithmetic

All caller-provided record, progress, destination-slot, and destination-storage addresses must be valid for the accesses actually performed. Callback targets, separator-lookup objects, and dependency-accessed memory must likewise be valid.

Unsuppressed ordinary storage requires a readable 32-bit destination-address slot and writable destination space for one or two consecutive 32-bit words. Either result mode advances the cursor by four bytes.

No validation of caller-provided record, progress, destination-slot, or destination-storage bounds is visible. This is distinct from the explicit local representation-capacity checks: significand retention is limited to 18 digit bytes, and exponent retention to eight digit positions.

Counts, field widths, leading-zero counts, and decimal adjustments use 32-bit quantities. Signed additions and subtractions have no visible overflow checks. Main significand digit classification uses unsigned 32-bit subtraction. Exponent classification subtracts ASCII `0` from a signed input value before interpreting the result as unsigned. Behavior requiring signed overflow or invalid address arithmetic is **documented_only**; this contract does not assign wraparound semantics to it.

## Behavior

### Entry and leading-input processing

Flags and field width are copied before the first dependency call. Decimal adjustment and leading-zero count start at zero.

F-187ab9ba4eb6 supplies a structure used for separator lookup. Through its pointer field at byte offset 44, the function obtains a 32-bit displacement from a pointed-to object and reads one unsigned byte at that object’s base plus the displacement. That byte becomes the captured separator.

The count starts at `-1`. Each initial-loop iteration:

- Increments the count.
- Calls fetch.
- Calls the leading-input predicate.

A nonzero predicate result repeats the loop. After \(k\) initial fetches, the count is \(k-1\): skipped items contribute to the count, but the current item does not yet contribute. This loop neither reduces field width nor directly writes progress.

When the predicate first returns zero, a current value of `0xffffffff` causes immediate return of `-1`, without local retraction, conversion, or destination storage.

Whitespace skipping is inferred intent only. Predicate classification is unknown, and a predicate that remains nonzero prevents termination.

### Local flags and sign

After the initial sentinel check, copied flag bits `0x400`, `0x200`, and `0x80` are cleared. Other copied bits remain.

| Bit | Local role |
|---|---|
| `0x400` | Negative significand |
| `0x200` | A digit was accepted in the currently required phase |
| `0x80` | Separator encountered |
| `0x100` | Negative exponent after exponent entry clears its previous value |

With positive remaining width, a current `+` or `-` is consumed. Minus sets `0x400`. The count increases, fetch obtains the next item, and width decreases by one. Nonpositive width prevents sign consumption.

The significand representation begins with ASCII `+` or `-`. Retained digit bytes are numeric values zero through nine, not ASCII digit codes.

### Prefix delegation and leading zeroes

With positive remaining width, current `i`, `I`, `n`, or `N` triggers F-d86674b5a239. Before calling it, the function assigns that current 32-bit input value to the scratch word later supplied to F-c7bf4be19b88.

The delegated parser receives, in order:

- The 32-bit value `0xfffffffd`, representing `-3`.
- Input context.
- Progress pointer.
- Control-record pointer.
- Current count.
- Local flags.
- Remaining width.

A return other than `-3` is returned immediately. On `-3`, local scanning continues without visibly refreshing the current input, count, flags, or width. There is no local restoration of input modified by the parser.

Leading ASCII zeroes are then consumed while width is positive. For each zero, the function increments the count, fetches the next item, reduces width, sets the digit-accepted flag, writes the count to progress, and increments the separate leading-zero count. These zeroes do not occupy significand digit storage.

With positive remaining width, current `x` or `X` invokes F-9da4d4bd3637 only when exactly one leading zero was consumed. Its arguments and return handling match the preceding delegation. Thus `0x` can qualify, but `00x` cannot through this rule. A zero that exhausts width prevents the fetched `x` from qualifying.

### Initial separator and fractional-zero prepass

After leading-zero processing, the current value is compared with the separator without a positive-width check.

On a match, the separator-seen flag is set. The function reduces width, increments the count, and fetches another item. If the fetched item is ASCII zero, it reduces the decimal adjustment, sets the digit-accepted flag, and writes one more than the current count to progress. It then repeats the width reduction, count increment, and fetch.

This prepass stops only when a fetched item is not ASCII zero. It has no width-based exit and may consume the separator and subsequent zeroes beyond the nominal field width.

Each accepted fractional zero is followed by another fetch. At prepass exit, the count includes the separator and zeroes, but not the terminating lookahead. Fractional zeroes affect the decimal adjustment rather than occupying retained digit positions.

### Main significand scan

The main loop first checks width. Width below one proceeds directly to ordinary finalization without classifying the current value.

With positive width, a separator is accepted if the separator-seen flag is clear. This comparison precedes digit classification. Otherwise, digits are recognized by unsigned 32-bit subtraction of ASCII `0`, accepting results zero through nine.

The function explicitly checks the retained significand position against its 18-digit limit:

- While capacity remains, a digit is appended.
- A retained digit after the separator decreases decimal adjustment.
- Once capacity is full, an additional digit before the separator increases adjustment.
- Additional digits after the separator are consumed without changing adjustment.

Accepted digits set the digit-accepted flag. A separator alone does not.

After accepting a digit or separator, width decreases. If a digit has already been accepted, the next count value is written to progress. The count then increases, fetch obtains the next item, and local flags are updated.

A separator following accepted digits therefore advances reported progress even though it is not a digit.

### Exponent processing

An `e` or `E` starts exponent handling only with positive width and an accepted significand digit. Exponent entry clears both the digit-accepted and negative-exponent flags. At least one exponent digit is now required.

Consuming the exponent marker fetches another item even when the marker exhausts width. A following sign is consumed only if width remains after the marker. Minus sets the negative-exponent flag; consuming either sign causes another fetch.

The exponent representation starts with ASCII `+` or `-`. Its write position is explicitly checked against an eight-digit retention limit. Leading zeroes are written at the first digit position without advancing that position. From the first nonzero digit onward, digits advance the position until capacity is reached. If all exponent digits are zero, final termination overwrites the unadvanced first digit position.

Exponent digits require positive remaining width. Each accepted digit first reduces width.

After retained capacity is exhausted, every additional exponent digit causes fresh, ordered global reads:

1. A first 32-bit global is read into decimal adjustment.
2. For a negative exponent, a second 32-bit global is read and replaces that adjustment.

The first read still occurs for a negative exponent. These are repeated reads, not an established cached constant.

After retention or overflow-adjustment handling, the function increments the count, fetches the next item, writes the count to progress, and sets the digit-accepted flag. A fetch callback may therefore change globals before a later excess digit reads them.

Exponent termination goes directly to ordinary finalization. Significand scanning does not resume.

### Ordinary conversion, scratch state, and storage

Ordinary finalization first calls retraction once, including on width exhaustion or missing digits. The current lookahead is not passed to it.

Both representations are then terminated with byte `0xff`. Without exponent entry, the exponent representation consists only of that terminator.

Two local 32-bit conversion-result words are explicitly initialized to zero. F-e4f4e6c989bc receives their address, the exponent representation, the signed significand representation, and decimal adjustment.

Only after conversion returns does the function check the current digit-accepted flag. If clear, it returns `-2` without its own cursor advancement or destination write. Conversion therefore also occurs on this failure path.

If either flag `0x04` or `0x20` is set, the function selects the two-word result. Otherwise, it calls F-c7bf4be19b88 with the address of a separate 32-bit scratch word and the two-word result.

Unlike the two-word buffer, this scratch word is **not zero-initialized**:

- An eligible `i`/`I`/`n`/`N` delegation attempt directly assigns the current input value to it before calling F-d86674b5a239.
- If that parser returns `-3` and execution later reaches narrowing, this assignment remains the last visible initialization before F-c7bf4be19b88.
- On paths without that assignment, no initialization of the scratch word is established before narrowing.

The narrowing dependency’s read/write contract is unknown. It must not be assumed to ignore incoming scratch contents, initialize every bit, or completely overwrite the word. The function subsequently stores the scratch word’s contents without a separate completeness check.

Flag `0x01` suppresses the function’s own destination write and cursor advancement. It does not suppress conversion or, in one-word mode, the narrowing call.

Unsuppressed storage occurs in this order:

1. Read the live cursor at record offset zero.
2. Write cursor plus four bytes back to that record field.
3. Read the destination address from the old cursor location.
4. Write the selected result to that destination.

Two-word storage writes the first word before the second word at destination offset four. One-word storage writes the post-call scratch contents. The function then returns the accumulated count.

## Side effects

Direct effects include callbacks, selected progress writes, excess-exponent global reads, conversion calls, and conditional cursor and result writes.

Progress is not initialized. Without a qualifying direct write, its prior value may remain. An incomplete exponent can leave the last direct progress write at the accepted-significand position.

These are statements about this function’s own operations, not unconditional final memory values. Dependencies may modify reachable memory unless separate contracts exclude that behavior.

Flags and width remain local snapshots. Callback targets are read afresh. The destination cursor is read after conversion dependencies return. Live-record changes can therefore affect later callback selection and destination storage.

No direct allocation or release is visible. Dependencies receive addresses of local representations, conversion results, and scratch storage whose lifetimes end with this invocation. Retention, allocation, release, shared-state mutation, and ownership behavior are unresolved.

The retraction call does not establish that exactly one input item is restored, that sentinel retraction succeeds, or that failure is reported.

Overlapping progress, record, destination-slot, and destination storage can make access ordering observable.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless overridden, assume ASCII input, separator `.`, an immediately false leading predicate, valid nonoverlapping storage, non-overflowing arithmetic, and normally returning dependencies. Assume callbacks and dependencies do not mutate unrelated state, fetch supplies the stated sequence, and conversion dependencies perform whatever writes their own contracts require. Numeric result encodings and complete narrowing-output initialization remain unspecified.

1. **Initial sentinel.** A first fetch of `0xffffffff` returns `-1`, without ordinary retraction or conversion.

2. **Ordinary digits.** With width at least three, `12Q` accepts two digits, fetches `Q`, retracts once, and reaches return `2`. The last direct progress write is `2`. In one-word mode, no scratch initialization before narrowing is established.

3. **Separator without digits.** `.Q`, with sufficient width, consumes the separator and fetches `Q`. Retraction and conversion occur before return `-2`. There is no direct progress write.

4. **Missing exponent digits.** For `1eQ`, width at least two permits exponent entry and produces ordinary return `-2`; the last direct progress write is `1`. Width one instead accepts `1`, fetches `e`, and finalizes before exponent recognition, reaching return `1`.

5. **Signed exponent.** With sufficient width, `1e-2Q` constructs positive-significand and negative-exponent representations, reaching return and last direct progress write `4`.

6. **Width overrun in fractional prepass.** With width one, `.00Q` fetches through both zeroes to `Q`. Count and last direct progress write reach `3`; decimal adjustment becomes `-2`.

7. **Delegation eligibility.** With sufficient width, `0x` invokes F-9da4d4bd3637, while `00x` does not. A non-`-3` delegated return bypasses local ordinary finalization.

8. **Repeated overflow-adjustment reads.** `1e1234567890Q` has two excess exponent digits. Each reads the first adjustment global before its next fetch. With a negative exponent, each reads the first global and then the second. Changes made by intervening fetch calls affect later reads.

9. **Assigned scratch before narrowing.** Override the separator to `i`. With sufficient width and input `i2Q`, suppose F-d86674b5a239 returns `-3`. The initial `i` is then accepted as the separator, and `2` satisfies the digit requirement. In one-word mode, narrowing is reached with `0x00000069` as the scratch word’s last visible initialization. This does not establish what narrowing writes or what result is ultimately stored.

10. **Suppressed storage.** With flag `0x01`, a valid ordinary field reaches its count return without this function’s cursor advancement or destination write. Conversion still occurs, and one-word mode still calls narrowing with the path-dependent scratch state described above.
