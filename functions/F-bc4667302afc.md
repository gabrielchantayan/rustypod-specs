# F-bc4667302afc

## Purpose

F-bc4667302afc requests a position and a bounded transfer of 12-byte records, transforms the first two four-byte fields of each selected record, and publishes the requested starting index.

The visible operation has three stages:

1. Submit a two-word position derived from stored base-address fields and the starting index.
2. Request data into a descriptor-provided buffer and require an exact transfer result.
3. Transform two fields per record, then store the starting index in the current descriptor.

The four-byte return value is **0** on the completed path and **3** on either explicit failure path. Dependency failures, faults, and nonreturning calls are not visibly converted into these return values.

**Inferred intent:** a windowed record loader limited to 32,768 records per invocation. The meanings of the records, position, transformation, and dependency mode arguments are not established.

### Context layout

Offsets are relative to the context address.

| Offset | Width | Visible use |
|---|---:|---|
| +0x08 | 4 bytes | Operation-object reference used to resolve indirect calls and supply their receiver argument. |
| +0x28 | 4 bytes | Descriptor reference. |

| +0x10C | 4 bytes | Base high word, sampled during positioning-call argument preparation. |

The operation object contains a dispatch-table reference at offset +0. Callable entries are accessed at dispatch offsets +0x14 and +0x10.

These fields describe required accesses, not complete object layouts. The object used to resolve a callable and the object subsequently passed as its receiver are separately read; their equality is not enforced.

### Descriptor layout

| Offset | Width | Visible use |
|---|---:|---|
| +0x00 | 4 bytes, signed interpretation | Initial limit, L, used to select a local record count. |
| +0x04 | 4 bytes | Starting-index publication on success. |
| +0x08 | 4 bytes | Buffer address used for transfer and field processing. |

L is sampled before either indirect call. Changes to that field afterward do not recalculate the selected count.

Descriptor and buffer references are read again at later stages. There is no single retained descriptor-and-buffer snapshot governing the whole operation.

### Record layout

Each record occupies 12 bytes.

| Record-relative offset | Width | Direct treatment |
|---|---:|---|
| +0 | 4 bytes | Replaced with the first result from F-76bf07f4ac67. |
| +4 | 4 bytes | Replaced with the second result from F-76bf07f4ac67. |
| +8 | 4 bytes | No direct transformation or store by this function. |

The requested transfer covers all 12 bytes per selected record, including the third field.

### Return values

- **0:** the positioning dependency returned zero, the transfer dependency returned exactly the requested byte count, all required helper calls returned, and final publication completed.
- **3:** positioning returned nonzero, or transfer returned a value unequal to the requested byte count.

These gates establish how this function interprets dependency results, not the dependencies’ complete error conventions.

## Behavior

### Count selection

The function first samples the signed descriptor limit L. It selects a signed 32-bit local count C using comparisons against S + 32,767:

- If L is at most S + 32,767, C is L − S.
- If L is greater than S + 32,767, C is 32,768.

When the signed addition and subtraction are representable, this selects the smaller of L − S and 32,768.

Consequences:

- L = S selects zero records.
- L = S + 32,767 selects 32,767 records.
- L = S + 32,768 selects 32,768 records.
- Larger representable positive differences also select 32,768 records.
- L < S selects a negative count. There is no lower-bound clamp or rejection.

The threshold addition and count subtraction are shown as signed 32-bit arithmetic. Inputs causing signed overflow are **documented_only**; a portable wrapping interpretation is not established.

### Position calculation and base sampling

Position preparation does **not** take an atomic or immutable two-word base snapshot.

Define:

- **A:** the first four-byte low-word sample from context +0x108.
- **P:** the four-byte product representation used for S × 12.
- **U:** the low 32 bits of A + P.
- **B:** the second four-byte low-word sample from context +0x108.
- **H:** the four-byte high-word sample from context +0x10C.

The established stage order is:

1. Read A and calculate the retained intermediate U.
2. Resolve the positioning callable through dispatch offset +0x14.
3. Prepare the positioning-call arguments, including the separate reads yielding B and H.

The relative order of B, H, and other reads within the call-argument expression is not established. No total ordering among those reads is imposed here.

The submitted low address word is:

**low = (U + 16) modulo 2³²**

The submitted high address word is:

**high = (H + carry(B, P) + extra(U)) modulo 2³²**

Here:

- **carry(B, P)** is 1 exactly when unsigned addition of the four-byte operands B and P exceeds 0xFFFFFFFF; otherwise it is 0.
- **extra(U)** is 1 exactly when U > 0xFFFFFFEF; otherwise it is 0.

Thus the low argument and the first carry can depend on **different samples** of context +0x108. The additional-16 carry depends on the retained U, not on a recalculation using B. H is sampled during argument preparation, not retained alongside A.

For stable base-address fields, nonnegative S, and representable signed multiplication S × 12, the result corresponds to adding 12 × S + 16 to the stored two-word base, modulo 2⁶⁴. That simplification is not unconditional: changing samples can produce a pair that does not represent addition to one coherent base snapshot.

Only the four-byte product participates in the first low-word addition and carry calculation. No signed high-word contribution for S × 12 is visibly added. Consequently, replacing this computation with unrestricted signed or unsigned 64-bit multiplication is not justified. Signed-overflow cases in the multiplication remain **documented_only**.

### Positioning call

The callable at dispatch offset +0x14 is labeled **F-indirect-001**. It receives five visible arguments:

1. The operation-object address.
2. The resolved callable address itself.
3. The calculated low address word.
4. The calculated high address word.
5. The literal value 0.

The callable-address argument is part of the visible call shape; its purpose is unknown. The operation-object reference passed as the first argument is read separately from the reference used to resolve the callable.

If F-indirect-001 returns nonzero, this function returns 3. It does not call the transfer dependency, perform its own transformation stores, or publish S on that path.

No rollback of dependency side effects is visible.

### Transfer call

After a zero positioning result, the function resolves the callable at dispatch offset +0x10 and invokes **F-indirect-002** with:

1. An operation-object address.
2. A buffer address obtained through the current descriptor’s +0x08 field.
3. The signed 32-bit byte-count expression C × 12.
4. The literal value 2.

The relevant operation-object, descriptor, and buffer references are obtained after positioning returns. Positioning-side changes can therefore affect the transfer. Reads within transfer-call preparation are not established as one atomic snapshot.

The transfer return value must equal C × 12 exactly. Any unequal value causes return 3, including shorter and larger results. There is no retry, partial-record processing, or local rollback.

For C from 0 through 32,768, the requested count ranges from 0 through 393,216 bytes and fits in signed 32 bits.

A negative C can produce a negative byte-count argument. Its interpretation by F-indirect-002 is unknown. If C × 12 overflows signed 32-bit arithmetic, the supplied representation does not establish a portable result.

### Field transformations

After an exact transfer result, records are processed in increasing index order, beginning at index zero, while the signed index is less than C.

For each record, the observable sequence is:

1. Obtain the current descriptor and buffer reference; pass the address of the first field to F-76bf07f4ac67.
2. After the helper returns, obtain the descriptor and buffer reference again; store the returned four-byte value at the first-field position for that record.
3. Obtain the current descriptor and buffer reference; pass the address of the second field to F-76bf07f4ac67.
4. After that helper returns, obtain the descriptor and buffer reference again; store the returned four-byte value at the second-field position.

The first store completes before the second helper call. Both stores for one record precede processing of the next record.

Each helper receives an address, not a value already loaded by this function. Its reads, writes, and other effects are not visible here.

A helper can receive an address in one buffer and have its result stored into another if the relevant references change before the subsequent store. There is no retained destination address across the helper call.

The third field is not directly transformed. This does not establish that it remains unchanged by the transfer, helpers, aliasing, or other participants.

### Publication

After the loop, the function reads the current descriptor reference and writes S as four bytes at descriptor +0x04. It then returns 0.

Publication occurs even when C is zero. It also occurs for a negative C if positioning succeeds and transfer returns the matching representable negative byte count: the signed loop condition then permits no iterations.

No count, transferred-byte total, or separate validity flag is directly published.

## Side effects

### Direct effects

The function directly performs:

- Two four-byte field stores per processed record.
- One four-byte starting-index store after successful processing.

It does not visibly allocate or release memory.

### Dependency and changing-state effects

No dependency is assumed to preserve globals, context fields, descriptor references, buffer references, operation objects, or storage lifetimes.

Accordingly:

- The transfer destination need not be the buffer subsequently transformed.
- A helper’s input address need not equal its result-store address.
- Publication can target a descriptor different from the one supplying L.
- Separately read operation-object references need not identify the same object.

The two base-low reads and later high-word read also do not establish a coherent base snapshot. These are consequences of the visible sampling pattern, not claims that concurrent mutation is supported or that any dependency actually performs such mutation.

### Failure and partial completion

A nonzero positioning result prevents the transfer.

A mismatched transfer result prevents this function’s transformation stores and publication, but does not undo transferred data or dependency effects.

If a helper faults or does not return, earlier writes may already have occurred. There is no visible handler converting that event into return 3 or restoring prior state.

Ownership is unspecified. Passing context, descriptor, buffer, or field addresses does not establish ownership transfer. Absence of direct allocation or release does not establish that dependencies preserve storage.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, assume accessible memory, stable references and base fields, representable arithmetic, and normally returning dependencies.

### Ordinary successful load

For S = 10 and L = 15:

- C is 5.
- The requested position is the stable base plus 136.
- The transfer request is 60 bytes.
- Positioning result 0 and transfer result 60 permit ten helper calls.
- Field addresses occur at buffer-relative offsets 0, 4, 12, 16, 24, 28, 36, 40, 48, and 52.
- Publication writes 10 to descriptor +0x04, followed by return 0.

### Window boundaries

For L = S + 32,767, the request is 393,204 bytes.

For L = S + 32,768, or a larger representable positive difference, the request is 393,216 bytes.

### Empty range

For L = S, positioning still occurs. After a zero positioning result, transfer is called with byte count zero. Transfer result zero permits publication and return 0 without helper calls.

### Explicit failures

A positioning result of 7 produces return 3 without transfer.

For C = 2, the requested count is 24. Transfer result 12 or 25 produces return 3 without field transformations or publication. The complete first record in the 12-byte case is not processed locally.

### Additional-16 carry

For S = 0 and stable base low word 0xFFFFFFF0, the submitted low word is zero and the high word is the sampled high word plus one, modulo 2³².

### Distinct low-word samples

Conditionally suppose the environment supplies these samples without otherwise invalidating execution:

- S = 2, so P = 24.
- A = 0xFFFFFFF0.
- B = 0.
- H is unchanged.

Then U is 8, the submitted low word is 24, and both high-word carry contributions are zero. The submitted high word is H.

If B instead remained equal to A, the first carry would be one and the high argument would be H + 1 modulo 2³². This distinguishes the observed two-sample calculation from unconditional addition to the initially sampled base.

### Starting index beyond the limit

For L = 9 and S = 10, C is −1 and the byte-count expression is −12. If positioning returns zero and transfer returns −12, no helper calls occur; S is published and the function returns 0.

This is an observable conditional edge case, not recommended usage.

### Helper changes the buffer

If the first helper changes the descriptor’s buffer reference before returning, its result is stored using the newly read buffer reference, not necessarily at the address passed to the helper.
