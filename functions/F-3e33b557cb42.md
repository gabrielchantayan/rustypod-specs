# F-3e33b557cb42

## Purpose

F-3e33b557cb42 traverses address-based records, selects visits through an external predicate, and requests a 48-byte object for each selected visit. It directly initializes portions of that object, publishes its address through a context-associated dependency, invokes a population dependency, and conditionally invokes another dependency controlled by a context byte.

The result indicates whether the selected-visit count, reduced modulo 65,536, is nonzero. It is not an unrestricted “at least one record selected” result: exactly 65,536 selected visits produce false on normal completion.

The supplied body establishes access widths, call order, direct writes, and branch conditions. It does not establish the records’ meaning, descriptor contents, dependency ownership rules, or a broader object model. “Allocation,” “construction,” “cleanup,” “insertion,” “population,” and “activation” below are descriptive roles, not additional dependency guarantees.

## Interface

### Inputs and storage layout

The function receives two address-bearing arguments represented as 32-bit signed integers:

- **Context address:** used to locate insertion-associated storage and an activation flag, and passed to population and activation.
- **Sequence-holder address:** used to obtain the initial cursor and the repeatedly consulted endpoint.

| Storage | Byte offset | Access width | Visible use |
|---|---:|---:|---|
| Sequence holder | `0x14` | 32 bits | Initial cursor, read once |
| Sequence holder | `0x18` | 32 bits | Endpoint, reread at each loop condition |
| Context | `0x6c` | 8 bits | Activation flag |
| Context | `0x84` | Address calculation only | Address passed to insertion |

This function does not directly dereference the context storage at `0x84`. It passes that address to a dependency.

The normal cursor increment is 40 bytes, hexadecimal `0x28`. The function does not directly read record fields; record interpretation is delegated.

Three global descriptor values are supplied to dependencies: one for selection and one for each of two lookups. Each is obtained at its respective call site rather than captured once at function entry. Their definitions, contents, and storage widths are not supplied.

### Local storage exposed to dependencies

The body uses:

- One mutable 32-bit cursor slot.
- One shared 32-bit lookup-output slot.
- Two four-byte temporary-storage regions, reused for both lookup sequences and across visits.
- One 16-byte initialization-result region, read as four 32-bit words.

The lookup-output slot is not visibly initialized before its first use. Both lookup calls receive its address. Population receives the cursor slot’s address.

These addresses escape to dependencies. No supplied contract prevents dependencies from retaining aliases and modifying the corresponding storage during later calls while that storage remains live. Consequently, later reads cannot generally be attributed to the most recent apparent producer without a preservation assumption.

### Result and arithmetic

The function returns a Boolean on normal completion.

A 32-bit unsigned selected-visit counter starts at zero. Every predicate result equal to exactly `1` causes an increment followed by a mask of `0xfffeffff`, which clears bit 16. Starting from zero, the reachable counter values remain within `0–65,535`; the update therefore implements counting modulo 65,536.

The return is true exactly when that counter is nonzero. Counting occurs before lookup, allocation, insertion, population, or activation. No dependency success result is required for the increment itself.

Address calculations are represented differently: cursor advancement, context and sequence-holder offsets, and the lookup-output adjustment use signed-integer address-bearing expressions. Behavior at signed overflow or outside valid storage is not established here.

### Preconditions for defined, normal execution

Every executed access must have valid storage and suitable alignment for its width. In particular:

- The sequence-holder fields must be readable.
- Record addresses passed to dependencies must satisfy those dependencies’ requirements.
- The context flag must be readable when tested and writable when set.
- The allocation result must support the visible accesses within a 48-byte object.
- The insertion result must identify writable storage for a 32-bit object address.
- Lookup-output and initialization-result reads must obtain values suitable for their subsequent uses.
- Any aliases retained by dependencies must remain valid for their actual use.

The function performs no visible validation of these conditions. Normal termination also requires the cursor eventually to equal the endpoint at a loop-condition evaluation.

## Behavior

### Traversal and selection

The function initializes the counter and loads the cursor from sequence-holder offset `0x14`.

At each loop condition, it reads the endpoint at offset `0x18` and compares it with the current cursor. Equality ends traversal without visiting that address. Inequality enters the body. There is no ordering comparison, distance calculation, range check, or fixed iteration bound.

F-2fb175a232ca receives the cursor value used at its call and the selection descriptor:

- Exactly `1` selects the visit.
- Every other result skips the selected-path work.

On the selected path, the counter is updated before other work.

At the end of every normally completed visit, the function reads the cursor slot, adds 40, and stores the result back. This read occurs after all dependencies executed during that visit, including any activation. The next loop condition rereads the endpoint.

Population explicitly receives the cursor’s address. Once that address has escaped, subsequent dependencies may modify the slot through retained or obtained aliases. This matters both within that selected visit and in later visits. A predicate call, temporary-construction call, lookup, cleanup, or activation is not established to preserve an already-exposed cursor.

Thus, the predicate’s record, the first lookup’s record, the second lookup’s record, and the increment’s base need not remain identical.

### First lookup sequence

For a selected visit, after incrementing the counter:

1. F-9b9c1c7483f4 receives the first four-byte temporary region, the first lookup descriptor, and the other four-byte temporary region.
2. Its 32-bit return value becomes the lookup argument.
3. F-92c0da5f24b7 receives the cursor value read for that call, the constructed argument, and the shared 32-bit output slot’s address.
4. F-8a5aadac202f receives the first temporary region.

The first lookup’s return status is ignored. Its output slot is not checked.

The cursor supplied to this lookup is read after the construction call. If an alias to the cursor escaped during an earlier selected visit, construction or another intervening dependency may have changed it.

The shared output slot is not snapshotted after this lookup. Cleanup, allocation, and initialization dependencies execute before insertion obtains its argument. Because the slot’s address has escaped, those dependencies may modify it through aliases. The insertion argument is therefore based on the slot’s contents at the later read, not necessarily the value originally written by this lookup.

### Allocation and direct initialization

F-8157a180d901 receives the size `0x30`, or 48 bytes. Its returned address is used without a null check or other validation.

The direct initialization order is:

1. A 32-bit zero is written at object offset `0x2c`.
2. F-5bb1b38eb3e5 receives the 16-byte result region’s address and two zero arguments.
3. Four 32-bit words are read from that region and written, in order, to object offsets `0x14`, `0x18`, `0x1c`, and `0x20`.
4. Those four object words are read back and copied, in order, to offsets `0x04`, `0x08`, `0x0c`, and `0x10`.
5. A 32-bit zero is written at `0x24`.
6. A 32-bit zero is written at `0x28`.
7. A 16-bit zero is written at `0x00`.

| Object byte range | Directly written contents |
|---|---|
| `0x00–0x01` | 16-bit zero |
| `0x02–0x03` | No direct write |
| `0x04–0x13` | Copies read from `0x14–0x23` |
| `0x14–0x23` | Four 32-bit initialization-result words |
| `0x24–0x27` | 32-bit zero |
| `0x28–0x2b` | 32-bit zero |
| `0x2c–0x2f` | 32-bit zero, written before the initialization dependency |

This is partial initialization, not whole-object zeroing. The initialization-result region is itself not visibly initialized before its producer runs.

The table records direct writes, not unconditional final contents. For example, the write at `0x2c` precedes a dependency call; no supplied contract prevents that dependency from modifying the object through an alias. Later dependencies may likewise alter any reachable object contents.

### Insertion and population

After direct initialization, the function reads the shared 32-bit lookup-output slot. F-e5963bb0d688 receives:

- The address at context offset `0x84`.
- The slot’s **then-current value plus four**.

There is no intervening dependency call between this slot read and the insertion call. The addition is an address-bearing arithmetic operation; this function does not dereference the adjusted value.

Only if intervening dependencies preserve the slot does this argument equal the first lookup’s original output plus four. The function does not enforce that preservation.

The insertion dependency’s return value is treated as a writable address. The function writes the new object’s address there as a 32-bit value.

It then calls F-76df4e894df4 with the context address, the cursor slot’s address, and the object address. Its return value is unused.

Publication therefore precedes population. No visible rollback removes the published address if population fails to return normally.

### Second lookup and activation

After population returns:

1. F-9b9c1c7483f4 receives the reused temporary regions and the second lookup descriptor.
2. **After that construction call**, F-92c0da5f24b7 receives the cursor value read for this second lookup, the newly constructed argument, and the shared output slot’s address.
3. The second lookup’s 32-bit return value is retained.
4. F-8a5aadac202f receives the temporary.
5. The retained lookup result controls activation eligibility.

The second lookup does not necessarily use the cursor value left immediately after population. The intervening construction call may change it through an alias.

If the second lookup result is zero, the function skips the flag test and activation. If it is nonzero, the function reads the context byte at `0x6c`, after cleanup:

- A zero byte causes F-fe5d1bf4822f to receive the context and object addresses.
- After that call returns normally, the function writes the byte value `1` to the flag.
- A nonzero byte skips activation and the flag write.

The output slot’s contents do not control this decision.

The flag write follows activation, so it is not a pre-call reentrancy guard. A dependency may also change the flag between visits; the body does not guarantee at most one activation per invocation.

Finally, the loop increment reads the cursor after the second lookup, cleanup, flag decision, and any activation. It adds 40 to that then-current value, not necessarily to the second lookup’s record address.

## Side effects

Directly established effects include endpoint reads, dependency calls, one 48-byte allocation request per selected visit, partial object initialization, a 32-bit publication write, and conditional flag updates.

The function exposes local storage to dependencies and reuses it. Retained aliases can therefore affect later observable reads, particularly:

- The output-slot read immediately before insertion.
- Cursor reads for later lookups and loop advancement.
- Temporary or initialization-result contents subsequently consumed.

No explicit object deallocation appears. This does not establish permanent retention, ownership transfer, or absence of release inside dependencies.

No explicit recovery branch, exception handler, transaction, or rollback is visible. A dependency that does not return normally can leave earlier allocations, publication, object writes, and flag changes in place. An invalid allocation or insertion result is not converted into a defined false return.

The function supplies no synchronization. Concurrency safety and dependency preservation of globals, context, sequence-holder fields, objects, or exposed locals remain unspecified.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Address arithmetic and accesses must satisfy the stated preconditions.

1. **Initially empty traversal.** If initial cursor and endpoint compare equal, the result is false. No selection or selected-path dependency is called.

2. **Exact-one selection.** A visit whose predicate returns `2`, `0`, or `-1` does not allocate an object or increment the counter. If there are no other selected visits and traversal ends, the result is false.

3. **Selected visit without activation.** With one selected visit, normal dependency completion, and a zero second lookup status, initialization, publication, and population occur. The activation decision does not read the flag. Normal completion returns true.

4. **Clear activation flag.** If the second lookup returns nonzero and the flag read after cleanup yields zero, activation occurs. On its normal return, the function writes `1` to the flag, even if activation itself changed that byte.

5. **Existing nonzero flag.** If that flag read yields `7`, activation and the direct flag write are skipped. This function does not normalize the byte to `1`.

6. **Ignored first status.** If the first lookup returns zero but usable slot contents are available when insertion reads them, processing continues. The first status alone causes no skip.

7. **Output alias changes insertion.** Suppose the first lookup writes value X, but a later initialization dependency changes the shared slot to Y through a retained alias. Insertion receives Y plus four. It receives X plus four only if X remains the slot’s value at the insertion read.

8. **Cursor timing after population.** Suppose population leaves the cursor at B. The second lookup receives B only if the subsequent construction call preserves it. If construction changes it to C, that lookup receives C. If the cursor remains B through every remaining call, the increment produces B plus 40; if a later call changes it to D, the increment instead uses D plus 40.

9. **Changed endpoint.** If a dependency changes the endpoint, the next loop-condition evaluation reads the new value. Traversal does not use an entry-time endpoint snapshot.

10. **Counter wrap.** Exactly 65,536 selected visits followed by normal termination produce false. Exactly 65,537 produce true, regardless of whether activation occurred.

11. **Partial initialization.** If object bytes `0x02–0x03` initially contain a pattern and dependencies leave them unchanged, that pattern survives direct initialization. Requiring all 48 bytes to become zero would contradict the visible writes.
