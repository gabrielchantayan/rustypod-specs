# F-b3c86e5407f5

## Purpose

No application-level purpose is established. Repeated accesses at byte offset 20 suggest regular address construction, but do not establish an object type, array, protocol, or device interface.

This contract distinguishes:

## Behavior

### Description conventions

The following terms describe observable values and addresses, not implementation identifiers:

- **Saved initial word:** the unsigned word read near entry.
- **Entry store value:** the ambient 32-bit value written twice near entry.
- **Word slot of a result:** address equal to four times that result, plus 20.
- **Wide slot of a result:** address equal to sixteen times that result, plus 20.

Dependency occurrences have opaque IDs **F-U001**, **F-U002**, and so forth in execution order. An occurrence ID does not establish a distinct function identity.

Two sequence descriptions specify call ordering:

- A **five-call sequence** consists of a call with the stated arguments, three calls with no explicit arguments shown, and a final call whose primary result is retained.
- A **nine-call sequence** consists of a call with the stated arguments; a result-producing call; a call receiving that result; another result-producing call; a call receiving that second result and any stated additional argument; three calls with no explicit arguments shown; and a final result-producing call.

“No explicit arguments shown” is not a claim that the actual calling convention supplies no arguments or ambient inputs.

A sequence’s retained result is its final primary result unless a secondary channel is expressly identified. Dependencies may modify memory; saved values described here are not fresh reads.

### Entry ordering

The entry prefix:

1. Writes the entry store value at four times the second argument, plus 20.
2. Reads the saved initial word from the ambient address plus 20.
3. Performs a nine-call sequence. **F-U001**, its first call, receives four times the second argument, the second argument, the original third argument, and the second argument again, in that order.
4. Repeats the initial word store.
5. Performs a five-call sequence beginning with four times the nine-call sequence’s retained result.

The initial read follows the first store. If their storage overlaps, the read may observe that write. The second store is separately observable and can overwrite an intervening dependency update.

The **fixed tail-selector address** is 1024 times the saved tail-selector base, plus one, subject to the stated signed-address arithmetic uncertainty.

- Call a dependency with twice the initial loop field.
- Call a dependency with no explicit arguments shown and retain its primary result as the initial carried value.

The fixed tail-selector address is retained throughout the represented loop. Neither subsequent carried values nor later four-times call arguments replace its base.

2. The function freshly reads the byte at the fixed tail-selector address and writes zero at that byte’s value plus 17.
3. A five-call sequence begins with four times the first sequence’s retained result.
4. The carried value becomes four times the second sequence’s retained result.
5. The unsigned loop field becomes the represented result of shifting that same retained result left by twenty-six.

## Side effects

## Acceptance examples

These are conditional static criteria, not executed tests.

### Entry aliasing and saved reads

If the initial store and ambient word read address the same word, both complete, and no external modification intervenes, the read observes the stored entry value.

If a dependency later changes that location, subsequent initial-word field extractions still use the saved read.

### Extracted fields

For a third argument of `0xffffffff`, the final four-argument call in the main word stages receives 2047 as its fourth argument. For `0x001fffff`, it receives zero.

For a saved initial word of `0xabcdef12`:

- Right shift by sixteen gives `0x0000abcd`.
- Right shift by twenty-four gives `0x000000ab`.
- Right shift by twenty-three gives `0x00000157`.
- The direct byte-store address is 29.

### Selector rereads and byte fields

A selector byte of 3 selects destination 20. If it becomes 9 before the next read, that read selects destination 26.

For an unsigned result of `0x12345678` used in the first pair of selector-based byte stores, the first stored byte is `0xe0`; the second is `0x23`. The second extraction uses the original result, not its four-times value.

### Fixed tail selector

If the direct-store result is 1, its saved tail-selector base is 4 and the tail-selector address is 4097.

If the later seven-call result is 3, the immediately following five-call sequence begins with 12. That does not change the tail-selector address to 12289: the tail preparation and every loop iteration still read address 4097, provided those accesses complete.

Different byte contents at address 4097 may nevertheless select different store destinations on successive reads.

### Loop target and field transitions

If execution completes two iterations, the opening call of the first uses **F-L001**; the opening call of the second uses **F-L002**, selected using the value established by the preceding iteration’s final sequence. Treating both opening calls as using the entry target would violate the represented relationship.

An initial loop field of 31 still supplies zero as the first iteration’s shifted second argument.

Conditionally on 32-bit truncating semantics for the signed left shift, a subsequent retained result of 1 yields loop field `0x04000000`, so the following iteration supplies `0x00040000`.
