# F-3410c924e389

## Purpose

F-3410c924e389 converts a requested state to a Boolean byte, publishes that byte to global-associated and object-associated storage, and then either invokes an indirect operation or sets an object-associated marker.

The established contract is a sequence of memory accesses and conditional dispatch. The application-level meanings of the object, requested state, condition bytes, and marker are not established. “Publication” describes the stores; it does not imply synchronization or visibility guarantees between threads.

On paths that complete normally, the routine returns a 32-bit status:

- **0** when the marker branch completes or the indirect operation returns zero.
- **7** when the indirect operation returns any nonzero value.

Both publication stores precede indirect dispatch. Returning 7 does not undo those writes or establish that the requested state was rejected before publication.

## Interface

### Inputs

The supplied representation exposes two 32-bit integer inputs.

**Object address**

- A zero value causes a call to F-bb50a072e902.
- A nonzero value is used directly as the effective object address.
- When resolution is required, the resolver’s returned value becomes the effective object address.
- The effective address is not checked for nullness, bounds, alignment, or lifetime before use.

The address-bearing input is represented as an integer. Its zero test does not depend on signedness. Whether a nonzero bit pattern denotes usable storage is a caller and platform precondition, not a validation performed here.

**Requested state**

- Zero produces the byte value **0**.
- Every nonzero 32-bit value produces the byte value **1**.

Normalization tests the full input, not just its low byte. Thus, a requested state of 0x00000100 produces 1. Negative nonzero values also produce 1.

### Output

The return value is 32 bits. The explicit normal returns are 0 and 7.

No normal return value is established if a memory access faults or a dependency fails to return normally. There is no explicit local recovery path for either event.

### Relevant storage

“Global-base holder” below means the global storage location from which the routine reads an address. “Global base” means the address obtained by that read; these are distinct locations.

| Storage or address relationship | Access | Established role |
|---|---|---|
| Global-base holder | 32-bit address-bearing read | Supplies the global base after optional object resolution |
| Global base + 0x01 | One-byte write | First requested-state publication |
| Effective object + 0x90 | One-byte read | First branch condition |
| Effective object + 0x94 | 32-bit address-bearing read | Root of the indirect-dispatch lookup |
| Effective object + 0x98 | Conditional one-byte read | Second branch condition |
| Effective object + 0xA1 | One-byte write | Second requested-state publication |
| Effective object + 0xA2 | Conditional one-byte write | Marker set by the non-dispatch branch |

On the indirect branch, the address read from object offset 0x94 identifies storage whose first 32-bit address-bearing value supplies a table base. The callable entry is read at byte offset 0x20 from that table base.

The supplied integer and pointer representation supports a 32-bit address model. Byte-access widths and byte offsets are explicit. Original declarations, complete structure layouts, alignment requirements, and the machine-level calling convention are not established.

### Preconditions for fault-free completion

Required access depends on the selected path:

- The global-base holder must be readable **after** optional object resolution.
- The resulting global base plus 0x01 must be writable.
- Effective object plus 0xA1 must be writable.
- Effective object plus 0x90 must be readable.
- Effective object plus 0x98 must be readable only if the first condition byte is nonzero.
- Effective object plus 0xA2 must be writable if the marker branch is selected.
- The complete dispatch lookup must be readable and identify a valid callable target if the indirect branch is selected.

Readability of the global-base holder is separate from writability of the destination it identifies. Satisfying one does not establish the other.

No explicit bounds, null-address, lifetime, alignment, or address-overflow checks enforce these preconditions.

## Behavior

### Object resolution precedes the global-base read

When the supplied object address is zero, the routine invokes F-bb50a072e902 without explicit arguments and uses its returned value as the effective object address. A nonzero supplied address bypasses this call.

The optional resolution finishes before the routine reads the global-base holder. Consequently:

- A resolver that does not return normally prevents the later global-base read and publication stores from being reached.
- If the resolver changes the global-base holder, the subsequent read obtains the value present after the resolver returns.
- A base cached before the resolver is not a conforming substitute for this post-resolution read unless its equivalence is independently established.

No preservation guarantee is available for F-bb50a072e902. In particular, the resolver must not be assumed to preserve the global-base holder, its referent, or object-associated storage.

A zero resolver result is not rejected. The routine continues with accesses relative to that result.

### Read the global base and publish the requested state

After resolving the effective object address, the routine reads the address-bearing value from the global-base holder. It then performs these one-byte writes in order:

1. Write the normalized requested state to the retrieved global base plus 0x01.
2. Write the same normalized requested state to effective object plus 0xA1.

Both stores precede the branch-condition reads. Neither store depends on the destination’s previous value. Repeating a request does not skip publication or subsequent branch selection.

The two destinations are not established to be disjoint. Nor is the global destination established to be disjoint from the marker, condition bytes, dispatch data, or the global-base holder itself.

Aliasing does not remove either store. Later accesses use the state resulting from earlier writes, subject to dependency effects and external interference. For example, if the first destination aliases a condition byte, that publication can affect which branch is selected.

The retrieved global base supplies the first store’s address. The represented sequence contains no second global-base-holder read between the publication stores.

### Select the branch using ordered byte reads

The routine first reads the byte at effective object plus 0x90.

- If it is zero, the routine selects indirect dispatch without reading the byte at offset 0x98.
- If it is nonzero, the routine reads the byte at effective object plus 0x98:
  - A nonzero second byte selects indirect dispatch.
  - A zero second byte selects the marker branch.

Both conditions distinguish zero from nonzero. Values such as 2 and 0xFF count as nonzero; equality to 1 is not required. Character signedness does not change these decisions.

The relevant condition values are those observed after the two publication stores, not necessarily their values at function entry.

### Marker branch

When the first condition byte is nonzero and the second is zero, the routine writes the byte value **1** to effective object plus 0xA2 and returns **0**.

On this branch:

- The dispatch pointer chain is not accessed.
- The indirect target is not invoked.
- The marker is set regardless of whether the requested state normalized to 0 or 1.
- The marker’s previous value is not read.
- No further local success check is performed.

The routine has no explicit marker-clearing operation. However, this does not mean that the marker cannot become zero: an earlier publication store can write zero there if its destination aliases the marker.

### Indirect branch

When the first condition byte is zero, or both condition bytes are nonzero, the routine obtains a callable through these ordered address relationships:

1. Read an address-bearing value at effective object plus 0x94.
2. Read the table-base address from the beginning of the storage identified by that value.
3. Read the callable entry at table base plus 0x20.
4. Invoke the selected target.

The call supplies no explicit arguments in the supplied representation. This does not establish the absence of machine-level context conveyed through registers, stack state, or an implicit calling convention.

The returned result is tested as a 32-bit integer:

- Zero maps to status **0**.
- Any nonzero value maps to status **7**.

The result is not propagated verbatim. Positive and negative nonzero results receive the same mapping.

This branch has no dedicated marker store and no rollback of the publication stores. Nevertheless, the marker’s final value depends on any earlier aliased writes and any effects of the indirect target. Absence of a dedicated marker write is not a general marker-preservation guarantee.

## Side effects

### Direct access order

For a normally progressing invocation, the established sequence is:

1. Optionally invoke F-bb50a072e902.
2. Read the address-bearing value from the global-base holder.
3. Write one normalized byte to the retrieved global base plus 0x01.
4. Write one normalized byte to effective object plus 0xA1.
5. Read the first condition byte at offset 0x90.
6. Read the second condition byte at offset 0x98 only when the first is nonzero.
7. Either write 1 to the marker at offset 0xA2, or perform the dispatch lookup and invoke its target.
8. Return the selected status.

This is the logical access order established by the supplied representation. It does not establish atomicity, volatile qualification, memory barriers, or inter-thread ordering.

An invalid access can prevent later operations from being reached. There is no all-or-nothing update guarantee.

### Dependency effects

Neither dependency has an established state-preservation contract.

The resolver may change state before the global-base read. The indirect target may change state after publication, including the published bytes or marker if it can reach them. Therefore, the publication sequence establishes that writes occur before dispatch, not that their values survive the call.

### Ownership and lifetime

The routine contains no explicit allocation, release, reference-count change, or ownership-transfer operation.

This absence does not establish whether either dependency allocates, retains, releases, or invalidates storage. Such dependency behavior is **documented_only**. Fault-free continuation requires the storage used by subsequent accesses to remain usable when those accesses occur.

### Errors

Status 7 is tied specifically to a nonzero indirect result. The routine does not explicitly return 7 for an invalid object, unreadable global-base holder, unusable global base, invalid dispatch chain, or abnormal dependency termination.

Outcomes of those failures are **documented_only**. They must not be replaced with an invented clean-error contract.
