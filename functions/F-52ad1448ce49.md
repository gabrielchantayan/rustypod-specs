# F-52ad1448ce49

## Purpose

F-52ad1448ce49 processes a request to remove a named schema object. It resolves the object, applies policy and protection checks, checks the requested object kind, conditionally requests database-program work, invalidates selected schema state, and performs cleanup of the supplied name-list allocation.

**Inferred intent:** this is a DROP TABLE / DROP VIEW compilation operation with special handling for virtual-table-like objects. The established behavior is a sequence of calls and state mutations; it does not establish synchronous deletion of persistent storage.

There is no explicit return value. Outcomes are observable through diagnostics, dependency calls, generated work, schema flags, and allocation accounting. Ordinary rejection paths still reach name-list cleanup. Invalid accesses or nonreturning dependencies can prevent completion.

## Interface

### Arguments and representation

| Argument | Representation | Contract |
|---|---|---|
| Compilation context | Required pointer to writable structured state | Supplies database pointers and early-stop state; passed to compilation and diagnostic dependencies. |
| Name list | Pointer to an allocator-backed structured allocation | Subject to cleanup on ordinary return. Null is safe only when processing reaches cleanup without first reading list contents. |
| Kind selector | 32-bit integer | Zero requests table-like handling; any nonzero value requests view-like handling. Lookup receives the original value. |
| Missing-object option | 32-bit integer | After a null lookup result, nonzero requests one additional call; zero omits it. |

The visible representation has 32-bit pointers and words, signed 32-bit storage identifiers, 16-bit count and flag fields, and 8-bit object flags. All offsets below are bytes.

### Context, database, and schema

The context contains a database pointer at offset 0 and a 32-bit early-stop field at offset 64. The database pointer is captured at entry.

The captured database contains a slot-array pointer at offset 8 and an 8-bit early-stop flag at offset 30. Slot records have a 24-byte stride:

- Offset 0: a 32-bit database identifier.
- Offset 20: a schema pointer.

A schema supplies:

- Offset 16: an invalidation-list head.
- Offset 84: a protected-object pointer.
- Offset 90: a 16-bit flag field, of which mask `0x0002` is relevant.

No visible bounds check validates a resolved slot index before slot access.

### Name-list layout and ownership

The list has a signed 16-bit count at offset 0. Entries begin at offset 8 and have a 48-byte stride. Lookup reads the words at list offsets 12 and 8, passing them in that order, without first checking the count.

Cleanup accesses entry-relative offsets 0, 4, 8, 12, 16, 28, and 32. Allocator metadata preceding the public list pointer is also required. A plain array with the same entry layout is insufficient.

The function attempts to consume the list through field-cleanup calls, accounting changes, and allocator calls. Actual release behavior belongs to those dependencies; successful deallocation is not independently established.

## Behavior

### Entry checks and lookup

The database pointer is captured before testing the context’s offset-64 field.

- A nonzero context field skips lookup and removal processing.
- Only if that field is zero is the captured database’s offset-30 byte read.
- A nonzero database byte also skips processing.

Both paths continue to name-list cleanup.

Otherwise, F-3747d6ba198f receives the context, unchanged kind selector, list word at offset 12, and list word at offset 8.

If lookup returns null, a nonzero missing-object option causes F-225d0f6e8fad to receive the context once. Processing then proceeds to cleanup. The option does not bypass lookup or establish that lookup diagnostics are suppressed.

### Slot resolution and policy

For a non-null object, F-49f750c2c596 receives the captured database and the object’s offset-76 word. Its result becomes the selected slot index.

If the object’s offset-57 byte is nonzero, F-382bffe8f3c1 receives the context and object. A nonzero result goes directly to cleanup.

The selected slot’s first word is then captured through the captured database’s current slot-array pointer.

F-0055bebe0706 is called with the context and operation 9; no further arguments are visible at this call site. Nonzero stops processing.

The next operation is selected as follows:

| Kind selector | Special byte | Slot index | Operation | Auxiliary value |
|---|---|---|---:|---|
| Zero | Zero | 1 | 13 | Zero |
| Zero | Zero | Other | 11 | Zero |
| Zero | Nonzero | Any | 30 | Word at offset 4 of the pointer at object offset 60 |
| Nonzero | Not consulted for this selection | 1 | 15 | Zero |
| Nonzero | Not consulted for this selection | Other | 17 | Zero |

For a zero selector, the special byte is read again after the first policy call. It is not a cached classification.

F-0055bebe0706 next receives the context, selected operation, current object name, auxiliary value, and captured slot word. If it returns zero, a further call receives the context, operation 9, current object name, zero, and that same captured slot word. Either nonzero result ends processing.

### Protection and kind checks

Protection testing is short-circuited:

1. Read the object’s offset-52 byte.
2. If nonzero, select the protection diagnostic without reading the slot-array/schema chain for the protected-object comparison.
3. Only if zero, follow the captured database’s current slot array to the selected schema and compare its offset-84 pointer with the resolved object.

A protected object causes F-2022b0f73f3b to receive the context, a removal-prohibition template, and the object name.

Otherwise, a zero selector requires a zero object field at offset 24; a nonzero selector requires that field to be nonzero. Mismatch produces a diagnostic directing use of the other removal command. Exact rendering belongs to F-2022b0f73f3b.

Protection precedes kind validation. A protected, kind-mismatched object receives the protection diagnostic.

### Conditional program work

For an accepted object, F-9b3ea8470521 receives the context. If it returns zero, the program-work phase is skipped, but schema invalidation remains reachable.

A nonzero result is retained as the primary program handle:

1. Capture the current slot-array pointer from the entry-captured database.
2. Call F-274b53956040 with the context, 1, and selected slot index.
3. Read the special byte. If nonzero, call F-9b3ea8470521 again; if that result is nonzero, pass the second handle and operation 118 to F-7f44e0e8f855. Subsequent final emissions use the first handle.
4. Traverse the dependent-object list from object offset 32. Call F-cb1bc0706bec with the context and each node. Read each next link at offset 40 after the call.
5. Read object byte 56. If nonzero, issue a sequence-related request through F-66c61ffd0a02.
6. Issue a schema-catalog request through F-66c61ffd0a02, passing a database identifier read through the saved slot-array pointer, the selected catalog name, and the current object name. Slot 1 selects `sqlite_temp_master`; other slots select `sqlite_master`.
7. Call F-4e77314e8c36 with the captured database, `sqlite_stat1`, and a slot identifier read through the database’s current slot-array pointer. A nonzero result causes another F-66c61ffd0a02 call.

The sequence and statistics call sites visibly supply the context and template. Complete SQL strings and additional formatting operands are not established.

### Storage-removal selection and snapshot boundaries

The storage loop is entered only for a zero kind selector and a zero special byte at the loop-entry check.

Immediately before entering the loop, the signed 32-bit primary storage identifier at object offset 20 is read once. That value remains cached across every subsequent slot-resolution and storage-removal call. Changing the object’s offset-20 field during a dependency call does not change this cached candidate.

Each iteration:

- Uses zero as the initial “no previous bound” state.
- Seeds its candidate with the cached primary identifier if there is no bound or that identifier is strictly below the preceding selection; otherwise seeds zero.
- Rereads the associated-list head at object offset 16.
- Traverses the current list, reading each signed identifier and next link.
- Admits identifiers strictly below the previous bound, when bounded, and replaces the candidate only with a strictly greater eligible identifier.
- Stops if the selected candidate is zero.

For each nonzero selection, F-49f750c2c596 receives the context’s **current** database pointer and a newly read object offset-76 value. F-fa17eddb09c3 then receives the context, selected identifier, and that resolution result. The selected identifier becomes the next strict upper bound.

Thus, with stable positive identifiers, requests are distinct and descending. The primary identifier is cached; the associated-list head and slot-resolution inputs are live reads.

Signed edge cases matter. A negative primary identifier can seed a candidate. A negative associated identifier cannot replace a zero seed. This is not an unrestricted sorted enumeration of all signed identifiers.

### Final emissions

For a zero selector whose loop-entry special check was nonzero, operation 101 is emitted directly. Otherwise—after the ordinary storage loop, or for a nonzero selector—the special byte is read again and controls operation 101.

F-0b0cd8d831b7 receives the primary handle, operation 101 when selected, slot index, two zeros, current object name, and a final zero. Operation 84 is then emitted with the same argument shape regardless of operation 101.

F-2e31112ab290 follows with the context and selected slot index.

### Schema invalidation

After the accepted path, including a zero primary program handle, the selected schema is read through the entry-captured database’s current slot array.

If flag mask `0x0002` is clear, no invalidation traversal occurs. If set:

- Traverse the list at schema offset 16, following each node’s first word.
- Read the pointer at node offset 8 and its 32-bit field at offset 24.
- If that field is nonzero, call F-a116356a135b with no explicit arguments.
- Read each next link after any call.
- Refetch the selected schema through the captured database’s current slot array.
- Clear mask `0x0002` with a 16-bit read-modify-write, preserving other bits.

The traversal uses its initial head; the final flag write uses the refetched schema.

## Side effects

### Entry cleanup and accounting-pointer capture

A null list returns immediately at cleanup.

For a non-null list, each loop-condition evaluation first reads the global accounting-state pointer, then compares the signed loop index with the current signed 16-bit count. This pointer read occurs even on the terminating evaluation, including when the initial count is zero or negative.

For each visited entry, calls occur in this order:

| Entry offset | Dependency |
|---:|---|
| 0 | F-94cb53877c15 |

| 28 | F-841dc33ee157 |

Each field is read when its call is prepared, after preceding calls. Zero values are passed, not skipped. Null handling and ownership effects inside dependencies are unknown. The entry address advances 48 bytes; the count is reread.

### Global accounting

Subtract the signed 32-bit displacement at list offset −4 from the public list address to derive the internal allocation address. Address arithmetic follows the visible 32-bit representation.

A 32-bit accounting amount is read at allocation offset −8. Accounting then proceeds in this order:

1. Reread the global accounting pointer and read its low word at offset 56.
2. Reread the global pointer to form the high-word source address at offset 60.
3. Reread the global pointer and write the low-word subtraction at offset 56.
4. Read the high-word source and write the adjusted high word at offset 60 of the pointer captured by the **terminating entry-loop condition**.

The high-word adjustment subtracts the amount’s arithmetic sign extension plus the unsigned borrow from the low subtraction. All word results are 32-bit. This differs from unsigned 64-bit subtraction when the amount’s high bit is set.

The high-word destination is therefore not specified as a fresh global-pointer read.

F-2fd8826557a4 is called next. The allocator-state pointer is read afterward.

### Allocator-state mutations and release calls

If the internal allocation address equals numeric address 8, allocator-body processing is skipped. Earlier accounting changes and F-2fd8826557a4 have already occurred.

Otherwise, the 32-bit header at allocation offset −16 must be nonzero and have bit 0 clear. Failure calls nonreturning F-a817d8d58c10.

After F-c0fc6d033caa receives the captured allocator state:

- Read unsigned 16-bit metadata at allocation offset −12.
- Reread the header and mask it with `0x3ffffffc` to obtain the size.
- Subtract that size from allocator-state offsets **548 + 4 × first metadata**, then **780**.
- Read unsigned 16-bit metadata at allocation offset −10.
- Subtract the same size from offsets **224 + 4 × second metadata**, then **544**.

Next, F-09dcb55e8e0a returns a counter index. After it returns:

1. Decrement the 32-bit counter at allocator-state offset **784 + 4 × result**.
2. Decrement the counter at offset **912**.
3. Reread the allocation header, mask with `0x3ffffffc`, and subtract that value from offset **8**.

Finally, F-cc6c9b4a0f68 receives the captured allocator state and header address, followed by F-e586bff64fb7 receiving that state.

The state pointer remains captured across these calls. Metadata indices and returned indices have no visible bounds checks. Arithmetic has no explicit underflow checks. The header is not revalidated after dependencies mutate it.

## Acceptance examples

These are conditional static cases, not executed tests.

1. **Early stop:** a nonzero context stop field prevents the database stop-byte read and lookup. A non-null list still undergoes cleanup.

2. **Null input:** with both stop conditions clear, a null list cannot reach lookup safely because its offset-8 and offset-12 words are required.

3. **Missing object:** null lookup plus nonzero option calls F-225d0f6e8fad once; zero option omits it. Both reach cleanup.

4. **Protection short circuit:** after successful policy checks, a nonzero object byte 52 selects the protection diagnostic without the protected-object schema dereference. Kind mismatch does not override it.

5. **Stable positive roots:** cached primary 7 and associated identifiers 3, 12, 7, and 0 produce requests for 12, 7, and 3.

6. **Cached primary, live list:** after selecting 12, suppose a dependency changes object field 20 from 7 to 10 and replaces the associated list with identifiers 9 and 3. With subsequent state stable, remaining requests are 9, 7, and 3—not 10. New offset-76 values and current context database pointers are used for subsequent slot resolutions.

7. **No program handle:** a zero first F-9b3ea8470521 result skips maintenance, storage requests, and final emissions, but not eligible schema invalidation.

8. **Zero-count cleanup:** no entry-cleanup calls occur, but the terminating condition still captures the accounting pointer used for the later high-word destination.

9. **Header changes across calls:** a valid initial header is followed by a changed header after F-c0fc6d033caa. The four size-accounting decrements use the reread masked size. A further change during F-09dcb55e8e0a affects the later offset-8 subtraction, not those completed decrements.

10. **Invalid header:** for a non-sentinel allocation, a zero header or set bit 0 causes nonreturning failure after global accounting has already changed.
