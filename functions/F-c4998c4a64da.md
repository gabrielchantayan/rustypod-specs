# F-c4998c4a64da

## Purpose

F-c4998c4a64da conditionally detaches a selected node from a binary-tree-shaped structure, performs color-dependent structural repair, places the detached node at the head of a separate chain, and decrements a 32-bit counter. It writes one 32-bit result to caller-provided storage and has no explicit return value.

The link arrangement, cached endpoints, and repair operations suggest deletion from an ordered, red–black-style tree. That is inferred intent. The established contract is the visible sequence of accesses, decisions, writes, and dependency calls; it does not guarantee conventional tree balancing.

The result is prepared through opaque dependencies before the removal target is reread. Consequently, the result need not identify the node that is detached.

This is a static behavioral contract. No runtime tests have been performed.

## Behavior

### 1. Decision and result preparation

The function first reads the selection’s 32-bit value into a temporary, then reads the container’s header address into another temporary. It passes the addresses of these temporaries to F-9ed8931accde.

If that dependency returns nonzero, the function:

1. Rereads the header address from container offset +16.
2. Uses that value as the result.
3. Writes the result to the output destination and returns.

On this branch, the function itself performs no structural removal, chain insertion, or counter decrement. This does not constrain the dependency’s own effects.

If the decision result is zero, the function calls F-029238addcdd with the address of the first temporary. It then rereads the selection storage and uses that current value as the selected node address.

The first temporary is not directly reassigned afterward on the removal path. Its eventual contents supply the final output. The function does not establish that those contents equal either the initial selection or the reread target.

### 2. Choosing the structural case

The selected node’s left link is inspected first.

- With no left child, its right link determines whether the case is a leaf or a right-child replacement.
- With a left child but no right child, the left child is the replacement.
- With both children present, the function searches from the right child along left links. The first node with a null left link is the successor. Its right child is the initial repair candidate associated with the successor’s former position.

For a leaf, the repair candidate is the selected node’s parent. For a direct-child replacement, it is the replacement child.

No key comparison, payload copy, or payload destruction is visible.

### 3. Leaf removal

If the selected leaf’s parent equals the current header address, the function writes:

1. The header’s right link to that header address.
2. The header’s left link to that header address.
3. The header’s root link to zero.

Otherwise, it reads the parent’s left link. If that link equals the selected node, it clears the left link; otherwise, it clears the right link without separately verifying a right-link match.

Each such clear consists of four zero-byte stores in increasing address order. Other link assignments are represented as 32-bit stores. No atomicity guarantee follows from either representation.

The cleared side determines the sole cached endpoint checked:

- A left-link clear checks the header’s cached minimum.
- A right-link clear checks the cached maximum.

If that cache equals the selected node, it is replaced with the parent address. The opposite cache is not independently checked in this branch.

### 4. Replacement by one child

For a selected node replaced directly by its non-null child, the function first writes the selected node’s parent into the child’s parent field.

It then checks whether the header’s root link names the selected node. If so, that root link becomes the child. Otherwise, it checks the selected node’s parent’s left link, replacing it on a match and replacing the parent’s right link otherwise.

The minimum cache is processed before the maximum cache:

- If the minimum cache names the selected node, the replacement cache value is the selected node’s parent when the selected node’s right link is null. Otherwise, it is the leftmost node reached from the replacement child.
- If the maximum cache names the selected node, the replacement cache value is the selected node’s parent when the selected node’s left link is null. Otherwise, it is the rightmost node reached from the replacement child.

These are the actual conditional rules. Their interpretation as correct endpoint maintenance depends on structural consistency.

### 5. Two-child successor transplantation

The successor takes the selected node’s structural position. The original selected node remains the node subsequently inserted into the detached chain.

The visible ordering is:

1. The selected node’s left child receives the successor as its parent.
2. The successor receives the selected node’s left link.
3. The successor’s former position and right-subtree relationships are adjusted.
4. The selected node’s incoming root or parent link is redirected to the successor.
5. The successor receives the selected node’s parent.
6. The successor’s and selected node’s color bytes are exchanged.

For an immediate-right-child successor, a non-null successor right child receives the successor as parent. The right subtree is not separately attached again.

For a non-immediate successor:

- Its non-null right child first receives the successor’s former parent.
- Its former parent’s left link becomes that right child, including zero when absent.
- The successor receives the selected node’s right link.
- That right subtree’s root receives the successor as parent.

Incoming-link redirection uses the same root-first, then parent-left-match, otherwise parent-right rule as direct-child replacement.

If the successor’s former right child is null, the repair candidate becomes the transplanted successor itself. Otherwise, that right child remains the repair candidate.

The original selected node acquires the successor’s former color through the exchange. No payload move or explicit cached-endpoint update occurs in this branch.

### 6. Color-dependent repair

Repair is entered only when:

- The repair candidate differs from the current header address; and
- The detached node’s color byte is nonzero.

The detached color is not read for this decision when the candidate equals the header. Following a successor transplant, this gating byte is the successor’s former color.

Once entered, the loop checks the current root before reading the candidate’s color. An iteration proceeds only if the candidate is not the current root and its color is exactly 1. A nonzero detached color other than 1 can therefore enter repair, while a candidate color other than 1 immediately ends the loop.

Each iteration reads the candidate’s parent and compares the parent’s left link with the candidate. A match selects the right sibling; otherwise, the left sibling is selected without separately checking that the candidate is the right child.

For the following descriptions, the **near child** is the sibling child facing the candidate, and the **far child** is the other sibling child.

#### Zero-colored sibling

When a non-null sibling has color 0, the function:

1. Writes sibling color 1.
2. Writes parent color 0.
3. Calls the corresponding structural dependency.
4. Reloads the candidate’s parent and the sibling on the same opposite side.

F-2f1a529549b6 is used when the candidate was on the left; F-8dda4e0c371c is used for the mirrored case.

The dependency’s complete transformation is unknown. Subsequent decisions use the reloaded links, not an assumed rotation result.

#### Missing sibling

If the sibling is null, either initially or after the zero-colored-sibling dependency call, the function writes the current candidate’s color to 0 and advances the candidate to its parent.

Every visible entry into this handling supplies a parent address:

- Without the dependency call, it is the parent read at the beginning of the iteration.
- After that call, it is the parent reloaded from the current candidate.

The next loop check uses that parent as the candidate. No visible path carries a sibling or child color byte into this address assignment.

#### Non-null sibling

If both sibling children are either null or color 1, the function writes sibling color 0 and advances the candidate by rereading its parent link. It does not write the candidate’s color to 0 in this case.

Otherwise, if the far child is null or color 1:

1. The non-null near child is written to color 1.
2. The sibling is written to color 0.
3. The complementary structural dependency is called.
4. The sibling is reloaded through the candidate’s current parent.

For a left-side candidate this intermediate call uses F-8dda4e0c371c; for a right-side candidate it uses F-2f1a529549b6. If the reloaded sibling is null, repair proceeds directly to completion.

With a non-null sibling available for the final transformation, the function:

1. Copies the current parent’s color into the sibling.
2. Writes parent color 1.
3. Writes the far child’s color to 1, if that child exists.
4. Calls F-2f1a529549b6 for a left-side candidate, or F-8dda4e0c371c for a right-side candidate.
5. Leaves the loop.

After loop termination or an explicit exit to repair completion, the current candidate is written to color 1. This completion write occurs only if repair was entered; the initial skip paths do not perform it.

The tests distinguish zero, exactly 1, and other byte values. Treating every nonzero value as black would not reproduce the visible behavior.

### 7. Detached-chain insertion and output

After structural processing and any repair, the function performs these operations in order:

1. Reads the current detached-chain head at container offset +4 and stores it in the detached node’s right field.
2. Writes the detached node’s address as the new chain head.
3. Reads the counter at container offset +20 and stores its value decreased by one.
4. Writes the result temporary to the output destination.

Chain insertion does not clear the detached node’s parent or left fields.

The counter access is 32 bits wide. No range check, saturation, underflow report, or wider counter storage is visible. At the 32-bit representation level, decrementing zero produces all one bits; a portable signed-arithmetic interpretation is not established by the supplied representation.

## Acceptance examples

These are conditional static expectations, not executed tests. Structural conditions below apply **at the selection reread after F-029238addcdd**, unless another observation point is explicitly identified. They are not guarantees derived solely from function-entry state.

### Early output

If F-9ed8931accde returns nonzero and the subsequently reread header address is H:

- The output receives H.
- F-029238addcdd is not called.
- The function body performs no removal, chain insertion, or decrement.

This does not exclude changes made by F-9ed8931accde.

### Removing the only node

Suppose the initial decision is zero and, at the structural observation point:

- Selection identifies the sole node N.
- The header is H, the root is N, and both cached endpoints are N.
- N has null children and parent H.
- Required memory is valid and no relevant aliasing disturbs these relationships.

Then the header’s right and left links become H, followed by a null root. The repair candidate is H, so repair is skipped.

N becomes the detached-chain head; its right field receives the previous chain head. The counter is decremented, and the result temporary is written to the output.

Normal return of the initial dependencies alone is insufficient to establish these outcomes: the specified one-node configuration must exist after their effects.

### Removing a node with one right child

Suppose the reread target has no left child, has right child R, and the relevant parent, root, and cache relationships are consistent at that point.

Before any repair dependency:

- R receives the target’s parent.
- The root or incoming parent link is redirected to R.
- If the minimum cache names the target, it becomes the leftmost node reachable from R.

Later color and structural effects depend on the repair state and any invoked dependency. Entry-state conditions alone do not establish this example.

### Immediate successor without a right child

Suppose the reread target has two children, its right child S has no left or right child, and the relevant structural links are consistent at that observation point.

Before repair:

- S takes the target’s incoming position and left subtree.
- S and the target exchange color bytes.
- S becomes the repair candidate.
- The original target remains the node designated for detached-chain insertion.

Final tree properties additionally depend on any repair dependencies.

### Missing-sibling ascent

At a repair iteration, suppose the candidate is not the current root, has color 1, and its selected sibling is null. If its parent read for that iteration is P, the function writes candidate color 0 and uses P as the next candidate.

If the sibling instead becomes null after the zero-colored-sibling dependency call, P is the parent reloaded after that call. The same ascent occurs using that reloaded address.

### Zero counter

If completion reaches the counter read with its 32-bit representation equal to zero, the decrement stores all one bits. No underflow status is returned. This condition applies at the counter read, not necessarily at entry.
