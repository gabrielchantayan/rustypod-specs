# F-c97926c32b91

## Purpose

F-c97926c32b91 acquires one 20-byte slot from a caller-supplied pool state and partially initializes that slot. It first prefers a recycled slot. If none is available, it consumes the next unused slot in the current backing region. When that region is exhausted, it allocates a new region and links a new region descriptor into the pool.

The routine has no explicit return value and does not explicitly publish the selected slot through an output parameter. Its observable result is the change to pool metadata, any newly allocated descriptor, and selected bytes of the acquired slot.

The interpretation as a reusable-slot pool is inferred intent. The field accesses, allocation requests, selection precedence, and stores described below are established by the supplied static evidence.

## Interface

### Pool argument

The sole argument is an address of writable pool state. The supplied representation uses four consecutive 32-bit fields:

| Byte offset | Width | Role in this routine |
|---|---:|---|
| 0 | 4 bytes | Address of the current region descriptor, or zero |
| 4 | 4 bytes | Address of the first recycled slot, or zero |
| 8 | 4 bytes | Address of the next unused slot in the current region |
| 12 | 4 bytes | End address used to determine whether the current region is exhausted |

These are descriptive roles, not evidence of a complete external type definition. The routine accesses no additional pool fields.

Addresses are represented through 32-bit fields in the supplied representation. This contract describes that representation; it does not imply compatibility with a layout using wider pointers or native-sized fields on another target.

The pool argument itself is not checked for nullness, alignment, accessibility, or internal consistency.

### Region descriptor

Each newly created descriptor is requested as a 12-byte allocation and is populated as follows:

| Byte offset | Width | Stored value |
|---|---:|---|
| 0 | 4 bytes | Pool descriptor-head value read after both allocation calls |
| 4 | 4 bytes | New region capacity, in slots |
| 8 | 4 bytes | Address returned for the new backing region |

When an existing descriptor is consulted to determine growth, only its capacity field at offset 4 is read.

### Slot layout

The slot stride is exactly 20 bytes. For the selected slot, the routine performs these writes, in this order:

| Byte offset | Width | Value |
|---|---:|---|
| 4 | 4 bytes | Zero |
| 8 | 4 bytes | Zero |
| 12 | 4 bytes | Zero |
| 0 | 1 byte | Zero |

Thus, 13 bytes are explicitly cleared. Bytes 1–3 and 16–19 are not explicitly written by slot initialization. No meaning for those untouched bytes is established.

For a recycled slot, the 32-bit field at offset 12 is read as the next recycled-slot address before that field is cleared.

### Result and completion

There is no explicit return value, success flag, error code, or selected-slot output. Normal completion means the selected path's metadata changes and slot-initialization stores have been executed, subject to the dependency returning normally and all accessed memory being valid.

## Behavior

### 1. Prefer a recycled slot

The first selection operation reads the pool field at offset 4.

If that field is nonzero:

1. Its value identifies the selected slot.
2. The routine reads the 32-bit value at selected-slot offset 12.
3. It writes that value to pool offset 4, removing the selected slot from the front of the recycled chain.
4. It performs the four slot-initialization writes listed under Interface.

On this path, the routine does not consult the current-region cursor, region end, or descriptor head. It makes no allocation call and does not explicitly advance the unused-slot cursor.

The recycled-slot chain is not traversed or validated. A one-element chain is represented by a zero next-link value. A cycle or self-link is not detected.

### 2. Consume an unused slot when no recycled slot exists

If the initially read recycled-slot address is zero, the routine reads the next-unused address at pool offset 8 and compares it with the end address at pool offset 12.

If the addresses differ:

1. The next-unused address identifies the selected slot.
2. Pool offset 8 is updated to the selected address plus 20 bytes.
3. The selected slot is partially initialized.

There is no less-than comparison, range check, alignment check, or remaining-byte check. Inequality alone selects this path. In particular, a cursor beyond the end address is not treated as exhausted; it is used as the selected address and advanced again.

Under an intended well-formed layout, the unused range consists of whole 20-byte slots, so differing cursor and end addresses indicate an available slot. That invariant is a caller-side precondition, not something this routine enforces.

### 3. Allocate a region when the cursor equals the end

When no recycled slot exists and the next-unused address equals the end address, the routine calculates a new capacity.

If the pool's descriptor-head field is zero, the new capacity is 32 slots.

Otherwise, the routine reads the existing head descriptor's 32-bit unsigned capacity, denoted here as \(C\), and computes two 32-bit unsigned candidates:

- Additive candidate: \(C + 32\).
- Proportional candidate: \(C + (C \mathbin{\mathrm{>>}} 1) + (C \mathbin{\mathrm{>>}} 3)\).

The right shifts are unsigned. Each arithmetic result is subject to 32-bit unsigned wraparound. The routine chooses the proportional candidate when the wrapped additive candidate is less than or equal to it; otherwise it chooses the additive candidate. Equivalently, it chooses the larger of the two already-wrapped candidates.

Without overflow, the proportional candidate is \(C + \lfloor C/2 \rfloor + \lfloor C/8 \rfloor\). This is not the same expression as first multiplying by 13 and then dividing by 8 for every possible \(C\), because the two shifted terms are truncated separately.

The routine then performs the following operations in order:

1. Calls F-871e64ddc6de with a size argument of 12 and a second argument of zero.
2. Calls F-871e64ddc6de again with a size argument equal to the selected capacity multiplied by 20, using 32-bit arithmetic, and a second argument of zero.
3. Writes the second call's result into the new descriptor at offset 8.
4. Reads the pool's descriptor-head field and writes it into the new descriptor at offset 0.
5. Writes the selected capacity into the descriptor at offset 4.
6. Publishes the new descriptor address at pool offset 0.
7. Reads the backing-region address from the new descriptor at offset 8 and uses it as the selected-slot address.
8. Writes the selected-slot address plus the capacity multiplied by 20 into pool offset 12.
9. Writes the selected-slot address plus 20 into pool offset 8.
10. Performs the selected slot's four initialization writes.

The first slot of the new region is therefore consumed immediately. For a nonzero, non-overflowing capacity and valid backing allocation, the new cursor points to the second slot.

The descriptor predecessor is read after both dependency calls. It is not necessarily the same value used earlier to decide the capacity: the dependency's effects on pool state are unknown.

### 4. Arithmetic and address boundaries

There are no explicit overflow checks for:

- Capacity growth.
- Capacity multiplied by the 20-byte stride.
- Construction of the new end address.
- Advancement of the next-unused address.

In particular, growth is not guaranteed to remain monotonic once 32-bit arithmetic wraps. The backing-region size request is the wrapped product, not an arbitrary-precision product.

Safe use requires address calculations and requested allocation sizes to be consistent with actual accessible storage. The supplied evidence does not establish portable behavior for address calculations that overflow the target address space.

## Side effects

### Pool metadata

Depending on the path, the routine explicitly changes:

- **Recycled path:** the recycled-slot head at pool offset 4.
- **Existing-region path:** the next-unused cursor at pool offset 8.
- **New-region path:** the descriptor head at offset 0, region end at offset 12, and next-unused cursor at offset 8.

Every normal path also partially clears the selected slot.

These descriptions identify direct stores by this routine. They do not claim that other fields remain unchanged across dependency calls, because the dependency's side effects are not supplied.

### Allocation and lifetime

The exhausted-region path makes exactly two explicit calls to F-871e64ddc6de: first for a descriptor, then for backing storage. It links the new descriptor to the descriptor-head value observed after those calls.

The routine contains no explicit release operation and does not unlink an old region. The descriptor chain retains a reference to the previously observed head, but ownership, eventual reclamation, and lifetime guarantees are not established.

The routine does not explicitly add an acquired slot back to the recycled chain.

### Ordering and visibility

Pool bookkeeping precedes slot initialization:

- A recycled slot is removed from the recycled head before being cleared.
- An unused-slot cursor is advanced before its selected slot is cleared.
- A new descriptor, end address, and cursor are published before the first slot is cleared.

The evidence establishes this sequential access order. It does not establish atomic publication, synchronization, memory-order guarantees, or safe concurrent observation.

### Invalid state and failed allocation

No allocation result is checked before use. There is no explicit rollback or error-reporting path.

If the descriptor allocation returns an unusable address, descriptor writes may fail after the backing-storage allocation has already been attempted. If the backing allocation returns an unusable address, the routine can publish descriptor and pool metadata containing that result before attempting slot initialization.

Consequently, successful safe execution requires the dependency to return suitable usable memory, or otherwise prevent execution from reaching invalid accesses. Its failure convention is unknown.

Malformed pool pointers or slot links can likewise produce invalid reads or writes. The routine supplies no validation or recovery for them.

Suppose the recycled head identifies slot A, slot A's next-link identifies slot B, and the current region is exhausted.

- The unused cursor and region end receive no direct writes.
