# F-84549ebf9997

## Purpose

F-84549ebf9997 creates a node, attaches it beneath a supplied position in a linked structure, performs color-based repair, and returns the created node through an output location.

The established behavior is consistent with insertion into a red-black binary search tree whose header stores the root and two boundary-node pointers. That interpretation is inferred from field use and repair patterns; the supplied evidence does not establish a complete tree API, comparator contract, allocator contract, or dependency implementation.

This operation does not search for an insertion position or reject duplicate values. The caller supplies the attachment position and a flag that can force one attachment direction.

All behavior below is based on static evidence. No runtime tests have been performed.

## Interface

The operation takes five inputs, in this order:

| Input | Role | Width and access |
|---|---|---|
| Result location | Receives the created node address at normal completion | One writable 32-bit word |
| Container address | Identifies the header-pointer field, count field, and comparison context | Address represented in a 32-bit word |
| Direction override | Any nonzero value forces attachment through offset +8 | 32-bit integer; tested only for zero versus nonzero |
| Attachment position | Existing node or header beneath which the new node is attached | Address represented in a 32-bit word |
| Payload source | Supplies two words copied into the new node and is passed to the comparison dependency when needed | Two readable 32-bit words |

No ordinary return value is established. The observable result is the final write to the result location, together with mutations to the container and linked nodes.

### Container layout

The following offsets are relative to the container address:

| Offset | Established use |
|---|---|
| +0x10 | 32-bit header address |
| +0x14 | 32-bit count, incremented once before attachment |
| +0x19 | Address passed as the first comparison argument |

The extent and interpretation of the comparison context beginning at +0x19 are unknown.

### Header and node layout

The operation uses these node-relative fields:

| Offset | Access width | Established use |
|---|---:|---|
| +0x00 | 1 byte | Color or repair-state marker |
| +0x04 | 4 bytes | Parent address; on the header, root address |
| +0x08 | 4 bytes | First child address; on the header, one boundary address |
| +0x0c | 4 bytes | Second child address; on the header, the other boundary address |
| +0x10 | 4 bytes | First payload word |
| +0x14 | 4 bytes | Second payload word |

For clarity, this contract calls offset +0x08 **left**, offset +0x0c **right**, marker value zero **red**, and marker value one **black**. These names describe the inferred tree interpretation. The actual branch predicates distinguish zero from nonzero; they do not require every preexisting nonzero marker to equal one.

### Preconditions

Successful ordinary use requires:

- A valid container and header, with the fields used by the selected execution path readable and writable.
- A valid attachment position.
- A readable payload source and writable result location.
- A node-producing dependency that returns storage suitable for all subsequent accesses.
- Linked parent, child, and root fields sufficient for every repair iteration that is reached.
- Dependency behavior compatible with the linked structure.

The function does not check these conditions. It does not explicitly reject a null result location, null payload source, invalid attachment position, inconsistent topology, or count overflow.

Nonoverlapping inputs are the simplest supported usage model. Aliasing is not prohibited by an explicit check, but it can change behavior because payload accesses, structural writes, and output publication occur at different times.

## Behavior

### Node acquisition and payload transfer

The first action is a call to F-7f32c2914faf with the container address. Its return value is retained as the created node address and is the address eventually published to the result location.

The function then tests whether the address at created-node offset +0x10 is nonzero. If so, it transfers the payload in this order:

1. Read the first 32-bit source word and write it at created-node offset +0x10.
2. Read the second 32-bit source word and write it at created-node offset +0x14.

The second source word is not established as having been read before the first destination write. Overlapping source and destination storage can therefore affect the second transfer.

This guard is not a normal null-node check: it tests the payload address, not the created node address. A null created-node address does not, by itself, make this test false. Under a 32-bit wrapping-address interpretation, the exceptional base value that makes the tested address zero is 0xfffffff0. The language-level validity of such exceptional address arithmetic is not established.

After this guarded transfer, the function increments the container count by one. The count update precedes attachment-direction selection, any comparison call, parent-link installation, and repair.

### Attachment-direction selection

Attachment uses the left field if either:

- The current header address equals the supplied attachment position; or
- The direction override is nonzero.

Neither case invokes the comparison dependency.

Otherwise, F-bcefa5957e76 is called with:

1. The address at container offset +0x19.
2. The original payload-source address.
3. The address at attachment-position offset +0x10.

A nonzero comparison result selects left attachment. A zero result selects right attachment. No positive-versus-negative distinction is made.

The comparison is called after node creation, payload transfer, and count increment. It receives the original source address rather than the copied payload address. If earlier operations or aliasing changed source storage, the comparison can observe those changes.

There is no duplicate-key rejection or alternate completion path based on comparison equality.

### Attachment and boundary maintenance

For left attachment, the function first writes the created node address into the attachment position’s left field. It then reads the container’s header address.

If that header address equals the attachment position:

- The header’s root field is set to the created node.
- The header address is read again from the container.
- That header’s right boundary field is set to the created node.

The earlier left-field write has already populated the attachment position’s left field. In the ordinary empty-tree interpretation, root and both boundary fields consequently refer to the created node.

If the header address differs from the attachment position:

- The header’s left boundary field is inspected.
- It is replaced by the created node only if it currently equals the attachment position.

For right attachment:

- The created node is written into the attachment position’s right field.
- The current header’s right boundary field is inspected.
- It is replaced by the created node only if it currently equals the attachment position.

After attachment and boundary maintenance, the created node’s parent field is set to the supplied attachment position.

The function does not explicitly initialize the created node’s child fields or its initial color byte. Any required initial values must already exist, be supplied by F-7f32c2914faf, or arise from behavior not present in the supplied evidence.

### Color-based repair

Repair starts with the created node as the current repair node.

At the start of each iteration, the current root address is obtained through the container’s header and compared with the current repair node. If they match, repair ends.

Otherwise, the current repair node’s parent is read. If that parent’s marker is nonzero, repair ends. A zero parent marker enters the repair cases.

The grandparent is then obtained from the parent field. Case selection depends on whether the parent equals the grandparent’s left child.

#### Parent is the grandparent’s left child

The grandparent’s right child is the uncle.

If the uncle exists and has marker zero:

- The parent marker is written as one.
- The uncle marker is written as one.
- The grandparent reached through the current repair node’s parent chain is written as zero.
- Repair continues with that grandparent as the current repair node.

If the uncle is absent or has a nonzero marker:

- If the current repair node is its parent’s right child, F-6e50c907f5e4 is called with the container and parent. The previously selected parent then becomes the current repair node.
- The parent reached from the current repair node is marked one.
- Its parent is marked zero.
- F-58326c7630ef is called with the container and the grandparent obtained through that updated parent chain.

#### Parent is not the grandparent’s left child

This branch does not separately prove that the parent is the grandparent’s right child. Valid tree topology is an external precondition.

The grandparent’s left child is the uncle.

If the uncle exists and has marker zero, the same recolor-and-ascend behavior applies: parent and uncle become one, the grandparent becomes zero, and repair continues from the grandparent.

Otherwise:

- If the current repair node is its parent’s left child, F-58326c7630ef is called with the container and parent, with additional argument values described under Dependencies. The previously selected parent becomes the current repair node.
- The parent reached from the current repair node is marked one.
- Its parent is marked zero.
- F-6e50c907f5e4 is called with the container and the grandparent obtained through that updated parent chain.

The two dependency roles are consistent with opposing rotations, but their complete mutations and guarantees are not established. In particular, links used after a dependency call are read from memory again; this contract does not assume the call preserves them.

### Finalization

When repair ends:

1. The container’s header address is read.
2. The root address is read through that header.
3. The root marker byte is written as one.
4. The originally created node address is written to the result location.

The final root-color write occurs even when the repair loop performs no iterations. The returned node address is the original created node, not the potentially changed repair node.

No rollback, deallocation, or explicit error return appears.

## Side effects

Directly established effects include:

- One call to the node-producing dependency.
- Up to two 32-bit payload writes, in source order.
- One count increment.
- One attachment-child write.
- Conditional header root and boundary writes.
- One created-node parent write.
- Zero or more repair-marker writes and repair-dependency calls.
- One final root-marker write.
- One final 32-bit result write.

The count is stored in a 32-bit field. Overflow handling is absent. The source presents signed integer addition, but does not establish a portable overflow policy; wraparound is not an unconditional contract.

No payload pointer is stored as the payload itself: the two words are copied. Whether either word encodes an owned resource is unknown.

The function contains no explicit release of the created node, old payloads, or any other allocation. Ownership transfer, allocator failure behavior, exceptions, nonlocal exits, and dependency-managed cleanup remain unknown.

If an access or dependency fails after mutation begins, no recovery behavior is established. In particular, the count may already have changed before attachment or repair completes.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed tests. They assume valid, nonaliasing storage and compatible dependency behavior.

### Empty structure

Given a header that is also the attachment position, and a node-producing dependency returning a suitably initialized node:

- Comparison is skipped regardless of the direction override.
- The count increases once.
- The header’s left, root, and right fields become the created node.
- The created node’s parent becomes the header.
- Repair immediately recognizes the created node as root.
- The created node’s marker becomes one.
- The result location receives its address.

### Forced left attachment

Given a nonheader attachment position and a nonzero direction override:

- Comparison is not called.
- The created node is written to the position’s left field.
- The header’s left boundary changes only if it previously equaled that position.
- Subsequent repair depends on the parent marker and topology.

The operation does not first verify that the overwritten child field was empty.

### Comparison-selected right attachment

Given a zero direction override, a nonheader position, and comparison result zero:

- Comparison receives the original payload-source address.
- The position’s right field is replaced.
- The header’s right boundary changes only if it previously equaled that position.

A comparison result interpreted elsewhere as “equal” is not rejected here.

### Nonzero parent marker

Given a newly attached node that is not root and whose parent marker is any nonzero byte:

- Repair exits without entering an uncle case.
- The current root is still marked one.
- The created node address is published.

A preexisting parent marker of two follows the same exit predicate as one.

### Red parent and red uncle

Given a zero parent marker and an existing zero-marker uncle:

- Parent and uncle are marked one.
- The grandparent is marked zero.
- Repair continues from the grandparent rather than immediately returning.

Further repair depends on the updated ancestor relationships.

### Aliased result location

If the result location aliases a writable structure field, the final output write overwrites that field after root finalization. No preservation guarantee is established for such usage.
