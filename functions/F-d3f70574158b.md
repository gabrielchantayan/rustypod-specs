# F-d3f70574158b

## Purpose

F-d3f70574158b coordinates two temporary traversal states using two fields of a caller-supplied object. It processes pairs while both advancement calls report success, repositions the second state, processes the second state alone, exchanges the object’s two fields, and finalizes the temporary states in reverse initialization order.

The established contract is the sequence of calls, argument evaluations, direct memory accesses, and branch decisions. The evidence does not establish collection semantics, ownership transfer, or the meaning of the positioning marker.

Reconciliation of two collections followed by an exchange of roles is inferred intent, not required semantics. In particular, the second-only traversal is not established to visit only unmatched values.

Values used in processing come from mutable output locations whose addresses are passed to dependencies. They are not protected snapshots of values originally supplied by advancement calls.

The function performs no explicit validation of the input address, object size, alignment, field contents, or object type. The supplied representation indicates 32-bit integer address carriers and output values; it does not independently establish a portable native-pointer model.

### Temporary storage and output locations

Observable behavior includes dependency calls, their effects, direct byte reads through output-derived addresses, and the two four-byte writes to the input object.

## Behavior

### Initialization

The function reads the four-byte field at input offset `0xA8` and invokes F-538044b67754 with:

1. The first 20-byte state.
2. The field value just read.
3. The marker `0xFFFFFFFE`.

Only after that call returns does it read the four-byte field at offset `0xAC`. It invokes F-538044b67754 with the second state, this newly read field value, and the same marker.

The two field values are therefore not captured together before initialization. If the first initialization changes the second field through shared state or aliasing, the second initialization receives the changed value.

The marker is the 32-bit pattern `0xFFFFFFFE`, equivalent to −2 under signed 32-bit interpretation. Its operational meaning is unknown.

### Paired advancement

Each paired attempt first invokes F-6e4651b532dc with the first state and the address of the first output location.

- A zero result immediately ends the paired phase.
- A nonzero result causes F-6e4651b532dc to be invoked with the second state and the address of the second output location.
- A zero result from that second call ends the paired phase.
- Two nonzero results permit pair processing.

Only the zero/nonzero distinction matters to this caller. No particular nonzero result is required.

The calls are short-circuited. When the first call returns zero, the second call is omitted for that attempt. When the first succeeds and the second returns zero, the first advancement has already occurred; this function performs no rollback.

Success does not freeze either output location. In particular, the second advancement may modify the first output location if a dependency retained access to it. Pair processing uses the contents available after both advancement calls have returned, not necessarily the contents originally supplied by the first call.

### Pair processing

After two successful advancement results, the function invokes F-f3f729ad60be with:

1. The current contents of the second output location.
2. An address-like integer formed by adding `0x14`, or 20 bytes, to the current contents of the first output location.

The second argument is the arithmetic result itself. This function does not load a four-byte value from that address at this point.

The source establishes no intervening dependency call between successful second advancement and evaluation of these arguments. It does not establish the relative evaluation order of the two arguments.

After F-f3f729ad60be returns, the function invokes F-8aad945a5dcd with:

1. Contents read from the second output location during argument evaluation.
2. An integer obtained by reading one character-sized byte at an address formed from contents read from that output location plus `0x10`, or 16 bytes.

These are fresh uses of the output location after F-f3f729ad60be returns. That dependency may have changed the location through retained access or another alias. Consequently:

- The byte read need not use the address passed to F-f3f729ad60be.
- F-8aad945a5dcd need not receive the same address-like value as F-f3f729ad60be.
- Keeping the originally supplied object readable is insufficient if the output location now identifies different storage.

The representation does not establish the evaluation order between F-8aad945a5dcd’s first argument and its byte-derived argument. If the output location remains stable throughout that expression, both uses obtain the same contents. Behavior under concurrent or otherwise externally induced changes during evaluation is not established.

The byte read occurs after F-f3f729ad60be returns and before F-8aad945a5dcd is invoked. Thus changes to the ultimately selected byte made by the earlier call can affect the integer argument.

Character signedness remains unresolved. Bytes below `0x80` convert to their corresponding nonnegative integer values. For bytes `0x80` through `0xFF`, the evidence does not decide signed versus unsigned extension. For example, `0xFF` may become −1 or 255.

After F-8aad945a5dcd returns, the next paired attempt begins with first-state advancement.

This happens regardless of which advancement returned zero, including immediate failure of the first advancement.

The function then repeatedly invokes F-6e4651b532dc with the second state and the address of the second output location:

No pair-processing dependency is called during this phase. The function performs no direct membership check, duplicate suppression, or exclusion of values previously processed as pairs.

The traversal might revisit prior values, continue from a position, or reflect changes made by earlier callbacks. Those semantics belong to the dependencies and remain unresolved.

### Field exchange

After the second-only traversal returns zero, the function performs these direct accesses in order:

1. Reads the current four-byte field at offset `0xA8` and retains its value.
2. Reads the current four-byte field at offset `0xAC`.
3. Writes the value from the second read to offset `0xA8`.
4. Writes the retained value to offset `0xAC`.

The exchange uses the field contents present at this late stage, not necessarily the initialization values.

No dependency call occurs between these accesses. Atomicity and synchronization are not established. Without intervening external changes, the interval between the two writes has both fields containing the value read from offset `0xAC`.

These writes are defined by their addresses relative to the input object. If those addresses overlap an object referenced through an output location, the exchange also writes into that object. Disjointness is not established.

### Finalization

The function then returns without a value. No direct field restoration follows either call. If finalization changes the fields indirectly, those changes are not undone by this function.

## Side effects

### Direct accesses

The established direct object accesses are:

- Initialization-time reads of the two four-byte input fields.
- A one-byte read for each successfully processed pair, using post-F-f3f729ad60be contents of the second output location.
- Late reads of both four-byte input fields.
- Writes to the input-relative addresses at offsets `0xA8` and `0xAC`.

The function also reads output-location contents to construct dependency arguments and supplies local state and output storage to dependencies.

It is not valid to conclude that the function never writes into an object identified by an output value. Its explicit object writes target the two input-relative fields; whether those addresses also belong to an output-referenced object depends on aliasing.

### Dependency-mediated effects

No supplied dependency body establishes preservation of globals, input fields, output locations, backing storage, or yielded objects.

A dependency may retain an output-location address and later use it. This possibility matters across both advancement calls and processing calls. The function provides no snapshot or isolation mechanism.

For normal execution, the address actually selected for the byte read must remain readable at that read. Readability of an earlier address alone does not satisfy this requirement. Continued traversal also requires compatibility between any callback mutations and the later state operations.

### Ownership and lifetime

The temporary states and output locations are local to the invocation. The function contains no explicit heap allocation or heap release.

The finalization calls establish call order, not resource-release semantics. Neither F-944b595e25e9 nor F-fe8fbcac931c is established to free, destroy, retain, or transfer ownership of anything.

Whether dependencies retain local-storage addresses is unknown. Any use beyond the invocation’s lifetime would require a lifetime arrangement not established here.

### Errors and termination

Zero advancement results end phases. The caller does not distinguish exhaustion from an error represented by zero.

There is no explicit recovery for invalid addresses, incompatible state, arithmetic failure, callback failure, or abnormal control transfer. Other dependency results do not control the visible branches.

Field exchange and finalization occur only if preceding operations return normally and the traversals terminate. An indefinitely successful advancement sequence can prevent both.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, dependencies return normally and no concurrent changes occur.

### Immediate first-state termination

If the first advancement returns zero, the paired phase makes no second advancement and no pair-processing calls. The second state is still repositioned and traversed alone. After that traversal terminates, the current fields are exchanged and finalization runs second state first.

### First success followed by second failure

If the first advancement succeeds and the second returns zero, neither pair-processing dependency is invoked for that attempt. The first advancement is not reversed. Repositioning follows.

### Second advancement changes the first output

Suppose the first advancement leaves address A in its output location. The second advancement succeeds and, through retained access, replaces that first output with C while leaving B in the second output.

F-f3f729ad60be receives B and C plus 20, not B and A plus 20.

### Pair processing redirects the second output

Suppose F-f3f729ad60be receives B, then changes the second output location to C. If that location remains C during the following argument evaluations, F-8aad945a5dcd receives C and an integer derived from the byte at C plus 16.

The continued readability of B does not change this result.

### Pair processing changes the selected byte

Suppose the second output location remains B throughout both processing-call argument evaluations. F-f3f729ad60be changes the byte at B plus 16 from 3 to 7, and that byte remains readable.

F-8aad945a5dcd receives B and 7. Without the output-location stability condition, this conclusion is not established.

### Repositioning revisits prior values

If the second-only traversal presents two values previously used in pairs, F-fe8fbcac931c is called for each current output value. Earlier pair processing does not exclude them.

### Callbacks change the fields

If dependencies leave C at input offset `0xA8` and D at `0xAC` before the exchange, the direct writes leave D at `0xA8` and C at `0xAC`, absent intervening changes. Later finalization effects remain possible.

### Output-referenced storage aliases the input

If an output-referenced object overlaps the input field at `0xA8`, the exchange’s write to that field also modifies that object’s storage. No nonaliasing exemption is implied by the traversal terminology.

### Equal fields and high-bit bytes

Equal field contents do not suppress either exchange write or any dependency call.

If the selected byte is `0x80`, whether its integer interpretation is 128 or −128 remains dependent on unresolved character signedness.
