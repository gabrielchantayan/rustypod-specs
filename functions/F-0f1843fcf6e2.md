# F-0f1843fcf6e2

## Purpose

F-0f1843fcf6e2 resolves a 32-bit selector using a context-backed entry collection and, when no entry matches, a relative-offset table.

A normal return has one of two sources:

- A matching entry supplies its stored 32-bit value directly.
- Otherwise, two bytes selected from backing storage supply an unsigned relative offset, which is added to the backing base.

Entries are visited from highest index to lowest. Some nonmatching entries reduce the working selector by one. Subsequent comparisons and fallback indexing use that adjusted selector, not necessarily the original input.

**Inferred intent:** The entries may represent exceptions to an otherwise indexed relative-offset lookup. This interpretation establishes no additional requirements concerning sorting, valid selector ranges, object types, ownership, or allocation boundaries.

### Context layout

Offsets below are byte offsets from the context address.

| Offset | Read width | Meaning |
|---|---:|---|
| `0x02` | 8 bits | Unsigned entry count |
| `0x0E` | 16 bits | Unsigned displacement locating the fallback offset table |

Entries have an eight-byte stride. For each visited entry, the function reads its two-byte key. It reads that entry’s four-byte result only upon a match. The remaining two bytes of a nominal entry are not explicitly consumed as entry data.

## Behavior

### Descending traversal

The function reads the entry count once.

A zero count reaches fallback without reading an entry key or result. Otherwise, traversal starts at index count minus one and proceeds toward index zero.

At each visited entry, its unsigned 16-bit key is extended to 32 bits without changing its numeric value. The comparison uses a signed interpretation of the current 32-bit selector; every extended key remains nonnegative.

| Condition at the visited entry | Required behavior |
|---|---|
| Signed selector is less than the key | Continue to the next lower entry without changing the selector |
| Current selector equals the key | Read and return this entry’s stored 32-bit result |
| Signed selector is greater than the key | Reduce the selector by one, then continue to the next lower entry |

Equality compares the complete current 32-bit selector with the extended key. It is not a low-16-bit comparison.

A match ends traversal immediately. Lower-index keys and results are not read. The stored result is returned without decoding, adding the backing base, or dereferencing it.

A reduction can create a match at a lower entry. Replacing this behavior with a search for the original selector would change the contract.

There is no visible sorting or uniqueness requirement. If the current selector matches a higher-index entry, that entry wins even if a lower entry has the same key.

### Selector boundaries

Selectors from `0x80000000` through `0xFFFFFFFF` have negative signed interpretations under the recovered model. Since every key is nonnegative, such selectors:

- Compare as less than every key.
- Never match.
- Never decrease.
- Reach fallback with their original bit pattern.

Unsigned ordering would produce different behavior and is not interchangeable with the observed signed comparison.

For selectors from zero through `0x7FFFFFFF`, reductions cannot underflow. A reduction occurs only when the selector is greater than a nonnegative key, so the selector must be at least one before that reduction.

There can be at most one reduction per visited entry and at most count reductions overall. Exhausting the collection does not itself reduce the selector.

### Fallback selection

Fallback occurs when the count is zero or all entries have been visited without a match.

The function first reads the backing base from context offset `0x44`. It then reads the unsigned 16-bit table displacement from offset `0x0E`.

The current selector determines a two-byte slot. Its combined displacement is:

\[
D = \bigl(2S + T\bigr) \bmod 2^{32},
\]

where \(S\) is the current selector and \(T\) is the unsigned table displacement.

Both doubling and displacement addition use unsigned 32-bit arithmetic. Either operation can discard excess high bits.

The resulting 32-bit displacement is held in a signed intermediate for the backing-byte address expressions. Subject to valid target address arithmetic, the selected bytes are at the backing base plus that displacement and at the immediately following address.

The lower-addressed byte supplies the high eight bits of the decoded offset; the following byte supplies the low eight bits:

\[
R = 256H + L.
\]

The decoded relative offset is unsigned and ranges from zero through 65,535.

The return value is the 32-bit sum of the backing base and this decoded offset. The table displacement affects the selected byte pair, but **does not contribute directly to the returned address**.

A decoded offset of zero returns the backing-base bit pattern. A decoded offset of `0xFFFF` adds 65,535, not negative one. The function does not read from the resulting destination.

### Arithmetic guarantees and limits

The arithmetic stages have different guarantees:

1. **Selector reduction:** Unsigned subtraction by one, reached only when the selector is positive under the signed comparison. It cannot underflow on that path.
2. **Slot displacement:** Unsigned 32-bit doubling and addition, with modulo-\(2^{32}\) wraparound.
3. **Effective addresses:** The recovered expressions use signed arithmetic for the backing-byte addresses. Portable behavior when those expressions overflow is not established.
4. **Final result:** Unsigned 32-bit addition of the decoded offset and backing-base bit pattern, with modulo-\(2^{32}\) wraparound.

Conversion of a high-bit-set final value through the signed return type depends on the recovered target’s conversion conventions. It does not create a separate error indication.

Defined unsigned displacement wraparound must not be treated as proof that arbitrary effective-address overflow is valid. Addressability, alignment, and target-specific pointer interpretation remain separate requirements.

## Side effects

### Observable reads

The visible control flow establishes this logical ordering:

1. Read the count.
2. Read visited keys in descending index order.
3. On a match, read that entry’s result and return.
4. Otherwise, after traversal ends, read the backing base.
5. Read the table displacement.
6. Read the selected backing-byte pair and compute the result.

Results of nonmatching entries are not explicitly read.

The backing bytes have fixed positional significance, but the expression does not establish which of the two byte loads executes first. High-byte-first decoding is not a promise of high-byte-first access.

Because access roles overlap, avoiding fallback does not necessarily avoid the physical bytes occupied by fallback metadata. For example, visiting entry 5 reads bytes also used by the backing-base field.

These observations describe the body’s logical accesses. They do not establish instruction-level, speculative, bus-level, or volatile-memory behavior.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless an example explicitly discusses an arithmetic boundary, all reached addresses are assumed readable and all effective-address calculations are assumed valid without signed overflow.

### Empty collection

Given count zero, selector 3, table displacement `0x10`, and backing base `0x10000000`, the selected byte addresses are `0x10000016` and `0x10000017`.

If those bytes are `0x12` and `0x34`, the decoded offset is `0x1234` and the result is `0x10001234`.

No entry key or result is read. The table displacement is not added to the returned result.

### Immediate match

Given one entry with key 7, selector 7, and stored result `0xF1234567`, the result has that same 32-bit pattern.

No fallback-specific metadata or backing-byte reads occur. The result’s negative signed interpretation is not an error indication.

Whether receiving that value transfers ownership remains unspecified without external contract evidence.

### Reduction creates a match

Given count 3 and initial selector 5, let the keys at indices 2 and 1 be 2 and 4.

Index 2 reduces the selector to 4. Index 1 then matches and supplies its stored result. Index zero is not examined.

### Larger key preserves the selector

Given count 2 and selector 3, let index 1 have key 9 and index zero have key 3.

The first visit leaves the selector unchanged. Index zero matches selector 3.

### Exhaustion uses the adjusted selector

Given count 2, initial selector 5, and keys 1 and 2 at indices 1 and zero, both visits reduce the selector.

Fallback uses selector 3. Its slot begins six bytes beyond the table displacement, not ten.

### Equality uses all 32 bits

Given one entry, selector `0x00010000`, and key zero, there is no match despite equal low 16 bits.

The selector decreases to `0x0000FFFF`, and fallback uses that reduced value.

### Duplicate keys favor the first reached match

Given two entries with key 7 and selector 7 upon reaching the higher-indexed entry, that entry supplies the result. The lower duplicate is not examined.

### High-bit selector and multiplication wraparound

Given selector `0x80000000`, every visited entry is skipped without reduction.

Doubling the selector in 32-bit unsigned arithmetic yields zero. With table displacement `0x10`, fallback selects the bytes at backing base plus `0x10` and the following address, subject to valid address arithmetic.

### Displacement addition wraparound

Given selector `0xFFFFFFFF`, every key is skipped and the selector remains unchanged.

Doubling yields `0xFFFFFFFE`. Adding table displacement 2 wraps the combined displacement to zero. Fallback selects the bytes at the backing base and its following address.

### Byte order and unsigned offset

A selected pair containing `0x01` followed by `0x02` supplies offset `0x0102`, not `0x0201`.

A pair containing `0xFF` followed by `0xFF` supplies offset 65,535. It is not a signed negative offset.

### Final result wraparound

If a valid fallback read decodes offset `0x20` and the backing-base bit pattern is `0xFFFFFFF0`, final unsigned addition produces `0x00000010`.

This condition does not establish that the result points to valid storage or that any overflowing signed effective-address expression is permitted.
