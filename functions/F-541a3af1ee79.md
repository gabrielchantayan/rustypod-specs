# F-541a3af1ee79

## Purpose

F-541a3af1ee79 validates a requested 32-bit state for a selector and category, compares it with a stored state word, and conditionally replaces that word. For selected categories, it sends one notification for each changed bit within a category-specific range.

Every accepted request that completes normally also invokes an object finalizer and checks whether to invoke completion dependencies. This occurs even when the captured state is unchanged or no bit notifications are emitted.

The state update, notification delivery, and completion processing are distinct effects. No transactional relationship, rollback, synchronization guarantee, or application-level meaning is established.

This contract distinguishes:

- **Established:** behavior supported by the supplied static representation.
- **Inferred intent:** plausible interpretation that adds no contractual guarantee.
- **documented_only:** unresolved details requiring additional evidence.

No runtime tests have been performed.

## Interface

### Inputs

| Input | Width and interpretation | Role |
|---|---|---|
| Selector | Signed 32-bit integer | Controls an initial comparison and contributes to the record address. |
| Category | Unsigned 32-bit integer | Selects a rejection mask, notification class, notification range, and record offset. |
| Requested state | Unsigned 32-bit integer | Supplies the validation bits, replacement word, and notification values. |

There are no explicit pointer arguments or output buffers.

### Return value

The function returns a 32-bit quantity:

- **4:** the initial selector/category condition fails, or the requested state intersects the selected rejection mask.
- **0:** the request passes validation and execution completes normally.

No separate status distinguishes an unchanged state, a changed state, notifications outside the examined range, or suppressed completion processing. The visible dependency results do not select a different normal return value.

These numeric values are established; their application-level error names are **documented_only**.

### Preconditions for safe completion

Passing validation does not establish memory safety. Normal completion requires:

- Valid shared configuration storage whenever it is read.
- A readable selected state word and, when the captured difference is nonzero, writable state storage.
- An initializer that establishes a usable indirect-operation target in the local temporary object.
- Valid completion-object addresses for whichever field reads are actually performed.
- Dependencies that satisfy the required calling and storage-lifetime conditions and return normally.

The selector comparison supplies no lower bound. Negative selectors can pass and affect address calculation. Their safe operating range is **documented_only**.

Completion processing can use two different object bases. Validity of the object used for the branch check does not establish validity of the earlier captured object used for the eventual completion argument.

## Behavior

### 1. Initial validation

The request proceeds only if:

- The signed selector is less than 3.
- The unsigned category is less than 135.

Otherwise, it returns 4 without initializing the local object, selecting or reading the state record, sending notifications, or checking completion state.

A negative selector satisfies the visible selector condition. An unsigned category with its high bit set is greater than 134 and is rejected.

### 2. Category parameters and rejection mask

The initial parameters are a rejection mask of `0xFFFFFFFF`, a notification class byte of `0xFF`, and a notification bit count of zero.

The following categories replace those defaults:

| Category | Rejection mask | Class byte | Examined bit positions |
|---|---:|---:|---|
| 0 | `0xF8000000` | `0x00` | 0–26 |
| 2 | `0xFFFFFF00` | `0x01` | 0–7 |
| 3 | Unknown shared 32-bit value | `0x02` | 0–12 |
| 4 | Unknown shared 32-bit value | `0x03` | 0–19 |

Validation succeeds exactly when the bitwise intersection of the requested state and the selected rejection mask is zero.

Consequently:

- Category 0 admits precisely the requests with bits 27–31 clear.
- Category 2 admits precisely the requests with bits 8–31 clear.
- Categories 3 and 4 depend on shared values whose contents are unavailable.
- Every other category below 135 admits only requested state zero.
- Requested state zero passes this mask condition for every category.

A mask rejection returns 4 before object initialization or record access. Categories 3 and 4 can nevertheless require a shared-mask read before rejection.

The notification range does not define the rejection mask. In particular, the unknown masks for categories 3 and 4 must not be replaced with masks inferred from their notification counts.

### 3. Initialization and record addressing

After successful validation, F-7a117b899bf6 receives the address of an eight-byte local temporary object.

Record addressing occurs afterward. The record address combines:

- A shared base address.
- A shared stride factor multiplied by the signed selector and by 4.
- The unsigned category multiplied by 12.

The state word occupies bytes 8–11 relative to that record address. The remaining eight bytes of the apparent 12-byte category record are not described by the visible accesses.

The selector stride is a shared value, not an established fixed table width. The initializer precedes the address calculation; its preservation of shared addressing configuration is not guaranteed.

The supplied representation uses 32-bit address and arithmetic quantities. No widening, checked multiplication, bounds validation, or alignment repair is visible. Exact overflow semantics and behavior on invalid addresses remain **documented_only**. The signed selector test does not prove that the resulting address is valid.

### 4. State capture before the indirect operation

The function reads the selected 32-bit state word and captures its exclusive-or with the requested state. This difference identifies positions that differed at that read.

Only afterward does it invoke an indirect operation through the initialized temporary object. The operation-table entry is at byte offset 12 in the table referenced by that object. The operation receives the temporary-object address and the selected record address.

The ordering is material:

1. Initialization completes.
2. The record address is calculated.
3. The state word is read and the difference is captured.
4. The indirect operation runs.

The indirect operation runs even when the captured difference is zero. No subsequent state read recomputes that difference.

Any interpretation of the indirect operation as acquiring a lock therefore does not establish protection for the earlier state read. If the operation changes the stored state, the subsequent decision still follows the captured difference.

### 5. Full-word state replacement

When the captured difference is zero, this function performs no explicit state-word store and sends no bit notifications.

When the captured difference is nonzero, it writes the entire requested 32-bit word to the selected state address before sending any notifications. It does not merge only changed bits and does not revalidate the state after the indirect operation.

The write occurs even when:

- The configured notification count is zero.
- All changed bits lie above the notification range.
- The indirect operation has already changed the state.

These statements concern this function’s explicit store. Dependencies may independently mutate state.

### 6. Bit notifications and payload layout

For a nonzero captured difference, examination begins at bit 0 and proceeds upward within the category’s configured count. A notification is sent only when the corresponding captured difference bit is set.

Its value is the requested bit, not the previous stored bit:

- A value byte of 0 reports a requested clear bit.
- A value byte of 1 reports a requested set bit.

Each notification invokes F-c6c589453fa8 with fixed scalar arguments 2 and 0, a pointer to local payload storage, and a byte count of 12.

| Payload offset | Width | Content |
|---:|---:|---|
| 0 | 1 byte | Category-specific class |
| 1–3 | 3 bytes | Not explicitly initialized by this function |
| 4–7 | 4 bytes | Bit position as an unsigned 32-bit quantity |
| 8 | 1 byte | Requested bit value, 0 or 1 |
| 9–11 | 3 bytes | Not explicitly initialized by this function |

For each emitted notification, the visible payload writes occur in this order: value byte at offset 8, class byte at offset 0, then position word at offset 4. The dependency is called after those writes.

The same local payload storage is reused. The six unspecified bytes are not promised to be zero, stable between calls, or meaningful. Their contents may reflect prior storage contents or dependency effects. Byte order of the position word is **documented_only**.

After each examined position, the remaining captured difference and remaining requested bits are logically shifted right by one. Examination stops when the configured count is exhausted or no difference bits remain.

Thus:

- Notification positions are strictly ascending.
- Maximum notification counts are 27, 8, 13, and 20 for categories 0, 2, 3, and 4.
- Other categories send no notifications.
- Changed bits above the configured range are not reported, although the full-word replacement has already occurred.

### 7. Finalization and completion-base reads

After state processing, F-ec22bd8215d3 receives the temporary-object address. This call also occurs when the captured difference was zero.

Completion processing then performs **two separate reads of the same shared completion-base global**, in this order:

1. The first base value is captured for possible later use.
2. The global is read again, independently. The signed 32-bit field at byte offset 24 from this second base controls the completion branch.

The two base values are not established to be equal. No dependency call intervenes between those two global reads, but no stability or concurrency guarantee is supplied.

If the branch-controlling field equals −1, the result provider and completion consumer are skipped. In particular, no field read through the earlier captured base is required on this branch.

Otherwise:

1. A result-provider dependency whose opaque ID is unavailable is invoked with no explicit arguments.
2. After it returns, a 32-bit field is read at byte offset 24 from the **first, captured base**.
3. F-8becc2a0337c receives the provider’s 32-bit result and that field’s 32-bit contents.

There is no refresh of the captured base after the provider call and no second sentinel check before the consumer call.

The branch-controlling field and the consumer-argument field may therefore belong to different objects. The later field may contain the −1 bit pattern without suppressing F-8becc2a0337c. Changes to the shared completion-base global during the provider call do not redirect the later field read.

## Side effects

### Observable ordering

On a normally completing accepted path, the established sequence is:

1. Initialize local temporary storage.
2. Calculate the record address and read its state word.
3. Invoke the indirect operation.
4. If the captured difference is nonzero, replace the state word and send eligible notifications.
5. Finalize the temporary object.
6. Read and capture the completion-base global.
7. Read that global again and inspect the field through the second base.
8. If enabled, invoke the provider, read the argument field through the first base, and invoke the completion consumer.

Rejected requests do not reach this sequence. Category-mask rejection may still have read a shared mask.

### Ownership and lifetime

The temporary object and notification payload are function-local storage. No explicit heap allocation, deallocation, or ownership transfer appears.

The initializer/finalizer pairing does not prove resource acquisition, locking, or release semantics. Passing the record address does not establish transfer of the record.

The payload pointer is not guaranteed to remain usable after return, and its storage is reused before return. Whether F-c6c589453fa8 copies, retains, or mutates the payload is **documented_only**. Any deferred-use guarantee requires an additional dependency contract.

### Failure and concurrency

No explicit atomic operation, retry, rollback, or dependency-failure recovery is visible.

A notification occurs after the state replacement; no visible mechanism reverses that replacement if delivery fails. A dependency that fails to return normally can prevent later notifications, finalization, completion, or the normal return.

Dependencies are not assumed to preserve globals, records, payload bytes, or completion fields. External changes between memory reads are likewise not ruled out. The separate completion-base reads must not be collapsed into a single stable-object assumption.

## Acceptance examples

These are conditional criteria derived from static evidence, not executed tests. Accepted-path examples assume valid accessed addresses and normally returning dependencies.

1. **Selector boundary.** Selector 3, category 0, request zero returns 4 without dependency calls. A negative selector is not rejected by this comparison, but safe addressing is not guaranteed.

2. **Unsigned category boundary.** Selector 0 and category 135 return 4 for any request. The same applies to every larger unsigned category.

3. **Known mask boundaries.** Category 0 accepts `0x07FFFFFF` and rejects `0x08000000`. Category 2 accepts `0x000000FF` and rejects `0x00000100`, assuming the selector passes.

4. **Unknown masks.** Categories 3 and 4 accept zero. Acceptance of a particular nonzero request is conditional on its intersection with the corresponding shared mask being zero; the notification count alone cannot decide acceptance.

5. **Default category.** Category 1 rejects request 1 and accepts request zero. If its captured state is nonzero, the accepted request writes zero and emits no bit notifications.

6. **Notification order and values.** For category 2, a captured state of `0x00000002` and request `0x00000005` produce a difference of `0x00000007`. The full word is first replaced with `0x00000005`; notifications then report class 1 at positions 0, 1, and 2 with values 1, 0, and 1.

7. **Unchanged capture.** If the captured state equals an accepted request, the indirect operation and finalizer still run, followed by completion processing. This function performs no state replacement or notification.

8. **Change outside the examined range.** For category 2, captured state `0x80000000` and request zero cause a full-word write of zero but no notifications.

9. **Indirect mutation does not change the captured decision.** If the captured state equals the request and the indirect operation subsequently changes that state, this function does not restore the request.

10. **Same-base completion mutation.** Assume both completion-base reads return the same object. If its branch-controlling field is not −1 and the provider then changes that object’s offset-24 field to −1, F-8becc2a0337c still runs with the provider result and the reread −1 bit pattern.

11. **Different completion objects.** Suppose the first base read identifies object A and the second identifies object B. If B’s offset-24 field is not −1, the provider runs. If it changes A’s offset-24 field, the consumer receives that changed field from A, not B’s branch-controlling value. A provider change to the global base does not redirect this read.

12. **Different-base suppression.** With first base A and second base B, if B’s field is −1, completion dependencies are skipped regardless of A’s field. No offset-24 field read through A is required by this branch.
