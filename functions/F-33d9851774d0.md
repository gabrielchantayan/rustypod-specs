# F-33d9851774d0

## Purpose

F-33d9851774d0 performs indirect dispatch through a table associated with an embedded region of a caller-supplied object. A selector determines whether dispatch consists of one invocation or a three-invocation sequence.

The established behavior is:

- Invoke dependency F-d3bd01f9a5fa before inspecting the object or selector.
- Resolve an indirect target through the object’s embedded region.
- If the selector equals exactly 3, issue two invocations with distinct ordinal values and distinct addresses within the enclosing object.
- Issue a final invocation with ordinal 2 for that selected case, or ordinal 0 otherwise.

The observed arrangement is consistent with operations on an embedded interface or subobject. That interpretation is inferred intent, not an established object model. The meanings of the ordinals and the addressed storage are unknown.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

### Inputs

The recovered interface has two input values:

| Input | Established use |
|---|---|
| Enclosing-object address | Used to locate an embedded dispatch region and to form two additional addresses within the enclosing object. |
| Selector address | Dereferenced once to obtain the value compared with 3. |

The enclosing-object address is represented as an integer in the recovered interface. Its use is address-like; no scalar interpretation of that input is otherwise visible.

The selector address designates an integer-sized value. The recovered representation uses a 32-bit integer model. The comparison is against exactly 3, with no masking, range check, or conversion to a Boolean.

The interface has no explicit size, capacity, ownership flag, or error-output parameter.

### Address layout

The following offsets are relative to the enclosing-object address:

| Offset | Role visible in this function |
|---|---|
| 0xA8, decimal 168 | Address of the embedded dispatch region; also the receiver supplied to every indirect invocation. |
| 0xE8, decimal 232 | Address supplied as the third argument of the second invocation on the selector-equals-3 path. |
| 0xEC, decimal 236 | Address supplied as the third argument of the first invocation on the selector-equals-3 path. |

The first address-bearing word at the embedded region is treated as a dispatch-table address. A callable target is then read at byte offset 0x3C, decimal 60, from that table address.

These are byte offsets, not indices scaled by the size of an integer or pointer.

The two addresses at offsets 0xE8 and 0xEC are passed onward; this function does not directly read or write the storage they identify. Their spacing does not establish their types, extents, or access direction.

### Outputs and return

No result value is explicitly returned by the recovered interface. Results of dependency invocations are not inspected or propagated as explicit return values.

Any externally visible result must therefore arise through dependency behavior or other effects of executing the calls. The function itself exposes no success/failure status.

## Behavior

### 1. Initial dependency invocation

The first visible action is an invocation of F-d3bd01f9a5fa with no explicit arguments in the recovered representation.

No object-table read or selector dereference appears before this invocation.

The function does not inspect a result from this dependency. Its effects are unknown. In particular, it must not be assumed to preserve global state, the selector’s contents, the dispatch region, or other reachable memory.

### 2. Initial indirect-target resolution

After the initial dependency returns, the function:

1. Reads the table address stored at the enclosing-object address plus 0xA8.
2. Reads a callable target at that table address plus 0x3C.
3. Retains that target for the next applicable invocation.

Both reads occur before the selector is dereferenced.

The target retained here is used for the first indirect invocation on either branch. There is no additional table lookup between the selector comparison and that first invocation.

Consequently, target selection depends on memory as observed after F-d3bd01f9a5fa, not necessarily on the state at function entry.

### 3. Selector observation

The function reads the integer at the selector address and compares it with 3.

There is one explicit selector read. Subsequent dependency effects do not trigger a second selector evaluation or a branch change.

The outcomes are:

- Exactly 3: execute the three-invocation path.
- Any other represented integer value: execute the single-invocation path.

No other selector value receives a distinct path.

### 4. Three-invocation path

When the observed selector equals 3, the function performs the following sequence.

**First invocation**

The initially retained target receives three explicit arguments:

1. The enclosing-object address plus 0xA8.
2. The ordinal value 0.
3. The enclosing-object address plus 0xEC.

The third argument is the address itself, not a value read from that location.

**Second target resolution and invocation**

After the first invocation returns, the function reads the table address from the embedded region again and reads the callable target at table offset 0x3C again.

That newly resolved target receives three explicit arguments:

1. The enclosing-object address plus 0xA8.
2. The ordinal value 1.
3. The enclosing-object address plus 0xE8.

The first invocation may therefore influence which target receives the second invocation. The function does not require the table address or target to remain unchanged.

**Third target resolution and final invocation**

After the second invocation returns, the function again reads the table address from the embedded region and resolves the target at table offset 0x3C.

The final invocation supplies two explicit arguments:

1. The enclosing-object address plus 0xA8.
2. The ordinal value 2.

No third argument is explicitly supplied for this final invocation in the recovered representation. It must not be specified as a null address, either previously supplied field address, or an inherited argument.

Thus, the selected path has three target resolutions and three indirect invocations, with ordinal order 0, 1, 2. The address-bearing arguments occur in descending offset order: 0xEC first, then 0xE8.

### 5. Single-invocation path

When the observed selector is not 3, the function uses the initially retained target without another table lookup.

It supplies two explicit arguments:

1. The enclosing-object address plus 0xA8.
2. The ordinal value 0.

Neither additional field address is supplied as an explicit argument on this path. The function does not directly access the storage at either field address.

### 6. Completion and abnormal execution

The recovered representation shows completion after the final indirect invocation, with no subsequent explicit work.

There is no visible retry, fallback target, error-status interpretation, null check, or local recovery mechanism. If an invoked dependency does not return, faults, or otherwise transfers control away, the later operations described above are not established as occurring.

The exact low-level return behavior of the final indirect transfer remains uncertain because its call/transfer structure was not fully recovered.

## Side effects

### Direct effects

The visible body performs memory reads and dependency invocations. It contains no explicit stores to the object, the selector, or global storage.

It contains no explicit allocation, deallocation, reference-count update, or ownership-transfer operation.

The explicit memory-read order is significant:

- Initial dependency invocation precedes all relevant reads.
- Initial table-address and target reads precede the selector read.
- On the three-invocation path, each later table resolution follows completion of the preceding indirect invocation.

These describe the recovered operation order, not a hardware memory-ordering guarantee.

### Dependency-mediated effects

The function supplies an embedded-region address to every indirect target. On the selected path, it additionally supplies two addresses within the enclosing object.

The targets’ access rights and actions are unknown. They may read or modify reachable state, but this function does not establish that they do so. In particular, the supplied addresses cannot be classified as output buffers solely from their position in the invocation.

No preservation or lifetime guarantee is established for any dependency. Whether dependencies retain addresses, release resources, modify globals, or invalidate later accesses is documented_only.

Aliasing is not prohibited by a visible check. If the selector overlaps dispatch-related storage, behavior depends on the values read at the specified points; the function provides no special alias-handling path.

## Acceptance examples

These examples are conditional static acceptance criteria, not reports of executed tests.

### Selector other than 3

Given a normally returning initial dependency, a readable selector containing 0, and a valid initial target:

- The initial dependency occurs first.
- One table resolution occurs before the selector read.
- One indirect invocation receives the embedded-region address and ordinal 0.
- No explicit third argument is supplied.
- No later table resolution occurs.

The same branch applies to represented values such as 2, 4, and −1.

### Selector exactly 3 with stable dispatch state

Given a selector observed as 3 and dependencies that return normally without changing dispatch state:

- Three indirect invocations occur.
- Their ordinals are 0, 1, and 2, in that order.
- Their receiver is always the enclosing-object address plus 0xA8.
- The first invocation additionally receives the address at offset 0xEC.
- The second additionally receives the address at offset 0xE8.
- The third has only two explicit arguments.
- The dispatch slot is resolved separately for each invocation.

### Initial dependency changes the selector

Given that the selector contains 0 at entry but F-d3bd01f9a5fa changes it to 3 before returning, the three-invocation path is selected, provided intervening accesses succeed.

Entry-time selector contents do not determine the branch independently of the initial dependency.

### First indirect invocation changes dispatch state

Given selector 3, if the first indirect invocation replaces the table address or changes the relevant slot, the second invocation uses the newly resolved target.

Likewise, a change during the second invocation affects the target resolved for the final invocation.

### First indirect invocation changes the selector

Given that the selector was read as 3, changing it during the first invocation does not switch to the single-invocation path. No selector reread is present.

### Invalid dispatch state with an otherwise readable selector

A readable selector does not bypass an invalid initial table access. Initial target resolution precedes selector observation on both branches.

No particular exception, signal, or fault response is specified.
