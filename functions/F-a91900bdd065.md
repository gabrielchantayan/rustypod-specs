# F-a91900bdd065

## Purpose

F-a91900bdd065 exposes a partially recovered, conditionally executed memory-update sequence. Its established behavior consists of:

- Testing a 32-bit control input.
- Optionally updating two memory locations and invoking F-586bc972b85f.
- Using a byte from a stack-associated value to select two very low memory addresses for 32-bit writes.
- Reaching a boundary where ordinary execution could not be recovered.

The available evidence does **not** establish a successful return, a conventional error result, or a complete end-to-end operation. A further indirect invocation appears in the recovered representation, but its reachability is doubtful under an ordinary address model.

This contract describes the observable operations supported by the supplied static evidence. It does not treat failed instruction recovery as proof of a particular processor exception, process termination, or intended application behavior.

## Behavior

### 1. Control gating

The control argument is tested first.

If control is zero:

- The context-dependent sequence is skipped.
- The selector-derived memory update is skipped.
- F-586bc972b85f is not invoked by the displayed path.
- The two low-address writes are skipped.
- The later indirect invocation is skipped.
- Execution reaches the final unrecovered-instruction boundary.

No ordinary return or specific fault mechanism can be assigned to that boundary from this evidence alone.

If control is nonzero, execution continues with the context-dependent sequence.

### 2. Optional context-dependent sequence

If the implicit context value is zero, this entire sequence is skipped.

Otherwise, let the effective selector be the selector’s low 12 bits. Its range is 0 through 4095. The derived base address is the effective selector multiplied by 4096.

The sequence has this visible order:

1. Write the 16-bit value `0x4A28` at context address plus `0x3A`.
2. Write the 8-bit value `0xC0` at the derived base address plus `0x1F`.
3. Invoke F-586bc972b85f with four arguments:
   - The stack-associated address at recovered displacement `0x1EC`.
   - The 32-bit constant `0x45000000`.
   - The derived base address.
   - The effective selector shifted left by 10 bits.

The two writes precede the invocation. No rollback is shown if the second write or the invocation fails.

The arithmetic has these established bounds:

- Effective selector: `0x000` through `0xFFF`.
- Derived base: `0x00000000` through `0x00FFF000`.
- Byte-write address: `0x0000001F` through `0x00FFF01F`.
- Fourth dependency argument: `0x00000000` through `0x003FFC00`.

These selector-derived calculations do not overflow a 32-bit value. Selector bits above bit 11 have no displayed effect on this sequence.

The context-address addition is different: its safety depends on the context value and the actual machine’s address arithmetic. No bounds or overflow check is visible.

No result from F-586bc972b85f is visibly inspected. Subsequent behavior requires that the invocation return and leave execution able to continue. Its effects on memory, registers, stack-associated values, or global state are not supplied and must not be assumed absent.

### 3. Stack-derived low-address writes

After the optional sequence, execution uses the upper eight-bit slice of the four-byte stack-associated value at displacement `0x168`. In the recovered scalar representation, this is bits 24 through 31. Denote its unsigned value by B.

Two 32-bit writes follow, in order:

1. Write a 32-bit integer representation of the address of that same stack-associated location to address B shifted right by 5.
2. Write B shifted right by 2 to the next 32-bit position, four bytes beyond the selected address.

Consequently:

- The first destination address ranges from 0 through 7.
- The second destination address ranges from 4 through 11.
- The second stored value ranges from 0 through 63.
- Neither destination is guaranteed to be four-byte aligned.

The second write is displaced by four bytes, not one byte.

The recovered expressions obtain the byte slice at multiple points. The evidence does not justify a stronger guarantee that it is sampled once and retained across all operations. In particular, aliasing, memory-mapped effects, or changes caused by the preceding invocation could matter. The simple formulas above describe the case where the relevant byte remains stable.

The first stored value is a pointer converted to a 32-bit integer in the recovered representation. Its exact bit pattern depends on the execution address model. Target byte order determines how both 32-bit stores appear as individual bytes in memory.

No validation, alignment correction, or recovery branch is shown for either destination. If the first write prevents further execution, the second write is not reached.

### 4. Stack-address comparison and recovery boundary

After the two writes, the recovered representation compares the address of the stack-associated location at displacement `0x168` against zero.

If that address is nonzero, execution reaches an unrecovered-instruction boundary before the displayed indirect invocation.

In a conventional execution model, an accessible stack object has a nonzero address, making this the expected represented branch. That is an inference, not proof of the original machine-level control flow. The evidence contains explicit instruction-recovery and control-flow warnings.

### 5. Questionable indirect-invocation path

Only if the stack-associated address comparison evaluates equal to zero does the recovered representation proceed to a further indirect invocation.

Let V be the 32-bit unsigned stack-associated value at recovered displacement `0x338`. The displayed arguments are:

1. An unsigned byte read from address `(V shifted right by 2) + 1`.
2. V shifted left by 17 bits, retaining the low 32 bits.
3. V shifted right by 2 bits.
4. V shifted right by 4 bits.

The byte-read address ranges from `0x00000001` through `0x40000000`; its addition does not overflow 32 bits. The left shift can discard high bits. It is not an unbounded multiplication.

The byte must be read to supply the invocation argument. Its widening and the full calling convention are not established.

No opaque identifier was supplied for this indirect dependency. Its behavior, ownership rules, and return behavior therefore remain documented_only.
