# F-84e8874bcd0c

## Purpose

F-84e8874bcd0c selects one 20-byte record from a state-managed pool and partially initializes it. Selection prefers a linked list of reusable records. If that list is empty, the function consumes the next record from a contiguous region, obtaining a new region when the current cursor equals its limit.

This pool-management interpretation is **inferred intent**. The established behavior is the sequence of reads, allocations, state updates, and record writes described below.

The function has no explicit return value. In particular, it does not return the selected record’s address. Its externally visible results are memory changes and, on the growth path, two calls to F-871e64ddc6de.

## Interface

The sole argument is an address of mutable state. The supplied representation uses four consecutive 32-bit fields:

| Byte offset | Width | Behavioral role |
|---|---:|---|
| 0 | 32 bits | Address of the current allocation descriptor, or zero |
| 4 | 32 bits | Address of the first reusable record, or zero |
| 8 | 32 bits | Cursor identifying the next contiguous record |
| 12 | 32 bits | Limit compared against the cursor |

These role names describe usage, not independently established type definitions. Addresses are represented as 32-bit values in the supplied evidence. Byte order is not established.

There is no input validation. The argument must address readable state and writable fields for the path taken. Every record, descriptor, or contiguous region subsequently accessed must also provide the required accessible storage. Behavior for invalid addresses is not defined by an explicit error-handling contract.

### Allocation descriptor

When contiguous storage must grow, the function requests a 12-byte descriptor with this layout:

| Byte offset | Width | Value written |
|---|---:|---|
| 0 | 32 bits | State’s descriptor-head value, read after both dependency calls |
| 4 | 32 bits | Newly calculated capacity |
| 8 | 32 bits | Address returned by the second dependency call |

If the state’s descriptor head is nonzero when capacity is calculated, the existing descriptor’s 32-bit field at offset 4 supplies the previous capacity.

The descriptor therefore appears to link allocation blocks. Whether that chain governs ownership or eventual destruction is not established.

### Record layout

Records have a stride of 20 bytes. The selected record is accessed as follows:

| Byte offset | Width | Treatment |
|---|---:|---|
| 0 | 1 byte | Written as zero |
| 1–3 | 3 bytes | Not directly written |
| 4 | 32 bits | Written as zero |
| 8 | 32 bits | Written as zero |
| 12 | 32 bits | Read as a next-record address on the reuse path, then written as zero |
| 16–19 | 4 bytes | Not directly written |

Thus, the function does **not** clear an entire record. It directly clears 13 of its 20 bytes.

### Output

There is no explicit return value, status code, or output argument containing the selected record address. Successful completion leaves the state advanced and the selected record partially cleared.

## Behavior

### 1. Selection priority

The first state read obtains the 32-bit value at offset 4.

If that value is nonzero, it identifies the selected reusable record. The function reads the 32-bit link at that record’s offset 12 and writes that link into the state’s offset-4 field. It then performs the common record initialization.

On this path:

- No contiguous cursor or limit is read.
- No allocation dependency is called.
- The state’s descriptor head, cursor, and limit are not directly written.
- The selected record’s next link is read before that link is cleared.

A reusable record therefore takes precedence even when the contiguous cursor would otherwise indicate exhaustion.

If the initial offset-4 value is zero, the function instead reads the contiguous cursor at state offset 8 and compares it with the limit at offset 12.

### 2. Existing contiguous storage

When the cursor and limit differ, the cursor value is the selected record address. The function writes the selected address plus 20 into the state’s cursor field, then performs the common record initialization.

The test is equality only. There is no ordering comparison, range check, alignment check, or check that 20 writable bytes remain. A cursor beyond the limit, or a cursor with fewer than 20 bytes remaining, is not rejected by this function.

Safe use therefore requires the caller-maintained state to ensure that an unequal cursor and limit identify a valid next record.

### 3. Exhausted contiguous storage

When the cursor equals the limit, the function calculates a new capacity.

If the state’s descriptor head is zero, the capacity is 32 records.

Otherwise, it reads the existing head descriptor’s unsigned 32-bit capacity field. Two unsigned 32-bit candidates are formed:

- The previous capacity plus 32.
- The previous capacity plus its logical right shift by one, plus its logical right shift by three.

The larger candidate under unsigned comparison becomes the new capacity. Equality also selects the second candidate, with no difference in the resulting numeric value.

For values without overflow, the second candidate is the previous capacity plus the integer floors of one half and one eighth of that capacity. It must not be replaced with an unrestricted real-number multiplication by 1.625.

All capacity additions use 32-bit unsigned arithmetic. Overflow wraps modulo \(2^{32}\), and comparison occurs after that wrapping. Consequently, the result is not guaranteed to exceed the previous capacity or to represent a safe allocation size.

### 4. Allocation and descriptor publication

After capacity calculation, the function calls F-871e64ddc6de twice, in this order:

1. First argument 12; second argument zero.
2. First argument equal to the new capacity multiplied by 20 using 32-bit arithmetic; second argument zero.

The first returned value is treated as the descriptor address. The second is treated as the record-storage address.

The subsequent direct memory operations occur in this order:

1. Write the storage address into the new descriptor at offset 8.
2. Read the state’s current descriptor head and write it into the new descriptor at offset 0.
3. Write the calculated capacity into the new descriptor at offset 4.
4. Publish the new descriptor address into the state at offset 0.
5. Read the storage address back from the new descriptor at offset 8.
6. Write the storage address plus the capacity-times-20 byte count into the state’s limit field.
7. Write the storage address plus 20 into the state’s cursor field.
8. Initialize the selected record at the storage address.

The descriptor-head read used to populate the new descriptor’s link occurs **after both dependency calls**. It is not an earlier saved head value. Conversely, the capacity has already been calculated before either call.

The contract cannot assume that F-871e64ddc6de preserves the input state, other globals, or overlapping memory. Any such preservation is an additional dependency precondition, not established behavior of this function.

### 5. Common record initialization

After the selected path updates the pool state, the function performs these direct writes to the selected record, in order:

1. Zero the 32-bit field at offset 4.
2. Zero the 32-bit field at offset 8.
3. Zero the 32-bit field at offset 12.
4. Zero the single byte at offset 0.

Bytes 1–3 and 16–19 are not directly initialized. Existing contents at those positions remain unless another effect, including aliasing or dependency behavior, changes them.

No record field is set to a nonzero “allocated” marker, and the selected address is not explicitly published into a separate active-record field.

### Arithmetic and boundary conditions

The supplied representation uses 32-bit address-bearing fields and unsigned 32-bit size calculations. The storage request’s byte count can wrap independently of the capacity calculation.

Cursor and limit updates use byte displacements of 20 and capacity times 20 respectively. The function contains no explicit protection against address overflow, invalid pointer formation, overlapping allocations, or an allocation smaller than one record. Behavior outside valid accessible storage is not specified by a recovery path.

Zero is a sentinel for an empty reusable list and an absent descriptor head. A zero cursor is not separately rejected. If cursor and limit are unequal, even a zero cursor follows the existing-storage path and is subsequently used as a record address.

## Side effects

### Direct state changes

- **Reuse path:** replace the reusable-list head with the selected record’s link.
- **Existing contiguous-storage path:** advance the cursor by 20.
- **Growth path:** publish a new descriptor head, replace the contiguous limit, and set the cursor one record beyond the newly obtained storage base.
- **Every completing path:** partially clear the selected record.

These are the direct writes. If the state, descriptors, and records overlap, later writes may alter earlier results. The function does not detect or prevent such overlap.

### Allocation, ownership, and lifetime

Only the growth path calls F-871e64ddc6de, and it makes exactly two direct calls.

No release operation is visible. Existing descriptors and storage are not explicitly freed. The new descriptor records a link to the state’s then-current descriptor head, but that link alone does not establish an ownership or reclamation policy.

There is no rollback. State changes occur before record initialization completes. On the growth path, the descriptor is published before the limit and cursor updates and before record clearing. On the reuse path, the reusable-list head is advanced before record clearing.

### Failure handling and concurrency

Returned addresses are not checked for zero or other failure indicators. If the first dependency call returns normally with an unusable address, the second dependency call still occurs before the first descriptor write is attempted.

There is no explicit error return, retry, cleanup, synchronization, or transactional publication. Fault delivery and dependency exceptions are outside the established contract. The ordering described here does not establish atomicity, thread safety, or suitability for concurrent observation.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not runtime test results. Unless otherwise stated, they assume valid, distinct storage, successful dependency calls, and no intervening dependency mutation of the state.

### Reuse takes priority

Given a nonzero reusable-list head identifying a record whose offset-12 link identifies another record:

- The first record is selected.
- The state’s reusable-list head becomes the second record’s address.
- No allocation occurs.
- Cursor and limit remain directly unchanged.
- The selected record receives the four initialization writes in the specified order.
- Its link field is zero afterward.

This remains the selected path even if cursor and limit are equal.

### Reusing the last listed record

Given a nonzero reusable-list head and a zero link at the selected record’s offset 12, the reusable-list head becomes zero before record initialization. Contiguous storage is not consumed during this invocation.

### Consuming existing storage

Given an empty reusable list and a cursor different from the limit, the old cursor identifies the selected record. The cursor advances by 20 before initialization. Neither the descriptor head nor the limit is directly changed.

### Initial growth

Given an empty reusable list, equal cursor and limit, and a zero descriptor head:

- Capacity is 32.
- Dependency requests are 12 bytes and 640 bytes, in that order, each with a second argument of zero.
- The descriptor stores the returned storage base, a zero link under the stated preservation assumption, and capacity 32.
- The state’s limit becomes storage base plus 640.
- Its cursor becomes storage base plus 20.
- The first record in the new storage is partially cleared.

### Capacity selection

For previous capacity 64, the candidates are 96 and 104. The chosen capacity is 104, and the storage request is 2,080 bytes.
