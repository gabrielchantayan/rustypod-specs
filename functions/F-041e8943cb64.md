# F-041e8943cb64

## Purpose

F-041e8943cb64 selects processing according to a primary category and, when that category is `0x13`, a secondary discriminator.

Three secondary values receive explicit handling:

- `0x6219`: invoke two dependencies, then a receiver callback.
- `0x80aa`: expose a working record to a dependency, compare two selected fields with receiver state, and perform update-related calls if either comparison differs.
- `0x80ab`: expose the same working record to a dependency, compare three selected fields with receiver state, and perform update-related calls if the comparison sequence does not establish equality.

Other primary categories are delegated to F-6e38c8351d29. Unrecognized secondary values cause no branch-specific processing.

On normal return, the 64-bit result combines the final first working word with either the constant `1` or the fallback dependency’s result.

These are static observations. “Category,” “record,” “transfer,” and “notification” are descriptive interface roles, not established application meanings. In particular, the final `0x80ab` comparison has unresolved source-subfield signedness and promotion behavior; it is not specified as unconditional equality of two 16-bit patterns.

## Behavior

### Primary category

After initializing the working record, read the 32-bit category at message offset `4`.

If the category is not `0x13`:

1. Invoke F-6e38c8351d29 with the receiver address and message address.
2. Use its 32-bit result as the low result word.
3. Use the final first working word as the high result word.

This path does not explicitly pass the auxiliary or additional word to the fallback dependency. It performs no secondary lookup, selected-field comparison, transfer request, or notification dispatch of its own.

The message-address arithmetic is represented at 32-bit width. No wider calculation or overflow rejection is established.

### Secondary lookup and shared-token capture

For primary category `0x13`, the established sequence is:

1. Invoke F-682adfd5a561 with the message address and `0x0c00`.
2. After that call returns, read a 32-bit shared notification token from global storage.
3. Read the 32-bit discriminator at offset `0x0c` from the returned address.
4. Select a branch using that discriminator.

The shared-token read precedes the discriminator read. It occurs even if the discriminator is unrecognized or the selected branch sends no notifications.

There is no explicit check of the lookup result before reading its discriminator. The captured token is reused by later notification calls; its global source is not explicitly reloaded for each notification.

For an unrecognized discriminator, no further explicit branch operation occurs. Normal return uses low word `1` and the final first working word as its high word.

### Discriminator `0x6219`

Invoke, in order:

1. F-6ac70711bbb5, with no explicit arguments.
2. F-4fd1138799c3, with no explicit arguments.
3. The receiver callback selected through dispatch-table byte offset `0xd8`, passing the receiver address.

The receiver dispatch table for the final call is read after the first two dependencies return. Neither dependency is assumed to preserve receiver state or globals.

This branch performs no explicit working-record decoding, comparison, transfer, associated-object processing, or notification loop.

### Discriminator `0x80aa`

First invoke F-59222578e3f0 with the working-record address.

Then perform these comparisons in order:

1. Numeric bits `23:16` of the first working word against the zero-extended receiver byte at `0x60`.
2. Only if the first comparison is equal, numeric bits `15:8` of the first working word against the zero-extended receiver byte at `0x5f`.

These source extractions are numeric shifts and masks; their meaning does not depend on byte order. A first-comparison mismatch skips the second comparison, including its receiver-byte read.

If both comparisons are equal, skip the transfer, receiver update callback, associated-object processing, and notification loop.

Otherwise:

1. Invoke the transfer dependency with destination receiver plus `0x5e`, source equal to the working-record address, and size argument `10`.
2. Invoke the receiver callback at dispatch-table byte offset `0x58`, passing the receiver address and two 32-bit values read from separate global sources.
3. Perform notification count selection and dispatch as described below.

The two global callback arguments are read after the transfer returns. Their relative evaluation order is not established. Separate sources do not imply different values.

The `0x58` callback completes before the associated-object check. Its effects may therefore alter the subsequently read associated-object address, count, dispatch table, or other reachable state.

### Discriminator `0x80ab`

First invoke F-59222578e3f0 with the working-record address.

The comparison sequence is short-circuited:

1. Compare numeric bits `31:24` of the first working word with the zero-extended receiver byte at `0x61`.
2. If the first comparison is equal, compare numeric bits `7:0` of the second working word with the zero-extended receiver byte at `0x62`.
3. If both preceding comparisons are equal, compare a two-byte source subfield beginning at byte offset `2` within the second working word with the receiver word at `0x64` explicitly narrowed to signed 16 bits.

The third source subfield occupies record offsets `6` and `7`. Mapping it to numeric bits `31:16` of the second word requires a little-endian layout assumption. That mapping is not unconditional.

For the final receiver operand, the representation reads a 32-bit receiver word and explicitly narrows it to signed 16 bits. Under the usual signed 16-bit interpretation, a retained pattern of `0x8000` denotes `-32768`, not `32768`.

The source subfield’s signedness and the comparison’s resulting promotion behavior are unresolved. Consequently:

- Matching source and receiver 16-bit patterns do not unconditionally establish equality.
- If a source pattern of `0x8000` is interpreted as unsigned and promoted to `32768`, while the narrowed receiver operand promotes to `-32768`, the comparison is unequal.
- If both operands instead reach comparison as the signed value `-32768`, they compare equal.

These are conditional interpretations, not a choice of one unresolved source type. No normalization to unsigned bit-pattern equality is specified.

A mismatch in either earlier comparison skips later comparisons and their receiver reads. If all three comparisons evaluate equal under the applicable operand types and conversions, skip update and notification processing.

Otherwise:

1. Invoke the transfer dependency with destination receiver plus `0x5e`, source equal to the working-record address, and size argument `10`.
2. Perform notification count selection and dispatch.

This branch does not invoke the receiver callback at `0x58`.

### Notification count and dispatch

This processing occurs only after a mismatch in `0x80aa` or `0x80ab`, after all preceding branch-specific calls.

Read the associated-object address at receiver offset `0x68`:

- If zero, read the signed 32-bit count at receiver offset `0x2c`.
- If nonzero, select count `3` and invoke the associated object’s callback through its dispatch-table byte offset `0x170`.

The associated-object callback has no explicit arguments in the supplied representation. An implicit receiver convention is not established. Its return value is unused and does not determine the selected count.

After count selection and any associated-object callback, capture a 32-bit branch-specific token from global storage. The two mismatch branches use separate token sources. Their values may nevertheless be equal.

For each signed index beginning at zero and strictly less than the selected count, invoke the receiver callback at dispatch-table byte offset `0x74` with:

1. Receiver address.
2. Shared token captured before the discriminator read.
3. Branch-specific token captured after count selection.
4. Current 32-bit index.

Indices increase in order. A zero or negative count produces no notification calls, but the branch-token read still occurs. A positive count produces exactly that many calls if all calls return normally.

The selected count and captured tokens are not explicitly reloaded during iteration. The receiver dispatch table is accessed for each invocation; no single callback target is cached for the entire loop.

For count `2,147,483,647`, the final delivered index is `2,147,483,646`. The next increment reaches the count and terminates the loop without requiring signed overflow.

## Side effects

The function directly initializes its working record and exposes its address to dependencies. Other nonlocal effects are mediated through calls.

F-59222578e3f0 may modify the record used for comparisons and result composition. The transfer dependency receives both receiver-relative destination storage and the working-record address. Argument roles suggest a transfer, but do not establish exact reads, writes, overlap handling, or source preservation.

Call ordering constrains subsequent observations:

- Transfer precedes count selection.
- In `0x80aa`, the `0x58` callback also precedes count selection.
- The associated-object callback precedes branch-token capture.
- Each notification may affect state read for later indirect dispatch.

Later changes to the shared-token global do not cause an explicit recapture; notifications use the earlier captured value.

No allocation, release, reference-count change, or ownership transfer is explicit. Passing the working-record address does not establish permission to retain it after return. Unknown callees are not assumed to preserve globals, preserve receiver memory, avoid retention, or release memory.

A low result word of `1` indicates the distinguished-category normal-return path. It does not independently certify successful decoding, transfer, or notification delivery.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless otherwise stated, they assume valid memory and normal return from every reached dependency.

1. **Fallback result composition.**  
   With a category other than `0x13`, initial message address `0x10203040`, fallback result `0x55667788`, and unchanged first working word, the result is `0x1020304055667788`. No secondary lookup occurs.

2. **Unrecognized discriminator.**  
   The shared token is read after lookup and before the discriminator access. An unrecognized discriminator causes no decoder or branch callback. The low result word is `1`.

3. **Special-branch ordering.**  
   For `0x6219`, F-6ac70711bbb5 completes before F-4fd1138799c3 begins. Both precede the receiver’s `0xd8` callback.

4. **Two-field equality.**  
   For `0x80aa`, matching selected bytes skip transfer, the `0x58` callback, associated-object processing, and notifications. Differences in unselected record fields alone do not trigger an update.

5. **First mismatch and negative count.**  
   For `0x80aa`, a first-comparison mismatch skips the receiver-byte read at `0x5f`. Transfer and the `0x58` callback occur. If subsequent selection finds no associated object and reads count `-1`, the branch token is captured but no notification occurs.

6. **Associated-object path.**  
   For a mismatching `0x80ab` record, a nonzero associated-object address after transfer selects count `3`. Its `0x170` callback precedes branch-token capture and notifications with indices `0`, `1`, and `2`. No `0x58` callback occurs.

7. **Conditional positive final comparison.**  
   Assume little-endian layout, second working word `0x12340056`, matching earlier comparisons, and receiver word `0xabcd1234`. The source subfield has pattern `0x1234`; the receiver narrows to signed value `4660`. If source interpretation and comparison conversions preserve source value `4660`, the final comparison is equal. Without the layout and conversion conditions, this example does not establish equality.

8. **Same high-bit pattern, conditional mismatch.**  
   Assume the final source subfield and narrowed receiver both have pattern `0x8000`, and earlier comparisons match. If the source is unsigned and promotes to `32768`, while the receiver promotes to `-32768`, the final comparison is unequal. Transfer and count selection follow despite identical 16-bit patterns.

9. **Same high-bit pattern, alternative conditional equality.**  
   With the same patterns and earlier matches, if source interpretation and promotions instead compare signed `-32768` with signed `-32768`, update processing is skipped. The supplied evidence does not select between this case and the preceding case.

10. **Captured tokens and final high word.**  
    Equal values in separate token sources are permitted. If decoding sets the first working word to `0xa1b2c3d4` and later calls leave it unchanged, normal distinguished-category return is `0xa1b2c3d400000001`.

## Evidence

The supplied static representation establishes input widths, working-record initialization, category selection, shared-token capture before discriminator access, explicit call arguments, receiver offsets, short-circuit comparison structure, signed notification bounds, and 64-bit result composition.
