# F-3147708f5aba

## Purpose

F-3147708f5aba searches a grouped table for a record associated with a context-selected identifier and a caller-supplied lookup value. On success, it produces a tagged result containing either a payload-relative address or an unsigned 32-bit value.

The function has two distinct failure mechanisms:

- A preliminary dependency can return a nonzero status that is propagated without searching.
- Once table processing begins, failure to obtain an accepted record returns status 6.

The result tag is initially cleared. A failed search does not initialize the result’s value field.

These are source-established behaviors. Descriptions such as “lookup value,” “payload,” and “group” are inferred roles for the observed data, not independently established application semantics.

### Return value

The supplied representation returns a 64-bit composite:

- Upper 32 bits: the original context argument’s bit pattern.
- Lower 32 bits: the status bit pattern.

Status 0 accompanies a successfully populated result. Status 6 denotes failure after entering table processing. A nonzero preliminary-dependency result is returned unchanged in the lower half when that dependency prevents table processing.

The actual caller-facing ABI interpretation of this composite is not independently established. It must not be simplified to a standalone integer status without additional evidence.

### Preconditions

Normal, defined operation requires readable context fields, valid directory and record storage, and readable selector-bearing data whenever the corresponding path reaches them. Successful paths require writable result storage.

The function does not establish allocation bounds for the table or record area. It also does not independently establish payload validity beyond the specific unsigned comparisons described below.

No non-aliasing guarantee is visible. Ordinary use with separate context, table, payload, and result storage is straightforward; overlapping storage can change later reads and is not safely described as an ordinary independent-output interface.

## Behavior

### Entry and preliminary gate

The function first reads and retains the four-byte selector-data address from context offset `0x58`. It then writes zero to the result tag.

Only after that write does it inspect the context byte at `0x304`.

- If the byte is nonzero, table processing begins without calling F-815f5f2d4275.
- If the byte is zero, F-815f5f2d4275 is called with the context address and the four-byte value read from context offset `0x68`.
- If that call returns zero, table processing begins.
- If it returns nonzero, the function returns that status without searching or writing the result value.

The retained selector-data address is not refreshed after the preliminary call. In contrast, the table-processing context fields are read afterward. Consequently, changes made by that dependency can affect table processing without changing which selector-data address was retained.

### Directory and record layout

The grouped table has an eight-byte leading region that this function does not interpret.

The directory begins eight bytes after the table base. Each directory entry occupies four bytes:

| Entry offset | Width | Meaning |
|---|---:|---|
| `0` | 2 bytes | Identifier, decoded most-significant byte first |
| `2` | 2 bytes | Record count, decoded most-significant byte first |

The record area begins immediately after all directory entries. Its initial address is the directory start plus four times the group count.

Each record occupies ten bytes:

| Record offset | Width | Meaning |
|---|---:|---|
| `0` | 4 bytes | First unsigned quantity, decoded most-significant byte first |
| `4` | 1 byte | Not inspected |
| `5` | 1 byte | Flags and result subtype |
| `6` | 4 bytes | Second unsigned quantity, decoded most-significant byte first |

The first unsigned quantity is used as a payload offset for comparison. The second is either another payload offset or a directly returned value.

### Search eligibility

Table processing establishes default status 6.

The table base and group count are read, and the initial directory and record-area addresses are formed before search eligibility is fully resolved.

A directory search occurs only if:

- The retained selector-data address is nonzero.
- The lookup argument is nonzero.
- F-1cb585febd84, called with the lookup argument, returns a nonzero 32-bit value.

That dependency’s return is subsequently used as the lookup length.

If an eligibility condition fails, status 6 is returned. The result tag remains zero except for possible external or aliasing effects.

### Group selection

Directory entries are examined in order. For each entry, the function reads its record count and compares its identifier with the two-byte value accessed at offset `0x0e` from the retained selector-data address.

For every nonmatching entry:

- The record pointer advances by ten times that entry’s record count.
- The directory pointer advances by four bytes.

The selector value is read during each comparison, rather than captured once before the directory scan.

The first matching entry ends directory selection. Later entries with the same identifier are not considered, even if the selected group has no records or none of its records is accepted.

If no entry matches, the function returns status 6.

The directory identifier is explicitly byte-assembled, while the selector is read through a native two-byte signed access in the supplied representation. Identifier equality for values with the high bit set therefore needs the signedness and target-representation qualification recorded under **Uncertainties**.

### Record selection

Only records belonging to the selected group are examined, in stored order.

For each record:

1. The flag byte at offset 5 is read.
2. A clear `0x10` bit rejects the record immediately.
3. Otherwise, both four-byte quantities are decoded.
4. The first quantity must satisfy the comparison bounds described below.
5. F-fca51b715561 must return zero when called with the lookup argument and the payload-base-plus-first-quantity address.
6. The subtype must be supported, and address-bearing subtypes must pass their additional validation.

A rejected record advances the record pointer by ten bytes and decreases the remaining record count by one. Exhaustion returns status 6.

### Comparison bounds

Let the first record quantity be the candidate offset, the dependency-produced lookup length be the lookup length, and the context extent be the payload extent. These are compared as unsigned 32-bit quantities.

The comparison dependency is called only when both of these strict conditions hold:

- Candidate offset is less than payload extent.
- Lookup length is less than payload extent minus candidate offset.

Equality fails in both cases. Thus, a lookup whose reported length exactly fills the remaining extent is rejected.

The subtraction is reached only after establishing that the candidate offset is strictly smaller than the extent. This prevents subtraction underflow on that path.

The payload base is read to form the second argument to F-fca51b715561. A zero return means that this record may proceed; every nonzero return rejects it.

The supplied evidence does not establish whether that dependency compares strings, bytes, or another representation. It also does not establish how much memory the dependency reads.

### Subtype handling and success

The subtype is the low four bits of the saved flag byte. Flag bits `0x20`, `0x40`, and `0x80` do not otherwise affect this function’s selection logic.

For subtype **0 or 1**:

- The second record quantity must be strictly less than a newly read payload extent.
- F-ae943ba26e22 is called with the newly formed payload-base-plus-second-quantity address and a second argument of zero.
- A zero return rejects the record.
- A nonzero return accepts it.
- The function writes result tag 1, then writes the payload base plus the second quantity to the result value.

For subtype **2 or 3**:

- No extent check is applied to the second quantity.
- No call to F-ae943ba26e22 is made.
- The function writes the subtype as the result tag, then writes the second quantity unchanged to the result value.

Subtypes **4 through 15** reject the record.

The first accepted record terminates the search with status 0. No later records are examined.

## Side effects

The function’s explicit result writes are ordered:

1. Clear the tag on entry.
2. On success, write the accepted tag.
3. Write the four-byte result value.

There is no explicit clearing of the value field on failure and no explicit write to result bytes 1 through 3.

The function has no direct allocation, deallocation, or ownership-transfer operation in the supplied evidence. For tag 1, it returns a computed address; this alone does not establish ownership, lifetime, mutability, or permission to release that address.

Calls to dependencies may have additional side effects. Their effects on shared memory, context fields, allocations, or ownership are unknown.

Several values are retained across calls: the entry selector-data address, the selected record count, the lookup length, the decoded record quantities, and the record flag. Other values are reread, notably payload base and extent. For subtype 0 or 1, the address passed to the validation dependency can differ from the address ultimately stored if the payload base changes during that call.

Overlapping result and context storage can also matter: the success tag is written before the final payload-base read used for an address-valued result.

The initial table-base accesses are separate reads in the supplied representation. No synchronization or atomic snapshot guarantee is established.

## Acceptance examples

These examples assume valid, nonoverlapping storage, stable context fields during dependency calls, ordinary nonnegative group counts, and identifiers whose comparison is unambiguous.

1. **Preliminary rejection.** The bypass flag is zero and F-815f5f2d4275 returns 9. The result tag is cleared, its value field is not explicitly written, and the return has status 9 below the original context bits.

2. **Empty lookup.** Table processing is entered, but F-1cb585febd84 returns zero. No directory entry is examined. Status is 6.

3. **Strict comparison boundary.** Payload extent is 100, candidate offset is 80, and lookup length is 20. The record is rejected without calling F-fca51b715561 because the lookup length equals the remaining extent.

4. **Eligible comparison range.** With extent 100, offset 80, and lookup length 19, the comparison bounds pass. Acceptance still depends on a zero comparison return and valid subtype handling.

5. **Direct-value result.** An eligible record has subtype 2, the comparison returns zero, and its second quantity is `0xffffffff`. The function returns status 0, tag 2, and value `0xffffffff`; that quantity is not checked against the payload extent.

6. **Address boundary rejection.** An otherwise eligible subtype-1 record has second quantity equal to the payload extent. It is rejected without calling F-ae943ba26e22.

7. **Address normalization.** An otherwise eligible subtype-0 record has an in-range second quantity, and F-ae943ba26e22 returns nonzero. The result uses tag 1, not tag 0, and stores the computed payload address.

8. **First matching group wins.** Two directory entries share the selector identifier. The first has zero records; the second contains an acceptable record. The function returns status 6 without searching the second group.

9. **Rejected candidate followed by success.** Within one selected group, a subtype-4 record passes the comparison but is rejected. A later eligible subtype-3 record succeeds, producing tag 3 and its second quantity.

## Uncertainties

- **documented_only — Target ABI:** The 64-bit composite is visible in the supplied representation, but its machine-level return convention is not independently verified.
- **documented_only — Selector signedness and byte order:** The selector uses a native signed two-byte access, unlike the explicitly most-significant-byte-first directory identifier. Under ordinary signed promotion, a negative selector does not equal a positive byte-assembled identifier. Exact high-bit behavior requires confirmation of the representation’s type semantics and target byte order.
- **documented_only — Malformed group counts:** The group count is consumed as a signed-width quantity, with termination based on reaching zero rather than positivity. Negative counts are not rejected. No safe finite-table behavior is established for them.
- **documented_only — Address arithmetic:** Address additions and directory-size calculations have no explicit overflow checks. The representation uses 32-bit addresses, but safe behavior for wrapped or otherwise invalid addresses is not established.
- **documented_only — Dependency semantics:** Read extent, mutation, errors, and ownership behavior of dependencies remain unknown.
- **documented_only — Concurrent mutation:** There is no visible synchronization. The contract does not promise a coherent snapshot under concurrent changes.
- **Inferred intent:** The strict lookup-length bound may reserve room for an additional byte, but no terminator requirement is independently proven.
