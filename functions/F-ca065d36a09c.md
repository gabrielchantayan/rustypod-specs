# F-ca065d36a09c

## Purpose

F-ca065d36a09c performs a two-stage indirect dispatch on a supplied object-like memory region. It first invokes a query operation. A zero query result selects one subsequent operation; every nonzero result selects another. The selected operation receives the same object argument.

The important state-sensitive property is that the dispatch-table reference used for the second operation is read **after the query returns**. The function does not retain the initial table reference for both stages. A query that changes the object’s leading table reference can therefore change the destination of the second dispatch.

This is an independent contract derived from the supplied static representation. Terms such as “object,” “table,” and “query” describe observable roles, not a proven class hierarchy or application purpose.

The function accepts one pointer-like argument, referred to here as the **object reference**.

The supplied representation treats the beginning of the referenced storage as an integer-sized field containing a dispatch-table address. The function uses that address to locate indirect-call targets at fixed byte offsets.

The relevant layout is:

| Location | Required role |

## Behavior

### Initial query dispatch

The function reads the table reference from the beginning of the object storage. It then reads the query target from byte offset 140 in that table and invokes that target with the original object reference.

The initial table reference determines the query target only. The representation does not show the function caching either possible second-stage target before invoking the query.

The query is permitted, from the caller’s visible behavior, to have effects not described in this excerpt. In particular, there is no evidence that it preserves object contents, the table reference, globals, allocations, or the validity of the object itself.

### Result classification

If the query returns normally, its integer result is classified into exactly two cases:

- **Zero:** select the operation at table offset 96.
- **Nonzero:** select the operation at table offset 136.

Positive and negative nonzero results use the same branch. There is no distinct treatment of a negative result as an error, no special handling for one particular positive value, and no range-based selection.

The query result is not otherwise used by this function.

### Post-query dispatch

After the query completes, the function reads the table reference again from the original object address. It obtains the selected target from this post-query table reference.

This establishes two independent influences on the second dispatch:

1. The query’s returned integer chooses the slot offset.
2. The object’s table-reference field after the query chooses the table containing that slot.

For example, a query can return zero while replacing the object’s table reference. The selected operation then comes from offset 96 of the replacement table, not from offset 96 of the initial table.

The selected target receives the original object reference. A modified table reference does not substitute a different object argument.

Only the selected slot is explicitly read at this stage. The supplied representation does not show a read of the other branch’s slot.

### Completion and abnormal control flow

If both indirect invocations return normally, the function completes without an explicit additional state update.

If the query does not return normally, the representation provides no path to the second dispatch. If the selected operation does not return normally, ordinary completion of F-ca065d36a09c does not follow.

There is no visible local error handler, status conversion, retry, fallback operation, or cleanup path. The consequences of faults, exceptions, termination, or nonlocal control transfers inside dependencies are unknown.

The second transfer is represented as an indirect invocation, but its exact machine-level call-versus-tail-transfer form is unresolved. The contract therefore establishes selection, argument forwarding, and the absence of further explicit work without requiring a particular stack-frame mechanism.

1. Read the initial table reference from the object.
2. Read the query target at offset 140 from that table.
3. Invoke the query and receive its result.
4. Read the table reference again from the original object address.
5. Read the selected target at offset 96 or 136 from that table.
6. Invoke the selected target.

## Acceptance examples

These examples are conditional contract checks, not reports of executed tests.

### Zero result with an unchanged table

Given a valid object whose table reference remains unchanged, if the query returns zero, the function must invoke the target at offset 96 in that table with the original object reference.

It must not select offset 136 merely because that slot contains a valid target.

### Positive nonzero result

Given valid storage and compatible targets, if the query returns one or any other representable positive nonzero value, the function must select offset 136 in the post-query table.

The magnitude of the result must not change the selected offset.

### Negative nonzero result

If the query’s integer result is negative and nonzero, the function must select offset 136. A negative value must not, by itself, cause a local error return or suppress the second dispatch.

### Query replaces the table reference

Given an initial table A, suppose the query invoked through A replaces the object’s leading table reference with table B and returns zero.

The required second target is the entry at offset 96 in B. Choosing the corresponding entry in A would violate the observed post-query reload behavior.

If the same replacement occurs with a nonzero result, the required entry is offset 136 in B.

### Query changes a selected table entry

Suppose the query leaves the table reference unchanged but changes the entry that will be selected. If that change is visible when the selected slot is read, the subsequent invocation uses the changed entry.

This follows from reading the selected target after the query rather than caching it beforehand.

### Invalid unselected slot

If the query returns zero, the function has no explicit need to read the offset-136 entry. An unusable target stored there does not, by itself, violate the accesses required for that path.

This example assumes the table and selected slot are otherwise accessible and dependencies do not independently use the unselected slot.

### Query invalidates the object

If the query makes the original object storage inaccessible and then returns, the function still attempts its post-query table-reference read. No safe error result or recovery behavior is established.

### Query does not return

If the query transfers control away without returning, the second invocation is not reached through the displayed normal path. The function contains no visible mechanism to force that invocation afterward.
