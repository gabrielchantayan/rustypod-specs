# F-663b186301f2

## Purpose

F-663b186301f2 obtains an object address, initializes four consecutive 32-bit fields, invokes a preparation dependency using a descriptor count, rereads and records that count, invokes a final dependency, and returns the obtained address.

The final dependency receives an object field, a descriptor field, and the recorded count shifted left by two bits. This shape suggests an operation on four-byte elements, but neither a memory transfer nor an element-container abstraction is established by the supplied body.

The contract is an ordered sequence of memory accesses and dependency calls. It does not establish allocation policy, storage capacity, ownership, or disjointness between the object and descriptor. In particular, writes addressed through the object can modify descriptor fields when their storage overlaps.

## Behavior

### Obtaining and initializing the object

The first visible operation calls F-c5da7fd8e586 without explicit arguments.

After that dependency returns, the function reads a global 32-bit initializer and writes it to object offset +0. The initializer is not captured before the dependency call. A change made to the initializer by that dependency can therefore affect the value written.

The function then writes zero to object offsets +4, +8, and +12, in that order.

All four writes precede the first descriptor-count read. Their effects must be considered before interpreting the descriptor’s contents. If the object overlaps the descriptor, initialization can change the count or the field later supplied to the final dependency.

For example:

- If the object and descriptor have the same base, initialization sets descriptor offsets +4 and +8 to zero before either is read.
- If the object begins four bytes after the descriptor, initialization writes the global initializer to descriptor offset +4 and zero to descriptor offset +8, as well as writing the next two object fields.

These consequences follow from coincident field locations; they do not require either dependency to modify the descriptor.

### First count observation and preparation

After initialization, the function reads 32 bits from descriptor offset +4 and calls F-a709b42a5ce0 with:

1. The obtained object address.
2. The value from that read.

The return value is unused.

The count supplied here is the value present **after initialization**, not necessarily the value present at function entry. Initialization may already have changed it through aliasing.

The supplied body does not establish whether F-a709b42a5ce0 allocates storage, establishes capacity, modifies object fields, changes descriptor storage, preserves globals, or invalidates memory. Its effects cannot be restricted to the two explicit arguments.

### Second count observation and assignment

After preparation returns, the function reads descriptor offset +4 again as a signed 32-bit value.

It then writes that value to object offset +4 and retains the observed value for the final size calculation.

The two count reads are distinct. The second need not equal the first, and no consistency check compares them. A change during preparation can therefore produce a different recorded count and final size argument.

The assignment to object offset +4 is itself significant to subsequent descriptor observations. If that destination overlaps descriptor offset +8, the assignment modifies the field that will be read for the final dependency.

In particular, when the object begins four bytes after the descriptor:

- Object offset +4 and descriptor offset +8 identify the same four bytes.
- Storing the second count observation overwrites descriptor offset +8.
- The final dependency’s second argument is consequently read from the overwritten field, not from an earlier value left there by preparation.

Other overlaps may also connect object writes to descriptor storage. The body supplies no general disjointness guarantee.

There is no visible conditional guard around F-unknown-01. A zero count does not cause the caller to skip the call.

### Arithmetic

The visible size operation is a left shift by two on the signed 32-bit count representation. It is not a checked size conversion.

For counts from 0 through 536,870,911 inclusive, four times the count is representable as a signed 32-bit integer. In this range, the shift has the straightforward mathematical result of multiplying by four.

For negative counts or counts greater than 536,870,911, the supplied representation does not establish a portable arithmetic result. The function performs no visible rejection or range check. This contract therefore does not promise unsigned wraparound, mathematical multiplication, a particular fault, or a particular final-call argument for those cases.

A raw 32-bit bit-shift interpretation would discard bits shifted beyond the word and insert two low zero bits. That observation does not resolve the executable’s arithmetic semantics or the final dependency’s parameter type.

## Acceptance examples

These are conditional consequences of the static representation, not executed tests. Each example assumes the relevant accesses are valid, dependencies return normally, and effects not specified in the example do not alter the stated observations.

### Stable, disjoint storage

Suppose object and descriptor storage are disjoint, descriptor offset +4 remains 3, and preparation leaves that count unchanged.

Preparation receives 3. The function subsequently assigns 3 to object offset +4 and supplies 12 as the final dependency’s third argument. It returns the address obtained from F-c5da7fd8e586.

This does not establish that any bytes are copied.

### Count changed during preparation

Suppose initialization does not overlap the descriptor, the first count observation is 3, and preparation changes descriptor offset +4 to 5.

Preparation receives 3. The caller then records 5 and supplies 20 as the final third argument. Reusing the first observation for either action would not match the visible behavior.

### Descriptor field changed during preparation

Suppose preparation changes descriptor offset +8.

The final dependency receives the value read from that field **after the count assignment**. If the assignment does not overlap that field and no other intervening effect changes it, this is the value left by preparation. Without that condition, the preparation-time value is not guaranteed to survive.

### Count assignment overwrites the final descriptor argument

Suppose the object begins four bytes after the descriptor, preparation leaves a second count observation of 5 at descriptor offset +4, and it leaves a different value at descriptor offset +8.

The caller writes 5 to object offset +4, which is descriptor offset +8. The final dependency therefore receives 5 as its second argument and 20 as its third argument. The earlier value left at descriptor offset +8 is not used.

### Initialization changes the first count

Suppose object and descriptor have the same base and preparation does not subsequently change the relevant fields.

Initialization sets descriptor offset +4 to zero. Preparation therefore receives zero, regardless of that field’s entry value. The later recorded count and final third argument are also zero. The final call still occurs.

### Four-byte-offset overlap during initialization

Suppose the object begins four bytes after the descriptor, the initializer read is 3, and preparation preserves the relevant initialized storage.

Initialization places 3 at descriptor offset +4 and zero at descriptor offset +8. Preparation receives 3. The subsequent count assignment changes descriptor offset +8 to 3.

The final dependency receives zero as its first argument, 3 as its second, and 12 as its third.

### Preparation changes the object argument field

Suppose preparation changes object offset +8 and that value survives until the final argument read.

The replacement value becomes the final dependency’s first argument. The initialization-time zero is not a fixed argument.
