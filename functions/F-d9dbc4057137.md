# F-d9dbc4057137

## Purpose

F-d9dbc4057137 conditionally invokes F-70a021fc7c24 after checking a descriptor-relative field and a signed quantity processed by F-1c61b1704268.

The established behavior does not identify the application-level operation. Interpretations such as reading, copying, extracting, or releasing data remain unproven.

The function returns a 64-bit composite value and optionally writes a 32-bit quantity to caller-provided storage. The lower return word is status-like. The upper word contains either the original base argument’s address representation or the address of temporary local storage.

Quantity acceptance precedes the operation call. The optional quantity output, however, is read from the current local quantity after that call. F-1c61b1704268 receives this local quantity’s address and may retain it; F-70a021fc7c24 may subsequently modify the still-live quantity through retained state. Successful acceptance therefore does not establish that the final output still satisfies the acceptance comparisons.

## Interface

The function has six arguments, in this order:

| Argument | Established representation | Observed use |
|---|---|---|
| Descriptor | 32-bit pointer to a 32-bit integer | Tested for null; its first word contributes an address offset; forwarded to F-1c61b1704268. |
| Base | 32-bit pointer | Selects the field-address base when non-null; forwarded unchanged to F-1c61b1704268; initially supplies the upper return word. |

| Requested quantity | Signed 32-bit integer | Tested against zero, copied into mutable local storage, and used in signed acceptance comparisons. |
| Operation argument | 32-bit integer | Tested against zero and supplied as the second argument to F-70a021fc7c24. Its domain is unknown. |
| Quantity output | Optional 32-bit pointer | When non-null, receives one 32-bit write during normal finalization. |

The return layout is:

| Bits | Contents |
|---|---|
| 0–31 | Final 32-bit status representation |
| 32–63 | Path-dependent 32-bit address representation |

A status of −50 has lower-word representation `0xFFFFFFCE`. It does not establish a sign-extended 64-bit result, because the upper word is supplied separately.

Two global 32-bit values serve as status sources:

- The **initial status source**, read before the descriptor null check.
- The **field-rejection status source**, read after both field-observation calls.

Their numeric values and semantic meanings are not supplied.

### Preconditions and storage lifetime

Every memory access reached during execution must be valid:

- The descriptor must support a 32-bit read whenever its first word is used.
- Each computed field address must satisfy F-c19b4c0cb7f7’s requirements.
- A non-null quantity-output pointer must support a 32-bit write.
- Dependency arguments must satisfy those dependencies’ independently established requirements.

The function does not locally establish these conditions. In particular, a null base does not prevent field access; it selects a fixed fallback base address.

The mutable quantity and saved operation value occupy temporary local storage. Their storage remains live during the dependency calls but is not persistent caller-owned output storage after return. Passing the quantity’s address does not establish that F-1c61b1704268 refrains from retaining it.

## Behavior

### Initial state and null descriptor

The function reads the initial status source before checking whether the descriptor is null.

It establishes two other initial values:

- The upper return word represents the original base argument, including zero for a null base.
- The mutable local quantity equals the requested quantity.

A null descriptor bypasses all dependencies and proceeds directly to finalization using the previously read initial status.

Consequently, a null descriptor is not intrinsically a nonzero-status condition. If the initial status is zero, a supplied quantity output receives the original request. If the initial status is nonzero, that output receives zero.

### Entry conditions

For a non-null descriptor, both the requested quantity and operation argument must be nonzero to enter the field-checking path.

These are zero tests, not positivity tests. A negative requested quantity passes this entry condition.

If either argument is zero:

- Status becomes signed 32-bit −50.
- No dependency is called.
- The upper return word remains the original base representation.
- Execution proceeds to finalization.

The operation value is not an entry gate. A zero operation value can reach the field checks and quantity-processing dependency.

### Field-address construction and observations

The field-checking path selects the original base when non-null, or a fixed fallback address otherwise. It also saves the operation value in local 32-bit storage before either field-observation call.

Each field address combines:

- The selected base.
- The descriptor’s first 32-bit word.
- An additional displacement of 14 bytes.

This is a 32-bit address calculation. The contract does not treat it as an unbounded mathematical sum, require a nonnegative descriptor offset, or establish that an address produced by wraparound is valid.

F-c19b4c0cb7f7 is called twice in order. Both calls occur before the rejection decision, even if the first result alone would suffice to reject.

The acceptance tests use different portions of the two results:

- The first result’s least-significant eight bits must be zero.
- Bits 8–15 of the second result must be zero.

Other result bits do not affect this decision. The evidence does not establish the dependency’s memory-read width or byte order merely from these tests.

The address expression reads the descriptor’s first word separately for the two calls. If the first dependency call changes that word, the second computed address may differ. Equal addresses therefore require stability of the relevant descriptor state; equal observations additionally require whatever stability the dependency itself needs.

After both calls return, the function reads the field-rejection status source. That read occurs whether the tested result portions pass or fail.

If either tested portion is nonzero, execution finalizes with that status value. The upper return word still represents the original base. Because the status source’s value is unknown, field rejection does not necessarily imply a nonzero status.

### Quantity-processing dependency

If both field tests pass, the upper return word is changed to the address of the local storage containing the saved operation value.

The function then calls F-1c61b1704268 with:

1. The original descriptor.
2. The original base, including null when supplied.
3. The integer constant 1.
4. The address of the mutable local quantity.

The fallback base selected for field observations is not substituted for the original base in this call.

The dependency’s 32-bit return becomes the status. A nonzero return skips the quantity acceptance comparisons and the operation call.

F-1c61b1704268 can modify the local quantity through the supplied address. Its implementation and retention behavior are unknown. In particular, the address may remain reachable through dependency-managed state after this call returns; normal return does not imply that the local quantity becomes inaccessible to subsequent dependencies.

### Quantity acceptance

When F-1c61b1704268 returns zero, the function evaluates the current local quantity using signed 32-bit comparisons.

Acceptance requires both:

- The local quantity is no greater than the requested quantity.
- Either the original operation value is nonzero, or the requested quantity is no greater than the local quantity.

Thus:

- With a nonzero operation value, any local quantity at or below the request passes these comparisons.
- With a zero operation value, the local quantity must equal the request.

There is no separate lower-bound check. Zero and negative quantities can satisfy the comparisons. Negative requests are also evaluated according to signed ordering rather than rejected categorically.

If acceptance fails, status becomes −50 and the operation is not called. The upper return word remains the address of the temporary operation-value storage.

### Operation and subsequent quantity state

On acceptance, F-70a021fc7c24 is called with:

1. The saved operation value.
2. The original operation argument.

The local quantity is not passed directly to this dependency. Nevertheless, indirect access remains possible because F-1c61b1704268 previously received its address and may have retained it.

F-70a021fc7c24’s return value is ignored. The wrapper retains zero status when this call returns normally; it does not derive status from the operation’s return value.

The quantity comparisons are not repeated after the operation. If the operation changes the local quantity through retained state, finalization uses the changed value. That value need not equal the quantity checked earlier, remain within the requested bound, or retain the same sign.

### Finalization

Every normal exit tests the quantity-output pointer.

When it is non-null:

- If status is nonzero, the function replaces the local quantity with zero.
- It then writes the current local quantity to the output location as one 32-bit value.

Accordingly:

- Nonzero status guarantees a zero quantity output on normal completion.
- Zero status produces the local quantity present at finalization.
- On the successful-operation path, that is the post-operation quantity, potentially modified through dependency side effects.

Zero-status outputs are not restricted to the original request or to the value left immediately upon F-1c61b1704268’s return.

When the output pointer is null, no output write occurs. The status-dependent replacement of the local quantity with zero is also skipped.

The function then returns the composite status and address representation. An upper word identifying temporary local storage does not grant a valid post-return dereference or transfer ownership of that storage.

## Side effects

Directly established effects, in execution order where applicable, are:

- Reading the initial status source.
- Initializing local state.
- Reading the descriptor’s first word for each field-address expression.
- Calling F-c19b4c0cb7f7 twice, sequentially.
- Reading the field-rejection status source after both calls.
- Conditionally passing writable local quantity storage to F-1c61b1704268.
- Conditionally calling F-70a021fc7c24.
- Finally writing one 32-bit quantity through a non-null output pointer.

Dependency effects occur before the final output write. If the output pointer aliases storage accessed or changed by a dependency, the final write occurs later and can overwrite that storage.

The local quantity remains live across both quantity processing and the operation. Changes made through a retained quantity address during the operation affect the subsequent output without triggering renewed acceptance checks.

No direct allocation, release, ownership transfer, or persistent storage mechanism is evidenced in this function. Dependency ownership, retention, allocation, and release behavior remain unknown.

No local exception recovery or memory-fault conversion is shown. Finalization guarantees apply only when execution reaches finalization normally; they do not cover a fault or dependency that does not return normally.

## Acceptance examples

These are conditional static contracts, not runtime observations. All examples assume valid reached memory accesses and normally returning dependencies. Any additional preservation condition is stated explicitly.

1. **Null descriptor, nonzero initial status.**  
   If the initial status is 7, the request is 12, and an output pointer is supplied, no dependency is called. The output receives zero. The lower return word is 7, and the upper word represents the original base.

2. **Null descriptor, zero initial status.**  
   With initial status zero and request 12, the output receives 12. No field validation or operation occurs despite zero status.

3. **Zero entry argument.**  
   For a non-null descriptor, a zero request or zero operation argument produces status −50 without calling any dependency. A supplied output receives zero. The upper word remains the original base representation.

4. **First observation rejects.**  
   If the first observation has a nonzero low byte, the second observation still occurs. The field-rejection status source is then read and used. Neither later dependency is called. If that status is zero, a supplied output receives the original request; otherwise it receives zero.

5. **Shorter quantity accepted with nonzero operation value.**  
   Suppose field checks pass, the request is 10, the operation value is nonzero, and F-1c61b1704268 returns zero with quantity 6. The operation is called. Status remains zero. A supplied output receives the quantity present after the operation: it is 6 only if the operation leaves that local quantity unchanged.

6. **Shorter quantity rejected with zero operation value.**  
   With request 10, operation value zero, and a successful quantity-processing result of 6, acceptance fails. The operation is not called. Status becomes −50, and a supplied output receives zero.

7. **Negative quantity accepted by signed comparison.**  
   With request 10 and nonzero operation value, a successful quantity-processing result of −1 passes the comparisons. The operation is called. A supplied output receives −1 only if the quantity remains unchanged through that call; otherwise it receives the post-operation quantity. This does not establish that −1 satisfies the dependencies’ own contracts.

8. **Post-operation quantity exceeds the checked bound.**  
   Suppose request 10 and nonzero operation value permit a processed quantity of 6. If the operation then changes the still-live quantity to 20 through retained state, the function does not recheck it. Status remains zero, and a supplied output receives 20.

9. **Quantity-processing failure after mutation.**  
   If F-1c61b1704268 sets the quantity to 6 but returns 9, the operation is not called. A supplied output receives zero, not 6. The lower word is 9; the upper word represents temporary operation-value storage.

10. **Descriptor mutation between observations.**  
    If the first field dependency changes the descriptor’s offset, the second address uses the subsequently read offset. An expectation that both calls use the same address requires descriptor stability.
