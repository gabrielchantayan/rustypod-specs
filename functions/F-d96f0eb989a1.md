# F-d96f0eb989a1

## Purpose

F-d96f0eb989a1 processes complete 128-bit units according to a one-byte mode selector. It returns the number of bits accounted for by completed units, rather than the requested length or a byte count.

Three selectors are recognized:

- **1:** one processing-dependency invocation per 16-byte unit, using the current input and output addresses.
- **2:** one processing-dependency invocation per unit, four state-word combinations, then two transfer-dependency invocations.
- **3:** one transfer-dependency invocation per unit, followed by 128 processing invocations interleaved with state shifts and output-bit updates.

Direct-block, chained-block, and bit-feedback interpretations are inferred intent. The supplied evidence does not establish cryptographic algorithms, security properties, or dependency guarantees.

| 3 | Input storage address | Unsigned 32-bit value used as an address |
| 4 | Requested bit count | Unsigned 32-bit value, rejected for work when its signed interpretation is negative |

### Descriptor layout

| Offset | Established use |

| 4–19 | Sixteen-byte mutable state used by modes 2 and 3 |

Mode 2 reads the state as four consecutive 32-bit words at offsets 4, 8, 12, and 16. Mode 3 reads and writes it as sixteen bytes. No direct access to offsets 1–3 is established.

### Context layout

| Offset | Established use |
|---|---|
| 0 | One-byte admission check when the captured mode is not 3 |
| 76 | 32-bit value read for each processing invocation |
| 80 | Beginning of the context region supplied to F-025193859ccb |

The extents and internal layouts of the two dependency context regions are unknown.

### Result

The return value is a signed 32-bit integer:

- **−5:** descriptor or context rejection, or unsupported selector reached at dispatch.
- **0:** an admitted no-work request, or a recognized selector with fewer than 128 requested bits.
- **Positive multiple of 128:** the number of bits represented by the completed unit count.

For admitted lengths \(L\) from 1 through \(2^{31}-1\), the unit count is

\[
N=\left\lfloor L/128\right\rfloor,
\]

and normal completion returns \(128N\). The maximum result is 2,147,483,520, within the signed 32-bit range.

### Preconditions and storage

Non-null addresses must designate storage suitable for every reached access. The function does not validate allocation extents, output nullness, alignment, overlap, or dependency-specific requirements.

The descriptor mode byte must be readable after the null checks. Modes other than 3 additionally require a readable context byte at offset 0. Actual processing requires usable dependency context storage and data storage. Modes 2 and 3 require mutable descriptor state.

State/input overlap is **not rejected**, but it changes behavior. In particular, preserving the original input-bit sequence during mode 3 requires conditions beyond exact input/output aliasing: descriptor state must also be disjoint from the processed input/output region, and dependencies must not otherwise change the relevant bytes.

## Behavior

### Admission and no-work precedence

Admission occurs in this order:

1. If the descriptor or context address is null, return −5 without reading the descriptor mode.
2. Otherwise, read and retain the descriptor’s mode byte.
3. If the captured mode is not 3, read context offset 0. If that byte is zero, return −5.
4. After admission, return 0 if the input address is zero, the requested bit count is zero, or the bit count has its high bit set.

Mode 3 skips the context-byte admission read, but still requires a non-null context address.

These checks precede selector dispatch. Consequently:

- A rejected context produces −5 even for zero-length work.
- An unsupported selector can return 0 when it passes admission and meets a no-work condition.
- An unsupported selector with a positive admitted length returns −5 even when that length is below 128.

The output address is never explicitly checked.

### Unit count and workspace

For a positive admitted length, only complete 128-bit units are processed. A remainder of 1–127 bits schedules no additional work.

Before dispatch, a 16-byte local workspace is initialized as four consecutive 32-bit values:

1. Descriptor address.
2. Context address.
3. Original input address.
4. Original requested bit count.

Modes 2 and 3 pass the workspace address to a dependency. It is initialized once, not once per unit or invocation. If a dependency leaves some workspace bits unwritten, subsequent behavior can depend on the initial contents or earlier workspace contents.

The initially captured mode controls the entire dispatch. Later writes to the descriptor mode byte do not cause redispatch.

### Mode 1

For every complete unit, F-025193859ccb receives:

1. Context address plus 80.
2. The current 32-bit value at context offset 76.
3. Current input address.
4. Current output address.

After each invocation, input and output addresses advance by 16 bytes.

There are no explicit caller-side input, output, or descriptor-state writes in this mode. This does not restrict what the dependency may write. Its return value is ignored.

The context word is read anew for each invocation, so dependency mutations or aliasing can affect later supplied values.

### Mode 2

Each complete unit has this observable sequence:

1. Invoke F-025193859ccb with context offset 80, a fresh read of the word at context offset 76, the current input address, and the local workspace address.
2. Combine each of the four workspace words with the corresponding descriptor-state word using exclusive OR. These state reads and workspace updates proceed in ascending word-offset order.
3. Invoke the unidentified transfer dependency with descriptor state as apparent destination, current input as apparent source, and length 16.
4. Invoke that dependency with current output as apparent destination, workspace as apparent source, and length 16.
5. Advance both data addresses by 16 bytes.

The input is not snapshotted before the processing invocation. The state-transfer request uses the input address only after the processing invocation and all four word combinations.

The order of the transfer requests is significant under overlap: the requested state transfer precedes the requested output transfer.

If the processing dependency fully writes a transformed block, the transfers are ordinary copies, and storage is appropriately disjoint, the output is the transformed block XOR the state observed during the word combinations. The next state is the input block observed during the state transfer. Those value-level conclusions are conditional; dependency behavior is not established independently.

### Mode 3

At the beginning of each complete unit, the function invokes the unidentified transfer dependency with current output as apparent destination, current input as apparent source, and length 16.

It then performs exactly 128 bit iterations. For iteration \(k\), from 0 through 127, the selected data byte is \(\lfloor k/8\rfloor\), and its selected bit position is \(7-(k\bmod8)\). Thus traversal is most-significant-bit first within each byte.

Each iteration has the following ordering:

1. Invoke F-ce3bd5ea2520 with context offset 320, a fresh read of the word at context offset 76, descriptor state, and workspace.
2. Update the first fifteen state bytes in ascending address order. Each byte receives its previous value shifted left by one bit, with the high bit of the next state byte entering the low bit. The stored result is one byte.
3. Update the final state byte by shifting it left and inserting the selected input bit into its low bit.
4. Read and update the selected output byte, toggling its selected bit according to numeric bit 7 of the workspace’s first 32-bit word.

The first fifteen state-byte writes occur before the selected input-bit read. The final state-byte write occurs before the output-byte update.

Only numeric bit 7 of the workspace’s first word directly contributes to the output update. It is positioned at output bit \(7-(k\bmod8)\). Identifying that numeric bit with a particular workspace byte requires a target byte-order assumption.

After all 128 iterations, both data addresses advance by 16 bytes.

#### Exact input/output aliasing

Exact input/output aliasing alone does **not** guarantee feedback from the original input sequence.

That guarantee holds under all of the following conditions:

- Input and output designate the same processed region.
- The descriptor-state region is disjoint from that region.
- The initial transfer preserves the bytes for identical source and destination.
- Processing dependencies do not otherwise mutate the relevant input/output bytes.

Under those conditions, each selected input bit is read before its corresponding output-bit update. Earlier **output-bit updates** affect only earlier bit positions, so they do not change the bit currently being read for feedback.

If descriptor state overlaps input/output, the caller’s own state shifts can modify current or future input bits before they are read. This remains true when dependencies preserve all input/output bytes. Output updates can also affect overlapping state and thereby change subsequent iterations.

Partial input/output overlap has no general preservation guarantee either.

### Completion and errors

Recognized modes return \(128N\) after their loops finish. For \(N=0\), they make no processing or transfer calls and perform no direct descriptor-state or output updates.

Dependency return values are ignored. There is no explicit rollback, dependency-error conversion, or partial-progress result. Faults, nonreturning dependencies, and other abnormal execution do not have an established normal-return contract.

## Side effects

### Direct and dependency-mediated effects

- **Mode 1:** caller-side address advancement; data effects are delegated to F-025193859ccb.
- **Mode 2:** workspace updates and dependency calls requesting state and output transfers.
- **Mode 3:** a requested initial output transfer, direct state-byte writes, and direct output-byte updates.

Modes 2 and 3 do not reset or restore descriptor state on entry or exit. Later calls can observe the resulting state, subject to dependency behavior and aliasing.

There is no explicit caller-side allocation or release operation. This does not establish that dependencies avoid allocation, retention, release, global mutation, or access outside their apparent output arguments.

### Observable ordering under overlap

The following order is established:

- Mode 2 state-word reads follow its processing invocation.
- Mode 2 requests the state transfer before the output transfer.
- Mode 3 requests the initial transfer before its first processing invocation.
- Every mode-3 processing invocation precedes that iteration’s direct state writes.
- Mode 3 writes its first fifteen state bytes before reading feedback input.
- Mode 3 writes its final state byte before updating output.
- Every processing invocation receives a newly read context word.

There is no general snapshot protecting input or state from these effects. Even with dependencies that preserve input, caller-side state writes can change feedback input when storage overlaps.

## Acceptance examples

These are conditional static acceptance cases, not runtime observations. Unless stated otherwise, reached memory accesses are valid and dependencies return normally.

1. **Null admission:** A null descriptor or null context returns −5, regardless of length, input, or output.

2. **Mode-3 admission exception:** A non-null context with a zero first byte does not itself reject mode 3. Processing a complete unit still requires valid dependency context storage.

3. **Validation before no-work:** Mode 1 with context byte zero returns −5 for a zero-bit request. With that context byte nonzero, a zero input address returns 0 without processing.

4. **High-bit length:** After admission succeeds, lengths from 2,147,483,648 through 4,294,967,295 return 0 without processing or transfer calls.

5. **Truncation:** A recognized mode with nonzero input and length 255 processes one unit and returns 128. The remaining 127 bits schedule no work.

6. **Short recognized versus unsupported request:** Mode 2 with length 127 returns 0 without processing, transfer, or state updates. Mode 4 with nonzero context byte and the same admitted length returns −5. Changing that unsupported request’s length to zero instead returns 0.

7. **Mode-2 block result:** Suppose the processing dependency fully writes block \(T\), the four state reads observe block \(S\), transfers perform ordinary byte copies, and relevant storage is disjoint. Output is \(T\mathbin{\mathrm{XOR}}S\). Next state equals input as observed by the state transfer, not necessarily input as it existed at function entry.

8. **Mode-3 zero contribution, disjoint storage:** Suppose transfers are ordinary copies, state/input/output are disjoint, and processing invocations modify only workspace while supplying a zero contribution bit. Output equals input. After one unit, state contains the input’s 128 bits in traversal order.

9. **Mode-3 exact input/output aliasing:** Suppose input equals output, descriptor state is disjoint from the entire processed region, the initial transfer preserves identical source/destination storage, and processing invocations modify only workspace. A contribution bit of one on every iteration complements every output bit, while feedback still receives the original input bits.

10. **State-overlap counterexample:** Let input and output both begin at descriptor offset 4. Initially that shared sixteen-byte region contains `80` followed by fifteen `00` bytes, in hexadecimal. Suppose the initial transfer preserves identical source/destination storage and the processing dependency changes only workspace, supplying a zero contribution bit. On the first iteration, the direct state shift changes the first byte from `80` to `00` before feedback reads its selected input bit. Feedback therefore receives zero, although the original first input bit was one. Exact input/output aliasing and dependency preservation do not prevent this change.
