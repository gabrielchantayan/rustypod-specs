# F-fdc51ee59246

## Purpose

F-fdc51ee59246 searches an object-backed input using a captured 32-bit target marker. When its post-scan marker comparison succeeds, it requests storage, attempts to read a payload, and conditionally passes that payload and two caller-supplied output regions to F-0644ced486d8.

Restoration is attempted **only after a payload read returns exactly the requested amount**, regardless of why scanning stopped. Header-read failure or search-limit exhaustion does not independently prevent restoration: either can leave the mutable marker equal to the captured target, permitting allocation and payload reading.

The visible body establishes call ordering, explicit memory accesses, comparisons, and result construction. “Record,” “payload,” “allocation,” “release,” and “position” describe inferred roles; they do not establish the external format or unknown dependency contracts.

## Behavior

### Initialization and initial positioning

Mutable marker and size storage are initialized from their respective arguments. A separate candidate size and the accumulated skipped-record size begin at zero.

The function then:

1. Calls slot 0x1c with the input object and saves its 32-bit result.
2. Establishes an upper return word of 1.
3. Calls slot 0x14 with the input object, that slot’s callback address, 0x1c, and zero.
4. Reads the target-marker global into a captured comparison value.

The initial positioning result is ignored. Scanning proceeds even if the callback uses its return value to indicate failure.

The target is captured after both initial callbacks. Later changes to the target-marker global do not cause an explicit reload by this body.

### Header-read attempts

Every evaluation of the scan condition first resets the candidate size to zero. The remaining operations are short-circuited in this order:

1. Compare the accumulated skipped-record size with the search limit using a signed comparison.
2. If the accumulator is smaller, call slot 0x10 with the mutable size address, requested amount 4, and mode 1.
3. Continue only if the returned value is exactly 4.
4. Call slot 0x10 with the mutable marker address, requested amount 4, and mode 2.
5. Continue only if that returned value is exactly 4.
6. Copy the then-current mutable size into the candidate size.
7. Compare the then-current mutable marker with the captured target.

A complete header whose marker matches ends scanning with the copied candidate size. A complete header whose marker differs enters the skip path.

The mutable size is read for the candidate **after the marker-read callback returns**. It is not necessarily identical to the value originally written by the size-read callback. That earlier callback received the storage address, and no preservation guarantee is supplied for subsequent dependencies.

A failed size read prevents the marker read. A failed marker read prevents candidate-size assignment. Either callback may have changed its destination despite returning a value other than 4.

No byte-order conversion is explicit in this body. Any conversion or mode-specific interpretation belongs to slot 0x10.

### Skipping and accumulator updates

For a complete, nonmatching header, the function constructs a skip request from the mutable size as it exists **before** the skip callback. The request supplies:

- A low word calculated as mutable size minus 8.
- A high word derived from the sign of that calculated 32-bit amount.

The slot 0x14 call also receives the input object and that slot’s callback address. Its result is ignored.

**After this callback returns, the function reads mutable size again and adds that value to the accumulator.** It does not necessarily add the size used to construct the skip request, the candidate-size snapshot, or the skip amount.

This distinction is observable. The size-read callback has received the size-storage address and may retain it. The skip callback is not established to preserve that storage. For example, a skip request constructed from size 16 can be followed by an accumulator increment of 24 if the callback changes mutable size to 24.

The next scan-condition evaluation resets the candidate size to zero and applies the signed limit comparison. No additional progress check is visible.

### Search-limit semantics

The search limit gates the beginning of a header attempt. It does not bound actual bytes read, a prospective record end, a payload extent, or the callback’s current position.

Consequently:

- A nonpositive limit prevents the first header attempt.
- A positive limit permits the first attempt because the accumulator starts at zero.
- A matching record can exceed the remaining limit and still proceed to payload acquisition.
- A skip can leave the accumulator beyond the limit.
- Header-read lengths are not separately added to the accumulator.
- An increment of zero leaves the accumulator unchanged.
- A negative increment can reduce it.

The increment is the post-skip mutable size. Statements about a header size causing a particular accumulator value require preservation of that size through the relevant callbacks.

There is no explicit iteration bound. Nontermination or unexpected movement remains possible depending on callback behavior and arithmetic.

### Post-scan marker decision

After scanning stops, the function compares the current mutable marker with the captured target. It does not require that scanning ended on a complete matching header.

If the marker differs, the function returns upper word 1 and lower word 0xffffffff. There is no restoration attempt or explicit status-byte write.

If the marker matches, payload acquisition is attempted using the candidate size:

- A complete matching header supplies the size copied after both exact header reads.
- A failed header read or a failed limit comparison leaves the candidate size at zero for that evaluation.
- A short marker read can nevertheless leave the marker equal to the target.
- A marker retained or changed across a skip can equal the target when a subsequent limit comparison stops scanning.

Thus, header-read failure and search exhaustion can both lead to payload acquisition. They are not independent terminal-error conditions.

### Payload acquisition and exact-result gate

The requested payload amount is candidate size minus 8, calculated using the visible 32-bit arithmetic.

The function calls F-d33f6d597e5d with that amount. A zero result ends this path without processing, release, restoration, or an explicit status-byte write.

For a nonzero result, slot 0x10 is called with:

- The input object.
- The acquired address.
- The requested payload amount.
- Mode 2.

The returned 32-bit value must equal the requested amount exactly. Any unequal result causes one call to F-5e3309c9d083 with the acquired address, followed by return words 1 and 0xffffffff. There is no restoration attempt or explicit status-byte write on that path.

There is no special handling for zero or negative amounts. In particular, equality with a negative requested amount satisfies the visible comparison; the function does not separately classify negative callback results as failure.

### Processing, release, restoration, and final result

On an exact payload-read result, F-0644ced486d8 receives, in order:

1. Processing context.
2. Acquired payload address.
3. Requested payload amount.
4. Output base plus 24 bytes.
5. Output base plus 8 bytes.

The processor result is saved. The function then calls F-5e3309c9d083 with the payload address and sets the upper return word to zero.

Next it invokes slot 0x14 with the input object, that slot’s callback address, the saved position-like word, and a literal zero high word. This restoration attempt occurs whether the processor returned zero or nonzero. Its return value is ignored.

Only after restoration returns does the function select the explicit status and lower return word:

- Processor result zero: write byte 4 at output offset 0, then read the success-result global for the lower word.
- Processor result nonzero: write byte 0 at output offset 0 and use lower word 0xffffffff.

A reported restoration failure does not alter these branches.

## Side effects

The full processing path has this established order:

1. Save the slot 0x1c result.
2. Attempt initial positioning.
3. Capture the target-marker global.
4. Attempt headers and skips.
5. Request payload storage.
6. Read the payload.
7. Invoke processing.
8. Invoke release.
9. Attempt restoration.
10. Write the status byte.
11. On processor success, read the success-result global.

During each skip, the request amount is established before the callback, while the accumulator increment is read from mutable storage after it returns.

The body does not explicitly write input-object fields. Its callbacks may change the object, callback table, input position, globals, or other reachable memory. Callback-table accesses are not a promise that the same callback implementation remains installed throughout the function.

The target global is captured once. The success-result global is read late, after processing, release, restoration, and the status write. Those dependencies or an aliasing status write may therefore affect the returned success word.

Early exits perform no explicit status-byte write. This is not a guarantee that the output object remains unchanged: dependencies and aliases are unconstrained by the supplied evidence.

Assuming reached calls return normally, every nonzero acquired payload address is passed once to F-5e3309c9d083: either after an unequal payload-read result or after processing. This call sequence does not establish conventional ownership. The processor might retain, modify, or release the payload; the release dependency’s actual effects are unknown.
