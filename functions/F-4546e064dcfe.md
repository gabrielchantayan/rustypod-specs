# F-4546e064dcfe

## Purpose

F-4546e064dcfe looks up a record associated with a non-null object, creates a record when lookup returns zero, refreshes record metadata, and copies a context word into the object. A nonzero context flag additionally enables traversal, accumulation of selected records’ metadata, and reporting of the accumulated value.

Registration, refresh, and aggregate maintenance are inferred intent. The established contract is the visible sequence of calls, reads, writes, and result construction below.

A null object returns zero without accessing the context. On normal completion for a non-null object, the result has low 32 bits equal to `1`. Its high 32 bits come from an address slot at return time. When aggregation runs, that slot is exposed to a dependency; its eventual contents are not necessarily the input object address, the last successfully yielded record, or the value left by the unsuccessful advancement.

## Interface

### Inputs

The supplied representation uses 32-bit addresses and exposes four arguments:

| Input | Width | Observed role |
|---|---:|---|
| Context address | 32 bits | Identifies context fields and an embedded collection interface. |
| Object address | 32 bits | Nullable address of an object with an indirect-call table and a writable word. |
| Auxiliary word | 32 bits | Copied into local storage whose address is passed to traversal dependencies when aggregation runs. |
| Auxiliary address | 32 bits | Copied into a separate local slot; the incoming address is not directly dereferenced. |

The auxiliary word is opaque. Its local storage, rather than its value alone, is supplied to traversal preparation, advancement, and finalization.

On creation, the auxiliary-address slot is overwritten with the allocated record address before its address is passed to insertion. The incoming auxiliary-address value has no established externally visible influence.

### Result

The exposed result is 64 bits:

- **Null object:** all bits are zero.
- **Normal non-null completion:** low 32 bits are `1`; high 32 bits are the contents of the object-or-record address slot when the return is constructed.
- **Late allocation-zero branch:** the visible representation also contains a return with low 32 bits zero and high 32 bits taken from that slot. This check occurs after writes through the allocation result, so it is not an established safe allocation-failure path.

The address slot initially contains the input object address. If aggregation is skipped, no visible operation changes it.

If aggregation runs, the slot is cleared and its address is passed to advancement. Advancement may modify it or retain its address. Target resolution, aggregate reporting, and traversal finalization subsequently execute with unknown effects. Consequently, the high return half is determined by the slot’s contents **after those calls**, not merely by its contents when traversal stops.

The result must not be reduced to an unconditional Boolean or an invariant object-address/status pair.

The object’s indirect-call table has observed operations at byte offsets `0x08` and `0x0c`. Both receive the object address.

A created record is requested as 12 bytes. This function explicitly initializes only the two complete words at offsets `0x00` and `0x04`, plus one byte at offset `0x08`. It does not explicitly initialize the other three bytes.

## Behavior

### Null-object path

The function checks the object address before accessing context storage or invoking a dependency.

For a zero object address:

- It returns zero.
- It does not invoke object operations.
- It does not perform lookup, allocation, insertion, traversal, or reporting.
- Context validity is not required by this path.

### Lookup

For a nonzero object address, the function reads the object’s indirect-call table and invokes the entry at offset `0x08`, passing the object address.

The resulting 32-bit value is supplied with the context address to F-7e752d2f2d1f. A nonzero result is treated as an existing record address. Zero selects creation.

The callback result’s semantic meaning, uniqueness, and relationship to the later metadata value are not established.

### Creation

When lookup returns zero, the visible order is:

1. F-8157a180d901 receives a request for 12 bytes.
2. The object operation at table offset `0x0c` is invoked.
3. Byte value `1` is written at allocation offset `0x08`.
4. The metadata callback’s 32-bit result is written at offset `0x04`.
5. The object address is written at offset `0x00`.
6. The allocation result is checked for zero.
7. For a nonzero allocation, insertion is invoked.

The object operation is therefore called before any record initialization, and all three initialization writes precede insertion.

The zero check does not protect the preceding writes. If allocation returns zero, writes are attempted relative to address zero after the metadata callback. Under ordinary invalid-null-address conditions, this path cannot be relied upon to reach the check or return normally. If those accesses are executable in a particular environment and control reaches the check, the visible branch returns without insertion, refresh, object update, or aggregation.

For insertion, the function overwrites the auxiliary-address slot with the allocation address. It invokes the collection operation at table offset `0x1c`, passing:

- The embedded collection address, context plus `0x4c`.
- The address of that local slot.

Insertion’s return value is ignored. Insertion may modify the supplied slot, but subsequent metadata refresh still targets the original allocation address. Replacing the slot does not redirect that refresh.

### Metadata refresh and object update

The existing-record path and successful creation path converge on the following order:

1. Invoke the object operation at table offset `0x0c`.
2. Write its 32-bit result to the selected record at offset `0x04`.
3. Read the context’s 32-bit word at offset `0x48`.
4. Write that word to the object at offset `0x04`.
5. Read the context flag byte at offset `0x64`.

An existing record receives one metadata callback invocation. A newly created record receives two: one before insertion and one afterward. The results need not agree; the second result overwrites the first metadata value.

For an existing record, this function does not directly rewrite the object-address word or selection field. Refresh therefore does not itself activate a record whose selection test is zero.

Each object invocation uses the object’s then-current indirect-call table. No callback-preservation guarantee is established for the table, context, object, or record. The context value and flag are read only after the preceding callback and metadata store.

### Optional aggregation

A zero flag skips all traversal and reporting operations.

For a nonzero flag, the function:

1. Calls F-8ca21d3a8cca with the address of the auxiliary-word storage and the embedded collection address.
2. Sets a 32-bit accumulator to zero.
3. Clears the object-or-record address slot to zero.
4. Repeatedly calls F-b38a3aba0e18 with the addresses of the auxiliary-word storage and that address slot.
5. Processes the slot as a record address whenever advancement returns nonzero.
6. Stops processing records when advancement returns zero.
7. Calls F-194cdec98e23 with context plus `0x44`.
8. Calls F-dfef7b6c143e with the preceding result, the accumulated value, and zero.
9. Calls F-d0d3f100effc with the address of the auxiliary-word storage.
10. Constructs the normal return value using the address slot’s contents at that time.

For each successful advancement, the function reads the yielded record’s 32-bit word at offset `0x08` and tests its low eight bits. If those bits are nonzero, it reads the metadata word at offset `0x04` and adds it to the accumulator. Otherwise, that record contributes nothing.

A selection word of `0x00000100` is unselected despite being nonzero as a whole word.

An unsuccessful advancement does not cause a record inspection. It may nevertheless change the address slot or retain access to it. Later calls are not established to preserve that slot, directly or through retained references.

Traversal follows the dependency’s yielded sequence. No deduplication, sorting, record validation, or reconciliation with lookup is visible. The aggregation flag is not retested.

### Arithmetic and packing

Metadata and accumulator storage are 32 bits. The supplied representation expresses accumulation using signed 32-bit values. No wider accumulator, overflow check, or saturation is visible.

Totals whose intermediate additions remain within the signed 32-bit range have an established arithmetic result. Signed-overflow behavior is **documented_only**; modular wraparound is not promised.

Return construction combines two 32-bit halves. Address halves are bit patterns, including addresses with bit 31 set; this packing does not imply signed numerical interpretation of an address.

## Side effects

### Direct effects and ordering

Depending on the path, the function directly:

- Initializes three portions of a newly allocated record.
- Replaces a record’s metadata word.
- Replaces the object’s word at offset `0x04`.
- Changes local insertion, traversal, and address-slot storage.

Creation writes the selection byte, metadata word, and object-address word in that order. Insertion follows those writes. Final metadata refresh precedes the object update, which precedes aggregation preparation.

No direct release of the object or allocated record is visible.

### Dependency-mediated effects

All called dependencies may have additional effects not established here. In particular:

- Insertion can access the address of its local record-address argument.
- Advancement can access and potentially retain the address of the slot later used for the high return half.
- Subsequent target resolution, reporting, and finalization cannot be assumed to leave an exposed slot unchanged.
- No dependency is assumed to preserve globals, reachable storage, or ownership.

Finalization follows reporting only if preceding calls return normally. No visible exception handler or compensating cleanup guarantees finalization after an earlier failure.

### Ownership and lifetime

Allocation occurs only after lookup returns zero. Collection retention is plausible intent, not established ownership transfer.

Normal creation-path continuation requires the original allocation to remain writable after insertion. If insertion releases it or otherwise invalidates it, the later metadata store is unsafe.

Whether lookup returns borrowed storage, insertion retains or releases records, traversal retains references, or finalization releases traversal resources remains **documented_only**.

A pointer to local storage is supplied to dependencies. Whether any retained pointer escapes beyond the invocation, and how a dependency would manage that lifetime, is not established.

### Preconditions and errors

Normal completion requires every accessed address and indirect-call target to be usable when accessed. This includes the context, object, selected record, and every record processed after successful advancement.

No explicit recovery is provided for invalid non-null addresses, invalid call-table entries, malformed records, allocation failure, dependency failure, or exceptional control transfer. Termination additionally requires advancement eventually to return zero.

A low return half of `1` establishes reaching normal result construction. It does not independently establish insertion success, reporting success, or valid ownership.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests.

### Null object

Given object address zero, the result is zero and no dependency is invoked. The context need not be valid.

### Existing record without aggregation

Given valid storage, lookup returning an existing record, metadata result `23`, context word `9`, and a zero flag at the time of its read:

- Record metadata becomes `23`.
- The object’s word at offset `0x04` becomes `9`.
- The existing record’s object-address and selection fields are not directly changed.
- Allocation, insertion, traversal, and reporting are skipped.
- Normal return has the input object-address bits in the high half and `1` in the low half.

### Creation with changing metadata

Given successful allocation and successive metadata results `10` and `14`:

- Insertion is called after the selection byte is set to `1`, metadata is set to `10`, and the object address is stored.
- The original allocation’s metadata is subsequently set to `14`.
- Changing insertion’s local record-address argument does not redirect that refresh.

This requires insertion to leave the original allocation usable.

### Selection by low eight bits

Suppose successful advancements yield these valid records:

| Selection word | Metadata |
|---|---:|
| `0x00000001` | 7 |
| `0x00000000` | 100 |
| `0x00000100` | 200 |

Provided dependencies do not invalidate the required reads, the reported total is `7`. Only the first selection word has nonzero low eight bits.

### Empty traversal and return-slot preservation

If aggregation runs and the first advancement returns zero, no record contributes to the accumulator. Target resolution, reporting with total zero, and finalization still occur on normal completion.

Two distinct conditional outcomes follow:

- If advancement leaves the cleared address slot unchanged **and all subsequent calls leave it unchanged**, the full return value is `1`.
- If advancement writes address bits into the slot **and all subsequent calls leave those bits unchanged**, those bits form the high return half; the low half is `1`.

Neither outcome follows from advancement alone. If a later call changes the slot, including through a retained reference, the contents present at return determine the high half instead.

### Allocation returning zero

A zero allocation result is followed by the metadata callback and attempted writes relative to zero before the allocation check. A safe failure return is not an established requirement.
