# F-696b25f8f663

## Purpose

F-696b25f8f663 conditionally copies one four-byte value into caller-provided storage. Eligibility requires agreement on a scaled quantity followed by successful numerical qualification of a descriptor. After the copy, a separate status interaction determines whether the explicit result is zero or 0x11.

**A result of 0x11 does not mean that no copy occurred.** The copy precedes the status interaction that can produce this result. Conversely, a zero result does not guarantee that the copied value survives subsequent dependency effects or aliased writes.

The application-level meaning of the operation is **documented_only**. The visible behavior does not establish allocation, reservation, persistence, commitment, or ownership transfer.

This contract describes explicit normal-return paths. It does not prescribe a result following invalid arithmetic, invalid memory access, or abnormal dependency termination.

## Interface

### Caller-facing values

| Value | Representation | Established use |
|---|---|---|
| First argument | Four-byte opaque value | Not directly read or forwarded. |
| Quantity | Signed 32-bit integer | Scaled by 512 for the quantity interaction and acknowledgment comparison. |
| Destination | Address of four-byte storage | Receives the conditional copy. |
| Result | Four-byte value | Explicit normal results are 0 and 0x11. |

The result’s signedness is not established; both explicit values have the same numerical meaning under either interpretation.

The quantity is not a copy length. A quantity of zero, a negative quantity, or a quantity greater than one can pass the quantity condition, but the designated copy remains four bytes.

There is no direct destination validation. When the copy is reached, the destination must support a four-byte write under the execution environment’s extent, lifetime, permission, and alignment rules. If that copy is not reached, this particular write imposes no access requirement. Dependencies and aliases may still make the same storage relevant.

### Internal storage and externally supplied addresses

The visible storage comprises:

- An 84-byte processing workspace.
- An eight-byte wrapper workspace.
- A four-byte acquisition token.
- A signed 32-bit acknowledgment slot.
- Four bytes of preparation auxiliary storage.
- Descriptor storage containing an address-bearing field and a signed 32-bit companion at byte displacement four.

The descriptor layout describes the observed fields, not a complete object definition. Complete extent, pointer representation, and any dependency-specific layout requirements remain **documented_only**.

The token is explicitly initialized to zero before acquisition. No comparable direct initialization is visible for the other storage before its first dependency interaction. Any later consumption therefore requires that the relevant dependency effects establish valid contents.

Two returned values have distinct address roles:

- Acquisition supplies a retained signed 32-bit value from which the control-byte address is derived by adding 24.
- Wrapper initialization supplies the address of a four-byte setup target.

Neither returned address is established to lie within a workspace.

## Behavior

### Setup and observation timing

Descriptor preparation occurs before token initialization and acquisition. Acquisition is followed by a direct zero write to the derived control byte.

Wrapper initialization occurs after that control write. Only after initialization returns does the function read the shared four-byte setup value and write it to the returned setup target. No dependency call intervenes between that read and write.

This timing matters: wrapper initialization may alter the shared value before it is sampled. The setup write is not specified to use a value captured before initialization.

A preliminary status interaction follows the setup-target write and precedes quantity-phase initialization. Its return value is not directly used to accept or reject the operation. Its effects remain relevant; the contract does not assume that it preserves any global or supplied storage.

### Quantity eligibility

The quantity request is the input quantity multiplied by 512 using signed 32-bit arithmetic. Quantity eligibility requires both:

- A zero result from F-e7da18b5c98f.
- An acknowledgment exactly equal to a separately evaluated quantity-times-512 value.

A nonzero processing result prevents the direct acknowledgment read and the comparison’s second scaling evaluation. It does not avoid the scaling needed to supply the processing request.

There is no positivity requirement, tolerance, rounding allowance, or partial-acceptance threshold. Exact acknowledgment establishes numerical agreement only, not the dependency’s underlying actions.

The representable quantity interval is **−4,194,304 through 4,194,303**, inclusive. Its endpoint products are −2,147,483,648 and 2,147,483,136. Outside this interval, the signed multiplication is unrepresentable. Wrapping, saturation, and an orderly 0x11 result are not established alternatives.

Quantity rejection prevents descriptor-phase initialization, descriptor processing, the designated copy, and the decisive status interaction. The quantity phase is nevertheless finalized before common cleanup on each explicit normal-return rejection path.

### Descriptor eligibility

After quantity acceptance and quantity-phase finalization, the same workspaces are used for a descriptor phase.

A nonzero result from F-daef4b52b13b rejects the descriptor without directly reading the qualification operands. Following a zero result, qualification uses:

- The descriptor’s signed 32-bit companion.
- The descriptor’s address-bearing value converted to signed 32-bit.

The numerical separation is the companion minus the converted address. Qualification requires that the separation, shifted right by three positions, equal one.

For a defined, nonnegative separation, the accepted interval is **8 through 15 inclusive**. The separation need not equal eight or be divisible by eight.

The representation does not establish the relative read order of the two operands. Address-to-integer conversion, unrepresentable signed subtraction, and right shifting a negative signed value depend on execution-model rules not supplied here.

This numerical check does not establish memory safety. In particular, acceptance does not prove that the address identifies four readable bytes or that the referenced storage remains alive.

### Copy and final result

After both eligibility conditions pass, the function reads one four-byte value through the descriptor-provided address and writes it to the destination.

The source value must be obtained before the destination write completes. No bytewise access order, atomicity guarantee, or general rule for partially overlapping ranges is established. The address used for qualification is not established to be a retained snapshot reused for the copy.

Descriptor-phase finalization follows the copy. The decisive status interaction follows finalization. Once that interaction returns normally, the function writes one to the derived control byte, regardless of whether the returned status is zero or nonzero.

The explicit result is then determined as follows:

| Reached outcome | Designated copy | Decisive status interaction | Explicit result |
|---|---|---|---|
| Quantity rejected | Absent | Absent | 0x11 |
| Quantity accepted; descriptor rejected | Absent | Absent | 0x11 |
| Both accepted; decisive status zero | Already completed | Completed before the control-byte write of one | 0 |
| Both accepted; decisive status nonzero | Already completed | Completed before the control-byte write of one | 0x11 |

All rows require normally returning dependencies and valid reached operations. Common cleanup occurs before either explicit result is returned.

There is no established rollback for a nonzero decisive status. There is also no preservation guarantee for a successful copy: finalization, decisive status, the control-byte write, and cleanup all occur later and may affect aliased storage.

### Phase lifecycle

Both processing phases use the same processing and wrapper workspaces. Quantity processing uses selector zero; descriptor processing uses selector one. Both receive the ordered additional configuration values 5, 1024, 1, and 0.

Each reached phase receives exactly one finalization call on every explicit normal-return path:

- Quantity rejection is followed by quantity finalization.
- Quantity acceptance is followed by quantity finalization before descriptor-phase initialization.
- Descriptor rejection is followed by descriptor finalization.
- Descriptor acceptance is followed by the copy and then descriptor finalization.

A nonzero decisive status does not cause a second descriptor finalization.

These lifecycle labels describe call roles only. They do not establish construction, destruction, resource release, restoration, or transaction semantics.

| Derived control byte | Zero write after acquisition. |

Both control-byte writes use the retained acquisition result plus 24. There is no second acquisition. The later address calculation occurs after the decisive status interaction.

For signed 32-bit addition, the retained acquisition value must be at most **2,147,483,623** for adding 24 to remain representable. Adding positive 24 creates no additional lower-bound restriction within the signed 32-bit range. Representability alone does not establish a valid address conversion or accessible byte.

Rejection omits the direct control-byte write of one. It does not establish that the byte remains zero: dependencies and aliases may change it.

### Ownership and aliasing

No direct allocation or release of destination storage is visible. Supplying storage to a dependency does not by itself establish ownership transfer, retention rights, or release permission.

No general disjointness guarantee is established among the destination, source, descriptor, workspaces, token, setup target, shared setup value, and control location. Subject to valid reached accesses:

- Setup writes may affect the destination before eligibility is known.
- The copy may modify storage later consumed by a dependency.
- The later control-byte write may overwrite one byte of the copied value.
- Dependencies may change or invalidate previously observed storage.

“Copy absent” therefore means only that the designated four-byte transfer is absent, not that destination storage is unchanged.
