# F-501804493e4c

## Purpose

F-501804493e4c examines a mutable node’s type byte, conditionally finds or creates a table record, annotates the node, or delegates child traversal.

Established dispatch behavior:

- Types `0x95` and `0x97` use filter-gated, pair-keyed registration.
- Type `0x96` uses a separate registration table when context depth is zero.
- Every other case, including type `0x96` at nonzero depth, uses the traversal path.

Ordinary returns are four-byte values restricted to zero and one. One identifies a registration-oriented path, not necessarily successful registration: filter rejection and negative slot indices also return one. Traversal paths return zero regardless of the traversal dependency’s result.

“Registration,” “filter,” “association,” and “sequence” describe observable roles. Their domain meanings are inferred, not established.

## Interface

### Arguments and representation

The four arguments are:

1. A context reference.
2. A mutable node reference.
3. An opaque four-byte traversal argument.
4. A four-byte slot-selection seed, also forwarded to traversal.

The supplied representation uses four-byte references and integers. Equal width does not establish interchangeability between references and numerical values.

At entry, the function captures the context’s filter reference, registration-state reference, and runtime-state reference, in that order, then reads the node’s type byte. It also initializes local output-index storage from the fourth argument. The captured structure references are not generally refreshed after dependency calls; fields within those structures may be reread.

## Behavior

### Pair-keyed processing

This path applies to types `0x95` and `0x97`, independent of depth.

#### Filter gate

A null captured filter reference immediately returns one. No registration annotation, type normalization, or traversal occurs.

A nonnull filter has a signed two-byte count at offset `0x00`. Entries start at `0x08`, have stride `0x30`, and expose their compared four-byte key at entry offset `0x18`; the first key is therefore at filter offset `0x20`.

Entries are examined in increasing index order. Each iteration checks the count before reading the node’s primary key and comparing it with the entry key. The node primary key is reread for each examined entry. The matching value is retained for the subsequent pair-table search.

A nonpositive count, or exhaustion without equality, returns one without registration or traversal. Equality is direct four-byte equality, not a dependency-defined relationship.

#### Pair-table search

The initial pair-table reference establishes a cursor. Records have stride `0x18`:

| Offset | Width | Content |
|---|---:|---|
| `0x00` | 4 | Payload |
| `0x04` | 4 | Primary key |
| `0x08` | 4 | Secondary key |
| `0x0C` | 4 | Association identifier |
| `0x10` | 4 | Sequence number |
| `0x14` | 4 | Originating node reference |

The signed count is read at each loop condition. Primary keys are compared first, using the primary-key value retained from filter acceptance. Only a primary match causes the node’s secondary key and the record’s secondary key to be compared.

The first matching pair stops the search. Otherwise the cursor advances by `0x18` and the index increases. After exit, the signed count is read again. Creation is attempted when that count is less than or equal to the search index.

No dependency is called during this search. Under stable storage, an existing match is reused without replacing its record contents or consuming counters.

#### Pair-record creation

Before F-d8fb735e64d8, output-index storage is reset to the fourth argument. The dependency receives, in order:

1. Current root handle.
2. Current pair-table reference.
3. Element size `0x18`.
4. Literal mode `3`.
5. Address of the pair-table count.
6. Address of its management field.
7. Address of output-index storage.

Its returned reference is written to the pair-table field unconditionally. The output index is then tested as signed four-byte data. A negative value suppresses record initialization.

For a nonnegative value, the selected record address uses the returned reference and that output index. Initialization order is:

1. Copy node payload `0x3C`.
2. Copy primary key `0x24`.
3. Copy secondary key `0x28`.
4. Read the shared sequence counter and write its incremented value back.
5. Store that incremented value as the record sequence.
6. Store the current node reference.
7. Store provisional association value `0xFFFFFFFF`.
8. Resolve the association or consume the fallback counter.

Association resolution reads the optional source reference at registration-state offset `0x08`. Its signed four-byte count is at `0x00`, and its entry-array reference is at `0x0C`. Entries have stride 12; their first four-byte field supplies a candidate-node reference.

The array reference establishes the cursor once; the source count is reread at each loop condition. Candidate tests occur in order: type exactly `0x95`, primary-key equality, then secondary-key equality. The current node’s keys are read for the reached comparisons. The first qualifying candidate supplies its zero-based source index.

After scanning a present source, the record’s association field is tested as signed. A nonnegative value bypasses fallback assignment. Otherwise, or when the source is absent, the current fallback counter is stored in the record and the counter is incremented. A type-`0x97` candidate does not qualify.

#### Pair annotation

After reuse or attempted creation, writes occur in this order:

1. Captured registration-state reference to node `0x2C`.
2. Type byte `0x97`.
3. Current output-index value to node `0x30`.

The function returns one. Negative output indices still reach these writes.

There is no separate saved index for final annotation on this path: the output-index storage itself supplies the final value.

### Type-`0x96` registration at depth zero

#### Search and post-search decision

The function loads the type-`0x96` table reference once to establish its search cursor and initializes a separate search index to zero. Records have stride `0x10`:

| Offset | Width | Content |
|---|---:|---|
| `0x00` | 4 | Node reference |
| `0x04` | 4 | F-d92bc662c47a result |
| `0x08` | 4 | Sequence number |
| `0x0C` | 4 | Conditional identifier |

At each loop condition, the signed table count is reread. If the search index is smaller, F-728a4665dcf4 receives the cursor’s node reference and the current node reference.

- Zero advances the index by one and the cursor by `0x10`.
- Nonzero exits without advancing either.
- An exhausted count exits without a comparison call.

The cursor continues from the initially loaded table reference. Changes to the table-reference field during comparison do not redirect it.

After exit, the signed count is read again. Creation is attempted if this count is less than or equal to the search index. Thus, nonzero comparison does **not** unconditionally select an existing record. Reuse requires the post-exit count to remain greater than the index.

#### Creation, index snapshot, and initialization

Creation first captures the nested runtime byte described above. F-d8fb735e64d8 then receives the current root handle, current type-`0x96` table reference, element size `0x10`, mode `3`, addresses of its count and management field, and the output-index address. That output storage was initialized from the fourth argument.

Immediately after the call:

1. The output index is copied into a separate saved annotation index.
2. The returned table reference is written to registration-state offset `0x20`.
3. The live output-index storage is tested for nonnegativity.
4. If eligible, that live value and the returned reference determine the record address.

Final annotation uses the saved copy, not the live output-index storage. These are distinct values if later activity modifies storage whose address was passed to the dependency. Neither non-retention of that address nor preservation by subsequent dependencies is established.

For an eligible record, initialization proceeds:

1. Store the current node reference.
2. Increment the shared sequence counter.
3. Store the incremented sequence value.
4. Read node `0x10`. If null, use auxiliary value zero; otherwise reread the reference and read its first four-byte value.
5. Call F-d92bc662c47a with the current root handle, node `0x14`, unsigned node `0x18` logically shifted right once, the auxiliary value, the captured byte, and zero.
6. Store the returned four-byte value at record `0x04`.
7. Read the node’s two-byte flags.
8. If bit `0x0010` is clear, store `0xFFFFFFFF` at record `0x0C`.
9. Otherwise, store the current runtime counter `0x44`, then increment that counter.

The selected record address is retained across F-d92bc662c47a. Neither the table reference nor record address is reacquired afterward. Flags and the conditional counter are read after that call.

Finally, write the captured registration-state reference to node `0x2C`, then the annotation index to `0x30`, and return one. For reuse, this index is the search index; for attempted creation, it is the saved post-acquisition copy. No type-byte store is performed.

### Traversal

All other dispatch cases use this path.

First read node `0x38`. If zero, return zero.

If nonzero:

1. Read and increment context depth.
2. Reread node `0x38`.
3. Invoke F-f0407b0f8a34 with that second child-reference value, F-501804493e4c as callback, context, fourth argument, context again, current node, and third argument, in that order.
4. After ordinary return, read the then-current depth and decrement it.
5. Return zero, ignoring the dependency result.

The tested and passed child references need not be identical. For example, if the child field aliases the depth field, the intervening increment changes the value supplied to traversal.

The decrement is not restoration of a saved entry depth. Dependency changes to depth affect the final result.

## Side effects

Record fields retain node references and copied keys. Their lifetime obligations belong to an external contract. Allocation, relocation, or release inside F-d8fb735e64d8 remains unknown.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid nonoverlapping storage, representable arithmetic, and dependencies preserving unrelated state.

1. **Absent filter:** Type `0x95` with a null filter returns one without annotation, normalization, or traversal.

2. **Filter rejection:** No matching primary key returns one without searching either registration table, even if children exist.

3. **Pair reuse:** Accepted keys match pair record 4. The node receives the registration-state reference, type `0x97`, and index 4. No sequence or fallback counter is consumed.

4. **Association qualification:** Source entry 2 referencing a matching type-`0x95` node supplies association 2. Changing that candidate to type `0x97`, with no other qualifier, causes fallback assignment and counter increment.

5. **Stable type-`0x96` match:** A comparison at index 3 returns nonzero and the post-exit count remains greater than 3. Index 3 is annotated; no creation call occurs.

6. **Count shrinks during comparison:** At index 0, F-728a4665dcf4 returns nonzero but changes the count to zero. The post-exit test requires creation through F-d8fb735e64d8.

7. **Reference changes during search:** At index 0, comparison returns zero and replaces the table-reference field while leaving count 2. The next comparison reads the record at the original base plus `0x10`, not the replacement base.

8. **Saved versus live index:** Type-`0x96` acquisition produces index 2. Initialization selects record 2. If F-d92bc662c47a subsequently changes retained output-index storage to 9, final node annotation still uses saved index 2. This scenario is conditional on dependency retention and mutation, not evidence that either occurs.

9. **Negative acquisition index:** With nonoverlapping storage and output `-1`, the returned table reference is stored, initialization is skipped, and annotation receives `0xFFFFFFFF`. Pair processing also normalizes the type to `0x97`. Both paths return one.

10. **Flag timing and unsigned quantity:** A new type-`0x96` record with quantity `0xFFFFFFFF` passes `0x7FFFFFFF` to F-d92bc662c47a. Conditional-identifier assignment follows the flag bit visible after that dependency returns.

11. **Child/depth alias:** On a traversal path, suppose node `0x38` and context depth denote the same four-byte cell initially containing 5. The nonzero test succeeds, the increment changes it to 6, and traversal receives child-reference bits 6. If traversal leaves depth unchanged, the final decrement produces 5.
