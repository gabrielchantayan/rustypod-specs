# F-391e3d30e634

## Purpose

F-391e3d30e634 attempts to obtain a 32-byte-aligned memory region for a positive, signed-32-bit-sized request. A successful allocation includes internal metadata before the returned address and increases a shared outstanding-byte counter. A shared peak counter is raised when the updated outstanding count exceeds it.

The function can invoke a recovery dependency before allocation when an enabled accounting threshold is reached, and again after an initial allocation failure. The meaning and effectiveness of that recovery operation are not established.

The function returns either an aligned address represented by a 32-bit unsigned value or zero. Zero can result from an inadmissible request, a nonzero gating result, or two unsuccessful allocation attempts. The interface does not distinguish these outcomes.

## Interface

### Input

One 32-bit unsigned request value, interpreted as signed for the initial admissibility check.

Accepted bit patterns are:

- Minimum: 1.
- Maximum: 2,147,483,647, or 0x7fffffff.

Rejected bit patterns are:

- Zero.
- Every value from 0x80000000 through 0xffffffff.

Consequently, this is not an interface for the full unsigned-32-bit size range.

### Output

A 32-bit unsigned value:

- Zero indicates that no successful result was produced.
- A nonzero successful result is an address divisible by 32.

The returned address is an interior address within the underlying allocation, not the allocator’s base address.

### Referenced shared state

For this contract, **accounting record** denotes the record whose address is captured after the preparation dependency returns. **Control record** denotes the separately referenced record containing the threshold-enable field.

The relevant layout is:

| Record | Byte offset | Width | Meaning established by use |
|---|---:|---:|---|
| Control record | +8 | 32 bits | Zero disables the preliminary threshold check; any nonzero value enables it |
| Accounting record | +0x20 | 32 bits | Threshold low word |
| Accounting record | +0x24 | 32 bits | Threshold high word |
| Accounting record | +0x38 | 32 bits | Outstanding-byte count low word |
| Accounting record | +0x3c | 32 bits | Outstanding-byte count high word |
| Accounting record | +0x40 | 32 bits | Peak-byte count low word |
| Accounting record | +0x44 | 32 bits | Peak-byte count high word |

Each paired quantity has a low 32-bit word and a high 32-bit word. These offsets establish word significance, not byte endianness.

The comparisons use signed interpretation of the high words, with unsigned low-word comparison resolving equal high words. Thus, the paired comparisons are signed-64-bit-style comparisons, not unrestricted unsigned-64-bit comparisons.

### Preconditions

Defined successful operation requires:

- Valid shared-record addresses and readable fields when accessed.
- Writable accounting fields when a successful allocation is recorded.
- A successful allocator result that supports the metadata writes and the requested payload.
- Address arithmetic that yields valid locations without wrapping into unrelated memory.
- Appropriate exclusion or other synchronization if concurrent access would otherwise invalidate the accounting or allocation assumptions.

The function does not establish these conditions itself.

## Behavior

### Request filtering

The signed-32-bit positivity check occurs before dependency calls or shared-state access.

For a rejected request, the function returns zero immediately. It does not perform preparation, threshold checking, gating, allocation, metadata initialization, or accounting updates.

For an accepted request, the sign-extension contribution used in subsequent two-word arithmetic is zero.

### Preparation and accounting-record capture

The function first calls F-54383d765e10 without arguments.

After that dependency returns, it captures the accounting-record address for later successful-allocation accounting. Preparation may therefore influence which record is captured.

The control record’s enable field is then inspected. No assumption is made that preparation preserves any global state.

### Conditional threshold action

If the enable field is zero, this preliminary action is skipped.

If it is nonzero, the function forms a projected outstanding count by adding the requested byte count to the current outstanding count:

- The low-word addition is 32-bit addition.
- Carry out of the low word is added to the high word.
- The accepted request contributes zero to the high word apart from that carry.
- The arithmetic has no separately reported overflow condition.

The projected count is compared with the stored threshold using the paired signed comparison described above.

F-570f57d734a2 is called with the original requested byte count when the projected count is **greater than or equal to** the threshold. Equality triggers the call.

This call is not itself a rejection or a successful allocation. If it returns, execution continues to the gating dependency. There is no explicit second threshold check after it returns.

The projected value is not saved for the eventual accounting write. Successful-allocation accounting later reads the outstanding count again. Effects of intervening dependencies can therefore influence that update.

### Allocation gate

After the preliminary threshold action, if any, the function calls F-19123db18ab4 with the 32-bit value zero.

- A zero result permits allocation attempts.
- Any nonzero result causes the function to return zero without calling the allocator.

Preparation and a threshold-triggered recovery call may already have occurred before a nonzero gate result is observed.

### Allocation and retry

Each allocation attempt calls F-849ccca8c593 with:

**requested byte count + 44 bytes**

For accepted inputs, this argument lies between 45 and 2,147,483,691 bytes, inclusive. This addition does not wrap a 32-bit unsigned value.

If the first attempt returns a nonzero address, the function proceeds directly to initialization.

If the first attempt returns zero:

1. F-570f57d734a2 is called with the original requested byte count.
2. F-849ccca8c593 is called again with the same request-plus-44 size.
3. A second zero result causes an immediate zero return.

There is exactly one retry after an allocation failure. The retry does not repeat preparation, the threshold comparison, or the gate.

A single invocation can call F-570f57d734a2 twice: once for the preliminary threshold condition and once after the first allocation failure.

### Successful allocation layout

Let **base** be the nonzero address returned by F-849ccca8c593.

The returned payload address is obtained by adding 44 bytes to base and rounding that address downward to a multiple of 32. Equivalently, the low five bits of the 32-bit address sum are cleared.

Subject to nonwrapping address arithmetic, this places the payload after the fixed header while keeping a requested-size payload within the requested underlying allocation.

The function performs these metadata writes in this order:

| Location | Width | Written value |
|---|---:|---|
| base + 4 | 32 bits | Zero |
| base | 32 bits | Original requested byte count |
| payload address − 4 | 32 bits | Payload address minus the address base + 8 |

The first two words therefore represent the accepted requested size as a low/high pair with a zero high word.

The word immediately before the payload stores a displacement relative to base + 8. It does **not** directly store the complete distance from the allocation base to the payload.

For ordinary four-byte-aligned base addresses, and without address wrap:

- Payload displacement from base is between 16 and 44 bytes, in multiples of four.
- The stored displacement is between 8 and 36 bytes, in multiples of four.
- The displacement word does not overlap the two size words.

Four-byte alignment of the allocator result is a required compatibility property for the word-oriented accesses, rather than a property proven about the allocator dependency here.

The function does not initialize the requested payload bytes.

### Successful-allocation accounting

After metadata initialization, the function updates the accounting record captured after preparation.

It reads the then-current outstanding count and adds the original requested byte count, carrying from the low word into the high word. The additional 44 allocation bytes and any alignment padding are not included.

The observable writes occur in this order:

1. Outstanding-count low word.
2. Outstanding-count high word.

The resulting count is compared against the peak count using the signed paired-word comparison.

If the peak is strictly less than the updated outstanding count, the peak is replaced. The peak low word is written before the peak high word. The replacement values are read from the outstanding-count fields.

If the peak equals or exceeds the updated outstanding count, neither peak field is written.

The function then returns the aligned payload address.

## Side effects

### Direct effects

For a successful allocation, direct effects are:

- Three 32-bit allocation-metadata writes.
- Two outstanding-counter writes.
- Two additional peak-counter writes if the peak must increase.

There is no direct payload initialization, deallocation, or rollback.

For rejected inputs, there are no direct shared-state accesses or dependency calls.

For gate rejection or two allocator failures, the function performs no allocation-metadata writes and no direct accounting-counter writes. Dependencies already called may nevertheless have modified state.

### Visibility and ordering

Metadata initialization precedes the accounting writes. Accounting completion precedes the successful return.

The two-word counter updates are separate stores, not an atomic 64-bit publication. An observer without suitable synchronization can potentially see an intermediate low/high combination. Peak updates are likewise split across two stores.

The supplied representation establishes the order of separate writes and dependency calls. It does not establish a unique machine-level order for every read occurring within an arithmetic or comparison expression.

### Ownership

On success, the caller receives an interior payload address associated with an underlying nonzero allocator result.

The function retains no demonstrated independent ownership handle and calls no release dependency. The correct release operation, payload lifetime, and whether the stored metadata is sufficient for some separate release interface are unknown.

F-570f57d734a2 may affect existing allocations or global accounting; neither ownership transfer nor preservation is established by this function.

No dependency is assumed to preserve global pointers, counters, enable fields, or allocation state.

In particular, the captured accounting-record address remains the target for successful-allocation bookkeeping even if an intervening dependency changes the global reference from which that address was originally obtained. The captured record must remain valid.

Dependency termination, exceptions, nonlocal exits, internal synchronization, and memory-release behavior are not specified by the supplied evidence.

## Acceptance examples

These are conditional contract examples derived from static evidence. They are not runtime observations.

### Rejected signed interpretation

For an input of 0x80000000, the result is zero despite the input’s unsigned magnitude being positive. No dependency is called.

The same no-call behavior applies to zero and 0xffffffff.

### Disabled threshold check

Assume the request is 64, the control field is zero, the gate returns zero, and the first allocator call succeeds.

The allocator receives 108. No preliminary recovery call occurs, regardless of the stored threshold. Metadata is initialized, the outstanding count increases by 64, and an aligned payload address is returned.

### Exact threshold equality

Assume an outstanding count of 100, a threshold of 164, an enabled threshold check, and a request of 64.

The projected count equals the threshold, so F-570f57d734a2 is called before the gate.

This does not guarantee that a later successful allocation leaves the outstanding count at 164: intervening dependencies may change it before the accounting update.

### Gate prevents allocation

Assume an accepted request and a nonzero gate result.

The result is zero, and F-849ccca8c593 is never called. Preparation has already occurred, and a threshold-triggered recovery call may also have occurred.

### Recovery after allocation failure

Assume a request of 32, a zero gate result, and allocator results of zero followed by a usable nonzero base.

The allocator receives 76 on both attempts. Between them, F-570f57d734a2 receives 32. Only the successful allocation receives metadata, and the function directly adds 32—not 76—to the outstanding count.

If the second result is also zero, the function returns zero without direct counter updates.

### Concrete alignment layout

Assume a request of 64 and an allocator base of 0x1000, with valid writable storage.

The allocator request is 108 bytes. The returned payload address is 0x1020.

The metadata values are:

- At 0x1004: zero.
- At 0x1000: 64.
- At 0x101c: 24.

The stored 24 is the distance from 0x1008 to 0x1020, not the 32-byte distance from base to payload.

### Low-word carry and peak behavior

Assume the outstanding count has high word zero and low word 0xfffffff0 immediately before accounting, and the successful request is 32.

The updated outstanding count has high word one and low word 0x10.

If the peak equals that updated value, it is unchanged. If the peak is smaller under the specified signed paired comparison, both peak words are replaced, low first.

## Uncertainties

The following are **documented_only**:

- The operational meaning of preparation, gating, and recovery.
- The allocator’s guaranteed alignment, storage lifetime, and failure semantics beyond the caller’s zero/nonzero handling.
- The supported release interface for the returned interior address.
- The intended units or policy meaning of the threshold, beyond its comparison against requested-byte accounting.
- Whether a broader subsystem prevents counters from entering the signed-negative half of the paired representation.
- Behavior at address-space wraparound or when shared-record pointers become invalid.
- Synchronization guarantees supplied by callers or dependencies.
- Any additional indirect state changes performed by dependencies.
- Runtime behavior of the supplied representation on its original execution platform.

The apparent intent is aligned allocation with outstanding and peak byte tracking, plus pressure-related recovery. That interpretation is inferred; it does not establish undocumented dependency behavior.

## Evidence

Established static evidence consists of the supplied function representation and the supplied opaque dependency mapping.

It supports the input bounds, dependency-call conditions, single retry, request-plus-44 allocation size, 32-byte address alignment, metadata layout, requested-byte-only accounting, inclusive preliminary threshold comparison, strict peak comparison, and explicit write ordering described above.

The paired comparison interpretation follows from the low-word borrow handling and signed-overflow-aware high-word comparisons. It is not based on an assumption that the counters are always nonnegative.

No implementation beyond the supplied material was inspected. No runtime tests were performed.
