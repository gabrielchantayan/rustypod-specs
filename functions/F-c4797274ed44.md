# F-c4797274ed44

## Purpose

F-c4797274ed44 processes a non-null address by locating the first descriptor whose inclusive address interval contains it. It increments that descriptor’s 32-bit progress counter and then follows one of two paths:

- Store the address at the front of a descriptor-local singly linked chain.
- If the incremented counter equals a descriptor threshold and the descriptor is not the sole descriptor in the initially captured context’s list, attempt to unlink and release the descriptor’s backing allocation.

These are established structural behaviors. Interpreting the operation as returning an item to a pool, and the counter as a count of returned items, is plausible intent rather than an established interface guarantee.

The function returns no value. Its observable results are memory writes, dependency calls, early returns, and a possible non-returning error path.

## Interface

### Input and result

The sole input is an address, or null.

For the ordinary chain-insertion path, the address must identify at least four writable bytes. The function stores a 32-bit link at that address. For other paths, the input is used only in interval comparisons and is not necessarily dereferenced.

The function has no status result. A null input, rejected gate, unsuccessful search, failed descriptor-tag check, ordinary insertion, and successful release all return without a distinguishable return value.

### Widths and layouts

The supplied representation uses 32-bit addresses and 32-bit words. Offsets below are byte offsets. The two allocation-header indices are unsigned 16-bit values.

A globally reachable context reference supplies a context address from offset `+4`. That context contains a descriptor-list head at offset `+12`.

Each searched descriptor has the following accessed layout:

### Preconditions

Beyond the explicit null-input check, the function does not establish memory safety. Applicable execution paths require readable global references, readable context and descriptor fields, and writable counters, links, and accounting locations.

Additional structural requirements include:

- The searched list must reach a match or terminate for the search to finish.
- The owner list used during unlinking must permit the predecessor search to terminate if the descriptor is not its head.
- Header indices and a dependency-supplied accounting index must address valid accounting locations.
- The input must be writable if ordinary insertion occurs.
- Any required synchronization or protection against concurrent mutation must be supplied externally or by dependencies whose behavior is not provided.

There is no visible validation of input alignment, item boundaries, prior insertion, or correspondence between the input and a particular allocated item.

## Behavior

### 1. Null handling, context capture, and gate

A null input returns immediately. This path performs no depicted global access and calls no dependency.

For a non-null input, the function first captures a context address from the global context reference’s `+4` field. It then calls F-8ff94386ac71.

If that dependency returns zero, the function returns without searching or making a direct write. Side effects of the dependency remain possible.

If it returns nonzero, the function reads the descriptor-list head at offset `+12` of the previously captured context. The context address is not recaptured after the call. The head is read after the call, so any dependency modification to that captured context’s head can affect the search.

### 2. First matching interval

The function traverses descriptors through their `+8` next links.

A descriptor matches when the input address is both:

- Greater than or equal to its lower bound.
- Less than or equal to its upper bound.

The lower comparison precedes the upper comparison; a failed lower comparison does not require the upper-bound read in the depicted expression.

The first matching descriptor is selected. Overlapping ranges therefore resolve by list order. If traversal reaches null without a match, the function returns without a direct write.

These are address comparisons, not comparisons of the contents at the input. The supplied representation does not conclusively establish unsigned machine-address ordering versus the ordering represented by its pointer comparisons. Behavior involving ordering-sensitive high-bit addresses remains unresolved.

### 3. Counter increment and branch selection

For a selected descriptor, the function reads its 32-bit progress counter, increments it, and writes the result back before any tag validation or item-chain write.

It compares the incremented result with the threshold. The counter write is not rolled back on any subsequent early return or error path.

The arithmetic is 32-bit. Its machine-level result is the low 32 bits of the sum; no checked-overflow handling is depicted. The representation’s signed integer types do not justify a portable signed-overflow contract.

If the incremented value does not equal the threshold, execution proceeds directly to ordinary insertion.

If it equals the threshold, the function rereads the descriptor-list head from the initially captured context:

- If that head is the selected descriptor and the selected descriptor’s next link is null, the descriptor is treated as the sole list member. Execution proceeds to ordinary insertion.
- Otherwise, execution enters the removal/release path.

Thus threshold equality alone does not imply release. The sole-member exception preserves the descriptor and still links the input into its item chain.

### 4. Ordinary item-chain insertion

The function performs these writes in order:

1. Store the descriptor’s current `+28` chain-head word into the first four bytes at the input address.
2. Store the input address into the descriptor’s `+28` chain-head field.

No release dependency is called on this path. The function then returns.

This overwrites the first word of the supplied item. It does not validate the previous head or detect duplicate insertion.

If the input aliases the descriptor, its fields, or other involved storage, the first write can affect the later operation. No general alias exclusion is enforced. The description as insertion into an independent item chain presumes non-conflicting storage.

### 5. Tag validation and owner-list unlinking

On the removal path, the selected descriptor’s tag is compared with a globally supplied expected tag.

A mismatch causes an immediate return. At that point:

- The progress counter has already been incremented.
- The input has not been added to the item chain.
- No descriptor release has occurred.

For a matching tag, unlinking uses the owner address stored in the descriptor, not necessarily the context captured before the gate call.

The function reads the owner’s list head:

- If the selected descriptor is that head, the owner’s head field is replaced by the selected descriptor’s next link.
- Otherwise, it traverses the owner list to find a descriptor whose next link is the selected descriptor. On success, that predecessor’s next link is replaced by the selected descriptor’s next link.
- If traversal reaches null without finding a predecessor, execution nevertheless continues to release processing.

A missing owner-list entry is therefore not an error return and does not prevent the later release attempt. Agreement between the search context and descriptor owner is an external invariant, not a checked condition.

### 6. Release preparation and header validation

After the unlink attempt, the function calls F-2fd8826557a4 with no explicit arguments.

It then captures an accounting-base address through a separate global reference. Because this capture occurs after the dependency call, changes made by that call can affect which accounting base is selected.

The function examines the 32-bit allocation control word eight bytes before the descriptor. Either of these conditions invokes F-a817d8d58c10:

- The control word is zero.
- Its least-significant bit is set.

That dependency is represented as non-returning. No recovery path is established if it unexpectedly returns.

This validation occurs after the counter increment and unlink attempt. Consequently, rejection can leave the descriptor already removed from a list. There is no depicted rollback.

For an accepted control word, the function calls F-c0fc6d033caa with the captured accounting-base address.

### 7. Accounting and final release calls

After F-c0fc6d033caa returns, the function reads the first unsigned 16-bit header index and obtains a size by masking the allocation control word with `0x3ffffffc`.

The mask retains bits 2 through 29 and clears bits 0, 1, 30, and 31. The resulting size is a multiple of four, between zero and `0x3ffffffc`, inclusive.

The function subtracts that size from four 32-bit accounting locations, in this order:

1. Accounting base plus `0x224 + 4 × first index`.
2. Accounting base plus `0x30c`.
3. Accounting base plus `0xe0 + 4 × second index`.
4. Accounting base plus `0x220`.

The second unsigned 16-bit header index is read for the third update. Each index has range 0 through 65,535, giving a scaled index range of 0 through 262,140 bytes before adding the table offset.

The function then calls F-09dcb55e8e0a with no explicit arguments. Using its returned index, it decrements:

5. The 32-bit location at accounting base plus `0x310 + 4 × returned index`.
6. The 32-bit location at accounting base plus `0x390`.

Finally, it rereads the allocation control word, masks it again with `0x3ffffffc`, and subtracts that newly obtained size from:

7. The 32-bit location at accounting base plus `8`.

The final subtraction is not guaranteed to use the size used for the earlier four subtractions. F-09dcb55e8e0a may affect the header, and no preservation contract is supplied.

The function then calls:

1. F-cc6c9b4a0f68 with the captured accounting base and the address of the allocation control word, eight bytes before the original descriptor.
2. F-e586bff64fb7 with the same captured accounting base.

It then returns. The original header address remains the argument to F-cc6c9b4a0f68 even though a separate working pointer is used for an indexed counter earlier in this sequence.

Accounting operations have no depicted underflow checks. Their stored results are 32-bit arithmetic results. Computed accounting addresses can overlap each other or other storage; the stated update order matters in such cases. No bounds check is shown for the index returned by F-09dcb55e8e0a.

## Side effects

Direct effects depend on the path:

| Path | Direct effects |
|---|---|
| Null input | None depicted |
| Gate returns zero | None after context capture |
| No matching descriptor | List reads only |
| Ordinary insertion | Counter increment; input first-word overwrite; chain-head replacement |
| Threshold equality, sole descriptor | Same as ordinary insertion |
| Removal-path tag mismatch | Counter increment only |
| Removal/release | Counter increment; possible list unlink; ordered accounting writes; dependency calls |

The function does not visibly release the input address as a standalone allocation. Instead, the release dependency receives the selected descriptor’s preceding header address.

Actual ownership transfer, reclamation, lock state, and dependency-induced global effects are unknown. Calling a dependency is not evidence that it frees memory or preserves unrelated state.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid accessible memory, non-conflicting storage, and dependencies that return normally without modifying the described fields.

1. **Null input.** The function returns without calling the gate or reading the depicted globals.

2. **Rejected gate.** A non-null input causes context capture and a gate call. If the gate returns zero, the descriptor-list head is not subsequently read by this function.

3. **Inclusive endpoints.** An input equal to either interval endpoint matches that descriptor if no earlier descriptor matches. A nonmatching input that reaches the end of the list causes no counter increment.

4. **Ordinary insertion.** A matching descriptor has counter 3, threshold 8, and item-chain head address A. Processing input B changes the counter to 4, stores A at B, and changes the chain head to B.

5. **Threshold reached with one descriptor.** The selected descriptor is the captured context’s head and has a null next link. Reaching the threshold still inserts the input into the item chain. It does not validate the tag or call release dependencies.

6. **Threshold reached with another descriptor present.** The selected descriptor is the head and has a non-null successor. With a valid tag and stable owner information, its owner’s head becomes that successor before release preparation begins. The input receives no direct item-chain write.

7. **Tag mismatch.** Removal is selected, but the tag differs from the global expected value. The incremented counter remains stored. Neither insertion nor release follows.

8. **Descriptor absent from owner list.** The search context contains the selected descriptor, but its owner list is finite and does not contain it. After the unsuccessful predecessor search, the release sequence still proceeds.

9. **Header rejection after unlink.** With a valid tag but a zero control word, unlinking can occur before F-a817d8d58c10 is invoked. Restoration of the list is not established.

10. **Masked size and reread.** If the control word is `0x40000022`, it passes the depicted validity check and contributes a masked size of `0x20`. If F-09dcb55e8e0a changes that word to `0x40`, the final base-plus-eight subtraction uses `0x40`, while the earlier four subtractions used `0x20`.

11. **Duplicate insertion.** If the input already equals the item-chain head and ordinary insertion occurs, its first word is set to its own address. No duplicate-detection path prevents that self-link.
