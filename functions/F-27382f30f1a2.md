# F-27382f30f1a2

## Purpose

F-27382f30f1a2 conditionally constructs and submits a request containing data derived from three shared 32-bit fields. A zero second argument permits an immediate successful return when three current-versus-saved comparisons match. A nonzero second argument disables that shortcut.

The function distinguishes two ways of locating state:

- It captures a state-block address from a shared root at entry.
- It subsequently references the shared root again to obtain the initial field A value and evaluate the shortcut.
- After shortcut evaluation, its state-block accesses use the captured address.

These accesses need not concern the same block if the shared root changes. The supplied body does not establish root stability.

Local failure results are decimal 19 and 28. Otherwise, the function returns zero for the shortcut or returns the submission dependency’s 32-bit status. A zero submission status triggers three saved-field assignments in the captured block.

“Request,” “current,” “saved,” and “submission” describe visible roles. Their domain meanings are not established.

## Behavior

### Root capture and shortcut evaluation

The function first captures the address held in the shared root. It then tests whether the second argument is zero and obtains initial current A through a separate root reference at offset `+0x14`.

The initial current-A read occurs even when the second argument is nonzero. It is not a read through the previously captured address.

If the second argument is zero:

1. Saved A is obtained through the shared root at `+0x20` and compared with the already obtained initial A.
2. Only if A matches, current B and saved B are obtained through root-relative accesses at `+0x1C` and `+0x24` and compared.
3. Only if B also matches, current C and saved C are obtained through root-relative accesses at `+0x18` and `+0x28` and compared.

All three comparisons matching causes immediate return of zero. A mismatch prevents later comparison stages. A nonzero second argument prevents all saved-field comparison stages.

Each field access in this shortcut logic references the shared root, rather than the captured block address. The body does not establish that successive root references yield the same address. It also does not establish the operand-read order within the B comparison or within the C comparison. The order between comparison stages is established.

Consequently:

- Initial A and saved A may come from different blocks.
- The two operands of a B or C comparison are not guaranteed to come from one block if the root changes between accesses.
- Successful shortcut evaluation establishes equality of the values actually observed, not necessarily equality of all six fields in one block at one instant.
- Equating the captured block with every block used during comparison requires an additional root-stability condition.

The shortcut performs no dependency calls and no explicit shared-state writes. Equality compares all 32 bits; signed interpretation does not affect it.

### Processing gate

If the shortcut is not taken, F-dddd9a40027c receives the initial A obtained through the root during entry processing.

A zero result causes immediate return of 19. No payload initialization, construction, submission, or trailing dependency calls follow.

A nonzero result permits continuation; its value is otherwise discarded.

This gate argument is not refreshed from the captured block. It can therefore differ from the A later supplied for payload preparation, either because the root changed before initial A was read or because intervening activity changed field contents.

### Payload preparation

After a nonzero gate result, all three local 32-bit slots are initialized to zero, in payload-offset order `+0`, `+4`, `+8`.

Preparation then proceeds in this order:

1. F-b9d9c0b9bfab receives the first slot’s address and a fresh read of captured-block current A.
2. F-b9d9c0b9bfab receives the third slot’s address and a fresh read of captured-block current C.
3. F-b7af80e829ec is called.
4. Its returned object supplies the table used for U-04, an indirect call through byte offset `+0x90`.
5. If U-04 returns nonzero, F-b9d9c0b9bfab receives the middle slot’s address and a fresh read of captured-block current B.

U-04 has no explicit arguments in the supplied invocation. Its receiver convention and complete ABI are unknown.

A zero U-04 result omits the explicit B transformation and its associated current-B read. The middle slot is guaranteed to have been initialized to zero, but not guaranteed to remain zero: the earlier transformation calls have unknown write bounds.

These field reads are separated by calls. They do not establish an atomic snapshot, even though their base address is the same captured address.

### Saved-field update

Only a zero submission status triggers these explicit operations:

1. Read current A from the captured block and write it to saved A in that block.
2. Read current B from the captured block and write it to saved B in that block.
3. Read current C from the captured block and write it to saved C in that block.

These are fresh post-submission reads. They do not reuse initial A, comparison operands, or prepared payload values.

A changed shared root does not redirect these assignments to its new target. The captured address remains their base. The update consists of three separate 32-bit assignments, not an established atomic transaction.

Unknown dependencies may change the captured block before, during, or after this sequence. The direct assignments do not guarantee that the same values remain present at return.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests.

### Stable-root matching state

Given a zero second argument, an unchanged root throughout evaluation, and matching A, B, and C values at their respective comparison reads:

- Return zero.
- Make no dependency calls.
- Perform no explicit saved-state writes.

An atomic six-field snapshot is not additionally guaranteed.

### Root changes after capture

Suppose entry captures block P, then the root changes to block Q before initial A is read and remains Q through shortcut evaluation.

- Initial A and all shortcut operands come from Q.
- If all comparisons match and the second argument is zero, return zero without inspecting P’s saved fields.
- If processing continues, the gate receives the initial A from Q.
- Payload preparation, construction-state reads, trailing state reads, and any explicit saved-field updates use P.

Neither P nor Q is required to equal the other.

### Root changes during comparison

Given a zero second argument, initial A read from Q, and saved A later read from R:

- The A stage succeeds if those two observed 32-bit values match.
- B and C stages remain conditional on preceding matches.
- Successful shortcut evaluation does not prove that Q, R, or any single block contains three matching pairs simultaneously.

### Forced processing and gate failure

Given a nonzero second argument:

- Still capture the root and obtain initial A through a separate root reference.
- Do not perform saved-field comparisons.
- Call F-dddd9a40027c with that initial A.
- If it returns zero, return 19 without payload preparation or later calls.

### Capability disabled

Given a nonzero gate result and zero from U-04:

- Prepare A and C through their transformation calls.
- Omit the B transformation.
- Supply the local 12-byte region to construction.

If both transformations write only their designated slots, the middle slot remains zero. Otherwise its construction-time value is documented_only.

### Construction failure

Given zero from F-cd7e1905512f:

- Return 28.
- Do not call U-01, F-256e8a77aa59, either trailing dependency, or U-03.
- Do not perform explicit saved-field assignments.
- Do not assume earlier dependency effects were undone.

### Submission success after state mutation

Given construction succeeds and submission returns zero after changing captured-block current A:

- Copy the changed A into captured-block saved A.
- Then copy fresh B and C reads into that block’s saved fields.
- Execute the trailing sequence.
- Return zero if all calls return normally.

Changing the root during submission does not redirect those explicit assignments.

### Submission failure

Given a nonzero submission status:

- Skip the explicit saved-field update.
- Still execute both U-02 calls, both trailing dependencies, and U-03.
- Return the submission status if trailing calls return normally.

Skipping direct assignments does not guarantee unchanged saved fields across unknown dependencies.
