# F-a836bb8e1d17

## Purpose

F-a836bb8e1d17 selects and returns the greater of two signed integer values supplied indirectly through pointers. For valid input objects whose values remain stable during the operation, its result is their signed maximum.

The result is an integer value, not an address, reference, ownership token, or indication of which input supplied it. Equal values produce that same integer result. Static evidence establishes that equality favors the second input’s selection path, but the returned value alone cannot distinguish that path from selection of an equal first input.

The maximum description requires stable inputs. The function provides neither an atomic snapshot of the pair nor synchronization with writers. Its source-level reads also do not establish a device-access protocol or a fixed sequence of physical memory transactions.

## Interface

### Inputs

The interface accepts two pointers, designated here as the **first input** and **second input**. Each points to one object of the implementation’s signed integer type.

Both objects must be readable for every access required by the operation. In particular:

- Neither pointer may be null.
- Each address must satisfy the target’s alignment and object-access requirements.

- Each object must hold a value that can legally be read using the declared integer type.
- The caller must satisfy any applicable synchronization requirements.

Both pointers are required even when the caller already knows which value is greater. There is no supported missing-input case.

The pointers need not designate distinct objects. Passing the same valid object as both inputs is permitted. No surrounding structure, array extent, length field, terminator, or additional element is part of this interface.

### Output

The function returns one value of the same signed integer type as the input objects.

There is no separate status output. Every valid value of the return type can be a successful result; no integer is reserved to signal an error. The function does not return either input pointer.

## Behavior

### Required result for stable inputs

When both objects are valid and stable, the function returns the larger signed value. If the values are equal, it returns their common value.

This requirement applies across the entire representable range, including negative values and the minimum and maximum values of the target type. There is no special handling for zero, negative values, or endpoints.

Selection is inclusive in favor of the second input: a comparison finding the first value less than or equal to the second permits the second input to supply the result. A strictly greater first value leaves the first input’s earlier selected value as the result.

These selection details matter to the source-level access behavior. They do not create an additional output identifying the selected object.

### Read relationships

The supplied body establishes more than the stable-input mathematical result, but less than a fixed hardware-load trace.

A value from the first input is selected before the comparison is evaluated. The comparison involves another reference to the first input and a reference to the second input. If the comparison favors the second input, a subsequent reference to that input supplies the selected result.

Consequently, the source-level ordering has these constraints:

- The first input’s initial value acquisition precedes evaluation of the comparison.
- The comparison precedes the conditional acquisition of the second input’s return value.
- The relative evaluation order of the two comparison operands is not established.

The comparison’s second-input reference and the conditional return-value reference are separate source evaluations. Likewise, the first input’s initial reference and comparison reference are separate source evaluations.

Neither input is volatile-qualified. Separate source references therefore do not guarantee separate machine loads: an implementation may reuse previously obtained values when permitted by the applicable execution rules. Conversely, the supplied evidence does not establish the emitted instruction sequence.

A consumer must not rely on this interface for an exact physical read count, a guaranteed ordering between the comparison’s operand reads, or a memory-mapped device transaction protocol.

### Stability and concurrent changes

The function does not expressly capture a single simultaneous snapshot of both input values. Its stable-input maximum guarantee must not be extended to mean “the maximum of both objects at one common instant” when either object can change.

The evidence also does not establish a general contract for changing inputs. If some separately defined execution environment permits changes between the source-level evaluations, the selected value need not correspond to a maximum of a simultaneous pair. Such an environment and its access rules would need independent justification.

This qualification does not make ordinary unsynchronized concurrent mutation valid. The input objects are not declared atomic, and the body supplies no locking or other synchronization. Conflicting unsynchronized accesses can place an execution outside defined behavior under the applicable language memory model.

There are no writes through either pointer, so sharing the object does not introduce an internal write/read interaction. Aliasing does not waive alignment, lifetime, initialization, or synchronization requirements.
