# F-6a9ae7071ae3

## Purpose

F-6a9ae7071ae3 sets bits in caller-supplied byte-addressed storage. Bit numbering proceeds from the most significant bit to the least significant bit within each byte, then continues at the most significant bit of the next byte.

For a nonnegative length whose endpoint calculation does not wrap, the operation sets exactly the half-open bit interval beginning at the supplied start position and extending for the supplied length. Bits outside that interval retain their values in ordinary memory without concurrent modification.

Contiguous forward-range setting is inferred intent. The routine does not validate the length or endpoint ordering. Negative lengths and wrapped endpoints follow the specific traversal rules below; they do not request reverse traversal or a circular range.

## Interface

The routine accepts three values:

| Input | Meaning | Representation in the supplied material |
|---|---|---|
| Start position | Index of the first selected bit | Unsigned integer |
| Length | Value added to the start position to determine the excluded endpoint | Signed integer |
| Storage address | Base address used for byte accesses | Signed integer interpreted through address calculations |

There is no return value, status code, changed-bit count, or returned storage address.

### Width and address model

The detailed numeric examples use 32-bit unsigned arithmetic, 32-bit signed inputs, and 8-bit storage units. These widths are consistent with the supplied representation, but their original type definitions and execution ABI are not independently established. Their external confirmation is `documented_only`.

Under this model:

- The length is converted to unsigned for addition to the start position.
- Endpoint arithmetic is modulo \(2^{32}\).
- Dividing a bit position by eight gives its byte offset.
- The remainder modulo eight gives its within-byte bit offset.
- Within-byte offset zero selects mask `0x80`; offset seven selects mask `0x01`.
- The largest byte offset directly derived from a bit position is `0x1FFFFFFF`.

The storage-address calculation combines the signed base input with an unsigned byte offset. Under the same width assumptions, its numeric result is modulo \(2^{32}\). Whether that numeric value identifies usable storage depends on the platform’s integer-to-address interpretation.

Multi-byte integer endianness does not change the specified ordering of bits within individual storage bytes.

### Preconditions and ownership

The caller must make every byte touched by the selected path accessible. No storage extent is provided, and the routine performs no bounds check.

Access requirements depend on how a byte is covered:

- A partially covered byte must be readable and writable. Each selected bit causes a separate byte read and byte write.
- A completely covered byte receives a direct write of `0xFF`. The represented operation does not read its prior value.

There is no explicit allocation, release, ownership transfer, or retention of the supplied address. The routine does not supply synchronization or establish exclusive access to storage.

A zero-length operation performs no storage access. This does not establish a general platform guarantee for arbitrary integer-to-address conversions; it establishes that the represented path does not dereference the address.

## Behavior

### Endpoint and layout

The endpoint is the unsigned sum of the start position and the length after unsigned conversion. Start and endpoint positions each determine a byte offset and a within-byte bit offset.

For ordinary nonwrapping ranges, the endpoint is excluded. An endpoint exactly at a byte boundary does not select any bit in the byte beginning there.

Processing has three possible phases, in this order:

1. A partial starting-byte update, only for a non-byte-aligned start.
2. Direct writes to complete bytes.
3. A partial ending-byte update, when the termination conditions permit it.

The routine does not reject an endpoint that numerically precedes the start.

### Partial starting byte

A nonzero start bit offset enables this phase.

When the start and endpoint have the same byte offset, the selected within-byte offsets begin at the start offset and stop before the endpoint offset. If the endpoint offset is equal to or below the start offset, no bit is selected and no byte access occurs in this phase.

When the start and endpoint have different byte offsets, the phase selects the remainder of the starting byte, through offset seven. This happens even when endpoint wrap or a negative length places the endpoint byte before the starting byte.

Each selected bit causes a distinct read–modify–write of the starting byte:

- The current byte value is read.
- The selected mask is combined with that value using bitwise OR.
- The combined byte is written to the same address.

Selected masks proceed toward the least significant bit. Already-set bits still cause their corresponding reads and writes.

After this phase, the current byte position advances by one, including when the phase selected no bits. For a same-byte interval, this advancement places the current position beyond the endpoint byte and prevents a later ending-fragment update.

A byte-aligned start skips this entire phase.

### Complete bytes

Every current byte whose offset is strictly below the endpoint byte offset receives one direct write of `0xFF`. These writes proceed in ascending byte-offset order.

No prior-value read is represented for these writes. For an ordinary nonwrapping interval, they cover precisely the fully selected bytes between any boundary fragments.

The full-byte phase can be empty. In particular, a byte-aligned start and an endpoint inside that same byte require no full-byte write.

### Partial ending byte

There is no ending-byte access if either:

- The current byte position is greater than the endpoint byte position; or
- The endpoint’s within-byte offset is zero.

Otherwise, the routine selects within-byte offsets zero through one less than the endpoint offset in the current byte. Each selected bit causes a separate read–modify–write, starting with mask `0x80` and proceeding toward less significant bits.

For a byte-aligned start whose nonempty range remains within that byte, this ending phase performs the entire update. For example, start 0 and length 3 use masks `0x80`, `0x40`, and `0x20` here, not in the starting phase.

### Ordinary-range guarantees

Assuming a nonnegative length, no unsigned endpoint wrap, ordinary accessible memory, and no concurrent modification:

- Every bit in the requested half-open interval becomes set.
- Bits outside the interval retain their values.
- Selected bits that were already set remain set.
- A zero length causes no storage access.
- A nonempty interval confined to one byte with a **non-byte-aligned start** is handled entirely by the partial starting-byte phase.
- A nonempty interval confined to one byte with a **byte-aligned start and nonaligned endpoint** is handled entirely by the partial ending-byte phase.
- A byte-aligned interval ending at a byte boundary uses only direct full-byte writes.

A whole-byte interval is not a partial-byte interval: start 0 and length 8 produce one direct write of `0xFF`, rather than eight bitwise read–modify–writes.

### Negative lengths and endpoint wrap

Negative lengths are not rejected. Their unsigned conversion can produce an endpoint before the start, in the same byte, or far later in the unsigned byte ordering.

The resulting behavior is determined by the calculated coordinates:

| Calculated relationship | Storage behavior |
|---|---|
| Endpoint byte precedes a byte-aligned start | No access |
| Endpoint byte precedes a nonaligned start | Set the remaining bits in the starting byte, then return |
| Same start and endpoint byte; nonaligned start; endpoint offset no greater than start offset | No access |
| Same start and endpoint byte; endpoint offset greater than start offset | Set the forward within-byte interval |
| Endpoint byte follows the start byte | Perform forward traversal through the calculated endpoint |

Unsigned wrap is not treated as a request to continue from the highest bit position back to bit zero. In particular, a wrapped endpoint can cause only a starting-byte suffix to be updated, or no update at all.

A negative length can also cause a very large forward update when its converted endpoint lies later in the unsigned ordering. No length-based limit or protective rejection is represented.

## Side effects

The explicit data-memory effects are byte reads and writes at the supplied base address plus selected byte offsets.

Their order is:

1. Starting-fragment read–modify–writes, in increasing within-byte offset.
2. Complete-byte writes, in increasing byte offset.
3. Ending-fragment read–modify–writes, in increasing within-byte offset.

Within each per-bit update, the byte read precedes the corresponding byte write. A fragment selecting three bits therefore entails three reads and three writes to one byte, not one aggregated update. A sequence of three complete bytes entails three direct writes without represented reads of their prior contents.

The body contains no explicit external call or named-global access. This does not imply that the caller-supplied address cannot refer to global, shared, or device storage.

The routine provides no explicit locking, atomic bit operation, memory barrier, or rollback. Concurrent modification can be lost when an intervening update is overwritten by a later write derived from an earlier read. Device-memory behavior can differ from ordinary-memory value expectations because each represented access may have its own effect.

The represented access order does not establish actual instruction selection, bus transaction widths, or hardware-level ordering.

There is no explicit recoverable error path for invalid addresses, insufficient storage, negative lengths, endpoint wrap, or numeric address wrap. If an access cannot complete, the body supplies no failure status or restoration mechanism. Platform fault behavior and the visibility of already-completed accesses are `documented_only`.

This case distinguishes the ending-fragment path from the preceding nonaligned example.

- Their prior contents are not explicitly read.

### Starting fragment followed by complete bytes

- Byte offset 0 receives masks `0x04`, `0x02`, and `0x01` through separate read–modify–writes.

### Zero length

Given any start position and length zero, no storage access occurs.

For an aligned start, both fragment updates are absent. For a nonaligned start, the starting phase selects no bits and advances the current byte position beyond the endpoint byte, preventing an ending update.

### Negative length with an earlier endpoint

Given start 11 and length −8:

- The endpoint is 3.
- The start is at byte offset 1, within-byte offset 3.
- Byte offset 1 receives masks `0x10`, `0x08`, `0x04`, `0x02`, and `0x01`.
- No earlier byte is accessed.

This is not a backward eight-bit update.

### Negative length with a large forward endpoint

Given start 0 and length −1:

- The endpoint is `0xFFFFFFFF`.
- Byte offsets 0 through `0x1FFFFFFE` each receive a direct write of `0xFF`.
- Byte offset `0x1FFFFFFF` receives ending-fragment masks `0x80` through `0x02`.
- That last byte’s least significant bit is preserved.

This expectation requires the entire touched address range to be accessible.

### Wrapped endpoint

Given start `0xFFFFFFF8` and length 8, the endpoint is zero. The start is aligned and lies after the endpoint in byte ordering, so no storage access occurs.

Given start `0xFFFFFFFD` and length 4, the endpoint is 1. The routine applies masks `0x04`, `0x02`, and `0x01` to byte offset `0x1FFFFFFF`, then returns. Byte offset 0 is not accessed.
