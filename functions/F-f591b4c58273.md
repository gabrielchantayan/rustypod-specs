# F-f591b4c58273

## Purpose

F-f591b4c58273 conditionally updates a one-byte field in an indirectly referenced object and invokes F-e0ba31379901 when the field’s previously observed value differs from a supplied 32-bit unsigned value.

The comparison uses the full supplied value, but the write retains only its low eight bits. Consequently, this is not simply a “notify when the stored byte changes” operation: an input greater than 255 always takes the update-and-call path, even when its low eight bits already equal the stored byte.

The function returns a 32-bit zero after either path completes normally. The meaning of the byte field and the purpose of the dependency are not established by the supplied evidence.

## Behavior

### Initial observation

The function first reads the object-address slot from the container. It then reads the byte field at offset `0xB35` from that object.

The byte is interpreted as unsigned, yielding a value from 0 through 255. That value is compared numerically against the complete 32-bit unsigned requested value. The requested value is not reduced to eight bits before the comparison.

If the two values are equal, the function returns zero. On this path, the supplied body performs no byte write and does not invoke F-e0ba31379901.

### Mismatch handling

If the initial comparison differs, the function performs these observable actions in order:

1. It reads the container’s object-address slot again.
2. It writes the low eight bits of the requested value to the byte field at offset `0xB35` from that newly obtained object address.
3. It reads the container’s object-address slot again.
4. It invokes F-e0ba31379901 with that most recently obtained four-byte value as its sole visible argument.
5. If the dependency returns normally, it returns a 32-bit zero.

The mismatch path therefore contains three object-address-slot reads in total: one for the comparison, one for the write, and one for the dependency argument.

The evidence does not show the initially obtained object address being retained for all subsequent uses. A behavioral description must preserve these separate reads rather than promise that the comparison, write, and call necessarily concern the same object.

If the slot remains unchanged throughout the operation, all three reads identify the same object. If it changes between reads, the function contains no visible consistency check or retry. Whether such changes are permitted by the surrounding execution model is unknown.

### Integer-width consequences

The stored result is the requested value modulo 256. This is a consequence of the one-byte write, not a validation rule.

For requested values from 0 through 255, equality with the initially observed byte suppresses both the write and dependency invocation.

For requested values from 256 through 4,294,967,295, equality is impossible because the observed byte cannot exceed 255. Every such request takes the mismatch path.

In particular, a mismatch does not guarantee that the write changes the byte’s bit pattern. The existing byte may already equal the requested value’s low eight bits. The write and dependency invocation still occur because the decision used the full requested value.

The field’s later signed interpretation, if any, is not established. The initial comparison explicitly observes an unsigned byte; the write establishes only an eight-bit stored representation.
