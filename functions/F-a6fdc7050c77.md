# F-a6fdc7050c77

## Purpose

F-a6fdc7050c77 replaces an association stored in an owner object. It first notifies a dependency about any existing association, stores the requested replacement, and, when the replacement is non-null, notifies a second dependency. A nonzero control argument additionally enables an indirect operation on the replacement.

The established behavior is an ordered sequence of calls and memory accesses. Describing those calls as “detach,” “attach,” or “activate” would imply semantics not established by the supplied evidence. In particular, the function does not itself establish reference-counting, destruction, allocation, or transfer-of-ownership rules.

The function has no explicit success result and implements no rollback.

## Interface

### Inputs

| Input | Representation and role |
|---|---|
| Owner | An address-bearing argument identifying an object with an association field at byte offset **52** (`0x34`). The recovered declaration represents this argument as an integer, although its use is address-like. |
| Replacement | A nullable pointer-like value. It is stored in the owner’s association field and, when non-null, passed to F-d0317826fab2. If the control argument is nonzero, it is also used for indirect dispatch. |
| Control | An integer tested for equality with zero. Zero suppresses the final indirect operation; every nonzero value enables it, provided the replacement is non-null. |

These names describe interface roles, not source-level identifiers.

### Output

There is no explicit return value. Normal completion occurs after the required calls, if any, finish. The function does not report whether those calls succeeded or whether they changed the association again.

### Width and layout model

The supplied representation uses integer-sized loads for the existing association and the replacement’s dispatch-table address, while writing the association through a pointer-sized lvalue. This is consistent with a **32-bit address model**, in which those loads and the pointer store are each four bytes.

That model supports the following layout description:

| Location | Required use |
|---|---|
| Owner address + 52 | Association field: read before replacement and overwritten with the requested replacement. |
| Replacement address + 0 | Dispatch-table address, read only when indirect dispatch is enabled and reached. |
| Dispatch-table address + 332 (`0x14c`) | Indirect operation address. |

The offsets are byte offsets. The dispatch offset is not a count of entries.

The supplied evidence does not independently establish the platform ABI, integer widths, pointer widths, alignment rules, or exact indirect-call convention. Consequently, the four-byte access description is conditional on the apparent 32-bit model. It must not be generalized to a 64-bit interface merely by widening pointers.

## Behavior

### 1. Inspect the existing association

The function first reads the owner’s association field and compares the value with zero.

If that read is zero, it does not call F-96f4ed7653c7.

If that read is nonzero, the supplied representation reads the association field again to obtain the first argument for F-96f4ed7653c7. The owner is the second argument.

The distinction between the condition read and the argument read matters when describing the source-facing access sequence: the first value controls whether the call occurs; the second supplies its association argument. They are not explicitly captured as one saved value. With stable ordinary memory they will agree. The evidence does not establish concurrent-access semantics or guarantee two separate physical loads in an executable.

The replacement has not yet been stored when this call begins.

### 2. Store the requested replacement

After the optional F-96f4ed7653c7 call returns normally, the function unconditionally writes the replacement into the owner’s association field.

This write occurs whether the replacement is null or non-null. It also occurs when the replacement equals the previously stored association. There is no equality-based shortcut.

If F-96f4ed7653c7 changes the same field and returns, this write overwrites that change. The function does not reread the field to decide whether the requested replacement is still appropriate.

If F-96f4ed7653c7 does not return normally, the supplied normal path does not reach the replacement store. There is no visible recovery path that completes the assignment after such a failure.

### 3. Handle a null replacement

If the replacement argument is null, the function returns after storing it.

Neither F-d0317826fab2 nor the indirect operation is invoked on this path. The control argument does not affect this outcome.

The decision uses the replacement argument, not a fresh read of the association field.

### 4. Notify the non-null replacement

For a non-null replacement, the function calls F-d0317826fab2 with:

1. The replacement.
2. The owner.

The association-field write precedes this call. At entry to this dependency, the function has already performed the store that publishes the requested association. That ordering does not guarantee that the field remains unchanged throughout the call.

The dependency’s result is not inspected. After it returns normally, the next decision uses the control argument.

### 5. Apply the control gate

If the control argument is zero, the function returns without performing its own dispatch-table reads.

If the control argument is nonzero, the function proceeds to indirect dispatch. There is no distinction among positive values, negative values, or particular nonzero bit patterns.

The gate does not suppress the association replacement or F-d0317826fab2. It controls only the final indirect operation.

### 6. Perform indirect dispatch

When this stage is reached, the function uses the original non-null replacement argument, not the association field’s current contents.

It reads a dispatch-table address from the beginning of the replacement object, then obtains the operation address from byte offset 332 within that table. It invokes the selected operation with:

1. The replacement.
2. The owner.

These reads occur after F-d0317826fab2 returns. A dispatch-table change made by that dependency can therefore affect which operation is selected.

The function does not verify that the replacement remains valid, that the table address is non-null, or that the selected entry is callable. It does not inspect an operation result or perform an explicit association-field write afterward.

## Side effects

### Direct memory effects

The only explicit data write is the replacement store at owner offset 52.

The function’s own established read sequence is:

1. Read the existing association for the zero test.
2. If nonzero, read it again as the association argument for F-96f4ed7653c7.
3. After the replacement store and F-d0317826fab2, and only when indirect dispatch is enabled, read the replacement’s dispatch-table address.
4. Read the selected operation address from that table.

There is no explicit readback of the association field after writing it.

No allocation, deallocation, reference-count adjustment, logging, or global-variable access is directly shown. This does not constrain the dependencies: their memory effects, global effects, and resource operations are unknown.

### Ownership and lifetime

Storing the replacement establishes a pointer-like association in the owner. It does not, by itself, prove ownership transfer or lifetime extension.

Likewise, the old-association call does not prove that the old association is released, and the new-association call does not prove that the replacement is retained.

The optional indirect operation creates a lifetime requirement: after F-d0317826fab2 returns, the original replacement must remain usable for dispatch. This function does not visibly enforce that requirement.

### Reentrancy and state changes during calls

The function contains no visible reentrancy guard.

If a dependency reenters this function or modifies the owner, the outer invocation continues with its own arguments after the dependency returns:

- The outer replacement store still follows the old-association call.
- Following the new-association call, optional dispatch still targets the outer replacement argument.
- Changes to the owner’s association field do not redirect that dispatch.
- Changes to the replacement’s dispatch table can redirect it.

Thus, normal return does not guarantee that the owner still contains the requested replacement. A dependency invoked after the store may have changed the field.

### Errors and abnormal completion

No error status is produced or checked. There is no visible rollback, retry, or exception-handling path.

Invalid storage or an invalid dispatch target may prevent normal completion. The precise fault or exception behavior depends on the execution environment and dependencies and is not established here.

## Acceptance examples

These are conditional contract examples derived from static evidence. They have not been executed.

### Empty association replaced with null

Given a valid owner whose association field is zero, a null replacement, and any control value:

- F-96f4ed7653c7 is not invoked.
- A null value is written to the association field.
- F-d0317826fab2 and the indirect operation are not invoked.
- The function returns normally if the memory accesses complete normally.

### Existing association cleared

Given a stable nonzero existing association and a null replacement:

- F-96f4ed7653c7 receives the existing association and owner before the replacement write.
- If it returns normally, the association field is overwritten with null.
- No new-association notification or indirect dispatch follows.

If the dependency changes the field before returning, the outer null store still follows.

### Non-null replacement with zero control

Given a valid non-null replacement and zero control:

- Any required old-association call completes before the store.
- The replacement is stored.
- F-d0317826fab2 receives the replacement and owner.
- After it returns, the function performs no indirect dispatch of its own.

This does not constrain dispatches performed internally by the dependency.

### Non-null replacement with nonzero control

Given a valid non-null replacement, nonzero control, and dependencies that return normally:

- The replacement is stored before F-d0317826fab2.
- Dispatch-table lookup occurs after that dependency returns.
- The selected operation receives the replacement and owner.

A negative control value enables this path just as a positive nonzero value does.

### Replacement equals the existing association

Given stable memory containing the same non-null value supplied as the replacement:

- The old-association notification still occurs.
- The same value is stored again.
- The new-association notification still occurs.
- Optional indirect dispatch remains controlled by the control argument.

Identity equality does not make the operation a no-op.

### New-association notification changes state

Suppose F-d0317826fab2 changes the owner’s association to another value and returns normally. With nonzero control, dispatch still uses the original replacement.

Suppose instead it changes the original replacement’s dispatch table. The subsequent lookup uses the table then present, subject to valid memory and callable-target requirements.
