# F-4384ab7eb5a7

## Purpose

F-4384ab7eb5a7 traverses a count-bounded sequence of records and selects a record using one of two criteria:

- **Occurrence mode:** the requested occurrence of a matching 32-bit primary value.
- **Paired-value mode:** a record matching both a primary and a secondary 32-bit value.

On selection, the function returns the current record address and optionally writes its one-based traversal index. Paired-value selection can also report the inclusive index span from the first primary match to the selected record.

Every ordinary unsuccessful path returns zero. **A zero return does not, by itself, establish that selection failed.** Only the initial lookup result is checked for zero. Later address advancement can produce a zero current record address without stopping traversal. If subsequent dependency results satisfy the selection criteria, the function writes the success outputs and returns that zero address.

Interpreting zero exclusively as failure therefore requires an external invariant excluding zero-valued addresses from later traversal positions, or excluding successful field observations at those positions. Neither invariant is established here.

The terms “record,” “primary,” “secondary,” and “displacement” describe inferred structural roles. Their application meaning is unknown.

## Interface

### Arguments and return value

The interface has seven arguments in this order:

| Position | Contract name | Representation | Role |
|---|---|---|---|
| 1 | Handle | Pointer to a 32-bit integer | Passed to the initial lookup dependency; subsequently dereferenced for count-address construction. May be null. |
| 2 | Selector | Signed 32-bit integer | Passed unchanged to the initial lookup. After successful lookup, zero is replaced with 12 for count-address construction. |
| 3 | Primary value | Unsigned 32-bit integer | Compared against the complete assembled primary field. |
| 4 | Occurrence selector | Signed 32-bit integer | Zero requests paired-value mode; nonzero requests occurrence mode. Updated locally on primary matches in occurrence mode. |
| 5 | Secondary value | Unsigned 32-bit integer | Compared against the assembled secondary field only in paired-value mode. |
| 6 | Index output | Optional pointer to a 32-bit integer | Receives the selected traversal index on selection; receives zero on ordinary unsuccessful completion with a nonnull handle. |
| 7 | Span output | Optional pointer to a signed 16-bit integer | Written only on paired-value selection. |

The return is a 32-bit integer carrying the current record-address representation on selection, or zero on ordinary unsuccessful completion. These result categories overlap when the selected address is zero. There is no separate status result.

The occurrence selector is passed by value. Its local updates are not written back to the caller.

### Memory and dependency preconditions

Null handle and null output pointers have explicit behavior. Other storage validity is not checked locally.

Normal completion requires that every executed operation be supported:

- The initial dependency must accept the supplied handle and selector.
- Subsequent handle dereferences must be valid.
- Count and field dependencies must accept the addresses supplied on the executed path.
- Each nonnull output pointer must support the corresponding store.

A zero current record address is not itself a local termination condition. Primary-field calls would then receive address 4, and secondary-field calls, if required, would receive address 8. An unsuccessful examination at that position would also cause displacement calls with address zero. Whether these dependency calls can return normally is not established.

The function supplies no general validation of alignment, allocation boundaries, record sizes, address ownership, or address arithmetic.

### Observed layout

Relative to the current record address:

| Byte offset | Observed role |
|---|---|
| 0 | Displacement used for next-record advancement |
| 4 | Primary comparison field |
| 8 | Secondary comparison field |

Each required field is assembled from four dependency results obtained at the same field address. These offsets do not establish that a field is read atomically or by a single underlying memory access.

The traversal count is assembled from two dependency results. Each count-call address uses the base currently stored through the handle, the effective selector, and an additional displacement of 14 bytes.

## Behavior

### Entry and initial lookup

A null handle causes an immediate zero return. Neither output is written, and no dependency is called.

For a nonnull handle, the function first calls **F-a01d9d48df66** with the handle and the original selector.

If this dependency returns zero, traversal does not begin. The function writes zero to the index output if present, leaves the span output untouched, and returns zero. No count or record-field dependency is called by this function on that path.

A nonzero result becomes the initial current record address. This is the only explicit zero-address rejection in the traversal setup or loop.

After successful lookup, a zero selector is replaced with 12. Other selector values, including negative values, remain unchanged. Consequently, the initial lookup receives the original zero selector, while subsequent count-address construction uses 12.

### Count acquisition

The function calls **F-c19b4c0cb7f7** twice, in order. For each call, it constructs the supplied address from:

- A fresh read of the 32-bit base stored through the handle.
- The effective selector.
- A further displacement of 14 bytes.

The two handle dereferences are distinct. A change to the stored base during the first dependency call can affect the second call’s address.

The assembled count takes:

- Bits 0–7 of the first result as count bits 8–15.
- Bits 8–15 of the second result as count bits 0–7.

Other result bits do not contribute. The count is between 0 and 65,535 inclusive and is not reacquired during traversal.

If both results have the same relevant 16-bit value, the assembly exchanges that value’s two bytes. Identical dependency results are not required.

A zero count skips all record processing. The index output is cleared if present, the span output remains unchanged, and the function returns zero.

### Field assembly

For each required primary, secondary, or displacement field, the function calls **F-c223c8c1cf8e** four times at that field’s address.

The assembled 32-bit pattern takes:

| Result observation | Contributing bits | Destination bits |
|---|---|---|
| First | 0–7 | 24–31 |
| Second | 8–15 | 16–23 |
| Third | 16–23 | 8–15 |
| Fourth | 24–31 | 0–7 |

Thus, four identical results produce a byte-reversed 32-bit pattern. Differing results produce a composite of four observations.

The function performs no consistency check or retry. The four calls and their order are observable behavior; replacing them with one observation would require an additional dependency guarantee.

These descriptions express the visible bit-selection behavior. Exact executable treatment of signed intermediate shifts and arithmetic boundaries remains documented_only.

### Traversal order

Traversal indices begin at 1 and proceed through the acquired count, inclusive.

At each position, the primary field at offset 4 is assembled first and compared against the complete unsigned 32-bit primary argument.

A primary mismatch:

- Does not update the occurrence countdown.
- Does not establish the first primary-match position.
- Does not read the secondary field.
- Proceeds to displacement acquisition and advancement.

A primary match follows the occurrence or paired-value rules below.

There is no zero-address check at the start of an iteration or after advancement. The count bounds examinations, not valid addresses or distinct records.

### Occurrence mode

An initially nonzero occurrence selector requests occurrence mode.

On each primary match, the local selector is decremented and reduced to a signed 16-bit representation. The resulting value is retained for the next primary match. If that value is zero, the current record is selected immediately.

Under the visible 16-bit reduction behavior:

- Positive requests from 1 through 32,767 select the corresponding primary occurrence.
- A nonzero input with low 16 bits equal to 1 selects the first primary match.
- A nonzero input with low 16 bits equal to zero requires 65,536 primary matches to reach zero. The maximum traversal count permits only 65,535 examinations.
- Negative inputs and larger positive inputs must not be treated as unrestricted mathematical occurrence counts.

The exact boundary semantics of the arithmetic expression implementing this narrowing, including signed overflow and shifting, are not independently established.

On selection, the function writes the current one-based index to the index output if present and returns the current record address. It does not read the secondary field or write the span output.

This selection path applies even when advancement has made the current address zero. In that case, the success index write still occurs, and the return value is zero. The unsuccessful-completion index clearing is not executed afterward.

### Paired-value mode

An initially zero occurrence selector requests paired-value mode.

At the first primary match, the function stores the current index in signed 16-bit internal storage before acquiring the secondary field. Later primary matches retain that first-match position.

Although indices above 32,767 have negative signed 16-bit representations, no possible traversal index has a zero low-16-bit representation: indices range only from 1 through 65,535. The stored first-match position therefore does not become indistinguishable from the initial zero sentinel within this bound.

For every primary match, the function assembles the secondary field at offset 8 and compares it against the complete unsigned 32-bit secondary argument.

A secondary mismatch continues traversal. A secondary match selects the current record and causes these actions in order:

1. Write the one-based traversal index to the index output, if present.
2. Write the inclusive span to the span output, if present.
3. Return the current record address.

The span is the selected index minus the first primary-match index, plus one, reduced to 16 bits. It counts traversal positions, including intervening primary mismatches.

The mathematical span ranges from 1 through 65,535. Values above 32,767 have negative representations through the signed 16-bit output type.

As in occurrence mode, a zero current address does not prevent selection. Successful comparisons at that position cause the success writes and a zero return.

### Advancement and exhaustion

After every examination that does not select a record, the function assembles the displacement at offset 0 and adds it to the current address.

This occurs even after the final permitted examination. The four final displacement calls therefore remain observable, although the resulting address is not inspected.

No local check rejects a zero displacement, a repeated address, a resulting zero address, an out-of-allocation address, or a displacement that would move backward under a signed interpretation.

After exhausting the count without selection, the function writes zero to the index output if present, leaves the span output untouched, and returns zero.

## Side effects

The direct output behavior is:

| Outcome | Index output, if present | Span output, if present | Return |
|---|---|---|---|
| Null handle | Unchanged | Unchanged | Zero |
| Initial lookup returns zero | Zero | Unchanged | Zero |
| Zero count or exhausted search | Zero | Unchanged | Zero |
| Occurrence selection | Selected index | Unchanged | Selected address, possibly zero |
| Paired-value selection | Selected index | Inclusive span reduced to 16 bits | Selected address, possibly zero |

On paired-value selection, the 32-bit index store precedes the 16-bit span store. Overlapping output storage can make the later store overwrite part of the earlier result. No alias restriction or protective buffering is visible.

With valid, nonoverlapping index storage, normal completion, and no interfering writes, a selected index is positive even when the returned address is zero. Without such an output or an external address invariant, the return alone cannot distinguish that selection from unsuccessful completion.

There is no explicit allocation, release, or record mutation in this function. Dependencies may nevertheless allocate, release, mutate the handle or records, or affect globals; their bodies and contracts are unavailable.

No local recovery converts a dependency fault or nonlocal exit into an ordinary failure result.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless otherwise stated, dependencies return normally, addresses are accepted, field observations are stable, arithmetic follows the stated representation behavior, and output storage is valid and nonoverlapping.

1. **Null handle preserves outputs.**  
   A null handle returns zero without dependency calls or output writes.

2. **Initial lookup failure clears only the index.**  
   With a nonnull handle and zero initial lookup result, the index output becomes zero if present. The span remains unchanged. No count or field calls occur.

3. **Zero selector has distinct lookup and count uses.**  
   With selector zero and successful lookup, the lookup receives zero. Each count-call address is 26 bytes beyond the base observed for that call, subject to the unresolved address-arithmetic boundary rules.

4. **Second primary occurrence.**  
   With occurrence selector 2 and primary matches at indices 2 and 5, selection occurs at index 5. The index output becomes 5; the span is untouched; secondary fields are not acquired.

5. **Span includes intervening mismatches.**  
   In paired-value mode, a first primary match at index 2 with the wrong secondary value, followed by the first complete pair at index 6, produces index 6 and span 5.

6. **Immediate pair selection.**  
   If the first primary match also satisfies the secondary comparison, the span is 1.

7. **Large signed span.**  
   A first primary match at index 1 and paired selection at index 40,000 produce a span pattern representing 40,000 unsigned, or −25,536 as a signed 16-bit value.

8. **Repeated addresses remain separate examinations.**  
   With count 3, zero displacement, a stable primary match, and occurrence selector 3, the same address is selected on its third examination. The reported index is 3.

9. **Final unsuccessful examination still advances.**  
   With count 1 and a primary mismatch, four primary-field calls precede four displacement calls. The function then clears the index output and returns zero.

10. **Differing observations are combined.**  
    Four field results containing respectively only 0x12, 0x3400, 0x560000, and 0x78000000 produce the assembled pattern 0x12345678. No consistency check intervenes.

11. **Paired selection can return zero.**  
    Suppose the count is 2. At the initial nonzero address, the primary matches but the secondary does not. Advancement then produces current address zero. If the dependencies accept calls at addresses 4 and 8 and their assembled values match both requested values, the function writes index 2, then span 2, and returns zero. It does not subsequently clear the index.

12. **Occurrence selection can also return zero.**  
    Suppose occurrence selector 1, count 2, an initial primary mismatch, and advancement to address zero. If the next primary assembly matches, the function writes index 2 and returns zero, leaving the span untouched. With no index output, the return alone does not distinguish this selection from failure.

## Uncertainties

The following remain documented_only:

- Exact executable semantics of signed intermediate shifts, overflow, narrowing, and 32-bit address arithmetic at representation boundaries.
- Whether any caller invariant prevents traversal from reaching address zero.
- Whether dependencies accept zero or zero-derived addresses and can return matching field values there.
- Dependency validation, mutation, allocation, release, global effects, and failure behavior.
- Allocation boundaries, alignment requirements, concurrency guarantees, and output-aliasing restrictions.
- Domain meanings of the selector, count, fields, and displacement.
- Whether repeated observations are intentional requirements or consequences of the supplied representation.

These unknowns do not justify treating zero as an unambiguous failure result. The established control flow permits selection at a later zero current address if the required dependency calls complete and comparisons succeed.

## Evidence

Established static evidence consists of the supplied function body: argument widths, explicit branches, dependency call order, byte-selection expressions, bounded traversal, address advancement, and output stores.

In particular, the initial lookup result is checked for zero, but later current addresses are not. Both selection branches return the current address after their applicable success writes. These facts establish the conditional zero-address selection behavior independently of any domain interpretation.

Search terminology, record roles, and possible encoded-data intent are inferences rather than independently established application semantics.

No runtime tests have been performed. The acceptance examples describe conditional consequences of static evidence, not observed executions.
