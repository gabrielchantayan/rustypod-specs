# F-1c1004f97fea

## Purpose

F-1c1004f97fea combines two integer inputs into a 32-bit value and emits one, two, or three bytes through a caller-supplied output cursor. It advances the cursor before each corresponding byte write.

For combined values from zero through `0xFFFF`, the emitted bytes have the shape of a one-, two-, or three-byte UTF-8 encoding. This is an inferred interpretation, not a validation guarantee. The function does not reject surrogate values, does not enforce a Unicode scalar-value range, and does not generate four-byte encodings.

The paths emitting two or three bytes additionally invoke an unresolved indirect dependency after their final byte write. The one-byte path returns without that invocation. Because the dependency's behavior is unknown, the locally produced bytes and cursor position are not unconditional guarantees about the state visible after the entire function returns.

## Interface

### Inputs

The function has three arguments:

1. **Cursor-slot address.** An address identifying a writable four-byte slot. The slot's contents are interpreted as the address of the next output byte.
2. **Unsigned component.** A 32-bit unsigned integer.
3. **Shifted component.** A 32-bit integer presented as signed in the supplied representation.

These names describe argument roles, not source identifiers.

The function has no explicit length, capacity, destination-end, encoding-mode, or error-reporting argument.

### Combined value

For the observable bit-level behavior, define the **combined value** as the bitwise OR of:

- the unsigned component; and
- the shifted component's 32-bit bit pattern shifted left by eight positions, retaining only the low 32 bits.

The operation is an OR, not an addition or concatenation of independently masked fields. The unsigned component is not restricted to its low byte before combination.

The shifted component's original bits 24 through 31 do not contribute to the resulting 32-bit value. Its original bits 0 through 23 contribute at positions 8 through 31. The combined value's low eight bits therefore come entirely from the unsigned component.

This bit-vector interpretation describes the supplied low-level operations. It does not assert portable signed-shift semantics in a particular implementation language.

### Output and return

There is no explicit return value or status code.

The function's direct outputs are:

- writes to the cursor slot;
- writes of individual bytes through addresses obtained from that slot;
- an indirect invocation on the two-byte and three-byte paths.

Under ordinary nonoverlapping storage conditions, the local emission advances the cursor by one, two, or three bytes. On the multi-byte paths, this describes the state immediately before the indirect invocation, not necessarily the final state after it.

### Preconditions

For defined ordinary use:

- The cursor-slot address must identify readable and writable storage of the required width.
- The initial cursor must identify writable output storage.
- Each subsequently reloaded cursor must likewise identify a writable byte.
- Address increments must remain meaningful and valid for the execution environment.
- The cursor slot must not overlap the emitted bytes if the caller expects simple sequential output and a final cursor equal to the original cursor plus the emitted byte count.
- The unresolved indirect invocation must be valid on paths that reach it.

No local checks establish these conditions.

## Behavior

### Path selection

The function first forms the combined value and loads the initial output address from the cursor slot.

The combined value is compared as an unsigned 32-bit quantity:

| Combined value | Local emission size | Indirect invocation |
|---|---:|---|
| `0x00000000`–`0x0000007F` | 1 byte | No |
| `0x00000080`–`0x000007FF` | 2 bytes | Yes |
| `0x00000800`–`0xFFFFFFFF` | 3 bytes | Yes |

There is no fourth path for large values, and no validation failure path.

### Byte values

For the one-byte path, the byte written is the low eight bits of the unsigned component. Within this path, that is also the combined value.

For the two-byte path:

- The first byte is `0xC0` OR the combined value shifted right by six.
- The second byte is `0x80` OR the unsigned component's low six bits.

The first byte is stored as an eight-bit quantity. Because this path is limited to combined values below `0x800`, its first byte lies between `0xC2` and `0xDF`.

For the three-byte path:

- The first byte is `0xE0` OR bits 12 through 19 of the combined value.
- The second byte is `0x80` OR bits 6 through 11 of the combined value.
- The third byte is `0x80` OR the unsigned component's low six bits.

The final-byte rule is equivalent to using the combined value's low six bits, because shifting the other component by eight cannot affect them.

The three-byte first-byte rule includes eight extracted bits before the OR. It is not restricted to a four-bit payload. For combined values above `0xFFFF`, the first byte can therefore lie outside the usual three-byte UTF-8 leading-byte range. Combined-value bits 20 through 31 do not affect the emitted bytes once this path has been selected.

### Ordered memory operations

The order of cursor updates and byte writes is part of the behavior. A cursor update occurs before its associated byte write, not afterward.

#### One-byte path

After the initial cursor load:

1. The cursor slot is written with the initial output address plus one byte.
2. The output byte is written at the initial output address.
3. The function returns.

There is no subsequent cursor reload and no indirect invocation.

#### Two-byte path

After the initial cursor load:

1. The cursor slot is written with the initial output address plus one byte.
2. The leading byte is written at the initial output address.
3. The cursor slot is read again.
4. The cursor slot is written with that reloaded address plus one byte.
5. The trailing byte is written at the reloaded address.
6. The unresolved indirect dependency is invoked.
7. If that invocation returns normally, the function returns without further locally specified output writes.

#### Three-byte path

After the initial cursor load:

1. The cursor slot is written with the initial output address plus one byte.
2. The leading byte is written at the initial output address.
3. The cursor slot is read again.
4. The cursor slot is written with that reloaded address plus one byte.
5. The middle byte is written at the reloaded address.
6. The cursor slot is read again.
7. The cursor slot is written with that reloaded address plus one byte.
8. The trailing byte is written at the reloaded address.
9. The unresolved indirect dependency is invoked.
10. If that invocation returns normally, the function returns without further locally specified output writes.

These sequences describe the order of operations established by the supplied representation. They do not establish atomicity, synchronization, or cross-thread visibility guarantees.

### Aliasing and externally changed cursor contents

The cursor reloads are behaviorally significant. Later byte destinations are obtained from the slot again rather than unconditionally derived from the initial output address.

If an output byte overlaps the cursor slot, that byte write may change the address used for the next emission. Even the one-byte path can leave a cursor value different from the previously stored incremented address if its output byte overwrites part of the slot.

The exact consequences of such overlap depend on address representation, byte order, and storage layout, which are not fully specified here. A replacement must not silently assume nonaliasing when claiming to preserve behavior for overlapping storage.

Likewise, the local sequence does not promise that concurrently modified cursor contents are ignored. Whether such concurrent access is valid is outside the established contract.

### Validation and failure behavior

The function performs no visible:

- destination-capacity check;
- null-address check;
- Unicode scalar-value check;
- surrogate exclusion;
- upper-bound rejection;
- allocation;
- terminator append;
- error-code generation.

A zero-valued combined input emits a zero byte and advances the cursor; it is not a request to stop emission.

Invalid storage or an invalid indirect target may prevent normal completion. No particular exception, signal, recovery mechanism, or rollback is established. Since cursor stores precede the corresponding byte stores, partial execution can leave an advanced cursor even when the following byte write does not complete.

## Side effects

### Cursor and output storage

The function directly reads and writes the caller's cursor slot and writes bytes at the addresses selected by that slot.

For disjoint, stable storage:

- the one-byte path performs one cursor store and one output-byte store;
- the two-byte path performs two cursor stores and two output-byte stores;
- the three-byte path performs three cursor stores and three output-byte stores.

The initial slot load occurs on every path. Each additional byte after the first requires another slot load.

The supplied representation shows no reads of existing output-byte contents and no clearing of unused output storage.

### Ownership and lifetime

No direct allocation, release, ownership-transfer operation, or retained-pointer store is visible in the local emission logic.

This establishes neither ownership nor lifetime behavior for the unresolved dependency. In particular, callers cannot assume that it preserves the cursor slot, preserves the emitted bytes, avoids retaining addresses, or avoids releasing memory.

### Global and external state

No direct global-state access is established by the visible local emission operations.

The indirect invocation may have additional effects. Its effects on global state, external resources, memory ownership, and control flow are unknown.

## Dependencies

One unresolved indirect dependency is invoked on every path whose combined value exceeds `0x7F`.

No opaque function ID for that dependency is supplied. Its identity is therefore **documented_only**, rather than assigned an invented identity or associated with F-1c1004f97fea itself.

Established facts about this dependency boundary:

- Invocation occurs after the final local byte write.
- Both the two-byte and three-byte paths reach it.
- The one-byte path does not.
- The representation displays no explicit arguments at the invocation.
- No result from it is used by the visible local logic.
- If it returns normally, there are no further visible local output writes before return.

Unknowns include its calling convention, implicit inputs, target selection, return behavior, preservation obligations, memory effects, and ownership effects. The absence of displayed arguments is not evidence that it consumes no machine state.

## Acceptance examples

The following are conditional acceptance cases derived from static inspection, not executed tests.

Unless stated otherwise, assume valid, disjoint, stable cursor and output storage. For multi-byte cases, bytes and cursor advancement describe the state immediately before the indirect invocation. Treating them as final post-return results additionally requires that the dependency return normally without changing that state.

| Unsigned component | Shifted component | Combined value | Emitted bytes, in order | Local cursor advance |
|---|---|---|---|---:|
| `0x00000000` | `0` | `0x00000000` | `00` | 1 |
| `0x0000007F` | `0` | `0x0000007F` | `7F` | 1 |
| `0x00000080` | `0` | `0x00000080` | `C2 80` | 2 |
| `0x000007FF` | `0` | `0x000007FF` | `DF BF` | 2 |
| `0x00000800` | `0` | `0x00000800` | `E0 A0 80` | 3 |
| `0x0000D800` | `0` | `0x0000D800` | `ED A0 80` | 3 |
| `0x0000FFFF` | `0` | `0x0000FFFF` | `EF BF BF` | 3 |
| `0x00010000` | `0` | `0x00010000` | `F0 80 80` | 3 |
| `0x00100000` | `0` | `0x00100000` | `E0 80 80` | 3 |
| `0xFFFFFFFF` | `0` | `0xFFFFFFFF` | `FF BF BF` | 3 |

These cases distinguish important boundaries:

- `0x7F` does not invoke the indirect dependency; `0x80` does.
- `0x7FF` emits two bytes; `0x800` emits three.
- `0xD800` is emitted without surrogate rejection.
- `0x10000` still emits only three bytes.
- `0x100000` demonstrates loss of high combined-value bits in the three-byte payload.

Additional combination cases:

- With unsigned component `0x41` and shifted component `1`, the combined value is `0x141`; emission is `C5 81`, with a local advance of two bytes.
- With unsigned component `0x100` and shifted component `1`, the combined value remains `0x100`; emission is `C4 80`. This distinguishes OR from addition, which would produce a different combined value.
- With unsigned component `0x41` and shifted component `0x01000000`, the 32-bit shifted contribution is zero; emission is the single byte `41`, and no indirect invocation occurs.

An ordering-sensitive acceptance condition is also required: immediately before each local output-byte store, the corresponding cursor increment has already been stored. An implementation that postpones all cursor updates until after emission is not equivalent for aliasing or partial-failure observations.

## Uncertainties

### Established static evidence

The supplied representation establishes the combination operation, unsigned branch thresholds, byte extraction rules, cursor reloads, cursor-before-byte store order, and the conditional indirect invocation.

### Inferred intent

The encoding resembles UTF-8 for combined values through `0xFFFF`. A likely intended role is encoding a value assembled from two components. Neither interpretation establishes that the arguments are individually bytes or that callers supply only valid Unicode scalar values.

### Documented-only unknowns

The following remain **documented_only**:

- the unresolved dependency's identity and full behavior;
- the source of its target address;
- the complete calling convention;
- byte order of address storage;
- required cursor-slot alignment;
- address-overflow behavior;
- validity and consequences of concurrent mutation;
- exact failure behavior for invalid accesses or invocation;
- caller-enforced capacity, value-range, and lifetime invariants.

The representation uses a four-byte cursor slot, but it does not supply a complete platform ABI. Exact pointer-layout claims beyond that observed width would require additional evidence.
