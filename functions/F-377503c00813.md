# F-377503c00813

## Purpose

F-377503c00813 updates address-bearing fields using two supplied addresses. With valid, suitably separated storage and stable memory, its effects correspond to inserting a candidate immediately after an anchor in a doubly linked structure.

That structural interpretation is **inferred intent**. The established behavior is an ordered sequence of two 32-bit reads and four 32-bit writes. There is no visible validation of structure membership, removal of the candidate from an existing structure, or rejection of overlapping storage.

The access order matters. The anchor’s forward-link field is read twice, with both candidate-field writes between those reads. If storage overlaps, those writes can change the second value and redirect the subsequent write.

## Interface

### Inputs

The function receives two 32-bit address-bearing integer values:

- **Anchor address:** used as the base for both explicit reads and the final write.
- **Candidate address:** used as the base for the first two writes and as the value stored by the final two writes.

These names describe operational roles, not established object types. Neither input is explicitly checked for zero, equality, alignment, accessibility, or membership in a structure.

For discussion, fields at +4 and +8 are called the **forward link** and **backward link**, respectively. Those names reflect inferred list semantics.

## Behavior

### Ordered memory effects

The function first reads the 32-bit value at the anchor’s forward-link field and retains that value.

It then writes the anchor address into the candidate’s backward-link field. After that, it writes the retained value into the candidate’s forward-link field.

Only after those two writes does it read the anchor’s forward-link field again. The value obtained by this second read selects the base whose backward-link field receives the candidate address.

The final memory operation writes the candidate address into the anchor’s forward-link field.

Consequently:

- Both reads are explicitly addressed through the anchor input.
- The candidate backward-link write precedes the candidate forward-link write.
- Both candidate writes precede the second anchor-link read.
- The write selected by the second read precedes the final anchor write.
- The candidate’s forward-link write uses the first read’s value, regardless of what the second read returns.

No read is explicitly addressed through the candidate input. This does not guarantee that the candidate’s previous fields are unread. For example, equal inputs make the initial read access the candidate’s previous forward link. Placing the candidate four bytes below the anchor makes that read access the candidate’s previous backward link.

The two reads cannot generally be treated as one observation. Earlier writes can alter the second value through aliasing. External mutation could also make the values differ, although the function supplies no synchronization for such use.

These ordering statements describe the supplied static representation. They do not establish atomicity, inter-thread visibility, or a machine-level memory-ordering guarantee.

### Result with separated storage

Assume that the relevant anchor, candidate, and original-successor fields do not overlap, every access succeeds, and no external mutation occurs.

On completion:

- The anchor’s forward link contains the candidate address.
- The candidate’s backward link contains the anchor address.
- The candidate’s forward link contains the original successor address.
- The original successor’s backward link contains the candidate address.

Under these assumptions, the anchor’s backward link and the original successor’s forward link are not written. The candidate’s previous link values do not affect the result because neither read intersects them.

The function does not repair the candidate’s former neighbors. If the candidate already belongs to another structure, overwriting its links can leave that structure inconsistent. The original successor’s backward link is overwritten without checking its previous value.

### Equal inputs and overlapping storage

There is no explicit inequality or overlap check.

An early write does not establish a lasting field value if a later write intersects that field. In particular, the candidate’s backward link can be changed again by the destination selected by the second read or by the final anchor write.

When both inputs identify the same address, the first write places that address in the shared backward-link field. The next write restores the initially read value to the shared forward-link field. With stable ordinary memory, the second read therefore obtains that initial value.

The selected backward-link write can nevertheless intersect either shared field. Equal inputs alone do not guarantee that both fields finish as self-links.

If the selected write is disjoint from both shared link fields, both shared fields finish containing the shared input address. This disjointness is **sufficient, not necessary**. If the initial forward link also identifies the shared input address, the selected write overlaps the shared backward-link field but stores the same address already placed there; both fields still finish as self-links.

For other overlaps, earlier writes can change the second read, redirect its selected destination, or be partly overwritten by later writes. Partial-overlap results depend on byte order and the environment’s handling of the relevant accesses.

## Acceptance examples

These examples are conditional deductions from static evidence, not runtime test results. Except where stated otherwise, they assume stable ordinary memory and successful completion of all required accesses.

### Ordinary insertion

Assume the anchor initially points forward to a successor, and the relevant fields of the anchor, candidate, and successor are pairwise non-overlapping.

The resulting links are:

- Anchor forward to candidate.
- Candidate backward to anchor.
- Candidate forward to successor.
- Successor backward to candidate.

The candidate’s previous link values are neither read nor used under these separation assumptions.

### Self-linked anchor with a separate candidate

Assume the anchor’s initial forward link identifies the anchor itself. The candidate’s relevant fields are disjoint from both anchor fields.

Both candidate links finish containing the anchor address. Both anchor links finish containing the candidate address. The destination selected by the second read is the anchor’s own backward-link field.

### Equal inputs with a separated successor write

Assume both inputs identify the same address. The initial forward link identifies storage whose field at +8 is disjoint from both shared input link fields.

The initial read also reads the candidate’s previous forward link. On completion, both shared input fields contain the shared input address. The backward-link field reached through the original forward link also contains that address.

The disjointness condition is sufficient for these results; it is not necessary.

### Equal inputs and an initial self-link

Assume both inputs and the initial forward link identify the same address.

The selected backward-link write targets the shared backward-link field, overlapping the first write. Both writes store the same shared input address.

Both shared link fields finish containing that address. The backward-link field reached through the original forward link is the same shared backward-link field and also contains that address.

This overlapping case demonstrates why disjointness is not a necessary condition for the preceding example’s final values.

### Candidate four bytes below the anchor

Assume:

- The anchor address is 0x1000.
- The candidate address is 0x0FFC.
- The initial word at 0x1004 contains 0x2000.
- Storage around 0x2000 is disjoint from the written ranges.

The first read at 0x1004 also reads the candidate’s previous backward link. The first write changes that word to 0x1000. The candidate’s forward-link word at 0x1000 receives the retained value 0x2000.

The second read at 0x1004 consequently obtains 0x1000, not 0x2000. Its selected write targets 0x1008 and stores 0x0FFC. The final write stores 0x0FFC at 0x1004.

On completion:

- The candidate’s forward link contains 0x2000.
- The candidate’s backward link contains 0x0FFC, not the anchor address.
- Both anchor link fields contain 0x0FFC.
- The field at 0x2008 has not been written.

This example demonstrates both an indirect read of a previous candidate field and destination redirection caused by an intervening write.

### Equal inputs with a partially overlapping destination

Assume both inputs are 0x1000, the initial forward-link word is 0x1001, and the environment uses little-endian storage and supports the required unaligned write.

The first backward-link write places 0x00001000 at 0x1008. The next write preserves 0x00001001 at 0x1004, so the second read obtains 0x1001.

The selected write begins at 0x1009 and stores 0x00001000. Its partial overlap leaves the word at 0x1008 equal to **0x00100000**. The final write places 0x00001000 at 0x1004 without changing that backward-link word.

Equal inputs and successful execution therefore do not alone imply two self-links.

### Candidate equals the original successor

Assume the anchor initially points to the candidate, with their relevant fields disjoint.

The candidate’s forward link becomes its own address. Its backward link first receives the anchor address, then receives its own address through the selected backward-link write. The anchor continues to point to the candidate.

Reinserting the existing successor is not a no-op.

### Failure at the selected backward-link write

Assume both reads and both candidate writes succeed, but execution stops at the selected backward-link write.

The final anchor write has not occurred. The completed candidate writes are not rolled back. If storage overlaps, those writes may already have changed the anchor.

No claim is made about partial effects of the failing access itself.

## Evidence

Both candidate-field writes precede the second read. The final write targets anchor +4. No calls, explicit conditional branches, or returned value are visible.
