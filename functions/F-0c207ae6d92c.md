# F-0c207ae6d92c

## Purpose

F-0c207ae6d92c changes an object’s byte-sized mode and coordinates associated callbacks, embedded scheduling state, and possible insertion into a shared singly linked list.

The requested mode is a 32-bit unsigned value, but the stored mode occupies only one byte. Requests equal to 1 or 2 take a scheduling-related path. Every other request takes a shorter reset-and-notify path.

**Established behavior:** the function compares the full request against the current mode byte, invokes mode-dependent callbacks, changes object fields, and conditionally modifies a shared list.

**Inferred intent:** modes 1 and 2 activate two different configurations of a timed activity. Other modes deactivate or reset that activity. Field names such as “interval,” “deadline,” and “membership” below are descriptive interpretations, not independently established API meanings.

## Interface

### Inputs and result

- **Object:** a pointer into a mutable object with a dispatch-table pointer at byte offset `0x000`.
- **Requested mode:** a 32-bit unsigned integer.
- **Result:** no explicit return value.

There is no visible null check, object-size check, mode-range validation, allocation-failure handling, or error result.

## Behavior

### 1. Compare the stored byte with the full request

The function first reads the mode byte at `0x198`, promotes its value, and compares it with the entire 32-bit requested mode.

If equal, it returns immediately. No dependency call or write by this function precedes that return.

This is not a comparison of low bytes. For example, a stored mode of 1 equals request 1 but does not equal request 257.

### 2. Requests other than 1 and 2

When the initial comparison did not return and the request is neither 1 nor 2, the following operations occur in order:

1. Invoke F-936a8728139d with the address of the embedded subobject at `0x16C`.
2. Store the request’s low eight bits at `0x198`.
3. Write zero to the two-byte field at `0x160`.
4. Invoke F-indirect-01 with the object and argument 1.
5. Invoke F-indirect-02 with the object and argument 1.
6. Return.

The mode and two-byte field are therefore written before either indirect callback on this path, but after F-936a8728139d.

This path does not directly perform the status query, shared-value copy, membership test, or list insertion described below. Dependencies may have additional effects; their absence cannot be assumed.

Requests outside the byte range are accepted by the visible control flow. They are distinguished using their full 32-bit values and then truncated when stored.

### 3. Initial callbacks for requests 1 and 2

If the request is 1:

1. Invoke F-indirect-01 with argument 0.
2. Invoke F-indirect-02 with argument 0.

If the request is 2:

1. Invoke F-indirect-01 with argument 1.
2. Invoke F-indirect-02 with argument 1.

The object is passed to both callbacks.

Neither callback is preceded by this function’s write of the new stored mode on these paths. Unless a callback changes it, they observe the previous stored mode.

### 4. Query, status update, and shared-state refresh

After the two callbacks for request 1 or 2:

1. Invoke F-indirect-03 with the object.
2. If its result is zero, write byte value 1 at `0x199`.
3. Store the requested mode at `0x198`.
4. Invoke F-936a8728139d.
5. Read a shared four-byte value and copy it into the object at `0x18C`.
6. Read the membership-like field at `0x188`.

The invocation of F-936a8728139d in this path has no recoverable explicit argument in the supplied representation. It must not be asserted to receive the same subobject pointer as its invocation on the other path.

A nonzero query result does not cause a direct write to `0x199`. The function does not explicitly clear that byte in any branch.

If the membership-like field is nonzero at step 6, the function returns. In particular, this decision uses the value after F-936a8728139d and the shared-value copy, not necessarily its entry value.

### 5. Preparation when membership is zero

If the field at `0x188` is zero:

1. Read a shared handle, here called **G-handle**.
2. Invoke F-338d16f9ce72 with that handle.
3. Invoke F-add44d4e9aaa with the embedded subobject address at `0x16C`.
4. Read the four-byte interval-like field at `0x170`.

The interval is read after both dependencies. An entry-time value is not substituted for this later value.

If the interval is zero, skip deadline computation and list insertion. Continue with the release-like operation and final shared-state check.

### 6. Deadline computation and list insertion

For a nonzero interval, the function:

1. Invokes F-unknown-01, which returns a four-byte value.
2. Reads a shared pointer to a list-head cell, called **G-head-cell**.
3. Computes the returned value plus the interval multiplied by 1000, storing the result at `0x174`.
4. Reads another shared four-byte value, **G-insertion-value**, and copies it to `0x184`.
5. Reads the initial node pointer from the previously obtained head cell.

The expression uses the four-byte interval as an integer value. A negative nonzero interval does not have a separate rejection branch.

The visible representation does not establish a portable overflow rule for the multiplication or addition. Mathematical, unbounded arithmetic is not an acceptable replacement for the actual target’s arithmetic behavior.

#### Traversal

Starting at the initial node:

- If the current node is null, stop.
- Otherwise invoke F-0d70d6f9010c with:
  - the address eight bytes into the current node;
  - the object’s deadline address at `0x174`.
- If the comparison result is nonzero, stop at that node.
- If the result is zero, read that node’s next pointer and continue, retaining the node as the predecessor.

Thus the predicate’s exact visible interpretation is **zero means advance; nonzero means insert before the current node**. Ascending order, descending order, equality handling, timestamp signedness, and wraparound ordering are not established without the dependency’s contract.

The next pointer is read after the comparison call. A contract must not replace this with an entry-time snapshot of the chain or assume that the comparator leaves the list and deadline unchanged.

#### Publication order

Once the stopping node and predecessor are determined:

1. If there is no predecessor, write the embedded subobject address into the shared head cell.
2. Otherwise, write that address into the predecessor’s next-pointer field.
3. Write value 1 to the object’s membership-like field at `0x188`.
4. Write the stopping-node pointer into the embedded next-pointer field at `0x16C`.

The new node is therefore published before its membership flag and next pointer are written. This ordering is part of the visible behavior. Its safety for concurrent observers depends on synchronization that is not established here.

### 7. Release-like operation and final shared-state check

After preparation, whether the interval was zero or insertion occurred:

1. Read a separate shared handle, **G-release-handle**.
2. Invoke F-5bcae2eff9a7 with it.
3. Read G-handle again and dereference it to obtain a pointer.
4. If that pointer is nonnull, read its first four-byte field.
5. If both the pointer and that first field are nonzero, invoke F-unknown-02 through a shared function pointer.
6. Return.

If the pointer is null, its first field is not read. If either tested value is zero, F-unknown-02 is not invoked.

G-handle is read afresh after F-5bcae2eff9a7. Its earlier value passed to F-338d16f9ce72 is not necessarily reused.

## Side effects

### Direct object changes

Depending on the branch, direct writes can affect:

- the stored mode byte;
- the two-byte field at `0x160`;
- the status byte at `0x199`;
- the shared-value copy at `0x18C`;
- the deadline-like field;
- the insertion-associated shared-value copy;
- the membership-like field;
- the embedded next pointer.

The function does not itself allocate or release memory in the visible representation. This does not establish that its dependencies refrain from doing so.

### Shared changes

Insertion writes either the shared head cell or an existing node’s next pointer. The final indirect dependency may create further effects that are not specified here.

F-338d16f9ce72 and F-5bcae2eff9a7 appear paired around preparation and insertion, but their arguments come from distinct shared locations. Their roles as lock/unlock, acquire/release, or another synchronization mechanism are **inferred intent**, not established behavior.

### Failure and partial progress

No explicit error status or rollback path is visible. Callback and dependency results are ignored except for the query result, the comparison result, and the value used in deadline computation.

If a dependency does not return normally, preceding writes and calls have already occurred. Fault behavior, exceptions, nonlocal transfers, and recovery are not specified by this function.

No assumption is made that dependencies preserve object fields, globals, list topology, or memory ownership.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, dependencies return normally and do not alter fields relevant to the example.

1. **Exact no-op.** With stored mode 2 and request 2, the function returns after the byte comparison. No callback or direct write occurs.

2. **Full-width request comparison.** With stored mode 1 and request 257, the function does not return early. It takes the general path, eventually stores byte value 1, clears the two-byte field, and invokes both configuration callbacks with 1.

3. **Request 1 callback visibility.** With stored mode 0 and request 1, both configuration callbacks receive 0 while the stored mode remains 0. The mode becomes 1 only after the query.

4. **Query-controlled flag.** On a request-2 path, a zero query result causes a byte write of 1 at `0x199`. A nonzero result causes no direct write there, even if its previous value was already 1.

5. **Membership prevents preparation.** If `0x188` is nonzero when read after F-936a8728139d, the shared value has already been copied to `0x18C`, but preparation, interval reading, insertion, and the release-like call are skipped.

6. **Zero interval.** With membership zero and interval zero after F-add44d4e9aaa, no deadline computation or list publication occurs. F-5bcae2eff9a7 and the final shared-state checks still occur.

7. **Insertion into an empty list.** With a nonzero interval and null head, no comparison call occurs. The embedded subobject becomes the head, membership becomes 1, and its next pointer becomes null, in that write order.

8. **Insertion before the first node.** If the first comparison returns nonzero, the new node becomes the head and its next pointer is ultimately set to the former first node.

9. **Insertion after traversed nodes.** If comparisons return zero for two nodes and nonzero for the third, the second node’s next pointer is changed to the embedded subobject. The embedded next pointer is subsequently set to the third node.

10. **Final callback gating.** After the release-like call, a null pointer obtained through G-handle suppresses both the pointed-to field read and F-unknown-02. A nonnull pointer with first field zero suppresses only the callback.
