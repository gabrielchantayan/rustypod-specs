# F-1111096c956d

## Purpose

F-1111096c956d conditionally performs repeated search-and-update operations on a state object, using two supplied values as the search and replacement inputs. It returns the number of update sequences completed before the search dependency reports its designated termination value.

The apparent intent is replacement of occurrences in a mutable text-like object. That interpretation is inferred from the dependency call pattern, not established by dependency implementations. The established behavior is narrower: obtain two extent-like values, conditionally compare the inputs, inspect a pointer-bearing field of the state object, and then repeat a search followed by two ordered operations.

This function does not itself establish allocation policy, text encoding, match boundaries, successful replacement, or ownership transfer. Those properties remain dependent on the opaque callees.

## Interface

### Inputs

The function accepts three values represented as 32-bit integers in the supplied static representation:

1. **State handle** — used as an address-bearing value for a mutable object and passed to the search and update dependencies.
2. **Search input** — passed to an extent dependency, a comparison dependency when applicable, and the search dependency.
3. **Replacement input** — passed to an extent dependency, the comparison dependency when applicable, and the second update dependency.

Zero has an explicit absent-input meaning for the search and replacement inputs. A zero state handle has no corresponding explicit guard.

The integer representation of the handles does not establish that arbitrary integer values are valid addresses. Whenever the guarded execution path reaches the state object, the state handle must designate storage suitable for the reads and dependency operations described below.

### Result

The result is represented as a 32-bit integer.

On normal completion:

- It is zero when either supplied input is zero.
- It is zero when the input comparison establishes equivalence, although the state-field inspection still occurs.
- It is zero when the inspected state pointer is null or its first byte is zero.
- Otherwise, it counts iterations in which both update calls return and execution reaches the counter increment.

The result is not independently validated as a count of successful replacements. The visible function does not examine either update dependency’s return value.

### Visible state layout

The function directly accesses the following state:

| Location | Access | Established meaning |
|---|---|---|
| State base plus 4 bytes | Read a pointer-valued field | Address used for a one-byte content check |
| Byte at that pointer, if non-null | Read one character-sized value | Zero suppresses the update loop |

No other state-object fields are directly accessed by the visible body. Dependencies may access additional state.

The supplied representation uses pointer-bearing 32-bit integer inputs and a pointer field at byte offset 4. The exact pointer width, alignment rules, byte order, and full object layout require target ABI confirmation; the field offset alone does not establish them.

## Behavior

### Absent-input path

If either the search input or replacement input is zero, the function returns zero.

On this path:

- No dependency is called.
- The state object is not dereferenced.
- The nonzero input, if any, is not inspected.
- The state handle need not designate readable storage for the visible body to complete this path.

This is the only explicitly guarded path that avoids state inspection altogether.

### Input extent and comparison phase

When both supplied inputs are nonzero, the function first calls F-d8cbf9aa79a9 with the search input. It then calls the same dependency with the replacement input.

These calls occur in that order. Their results are retained separately as the search extent and replacement extent. The visible function does not reject zero or negative results and does not recompute them during later iterations.

If the two extent results differ, the comparison dependency is not called and the inputs are treated as not equivalent for loop gating.

If the two extent results are equal, the function calls F-7f14f1ab6851 with:

- The search input;
- The replacement input;
- The search extent.

A zero comparison result marks the inputs as equivalent. Any nonzero comparison result marks them as not equivalent.

The function does not directly compare the search and replacement handles. Equal handles do not themselves bypass the extent or comparison calls.

The extent-like and comparison-like interpretations are inferred. In particular, the supplied body does not establish whether extents count bytes, characters, elements, or another unit.

### State inspection and loop eligibility

After the extent calls and any conditional comparison call, the function reads the pointer-valued field at state base plus 4 bytes.

If the pointer is non-null, the function reads its first byte. If the pointer is null, no read through that pointer occurs.

This state inspection occurs even when the earlier comparison has established input equivalence. Consequently, equivalent inputs do not make an invalid state handle safe.

The update loop is eligible only when all three conditions hold:

- The inspected pointer is non-null;
- The first byte read through that pointer is nonzero;
- The inputs were not classified as equivalent.

Otherwise, the function returns zero after the described calls and reads.

The pointer and first-byte check are performed only once. The function does not repeat that eligibility check after dependency calls mutate the object or related state.

### Repeated search and update phase

For an eligible loop, the completed-iteration count and search offset both begin at zero.

Each iteration calls F-a21141daa905 with the state handle, search input, and current offset.

A result of exactly −1 terminates the loop and returns the completed-iteration count. This terminal search is not followed by either update call.

Every other search result is passed onward without a visible validity check. For such a result, the function:

1. Calls F-491a7a9bcafa with the state handle, search result, and retained search extent.
2. After that call returns, calls F-e21f946ded8c with the state handle, the same search result, replacement input, and retained replacement extent.
3. After that call returns, increments the completed-iteration count by one.
4. Advances the search offset by the retained replacement extent.

These steps impose an observable ordering. The second update is not issued until the first returns. The count is not incremented until both return. The next search occurs only afterward.

The next offset is the previous offset plus the replacement extent. It is **not** computed from the position returned by the search dependency. For example, a first match reported at position 20 with a replacement extent of 3 leads to a second search offset of 3, not 23.

Neither update result is tested. If a dependency reports failure through a normal return value, the visible function still proceeds unless the dependency’s behavior prevents normal continuation.

### Arithmetic and termination

The count, offset, extent results, and search results are represented as 32-bit integer values. The terminal search value is the signed value −1.

No visible overflow check protects either:

- Incrementing the completed-iteration count;
- Adding the replacement extent to the search offset.

For executions that remain within the representable range, the offset advances by the same retained replacement extent after every completed iteration. Arithmetic behavior outside that range is documented_only: the supplied representation does not establish a portable overflow contract.

A zero replacement extent leaves the offset unchanged. A negative replacement extent decreases the offset when the addition remains representable. Neither case is rejected.

Termination depends on F-a21141daa905 eventually returning −1, or on a dependency otherwise preventing continuation. The visible function supplies no iteration limit, progress check, or empty-search guard.

## Side effects

The visible body directly reads the state pointer field and, conditionally, one byte through that pointer. It contains no direct write to the caller’s object storage.

All externally visible mutation is delegated. In particular:

- The extent and comparison dependencies may have side effects; purity is not established.
- The search dependency may alter state; read-only behavior is not established.
- Both update dependencies receive the state handle and may mutate it or associated storage.
- The second update receives the replacement input, but its copying, borrowing, retention, and release behavior are unknown.
- Input storage may alias the state’s storage. The function performs no visible snapshot or alias check.

The initial state inspection observes the object after the extent and comparison phase, including any changes those dependencies have made. Later operations use the originally retained extent results even if a dependency changes input contents.

There is no visible allocation, release, explicit ownership transfer, rollback, exception handler, or transactional boundary in this function. This does not imply that dependencies allocate nothing, release nothing, preserve globals, or leave caller-owned storage intact.

If execution stops between the two update calls, effects already performed by the first are not visibly rolled back. Likewise, changes made by dependencies before an abnormal exit may remain observable.

## Acceptance examples

These examples are conditional behavioral expectations derived from static evidence, not executed tests. Except where stated otherwise, assume valid storage, representable arithmetic, and normally returning dependencies.

### Absent search input

Given a zero search input and any replacement input, the function returns zero without calling dependencies or reading the state object. This remains true when the state handle is zero.

### Absent replacement input

Given a nonzero search input and a zero replacement input, the function returns zero without examining the search input or state object.

### Equivalent inputs still require state inspection

Given nonzero inputs whose extent results are equal and whose comparison result is zero:

- Both extent calls occur, followed by the comparison call.
- The state pointer field is read.
- Its first byte is also read if the pointer is non-null.
- No search or update call occurs.
- The result is zero.

An invalid state object is not protected by input equivalence.

### Unequal extents with an empty state

Given extent results of 4 and 2, and a non-null inspected state pointer whose first byte is zero:

- The comparison dependency is skipped.
- The pointer field and first byte are read.
- No search occurs.
- The result is zero.

The same loop suppression applies when the inspected pointer is null, but without the pointed-to byte read.

### No reported match

Given eligible state and nonequivalent inputs, if the first search at offset zero returns −1, neither update dependency is called and the function returns zero.

### Two completed iterations

Given a search extent of 4, replacement extent of 2, and search results of 10, 20, and then −1:

- Searches receive offsets 0, 2, and 4.
- The first update pair receives position 10; the second receives position 20.
- Each first update receives extent 4.
- Each second update receives the replacement input and extent 2.
- The function returns 2.

The reported positions do not determine the next offsets.

### Zero replacement extent

Given eligible state and a replacement extent of zero, every search receives offset zero unless execution leaves the visible loop. If the search dependency never returns −1, the function has no visible mechanism that guarantees termination.

### Other negative search result

If the search dependency returns −2, that value is passed as the position to both update dependencies. It is not treated as termination by this function. The consequences depend on those dependencies.

### Normally returned update failure

If an update dependency returns a value that its own contract interprets as failure, but returns normally, this caller does not inspect that value. It continues through the remaining sequence and counts the iteration after both calls return.

## Uncertainties

The following are documented_only:

- Whether the inputs are terminated strings, explicit-length buffers, or another representation.
- Extent units, valid ranges, and dependency error conventions.
- Search semantics, including overlap, encoding, case sensitivity, and empty-input behavior.
- Whether returned positions and supplied offsets use the same units as the extents.
- Bounds requirements for state storage and dependency accesses.
- Dependency effects on globals, input contents, allocation, ownership, and lifetime.
- Behavior when inputs alias storage changed by an update.
- Overflow behavior and termination for all possible inputs.
- Behavior after invalid memory access, dependency failure that prevents return, or other abnormal control transfer.

These unknowns prevent a stronger claim that the result always equals the number of successful textual replacements.
