# F-1e3807631a4d

## Purpose

F-1e3807631a4d reports whether the first matching entry in a fixed-size table has a nonzero status byte.

The function searches at most 34 entries, in increasing index order. An entry matches when its 32-bit key equals a 32-bit value obtained from global storage. On the first match, the function returns 0 if that entry’s status byte is zero, or 1 otherwise. It does not inspect later entries after finding a match.

If no entry matches, the function returns 0. Consequently, a zero result does not distinguish “no matching entry” from “the first matching entry has a zero status byte.”

This describes the established behavior. Any interpretation of the key as an identifier, or the status as an enabled, active, or valid flag, is inferred intent rather than an established domain meaning.

## Interface

### Inputs

There are no explicit parameters. The function obtains its inputs from two global storage locations and from memory reached through one of them:

- **Table-base storage:** supplies the base address used to locate table entries.
- **Comparison-value storage:** supplies the 32-bit value against which entry keys are compared.
- **Table memory:** supplies keys and, conditionally, a status byte.

These labels describe roles; they are not exported symbol names.

The table uses a fixed stride of 20 bytes. For an entry with zero-based index \(i\), the relevant fields are:

| Field | Offset from entry start | Width | Use |
|---|---:|---:|---|
| Key | 4 bytes | 32 bits | Compared for equality with the global comparison value |
| Status | 16 bytes | 8 bits | Tested for zero only when the key matches |

The function does not explicitly inspect the other bytes within an entry.

### Output

The function returns a 32-bit result with exactly one of these values on normal completion:

- **0:** no matching key was found, or the first matching entry’s status byte was zero.
- **1:** the first matching entry’s status byte was nonzero.

The supplied representation establishes a four-byte return value, but not a higher-level Boolean return type or a complete calling convention.

### Preconditions

For defined, normally completing execution:

- The global storage needed by the executed path must be readable.
- Each key address actually visited must permit a valid 32-bit read under the target’s memory and alignment rules.
- If a key matches, its status address must permit a valid one-byte read.
- Address calculations must identify the intended storage without invalid address arithmetic.

The function performs no explicit null check, bounds check, table-length check, or access validation.

A complete 34-entry layout occupies 680 bytes at the stated stride. However, the function does not read every byte in that region. With a stable base, the last key occupies offsets 664 through 667 relative to that base, and the last entry’s status byte is at offset 676. That status byte is read only if the last entry matches. ## Behavior

### Search order and bound

The search begins at index 0. Each visited entry has its key compared with the global comparison value.

A nonmatching entry advances the search by one index. The function visits indices 0 through 33 at most. After a nonmatch at index 33, it returns 0 without attempting index 34.

The supplied representation uses an unsigned search index. Its observed values remain between 0 and 34 inclusive, so the loop’s index increment does not wrap. The largest stride product used for an entry is \(33 \times 20 = 660\) bytes. Thus, index and stride arithmetic do not overflow a 32-bit unsigned index within this search. Whether adding the resulting offset to the table base produces a valid address remains a memory-layout precondition.

The bound is fixed. No terminator, count field, sentinel key, or table-supplied length participates in stopping the search.

### Key comparison

For each visited entry, the function obtains the entry’s 32-bit key and the global 32-bit comparison value, then tests them for equality.

The key access is represented as a signed 32-bit integer read. Because the operation is equality rather than ordering, negative values do not receive special treatment. Equal 32-bit integer values match, including negative values under the target integer representation.

The relative evaluation order of the key read and the comparison-value read is not established by the supplied expression. An implementation must not derive a documented ordering between those two reads from this evidence alone.

The supplied body references global storage within the loop rather than visibly capturing both inputs once at entry. Therefore, a stable snapshot of the base address and comparison value is not established. Equally, the evidence does not establish volatile semantics or require a particular machine-level reload sequence.

### First-match decision

When an entry’s key matches, the function reads the status byte at offset 16 for that entry position.

It then returns immediately:

- Status equal to zero produces 0.
- Any nonzero status produces 1.

The result is normalized. A status byte of 2, for example, yields 1 rather than 2. The signedness of a plain character does not change this zero-versus-nonzero decision.

Later entries cannot override the decision. In particular, a matching entry with a zero status causes an immediate zero return even if a later matching entry has a nonzero status.

The status field is not read for entries whose keys do not match.

### No-match decision

If all 34 keys fail to match, the function returns 0. No status byte is read along this path.

## Acceptance examples

The following are conditional behavioral examples, not reports of executed tests. Unless stated otherwise, assume valid memory, a stable table base, and a stable comparison value.

1. **Match at the first entry, zero status.**  
   Entry 0 has the comparison key and a status of zero. The result is 0. No later key or status is inspected.

2. **Match at the first entry, nonzero status.**  
   Entry 0 matches and has status 7. The result is 1, not 7.

3. **Nonmatching entries with nonzero status.**  
   Entries 0 through 5 do not match, regardless of their status bytes. Entry 6 matches and has status zero. The result is 0. Status bytes for entries 0 through 5 are not needed by this path.

4. **Duplicate keys with conflicting statuses.**  
   Entry 3 matches with status zero, and entry 8 matches with status one. The result is 0 because entry 3 is the first match. Entry 8 cannot affect the result.

5. **Final searchable entry matches.**  
   Entries 0 through 32 do not match. Entry 33 matches and has a nonzero status. The result is 1.

6. **Match beyond the search bound.**  
   None of entries 0 through 33 matches. An additional entry at index 34 has the comparison key. The result remains 0; index 34 is outside the search.

7. **High-bit status value.**  
   The first matching entry has status byte value 128 or 255. The result is 1. Only zero versus nonzero matters.

8. **Negative matching key.**  
   The global comparison value and an entry key represent the same negative 32-bit integer. They match normally. The first such entry’s status determines the result.

9. **Early return before inaccessible later entries.**  
   Entry 0 is readable, matches, and has a readable status. Later entry storage is inaccessible. Under ordinary memory semantics, this path returns from entry 0 without requiring reads of those later entries.

10. **No match with inaccessible status fields.**  
    All 34 required key reads are valid and nonmatching. Status fields are not accessed on this path. This example does not waive any independent allocation or memory-validity requirements imposed by the environment.
