# F-39af4974f3d2

## Purpose

F-39af4974f3d2 conditionally writes an object-address value into a shared slot, then dispatches an indirect operation on the object selected from that slot. The operation receives the selected object address and the address of an invocation-local, mutable copy of the caller’s 32-bit input.

The condition and the write do **not necessarily concern the same slot**. After an opening dependency call, the wrapper captures an externally supplied slot address. It then evaluates that external address separately to locate the value tested against zero. The initialization write and subsequent object-selection read use the captured address, irrespective of which slot supplied the zero-test value.

An opening call to F-4a19e3742733 and a closing call to F-fd58bea73663 surround the normal processing sequence. Their placement suggests a paired access protocol, but synchronization and resource-management semantics are not established.

This contract describes the supplied representation’s static behavior. Dependency semantics, ownership rules, and abnormal-exit behavior remain unspecified where the representation does not establish them.

## Interface

### Input

The function accepts one opaque 32-bit value.

- No signedness or numeric interpretation is established.
- No restriction on permitted bit patterns is shown.
- The value is copied into a four-byte local cell before the first dependency call.
- The indirect operation receives the address of this local cell, not the address of caller-owned argument storage.

### Output

The function has no explicit return value or status result.

The local cell’s final contents are neither inspected for a result nor copied back to caller-owned storage. Observable effects instead arise from shared-state changes, dependency calls, and the indirect operation.

### External state

The wrapper accesses two distinct external values:

| External value | Established use |
|---|---|
| Protocol argument | Read for the opening call and read again for the closing call |
| Shared-slot address | Evaluated once for capture, then separately to locate the zero-test value |

The protocol argument’s width, type, and meaning are not independently established. It must not be assumed to be a lock, handle, object pointer, or immutable token.

The shared-slot address identifies storage containing a 32-bit object-address representation. Its two evaluations are distinct in the supplied representation. No established stability guarantee makes their results equal.

### Represented layout

The representation supports the following 32-bit layout:

| Storage or location | Interpretation used by the wrapper |
|---|---|
| Slot selected for the zero test | A 32-bit value compared with zero |
| Captured slot | A 32-bit value conditionally written, then read as an object address |
| Selected object, byte offset 0 | A 32-bit dispatch-table base address |
| Dispatch table, byte offset 28 | A callable-address entry |
| Local input cell | Four bytes initially containing the input bit pattern |

The dispatch offset is **28 bytes**, not 28 entries. Under a four-byte-entry layout, this is the entry with zero-based index seven.

The indirect call supplies two explicit arguments: the selected object address and the local input-cell address. Calling-convention details beyond those arguments are documented_only.

### Preconditions for normal dispatch

Normal dispatch requires usable storage for every address actually accessed: the external state, the independently selected zero-test slot, the captured slot, the selected object, and its dispatch table. The resolved callable entry must also support the represented invocation.

These are conditions for successful execution, not validations performed by the wrapper. Alignment requirements, executable-address constraints, and precise fault behavior are documented_only.

## Behavior

### 1. Local input and opening call

The wrapper first initializes its local four-byte cell with the input’s 32-bit value.

It then reads the current protocol argument and passes that value to F-4a19e3742733. No return value from this dependency is used.

The shared-slot address is not captured until the opening dependency returns. Changes that dependency makes to the external shared-slot address can therefore affect the subsequent capture.

### 2. Two distinct slot-address evaluations

After the opening call returns, the wrapper performs these operations in order:

1. Evaluates the external shared-slot address and retains the resulting address as the **captured slot**.
2. Separately evaluates the external shared-slot address again.
3. Reads the 32-bit value at the address obtained by the second evaluation.
4. Compares that value with zero.

The second evaluation determines the **tested slot**. It does not replace the captured slot address.

No dependency call appears between the capture and the second evaluation. Nevertheless, the representation does not establish that the external address remains stable across them. The contract therefore does not equate the captured and tested slots.

The zero comparison covers the complete represented 32-bit value. It is not a partial-field or sign test.

### 3. Conditional initialization write

The value read from the tested slot controls the branch:

- **Nonzero tested value:** Both initialization dependencies are skipped.
- **Zero tested value:** F-8157a180d901 is called with the numeric value 16. After it returns, F-e194f3fbdfaa is called without an explicit argument. The latter call’s 32-bit result is written to the captured slot.

The captured slot is the write destination even if the tested slot is elsewhere. Thus:

- A zero tested value can cause an existing nonzero value in the captured slot to be overwritten.
- A nonzero tested value can suppress initialization even when the captured slot contains zero.

The direct return value from F-8157a180d901 is not retained or explicitly passed to F-e194f3fbdfaa. Hidden communication between these dependencies is possible but unestablished. The argument 16 does not, by itself, establish allocation or object size.

The result from F-e194f3fbdfaa is stored without validation. The wrapper does not check for zero, an error sentinel, a valid object layout, or consistency with the tested slot.

Changes to the external shared-slot address during either initialization dependency do not redirect this write. Changes those dependencies make to the captured slot’s contents are overwritten by the result when the write is reached normally.

No retry, rollback, or explicit release of an overwritten value is shown.

### 4. Object selection and dispatch

After either branch, the wrapper reads the 32-bit contents of the captured slot and uses that value as the selected object address.

This is a later slot read, distinct from the zero-test read. On the initialization path, it follows the write of F-e194f3fbdfaa’s result. The wrapper does not directly substitute that dependency’s return value for the object-selection read.

The wrapper then:

- Reads the dispatch-table base from the selected object’s first four-byte word.
- Resolves the callable entry at byte offset 28 from that base.
- Invokes the resolved target with the selected object address and the local input-cell address.

The receiver remains the selected object address; the wrapper does not perform another shared-slot read to choose a different receiver for that call.

No null check, bounds check, callable-address check, or checked-address-arithmetic recovery is shown. An unusable selected object or dispatch entry is not converted into a defined wrapper-level error result.

The indirect operation can modify the local cell. The wrapper does not inspect the modified contents afterward.

### 5. Closing call and return

If the indirect operation returns normally, the wrapper reads the protocol argument again and passes its current value to F-fd58bea73663.

This is a fresh external read, not reuse of a saved opening argument. Intervening changes may therefore cause the opening and closing calls to receive different values.

After F-fd58bea73663 returns, the wrapper returns without an explicit result.

The representation shows no cleanup mechanism that guarantees a closing call after a fault, exception, nonlocal exit, or other failure to return normally.

## Side effects

### Direct wrapper effects and access order

The established sequence is:

1. Initialize the local four-byte input cell.
2. Read the protocol argument and call F-4a19e3742733.
3. Evaluate and capture the external shared-slot address.
4. Evaluate that external address again.
5. Read the 32-bit value at the second address and test it against zero.
6. If that value is zero, call F-8157a180d901 with 16, call F-e194f3fbdfaa, and write the latter result to the captured slot.
7. Read the captured slot to select the object.
8. Read the object’s dispatch-table base and the callable entry at byte offset 28.
9. Invoke the indirect operation.
10. After normal indirect return, reread the protocol argument and call F-fd58bea73663.

The wrapper performs no direct write to the tested slot merely because that slot supplied the branch condition. It writes there only if the captured slot happens to be the same storage.

### Dependency effects

Dependencies and the indirect target may affect shared state, slot contents, object storage, dispatch storage, or the protocol argument. Their preservation of such state is not established.

The retained captured address determines later accesses, but retaining an address does not ensure that the addressed storage remains valid.

### Ownership and lifetime

No ownership transfer is established for the input, protocol argument, selected object, or initialization result.

The local input cell has invocation-local lifetime and is available during the indirect call. The wrapper does not extend that lifetime beyond the invocation. Retention of its address must not be interpreted as granting persistent valid storage.

The wrapper contains no explicit destruction or deallocation. Dependencies may nevertheless allocate, release, or transfer ownership internally; their contracts are unavailable.

### Concurrency

The representation does not establish atomic accesses, memory ordering, mutual exclusion, or single initialization under contention.

In particular, the separate external-address evaluations must not be collapsed into a guarantee that the condition concerns the captured slot. A protocol that keeps those evaluations equal would be an additional environmental or dependency guarantee.

Safe concurrent use requires sufficient guarantees to keep every accessed slot, selected object, and dispatch entry valid. The wrapper alone does not supply those guarantees.

## Acceptance examples

These are conditional expectations from static evidence, not executed tests. Successful cases assume valid storage and normally returning dependencies.

### Stable address with an existing object

If both external slot-address evaluations identify the same slot, and that slot contains a valid nonzero object address:

- The opening dependency runs before either address evaluation.
- Both initialization dependencies are skipped.
- The later captured-slot read selects the object.
- Dispatch uses its table entry at byte offset 28.
- The indirect target receives the object and a local cell initially containing the input.
- The closing dependency runs after normal indirect return.

The wrapper performs no direct slot write on this path. Selecting the same object as the zero-test value additionally requires that the slot contents remain unchanged until selection.

### Stable address with an empty slot

If both evaluations identify the same zero-valued slot:

- F-8157a180d901 receives 16.
- F-e194f3fbdfaa runs afterward.
- Its result is written to that slot.
- Object selection subsequently reads that slot.

If the result is a valid object address and the slot remains unchanged before selection, dispatch uses that object. No equality is required between this address and F-8157a180d901’s unused return value.

### Different captured and tested slots: initialization occurs

Suppose the first evaluation captures slot A, while the second identifies slot B. Slot B contains zero; slot A contains a valid existing object address.

- The zero in B causes both initialization dependencies to run.
- F-e194f3fbdfaa’s result is written to A, overwriting A’s existing value.
- Object selection reads A.
- The wrapper does not directly write B.
- No explicit release of A’s overwritten value occurs.

This demonstrates that initialization is not conditioned on A being empty.

### Different captured and tested slots: initialization is skipped

Suppose the first evaluation captures slot A, while the second identifies slot B. Slot B is nonzero; slot A is zero.

- Both initialization dependencies are skipped.
- Object selection reads zero from A, assuming A remains unchanged.
- The wrapper proceeds toward object access without a defined null-result response.

A nonzero value in the tested slot does not establish a usable object in the captured slot.

### Initialization returns zero

If the tested slot contains zero and F-e194f3fbdfaa returns zero:

- Zero is written to the captured slot.
- No retry or explicit failure result occurs.
- If the captured slot remains zero until selection, the wrapper attempts object access using zero.

Successful completion is not guaranteed. The precise machine-level consequence is documented_only.

### An initialization dependency redirects the external address

If the captured slot is A and an initialization dependency changes the external shared-slot address to B:

- The initialization write still targets A.
- The subsequent object-selection read still uses A.
- No new external slot-address evaluation redirects this invocation to B.

This assumes A remains valid.

### The protocol argument changes

If the opening call receives one protocol-argument value and an intervening operation changes the externally stored value:

- The closing call receives the value present at its own read.
- The wrapper does not enforce equality with the opening value.

### The indirect operation changes the input cell

For any 32-bit input, including all-zero and all-one patterns:

- The cell initially contains exactly that pattern.
- The indirect operation may modify it.
- The wrapper neither returns the modified value nor copies it back to caller-owned argument storage.

### Execution does not reach closing normally

If an earlier dependency, memory access, or indirect operation fails to continue normally, the representation establishes no guaranteed closing call or rollback. Exact abnormal-exit handling is documented_only.

## Evidence
