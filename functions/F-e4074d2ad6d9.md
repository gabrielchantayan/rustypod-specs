# F-e4074d2ad6d9

## Purpose

F-e4074d2ad6d9 rearranges four-byte address-bearing fields in a linked structure. Under the inferred interpretation of those fields as binary-tree links, it performs a right rotation around a supplied **Pivot**:

- Pivot’s left child, called **Promoted**, takes Pivot’s former position.
- Promoted’s former right child becomes Pivot’s left child.
- Pivot becomes Promoted’s right child.
- Parent links and the selected incoming link are updated accordingly.

The tree interpretation explains the apparent purpose; it is not a validated input property. Established behavior consists of the field accesses, comparisons, and writes described below. The function does not check that the supplied objects form a tree.

This is a static behavioral contract. No runtime tests have been performed.

## Interface

### Inputs and result

The function accepts two arguments represented as 32-bit integer quantities in the supplied representation:

| Argument | Meaning in this contract |
|---|---|
| Context | Address of an object whose field at byte offset 16 identifies a root-holder object. |
| Pivot | Address of the node whose links are rearranged. |

Both arguments are used as addresses. The representation does not establish native pointer width, a portable address conversion rule, or special handling of values whose signed interpretation is negative.

There is no explicit return value or status. On normal completion, results are communicated through memory changes.

### Accessed layout

Every accessed field is four bytes wide. Offsets below are byte offsets.

| Object | Offset | Role |
|---|---:|---|
| Context | 16 | Root-holder address |
| Root holder | 4 | Designated-root address |
| Node | 4 | Parent address |
| Node | 8 | Right-child address |
| Node | 12 | Left-child address |

The designated root is reached through a separate object: Context’s field at offset 16 contains the holder address, not the designated-root value itself.

“Parent,” “right child,” and “left child” are semantic labels inferred from the access pattern. The function follows the same offsets even when the stored relationships are inconsistent.

No access to a node field at offset 0 is established. Payload layout, metadata, allocation size, node tags, and any fields outside the listed accesses remain unspecified.

### Preconditions

For ordinary successful operation, every executed read and write must address accessible storage with the permissions and alignment required by the target platform. In particular:

- Pivot’s left-child field must supply an address through which Promoted’s right-child and parent fields can be accessed.
- A nonzero transferred-child address must permit writing its parent field.
- Context must supply a root-holder address through which the designated-root field can be read.
- The root-holder field must be writable when the root-replacement branch is selected.
- On the non-root branch, Pivot’s parent address must permit reading its right-child field and writing the selected child field.
- All address-plus-offset calculations must resolve to the intended storage.

For the conventional rotation postconditions, the structure must additionally be stable, appropriately non-overlapping, and internally consistent. The designated root must be accurate, and a non-root Pivot’s parent must actually reference Pivot.

These are preconditions, not checks. A null or invalid address does not cause a defined validation error or early return.

## Behavior

### Link transfer and initial parent assignment

The function first reads Pivot’s left-child field at offset 12. That value selects Promoted and is retained for the rest of the operation.

Promoted’s right-child field at offset 8 is then read, and its four-byte value is written into Pivot’s left-child field. Under the tree interpretation, this transfers Promoted’s right subtree to Pivot’s left side.

The function subsequently reads Promoted’s right-child field again to test whether it is zero. A zero value skips the transferred-child parent update. A nonzero value causes another read of that same field to obtain a destination address; Pivot’s address is written to the destination’s parent field at offset 4.

These are separate reads. In stable, non-overlapping storage, they refer to the same transferred child. The function does not enforce that equivalence. An earlier overlapping write or an unsupported concurrent change can make the copied value, tested value, and eventual destination differ.

After this conditional update, Pivot’s parent field is read and its four-byte value is written into Promoted’s parent field.

### Incoming-link selection

Only after those writes does the function read Context’s field at offset 16. It forms the address of the designated-root field by adding byte offset 4 to the resulting holder address, then reads that field.

The designated-root value is compared with Pivot’s address:

- **Equal:** Promoted’s address replaces the designated-root value. No old-parent child field is consulted on this branch.
- **Not equal:** Pivot’s parent field is read again. The right-child field of that parent is read and compared with Pivot’s address. Equality selects the parent’s right-child field for replacement with Promoted. Otherwise, the parent’s left-child field is replaced with Promoted.

The fallback to the left-child field does not include a read or equality check of its previous value. An inconsistent parent can therefore have an unrelated left-child link overwritten.

On the root branch, the designated-root field address already obtained is used for the write; Context’s root-holder field is not looked up again.

### Final link assignments

After the selected incoming link has been replaced, the function writes Pivot’s address to Promoted’s right-child field. It then writes Promoted’s address to Pivot’s parent field.

Normal completion follows these writes. There is no subsequent validation or repair pass.

### Read timing and retained values

The established ordering is significant:

- Promoted’s address is selected once, before any write, and retained.
- Promoted’s right-child field is read for the transfer, read again for the zero test, and read a third time for the destination when the test succeeds.
- Pivot’s parent is read before assigning Promoted’s parent. On the non-root branch, it is read again before inspecting the old parent’s right-child field.
- The root-holder lookup occurs after the transferred-child repair and Promoted-parent assignment.
- The incoming-link replacement precedes the final Promoted-right and Pivot-parent writes.

Consequently, this function does not operate on a complete entry-time snapshot. With overlapping storage, later reads may observe earlier writes. The source-level access order is established; a portable machine-level synchronization or atomicity guarantee is not.

### Conditional tree postconditions

Assume distinct, appropriately non-overlapping objects, stable storage, a valid tree, and successful accesses. Let:

- **Transferred** be Promoted’s entry-time right child, possibly zero.
- **Former Parent** be Pivot’s entry-time parent.

The resulting relationships are:

| Relationship | Value after completion |
|---|---|
| Pivot’s left child | Transferred |
| Transferred’s parent, when Transferred is nonzero | Pivot |
| Promoted’s parent | Former Parent |
| Promoted’s right child | Pivot |
| Pivot’s parent | Promoted |
| Incoming link formerly identifying Pivot | Promoted |

For a designated-root Pivot, the incoming link is the root-holder field. Otherwise, the function selects the old parent’s right-child field when its comparison succeeds, and the left-child field when it fails.

Under these assumptions, Promoted’s left-child field and Pivot’s right-child field remain unchanged. No payload movement, balancing metadata update, recoloring, height adjustment, or node-count change is established.

### Root and malformed-structure behavior

Root status is determined exclusively by equality with the designated-root field, not by whether Pivot’s parent is zero.

A designated-root Pivot with a nonzero parent still takes the root branch. That parent value has already been copied into Promoted’s parent; it is not normalized to zero.

Conversely, a Pivot unequal to the designated root takes the parent-link branch even if its parent value is zero. The function then attempts to access the right-child field through that value.

A zero Promoted value is not a supported empty-subtree branch. The function proceeds to access the right-child field through that value before any zero test of a transferred child.

Cycles, self-links, overlapping objects, and inconsistent parent-child relationships are not rejected. For such inputs, the ordinary tree postconditions do not apply. The ordered accesses remain the static account, subject to the platform’s rules for valid execution.

## Side effects

The function performs in-place four-byte field writes. On a stable, non-overlapping path, it executes:

- **Five stores** when the transferred child is zero.
- **Six stores** when the transferred child is nonzero.

The five unconditional stores update:

1. Pivot’s left-child field.
2. Promoted’s parent field.
3. One selected incoming-link field.
4. Promoted’s right-child field.
5. Pivot’s parent field.

The transferred child’s parent update contributes the one conditional store. These counts describe executed stores, not necessarily distinct destinations when storage aliases.

No allocation, deallocation, whole-node copy, external call, I/O operation, or explicit global-variable access appears in the supplied body. Caller-provided addresses can nevertheless refer to shared or global storage.

The function visibly changes references only. It does not visibly acquire ownership of an allocation or release any storage. Broader ownership and lifetime rules are not established.

The update is not transactional. Several fields change before the incoming link is replaced, and the final reciprocal links are written afterward. Intermediate states need not satisfy tree invariants.

No lock, atomic primitive, rollback, or recovery mechanism is present. If an access fails after an earlier successful write, the structure may remain partially modified. The fault mechanism and externally observable failure reporting are platform-dependent and unresolved.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Except where an inconsistency is explicitly stated, assume accessible, stable, non-overlapping storage and a consistent tree.

### Designated root with a transferred child

Initially, the designated root is Pivot, Pivot’s parent is zero, Pivot’s left child is Promoted, and Promoted’s right child is a nonzero Transferred node.

Expected completion:

- The designated root becomes Promoted.
- Promoted’s parent becomes zero.
- Promoted’s right child becomes Pivot.
- Pivot’s parent becomes Promoted.
- Pivot’s left child becomes Transferred.
- Transferred’s parent becomes Pivot.

Six stores execute. No old-parent child field is consulted.

### Non-root Pivot in its parent’s right-child field

Initially, the designated root differs from Pivot, Pivot’s parent is Former Parent, and Former Parent’s right-child field equals Pivot.

The right-child comparison succeeds. Former Parent’s right-child field becomes Promoted, and the designated-root field is not written. The remaining links follow the conditional tree postconditions.

The total is five stores with a zero transferred child or six with a nonzero transferred child.

### Non-root Pivot in its parent’s left-child field

Initially, the designated root differs from Pivot, Former Parent’s right-child field differs from Pivot, and Former Parent’s left-child field equals Pivot.

The failed right-child comparison selects Former Parent’s left-child field for replacement with Promoted. Its previous value is not read as part of selecting that destination.

### Zero transferred child

Initially, Promoted’s right-child field is zero.

Pivot’s left-child field becomes zero. The transferred-child parent write is skipped. Promoted’s right-child field ultimately becomes Pivot, and the other parent and incoming-link assignments still occur.

Five stores execute. This supported zero-child case does not establish support for a zero Promoted address.

### Parent does not reference Pivot

Assume the designated root differs from Pivot and all accesses remain valid, but neither child field of Former Parent equals Pivot.

Former Parent’s left-child field is overwritten with Promoted because the right-child comparison fails. No explicit validation error is returned, and the function does not refuse the update.

This example describes malformed-input behavior, not a valid rotation postcondition.

### Designated root has a nonzero parent

Assume the designated-root field equals Pivot, but Pivot’s parent contains a nonzero address.

Promoted receives that address as its parent, and the designated root becomes Promoted. The function does not dereference the old parent’s child fields on this branch and does not clear Promoted’s parent.
