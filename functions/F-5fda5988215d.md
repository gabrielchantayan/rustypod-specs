# F-5fda5988215d

## Purpose

F-5fda5988215d conditionally writes a signed 32-bit value to an address selected relative to a shared base address. It returns a 32-bit status distinguishing argument rejection from normal completion of the store.

The accepted selectors are exactly **1 and 2**. The accepted candidate values are all signed 32-bit integers **less than 3**, including every negative value. There is no lower-bound check.

The body establishes one explicit shared-base read and one explicit destination store on the accepted path. It establishes no non-aliasing relationship between the location holding the base address and the selected destination. Consequently, an accepted store may also overwrite the shared base-address location if those locations overlap.

The broader application purpose is unknown. Interpreting the selected addresses as configuration fields, device state, or entries in a record array is inferred intent rather than established behavior.

## Interface

### Arguments

The recovered interface has three arguments, in this order:

| Argument | Width and interpretation | Established use |
|---|---|---|
| First | Opaque 32-bit value | Unused by the supplied body. |
| Second | Signed 32-bit selector | Validated using unsigned 32-bit arithmetic; selects the destination when accepted. |
| Third | Signed 32-bit candidate value | Compared with 3 using signed ordering, then stored unchanged if accepted. |

The first argument is not established as a pointer, handle, ownership token, or length. The routine imposes no validity requirement on it.

Under otherwise identical initial conditions, changing only the first argument does not change the body’s validation decisions, selected address, stored value, or normal return status.

### Return value

The normal return value is a 32-bit status:

- **0:** Both argument checks passed, and the destination store completed before the normal return.
- **9:** At least one argument check failed. The body did not read the shared base address or attempt the destination store.

These are the only normal return values established by the supplied body.

A memory-access fault is not converted into status 9. No normal return or recovery behavior is established if an accepted call cannot read the shared base or complete the destination store.

### Memory prerequisites

A normally completing accepted call requires:

- A readable location containing the shared base address.
- A computable destination address using that base and the selected displacement.
- A destination supporting the required 32-bit store.

The body performs no explicit validation of address validity, storage extent, alignment, lifetime, or access permissions.

No non-aliasing prerequisite is enforced. If preserving the shared base-address location is required by a caller, that caller needs an additional non-overlap guarantee not established by this routine.

## Behavior

### Selector validation

The selector check subtracts one using unsigned 32-bit arithmetic, then accepts the result only if it is less than two.

The subtraction is modulo \(2^{32}\). This admits exactly two original selector values:

| Selector | Unsigned subtraction result | Decision |
|---:|---:|---|
| 1 | 0 | Accept |
| 2 | 1 | Accept |
| 0 | \(2^{32}-1\) | Reject |

All negative signed selectors and all selectors greater than 2 are rejected.

This is not a signed subtraction whose interpretation depends on signed overflow. The unsigned operation determines the boundary behavior.

A rejected selector causes return 9 without proceeding to the candidate comparison, shared-base read, or destination store.

### Candidate validation

For an accepted selector, the candidate is compared with 3 using signed 32-bit ordering.

The accepted interval is:

\[
-2^{31} \leq \text{candidate} \leq 2
\]

The rejected interval is:

\[
3 \leq \text{candidate} \leq 2^{31}-1
\]

There is no clamping, normalization, or lower-bound validation. An accepted negative value is stored unchanged.

A rejected candidate causes return 9 without reading the shared base or attempting the destination store.

### Destination layout

After both checks pass, the body reads the shared base address. The selected destination has the following byte displacement from the value obtained by that read:

\[
\text{displacement} = (\text{selector} \times 276) + 8
\]

| Selector | Decimal displacement | Hexadecimal displacement | Store width |
|---:|---:|---:|---:|
| 1 | 284 bytes | 0x11C bytes | 32 bits |
| 2 | 560 bytes | 0x230 bytes | 32 bits |

The two displacements differ by 276 bytes. This is consistent with a repeated-unit stride of 276 bytes and an internal field offset of eight bytes, but it does not establish a complete object layout.

For accepted selectors, the displacement calculations produce small positive values without requiring 32-bit overflow. The validity and platform-specific behavior of combining the displacement with the actual base address are separate environmental matters.

### Observable access order

For an accepted call that completes normally, the body establishes this order:

1. Accept the selector.
2. Accept the candidate.
3. Perform one explicit read of the shared base-address location.
4. Use the obtained base value to determine the selected destination.
5. Perform one explicit 32-bit store of the candidate to that destination.
6. Return 0.

There is **no separate load through the computed destination address** before the store. There is also no destination-value comparison or equality-based suppression of the store.

This does not establish that the destination’s previous contents are never read. If the destination overlaps the shared base-address location, the base-address read accesses some or all of those same bytes before they are overwritten.

The order above describes the body’s accesses and control flow. It does not establish synchronization, hardware atomicity, memory-barrier behavior, or ordering guarantees for concurrent observers.

### Aliasing consequences

The selected store may overlap the location from which the base address was obtained. The supplied body neither checks for nor excludes that arrangement.

If such an overlap exists:

- The base read occurs before the destination store.
- The base read may read bytes that also belong to the destination.
- The store may overwrite some or all of the shared base-address representation.
- The body performs no second base read after the store.
- The body performs no restoration of overwritten base-address bytes.

The current store uses the base value already obtained. Overwriting its storage does not introduce another address calculation or destination access in this invocation. A later invocation may encounter the altered base state; its outcome is not determined by this invocation’s success status alone.

## Side effects

### Accepted call

The accepted path contains one explicit 32-bit destination store. The value written is exactly the accepted candidate.

There is no separate destination load, read-modify-write operation, or explicit second store. However, the destination store cannot be described unconditionally as preserving the shared base-address location: preservation requires non-overlap between that location and the store.

Similarly, the base read cannot be described unconditionally as avoiding the destination’s old contents. If the locations overlap, that read accesses the overlapping bytes.

If the destination already contains the candidate, the body still performs the store. Equal existing contents do not bypass it.

### Rejected call

A rejected call does not reach the explicit shared-base read or destination store. This remains true whether rejection occurs at the selector check or the candidate check.

These are statements about this body’s explicit accesses, not guarantees about unrelated activity elsewhere in the process or system.

### Ownership and lifetime

The body contains no allocation, deallocation, ownership transfer, retention, or release operation. It does not dereference or release the first argument.

The body does not establish ownership of either the shared base-address location or the destination storage. It also does not extend their lifetimes.

### Errors and synchronization

No explicit locking, retry, logging, notification, rollback, or exception recovery appears.

Status 9 reports argument rejection only. It is not an established report for unreadable base storage, an invalid computed address, insufficient backing storage, misalignment, or a failed store.

Additional conditional requirements:

- **Unused argument:** With otherwise identical initial state and accepted arguments, changing only the first argument leaves the selected store and normal status unchanged.
- **Already-equal destination:** If the selected destination already contains the candidate, the explicit store still occurs before return 0.
- **Unusable base on rejection:** If either argument check fails, unusable base storage does not affect this body’s rejected path because that path does not read it.
- **Unusable storage on acceptance:** If both checks pass but a required memory access cannot complete, neither return 9 nor recovery is specified.
- **Disjoint base storage:** If the destination does not overlap the shared base-address location, the explicit destination store does not overwrite that location.
- **Aliased base storage:** If the destination overlaps the shared base-address location and the accesses complete, the base read precedes the overlapping store. Preservation of the base-address bytes is not required.
- **Prior destination contents:** With overlap, the base read may access the destination’s previous contents. Without overlap, the body still performs no separate load through the destination.
- **Other selected position:** For a valid, non-wrapping ordinary-memory arrangement, selecting one displacement causes no explicit store at the other displacement.
