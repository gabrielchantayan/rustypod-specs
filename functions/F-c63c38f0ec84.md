# F-c63c38f0ec84

## Purpose

F-c63c38f0ec84 modifies a three-field descriptor associated with contiguous 16-byte records. Its inferred purpose is insertion of one record, either within existing storage or after obtaining replacement storage.

The directly established behavior is narrower than a general insertion operation:

- The spare-capacity path advances the logical end, duplicates the last record, shifts records backward, and finally reads the supplied source record.
- The growth path computes a capacity request, calls dependencies with incompletely established contracts, directly writes one record under a nonzero-address condition, and replaces the descriptor fields.
- The spare-capacity path has no ordinary append case or established safe empty-sequence insertion case.
- Dependency side effects and source aliasing can change the outcome.

“Storage start,” “logical end,” and “storage limit” describe the apparent roles of descriptor fields. Their conventional container semantics are inferred, not validated by the function.

This contract is based on static evidence only. No runtime tests have been performed.

## Interface

The function receives three addresses and has no explicit result value or status return.

| Input | Representation and use |
|---|---|
| Descriptor | Three consecutive 32-bit fields, at byte offsets 0, 4, and 8, interpreted respectively as storage start, logical end, and storage limit. |
| Position | A 32-bit address identifying the intended insertion position. The two execution paths treat this address differently. |
| Source | Address of a 16-byte record consisting of four 32-bit words at offsets 0, 4, 8, and 12. |

The supplied representation uses 32-bit addresses and arithmetic quantities. No interpretation of individual record words is established.

For conventional insertion semantics, the caller must provide:

- A readable and writable descriptor.
- Active records between storage start and logical end.
- Sufficient writable storage through storage limit.
- Record boundaries separated by 16 bytes.
- A Position within the supported range for the selected path.
- Source words that remain readable when the function actually accesses them.

These are preconditions for the intended interpretation, not checked conditions. In particular, the spare-capacity path requires Position to identify an existing record boundary for ordinary, bounded insertion.

Descriptor fields, records, and Source are not checked for overlap. If record writes overlap the descriptor, later descriptor accesses can observe modified values. Conventional examples below exclude that overlap.

The initial dependency call can modify the descriptor, record storage, Source, or other state before either path begins. Entry-time container validity alone therefore does not establish validity of subsequent operations.

## Behavior

### Initial reads and path selection

The function first reads storage start, then storage limit, retaining both values. It then calls F-10e1e4cd0e66 with the descriptor.

The branch quantity is formed by subtracting the retained start from the retained limit, applying a signed right shift by four bits to the 32-bit difference, and interpreting the resulting bits as unsigned. The growth path is selected when that unsigned quantity is less than or equal to the dependency’s unsigned 32-bit result. Otherwise, execution enters the spare-capacity path.

For a valid, nonnegative, record-aligned extent, the branch quantity represents capacity in records. If the dependency reports the current record count, the condition means that capacity is no greater than count. That meaning of the dependency result is not independently established.

The comparison combines descriptor values read before the call with a result returned by the call. Subsequent operations can use descriptor values changed by that call. The function does not refresh the retained start and limit before choosing the path.

A negative or misaligned extent is not rejected. Nor is this branch simply a comparison of logical end with storage limit.

### Arithmetic limits

The visible calculations operate on 32-bit quantities. Unsigned capacity additions and left shifts can discard high bits. No checked overflow, saturation, bounds validation, or arithmetic-error return appears.

Signed address differences and additions are also present in the supplied representation. Mathematical address formulas in this contract describe inputs for which the relevant calculations remain representable. Behavior beyond that range is not established as a portable language-level guarantee.

Clearing the low four bits of an address difference is a bit operation. It does not validate that either address belongs to an allocation.

### Growth path: request and transfer calls

The function calls F-10e1e4cd0e66 a second time with the descriptor. This second result supplies the capacity-growth basis; the first result is not reused for that purpose.

It computes two unsigned 32-bit candidates:

- The second result plus 32.
- The second result plus its logical right shift by one bit, plus its logical right shift by three bits.

The larger unsigned candidate becomes the selected capacity. Without overflow, this is the greater of a 32-record increment and an approximately 1.625-times growth calculation. The two shifted contributions truncate separately.

The function calls F-871e64ddc6de with the selected capacity shifted left by four bits and a second argument of zero. The first argument is the corresponding byte count only when the shift loses no significant bits.

The returned 32-bit value is retained as the prospective new base. There is no immediate failure or zero-result check.

Next, F-52aacc229f06 is called with two visible arguments:

1. The descriptor’s storage start, read for this call.
2. Position.

The supplied evidence does not establish a destination, transfer semantics, return-value use, or preservation guarantees for this call.

### Growth path: direct record write

After that call, the function reads storage start again. It subtracts this current start from Position, clears the low four bits of the difference, and adds the resulting offset to the retained new base.

If the computed address is nonzero, Source is copied there in this order:

1. Read Source words at offsets 4, 8, and 12, retaining their values.
2. Read the Source word at offset 0 and write it to destination offset 0.
3. Write the retained values to destination offsets 4, 8, and 12, in that order.

If the computed address is zero, this direct record copy is skipped, including its Source reads.

This is a guard on the computed insertion address, not on the returned base. A zero base does not necessarily suppress the copy, and a nonzero base does not necessarily guarantee a nonzero computed address.

Position is not required by an explicit check to be aligned. The growth path instead clears the low four bits of its difference from the currently observed start.

### Growth path: remaining calls and publication

The function next calls F-52aacc229f06 with four visible arguments:

1. Position.
2. The descriptor’s current logical end.
3. The retained new base plus the low-four-bits-cleared difference between Position and the descriptor’s current storage start, plus 16 bytes.
4. The descriptor address.

The start and end used here are read after the direct record write. They need not equal values observed earlier. In particular, a dependency or overlapping direct write could alter the descriptor. The supplied representation does not establish a separate observable order among reads used to form this call’s arguments.

F-10e1e4cd0e66 is then called a third time. Its 32-bit result is retained for the final logical-end calculation. Equality with either earlier result is not established.

The function next reads and retains the descriptor’s current storage start. An empty-body traversal begins there and advances by 16 bytes until its cursor equals the descriptor’s logical end. The loop condition accesses the logical-end field; the body performs no explicit record copy, destruction, or callback.

Normal completion requires the endpoint to be reached. A malformed endpoint has no explicit error or escape path. This is not an ordering-based bounds check.

After traversal, F-ff1bdc376dcd receives:

1. The start retained before traversal.
2. The signed right shift by four bits of the difference between the descriptor’s then-current storage limit and that retained start.
3. Zero.

Only after this call does the function publish the replacement descriptor, in this order:

1. Storage start becomes the retained new base.
2. Logical end becomes that base plus 16 times the third dependency result, plus 16 bytes.
3. Storage limit becomes that base plus 16 times the selected capacity.

These calculations use retained values, not a fresh size query after F-ff1bdc376dcd. No rollback or post-publication validation is visible.

### Spare-capacity path

All operations in this subsection occur after the initial F-10e1e4cd0e66 call has returned and the branch has selected this path. Descriptor and record values at this point may differ from function-entry values.

The function reads the current logical end and retains it as the old end. It immediately writes old end plus 16 bytes into the descriptor’s logical-end field.

If the old end is nonzero, it copies the 16 bytes immediately preceding that address into the slot beginning at the old end. The copies occur word by word, in increasing offset order: read one source word, write its destination word, then proceed to the next word. Unlike later copies, the higher-offset words are not all read before the first write.

A backward cursor is then positioned at old end minus 16 bytes. While it does not equal Position, the function copies the record immediately preceding the cursor into the record at the cursor:

1. Read the preceding record’s words at offsets 4, 8, and 12.
2. Read its word at offset 0 and write destination offset 0.
3. Write the retained higher-offset words in increasing offset order.
4. Move backward by one 16-byte record.

For a valid nonempty sequence and Position at an existing record boundary, these operations shift the records beginning at Position one slot toward the old end.

The loop uses address equality, not ordering. There is no lower-bound check against storage start. Position must be reached by the backward progression for ordinary bounded operation.

After the cursor equals Position, Source is copied into Position. The copy reads Source offsets 4, 8, and 12 first, then reads and writes offset 0, then writes offsets 4, 8, and 12.

Source is therefore not snapshotted before record movement. If it points into affected storage, the inserted words can reflect the post-shift contents rather than the function-entry contents.

### Unsupported boundaries and aliasing

Within the spare-capacity path, Position equal to old end does not trigger a direct append. The backward cursor starts one record before that address and moves toward lower addresses. A valid append result or normal bounded return is not established.

For an empty sequence with a nonzero old end, the initial duplication reads the record before that end. No safe empty insertion case is established.

The zero-old-end guard suppresses only the initial duplication. It does not validate subsequent cursor operations or the final Source copy.

The specified word-read order matters for overlapping Source and destination addresses. It is not equivalent in every overlap case to taking a complete record snapshot before any mutation.

## Side effects

Directly established effects are:

- Descriptor reads, including reads before and after dependency calls.
- Source reads when a direct record copy is executed.
- An early logical-end write on the spare-capacity path.
- Duplication, shifting, and insertion writes within existing storage on that path.
- A conditional 16-byte write at a computed prospective replacement-storage address.
- Three ordered descriptor writes at the end of the growth path.
- Dependency calls in the order described above.

There is no explicit bounds error, failure status, rollback, or exception-handling path. An invalid access after the spare-capacity end update can leave that update and earlier writes already performed. Exact fault or exception behavior is not established.

Allocation, transfer, and release are inferred roles, not proven ownership guarantees. No dependency is assumed to preserve globals, descriptor contents, records, Source, or ownership merely because of its apparent role.

## Acceptance examples

The first four examples begin **at entry to the spare-capacity path**, after the initial dependency has returned and selected that path. Their records, descriptor, and Source describe state at that point, not necessarily at function entry. They assume valid nonoverlapping descriptor storage, readable records, sufficient writable capacity, and representable address arithmetic.

To use the same examples as function-entry scenarios, additionally require that the initial call returns normally, selects the spare-capacity path, and preserves the descriptor and all relevant record and Source contents.

1. **Middle insertion**

   At path entry, storage contains A, B, C, with one spare slot. Position identifies B, and independent Source contains X.

   The logical end advances first. C is duplicated into the spare slot, B moves into C’s former slot, and X is written at Position. The resulting active sequence is A, X, B, C.

2. **Insertion before the last record**

   At path entry, storage contains A, B, C, with spare capacity. Position identifies C, and independent Source contains X.

   The initial duplication creates the new final C. The backward loop performs no iterations. The final copy produces A, B, X, C.

3. **Source affected by shifting**

   At path entry, storage contains A, B, C, with spare capacity. Position identifies B, while Source points to C’s original slot.

   C is duplicated into the new final slot. B is then written into C’s original slot. The final Source reads therefore supply B, producing A, B, B, C rather than A, C, B, C.

4. **Append position on the spare-capacity path**

   At path entry, Position equals the old logical end. The backward cursor starts one record before Position and moves toward lower addresses. This path is not accepted as an ordinary append operation; a valid result or normal bounded return is not promised.

5. **Growth request without overflow**

   Conditional on entering the growth path and the second F-10e1e4cd0e66 result being 8, the capacity candidates are 40 and 13. The selected capacity is 40, and F-871e64ddc6de receives 640 as its first argument.

   If execution reaches descriptor publication and the third result is also 8, the published logical end is 144 bytes after the retained new base, provided that address calculation is representable.

6. **Conditional insertion after growth**

   An insertion-equivalent final sequence requires additional dependency contracts: suitable replacement storage, the necessary prefix and suffix transfers, preservation of relevant values until their use, and normal return from the dependencies and traversal. The visible function alone does not establish that outcome.

7. **Capacity truncation**

   If unsigned capacity arithmetic or the left shift discards high bits, no explicit checked-failure branch intervenes. Rejection, saturation, or a guaranteed sufficiently large storage request is not an established outcome.
