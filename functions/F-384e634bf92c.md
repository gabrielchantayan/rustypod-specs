# F-384e634bf92c

## Purpose

F-384e634bf92c scans a zero-terminated byte sequence, submits ordinary spans to a dependency, and dispatches a restricted set of percent-prefixed conversions using four-byte argument slots.

The visible behavior resembles a formatting routine, but does not establish compatibility with a standard formatted-output API:

- Parsing recognizes at most one leading zero, one decimal digit, and one lowercase `l`.
- Only character conversion uses the retained digit, and only when it equals `4`.
- A backslash is handled literally, not as an escape introducer.
- Both hexadecimal conversion letters select the same table-driven construction.
- Unsupported conversions submit a space.
- String and hexadecimal branches execute a software interrupt whose interface is unknown.
- The represented return value is neither an established output count nor an updated argument cursor.

This contract describes static evidence. Dependency output, interrupt behavior, and external calling-convention compatibility remain unverified.

## Interface

### Inputs

| Input | Representation | Established role |
|---|---|---|
| Format address | 32-bit pointer to bytes | Starting position for scanning and conversion parsing. |
| Argument address | 32-bit pointer to 32-bit unsigned words | Starting argument cursor. Consuming a slot advances the local cursor by four bytes. |
| Auxiliary word | Opaque 32-bit value | Initializes four bytes of local storage subsequently overwritten by hexadecimal processing. |
| Auxiliary control word | Unsigned 32-bit value | Initializes a neighboring local word. Hexadecimal processing clears its least-significant eight bits. |

The lowercase `l` modifier does not increase argument width. Numeric and character conversions still consume one four-byte slot.

### Return representation

The supplied representation returns a 64-bit integer. Its low 32 bits are zero. Its high 32 bits are obtained from a four-byte local field initialized with the original argument address.

Hexadecimal processing overwrites that field with the first four bytes, in address order, of its eight-byte construction. Therefore, subject to normal returns and no other modification of the field:

- Before any hexadecimal conversion, the high half equals the original argument address.
- After a hexadecimal conversion, the high half reflects the first four constructed bytes interpreted according to target byte order.
- Ordinary argument-cursor advancement does not update this field.
- A later hexadecimal conversion replaces the earlier hexadecimal contribution.

The external meaning and ABI accuracy of this represented return are **documented_only**.

### Preconditions and ownership

No explicit pointer validation, argument-count check, or format-length bound is visible.

Defined memory access requires readable format storage at every inspected address, readable argument slots on branches that load them, and readable global/table storage on hexadecimal branches. Incomplete percent conversions can continue beyond a zero terminator.

The function directly performs no allocation, release, or ownership transfer. Passing a format span to a dependency does not establish whether that dependency retains, modifies, or releases associated memory. The same uncertainty applies to addresses available through an undocumented interrupt convention.

## Behavior

### Scanning and span submission

At the start of each iteration, the current format byte is read. If it is zero, the function returns immediately.

Otherwise, scanning proceeds until encountering a zero byte, percent byte `0x25`, or backslash byte `0x5c`. If the stopping address is greater than the span’s starting address, F-249f40881306 is called with:

- The span’s original address.
- Its byte length, formed by subtracting address representations using 32-bit integer arithmetic.

The stopping byte is excluded from the submitted span. The function does not copy the span before the call. Address wrapping, invalid pointer ordering, and subtraction outside the applicable address range have no established safe behavior.

After the call, if any, the stopping byte is read again. Dispatch uses this later value, not necessarily the value that stopped scanning. A dependency that changes format storage can therefore change the subsequent dispatch. The next format position has been set to one byte after that stopping address.

A reread value of zero selects return. A reread percent selects conversion parsing. Otherwise, the numeric value obtained from the reread byte is passed to F-9b794b5e3b70. With unchanged format storage, this last case is the backslash path.

### Backslashes

An unchanged backslash stopping byte causes a call to F-9b794b5e3b70 with `0x5c`. Processing then resumes at the following byte.

No escape-sequence interpretation is visible. A backslash followed by `n` does not request a newline. A backslash followed by percent does not prevent the percent from introducing a conversion on the next iteration.

### Percent parsing

After percent, the parser recognizes these components in order:

1. One optional ASCII zero.
2. At most one decimal digit.
3. One optional lowercase `l`.
4. One conversion byte.

The retained digit defaults to zero. The optional leading zero has no separate visible formatting effect.

The digit test uses a 32-bit unsigned subtraction of ASCII zero followed by a comparison against ten. It recognizes the decimal range rather than a general width field.

The format cursor is positioned immediately after the selected conversion byte before the conversion action. Extra digits and repeated modifiers are not combined. They can become the conversion byte themselves, leaving following bytes for ordinary scanning.

No intermediate check rejects a zero byte. If the selected conversion byte is zero, the unsupported-conversion action occurs, then scanning resumes beyond that terminator.

### Signed decimal: `d`

This branch reads one 32-bit argument word and interprets its bits as signed 32-bit for the negativity test.

For a nonnegative value, the local argument cursor advances by four bytes, then F-62c65906c5c5 receives the loaded word.

For a negative value, the order is:

- Read the argument word.
- Call F-9b794b5e3b70 with minus-sign value `0x2d`.
- Negate the loaded value using unsigned 32-bit arithmetic.
- Advance the local argument cursor by four bytes.
- Call F-62c65906c5c5 with the resulting magnitude.

The argument slot is not reread after the minus-sign call. A change to that slot during the call does not alter the already-loaded value.

Unsigned negation is modulo \(2^{32}\). For input bits `0x80000000`, the magnitude remains `0x80000000`, or unsigned 2147483648. No overflow diagnostic is visible.

### Unsigned decimal: `u`

This branch reads one 32-bit argument word, advances the argument cursor by four bytes, and passes the loaded unsigned value to F-62c65906c5c5.

The dependency’s exact representation, destination, and error behavior are not established by this function.

### Character: `c`

This branch reads one 32-bit argument word and advances the local argument cursor by four bytes.

- If the retained digit equals `4`, it calls F-a809090bf0bb.
- Otherwise, it calls F-9b794b5e3b70 with the entire loaded 32-bit value.

No explicit eight-bit narrowing precedes the ordinary character call. Truncation, encoding, and range handling are dependency behavior.

The representation supplies no explicit arguments to F-a809090bf0bb. Although this branch consumes and loads a word, its relationship to that call is unknown. Four-character output is not an established contract.

### Hexadecimal: `x` and `X`

Both letters select the same branch. Neither selects a separate table or case mode.

The branch first loads one 32-bit argument word, then clears the least-significant eight bits of the local auxiliary control word, preserving its upper 24 bits.

It constructs eight bytes in a local scratch region. Construction proceeds from the region’s highest byte offset to its lowest:

- The first lookup uses the loaded word’s least-significant four bits and writes offset 7.
- Each succeeding lookup uses the next four-bit group and writes the next lower offset.
- The eighth lookup uses the original most-significant four bits and writes offset 0.

Between lookups, the working value is shifted logically right by four bits. Exactly eight lookups occur, including groups whose value is zero.

**Each iteration reads a global value holding the table base address, then reads one byte at that address plus the current four-bit index.** The representation does not establish a base address cached across iterations or conversions.

The observable lookup order therefore includes, for every generated byte:

- A read of the global table-base value.
- A byte read through that iteration’s base and index.
- A write to the selected scratch byte.

Changing the global base can redirect later reads to another table. Changing table contents can alter later bytes without changing the base. Dependencies or interrupts executed earlier can affect either source of data. If updates become visible between iterations, a single construction can contain bytes obtained through different base values or different table contents. No synchronization or stable-table guarantee is visible.

The represented local layout is:

| Offset from scratch start | Initial contents | Hexadecimal effect |
|---|---|---|
| 0–3 | Saved original argument address | Replaced by the first four constructed bytes in address order. |
| 4–7 | Auxiliary word | Replaced by the remaining four constructed bytes. |
| 8–11 | Auxiliary control word | Least-significant eight bits cleared; upper 24 bits preserved. |

Clearing the control word’s least-significant eight bits does **not**, by itself, identify which address contains the zero byte.

- **Conditional on little-endian layout**, offset 8 becomes zero, immediately following the eight generated bytes. The local region then contains an eight-byte sequence followed by a zero byte before the interrupt, absent other modification.
- Without that byte-order condition, only the numeric bit clearing is established. Immediate zero termination of the eight-byte sequence is not guaranteed.

After construction, the branch executes software interrupt `0x123456`. The argument cursor advances by four bytes only after the interrupt returns.

The table’s contents are unknown. Eight indexed bytes are established; conventional hexadecimal digits, letter case, and actual emission are not.

### String: `s`

This branch advances the local argument cursor by four bytes, then executes software interrupt `0x123456`.

No explicit argument-slot load, string-pointer dereference, length computation, or null-pointer check appears in this branch. String output cannot be required without evidence about the interrupt interface.

Its ordering differs from hexadecimal processing: string advancement occurs before the interrupt; hexadecimal advancement occurs afterward.

### Literal percent and unsupported conversions

A percent conversion byte causes F-9b794b5e3b70 to receive `0x25`, without consuming an argument.

Every unsupported conversion byte causes that dependency to receive space value `0x20`, also without consuming an argument. This includes uppercase `L`, excess digits selected as conversion bytes, and zero selected during incomplete parsing.

## Side effects

Directly established effects are:

- Format-byte reads, including rereading a stopping byte after span submission.
- Four-byte argument loads for `d`, `u`, `c`, `x`, and `X`.
- A global table-base read and an indexed table-byte read for each of eight hexadecimal iterations.
- Writes to local hexadecimal scratch storage and the auxiliary control word.
- Calls to the four identified dependencies.
- Software interrupt `0x123456` for `s`, `x`, and `X`.
- Changes to local format and argument cursors.

There are no visible direct writes to caller-owned format storage or argument slots. Advancing a local cursor does not update the caller’s pointer object.

These observations do not establish preservation of caller memory, globals, output channels, or ownership by dependencies or interrupt handlers. In particular, later hexadecimal processing must not assume earlier calls preserved either the global table base or table contents.

Ordinary dependency return values are ignored. There is no explicit error result, retry, rollback, or recovery path for invalid memory, dependency failure, or an interrupt that faults or does not return.

## Acceptance examples

These are conditional static criteria, not runtime results. Unless an example says otherwise, memory is readable, calls return normally, and no external effects alter relevant state.

1. **Empty format.** An initial zero causes immediate return without dependency calls or argument-slot loads. The represented return has zero low half and the original argument address as its high half.

2. **Ordinary text.** `abc` followed by zero produces one F-249f40881306 call covering exactly three bytes. The stopping zero is reread afterward.

3. **Stopping-byte mutation.** If the span dependency changes the percent that ended a scan into a backslash, subsequent dispatch submits `0x5c`; it does not parse the original percent.

4. **Literal percent and backslash.** `a%%b` submits span `a`, value `0x25`, then span `b`, consuming no arguments. A backslash followed by `n` submits `0x5c`, then treats `n` as ordinary text.

5. **Signed boundaries.** `%d` with −7 submits a minus sign before numeric value 7. Input bits `0x80000000` submit a minus sign followed by unsigned 2147483648. Each consumes one slot.

6. **Restricted width syntax.** `%9u` and `%09u` pass the same loaded unsigned value without established padding. `%12u` submits a fallback space for conversion byte `2`, then treats `u` as ordinary text; it consumes no argument.

7. **Modifier width.** `%lu` consumes four bytes, not eight.

8. **Character special case.** `%4c` loads and consumes one word, then calls F-a809090bf0bb without explicit call arguments. `%3c` instead passes the full word to F-9b794b5e3b70.

9. **Shared hexadecimal branch.** With identical argument values, an unchanged global base, and unchanged indexed contents, `%x` and `%X` construct identical bytes and execute the same interrupt.

10. **Conditional conventional digits.** If every lookup resolves through a stable table containing conventional hexadecimal digits, value `0x12` constructs six zero digits followed by the entries for 1 and 2. This does not establish interrupt output.

11. **Base versus contents.** If an earlier dependency redirects the global base, later hexadecimal lookups use that new base. If the base remains unchanged but indexed bytes change, later lookups use the changed contents. A prior hexadecimal interrupt can affect either before the next conversion.

12. **Conditional termination.** On little-endian layout, clearing the control word’s low eight bits places zero at offset 8. Without established byte order, immediate zero termination is not an acceptance requirement.

13. **String-path limit.** `%s` advances one slot before the interrupt, without an explicit slot load. Reading or emitting a pointed-to string is not an established requirement.

14. **Incomplete conversion.** A format ending immediately after percent selects zero as an unsupported conversion, submits a space, and resumes beyond that terminator. Subsequent behavior depends on accessible memory.
