# F-2cf379ad0812

## Purpose

F-2cf379ad0812 derives a masked value from one 16-bit table entry, supplies a compact representation of that value and its index to an opaque dependency, and subsequently stores the derived value in a destination table.

The source and destination are selected through separate base references. Their storage may be identical, overlapping, or distinct; the supplied evidence does not establish which. This is therefore a source-derived update, not necessarily an in-place update or a merge with the destination’s existing contents.

Two different representations of the derived value are observable:

- The final table write contains its lowest sixteen bits.
- The compact representation contains only its lowest nine bits, together with seven index bits.

The compact representation cannot, by itself, identify every bit written to the destination.

A notification or command operation bracketed by synchronization is a possible interpretation of the dependency sequence. Neither transport nor synchronization semantics are established.

## Behavior

### Source-derived value

One unsigned 16-bit source entry is read before any dependency is invoked. There is no visible second source-entry read.

The mask determines each bit of the derived value independently:

- A clear mask bit selects the corresponding source bit.
- A set mask bit selects the corresponding replacement bit.

The source entry is zero-extended for this calculation. Consequently, source-selected positions above bit 15 are zero.

Under the 32-bit integer interpretation, the mask and replacement participate at their full 32-bit width. Neither is first restricted to sixteen bits. Replacement-selected bits above bit 15 can therefore exist in the derived value, although they affect neither the compact representation nor the final table contents.

The destination’s prior contents do not participate. In particular, a zero mask preserves the source entry, not the entry already stored at the destination.

### Compact representation and storage layout

Before the dependency sequence begins, the function creates a four-byte local object containing a zero-extended 16-bit compact value.

The compact value has the following numeric bit layout:

| Compact bit positions | Meaning |
|---|---|
| 15–8 | Derived-value bits 7–0 |
| 7–1 | Index bits 6–0 |
| 0 | Derived-value bit 8 |

This layout applies where the represented index arithmetic is defined. The lowest seven index bits survive; higher index bits do not. Derived-value bits 9 and above are absent.

As a result:

- Indices differing by 128 can produce identical compact values for the same derived value.
- Such indices still select entries 256 bytes apart in a table.
- A change confined to derived-value bits 9–15 changes the final stored value without changing the compact value.
- Derived-value bit 8 affects the lowest compact bit, not the compact value’s high byte.

The four-byte object’s upper sixteen numeric bits are initially zero. Its memory-byte order depends on the target representation. Numeric field placement does not establish the byte sequence consumed by a dependency.

The object is prepared before F-b574a99094fc is called. No subsequent reconstruction of it is visible.

### Destination update

After all three dependencies return normally, the function uses the destination-table base reference and writes the lowest sixteen bits of the previously derived value at the selected entry.

The base used for this write is obtained after the dependency sequence. A dependency’s change to that reference can therefore redirect the final write. There is no established requirement that the destination base retain its entry-time value.

The stored value remains based on the original source read. There is no visible refresh from the source, no merge with the destination, and no recalculation from the compact object.

On the normal-return path, the write is unconditional. A dependency return value cannot suppress it through any decision visible in this function.

## Side effects

The source-base access and source-entry read precede all three dependency calls. The compact object is prepared before the first call. The calls follow the order specified above. Only after the third returns does the function access the destination base and perform the destination write.

These ordering constraints matter even if the two table references happen to alias:

- The function’s own table write does not precede the dependency sequence.
- Dependency changes to table contents occur after the source value has already been sampled.
- Dependency changes to the destination base can affect where the final write lands.

The ordering alone establishes neither atomicity nor synchronization with other execution contexts.
