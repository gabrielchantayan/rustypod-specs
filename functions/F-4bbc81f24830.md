# F-4bbc81f24830

## Purpose

The established behavior has three principal outcomes:

- Reject a null object.
- For certain same-owner cases, either increment the count or return a fixed error.

## Side effects

### Direct object mutations

Only two fields are visibly written:

- Offset 4: the 32-bit identity, after successful acquisition.
- Offset 18: either an incremented 16-bit count or the value one.

On acquisition success, the owner write precedes the count write. On the same-owner, mode-two success path, only the count is directly written.

The function does not directly modify the discriminator or mode fields.

“No direct write” does not mean “no state change.” Any dependency already invoked may have modified the object, globals, synchronization state, or other resources.

### Arithmetic and representation

The count is read as unsigned 16-bit data. The incremented value is ultimately stored as 16 bits.

Although the intermediate count result is represented using a signed 16-bit temporary in the supplied evidence, it must not be interpreted as a negative status or a reason to reject counts above 32,767. For example, incrementing 32,767 stores the bit pattern representing the unsigned count 32,768.

The explicit rejection at 65,535 prevents a successful count increment from wrapping to zero. A count of 65,534 successfully becomes 65,535; a subsequent otherwise-equivalent increment attempt is rejected.

### Ownership and lifetime
