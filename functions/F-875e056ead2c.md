# F-875e056ead2c

## Purpose

F-875e056ead2c conditionally adjusts an object’s eight-byte-record array toward a target count obtained from an associated context. On the count-mismatch path, it populates eligible destination indices from three source collections, assigning categories 0, 1, and 2 in that order.

Population starts at the **first observed destination count**, independently of later count observations and extent adjustment. Preservation of records already present when population begins is therefore not unconditional: inconsistent observations or intervening changes can cause such records to be overwritten.

Every normally completing path decrements a field in a separately acquired completion context and conditionally invokes an indirect callback.

Incremental synchronization of a cached array is inferred intent. The established behavior does not guarantee that the final extent equals the target, that every requested record is initialized, or that existing records are refreshed consistently.

## Behavior

### Initial observations and equality decision

The visible call order is:

1. Acquire the completion context through F-4286044f4c6c without an explicit argument.
2. Invoke F-4a19e3742733 without explicit arguments.
3. Acquire an object-associated context through F-4286044f4c6c.
4. Pass that context’s location at +104 to F-421ee22ef2f3 to obtain the target count.
5. Query the destination descriptor through F-3952b8ae1dfd.
6. Query the same descriptor through F-3952b8ae1dfd again.

The first destination-count result is retained as the population starting index. The second determines whether reconciliation is entered. Both results and the target are treated as 32-bit unsigned counts for the relevant comparisons.

If the second result equals the target:

- No extent-adjustment dependency is called.
- No source collection counts are read by the reconciliation logic.
- No destination records are explicitly populated.
- Completion handling follows.
- The incoming third argument remains the candidate third callback argument.

Equality does not validate record contents or the consistency of earlier observations.

### Extent adjustment on mismatch

A mismatch causes another destination-count query.

If this result is below the target, the function:

- Reads and retains the destination logical end.
- Queries the destination count again.
- Calls F-8e746d73846b with the descriptor address, retained logical end, target minus the latest count, and an address in temporary local storage.

The difference is a 32-bit unsigned subtraction. The growth condition is not checked again after the latest query. Consequently, if that query exceeds the target, the supplied difference wraps modulo \(2^{32}\).

The temporary storage’s initial contents, interpretation, and lifetime requirements are unknown. It is not established to contain a zero-filled record.

If the first count observed inside the mismatch branch is not below the target, another count query occurs. Direct truncation is entered only if this latest result exceeds the target. If it does not, extent adjustment is skipped, but population processing still follows.

### Direct truncation: captured values and fresh reads

Direct truncation first captures the logical end. It also computes a target address from a destination-base read plus eight times the target count. A further destination-base read is compared with the captured end.

If that base equals the captured end, no direct logical-end update occurs.

Otherwise:

- A visible copying region performs no iterations: its source cursor begins equal to its fixed stopping value. It therefore performs no record copies.
- A traversal cursor begins at the computed target address.
- **Every traversal condition reads object offset +16 again** and compares the cursor with that freshly read logical end.
- An unsuccessful comparison advances the cursor by eight bytes. The traversal itself performs no payload reads, payload writes, or destructor calls.
- After traversal terminates, the logical end is read again for the final subtraction.

The subtraction amount is derived from the **captured** end minus the **computed** target address, with the low three bits cleared by a 32-bit mask. The minuend is the **freshly reloaded** logical end, not necessarily the captured end.

Thus traversal termination and the final update can observe different logical ends. With stable memory, valid nonwrapping address relationships, and an eight-byte-aligned difference, the final end equals the computed target address. Without those assumptions, that result is not guaranteed.

A cursor that cannot encounter the values read from +16 may fail to terminate. No timeout or explicit failure exit is visible.

### Population observations and context independence

Population uses the original first destination-count result as its starting index. It does not substitute a post-adjustment count.

Before processing collections, the function independently:

1. Acquires an object-associated context and retains the address of its field at +104.
2. Acquires another object-associated context, reads its first-collection pointer at +8, and captures that collection’s count.

The retained +104 address is the table-field location. Each populated record reloads the 32-bit table base from that location. The location itself is not reacquired per record.

For every collection, three distinct observations must be distinguished:

- **Boundary count:** captured from a collection reached through a context acquisition for that count.
- **Initial-position collection:** obtained through another context acquisition, performed only when that collection is eligible for population.
- **Per-record collection:** obtained through a fresh context acquisition before each record lookup.

These contexts and collections need not agree. The body does not verify that an initial position is valid for a subsequently acquired collection.

### First collection

First-collection population is eligible when the retained destination index is below both the target and the captured first count.

On entry, a fresh context acquisition supplies the first collection to F-d3449d7b840a, together with the retained destination index. Its result establishes the initial lookup position.

Each iteration obtains another context and passes its first collection and the current lookup position to F-7d60babd66f2. It writes category 0 and advances the destination index.

The loop’s unsigned ordinal begins at the retained index and advances once per record. Population continues only while that ordinal is below the captured first count and the destination index is below the target. The collection count is not reread during this loop.

### Second and third collections

After first-collection processing, a fresh context acquisition supplies the second collection pointer at +12 and its count. This count acquisition occurs even if the target has already been reached.

The second interval begins at the captured first count. Its end is the 32-bit unsigned sum of the captured first and second counts. Eligibility requires the current destination index to be below the target, at least the interval start, and strictly below the interval end, using unsigned comparisons.

If eligible, another fresh context acquisition supplies the second collection to F-d3449d7b840a. The initial relative index is the destination index minus the captured first count.

For each record, another context acquisition supplies the second collection to F-7d60babd66f2. Category 1 is written. Iteration continues while the relative index is below the captured second count and the destination index is below the target.

The first-plus-second count sum is then retained as the third interval’s start. A fresh context acquisition supplies the third collection pointer at +4 and its count, even if no additional records are needed.

The third interval end adds the captured third count using 32-bit unsigned arithmetic. Eligibility and iteration follow the same structure as the second collection, with category 2 and indices relative to the third interval’s start.

For the second and third eligibility checks, when the destination index is below the target, the corresponding collection-pointer field is also visibly reread from the context just used for the count. That pointer value does not establish a shared identity with the later initial-position or per-record collection.

Wrapped interval sums are compared as unsigned values. They are not guaranteed to represent ordinary concatenated mathematical intervals. No fourth collection or fallback-fill operation exists.

### Record writes and lookup progression

For each populated record, the established sequence is:

1. Acquire a context and call F-7d60babd66f2 with that context’s relevant collection and the current lookup position.
2. Write the one-byte category at destination record offset +4.
3. Compute the next lookup position from the returned signed 32-bit value plus one.
4. Write the returned 32-bit value at record offset +0.
5. Advance the destination index, while retaining the just-populated index for addressing.
6. Read the 16-bit table entry corresponding to that retained global destination index and write it at record offset +6.

The destination-base field is reloaded for the separate record-field accesses. A record update is therefore not guaranteed to use one immutable destination base if memory changes between accesses.

The table entry is addressed at the current table base plus twice the populated global index, not a collection-relative index. The table-field address is retained independently of all collection contexts.

The next lookup position depends on the lookup **result**, not merely the preceding position. Because the result is represented as signed 32-bit and one is added to it, behavior at the signed maximum is unresolved. Unlike the explicitly unsigned count arithmetic, wrapping is not established.

The record byte at +5 is not explicitly written.

### Completion handling

After all preceding work returns and traversal terminates, the function:

1. Reads the completion context’s 32-bit counter at +100.
2. Subtracts one and writes the result back.
3. Reads the pointer at completion-context offset +92.
4. If nonzero, reads the pointer’s first 32-bit value.
5. Invokes the indirect callback only if both the pointer and the loaded value are nonzero.

The callback receives, in order:

- The value loaded through the +92 pointer.
- The decremented counter.
- The incoming third argument on the initial equality path, or the unresolved replacement value on the mismatch path.
- The address of the completion context’s +92 field.

The callback target is an unresolved indirect dependency; the loaded cell value is a callback argument, not an established callback address.

No callback result is used, and no explicit operations follow the callback. Counter arithmetic at the signed 32-bit minimum is unresolved.

## Side effects

Explicit effects comprise dependency calls, a possible logical-end update, population writes at record offsets +4, +0, and +6 in that order, a completion-counter update, and a conditional indirect callback.

No allocation, deallocation, record destruction, or ownership transfer is explicitly performed by the surrounding body. Dependencies may perform any of these; their contracts are not supplied.

Passing temporary storage to F-8e746d73846b does not establish whether it reads, modifies, copies, or retains that storage. Safe retention beyond the invocation is not established.

Writes are incremental and nontransactional. Interrupted execution can leave partial records, an adjusted extent without complete population, or populated records without the completion decrement.

Existing records are preserved only under suitable consistency assumptions. The unconditional rule is population of eligible indices beginning at the retained first count, not preservation of every record present at population time.

## Acceptance examples

These are conditional static consequences, not runtime results. Except where variation is explicit, assume valid storage, stable dependencies and memory, nonoverflowing arithmetic, representable lookup increments, and successful dependency completion.

1. **Initial equality skips reconciliation.**  
   If the second destination count and target are both four, no explicit extent adjustment or record population occurs. Completion still decrements the counter and may invoke the callback.

2. **Population spans three categories.**  
   With an initial retained count of one, target five, and source counts two, two, and one, successful growth is followed by category 0 at index one, category 1 at indices two and three, and category 2 at index four. Index zero is preserved under the stated stability assumptions.

3. **Stable truncation.**  
   With five aligned records, stable count observations of five, and target two, direct truncation places the logical end at the two-record boundary. Population does not run because its retained starting index is five. Removed records are not explicitly cleared or destroyed.

4. **Changing end during truncation.**  
   Suppose the captured end is 40 bytes beyond the base and the computed target address is 16 bytes beyond it. If traversal instead encounters a freshly read end 48 bytes beyond the base, and the final reload also reads that value, the rounded subtraction remains 24 bytes. The stored end is therefore 24 bytes beyond the base, not the target address.

5. **Already-present records can be overwritten.**  
   Suppose the first count is one, subsequent observations report three, the target is four, and growth leaves three existing records followed by added storage. If source eligibility covers indices one through three, population writes those indices. Records one and two can therefore be overwritten despite existing at population time.

6. **Insufficient source coverage.**  
   With retained count zero, target five, and three source counts of one each, only indices zero through two receive explicit source-loop population. Indices three and four have no guaranteed contents from these loops.

7. **Collection identity changes.**  
   A captured first count of two can govern iteration even if the initial-position acquisition and each per-record acquisition return different collections. Provided those dependencies accept the supplied positions, category-0 records contain results from the per-record collections, not necessarily the collection whose count was captured.

8. **Callback gating and argument selection.**  
   A null +92 pointer skips the cell read and callback. A non-null pointer containing zero permits the cell read but skips the callback. For a nonzero cell, an incoming third argument of 17 is forwarded on the equality path; the mismatch path instead supplies the unresolved replacement value.

9. **Signed lookup boundary.**  
   If a lookup returns the signed 32-bit maximum, the category write precedes the next-position addition. This contract does not require a wrapped next position or guarantee subsequent writes and completion for that execution.
