# F-9b364c7d5a0a

## Purpose

F-9b364c7d5a0a searches a table of two-field records for a key and returns the associated 16-bit value. It returns zero when the visible search does not find a matching key.

The table is searched by comparing the query against record keys and repeatedly narrowing a contiguous candidate interval. This supports the inferred intent of an exact-match lookup over records ordered by nondecreasing key.

Zero is not a distinct failure indicator: a matching record whose associated value is zero produces the same result as a failed lookup.

This contract distinguishes:

- **Established static behavior:** operations and control flow visible in the supplied material.
- **Inferred intent:** the sorted-table lookup interpretation and the conditions under which it works as intended.
- **Documented-only unknowns:** target execution details and behavior outside the supported memory and arithmetic assumptions.

No runtime tests have been performed.

The record stride is four bytes. For record index \(i\), its key is at byte offset \(4i\) from the table address, and its associated value is at byte offset \(4i+2\).

## Behavior

### Initial endpoint filtering

The first observable table read is the key of the first record. This read occurs regardless of the supplied count.

If that first key is greater than the query, the function returns zero immediately. On this path, it does not read the computed final key or any associated value.

Otherwise, it computes the address immediately after the declared records and reads the key one record before that address. For a valid positive count, this is the key of the last record.

If the query is greater than that final key, the function returns zero.

Consequently, entry into the search requires:

\[
\text{first key} \leq \text{query} \leq \text{last key}.
\]

These are unsigned numeric comparisons. A 16-bit table key is compared without interpreting its high bit as a sign bit.

On the represented 32-bit query model, any query above 65,535 cannot match a table key. Such a query passes the first-key comparison, causes the computed final key to be read, and then returns zero. It is not narrowed to 16 bits before comparison.

The endpoint checks do not themselves return a value for an equal key. Even when the query equals the first or last key, the function enters the interval search.

### Candidate interval and pivot selection

After successful endpoint filtering, the candidate interval initially spans all declared records.

Before each pivot read, the function checks whether the candidate interval has become empty. If its upper record address is below its lower record address, it returns zero without reading another key.

For a nonempty interval, the pivot is the middle record, choosing the lower of the two central records when the interval contains an even number of records.

For a valid interval containing \(m\) records, the pivot lies

\[
\left\lfloor \frac{m-1}{2} \right\rfloor
\]

records after its lower endpoint.

The visible calculation obtains this position from an address difference, shifts that difference right by three bits, and scales the result in 16-bit elements. Under the intended four-byte record layout and valid nonnegative arithmetic, this selects the lower midpoint described above.

### Comparison and interval changes

The function reads the pivot’s key and compares it with the query:

- **Query below the pivot key:** the next candidate interval retains the current lower endpoint and ends one record before the pivot.
- **Query equal to the pivot key:** the function reads the pivot’s associated value and returns it immediately.
- **Query above the pivot key:** the next candidate interval begins one record after the pivot and retains the current upper endpoint.

The comparisons impose those logical outcomes. They do not establish a requirement for an exact number of physical machine loads of the pivot key.

Only the associated value of a selected matching record is explicitly read. Associated values of rejected records do not participate in searching.

If narrowing exhausts the candidate interval, the function returns zero.

### Duplicate keys

Duplicate keys are not rejected. For a stable, nondecreasing table, a matching duplicate encountered at a pivot is returned immediately.

The function does not seek the first duplicate, the last duplicate, or a duplicate with a particular associated value. The selected record depends on the interval and lower-midpoint search path.

Changing the table length can change the selected duplicate even when the original duplicate records retain their relative order.

### Arithmetic and boundary limitations

The endpoint calculation scales the signed record count by two in units of 16-bit fields. The integer-address midpoint calculation also depends on signed arithmetic.

For the 32-bit model, counts above 1,073,741,823 already exceed the nonnegative representable range of that signed multiplication. That bound is not a sufficient memory-safety condition: pointer scaling, the available address space, the allocated object, and signed address-difference representability impose further restrictions.

The visible logic does not detect arithmetic overflow or address wraparound.

When narrowing below the first candidate, it can form an upper address one record before the lower address and then use an address comparison to recognize exhaustion. It does not deliberately dereference that exhausted upper position. The legality of forming and comparing such an address depends on the execution model; it must not be assumed to be portable across all language-level pointer models.

## Side effects

### Observable reads

For valid ordinary memory, the visible access order is:

1. Read the first key.
2. If the first-key comparison permits continuation, read the computed final key.
3. If both endpoint checks permit continuation, read pivot keys in search order.
4. On an exact pivot match, read that record’s associated value.

Endpoint keys can subsequently be revisited as pivot keys. The endpoint filter does not cache an associated value.

This order matters for invalid addresses, concurrently modified tables, and memory with read-triggered effects. The function provides no snapshot or synchronization mechanism.

### Writes and state changes

No explicit writes to the table, output memory, or global state appear in the supplied body.

The candidate bounds and pivot are internal search state. They do not constitute persistent table modification.

### Ownership and lifetime

The caller must keep the memory needed by the executed path readable for the duration of the call. No ownership transfer is established.

### Errors

Zero is the only visible lookup-failure result. There is no explicit error reporting or recovery for invalid memory, invalid count, misalignment, arithmetic failure, or concurrent modification.

A memory fault is not specified to become a zero return.

## Acceptance examples

The following examples are conditional expectations derived from static inspection. They assume readable, stable memory and arithmetic that follows the intended address model. They are not executed test results.

### Single-record match

For a table containing the record `(key 12, value 900)` and count 1, query 12 returns 900.

The first and final endpoint checks address the same key. The subsequent pivot also selects that record, and its associated value is returned.

### Query below the first key

For any positive-count table whose first key is 12, query 11 returns zero after the first-key read.

The computed final key and associated values are not read on this path.

### Query above the final key

For the ordered records `(12, 900)`, `(20, 901)`, and `(40, 902)`, query 41 returns zero after reading the first and final keys. No pivot search is entered.

### Missing key within the endpoint range

For the same three records, query 30 passes the endpoint filter.

The initial pivot has key 20. The search then considers the record with key 40, excludes it because 30 is smaller, exhausts the interval, and returns zero. No associated value is selected.

### Lower midpoint for an even-sized interval

For the records `(10, 100)`, `(20, 200)`, `(30, 300)`, and `(40, 400)`, query 20 returns 200 from the initial pivot.

The initial pivot is the second record, not the third.

### Duplicate selection

For the records `(5, 50)`, `(7, 70)`, `(7, 71)`, and `(9, 90)`, query 7 returns 70.

The initial lower midpoint is the second record, which matches immediately. The function does not continue to the later duplicate.

### Successful zero-valued result

For a single record `(12, 0)`, query 12 returns zero after finding the record and reading its value.

The result alone cannot distinguish this case from an absent key.

### Query wider than a key

On the represented 32-bit query model, query 65,536 returns zero for any valid positive-count table.

The query is not treated as key zero. The first and final keys are read, and the final endpoint comparison rejects it.

### Invalid count does not imply safe rejection

For count zero, the first key is still read.

If that key is greater than the query, the function returns zero immediately. Otherwise, the computed final-key location is one record before the supplied table address and is read. No safe empty-table result is established for that path.
