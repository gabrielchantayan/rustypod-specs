# F-8b1d38988a0b

## Purpose

F-8b1d38988a0b exposes a partially recovered sequence of four indirect calls followed by a 16-bit memory write. The first argument is supplied to the first call. A value derived from an incoming register is supplied to the third call alongside the second call’s result. The final write uses an address derived from the third argument.

The available representation ends at an instruction-decoding failure. It does not establish a normal return, a reliable terminal exception, or any behavior beyond the final visible write. Accordingly, this contract describes the recovered prefix, not a complete executable implementation.

No application-level purpose is established. Interpreting the calls as initialization, dispatch, device access, allocation, or another higher-level operation would be speculative.

## Behavior

### Recovered call sequence

The established relative order is:

1. Prepare the register-derived value by shifting the incoming register value left by nine bits.
2. Invoke D-01 with the first explicit argument.
3. Invoke D-02 without explicit arguments and obtain its 32-bit result.
4. Invoke D-03 with D-02’s result as its first explicit argument and the previously prepared shifted value as its second.
5. Invoke D-04 without explicit arguments.
6. Perform the destination-address calculation and write the 16-bit value 205.

No explicit use of D-01’s, D-03’s, or D-04’s return value appears. D-02’s result is forwarded to D-03 without a visible comparison, range check, dereference, or conversion to another width.

Each later step is conditional on execution reaching it. If a dependency does not return, the subsequent calls and final write are not established to occur. If a dependency changes memory or machine state, those effects happen before later steps according to this call order.

This sequence does not establish that dependencies preserve globals, memory, hardware state, or ownership. It also does not establish the precise instruction-level mechanism used to retain values across calls.

### Register-derived argument

The shifted quantity is prepared from the incoming register value before D-01. It is not visibly recomputed from that register after the intervening calls.

The apparent machine width is 32 bits. Under a 32-bit bit-vector interpretation, shifting left by nine discards the upper nine bits and inserts nine zero bits at the low end. For example:

- An incoming value of zero produces zero.
- An incoming value of one produces 512.
- An incoming value with only bit 23 set produces zero after 32-bit truncation.

The recovered signed-looking notation does not establish source-language signed-shift semantics. In particular, negative inputs or overflowing positive shifts must not be assigned portable language-level behavior from this representation alone. The examples above are conditional on the 32-bit bit-vector interpretation.

### Destination-address calculation

The final address is derived from the third argument in three stages:

- First, obtain a signed-looking right shift by 11 bits.
- Next, reinterpret that shifted value as an unsigned 32-bit quantity and shift it right by two bits.
- Finally, add the two quantities and use the sum as the destination address.

The distinction between the two shifts matters. The first operates on a recovered signed 32-bit input; the second explicitly operates on an unsigned 32-bit value.

For a precise conditional arithmetic model, let:

- \(p\) be the signed 32-bit third argument.
- \(q\) be \(p\) shifted right arithmetically by 11 bits.
- \(U(q)\) be the unsigned 32-bit interpretation of \(q\).

Then the destination is:

\[
A = \left(U(q) + \left\lfloor \frac{U(q)}{4} \right\rfloor\right) \bmod 2^{32}.
\]

This formula assumes an arithmetic first shift and 32-bit address arithmetic. The representation supports those as a plausible machine interpretation, but does not independently establish the architecture’s shift and pointer-conversion rules.

Under that interpretation:

- \(q\) ranges from \(-1{,}048{,}576\) through \(1{,}048{,}575\).
- For nonnegative \(p\), the address ranges from zero through 1,310,718.
- Negative \(p\) does not merely produce a negative or sign-extended destination. The unsigned second shift places the resulting addresses between `0x3FEC0000` and `0x3FFFFFFE`, with gaps.
- Inputs in the same arithmetic-right-shift bucket of 2,048 consecutive integers produce the same destination.
- The computed address need not be aligned to a two-byte boundary.

The low 11 input bits therefore do not independently select a byte within a destination object. They are discarded before address formation.

### Final memory write

The visible store writes a 16-bit quantity whose value is 205, or `0x00CD`.

This is not an 8-bit write. At the recovered representation level, it writes two bytes starting at the computed destination, including the zero-valued high portion of the 16-bit value.

Byte order is unknown:

- On a little-endian target, the two stored bytes would be `CD 00`.
- On a big-endian target, they would be `00 CD`.

No earlier destination read is explicit, so the operation is not visibly a read-modify-write. No allocation, object-boundary check, bounds check, or alignment adjustment precedes it.

The representation does not establish whether the destination refers to ordinary memory, memory-mapped hardware, an unmapped region, or another address-space category. It also does not establish whether a faulting or unaligned store can partially affect memory.
