# F-03c5c9b9557d

## Purpose

F-03c5c9b9557d conditionally detaches a node from a linked, color-marked binary structure, adjusts structural links and color markers, prepends the detached node to a recycled-node list, decrements a stored count, and writes a 32-bit result to caller-provided storage.

The structure suggests red-black-tree erasure with node recycling. This is **inferred intent**, not an unconditional guarantee of ordering, balance, or ownership. Dependency implementations and complete calling contracts are unavailable.

An initial dependency can bypass removal. On that branch, the function writes a freshly read container header reference to output without directly performing structural repair, recycling, or count adjustment.

All behavior below is established by static inspection unless explicitly identified as inferred or **documented_only**. No runtime tests have been performed.

## Interface

The function accepts three inputs and has no explicit return value.

| Input | Representation | Established role |
|---|---|---|
| Output storage | Address of a writable 32-bit word | Receives the final result. |
| Container | 32-bit address-valued input | Locates the header reference, recycled-list head, and count. |
| Input storage | Address of a readable 32-bit word | Supplies an initial position value and, after a dependency call, the target node address. |

The visible address and link representation is 32 bits. Color markers are accessed as individual bytes. This is not a native-pointer-width-independent interface.

|---|---:|---|---|

The function does not directly write node bytes +1 through +3 or payload beyond this prefix. Dependencies may do so.

### Preconditions and aliasing

Every address actually dereferenced must provide accessible storage of the required width and mutability. Traversals require links that eventually terminate. The function does not validate membership, ordering, count positivity, color range, parent-child consistency, or acyclicity.

Null children select supported structural cases; they do not inherently become null repair positions:

- Leaf removal selects the target’s parent.
- Sole-child removal selects the already nonnull child.
- Two-child removal selects the successor’s former right child, or the successor itself when that child is null.

A null leaf parent is malformed input, not a supported null-child replacement. Structural removal ordinarily dereferences that parent before reaching repair.

No non-aliasing guarantee is established. Overlap among output, input, container, header, and node storage can affect later reads or overwrite earlier writes. Dependencies also receive addresses of private temporaries; those addresses must not be treated as unescaped or immutable afterward.

## Behavior

### Entry decision and result storage

The function reads input storage into a private 32-bit result temporary, then reads the container’s header reference into a second 32-bit temporary. F-1c076abb7b7f receives the addresses of both temporaries.

If its integer result is nonzero, the function reloads the container’s header reference, assigns it to the result temporary, and writes that value to output. No subsequent dependency call or direct structural mutation occurs on this branch. Effects already caused by F-1c076abb7b7f remain possible.

If its result is zero, F-e4e03c421405 receives the result temporary’s address. After that call, the function rereads input storage and uses this new read as the target address.

The initial input value, the target address, and the eventual output value therefore need not agree. The output is the result temporary’s value **when the final assignment executes**, not necessarily its value immediately after F-e4e03c421405 returns. Earlier dependencies may retain its address, and later repair dependencies cannot be assumed to preserve it through retained aliases.

“Advance a position before erasing its former node” is a plausible interpretation, but the dependency behavior needed to establish that interpretation is unavailable.

### Structural selection

The target’s left-child reference is examined first.

- If it is null, the right-child reference determines leaf versus sole-right-child removal.
- If it is nonnull and the right child is null, the left child is the sole replacement.
- If both children are nonnull, the function finds a successor by following left links from the target’s right child until reaching a node with no left child.

In the two-child case, the successor moves into the target’s structural position. The original target remains the node selected for recycling. No payload exchange or payload copy is directly visible.

### Leaf removal

The target’s parent becomes the repair position.

When that parent equals the container’s currently read header reference, the function writes the header’s maximum reference first, minimum reference second, and root reference third. The first two receive the parent/header value; the root receives zero.

Otherwise, the function compares the parent’s left reference with the target. A match selects the left field for clearing; a nonmatch selects the right field without independently checking its previous value.

The selected parent link is cleared using four separate zero-byte writes in increasing byte-offset order. These are not represented as one 32-bit store.

The same left-versus-right decision selects the header’s cached minimum or maximum field. If that selected field equals the target, it is replaced with the parent. The other cached extremum is not examined by this leaf branch.

### Sole-child replacement

The nonnull child’s parent field is updated before the target’s incoming link is replaced.

The incoming link is selected by checking the current header’s root reference first. If that is not the target, the target’s parent is read and its left reference is checked. A left mismatch selects the parent’s right reference without further validation.

Cached extrema are considered afterward, minimum before maximum:

- If the minimum equals the target, it becomes the target’s parent when the target has no right child; otherwise it becomes the leftmost node reachable from the replacement.
- If the maximum equals the target, it becomes the target’s parent when the target has no left child; otherwise it becomes the rightmost node reachable from the replacement.

Each traversal ends at a null child reference. Cycles can prevent completion.

The surviving child is the repair position. The original target is recycled.

These descriptions assume ordinary consistent storage. Because fields are reread after earlier writes, overlapping storage can change later branch decisions.

### Two-child replacement

The successor is the leftmost node of the target’s right subtree. Its former right child is retained as a candidate repair position.

The target’s left child first receives the successor as its parent. The successor’s left field then receives the target’s left reference.

If the successor is the immediate right child, its right field is left unchanged; a nonnull right child receives the successor as parent.

For a deeper successor:

- A nonnull former right child receives the successor’s former parent.
- That former parent’s left field receives the former right child, including zero.
- The successor’s right field receives the target’s right reference.
- That right child receives the successor as parent.

The target’s incoming root or parent link is then redirected to the successor, using the same root-first, then parent-left, otherwise parent-right selection. The successor’s parent receives the target’s parent reference.

The successor’s original color byte is saved. Its color is replaced by the target’s color, and the target receives the saved successor color. Thus, the detached target carries the successor’s original marker into the repair decision.

If the successor’s former right child was null, the successor itself becomes the repair position. Otherwise, that child remains the repair position.

This branch contains no direct cached-minimum or cached-maximum update.

### Repair entry and termination

The function reloads the container’s header reference. Repair is entered only if the repair position differs from that header and the detached target’s color byte is nonzero. The detached color is not read for this decision when the position equals the header.

Once entered, each iteration first checks whether the position equals the current header’s root. Only if it does not does the function test whether its color is exactly 1. Either equality with the root or a color other than 1 exits the loop and writes 1 to the repair position.

Consequently:

- Detached color 0 skips repair entirely.
- Any nonzero detached color permits entry when the position differs from the header.
- Continued iteration requires position color exactly 1.
- Skipping repair does not imply a final color write.

Interpreting 0 as red and 1 as black is consistent with the apparent algorithm, but remains inferred terminology.

### Repair cases and dependency mapping

Each iteration reads the position’s parent. If the parent’s left reference equals the position, the sibling is the parent’s right child. Otherwise, the sibling is the parent’s left child; right-child membership is not independently verified.

“Near child” means the sibling child facing the repair position. “Far child” means the other child.

| Repair orientation | Sibling-color-0 call | Near-child adjustment call | Final outer call |
|---|---|---|---|
| Position is parent’s left child | F-bead5e7925d5, visibly supplied container and parent | F-bc14848ed03d, visibly supplied only container | F-bead5e7925d5, visibly supplied container and parent |
| Other orientation | F-bc14848ed03d, visibly supplied container and parent | F-bead5e7925d5, visibly supplied only container | F-bc14848ed03d, visibly supplied container and parent |

The calls suggest opposite rotation directions. Their full contracts are unresolved; no missing argument is supplied by this specification.

The observable repair cases are:

- **Absent sibling:** write 0 to the current position, move the position to its parent, and repeat.
- **Sibling color 0:** write 1 to the sibling, then 0 to the parent, and make the orientation-specific call above. Reload the position’s parent and sibling. If the reloaded sibling is null, follow the absent-sibling ascent, including writing 0 to the position.
- **Both sibling children absent or exactly color 1:** write 0 to the sibling, move the position to its parent, and repeat.
- **Far child absent or exactly color 1, after the preceding case did not apply:** write 1 to the near child if its link is nonnull, write 0 to the sibling, and make the near-child adjustment call. Reload the sibling from the position’s current parent.
- **Null sibling after that near-child call:** exit repair directly by writing 1 to the current position. This branch exists in both orientations. It skips the remaining sibling, parent, and far-child recoloring and skips the final outer call.
- **Final outer repair with a nonnull sibling:** copy the parent’s color to the sibling, write 1 to the parent, write 1 to the far child if present, and make the final outer call. Then write 1 to the current repair position.

The final outer call does not cause another loop iteration. The function does not verify the resulting structure.

### Recycling, count, and final output

After structural work and any repair, the function reads the recycled-list head and writes that value into the detached target’s +12 field. It then writes the target address as the new list head.

Next, it reads the 32-bit count and stores the result of decrementing it by one. There is no positivity check, saturation, or explicit underflow report.

Finally, it reads the result temporary for the output assignment. The temporary’s value at this point may reflect effects of later dependencies through retained aliases.

The count operation is represented as signed 32-bit arithmetic. Mathematical unbounded subtraction must not be assumed; exact behavior at signed-overflow boundaries is **documented_only**.

## Side effects

Direct writes can affect header root and extremum fields, node parent and child fields, color bytes, the detached target’s recycled-list link, the container’s list head and count, and caller output storage.

The major order is structural mutation, optional repair, recycled-list insertion, count decrement, and final output assignment. Header and node fields are reloaded at multiple points; the function does not operate from a complete immutable snapshot.

No direct allocation, deallocation, payload destruction, logging, or explicit error-status return is visible. Recycling establishes a list insertion, not a complete ownership or lifetime policy. The target’s remaining prefix fields are not generally cleared.

There is no visible rollback. Invalid storage, malformed links, nonterminating traversal, or dependency failure can expose partially modified state. No explicit error result describes such a state.

The function itself performs no structural writes on the bypass branch, but that does not constrain effects of the initial dependency.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, they assume accessible, consistent, non-overlapping storage and dependencies that do not introduce unrelated changes.

1. **Bypass after header mutation.** If F-1c076abb7b7f returns nonzero after changing the container’s header reference, output receives the reloaded reference. This function performs no direct recycling or count decrement.

2. **Single-node removal.** For a childless target whose parent is the header and whose color is 0, maximum and minimum become the header before root becomes zero. Repair is skipped. The target is prepended to the recycled list, and count 1 becomes 0.

3. **Left leaf cached as minimum.** If a non-root target is its parent’s left child and the cached minimum equals the target, the parent’s left field is cleared through four increasing-offset byte writes, then the cached minimum becomes the parent. Subsequent repair depends on colors and ancestry.

4. **Sole right child.** The child receives the target’s parent before the incoming root or parent link is redirected. If the target was cached minimum, the minimum becomes the replacement subtree’s leftmost node. The nonnull child is the repair position.

5. **Deep successor with a right child.** That child replaces the successor at its former position. The successor occupies the target’s position, the color bytes are exchanged, and the original target is recycled.

6. **Successor without a right child.** For a two-child target, the successor itself becomes the repair position when its former right child is null. This is not a null repair position. Sole-child and leaf branches likewise select a nonnull child or the target’s parent, respectively, under valid structural assumptions.

7. **Null sibling after near-child adjustment.** In either orientation, if the near-child dependency returns and the reloaded sibling is null, the function writes 1 to the current position and leaves repair. It does not perform the final sibling/parent/far-child recoloring or outer dependency call.

8. **Later mutation of the result temporary.** If an earlier dependency retains the temporary’s address and a later repair dependency changes its value through that alias, output receives the changed value present at final assignment—not the earlier post-advancement value.

9. **Output aliases count.** If output storage is the count field, the decrement occurs first, but final output overwrites it with the result temporary’s then-current value.
