# F-86ba2df20f39

## Purpose

F-86ba2df20f39 selects an entry from an eight-entry table using a 32-bit value obtained from an external dependency. It returns an integer representation of the selected entry’s address.

The established selection policy is:

1. Return the first entry whose leading 32-bit field equals the obtained value.
2. If no entry matches, initialize the first entry whose leading field is zero.
3. If neither search succeeds, initialize entry zero.

Initialization consists of a dependency call requesting an operation over 56 bytes, followed by two explicit 32-bit stores: the obtained value at entry offset 0 and the entry’s one-based position at offset 12. The dependency receives arguments consistent with zero-filling, but its actual behavior is not established here.

The apparent intent is a small keyed record table with zero marking availability. This interpretation does not establish that zero is an invalid lookup value. A zero-valued lookup can return a zero-leading-field entry without initializing it.

## Behavior

### Value acquisition and retained base

The first operation is a single call to the value-producing dependency. Its result is retained as a 32-bit value and is used for every matching comparison and for the leading-field store if initialization occurs.

After that call returns, the function retains the global table-base value. This retained base is used later for the leading-field store on an initialization path.

The searches, matching return expression, and initialization-address calculation use separate expressions referring to the global base. They are not expressed solely in terms of the earlier retained base. Consequently, the retained base and a later selected address must not be assumed to designate the same table if the global base changes.

This distinction establishes data dependencies in the supplied representation, not a precise count of machine-level global loads or a synchronization protocol.

### Matching search

The first search proceeds in ascending entry order, from index zero through index seven.

For each entry reached, the function reads its leading 32-bit field and compares it with the retained lookup value. On the first equality:

- No subsequent entry is examined by this search.
- The availability search does not run.
- F-ae3cfca28bf1 is not invoked.
- Neither explicit initialization store occurs.
- The function returns an address calculated for the matching index using the global-base expression on that return path.

The position field and remaining entry contents are not checked. An existing match is returned even if its position field is inconsistent with its location.

If the global base is stable, the lowest-index matching entry wins. A zero-leading-field entry does not take precedence over a later nonzero match: availability is considered only after the matching search fails completely.

If the global base can change during execution, the address returned for a matching index is not independently guaranteed to be the address whose leading field supplied the matching read.

### Availability search and fallback

Only after all eight matching comparisons fail does the function begin a second search, again at index zero.

This search reads leading 32-bit fields in ascending order and selects the first field observed to equal zero. It performs new reads rather than reusing the first search’s observations.

If no zero is found in all eight entries, index zero is selected unconditionally. No other field influences replacement. There is no age comparison, usage comparison, position check, or rotating replacement state.

Because the two searches are separate, table changes between reads can affect the result. For example, a field that was nonzero during the matching search can be observed as zero during the availability search. No retry or consistency check reconciles those observations.

### Initialization sequence

For the selected index, the function calculates an address using the then-referenced global base and the 56-byte stride. It retains this selected address across the dependency call.

The observable operation order is:

1. Invoke F-ae3cfca28bf1 with the selected address, zero, and a count of 56.
2. After that dependency returns normally, store the retained lookup value as a 32-bit integer at the selected index relative to the earlier retained base.
3. Store the selected index plus one as a 32-bit integer at offset 12 from the retained selected address.
4. Return the retained selected address.

The two stores therefore need not address the same entry if the early retained base differs from the base used to calculate the selected address.

A change to the global base inside F-ae3cfca28bf1 does not, by itself, redirect either subsequent store. Their address calculations depend on values already retained before the call. This does not guarantee that the dependency preserves the memory, mapping, lifetime, or writable status of those addresses.

The dependency’s return value is unused. Its arguments suggest a zero-fill operation, but the function alone does not establish that it writes any particular bytes, confines its writes to 56 bytes, or preserves unrelated state.

### Zero-valued lookup

Zero is accepted by the comparison logic without a special branch.

With stable table contents, a zero-valued lookup returns the first zero-leading-field entry during the matching search. That path does not initialize the entry or repair its position field.

If a stable table contains no zero-leading-field entry and the lookup value is zero, both searches fail. Entry zero is selected for initialization, and the explicit leading-field store writes zero. Under conventional zero-fill behavior, the resulting entry still has the value treated as available by the availability search.

Thus, the source does not establish a distinction between an unused entry and an entry whose key is zero.

### Widths and bounds

The lookup field, position field, retained lookup value, and address-valued return are represented as 32-bit integers.

The selected index is bounded to zero through seven. Its stride offset ranges from 0 to 392 bytes. The position value ranges from 1 to 8. These bounded calculations do not overflow a signed 32-bit integer.

Adding an offset to a base address is a separate issue. The supplied representation does not establish whether overflowing address-like integer arithmetic wraps, faults, or is outside the valid operating domain.

For a stable contiguous table:

- The last leading-field read starts at base offset 392 and occupies four bytes.
- The last position-field write starts at base offset 404 and occupies four bytes.
- A 56-byte operation on the last entry covers offsets 392 through 447 inclusive.

Endianness and alignment requirements are not established. No particular byte order should be inferred for the two integer stores.

## Side effects

On a matching path, the function performs table reads but no explicit table writes and no call to F-ae3cfca28bf1. This is not a globally read-only guarantee: the initial value-producing dependency may have unknown side effects.

On an initialization path:

- F-ae3cfca28bf1 is invoked once.
- Two explicit 32-bit stores follow its normal return, in leading-field then position-field order.
- The requested operation targets the selected 56-byte extent.
- If the table is full and has no matching entry, index zero is the replacement target.

Destruction of the selected entry’s previous contents depends on the dependency’s behavior. The caller of this function cannot infer a complete zeroed record merely from the call arguments.

The function contains no explicit allocation or release operation. The returned address is derived from global state. Ownership, validity duration, and permission to release that address are undocumented. Neither dependency is established to preserve or transfer ownership.

No lock, atomic read-modify-write operation, or other synchronization protocol is visible. Concurrent or reentrant mutation has no established safety guarantee.

There is no explicit error result, null check, recovery branch, or retry. The behavior of invalid accesses, arithmetic faults, dependency failures, and nonlocal exits is not established here. If the initialization dependency does not return normally, the subsequent explicit stores and ordinary return are not reached through the shown control flow.
