# F-890aeb946e5c

## Purpose

F-890aeb946e5c updates three fields in a destination object from a source record. If the copied status byte is zero and a separately stored destination key is nonzero, it obtains a 32-bit unsigned search bound and searches a destination-associated sequence for that key. On the first match, it replaces the copied 32-bit field with the matching entry’s zero-based index and sets the status byte to one.

The field names used here—“key,” “status,” “sequence,” and “search bound”—describe their observed roles, not established application-level meanings. In particular, the copied 32-bit field is not necessarily an index when no match is found.

This contract distinguishes explicit behavior in the supplied static representation from effects that depend on opaque dependencies. No runtime tests have been performed.

## Interface

### Inputs and result

The function receives two address-like arguments:

- **Destination address:** identifies the object to update and supplies the sequence reference and search key.
- **Source address:** identifies the record supplying the three copied fields.

The supplied representation uses 32-bit address and integer quantities. Object bounds, alignment requirements, pointer validity rules, and the exact calling convention are not established.

There is no explicit return value. Observable results consist of memory writes, dependency calls, and any effects those dependencies produce.

### Relevant destination layout

Offsets are in bytes from the destination address.

| Offset | Width | Observed role |
|---|---:|---|
| +0x18 | 4 bytes when read during search | Sequence-base address storage; this location’s address is also passed to F-774d5a2aa94a |
| +0x24 | 1 byte | Receives the source byte at +0x0c |
| +0x28 | 4 bytes | Initially receives the source word at +0x10; receives the matching index if the search succeeds |
| +0x2c | 1 byte | Receives the source byte at +0x14; a copied nonzero value skips the search; a successful search writes one |

Passing the address at destination +0x18 to a dependency does not establish that the dependency accesses only four bytes or that this location is an independently owned object.

### Relevant source layout

| Offset | Width | Observed use |
|---|---:|---|
| +0x0c | 1 byte | Copied to destination +0x24 |
| +0x10 | 4 bytes | Copied to destination +0x28 |
| +0x14 | 1 byte | Copied to destination +0x2c and used to decide whether to continue |

The four-byte copy is a transfer of the stored word. The function does not visibly transform its numeric value.

### Sequence layout

If the search executes, each entry occupies a stride of 0x0c bytes. Only the first four-byte word of each examined entry is explicitly read and compared with the saved key. No explicit reads of the remaining eight bytes are shown.

The sequence’s allocation size, ownership, element meaning, and relationship to the returned search bound are unknown.

## Behavior

### 1. Initial dependency call

Before any explicit source-field read or destination-field write, the function calls **F-774d5a2aa94a**, passing the address at destination +0x18.

The supplied representation does not use a return value from this call. Its effects are otherwise unknown. All subsequent field reads observe memory after this call returns; the function does not preserve source contents, destination contents, or a sequence-base value across it.

If the dependency does not return normally, the remaining behavior is not established by this function.

### 2. Ordered field copies

After the initial call returns, the function performs these accesses in order:

1. Reads one byte from source +0x0c, then writes it to destination +0x24.
2. Reads four bytes from source +0x10, then writes them to destination +0x28.
3. Reads one byte from source +0x14, retains that byte for the branch decision, then writes it to destination +0x2c.

This is not a snapshot copy of the source record. Each source field is read immediately before its corresponding write, after the earlier copies have completed.

Consequently, if the source and destination storage overlap, an earlier write can affect a later source read. No non-overlap check or temporary copy of the complete source record is visible.

### 3. Status gate

If the byte just read from source +0x14 is nonzero, the function returns immediately after writing it to destination +0x2c.

Any nonzero byte satisfies this gate. The function does not require the value to be one and does not normalize a nonzero copied status.

On this path, the function does not explicitly:

- Read the destination key at +0x30.
- Call F-32a0cd51a77a.
- Read the sequence-base address or any sequence entry.

These statements concern this function’s explicit accesses; they do not restrict what the initial dependency may have accessed.

### 4. Key gate

If the copied status byte is zero, the function reads the four-byte key at destination +0x30 and retains that value.

If the key is zero, it returns without calling F-32a0cd51a77a or explicitly accessing the sequence.

The key read occurs after all three copies. If overlapping storage makes one of those writes affect the key, the function uses the resulting key value, not an earlier value.

For a nonzero key, the retained value is used throughout the search. Later changes to destination +0x30 do not cause the key to be reloaded.

### 5. Bound acquisition

With a zero copied status and a nonzero saved key, the function calls **F-32a0cd51a77a** with no explicit arguments.

Its return is interpreted as a 32-bit unsigned search bound and retained for the entire search. The search index begins at zero.

This dependency runs after the copied fields have been written and after the key has been captured. Its side effects are unknown. In particular:

- It may affect destination fields that were just copied.
- It may change destination +0x30, but comparisons still use the saved key.
- It may change destination +0x18, whose contents are read during the search.
- It is not established that it preserves globals or memory associated with either input.

The returned bound is not refreshed between iterations.

### 6. Bounded search

Before each candidate entry access, the function compares the current index with the saved bound using unsigned 32-bit ordering. If the index is greater than or equal to the bound, the function returns without a successful-search write.

Otherwise, it:

- Reads the sequence-base address from destination +0x18.
- Reads the four-byte word at that base plus the current index multiplied by 0x0c.
- Compares that word with the saved key.

If the words differ, it increments the index by one and repeats the bound check.

If they match, the search stops immediately. The function writes the current index as a four-byte value to destination +0x28, then writes the byte value one to destination +0x2c, and returns.

The lowest examined index wins. Later duplicate matches are not read.

The sequence-base value is read anew for each examined entry. It is not visibly captured once before the loop. The supplied representation does not establish a concurrency or synchronization model; this repeated read alone is not a thread-safety guarantee.

### 7. Integer widths and address arithmetic

The search bound and index are 32-bit unsigned quantities. Equality of the candidate word and saved key compares their 32-bit representations; signed ordering is not involved.

For a bound of zero, the search performs no sequence-base or entry read.

For any 32-bit unsigned bound, an ordinary progressing search does not need the index to wrap: after examining the last permitted index, the next bound check terminates the loop. This remains true for the maximum bound, 0xffffffff; the largest permitted candidate index is then 0xfffffffe.

Entry-offset arithmetic is a separate concern. The stride multiplication uses a 32-bit unsigned index. Its mathematical result first exceeds 32 bits at index 0x15555556. No overflow check or wider checked offset calculation is visible. Large bounds therefore do not establish that successive accesses reach distinct, valid entries.

The representation does not settle how an invalid, overflowing, or out-of-allocation address behaves in the actual execution environment. This contract does not promise safe traversal merely because the unsigned bound check succeeds.

## Side effects

### Explicit writes

The function explicitly writes:

- One byte at destination +0x24.
- Four bytes at destination +0x28.
- One byte at destination +0x2c.
- On a successful search, another four-byte value at destination +0x28, followed by another byte at destination +0x2c.

No other explicit writes are shown. Dependencies may perform additional writes.

On search failure, this function performs no post-search writes. That does **not** guarantee the copied fields retain their original copied values: F-32a0cd51a77a may have changed them.

The successful-search writes occur after the matching entry read, in index-then-status order. No atomic grouping or rollback is shown.

### Ownership and lifetime

No explicit allocation, release, ownership transfer, or lifetime extension is visible.

The function passes destination +0x18 to F-774d5a2aa94a. Without that dependency’s contract, it is unknown whether the call retains the address, replaces referenced storage, or releases memory. Callers must not infer ownership preservation from the absence of an explicit release in this function.

### Preconditions and errors

Normal completion requires each executed access to address valid storage for its width and each invoked dependency to return normally. Required storage is path-dependent:

- The initial dependency is always called.
- The three source fields are always read after that call returns.
- The key is read only when the copied status is zero.
- The sequence-base field and candidate words are read only when the search bound permits an iteration.

There is no explicit validation of null addresses, allocation sizes, alignment, bound-to-storage consistency, or dependency success. No structured error result is returned. Fault behavior and dependency-specific errors are documented_only unknowns.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence, not executed tests. Except where a scenario states otherwise, assume valid, non-overlapping storage, normally returning dependencies, no dependency changes to the illustrated fields, stable sequence contents, and representable valid entry addresses.

### Nonzero copied status

If the source supplies status 0x80, the function copies all three source fields, leaves destination +0x2c equal to 0x80, and returns without explicitly reading the key or calling F-32a0cd51a77a.

It must not replace 0x80 with one merely because it is nonzero.

### Zero key

If the copied status is zero and the destination key is zero, all three copies occur, the key is read, and the function returns without obtaining a search bound.

### Empty search

If the copied status is zero, the key is nonzero, and F-32a0cd51a77a returns zero, the function returns without reading the sequence-base field or any candidate entry.

### First matching entry

If the bound is four and entries at indices zero and two both match the saved key, the function reads only entry zero, writes zero to destination +0x28, then writes one to destination +0x2c.

### Match at a later index

If the bound is three and only entry two matches, entries zero, one, and two are examined in that order. The final explicit writes are the four-byte value two at +0x28 and the byte one at +0x2c.

### No match

If the bound is two and neither entry matches, only entries zero and one are examined. No successful-search writes occur, and entry two is not read.

Under the stated dependency assumptions, the copied word and zero status remain unchanged. Without those assumptions, their final values are not guaranteed.

### Key changed by the bound dependency

If the saved key is 7 and F-32a0cd51a77a changes destination +0x30 to 9, candidate comparisons still use 7. This function does not restore the key field.

### Base changed by the bound dependency

If F-32a0cd51a77a changes destination +0x18 to another valid sequence base, the first candidate read uses that updated base. No pre-call sequence-base value has been saved by this function.
