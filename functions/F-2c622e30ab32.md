# F-2c622e30ab32

## Purpose

F-2c622e30ab32 conditionally derives two 32-bit results from a caller-supplied state object. It returns one result directly and stores the other through a caller-supplied output address.

A byte in the state object gates all processing. When that byte is not exactly one, the function returns zero without writing the output. On the active path, a separate zero-valued field triggers a dependency call followed by a one-byte state update. The two results then combine unsigned 16-bit values, a 32-bit base value, and a conditionally selected 32-bit adjustment.

This describes the observable behavior supported by the supplied static evidence. The application meaning of these fields is unknown. In particular, interpreting the results as positions, bounds, counts, or dimensions would be inferred intent rather than an established contract.

## Behavior

### 1. Activation gate

The function first reads the byte at state offset `0x43`.

If its value is anything other than exactly one:

- The return value is zero.
- There is no output write.
- No dependency is called.
- No other state field or nested-object byte is read.
- There is no direct state write.

The gate is an exact-value test, not a general nonzero test. A value of two takes the inactive path.

A zero return is not sufficient to identify an inactive invocation: active-path arithmetic can also produce zero.

### 2. Capture the nested-object address

On the active path, the function reads the 32-bit value at state offset `0x18` and retains it as the nested-object address for the remainder of the invocation.

This capture precedes the optional dependency call. If the dependency changes the address stored at `0x18`, the later nested-byte read still uses the previously captured address.

There is no check for a zero or invalid nested-object address.

### 3. Conditional dependency call and marker write

The function reads the 16-bit field at state offset `0x3E`.

If that field is nonzero, it skips both the dependency call and the marker write.

If that field is zero:

1. It reads the 32-bit field at state offset `0x1C`.
2. It calls F-4aa9d52845df with two arguments: the captured nested-object address and the value read from `0x1C`.
3. After the dependency returns normally, it writes the byte value one at state offset `0x42`.

The dependency's return value, if any, does not influence the visible computation.

The marker's previous value is not tested. Even if the marker is already one, a zero field at `0x3E` still causes the call. The marker therefore cannot be treated as an independently enforced “already processed” guard.

The function does not directly change `0x3E`. Repeated active invocations can consequently repeat the call while that field remains zero. Whether the dependency itself changes the field is unknown.

### 4. Read the result inputs and select the adjustment

After the optional call and marker write, the function performs these reads in the order shown by the supplied evidence:

1. The unsigned 16-bit return component at `0x38`.
2. The 32-bit return base at `0x20`.
3. The byte at offset `+3` of the captured nested object.

The nested byte selects the adjustment:

- If it is zero, read the 32-bit adjustment from state offset `0x28`.
- If it is nonzero, use an adjustment of zero without reading `0x28`.

The function then reads the unsigned 16-bit output component at `0x3A`.

All these reads occur after the dependency, if called. Dependency changes to the result fields or to the captured nested object's byte can therefore affect the calculation. The exception is the nested-object address itself: that address was already captured.

The function does not recheck the activation gate or the dependency-call condition after the call. Changes to those fields during the call do not restart or cancel the current active path.

### 5. Store and return the results

Let:

- **R** be the zero-extended 16-bit value read from `0x38`.
- **B** be the 32-bit value read from `0x20`.
- **A** be the selected 32-bit adjustment, or zero.
- **O** be the zero-extended 16-bit value read from `0x3A`.

The output receives the 32-bit result of **O − A**.

The direct return carries the 32-bit result of **R + B + A**.

The supplied arithmetic includes unsigned 32-bit conversion of the 16-bit components. The resulting additions and subtraction are therefore modulo \(2^{32}\), rather than saturating arithmetic. A negative interpretation of a 32-bit adjustment does not prevent this bit-pattern arithmetic.

For example, subtracting an adjustment of one from an output component of zero produces `0xFFFFFFFF`, not a reported error. As a signed 32-bit value, that bit pattern is conventionally interpreted as −1.

The output write occurs before the function returns. The inputs needed for the returned result have already been captured before that write.

## Side effects

### Direct writes

On an active invocation, the function directly performs:

- One byte write of one to state offset `0x42`, only if the field at `0x3E` was zero and the dependency returned normally.
- One 32-bit write through the output address, if execution reaches the final calculation.

On an inactive invocation, it performs neither write.

### Aliasing and ordering

The supplied evidence contains no non-aliasing restriction between the state object, nested object, and output destination.

The ordering matters when these regions overlap:

- The marker write precedes the result-field reads and the nested-byte read. If it aliases one of those later inputs, the later read observes the resulting memory state.
- The output write follows all direct input reads used for the results.
- If the output destination overlaps a state field, the output write may alter that field after it has been read.
- If the output destination overlaps the marker, the final contents need not retain the marker value one.
- The final output write does not cause the function to reread fields for its return calculation.

Exact effects of partially overlapping multi-byte fields depend on byte order and access semantics, which are not independently established here.

### Dependency effects and failure behavior

F-4aa9d52845df runs before the marker write and before the result inputs are read. Its effects on shared state, globals, object lifetime, or external resources are unknown.

There is no visible recovery path for an invalid memory access or a dependency that fails to return normally. The function exposes no separate error result. In particular:

- If the dependency does not return, neither the subsequent marker write nor the output write is reached.
- If a later read fails, the dependency and marker write may already have occurred.
- If the output write fails, earlier effects are not rolled back by any visible mechanism.

No synchronization, locking, or atomicity guarantee is established. The ordered observations above describe one invocation absent interfering concurrent activity.

These are conditional static acceptance examples, not executed tests. Unless otherwise stated, they assume valid memory, no concurrent interference, and a normally returning dependency wherever called.

### Inactive gate

The nested-object address and output address need not be dereferenced on this path.

### Active calculation without a dependency call

### Dependency changes later inputs

Suppose the condition field is zero, and F-4aa9d52845df changes the return component from 100 to 200 before returning. If the later read observes 200, the calculation uses 200.

If the dependency also replaces the address stored at `0x18`, the later nested-byte read still uses the address captured before the call. This example requires that the old address remain valid.

### Marker already set

### Unsigned wraparound

Given a return component of 65,535, a return-base bit pattern of `0xFFFFFFFF`, and zero adjustment, the return bit pattern is 65,534.

Neither case triggers a visible arithmetic-error branch.

### Output aliases an input field
