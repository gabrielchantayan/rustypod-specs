# F-c96d0b583a6b

## Purpose

F-c96d0b583a6b searches two ordered collections associated with a supplied owner and, when it finds an accepted candidate, invokes the collection-specific action for that candidate’s index.

The primary collection has strict precedence. The secondary collection is consulted only if the primary search finishes without accepting a candidate. At most one collection-specific action is invoked by this routine.

The apparent intent is to locate an item corresponding to a supplied target, using a 64-bit identifying value and, in the zero-value case, two additional 32-bit comparisons. This interpretation is inferred intent. The established behavior is the ordered sequence of calls and comparisons described below; the meanings of the values and the effects of the final actions are not established.

## Interface

### Inputs

The routine accepts two object addresses:

- **Owner:** supplies two collection counts, two indexed candidate-retrieval operations, and a stored value passed to the selected action.
- **Target:** supplies comparison values through a mixture of indirect dispatch and direct dependency calls.

The supplied representation uses 32-bit integers and a 32-bit object-address model. Each object is treated as beginning with a dispatch-table address. Indirect operations are identified here by their byte offsets within that table, not by an assumed class or method name.

The owner interface used by this routine is:

| Dispatch-table byte offset | Observed role |
|---|---|
| `0x1b4` | Obtain the primary collection count |
| `0x288` | Retrieve a primary candidate for an index |
| `0x1c4` | Obtain the secondary collection count |
| `0x28c` | Retrieve a secondary candidate for an index |

Each count is interpreted as an unsigned 32-bit value. Each retrieval receives a destination address, the owner address, and an unsigned 32-bit index.

The target interface used by this routine is:

| Dispatch-table byte offset | Observed role |
|---|---|
| `0x10` | Produce a 64-bit comparison value |
| `0x54` | Produce a 32-bit comparison value |

The owner also contains a 32-bit field at byte offset `0x40`. Its value is supplied as the first argument to whichever collection-specific action is selected. Its type, ownership, and validity requirements are not established.

### Local storage

The routine provides two distinct local storage regions of 20 bytes each:

- A reusable **candidate destination**, passed to indexed retrieval operations.
- A reusable **comparison object**, initialized once and then updated for every retrieved candidate.

The 20-byte sizes establish the storage supplied by the caller, not the full logical layout or ownership model of the objects stored there. No member layout within either region is established.

### Output and preconditions

There is no explicit return value and no explicit result-status output. A normal return alone does not distinguish a match from a complete miss.

For defined operation, the supplied objects, dispatch tables, invoked entries, and any dependency-required state must be valid for the accesses performed. There are no explicit null checks, range checks against current collection state, or validation of retrieved candidate data.

The routine does not establish recovery behavior for invalid addresses, dependency failures, exceptions, or other nonlocal exits.

## Behavior

### 1. Establish the primary search bound

The routine first invokes the owner operation at dispatch-table offset `0x1b4`. It saves the returned value as an unsigned 32-bit primary count.

Only after obtaining that count does it initialize the comparison object by calling F-1c06d0a5910b with its address and two zero-valued arguments.

This order matters. The initialization dependency may have effects, but those effects do not cause the primary count to be fetched again.

Initialization occurs even when the primary count is zero. It occurs exactly once along a normally returning execution, including executions that subsequently search the secondary collection.

### 2. Visit primary candidates in ascending index order

The primary search begins at index zero and visits increasing unsigned 32-bit indices strictly below the saved primary count.

For each visited index, the routine:

1. Invokes the owner retrieval operation at offset `0x288`, supplying the candidate destination, owner, and current index.
2. Calls F-047d22db5c73 with the comparison-object address followed by the candidate-destination address.
3. Applies the comparison procedure below.

The comparison object is reused across iterations. It is not reinitialized before each update. The candidate destination is also reused, and this routine does not explicitly initialize it before retrieval.

Whether retrieval fully constructs its destination, and whether F-047d22db5c73 performs assignment, conversion, copying, or some other transformation, are dependency-level unknowns. The established requirement is the order and argument relationship of these calls.

### 3. Compare a candidate with the target

The same comparison procedure is used for both collections.

#### Initial 64-bit comparison

After updating the comparison object, the routine:

1. Invokes the target operation at offset `0x10`, obtaining a 64-bit value.
2. Calls F-d3b5bb23607f on the comparison object, obtaining another 64-bit value.
3. Compares all 64 bits for equality.

If these values differ, the candidate is rejected immediately. No additional comparison calls are made for that candidate.

The target operation occurs first. The candidate-side operation may therefore observe effects caused by the target operation; purity is not established.

#### Repeated candidate-side 64-bit read

If the initial 64-bit values are equal, the routine calls F-d3b5bb23607f on the comparison object again.

If this second result is nonzero, the candidate is accepted immediately.

The second result is not compared again with the target’s earlier result, and it is not checked for equality with the first candidate-side result. Consequently, the established rule is not simply “equal nonzero identifiers.” That phrase describes the likely stable-value case but does not cover every permitted dependency behavior.

If the second result is zero, the routine proceeds to the first 32-bit comparison.

#### First 32-bit comparison

The routine calls:

1. F-45ba275d4fcc on the comparison object.
2. F-45ba275d4fcc on the target.

It compares the resulting 32-bit values for equality.

If they differ, the candidate is rejected. The final 32-bit comparison is skipped.

#### Final 32-bit comparison

If the first 32-bit values are equal, the routine calls:

1. F-3f2e817b9ef7 on the comparison object.
2. The target operation at dispatch-table offset `0x54`.

The candidate is accepted if and only if these 32-bit results are equal.

The 32-bit comparisons test equality only. Their signed interpretation does not affect whether the bit patterns are equal. Likewise, the 64-bit comparisons use only equality and zero testing; they do not impose an ordering.

### 4. Act on a primary match

On the first accepted primary candidate, the routine stops searching.

It reads the owner’s field at byte offset `0x40` and calls F-cace740d16db with:

- The field value.
- The accepted candidate’s index.

The field is read for the action after candidate evaluation, rather than captured before the search. Effects of earlier calls may therefore affect the value passed to the action.

After this action returns normally, the routine returns. It does not fetch the secondary count or retrieve any secondary candidate.

The effect of F-cace740d16db is unknown. In particular, the available evidence does not establish deletion, selection, notification, or ownership transfer.

### 5. Search the secondary collection after a primary miss

If all primary candidates are rejected, or the saved primary count is zero, the routine invokes the owner operation at offset `0x1c4` and saves its unsigned 32-bit result as the secondary count.

This count is fetched only after the primary search has completed. Effects of the primary search may therefore influence the secondary count.

The secondary search:

- Starts again at index zero.
- Uses the owner retrieval operation at offset `0x28c`.
- Reuses the same candidate destination and comparison object.
- Uses exactly the comparison procedure described above.
- Does not reinitialize the comparison object when changing collections.

On the first accepted secondary candidate, the routine reads the owner field at byte offset `0x40` and calls F-fdd6282abc07 with that value and the secondary index.

After that action returns normally, the routine returns.

If no secondary candidate is accepted, the routine returns without invoking either collection-specific action.

### 6. Bounds and arithmetic

Each search uses a saved unsigned 32-bit count. It does not refresh that count between candidates.

For a count of zero, no candidate is retrieved. For a count of one, only index zero is visited. For the maximum unsigned 32-bit count, the last eligible index is `0xfffffffe`. Incrementing that index produces `0xffffffff`, which fails the strict less-than comparison against the count; this loop structure does not require an index wraparound.

A count with its high bit set remains a large unsigned bound, not a negative value. The routine imposes no smaller limit.

Changes to collection contents during dependency calls are not reconciled with the saved bound. Safety and meaning under such changes depend on the owner’s retrieval contract.

## Side effects

The observable effects attributable directly to this routine are:

- Indirect calls through the owner and target dispatch tables.
- Calls to the named dependencies.
- Exposure of two local 20-byte regions to dependencies that may write them.
- A conditional read of the owner field at byte offset `0x40`.
- Invocation of at most one collection-specific action.

The routine contains no explicit heap allocation, deallocation, reference-count adjustment, or cleanup call. This does not establish that its dependencies allocate nothing, release nothing, or preserve any global state.

Neither local region receives an explicit destruction call on normal exit. Whether initialization, update, retrieval, or action dependencies internally manage resources is unknown.

The routine does not explicitly write to owner or target fields. Both objects are nevertheless passed to callees, so preservation of their state cannot be assumed.

Dispatch operations are resolved when their respective calls are made. The routine does not establish a single immutable dispatch-table snapshot for the entire search.

For a normally completed candidate evaluation:

- Target offset `0x10` is invoked once.
- F-d3b5bb23607f is invoked once or twice.
- The two F-45ba275d4fcc calls occur only if the initial 64-bit comparison succeeds and the second candidate-side 64-bit result is zero.
- The final pair of 32-bit-producing calls occurs only if the first pair compares equal.

These conditional calls are part of the observable behavior even if their apparent purpose is only to obtain comparison values.

## Acceptance examples

These are conditional contract examples, not runtime test results. Each assumes valid inputs and normally returning dependencies.

1. **Both collections empty.**  
   The primary count is zero. The comparison object is initialized. The secondary count is then obtained and is also zero. Neither retrieval operation, neither target comparison operation, and neither action is invoked.

2. **First primary candidate accepted by stable nonzero values.**  
   The target’s 64-bit result is 17. Both candidate-side 64-bit results are 17. The candidate is accepted without either 32-bit comparison stage. F-cace740d16db receives the current owner field value and index zero. The secondary count is never requested.

3. **Equal zero values require both additional comparisons.**  
   The target’s 64-bit result and both candidate-side 64-bit results are zero. The F-45ba275d4fcc results are equal, and the final candidate and target 32-bit results are equal. The candidate is accepted. If either 32-bit comparison differs, it is rejected.

4. **Initial mismatch short-circuits.**  
   The target’s 64-bit result is 17 and the first candidate-side result is 18. The candidate is rejected after one call to F-d3b5bb23607f. There is no second candidate-side read and no 32-bit comparison.

5. **A changing second read can accept a candidate.**  
   The target and first candidate-side results are both zero, but the second candidate-side result is 9. The candidate is accepted immediately. The routine does not require that 9 equal the earlier target result.

6. **A changing second read can trigger fallback.**  
   The target and first candidate-side results are both 17, but the second candidate-side result is zero. The routine performs the 32-bit comparisons. Acceptance depends on those comparisons, despite the earlier nonzero equality.

7. **Primary precedence overrides secondary possibilities.**  
   Primary indices zero and one are rejected; primary index two is accepted. F-cace740d16db is invoked for index two. No secondary count or candidate is requested, even if a secondary candidate would also match.

8. **Secondary indices are independent.**  
   Every primary candidate is rejected. Secondary index zero is rejected and index one is accepted. F-fdd6282abc07 receives index one, not an index offset by the primary count.

9. **Action state is read late.**  
   A dependency changes the owner field at byte offset `0x40` before a candidate is accepted. The selected action receives the field value present when that field is subsequently read, not an entry-time snapshot.
