# F-aa408aa1a280

## Purpose

Upon finding the first matching record encountered, it writes a supplied 32-bit replacement value to that record’s field at byte offset 8. It then invokes a finalization dependency and returns without an explicit result.

If the traversal dependency reports zero before a match is encountered, the function performs no direct record update and proceeds to finalization.

“Sequence,” “record,” and “finalization” describe the visible roles of the supplied values and dependencies. The evidence does not establish a particular container type, record class, traversal order, allocation scheme, or resource-release policy.

### Candidate traversal

The function calls F-6e4651b532dc with the state-region address and the address of the candidate-address slot.

Its returned integer is tested against zero:

- **Zero:** traversal stops immediately, without a direct read of a candidate record field.
- **Nonzero:** the function reads the four-byte field at byte offset 4 from the candidate address and compares it with the target.

Every nonzero result follows the same candidate-processing path. There is no separate treatment for positive versus negative values. Consequently, if the dependency uses a negative return value to represent an error, this caller does not recognize that convention as a distinct error path.

For a nonmatching candidate, the function makes no direct record write. It requests another candidate using the same state region and candidate-address slot.

There is no visible iteration limit, independent end condition, or cycle detection. A dependency that indefinitely supplies nonmatching candidates can cause the function to continue indefinitely.

### Match handling

A candidate matches when its 32-bit field at byte offset 4 equals the target value.

The comparison is exact 32-bit equality. It is not a range comparison, mask comparison, string comparison, or comparison against the candidate address. For equal-width integer values, signedness does not change this equality decision.

On the first match encountered, the function writes the replacement value as a four-byte value at byte offset 8 of that candidate.

The old value at byte offset 8 is not directly read before replacement. No visible retain, release, destructor, validation, or conversion operation is performed on either the old value or the replacement.

Traversal stops after this write. The function does not request another candidate or update additional matches.

## Side effects

### Direct memory access

For each candidate accepted through a nonzero traversal result, the function directly reads four bytes at record byte offset 4.

For the first matching candidate only, it directly writes four bytes at record byte offset 8. If no candidate matches before traversal returns zero, no direct record write occurs.

The function does not visibly access other record offsets. This does not constrain accesses made by dependencies.

The record layout established by the caller is therefore only:

| Byte offset | Width | Direct use |
|---|---:|---|
| 4 | 4 bytes | Match-field read |
| 8 | 4 bytes | Replacement-field write on a match |

The contents of bytes 0–3 and the total record size are unknown.

### Observable order

The visible order is:

1. Initialization dependency call.
2. One or more traversal dependency calls.
3. After each nonzero traversal result, a match-field read.
4. After the first successful comparison, a replacement-field write.
5. Finalization dependency call.
6. Return, if finalization returns normally.

There is no traversal call between the successful comparison and the replacement write. There is no further traversal call after that write.

The replacement write occurs before finalization. It is not deferred until finalization succeeds, and no rollback is visible.

## Acceptance examples

These examples are conditional consequences of the visible control flow, not runtime test results.

### No candidate supplied

Suppose initialization returns normally and the first traversal call returns zero.

The function must make no direct candidate-record read or write. It must call finalization once and return if finalization returns normally. The candidate-address slot need not contain a usable address for this path, because this function does not consume it after the zero result.

### First candidate matches

Suppose the first traversal call returns nonzero with a valid candidate whose four-byte field at offset 4 equals the target.

The function must write the replacement to offset 8 of that candidate, make no second traversal call, and invoke finalization afterward. This remains true if the field at offset 8 already contains the replacement value: no equality check suppresses the write.

### A mismatch precedes a match

Suppose traversal supplies a valid nonmatching candidate, followed by a valid matching candidate.

The function must read each candidate’s match field in that order. It must make no direct write to the first candidate and must write the replacement to the second candidate’s offset-8 field. It must then stop traversal and finalize.

### Multiple matching records are available

Suppose two records would match in the dependency’s traversal order.

Only the first encountered match receives a direct replacement write. The function must not request the later candidate after finding the first match.

### Exhaustion follows mismatches

Suppose several valid candidates do not match and a subsequent traversal call returns zero.

The function must have made no direct record writes. It must proceed to finalization without reading a record based on the final call’s candidate-address slot.

### A negative traversal result

Suppose traversal returns a negative nonzero integer.

The function must take the candidate-processing path, not a distinct error path. Safe continuation requires a valid candidate address despite that return value. If no valid address is supplied, no graceful-error behavior is established.

### Finalization changes the updated record

Suppose a match is found, the replacement is written, and finalization subsequently changes or releases that record.

The contract guarantees the write’s occurrence before finalization, not that the replacement remains readable after return. A post-return state assertion requires a stronger dependency contract.
