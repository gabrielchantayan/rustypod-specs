# F-025193859ccb

## Purpose

F-025193859ccb transforms a 16-byte input block into a 16-byte output block using a supplied sequence of 32-bit key words, a signed round-control value, and globally configured lookup-table addresses.

**Established static behavior:** initial key mixing, a control-dependent number of table-driven full rounds, and a final round that retains selected byte lanes from table entries. Output is serialized most-significant byte first.

**Inferred intent:** the table layout and byte permutation resemble an inverse AES-style block transformation. Table contents, key preparation, and known-answer results are unavailable, so neither algorithm identity nor cryptographic correctness is established.

This contract does not specify a block-chaining mode, padding, authentication, key generation, or a supported cryptographic key size.

## Interface

The function accepts four arguments in this order:

| Argument | Role |
|---|---|
| Key-word address | Caller-supplied address of readable native 32-bit words. Storage ownership is unknown. |
| Round control | Signed integer whose right-shifted value controls paired-round processing. |
| Input address | Address of a readable 16-byte block. |
| Output address | Address of writable storage for 16 bytes. |

There is no return value, returned length, or explicit success/error status.

### Data representation

The transformation uses eight-bit bytes and unsigned 32-bit data words. Data-word right shifts are logical; masks and XOR combinations operate on those 32-bit values.

Each consecutive four-byte input group is interpreted most-significant byte first. Thus bytes `01 23 45 67` represent the numeric word `0x01234567`. Output uses the same byte significance.

Key words and table entries are read directly as native 32-bit numeric values. They are not decoded using the input block’s byte-packing rule. A serialized key schedule must therefore have a representation appropriate to native word reads in the execution environment.

The supplied representation uses signed integer quantities for the round counter and stored table addresses. Their exact ABI widths, pointer-conversion rules, and signed-overflow behavior are **documented_only**. The 32-bit transformation data path does not establish a 32-bit address space.

### Preconditions for ordinary bounded operation

Let \(h\) denote the signed round control shifted right by one. For positive controls, \(h\) is the integer quotient by two.

The ordinary bounded contract requires:

- \(h \geq 1\).
- At least \(8h+4\) readable key words, equivalent to \(32h+16\) bytes.
- Sixteen readable input bytes and sixteen writable output bytes.
- Readable table entries at every selected address.
- Alignment sufficient for native key-word and table-entry reads.
- Representable address calculations and sufficient address space.
- Stable key data, table contents, and global table configuration when the ordinary mathematical transformation is required.
- No output overlap with storage still needed by later reads, except as explicitly discussed under aliasing.

The storage-size formulas are mathematical requirements, not claims that their evaluation is safe in an arbitrary machine integer type. The function does not check these preconditions.

Storage ownership, lifetime management, and authorization to access the supplied ranges are not established by the function body.

## Behavior

### Initial state

The input is divided into four ordered groups of four bytes. Each group is packed into a big-endian 32-bit value and XORed with the corresponding key word at index 0, 1, 2, or 3.

These four mixed words form the initial state. All input bytes are read before any output byte is written. The input block is not read again after initialization.

Initialization does **not** take a single snapshot of all table configuration before reading the input. The configuration accesses and initial mixing are interleaved as specified below.

### Full-round table layout

Four lookup regions supply full-round entries. Under stable configuration, their starts are related to the global full-round anchor as follows:

| Region | Start relative to anchor |
|---|---:|
| First | −3072 bytes |
| Second | −2048 bytes |
| Third | −1024 bytes |
| Fourth | 0 bytes |

Each region is indexed by an eight-bit selector. Selector \(v\), in the range 0–255, identifies a native 32-bit entry at byte offset \(4v\). Each region therefore spans 1024 bytes if all possible entries must be accessible.

The first three region addresses are captured separately during initialization, each from its own access to the global anchor. The fourth region is addressed through references to the global anchor during full-round expressions.

Consequently, the displayed layout describes a stable anchor configuration. It must not be interpreted as evidence that all four regions necessarily derive from one captured anchor value.

A separate global address supplies the final-round table, likewise indexed by eight-bit selectors with four-byte entry spacing.

### Full-round transformation

Number state words 0–3. Within each word, number bytes 0–3 from most significant to least significant.

Each full round combines four selected table entries and one round-key word for each new state word:

| New state word | First region, byte 0 of | Second region, byte 1 of | Third region, byte 2 of | Fourth region, byte 3 of |
|---|---|---|---|---|
| 0 | Previous word 0 | Previous word 3 | Previous word 2 | Previous word 1 |
| 1 | Previous word 1 | Previous word 0 | Previous word 3 | Previous word 2 |
| 2 | Previous word 2 | Previous word 1 | Previous word 0 | Previous word 3 |
| 3 | Previous word 3 | Previous word 2 | Previous word 1 | Previous word 0 |

The selected entries and the corresponding key word are XORed together. Full-round entries contribute all 32 bits.

Every selector in a round comes from that round’s previous state. A newly calculated word must not replace a previous-state word for another selection in the same round.

### Round count and key consumption

For \(h \geq 1\), processing consists of:

- Initial mixing with four key words.
- \(2h-1\) full rounds.
- One final masked-table round.

There are therefore \(2h\) rounds after initial mixing.

Key indices are relative to the original key-word address:

| Stage | Key-word indices |
|---|---|
| Initial mixing | 0–3 |
| Full round \(r\), numbered from 1 | \(4r\) through \(4r+3\) |
| Final round | \(8h\) through \(8h+3\) |

Full rounds are arranged in pairs, except that the last pair contains only its first full round. In the first full round of each pair, result words are completed in order 0, 1, 3, 2. In the second full round, they are completed in order 0, 1, 2, 3.

The half-count is decremented during the first round of each pair, after result word 3 and before result word 2 is completed. The zero test occurs after result word 2. A zero result ends full-round processing; otherwise the second round of the pair follows.

For stable ordinary memory, this evaluation order does not change the mathematical round result. It does constrain the ordering of completed expressions and their memory reads.

Positive controls \(2h\) and \(2h+1\) select the same round count. No parity check is performed.

### Final round

The final round uses the same source-word and byte-selection pattern as a full round, but all four selections use the final-round table.

Each selected entry contributes only the lane corresponding to its selector’s byte position:

| Selector byte position | Contributing bits | Mask |
|---|---|---|
| 0 | 31–24 | `0xFF000000` |
| 1 | 23–16 | `0x00FF0000` |
| 2 | 15–8 | `0x0000FF00` |
| 3 | 7–0 | `0x000000FF` |

The four masked contributions are XORed with the corresponding final key word. No further full-round transformation follows.

Each resulting word is written as four bytes, most significant first.

There is an address-source asymmetry:

- The four table references used for final result word 0 refer to the global final-table address at that stage.
- Final result words 1–3 use the final-table address captured at entry.

The first group is not established to use one newly captured common address. Its individual references must not be replaced by an assumed entry-time snapshot when describing observable accesses.

### Ordering of reads and writes

The supplied representation establishes these sequencing boundaries:

1. Capture the global final-table address for later use.
2. Compute the half-count from the round control.
3. Read the global full-round anchor and capture the third-region address, anchor minus 1024 bytes.
4. Complete initial state word 0 using input bytes 0–3 and key word 0.
5. Read the global full-round anchor again and capture the second-region address, anchor minus 2048 bytes.
6. Complete initial state word 1 using input bytes 4–7 and key word 1.
7. Complete initial state word 2 using input bytes 8–11 and key word 2.
8. Read the global full-round anchor again and capture the first-region address, anchor minus 3072 bytes.
9. Complete initial state word 3 using input bytes 12–15 and key word 3.
10. Complete all full rounds.
11. Calculate final result word 0, then write output bytes 0–3 in increasing address order.
12. Calculate final result word 1, then write output bytes 4–7 in increasing address order.
13. Calculate final result word 2, then write output bytes 8–11 in increasing address order.
14. Calculate final result word 3, then write output bytes 12–15 in increasing address order.

The three initialization reads of the full-round anchor are separate accesses, interleaved with input/key mixing. They are not one shared snapshot.

Within an individual expression, no strict left-to-right order is established among its operand reads. This applies both to the input-byte/key expressions and to expressions combining table entries with a key word. The sequence above must not be expanded into an unsupported order for those individual reads.

## Side effects

### Writes and state changes

On normal completion, exactly sixteen output-byte writes occur. There is no terminator, appended metadata, returned byte count, or visible write outside the output block.

No explicit write to global configuration is present. Output aliasing configuration storage could nevertheless modify it through the ordinary output writes.

No allocation, release, or ownership-transfer operation is visible. Ownership of input, output, key storage, and table storage remains **unknown**; the absence of memory-management operations does not establish who owns them.

No explicit secure erasure of keys, intermediate words, or other working state is present.

### Aliasing

Exact in-place input/output operation is compatible with the established sequence because every input byte is consumed before output begins. Partial input/output overlap has the same property, provided the output range is writable and does not also overlap other storage needed later.

Overlap with key storage or tables is different. Final output is incremental: one word is calculated and written before subsequent final words are calculated. Earlier output writes can therefore alter entries or key words needed later.

The function does not snapshot the complete key schedule or all lookup entries. Output/key or output/table overlap is not guaranteed to produce the result obtained from immutable original data.

### Errors and partial completion

There is no visible validation, error reporting, exception handling, or rollback.

Invalid or unreadable addresses, invalid alignment, or unrepresentable calculations may cause an execution-environment failure. The exact failure mechanism is **documented_only**.

A failure before final serialization occurs before any output write issued by this body. A failure during final processing can leave a written prefix. A fault during byte stores can leave even a partially written four-byte group; output is not atomic or transactional.

### Timing and access patterns

Lookup addresses depend on state bytes derived from input and key material. Data-independent memory access and constant-time behavior are not established.

### Input byte significance

These values describe initial mixing, not the final output.

### Synthetic tables

Suppose the control is in the bounded domain, every full-round entry is zero, every final-round entry is numerically `0xAABBCCDD`, and every key word read is zero. Also suppose configuration is stable and output does not overlap tables or key storage.

The final output is four repetitions of `AA BB CC DD`, regardless of input. Each final lookup contributes the appropriate byte lane from the same constant table value.

### In-place equivalence
