# F-3fd5e24e72e8

## Purpose

F-3fd5e24e72e8 performs a sequence of memory updates using one explicit input and three additional incoming machine-state values. It then transfers control indirectly, presenting four argument values.

The supplied static representation establishes memory-access relationships, but not an application-level purpose. In particular, it does not establish that the affected regions are objects, buffers, device registers, or valid process memory. Descriptions such as initialization, linking, dispatch, or serialization would be inferred intent rather than established behavior.

This contract preserves access order and overlapping-write effects. It does not reduce the function to its final memory contents: repeated stores, intermediate values, and reads after writes can matter when addresses overlap or memory has externally observable access behavior.

## Interface

### Inputs

The explicit input is a **32-bit value**, called the **request value** below. It is both stored unchanged and used as an address base for a four-byte read at displacement `0x74`. No validation distinguishes an integer payload from an address.

Three additional incoming values participate in the behavior:

- **Primary base:** used for byte and four-byte accesses, a doubled-address calculation, byte extraction, and a shift count.
- **Secondary base:** used for byte and four-byte writes; its low byte is also stored elsewhere.
- **Context base:** used for byte and four-byte accesses, including reads of further address-bearing values.

These names describe roles in this contract, not declared parameters or established object types. Their initialization and calling convention are not supplied. A caller cannot reproduce the behavior using the explicit input alone unless it also supplies the relevant incoming machine state.

### Widths and address notation

The visible representation uses:

- One-byte accesses for byte fields.
- Two-byte access for one later constant store.
- Four-byte accesses for words, address-bearing values, and most stored inputs.

An expression such as “primary base + `0x10`” denotes a byte displacement, not an array index scaled by an element size. Doubling an address-bearing value means multiplying its numerical value by two; it does not establish a two-element array operation.

The primary base is represented as an unsigned 32-bit quantity. Its doubled value therefore has 32-bit unsigned arithmetic semantics in the supplied representation. Address calculations involving signed quantities, target address conversion, and arithmetic right shifts have unresolved target-specific details described below.

## Behavior

### Repeated publication phase

The opening phase repeatedly publishes the same four values to the same four calculated destinations. Within each repetition, the observable store order is:

| Relative order | Destination | Width | Stored value |
|---|---|---:|---|
| First | Twice the primary base, plus `0x54` | 4 bytes | Request value |
| Second | Secondary base + `0x19` | 1 byte | Low byte of the primary base |
| Third | Primary base + `0x11` | 1 byte | Low byte of the secondary base |
| Fourth | Secondary base + `0x34` | 4 bytes | Twice the primary base |

The destinations do not advance between repetitions. No visible memory read, condition, or call separates these stores.

This is a repeated access sequence, not merely a requirement that four final values be present. Replacing it with one set of stores is not established as equivalent for observable or overlapping memory. The exact repetition count is left `documented_only`; no numerical count is asserted by this contract.

The primary-base and secondary-base low bytes are retained as values for later operations. Stores to memory do not themselves update those incoming base values.

### Initial reads and cross-region updates

After the repeated phase, the function reads a four-byte value beginning at absolute address `0xA9`, followed by a four-byte value at request value + `0x74`.

It then writes one byte at absolute address `0x3A`. That byte is the low eight bits of twice the primary-base low byte plus `0x30`. This is arithmetic byte generation, not an established conversion to a decimal digit.

Next, it reads four bytes at context base + `0x14`, then four bytes at primary base + `0x04`. These values are retained for later stores or transfer arguments.

The following changes occur before the next context-field read:

- Context base + `0x0D` receives the primary-base low byte.
- Primary base + `0x08` receives the byte `0x6C`.
- Primary base + `0x0D`, then primary base + `0x09`, receive the secondary-base low byte.
- Context base + `0x54` receives the context-base value as four bytes.
- Absolute address `0x67` receives the low byte of the earlier four-byte read from `0xA9`.

Only after those writes does the function read four bytes at context base + `0x44`. That read is sensitive to any overlap with earlier destinations. The resulting value will be called the **context word**.

The byte at absolute address `0x67` is then read and copied to absolute address `0x21`. This is a memory-to-memory propagation through an intervening read; it is not specified as a direct copy from the saved `0xA9` value.

### Overlapping field updates

The context word supplies three subsequent values:

- Its low byte is written to primary base + `0x10`.
- Its complete four-byte value is written to secondary base + `0x54`.
- Its right-shifted low byte is written to context base + `0x01`, with a shift count taken from the low eight bits of the primary base.

The four-byte field at secondary base + `0x54` is then overwritten with the primary-base value. The earlier context-word store remains part of the observable sequence.

A four-byte read at primary base + `0x40` occurs next. After that read, the word saved from primary base + `0x04` is written to secondary base + `0x74`. The newly read word is then written as four bytes at primary base + `0x10`.

That last store overlaps the earlier byte store at primary base + `0x10`. It also covers primary base + `0x11`, which was written during the repeated phase. It must not be modeled as an update to a separate, non-overlapping field.

The function next writes the context-base value to secondary base + `0x44`, reloads the byte at absolute address `0x67` into primary base + `0x09`, writes the primary-base low byte to context base + `0x09`, and writes the saved four-byte value from `0xA9` to primary base + `0x44`.

### Derived-address updates

The function now reads four bytes at primary base + `0x54`. Call the resulting address-bearing value the **linked base**. Its source is primary base + `0x54`, not twice the primary base + `0x54`.

Before using the linked base, the function again reads absolute byte address `0x67` and writes that byte to primary base + `0x09`. The two copies from `0x67` are separate accesses; they must not be assumed to obtain the same byte if intervening writes or external activity can affect that address.

The low byte of the previously saved request-relative word is then written to linked base + `0x0D`. The saved word from context base + `0x14` is written to context base + `0x54`, overwriting the earlier context-base self-value there.

A four-byte read at primary base + `0x14` follows. Its low byte is retained for a later linked-field update.

The function then:

- Writes the request-relative saved low byte to context base + `0x11`.
- Writes the linked-base low byte to primary base + `0x09`.
- Writes the complete linked-base value to primary base + `0x44`.

These operations can overwrite earlier byte copies and the earlier four-byte global-derived value.

### Final reads, writes, and transfer

A four-byte read at context base + `0x04` supplies another address-bearing value, the **record base**.

A two-byte value `0x0065` is written at twice the record base. This access is two bytes wide; it is not a byte store of a character.

The function then reads four bytes at record base + `0x64`. Call this the **record word**. After that read, it writes the low byte saved from primary base + `0x14` to linked base + `0x11`, then writes the four-byte constant `100` to linked base + `0x54`.

Next, it reads four bytes at record base + `0x74`, then four bytes at context base + `0x64`. Call the latter value the **destination base**.

The final visible stores, in order, are:

- The record-base low byte to context base + `0x09`.
- The record word, as four bytes, to destination base + `0x54`.
- The destination-base value, as four bytes, to twice the record word.

Only after those stores does the unresolved indirect transfer occur. Its four presented arguments, in order, are:

1. `0x72`.
2. The record word read from record base + `0x64`.
3. The word saved earlier from context base + `0x14`.
4. The word read from record base + `0x74`.

Later overwrites of the original read locations do not change these already captured argument values.

## Side effects

No disjointness is established among these locations. For example, a calculated destination may overlap a later input field or an absolute-address byte. Consequently:

- Reads obtain the contents present when they occur, after preceding visible writes.
- Saved values remain distinct from later rereads of their original locations.
- An early four-byte write can change a later address-bearing read.
- A fault or nonreturning transfer can leave a partially updated memory state.

Endianness affects the byte consequences of overlapping multi-byte accesses. No target byte order is supplied.

## Acceptance examples

These are conditional contract examples, not executed tests.

### Independent ordinary memory

If all accessed regions are valid, distinct where relevant, stable except for this function’s writes, and compatible with the target’s access requirements, the repeated opening phase stores the request value at twice the primary base + `0x54` and twice the primary base at secondary base + `0x34`.

In that same scenario, secondary base + `0x54` ultimately contains the primary-base value, not the earlier context word. Both stores are nevertheless part of the required access sequence.

### Byte truncation

If the primary-base low byte is `0xF0`, the byte written at absolute address `0x3A` is `0x10`: twice `0xF0` plus `0x30`, reduced to eight bits.

This does not imply printable output or a digit-range input requirement.

### Overlapping field replacement

If the four-byte read at primary base + `0x40` yields a particular word, the later four-byte store places that word at primary base + `0x10`. The prior byte written at exactly that address is superseded according to the target byte order. An implementation that preserves that earlier byte while updating only the other three bytes does not match this behavior.

### Captured transfer argument

If context base + `0x14` initially yields a word and later writes change that memory, the third presented transfer argument remains the saved word. It is not a fresh read performed at transfer time.

### Invalid derived destination

If the record word leads to an inaccessible address when doubled, the final four-byte store may fail after all earlier visible stores have occurred. No rollback, error return, or guaranteed arrival at the indirect destination is established.

### Large shift count

If the primary-base low byte is at least `32`, the shifted byte cannot be accepted against a guessed masking or zero-result rule. Expected behavior requires target-specific shift semantics. This case remains `documented_only`.
