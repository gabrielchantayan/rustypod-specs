# F-8b2bcc916975

## Purpose

F-8b2bcc916975 consumes one 16-bit input value through a mutable cursor and expands its four hexadecimal digits into four output bytes. Each digit becomes a byte whose upper and lower four-bit halves both equal that digit. Output order follows the numerical significance of the input digits, from most significant to least significant.

For a four-bit value \(n\), the expansion is \(17n\). Thus, zero expands to 0, one to 17, and fifteen to 255. This is exact integer expansion, without rounding or saturation.

The digit-expansion behavior is established by the supplied static evidence. An interpretation such as converting packed four-bit image components into eight-bit components is plausible but unestablished. No channel meanings, image format, or higher-level data model are part of this contract.

## Behavior

### Ordered memory effects

On a normal execution, the function performs the following memory operations in this order:

1. Reads the current input address from the cursor slot.
2. Writes the address of the next 16-bit element back into that slot.
3. Reads one 16-bit unsigned value from the original input address.
4. Writes the first output byte.
5. Writes the second output byte.
6. Writes the third output byte.
7. Writes the fourth output byte.

The input address used for the 16-bit read is the address captured before the cursor update. The function does not reload the cursor slot to determine where to read.

The cursor update therefore precedes the input read, rather than following successful conversion. With valid, disjoint storage, the observable result is one consumed 16-bit element and four produced bytes. The routine does not provide transactional behavior or rollback.

These are the memory effects expressed by the supplied static representation. Guarantees about hardware bus transactions, atomicity, compiler reordering, or observations by concurrent agents are not established.

### Output transformation

Let the loaded unsigned input value have four hexadecimal digits \(a\), \(b\), \(c\), and \(d\), ordered from most significant to least significant. Each digit is in the range 0 through 15.

The output is:

| Output offset | Selected input bits | Output value |
|---|---|---|
| 0 | 15 through 12 | \(17a\) |
| 1 | 11 through 8 | \(17b\) |
| 2 | 7 through 4 | \(17c\) |
| 3 | 3 through 0 | \(17d\) |

Equivalently, the two hexadecimal digits in each output byte are identical. An input numerically equal to 0xABCD produces bytes 0xAA, 0xBB, 0xCC, and 0xDD.

This order is defined by the loaded value’s bit significance. It does not independently establish which source-memory byte contains the upper half of that value. The 16-bit read uses the execution environment’s byte order; there is no explicit byte swap.

### Width and arithmetic properties

All four extracted digits are unsigned. There is no sign extension, signed comparison, clamping, or interpretation of the top input bit as a sign.

Every output value is between 0 and 255, inclusive. All outputs are multiples of 17. Inputs whose digits are identical produce four equal output bytes.

The least-significant digit is isolated through shifts on a 32-bit unsigned intermediate before being combined with its duplicate. Under the represented widths, discarded high bits cannot contribute to the output. This operation has the same result as multiplying the isolated four-bit digit by 17; it does not introduce a signed-overflow case.

The function always writes four bytes when it completes normally. No input value causes an early return, conditional omission, extra output, or different cursor increment.

### Overlapping storage

The supplied evidence contains no explicit non-overlap check or restriction. Overlap must nevertheless be interpreted according to the operation order, not as though the input were snapshotted before all writes.

If the cursor slot overlaps the input element, updating the cursor can change the bytes subsequently loaded as input. The converted value is then the value read after that update, subject to the execution environment permitting the overlapping accesses.

If the destination overlaps the input element, the complete 16-bit value is loaded before any output byte is written. The four outputs are calculated from that captured value; later output writes do not cause another input read.

If the destination overlaps the cursor slot, the output writes occur after the cursor update and can overwrite some or all of its stored representation. Consequently, a final cursor value advanced by two bytes is guaranteed only when later output writes do not alter the slot.

These observations describe the represented access sequence. They do not establish that every overlapping arrangement is valid under an unknown source language, memory model, or ABI.
