# F-9956f7343fc0

## Purpose

F-9956f7343fc0 selects the first nonzero object reference from a two-entry global table and invokes an indirectly resolved callback with the supplied operation.

When the operation is 8 and the unsigned selector is 0, 1, or 2, it also writes selected fields of one record, invokes two status-related dependencies, and reports a numeric outcome through F-1b765582ee90. The outcome is 1, 2, or 3.

The established contract concerns selection, callback evaluation, field accesses, and dependency calls. “Record reset,” “status,” and “outcome” are descriptive labels, not established domain meanings. No broader lifecycle, ownership, or resource-release operation is established.

## Interface

### Inputs and output

| Item | Representation | Use |
|---|---|---|
| Operation | Signed 32-bit integer | Passed unchanged to the callback; equality with 8 enables additional processing |
| Selector | Unsigned 32-bit integer | Values 0–2 select a record; all larger values prevent additional processing |
| Return | No explicit return value | Results are observable through memory effects and calls |

There is no explicit error result.

### Selection and callback layout

The global selection table has two relevant entries, each holding a 32-bit object reference, at byte offsets 0 and 4. A zero reference is unavailable.

A selected object has a 32-bit interface reference at byte offset 0x10. For callback lookup:

- The interface begins with a 32-bit dispatch-table reference.
- A callback reference occupies four bytes at dispatch-table offset 0x14.

The interface field at object offset 0x10 is evaluated separately for callback lookup and for the callback’s first argument. These are not established to be one cached value. Their relative evaluation order is unspecified by the supplied representation.

### Record layout

On the qualifying path, a subsequent evaluation of the selected object’s interface field supplies the record-storage reference. The record-array base is four bytes beyond that interface address.

Three record positions are used, with a stride of 0x20 bytes:

| Record index | Address relative to the subsequently obtained interface |
|---:|---:|
| 0 | 0x04 |
| 1 | 0x24 |
| 2 | 0x44 |

The selected record receives these writes, in order:

| Record-relative offset | Width | Stored value |
|---:|---:|---:|
| 0x00 | 32 bits | 0 |
| 0x04 | 32 bits | 0 |
| 0x0C | 32 bits | 0 |
| 0x10 | 32 bits | 0 |
| 0x14 | 32 bits | 0xFFFFFFFF |
| 0x18 | 32 bits | 0 |
| 0x1C | 16 bits | 0 |

The final value is the 32-bit all-ones pattern, not a claim about the signedness of the field.

No direct reset write covers record-relative bytes 0x08–0x0B or 0x1E–0x1F. Their preservation over the entire invocation depends on the effects of called functions.

### Access requirements

Required storage depends on the executed path:

- Table entry 0 must be readable. Entry 1 must be readable only if selection reaches it.
- After successful selection, the object’s interface field must support both callback-related evaluations.
- The interface obtained for lookup must support reading its dispatch-table reference, and that table must support reading its callback reference.
- The resolved callback must be callable with the evaluated first argument and the operation. Additional validity requirements imposed by the callback are unknown.
- On the qualifying record path, the object’s interface field must remain readable for the subsequent evaluation.
- The selected record must permit the seven writes listed above. The touched bytes are 0x00–0x07 and 0x0C–0x1D.
- If the status-dependent branch clears fields, bytes 0x18–0x1B of each of the three records must be writable.
- Otherwise, bytes 0x0C–0x0F of each record must be readable.

These accesses do not require every byte in the nominal 0x60-byte record span to be accessible. Whole-span accessibility is a possible conservative caller assumption, not a requirement established by the direct accesses.

Address calculations must designate valid storage for the accesses actually performed. No pointer validation or address-wrap protection is present. Dependency-specific requirements remain separate and unknown.

## Behavior

### 1. Select an object

Selection examines the two entries in order.

If entry 0 is nonzero, its object reference is selected, and entry 1 is not evaluated for selection. If entry 0 is zero, entry 1 is evaluated. If that entry is also zero, the function returns without invoking a callback or any named dependency.

The selected object reference is retained. The function does not repeat table selection after calling external code.

### 2. Resolve and invoke the callback

Successful selection leads to an indirect call. The call expression contains two separate evaluations of the selected object’s interface field:

- One evaluation supplies the interface used for callback lookup. Through that interface, the function obtains the dispatch-table reference and then the callback reference at offset 0x14.
- Another evaluation supplies the callback’s first argument.

The operation is the callback’s second argument.

The lookup chain has address dependencies: the lookup interface is needed to obtain the dispatch table, and that table is needed to obtain the callback. However, the supplied representation does not establish where the first-argument field evaluation occurs relative to those lookup evaluations. It therefore does not establish a single fully ordered sequence of callback-resolution reads.

If the interface field remains stable, both evaluations identify the same interface. If it changes between evaluations, the representation does not guarantee that the callback is looked up through the same interface that is passed as its first argument. Such mutation does not by itself establish that execution is valid; concurrency and callback preconditions are unknown.

No callback result is used.

The callback occurs before the operation and selector filters. Thus, neither an operation other than 8 nor an out-of-range selector prevents dispatch.

If the callback returns:

- An operation other than 8 causes an immediate return from the remaining processing.
- For operation 8, an unsigned selector greater than 2 also causes a return.

There is no explicit recovery if callback resolution fails or the callback does not return.

### 3. Obtain record storage after the callback

For operation 8 with selector 0–2, the function evaluates the originally selected object’s interface field again, after the callback returns.

This is a subsequent evaluation, not merely a “second read”: the callback expression already contains two separate evaluations.

The function retains the resulting address plus four bytes as its record-array base. Record processing can therefore use a different interface from either callback-related evaluation if the object’s field has changed.

Later record accesses use this retained array base. They do not reselect an object or reread its interface field after the status-related dependencies.

A signed selector check also appears before the selected-record writes. It leads to F-a817d8d58c10 when the signed value exceeds 2. That path is unreachable through the established preceding filter: every selector reaching it is already restricted by an unsigned comparison to 0, 1, or 2.

### 4. Write selected-record fields

The selected record is located at the retained array base plus the selector multiplied by 0x20.

Because the selector has already been restricted to 0–2, the multiplication produces only 0, 0x20, or 0x40. The nominal three-record extent is 0x60 bytes, but only the explicitly accessed fields require accessibility.

The seven stores occur in the order listed under **Interface**. They do not clear the whole record:

- Offset 0x14 receives 0xFFFFFFFF.
- The final write is 16 bits wide.
- The gaps at 0x08–0x0B and 0x1E–0x1F receive no direct reset write.

No allocation, destructor, release, or ownership-transfer operation is explicitly associated with these overwrites. Whether the previous contents carried resource obligations is unknown.

### 5. Invoke the status-related dependencies

After the record writes, the function initializes two distinct four-byte temporary locations:

1. The first receives 0.
2. The second receives 4.

It calls F-b9d333145f3e without explicit arguments. The returned 32-bit value becomes the first argument to F-ca2888499290. The remaining arguments are the addresses of the first and second temporaries, respectively.

After F-ca2888499290 returns:

- The first temporary’s contents are not examined by this function.
- Only the low eight bits of the second temporary determine the next branch.
- The upper 24 bits do not affect that decision.
- No return value from F-ca2888499290 is used.

The value forwarded from F-b9d333145f3e is not established to be an owned handle. Neither dependency is established to preserve globals, object fields, or record contents.

### 6. Derive and report the outcome

**When the second temporary’s low byte is 1 or 2:**

The function writes a 32-bit zero to offset 0x18 of record 0, then record 1, then record 2, using the retained array base.

This includes another write to the selected record’s offset-0x18 field. There is no direct read of any record’s offset-0x0C field on this branch.

It then calls F-1b765582ee90 with the 32-bit value 1.

**When the low byte is any other value:**

The function reads the 32-bit field at offset 0x0C of record 0, then record 1, then record 2, and combines those values using bitwise OR.

- If bit 0 of the combined value is clear, it calls F-1b765582ee90 with 2.
- If bit 0 is set, it calls F-1b765582ee90 with 3.

All three reads occur. A set low bit in an earlier record does not suppress later reads. Bits 1–31 do not affect the reported argument.

Although the selected record’s offset-0x0C field was previously written to zero, its later observed value need not be zero: the intervening dependencies have no established preservation contract.

The function returns after the reporting call returns.

## Side effects

The direct effects follow this partial ordering:

1. Selection-table evaluation precedes dispatch.
2. Both callback-related interface-field evaluations and callback lookup precede the indirect call, without an established total order between the first-argument evaluation and the lookup chain.
3. The callback returns before the operation and selector filters permit further work.
4. A subsequent interface-field evaluation supplies the retained record base.
5. The seven selected-record writes precede temporary initialization and the two status-related calls.
6. The branch-specific record accesses follow those calls.
7. F-1b765582ee90 follows the branch-specific accesses.

This describes the supplied static representation, not an atomicity, synchronization, or hardware memory-barrier guarantee.

The function directly performs no global-table write, allocation, deallocation, or explicit ownership transfer. Called functions may have such effects; none can be excluded from the available evidence.

The temporary addresses are supplied for the status-related call. Their use does not establish an ownership transfer or permission to retain them beyond their valid lifetime. Whether the dependency retains them is unknown.

Invalid storage, invalid callback references, and dependency failures have no explicit error conversion or recovery path here. Execution stops progressing through this contract if a required call does not return.

## Acceptance examples

These are conditional criteria derived from static evidence, not executed tests. Valid storage, valid calls, and returning dependencies are assumed where applicable.

1. **Empty selection table.** Both entries are zero. Both are evaluated in order; no callback or named dependency is called.

2. **First entry wins.** Both entries are nonzero. The first object is selected. The second entry is not evaluated for selection.

3. **Fallback selection.** Entry 0 is zero and entry 1 is nonzero. Dispatch uses the second object.

4. **Operation filter follows dispatch.** With operation 7, a selected object still receives the callback with operation 7. After the callback returns, this function performs no record reset, status query, or outcome report.

5. **Unsigned selector rejection.** With operation 8 and selector 3 or 0xFFFFFFFF, the callback still occurs. Subsequent processing returns before obtaining the record base. F-a817d8d58c10 is not reached.

6. **Independent callback evaluations.** If the interface field is stable, lookup and the first argument use the same interface. If the two evaluations observe different valid references, the contract does not require them to match or specify which evaluation happened first.

7. **Callback changes the interface.** With operation 8 and selector 1, the callback replaces the selected object’s interface field. Record processing uses the value obtained by the subsequent field evaluation, not a cached callback interface.

8. **Low byte selects clearing.** If the second temporary contains 0x12340002 after F-ca2888499290, offset 0x18 is cleared in records 0, 1, and 2, in that order, and the reported argument is 1.

9. **Nonzero flags without bit 0.** If the second temporary contains 0x00000100, the record-read branch applies. Observed flag values 0, 2, and 4 produce reported argument 2, despite their nonzero combined value.

10. **Bit 0 controls outcome 3.** On the record-read branch, observed values 0, 0x80000001, and 0 produce reported argument 3. The third read still occurs.

11. **Intervening mutation matters.** A status-related dependency changes the selected record’s offset-0x0C field to 1 after its initial zeroing. If the record-read branch then observes that value, it contributes to reported argument 3.

12. **Selective accessibility and preservation.** If all directly accessed ranges and dependency requirements are satisfied, the contract imposes no additional requirement that untouched record gaps be accessible. If those gaps hold prior values and no dependency modifies them, they retain those values.
