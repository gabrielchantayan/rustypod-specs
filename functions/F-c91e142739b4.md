# F-c91e142739b4

## Purpose

F-c91e142739b4 conditionally invokes a registered callback according to a 32-bit operation selector and a shared state word. It also invokes two surrounding dependency operations and, for selectors 1 and 4, an additional trailing dependency.

The established behavior distinguishes four selectors:

- **1 and 4:** invoke the callback only when the shared state word is exactly zero; write one before invoking it.
- **2 and 3:** invoke the callback only when the shared state word is exactly one; write zero after the callback returns.
- **All other values:** do not invoke the callback and do not directly change the state word.

Two resource-presence checks precede this processing. They return distinct nonzero status values and bypass all dependency calls.

An activation/deactivation interpretation is plausible, but not established. Likewise, the surrounding dependencies may implement synchronization or execution-context management, but their actual semantics are unknown. The contract below uses their observable call order rather than assigning them those roles.

Selectors outside the four recognized values are accepted by the dispatch logic. They still enter the surrounding dependency sequence after the resource checks succeed.

## Behavior

### 1. Capture the record reference and check resources

The function first captures the global record reference.

It then checks the callback-bearing field through the global reference. If that field is zero, it returns 11 immediately. No dependency or callback is invoked, and no explicit state write occurs.

Only if the first check passes does it check the resource field at offset 8 through the global reference. If that field is zero, it returns 17 immediately. Again, no dependency or callback is invoked, and no explicit state write occurs.

The ordering determines precedence: when both checked fields are zero, the result is 11.

The checks do not depend on the selector. Even an unrecognized selector requires both fields to be nonzero before the function proceeds.

The guard expressions use the global reference, whereas later accesses use the previously captured reference. In an execution where that reference remains unchanged, they concern the same record. The evidence provides no concurrency or memory-ordering model that would justify a stronger guarantee when the global reference changes asynchronously.

### 2. Enter the common dependency sequence

After both checks pass, the function:

1. Calls F-338d16f9ce72 with the resource at offset 8 obtained through the global reference.
2. Calls F-d0e18541f136 with no explicit arguments.
3. Retains the 32-bit result of F-d0e18541f136 for a later call to F-daf9d4e01656.

No result from F-338d16f9ce72 is used.

The state decision occurs after these calls. Consequently, it uses the state present at that later point, not a state snapshot taken before the calls. Either dependency may affect shared data unless its own contract establishes otherwise.

### 3. Dispatch according to the selector

#### Selectors 1 and 4

The function reads the captured record’s state word.

- If the state is exactly zero, it writes one to that word and then invokes the indirect callback.
- If the state is any other 32-bit value, it neither invokes the callback nor directly changes the state.

The callback receives the original selector and the original opaque payload. It receives 1 for selector 1 and 4 for selector 4; these selectors are not collapsed into a common callback argument.

The state write precedes callback-target lookup and invocation. A callback observing the same record therefore encounters the preceding write unless some intervening effect changes the state again.

There is no explicit state write after the callback on this branch. A callback modification to the state is not overwritten by this branch itself.

#### Selectors 2 and 3

The function reads the captured record’s state word.

- If the state is exactly one, it invokes the indirect callback and then, after normal callback return, writes zero to the state word.
- If the state is any other 32-bit value, it neither invokes the callback nor directly changes the state.

The callback receives the original selector and payload.

Unlike the selector-1/4 branch, the callback runs before the state write. Without other effects, the callback therefore encounters state one. If the callback changes that same state word and returns normally, the function subsequently overwrites it with zero.

#### Other selectors

The function performs no callback invocation and no explicit state access or modification for the dispatch decision. It continues to the common trailing calls.

There is no selector-specific error result.

### 4. Perform common trailing calls

After dispatch completes normally, the function:

1. Calls F-daf9d4e01656 with the retained result from F-d0e18541f136.
2. Reads the resource at offset 8 from the captured record and passes it to F-1333331b2da1.

The resource passed to F-1333331b2da1 is read at this later point. It is not a saved copy of the value passed to F-338d16f9ce72. An intervening dependency or callback may therefore cause the two calls to receive different values.

For selectors 1 and 4 only, the function then reads the resource at offset 12 from the captured record and passes it to F-5bcae2eff9a7.

This final selector-dependent call occurs whether or not the callback ran. Its argument is not checked for zero.

After these calls return normally, the function returns zero.

## Side effects

### Explicit state writes

The function itself has only two established state-write cases:

| Selector | State at dispatch decision | Explicit write | Timing |
|---|---:|---:|---|
| 1 or 4 | 0 | 1 | Before callback invocation |
| 2 or 3 | 1 | 0 | After normal callback return |

No other explicit record writes are visible.

These conditions use exact values. A nonzero state other than one is not treated as the enabled condition for selectors 2 and 3. It also prevents the selector-1/4 transition because it is not zero.

### Indirect effects and ownership

Dependencies and the callback may have additional effects. The supplied evidence does not establish that they preserve globals, leave the record unchanged, retain its allocation, or refrain from releasing referenced resources.

The function directly performs no identifiable allocation, deallocation, reference-count adjustment, or ownership transfer. Passing the payload or resource words does not, by itself, establish an ownership convention.

Continued use of the captured record after calls makes record lifetime significant. Replacing the global reference during a dependency or callback does not redirect subsequent accesses that use the captured reference.

### Abnormal completion and reentrancy

No visible recovery or guaranteed-finalization mechanism covers abnormal termination of a dependency or callback. If a call does not return normally, later calls and writes are not established to occur.

This matters particularly for state ordering:

- For selectors 1 and 4, the state has already been written to one before the callback is entered.
- For selectors 2 and 3, the write to zero has not happened when the callback is entered.

The callback’s ability to reenter this function is unknown. If reentry is permitted by the surrounding environment, the same ordering governs what state a nested invocation can observe. No reentrancy safety guarantee follows from the visible function alone.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Except where stated otherwise, assume valid storage, normally returning calls, a stable global reference, and dependencies and callbacks that do not independently modify the record.

1. **First guard takes precedence.**  
   With both checked resource fields zero, any selector returns 11. There are no dependency calls, callback calls, or explicit state writes.

2. **Second guard rejects a missing resource.**  
   With a nonzero callback-bearing field and zero at offset 8, any selector returns 17 without invoking dependencies or the callback.

3. **Selector 1 changes zero to one before notification.**  
   With both guards satisfied and state zero, selector 1 writes one before invoking the callback with selector 1 and the unchanged payload. The common trailing calls and F-5bcae2eff9a7 then occur. The result is zero.

4. **Selector 4 retains its identity.**  
   Under the same state conditions, selector 4 invokes the callback with 4, not 1. Its state-write timing and trailing-call selection match selector 1.

5. **An already nonzero state suppresses selector-1/4 callbacks.**  
   With state one or any other nonzero word, selector 1 or 4 leaves the state unchanged and does not invoke the callback. The surrounding calls, including F-5bcae2eff9a7, still occur.

6. **Selector 2 notifies before clearing.**  
   With state one, the callback receives selector 2 while the state remains one. After normal callback return, the function writes zero. F-5bcae2eff9a7 is not invoked.

7. **Selector 3 requires exactly one.**  
   With state two, selector 3 does not invoke the callback and does not clear the state. The common dependency sequence still completes with result zero.

8. **Unrecognized selectors are not rejected.**  
   With valid checked resources, selector zero or a negative selector produces no callback or explicit state transition. The common dependencies run, F-5bcae2eff9a7 does not, and the result is zero.

9. **A callback mutation has branch-dependent persistence.**  
   If a selector-1 callback changes the state from one to seven and returns, this function does not subsequently overwrite seven. If a selector-2 callback changes the state from one to seven and returns, this function subsequently writes zero.

10. **The trailing resource is reread.**  
    If an intervening call changes offset 8 while preserving a valid captured record, F-1333331b2da1 receives the later value, not necessarily the value supplied to F-338d16f9ce72.
