# F-03c98c4d8f76

## Purpose

F-03c98c4d8f76 constructs a handle associated with a caller-provided context and a resource name. It conditionally searches a global descriptor registry, reuses a matching descriptor or initializes a new one, interprets temporary metadata, and publishes the handle. Participating handles may be inserted into an existing context-associated chain ordered by descriptor address.

These allocation, lookup, initialization, mutation, and publication operations are established by static evidence. Resource opening, caching, and format discovery are inferred intent. The resource format, exact special-name operand, installed data values, and complete ownership protocol are unknown.

## Interface

The function returns a 32-bit integer status and accepts five arguments:

| Argument | Representation | Established use |
|---|---|---|
| Name | Nullable byte pointer | Compared against an opaque data operand; conditionally inspected for an empty first byte; forwarded to dependencies. |
| Context | Pointer to 32-bit words | Supplies backend identity, entry count, entry-array pointer, and flags. |
| Output | Pointer to a 32-bit slot | Receives the handle on success or zero during common failure cleanup; two early failures leave it untouched. |

The visible representation uses 32-bit pointers and words, 16-bit fields, and byte fields. Descriptor-address ordering uses unsigned comparisons.

## Behavior

### Name classification and handle allocation

A null name is classified as not equal to the special operand, without invoking comparison. Otherwise, the name is compared against a named data operand, and a zero comparison result marks it as special. **The operand’s bytes are not supplied; no exact special-name string is established.**

The backend pointer is then captured from context offset `0x00`. F-1c177d5ba9f6 receives allocation size `0x18`.

If allocation returns null, return `7` without writing the output slot.

Otherwise, clear handle byte `0x08`, then store the context pointer at handle offset `0x00`. The function does not clear the whole handle. In particular, byte `0x09` and both links are not universally initialized here.

### Lookup eligibility and preparation

Registry lookup requires all of the following, evaluated with short-circuiting in this order:

1. The name was not classified as special.
2. Options bit `0x40` is clear.
3. Context flag `0x100000` is clear.
4. The name is non-null.
5. Its first byte is nonzero.
6. The current global registry object’s word at offset `0x0c` is nonzero.

The first two conditions are combined before the context flags are read. If an earlier condition excludes lookup, later eligibility reads are avoided. Ineligibility proceeds to new-descriptor allocation without explicitly clearing handle byte `0x09`.

On eligibility, the registry-object pointer used for the enabling-word read is captured for later traversal. Next:

1. Read the backend’s 32-bit word at offset `0x08` and add one.
2. Call F-391e3d30e634 without visible arguments.
3. Set handle byte `0x09` to one.
4. Read, OR with `0x80000`, and write context flags.
5. Check the helper result.

A zero helper result causes a cleanup request for the handle through F-94cb53877c15, followed by return `7`. The output remains untouched. There is no explicit reversal of the flag update.

For a nonzero helper result, invoke the backend callback selected at offset `0x28`, passing the captured backend, original name, previously calculated size, and helper result. No callback return value is used. The helper result remains the temporary value subsequently compared and submitted for cleanup; it is not a callback return.

The size calculation has a 32-bit result and no visible overflow handling. Behavior beyond the representable signed addition boundary is not established as a checked error or portable wraparound.

### Registry traversal and reuse

After the callback, traversal reads offset `0x08` of the **previously captured registry object**, not a freshly loaded global registry pointer.

For each descriptor:

1. Read its underlying-object pointer at descriptor offset `0x00`.
2. Read that object’s word at offset `0x5c`.
3. Compare the temporary value against that word using the unmapped comparison operation.
4. Only on equality, **reload the descriptor’s underlying-object pointer after comparison**, then read that object’s first word and compare it with the originally captured backend.

The object used for backend identity need not be the one used to obtain the comparison operand: the intervening comparison has no supplied preservation contract.

A match stores the descriptor in handle offset `0x04`, increments the descriptor’s 32-bit word at `0x50`, and stops traversal. No overflow check is visible. A nonmatch advances through descriptor offset `0x54`, read after the comparison activity.

After traversal, F-94cb53877c15 receives the temporary value whether a match was found or not. A hit skips new-descriptor initialization and reaches participation-dependent chain handling. A miss proceeds to allocation.

### New-descriptor initialization and metadata acquisition

F-1c177d5ba9f6 receives size `100`. A null result selects status `7` and common failure cleanup, including a cleanup request with the null descriptor value.

For a successful allocation:

1. Read a 32-bit value from a dedicated data location and store it at descriptor offset `0x44`.
2. Store the descriptor’s own address at offset `0x48`.
3. Call F-c24d8dd79401 with the captured backend, descriptor, original name, `0x54`, full options, and additional value.

The value installed at `0x44` is a data read, not an established literal or immutable constant.

A nonzero initialization status enters failure cleanup. On zero:

1. Capture the descriptor’s underlying-object pointer.
2. Invoke an unmapped preparation operation with a temporary area and length `100`.
3. Using the **captured object**, read its pointer at offset `0x6c` and inspect the pointed-to first word.
4. If that word is nonzero, reread the pointer at offset `0x6c` of the same captured object and pass it, the temporary area, and length `100` to F-779a651c5cc8.

Thus preparation may change the descriptor’s current object pointer without changing the object base used for these accesses. There is no null check before dereferencing the pointer obtained at `0x6c`.

If the inspected first word is zero, skip F-779a651c5cc8 and retain zero status. Otherwise, normalize status `0x20a` to zero; any other nonzero status enters cleanup.

### Attachment and metadata layout

After successful metadata processing, the following operations occur in order:

1. Reload the descriptor’s object pointer and store the address of descriptor offset `0x44` at object offset `0x78`.
2. Associate the descriptor with handle offset `0x04`.
3. Read a second dedicated data location and install its 32-bit value at current object offset `0xc4`.
4. Read a third dedicated data location and install its 32-bit value at current object offset `0xc8`.
5. Clear descriptor words at `0x08` and `0x0c`.
6. Copy current object byte `0x10` to descriptor byte `0x11`.
7. Assemble and store the metadata quantity described below.

The object pointer is reloaded for the later object accesses; they do not retain the object captured before preparation. The two later data reads occur after metadata processing, attachment, and handle association, in `0xc4` then `0xc8` order. Neither their contents nor immutability is established.

### Final arithmetic and registration

The subtraction has distinct access and arithmetic widths:

- Read the **32-bit descriptor word at offset `0x1c`**, spanning the fields at `0x1c` and `0x1e`.
- Convert that value to signed 16-bit form.
- Promote that signed value and the captured unsigned deduction to the arithmetic width and subtract.
- Store the result as 16 bits at descriptor offset `0x1e`.

The deduction is between zero and 255. The promoted difference fits signed 32-bit arithmetic; the final store retains its low 16 bits. There is no separate subtraction-range error.

Next, reload the descriptor’s object pointer and call F-3452f1df7e41 with it and the address of `0x1c`. This reload occurs after any accepted-branch calls or rejected-branch fallback call. Accepted metadata therefore causes one visible F-3452f1df7e41 call; rejected metadata causes two. The last call occurs after calculating `0x1e`, so no final consistency relationship between the two fields is established.

If handle byte `0x09` is zero, skip registration and chaining. Otherwise, set descriptor word `0x50` to one, obtain the current global registry pointer again, set descriptor word `0x40` to eight, copy that registry’s head into descriptor offset `0x54`, and replace the registry head with this descriptor.

This global-pointer reload can select a different registry object from the one captured for lookup.

### Context-chain insertion

Successful reuse and participating creation reach a further check of handle byte `0x09`. If nonzero, read the context entry count once and use it as a signed 32-bit bound. Nonpositive counts inspect no entries.

Inspect entries in ascending index order. The entry-array pointer is read for each entry access. Select the first non-null handle whose byte `0x09` is nonzero. If none exists, perform no chain insertion.

From the selected handle, follow offset `0x14` until finding a zero link. The visible traversal reads that link for both advancement and termination; it has no cycle detection.

Compare the new descriptor address with the terminal handle’s descriptor address using unsigned ordering:

- If smaller, set the new handle’s `0x10` link to the terminal handle, clear its `0x14` link, and set the terminal handle’s `0x14` link to the new handle, in that order.
- Otherwise, advance at least once toward `0x10`, continuing while the encountered descriptor address is strictly smaller than the new address. Reread the insertion predecessor’s `0x10` link, assign the new handle’s `0x10` and `0x14` links, update the following neighbor’s `0x14` if present, then update the predecessor’s `0x10`.

Equality does not prevent insertion. For an initially valid ordered chain, `0x14` runs toward nonincreasing descriptor addresses and `0x10` toward nondecreasing addresses. Existing ordering is not validated.

### Publication and errors

Normal success writes the handle pointer to the output and returns zero.

For common failure cleanup:

1. If a descriptor exists and its first word is nonzero, call F-2978ca5df7fb without visible arguments.
2. Submit the descriptor, including null after allocation failure, to F-94cb53877c15.
3. Submit the handle to F-94cb53877c15.
4. Clear the output slot.
5. Return the selected status.

Initialization and untolerated metadata errors retain their returned statuses. No explicit rollback restores context flags or dependency effects.

## Acceptance examples

These are conditional static criteria, not executed tests. Where relevant, they require valid accessible storage and no unmentioned dependency mutations.

1. **First allocation fails:** Return `7`; leave the output unchanged.
2. **Special classification:** A non-null name comparing equal to the opaque operand skips registry lookup regardless of its spelling. No particular literal string is required by the evidence.
3. **Lookup preparation fails:** With lookup eligible and F-391e3d30e634 returning zero, set participation and context flag `0x80000`, request handle cleanup, return `7`, and leave output unchanged.
4. **Object changes during comparison:** If comparison used one object’s `0x5c` but changes the descriptor’s object pointer, backend matching uses the replacement object’s first word.
5. **Descriptor allocation fails:** Request cleanup for null descriptor and allocated handle, clear output, and return `7`.
6. **Preparation changes association:** Metadata-source access still uses the object captured before preparation; subsequent attachment uses the descriptor’s reloaded object pointer.
7. **Metadata boundaries:** Temporary bytes `0x02, 0x00` at `0x10`–`0x11` yield accepted quantity `512`; `0x80, 0x00` yield accepted `32768`; `0x02, 0x01` yield rejected `513`.
8. **Captured deduction:** If temporary byte `0x14` is seven before the accepted-branch calls and those calls later change it, subtraction still uses seven.
9. **Signed conversion:** If the final 32-bit read has low halfword `0x8000` and deduction seven, signed conversion yields `−32768`; the difference is `−32775`, stored at `0x1e` as `0x7ff9`.
10. **Final helper changes size:** A final helper mutation of `0x1c` does not trigger recomputation of `0x1e`.
11. **No chain candidate:** A nonpositive entry count or absence of participating entry handles permits successful publication without visible insertion.
12. **Initialization error:** A nonzero initialization status is returned after applicable common cleanup and output clearing, without explicit context-flag rollback.
