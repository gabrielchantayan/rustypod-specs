# F-a0c5d57d1d48

## Purpose

F-a0c5d57d1d48 constructs one of two output-record formats, selecting the format from a 16-bit value in a caller-supplied context. It delegates payload processing, optionally reports whether the wide-format payload contains a value in particular numeric ranges, and maps a retained 16-bit processing status to one of three 32-bit return values.

The established behavior is record initialization, dependency invocation, conditional fallback processing, optional payload classification, and status translation. The semantic meaning of the context, payload, record header, and classification flag is not established. Describing the operation as text conversion or encoding would be inferred intent, not a proven interface contract.

## Interface

### Inputs and output locations

The function accepts six arguments:

| Argument | Established representation and use |
|---|---|
| Context | A 32-bit address-like argument. A 16-bit value at byte offset 2 selects the record format. The full argument is also passed to one dependency in the other format. |
| Header input | An opaque 32-bit value passed unchanged to F-946cac4b59bc. |
| Source | A 32-bit address-like argument. Zero has explicit control-flow significance. Nonzero values may be passed to processing dependencies and to F-1cb585febd84. |
| Extent | A 32-bit integer. It may be replaced before format selection. No positivity or bounds validation is visible. |
| Output record | A writable address used through both byte-sized and 16-bit accesses. It is mandatory on all ordinary execution paths. |
| Classification output | An optional writable location for a 32-bit value. A zero address disables classification reporting and also changes fallback behavior in the non-wide format. |

These argument descriptions concern the represented interface. They do not establish valid allocation sizes, the meaning of an extent unit, or the signedness expected by dependencies.

### Return value

The result is a 32-bit bit pattern derived from the final retained 16-bit processing status:

| Retained status | Return bit pattern | Signed 32-bit interpretation |
|---|---:|---:|
| Zero | `0x00000000` | 0 |
| `0x003F` | `0xFFFFFFDB` | −37 |
| Any other nonzero 16-bit value | `0xFFFFFFCE` | −50 |

The status starts at zero. If processing is skipped, the function therefore returns zero, assuming execution completes normally.

A zero return does not independently prove that every dependency succeeded. Some dependency results are ignored; others are replaced or narrowed before mapping.

### Minimum memory obligations

For ordinary completion, the context must support a 16-bit read at offset 2, and the record must support every access actually reached. The fixed record accesses include offsets 0 through 7, with additional storage potentially used by dependencies and payload scanning.

No record-capacity argument is present. The supplied evidence does not establish a universally sufficient output allocation.

The optional classification location must support a 32-bit write when nonzero. Alignment, overlap, address validity, and dependency-specific source requirements are not checked here.

## Behavior

### 1. Normalize the source and extent relationship

Normalization occurs before reading the context’s format selector.

- If the source is zero, the effective extent becomes zero, regardless of the supplied extent.
- If the source is nonzero and the supplied extent is zero, F-1cb585febd84 is called with the source. Its result becomes the effective extent.
- Otherwise, the supplied extent is retained.

A nonzero effective extent enables later processing. This is a zero/nonzero test, not a positive-length test. A negative 32-bit extent is not rejected by the visible function.

No guarantee is established about side effects of F-1cb585febd84. In particular, the context selector is read after that call, not captured before it.

### 2. Select the record format

The function reads a 16-bit value at context offset 2.

- A value equal to `0x482B` selects the wide-format path.
- Every other value selects the byte-oriented path.

This is a numeric 16-bit comparison. Translating the selector into a particular pair of bytes requires a target byte-order assumption.

### 3. Wide-format path

The visible record layout is:

| Byte offset | Visible use |
|---:|---|
| 0–1 | 16-bit header field, initially set to 6 |
| 2 onward | Destination supplied to F-946cac4b59bc |
| 6–7 | 16-bit payload-element count |
| 8 onward | Destination supplied to the wide-format processing dependency; subsequently scanned as 16-bit elements |

The header dependency’s complete write footprint is unknown, so these uses do not prove that its writes are confined to offsets 2–5.

The ordered operations are:

1. Set an internal 32-bit quantity to zero.
2. Write the 16-bit value 6 at record offset 0.
3. Call F-946cac4b59bc with the header input and the address at record offset 2. Its return value is ignored.
4. Write a 16-bit zero at record offset 6.
5. If the effective extent is nonzero, invoke F-d040ad03a6d9.
6. If classification reporting is enabled, initialize and potentially update the classification output.

The processing call receives, in order:

- Source.
- Effective extent.
- Record address at offset 8.
- Address of the internal 32-bit quantity.
- `0x1FE`.
- `0x3A`.
- `4`.

The dependency result is retained as a 16-bit status.

After that call, the function derives the record’s 16-bit count from the internal 32-bit quantity. Under the represented 32-bit shift behavior, this selects bits 1 through 16 of that quantity. Equivalently, interpret the quantity as a 32-bit bit pattern, shift it right by one, and retain the low 16 bits.

This is not an unrestricted division by two. High bits beyond bit 16 are discarded, and an odd low bit is discarded.

The function then updates the 16-bit field at record offset 0 by adding the low 16 bits of the internal quantity to the field’s value as read after the dependency call. Only the low 16 bits of the sum are stored.

Consequently, the final header field is not unconditionally “6 plus the reported quantity”: a dependency could have changed that field before the addition.

These count and header updates occur even when the retained processing status is nonzero.

#### Wide-format classification

When the classification output is nonzero:

1. Capture the 16-bit count at record offset 6 as an unsigned count.
2. Write a 32-bit zero to the classification output.
3. Read record elements sequentially, starting at offset 8, as unsigned 16-bit values.
4. On the first matching value, write a 32-bit one to the classification output and stop scanning.

An element matches exactly when its unsigned value belongs to either inclusive range:

- `0x3000` through `0x9FFF`.
- `0xFF00` through `0xFFEF`.

Values from `0xA000` through `0xFEFF` do not match. The subtraction used in the comparison is 32-bit unsigned arithmetic; values below `0xFF00` in that region do not become small positive offsets.

At most 65,535 elements are examined because the captured count is unsigned 16-bit. There is no check that this count fits the output allocation or agrees with the amount of initialized payload.

Classification occurs even after a nonzero processing status. With zero effective extent, the function itself initializes the count to zero, so no elements are scanned, absent overlapping-memory effects.

### 4. Byte-oriented path

The visible record uses are:

| Byte offset | Visible use |
|---:|---|
| 0 | Initially written as byte value 6; later conditionally updated |
| 1 | Initially written as byte value zero |
| 2 onward | Destination supplied to F-946cac4b59bc |
| 6 | Initially written as byte value zero; payload destination supplied to processing dependencies |
| 6–7 | Later read together as a 16-bit value when updating byte 0 |

The ordered operations are:

1. Write byte value 6 at offset 0.
2. Write byte value zero at offset 1.
3. Call F-946cac4b59bc with the header input and record address at offset 2. Ignore its return value.
4. Write byte value zero at offset 6.
5. If the effective extent is nonzero, call F-a3e615c98fcf with context, effective extent, source, and record address at offset 6.
6. Retain that dependency’s result as a 16-bit status.
7. If that status is nonzero and classification reporting is disabled, call F-079b3af77906 with effective extent, source, and record address at offset 6. Replace the retained status with its 16-bit result.
8. After processing, update byte 0 from the low eight bits of the sum of the 16-bit values read at offsets 0 and 6.
9. If classification reporting is enabled, write a 32-bit zero to its destination.

The fallback call is therefore controlled by two conditions together: a nonzero initial status and a zero classification-output address. A caller requesting classification suppresses fallback, even though the classification result in this format is always written as zero.

The byte-0 update occurs whenever the effective extent is nonzero, including after a processing failure. It does not occur when processing is skipped.

The update reads complete 16-bit values before narrowing the result. On a little-endian target, this produces the familiar low-byte sum using the bytes at offsets 0 and 6. That simplification is conditional on byte order. The function itself initializes only byte 6, not byte 7, before the possible 16-bit read at offset 6.

## Side effects

The function writes directly into caller-provided record storage. Initialization and processing are not transactional: there is no visible rollback on a nonzero status.

The optional classification output is written after the path’s processing and record updates. In the wide path it is first set to zero and may later be set to one. In the byte-oriented path it receives zero.

No direct allocation, deallocation, ownership transfer, or global-variable access is visible in this function. This does not establish that dependencies have no such effects. Their ownership rules and global-state behavior are unknown.

No explicit error is returned for null mandatory pointers, insufficient capacity, invalid alignment, invalid extent, or overlapping arguments. Such cases can produce invalid accesses or dependency-defined behavior.

Aliasing can change observable results. For example, wide-format classification captures the count before clearing the classification output, but reads payload elements afterward. If the classification destination overlaps the record, that clearing write can change the data subsequently scanned. The implementation does not prohibit or compensate for this overlap.

## Acceptance examples

These are conditional acceptance criteria derived from static behavior, not observed executions. Except where overlap is the subject, assume valid, nonoverlapping storage and dependencies that do not alter unrelated record fields.

1. **Zero source suppresses processing.**  
   Given a zero source and any supplied extent, neither format-specific processing dependency nor the extent-producing dependency is called. The header dependency is still called. The returned status maps to zero.

2. **Automatic extent precedes selection.**  
   Given a nonzero source and zero supplied extent, F-1cb585febd84 is called before the context selector is read. If it returns zero, format-specific processing is skipped.

3. **Wide-format quantity of ten.**  
   If wide-format processing reports an internal quantity of 10 and leaves the initial header field unchanged, the stored count is 5 and the header field becomes 16. A status of zero produces return value zero.

4. **Count truncation is observable.**  
   If the reported 32-bit quantity is `0x00020002`, the stored count is 1, not 65,537. Its low 16 bits are 2, so an unchanged initial header becomes 8.

5. **Classification boundaries.**  
   With a count covering the tested element, `0x2FFF` does not match; `0x3000` and `0x9FFF` match; `0xA000` and `0xFEFF` do not match; `0xFF00` and `0xFFEF` match; `0xFFF0` does not match. Scanning stops on the first match.

6. **Classification after failure.**  
   If wide-format processing returns `0x003F` but provides a count of one and a payload element of `0x3000`, enabled classification becomes one and the function returns `0xFFFFFFDB`.

7. **Fallback replaces the initial status.**  
   In byte-oriented mode, if initial processing returns a nonzero status and classification is disabled, fallback runs. If fallback returns zero, the function returns zero, regardless of the initial failure.

8. **Requesting classification suppresses fallback.**  
   Under the preceding initial failure, a nonzero classification-output address prevents fallback. The classification output becomes zero, and the initial status determines the return value.

9. **Byte-sized header wraparound.**  
   On a little-endian target, if the relevant low bytes after processing are 250 at offset 0 and 10 at offset 6, the stored byte at offset 0 becomes 4. No overflow error is reported.
