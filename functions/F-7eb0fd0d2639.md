# F-7eb0fd0d2639

## Purpose

F-7eb0fd0d2639 inspects one integer table entry when a numerically interpreted selector satisfies a descriptor-held boundary. A selected entry containing zero permits normal return. A selected entry containing any nonzero value triggers a dependency response: F-ee5919ca4be6 first, then F-feee9156a257 if the first call returns control.

The selector is carried through a pointer-shaped interface but is not dereferenced. Rejected selectors cause no table access. Selectors with a negative signed integer interpretation also cause no descriptor access.

**Inferred intent:** the boundary acts like an exclusive upper limit under ordinary corresponding pointer/integer conversions. The nonzero-entry response may represent an exceptional condition. Neither the boundary’s relationship to an allocation nor the purpose of the dependency response is established.

## Interface

### Inputs and result

The function has two ordered inputs:

1. **Descriptor reference:** identifies storage holding an integer table base followed by an integer boundary.
2. **Selector:** a pointer-shaped value used for comparison and integer address calculation, not as a reference to selector storage.

There is no explicit result value or output parameter. The function does not return the selected entry or a status indicating why inspection was skipped.

A null-shaped selector is not inherently an instruction to skip inspection. With the ordinary conversion of null to integer zero, it can select the first entry when the boundary is positive.

### Layout and integer widths

The supplied representation accesses integer objects. It explicitly uses a **four-byte address stride** between successive selector values. It does not independently provide a complete ABI specification.

For a 32-bit integer layout, the accessed storage is:

| Storage | Position | Interpretation |
|---|---|---|
| Table-base word | Descriptor bytes 0–3 | Signed integer participating in address arithmetic |
| Boundary word | Descriptor bytes 4–7 | Integer converted for pointer-shaped equality and signed ordering |
| Selected entry | Four bytes at the resulting address | Integer classified as zero or nonzero |

The boundary occupies the integer element immediately following the base element. Consequently, its byte offset is four under the stated 32-bit layout. The four-byte selection stride is explicit; it is not evidence that every other ABI property is known.

The table-base field is integer-sized, not an established native-pointer-sized field. The selected address is formed through integer arithmetic and then interpreted as an address. Treating the base field as a native pointer and performing ordinary pointer indexing would introduce representation and arithmetic assumptions not established here.

For the 32-bit cases below:

- The signed integer range is −2,147,483,648 through 2,147,483,647.
- The selector’s signed integer conversion controls the negative-selector rejection and ordering comparison.
- Pointer-shaped equality is a separate comparison and must not automatically be replaced by equality of the converted integers.

Native pointer width, integer-width confirmation from the original ABI, byte order, alignment requirements, and exceptional conversion behavior remain documented-only uncertainties.

### Path-dependent preconditions

Successful execution requires readable storage only along the path actually taken:

| Path | Required readable storage |
|---|---|
| Selector converts to a negative signed integer | None from the descriptor or table |
| Nonnegative selector is excluded by the boundary | Boundary word |
| Selector is admitted for inspection | Boundary word, base word, selected integer entry |

The function does not validate these access preconditions. An admitted selector is not proof of a valid address or an in-bounds allocation access.

Descriptor and table storage are not required by the local body to be distinct. Any overlap must still permit the required reads.

## Behavior

### Eligibility contract

A selector whose signed integer conversion is negative is rejected. That path returns normally without reading either descriptor field and without calling either dependency.

For a nonnegative selector, eligibility depends on the boundary in two distinct ways:

- The selector must not compare equal to the pointer-shaped value obtained from the stored boundary.
- The selector’s signed integer value must be no greater than the boundary’s signed integer interpretation.

Both conditions matter. Their usual simplification to a strict numeric upper bound is valid only when the relevant pointer and integer representations correspond in the ordinary way.

Under that ordinary interpretation:

| Relationship | Inspection outcome |
|---|---|
| Selector negative | No descriptor or table inspection |
| Selector equal to boundary | No entry inspection |
| Selector greater than boundary | No entry inspection |
| Selector nonnegative and less than boundary | One entry is inspected |

A zero or negative boundary therefore admits no selector in those ordinary cases. A positive boundary can admit selector zero.

Boundary rejection requires no base-word read. An inaccessible base word does not affect a path that successfully reads the boundary and then rejects the selector.

The boundary is not checked against allocation size, mapped memory, or any independently known table extent.

### Selected entry

An admitted selector identifies an address by adding a byte displacement of four times its signed integer value to the stored integer base. This describes the intended mathematical address calculation only where the represented integer operations and address conversion have a defined, usable result.

Exactly one selected integer is examined. There is no scan, neighboring-entry inspection, or dereference of a pointer stored in the selected entry.

The entry has only two relevant classes:

- **Zero:** normal return without dependency calls.
- **Nonzero:** dependency response, without distinguishing positive values from negative values.

The entry is not changed by the local body.

### Arithmetic boundaries

Eligibility does not ensure arithmetic safety.

For a signed 32-bit interpretation, selector 536,870,911 has a four-byte displacement of 2,147,483,644, which fits within the positive signed range. Selector 536,870,912 has a mathematical displacement of 2,147,483,648, which does not.

Even a representable displacement can produce an unrepresentable sum when combined with the stored base. Conversely, a representable integer sum does not establish that converting it to an address yields valid readable storage.

The function provides no explicit overflow check, alternate calculation, or recovery path. The evidence does not establish wrapping, trapping, or any other particular outcome for exceptional arithmetic.

### Dependency response and completion

A successfully read nonzero entry causes F-ee5919ca4be6 to be invoked without explicit arguments. If that call returns control to this function, F-feee9156a257 is invoked, also without explicit arguments.

The second dependency is marked as non-returning in the supplied representation. Its actual control-transfer mechanism is unknown.

The entry decision is final before either invocation. Changes made during the first dependency do not cause another eligibility check or entry read. In particular, setting the selected entry to zero does not prevent the second invocation when the first dependency returns control.

A nonzero entry does not guarantee that both dependencies execute: the first dependency may not return control. No ordinary-return guarantee is established after the nonzero response begins.

## Side effects

### Observable reads and their order

The local storage-access contract is:

1. Boundary observation, for a nonnegative selector.
2. Base observation, only when the selector is admitted.
3. Selected-entry observation, after the base has been obtained.
4. Dependency invocation, only after the selected entry has been observed as nonzero.

The represented body obtains the boundary once and reads the selected entry once. It does not reread either for consistency. No descriptor or table read is established after either dependency invocation.

These are properties of the represented local accesses, not guarantees about processor speculation, memory barriers, atomic transactions, or synchronization.

No selector-designated memory is read. Its pointer-shaped representation alone does not require it to identify a readable object.

### Writes and ownership

The local body performs no explicit caller-visible store, allocation, release, reference-count update, or ownership transfer. Its direct use of descriptor and table storage is read-only.

That local fact does not make the complete operation read-only. Dependency effects are unknown. Neither dependency may be assumed to preserve:

- Descriptor or table contents.
- Global or thread-local state.
- Allocation lifetimes.
- Ownership relationships.
- References available through implicit execution context.

The lack of explicit arguments does not rule out access through globals or other implicit inputs. It also does not establish that either dependency owns, borrows, retains, or releases any particular object.

If a dependency invalidates descriptor or table storage, there is no subsequent local access to that storage in the supplied body. This observation does not establish that the invalidation is permitted by surrounding contracts.

### Errors and concurrent changes

There is no local error status or recovery mechanism for an unreadable boundary, unreadable base, invalid selected address, exceptional conversion, arithmetic failure, or dependency failure.

The contract does not prescribe a particular signal, exception, diagnostic, or termination result for those conditions.

No locking or coherent-snapshot mechanism is established. Boundary, base, and entry are separate observations. Concurrent mutation may prevent them from describing a consistent table state; the evidence does not establish a supported concurrent-mutation protocol.

## Uncertainties

### Inferred intent

The ordinary eligibility rule supports interpreting the boundary as an exclusive limit. It does not establish a count, capacity, allocation length, or guarantee that all admitted entries exist.

The nonzero response may represent an assertion, diagnostic, cleanup action, or termination request, but none of those purposes is established.

### documented_only: representation

The original ABI is unavailable. Four-byte selector spacing is explicit; the full integer and pointer data model is not independently confirmed.

In particular, the evidence does not settle:

- Native pointer width.
- Complete pointer-to-integer and integer-to-pointer conversion behavior.
- Whether distinct pointer-shaped values can acquire the same signed integer interpretation.
- Byte order and alignment restrictions.
- Exceptional arithmetic and address-conversion outcomes.

A high-bit pointer-shaped selector is rejected as negative only when its signed conversion produces a negative value. A strict numeric upper bound is not a universal substitute for the separate pointer-shaped equality and signed ordering requirements.

### documented_only: dependencies and environment

Dependency implementations are unavailable. Their state changes, ownership effects, diagnostics, and completion behavior remain unresolved.

The second dependency’s non-returning annotation does not identify whether it terminates execution, transfers control through an exception, or uses another mechanism. Behavior contrary to that annotation is not established.

Fault delivery, special-memory effects, asynchronous interruption, and concurrent mutation remain environment-dependent.

## Evidence

- Two pointer-shaped inputs and no explicit result.
- Numeric use of the selector without dereferencing selector storage.
- Rejection of negative signed selector conversions before descriptor access.
