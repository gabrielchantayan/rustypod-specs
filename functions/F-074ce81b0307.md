# F-074ce81b0307

## Purpose

F-074ce81b0307 either updates a status flag in a supplied object or prepares its embedded record and conditionally links that record into a global list.

Established behavior has two principal paths:

- A nonzero result from an initial dependency selects a short path that assigns an object Boolean from a global byte’s zero/nonzero state.
- A zero result selects a preparation path. Two subsequent dependency results gate further processing. If both are nonzero, the function updates an object field and checks whether to process the embedded record further.

For an unmarked record, a nonzero interval-like field enables arithmetic and list insertion. A zero interval skips insertion but does not skip the subsequent notification and conditional dispatch.

“Preparation,” “interval,” “deadline,” “marker,” and “notification” are descriptive or inferred roles, not established dependency contracts. The visible evidence establishes accesses, call order, branch conditions, arithmetic, and link updates. It does not establish time units, chronological ordering, locking, or ownership transfer.

The function accepts one address-bearing input identifying an object. The supplied representation uses a 32-bit integer for that input and 32-bit addresses for derived accesses.

There is no exposed return value. Normal exits are void returns. Observable results are memory mutations and dependency interactions.

### Global indirection and retained addresses

Two distinct global roles require explicit indirection rules:

- **List-head-holder global:** contains the address of a writable 32-bit head slot. The function captures this address after the arithmetic value-provider returns, before writing `0x38` and `0x48`. It later reads and, for head insertion, writes the head through that retained address.
- **Shared dispatch-holder global:** contains an address that is passed as the argument to F-338d16f9ce72. Later, after F-5bcae2eff9a7, the function reads this same global again and dereferences the resulting address to obtain a pointer used in the dispatch condition.

These globals have different roles. In particular, the shared dispatch-holder global is not the list-head-holder global.

## Behavior

### 1. Initial status selection

The function first invokes F-637aeef1c8a7 without visible arguments.

If the result is nonzero, it reads a byte through a global-held address and stores whether that byte is nonzero into the object’s Boolean field at `0x5C`. It then returns.

The byte is read after the dependency returns; effects of that dependency can therefore influence the assigned Boolean. No later preparation, insertion, notification, or dispatch sequence is explicitly executed on this path.

If the result is zero, execution continues without an explicit write to `0x5C`.

### 2. Preparation and two gates

The longer path performs these calls in order:

1. F-936a8728139d with the embedded-record address at object offset `0x30`.
2. F-6904f7699031 with that address and a value read from a global.
3. F-29cbc89bd185 with the object address.

A zero result from F-29cbc89bd185 causes an immediate return. Otherwise, F-0ad803819e72 is called with the object address. A zero result from this second gate also causes an immediate return.

Only zero versus nonzero matters for both gates. There is no visible interpretation of separate error codes, diagnostic emission, or rollback. Effects of earlier calls remain in place.

### 3. Post-gate update and marker check

After both gates return nonzero, the function retains the embedded-record address and invokes F-936a8728139d for the second time.

This invocation has no visible argument in the supplied representation. It must not be silently treated as another explicit call with the embedded-record address. Its argument convention remains unresolved.

After this second invocation returns:

1. A global 32-bit value is read and written to object offset `0x50`.
2. The 32-bit marker at offset `0x4C` is read.

A nonzero marker causes a return. Thus an already-marked object still undergoes the preparation calls, both gates, the second F-936a8728139d invocation, and the explicit `0x50` write. It does not undergo the following unmarked-record processing or final notification sequence.

The marker is evaluated at this point, not captured at function entry. Dependency mutations, and any valid aliasing of preceding accesses, can affect the value observed.

### 4. Unmarked-record preparation

For a zero marker, the function:

1. Reads the shared dispatch-holder global and passes that value to F-338d16f9ce72.
2. Calls F-add44d4e9aaa with the embedded-record address.
3. Reads the 32-bit field at object offset `0x34`.

The first call receives the shared global’s value, not a pointer loaded from the storage that value designates.

If `0x34` is zero, the function skips the value-provider call, arithmetic writes, list traversal, and explicit insertion writes. It nevertheless proceeds to notification and dispatch checking.

If `0x34` is nonzero, its value is retained for the following arithmetic.

### 5. Arithmetic, holder capture, and head acquisition

For a nonzero interval-like value, the observable sequence is:

1. Invoke an unidentified dependency that supplies a 32-bit value.
2. Read the list-head-holder global and retain the address it contains.
3. Multiply the previously read interval-like value by 1000, add the supplied value, and write the result to object offset `0x38`.
4. Read another global 32-bit value and write it to object offset `0x48`.
5. Read the list head through the retained head-holder address.

The interval-like field is not re-read after the value-provider call. Changes to `0x34` during that call do not replace the retained arithmetic operand.

The holder capture is likewise significant. The address used for the head read is captured **before** the writes to `0x38` and `0x48`, but the head itself is read **after** both writes. Consequently:

- A write that aliases the global containing the holder address does not redirect this operation’s later head access.
- A write that aliases the captured head slot can affect the head subsequently read from that slot.
- The global value used for `0x48` is obtained after the `0x38` write; independence under aliasing must not be assumed.

Arithmetic is represented using 32-bit integer operands and a 32-bit destination, without visible overflow detection or saturation. Exact overflow semantics are not established. Examples requiring an exact numeric result below use operands whose product and sum are representable as signed 32-bit integers.

### 6. Traversal and insertion

Traversal begins with the head just read. For each non-null candidate, F-0d70d6f9010c receives:

- The address eight bytes into that candidate.
- The address of the new record’s field at object offset `0x38`.

A zero result advances past the candidate. Any nonzero result stops at that candidate; positive and negative results are not distinguished.

When advancing, the function reads the candidate’s successor after the comparison returns and retains that candidate as the predecessor. Comparator effects can therefore change the successor that is followed. The new arithmetic field is supplied by address, so the function does not establish that all comparisons observe its originally stored value.

Traversal stops at a nonzero comparison result or at null. Insertion then performs these writes in order:

1. If no candidate was passed, write the embedded-record address through the **previously captured head-holder address**. Otherwise, write it into the retained predecessor’s first word.
2. Write the 32-bit value 1 to object offset `0x4C`.
3. Write the stopped-at candidate address, possibly null, to object offset `0x30`.

There is no reload of the list-head-holder global before a head insertion, including after comparator calls. A comparator that changes that global does not redirect this function’s head-link write. Conversely, changes to the old captured slot can be overwritten by that write.

The new record is exposed through the incoming link before its successor is explicitly updated, with the marker write between them. No atomic-publication or concurrent-reader guarantee is established.

There is no visible cycle detection, duplicate search, or validation that the marker agrees with actual list membership. Comparator semantics do not establish ascending order, descending order, or treatment of equal values.

### 7. Notification and conditional dispatch

After unmarked-record processing, whether insertion occurred or was skipped:

1. A global value is read and passed to F-5bcae2eff9a7.
2. The shared dispatch-holder global is read again.
3. The resulting holder address is dereferenced to obtain a condition pointer.
4. If that pointer is non-null, its first 32-bit word is read.
5. If both the condition pointer and that word are nonzero, an indirect global target is invoked without visible arguments.
6. Otherwise, the function returns without that invocation.

The shared global in step 2 is the **same global** whose earlier value was passed to F-338d16f9ce72. The later read is fresh, not a retained copy of the earlier argument. F-338d16f9ce72, F-add44d4e9aaa, the value provider, comparator calls, F-5bcae2eff9a7, and intervening memory writes may affect the holder or storage reached through it.

A null condition pointer suppresses its own dereference. A null holder address is not guarded before the holder dereference.

The condition pointer’s first word is only a zero/nonzero condition. It is not shown as the indirect call target. The indirect invocation and its calling convention remain unresolved beyond the visible call site.

## Side effects

Conditional explicit object writes occur at `0x5C`, `0x50`, `0x38`, `0x48`, `0x4C`, and `0x30`. Insertion also writes either the captured global head slot or an existing node’s successor.

No allocation, release, copying of the full object, or ownership-transfer operation is explicit. Linking publishes an address inside the object to a global list. That storage must remain valid while subsequently accessed through the list, but the lifetime owner and removal protocol are unknown.

Dependencies must not be assumed to preserve globals, object fields, list links, or pointed-to storage. Their call placement does not prove resource acquisition, release, or synchronization.

There is no explicit rollback. Early returns preserve prior effects. This function has no visible local recovery mechanism for invalid memory, nonreturning dependencies, corrupt lists, or indirect-call failure.

## Acceptance examples

These are conditional static expectations, not execution results. They assume valid storage, returning dependencies, representable arithmetic where relevant, and no unspecified interfering effects.

1. **Short-path flag.** A nonzero initial selector result followed by a zero global byte assigns false at `0x5C`; a nonzero byte assigns true. No later explicit call sequence occurs.

2. **First gate rejection.** A zero F-29cbc89bd185 result occurs after the first two preparation calls. F-0ad803819e72, the second F-936a8728139d invocation, and the explicit `0x50` write do not occur.

3. **Second gate rejection.** A zero F-0ad803819e72 result prevents the second F-936a8728139d invocation and the `0x50` write.

4. **Already-marked record.** If both gates succeed and the marker is nonzero when checked, the second F-936a8728139d invocation and `0x50` write have occurred, but unmarked-record processing and notification do not occur.

5. **Zero interval.** If the marker is zero and the field at `0x34` is zero after F-add44d4e9aaa, no value-provider call, comparator call, or explicit insertion-block write occurs. Notification and dispatch checking still occur.

6. **Empty-list insertion.** With interval 2, supplied value 500, and a null head read through the captured holder, `0x38` becomes 2500. No comparison occurs. The head slot receives the embedded-record address, the marker becomes 1, and the successor becomes null, in that order.

7. **Insertion between nodes.** If the first comparison returns zero and the second returns any nonzero value, with no intervening relevant mutation, insertion places the new record after the first node and before the second.

8. **Captured holder survives global replacement.** Suppose the head-holder address is captured as one valid slot and a comparator subsequently changes the global to name another slot. If insertion is before the original first candidate, the original captured slot receives the new record address. The replacement slot is not selected by reloading that global.

9. **Capture precedes object writes.** If the `0x38` write aliases the global containing the head-holder address, later head access still uses the address captured before that write. This does not guarantee the contents of the captured slot are unchanged.

10. **Shared-holder re-read.** Suppose F-338d16f9ce72 receives one holder address, but F-5bcae2eff9a7 changes the shared global to a different valid holder. Dispatch checking uses the latter holder and its current stored pointer, not the earlier argument.

11. **Dispatch conditions.** A valid holder containing null suppresses dispatch without reading a condition word. A non-null condition pointer containing zero also suppresses dispatch. A non-null condition pointer containing a nonzero word selects the indirect invocation.
