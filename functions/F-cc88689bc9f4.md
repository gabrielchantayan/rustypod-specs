# F-cc88689bc9f4

## Purpose

F-cc88689bc9f4 coordinates a database-rebuilding operation through an attached auxiliary database. It temporarily changes connection flags, attaches and configures the auxiliary database, performs ordered preparation requests, transfers four adjusted metadata values, invokes a two-handle operation, and conditionally finalizes both handles.

Every normally returning path converges on cleanup. Cleanup restores the saved connection flags, writes a transaction-state byte, conditionally clears two fields of the auxiliary attachment entry, and invokes a final connection operation.

**Established static evidence:** the supplied representation establishes the field accesses, widths, call ordering, conditional execution, status handling, and explicit writes described below.

**Inferred intent:** the diagnostic and visible command descriptions identify a VACUUM-style operation. The auxiliary database appears to hold a rebuilt image. Transfer direction, locking, rollback, persistence, and ownership semantics are not established by the caller.

**Verification status:** static analysis only. No runtime tests have been performed. Acceptance examples are conditional requirements, not observed executions.

## Interface

### Arguments

The function receives four machine-level arguments:

| Argument | Represented width | Established role |
|---|---:|---|
| Diagnostic context | 32 bits | Passed to the diagnostic dependency on active-transaction rejection. |
| Connection address | 32 bits | Addresses mutable connection state and is passed to connection-level dependencies. |
| Initial metadata value | 32 bits | Initializes a local scratch slot subsequently passed by address to metadata reads. |
| Initial configuration value | 32 bits | Initializes a local slot that is replaced before any consequential use. |

These roles do not establish a public-language signature. Address-bearing values are represented as 32 bits; wider-address portability is unknown.

The initial metadata value can matter if a successful metadata reader leaves the scratch slot unchanged. The caller neither initializes that slot again between iterations nor verifies that a reader wrote it. Whether leaving it unchanged is permitted by the dependency is unknown.

The fourth argument has no demonstrated influence on subsequent calls or the return value: paths that use its scratch slot first replace its contents with a computed difference.

### Return value

The function returns a 64-bit packed result:

- Bits 63–32: the original 32-bit connection-address argument.
- Bits 31–0: the selected 32-bit status bit pattern.

Zero in the low word indicates that all checked operations reached on the successful path returned zero. Active-transaction rejection produces status **1**. Either initial configuration failure, or a nonzero configuration gate, produces status **7**. Other checked failures retain their returned status bit patterns.

The high word is not a newly created object or a dependency result.

### Preconditions

Defined operation requires valid addresses, accessible fields, usable handles, and storage that remains valid across dependencies. The caller performs no explicit null, bounds, attachment-count, or address-overflow checks.

Successful attachment must leave an attachment layout suitable for selecting the last entry. Dependencies must return normally for the subsequent control flow described here to occur. No guarantee is established for exceptions, faults, nonlocal exits, or invalidated retained addresses.

## Behavior

### 1. Temporarily change flags and inspect transaction state

The first relevant shared-memory operations are:

1. Read and retain the connection’s entire 32-bit flag word.
2. Write that word with bits **0x2800** set.
3. Read the transaction-state byte at +0x1C.

If the transaction-state byte is zero, invoke F-2cb24bca4183 with the diagnostic context, a diagnostic indicating that VACUUM cannot run within a transaction, and zero. Ignore its result, select status **1**, and proceed to cleanup.

Thus, the temporary flag write precedes even the rejection diagnostic. The diagnostic dependency may observe the modified flags.

Any nonzero transaction-state byte permits attachment processing.

### 2. Attach and retain the auxiliary entry

Read the original handle from the first attachment entry before issuing the attachment request.

Invoke F-95e6e7a9a92a with the connection and the visible request to attach an empty-named database as `vacuum_db`. If it returns nonzero, preserve that status and enter cleanup. No auxiliary-entry address has been selected for explicit cleanup.

On success, reread the connection’s attachment-array address and count. Select the last entry using:

**array address + count × 24 − 24**

Retain that entry’s address and its handle. The original handle remains the value captured before attachment; it is not refreshed from the possibly changed array.

The count is not checked for zero. The computation uses represented 32-bit address-bearing arithmetic; invalid counts, overflow, and invalid resulting addresses are unsupported rather than diagnosed.

### 3. Configure the auxiliary handle

Invoke F-0b4658e20c99 on the original handle. Its result does not control this function.

Read the original handle’s subordinate configuration fields at +0x1C and +0x1E as unsigned 16-bit quantities. Form the first minus the second and retain its 32-bit result.

The mathematical range is **−65,535 through 65,535**. The represented subtraction uses unsigned widened operands; negative mathematical differences therefore have the corresponding 32-bit result pattern. No clamping or range rejection appears.

Invoke F-96dd78c4ca33 on the original handle, ignoring its result.

Next, reread the original handle’s subordinate address and its 16-bit field at +0x1C. Invoke F-6ab8cec4fac2 with:

1. The retained auxiliary handle.
2. That newly read 16-bit field.
3. The retained 32-bit difference.

The field supplied here and the fields used to calculate the difference need not reflect one snapshot: an intervening dependency has no established preservation contract.

If this configuration call returns nonzero, select status **7** and enter cleanup.

Otherwise, invoke F-6ab8cec4fac2 again with the auxiliary handle, the connection’s current 32-bit field at +0x24, and the retained difference. A nonzero result again becomes status **7**, not the dependency’s original status.

Only if both calls return zero, read the unsigned gate byte at connection offset +0x1E. A nonzero gate selects status **7**. A zero gate permits preparation.

### 4. Run ordered preparation requests

Invoke F-95e6e7a9a92a with the visible request to disable synchronous behavior for `vacuum_db`. Propagate a nonzero result to cleanup.

On success, read the connection setting byte at +0x21. Under the represented signed interpretation, a negative value causes F-3f6a3abf1d81 to supply the setting. Otherwise, use the byte-derived value directly. Pass the selected setting and auxiliary handle to F-cf5d64798e84. Its result does not govern continuation.

The following calls are then attempted in order:

1. F-95e6e7a9a92a with the visible exclusive-transaction request.
2. Six calls to F-c1cb71515dbf, each with the connection and the value of its corresponding opaque global expression.
3. One call to F-95e6e7a9a92a with the connection and the value of a further opaque global expression.

Each call must return zero before the next call is reached.

The seven opaque preparation arguments are **separately evaluated global expressions**, not established immutable payloads. Each expression is evaluated when its call is reached, after preceding dependencies have returned. Different source locations do not establish different argument values. Dependencies may change globals or referenced storage; no global-preservation contract is available.

Immediately after the final opaque F-95e6e7a9a92a call returns, the function reads and retains the metadata-table reference from its global storage. **This reference read precedes the test of that call’s status and occurs even when the status is nonzero.**

If that final call failed, its status is then propagated to cleanup without accessing table bytes. Failures in earlier preparation calls prevent both the final call and this table-reference read.

### 5. Process four metadata records

Table-byte access occurs only if the final opaque preparation call returned zero. The reference used is the one captured immediately after that call; the global reference is not reread for each record.

Process records at offsets 0, 2, 4, and 6, in that order. For each record:

1. Read the selector byte and invoke F-70fe47664dff with the original handle, that selector, and the address of the metadata scratch slot.
2. On a nonzero result, preserve the status and enter cleanup.
3. On success, reread the selector byte and read the unsigned adjustment byte.
4. Invoke F-676079dace64 with the auxiliary handle, the reread selector, and the scratch value plus the adjustment.
5. On a nonzero result, preserve the status and enter cleanup.

No fifth record is processed.

The selector is read twice, with a dependency call between reads. The metadata writer need not receive the selector previously passed to the reader if the table bytes change. The adjustment is also read after the reader returns. No stronger ordering between the writer’s argument reads is established.

The adjustment lies between **0 and 255**. Addition produces a 32-bit result pattern, with no overflow check or saturation; carry beyond bit 31 is not retained.

The same scratch slot is reused throughout. Its initial contents come from the third argument, and its later contents depend on what each reader writes. A successful reader is not independently checked for output initialization.

### 6. Invoke the two-handle operation and finalize

After all four records succeed, invoke:

1. F-0b4658e20c99 on the original handle.
2. F-0b4658e20c99 on the auxiliary handle.
3. F-8996df13e56e with the original handle first and auxiliary handle second.
4. F-96dd78c4ca33 on the auxiliary handle.
5. F-96dd78c4ca33 on the original handle.

The two F-96dd78c4ca33 calls occur before testing the two-handle operation’s status. They therefore occur even when that operation fails. Their results do not replace its status.

If F-8996df13e56e returned zero, invoke F-8b4833f8202a on the auxiliary handle. If that succeeds, invoke the same dependency on the original handle.

Only if both finalizations succeed, reread the auxiliary handle’s current subordinate address and 16-bit field at +0x1C. Invoke F-6ab8cec4fac2 with the original handle, that field, and the retained difference.

This last configuration result becomes the selected status without normalization to 7. Failure at an earlier checked step prevents later checked steps in this stage.

“Transfer,” “finalize,” and possible acquisition/release pairing describe inferred roles, not established dependency semantics.

### 7. Perform common cleanup

All represented normally returning paths perform these operations in order:

1. Restore the saved entire 32-bit connection flag word.
2. Write **1** to the transaction-state byte at +0x1C.
3. If the retained auxiliary-entry address is nonzero:
   - Read its current handle field at +0x04.
   - Invoke F-7446dea3e07b with that value.
   - Write zero to the entry’s handle field.
   - Write zero to the entry’s field at +0x14.
4. Invoke F-aacdb1821b51 with the connection and zero.
5. Return the packed connection-address/status result.

The cleanup condition tests the retained entry address, not the handle value. There is no separate nonzero-handle test.

Restoring the entire flag word overwrites intervening changes to it. The transaction-state byte is not restored to its entry value: the explicit cleanup write is always 1, including after active-transaction rejection.

The cleanup handle is reread from the retained entry rather than taken from the cached auxiliary handle. Those values can differ.

Cleanup dependency results do not replace the selected status. Their effects remain unknown. In particular, the final dependency executes after all explicit shared-memory writes, so those writes do not establish the connection’s final state after return.

## Side effects

Explicit nonlocal writes comprise:

- The temporary flag-word update and later full-word restoration.
- The cleanup write of 1 to the transaction-state byte.
- The two zero writes to a nonzero retained auxiliary-entry address.

A metadata reader receives a writable address into local scratch storage. Retention of that address beyond the call is not established as valid.

Dependencies may additionally alter globals, table bytes, connection fields, attachments, database contents, allocation state, locks, or transactions. The caller supplies no general preservation guarantee.

No explicit allocation or deallocation primitive appears. Passing a handle to F-7446dea3e07b does not establish destruction, reference counting, memory release, or ownership transfer. The following zero write establishes only that this caller clears the stored reference.

Cleanup is not proof of rollback or atomicity. Failures can occur after preparation requests, metadata writes, the two-handle operation, or one successful finalization.

## Acceptance examples

Examples assume valid storage and normally returning dependencies unless stated otherwise.

1. **Active transaction:** With transaction-state byte zero, the flag update precedes the diagnostic. No attachment request occurs. Cleanup writes transaction state 1, and the returned low word is 1.

2. **Attachment failure:** If attachment returns 12, the low word is 12. No auxiliary-entry cleanup occurs because its address was not selected. Connection cleanup still runs.

3. **Configuration rejection:** If either initial F-6ab8cec4fac2 call fails, the low word is 7. If the first fails, the second is skipped. The gate is read only after both succeed.

4. **Preparation short circuit:** If the third F-c1cb71515dbf call fails, later preparation expressions are not evaluated for their calls. The final opaque call, metadata-table reference read, metadata-byte reads, and transfer stage are skipped.

5. **Mutable preparation globals:** If an earlier dependency changes the value used by a later preparation expression, that later call receives the value evaluated when reached. Equal values from different expressions do not violate this contract.

6. **Final preparation failure:** If the final opaque preparation call returns 19, the metadata-table reference is nevertheless read before status 19 directs execution to cleanup. No table selector or adjustment byte is accessed.

7. **Metadata arithmetic:** A scratch value of 100 and adjustment 3 produce 103. A scratch bit pattern of 0xFFFFFFFF and adjustment 1 produce 0x00000000. A failing writer prevents all later records and the transfer stage.

8. **Changed selector:** If the reader returns zero but changes its record’s selector, the writer receives the reread selector, not necessarily the reader’s selector.

9. **Transfer failure:** A nonzero F-8996df13e56e result is followed by F-96dd78c4ca33 on auxiliary then original handle. Neither finalization call occurs.

10. **Full success:** All four records, the two-handle operation, both finalizations, and final original-handle configuration execute. If every checked result is zero, the returned low word is zero. The high word remains the original connection address.
