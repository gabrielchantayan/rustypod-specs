# F-e23b7384348d

## Purpose

F-e23b7384348d dispatches a 32-bit event selector to operations on a receiver object. Depending on the selector, it invokes an opaque dependency, invokes a virtual method, stores an extracted event value, performs a bounded lookup, acknowledges an event without further action, or reports that the event was not handled.

The normal return value is a 32-bit status: **1 for a recognized path and 0 for a fallback path**. Recognition does not establish that a delegated operation succeeded. Dependency return values are generally ignored.

The supplied static evidence does not establish application-level meanings for the selectors, receiver fields, or dependencies. Descriptions such as “event,” “receiver,” and “lookup” identify structural roles, not confirmed domain semantics.

## Behavior

### Dispatch precedence and integer interpretation

The selector is read as a signed 32-bit integer. Dispatch first distinguishes:

1. Selector equal to **T**.
2. Selector less than **T**.
3. Selector greater than **T**.

The less-than partition is further divided by **B** and by **A + 3**. Those signed comparisons control reachability. An explicit hexadecimal selector is not an unconditional global mapping: its action applies only if the preceding comparisons lead to its containing branch.

Selector arithmetic includes **B + 1**, **A + 3**, and **A + 4**. No wider intermediate or range check is visible. Values that would overflow signed 32-bit arithmetic require an additional target-arithmetic assumption; this contract does not assign them portable behavior.

Before dispatch, the function captures **H** and initializes a local 32-bit extraction cell from the original fourth argument. Subsequent extraction does not initialize that cell from the rewritten fourth argument.

### Exact match at T

For selector **T**, invoke:

**F-7ae779eeaeea(receiver, 0, original third argument, original fourth argument)**

Then return 1.

This match takes precedence over every lower or upper dispatch rule.

### Event-value extraction

Both extraction paths invoke the event's virtual method at offset `0x08`, supplying the event and the address of the local 32-bit extraction cell.

The cell initially contains the original fourth argument. The extraction method's return value is ignored. On normal return:

- Selector `0x63800008` stores the resulting cell value at receiver offset `0x730`.
- Selector `0x63800025` passes the resulting cell value to F-7998b5b0038d.

The receiver write occurs after extraction returns. If extraction leaves the cell unchanged, the consumer receives the original fourth argument. This function does not distinguish that situation from successful extraction.

### Bounded lookup

The lookup path first reads a 32-bit word through the pointer at event offset `0x0c`. If that word is zero, it returns 1 immediately, without performing any lookup dependency calls.

For a nonzero word, the following operations occur in order:

1. Obtain an object from **F-938c950e5046()**.
2. Invoke that object's virtual method at `0xe8`, passing the object and **R**.
3. Pass the returned value and `0x1700` to **F-682adfd5a561**, obtaining a second object.
4. Pass the payload word to **F-0f333381a04d**, obtaining a third object.
5. Invoke the third object's virtual method at `0x14`. No explicit arguments are shown for this invocation. Its 32-bit result becomes the comparison target.
6. Invoke the second object's virtual method at `0x170`, passing that object. Interpret its result as an unsigned 32-bit starting position.

The search endpoint is the starting position plus 5, modulo \(2^{32}\). Before each candidate, the function requires the candidate to be unsigned-less-than that endpoint. If not, it returns 1 without notification.

For each admitted candidate:

- Candidate zero is skipped without calling the comparison dependency.
- For a nonzero candidate, read the receiver word at `0x30` and invoke **F-c47b877c6f23(that word, candidate − 1)**.
- Compare the returned 32-bit value with the previously obtained target.
- On equality, stop searching and invoke the receiver virtual method at `0x74`, passing **receiver, N, Q, candidate**, then return 1.
- Otherwise advance the candidate by one.

For a starting position at most `0xfffffffa`, five candidate positions are admitted. If the start is zero, only four comparison calls occur because position zero is skipped. For starts `0xfffffffb` through `0xffffffff`, endpoint addition wraps and the initial bound check rejects the search immediately.

There is no “not found” return status distinct from successful notification: both return 1.

### Ordered receiver virtual calls

For `0x6380002b`, invoke the receiver method at virtual-table offset `0x58` twice:

1. **receiver, current H, L**
2. **receiver, entry-captured H, M**

The first invocation completes before the second begins. The receiver's virtual dispatch information is resolved again for the second call; it must not be assumed unchanged.

The second call's **H** argument comes from the entry snapshot, not a post-call reload. Its **M** argument is obtained for that second invocation. If the first call changes external state, the second call may therefore combine an old **H** value with a changed **M** value or a changed virtual target.

## Side effects

The only explicit persistent data write visible in the function body is the extraction-path store to receiver offset `0x730`. The extraction method can also write the local cell through its supplied pointer.

All direct dependencies and virtual methods may have additional effects. Their effects, including changes to receiver fields, external words, object lifetimes, or virtual tables, are not constrained by this function's visible body.

In particular:

- Receiver offset `0x30` is read anew for each nonzero lookup candidate. It is not a search-wide snapshot.
- The lookup target and endpoint are retained across comparison calls.
- Virtual-method return values are ignored except where explicitly used to obtain objects, the lookup target, or the starting position.
- No explicit allocation, release, reference-count adjustment, or ownership transfer is shown.

The absence of an explicit release does not establish a leak. Dependencies may return borrowed objects or manage lifetimes internally. Conversely, nothing establishes that they retain objects or preserve the validity of subsequent accesses.
