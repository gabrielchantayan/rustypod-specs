# F-f17b5e0d319d

## Purpose

F-f17b5e0d319d obtains a node, copies an eight-byte value into its payload, attaches it to a tree-like structure, performs color-based repair, and writes the new node’s address to a caller-provided output slot.

The established structure and repair decisions are consistent with insertion into a red-black tree with a header holding the root and both extrema. That interpretation is **inferred intent**, not proof of the behavior of the node-acquisition or rotation dependencies.

This function does not search for an insertion parent, reject duplicate values, or validate the supplied attachment location. Successful ordered-tree insertion therefore depends on caller-supplied placement information and on dependency behavior not established here.

## Interface

The function has five inputs and no explicit return value:

| Input | Representation | Role |
|---|---|---|
| Result slot | Address of a writable four-byte slot | Receives the acquired node address after repair completes. |
| Container | 32-bit address | Identifies the container and is passed to several dependencies. |
| Placement selector | 32-bit integer | Any nonzero value selects left attachment without comparison. Zero permits comparison unless the parent is the header. |
| Attachment parent | 32-bit address | Node or header under which the acquired node is attached. |
| Value source | Address of at least two readable four-byte words | Supplies the eight-byte payload and is passed to the comparison dependency when needed. |

Pointer values and link fields are represented as 32-bit quantities in the supplied evidence. Colors are accessed as single bytes. The evidence does not establish endianness or general alignment rules.

## Behavior

### 1. Acquire a node and initialize its payload

The function first calls F-1c004ce19fed with the container address.

It then tests whether the returned address plus `0x10` is nonzero. If so, it performs these operations in order:

1. Read the first four-byte word from the value source.
2. Write that word to the node at `+0x10`.
3. Read the second four-byte word from the value source at `+0x04`.
4. Write that word to the node at `+0x14`.

This is not an atomic eight-byte copy or a guaranteed snapshot of both source words. If the first destination write aliases the second source word, the second read observes the intervening write.

The address test is **not a reliable null-node check**. A zero node address does not make “node address plus `0x10`” zero. Conversely, under wrapping 32-bit address arithmetic, the address `0xfffffff0` would make the tested sum zero and suppress the payload writes. The evidence does not establish whether that arithmetic situation has defined execution semantics.

Even when the payload writes are skipped, the function continues with count mutation, attachment, and node-field accesses.

### 2. Increment the count

After the payload-copy stage, the function reads the four-byte count at container `+0x14`, adds one, and writes it back.

This happens before comparison, link insertion, or balancing. There is no local rollback if a later operation fails or does not return.

The supplied representation uses a signed 32-bit count operation. No saturation, overflow check, or rejection is present. Exact behavior at signed overflow is **documented_only**: the evidence does not justify promising either defined wraparound or a particular failure mode.

### 3. Choose the attachment side

The function reads the current header address from container `+0x10`.

It selects left attachment without calling the comparator if either:

- The attachment parent equals that header address; or
- The placement selector is nonzero.

Otherwise it calls F-bcefa5957e76 with:

1. Container address plus `0x19`;
2. The original value-source address;
3. Attachment-parent address plus `0x10`.

Any nonzero result selects left attachment. Zero selects right attachment. The meaning of this result as “less than” is inferred, not established by this function alone.

The comparator receives the original source address, not the new node’s payload address. This distinction matters if the source has changed or aliases earlier writes.

The comparator can also affect later behavior through shared-state changes. The function does not preserve an immutable header snapshot across this call.

### 4. Attach the node and update header links

**Left attachment**

The function first writes the acquired node address to the attachment parent’s `+0x08` field.

It then reads the container’s header address again:

- If the header equals the attachment parent, it writes the acquired node address to that header’s `+0x04` field, then rereads the header address from the container and unconditionally writes the acquired node address to its `+0x0c` field.
- Otherwise, it examines the header’s `+0x08` field and replaces it with the acquired node address only if it currently equals the attachment parent.

Thus, under an unchanged header, insertion beneath the header sets its root, leftmost, and rightmost links to the new node.

**Right attachment**

The function writes the acquired node address to the attachment parent’s `+0x0c` field.

It then reads the header address from the container, examines the header’s `+0x0c` field, and replaces that field only if it equals the attachment parent.

**Parent link**

After the applicable attachment and header updates, the function writes the attachment-parent address to the acquired node’s `+0x04` field.

The function does not itself initialize the new node’s child links or initial color before repair. Those properties must come from F-1c004ce19fed or existing storage contents.

### 5. Repair color and structural relationships

Repair begins with the acquired node as the current repair node.

At each iteration, the function rereads the header and its root link. Repair stops if the current repair node is that root. Otherwise, it reads the current node’s parent and stops if the parent’s color byte is nonzero.

When the parent’s color is zero, repair examines the grandparent and determines whether the parent is the grandparent’s left child.

**Parent is the left child**

The uncle is the grandparent’s right child.

- If the uncle is nonzero and has color zero, the function writes color one to the parent, then color one to the uncle, then color zero to the grandparent. It continues repair from that grandparent.
- If the uncle is absent or has nonzero color:
  - If the current node is its parent’s right child, the function calls F-9e1830833494 on the container and parent. It then makes that previous parent the current repair node.
  - Using the links present after that optional call, it writes color one to the current node’s parent, writes color zero to that parent’s parent, and calls F-45138fcd9aa3 on the container and that grandparent.

**Parent is not the left child**

This branch treats the grandparent’s left child as the uncle. It does not independently verify that the parent is the grandparent’s right child.

- If that uncle is nonzero and has color zero, the same ordered recoloring occurs: parent to one, uncle to one, grandparent to zero. Repair continues from the grandparent.
- Otherwise:
  - If the current node is its parent’s left child, the function calls F-45138fcd9aa3 using the container and parent, with additional supplied arguments described under Dependencies. It then makes that previous parent the current repair node.
  - Using the resulting links, it writes color one to the current node’s parent, writes color zero to that parent’s parent, and calls F-9e1830833494 on the container and that grandparent.

The two structural dependencies are consistent with opposite-direction rotations. Their precise pointer updates are not established by the provided body.

After structural repair calls, the loop condition is evaluated again. There is no explicit iteration limit or malformed-tree detection.

### 6. Finalize and publish the result

When repair exits, the function rereads the container’s header and its root link, then writes color one to that root.

Only afterward does it write the originally acquired node address to the result slot.

The result is the inserted node, not necessarily the root or the final repair node. No success flag, comparison outcome, or count is returned.

## Side effects

Directly observable writes, in their principal order, are:

1. Up to two four-byte payload writes.
2. A four-byte count increment.
3. The attachment link.
4. Conditional or unconditional header-link updates, according to the attachment case.
5. The new node’s parent link.
6. Repair-time color writes, interleaved with dependency calls.
7. A final color-one write to the currently referenced root.
8. A four-byte result-slot write.

Dependency effects occur at their call positions and are not limited by this function.

There is no explicit release, destruction, rollback, diagnostic, or error return. F-1c004ce19fed may allocate, reuse, or otherwise obtain storage; its ownership contract is unknown. Calling it does not establish who must eventually release the node.

The function provides no synchronization and performs multi-step mutations. It does not establish safe concurrent observation or atomic insertion.

Aliasing can be significant. For example, if the result slot aliases a structural field, the final output write can overwrite that field after balancing. A normal-use contract should require noninterfering storage rather than assume undocumented alias safety.

## Acceptance examples

These are conditional specification examples, not executed tests.

### Header insertion

Given a stable header used as the attachment parent, valid node storage, and dependencies that preserve the expected structure:

- The comparator is not called, regardless of placement-selector value.
- The payload is copied before the count increment.
- The header’s leftmost, root, and rightmost fields become the acquired node address.
- The node’s parent becomes the header.
- Repair exits immediately because the new node is the root.
- The root color becomes one before the result slot receives the node address.

### Forced left attachment

Given a non-header parent and any nonzero placement selector:

- No comparison is performed.
- The parent’s left-child link is replaced.
- The header’s leftmost link changes only if it equals that parent.
- The parent’s right-child link is not directly changed by the attachment step.

Any later structural changes depend on repair and its callees.

### Comparison-selected right attachment

Given a zero placement selector, a non-header parent, and a comparator returning zero:

- The comparator runs after payload writes and count increment.
- The parent’s right-child link receives the new node.
- The header’s rightmost link changes only if it equals that parent.
- The new node’s parent field is written after these attachment updates.

### Recoloring with a zero-colored uncle

Given a non-root current node, zero-colored parent, and present zero-colored uncle:

- The parent and uncle receive color one in that order.
- The grandparent receives color zero.
- Repair continues from the grandparent.
- No rotation dependency is called for that iteration’s recoloring branch.

### Nonzero parent color

Given a current node that is not the root and whose parent color is nonzero:

- Repair stops without inspecting an uncle.
- The currently referenced root still receives color one.
- The result slot still receives the original acquired node address.

### Overlapping payload storage

Given valid overlapping source and destination storage where the first payload write changes the second source word:

- The second payload word is read after that modification.
- An eight-byte pre-copy snapshot is not an acceptable substitute.

### Interrupted dependency

If a dependency does not return normally, completion is not established. Earlier writes may already be visible, and neither rollback nor a final result-slot write is promised.
