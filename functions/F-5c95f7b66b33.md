# F-5c95f7b66b33

## Purpose

F-5c95f7b66b33 conditionally changes a one-byte field at offset +4 from a caller-supplied base address. It performs that change only when its ordered observations of the bytes at offsets +3 and +4 are both zero.

The decision is bracketed by calls to two dependencies, each receiving the address at offset +68 from the same base. Their actual behavior is not established. In particular, this contract does not assume that they acquire and release a lock, preserve surrounding memory, or preserve ownership.

On an ordinary completed execution, the function returns one of two 32-bit bit patterns:

- `0x00000000`: the qualifying zero-byte observations occurred, and the function performed its direct one-byte write.
- `0xFFFFFFFF`: the qualifying observations did not occur, and the function performed no direct write to either inspected field.

The result reports the branch taken within this function. It does not guarantee that the written value remains present after the final dependency call.

### Output

The return value is explicitly four bytes wide. Its defined ordinary-return values are:

|---|---|

## Behavior

### Observable order

For an execution in which both dependencies return normally and all required accesses succeed, the function’s direct behavior follows this order:

1. Call F-338d16f9ce72 with B + 68.
2. Read one byte at B + 3.
3. If that observed byte is nonzero, skip the read and write at B + 4.
4. If the observed byte at B + 3 is zero, read one byte at B + 4.
5. If both observed bytes are zero, write the one-byte value `0x01` to B + 4 and select the zero result.
6. Otherwise, retain the `0xFFFFFFFF` result without a direct field write.
7. Call F-1333331b2da1 with B + 68.
8. Return the selected 32-bit result.

The two dependency calls occur on every ordinary branch. Neither call’s return value is used to decide whether to inspect or modify the fields.

### Conditional reading

The read at B + 4 is conditional. It is absent when the observed byte at B + 3 is nonzero.

This distinction matters if reading B + 4 is externally observable, unsupported, or sensitive to access order. A replacement that always reads both bytes would not preserve the direct access behavior established here.

The comparisons distinguish zero from nonzero only. All nonzero byte patterns have the same effect, including values whose signed-byte interpretation would be negative. No ordering comparison or byte arithmetic is involved.

### Conditional writing

The only direct memory modification visible in this function is a one-byte write of `0x01` to B + 4.

That write occurs only after:

- The first dependency has returned.
- The function has observed zero at B + 3.
- The function has subsequently observed zero at B + 4.

The write is not an increment, a bitwise update, or a read-modify-write operation. It replaces the destination byte with the exact value `0x01`. No direct write to B + 3 is present.

### Separate observations, not a snapshot

The function does not reread B + 3 after reading B + 4. It also does not revalidate either condition before its write.

Consequently, the zero return is based on two ordered observations. It does not independently establish that the two bytes were simultaneously zero, that B + 3 remained zero until the write, or that B + 4 remained zero between its read and the write.

If the dependencies provide synchronization respected by other actors, stronger guarantees might follow from that external contract. They are not established here. Without such guarantees, concurrent access may also be invalid under the surrounding execution model; this function alone does not resolve that issue.

### Return selection versus final state

The second dependency is called after the branch decision and any direct write. The function performs no subsequent direct verification of the fields.

A zero result therefore means that this function performed the qualifying write, not that B + 4 necessarily equals `0x01` at return. The second dependency could change the field or its containing storage if its contract permits that behavior.

Likewise, `0xFFFFFFFF` means that this function did not perform the direct field write. It does not establish that neither dependency changed memory.

## Side effects

### Established direct effects

The direct effects are limited to:

- One call to F-338d16f9ce72 with B + 68.
- One one-byte read at B + 3.
- A conditional one-byte read at B + 4.
- A conditional one-byte write of `0x01` at B + 4.
- One call to F-1333331b2da1 with B + 68.

The function contains no visible direct allocation, deallocation, logging, callback registration, or global-variable access.

### Dependency effects and ownership

Both dependency calls may have effects not represented by the direct field accesses. Their behavior cannot be narrowed from the supplied material.

Passing B + 68 establishes an address argument, not an ownership transfer. It does not establish that either dependency borrows, retains, releases, allocates, or frees the addressed storage.

Similarly, the absence of direct global access does not establish absence of global effects: either dependency may access globals or external state.

The function resumes field access after the first call without validating the base again. Valid execution therefore depends on that call leaving the subsequent accesses permissible. Whether it actually does so is an external requirement, not a proven dependency guarantee.

### Failure handling

No local recovery or error translation is visible.

If the first dependency does not return normally, the later field accesses and second call are not guaranteed. If a direct access fails, the second call is likewise not guaranteed. If the second dependency does not return normally, no ordinary return value is produced.

The visible call structure must not be described as guaranteed cleanup during exceptional exit.

## Acceptance examples

These examples are conditional specifications, not reported test results. Except where stated otherwise, they assume valid storage, normal dependency returns, no intervening external modification, and dependencies that leave the condition bytes unchanged.

### First condition rejects the operation

After the first dependency returns:

- B + 3 contains `0x02`.
- The contents of B + 4 are irrelevant to the branch.

Expected behavior:

- Read B + 3.
- Do not directly read or write B + 4.
- Call the second dependency.
- Return `0xFFFFFFFF`.

The same result and direct access pattern apply to every other nonzero first-byte value.

### Second condition rejects the operation

After the first dependency returns:

- B + 3 contains `0x00`.
- B + 4 contains `0x80`.

Expected behavior:

- Read B + 3, then B + 4.
- Perform no direct write.
- Call the second dependency.
- Return `0xFFFFFFFF`.

The high bit in the second byte does not change the zero/nonzero decision.

### Both observations qualify

After the first dependency returns, both condition bytes contain `0x00`.

Expected behavior:

- Read B + 3, then B + 4.
- Write exactly one byte, `0x01`, to B + 4.
- Call the second dependency.
- Return `0x00000000`.

Under the stated unchanged-storage assumptions, B + 3 remains zero and B + 4 remains one.

### Repeated call without resetting the field

Starting from both bytes zero, a first call returns zero and leaves B + 4 equal to one under the assumptions above.

A second call then reads zero at B + 3 and one at B + 4. It performs no direct write and returns `0xFFFFFFFF`.

This illustrates a conditional transition from zero to one, not an unconditional setter.

### First dependency changes the decision inputs

Suppose the bytes are nonzero at entry, but the first dependency makes both zero before returning.

If the subsequent reads observe those zeros, the function performs the write and selects zero. Entry-time values are not the decision inputs.

### Second dependency changes the written field

Suppose both reads observe zero and the function writes `0x01`, but the second dependency then replaces B + 4 with another value.

If that dependency returns normally, the function still returns zero. There is no final field check that would revise the selected result.
