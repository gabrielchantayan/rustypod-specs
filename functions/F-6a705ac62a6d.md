# F-6a705ac62a6d

## Purpose

F-6a705ac62a6d conditionally submits a 32-byte operation record and, after submission returns, advances a caller-supplied horizontal position.

Preparation determines whether the operation proceeds and may replace the candidate object used for subsequent accesses. Successful preparation leads to record construction from workspace fields, position cells, and signed metrics reached through tagged references.

Placement or drawing is **inferred intent**. The established contract concerns preparation, memory accesses, record contents, dependency arguments, and the final position update. No graphics API, resource class, or coordinate convention is established.

## Behavior

### Preparation and continuation

The original-reference word is captured before either dependency runs. Later mutation of that cell does not replace the captured word used for the original metric.

F-acff1e21fa9a receives the workspace address first. F-16d4150c28a2 then receives:

- The workspace address.
- The context.
- The original-reference cell address.
- The address of the mutable local candidate slot.
- The preparation value.

A zero result from F-16d4150c28a2 ends the operation. There is no submission, successful-path metric access, or direct position update. Effects already produced by either dependency remain.

Every nonzero result permits continuation. No further interpretation of that result is established.

A replacement candidate controls subsequent candidate-header access and the candidate-derived submission argument. Changing the local slot does not itself overwrite a caller-side address variable or the candidate object.

### Metric correction

On continuation, the original primary metric is read first. The function then reads the current candidate’s reference word and its primary metric. Both signed 16-bit metrics are sign-extended for comparison.

The correction is zero when the original primary metric is at least the candidate primary metric. Otherwise, it is the positive difference narrowed to signed 16-bit and then sign-extended again.

The positive difference ranges from 1 through 65,535, so its subtraction fits signed 32-bit arithmetic. Narrowing can nevertheless change its value or sign. The supplied material does not establish the target’s out-of-range signed-conversion rule.

For example, under low-16-bit, two’s-complement interpretation, a difference of 60,000 produces a correction of −5,536. This is conditional on that interpretation; neither saturation nor retention of the full positive difference is established.

The masked candidate metric base is retained. Subsequent metric reads do not obtain a new base from the candidate header.

### Record contract

At submission entry, the local record has the following layout:

| Byte offset | Width | Content |
|---|---:|---|
| 0 | 32 bits | Zero |
| 4 | 32 bits | First bound |
| 8 | 32 bits | Selected extent |
| 12 | 32 bits | Second bound |
| 16 | 32 bits | Vertical start |
| 20 | 32 bits | Horizontal start |
| 24 | 32 bits | Vertical end |
| 28 | 32 bits | Horizontal end |

Coordinate and extent fields are signed 32-bit quantities. There is no bound normalization, clipping, minimum extent, or rejection of reversed coordinates.

The vertical adjustment is captured once before extent selection and reused for both placement decisions. The extent is **not** captured once for all uses.

For stable workspace contents, selected extent is the workspace extent unless both that extent and the captured vertical adjustment are zero. In that exceptional case, selected extent is the sum of fresh candidate primary and secondary metric reads. Those reads are separate from the primary read used for correction.

Two signed 16-bit metrics sum to a value between −65,536 and 65,534, which fits signed 32-bit arithmetic.

### Repeated workspace observations

The distinction between a stable workspace and separate reads is part of the contract:

- When the captured vertical adjustment is zero, an extent read determines whether metric-derived extent is selected.
- A separate extent read supplies the ordinary record extent, even when metric fallback subsequently replaces that field.
- The decision governing vertical placement uses another extent read when the captured vertical adjustment is zero.
- Workspace-derived vertical placement reads the extent again for the vertical end.

Consequently, the selected-extent decision and vertical-placement decision are not established as one shared decision. Under stable contents they agree; without that stability, their agreement is not guaranteed.

The first and second bounds are copied into the record, then read again for horizontal-span calculation. Equality between the recorded bound difference and the constructed horizontal span therefore also requires stable bound values.

These distinctions identify separate accesses in the supplied static body. They do not establish support for concurrent mutation or impose volatile-access semantics.

### Horizontal coordinates

With stable inputs, horizontal start is the horizontal position plus the second and first horizontal adjustments. Horizontal end is that start plus the second bound minus the first bound.

Each adjustment is sign-extended from signed 16-bit. The horizontal position is read once for record construction; horizontal end reuses the constructed horizontal start.

Negative adjustments remain negative. Reversed bounds can produce an end smaller than the start. Intermediate signed overflow is not repaired by a later addition that would bring the mathematical result back into range.

Horizontal construction occurs before vertical construction.

### Vertical coordinates

When the captured vertical adjustment and the extent observed for the vertical-placement decision are both zero, placement is metric-derived:

- Vertical start is one vertical-position read minus a fresh candidate primary metric, plus the correction.
- Vertical end is a separate vertical-position read plus a fresh candidate secondary metric, plus the correction.

These metric reads are independent of the reads used to select the record extent. Under stable positions and metrics, the vertical span equals the metric-derived selected extent. That equality is not unconditional.

Otherwise, placement is workspace-derived:

- Vertical start is the vertical position minus the captured vertical adjustment, plus the correction.
- Vertical end is that start plus a newly read workspace extent.

This branch reads the vertical-position cell once. A nonzero vertical adjustment prevents metric fallback even when the observed extent is zero. Negative extents are retained.

Independent operand reads within an expression have no established left-to-right ordering.

### Final horizontal update

Only after submission returns does the function read the advance and reread the horizontal-position cell. The final store is their signed 32-bit sum, with the advance sign-extended from signed 16-bit.

Neither operand is a construction-time snapshot. Submission may change the horizontal position, and it may affect workspace state through a previously retained address or another reachable alias. A dependency’s explicit argument list does not prove preservation of either operand.

The order between the two operand reads is not established. Zero and negative advances receive no special handling. The submitted record is not recomputed after this update.

## Acceptance examples

These are **conditional static acceptance cases**, not runtime observations. Unless qualified otherwise, dependencies return normally, required storage is valid, construction inputs remain stable, and signed arithmetic is representable.

### Preparation declines

If F-16d4150c28a2 returns zero, both preparation calls have occurred in order. The original-reference word has already been read. No successful-path candidate metric or position access occurs, no submission occurs, and there is no direct position write. Dependency effects remain possible.

### Stable metric-derived placement

Assume original primary metric 10; candidate primary and secondary metrics 14 and 6; bounds 2 and 12; extent and vertical adjustment zero; horizontal adjustments 1 and 2; and positions 100 horizontally and 50 vertically.

The correction is 4. Submission receives this record:

| Initial word | 0 |
| First bound | 2 |
| Selected extent | 20 |
| Second bound | 12 |
| Vertical start | 40 |

| Vertical end | 60 |
| Horizontal end | 113 |

If the post-submission horizontal-position read is 100 and the post-submission advance read is 7, the final store is 107. An advance of 7 observed only before submission is insufficient to establish that result.

### Workspace-derived placement

Using the preceding stable inputs but an extent of 8 produces selected extent 8, vertical start 54, and vertical end 62.

With extent zero and vertical adjustment 3 instead, selected extent remains zero and both vertical coordinates are 51. Metric fallback is disabled by the nonzero adjustment.

### Changed post-submission operands

If construction uses horizontal position 100 but submission leaves that cell at 250, a post-submission advance of 7 produces a final store of 257.

If submission instead leaves the position at 100 and the post-submission advance is −3, the final store is 97, regardless of an earlier advance value.

### Candidate replacement and reference capture

If preparation replaces the candidate, subsequent candidate-header and metric accesses use that replacement, and submission receives its address increased by twelve bytes.

If preparation also changes the original-reference cell, the original primary metric still derives from the word captured before preparation, provided the captured reference remains valid.

### Narrowed correction

For original primary −30,000 and candidate primary 30,000, the difference is 60,000. Under low-16-bit, two’s-complement narrowing, the correction is −5,536. Other target conversion rules remain unresolved.

### Different extent observations

If the environment permits distinct values at separate extent reads, an initial zero can select metric-derived record extent while a later nonzero value selects workspace-derived vertical coordinates. Conversely, record extent may be workspace-derived while later vertical placement is metric-derived.

These cases describe the absence of a shared extent snapshot; they do not assert that concurrent mutation is supported.
