# F-d9ac9f18580c

## Purpose

F-d9ac9f18580c performs an in-place link transformation that promotes a node’s first child into that node’s former position. The original node becomes the promoted node’s second child, and the promoted node’s former second child becomes the original node’s first child.

Under the conventional interpretation that the first child is the left child and the second child is the right child, this is a right rotation. That interpretation is inferred intent. The established behavior is the field-access and mutation sequence specified below.

The operation also updates either a separately stored root link or one child link in the original node’s parent. It performs no validation, allocation, release, balancing-metadata update, or external function call.

## Interface

The function receives two address-valued arguments:

- **Context address:** identifies storage containing a root-holder address at byte offset 16.
- **Target address:** identifies the node to be displaced by its first child.

There is no explicit return value and no reported success or failure status.

All listed fields are accessed as 4-byte quantities. Offsets are byte offsets from the relevant base address.

“Parent,” “first child,” “second child,” and “root” describe the roles suggested by the accesses. The routine does not check that the stored relationships form a tree.

The supplied representation uses integer-typed arguments and address-bearing 4-byte fields. A 32-bit address model is therefore indicated, but an authoritative ABI description is not supplied. This contract does not extend the routine to native-width pointers on a wider-address platform.

No complete object size, alignment declaration, payload layout, or ownership convention is established. The largest observed field offset is not proof of an allocation’s full size.

### Preconditions for a well-formed structural operation

For the ordinary, nonoverlapping-node interpretation:

## Behavior

### Established access and mutation order

The following sequence describes the accesses visible in the supplied function representation. Reads described separately must not be silently combined when reasoning about overlapping storage or externally changing memory.

1. **Select the promoted node.**  
   Read the target’s first-child field. Retain that address as the promoted node for the rest of the operation.

2. **Replace the target’s first child.**  
   Read the promoted node’s second-child field. Write that 4-byte value into the target’s first-child field.

3. **Conditionally repair the transferred child’s parent.**  
   Read the promoted node’s second-child field again and compare it with zero.

   If this read is nonzero, read that same field once more to obtain the destination node address, then write the target address into that node’s parent field.

   The branch test and destination selection are distinct reads. With stable, nonoverlapping storage they identify the same child. The routine itself does not ensure that stability.

4. **Give the promoted node the target’s current parent.**  
   Read the target’s parent field and write that value into the promoted node’s parent field.

5. **Locate and inspect the root field.**  
   Read the root-holder address from context offset 16. Read the field at root-holder offset 4 and compare it with the target address.

   This lookup occurs after the preceding child and parent writes. It is not an entry-time snapshot of the context.

6. **Reconnect the promoted node to the enclosing structure.**

   - If the root field equals the target address, write the promoted-node address into the root field.
   - Otherwise, read the target’s parent field again. Read that parent’s second-child field.
     - If it equals the target address, replace that second-child field with the promoted-node address.
     - Otherwise, write the promoted-node address into the parent’s first-child field.

   The fallback branch does not verify that the parent’s first-child field previously referred to the target.

7. **Make the target the promoted node’s second child.**  
   Write the target address into the promoted node’s second-child field.

8. **Finish the target’s parent link.**  
   Write the promoted-node address into the target’s parent field.

The function then returns without a value.

### Result under stable, distinct-object conditions

Let the entry-state relationships be:

- The target’s first child is the promoted node.
- The promoted node’s second child is the **transferred subtree**.
- The target’s parent is the **former parent**.

Assuming these objects and the root-holder storage do not overlap in ways that affect the accesses, and no other actor changes the fields during execution, the resulting relationships are:

| Relationship | Result |
|---|---|
| Target’s first child | Transferred subtree |
| Transferred subtree’s parent, if nonzero | Target |
| Promoted node’s parent | Former parent |
| Promoted node’s second child | Target |
| Target’s parent | Promoted node |
| Root or selected former-parent child link | Promoted node |

The target’s second-child field and the promoted node’s first-child field are not directly written. Payload and other metadata fields are not directly accessed.

For a root replacement, the promoted node inherits the target’s former parent-field value. There is no separate step forcing that field to zero. A null-parent convention, sentinel-parent convention, or other root-parent representation is preserved only through this copied value.

### Branch precedence

The root comparison takes precedence over inspecting the target’s parent. When the root field equals the target, the function does not follow the target’s parent to update an enclosing child link.

In the nonroot case, the parent’s second-child comparison takes precedence over the fallback first-child write. If both child fields refer to the target, only the second-child field is selected by this logic.

### Aliasing and concurrent changes

The compact result table applies only under its stated stability and distinctness conditions.

For example, writing the target’s first-child field can affect the subsequent reads of the promoted node’s second-child field if those locations overlap. Likewise, writing the promoted node’s parent field can affect the later context lookup or the later reread of the target’s parent if those storage locations overlap.

The routine contains no alias rejection, synchronization, retry, or rollback. Its ordered accesses, rather than an idealized tree transformation, define behavior where accessible storage overlaps. No atomicity or concurrent-reader safety is established.

## Side effects

The routine mutates caller-supplied storage in place. Its possible write locations are:

- Target first-child field.
- Parent field of the node selected by a nonzero reread of the promoted node’s second-child field.
- Promoted-node parent field.
- Either the root field or one child field of the parent selected in the nonroot branch.
- Promoted-node second-child field.
- Target parent field.

There are six stores when the transferred-child repair branch is taken and five when it is not. These counts describe executed stores, not necessarily distinct destinations when storage aliases.

The root-holder address stored in the context is read, not directly assigned by this function. Overlapping storage could nevertheless cause another store to affect it.

No allocation, deallocation, reference-count adjustment, callback, logging, or explicit external-global access appears in the supplied function. Node addresses are copied as 4-byte values; node contents are not copied wholesale.

No ownership transfer or lifetime guarantee is established. The function does not release any node, and callers must not infer that detached or reattached relationships alter ownership rules.

There is no structured error path. Invalid addresses, inaccessible fields, invalid arithmetic, or unsupported alignment have no specified recovery behavior here. Because writes precede several later reads, a failure partway through execution need not leave the structure unchanged.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless an example states otherwise, assume valid addresses, stable memory, distinct objects, and nonoverlapping fields.

### Root with a nonzero transferred subtree

Initially:

- The root field refers to the target.
- The target’s first child is the promoted node.
- The target’s parent is zero.
- The promoted node’s second child is another node.

Required result:

- The root field refers to the promoted node.
- The promoted node’s parent is zero.
- The promoted node’s second child is the target.
- The target’s parent is the promoted node.
- The target’s first child is the transferred node.
- The transferred node’s parent is the target.

The old target’s second child and the promoted node’s first child remain unchanged.

### Root with no transferred subtree

If the promoted node’s second-child field is zero throughout the relevant reads, the target’s first-child field becomes zero. No transferred-child parent store occurs.

The remaining root and parent changes proceed normally. A zero transferred subtree does not make the whole operation a no-op.

### Nonroot target in the parent’s second-child slot

If the root field does not equal the target and the target’s parent has its second-child field equal to the target, that second-child field becomes the promoted node.

The parent’s first-child field is not selected for an enclosing-link update. The promoted node receives the target’s former parent address.

### Nonroot target in the parent’s first-child slot

If the root field differs from the target and the parent’s second-child field differs from the target, the parent’s first-child field is overwritten with the promoted node.

This holds whether that first-child field previously contained the target or some other value. The function does not reject the latter inconsistency.

### Parent refers to the target in both child slots

If the target is nonroot and both parent child fields contain the target, the second-child field becomes the promoted node. The first-child field remains the target, absent aliasing effects.

This example captures branch precedence, not a guarantee that malformed input is repaired.

### Root with a nonzero parent representation

If the root field equals the target and the target’s parent contains a nonzero sentinel address, the promoted node receives that sentinel address. The function does not clear it or inspect the sentinel’s child fields through the nonroot branch.

### Missing promoted node

If the target’s first-child field is zero, the routine still attempts the promoted-node second-child read using that value as its base address. No checked failure result or no-op behavior is specified.

Such input is outside the ordinary valid-node preconditions.
