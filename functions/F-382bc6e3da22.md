# F-382bc6e3da22

## Purpose

F-382bc6e3da22 exposes two distinct recovered behaviors selected by an incoming processor carry condition:

- **Carry clear:** attempt an indirect call with three transformed inputs. If the call returns normally, execution reaches a region for which subsequent behavior is not recovered.
- **Carry set:** attempt a one-byte zero store at an address derived from an incoming unsigned 32-bit value, then repeatedly issue a coprocessor operation. The first operation receives a shifted version of the original value; later operations receive zero.

No application-level purpose is established. The evidence does not identify the addressed byte as a flag, establish an object layout, or show that the repeated operation implements initialization, synchronization, shutdown, or recovery.

This contract describes the supplied static representation, not independently verified executable behavior. Reports of invalid instruction data and removed control-flow regions limit confidence in the apparent function boundary and completeness.

## Interface

### Explicit inputs

The recovered interface presents four 32-bit argument slots:

| Input | Representation | Visible use |
|---|---|---|
| First argument | Opaque 32-bit quantity | Passed unchanged as the first indirect-call argument |
| Second argument | Opaque 32-bit quantity | No explicit use |
| Third argument | Opaque 32-bit quantity | No explicit use |
| Fourth argument | Unsigned 32-bit integer | Logically shifted right by two bits for the third indirect-call argument |

The absence of explicit uses for the second and third arguments does not establish that their associated machine state is irrelevant to an unresolved dependency. Only the visible argument data flow is established.

### Incoming machine state

The explicit argument list is insufficient to determine execution. The representation also depends on:

- An incoming carry condition.
- An incoming **unsigned 32-bit general-register value**, referred to below as the **base value**.
- An incoming link-register value used to derive an indirect-call target.
- Two incoming coprocessor-related operands, each represented as a 32-bit quantity.

“Original base value” means the incoming value before any visible update.

The carry condition is not computed from the explicit arguments in the recovered body. Carry clear selects the indirect-call path; carry set selects the store-and-loop path.

### Outputs and termination

No return value is declared, and no normal return is visible.

- On the carry-clear path, a normally returning dependency is followed by an unrecovered instruction region.
- On the carry-set path, the recovered loop has no exit.

These observations do not prove that every invocation runs indefinitely. An invalid transfer, memory fault, coprocessor exception, dependency action, or inaccurate control-flow recovery may prevent continued execution.

### Preconditions

No input validation or explicit error-reporting interface is visible.

Progress on the carry-clear path requires a usable indirect-call target and satisfaction of that target’s unknown requirements.

Progress on the carry-set path requires successful conversion of the computed 32-bit number to a usable byte address, writable storage at that address, and an environment in which the represented coprocessor operation can execute.

These are execution requirements, not checks performed by F-382bc6e3da22.

## Behavior

### Path selection

The first recovered decision examines the incoming carry condition. No explicit memory read, memory write, or state update precedes that decision in the supplied body.

The paths are mutually exclusive in the recovered control flow. In particular, the carry-clear path does not first perform the byte store, and the carry-set path does not first invoke the indirect dependency.

### Carry-clear path

The indirect-call target is derived by adding `0xEEC`, or 3,820, to the incoming link-register value.

The representation does not establish the complete machine-level semantics of this target calculation. Address-width handling, overflow treatment, instruction-set mode interpretation, alignment requirements, and behavior for an invalid target remain unresolved. The unsigned arithmetic rule established for the separate carry-set byte-address calculation must not be transferred to this calculation.

The attempted call has three visible arguments, in this order:

1. The first explicit argument, unchanged.
2. The original base value shifted left by three bits, with a 32-bit unsigned result.
3. The fourth explicit argument logically shifted right by two bits.

For the second call argument, bits shifted above bit 31 are discarded. The numerical result is the original base value multiplied by eight modulo \(2^{32}\).

For the third call argument, the high bits are filled with zero and the low two bits are discarded. The numerical result is unsigned division by four, rounded down. Its range is zero through `0x3FFFFFFF`.

The ordering above describes argument positions, not an independently established order of evaluating the argument expressions.

No explicit memory access is shown on this path before the indirect call. This does not restrict accesses or effects performed by the dependency, including memory allocation, release, global-state changes, or processor-state changes.

If the dependency returns normally, the recovered representation stops at invalid or undecodable instruction data. That boundary does not establish a deliberate halt, an error return, or a callable error-reporting routine. Subsequent execution is unknown.

No separate handling is visible for a dependency that faults, does not return, or redirects execution elsewhere.

### Carry-set address calculation and store

The first visible action is a one-byte zero store through an address derived from the original base value.

The address calculation has two distinct stages:

1. Add ten to the original unsigned 32-bit base value, producing an unsigned 32-bit result **modulo \(2^{32}\)**.
2. Convert that result to a byte pointer and attempt the store.

The numerical wrapping is established. For example, an original base value of `0xFFFFFFFC` produces the 32-bit number `0x00000006`, not `0x100000006`.

What remains unresolved is whether the resulting number converts to a usable address, what storage it identifies, whether that storage is writable, and how a failed access is handled. Numerical wrapping does not imply that the resulting address is valid.

The store writes exactly one byte with value zero. There is no visible preceding read of that byte and no bounds, null, accessibility, or alignment check.

The ten-byte displacement does not establish a containing object’s size or layout. The evidence supplies no additional fields, ownership relationship, or application meaning for the byte.

### Carry-set repeated operation

After the byte store, the recovered sequence enters an unconditional loop.

For the first iteration:

- The outgoing data value is the original base value logically shifted right by eleven bits.
- The tracked general-register value is then replaced with zero.
- The coprocessor operation is issued with the already computed outgoing data value.

The first outgoing value ranges from zero through `0x001FFFFF`. It is zero for original base values from `0x00000000` through `0x000007FF`.

For each subsequent iteration, the recovered data flow uses the zeroed tracked value, so the outgoing data is zero. The tracked value is again assigned zero before the operation.

The coprocessor operation has fixed numeric selectors 8, 5, and 4, together with the computed 32-bit data and the two incoming 32-bit coprocessor-related operands. These values describe the represented operation interface; they do not establish the operation’s hardware meaning.

There is no visible reassignment of the two coprocessor-related operands. Their reuse in the representation does not prove that external processor state remains unchanged.

The loop contains no further byte store, explicit memory reread, wait condition, or exit test. If every operation completes normally and the recovered control flow is accurate, repetition continues indefinitely.

## Side effects

### Memory and ownership

On the carry-set path, one explicit byte write is attempted before the loop. Its destination is obtained by converting the unsigned 32-bit result of adding ten modulo \(2^{32}\) to the original base value. The stored value is zero.

Thus, arithmetic overflow changes the numerical destination by wrapping; it is not an unresolved aspect of this path. Pointer conversion, address validity, accessibility, and fault behavior remain unresolved.

No allocation, deallocation, copying, retention, or ownership transfer is visible in this body. Writing through a derived pointer does not establish ownership of the addressed storage.

The carry-clear dependency’s effects are unknown. It must not be assumed to preserve globals, avoid allocation, retain memory, release memory, or leave caller-visible state unchanged.

### Register and coprocessor state

On the carry-set path, the tracked general-register value becomes zero before the first coprocessor operation and is repeatedly assigned zero thereafter in the recovered loop.

The coprocessor operation may affect processor or hardware state. Its effects, completion conditions, privilege requirements, and exception behavior are not established.

No return-state preservation guarantee is recoverable because no normal return is visible.

### Ordering and failures

The established sequence on the carry-clear path is:

- Select the path.
- Derive the call target and argument values.
- Attempt the indirect call.
- If it returns normally, reach unrecovered execution.

The established sequence on the carry-set path is:

- Compute the wrapped 32-bit destination number and attempt the byte store through its pointer conversion.
- Compute the first shifted outgoing value from the original base value.
- Clear the tracked general-register value.
- Issue the first coprocessor operation.
- Repeat with zero-valued outgoing data.

This is recovered execution order, not a hardware memory-ordering or barrier guarantee.

If the initial store faults, no coprocessor operation has been reached in the represented sequence. If a coprocessor operation faults, no recovery path is visible. Exception-handler behavior is outside the established contract.

## Acceptance examples

These are conditional static expectations, not runtime test results. They assume that execution reaches the relevant operation and that preceding operations complete where necessary.

### Carry clear: ordinary argument transformation

Given carry clear, a first explicit argument of `0x11223344`, an original base value of `0x00000103`, and a fourth explicit argument of `0x0000000B`, the visible indirect-call arguments are:

1. `0x11223344`
2. `0x00000818`
3. `0x00000002`

This establishes neither target validity nor dependency behavior.

### Carry clear: left-shift truncation

Given an original base value of `0xE0000001`, the second visible call argument is `0x00000008`.

The upper three bits are discarded. An unbounded multiplication result would not satisfy the recovered 32-bit behavior.

### Carry clear: unsigned right shift

Given a fourth explicit argument of `0xFFFFFFFF`, the third visible call argument is `0x3FFFFFFF`.

A sign-extending shift or upward-rounded division would not match this result.

### Carry set: nonzero first outgoing value

Given carry set and an original base value of `0x00001800`:

- The destination calculation produces `0x0000180A`.
- If conversion yields a writable byte address, one zero byte is stored there.
- If execution proceeds, the first coprocessor operation receives computed data `0x00000003`.
- Later operations receive computed data zero.
- The loop does not repeat the byte store.

### Carry set: wrapping destination calculation

Given carry set and an original base value of `0xFFFFFFFC`:

- Adding ten produces the unsigned 32-bit number `0x00000006`.
- The attempted byte-store destination is obtained by converting that number to a byte pointer.
- No claim is made that this pointer is usable or writable.
- If the store completes and execution proceeds, the first coprocessor data is `0x001FFFFF`, computed from the original base value rather than the wrapped destination number.
- Later outgoing data is zero.

Using a destination number of `0x100000006`, or using `0x00000006` as the input to the first right shift, would contradict the recovered arithmetic and data flow.

### Carry set: zero first outgoing value

Given carry set and an original base value of `0x000007FF`, the destination calculation produces `0x00000809` and the first computed coprocessor data is zero.

This zero result neither removes the preceding store nor terminates the loop.

### Carry set: failed initial store

If the initial store faults, the represented sequence has not yet issued a coprocessor operation. Any exception dispatch or handler effects remain outside this contract.
