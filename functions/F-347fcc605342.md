# F-347fcc605342

## Purpose

F-347fcc605342 traverses a sequence of link addresses and returns the first current link for which F-6449293f84f1 returns a nonzero result. If the starting link is null, or advancement reaches null without selection, it returns null.

This is an established dependency-controlled traversal. Interpreting it as a key lookup, comparison, or search for a particular record is inferred intent: the dependency’s selection criteria are not supplied.

The selected address is the current link address. It is not the address supplied as the dependency’s third argument, which is 16 bytes before that link.

## Interface

| Item | Width and role |

| First input | A signed 32-bit integer used as an address base and in arithmetic. For each nonnull current link, the function reads a signed 32-bit integer at this base plus 4 bytes. |
| Second input | An address identifying a readable 4-byte slot. The slot’s contents provide the starting link address. |

| Result | A null pointer, or the current link address associated with the first nonzero dependency result. |

The supplied representation uses 4-byte link slots, 4-byte integer fields, and address-bearing values loaded from those slots. This establishes the represented widths for this contract, not a complete platform ABI.

### Directly accessed layout

The function directly requires:

- A readable 4-byte starting-link slot at the second input.
- A readable signed 32-bit field at the first input’s base plus 4 bytes whenever the current link is nonnull.
- A readable 4-byte next-link slot at the current link address whenever the dependency returns zero.

The address passed as the dependency’s third argument is 16 bytes before the current link. This relationship does not establish the size, type, or complete layout of any surrounding object.

No non-aliasing condition is established. The starting-link slot, the base-relative integer field, and any visited next-link slot may identify the same storage. Distinct logical roles must not be treated as proof of distinct addresses.

### Preconditions

The starting-link slot must be readable even when it contains null. A null second input is not an empty-list sentinel: the function attempts to read through it.

For each nonnull current link:

- Computing the base-plus-4 address and reading its 4-byte integer must be valid.
- The signed arithmetic used to construct the first dependency argument must be valid for the execution model.
- Forming an address 16 bytes before the current link must be valid.
- The dependency’s own requirements for all three arguments must hold.

After a zero dependency result, the current link address must remain valid for the next-link read. No supplied dependency contract guarantees this.

A next-link read is not required after a nonzero dependency result. Selection alone therefore does not establish that the current link’s next-link slot is readable or that the returned address remains usable.

## Behavior

### Starting-link acquisition

The function first reads the 4-byte slot identified by the second input and interprets its contents as the current link address.

Initialization reads that slot once in its role as the source of the starting link. There is no separate initialization-role reload during traversal. This does **not** mean that the storage at that address can be read only once: subsequent integer-field or next-link accesses may reach the same storage through aliases.

If the acquired link is null, the function immediately returns null. On this path it does not:

- Read the base-relative integer field.
- Invoke F-6449293f84f1.
- Read a next-link slot.

The first input therefore need not identify readable memory on the empty path, provided the initial slot itself is readable.

### Processing a nonnull link

For each nonnull current link, the function reads the signed 32-bit integer at the first input’s base plus 4 bytes.

It constructs the dependency’s first argument by adding this integer to the original base value, then adding 1. The added 1 is a numeric increment corresponding to one byte in the address-oriented interpretation, not one 4-byte element.

The dependency receives, in order:

1. The derived base-relative value.
2. The original opaque 32-bit third input.
3. An address 16 bytes before the current link.

The 16-byte displacement follows from moving backward by four elements of 4 bytes each.

The base-relative integer is read anew before every dependency invocation. It is not captured once for the entire traversal. A previous dependency call can therefore affect a later first argument by modifying that field, including through an alias.

The supplied expression uses signed 32-bit integer arithmetic for the base-relative calculation. Neither overflow nor modulo-\(2^{32}\) address wrapping is established as supported behavior. Conditional acceptance requires valid address formation and representable intermediate arithmetic.

### Result handling and advancement

The dependency’s result is a signed integer used only for a zero/nonzero decision.

For a nonzero result:

- Traversal stops.
- The function returns the current link address.
- It does not perform a subsequent next-link read for that visit.
- It does not return the dependency’s result or the address 16 bytes before the link.

Positive and negative nonzero results have the same selection effect.

For a zero result:

- The function reads the 4-byte slot at the current link address.
- That slot’s contents become the next current link.
- A null value ends traversal with a null return.
- A nonnull value leads to another integer-field read and dependency invocation.

The next-link read occurs after the dependency returns. Under ordinary sequential execution, a dependency modification to that slot affects the advancement if the storage remains readable.

### Aliasing and mutation

Aliasing affects the meaning of the access sequence without adding a separate reload operation.

If the starting-link slot is also a visited next-link slot, a later advancement reads that storage again in its next-link role. For example, if the starting slot is at address A and contains A, initialization selects A as the current link. A dependency call that writes C into A and returns zero causes the subsequent next-link read to obtain C. Traversal advances to C.

If the starting-link slot is also the base-relative integer field, the same storage is read during initialization and again before processing a nonnull current link. The latter read interprets its contents as a signed integer for argument construction.

If the integer field is also a next-link slot, writes to that storage can affect both later argument construction and traversal. The function does not preserve independent copies of those logical fields.

A modification to the starting-link slot has no separate mechanism for replacing an already acquired current link. Whether that modification affects subsequent behavior depends on whether later accesses reach that storage through an integer-field or next-link alias.

### Termination and invalid structures

The function has no visible traversal bound, cycle detection, cancellation check, or structural validation.

A finite chain terminates if every dependency invocation returns normally and either:

- One invocation returns nonzero; or
- Successive zero results lead to a null next link.

A cycle can terminate if the dependency selects a link or changes traversal state. A cycle that remains intact while all dependency calls return zero has no internal termination mechanism.

Unreadable storage, invalid address arithmetic, or invalid dependency arguments do not map to a defined error result in the supplied body. Null is a traversal outcome, not a general failure code.
