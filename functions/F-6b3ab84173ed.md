# F-6b3ab84173ed

## Purpose

F-6b3ab84173ed performs an in-place structural transformation on linked records. Under the conventional interpretation of their fields as parent, left-child, and right-child links, the transformation is a **right rotation around the record supplied as the second argument**.

The second argument identifies the pivot. Its left child is promoted into the pivot’s former position. The promoted record’s former right child becomes the pivot’s left child, and the pivot becomes the promoted record’s right child. The incoming link to the pivot is updated either through a distinguished root slot or through the pivot’s former parent.

The rotation interpretation is inferred intent. The established behavior is the ordered set of four-byte field accesses described below. The function does not establish ordering properties, verify that the records form a tree, or update balancing metadata.

## Interface

### Arguments and result

The function accepts two arguments represented in the supplied source as 32-bit integer values used as addresses:

- **Context:** An address from which the function obtains the address of a root-holder record.
- **Pivot:** The address of the record to transform.

The function has no explicit return value and no status output. Successful completion is observable through memory changes only.

The address interpretation depends on the original execution environment. The supplied representation supports a 32-bit address model; it does not establish portability to an environment with wider pointers.

### Referenced layouts

All listed offsets are byte offsets. Each accessed field occupies four bytes.

| Record | Offset | Access | Structural interpretation |
|---|---:|---|---|
| Context | 16 | Read | Address of the root holder |
| Root holder | 4 | Read; conditionally written | Distinguished root link |
| Pivot | 4 | Read; eventually written | Parent link |
| Pivot | 8 | Read and written | Left-child link |
| Promoted record | 4 | Written | Parent link |
| Promoted record | 12 | Repeatedly read; eventually written | Right-child link |

The **promoted record** is the address initially read from the pivot’s offset-8 field. The **transferred child**, when nonzero, is obtained from the promoted record’s offset-12 field.

The function does not access a field at offset 0. The evidence does not establish complete record sizes, allocation boundaries, packing rules, or meanings for any unaccessed fields.

### Preconditions

For a valid, ordinary rotation:

- The pivot must identify accessible storage.
- Its left-child link must identify an accessible promoted record. A zero left-child link is not handled as an empty case.
- The context must contain an accessible root-holder address at offset 16.
- The root holder’s offset-4 slot must be readable and, when selected for replacement, writable.
- Each field written on the selected path must be writable.
- A nonzero transferred-child link must identify a record whose offset-4 field is writable.
- On the non-root path, the pivot’s parent link must identify a record whose offset-12 field is readable and whose selected child field is writable.

A well-formed tree additionally requires coherent parent and child relationships. The function does not check those relationships.

These are conditions for safe and structurally meaningful use, not validations performed by the function.

## Behavior

### Source-level access order

The following order is established by the supplied source. It describes source-level accesses, not a guarantee about individual hardware transactions, compiler reloads, atomicity, or synchronization.

1. **Obtain the promoted record.**  
   Read the pivot’s offset-8 field and retain that four-byte address value as the promoted record.

2. **Replace the pivot’s left-child link.**  
   Read the promoted record’s offset-12 field and write its four-byte contents into the pivot’s offset-8 field.

3. **Repair the transferred child’s parent, when present.**  
   Read the promoted record’s offset-12 field again and compare it with zero.

   If it is nonzero, the source evaluates that field again to obtain the destination record, then writes the pivot address to that record’s offset-4 field.

   If it is zero, no transferred-child parent write occurs.

4. **Give the promoted record the pivot’s current parent link.**  
   Read the pivot’s offset-4 field and write its contents to the promoted record’s offset-4 field.

5. **Locate and inspect the distinguished root slot.**  
   Read the context’s offset-16 field. Treat its contents as the root-holder address and locate its offset-4 slot. Read that slot and compare its value with the pivot address.

6. **Replace the incoming link to the pivot.**
   - If the distinguished root slot equals the pivot address, write the promoted-record address into that slot.
   - Otherwise, read the pivot’s offset-4 field again to obtain the former parent. Read that parent’s offset-12 field.
     - If this right-child field equals the pivot address, replace it with the promoted-record address.
     - Otherwise, write the promoted-record address to the parent’s offset-8 field.

   The fallback does **not** check whether the parent’s offset-8 field currently refers to the pivot.

7. **Attach the pivot below the promoted record.**  
   Write the pivot address into the promoted record’s offset-12 field.

8. **Update the pivot’s parent link.**  
   Write the promoted-record address into the pivot’s offset-4 field.

The function then returns without a value.

### Result for a well-formed, stable structure

Assume the relevant record fields do not overlap, there is no concurrent mutation, and the initial links form the expected tree relationship. Let:

- **X** be the pivot.
- **Y** be X’s original left child.
- **B** be Y’s original right child.
- **P** be X’s original parent.

The resulting relationships are:

| Relationship | Before | After |
|---|---|---|
| X’s left child | Y | B |
| Y’s parent | X in a conventional tree | P |
| Y’s right child | B | X |
| X’s parent | P | Y |
| B’s parent, if B is nonzero | Y in a conventional tree | X |
| Selected incoming link | X | Y |

The selected incoming link is determined by the distinguished root-slot comparison first. Only when that slot does not equal X does the function inspect P’s right-child field.

For nonoverlapping records, the function leaves Y’s left-child field, X’s right-child field, and other unlisted fields unchanged.

### Root selection and parent selection

Root status is determined solely by equality between the distinguished root-slot value and the pivot address. It is not determined from the pivot’s parent link.

Consequently:

- A pivot with a zero parent link still takes the non-root path if the root slot does not equal the pivot.
- A pivot with a nonzero parent link still takes the root path if the root slot equals the pivot.
- On the root path, the pivot’s parent-link value is copied into the promoted record. The function does not replace it with zero or any designated root-parent value.
- On the non-root path, a matching right-child link takes precedence. The left-child field is the unchecked fallback.

### Widths, arithmetic, and aliasing

All link transfers, comparisons, and stores concern four-byte values. The only explicit null test is the comparison of the promoted record’s right-child field with zero.

Address calculations use fixed byte offsets of 4, 8, 12, and 16. There is no length calculation, multiplication, range check, or explicit overflow handling. The evidence does not establish defined wraparound behavior for overflowing address calculations. Valid use requires these calculations to identify the intended accessible fields.

The concise rotation result above depends on noninterfering storage. The function performs no alias checks. If records or fields overlap, earlier writes may affect later reads. In particular:

- The promoted record’s right-child field is evaluated again after the pivot’s left-child field has been written.
- The pivot’s parent field is evaluated again on the non-root path.
- The root slot is inspected only after the initial child and parent-field updates.

The supplied source therefore does not support treating the operation as a simultaneous assignment from a complete entry-state snapshot.

## Side effects

The function modifies existing storage in place.

On the ordinary zero-transferred-child path, it performs five four-byte writes: the pivot’s left link, the promoted record’s parent link, the selected incoming link, the promoted record’s right link, and the pivot’s parent link. A nonzero transferred child adds one parent-link write.

No allocation, release, reference-count update, logging, callback, or external call appears in the supplied body. The function does not explicitly transfer memory ownership or end any record’s lifetime.

The updates are not transactional. Intermediate states exist in source order:

- The pivot loses its original left-child link before the incoming link is redirected.
- The promoted record receives its replacement parent link before the incoming link is redirected.
- The incoming link is redirected before the promoted record’s right link and the pivot’s parent link are finalized.

There is no rollback path. If an access fails or execution is interrupted, the source provides no recovery mechanism for earlier writes.

No locking or synchronization is shown. Safe concurrent observation or mutation is not established.
