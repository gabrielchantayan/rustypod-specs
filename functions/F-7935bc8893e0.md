# F-7935bc8893e0

## Purpose

F-7935bc8893e0 performs an initial operation on a supplied target, conditionally acquires and queries a token, and conditionally requests a transfer using a bounded 32-bit count. After the transfer dependency returns normally, it reads two values from target-relative addresses and assigns them through globally designated destinations. An acquired-path token is subsequently passed to a release-like dependency.

The two publication **source reads** are four bytes and two bytes, respectively. The supplied fragment does **not** establish the destination-store widths or the conversions applied by those assignments: the destination globals’ declarations are absent. Consequently, the function cannot be specified as necessarily writing four bytes and then two bytes.

Interpreting the sequence as loading an external resource into a target is inferred intent. The established behavior consists of call ordering, result-dependent branches, unsigned count selection, source reads, destination assignments, and the final conditional dependency call.

## Behavior

### Acquisition

4. The address of the token slot.

### Query and count selection

On the acquired path, the function calls F-110a6bcc4ac7 with the token slot’s contents and the address of the unsigned quantity slot.

A nonzero query result skips count selection, transfer, and both publications. Execution still reaches the release-like call if operations return normally.

A zero query result enables the following selection:

- The neighboring integer slot is tested first.
- If that slot is nonzero, the quantity slot is replaced with the retained limit.
- If that slot is zero, the unsigned quantity is compared with the retained limit.
- A quantity greater than the retained limit is replaced with that limit.
- Otherwise, the quantity remains unchanged.

The comparison uses unsigned 32-bit values. Equality retains the quantity. Values with the highest bit set are not treated as negative.

The neighboring-slot test short-circuits the comparison. When that slot is nonzero, selection does not require reading the previous quantity before replacing it.

No initialization guarantee is supplied for the query outputs. If a reached test or comparison consumes an output that the dependency did not validly initialize, this fragment provides no deterministic fallback. Such a case must not be assigned an invented count.

If an external dependency contract establishes these slots as the low and high parts of a nonnegative 64-bit quantity, this selection is consistent with bounding that quantity by a 32-bit limit. That interpretation remains conditional; the caller does not establish a 64-bit representation or its byte order.

### Publication

1. Read a four-byte value at the address represented by the target reference plus `0xAFC`, then assign that value through the first publication destination.
2. Read a two-byte value at the address formed from the second source-offset value and the target reference, then assign that value through the second publication destination.

The source reads occur after the transfer call, not before it.

For each assignment, the source-read width is established. The destination-store width and any conversion between the source value and the destination object are **documented_only**. In particular:

- A four-byte source read does not prove a four-byte destination store.
- A two-byte source read does not prove a two-byte destination store.
- Truncation, extension, signedness interpretation, and exact resulting destination bytes cannot be specified without the missing destination types or equivalent instruction evidence.

The first assignment completes before the second assignment. The fragment does not establish an exact evaluation order between obtaining a destination designator and evaluating that assignment’s source expression.

There is no local check that the selected count covers either publication source. The first read starts at offset `0xAFC` and requires four readable bytes there, independent of the selected transfer count. The second requires two readable bytes at its computed address.

There is also no transfer-success check before publication. If a dependency contract permits failed, partial, or zero-length transfers that nevertheless return normally, both assignments still follow. The caller does not establish whether those outcomes occur or how they are reported.

The second assignment can also overlap storage affected by the first. Exact overlap effects cannot be calculated from the source-read widths alone because the destination-store widths, conversions, and memory layout are unresolved.

No synchronization or thread-safety guarantee is shown.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid memory, normally returning dependencies, initialized query outputs wherever read, and no unmentioned mutation affecting the example.

### Preparation failure

If preparation returns zero:

- The initial operation has already occurred.
- Acquisition, query, transfer, publication, and release do not occur.

### Acquisition failure after a token write

If preparation succeeds and acquisition writes a token but returns nonzero:

- Query and transfer do not occur.
- Neither publication occurs.
- No release-like call occurs.

This expectation does not establish whether ownership remains outstanding.

### Query failure

If acquisition returns zero and query returns nonzero:

- No count is selected for transfer.
- Transfer and publication are skipped.
- The release-like dependency is called with the token slot’s then-current contents.

### Below, equal to, and above the limit

### Zero count

With retained limit zero and successful preparation, acquisition, and query, selection produces zero.

The transfer dependency is still called. Normal return still leads to the two source reads and destination assignments, followed by release. Zero does not waive the source-address validity requirements.

### Publications do not establish store widths

Suppose the four-byte source read yields `0x12345678` and the two-byte source read yields `0xABCD`.

The established expectation is two ordered assignments using those source values. Exact destination bytes are not determined by this fragment.

Different destination types require their own conversion and store-width expectations; they cannot inherit this conditional example.

### Mutation between publications

If the first destination aliases storage used for the second source read, the second read occurs after the first assignment and can observe its effects.

The exact changed bytes require the destination-store width, conversion, and byte layout. The four-byte first source read alone is insufficient to predict them.
