# F-efa80b3780a5

## Purpose

F-efa80b3780a5 performs an unconditional narrow memory write, then selects between two materially different behaviors:

- If any bit in positions 11–20 of the first argument is set, it clears one byte at a hidden-input-derived address and enters a represented endless sequence of coprocessor operations.
- Otherwise, it writes seven consecutive 32-bit destination words and reaches a boundary where instruction recovery stops.

Neither path establishes a normal return. The seven-word sequence must not be treated as a successfully returning initializer.

This contract describes the supplied static representation. Invalid-instruction warnings and discarded control-flow blocks limit its completeness. Architectural execution, hidden-input conventions, and memory access behavior remain unresolved where explicitly identified below.

## Interface

### Explicit inputs

The recovered interface exposes four argument positions:

| Position | Recovered width and interpretation | Represented use |
|---|---|---|
| First | Unsigned 32-bit integer | Selects the branch; supplies the first and sixth destination words |
| Second | Pointer to 32-bit words | Identifies the seven-word destination; supplies its address representation |
| Third | Opaque 32-bit quantity | No represented use |
| Fourth | Unsigned 32-bit integer | Determines the initial narrow store and the fourth destination word |

These are recovered types, not an independently verified calling convention. In particular, a 32-bit integer representation is established for the arithmetic discussed here, but the actual pointer model is not.

### Hidden inputs

The represented behavior also consumes four incoming values absent from the explicit argument list:

- A signed 32-bit value used to form the third destination word.
- An unsigned 32-bit value used as the byte-store address base, the initial source of a loop operand, and the seventh destination word.
- A first opaque 32-bit coprocessor-related value.
- A second opaque 32-bit coprocessor-related value.

The function does not visibly initialize these incoming values. Consequently, the four explicit arguments alone do not determine the complete represented behavior.

For clarity, “hidden unsigned input” below means its incoming value. The loop subsequently resets its local computational source to zero; that is not a write through the numeric address contained in the input.

### Outputs and completion

The recovered interface has no ordinary result value. Its observable outputs consist of memory stores and, on one branch, coprocessor operations.

No normal-return operation is represented:

- The coprocessor branch has no represented exit.
- The seven-word branch reaches an unresolved instruction boundary.

There is no established success result, error code, exception type, or caller-resumption guarantee.

### Storage and ownership requirements

To reach all represented effects on the selected path without an access failure, the environment must permit:

- One 16-bit store at the address derived from the fourth argument.
- On the coprocessor branch, one 8-bit store at the address derived from the hidden unsigned input.
- On the seven-word branch, seven consecutive 32-bit stores beginning at the second argument.

Any necessary alignment, address mapping, writability, and storage lifetime are environmental preconditions, not checks performed by the function.

No allocation, release, or ownership transfer is represented. The destination’s required extent is 28 bytes on the seven-word branch. The function does not validate that extent.

## Behavior

### Common initial store

Before either branch-specific sequence, the function derives an unsigned 32-bit quotient by shifting the fourth argument right by two bits.

It then performs a 16-bit store with:

- **Numeric address:** the quotient plus eight.
- **Stored bit pattern:** the low 16 bits of the quotient.

The quotient ranges from `0x00000000` to `0x3fffffff`. Adding eight therefore produces a numeric address from `0x00000008` to `0x40000007`, without unsigned 32-bit overflow.

Conversion of that numeric address to a usable pointer, and the consequences of attempting the store, depend on the execution environment. The address is not an offset from the destination pointer.

The narrow store is represented before all branch-specific memory effects. If it faults or otherwise prevents continued execution, neither later sequence is guaranteed to occur.

### Branch selection

The first argument selects the path according to whether bits 11 through 20, inclusive, contain any set bit.

- All ten bits clear: perform the seven-word sequence.
- At least one of those bits set: perform the byte clear and coprocessor loop.

Bits 0–10 and 21–31 do not affect this decision. They can still affect stored values on the seven-word path.

### Byte clear and coprocessor loop

On the nonzero-field path, the next represented memory effect is an 8-bit zero store.

The numeric address is calculated by adding ten to the hidden unsigned input using unsigned 32-bit arithmetic. **This addition wraps modulo \(2^{32}\) before conversion to the byte-store pointer.** For example, an incoming value of `0xfffffffc` produces the numeric address `0x00000006`.

The modulo calculation is established under the recovered width interpretation. Whether the resulting number denotes a valid pointer, which address space it selects, and whether the access succeeds remain unresolved.

After the byte store, the represented loop performs these operations in order:

1. Derive an unsigned operand by shifting the current computational source right by eleven bits.
2. Set that computational source to zero.
3. Issue the coprocessor operation with six represented inputs, in this exact order:

| Input position | Value |
|---|---|
| 1 | Fixed value 8 |
| 2 | Fixed value 5 |
| 3 | Fixed value 4 |
| 4 | The derived unsigned operand |
| 5 | The first hidden coprocessor-related input |
| 6 | The second hidden coprocessor-related input |

The architectural meanings and encoded widths of the three fixed inputs are not established. Their values and order are nevertheless part of the represented operation’s identity.

On the first iteration, the derived operand is the incoming hidden unsigned value shifted right by eleven, producing a value from zero through `0x001fffff`. Under the represented local data flow, subsequent iterations derive zero because the computational source has already been reset.

This later-zero behavior is conditional on continued execution following that represented data flow. It does not establish that the coprocessor operation preserves all registers, memory, global state, or the two hidden coprocessor-related values at an architectural level.

The byte clear occurs once before the loop, not once per iteration. No termination test or exit edge is represented. No seven-word destination sequence follows the loop in the shown control flow.

Calling this a retry loop, wait operation, or error handler would add unsupported intent. Coprocessor faults, privilege failures, traps, interrupts, and other architectural outcomes are not specified.

### Seven-word destination sequence

When the selected ten-bit field is zero, the function writes the following fields in ascending offset order:

| Byte offset | Store width | Value |
|---|---:|---|
| 0 | 32 bits | First argument unchanged |
| 4 | 32 bits | Destination pointer converted to an unsigned 32-bit integer |
| 8 | 32 bits | Hidden signed input shifted left by eleven bits |
| 12 | 32 bits | Fourth argument shifted right by six bits |
| 16 | 32 bits | Zero |
| 20 | 32 bits | First argument shifted left by eleven bits |
| 24 | 32 bits | Incoming hidden unsigned input |

The pointer-derived field is an address representation, not a value read from destination memory. Its behavior for pointers not representable in the recovered unsigned word type is not established.

The fourth argument’s right shift is unsigned and produces a value from zero through `0x03ffffff`.

The first argument’s left shift has a defined unsigned 32-bit interpretation: multiplication by 2,048 modulo \(2^{32}\). Its low eleven result bits are zero.

The hidden signed input’s left shift requires a separate limitation. The static representation establishes an eleven-bit left-shift expression, but not a portable result for negative inputs or values whose mathematical product exceeds the signed 32-bit range. For nonnegative inputs no greater than `0x000fffff`, the product is representable and unambiguous under conventional signed 32-bit arithmetic. A low-32-bit machine shift for other inputs is plausible, but not established as a universal contract.

Each destination store precedes the next in the represented execution sequence. The writes are not represented as an atomic transaction. An access failure may leave earlier stores in place; no rollback is shown.

After the seventh store, recovery stops at a bad-instruction boundary. That boundary does not establish successful completion, a specific exception, process termination, or a return.

### Aliasing and reads

No explicit destination-memory read is represented. Previously stored destination contents are not preserved by a read-modify-write operation.

The initial 16-bit store may overlap bytes later written by either branch. No non-aliasing precondition is established. For ordinary writable memory, a later overlapping store can replace bytes written by the initial store; the byte-level result depends on the unresolved byte order.

The third explicit argument has no represented influence. This is a property of the supplied fragment, not proof that every possible execution of the original executable ignores it.

## Side effects

The directly represented effects, in order, are:

1. One 16-bit memory store derived from the fourth argument.
2. On the nonzero-field branch, one 8-bit zero store, followed by repeated coprocessor operations.
3. Alternatively, on the zero-field branch, seven ordered 32-bit stores.

No explicit allocation, deallocation, global-variable access, memory barrier, or error-reporting write appears in the supplied representation.

That absence does not establish side-effect freedom for the coprocessor operation. Its effects on memory, devices, processor state, privilege state, and globals are unknown.

The contract specifies store widths and numeric values, not a byte serialization. Endianness is unresolved. Represented instruction order also does not establish cross-core visibility order, device ordering, or store atomicity.

## Dependencies

The supplied opaque mapping identifies only F-efa80b3780a5 itself. No separately identified callable dependency is available.

Two operation categories constrain the contract:

- **Coprocessor operation:** Receives the fixed inputs 8, 5, and 4, followed by the derived operand and the two hidden coprocessor-related inputs. Its architectural semantics, exceptional behavior, and state-preservation properties are unknown.
- **Terminal recovery boundary:** Marks the point where valid instruction recovery ends on the seven-word path. It is not established as a callable handler or an operation with a particular runtime outcome.

Neither is assigned an invented function ID. No ownership, memory-release, or global-preservation behavior is assumed for either category.

## Acceptance examples

These examples are conditional consequences of the static representation, not runtime observations. Unless otherwise stated, assume ordinary writable storage, required alignment, successful address conversion, and continued execution through the described operations.

### Zero-valued first argument

With a first argument of zero and a fourth argument of `0x00000100`:

- The initial 16-bit store targets numeric address `0x00000048` and writes `0x0040`.
- The seven-word branch is selected.
- Destination offset 0 receives zero.
- Offset 4 receives the destination’s unsigned 32-bit address representation.
- Offset 8 receives the hidden signed input shifted left by eleven, subject to the signed-arithmetic limitation.
- Offset 12 receives `0x00000004`.
- Offsets 16 and 20 receive zero.
- Offset 24 receives the incoming hidden unsigned value.

Normal return is not required or established.

### Branch boundary and unsigned shift

A first argument of `0x00000400` selects the seven-word branch. Its offset-20 value is `0x00200000`.

A first argument of `0x00000800` instead selects the coprocessor branch. Following the initial store, it performs the hidden-address byte clear and enters the loop.

A first argument of `0x80000000` selects the seven-word branch: the high bit is outside the tested field. Offset 0 receives `0x80000000`, while offset 20 receives zero under unsigned 32-bit shifting.

### Coprocessor input order

With an incoming hidden unsigned value of `0x00001800`:

- The byte clear targets numeric address `0x0000180a`.
- The first coprocessor operation receives, in order, 8, 5, 4, 3, the first hidden coprocessor-related input, and the second hidden coprocessor-related input.
- If execution continues according to the represented local data flow, later operations have zero in the fourth input position.

### Wrapped byte-store address

With an incoming hidden unsigned value of `0xfffffffc` on the coprocessor branch:

- Adding ten modulo \(2^{32}\) produces numeric address `0x00000006`.
- The attempted byte store writes zero through the pointer obtained from that number.
- If the store succeeds and the first loop operation is reached, its derived operand is `0x001fffff`.

This example establishes arithmetic, not that address six is mapped or writable.

### Alignment-sensitive initial store

With a fourth argument of four, the initial store targets numeric address nine and writes the 16-bit value one.

If the architecture rejects that unaligned access, execution may stop there. No realignment, alternate access, or error return is represented.

## Evidence

The supplied static representation directly supports the common 16-bit store, the bits-11–20 branch decision, the branch-specific byte clear, the six ordered coprocessor inputs, the local reset before each coprocessor operation, and the seven ordered destination stores.

The recovered unsigned 32-bit type supports modulo-\(2^{32}\) addition for the hidden-base-plus-ten calculation. Pointer conversion and access behavior are separate unresolved questions.

Warnings identify invalid instruction data, discarded unreachable blocks, and truncated control flow. Those limitations prevent treating the recovered fragment as a complete executable specification.
