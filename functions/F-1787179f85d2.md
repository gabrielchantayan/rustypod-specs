# F-1787179f85d2

## Purpose

F-1787179f85d2 conditionally acquires a byte region, interprets an eight-byte header, and constructs a separate output by selecting the first byte at successive stride-spaced positions.

Its established outcomes are:

- A preliminary callback returns nonzero, or the length checked after that callback is below eight: return zero without calling the acquisition dependency.
- Acquisition returns nonzero: return that status immediately.
- Header validation fails: assign failure status `3`, then perform common cleanup.
- Allocation reports nonzero status: perform common cleanup. The eventual return reads the status storage after cleanup and need not equal the status that selected this branch.
- Allocation reports zero status: select bytes, publish metadata, and return zero.

Zero does not uniquely identify successful extraction. It also represents preliminary nonprocessing and can be returned after allocation failure if cleanup changes the exposed status storage to zero.

The fixed-width-record interpretation is inferred intent. The directly established operation selects individual bytes, with each selection gated by a whole-stride boundary comparison.

## Interface

### Arguments and result

The representation uses a 32-bit address-and-word model. The function receives four 32-bit arguments:

1. **Context address:** identifies callback storage, pointer slots, and metadata.
2. **Input-object address:** passed to dependencies and used for an initial field read.
3. **Initial length:** an unsigned 32-bit value placed in writable local storage.
4. **Initial status value:** placed in local status storage, then overwritten by the preliminary callback’s result before a branch uses it. No independent effect of this initial value is established.

The result is a 32-bit status:

| Reached outcome | Result |
|---|---|
| Preliminary callback returns nonzero | Zero |
| Post-callback length check finds fewer than eight bytes | Zero |
| Acquisition returns nonzero | Acquisition’s returned status |
| Extraction completes | Zero |
| Common cleanup completes | Status storage read after cleanup |

Header rejection places `3` in the status storage before cleanup. Allocation failure instead enters cleanup with the status supplied through the allocation call. In particular, allocation failure does not guarantee a nonzero final result: allocation receives the status storage’s address, and cleanup may subsequently modify it through a retained pointer.

### Acquired-region layout

|---|---:|---|
| `0` | 16 bits | Big-endian format field |

## Behavior

### Initial capture and callback

The first explicit input-object read captures the 32-bit value at offset `0x1c`. Later changes to that field do not replace the captured allocation argument.

The initial length and status arguments are copied into local storage. The callback is then invoked with six arguments:

1. Context address.
2. Value read from a global datum during callback argument evaluation.
3. Input-object address.
4. Address of the writable local length storage.
5. Context address again.
6. Input-object address again.

The global datum is read after the initial input-object field capture and before callback invocation. It is not established to be a constant. Its value, width, meaning, and immutability are not supplied.

The callback-address read and the global-datum read both support this invocation, but their relative evaluation order is not established.

The callback’s return replaces the local status value. A nonzero result causes immediate return of zero. Otherwise, the function checks the unsigned local length against eight; a smaller value also causes immediate return of zero.

Neither exit explicitly acquires a region, invokes cleanup, or writes context metadata. Callback effects are not rolled back.

### Length observations and acquisition

The local length is mutable storage whose address has escaped to the callback. The function does not take one immutable length snapshot for all later purposes.

The relevant observations are distinct:

- The value checked against eight after callback success.
- The value read to supply the acquisition argument.
- The value read after acquisition success to form the retained region end.
- The value read during final metadata publication.

The callback may retain the length address, allowing later dependencies to modify it. In particular, acquisition can receive one length value and leave a different value for end-address formation. Allocation can later change the value that will be published without changing the already retained end address.

F-977b73bb902a receives:

1. Input-object address.
2. The unsigned 32-bit length read for this call.
3. Address of context slot `0x2bc`.

Its returned status replaces the status storage. A nonzero result is returned immediately, without explicit cleanup or metadata clearing. This remains true if acquisition changed the region-pointer slot before failing.

After acquisition returns zero, the function reads the region pointer from `0x2bc` and forms a retained end address using the then-current local length. It retains the source base and end for subsequent processing.

There is no second minimum-length check after acquisition. If acquisition changed the length below eight, the function nevertheless proceeds to the header reads. Safe execution then depends on actual accessible storage, not on the earlier length check.

### Header interpretation and validation

Header values are assembled from bytes in this order:

1. Requested count, from offsets `2` and `3`.
2. Stride, from offsets `4` through `7`.
3. Format field, from offsets `0` and `1`.

The ordering of individual byte reads within each assembly expression is not established. Count and stride are read even when the format field will subsequently reject the header.

Validation accepts exactly these bounds:

- Format equals zero.
- Requested count is at most `255`.
- Stride is at most `262144`, inclusive.

Neither count nor stride must be positive. Zero count and zero stride are independently accepted.

Validation does not require enough record-area bytes for the requested count. A shortage ordinarily reduces the selected count rather than causing an error.

On rejection, the function writes `3` to its status storage and enters common cleanup. No allocation call occurs.

### Allocation and status handling

For an accepted header, F-6dd003795db7 receives:

1. The previously captured input-object field.
2. Literal `1`.
3. Literal `0`.
4. Requested count.
5. Literal `0`.
6. Address of the local status storage.

The allocation return value is written to context slot `0x2cc` before the status is checked. Thus, even reported allocation failure overwrites that slot.

A zero status selects extraction. No separate null-result check occurs.

A nonzero status selects common cleanup. The status observed here selects the branch; it is not captured separately for the eventual return. Because allocation received the status address, a later dependency may modify that storage through a retained pointer.

If allocation does not write the status storage, its prior value is zero from acquisition success. The function does not detect this omission.

Allocation is requested even when the requested count is zero. No explicit release of any previous output pointer precedes its replacement.

### Byte selection

The selected count starts at zero, and the source cursor starts at the retained source base plus eight.

A selection requires:

- Selected count below the parsed requested count.
- Current source cursor plus the parsed stride no greater than the retained end address.

When these conditions permit selection, the function reads one byte at the source cursor and stores it at the current output base plus the selected count. It then increments the count and advances the source cursor by the stride.

The output base is read from context slot `0x2cc` for each store; it is not permanently captured before the loop. The representation does not establish the relative evaluation order of that pointer-slot read and the selected source-byte read. Both support the subsequent byte write.

The retained source base, end, count, and stride are not reparsed after allocation. A dependency’s later modification of the region-pointer slot or header does not itself replace those retained values. Changes to source payload bytes can still affect subsequent byte reads.

For a positive stride, the condition requires a whole stride to fit. A trailing partial stride is ignored even if its first byte is accessible.

Under nonwrapping arithmetic, stable relevant state, nonaliasing storage, and an end-forming length of at least eight, the selected count is the smaller of:

- Requested count.
- The integer quotient of the end-forming length minus eight, divided by stride.

This formula uses the length that formed the retained end, not necessarily the acquisition argument or published length.

With zero stride, the cursor does not advance. If the boundary comparison holds, the same byte is selected repeatedly until the requested count is reached. When the end-forming length is exactly eight, the comparison permits a read at the region’s declared end. Positive count can therefore trigger an out-of-region read.

Zero count causes no selected-byte reads or writes.

### Success publication

After selection stops, explicit 32-bit metadata writes occur in this order:

1. Actual selected count to `0x2c4`.
2. The local length read at publication time to `0x2c0`.
3. Parsed stride to `0x2c8`.

The function then returns zero.

The published length may differ from both the acquisition argument and the length used to form the retained end. Publishing a changed length does not recompute the end or repeat selection.

A reduced selected count is not an error. Allocation remains based on the requested count; this function does not initialize output bytes beyond those actually selected.

### Common cleanup

Header rejection and allocation-status failure share this sequence:

1. Invoke F-840cb7b3952f with the input-object address and the address of context slot `0x2bc`.
2. Write zero to context offset `0x2c0`.
3. Read and return the local status.

The cleanup dependency’s return value does not directly determine the result. Its side effects may matter, including modification of status storage previously exposed to allocation.

Consequently, allocation failure may return a different nonzero value or zero. Header rejection explicitly supplies `3` before cleanup; that is the returned value when the status remains unchanged.

The function does not explicitly clear actual count, stride, or output pointer on this path.

## Side effects

The established direct and dependency-mediated effects include:

- Reading the input-object field, callback-address slot, and global callback argument datum.
- Exposing writable length storage to the callback.
- Exposing the region-pointer slot to acquisition and cleanup.
- Exposing status storage to allocation.
- Replacing the output-pointer slot before checking allocation status.
- Writing selected output bytes before success metadata.
- Clearing published length only after common cleanup returns.

The successful path makes no explicit cleanup call for the acquired region. The function also makes no explicit release call for a previous output buffer or for an allocation result associated with failure.

Ownership, lifetime, reuse, and release obligations are therefore not established. Describing a dependency as acquisition, allocation, or cleanup identifies its role here, not a proven memory-management contract.

The operation is not transactional. Preliminary exits and acquisition failure perform no explicit metadata reset. Cleanup-path failure guarantees the function’s explicit published-length clear, not restoration of other state.

Aliases can affect execution. In particular, output writes that overlap context pointer storage or source bytes may influence subsequent reads. The ordinary extraction formulas assume such interference is absent.

## Acceptance examples

These are conditional consequences of static inspection, not executed tests. Unless stated otherwise, assume valid storage, nonwrapping arithmetic, no relevant aliasing, stable length after the callback, and dependencies that preserve relevant state except for their stated results.

1. **Callback declines.** A nonzero callback result produces zero without acquisition, allocation, cleanup, or explicit metadata publication.

2. **Short preliminary length.** Callback success with length seven produces zero without subsequent processing.

3. **Acquisition fails.** Acquisition returns nonzero. That status is returned without explicit cleanup, even if acquisition changed the region-pointer slot.

4. **Invalid header.** Nonzero format selects status `3`, invokes cleanup, then clears published length. With status preserved through cleanup, the result is `3`. Allocation does not occur.

5. **Validation boundaries.** Format zero, count `255`, and stride `262144` pass validation. Count `256` or stride `262145` fails. Passing validation does not guarantee any selection.

6. **Partial final record.** Length thirteen, count three, stride two: select bytes at offsets eight and ten. Publish count two, length thirteen, stride two.

7. **Header only.** Length eight, positive count, positive valid stride: allocation still requests the full count, but selection produces zero bytes.

8. **Zero count.** Allocation still occurs. On allocation success, no source-byte selection occurs and actual count zero is published.

9. **Zero stride with payload.** Length nine, count three, stride zero: select the byte at offset eight three times.

10. **Zero stride without payload.** Length eight, positive count, stride zero: the boundary condition permits the first read at offset eight. Safe access is not established.

11. **Different length observations.** Acquisition receives twelve, then changes the exposed length to ten. The retained end is base plus ten. Allocation changes that length to forty. For count three and stride two, selection yields one byte, but success publishes length forty. The end remains base plus ten.

12. **Post-acquisition shortening.** Acquisition receives eight and succeeds while changing the local length to four. Header reads still occur; no repeated eight-byte check protects them.

13. **Allocation failure with status mutation.** Allocation writes status five and returns a value that is stored in `0x2cc`. Cleanup, using a retained status pointer, changes status to zero. The function clears published length and returns zero without performing extraction.

14. **Mutable callback datum.** The callback receives the value read from the global datum for this invocation. No particular numeric value or stability across invocations is required by the supplied evidence.

## Uncertainties

The following remain **documented_only**:

- Application meanings of the header and selected bytes.
- Callback identity and global-datum value, width, and mutation rules.
- Dependency ownership, preservation, and address-retention contracts.
- Meaning of the captured input-object field.
- Guarantees associated with dependency success.
- Error-code meanings beyond the explicit assignment of `3`.
- Pointer-overflow behavior and invalid-access consequences.
- Behavior under concurrency or interfering aliases.
- Whether cleanup actually releases, clears, retains, or transforms any resource.

Likely intent is bounded extraction of one byte per fixed-width record. That interpretation does not justify adding positive-stride validation, a full-count requirement, immutable lengths, preserved failure status, or automatic resource release.
