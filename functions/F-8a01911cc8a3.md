# F-8a01911cc8a3

## Purpose

F-8a01911cc8a3 selectively handles a byte-tagged input record. A separate 32-bit selector must equal 12 before the record is inspected.

Recognized tags take one of two paths:

- Update fields in a destination object, then issue a three-argument indirect notification.
- Extract two unsigned values from the record, then issue a four-argument indirect notification without directly updating destination fields.

Most update paths surround their explicit writes with two dependency calls. One update tag, `0x82`, does not make those calls.

**Established static evidence:** tag selection, explicit field accesses, access widths, dependency arguments, and the ordering described below are present in the supplied representation.

**Inferred intent:** the two calls surrounding updates may delimit a protected update interval, and the indirect calls may notify another component. Neither synchronization semantics nor notification meaning is established.

**Unknown:** application-level meanings of the fields, tags, and notification tokens.

## Interface

The function has four inputs and no explicit return value:

| Input | Representation | Role |
|---|---|---|
| Object anchor | 32-bit address-bearing value | Base for destination fields, an embedded dependency context, and a preceding dispatch reference |
| Selector | 32-bit integer | Processing proceeds only when equal to decimal 12 |
| Auxiliary value | Opaque 32-bit value | Forwarded to the first dependency on applicable update paths |
| Record address | Byte-addressable pointer | Supplies the tag and selected payload fields |

Offsets below are hexadecimal. “Object offset” is relative to the object anchor; “record offset” is relative to the record address.

### Object layout used here

| Object offset | Access | Meaning established by this function |
|---|---|---|
| `−0x40` | Read one 32-bit address-bearing word | Dispatch-table reference |
| `+0x08`, `+0x0C`, `+0x10` | Write 32 bits each | Multi-field update |
| `+0x14`, `+0x16`, `+0x18` | Write 16 bits each | Multi-field update |
| `+0x1A` through `+0x1D` | Write 8 bits each | Multi-field update |
| `+0x1E` | Write 8 bits | Single-byte update |
| `+0x34` | Write 32 bits | Single-word update |
| `+0x38` | Write 32 bits | Word preceding a dependency-managed region |
| `+0x3C` | Address passed to a dependency | Destination region of unknown extent |

| `+0x440`, `+0x444` | Write 32 bits each | Two-word update |

Let the **dispatch receiver** mean the address at object offset `−0x40`. The word stored at that address supplies the dispatch-table address. Entries at table byte offsets `+0x10` and `+0x14` supply indirect call targets.

### Preconditions

For a normally completing recognized path:

- The fixed storage locations read by the function must be readable.
- Every selected record field must be readable at its stated width.
- Every selected destination field must be writable at its stated width.
- The dispatch reference and selected call target must be valid for the eventual invocation.
- Dependency-specific validity requirements must hold.

There are no explicit null, size, alignment, dispatch-target, or address-overflow checks.

The representation uses 32-bit address-bearing values. The supplied evidence does not establish portable behavior for overflowing address calculations, misaligned multi-byte accesses, or inaccessible memory.

## Behavior

### Entry and selector gate

The function first reads a fixed 32-bit stored value, called **extent token** below. This read occurs even when the selector will cause an immediate return.

If the selector is not 12, the function returns without reading the record tag, writing object fields, or invoking a dependency.

If the selector is 12, it reads the unsigned 8-bit tag at record offset `0x00`.

The recognized tags are:

`0x02`, `0x04`, `0x06`, `0x0B`, `0x0D`, `0x0F`, `0x11`, `0x80`, `0x82`, `0x84`, `0x86`, `0x8B`, `0x8D`, `0x8F`, and `0x91`.

Every other tag returns without further explicit record reads, destination writes, or calls. The entry-time fixed-value read has already occurred.

### Dependency and token notation

The following opaque function IDs identify dependency roles in this contract; they are not assertions of recovered external identities:

- **F-000000000001:** first call surrounding most updates.
- **F-000000000002:** second call surrounding those updates.
- **F-000000000003:** region-processing dependency used by `0x0D` and `0x8D`.
- **F-000000000004:** dynamically selected target from dispatch-table offset `0x10`.
- **F-000000000005:** dynamically selected target from dispatch-table offset `0x14`.

Each recognized tag selects its own fixed 32-bit notification-token storage location, denoted **N[tag]**. The underlying values are not supplied. Distinct storage locations do not prove distinct values.

Except for `0x82`, update paths have this outer sequence:

1. Call F-000000000001 with the embedded context address, the value 12, the auxiliary value, and the original record address.
2. Perform the tag-specific update, including F-000000000003 where applicable.
3. Call F-000000000002 with the embedded context address.
4. Read the dispatch-table reference from the dispatch receiver, then obtain the target at table offset `0x14`.
5. Read N[tag].
6. Invoke the selected F-000000000005 target with the dispatch receiver, the notification token, and a zero third argument.

These are call-boundary and explicit-access ordering requirements. They do not imply that dependencies leave the record, object, dispatch reference, or fixed token storage unchanged.

### Multi-field updates: `0x02` and `0x82`

Both tags explicitly transfer these fields:

| Record offset | Object offset | Width |
|---|---|---|
| `0x08` | `0x08` | 32 bits |
| `0x0C` | `0x0C` | 32 bits |
| `0x10` | `0x10` | 32 bits |
| `0x14` | `0x14` | 16 bits |
| `0x16` | `0x16` | 16 bits |
| `0x18` | `0x18` | 16 bits |
| `0x1A` | `0x1A` | 8 bits |
| `0x1B` | `0x1B` | 8 bits |
| `0x1C` | `0x1C` | 8 bits |
| `0x1D` | `0x1D` | 8 bits |

The explicit access order is significant:

- Read the 32-bit value at record offset `0x0C` first.
- Read the 32-bit value at record offset `0x08`, then write it to object offset `0x08`.
- Write the previously captured value to object offset `0x0C`.
- For each remaining row, in table order, read the record field and then write the corresponding object field.

For `0x02`, these accesses occur between F-000000000001 and F-000000000002. Its token is read after the final dependency and dispatch-target lookup.

For `0x82`, neither surrounding dependency is invoked. Its N[`0x82`] read occurs **after** the write at object offset `0x0C` and **before** the read at record offset `0x10`. After the remaining field transfers, the function resolves the target at table offset `0x14` and invokes it with the dispatch receiver, the already captured token, and zero.

Thus `0x82` differs from `0x02` both in dependency calls and in token-read timing.

### Single-field updates

The following tags use the ordinary surrounded-update sequence:

| Tags | Record offset | Object offset | Width |
|---|---|---|---|
| `0x04`, `0x84` | `0x08` | `0x1E` | 8 bits |
| `0x0B`, `0x8B` | `0x08` | `0x34` | 32 bits |
| `0x0F`, `0x8F` | `0x08` | `0x43C` | 32 bits |

Each path reads its source field after F-000000000001 returns and writes the destination before F-000000000002 is called.

Paired tags select the same explicit field operation but different notification-token storage locations.

### Word plus region processing: `0x0D` and `0x8D`

Both tags use this sequence:

1. Call F-000000000001 with the ordinary four arguments.
2. Read 32 bits at record offset `0x08` and write them at object offset `0x38`.
3. Call F-000000000003 with:
   - the address at object offset `0x3C`;
   - the address at record offset `0x0C`;
   - the extent token captured at function entry.
4. Call F-000000000002.
5. Resolve the target at dispatch-table offset `0x14`.
6. Read the tag-specific notification token.
7. Invoke F-000000000005 with the dispatch receiver, that token, and zero.

The third argument to F-000000000003 is the **entry-time captured value**, not a fresh read after F-000000000001. Changes to its backing storage during earlier calls therefore do not alter that argument.

No byte count, termination rule, overlap rule, or copy semantics can be assigned to F-000000000003 from this evidence.

### Two-word updates: `0x11` and `0x91`

These tags use the ordinary surrounded-update sequence. Within the update:

1. Read 32 bits at record offset `0x0C`.
2. Read 32 bits at record offset `0x08`.
3. Write the latter value at object offset `0x440`.
4. Write the previously captured offset-`0x0C` value at object offset `0x444`.

Each tag then selects its own notification token and invokes the table-offset-`0x14` target.

### Value-forwarding tags: `0x06`, `0x86`, and `0x80`

These paths make no explicit destination-field writes and do not call F-000000000001 or F-000000000002.

For `0x06` and `0x86`:

1. Read an unsigned 16-bit value at record offset `0x10`.
2. Read an unsigned 32-bit value at record offset `0x08`.
3. Resolve the target at dispatch-table offset `0x10`.
4. Read the tag-specific notification token.
5. Invoke F-000000000004 with the dispatch receiver, token, 32-bit record value, and unsigned 16-bit record value.

For `0x80`:

1. Read the unsigned byte at record offset `0x09`.
2. Read the unsigned byte at record offset `0x08`.
3. Resolve the target at dispatch-table offset `0x10`.
4. Read N[`0x80`].
5. Invoke F-000000000004 with the dispatch receiver, token, zero-extended offset-`0x08` byte, and zero-extended offset-`0x09` byte.

The last argument for `0x80` is represented as an unsigned 16-bit value after extension from the byte. Neither byte is sign-extended. Exact machine-level argument placement is not established.

## Side effects

### Direct effects

The function directly writes only the destination fields listed for the selected update tag. It does not explicitly write the record or the fixed token storage.

That is an access-level statement, not an aliasing guarantee. If record storage overlaps destination storage, a destination write can change a later record read. If other storage aliases a destination, it may also be affected.

The updates are individual accesses, not an established atomic transaction. Earlier writes can affect later reads under overlap. In particular, capturing the record word at `0x0C` before writing the first destination word is observably different from an arbitrary bulk copy.

### Dependency effects and ownership

All dependencies may have effects not visible in the supplied body. Their possible mutation of object state, input storage, dispatch state, globals, or external resources is unknown.

The function itself shows no explicit allocation, release, ownership transfer, rollback, or lifetime extension. Passing an address does not establish whether a dependency retains it, consumes it, or releases related memory.

No status from a dependency is explicitly inspected. The function has no explicit error result, validation failure report, retry, or cleanup-on-failure mechanism. If an access faults or a dependency does not return normally, subsequent operations are not guaranteed.

The dispatch target is fetched when its path reaches dispatch resolution. On surrounded-update paths, this is after both surrounding calls and any region-processing call. A dependency that changes the dispatch reference can therefore affect the target selected afterward.

The fixed notification tokens are also read at their stated points rather than uniformly captured at entry.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless stated otherwise, assume valid non-overlapping storage, normally returning dependencies, and dependencies that do not modify the fields relevant to the example.

1. **Selector rejection.** With selector 11, the extent-token read still occurs. There is no record dereference, destination write, or dependency invocation. Record validity is not needed for this path.

2. **Unsupported tag.** With selector 12 and tag `0x03`, the function reads the tag and returns. It does not inspect payload offsets or resolve a dispatch target.

3. **Unsigned byte forwarding.** With tag `0x80`, record byte `0x08` equal to `0xFE`, and byte `0x09` equal to `0x81`, F-000000000004 receives numeric payload values 254 and 129, respectively—not negative values. The offset-`0x09` read precedes the offset-`0x08` read.

4. **Unsigned halfword forwarding.** With tag `0x86`, an unsigned value 65,535 at record offset `0x10` is forwarded without signed interpretation. Bytes at offsets `0x0C` through `0x0F` are not explicit inputs to this path.

5. **Byte-width write.** With tag `0x84`, the explicit update changes only the byte at object offset `0x1E`. Adjacent bytes are not part of that write.

6. **Different paths for matching field layouts.** Tags `0x02` and `0x82` transfer the same listed fields under these assumptions. Only `0x02` invokes the two surrounding dependencies; each reads a different token location.

7. **Record mutation by the first dependency.** If F-000000000001 changes record offset `0x08` during tag `0x0B` handling, the explicit destination write uses the value read after that dependency returns. It is not an entry-time payload snapshot.

8. **Entry-captured extent.** For tag `0x8D`, if the extent token initially contains E and F-000000000001 changes its backing storage to another value, F-000000000003 still receives E.

9. **Late dispatch selection.** If F-000000000002 replaces the dispatch-table reference during tag `0x11`, the subsequent lookup uses the reference read after that call returns.

10. **No implicit full-record copy.** For tag `0x02`, record bytes before offset `0x08` and after offset `0x1D` are not transferred by the explicit field-update operations.

- Endianness of multi-byte fields.
