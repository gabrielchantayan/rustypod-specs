# F-9813035c7ce7

## Purpose

F-9813035c7ce7 invokes a dependency with a writable, function-local 32-bit value, then updates a caller-designated integer and returns a 64-bit composite result.

The composite contains:

- In bits 0–31, the integer read from the caller-designated location before this function’s update.
- In bits 32–63, the post-dependency local value combined by bitwise OR with packed status information.

The visible operation therefore resembles a fetch-and-add accompanied by status packaging. That description is inferred intent, not an atomicity guarantee. The supplied representation shows separate reads and a write, no synchronization, and no evidence that the entire operation is indivisible.

The dependency executes before the caller-designated integer is read. Consequently, “before the update” means after any effects of that dependency, not necessarily at entry to F-9813035c7ce7.

The source representation also refers to four one-byte status quantities and one unsigned one-byte status quantity without supplying them as explicit arguments. They contribute to the returned upper word. Their calling convention, provenance, and exact capture time are not established.

For clarity, this contract names those quantities by their apparent status roles:

- Negative status.
- Zero status.
- Carry status.
- Overflow status.
- Q status, represented as an unsigned byte.

These names describe their apparent interpretation. They do not establish that the values are normalized Boolean flags or identify an external register interface.

### Result

The result is a 64-bit bit pattern. Its signedness and semantic type are not established.

Let:

- **saved integer** be the first 32-bit integer read through the integer address after the dependency returns;
- **working word** be the local 32-bit word after the dependency returns;
- **status contribution** be the 32-bit packed status value described below.

Then:

- The result’s low 32 bits are the bit pattern of the saved integer.
- The result’s high 32 bits are the working word bitwise-ORed with the status contribution.

This is a logical bit layout, not a claim about memory byte order, register assignment, or an ABI-level two-field structure.

- The dependency must return normally.
- The dependency must not invalidate storage or execution state required for the subsequent operations.
- If a deterministic single-value interpretation of the two integer reads is required, the addressed storage must not change between those reads through concurrency, special memory behavior, or another external mechanism.

The visible body does not check these conditions. It contains no null-pointer check, bounds check, alignment check, or recoverable error result.

## Behavior

### 1. Establish the local word

The function initializes a writable local 32-bit word from the fourth argument.

This initialization precedes the dependency call. There is no visible access to the caller-designated integer before that call.

### 2. Invoke the dependency

The function calls F-0e28341fcf96 with the address of the local word.

The dependency receives access to that word through a pointer, rather than receiving only its value. The upper half of the eventual result uses the word as it exists after the dependency returns.

The visible caller does not use a return value from F-0e28341fcf96.

Nothing supplied establishes that the dependency:

- Preserves the local word.
- Preserves global state or status flags.
- Avoids modifying the caller-designated integer through some other reference.
- Avoids retaining the supplied pointer.
- Returns on every input.
- Performs no allocation, release, I/O, or other external action.

The caller’s subsequent behavior must therefore be understood conditionally on the dependency’s actual effects.

### 3. Save the first post-dependency integer read

After the dependency returns, the function reads the integer at the second argument and retains its 32-bit value for the result’s low half.

This read is distinct in the supplied representation from the read used to calculate the update.

If the dependency has changed that integer, the saved value reflects its post-dependency state. The function does not preserve the entry-time value before calling the dependency.

### 4. Calculate and store the updated integer

The function reads the addressed integer again, adds the first argument, and writes the result back to the same address.

The visible ordering is:

1. Dependency call.
2. First integer read, retained for the return value.
3. Second integer read, used as the addition operand.
4. Integer write.
5. Return of the composite result.

For ordinary stable memory, the two reads produce the same value. Under that condition, the result’s low half contains the pre-update value and the stored integer contains that value plus the increment.

The supplied representation expresses the addition using signed integer operands. It does not show a wider accumulator, saturation, an overflow check, or a separate overflow error path. Exact behavior outside the signed 32-bit range is not independently established by this representation. Machine-width wraparound is plausible inferred intent, but is not promoted here to a verified overflow guarantee.

The function does not visibly recompute the returned low half from the stored result. The low half comes from the earlier saved read.

### 5. Pack the status contribution

The status expression first combines:

- Negative status shifted left by four positions.
- Zero status shifted left by three positions.
- Carry status shifted left by two positions.
- Overflow status shifted left by one position.
- Q status without an initial shift.

That combined quantity is narrowed to eight bits, widened to an unsigned 32-bit quantity, and shifted left by 27 positions within 32-bit arithmetic.

Only the lowest five bits of the narrowed byte can survive that final shift. Thus the status contribution can affect only bits 27–31 of the upper word.

If the first four quantities are normalized to zero or one and Q also occupies only its least significant bit, the mapping is:

| Status | Bit in upper word | Bit in complete 64-bit result |
|---|---:|---:|
| Negative | 31 | 63 |
| Zero | 30 | 62 |
| Carry | 29 | 61 |
| Overflow | 28 | 60 |
| Q | 27 | 59 |

That clean one-status-per-bit mapping is conditional. Q is represented as a byte, so its bits 1–4 can also contribute to upper-word bits 28–31. The visible expression does not mask Q down to one bit before combining it.

Likewise, the supplied representation does not prove that the other status quantities are restricted to zero and one. Their exact non-Boolean behavior should not be inferred from their apparent names.

### 6. Form the upper word and return

The function combines the status contribution with the post-dependency working word using bitwise OR.

This is an additive bit-setting operation, not replacement of a status field:

- Every bit already set in the working word remains set.
- A zero status contribution cannot clear a working-word bit.
- A one in a relevant status position forces that position to one.
- Upper-word bits 0–26 come entirely from the working word.
- Upper-word bits 27–31 can come from either the working word or the status contribution.

The resulting upper word is concatenated with the saved integer’s 32-bit pattern to produce the 64-bit result.

There is no visible error tag or success flag separate from that composite.

## Acceptance examples

These examples are conditional behavioral checks, not reports of execution. No runtime tests have been performed.

### Ordinary update with no status contribution

Given that:

- F-0e28341fcf96 returns normally and leaves the working word at `0x01234567`;
- the addressed integer remains 20 through both reads;
- the increment is 3;
- the status contribution is zero;

the function stores 23 and returns `0x0123456700000014`.

The low half contains 20, not 23.

### Dependency mutation affects both observable outputs

Given that the dependency changes the working word to `0x00000002` and changes the caller-designated integer to 9 before returning, with no later interference, an increment of 4 and zero status contribution produce:

- Stored integer: 13.
- Returned value: `0x0000000200000009`.

The integer’s value before the dependency call is not returned merely because it existed at function entry.

### Normalized negative status

Given a working word of `0x00000003`, normalized negative status equal to one, all other status quantities zero, a stable addressed integer of 7, and increment 1:

- The upper word is `0x80000003`.
- The low word is `0x00000007`.
- The stored integer is 8.

### Existing status-position bits are not cleared

Given a working word of `0xF8000000` and all status quantities zero, the upper word remains `0xF8000000`.

An implementation that replaces those five bits with zero would not match the visible OR operation.

### A multi-bit Q value contributes to multiple positions

Given a working word of zero, the first four status quantities zero, and Q equal to `0x03`, the status contribution is `0x18000000`.

Treating Q solely as a Boolean would produce a different upper word and would require an additional precondition not established here.

### Negative saved integer

Given stable addressed storage containing −1, increment 1, and a zero upper word, the stored integer becomes zero while the returned low word is `0xFFFFFFFF`.

The negative integer contributes its 32-bit pattern; it does not sign-extend across the independently constructed upper word.

### Different values at the two reads

If the first read yields 10 and the second yields 12, and the increment is 3, the visible operation saves 10 for the return value and calculates a stored value of 15.

This example explains the two-read dependency. It does not establish that a concurrent race is supported or defined.
