# F-b375f1b4e852

## Purpose

F-b375f1b4e852 constructs an intermediate collection from a sequence of records, partitioning consecutive records according to a 32-bit field at byte offset 8. It then passes that collection through a conversion dependency and supplies the conversion result to a second dependency associated with the caller’s state.

On the established success path, it performs an additional conversion-related call, invokes a cleanup-like dependency, clears one word in the caller’s state, and returns a 64-bit result containing the first conversion result. On any explicitly checked failure, it invokes the same cleanup-like dependency, reports a fixed error, and returns a distinct 64-bit failure value.

“Collection,” “group,” “conversion,” and “cleanup” describe inferred roles. The visible evidence establishes the calls and their ordering, but not the underlying object types, ownership rules, or the full effects of those dependencies.

## Behavior

### Intermediate construction

The function begins with:

- A current-group handle of zero.
- A remembered grouping value of signed 32-bit `-1`, whose bit pattern is `0xFFFFFFFF`.
- An addressable outer-collection slot initially containing zero.

It calls F-c141a8d8555e and stores its 32-bit result in the outer-collection slot.

A zero result immediately selects the checked-failure path. A nonzero result starts iteration at signed 32-bit index zero.

### Iteration and observable reads

Each loop condition invokes F-10b760faca36 using a fresh read of the state word at byte offset 0. Its result is compared with the current index as a signed 32-bit integer.

If the index is not less than that result, iteration ends. Otherwise:

1. The state word at byte offset 0 is read again.
2. F-6bbddce1b930 receives that sequence handle and the current index.
3. The returned record address is used to read a 32-bit grouping field at byte offset 8.

The sequence handle is therefore not captured once for the entire operation. The count is also queried for every loop condition, including the final condition that ends iteration. Changes made by dependencies to the state or sequence can affect later iterations.

### Group boundaries

When the selected record’s grouping field differs from the remembered grouping value:

1. F-c141a8d8555e is called to obtain a new group handle.
2. A zero result selects checked failure immediately.
3. Otherwise, F-754616bec4de is called with the outer-collection handle and the new group handle.
4. A zero result selects checked failure immediately.
5. After that call succeeds, the selected record’s field at byte offset 8 is read again and becomes the remembered grouping value.

This second read is significant. The value remembered for later comparisons is the value present after the group has been attached, not necessarily the value that triggered creation of the group.

Regardless of whether a new group was created, F-754616bec4de is then called with the current-group handle and the selected record address. A zero result selects checked failure. A nonzero result permits the index to advance.

Grouping is based on transitions between adjacent processed records. There is no search for an earlier group with a matching value. For stable field values, a sequence of grouping values `4, 9, 4` produces three group-creation attempts, not two.

### Initial sentinel edge case

The remembered grouping value initially has all bits set. If the first selected record also has that value, the group-creation branch is skipped.

The first record is then passed to F-754616bec4de with a current-group handle of zero. The function contains no special handling for this case. Whether that call succeeds, fails, or has another effect depends on F-754616bec4de.

A contract that promises creation of a group for every first record would therefore contradict the visible behavior.

### Completion after destination acceptance

1. The caller state word at byte offset 8 is read again.
2. A 32-bit value is read at byte offset 4 from the address supplied by that word.
3. That value replaces the local slot initially populated from the third argument.
4. F-927fe5381082 is called again, visibly receiving the address of the outer-collection slot, the address of that local slot, and the conversion-related datum.
5. The second call’s return value is not checked or included in the function result.
6. F-fb5bc2dc656c is called with the then-current outer-collection handle and a shared cleanup-related datum.

The second conversion call and the cleanup-like call do not introduce a checked-failure branch. Their undocumented internal behavior remains outside this function’s established contract.

### Checked failure

The same failure path is reached when:

- Initial outer-collection creation returns zero.
- Creation of a required group returns zero.
- Attachment of a new group to the outer collection returns zero.
- Attachment of a record to the current group returns zero.
- F-aba38163eef3 returns zero.

That path performs, in order:

1. F-fb5bc2dc656c with the current outer-collection handle and cleanup-related datum.
2. F-4fc89ec41a6d with the fixed values `0x0D`, `0x9E`, and `0x41`.
3. Return of `0x00000000FFFFFFFF`.

## Side effects

The only explicit write to caller-owned state is a 32-bit zero at state byte offset 4 on the success path. No corresponding direct state write occurs on checked failure.

This does not establish that failure leaves caller state unchanged. Dependencies receive handles derived from that state and may have effects not shown here.

Other established effects include:

- Creation attempts through F-c141a8d8555e.
- Group and record attachment attempts through F-754616bec4de.
- Repeated sequence-count and record-selection calls.
- One conversion-related call before destination acceptance.
- A second conversion-related call only after destination acceptance.
- A cleanup-like call on both ordinary success and checked failure.
- A fixed error-reporting call on checked failure.

There is no visible rollback of successful earlier attachments. A later failure does not explicitly detach records, undo destination-side changes, or individually release the current group.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Successful completion assumes all intervening dependencies return normally and required addresses remain valid.

### Empty sequence

If initial creation succeeds and the first count result is zero:

- No record is selected and no group is created.
- The first conversion-related call still occurs.
- A nonzero destination-acceptance result leads to the second conversion call, cleanup, state clearing, and success return.
- A zero destination-acceptance result leads to cleanup, error reporting, and checked failure.

A negative initial count also ends iteration immediately because the index starts at zero and comparison is signed.

### Stable adjacent grouping

For three records with stable grouping values `6, 6, 8`, with all relevant dependency results nonzero:

- Two group-creation calls occur in addition to initial outer creation.
- The first two records are attached to the first group.
- The third record is attached to the second group.
- Processing proceeds to conversion.

For `6, 8, 6`, three groups are created. Earlier groups are not reused.

### First field equals the sentinel

If the first record’s grouping field is `0xFFFFFFFF`:

- No group is created for that record before its attachment attempt.
- F-754616bec4de receives zero as its first argument for that attachment.
- A zero result produces checked failure.
- A nonzero result allows processing to continue; the function does not reject it independently.

### Mutation during group attachment

Suppose a record initially has grouping value `3`, triggering a new group. If successful attachment of that group changes the record field to `7`, the remembered value becomes `7`. The next record is compared against `7`, not `3`.

### Rejection after conversion

If construction completes and the first conversion returns `0x12345678`, but F-aba38163eef3 returns zero:

- The second conversion call does not occur.
- The direct state-clearing write does not occur.
- Cleanup precedes error reporting.
- The function returns `0x00000000FFFFFFFF`, not a result containing `0x12345678`.

### Zero conversion payload

If the first conversion returns zero and F-aba38163eef3 nevertheless returns nonzero, the function can complete successfully with return value `0xFFFFFFFF00000000`. Zero is not independently rejected as a conversion payload.
