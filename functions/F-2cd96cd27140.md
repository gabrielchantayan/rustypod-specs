# F-2cd96cd27140

## Purpose

F-2cd96cd27140 conditionally replaces a numeric field in a caller-supplied record. It accepts the replacement only when the record pointer is non-null, the record’s first integer field matches an externally stored reference value, and the replacement is greater than 2,047.

On acceptance, it stores the replacement in the record’s fifth integer slot and returns status zero. On an ordinary rejection, it returns status 26 without writing the record.

This is a narrow validation-and-assignment operation. The supplied evidence does not establish what the record represents, what units the replacement uses, or why values below 2,048 are rejected. Interpreting the field as a size, capacity, or limit would be inferred intent rather than established behavior.

## Interface

### Inputs

**Record pointer**

A pointer to storage interpreted as a sequence of integer slots.

- A null pointer is an explicitly handled input.
- For a non-null pointer, the first integer slot must be readable for the comparison.
- If both the comparison and the numeric threshold check succeed, the fifth integer slot must be writable.
- The routine receives no allocation length, record version, or independent bounds information.
- A non-null pointer is not, by itself, evidence that the referenced storage is valid.

**Replacement value**

An unsigned integer tested against the inclusive rejection boundary of 2,047.

Under the recovered 32-bit integer model, its representable range is 0 through 4,294,967,295. The accepted numeric range is therefore 2,048 through 4,294,967,295, provided the record comparison succeeds.

The routine applies no visible upper bound beyond the input type’s range.

### Output

A 32-bit status value:

| Status | Meaning |
|---|---|
| 0 | The validation conditions succeeded, and the replacement was assigned to the fifth integer slot. |
| 26, hexadecimal 0x1A | At least one explicit validation condition failed. |

No distinct status identifies which validation condition failed. Invalid memory access is not shown as a status-returning error path.

## Behavior

### Validation and access gating

The routine first determines whether the record pointer is null.

If it is null:

- The routine returns 26.
- It does not read through the record pointer.
- It does not evaluate the external-reference comparison.
- It does not write record storage.
- The replacement value does not affect the outcome.

For a non-null record pointer, the routine compares the first integer slot with an externally stored reference value.

If they do not compare equal:

- The routine returns 26.
- It does not write the fifth integer slot.
- The replacement threshold does not need to be evaluated.
- No access to the fifth integer slot is required by this path.

Only if the comparison succeeds does the routine test whether the unsigned replacement exceeds 2,047.

If the replacement is 2,047 or less:

- The routine returns 26.
- It does not write the fifth integer slot.

If the replacement is greater than 2,047:

- The routine assigns the replacement to the fifth integer slot.
- It then returns zero.

These conditions are cumulative. A numerically acceptable replacement cannot override a null pointer or a failed reference comparison.

### Ordering guarantees and limits

The visible condition structure establishes the following ordering:

1. The null-pointer check gates the reference comparison.
2. A successful reference comparison gates the numeric threshold check.
3. Successful validation gates the destination assignment.
4. The assignment precedes the successful return.

The comparison requires both the first record field and the external reference value. The supplied expression does not establish which of those two operands is read first. A contract must not impose a record-first or reference-first order.

The routine does not visibly reread the first field after validation. It also does not visibly check the external reference again before writing the destination.

These are source-level access relationships. The fragment does not establish machine-instruction ordering, atomicity, memory barriers, or behavior for concurrently modified storage.

### Arithmetic and boundaries

The numeric decision is a comparison, not a calculation involving addition, subtraction, multiplication, or an allocation size.

Consequently:

- Exactly 2,047 is rejected.
- Exactly 2,048 is accepted when the record comparison succeeds.
- There is no visible rounding or alignment adjustment.
- There is no visible saturation or clamping.
- No value above the threshold is rejected merely for being large.

The routine checks the value it receives after any caller-side conversion to the unsigned input type. It does not inspect a caller’s original signed value or textual representation.

### Failure and validity limits

The explicit failure status covers validation failures only.

For a non-null pointer, the first field must be accessible even when the replacement is below the threshold: the field comparison precedes the numeric test. A small replacement is therefore not a safeguard against an invalid record pointer.

Similarly, a matching first field and an acceptable replacement lead directly to a destination write. There is no visible check that the allocation extends through the fifth slot or that this slot is writable.

The supplied evidence shows no exception handler, fault recovery, rollback, or alternate status for inaccessible memory.

## Side effects

On an ordinary rejected call, the routine makes no explicit write.

On an accepted call, its sole explicit write replaces the fifth integer slot. It does not explicitly modify the first field, the three intervening slots, or any later record storage.

The routine reads an external reference value but contains no separate assignment to that reference. This does not prove that the reference is unchanged in every possible execution: if caller-supplied writable storage aliases the reference’s storage, the destination assignment could affect it. No non-aliasing requirement or storage relationship is supplied.

There is no visible allocation, deallocation, ownership transfer, reference-count update, callback, or other function call. The pointer is used for comparison and conditional mutation; it is not visibly retained.

The fragment provides no synchronization. Concurrent access, external mutation, and device-memory behavior require a separate environmental contract.
