# F-4843d1ab1c04

## Purpose

F-4843d1ab1c04 acquires one 24-byte record from a caller-supplied allocation state and partially initializes that record.

The record is obtained, in priority order, from:

1. A singly linked list of reusable records.
2. The next unused position in an existing record region.
3. A newly allocated region, registered through a newly allocated region descriptor.

The function has no explicit return value. Its observable results are changes to the allocation state, possible allocation calls, writes to a new region descriptor, and initialization of the selected record.

The interpretation as a reusable-record pool is inferred intent. The selection rules, memory accesses, allocation requests, and initialization described below are established by the supplied static evidence.

## Interface

### Input state

The sole argument identifies a writable control structure containing four consecutive 32-bit fields:

| Byte offset | Meaning in this contract |
|---|---|
| 0 | Address of the current region descriptor, or zero |
| 4 | Address of the first reusable record, or zero |
| 8 | Address of the next unused record in the current region |
| 12 | Address marking the end of the current region |

Addresses are represented as 32-bit values in the supplied representation. The record stride is 24 bytes.

The function does not validate the control-structure address, field alignment, record addresses, descriptor addresses, or region boundaries.

### Region descriptors

Each region descriptor occupies 12 bytes:

| Byte offset | Meaning in this contract |
|---|---|
| 0 | Address of the preceding region descriptor |
| 4 | Record capacity, interpreted as an unsigned 32-bit integer |
| 8 | Address of the region’s record storage |

The function reads the current descriptor’s capacity when growth is necessary. It also links a newly allocated descriptor to the descriptor address held in the control structure after the allocation calls.

### Reusable records

A reusable record contains its successor address at byte offset 12, stored as a 32-bit value. This link is consumed before that same field is cleared during initialization.

A record must provide writable storage through byte offset 15 for the initialization performed here. Valid pool operation additionally requires 24-byte slots, because sequential allocation advances by that amount.

### Output and return

There is no explicit result value and no output parameter identifying the selected record.

The selected address exists internally during the operation. The function’s interface does not independently establish how a caller discovers or uses that record afterward.

### Preconditions

For defined, successful operation:

- The control structure must be readable and writable for all four fields.
- A nonzero reusable-list head must identify a readable successor field and writable initialization fields.
- When sequential allocation is selected, the next-unused address must identify a valid available record.
- When growth uses an existing descriptor, its capacity field must be readable.
- Allocation results must support the descriptor and record accesses described below.
- Aliasing, concurrent access, or dependency-induced mutation must not invalidate later reads or writes.

These are requirements on the surrounding environment, not conditions checked by this function.

## Behavior

### Record-source priority

The first decision reads the reusable-list head at control offset 4.

If that address is nonzero, the function selects that record without examining the next-unused address or region-end address for allocation purposes. It reads the selected record’s 32-bit successor at offset 12 and writes that successor into the reusable-list head.

If the reusable-list head is zero, the function reads the next-unused address and compares it with the region-end address.

- Unequal addresses select the next-unused address directly.
- Equal addresses trigger allocation of a new descriptor and record region.

The comparison is equality only. There is no ordering comparison, remaining-byte calculation, or verification that the next-unused address lies inside the region.

### Reuse path

On the reuse path, the observable operation order is:

1. Read the reusable-list head.
2. Read the selected record’s successor at record offset 12.
3. Replace the reusable-list head with that successor.
4. Perform the common record initialization.

The descriptor head, next-unused field, and region-end field are not directly written by this path.

The successor is captured before initialization clears record offset 12. Thus a nonzero successor remains reachable through the updated control structure even though the selected record’s former link is erased.

### Existing-region path

When no reusable record exists and the next-unused address differs from the region-end address, the function selects the next-unused address.

It writes the selected address plus 24 bytes into the next-unused field before initializing the selected record.

This path makes no allocation calls and does not directly modify the region-descriptor head or region-end field.

There is no explicit rejection of an inverted, misaligned, or otherwise inconsistent pair of region addresses. Address inequality alone is enough to enter this path.

### Growth capacity

When growth is required, the new capacity depends on the descriptor head read before either allocation call.

If that head is zero, the new capacity is 32 records.

Otherwise, let the existing descriptor’s capacity be an unsigned 32-bit value \(C\). Two unsigned 32-bit candidates are formed:

- An additive candidate: \(C + 32\).
- A proportional candidate: \(C + \lfloor C/2 \rfloor + \lfloor C/8 \rfloor\).

Each addition uses 32-bit unsigned arithmetic, including wraparound. The right shifts implement the indicated floor divisions on the unsigned value.

The selected capacity is the larger candidate under unsigned comparison. On equality, the proportional candidate is selected, with no numerical difference.

For non-overflowing values, this corresponds to choosing between an increase of 32 records and approximately 62.5% growth. That interpretation must not replace the specified wrapped arithmetic for large values.

The byte request for the record region is the selected capacity multiplied by 24, again as a 32-bit computation. No overflow check is present.

### Allocation and publication order

Growth invokes F-871e64ddc6de twice, in this order:

1. A request with arguments 12 and 0, whose result is used as the new descriptor address.
2. A request with arguments equal to the computed region byte size and 0, whose result is used as the record-region address.

Both calls occur before the function explicitly initializes the new descriptor.

After the calls return, the explicit memory-access order is:

1. Store the second allocation result at new-descriptor offset 8.
2. Read the control structure’s descriptor-head field and store that value at new-descriptor offset 0.
3. Store the selected capacity at new-descriptor offset 4.
4. Publish the new descriptor address in the control structure’s descriptor-head field.
5. Read the region address back from new-descriptor offset 8 and select it as the record address.
6. Store the selected record address plus the computed region byte size in the region-end field.
7. Store the selected record address plus 24 in the next-unused field.
8. Perform the common record initialization.

The old descriptor address used for capacity selection is therefore read before allocation, while the predecessor address written into the new descriptor is read after both allocation calls. They are the same only if intervening behavior leaves that control field unchanged.

Likewise, the selected record address is read from the newly written descriptor rather than treated as an independently guaranteed, immutable allocation result. Aliasing or external mutation could affect this read.

No deallocation or rollback is explicitly performed.

### Common record initialization

Every successful path ends with the following writes to the selected record, in this order:

1. Write a 32-bit zero at offset 4.
2. Write a 32-bit zero at offset 8.
3. Write a 32-bit zero at offset 12.
4. Write a single zero byte at offset 0.

These writes do not constitute initialization of the entire 24-byte record.

The function does not explicitly write:

- Bytes 1–3.
- Bytes 16–23.

Those bytes retain their previous contents unless affected by aliasing or behavior outside these explicit writes. In particular, the function does not establish that newly allocated records are fully zeroed.

## Side effects

### Control-state changes

Under ordinary non-overlapping storage assumptions:

| Selected path | Direct control-state changes |
|---|---|
| Reuse | Replace reusable-list head with the selected record’s successor |
| Existing region | Advance next-unused address by 24 bytes |
| New region | Replace descriptor head, set region end, and set next-unused address to the second slot |

The reusable-list head is not explicitly written on either sequential-allocation path.

These descriptions do not assert that F-871e64ddc6de preserves any control state or globals. Such guarantees are unavailable.

### Memory and ownership

The growth path retains both allocation results in the pool’s descriptor chain and current-region state. Previous descriptors remain linked through the new descriptor’s predecessor field.

The function contains no explicit release operation for:

- A record removed from the reusable list.
- An older record region.
- An older descriptor.
- Either newly requested allocation if a later operation fails.

Retention in the descriptor chain suggests pool-managed lifetime, but ownership transfer rules, allocator metadata, and eventual release responsibilities are not established.

### Errors and partial progress

The function has no explicit failure return, exception handling, null-result check, capacity limit, or overflow error path.

A failed allocation is not converted into a defined pool-level error. If an allocation result is unusable, later accesses can fail according to the execution environment.

Growth is not transactional. Depending on where an invalid access occurs, observable effects may include completed allocation calls, partial descriptor initialization, publication of a new descriptor, or updated control fields without completed record initialization.

The function provides no synchronization. Thread safety and reentrant safety require external guarantees.

## Acceptance examples

The following are conditional static acceptance examples, not executed tests. Except where noted, they assume valid, suitably aligned, non-overlapping storage; successful allocation; and no concurrent or dependency-induced mutation of relevant state.

### Reusable record takes precedence

Given a nonzero reusable-list head identifying record A, with successor B at A’s offset 12:

- A is selected even if the sequential region is exhausted.
- The reusable-list head becomes B.
- No allocation call occurs.
- The next-unused address and region-end address remain directly unchanged.
- A receives the four initialization writes in the specified order.
- A’s bytes 1–3 and 16–23 are not explicitly modified.

A zero successor empties the reusable list.

### Existing region supplies one slot

Given a zero reusable-list head, a next-unused address of \(P\), and a different region-end address:

- \(P\) is selected.
- The next-unused field becomes \(P + 24\) under the represented address arithmetic.
- No capacity is read from a descriptor.
- No allocation call occurs.
- The common initialization affects the record at \(P\).

This holds even when the addresses describe an invalid region; validity is a precondition, not a checked condition.

### First region has 32 slots

Given a zero reusable-list head, equal next-unused and region-end addresses, and a zero descriptor head:

- The capacity is 32.
- Allocation requests occur in the order 12 bytes, then 768 bytes, both with second argument zero.
- If the record-region address is \(B\), the region end becomes \(B + 768\), and next-unused becomes \(B + 24\).
- The record at \(B\) is initialized.
- The new descriptor records capacity 32 and, under the stated non-mutation assumption, a zero predecessor.

### Additive growth dominates

Given an exhausted region whose current descriptor records capacity 32:

- The additive candidate is 64.
- The proportional candidate is 52.
- The selected capacity is 64.
- The second allocation request is 1,536 bytes.

### Proportional growth dominates

Given an exhausted region whose current descriptor records capacity 64:

- The additive candidate is 96.
- The proportional candidate is 104.
- The selected capacity is 104.
- The second allocation request is 2,496 bytes.

### A descriptor with zero capacity is still consulted

Given a nonzero descriptor head whose capacity field is zero, with growth required:

- The capacity field is read.
- The candidates are 32 and zero.
- The selected capacity is 32.
- The existing descriptor is linked as predecessor if the descriptor-head field remains unchanged during allocation.

This differs observably from the zero-descriptor case because it performs a capacity read and retains an existing predecessor.

### Initialization is partial

Given a selected record containing nonzero bytes throughout:

- Offsets 4–15 become zero through three 32-bit writes.
- Byte 0 becomes zero through a later single-byte write.
- Bytes 1–3 and 16–23 remain unchanged under the non-aliasing assumption.

A requirement that all 24 bytes become zero would not match this function.
