# F-b1e11d250a75

## Purpose

F-b1e11d250a75 obtains a node address, invokes payload-related dependencies, increments a tree count, writes attachment links, performs color-based repair, and publishes the originally obtained address through an output slot.

**Established static evidence:** The function accesses parent and child links, one-byte colors, a four-byte count, and three header links. Repair combines recoloring with calls to two structural dependencies.

**Inferred intent:** This is insertion repair for a red-black tree. The header links behave as root, leftmost, and rightmost links. Color zero behaves as red; any nonzero color stops the red-parent repair condition. Explicit black-color writes use one.

The function does not search for an insertion position, check for duplicate keys, or verify that the selected child position is vacant. It receives an attachment parent and a side control.

The source establishes attachment writes before repair, not unconditional final membership. Later dependencies have unknown effects, and the final output write may alias tree storage. Normal completion establishes publication of the original node address after the final root-color write; final membership requires additional dependency and aliasing assumptions.

## Behavior

### Node acquisition and payload operations

F-7e6c7b36144f receives the tree address. Its result is retained as the original node address for attachment and final publication.

The function forms the address at node +16 and tests that derived address against zero. It does not test the node result itself against zero.

When the derived address is nonzero:

1. F-f4fd698ba468 receives node +16 and the source-value argument.
2. Its address-like result is advanced by four bytes.
3. F-dbd7946c31a3 receives that adjusted result and source value +4.

When node +16 is zero, both payload-related calls are skipped, but subsequent count, attachment, and node accesses remain.

A zero node result therefore has no conventional allocation-failure handling. In an ordinary flat-address interpretation, zero +16 is nonzero, so payload processing is attempted rather than skipped. Address-overflow behavior is not established.

### Count update and attachment decision

After payload processing, the function reads the four-byte count at tree +20, adds one, and writes the result back. This precedes comparison, attachment, and repair.

The displayed operation uses signed 32-bit arithmetic. Behavior when the count cannot be incremented within that range is **documented_only**; a portable wraparound guarantee must not be inferred.

The function next reads the current header address. It selects left attachment without comparison if either:

- That header address equals the supplied attachment parent; or
- The side control is nonzero.

Otherwise, it enters the comparison-controlled path. On entry to that path, the retained values later available as the fifth and sixth operands of one structural call are both set to zero. This happens before comparison and applies whether comparison selects left or right.

F-31a0b2b5649a then receives, in order:

1. Tree +25.
2. The source-value argument.
3. Attachment parent +16.

Any nonzero result selects left attachment; zero selects right attachment. There is no signed less-than/greater-than interpretation of this result.

### Attachment and header updates

For left attachment, the function first writes the original node address to attachment parent +8. It then reloads the header address.

- If the reloaded header differs from the attachment parent, it reads header +8 and replaces that link only if it equals the attachment parent.
- If the reloaded header equals the attachment parent, it writes the node address to that header’s +4 link. It then reloads the header address again and writes the node address to the resulting header’s +12 link unconditionally.

Thus, with a stable header and ordinary non-overlapping storage, header attachment writes leftmost, root, and rightmost in that order. Without header stability, those writes need not address one header object.

For right attachment, the function writes the original node address to attachment parent +12. It reloads the header address, reads that header’s +12 link, and replaces it only if it equals the attachment parent.

After these updates, the function writes the supplied attachment-parent address to original node +4.

The selected child link is overwritten without a prior vacancy check. No subtree-preservation operation is visible for a previously occupied link.

### Repair entry and stopping conditions

Repair initially uses the original node as its current node.

At each iteration, the function reloads the header and reads its root link. Equality between the current repair node and that root ends the loop without inspecting the current node’s parent color.

Otherwise, it reads the current node’s parent and that parent’s color. A nonzero parent color ends repair. A zero parent color proceeds to the grandparent and sibling-side logic.

The function reads the grandparent through the parent’s +4 link, then reads the grandparent’s +8 link. Equality between that left-child address and the parent selects the first repair branch. Inequality selects the complementary branch without checking that the parent is actually the grandparent’s right child.

### Parent matches the grandparent’s left child

The grandparent’s +12 link supplies the uncle address.

If the uncle is nonnull and has color zero, direct writes occur in this order:

1. Parent color becomes one.
2. Uncle color becomes one.
3. The grandparent reached by rereading the current node’s parent chain receives color zero.
4. That parent chain is read again to select the next current repair node.

If the uncle is null or has a nonzero color:

- If the current node equals the parent’s right child, F-c470755d11e4 receives the tree and the saved parent address. After it returns, the current repair node becomes that saved parent.
- The parent reached through the current repair node is colored one.
- The grandparent reached through the current parent chain is colored zero.
- F-b951efde8a28 receives the tree and the grandparent address obtained through the then-current parent chain.

The parent-chain reads after a structural call observe whatever state that dependency leaves. They are not fixed to the pre-call ancestry.

### Parent does not match the grandparent’s left child

Here the saved grandparent-left-child address is treated as the uncle address for color testing.

If it is nonnull and its color is zero, the same red-uncle recoloring and upward advancement described above occur.

Otherwise, if the current repair node equals the parent’s left child, the displayed invocation of F-b951efde8a28 has six operands:

| Position | Observed operand |
|---:|---|
| 1 | Tree address |
| 2 | Saved parent address |
| 3 | Saved grandparent-left-child address |
| 4 | If operand 3 is null: the 32-bit grandparent address. Otherwise: the uncle’s nonzero color byte widened to an unsigned 32-bit value. |
| 5 | Original side-control value, unless the comparison-controlled attachment path was entered, in which case zero |
| 6 | Original attachment-parent value, unless the comparison-controlled attachment path was entered, in which case zero |

The fourth-operand distinction follows from the branch’s short-circuit color test. A null uncle leaves the previously obtained grandparent address in that operand. A nonnull uncle replaces it with the unsigned widened color byte; zero would have selected recoloring instead, so the color supplied here is nonzero.

After this call, the current repair node becomes the saved parent address.

Whether or not the six-operand call occurs, the function then:

- Colors the current parent one.
- Colors the current grandparent zero.
- Calls F-c470755d11e4 with the tree and the grandparent obtained through the current parent chain.

Repair returns to the root and parent-color stopping tests.

### Final root color and publication

Once repair stops, the function reloads the header, reads its root link, and writes byte value one to that root’s color field. There is no visible null-root guard.

It then writes the original node address to the four-byte output slot.

That publication does not instead return the final root or the last repair node. It also does not prove that the original node remains reachable: structural dependencies may alter membership, and publication itself may overwrite tree storage if aliased.

## Acceptance examples

These are conditional static criteria, not runtime observations. Unless an example concerns invalid input, assume valid accessed storage, non-overlapping relevant fields, normal dependency returns, and the stated link stability.

1. **Stable header attachment.**  
   If the attachment parent equals a stable header, comparison is skipped. The function writes the node to header +8, +4, and +12 in order, then writes the header as the node’s parent. Repair immediately recognizes the node as root. The function colors it one and publishes its address.

2. **Forced left attachment.**  
   A nonzero side control with a non-header parent skips comparison and writes the parent’s +8 link. Header +8 changes only if its observed value equals the attachment parent.

3. **Comparison-selected right attachment.**  
   Zero side control, a non-header parent, and a zero comparison result select parent +12. The count increment has already occurred. The retained fifth and sixth operands for any later six-operand call are zero.

4. **Comparison-selected left attachment.**  
   Under the same comparison-entry conditions, any nonzero result selects parent +8. The retained operands remain zero even though attachment is left-sided.

5. **Nonzero parent color.**  
   If the current repair node is not root and its parent color is any nonzero byte, repair stops without entering a recoloring branch. The final observed root still receives color one.

6. **Red uncle.**  
   A nonnull, zero-colored uncle causes parent and uncle to receive one, followed by a parent-chain-derived grandparent receiving zero. Repair advances upward using newly read links.

7. **Six operands with no uncle.**  
   In the complementary branch, if the saved grandparent-left-child address is null and the triangle condition holds, the six-operand call receives null as operand three and the 32-bit grandparent address as operand four.

8. **Six operands with a nonzero-colored uncle.**  
   If that saved child address is nonnull with color 128, and the triangle condition holds, operand three is its address and operand four is unsigned 32-bit value 128. Operands five and six are the original controls or both zero according to whether comparison was entered.

9. **Null node result or occupied position.**  
   A null node result is not a defined recoverable failure. An occupied selected child link is overwritten without rejection.

10. **Publication without proven membership.**  
    If a structural dependency disconnects the original node while leaving subsequent accesses valid, the final output assignment still publishes that original address. If the output slot aliases a tree link, publication can overwrite that link after root recoloring.
