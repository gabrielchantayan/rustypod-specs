# F-71980e76ca3a

## Purpose

F-71980e76ca3a constructs a candidate object from a context and a descriptor, then decides whether to return that candidate using a final context-status observation.

The established contract has two distinct aspects:

- **Construction:** request candidate storage, populate a header, and associate ordered 32-bit dependency results with individual source bytes.
- **Acceptance:** return the acquired candidate only when the final status observation is zero. Otherwise, submit that candidate to F-94cb53877c15 and return null if that dependency completes normally.

Construction is not conditional on an initially clear status. Rejection occurs after construction, not before it.

**Inferred intent:** the candidate appears to be a compact object containing a header, a word sequence, and a byte sequence. The status may indicate an error, and rejection may perform cleanup. None of these interpretations establishes allocation, ownership, or destruction semantics.

This contract describes normal completion with valid memory accesses and returning dependencies. Invalid accesses, arithmetic outside established representable ranges, and dependency failures have no established recovery behavior.

## Behavior

### Construction scope

Acquisition through F-f053f140662a is attempted for positive, zero, and negative captured counts. Its arguments are the context’s first word and the calculated extent **16 + 5 × count**.

The count is captured before acquisition. The context word supplied to acquisition is not the authoritative snapshot for the candidate header: a later observation supplies that header word.

A null acquisition result excludes all direct candidate initialization and entry processing. It does not exclude the final status decision or rejection.

A non-null acquisition result permits construction without an intervening status check. Neither an initially nonzero status nor a status raised during entry processing independently stops construction.

### Header visibility and publication

The initial header has the following visibility constraints:

- The first header word is written before the byte-region address.
- Both writes precede entry processing.
- The count field is written after entry processing, including when there are no entries.
- The final status observation follows that count publication.

Consequently, an observer cannot treat the candidate’s count field as initialized by this invocation before publication. For a positive count, publication follows completion of all entry operations.

Publication is not a preservation guarantee. Dependencies or overlapping storage may have changed previously written header fields, results, or bytes. The function does not restore such contents before returning.

### Entry semantics

For a positive captured count, normal completion processes exactly that many positions in ascending order, beginning at zero.

Each position associates:

1. A 32-bit source value observed through the descriptor’s current word-source base.
2. A 32-bit result from F-039d16ce0621.
3. An associated source byte copied using the byte-source and byte-destination addresses observed for that position.

F-039d16ce0621 receives the context address, the source value, and the 32-bit all-ones value **0xFFFFFFFF**. Its returned word is stored without local interpretation. Zero and all-ones results do not receive special treatment.

The important ordering boundaries are:

- The source word is obtained before its dependency invocation.
- The result word is written before the associated-byte copy.
- That byte copy completes before the next entry’s processing.

The fixed result-word slots begin at candidate offset 16 and advance by four bytes per position. Associated-byte destinations instead use the current address held at candidate offset 12, advanced by the entry position.

### Mutation and overlapping storage

The contract does not require disjoint context, descriptor, candidate, or source storage. Their overlap can affect later observations.

In particular:

- A changed word-source base can redirect a later entry’s source-word read.
- A changed byte-source base can redirect the current entry’s byte read because that read occurs after the dependency invocation.
- A changed candidate byte-region address can redirect the current entry’s byte write.
- The result-word write itself can affect the subsequent byte copy when storage overlaps.

The current entry’s source word has already been selected when F-039d16ce0621 begins. Its associated byte has not.

The representation does not establish a finer order between observing the byte source and observing the byte destination within an individual copy. No alias-sensitive guarantee may depend on choosing one order.

Captured-count behavior remains distinct from mutable-memory behavior. Changing the descriptor count does not change the invocation’s processing cardinality, requested-size calculation, initial byte-region calculation, or final published count. It may nevertheless affect other behavior if the same memory participates in another role.

### Acceptance and rejection

Only the final zero/nonzero observation of context offset 64 determines the normal return decision. That observation occurs after construction when a candidate exists.

A zero observation permits return of the acquired candidate, including null.

A nonzero observation requires F-94cb53877c15 to receive the acquired candidate. If the dependency returns normally, the function returns null even if the dependency changes the status.

Rejection is not established rollback. There is no local promise that candidate contents, entry-dependency effects, ownership changes, or other state are restored.

## Side effects

- Initial header writes before entry processing.
- Each entry’s source-word read before its dependency call.
- Each result-word write before its associated-byte copy.
- Completion of one entry before processing the next.

- A null return does not prove that all resources were released.

There is no direct release of the context or source sequences. Effects of dependencies on those objects, other memory, and globals remain unresolved.
