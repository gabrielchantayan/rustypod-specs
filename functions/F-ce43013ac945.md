# F-ce43013ac945

## Purpose

F-ce43013ac945 interprets a three-byte control request. It obtains control objects, records a request token, queries capabilities, applies operation-specific gates, and invokes control methods. Several operations can save a previous control value and its associated token in shared bookkeeping.

The established contract concerns numeric results, memory accesses, dependency calls, and their ordering. The business meanings of the controls and bookkeeping are unknown. Support for later restoration is inferred intent; this function does not restore saved values.

This specification describes supplied static evidence. No runtime tests have been performed.

## Interface

The function accepts two 32-bit arguments and returns a 32-bit result.

| Argument | Established use |
|---|---|
| First | Opaque value forwarded only by operation 0 to F-c6cb91d68549. |
| Second | Request-object address, passed to F-5f5f14cedda3 and used for metadata reads. |

### Request layout

Offsets are byte offsets from the request-object address.

| Offset | Width | Meaning established here |
|---|---:|---|
| `+0x08` | 32 bits | Payload pointer |
| `+0x0c` | Unsigned 16 bits | Payload length |

The payload contains:

| Offset | Width | Use |
|---|---:|---|
| `+0` | Unsigned 8 bits | Operation selector |
| `+1` | 8 bits | Operation-specific value |
| `+2` | 8 bits | Operation-specific flag, or unused |

The payload pointer and length are captured once. The payload itself is not copied. Individual byte reads can therefore observe dependency-induced changes.

### Results

| Result | Established circumstances |
|---|---|
| 0 | Locally successful completion, subject to operation-specific rules |
| 4 | Common rejection, unsupported selector, operation-specific rejection, or unsuccessful operation 14 status |
| 7 | Zero eligibility result for operations using the ordinary eligibility convention |
| Any 32-bit value | Exact result returned by F-c6cb91d68549 for accepted operation 0 |

These numbers have no established symbolic error meanings.

### Preconditions and ownership

The request must support its metadata reads. It is passed to a dependency before those reads, without local address validation.

Payload, object, dispatch-table, and bookkeeping storage must be usable at every access actually reached. The payload length does not establish memory validity. In particular, some paths read bookkeeping even when no capture will occur.

No explicit allocation, deallocation, release, or ownership transfer appears. Dependency retention, ownership, and lifetime behavior remain documented_only. Invalid-address handling is not established as a numeric error return.

## Behavior

### Common entry processing

The following order precedes payload validation:

1. F-cdd33263ee89 supplies the primary control object.
2. F-5f5f14cedda3 receives the request address and supplies a 32-bit request token.
3. The payload pointer is read, followed by the unsigned 16-bit payload length.
4. F-5fd97c30efdc supplies a capability object.
5. Its dispatch slots `+0x20`, `+0x24`, and `+0x28` are called, in that order. Their full results are retained as capabilities A, B, and C.
6. The shared bookkeeping base is captured.
7. The primary object is checked for null.

A null primary object enters F-a817d8d58c10, represented as nonreturning. This takes precedence over returning 4 for an invalid payload. The capability object is dereferenced without a preceding local null check.

A null payload or captured length below 3 returns 4. Otherwise, the selector is read. Recognized operations require captured length exactly 3 for their accepted request behavior, but some calls and gates occur before that exact-length check. Operation 14 can also dispatch after an exact-length failure.

### Eligibility and capability gates

Operations 0, 1, 2, 4–10, 12, and 13 call F-e3db96f62982 with the captured token. Zero returns 7; nonzero permits further processing. Eligibility precedes exact-length validation.

Operations 4–7 first apply these capability gates:

| Operation | Required entry capability |
|---|---|
| 4 | At least one of A, B, or C is nonzero |
| 5 | A is nonzero |
| 6 | B is nonzero |
| 7 | C is nonzero |

A failed capability gate returns 4 without calling eligibility. Operation 4’s gate enables the combined operation; individually zero capabilities do not suppress individual channels.

Operation 3 has no eligibility call. Operation 14 uses a separate gate and returns 4, not 7, for zero eligibility.

### Operation 0: mapped forwarding

Following nonzero eligibility and exact-length validation, byte 1 must be at most 2 and byte 2 at most 1, using unsigned comparisons. Invalid values return 4.

| Byte 1 | Forwarded 32-bit value |
|---:|---:|
| 0 | 0 |
| 1 | 2 |
| 2 | 1 |

F-c6cb91d68549 receives the first function argument, captured token, mapped value, and the truth value of byte 2. Its entire 32-bit result is returned unchanged.

### Operations 1, 2, and 10: compare, optionally capture, then act

| Operation | Getter slot | Action slot | Flag offset | Saved-byte offset | Token offset |
|---|---:|---:|---:|---:|---:|
| 1 | `+0xc0` | `+0xbc` | `+0x03` | `+0x10` | `+0x40` |
| 2 | `+0xc8` | `+0xc4` | `+0x02` | `+0x0f` | `+0x3c` |
| 10 | `+0xd0` | `+0xcc` | `+0x01` | `+0x0e` | `+0x38` |

Offsets refer to the captured bookkeeping base; methods belong to the primary object.

After eligibility and exact-length validation, the getter runs **before either parameter is validated**. Getter-induced payload changes therefore affect subsequent validation.

Byte 1 must designate numeric 0 or 1. Byte 2 must likewise be 0 or 1. Invalid parameters return 4 after the getter, without the subsequent bookkeeping or action.

The full 32-bit getter result is compared with the requested numeric value from byte 1.

**When those values differ, the existing flag byte is always read before the action call, including when validated byte 2 is 0.** The capture predicate uses bitwise combination rather than short-circuit conjunction. Capture occurs only when byte 2 is 1 and the flag’s least-significant bit is clear. Other flag bits do not affect capture eligibility.

If capture occurs, writes are ordered:

1. Four-byte request token.
2. Flag byte 1.
3. Low eight bits of the getter result.

The action method then runs with the primary object and no explicit requested-value argument. It runs on every valid unequal-value path, whether capture occurred or not. Its result is ignored. Whether it toggles, sets, or otherwise changes a control is unknown.

When current and requested values match, this function performs neither the flag read for capture nor the action call.

Finally, validated byte 2 equal to 0 causes a flag write of 0; byte 2 equal to 1 causes no final clear. Thus the unequal-value path with byte 2 equal to 0 has the specific order **flag read, action call, flag clear**. The read is not omitted merely because capture is disabled.

The validated capture decision is retained across the action call rather than reread from the payload. Valid completion returns 0.

### Operation 3: capability-object action

Captured length must equal 3. Neither parameter byte is inspected.

Capability-object slot `+0x1c` is invoked. A nonzero result yields 0; zero yields 4.

### Operations 4–7: direct channel controls

| Channel | Setter slot | Getter slot | Flag offset | Saved-byte offset | Token offset |
|---|---:|---:|---:|---:|---:|
| A | `+0x68` | `+0x6c` | `+0x08` | `+0x09` | `+0x50` |
| B | `+0x70` | `+0x74` | `+0x0a` | `+0x0b` | `+0x54` |
| C | `+0x78` | `+0x7c` | `+0x0c` | `+0x0d` | `+0x58` |

Following the capability gate, eligibility, and exact-length check:

| Operation | Addressed channels | Byte-1 interpretation |
|---|---|---|
| 4 | A, B, C | Zero becomes 32-bit 0; any nonzero byte becomes 32-bit 1 |
| 5 | A | Unsigned 0–2 accepted numerically; larger values return 4 |
| 6 | B | Zero/nonzero normalization to 32-bit 0/1 |
| 7 | C | Zero/nonzero normalization to 32-bit 0/1 |

Byte 2 accepts every byte value. Zero clears each addressed flag without reading that flag for capture and without calling its getter. Nonzero enables capture consideration.

On capture-enabled paths, each addressed flag is read. Only an entire flag byte equal to zero permits capture. Capture writes flag 1, writes the four-byte token, calls the getter, then writes the returned low byte to saved storage. A nonzero flag suppresses all those capture actions.

Every addressed setter runs regardless of capture. Its selected argument is retained across capture getters; setter results are ignored. Completion returns 0.

For operation 4, all bookkeeping precedes all setters. Flag clearing runs A, B, C. Capture processing also runs A, B, C, with each later flag read occurring after preceding getters return. Setters then run A, B, C with the same retained argument. Consequently, an earlier getter can change a later channel’s capture eligibility by changing its flag, but changing payload byte 1 does not change the retained setter argument.

### Operation 8: selection after a getter

After eligibility and exact-length validation, an unsigned initial byte-1 value above 3 returns 4 without calling the getter.

Otherwise, primary-object slot `+0xe8` supplies a full 32-bit current value. Byte 1 is read again after this call, **without another range check**:

| Post-getter byte 1 | Selected 32-bit value |
|---|---|
| 0 | The returned current value |
| 1 | 1 |
| 2 | 2 |
| Any other byte, including 3–255 | 3 |

Equality of the full current and selected values returns 0 without a setter. Otherwise, slot `+0xe4` receives the selected value; its result is ignored, and the function returns 0. Byte 2 is unused.

A post-getter zero preserves the returned current value even outside 0–3. An initially invalid byte cannot be repaired by this getter because rejection precedes the call.

### Operations 9, 12, and 13: strict Boolean setters

| Operation | Getter slot | Setter slot | Flag offset | Saved-byte offset | Token offset |
|---|---:|---:|---:|---:|---:|
| 9 | `+0xf0` | `+0xec` | `+0x04` | `+0x11` | `+0x44` |

| 13 | `+0xf8` | `+0xf4` | `+0x06` | `+0x13` | `+0x4c` |

After eligibility and exact-length validation, byte 1 is checked first and byte 2 second. Each must be 0 or 1; otherwise return 4.

The 32-bit setter argument is selected before any capture getter. Byte 2 equal to 0 clears the flag without a capture flag read or getter call. Byte 2 equal to 1 reads the flag and captures only if the whole byte is zero.

Capture ordering differs from operations 4–7: the getter runs first, followed by writes of saved low byte, token, and flag 1, in that order.

The setter always runs with the retained argument, even if capture was suppressed or the control already has the requested value. Its result is ignored; completion returns 0.

### Operation 14: separately gated dispatch

Capability-object slot `+0x2c` runs first. Zero returns 4 without final dispatch.

After a nonzero gate, the selected control argument starts at 0 and eventual status at 4. Eligibility is checked. Only nonzero eligibility and captured length exactly 3 permit classification:

- F-76ed42657cca receives the token. Zero qualifies directly.
- Otherwise, an unidentified dependency supplies an address. That address plus 4 and the token are passed to F-1bc5bcdc9cca. Only result `0x0000d000` qualifies.

For a qualifying request, byte 1 equal to 1 selects argument 1; every other value selects 0. Nonqualifying requests retain argument 0.

Within the eligible, exact-length path, a subsequent unsigned byte-1 read below 2 changes the status to 0 independently of qualification. Byte 2 is unused.

After any successful capability gate, F-15643c36365d supplies a final control object. Its slot `+0x44` receives the selected argument. The method result is ignored; the selected status is returned.

Therefore, zero eligibility or nonexact length still dispatches argument 0 and returns 4. Failed classification with byte 1 equal to 0 or 1 dispatches argument 0 but returns 0. Common null-payload and minimum-length failures occur earlier and never reach this dispatch.

## Side effects

Bookkeeping flags and saved values occupy one byte each; token fields occupy four bytes. Clearing a flag does not erase its token or saved value.

Reads are part of the contract independently of writes. In particular, operations 1, 2, and 10 read their flag on every valid unequal-value path, even with capture disabled. That read precedes the action, and any final clear follows the action.

There is no visible rollback or restoration. Dependency failure or nonreturn can leave earlier calls and writes effective.

Captured object pointers, metadata, token, capability results, and bookkeeping base are not refreshed automatically. Changing request metadata after capture does not redirect payload reads. Payload and bookkeeping contents remain observable at their individual read points.

Dependencies are not assumed to preserve globals, memory, objects, or dispatch tables. Retaining an object pointer does not establish that subsequent method lookup yields the same implementation. No synchronization or atomic transaction is established.

Observed widths are 8-bit payload and bookkeeping bytes, unsigned 16-bit length, and 32-bit arguments, pointers, tokens, selected control values, and full-value comparisons. Saved results retain only their low eight bits.

Address arithmetic uses fixed byte offsets, including operation 14’s address-plus-4 adjustment. No variable-size traversal or checked address arithmetic is established.

## Evidence

The supplied static representation establishes the field widths, numeric predicates, call ordering, dispatch offsets, and bookkeeping access sequences described above.

For operations 1, 2, and 10, the unequal-value branch contains a flag-byte access as an operand of the bitwise capture predicate. It is not guarded by short-circuit evaluation of the capture decision. The action follows that predicate, and the byte-2-zero flag clear follows the action.
