# F-9e8aef50590c

## Purpose

F-9e8aef50590c selects one of two fields in an indexed object and replaces that field with the least significant bit of an unsigned input value.

The selector determines which field is written:

- Selector **4** targets the 32-bit field at object-relative byte offset **0x118**.
- Selector **5** targets the 32-bit field at object-relative byte offset **0x198**.
- Any other selector produces the 32-bit result **0xFFFFFF0D**, after the object-address lookup has already occurred.

A supported selector produces result **0** after the selected write completes.

These are static observations from the supplied representation, not runtime-verified behavior. The application meanings of the object, the selectors, and the two fields are unknown. Treating the fields as flags is inferred intent, not an established semantic guarantee.

## Interface

### Inputs

| Input | Width and interpretation | Role |
|---|---|---|
| Object index | Signed 16-bit integer | Selects an entry in a global table using a byte stride of 0x18C, or 396 bytes. |
| Field selector | Signed 32-bit integer | Chooses the destination field when equal to 4 or 5. |
| Input value | Unsigned 32-bit integer | Supplies the least significant bit used as the complete replacement field value. |

The signed interpretation of the object index matters. Negative indices are not rejected and produce displacements before the table base. Whether any such entry is valid depends on the surrounding memory layout.

The supplied representation does not establish how an external caller’s wider argument is converted into the signed 16-bit index. This contract starts with the value received at the stated interface.

### Return value

The result is a 32-bit quantity:

| Condition | Result bits |
|---|---|
| Selector is 4 or 5 and the required accesses complete | 0x00000000 |
| Selector is neither 4 nor 5 and the initial lookup completes | 0xFFFFFF0D |

Interpreted as a signed 32-bit integer, 0xFFFFFF0D is **−243**. Its semantic error category is unknown; no named error or platform error mapping is established.

Memory-access failures are not represented by a separate return value in the supplied body. Normal return requires the accesses on the chosen path to complete.

### Required memory layout

The routine relies on a global location containing a table base. For index \(i\), the selected entry begins at a displacement of \(396 \times i\) bytes from that base.

The first 32-bit quantity at the selected entry is read and subsequently used as an object address for supported selectors. This establishes an address-bearing entry header, not the rest of the entry’s layout. In particular, the 396-byte table stride does not establish the size of the separately addressed object.

For selector 4, four writable bytes must exist at object offsets 0x118 through 0x11B. For selector 5, four writable bytes must exist at offsets 0x198 through 0x19B.

The representation uses a 32-bit integer load as the object address. This supports a 32-bit address model for the described operation; portability to another address width is not established.

## Behavior

### Lookup precedes selector validation

The routine first obtains the table base and reads the address-bearing 32-bit quantity at the indexed entry. Only afterward does it decide whether the selector is supported.

Consequently, an unsupported selector does **not** bypass table access. A caller cannot rely on receiving 0xFFFFFF0D when the table-base location or selected entry is inaccessible.

For the full signed 16-bit index range, multiplying the index by 396 fits within signed 32-bit arithmetic:

- Index −32768 yields a displacement of −12,976,128 bytes.
- Index 32767 yields a displacement of 12,975,732 bytes.

Thus, the stride multiplication itself does not overflow a signed 32-bit integer for an input of the declared width. This does not establish that adding the displacement to the table base produces a valid address. Address-space boundaries, allocation extent, and valid entry ranges remain external preconditions.

### Selector 4

For selector 4, the routine writes the input value masked to its least significant bit into the 32-bit field at object-relative offset 0x118.

The stored value is exactly:

- **0**, when the input value is even.
- **1**, when the input value is odd.

This is a complete 32-bit replacement. It is not an update that preserves other bits in the destination field. For example, a previous field value with upper bits set becomes exactly 0 or exactly 1.

No read of the previous destination value is expressed. After the store completes, the routine returns zero.

### Selector 5

For selector 5, the same normalization and replacement apply at object-relative offset 0x198.

The field at offset 0x118 is not an additional destination on this path. After the store completes, the routine returns zero.

### Unsupported selectors

Any signed 32-bit selector other than 4 or 5 produces 0xFFFFFF0D once the initial lookup has completed.

This path expresses no destination-field write and no access through the loaded object address. Therefore, an unusable loaded object address need not prevent this return, provided that reading the address-bearing table entry itself succeeds.

The routine does not clamp, remap, or otherwise normalize unsupported selectors.

### Successful-access preconditions

The supplied body contains no checks for:

- A valid table base.
- An in-range object index.
- A nonzero or otherwise valid loaded object address.
- Sufficient object extent for the selected field.
- Writable destination memory.
- Alignment or concurrent access safety.

These conditions must be supplied by the caller or environment where needed. Their absence must not be converted into invented error returns.

## Side effects

The explicit memory-access sequence is:

1. Read the global table-base value.
2. Read the 32-bit address-bearing quantity at the selected table entry.
3. For selector 4 or 5, write one 32-bit normalized value at the selected object-relative offset.

There is no expressed write to the table entry, no destination read-modify-write, and no explicit write to the other candidate field.

The routine contains no expressed allocation, deallocation, ownership transfer, reference-count operation, callback, logging operation, or external function call. It uses existing memory; it does not establish who owns that memory or how long it remains valid.

No synchronization mechanism is expressed. Atomicity, visibility across threads, protection against concurrent replacement of the table entry, and device-memory ordering are not established. The source-level access sequence does not by itself specify machine-level memory barriers or instruction ordering.

Aliasing is not prohibited by the supplied representation. If a selected destination overlaps the table, the table-base location, or other shared storage, the write may modify that storage. The routine provides no alias check or isolation guarantee.
