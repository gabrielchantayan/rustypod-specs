# F-a0470fde8131

## Purpose

F-a0470fde8131 conditionally scans a sequence of records obtained through an indirect callback. It recognizes an initial record by a 16-bit marker, obtains a bounded iteration count through helper calls, transforms a 32-byte field in each eligible record, and tests that field against a fixed reference. On the first successful comparison, it obtains two 32-bit values through additional helper calls and writes them to the caller’s third and fourth arguments.

The established success condition is a zero result from the comparison dependency, after the initial marker check and record-selection rules have been satisfied. The reference is associated with the name `APPLE_HFS`, suggesting a filesystem-type search. That interpretation is inferred intent, not an independently established description of the callback, record format, or comparison semantics.

Success returns numeric 1. All ordinary unsuccessful paths return numeric 0. Both paths invoke the finalization dependency before returning.

## Behavior

### Initialization and initial record acquisition

The first externally visible call is to F-d9e0ae06e54d with the address of the local pointer state. The retained working-buffer address is captured after this call returns.

The function then reads the first argument’s dispatch-table pointer and selects the entry at byte offset 12. It invokes that entry with four arguments, in this order:

1. The original first argument.
2. The 32-bit integer 1.
3. The retained working-buffer address.
4. The 32-bit integer 1.

The callback result is interpreted as a 32-bit integer. A nonzero result prevents the marker check and all scanning. The function proceeds directly to finalization and returns 0.

If the callback returns zero, the function reads the unsigned 16-bit value at working-buffer offset 0. Scanning proceeds only if this value is `0x4D50`.

The visible marker computation subtracts `0x4000` from the promoted unsigned 16-bit value and tests for `0x0D50`. Across the entire 16-bit input range, this is equivalent to requiring `0x4D50`; no 16-bit wraparound is needed to reach that conclusion.

A different marker causes finalization followed by return 0.

### Iteration count

After successful initial acquisition and marker recognition:

1. F-4055be9c3f18 is called with the working-buffer address plus 4.
2. F-b5c826d2ab04 is called without explicit arguments.
3. Its result is interpreted as a signed 32-bit count.
4. Values greater than 255 are replaced with 255.

There is no lower clamp. A zero or negative signed count produces no iterations and therefore no transformation, comparison, or explicit result stores.

The relationship between the address-taking call and the following no-argument call is not exposed. The contract establishes their order, not an internal decoding mechanism or shared-state implementation.

### Record selection and callback reuse

For a positive effective count, iteration indices run from 1 through that count, inclusive.

Iteration 1 uses the buffer already obtained by the initial callback. No second callback is issued for index 1.

For each later index, the function rereads the first argument’s dispatch-table pointer and the callable entry at byte offset 12. It invokes the selected entry with:

- The original first argument.
- The current index.
- The retained working-buffer address.
- The integer 1.

Thus, later iterations do not necessarily use the callable selected for the initial invocation. Changes to the dispatch table can affect subsequent dispatches.

A zero callback result makes the current buffer eligible for transformation and comparison. A nonzero result skips those operations for that index but does not terminate the scan.

The retained working-buffer address is reused throughout. The body does not allocate a separate buffer per record or restore bytes modified during earlier iterations.

### Field transformation and comparison

For each eligible record, the function processes exactly 32 byte positions in ascending address order, starting at offset 48.

At each position:

- It reads the current byte.
- It calls F-0559024c3751 with that byte value.
- It stores the dependency’s one-byte result back to the same position.

Each byte’s store occurs before the next byte is read. The transformation is not staged in a separate buffer, and no original copy is retained by this body.

After all 32 stores, the function calls F-fca51b715561 with:

- The working-buffer address plus 48.
- A fixed reference associated with `APPLE_HFS`.
- The 32-bit value 32.

A zero comparison result is treated as a match. A nonzero result continues the scan.

The body does not establish whether the byte transformation changes case, whether the comparison stops at a terminator, whether it compares all 32 bytes, or how the reference is padded. Those properties belong to the dependencies and reference data.

### Match handling and output order

On the first zero comparison result, the function performs these operations in order:

1. Calls F-4055be9c3f18 with the working-buffer address plus 8.
2. Calls F-b5c826d2ab04 without explicit arguments.
3. Stores the resulting 32-bit value through the original third argument.
4. Calls F-4055be9c3f18 with the working-buffer address plus 12.
5. Calls F-b5c826d2ab04 without explicit arguments.
6. Stores the resulting 32-bit value through the original fourth argument.
7. Calls F-cc6f52873d53 with the address of the local pointer state.
8. Returns 1.

The output destinations are the original argument values, not destinations recomputed from the possibly replaced working-buffer pointer.

The first output store precedes the second field-processing call. This ordering is significant if the first output destination overlaps the working buffer or other state observed by a dependency.

The two output values are not visibly clamped or range-checked. The signed interpretation and upper clamp used for the iteration count do not apply to these output stores.

No further records are visited after a match.

### Unsuccessful completion

If the count permits no iterations, or every attempted record is skipped or compares nonzero, the function calls F-cc6f52873d53 with the address of the local pointer state and returns 0.

The body performs no explicit result stores on these paths. This is not a guarantee that the caller’s destination storage remains unchanged: it may alias the working buffer, and dependencies may have additional side effects.

## Side effects

The function’s explicit side effects are:

- Creation of local pointer state supplied to initialization and finalization dependencies.
- Indirect callback invocations, including repeated dispatch-table reads.
- In-place modification of the 32-byte field for every eligible record.
- Two ordered 32-bit output stores on a match.

Previously transformed fields are not rolled back when comparison fails. Callback rejection likewise does not trigger restoration of the buffer.

Aliasing is not prohibited by the visible body. If the two output destinations coincide, the second explicit store follows the first at that address. If an output overlaps record data, the write can affect a later helper call. Dependency side effects, including finalization effects, may further change the resulting memory state.

F-cc6f52873d53 is invoked once on every visible ordinary return path. It is not invoked after every record. No exception handling, fault recovery, or cleanup guarantee for nonlocal exits is shown.

Ownership is unspecified. The body does not directly allocate or release storage, but this does not establish that its dependencies refrain from doing so. Calling the last dependency “finalization” describes its position in the lifecycle, not proven deallocation behavior.

The body also does not establish reentrancy, thread safety, preservation of globals, or preservation of caller-visible state by any dependency.

## Acceptance examples

These examples are conditional behavioral checks derived from the static body. None has been executed.

1. **Initial callback rejection.** If initialization and the initial callback return normally, and that callback returns nonzero, the function must skip its marker read, count acquisition, transformations, comparisons, and explicit output stores. It must finalize and return 0.

2. **Unrecognized marker.** If the initial callback returns zero and the unsigned marker is not `0x4D50`, the function must finalize and return 0 without invoking the count-related helper pair.

3. **Nonpositive count.** If the marker matches and the count dependency returns signed zero or a negative value, no record iterations occur. Finalization precedes return 0.

4. **Upper count boundary.** If the count result is 256 and no comparison succeeds, the effective count is 255. There is one initial callback for index 1 and one later callback for each index from 2 through 255. There is no callback for index 256.

5. **First-record match.** If the effective count is positive and the first comparison returns zero, exactly 32 byte-transform calls occur before that comparison. The first output store precedes the helper call for the second output. Finalization precedes return 1. No callback for index 2 occurs.

6. **Rejected intermediate record.** With an effective count of 3, if index 1 compares nonzero, index 2’s callback returns nonzero, and index 3’s callback returns zero, index 2 receives no transformation or comparison. Index 3 is still eligible.

7. **Initialization replaces the buffer.** If initialization substitutes another valid working address, callbacks and record-relative accesses use that address. Successful output stores still use the original third and fourth argument values.

8. **Dispatch entry changes.** If a dependency changes the object’s dispatch entry before a later iteration, that iteration uses the entry found by its fresh dispatch-table reads.

9. **Aliased output affects later processing.** If the first output destination overlaps data observed by the second output’s helper calls, those calls occur after the first store. Acceptance cannot assume both values were obtained from an unchanged record snapshot.
