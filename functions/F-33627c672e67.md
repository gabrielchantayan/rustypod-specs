# F-33627c672e67

## Purpose

F-33627c672e67 interleaves indirect dependency calls with computed-address byte and 32-bit word accesses, then enters an unconditional repeating sequence.

The supplied static representation does not establish an application-level purpose such as decoding, allocation, initialization, or serialization. Repeated address scaling and fixed offsets do not establish object types or field meanings.

The observable behavior includes:

- Three explicit 32-bit inputs, with no explicit consumption of the second.
- Dependence on incoming machine state beyond those inputs.
- Word stores at computed bases plus 20 bytes.
- Byte stores whose destinations depend on unsigned byte reads.
- Values retained across dependency calls rather than reloaded.
- A terminal loop whose carried argument and loop field are independently transformed from the same raw dependency result.

This is a **documented_only** contract based on static evidence. It does not establish that the recovered representation faithfully describes executable instructions.

## Behavior

### 1. Initial calls and first word store

The first dependency target is formed by adding 4094 bytes to incoming control state. The call receives the first explicit argument.

Four further indirect calls follow. The last supplies an index. The routine stores the incoming machine-state payload at the word slot of four times that index.

The four-scaled index is passed to another dependency. Four subsequent calls produce the result retained for the first byte sequence.

The first word payload is not established as an explicit argument, initialized local object, constant, or dependency return.

### 2. First selector-controlled byte sequence

The selector address is one plus the first argument logically shifted right by eight.

The first selector read determines the destination of a byte store containing the low eight bits of the retained dependency result shifted left by two. A dependency then receives that shifted result.

After further calls, including one producing a newer result, the selector is read again. The second byte store uses the **earlier retained result**, masked to 30 bits and logically shifted right by 20. Byte truncation makes this stored value bits 20 through 27 of that earlier result.

The newer result is instead shifted left by two and passed to the next dependency.

The two selector reads are separate observable accesses. Intervening calls may change the selector, so the two byte stores need not share a destination.

### 3. Repeated store selected by the third argument

After additional calls, a value is read from numerical address 60 and converted to unsigned 32 bits. The source-access width and any extension before conversion are not established.

The destination is the word slot of four times the third argument logically shifted right by seven.

The captured value is stored there, passed to a dependency, and stored at the same destination again after intervening calls. There is no explicit reread of address 60 between the stores.

A result obtained before the second store is subsequently shifted left by two and passed onward. It does not replace the retained payload.

### 4. Capturing primary and secondary snapshots

A dependency-derived index supplies a four-scaled base, a sixteen-scaled base, and a retained value formed by shifting the index left by 26.

The routine first stores the four-scaled base at the sixteen-scaled base’s word slot. It then reads a 32-bit word from the four-scaled base’s word slot. This read supplies the **primary snapshot**.

The store precedes the read. If the addresses alias, that ordering matters.

A dependency receives four explicit values: the sixteen-scaled base, the four-scaled base, the retained left-shifted value, and the four-scaled base again. Further calls include forwarding opaque results between dependencies.

The earlier setup store is later repeated using its retained bases, despite an intervening dependency having returned a newer index. That newer index, scaled by four, is passed onward instead.

A subsequent index supplies another four-scaled and sixteen-scaled pair. The retained left-shifted value is logically shifted right by seven. The routine then:

- Stores this new four-scaled base at the new sixteen-scaled base’s word slot.
- Reads a 32-bit word from the new four-scaled base’s word slot, forming the **secondary snapshot**.
- Calls dependencies, including one receiving the four-scaled base in two explicit argument positions.
- Writes the secondary snapshot logically shifted right by eight back to its four-scaled base’s word slot.

The final write uses the captured secondary snapshot, not a fresh read of its source.

### 5. Primary-snapshot transformations and word writes

The following explicit stores occur in order. Each newly introduced setup index comes from a dependency result; intervening calls separate the indicated stages.

| Stage | Destination | Stored 32-bit value |
|---|---|---|
| First setup | Word slot of sixteen times a new index | Four times that index |
| First follow-on | Word slot of the retained four-scaled base | That four-scaled base itself |
| Second setup | Word slot of sixteen times another index | Four times that index |
| Second follow-on | Same sixteen-scaled base’s word slot | Same retained four-scaled value |
| Third setup | Word slot of sixteen times another index | Four times that index |
| Third follow-on | Word slot of eight times the primary snapshot logically shifted right by eight | The third setup’s retained four-scaled value |
| Fourth setup | Word slot of sixteen times another index | Four times that index |
| Fourth follow-on | Word slot of eight times the primary snapshot logically shifted right by eight | That snapshot-derived base itself |

The snapshot-derived base means: logically shift the primary snapshot right by eight, then multiply by eight.

During this portion, dependencies receive the primary snapshot logically shifted right by sixteen, sometimes alongside forwarded opaque results. A later call receives four explicit arguments:

- The snapshot-derived base.
- That base again.
- The primary snapshot logically shifted right by sixteen.
- The retained left-shifted value after a total of three successive logical right shifts by seven.

The first two right shifts update the retained value at separate earlier stages; the third is applied for this argument. Under 32-bit bit-vector interpretation, an index shifted left by 26 and then right by seven three times becomes its original low six bits shifted left by five.

This identity establishes no application-level field meaning.

### 6. Secondary-register payload and further stores

A later dependency exposes a value through a secondary result register. That value supplies:

- A payload multiplied by 16,777,216.
- A destination base multiplied by 67,108,864.

The payload is stored at that base’s word slot and passed to a dependency. After further calls, the same retained payload is stored at the word slot of four times a newly returned index.

Two more store groups follow:

1. A new index supplies four-scaled and sixteen-scaled bases. The four-scaled value is stored at the sixteen-scaled base’s word slot. After intervening calls, that retained four-scaled value is stored at the four-scaled word slot selected by a newer index.
2. Another index similarly supplies a setup store. After intervening calls, the primary snapshot logically shifted right by 24 is stored at the four-scaled word slot selected by another newer index.

The four-scaled value from the second group remains available for later selector-base computation. It is distinct from the earlier secondary snapshot.

### 7. Preparing later byte operations

A further index supplies four-scaled and sixteen-scaled bases. The four-scaled value is stored at the sixteen-scaled base’s word slot.

The retained four-scaled value identified at the end of the preceding stage has bit 31 cleared and is logically shifted right by seven. This supplies the **later selector base**. Its selector address is that base plus one.

A dependency receives the current sixteen-scaled base twice, followed by the primary snapshot logically shifted right by 23.

After additional calls, the routine stores the sixteen-scaled base itself at that base’s word slot. A newer dependency result is shifted left by two and passed onward.

### 8. Later selector-controlled byte operations

Another dependency result supplies a retained byte payload.

The routine reads the later selector and stores the low byte of this payload shifted left by two at the resulting selector destination. A dependency receives that shifted value in three explicit argument positions.

After intervening calls, the selector is read again. The next byte store contains bits 20 through 27 of the retained payload. A newer dependency result is shifted left by two and passed onward instead of replacing that retained payload.

A subsequent result supplies a new byte payload. Its low byte after a left shift by two is written directly to:

**28 plus the primary snapshot logically shifted right by 31.**

This address is either 28 or 29.

Immediately afterward, without an intervening dependency call, the routine reads the later selector again and stores zero at its selected destination. The preceding direct byte store can affect this read if it aliases the selector address.

Further dependencies receive the primary snapshot’s top bit and the latest byte payload masked to 30 bits and logically shifted right by six.

After more calls, the later selector is read again and another zero byte is stored at its selected destination. A recently returned result, shifted left by two, is then passed onward.

The zero stores remain separate operations because calls and fresh selector reads intervene.

### 9. Transition into the terminal loop

A further result is masked to 30 bits and logically shifted right by 25. This becomes the **initial loop field**, ranging from 0 through 31.

A different selector address is formed from the left-shifted payload used for the direct store to address 28 or 29: multiply that retained shifted payload by 1024, then add one. Under 32-bit bit-vector interpretation, this address calculation wraps to 32 bits.

The byte at this **loop selector address** is read, and zero is stored at its selected destination.

A dependency receives twice the initial loop field. The next dependency supplies the **initial carried argument**. That result enters the first loop iteration **without scaling**.

### 10. Terminal repeating sequence

Each iteration begins with an indirect call receiving:

- The current carried argument.
- The current loop field logically shifted right by eight.

Four further indirect calls follow; the last supplies an intermediate result. The loop selector is then read again, and zero is stored at its selected destination.

A dependency receives the intermediate result shifted left by two. Four more indirect calls follow. The last produces the **raw tail result** for that iteration.

Two independent transformations of this same raw tail result establish the next iteration’s state:

| Next state component | Transformation |
|---|---|
| Carried argument | Raw tail result shifted left by two |
| Loop field | Raw tail result shifted left by 26 |

The loop field is **not** formed by shifting the already transformed carried argument left by 26.

The loop selector address remains based on the retained pre-loop byte payload. The selector byte is nevertheless reread each iteration.

The initial loop field is at most 31, so the first iteration’s second argument is zero. Later fields follow the separate tail-result transformation and need not yield zero.

The first iteration also differs in two other respects:

- Its carried argument is an unscaled pre-loop result.
- Its initial call target derives from the pre-loop target state; later iterations use target state established at the loop tail.

## Acceptance examples

These are conditional static acceptance checks, not executed tests. They assume valid accesses, returning dependencies, and the stated memory or arithmetic interpretation.

1. **Selector rereads can select different destinations.**  
   If the first selector read yields 3, the first store targets address 20. If a dependency changes the selector to 9, the later store targets address 26.

2. **The earlier byte payload is retained.**  
   For a retained payload of hexadecimal 12345678, the shifted low-byte store writes hexadecimal E0. Its later extracted-byte store writes hexadecimal 23, regardless of a newer dependency result.

3. **Third-argument indexing discards seven low bits.**  
   Third arguments 0 and 127 select address 20; 128 selects address 24. Both stores use the same captured address-60-derived payload.

4. **The secondary snapshot is not reloaded.**  
   A captured secondary snapshot of hexadecimal 89ABCDEF produces a later store of hexadecimal 0089ABCD, even if an intervening dependency changes the original location.

5. **Setup can affect snapshot capture.**  
   A zero setup index makes both scaled word slots address 20. Under ordinary memory semantics, the setup stores zero before the snapshot read, which consequently obtains zero.

6. **The direct byte destination follows the primary snapshot’s top bit.**  
   A clear top bit selects address 28; a set top bit selects address 29.

7. **Loop-entry and recurring state use different transformations.**  
   The first carried argument is an unscaled pre-loop dependency result, and the first second argument is zero. If an iteration’s **raw tail result** is 1, then under 32-bit bit-vector interpretation the next carried argument is 4, the next loop field is hexadecimal 04000000, and the following second argument is hexadecimal 00040000. A recurring carried argument of 1 is impossible under that interpretation because shifting left by two clears its low two bits.

8. **The next loop field is independent of carried-argument truncation.**  
   If the raw tail result is hexadecimal 40000001, the same bit-vector interpretation again yields carried argument 4 and loop field hexadecimal 04000000. Applying the 26-bit shift to carried argument 4 would instead produce hexadecimal 10000000 and would violate the represented transition.

9. **Zero stores do not guarantee persistent zero.**  
   Each explicit zero store affects its freshly selected destination when reached. A dependency may subsequently change that memory or the selector.
