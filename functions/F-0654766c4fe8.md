# F-0654766c4fe8

## Purpose

F-0654766c4fe8 conditionally obtains a nonnegative handle, invokes associated dependencies, and writes two scaled 32-bit quantities to caller-supplied destinations.

The returned value is not necessarily a success indicator for the output writes. On the path that writes both outputs, the return value is the 32-bit result obtained earlier from F-af004737bec8, without an apparent check of that result. Acquisition failure and a null lookup result instead produce the return bit pattern `0xFFFFFFFF`.

**Established static evidence:** the dependency order, branch conditions, field widths and offsets, output assignment order, and return-value selection described below.

**Inferred intent:** the two destinations may represent related dimensions or counts multiplied by a common factor. Their units and domain meanings are not established.

## Interface

| Item | Contract |
|---|---|

| Second argument | Address of a writable 32-bit destination, called the **second destination** below. |
| Third argument | Address of a writable 32-bit destination, called the **third destination** below. |
| Return | A 32-bit bit pattern: initially `0xFFFFFFFF`, potentially replaced by F-af004737bec8, and reset to `0xFFFFFFFF` if lookup yields zero. |

The destination argument names describe their positions in the interface, not their write order. The third destination is written before the second destination.

The destinations need to be writable only on the branch where acquisition succeeds and lookup returns nonzero. The supplied body does not dereference them on acquisition failure or null lookup. It performs no explicit destination validation.

## Behavior

### Acquisition and dependency sequence

The function first establishes `0xFFFFFFFF` as its prospective return value and calls F-91c65c9d4f51 without arguments.

Its result is tested as a signed 32-bit value:

- A negative result causes immediate return of `0xFFFFFFFF`.
- A zero or positive result is retained as the handle for the remaining dependency calls.

Thus, zero is an accepted handle. Failure is not restricted to a result of negative one; every negative result takes the early-return path.

For a nonnegative handle, the function performs these calls in order:

1. F-6443787f9616 with the handle. Its result, if any, is unused.
2. F-af004737bec8 with the handle. Its 32-bit result becomes the prospective return value.
3. F-18bc1d07eb44 with the handle. Its result is tested against zero and, if nonzero, used as the record base.

There is no visible check of the result from F-af004737bec8 before lookup or output processing. Even `0xFFFFFFFF` from that dependency does not itself prevent output writes.

### Null lookup

If F-18bc1d07eb44 returns zero:

- The prospective return value becomes `0xFFFFFFFF`, replacing any result from F-af004737bec8.
- Neither destination is written directly by this function.
- F-591e5dd605b9 is called with the handle.
- The function returns `0xFFFFFFFF`, provided that final call returns normally.

This does not establish that dependencies leave the destination memory unchanged. Their indirect effects are unknown.

### Nonzero lookup and ordered output accesses

For a nonzero lookup result, the supplied representation establishes the following sequence of field reads and destination assignments:

1. Read the 32-bit quantity at offset 500.
2. Write that quantity, unscaled, to the third destination.
3. Read the unsigned 16-bit factor at offset 460.
4. Multiply that factor by the quantity retained from step 1.
5. Write the 32-bit product to the third destination.
6. Read the 32-bit quantity at offset 124.
7. Subtract two from that quantity.
8. Write the adjusted quantity, unscaled, to the second destination.
9. Read the unsigned 16-bit factor at offset 460 again.
10. Multiply this newly read factor by the adjusted quantity retained from step 7.
11. Write the 32-bit product to the second destination.

There are two assignments to each destination. The initial assignments are part of the represented behavior; the function does not merely compute both final values and then publish them.

The factor is read twice rather than captured once for both products. With stable, non-overlapping memory, the two reads obtain the same value. With aliasing or externally changing memory, equality is not guaranteed.

The read at offset 500 is retained for the third-destination calculation. Changing that field through the initial third-destination write does not cause it to be reread. Likewise, the adjusted quantity for the second destination is retained across its first write.

After these assignments, F-591e5dd605b9 is called with the handle. The function then returns the saved result from F-af004737bec8, provided execution and the final dependency return normally.

### Arithmetic widths

The factor is unsigned and 16 bits wide, so its numeric range is 0 through 65,535. It is widened to an unsigned 32-bit operand for multiplication. The other operand consequently participates as a 32-bit unsigned value, including when its signed interpretation is negative.

Each product is a 32-bit result modulo \(2^{32}\). There is no visible saturation, overflow error, or wider result exposed to the caller. A negative retained quantity is therefore multiplied using its corresponding unsigned 32-bit bit pattern.

The subtraction of two is represented as signed 32-bit arithmetic. If the field at offset 124 is at least \(-2{,}147{,}483{,}646\), the mathematical result is representable. For either of the two smaller signed values, the supplied representation alone does not establish whether the original execution contract guarantees wrapping or treats the arithmetic as outside its valid domain. Those cases are documented-only unknowns, not unconditional wrapping guarantees.

### Aliasing

The supplied body contains no non-aliasing check.

If the second and third destinations are the same valid 32-bit location, and neither overlaps the source fields, the second destination’s final product overwrites the third destination’s final product. The shared location therefore ends with the second calculation, subject to any later effects of F-591e5dd605b9.

If a destination overlaps the record:

- The first third-destination write can change the factor before its first read.
- Either third-destination write can change the field at offset 124 before that field is read.
- The first second-destination write can change the factor before its second read.

Consequently, a model that snapshots all three record fields before writing either destination is not equivalent for all aliasing arrangements.
