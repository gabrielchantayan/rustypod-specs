# F-d040ad03a6d9

## Purpose

F-d040ad03a6d9 decodes a byte stream into sequential 16-bit destination units. Its intrinsic decoding accepts ASCII and selected two- and three-byte forms resembling UTF-8. It rejects four-byte leading forms, accepts some overlong two-byte forms, and does not exclude surrogate values.

Two option bits enable opaque dependencies:

- `0x00000004`: conversion of a successfully decoded multibyte value, potentially producing two output units.
- `0x00000001`: a dependency call immediately before each applicable output store, whose return value replaces the value being stored.

Processing stops on a zero leading byte, exhaustion of the declared input count, an encoding rejection, or a destination-boundary failure. Errors retain preceding output. The reported output length is in **bytes**, not 16-bit units.

Text decoding with optional conversion is inferred intent. The dependency mappings, transformation semantics, and external error-code meanings are not established.

## Interface

The function accepts seven positional arguments and returns a 32-bit status.

| Position | Input |
|---|---|
| 1 | Address of the input bytes. |
| 2 | Signed 32-bit input-length value. Zero stops processing, but this value does not bound continuation-byte reads. |
| 3 | Address of destination storage, written in 16-bit units. |
| 4 | Address of a writable 32-bit output-byte-count field. |
| 5 | Unsigned 32-bit destination extent, measured in bytes. |
| 6 | Opaque 32-bit value with no explicit use in the supplied body. |
| 7 | Unsigned 32-bit flags. Only bits `0x1` and `0x4` are explicitly tested. |

### Results

| Status | Established meaning |
|---|---|
| `0x00000000` | Processing ended because the remaining input count was zero or a zero leading byte was encountered. |
| `0x00000016` | The current encoded form was rejected. |
| `0x0000003F` | The destination cursor reached or passed its boundary before the next required output operation. |

Every explicit return writes the output-byte-count field. These guarantees describe normal execution through the supplied body; invalid memory accesses or abnormal dependency exits are not converted into these statuses.

### Storage and arithmetic

Address calculations and output-count reporting use a 32-bit address representation. The destination boundary is the original destination address plus the unsigned byte extent. The final count is the accounted destination-address difference, written as a 32-bit quantity.

Safe use requires:

- A valid writable output-count field.
- Suitable backing storage and alignment for every 16-bit destination store.
- Readable input covering every byte actually inspected, including continuation bytes beyond the declared count.
- Address arithmetic that does not wrap.
- Defined signed input-count arithmetic.
- Dependency behavior compatible with the supplied temporary storage.

A nonnegative input count covering complete encoded forms and an even destination extent are ordinary safe-use conditions, not validations performed by the function. An odd extent can permit a store extending one byte beyond the declared boundary.

No destination terminator is appended. No consumed-input count or final input address is returned.

## Behavior

### Entry and leading-byte inspection

The function establishes the destination boundary before inspecting input. It initially accounts for zero output bytes and selects success as its status.

At the beginning of each iteration, it forms the remaining input count minus one. Equality of that result to `-1` selects successful termination without reading input. For arithmetic within its defined range, this is equivalent to testing whether the current count is zero.

Otherwise, the function reads the leading byte. A zero leading byte terminates successfully without emitting a unit. Bytes after that terminator are not decoded.

Only after this leading-byte read and zero-byte decision does it compare the destination cursor with the boundary. Processing requires the cursor to be strictly below the boundary. This test does not require two bytes to remain.

Consequences:

- Count zero succeeds without reading input, including with zero destination capacity.
- A zero leading byte succeeds even when the destination is full.
- A nonzero leading byte is read before a full-destination error.
- A full destination takes precedence over validating that nonzero byte’s encoding.
- With one byte of declared destination space remaining, a 16-bit store is still permitted.

### Intrinsic decoding

#### Single-byte forms

Leading bytes `0x01`–`0x7F` produce the same numeric value. They bypass the optional multibyte conversion dependency.

A literal `0x00` never reaches ordinary output handling: it has already terminated processing.

#### Two-byte forms

Leading bytes `0xC0`–`0xDF` select a two-byte form. The continuation byte must have its high two bits equal to binary `10`.

An additional gate applies to leads `0xC0` and `0xC1`: the continuation byte must equal `0x80`. Leads `0xC2`–`0xDF` do not have this additional restriction.

The decoded value combines five lead payload bits and six continuation payload bits. Thus:

- `C0 80` decodes to zero.
- `C1 80` decodes to `0x0040`.
- Other continuations after `C0` or `C1` are rejected.
- Accepted two-byte values do not exceed `0x07FF`.

This is not strict UTF-8 validation: two overlong representations are admitted.

#### Three-byte forms

Leading bytes `0xE0`–`0xEF` select a three-byte form.

The first continuation byte must have the continuation prefix. The partial value formed from the lead and that byte, shifted into position for the final six bits, must be greater than `0x07FF`. Only then is the final continuation examined. That final byte must also have the continuation prefix.

For stable input:

- Values below `0x0800` are rejected.
- The largest decoded value is `0xFFFF`.
- `0xD800`–`0xDFFF` are accepted; no surrogate exclusion appears.
- No noncharacter exclusion appears.

An explicit 32-bit mask is present in partial-value construction, but it does not change values possible from these fields.

#### Rejected leading forms

Nonzero leads `0x80`–`0xBF` and `0xF0`–`0xFF` are rejected after the initial capacity check.

The intrinsic decoder has no four-byte path and does not itself construct a surrogate pair for a supplementary character. This restriction does **not** establish what the optional conversion dependency can produce: that dependency can supply two units whose mapping is unknown.

### Continuation reads and input-count handling

Continuation reads are not guarded by the remaining input count.

The supplied expression structure also contains repeated reads of continuation addresses:

- For `C0` or `C1`, the extra gate reads the continuation before the separate prefix check.
- An accepted two-byte continuation is read for prefix validation and again for payload extraction.
- In a three-byte form, the first continuation is captured once; the final continuation has separate prefix and payload reads.

These distinctions matter for unstable or externally modified memory. The ordinary decoding descriptions assume stable input; no concurrency, volatile-memory, or machine-level load guarantee is supplied.

Successful decoding prepares an input-count reduction of one, two, or three bytes. That remaining count becomes the next iteration’s count after the ordinary output store completes. A two-unit conversion still consumes only the original encoded character.

If a declared count of one accompanies accessible bytes `C2 A2`, the function can decode and emit `0x00A2`, leaving a negative remaining count. Processing then continues rather than stopping for insufficient declared input. Negative initial counts likewise do not mean empty input.

Signed overflow in these count calculations is not established as a supported interface behavior.

### Optional multibyte conversion

After successful two- or three-byte decoding, flag `0x4` enables F-0e9b7551ba6d. The call supplies:

- The decoded numeric value.
- The address of temporary storage consisting of two 16-bit slots.

The dependency’s 32-bit return becomes the current output value. The function then reads the temporary’s first 16-bit slot.

That **first read** selects the output path:

- Zero selects ordinary single-unit output of the returned value.
- Nonzero selects a two-unit path.

There is no visible initialization or reset of this slot before a conversion call. Predictable branch selection therefore requires the dependency to establish a defined first-slot value for that call. Only the first slot is explicitly read by this function.

On the two-unit path, the observable order is:

1. Optionally call F-0ec8efa9c769 if flag `0x1` is set.
2. Store the low 16 bits of the current returned value as the first unit.
3. Account for that unit by advancing the destination position two bytes.
4. Check whether that advanced position is strictly below the destination boundary.
5. If not, return `0x3F`, retaining and counting the first unit.
6. Otherwise, **reread** the conversion temporary’s first slot to obtain the second value.
7. Send this reread value through ordinary output handling.

The second value is not a saved copy of the value used for branch selection. No second-slot read occurs on this path.

The intervening dependency call cannot be assumed to preserve the first slot. F-0e9b7551ba6d received its address, and dependency retention and shared-state effects are unknown. Consequently, an initially nonzero slot can select two-unit output while its later reread supplies a different value, including zero.

If capacity fails after the first unit, the second slot read and second output operation do not occur.

### Ordinary output handling

The ordinary path replaces a current numeric value equal to zero with `0x002F`.

If flag `0x1` is set, F-0ec8efa9c769 is called next. No explicit argument is shown. Its return replaces the value to be stored.

The function then writes the low 16 bits and advances the accounted destination position by two bytes.

Important distinctions:

- The separate first store of a two-unit conversion bypasses zero substitution.
- The reread second value enters ordinary zero substitution, even if its initial branch-selection value was nonzero.
- Substitution happens before F-0ec8efa9c769, not after it.
- A zero returned by F-0ec8efa9c769 is stored as zero.
- A nonzero wider conversion result whose low 16 bits are zero is not replaced merely because truncation produces a zero unit.

Flag `0x1` can therefore cause two dependency calls for one converted input character, one before each store.

### Completion and partial output

The final output-byte count includes every accounted 16-bit store. In particular, it includes the first unit of a two-unit conversion when capacity prevents its second unit.

An encoding error contributes no output for that character. Earlier stores remain intact. Neither decoding errors nor destination errors roll back output.

## Side effects

The body directly performs input reads, sequential 16-bit destination stores, reads of the conversion temporary’s first slot, and a final 32-bit output-count write.

The output-count write follows destination stores. If its field aliases destination storage, that final write can overwrite output. No alias check appears.

Input and destination overlap is also unchecked. Earlier output stores may modify bytes inspected in later iterations. Behavior in that situation cannot be derived from an immutable snapshot of the original input.

The visible body does not allocate, release, or explicitly retain caller-provided storage. It exposes temporary storage to F-0e9b7551ba6d. This does not establish either dependency’s ownership, retention, callback, global-state, or exceptional-control-flow behavior.

Argument six is not directly consumed. Its lack of direct use does not establish independence of unknown dependencies from ambient state.

## Acceptance examples

These are conditional static examples, not runtime observations. Unless stated otherwise, input is stable, flags are zero, storage is valid and nonoverlapping, address arithmetic does not wrap, and declared lengths and capacities suffice.

1. **Empty input:** Count zero causes no input read, returns `0`, and reports zero output bytes.

2. **Terminator:** `41 00 42` emits `0x0041`, then returns success with count two. `42` is not decoded.

3. **No appended terminator:** `41` with input count one emits one unit and reports two bytes. No additional zero unit is written.

4. **Ordinary multibyte forms:** `C2 A2` emits `0x00A2`; `E2 82 AC` emits `0x20AC`.

5. **Exceptional two-byte forms:** `C0 80` emits `0x002F` through zero substitution. `C1 80` emits `0x0040`. `C1 81` returns `0x16` without output for that sequence.

6. **Three-byte threshold:** `E0 9F BF` is rejected; `E0 A0 80` emits `0x0800`.

7. **Intrinsic surrogate acceptance:** `ED A0 80` emits the single unit `0xD800`.

8. **Four-byte rejection:** With room available, `F0 90 80 80` returns `0x16` without decoding its continuations.

9. **Capacity precedence:** With zero destination extent, a nonzero leading byte returns `0x3F`, even if invalid. A zero leading byte instead succeeds.

10. **Odd extent:** Extent one with at least two writable backing bytes permits `41` to produce a two-byte store and report two bytes.

11. **Retained prefix:** `41 80` emits `0x0041`, then returns `0x16` with count two, provided capacity remains when `80` is inspected.

12. **Declared-length overread:** Count one with accessible `C2 A2 00` can emit `0x00A2`, continue with a negative count, then stop successfully at the accessible zero.

13. **Stable two-unit conversion:** With flag `0x4`, suppose F-0e9b7551ba6d returns `0x0041` and the first slot reads as `0x0042` both times. Capacity four yields `0x0041, 0x0042`. Capacity two yields only `0x0041`, status `0x3F`, and count two; no second slot read occurs.

14. **Changed slot:** With both flags set, suppose the initial slot read is nonzero, the intervening F-0ec8efa9c769 invocation returns `0x0041` and changes that slot to zero, and capacity permits continuation. The first unit is `0x0041`; the reread second value is zero and undergoes ordinary substitution before the second dependency call. The second stored unit depends on that call’s return, not the original slot value.

15. **First-unit zero:** With only flag `0x4`, a conversion return of zero and an initially nonzero slot produces a zero first unit. If the later slot reread is zero, the second unit is `0x002F`.

16. **Possible converted surrogate pair:** If conversion returns `0xD800` and both slot reads yield `0xDC00`, sufficient capacity produces those two units. The body does not forbid this dependency-defined result.

17. **Truncation:** If F-0ec8efa9c769 returns `0x12345678`, that store writes `0x5678`.
