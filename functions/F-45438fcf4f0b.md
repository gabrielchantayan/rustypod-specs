# F-45438fcf4f0b

## Purpose

F-45438fcf4f0b partially populates an existing destination object from a source record, a separately supplied selector byte, and additional entry-state values. It validates two source fields, selects a mode-dependent value, calls an assessment dependency, and derives further destination fields.

The operation is not transactional. Rejection leaves earlier writes in place. A successful path additionally increments a shared counter and calls a second dependency.

“Population,” “assessment,” and “completion” describe the apparent roles of these operations, not established application-level meanings. The evidence does not establish that the entry-state values used for initialization are zero and one.

## Behavior

The following ordering describes the accesses visible in the supplied static representation. It is not a claim about atomicity, synchronization, or hardware-level access guarantees.

### 1. Initial population

Before any visible rejection, perform these accesses in order:

1. Write the fill byte to Destination + `0x48`.
2. Read the selector byte through the selector pointer; write that captured byte to Destination + `0x58`.
3. Read and copy these source words, one pair at a time:

   | Source offset | Destination offset |
   |---|---|
   | `0x04` | `0x50` |
   | `0x18` | `0x64` |
   | `0x14` | `0x54` |
   | `0x28` | `0x74` |

4. Write the fill word to Destination + `0x88`, then `0x84`.
5. Write the marker byte to Destination + `0x8D`.

The captured selector then determines the following accesses:

| Captured selector | Ordered behavior |
|---|---|
| 0 or 7 | Write the fill byte to destination offsets `0x42`, then `0x43`. Individually read source bytes `0x30`–`0x33` and write them to destination bytes `0x5D`–`0x60`, in increasing order. |
| 1, 2, or 5 | Write the fill byte to destination offsets `0x42`, then `0x43`. |
| 3 | Write the fill byte to destination offsets `0x42`, then `0x43`. Individually read source bytes `0x2C`–`0x2F` and write them to destination bytes `0x59`–`0x5C`, in increasing order. |
| 4 | Read Source + `0x10` and write that byte to Destination + `0x42`; then read Source + `0x11` and write it to Destination + `0x43`. |
| 6 or any other byte | No additional accesses in this selector-dependent stage. |

An unlisted selector does not itself cause rejection. This dispatch uses the captured selector, not a reread of its original storage.

### 2. Width-like field

Read Source + `0x08` as an unsigned 32-bit word, then write the fill byte to Destination + `0x40`.

- If the captured source value is at most 8, continue without writing Destination + `0x3C`.
- Otherwise, read Source + `0x08` again as unsigned:
  - If this second value exceeds 16, return `0xFFFFFFFF`.
  - Otherwise, write the marker word to Destination + `0x3C` and continue.

For stable source memory, values 0–8 pass without initializing `0x3C`; values 9–16 pass after initializing it; larger unsigned values reject.

There is no lower-bound rejection. The second read occurs only when the first value exceeds 8. If the first value exceeds 8 but the second is at most 8, the marker write still occurs.

The write to Destination + `0x40` separates the two possible source reads. Overlap can therefore affect the second value.

### 3. One-or-two field

Read the 32-bit field at Source + `0x0C` and compare it with 1.

- If equal to 1, write the marker byte to Destination + `0x41`.
- Otherwise:
  1. Write the fill byte to Destination + `0x41`.
  2. Read Source + `0x0C` again and compare it with 2.
  3. If unequal to 2, return `0xFFFFFFFF`.
  4. If equal to 2, read Destination + `0x3C` as a signed 32-bit value, add one, and write the result back.

For stable source memory, only 1 and 2 pass. The increment can use pre-existing destination state because the preceding stage need not initialize `0x3C`. Signed-overflow behavior is not established.

After either accepted branch, read Source + `0x0C` again and copy that word to Destination + `0x14`. This final read need not match either comparison read.

### 4. Common initialization

After those validations pass, perform these writes in order:

1. Fill word to Destination + `0x08`.
2. Fill word to Destination + `0x0C`.
3. Fill byte to Destination + `0x05`.
4. Fill byte to Destination + `0x04`.
5. Fill word to Destination + `0x4C`.
6. Marker byte to Destination + `0x45`.
7. Fill byte to Destination + `0x46`.

### 5. Source-mode dispatch and external data

Read the byte at Source + `0x00`. This mode is independent of the earlier selector.

| Source mode | Behavior |
|---|---|
| 0, 3, or 5 | Write the fill word to Destination + `0x78`; continue. |
| 1 | Read external 32-bit data item A, then write its captured value to Destination + `0x78`; continue. |
| 7 | Read external 32-bit data item B, then write its captured value to Destination + `0x78`; continue. |
| 2, 4, 6, or any other byte | Return `0xFFFFFFFF`. |

Items A and B occupy distinct external locations. Their values may be equal. Neither immutability nor independence from earlier writes is established.

A mode rejection occurs after common initialization. It performs no explicit write to Destination + `0x78` and calls neither dependency.

### 6. Embedded-region assessment

Call F-6d8c85350b66 with Source + `0x40`. Its represented result is a signed 32-bit value; only equality with zero controls the branch. Any nonzero result, including a negative one, selects the nonzero branch.

#### Zero result

Write the fill byte to Destination + `0x28`. Then write the fill word to destination offsets `0x2C`, `0x30`, `0x34`, `0x38`, `0x7C`, and `0x80`, in that order.

This branch performs no explicit source reads from the embedded region after the call.

#### Nonzero result

Perform these accesses in order:

1. Write the marker byte to Destination + `0x28`.
2. Read the word at Source + `0x40`; write it to Destination + `0x2C`.
3. Read Source + `0x44`; retain the signed 32-bit value and write it to Destination + `0x30`.
4. Read Source + `0x48`; retain the signed 32-bit value and write it to Destination + `0x34`.
5. Read Source + `0x50`; retain the signed 32-bit value and write it to Destination + `0x38`.

There is no explicit read of Source + `0x4C`.

Next, read Destination byte `0x58`. If it equals 7, replace destination words `0x30`, `0x34`, and `0x38`, in that order, with the corresponding retained source values shifted left by one bit. These are signed shifts in the representation; behavior for negative operands or results outside the signed range is unresolved.

This decision uses the destination byte after the dependency returns. It need not equal the initially captured selector.

Next:

1. Read Destination + `0x78` as unsigned 32-bit and retain it as the base.
2. Read Destination + `0x30` as signed 32-bit. Convert it to unsigned for addition with the base, add modulo $2^{32}$, and write the unsigned result to Destination + `0x7C`.
3. Read Destination + `0x34` as unsigned 32-bit and compare it with the retained base.
4. If that comparison value is greater than the base, read Destination + `0x34` again as unsigned and subtract the retained base using unsigned 32-bit arithmetic.
5. Otherwise, select signed zero without a second read of `0x34`.
6. Write the selected signed result to Destination + `0x80`.

On the subtraction branch, the unsigned difference is assigned to a signed 32-bit temporary before the destination write. Differences within the signed range convert exactly. Conversion of larger unsigned results is not resolved by the supplied representation.

The two reads of `0x34` are distinct. Only with stable storage between them does this computation correspond mathematically to subtraction floored at zero; even then, the signed-conversion caveat applies to large differences. If the second value is below the base despite the earlier successful comparison, the unsigned subtraction wraps modulo $2^{32}$.

### 7. Successful completion

After either assessment branch:

1. Read the external shared-counter pointer and retain that pointer.
2. Write the fill byte to Destination + `0x8C`.
3. Read the signed 32-bit counter through the retained pointer.
4. Add one and write the result through that same retained pointer.
5. Read the external argument data item.
6. Call F-266a29fc8dc5 with that captured argument and a second argument equal to zero.
7. Return `0x00000000` if the call returns normally.

The counter pointer is captured **before** the destination-byte write. If that write aliases the external pointer’s storage, the increment still uses the previously captured pointer.

Conversely, the final argument is read **after** the counter update. Its value can reflect earlier writes, including an overlapping counter write. Its concrete value and storage width are not independently established by the supplied representation.

The counter increment is represented as signed arithmetic; signed overflow remains unresolved. The final dependency’s result does not determine the visible success result.

## Side effects

### Partial updates

Rejection does not undo earlier writes:

- Width rejection follows initial population, selector-dependent accesses, and the write to `0x40`.
- One-or-two rejection additionally follows the write of the fill byte to `0x41`.
- Mode rejection additionally follows the accepted-field copy to `0x14` and common initialization.

No explicit counter increment or dependency call occurs on those rejection paths.

Fields omitted by a branch are not implicitly cleared. Examples include selector-specific byte ranges, `0x42` and `0x43` for unlisted selectors, and `0x3C` when the first width reading is at most 8 and the first one-or-two reading equals 1.

These preservation statements concern explicit accesses only; overlapping storage can change other fields.

### Aliasing and dependency effects

The function does not snapshot its inputs. Source, destination, selector storage, and external data are not proven disjoint.

Earlier writes can therefore affect later reads. In particular:

- Repeated source-field reads can disagree.
- Mode-specific external data can reflect earlier destination writes.
- F-6d8c85350b66 can affect subsequently read destination or external data unless its independent contract prohibits that.
- The captured counter pointer survives a later change to its external storage.
- The final argument read can observe the counter update.
- F-266a29fc8dc5 can modify state after this body’s final explicit writes.

No synchronization or atomic counter operation is visible.

### Arithmetic distinctions

Unsigned addition for `0x7C` and unsigned subtraction on the `0x80` branch have established modulo-$2^{32}$ arithmetic in the supplied representation. They are not merely assumptions about typical machine wrapping.

Separate unresolved cases are signed increments, signed left shifts, and conversion of an out-of-range unsigned difference to the signed temporary used for `0x80`.

## Acceptance examples

These are conditional specifications, not executed tests. Unless qualified, assume valid disjoint storage, stable values, normally returning dependencies without relevant mutations, and defined signed arithmetic.

1. **Width rejection.** With Source + `0x08` equal to 17 on both reads, return `0xFFFFFFFF`. Initial population and the write to `0x40` have occurred; later validation and both dependency calls have not.

2. **Invalid one-or-two field.** With width 8 and Source + `0x0C` equal to 3, write the fill byte to `0x41`, then reject. Do not increment `0x3C` or perform common initialization.

3. **Pre-existing destination state.** With width 8, the one-or-two field equal to 2, and destination word `0x3C` initially 10, that word becomes 11. With width 9 and marker word 1 instead, it first becomes 1 and then 2.

4. **Late mode rejection.** With accepted validation fields and mode 2, reject after common initialization. Do not explicitly write `0x78`, call either dependency, or increment the counter.

5. **External mode data need not differ.** If items A and B both contain 12, modes 1 and 7 each write 12 to `0x78`. Each mode reads its own external item; distinct locations do not require distinct values.

6. **Zero assessment does not necessarily clear.** With fill word `0x11223344` and assessment result zero, write `0x44` to `0x28` and `0x11223344` to every listed zero-branch word. Continue through successful completion.

7. **Selector-seven scaling.** With the later destination selector equal to 7, nonzero assessment, retained source values 3, 8, and 5, and retained base 2, destination words `0x30`, `0x34`, `0x38`, `0x7C`, and `0x80` become 6, 16, 10, 8, and 14 respectively.

8. **Stable subtraction floor.** With nonzero assessment, no scaling, base 10, and `0x34` stably equal to 6 or 10, write zero to `0x80`. If it is stably 16, the successful comparison is followed by a second read and the stored result is 6.

9. **Unsigned addition wrap.** With no scaling, `0x30` equal to 3, and retained base `0xFFFFFFFF`, write 2 to `0x7C`. This follows established unsigned arithmetic, without relying on signed-overflow behavior.

10. **Changing subtraction operand.** If the comparison reads 12 against base 10 but the second read yields 6, the unsigned difference is `0xFFFFFFFC`. Its subsequent signed conversion and stored result remain **documented_only**; zero is not justified.

11. **Captured counter pointer.** If the external pointer initially identifies valid counter storage and the write to `0x8C` changes that pointer’s stored representation, increment through the originally captured pointer, provided all accesses remain valid.

12. **Late final argument.** If the counter storage overlaps the final argument item, the argument read occurs after the increment and observes the resulting storage according to the unresolved layout and width rules.
