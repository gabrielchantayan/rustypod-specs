# F-8a8704b99c02

## Purpose

F-8a8704b99c02 removes entries from a sentinel-delimited, doubly linked chain and places each removed entry onto a singly linked chain held by the same containing object. It reduces a stored count once for each removal.

Under a stable, well-formed structure, the operation empties the active chain, leaves its sentinel linked to itself in both directions, and prepends the removed entries to the secondary chain in reverse traversal order. The secondary chain’s previous contents remain behind those entries.

“Active chain,” “secondary chain,” and “count” are descriptive terms for the observed fields. Interpreting the secondary chain as a reusable-entry pool is inferred intent, not an established ownership or allocation contract.

## Interface

**Input:** one address-bearing argument identifying a writable containing object.

**Output:** no return value. Results are observable through memory mutations.

The supplied representation uses four-byte integer and address-bearing fields. The layout below describes that representation; it is not a portable native-pointer interface for arbitrary host architectures.

### Containing-object layout

Offsets are in bytes relative to the input address.

| Offset | Width | Observed role |
|---|---:|---|
| `+0x04` | 4 bytes | Head address of the secondary chain |
| `+0x10` | 4 bytes | Address of the active-chain sentinel |
| `+0x14` | 4 bytes | Integer count decremented for each removed entry |

The routine does not explicitly write the sentinel-address field.

### Entry and sentinel layout

| Offset | Width | Observed role |
|---|---:|---|
| `+0x00` | 4 bytes | Successor address while active; secondary-chain link after removal |
| `+0x04` | 4 bytes | Predecessor address while active |

The sentinel is accessed using the same two-link layout. No payload layout is established. The routine does not explicitly clear a removed entry’s predecessor field.

### Preconditions for ordinary completion

The following conditions support the ordinary, finite emptying behavior:

- The input address and all accessed fields designate valid, suitably aligned storage.
- The sentinel and every traversed entry provide readable link fields and writable locations needed for unlinking.
- Following successor links from the sentinel reaches the same sentinel after finitely many entries.
- Forward and backward links agree sufficiently for unlinking to preserve the remaining chain.
- The sentinel-address field and relevant links are not concurrently modified.
- Object fields and link storage do not overlap in a way that changes the intended operation.
- Address calculations are valid in the target representation.
- Each count decrement is defined by the applicable integer semantics.

The count need not equal the number of entries for traversal to occur. It does not control traversal or termination.

The secondary-chain head may be a null address: the routine copies that value into a removed entry’s link without dereferencing it. For the resulting secondary chain to remain usable, a non-null prior head must identify an appropriate existing chain.

## Behavior

### Initial observations

The routine first reads the sentinel address from the containing object and retains that address as its termination reference.

It then independently reads the sentinel-address field again and reads the successor field at the resulting address. That successor becomes the current entry.

These are two distinct reads of the sentinel-address field. Under stable memory they produce the same address. If they differ, the initial current entry can come from a different sentinel than the retained termination reference.

An initially empty, stable active chain has its sentinel’s successor equal to the sentinel. In that case, the routine returns without entering the removal body.

### Termination reference and live sentinel checks

Before each body execution, the routine compares the current entry with the sentinel address retained at entry. Equality ends processing.

When they differ, the routine reads the containing object’s sentinel-address field again and compares the current entry with that newly read address.

If the current entry equals this newly read sentinel address, the routine does not unlink an entry, decrement the count, or update the secondary-chain head during that body execution. Instead, it reads the sentinel-address field once more, uses that value as the current entry, and returns to the termination comparison.

This distinction is observable when the stored sentinel address changes. The retained termination address is never replaced by the later sentinel-field reads.

Under ordinary stable conditions, the extra branch does not occur: an actual entry differs from the sentinel, and reaching the sentinel ends processing before the body.

### Removal and transfer

For a current entry that differs from both the retained termination reference and the sentinel address read for the body check, the routine performs these ordered effects:

1. **Retain the successor.** It reads the current entry’s successor into temporary traversal state. This retained address determines the next current entry after removal.
2. **Repair the predecessor’s forward link.** It writes the current entry’s successor address into the successor field of the entry designated by the current entry’s predecessor.
3. **Repair the successor’s backward link.** It writes the current entry’s predecessor address into the predecessor field of the entry designated by the current entry’s successor.
4. **Reduce the count.** It reads the containing object’s count, subtracts one, and writes the result back.
5. **Link into the secondary chain.** It reads the containing object’s secondary-chain head and writes that address into the removed entry’s successor field.
6. **Publish the new secondary head.** It writes the removed entry’s address into the containing object’s secondary-chain head.
7. **Advance traversal.** It makes the successor retained in step 1 the current entry.

The retained successor is necessary because the removed entry’s successor field is repurposed before traversal advances.

The unlink operations read the current entry’s link fields again; they do not use only the initially retained successor. Consequently, the supplied representation does not support a claim that every operation associated with a removal uses one immutable link snapshot.

The sequence above establishes the order between separate memory-update operations. It does not establish a total ordering among address and value reads used within the same assignment expression.

### Stable, well-formed result

For an active chain containing entries in forward order A, B, C, the removals occur in that order. Each entry is prepended to the secondary chain, so its final prefix is C, B, A.

Both directions of the active chain are repaired on every removal. Removing the first entry updates the sentinel’s forward link through the predecessor repair. Removing the last entry updates the sentinel’s backward link through the successor repair. After the final removal, both sentinel links point to the sentinel.

For \(N\) removed entries, the count undergoes \(N\) separate decrements. Where all intermediate arithmetic is defined, its final value is the initial value minus \(N\). It is not independently reset to zero.

The routine does not inspect entry payloads or derive the number of entries from the count.

### Integer and address boundaries

The count is represented as a four-byte integer and is manipulated as a signed integer in the supplied representation.

There is no zero check, saturation, minimum-value check, or reconciliation with actual chain length. A zero count with one removable entry becomes negative one, provided that operation is defined. A decrement below the minimum signed value is not assigned a guaranteed result by this contract: the supplied source-level expression does not establish defined wraparound.

Likewise, invalid address arithmetic is not given a portable recovery behavior. The contract requires valid target-address calculations rather than assuming arbitrary integer addresses are safe.

## Side effects

The routine explicitly writes:

- Each removed entry’s predecessor’s successor field.
- Each removed entry’s successor’s predecessor field.
- The containing object’s count, once per removal.
- Each removed entry’s successor field, to form the secondary chain.
- The containing object’s secondary-chain head, once per removal.

For distinct, conventionally arranged objects, it does not explicitly write:

- The containing object’s sentinel-address field.
- A removed entry’s own predecessor field.
- Entry payload fields beyond the first two link fields.
- Any allocation or ownership metadata.

A removed entry’s predecessor field therefore remains stale under the ordinary non-overlapping layout. The secondary chain is established through successor fields only; no corresponding backward-link invariant is maintained.

No allocation, deallocation, payload destruction, callback, or external function invocation appears in the supplied body. Entries remain in memory and become reachable through the secondary-chain head. This supports a structural transfer contract, not a claim that memory is released.

The transfer is not atomic. In particular:

- Neighbor links are repaired before the count changes.
- The count changes before the removed entry is linked into the secondary chain.
- The removed entry’s new link is stored before it is published as the secondary-chain head.

There is no explicit rollback or error reporting. An invalid access or other execution failure can occur after earlier mutations have taken effect. Concurrency safety is not established.

Aliasing can make a nominal link write affect a containing-object field or another unexpected location. The ordinary result described above excludes such overlapping layouts.

## Dependencies

There are no explicit function dependencies in the supplied body. No additional opaque function IDs are required.

The operation depends on the caller providing:

- The containing-object layout described above.
- Valid entry and sentinel storage.
- A traversable active chain.
- Access rights for all affected link and count fields.
- Appropriate synchronization and lifetime protection.

It does not establish ownership of either chain. Whether another operation later reuses, releases, or destroys transferred entries is `documented_only`.

## Acceptance examples

These are conditional acceptance cases derived from static evidence. They have not been executed.

### Empty active chain

**Given:** the sentinel-address field is stable, and the sentinel’s successor points to the sentinel.

**Expected:** the routine returns without writing the count, secondary-chain head, or any link field. An inconsistent count is not corrected.

### One active entry and an empty secondary chain

**Given:** the active chain contains one entry A, both directions are consistent, the count is one, and the secondary-chain head is null.

**Expected:**

- Both sentinel links become the sentinel address.
- The count becomes zero.
- The secondary-chain head becomes A.
- A’s successor field becomes null.
- A’s predecessor field is not explicitly cleared.

### Several active entries and an existing secondary chain

**Given:** the active chain is sentinel → A → B → C → sentinel, its backward links are consistent, the count is three, and the secondary-chain head is H.

**Expected:**

- The active chain becomes empty in both directions.
- The count becomes zero.
- The secondary chain begins C → B → A → H.
- Existing links beyond H are not traversed or explicitly rewritten.

### Count does not match chain length

**Given:** two well-formed active entries, a stable sentinel, and an initial count of seven.

**Expected:** both entries are transferred, and the final count is five. The count does not prevent traversal and is not forced to zero.

**Given instead:** one active entry and an initial count of zero.

**Expected:** the entry is still transferred, and the count becomes negative one, subject to the stated integer semantics.

### Signed count boundary

**Given:** a removable entry and the minimum representable signed count.

**Expected:** no particular post-decrement value is guaranteed by this contract. There is no established checked-error or saturation path.

### Sentinel-address field changes

**Given:** the retained entry-time sentinel is S, the current entry is T, T differs from S, and a later sentinel-field read yields T.

**Expected:** that body execution skips removal and count adjustment, then rereads the sentinel-address field to choose the next current entry.

If the field remains T, the routine can repeat this branch indefinitely because T still differs from S. This is not a supported synchronization mechanism.

### Malformed successor cycle

**Given:** successor traversal enters a cycle that does not reach the retained sentinel.

**Expected:** normal termination is not guaranteed. The routine has no cycle detector, count-based traversal limit, or malformed-chain error result.
