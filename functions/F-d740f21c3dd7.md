# F-d740f21c3dd7

## Purpose

F-d740f21c3dd7 searches a caller-supplied integer sequence for a requested value. If that value is already present, it returns −1. Otherwise, it optionally invokes F-65d7c1ee7da2, searches for the first zero-valued element, and, if one is found, increments a descriptor counter before writing the requested value into that element.

The behavior is not conventional append or insertion:

- An existing occurrence takes precedence over an available zero slot.
- The function does not append when the searched range contains no zero.
- The dependency call is controlled by equality between two descriptor fields, not by an observed absence of zero slots.
- A successful selection increments a counter but does not separately increase the scan-length field.
- The same return value, −1, covers both duplicate detection and failure to find a zero slot.
- Dependency effects can remain visible even when the function ultimately returns −1.

Interpreting zero as an available-slot marker is consistent with the operations. Interpreting the descriptor as a particular collection type, or the dependency as a storage-growth operation, is inferred intent rather than established behavior.

## Interface

### Inputs and representation

The function receives a descriptor reference and a requested integer value.

The supplied representation uses four-byte integer fields and four-byte element spacing. The contract describes integer values and signed comparisons as 32-bit operations. It does not establish a portable native-pointer representation.

The descriptor comprises at least these three consecutive fields:

| Byte offset | Contract name | Width | Observed role |
|---|---|---|---|
| 0 | Storage-address field | 32 bits | Integer representation used to form element addresses |
| 4 | Scan-length field | 32 bits | Signed scan bound |
| 8 | Counter field | 32 bits | Compared with the scan length and incremented on slot selection |

These names identify uses, not domain guarantees. The counter is not established to mean occupancy, capacity, or the number of nonzero elements.

The storage-address field is a four-byte integer representation used as an address. It must not be silently replaced in this contract by a native pointer of an unspecified width. How that integer becomes a usable address depends on the execution environment.

### Output

On normal return, the signed 32-bit result is:

- −1 if the initial search finds the requested value;
- −1 if the later search finds no zero-valued element;
- the zero-based index of the first zero-valued element selected by the later search, after the counter update and element write complete.

A successful index is nonnegative and strictly less than the bound captured for the second scan. Index zero is a successful index, not a failure indicator.

No additional result distinguishes dependency failure, inaccessible memory, arithmetic failure, or insufficient allocation. Such conditions have no explicit recovery branch.

### Preconditions for ordinary defined execution

The descriptor must support every field access reached. Each element address actually examined must identify readable four-byte storage; the selected destination must also be writable.

Address conversion, address addition, four-byte index scaling, loop arithmetic, and the counter increment must be valid under the actual environment’s rules. The displayed operations do not establish widened address arithmetic, checked arithmetic, or a portable wraparound policy.

In particular:

- A valid signed scan bound does not by itself make four times an index representable in signed 32-bit arithmetic.
- A representable scaled index does not by itself make its addition to the storage-address representation valid.
- Incrementing the maximum signed 32-bit counter has no portable result established here.

Disjoint descriptor and element storage is sufficient for the simple independent-field postconditions below, but is not enforced by the function. Aliasing behavior is addressed separately.

## Behavior

### Initial duplicate search

The function searches in increasing index order, starting at zero. Each continuation comparison uses the current scan-length field as a signed bound. The first scan therefore does not capture one immutable length at entry.

For each visited index, it obtains the storage-address field, forms the corresponding four-byte element address, reads the element, and compares it with the requested value.

The first equality causes an immediate return of −1:

- No dependency call occurs.
- No descriptor or element write is performed by this function.
- Later elements are not examined.

With stable metadata, a positive length causes examination of indices zero through length minus one, unless a match is found earlier. A zero or negative length causes no element reads in this phase.

The repeated field accesses describe the supplied body’s data dependencies. They do not establish atomic accesses, synchronization, or supported concurrent mutation.

### Conditional dependency invocation

If the duplicate search finishes without a match, the function compares the counter field with the scan-length field.

Equality causes a call to F-65d7c1ee7da2 with the same descriptor reference. Inequality skips the call.

This condition has no positivity requirement. For example, equal zero fields or equal negative fields can trigger the call even though the initial search examined no elements.

The call occurs before the search for a zero-valued slot. It can therefore occur even when a zero slot was already present in the initially searched range.

The function does not inspect a returned status or repeat duplicate detection after the call. If the dependency returns normally, execution continues using the resulting descriptor and storage state. No preservation, allocation, or success guarantee is established for that dependency.

### Search for a zero-valued element

After the optional dependency call, the function reads the scan-length field and retains that value as the second scan’s bound.

This bound may differ from the lengths observed during the first scan. Unlike the first scan, the second scan does not reread the length for each continuation comparison.

The search proceeds in increasing index order. Element addressing uses the descriptor’s storage-address field. The first element equal to zero is selected.

Under ordinary defined execution:

- A positive captured bound allows selection only at indices from zero through bound minus one.
- A zero or negative captured bound causes no element reads.
- Exhausting the range without finding zero produces a result of −1.
- Finding zero at index zero is sufficient for the update path.

The additional conditions between selection and mutation do not exclude any normally reachable selected index: a found index is nonnegative and strictly below the captured bound.

### Counter update and element write

After selecting a zero-valued element, the function reads the counter, adds one, and writes the incremented value back to offset 8 of the descriptor. It then reads the storage-address field at offset 0 and writes the requested value into the selected four-byte element. Finally, it returns the selected index.

The counter write precedes both the final storage-address read and the element write.

For disjoint storage, successful normal execution therefore produces:

- the counter’s previous value plus one;
- the requested value at the selected index;
- no separately targeted write to the storage-address or scan-length field.

For overlapping storage, those independent postconditions need qualification: the selected element write may itself target descriptor bytes.

If no zero-valued element is found, neither the counter update nor the element write occurs. Any earlier dependency effects remain; there is no rollback.

### Requested value zero

Zero is both a possible requested value and the marker sought by the second scan.

If the storage, relevant elements, and scan range remain unchanged between searches:

- A zero in the range makes the first scan return −1.
- An absence of zeros leaves the second scan without a selectable element.

Under those conditions, requesting zero cannot succeed.

This restriction is conditional, not absolute. If the dependency changes storage or extends the range so that the second search encounters a zero not encountered by the first, the function can select it, increment the counter, write zero to the already-zero element, and return its index.

Similarly, if the dependency introduces the requested nonzero value and also leaves a selectable zero, the function can create another occurrence. There is no post-call duplicate check.

## Side effects

### Direct mutations and ordering

The only separately targeted descriptor mutation is the counter increment. The other direct mutation is the selected four-byte element write.

The established phase ordering is:

1. Duplicate search.
2. Counter-versus-length comparison and possible dependency call.
3. Capture of the second scan’s bound.
4. Increasing-index search for zero.
5. Counter read, increment, and write on selection.
6. Final storage-address read and selected-element write.
7. Return of the selected index.

This ordering does not specify the relative machine-level evaluation order of operands within an individual comparison or address expression.

The counter increment and element write are not made transactional by the supplied body. If execution fails after the counter write but before completion of the element write, no rollback is present.

### Aliasing

Under the stated valid descriptor layout, the counter field occupies bytes 8–11 and the storage-address field occupies bytes 0–3. These fields do not overlap.

Consequently, the counter write at offset 8 does **not** change the storage-address field subsequently read at offset 0. Overlap between element storage and the descriptor does not, by itself, invalidate that fact.

Overlap can nevertheless affect observable results:

- The counter write can change an element whose storage overlaps the counter field.
- The selected element write can overwrite descriptor bytes if its destination overlaps the descriptor.
- A selected element that coincides with the counter field receives the increment first and the requested value afterward. Its final contents need not equal the incremented counter value.

Thus, the counter and selected element cannot generally be treated as independently changing objects when their storage overlaps. This is distinct from claiming that the counter increment changes the stored base address.

### Ownership and lifetime

The function does not directly allocate, release, or transfer storage ownership. It uses the supplied descriptor and addresses derived from it during the invocation.

No such restriction can be assigned to F-65d7c1ee7da2. The dependency may have ownership or lifetime effects not visible in this body. Callers cannot infer that pre-call element addresses remain valid after it returns.

### Errors

There are no explicit checks for null references, alignment, allocation extent, valid integer-to-address conversion, arithmetic overflow, or dependency failure.

Invalid access, invalid arithmetic, or abnormal dependency execution is not specified to return −1. The contract provides normal-path behavior only where the reached operations are valid.

Additional conditional cases:

- **Duplicate introduced by dependency:** Initially, elements are [12, 24], length and counter are both 2, and the requested value is 37. If the dependency leaves elements [37, 0] with length and counter still 2, the function increments the counter to 3, writes 37 at index 1, and returns 1. It does not reject the occurrence introduced at index 0.
- **Zero made available by dependency:** Initially, length and counter are both 0 and the requested value is 0. If the dependency establishes one readable, writable zero element, sets length to 1, and leaves counter 0, the function increments the counter to 1, writes zero at index 0, and returns 0.
- **Selected element aliases the counter:** The storage-address field denotes the counter field itself, length is 1, counter is 0, and the requested value is 7. With valid address representation and access, the function skips the dependency, selects index 0, writes counter value 1, then writes 7 to that same element. It returns 0 with the counter field containing 7. The storage-address field is unchanged by both writes.

## Uncertainties

### Established static evidence

The supplied body establishes duplicate-first ordering, equality-controlled dependency invocation, the second scan’s captured bound, first-zero selection, acceptance of index zero, counter-before-element write ordering, and both normal meanings of −1.

It also establishes distinct descriptor offsets for the counter and storage-address field. The counter write cannot overwrite the storage-address field under that layout.

### Inferred intent

The sequence appears to use zero as an available-slot marker. The dependency may support storage management. Neither interpretation establishes metadata invariants or additional behavior.
