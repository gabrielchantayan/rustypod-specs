# F-abdb265693e5

## Purpose

F-abdb265693e5 conditionally processes records associated with an externally obtained handle. It obtains position-related data through a callback, maintains an identity-associated index, may dispatch one record, and may request another invocation through an embedded object.

“Position,” “record,” “identity,” and “scheduling” describe inferred intent. Established behavior consists of the field accesses, arithmetic, dependency calls, and branch conditions below. The meanings and units of these values are not established.

The function has no explicit result. Several paths return without dispatching a record or requesting scheduling.

For the optional object, its first 32-bit word supplies a table address. A call target is obtained from byte offset `0x124` within that table. The exact calling convention, including any implicit receiver, is unknown.

### Callback output storage

The position callback receives two explicit addresses:

- Storage subsequently read as two adjacent 32-bit identity words.
- Storage holding one unsigned 32-bit position value.

The position storage is initialized to zero before the enable check. The identity storage is not initialized before the callback.

The callback result is tested only for zero versus nonzero. For successful processing, subsequently consumed identity words must have defined contents. The initialized position can remain zero if the callback does not change it.

These output addresses escape to the callback. Whether the callback retains or publishes them is unknown. Consequently, later dependencies could modify this storage even when those addresses are not explicit arguments to those dependencies.

### Record output storage

Record retrieval receives an output address. The visible consumer uses:

- A leading 12-byte area passed to dispatch.
- An unsigned 32-bit timing word immediately following that area, at offset 12.

The required readable output span is therefore 16 bytes. The first lookup-related retrieval uses one temporary area. Record processing and its loop use a separate temporary area, reused across retrievals.

The retrieval dependency’s complete write contract is unknown. Defined processing requires the timing word to be readable and, when dispatch occurs, the leading area to be suitable for the dispatch dependency.

### Results and ownership

There is no explicit return value or error code. Observable outputs are object writes and dependency calls.

No allocation, release, or ownership transfer is explicitly performed. Temporary output storage belongs to the invocation; retention of its addresses requires a separate lifetime contract that is not supplied.

## Behavior

### Interpretation of changing storage

The position and identity outputs are storage locations, not immutable callback results. Each later use reads their then-current contents. In particular:

- The transformation dependency runs before the identity comparisons.
- The resolution count call runs before the position is read for index lookup.
- Retrieval runs before the position is read for timing comparisons.
- Dispatch-related dependencies run before the loop’s later position reads.

Where formulas below use \(t\), it means the unsigned 32-bit position read for that particular decision or argument calculation. It does not imply a single fixed value throughout the invocation.

Fixed-position interpretations require dependencies not to modify escaped output storage between the relevant reads. Examples explicitly state that assumption where applicable. Concurrent mutation and synchronization rules are not established.

The obtained handle is different: its address is not visibly exposed. Its scalar value is retained for subsequent handle-taking calls; callback-output aliasing does not itself establish a way to modify that scalar.

### 1. Enable and classification

After initializing position storage to zero, the function reads `0x70`.

- If zero, it returns without calling any listed dependency or directly changing the object.
- Otherwise, it calls F-3044f680bd12 with the object address.

If the returned 32-bit handle-like value is zero, F-3143474ecc5b receives the object address and `100`, then the function returns.

For a nonzero handle, F-308ee2dda2ec classifies it:

- Result `1`: call F-3143474ecc5b with the object address and `100`, then return.
- Result `2` or `3`: perform the scheduling pair with argument `100`, then return.
- Every other result: continue to callback and record processing.

No other classification is treated as an error. Negative results also follow the general path.

### 2. Optional guarded call

On the general path, the function checks the pointer at `0x28`. Only if nonzero does this condition inspect the guard byte at `0x68`.

If the pointer is nonzero and the guard is zero:

1. Write `1` to `0x68`.
2. Obtain the indirect target through the optional object’s table entry at `0x124`.
3. Invoke that target.

The guard write precedes the call. Reentrant execution can therefore observe the changed guard. This is not an unconditional lifetime-wide one-shot guarantee: dependencies or other actors may change the guard later.

A null optional pointer or nonzero guard suppresses this indirect call.

### 3. Position acquisition and transformation

The function reads and invokes the callback at `0x2c`, passing the two output addresses.

A zero result returns immediately. Earlier effects, including the guard write and optional call, remain in effect.

For a nonzero result, the unsigned position storage is adjusted:

\[
a =
\begin{cases}
0, & p < 600,\\
p-600, & p \ge 600,
\end{cases}
\]

where \(p\) is the position consumed by this adjustment. The adjusted value is written to position storage.

F-d7be9cfb4000 receives the adjusted position and `10`. Its 32-bit result is then written into position storage. No division, rounding, or unit-conversion semantics are established.

If this dependency changes escaped identity storage, subsequent identity comparisons observe those changes. If it changes position storage during the call, the normal post-call assignment replaces that content with its returned value. Later dependencies may change position storage again; the transformation is not automatically repeated.

### 4. Identity matching and index resolution

The second identity word is compared with the object word at `0x64`. Only if equal is the first identity word compared with `0x60`. These comparisons occur after the transformation dependency returns.

If both match and the signed cached index at `0x5c` is not `-1`, resolution is skipped.

If either identity word differs, the function writes, in order:

1. `-1` to `0x5c`.
2. The first current identity word to `0x60`.
3. The second current identity word to `0x64`.

If the identity matches but the index is already `-1`, those identity writes do not occur.

When resolution is required, F-d25a91b7600a receives the handle. A zero result causes immediate return. Identity-change writes, if any, have already occurred.

For any nonzero result, including a negative result, F-261627257752 receives the handle and the position read after that count call. Its signed 32-bit result is stored at `0x5c`.

- Result `-1`: schedule with argument `1000`, then return.
- Any other result: retrieve a record using F-c5d56ea8f2d9, the handle, and that returned index.

After retrieval, compare its unsigned timing word \(r\) with the then-current position \(t\).

- If \(r>t\), schedule with \((r-t)\times10+1\), then return.
- Otherwise, enter record processing.

This retrieval is not directly dispatched. Record processing retrieves again into the other temporary area.

### 5. Record processing and dispatch eligibility

F-d25a91b7600a is called with the handle. After it returns, the current cached index is compared with its signed 32-bit result.

If the index is not less than that result, write `-1` to `0x5c` and return.

Otherwise, retrieve the record at the current cached index into the processing output area. After retrieval, read the unsigned position \(t\) and timing word \(q\) for the eligibility test:

\[
(t-q)\bmod 2^{32}<132.
\]

If true:

1. Increment the current cached index by one.
2. Call F-ac356e5603c7.
3. Call F-78443a7fbacd.
4. Read `0x14` if the selector returned zero; otherwise read `0x18`.
5. Call F-97f5558e6116 with that target and the processing record address.

The index increment precedes all three dispatch-related calls. The target read occurs after both preceding dependencies return, so their object mutations can affect the selected target value. The dispatch receives an address, not a protected snapshot of record contents.

If the unsigned difference is at least `132`, this phase neither increments the index nor dispatches.

This is not an absolute-distance test. A slightly future timing value normally produces a large wrapped difference. Values near the unsigned wrap boundary must be evaluated modulo \(2^{32}\).

There is at most one direct dispatch call along a normal, non-reentrant invocation path.

### 6. Skipping and scheduling

After the optional dispatch, the function repeatedly:

- Calls F-d25a91b7600a.
- Compares its signed result with the then-current cached index.
- Leaves the loop if the result is less than or equal to the index.
- Otherwise retrieves the record at the current index into the reused processing area.

After each such retrieval, it compares the then-current unsigned position \(t\) with that record’s timing word \(q\).

If \(t\le q\), it schedules with \((q-t)\times10+1\) and leaves the loop without a loop-step index increment.

If \(t>q\), it increments the current cached index and repeats. Records passed by this increment are not dispatched by the loop.

After either loop exit, including an exit following scheduling, F-d25a91b7600a is called once more. The current index is retained only if it is signed-less-than this final result. Otherwise, `-1` is written to `0x5c`.

Thus, scheduling inside the loop does not suppress the final count call or prevent subsequent index invalidation.

### Scheduling and arithmetic

Every scheduling request consists of:

1. F-6904f7699031 with the address at object offset `0x30` and the 32-bit scheduling argument.
2. F-ec4cfa552cce with that embedded address.

Neither return value is inspected.

Position and timing comparisons are unsigned. Timing-derived subtraction and multiplication use 32-bit arithmetic:

\[
d=(10\Delta+1)\bmod 2^{32}.
\]

No saturation or overflow rejection is visible. The receiver’s interpretation of that bit pattern is unknown.

Index/count comparisons are signed. There is no general lower-bound validation: negative indices other than `-1` are not categorically rejected. Index increments have no visible overflow guard; signed-overflow behavior remains unresolved.

## Side effects

Direct object writes are limited to the guard, cached index, and cached identity fields. The function also initializes and updates temporary position storage and supplies temporary output areas to dependencies.

Dependencies may modify object fields, globals, external sequence state, or storage whose addresses previously escaped. No preservation guarantee is assumed.

In particular, neither identity nor transformed position is guaranteed stable across calls. A dependency can affect a later lookup argument, cache comparison, dispatch decision, or scheduling calculation by modifying escaped output storage. The obtained handle’s address is not visibly exposed and must not be conflated with those outputs.

Retrieval exposes record output addresses. Dispatch additionally receives the processing record address. Ownership, retention, and mutation rights for those addresses are not established.

There is no visible rollback, locking, exception handling, error translation, explicit release, or destruction. Termination requires returning callees and loop progress not defeated by changing state or problematic index values.

## Acceptance examples

These are conditional static deductions, not executed tests. Except where mutation is explicit, assume dependencies return normally, initialize required outputs, and do not modify relevant object or escaped storage beyond their stated outputs.

1. **Disabled:** With `0x70` zero, no listed dependency runs and no object field is directly changed. Position initialization is invocation-local.

2. **Missing handle:** A zero handle causes F-3143474ecc5b with the object and `100`; classification, callback, and scheduling do not follow.

3. **Classification shortcut:** Classification `2` or `3` produces the scheduling pair with `100`, without callback or record processing.

4. **Guard before callback failure:** A nonnull optional object and zero guard produce the guard write before the indirect call. A subsequent zero callback result returns without cache processing.

5. **Identity changed during transformation:** Suppose the callback supplies an identity matching the cache, but publishes its output address. If F-d7be9cfb4000 changes that identity to a different pair, the later comparisons detect the changed pair. The index is invalidated and that current pair is cached.

6. **Position changed before lookup:** Suppose transformation stores `10`, resolution is required, and the first count call changes escaped position storage to `37` while returning nonzero. Index lookup receives `37`, not `10`; no second transformation occurs.

7. **Changed identity, zero count:** A mismatched identity followed by a zero resolution count leaves the new identity stored and index `-1`. No lookup follows.

8. **Lookup miss:** A nonzero resolution count followed by lookup result `-1` stores that sentinel and schedules with `1000`.

9. **Future initial retrieval:** If the first retrieval returns timing seven greater than the position read afterward, without wrap, the scheduling argument is `71`. No dispatch follows.

10. **Retrieval changes dispatch eligibility:** Enter record processing with position `100`. If retrieval writes timing `100` but also changes escaped position storage to `232`, the unsigned difference is `132`; this phase does not dispatch. Using the pre-retrieval position would give the wrong decision.

11. **Dispatch threshold:** With stable position and no wrap, timing \(t-131\) is eligible; timing \(t-132\) is not. Eligibility increments the index before dispatch-related dependencies.

12. **Exact-position loop record:** A loop retrieval with timing equal to the position read afterward schedules with `1`, leaves the index unchanged in that loop step, and still performs the final count call.

13. **Scheduling overflow:** A future timing difference of `429496730` produces scheduling bit pattern `5`. This establishes arithmetic wrap, not a semantic five-unit delay.
