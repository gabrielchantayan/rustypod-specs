# F-ebd170a93754

## Purpose

F-ebd170a93754 performs an in-place structural rotation involving a supplied node, its right-side child, and a root-reference structure.

Under the conventional, non-overlapping tree layout described below, the supplied node moves down to become the left-side child of its former right-side child. The promoted child replaces the supplied node in either the root slot or its former parent’s child slot. The promoted child’s former left-side subtree becomes the supplied node’s right-side subtree.

The rotation interpretation is inferred from the field-access pattern. The established behavior is the ordered sequence of 32-bit reads, comparisons, and writes specified below. The function does not validate that the objects form a tree.

## Interface

### Inputs

The function takes two inputs:

- **Context address:** an address-bearing value used to locate a root-reference structure.
- **Pivot address:** an address-bearing value identifying the node being moved downward.

Both inputs are represented as `int` in the supplied representation and are used in address calculations. The representation shows 32-bit field transfers and address-bearing fields. It does not independently establish a portable calling convention, native pointer width, or behavior for integer-address overflow.

The inputs must identify accessible storage for every field actually reached by the selected execution path. There is no explicit null check on either input.

The **transferred subtree** is, in an ordinary non-overlapping tree, the promoted node’s left-side child.

## Behavior

### Ordered memory effects

The sequence below specifies the observed memory-access structure. It does not impose an otherwise unestablished ordering between independent operand evaluations within a single assignment.

1. **Select the promoted node.**  
   Read four bytes at pivot offset 12 and retain the resulting address.

2. **Replace the pivot’s right-side link.**  
   Read four bytes at promoted-node offset 8 and write that value to pivot offset 12.

3. **Conditionally update the transferred subtree’s parent.**  
   Read promoted-node offset 8 again and compare its value with zero.

   - If the value is zero, perform no subtree-parent write.
   - If the value is nonzero, read promoted-node offset 8 again to obtain the destination node address, then write the pivot address at that node’s offset 4.

   These are distinct reads. The value copied into the pivot’s right-side field is not explicitly retained for this test or destination selection. Likewise, the value tested for nonzero is not explicitly retained as the destination address.

4. **Give the promoted node the pivot’s current parent.**  
   Read four bytes at pivot offset 4 and write that value to promoted-node offset 4.

5. **Locate and inspect the root slot.**  
   Read the address at context offset 16. The root slot is four bytes beyond that address. Read the root slot and compare its value with the pivot address.

   The root-reference lookup occurs after the preceding writes.

6. **Replace the pivot’s incoming link.**

   - **Recorded-root case:** If the root slot equals the pivot address, write the promoted-node address to that root slot.
   - **Non-root case:** Otherwise, read the address at pivot offset 4. Read that parent node’s field at offset 8 and compare it with the pivot address.
     - If equal, write the promoted-node address to the parent’s offset 8.
     - If unequal, write the promoted-node address to the parent’s offset 12.

   The non-root case does not check that the parent’s offset-12 field actually contains the pivot before overwriting it.

7. **Make the pivot the promoted node’s left-side child.**  
   Write the pivot address to promoted-node offset 8.

8. **Make the promoted node the pivot’s parent.**  
   Write the promoted-node address to pivot offset 4.

After these writes, the function returns without a value.

### Result for a conventional tree

Assume stable, valid, non-overlapping objects. Let:

- The pivot initially have a parent and a right-side child.
- The right-side child be the promoted node.
- The promoted node initially have a left-side subtree, possibly absent.

The final structural relationships are:

| Relationship | Final value |
|---|---|
| Pivot’s right-side child | Promoted node’s former left-side child |
| Transferred subtree’s parent, if present | Pivot |
| Promoted node’s parent | Pivot’s former parent |
| Pivot’s former incoming root or parent link | Promoted node |
| Promoted node’s left-side child | Pivot |
| Pivot’s parent | Promoted node |

The pivot’s left-side child and the promoted node’s right-side child are not directly written.

For a pivot recognized as the root, the promoted node receives whatever parent value the pivot previously held. The function does not independently clear that parent field or normalize it to zero. A null-parent convention or sentinel-parent convention must therefore already be represented by the pivot’s existing parent value.

### Selection and validation rules

Root status is determined solely by equality between the root slot and the pivot address. It is not inferred from the pivot’s parent field.

For a non-root pivot, the left-side child slot is selected only when its contents equal the pivot address. Every other value selects the right-side child slot. This includes inconsistent structures in which neither child slot identifies the pivot.

The only explicit null-sensitive conditional concerns the promoted node’s left-side child. There is no corresponding guard before accessing the promoted node itself.

### Intermediate states

The operation consists of multiple separate writes, not an established atomic update.

In particular, the pivot’s right-side link changes before the root or former parent link changes. The incoming link is then redirected before the final two parent-child writes complete. An observer reading during execution could therefore see an intermediate structure that does not satisfy the final bidirectional relationships.

No synchronization or memory-ordering guarantee is visible.

### Aliasing and changing fields

The conventional result table depends on the stated preconditions. The ordered accesses remain important when fields overlap or change during execution:

- A write to pivot offset 12 could affect a later read if storage aliases.
- The repeated reads of promoted-node offset 8 are not a single snapshot.
- The root-reference address and root value are read only after the earlier structural writes.
- The pivot’s parent is read once for assignment to the promoted node and, on the non-root path, read again to locate the parent.
- Later writes can overwrite earlier results when destinations coincide.

The function does not detect such cases. A simplified rotation description must not replace the access sequence when documenting overlapping or unstable storage.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed test results. Each ordinary-tree example assumes stable, accessible, suitably aligned, non-overlapping storage.

### Pivot is the recorded root; transferred subtree exists

Initially:

- The root slot identifies the pivot.
- The pivot’s right-side child identifies the promoted node.
- The promoted node’s left-side child identifies a separate subtree.
- The pivot has a caller-defined parent value.

On normal completion:

- The root slot identifies the promoted node.
- The promoted node retains the pivot’s former parent value.
- The promoted node’s left-side child is the pivot.
- The pivot’s parent is the promoted node.
- The pivot’s right-side child is the transferred subtree.
- The transferred subtree’s parent is the pivot.

The function must not be described as clearing the new root’s parent unless the old root’s parent was already zero.

### Pivot is a parent’s left-side child; transferred subtree is absent

Initially, the root slot does not identify the pivot, the pivot’s parent has the pivot in its offset-8 field, and the promoted node’s offset-8 field is zero.

On normal completion:

- The former parent’s left-side field identifies the promoted node.
- The promoted node’s parent identifies that former parent.
- The pivot’s right-side field is zero.
- The promoted node and pivot acquire the final relationships described above.
- No transferred-subtree parent write occurs.

### Pivot is a parent’s right-side child

Initially, the pivot is not the recorded root, and its parent’s left-side field does not equal the pivot. If the parent’s right-side field does identify the pivot, normal completion replaces that field with the promoted-node address.

The right-side choice results from the failed left-side comparison, not from a successful right-side comparison.

### Inconsistent parent linkage

Suppose the pivot is not the recorded root and neither child field of its recorded parent identifies it. Provided all accesses remain valid, the function still overwrites that parent’s right-side field with the promoted-node address.

An implementation that instead rejects this condition or preserves the right-side field would differ from the established branch behavior.

### Missing right-side child

If the pivot’s right-side field is zero, the function does not take an early return. It attempts an access at offset 8 relative to that zero address.

The resulting environmental behavior is not established. This is not a supported empty-child rotation case.
