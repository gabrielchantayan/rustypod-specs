# F-96b280e9c2c9

## Purpose

F-96b280e9c2c9 requests workspace and uses it as a depth-limited stack while inspecting records in a byte-addressed buffer. Each 12-byte frame stores a position, two counters, and a boundary.

Established behavior includes input gating, workspace initialization, record decoding, descent for every nonzero child count, completion processing, status selection, and dependency calls. Nested-record traversal or validation is inferred intent, not an established format contract. The representation does not establish that accepted inputs are memory-safe or that processing terminates.

The result combines a 32-bit status with a 32-bit selected pointer. The selected pointer may identify the original descriptor, workspace, or null. Passing workspace to the final dependency does not establish whether the returned pointer remains usable.

## Interface

### Inputs and descriptor

The inputs are an unsigned 32-bit frame capacity and a nullable descriptor pointer. Active processing uses these descriptor fields:

| Byte offset | Width | Established role |
|---|---:|---|
| 0 | 32 bits | Buffer address, also tested against zero |
| 4 | 32 bits | Extent-like value used in two scaling calculations |

The extent’s units are unknown.

Active processing requires, in short-circuit order:

1. A non-null descriptor.
2. A nonzero first descriptor word.
3. Nonzero capacity.

A null descriptor is not dereferenced. For a non-null descriptor, the first word is read even when capacity is zero.

Positions, boundaries, addresses, depth, capacity, and statuses are represented with 32 bits. Frame counters have 16-bit storage. Record fields are assembled from 8-bit reads. These facts do not establish an external ABI or native byte order.

### Result

| Result bits | Content |
|---|---|
| 0–31 | Retained status |
| 32–63 | Selected pointer |

The selected pointer initially equals the descriptor pointer. A workspace-request call replaces it with that dependency’s result, including null. The final dependency does not replace or clear it.

### Global parameter roles

The representation reads distinct globals serving these roles:

- Inactive, allocation, format, and capacity statuses.
- Initial extent-check factor and root-boundary factor.
- Root-position seed.
- Counter unit and target factor.
- Position decoder and encoder.
- Boundary decoder and encoder.
- Current-counter decoder and target-counter decoder.

Their values, consistency across reads, and relationships are unknown. An encoder is not assumed to invert a decoder. Status values are not assumed nonzero or distinct.

## Behavior

### Arithmetic and record representation

Unsigned 32-bit calculations retain their low 32 bits, and unsigned comparisons use those results. In particular, the workspace request is capacity multiplied by 12 with 32-bit truncation; no overflow rejection is visible.

Some represented calculations use signed intermediates. Their overflow behavior remains documented_only. Describing a low-bit result does not establish portable semantics when an intervening signed operation overflows.

For record decoding, each source byte is multiplied by 23 and reduced to eight bits:

- Transformed bytes at record offsets 0 through 3 form the 32-bit length, most significant byte first.
- Transformed bytes at offsets 14 and 15 form a 16-bit child count, most significant byte first.

These are transformed fields, not raw big-endian integers. Their explicit byte assembly does not establish the native byte order of workspace word accesses. A total order among reads within a compound expression is not established.

### Inactive inputs

The inactive-status global is read before the input checks. Failure of any active-path condition returns that captured status and the original descriptor pointer.

No dependency is called and no workspace frame is written on these paths.

### Workspace request and result gate

For active inputs, F-d33f6d597e5d receives the 32-bit capacity-times-12 request. After it returns, the sequence is:

1. Read and retain the root-boundary factor.
2. Compute an intermediate from one minus the represented workspace address.
3. Compare the pointer with address one; replace the intermediate with zero when the pointer is greater.
4. Read the allocation-status global.
5. Branch on whether the previously computed intermediate is zero.

Thus, pointer-test computation precedes the allocation-status read, but the branch follows it.

Under the represented address arithmetic, null is rejected. Address one and addresses greater than one pass this gate. Passing establishes neither accessible storage nor alignment. Pointer ordering and signed-overflow details remain documented_only.

A null result returns null and the captured allocation status without calling F-5e3309c9d083.

### Initial extent check and root frame

For accepted workspace, the format status is read. The function then requires the unsigned 32-bit product of the extent-check factor and the descriptor’s second word to exceed 31.

A product at most 31 causes a final dependency call without frame initialization. The result retains the workspace pointer and captured format status.

A product greater than 31 permits root initialization. Frames have a 12-byte stride:

| Frame offset | Width | Field |
|---|---:|---|
| 0 | 32 bits | Encoded position |
| 4 | 16 bits | Encoded current counter |
| 6 | 16 bits | Encoded target counter |
| 8 | 32 bits | Encoded boundary |

Root writes occur in this order:

1. Position from the root-position seed.
2. Current counter from the low 16 bits of a counter-unit read.
3. Target counter from the low 16 bits of a target-factor read.
4. Boundary from the retained root-boundary factor multiplied by a new read of the descriptor’s second word.

The boundary’s extent read follows the first three frame writes. Other workspace bytes are not cleared. Depth becomes one, and traversal begins with carried status zero.

### Outer-pass entry

Every outer iteration first reads the current-counter decoder, then the counter unit. These values are retained for possible advancement during that pass.

Both reads precede the exit guard. Consequently:

- A zero-depth exit still performs both reads.
- A nonzero processing outcome produces one terminal iteration that performs both reads without inspecting a frame.
- A zero outcome starts another processing pass.

A nominal error status equal to zero therefore need not stop processing.

### Record inspection

For nonzero depth, the top frame is inspected in this sequence:

1. Decode its position using a position-decoder read.
2. Add 20 to form the header-end offset.
3. Read the format status as the tentative outcome.
4. Require position not to exceed header end.
5. If that succeeds, decode the frame boundary.
6. Require header end not to exceed that boundary.

The first comparison rejects unsigned wrap in position plus 20.

Only after these checks does the function read the descriptor’s buffer-address word and decode length and child count. Further processing requires:

- Length greater than 19.
- Position plus length not below position.
- That record end not beyond the decoded boundary.

The capacity-versus-depth comparison is computed during record decoding, before the final record-validity decision.

The captured buffer address is reused throughout completion for this inspection, including accesses associated with enclosing frames. These offset checks do not establish accessible backing storage, safe buffer-address addition, or adequate workspace.

### Descent for nonzero child count

Every child count from one through 65,535 selects descent.

The capacity status is read first. If depth is at least capacity, no child frame is written, and that status becomes the processing outcome.

Otherwise, the next frame is written in this order:

1. Position: parent header end multiplied by a position-encoder read.
2. Current counter: low 16 bits of a fresh counter-unit read.
3. Target counter: low 16 bits of child count multiplied by the low 16 bits of a target-factor read.
4. Boundary: parent record end multiplied by a boundary-encoder read.

The initialization read of the counter unit is distinct from the outer-entry capture. Depth increases by one, and successful descent restores the previously carried status rather than retaining the tentative capacity status.

There is no visible workspace growth or reallocation.

### Completion for zero child count

Completion repeatedly examines the top frame while depth is nonzero. Each iteration saves its entering carried status.

It compares two values, each reduced to 16 bits:

- A fresh current-counter decoder multiplied by the unsigned 16-bit field at frame offset 4.
- A fresh target-counter decoder multiplied by the unsigned 16-bit field at frame offset 6.

These decoder reads are distinct from the outer-entry capture.

#### Unequal transformed counters

When the comparison differs, completion:

1. Decodes the frame position.
2. Decodes four length bytes using the previously captured buffer address.
3. Writes a replacement position equal to the position encoder multiplied by decoded position plus decoded length.
4. Updates the 16-bit current-counter field.
5. Leaves completion with the status saved at this iteration’s entry.

The update uses the following quantities:

- The counter unit captured at outer-pass entry.
- The current-counter decoder captured at outer-pass entry.
- The low 16 bits obtained by reading the **32-bit word beginning at frame offset 4**, then narrowing that word.

The stored result is the low 16 bits of:

**captured counter unit × (captured counter decoder × narrowed word + 1).**

This is not established as a direct read of the current-counter halfword. The 32-bit read spans both counter fields. Which field supplies its low 16 bits depends on native storage byte order and access interpretation. Under conventional little-endian storage, those bits correspond to the field at offset 4; under conventional big-endian storage, they correspond to the field at offset 6. Neither byte order is established here.

The replacement-position write precedes the 32-bit word read used for advancement. Fresh comparison decoders do not replace the captured factors.

Advancement does not repeat the earlier header, minimum-length, addition-wrap, or boundary checks.

#### Equal transformed counters

Every equal-counter iteration:

1. Decodes the frame position.
2. Unconditionally reads the format-status global.
3. Evaluates whether decoded position plus decoded record length equals the decoded frame boundary.

The format-status read precedes evaluation of the equality expression, including its length-byte reads and boundary decoding. Relative operand-read ordering inside that expression remains unspecified.

If equality holds, depth decreases by one, and the iteration’s saved carried status is restored. The newly read format status is discarded.

If equality fails, the newly read format status becomes the carried status. Depth and frame contents remain unchanged, and completion repeats immediately rather than returning to the outer status guard.

Stable equal counters and a stable end-versus-boundary mismatch therefore produce nontermination, even when format status is nonzero. If later reads permit progress, a subsequent iteration saves the mismatch-selected status; a successful pop restores that saved value, not necessarily the original zero status.

### Final dependency call

Initial extent rejection or an outer-loop exit calls F-5e3309c9d083 with the selected workspace pointer.

After normal return, the result contains that pointer and the retained status. No subsequent status-global reload is visible.

For traversal exits, the terminal outer-entry decoder and counter-unit reads occur before this call. Nontermination, invalid accesses, or abnormal dependency behavior can prevent it.

## Side effects

Direct writes target workspace frame fields. Reads include descriptor words, record bytes, workspace fields, and globals.

Configuration is not captured atomically. Observable distinctions include:

- Root-boundary-factor capture after the workspace request.
- Pointer-test computation before allocation-status capture.
- A fresh descriptor extent read after three root writes.
- Decoder and counter-unit reads before every outer guard.
- Fresh counter decoders for completion comparisons.
- A fresh counter unit for child initialization.
- Outer-entry captures for advancement arithmetic.
- An unconditional format-status read on every equal-counter completion iteration.

No non-aliasing check is visible. Workspace writes may affect later descriptor or buffer reads if regions overlap. Advancement must retain its 32-bit counter-word read; replacing it with a halfword read would introduce an unestablished byte-order assumption.

There is at most one workspace-request call. An accepted workspace result reaches one final dependency call only if execution reaches a corresponding normal exit.

Ownership is unresolved. The final dependency may invalidate storage; if so, the returned workspace pointer is dangling. Inactive paths instead return the caller-supplied descriptor pointer.

No explicit recovery is shown for inaccessible storage, insufficient workspace, arithmetic-derived invalid addresses, or dependency failures other than a null workspace result.

## Acceptance examples

These are conditional static criteria, not executed tests. They assume accessible storage and defined arithmetic for the operations involved.

1. **Null descriptor.** Any capacity returns the captured inactive status and null pointer, with no descriptor dereference or dependency call.

2. **Zero capacity.** A readable non-null descriptor’s first word is read before capacity prevents the workspace request. The original descriptor pointer is returned.

3. **Null workspace.** Root-boundary capture and pointer-test computation precede allocation-status capture. The gate rejects null, and no final dependency call occurs.

4. **Workspace address one.** The subtraction produces zero, and the greater-than-one comparison leaves it unchanged. The allocation status is read before the gate accepts the pointer. This establishes no storage-validity guarantee.

5. **Extent threshold.** A scaled extent of 31 produces no frame writes and one final dependency call. A value of 32 passes this check only.

6. **Child count one.** Valid record bounds and spare capacity cause a child push. At full capacity, the capacity status is selected instead; zero-child completion is not entered.

7. **Fresh child initialization.** If outer entry captures counter unit five but child initialization reads seven, the child current-counter field receives seven.

8. **Captured advancement.** Suppose the captured decoder is three, the captured unit is five, and narrowing the 32-bit word read at frame offset 4 yields two. Unequal-counter advancement stores 35. Merely specifying that the halfword at offset 4 equals two is insufficient without a byte-order assumption.

9. **Byte-order-sensitive advancement.** Suppose the two counter halfwords hold two and nine, and the captured factors are three and five. Conventional little-endian interpretation of the spanning word gives an advancement result of 35; conventional big-endian interpretation gives 140. The supplied evidence does not select either interpretation.

10. **Successful equal-counter pop.** Format status is read after position decoding and before equality evaluation even when equality succeeds. The pop restores the iteration’s saved status, not the newly read value.

11. **Repeated mismatch.** Stable equal transformed counters and a persistent end-versus-boundary mismatch repeatedly read format status and evaluate equality without reducing depth or reaching the final dependency.

12. **Mismatch followed by success.** A mismatch selecting a nonzero status can affect a later successful pop: that later iteration restores its own saved nonzero status.

13. **Header wrap.** Wrapped position plus 20 fails before record-byte access. If the selected format status is nonzero, a terminal outer iteration reads the decoder and counter unit before the final dependency.

14. **Request overflow.** Capacity-times-12 may wrap while the original capacity remains the depth limit. Passing a depth check does not establish that the corresponding frame fits the returned storage.
