# F-57a123ecc9c9

## Purpose

F-57a123ecc9c9 selects one 24-byte storage unit from a caller-supplied state object and clears four fields within that unit. It prefers a linked supply of reusable units. When that supply is empty, it uses the next unit in a contiguous region, acquiring a new region if the current position equals the region’s end.

The function has no explicit return value. Its observable results are state updates, selected-unit writes, and, on the region-growth path, two calls to F-871e64ddc6de.

The interpretation as a storage pool is inferred intent. The selection rules, byte offsets, arithmetic, and write order below are established by the supplied static representation. No runtime tests have been performed.

## Interface

### Input state

The single argument is an address of a mutable object containing at least four consecutive 32-bit words:

| Byte offset | Contract name | Observed use |
|---|---|---|
| 0 | Region-chain head | Address of the latest region descriptor, or zero. |
| 4 | Reusable-unit head | Address of a reusable unit, or zero. |
| 8 | Sequential position | Address selected when the reusable-unit head is zero. |
| 12 | Sequential end | Compared with the sequential position to decide whether to acquire another region. |

These names describe observed roles, not independently established source-level types.

The supplied representation uses 32-bit integer words and stores addresses in those words. This contract therefore describes a 32-bit address representation. Portability to wider pointers is not established.

### Region descriptor layout

A nonzero region-chain head is treated as the address of a descriptor with this 12-byte layout:

| Byte offset | Width | Observed use |
|---|---|---|
| 0 | 32 bits | Link to the preceding descriptor. |
| 4 | 32 bits | Capacity used to calculate the next region’s capacity. |
| 8 | 32 bits | Address of the descriptor’s storage region. |

Existing descriptors are not otherwise inspected or validated.

### Unit layout

Each sequentially consumed unit occupies 24 bytes. For the selected unit:

| Byte offset | Width | Operation |
|---|---|---|
| 0 | 8 bits | Written as zero. |
| 1–3 | 3 bytes | Not directly written. |
| 4 | 32 bits | Written as zero. |
| 8 | 32 bits | Written as zero. |
| 12 | 32 bits | Read as a successor address on the reusable-unit path, then written as zero. |
| 16–23 | 8 bytes | Not directly written. |

The 24-byte stride does not imply that all 24 bytes are initialized.

### Output and validity requirements

There is no explicit result address, status code, or error value. The selected unit’s address is used internally and is not written to a dedicated output field.

For normal completion:

- The state object must support the specified reads and writes.
- A nonzero reusable-unit head must designate memory supporting a 32-bit read at offset 12 and all selected-unit writes.
- A sequential position used without region growth must designate memory supporting all selected-unit writes.
- A nonzero descriptor address used for capacity calculation must support a 32-bit read at offset 4.
- Results from F-871e64ddc6de must support their subsequent uses.

There are no explicit checks enforcing these requirements.

## Behavior

### 1. Select the reusable-unit path first

The function first reads the reusable-unit head at state offset 4.

If that value is nonzero:

1. That address becomes the selected unit.
2. A 32-bit successor address is read from the selected unit at offset 12.
3. The successor is written to the state’s reusable-unit head.
4. The selected unit is initialized as described under “Selected-unit initialization.”

On this path, the function does not directly read the sequential position, sequential end, or region-chain head. It does not call F-871e64ddc6de.

The successor is consumed before the selected unit’s offset-12 field is cleared. There is no validation of the successor, no membership check, and no cycle detection. A self-link is therefore not rejected: with ordinary nonoverlapping memory, the state remains pointed at the same unit while that unit’s link field becomes zero.

### 2. Otherwise, select the sequential position

If the reusable-unit head is zero, the function reads the sequential position at state offset 8 and compares it for equality with the sequential end at offset 12.

If the two addresses differ:

1. The existing sequential position becomes the selected unit.
2. The state’s sequential position is written with the selected address advanced by 24 bytes.
3. The selected unit is initialized.

The comparison is equality only. The function does not establish that the position is below the end, within an allocation, aligned, or at least 24 bytes from the end. A position beyond the end still takes this path if its address differs from the end address.

A zero sequential position paired with a nonzero end also takes this path. There is no fallback allocation or null-address check before attempting the selected-unit writes.

### 3. Acquire a region when position equals end

If the sequential position equals the sequential end, the function calculates a new capacity.

If the region-chain head is zero, the capacity is 32 units.

Otherwise, it reads an unsigned 32-bit capacity, \(n\), from offset 4 of the current region descriptor. It forms two candidates:

- Additive candidate: \(a = (n + 32) \bmod 2^{32}\).
- Proportional candidate: \(g = (n + \lfloor n/2 \rfloor + \lfloor n/8 \rfloor) \bmod 2^{32}\).

The selected capacity is \(g\) if \(a \leq g\) under unsigned comparison; otherwise it is \(a\). Equivalently, it selects the unsigned maximum of the two already-wrapped candidates.

The shifts used to obtain the fractional terms operate on the original unsigned 32-bit capacity. This is not an unbounded-integer growth calculation, and it is not a saturating calculation. Overflow can make the result smaller than the old capacity.

The requested storage byte count is:

\[
b = (24 \times \text{selected capacity}) \bmod 2^{32}.
\]

There is no check that this multiplication preserves the mathematical product.

The function then performs the following dependency calls and direct memory operations in order:

1. Calls F-871e64ddc6de with first argument 12 and second argument zero.
2. Calls F-871e64ddc6de with first argument \(b\) and second argument zero.
3. Writes the second call’s result into offset 8 of the descriptor returned by the first call.
4. Reads the current region-chain head from the state and writes it into descriptor offset 0.
5. Writes the selected capacity into descriptor offset 4.
6. Writes the new descriptor address into the state’s region-chain head.
7. Reads the storage address back from descriptor offset 8 and uses it as the selected unit.
8. Writes the selected address advanced by \(b\) bytes into the state’s sequential end.
9. Writes the selected address advanced by 24 bytes into the state’s sequential position.
10. Initializes the selected unit.

The initial capacity decision is made before either dependency call. The predecessor link is read from the state after both calls. Consequently, if a dependency changes the region-chain head, the descriptor linked as predecessor need not be the descriptor whose capacity determined the allocation size.

The function does not re-evaluate the reusable-unit head, the original equality comparison, or the selected capacity after the calls.

### 4. Selected-unit initialization

After path-specific state updates, the function directly writes the selected unit in this order:

1. Zero to the 32-bit field at offset 4.
2. Zero to the 32-bit field at offset 8.
3. Zero to the 32-bit field at offset 12.
4. Zero to the single byte at offset 0.

It does not directly clear bytes 1–3 or 16–23.

This order matters if the selected memory aliases state, descriptor memory, or another observable object. The function contains no alias checks. Ordinary pool-like interpretations require a valid, nonoverlapping layout; such nonoverlap is not enforced by the function itself.

## Side effects

### Direct state changes

With valid nonoverlapping memory:

- **Reusable-unit path:** updates only the reusable-unit head among the four state words.
- **Sequential path without growth:** updates only the sequential position among the four state words.
- **Growth path:** updates the region-chain head, sequential end, and sequential position. It makes no direct write to the reusable-unit head.

Every successful path also performs the four selected-unit writes described above.

These statements describe direct operations by this function. They do not constrain additional effects of F-871e64ddc6de or effects caused by aliasing.

### Memory lifetime and ownership

The growth path obtains two dependency results and records them as a descriptor and storage-region address. It links the new descriptor to the state’s then-current region-chain head.

No release operation appears. No old region is copied, resized in place, unlinked, or explicitly discarded. Under a valid stable pool layout, the descriptor chain retains references to earlier regions.

The source does not establish:

- Whether dependency results represent newly allocated memory.
- Whether ownership is transferred.
- Who must eventually release the descriptor or storage.
- Whether the two returned regions are distinct.
- Whether either returned region is initialized.

The function’s own partial initialization must not be interpreted as full-unit initialization.

### Errors and partial updates

There is no explicit failure branch, rollback, exception handling, or status reporting.

The first dependency result is not checked before descriptor writes. The second result is not checked before it is recorded and used as the selected-unit address.

If an operation faults or the dependency does not return normally, previously completed effects remain possible. For example:

- The first dependency call can complete before the second fails.
- A reusable-unit head can be advanced before a selected-unit write fails.
- A new descriptor can be published in the state before selected-unit initialization fails.

No failure atomicity is established.

### Concurrency

No synchronization or atomic protocol is visible. State fields and unit fields are updated through separate accesses. The representation does not establish thread safety, reentrancy safety, or safe concurrent observation.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Unless stated otherwise, they assume valid nonoverlapping memory, adequate address range, normal dependency returns, and no dependency mutation of relevant state.

### Reuse takes precedence over sequential exhaustion

Given a nonzero reusable-unit head pointing to unit A, whose offset-12 successor is B, the function must:

- Write B into the reusable-unit head.
- Perform the four specified zero writes in A.
- Make no dependency calls.
- Leave the sequential position and end directly unchanged.

This applies even if the sequential position equals the sequential end.

### Sequential consumption preserves uninitialized bytes

Given a zero reusable-unit head and a sequential position P different from the end, the function must advance the position to P plus 24 bytes and initialize the specified fields at P.

If bytes 1–3 and 16–23 initially contain nonzero values, those bytes must remain unchanged by the function’s direct writes. Whole-unit zeroing would not match the observed behavior.

### First region

Given a zero reusable-unit head, equal sequential position and end, and a zero region-chain head:

- Capacity is 32.
- Dependency requests are 12 and 768, in that order, each paired with a second argument of zero.
- If the returned descriptor is H and storage address is D, H receives predecessor zero, capacity 32, and storage address D.
- The state receives region-chain head H, sequential end D plus 768, and sequential position D plus 24.
- The first unit at D receives the four initialization writes.

### Additive growth wins

Given an existing descriptor capacity of 32 on the growth path, the proportional candidate is 52 and the additive candidate is 64. The selected capacity is 64, and the storage request is 1,536 bytes.

### Proportional growth wins

Given an existing descriptor capacity of 64 on the growth path, the proportional candidate is 104 and the additive candidate is 96. The selected capacity is 104, and the storage request is 2,496 bytes.

### Wrapped allocation size

Given an existing descriptor capacity of \(2^{31}\), the selected capacity is hexadecimal D0000000. Multiplication by 24 produces a 32-bit request of hexadecimal 80000000 after wrapping.

The function does not reject this case. Safe completion cannot be inferred from the requested byte count alone.

### Dependency changes the predecessor

Given a growth calculation based on descriptor A, suppose a dependency call changes the state’s region-chain head to B and both calls return normally.

The new descriptor’s predecessor field must receive B, the value read after the calls. The capacity remains the value calculated earlier from A.
