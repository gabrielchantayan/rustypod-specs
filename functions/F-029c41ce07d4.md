# F-029c41ce07d4

## Purpose

F-029c41ce07d4 computes a Boolean condition from two dependency results, performs a resource-dependent lookup in shared state, and, when a matching entry is accepted, synchronizes a byte in that entry’s associated object.

If the stored byte differs from the computed Boolean value, the function writes the new value and makes two ordered virtual calls. It returns a 32-bit success indication for an accepted entry, including an entry whose byte already has the required value.

The apparent intent is to update a named Boolean property and issue two notifications when its value changes. That interpretation is inferred. The established behavior is the lookup, byte comparison and write, dispatch sequence, and return behavior described below. In particular, the traversal must not be replaced by a conventional ordered-container search without additional evidence.

### Output

- **0:** the resource dispatch returned zero, the resource-processing dependency returned zero, or the final iterator check returned nonzero.
- **1:** the final iterator check returned zero and the associated byte was examined, whether or not a write and notification sequence was necessary.

A return of 1 does not independently establish that either notification succeeded. Their results are not checked.

## Behavior

### 1. Compute the desired Boolean value

The function performs these calls in order:

1. F-7e4f952e879e, without explicit arguments.
2. F-25a21d84b35d, without explicit arguments.
3. F-83f4b29c99c5, with the value obtained by dereferencing the predicate input reference.

The desired Boolean value is true exactly when both calls in steps 2 and 3 returned nonzero. Negative nonzero results also count as true. Both dependencies are called; this is not a short-circuit decision that skips the third call when the second result is zero.

The function retains:

- A Boolean representation of the decision.
- A 32-bit unsigned representation equal to exactly 0 or 1.

The result of F-7e4f952e879e is not used. Its effects, if any, precede the predicate calls.

### 2. Resolve and process a resource

The function calls F-938c950e5046 to obtain a dispatch object. It then invokes the callable at offset `0xF8` in that object’s dispatch table, passing:

1. The object itself.
2. The resource selector.

If that invocation returns zero, the function immediately returns 0. No lookup or target-byte access follows.

Otherwise, the function calls F-682adfd5a561 with:

1. The nonzero dispatch result.
2. The constant `0x1700`.

After that call, the function reads and saves the container global. It then checks the dependency’s result. If the result is zero, it returns 0.

Thus, even on this second early-failure path, the container global is read after the dependency returns. That read is distinct from dereferencing the container.

### 3. Construct the lookup record and initialize traversal

For the continuing path, the function constructs an eight-byte temporary record:

- First word: the lookup token.
- Second word: the computed 0-or-1 value.

The lookup token is stored before traversal setup. The second word is stored after the initial traversal and candidate references have been obtained.

The initial references are read as follows:

1. Re-read the container global.
2. Follow its field at offset `0x10`.
3. Read that referenced object’s field at offset `0x04` to obtain the initial traversal pointer.
4. Re-read the container global again.
5. Read its field at offset `0x10` to obtain the initial candidate.

These reads do not all use the container base saved after F-682adfd5a561. Later comparator context and header accesses use that saved base.

The function does not establish that these separately read container values are identical under concurrent mutation or dependency side effects.

### 4. Traverse the structure

While the traversal pointer is nonzero, the function calls F-bcefa5957e76 with:

1. The saved container base plus `0x19`.
2. The current traversal node’s address plus `0x10`.
3. The address of the temporary lookup record.

Only zero versus nonzero in the result controls traversal:

- **Zero result:** read the node’s pointer-valued field at offset `0x08`; use that child pointer as both the next traversal pointer and the new candidate.
- **Nonzero result:** read the node’s pointer-valued field at offset `0x0C`; use it as the next traversal pointer, leaving the candidate unchanged.

The zero-result branch records the selected child, not the node just compared. If that child is zero, the candidate becomes zero and traversal terminates.

No ordering relation such as “less than,” “greater than,” or “equal” is established for these comparator results. A negative result takes the same branch as any other nonzero result.

### 5. Select a candidate or header

After traversal terminates, the function reads the saved container’s field at offset `0x10` into temporary header storage.

It calls F-f063d8ade9f7 with addresses of:

1. The candidate storage.
2. The temporary header storage.

If this call returns nonzero, the candidate is not used for the next comparison.

If it returns zero:

1. F-539f08165386 is called with the current candidate value.
2. F-bcefa5957e76 is called with:
   - The saved container base plus `0x19`.
   - The temporary lookup record’s address.
   - The result from F-539f08165386.
3. A zero comparator result selects the current candidate.

If the initial check returned nonzero, or the subsequent comparator returned nonzero, the function instead selects a value freshly read from the saved container’s field at offset `0x10`.

The argument ordering of the second comparator call differs from the traversal calls: the lookup record is now its second argument, rather than its third.

F-f063d8ade9f7 receives writable addresses. The contract does not assume it leaves those temporary values unchanged. Later steps use their values after the call.

### 6. Perform the final check

The selected value is copied into a new temporary entry slot. The saved container’s field at offset `0x10` is read again into a new temporary header slot.

F-f063d8ade9f7 is called with the addresses of those two slots.

- A nonzero result causes a return of 0.
- A zero result permits the associated-object access.

Any changes the dependency makes to the entry slot affect which entry is subsequently dereferenced. The function does not retain an independently validated node reference for the byte access.

### 7. Synchronize the byte and notify

For an accepted entry, the function:

1. Reads its pointer-valued field at offset `0x14`.
2. Reads the associated object’s byte at offset 100.
3. Compares that byte numerically with the original 32-bit desired value, 0 or 1.

This is an exact byte-value comparison, not a test of whether the old byte is merely zero or nonzero. For example, an old value of 2 differs from a desired value of 1.

If the values are equal, no write or notification call occurs, and the function returns 1.

If they differ:

1. The associated-object pointer is obtained again through the entry’s field at offset `0x14`.
2. The Boolean value is written to byte offset 100.
3. F-9d0ecc5f6adf is called to obtain a notification dispatch object.
4. Its virtual entry at offset `0x58` is called with the object, the first event selector, and the current first word of the lookup record.
5. The same dispatch-table offset is invoked again on the same object, with the second event selector and the current first word of the lookup record.
6. The function returns 1 if execution returns normally from both calls.

The target-byte write precedes notification-object acquisition and both notifications. There is no rollback path.

The second dispatch-table lookup occurs after the first notification returns. The function does not establish that the first notification preserves the object’s dispatch table.

## Acceptance examples

These examples are conditional static acceptance criteria, not executed tests.

1. **First resource failure.** If the `0xF8` dispatch returns zero, the result is 0. The initial three dependencies and dispatch-object acquisition have already occurred. F-682adfd5a561 and the lookup do not occur.

2. **Resource-processing failure.** If resource dispatch returns nonzero but F-682adfd5a561 returns zero, the result is 0 after the container-global read. No lookup or target-byte update follows.

3. **Both predicates nonzero.** Predicate results of −1 and 7 produce desired value 1, not either original integer.

4. **One predicate zero.** If either predicate result is zero, the desired value is 0. Both predicate dependencies still execute.

5. **Accepted unchanged entry.** If the final check returns zero and the associated byte already equals the desired value, the result is 1 with no byte write, notification-object acquisition, or notification calls.

6. **Accepted changed entry.** If the desired value is 1 and the associated byte is 0, the byte becomes 1 before notification-object acquisition. The first selector is dispatched before the second. Normal completion returns 1.

7. **Noncanonical old byte.** If the desired value is 1 and the old byte is 2, the function takes the change path and writes 1. It does not treat both values as equivalent truth values.

8. **Zero traversal branch.** If a traversal comparison returns zero and the offset-`0x08` child is zero, both traversal and candidate become zero. Any handling of that candidate belongs to the subsequent dependencies; no current-node fallback may be silently substituted.

9. **Final rejection.** If the final F-f063d8ade9f7 call returns nonzero, the result is 0 without accessing the associated-object byte.

10. **Notification failure semantics.** If a notification returns an ordinary error value, that value is ignored. If it does not return normally, completion and the second notification are not guaranteed; the preceding byte write is not undone by this function.
