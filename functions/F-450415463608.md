# F-450415463608

## Purpose

F-450415463608 transforms two 32-bit operand encodings into a 64-bit result. Its operand classification, sign handling, reciprocal approximation, and infinity encodings are consistent with a software binary32 division primitive. That interpretation is **inferred intent**, not an established guarantee of IEEE 754 division.

The established interface returns two distinguishable 32-bit words:

- A low word containing a computed encoding, a selected constant, or a delegated result.
- A high word containing arithmetic metadata on the ordinary arithmetic path, but the original second operand on several exceptional paths.

Consequently, the returned value must not be treated uniformly as a binary64 floating-point number or as a binary32 result with a universally consistent status word.

NaN-like inputs can transfer control through an entry-state-dependent indirect target. The target’s identity and behavior are not established.

## Interface

### Explicit inputs

The visible entry accepts four 32-bit words:

| Position | Behavioral role |
|---|---|
| First | Primary operand encoding. |
| Second | Secondary operand encoding. |
| Third | No visible use. |
| Fourth | No incoming-value contribution to any visible result or dependency argument. |

The first two operands are interpreted as bit patterns, not converted from integer values to floating-point values.

For classification:

- Bit 31 is the sign bit.
- Bits 30–23 form an 8-bit exponent field.
- Bits 22–0 form a 23-bit fraction field.

An exponent of zero selects exceptional handling, even when the fraction is nonzero. An exponent of 255 also selects exceptional handling.

### Implicit inputs

Some paths additionally depend on:

- A byte lookup table.
- A 32-bit configuration word.
- A 32-bit default-result word.
- Three further 32-bit data words used by delegated paths.
- An incoming continuation/link value.
- Bit 0 of an incoming machine-status quantity.

These are observable dependencies, not values supplied by the four explicit arguments.

### Return layout

For a locally constructed return, the 64-bit value is:

\[
(\text{high word} \times 2^{32}) \;|\; \text{low word}.
\]

This describes bit significance, not an in-memory byte order. No result buffer or output pointer is present.

Delegated paths return the indirect target’s 64-bit result without a visible local adjustment.

### Arithmetic conventions

Except where explicitly identified as signed:

- Intermediate arithmetic is 32-bit and wraps modulo \(2^{32}\).
- Comparisons are unsigned.
- Right shifts insert zero bits.
- Multiplication retains only its low 32 bits.
- A carry means the carry out of a 32-bit unsigned addition.

Signed comparisons interpret bit 31 as the sign bit. Arithmetic right shifts replicate that bit. These distinctions affect the reciprocal refinement and the range-handling decisions.

No explicit argument is dereferenced. There is no visible caller-owned memory requirement for the four argument words.

## Behavior

### Classification and path selection

The ordinary arithmetic path is selected only when both operands have exponent fields in the inclusive range 1–254.

All other operand pairs enter exceptional handling. This includes subnormal encodings; they are not normalized and fed back into the ordinary arithmetic path.

The result-sign candidate begins as the exclusive-or of the two operand sign bits. Exceptional handling can modify this candidate for negative nonzero exponent-zero encodings.

### Ordinary arithmetic

#### Significands and normalization

Each operand contributes a 24-bit significand formed from its 23-bit fraction with an implicit leading one.

The first significand is compared with the second:

- If the first is at least the second, it is used unchanged.
- Otherwise, it is doubled.

Equality belongs to the first case.

The exponent accumulator incorporates the exponent difference, a bias contribution of 125, and the sign candidate stored in bit 8. Before its final use, that accumulator receives an arithmetic-right-shift correction and a one-unit increment when the original first significand was at least the second.

This accumulator is not simply an independently stored binary32 exponent: its low bits and signed interpretation participate in later decisions.

#### Table-seeded quotient refinement

Exactly one byte is read from the reciprocal-seed table. Selection depends on the upper seven bits of the second significand. Across ordinary inputs, the selector ranges from 64 through 127 and addresses entries in reverse displacement order from the table anchor.

The selected byte feeds a reciprocal refinement using wrapped 32-bit products and arithmetic right shifts by 4 and 21. Two quotient contributions are then obtained using logical right shifts by 20 and 19. Residual scaling uses factors of \(2^{11}\) and \(2^{12}\).

These are integer operations on encoded significands. Replacing them with host floating-point division is not established to preserve the low result word or metadata.

After refinement, a residual is conditionally reduced by the second significand. The reduction occurs when adding the two’s-complement negation of that significand produces an unsigned carry.

The following three residual properties then affect the result:

1. Whether the corrected residual is nonzero.
2. Whether doubling it and adding the negated second significand produces an unsigned carry.
3. Whether its wrapped doubled value equals the second significand exactly.

The third property is the visible exact-halfway condition. Its relationship to a particular external rounding mode is not established.

#### Metadata

Before range handling, the high word contains:

| Bits | Condition |
|---|---|
| 8 | Result-sign candidate. |
| 30 and 1 | Set together when the corrected residual is nonzero. |
| 30 and 0 | Set together when the doubled-residual comparison produces carry. |
| 2 | Set when the doubled residual equals the second significand. |

Bit 3 is set on every locally returned ordinary-path result.

Some range-handling branches also place the low result word’s pre-adjustment least significant bit into high-word bit 31. This is a one-bit transfer, not a full-word negation.

The low candidate combines the two quotient contributions, both residual carry decisions, and the adjusted exponent accumulator, using wrapped 32-bit arithmetic.

#### Range handling

Let the adjusted exponent accumulator mean the value after its signed-shift correction and comparison increment.

The direct return is selected when:

- The exact-halfway condition holds and the doubled-residual carry is clear; or
- The exact-halfway condition does not hold and the accumulator is at most `0x00fbffff`.

That return preserves the low candidate and sets high-word bit 3.

Otherwise, extended range handling applies:

- High-word bit 3 is set.
- The low candidate’s current bit 0 is copied into high-word bit 31.
- Low-word bit 0 is cleared if either the exact-halfway condition holds or the accumulator equals `0x00fc0000`.

The resulting branches are:

1. **Accumulator below `0x00fc0000`, unsigned:** return the candidate.
2. **Accumulator at least that threshold unsigned, but with a negative signed difference from it:** return the candidate, except replace it with zero when accumulator bits 4–7 are nonzero.
3. **Remaining accumulator values:** apply a wrapped candidate-range test. If twice the candidate plus `0x01000000` exceeds `0xfdffffff`, return the candidate. Otherwise, return either `0x7f800000` or `0xff800000`.

The choice between those last two encodings depends on the signed interpretation of the candidate plus `0xa0000000`. A negative interpretation selects `0xff800000`; otherwise `0x7f800000` is selected.

These exact predicates are established. Describing every such branch as conventional underflow or overflow would go beyond the evidence.

### Exceptional handling without NaN-like operands

#### Neither operand has exponent 255

If the second operand has a nonzero exponent, the first necessarily has exponent zero on this path. The function returns:

- High word: the original second operand.
- Low word: the second operand’s sign bit, toggled only when the first operand is exactly `0x80000000`.

Thus, a nonzero negative subnormal first operand does not receive the same treatment as exact negative zero in this branch.

If both exponent fields are zero:

- High word: the original second operand.
- Low word: the default-result data word.

Fractions and signs do not further distinguish this branch.

Otherwise, the second exponent is zero and the first exponent is nonzero. The low word is an infinity encoding. Its sign is initially the operand-sign exclusive-or, then toggled independently for each operand that is a negative, nonzero exponent-zero encoding. The high word remains the original second operand.

#### At least one operand has exponent 255, but neither is NaN-like

A NaN-like encoding is detected by checking whether an operand’s wrapped doubled bit pattern exceeds `0xff000000`. This identifies an all-ones exponent with a nonzero fraction, irrespective of sign.

When neither operand satisfies that test:

- Two infinity operands return the default-result data word in the low word.
- An infinite second operand otherwise forces the low magnitude to zero.
- If the second operand is not infinite, the first operand’s sign-cleared encoding supplies the low magnitude.
- The adjusted sign candidate is merged into the low word.

The same negative-subnormal sign toggles described above apply before that merge.

All these returns preserve the original second operand as the high word.

### NaN-like operands and configuration dispatch

If either operand is NaN-like, the configuration word’s low four bits select delegated behavior. The indirect target is the incoming continuation/link value with its bottom two bits cleared.

The visible dependency calls are:

| Configuration case | Visible argument words |
|---|---|
| Low nibble 9; bit 20 clear | One word: zero. |
| Low nibble 9; bit 20 set; any of bits 16–18 set | Two words: `8`, and the bitwise complement of the configuration shifted left 15, then shifted left once more. Both shifts retain 32-bit results. |
| Low nibble 9; bit 20 set; bits 16–18 clear | Three words: `0x30000000`, original second operand, and `0x30000000` with incoming status bit 0 inserted at bit 27. |
| Low nibble 10 | One word: a selected data word, overridden with `0x80000000` when configuration bit 6 is set. |
| Low nibble other than 8, 9, or 10 | No explicit arguments visible. |
| Low nibble 8; bit 6 set | Two zero words. |
| Low nibble 8; bit 6 clear; bit 4 clear | Two words: another data word and the original second operand. |
| Low nibble 8; bit 6 clear; bit 4 set | Two words: zero and a replacement data word. |

For low nibble 8 with bit 6 clear, the first data word is read before testing bit 4, including when bit 4 subsequently causes its value to be discarded.

For low nibble 10, its data word is read before the bit-6 override.

No local NaN payload propagation, quieting policy, or exception policy can be established beyond these dispatch conditions and argument values.

## Side effects

### Observable reads

The visible local behavior includes:

- One seed-table byte read on the ordinary path.
- One default-result word read on either default-result branch.
- Configuration-word reads on NaN-like paths.
- Conditional data-word reads for delegated arguments.
- Use of incoming continuation and status state where described.

The configuration expression occurs repeatedly in the visible representation. There is no established snapshot guarantee across those references. Stability during a call is therefore a precondition for treating dispatch as a decision over one configuration value.

### Writes and ownership

No explicit memory writes, allocation, deallocation, reference-count updates, or ownership transfers are visible in locally completed paths.

This does not establish that delegated paths are side-effect-free. The indirect target may modify globals, access memory, transfer control elsewhere, or fail to return. Its ownership and lifetime obligations are unknown.

No error code, exception object, or logging mechanism is visibly produced by local paths. Special encodings and metadata are returned as data.

## Dependencies

The only supplied opaque function identity is F-450415463608 itself. No opaque identity is supplied for the indirect target; its behavior is **documented_only** rather than assigned an invented function ID.

Data dependencies are:

- The reciprocal-seed byte table.
- The configuration word.
- The default-result word.
- The three delegated-argument data words.

Their contents, initialization rules, mutability, and storage lifetime are not supplied.

Correct execution requires every selected data access to be valid. Delegated execution additionally requires the aligned incoming target to be valid under the applicable calling convention. Neither requirement is checked visibly.

For ordinary-path boundary acceptance:

- Equal significands must take the non-doubling normalization case.
- An exact-halfway residual must set high-word bit 2.
- Entry into extended handling must capture candidate bit 0 before any required clearing of that bit.
- Changing only the third or incoming fourth explicit argument must not change visible local behavior when all implicit inputs remain fixed.

## Uncertainties

### Inferred intent

The arithmetic strongly resembles binary32 division with residual-based rounding metadata. The intended rounding convention, consumer of the metadata, and treatment of the high word by callers are not established.

### documented_only

The following remain unresolved:

- Seed-table contents and their numerical accuracy.
- Default-result and delegated-data values.
- Meaning of configuration modes and flags.
- Indirect target identity, full calling convention, effects, and return guarantees.
- Whether incoming continuation and status values reflect the true external interface or an incomplete representation of machine-level control flow.
- Concurrency and volatility rules for shared data.
- Whether surrounding code interprets return metadata as floating-point exception information.

These unknowns prevent an unconditional claim of IEEE 754 conformance or complete numerical equivalence to hardware division.

## Evidence

The supplied static representation establishes the explicit argument widths, bit classifications, integer operations, conditional reads, local return construction, and visible indirect-call argument shapes described above.

No external dependency implementation, table contents, caller contract, or runtime observation was supplied. No runtime tests have been performed. The acceptance examples are deductions from visible branch conditions, not claims of observed execution.
