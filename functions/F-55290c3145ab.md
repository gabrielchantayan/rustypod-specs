# F-55290c3145ab

## Purpose

F-55290c3145ab validates three numeric inputs and, when they are accepted, coordinates an object-state update with one of two notification operations.

The established behavior is a bounded two-component conversion followed by ordered indirect calls. One input selects a final control state; the other two contribute to a value calculated as the first component multiplied by 60 plus the second component.

**Inferred intent:** the bounds and conversion resemble an hours-and-minutes setting with an enable-like selector. Neither time-related units nor the meaning of the control state is established by the available evidence. This contract therefore uses “selector,” “first component,” “second component,” and “control operation” rather than assigning application-specific semantics.

The function returns the 32-bit value 4 for rejected numeric inputs and the 32-bit value 0 after the accepted path completes normally. It does not establish that its dependencies succeeded.

## Interface

The interface consists of six positional inputs and one 32-bit result.

| Position | Contract name | Width and interpretation | Use |
|---|---|---|---|
| 1 | Context | Opaque 32-bit value | Forwarded to the selected notification dependency. Not directly dereferenced by this function. |
| 2 | Selector | Unsigned 32-bit integer | Must be 0 or 1. Also determines whether a final control operation is issued with argument 1. |
| 3 | First component | Unsigned 32-bit integer | Must be in the inclusive range 0–23. Contributes 60 times its value to the converted value. |
| 4 | Second component | Unsigned 32-bit integer | Must be in the inclusive range 0–59. Contributes directly to the converted value. |
| 5 | Notification selector | Signed 32-bit integer | Zero selects F-0c4d2e445922; every nonzero value selects F-bffb4f8e6161. |
| 6 | Auxiliary value | Opaque 32-bit value | Forwarded only to F-bffb4f8e6161. |

The result is a status word:

- **4:** at least one of the three numeric constraints is violated.
- **0:** the inputs are accepted and the complete accepted-path call sequence returns normally.

There is no explicit output buffer, output pointer, allocation request, or ownership-transfer parameter.

### Preconditions

Numeric validity is checked internally. Object validity and dependency availability are not.

For normal completion on the accepted path:

- F-a4a34621f0a7 must return a usable object reference.
- The object must support all indirect dispatches reached by the selected path.
- The object and its dispatch structure must remain usable across intervening dependency calls.
- Each dependency invoked on the path must return normally.

These requirements are not validated by F-55290c3145ab. Failure to satisfy them does not have an established conversion into status 4 or any other reported error.

The context and auxiliary values have no locally established validity requirements beyond their 32-bit representation. Their interpretation, including whether either represents an address or resource, belongs to the receiving dependency.

## Behavior

### Numeric acceptance

The accepted domain is exactly:

- selector is 0 or 1;
- first component is no greater than 23;
- second component is no greater than 59.

All three comparisons use unsigned interpretation where applicable. A 32-bit pattern that would represent a negative number under a signed interpretation is therefore outside the accepted range for any of these three inputs.

The rejection decision has the following short-circuit structure:

- A selector of 2 or greater causes rejection without further component comparisons.
- For a selector of 0 or 1, an excessive first component causes rejection without comparing the second component.
- Otherwise, the second component determines the remaining validity condition.

This comparison order does not create any established external memory access: the inputs are passed by value.

Rejected inputs return 4 without acquiring an object, invoking a notification dependency, or making an indirect call.

### Object acquisition and dispatch layout

Accepted inputs first cause a call to F-a4a34621f0a7 with the 32-bit argument 4.

The returned reference is treated as an object whose leading field supplies a dispatch-table base. The available representation uses 32-bit words for this dispatch mechanism. Relevant entries are selected by these byte offsets from that base:

| Byte offset | Role established by this function |
|---|---|
| 0x28 | Control operation receiving the object and one numeric argument |
| 0x2c | First observation operation receiving the object and returning a 32-bit value |
| 0x30 | Value operation receiving the object and the converted numeric value |
| 0x34 | Second observation operation receiving the object and returning a 32-bit value |

These are byte offsets, not entry numbers.

The object’s dispatch-table base and the selected entry are read for each indirect invocation. The contract does not require the dispatch table or its entries to remain unchanged between calls. In particular, the function does not establish that the target reached at offset 0x28 for a later invocation must equal the target reached at that offset earlier.

The object reference itself is retained for the remaining sequence. There is no established reacquisition after notification.

### Observations before notification

After acquisition, the function invokes the observation operation at offset 0x2c, then the observation operation at offset 0x34.

Each receives the acquired object as its only explicit argument. Their 32-bit return values are retained separately, in that order.

Both observations happen:

- before either notification dependency;
- before the control operation with argument 0;
- before the value operation;
- regardless of whether their returned values will be passed onward.

Thus the zero notification-selector path still performs both observations. They cannot be omitted merely because that branch does not forward their results: either observation may have effects not described by its return value.

### Notification selection

Exactly one notification dependency is called on a normally progressing accepted path.

If the notification selector is zero, the call is to F-0c4d2e445922 with:

1. the context;
2. the 32-bit constant 10.

If the notification selector is nonzero, including a negative signed value, the call is to F-bffb4f8e6161 with:

1. the context;
2. the 32-bit constant 10;
3. the auxiliary value;
4. the result of the observation at offset 0x2c;
5. the result of the observation at offset 0x34.

The two observations are forwarded as their previously obtained values. They are not repeated after notification.

No notification return value is used to choose a status or alter the remaining explicit sequence. This does not establish that notification is side-effect-free or cannot interrupt execution.

### Ordered update operations

After notification returns normally, the function performs these operations in order:

1. Invoke the control operation at offset 0x28 with the object and argument 0.
2. Invoke the value operation at offset 0x30 with the object and the converted numeric value.
3. If the selector is 1, invoke the control operation at offset 0x28 again with the object and argument 1.

For selector 0, the third operation is absent.

The converted value is:

**60 × first component + second component.**

On the accepted domain, the multiplication is at most 1,380 and the sum is at most 1,439. The calculation therefore fits in 32 bits without wrapping. Its minimum is 0.

No rounding, normalization, clamping, or carry adjustment is performed. For example, a second component of 60 is rejected rather than converted into an additional unit of the first component.

After the required update calls return normally, the function returns 0. Returns from the update operations are not used as success indicators.

## Side effects

The direct, established effects are dependency invocations and the reads needed for indirect dispatch. There is no explicit direct store to a caller-provided buffer or to an object data field in the available body.

The indirect calls may modify the object or other state. The notification dependencies and F-a4a34621f0a7 may also have effects. Their complete effects are not established here.

The required ordering on an accepted path is:

- acquisition;
- first observation;
- second observation;
- selected notification;
- control operation with 0;
- value operation;
- optional control operation with 1;
- successful status return.

This ordering matters even where a dependency’s return value is ignored.

### State and ownership limits

The control operation’s arguments establish requested operations, not a proven final state. It is not established that argument 0 disables anything, that argument 1 enables anything, or that the value operation stores its argument unchanged.

There is no explicit release operation for the acquired object. That absence does not establish:

- that the object is newly allocated;
- that the caller or this function owns it;
- that it is borrowed or globally shared;
- that retaining it is a leak;
- that any indirect operation releases it.

Likewise, the context and auxiliary values are forwarded without an explicit retain, copy of underlying storage, or release. Their downstream ownership semantics are unknown.

No preservation guarantee for globals, object fields, dispatch entries, or other shared state may be inferred for any dependency.

### Errors and partial execution

Numeric rejection occurs before all dependency calls and returns 4.

There is no explicit null check, dispatch-target check, rollback, retry, or dependency-error mapping. If a dependency faults, does not return, or invalidates state needed later, normal completion is not established.

The routine is not established to be transactional. A failure after notification or after a control operation may leave earlier effects in place.

## Acceptance examples

These examples specify conditional behavior. They are not runtime observations. Accepted-path examples assume all required objects and dispatch targets are usable and all dependencies return normally.

### Minimum values, zero notification selector

Inputs include selector 0, first component 0, second component 0, and notification selector 0.

Expected behavior:

- Acquire the object with argument 4.
- Perform both observations in order.
- Call F-0c4d2e445922 with context and 10.
- Perform the control operation with 0.
- Perform the value operation with 0.
- Do not perform a control operation with 1.
- Return 0.

The auxiliary value is not forwarded on this path.

### Maximum values, nonzero notification selector

Inputs include selector 1, first component 23, second component 59, and any nonzero notification selector.

Expected behavior:

- Acquire and observe the object in the prescribed order.
- Pass both observation results, in their original order, to F-bffb4f8e6161 along with context, 10, and the auxiliary value.
- Perform control with 0, value with 1,439, then control with 1.
- Return 0.

### Selector rejection

Selector 2 with otherwise valid components returns 4 and causes no dependency invocation. The same applies to any larger unsigned selector.

### Component boundary rejection

With selector 0 or 1:

- first component 24 is rejected;
- second component 60 is rejected;
- first component 23 and second component 59 are accepted.

Rejected cases return 4 without acquisition or notification.

### Signed notification selection

A notification selector of −1 selects F-bffb4f8e6161, not F-0c4d2e445922. Only zero selects the latter.

### Ignored observation results

With notification selector 0, both observations must still occur. Their returned values are not passed to F-0c4d2e445922, but their possible side effects remain part of the required call sequence.

### Dispatch changes during execution

If notification changes the acquired object’s dispatch-table reference while leaving the object usable, the later update operations resolve their targets through the then-current dispatch data. Reusing targets cached before notification would not preserve the established access behavior.

### Dependency failure

If acquisition returns an unusable reference, no defined status response is established. Returning 4 as a replacement for the ensuing failure would add behavior not present in this contract.
