# F-5c8c9e1af152

## Purpose

F-5c8c9e1af152 prepares a record header within an encoded, variable-length collection. It obtains a collection offset, selects an identifier and insertion offset, and requests a structural change through F-35c7724f8775. Only a zero result from that dependency authorizes direct writes of the record header, collection count, and output offset.

Record insertion is the inferred intent. Actual allocation, movement of existing records, collection-extent maintenance, and payload initialization are not established by this function.

Two maximum-count behaviors constrain that interpretation:

- With 65,535 records, automatic identifier selection cannot complete normally through its scan-exhaustion condition.
- With 65,535 records and an explicit nonzero identifier, position zero selects the first-record offset, while explicit position 65,536 enters a traversal that cannot terminate through its counter condition.

## Interface

The result is an unsigned 32-bit value. Seven arguments are accepted:

| Argument | Representation | Established role |
|---|---|---|
| Buffer handle | Pointer to a 32-bit address-bearing cell | Supplies the collection-buffer base address indirectly. Dependencies receive the handle and may change it. |
| Requested identifier | Unsigned 32-bit | Nonzero is used unchanged; zero initiates automatic selection. |
| Record discriminator | Unsigned 32-bit | Participates in identifier-conflict detection and is written into the new header. |
| Output-offset destination | Pointer to a 32-bit cell | Receives the selected insertion offset after successful structural update and all direct buffer writes. |
| Requested position | Unsigned 32-bit, also interpreted as signed 32-bit | Controls insertion-boundary traversal. Zero has special handling. |
| Requested payload extent | Signed 32-bit | Increased by 20 to obtain the new record extent. |
| Lookup context | Opaque 32-bit value | Passed unchanged to F-e81ed1edd673. |

Addresses and offsets follow the supplied 32-bit representation. A wider-address implementation requires an explicit compatibility decision.

### Encoding and layout

Each stored byte is decoded by multiplying it by 23 and retaining eight bits. Fields are assembled in big-endian significance order. Encoding multiplies each plain byte by −89 and retains eight bits, equivalently multiplying by 167 modulo 256. These byte transformations are inverses.

At the collection offset returned by F-e81ed1edd673:

| Relative byte offset | Width | Use |
|---|---:|---|
| 0 | 4 bytes | Encoded collection extent |
| 14 | 2 bytes | Encoded record count |
| 20 | — | First-record boundary |

A record has the following relevant layout:

| Relative byte offset | Width | Use |
|---|---:|---|
| 0 | 4 bytes | Encoded record extent |
| 4 | 4 bytes | Encoded discriminator |
| 8 | 4 bytes | Encoded identifier |
| 12 | 8 bytes | Written as zero for the new record |
| 20 | Variable | Possible payload, not directly initialized here |

The semantic meanings of the collection’s other header bytes and the eight zeroed record bytes are unknown.

### Preconditions and limits

Defined memory access requires a readable buffer-handle cell, accessible metadata and traversal targets, and writable destinations after structural-update success. The output destination need only be accessed on that success path, but it is not checked for null beforehand.

These requirements are not enforced by bounds checks. Collection extent does not bound traversal. Extents need not be positive, aligned, or consistent with allocated storage to pass the visible branches.

Safe storage alone does not guarantee termination. In particular, maximum-count automatic selection and maximum-count explicit position 65,536 have no normal counter-based completion.

## Behavior

### Result selection and lookup

The function first reads and saves an entry-default global result value.

A null buffer handle, or a non-null handle containing address zero, returns that saved value without invoking either dependency.

Otherwise, F-e81ed1edd673 receives the buffer handle and lookup context. Its 32-bit result is interpreted as a collection offset:

- Zero prevents collection processing.
- Every nonzero value, including one, permits collection processing.

After the lookup call, a second global result value is read. A zero lookup result returns this later-read value. It is not necessarily equal to its value before the dependency ran.

The concrete values and intended meanings of these global results are unavailable.

### Metadata and eligibility

For a nonzero collection offset, the function reloads the buffer address from the handle and retains that address for metadata reads and subsequent traversals.

It decodes the collection extent, then the 16-bit record count. Individual byte-load ordering within a multi-byte decoding expression is not independently established.

Eligibility depends on the count:

- A nonzero count bypasses the collection-extent eligibility test.
- A zero count causes a third global result value to be read. Processing continues only if the decoded collection extent is less than 21. Otherwise, that third value is returned.

Consequently, this is not a general collection-size validation. A nonempty collection is not rejected here for an unusual extent.

For an eligible collection, the candidate next count is the old count plus one, held in 32 bits. Its range is 1 through 65,536. The requested position and candidate next count are then compared as signed 32-bit values.

Processing continues only when the signed requested position is no greater than the signed candidate next count. Failure returns the entry-default value saved before lookup, not a newly read default.

Requested positions with the high bit set are negative under this comparison and therefore pass it.

### Extent arithmetic

After the eligibility and position checks, 20 is added to the signed payload extent. The result supplies the new record extent.

There is no explicit rejection of negative payload extents, extents smaller than the fixed header, or signed overflow. The behavior of an overflowing signed addition is documented_only; no checked-arithmetic error path is established.

The requested resulting collection extent is the unsigned 32-bit sum of the old collection extent and the resulting new-record-extent bit pattern. That unsigned sum wraps modulo \(2^{32}\). No check relates it to allocation size or actual traversed boundaries.

### Identifier selection

A nonzero requested identifier is accepted unchanged. Duplicate discriminator-and-identifier pairs are not rejected on this path.

A zero requested identifier initiates candidate selection beginning with one. For each candidate, scanning starts at collection offset plus 20.

At each scanned location:

- The discriminator is decoded first.
- The identifier is decoded only when the discriminator matches.
- A matching discriminator and identifier constitutes a conflict.
- A conflict stops that candidate’s scan; the next candidate starts again at the first-record boundary.
- Without a conflict, the record extent is decoded and added to the traversal offset.

The scan counter begins at one. Its update increments the 32-bit value and then clears bit 16. Starting from one, it therefore progresses through 65,535 and then becomes zero; it never reaches 65,536. This is not an unrestricted 32-bit increment.

For counts below 65,535, a candidate scan can end by advancing its counter beyond the count. Under stable, well-formed storage and defined arithmetic, automatic selection chooses the smallest positive identifier absent for the requested discriminator. For count \(N<65{,}535\), such an identifier exists no later than \(N+1\).

For count 65,535, the scan counter is always no greater than the count. Therefore:

- An absent candidate does not finish scanning after the counted records. Scanning proceeds beyond that sequence.
- A conflict merely advances to another candidate and restarts scanning.
- No candidate can be accepted through exhaustion of the counted records.

Automatic selection at maximum count cannot complete normally through the visible control flow, even when the original counted collection is well formed and stable. A fault, invalid address, arithmetic problem, or external interruption is not successful selection. No smallest-unused-identifier guarantee applies at this count.

### Insertion-boundary selection

Insertion traversal occurs only after identifier selection finishes. Its initial offset is collection offset plus 20.

For an eligible empty collection, that offset is used without record traversal.

For a nonempty collection, the effective traversal position is:

- The low 16 bits of candidate next count when requested position is zero.
- Otherwise, the requested position unchanged.

The traversal counter starts at one. While its signed value is less than the signed effective position, the function reads the current record extent, advances the offset by that extent, and applies the same increment-and-clear-bit-16 counter update used by identifier scanning.

For counts below 65,535:

- Position one selects the first-record boundary.
- Accepted positive position \(P\) skips \(P-1\) records.
- Position count plus one selects the boundary after all counted records.
- Position zero selects that same boundary.
- A high-bit-set requested position selects the first-record boundary because the signed traversal condition is initially false.

At count 65,535, assuming an explicit nonzero identifier:

- Position zero truncates candidate next count 65,536 to zero. The insertion traversal performs no reads and selects the first-record boundary.
- Positions one through 65,535 select their corresponding boundaries.
- Explicit position 65,536 passes the initial position check but cannot terminate through traversal-counter progression. After skipping the 65,535 counted records, the counter becomes zero. The next iteration reads an extent at the boundary beyond the counted sequence, and traversal continues unless execution is otherwise interrupted.
- High-bit-set positions still select the first-record boundary.

With a zero requested identifier at maximum count, none of these insertion-selection outcomes is reached normally, because automatic identifier selection precedes them.

### Structural update

Once both identifier and insertion offset have been selected, F-35c7724f8775 receives, in order:

1. Collection offset.
2. Requested resulting collection extent.
3. Selected insertion offset.
4. Buffer handle.

Its unsigned 32-bit result becomes the function result without translation.

Only zero authorizes the direct writes described below. Every nonzero result suppresses those writes. Failure does not imply that the dependency preserved the buffer, handle, globals, or other state.

### Successful writes

After a zero structural-update result, the function reloads the buffer address before each of these groups:

1. Four encoded bytes of new record extent at the insertion offset.
2. Four encoded bytes of discriminator at insertion offset plus 4.
3. Four encoded bytes of selected identifier at insertion offset plus 8.
4. Zero bytes at insertion offsets plus 12 and 13.
5. Zero bytes at insertion offsets plus 14 and 15.
6. Zero bytes at insertion offsets plus 16 through 19.
7. Two encoded bytes of candidate next count at collection offsets plus 14 and 15.

Within each group, byte stores proceed in increasing-address order. The output-offset destination is written last, with the selected 32-bit insertion offset.

Only the low 16 bits of the candidate next count are stored. A prior count of 65,535 therefore becomes zero whenever the function reaches and completes these writes.

There is no rollback if a later memory access fails.

## Side effects

Direct writes are confined to the new record’s 20-byte header, the collection’s two-byte count, and the output-offset destination.

The function does not directly write the payload or collection extent, free storage, or return the selected identifier through a separate output.

Both dependencies may have additional effects. Their allocation, relocation, ownership, release, and failure-preservation behavior is unknown. Passing the buffer handle does not establish ownership transfer.

Address timing is observable:

- The entry-default result is saved before any dependency call.
- Other result globals are read later.
- Metadata and traversals use the buffer address captured after lookup.
- Success-write groups independently reload the handle.
- The output-offset write occurs after all buffer-write groups.

No alias protection is present. If a destination overlaps the handle cell, collection metadata, another header field, or the output cell, earlier writes can affect later accesses according to this order. Repeated handle reloads do not guarantee that all write groups target the same allocation.

No concurrency-safety guarantee is established.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Normal-completion cases assume accessible storage, defined arithmetic, stable metadata, and dependency behavior sufficient for the specified writes.

1. **Null handle.** The entry-default result is returned. Neither dependency is called, and no output offset is written.

2. **Zero lookup result.** With a nonzero initial buffer address, lookup returns zero. The second global result is read after that call and returned. Structural update is not called.

3. **Empty collection rejected.** Count is zero and collection extent is 21. The third global result is read and returned, with no structural-update call.

4. **Empty collection accepted.** Count is zero, collection extent is 20, position is zero, identifier is zero, and payload extent is 8. Identifier one and insertion offset collection offset plus 20 are selected. Structural update receives resulting extent 48. A zero result permits a record extent of 28, count one, and publication of the insertion offset.

5. **Smallest absent identifier below maximum count.** Count is two. Both records have the requested discriminator and identifiers one and three. Automatic selection chooses two. A record with a different discriminator would not conflict solely because its identifier matched.

6. **Explicit duplicate.** A nonzero requested identifier already exists with the same discriminator. This function performs no duplicate-rejection scan. Remaining checks and dependency success still govern completion.

7. **Position rejected.** Count is two and position is four. The saved entry-default result is returned; structural update and direct output publication do not occur.

8. **Signed position.** Count is two, identifier is explicitly nonzero, and position is 0x80000000. The signed position check passes, and insertion selection uses the first-record boundary without advancing through records.

9. **Structural-update failure.** The dependency returns a nonzero 32-bit value. That exact value is returned. No direct header, count, or output-offset writes follow, but dependency mutations remain possible.

10. **Maximum count, zero position, explicit identifier.** Count is 65,535 and identifier is nonzero. Position zero selects the first-record boundary because the effective position truncates to zero. Structural update is reachable. If it returns zero and all writes complete, the stored count becomes zero.

11. **Maximum count, explicit position 65,536.** Count is 65,535 and identifier is nonzero. The position check passes. Traversal advances through the counted records, wraps its counter to zero, and continues reading extents beyond that sequence. It does not reach structural update through normal counter-based termination.

12. **Maximum count, automatic identifier.** Count is 65,535 and identifier is zero, including when position is zero. An absent candidate causes scanning beyond the counted sequence; a conflict causes another candidate attempt. Neither outcome provides normal completion of identifier selection. The zero-position structural-update case in example 10 therefore does not apply.
