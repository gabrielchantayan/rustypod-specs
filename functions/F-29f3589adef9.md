# F-29f3589adef9

## Purpose

F-29f3589adef9 performs a chunked transfer through an opaque dependency and reports cumulative progress through a caller-supplied 32-bit output location.

The established behavior is a preparation step followed by repeated transfer attempts. The operation returns:

- **0** when its remaining-length state reaches zero.
- **3** when preparation reports failure.
- **5** when a transfer attempt returns a nonnegative result smaller than the amount requested for that attempt.
- **The result of F-10684331fba7** when a transfer attempt returns a value whose signed 32-bit interpretation is negative.

A conventional interpretation is that the operation transfers bytes from a caller-provided buffer into a prepared destination. That interpretation is inferred, not established: the direction of transfer, the units of the counts, and the meaning of the prepared object are not defined by the available evidence.

## Interface

The operation accepts seven arguments, in this order:

| Argument | Established representation and use |
|---|---|
| Context | A 32-bit address-like value. Supplies storage at byte offsets 32 and 36, and an address at byte offset 40 passed to a dependency. |
| Preparation selector | An opaque 32-bit value passed to F-c17dbd9c1a69. |
| Setup value | An opaque 32-bit value passed to F-58205e0d2cf0. |
| Requested length | An unsigned 32-bit count used to initialize the remaining-length state. |
| Progress output | An address of a writable 32-bit location. The operation clears this location before calling any dependency and updates it after each nonnegative transfer result. |
| Transfer address | A 32-bit address-like value passed to F-bb3053c86063 and advanced by each nonnegative transfer result. |
| Per-attempt context value | An opaque 32-bit value written to context offset 36 before every transfer attempt. |

The return value is a 32-bit unsigned value. Transfer results use a mixed interpretation: their high bit determines whether they enter the error path, while nonnegative results are compared and subtracted as unsigned counts.

### Layout requirements

The operation directly uses the following locations:

| Location | Access |
|---|---|
| Progress output, bytes 0–3 | Written with zero at entry; subsequently read and written for progress accumulation. |
| Context, bytes 32–35 | Written with zero before each transfer attempt. |
| Context, bytes 36–39 | Written with the per-attempt context value before each transfer attempt. |
| Context, starting at byte 40 | Its address is passed to F-c17dbd9c1a69. The required extent and layout are unknown. |
| Shared chunk-limit pointer | Read after setup and again during each attempt. |
| The 32-bit word addressed by a selected chunk-limit pointer | Read to determine an attempt’s requested length. |

The evidence does not establish alignment requirements, byte order, permissible address ranges, or the size of the context beyond these accesses and the opaque dependency’s requirements.

The progress output must be writable even when the requested length is zero or preparation fails. Context and transfer-address validity requirements may also arise inside dependencies; this operation does not validate them.

## Behavior

### 1. Entry and preparation

The first observable memory write is a 32-bit zero to the progress output.

The operation then invokes F-c17dbd9c1a69 with:

1. The context address plus 40 bytes.
2. The preparation selector.
3. The address of a local 32-bit result slot.

That dependency returns a 64-bit result. Its low 32 bits and high 32 bits have separate uses:

- A zero low half selects preparation failure.
- A nonzero low half allows processing to continue.
- On continuation, the high half is forwarded to another dependency.

If the low half is zero, the operation returns **3**. It does not call the setup or transfer dependencies on this path. The progress output has already been cleared, although the preparation dependency could itself have changed accessible memory.

If the low half is nonzero, the operation calls F-58205e0d2cf0 with five arguments:

1. The 32-bit value in the local result slot.
2. The high 32 bits of the preparation result.
3. The setup value.
4. A 32-bit zero.
5. A 32-bit zero.

The result of this setup call is not used to select any branch or return status. No setup-failure check is visible.

The local result slot is not visibly initialized before preparation. Successful preparation therefore needs to supply a valid value there, or some separately established calling convention must make its subsequent use valid.

### 2. Initial chunk-limit capture

After setup returns, the operation reads a shared pointer to a 32-bit chunk-limit word and retains that pointer for later comparisons.

This capture occurs even if the requested length is zero. The zero-length path does not, however, visibly dereference the captured pointer.

The retained pointer and the shared pointer are not interchangeable in the contract. Later iterations reload the shared pointer, but comparisons continue to use the originally retained pointer.

### 3. Completion check

At the beginning of each loop iteration, the operation checks the unsigned 32-bit remaining length.

If it is zero, the operation returns **0** immediately. No per-attempt context writes or transfer call occur during that iteration.

Consequently, a zero-length request still performs preparation and, if preparation succeeds, setup. It is not an unconditional success shortcut.

### 4. Per-attempt state writes

For each iteration whose remaining length is nonzero, the operation performs these writes in order:

1. Write the per-attempt context value to context offset 36.
2. Write zero to context offset 32.

These writes occur before selecting the attempt length and before invoking the transfer dependency. They recur on every attempt, including an attempt that subsequently reports a short result or an error.

Neither field is visibly restored on return.

### 5. Attempt-length selection

After the context writes, the operation reloads the shared chunk-limit pointer. It then compares the remaining length with the 32-bit word addressed by the retained pointer.

The selection rule is:

- If the remaining length is less than or equal to the retained pointer’s current word, request the remaining length.
- Otherwise, request the word addressed by the newly loaded shared pointer.

The selected value is obtained after the comparison. The operation does not take one immutable numeric snapshot of the limit for its entire execution.

If the shared pointer and its target remain stable, this is equivalent to requesting the smaller of the remaining length and the chunk limit. That equivalence is conditional. A dependency may change the shared pointer or its target; the visible operation contains no protection against such changes.

### 6. Transfer invocation and result classification

F-bb3053c86063 receives:

1. The prepared 32-bit value supplied through the local result slot.
2. The current transfer address.
3. The selected unsigned 32-bit attempt length.

Its 32-bit result is first interpreted as signed.

#### Negative signed result

If the result has its high bit set, the operation:

1. Calls F-10684331fba7 with the context.
2. Returns that dependency’s 32-bit result unchanged.

The failed attempt’s result is not added to progress, subtracted from the remaining length, or added to the transfer address.

The context writes for this attempt have already occurred. Any effects inside F-bb3053c86063 or F-10684331fba7 remain possible. In particular, the caller cannot assume that the progress output retains its earlier value if either dependency can reach it.

#### Nonnegative result

For a result in the range 0 through 2,147,483,647, the operation:

1. Determines whether the returned count is smaller than the requested attempt length, using unsigned comparison.
2. Subtracts the returned count from the unsigned 32-bit remaining length.
3. Advances the transfer address by the returned count.
4. Reads the current 32-bit progress output and adds the returned count.
5. Writes the resulting 32-bit value back to the progress output.

If the returned count is smaller than the attempt length, the operation then returns **5**. The short attempt’s progress is included before this return.

Otherwise, another iteration begins.

### 7. Arithmetic and termination boundaries

No visible check rejects a returned count larger than the requested attempt length.

An oversized nonnegative result is therefore not a short result. The remaining-length subtraction is unsigned 32-bit arithmetic and can wrap. Such a result may cause later attempts to operate on a much larger remaining length rather than terminate.

The transfer address and progress storage are also 32-bit quantities. The source-facing representation uses signed types for some associated arithmetic, so portable signed-overflow behavior cannot be established. Callers should not rely on address wraparound or progress overflow as a supported interface behavior.

A requested attempt length may exceed 2,147,483,647. A returned value with the same bit pattern would nevertheless enter the negative-result path. There is no visible guard limiting attempt lengths to the nonnegative signed-result range.

A zero chunk limit is not rejected. If the remaining length is positive, the selected attempt length is zero, and the dependency returns zero, the operation neither reduces the remaining length nor reports a short result. It repeats. Termination then depends on changed state or a later different dependency result.

## Side effects

Established direct side effects are:

- Clearing the progress output at entry.
- Repeated writes at context offsets 36 and 32, in that order.
- Progress accumulation after each nonnegative transfer result.
- Calls to preparation, setup, transfer, and conditional error-processing dependencies.
- Reads of a shared pointer and its selected 32-bit target.

There is no visible allocation, release, close, or finalization call. This does **not** establish that dependencies allocate nothing, retain nothing, or perform cleanup. Ownership of the prepared value and any associated resource is undocumented.

The local result slot’s address is exposed to F-c17dbd9c1a69. Whether that dependency retains the address is unknown; no lasting validity of that local address is promised.

No explicit alias restrictions are visible. Aliasing can materially change behavior:

- If the progress output overlaps context offset 32 or 36, per-attempt context writes can replace the progress value before accumulation.
- If context writes overlap chunk-limit storage or its pointer, those writes can influence selection in the same attempt.
- If dependencies modify the progress output, the next accumulation uses its then-current contents rather than an independently maintained total.

No synchronization or atomicity guarantees are established. Concurrent mutation is not a supported assumption merely because shared state is read repeatedly.

## Acceptance examples

These examples are conditional contracts, not runtime observations. Unless stated otherwise, dependencies do not alter the progress output or relevant shared state, address arithmetic remains valid, and returned counts obey the stated conditions.

1. **Preparation failure**  
   Given any requested length, when preparation returns a zero low half, the operation first clears progress and then returns **3**. Setup, transfer, and error processing are not called.

2. **Successful zero-length request**  
   Given a requested length of zero and successful preparation, setup still runs. The operation captures the shared chunk-limit pointer and returns **0**, without per-attempt context writes or a transfer call.

3. **Exact completion across chunks**  
   Given a requested length of 10, a stable chunk limit of 4, and transfer results of 4, 4, and 2, the requested attempt lengths are 4, 4, and 2. Transfer addresses are the original address, original plus 4, and original plus 8. Final progress is 10 and the return value is **0**.

4. **Short first attempt**  
   Given a requested length of 10, a stable chunk limit of 4, and an initial transfer result of 3, progress becomes 3 and the operation returns **5**. No second transfer occurs.

5. **Short attempt after prior progress**  
   Given a requested length of 10, a stable chunk limit of 4, and results of 4 followed by 1, final progress is 5 and the return value is **5**.

6. **Negative result after prior progress**  
   Given an initial successful count of 4 followed by a result whose high bit is set, only the first count is directly accumulated. F-10684331fba7 runs, and its result is returned without normalization. Final progress is 4 only if the dependencies leave that location unchanged.

7. **Zero-length attempt without progress**  
   Given positive remaining length, a stable zero limit, and a transfer dependency that always returns zero without changing relevant state, the operation repeats rather than returning **0** or **5**.

8. **Oversized nonnegative result**  
   Given remaining length 3, attempt length 3, and result 4, the operation does not report a short result. Remaining length becomes 4,294,967,295. Further behavior depends on subsequent calls and address validity.

9. **Changed shared pointer between attempts**  
   Given an initially retained limit word of 4, a later shared pointer targeting a word containing 2, and remaining length greater than 4, the next attempt requests 2. The original word controls the comparison; the newly selected target supplies the requested count.

## Uncertainties

**Inferred intent:** chunked transfer, with **3** representing preparation failure and **5** representing incomplete transfer. These descriptive meanings do not establish external status-code definitions.

**documented_only unknowns:**

- Transfer direction, count units, and buffer access permissions.
- Full context layout and dependency-specific preconditions.
- Prepared-value ownership, lifetime, and cleanup obligations.
- Dependency mutation of globals, context, output, or caller memory.
- Guarantees that transfer counts do not exceed requested lengths.
- Required positivity and stability of the chunk limit.
- Supported behavior when signed address or progress arithmetic overflows.
- Reentrancy, thread safety, fault handling, and invalid-pointer behavior.

## Evidence

The contract is based solely on static inspection of the supplied function body and the supplied opaque dependency mapping.

Directly established facts include the entry write, dependency argument order, low/high preparation-result handling, context offsets and write order, distinct retained and reloaded chunk-limit pointers, signed transfer-result classification, unsigned short-result comparison, progress-update ordering, and return paths.

No runtime tests have been performed. Dependency implementations, external interface definitions, ownership rules, and synchronization guarantees were not available. Acceptance examples specify consequences under explicit conditions; they are not claims of observed execution.
