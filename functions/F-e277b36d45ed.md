# F-e277b36d45ed

## Purpose

F-e277b36d45ed routes an event-like record through an object’s indirect handlers. It also invokes a separate dependency for one distinguished event subtype.

The established behavior is an ordered dispatch sequence:

1. Conditionally invoke F-4fd087f2325e for category `0x16` and a distinguished nested subtype.
2. Conditionally invoke a preliminary indirect handler for category `0x16`, subtype zero.
3. Invoke one of two primary indirect handlers.
4. If processing has not already returned, conditionally invoke a final indirect handler for category `0x0f` whose associated value matches an object field.

Every indirect handler’s nonzero result terminates processing and is returned unchanged. A zero result allows processing to continue. The separate dependency’s result is not inspected.

The category, nested subtype, object dispatch-table pointer, and other fields are read at their respective stages. They are not captured as one immutable event snapshot. Mutations by earlier dependencies can therefore affect later routing.

Calling this an event-dispatch mechanism is inferred intent. The numeric routing rules and call order are established static behavior.

## Behavior

### 1. Distinguished-subtype notification

The function first reads the record category at offset `0x04`.

If the category is not `0x16`, this stage does not read the nested-record reference or subtype and does not call F-4fd087f2325e.

If the category is `0x16`, it:

1. Reads the nested-record reference at record offset `0x08`.
2. Reads the subtype at nested-record offset `0x04`.
3. Subtracts `0x2500` from that subtype and compares the result with `2`.

If the comparison succeeds, it reads the full integer at object offset `0x110`, converts that value to the character-sized argument type, and invokes F-4fd087f2325e with:

- The original object reference.
- The converted character-sized value.

For the ordinary 32-bit interpretation, subtype `0x2502` satisfies the comparison. Both the subtraction and result are small and representable for that input.

The subtraction is part of the supplied behavior, rather than an independently established direct subtype comparison. Overflow semantics for extreme subtype values are not specified by an external ABI or instruction listing.

The object field is read at integer width before conversion; this is not established as a byte-only memory load. Character signedness and the resulting argument interpretation for values with a set character sign bit remain unspecified.

After this call returns normally, processing continues. There is no result-dependent early return from this stage.

### 2. Preliminary zero-subtype handling

The function reads the record category again. It does not reuse the category or subtype from the first stage.

If this category is `0x16`, it reads the current nested-record reference and then its subtype. If the subtype is zero, it:

1. Reads the object’s current dispatch-table reference.
2. Reads the callable entry at table offset `0x124`.
3. Invokes that entry with the original object and record references.

A nonzero result is returned immediately. A zero result allows processing to continue.

This stage can observe changes made by F-4fd087f2325e. For example, the first dependency can change the category, replace the nested-record reference, or change the nested subtype. No preservation guarantee for those fields is established.

### 3. Primary handling

Unless the preliminary handler returned nonzero, the function reads the record category again.

If the current category is `0x16`, it reads the current nested-record reference and nested subtype. It selects:

- Table offset `0x10c` if that subtype is `0x2a`.
- Table offset `0x110` otherwise.

If the current category is not `0x16`, it selects table offset `0x110` without dereferencing a nested record.

After making that selection, it reads the object’s current dispatch-table reference, retrieves the selected entry, and invokes it with the original object and record references.

Exactly one primary handler is invoked on a normally executing path that reaches this stage. This includes records with categories other than `0x16` and `0x0f`; such categories do not bypass primary handling.

A nonzero primary-handler result is returned immediately. A zero result allows the final stage to execute.

The selected primary slot reflects record state observed before the primary call. The subsequent table lookup uses the object’s dispatch-table reference at that stage, not a table reference retained from an earlier call.

### 4. Final matching-record handling

After a primary handler returns zero, the function reads the record category again.

If the category is not `0x0f`, the function returns zero without reading the record’s offset-`0x08` field or the object’s offset-`0x50` field for this stage.

If the category is `0x0f`, it reads, in order:

1. The full value at record offset `0x08`.
2. The full comparison value at object offset `0x50`.

If the values differ, it returns zero.

If they match, it reads the object’s current dispatch-table reference, retrieves the callable entry at table offset `0x0e0`, and invokes it with the original object and record references.

A nonzero result is returned unchanged. A zero result leads to a zero return.

The comparison has no established meaning beyond full-width equality. Interpreting the compared values as handles, identifiers, or references is inferred intent, not an established contract.

- The distinguished-subtype dependency and preliminary handler are skipped.

- The primary handler at table offset `0x110` runs first.
- The handler at table offset `0x0e0` runs afterward.

- It does not perform the final-stage equality reads.

- It invokes the handler at table offset `0x124`.
