# F-43e9fa7452ce

## Purpose

F-43e9fa7452ce parses a count-prefixed sequence of byte-oriented records within a caller-supplied input boundary. Each record contains a one-byte payload length, a one-byte identifier, and the declared number of payload bytes.

For each structurally complete record, the function optionally searches a dispatch table and invokes the first matching handler. Records without a matching handler are skipped. Processing stops after the declared record count, on a structural error, or when a handler returns a nonzero result.

The function returns a 32-bit status and writes its stopping address through the caller’s cursor slot. Structural errors and handler failures have different cursor-position rules.

The visible format and dispatch behavior are established by static evidence. Their application-specific meaning is unknown.

## Interface

### Arguments and result

The function has four arguments:

1. **Cursor slot:** an address of a readable and writable 32-bit slot. On entry, the slot contains the initial input address. On every ordinary return, the function stores its stopping address in this same slot.
2. **Input boundary:** a byte address used as the exclusive upper boundary of the input.
3. **Dispatch table:** either null or an address of consecutive two-word entries.
4. **Auxiliary argument:** a pointer-shaped value with no established observable effect in the supplied body. It is not dereferenced or passed as a handler argument.

The represented interface uses 32-bit address-bearing slots, 32-bit table words, and a 32-bit integer result. Input fields are unsigned eight-bit quantities.

A result of zero indicates completion of all declared records. A detected structural error produces status 8 if the diagnostic dependency returns normally. A nonzero handler result is returned unchanged.

### Input layout

The initial input address identifies the count byte.

| Field | Width | Interpretation |
|---|---:|---|
| Record count | 1 byte | Number of records, from 0 through 255 |
| Payload length | 1 byte per record | Payload size, from 0 through 255 |
| Identifier | 1 byte per record | Dispatch key, from 0 through 255 |
| Payload | Declared length | Bytes bounded by the addresses supplied to a handler |

Each record occupies two header bytes plus its payload: between 2 and 257 bytes. The payload length excludes the header.

The count determines how many records are processed. The function does not require the records to consume all available input.

### Dispatch-table layout

Each entry consists of two consecutive 32-bit words and occupies eight bytes.

| Word | Interpretation |
|---|---|
| First | Identifier compared against the zero-extended record identifier |
| Second | Handler address; zero terminates the search |

The handler word is checked for termination before the entry’s identifier is used for matching. A zero handler word terminates the search regardless of the identifier word.

Matching uses the complete 32-bit identifier word. Values outside 0–255 cannot match an input identifier.

A selected handler receives two addresses:

- the first payload byte;
- the address immediately after the payload.

Its result is a 32-bit integer. The auxiliary argument is not supplied to it.

### Preconditions and storage overlap

Ordinary execution requires:

- A cursor slot readable at entry and writable when the final store occurs.
- Accessible input bytes for every read actually performed.
- Address comparisons and additions compatible with the nonwrapping, same-region boundary interpretation described here.
- For a nonnull dispatch table, readable entries through a terminator or an earlier selected match.

The function does not establish that these storage regions are disjoint. The cursor slot may overlap input storage or dispatch-table storage. Such overlap must be accounted for when determining the effect of the final four-byte cursor store; it is not independently rejected.

The body does not validate arbitrary pointer accessibility, table termination, handler validity, or arithmetic wraparound. Failures involving those conditions are not established as recoverable status-8 errors.

## Behavior

### Count acquisition

The function first reads the initial input address from the cursor slot.

Before reading the count, it checks whether the address immediately after the initial input address exceeds the boundary. Equality is accepted: exactly one available byte is sufficient.

If the count byte is unavailable:

- F-4457a9a44a68 is called with a fixed diagnostic argument.
- If that call returns normally, status 8 is selected.
- The original input address is stored in the cursor slot before return.

If the count is available, it is read as an unsigned byte and used as a 32-bit loop quantity. The first record starts immediately after the count byte.

A zero count succeeds without examining a record header or searching the dispatch table. The final cursor is immediately after the count byte, even when additional input remains.

Subsequent modification of the count byte does not change the acquired record count.

### Record-header validation

For each declared record, the function checks whether the complete two-byte header fits within the boundary.

A header ending exactly at the boundary is accepted. A header extending beyond the boundary causes a structural error before either header byte is read for record interpretation.

On an incomplete header:

- F-4457a9a44a68 is called.
- Status 8 is selected if it returns normally.
- The final cursor identifies the start of that record’s header.

A single remaining header byte does not cause the cursor to advance by one.

### Payload extent and validation

For an available header, the represented evaluation reads the identifier byte before the payload-length byte.

The payload starts immediately after the header. Its end is calculated by adding the unsigned payload length to that start address. The length is at most 255; the address calculation remains subject to the nonwrapping interpretation required above.

A payload ending exactly at the boundary is accepted. A payload ending beyond it causes a structural error.

On an incomplete payload:

- F-4457a9a44a68 is called.
- Status 8 is selected if it returns normally.
- The final cursor identifies the payload start, not the header start or the input boundary.
- No handler is invoked for that record.

The parser does not inspect payload contents to establish structural validity. It checks the calculated extent.

### Handler selection

Dispatch begins only after the complete record extent has been accepted.

A null table skips dispatch. Otherwise, searching starts at the beginning of the table for each record. Entries are considered in ascending eight-byte strides:

- A zero handler word ends the search without a call.
- A nonzero handler word permits comparison of the entry identifier with the record identifier.
- The first matching entry supplies the handler.
- Reaching the terminator without a match causes the record to be ignored.

Unknown identifiers are not errors. Later duplicate entries are not considered after a match, including when the selected handler returns zero.

A zero-length payload is valid. Its handler receives equal start and end addresses.

### Handler results and continuation

If the selected handler returns zero, processing continues at the previously calculated payload end.

If it returns nonzero:

- No further record is processed.
- Its 32-bit result is returned without translation.
- The final cursor identifies the current payload start.
- This path does not itself call F-4457a9a44a68.

A handler result of 8 is therefore numerically indistinguishable from the structural-error status, but its diagnostic activity and stopping position can differ.

For an ignored record, continuation also begins at the validated payload end. Every successfully consumed record advances by at least two bytes, including an empty record.

After all declared records are consumed, the result is zero and the final cursor identifies the address immediately after the last payload. For zero records, it instead identifies the address immediately after the count.

### Mutation and saved state

The current record’s calculated payload end is retained across a handler call. Changing that record’s length byte during the call does not cause the parser to recalculate its continuation address.

Later record headers and later table searches read their relevant storage when reached. Handler changes to that storage can therefore affect subsequent parsing, provided the storage remains valid.

The function does not reread the cursor slot to obtain its continuation position. A handler that can reach and modify the slot does not thereby redirect the saved parsing position. The final store overwrites the slot on an ordinary return.

That final store can itself alter input or table bytes if the slot overlaps either region. It occurs after the parsing and dispatch work leading to the return; there is no subsequent parser read that reinterprets those overwritten bytes during this invocation. The changed bytes can nevertheless be visible to the caller or to later operations.

No preservation of unrelated state or memory by dependencies is established.

## Side effects

- An initial 32-bit read of the cursor slot.
- A count-byte read when the initial boundary check permits it.
- Identifier and length reads for complete headers.
- Dispatch-table reads when dispatch is enabled.
- Indirect calls to selected handlers.
- A call to F-4457a9a44a68 on detected structural errors.
- A final 32-bit store of the stopping address to the cursor slot on each ordinary return.

The function has no separate input or dispatch-table write operation. However, the final cursor-slot store can directly modify either region through overlap. Consequently, input and table contents are not unconditionally preserved, even with a null table or handlers that perform no writes.

The visible body does not directly allocate, free, or copy payload storage. It does not read payload contents for validation. If the cursor slot lies within payload storage, its initial read and final write nevertheless access that storage in the slot’s role.

The final store follows a returning diagnostic call or a returning handler failure. If a dependency does not return normally, the evidence does not establish that the store occurs.
