# F-07788537820e

## Purpose

F-07788537820e checks a request-selected byte marker and, if that marker is nonzero, clears a selected marker before performing one of three operations:

- Complete a pending byte transfer into context-associated storage.
- Increment a byte counter and conditionally set a notification and rearm a marker.
- Produce a 32-bit result from a masked table entry or dependency F-c839d081f221.

The function returns a separate 32-bit status. Acceptance of a marker does not guarantee success, and failures do not generally restore the cleared marker.

“Pending transfer,” “notification,” and “rearming” describe inferred roles. The concrete accesses and branch conditions below are established by the supplied static representation; an external protocol is not established.

Global base values are not uniformly snapshotted. Some accesses use retained addresses, while others reread global base storage. Consequently, references described as belonging to one table or record can address different storage if those bases change.

## Interface

### Arguments and return

The function accepts:

| Argument | Established use |
|---|---|
| Context address | A 32-bit address-like value identifying context fields |
| Request | An unsigned 32-bit word |
| Output address | An address used for 32-bit result writes |

The return value is a 32-bit pattern:

| Pattern | Conditions |
|---|---|
| `0x00000000` | Successful transfer completion, special-counter handling, or ordinary result production |
| `0xFFFFFFFD` | Selected availability byte is zero, or the saved pending count equals `0xFFFFFFFF` |
| `0xFFFFFFFF` | Insufficient transfer capacity, zero destination, or nonzero post-copy status |

The two error patterns correspond to −3 and −1 when interpreted as signed 32-bit integers. A named error enumeration is not established.

The output word is independent of the return status. Immediate marker rejection does not explicitly write it. Transfer processing first writes zero to it, including transfer paths that subsequently fail. Ordinary result production can write any dependency-returned 32-bit pattern while the function itself returns zero.

### Storage layout

Offsets below are byte offsets. These labels describe roles, not exported identifiers.

| Storage | Accessed layout |
|---|---|
| Marker table A | Byte entries indexed from 0 through 127 |
| Marker table B | Byte entries indexed from 0 through 127 |

The result-table stride does not establish the contents or meaning of the intervening bytes.

### Preconditions and ownership

Every reached access requires suitable readable or writable storage. In particular:

- The table-A global base location is read even when table B is selected or the marker check fails.
- The selected table’s global base location must support the separate reads used for checking and clearing.
- Accepted-marker paths read the shared-record global base location.
- Each actual output write requires a writable 32-bit output location.
- Transfer copying requires valid source and destination accesses for the iterations actually performed.
- Delegated execution additionally requires F-c839d081f221’s unknown preconditions.

There is no general address validation or enforced disjointness. Aliases can cause an earlier write to affect a later field or global-base read. Ordinary examples assume nonoverlapping storage and stable external state unless stated otherwise.

No allocation, release, or ownership transfer is directly visible in this function. Such effects cannot be excluded inside the dependency.

## Behavior

### 1. Capture the rearming base and check availability

Before checking availability, the function reads and retains the current base of marker table A. This retained address is used only for possible later rearming; it is not the address source for the availability check or its subsequent clear.

The marker index is the request’s low seven bits, ranging from 0 through 127. Request bit 7 selects the table:

- Clear: table B.
- Set: table A.

Higher bits do not affect table selection or index.

The function reads the selected table’s current global base and reads the byte at that base plus the index. If the byte is zero, it returns `0xFFFFFFFD`, without an explicit output or context write. The entry snapshot of table A has nevertheless already occurred.

For a nonzero byte, the function separately reads the selected table’s global base again and writes zero at that base plus the index. Any nonzero byte passes the availability check.

Under a stable selected-table base, this clears the byte that was checked. If the base changes between the two accesses, the clear can target a different table instance or memory region. The retained table-A base is not substituted for either access, even when table A is selected.

There is no general rollback of this clear.

### 2. Snapshot the shared-record base

After the marker clear, and before branching on whether the index is zero, the function reads and retains the current shared-record base.

This snapshot occurs on every accepted-marker path. It supplies the addresses for:

- The transfer source-address read.
- The post-copy status-byte read.
- The special-path target-counter read.
- The special-path notification write.

It does **not** supply the addresses for:

- The pending-count read.
- Pending-count invalidation.
- The special-request-byte comparison.

Those three operations independently reread the global shared-record base when reached. In particular, the pending-count read and invalidation use separate base reads.

A marker clear that aliases global base storage can therefore affect the subsequent shared-record snapshot. Later changes to that global base do not alter the retained address.

### 3. Exact request zero: pending-transfer processing

Only request `0x00000000` selects this path. A nonzero request with index zero takes the separate path described below.

After the shared-record snapshot, the function:

1. Rereads the global shared-record base and reads the 32-bit pending count at `+0x10`.
2. Rereads the global shared-record base again and writes `0xFFFFFFFF` at `+0x10`.
3. Writes zero to the output word.
4. Checks whether the saved count equals `0xFFFFFFFF`.

Thus, the count read and the invalidation can address different records. Neither is required to address the retained record used later for source and status accesses.

If the saved count is the sentinel, the function returns `0xFFFFFFFD`. It does not explicitly modify context capacity or destination on this path. The invalidation and output-zero write have already occurred.

#### Capacity and destination admission

For a nonsentinel count, the function reads context capacity and compares it with the saved count as **unsigned 32-bit values**.

If capacity is smaller, it:

- Writes zero to the context destination.
- Writes zero to context capacity.
- Returns `0xFFFFFFFF`.

No source-address read or byte copy is performed on that branch.

If capacity is sufficient, the function reads the context destination. If it is zero, the function writes zero to capacity and returns `0xFFFFFFFF`, without a copy. A zero destination is rejected even when the saved count is zero. This branch does not separately rewrite the destination field.

#### Source selection and copying

With sufficient capacity and a nonzero destination, the function reads the source address at `+0x14` from the **retained shared-record base**. That read occurs even if the loop will perform no iterations.

Loop continuation interprets the saved count as a signed 32-bit integer:

| Saved count | Iterations |
|---|---|
| `0x00000000` through `0x7FFFFFFF` | The count’s numeric value |
| `0x80000000` through `0xFFFFFFFE` | Zero |
| `0xFFFFFFFF` | Already rejected as the sentinel |

Each iteration has this access order:

1. Read the current destination address from context `+0xA4`.
2. Read one byte through the locally held source address.
3. Write the destination address advanced by one byte back to context `+0xA4`.
4. Write the source byte to the destination address read in step 1.
5. Advance the locally held source address by one byte.

The destination field is reread each iteration. Source advancement is local; the function does not write the advanced source address back to the shared record.

This is a forward byte copy, not an established overlap-safe move. The destination-address update precedes the byte store, so copying into the destination field itself can affect subsequent destination reads.

#### Post-copy outcome

After the loop, including a zero-iteration loop, the function reads the status byte at `+0x02` using the retained shared-record base.

If that byte is nonzero, it returns `0xFFFFFFFF`. There is no explicit capacity reset, destination reset, or copy rollback on this branch. Under nonaliasing, stable-state conditions, output remains zero and destination remains advanced by the number of iterations.

If the status byte is zero, the function:

1. Rereads context capacity.
2. Writes that capacity minus the saved count to output, with a 32-bit result.
3. Writes zero to the context destination.
4. Writes zero to context capacity.
5. Returns zero.

The subtraction produces the low 32 bits of the difference. The capacity used for this result is the completion-time read, not necessarily the admission-time value.

### 4. Nonzero request with index zero

For every nonzero request whose low seven bits are zero, the function:

1. Writes `0xFFFFFFFF` to context `+0x80`.
2. Selects `0x0000007F` as the result mask.
3. Continues to ordinary result production.

It does not inspect or invalidate the pending count and does not perform the special-request comparison.

With bit 7 clear, it uses the index-zero result-table word masked with `0x7F`. With bit 7 set, it delegates; the selected mask is not applied to the dependency result.

The shared-record base snapshot described earlier still occurs, although this path does not subsequently use it for a record-field access.

### 5. Nonzero index: special-request handling

For a nonzero index, the function first reads the shared 32-bit mask. It then rereads the global shared-record base and reads the special-request byte at `+0x09`.

The entire unsigned 32-bit request is compared with that byte’s value, promoted to the range 0 through 255. Requests above 255 cannot match.

On a match, the function:

1. Writes zero to output.
2. Reads the context counter byte at `+0x84`.
3. Increments it with byte-width wraparound and writes the updated byte back.
4. Reads the target-counter byte at `+0x08` using the retained shared-record base.
5. Compares the updated counter with that target.

The record supplying the special-request byte can differ from the retained record supplying the target.

If the bytes match, the function returns zero without explicitly writing notification or rearming a marker.

If they differ, it:

1. Writes one to notification at retained shared-record base `+0x03`.
2. Writes one at the selected index using the **table-A base retained before availability checking**.
3. Returns zero.

Rearming always targets the entry snapshot of table A. It can therefore differ both from the table originally selected and from a later current table-A base. Existing notification or marker values are not explicitly cleared on the matching-counter branch.

### 6. Ordinary result production

This stage is reached by a nonzero index-zero request or a nonzero-index request that fails the special-request comparison.

With bit 7 clear, the function reads the 32-bit result-table word at the index’s 32-byte stride and applies:

- `0x0000007F` for index zero.
- The previously read shared mask for a nonzero index.

With bit 7 set, it calls F-c839d081f221 with the context address, the seven-bit index, and a zero-valued third argument. Its 32-bit return value becomes the result without masking or status interpretation.

After obtaining the result, the function writes it to output and returns zero. A dependency result of `0xFFFFFFFF` or `0xFFFFFFFD` remains output data, not this function’s return status.

## Side effects

Directly visible writes are path-dependent:

- Clear a marker using a fresh selected-table base read.
- Invalidate a pending-count field using a fresh shared-record base read.
- Write the output word.
- Update or clear context transfer fields.
- Copy source bytes into destination storage.
- Set context `+0x80` to `0xFFFFFFFF`.
- Increment the context counter byte.
- Set notification through the retained shared-record base.
- Rearm a marker through the entry table-A snapshot.

Except for immediate marker rejection, each normal-return path explicitly writes output at least once. This does not guarantee that output retains that value under aliasing or dependency mutation.

No locking, atomic operation, allocation, deallocation, or source clearing is directly visible. The access ordering describes the supplied static representation, not a synchronization guarantee. Invalid accesses have no established normal return or rollback behavior.

## Acceptance examples

These are conditional static predictions, not executed tests. Unless specified otherwise, assume valid nonoverlapping storage, stable bases and field values, accepted markers, and normal dependency return.

1. **Unavailable marker.**  
   If the checked byte is zero, return `0xFFFFFFFD` without an explicit output write. The table-A base snapshot and selected-table base read have already occurred; no shared-record snapshot occurs.

2. **Check and clear use different bases.**  
   Request 5 checks a nonzero byte in one table-B instance. If the global table-B base changes before the clear’s separate base read, the function clears index 5 in the new instance. It need not clear the byte it checked.

3. **Masked result.**  
   For request 5, a nonmatching special-request byte, result word `0xA5A55A5A`, and mask `0x00FF00FF`, output is `0x00A5005A`; return is zero.

4. **Full request comparison.**  
   Request `0x00000105` selects table B, index 5, but cannot equal a byte-valued special request. It takes ordinary result production.

5. **Successful transfer.**  
   For exact request zero, count 3, capacity 8, nonzero destination, source bytes `11 22 33`, and zero status, copy those bytes, output 5, clear destination and capacity, and return zero. Pending-count invalidation precedes copying.

6. **Distinct shared records.**  
   Suppose the post-clear snapshot retains record R. The count-read base then supplies record S with count 3, and the invalidation base supplies record T. With no relevant aliases, the function invalidates T’s pending count, uses R’s source address and status, and does not explicitly invalidate S’s pending count.

7. **Sentinel count.**  
   A saved count of `0xFFFFFFFF` causes output zero and return `0xFFFFFFFD`, after the separately addressed invalidation. Context transfer fields are not explicitly cleared.

8. **Insufficient capacity.**  
   Count 9 and capacity 8 produce no copy, clear destination then capacity, and return `0xFFFFFFFF` with output zero.

9. **Zero destination with zero count.**  
   Count zero does not bypass destination validation. A zero destination causes failure and capacity clearing, rather than successful zero-byte completion.

10. **Post-copy failure.**  
    Count 3, capacity 8, valid destination, and nonzero retained-record status produce three copied bytes before failure. Output remains zero, capacity remains 8, and destination remains advanced by three under the stated assumptions.

11. **Unsigned admission, signed loop.**  
    Count `0x80000000`, capacity `0x80000005`, nonzero destination, and zero status produce no byte copies. The source-address field is still read. Output is 5, transfer fields are cleared, and return is zero.

12. **Special comparison and target use different records.**  
    The retained record’s target is 9, while a later global base supplies a special-request byte equal to request 5. Starting from counter 7, the function outputs zero, increments to 8, and writes notification through the retained record because 8 differs from 9.

13. **Rearm uses the entry snapshot.**  
    If request 5 takes the mismatching-counter branch, rearming writes index 5 through the table-A base captured before availability checking. A later change to the global table-A base does not redirect this write. The consumed table-B marker is not restored.

14. **Counter wrap reaches target.**  
    A matching special request with counter `0xFF` and retained-record target zero increments to zero and returns successfully without explicitly setting notification or rearming.

15. **Nonzero request, zero index.**  
    Request `0x00000100` clears the selected table-B marker, snapshots the shared-record base, writes `0xFFFFFFFF` to context `+0x80`, and outputs the index-zero result word masked with `0x7F`. It does not process a pending transfer.

16. **Dependency result is data.**  
    If a delegated path receives `0xFFFFFFFF` from F-c839d081f221 normally, it writes that pattern to output and returns zero.
