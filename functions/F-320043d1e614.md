# F-320043d1e614

## Purpose

F-320043d1e614 updates a destination reference slot from a source reference slot, except when both arguments identify the same slot. For distinct slots, it first invokes a dependency on the destination, copies the source’s current reference value into the destination, and, if that value is nonzero, increments a field in the referenced object. Two conditional dependency calls surround that increment.

The structure is consistent with reference assignment involving destination cleanup and shared-object reference accounting. That interpretation is inferred intent, not an established contract for the dependencies. In particular, the supplied evidence does not establish that any dependency releases memory, acquires a lock, releases a lock, or preserves unrelated state.

The function returns the original destination-slot address on every normally returning path. It has no explicit error result.

## Interface

**Inputs**

- **Destination slot:** An address identifying a writable reference slot.
- **Source slot:** An address identifying a readable reference slot.

The equality comparison concerns the slot addresses, not their contents. Two different slots containing the same object reference do not qualify for the self-assignment shortcut.

**Output**

- The original destination-slot address.
- No independently owned object or newly allocated storage is explicitly returned.

**Representation and widths**

The supplied representation uses integer-sized slot contents as object references and accesses integer-sized fields at byte offsets 4 and 8 from a nonzero reference value. The apparent target model is a 32-bit reference word and 32-bit integer fields:

| Location | Observed role |
| --- | --- |
| Destination slot, offset 0 | Reference value written during assignment |
| Source slot, offset 0 | Reference value read during assignment |
| Referenced object, byte offset 4 | Integer field incremented by one |
| Referenced object, byte offset 8 | Integer field tested against zero twice |

These widths reflect the apparent source model rather than independently supplied ABI documentation. A strict portability claim about the width of an integer or the conversion between an integer and an address is **documented_only**.

No access to the referenced object’s offset-0 field is established. The offsets above do not establish a complete object layout, object size, field names, or ownership model.

**Validity preconditions**

For a non-self assignment to complete normally:

- The destination must satisfy the requirements of F-81c78ba89c2e and remain suitable for the subsequent slot write.
- The source must be readable when the source read actually occurs, after that dependency returns.
- Any nonzero reference obtained from the source must support the object-field accesses described below.
- The offset-4 field must be readable and writable when the increment occurs.
- The offset-8 field must be readable at each of its two separate tests.
- The dependency calls must return normally if execution is to reach the function’s normal return.

The wrapper does not validate these conditions.

For equal slot addresses, the wrapper does not dereference either argument or invoke a dependency. Equality therefore selects a materially different access path; it is not merely an optimization after validation.

## Behavior

### Self-assignment

If the destination and source slot addresses compare equal, the function returns the destination address immediately.

On this path, the wrapper:

- Does not read the slot contents.
- Does not write the slot contents.
- Does not inspect any referenced object.
- Does not invoke any dependency.
- Does not increment any field.

This remains true even when the slot would contain a nonzero reference. Equality of the two slot addresses is the sole condition for this shortcut.

### Distinct-slot assignment

For different slot addresses, the following order is established by the supplied static evidence.

1. **Invoke the destination dependency.**  
   F-81c78ba89c2e receives the destination-slot address. This invocation precedes the source read.

2. **Read the source reference.**  
   After the dependency returns, the function reads the integer-sized value currently stored in the source slot.

3. **Write the destination reference.**  
   The value just read is written into the destination slot.

4. **Handle the copied reference if nonzero.**  
   A zero value skips all direct object-field accesses and both conditional dependencies. A nonzero value selects the object-accounting sequence described below.

5. **Return the destination-slot address.**  
   Normal completion returns the original destination address, not the copied reference value.

The read-after-dependency order is significant. The function does not take a source snapshot before invoking F-81c78ba89c2e. If that dependency changes the source slot through an alias or other reachable state, the subsequently read value is the changed value.

The destination overwrite occurs before either offset-8 test and before the offset-4 increment. The wrapper does not defer publication of the new reference until accounting finishes.

### Nonzero copied reference

The object selected for subsequent direct field accesses is the nonzero reference captured from the source read. Those accesses do not reload the object reference from the destination slot.

The sequence is:

1. Read the integer field at byte offset 8 from the captured object address.
2. If that value is nonzero, invoke F-338d16f9ce72.
3. Read the integer field at byte offset 4 from the captured object address.
4. Add one and write the result back to that same field.
5. Read the integer field at byte offset 8 again.
6. If this second value is nonzero, invoke F-1333331b2da1.

The two offset-8 tests are separate reads. The second decision is not cached from the first. Consequently, the two conditional calls need not occur as a pair.

For example:

- A nonzero first read and a zero second read cause only F-338d16f9ce72 to be called.
- A zero first read and a nonzero second read cause only F-1333331b2da1 to be called.
- Two nonzero reads cause both calls, in the stated order.
- Two zero reads cause neither call.

These combinations describe the wrapper’s branching behavior. They do not establish that external mutation or dependency behavior making each combination possible is valid under the larger program’s protocol.

The offset-4 read occurs after F-338d16f9ce72 returns, when that call is selected. If the dependency changes the field, the increment uses the field value observed afterward. Likewise, if a dependency changes the destination slot, the remaining direct field accesses still target the captured object address.

### Arithmetic

The directly expressed accounting operation is an integer increment by one, implemented as a read followed by a write. The evidence does not show an atomic increment primitive, a saturation check, a maximum-value check, or an overflow error path.

Under the apparent signed 32-bit interpretation, an initial offset-4 value of 2,147,483,646 can be incremented to 2,147,483,647 without exceeding the representable range. An initial value of 2,147,483,647 reaches the arithmetic boundary.

Behavior at that boundary is **documented_only**. The supplied source representation does not independently establish whether the executable wraps, follows a source-language overflow rule, or relies on a precondition excluding overflow. A behavioral contract must not silently choose modulo arithmetic.

There is no explicit rejection of negative offset-4 values. Where the increment is representable, the direct operation adds one regardless of the value’s inferred accounting meaning.

## Side effects

The wrapper’s established direct writes are:

- One destination-slot write on every distinct-slot path that reaches the write.
- One offset-4 object-field write when the copied reference is nonzero and execution reaches the increment.

The wrapper does not directly write the offset-8 field. Its value can nevertheless differ between reads because dependency effects and other permitted mutations are not specified here.

Additional side effects may arise from:

- F-81c78ba89c2e on every distinct-slot path.
- F-338d16f9ce72 when the first offset-8 test is nonzero.
- F-1333331b2da1 when the second offset-8 test is nonzero.

There is no explicit allocation or deallocation in the wrapper. No ownership transfer, retain guarantee, or release guarantee can be assigned to a dependency merely from its placement.

The wrapper provides no explicit rollback. If execution fails after the destination write, the supplied evidence contains no recovery step restoring the prior destination value. Similarly, no compensating decrement is shown if execution stops after the offset-4 increment.

The wrapper contains no explicit synchronization operation beyond the two opaque conditional calls. Their placement alone does not establish thread safety, mutual exclusion, atomicity, or a memory-ordering guarantee.

Because dependency effects are unspecified, normal return alone does not prove that the destination still contains the copied reference or that the incremented field still has the directly written value. Later dependency effects could alter either. Such postconditions require additional dependency contracts.

## Acceptance examples

The following are conditional acceptance examples derived from static evidence. They are not reports of executed tests.

### Equal slot addresses

Given identical destination and source addresses, the function must return that address without any dependency invocation or wrapper memory access.

This example distinguishes address equality from equality of stored references.

### Distinct slots with a zero source value

Given distinct valid slots, and assuming F-81c78ba89c2e returns normally and the subsequent source read yields zero:

- F-81c78ba89c2e must be invoked first.
- Zero must be written to the destination.
- No direct object-field access may follow.
- Neither conditional dependency may be invoked.
- Normal return must yield the destination address.

### Nonzero reference with both condition reads zero

Assume the source read yields a valid nonzero object reference, the offset-4 value is 7, both offset-8 reads yield zero, and no intervening effects alter the relevant fields.

The destination must be written with the captured reference. The offset-4 field must then be written as 8. Neither conditional dependency is invoked.

### Nonzero reference with both condition reads nonzero

Assume both offset-8 reads yield nonzero values and all accesses and calls complete normally.

The observable order must include:

- Destination dependency.
- Source read.
- Destination write.
- First offset-8 read.
- F-338d16f9ce72.
- Offset-4 read and increment write.
- Second offset-8 read.
- F-1333331b2da1.

The increment must use the offset-4 value read after the first conditional dependency returns.

### Source mutation during the destination dependency

Assume the source initially contains one reference, but F-81c78ba89c2e changes that slot to a different reference before returning.

The wrapper must copy the later value. An implementation that copies the initial value by reading the source before the dependency would violate the established order.

### Changed condition between tests

Assume the first offset-8 read is nonzero and F-338d16f9ce72 changes that field to zero, with no later change before the second read.

The first conditional dependency is invoked, the increment occurs, and F-1333331b2da1 is not invoked. Reusing the first test result would not match the supplied behavior.

### Different slots containing the same reference

Assume the slot addresses differ but their initial stored values are equal.

The destination dependency must still be invoked. There is no stored-value equality shortcut. Whether that dependency preserves the referenced object’s validity is an external precondition, not a guarantee established by this wrapper.

## Uncertainties

The following remain **documented_only**:

- Exact ABI widths and integer-to-address interpretation.
- Complete object layout, alignment requirements, and allocation size.
- Whether offset 4 is a reference count and offset 8 is a synchronization flag.
- Whether F-81c78ba89c2e releases, clears, destroys, or otherwise modifies the destination or its prior referent.
- Whether the conditional dependencies implement synchronization.
- Dependency effects on globals, slots, object fields, lifetime, or ownership.
- Arithmetic behavior when the increment exceeds the representable range.
- Validity of unusual aliasing among slots and object fields.
- Concurrent access rules and data-race behavior.
- Failure behavior for invalid addresses or non-returning dependencies.

Inferred intent is reference assignment with conditional protection around shared accounting. That interpretation does not resolve these unknowns or strengthen the established postconditions.
