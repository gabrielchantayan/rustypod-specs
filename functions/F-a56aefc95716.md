# F-a56aefc95716

## Purpose

F-a56aefc95716 derives two endpoints from a pointer-linked structure, counts advancement steps between those endpoints using opaque iterator helpers, and passes copies of the resulting endpoint state to a final operation.

The established return value is the number of advancement calls made before the endpoint-check helper returns exactly one. It is not independently established as the number of nodes removed, elements matched, or objects released.

The paired searches and final operation suggest a range-oriented container operation. That interpretation is inferred intent, not a substitute for the observable branch rules. In particular, both searches sometimes retain a selected **child pointer**, rather than the address of the node being compared.

## Interface

### Inputs

The function receives two arguments:

- **Object address:** an integer-valued address used to access a structure and to form an embedded comparison-context address.
- **Search argument:** an opaque 32-bit value passed unchanged to comparison calls. Its type is not established. It may encode an address or another representation expected by the comparison dependency.

The supplied representation uses 32-bit integer fields for addresses, links, iterator words, endpoints, and the returned count. No 64-bit address or count behavior is established.

### Return value

The function returns a 32-bit integer count, initially zero and incremented once for each endpoint check whose result is not exactly one.

The result of the final dependency call is ignored. There is no separate success flag or error return.

The context address at object offset `0x19` need not be word-aligned. This function passes that address to the comparison dependency; it does not directly perform a word-sized access there.

A zero node address terminates a search. A zero header address is not treated as an empty structure: the function attempts to read the root field through that address.

## Behavior

### First endpoint search

The function first reads the object’s header address and then the root address at header offset `0x04`. It separately reads the object’s header address again to initialize the first endpoint candidate.

These are distinct reads. The candidate is not necessarily the header address used for the preceding root read if intervening activity changes the object.

For each nonzero current node, the function calls F-a1e786bd6046 with:

1. The comparison-context address at object offset `0x19`.
2. The current node’s comparison-data address at node offset `0x10`.
3. The unchanged search argument.

The returned value controls the next link read:

- **Exactly zero:** read the link at node offset `0x08`, use it as the next node, and also replace the first endpoint candidate with that link value.
- **Any nonzero value:** read the link at node offset `0x0c` and use it as the next node, without changing the candidate.

The selected link is read after the comparison call. If that call changes the relevant link, the subsequent read observes the changed value.

When the current node becomes zero, the first search ends. The retained candidate may be:

- The separately read header address, if no zero-result branch replaced it.
- A nonzero child address selected by a zero-result branch.
- Zero, if the last candidate update selected a null child.

There is no fallback that replaces a null candidate with the last compared node.

### Second endpoint search

The function starts a new traversal by reading the object’s header address and its root field again. It separately reads the object’s header address to initialize the second endpoint candidate.

Consequently, the second search does not necessarily use the root or header observed by the first search. There is no snapshot or consistency check across the two searches.

For each nonzero current node, the comparison call uses:

1. The same comparison-context address.
2. The search argument.
3. The current node’s comparison-data address.

The last two comparison arguments are reversed relative to the first search.

The returned value controls traversal as follows:

- **Exactly zero:** read the link at node offset `0x0c` and use it as the next node, without changing the second candidate.
- **Any nonzero value:** read the link at node offset `0x08`, use it as the next node, and replace the second candidate with that link value.

Again, the selected link is read only after the comparison returns.

The second candidate can remain the header address, become a nonzero child address, or become zero. No validation establishes that the two candidates are ordered or mutually reachable.

### Traversal-state construction

After the searches, the function prepares a contiguous four-word state block. Its initial contents are:

| Byte offset | Initial 32-bit value |
|---:|---|
| `0x00` | First endpoint candidate |
| `0x04` | Zero |
| `0x08` | Zero |
| `0x0c` | First endpoint candidate |

A separate 32-bit endpoint word initially contains the second endpoint candidate.

The two copies of the first candidate are distinct storage locations. The function does not establish which word is authoritative for the helpers or require them to remain equal.

The count is initialized to zero.

### Endpoint checking and advancement

The function repeatedly calls F-425cd6ff9d42 with:

1. The address of the four-word state block.
2. The address of the separate endpoint word.

Its return value is tested against **exactly one**:

- A return of one ends the loop immediately.
- Every other return value causes the count to increase by one, followed by a call to F-d92e879159c4 with the state-block address.
- After the advancement call returns, the endpoint check repeats.

Thus, a return of two or a negative value is not treated as successful termination merely because it is nonzero.

The count increment occurs before the advancement call. If an advancement call does not return normally, this function does not reach its normal return.

Both helpers receive addresses of mutable storage. The endpoint-check helper may modify the state block or endpoint word; the advancement helper may modify the state block. Their actual mutations are unknown. The function does not restore the initial contents between calls.

No explicit error interpretation is applied to either helper’s result. F-d92e879159c4’s return value, if any, is ignored.

### Final operation and return

After an endpoint check returns one, the function:

1. Copies the current separate endpoint word into another local word.
2. Copies the current fourth word of the state block into another local word.
3. Calls F-9a305cc01ef7 with:
   - An address of a four-byte scratch area.
   - The original object address.
   - The address of the copied fourth state word.
   - The address of the copied endpoint word.
4. Returns the accumulated count.

The copies reflect state **after** the terminating endpoint check, including any changes that check made.

The final dependency receives addresses of copies, not the original state-block word or original endpoint word. Changes made through those argument addresses therefore affect the copies directly.

The scratch area is not explicitly initialized before the call. This function does not subsequently inspect it. The supplied evidence does not establish what the dependency writes there or whether four bytes satisfy its actual output contract.

The final operation is called even when the count is zero.

## Acceptance examples

The following are conditional specification examples, not executed tests.

### Empty roots with immediate termination

Suppose both root reads produce zero, the separately read header addresses are the same value, and no relevant state changes occur.

Both endpoint candidates retain that header address. The four-word state begins with that address in its first and fourth words and zero in its middle words. The separate endpoint word contains the same header address.

If the first endpoint check returns one:

- No comparison calls occur.
- No advancement call occurs.
- The final operation is called once.
- The returned count is zero.

An empty root alone does not guarantee this outcome; termination still depends on the endpoint-check dependency.

### First search selects a null child

Suppose the first search starts at a nonzero node, its comparison returns zero, and the node’s `0x08` link is zero.

The first endpoint candidate becomes zero and the first search ends. The candidate is not replaced by the node address or header address.

### First search preserves the header candidate

Suppose every first-search comparison returns nonzero until a `0x0c` link produces zero.

No candidate update occurs during that search. The first endpoint remains the header address read for candidate initialization.

### Reversed operands affect the second search

Suppose the comparison dependency returns zero for a node-data/search-argument ordering but nonzero for the reversed ordering.

The first search selects the node’s `0x08` link and updates its candidate. The second search also selects `0x08` and updates its candidate, but does so under its nonzero-result rule. The two searches must not be implemented using an identical operand order.

### Nonboolean endpoint result

Suppose successive endpoint checks return two and then one, and all calls return normally.

The function increments the count once, calls the advancement dependency once, then stops. It returns one after the final operation. The initial result of two does not terminate the loop.

### Mutation during the terminating check

Suppose the terminating endpoint check returns one while also changing the separate endpoint word and the fourth state word.

The final dependency receives pointers to copies of those changed values. It does not receive the values that existed before the terminating check.

### Zero-count final operation

Suppose the first endpoint check returns one.

The final operation still occurs. A zero return count does not mean that no dependency-mediated mutation occurred.
