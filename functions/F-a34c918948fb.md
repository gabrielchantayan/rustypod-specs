# F-a34c918948fb

## Purpose

F-a34c918948fb selects one 24-byte record from caller-supplied allocation state and partially initializes it. Selection favors a linked reusable record; otherwise, it consumes the next record in a contiguous region. If that region is exhausted, it obtains a new region and an associated descriptor through F-871e64ddc6de.

The function has no explicit return value and does not directly return the selected record’s address. Its observable results are changes to allocation state, descriptor storage, and the selected record.

The interpretation as a record pool is inferred intent. The established behavior is address selection, conditional allocation, state advancement, and specific byte and word writes. It does not establish that the selected record is fully initialized, that ownership transfers to the caller, or that old storage is released.

The state pointer is not checked for null, alignment, or accessibility. Valid writable storage is a caller precondition.

### Region descriptor

A newly allocated descriptor occupies 12 bytes:

| Byte offset | Width | Observed role |
|---|---:|---|
| 0 | 32 bits | Link to the descriptor head observed after both dependency calls |
| 4 | 32 bits | Capacity in records |
| 8 | 32 bits | Base address of the new record region |

When computing growth, the function reads only the capacity field of an existing head descriptor. It does not traverse the descriptor chain.

| Byte offset | Width | Use |

## Behavior

### Selection precedence

The reusable head is inspected first.

If it is nonzero, the referenced record is selected even if the sequential region is exhausted or has other unusual state. This path does not inspect the descriptor head, sequential cursor, or region end.

If the reusable head is zero, the sequential cursor is selected provisionally and compared with the region end. Only equality triggers region growth. The function does not check whether the cursor is below the end, whether there is room for a whole record, or whether either address is aligned.

After a record has been selected through any path, the same partial initialization is performed.

### Reusing a linked record

For a nonzero reusable head:

1. The address in that field identifies the selected record.
2. A 32-bit successor address is read from the selected record at byte offset 12.
3. That successor replaces the state’s reusable head.
4. The selected record is partially initialized.

The successor is consumed before the offset-12 field is cleared. There is no traversal, validation, or attempt to detect cycles.

On this path, the function directly changes only the reusable-head field and the selected record. It makes no dependency calls and does not directly advance the sequential cursor or change the region end or descriptor head.

These field-level statements assume the state and record storage do not overlap. No aliasing protection exists.

### Consuming an existing sequential region

When the reusable head is zero and the sequential cursor differs from the region end:

- The original cursor identifies the selected record.
- The state’s sequential cursor is advanced by 24 bytes.
- The selected record is partially initialized.

No descriptor is consulted and no dependency call is made.

The inequality check is not a bounds check. A cursor beyond the end is still consumed if the two addresses differ. Safe use requires the caller’s state to ensure that the selected record and its successor cursor are valid for the intended region.

### Growing the region

When the reusable head is zero and the sequential cursor equals the region end, the function computes a new capacity.

If the descriptor head is zero, the new capacity is 32 records.

Otherwise, let \(c\) be the unsigned 32-bit capacity read at byte offset 4 of the current head descriptor. Two unsigned 32-bit candidates are formed:

\[
a = (c + 32) \bmod 2^{32}
\]

\[
b =
\left(
c + \left\lfloor c/2 \right\rfloor
+ \left\lfloor c/8 \right\rfloor
\right) \bmod 2^{32}
\]

The new capacity is the unsigned maximum of \(a\) and \(b\). Equality selects the same numeric result either way.

For ordinary capacities without overflow, the rule chooses between adding 32 records and adding approximately five eighths of the old capacity. That growth interpretation does not supersede the actual wrapped arithmetic.

The function then calls F-871e64ddc6de twice, in this order:

- A request with first argument 12 and second argument zero, whose result is used as descriptor storage.
- A request with first argument equal to the new capacity multiplied by 24, and second argument zero, whose result is used as record-region storage.

The record-region request size is a 32-bit multiplication result. There is no overflow guard.

After both calls return, descriptor publication and cursor setup occur in this order:

1. Store the returned record-region address in the new descriptor’s offset-8 field.
2. Read the state’s descriptor head again and store it in the new descriptor’s offset-0 field.
3. Store the computed capacity in the new descriptor’s offset-4 field.
4. Publish the new descriptor address as the state’s descriptor head.
5. Read the record-region address back from the new descriptor.
6. Set the state’s region end to that address plus the capacity multiplied by 24.
7. Set the state’s sequential cursor to that address plus 24.
8. Partially initialize the first record at that address.

The descriptor head used as the new descriptor’s link is a post-call observation. It is not necessarily the same value used earlier to decide the capacity. The dependency’s implementation is unavailable, so preservation of caller state or globals must not be assumed.

Likewise, the function does not recheck the reusable head after either dependency call.

### Common partial initialization

For the selected record, writes occur in this order:

1. A 32-bit zero at byte offset 4.
2. A 32-bit zero at byte offset 8.
3. A 32-bit zero at byte offset 12.
4. A one-byte zero at byte offset 0.

The first four bytes are not cleared as a unit. Bytes 1–3 remain untouched by these direct writes. Bytes 16–23 are also untouched.

The function does not establish zero-filled payload storage or a completely zeroed record.

### Arithmetic limits

Capacity additions, the shifted-capacity sum, and multiplication by 24 use the recovered unsigned 32-bit arithmetic. Overflow is not rejected.

Consequences include:

- Wrapped growth candidates need not exceed the previous capacity.
- The byte request need not equal the unbounded mathematical product of capacity and 24.
- A wrapped allocation request can be smaller than the nominal record count suggests.
- No check ensures that the requested storage covers even the record subsequently initialized.

Pointer validity at extreme values remains subject to the target’s actual execution semantics. The source provides no checked-address behavior.

## Side effects

### Direct state changes

| Path | Direct state writes |
|---|---|
| Reusable record | Replace reusable head with the selected record’s successor |
| Existing sequential region | Advance sequential cursor by 24 bytes |
| New region | Publish descriptor head; set region end; set sequential cursor |

Every path also performs the four record-initialization writes.

The new-region path directly initializes all three fields of the new descriptor. It contains no release operation, descriptor-chain traversal, or clearing of the rest of the record region.

### Ownership and lifetime

The previous descriptor head is linked into the newly allocated descriptor rather than explicitly discarded. This supports an inferred intent to retain older regions.

Ownership rules are not established. In particular:

- No release dependency is invoked by this function.
- There is no evidence that the caller receives ownership of the selected record.
- There is no evidence that F-871e64ddc6de returns fresh, disjoint, or zero-filled storage.
- No cleanup is attempted if the second dependency call fails after the first succeeds.
- Eventual reclamation of descriptors and record regions is outside the supplied evidence.

### Visibility and concurrency

State changes occur before the selected record’s clearing writes. On the growth path, the new descriptor is published before the new region end and cursor are written.

No locking, atomic operations, or synchronization protocol appears in the supplied body. Concurrent use cannot be considered safe from this evidence. The specified order is the order represented by the supplied body, not a cross-thread visibility guarantee.

## Acceptance examples

These examples are conditional consequences of the static evidence, not reports of executed tests. Unless stated otherwise, they assume accessible, suitably aligned, nonoverlapping storage, no arithmetic overflow, and dependency behavior that does not unexpectedly alter the relevant state.

### Reuse takes precedence

Given a nonzero reusable head whose offset-12 successor is a second record:

- The first record is selected.
- The reusable head becomes the second record’s address.
- No region allocation occurs.
- The sequential cursor, region end, and descriptor head receive no direct writes.
- The selected record’s offsets 4, 8, and 12 become zero words, and offset 0 becomes a zero byte.

This remains the selected path even if the sequential cursor equals the region end.

### Sequential consumption preserves untouched bytes

Given no reusable record and a cursor identifying a valid 24-byte record before a distinct region end:

- No dependency call occurs.
- The cursor advances by 24 bytes.
- The four specified clearing writes occur.
- Nonzero bytes initially present at offsets 1–3 or 16–23 remain unchanged by this function’s direct writes.

### First region

Given no reusable record, equal cursor and end, and a zero descriptor head:

- Capacity is 32.
- Dependency requests are 12 bytes followed by 768 bytes, each with second argument zero.
- If the head remains zero during the calls, the new descriptor’s link is zero.
- The region end is the returned region base plus 768.
- The sequential cursor is the returned region base plus 24.
- The first record receives partial initialization.

### Growth examples

With the growth path selected and an existing capacity of 32:

- The candidates are 64 and 52.
- Capacity becomes 64.
- The record-region request is 1,536 bytes.

With an existing capacity of 128:

- The candidates are 160 and 208.
- Capacity becomes 208.
- The record-region request is 4,992 bytes.

An existing descriptor whose capacity is zero is distinct from having no descriptor, but both produce capacity 32.

### Head changes during a dependency call

Suppose growth capacity is computed from one descriptor, but F-871e64ddc6de changes the state’s descriptor head before the final descriptor writes.

The new descriptor must link to the head read after both calls, while retaining the capacity computed before those calls. Linking to the earlier head instead would not match the supplied behavior.

### Malformed cursor ordering

Given no reusable record and a cursor numerically beyond, but unequal to, the region end, the function does not trigger growth solely because of that ordering. It attempts sequential consumption.

This is not an acceptance of memory safety for that input; it identifies the absence of a bounds check.
