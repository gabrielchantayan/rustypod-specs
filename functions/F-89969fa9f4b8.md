# F-89969fa9f4b8

## Purpose

F-89969fa9f4b8 conditionally constructs a small request in temporary storage and passes it to F-be41255119f8. It admits the request only when the supplied object pointer is non-null, the object’s leading 32-bit value matches a reference value, and another 32-bit object field is nonzero.

On rejection, it returns the 32-bit value `7` without calling the dependency. On admission, it returns the dependency’s 32-bit result without translating it.

The constructed request combines the complete second argument, a fixed marker, the third argument, the low eight bits of the second argument, and a bitwise-modified byte drawn from the object.

This is a source-facing static contract. It describes the behavior established by the supplied representation, identifies layout assumptions, and does not attribute undocumented behavior to the dependency.

## Interface

| Input | Width and role | Requirements |
|---|---|---|
| Object pointer | Pointer to an object accessed through 32-bit integer fields | May be null. If non-null, the fields actually reached by validation and construction must be readable. |
| Value argument | 32-bit uninterpreted value | All 32 bits are preserved in the first request word. Its low eight bits are also used in the second request word. |
| Byte argument | 8-bit uninterpreted value | Used unchanged in the least significant byte of the second request word. |

The established object accesses use the following layout:

| Byte offset | Access width | Role |
|---|---|---|
| `0` | 32 bits | Compared for equality with a reference value. |
| `12` | 32 bits | Its low eight bits contribute to the third request word. |

These offsets follow the supplied representation’s 32-bit integer indexing. They are not evidence that the complete object is exactly 72 bytes long or that all intervening bytes are meaningful fields.

A non-null pointer is not sufficient for safety. The function does not independently establish allocation size, alignment, accessibility, lifetime, or object provenance. The matching leading value is a validation condition, not proof that subsequent memory accesses are valid.

### Output

The result is a 32-bit value:

- `7` when any admission condition fails.
- The exact 32-bit result of F-be41255119f8 when all admission conditions pass.

No separate success value is established. A result of `7` does not, by itself, prove that validation failed: the dependency may also return that value.

### Temporary request representation

The supplied representation places three 32-bit words in successive temporary stack locations and passes a pointer to the first word. The resulting candidate request extent is 12 bytes.

The logical words, in order, are:

| Word | Logical 32-bit value |
|---|---|
| First | The complete value argument. |
| Second | The low eight bits of the value argument in bits 16–23, `0x03` in bits 8–15, and the byte argument in bits 0–7. Bits 24–31 are zero. |
| Third | `0xEF` in bits 24–31; the bitwise OR of `0xA0` and the low eight bits of the object field at offset `12` in bits 16–23; zero in bits 0–15. |

The logical word values are established by the construction. Their byte order in memory depends on target endianness. The adjacent temporary locations support the 12-byte layout, but the dependency’s actual read extent is not supplied.

## Behavior

### Admission and observable read order

Admission is short-circuited:

1. The object pointer is checked for null.
2. Only for a non-null pointer is the leading object value compared with the reference value.
3. Only after that comparison succeeds is the 32-bit field at offset `68` read and checked for nonzero.
4. Only after all admission conditions succeed is the field at offset `12` read for request construction.

Consequently:

- A null pointer causes rejection without an object dereference.
- A mismatching leading value prevents this function from reading offsets `68` and `12`.
- A matching leading value with a zero field at offset `68` prevents the read at offset `12`.
- A nonzero field at offset `68` admits construction regardless of that field’s sign or individual bit pattern.

The reference value is read for the leading-value comparison. Its numeric value and lifecycle are not established. The representation does not establish the relative machine-level order of the object-tag read and the reference-value read within that comparison.

No locking, atomic snapshot, or retry is visible. The admission fields and construction field are separate accesses. No coherent cross-field snapshot is guaranteed if another execution context modifies the object or reference value.

### Rejection

If admission fails, the function returns `7`.

This path does not call F-be41255119f8 and does not construct the successful-path request. No caller-memory write or ownership action is visible on this path.

Invalid memory access is not an admission failure that the function explicitly converts to `7`. A non-null but unreadable pointer may fault before a rejection result can be produced.

### Request construction

After admission, the function prepares the temporary request.

The second word has these exact properties:

- The byte argument is retained without transformation in bits 0–7.
- Bits 8–15 contain the fixed value `0x03`.
- Only the low eight bits of the value argument appear in bits 16–23.
- Bits 24–31 are zero.

The extraction of the value argument’s low byte does not cause sign extension into the high byte of this word. A low byte of `0xFF` therefore contributes `0x00FF0000`, not `0xFFFF0000`.

The third word uses only the low eight bits of the 32-bit object field at offset `12`. Its upper 24 bits do not affect this word.

The selected byte is combined with `0xA0` by bitwise OR, not addition and not replacement. Thus:

- Bits selected by `0xA0` are always set in the resulting byte.
- Any other set bits in the selected object byte remain set.
- A selected byte of `0xFF` remains `0xFF`; it does not wrap.

The supplied construction order is:

1. Prepare the second request word.
2. Read the object field at offset `12` and prepare the third request word.
3. Store the complete value argument as the first request word.
4. Call the dependency.

These are writes to temporary storage, not direct writes to caller-owned memory. The dependency receives the prepared request only after those writes.

All shifts and concatenations remain within the represented 32-bit words. No overflow-dependent arithmetic is required to explain the construction.

### Dispatch and return

The dependency is called exactly once on an admitted path, with:

- The original object pointer.
- A pointer to the first word of the temporary request.

The function does not visibly copy the object, substitute another object pointer, or provide an explicit request-length argument.

If the dependency returns normally, its result is returned unchanged. There is no visible result classification, retry, error translation, post-call object check, or cleanup action.

If the dependency does not return normally, no alternate completion behavior is established for this function.

## Side effects

The function directly:

- Reads the reference value used for admission.
- Reads the object fields reached by the admission path.
- Writes the three request words into temporary storage.
- Calls F-be41255119f8 on an admitted path.

No direct write to the object or another persistent data structure is visible. No allocation or release operation is visible.

The absence of direct persistent writes does not make an admitted call side-effect-free. The dependency receives the object pointer and may have effects that are not described in the supplied material.

### Ownership and lifetime

The function uses the object pointer but does not visibly acquire, transfer, or release ownership of the object.

The request storage is temporary and belongs to this invocation. Its pointer is supplied to the dependency during the call. There is no visible heap allocation, ownership-transfer mechanism, or extension of that storage’s lifetime beyond this invocation.

Whether the dependency merely reads, modifies, copies, retains, or otherwise uses that pointer is unknown. Safe consumption requires that any use depending on the original temporary storage finish while that storage remains valid. This is a lifetime constraint, not an established guarantee about dependency behavior.

The function likewise provides no evidence that the dependency preserves the object, the reference value, other globals, or memory ownership.

## Acceptance examples

These examples are conditional static expectations, not reported runtime tests. They assume readable, suitably aligned memory and no concurrent modification. Dependency outcomes are stipulated where needed.

### Null object

Given a null object pointer:

- Return `7`.
- Do not dereference the object.
- Do not call F-be41255119f8.

### Leading-value mismatch

Given a readable leading object value that differs from the reference:

- Return `7`.
- Do not read the fields at offsets `68` or `12` through this function’s path.
- Do not call the dependency.

### Zero admission field

Given a matching leading value and a zero 32-bit field at offset `68`:

- Return `7`.
- Do not read the field at offset `12`.
- Do not call the dependency.

### Nonzero admission field

Given a matching leading value, a field at offset `68` equal to `0x80000000`, and readable construction data:

- Admit the request.
- Treat the field as nonzero; no positive-value requirement applies.
- Call the dependency once.

### Representative request

Given successful admission, with:

- Value argument `0x12345678`.
- Byte argument `0x9B`.
- Object field at offset `12` equal to `0x1122335A`.

The request’s logical words are:

| Word | Expected value |
|---|---|
| First | `0x12345678` |
| Second | `0x0078039B` |
| Third | `0xEFFA0000` |

The third word contains `0xFA` because `0x5A` bitwise-OR `0xA0` equals `0xFA`.

If the target is little-endian, the corresponding 12 request bytes are, in increasing address order:

`78 56 34 12 9B 03 78 00 00 00 FA EF`

That byte sequence is conditional on endianness; the logical word values are not.

### Object-byte boundaries

With admission satisfied, the third request word depends on the selected object byte as follows:

| Low byte at offset `12` | Third word |
|---|---|
| `0x00` | `0xEFA00000` |
| `0x1F` | `0xEFBF0000` |
| `0xA0` | `0xEFA00000` |
| `0xFF` | `0xEFFF0000` |

Changing only the upper 24 bits of the object field leaves these results unchanged.

### Value-argument truncation and preservation

For value argument `0xFFFFFF80` and byte argument `0xFF`, with admission satisfied:

- The first request word is `0xFFFFFF80`.
- The second request word is `0x008003FF`.
- The second word’s most significant byte remains zero.

### Result forwarding

If admission succeeds and the dependency returns `0xDEADBEEF`, this function returns `0xDEADBEEF`.

If the dependency returns `7`, this function also returns `7`; that result cannot distinguish dependency completion from local rejection.
