# F-36e0b575ef51

## Purpose

F-36e0b575ef51 recognizes one of two selector categories and, for a recognized category, either accepts a distinguished value without dispatching or invokes a category-specific indirect operation.

The selector categories are identified by the labels **HandleLock** and **HandleAddressBook**. These labels establish which comparison operands are supplied; they do not establish what the eventual operations do. In particular, the available evidence does not prove that this function acquires a lock, changes an address book, transfers ownership, or validates a handle.

The result is a 32-bit recognition/acceptance indicator:

- **0:** Both selector comparisons returned nonzero; no indirect operation was invoked.
- **1:** A selector comparison returned zero, and either the distinguished-value check bypassed dispatch or the selected indirect operation returned normally.

A result of 1 is not evidence that the indirect operation succeeded. Its return value is not used.

## Interface

### Inputs

The function receives three arguments:

| Input | Represented form | Observable role |
|---|---|---|
| Object reference | Pointer to integer storage | Passed unchanged to the selected indirect operation. When dispatch is needed, its first stored integer supplies the base used to locate the operation pointer. |
| Selector | Opaque 32-bit value | Passed unchanged to the selector-comparison dependency, alongside one of the two fixed selector labels. |
| Candidate value | Integer, represented as 32 bits | Compared against a shared distinguished value and, if dispatch occurs, passed unchanged to the selected operation. |

The selector’s underlying representation is unknown. Although the labels suggest textual comparison, the evidence does not establish that the selector must be a character pointer, that it is null-terminated, or that comparison is case-sensitive.

The candidate value is tested only for equality in this function. There is no local range check, arithmetic transformation, signed-order comparison, or normalization.

### Output

The normal return is a 32-bit value whose only established values are 0 and 1.

There is no separate output buffer or explicit error object. Effects produced by dependencies may be externally observable, but their nature is not specified by the available evidence.

### Object layout required for dispatch

When an indirect operation is needed, the function:

1. Reads the first integer stored at the object reference.
2. Uses that integer as the base address of a dispatch structure.
3. Reads an operation pointer at a category-specific byte offset from that base.

The offsets are:

| Recognized category | Operation-pointer offset |
|---|---:|
| HandleLock | 0x124, or 292 bytes |
| HandleAddressBook | 0x128, or 296 bytes |

These are byte offsets, not element indices. No other object fields or dispatch entries are explicitly read.

The representation suggests a 32-bit address-bearing object header and adjacent 32-bit dispatch entries. However, the supplied material does not independently establish the executable ABI, pointer width, alignment rules, or address-arithmetic behavior. The offsets and integer reads are established; a fully portable object layout is not.

### Preconditions

For a normal return:

- The selector-comparison dependency must accept the supplied selector and fixed label arguments and return normally.
- The shared distinguished-value storage must be readable wherever the selected path accesses it.
- If dispatch is required, the object reference, its first stored integer, the selected operation-pointer slot, and the operation target must all be usable under the actual ABI.
- The selected operation must accept the object reference and candidate value and return normally.

This function performs no explicit validation of those conditions.

On paths that bypass dispatch, the function itself does not dereference the object reference. That does not establish that every dependency is independent of object-related global state.

## Behavior

### 1. First selector comparison and shared-value observation

The function first invokes dependency **F-D01** with:

- The selector argument.
- The fixed HandleLock label.

After that call returns, it reads the shared distinguished value and retains the observed integer for possible use on the second-category path.

This read occurs before the first comparison result determines the branch. Consequently, it occurs even when neither category will ultimately be recognized.

The comparison result is interpreted only by whether it is zero:

- Zero selects the HandleLock path.
- Nonzero leads to a second comparison.

No particular meaning is assigned to positive versus negative nonzero results.

### 2. HandleLock path

If the first comparison returned zero, the function compares the candidate value with a **fresh read** of the shared distinguished value.

The earlier retained observation is not the value used for this equality test.

If the candidate equals the freshly read value:

- The function returns 1.
- It does not explicitly dereference the object reference.
- It does not fetch or invoke either dispatch operation.
- It does not perform the HandleAddressBook comparison.

Otherwise, it reads the first integer at the object reference, fetches the operation pointer at byte offset 0x124 from that base, and invokes **F-D02** with:

- The original object reference.
- The original candidate value.

After that operation returns normally, the function returns 1 without inspecting its result.

### 3. Second selector comparison

If the first comparison returned nonzero, the function invokes **F-D01** again, this time with:

- The same selector argument.
- The fixed HandleAddressBook label.

If this second comparison also returns nonzero, the function returns 0.

On this unrecognized-selector path, the function has already performed:

- Both selector-comparison calls.
- The shared-value read between them.

It does not perform a dispatch lookup or invoke either indirect operation.

### 4. HandleAddressBook path

If the second comparison returns zero, the function compares the candidate against the **retained shared-value observation made after the first comparison**.

It does not refresh that observation after the second comparison.

If the values are equal:

- The function returns 1.
- It performs no explicit object dereference or dispatch lookup.

Otherwise, it reads the first integer at the object reference, fetches the operation pointer at byte offset 0x128 from that base, and invokes **F-D03** with the original object reference and candidate value.

After that operation returns normally, the function returns 1, ignoring its result.

### Precedence and observation timing

The first category has strict precedence. Once the first comparison returns zero, the second comparison is never attempted.

The shared-value timing differs between categories:

- **HandleLock:** The equality decision uses a second read taken on that branch.
- **HandleAddressBook:** The equality decision uses the observation captured before the second comparison.

This distinction matters if the shared value changes between observations, including through behavior of a comparison dependency. No assumption that either dependency preserves global state is justified.

### Arithmetic and widths

The function performs no arithmetic on the candidate value or selector.

Dispatch lookup uses fixed positive byte displacements, 292 and 296, from the integer-derived base. There is no explicit overflow check, bounds check, or alignment check. Behavior for an unusable base or an address calculation outside the valid address space is not established.

The returned indicators and opaque selector value are represented as 32-bit quantities. Candidate and shared-value comparisons use the represented integer width. Nothing in this function gives special treatment to negative values, zero, or a maximum-width bit pattern beyond ordinary equality.

## Side effects

### Explicit local effects

The established explicit effects are:

- One or two calls to the comparison dependency.
- One shared-value read on every path that reaches a selector decision.
- An additional shared-value read on the HandleLock path.
- If dispatch is required, one read of the object’s first integer and one read of the selected operation pointer.
- At most one indirect operation call.

The function contains no explicit write to the object, the shared distinguished value, or selector storage.

### Dependency effects

The absence of explicit writes does not make this function observably read-only. Both the comparison dependency and the selected operation may have effects not shown here.

No guarantee is established concerning:

- Preservation of globals.
- Object mutation.
- Allocation or deallocation.
- Reference-count changes.
- Lock acquisition or release.
- I/O.
- Reentrancy or synchronization.

Operation-pointer lookup occurs after the relevant comparison calls. Therefore, dispatch is based on object storage read at that later point, not on a dispatch base captured on entry.

### Ownership and lifetime

The function passes the original object reference and candidate value directly to the selected operation. It performs no explicit copy, retain, release, allocation, or deallocation.

No ownership transfer is established by that forwarding. The selected operation’s ownership behavior is unknown, so callers cannot infer that the object remains alive or unchanged after a result of 1.

The selector is passed to the comparison dependency without a local ownership operation. Its required lifetime and any retention by that dependency remain unspecified.

### Failures and abnormal termination

No explicit recovery or error translation surrounds the dependency calls or indirect dispatch.

The function does not check for a null object reference, an invalid dispatch base, or an unusable operation pointer when dispatch is required. The evidence does not specify how resulting faults or other abnormal exits are reported.

The stated 0/1 result contract applies only when execution returns normally.

## Acceptance examples

These examples are conditional contracts, not reported executions. Unless stated otherwise, all dependencies return normally and required memory accesses are valid.

### First category, bypass

Given:

- F-D01 returns zero for HandleLock.
- The candidate equals the shared value read on the HandleLock branch.

Expected:

- Return 1.
- One comparison call.
- Two explicit shared-value reads.
- No second-category comparison, object-header read, dispatch-pointer read, or indirect operation call.

### First category, dispatch

Given:

- The first comparison returns zero.
- The candidate differs from the branch’s fresh shared-value observation.

Expected:

- Invoke the operation from offset 0x124 exactly once.
- Pass the original object reference and candidate.
- Return 1 after the operation returns, regardless of its return value.

### Neither category recognized

Given both comparison calls return nonzero:

- Return 0.
- Perform the shared-value read between the two calls.
- Do not explicitly dereference the object or call a dispatch operation.

A null object reference is therefore not, by itself, an explicit dereference failure on this path. This example does not establish that the comparison dependency accepts every selector.

### Second category uses the earlier observation

Given:

- The first comparison returns nonzero.
- The intervening shared-value read observes 17.
- The second comparison changes that shared value to 23 and returns zero.
- The candidate is 17.

Expected:

- Return 1 without dispatch.
- Use the retained observation of 17, not the later value of 23.

With candidate 23 under the same conditions, dispatch through offset 0x128 is required.

### First category uses a fresh observation

Given:

- The first comparison returns zero.
- The first shared-value read observes 17.
- The HandleLock branch’s subsequent read observes 23.
- The candidate is 17.

Expected:

- Dispatch through offset 0x124.
- Do not bypass merely because the earlier observation matched.

This example is conditional on the execution environment permitting those differing observations; it does not assert a threading model.

### Recognition does not prove operational success

Given a recognized category, a nonmatching candidate, and a selected operation that returns a failure-like value normally:

- The wrapper still returns 1.
- The operation’s result is not propagated or translated.
