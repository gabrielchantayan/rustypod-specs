# F-2221de0fd90b

## Purpose

F-2221de0fd90b performs an ordered series of memory reads and writes using four explicit arguments and three additional address-bearing values supplied by the execution context. It then invokes an unresolved indirect dependency with four arguments.

The established behavior is memory manipulation and an indirect invocation. A higher-level purpose—such as updating a particular kind of object, table, or protocol state—is not established. In particular, values loaded from memory are sometimes used as base addresses and sometimes doubled to form destination addresses. Those operations must not be reinterpreted as ordinary array accesses without additional evidence.

This contract describes the supplied static representation. No runtime tests have been performed.

## Interface

The visible entry interface supplies:

| First argument | 32 bits | Written to the primary region at offset `0x10`. |

### Additional execution-context inputs

Three address-bearing values are used without visible initialization in the body:

- **Primary region base:** used for reads and writes at offsets `0x09`, `0x10`, `0x14`, `0x44`, and `0x54`.
- **Auxiliary region base:** used for a write at offset `0x44`.

These are required inputs to the observed behavior even though they are not among the four explicit arguments. Their delivery mechanism and caller obligations are not established.

A distinguished byte location, displayed as address `0x67`, is also accessed. This document refers to it as the **shared byte location**. Whether that displayed address denotes an ordinary absolute address, a special memory mapping, or an artifact of the supplied representation is unresolved.

## Behavior

### Widths and interpretation

The supplied representation distinguishes 8-bit, 16-bit, and 32-bit memory operations. Full-width values are treated here as 32-bit quantities, consistent with the four-byte accesses shown.

A byte write derived from a wider value retains only its low eight bits. Thus, writing the low byte of a region base or a loaded value does not store a complete address.

Offsets are byte offsets. In particular, decimal `100` and hexadecimal `0x64` identify the same offset. The 32-bit constant written at offset `0x54` of a derived region is decimal `100`, equivalent to `0x00000064`.

Byte order is not established. A 32-bit write therefore specifies a value and width, not a particular ordering of its four constituent bytes.

### Ordered accesses before the indirect invocation

The following sequence is the order established by the supplied representation. Descriptive names for loaded values identify captured results, not additional memory locations or implementation variables.

1. Write the first argument as 32 bits to the primary region at offset `0x10`.

2. Write the secondary region base as a 32-bit value to the auxiliary region at offset `0x44`.

3. Write the low eight bits of the second argument to the shared byte location.

4. Read the shared byte location and write that byte to the primary region at offset `0x09`.

5. Write the low eight bits of the primary region base to the secondary region at offset `0x09`.

6. Write the second argument as 32 bits to the primary region at offset `0x44`.

7. Read a 32-bit address-bearing value from the primary region at offset `0x54`. This captured value is the **derived region base** for subsequent accesses.

8. Read the shared byte location again and write that byte to the primary region at offset `0x09`. This is a separate read and write, not merely a statement that the previous value remains there.

9. Write the fourth argument as one byte to the derived region at offset `0x0D`.

10. Write the third argument as 32 bits to the secondary region at offset `0x54`.

11. Read a 32-bit value from the primary region at offset `0x14`. Its captured low byte is used later.

12. Write the fourth argument as one byte to the secondary region at offset `0x11`.

13. Write the low eight bits of the derived region base to the primary region at offset `0x09`.

14. Write the derived region base as a 32-bit value to the primary region at offset `0x44`.

15. Read a 32-bit value from the secondary region at offset `0x04`. This is the **first address value**.

16. Write the 16-bit value `0x0065` to the address formed by doubling the first address value. This is a two-byte write of decimal `101`; it is not a four-byte write or a write relative to one of the named region bases.

17. Read a 32-bit value from the address obtained by adding `0x64` to the first address value. This captured result is the **second address value**.

18. Write the low eight bits of the value captured from the primary region at offset `0x14` to the derived region at offset `0x11`.

19. Write the 32-bit value `0x00000064` to the derived region at offset `0x54`.

20. Read a 32-bit value from the address obtained by adding `0x74` to the first address value. This is the **forwarded value** used as the fourth argument of the indirect invocation.

21. Read a 32-bit value from the secondary region at offset `0x64`. This is the **final region base**.

22. Write the low eight bits of the first address value to the secondary region at offset `0x09`.

23. Write the second address value as 32 bits to the final region at offset `0x54`.

24. Write the final region base as a 32-bit value to the address formed by doubling the second address value.

25. Invoke the unresolved indirect dependency with the following ordered argument values:
   - first: `0x72`, decimal `114`;
   - second: the captured second address value;
   - third: the original third argument;
   - fourth: the captured forwarded value.

The first invocation argument is a constant, not a value loaded from any of the modified regions. The third invocation argument is the original explicit argument, not a fresh read of the secondary region at offset `0x54`.

### Aliasing and captured values

No non-aliasing guarantee is established. The primary, auxiliary, secondary, derived, and final regions may overlap each other, the shared byte location, or either doubled-value destination.

Consequently, the ordered accesses are more authoritative than any simplified list of final field values:

- A write before a read can change the value that read captures.
- A later write does not retroactively change an already captured value.
- A write through one base can affect a field described through another base.
- The 16-bit doubled-address write can affect either of the later reads based on the first address value if their byte ranges overlap.
- The final 32-bit doubled-address write can overwrite an earlier destination.

The shared byte location is read twice. The contract must not replace those reads with unconditional reuse of the second argument’s low byte: an intervening aliased write, or an externally visible memory change where applicable, could alter the byte read.

### Arithmetic limits

The two doubled-address expressions use values represented as 32-bit integers. The supplied representation does not establish the machine-level treatment of signed overflow, address truncation, or address-space wrapping.

Accordingly:

- Doubling is established as the intended address-forming operation in the representation.
- Exact behavior for values whose doubling exceeds the relevant representable range is **documented_only**.
- Offset additions near address-space boundaries are likewise **documented_only**.
- No bounds check, overflow check, or alternative arithmetic path is visible.

Assume all accessed ranges are valid and mutually non-overlapping, all address calculations remain within the supported range, and no external actor changes memory.

If:

- the second argument is `0xA1B2C3D4`;
- the fourth argument is `0x7E`;

### Doubled addresses are absolute destinations

Assume the first address value is `0x1000` and the second address value is `0x1800`, with valid ordinary address arithmetic.

The direct sequence must:

- write 16-bit `0x0065` at address `0x2000`;
- read the second address value from address `0x1064`;
- read the forwarded value from address `0x1074`;
- write the final region base as 32 bits at address `0x3000`.

The doubled destinations must not be treated as offsets added to the primary or secondary region bases.

### Captured values survive later overwrites

Suppose the write of 16-bit `0x0065` at twice the first address value overlaps the location from which that first address value was read.

The captured first address value remains the basis for the subsequent reads at offsets `0x64` and `0x74`. The function does not visibly reload it from secondary offset `0x04`.

### Indirect arguments do not depend on later field contents

Assume the second address value and forwarded value have been captured successfully. If subsequent direct writes overwrite their original source locations through aliasing, the indirect invocation still receives the captured values.

Likewise, changing secondary offset `0x54` through aliasing does not change the third invocation argument: that argument is the original third explicit input.

### Invalid derived destination
