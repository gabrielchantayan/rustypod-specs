# F-208392f0520a

## Purpose

F-208392f0520a writes a variable-width identifier followed by a variable-width length field into caller-supplied storage, then advances a caller-owned output cursor past those fields.

The identifier combines two caller-supplied high-order bits, a bit controlled by whether a mode value is nonzero, and a tag number. The length is normally encoded as a short or long definite length. One exact mode-and-length combination instead emits the single byte `80`.

The layout resembles an ASN.1-style identifier and length header. That interpretation is inferred intent, not a guarantee of standards compliance. In particular, negative inputs are not rejected and can produce encodings that would not represent valid nonnegative tags or lengths.

The function writes only the header. It does not copy a value payload, append a terminator, or allocate storage.

## Interface

The function has five inputs and no explicit return value:

| Input | Role |
|---|---|
| Cursor slot | Writable storage holding the address at which header output begins. Updated on normal completion to the first byte after the header. |
| Mode | Signed integer. Any nonzero value sets identifier bit `20`; the exact value 2 also enables a special zero-length encoding. |
| Length | Signed integer used to select and populate the length encoding. |
| Tag number | Signed integer used to select and populate the identifier encoding. |
| Class-bit input | An 8-bit value. Only bits selected by mask `C0` contribute to the output. |

All byte values and masks in this contract are hexadecimal unless explicitly described as decimal.

**Width model.** The supplied representation identifies the cursor slot as four-byte storage and the class-bit input as one byte. The integer calculations are described here using signed 32-bit integers, consistent with the supplied representation. Exact target ABI details and pointer representation are not independently established. Bounds stated below depend on this 32-bit model.

**Normal-call preconditions:**

- The cursor slot is readable and writable.
- Its initial contents identify writable output storage.
- The output storage has enough capacity for the complete header.
- The required address calculations remain valid.
- For the ordinary independent-buffer contract, output bytes do not overlap the cursor slot.

There is no capacity argument and no validation of these conditions. Nonnegative tags and lengths are not enforced preconditions of the implementation: negative values have observable encoding behavior described below.

With signed 32-bit inputs, a header occupies between 2 and 11 bytes. Eleven bytes is a sufficient capacity bound for every tag-and-length combination under that model.

On normal completion, the cursor slot contains the initial output address plus the number of header bytes emitted. There is no returned byte count or error status.

## Behavior

### Identifier flags

The first identifier byte incorporates:

- Bits `C0` from the class-bit input.
- Bit `20` when mode is nonzero; otherwise that bit is clear.
- A five-bit tag field, or the value `1F` indicating an extended tag representation.

The lower six bits of the class-bit input are ignored. They cannot independently set the mode-controlled bit or change the tag field.

Mode values are not restricted to 0, 1, and 2. For identifier construction, every nonzero value—including a negative value—has the same effect.

### Short identifier

A tag number less than decimal 31 uses exactly one identifier byte.

The low five bits of that byte are the low five bits of the tag number after conversion to a byte. Those bits are combined with the identifier flags.

The comparison is signed. Consequently, every negative tag number takes this short-identifier path. For example, tag −1 contributes `1F`, but does not cause any extended tag bytes to be emitted. Tag −32 contributes `00`.

This behavior is truncation, not rejection, normalization, or validation.

### Extended identifier

A tag number of decimal 31 or greater uses an initial identifier byte whose low five bits are `1F`, followed by a minimal sequence of seven-bit groups representing the positive tag number.

The group sequence has these properties:

- Most-significant group first in the completed buffer.
- No leading zero group.
- Bit `80` set in every group except the last.
- The last group has bit `80` clear.

The number of groups is the number of seven-bit right shifts needed to reduce the positive tag number to zero. For a signed 32-bit tag, there are between one and five groups.

Thus tag 31 uses an extended representation even though its value fits in five bits. The short-form cutoff is strictly less than 31.

### Length selection

Length handling follows identifier emission.

If mode is exactly 2 and length is exactly zero, the function writes the single length byte `80`. No additional length bytes are written.

Otherwise:

- A length greater than decimal 127 uses long-form encoding.
- Every other length uses one byte, obtained by converting the length to an 8-bit value.

The special case depends on the exact mode value, not merely its nonzero status. Mode 1 and mode 2 therefore produce the same identifier flag but different length bytes when length is zero.

### Long-form length

A positive length greater than 127 is represented by:

1. A byte containing `80` combined with the number of following length bytes.
2. The length itself, in the minimum number of bytes, most-significant byte first.

For signed 32-bit inputs, the number of following bytes is between one and four. The initial long-form byte therefore ranges from `81` through `84`.

Examples of the length field alone:

| Decimal length | Length bytes |
|---:|---|
| 127 | `7F` |
| 128 | `81 80` |
| 255 | `81 FF` |
| 256 | `82 01 00` |
| 2,147,483,647 | `84 7F FF FF FF` |

No leading zero length byte is emitted.

### Negative lengths

Negative lengths never enter the long-form branch and never satisfy the special zero-length condition. They produce exactly one length byte, retaining only the low eight bits.

For example:

- Length −1 emits `FF`.
- Length −128 emits `80`.
- Length −256 emits `00`.

These bytes are not accompanied by additional length data. In particular, a negative input can produce a byte resembling an indefinite-length marker or a long-form prefix without the corresponding semantic structure. The function does not detect this.

### Cursor advancement and size

The identifier occupies:

- One byte for any tag less than 31, including negative tags.
- One initial byte plus one to five group bytes for an extended tag.

The length field occupies:

- One byte for the special mode-2, zero-length case.
- One byte for ordinary lengths at or below 127, including negative lengths.
- One prefix byte plus one to four value bytes for positive lengths above 127.

The cursor advances by the sum of those sizes. It advances by encoded header size, not by the supplied length and not by any payload size.

## Side effects

### Reads and writes

The following order is established by the supplied static representation, conditional on execution continuing normally:

1. The function reads the initial output address from the cursor slot.
2. It writes the first identifier byte.
3. If the identifier is extended, it writes its group bytes.
4. It writes the first length byte.
5. If the length is long-form, it writes its remaining bytes.
6. It writes the final advanced address into the cursor slot.

There is no intermediate cursor-slot update and no explicit read of existing output-byte contents.

The completed buffer is ordered most-significant-first where appropriate, but the actual stores are not uniformly in increasing address order:

- Extended tag groups are populated from the highest-addressed group backward toward the first group.
- The last tag group receives one store with its continuation bit clear.
- Each earlier tag group first receives a store with its continuation bit clear, then a second store to the same byte with bit `80` set.
- Long-form length value bytes are also populated from the highest address backward, after their prefix byte has been written.

These are static store-order observations. The source does not establish volatile, atomic, inter-thread, or memory-mapped-I/O guarantees. The intermediate tag stores must not be treated as a portable synchronization protocol.

### Ownership and state

The function uses caller-provided memory. It does not allocate or release storage, transfer ownership, retain the output address, or call another function.

It changes output bytes and the cursor slot. It does not explicitly access global state.

No payload bytes are written, even when a positive length is supplied. The special `80` length byte is not followed by any end marker.

### Errors and partial effects

No explicit failure path, validation result, or rollback is present.

An invalid pointer or insufficient output capacity can lead to invalid memory access. Earlier output stores may already have occurred before a later access fails. Because the cursor update is last, partial output may exist while the cursor slot still contains its original value.

Aliasing between the cursor slot and output storage is not checked. Such overlap can make the final cursor write overwrite header bytes, or make earlier header stores overwrite the slot’s old representation. No disjoint-buffer result is promised for overlapping storage.
