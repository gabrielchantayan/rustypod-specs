# F-c9ae8ae96286

## Purpose

F-c9ae8ae96286 conditionally fills four 32-bit fields in a supplied record using two indirect callbacks. A one-byte marker controls entry to the update path.

When the marker is zero, the function calls the first callback, handles its status, calls the second callback, handles its status, publishes four temporary values to the record, and writes the marker as one. When the marker is nonzero, it performs none of those operations.

A nonzero callback status causes the corresponding temporary pair to be zeroed immediately after that callback returns. The timing matters: the second callback runs after the first pair’s status handling and can modify that pair if it obtains access to its addresses. Publication therefore uses the temporary values present after the second callback and its status handling, not necessarily the first pair’s values immediately after its own status handling.

Lazy initialization or caching is inferred intent. The meanings of the result words and callback statuses are not established.

## Interface

### Arguments and return

The function receives:

1. **Dispatch descriptor address:** identifies a dispatch-table reference and a callback context word.
2. **Result-record address:** identifies the input words, marker, and destination words described below.

There is no explicit return value. Callback statuses are handled internally and are not returned to the caller.

### Widths and address representation

The supplied representation establishes four-byte accesses for descriptor words, dispatch entries, record input words, temporary output words, and record destination words. The marker is accessed as one byte.

The callback status is represented as an integer compared with zero. The representation is consistent with a 32-bit integer and address model; it does not independently establish the complete machine ABI or original source-language declarations.

The record words are opaque 32-bit values. Their signedness, units, and interpretation are unknown. The function performs no arithmetic on their contents and does not narrow them when publishing them.

Address calculations use fixed byte offsets. No explicit overflow, bounds, or alignment checks are present. Portable address-wrap behavior is not established.

If the marker is zero, defined completion additionally requires:

## Behavior

### Marker gate

The function first reads the byte at record offset `0x18`.

If the byte is nonzero, it returns without explicitly reading the descriptor or record input words, calling either callback, or writing the record. Every nonzero byte takes this path. An existing marker such as `0x80` is not normalized to one.

If the byte is zero, the function enters the update path. It does not recheck the marker before either callback or before publication.

### First callback and immediate status handling

The first callback is resolved through dispatch-table offset `0x10`. Its six logical arguments are:

1. The descriptor context word.
2. The entry value obtained from dispatch-table offset `0x10`.
3. The record word at `0x08`.
4. The record word at `0x0c`.
5. The address of the first pair’s first four-byte temporary.
6. The address of the first pair’s second four-byte temporary.

The two output locations are distinct. Neither has explicit initialization before the call.

The listed order describes argument positions, not a proven order of evaluation among the argument reads and target lookup.

After the callback returns normally:

- A zero status leaves both temporaries unchanged by this function.
- Any nonzero status causes the function to write zero to the first temporary and then zero to the second temporary.

These zero writes occur before the second callback. They establish the first pair’s values at that point, not an immutable pair reserved for later publication. The function neither copies the pair into protected storage nor prevents its addresses from having escaped through the first callback.

A nonzero first status does not suppress the second callback.

### Second callback and immediate status handling

After handling the first status, the function resolves the callback through dispatch-table offset `0x14`. Its arguments have the same shape:

1. The descriptor context word.
2. The entry value obtained from dispatch-table offset `0x14`.
3. The record word at `0x08`.
4. The record word at `0x0c`.
5. The address of the second pair’s first four-byte temporary.
6. The address of the second pair’s second four-byte temporary.

These output locations are distinct from each other and from the first pair. They also have no explicit initialization before their callback.

The second call’s descriptor, table, context, and record-input accesses occur after the first callback and its status handling. They are not guaranteed to use entry-time values. Mutations made by the first callback can therefore affect the second call.

The second callback is not restricted by this body to writing its own supplied output locations. For example, the first callback may have stored its output addresses in reachable state, allowing the second callback to modify the first pair while the invocation remains active.

After the second callback returns normally:

- A zero status leaves the second pair unchanged by this function.
- Any nonzero status causes zero to be written to the second pair’s first temporary and then its second temporary.

There is no later callback invocation before publication. Thus, for normal defined execution without independent intervening mutation, a nonzero second status makes the second pair’s published words zero regardless of what either callback previously placed in those two temporaries. This zeroing is unconditional with respect to callback-produced values.

There is no corresponding second zeroing of the first pair.

### Publication

After the second status has been handled, the function performs these explicit record writes in order:

1. First pair’s first temporary to `0x1c`.
2. First pair’s second temporary to `0x20`.
3. Second pair’s first temporary to `0x24`.
4. Second pair’s second temporary to `0x28`.
5. Byte value one to `0x18`.

Each destination receives the temporary value available when that publication operation reads it. The function does not publish an earlier snapshot of the first pair.

Consequently:

- A first nonzero status guarantees that the first pair was zeroed before the second callback, but guarantees zero first-pair destinations only if those temporaries are not subsequently modified before their publication reads.
- Two nonzero statuses do not, by themselves, guarantee four zero destinations.
- A second nonzero status zeroes the second pair immediately before the publication phase; no subsequent callback can alter it within this function’s call sequence.

These are ordered operations in the supplied representation, not a guarantee of atomic publication, a memory barrier, or synchronization with other threads.

### Completion and failure

Normal completion of the zero-marker path writes the marker as one regardless of either callback’s status. The marker therefore indicates completion of this update path, not proven callback success.

The function exposes no distinct error return and performs no retry.

If a callback faults, does not return, or transfers control elsewhere, execution of the remaining operations is not established. There is no visible recovery or rollback. If a later memory access fails, earlier callback effects or completed writes are not shown to be undone.

## Side effects

### Direct effects

The nonzero-marker path has no explicit write side effects.

A normally completing zero-marker path:

- Calls two indirect targets, in order.
- Passes four distinct temporary output addresses across those calls.
- Conditionally zeroes each pair immediately after its callback.
- Writes four four-byte record destinations.
- Writes the one-byte marker last.

There is no visible direct allocation, deallocation, resource release, or ownership transfer.

### Callback effects and temporary lifetime

The callback bodies are unavailable. They are not established to preserve the descriptor, dispatch table, record, globals, or other reachable storage. They may have effects beyond the direct operations listed above.

In particular, passing output addresses does not establish that those addresses remain private to their respective callbacks. Retaining the first pair’s addresses in reachable storage can allow modification during the second callback, while the outer invocation’s temporary storage is still active.

Conversely, the passage of an address does not establish ownership transfer or permission to use it after the temporary’s lifetime ends. Escape policy, asynchronous use, and resource ownership are **documented_only**. This function provides no visible enforcement of such policies.

### Reentrancy and concurrency

The function installs no in-progress marker before calling out. If a callback reenters with the same record while its marker is still zero, the nested invocation can take the update path again.

A callback’s change to the marker does not alter the already-entered outer path, because that path contains no further marker test.

No lock, atomic protocol, or exclusive-initialization mechanism is established. Concurrent initialization, coherent snapshots, and cross-thread visibility are not guaranteed.

### First callback returns nonzero without later modification

Given a zero marker, suppose the first callback returns nonzero, the second supplies two established outputs and returns zero, and the second callback does not modify the first pair through retained addresses or other access.

The first two destinations must be zero. The second two receive the second pair’s values at publication. The second callback must still be invoked.

### Both callbacks return nonzero without first-pair modification

All four destinations must be zero, and the marker must become one.

Without that condition, only the second pair’s zero publication follows from the two statuses alone.

### Zero status with incomplete outputs
