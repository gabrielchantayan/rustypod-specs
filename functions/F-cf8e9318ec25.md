# F-cf8e9318ec25

## Purpose

F-cf8e9318ec25 traverses a linked sequence and conditionally processes each entry using two bitmaps. A match in the first bitmap selects processing followed by setting bit `0x200` in an associated target’s flags. If the first bitmap does not match, a match in the second selects the same processing followed by clearing that bit. An entry matching neither bitmap receives no direct processing or flag update.

The first bitmap has precedence: when its selected bit is set, the second bitmap is not read.

This is a source-facing behavioral contract based on the supplied static evidence. Semantic meanings such as “enabled,” “disabled,” “registered,” or “removed” are not established. The dependency calls may have substantial effects beyond the direct operations described here.

## Interface

**Input:** one address-like argument identifying a caller-supplied object, called the **owner** below.

**Output:** no explicit return value. Normal completion occurs when the current sequence-node address is null. There is no explicit status result or error-reporting path.

The visible representation uses 32-bit pointer-bearing and scalar fields. Offsets below are byte offsets; a word occupies four bytes. These descriptions identify accessed fields, not complete object definitions.

The owner, traversal context, sequence descriptor, entries, targets, and bitmap storage must be valid for the accesses actually reached. No checks establish their sizes, alignment, allocation state, or mutual independence.

The owner’s interior address at offset `0x200` is passed as an address, not as the contents stored there. By contrast, the value at owner offset `0x208` is read and used as the traversal-context address.

## Behavior

### Initial state acquisition

The function first reads the traversal-context address from the owner. It then reads the sequence-descriptor address from that context and the initial node address from the descriptor.

The traversal-context address is retained for the traversal. It is not reread from the owner for each node. Likewise, the sequence descriptor and initial head are not revisited after initialization.

Consequently, changes made by dependencies to the owner’s traversal-context field or the descriptor’s head field do not by themselves redirect the already-running traversal. Changes to fields within the retained context, or to a current node’s next link, can affect later accesses because those fields are read later.

A null initial node causes normal return, but only after the initialization reads. It does not make a null or invalid owner, traversal context, or descriptor acceptable.

### Bitmap selection for an entry

For a non-null current node, the function reads its entry address. It then performs two reads of that entry’s selector field:

- The first supplies the word index by an unsigned right shift of five bits.
- The second supplies the bit position from its low five bits.

The mask is a 32-bit single-bit mask at that position. With a stable selector value \(s\), the selected word index is \(\lfloor s/32 \rfloor\), and the selected bit position is \(s \bmod 32\).

These are separate selector reads. The visible operations do not capture one selector value for both calculations. If the field can change between reads under the execution environment, the selected word and selected bit need not come from the same value. No synchronization or atomic snapshot mechanism is visible.

The function reads the first bitmap address from the retained traversal context and then reads the selected bitmap word. The address is formed from the bitmap base, a four-byte initial displacement, and four bytes per selected word.

There are three outcomes:

1. **First bitmap matches.** The function selects processing followed by setting flag bit `0x200`. It does not read the second bitmap address or its selected word.
2. **First bitmap does not match, second bitmap matches.** The function reads the second bitmap address and selected word, using the same already-computed word index and mask. It selects processing followed by clearing flag bit `0x200`.
3. **Neither bitmap matches.** The function performs no dependency calls for this entry and no direct target-flags access. It advances to the next node.

In particular, an entry absent from both bitmaps does not have bit `0x200` cleared. Its target is not even read by this function on that path.

### Processing a selected entry

Both matching paths execute the same three dependency calls, in the same order:

1. Read the target address from the initially obtained entry. Read the four-byte value at target offset `0x08`. Call **F-58820f51cfa6** with that value as its first argument and the target address as its second.
2. Reread the entry-address field of the current node. Call **F-a7b0f949da8d** with the owner address, the retained target address, and this newly read entry address, in that order.
3. Call **F-514f645f8582** with the owner’s interior address at offset `0x200` and the retained target address, in that order.

The reread in the second step is significant. Its third argument is not guaranteed to equal the entry address originally used to obtain the selector and target. For example, if the first dependency changes the current node’s entry field and execution remains valid, the second dependency receives the changed entry address while still receiving the original retained target address.

The target itself is not reacquired between calls. Changes to the entry’s target field do not redirect subsequent calls or the final flag access during this iteration.

No dependency return value is inspected. This establishes neither success nor failure semantics for those dependencies.

### Flag update after processing

Only after all three dependency calls return does the function read the retained target’s flags word at offset `0x18`.

- For a first-bitmap match, it writes the word with bit `0x200` set.
- For a second-bitmap-only match, it writes the word with bit `0x200` cleared.

The operation is 32-bit. The clear mask is `0xfffffdff`; all bits other than `0x200` retain their values from the flags read performed after the calls.

Thus, unrelated flag changes made by dependencies are preserved if they are present when that final read occurs. The function does not restore a flags snapshot taken before processing. Conversely, any dependency change to bit `0x200` is overridden by the selected set-or-clear operation.

The selected operation is determined before the dependency calls. The bitmaps are not rechecked afterward.

There is a direct flags write on each selected path even when the selected bit already has the requested value. The function does not skip processing or the write merely because the final bit value would be unchanged.

### Traversal advancement and completion

After either processing or skipping the current entry, the function reads the next-node address from the current node’s offset `0x00`. That read occurs after the dependency calls and flag write on a selected path.

Accordingly, changes to the current node’s next link made during dependency processing can redirect the remainder of traversal. The next node is not captured before calling the dependencies.

A null next-node address causes normal return at the next null-node check. There is no cycle detection, iteration bound, or explicit cancellation check. A cyclic chain can continue indefinitely unless some executed effect changes the traversal or prevents further execution.

## Side effects

The only explicit memory write visible in F-cf8e9318ec25 is the selected target’s flags-word update.

The function also invokes three dependencies for every selected node. Their writes, global-state changes, allocation behavior, ownership effects, and failure behavior are unknown. The absence of other direct writes in this function must not be interpreted as absence of other externally observable effects.

There is no visible allocation, deallocation, ownership transfer declaration, rollback, or error recovery in this function. In particular, the calls must not be assumed to retain or release any argument.

For execution to continue normally on a selected path:

- The retained target must remain valid for subsequent calls and the final flags read and write.
- The current node must remain valid for its entry-field reread after the first dependency and its next-link read after processing.
- The owner and its interior address must remain valid for their subsequent uses.
- Storage reached in later iterations must remain valid when accessed.

A dependency that releases one of these objects without preserving its later accessibility would conflict with the function’s subsequent accesses. The supplied evidence does not establish whether any dependency does so.

The operation is not presented as transactional. Dependency effects precede the flags write, and the source contains no recovery path for partial progress.

## Acceptance examples

These are conditional acceptance scenarios derived from static evidence, not executed tests. Unless stated otherwise, they assume valid storage, stable selectors, terminating links, and dependencies that return while leaving subsequently accessed storage valid.

1. **Empty sequence.**  
   The initialized head address is null. The function returns without reading an entry, accessing either bitmap, calling a dependency, or writing target flags.

2. **Neither bitmap contains the entry.**  
   Both selected bits are clear. No dependency is called for that node. Even if its target’s flag bit `0x200` is set beforehand, this function leaves that flags word untouched.

3. **First bitmap only.**  
   The first selected bit is set. All three dependencies run in the specified order. If the post-call flags value is `0x00000005`, the function writes `0x00000205`. The second bitmap is not accessed.

4. **Second bitmap only.**  
   The first selected bit is clear and the second is set. The same three calls occur. If the post-call flags value is `0x00000305`, the function writes `0x00000105`.

5. **Both bitmaps contain the entry.**  
   The outcome is the set operation, not the clear operation. The second bitmap is not consulted. Its address need not be dereferenceable for this iteration, provided no other executed operation accesses it.

6. **Word boundary.**  
   A stable selector of `31` chooses bit 31 of the word at bitmap offset `0x04`. A selector of `32` chooses bit 0 of the word at offset `0x08`. These examples require those bitmap words to exist.

7. **Dependency changes unrelated flags.**  
   On a first-bitmap match, suppose the flags word after the third call is `0x80000001`. The direct write is `0x80000201`; the high bit is preserved.

8. **Dependency changes the node’s entry.**  
   Suppose the first dependency changes the current node’s entry address. The second dependency receives that changed address as its third argument. Its target argument and the eventual flags target remain the previously retained target.

9. **Dependency changes the next link.**  
   Suppose dependency processing changes the current node’s next link to null. The function completes the selected flags write, then reads that null link and terminates rather than visiting the former successor.

10. **Repeated target.**  
    Two nodes may refer to the same target. Each node is independently evaluated and, if selected, processed. With no intervening dependency changes to that bit, an earlier set followed by a later clear leaves bit `0x200` clear. No deduplication is visible.

## Uncertainties

The following are **documented_only** unknowns, not inferred guarantees:

- The semantic identities of the owner, entries, targets, bitmaps, and flag bit.
- Complete object layouts, capacities, alignment requirements, and aliasing restrictions.
- Dependency ownership, memory-lifetime, global-state, reentrancy, and error behavior.
- Concurrency rules and whether selector or bitmap reads require synchronization.
- Platform fault behavior for invalid addresses or arithmetic overflow.
- Whether the linked sequence is guaranteed acyclic or stable during processing.

The selector is unsigned and 32-bit. Its word index can therefore reach `0x07ffffff`. Multiplication by four reaches `0x1ffffffc`, and the additional four-byte displacement reaches `0x20000000`. Those offset calculations fit within 32 unsigned bits, but addition to a bitmap base can still exceed the address space or allocated storage. No bounds check prevents either condition.

The visible bit-mask construction uses a shift count limited to 0–31. The supplied representation supports a 32-bit single-bit mask interpretation, including bit 31. It does not independently establish source-language signed-shift guarantees or platform behavior beyond that representation.

An inferred intent is to reconcile target membership or status against two classifications. That interpretation is not needed for the contract and must not replace the established first-bitmap precedence, dependency ordering, or post-call flag update.
