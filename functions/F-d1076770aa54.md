# F-d1076770aa54

## Purpose

F-d1076770aa54 coordinates two ordered object-setup operations. The first operation selects one of two dependency paths according to a 32-bit mode argument. The second operation uses a common dependency path regardless of mode, provided preceding operations return normally.

Before selecting the first path, the function prepares a template-backed record and replaces one 32-bit field with a table-derived value. The nonzero-mode path prepares a second record with additional fixed fields. Both paths forward the same two caller-supplied 32-bit values.

**Established static evidence:** the function performs no explicit validation, reports no status, and contains no explicit cleanup or release operation.

**Inferred intent:** the allocation-like requests followed by setup calls suggest construction of objects with different layouts or types. Their identities, attachment relationships, and eventual ownership are not established.

## Interface

The function accepts four arguments and has no explicit return value.

| Argument | Width and interpretation | Observable use |
|---|---|---|
| Object reference | 32-bit address-like value | Supplies the address of a byte read at offset 4. |
| Mode | 32-bit integer | Compared with 0 and 1. Its exact value is not forwarded. |
| First forwarded value | Opaque 32-bit value | Passed unchanged to both selected setup operations. |
| Second forwarded value | Opaque 32-bit value | Passed unchanged to both selected setup operations. |

The object reference is not passed directly to the setup dependencies. Its only explicit use is the byte read at offset 4.

Mode is not treated as a simple Boolean throughout:

- Mode 0 selects the zero-mode setup path.
- Every nonzero mode selects the alternate setup path.
- Only mode 1 can select the second entry of the table used to adjust the initial record.

The function supplies the setup dependencies with:

1. The result of an allocation-like dependency call.
2. A literal zero.
3. The first forwarded value.
4. The second forwarded value.
5. An address of temporary, stack-resident record storage.

The return values of the setup dependencies, if any, are not inspected.

## Behavior

### Record preparation and table selection

The first observable dependency operation is a transfer request with an initial template source, temporary destination storage, and a length of 104 bytes.

After that operation returns, the function reads one byte at offset 4 from the object reference. It tests bit 0 of that byte.

The table selector is:

| Flag bit 0 | Mode | Selected table entry |
|---|---|---|
| Clear | Any value | Entry 0 |
| Set | Exactly 1 | Entry 1 |
| Set | Any value other than 1 | Entry 0 |

The flag byte is read even when mode is not 1. Mode does not bypass the object-reference access.

The selected table entry is a 32-bit value, with entries spaced four bytes apart. The function subtracts 20 from that value and writes the result into the initial temporary record at byte offset 72.

The subtraction is displayed as signed integer arithmetic. The supplied material does not establish a portable overflow rule. Acceptance claims involving a result outside the signed 32-bit range are therefore **documented_only**. For values whose subtraction is representable, the written value is the selected entry minus 20.

This write occurs after the initial template-transfer call and before either allocation-like call.

### Mode 0

For mode 0, the function:

- Calls F-8157a180d901 with the request value 544, or hexadecimal 0x220.
- Passes its returned 32-bit value to F-7f6becd152e6.
- Supplies F-7f6becd152e6 with the literal zero, both forwarded arguments, and the initial temporary record.

No branch-local replacement record is prepared on this path.

The table selector must be 0 on this path, irrespective of the flag byte. Nevertheless, the flag byte is still read.

There is no check between the allocation-like return and the setup call. A zero or other failure-indicating return, if such a convention exists, is forwarded unchanged.

### Nonzero mode

Every nonzero mode follows the alternate setup path. Before allocating, the function places five consecutive 32-bit fields in temporary storage:

| Offset relative to the alternate record base | Assigned value |
|---|---|
| 104 | 30 |
| 108 | A 32-bit value read from a separate global source |
| 112 | 2 |
| 116 | 25 |
| 120 | 5 |

These assignments occur in the listed order.

The function then requests a 104-byte transfer from the initial temporary record to the alternate temporary record. Consequently, under ordinary byte-transfer semantics, the table-derived field at offset 72 is carried into the alternate record.

After the transfer returns, the function writes the 32-bit value 8 at offset 48 of the alternate record. This explicit write takes precedence over whatever the transfer placed at that position.

The function next reads a separate global request value and supplies it to F-8157a180d901. Unlike the zero-mode request, this request value is not a literal established by the supplied material.

It passes the allocation-like result to F-4a73b9be0f3a, together with the literal zero, both forwarded arguments, and the alternate record address.

Mode values such as 2 and −1 therefore use F-4a73b9be0f3a, but select table entry 0. Mode 1 uses the same setup dependency and selects table entry 1 only if flag bit 0 is set.

### Common final operation

After the selected branch setup dependency returns, the function performs a common operation:

- Requests a 104-byte transfer from a second template source into a separate temporary record.
- Calls F-8157a180d901 with 560, or hexadecimal 0x230.
- Calls F-60fe53f7ab39 with that result, the literal zero, both forwarded arguments, and the second-template record address.

This operation is not skipped based on a setup return value. The function does not inspect such a value.

The second template transfer occurs after the branch setup call. Thus, if an earlier dependency changes the second template’s backing storage, the later transfer may observe that change. The function does not snapshot both templates at entry.

Normal completion then returns without an explicit result.

### Temporary-storage layout

The supplied declarations must not be interpreted as independent, adequately sized arrays. The requested transfers exceed two displayed array extents.

The recoverable layout relationships are:

- The initial destination has a displayed extent of 72 bytes, but receives a 104-byte transfer request.
- Its explicitly replaced 32-bit field is at offset 72, immediately after that displayed extent.
- The alternate destination has a displayed extent of 48 bytes, but receives a 104-byte transfer request.
- Its explicit value 8 is written at offset 48.
- The alternate path’s five additional words occupy offsets 104 through 123.
- The final common record has a displayed extent of 104 bytes and receives a 104-byte transfer request.

These relationships establish the relevant spans and explicit field positions. They do not establish the meaning or validity of every byte covered by the larger transfer requests.

The five alternate-path fields are contiguous with the transferred 104-byte span. That supports an interpretation of a larger composite record, but the function itself does not establish how many bytes F-4a73b9be0f3a reads.
