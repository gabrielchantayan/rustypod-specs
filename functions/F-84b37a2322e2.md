# F-84b37a2322e2

## Purpose

F-84b37a2322e2 submits a requested amount of data through a context-associated resource selected by a 32-bit selector.

The function has two paths:

- **Nonzero mode:** admit at most one resource-capacity-sized request, submit it, and return the selected resource index through an output word.
- **Zero mode:** submit capacity-limited chunks, consult a completion dependency after each successful submission, and accumulate reported progress through the output word.

These descriptions identify the visible control flow. Interpreting the paths as “asynchronous” and “synchronous,” or interpreting the resource as a particular device or endpoint, is inferred intent rather than established behavior.

The return value is a status, not a byte count. The output word has mode-dependent meaning: a selected index in nonzero mode, and accumulated progress in zero mode.

## Interface

The interface has six inputs and one 32-bit status result.

| Input | Representation | Established use |
|---|---|---|
| Context | 32-bit address-like value | Passed to dependencies; a word at byte offset `0x34` is read for each submission. |
| Selector | Unsigned 32-bit word | Its low seven bits control initial eligibility. The complete word is passed to selection, preparation, and submission dependencies. |
| Data address | 32-bit address-like value | Passed to submission; advanced by reported progress in zero mode. |
| Requested amount | Unsigned 32-bit word | Governs admission, chunk size, and remaining work. |
| Output address | Address of a writable 32-bit word | Initialized after admission; subsequently holds an index or accumulated progress. |
| Mode | 32-bit integer | Zero selects the iterative completion path; every nonzero value selects the single-submission path. |

The returned status is a 32-bit integer:

- `-1` represents explicit local admission failure.
- `0` represents one of several successful or non-error exits described below.
- A nonzero submission or completion status is returned unchanged.

A returned `-1` cannot by itself distinguish local rejection from a dependency returning the same status.

### Resource record layout

Selection identifies an entry in a table with a **24-byte stride**. The function uses these fields relative to the selected record:

| Byte offset | Width | Access |
|---|---:|---|
| `0x08` | 32 bits | Written with zero before each submission. |
| `0x0C` | 32 bits | Read once as capacity during admission. |
| `0x13` | 8 bits | Read once as an eligibility indicator. |
| `0x14` | 8 bits | Written with one before each submission. |

The eligibility indicator and capacity must both be nonzero. Their names describe their use here, not independently established meanings.

### Memory and dependency preconditions

For defined, successful execution, the selected record, context field, output word, and memory accessed by dependencies must be valid for their respective operations. The function does not visibly validate these addresses.

In particular:

- A null or invalid output address is not made safe by requesting zero work. An admitted zero-length request still writes zero to the output word.
- The function does not establish how much data memory a submission dependency may access.
- A successful completion dependency must supply a usable 32-bit residual value for progress accounting.
- Successful selection must identify an accessible record. No local bounds check is visible.

No non-aliasing restriction is checked. If the output word overlaps the context, resource record, or submitted memory, writes can affect subsequent behavior. The ordinary descriptions below assume those locations do not overlap in behavior-changing ways; the function does not enforce that assumption.

## Behavior

### 1. Initial eligibility and selection

The function first examines the selector’s low seven bits.

If all seven are zero, it returns `-1`. It does not call a dependency or access the output word on this path. Nonzero higher selector bits do not compensate for zero low-seven bits.

Otherwise, it calls F-36a285714182 with the context and complete selector.

A selection result of `0xFFFFFFFF` causes immediate rejection with `-1`. No selected-record field is read on that path.

For any other selection result, the function computes the selected-record address from the table base plus the result multiplied by 24. It then:

1. Reads the byte at record offset `0x13`.
2. If that byte is nonzero, reads the 32-bit capacity at offset `0x0C`.
3. Rejects if either value is zero.
4. In nonzero mode only, rejects if the requested amount exceeds capacity, using an unsigned comparison.

All these rejection paths leave the output word untouched by this function. Dependencies already called may have their own effects.

The selected index, record address, and capacity are retained for subsequent processing. The function does not reselect or reread capacity for later chunks.

### 2. Preparation and output initialization

After admission, the function calls F-43fd78cbcdfd with:

- The context.
- The complete selector.
- The selected index.

No returned status is tested.

It then writes zero to the output word.

The supplied representation also conditionally assigns `-1` to a provisional status when the requested amount has bit 31 set. This does **not** establish rejection of such amounts: a nonzero request proceeds to submission, whose result replaces that status. The only immediate return after initialization is for an exactly zero requested amount, for which bit 31 is clear.

If the requested amount is zero, the function now returns `0`. Thus an admitted zero-length request still performs selection, record eligibility checks, preparation, and output initialization, but performs no submission.

### 3. Chunk submission

For each nonzero remaining amount, the function chooses the smaller of:

- The remaining amount.
- The cached capacity.

This comparison is unsigned. Both values are nonzero at the first submission, so the chosen chunk is nonzero.

The following observable operations occur in order:

1. Call F-338d16f9ce72 with the context.
2. Write a 32-bit zero at selected-record offset `0x08`.
3. Write an 8-bit one at selected-record offset `0x14`.
4. Read the 32-bit word at context offset `0x34`.
5. Call F-855e5285ebdd with that word, the complete selector, the current data address, and the chunk amount.
6. Call F-1333331b2da1 with the context.
7. Inspect the submission status.

The context field is read anew for every submission. It is not cached during initial admission.

F-1333331b2da1 is called even when submission returns a nonzero status. On such a status, the function returns it immediately. It does not call the completion dependency or account progress for that submission.

The roles of F-338d16f9ce72 and F-1333331b2da1 as lock/unlock or enter/leave operations are plausible but unproven. The established contract is their position around the record writes and submission.

### 4. Nonzero-mode completion

After a successful submission in nonzero mode, the function writes the selected index to the output word and returns `0`.

There is no call to F-aa4f0ee63909 on this path. Consequently, return zero establishes successful submission according to F-855e5285ebdd, not independently observed completion of data transfer.

The output index can itself be zero. Its meaning depends on mode and return status, not on being nonzero.

### 5. Zero-mode completion and accounting

After each successful submission in zero mode, the function calls F-aa4f0ee63909 with:

- The context.
- The selected index.
- The address of a temporary 32-bit residual word.

It derives progress by subtracting the residual from the submitted chunk amount at 32-bit width.

If the completion status is nonzero, that status is returned. The current chunk does not cause a data-address advance, output increment, remaining-amount reduction, or call to F-d7be9cfb4000. Earlier progress remains, subject to any dependency writes.

On completion status zero, the function performs these updates in order:

1. Advance the current data address by the derived progress.
2. Read the output word and write back its value plus that progress.
3. Reduce the remaining amount by that progress.
4. Call F-d7be9cfb4000 with the progress and cached capacity.
5. Inspect the dependency’s secondary return channel.

A nonzero secondary result causes an immediate return of `0`, even if the remaining amount is nonzero.

A zero secondary result permits another iteration. At the beginning of that iteration, a zero remaining amount causes return `0`; otherwise, another chunk is submitted.

The ordinary return value of F-d7be9cfb4000 is not used in the visible decision.

### 6. Widths, arithmetic, and termination

Amounts, capacity, selector, selected index, and output updates operate on 32-bit words. The eligibility field is one byte.

For the represented machine-width behavior, the relevant arithmetic is low-32-bit arithmetic:

- Selected-record displacement is the index multiplied by 24.
- Progress is chunk amount minus residual.
- Data-address advancement adds progress.
- Accumulated output adds progress.
- Remaining amount subtracts progress.

There is no visible check that residual is at most the submitted chunk. A larger residual therefore does not produce a local validation error; it produces a wrapped subtraction result, which affects subsequent accounting if completion reports success.

Similarly, there is no visible overflow check for output accumulation or address advancement.

Termination depends partly on dependency results:

- A full residual gives zero progress.
- If completion keeps succeeding with zero progress and F-d7be9cfb4000 keeps producing a zero secondary result, the visible loop has no progress-based termination safeguard.
- A nonzero secondary result can terminate successfully without exhausting the request.

Interpreting F-d7be9cfb4000 as a division/remainder operation would explain a boundary-sensitive stopping rule, but that interpretation is not established by this function alone.

## Side effects

Direct effects are:

- Reading the selected record’s eligibility byte and, conditionally, its capacity.
- Initializing the output word after preparation.
- Clearing record offset `0x08` and setting offset `0x14` before every submission.
- Reading context offset `0x34` for every submission.
- Writing the selected index in nonzero mode after submission succeeds.
- Reading and updating accumulated progress in zero mode after completion succeeds.

No direct allocation, deallocation, copying of payload data, or restoration of the record fields is visible.

That does not establish ownership or lifetime behavior of dependencies. The function passes addresses and context values to opaque dependencies; they may access memory or change shared state according to contracts not supplied here.

The cached capacity and selected-record address are not refreshed after dependency calls. Conversely, the context field and output word are explicitly reread at their documented use points. A dependency that changes these locations can therefore affect later operations.

An error return does not roll back earlier effects. Record writes, preparation, successful earlier chunks, and dependency effects can remain observable.

## Acceptance examples

These are conditional contract examples derived from static evidence, not executed tests. Unless stated otherwise, dependencies do not alter the relevant memory beyond the described effects.

1. **Selector rejection:** With selector `0x00000080`, the low seven bits are zero. The result is `-1`, with no dependency calls and no output write.

2. **Selection failure:** With eligible low selector bits, if F-36a285714182 returns `0xFFFFFFFF`, the result is `-1`. No record eligibility or capacity read follows.

3. **Disabled record:** If selection succeeds but the byte at offset `0x13` is zero, the result is `-1`. Capacity is not read, preparation is not called, and the output remains untouched.

4. **Mode-dependent capacity admission:** With capacity 64 and request 65, nonzero mode rejects before preparation. Zero mode admits and begins with a 64-unit chunk.

5. **Admitted zero request:** With valid selection, nonzero eligibility, and capacity 64, request zero causes preparation, output initialization to zero, and return zero. No submission occurs in either mode.

6. **Successful nonzero-mode submission:** With selected index 3, capacity 64, request 20, and successful submission, the output becomes 3 and the result is zero. No completion call occurs.

7. **Submission failure:** If submission returns status 7, F-1333331b2da1 still runs before status 7 is returned. With no earlier progress or dependency interference, the initialized output remains zero.

8. **Multi-chunk zero-mode progress:** With capacity 64, request 100, residual zero on both completions, and zero secondary results from F-d7be9cfb4000, submissions have amounts 64 and 36. The second data address is the original address plus 64, the output ends at 100, and the result is zero.

9. **Early successful stop:** With capacity 64, request 100, and residual 4 for the first chunk, progress is 60. If F-d7be9cfb4000 produces a nonzero secondary result, the function returns zero with output 60 despite 40 units remaining.

10. **Completion failure after earlier progress:** If an earlier chunk accounts 64 and a later completion returns status 9, the result is 9. The failed chunk adds no progress; the output remains 64 absent dependency interference.

11. **Out-of-range residual:** For a 16-unit chunk and residual 17, the progress calculation yields `0xFFFFFFFF` at 32-bit width. No local residual-range rejection occurs. Subsequent behavior depends on the resulting wrapped accounting and dependency results.

## Uncertainties

The following are **documented_only**:

- The resource’s domain meaning, payload direction, and units of measurement.
- The table’s valid index range and addressability guarantees.
- Exact ownership and lifetime obligations for submitted memory.
- Whether successful submission means queued, accepted, or completed work.
- Whether the surrounding dependency calls provide synchronization.
- Whether preparation or other dependencies mutate the table, context, output, or payload.
- The residual contract, particularly bounds and initialization on failure.
- The meaning of F-d7be9cfb4000’s secondary result.
- Behavior of invalid addresses and fault handling outside the visible function.
- A portable language-level signed-overflow interpretation. The arithmetic contract above describes represented 32-bit machine operations, not a guarantee for a rewritten implementation in another language.
