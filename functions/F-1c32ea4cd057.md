# F-1c32ea4cd057

## Purpose

F-1c32ea4cd057 selects one 24-byte record from a caller-supplied pool state and partially initializes that record. It preferentially removes a record from a reusable-record chain. If that chain is empty, it consumes the next unused record in the current backing region, allocating a new region when the current region is exhausted.

The function has no explicit return value. Its externally visible results are changes to the supplied state, writes to the selected record, and, on the growth path, calls to F-871e64ddc6de and construction of a new region header.

“Pool,” “record,” and “reusable-record chain” describe the apparent organization of the observed fields. They are inferred intent, not evidence of a particular public container API, object lifetime model, or allocator ownership policy.

## Interface

### Input and result

The function receives one address identifying a writable state structure. It does not receive a size, record index, or output-address argument.

The supplied representation uses 32-bit words and 32-bit address values. The accessed state occupies at least 16 bytes:

| Byte offset | Width | Behavioral role |
|---|---:|---|
| 0 | 4 bytes | Address of the most recently linked region header, or zero |
| 4 | 4 bytes | Address of the first reusable record, or zero |
| 8 | 4 bytes | Address of the next unused record in the active region |
| 12 | 4 bytes | End address used to detect exhaustion of the active region |

The function does not explicitly return either the selected record address or a status. A caller may be able to derive the selected record from its knowledge of the prior state, but that is not a separately established return contract.

### Region-header layout

Each newly allocated header is requested as a 12-byte allocation and receives these fields:

| Byte offset | Width | Value written |
|---|---:|---|
| 0 | 4 bytes | The state’s region-header address read after both allocation calls |
| 4 | 4 bytes | The selected record capacity |
| 8 | 4 bytes | The address returned by the backing-storage allocation |

For an existing region header, this function reads only the capacity at offset 4.

### Record layout

Records have a stride of 24 bytes. Within the selected record, the function writes:

| Byte offset | Width | Result |
|---|---:|---|
| 0 | 1 byte | Zero |
| 4 | 4 bytes | Zero |
| 8 | 4 bytes | Zero |
| 12 | 4 bytes | Zero |

For a reusable record, the 32-bit field at offset 12 is first read as the address of the next reusable record.

Bytes 1–3 and 16–23 are not explicitly written. The function therefore does not establish a fully zeroed record, even though several fields become zero.

### Preconditions for ordinary successful use

The state address must permit the indicated reads and writes. Any selected record must permit a 32-bit read at offset 12 when obtained from the reusable chain, and must permit the initialization writes listed above.

If growth is required and the region-header address is nonzero, that address must permit a 32-bit capacity read at offset 4. The two calls to F-871e64ddc6de must return addresses usable for the subsequent operations if execution is to complete normally.

The function performs no explicit validation of these conditions. It also does not validate alignment, consistency between the next-unused and end addresses, or the accessibility of a whole 24-byte record.

## Behavior

### 1. Prefer the reusable-record chain

The first state access reads the reusable-record address at offset 4.

If that value is nonzero:

1. The addressed record is selected.
2. Its 32-bit field at offset 12 is read.
3. That value is written to the state’s reusable-record field.
4. The selected record is partially initialized as described below.

This path does not read the next-unused address, end address, or region-header capacity. It makes no allocation calls and does not explicitly update the state’s region-header, next-unused, or end fields.

The chain is not checked for cycles or self-links. For example, a record whose offset-12 field points to itself leaves that same address in the reusable-record field, even though the selected record’s offset-12 field is subsequently cleared.

### 2. Otherwise select the next unused record

If the reusable-record address is zero, the function reads the next-unused address at state offset 8, then reads the end address at offset 12 and compares the two for equality.

If they differ, the next-unused address is selected directly. The function writes the selected address plus 24 to the state’s next-unused field, then partially initializes the selected record.

The check is equality only. An address beyond the recorded end does not trigger growth merely because it is beyond that end. Likewise, the function does not check that at least 24 bytes remain between the two addresses.

If the next-unused and end addresses are equal, the function follows the growth path.

### 3. Choose a new capacity

On the growth path, the function reads the region-header address at state offset 0.

If it is zero, the new capacity is 32 records.

Otherwise, the function reads the existing header’s 32-bit unsigned capacity and computes two candidates:

- Existing capacity plus 32.
- Existing capacity plus its unsigned right shift by one, plus its unsigned right shift by three.

All additions are 32-bit unsigned arithmetic. The larger candidate is selected using an unsigned comparison. In a tie, the shifted-sum candidate is selected, with no difference in the resulting capacity.

For values that do not overflow, the shifted-sum candidate is the existing capacity plus the integer parts of one-half and one-eighth of that capacity. It is not generally identical to rounding a single multiplication by 1.625.

There is no overflow detection or saturation. The comparison operates on already-wrapped 32-bit results. Consequently, the chosen capacity need not exceed the previous capacity for extreme inputs.

### 4. Allocate and link a new region

After choosing a capacity, the function makes two calls to F-871e64ddc6de, in this order:

1. A call with first argument 12 and second argument zero, whose result is used as a region-header address.
2. A call with first argument equal to the chosen capacity multiplied by 24, and second argument zero, whose result is used as the backing-storage address.

The allocation-size multiplication is 32-bit arithmetic and may wrap. There is no local check that the resulting byte count can hold the chosen number of records.

After the second call returns, the function performs these operations in order:

1. Write the backing-storage address into the new header at offset 8.
2. Read the state’s current region-header address and write it into the new header at offset 0.
3. Write the chosen capacity into the new header at offset 4.
4. Write the new header address into state offset 0.
5. Read the backing-storage address from the new header at offset 8.
6. Write that address plus the capacity-times-24 byte span into the state’s end field.
7. Write that address plus 24 into the state’s next-unused field.

The first record of the new backing region is selected for initialization.

The old region-header address stored in the new header is read after both dependency calls. It is not necessarily the same value used earlier to obtain the old capacity if a dependency call changes the supplied state through an alias or other means.

The function contains no cleanup or rollback path between these operations.

### 5. Partially initialize the selected record

All selection paths converge on the same explicit write sequence:

1. Write a 32-bit zero at record offset 4.
2. Write a 32-bit zero at record offset 8.
3. Write a 32-bit zero at record offset 12.
4. Write a one-byte zero at record offset 0.

The one-byte write occurs last. It must not be interpreted as a four-byte write or as a full-record clear.

State advancement or reusable-chain removal occurs before these record writes. No atomic transaction or synchronization mechanism is established by the supplied evidence.

## Side effects

### State changes

Under ordinary non-overlapping storage assumptions:

- Reusable-record selection changes only the reusable-record field of the state.
- Selection from existing unused storage changes only the next-unused field.
- Growth changes the region-header, end, and next-unused fields.
- Growth does not explicitly change the reusable-record field, which was observed as zero before that path was entered.

These statements describe explicit writes by this function. They do not assert that F-871e64ddc6de preserves the state or any globals.

### Record changes

The selected record receives three 32-bit zero writes and one byte-sized zero write. Other bytes retain whatever values their storage provides unless affected by aliasing or dependency behavior.

On the reusable path, the former link value is consumed before its field is cleared. On the unused-storage paths, the offset-12 field is cleared without first being read.

### Allocation and ownership

Growth requests two allocations and retains their returned addresses in the pool structure. Existing headers are linked behind the new header; no explicit release operation appears.

This establishes neither who owns the returned allocations nor who must eventually release them. The lifetime and release protocol remain unknown.

### Failure behavior

There are no explicit error returns, null-result checks, capacity-overflow checks, or recovery actions.

If F-871e64ddc6de returns normally with unusable addresses, subsequent accesses may fail or affect unintended storage. If the dependency throws, terminates, transfers control elsewhere, or otherwise does not return normally, that behavior is outside the locally established contract.

The function also does not prevent invalid state from producing writes through zero, wrapped, stale, or out-of-range addresses.

## Acceptance examples

These examples are conditional static acceptance criteria, not reports of execution. Unless stated otherwise, they assume valid, suitably aligned, non-overlapping storage; ordinary returning dependency behavior; and no concurrent or dependency-induced state mutation.

### Reusable record takes precedence

Given a nonzero reusable-record address whose offset-12 field contains a second record address:

- The first record is selected.
- The state’s reusable-record address becomes the second address.
- No allocation call occurs.
- The next-unused and end fields are not consulted by this function.
- The selected record receives zero writes at offsets 4, 8, 12, then 0, with the widths specified above.

This remains the selected path even if the unused-storage fields would otherwise indicate exhaustion.

### Existing unused storage

Given a zero reusable-record address and distinct next-unused and end addresses:

- The original next-unused address is selected.
- The next-unused field advances by 24.
- No allocation call occurs.
- The four initialization writes target the selected record.

No capacity-header read is required on this path.

### First region

Given a zero reusable-record address, equal next-unused and end addresses, and a zero region-header address:

- The chosen capacity is 32.
- The dependency calls request 12 and 768 bytes, in that order.
- The new header records capacity 32 and the backing-storage address.
- With no intervening state mutation, the header’s previous-header field is zero.
- The state’s end address becomes backing address plus 768.
- The next-unused address becomes backing address plus 24.
- The record at the backing address is partially initialized.

### Growth using the minimum increment

Given exhaustion and an existing capacity of 32:

- The increment candidate is 64.
- The shifted-sum candidate is 52.
- The chosen capacity is 64.
- The backing-storage request is 1,536 bytes.

### Growth using the shifted-sum candidate

Given exhaustion and an existing capacity of 64:

- The increment candidate is 96.
- The shifted-sum candidate is 104.
- The chosen capacity is 104.
- The backing-storage request is 2,496 bytes.

### Overflow is not corrected

Given an existing capacity of 4,294,967,295:

- The increment candidate wraps to 31.
- The shifted-sum candidate wraps to 2,684,354,557.
- The latter is selected by the unsigned comparison.
- Multiplication by 24 wraps to a backing-storage request of 4,294,967,224 bytes.

Acceptance requires preserving this arithmetic behavior, not replacing it with saturation, rejection, or a wider mathematical calculation.

### Partial initialization

Given a selected record with known preexisting bytes:

- Bytes 0, 4–7, 8–11, and 12–15 become zero.
- Bytes 1–3 and 16–23 are not explicitly changed by this function.

### Inconsistent boundary state

Given an empty reusable chain and a next-unused address that differs from, but is beyond, the end address:

- The function takes the existing-unused-storage path rather than the growth path.
- It advances the next-unused address and attempts the record writes.

Such a state is unsafe for normal use; the example captures the absence of a range check.
