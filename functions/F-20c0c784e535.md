# F-20c0c784e535

## Purpose

The established behavior is a two-path contract:

- If object acquisition returns null, the function returns the 32-bit value `0xffffffff`.
- If acquisition returns a non-null object, the function invokes an object-selected operation on the temporary record, obtains its result from F-cd21e6662a3e, invokes F-ee5919ca4be6 on that record, and returns the previously obtained result.

The temporary record initially contains the four input words in their original order. The object-selected operation receives both the record address and the acquired object, plus a separate copy of the second input word.

This structure suggests a preparation, result-production, and finalization workflow. Those semantic roles are inferred intent, not established dependency contracts. In particular, the available evidence does not establish that finalization frees memory, that the result represents success, or that the acquired object is owned by this function.

On this path, it does not invoke:

- The object-selected operation.
- F-cd21e6662a3e.
- F-ee5919ca4be6.

### Non-null acquisition and indirect dispatch

If acquisition returns a non-null value, the function uses it as an object address.

The dispatch target is obtained through two dependent reads:

- The object’s first 32-bit word supplies a dispatch-table address.
- The entry at byte displacement `0x150` from that address supplies the operation to invoke.

`0x150` is a byte displacement of 336, not a count of table entries. In a table of four-byte entries, it corresponds to zero-based entry 84; that indexing interpretation is secondary to the established byte displacement.

1. The address of the temporary record’s first word.
2. The acquired object address.
3. The original second input word.

No input-derived arithmetic is performed to locate the dispatch entry. No visible null check or validity check is applied to the dispatch-table address or the selected entry.

Mutations made through that address may be observed by later dependencies because all three receive the same address, with no intervening record reinitialization.

The dependencies receive its address only during execution of this function. The wrapper does not establish a supported lifetime for that address after return. A dependency that retains it would require an external justification not present in the supplied evidence.
