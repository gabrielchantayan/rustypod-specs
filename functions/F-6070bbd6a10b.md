# F-6070bbd6a10b

## Purpose

F-6070bbd6a10b conditionally searches 205 candidate positions for a numeric key. An external entry gate and the requested key determine whether the search begins. Once admitted, the search visits positions in ascending order and returns the first position whose candidate key equals the requested key.

The result is not an unambiguous success indicator. Zero can mean that the search was skipped or that position zero matched. A fully completed search without a match returns 2,147,483,647.

The established behavior is a gated, bounded lookup. Interpreting the gate as an initialization flag or the candidates as application records is inferred intent, not part of the established contract.

## Behavior

### Entry decision and access order

The function obtains the state-region base through the global reference and reads the gate before deciding whether the requested key is zero.

If the gate is zero, the function immediately returns zero. F-06d80ba0959e is not called.

If the gate is nonzero but the requested key is zero, the function also returns zero without calling the dependency.

Consequently, zero input does not bypass the state access. An unreadable gate does not become safe merely because the requested key is zero.

Any nonzero gate admits a nonzero requested key to traversal. The gate’s sign and magnitude otherwise have no effect. In particular, it is not used as a candidate count or search bound.

Only one gate-field read is established. The function does not recheck the gate during traversal.

### Candidate traversal and first-match rule

With a nonzero gate and nonzero requested key, the function visits positions 0 through 204, inclusive.

At each reached position, the relevant order is:

1. Invoke F-06d80ba0959e with the current position.
2. After that invocation returns, read the unsigned 16-bit key at byte offset 10 from its returned address.
3. Compare that key numerically with the requested key.
4. Return the current position immediately if they are equal.

A failed comparison advances traversal to the next position. After a failed comparison at position 204, traversal ends with the exhaustion result. Position 205 is never passed to the dependency.

The first equality wins. Once a match occurs, later positions are neither requested nor read by this function. Duplicate matching keys therefore select the lowest visited position, subject to the values actually read during that invocation.

The dependency call precedes the corresponding key read. The function does not obtain that key before calling the dependency. Changes the dependency makes to returned storage can therefore affect the comparison.

### Comparison width and key boundaries

The candidate key is interpreted as an unsigned 16-bit value and compared with the full requested key. The requested key is not narrowed to 16 bits.

This establishes the following boundaries:

- Candidate keys range from 0 through 65,535.
- A requested key greater than 65,535 cannot match any candidate key.
- A requested key of zero never reaches candidate comparison.
- A candidate key of zero cannot match a nonzero requested key.
- Matching low 16 bits alone are insufficient for equality.

An oversized requested key does not cause an early rejection after admission. With a nonzero gate, such an input still visits all 205 positions if every required dependency call and memory access completes normally.

### Exhaustion and arithmetic

The exhaustion result is 2,147,483,647, represented by hexadecimal 0x7fffffff. It differs from every successful position and from the maximum 32-bit unsigned value.

The position starts at zero. Each failed comparison increments it by one. After the failure at position 204, the position becomes 205, which ends traversal.

Under the represented 32-bit unsigned model, this arithmetic does not overflow. The bound is fixed at 205 positions; neither the gate’s value nor any candidate field changes it.

### State changes during traversal

Admission depends on the initial gate read. If a dependency call later changes the gate to zero, that change does not trigger a gate-based stop in this function.

This does not imply that other state remains unchanged. F-06d80ba0959e may modify global state or candidate storage, and different invocations may return different addresses. The function makes no explicit snapshot, stability check, or synchronization arrangement.

Concurrency semantics and the visibility of unsynchronized external changes are unresolved. The access order described here is the order established by the supplied static representation, not a guarantee about arbitrary concurrent execution.
