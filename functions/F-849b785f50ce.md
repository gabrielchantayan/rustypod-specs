# F-849b785f50ce

## Purpose

F-849b785f50ce performs a gated, indexed candidate search. It obtains a bucket index from F-6afbe0364bb3, examines the bucket’s unsigned 16-bit candidate count, and tests candidates through F-9c95e8b5632c. It returns a 32-bit success indicator and, on success, stores the accepted candidate’s 32-bit value through an output address.

The bucket representation depends on its count:

- A zero count represents an empty bucket.
- A count of one means the bucket’s 32-bit slot directly contains the candidate.
- A count greater than one means the slot contains the address of a sequence of 32-bit candidates.

The search stops at the first candidate for which F-9c95e8b5632c returns nonzero.

These are established properties of the supplied static representation. The application-level meanings of the context, candidates, selector arguments, and acceptance predicate are unknown.

## Interface

### Inputs

The function receives four arguments:

| Argument | Role and established representation |
|---|---|
| Context address | An address used to read a flag word and two table-address fields. It is also passed unchanged to F-9c95e8b5632c. |
| First opaque value | A 32-bit value passed unchanged to both dependencies. This function does not directly dereference it. |
| Second opaque value | A 32-bit value passed twice to F-6afbe0364bb3 and once to F-9c95e8b5632c. This function does not directly dereference it. |
| Output address | An address passed twice to F-6afbe0364bb3. On successful candidate acceptance, this function writes one 32-bit candidate value there. |

No constness, non-aliasing, or ownership guarantees are established for these arguments.

### Context layout

The following context-relative fields are accessed:

| Byte offset | Width | Observed use |
|---|---:|---|
| +4 | 32 bits | Flag word; mask `0x00000004` controls whether lookup is attempted. |
| +20 | 32 bits | Candidate-slot table address. Initially checked for zero, then read again after the selector returns. |
| +24 | 32 bits | Candidate-count table address, read after the selector returns. |

The initial +20 read is conditional on the flag test. The +24 field is not read on the disabled path or when the initial +20 value is zero.

No other context fields are directly accessed by this function. Dependencies may access additional state.

### Table layout

For a selector result interpreted as an index:

- The candidate-slot entry is at the slot-table address plus four times the index.
- The candidate-count entry is at the count-table address plus two times the index.
- Slot entries occupy four bytes.
- Count entries occupy two bytes and are interpreted as unsigned values from 0 through 65,535.

When the count exceeds one, the selected slot is interpreted as an address. Candidates are read at successive four-byte offsets from that address.

The slot’s interpretation is determined solely by the count. A slot containing zero is not independently treated as an empty bucket.

### Return value and output

The function returns a 32-bit value:

- **1:** A candidate was accepted, and its value was written to the output address.
- **0:** Lookup was bypassed, the bucket was empty, or all tested candidates were rejected.

The return value does not expose a dependency’s original nonzero result.

A return of zero does **not** guarantee that the output storage remains unchanged. F-6afbe0364bb3 receives the output address, and either dependency may have other access to aliased storage.

### Preconditions for defined execution

On every executed path, the addresses actually read or written must designate suitably accessible storage:

- The context flag field must be readable.
- Additional context fields and table entries must be readable when their corresponding branches execute.
- Candidate-list storage must remain readable for each attempted list access.
- The output destination must be writable when this function accepts a candidate.
- Dependencies must receive arguments valid under their own, unspecified contracts.

There is no local bounds check on the selector result, no local null check on the count-table address, and no local null check on a multi-candidate list address. Arithmetic overflow, invalid addressing, misalignment, and dependency failures have no defined recovery behavior in the supplied evidence.

## Behavior

### 1. Gate lookup using the context

The function first reads the 32-bit flag word at context offset +4.

If mask `0x00000004` is clear, it returns zero. It does not directly read either table-address field, invoke either dependency, or write through the output address on this path.

If that bit is set, the function reads the 32-bit field at context offset +20. If this value is zero, it returns zero without invoking either dependency.

Other flag bits do not affect the visible decision. This function does not subsequently reread the flag word.

### 2. Obtain a bucket index

When the flag is enabled and the initial slot-table address is nonzero, the function calls F-6afbe0364bb3 with five arguments, in this order:

1. The first opaque value.
2. The second opaque value.
3. The same second opaque value again.
4. The output address.
5. The same output address again.

The duplicated positions receive identical values, not distinct copies of the referenced storage.

The dependency’s result is used as the bucket index. No result value is treated as a selector failure before table addressing. In particular, there is no explicit rejection of a negative index or an index exceeding a table’s extent.

After the dependency returns, the function rereads the context field at +20. The earlier nonzero value serves only as an entry gate; it is not the table base used for subsequent addressing.

Consequently, if F-6afbe0364bb3 changes the +20 field, the later lookup uses the changed value. No second nonzero check is performed.

### 3. Locate the slot and capture the count

Using the reread slot-table address and the selector result, the function establishes the address of the four-byte slot for that index.

It then reads the count-table address from context offset +24 and reads the selected unsigned 16-bit count.

The count is retained for the rest of this invocation. This function does not reread the count entry during candidate testing.

Establishing the slot address does not itself read the slot’s contents. If the captured count is zero, the function returns zero without reading a candidate slot or invoking F-9c95e8b5632c.

### 4. Test a single-candidate bucket

If the captured count is exactly one:

1. The function reads the selected slot’s four-byte contents as the candidate value.
2. It calls F-9c95e8b5632c with the context address, candidate value, first opaque value, and second opaque value, in that order.
3. If the dependency returns nonzero, the function writes the previously read candidate value to the output address and returns one.
4. If the dependency returns zero, the function returns zero without making its own output write.

The candidate is not reread after the dependency returns. A dependency mutation of the slot does not change the candidate written for that successful attempt.

A zero candidate value is still submitted to F-9c95e8b5632c; it is not rejected locally.

### 5. Test a multi-candidate bucket

If the captured count is greater than one, the function examines candidate positions in ascending order, beginning at position zero and ending, if necessary, at count minus one.

For each attempted position:

1. It reads the four-byte contents of the already selected slot and interprets those contents as the current candidate-list address.
2. It reads a four-byte candidate at that address plus four times the position.
3. It calls F-9c95e8b5632c with the context address, candidate value, first opaque value, and second opaque value.
4. A nonzero result causes the saved candidate value to be written to the output address, followed by an immediate return of one.
5. A zero result advances to the next position.

If every candidate is rejected, the function returns zero.

The **selected slot address remains fixed**, but the **list address stored in that slot is reread for every attempted position**. Thus, a rejected predicate call can change which list supplies the next candidate by modifying the selected slot.

The traversal position is not reset when the list address changes. For example, after rejecting position zero from one list, a changed slot causes position one—not position zero—to be read from the replacement list.

Changes to the context’s table-address fields during candidate testing do not redirect the already established slot address. Changes to the count entry do not alter the captured iteration limit.

### 6. Integer-width and ordering constraints

The count is zero-extended from 16 bits. A multi-candidate search therefore attempts at most 65,535 predicate calls.

The traversal position is represented as a 32-bit unsigned value. Over the permitted count range, its largest candidate-byte displacement is 262,136, corresponding to position 65,534 multiplied by four. The position counter and this displacement do not overflow 32 bits.

This does not establish safety for adding the displacement to an arbitrary list address. Likewise, the selector result is not range-checked before multiplication by four or two. Exact behavior for overflowing index arithmetic or invalid derived addresses is not established and must not be replaced by an assumed wraparound contract.

Observable ordering includes:

- The initial gate reads precede the selector call.
- The post-selector slot-table read precedes the count-table read.
- The count is read before any candidate slot contents.
- Each candidate read precedes its predicate call.
- A successful predicate call completes before this function writes the accepted candidate.
- No later candidate is read after acceptance.

## Side effects

### Direct effects

The function directly performs:

- Reads of the context fields needed by the selected path.
- One selected count-entry read after a successful entry gate.
- Candidate-slot and candidate-list reads as described above.
- Exactly one four-byte output write on a normally completing successful path.

It does not directly allocate, free, retain, or release memory. No ownership transfer is established by its own operations.

### Dependency effects and aliasing

Dependency side effects are not constrained by the supplied evidence.

F-6afbe0364bb3 receives the output address twice and may alter accessible storage before the bucket lookup. F-9c95e8b5632c receives the context and opaque values; those values or global state may provide further access to relevant memory.

The contract therefore does not assume either dependency:

- Preserves context fields, tables, candidates, or output storage.
- Preserves global state.
- Leaves memory allocated or accessible.
- Avoids allocation or release.
- Returns normally.

If a dependency invalidates memory needed by a later operation, this function provides no visible safeguard.

Aliasing is not checked. For example, output storage may overlap a slot or context field. On success, the final candidate write may consequently mutate lookup-related storage. The function returns immediately after that write.

There is no transactional rollback: a zero return does not undo changes made during dependency calls.

## Acceptance examples

These examples are conditional static expectations, not runtime test results. Unless stated otherwise, they assume valid addressing, normal dependency returns, and no relevant dependency mutations.

1. **Lookup disabled.**  
   Given a context whose flag word does not contain mask `0x00000004`, the result is zero. Neither dependency is called, and neither table-address field is directly read.

2. **Enabled but initially missing slot table.**  
   Given the flag bit set and the initial +20 field equal to zero, the result is zero. The selector is not called, and the count-table field is not read.

3. **Empty selected bucket.**  
   Given a passing entry gate, a valid selector result, and a selected count of zero, the selector is called once. No candidate-slot contents are read, no predicate is called, and the result is zero.

4. **Direct candidate accepted.**  
   Given a selected count of one and slot value 42, a nonzero predicate result causes a four-byte value of 42 to be written to the output destination and a return of one.

5. **Direct candidate rejected.**  
   With the same bucket but a zero predicate result, the function returns zero without its own output write. Output preservation additionally requires that dependencies did not modify that storage.

6. **First accepted list candidate wins.**  
   Given a count of three and an unchanged list containing 10, 20, and 30, predicate results zero then nonzero cause calls for 10 and 20 only. The output receives 20; the third candidate is not read.

7. **Selector changes the table base.**  
   Given an initially nonzero +20 field, if the selector replaces it with another valid table address, the function selects its slot from the replacement table. It does not continue using the initially observed base.

8. **Predicate changes the selected list address.**  
   Given a count of three, suppose position zero is rejected and that predicate call changes the selected slot to a replacement list address. The next attempt reads position one from the replacement list.

9. **Predicate changes the count entry.**  
   Given a captured count of three, changing the count entry to zero during the first rejected predicate call does not shorten the search. The function continues toward the original limit, provided subsequent accesses remain valid.

10. **Candidate storage changes during acceptance.**  
    If a predicate accepts a candidate but changes the storage from which it was read, the output still receives the candidate value captured before the call.

11. **Zero-valued candidate.**  
    A direct slot value of zero with count one is passed to the predicate. If accepted, zero is written to the output and the function returns one.
