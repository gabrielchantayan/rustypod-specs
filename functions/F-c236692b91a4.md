# F-c236692b91a4

## Purpose

F-c236692b91a4 coordinates two indirect operations on an object referenced by a caller-provided record. It supplies temporary storage to the first operation, conditionally writes a one-byte marker into the caller-provided record, invokes the second operation, and then passes the temporary storage to a final dependency.

The established behavior is an ordered sequence of calls and a conditional byte write. The meaning of the operations, the marker, and the temporary contents is not established. In particular, the evidence does not establish that the first operation acquires a resource, that the final dependency releases one, or that the marker represents successful completion.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

The function accepts four arguments and has no explicit return value:

| Argument | Established representation | Observable use |
|---|---|---|
| Record address | Pointer to storage whose leading element is a 32-bit value | Its leading value supplies an object address for each indirect call. The byte at offset 13 from the record address may be written. |
| First forwarded value | Opaque 32-bit value | Passed unchanged to both indirect operations. |
| Mode value | 32-bit integer | Compared with exactly 1, then passed unchanged to the second indirect operation. |
| Second forwarded value | Opaque 32-bit value | Passed unchanged to the second indirect operation. |

The recovered operations use a 32-bit address model: object addresses and dispatch-table addresses are read through 32-bit storage, and address arithmetic is represented with 32-bit integer conversions. This is not evidence for a portable interface using native-width pointers on a different architecture.

The function also provides a temporary storage region of 24 bytes for the duration of its invocation. Its structure, required alignment, and contents are not established.

### Record and object layout

The visible accesses require the following layout relationships:

- At byte offset 0 in the caller-provided record is a 32-bit object-address value.
- At byte offset 0 in the referenced object is a 32-bit dispatch-table-address value.
- A callable target is obtained from byte offset `0x170`, or 368, in that dispatch table for the first indirect operation.
- A callable target is obtained from byte offset `0xe0`, or 224, in the dispatch table used for the second indirect operation.
- When the mode equals 1, the function writes the byte value 1 at byte offset `0x0d`, or 13, in the caller-provided record.

The marker belongs to the record addressed by the first argument, not necessarily to the referenced object. Their relationship beyond the leading object-address value is unknown.

### Preconditions

For a defined normal execution, all memory accesses and indirect calls actually reached must be valid. This includes:

- A readable leading 32-bit value in the record whenever a receiver is resolved.
- A readable dispatch-table address at the beginning of each resolved object.
- A valid callable target at each selected dispatch-table offset.
- Writable storage at record offset 13 when the mode equals 1.
- Compatibility between each dependency and the arguments it receives.

The function performs no visible null checks, bounds checks, target validation, or mode validation. Additional requirements imposed by the dependencies are documented_only.

## Behavior

### 1. Initial temporary-storage call

The function first invokes F-ba5a4c1e0746 with:

1. The address of the 24-byte temporary region.
2. Zero.
3. Zero.

There is no visible initialization of the temporary region before this call. Any defined initial contents required by later operations must therefore come from this dependency or from requirements not available in the evidence.

No return value from F-ba5a4c1e0746 is visibly tested or used. If it returns normally, execution proceeds.

Although this call occurs before the explicit record accesses described below, it must not be assumed to leave the record, globals, or other reachable state unchanged. Its effects are not supplied.

### 2. First receiver resolution and indirect operation

After F-ba5a4c1e0746 returns normally, the function resolves the first indirect target through these dependent reads:

1. Read the leading 32-bit object-address value from the caller-provided record.
2. Read the dispatch-table address from the beginning of that object.
3. Obtain the callable target at dispatch-table byte offset 368.

The selected target is invoked with:

1. The resolved object address as receiver.
2. The first forwarded 32-bit value.
3. The address of the temporary region.

The temporary address is the same one passed to F-ba5a4c1e0746. The wrapper neither interprets the region nor visibly reads its contents between these calls.

Any result of this indirect operation is ignored by the visible wrapper. A normal return leads to the mode check.

### 3. Conditional marker write

The function compares the mode value with exactly 1.

- If equal, it stores the one-byte value 1 at record offset 13.
- Otherwise, it performs no direct write to that byte at this step.

The condition is equality, not a general nonzero test. A mode of 2 does not select the write. Neither does a negative mode.

This is a byte store, not a 32-bit assignment or a bitwise update. The direct effect is to replace the complete byte at that address with 1. The wrapper does not directly modify adjacent bytes as part of this store.

This step occurs only after the first indirect operation returns normally and before the second indirect operation is invoked. If the byte was already 1, the source still specifies the store. If the mode is not 1, the wrapper does not clear the byte.

### 4. Second receiver resolution and indirect operation

The function obtains the receiver and dispatch target again from the caller-provided record. It does not visibly reuse the object or dispatch-table address resolved for the first indirect operation.

The dependent reads are:

1. Read the record’s leading 32-bit object-address value again.
2. Read the dispatch-table address from the beginning of that object.
3. Obtain the callable target at dispatch-table byte offset 224.

The selected target is invoked with:

1. The newly resolved object address as receiver.
2. The first forwarded 32-bit value.
3. The original mode value.
4. The second forwarded 32-bit value.
5. Zero.

The mode is not normalized to a Boolean. For example, a mode of 2 is forwarded as 2 even though it does not cause the marker write.

The separate receiver resolution matters if an earlier dependency modifies the record or referenced object. The first indirect operation may affect which object or dispatch table is used by the second operation. The wrapper imposes no visible identity check between the two receivers.

Any result of the second indirect operation is ignored by the visible wrapper.

### 5. Final temporary-storage call and return

After the second indirect operation returns normally, the function invokes F-4e292a3dd745 with the address of the same temporary region.

After this dependency returns normally, the function returns without an explicit result.

The evidence establishes this call on the normal continuation path. It does not establish an exception handler, fault handler, or other mechanism that guarantees the call after an earlier operation fails to return normally.

## Side effects

The only explicit caller-storage write performed by the wrapper is the one-byte marker store at record offset 13 when the mode equals 1.

Other effects are delegated:

- F-ba5a4c1e0746 receives writable temporary storage.
- The first indirect operation receives the temporary address and the receiver address.
- The second indirect operation receives the receiver address and the forwarded values.
- F-4e292a3dd745 receives the temporary address.

Their memory writes, external effects, global-state changes, allocation behavior, and ownership actions are unknown. Opaque forwarded values may have additional meaning to those dependencies; the wrapper does not establish whether they represent scalars, addresses, handles, or something else.

The temporary region is local to this invocation. It is not returned by the wrapper. Passing its address establishes access during the calls, but does not establish permission to retain it after the invocation ends. Any retention or ownership protocol is documented_only.

The marker write is not a rollback-protected transaction. Once reached with mode 1, the write precedes the second indirect operation. No visible recovery path restores the previous byte. Conversely, the marker is not guaranteed to remain 1 at return: subsequent dependencies could modify that byte through aliases or other reachable state.

No synchronization or atomicity guarantee is established. The sequence described here is the source-level order within this invocation, not a concurrency contract.

## Acceptance examples

These examples are conditional consequences of the static sequence, not reports of executed tests.

### Mode equals 1

Given valid accesses and normally returning dependencies, the required order is:

1. F-ba5a4c1e0746 receives the temporary address and two zeros.
2. The indirect target at offset 368 receives the first resolved receiver, the first forwarded value, and that temporary address.
3. The byte at record offset 13 is written with 1.
4. The indirect target at offset 224 is selected through a fresh resolution and receives the five specified arguments.
5. F-4e292a3dd745 receives the same temporary address.
6. The wrapper returns.

A second operation that reads the marker before any subsequent mutation can observe the wrapper’s write. The first operation runs before that write.

### Mode equals 0 or 2

Both modes skip the wrapper’s marker store. The second indirect operation receives the original mode, respectively 0 or 2.

If the marker was previously 1, this wrapper does not clear it merely because the mode differs from 1. Dependencies remain free to change it according to their unknown behavior.

### Earlier operation replaces the receiver

Suppose the first indirect operation changes the record’s leading object-address value from one valid object to another. If execution continues normally, the second indirect operation is resolved through the replacement object.

Using a receiver cached before the first call would not match the visible sequence.

### Earlier operation does not return normally

If the first indirect operation does not return normally, the provided body establishes no execution of the later marker store, second indirect call, or final dependency.

This is not a claim about whether a particular failure mechanism exists; that behavior is unknown.

### Later operation changes the marker

If mode equals 1 and the second indirect operation subsequently writes a different value to record offset 13, that later value can be the final observable value. Requiring the marker to equal 1 at return would add a guarantee absent from the evidence.
