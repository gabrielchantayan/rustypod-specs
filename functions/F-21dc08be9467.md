# F-21dc08be9467

## Purpose

F-21dc08be9467 resets activation-related fields in a table of fixed-size records, selects records using a most-significant-bit-first bitmap, publishes pointers to selected records in a separate array, and sorts those pointers by a signed 32-bit record key.

The records themselves are not reordered. Selection changes record flags; sorting changes only the pointer array.

The apparent intent is to rebuild an ordered active-record list. That intent is inferred. The established behavior includes unchecked record addressing, capacity checks performed after activation, and reversal of selection order among equal-key entries.

## Interface

The function accepts two addresses and has no explicit return value.

All word fields, stored addresses, and pointer-array entries in the supplied representation are 32 bits wide. Bitmap elements are 8 bits wide. Offsets below are byte offsets.

### Table descriptor

The first argument identifies a descriptor with these accessed fields:

| Offset | Width | Meaning |
|---|---:|---|
| +0 | 32 bits | Record count used for reset; subsequently reread as pointer-array capacity |
| +4 | 32 bits | Output count of successfully appended record pointers |
| +8 | 32 bits | Address of the record storage |
| +12 | 32 bits | Address of the output pointer array |

The output count is overwritten after selection completes. Its incoming value is not used.

Each record occupies 28 bytes. The function accesses:

| Record offset | Width | Meaning |
|---|---:|---|
| +0 | 32 bits | Signed sort key |
| +16 | 32 bits | Flags; activation is represented by bit value 4 |
| +24 | 32 bits | Field reset to the bit pattern `0xFFFFFFFF` |

Other record fields are not directly accessed.

### Bitmap descriptor

The second argument identifies a descriptor with these accessed fields:

| Offset | Width | Meaning |
|---|---:|---|
| +0 | 32 bits | Number of bitmap positions to examine |
| +8 | 32 bits | Address of bitmap bytes |

The field at offset +4 is not accessed.

The bitmap count is a bit count, not a byte count. Without aliasing that changes future input, processing requires the smallest whole number of bytes sufficient to contain that many bits. A zero bit count requires no bitmap-byte dereference.

### Preconditions for defined operation

The caller must provide valid, appropriately aligned storage for every accessed descriptor word, record word, and pointer-array entry. Bitmap bytes must be readable.

For ordinary table use:

- The record allocation must contain every record visited during reset.
- Every selected bitmap index must identify an accessible record, even when that index exceeds the declared record count.
- The pointer array must have enough writable entries for every pointer actually appended.
- Address calculations must remain within valid storage.
- Record keys must be readable when sorting reaches them.

The function does not validate these conditions. In particular, the descriptor’s record count is not used to reject bitmap indices before record access.

No ownership transfer, allocation, or deallocation is directly visible.

## Behavior

### 1. Capture initial inputs

Before resetting records, the function reads, in order:

1. The bitmap-byte address.
2. The bitmap bit count.
3. The record-storage address.

It then reads the table’s record count to determine the number of reset iterations.

The bitmap address and bit count are retained for the selection pass. Later modification of those descriptor fields does not redirect or resize that pass. The reset pass similarly uses its captured record base and iteration count.

The output pointer-array address is not captured at this stage.

### 2. Reset records

The function visits the declared records in increasing storage order, advancing 28 bytes per record.

For each record, it performs these observable operations in order:

1. Read the 32-bit flags word at offset +16.
2. Write that word back with bit value 4 cleared.
3. Write `0xFFFFFFFF` to the word at offset +24.

All flag bits other than bit value 4 are preserved by the flags update. The reset of the field at offset +24 occurs regardless of whether that record will later be selected.

A zero record count produces no record-reset accesses. It does not prevent later selection accesses if the bitmap count is nonzero.

The reset pass does not clear the output pointer array or immediately change the output count.

### 3. Scan the bitmap and activate records

Bitmap positions are examined in increasing index order, starting at zero and stopping before the captured bit count.

Bits within each byte are consumed from bit value 128 down through bit value 1. Thus:

- Bitmap position 0 uses the high bit of the first byte.
- Position 7 uses the low bit of the first byte.
- Position 8 uses the high bit of the second byte.

A byte is read only when its first position is reached. Its value is retained while its remaining positions are processed. Unused low-order bits in the last consumed byte are ignored.

A clear bit causes no direct record access for that position.

For a set bit at index \(i\), the function:

1. Rereads the table’s record-storage address.
2. Computes the candidate record address as that address plus \(28i\).
3. Reads the candidate’s flags.
4. Does nothing further for that candidate if bit value 4 is already set.
5. Otherwise, writes the flags with bit value 4 set.
6. Rereads the table’s record count and compares it, unsigned, with the number of pointers appended so far.
7. If capacity remains, rereads the output-array address, writes the candidate address into the next 32-bit entry, and increments the local appended count.
8. If capacity does not remain, invokes F-4457a9a44a68 with a static diagnostic argument.

Activation therefore precedes the capacity check. A candidate can acquire the active flag without being appended.

The appended count starts at zero. A capacity failure does not increment it. If the dependency returns, processing continues with subsequent bitmap positions.

The activation-bit check is a duplicate-suppression mechanism based on current record memory, not on a search of the output list. With ordinary nonoverlapping storage and in-range indices, reset clears that bit before selection and each bitmap index addresses a different record. Outside those conditions, preexisting or newly modified flags can suppress appending.

### 4. Publish the count

After all bitmap positions have been examined, the function writes the local appended count to table offset +4.

This publication occurs before sorting. Thus the published count may already be visible while the pointer array is only partially sorted.

Entries beyond the appended count are not cleared by this function. They may retain pointers from an earlier use.

### 5. Sort the output pointers

After publishing the count, the function rereads the output-array address and sorts the appended pointers in place.

Ordering uses the signed 32-bit word at offset zero of each pointed-to record. Smaller signed values precede larger values. For example, the bit pattern `0xFFFFFFFF` sorts as −1, before zero.

The established comparison moves a newly considered entry ahead of preceding entries whose keys are greater than **or equal to** its key. Consequently:

- Final keys are in nondecreasing signed order under ordinary valid-storage conditions.
- Equal-key entries do not retain selection order.
- Equal-key entries are reversed relative to their insertion order.

For each move past a preceding entry, the function first writes that preceding pointer into the higher slot and then writes the candidate pointer into the lower slot. These intermediate writes are observable; this is not an atomic list replacement.

The sort loop compares against a signed interpretation of the appended count. For counts from zero through `0x7FFFFFFF`, its ordinary meaning is a sort of that many entries. If the appended count has its high bit set, the initial signed loop condition is false and no sorting iterations occur. No practical validity of such an enormous allocation is established.

### Integer and address semantics

Descriptor counts and the bitmap index are unsigned 32-bit values. The capacity comparison is unsigned.

Address addition and index scaling use the supplied 32-bit representation. No widened overflow check is visible for:

- Advancing the reset address by 28 bytes.
- Computing a selected record address from \(28i\).
- Computing a pointer-array slot from four times the appended count.
- Computing sorting-slot addresses.

Wrapping calculations do not establish permission to access the resulting address. Correct use requires valid storage for the actual accesses.

## Side effects

Direct writes are limited to:

- Clearing activation bit value 4 in every reset record.
- Resetting each such record’s offset +24 word to `0xFFFFFFFF`.
- Setting activation bit value 4 in selected candidates that were not already active.
- Appending candidate addresses to the pointer array.
- Publishing the appended count.
- Rearranging pointer-array entries during sorting.

The function does not directly write bitmap bytes, change record keys, or move record contents.

These statements describe direct accesses, not guaranteed isolation. No nonaliasing condition is enforced. For example, output-array writes could alter future bitmap bytes if the caller overlaps those buffers. A bitmap byte already loaded remains cached for its remaining positions, whereas a later byte is read only when reached.

Likewise, overlapping records, descriptors, or output storage can change later descriptor reads, flags, and keys. The algorithm does not protect against such effects.

There is no visible rollback. If an invalid access or dependency behavior interrupts execution, earlier mutations may remain, and the output count may still be its incoming value if count publication has not yet occurred.

No return status reports overflow or partial completion.

## Dependencies

### F-4457a9a44a68

This dependency is invoked when a newly activated candidate cannot be appended because the local appended count is not less than the table’s current count/capacity field.

The call receives one static diagnostic argument. The diagnostic’s apparent subject is activation-list capacity exhaustion.

Established call-site behavior:

- The candidate’s activation flag has already been set.
- The candidate pointer has not been appended.
- The local appended count is unchanged.
- If the call returns, bitmap processing continues.
- Additional qualifying candidates can trigger additional calls.

The dependency’s implementation is unavailable. Whether it logs, terminates execution, transfers control, mutates shared memory, or releases memory is **documented_only**. It must not be assumed to preserve table fields, record storage, output storage, or global state.

In particular, continued correctness after a returning call depends on whatever storage and state remain valid. Subsequent selection iterations reread relevant table fields, whereas the bitmap stream position, captured bit count, and local appended count are not reinitialized.

## Acceptance examples

These examples are conditional on valid, nonoverlapping storage, no external mutation, and no dependency effects unless explicitly stated.

### Empty selection with a nonempty table

Given three records and a bitmap bit count of zero:

- All three records have activation bit value 4 cleared.
- All three offset +24 words become `0xFFFFFFFF`.
- The output count becomes zero.
- No bitmap byte is read.
- Existing pointer-array entries remain unchanged.
- No sorting iterations occur.

### Bit order and key order

Given four records with signed keys 30, 10, 20, and 40, and a bit count of four with first bitmap byte `0xA0`:

- Positions 0 and 2 are selected.
- Their record pointers are initially appended in that order.
- The final pointer order is record 2, then record 0, because 20 precedes 30.
- The output count is two.
- Records 0 and 2 finish active; records 1 and 3 finish inactive.
- All four offset +24 fields have been reset.

### Ignored trailing bits

Given a bit count of one and first bitmap byte `0x7F`, no record is selected. The set low-order bits lie outside the requested one-bit range.

Given the same count and byte `0x80`, record 0 is selected if its candidate access and append are valid.

### Signed key comparison

Given selected records with key bit patterns `0x00000000`, `0xFFFFFFFF`, and `0x80000000`, the resulting key order is:

1. `0x80000000`, interpreted as −2147483648.
2. `0xFFFFFFFF`, interpreted as −1.
3. `0x00000000`, interpreted as zero.

Unsigned key ordering would not satisfy the contract.

### Equal keys

Given three selected records with equal signed keys, selected in index order 0, 1, 2, the final pointer order is 2, 1, 0.

A stable sort preserving 0, 1, 2 would not match the established behavior.

### Capacity exhaustion after activation

Suppose the declared record count is one, but backing storage safely contains at least two records. Let both first bitmap positions be selected, and let record 1 initially have activation bit value 4 clear.

- Only record 0 is reset by the reset pass.
- Record 0 is activated and appended.
- Record 1 is then activated before capacity is checked.
- The capacity check fails for record 1.
- F-4457a9a44a68 is invoked.

If that dependency returns without relevant mutations, the final output count is one, while both records are active. Record 1’s offset +24 field is not reset by this invocation.

This example does not make an out-of-range record access safe without the stated extra backing storage.
