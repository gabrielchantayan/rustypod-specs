# F-b002ce492389

## Purpose

F-b002ce492389 obtains external state, applies two eligibility gates, and searches a shared, tree-shaped structure. If its final iterator-like check permits record access, it compares a record’s one-byte field with an unsigned 32-bit requested value. A difference causes a byte write followed by two ordered notification calls.

**Established:** a normal return of one means the final iterator-like check returned zero. It does not mean the stored byte changed, that the requested value fits in a byte, or that notifications succeeded.

**Inferred intent:** the function appears to synchronize a record status with externally obtained state. “Status,” “container,” “candidate,” and “notification” describe apparent roles, not established application semantics.

Two calls made before the search receive address-like and value arguments. Their implementation is absent; whether either call writes memory is unknown.

### Address-like argument calls and effective status

After both gates pass, F-unresolved-01 is invoked with:

- A first argument loaded from the shared first-address slot.
- The captured mode word as its second argument.

After that call returns, the function loads the shared key-address slot and retains its 32-bit value for the lookup key.

It then invokes F-unresolved-01 again. For this call, the first argument is formed from a **new load** of the same key-address slot, minus **62 bytes**. The second argument depends on the captured mode:

- For zero mode, the second argument is zero. After the call returns, the effective requested status becomes zero.
- For nonzero mode, the second argument is the captured auxiliary word. The effective requested status remains the originally captured unsigned status.

The retained key-address value therefore need not equal the address-slot value used for the second call or any later value in that slot.

Neither call result is inspected. The source establishes the calls and their arguments, not a memory-write operation. Whether these calls read or write memory, retain an argument, transfer ownership, or affect shared state is **documented_only**.

### Lookup storage and initial reads

The function obtains a container pointer from its shared slot and retains it for subsequent comparator-context calculations and later header reads.

The lookup storage comprises two adjacent 32-bit words:

| Relative offset | Initial contents |
|---|---|
| 0 | Retained key-address value |
| 4 | Effective requested status |

The first word is initialized before the initial traversal reads; the second is initialized before the traversal loop.

The initial traversal setup also rereads the shared container-pointer slot:

1. A load of that shared slot identifies a container whose offset-16 field supplies a header pointer. The header’s offset-4 field supplies the initial traversal node.
2. A separate load of the shared container-pointer slot identifies a container whose offset-16 field supplies the initial candidate.

These are distinct reads, not a guaranteed single snapshot. Subsequent comparator contexts and post-traversal header reads use the retained container pointer. Without mutation, these sources may agree; agreement is not independently enforced.

The lookup storage’s address is passed to dependencies. Its later contents must not be assumed unchanged. In particular, the effective requested status retained for the final byte comparison is distinct from the copy initially placed in the lookup storage’s second word.

It passes their addresses to F-f063d8ade9f7.

If that call returns nonzero, the selected value is a fresh header value read through the retained container pointer.

If it returns zero:

1. The then-current candidate-slot value is passed to F-539f08165386.
2. That dependency’s 32-bit result becomes the third argument to F-bcefa5957e76.
3. The first two arguments are the retained container address plus 25 and the address of the lookup storage, respectively.

This use of F-bcefa5957e76 places the lookup-storage address in the second argument position, unlike traversal.

### Final iterator-like check

The selected value is copied into a new addressable 32-bit slot. Another slot receives a fresh header value from the retained container’s offset-16 field. Their addresses are passed to F-f063d8ade9f7.

- A **nonzero** result causes an immediate zero return, without the subsequent record-byte access.
- A **zero** result permits record access using the selected-value slot as it exists after this call.

The caller does not replace this dependency with a direct pointer-equality test. Even selecting the header does not, by itself, establish the eventual return value.

### Record comparison, update, and notifications

On the accepted path, the function reads the record pointer at selected-node offset 20, then reads the record byte at offset 100.

The byte is promoted to an unsigned value in the range 0–255 and compared with the **full unsigned 32-bit effective requested status**.

If equal, the function returns one without a byte write, notification-object acquisition, or notification call.

If unequal, the following occur in order:

1. The record pointer is read again through the selected node’s offset-20 field.
2. The record byte at offset 100 is written with the effective status’s low eight bits.
3. F-9d0ecc5f6adf is called to acquire a notification object.
4. The object’s virtual method at dispatch-table offset 88 is invoked with the first shared notification identifier and the current first lookup-storage word.
5. That virtual-method slot is invoked again on the same acquired object, using the second shared notification identifier and the current first lookup-storage word.
6. The function returns one.

The unknown virtual notification dependency is labeled F-unresolved-03.

The method entry is obtained separately for each invocation. The second identifier and lookup word are read for the second call; they are not guaranteed to retain their first-call values. The same object pointer is reused, but its dispatch table is not established to remain unchanged.

Notification return values are ignored. The byte write precedes acquisition and both calls; there is no visible rollback if a later operation does not return normally.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. They assume valid reached memory and normally returning dependencies unless stated otherwise.

1. **First gate rejects.** If F-unresolved-02 returns zero, the result is zero. F-682adfd5a561, both F-unresolved-01 calls, traversal, and notifications are not reached.

2. **Second gate rejects.** If the first gate returns nonzero and F-682adfd5a561 returns zero, the result is zero. Initial acquisition calls have occurred, but the address-like argument calls and lookup have not.

3. **Zero mode overrides the requested status.** With zero mode and an originally requested status of 300, the second F-unresolved-01 call receives zero as its value argument. The lookup’s second word is initially zero, and the eventual record-byte comparison uses zero. Whether F-unresolved-01 writes anything is not determined.

4. **Address-slot mutation separates arguments.** If the first F-unresolved-01 call leaves the key-address slot at 1000, that value is retained. If the slot is 2000 when loaded for the second call, its first argument is 1938. The lookup’s first word initially remains 1000.

5. **Final rejection prevents record access.** If the final F-f063d8ade9f7 call returns nonzero, the result is zero. Earlier calls and traversal may already have occurred, but the subsequent record-pointer and status-byte accesses do not occur.

6. **Matching byte avoids notifications.** If the final check returns zero, the effective status is 7, and the reached record byte is 7, the result is one without a byte write or notification-object acquisition.

7. **Different byte triggers ordered operations.** Under the same conditions, with stored byte 3, the function writes 7 before acquiring the notification object. The first notification invocation precedes the second. Normal completion returns one, irrespective of ignored notification return values.

8. **Full-width comparison differs from byte comparison.** With effective status 256 and stored byte zero, comparison differs. The function writes zero and issues both notification calls. If all relevant state and dependency outcomes remain unchanged, a subsequent invocation with status 256 again takes this path.

9. **Zero-branch candidate can be null.** If a traversal comparison returns zero and the offset-8 child is null, both traversal and candidate become null. Later behavior depends on the iterator-like dependencies; the preceding node is not retained as the candidate.

10. **Lookup mutation does not redefine the retained status.** If a comparison dependency changes the lookup’s second word from 7 to 9, subsequent lookup operations may observe 9. The final record-byte comparison still uses the independently retained effective status of 7.
