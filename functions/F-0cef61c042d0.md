# F-0cef61c042d0

## Purpose

F-0cef61c042d0 advances a 36-byte-unit storage state. It first prefers a linked available-entry chain. If that chain is empty, it advances a cursor in the current storage region, obtaining and linking a new region when the cursor equals the region boundary.

The established behavior is state mutation, not delivery of an entry through a return value. The function neither initializes a 36-byte entry nor explicitly returns its address.

The layouts suggest a pool or arena with reusable entries and chained storage blocks. That interpretation is inferred intent. The contract below describes the observable operations independently of that interpretation.

## Interface

The function has two inputs:

- **State address:** a pointer to writable state containing four consecutive 32-bit words.
- **Mode:** a 32-bit integer. Only equality to zero matters. All nonzero values select the same behavior.

There is no explicit result value.

### State layout

| Byte offset | Width | Contract role |
|---|---:|---|
| 0 | 32 bits | Address of the current block header, or zero |
| 4 | 32 bits | Address of the first available entry, or zero |
| 8 | 32 bits | Current sequential cursor |
| 12 | 32 bits | Sequential region boundary |

Addresses are represented by 32-bit words in the supplied representation. Address increments use byte units.

An available entry must expose a readable 32-bit successor address at offset 0. No other available-entry fields are accessed by this function.

A block header occupies 12 bytes:

| Byte offset | Width | Contract role |
|---|---:|---|
| 0 | 32 bits | Previous block-header address |
| 4 | 32 bits | Block capacity, in 36-byte units |
| 8 | 32 bits | Backing-region address |

### Preconditions

For defined ordinary operation:

- The state address must designate accessible storage for all four state words.
- A nonzero available-entry address must permit a 32-bit read at its beginning.
- When capacity is derived from a nonzero current block-header address, that header must permit a 32-bit read at offset 4.
- Each result from F-871e64ddc6de must be suitable for the accesses that follow.
- Alignment and address validity must satisfy the target environment.

For the ordinary pool interpretation, state, headers, and entry storage should not overlap, and concurrent mutation should not occur. The function does not validate those conditions. The consequences of unusual aliasing or external mutation are not fully established.

## Behavior

### 1. Prefer an available entry

The first decision reads the available-entry word at state offset 4.

If it is nonzero:

1. The function obtains the 32-bit word at the beginning of the referenced entry.
2. It stores that successor address into state offset 4.
3. It returns immediately.

On this path, the function does not examine the mode, compare the cursor with the boundary, obtain storage, or explicitly write the block-header, cursor, or boundary fields.

The popped entry is not cleared, initialized, released, or returned explicitly. Its existing first word remains unchanged unless an unusual overlap makes the state write affect the entry itself.

### 2. Decide whether to obtain a new region

When the available-entry word is zero, the function compares the cursor at offset 8 with the boundary at offset 12.

If they differ, it skips region creation and proceeds directly to the final cursor increment.

The comparison is equality only. There is no test that the cursor is below the boundary, within the region, or aligned to a 36-byte entry boundary. A cursor beyond the boundary still takes the no-allocation path if it is unequal to the boundary.

If cursor and boundary are equal, the function selects a capacity and obtains a new header and backing region.

### 3. Select the capacity

Capacity is a 32-bit unsigned quantity.

For a nonzero mode, capacity is exactly **1**. The current header’s capacity is not consulted for this decision.

For a zero mode:

- If the current block-header word is zero, capacity is **32**.
- Otherwise, the function reads the unsigned 32-bit capacity at offset 4 of the current header and computes two candidates:
  - Previous capacity plus 32.
  - Previous capacity plus its unsigned right shift by one, plus its unsigned right shift by three.

The second candidate therefore uses separately truncated halves and eighths. It is not defined as a floating-point multiplication.

Both candidates use 32-bit unsigned arithmetic. Additions wrap modulo \(2^{32}\), and selection uses an unsigned comparison. The larger wrapped candidate becomes the new capacity. If the candidates are equal, the selected numerical value is that shared value.

For capacities where no arithmetic wraps, this is a growth rule choosing between an increment of 32 and an approximately 62.5% increment. That growth interpretation does not override the actual wrapping arithmetic.

### 4. Obtain and publish a new region

After selecting capacity, the function invokes F-871e64ddc6de twice, in order:

1. A request with arguments **12** and **0**, whose result is used as the new block-header address.
2. A request with arguments **capacity × 36** and **0**, whose result is used as the backing-region address.

The second request’s byte count is calculated at 32-bit width. Overflow is not detected.

Both calls occur before the function explicitly initializes the new header or publishes it in the state. The first result must remain usable across the second call.

After both calls return, the explicit writes and relevant reads occur in this order:

1. Store the second result into the new header at offset 8.
2. Read the current block-header word from state offset 0 and store it into the new header at offset 0.
3. Store the selected capacity into the new header at offset 4.
4. Store the new header address into state offset 0.
5. Read the backing-region address from the new header at offset 8.
6. Store that address into the state cursor at offset 8.
7. Store that address plus capacity × 36 into the state boundary at offset 12.

The previous-header value used for linking is read after both dependency calls. It is not necessarily the header value previously consulted during capacity selection. If a dependency changes the state through an external mechanism, the value linked here can differ.

Likewise, the backing address used for the cursor and boundary is read from the header after publication. Under the ordinary nonoverlapping layout it equals the second dependency result. The explicit read remains significant if storage aliases or external mutation occurs.

### 5. Advance the cursor

Every path that reaches this stage reads the current cursor, adds **36 bytes**, and stores the result back into state offset 8.

Consequently, after ordinary successful region creation:

- The state points to the new header.
- The cursor is backing-region start plus 36.
- The boundary is backing-region start plus capacity × 36.
- The available-entry word has no explicit write on this path.

For capacity 1, cursor and boundary become equal immediately after this increment.

No entry contents are initialized by this final step. The function does not write at the cursor or at the region’s first entry.

## Side effects

### Explicit memory effects

There are three principal paths:

| Path | Explicit state writes | Explicit non-state writes |
|---|---|---|
| Available entry exists | Available-entry head replaced by its successor | None |
| No available entry; cursor differs from boundary | Cursor advanced by 36 | None |
| No available entry; cursor equals boundary | Current header, cursor, and boundary updated | Three new-header words initialized |

These describe the function’s own accesses under ordinary nonoverlapping storage. They do not limit effects performed by F-871e64ddc6de.

The source does not establish a total order between every read used in a comparison. It does establish that the available-entry decision precedes any cursor/boundary decision, and that the header and state writes during region creation follow the sequence described above.

### Ownership and lifetime

The function retains the two dependency results through the current header and its backing-region field. It also links the previously current header rather than explicitly releasing it.

There is no explicit release operation, rollback, or cleanup on any path. The dependency’s ownership rules are unknown; retaining an address does not establish who must eventually release it.

Removing an available entry from the chain does not itself establish ownership transfer to a caller, because this function has no explicit entry-valued result.

### Errors and partial updates

There is no explicit validation, error return, null-result check, or arithmetic-overflow check.

If the first dependency call returns an unusable header address, the function still attempts the second call before its first explicit header write, provided execution returns normally from both calls.

If both calls return normally, the function writes the second result into the header without first validating it. A zero backing-region result is not itself followed by a backing-region dereference in this function; it is used in address arithmetic and state storage.

A failure during subsequent writes can leave a partially initialized header or partially updated state. No transactional guarantee is established.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, they assume valid nonoverlapping storage, normal dependency returns, no external mutation, and no address overflow.

### Available entry takes precedence

Given:

- The available-entry head references entry A.
- A’s first word contains entry B’s address.
- Cursor equals boundary.

The resulting available-entry head is B. Cursor, boundary, and current header receive no explicit writes, and F-871e64ddc6de is not called. Either mode value produces this result.

If A’s first word is zero, the resulting available-entry head is zero.

### Existing region has unequal cursor and boundary

Given a zero available-entry head and unequal cursor and boundary, the cursor advances by 36 bytes. No dependency call occurs, regardless of mode.

This also applies when the cursor is numerically greater than the boundary. The function does not reject or repair that state.

### Initial region in zero mode

Given a zero available-entry head, equal cursor and boundary, a zero current-header word, and mode zero:

- Selected capacity is 32.
- Dependency requests are 12 bytes and 1,152 bytes, in that order.
- The new header records a zero previous-header link, capacity 32, and the returned backing address.
- Final cursor is backing start plus 36.
- Final boundary is backing start plus 1,152.

### Region creation in nonzero mode

Given a zero available-entry head and equal cursor and boundary, any nonzero mode selects capacity 1.

The dependency requests are 12 and 36 bytes. The existing header is linked as the previous header, but its capacity is not read for capacity selection. Final cursor and boundary both equal backing start plus 36.

### Ordinary growth

With zero mode and previous capacity 32, the candidates are 64 and 52. Selected capacity is 64, requesting 2,304 backing bytes.

With previous capacity 64, the candidates are 96 and 104. Selected capacity is 104, requesting 3,744 backing bytes.

With previous capacity 65, the shifted terms are 32 and 8. The candidates are 97 and 105, so capacity is 105.

### Unsigned overflow remains observable

With zero mode and previous capacity \(0x80000000\):

- The additive candidate is \(0x80000020\).
- The shifted-growth candidate is \(0xD0000000\).
- Unsigned comparison selects \(0xD0000000\).
- Multiplication by 36 wraps to a byte count of \(0x40000000\).

No overflow error is explicitly reported. This example describes arithmetic selection only, not the feasibility of obtaining or using that storage.
