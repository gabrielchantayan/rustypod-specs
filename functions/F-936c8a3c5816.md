# F-936c8a3c5816

## Purpose

F-936c8a3c5816 selects and constructs one of three unsigned packed-integer layouts from four scalar components. A pointer-shaped selector determines which layout applies; the selector’s pointed-to contents are not accessed.

The established operation is bit selection and packing:

- The literal selector 0x565 selects a 5–6–5 layout.
- A distinguished object address selects a 4–4–4–4 layout, subject to the comparison precedence below.
- The literal selector 0x2565 selects the 5–6–5 layout if the distinguished-address comparison has not matched.
- All remaining selectors select a 5–5–5 layout whose highest possible set bit is bit 14.

Color-format interpretation is inferred intent. Component names in this contract identify argument positions, not verified red, green, blue, or alpha semantics.

The function does not round, clamp, saturate, or normalize its inputs. It retains specified bits and places them into nonoverlapping result fields.

## Interface

### Inputs

The function receives five arguments in this order:

| Position | Contract name | Supplied representation | Role |
|---|---|---|---|
| 1 | Selector | Byte-pointer-shaped value | Compared with two literal values and one object address |
| 2 | Component A | Unsigned integer | Supplies a field in every layout |
| 3 | Component B | Unsigned integer | Supplies a field in every layout |
| 4 | Component C | Unsigned integer | Supplies a field in every layout |
| 5 | Component D | Unsigned integer | Supplies a field only in the 4–4–4–4 layout |

The supplied representation identifies the components and return value as unsigned integers but does not independently establish their ABI widths. A 32-bit unsigned interface is a working interpretation, not a verified original-ABI fact. The numerical descriptions below require unsigned integer values capable of representing the specified 16-bit results.

Contributing input bits range from **bit 2 through bit 7**, depending on the component and selected layout. In particular, Component B’s bit 2 contributes to result bit 5 in the 5–6–5 layout. No component bit above bit 7 contributes.

The recognized selector identities are:

- The literal pointer-shaped value 0x565.
- The literal pointer-shaped value 0x2565.
- A distinguished object address.

The distinguished address is represented by an address-labelled object associated with 0x1444. The comparison uses that object’s address, not an explicitly written numeric pointer constant. Numeric 0x1444 is therefore not independently established as a usable selector value in a relocated or differently loaded environment.

### Output

The function returns one unsigned integer.

| Layout | Occupied result bits | Maximum numerical result |
|---|---|---:|
| 5–6–5 | 15–0 | 0xFFFF |
| 4–4–4–4 | 15–0 | 0xFFFF |
| 5–5–5 | 14–0 | 0x7FFF |

All result bits above bit 15 are zero if the return type is wider than 16 bits. In the default 5–5–5 layout, bit 15 is also zero.

There is no output buffer, separate status value, or explicit error result.

### Preconditions and input domain

The selector is not dereferenced. The function establishes no requirement for readable selector-designated storage, allocation size, alignment, or ownership.

Passing the pointer-shaped literal selectors must still be valid for the actual execution environment and calling convention. The supplied material does not establish a portable language-binding procedure for constructing those values.

The components need not be restricted to the range 0 through 255. Larger representable unsigned values are processed by retaining only the specified low-byte bits. No out-of-range rejection is present.

## Behavior

### Layout selection and precedence

Selector decisions have the following precedence:

1. Equality with 0x565 selects 5–6–5 immediately.
2. Otherwise, equality with the distinguished address selects 4–4–4–4.
3. Otherwise, equality with 0x2565 selects 5–6–5.
4. Otherwise, the default 5–5–5 layout applies.

Unrecognized selectors are accepted through the default path rather than rejected.

Normally the two literal selector values produce the same layout. Their equivalence is conditional on the distinguished address not coinciding with 0x2565. If such a coincidence existed, the earlier distinguished-address comparison would select 4–4–4–4. If the distinguished address coincided with 0x565, the first comparison would still select 5–6–5.

This precedence is established; whether either address coincidence is possible in the intended deployment is not established.

### 5–6–5 layout

This layout places retained component bits as follows:

| Result field | Source field | Width |
|---|---|---:|
| Bits 15–11 | Component A, bits 7–3 | 5 |
| Bits 10–5 | Component B, bits 7–2 | 6 |
| Bits 4–0 | Component C, bits 7–3 | 5 |

Component D has no effect.

The numerical contributions are:

- Component A masked by 0xF8 and shifted left by 8.
- Component B masked by 0xFC and shifted left by 3.
- Component C masked by 0xF8 and shifted right by 3.

These fields are combined by bitwise OR. Their destination ranges do not overlap, so their sum is numerically equivalent.

Component B retains one more low-order input bit than Components A and C. Its bit 2 becomes result bit 5; its bit 7 becomes result bit 10. Components A and C discard bits 2–0, while Component B discards only bits 1–0.

### 4–4–4–4 layout

This layout places the upper nibble of each component’s low byte into the result:

| Result field | Source field | Width |
|---|---|---:|
| Bits 15–12 | Component D, bits 7–4 | 4 |
| Bits 11–8 | Component A, bits 7–4 | 4 |
| Bits 7–4 | Component B, bits 7–4 | 4 |
| Bits 3–0 | Component C, bits 7–4 | 4 |

The final scalar argument, Component D, supplies the highest result field.

The numerical contributions are:

- Component D masked by 0xF0 and shifted left by 8.
- Component A masked by 0xF0 and shifted left by 4.
- Component B masked by 0xF0 without shifting.
- Component C masked by 0xF0 and shifted right by 4.

The fields are combined by bitwise OR. All component bits 3–0 are discarded. A discarded lower nibble cannot carry into or round the retained upper nibble.

### Default 5–5–5 layout

The fallback layout is:

| Result field | Source field | Width |
|---|---|---:|
| Bit 15 | Constant zero | 1 |
| Bits 14–10 | Component A, bits 7–3 | 5 |
| Bits 9–5 | Component B, bits 7–3 | 5 |
| Bits 4–0 | Component C, bits 7–3 | 5 |

Component D has no effect.

The numerical contributions are:

- Component A masked by 0xF8 and shifted left by 7.
- Component B masked by 0xF8 and shifted left by 2.
- Component C masked by 0xF8 and shifted right by 3.

The fields are combined by bitwise OR. Bits 2–0 of each participating component are discarded.

No implicit high-bit flag is inserted. Even when every retained component bit is one, the result is 0x7FFF rather than 0xFFFF.

### Widths, arithmetic, and representation

Every shifted component is masked before shifting. The largest possible individual field is 0xF800, and the largest combined result is 0xFFFF. The packing requires no numerical result wider than 16 bits.

For unsigned arithmetic wide enough to represent these values, no relevant overflow or shift-width boundary is crossed. Input bits above bit 7 cannot affect the result, including when the component interface is wider than one byte.

The result is an integer, not a serialized byte sequence. This function establishes neither little-endian nor big-endian storage order. Any later conversion of the result to bytes belongs to a caller or another operation.

## Side effects

The supplied body has no externally visible stores, function calls, allocation, release, or I/O.

In particular:

- Selector-designated storage is neither read nor written.
- The distinguished object’s contents are neither read nor written.
- No memory ownership is acquired, retained, transferred, or released.
- No global object is modified.
- No explicit failure, diagnostic, or exception path is present.

The selector comparisons occur in the precedence order specified above. Obtaining the distinguished object’s address does not constitute reading its contents.

All component operands are scalar argument values already supplied at entry. Their masks and combinations introduce no additional memory reads through those values. The supplied representation does not establish an externally meaningful evaluation order among the independent scalar operands within a packing expression.

Caller-side argument evaluation and any memory access used to obtain arguments occur outside this function’s contract.

## Dependencies

There are no callable dependencies in the supplied body. No additional opaque function IDs are required.

The only externally identified entity is the distinguished object whose address participates in selector comparison. Address identity matters; its contents, size, mutability, and ownership do not affect the shown computation.

## Acceptance examples

The following are conditional expectations derived from static analysis. They are not executed test results.

### Representative mixed components

For A = 0xAB, B = 0xCD, C = 0xEF, and D = 0x12:

| Selector condition | Expected result |
|---|---:|
| Equal to 0x565 | 0xAE7D |
| Equal to 0x2565 and unequal to the distinguished address | 0xAE7D |
| Equal to the distinguished address and unequal to 0x565 | 0x1ACE |
| Unequal to all recognized selector identities | 0x573D |

The distinguished-address case requires actual address equality. Merely passing numeric 0x1444 does not establish that condition.

### Zero and maximum fields

With all four components zero, the result is zero for every selector.

With all four components equal to 0xFF:

- A selected 5–6–5 layout returns 0xFFFF.
- A selected 4–4–4–4 layout returns 0xFFFF.
- The default 5–5–5 layout returns 0x7FFF.

The default result demonstrates that bit 15 remains clear independently of Component D.

### Component B’s bit-2 boundary

With A = 0 and C = 0:

| Selected layout | B | Expected result |
|---|---:|---:|
| 5–6–5 | 0x03 | 0x0000 |
| 5–6–5 | 0x04 | 0x0020 |
| Default 5–5–5 | 0x04 | 0x0000 |
| Default 5–5–5 | 0x07 | 0x0000 |
| Default 5–5–5 | 0x08 | 0x0020 |

These cases distinguish retention of B’s bit 2 in 5–6–5 from its rejection in 5–5–5. Component D may have any representable value in these cases because neither layout uses it.

### Fourth-component boundary

With A, B, and C zero, a selected 4–4–4–4 layout returns:

- 0x0000 for D = 0x0F.
- 0x1000 for D = 0x10.

For either other layout, changing D alone leaves the result unchanged.

### Wider components

If 32-bit component arguments are supported, A = 0x000000AB and A = 0x123456AB produce identical results when the selector and other components are fixed.

The same low-byte equivalence applies independently to every component. Additional discarded-bit equivalences depend on the selected layout.

### Selector storage independence

If two calls use the same selector identity and scalar values, changing bytes stored at that selector address does not change the result. The function does not inspect those bytes.

This is a statement about the absence of a pointee read, not a requirement that the selector designate allocated or readable storage.

## Evidence

Established behavior comes from static inspection of the supplied body: three ordered selector comparisons, unsigned masks and shifts, bitwise combinations, and returns. The body contains no calls, pointer dereferences, or externally visible stores.

The 0xFC mask on Component B in the 5–6–5 path retains bits 7–2. Its left shift by three places input bit 2 into result bit 5. The other component masks and shifts establish the field mappings and discarded-bit boundaries described above.

Color-packing intent and the working 32-bit ABI interpretation are inferences, not additional established behavior. No runtime tests have been performed.
