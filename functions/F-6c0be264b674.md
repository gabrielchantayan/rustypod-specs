# F-6c0be264b674

## Purpose

F-6c0be264b674 conditionally removes an indexed 32-bit entry from selected storage. On an accepted operation, it copies subsequent entries toward lower addresses, clears the final position reached, updates the selected count field, and returns `0`.

A zero gate byte bypasses record processing and returns `1`.

Indexed removal is inferred intent. The established behavior consists of global reads, signed comparisons, 32-bit entry transfers, a zero write, and a count update. Ordinary list-removal semantics require valid storage, nonoverlapping metadata, and stable state.

Record selection has an observable distinction: after a nonzero gate, the function reads the global record base once unconditionally. Selector `1` causes a second read of that global, and the selected address is derived from the **second** value. The two reads must not be treated as a single snapshot without an explicit stability assumption.

## Interface

The function accepts four arguments and returns a 32-bit status.

| Argument | Representation | Role |
|---|---|---|
| Index | Signed 32-bit integer | Validated against zero, the selected bound, and the initial count; subsequently identifies entry positions. |
| Selector | Signed 32-bit integer | Selects the second-base-read path only when exactly equal to `1`. |
| Third argument | Opaque 32-bit value | Unused by the supplied body. |
| Fourth argument | Signed 32-bit integer | Its incoming value does not affect the established result or memory-access path. |

For a nonnegative index and nonzero initial count, the fourth argument is replaced by the selected bound before the relevant validation. For a negative index, rejection is independent of its incoming value. This does not establish a broader purpose for that argument.

### Global inputs and selection

The function depends on a global gate reference and a global record-base value.

After reading a nonzero gate byte:

- It reads the global record base unconditionally.
- If the selector is not `1`, that first observed value becomes the selected address.
- If the selector is `1`, it reads the global record base again. The selected address is the second observed value plus `0x48` bytes. The first observed value is not used to address the selected record.

Only under a stable-global assumption does this reduce to selection between a record at a common base and another record `0x48` bytes later.

### Selected storage layout

All offsets below are relative to the selected address.

| Offset | Access width | Role |
|---|---:|---|
| Four times an entry index | 32 bits | Entry position |
| `0x40` | 32 bits | Signed count |
| `0x44` | 32 bits | Signed bound |

Entry values are opaque 32-bit patterns. The body does not establish whether they represent numbers, handles, pointers, or other objects.

Sixteen nonoverlapping 32-bit entry positions fit before the count field. This is a layout observation, not an enforced capacity:

- Entry position `16` aliases the count.
- Entry position `17` aliases the bound.
- Entry position `18` begins at offset `0x48`.

### Results

| Status | Condition |
|---:|---|
| `0` | The accepted mutation path reaches its return. |
| `1` | The gate byte is zero. |
| `5` | The selected count is initially zero. |
| `6` | The initial count is nonzero, but index validation fails. |

No explicit status covers inaccessible memory, invalid address arithmetic, or a failed load or store.

## Behavior

### Gate and base reads

The gate byte is read before record processing. If it is zero, the function returns `1` without reading the global record base or accessing selected-record metadata or entries.

With a nonzero gate, the global record base is read once before the selector-dependent branch. Selector `1` causes another read of the same global; the selected address then uses that second result plus `0x48`. Every other selector uses the first result without displacement.

These reads are distinct in the supplied body’s access sequence. In particular, selector `1` does not mean “add `0x48` to the first observed base.” If the global changes between the reads, the second value controls subsequent record accesses.

After selection, the body uses the selected address for metadata and entry accesses. It does not explicitly reread the global record base during validation or mutation.

This describes source-level access order, not guaranteed hardware transactions, compiler treatment of shared memory, or synchronization.

### Initial count and validation precedence

The selected count at offset `0x40` is read as a signed 32-bit value.

If that value is zero, the function returns `5` immediately. The bound is not read. Thus an empty record returns `5` even for a negative index.

For a nonzero initial count:

- A negative index is rejected with `6`, without reading the bound.
- A nonnegative index causes a signed 32-bit read of the bound at offset `0x44`.
- Acceptance requires the index to be strictly less than both the bound and the initial count.

The effective acceptance conditions are therefore:

- Index is nonnegative.
- Index is less than the signed bound.
- Index is less than the initial signed count.

The supplied comparisons account for signed subtraction overflow. Validation must not be reduced to checking the sign of a wrapping difference alone.

Consequences:

- Equality with either the bound or the count is rejected.
- A negative count is nonzero but cannot admit any index.
- A zero or negative bound cannot admit any index.
- Successful validation implies that the initial count is positive.
- Validation does not establish that entry addresses are within an allocation.

No record writes occur on these rejection paths.

### Accepted mutation

The function first compares the accepted index with the initial count minus one. Because acceptance implies a positive signed count, this initial subtraction is within signed 32-bit range.

If the index is already that last position, no shifting-loop count read or entry transfer occurs. The function proceeds directly to clearing that position.

Otherwise, shifting proceeds toward lower entry positions. Before each possible transfer, the current count field is read again. A transfer occurs while the current entry position is signed-less-than that freshly read count minus one.

For each transfer:

- The next 32-bit entry is read.
- Its value is written into the current entry position.
- The current position advances by one.

A subsequent loop-condition evaluation reads the count again. The loop extent therefore follows live count reads, not an immutable initial-count snapshot. The terminating evaluation also reads the count.

When shifting ends, or when shifting was bypassed, the function:

1. Writes a 32-bit zero into the current entry position.
2. Reads the count field again.
3. Decrements that newly read value.
4. Writes the result to the count field.
5. Returns `0`.

The final count update is not universally “initial count minus one.” Its input is the count observed after the clearing write.

### Ordinary removal semantics

If entries do not overlap metadata, the count remains stable until the final update, all required addresses are valid, and arithmetic remains representable, accepted removal has the conventional result:

- Entries preceding the requested index remain unchanged.
- Later occupied entries move down by one position.
- The old last occupied position becomes zero.
- Count decreases by one.
- Bound remains unchanged.

This simplified description is conditional. The specified access sequence governs cases with metadata overlap or changing state.

### Metadata overlap

The function does not enforce the apparent sixteen-entry region.

An accepted operation can therefore read or write metadata as entries:

- Writing entry position `16` overwrites the count.
- A later loop-condition read observes the then-current count, including a value written through that alias.
- Clearing entry position `16` sets the count to zero before the final decrement reads it.
- Writing or clearing entry position `17` changes the bound.

Entry position `18` is at selected address plus `0x48`. Under a stable-base, adjacent-record interpretation, this can reach the following record. Neither that interpretation nor a sufficient allocation size is independently established by the body.

## Side effects

### Read ordering

The supplied body establishes the following order:

1. Read the gate byte through the global gate reference.
2. If the gate is nonzero, read the global record base unconditionally.
3. If the selector equals `1`, read the global record base again and derive the selected address from this second result.
4. Read the selected count.
5. If the count is nonzero and the index is nonnegative, read the selected bound.
6. On a shifting path, read the current count before each possible entry transfer.
7. Read each source entry before writing its destination.
8. Clear the final entry position before reading the count for the final decrement.

The first base read remains part of the selector-`1` path even though its result is not used for selected-record addressing.

These constraints describe the supplied body, not atomicity, physical bus activity, or guarantees for unsynchronized concurrent access.

### Writes and ownership

Only the accepted mutation path explicitly writes storage. It writes entry positions and the count; overlap can make entry writes affect the bound or later storage as well.

There are no explicit calls, allocations, releases, callbacks, I/O operations, or ownership transfers. Copying or clearing a 32-bit pattern does not establish acquisition or disposal of any resource represented by that pattern.

The body provides no locking, atomic update protocol, rollback, or protection from concurrent changes.

### Preconditions for ordinary behavior

The caller or environment must provide:

- A readable gate reference and gate byte.
- With a nonzero gate, a readable global record-base location, including both reads when selector is `1`.
- Accessible selected metadata.
- Readable and writable storage for every entry address actually reached.
- Storage supporting the required 32-bit accesses.
- Nonoverlapping entry and metadata regions if ordinary removal semantics are required.
- Stable count and entry state if the intended result must correspond to the initially observed record.

A stable global record base is additionally required to interpret selector `1` as choosing the second record relative to the same base observed by the unconditional read. Without that assumption, selection follows the second observed value instead.

Failure of these preconditions is not mapped to a documented error status.

## Acceptance examples

These are conditional static examples, not executed tests. Unless an example states otherwise, assume a nonzero gate, valid addresses, stable state, representable address arithmetic, and entry accesses that do not overlap metadata.

### Disabled operation

With a zero gate, any argument values produce status `1`.

The global record base is not read. Neither count nor bound is read, and no entry or metadata write occurs. The gate reference and byte must still be readable.

### Empty record

With selected count `0`, indices `-1`, `0`, and any other signed value produce status `5`.

The bound is not read. Base selection, including the second global-base read for selector `1`, has already occurred before this result.

### Interior removal

Given count `4`, bound `16`, index `1`, and entries `[11, 22, 33, 44]`:

- Status is `0`.
- Entries become `[11, 33, 44, 0]`.
- Count becomes `3`.
- Bound remains `16`.

The value `33` is transferred before `44`. The count is reread for loop continuation and again after the final clear for the decrement.

### Last-entry removal

Given count `3`, bound `16`, index `2`, and entries `[11, 22, 33]`:

- Status is `0`.
- Entries become `[11, 22, 0]`.
- Count becomes `2`.

No entry transfer or shifting-loop count read occurs. The count is still reread after clearing the entry.

### Independent restrictions

With count `4` and bound `2`, index `1` is accepted, but index `2` returns `6`.

With count `2` and bound `16`, index `1` is accepted, but index `2` returns `6`.

Rejected cases perform no record write.

### Stable-base selector behavior

If the global base remains unchanged across its reads:

- Selector `1` performs two global-base reads and selects base plus `0x48`.
- Selectors `0`, `2`, and `-1` each perform one global-base read and select the unadjusted base.

Equivalent selected addresses do not make the one-read and two-read paths interchangeable.

### Changing global base

Suppose the unconditional base read observes address A, while the selector-`1` reread observes address B.

The selected address is B plus `0x48`, not A plus `0x48`. The count is read from B plus `0x88`, and, if validation requires it, the bound from B plus `0x8C`.

No selected-record access through A is established by this invocation. The earlier read of the global base nevertheless occurred.

### Negative metadata

A count of `-1` does not produce `5`; it produces `6` for every index.

A positive count with a zero or negative bound also rejects every index with `6`. Negative indices skip the bound read; nonnegative indices read it.

### Count-field alias

Given count `17`, bound `18`, and index `16`, validation accepts the index.

The index equals the initial last position, so shifting is bypassed. Clearing entry position `16` clears the count itself. The final decrement then reads zero and stores `-1`. Status is `0`.

This demonstrates that the final count need not equal the initial count minus one.

The gate’s meaning and the bound’s semantic identity remain unestablished. Calling the bound a capacity or a selected position would add unsupported meaning.
