# F-8d603c281c73

## Purpose

F-8d603c281c73 conditionally removes a designated node from a linked, tree-shaped structure. On its removal path, it updates structural links, conditionally adjusts one-byte node states, links the removed node into a container-associated list, decrements a 32-bit count, and writes a 32-bit result to caller-provided storage.

Two outcomes are established:

- A nonzero result from F-d747682ef415 bypasses this function’s removal operations. The output is then reloaded from the container’s header-address field.
- A zero result invokes F-577be888b76b and proceeds with removal of the node subsequently read from the input location. The output is the then-current local result word.

The layout and repair operations suggest a red-black tree with a header recording its root and extrema. This is inferred intent, not an established guarantee of ordering, balancing, or correctness for arbitrary inputs.

## Behavior

### Initial decision

The first observations are the input-location word and then the container’s header-address word. They are copied into separate local 32-bit words.

F-d747682ef415 receives the addresses of those local words. It may modify them; its wider effects are unknown.

If its return value is nonzero, the function reloads the container’s header-address word into the local result word and writes that result to the output destination. It performs none of its own structural removal, repair, list insertion, or count decrement on this path. This does not imply that the dependency had no side effects.

If its return value is zero, F-577be888b76b receives the address of the local result word. After that call returns, the function rereads the input location to obtain the requested node address. Removal therefore uses neither an assured original input snapshot nor necessarily the value held in the local result word.

### Structural case selection

The requested node’s left-child field is read first.

- If the left child is null, the right child determines whether the node is a leaf or has one replacement child.
- If the left child is nonnull and the right child is null, the left child is the replacement.
- If both children are nonnull, selection starts at the right child and follows left-child links until reaching a node whose left child is null. This node is called the successor below. Its right child is the possible replacement at its former position.

Some fields are read repeatedly rather than captured in a single structural snapshot. No key comparison, payload comparison, or payload copying participates in selection.

### Leaf removal

The initial repair position is the requested node’s parent.

If that parent equals the container’s current header address, the direct writes occur in this order:

1. Header right-extreme becomes the parent address, which matched the header.
2. Header left-extreme becomes that same address.
3. Header root becomes zero.

These are separate writes, with header-address reloads between operations; they are not an atomic empty-container update.

Otherwise, the parent’s left-child field is compared with the requested node. An exact match selects the left link; any other value selects the right link. The selected 32-bit link is cleared through four consecutive one-byte writes in increasing address order.

Only the corresponding header extreme is then considered: left-extreme for a left-link removal, right-extreme otherwise. If that extreme equals the requested node, it becomes the parent address.

### Removal with one child

The nonnull child becomes the repair position and structural replacement.

The replacement’s parent is first assigned the requested node’s parent. The current header root is then compared with the requested node:

- A match redirects the root to the replacement.
- Otherwise, the requested node’s parent is consulted. An exact left-child match redirects its left link; otherwise, its right link is redirected.

The left-extreme and right-extreme fields are checked separately, in that order, and changed only when equal to the requested node.

For the left-extreme update:

- If the requested node’s right child is null, the new extreme is its parent.
- Otherwise, the new extreme is found by following left-child links from the replacement.

For the right-extreme update:

- If the requested node’s left child is null, the new extreme is its parent.
- Otherwise, the new extreme is found by following right-child links from the replacement.

The requested node remains the object later linked into the container-associated list.

### Removal with two children

The successor is moved into the requested node’s structural position; payloads are not exchanged.

The direct structural changes have this order:

1. The requested node’s left child receives the successor as parent.
2. The successor receives that left child.
3. The successor’s former position is handled.
4. The root or the requested node’s parent link is redirected to the successor.
5. The successor receives the requested node’s parent.
6. The two nodes’ state bytes are exchanged.

If the successor is the requested node’s immediate right child, a nonnull successor right child receives the successor as parent. The successor’s right-child field is not separately reassigned in this case.

Otherwise, a nonnull successor right child receives the successor’s former parent. That parent’s left link is assigned the successor’s former right child, including null when applicable. The successor then receives the requested node’s right subtree, and that subtree receives the successor as parent.

The repair position is the successor’s former right child if nonnull. Otherwise, it is the successor itself. This latter case uses the concrete successor address, not an abstract null position.

The successor receives the requested node’s then-current state; the requested node then receives the saved byte. Immediately after this exchange, the requested node therefore holds the successor’s saved pre-exchange state.

The requested node is the object subsequently linked into the container-associated list. Its state **at retirement is not unconditionally established by the exchange**. ### Conditional state repair

Repair is entered only if the repair position differs from the currently loaded header address and the retiring node’s state byte is nonzero. When the position equals the header, the retiring state need not be read for this decision.

Within an entered repair sequence, each iteration first compares the repair position with the current root. A match finishes repair without requiring that iteration’s position-state read. Otherwise, repair also finishes if the position’s state is anything other than exactly 1.

For a state-1 position below the root, its parent is read. An exact match with the parent’s left child selects the left orientation; all other cases select the mirrored orientation.

| Orientation | Sibling | Inner sibling child | Outer sibling child |
|---|---|---|---|
| Position matches parent’s left child | Parent’s right child | Sibling’s left child | Sibling’s right child |
| Otherwise | Parent’s left child | Sibling’s right child | Sibling’s left child |

The repair cases are:

- **Missing sibling:** The current position is assigned state 0, and repair continues from the parent.
- **Sibling in state 0:** The sibling is assigned state 1, then the parent state 0. An orientation-dependent dependency is called. The position’s parent and corresponding sibling are reloaded. If the sibling is now absent, the missing-sibling case applies using the reloaded parent.
- **Both sibling children null or exactly state 1:** The sibling is assigned state 0, and repair continues from the position’s then-current parent.
- **Outer child null or exactly state 1, after the preceding both-child condition failed:** The inner child is assigned state 1 when present, then the sibling is assigned state 0. The opposite-orientation dependency is called, and the sibling is reloaded through the position’s parent. If now absent, repair finishes.
- **Final case:** The sibling receives the parent’s state byte; the parent is assigned state 1; the sibling’s outer child is assigned state 1 when present. An orientation-dependent dependency is called, and repair finishes.

The inner-child condition is considered before the both-child decision’s outer-child condition. The outer-child field and state can be read again for the subsequent case. Dependencies can invalidate assumptions based on earlier reads; only the explicit reloads are established.

Every exit from an entered repair sequence reaches a final write of state 1 to the current repair position. This includes exits caused by a root match, a position state other than 1, or a missing reloaded sibling after an inner adjustment.

The branch conditions do not treat all nonzero states alike. For example, a position in state 2 exits the loop and is assigned state 1; a sibling child in state 2 does not satisfy an “exactly state 1” condition.

### Retirement and output

After structural removal and any repair, the function:

1. Copies the current container list-head word into the retiring node’s offset +12.
2. Stores the retiring node’s address as the container list head.
3. Reads the 32-bit count, decrements it by one, and writes it back.
4. Writes the then-current local result word to the result destination.

The retiring node’s parent and left-child fields are not systematically cleared. Its right-child field is repurposed as list linkage. There is no direct storage release.

The final result is not recomputed from the retiring node address. Its meaning depends on the earlier dependency operations and any subsequent effects on the local result storage.
