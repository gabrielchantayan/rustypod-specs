# F-1669c519a031

## Purpose

F-1669c519a031 traverses records from a fixed source, processes each successful record’s identifiers against shared tracking storage, and conditionally invokes a caller-supplied callback.

Identifier processing precedes callback eligibility. Consequently, a record can cause direct tracking writes even if it is subsequently excluded from callback delivery or its callback requests termination. This establishes write ordering, not persistence: dependencies and the callback have unknown effects and may alter the same storage.

The established contract covers call sequencing, argument relationships, storage widths, conditional direct writes, and normal termination. Descriptions such as “record,” “enumeration,” and “tracking” express observed roles; their application-level meaning is not established.

## Interface

### Inputs and return

The function accepts:

1. **A callback address.** For each eligible record, the function invokes this address with seven arguments:

   | Position | Value |
   |---|---|
   | 1 | The 32-bit context obtained once from F-33c2b4a03348 during setup |
   | 2 | The attribute buffer’s first byte, interpreted as an unsigned 8-bit value |
   | 3 | The 32-bit value in metadata output B |
   | 4 | The 32-bit value in metadata output C |
   | 5 | Zero |
   | 6 | The 32-bit result of F-44362605ab79 called after record processing |
   | 7 | The 32-bit value in metadata output A |

   The callback result is tested as a 32-bit integer. Zero stops enumeration; any nonzero result permits continuation.

2. **A continuation argument.** An opaque 32-bit value passed unchanged to F-41e251a24ab6 after each nonzero callback result. It is not otherwise interpreted.

The function returns no value. It supplies no explicit error result.

The attribute byte and metadata arguments are read after record processing and the second conversion call, not necessarily as they were when enumeration returned. Their relative evaluation order within callback argument preparation is not established.

- Three separate 32-bit metadata outputs.
- A 32-bit identifier cursor-like value.
- Saved 32-bit context and record-seed values.

The metadata names are defined by their output-address order in the enumeration call:

## Behavior

### Setup

The function establishes a zero attribute mask and retains the fixed source reference, callback address, and continuation argument.

The externally relevant setup order is:

1. F-bfade2068003 receives `8` and `0`.
2. F-33c2b4a03348 is called; its result is saved as the callback context.
3. F-ddeb195e4df1 receives the enumeration-state address, fixed source reference, zero attribute mask, and another zero.
4. A global 32-bit record-seed value is read and saved.

The seed is sampled after enumeration initialization. The function does not explicitly reread that global during subsequent iterations. Likewise, the callback context is acquired once, rather than once per record.

The fixed source’s contents and interpretation are not established.

### Enumeration attempts

Before every call to F-b84ca98fab94, the function:

- Assigns the saved seed to the current record’s first word.
- Assigns zero to its second word.
- Resets metadata B and C to zero.

It does not explicitly reset metadata A, either byte buffer, or the cursor-like storage at this point.

F-b84ca98fab94 then receives the storage addresses in the order specified under Interface.

If its result is zero, enumeration ends immediately. That attempt performs no identifier processing, eligibility evaluation, callback invocation, or continuation notification. Final current-record cleanup still occurs.

If its result is nonzero, identifier processing begins. No distinction between exhaustion and an enumeration error is visible on the zero-result path.

### Identifier processing

For each successful enumeration result:

1. F-d8cbf9aa79a9 receives the current record’s second word. Its unsigned 32-bit result is saved as the identifier count.
2. F-44362605ab79 receives the current-record address. Its 32-bit result initializes cursor-like storage.
3. The function performs the reported number of identifier iterations, subject to normal execution of dependencies and memory accesses.

The conversion call occurs even when the identifier count is zero. The count is obtained before that conversion and is not recomputed if conversion changes the record.

Each identifier iteration has this ordering:

1. Load the selected shared-object address through the global tracking-object reference.
2. Call F-d3922c7fe0ec with the cursor-like storage address, obtaining an unsigned 32-bit identifier.
3. Determine the bitmap word index by unsigned division by 32 and the bit position by remainder modulo 32.
4. Call F-88658862e573 with the selected object address, word index, and bit position.
5. If the test result is zero:
   - Read the selected object’s count-like field at offset 4.
   - Write its incremented value.
   - Access the bitmap through the pointer field at offset 8.
   - Read the selected bitmap word and write it with the selected bit set.
6. If the test result is nonzero, perform neither direct update.

The selected object address is captured before the identifier-reading call and reused for that iteration. If either dependency changes the global object selection, the current iteration still uses the captured address. The next identifier iteration loads the selection again.

The bitmap pointer is accessed after the test dependency returns. It must not be assumed to have the value it held before that call.

The count-field write precedes the bitmap-word write. The function does not independently test the bit before incrementing: the zero result from F-88658862e573 controls both direct writes.

### Integer and address boundaries

Identifiers, identifier counts, and the loop counter are unsigned 32-bit quantities. A count of zero produces no identifier iterations. A count of 4,294,967,295 requests that many iterations; normal loop termination does not require incrementing the counter past that value.

Across the full identifier range:

- Word indices range from 0 through 134,217,727.
- Bit positions range from 0 through 31.
- Bitmap-word byte displacements range from 0 through 536,870,908.

The word-index multiplication by four stays within an unsigned 32-bit quantity. Adding that displacement to the bitmap base still requires a valid, accessible address; the function provides no capacity check.

The bit update is represented as setting one bit while preserving other bits read from the word. Bit position 31 selects the high bit. Portable signed-shift behavior is not established by the supplied representation.

The count-like increment uses a signed 32-bit view. Overflow behavior is unresolved. Saturation, an overflow error, and portable wraparound must not be assumed.

### Eligibility evaluation

Only after all identifier iterations does the function evaluate callback eligibility.

The condition combines:

- A zero intersection between the local attribute mask and the attribute buffer’s first byte.
- A zero first byte in the control buffer.

The local mask is initialized to zero and has no visible subsequent assignment. It therefore excludes no attribute-byte value under the visible execution model.

The control byte is read at eligibility evaluation, after identifier processing. Its value when enumeration returned is not necessarily its value at this later read. Enumeration received the buffer address; retention and later modification through dependencies are not ruled out.

If the control byte is nonzero at evaluation, record processing, callback delivery, and continuation notification are skipped. In-loop current-record cleanup follows, then another enumeration attempt.

### Callback delivery and continuation

For an eligible record:

1. F-f0b79b581bd5 receives the current-record address, zero, and the same fixed source reference used during setup.
2. F-44362605ab79 receives the current-record address again.
3. The callback is invoked using the argument mapping in Interface.

The second conversion is distinct from the earlier cursor-initialization conversion and follows record processing. Its result need not equal the earlier result.

The attribute byte and metadata B, C, and A are read for callback argument preparation after both of these dependency calls. They are not guaranteed to retain enumeration-return values. The supplied evidence does not establish dependency purity, preservation of retained output storage, or a particular relative order among these argument reads.

Eligibility is not reevaluated after record processing or the second conversion. A subsequent change to the control buffer does not introduce another visible eligibility check.

If the callback returns zero:

- The loop ends.
- F-41e251a24ab6 is not called for that record.
- No further enumeration attempt occurs.
- Final cleanup follows.

If the callback returns nonzero:

- F-41e251a24ab6 receives the original continuation argument exactly once.
- In-loop current-record cleanup follows.
- Another enumeration attempt follows cleanup.

### Cleanup and return

An unmapped operation receives the current-record address:

- Once after each processed record that continues, whether delivered or skipped.
- Once after loop exit, whether caused by a zero enumeration result or a zero callback result.

A callback-terminated record does not receive both an in-loop and final cleanup call; that exit bypasses in-loop cleanup.

After final current-record cleanup:

1. F-eecd2e1474fa receives the enumeration-state address.
2. F-85722f62e20a receives `8` and `1000`.
3. The function returns without a result.

These guarantees apply to normal control flow. No exception handling, fault recovery, or protection against dependency-driven nonlocal exits is visible.

## Side effects

### Direct effects

For each zero result from F-88658862e573, the function directly performs one count-like increment and one bitmap-word write, in that order.

Those write events precede eligibility evaluation and any callback for the record. This does not guarantee that their values persist: intervening or later dependencies may alter the tracking object, bitmap, or selection.

The function reads the record-seed global once and reloads the shared-object selection once per identifier iteration. It does not visibly assign either global reference.

### Dependency effects and ownership

Dependencies and the callback may have additional effects. No preservation guarantee is established for globals, records, metadata, buffers, or shared tracking storage.

The enumeration dependency receives addresses of the local output storage. The evidence does not establish whether it retains those addresses or whether later dependencies can modify that storage. This matters at the later control-byte and callback-argument reads.

The enumeration state and current-record storage are local to the invocation. Passing their addresses does not establish ownership transfer. The cleanup-shaped operation’s actual behavior—release, reset, reference adjustment, or otherwise—is unknown.

The callback receives a converted record-related value, not an established ownership grant. Its validity after callback return, record cleanup, or function return is documented_only. No right to retain or release that value is established.

No synchronization, atomicity, or reentrancy guarantee is visible.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests.

### Empty enumeration

If the first enumeration result is zero, there are no identifier-processing or callback calls. Current-record cleanup runs once, followed by enumeration-state finalization and the final `8, 1000` call.

The cleanup input has the prepared record values unless enumeration changed them.

### Metadata initialization and delivery

If enumeration leaves B and C untouched and no subsequent dependency changes them, callback arguments 3 and 4 are zero.

If A, B, and C contain usable values of 101, 202, and 303 when callback arguments are read, arguments 3, 4, and 7 are respectively 202, 303, and 101. A has no explicit per-attempt default.

### Control-byte changes before eligibility

Suppose enumeration returns with a zero control byte, but identifier processing changes that byte to nonzero. If it is nonzero when eligibility is evaluated, no callback occurs.

Conversely, a nonzero byte at enumeration return does not itself exclude the record if the byte is zero at eligibility evaluation.

In either case, any direct tracking writes occur before the eligibility decision. Their persistence is not guaranteed.

### Values changed after eligibility

Suppose the record passes eligibility, and record processing or the second conversion changes the attribute byte or metadata through retained storage addresses. The callback receives those values as read afterward, rather than guaranteed enumeration-return values.

A control-byte change during those calls does not cause a second eligibility check.

### Bitmap boundaries and repeated identifiers

Given valid storage, a zero tracking-test result, and a valid increment:

| Identifier | Word index | Bit position |
|---:|---:|---:|
| 0 | 0 | 0 |
| 31 | 0 | 31 |
| 32 | 1 | 0 |
| 4,294,967,295 | 134,217,727 | 31 |

Each occurrence causes the count write followed by the corresponding bit-setting write.

For repeated identifiers, two zero test results cause two increments, even if the bit is already set. A nonzero second test result suppresses both direct writes for that occurrence. Deduplication therefore depends on dependency behavior.

### Callback termination and continuation

For a zero callback result, identifier processing, record processing, and the second conversion have already occurred. No continuation notification follows; final record cleanup and finalization do.

For a nonzero callback result, the original continuation argument is passed once to F-41e251a24ab6 before record cleanup and the next attempt.

### Shared-object reselection

If identifier reading changes the global object selection, the current identifier still uses the previously captured object address. The next identifier iteration reloads the selection.
