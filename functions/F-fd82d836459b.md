# F-fd82d836459b

## Purpose

F-fd82d836459b associates a non-null record sequence with a caller-supplied state object, counts the records preceding a sentinel, and adjusts an embedded sequence of four-byte elements toward that count.

The established behavior is narrower than a general-purpose resize operation:

- The record count is discovered by examining a two-byte field in successive 24-byte records.
- The discovered count is written into the state before any dependency is called.
- An embedded sequence is queried and conditionally passed to a growth dependency or subjected to trailing-element cleanup.
- A temporary four-byte value is passed to a cleanup dependency.
- The input record address is committed to the state last.
- The return value reports only whether the input record address was non-null. It is not an independently checked success indication for allocation, cleanup, or resizing.

The interpretation of the embedded storage as a container, and of the dependency calls as size, growth, and destruction operations, is inferred intent. The field accesses and dependency-call ordering below are established static evidence.

## Interface

### Inputs

The function has two arguments:

1. **State address.** A pointer to writable storage containing at least four consecutive four-byte fields.
2. **Record-sequence address.** An address represented by a 32-bit integer in the supplied representation. Zero selects the no-operation path.

The visible state layout is:

| Byte offset | Width | Established use |
|---|---:|---|
| 0 | 4 bytes | Receives the record-sequence address at the end of the non-null path. |
| 4 | 4 bytes | Receives the discovered record count before dependency calls. |
| 8 | 4 bytes | Beginning of the embedded object passed to dependencies; also read as an element-storage start address on the shortening path. |
| 12 | 4 bytes | Read as an element-storage endpoint or insertion position; conditionally adjusted on the shortening path. |

Dependencies receive the address at state offset 8, not the address of the entire state object. Their complete object-layout requirements are unknown. The four visible fields therefore do not establish the minimum storage size required by those dependencies.

The record layout relevant to this function is:

| Record-relative offset | Width | Established use |
|---|---:|---|
| 4 | 2 bytes | Unsigned sentinel-discrimination field. |
| Other bytes | — | Not directly read by this function. |
| Record stride | 24 bytes | Distance to the next discriminator field. |

The sentinel comparison uses an externally stored comparison value. Its numeric value and declaration width are not supplied.

### Output

The result is a Boolean:

- **False:** the record-sequence address is zero.
- **True:** the record-sequence address is nonzero and execution reaches the return.

There is no explicit error result for an inaccessible sentinel, invalid state, allocation failure, inconsistent storage endpoints, or dependency failure.

### Preconditions for defined completion

For the non-null path:

- The record sequence must provide readable two-byte discriminator fields at 24-byte intervals through a matching sentinel.
- Address progression and element-address calculations must be valid for the execution environment.
- The state must permit the reads and writes described here.
- The embedded object must satisfy the preconditions of the dependencies invoked.
- Any trailing-element range used by the shortening path must be valid for repeated four-byte advancement and cleanup.
- Dependencies must return normally for the function to reach its final state commit and Boolean return.

The null path does not dereference the state address.

## Behavior

### Null input

A zero record-sequence address causes an immediate false result.

This path performs no direct state access, no record read, and no dependency call. In particular, the function does not clear a previously stored address, count, or embedded sequence.

### Sentinel scan

For a nonzero record-sequence address, the function begins with a 32-bit unsigned count of zero.

It reads the two-byte discriminator at offset 4 of the first record and compares it with the external sentinel value. For each nonmatching record, it increments the count and advances the record address by 24 bytes. The first matching record terminates the scan and is excluded from the count.

Only the discriminator field is directly inspected. No other record content is copied or validated.

The sentinel value is referenced by the comparison on each scan iteration. The supplied evidence does not establish a single cached sentinel value for the entire scan. Stability of that external value must not be assumed if some outside actor can modify it.

The function does not impose a maximum record count, validate the address range, or provide a fallback when no sentinel is reachable.

The count is explicitly unsigned and 32 bits wide. Its increment therefore has a modulo-\(2^{32}\) interpretation. That fact does not make overflowing address traversal valid or guarantee that an extremely long scan can complete safely.

### Early count publication and temporary initialization

After finding the sentinel, the function writes the discovered count to state offset 4.

It then prepares the embedded-object address at state offset 8 and initializes a local four-byte temporary to zero.

This ordering matters: the published count already has its new value when the first dependency is called, while the record-sequence address at state offset 0 has not yet been updated.

If the supplied record storage overlaps the state, the complete scan occurs before this count write. The function neither prohibits overlap explicitly nor provides general alias protection.

### First size observation and branch selection

The function calls F-af60ab6f2bde with the embedded-object address. Its result is treated as a 32-bit unsigned quantity and compared with the discovered count.

There are two branches:

- If this first result is smaller than the count, the function takes the growth path.
- Otherwise, it takes the non-growth path and obtains another size observation.

The first result is not retained as the authoritative size for subsequent arithmetic. Both branches call F-af60ab6f2bde again before deciding their remaining work.

Consequently, callers must not assume that the two observations are equal or that the dependency is free of side effects.

### Growth path

When the first size observation is smaller than the discovered count, the function:

1. Reads the four-byte field at state offset 12 and retains that value as the insertion-position argument.
2. Calls F-af60ab6f2bde a second time with the embedded-object address.
3. Forms a 32-bit unsigned difference: discovered count minus the second result.
4. Calls F-696c4949eef0 with:
   - the embedded-object address;
   - the previously captured insertion position;
   - the unsigned difference;
   - the address of the zero-initialized four-byte temporary.

The insertion position is captured **before** the second size call. If that call changes the field at offset 12, the growth dependency still receives the earlier value.

There is no second check that the newly observed size remains smaller than the count. If it equals the count, the growth dependency receives a zero difference. If it exceeds the count, subtraction wraps modulo \(2^{32}\).

The function does not inspect a return value from F-696c4949eef0 or perform a visible postcondition check afterward.

### Non-growth path

When the first size observation is at least the discovered count, the function calls F-af60ab6f2bde again.

- If the second result is equal to or smaller than the count, no direct shortening work is performed.
- If the second result is larger than the count, the shortening path runs.

Thus a first observation larger than the count does not by itself guarantee shortening. Conversely, a second observation smaller than the count does not cause growth from this branch.

### Shortening path

The function first captures the endpoint from state offset 12.

It then reads the start address from state offset 8 and computes a target address by advancing that address by the discovered count in four-byte elements. The byte displacement is therefore four times the count, subject to valid address arithmetic.

The function reads the start field again and compares it with the captured endpoint.

If those values are equal, the shortening block does nothing further: there are no trailing-element cleanup calls and no endpoint adjustment.

Otherwise:

- An apparent element-transfer loop has identical initial source and terminal addresses. Its body therefore executes zero times in the supplied control flow.
- No element copying is established by that loop.
- The function reloads state offset 12 once to obtain the cleanup termination address.
- Starting at the computed target address, it calls F-6f30a944789d on each four-byte slot until the advancing address equals that reloaded endpoint.
- The cleanup termination address is not refreshed after individual cleanup calls.

This is an equality-terminated traversal, not a bounds-checked traversal. If the starting address and termination address do not describe a reachable four-byte-stepped range, the function has no visible protection against invalid access or failure to terminate.

After cleanup, the function adjusts state offset 12. The amount subtracted is the byte difference between the originally captured endpoint and the computed target address, with the lowest two bits cleared. That amount is subtracted from the **then-current** value of state offset 12.

For coherent four-byte-aligned storage whose endpoint remains unchanged during cleanup, this places the endpoint at the target address. That outcome is conditional, not universal. If cleanup changes the endpoint field, the final adjustment is applied to the changed value. The function does not simply assign the target address.

### Final cleanup and address commit

After either resizing branch completes, the function calls F-6f30a944789d with the address of the local four-byte temporary.

This call occurs even when:

- The count is zero.
- No growth or shortening occurred.
- The growth dependency was not called.
- The temporary remains zero.

If the growth dependency modified the temporary, the final cleanup receives its modified contents.

Only after this cleanup call returns does the function write the input record-sequence address to state offset 0. It then returns true.

The count at offset 4 is not rewritten at the end. A dependency that changes it can therefore affect the final state.

## Side effects

### Direct memory effects

The non-null path directly:

- Reads record discriminator fields until a sentinel match.
- Reads the external sentinel comparison value during scanning.
- Writes the discovered count to state offset 4.
- Reads embedded-storage fields on the applicable paths.
- Conditionally adjusts the endpoint at offset 12.
- Writes the record-sequence address to offset 0 after final temporary cleanup.

It does not directly allocate memory, release record storage, copy record contents, or establish ownership of the supplied record sequence.

### Dependency-mediated effects

Dependencies may read or modify the embedded object, the temporary, surrounding state, globals, or other reachable memory. Their implementations are not provided.

No preservation guarantee is established for globals or state fields across dependency calls. In particular, the contract must preserve the distinction between captured values and later field reloads.

Passing slot addresses to F-6f30a944789d does not by itself prove that it frees an allocation, destroys an owned object, or leaves the slot unchanged.

### Partial completion

The visible ordering permits partial state updates if execution stops before normal return:

- A scan failure occurs before the function publishes the count.
- A failure during dependency processing can occur after the count is published but before the record address is committed.
- A failure during final temporary cleanup prevents the final record-address write.

There is no visible rollback mechanism.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests.

1. **Null input preserves state directly.**  
   Given a zero record-sequence address, the result is false, with no state dereference and no dependency call.

2. **Immediate sentinel produces count zero.**  
   Given a matching discriminator in the first record, the function publishes zero at offset 4. Both size observations and final temporary cleanup still occur. Shortening depends on the second size result and the storage-field conditions.

3. **Two records precede the sentinel.**  
   Given nonmatching discriminators at relative offsets 4 and 28 and a matching discriminator at offset 52, the published count is two. No subsequent record discriminator is required by this scan.

4. **Stable growth from two elements to five.**  
   Given a discovered count of five and size observations of two and two, F-696c4949eef0 receives a difference of three, the endpoint captured before the second observation, and the temporary’s address. Final temporary cleanup precedes the record-address commit.

5. **Changed size on the growth path is not revalidated.**  
   Given a count of five, a first size result of two, and a second result of six, the growth dependency receives \(2^{32}-1\), not a rejected request.

6. **Equal sizes avoid element cleanup.**  
   Given both size results equal to the discovered count, no growth call and no trailing-slot cleanup occur. The local temporary still receives its cleanup call.

7. **Stable shortening cleans the trailing slots.**  
   Given a count of two, both size observations equal to five, a valid start address, an endpoint five four-byte elements later, and dependencies that preserve these fields, trailing cleanup receives the addresses at byte displacements 8, 12, and 16 from the start. The endpoint is then adjusted to displacement 8.

8. **An empty storage representation bypasses shortening work.**  
   Given that the shortening branch is selected but the reread start equals the captured endpoint, no trailing-slot cleanup or direct endpoint adjustment occurs.

9. **The second observation controls shortening.**  
   Given a count of five, a first size result of seven, and a second result of four, neither growth nor shortening occurs. The count has nevertheless already been published as five.

## Uncertainties

The following remain **documented_only**:

- The sentinel’s numeric value, declared width, and stability.
- The complete embedded-object layout and required allocation size.
- Whether F-af60ab6f2bde measures four-byte elements, despite that interpretation fitting the surrounding accesses.
- The growth dependency’s allocation, insertion, and ownership semantics.
- The cleanup dependency’s actual effects on slots, allocations, globals, or state.
- Whether dependencies can fail through exceptions, termination, nonlocal control transfer, or other mechanisms.
- Valid concurrency, reentrancy, and aliasing conditions.
- Behavior for malformed storage ranges or invalid pointer arithmetic.
- Whether the zero-iteration transfer loop reflects an intentional implementation or an imperfect recovered representation.

Inferred intent must not replace the observed repeated queries, conditional endpoint adjustment, or final commit ordering.
