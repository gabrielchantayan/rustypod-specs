# F-03b35c352059

## Purpose

F-03b35c352059 conditionally detaches a supplied record from a linked structure, clears three linkage fields in that record, adjusts structural counters, and invalidates two owner-associated state slots.

The established behavior is narrower than “remove any record.” Two dependencies can reject the operation before linkage processing. An additional consistency check rejects a record with no parent and no neighbors unless both owner-level endpoints identify that record. Other linkage configurations are not validated before modification.

**Inferred intent:** the structure appears to support owner-level lists and parent-owned child lists, with direct-child and ancestor-associated counts. The final two slots appear to represent state requiring invalidation after a structural change. Those interpretations are not required to describe the observed field operations.

The function has no explicit return value. Completion, rejection, and partial execution are distinguishable only through side effects or external behavior.

## Interface

### Input and result

The function accepts one 32-bit value used as the address of a record, called the **target** in this contract. It returns no explicit result.

The supplied representation uses four-byte fields and 32-bit address-bearing values. A zero address-bearing field is treated as absent. No target-null check is present.

All offsets below are byte offsets from the relevant record address. The names describe operational roles, not independently established type declarations.

### Preconditions

For a normally completing call, every address actually dereferenced must identify suitably accessible storage. Writable fields must permit four-byte writes. Traversed parent links must eventually reach zero.

The function does not establish these conditions. It does not validate address ranges, alignment, ownership consistency, reciprocal neighbor links, counter ranges, or acyclicity.

Because the first gate precedes all direct target reads, a target that would otherwise be invalid need not be dereferenced when that gate returns zero. That is an access-order property, not a general guarantee that invalid targets are accepted.

## Behavior

### 1. Apply two gates and capture the owner

The function first calls F-3b037d560480 without explicit arguments.

- If its 32-bit result is zero, the function returns immediately.
- Otherwise, the function reads the target’s owner field at `+0x0c`.

It then calls F-06f4ceb6a4f2 with that captured owner value.

- If the result is zero, the function returns immediately.
- Any nonzero result permits further processing; the magnitude is not otherwise used.

No direct structural writes by F-03b35c352059 occur before both gates succeed. The dependencies themselves may have side effects; their preservation of memory or global state is not established.

The captured owner address is used throughout the remainder of the function. The target’s owner field is not reread after the second gate.

### 2. Capture the parent and choose the first unlink write

After both gates succeed, the function reads and retains the target’s parent field at `+0x10`. This captured value controls parent-specific endpoint updates and later counter traversal, even after the target’s parent field is cleared.

The first linkage update follows these cases:

| Captured parent | Target predecessor | Additional condition | First linkage write |
|---|---|---|---|
| Any value | Nonzero | None | Predecessor’s successor becomes the target’s successor |
| Nonzero | Zero | None | Captured parent’s first-child endpoint becomes the target’s successor |
| Zero | Zero | Target successor is nonzero | Owner’s first endpoint becomes the target’s successor |
| Zero | Zero | Target successor is zero and both owner endpoints identify the target | Owner’s first endpoint becomes zero |
| Zero | Zero | Target successor is zero and either owner endpoint does not identify the target | Return without direct writes |

The last case is the only explicit linkage-consistency rejection.

For the isolated, parentless case, the owner’s first endpoint is read first. The owner’s last endpoint is read only if the first endpoint equals the target. The operation proceeds only if both comparisons succeed.

Consequently:

- A parentless target with neither neighbor is accepted only when both owner endpoints equal it.
- A target with a parent is not subject to that owner-endpoint check.
- A target with either neighbor is not subject to that owner-endpoint check.

Neighbor reciprocity is not checked. A nonzero predecessor is trusted as the destination of the first write.

### 3. Choose the second unlink write

After the first linkage write, the function reads the target’s successor field again.

- If the successor is nonzero, that successor’s predecessor field becomes the target’s current predecessor.
- If the successor is zero and the captured parent is nonzero, the captured parent’s last-child endpoint becomes the target’s current predecessor.
- If the successor is zero and the captured parent is zero, the owner’s last endpoint becomes the target’s current predecessor.

This establishes the normal two-sided unlink behavior: first repair the predecessor side or first endpoint, then repair the successor side or last endpoint.

The target’s neighbor values are not both snapshotted before the writes. The successor and predecessor fields are read at multiple points. If address ranges overlap, an earlier write can therefore affect a later read. The ordinary interpretation as list removal assumes records and relevant fields do not overlap in a way that changes those reads.

### 4. Clear the target’s linkage fields

After both unlink writes, the function performs these four-byte stores in order:

1. Clear the target’s parent field at `+0x10`.
2. Clear its successor field at `+0x14`.
3. Clear its predecessor field at `+0x18`.

The target’s owner field at `+0x0c` is not directly cleared.

No separate membership flag is written. Detachment is represented by the linkage and endpoint changes plus the cleared linkage fields.

### 5. Adjust parent and ancestor counters

This phase runs only when the captured parent is nonzero.

First, the captured parent’s counter at `+0x20` is tested. If it is nonzero, the field is reread and decreased by one. A zero value is left unchanged.

The function then traverses from that same captured parent:

- At each visited record, its counter at `+0x1c` is tested.
- If nonzero, that counter is reread and decreased by one.
- The next record is obtained from the current record’s parent field at `+0x10`.
- Traversal ends when that next address is zero.

Thus, in an ordinary acyclic hierarchy, the direct parent receives both the `+0x20` update and the `+0x1c` update. Higher ancestors receive only the `+0x1c` update.

There is no visited-record tracking or cycle detection. Counter values do not control traversal termination. A zero counter prevents only that counter’s decrement; it does not stop ascent.

The traversal uses live parent fields, not a precomputed ancestor sequence.

### 6. Decrement the owner counter

After parent processing, or immediately after clearing the target’s links when there is no captured parent, the function decreases the owner’s counter at `+0x30` by one.

Unlike the parent-associated counters, this decrement is unconditional. An initial zero does not suppress the operation.

All affected counters occupy 32 bits. No widening, overflow check, or saturation is shown. Under ordinary 32-bit machine subtraction, decrementing zero produces the bit pattern `0xffffffff`. The supplied representation does not independently establish a language-level signed-overflow contract for every possible counter value.

### 7. Process the two owner state slots in order

The function next reads the owner’s first state slot at `+0x910`.

- If zero, it makes no call for that slot.
- If nonzero, it calls F-1137792fba7d without an explicit argument and then writes zero to that slot.

Only after this first-slot processing does it read the second slot at `+0x914`.

- If zero, the function returns.
- If nonzero, it calls F-1137792fba7d without an explicit argument, then writes zero to that slot and returns.

The second decision uses the value observed after any first call. It is not based on a snapshot taken before invalidation begins.

Each slot is cleared after its corresponding dependency call returns, not before. If the dependency modifies that same slot and returns normally, the subsequent zero write replaces its modification.

- A predecessor’s successor field or a first endpoint.

- The target’s three linkage fields.
- The captured parent’s direct-parent-associated counter.
- Counters along the captured parent’s ancestor chain.
- The owner’s counter.
- Either or both owner state slots.

The target’s storage is not explicitly freed. No allocation, copying of record contents, or explicit deallocation is shown.

Calling F-1137792fba7d does not establish that any slot value is released: the function receives no explicit slot value or owner address. Its ownership and resource-management effects are unknown.

There is no rollback. If an invalid access, nonreturning dependency, or other execution failure occurs after writes have begun, earlier changes are not explicitly reversed.

No locking, atomic transaction, or synchronization is shown. Concurrent mutation guarantees are therefore not established. Even nonzero counter checks and their corresponding decrements use separate reads.

## Acceptance examples

These are conditional static acceptance examples, not executed tests. Unless stated otherwise, both gates succeed, dependencies return normally, storage is valid and nonoverlapping, and no concurrent mutation occurs.

### Gate rejection

If F-3b037d560480 returns zero, there are no direct target reads or structural writes by this function.

If the first gate succeeds but F-06f4ceb6a4f2 returns zero, the target’s owner has been read and passed to that dependency, but this function makes no direct linkage or counter writes.

Neither example promises that dependency calls are side-effect-free.

### Interior child

Suppose the target has a nonzero parent, predecessor, and successor.

The predecessor’s successor becomes the original successor. The successor’s predecessor becomes the original predecessor. Neither parent endpoint is directly changed. The target’s three linkage fields become zero.

The direct parent’s `+0x20` counter decreases only if nonzero. Each visited ancestor’s `+0x1c` counter decreases only if nonzero. The owner counter decreases unconditionally.

### Only child

Suppose the target has a nonzero parent and both neighbors are zero.

Both parent endpoints become zero. No comparison against either owner endpoint occurs. Counter and state-slot processing then proceeds.

### Only owner-level record

Suppose the target has no parent and no neighbors, and both owner endpoints equal the target.

Both owner endpoints become zero. The target’s linkage fields are cleared. No parent counters are visited. The owner counter is decremented.

If either owner endpoint does not equal the target, the operation instead returns before any direct write, counter decrement, or state-slot processing.

### Zero and negative-looking counters

A zero parent-associated counter remains zero, but traversal continues.

A zero owner counter is still decremented. Under 32-bit machine subtraction, its resulting bit pattern is `0xffffffff`.

The nonzero checks are not positivity checks. A counter with a negative signed interpretation is still eligible for decrement.

### State-slot interactions

If both state slots remain zero throughout their respective checks, F-1137792fba7d is not called.

If both remain nonzero until checked, it is called twice, with the first slot cleared before the second slot is inspected.

If processing the first slot causes the second slot to become zero, the second call is skipped. If it changes the second slot from zero to nonzero, a second call occurs. These outcomes follow from the live second-slot read; the dependency’s actual behavior remains unknown.
