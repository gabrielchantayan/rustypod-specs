# F-5687b5b3f1c8

## Purpose

F-5687b5b3f1c8 processes a signed-length-bounded byte sequence across an initial destination region and, when required, additional regions obtained through dependencies. It selects between two external data operations according to the signed source-run count, updates region links, and publishes a metadata value through a caller-provided output address.

Copying, clearing, allocation, linking, and release are inferred purposes of dependencies, not established implementations. The established contract is the argument construction, call order, direct memory accesses, state transitions, and return behavior described below.

The function returns zero when the remaining count is signed-nonpositive. It otherwise propagates a nonzero acquisition or conditional post-acquisition status. Earlier effects are not rolled back.

## Interface

### Arguments and result

The interface has ten arguments, each represented by a 32-bit slot.

| Position | Meaning established by use |
|---|---|
| 1 | Context address. |
| 2 | Base address used for arithmetic, metadata parsing, and the initial link location. |
| 3 | Initial source address in ordinary mode. |
| 4 | Not accessed by this function. |
| 5 | Initial source-run count; also the low word of an operand passed to F-14a62729627b. |
| 6 | High word paired with argument 5 for that arithmetic dependency. |
| 7 | Replacement source address. Also the initial source in alternate mode. |
| 8 | First extension count and, in ordinary mode, replacement-source run length. |

| 10 | Address receiving a 32-bit output value. |

Arguments 5, 8, and 9 have 32-bit unsigned representations in the supplied listing. Source-run and remaining-count decisions use signed 32-bit interpretations. Address representations are 32 bits; portability to wider pointers is not established.

The 32-bit result is:

- Zero on normal completion.
- The nonzero status from F-66c60373345b on acquisition failure.
- The nonzero status from F-97f36d1a1364 on post-acquisition failure.

No local validation status is generated.

### Operational preconditions

Reached memory accesses require valid, suitably sized storage. Dependencies must accept the argument representations passed to them, including zero handles where specified. The function does not enforce these conditions.

No non-aliasing, overlap-safety, ownership-transfer, or termination guarantee is established. Such requirements depend on dependency contracts and the caller’s objects.

## Behavior

### Entry and initial address construction

The retained handle, candidate-handle slot, and persistent candidate-index slot initially contain zero. The subordinate-state address is captured from context offset `0x40`; subsequent accesses use that captured address rather than rereading the context pointer.

Context offset `0x04` selects an adjustment of four when zero, otherwise zero. Context offset `0x07` is then read.

If extensions are disabled, both effective extension counts become zero. The preliminary arithmetic call is omitted, and the high word for the following arithmetic call remains zero.

If extensions are enabled:

1. The extension counts are added as a 32-bit unsigned sum.
2. F-14a62729627b receives the base address plus the adjustment, zero, the extension sum, and that sum’s signed high extension.
3. The returned low word is added to the adjustment.
4. The returned high word is retained for the next call.

The fourth argument is derived from bit 31 of the completed 32-bit sum: zero or all ones under the represented arithmetic-shift behavior. It is not the carry from adding the extension counts.

F-14a62729627b is then called unconditionally with:

- The base address plus the accumulated adjustment.
- The retained high word.
- Argument 5.
- Argument 6.

Only the low 32 bits of this second result are subsequently used.

F-200380a3070f next receives the context address, base address, and temporary metadata storage. No parser return value is checked.

### Mode selection and output publication

After parsing, the effective extension counts are added to form the remaining count. Context offset `0x03` is read at this point. Earlier dependencies can therefore affect mode selection by modifying that byte.

In ordinary mode:

- Argument 5 is added to the remaining count.
- The current source is argument 3.
- The source-run count is argument 5.
- The replacement-run count is the effective argument 8.

In alternate mode:

- Argument 5 is not added to the remaining count.
- The current source is argument 7.
- The source-run count is the effective argument 8.
- The replacement-run count is zero.

The initial destination is the base address plus the accumulated adjustment plus the low word of the second arithmetic result.

Initialization then proceeds in this order:

1. Read the 16-bit metadata field at offset 30 and store its zero-extended value through the 32-bit output address.
2. Read the unsigned 16-bit metadata field at offset 26 as destination capacity.
3. Read the unsigned 16-bit metadata field at offset 28 and add it to the base address to form the current link location.

The output store precedes both the first completion check and these latter metadata reads. Aliasing can therefore matter.

### Completion check

Each iteration begins by interpreting the remaining count as signed 32-bit.

If it is less than one, F-6cc778185718 receives the retained handle, and the function returns zero. This call occurs even if the retained handle is zero.

Consequently, remaining-count bits `0x80000000` through `0xffffffff` select completion rather than a large positive transfer. Address preparation, parsing, and output publication have already occurred.

### Candidate selection when capacity is zero

Acquisition is attempted only when the current capacity is exactly zero. A negative signed interpretation of a nonzero capacity does not select acquisition.

If subordinate-state offset `0x16` is nonzero, candidate search proceeds as follows:

1. Increment the persistent 32-bit index slot.
2. Call F-c76bdec3f9e1 with the captured subordinate-state address.
3. After that call returns, read the current index-slot value and save it separately.
4. Compare the query result against the current index-slot value. If equal, repeat the increment-and-query sequence.
5. Once unequal, call F-d7be9cfb4000 with `0x40000000` and the 16-bit field read from subordinate-state offset `0x1c`.
6. Compare that result plus one against the saved post-query index value. If equal, repeat the outer search.

The comparison after F-d7be9cfb4000 does **not** reread the index slot. Conversely, the comparison after F-c76bdec3f9e1 does not necessarily use the value produced by the preceding increment: it uses the slot after the query returns.

This distinction matters because F-66c60373345b receives the index slot’s address on acquisition calls. If a previous call retained that address, later dependencies could modify the slot. Neither preservation nor such modification is established.

No iteration bound is visible.

### Acquisition and failure paths

F-66c60373345b receives:

1. The captured subordinate-state address.
2. The candidate-handle slot’s address.
3. The candidate-index slot’s address.
4. The current candidate-index value.
5. Zero.

Both slots may be updated. Neither is reset before each acquisition.

After acquisition returns, subordinate-state offset `0x16` is read again, including when acquisition returned an error.

For a nonzero acquisition status, the retained handle is passed to F-6cc778185718, then the acquisition status is returned. The candidate handle is not passed to cleanup on this path.

For successful acquisition, the reread flag determines whether F-97f36d1a1364 is called. When required, it receives the subordinate-state address and the current index-slot value.

If that dependency returns a nonzero status:

1. The current candidate-handle slot value is passed to F-6cc778185718.
2. The retained handle is passed to F-6cc778185718.
3. The post-acquisition status is returned.

No successful-link commit occurs on either error path. If the candidate and retained handles have equal values, post-acquisition failure passes that value to cleanup twice; no distinctness check exists.

### Successful acquisition and escaped-slot rereads

Successful acquisition, including successful post-acquisition processing when required, is committed in this order:

1. F-cfb711b78946 receives the current link location and the current index-slot value.
2. F-6cc778185718 receives the retained handle.
3. The candidate-handle slot is read, and that value becomes the retained handle.
4. The 32-bit data address at offset `0x44` of the object selected by that candidate value is loaded and becomes the new link location.
5. F-cfb711b78946 receives this new link location and zero.
6. The candidate-handle slot is read again.
7. The 32-bit data address at offset `0x44` of the object selected by this second candidate value is loaded. That address plus four becomes the payload destination.
8. The unsigned 16-bit subordinate size at offset `0x1e` is read, and four is subtracted to obtain capacity.

These are not merely two loads from a guaranteed common object. The candidate slot has escaped through F-66c60373345b. The old-link helper or retained-handle cleanup may affect its value before the retained-handle assignment. The new-link initialization helper may affect it before the second object selection.

Therefore:

- The retained handle reflects the slot value after the old-link helper and old retained-handle cleanup.
- The first data-address load selects an object using that value.
- The second data-address load can select a different object.
- The payload destination need not belong to the retained handle.
- The stored link location remains the first loaded data address, even if the second load selects another object or address.

Even when the candidate slot is unchanged, the data-address field itself can change across the intervening dependency call.

### Span processing

The proposed span is the signed minimum of capacity and remaining count.

If the source-run count is signed-nonpositive, F-X01 receives the destination and proposed span. Its inferred purpose is clearing.

Otherwise, the span is additionally limited by a signed comparison with the source-run count. F-X02 receives the destination, current source, and resulting span. Its inferred purpose is copying.

After either operation, state changes occur in this order:

1. Subtract the span from the source-run count.
2. Advance the source address by the span.
3. If the resulting source-run count is exactly zero, replace it with the replacement-run count and reset the source address to argument 7.
4. Subtract the span from the remaining count.
5. Advance the destination by the span.
6. Subtract the span from capacity.

The source address advances even after F-X01. A signed-negative source-run count is not reset merely because it is nonpositive; the reset tests exact zero after subtraction.

In ordinary mode, a positive replacement-run count is reloaded whenever a run reaches zero. There is no separate transition to a final clearing phase while that replacement count remains positive.

## Side effects

Directly established effects include metadata publication, context and object reads, state-slot exposure, and the dependency calls above.

The following limitations are material:

- The output value is published before any transfer-loop completion or acquisition failure.
- Committed links and earlier data-operation effects are not rolled back after a later error.
- Candidate-handle and candidate-index addresses escape to F-66c60373345b. Future calls cannot be assumed to preserve those slots.
- The function maintains one retained-handle value, but this does not establish the lifetime of linked storage.
- Cleanup calls occur with zero on some paths. Their safety and meaning require F-6cc778185718’s contract.
- Link encoding, data-operation memory effects, overlap behavior, and dependency effects on aliased memory are unknown.

## Acceptance examples

These are conditional static examples, not executed tests. Unless otherwise stated, dependencies return normally and do not modify relevant state beyond the specified scenario.

1. **Zero total still publishes output.**  
   With extensions disabled, ordinary mode, and argument 5 zero, the unconditional arithmetic call and parser still run. The publication field is zero-extended into the output word. F-6cc778185718 receives zero, and the function returns zero without a data-operation call.

2. **Initial adjustment.**  
   With extensions disabled and context offset `0x04` zero, the unconditional arithmetic call receives the base plus four as its first word. If its low result is zero, the initial destination is the base plus four.

3. **Repeated replacement runs.**  
   With ordinary mode, enabled extensions, counts 3, 2, and 3 in arguments 5, 8, and 9, and sufficient initial capacity, F-X02 receives spans 3, 2, 2, and 1. The first uses argument 3; each replacement run restarts at argument 7.

4. **Alternate mode reaches F-X01.**  
   With alternate mode, enabled extensions, argument 8 equal to 2, argument 9 equal to 3, and sufficient capacity, F-X02 first receives argument 7 and span 2. F-X01 then receives span 3. Argument 5 does not contribute to the remaining count.

5. **Post-query index, then saved comparison.**  
   Suppose an earlier acquisition exposed the index slot. Search increments it from 5 to 6, but F-c76bdec3f9e1 changes it to 9 and returns 6. The inner search stops because 6 differs from the current value 9; the saved value is 9. If F-d7be9cfb4000 then changes the slot to 12 and returns 8, the outer search repeats because 8 plus one equals saved value 9. The next increment starts from 12 and produces 13.

6. **Payload and retained handle can diverge.**  
   Suppose successful commit reaches the retained-handle assignment with the candidate slot selecting a first object. Its data address becomes the new link location. If the zero-link initialization call changes the candidate slot to a second object, the payload destination uses the second object’s data address plus four. The retained handle still selects the first object, and the link location remains its previously loaded address.

7. **Post-acquisition failure.**  
   If acquisition succeeds, the reread flag is nonzero, and F-97f36d1a1364 returns 7, candidate cleanup precedes retained cleanup, and the result is 7. Neither successful-link helper call occurs.

8. **High-bit total completes immediately.**  
   If mode selection produces remaining bits `0x80000000`, output publication still occurs. The signed completion check then selects retained-handle cleanup and return zero without a data operation.

## Uncertainties

**documented_only — Arithmetic semantics.**  
Unsigned 32-bit additions and subtractions use word-width arithmetic in the listing. Signed comparisons, address expressions, signed index increment, and result-plus-one operations also appear. Exact signed-overflow and address-overflow behavior requires target-level semantics. No checked arithmetic or saturation is visible.

**documented_only — Region sizes at or below four.**  
Size four produces zero payload capacity and permits repeated acquisitions without byte progress. Smaller unsigned 16-bit sizes produce a subtraction result with a negative signed interpretation under the represented 32-bit model. Signed span selection can then pass that bit pattern to a data helper. No malformed-size rejection is visible.

**documented_only — Dependency semantics and ownership.**  
Actual arithmetic, parser completeness, link encoding, copying, clearing, allocation, release, and retained-address lifetimes require dependency specifications.

**documented_only — Aliasing and preservation.**  
No local checks prevent overlapping output, context, metadata, or object storage. Escaped-slot mutations are possible contract conditions, not demonstrated dependency behavior. Distinct-object payload selection is therefore permitted by the visible sequence but not established as intended operation.

**documented_only — Termination and failures outside returned statuses.**  
Search can repeat without bound. Zero-capacity acquisition can repeat without byte progress. Invalid memory, dependency nonreturn, and malformed counts are not converted into local error statuses.
