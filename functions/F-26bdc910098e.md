# F-26bdc910098e

## Purpose

F-26bdc910098e prepares two temporary objects, creates three temporary adapters from those objects, invokes a combining dependency, and performs ordered cleanup. Normal completion returns the 32-bit value 1.

The established contract is the extraction, call, write, and cleanup sequence described below. “Object,” “adapter,” and “combining” are descriptive labels for data flow, not established domain semantics. The function does not establish whether the operation draws, copies, transforms, blends, or otherwise processes its inputs.

Dependency return values are not checked for success or failure. Two lookup results and the result of the third adapter-preparation call are forwarded to later dependencies.

### Context layout

Offsets are measured in bytes from the context address.

| Offset | Width | Use |
|---|---:|---|
| +0x04 | 16 bits | Signed format selector, compared with 5. |
| +0x4d | 8 bits | Character converted to an integer for the second lookup and second constructor. |

The record address is obtained by adding the two 32-bit components at +0x58 and +0x68. Their individual meanings are unknown; neither is established as an allocation base or an offset. Overflow behavior and address-provenance requirements for this calculation remain **documented_only**.

### Selected record layout

Format 5 selects the wide layout. Every other format value selects the compact layout; no additional format validation is visible.

| Field | Wide layout | Compact layout |
|---|---|---|
| Four-component tuple | Four 32-bit integers at +0, +4, +8, +12 | Four signed 16-bit values at +0, +2, +4, +6, widened to 32 bits |

The representation expresses compact tuple extraction at +0 and +4, and compact additional-integer extraction at +8, using 32-bit reads followed by signed 16-bit truncation. It expresses the other compact tuple components and the compact selector as 16-bit reads. Thus, the logical field widths do not establish exclusively 16-bit physical access requirements. Target byte order and exact machine instructions are not independently established.

Bytes between the selector-bearing region and the payload are not explicitly interpreted by this function. A dependency receiving the payload address may access additional bytes under its own contract.

## Behavior

### 1. Initialize the first object and select the record

The first operation is a call to F-a891c2749310 with the address of a 184-byte temporary region.

After that call returns:

1. The function obtains the record address from the context components at +0x58 and +0x68.
2. It reads the format selector at +0x04.
3. It chooses the wide layout only for format 5.

The relative evaluation order of the two address-addition operands is not established. The context is not captured before the initialization call, so changes made during that call can affect the subsequent address and format reads.

Once obtained, the selected record address is retained for this extraction path. The visible body does not recompute it after the first lookup.

### 2. Extract parameters and construct the first object

The two layouts have different tuple-read timing.

For the wide layout:

1. The payload address is selected as record address +32.
2. The signed low 16 bits of the word at +20 are passed to F-b4551e3e3ef6 with a second argument of zero.
3. After that dependency returns, the four 32-bit tuple components are copied, in component order, from +0, +4, +8, and +12.
4. The selector-bearing word at +20 is read again and converted to a signed 16-bit selector.
5. The 32-bit additional integer at +16 is read.

For the compact layout:

1. The four tuple components are extracted and sign-extended in component order, before the lookup.
2. The payload address is selected as record address +20.
3. The signed 16-bit selector at +10 is passed to F-b4551e3e3ef6 with a second argument of zero.
4. After that dependency returns, the selector at +10 is read again.
5. The additional integer at +8 is extracted as a signed 16-bit value and widened.

Consequently:

- The wide tuple reflects reads after the lookup.
- The compact tuple reflects reads before the lookup.
- Both layouts obtain the constructor selector after the lookup.
- Both layouts obtain the additional integer after the lookup.

The selector supplied to the lookup need not equal the selector later supplied to the constructor.

F-8a2ae74ef867 then receives, in order:

1. The first 184-byte temporary region.
2. The address of the temporary four-component, 32-bit tuple.
3. The selected payload address.
4. The additional integer.
5. The post-lookup signed selector.
6. The lookup result.
7. Zero.
8. Zero.

Any return value from this construction call is ignored. The tuple storage remains relevant: its first component is explicitly overwritten later, after the second lookup returns.

### 3. Prepare the two-part descriptor

After F-8a2ae74ef867 returns, the function prepares a contiguous 32-byte descriptor consisting of two 16-byte parts.

Each part initially has this layout:

| Offset within a part | Width | Value |
|---|---:|---|
| +0 | 32 bits | Zero |
| +4 | 32 bits | First caller-supplied word |
| +8 | 32 bits | Sum of the two signed context components |
| +12 | 32 bits | Second caller-supplied word |

The visible preparation order is:

1. Read the first caller word and store it at first-part +4.
2. Read the signed context components at +0x52 and +0x54, widen them, add them, and store the result at first-part +8.
3. Read the second caller word and store it at first-part +12.
4. Store zero at second-part +0.
5. Store zero at first-part +0.
6. Copy the captured first word, sum, and second word into second-part +4, +8, and +12, respectively.

The two context operand reads have no established relative evaluation order. Each operand is widened before addition. Their mathematical sum lies between −65536 and 65534, inclusive, and therefore fits a signed 32-bit integer. The sum is not narrowed back to 16 bits.

Both descriptor parts initially contain the same values, even if earlier dependencies changed the caller data: the descriptor reads occur only after the first constructor returns.

F-c6d95d05936a is then called with the first part’s address. Its effects are unknown. Neither part is guaranteed to retain its initial contents after this call.

## Side effects

Direct writes target function-local temporary storage: the tuple, descriptor, and other temporary bookkeeping. In particular, the first tuple component receives an explicit 32-bit zero write after the second lookup returns.

The body contains no explicit store through the context, selected record, or word-pair address. This does not establish their immutability: dependencies may access caller memory or shared state.

Temporary addresses escape to dependencies. Their storage is local to the invocation; no safe lifetime beyond the invocation is established. Retention, aliasing, ownership transfer, and resource-management effects are unknown.

The ordered cleanup calls establish which addresses are supplied and when. They do not establish whether a dependency frees memory, releases references, modifies shared state, or performs another action.

No assumption that a dependency preserves globals, caller memory, descriptor contents, or previously supplied tuple storage is part of this contract.

## Acceptance examples

These examples are conditional consequences of static evidence, not executed tests.

### Wide additional integer and negative selector

Given format 5, if the additional-integer field contains 70000 **when read after the first lookup**, the first constructor receives 70000 without 16-bit truncation.

If the selector-bearing word has low 16 bits 0xffff at the lookup read, the lookup receives −1. If those bits remain 0xffff at the post-lookup reread, the constructor also receives −1. Upper selector-word bits do not contribute.

The payload address is record address +32.

### Compact signed values

For any format other than 5:

- A compact tuple component encoded as 0xfffe when captured before the lookup becomes −2.
- An additional integer encoded as 0x8000 **at its post-lookup read** becomes −32768.
- The payload address is record address +20.

An initial additional-integer encoding alone is insufficient to determine the forwarded value if the lookup changes that field.

### Lookup-induced record mutation

If the first lookup changes a tuple component before returning, the wide path reads the changed component afterward. The compact path has already captured its tuple before that lookup.

If the lookup changes the selector or additional integer, subsequent reads use the post-lookup contents in either layout.

### Descriptor boundary

If both signed position components are −32768 when read, each descriptor part initially receives −65536 at +8. No 16-bit truncation occurs.

Later descriptor contents depend on intervening dependency effects.

### Tuple-address retention

If a dependency retains the tuple address passed to F-8a2ae74ef867, and reads its first component during F-7627a10679c2 before any further mutation of that location, it observes zero. The explicit zero write has already occurred after the second lookup.

This example does not establish that any dependency retains the address.

### Second selector mutation

If the second lookup changes context +0x4d, the second constructor uses the reread character, not necessarily the lookup’s selector. The tuple-zero write occurs between the lookup’s return and that reread.

### Normal completion

If every dependency returns normally, all three adapter cleanup calls and both object cleanup calls occur in the specified order, followed by return value 1. No visible dependency status selects another return value.
