# F-80ad7943304b

## Purpose

F-80ad7943304b performs a guarded operation on an object referenced by an input descriptor. It returns a 32-bit status and, on one eligible path, publishes the object's own address into an object field before invoking a sequence of dependencies.

The established behavior distinguishes four conditions:

- An input descriptor whose narrowed status field is nonzero is rejected with status 26.
- A null object reference or an object whose leading word does not match a global comparison value is rejected with status 26.
- An otherwise matching object with a negative signed field is rejected with status 7.
- An otherwise eligible object is either processed, rejected as already self-marked, or accepted without processing, according to an address-sized marker field.

The marker assignment suggests an in-progress or self-reference convention. That interpretation is inferred intent, not an established synchronization, ownership, or lifecycle guarantee. The contract below specifies the observed checks, writes, and calls without assigning undocumented meanings to them.

## Interface

### Input

The function takes one pointer to an input descriptor. No descriptor length is supplied.

The supplied representation uses 32-bit integer words and encodes object addresses in such words. Offsets below are byte offsets under that representation. They describe required fields, not complete structure definitions.

| Descriptor offset | Width represented | Use |
|---|---:|---|
| 0 | 32 bits | Object address, read only after the descriptor status check passes |
| 8 | 32-bit word narrowed to 8 bits | Early rejection status |

The descriptor status check examines the value after narrowing to 8 bits. It does not test whether the entire 32-bit word is zero.

A descriptor must be readable at the locations actually reached. There is no explicit null-descriptor check. A null or invalid descriptor is therefore not assigned a defined error status by the visible function.

### Referenced object

When the descriptor status permits further work, its first word supplies the object address. A zero address is explicitly rejected.

For a nonzero address, the function accesses these object-relative fields:

| Object offset | Width represented | Use |
|---|---:|---|
| 0 | 32 bits | Comparison against a global value |
| 396 | Signed 32 bits | Negative-value rejection check |
| 548 | 32 bits, also interpreted as an address | Processing marker |
| 552 | Address passed to dependencies | First interior dependency argument |
| 556 | Address passed to a dependency | Second interior dependency argument |
| 560 | 32-bit word narrowed to 8 bits for a check; one byte for a write | Conditional branch selector and clear location |

The object must support the reads and writes reached on its selected path. Dependency calls may require additional valid storage; their requirements are not established here.

### Output

The return value is a 32-bit status:

| Value | Established condition |
|---:|---|
| 0 | An eligible object either completes the visible dependency sequence or has a nonzero marker different from its own address |
| 7 | A matching object has a negative signed value at offset 396 |
| 26 | Descriptor status is nonzero after narrowing, object address is zero, leading object word mismatches the global comparison value, or marker equals the object's own address |

These meanings describe this function's branches. Broader symbolic meanings for the numeric statuses are unknown.

All statements about a returned status assume that reached memory accesses succeed and every invoked dependency returns normally.

## Behavior

### 1. Descriptor status takes precedence

The first visible decision uses the descriptor word at offset 8, narrowed to 8 bits.

If the narrowed value is nonzero, the function returns 26. It does not visibly load the object address, validate an object, modify object storage, or call any dependency on this path.

Consequently, upper bits of this descriptor word do not independently cause rejection. A 32-bit value whose low eight bits are zero passes this check.

The supplied representation does not establish the exact machine instruction or physical load width used to implement the narrowing.

### 2. Object address and identity are checked

After the descriptor status passes, the function reads the descriptor's first word as an object address.

A zero address produces status 26 without an object dereference.

For a nonzero address, the leading object word must equal a global comparison value. A mismatch produces status 26. There is no visible mutation or dependency call before this comparison succeeds.

The global comparison value's initialization, meaning, and stability are not established. The visible comparison uses it during this invocation; no persistent identity guarantee follows from a successful match.

The representation establishes the comparison as preceding subsequent field checks. It does not establish the relative machine-level read order of the two comparison operands.

### 3. The signed field is checked before the marker

For an object that passes the identity comparison, the 32-bit field at offset 396 is interpreted as signed.

If this value is less than zero, the function returns 7. The marker is not visibly examined or changed on that path.

Zero and positive signed values proceed to marker handling. This is specifically a signed comparison: a word with its high bit set is negative under the represented 32-bit interpretation.

### 4. The marker selects processing, rejection, or no-op success

The 32-bit marker at offset 548 has three relevant cases.

**Zero marker.** The function writes the object's own address into the marker and proceeds to the dependency sequence described below. The write occurs before the first dependency call.

**Marker equal to the object's own address.** The function returns 26. It performs no visible write and invokes no dependency.

**Any other nonzero marker.** The function returns 0 without invoking a dependency or visibly modifying the object.

The third case is part of the established contract. A nonzero marker is not uniformly an error, and status 0 does not imply that the processing sequence ran.

There is no visible retry, wait, marker validation, or attempt to follow a nonzero marker as another object reference.

### 5. Processing begins after publishing the self-address

For the zero-marker path, the sequence is:

1. Store the object's address at object offset 548.
2. Invoke F-6f7f27926f9e with the address at object offset 552.
3. After that call returns, examine the word at object offset 560 narrowed to 8 bits.
4. Select the conditional sequence below.
5. Invoke F-d0445c96ec5d with the base object address.
6. Return 0.

The selector is examined **after** F-6f7f27926f9e returns. Its entry value does not alone determine the branch: that dependency may modify the selector or related storage.

The interior arguments are addresses within the object, not the values stored at those offsets.

### 6. A selector value of exactly one adds a clear and a call

If the narrowed selector equals exactly 1:

- One byte at object offset 560 is written with zero.
- F-259d2fe281b0 is invoked with the address at object offset 552.
- F-f40e9b30ff3b is invoked with the address at object offset 556.
- F-d0445c96ec5d is then invoked with the base object address.

If the narrowed selector is anything other than 1:

- This function does not perform the byte clear.
- F-259d2fe281b0 is invoked with the address at object offset 552.
- F-f40e9b30ff3b is skipped.
- F-d0445c96ec5d is invoked with the base object address.

Thus F-259d2fe281b0 is reached once on either processing branch, whereas F-f40e9b30ff3b is reached only for a selector of exactly 1. Other nonzero selector values do not take the special branch.

The clear is explicitly byte-sized. It must not be specified as clearing the entire 32-bit field.

The narrowed read selects the low eight value bits of the represented word. The write targets the byte at the field's starting address. These correspond to the same portion of the word under a little-endian interpretation; that correspondence should not be generalized to another byte order without additional evidence.

## Side effects

The function's directly visible writes are limited to the zero-marker processing path:

- A 32-bit self-address write at object offset 548.
- A conditional one-byte zero write at object offset 560.

There is no visible write to the input descriptor.

There is no direct allocation or deallocation in the supplied function. This does **not** establish that its dependencies allocate nothing, release nothing, or preserve the object's lifetime.

In particular:

- The marker is not visibly restored or cleared after the dependency sequence.
- Its final value cannot be guaranteed, because dependencies may modify it.
- The selector's final value cannot be guaranteed, even after the byte clear.
- No global-preservation guarantee is available for any dependency.
- The function does not revalidate the object or its lifetime between calls.
- No visible rollback or cleanup handles an abnormal dependency exit.

The caller must satisfy whatever object-lifetime and synchronization requirements make the reached sequence valid. No atomic operation, lock guarantee, or thread-safety property is established by the marker assignment alone.

Aliasing between the descriptor and object is not prohibited by a visible check. Claims about unchanged descriptor storage therefore concern direct descriptor-targeted writes, not all possible effects through aliased object storage or dependencies.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Each assumes valid reached memory and normally returning dependencies unless stated otherwise.

1. **Descriptor status rejects before object access.**  
   With a descriptor status whose low eight bits equal 2, the result is 26. Even if the descriptor's first word contains an unusable address, this path does not visibly read that word or dereference the object.

2. **Upper descriptor bits do not cause rejection.**  
   A descriptor status of hexadecimal 00000100 passes the initial narrowed check. The final result then depends on the object checks; passing this check alone does not imply success.

3. **Null object is rejected.**  
   With a passing descriptor status and a zero object address, the result is 26 and no dependency is invoked.

4. **Identity mismatch precedes the signed-field check.**  
   If the leading object word differs from the global comparison value, the result is 26 regardless of what later object fields would contain. The visible function does not reach those later fields.

5. **Negative signed field takes precedence over a self-marker.**  
   For a matching object whose offset-396 field is −1, the result is 7, even if its marker would equal its own address. Marker handling is not reached.

6. **A self-marker rejects without processing.**  
   For a matching object with a nonnegative signed field and a marker equal to its own address, the result is 26. No dependency is invoked.

7. **A different nonzero marker produces no-op success.**  
   For the same eligible object but a nonzero marker different from its address, the result is 0. The dependency sequence does not run.

8. **Selector one selects the additional call.**  
   With a zero marker and a narrowed selector of 1 after F-6f7f27926f9e returns, the function writes the self-marker, clears one byte at offset 560, and reaches dependencies in this order: F-6f7f27926f9e, F-259d2fe281b0, F-f40e9b30ff3b, F-d0445c96ec5d. It then returns 0.

9. **Other selector values omit the additional call.**  
   Under the same conditions but with a narrowed selector of 2, there is no direct selector-byte clear and no F-f40e9b30ff3b call. The other three dependencies remain ordered as specified.

10. **The selector decision observes post-call state.**  
    If the selector is initially 1 but F-6f7f27926f9e changes its narrowed value to 0, the additional call is skipped. Conversely, a change from 0 to 1 selects the clear and additional call.

## Uncertainties

The following remain documented_only:

- Complete descriptor and object layouts, allocation sizes, and alignment requirements.
- The global comparison value's identity, provenance, and mutation rules.
- The intended meanings of the signed field, marker, and selector.
- Concrete ABI, byte order, and exact machine-level access widths beyond the supplied representation.
- Dependency effects on globals, object storage, ownership, and lifetime.
- Whether any dependency can exit abnormally or fail without returning.
- Permitted concurrent access and required external synchronization.
- Whether external invariants prevent descriptor/object aliasing.

A repeated-call guarantee cannot be inferred merely from the self-marker write. If dependencies leave the marker unchanged and preserve the object, a later otherwise eligible invocation encounters the self-marker and returns 26. Those dependency-preservation conditions are not established.

## Evidence

**Established static evidence:** the supplied function representation shows the branch precedence, represented 32-bit fields, 8-bit narrowing checks, signed negative comparison, self-address write, conditional one-byte clear, dependency arguments and ordering, and numeric return statuses described above.

**Inferred intent:** the self-address marker may distinguish an in-progress or already-handled object. The paired calls using offset 552 may concern related state. Neither interpretation is needed to define the observable contract, and neither is asserted as fact.

**Unknown behavior:** dependency internals, broader caller invariants, runtime fault behavior, and concrete platform details not supplied by the representation.

No runtime tests have been performed. The acceptance examples are static behavioral expectations, not observations of execution.
