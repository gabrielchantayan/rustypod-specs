# F-1e7091dc86a0

## Purpose

F-1e7091dc86a0 replaces a destination field with a signed integer obtained from a fixed location relative to an input base. A nonzero replacement value also selects another field whose contents are increased by one.

The operation is an unconditional replacement, not an exchange, comparison, or replace-if-different operation. It neither returns the displaced value nor performs cleanup on its behalf. Equality between the destination’s existing contents and the selected value does not suppress the additional update.

**Established static evidence:** destination replacement, followed by a conditional increment at an address derived from the replacement value.

**Inferred intent:** the selected value may represent an object address, and the additional field may be a reference count. These interpretations do not establish ownership transfer, object validity, lifetime extension, or any release obligation.

## Interface

### Inputs and output

Two inputs are supplied:

| Input | Contract role |
|---|---|
| Destination address | Identifies the signed-integer field to be replaced. |
| Input base | A signed integer from which the source address is derived. |

There is no returned value. In particular, the operation does not return a status, the destination’s previous contents, or a resource handle.

This contract uses three storage roles:

| Role | Location |
|---|---|
| Source field | Address obtained by adding 2196 to the input base and interpreting the result as an address. |
| Destination field | Storage identified directly by the destination argument. |
| Related field | For a nonzero source capture, address obtained by adding 4 to that captured integer and interpreting the result as an address. |

The numbers 2196 and 4 are integer address displacements, not counts of signed-integer elements. On a conventional byte-addressed platform, they denote byte offsets. The supplied evidence does not independently establish that platform mapping.

The **captured value** means the signed integer obtained from the source field for this invocation. Subsequent changes to source storage do not replace that capture or select a different related field.

### Widths and representation

The source, destination, and related field are accessed using the same signed-integer type. The input base and captured value also use that type.

Its exact width is **documented_only**. The evidence does not independently establish a 32-bit width, four-byte field accesses, pointer width, byte order, or alignment requirements. In particular, the related-field displacement of 4 does not prove that the field itself occupies four bytes.

Let the signed-integer type’s representable range be the applicable arithmetic range. Address-forming additions and the related increment must be evaluated under that type’s rules. No wider intermediate, unsigned arithmetic, saturation, or checked-arithmetic result is established.

Integer-to-address conversion is also an environmental prerequisite. The numerical additions alone do not prove that their results designate accessible storage.

### Preconditions for normal completion

The source must support the required read, and the destination must support the required write. A nonzero capture additionally requires a readable and writable related field.

These requirements include adequate extent, alignment, permissions, valid access semantics, and storage lifetime. Address formation must be valid under the applicable arithmetic and address-conversion rules. When an increment is required, the value encountered at the related field must have a valid successor.

No explicit rejection rule applies merely because the input base or captured value is negative. A negative capture is nonzero and therefore selects the related update, provided the resulting address formation and accesses are valid.

## Behavior

### Replacement and conditional increment

For separate fields and valid execution, the destination receives the captured source value.

A zero capture requires destination replacement with zero but requires no related-field access. A nonzero capture requires the related field’s contents to increase by one. The related field need not initially be positive: zero may become one, and a negative value may become its successor.

The destination’s entry contents do not influence either decision. There is no comparison against those contents and no cleanup based on them. An already-matching destination therefore receives the same replacement and still requires the increment for a nonzero capture.

The separate source field is not modified. It can change through this operation only if it overlaps storage written in another role.

### Ordering guarantees

The static evidence establishes these observable access relationships:

- Source capture precedes destination replacement.
- For a nonzero capture, destination replacement precedes the related-field read.
- The related-field write uses the value obtained by that related-field read, increased by one.

The captured integer determines the replacement, the zero/nonzero decision, and the related-field location. The operation does not revisit the source to choose a different value after replacement.

These relationships matter for overlapping storage and for identifying which access precedes a possible failure. They do not establish a particular machine-instruction sequence, indivisible accesses, volatile semantics, memory barriers, or cross-thread visibility guarantees.

### Overlapping storage

The body contains no explicit requirement that the three storage roles be disjoint. The following consequences apply only when the proposed overlaps and all resulting accesses are valid.

**Destination and source coincide.** The capture is written back to the same field. A nonzero capture still requires the related increment; self-replacement does not suppress it.

**Destination and related field coincide.** Replacement occurs before the related-field read. Consequently, the increment operates on the captured value just written there, not on the destination’s entry contents. The final shared value is the captured value’s successor, assuming that successor is valid.

**Source and related field coincide, with a separate destination.** The destination receives the capture. The later increment changes source storage to the capture’s successor. That change does not redirect the operation or cause another increment.

**All three roles coincide.** If such a layout is valid, a nonzero capture is written back and then increased by one. This is a conditional consequence of the access order, not evidence that a caller can construct that layout on every platform.

Thus, replacement with the captured value is an event guarantee. It is not an unconditional final-state guarantee for destination storage: an overlapping related-field write may subsequently change it.

Partial overlap is **documented_only**. Its final byte-level effects depend on field width, byte order, alignment, address mapping, and the validity of the overlapping accesses. The evidence supplies no representation-independent result for that case.

### Arithmetic boundaries

There is no explicit overflow detection or alternative arithmetic path.

Normal-completion claims require valid additions for both address formation and the increment. A hypothetical wrapped address does not establish that the signed addition producing it was valid.

Likewise, when the related-field read obtains the maximum representable signed integer, neither wraparound nor saturation is an acceptance requirement. The treatment of an out-of-range addition remains **documented_only**.

The relevant increment operand is the value actually read after destination replacement. If destination and related field coincide, the captured value—not the field’s entry contents—determines whether the successor is representable.

### Invalid execution and errors

There is no explicit error result, validation branch, recovery path, or rollback.

An invalid source access affects capture. An invalid destination access affects replacement. With a nonzero capture, problems involving related storage or its increment concern an operation ordered after destination replacement.

This ordering does not guarantee a recoverable partial result. Fault delivery, exception handling, termination, and the observability of earlier effects after invalid arithmetic or storage access are not established.

The operation provides no transactional contract: callers cannot rely on all-or-nothing completion or a status indicating which effects occurred.

## Side effects

### Memory effects

For separate, valid fields, the represented effects are a source read and destination write, plus a related-field read and write when the capture is nonzero.

There is no separate read of the destination’s old contents for comparison, return, or cleanup. Destination storage may nevertheless be read when it also serves as the source or related field.

No explicit allocation, deallocation, external call, lock, notification, or independently named global access appears in the body. This does not establish global-state preservation: any addressed storage may itself be global or globally reachable.

### Ownership and lifetime

Replacing an occupied destination does not release, destroy, or otherwise dispose of its prior value. Any obligation associated with that displaced value must come from an external contract.

The conditional increment does not establish that the captured integer identifies a live allocation, that ownership is acquired, or that a matching release operation exists. A possible reference-count interpretation is insufficient to establish those properties.

Storage must already remain valid for the required accesses. The increment cannot be assumed to repair an invalid lifetime or make a reclaimed object safe to access.

### Concurrency

No explicit synchronization or atomic read-modify-write guarantee is present. The related update must not be credited with preventing lost updates.

Any concurrent access, publication, or reclamation protocol is external to this contract. The represented access order alone does not provide safe inter-thread publication or protect storage lifetime.

## Acceptance examples

These examples are conditional criteria derived from static evidence, not runtime observations. Unless overlap is stated, assume separate fields, stable storage, valid address formation, valid accesses, and representable arithmetic results.

### Zero capture with an occupied destination

The source contains zero, and the destination contains a nonzero value.

Normal completion leaves zero in the destination. No related field is accessed, and no cleanup of the displaced value is performed.

An unwritable destination does not become acceptable merely because the capture is zero; the replacement remains required.

### Nonzero capture with an ordinary related value

The source contains a nonzero value selecting valid related storage, initially containing 7.

Normal completion leaves the capture in the destination and 8 in the related field. The separate source remains unchanged. The destination replacement occurs before the related-field read.

### Destination already matches

The destination already contains the same nonzero value as the source, and the related field initially contains 7.

Normal completion still changes the related field to 8. Skipping the increment because the destination already matches would violate the contract.

### Nonpositive related contents

A nonzero capture selects a related field containing zero.

Normal completion changes that field to one. In a separate case, an initial value of −2 becomes −1. Neither case has a sign-based rejection condition.

A negative capture similarly selects the nonzero behavior when its derived related address and required accesses are valid.

### Destination is the related field

A nonzero capture selects the destination itself as related storage. The destination’s entry contents differ from the capture.

Normal completion leaves the captured value’s successor in the shared field. Using the destination’s entry contents as the increment operand would violate the required access order.

### Source is the related field

A valid layout makes the source also be the related field selected by its captured contents. The destination is separate.

Normal completion leaves the capture in the destination and its successor in the source. The changed source contents do not trigger reselection or an additional update.

### Increment boundary

A nonzero capture selects a separate related field containing the maximum representable signed integer.

This case has no specified normal-successor result. A wrapped value, saturated value, recoverable error, or particular fault is not required by the evidence.

Similarly, overflowing address arithmetic is not made valid by an apparently usable wrapped address.
