# F-660a676af301

## Purpose

F-660a676af301 interprets an input stream containing ordinary items and percent-led conversion requests. It consumes values from a separate argument area, records conversion settings in a mutable context, and delegates literal output, individual output, and conversions.

Established responsibilities are:

- Count ordinary scanned items and report eligible literal spans.
- Parse table-defined flags, width, precision, and one length-modifier group.
- Select conversion dependencies and advance an internal argument cursor.
- Return the context’s current 32-bit count field.

The conversion letters suggest formatted output. Compatibility with a particular formatting standard is not established. Flag meanings, conversion results, output-error behavior, and some numeric argument-delivery mechanisms remain unresolved.

## Interface

### Inputs and result

The function receives:

1. A context pointer.
2. An argument-area pointer.
3. Two additional 32-bit values, initially placed in adjacent temporary words.

Argument words and encoded addresses are 32 bits. The two additional values have no established effect on dispatch or the result: both temporary words are overwritten before their address is supplied to a floating conversion dependency.

The return value is the unsigned 32-bit value currently stored at context offset 60. It is not an independently computed output length.

### Context layout

Offsets are byte offsets from the context pointer.

| Offset | Width | Established role |
|---|---:|---|
| 24 | 32 bits | Parsed flags and modifier bits |
| 28 | 32 bits | Individual-output callback address |
| 32 | 32 bits | Literal-span callback address |
| 36 | 32 bits | Second argument to individual-output callback |

Every context callback target is obtained by clearing the low two bits of its encoded address with mask `0xfffffffc`. Callback fields are read for their respective invocations; the function does not establish immutable callback targets.

The location addressed by offset 44 is read as a 32-bit value during literal scanning. Interpreting that value as a source cursor is inferred intent.

### Preconditions and arithmetic

No context validation, bounds check, callback validation, argument-storage check, or null-pointer recovery is visible. Required storage and callback targets must be valid for all accesses actually reached.

Ordinary argument slots occupy four bytes. Selected conversions use an eight-byte slot beginning at the address obtained by adding seven to the cursor and clearing its low three bits, then advance eight bytes from that address. Address arithmetic is 32-bit; describing this as upward alignment assumes no address wraparound.

The argument cursor is local to this invocation. No writeback to the caller’s argument-pointer variable is visible.

## Behavior

### Initialization and literal scanning

The function captures a global-derived flag-table reference, then writes zero to the count field before calling any callback. The captured reference is reused; table bytes are read as flag candidates are encountered rather than copied in advance.

Each outer iteration:

- Reads the 32-bit value at the location addressed by context offset 44.
- Saves that value as both the span start and the initially captured span end.
- Invokes the input callback repeatedly until it returns zero or `0x25`, the percent character.

For every other returned value, the function reads the value currently addressed by offset 44, replaces the captured span end with it, then increments the current context count modulo \(2^{32}\).

The scanning input calls have no explicit arguments in the supplied representation. Input calls during conversion parsing instead explicitly receive the current value of context offset 44. A uniform callback ABI cannot be established from these differing call forms.

After scanning stops, unequal saved start and captured end values cause a literal-span callback with the context and saved start value. No explicit length or end address is supplied. This callback occurs before either end-of-input return or conversion parsing.

Consequently:

- Ordinary input increments count even when no span callback occurs.
- A stopping zero or percent does not itself refresh the captured span end.
- Input-state mutations during the stopping call do not alone determine span notification.
- Input and span callbacks can alter the count that is subsequently incremented or returned.

When scanning stops on zero, the function returns the current count after any span callback.

### Table-defined flag scanning

After a percent, the function repeatedly obtains another input value. A candidate is consumed as a flag only when both conditions hold:

- Its value is within `0x20` through `0x30`, inclusive.
- Its corresponding flag-table byte is nonzero.

Each consumed byte value is ORed into a local flag accumulator. The first candidate failing either condition is retained for field or conversion parsing.

The table contents are unavailable. In particular, the range includes percent, asterisk, and period. A second percent need not become a percent escape; an initial asterisk need not become dynamic width; an initial period need not introduce precision. Each can instead be consumed as a flag if its table entry is nonzero.

Table-derived bits may include bits also associated with later parsing decisions. Their presence cannot generally be attributed exclusively to a particular modifier or punctuation mark.

After flag scanning stops, the function writes zero to precision, then zero to width. These writes do not guarantee that either field remains zero across subsequent callbacks.

### Width and precision

Width is processed first. A period retained after width processing introduces precision; the function reads another input item and then adds bit `0x20` to the local flags.

Either field can be supplied by an asterisk or decimal digits:

- **Asterisk:** Read one argument word and store it unchanged in the selected field. Invoke the input callback for the next candidate and advance the internal argument cursor by one word.
- **Decimal digits:** Store the first digit’s numeric value directly. For each subsequent digit returned by an input callback, read the field’s current value and replace it with ten times that value plus the digit, modulo \(2^{32}\).

Callback mutations therefore participate in decimal accumulation. The callback returning a nondigit can also leave a changed field without a subsequent arithmetic write. If no numeric form is recognized, there is no field assignment in that branch; intervening callbacks may already have changed the initialized zero.

For dynamic precision, the signed-negative check occurs **after** the input callback following the argument store. If the current precision field then has its high bit set, local flag bit `0x20` is cleared. The check does not restore or replace precision. A negative argument alone guarantees neither a cleared bit nor a retained negative field.

There are at most two field stages. Another period encountered while processing precision is not accepted as a third field.

After field parsing, the function reads the current width. If its signed 32-bit interpretation is negative, the function stores its modular negation and toggles local bit `0x01`. This is exclusive OR, not an unconditional set. Negating `0x80000000` leaves that bit pattern unchanged.

Next:

- If local bit `0x01` is set, clear local bit `0x10`.
- If local bit `0x02` is set, clear local bit `0x04`.

These operations use the local flag accumulator. Later modifier-input callbacks may mutate context width or precision; the function does not normalize those fields again before dispatch.

### Length modifiers and flag publication

At most one modifier group is recognized:

| Modifier | Bits added |
|---|---:|
| Single `l` | `0x40` |
| Double `ll` | `0x80` |
| Single `h` | `0x100` |
| Double `hh` | `0x400` |
| `j` | `0x80` |
| `L`, `t`, or `z` | None |

A single `l` or `h` requires lookahead to distinguish its doubled form. The recognized group consumes the input needed to obtain the conversion candidate. There is no general modifier-chain loop.

The accumulated flags are written to context offset 24 after modifier processing and before dispatch, including when the resulting conversion candidate is zero. This publication can overwrite changes that earlier input callbacks made to that field.

#### Strings and characters

An `s` argument is read as the address supplied to a string dependency:

- With bit `0x40` clear: F-37a2eb8d9048 receives context and address.
- With bit `0x40` set: F-ac279a2a077b receives context, address, and `0xffffffff`.

The sentinel’s meaning is unknown.

For `c`, the consumed word supplies character bits to temporary storage:

- With bit `0x40` clear, the temporary word receives the argument’s low eight bits in bits 0–7 and zero in bits 8–15. Bits 16–31 are retained from the temporary’s previous contents. Its address is supplied to F-37a2eb8d9048.
- With bit `0x40` set, the temporary word receives the argument’s low sixteen bits in bits 0–15 and zero in bits 16–31. Its address and the value one are supplied to F-ac279a2a077b.

These are integer bit layouts, not established memory byte sequences. Describing either address as pointing to a character followed by a zero terminator requires additional byte-order and representation evidence.

All four string/character calls occur only if the current context field at offset 48 is zero. The argument read, cursor advancement, and character temporary construction still occur when the gate prevents the call.

#### Floating paths

The function selects an aligned eight-byte slot, advances its cursor beyond that slot, and copies two consecutive 32-bit words into adjacent temporary words: first word read and stored, then second word read and stored. The dependency receives context, candidate, and the temporary address.

Visible alignment, copying, cursor advancement, and dependency selection do not branch on modifier bits. Overall conversion behavior may nevertheless depend on those bits because they have been stored in the context before invocation.

Floating representation, word significance, rounding, special values, and output syntax are not established.

#### Fallback and termination

Any unmatched nonzero candidate goes to the individual-output callback with the candidate and the current value at context offset 36. After that callback returns, the function increments the current count modulo \(2^{32}\).

Fallback consumes no conversion argument. Earlier dynamic fields may already have consumed arguments.

A second percent reaches this path only if it survives flag scanning and subsequent parsing as the conversion candidate.

A zero conversion candidate returns the current count without invoking a conversion or fallback callback. Field stores, argument consumption, and flag publication already performed are not rolled back.

## Side effects

Direct persistent writes are to context offsets 24, 52, 56, and 60. Temporary words are also modified for character and floating paths.

The function directly increments count only for ordinary scanned items and fallback output. Each increment reads the current field; callback changes participate in the result. Conversion dependencies may also modify count.

Input callbacks can change fields used by later parsing, including precision between a dynamic-precision store and its sign check, or width/precision between decimal accumulation steps. Context values must not be treated as preserved across calls without an additional dependency contract.

No allocation, deallocation, ownership transfer, or resource-release operation is explicitly performed by this function. Address arguments do not establish whether a dependency borrows, modifies, retains, or releases storage. Temporary addresses have no established validity after the enclosing invocation ends.

Input return values control parsing. Other callback and dependency return values do not visibly determine local error handling. There is no separate error return, rollback, or established recovery for invalid memory, output failure, or nonterminating input.

## Acceptance examples

These are conditional static cases, not executed tests. Preservation conditions are stated where needed.

1. **Immediate zero.** Count is reset before the first input call. If that call returns zero, no span callback occurs and the current count is returned. The result is zero only if the input callback leaves count zero.

2. **Three ordinary items.** If three ordinary items precede zero, there are three direct increments. A result of three requires every relevant input callback and any span callback to preserve count. Span notification separately requires unequal saved start and captured end values.

3. **Percent escape.** If the percent table entry is zero, a percent immediately following the introducer survives flag scanning, reaches fallback, and causes one direct count increment after the output callback. If that entry is nonzero, this conclusion does not follow.

4. **Dynamic width and unknown candidate.** Starting after flag scanning with an asterisk as the retained candidate, one word is consumed for width. If the next candidate is an unrecognized conversion, it reaches fallback without another conversion-argument read. For an asterisk immediately after the introducer, this requires its table entry to be zero.

5. **Dynamic negative precision.** Starting after flag scanning with a period, followed by an asterisk and argument `0xffffffff`, the argument is stored in precision. If the subsequent input callback preserves precision, bit `0x20` is cleared and the field remains `0xffffffff`. If that callback instead writes seven, the negative-precision rule does not clear the bit and the field is seven. An initial period must have a zero table entry to reach this path directly.

6. **Negative width toggles.** Starting after flag scanning with dynamic width, suppose width is negative at normalization and local bit `0x01` is already set. Normalization clears that bit by toggling it. A negative argument alone is insufficient if an intervening callback changes width.

7. **Live decimal accumulation.** Starting after flag scanning with width digit one, suppose the callback returning digit two changes width to seven. The next accumulation stores 72, not 12. A later nondigit callback may change it again before normalization.

8. **Alignment.** For a nonwrapping cursor four modulo eight, an eight-byte conversion skips four bytes and leaves its cursor twelve bytes beyond the original address.

9. **Gated string.** If offset 48 is nonzero at the `s` gate check, the pointer word is still read and consumed, but neither string dependency is called.

10. **Zero narrow character.** A zero argument clears the temporary’s low sixteen bits; its upper sixteen bits remain retained. Neither the byte sequence at the supplied address nor whether output occurs follows without byte-order and F-37a2eb8d9048 semantics.

11. **Modifier-sensitive floating dependency.** Two floating requests differing only in modifier bits follow the same visible slot/copy path and dependency selection. Equal output is not required because the dependency can inspect the published flags.

12. **Truncated conversion.** If the final candidate is zero, the current count is returned without fallback. Already consumed dynamic arguments and previously published fields remain effective.
