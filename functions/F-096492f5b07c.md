# F-096492f5b07c

## Purpose

F-096492f5b07c consumes pairs of signed 16-bit values and uses them to update two caller-supplied tables. Each table has a signed 32-bit entry count followed by fixed-size records. A record’s first two words are a key and an associated signed value; its remaining six words have no interpreted meaning in the supplied evidence.

The first complete input pair always targets the second table. A selector determines whether subsequent pairs also target the second table or instead target the first table.

For each selected table, the function searches by key. It either conditionally updates an existing matching record or inserts a new record at the search position. At completion, it writes both locally maintained counts back to their table headers.

**Inferred intent:** the tables represent ordered collections of endpoint-like keys and signed differences. This interpretation is not required by the contract; no application-level meaning for either field is established.

The 16-bit and 32-bit interpretations follow the supplied type representation. The evidence does not independently establish byte order or all target ABI details.

### Table layout

Each table begins with a 4-byte signed count. The first record begins 4 bytes after that header. Records have a 32-byte stride:

| Record-relative byte offset | Meaning |
|---|---|
| 0–3 | Signed 32-bit key |
| 4–7 | Signed 32-bit associated value |
| 8–31 | Six additional 32-bit words, uninterpreted here |

The function directly interprets only the key and associated value. During insertion, it requests movement of complete 32-byte records.

### Preconditions for ordinary bounded operation

The following are necessary for the normal table-update interpretation:

- Both table headers are readable and writable, including when no complete input pair exists.
- Every consumed input pair is readable.
- Selected table counts are nonnegative and describe accessible records.
- Selected records are sorted in nondecreasing signed-key order if ordered lookup and insertion are expected.
- Each insertion has capacity for one additional 32-byte record.
- Count increments, record offsets, and pointer calculations remain representable and address valid storage.
- Any desired independence between the two tables and the input is provided by suitable nonaliasing.
- The external dependency satisfies the record-transfer behavior described under **Dependencies**.

There is no capacity argument and no visible validation of any of these conditions.

The function does not establish ownership of any argument. It visibly performs no allocation or release. The external dependency’s ownership behavior is not established.

## Behavior

### Entry and completion

The function first reads the first table’s header into a local count, then reads the second table’s header into another local count. These reads occur even when the input element count is zero or one.

The function processes only complete input pairs. At the first point where fewer than two elements remain, it:

1. Writes the locally maintained first-table count to the first table’s header.
2. Writes the locally maintained second-table count to the second table’s header.
3. Returns without an explicit result.

Consequently, an odd trailing element is ignored and is not read through the pair-processing path. It does not trigger an error.

Counts are retained locally throughout processing. Table headers are not updated after each insertion. If the external dependency changes a header, that change does not refresh the corresponding local count and can be overwritten at completion.

### Pair routing and arithmetic

For a complete pair, let its first signed 16-bit element be \(a\) and its second be \(b\). Both are sign-extended before subtraction.

Routing and field derivation are:

| Pair position and selector | Target | Key | Associated candidate |
|---|---|---|---|
| First complete pair, any selector | Second table | \(b\) | \(a-b\) |
| Later pair, nonzero selector | Second table | \(b\) | \(a-b\) |
| Later pair, zero selector | First table | \(a\) | \(b-a\) |

For the second-table route, the second input element is read before the first. For the first-table route, the first input element is read before the second.

The subtraction is signed 32-bit arithmetic after sign extension. Its mathematical result lies between −65,535 and 65,535 inclusive, so the subtraction itself does not overflow a signed 32-bit value.

After a pair has been handled, the input pointer advances by two 16-bit elements, and the unsigned remaining-element count decreases by two. Subtraction occurs only when the count is at least two, so this particular countdown does not underflow.

### Searching the selected table

Each pair starts a fresh search at the selected table’s first record, using that table’s current **local** count.

Records are examined in forward order using signed key comparisons:

- A stored key less than the candidate key is skipped.
- A stored key equal to the candidate key selects the existing-record update.
- A stored key greater than the candidate key selects insertion immediately before that record.
- Reaching the end selects append.

The search does not validate ordering. For an unsorted table, it may insert before an earlier greater key without discovering an equal key later in the table. If duplicate keys already exist, the first equality reached by this search is the only matching record considered.

The search comparisons are against record storage as encountered, not against a snapshot of the table taken at entry.

### Updating an existing record

A matching key never increments the local count and never invokes the record-transfer dependency.

Let \(d\) be the new associated candidate and \(v\) the existing associated value:

- If \(d < 0\), retain \(v\) when \(v \leq d\); otherwise write \(d\).
- If \(d \geq 0\), retain \(v\) when \(d \leq v\); otherwise write \(d\).

Equivalently, a negative candidate selects the signed minimum of the old and new values, whereas a nonnegative candidate selects their signed maximum.

The branch depends on the **candidate’s sign**, not the old value’s sign. This is not a general “greatest absolute magnitude” rule. In particular:

- A negative candidate replaces an existing nonnegative value.
- A nonnegative candidate replaces an existing negative value.
- A zero candidate can replace a negative value but does not replace a positive value.

Only the associated-value word can be directly changed on this path. The key and the other six words are not directly written.

### Inserting a record

Insertion uses the position found by the search. If existing records follow that position, the function invokes the external dependency once per following record, in reverse record order.

For an insertion position with \(r\) records remaining:

- The first request transfers the last existing record into the following record slot.
- Subsequent requests proceed toward the insertion position.
- The final request transfers the existing record at the insertion position into its following slot.

Each request has a length of 32 bytes. The destination is one record above the source. The insertion-position pointer itself remains fixed throughout these requests.

After the transfer requests finish, or immediately for append, the function:

1. Writes the candidate associated value into the insertion slot.
2. Increments the selected table’s local count.
3. Writes the candidate key into the insertion slot.

The last six words of the inserted slot are not directly initialized. Appending therefore leaves those words as they were in the spare storage. Inserting before an existing record leaves them as they are after the dependency calls; under ordinary copying behavior, they retain the displaced record’s previous contents.

No header count is published at this point. Both header writes occur only at completion.

## Side effects

### Direct reads and writes

The function directly:

- Reads both table counts on entry.
- Reads two signed 16-bit input elements per processed pair.
- Reads selected table keys during search.
- Reads a matching record’s associated value when deciding whether to replace it.
- Writes an associated value when the replacement rule requires it.
- Writes a new record’s associated value and key on insertion.
- Writes both table counts at completion, in first-table then second-table order.

The source representation does not establish volatile or atomic accesses. Exact physical load counts, atomicity, and concurrent-observer guarantees are therefore outside this contract.

### Aliasing and visibility

There is no visible alias check or synchronization.

If the two table pointers identify the same storage, the function still maintains two separate local counts. Their final header writes target the same address in sequence, so the second-table count is written last. During processing, routing can use a local count that no longer reflects changes made through the other table view.

If records overlap the input sequence, record updates or dependency calls can change input values that have not yet been read. Likewise, overlap between headers and records can make direct record writes affect header storage before completion.

These cases are not rejected. The ordinary independent-table interpretation requires appropriate storage separation.

The dependency may have additional side effects. Its preservation of input memory, table memory, global state, and unrelated memory is not established merely by this caller.

### Errors and failure handling

There is no explicit error result, exception handling, rollback, capacity check, null check, or malformed-count rejection.

If a dependency call fails to return, the remaining processing and final header writes are not reached. If it returns an error indication through an otherwise unused result, no caller-side handling is visible.

A failure after earlier record writes or transfers can leave partially modified storage with unpublished local counts. No transactional guarantee is established.

## Acceptance examples

These examples are static contract examples, not runtime observations. Unless stated otherwise, tables are separate, counts and storage are valid, keys are sorted, capacity is sufficient, and F-000000000001 performs the intended transfer without unrelated effects.

### No complete pair

With an element count of zero or one:

- Both table headers are read.
- No input pair is read.
- No record is searched or changed.
- Both cached counts are written back, first table first.

An inaccessible input pointer does not itself affect this path because no input element is read. Both table headers must still be accessible.

### Zero selector routes only the first pair to the second table

Given initially empty tables, selector zero, and input pairs \((7,3)\), then \((4,9)\):

- The second table receives key 3 with associated value 4.
- The first table receives key 4 with associated value 5.
- Both final counts are 1.

### Nonzero selector routes every pair to the second table

Given initially empty tables, a nonzero selector, and the same two pairs:

- The second table receives key 3 with value 4 and key 9 with value −5.
- The second-table count becomes 2.
- The first-table count remains 0.

The selector’s magnitude and sign make no difference beyond being nonzero.

### Equal-key signed replacement

For an existing matching key:

| Existing value | Candidate | Result |
|---:|---:|---:|
| −8 | −3 | −8 |
| −2 | −3 | −3 |
| 8 | 3 | 8 |
| 2 | 3 | 3 |
| 8 | −3 | −3 |
| −8 | 3 | 3 |
| −8 | 0 | 0 |
| 8 | 0 | 8 |

Every row leaves the count unchanged and requires no transfer call.

### Middle insertion

Suppose a selected table has keys 2, 6, and 10, and a pair produces candidate key 5.

The function requests transfer of key 10’s full record into the spare slot, then key 6’s full record into the following slot. It then writes the new associated value and key into the former key-6 slot.

Under the dependency assumption, the resulting key order is 2, 5, 6, 10. The selected local count increases by one; its header is updated only at completion.

### Extreme signed input values

For a second-table pair with first element 32,767 and second element −32,768, the candidate key is −32,768 and the associated candidate is 65,535.

Reversing those elements produces key 32,767 and candidate −65,535. Neither result is truncated to 16 bits.

### Odd element count

With five input elements, exactly two pairs are processed. The fifth element is ignored. Routing depends on the first and second pairs, not on the unused trailing element.

## Uncertainties

The following are **documented_only**, not inferred guarantees:

- The exact target ABI, byte order, and pointer width.
- The external dependency’s implementation and memory-preservation contract.
- Caller-provided capacities and whether valid callers guarantee sorted, unique keys.
- The meaning or required initialization of the six uninterpreted record words.
- Whether aliasing is intentionally supported.
- The behavior of invalid pointers, negative counts, overflowing count increments, or out-of-range pointer calculations.
- Thread-safety, signal-safety, atomicity, and behavior under concurrent mutation.

A negative table count is especially unsafe: the scan terminates on a remaining count of exactly zero, not on a nonpositive count. A negative value is therefore not treated as an empty table and can lead to out-of-bounds traversal or arithmetic outside a well-defined range.
