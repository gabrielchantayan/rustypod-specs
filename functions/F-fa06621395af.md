# F-fa06621395af

## Purpose

F-fa06621395af performs a bounded, forward byte copy with a trailing-boundary adjustment based on UTF-8-like byte patterns.

Its apparent intent is to copy a string into a fixed-size destination while reserving a terminating zero and avoiding a partially copied final multibyte character. That intent is an inference, not a complete description of its behavior. The function does not validate UTF-8, does not always terminate its output for malformed input, and does not return a conventional destination pointer.

For a positive byte budget, it copies until either a source zero is encountered or the budget is exhausted. It then examines the first destination byte of the most recently encountered non-continuation-byte sequence. Depending on that byte’s apparent encoded width and its position relative to the destination boundary, it may replace that byte with zero, discarding the sequence from the resulting zero-terminated view.

The return value is pointer-typed in the supplied representation but appears to encode a one-based destination position. Its exact interpretation depends on the target’s pointer and integer arithmetic model.

## Interface

The function has three inputs:

- **Destination:** a byte-addressable pointer to storage that the function may read and write.
- **Source:** a byte-addressable pointer from which the function reads bytes sequentially.
- **Byte budget:** a signed integer controlling the maximum number of loop iterations for ordinary positive inputs.

The declared result is a byte pointer.

### Widths and layout

The operation treats storage as a linear sequence of bytes. It uses masks corresponding to 8-bit character encodings and performs no wider loads, stores, or byte-order conversions.

The supplied representation does not independently establish the target ABI’s pointer width or signed-integer width. In particular, the return expression converts the destination pointer to a signed integer before combining it with a pointer. A 32-bit flat-address interpretation is plausible, but must remain conditional rather than an unconditional portability guarantee.

The result has two distinct cases:

- A zero budget returns a null pointer.
- A nonzero budget reaches a pointer-arithmetic result described under **Behavior**, assuming execution completes without invalid memory access or arithmetic problems.

### Preconditions for a well-defined positive-budget use

For a positive budget of \(N\):

- The destination must support forming its one-past-budget boundary, \(D + N\).
- Destination bytes written during execution must be writable.
- The destination byte selected for the final boundary check must be readable.
- The source must remain readable through the first zero encountered, or through all \(N\) source-byte reads if none is encountered.
- Pointer comparisons and arithmetic must be meaningful under the execution model.

Providing a writable destination region of at least \(N\) bytes and a sufficiently readable source satisfies the ordinary storage requirements. The implementation does not check those requirements.

Source and destination need not be distinct in the visible body. However, overlapping storage can change later source reads, so overlap does not have snapshot-copy semantics.

Negative budgets are not rejected. No safe negative-budget operating contract is established.

## Behavior

### Zero budget

A zero budget causes an immediate null return.

In this case, the function does not read source or destination memory, write destination memory, or perform the later boundary classification. Null source and destination pointers therefore do not themselves cause a dereference on this path.

### Forward copy and observable access order

For a positive budget, the function first establishes the destination boundary at exactly \(N\) bytes after the destination start.

It also establishes a remembered sequence position, initially the destination start. That position is updated whenever a copied nonzero source byte is not a continuation byte.

Each copy iteration has the following observable ordering:

1. Read the current source byte.
2. Decrease the remaining budget.
3. If the byte is zero, write zero to the current destination position and stop copying.
4. Otherwise, classify whether the byte is a continuation byte.
5. If it is not a continuation byte, remember the current destination position.
6. Write the byte to the current destination position.
7. Advance the source and destination positions.
8. Continue only if budget remains.

A continuation byte is any byte from `80` through `BF`, inclusive. Every other nonzero byte updates the remembered position, including malformed encoding bytes.

The first source zero is copied, but it does not update the remembered sequence position. No subsequent source byte is read.

For a positive budget, the loop executes at least once. If there is no source zero within the budget, exactly \(N\) source bytes are read and exactly \(N\) initial destination writes occur.

### Final byte classification

After copying stops, the function reads the byte currently stored at the remembered destination position.

This is a destination read, not a reread of the source. Its value reflects earlier writes and any effects of aliasing.

The byte determines an apparent sequence width:

| Destination byte | Apparent width |
|---|---:|
| `00`–`7F` | 1 |
| `C0`–`DF` | 2 |
| `E0`–`EF` | 3 |
| `F0`–`F7` | 4 |
| `80`–`BF`, `F8`–`FF` | 0 |

These categories are not UTF-8 validity checks. For example, `C0`, `C1`, and `F5`–`F7` receive nonzero widths even though they cannot begin valid modern UTF-8 encodings.

The function does not verify that following bytes are continuation bytes. It does not check overlong encodings, surrogate encodings, scalar-value limits, or whether the apparent sequence is otherwise well formed.

### Boundary adjustment

Let:

- \(D\) be the destination start;
- \(E = D + N\) be the original destination boundary;
- \(A\) be the remembered sequence position;
- \(W\) be the apparent width read from that position.

If \(E \leq A + W\), the function writes zero at \(A\).

The equality case is significant: a sequence whose apparent end falls exactly at the destination boundary is removed. This leaves room for a zero within the budget rather than retaining a sequence that consumes the entire remaining space.

If the condition is false, no final zero is added.

For ordinary positive-budget executions, the remembered position lies within the destination budget. Consequently, a width of zero does not trigger this boundary adjustment.

Replacing the remembered byte does not erase later bytes. Previously copied continuation bytes or other suffix bytes remain in storage after the newly written zero.

### Result selection

Before the final adjustment, the selected result position is the destination position written by the final copy iteration. This is either:

- the copied source zero’s destination position; or
- the last byte copied because the budget was exhausted.

If the boundary adjustment writes a zero at the remembered sequence position, that position becomes the selected result position instead.

The visible return expression adds one minus the signed-integer conversion of the destination address to that selected pointer.

Under a flat, same-width address model where the pointer-to-integer conversion and arithmetic behave as intended, the resulting address value equals:

\[
\text{selected destination offset} + 1
\]

Thus, under that interpretation, the return encodes a one-based offset rather than a pointer into the destination. When the selected byte is the effective terminator of an otherwise ordinary copied string, this is its byte count including the zero.

That interpretation is conditional. The declared pointer return type does not itself guarantee count semantics, and the supplied material does not establish portable behavior for the address cancellation.

### Malformed input and termination

The function is byte-pattern-aware, not encoding-validating.

For well-formed UTF-8 input and a positive budget, the boundary adjustment supports retaining only complete sequences with a zero inside the budget. For arbitrary bytes, a terminating zero is not guaranteed.

Examples of malformed-input behavior include:

- A budget-sized run of continuation bytes can be copied without adding zero.
- A trailing byte from `F8` through `FF` has apparent width zero and can remain as the final nonzero byte.
- Invalid sequences can remain in the retained prefix.
- A leading continuation byte is not rejected.

### Overlap

Reads and writes are interleaved, one byte at a time. No source snapshot is made.

If destination writes overlap source locations that have not yet been read, those writes may alter later input bytes. The result must therefore be determined from the stated access order, not from a separate immutable copy of the original source.

## Side effects

For positive budgets, the function writes only to destination positions reached during copying or to the remembered position within that copied region, assuming valid ordinary pointer arithmetic.

It may overwrite the same byte twice: once during copying and once during boundary adjustment.

It does not clear unused destination capacity. It does not erase bytes following a zero introduced by truncation.

The visible body contains:

- no allocation or deallocation;
- no ownership transfer;
- no external calls;
- no explicit global-state access;
- no I/O;
- no explicit error reporting.

Source bytes are not directly written through the source pointer, but can change when source and destination storage overlap.

Invalid pointers, inadequate storage, and invalid arithmetic have no visible recovery path. The function does not translate such conditions into a documented error result.

## Acceptance examples

The following are conditional static expectations, not runtime observations.

Except for the zero-budget example, assume a positive budget, adequate memory, nonoverlapping source and destination, and ordinary flat-address behavior. Reported numeric results additionally assume the return expression implements the one-based-offset interpretation described above. Byte values are hexadecimal.

### Zero budget

With budget zero, the result is null and no memory is accessed, regardless of the pointer values supplied.

### Empty source

With source beginning `00` and budget 4:

- The first destination byte becomes `00`.
- No later source byte is read.
- The numeric result is 1.
- Remaining destination bytes are unchanged.

With budget 1, the final adjustment writes zero to the same destination byte again. The result remains 1.

### ASCII source fits with its zero

With source `41 42 00` and budget 3:

- Destination begins `41 42 00`.
- The source zero is copied.
- No truncation occurs.
- The numeric result is 3.

### ASCII consumes the entire budget

With source beginning `41 42 43` and budget 3:

- The three bytes are initially copied.
- The final ASCII byte has apparent width 1 and ends exactly at the boundary.
- It is replaced with zero.
- Destination becomes `41 42 00`.
- The numeric result is 3.

With budget 1 and any nonzero ASCII first byte, the final destination byte is `00`, and the numeric result is 1.

### Two-byte sequence exactly fills the budget

With source beginning `C2 A2` and budget 2:

- Both bytes are initially copied.
- The sequence’s apparent end equals the destination boundary.
- Its first byte is replaced with zero.
- Destination becomes `00 A2`.
- The numeric result is 1.

The second byte remains in memory after the zero.

With source `C2 A2 00` and budget 3, the sequence and source zero are retained, and the numeric result is 3.

### Incomplete final sequence

With source beginning `41 E2 82` and budget 3:

- The last remembered sequence begins at destination offset 1.
- Its apparent width is 3, extending beyond the budget.
- Destination becomes `41 00 82`.
- The numeric result is 2.

### Continuation-only malformed input

With source beginning `80 81` and budget 2:

- Both bytes are copied.
- The remembered position remains at destination offset 0.
- Its byte has apparent width zero.
- No terminator is added.
- Destination remains `80 81`.
- The numeric result is 2, despite the absence of a zero.

### Invalid high byte at the boundary

With source beginning `41 FF` and budget 2:

- `FF` becomes the remembered byte.
- Its apparent width is zero.
- No final replacement occurs.
- Destination remains `41 FF`.
- The numeric result is 2.

This case must not be accepted as evidence that the function guarantees zero termination for arbitrary byte input.
