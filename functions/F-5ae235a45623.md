# F-5ae235a45623

## Purpose

F-5ae235a45623 repeatedly resolves and invokes an executable target using a selector byte in a caller-supplied object and a table base captured at entry. Resolution has two forms: direct invocation of an entry’s executable-pointer field, or indirect lookup through an object-relative location containing a 32-bit integer.

There is no visible normal termination condition. Whenever an invoked target returns normally, selection begins again. Changes to the selector or table contents can therefore affect later iterations.

The repeated reads, resolution operations, invocation, and repetition are established by the supplied static representation. Describing the function as a dispatcher is inferred intent. No runtime tests have been performed.

## Interface

**Input.** One signed 32-bit integer is used as the object’s address. It is not treated as an object identifier or an allocation size. The representation does not independently establish the complete machine-address model.

**Output.** No return value or normal-return path is visible. If every invocation returns normally and all subsequent operations remain valid, the function continues indefinitely.

**Invocation interface.** The resolved target is invoked with no explicit arguments shown. Its calling convention, actual inputs, return type, and effects are unknown. The absence of explicit arguments does not establish that a target observes no register, stack, or ambient state.

### Relevant layout and widths

Offsets are byte offsets. The following describes accesses, not a complete object or table schema.

| Location | Read | Role |
|---|---|---|
| Global table-base storage | Signed 32-bit integer, once at entry | Captured base used for entry selection |
| Object address + `0x22D` | Plain-character byte, once per iteration | Entry selector |
| Selected entry + `0x08` | Unsigned 32-bit integer | Mode bit and indirect displacement encoding |
| Selected entry + `0x04` | Executable-pointer value | Direct target or value converted to an indirect lookup offset |
| Computed object-relative location | Signed 32-bit integer, indirect mode only | Integer operand for the second-lookup address calculation |
| Computed second-lookup location | Executable-pointer value, indirect mode only | Final invocation target |

The entry stride is 16 bytes. There are no separate field reads beginning at entry offsets `0x00` or `0x0C`. Because executable-pointer width is not independently established, the complete byte extent of the executable-pointer reads must not be inferred solely from the stride.

The integer model used here is 32-bit signed integers and 32-bit unsigned integers. Executable-pointer width, pointer representation, byte order, and alignment requirements remain unresolved. In particular, the first indirect-resolution load is exactly a 32-bit integer load under this model, not a pointer-sized load.

### Preconditions for valid execution

The environment must provide:

- Readable global table-base storage.
- A readable selector at the supplied object address plus `0x22D`.
- Readable control and executable-pointer fields at every selected entry.
- In indirect mode, readable storage for the 32-bit integer load and the final executable-pointer load.
- A resolved target compatible with the actual invocation mechanism.
- Valid storage lifetimes for every access, including accesses after a target returns.
- Address calculations and integer-to-address interpretations that are valid in the execution environment.

The function performs no visible validation of these conditions. A non-null object address alone does not establish them.

## Behavior

### Entry-time capture

The function reads the global table-base value once and retains that signed 32-bit value for entry selection.

It does not visibly reload the global storage after an invoked target returns. A target’s replacement of the global base therefore does not, by itself, redirect this active invocation to the replacement table.

The capture does not snapshot table contents. Entry fields are read again on every iteration.

### Ordered selection and invocation

Each iteration has the following observable order:

1. Read the selector byte from object offset `0x22D`.
2. Calculate the selected entry address relative to the retained base, using a 16-byte stride.
3. Read the unsigned 32-bit control word at entry offset `0x08`.
4. Read the executable-pointer field at entry offset `0x04`.
5. If control bit 0 is set, perform the additional integer and executable-pointer reads described below.
6. Invoke the resolved target.
7. If the invocation returns normally, start another iteration with a new selector read.

The control-word read precedes the executable-pointer-field read despite its higher address.

The selector, control word, and executable-pointer field are not cached across iterations. No locking, atomic snapshot, or consistency check is visible. Concurrent modification can therefore affect separate reads independently; the function does not establish a coherent entry version.

### Selector interpretation

The selector is read through a plain-character type and promoted before multiplication. Plain-character signedness is unresolved.

For selector bytes `0x00` through `0x7F`, the displacement is unambiguous: zero through 127 strides forward.

For bytes `0x80` through `0xFF`:

- An unsigned interpretation selects entries 128 through 255 forward.
- A signed 8-bit interpretation selects entries before the retained base.

The corresponding displacement ranges are:

| Character interpretation | Possible displacement |
|---|---|
| Unsigned 8-bit | `0` through `4080` bytes |
| Signed 8-bit | `−2048` through `2032` bytes |

Multiplication by 16 fits in signed 32-bit arithmetic for either range. The subsequent addition to the retained base has separate overflow and address-validity concerns.

There is no selector range check. Negative selection under the signed interpretation is not rejected.

### Direct resolution

When control bit 0 is clear, the executable-pointer field read from the entry is invoked directly.

In this mode:

- No object-relative integer read occurs.
- No second-lookup executable-pointer read occurs.
- No low-bit mask is applied to the target.
- Other control-word bits do not affect resolution.

The clear mode bit does not validate the executable pointer. There is no visible null check, executable-address check, or compatibility check.

### Indirect resolution: displacement and integer load

When control bit 0 is set, the entry’s executable-pointer field is not invoked directly.

The complete control word is converted from unsigned 32-bit to signed 32-bit and shifted right by one. The resulting signed value supplies an object-relative displacement.

For control words below `0x80000000`, the conversion is representable, and shifting produces a nonnegative displacement. For example, `0x00000009` produces a displacement of four bytes.

For control words with bit 31 set, the unsigned-to-signed conversion and the right shift of a negative signed value require execution-model details not supplied here. Arithmetic right shift after a two’s-complement interpretation would allow negative displacements, but that behavior is conditional, not established for every environment.

The displacement is added to the signed 32-bit object-address value. At the resulting location, the function reads a **signed 32-bit integer**.

That integer is subsequently used numerically. The representation does not establish that the loaded storage contains a native pointer, that its width matches executable-pointer width, or that the loaded value is already a valid address.

### Indirect resolution: masked offset and second lookup

The entry’s executable-pointer value is converted to an unsigned 32-bit integer. The result is masked with `0xFFFFFFFC`, clearing its lowest two bits.

The pointer-to-integer conversion is distinct from the mask. Its mapping is not independently established. If executable pointers have a wider or otherwise different representation, the source does not justify treating the conversion as a lossless preservation of the entire pointer.

Once the unsigned 32-bit conversion result is available, the mask has an exact numeric effect: the offset is a multiple of four between zero and `0xFFFFFFFC`.

The second-lookup calculation combines:

- The signed 32-bit integer loaded from the object-relative location.
- The masked unsigned 32-bit offset.

Under the stated integer model, the signed operand is converted to unsigned 32-bit, and **the addition is unsigned 32-bit arithmetic modulo \(2^{32}\)**. A negative loaded integer contributes its residue modulo \(2^{32}\). Overflow of this unsigned addition wraps; it is not an unresolved signed-overflow case.

The resulting 32-bit unsigned number is then used as the location of an executable-pointer read. Whether that number denotes a valid, readable, suitably aligned address remains unresolved. Defined modular arithmetic does not imply a valid memory access.

The executable pointer read at that location is invoked. No fallback path is visible if either indirect read is invalid.

Clearing the offset’s lowest two bits does not ensure alignment of the final address: the loaded integer also contributes to that address. Nor does the mask establish that the discarded bits are flags.

### Arithmetic boundaries and termination

The second-lookup unsigned addition has established modulo-\(2^{32}\) behavior under the stated model. That conclusion must not be generalized to every calculation in the function.

Entry-base addition and object-address-plus-displacement use signed integer operands in the representation. Their behavior at signed overflow is not established as wrapping. Numeric-to-address interpretation and address validity also remain separate questions.

There is no visible bounds check, overflow check, error return, or recovery branch.

A returning target causes another iteration. A target that never returns prevents normal loop continuation. Faults, exceptions, or nonlocal transfers may also interrupt execution, but their handling is outside the supplied behavior.

## Side effects

The visible body contains no explicit application-memory writes. It reads global, object, and table-related storage, then transfers control to a dynamically resolved target.

This does not make the overall operation read-only:

- Targets may modify the selector, table entries, globals, or unrelated storage.
- Targets may allocate, release, or invalidate memory.
- Targets may perform I/O or transfer control without returning.
- Reads may themselves be observable when directed at special memory.

None of those target effects is established as occurring, and none may be assumed absent.

No ownership transfer is visible in the function itself. It does not visibly allocate, retain, release, or free the object or table. An invoked target’s ownership contract is unknown.

If a target returns after invalidating storage needed by the next iteration, the function still proceeds to its next required access. There is no visible lifetime revalidation.

Ordinary stack and register effects depend on the execution environment and are not specified by this application-memory contract.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not runtime results. Unless specified otherwise, required accesses and invocations are valid.

### Direct selection and repetition

With selector `3`, the entry begins 48 bytes after the retained base.

If control bit 0 is clear, the entry’s executable-pointer field is invoked without either indirect read. If the target returns without relevant changes, the next iteration rereads the selector, control word, and executable-pointer field before invoking again.

Permanently caching the first target would not satisfy this behavior.

### Selector changed by a target

An initial selector of `1` selects the entry 16 bytes after the retained base.

If its target changes the selector to `4` and returns, the next iteration selects the entry 64 bytes after that same retained base.

### Global base replaced by a target

Suppose the function captures base A, and a target subsequently changes the global base storage to B.

After normal return, the active invocation continues selecting relative to A. A later, separate invocation may capture B.

Changes to entries at A remain observable through subsequent entry reads.

### Positive indirect displacement

With control word `0x00000009`, indirect mode applies and the displacement is four bytes.

Suppose the entry field’s unsigned 32-bit conversion result is `0x0000000B`, and the signed 32-bit integer read at object address plus four is `0x00001000`.

The masked offset is eight. The second lookup reads an executable pointer at numeric address `0x00001008`, subject to valid address interpretation, and invokes that pointer.

The first indirect read is four bytes under the stated model, independently of executable-pointer width.

### Unsigned wraparound in the second lookup

With the same displacement, suppose the object-relative integer load returns `−16`, and the entry field converts to unsigned value `0x00000023`.

The masked offset is `0x00000020`. Converting `−16` to unsigned 32-bit yields `0xFFFFFFF0`; adding the offset modulo \(2^{32}\) yields `0x00000010`.

The next attempted executable-pointer read is therefore based on numeric address `0x00000010`, not a wider unwrapped sum. Whether that address is usable is a separate condition.

### Clear mode bit with other bits set

Control word `0x00000100` selects direct mode. The remaining bits do not cause an object-relative lookup.

### High-bit selector

For selector byte `0xFF`:

- Signed 8-bit interpretation selects one stride before the retained base.
- Unsigned interpretation selects 255 strides after it.

A definitive expected entry requires resolving character signedness.

### Non-returning target

If D-01 never returns, there is no subsequent selector read through normal loop continuation. The function contains no independent mechanism forcing another iteration.
