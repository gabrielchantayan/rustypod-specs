# F-31e19ec0ca86

## Purpose

F-31e19ec0ca86 captures selected 32-bit values into storage selected through global bases, copies two 128-byte blocks into adjacent portions of another globally selected region, and then performs a fixed sequence of configuration and control writes.

Global selection does not establish independence from callers. Callers may supply, modify, own, or alias any of these regions. The function neither establishes ownership nor checks whether the regions overlap.

The established behavior is an ordered sequence of memory accesses. Terms such as “register window,” “snapshot,” “configuration,” and “control” describe apparent roles, not verified hardware semantics. Interpreting the sequence as device initialization is inferred intent only; no readiness outcome is established.

## Interface

### Invocation and implicit inputs

The function has no explicit arguments and no explicit return value. Its inputs are values obtained through global storage and memory reached through those values.

| Contract name | Role |
|---|---|
| Register-window base | Selects the sources for selected-value capture and the first block copy, and the destinations for six later writes. |
| Snapshot base | Selects the destination for 23 captured words. |
| Block-output base | Selects the destination for two adjacent 128-byte blocks. |
| Auxiliary-source base | Selects the source for the second block; its global storage is read repeatedly during the first block copy. |
| Configuration word | Supplies the final 32-bit register-window write. |
| Primary-control base | Selects two initial control destinations and one repeatedly written destination. |
| Secondary-control base | Selects two other initial control destinations and another repeatedly written destination. |

These names denote roles within this contract, not source identifiers or ownership categories. A global base is not necessarily read only once. The distinction between retained base values and later global reads matters if global storage changes or aliases a written region.

### Outputs and widths

On normal completion, the function performs:

- 23 selected-value writes, each 32 bits wide.
- 64 block-output writes, each 32 bits wide.
- Six register-window configuration writes.
- Four initial control writes.
- 128 further control writes, arranged as 64 ordered pairs.

This is 225 explicit destination writes. It does not include reads of payloads or global storage.

Every explicit payload transfer and destination write is 32 bits wide. Copied values retain their complete bit patterns. The payload `0xFFFFFFFF` means 32 one-bits; the contract does not assign it a signed numeric interpretation.

There is no returned status, count, pointer, or readiness indication.

### Preconditions for normal completion

Every effective address must support the corresponding 32-bit access. Alignment, access permissions, address arithmetic, and any device-access restrictions must satisfy the execution environment.

In particular:

- The selected register-window offsets must be readable.
- Snapshot destinations from offset `0x08` through word offset `0x60` must be writable.
- Both block-output halves must be writable.
- The selected auxiliary source must provide 128 readable bytes through 32 word accesses.
- The listed configuration and control destinations must be writable.
- The primary-control base must permit the effective address at displacement `−0xBFF100`.

The function performs no visible validation of these conditions.

No null, sentinel, or special-case base value is recognized. A zero-valued base does not skip a stage; it participates in the same effective-address calculations.

Payload widths are established, but the supplied representation does not independently settle the target pointer width, byte order, alignment rules, or address-overflow semantics. Correctly resolving the effective addresses is an environmental precondition, not an assumed portable arithmetic guarantee.

The order in which the first transfer evaluates its two global-based address expressions is not independently established. The table does not require those global reads to be simultaneous.

### First block and auxiliary-base sampling

After selected-value capture, the function reads and retains the block-output base.

It transfers 32 consecutive 32-bit words from the retained register-window base into the first half of the block-output region:

- Source word offsets: `0x100` through `0x17C`.
- Destination word offsets: `0x00` through `0x7C`.
- Source byte extent: `0x100` through `0x17F`.
- Destination byte extent: `0x00` through `0x7F`.

Transfers proceed in ascending word order. Each source read supplies one destination write.

After each destination write, the function reads the auxiliary-source-base global. There are exactly 32 such reads in the displayed sequence. Only the last sampled value supplies the source base for the second block.

Consequently:

- The auxiliary source is not fixed at function entry.
- Intermediate sampled bases do not select individual words of the second block.
- A first-block write that aliases the auxiliary-base global can affect the following sample.
- The final sample occurs after the first block’s last destination write and before the second block begins.

The function does not use a data-dependent length, terminator, or early-exit condition.

### Second block

Using the final sampled auxiliary base, the function transfers another 32 consecutive 32-bit words:

- Source word offsets: `0x00` through `0x7C`.
- Destination word offsets: `0x80` through `0xFC`.
- Source byte extent: `0x00` through `0x7F`.
- Destination byte extent: `0x80` through `0xFF`.

Transfers again proceed in ascending word order, with each source read supplying its corresponding destination write. The auxiliary-base global is not visibly reread during this stage.

Both blocks use the same retained block-output base. Together they explicitly write 256 consecutive destination bytes.

Neither block is captured into a separate temporary buffer. If an earlier destination write alters a later unread source word, that later read can observe the altered value. The operation must not be treated as an overlap-safe bulk copy.

### Register-window configuration

After both blocks finish, the function performs six full-width writes through the register-window base retained before selected-value capture:

| Order | Register-window offset | 32-bit payload |
|---:|---:|---:|
| 1 | `0xC000CC` | `0x00000008` |
| 2 | `0xC000D8` | `0x10000000` |
| 3 | `0xC0008C` | `0x00000000` |
| 4 | `0xC000EC` | `0x00000008` |
| 5 | `0x000014` | `0xFFFFFFFF` |
| 6 | `0x000010` | Configuration word read from global storage |

The configuration word is read for the sixth write, after the write at offset `0x14`. It is not captured at entry or before the block copies. Earlier writes that alias its global storage may therefore affect the value used.

These are replacement writes, not read-modify-write operations.

Five of these destinations were read during selected-value capture. With stable base globals, nonaliasing output storage, and no independent source changes, the corresponding snapshot entries retain the pre-configuration observations. The function does not deliberately refresh them after configuration.

### Initial control writes

The function next reads and retains the primary-control base. It then performs:

1. A write of `0xFFFFFFFF` at offset `0xAC`, using an explicit reread of the primary-control-base global.
2. A write of `0xFFFFFFFF` at offset `0xB8`, using the retained primary base.

It then reads and retains the secondary-control base and performs:

3. A write of `0xFFFFFFFF` at offset `0x14`, using an explicit reread of the secondary-control-base global.
4. A write of `0x00000000` at offset `0x10`, using the retained secondary base.

Stable globals make each reread equivalent to its retained value. Without that condition, the first write for either control role may target a different base from subsequent writes.

There is no readback or success check.

### Repeated control writes and completion

The final stage consists of exactly 64 iterations. Every iteration writes:

1. `0x00000001` at displacement `−0xBFF100` from the retained primary-control base.
2. `0x00000001` at offset `0xF00` from the retained secondary-control base.

The addresses do not advance. These are 128 writes to two invariant effective addresses, not an array traversal. If those addresses alias, both writes in each pair target the same location.

The bounded iteration counts are 32, 32, and 64. Their word-offset calculations do not require an unbounded counter or data-dependent arithmetic; the largest block word offset is `0x7C`. Effective-address arithmetic remains subject to the environmental requirements described above.

There is no explicit polling, delay, acknowledgment read, or retry condition. Normal return follows the sixty-fourth pair, without any established guarantee that external hardware has completed an operation.

## Side effects

The function performs no explicit allocation, deallocation, ownership transfer, or external function call. Destination storage is selected through globals; it may still be caller-owned or caller-controlled. The function does not establish exclusive access to it.

For ordinary, disjoint regions with stable globals:

- Snapshot bytes outside `0x08`–`0x63` receive no explicit snapshot writes.
- The block-output region receives exactly two adjacent 128-byte blocks.
- Register-window configuration affects the six listed word locations.
- Control writes affect the four initial locations and two repeated-write locations.

These are conditional region descriptions, not nonaliasing guarantees. If regions overlap one another or global storage, earlier writes can alter later payloads, later base samples, or previously written results. There is no overlap detection or synchronization.

Device-backed reads and writes may have additional effects, including effects caused by reading alone. Those effects are not established by the supplied evidence.

There is no explicit error reporting, rollback, exception handling, or transactional boundary. An interruption or failed access may leave a completed prefix of the access sequence. The function defines no recovery result for that situation; actual fault delivery and continuation behavior remain environmental unknowns.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests.

### Caller-supplied destination storage

Given valid, stable destination bases that refer to caller-owned storage, ownership alone does not change the transfer sequence. The function writes through those bases without allocating replacement storage or releasing the supplied regions.

This does not imply that caller-owned storage is disjoint from sources or globals; any aliasing must still follow the ordered-access behavior.

### Capture precedes configuration

Given stable globals, disjoint output storage, and stable source contents during capture:

- The value observed at register-window offset `0xC000CC` reaches snapshot offset `0x34`.
- The function later writes `0x00000008` at register-window offset `0xC000CC`.
- The snapshot entry retains the earlier observation.

The same capture-before-configuration relationship applies to source offsets `0x10`, `0xC0008C`, `0xC000EC`, and `0xC000D8`, mapped respectively to snapshot offsets `0x08`, `0x38`, `0x3C`, and `0x58`.

### Exact block boundaries

Given valid, disjoint regions containing distinguishable words:

| Source | Destination |
|---|---|
| Register-window offset `0x100` | Block-output offset `0x00` |
| Register-window offset `0x17C` | Block-output offset `0x7C` |
| Auxiliary offset `0x00` | Block-output offset `0x80` |
| Auxiliary offset `0x7C` | Block-output offset `0xFC` |

Neither block performs a thirty-third transfer. The final destination word occupies bytes `0xFC` through `0xFF`.

### Final auxiliary sample selects the whole second block

If auxiliary-base reads during the first block yield different valid bases, the value sampled after the thirty-second first-block write selects all 32 second-block source words.

Changing the global after that sample does not, by itself, change the retained second-block source base. This criterion does not prescribe platform-specific visibility of concurrent updates.

### Forward overlap affects later reads

If the first destination word of a block overlaps its next unread source word, that destination write can change the payload read for the next transfer. Acceptance must follow sequential word accesses rather than require the original contents of the entire source block.

### Configuration is sampled late

If valid aliasing causes the write at register-window offset `0x14` to update the configuration-word global, the final write at offset `0x10` uses the subsequently read configuration value, not an entry-time copy.

### Repetition is observable in the access sequence

Given an observer that records the displayed memory accesses, the final stage contains 64 primary-then-secondary pairs, each carrying `1`. Merely observing a final stored value of `1` at both locations does not establish that all pairs occurred.

### Payloads do not terminate copying

A copied word containing zero or `0xFFFFFFFF` is transferred unchanged. Neither pattern shortens a block, skips a subsequent transfer, or alters the fixed iteration counts.
