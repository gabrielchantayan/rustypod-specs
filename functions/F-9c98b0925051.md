# F-9c98b0925051

## Purpose

F-9c98b0925051 conditionally scans indexed entries supplied by an indirect callback. It stops normally when scanning is disabled or when every examined entry has a zero leading integer. On the first entry whose leading integer is nonzero, it invokes F-896f1e0faadb and, if that invocation returns normally, invokes F-feee9156a257.

The supplied static representation marks F-feee9156a257 as non-returning. Consequently, the nonzero-entry path has no represented normal return after that invocation.

This is a behavioral description of the supplied static evidence, not a claim about runtime observations. The meanings of the entries, the enable field, and the two direct dependencies are not established. In particular, identifying the nonzero-entry path as an assertion, exception, termination, or validation failure would exceed the evidence.

## Interface

### Input and return

The function receives one pointer to an object represented as an array of integer-sized fields. It has no represented return value and no explicit output parameter.

For layout discussion, the supplied representation supports a 32-bit integer-field model:

| Location | Observed role |
|---|---|
| Integer field 0, nominal byte offset 0 | Address used as the base for an indirect dispatch-slot lookup. |
| Integer field 1, nominal byte offset 4 | Signed scan bound, captured once before scanning. |
| Integer field 10, nominal byte offset 40 | Enable value, tested after conversion to a character-sized value. |
| Dispatch-base byte offset 64 | Location containing the indirect callback address. |
| Integer field 0 of each callback result | Value tested for zero versus nonzero. |

These byte offsets for object fields follow the 32-bit integer interpretation. The dispatch displacement of 64 bytes is explicit in the supplied representation. The source material does not independently establish the complete target ABI, pointer width, endianness, alignment rules, or original source-language object type.

The enable test is not a full-integer nonzero test. It compares a character-converted value with zero. Under an eight-bit truncating character conversion, this is a test of the low eight bits of the field’s numerical value. The mapping from that numerical portion to a particular addressed byte depends on endianness. The exact machine load width cannot be recovered from this representation alone.

### Indirect callback

The indirect callback receives:

1. The same object pointer supplied to F-9c98b0925051.
2. The current zero-based scan index.

Its result is treated as a pointer to readable integer storage. The first integer at that address is read and tested. The routine does not inspect any other returned fields.

No validation of the returned pointer is represented. A null, invalid, insufficiently aligned, or unreadable result is not converted into a documented error return.

### Preconditions

Successful execution requires valid storage and callable targets for every location actually reached:

- The enable field must be readable even when scanning is disabled.
- If enabled, the scan-bound field must be readable.
- For each callback invocation, the dispatch-base field and the callback slot must be readable, and the selected address must be callable with the represented arguments.
- Every normally returned callback result must support the leading-integer read.
- On a nonzero-entry path, the direct dependencies must be callable.

These requirements are path-dependent. A disabled invocation does not need to reach the scan-bound field, dispatch storage, or any entry result.

## Behavior

### Enable gate

The first represented operation reads the enable field and evaluates its character-converted value.

If that value is zero, the function returns immediately. It does not read the scan bound, resolve the indirect callback, or invoke either direct dependency.

No subsequent enable-field test is represented. Changing the enable field during a callback therefore does not, by itself, alter the already-started scan’s control flow.

### Bound capture

If enabled, the function reads the signed scan bound once and begins scanning at index zero.

Before any callback invocation, it compares the current index with the captured bound. If the bound is less than or equal to the index, it returns normally.

Consequences include:

- A zero bound produces no callback invocations.
- A negative bound also produces no callback invocations.
- A positive bound permits indices from zero through one less than that bound, unless an earlier nonzero entry or a dependency’s control transfer prevents further progress.
- Callback changes to the object’s stored bound do not replace the captured bound.

The scan is therefore not a live traversal of a repeatedly read count.

### Entry examination

For each permitted index, the routine resolves the callback through the object’s dispatch-base field and the slot at displacement 64. It then invokes the callback with the object pointer and current index.

The callback address is not represented as cached across iterations. The dispatch-base field and dispatch slot are consulted again when another entry is reached. Thus, a callback that changes the object’s dispatch base or a later-used callback slot may affect subsequent dispatch, provided execution and all accessed storage remain valid.

After a callback returns normally, the routine reads the leading integer from its returned pointer:

- If the integer is zero, the routine advances to the next index.
- If the integer is nonzero, the routine stops scanning immediately and enters the direct-dependency path.

Both positive and negative nonzero integers select that path. The tested value is not accumulated, copied to an output, or forwarded as an explicit argument to either direct dependency.

The tested entry is examined only after the callback returns. Consequently, the callback may determine or modify the value that this read observes. The evidence does not establish that the returned pointer denotes a persistent object, a temporary buffer, an element of the original object, or separately allocated storage.

### Exhaustion and arithmetic

When every examined leading integer is zero, the routine returns after the next bound comparison rejects the index.

Under the represented signed 32-bit integer model, the index progression does not itself require signed overflow. An increment occurs only after processing an index strictly below the captured bound. For the largest positive signed bound, the last examined index is one below that bound, and its increment reaches the bound without exceeding the signed maximum. The following comparison ends the scan.

This arithmetic property does not guarantee practical completion. A large positive bound can require many indirect calls, and a callback may fail to return, invalidate later storage, or transfer control elsewhere.

### Nonzero-entry path

Upon observing the first nonzero leading integer, the routine:

1. Invokes F-896f1e0faadb without explicit arguments.
2. If that invocation returns normally, invokes F-feee9156a257 without explicit arguments.

There are no further represented entry reads, index advances, or callback invocations on this path.

The ordering matters. F-feee9156a257 is not established as reachable if F-896f1e0faadb terminates execution, throws, faults, or otherwise does not return normally.

The supplied annotation classifies F-feee9156a257 as non-returning. There is no represented continuation that defines what should happen if that classification is incorrect.

## Side effects

### Direct effects

The routine directly performs reads and calls. No direct write to the input object, dispatch storage, or returned entry storage is represented.

Its scan index and captured bound are internal control state; they are not explicit outputs.

Absence of direct stores does not make the invocation externally side-effect-free. All invoked dependencies may have effects that are not described by the supplied body.

### Ordering of observable operations

On an enabled scan, the represented order is:

- Read the enable value.
- Read and capture the signed bound.
- For each reached index, resolve the callback through the dispatch storage.
- Invoke that callback.
- After its normal return, read the leading integer at its result.
- Either proceed to the next index or invoke the two direct dependencies in their stated order.

If a callback does not return normally, no subsequent leading-integer read or later call by this routine is established.

This is the logical ordering shown by the supplied representation. Exact machine load widths, memory-ordering instructions, concurrency guarantees, and volatile behavior are not established.

### Ownership and lifetime

No allocation, deallocation, retain, release, or ownership-transfer operation is explicitly represented.

The routine does not explicitly release callback results. This does not establish a leak: ownership and lifetime rules are unknown. The callback may return borrowed storage or manage storage through an undisclosed protocol.

Likewise, no dependency may be assumed to preserve globals, retain the input object, leave dispatch storage unchanged, or refrain from releasing memory. If a dependency changes storage later accessed by this routine, continued validity is a caller/dependency precondition rather than a guarantee supplied here.

### Error handling

There is no explicit error result and no represented recovery for invalid object fields, bad dispatch addresses, invalid callback results, or dependency failures.

The nonzero-entry path is an established behavioral branch, but its semantic classification as an error is unknown. Hardware faults, language exceptions, process termination, and other nonlocal transfers cannot be characterized further from the supplied evidence.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Unless stated otherwise, all reached storage and calls satisfy the preconditions.

### Disabled invocation

Given an enable value whose character conversion equals zero, the invocation returns without reading the bound or calling any dependency.

Under an eight-bit truncating conversion, a numerically nonzero field whose low eight bits are zero still satisfies this case. Treating every nonzero full-width enable field as enabled would not match that interpretation.

### Enabled with a nonpositive bound

Given an enabled object and a captured bound of zero or a negative signed value, the invocation returns without resolving or calling the indirect callback. Neither direct dependency is invoked.

### All entries zero

Given a captured bound of three, callbacks that return normally, and leading integers of zero at all three returned addresses, callback indices are observed in order: zero, one, two.

The invocation then returns normally. Neither direct dependency is invoked.

### First nonzero entry

Given a captured bound of four and leading integers of zero, negative seven, zero, and zero, only indices zero and one are requested.

After reading negative seven at index one, the routine invokes F-896f1e0faadb. If that returns normally, it invokes F-feee9156a257. Entries two and three are not requested.

### Bound mutation during scanning

Given an initial captured bound of three, suppose the callback at index zero changes the object’s stored bound to zero and returns a zero-valued entry.

If subsequent calls return normally and storage remains valid, indices one and two are still eligible. The original bound governs the scan.

### Dispatch mutation during scanning

Given a positive bound greater than one, suppose the callback at index zero changes the dispatch base or callback slot and returns a zero-valued entry.

The next callback is resolved through the dispatch storage reached on that next iteration, rather than through a callback address cached before index zero.

### Non-returning first dependency

Given a nonzero leading integer, if F-896f1e0faadb does not return normally, there is no established invocation of F-feee9156a257.

This distinguishes the observed call sequence from an unconditional guarantee that both dependencies execute.
