# F-9966ca29b392

## Purpose

F-9966ca29b392 rewires a small set of four-byte links. Interpreting those links as parent, left-child, and right-child references, it performs a right rotation around the supplied target, promoting the target’s left child.

The link accesses and their ordering are established by the supplied static body. The tree terminology and right-rotation interpretation are inferred from the relationships among those accesses; no complete type definitions or structural validation establish them independently.

The operation updates either a distinguished root slot or one child link in the target’s parent. It does not compare payload values or ordering keys, inspect payload fields, update balancing metadata, allocate storage, or release storage. It does compare link values: a repeatedly read transfer-subtree link against zero, the root slot against the target, and, conditionally, a parent’s right-child-like link against the target.

No runtime tests have been performed.

The following roles describe addresses encountered during execution:

- **Initial transfer subtree:** the address first read from the promoted node’s offset-12 field and copied into the target’s offset-8 field.
- **Former parent:** the target’s initial parent-like link, when discussing stable, non-overlapping tree input.

The transfer-subtree link is read repeatedly rather than retained once. Consequently, outside the stable, non-overlapping case, later uses need not identify the initial transfer subtree.

### Preconditions for the intended rotation

A conventional tree-rotation result requires:

- Accessible context storage at offset 16 and an accessible root-holder field at offset 4.
- A live target with readable and writable fields at the accessed offsets.
- An initial target left-child-like link identifying an accessible promoted node.
- A writable parent-like field in the node selected for transfer-subtree repair, if that repair is taken.
- An accessible parent node when the root slot does not equal the target.
- Non-overlapping relevant fields and no intervening external mutation.
- A consistent incoming link: either the root slot identifies the target or the former parent identifies it through the appropriate child link.

These are preconditions for the intended result, not checks performed by the function. In particular, the promoted-node address is dereferenced without a zero check, and the non-root fallback does not verify that the parent’s left-child-like link identifies the target.

## Behavior

### Intended structural result

For valid, stable, non-overlapping tree input, normal completion has the following result:

- The promoted node replaces the target in the distinguished root slot or in the former parent.
- The promoted node’s parent-like link becomes the target’s former parent-like link.
- The target becomes the promoted node’s right child.
- The target’s parent-like link becomes the promoted-node address.
- The initial transfer subtree becomes the target’s left child.
- If the transfer subtree is nonzero, its parent-like link becomes the target address.

The promoted node’s left-child-like field and the target’s right-child-like field are not directly written. Their preservation as distinct fields requires the non-overlap assumption.

The function does not establish ordering, balance, acyclicity, or general tree validity.

### Transfer and conditional parent repair

The first memory read obtains the promoted-node address from the target’s offset-8 field.

The promoted node’s offset-12 field is then read, and that four-byte value is written into the target’s offset-8 field. This is the first write. It occurs before root or parent attachment is repaired.

After this write, the promoted node’s offset-12 field is read again and compared with zero:

- If that second read is zero, transfer-subtree parent repair is skipped.
- If it is nonzero, the same field is read a third time. The address obtained by this third read selects the object whose offset-4 field receives the target address.

There is no separate zero check on the third value. The value copied into the target, the value tested against zero, and the value used to select the repair destination are therefore distinct observations of the same field.

For stable, non-overlapping memory, those observations agree. With aliasing or external mutation, they may differ. For example, a nonzero test does not by itself establish that the subsequent repair destination is nonzero or valid.

### Promoted node’s upward link

After the optional repair, the target’s offset-4 field is read. Its four-byte value is copied into the promoted node’s offset-4 field.

This copy precedes the root-slot test and any parent-child attachment repair. The copied value is whatever is present at that point, not an independently preserved initial parent value.

### Incoming attachment selection

The function next reads the root-holder address from context offset 16 and reads that holder’s offset-4 field.

If the root slot equals the target address, the root slot receives the promoted-node address. The slot used for this write is the one selected by that root-holder lookup; the context’s root-holder reference is not reread for the write.

The root match takes precedence over parent-child inspection. On this branch, the target’s parent-like link has already been read for the preceding copy, but the parent’s child fields are not inspected.

If the root slot does not equal the target address:

- The target’s offset-4 field is read again to obtain the parent address.
- That parent’s offset-12 field is read and compared with the target address.
- A match selects the parent’s offset-12 field for replacement with the promoted-node address.
- A mismatch selects the parent’s offset-8 field for replacement with the promoted-node address.

The fallback does not read or validate the previous left-child-like value. A malformed non-root relationship can therefore cause an unrelated left-child-like link to be overwritten.

The parent address used on this branch comes from a separate read after the earlier upward-link copy. Equality with the value copied into the promoted node is conditional on stable, non-overlapping memory.

### Final attachment

After the incoming root or parent link is replaced, the promoted node’s offset-12 field receives the target address.

The target’s offset-4 field then receives the promoted-node address. This is the final write.

The order matters: the incoming attachment is repaired before the promoted node’s right-child-like field is overwritten, and that downward link is installed before the target’s final parent-like link.

## Side effects

### Writes and their order

On normal completion, the function performs **five four-byte writes when transfer-subtree parent repair is skipped, or six when that repair occurs**.

The ordered writes are:

1. The target’s left-child-like field receives the first value read from the promoted node’s right-child-like field.
2. Conditionally, the parent-like field selected through the third transfer-link read receives the target address.
3. The promoted node’s parent-like field receives the value read from the target’s parent-like field.
4. Exactly one incoming attachment receives the promoted-node address: the root slot, the selected parent’s right-child-like field, or that parent’s left-child-like field.
5. The promoted node’s right-child-like field receives the target address.
6. The target’s parent-like field receives the promoted-node address.

There are five unconditional writes and one conditional write. The count concerns executed write operations, not distinct destination addresses or changed values. Aliased destinations and stores of an already-present value do not reduce that count.

For ordinary stable tree input, a zero transfer-subtree link produces five writes, and a nonzero link produces six. More generally, the count is controlled by the second read of the promoted node’s offset-12 field.

There is no direct write to context offset 16. Aliasing can nevertheless make a destination overlap storage described under another role; preservation claims require distinct relevant fields.

## Acceptance examples

These examples are conditional criteria derived from static evidence. They are not executed test results.

### Root target with an empty transfer subtree

Given valid, stable, non-overlapping objects, a root slot equal to the target, and a zero promoted-node right-child-like link:

- The target’s left-child-like field becomes zero.
- No transfer-subtree parent write occurs.
- The promoted node receives the target’s former parent-like value, without requiring that value to be zero.
- The root slot becomes the promoted-node address.
- The promoted node’s right-child-like field becomes the target.
- The target’s parent-like field becomes the promoted node.
- Exactly five four-byte writes occur.
- The parent-child selection branch is not taken.

### Nonzero transfer subtree

Given otherwise valid stable tree input and a nonzero transfer-subtree link:

- The target’s left-child-like field becomes that link.
- The transfer subtree’s parent-like field becomes the target.
- That repair occurs before the promoted node’s upward link and incoming attachment are written.
- Exactly six four-byte writes occur.

### Non-root target selected through the parent’s right child

Given a root slot different from the target and a parent whose right-child-like field equals the target:

- The parent’s right-child-like field receives the promoted-node address.
- The parent’s left-child-like field is not directly written.
- Under stable, non-overlapping conditions, the promoted node’s parent-like field becomes that parent’s address.
- No root-slot write occurs.

### Unchecked left-child fallback

Given a non-root target and an accessible parent whose right-child-like field does not equal the target:

- The parent’s left-child-like field receives the promoted-node address.
- Its previous value need not equal the target.
- No structural-consistency error is returned.

This describes the branch behavior, not a guarantee that malformed input yields a valid tree.

### Missing promoted node

If the target’s initial left-child-like value is zero, there is no empty-child return path. The next access attempts to read the field at offset 12 from that address value.

Successful completion is not promised. Exact platform behavior is documented_only.

### Transfer-link observations disagree

If earlier aliasing effects or external mutation make the first transfer-link read nonzero but the second zero:

- The first value is still copied into the target’s left-child-like field.
- The transfer-subtree parent repair is skipped.

If the second read is nonzero, the repair destination comes from the third read, not from the first or second value. These are access-sequence criteria only; they do not promise safe or portable concurrent execution.
