# F-447693a4cb8d

## Purpose

F-447693a4cb8d performs an in-place link transformation consistent with a left rotation of a parent-linked binary tree. It promotes the selected node’s right child into that node’s position, moves the promoted node’s former left subtree to the selected node’s right side, and makes the selected node the promoted node’s left child.

The link transformation is established by the supplied static evidence. Its intended use in a binary tree is an interpretation of that transformation, not evidence that the routine enforces any tree invariant.

The routine does not search for a node, compare keys, validate links, or rebalance a larger structure. It performs no explicit allocation, release, or dependency call. Successful use requires the caller to supply a suitable writable structure, including a non-null right child for the selected node.

## Behavior

### Observable access order

The static evidence establishes the following ordered phases. This is the ordering of the represented field accesses, not a claim about machine-level atomicity or a concurrency memory model.

1. **Obtain the promoted node and move its left link.**

   The routine first reads the selected node’s right-child field. That address identifies the promoted node throughout the remaining operation.

   It then reads the promoted node’s left-child field and writes the resulting four-byte value to the selected node’s right-child field.

   The promoted node is dereferenced without a preceding null check.

2. **Repair the transferred subtree’s parent, conditionally.**

   After the selected node’s right-child field has been written, the routine reads the promoted node’s left-child field again and tests it against zero.

   If that read is nonzero, the routine obtains the destination address from another read of the same promoted-node field and writes the selected-node address into that destination node’s parent field.

   Under stable, non-overlapping storage, these reads identify the same transferred subtree. If the link is zero, no transferred-subtree parent field is accessed or written.

3. **Give the promoted node the selected node’s current parent.**

   The routine reads the selected node’s parent field and writes that four-byte value into the promoted node’s parent field.

   This occurs before the container’s header address and root slot are inspected.

4. **Replace the incoming link to the selected node.**

   The routine reads the header-like object’s address from the container at offset `0x10`, then inspects the root slot at offset `0x04` in that object.

   If the root slot equals the selected-node address, it overwrites the root slot with the promoted-node address.

   Otherwise, it reads the selected node’s parent field again. It reads that parent’s left-child field and compares it with the selected-node address:

   - If they are equal, it writes the promoted-node address into the parent’s left-child field.
   - Otherwise, it writes the promoted-node address into the parent’s right-child field.

   The latter case does not verify that the parent’s right-child field previously named the selected node.

5. **Complete the new parent/child relationship.**

   The routine writes the selected-node address into the promoted node’s left-child field.

   Finally, it writes the promoted-node address into the selected node’s parent field.

   The routine then returns without a value.

### Result for a well-formed, stable tree

When the input links are consistent and the relevant fields do not overlap unexpectedly, the resulting relationships are:

- The promoted node occupies the selected node’s former position.
- The promoted node’s parent is the selected node’s former parent.
- The selected node becomes the promoted node’s left child.
- The selected node’s parent becomes the promoted node.
- The transferred subtree becomes the selected node’s right child.
- A non-null transferred subtree has its parent changed to the selected node.
- The incoming root or parent-child link now identifies the promoted node.

The selected node’s left-child field and the promoted node’s right-child field are not explicitly written. Neither are payload fields or any balancing metadata.

This is a local transformation. The routine does not traverse ancestors or descendants beyond the fields described above.

### Root selection and malformed links

Root handling is determined solely by equality between the root slot and the selected-node address. The selected node’s parent value is not used to decide whether it is the root.

For a non-root node, only the old parent’s left-child link is tested. A mismatch selects the right-child write unconditionally. Consequently, malformed input can cause an unrelated right-child link to be overwritten.

The routine also copies the selected node’s old parent value into the promoted node even on the root path. It does not normalize a root parent to zero or to any particular sentinel. Any root-parent convention must already be represented by the input.

## Side effects

All established effects are direct memory reads and writes through the supplied addresses and their linked objects.

With valid, stable, non-overlapping fields, normal completion performs:

- **Five four-byte writes** when the transferred subtree is null.
- **Six four-byte writes** when the transferred subtree is non-null.

Those writes affect:

1. The selected node’s right-child field.
2. Conditionally, the transferred subtree’s parent field.
3. The promoted node’s parent field.
4. Exactly one incoming-link slot: the root slot, the old parent’s left-child field, or the old parent’s right-child field.
5. The promoted node’s left-child field.
6. The selected node’s parent field.

The container’s field at offset `0x10` is read, not explicitly written.

The operation is not transactional. Several mutations precede the root-slot lookup and incoming-link update. An invalid later access can therefore occur after earlier fields have already changed. No rollback, explicit error result, or recovery path is present.

Intermediate states do not necessarily satisfy the final parent/child relationships. The evidence supplies no synchronization protocol, atomic rotation guarantee, or protection for concurrent observers. The repeated reads also mean that concurrent mutation cannot safely be modeled as operating on one initial snapshot.

The routine does not explicitly allocate or release memory, invoke destructors, adjust reference counts, or establish ownership transfer. It rearranges stored addresses. The caller remains responsible for object lifetimes, access permissions, and any surrounding ownership discipline.

The decision to write P’s right-child field depends on the left-child comparison, not on a separate verification of P’s right-child value.
