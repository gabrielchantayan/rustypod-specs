# F-129dd09ab861

## Purpose

F-129dd09ab861 checks the bounds of a count-prefixed sequence of variable-length items and advances a caller-supplied cursor across that sequence.

Each item has a two-byte header followed by a payload. The first header byte supplies the payload length. This function does not inspect the second header byte or any payload byte. Its established behavior is therefore structural traversal, not validation of item contents.

The function returns a 32-bit status and writes a cursor value back to the caller on both success and handled bounds failure. A bounds failure also invokes diagnostic dependency F-4457a9a44a68.

The apparent intent is to skip an extra-items section while rejecting truncated encodings. That interpretation is inferred; the observable contract below does not depend on a particular enclosing format.

## Interface

### Inputs

1. **Cursor cell**

   A pointer to a caller-owned cell containing the current input address. The supplied representation reads and writes this cell as one 32-bit word and interprets its contents as a byte pointer.

   The cell must be readable at entry and writable when the function completes. Its contents are not checked for nullness or general address validity.

2. **Exclusive limit**

   A byte pointer identifying the first address beyond the available input.

   Bounds checks permit a required region to end exactly at this address. They reject a required region whose endpoint exceeds it.

### Encoded layout

At the initial cursor:

| Component | Width | Meaning to this function |
|---|---:|---|
| Item count | 1 byte | Unsigned number of items to traverse |
| Item header, repeated for each item | 2 bytes | First byte is an unsigned payload length; second byte is not read |
| Item payload, after each header | Length specified by that header | Skipped without being read |

The item count and each payload length range from 0 through 255. The count is widened to an unsigned 32-bit loop counter. It is not interpreted as signed.

No alignment or padding is introduced between components.

### Outputs

The return value is a 32-bit status:

- **0:** The count byte and all declared items fit within the supplied limit.
- **8:** A required count byte, item header, or item payload fails a bounds check, provided the diagnostic dependency returns normally.

The cursor cell is updated as described in **Behavior**. An error does not generally preserve the entry cursor.

### Preconditions and address model

The contract assumes:

- The cursor cell is a valid object for the initial 32-bit read and final 32-bit write.
- Input bytes actually read by this function are accessible.
- Cursor and limit addresses support meaningful ordering and distance calculations over the intended input region.
- Pointer additions used in the checks do not wrap or otherwise leave the valid address model.

The function does not establish these conditions. In particular, it does not turn arbitrary invalid pointers into status 8. Behavior for address overflow, unrelated address regions, inaccessible memory, or a non-writable cursor cell is not established by the supplied material.

## Behavior

### Entry and count handling

The first observable data access is a read of the cursor cell. This obtains the initial input address.

Before reading the count byte, the function checks whether the address one byte after the initial cursor lies beyond the exclusive limit.

- If that endpoint exceeds the limit, the function takes the bounds-failure path. The cursor selected for final writeback is the original input address.
- Otherwise, the function reads exactly one count byte and begins traversal immediately after it.

Thus, an empty available region is rejected without reading a count byte. A region containing exactly the count byte is sufficient when the count is zero.

For a zero count, the function succeeds and advances the cursor by one byte. It does not examine any subsequent bytes.

### Item traversal

Items are processed in their encoded order. The declared count determines how many items must be traversed; encountering the limit does not independently terminate a nonempty sequence successfully.

For each item:

1. The function checks that the complete two-byte header fits before or at the exclusive limit.
2. Only when that check passes, it reads the first header byte as an unsigned payload length.
3. It checks that the payload endpoint, measured from immediately after the two-byte header, fits before or at the limit.
4. When the payload fits, the next item starts at that endpoint.

The second header byte must be within the available region, but this function does not read its value. Payload bytes likewise must lie within the declared bounds, but their contents are not read.

A zero-length payload is valid. It still requires a complete two-byte header, and the next item begins immediately after that header.

A header or payload ending exactly at the limit is accepted. If more items remain after such an endpoint, the following item fails its header check.

### Successful completion

After all declared items have been traversed, the function writes the address immediately following the final payload into the cursor cell and returns 0.

The function does not require that this address equal the exclusive limit. Trailing bytes are accepted and remain unconsumed.

Under the non-wrapping address preconditions, total advancement on success is:

\[
1 + 2N + \sum_{i=1}^{N} L_i
\]

where \(N\) is the unsigned count and each \(L_i\) is an unsigned payload length.

The maximum encoded extent represented by these fields is 65,536 bytes: one count byte plus 255 items, each with a two-byte header and a 255-byte payload. This is a consequence of the field widths, not an additional explicit size check.

### Bounds failure and cursor position

The final cursor depends on which check fails:

| Failure | Cursor selected for final writeback |
|---|---|
| Count byte does not fit | Original input address |
| Current item’s two-byte header does not fit | Start of that item’s header |
| Header fits, but its declared payload does not fit | Start of that item’s payload, immediately after the header |

Consequently, a payload failure consumes the header for purposes of cursor writeback, even though the payload is rejected. A header failure leaves the cursor at that header’s start, after any previously accepted items.

There is no rollback to the beginning of the sequence and no writeback of the rejected payload’s endpoint.

On any of these failures, the function invokes F-4457a9a44a68 with a fixed diagnostic argument. If that call returns normally, the function selects status 8, writes the selected cursor, and returns.

## Side effects

### Reads and their order

Excluding accesses performed internally by the diagnostic dependency, the established input reads occur in this order:

1. One 32-bit read from the cursor cell.
2. One count-byte read, only after the count-byte bounds check passes.
3. One length-byte read for each item whose complete two-byte header passes its bounds check.

No header length is read for an item whose header is truncated. No count byte is read when the initial one-byte region fails its check.

The function does not read second header bytes or payload contents.

### Writes and their order

On a normally completing invocation, the function performs one final 32-bit write to the cursor cell. It does not update that cell incrementally while traversing items.

For a handled bounds failure, the diagnostic call precedes this final write. Therefore:

- In the absence of independent mutation, the cursor cell still contains its entry value when the diagnostic call begins.
- The cursor cell is not used as the live traversal position.
- If the diagnostic dependency changes the cursor cell and then returns, the final write replaces that change with the cursor selected by this function.

There are no direct writes to the encoded input through the traversal pointers. However, if the cursor cell aliases the encoded region, its final write can modify that region. No aliasing restriction or protective copy is established.

### Ownership and external state

The function contains no explicit allocation, deallocation, or transfer of ownership. It uses caller-provided addresses for traversal and cursor writeback.
