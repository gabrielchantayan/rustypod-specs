# F-d205b6619363

## Purpose

F-d205b6619363 invokes F-704f99fd5e22 repeatedly until that dependency returns a nonzero 32-bit result. Before every invocation, it initializes two distinct 32-bit work slots from a value captured from global storage. Each invocation also receives the original context input and a 32-bit field captured from that context.

After the first nonzero dependency result, the function returns a 64-bit value assembled from two components:

- Bits 63–32 contain the final 32-bit contents of a separate invocation-local slot.
- Bits 31–0 contain the 32-bit address representation of that same slot.

The return-related slot is initialized to zero before the loop. The function body contains no explicit subsequent write to it, and its address is not directly passed to the dependency. Nevertheless, the unavailable dependency contract does not establish that this storage remains unchanged. A zero upper half is therefore conditional on preservation of the slot, not an unconditional output guarantee.

The observable control structure is “repeat while the dependency returns zero.” Describing this as retrying an operation is an inference about intent. The evidence does not identify zero as failure, nonzero as success, or the returned address representation as a usable persistent pointer.

## Behavior

### Entry sequence

The visible entry operations occur in this order:

1. Read the 32-bit global initialization source.
2. Write zero into the separate 32-bit return-related slot.
3. Read the 32-bit context field at byte offset 720.
4. Enter the attempt loop.

An invalid context-field access may prevent the first dependency call. The function contains no explicit validation or recovery for that access.

### Work-slot initialization

Before every dependency invocation, the function writes the captured global value into both work slots.

The visible write order is significant:

1. Initialize the work slot supplied as the fourth argument.
2. Initialize the work slot supplied as the third argument.
3. Invoke F-704f99fd5e22.

The two arguments point to distinct 32-bit locations. At the caller’s handoff to the dependency, both slots have been initialized with the same captured bit pattern.

After the dependency returns, this function does not directly read either work slot. The dependency may have used or modified their contents, but those contents are not selected as the caller’s output or loop condition.

If another attempt occurs, the caller overwrites both work slots again before invoking the dependency. Thus, changes made through these work-slot pointers are not carried into the next attempt as the caller’s selected initial values.

### Captured inputs across attempts

The supplied body contains no additional global-source read or context-field read during the loop. It reuses the captured initialization value and captured field argument.

Consequently, changing the original global source or the context field does not, by itself, make this caller select new values on the next attempt. Such changes are not rolled back, however. The dependency may observe them through its own accesses.

This distinction concerns explicit caller behavior. It is not a general guarantee that the dependency preserves globals, the context, or all invocation-local storage.

### Loop decision

The dependency is invoked at least once on any ordinary execution that reaches the loop.

After each ordinary dependency return:

- A 32-bit zero result causes another attempt.
- Any nonzero 32-bit result ends the loop.

The test does not distinguish positive values from negative values. A result whose only set bit is bit 31 terminates the loop.

There is no visible attempt limit, counter-based exit, timeout, delay, backoff, cancellation check, or alternate normal exit.

If every dependency invocation returns zero, execution continues through the reset-and-call cycle indefinitely, absent an abnormal interruption. If an invocation never returns, this function cannot reach another loop decision or normal completion.

### Completion and return-slot preservation

After the first nonzero dependency result, the function constructs the 64-bit return value using the return-related slot’s contents at that time and that slot’s address representation.

The initialization to zero is not a substitute for the final contents used by the return expression. Both of the following facts must be retained:

- **Established:** the caller initializes the slot to zero and contains no explicit later write to it.
- **Unresolved:** the dependency contract does not establish preservation of that storage throughout its calls.

Neither work-slot argument directly points to the return-related slot. This limits the visible pointer exposure but does not prove an unrestricted noninterference guarantee. Conversely, the evidence does not demonstrate that the dependency actually changes the slot.
