# F-45138fcd9aa3

## Purpose

F-45138fcd9aa3 performs a local rearrangement of linked records. Under the conventional interpretation of the observed fields as parent, left-child, and right-child links, the operation is a **right rotation around the supplied pivot**.

The established behavior is a sequence of 32-bit reads and writes. The tree interpretation is inferred from the relationships between those accesses; it is not independently established by type definitions, callers, or runtime observations.

For a valid, non-aliased tree neighborhood, the operation:

- Promotes the pivot’s left child into the pivot’s former position.
- Transfers the promoted record’s former right subtree to the pivot’s left side.
- Makes the pivot the promoted record’s right child.
- Repairs the affected parent links.
- Replaces either the external root link or the former parent’s selected child link.

No ordering keys, payload values, balance metadata, or allocation state are inspected.

## Interface

### Inputs

The function accepts two machine-level arguments represented as 32-bit integer values in the supplied evidence:

| Argument | Role | Observed use |
|---|---|---|
| Control address | Address of a control structure | Supplies an indirect reference used to locate the root-link cell. |
| Pivot address | Address of the record being rearranged | Supplies the record’s parent and child links and identifies the record being replaced in its former position. |

These arguments are used as addresses, not as ordinary numeric quantities. Their signed declarations do not establish signed semantics for stored link values.

### Observed layouts

All accessed fields are four bytes wide. Offsets below are byte offsets.

**Control structure**

| Offset | Meaning supported by access pattern |
|---|---|
| +16 | Address of a separate root-holder record. |

**Root-holder record**

| Offset | Meaning supported by access pattern |
|---|---|
| +4 | Root link, compared with the pivot and conditionally replaced. |

**Linked record**

| Offset | Inferred role |
|---|---|
| +4 | Parent link. |
| +8 | Left-child link. |
| +12 | Right-child link. |

Only these fields are established. Record sizes, fields at other offsets, alignment guarantees, byte order, and whether the root holder is also usable as an ordinary linked record are unknown.

The promoted record is selected by reading the pivot’s +8 field. A zero value is explicitly recognized only when checking the promoted record’s +12 field; that check controls whether a transferred child receives a parent-link update.

### Output

The function has no explicit return value.

Its result is observable through memory mutations. No status value communicates success, invalid input, or partial completion.

### Preconditions for the intended rotation

The following conditions are needed to interpret the operation as a valid tree rotation:

- The control address identifies readable storage containing a valid root-holder address at +16.
- The root-holder’s +4 field is readable and, when the pivot is the root, writable.
- The pivot is a valid writable linked record.
- The pivot’s +8 link identifies a valid, nonzero, writable promoted record.
- A nonzero right-child link of the promoted record identifies storage with a writable parent field.
- If the root link does not equal the pivot, the pivot’s parent link identifies a valid parent record.
- In that non-root case, the pivot is actually one of that parent’s children.
- Relevant records and link cells do not overlap in ways that change the intended interpretation of the ordered accesses.
- Relevant links remain stable during the operation, apart from this function’s own writes.

These conditions are not validated. Violating them does not produce a defined rejection response.

## Behavior

### Terminology

The following descriptive roles are used:

- **Pivot:** the record supplied by the second argument.
- **Promoted record:** the record selected from the pivot’s left-child field.
- **Transferred subtree:** the record, if any, reached through the promoted record’s right-child field.
- **Former parent:** the record identified by the pivot’s parent field in an ordinary, stable tree.
- **Root link:** the four-byte cell at +4 in the root-holder record obtained through the control structure.

These are explanatory roles, not additional stored state.

### Ordered accesses and mutations

The established access order is significant. The function does not collect a complete snapshot before starting its writes.

1. **Select the promoted record.**  
   Read the pivot’s +8 field once. Retain that value as the promoted record’s address for the remaining operation.

2. **Replace the pivot’s left-child link.**  
   Read the promoted record’s +12 field and write that four-byte value into the pivot’s +8 field.

3. **Conditionally repair the transferred subtree’s parent.**  
   Read the promoted record’s +12 field again and compare it with zero.

   If that read is nonzero, read the same field once more to obtain the destination record address, then write the pivot address into that record’s +4 field.

   Consequently, the value copied into the pivot’s left-child field, the value tested for zero, and the address used for the parent-link write come from separate reads. They coincide for stable, non-overlapping ordinary memory, but the function does not enforce their equality.

4. **Assign the promoted record’s parent.**  
   Read the pivot’s +4 field and copy its four-byte value into the promoted record’s +4 field.

5. **Locate and inspect the root link.**  
   Read the control structure’s +16 field to obtain the root-holder address. Read that holder’s +4 field and compare it with the pivot address.

   This root lookup occurs after the earlier child-link and parent-link mutations.

6. **Reconnect the promoted record at the pivot’s former position.**

   - If the inspected root link equals the pivot address, write the promoted record’s address into that root-link cell.
   - Otherwise, read the pivot’s +4 field again to select a parent record. Read that parent’s +12 field.
     - If it equals the pivot address, replace that +12 field with the promoted record’s address.
     - Otherwise, replace that parent’s +8 field with the promoted record’s address.

   The non-root path does not check whether the parent’s +8 field actually contains the pivot. Failure of the right-child comparison is sufficient to select the left-child write.

7. **Attach the pivot beneath the promoted record.**  
   Write the pivot address into the promoted record’s +12 field.

8. **Finish the pivot’s parent update.**  
   Write the promoted record’s address into the pivot’s +4 field.

The function then returns without an explicit result.

### Result for an ordinary valid tree

Assuming stable, distinct records and a consistent tree:

| Relationship | Before | After |
|---|---|---|
| Pivot’s left child | Promoted record | Transferred subtree, possibly zero |
| Promoted record’s right child | Transferred subtree | Pivot |
| Pivot’s parent | Former parent or root-associated parent value | Promoted record |
| Promoted record’s parent | Pivot | Pivot’s former parent value |
| Transferred subtree’s parent, when present | Promoted record | Pivot |
| External link formerly naming the pivot | Pivot | Promoted record |

The pivot’s right-child field and the promoted record’s left-child field are not directly written. Under the same assumptions, their subtrees remain attached as before.

The operation does not clear the promoted record’s parent when making it the root. Instead, it copies the pivot’s existing parent value. Whether that value should be zero, a sentinel, or another convention is not established.

### Widths and address arithmetic

Each link read and write transfers exactly 32 bits. Root and child selection use equality comparisons on those values; there are no ordering comparisons.

The observed address calculations add fixed byte offsets of 4, 8, 12, or 16. There are no counters, multiplicative sizes, or variable-length copies.

The supplied evidence does not define behavior for address overflow, misalignment, inaccessible addresses, or address representations wider than the observed fields. This contract does not assume safe wrapping or implicit widening.

## Side effects

### Memory changes

For a valid rotation with distinct storage, the function performs:

- Five unconditional four-byte writes:
  - Pivot’s left-child link.
  - Promoted record’s parent link.
  - One root or former-parent child link.
  - Promoted record’s right-child link.
  - Pivot’s parent link.
- One additional four-byte write when the promoted record’s right-child check is nonzero:
  - Transferred subtree’s parent link.

Thus, an ordinary execution performs five or six stores. The root-versus-non-root decision changes the destination of one store, not the number of stores.

These counts describe executed stores, not necessarily distinct memory cells when inputs alias.

### Ownership and lifetime

It does not establish that any record becomes newly owned, unowned, or eligible for destruction. Such policies would require an external contract.

### Partial updates and concurrency

No synchronization, locking, or atomic multi-field commit is visible. Intermediate states exist in which child and parent links have not yet been made mutually consistent. Concurrent traversal or mutation requires an external protocol not supplied here.

### Other effects

There are no visible calls, I/O operations, logging operations, callbacks, or explicit accesses to named global objects. This does not prove that argument-reachable storage is not shared or global.

## Acceptance examples

These are conditional acceptance examples derived from the static accesses. They are not executed tests.

### Root rotation with a transferred subtree

Given distinct valid records **Pivot**, **Promoted**, and **Transfer**, assume:

- The root link names Pivot.
- Pivot’s left child is Promoted.
- Promoted’s right child is Transfer.
- Pivot’s parent field contains a root-parent value.
- Transfer’s parent is Promoted.

Expected final relationships:

- The root link names Promoted.
- Promoted’s parent contains the pivot’s former root-parent value.
- Promoted’s right child is Pivot.
- Pivot’s parent is Promoted.
- Pivot’s left child is Transfer.
- Transfer’s parent is Pivot.

The root-parent value is copied, not normalized.

### Non-root pivot on its parent’s right side

Given a valid former parent whose right-child link names Pivot, and a root link that does not name Pivot:

- The former parent’s right-child link becomes Promoted.
- Its left-child link is not directly modified.
- Promoted’s parent becomes the pivot’s former parent value.
- The remaining local links change as described for the rotation.

### Non-root pivot on its parent’s left side

Given a valid former parent whose left-child link names Pivot and whose right-child link does not:

- The former parent’s left-child link becomes Promoted.
- Its right-child link is not modified by the reconnecting store.

The function selects this branch because the right-child comparison fails; it does not verify the left-child relationship.

### No transferred subtree

Given stable links and a zero right-child field in Promoted:

- Pivot’s left-child field becomes zero.
- No transferred-child parent-link write occurs.
- The root or former-parent link is still updated.
- Promoted’s right child becomes Pivot.
- Pivot’s parent becomes Promoted.

No record at address zero is accessed for the transferred-child repair.

### Inconsistent former-parent relationship

Given otherwise accessible, non-overlapping storage, suppose the root link does not name Pivot and neither child field of the selected parent names Pivot.

Expected observed behavior:

- The parent’s left-child field is overwritten with Promoted.
- No relationship error is reported.
- The earlier and subsequent link mutations still occur.

This is evidence of missing validation, not acceptance of the structure as a valid tree.

### Missing promoted record

If the pivot’s left-child field is zero, the function still attempts to read a four-byte field at offset +12 from that value.

There is no early return for this case. A successful no-op, clean error result, or unchanged structure is not an acceptance requirement. The resulting machine behavior depends on the execution environment.
