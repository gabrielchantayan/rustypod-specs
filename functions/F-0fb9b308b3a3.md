# F-0fb9b308b3a3

## Purpose

F-0fb9b308b3a3 conditionally removes a selected node from a linked structure, performs byte-color-dependent repair, prepends the removed node to a separate list, decrements a 32-bit count, and writes a 32-bit result to caller-provided storage.

The structure and repair cases are consistent with red–black-tree deletion using a header and cached extrema. That interpretation is inferred intent. The established contract consists of the accesses, branches, calls, and state changes described below; it does not establish full tree-invariant preservation.

Removal does not itself destroy or release the node. The function visibly reuses the removed node’s right-link field as a list link. Dependency behavior, including ownership effects, remains unknown.

## Interface

The function accepts three inputs and has no direct return value.

| Input | Representation | Established role |
|---|---|---|
| Result destination | Address of writable 32-bit storage | Receives the final result word. |
| Container | Address carried in the supplied 32-bit representation | Locates the detached-list head, header pointer, and count. |
| Selection storage | Address of readable 32-bit storage | Supplies an initial word and, after dependency calls, the node address used for removal. |

All observed pointer-bearing fields occupy four bytes. This contract describes the supplied 32-bit representation, not a native 64-bit layout. Byte order and alignment requirements are not independently established.

Completing execution requires all reached accesses to address suitable storage, all traversals to terminate, and dependencies to return with subsequent accesses still usable. The function does not detect cycles or bound traversal length.

## Behavior

### Initial gate and result preparation

The function first reads the 32-bit selection word into a local result slot, then reads the container’s header word into a separate local slot. It calls F-4cec57b703f5 with the addresses of those two slots.

If the returned integer is nonzero, the function rereads container +16, replaces the local result with that word, writes it to the result destination, and returns. None of this function’s structural removal, detached-list insertion, or count-decrement operations executes on that path. Effects performed by the dependency are not excluded.

If the return is zero, F-8f8f82c1972b receives the address of the local result slot. The function then rereads selection storage to obtain the selected node.

Thus:

- Structural selection uses the later selection-storage read, not necessarily the original word.
- Either dependency can potentially modify the local result through its supplied address.
- On the zero-gate path, subsequent visible structural processing does not deliberately replace that local result.
- The semantic meaning of the result word is unknown.

### Choosing the structural case

The selected node’s left link is examined first, followed by its right link as required.

- With neither child present, the function uses leaf removal.
- With exactly one child present, that child becomes the replacement.
- With both children present, the function follows left links from the right child to select the leftmost node in that subtree. This distinct successor’s right child becomes the replacement for its former position.

The successor search has no cycle detection. The selected node remains the node destined for the detached list; the successor is moved structurally rather than copied as payload.

### Leaf removal

The initial repair focus is the selected node’s parent.

If that parent equals the header address read for the comparison, the visible stores occur in this order:

1. Header +12 receives the parent/header address.
2. Header +8 receives the same address.
3. Header +4 receives zero.

Header storage is reached through reads of container +16. Under stable, nonoverlapping storage, this represents an empty structure with both cached extrema referring to the header.

Otherwise, the function reads the parent’s left link. Equality with the selected node chooses the left side; inequality chooses the right side without separately checking the right link.

The chosen child link is cleared using four separate byte stores in increasing address order: offsets +8 through +11 for the left side, or +12 through +15 for the right side.

The same side decision chooses the header cache to inspect: +8 for left, +12 for right. If that cache equals the selected node, it receives the parent address. The side decision is retained rather than recomputed after clearing the link.

### Replacement by the sole child

The replacement is nonnull in this case.

First, the selected node’s parent word is written into the replacement’s parent field. The selected node’s position is then redirected:

- If the current header root equals the selected node, the root receives the replacement.
- Otherwise, the selected node’s parent left link is compared with the selected node. Equality selects that link; inequality selects the parent’s right link.

The first-extremum cache is processed before the second-extremum cache.

If header +8 equals the selected node, its new value is:

- The selected node’s parent when the selected node’s right link is null.
- Otherwise, the leftmost node reachable from the replacement.

If header +12 equals the selected node, its new value is:

- The selected node’s parent when the selected node’s left link is null.
- Otherwise, the rightmost node reachable from the replacement.

These searches follow the applicable child links until null. The replacement becomes the repair focus, while the original selected node remains the detached-node identity.

### Replacement by a distinct successor

For a selected node with two children, the observable structural sequence is:

1. The selected node’s left child receives the successor as parent.
2. The successor’s left link receives the selected node’s left link.
3. The successor’s former position is processed.
4. The root or selected parent’s child link is redirected to the successor.
5. The successor’s parent receives the selected node’s parent word.
6. The successor’s original color byte is saved; the successor receives the selected node’s color; the selected node receives the saved color.

If the successor is the selected node’s immediate right child, a nonnull successor right child receives the successor as parent.

For a deeper successor:

- A nonnull successor right child receives the successor’s former parent.
- The former parent’s left link receives that child, including null.
- The successor’s right link receives the selected node’s right link.
- That right-subtree root receives the successor as parent.

The repair focus is the successor’s former right child when nonnull, otherwise the moved successor itself. No temporary null-leaf object is created.

This branch contains no explicit cached-extremum update. The original selected node is ultimately listed as detached, and its color at repair entry is the successor’s original color.

### Repair entry and iteration

After structural removal, the function rereads the header address. Repair is skipped if the focus equals that header. Otherwise, repair is entered only if the detached node’s current color byte is nonzero.

An entered repair phase checks the current header root before checking the focus color. If the focus equals that root, or its color is not exactly one, repair exits to final focus recoloring.

Otherwise, the focus parent is read. Equality between the focus and the parent’s left link selects the left-focus orientation; inequality selects the opposite orientation.

For the descriptions below:

| Orientation | Sibling | Near child | Far child |
|---|---|---|---|
| Focus is parent’s left child | Parent’s right child | Sibling’s left child | Sibling’s right child |
| Other orientation | Parent’s left child | Sibling’s right child | Sibling’s left child |

Zero and exactly one have distinct operational meanings. Their identification as red and black is inferred; arbitrary nonzero bytes are not normalized to one.

### Missing sibling and zero-colored sibling

If the sibling is initially null, the function writes zero to the focus color, advances the focus to the parent value already read, and repeats the iteration checks.

For a nonnull sibling with color zero, the function:

1. Writes one to the sibling.
2. Writes zero through the focus’s parent link to the parent color.
3. Calls the orientation’s transformation dependency with the container address and a word read from the focus’s parent field.
4. Rereads the focus’s parent field.
5. Reloads the sibling from that parent.

If the reloaded sibling is null, the function writes zero to the focus color and advances the focus to the reread parent. It then repeats the iteration checks.

The transformation call is F-b82c2922b45c for a left focus and F-9966ca29b392 for the opposite orientation.

### Propagation, preparation, and finishing

For a nonnull sibling surviving the preceding handling, the near-child pointer is captured first. Its color is inspected if nonnull.

When the near child is null or exactly one, the far-child pointer and, if present, its color are inspected. If the far child is also null or exactly one, the propagation case applies:

- The sibling receives color zero.
- The focus advances through its current parent field.
- Iteration checks resume.

If propagation does not apply, the far-child pointer and color are inspected for the preparation decision. This is a further inspection where the far child was already examined during the propagation decision.

**Preparation occurs exactly when the far child is null or its color equals one.** Otherwise, execution proceeds directly to finishing.

Preparation has the following ordered effects:

1. The sibling’s near-link field is reread as a nonnull guard.
2. If that guard is nonzero, one is written through the previously captured near-child pointer—not through a newly captured pointer.
3. The sibling receives color zero.
4. The preparation dependency is called with only the container address visibly supplied.
5. The focus’s current parent is reread, and the sibling is reloaded from it.
6. A null reloaded sibling exits directly to final focus recoloring.

For a left focus, preparation calls F-9966ca29b392 and reloads the parent’s right link. For the opposite orientation, it calls F-b82c2922b45c and reloads the parent’s left link.

When finishing is reached:

1. The sibling receives the color read through the focus’s current parent link.
2. The parent reached through that link receives one.
3. The sibling’s far child receives one if nonnull.
4. The finishing dependency is called with the container address and a word read from the focus’s parent field.
5. Repair exits to final focus recoloring rather than starting another iteration.

Finishing uses F-b82c2922b45c for a left focus and F-9966ca29b392 otherwise.

Every normal exit from an entered repair phase writes one to the final focus’s color. That store does not occur when repair was skipped entirely.

### Detached list, count, and output

After structural processing and any repair:

1. Container +4 is read.
2. That old list head is written to the detached node’s +12 field.
3. The detached node address is written to container +4.
4. The 32-bit count at container +20 is read, decremented, and written back.
5. The local result word is written to the result destination.

The count has no zero check. At the 32-bit representation level, decrementing zero yields `0xffffffff`. Source-language signed-overflow behavior is not established by the supplied representation.

## Side effects

Direct writes can affect structural links, cached extrema, node colors, the detached-list head, count storage, and result storage.

Removal does not generally clear the detached node’s parent or left link. Its right link is overwritten with the prior detached-list head. In the successor case, its color is exchanged before repair.

No explicit allocation, release, payload destruction, or payload copying appears in this function. Retention on a separate list suggests later reuse or reclamation, but ownership and lifetime policy are unknown.

There is no rollback or explicit synchronization. A failed access or nonreturning dependency can leave earlier writes visible. The four byte stores clearing a leaf link are not represented as one indivisible 32-bit store.

Dependencies may alter globals, links, colors, ownership, or storage lifetime. The contract does not assume preservation beyond the conditions explicitly attached to completing execution.

## Acceptance examples

These are conditional static examples, not executed tests. They assume suitable live storage and no interfering effects except those stated.

1. **Nonzero gate.** If F-4cec57b703f5 returns nonzero, output receives container +16 reread after that call. This function performs no subsequent removal, list insertion, or decrement.

2. **Only node.** If the selected node has no children and its parent equals the stable header, header stores occur in order +12, +8, +4, producing self-referencing extrema and a null root. Repair is skipped; list insertion and decrement follow.

3. **Left leaf.** A non-header parent whose left link equals the selected leaf has that link cleared through four increasing-address byte stores. A matching first-extremum cache becomes the parent.

4. **Sole right child.** The child receives the selected node’s parent and replaces it structurally. A matching first-extremum cache becomes the leftmost node reachable from that child.

5. **Deeper successor.** The successor’s former parent left link receives its former right child. The successor moves into the selected position, colors are exchanged, and the original selected node is listed as detached.

6. **Propagation.** During entered repair, a nonnull sibling with both children null or exactly one receives zero; focus advances to its current parent. Neither preparation nor finishing executes in that iteration.

7. **Left-focus preparation.** After propagation is excluded, a null or exactly-one far/right child requires preparation. The guarded write uses the captured near/left pointer, the sibling becomes zero, and F-9966ca29b392 visibly receives only the container.

8. **Direct finishing.** After propagation is excluded, a nonnull far child whose color is not one bypasses preparation. Finishing recolors and calls the orientation’s finishing dependency with container and the freshly read parent word.

9. **Preparation reload is null.** If the preparation dependency leaves the reloaded sibling null, finishing is skipped. The current focus receives one before list insertion.

10. **Zero-colored sibling.** For a left focus, the sibling becomes one, the parent becomes zero, and F-b82c2922b45c receives container and the parent-field word. The opposite orientation uses F-9966ca29b392 with the same visible argument shape.

11. **Zero count.** If removal completes with count initially zero, list insertion still precedes writing the decremented 32-bit count. No underflow error is reported.

12. **Changed result slot.** On the zero-gate path, dependency modification of the local result slot affects final output. Structural selection still uses the later selection-storage read.
