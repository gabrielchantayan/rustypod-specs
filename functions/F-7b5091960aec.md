# F-7b5091960aec

## Purpose

F-7b5091960aec dispatches a rectangular fill operation according to a format selector stored in a caller-supplied context.

Established behavior consists of:

- A signed comparison of two rectangle endpoints against context limits.
- Additional parity restrictions for formats 0 and 1.
- One, two, or three ordered calls to a fill dependency.
- Format-specific address calculations, pattern widths, rectangle dimensions, and stride arguments.

The apparent intent is to fill either a packed surface or related full-resolution and reduced-resolution planes. That interpretation is inferred from the addressing and dimensions; the actual storage formats and the dependencies’ memory effects are unknown.

The function has no explicit result value. Rejected requests return without calling either dependency. There is no explicit error report.

## Interface

### Inputs

The visible interface has four arguments:

| Argument | Established use |
|---|---|
| Context | A 32-bit address identifying a structure containing a format byte, two limit words, and a stride word. Also passed to dependencies. |
| Pattern storage | An address from which the function reads a 32-bit word and, for some formats, additional byte or halfword views of that storage. |
| Rectangle storage | An address identifying four consecutive 32-bit words. |
| Opaque argument | A 32-bit value forwarded to the first address-resolution call on every accepted path. |

Addresses and address arithmetic are represented as 32-bit quantities in the supplied material. No portable behavior for a wider pointer model is established.

### Context layout

Only these fields are directly accessed:

| Byte offset | Width | Use |
|---|---:|---|
| 8 | 8 bits | Format selector. Values 0–4 are handled. |
| 12 | 32 bits | Vertical endpoint limit, compared as signed. |
| 16 | 32 bits | Horizontal endpoint limit, compared as signed. |
| 20 | 32 bits | Stride-like value used in offset calculations and fill arguments. |

No meaning is established for other context bytes.

### Rectangle layout

| Byte offset | Width | Contract name |
|---|---:|---|
| 0 | 32 bits | Horizontal start, \(x_s\) |
| 4 | 32 bits | Horizontal end, \(x_e\) |
| 8 | 32 bits | Vertical start, \(y_s\) |
| 12 | 32 bits | Vertical end, \(y_e\) |

The endpoints are treated as inclusive when dimensions are calculated.

The same words participate in unsigned-width arithmetic and signed comparisons or shifts. They are not uniformly unsigned coordinates.

### Pattern layout

The function uses the following views:

- A 32-bit word at offset 0.
- A byte at offset 1 for format 0.
- A byte at offset 2 for format 0.
- A 16-bit halfword at offset 2 for format 1.

The low 8 or 16 numerical bits of the 32-bit word are also used in several paths. Relating those numerical portions to particular memory bytes requires the target byte order, which is not independently established here.

A caller must provide readable storage sufficient for the actual accesses. In particular, a one-byte fill does not imply that a one-byte pattern allocation is sufficient: its initial pattern value is obtained through a 32-bit read.

### Result and ownership

There is no explicit return value or status channel.

No allocation, release, ownership transfer, or direct store through an input pointer is visible in this function. Dependencies receive the context, and the first address-resolution call also receives both storage pointers. Their ownership and mutation behavior are unknown.

## Behavior

### 1. Endpoint rejection

The function first reads the horizontal limit from context offset 16, then the horizontal end from rectangle offset 4.

It proceeds to the vertical check only if:

\[
\operatorname{signed32}(x_e) < \operatorname{signed32}(\text{horizontal limit}).
\]

Otherwise it returns immediately. In that case, no vertical endpoint, vertical limit, format selector, pattern data, or dependency is accessed by the visible function.

If the horizontal check passes, it reads the vertical end and the context limit at offset 12. It returns unless:

\[
\operatorname{signed32}(y_e) < \operatorname{signed32}(\text{vertical limit}).
\]

Consequences:

- Equality with either limit is rejected.
- These are signed comparisons, including for words with their high bit set.
- Neither start coordinate is checked against zero.
- Neither start coordinate is checked against its endpoint.
- No clipping occurs.

The subtraction and signed-overflow tests shown in the supplied material implement these signed comparisons. A replacement must not simplify them into unsigned comparisons or a test of the wrapped subtraction’s sign alone.

### 2. Dimension and initial-offset calculation

After both endpoint checks pass, the function reads the horizontal and vertical starts and forms:

\[
W = x_e - x_s + 1,
\qquad
H = y_e - y_s + 1,
\]

and:

\[
O = y_s S_0 + x_s,
\]

where \(S_0\) is the stride word read from context offset 20 at this stage.

These are 32-bit calculations. Intermediate addition, subtraction, and multiplication retain the resulting 32-bit bit pattern; there is no visible overflow check or saturation.

The initial dimensions and offset are computed before rejection of an unsupported format. Thus an unsupported format does not avoid the earlier rectangle and stride reads.

### 3. Format selection

The format byte is first read to reject values greater than 4. A value in 0–4 reaches a further read used for dispatch.

For ordinary stable memory, both reads select the same format. Behavior when the selector changes between those reads is not fully specified by the supplied representation.

For supported formats, the function also forms:

\[
H_{1/2} = \operatorname{ASR32}(H,1),
\]

where ASR32 is a sign-preserving right shift of the 32-bit bit pattern. This is not unsigned division by two for values with bit 31 set.

### 4. Shared parity restrictions for formats 0 and 1

Formats 0 and 1 return without dependency calls unless all of these conditions hold:

- \(W\) is even.
- \(H\) is even.
- \(x_s\) is even.
- \(x_e\) is odd.
- \(y_s\) is even.
- \(y_e\) is odd.

These tests do not prove positive dimensions or ordered endpoints. Wrapped or reversed rectangles can satisfy the parity conditions.

Formats 2, 3, and 4 have no corresponding parity restrictions.

### 5. Format 0: three ordered fills

The first resolution request uses selector 0 and receives the context, cached horizontal start, cached initial offset, pattern pointer, rectangle pointer, and opaque argument.

After that request returns a 32-bit base value, the function calls the fill dependency with:

- Destination: returned base plus cached \(O\).
- Pattern: the low eight bits of a newly read 32-bit pattern word, converted through an 8-bit character type.
- Element width: 1.
- Dimensions: cached \(W\) and \(H\).
- Stride: a fresh context-offset-20 read.

The first pattern’s extension to the dependency’s argument width is not fully established. Its selected eight-bit pattern is established.

After the first fill returns, the horizontal dimension becomes:

\[
W_{1/2} = \operatorname{ASR32}(W,1).
\]

The function then rereads rectangle coordinates and stride to calculate a shared secondary offset:

\[
C =
\operatorname{ASR32}\bigl(\operatorname{wrap32}(y_s' S_1),2\bigr)
+
\operatorname{ASR32}(x_s',1),
\]

with the addition also limited to 32 bits.

This expression is significant: the product is formed before its arithmetic shift. It is not generally interchangeable with separately halving the row and stride.

The second resolution request uses selector 2. Its returned base is combined with \(C\), followed by a fill using:

- Pattern byte at offset 1, read after that resolution request.
- Element width 1.
- Dimensions \(W_{1/2}\) and cached \(H_{1/2}\).
- A newly read stride arithmetically shifted right by one.

After the second fill returns, the third resolution request uses selector 3. Its returned base is combined with the same cached \(C\), followed by a fill using:

- Pattern byte at offset 2, zero-extended.
- Element width 1.
- The same reduced dimensions.
- Another newly read stride arithmetically shifted right by one.

The secondary offset is not recomputed after the second fill.

### 6. Format 1: two ordered fills

The first resolution and fill match format 0’s first resolution and full-resolution fill.

After that fill returns, the function rereads rectangle coordinates and stride and calculates:

\[
C_1 =
\operatorname{ASR32}(y_s',1) S_1 + x_s',
\]

using 32-bit multiplication and addition.

The second resolution request uses selector 1. In addition to the context and selector, the visible call supplies a separately read vertical start shifted arithmetically right by one, followed by cached \(C_1\).

After resolution, the function reads the 16-bit pattern at byte offset 2. It then performs the second fill with:

- Destination: returned base plus cached \(C_1\).
- Pattern: that halfword, zero-extended.
- Element width: 2.
- Width: original cached \(W\), not \(W_{1/2}\).
- Height: cached \(H_{1/2}\).
- Stride: a fresh, unshifted stride read.

The different width and stride treatment from format 0 is established behavior.

### 7. Formats 2, 3, and 4: one fill

These formats each issue one initial resolution request, with the context, selector, cached horizontal start and offset, both storage pointers, and the opaque argument.

| Format | Resolution selector | Destination | Pattern | Element width |
|---|---:|---|---|---:|
| 2 | 4 | Base \(+ 2O\) | Low 16 bits of a fresh 32-bit pattern read | 2 |
| 3 | 5 | Base \(+ 4O\) | Fresh 32-bit pattern word | 4 |
| 4 | 6 | Base \(+ 2O\) | Low 16 bits of a fresh 32-bit pattern read | 2 |

All three fills receive cached \(W\), cached \(H\), and a newly read, unshifted stride.

For format 3, the visible statement order reads that final stride before reading the pattern word. For formats 2 and 4, the pattern word is read before the final stride.

Destination scaling and addition are 32-bit operations. No address-overflow detection is visible.

## Side effects

### Direct and delegated effects

The visible function directly reads memory and invokes dependencies. It contains no direct destination-memory write.

Actual fill writes, context changes, allocation, release, or other externally visible actions are delegated and unknown. The dependency names used here do not establish their implementation.

There is no check of a resolver result for null, failure, alignment, or suitability. Any returned bit pattern is used in address arithmetic. Fill results are not examined.

### Ordering and mutable state

For accepted stable inputs, the dependency sequence is:

| Format | Ordered sequence |
|---|---|
| 0 | Resolve 0, fill, resolve 2, fill, resolve 3, fill |
| 1 | Resolve 0, fill, resolve 1, fill |
| 2 | Resolve 4, fill |
| 3 | Resolve 5, fill |
| 4 | Resolve 6, fill |

Later operations do not use a complete immutable snapshot:

- Dimensions and the initial offset are cached before any dependency call.
- Pattern values are read after their corresponding resolution requests.
- Fill stride arguments are read after the corresponding resolution requests.
- Formats 0 and 1 reread rectangle coordinates and stride after their first fill.
- Format 0 retains its secondary offset across its second fill.

A dependency may therefore change data used by later operations. No preservation guarantee may be assumed.

The material establishes statement-level ordering and ordering across completed calls. It does not establish a universal evaluation order among independent argument expressions within one call.

There is no rollback path. If a later dependency fails to return normally, earlier dependency effects may already have occurred.

## Acceptance examples

These examples are conditional static expectations, not executed tests. Unless stated otherwise, assume stable readable input storage, dependencies that return normally without mutating inputs, and arithmetic values small enough to avoid wraparound.

### Format 0 with an aligned rectangle

For \(x_s=2\), \(x_e=5\), \(y_s=4\), \(y_e=7\), stride 16, and limits greater than the endpoints:

- Dimensions are 4 by 4.
- Initial offset is 66.
- Resolution selectors are 0, 2, and 3, in that order.
- The first fill uses destination base plus 66, width 4, height 4, element width 1, stride 16.
- The shared secondary offset is 17.
- The second and third fills each use their respective base plus 17, width 2, height 2, element width 1, stride 8.
- Their patterns come from byte offsets 1 and 2 respectively.

### Format 1 with the same rectangle

The first fill is the same full-resolution operation.

The secondary offset is 34. The second resolution uses selector 1 and shifted vertical start 2. The second fill uses destination base plus 34, width 4, height 2, element width 2, stride 16, and the halfword at pattern offset 2.

### Packed-format destination scaling

For \(x_s=1\), \(x_e=3\), \(y_s=2\), \(y_e=4\), stride 10, and passing limits:

- Width and height are both 3.
- Initial offset is 21.
- Formats 2 and 4 fill at their returned base plus 42 using two-byte elements.
- Format 3 fills at its returned base plus 84 using four-byte elements.
- Each receives width 3, height 3, and stride 10.

Odd dimensions and starts do not cause parity rejection on these paths.

### Rejections and non-rejections

- A horizontal endpoint equal to its limit causes immediate return without dependency calls.
- A passing horizontal endpoint followed by a vertical endpoint equal to its limit also causes return without dependency calls.
- Format 0 or 1 with an odd horizontal start is rejected even if both endpoint-limit checks pass.
- A stable format value of 5 is rejected after the initial dimension and offset calculations.
- Reversed endpoints are not independently rejected. If another explicit check does not reject the request, wrapped dimensions can reach a dependency.

### Dependency mutation

If the first resolution request changes the pattern word or stride, the first fill uses the subsequently read values, while retaining the previously calculated dimensions and initial offset.

If the first fill in format 0 changes rectangle starts or stride, those changes affect the secondary-offset calculation. They do not recompute the original dimensions.
