# F-e9681753d786

## Purpose

F-e9681753d786 locates a resource group in a binary input, selects a record using a signed index, requests a 176-byte result object, initializes three fields from that record, and invokes a dependency to complete loading.

Recognition of an MZ/NE-style container and selection of a font-resource category are **inferred intent**. The established contract consists of the signature checks, traversal rules, arithmetic, dependency calls, and observable writes described below. It does not establish general format conformance or malformed-input safety.

The function returns a 32-bit status:

- Zero after successful final loading.
- 2 for either signature mismatch or an absent or unusable matching group.
- 132 when a usable matching group exists and the requested index is at least its count.
- Dependency-provided statuses on the specified failure paths.

This contract is based on static evidence only. No runtime tests have been performed.

## Interface

### Inputs and context layout

The function receives a mutable context address and a signed 32-bit entry index.

The context is accessed as 32-bit words:

| Byte offset | Width | Direct use |
|---|---:|---|
| 0 | 32 bits | Publication of the matching group’s entry count |
| 100 | 32 bits | Allocation-related value captured on entry |
| 104 | 32 bits | Input-state address or handle captured on entry |
| 132 | 32 bits | Result-object address slot, cleared on entry and later assigned the allocation result |

The input-state value is captured first, followed by the allocation-related value. Both captures precede the initial clearing of the result slot and every dependency call. Later changes to their context slots do not replace the captured values used by this function.

The context must permit the described reads and writes. No explicit null-address, alignment, or extent checks are visible.

### Input-state layout

The function directly accesses these fields relative to the captured input-state value:

| Byte offset | Width | Direct use |
|---|---:|---|
| 32 | 32 bits | Cursor-like value, read and updated |
| 36 | 32 bits | Base-like value, read during matching-group position calculation |

“Cursor-like” and “base-like” describe usage, not an established representation. Their relationship to actual input addresses, offsets, or frame boundaries depends on unavailable dependency contracts.

The field at offset 32 is interpreted differently in different arithmetic expressions: unwanted-group skipping uses unsigned 32-bit arithmetic, while selected-record consumption uses signed 32-bit addition.

### Result-object layout

The allocation request is exactly 176 bytes. Following successful selected-record frame acquisition, the function directly writes:

| Byte offset | Width | Value |
|---|---:|---|
| 0 | 32 bits | Low 16 bits of the first record read, shifted using the alignment read’s low eight bits |
| 168 | 32 bits | Low 16 bits of the second record read, shifted using the same shift count |
| 4 | 32 bits | Low 16 bits of the alignment read, zero-extended |

These writes occur in the order shown. The remaining object bytes are not directly initialized here.

The result-slot address is read separately for each object write and again for the final-loading call. The function does not retain one object address across the intervening dependencies.

### Output and ownership conditions

The result slot is cleared before the first dependency call. A previously stored address is overwritten without a visible release operation before that clearing.

A usable matching group causes the count to be published before index rejection or allocation. Subsequent failure does not cause a direct rollback of that write, although dependencies may modify the context.

An allocation result is stored before its separately supplied status is checked. Allocation failure therefore does not imply that the result slot is zero.

No ownership-transfer, release, or complete-initialization guarantee is established. Safe object writes require the allocation dependency’s zero-status behavior to provide suitable writable storage at the address subsequently obtained from the context.

## Behavior

### Initial positioning and first header

After capturing the two context values and clearing the result slot, the function calls F-e40a3ceddab2 with the captured input state and position zero. A nonzero status is returned immediately, without shared cleanup.

Only after that positioning call succeeds does the function read the first descriptor argument from a global location. It passes that value, the captured input state, and temporary header storage to F-de70a5256fd2. A nonzero decoding status is returned immediately.

The first decoded signature is a signed 16-bit field compared against `0x5A4D`. A mismatch selects status 2 and invokes shared cleanup.

The descriptor is not established to be fixed. Its value is the value read from its global location at this decoding call, after the preceding positioning dependency has run.

### Second header and table frame

When the first signature matches, an unsigned 16-bit field decoded from the first header supplies the next position for F-e40a3ceddab2. A nonzero positioning status is returned immediately.

After successful positioning, the function reads the second descriptor argument from a separate global location and calls F-de70a5256fd2 with separate temporary header storage. A nonzero decoding status is returned immediately.

The second descriptor’s global location is distinct from the first descriptor’s location. Their stored values need not be distinct. Neither value is established as constant, and dependencies between the two reads may change either global.

The second decoded signature is a signed 16-bit field compared against `0x454E`. A mismatch selects status 2 and invokes shared cleanup.

After both signatures match:

- The candidate record position starts at zero.
- F-e40a3ceddab2 receives the sum of the first header’s unsigned 16-bit position field and a second-header unsigned 16-bit table-start displacement.
- F-d036abe1e536 then receives a length obtained by subtracting that table-start displacement from another second-header unsigned 16-bit displacement.

Each of these calls has an immediate return on nonzero status; shared cleanup is not invoked on those failures.

The positioning sum ranges from zero through 131070. The frame-length operands are converted to unsigned 32-bit values before subtraction. A reversed displacement ordering therefore wraps modulo \(2^{32}\); the function does not explicitly reject it.

Exact input-byte offsets, descriptor contents, and decoding byte order are not established.

### Group traversal

After table-frame acquisition succeeds, F-18ed0aca2e0e supplies an alignment value. The function retains it for later use; it does not validate it.

Subsequent calls to the same dependency supply group identifiers. Each identifier is narrowed to signed 16 bits:

- Zero terminates traversal without a match.
- The bit pattern `0x8008`, interpreted as −32760, selects the desired group.
- Any other nonzero identifier selects the skipping path.

A count is read only for a nonzero identifier. Its low 16 bits, zero-extended, determine the group count.

For an unwanted group, the function reads the current input-state field at offset 32 and replaces it with that value plus twelve times the count plus four. This calculation uses **unsigned 32-bit arithmetic** and wraps modulo \(2^{32}\). No positioning dependency or explicit bounds check accompanies this write.

For the desired group, including a desired group with count zero, the function:

1. Calls F-b03b1199772e.
2. Reads the input-state fields at offsets 32 and 36 after that call.
3. Combines the dependency’s signed 32-bit result with the signed difference between those fields and an additional four.
4. Retains the resulting candidate record position and stops traversal.

Both input-state reads follow F-b03b1199772e. Their relative evaluation order is not established. The signed arithmetic’s behavior outside representable ranges remains unresolved.

When a zero identifier terminates traversal, the retained count is zero and the candidate record position remains zero. A count from a previously skipped group is not treated as the matching count.

After either termination or a match, F-9787e15c337d is called once. Its return value does not determine success or failure.

The twelve-byte stride and four-byte adjustment are established arithmetic. Their interpretation as record width and reserved group-header space is inferred.

### Missing or unusable group

Following traversal finalization, either a zero matching count or a zero candidate record position causes rejection.

On this path, the function obtains a diagnostic-object address from a global location and reads a signed 32-bit level at byte offset 204 within that object. These reads occur after F-9787e15c337d; that dependency is not assumed to preserve the global or diagnostic object.

If the level exceeds one, F-4457a9a44a68 receives a diagnostic indicating that the file contains no font resources.

The function then returns 2 directly:

- It does not directly publish an entry count.
- It does not allocate an object.
- It does not invoke shared cleanup.

Dependency effects, including effects of traversal finalization or diagnostic emission, remain possible.

### Count publication and index comparison

For a nonzero count and nonzero candidate record position, the count lies between 1 and 65535. The function compares it with the requested index as signed 32-bit values and writes the count to context offset 0.

If the index is greater than or equal to the count, the function returns 132 without allocation or shared cleanup.

There is no explicit negative-index rejection. Every negative index passes this comparison for a usable group. Such an index proceeds toward allocation and signed selected-position arithmetic.

The caller-side precondition for selecting an actual group member is therefore a nonnegative index strictly below the count. The function does not enforce the nonnegative part.

### Allocation and selected-record preparation

For an index that passes the comparison, F-3ce007b692cc receives:

- The allocation-related value captured on entry.
- A request for 176 bytes.
- Writable temporary storage for a separate status result.

The returned 32-bit value is stored into context offset 132 before that status is checked.

If the status is nonzero, the function returns it immediately. Shared cleanup is not called, regardless of the returned address value.

On allocation status zero, F-e40a3ceddab2 receives the candidate record position plus twelve times the signed requested index. A nonzero positioning status invokes shared cleanup.

If positioning succeeds, F-d036abe1e536 receives a requested frame length of twelve. A nonzero status also invokes shared cleanup.

No independent null check follows successful allocation, and no explicit overflow or range check protects the selected-position arithmetic.

### Record initialization and final loading

After selected-record frame acquisition succeeds, the observable sequence is:

1. F-18ed0aca2e0e supplies the first record value.
2. The current result slot is read, and object offset 0 is written.
3. F-18ed0aca2e0e supplies the second record value.
4. The current result slot is read, and object offset 168 is written.
5. The current result slot is read again, and object offset 4 is written.
6. The input-state field at offset 32 is read and incremented by eight using signed 32-bit arithmetic.
7. F-9787e15c337d is called.
8. The current result slot is read and passed with the captured input state to F-42fb116e4921.

For each of the first two object fields, only the record read’s low 16 bits participate. The shift count is the alignment read’s low eight bits. The field at offset 4 instead receives the alignment read’s low 16 bits.

For shift counts from zero through 31, the shifted value has unsigned 32-bit behavior; bits shifted beyond that width are discarded. Shift counts of 32 or greater have no established portable result in the supplied representation.

Dependency changes to the result slot can redirect later object writes or the final-loading argument. No slot-preservation guarantee is assumed.

A zero status from F-42fb116e4921 produces a zero return without shared cleanup. A nonzero status invokes shared cleanup and is then returned.

## Side effects

Established direct writes are:

- Clearing context offset 132 on entry.
- Publishing a usable group’s count at context offset 0.
- Storing the allocator’s returned value at context offset 132.
- Advancing the input-state field at offset 32 when skipping unwanted groups.
- Writing three result-object fields.
- Incrementing the input-state field at offset 32 by eight after the selected record reads.

Observable reads include the two descriptor globals at their respective decoding calls, the diagnostic global and level on the missing-group path, and repeated result-slot reads during initialization and final loading.

Additional effects may arise from every dependency. No rollback guarantee is established. In particular, an error can leave the entry-time clearing, count publication, allocation-result assignment, or earlier object writes observable, subject to later dependency modifications.

The two cursor-update cases must remain distinct:

- **Unwanted-group skipping:** unsigned 32-bit arithmetic, with defined modulo-\(2^{32}\) wrapping.
- **Selected-record consumption:** signed 32-bit addition of eight, with unresolved behavior if the mathematical result exceeds signed representability.

## Acceptance examples

These are conditional static expectations, not executed tests.

1. **Initial positioning failure.** If the first F-e40a3ceddab2 call returns 7, the function returns 7. Its direct result-slot clearing has already occurred. Neither descriptor decoding nor shared cleanup is called.

2. **Descriptor mutation during positioning.** If initial positioning changes the first descriptor global and succeeds, the following decoding call receives the value read after that positioning call. If later positioning changes the second descriptor global, the second decoding call likewise receives its subsequently read value. Equal descriptor values are permitted despite the separate global locations.

3. **Signature mismatch.** If the first decoded signature differs from `0x5A4D`, shared cleanup is called and the function returns 2. The second positioning and decoding calls do not occur.

4. **Reversed table displacements.** If the table-end displacement is 16 and the table-start displacement is 32, the requested table-frame length is 4294967280. There is no direct ordering rejection; further behavior depends on F-d036abe1e536.

5. **Unsigned unwanted-group wrap.** If an unwanted group has count one and the cursor read for skipping is 4294967292, the direct cursor write is 12. This follows unsigned 32-bit wrapping, not unresolved signed-overflow behavior.

6. **Zero identifier.** A zero group identifier causes no count read for that identifier. Traversal finalization occurs, followed by return 2. Diagnostic emission depends on the level read afterward. No direct count publication occurs.

7. **Index equals count.** With matching count three and nonzero candidate record position, index three causes publication of three and return 132, without allocation.

8. **Negative index.** Under the same group conditions, index −1 passes the comparison. After successful allocation status, the selected-position calculation targets twelve less than the candidate record position if the signed intermediate calculations remain representable. Safe negative-index rejection is not established.

9. **Ordinary initialization.** With alignment four, record values 32 and five, stable relevant addresses, representable arithmetic, and successful dependencies, the direct object writes are 512 at offset 0, 80 at offset 168, and four at offset 4. Final loading follows; its zero status produces a zero function result.

10. **Allocation error.** A returned allocation value is stored before a separately supplied nonzero status is returned. Shared cleanup does not occur.

11. **Final-loading error.** A nonzero final-loading status causes shared cleanup and is then returned. The cleanup dependency’s own return value does not replace it.

## Uncertainties

The following remain **documented_only**:

- **Descriptor contents and header encoding:** Exact source-byte layouts, byte order, and descriptor meanings are unavailable. The descriptor arguments are mutable global reads, not established constants.
- **Primitive-read ABI:** The supplied representation exposes a wide return for one count read while other uses consume narrower portions. The actual return convention and any independent failure reporting are unknown.
- **Large shift counts:** Alignment values whose low eight bits exceed 31 lack an established portable shift result. Processor-specific masking is not assumed.
- **Signed arithmetic overflow:** Matching-group record-position construction, signed index multiplication by twelve, selected-position addition, and the selected-record cursor increment have no visible overflow checks. Behavior outside signed representability is unresolved. This uncertainty does not apply to unsigned unwanted-group skipping or unsigned table-length subtraction.
- **Input bounds:** Direct cursor changes have no visible bounds checks. Whether dependencies enforce bounds or reject malformed frames is unknown.
- **Allocation and ownership:** Zero allocation status is not followed by an address validity check. Initialization beyond the three writes, ownership transfer, and release policy remain dependency-defined.
- **Aliasing and mutation:** Dependencies may change globals, context slots, or input state. Concurrency, reentrancy, and aliasing guarantees are not established.
- **Cleanup effects:** Neither resource release nor restoration of earlier state is established.
