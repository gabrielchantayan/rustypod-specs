# F-732402c6dc47

## Purpose

F-732402c6dc47 performs metadata-driven accounting followed by calls associated with an address supplied by its caller.

The established behavior consists of an initial dependency call, address normalization, global accounting writes, header validation, state-specific accounting, and final dependency calls. Allocation release is an inferred purpose, not an established ownership contract. The available evidence does not identify which dependency, if any, releases storage.

This is not a null-safe release interface. Before testing the supplied address for zero, the function reads a 32-bit word at that address plus 28 bytes and passes it to a dependency.

The global accounting operations do not unconditionally update a single accounting pair. They use four separately evaluated accounting-base values, with different capture and access times. Interpreting the writes as an ordinary two-word subtraction requires additional agreement and stability assumptions.

## Interface

### Input and output

The sole input is a **supplied address**, represented by a 32-bit integer and used for address arithmetic and memory accesses.

There is no specified return value. Ordinary completion returns without a result. Header rejection invokes a dependency designated non-returning in the supplied representation; that dependency’s implementation is unavailable.

### Widths and arithmetic

The visible representation uses:

- 32-bit addresses, metadata words, accounting fields, and counts.

Stored accounting results are described as 32-bit bit patterns, retaining the low 32 bits of the relevant arithmetic. This does not establish portable language-level behavior for arbitrary addresses or overflowing signed address calculations. No range check is visible for either category index or the index returned by a dependency.

## Behavior

### Initial call and early accounting-base capture

The function first reads the 32-bit word at supplied address +28 and calls **F-94cb53877c15** with that value as its sole argument.

Only after this call returns does the function evaluate the global accounting base and retain that value as the **initial accounting-base snapshot**. This capture precedes the zero-address check.

If the supplied address is zero, the function then returns. The initial read, dependency call, and accounting-base capture have already occurred. No normalization or accounting-field access follows on this path.

Consequently, a zero input still attempts to read address 28. A clean return depends on that read and the initial dependency call completing.

### Address normalization and amount acquisition

For a nonzero input, the function reads the 32-bit displacement at supplied address −4 and subtracts it from the supplied address. The result is the **normalized address**.

It then reads the 32-bit **initial amount** at normalized address −8.

There is no visible validation of the displacement, the resulting address, or the amount before subsequent accounting operations.

### Global accounting: separate base evaluations and delayed upper read

The global accounting sequence uses four accounting-base evaluations in total:

1. The initial accounting-base snapshot, captured after F-94cb53877c15 and before the zero check.
2. A fresh base evaluation used to read the lower word at offset +56, after the initial amount has been read.
3. Another fresh base evaluation used to capture the **upper-source address**, equal to that evaluated base plus 60. The upper word itself is not read yet.
4. Another fresh base evaluation used to select the lower-write destination at offset +56.

The function writes the lower result to the destination selected by the fourth evaluation. That result is the previously read lower word minus the initial amount, retaining 32 bits.

Only after this lower write does the function read the upper word through the previously captured upper-source address. It computes the upper result and writes it at offset +60 from the **initial accounting-base snapshot**.

Thus:

- The lower source and lower destination can derive from different base evaluations.
- The upper source address is captured before the lower write.
- The upper source value is read after the lower write.
- The upper destination uses the earliest base snapshot, not a newly evaluated base.
- No dependency call intervenes in this accounting sequence, but no supplied concurrency contract guarantees that the separate base evaluations agree.

The upper adjustment combines two quantities:

- A borrow equal to one when the previously read lower word is unsigned-less-than the initial amount, and zero otherwise.
- The signed extension of the initial amount’s sign bit: zero when bit 31 is clear, and −1 when bit 31 is set.

The upper result is the upper-source value minus that signed extension and minus the borrow, retaining 32 bits.

If all four base evaluations agree, the relevant storage remains stable, and no interference changes the accessed fields, these operations implement subtraction of the sign-extended 32-bit amount from one two-word accounting value. Without those conditions, the established contract is the separate source reads and destination writes above—not an update to one accounting pair.

Aliasing also matters: if the lower-write destination coincides with the captured upper-source address, the later upper read observes storage after that lower write, absent intervening interference.

### Transition call and state capture

After the global accounting writes, the function calls **F-2fd8826557a4** with no explicit arguments.

After that call returns, it loads the state pointer through a separate global pointer cell. This produces the **captured state** used throughout the remaining processing.

The function does not use a state pointer captured before F-2fd8826557a4. Later changes to the global state-pointer cell do not themselves replace the captured state.

### Normalized-address sentinel

If the normalized address equals 8, the function returns after the state-pointer load.

This path still performs:

- The initial amount read at normalized address −8, which is address zero for this sentinel.
- All global accounting operations.
- F-2fd8826557a4.
- The state-pointer load.

It does not validate the header, access state fields through the captured state, or invoke the remaining dependencies. The sentinel therefore does not protect the earlier low-address amount read.

### Header validation

For a normalized address other than 8, the **header address** is normalized address −16.

The function first reads the 32-bit header word and tests it for zero. If that read is nonzero, it reads the header word again and tests bit 0.

Either a zero first read or a second read with bit 0 set invokes **F-a817d8d58c10**, designated non-returning in the representation.

The two validation reads are distinct. Passing the first test does not establish that the second read observes the same word. Bits 1, 30, and 31 do not independently cause rejection.

The global accounting writes and F-2fd8826557a4 have already occurred before rejection. There is no visible rollback.

### Category and aggregate accounting

Following successful validation, the function calls **F-c0fc6d033caa** with the captured state.

After that call returns, it:

- Reads the unsigned 16-bit first category index.
- Reads the header word and retains only bits 2 through 29 using mask `0x3FFFFFFC`.
- Subtracts that captured **masked amount** from the first category field.
- Subtracts the same amount from the aggregate at state offset +780.
- Reads the unsigned 16-bit second category index.
- Subtracts the same amount from the second category field.
- Subtracts the same amount from the aggregate at state offset +544.

Each field update reads the selected field and writes its 32-bit subtraction result. The updates occur in the listed order.

The masked amount is between zero and `0x3FFFFFFC`, inclusive, and is divisible by four. It is captured once for these four subtractions. The second category index is read only after the first two writes.

Neither the validation reads nor values preceding F-c0fc6d033caa constrain what the later metadata reads must observe. That dependency’s effects are unknown.

### Count updates and final amount subtraction

The function next calls **F-09dcb55e8e0a** with no explicit arguments.

It uses the returned 32-bit index to select the state field at +784 plus four times that index and decrements that field. It then decrements the state field at +912.

There is no visible validation of the returned index. Its intended range and signedness semantics are **documented_only**.

After those count writes, the function reads the header again, applies `0x3FFFFFFC`, and subtracts the resulting amount from the state field at +8.

This final masked amount need not equal the amount used for the earlier four subtractions. Dependency effects, prior writes, or aliasing can change the header before this reread. The representation does not establish a separate ordering between the destination-field read and header read within this last subtraction; both precede its result write.

### Final calls

After all direct state writes, the function calls **F-cc6c9b4a0f68** with the captured state and header address.

If that call returns, it calls **F-e586bff64fb7** with the captured state, then returns.

There is no further direct header access after F-cc6c9b4a0f68. That ordering is compatible with a dependency consuming header-associated storage, but does not establish a release or ownership transfer.

## Side effects

On a nonzero-input path, the function directly performs two global accounting writes. Their destinations need not belong to the same object because they use separately evaluated or captured accounting bases.

On a validated nonsentinel path, it additionally performs seven state write operations: four category or aggregate subtractions, two count decrements, and one subtraction at offset +8. These are seven operations, not necessarily seven distinct storage locations.

Arithmetic is unchecked in the visible representation. There is no saturation, underflow rejection, or rollback. A decremented zero count produces the 32-bit all-ones pattern.

Dependency side effects are additional and unknown. No dependency is assumed to preserve globals, metadata, accounting fields, or storage lifetime. No lock acquisition, lock release, allocation release, or ownership transfer is established solely by call order.

There is no explicit status-based error reporting. Invalid memory accesses can prevent completion; header rejection invokes the designated non-returning dependency after earlier effects have occurred.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless stated otherwise, accesses are valid, dependencies return normally, relevant storage does not alias, and no external or dependency mutation affects the illustrated values. Examples involving one accounting pair additionally require all four accounting-base evaluations to agree.

1. **Zero supplied address.** If address 28 is readable, its word is passed to F-94cb53877c15. After that call returns, the accounting base is captured and the function returns. No accounting-field write or F-2fd8826557a4 call occurs.

2. **Borrow with one stable accounting pair.** Lower word 3, upper word 10, and initial amount 5 produce lower `0xFFFFFFFE` and upper 9.

3. **Sign-bit amount with one stable accounting pair.** Lower word 5, upper word 10, and amount `0xFFFFFFFF` produce lower 6 and upper 10. The borrow of one and signed extension of −1 cancel in the upper adjustment.

4. **Different accounting bases.** Suppose the initial snapshot designates one object, the lower-read evaluation a second, the upper-source capture a third, and the lower-write evaluation a fourth. With lower source 3, upper source 10, and amount 5, the fourth object receives `0xFFFFFFFE` at +56 and the first receives 9 at +60. No corresponding update to either source object is implied.

5. **Captured upper address aliases the lower destination.** Suppose both addresses designate the same word, the lower source is 3, and the amount is 5. The lower write stores `0xFFFFFFFE`; the later upper-source read obtains that value. The upper result is `0xFFFFFFFD`, written through the initial snapshot’s upper destination. The upper source is not read before the lower write.

6. **Sentinel.** Normalization to 8 still reads the initial amount at address zero, performs both global accounting writes, calls F-2fd8826557a4, and loads the state pointer. No header validation follows.

7. **Rejected header.** A zero first validation read invokes F-a817d8d58c10 without the second validation read. A nonzero first read followed by a bit-0-set second read also invokes it. Earlier global effects are not rolled back.

8. **Masked flags.** A stable header of `0xC0000022` passes validation and yields masked amount 32. Under the stated stability assumptions, all five amount-based state subtractions use 32.

9. **Changed final amount and count underflow.** If F-09dcb55e8e0a changes a previously 32-byte masked header amount to 64, the first four subtractions still use 32 and the final subtraction uses 64. A selected zero count becomes `0xFFFFFFFF`.
