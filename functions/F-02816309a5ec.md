# F-02816309a5ec

## Purpose

F-02816309a5ec coordinates an operation using a context and a caller-supplied descriptor. It first checks whether descriptor-associated state is available. If so, it attempts to complete the operation through that state. Otherwise, or after particular existing-state outcomes, it enters a preparation path.

Preparation can lead either to finalization or to a capacity decision followed by a write-shaped operation. Successful completion updates the descriptor’s leading fields. Handled failures invoke a cleanup-shaped dependency and then clear those fields. Failure of the initial dependency returns immediately without either action.

These control-flow properties are established by static evidence. “Existing state,” “preparation,” “capacity,” “finalization,” and “cleanup” describe roles within this function; they do not establish the domain meaning or ownership behavior of the dependencies.

## Interface

### Inputs and result

The function receives four arguments:

1. **Context holder:** an address from which a 32-bit context reference is read after the initial dependency succeeds.
2. **Descriptor:** writable storage with direct accesses within its leading 16 bytes. The address 28 bytes beyond its base is also passed to dependencies.
3. **Value reference:** an address passed to an operation dependency and, on one branch, dereferenced for a 32-bit value.
4. **Auxiliary value:** an opaque 32-bit value forwarded unchanged to operation dependencies.

The result is a signed 32-bit status. Completed success returns zero. Failure usually returns the nonzero status that selected failure handling. An existing-state lookup failure instead initiates fallback and need not become the final result.

The supplied representation establishes 32-bit words, 16-bit halfwords, byte-sized flag tests, and a 32-bit address model. Byte order is not established.

## Behavior

### Entry and context selection

The function initializes the first 32-bit word of its private resource record to zero. It does not visibly initialize the other four words.

It calls F-ad862549a0f2 without explicit arguments.

- A nonzero result is returned immediately.
- Zero permits further processing.

On this immediate return, the function performs no direct context-holder read, descriptor write, or cleanup call. This does not constrain side effects performed by F-ad862549a0f2 itself.

After initial success, the function reads the context reference from the context holder. It retains that reference for the remainder of the invocation rather than rereading the holder. Thus, changes made before this read can affect context selection; later holder changes do not redirect subsequent direct accesses.

It then calls F-60be901ce2de with the selected context, descriptor, and first flag-buffer address.

- Nonzero status enters handled failure.
- On zero status, a zero first flag byte selects preparation.
- A nonzero first flag byte selects the existing-state path.

Only the first byte controls this decision. Any nonzero byte has the same branch effect.

### Existing-state path

The function reads descriptor offset 4 into its working-location slot, then calls F-5f9a16493218 with the context, that location value, and resource-record address.

If this call returns nonzero, the function calls F-6e3669b482ce with the descriptor and enters preparation. It does not return the lookup status or invoke cleanup between these two calls. Any resource-record changes made by the unsuccessful lookup remain available to later calls; there is no visible reset.

If the lookup succeeds, the function calls F-68fdc7617c2f with:

- The selected context.
- The current first resource word, by value.
- The descriptor.
- The value reference.
- The auxiliary value.
- The second flag-buffer address.

Nonzero status enters handled failure. On zero status, the first byte of the second flag buffer selects between two outcomes.

**Zero flag:** The function calls F-6e3669b482ce with the descriptor, then F-b0f922796692 with the context and resource-record address.

- Zero cleanup status leads to preparation.
- Nonzero cleanup status leads to handled failure, preserving that status for return.

Handled failure calls F-b0f922796692 again. Consequently, this edge can make two consecutive cleanup calls with no preparation call between them.

**Nonzero flag:** The function calls F-f7c5b7585b2d with the context, resource-record address, and two zero-valued arguments.

- Nonzero status enters handled failure.
- Zero status is followed by a direct signed 32-bit increment of context offset 100, then successful descriptor completion.

No direct increment of context offset 52 occurs on this existing-state completion branch.

### Preparation path

Preparation is reached directly from the initial flag, after failed existing-state lookup, or after successful cleanup of existing state that did not complete the operation.

The function calls F-5d3e17c1b8e7 with:

- The selected context.
- The descriptor’s offset-28 address.
- The 128-byte workspace address.
- The working-location address.
- The resource-record address.

Nonzero status enters handled failure.

After zero status, the function calls F-68fdc7617c2f using the same argument roles described for the existing-state path. In particular, the first resource word is passed by value from its current contents.

Nonzero status enters handled failure. With zero status:

- A nonzero first flag byte selects F-f7c5b7585b2d with the context, resource-record address, and two zeros. Success proceeds to descriptor completion; failure enters handled failure.
- A zero first flag byte selects the capacity-and-write branch.

Successful preparation followed by successful finalization does not directly increment either observed context counter.

### Capacity arithmetic and decision

The arithmetic has distinct unsigned and signed stages. They must not be treated as one uniformly wrapping computation.

First, the unsigned 16-bit value at context offset 2 is converted to unsigned 32 bits. The signed 32-bit value at offset 36 is also converted to unsigned 32 bits for subtraction. The subtraction and subsequent addition of one are unsigned 32-bit operations, modulo $2^{32}$.

The resulting unsigned value is then converted to the signed 32-bit value used for the positivity test.

- When the unsigned result is representable as signed 32 bits, its signed value is established.
- When it exceeds the signed 32-bit maximum, the exact conversion result is documented_only. This contract does not assume a particular negative value or branch outcome.

Only a signed value strictly greater than zero triggers the capacity dependencies.

For that positive value, the function reads context offset 32 as signed 32 bits and adds the positive signed value. **Both operands of this proposal-forming addition are signed.** Its result is assigned to an unsigned 32-bit proposal.

For a representable signed sum, conversion to the unsigned proposal is defined modulo $2^{32}$; a negative representable sum therefore becomes a large unsigned value. If the signed addition overflows, the resulting behavior is documented_only. The unsigned destination does not establish wrapping semantics for the preceding signed addition.

The function then:

1. Calls F-2d8bccefd701 with the context.
2. Compares its unsigned 32-bit result against the already formed unsigned proposal.
3. Increments the proposal if, and only if, the returned value is strictly smaller.
4. Calls F-308710cf24ed with the context and resulting proposal.

The optional increment is genuinely unsigned 32-bit arithmetic and wraps modulo $2^{32}$. Equality does not trigger it. The proposal is formed before F-2d8bccefd701 runs and is not recomputed from context changes made by that call.

Nonzero status from F-308710cf24ed enters handled failure. If the signed difference is zero or negative, both capacity dependencies are skipped.

After cleanup returns, the function clears descriptor offsets 0, 4, 8, 10, and 12, in that order, using widths of 32, 32, 16, 16, and 32 bits. It returns the status that selected handled failure, not the cleanup result.

No direct rollback of context changes or dependency side effects is visible.

## Side effects

The function directly rewrites the descriptor’s leading 16 bytes on every completed success or handled-failure path. Initial dependency failure bypasses those direct writes.

It directly increments context offset 100 only after existing-state finalization succeeds, and offset 52 only after F-cac7073e9138 succeeds. Each increment reads the then-current signed 32-bit field. Signed overflow behavior remains documented_only.

Resource-record contents are carried between calls and fallback paths without a general reset. A cleanup-shaped call may modify that record before a later cleanup or preparation call receives it.

There is no direct allocation or release primitive. Neither finalization nor cleanup proves release, ownership transfer, reference retention, or complete resource disposal. No success-path cleanup call follows descriptor completion.

Private addresses passed to dependencies are invocation-local. The source does not establish whether dependencies retain them or whether such retention is valid. Dependency effects on globals, context storage, descriptor storage, and indirectly reachable memory are not constrained by this contract.

## Acceptance examples

These are conditional static acceptance criteria, not executed tests. Unless stated otherwise, storage does not overlap, required outputs are initialized by dependencies, arithmetic is representable where required, and dependencies make no additional changes.

1. **Initial rejection.** If F-ad862549a0f2 returns a nonzero status, that status is returned without a direct context-holder read, subsequent dependency call, or direct descriptor write.

2. **Initial descriptor-check failure.** If F-60be901ce2de fails, cleanup precedes descriptor clearing. The check’s status is returned even if cleanup returns a different status.

3. **Existing-state completion.** Successful lookup, a successful operation with nonzero flag, and successful finalization increment context offset 100 once. Descriptor offset 0 receives the current context offset 52 without this function directly incrementing it.

4. **Lookup fallback.** A failed F-5f9a16493218 call is followed by F-6e3669b482ce and preparation, without intervening cleanup. Later success yields zero rather than the lookup’s failure status.

5. **Repeated cleanup.** If the existing-state operation succeeds with a zero flag and its explicit cleanup fails, cleanup runs again before descriptor clearing. The first cleanup’s failure status is returned.

6. **Preparation finalized.** Preparation followed by a successful operation with nonzero flag and successful finalization returns zero without directly incrementing either context counter.

7. **Ordinary capacity calculation.** With context offset 2 equal to 10, offset 36 equal to 8, and offset 32 equal to 20, the unsigned difference is 3, its signed conversion is 3, and the signed proposal-forming sum is 23. Query result 22 produces request 24; query result 23 leaves request 23.

8. **Skipped capacity calls.** With offset 2 equal to 7 and offset 36 equal to 8, the unsigned difference and signed value are zero. Both capacity calls are skipped, but the write-shaped sequence is still attempted.

9. **Defined unsigned increment wrap.** With offset 2 equal to 0, offset 36 equal to 0, and offset 32 equal to −2, the positive difference is 1. The signed proposal-forming sum is −1, representable as signed 32 bits. Conversion gives unsigned proposal 4,294,967,295. A query result of zero triggers the unsigned increment, producing request zero.

10. **Arithmetic boundaries remain unresolved.** With offset 2 equal to 0 and offset 36 equal to 2, the unsigned difference is 4,294,967,295; its conversion for the signed positivity test is documented_only. Separately, a positive difference of 1 added to signed offset-32 value 2,147,483,647 causes signed-addition overflow; no wrapping proposal is promised.
