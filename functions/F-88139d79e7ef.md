# F-88139d79e7ef

## Purpose

F-88139d79e7ef applies a selection to a state object reached through an outer object. A zero selection requests a distinguished “no selection” state. Other selections are converted to a zero-based, 32-bit index and checked before being applied.

The established behavior comprises:

- Two unconditional preparatory dependency calls.
- Acquisition of a state pointer from the outer object.
- Selection conversion and, when applicable, range validation.
- A 32-bit selection-field write.
- Either a 16-bit clearing write or a selection-application dependency call.
- Four subsequent dependency calls in a fixed order.
- A 32-bit success or rejection result.

“Selection,” “state,” and “preparatory” are descriptive interpretations. The supplied material does not establish the domain represented by the objects or the effects performed inside dependencies.

## Behavior

### 1. Unconditional preparation

Before interpreting or validating the selection, the function performs these operations in order:

1. Read the 32-bit state address from the outer object at `0x40`, then call F-7c96094455b3 with that address and the value `4`.
2. Read the same outer-object field again, then call F-5a2ec88cfd0b with the newly read address and the value `0`.
3. Read the outer-object field a third time and capture its current value for the remaining visible operations.

These are three distinct reads. They must not be described as one initial lookup reused throughout the function. Either preparatory dependency may affect memory, including the outer object or its state-pointer field; its implementation is unknown.

Consequently, the two preparatory calls and the remaining work can use different state addresses. Once the third read has occurred, this body uses the captured address for subsequent state accesses and dependency arguments. It does not explicitly refresh that address after validation or later calls.

### 2. Selection normalization

An input selection of zero produces the sentinel index `0xFFFFFFFF`.

For a nonzero input, the visible expression subtracts one and stores the result in a 32-bit unsigned index.

Under the target-width, modulo-\(2^{32}\) interpretation of this operation:

- Input `1` produces index `0`.
- Input `2` produces index `1`.
- Input `0x7FFFFFFF` produces index `0x7FFFFFFE`.
- Input `0x80000000` produces index `0x7FFFFFFF`.
- Input `0xFFFFFFFF` produces index `0xFFFFFFFE`.

The signed-overflow qualification for input `0x80000000` is documented under **Uncertainties**. It must not be silently replaced with a blanket rule that every negative input is rejected.

### 3. Validation

The sentinel index bypasses validation entirely.

For a non-sentinel index:

- If its signed 32-bit interpretation is negative, return `0xFFFFFFCE` without calling F-1813c89b0386.
- Otherwise, call F-1813c89b0386 with the captured state address plus `0xE64`.
- Interpret the low 32 bits of that dependency’s returned value as an unsigned quantity.
- Reject with `0xFFFFFFCE` if that quantity is less than or equal to the normalized index.
- Continue only when the quantity is strictly greater than the index.

For an accepted non-sentinel selection, the operative comparison is therefore:

\[
0 \leq \text{index} < \text{returned low 32-bit quantity}.
\]

The first inequality uses a signed interpretation; the second comparison is unsigned.

The dependency’s return is represented as wider than 32 bits in the supplied material. Its upper portion does not affect the validation outcome or a subsequently visible operation on this path. No independent meaning for that portion is established.

A rejection occurs after the two preparatory calls. Rejection following the quantity comparison also occurs after F-1813c89b0386. Neither rejection path rolls back those calls or their possible effects.

### 4. Accepted-state update

The following action depends on the index:

- **Sentinel:** write a 16-bit zero at captured-state offset `0x22C`.

The selection-field write occurs before either the 16-bit clearing write or the application call. No result from F-9cc4a3bb48b4 is checked.

## Side effects

The direct writes performed by this body are:

- One 32-bit write at captured-state offset `0x10` on every accepted path.
- One additional 16-bit zero write at captured-state offset `0x22C` on the sentinel path.

There are no explicit state writes by this body before validation finishes. However, dependency calls preceding a rejection may themselves modify state or other memory.

The ordered calls are part of the behavior even when their implementations are unavailable. They must not be treated as pure operations, presumed harmless, or merged based solely on the visible arguments.

The values written directly are not guaranteed to remain unchanged at return. F-9cc4a3bb48b4 and the four subsequent dependencies may modify the same storage. The evidence establishes the write events and their ordering, not an invariant final memory image after unknown callees run.

No allocation, release, ownership transfer, or reference-count operation is explicit in this body. Passing an address to a dependency does not establish that the dependency borrows it, retains it, releases it, or leaves its lifetime unchanged.

No atomicity or concurrency guarantee is established. In particular, the three outer-object field reads are not shown as a single consistent snapshot.
