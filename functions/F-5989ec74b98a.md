# F-5989ec74b98a

## Purpose

F-5989ec74b98a prepares and emits a byte sequence through a state-selected callback. It initializes two expansion fields, invokes a preparation dependency with a 32-byte temporary destination, adjusts a width field, conditionally emits a prefix, and processes the prepared sequence.

Within that sequence, two byte values act as expansion markers:

- `0x3C` selects the signed expansion field at state offset `0x0C`.
- `0x3E` selects the signed expansion field at state offset `0x10`.

Each marker requests zero or more callbacks carrying `0x30`. The marker itself is not emitted. Other prepared bytes are passed directly to the callback.

**Established behavior:** initialization, dependency placement, prefix-presence capture, width arithmetic, marker processing, and count updates.

**Inferred intent:** this is a formatting stage using placeholder markers for zero-filled runs, with a separate dependency handling padding or alignment. Neither that formatting policy nor the dependencies’ internal behavior is established.

Every direct output invocation uses the current callback address with its low two bits cleared. The callback receives a byte-derived value, or the integer value `0x30` for expansion output, followed by the current 32-bit field at `0x24`. Its return value is ignored. The exact promoted representation of ordinary bytes above `0x7F` is not established.

Preparation receives a temporary destination of exactly 32 bytes. This routine supplies no separate capacity argument and performs no length validation or terminator scan.

### Preconditions

Defined operation requires:

- Accessible state storage for every field used at each stage.
- A readable first byte through the pointer at `0x08` when prefix presence is tested, even if that byte is zero.
- A valid current prefix pointer again when a prefix callback occurs.
- A callable masked callback address whenever direct output occurs.
- Preparation that does not overrun the temporary destination and initializes every position later consumed.
- Representable signed arithmetic where described below.
- Dependency and callback mutations that leave subsequent accesses valid.

These requirements are not enforced by this routine. No global-state preservation, ownership behavior, or absence of state mutation is assumed for any dependency.

## Behavior

### Preparation and initial state

Before preparation, the routine writes `0xFFFFFFFF` to the first expansion field and then to the second expansion field. Both are subsequently interpreted as signed 32-bit values, so their initial value is negative one.

It then reads the flags. If mask `0x20` is clear, the field at `0x38` is written with six. If that mask is set, this routine does not change the field at this stage.

F-a3c52ff480bf is called once with the preparation input, temporary destination address, preparation control, and state address, in that order. Its signed 32-bit result is retained as the prepared length.

There is no rejection of a negative result or a result exceeding 32. Preparation may change state, including the expansion fields; subsequent behavior uses the resulting state rather than assuming the initialized values survived.

### Prefix-presence capture

After preparation returns, the routine reads the pointer at `0x08` and tests whether its first byte is nonzero. It retains an unsigned 32-bit indicator: zero for absent, one for present.

Only presence is retained. Neither the prefix pointer nor the byte value is saved for later output.

Consequently, later dependency activity can change the eventual prefix byte without changing the saved decision to emit it.

### Width adjustment and integer semantics

The width adjustment uses the prepared length, the saved prefix-presence indicator, and a signed expansion adjustment.

For stable first and second expansion values \(A\) and \(B\), the mathematical expansion adjustment is:

\[
E =
\begin{cases}
A-1,& A>0\\
0,& A\leq 0
\end{cases}
+
\begin{cases}
B-1,& B>0\\
0,& B\leq 0.
\end{cases}
\]

Evaluation order matters for signed overflow and state reads:

- The first expansion field is tested for positivity and, when positive, read again to obtain its contribution.
- The second expansion field is read once for this calculation.
- When the second value is positive, that value is first added to the accumulated adjustment; only afterward is one subtracted.
- The prepared length is then added to the adjustment using signed 32-bit arithmetic.

Thus, representability of the final mathematical adjustment alone is insufficient. The preceding signed additions must also be representable. For example, adding a positive second expansion value can overflow before the subsequent subtraction of one, even when the mathematically combined correction would fit.

The unsigned prefix indicator changes the arithmetic domain for the remaining operations. After the signed adjustment-plus-length subexpression has been evaluated, its result is converted to unsigned 32-bit form before adding the prefix indicator. The old width value is also converted to unsigned for the subtraction. **The prefix addition and the width subtraction therefore wrap modulo \(2^{32}\).**

Let:

- \(W\) be the old width bit pattern interpreted as an unsigned 32-bit integer;
- \(L\) be the saved signed prepared length;
- \(P\) be the saved unsigned presence indicator, either zero or one.

For stable expansion fields and representable preceding signed intermediates, the stored width bit pattern is:

\[
W_{\text{new}}
=
\bigl(W-(E+L+P)\bigr)\bmod 2^{32}.
\]

This equation describes the stored 32-bit pattern, not unrestricted signed subtraction. In particular, crossing the signed boundary during the final width subtraction does not itself cause signed overflow.

The width is adjusted once, before helper calls and direct output. Later changes to expansion counts, prefix state, or output state do not trigger recomputation.

The adjustment does not inspect marker frequency. Each positive expansion field contributes one correction whether its marker is absent, appears once, or appears repeatedly.

### Helper placement and prefix emission

After adjusting width, the routine tests mask `0x10` in the current flags. If clear, it calls F-be81034a42a8 with the state address.

If saved prefix presence is true, it then reads the current prefix pointer and current first byte and invokes the current output callback. After the callback returns, it reads the current output count, adds one using signed arithmetic, and stores the result.

The routine subsequently reads the flags again. If mask `0x10` is now set, it calls F-be81034a42a8.

The two flag tests are independent:

- With a stable clear flag, the helper runs once before the optional prefix.
- With a stable set flag, it runs once after the optional prefix.
- A clear-to-set change during intervening execution can cause two calls.
- A set-to-clear change can cause neither call, if intervening execution occurs and makes that change.

A prefix classified as present is emitted even if its current byte has become zero. A prefix classified as absent is not emitted by this step even if a later helper introduces a nonzero prefix.

### Prepared-sequence processing

After the helper and prefix stages, processing starts at temporary-buffer position zero.

Before each byte read, the signed position is compared with the saved signed length. If the position is greater than or equal to the length, F-ea83ae94b50b is called with the state address, after which the routine returns.

Accordingly, zero or negative lengths cause no temporary-buffer reads. They do not bypass width adjustment, prefix processing, or the helper tests.

Each consumed position has one of three behaviors:

| Prepared byte | Direct output | Subsequent count update |
|---|---|---|
| Other than `0x3C` or `0x3E` | One callback carrying the byte-derived value | Read current count, add one, store |
| `0x3C` | Repeated callbacks carrying `0x30`, controlled by field `0x0C` | Read current count, then current first expansion field; add and store |
| `0x3E` | Repeated callbacks carrying `0x30`, controlled by field `0x10` | Read current count, then current second expansion field; add and store |

For either expansion marker, a signed iteration counter starts at zero. The selected expansion field is reread before each prospective callback. Output continues while the counter is less than that current signed field, with the counter advancing after each callback.

This makes expansion length responsive to callback mutations. Reducing the bound can stop emission early; increasing it can extend emission.

The routine does not increment its output-count field after each expansion callback. Instead, after the expansion loop ends, it adds the expansion field’s then-current value to the then-current count. That value need not equal the number of callbacks actually performed.

A zero or negative expansion value initially produces no expansion callbacks. Nevertheless, the value is added to the output count. An unchanged negative-one sentinel therefore decreases the count by one when its marker is processed.

After processing an ordinary byte or marker, the prepared position advances by one. Emitted bytes are not recursively interpreted as markers. No byte serves as a sequence terminator.

## Side effects

The routine’s direct state writes comprise:

- Initializing both expansion fields.
- Conditionally initializing the setting at `0x38`.
- Updating width once.
- Updating the output count after a prefix, ordinary byte, or completed marker expansion.

Dependencies and callbacks may have additional effects not bounded by this list.

Callback selection and the opaque callback argument are obtained anew for each direct invocation. Changes to these fields can affect later output, including later callbacks within the same expansion. The exact relative evaluation order among callback-address, argument, and byte-related reads within an invocation is not established.

For ordinary output and the prefix, callback mutations to the output count occur before the routine’s subsequent increment. For marker output, all expansion callbacks precede the routine’s final count and expansion-field reads.

The routine performs no explicit allocation, deallocation, release, or ownership transfer. The preparation destination is temporary storage available during this invocation, not durable storage after return. Whether a dependency retains its address is unknown.

There is no explicit error result, callback-failure check, null check, bounds repair, or rollback. Negative preparation results are treated as lengths, not recognized as errors. Effects already completed are not undone if later execution faults or a dependency does not return.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid storage, representable signed intermediates, no relevant helper effects, and callbacks that do not mutate state.

### Ordinary sequence

Preparation supplies `abc`, returns three, leaves both expansion fields nonpositive, and leaves an absent prefix.

Expected behavior:

- Width decreases by three modulo \(2^{32}\).
- Direct callbacks carry `a`, `b`, and `c`, in order.
- Output count increases by three, provided its signed additions are representable.
- F-ea83ae94b50b runs after processing the third position.

### Two expansions

Preparation supplies `a<b>c`, returns five, and leaves expansion counts three and two. The prefix is absent.

Expected behavior:

- Width decreases by eight modulo \(2^{32}\).
- Direct output is `a000b00c`.
- Output count increases by eight when its signed additions are representable.

### Unsigned width crossing the signed boundary

The old width bit pattern is `0x80000000`. Preparation returns one, the expansion adjustment is zero, and the prefix is absent.

Expected stored width: `0x7FFFFFFF`.

The signed adjustment-plus-length result is one. The final subtraction is unsigned, so this case does not involve signed overflow in the width update.

### Unsigned width underflow

The old width is zero, preparation returns one, the expansion adjustment is zero, and the prefix is absent.

Expected stored width: `0xFFFFFFFF`, by modulo-\(2^{32}\) subtraction.

This establishes no wrapping guarantee for separate signed output-count additions.

### Prefix placement and mutation

Preparation supplies `12`, returns two, and leaves a nonzero prefix byte `-` with nonpositive expansion fields.

With a stable clear `0x10` flag, F-be81034a42a8 precedes direct output `-12`. With a stable set flag, the prefix callback precedes that helper, followed by callbacks for `12`. Width decreases by three modulo \(2^{32}\).

If the first helper instead changes the prefix byte to zero after presence was captured, the prefix callback still occurs and carries zero.

### Negative expansion sentinel

Preparation supplies only `<`, returns one, and leaves the first expansion field at negative one. The prefix is absent.

Expected behavior:

- Width decreases by one modulo \(2^{32}\).
- No expansion callback occurs.
- The output count decreases by one, if representable.
- Finalization still occurs.

### Dynamic expansion bound

A first-marker expansion begins with count three. Its first callback changes that field to one without changing the output count.

Expected behavior: exactly one `0x30` callback occurs, the next comparison terminates expansion, and the final count adjustment adds one rather than three.

### Nonpositive prepared length

Preparation returns negative one, both expansion fields remain nonpositive, the prefix is absent, and old width is zero.

Expected behavior: width becomes one; no temporary-buffer byte is read; the conditional helper stages still occur; F-ea83ae94b50b is called.

For a returned length of zero under otherwise identical conditions, width remains zero and traversal likewise performs no buffer reads.

## Uncertainties

The following remain **documented_only**:

- Meanings of the opaque preparation inputs and the setting at `0x38`.
- Preparation guarantees about destination bounds, initialized bytes, marker placement, and returned lengths.
- Error conventions and nonreturning behavior of dependencies.
- Promotion and signedness of byte-derived callback values above `0x7F`.
- Target behavior when preceding signed expansion arithmetic, adjustment-plus-length arithmetic, or signed output-count arithmetic overflows.
- Structure alignment, byte order, and ABI details beyond the represented widths and accesses.
- Meaning of the callback address’s low two bits.
- Concurrency, asynchronous mutation, synchronization, and reentrancy guarantees.
- Dependency ownership, pointer retention, and global-state effects.
- Whether width and count accounting are intended to match actual emitted bytes for every supported representation.

These uncertainties do not extend to the final unsigned prefix addition and width subtraction: their modulo-\(2^{32}\) behavior is established under the represented model, conditional on valid preceding signed computation.

A length above 32 permits traversal beyond the temporary destination if execution reaches those positions. No safe truncation is established. Marker multiplicity and mutable expansion bounds can also separate width accounting, count accounting, and actual callback totals; no invariant preventing that separation is supplied.
