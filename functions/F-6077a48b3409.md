# F-6077a48b3409

## Purpose

F-6077a48b3409 searches a context-associated database collection for a requested name and conditionally clears two fields in a matching entry. Its apparent purpose is database detachment, with restrictions on reserved entries, transaction state, and a resource-associated status byte.

The established behavior is narrower than a complete detachment guarantee: the function invokes an opaque dependency, clears two entry fields, and invokes another dependency. Whether those calls close a database, release memory, update external state, or invalidate other objects is not established.

On refusal or unsuccessful selection, the function constructs a diagnostic in a temporary buffer and passes that buffer to a reporting dependency. It has no explicit return value conveying success or failure.

## Interface

### Inputs

The function receives three arguments:

1. **Context address.** A value used as an address. A 32-bit field at byte offset 24 supplies the address of the collection state.
2. **Uninterpreted 32-bit argument.** No direct read or use of this argument appears in the supplied body.
3. **Request-word address.** An address from which the function immediately reads one 32-bit word. That word is passed to F-95b79f0a129e to obtain the search-name representation.

No argument validation is visible. In particular, a null context address or request-word address does not receive a defined diagnostic path before dereference.

The first entry field is treated as a name operand by inference from its use, not by a demonstrated string layout. The encoding, termination requirements, and comparison rules are delegated to dependencies.

## Behavior

### 1. Resolve the requested name

The function first reads the 32-bit word at the third argument’s address and calls F-95b79f0a129e with that word.

The dependency’s result is represented as 64 bits. Its low 32 bits are interpreted as an address. Its high 32 bits do not determine any visible branch or dependency argument in this body.

Only after that dependency returns does the function read the collection-state address from the context.

If the returned low address is zero, the function substitutes the address of a fixed static object. The contents of that object are not supplied. It must not be specified as an empty string, a particular database name, or any other concrete value.

The resolved address, including any substitution, is then retained as the second operand for subsequent comparisons.

### 2. Search the collection

The search starts at index zero and continues while the index is less than the signed 32-bit entry count read from the collection state.

For each visited index:

1. The function reads the entry-storage address and identifies the entry at that address plus 24 times the index.
2. It reads the entry’s 32-bit resource field at offset 4.
3. If that field is zero, it does not call the comparison dependency for that entry.
4. If that field is nonzero, it calls F-e6db2171781a with the entry’s first 32-bit field and the resolved search-name address.
5. A zero low 32-bit comparison result ends the search at that entry. Any other low 32-bit result continues the search.

The comparison result is represented as 64 bits, but its high half does not govern the visible behavior.

Under stable collection contents, this selects the first occupied entry whose comparison result is zero. The function does not continue searching for another matching entry if that first match is later rejected.

The count is read during loop evaluation rather than captured once for the entire search. The entry-storage address is also read when computing each visited entry. Consequently, dependency-driven changes to those fields can affect subsequent iterations. The function does not establish snapshot semantics.

### 3. Determine whether the selected index is eligible

After the search, the function reads the entry count again. Further processing requires both:

- The current index is less than that count.
- The current index is greater than one.

Thus indices zero and one are excluded from the successful path. With stable state, a match at either index terminates the search but is rejected; a later matching entry is not considered.

A zero or negative signed count causes no search iterations. Under stable state, that leads directly to diagnostic construction.

The two eligibility comparisons are not a substitute for memory safety. In particular, they do not prove that entry storage is large enough or remains unchanged.

### 4. Check transaction-related state

For an eligible index, the function reads the byte at collection-state offset 28.

If this byte is zero, the function calls F-ea27adaa2931 with:

- The value 128.
- The temporary diagnostic buffer.
- An additional static diagnostic operand associated with refusing detachment within a transaction.

It then proceeds directly to diagnostic reporting. It does not inspect the resource status byte, invoke the success-path dependency, or perform the two explicit entry-field clears on this branch.

The exact diagnostic bytes are not established by the supplied material. The diagnostic operand’s label supports the transaction-refusal interpretation, but is not a complete string literal.

Any nonzero value of the transaction-related byte allows execution to proceed to the resource check.

### 5. Check the selected resource

After the transaction check passes, the function rereads the selected entry’s resource field. It does not rely on the earlier value that allowed the entry to be compared.

There are two cases:

- **Resource field is now zero:** the function proceeds to the successful path without reading a resource status byte.
- **Resource field is nonzero:** the function reads the byte at offset 8 of that resource. A zero byte permits the successful path; a nonzero byte selects the common diagnostic path.

This reread is observable. For example, a comparison dependency could leave the selected entry’s resource field zero, in which case no resource dereference occurs after the transaction check.

The resource status byte is read as an unsigned byte. Only zero versus nonzero matters. The interpretation of a nonzero value as “busy,” “locked,” or another condition is not established.

### 6. Perform the successful-path sequence

When the selected index is eligible, the transaction-related byte is nonzero, and the resource check permits continuation, the function performs these operations in order:

1. Calls F-7446dea3e07b, with no explicit arguments shown.
2. Writes zero to the selected entry’s 32-bit resource field at offset 4.
3. Writes zero to the selected entry’s 32-bit field at offset 20.
4. Calls F-aacdb1821b51 with the previously obtained collection-state address and a zero second argument.
5. Returns without constructing or reporting a diagnostic.

The selected entry address is retained across the first call. The collection-state address is likewise not reloaded from the context before the final call.

The body does not visibly decrement the entry count, compact entry storage, clear the entry’s first field, or clear the whole 24-byte entry. Dependencies may have additional effects, but those are not supplied here.

### 7. Construct and report other diagnostics

The common diagnostic-construction path is reached when:

- No eligible entry is selected.
- A match is found at index zero or one.
- An eligible entry passes the transaction check but has a nonzero resource status byte.

On this path, F-ea27adaa2931 is called with the value 128 and the temporary diagnostic buffer. No explicit third argument is shown for this call. Its message, formatting rules, and any additional argument requirements are unknown.

Both this path and the transaction-refusal path then call F-d8267ca9780b with:

- The original context address.
- The temporary diagnostic buffer.
- The 32-bit all-ones value, 4,294,967,295, equivalent to −1 if interpreted as signed 32-bit.

The meaning of that final value is delegated to F-d8267ca9780b. It is not established as a length, error code, or sentinel by the call alone.

## Acceptance examples

These are conditional specification examples, not executed tests. Unless stated otherwise, memory is valid and dependencies do not mutate collection structure or prevent normal return.

1. **Eligible match with zero resource status.**  
   Index two is the first occupied matching entry, the transaction-related byte is nonzero, and its resource status byte is zero. The required sequence is F-7446dea3e07b, clear offset 4, clear offset 20, F-aacdb1821b51 with collection state and zero, then return. No diagnostic dependency is called on that path.

2. **Transaction refusal takes precedence.**  
   An eligible entry matches, but the transaction-related byte is zero. The transaction-specific diagnostic construction and reporting calls occur. The resource status byte is not read by this body, and neither explicit entry clear occurs.

3. **Nonzero resource status.**  
   An eligible match passes the transaction check and has a nonzero resource status byte. The common diagnostic-construction call occurs, followed by reporting. The successful-path sequence does not occur.

4. **Reserved match shadows a later match.**  
   Index one compares equal, and index three would also compare equal. Search stops at index one. The function takes the common diagnostic path without comparing index three.

5. **Unoccupied entry is skipped.**  
   An entry’s resource field is zero when visited. Its first field is not passed to F-e6db2171781a, regardless of what that field contains.

6. **Null resolved address uses the static fallback.**  
   F-95b79f0a129e returns a result whose low half is zero. Subsequent comparisons receive the fixed static-object address, not zero. No particular fallback contents are required by this contract.

7. **Resource disappears during comparison.**  
   An eligible occupied entry compares equal, and the comparison leaves its resource field zero. If the transaction-related byte is nonzero, the function skips the resource status-byte read and performs the successful-path sequence.

8. **Nonpositive count.**  
   The signed entry count is zero or negative and remains unchanged. No entry comparison occurs. The common diagnostic path is taken.

9. **Nonzero comparison-result high half.**  
   A comparison returns a nonzero high half but a zero low half. The search treats it as a match; the high half does not override that result.
