# F-18d6a2021b62

## Purpose

F-18d6a2021b62 parses a structured binary region obtained through a stream-like context and populates a caller-supplied destination. The region contains a fixed header, optional flag-controlled data, length-delimited extension records, a list of 16-bit values, and a variable-width entry table.

The operation is incremental, not transactional. Errors can leave header fields, counts, allocation results, decoded arrays, and dependency side effects in place. Some errors invoke common finalization; others return immediately.

A physical-font interpretation is inferred intent, not a prerequisite of this contract. Fields below are identified by their observable representation and placement.

## Interface

### Arguments and return value

The function receives four arguments:

| Argument | Established use |
|---|---|
| Destination | Writable structure addressed in 32-bit words |
| Context | Object with readable 32-bit fields at byte offsets `0x1C` and `0x20`; also passed to dependencies |
| Position | 32-bit value passed to the initial positioning dependency, stored in the destination, and used in a later position calculation |
| Requested extent | 32-bit value passed to the acquisition dependency and used to calculate the input boundary |

The highest explicit destination write occupies bytes `0x94`–`0x97`. At least `0x98` writable bytes are therefore required for paths reaching that write. Dependencies receiving the destination may require additional storage; their requirements are not established here.

The return value is a 32-bit status:

- Zero on the locally successful path, assuming the relevant dependencies report success.
- `8` for locally detected insufficient or out-of-bounds input.
- A nonzero dependency status on the propagation paths described below.

There are no explicit checks for null pointers, destination capacity, context validity, or a negative requested extent.

### Representation and preconditions

The supplied representation uses 32-bit words and addresses. Encoded multibyte integers are big-endian:

- One byte yields `0`–`255`.
- Two bytes yield `0`–`65,535`.
- Three bytes yield `0`–`16,777,215`.

Decoded values occupy full 32-bit destination words. No consumer-defined signed meaning for these values is established.

Ordinary bounded parsing requires valid objects, a coherent acquired region, meaningful nonwrapping address arithmetic, and writable storage supplied by successful allocation dependencies. Invalid pointers, overlapping input and output, wrapped address calculations, and negative extents are outside the established ordinary-input behavior.

## Behavior

### Initial writes and acquisition

Before making any dependency call, the function:

1. Reads context offset `0x1C` and writes that value to destination `0x00`.
2. Writes the position argument to destination `0x04`.
3. Writes zero to destination `0x88`.
4. Writes the address of destination `0x88` to destination `0x8C`.

The context value captured in the first step is retained for later extension-handler and allocation calls. Those uses do not reread context `0x1C` or destination `0x00`.

F-e40a3ceddab2 is then called with the context and position. A nonzero result returns immediately, without common finalization.

If that succeeds, F-d036abe1e536 is called with the context and requested extent. Its nonzero result also returns immediately.

After both succeed, context `0x20` is read and stored at destination `0x94`. A separate read of context `0x20` supplies the parsing base. The parsing boundary is that second value plus the requested extent. These reads are distinct; the stored value and parsing base are not contractually interchangeable if the context can change between reads.

### Fixed header and optional dependency

The function requires 15 bytes before decoding any fixed-header field. It reads seven successive big-endian 16-bit values from the first 14 bytes and writes them, in order, to destination `0x08` through `0x20`. The following byte is captured as the flags and written to `0x24`.

When flag `0x04` is clear, two more bytes are required. Their big-endian value is written to destination `0x28`. When this flag is set, those bytes are absent and the function does not initialize `0x28`.

When flag `0x80` is set, F-43e9fa7452ce receives:

- A reference to the current parsing cursor.
- The parsing boundary.
- A value read from an opaque global at this call site.
- The destination.

The global read occurs after the initial positioning and acquisition calls and after fixed-header processing, including the shared-value field when present. The argument is not established to be a fixed constant or a value captured at entry. Earlier unknown dependencies may change that global; its value and immutability are not established. With flag `0x80` clear, this call and its associated global read are absent from the visible path.

A nonzero result takes common finalization with that status. A zero result continues with the cursor supplied through the reference. No local validation establishes that the returned cursor remains within the acquired region.

Later local flag decisions use the captured flag byte, not a reread of destination `0x24`. A dependency changing that destination field does not, by itself, change those local decisions.

### Extension region

Three bytes at the current cursor encode an unsigned 24-bit extension-region length. The cursor advances beyond the length field. A nonzero declared region must fit within the parsing boundary; otherwise the function takes the local status-`8` path.

A zero length skips record processing. Within a nonempty bounded region, each record begins with a big-endian 16-bit total length followed by a big-endian 16-bit type. The total length includes these four header bytes.

Record processing stops if:

- Fewer than four bytes remain.
- The next total length is less than four.
- The total length exceeds the remaining declared region.

These conditions do not themselves report an error. Subsequent parsing resumes at the end of the entire declared extension region, including any unprocessed remainder.

For a record that passes these checks:

- **Type 1 or 3:** F-69104db11679 receives the payload address, total length minus four, and the initially captured context `0x1C` value. A nonzero result returns immediately, bypassing common finalization.
- **Type 2:** If total length is at least `0x24`, the 16-bit values at record-relative byte offsets `0x0E`, `0x10`, and `0x12` are written to destination `0x2C`, `0x30`, and `0x34`, respectively. A shorter record makes none of these writes.
- **Other types:** No type-specific local action occurs.

After a handled or skipped well-formed record, the record cursor advances by its total length and the remaining length decreases accordingly. Multiple qualifying type-2 records overwrite the same fields in encounter order.

### First array

At the extension-region end, one byte is required for the first-array count. The count is written to destination `0x68` before checking availability of the array data.

Two encoded bytes are required for each element. The byte-sized count limits this requirement to 510 bytes. If those bytes do not fit, the function reports local status `8` without making the first allocation call.

Otherwise, F-6dd003795db7 receives, in order:

- The initially captured context `0x1C` value.
- Element size `4`.
- Zero.
- The count.
- Zero.
- A writable status location.

The returned allocation value is stored at destination `0x6C` before that status is inspected. A nonzero status takes common finalization.

On success, each successive big-endian 16-bit input value is written into a consecutive 32-bit array element. A zero count still invokes the dependency but performs no element writes. The function uses the allocation pointer held in destination `0x6C` during these writes; validity and suitability of that storage are external requirements.

### Post-list header and second allocation

Eight further bytes must fit before any post-list-header field is decoded. Their destination writes occur in this order:

1. First byte to `0x70`.
2. Second byte to `0x74`.
3. First big-endian 16-bit value to `0x44`.
4. Second big-endian 16-bit value to `0x38`.
5. Final big-endian 16-bit value, the entry count, to `0x78`.

Destination `0x7C` is then assigned the 32-bit calculation:

**address immediately after this header + original position − current context field at `0x20`.**

Context `0x20` is reread for this calculation. An intervening dependency can therefore affect the stored source position without changing the earlier captured parsing boundary.

F-6dd003795db7 is called again with the initially captured handle, element size `16`, zero, the entry count, zero, and the status location. Its return is stored at destination `0x80` before status inspection. A nonzero status takes common finalization.

The second allocation occurs before the encoded table’s total size is checked.

### Entry-table decoding

Each output entry consists of four consecutive 32-bit words, occupying 16 bytes. Its encoded size depends on the captured flags:

| Flag | Effect on encoded size |
|---|---|
| Base layout | Four bytes |
| `0x02` set | Add one byte |
| `0x04` set | Add two bytes |
| `0x08` set | Add one byte |
| `0x10` set | Add one byte |
| `0x20` set | Add one byte |

The encoded width is therefore 4–10 bytes per entry. With a 16-bit count, the maximum encoded requirement is 655,350 bytes; the maximum output size is 1,048,560 bytes. These products fit within 32 bits, although adding them to addresses still requires a nonwrapping range.

The entire encoded table is checked against the parsing boundary before any entry is decoded. Entries are then processed in order:

| Output word | Input or source |
|---|---|
| 0 | One byte if `0x02` is clear; otherwise a big-endian 16-bit value |
| 1 | Current destination `0x28` if `0x04` is clear; otherwise a big-endian 16-bit value from the entry |
| 2 | One byte if `0x10` is clear; otherwise a big-endian 16-bit value |
| 3 | Big-endian 16-bit value if `0x20` is clear; otherwise a big-endian 24-bit value |

If flag `0x08` is set, one encoded byte between the sources for words 1 and 2 is skipped. No output word is assigned from that byte.

Words are written in order 0, 1, 2, 3. The entry-array base is obtained from destination `0x80` for each entry. In shared-value mode, destination `0x28` is read for each entry rather than using an independently retained copy.

Bits `0x01` and `0x40` have no direct local decoding effect. Successful parsing does not require exact exhaustion of the region; trailing bytes are allowed.

### Errors and common finalization

A failed local boundary check sets status `8`, invokes F-4457a9a44a68 with a fixed invalid-input diagnostic, and enters common finalization.

Common finalization occurs in this order:

1. Call F-9787e15c337d with the context.
2. Call F-b03b1199772e with the context.
3. Store the second call’s return value at destination `0x90`.
4. Write zero to destination `0x94`.
5. Return the retained parsing or dependency status.

The finalization return values do not replace the returned status.

Errors from the initial positioning dependency, initial acquisition dependency, or F-69104db11679 return immediately instead. They do not invoke this sequence. In particular, an extension-handler error does not cause this function to clear destination `0x94`.

## Side effects

Destination writes are incremental. There is no rollback, comprehensive initialization, or explicit deallocation of either allocated array.

Both allocation results are stored even when their accompanying status is nonzero. A first allocation can remain recorded after a later header failure; a second allocation can remain recorded after a table-size failure.

The writes at `0x88` and `0x8C` resemble sentinel initialization, but only their values and ordering are established. Linked-list semantics are inferred.

The optional flag-`0x80` path reads an opaque global at invocation time. Nothing here establishes that this global is immutable or unaffected by earlier calls.

Dependencies may change the context, destination where supplied, globals, or other reachable state. No unknown dependency is assumed to preserve globals, allocate zeroed storage, transfer ownership, or release memory. Explicit post-call writes described above still occur on their respective paths.

## Acceptance examples

These are conditional static cases, not executed tests. They assume valid nonoverlapping storage, nonwrapping arithmetic, and the stated dependency outcomes.

1. **Minimal zero-count object.** With flags clear, zero extension length, zero first-array count, and zero entry count, 29 bytes suffice: 15 fixed-header bytes, two shared-value bytes, three extension-length bytes, one count byte, and eight post-list-header bytes. Both allocation calls occur with count zero. Successful dependencies lead to common finalization and status zero.

2. **All entry-width options.** Flags `0x3E` omit the shared header value. Each entry consumes ten bytes and produces 16-bit, 16-bit, 16-bit, and 24-bit values in four words, with an intervening skipped byte.

3. **Call-time global value.** Suppose flag `0x80` is set and an initial dependency changes the opaque global before fixed-header processing completes. The optional dependency receives the value read at its invocation, not an entry-time snapshot. No particular value is required by the visible local logic.

4. **No optional call.** With flag `0x80` clear, the function does not make F-43e9fa7452ce’s call-site global read or invoke that dependency.

5. **Short fixed header.** Fewer than 15 available bytes after acquisition causes status `8`, diagnostic emission, and common finalization. None of the seven decoded header fields is written locally.

6. **Truncated first array.** A count of three with fewer than six following bytes writes destination `0x68`, but does not invoke the first allocation. The result is local status `8` after common finalization.

7. **Malformed internal extension record.** A bounded extension region containing a next-record length of two stops record processing without a local error. Parsing resumes at the declared region end and can still succeed.

8. **Extension-handler error.** A nonzero type-3 handler status returns immediately. Common finalization and the explicit clearing of destination `0x94` do not occur.

9. **Truncated table after allocation.** If the second allocation succeeds but the encoded table is one byte short, no entry is decoded. The allocation result remains stored, followed by the diagnostic and common finalization with status `8`.

10. **Trailing bytes.** Extra bytes after a complete table do not cause rejection.
