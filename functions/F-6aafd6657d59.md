# F-6aafd6657d59

## Purpose

F-6aafd6657d59 conditionally transfers a bounded quantity from a buffered source to a caller-supplied destination, then adjusts the source’s remaining count and either compacts its remaining bytes or advances its data address.

Every invocation first clears the low four bits of a context status field. When the observed buffered count is zero, the function instead returns a separate context value and, if that value is nonzero, sets the low status bits to hexadecimal 9.

The interpretation as buffered consumption is inferred intent. The established behavior is the sequence of memory accesses, conditional dependency invocation, state changes, and return selection described below. In particular, the return value is not consistently a count of bytes transferred.

## Interface

### Inputs

The function accepts three values represented as 32-bit integers:

1. **Context address.** Used as the base address of a record containing status, an empty-buffer result, and a descriptor address.
2. **Destination value.** Zero disables the transfer path. A nonzero value is passed as the first argument to dependency D-01 when the effective transfer amount is positive.
3. **Requested amount.** Compared with the buffered count using signed 32-bit ordering.

The source representation uses integer-valued addresses and four-byte record fields. This contract describes that apparent 32-bit address model; it does not establish portability to a different pointer width or execution environment.

### Context layout

| Byte offset | Width | Interpretation |
|---|---:|---|
| +0x14 | 32 bits | Status and mode bits |
| +0x1c | 32 bits | Signed result used when the observed buffered count is zero |
| +0x20 | 32 bits | Address of the buffer descriptor |

The status field has two independently relevant regions:

- Bits 0–3 are cleared at entry.
- Bit 9, mask 0x200, selects the post-transfer adjustment strategy when reread after D-01 returns.

No meaning is established for the other bits.

### Buffer descriptor layout

| Byte offset | Width | Interpretation |
|---|---:|---|
| +0x00 | 32 bits | Signed buffered count |
| +0x04 | 32 bits | Data address |

The descriptor address is captured once from the context. Later operations use that captured address; they do not reload the descriptor address from the context.

### Output

The function returns a signed 32-bit value selected as follows:

- Ordinarily, the lesser of the observed buffered count and the requested amount, using signed comparison.
- If the transfer path is skipped and the observed buffered count is zero, the value read from context offset +0x1c.

There is no distinct established error-result convention.

### Preconditions

The context and descriptor must support the accesses described here. Entering the function requires readable context fields and a writable status field even if the destination is zero or the requested amount is nonpositive.

Executing the transfer path additionally requires whatever D-01 demands of its arguments. The descriptor count must be writable. Depending on the selected adjustment mode, either the descriptor data-address field must be writable or the relevant source-buffer bytes must be readable and writable.

No null-context, null-descriptor, address-range, alignment, capacity, or destination-size validation is visible.

## Behavior

### 1. Capture the descriptor and clear entry status

The function first reads the descriptor address from context offset +0x20.

It then reads the 32-bit status field at context offset +0x14, clears its low four bits, and writes the resulting value back to the same field. This cleared value is also retained for a possible later empty-buffer status write.

The count is read from the captured descriptor only after this status write.

This order is significant if the status field aliases descriptor storage: the count used for the signed comparison is the value observed after the status clear, not necessarily the count present at function entry.

### 2. Select the effective amount

Let the **observed count** be the signed 32-bit count read at this point.

The **effective amount** is the signed minimum of the requested amount and the observed count. There is no independent clamp to zero.

Consequently:

- A negative request can produce a negative effective amount.
- A negative count can produce a negative effective amount even for a positive request.
- The effective amount cannot exceed the observed count under signed ordering.

The decision to transfer requires both:

- A nonzero destination value.
- A strictly positive effective amount.

A null destination does not, by itself, force the return value to zero.

### 3. Handle the skipped-transfer path

If either transfer condition is false, D-01 is not called and the normal count-reduction and buffer-adjustment operations are skipped.

If the observed count is nonzero, the function returns the effective amount.

If the observed count is zero, the function reads the signed 32-bit field at context offset +0x1c and uses that value as its return value, replacing the effective amount. This replacement occurs even if the requested amount was negative.

If this empty-buffer result is nonzero, the function also writes the retained cleared-status value with hexadecimal 9 added by bitwise OR to context offset +0x14. The resulting low nibble is exactly 9. The other bits come from the retained entry-time status snapshot, not from a fresh status read.

If the empty-buffer result is zero, there is no second status write.

### 4. Invoke the transfer dependency

For a nonzero destination and positive effective amount, the function reads the data address from descriptor offset +0x04 and invokes D-01 with three arguments, in this order:

1. Destination value.
2. Descriptor data address.
3. Effective amount.

The dependency’s return value, if any, is ignored.

The established fact is the invocation and its arguments. Successful copying, overlap support, failure handling, ownership behavior, and preservation of caller-accessible memory are not established by this function alone.

### 5. Reduce the live descriptor count

After D-01 returns normally, the function rereads the count from the captured descriptor, subtracts the effective amount, and writes the result back.

This is not necessarily a subtraction from the earlier observed count. If D-01 changes the descriptor count, that changed value participates in the subtraction.

The effective amount itself remains the value selected before the dependency call.

### 6. Choose the adjustment mode using live status

After updating the count, the function rereads the context status field and examines mask 0x200.

Thus, the adjustment mode is selected from post-dependency state. The entry-time mode is not authoritative if D-01 changes that bit.

#### Bit 9 clear: forward byte compaction

The function reads the descriptor data address once for this compaction operation.

Starting at byte offset zero, it repeatedly:

- Checks whether the current signed index is less than the live descriptor count.
- Reads a byte at the captured data address plus the effective amount plus the index.
- Writes that byte at the captured data address plus the index.
- Advances the index by one.

The descriptor count is consulted again for each continuation check. The data address used by the compaction operation is not refreshed on each iteration.

Under ordinary nonaliasing conditions with a stable, nonnegative remaining count, this shifts the remaining bytes downward by the effective amount. If the remaining count is zero or negative, no compaction byte accesses occur.

No clearing of the old tail bytes is visible.

#### Bit 9 set: data-address advancement

The function reads the current descriptor data address, adds the effective amount, and writes the result back to descriptor offset +0x04.

It does not perform the byte-compaction loop in this mode.

### 7. Return

After either adjustment strategy, the function returns the effective amount selected before D-01.

It does not inspect a dependency result, verify destination contents, or replace the return value with the updated descriptor count.

## Side effects

### Unconditional effects

For valid entry storage, every invocation:

- Reads the context’s descriptor address.
- Reads and writes the context status field.
- Reads the descriptor count.

Clearing the low status nibble is therefore observable even when no transfer occurs.

### Conditional effects

On the empty-buffer path, the function reads context offset +0x1c. A nonzero value causes a second status write.

On the transfer path, the function:

- Invokes D-01.
- Reads and writes the descriptor count after that invocation.
- Rereads context status.
- Either reads and writes buffer bytes or reads and writes the descriptor data address.

### Ownership and lifetime

No direct allocation, deallocation, or ownership transfer is visible in F-6aafd6657d59.

This does not establish that D-01 allocates nothing, releases nothing, or preserves the lifetime of supplied storage. Normal continuation after D-01 requires the subsequently accessed context, descriptor, and buffer storage to remain valid.

### Aliasing and reentrancy

If the destination, source buffer, descriptor, or context overlap, writes may affect later reads. Relevant ordering includes:

- The entry status write precedes the first descriptor-count read.
- D-01 precedes the count reread and mode reread.
- The count update precedes the mode reread.
- Compaction proceeds in increasing byte-offset order and rereads its count bound.

## Acceptance examples

These are conditional acceptance cases derived from static evidence. They are not runtime observations.

Unless otherwise stated, assume valid, nonoverlapping storage, representable arithmetic, and a D-01 implementation that copies the requested bytes without changing the context or descriptor.

### Partial consumption with compaction

Given a descriptor count of 5, source bytes “ABCDE,” a nonzero destination, a requested amount of 2, and status bit 9 clear:

- The entry status low nibble is cleared.
- D-01 receives the destination, the source address, and amount 2.
- The count becomes 3.
- Compaction writes “CDE” into source offsets 0 through 2, in that order.
- The data-address field is not explicitly updated by the compaction path.
- The return value is 2.

No assertion is made about clearing source offsets 3 and 4.

### Consumption limited by the count

Given count 3 and request 8 with a nonzero destination:

- The effective amount is 3.
- D-01 is called with amount 3.
- The count becomes zero.
- In compaction mode, there are no compaction byte accesses.
- In advancement mode, the data address advances by 3.
- The return value is 3.

The empty-buffer result field is not consulted merely because this transfer leaves the count at zero.

### Null destination with available data

Given count 5, destination zero, and request 2:

- D-01 is not called.
- No explicit count reduction or buffer adjustment occurs.
- The low status nibble is still cleared.
- The return value is 2, not zero.

### Nonpositive request with nonzero count

Given count 5 and request −2:

- The effective amount is −2.
- No transfer occurs, even with a nonzero destination.
- The function returns −2.

Given count −3 and request 5, it likewise skips transfer and returns −3.

### Empty count with a nonzero alternate result

Given observed count zero, context offset +0x1c equal to 7, and initial status 0x000002AF:

- The first status write is 0x000002A0.
- D-01 is not called.
- The later status write is 0x000002A9.
- The return value is 7.

The same replacement rule applies if the request is negative. A nonzero negative alternate result also causes the hexadecimal-9 status write.

### Empty count with zero alternate result

Given observed count zero and context offset +0x1c equal to zero:

- The function returns zero.
- The low status nibble remains cleared.
- No second status write occurs.

### Dependency-modified state

Given initial count 5, request 2, and a nonzero destination, suppose D-01 returns after changing the descriptor count to 9 and setting status bit 9.

Then, provided all later accesses remain valid:

- The caller subtracts 2 from the live count 9, storing 7.
- The caller selects address advancement from the live status bit.
- It advances the then-current data address by 2.
- It returns 2.

This distinguishes the established live-state behavior from a contract that incorrectly assumes dependency preservation.
