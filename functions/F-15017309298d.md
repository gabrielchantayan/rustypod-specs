# F-15017309298d

## Purpose

F-15017309298d conditionally prepares an operation on a resolved schema object, then performs common source-descriptor cleanup and, when a destination name was obtained, allocation-accounting and release operations.

**Established static behavior:** ordered lookups and rejection gates, existing-name restriction, destination validation, conditional operation emission, formatting calls, a context-counter update, and cleanup with explicit metadata and accounting accesses.

**Inferred intent:** schema-object renaming. This interpretation follows from the name operands, diagnostic identifiers, `sqlite_` restriction, `sqlite_sequence` lookup, and update-oriented formatting identifier. Successful renaming, generated statements, and eventual database effects are not established.

The interface has no explicit return value or success indicator. Early rejection, unavailable resources, and completed preparation can all reach ordinary cleanup.

## Interface

### Arguments and widths

The function accepts three arguments:

1. **Operation context:** a pointer whose first 32-bit word supplies a database-like pointer. A 32-bit field at byte offset `0x48` is conditionally incremented.
2. **Source descriptor:** an address passed to source resolution and common cleanup. Resolution consumes its 32-bit fields at offsets `0x0C` and `0x08`.
3. **Destination-name input:** an opaque 32-bit value passed to F-e7c4e7dd076d.

Pointers and general operands have 32-bit representations in the supplied material. Flags are read as bytes. Two allocation selectors are read as unsigned 16-bit quantities.

No local bounds, pointer-validity, selector-range, or alignment checks are established beyond the explicit header checks. Invalid memory is not converted into a recoverable local diagnostic.

## Behavior

### Entry gate and resolution

The function captures the context’s database pointer and initially retains no destination name.

A nonzero byte at offset `0x1E` of that captured database object skips resolution and all substantive preparation.

Otherwise, F-3747d6ba198f receives the context, zero, the source descriptor’s word at `0x0C`, and its word at `0x08`. A zero result goes directly to common cleanup.

For a nonzero resolved object, F-49f750c2c596 receives a **fresh read** of the context’s database pointer and the resolved object’s word at `0x4C`. Its result is retained as a slot index.

After that call, the function reads the array pointer at offset `0x08` of the **entry-captured** database object. The first word of the entry selected by index times `0x18` becomes the retained database-associated value.

The database pointer supplied to slot lookup can therefore differ from the object supplying the array. The array pointer itself is read after slot lookup, not at entry.

### Destination construction and conflict checks

F-e7c4e7dd076d receives the entry-captured database pointer and destination-name input. Its result is retained for cleanup. Zero ends substantive processing.

For a nonzero destination name:

- F-4e77314e8c36 receives the entry-captured database pointer, destination name, and retained database-associated value.
- Only if its result is zero does F-cf5dd1ff88c3 receive those same operands.
- A nonzero result from either lookup selects a static diagnostic payload and a call to F-2022b0f73f3b with the context and that payload, followed by cleanup.

The first lookup suppresses the second when it finds a conflict. No separate name argument is visibly supplied to the diagnostic call.

The diagnostic identifier is truncated. Its complete wording, including whether it explicitly names both table and index conflicts, is **not established**. “Conflict diagnostic” describes the branch condition, not a reconstructed message.

### Existing-name restriction

When both conflict results are zero, F-1cb585febd84 receives the resolved object’s existing-name value. Its result is compared with seven as an unsigned 32-bit quantity.

A result below seven skips prefix comparison. Otherwise, F-abcb7c332db0 receives a fresh existing-name read, the static `sqlite_` prefix, and seven.

A zero comparison result selects the table-may-not-be-altered diagnostic payload and cleanup. A nonzero result permits destination validation.

This check concerns the existing name, not the destination. Measurement units, encoding, and comparison case sensitivity depend on the callees. The two existing-name reads need not produce the same value if the measuring dependency changes the object.

### Destination validation and object rejection

F-1f4e8061d0b5 receives the context and destination name. A nonzero result goes directly to cleanup without another diagnostic from this function.

Only after a zero validator result does the function read the resolved object’s word at `0x18`. Nonzero selects the view-may-not-be-altered diagnostic payload. Zero permits preparation.

Thus, destination-validation failure suppresses both the view-field read and the local view diagnostic.

## Side effects

### Diagnostics and ownership boundaries

Conflict rejection, restricted-existing-name rejection, and view rejection select calls to F-2022b0f73f3b. The complete rendered diagnostics are unavailable; the conflict payload identifier is specifically truncated.

Every ordinary cleanup path first passes the source descriptor to F-ed9979230848, including initial-gate and resolution-failure paths. This establishes the call, not whether that dependency frees nested storage or consumes ownership.

Likewise, F-94cb53877c15’s use of the optional result does not establish how that result was allocated or what ownership rules apply.

No explicit rollback reverses earlier dependency effects after a later gate fails.

### Accounting-pointer captures and ordered updates

Immediately after source cleanup returns, the function reads the global accounting pointer and retains this **initial snapshot**. This read occurs even when no destination name exists. A zero destination name then returns without reading its allocation metadata.

For a nonzero destination name, the observable sequence is:

1. Read the 32-bit displacement four bytes before the name.
2. Subtract that displacement from the name address to obtain the allocation base.
3. Read the 32-bit accounting size eight bytes before that base.
4. **Reread the global accounting pointer**, then read the low word at offset `0x38` through that pointer.
5. **Separately reread the global accounting pointer**, and retain the address at offset `0x3C` as the high-word read address. The high-word contents are not yet read.
6. **Separately reread the global accounting pointer again**, and write the saved low word minus the accounting size at offset `0x38` through this pointer.
7. Read the high word through the previously captured high-word read address.
8. Write the adjusted high word at offset `0x3C` through the **initial snapshot**, not through a newly loaded pointer or necessarily through the high-word read address.
9. Call F-2fd8826557a4.
10. Load the current allocator-state pointer through a separate global pointer.

There are therefore four accounting-pointer observations: the initial snapshot and three later reloads. Their targets are not required to be identical. The low-word read, high-word address capture, low-word write, and high-word write must not be collapsed into updates on one assumed-stable object.

The high-word adjustment subtracts the arithmetic sign extension of the accounting size interpreted as signed 32-bit, plus a borrow of one when the saved unsigned low word is less than the unsigned size. The sign-extension term is zero or all ones. Word arithmetic therefore does not represent unrestricted unsigned 64-bit subtraction for sizes with bit 31 set.

The high-word contents are read **after** the low-word write. No non-aliasing guarantee is established: that write may affect the captured high-word location, the initially captured object, the global pointer storage, or other later-observed storage if the supplied addresses overlap. The retained addresses and values still determine the accesses described above.

### Special base and header validation

If the recovered allocation base equals address value eight, block-release processing stops after accounting, F-2fd8826557a4, and the allocator-state load.

Otherwise, the header address is base minus `0x10`. The function reads the header to check for zero. If nonzero, it reads the header again to check its low bit. Zero on the first check or a set low bit on the second selects F-a817d8d58c10. The supplied representation marks that call as non-returning.

### Allocator updates and release calls

For an accepted header, F-c0fc6d033caa receives the captured allocator-state pointer. After it returns:

1. Read the unsigned 16-bit selector at allocation base minus `0x0C`.
2. Reread the header and retain its value masked with `0x3FFFFFFC`.
3. Reduce the allocator counter at `0x224 + 4 × first selector` by that retained size.
4. Reduce the counter at `0x30C` by the same size.
5. Only now read the unsigned 16-bit selector at allocation base minus `0x0A`.
6. Reduce the counter at `0xE0 + 4 × second selector` by the retained size.
7. Reduce the counter at `0x220` by that size.
8. Call F-09dcb55e8e0a.
9. Decrement the counter at `0x310 + 4 × returned index`.
10. Decrement the counter at `0x390`.
11. Reread the header, mask it with `0x3FFFFFFC`, and reduce the counter at `0x08` by this fresh size.
12. Call F-cc6c9b4a0f68 with the captured allocator-state pointer and header address.
13. Call F-e586bff64fb7 with that same allocator-state pointer.

The first four size reductions use one retained size. The final reduction uses a later header read. The second selector is not captured alongside the first: intervening counter writes can affect it through aliasing. No dependency is assumed to preserve globals, counters, metadata, or headers.

## Acceptance examples

These are conditional static-contract examples, not executed tests. Selected storage must be valid, and dependencies must return except on the invalid-header path.

1. **Initial gate set:** Resolution and destination construction are skipped. Source cleanup and the initial accounting-pointer snapshot still occur.

2. **Resolution returns zero:** Slot lookup and destination construction do not occur. Source cleanup remains required.

3. **First conflict found:** The second lookup is suppressed. The selected conflict diagnostic precedes cleanup. Its complete text is not an acceptance requirement.

4. **Restricted existing name:** With both conflicts absent, a measure of seven and zero prefix-comparison result reject before destination validation. A measure below seven suppresses prefix comparison.

5. **Validator rejects:** A nonzero validator result suppresses the view-field read and local view diagnostic, irrespective of the field’s potential value.

6. **Captured emission conditions:** If both captured conditions are nonzero, later changes to their source fields do not suppress emission. Both emission calls receive the saved incremented counter.

7. **Optional formatting result:** A nonzero F-a7935d637b3c result selects nine post-payload operands, including six destination-name operands. F-94cb53877c15 follows formatting; final preparation follows that handling call.

8. **Different accounting-pointer observations:** If the initial snapshot, low-word read, high-word address capture, and low-word write designate different objects, each access uses its specified source. The high-word write still targets the initial snapshot.

9. **Aliased accounting locations:** If the captured high-word read address equals the low-word write address, the high-word read observes the location after that write, subject to any other permitted mutation. It is not an earlier high-word snapshot.

10. **Signed accounting size:** With stable, nonoverlapping accounting storage, size `0xFFFFFFFF`, saved low word zero, and saved high word five, the low result is one and the high result remains five: sign extension and borrow cancel.

11. **Interleaved selectors:** First selector two and second selector three select counters at `0x22C`, `0x30C`, `0xEC`, and `0x220`. The second selector is read after the first two reductions.

12. **Changing header or special base:** A header mutation during F-c0fc6d033caa affects the first retained size; a mutation during F-09dcb55e8e0a can independently affect the final size. Base eight skips header processing entirely. A rejected header instead reaches the non-returning invalid-header dependency after initial accounting.
