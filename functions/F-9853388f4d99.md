# F-9853388f4d99

## Purpose

F-9853388f4d99 selects between direct delegation and a staged operation using bit `0x10` of a caller-supplied control word.

The staged operation obtains local working state from preparation, invokes processing with a local position pointer, adjusts an extent using the position change during processing, and selects one of two acceptance conditions:

- The adjusted extent must equal zero.
- An optional final-validation dependency must return nonzero.

Staged acceptance commits the current local position to caller storage and returns one. Failures have different observable effects: some report and return zero without explicit cleanup; preparation has a distinguished all-ones result; two late rejection paths report, invoke cleanup, clear the caller’s primary slot, and return zero.

The data format and resource semantics are unknown. “Position,” “extent,” “indicator,” “report,” and “cleanup” describe observable roles, not established domain meanings.

## Interface

The function receives six arguments and returns a 32-bit value.

| Argument | Representation | Observable role |
|---|---|---|
| Primary slot | Pointer to a 32-bit word | Pointer checked for null; forwarded to processing and cleanup; explicitly cleared on late rejection. |
| Caller position | Pointer to a signed 32-bit integer | Read before dispatch; forwarded directly on the direct path; explicitly overwritten on staged acceptance. |
| Operation value | Opaque 32-bit value | Forwarded to direct processing or staged preparation. |

| Context B | Opaque 32-bit value | Forwarded to direct processing, staged preparation, and staged processing. |

### Storage requirements

If the primary-slot pointer is null, the function returns zero without explicitly dereferencing any other argument.

Otherwise:

- Caller-position storage must permit a 32-bit read before dispatch.
- The first control word must permit a 32-bit read.
- Staging additionally requires a readable second control word, four bytes after the first.
- Staged acceptance requires writable caller-position storage.
- Late rejection requires writable primary-slot storage after cleanup returns.
- Dependencies may require additional accessible storage or impose other preconditions; those requirements are unavailable here.

The staged path provides a signed 32-bit local position, a signed 32-bit local extent, and two separate four-byte indicator areas. Only the first byte of each indicator area is inspected by this function. No interpretation is established for the remaining bytes.

The function performs no visible pointer validation beyond the primary-pointer null check. No bounds checking, alignment repair, byte-order conversion, or serialization is established.

## Behavior

### Initial reads and dispatch

The initial gate tests the primary-slot pointer itself, not the word it addresses.

For a non-null primary pointer, the function first copies the caller’s signed 32-bit position into local working storage. It then reads the first control word and tests bit `0x10`.

If that bit is clear, F-5240b5dfa2f6 receives the original six arguments, including the original caller-position pointer. Its result is returned unchanged. This function performs no subsequent explicit reporting, cleanup, or position commit on that path.

The initial position read still occurs before direct dispatch, even though the local copy is not supplied to the direct call.

If bit `0x10` is set, execution continues through staging.

### Staged preparation

F-38f7a73546d9 receives eleven arguments in this order:

1. Address of the local signed 32-bit extent.
2. Zero.
3. Zero.
4. Address of the first four-byte indicator area.
5. Address of the second four-byte indicator area.
6. Address of the local signed 32-bit working position.
7. The operation value.
8. The second control word.
9. The first control word masked with `0xc0`.
10. Context A.
11. Context B.

The first control word is therefore read for dispatch and again to obtain the masked preparation argument. The second control word and the masked first word are supplied as values, not as addresses of those individual words. No relative evaluation order is established between these separate argument reads.

The extent and both indicator areas are uninitialized before preparation. The working position already contains the initial caller-position value. Defined downstream behavior requires that every subsequently consumed local value be established by the time it is read.

Immediately after preparation returns, the function saves the current working position. This saved post-preparation position is the baseline for the later movement calculation. Changes made to the position during preparation are not included in that later difference.

Preparation’s signed 32-bit result selects the next action:

- **Zero:** call F-4fc89ec41a6d with `(0x0d, 0x84, 0x3a, 0, 0)`, then return zero.
- **Signed `−1`:** return `0xffffffff` without an explicit report, cleanup call, or caller-position commit.
- **Any other nonzero value:** inspect the first byte of the second indicator area.

If the second indicator byte is zero, the function reports `(0x0d, 0x84, 0x78, 0, 0)` and returns zero. Otherwise, staged processing proceeds. Any nonzero byte passes this gate; equality to one is not required.

### Staged processing

F-5240b5dfa2f6 receives:

1. The original primary-slot pointer.
2. The address of the local working position.
3. The local extent’s value when the call argument is evaluated.
4. The original control-storage pointer.
5. Zero.
6. Context B.

Unlike direct dispatch, this call receives a local position pointer, the extent in place of the original operation value, and zero in place of Context A.

If processing returns zero, the function reports `(0x0d, 0x84, 0x3a, 0, 0)` and returns zero. It does not explicitly invoke cleanup, clear the primary slot, or commit the working position on that branch.

Any nonzero processing result proceeds to extent adjustment. In particular, `0xffffffff` is accepted as nonzero here; preparation’s special handling of signed `−1` does not apply to processing.

### Post-processing extent adjustment

After a nonzero processing result, the function calculates:

**Adjusted extent = current post-processing extent − (post-processing working position − saved post-preparation position).**

The starting extent is the value present in local extent storage after processing returns. It is not necessarily the value preparation originally produced or the value supplied as the processing argument.

Preparation receives the address of the local extent. Its implementation is unknown, so it could retain that address and make it available to effects occurring during processing. The visible body provides no guarantee that the extent remains unchanged across the processing call. Passing its value to processing does not establish such a guarantee.

Subject to representable signed 32-bit arithmetic:

- Forward position movement subtracts from the current post-processing extent.
- Backward movement adds to that current extent.
- No movement leaves that current extent unchanged.

These statements are relative to the extent present after processing, not necessarily the prepared extent.

The subtraction establishing movement and the subtraction establishing the adjusted extent use signed 32-bit operands in the supplied representation. No wider intermediate, overflow check, saturation, or guaranteed wrapping rule is established. The contract does not assign a numerical result where either subtraction exceeds the representable signed 32-bit range.

There is no visible requirement that movement be forward, that the extent be nonnegative, or that movement stay within an earlier extent.

### Final selection and acceptance

After extent adjustment, the function reads the first byte of the first indicator area. This is its value at that point, after processing; it is not guaranteed to remain the byte originally established by preparation.

If the first indicator byte is zero:

- An adjusted extent equal to zero is accepted.
- Any other adjusted extent causes late rejection with reason `0x77`.

If the first indicator byte is nonzero:

- F-04d7b0f7c6e9 receives the address of the local working position.
- A nonzero result accepts.
- A zero result causes late rejection with reason `0x89`.

On the nonzero-indicator branch, the adjusted extent is computed but not used as an acceptance condition. A nonzero or negative adjusted extent does not independently reject that branch. This does not remove the requirement that the preceding arithmetic have defined behavior.

On acceptance, the function writes the current local working position to caller-position storage and returns one. If final validation was invoked, the committed position is the value present after that dependency returns. It may differ from the position produced by processing.

### Late rejection

Both late rejection cases perform the following sequence:

1. Report through F-4fc89ec41a6d using `(0x0d, 0x83, reason, 0, 0)`.
2. Invoke F-a8ecb9fc98cf with the original primary-slot and control-storage pointers.
3. Write a 32-bit zero to the primary slot.
4. Return zero.

The reason is `0x77` for a failed exact-extent check or `0x89` for a zero final-validation result.

There is no explicit caller-position commit on either rejection path. The final primary-slot write occurs after cleanup returns and overwrites any value cleanup left there, provided the slot remains valid and writable.

## Acceptance examples

These are conditional consequences of static control flow, not executed tests. Unless specified otherwise, storage is valid and non-overlapping, dependencies return normally, downstream local reads have established values, and both arithmetic subtractions are representable.

5. **Exact consumption with unchanged extent.**

The first indicator is zero when inspected. The adjusted extent is zero, so the function commits `112` and returns one.

6. **Remaining extent with unchanged extent storage.**  
   Under the same preparation conditions, processing leaves extent `12` and position `108`. With a zero first indicator, the adjusted extent is `4`. The function reports `(0x0d, 0x83, 0x77, 0, 0)`, invokes cleanup, clears the primary slot, and returns zero without an explicit position commit.

7. **Extent changed during processing.**  
   Preparation leaves position `100` and supplies extent `12` to processing. Suppose effects during processing change local extent storage to `8`, processing leaves position `108`, and its result is nonzero. With a zero first indicator, the adjusted extent is `8 − (108 − 100) = 0`; the function accepts and commits `108`. This outcome is conditional on that storage change being possible under the dependency implementations.

9. **Validation rejects.**

10. **All-ones processing result.**  
    A processing result of `0xffffffff` proceeds to extent adjustment and final selection. It does not itself cause the function to return `0xffffffff`.
