# F-9745300f5090

## Purpose

F-9745300f5090 initializes selected fields of a caller-supplied state object from a configuration record, validates two numeric selectors, and rejects unsupported types. On a supported path, it calls F-6d8c85350b66 to select between cleared and populated parameter state, updates an externally addressed counter, and calls F-266a29fc8dc5 before returning success.

Initialization is partial and nontransactional. Every explicit rejection occurs after state writes; no rollback is present. Even successful execution does not locally initialize every byte of the state object.

The interpretation of this operation as configuration of an operational instance, and of its derived fields as range-like parameters, is inferred intent. The established contract is expressed in offsets, widths, observations, and effects rather than application-specific field names.

### Numeric validation

The function first observes configuration word `0x08` as unsigned, then clears state byte `0x40`.

If the first observation is at most 8, this check makes no further change to state `0x3C`. Otherwise, configuration `0x08` is read again:

- A second observation greater than 16 causes immediate rejection.
- A second observation at most 16 causes state word `0x3C` to be written as one.

Thus the accepted stable range is 0–16, inclusive. There is no positive lower bound. The two comparisons do not necessarily use the same observation: a first observation of 9 followed by a second observation of 0 still causes the write of one.

Configuration word `0x0C` is then observed:

- An observation equal to 1 causes state byte `0x41` to become one.
- Otherwise, state `0x41` is cleared before another observation of configuration `0x0C`. If that second observation is not 2, the function rejects. If it is 2, state word `0x3C` is read, incremented, and written back.

Under stable, disjoint storage without relevant external mutation, the resulting mode word is:

| Configuration `0x08` | Configuration `0x0C` | State `0x3C` |
|---|---:|---:|
| 0–8 | 1 | 0 |
| 9–16 | 1 | 1 |
| 0–8 | 2 | 1 |
| 9–16 | 2 | 2 |

The increment is represented as signed 32-bit arithmetic. The ordinary values above do not overflow; arbitrary intervening changes to the state word can invalidate that guarantee.

After validation, configuration `0x0C` is read again and copied to state word `0x14`. That copy need not equal the observation that passed validation.

### Dependency-selected parameter state

F-6d8c85350b66 is called with configuration base plus `0x40`. Its 32-bit result is tested only for zero versus nonzero. A nonzero result is not a local error.

**Zero result:** state byte `0x28` is cleared, followed by state words `0x2C`, `0x30`, `0x34`, `0x38`, `0x7C`, and `0x80`, in that order. No parameter words are directly read from the configuration in this branch.

**Nonzero result:** state byte `0x28` becomes one. Configuration word `0x40` is copied to state `0x2C`. Next, configuration words `0x44`, `0x48`, and `0x50` are read in that order and copied respectively to state `0x30`, `0x34`, and `0x38`. Each of these last three configuration observations is retained.

The function then reads state byte `0x58`. If it equals 7, state `0x30`, `0x34`, and `0x38` are overwritten, in that order, with the corresponding retained configuration observations shifted left by one. The source observations are not reread from either object for these shifts.

The shift decision occurs after F-6d8c85350b66. It depends on current state `0x58`, not directly on either configuration type observation. The dependency is not known to preserve that byte.

The shifts are represented on signed 32-bit values. Nonnegative inputs through `0x3FFFFFFF` have an unambiguous doubled result. Negative inputs and values whose doubling exceeds signed range have target semantics not established by the supplied evidence.

After any scaling, state word `0x78` is read as unsigned and retained as the base for both derived words:

- State `0x30` is read and added to the retained base. The 32-bit sum is written to state `0x7C`, with unsigned wrapping modulo \(2^{32}\).
- State `0x34` is read as unsigned for comparison with the retained base.
- If that comparison observation is greater than the base, state `0x34` is read **again**. This second observation, minus the retained base, supplies the unsigned 32-bit difference written to state `0x80`.
- Otherwise, zero is written to state `0x80`, without the subtraction read.

The successful comparison constrains only the first observation of `0x34`. It does not establish that the actual subtraction observation exceeds the base. If the value changes between observations, subtraction can underflow and wraps modulo \(2^{32}\). With stable storage, this operation behaves as a difference clamped to zero; without stability, that description is insufficient.

Configuration word `0x4C` is not directly read by this function.

### Successful completion and counter-pointer capture

After either parameter branch, the completion sequence is:

1. Read and retain the external global counter pointer.
2. Clear state byte `0x8C`.
3. Read the counter through the retained pointer, increment it, and write the result through that same pointer.
4. Obtain the external first argument for F-266a29fc8dc5 and call it with that argument and a second argument of zero.
5. Return zero if the call returns normally.

The counter pointer is acquired **before** the state-byte clear, while the counter value is read **after** it. The pointer is not reacquired between those operations.

This distinction matters when storage aliases. If clearing `0x8C` changes the storage from which the external pointer was obtained, the local counter operation still uses the captured pointer. If `0x8C` overlaps the counter itself, the counter read observes storage after the clear, subject to target representation and access rules.

The counter increment is represented as signed 32-bit arithmetic. Its behavior at signed overflow is unresolved. F-266a29fc8dc5’s result is ignored; no local writes follow that call.

## Acceptance examples

These are conditional static consequences, not executed tests. Unless a scenario specifies changing observations or aliasing, assume valid disjoint storage, stable relevant memory, normally returning dependencies without relevant mutations, and no signed overflow.

1. **Accepted lower boundary.** Type 0, configuration `0x08 = 0`, configuration `0x0C = 1`, and a zero result from F-6d8c85350b66 produce local success. 2. **Accepted upper boundary.** Type 5 with configuration `0x08 = 16` and `0x0C = 2` produces state `0x3C = 2` and `0x41 = 0`, and can reach success.

3. **First-selector rejection.** Stable configuration `0x08 = 17`, or `0xFFFFFFFF` interpreted unsigned, causes rejection after state `0x40` is cleared. This invocation has not yet written `0x41`. Common and initial type-dependent writes remain.

4. **Second-selector rejection.** With configuration `0x08 = 9` and stable `0x0C = 3`, state `0x3C` becomes one and `0x41` becomes zero before rejection. The copy to state `0x14` is not reached.

5. **Late unsupported type.** Type 4 with valid numeric selectors copies configuration bytes `0x10` and `0x11` to state `0x42` and `0x43`, performs the remaining initialization, and then rejects. State `0x78` is not locally initialized.

6. **Type-7 scaling.** With a nonzero first dependency result, state `0x58 = 7`, configuration words `0x44 = 3`, `0x48 = 10`, `0x50 = 4`, and state `0x78 = 5`, the derived state is `0x30 = 6`, `0x34 = 20`, `0x38 = 8`, `0x7C = 11`, and `0x80 = 15`.

8. **Changed subtraction observation.** Where the execution environment permits these observations, a retained base of 5, comparison observation of 10, and subtraction observation of 3 produce state `0x80 = 0xFFFFFFFE`. The comparison passes, but the later unsigned subtraction underflows. This example does not establish that unsynchronized concurrent mutation is valid on the target.

9. **Wrapping addition.** With no scaling, state `0x30 = 0xFFFFFFFE` and retained base 5 produce state `0x7C = 3`.

10. **Captured counter pointer.** Suppose the counter-pointer storage overlaps state byte `0x8C`, but its captured target is a distinct valid counter containing 12.
