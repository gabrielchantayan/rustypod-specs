# F-6e3b7d6b0f05

## Purpose

F-6e3b7d6b0f05 wraps a delegated operation with conditional handling of a saved byte region and an output-count adjustment.

The established behavior consists of three principal paths:

- A zero-control path that writes a zero output count and returns success without consulting the context.
- A flag-selected path that forwards all five inputs to F-3feba7061ccf and returns its result unchanged.
- A wrapper-managed path that validates a byte count, conditionally invokes a transfer helper before delegation, and updates context state and the output count after successful delegation.

The likely intent is to prepend previously saved bytes and, under some conditions, retain a trailing region for a later operation. That interpretation is inferred from addresses, counts, and state transitions. The supplied evidence does not independently establish the transfer helper’s semantics or the larger protocol.

## Interface

### Inputs and result

The interface has five positional inputs:

| Position | Contract-level name | Established representation and use |
|---|---|---|
| 1 | Context | Address of a mutable structure accessed through 32-bit words. Also passed to F-3feba7061ccf. |
| 2 | Output address | A 32-bit value passed to dependencies and used in address arithmetic. |
| 3 | Count location | Address of a mutable 32-bit quantity. The wrapper writes or adjusts this quantity on some paths. |
| 4 | Auxiliary value | An opaque 32-bit value forwarded unchanged. |
| 5 | Control value | A 32-bit integer tested only for equality to zero by this wrapper, then forwarded unchanged when delegation occurs. |

The result is a 32-bit value:

- The zero-control path returns 1.
- The flag-selected path returns the exact 32-bit result from F-3feba7061ccf.
- The wrapper-managed path returns 0 when F-3feba7061ccf returns zero, and 1 after any nonzero result.
- An oversized byte count invokes a dependency represented as nonreturning.

A negative control value is nonzero and therefore does not select the zero-control path. No positive-only constraint is established.

### Context layout used by this function

Offsets below are byte offsets from the supplied context address. Each listed scalar access is 32 bits.

| Offset | Role established by use |
|---|---|
| 0 | Address of another object. On the wrapper-managed path, its 32-bit field at offset 4 supplies a byte count. |
| 12 | State field read after successful delegation when the saved byte count is at least 2. |
| 92 | Flags word. Bit mask 0x100 selects direct delegation. |
| 100 | Pending-state field. Its initial value controls the pre-delegation transfer and the final count adjustment. It is later set to either 0 or 1. |
| 108 | Beginning of an inline region supplied as a transfer endpoint. |

No other context fields are directly accessed by the wrapper. Dependencies may access additional fields.

The inline region’s allocation size is unknown. The wrapper permits byte counts from 0 through 32, inclusive, but that check does not prove that every supplied context has enough storage.

### Preconditions

Preconditions are path-dependent:

- With a zero control value, the count location must permit a 32-bit write. The wrapper does not itself require a readable context on that path.
- With a nonzero control value, the context flags word must be readable.
- On the wrapper-managed path, the context’s first word and the referenced object’s field at offset 4 must be readable.
- Later context fields and the count location must be readable or writable as required by the selected branch.
- Any dependency-specific validity, capacity, alignment, overlap, and ownership requirements remain undocumented.

The wrapper performs no explicit null-pointer, output-capacity, overlap, or count-underflow checks.

## Behavior

### 1. Zero control value

When the fifth input equals zero, the wrapper:

1. Stores the 32-bit value 0 at the count location.
2. Returns 1.

It does not directly read the context, inspect flags, obtain a byte count, or invoke any dependency on this path.

If the count location aliases other caller-visible state, the zero store affects that state normally. No non-aliasing requirement is established.

### 2. Flag-selected direct delegation

For a nonzero control value, the wrapper reads the context flags word at offset 92.

If bit 0x100 is set, it invokes F-3feba7061ccf with all five original inputs and immediately returns that dependency’s result unchanged.

Consequences:

- The wrapper does not read the byte-count field through context offset 0.
- It does not apply the upper bound of 32.
- It does not directly read or update the pending-state field.
- It does not directly adjust the count location.
- A nonzero dependency result is not normalized to 1.

These statements concern wrapper accesses only. F-3feba7061ccf may perform additional reads, writes, or calls.

### 3. Byte-count acquisition and bound check

If bit 0x100 is clear, the wrapper reads the address stored at context offset 0, then reads a 32-bit unsigned byte count at offset 4 of the referenced object.

The wrapper retains this byte count across subsequent calls. It does not reload the count after delegation.

If the unsigned count exceeds 32, the wrapper invokes the nonreturning diagnostic dependency described below. This occurs before the pending-state field is read and before either the transfer helper or F-3feba7061ccf is called.

The valid range established by this check is 0 through 32 inclusive. In particular, zero is accepted. A bit pattern representing a negative signed 32-bit number is nevertheless a large unsigned count and fails this check.

### 4. Optional pre-delegation transfer

After a successful bound check, the wrapper reads and saves the pending-state field at context offset 100.

If that saved value is nonzero, the wrapper invokes the transfer dependency with these argument positions:

1. The original output address.
2. The address of the context’s inline region at offset 108.
3. The saved byte count.
4. The auxiliary value.
5. The auxiliary value again.

It ignores the dependency’s return value, if any.

After this call, the wrapper advances its local output address by the saved byte count. This advancement is based on the saved count, not a reloaded context value.

The transfer call occurs even when the byte count is zero, provided the saved pending-state value is nonzero. No special zero-length bypass is present.

If the saved pending-state value is zero, the wrapper makes no pre-delegation transfer call and leaves its local output address unchanged.

### 5. Main delegation and failure

The wrapper calls F-3feba7061ccf with:

- The original context address.
- The possibly advanced output address.
- The original count-location address.
- The original auxiliary value.
- The original control value.

If the result is zero, the wrapper immediately returns 0.

On that failure path, the wrapper does not perform its post-delegation pending-state update or final count adjustment. It does not roll back:

- Any pre-delegation transfer effects.
- Any changes made by F-3feba7061ccf.
- Any other dependency effects.

The local advancement of the output address is not itself a write to caller storage, but the advanced address is observable by F-3feba7061ccf.

### 6. Successful post-delegation state update

For any nonzero result from F-3feba7061ccf, the wrapper uses its saved byte count to select the following behavior.

**Byte count below 2**

The wrapper stores 0 at context offset 100. It does not read the context field at offset 12 for this decision.

**Byte count at least 2**

The wrapper reads the current 32-bit field at context offset 12, after F-3feba7061ccf has returned.

- If this field is nonzero, the wrapper stores 0 at context offset 100.
- If this field is zero, the wrapper:
  1. Reads the current count and subtracts the saved byte count.
  2. Stores the resulting 32-bit count.
  3. Stores 1 at context offset 100.
  4. Invokes the transfer dependency with three observed argument positions: the inline-region address, the current count plus the adjusted output address, and the saved byte count.

The transfer dependency’s result is not checked.

The address supplied as the second transfer argument is formed using a count read after the subtraction and pending-state write. If those locations alias, the pending-state write can affect the count used for address formation.

The three-argument invocation and the earlier five-argument invocation target the same transfer dependency in the supplied evidence. Its actual calling contract is not established.

### 7. Final count adjustment and return

After the successful post-delegation branch, the wrapper consults the saved, pre-delegation pending-state value.

If that saved value was nonzero, it reads the current count, adds the saved byte count, and stores the result. This uses the count as it exists after any post-delegation transfer call.

It does not reload the pending-state field to decide whether to perform this addition.

Finally, the wrapper returns 1, regardless of which nonzero value F-3feba7061ccf returned.

### Arithmetic boundaries

The supplied operations use 32-bit quantities. No wider checked arithmetic is visible.

The byte-count check guarantees that the later signed comparison against 2 is applied only to values from 0 through 32. Thus, that comparison introduces no signed-range ambiguity on returning executions.

Count subtraction has no guard requiring the existing count to be at least the byte count. Count addition and address addition have no overflow checks. No saturation, error result, or recovery behavior is established for such cases.

The source representation does not settle language-level overflow or invalid-address behavior. Portable behavior outside valid count and address ranges is therefore documented_only, not guaranteed.

## Side effects

Direct wrapper effects are limited to:

- Reads of the context and referenced byte-count field on the applicable paths.
- Writes to the count location.
- Writes of 0 or 1 to the context pending-state field.
- Calls to dependencies with caller-provided addresses and values.

The wrapper contains no explicit allocation, release, ownership transfer, synchronization, or global-variable access. This does not establish that dependencies lack those effects.

The wrapper retains the byte count and initial pending-state value across calls. Other relevant state is read later:

- The field at context offset 12 is read after successful main delegation.
- Counts used in post-delegation arithmetic are read when needed.
- The final addition reads the count after the optional trailing transfer.

Consequently, dependency mutations can affect later behavior. There is no basis to assume that dependencies preserve globals, leave pointed-to memory unchanged, or retain or release no memory.

No aliasing exclusions are established. The stated read/write order remains relevant when the count location overlaps context fields or transfer regions. Examples below use distinct storage to avoid implying an undocumented non-aliasing guarantee.

## Acceptance examples

These are conditional static acceptance cases, not executed tests.

1. **Zero control with an otherwise unusable context**

   Given a writable count location and a zero control value, the count becomes 0 and the result is 1. The wrapper makes no context read or dependency call.

2. **Direct delegation preserves a noncanonical success result**

   Given nonzero control, flag bit 0x100 set, and F-3feba7061ccf returning 7, the wrapper returns 7. It performs no wrapper-managed count adjustment.

3. **Unsigned count rejection**

   Given nonzero control, the direct-delegation flag clear, and a byte count of 33, the diagnostic dependency is invoked before the pending-state read or main delegation. The same applies to 0xFFFFFFFF.

4. **Main failure preserves earlier effects**

   Given a nonzero initial pending-state value and a valid byte count of 8, the pre-delegation helper is invoked and F-3feba7061ccf receives the output address advanced by 8. If the latter returns zero, the wrapper returns 0 without its post-delegation state update or count adjustment.

5. **Successful trailing-region handling without an initial pending region**

   Assume distinct storage, an initial pending-state value of zero, byte count 8, and successful main delegation leaving count 20 and the field at context offset 12 equal to zero. The wrapper changes the count to 12, sets pending state to 1, and invokes the trailing helper with the inline-region address, the original output address plus 12, and length 8.

   If that helper leaves the count unchanged, the final count is 12.

6. **Both initial and trailing handling**

   Under the preceding assumptions except for an initially nonzero pending-state value, main delegation receives the original output address plus 8. A count of 20 after delegation is reduced to 12, and the trailing helper receives that adjusted output address plus 12.

   If the trailing helper leaves the count unchanged, the final addition restores the count to 20. Pending state remains 1 unless changed through aliasing or dependency effects.

7. **Byte count of 1**

   With successful main delegation and byte count 1, pending state is set to 0 without consulting context offset 12. An initially nonzero pending state still causes the pre-delegation helper call and a final count increment of 1.

8. **Byte count of zero**

   A nonzero initial pending state still causes a zero-length pre-delegation helper call. After successful main delegation, pending state is cleared, and the final arithmetic addition is zero. The helper’s behavior for zero length remains unknown.
