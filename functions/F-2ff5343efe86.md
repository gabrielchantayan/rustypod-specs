# F-2ff5343efe86

## Purpose

F-2ff5343efe86 performs two ordered indirect invocations through dispatch information obtained from the same caller-supplied object address.

Its distinguishing behavior is the handling of one shared input, designated **Shared A**:

- Before the first invocation, Shared A is assigned to a retained destination explicitly represented as four bytes.
- The first invocation receives a separate, direct use of Shared A, not that retained destination.
- The second invocation receives the retained four-byte value, not a fresh use of Shared A.

The declared type and width of Shared A are unknown. Consequently, the capture does **not** establish that Shared A itself is four bytes or that its original value or representation survives assignment unchanged. The conversion, if any, into the retained destination is unresolved.

Each invocation resolves its target independently. Changes made by the first invoked dependency can therefore affect the second target and the second invocation’s final argument.

These are properties of the supplied static representation. The application-level purpose of the two operations is unknown.

## Interface

The function accepts one object address. The same address is supplied as the first argument to both indirect invocations.

## Behavior

The retained destination is subsequently used for the second invocation’s middle argument. No explicit reassignment to that destination appears between its capture and use.

### First invocation

The wrapper resolves a callable through the object’s dispatch entry at byte offset `0x58`. The invocation role is designated **F-INDIRECT-01**.

The invocation receives:

1. The original object address.
2. A separate, direct use of Shared A.
3. A use of Shared B.

The middle argument does not come from the retained destination. Even if Shared A has not changed since the initial capture, the direct Shared A argument and the retained argument used later are not established to have identical values or representations: the retained path includes assignment into a four-byte destination.

The initial capture precedes preparation of this invocation in the supplied representation. Within the first call expression, the relative evaluation order of the following is not established:

- Reading the object’s dispatch-base field.
- Reading the selected callable entry.
- Reading Shared A for the middle argument.
- Reading Shared B for the final argument.

The callable-entry access necessarily depends on obtaining its dispatch base. No additional total ordering among these preparatory reads is justified by the supplied material.

F-INDIRECT-01 must return normally before the represented path proceeds to the second invocation.

### Second dispatch lookup

After F-INDIRECT-01 returns, the wrapper resolves a callable again through the original object address at the same byte offset, `0x58`. This invocation role is designated **F-INDIRECT-02**.

The target is not visibly cached across the first invocation. Therefore:

- A change to the object’s dispatch-base field can change the second lookup.
- A change to the relevant callable entry can change the second target.
- The two invocations can select the same callable or different callables.

Normal return from F-INDIRECT-01 does not establish that the object or dispatch storage remains valid. The wrapper nevertheless uses the original object address again, without a visible lifetime or validity check.

### Second invocation

F-INDIRECT-02 receives:

1. The original object address.
2. R, the retained four-byte value resulting from the initial assignment.
3. A use of Shared C after the first invocation returns.

The wrapper does not explicitly reload Shared A to supply this second middle argument. A change to Shared A during F-INDIRECT-01 therefore does not, through a fresh Shared A read, replace R.

This does not establish that unknown callees preserve arbitrary memory. The source shows no direct wrapper reassignment to the retained destination and no explicit passing of its address; broader callee effects remain unresolved.

The relative order between the second dispatch lookup and the Shared C read is not established. Both occur in preparation for the second invocation after the first returns.
