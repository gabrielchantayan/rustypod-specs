# F-9444ff86c269

## Purpose

F-9444ff86c269 conditionally performs cleanup on a sequence of fixed-size records, then conditionally updates allocation accounting and invokes allocation-management dependencies.

Two independent one-byte fields control these phases. A nonzero record-cleanup flag enables the first phase; a nonzero allocation-accounting flag enables the second. The second flag is read only after record cleanup, so changes made during record cleanup can affect whether accounting proceeds.

The established behavior is a sequence of memory accesses, accounting updates, and dependency calls. Interpreting this sequence as destruction of an object followed by release of its backing allocation is plausible intent, not a demonstrated ownership or deallocation guarantee.

## Interface

**Input:** one 32-bit address-like value identifying an object, or zero.

**Output:** no return value is established. Normal completion returns no status. An invalid allocation-header condition invokes a dependency identified as non-returning.

The input is represented as a 32-bit integer in the supplied material but is used as a memory address. This contract does not establish portability to wider pointers.

### Object layout

Offsets are byte offsets from the supplied nonzero object address.

| Offset | Width | Established use |
|---|---:|---|
| +4 | 16 bits, unsigned | Record count, read repeatedly during iteration |
| +6 | 8 bits | Allocation-accounting flag; zero disables the second phase |
| +7 | 8 bits | Record-cleanup flag; zero disables the first phase |
| +8 | 32 bits | Address of the first record |

Each record occupies 40 bytes. A 32-bit field at record offset +36 determines whether F-74b5a05d0094 is called for that record. The other record fields are not directly examined by this function.

### Allocation-prefix layout

If the allocation-accounting flag is nonzero, the function reads a 32-bit displacement at object offset −4. Subtracting that displacement from the object address produces an adjusted address.

The following fields are then addressed relative to that adjusted address:

| Offset | Width | Established use |
|---|---:|---|
| −16 | 32 bits | Allocation header, validity predicate, and masked accounting quantity |
| −12 | 16 bits, unsigned | First accounting-table index |
| −10 | 16 bits, unsigned | Second accounting-table index |
| −8 | 32 bits | Quantity used by an earlier two-word accounting update |

The displacement and the quantity at −8 have signed interpretations in particular operations described below. The two indices are unsigned.

## Behavior

### 1. Zero input

A zero input returns immediately. No object fields, global state, or allocation metadata are accessed, and no dependencies are called.

### 2. Optional record cleanup

For nonzero input, the function reads the byte at object offset +7.

If that byte is zero, it skips record cleanup without reading the record-array address or count for that phase.

If the byte is nonzero:

1. It reads and retains the 32-bit record-array address from object offset +8.
2. It starts at record index zero.
3. Before each potential iteration, it reads the current unsigned 16-bit count at object offset +4.
4. For an index below that current count, it reads the current record’s 32-bit field at offset +36.
5. If that field is nonzero, it calls F-74b5a05d0094 with the current record address.
6. It advances the record address by 40 bytes and increments the index, then evaluates the count again.

The count is not snapshotted. A dependency-induced change to the count can shorten or extend traversal. In contrast, changing the object’s record-array field does not redirect the ongoing traversal: its starting address has already been retained.

The cleanup flag is not rechecked during traversal. Each record’s gating field is examined only when that record is reached. This function does not itself clear the field or revisit a previously processed record.

The count is unsigned 16-bit, so each read yields a value from 0 through 65,535. Under otherwise valid execution, this bounds the visited indices; arithmetic on record addresses still requires valid accessible storage.

### 3. Optional allocation accounting

After record cleanup, the function retains the address held in a global accounting-object pointer. It then reads the byte at object offset +6.

If that byte is zero, the function returns. The global pointer value has already been read, but the subsequent accounting-field accesses and dependency calls do not occur.

If the byte is nonzero, the function continues with the original object address. The supplied representation contains another zero-input check here, but the local input has not changed since the initial check. It does not establish an additional reachable null-input case.

### 4. Address adjustment and two-word accounting

The function reads the 32-bit displacement immediately before the object and subtracts it from the object address. All later allocation-prefix accesses use this adjusted address, not the original object address.

It reads the 32-bit quantity at adjusted offset −8. It then updates two adjacent 32-bit words in the global accounting structure:

- Offset +56 is the low word.
- Offset +60 is the high word.

The low word is written first. It becomes its previous value minus the quantity, modulo \(2^{32}\).

The high-word update subtracts the sum of:

- The quantity’s arithmetic sign extension: zero if bit 31 is clear, or −1 if bit 31 is set.
- A borrow indicator: one if the previous low word is less than the quantity under unsigned comparison, otherwise zero.

Consequently, this is consistent with subtraction of a **sign-extended 32-bit quantity** from a two-word value, rather than unconditional subtraction of an unsigned 32-bit quantity. In particular, a quantity with bit 31 set can increase the high word when the low-word subtraction does not borrow.

The high-word destination uses the global accounting-object address retained before reading the allocation-accounting flag. The low-word access and high-word source address are obtained through the global pointer during this accounting sequence. There is no dependency call between these pointer accesses. No concurrent-mutation guarantee is established; treating all these addresses as identical requires a stable global pointer during the sequence.

After both writes, the function calls F-2fd8826557a4 with no explicit arguments.

### 5. Allocation-manager selection and sentinel case

After F-2fd8826557a4 returns, the function reads an allocation-manager address through a separate global pointer location.

If the adjusted address equals the numeric value **8**, it returns without inspecting the allocation header or calling the remaining dependencies.

This sentinel does not bypass the earlier work. Record cleanup, prefix displacement and quantity reads, the two accounting writes, F-2fd8826557a4, and the allocation-manager pointer read have already occurred.

### 6. Header validation

For any adjusted address other than 8, the function examines the 32-bit header at adjusted offset −16.

It invokes F-a817d8d58c10 if either:

- The header is zero.
- Bit 0 of the header is set.

That dependency is identified as non-returning in the supplied evidence. No ordinary error return, rollback, or local recovery path is established. The earlier two-word accounting update and F-2fd8826557a4 call occur before this failure condition is handled.

The validity predicate is not a positive-size check. For example, a nonzero header whose only set bit is bit 1 passes, even though its masked accounting quantity is zero.

### 7. Allocation-manager accounting and completion calls

For a header that passes the predicate, the function calls F-c0fc6d033caa with the selected allocation-manager address.

After that call returns, it performs these operations in order:

1. Reads the unsigned 16-bit index at adjusted offset −12.
2. Reads the header again and retains its value masked with `0x3FFFFFFC`.
3. Subtracts that retained quantity from the 32-bit manager entry at offset \(548 + 4 \times \text{first index}\).
4. Subtracts the same quantity from the manager word at offset 780.
5. Reads the unsigned 16-bit index at adjusted offset −10.
6. Subtracts the same retained quantity from the manager entry at offset \(224 + 4 \times \text{second index}\).
7. Subtracts the same quantity from the manager word at offset 544.
8. Calls F-09dcb55e8e0a with no explicit arguments.
9. Decrements the manager entry at offset \(784 + 4 \times \text{returned index}\).
10. Decrements the manager word at offset 912.
11. Reads the header again, masks it with `0x3FFFFFFC`, and subtracts that newly obtained quantity from the manager word at offset +8.
12. Calls F-cc6c9b4a0f68 with the manager address and the address of the header at adjusted offset −16.
13. Calls F-e586bff64fb7 with the manager address.
14. Returns if those dependencies return normally.

All described counter writes are 32-bit operations, with modulo-\(2^{32}\) arithmetic and no visible underflow handling.

The mask clears bits 31, 30, 1, and 0. Its result is a multiple of four between zero and `0x3FFFFFFC`. The significance of the cleared bits is not established.

F-c0fc6d033caa runs after header validation but before the index reads and masked-quantity capture. Its effects must not be assumed absent. There is no second validity check after it returns.

Similarly, F-09dcb55e8e0a runs before the final header reread. The quantity subtracted at manager offset +8 can therefore differ from the quantity used for the four earlier quantity-based updates.

The returned index has no visible range validation. The selected manager address remains the one captured before header validation; this function does not reload it after these calls.

## Side effects

The established direct effects are:

- Reads of object flags, a potentially changing record count, record gating fields, allocation-prefix metadata, and global pointer storage.
- Conditional per-record calls.
- Two global accounting writes before allocation-header validation.
- Further manager-accounting writes after validation.
- Calls that may have additional effects not specified here.

The function performs no explicit write to the object’s flags, count, record-array field, or allocation header. This does not imply that dependencies leave them unchanged.

No direct memory-release primitive is established by the provided material. F-cc6c9b4a0f68 receives the header address, and F-e586bff64fb7 follows it, but their ownership and release effects remain unknown.

Failure is not transactional. A header-validation failure occurs after earlier side effects. A fault or nonlocal exit in a dependency can likewise leave a partially completed operation. No restoration path is shown.

## Acceptance examples

These are conditional consequences of the static evidence, not executed tests.

1. **Null input.** Given input zero, the function returns without any dependency calls or memory accesses through the input.

2. **Both phases disabled.** Given a valid nonzero object with both flags zero, no record traversal or allocation-prefix access occurs. The global accounting-object pointer is still read before the allocation-accounting flag causes return.

3. **Selective record cleanup.** Given a stable count of three, a valid record array, a nonzero cleanup flag, and gating fields zero, nonzero, nonzero, F-74b5a05d0094 receives the second record and then the third. With allocation accounting disabled, no later dependencies are called.

4. **Count reduction during cleanup.** Given an initial count of three, if the first record’s dependency changes the count to one, the next loop condition ends traversal. This requires the object and current record to remain accessible through the intervening operations.

5. **Negative signed accounting quantity.** Given a stable global accounting pointer, an old low word of 5, and a quantity bit pattern of `0xFFFFFFFF`, the low word becomes 6. The unsigned subtraction borrows, while sign extension contributes −1, so the high word is unchanged. Together these writes increase the two-word value by one.

6. **Sentinel adjusted address.** Given valid preceding accesses and an adjusted address of 8, the initial accounting update and F-2fd8826557a4 still occur. Header validation and the remaining dependency calls do not.

7. **Invalid header after prior effects.** Given a non-sentinel adjusted address and a zero header, F-a817d8d58c10 is invoked only after the initial accounting writes and F-2fd8826557a4. The path is not a no-effect rejection.

8. **Accepted zero masked quantity.** Given header value 2, unchanged through the relevant reads, header validation succeeds and the masked quantity is zero. Quantity-based writes preserve their numerical values, while the two count decrements and remaining dependency calls still occur.

9. **Header mutation across a dependency.** If the first masked quantity is 64 and F-09dcb55e8e0a changes the header so its later masked value is 128, the earlier four quantity-based updates subtract 64, while the update at manager offset +8 subtracts 128.
