# F-4439a539b76a

## Purpose

F-4439a539b76a scans a byte-addressed input sequence and returns a count determined by the leading byte at each visited position. A zero byte terminates the scan only when encountered at a visited leading position.

The function resembles a counter for characters in a variable-width encoding, but encoding validity is neither checked nor established. Its behavior is defined by byte ranges, fixed advances, and selective increments. In particular, some nonzero leading bytes consume three positions without increasing the count.

The function does not accept an input length. Safe completion requires readable storage for every leading-position read and every additional read described below, and a zero byte at a leading position eventually reached by the scan. A zero elsewhere in the storage does not necessarily terminate it.

The result is an integer count initialized to zero and incremented for selected nonzero leading bytes.

The second and third arguments are explicitly represented as four-byte values. The fourth argument and the return value are represented as unsigned and signed integer types, respectively. ## Behavior

### Scan classification

At each visited position, the function first obtains the current byte. A zero ends the scan immediately, returning the count accumulated so far.

For a nonzero leading byte, progression and counting are:

| Leading byte | Advance to next leading position | Additional byte read | Count increment |
|---|---:|---|---:|
| `0x01–0x7F` | 1 byte | None | 1 |
| `0x80–0xBF` | 3 bytes | Byte at offset 2 | 0 |
| `0xC0–0xDF` | 2 bytes | None | 1 |
| `0xE0–0xEF` | 3 bytes | Byte at offset 2 | 1 |
| `0xF0–0xFF` | 3 bytes | Byte at offset 2 | 0 |

Offsets in this table are relative to the current leading position.

The advance is not the number of bytes actually read. A two-byte advance reads the leading byte but does not explicitly read the intervening byte. A three-byte advance reads the leading byte and the byte at offset 2, but does not explicitly read the byte at offset 1.

The additional offset-2 read does not validate the input and does not influence the classification of the current leading byte. Nevertheless, the read occurs in the supplied body and creates a readability requirement.

### Order of reads and local state changes

The following order describes source-level evaluations, not a guarantee of distinct physical memory transactions after compilation.

1. The local count begins at zero.
2. At the current leading position, the function forms the address one byte ahead and reads the leading byte as an unsigned value.
3. If that byte is zero, the function returns the current count. No second evaluation of that leading byte is required by this terminating path.
4. For a nonzero leading byte, the source evaluates the leading byte again to determine whether its high bit is set.
5. If the high bit is clear, the next leading position is one byte ahead and the count increases by one.
6. If the high bit is set, the fourth argument’s local working value is replaced with the first-read leading byte masked by `0xE0`.
7. A masked value of `0xC0` selects a two-byte advance and one increment.
8. Any other masked value selects a three-byte advance. On that path, the byte at offset 2 is read into the local working value before the possible count increment. The current leading byte contributes one increment only if its first-read value masked by `0xF0` is `0xE0`.
9. The scan repeats at the selected next leading position.

For stable input storage, these evaluations produce exactly the classification table above. The supplied body does not establish coherent behavior for concurrently modified input. In particular, the initial value test and the later high-bit evaluation are separate source expressions. No synchronization or volatile-access contract is present.

### Termination and skipped zeros

Only the leading-position read controls termination.

Therefore:

- An initial zero produces a result of zero.
- A zero at offset 1 of a two-byte or three-byte step is skipped.
- A zero at offset 2 of a three-byte step is read, but does not end the scan.
- After either kind of skipped zero, scanning continues at the full selected advance.
- A conventional zero-terminated byte allocation is not sufficient by itself to ensure safety if an earlier leading byte makes the scan skip its terminator.

The function does not search for the earliest zero in address order.

### Incoming fourth argument

The incoming fourth value is compared on some paths, but it cannot affect the observable result for stable, valid input:

- On a high-bit-clear iteration, the increment and one-byte advance do not depend on that comparison.
- On a high-bit-set iteration, the value is replaced before the comparison can affect progression.

Subsequent assignments to this argument are local changes. The interface does not pass a pointer through which those assignments would update caller storage.

### Counting and arithmetic limits

Each visited nonzero leading position contributes either zero or one. No iteration decreases the count.

The count is not necessarily:

- The number of bytes traversed.
- The number of nonzero bytes present.
- The number of valid encoded characters.
- The number of Unicode scalar values.

There is no overflow check. If enough counted positions are visited to exceed the signed result type’s representable range, the supplied material does not establish a portable result. Signed wraparound must not be treated as part of the contract.
