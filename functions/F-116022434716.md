# F-116022434716

## Purpose

F-116022434716 searches up to four identifier positions in an indirectly referenced object. A nonzero candidate equal to the request’s comparison word selects an ordered dependency sequence, followed by lookup and possible invocation of a callback.

Three normal-return outcomes are established:

- **No match:** call F-4fc89ec41a6d with arguments **(6, 108, 110, 0, 0)**, then return the 32-bit word `0xffffffff`.
- **Match, callback absent after preparation:** complete the preparation sequence, call F-4fc89ec41a6d with arguments **(6, 108, 105, 0, 0)**, then return zero.
- **Match, callback present after preparation:** invoke the callback with six arguments and return its 32-bit result unchanged.

“Preparation” names the four ordered calls preceding callback lookup. It does not establish what those dependencies construct, initialize, retain, or release.

The identifier namespace, application-level operation, and meanings of the fixed dependency arguments are unknown. Interpreting F-4fc89ec41a6d as a diagnostic-reporting operation is plausible but unproven; only its invocation and arguments are established.

## Behavior

### Identifier search

The search examines candidate positions in increasing order: offsets **44, 48, 52, 56**. It examines at least the first position on normal entry and never examines a fifth position.

For each reached position, the object-reference word is read to obtain the object address, then the candidate word at that position is read.

A zero candidate immediately ends the search as unmatched. The request comparison word is not read for that candidate.

For a nonzero candidate, the request’s 32-bit word at offset 0 is read and compared for equality with the candidate. Equality selects preparation. Inequality allows the next position, unless the fourth candidate has already been considered.

Consequences:

- Zero is a terminator, not a matchable identifier.
- A request comparison value of zero cannot match.
- The first match stops scanning.
- No candidate after a zero terminator is read.
- The request comparison word is read again for each reached nonzero candidate; it is not saved once for the whole search.
- The object address is obtained again for successive candidate accesses; the list is not captured as a stable snapshot.

Thus, stable-list behavior requires external stability. If the reference or request changes between accesses, different iterations may use different object addresses or comparison values. The supplied body provides no synchronization contract for such changes.

The candidate index takes values zero through three at candidate accesses. Multiplication by four and addition of the 44-byte displacement produce offsets from 44 through 56 without overflowing the index arithmetic. This does not establish that adding those offsets to an arbitrary object address is valid or that address wraparound has a defined recovery behavior.
