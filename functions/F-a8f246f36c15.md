# F-a8f246f36c15

## Purpose

F-a8f246f36c15 returns a signed integer selected from a request and a value held in addressed storage.

Negative requests produce zero without accessing the addressed storage. Nonnegative requests are limited by the stored value when that value is stable: the result is the smaller of the request and the stored value.

The stable-storage qualification matters. The supplied representation contains a comparison read and, conditionally, a separate read supplying the result. It does not establish a single retained snapshot or a guaranteed number of physical memory transactions.

The stored value is called the **bound** in this contract for convenience. That name does not establish a domain invariant. In particular, the bound need not be nonnegative, and the function does not guarantee a nonnegative result.

## Interface

### Inputs and result

| Item | Contract |
|---|---|
| Base | Integer-valued address input identifying the storage used for the bound |
| Request | Signed integer candidate whose sign determines whether bound storage is accessed |
| Result | Signed integer returned directly; there is no separate status output |

The base, request, loaded bound, and result have the same represented integer type. The base is not declared as a pointer in the supplied interface; its use as an address depends on the execution environment’s integer-to-address interpretation.

No output buffer, callback, context object, or explicit ownership argument is present.

### Widths and layout

The bound is addressed at byte displacement **4** from the base. No meaning is established for the preceding storage or for any other offset. In particular, the representation does not establish a containing record’s type, size, field count, or allocation boundary.

The bound is interpreted as a signed integer, not as an unsigned quantity or a collection of independent bytes.

The exact integer width, address width, integer storage size, byte order, signed representation, and required alignment are **documented_only**. A displacement of four bytes does not, by itself, establish a four-byte load.

If the target uses 32-bit signed integers, the request, bound, and result would have the range −2,147,483,648 through 2,147,483,647. That is a conditional interpretation, not an established target property.

### Preconditions

The negative-request path has no bound-storage readability requirement because it does not access that storage or compute the bound’s address.

For a nonnegative request, normal completion depends on:

- A valid calculation of the address at displacement 4.
- A supported interpretation of the calculated integer as an address.
- Storage readable as the represented signed integer type, with any required alignment.
- Continued readability for every bound access that occurs.
- Compliance with the execution environment’s rules for shared or changing memory.

The function performs no explicit validation of these conditions. An invalid address is not converted into a defined error result.

These are requirements for meaningful execution, not evidence that callers satisfy them.

## Behavior

### Selection rules

For every representable negative request, the result is zero. The base does not influence that result, and no bound access is represented on this path.

For a nonnegative request, the first bound observation determines the selection:

| Relationship between the first bound observation and the request | Selected result |
|---|---|
| Bound observation is greater than the request | Request |
| Bound observation equals the request | Request |
| Bound observation is smaller than the request | Value obtained by the subsequent bound read |

Equality therefore belongs to the request-selected case. A separate return-value read of the bound appears only in the strictly-smaller case.

When the subsequent read supplies the result, that value receives no further sign check or comparison. The function does not enforce that it remains below the request, matches the earlier observation, or is nonnegative.

### Ordering and access guarantees

The represented ordering is:

- The request’s sign determines whether storage is accessed at all.
- On the nonnegative path, the comparison observation precedes the result decision.
- When that observation selects the bound, the result-producing observation follows it.

This describes the dependencies and access expressions in the supplied representation. It is not a guarantee of two machine loads on the bound-selected path.

No volatile access, atomic access, synchronization operation, or memory-ordering primitive is declared. Compiler treatment and the target memory model therefore remain relevant. The representation alone does not establish that another thread, a device, or a signal handler may legally change the storage between observations.

Likewise, a source-level absence of a second read on the request-selected path is not an independently verified machine-level access trace.

### Stable bound

When all relevant observations see the same bound, the function has a simple numerical interpretation:

- Every negative request yields zero.
- Every nonnegative request yields the lesser of the request and the bound.

This is not a clamp into a nonnegative interval. With a stable negative bound, every nonnegative request produces that negative bound. With a stable zero bound, every request produces zero.

The numerical interpretation requires no assumption about why the bound exists. It could represent a limit, but the supplied material does not establish that purpose.

### Changing bound

Where the execution model permits distinct observations, selection and returned value need not agree as a numerical minimum.

For example, a request of 5 and an initial bound observation of 2 select the bound-result case. If the subsequent permitted observation is 9, the represented result is 9. There is no final restriction to 5 or 2.

Conversely, an initial bound observation of 9 with the same request selects the request result. A later change to the storage does not introduce a result-producing bound read into the represented behavior.

These are conditional descriptions of the supplied representation. They do not authorize unsynchronized concurrent mutation or require independently observable repeated reads.

### Arithmetic boundaries

The request is tested and compared, but it is not negated, incremented, decremented, or otherwise arithmetically transformed. The minimum representable negative request therefore follows the zero-result path without requiring a representable positive magnitude.

A maximum representable request is also handled by comparison rather than request arithmetic.

The base does participate in addition by 4 on the storage-accessing path. No overflow check or explicit wrapping rule is present. The contract does not promise that a base near the integer limit wraps to a usable address. Arithmetic validity and integer-to-address conversion remain prerequisites whose exact rules depend on the target.

## Side effects

No explicit memory write, allocation, deallocation, ownership transfer, or function call appears in the supplied body.

The inputs are passed as integer values. The function does not write the selected result back to caller storage. Choosing the bound changes the returned value, not the bound itself.

The representation does not identify who owns the addressed storage. It establishes neither an ownership acquisition nor a release, retention, or destruction operation. Callers must not infer lifetime management from this function.

The conditional bound reads are the only explicit accesses to external storage. Their addresses could refer to ordinary memory, shared state, or special mappings; the function does not classify them. Consequently, the absence of explicit writes does not establish that reading a special mapping has no external consequences.

There is no explicit diagnostic, recovery path, exception translation, or error indicator for unreadable storage, unsuitable alignment, invalid address arithmetic, or unsupported address conversion. Whether such conditions fault, invalidate execution, or have another outcome is **documented_only**. A fault is not specified as a successful zero return.

## Acceptance examples

These examples are static contract cases, not executed tests. Unless an example says otherwise, assume valid address arithmetic, suitably aligned readable storage, and a bound that remains stable throughout the invocation.

Additional acceptance conditions:

**Negative request with an unusable base.** The represented path returns zero without calculating or accessing the bound address. This does not make that base suitable for a nonnegative request.

**Nonnegative request with inaccessible storage.** No successful result is guaranteed. The implementation contains no explicit fallback value for this condition.

**Valid first read but unavailable subsequent read.** If the first observation selects the bound and the required subsequent access cannot complete, the representation does not provide a successful result using the earlier observation instead.

**Permitted changing observations.** With request 5, first observation 2, and subsequent observation 9, the represented result is 9, provided the execution environment permits those observations. With subsequent observation −4 instead, the represented result is −4.

**First observation selects the request.** With request 5 and first observation 9, the represented result is 5. No result-producing bound read is present on that path.

**Address calculation at a numerical boundary.** A nonnegative request does not establish successful completion when adding 4 to the base is invalid. Neither wraparound nor a particular error outcome is an acceptance requirement.
