# F-0083d012108d

## Purpose

F-0083d012108d traverses a bucketed collection and invokes one of two caller-supplied callbacks for each encountered entry. Buckets are processed in descending index order. Within each bucket, traversal follows the entry links in their stored order.

A selector chooses between a one-argument callback and a two-argument callback. The second form receives the same caller-supplied context value on every invocation.

The established behavior is traversal and callback dispatch, not removal, destruction, or ownership transfer. The function itself performs no explicit collection updates, allocation, or release. Any such effects would have to come from a callback.

## Interface

### Inputs

Five arguments are supplied:

1. **Collection descriptor address.** An address identifying a structure whose relevant fields are:
   - At byte offset 0: a 32-bit value used as the bucket-array base address.
   - At byte offset 12: a signed 32-bit bucket count.

   The fields at byte offsets 4 and 8 are not read by the visible function. No larger descriptor layout is established.

2. **Callback selector.** A 32-bit integer:
   - Zero selects the third argument.
   - Any nonzero value selects the fourth argument.

3. **One-argument callback address.** Invoked with the entry’s 32-bit payload when the selector is zero.

4. **Two-argument callback address.** Invoked with the entry’s 32-bit payload and the fifth argument when the selector is nonzero.

5. **Context value.** An uninterpreted 32-bit value passed as the second argument to the two-argument callback. The visible function does not dereference or otherwise interpret it.

### Collection layout

The supplied representation uses four-byte slots and 32-bit address-bearing values.

The bucket array contains bucket-head addresses at a stride of four bytes. A zero head address denotes an empty bucket.

Each reachable entry has at least two readable four-byte fields:

| Entry offset | Meaning |
|---|---|
| 0 | Uninterpreted 32-bit payload |
| 4 | Address of the next entry, or zero to terminate the chain |

The payload may represent an integer, address, handle, or other four-byte value. Its meaning is not established by this function.

The layout describes the supplied representation, not a portable native-pointer layout. Byte order, alignment requirements, and the machine calling convention are not established by the supplied evidence.

### Output

The function returns without a result value when traversal completes. Callback return values, if any, are not inspected.

No status code, visit count, or error result is produced.

### Preconditions for ordinary completion

For a nonempty traversal:

- The descriptor’s count field must be readable.
- Each accessed bucket slot must be readable.
- Each reached nonzero entry address must expose both entry fields.
- The selected callback must be callable with the indicated argument form.
- Address and index calculations must remain within the valid range of the execution environment.
- Callbacks must return normally if traversal is to continue.
- The evolving chains must terminate if the function is to finish.

These are requirements for a valid execution, not checks performed by the function.

## Behavior

### Count capture and bucket order

The descriptor’s signed 32-bit bucket count is read once, before bucket traversal.

For an ordinary positive count \(N\), bucket indices are visited in this order:

\(N-1, N-2, \ldots, 1, 0\).

The traversal index is decremented before deciding whether to process a bucket. Consequently, a count of zero causes no bucket access and no callback invocation.

A negative count also causes no traversal when its initial decrement remains representable and negative. The minimum signed 32-bit value is a separate arithmetic boundary discussed under **Uncertainties**.

Callback changes to the descriptor’s count do not alter the already captured traversal bound. They do not add buckets to, or remove buckets from, this invocation’s scheduled index sequence.

### Bucket-head reads

For each scheduled bucket, the visible read sequence is:

1. Read the bucket-array base from the descriptor.
2. Read the head address at the current index, using a four-byte stride.
3. Traverse the resulting chain until its current entry address is zero.

The bucket-array base is read again for each bucket. It is not captured once for the whole invocation.

Accordingly, a callback that changes the descriptor’s base can affect where later buckets are read. Changes to a not-yet-read bucket head can also affect later traversal. This is not a collection-wide snapshot.

An empty bucket produces no entry reads and no callback invocation.

### Entry reads and callback timing

For every reached nonzero entry, the visible sequence is:

1. Read the entry’s 32-bit payload.
2. Read its next-entry address.
3. Retain that next-entry address as the traversal continuation.
4. Invoke the selected callback using the captured payload.
5. If the callback returns normally, continue from the retained address.

Both entry fields are therefore read before the callback begins.

Changing the current entry’s payload during the callback cannot change the argument already supplied for that visit. Changing the current entry’s link during the callback cannot change the continuation already retained for that visit.

The function does not reread the current entry after its callback. Its payload and link are no longer needed by that iteration. This limited observation is not a general guarantee that arbitrary entry destruction is safe: the retained successor, future bucket accesses, or callback behavior may still depend on memory affected by the callback.

The successor’s fields are read only when traversal reaches that successor. A callback can therefore affect a future payload or link by changing that future entry before it is visited, provided the resulting memory remains valid.

### Callback selection

The selector is tested for each encountered entry:

- Zero dispatches to the one-argument callback.
- Nonzero dispatches to the two-argument callback.

There is no additional distinction among nonzero selector values. A negative selector selects the same callback form as a positive nonzero selector.

The context value is supplied unchanged by this function to every two-argument invocation. It is not supplied to the one-argument callback.

Only the selected callback is invoked. Neither callback is invoked when no entry is reached.

### Completion and repeated visits

There is no deduplication, visited-entry set, or cycle detection.

If two buckets lead to the same entry, that entry can receive more than one callback. Likewise, linked chains may merge and cause a shared suffix to be visited repeatedly.

A stable nonterminating cycle prevents the current bucket’s traversal from finishing, so lower-index buckets are not reached. Callback mutations may change that outcome; the function itself does not impose a traversal limit.

There is no callback-result-based early stop. Continuation depends on normal callback return and the retained next-entry address, not on a callback return value.

## Side effects

### Direct effects

The visible function:

- Reads descriptor fields, bucket-head slots, and entry fields.
- Invokes caller-supplied callbacks.
- Maintains local traversal state.

It contains no explicit writes to the descriptor, bucket array, entries, or payload storage. It does not explicitly allocate memory, release memory, clear buckets, unlink entries, or reset the bucket count.

Calling it does not, by itself, establish that the collection is empty or destroyed afterward.

### Callback effects and ownership

Callbacks may have externally observable effects. Their implementations are unavailable, so this contract does not assume that they preserve globals, preserve collection memory, return normally, or refrain from reentering this function.

Passing a payload or context value does not establish ownership transfer. The function makes no payload copy beyond capturing the four-byte value used for the call, and it performs no explicit release afterward.

The function’s own retention of the next-entry address does not keep the successor alive. If a callback invalidates that address, a later iteration may access invalid memory.

The descriptor and future bucket storage must remain valid whenever subsequent reads require them.

### Synchronization and errors

No explicit locking, atomic access, consistency check, or mutation guard is visible.

There is no explicit handling for invalid addresses, an invalid selected callback, malformed chains, arithmetic failures, or failures within a callback. The function does not translate such failures into a return status or perform visible recovery.

Reentrant or concurrent behavior depends on the actual memory changes and callback behavior. Thread safety is not established.

## Acceptance examples

These examples are conditional consequences of the static evidence, not results of runtime tests. Unless stated otherwise, they assume valid memory, representable arithmetic, normally returning callbacks, and no callback mutation.

### Descending buckets, forward chains

For a count of three:

- Bucket 2 contains payloads A followed by B.
- Bucket 1 is empty.
- Bucket 0 contains payload C.

The callback receives A, then B, then C. The function does not process bucket 0 first or reverse the links within bucket 2.

### Zero and nonzero selectors

For one reachable payload P and context K:

- Selector zero invokes only the one-argument callback with P.
- Selector one invokes only the two-argument callback with P and K.
- Selector negative one also invokes only the two-argument callback with P and K.

The context is not dereferenced by this function.

### No reached entries

With a count of zero, the count field is read, but the bucket-array base and bucket heads are not read.

With a positive count and all bucket heads zero, the corresponding bucket reads occur, but no callback is invoked.

These cases do not exercise either callback address. They do not establish that the same callback values would be valid for a nonempty traversal.

### Current-link mutation

Suppose an entry points to successor B when its two fields are read. Its callback then changes that entry’s link to C.

The next iteration uses B, not C, because B was retained before the callback. B must still identify valid entry storage when accessed.

### Future-entry mutation

Suppose a callback changes the payload of a not-yet-visited successor while leaving that successor valid.

When traversal reaches the successor, it reads the changed payload. Payloads for future entries are not prefetched by this function.

### Descriptor mutation between buckets

Suppose a callback changes the bucket-array base before traversal reaches a lower-index bucket.

That later bucket uses the base read from the descriptor at that time. A concurrent change to the descriptor’s count does not change the scheduled bucket indices.

### Shared entry

If two separately traversed bucket chains both reach the same entry, the callback is invoked for that entry on each encounter. Shared identity does not suppress a visit.

## Uncertainties

### Established static evidence

The supplied representation establishes:

- Four-byte bucket slots and entry fields.
- A signed count with decrement-before-check traversal.
- Descending bucket order.
- Per-bucket rereading of the descriptor’s base.
- Payload and successor reads before callback invocation.
- Zero-versus-nonzero callback selection.
- No explicit collection writes, allocation, release, or validation.

### Inferred intent

The structure is consistent with iteration over chained buckets, possibly in a hash-based collection. A callback could plausibly process or dispose of payloads.

Those interpretations do not establish hashing semantics, disposal behavior, entry ownership, or collection destruction.

### Documented-only boundaries

- **Minimum signed count:** decrementing \(-2^{31}\) is outside signed 32-bit representability. The supplied representation does not establish the intended language semantics or exact machine behavior at this boundary.
- **Large index arithmetic:** the four-byte stride requires address arithmetic whose intermediate width and overflow behavior are not fully established. No wraparound behavior is promised.
- **Address representation:** four-byte address-bearing fields are visible, but byte order, alignment, address-space rules, and calling convention are not supplied.
- **Callbacks:** identities, permitted mutations, ownership rules, failure mechanisms, and global-state effects are unknown.
- **Invalid execution:** fault behavior, unwinding, and recovery are not established.
- **Concurrency:** the visible access sequence supplies no synchronization guarantee.
