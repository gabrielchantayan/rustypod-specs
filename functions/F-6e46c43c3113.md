# F-6e46c43c3113

## Purpose

F-6e46c43c3113 performs a synchronous sequence of status queries, register-like writes, conditional waits, and final validation. It returns the 32-bit value **1** when final validation succeeds and **0** on each explicit failure path. Every explicit failure path calls a diagnostic dependency before returning.

A successful operation can optionally retrieve and store one additional 32-bit value through a caller-provided address.

The descriptions “controller availability,” “command launch,” “completion,” “response readiness,” and “busy clear” express inferred intent. The established contract is the access order, dependency calls, masks, branches, and stores described below. No particular device protocol or timing unit is established.

## Interface

The function accepts four inputs:

| Input | Representation and use |
|---|---|
| Command word | Unsigned 32-bit value. Written unchanged during setup and subsequently written with bit 31 forced on. Selected bits control later phases. |
| Parameter word | Opaque 32-bit value, written unchanged during setup. |
| Optional output address | Null or an address writable for one 32-bit result. A direct result store occurs only after successful final validation. |
| Caller timeout argument | Opaque 32-bit value passed as the second argument to timeout checks during availability, completion, and response waits. |

The return value is a 32-bit word. Explicit returns are exactly zero and one; nonzero dependency results are not returned directly.

### Command-bit interpretation

| Mask | Local effect |
|---|---|
| `0x80000000` | Forced on in the start write. |
| `0x00070000` | Any selected bit enables the response-status phase after completion. |
| `0x00080000` | Enables the busy-clear phase, but only after a selected response-status phase succeeds. |
| `0x00100000` | Passed, without Boolean normalization, to final validation. |

The command is not sanitized. If bit 31 is already set, the setup command write already contains that bit. Untested command bits remain present in both command writes.

### Preconditions

The function performs no visible validation of the following requirements:

- Shared context and target addresses must support the accesses described below.
- The target must accept the specified 32-bit stores.
- A non-null output address must support a four-byte store.
- Dependencies must return normally for execution to continue.
- Any required coordination of concurrent access must be supplied externally.

A null output address is supported. Invalid shared addresses and invalid non-null output addresses have no local recovery path.

Pointer width, alignment rules, byte order, and hardware ordering requirements are not independently established. Offsets below are byte offsets; describing a four-byte word access does not establish an external data format.

## Behavior

### Shared-state layout and retained addresses

The function directly uses three shared values:

- A context reference containing an address.
- A 32-bit setup word.
- An early-failure diagnostic value.

The visible context and target accesses are:

| Base | Byte offset | Access |
|---|---:|---|
| Context address | `+0x04` | Read a target address. |
| Context address | `+0x18` | Read a 32-bit timeout argument during busy-clear checks. |
| Target address | `+0x08` | Write a 32-bit command word. |
| Target address | `+0x0C` | Write the 32-bit parameter word. |
| Target address | `+0x14` | Write the shared 32-bit setup word. |

This is a partial access layout, not a complete structure definition.

The distinction between a retained context address and a later read of the shared context reference is observable. Dependencies are not assumed to preserve either shared references or memory reached through them.

### 1. Obtain one timing reference

The function calls F-U01 once, with no visible arguments, and retains its 32-bit result.

Every timeout check uses this retained result as its **first argument**. No new timing reference is obtained between phases.

The same result is also supplied as the argument to the first availability query. Subsequent availability queries receive zero.

Whether the retained value establishes a shared elapsed-time budget is unknown because the timeout dependency’s behavior is unavailable.

### 2. Wait for availability

Each iteration calls F-a63d7d1563a4 and tests its result with mask `0x30`.

After the query, and before deciding whether to continue or proceed, the function reads the shared context reference and retains that address. This read occurs even when the availability result has selected bits set.

If both bits selected by `0x30` are clear, execution proceeds immediately to setup. No timeout check is made for that successful iteration.

Otherwise, the function calls F-U02 with:

1. The original timing reference.
2. The caller timeout argument.

A zero return permits another availability query, using argument zero. A nonzero return selects the availability-timeout diagnostic and then returns zero.

Thus availability is checked before timeout on every iteration. A dependency that continues returning an unavailable status while F-U02 continues returning zero can keep this phase running indefinitely.

### 3. Perform setup writes

After availability succeeds, the function reads the shared context reference again and obtains a target address from offset `+0x04` of that context.

Using this one resolved setup target, it performs these 32-bit stores in order:

1. Read the shared setup word and write it to target offset `+0x14`.
2. Write the parameter word to target offset `+0x0C`.
3. Write the unmodified command word to target offset `+0x08`.

No dependency call appears between these three stores.

The context used for this target lookup comes from a separate shared-reference read. It must not be assumed identical to the context address retained immediately after the successful availability query.

### 4. Check launch permission

After all setup writes, the function calls F-a0d99869473e with no visible argument and tests bit `0x01` of its result.

If that bit is clear:

1. It calls F-a0d99869473e again, also with no visible argument.
2. It reads the shared early-failure diagnostic value.
3. It calls F-1b7fa166ef25 with that diagnostic value and the second status result.
4. It returns zero.

The diagnostic therefore receives a fresh status result, not necessarily the result that caused failure. The shared diagnostic value is obtained after the second status call; that dependency is not assumed to preserve it.

This path performs the setup writes but no start write, completion wait, final validation, or optional result retrieval.

If bit `0x01` is set, execution proceeds to the start write.

### 5. Start the operation

The function reads a target address from offset `+0x04` of the context address retained during the successful availability iteration. It then writes the command word ORed with `0x80000000` to offset `+0x08` of that target.

This is a full 32-bit store. It does not read or merge the existing target command word.

The start target is resolved separately from the setup target. In particular:

- Changing the shared context reference does not replace the already retained context address.
- Changing the target field within the retained context can change the destination of the start write.
- The setup and start writes are not guaranteed to reach the same target.

After the start write, the function calls F-U03 with the literal value `1000`. Its returned 32-bit value becomes the argument to the first completion-status query. Neither a delay duration nor a time unit is established for this call.

### 6. Wait for completion

The function calls F-a0d99869473e and tests bit `0x04`.

The first query receives the return value from F-U03 and occurs before any completion-phase timeout check.

When bit `0x04` is clear, the function calls F-U02 with:

1. The original timing reference.
2. The caller timeout argument.

A nonzero result selects the completion-timeout diagnostic and returns zero after reporting. A zero result permits another status query, now with argument zero.

When bit `0x04` is set:

- If the command AND `0x00070000` is zero, execution proceeds directly to final validation.
- Otherwise, execution enters the response-status phase.

Setting `0x00080000` alone does not introduce a busy-clear wait.

### 7. Conditionally wait for response status

This phase occurs only when the command AND `0x00070000` is nonzero.

The function makes a fresh F-a0d99869473e call. Its first argument is the successful completion-status result. It does not reuse that result as the response-status observation.

The new result is tested with `0x10`.

If the bit is clear, F-U02 receives:

1. The original timing reference.
2. The caller timeout argument.

A nonzero result selects the response-timeout diagnostic and returns zero after reporting. A zero result permits another response-status query with argument zero.

If bit `0x10` is set:

- A clear command bit `0x00080000` leads to final validation.
- A set command bit `0x00080000` leads to the busy-clear phase.

The first response query precedes any timeout check for this phase.

### 8. Conditionally wait for busy clear

This phase requires both a selected response-status phase and command bit `0x00080000`.

The function makes another fresh F-a0d99869473e call, initially passing the successful response-status result. It tests bit `0x200`.

If that bit is clear, execution proceeds directly to final validation, without a busy-phase timeout check.

If the bit is set, the function freshly reads the 32-bit word at offset `+0x18` of the retained context address and calls F-U02 with this exact positional contract:

1. **First argument: the original timing reference returned by F-U01.**
2. **Second argument: the freshly read 32-bit word from retained context offset `+0x18`.**

The arguments are not reversed. The caller timeout argument is not used for this phase.

A nonzero timeout result selects the busy-clear-timeout diagnostic and returns zero after reporting. A zero result permits another status query with argument zero.

The context timeout word is read again for every busy timeout check. Consequently, changes to that word between checks can affect later arguments. Changes to the shared context reference alone do not redirect these reads away from the retained context address.

### 9. Validate and optionally retrieve a result

After the required status phases, the function calls F-67659c2b52de with the command AND `0x00100000`.

The argument is exactly either `0x00000000` or `0x00100000`, never a normalized one.

A zero return selects the final command-failure diagnostic and returns zero after reporting.

Any nonzero return is accepted as success. If the output address is non-null, the function then:

1. Calls F-7b608acf5ce9 with no visible arguments.
2. Stores its returned 32-bit word at the output address.

It returns one whether the output address is null or non-null. With a null output address, the retrieval dependency is not called.

## Side effects

### Direct memory effects

A path reaching the start write performs three setup stores followed by one start store. Successful validation with a non-null output address adds one 32-bit output store.

No explicit failure path performs the optional output store. This does not guarantee unchanged output memory: the address may alias a setup or start destination, and dependencies may modify memory independently.

The function also performs the shared-reference, target-address, setup-word, diagnostic-value, and busy-timeout reads described above. Status observations occur through dependencies rather than direct status-register reads in this function.

### Failure state

No visible rollback, cancellation, reset, restoration, or compensating write follows failure.

A launch-permission failure leaves the setup writes performed. A later timeout or final-validation failure leaves both setup and start writes performed. Whether a launched operation continues after timeout is unknown.

Each explicit failure path makes one diagnostic call. The function does not establish behavior for dependency traps, exceptions, invalid accesses, or non-returning calls.

### Ownership and coordination

No allocation, release, ownership transfer, or retention of the caller’s output address is visible locally.

This does not constrain dependency ownership behavior. Dependencies may change shared data or affect object lifetimes; their internals are unavailable. Continued execution requires subsequent accesses to remain valid.

No local lock or explicit synchronization operation is visible. Suitable concurrent-access and device-ordering requirements remain external preconditions.

## Dependencies

F-U01, F-U02, and F-U03 are opaque dependency IDs used where no publishing ID was supplied.

| Function ID | Established local use |

| F-U02 | First argument is always the original timing reference. Second argument is the caller timeout in the first three wait phases, or the freshly read retained-context `+0x18` word in the busy-clear phase. Zero continues polling; nonzero selects failure. |
| F-U03 | Called with `1000`; its return feeds the first completion-status query. |
| F-a63d7d1563a4 | Supplies availability results tested with `0x30`; receives the timing reference initially and zero on retries. |

The represented calls do not establish complete external signatures. F-a0d99869473e appears both without visible arguments and with one; F-1b7fa166ef25 appears with two visible arguments for early failure and one for the other failures.

No dependency is assumed to be pure, preserve globals, preserve target contents, or acquire or release memory.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume valid accesses and normally returning dependencies.

1. **Availability failure before setup.** If availability reports a selected `0x30` bit and F-U02 then returns nonzero, the function reports availability timeout and returns zero without direct setup or output stores.

2. **Observed readiness precedes timeout.** If an availability result has `0x30` clear, that iteration proceeds to setup without checking timeout.

3. **Launch rejection uses a second observation.** If the first launch-status result lacks bit `0x01`, all setup stores have occurred. A second status result is supplied to the diagnostic. No start store occurs.

4. **No response selection.** With `0x00070000` clear, successful completion proceeds directly to validation, even if `0x00080000` is set.

5. **Fresh phase observations.** When response and busy phases are selected, each makes its own first status call. Bits present in the preceding phase’s result do not eliminate that call.

6. **Busy timeout argument order.** If the retained timing reference is `0x12345678`, the current retained-context timeout word is `0x00000020`, and busy remains set, F-U02 receives first `0x12345678`, then `0x00000020`. It does not receive those values in reverse order.

7. **Busy timeout word can change.** If a busy timeout check returns zero and a later busy result remains set, the next check rereads retained context `+0x18`. A changed word is used as the second argument; the original timing reference remains first.

8. **Busy clear avoids a timeout check.** If the first busy-status result has `0x200` clear, validation follows without reading the busy timeout word for a timeout check.

9. **Validation is not Boolean-normalized.** A command containing `0x00100000` passes that exact masked value to validation. Any nonzero validation return permits success.

10. **Optional retrieval requires success and an address.** A successful validation with non-null output causes one retrieval call and one result store. A null output suppresses both. Failed validation suppresses both regardless of the output address.
