# F-80b30d892f47

## Purpose

F-80b30d892f47 conditionally updates three adjacent state fields in response to a tagged input record. It recognizes two tags:

- **20 (0x14):** when the stored marker is zero, store the input value as the marker and increment a counter.
- **21 (0x15):** when the stored marker is nonzero, add the difference between the input value and the marker to an accumulator, then clear the marker.

Other tags do not trigger state-field accesses or writes.

The structure suggests paired begin/end events, an interval accumulator, and a count of accepted begin events. These meanings are **inferred intent**, not established interface semantics. The input value’s units, clock source, signedness at the application level, and permitted range are unknown.

A zero marker is the sole inactive-state representation. Consequently, accepting a begin-tagged record whose input value is zero increments the counter but leaves the marker indistinguishable from an inactive state.

## Behavior

### Tag dispatch

The function first reads the tag and compares it with 20.

If that comparison succeeds, it processes the begin case and returns without performing the comparison against 21.

If that comparison fails, the supplied representation evaluates the tag again for comparison with 21. A successful second comparison selects the end case; otherwise the function returns without accessing the state fields.

For a stable record, this is equivalent to selecting behavior from one tag value. For a concurrently changing or externally mutable record, a single captured tag value is not an established guarantee. Exact machine-level load counts are not established by this representation.

### Begin case: tag 20

The function reads the marker.

If the marker is nonzero, the event is ignored. It does not access the input value or counter, and performs no direct state write.

If the marker is zero:

1. It reads the input value and writes that 32-bit value to the marker.
2. After that marker write, it reads the counter, adds one, and writes the result to the counter.
3. It returns.

The accumulator is not accessed on this path.

The counter increment depends on the marker’s value before the marker assignment. It does not depend on whether the newly stored marker is nonzero. Thus an input value of zero still causes the increment.

The marker assignment precedes the counter update in the supplied control flow. The pair of writes is not presented as an atomic transaction. If execution fails during the later counter access or update, the function contains no rollback of the earlier marker write.

### End case: tag 21

The function reads the marker.

If the marker is zero, the event is ignored. It does not access the input value or accumulator, and performs no direct state write.

If the marker is nonzero:

1. It obtains the input value, marker value, and accumulator value needed for the calculation.
2. It updates the accumulator with its previous value plus the difference between the input value and marker.
3. After writing the accumulator, it writes zero to the marker.
4. It returns.

The counter is not accessed on this path.

The calculation has the represented grouping “input value minus marker, then plus accumulator.” No guard rejects an input value smaller than the marker. When representable under signed 32-bit arithmetic, a negative difference reduces the accumulator.

The marker condition and arithmetic expression are distinct source-level uses of the marker. Under interfering mutation, the representation does not establish that the tested value and the arithmetic value must agree.

The accumulator write precedes the marker clear. No relative order is established among the individual operand reads within the arithmetic expression. The operation is not transactional: the function contains no rollback if the accumulator write succeeds but the subsequent marker write fails.

### Other tags

For any stable tag other than 20 or 21, the function returns without directly reading or writing the three state fields and without reading the input value.

This does not make an invalid record address safe: tag access remains necessary.
