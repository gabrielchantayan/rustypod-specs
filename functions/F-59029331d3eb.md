# F-59029331d3eb

## Purpose

F-59029331d3eb obtains two dependency results, uses them and caller-record data to construct an object-like value, and submits that value through a mutable slot. It records the submission result and a status in a destination record captured from the caller’s input record.

When submission does not return the distinguished failure value and the object status is zero, the function invokes a further dependency. It then conditionally copies a destination field into secondary storage.

“Construction,” “submission,” “object,” and “status” describe the visible relationships; their domain meanings are inferred, not established.

This contract describes the supplied static representation. Dependency implementations, original declarations, and runtime behavior are unavailable. No runtime tests have been performed.

| Offset | Represented access | Role |
|---|---|---|
| `+0x00` | One 32-bit read | Destination address captured before dependency calls. |

| Offset | Represented access | Role |

### Object layout

For a submission result other than `-1`, the post-submission slot value is used as an object address. A 32-bit status is read at object offset `+0x1C`.

No other object fields are explicitly accessed by this body. Dependencies may access additional storage.

### Return value

The represented return is the 64-bit concatenation of high word `1` and low word `0x400`:

**`0x0000000100000400`**

Every normally returning branch produces this represented value. Whether the original interface declared or consumed a 64-bit scalar return is unresolved.

### Address and arithmetic assumptions

There are no explicit overflow or address-range checks. This contract does not assign portable wrapping semantics to signed address arithmetic or promise meaningful behavior for overflowing additions. Acceptance expectations assume valid address calculations and storage for every reached access.

## Behavior

### Initial capture and preparation

Before any dependency call, the function reads input `+0x00` and retains that value as the destination base. Later modifications of the input’s destination word do not select a different destination for this invocation.

The function then calls:

1. F-8157a180d901 with `0x54`, decimal 84.
2. F-ecd1af0519f9 with the input-record address advanced by `0x04`.

The first call’s result and the second call’s result become the first two construction arguments.

The byte-derived construction inputs are evaluated after these calls. Mutations made by either dependency can therefore affect those inputs. The representation does not establish the relative evaluation order of the byte read at `+0x0D` and the word-derived character argument at `+0x0C`.

### Construction

F-3fc3239fa339 receives seven arguments in this positional order:

1. The result of F-8157a180d901.
2. The result of F-ecd1af0519f9.
3. The byte read at input `+0x0D`.
4. The integer obtained by converting the word at input `+0x0C` through plain character.
5. `0x400`, decimal 1024.
6. `1`.
7. `0`.

Argument position does not imply an evaluation order for the two record-derived expressions.

The construction result overwrites the local slot initially populated from the fourth function argument. No visible check rejects either preparatory result or the construction result.

### Submission

F-95df8f1d704c receives the unchanged first function argument and the address of the mutable local slot.

The dependency can replace that slot’s contents. Subsequent object-relative operations use the slot value after submission returns, not necessarily the construction result.

The returned 32-bit submission result is written to destination `+0x34`. This write precedes both the failure-status write and any object-status read.

### Distinguished failure

If the submission result is exactly signed 32-bit `-1`, with bit pattern `0xFFFFFFFF`, destination `+0x28` receives `0x19`, decimal 25.

On this branch, the body does not explicitly:

- Read object `+0x1C`.
- Call F-ba73242d24e3.
- Read destination `+0x14`.
- Read destination `+0x30` for propagation.
- Write to a secondary record.

No other negative result receives this treatment.

### Nonfailure status handling

For every submission result other than `-1`, the function reads the 32-bit status at offset `+0x1C` from the current slot value and writes that status to destination `+0x28`.

The complete status value is copied without range checking or translation.

If the status is nonzero, there are no further explicit record accesses before return. A copied status of 25 is therefore possible independently of the distinguished failure branch. The submission-result field preserves the distinction, subject to later mutation or aliasing.

### Zero-status processing

If the status read from the object is zero, F-ba73242d24e3 is called with:

- The current object address from the local slot.
- The address of destination `+0x30`.

Its return value, if any, is unused.

The supplied address does not prove that the dependency initializes destination `+0x30`. Nor does it establish allocation, transfer, retention, or release behavior.

The branch decision uses the status already read. The body does not re-read destination `+0x28` or object status after this dependency returns.

### Secondary propagation: check and reload

After F-ba73242d24e3 returns, the function reads destination `+0x14` to test whether it is nonzero.

If this **check read** yields zero, no secondary assignment is performed. In particular, the body does not perform the assignment’s second read of destination `+0x14` or its read of destination `+0x30`.

If the check read yields nonzero, the assignment requires two additional reads:

- A second 32-bit read of destination `+0x14`, used to form the secondary write address.
- A 32-bit read of destination `+0x30`, used as the value to write.

The representation does **not** establish the relative evaluation order of those two reads. Both belong to the taken assignment, after the nonzero check; neither should be described as necessarily preceding the other.

The function writes the obtained value to offset `+0x08` from the address obtained by the **second** `+0x14` read. The checked value is not retained as the assignment’s destination address.

Consequences:

- The nonzero check does not guarantee that the reloaded address is equal to the checked value.
- There is no second nonzero check on the reloaded address.
- A zero reloaded value is not treated as a request to skip the assignment.
- The dependency’s post-call mutations can affect the checked address, the reloaded address, and the propagated value.
- Any difference between the two address reads must be described in terms of their actual observations, without assuming synchronization or a supported concurrent-mutation model.

## Side effects

### Explicit ordering

The visible sequence establishes these ordering relationships:

1. The destination base is captured.
2. The preparatory dependencies, construction dependency, and submission dependency run in that order.
3. Destination `+0x34` receives the submission result.
4. On failure, destination `+0x28` receives 25; otherwise, object status is read and then written to destination `+0x28`.
5. Only for zero object status, F-ba73242d24e3 runs.
6. After that call, destination `+0x14` is read for the nonzero check.
7. Only if the check succeeds, destination `+0x14` is reloaded and destination `+0x30` is read, with their relative order unspecified.
8. The secondary 32-bit write uses those assignment-read values.

These are represented memory operations, not guarantees of atomicity, synchronization, transactional behavior, or rollback.

### Aliasing and mutation

The body contains no checks prohibiting overlap among the input record, destination record, object, and secondary storage.

Earlier writes can therefore influence later reads when storage overlaps. For example, the submission-result write precedes the object-status read; those accesses cannot be treated as independent if they address overlapping storage.

Dependency calls may mutate accessible records or other state. A mutation to the input’s destination word does not replace the already captured destination base, but a mutation to a field within that destination can affect later reads.

The function does not restore destination status or submission-result fields after the final dependency or secondary write. Their final values are not guaranteed to equal the earlier explicit writes if later mutation or aliasing changes them.

### Ownership and validity

There is no explicit release operation in this body. This establishes neither a leak nor ownership by the caller.

Required validity is path-dependent:

- The input record must support the actual reads and the interior-region dependency call.
- The captured destination must support each reached field access.
- A nonfailure submission must leave a slot value supporting the status read.
- Zero-status processing must satisfy F-ba73242d24e3’s unknown requirements.
- A taken propagation assignment requires valid storage at offset `+0x08` from the **reloaded** secondary address.

A valid nonzero checked address alone is insufficient for the last requirement.

No explicit null, bounds, alignment, or lifetime checks protect these operations. Invalid storage has no defined recovery path in the supplied body.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, they assume valid storage, returning dependencies, and no additional mutations or aliasing that change the observations.

### Distinguished failure

If submission returns `-1`, destination `+0x34` receives `0xFFFFFFFF`, followed by 25 at `+0x28`. There is no explicit object-status read or final dependency call. The represented return is `0x0000000100000400`.

### Nonzero status

If submission returns 7 and the post-submission object status is 6, destination `+0x34` receives 7 and destination `+0x28` receives 6. F-ba73242d24e3 and secondary propagation are skipped.

If submission instead returns `-2`, the function still attempts the object-status read. It does not substitute 25 solely because the submission result is negative.

### Replaced object

If construction produces one address and submission replaces the mutable slot with another valid address, the status comes from the replacement object. If that status is zero, the replacement object address is passed to F-ba73242d24e3.

### Zero secondary check

If object status is zero and the first post-call read of destination `+0x14` yields zero, the final dependency has already run, but the body performs no secondary assignment. It neither reloads `+0x14` for that assignment nor reads `+0x30` as its source value.

### Stable secondary address

If the post-call check read and subsequent reload of destination `+0x14` both yield the same valid address, and the assignment’s read of `+0x30` yields `0x12345678`, that value is written at offset `+0x08` from that address.

The copied value need not be a pointer or have been newly initialized by the final dependency.

### Different check and reload observations

Conditionally, if the check read yields one nonzero address but the assignment reload yields a different valid address, the write targets offset `+0x08` from the **second** address. The first address only enabled the branch.

This expectation does not establish a supported mechanism for concurrent mutation. It identifies which represented read supplies the write address.

If the reload yields zero, the body has no guard suppressing the assignment. Validity or fault behavior for the resulting address is not specified.

### Assignment-read ordering

An acceptance requirement must not demand that the address reload precede the `+0x30` read, or that the value read precede the address reload. Neither relative order is established.

### Character conversion

Under an 8-bit-character model, a selected value of `0x7F` promotes to 127 for either ordinary signed or unsigned character interpretation. For `0x80`, signed 8-bit character interpretation gives −128, while unsigned interpretation gives 128. Choosing one interpretation requires additional platform evidence.
