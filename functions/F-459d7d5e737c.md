# F-459d7d5e737c

## Purpose

F-459d7d5e737c scans a selected collection of fixed-size records, proposes links between qualifying pairs, and then reconciles those links in a second pass.

The first pass considers an ordered pair only when the first record is eligible, the records have complementary tags, their coordinates have the required ordering, and their intervals overlap sufficiently. A qualifying pair produces one computed cost. Each endpoint independently accepts the other as its link target if that cost is strictly lower than its current stored cost.

The second pass increments a counter at every nonnull link target. It retains reciprocal links and converts nonreciprocal links into a different pointer field.

This describes the visible operations. Interpreting the records as geometric objects or the links as a matching algorithm is inferred intent, not an established application-level contract.

## Interface

## Behavior

### Setup and cached values

The visible setup reads, in order:

1. The record start address.
2. The secondary-object address and then its scale input.
3. The selected tag.
4. The record count used to compute the end address.

The end address is the start address plus the record count multiplied by 48, represented as a 32-bit address value.

Two scale-derived quantities are prepared before scanning:

- **Required overlap:** the signed result of multiplying the scale input by eight, then dividing by 2048 with truncation toward zero. If that result is exactly zero, it is replaced by one.
- **Dependency argument:** the signed product of a global 32-bit multiplier and the scale input, divided by 2048 with truncation toward zero.

The division description applies when the intermediate signed values are interpreted as the 32-bit values shown by the evidence. Multiplication overflow is discussed under Uncertainties.

Only a zero required-overlap result is replaced. A negative result remains negative; this is not a general clamp to a positive minimum.

The start, end, selected tag, overlap threshold, and dependency argument are prepared once. They are not visibly refreshed after dependency calls.

### First pass: proposing links

The outer scan begins at the record start address and advances by 48 bytes. Each loop condition compares the current address with the end address using an unsigned comparison.

For each outer record:

1. Its field at +40 is read.
2. Its field at +36 is compared with that value.
3. Only if those values differ is its tag tested against the selected tag.

An outer record proceeds to pair examination only when both tests pass. A record failing these tests can still be used as an inner candidate by another outer record.

For each eligible outer record, an inner scan visits the entire collection in the same address order. The record itself is skipped. Every other candidate is evaluated through these gates:

1. **Complementary tags.** The candidate tag and a freshly read outer tag must sum to zero under the represented promotions and 32-bit arithmetic.
2. **Coordinate ordering.** Candidate coordinate minus outer coordinate must be nonnegative.
3. **Sufficient interval overlap.** The smaller upper bound minus the larger lower bound must be at least the required overlap.

The coordinate difference lies between −65,535 and 65,535 because both coordinates are signed 16-bit values. The interval difference has the same range. These particular differences therefore fit a signed 32-bit integer without overflow.

On a signed-character interpretation, the tag gate admits additive opposites such as +1 and −1, and also two zero tags. On an unsigned-character interpretation, only two zero tags can pass. Equal tag bytes alone do not establish complementarity.

The interval test uses subtraction without adding one. Intervals that merely touch produce overlap zero. There is no normalization of reversed interval bounds.

### Cost computation and independent updates

For every ordered pair passing all gates, F-870c4fcf7295 is called once with the prepared dependency argument. Its returned integer is added to the previously computed coordinate difference to obtain a proposed cost.

The updates occur in this order:

1. Read the outer record’s current best cost.
2. If the proposed cost is strictly smaller:
   - Write the proposed cost to the outer best-cost field.
   - Write the candidate address to the outer active-link field.
3. Read the candidate’s current best cost.
4. If the same proposed cost is strictly smaller:
   - Write it to the candidate best-cost field.
   - Write the outer address to the candidate active-link field.

Acceptance is independent at the two endpoints. A pair can update both endpoints, one endpoint, or neither. Equal costs do not replace existing links.

No active links, best costs, counters, or secondary links are initialized by this routine before processing. Their entry values influence the result.

The dependency call precedes both best-cost comparisons. The routine does not visibly revalidate tags, coordinates, interval bounds, or eligibility after that call. Its calculated coordinate difference remains the one obtained before the call. Conversely, best-cost fields are read after the call, so dependency writes to those fields can affect acceptance.

An unordered pair can be examined in both directions if both records satisfy the outer eligibility tests and both coordinate-order tests pass. For distinct coordinates, ordinarily only the increasing-coordinate direction passes. With equal coordinates, both directions can pass. A dependency call is made for each qualifying ordered encounter; there is no visible deduplication or result caching.

### Second pass: counting and reconciling links

After all pair processing, the routine scans the same span again in ascending address order.

For each record:

1. Read its active-link address.
2. If that address is zero, do nothing further for that record.
3. Otherwise, increment the target’s 32-bit counter at offset +24.
4. Read the target’s active-link address.
5. If that value equals the current record’s address, leave the current active link unchanged.
6. Otherwise:
   - Clear the current record’s active-link field to zero.
   - Read the target’s active-link field again.
   - Copy that newly read value to the current record’s secondary-link field at +20.

Thus, every encountered nonnull active link causes a target counter increment, including a link subsequently removed as nonreciprocal.

Reciprocal links do not cause the secondary-link field to be cleared or updated. Null links also leave that field unchanged.

This pass is sequential and operates on live state, not a snapshot. A link cleared for an earlier record can affect the reciprocity test or copied secondary link of a later record. The copied value is not necessarily nonzero, valid, or inside the selected collection.

The second read of a target’s active link is distinct from the read used for the reciprocity decision. It occurs after clearing the current record’s active link.

## Side effects

Visible direct writes are limited to:

- Best costs and active links during pair processing.
- Counters at nonnull active-link targets during reconciliation.
- Clearing nonreciprocal active links.
- Writing secondary links for those nonreciprocal cases.

The routine does not visibly allocate, release, or transfer ownership of storage. Storing an address in a link field establishes no demonstrated ownership rule.

Counter increments do not represent the final number of retained reciprocal links. They count nonnull links encountered during this invocation’s reconciliation pass. Counters are neither reset nor decremented when a link is cleared.

Targets are dereferenced without a collection-membership check. Consequently, direct counter writes can occur outside the scanned record span.

F-870c4fcf7295 may have additional effects. Its memory access, allocation, ownership, global-state behavior, and error behavior are not established here.

No rollback is visible. If execution stops during a dependency call or an invalid memory access, earlier writes are not visibly undone.

## Acceptance examples

These examples are conditional static consequences, not results of runtime testing.

1. **Empty span.**  
   If the computed end address equals the start address, neither scan processes a record and there are no dependency calls. Setup reads, including the scale and global-multiplier accesses, still occur.

2. **Zero scale.**  
   With scale zero and ordinary non-overflowing arithmetic, the required overlap becomes one and the dependency argument is zero. A pair whose intervals only touch fails the overlap gate.

3. **Positive scale.**  
   With scale 256, the required overlap is one. A pair with outer interval [0, 10] and candidate interval [5, 15] has overlap five and passes that gate.

4. **Negative overlap threshold.**  
   With scale −256, the required overlap is −1. An interval difference of −1 passes. The routine does not replace this negative threshold with one.

5. **Only one endpoint improves.**  
   Assume a qualifying pair has coordinate difference three, the dependency returns seven, and addition does not overflow. The proposed cost is ten. If the outer best cost is twenty and the candidate best cost is five, only the outer endpoint is updated.

6. **Equal-cost retention.**  
   If a proposed cost equals an endpoint’s existing best cost, that endpoint’s existing active link remains unchanged by that proposal, regardless of which candidate was encountered.

7. **One-way link to an unlinked record.**  
   Suppose record A links to B, B has no active link, and no other relevant state changes intervene. Processing A increments B’s counter, clears A’s active link, and writes zero to A’s secondary link. Processing B makes no further change.

8. **Reciprocal pair.**  
   Suppose A links to B and B links to A. Each link is retained when processed, and each target counter is incremented once for this pair. Existing secondary-link values remain untouched.

9. **Order-sensitive chain.**  
   Suppose records are visited in the order A, B, C, with links A→B, B→C, and C→A. Processing A clears A’s link and copies C into A’s secondary link. Processing B then clears B’s link and copies A into B’s secondary link. Processing C sees A’s now-null link, clears C’s link, and copies zero into C’s secondary link. All three target-counter increments still occur.

10. **Outer ineligibility does not exclude a candidate.**  
    A record with equal fields at +36 and +40 is skipped as an outer record. It may still receive a proposed link, a best-cost update, or a reconciliation counter increment through another record.

## Uncertainties

The following are **documented_only**:

- **Character signedness.** The representation uses plain character reads. Complementary nonzero tags require a signed-character interpretation; that interpretation is not independently proven.
- **Overflow semantics.** Address calculations, scale multiplication, multiplier multiplication, proposed-cost addition, and counter increments can exceed their mathematical ranges. The representation establishes fixed-width operations but does not independently establish portable signed-overflow semantics. Examples above avoid such overflow.
- **Wrapped scan bounds.** Start and end are compared as unsigned addresses. A wrapped end address does not reliably describe a valid span. Pointer increments can also wrap; no general termination guarantee is established for malformed ranges.
- **Aliasing and concurrency.** No non-aliasing guarantee, synchronization, or concurrent-mutation model is supplied. Descriptors, records, and link targets are not visibly checked for overlap.
- **Dependency behavior.** No guarantee establishes that F-870c4fcf7295 preserves record storage, globals, ownership, or other memory.
- **Application meaning.** Geometric matching, nearest-neighbor selection, and the meaning of secondary links are inferred interpretations, not proven contracts.
- **Failure reporting.** No explicit error branch is visible. Dependency failure behavior and invalid-access outcomes are unknown.
