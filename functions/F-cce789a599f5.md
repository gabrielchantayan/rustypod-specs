# F-cce789a599f5

## Purpose

F-cce789a599f5 processes a collection into a destination identified by a caller-supplied cursor cell.

The supplied static representation establishes two paths:

- **Direct:** process each fetched element using the caller’s cursor cell.
- **Staged:** process elements using a temporary-output cursor, build 12-byte records, submit those records to an ordering dependency, and transfer the recorded results to the destination. Mode 2 additionally submits the resulting element sequence for collection writeback.

The apparent intent is to produce output either in collection order or in an order determined from staged results. The actual ordering criterion is unknown.

The ordering call receives a callback-related value read from a global location. The location is fixed in the supplied representation; its contents are not established as constant. The read occurs after record construction and after the separate collection-count query immediately preceding the ordering call. Earlier dependencies are not assumed to preserve that global.

This contract describes static evidence, not observed execution. No runtime tests have been performed.

### Result

- **0:** at least one of the two staged allocation results is zero.
- **1:** execution reaches the normal end of the selected path.

Status 1 is not an independently verified success result for processing, ordering, transfer, writeback, or release. Their results are ignored or otherwise not validated.

## Behavior

### Path selection

Mode 0 selects direct processing without a separate count query for the selection decision.

For any nonzero mode, F-10b760faca36 is first called with the collection. Its result is compared as a signed 32-bit count:

- Less than 2 selects direct processing.
- At least 2 selects staging.

The selection count is not reused as an authoritative bound. Later phases obtain fresh counts.

Consequently, mode 2 does not necessarily cause staging or collection writeback. A selection count of one, zero, or a negative value selects the direct path.

### Direct processing

The direct loop starts at index zero and queries F-10b760faca36 before every possible iteration, including the terminating check.

While the index is less than the newly obtained signed count:

1. F-6bbddce1b930 fetches the element at that index.
2. F-211bb2c8ea63 receives the fetched value, the caller’s destination cursor-cell address, and the processing context.
3. The index advances by one.

The processing result is ignored.

The wrapper does not explicitly read or write the destination cursor cell on this path. Any output production or cursor advancement is a dependency effect.

A changing count can shorten or extend iteration. If the first loop count is zero or negative, no element is fetched or processed and the function normally returns 1.

This path makes no staged allocation, ordering, transfer, explicit collection-writeback, or release calls.

### Staged allocation

After staging is selected, another count query supplies the record-allocation size calculation. The wrapper multiplies that count by 12 and calls F-43da6b23bd44 with the calculated value and two zero arguments.

It then calls F-43da6b23bd44 with the scratch request and two zero arguments.

The first result is used as a record-array base. The second is used as the initial scratch cursor.

Both calls occur before either result is checked. A zero first result therefore does not suppress the second request.

If either result is zero, the function returns 0 immediately. No release call occurs on this branch, including when the other request returned a nonzero value.

There is no visible multiplication-overflow check, negative-size rejection, or scratch-capacity validation. Exact behavior outside valid arithmetic and allocation domains is **documented_only**.

### Record construction

When both allocation results are nonzero, a local writable 32-bit cursor cell is initialized with the scratch allocation result.

Record generation starts at index zero and the record-array base. Each loop check obtains a fresh count. For every accepted index, the observable order is:

1. Fetch the element through F-6bbddce1b930.
2. Read the current local scratch cursor and store it in the record’s first word.
3. Call F-211bb2c8ea63 with the fetched element, the local cursor-cell address, and the processing context.
4. Store the processing result in the second word.
5. Store the fetched element value in the third word.
6. Advance to the next 12-byte record.

Each record has this layout:

| Byte offset | Width | Meaning established by use |
|---|---:|---|
| 0 | 32 bits | Scratch cursor captured before processing |
| 4 | 32 bits | Processing result, later supplied as transfer extent and used for destination advancement |
| 8 | 32 bits | Fetched element value retained for possible collection writeback |

The first word is a pre-processing snapshot. The wrapper does not itself advance the scratch cursor; any advancement during processing comes from dependency effects on the local cell.

The second word’s use supports an extent interpretation. Its units, valid range, and interpretation by the transfer dependency are not independently established.

The function does not retain a separate initialized-record count. Count growth can cause construction to exceed the original allocation calculation. Count shrinkage can leave allocated records unwritten.

### Ordering and callback-global observation

After the record-construction loop ends, the wrapper performs these operations in order:

1. Obtain a fresh collection count through F-10b760faca36.
2. Read the contents of the callback-bearing global location.
3. Call F-4d426a8054f4 with the record-array base, that fresh count, the record width of 12 bytes, and the value read from the global.

The global is not read once at entry, before allocation, or before record construction. Its contents are observed after all construction-time calls and after the immediately preceding count call.

This distinction is observable: processing dependencies, collection dependencies, or other permitted state changes may alter the global before its read. In particular, the immediately preceding count query can affect the callback-related value subsequently supplied to the ordering operation.

The wrapper contains no explicit write to this global and no validation of its contents. The fixed identity of the storage location does not establish immutability, a fixed callback target, callback validity, or preservation by any dependency.

The call shape supports an ordering interpretation, but neither the ordering dependency nor the callback implementation is supplied. Ordering criterion, stability, direction, failure behavior, and treatment of invalid callback values remain unknown. No ordering result is checked.

The ordering count need not equal the allocation count or the number of initialized records.

### Transfer to the destination

After the ordering call returns, the wrapper explicitly reads the caller’s destination cursor cell into its local cursor cell.

Transfer traversal begins at the record-array base. Every loop check obtains another fresh collection count. Each accepted iteration:

1. Calls the unmapped transfer dependency with the current local destination cursor, the record’s first word, and the record’s second word.
2. Reads the record’s second word again after the call returns.
3. Advances the record traversal by 12 bytes.
4. Adds the re-read second word to the local destination cursor.

The extent passed into the transfer call and the extent used afterward need not match if accessible record storage changes during that call.

The local cursor cell is the same local storage previously exposed to processing as the scratch cursor cell. The evidence does not establish that dependencies forget its address or preserve its contents. Normal cursor-advancement examples therefore require dependencies not to mutate this cell unexpectedly.

After transfer traversal terminates, the wrapper writes the local cursor to the caller’s destination cursor cell exactly once. This explicit write occurs before optional collection writeback and before release calls. Later dependency effects are not constrained to preserve the written value.

### Optional collection writeback

Only staged execution with mode exactly 2 performs explicit collection writeback.

This traversal starts at index zero and the record-array base. Each loop check obtains a fresh collection count. For each accepted index, F-c2674fa3e73d receives the collection, the index, and the current record’s third word. Traversal then advances by 12 bytes.

The values used are the record contents at writeback time, not a separately preserved original element sequence.

Other modes omit this phase. Mode 2 on the direct path also omits it. Dependencies on either path may nevertheless mutate the collection.

### Release and normal completion

After transfer and any mode-2 writeback, F-5990a26eaaa3 is called first with the original record allocation result, then with the original scratch allocation result.

The scratch release argument is not the advanced scratch or destination cursor.

If both release calls return normally, the function returns 1. No rollback or recovery path is visible for abnormal execution inside a dependency.

- Indexed element fetches and processing calls.
- Two staged allocation requests, even when the first returns zero.
- Writes to three-word temporary records.
- A read from the callback-bearing global after record construction and the ordering-count query.
- An ordering call receiving the global’s then-observed contents.
- Transfer calls using record-supplied values.
- A post-call re-read of each transferred record’s extent.
- One explicit destination cursor-cell write after staged transfer.
- Optional indexed collection-writeback calls.
- Two release calls on normal staged completion.

The wrapper does not explicitly write the callback-bearing global. Dependencies may change it; no preservation guarantee is supplied.

Passing an allocation or element value to a dependency does not establish ownership transfer. The release calls establish the wrapper’s cleanup attempts, not allocator/releaser compatibility or continued ownership.

The allocation-failure branch performs no explicit cleanup. There is no synchronization, snapshot enforcement, capacity check, or general rollback.

## Acceptance examples

These are conditional static expectations, not runtime results.

1. **Empty direct execution.** With mode 0 and an initial loop count of zero, the function returns 1 without fetching, processing, allocating, or explicitly dereferencing the destination cursor cell.

2. **Mode 2 with one element.** If the selection count is one and direct-loop counts remain one, index zero is processed once. No ordering or explicit collection writeback occurs.

3. **Negative mode with staging.** A negative mode and a selection count of at least two select staging. The negative mode does not enable writeback.

4. **Partial allocation success.** If the first request returns zero and the second returns nonzero, both requests occur, the result is 0, and neither result is passed to the release dependency.

5. **Callback global changed during construction.** Suppose processing changes the callback-bearing global, and it remains at that new value through the subsequent ordering-count query. The ordering call receives that new value, not an entry-time snapshot.

6. **Callback global changed by the ordering-count query.** Suppose record construction leaves one value in the global, but the immediately following count query replaces it with another. If it remains unchanged until read, the ordering call receives the replacement. No separate validation is performed.

7. **Conditional reordered transfer.** Assume a stable count of two, valid storage, two processing results of four address units each, an ordering operation that places the second record first, and transfer behavior that copies those extents without unexpected mutation. The second staged region is transferred before the first, and the destination cursor advances by eight address units. This does not establish that the actual callback chooses that order.

8. **Conditional mode-2 writeback.** Under the preceding assumptions with mode 2, writeback submits the second fetched element for index zero and the first for index one. These calls follow the explicit destination cursor write.

9. **Count growth after sizing.** If sizing uses two records but construction permits three, no resizing or explicit rejection occurs. Safe storage access is not established.

10. **Extent mutation during transfer.** If a transfer receives extent four but changes that record’s second word to six before returning, the subsequent cursor addition uses six, assuming the call returns and the relevant storage remains valid.

## Uncertainties

The following are **documented_only**, not additional guarantees:

- **Arithmetic:** The representation uses 32-bit counts, record words, and cursor values. No overflow checks are visible for multiplication, index advancement, or cursor addition. Exact overflow and address-conversion semantics are not established.
- **Count consistency:** Selection, sizing, construction, ordering, transfer, and writeback use distinct observations. Later phases can encounter unwritten records.
- **Capacity:** Neither scratch output nor destination transfers are checked against available storage.
- **Callback global:** Its initialization, original declared type, lifetime, mutability rules, and synchronization are unknown. Only its read location and sequencing are established.
- **Callback behavior:** No particular comparison rule, stable ordering, or valid callback target is established.
- **Transfer:** Copying is inferred intent. Units, overlap handling, and failure behavior are unknown.
- **Dependency effects:** Globals, records, collection state, cursor storage, allocation ownership, and retained values are not assumed preserved.
- **Errors:** Only zero allocation results explicitly produce status 0. Other failures may remain unchecked or prevent normal return.
- **Lifetimes:** Continued validity of stored element values, temporary regions, and exposed cursor-cell addresses is not proved.
