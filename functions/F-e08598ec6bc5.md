# F-e08598ec6bc5

## Purpose

F-e08598ec6bc5 accepts an optional length-prefixed sequence of 16-bit units and attempts to obtain a one-based record identifier in a mutable context. Depending on captured context flags, it searches for an existing record before allocating a descriptor and placing a new payload.

Established behavior includes duplicate lookup, descriptor free-list manipulation, storage-adjustment requests, payload-space accounting, and conditional counter increments. “Interning” and “reference acquisition” are **inferred intent**, not established API guarantees. Neither a character encoding nor a terminator convention is established.

Successful completion returns zero. An initially empty input returns zero after admission, without an additional local output write. It does **not** guarantee a final zero identifier: the output was cleared before an intervening dependency call that is not known to preserve it.

Explicit admission rejection returns −50. Checked preparation and storage-adjustment failures propagate their dependency results.

This is a static behavioral contract. No runtime tests have been performed.

## Interface

### Arguments and result

The function receives three machine-level arguments:

| Argument | Established interpretation |
|---|---|
| Context address | A 32-bit address identifying mutable context state. |
| Sequence address | Zero, or an address whose first unsigned 16-bit unit gives the payload length in 16-bit units. |
| Identifier output address | Address of a writable 32-bit word. Its incoming contents are also passed to a dependency. |

The result is a signed 32-bit status.

The output address is not safely optional. After initial admission succeeds, its contents are read without a null check. A later conditional clearing does not protect that earlier read.

For nonnull input, the payload starts two bytes after the sequence address. The byte count is twice the unsigned prefix, ranging from zero through 131,070. This conversion fits in 32 bits. For null input, both the payload address and initial byte count are zero.

Only the prefix is captured before the first dependency call. Payload bytes are consumed later; no immutable input snapshot is established.

## Behavior

### Admission and initial output handling

The observable sequence is:

1. Capture the optional input prefix, derived payload address, and byte count.
2. Invoke F-0aff6a5050f5 with no explicit argument visible in the supplied body.
3. If its result is zero, return −50 before any local output read or write.
4. Read the incoming output word and invoke F-808c5d99c3bd with the context and that value.
5. If preparation returns nonzero, return that result without a local output-clearing write.
6. Otherwise, clear the output word to zero when its address is nonnull.
7. Invoke F-0aff6a5050f5 with the context argument.
8. Reject with −50 if that result is zero.
9. Read +48. Reject if nonzero. Only when it is zero, read flags at +4 and reject if bit 6 is set.

Bit 0 from this admission-time flags read is retained for later decisions. Subsequent changes to bit 0 do not replace that captured decision.

If the captured byte count is zero, return zero at this point. There is no subsequent local output write, lookup, or insertion. The second admission dependency may already have changed the output, directly or through aliased storage; therefore the final identifier remains dependency-defined absent preservation assumptions.

- Set: invoke F-849b785f50ce.

For linear lookup, the payload base, counter base, and descriptor base are captured, in that order, after the pre-lookup dependency. Descriptors are visited in increasing zero-based order. The signed bound at +28 is reread for each loop condition; a nonpositive bound prevents the first iteration.

For each descriptor:

2. If that result is nonzero, the descriptor’s second word is compared with the captured byte count.
3. If lengths match, the unidentified comparison dependency receives the input payload address, stored-payload address, and byte count.

### Descriptor selection and storage growth

Every allocation-loop iteration starts by invoking F-30a0e9a392e7 with the context and zero. Its result is ignored.

If +32 is nonzero, the function uses the descriptor base and one-based head to locate an eight-byte descriptor. It replaces +32 with that descriptor’s second word before testing whether the calculated descriptor pointer is nonzero.

A nonzero calculated pointer proceeds to payload placement. Its one-based identifier is derived from the descriptor’s byte displacement relative to a newly read descriptor-array base, shifted right by three, plus one. The pointer test is not validation of the index or accessible storage.

If no usable descriptor is obtained, descriptor storage is adjusted:

1. If the unsigned value at +44 is below 4,096, the field is doubled.
2. F-7eff13797b9b receives the address of +8 and an amount formed from a read of +44 multiplied by eight.
3. A nonzero result is returned immediately.
4. If captured bit 0 is set, F-7eff13797b9b receives the address of +12 and an amount formed from a **new read** of +44 multiplied by four.
5. If counter adjustment fails, F-7eff13797b9b is invoked again for +8, with an amount formed from **another read** of +44 multiplied by negative eight. That rollback result is ignored; the counter-adjustment failure is returned.

These are separate context reads around calls that may mutate the context. The rollback request is not necessarily the negative of the original descriptor-adjustment request. An exact inverse requires additional stability assumptions and suitable arithmetic.

After successful required adjustments, initialization begins at the descriptor address calculated from the then-current descriptor base and +28. Initialization does not operate on a captured count-and-batch pair:

- The unsigned iteration position starts at zero.
- Every loop condition rereads +44.
- Each visited descriptor’s first word is set to `0x80000000`.
- Beginning with the second visited descriptor, the previous descriptor’s second word is assigned the current +28 value plus the iteration position plus one.
- The descriptor pointer advances by eight bytes per iteration.
- After the loop, +32 is assigned the then-current +28 plus one.
- Then +28 is assigned the sum of its then-current value and the then-current +44.

The descriptor writes themselves can affect later field reads if storage aliases the context. No single original count or batch governs all these operations.

**The final visited descriptor’s second word is not explicitly initialized.** A terminating free-list link requires an additional storage guarantee not established here. If no descriptors are visited, neither descriptor word is initialized, but the final head and count assignments still occur.

Under stable, non-aliasing storage and a fixed positive batch, this builds links between newly visited descriptors and advances the count by that batch. That simplified description does not apply unconditionally.

Allocation then repeats, including another F-30a0e9a392e7 invocation.

## Side effects

Local writes can affect the output, descriptors, counters, free-list head, descriptor count, payload-space accounting, and growth settings. Storage-adjustment dependencies receive handle-field addresses and may change handles or backing storage.

The operation is not transactional:

- Output clearing precedes later admission rejection.
- Lookup dependencies can modify the output even when lookup reports no match.
- Growth settings can change before an adjustment fails.
- Counter-adjustment failure triggers an attempted rollback whose amount uses a fresh batch read and whose result is ignored.
- Payload-adjustment failure relinks the selected descriptor but does not undo all preceding state changes.
- Counter increments have no overflow checks.
- Indexed insertion is invoked after local publication, and its result does not affect the returned success.

There is no local release of the input sequence and no explicit ownership transfer. Whether dependencies allocate, release, retain, or invalidate storage is **documented_only**. F-70a021fc7c24 is used as a payload-transfer operation, but overlap handling and transfer guarantees require its own contract.

The lookup call pair does not locally surround subsequent allocation. Thread safety, reentrancy, and global-state preservation are not established.
