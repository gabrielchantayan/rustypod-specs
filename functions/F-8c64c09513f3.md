# F-8c64c09513f3

## Purpose

F-8c64c09513f3 is a configuration-controlled routine accepting three unsigned words and returning one unsigned word. Its directly established data operation is a single-byte transformation:

\[
T(b)=(-41b)\bmod 256=(215b)\bmod 256.
\]

Two control states perform this transformation at calculated source and destination addresses. Other states initialize working values, calculate addresses and selectors, compare addresses, or save a return value.

The supplied body does **not** establish an ordinary buffer-processing API. In particular, it does not establish that the arguments are a length, source pointer, and destination pointer; that accesses are contiguous; that overlap is handled safely; or that the result counts processed bytes.

The contract is conditional on external configuration and target arithmetic semantics. Concrete traversal, valid argument ranges, and termination remain **documented_only**.

## Interface

### Arguments and result

The interface has three unsigned-word arguments:

| Argument | Established use when the argument-capture state executes |
|---|---|
| First | Replaces a working quantity subsequently used by destination preparation and one transfer’s post-store arithmetic. |
| Second | Replaces an arithmetic scratch value, which can feed fallback calculations. |
| Third | Replaces a candidate destination address. |

Argument capture is conditional. Entry alone does not install these arguments into the working state.

The result is a dedicated accumulator, initially zero. Only the result-saving state changes it: that state multiplies an external scale by a distinct **result factor**. Reaching the return state returns the saved accumulator unchanged.

The result factor is not the first-argument-related quantity. Consequently, neither a direct argument-to-result relationship nor a byte-count interpretation is established.

The following descriptive names distinguish persistent roles; they are specification terminology, not source identifiers.

| Working role | Initial value and significant updates |
|---|---|
| Quantity | Zero; receives the first argument; later replaced by progress, offset, and fallback arithmetic. |
| Scratch | Zero; receives the second argument; later receives transfer products, arithmetic differences, or the saved result. |
| Candidate destination | Zero; receives the third argument or the active destination. |
| Active destination | Zero; receives the candidate destination during destination preparation. |
| Active source and saved source address | Zero; established together by source preparation. |
| Working offset | Zero; replaced by progress, offset, and fallback arithmetic; used by source preparation. |
| Progression accumulator | Zero; receives a configured initial value or the scaled-index transfer’s post-store product. |

These roles are not interchangeable. In particular, the offset calculation consumes the **transfer accumulator**, whereas the progress calculation consumes the **progression accumulator**.

## Behavior

### Dispatch and configuration reads

Entry obtains an initial selector from an external word. Other working roles start at zero.

Each dispatch:

1. Reads the external dispatch multiplier into a temporary.
2. Takes the current scratch value as the default fallback input.
3. Reads the external selector base for a range check.
4. If that check admits a displacement from 0 through 17, reads the selector base **again** to determine the switch displacement.

The two base reads are distinct. No coherent configuration snapshot is established. If the first read admits dispatch but the second produces a displacement with no matching state, no state body executes. Control instead reaches the common arithmetic transition described below.

The range check includes subtraction followed by unsigned interpretation. Whether the subtraction itself has defined behavior depends on the undeclared external type and applicable signed arithmetic rules.

The routine references 33 external configuration locations. Repeated references to one location are not interchangeable with one cached value.

### Preparation and direct transitions

The visible state set includes these behaviors:

- Clear the result factor, then take a configured transition.
- Capture all three arguments, then continue.
- Clear the transfer accumulator, then continue.
- Load a configured value into the result factor.
- Load a configured initial value into the progression accumulator.
- Take a configured transition without changing data memory; two states use the same transition location.
- Load the selector from the selector-base location. With unchanged configuration and defined arithmetic, the next dispatch selects displacement zero.
- Return the saved result.

Source preparation forms the active source by adding an external address-related word to the working offset. It then reads its next-selector configuration, copies the working offset into the result factor, and saves the active source address for comparison.

Thus the source address does not directly receive the second argument. That argument is captured into scratch, while source preparation uses the separate working offset.

### Destination preparation

This state first reads a configured next selector and installs the candidate destination as the active destination. It then examines the quantity:

- **Zero:** scratch becomes zero; execution takes the already loaded transition.
- **One:** scratch receives a configured initial value, and a configured increment is also read; execution takes the already loaded transition.
- **Any other value:** the same initial-value and increment reads occur, but execution enters fallback using the increment as fallback input.

The quantity may have changed since argument capture. This is not an unconditional validation of the first argument.

For the quantity-one path, the increment read still occurs even though its temporary value is not subsequently used before the next dispatch resets the fallback input.

### Scaled-index transfer

The transfer offset is the product of the external scale and the current transfer index, interpreted through the target’s conversion rules. This product replaces the result factor.

The scale read occurs **before** the byte transfer. Both addresses use that calculated offset:

- Read one byte from active source plus offset.
- Store its transformed value at active destination plus offset.

After the store, scratch becomes the offset multiplied by the multiplier captured at dispatch. The state then reads its next-selector configuration and copies scratch into the progression accumulator.

It does not reread the multiplier after the store.

### Derived-offset transfer

This state uses the previously saved derived transfer offset:

- Read one byte from active source plus derived offset.
- Store its transformed value at active destination plus derived offset.

Only **after the store** does it read the external scale. Scratch becomes the product of the quantity, that scale, and the multiplier captured at dispatch. It then reads its next-selector configuration and copies scratch into the transfer accumulator.

This ordering differs materially from the scaled-index transfer. A store aliasing the scale location can affect this state’s post-store product, but cannot retroactively change the scale already used by a scaled-index transfer.

### Byte semantics and aliasing

There is no explicit read of the old destination byte or read-back after the store. The source value needed for the transformation is obtained before its destination write.

Under the 8-bit storage model, interpreting a loaded character as signed rather than unsigned does not change the final low-byte transformation. The two input interpretations differ by 256.

Identical source and destination addresses are not rejected. A later transfer may read a byte modified by an earlier transfer. Neither exact in-place operation nor partial overlap implies a protected traversal order.

### Address comparison

The comparison state tests whether the active destination is unsigned-less-than the saved source address.

It reads the “less-than” selector configuration even when the comparison is false. It then copies the active destination into the candidate destination and reads the other selector configuration, also unconditionally.

Under the normal word-arithmetic interpretation:

- Less-than selects the first configuration value.
- Equality or greater-than selects the second.

Both reads occur regardless of selection. This state does not itself transfer a byte or update the result factor. Its behavior establishes address-sensitive control flow, not overlap safety.

### Progress calculation

This calculation consumes the progression accumulator.

It obtains:

- A transfer-accumulator value from a configured factor shifted right one, multiplied by the progression accumulator.
- A result-factor value from a **separate read** of that factor, multiplied by the progression accumulator, plus one.
- A transfer index from the progression accumulator plus a configured increment.

The shifted factor’s type is unknown. Its right shift is logical halving only if the factor is unsigned or target semantics independently establish that result. Later multiplication by an unsigned value does not determine the earlier shift’s signedness.

The calculation also:

- Places transfer accumulator minus one into scratch.
- Replaces the working offset with the complement of scratch OR a configured mask.
- Replaces the quantity using a configured subtraction/OR/XOR/complement expression involving the transfer accumulator, result factor, and working offset.
- Replaces scratch with quantity minus transfer accumulator.

The branch condition is scratch’s unsigned high bit, not an ordinary unsigned less-than test.

Selector construction uses two reads of **one** configuration location:

- First read: its value plus 13 becomes one candidate.
- Second read: its unadjusted value becomes the other candidate.

High bit zero selects the first-read value plus 13; high bit one selects the second-read value. The common transition also copies scratch into the result factor, replacing its earlier product-plus-one value.

### Offset calculation

This calculation consumes the transfer accumulator, **not** the quantity populated from the first argument.

It derives:

- An index product from an external index factor times the transfer accumulator.
- The derived transfer offset from a right-shifted external factor times that accumulator.
- A working offset incorporating the index product, \(0x5C007C00\), a separately read full-factor product plus one, and a configured OR mask.
- A transfer index equal to the index product plus 14.
- Scratch from an expression involving subtraction, XOR, complement, configured masks, and constants −17, \(0xFFFFFFEF\), and 15.

The right-shift qualification from the progress calculation applies here too: unsigned multiplication after the shift does not establish logical halving.

The quantity is then replaced by **transfer accumulator minus a configured decrement**. It is not decremented from its previous value.

The condition is formed by interpreting scratch as signed, shifting right 31, and adding one. With conventional arithmetic signed right shift:

- Negative scratch gives condition zero.
- Nonnegative scratch gives condition one.

The state reads its selector configuration twice, first subtracting one from the first read and then obtaining the unadjusted second read. Condition zero selects the first-read value minus one; condition one selects the second-read value.

The common transition copies scratch into the result factor. Nonstandard signed-shift behavior can invalidate this binary-choice interpretation and remains **documented_only**.

### Fallback and common arithmetic transition

Fallback is reached by an explicit state, an out-of-range range-check result, or the nonzero/non-one destination-preparation path.

Its input is normally dispatch-entry scratch. Destination preparation instead supplies its configured increment.

Fallback replaces the working offset with input times external scale. It replaces the quantity using an index-factor product minus one, ORed with working offset plus one. Scratch is then calculated using the input, quantity, a repeatedly read mask, and a separately read index factor shifted right 30.

These repeated configuration occurrences are distinct reads. The shifted external factor’s type is unknown; its shift must not automatically be treated as unsigned.

Scratch’s unsigned high bit supplies the fallback condition. The selector configuration is read twice:

- First read minus six supplies the condition-zero candidate.
- Unadjusted second read supplies the condition-one candidate.

The common arithmetic transition copies scratch into the result factor. For a binary condition \(c\), its selector calculation is a word-arithmetic weighted combination: \(c\) times the unadjusted candidate, plus \(c\mathbin{\mathrm{XOR}}1\) times the adjusted candidate. Both selector reads have already occurred; this is not conditional reading.

If the second selector-base read matches no switch state, this same transition executes without a branch calculation. It instead uses dispatch-entry scratch as the multiplier-like condition, the current selector, and the captured dispatch multiplier. Scratch need not be binary in that case; describing this path as choosing one of two selectors would be incorrect.

### Saving and returning a result

The result-saving state multiplies external scale by the current result factor and saves the product. It then reads its next selector and copies the saved result into scratch.

The return state returns the saved result. It still follows the dispatch multiplier read and applicable selector-base reads. No unconditional bound on dispatches or transfers is visible.

**Condition:** Result saving uses scale 4 and result factor \(0x40000001\), followed by return without another save.
