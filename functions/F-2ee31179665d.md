# F-2ee31179665d

## Purpose

F-2ee31179665d copies two bytes from an input record into a mutable control record. It then uses subsequent reads of an input selector byte to choose one of two references held by the control record. For a recognized selector, it transfers another control-record byte into the selected object and invokes an indirectly resolved callback.

The function returns the 32-bit value zero on every path that reaches an ordinary return. This includes the path that rejects an unrecognized selector. Consequently, its return value does not distinguish callback execution from selector rejection.

The names “control record,” “input record,” and “selected object” describe observable roles, not established application-level types. The intended business purpose is unknown.

## Interface

The function receives two address-bearing arguments:

- **Control-record address:** identifies a mutable record containing two object references and three relevant byte fields.
- **Input-record address:** identifies storage containing two relevant bytes.

The supplied representation uses 32-bit integer and address operations. The layouts below therefore describe the apparent 32-bit execution model. They are not a portable layout for an arbitrary pointer width.

## Behavior

### Initial byte copies

Before deciding whether to dispatch, the function performs two byte transfers in this order:

1. It reads the input byte at offset 16 and stores that value at control-record offset 13.
2. It reads the input byte at offset 17 and stores that value at control-record offset 14.

Each transfer is exactly one byte. Neither copy performs string interpretation, range validation, or multibyte conversion.

The first store precedes the second input read. If the first destination aliases the second input byte, the second transfer therefore reads the value resulting from that first store.

Both stores precede selector evaluation. Even an invocation that ultimately rejects its selector has already modified these two control-record bytes, assuming the accesses complete.

### Selector evaluation

The selector is read again from input offset 16 after the two copies. Dispatch is not based on a retained copy of the first byte read.

The selection rules are:

- If the first post-copy selector read equals zero, the function takes the selector-zero branch.
- Otherwise, the selector is read again.
- If this additional read equals one, the function takes the selector-one branch.
- Otherwise, the function returns zero without the object-byte transfer or callback invocation.

Thus, there can be three reads of input offset 16: the initial copy read, the zero-comparison read, and, conditionally, the one-comparison read.

For stable, non-overlapping storage, zero selects one branch, one selects the other, and every other byte value rejects dispatch. For storage that changes between reads, the two comparisons need not observe the same value. A zero observed only by the second comparison does not select the selector-zero branch; that comparison accepts only one.

The comparisons distinguish zero and one identically regardless of whether the underlying byte interpretation is signed or unsigned. No broader signed-range behavior is involved.

### Recognized branch: value transfer

For the selector-zero branch, the object reference is obtained from control-record offset 4. For the selector-one branch, it is obtained from control-record offset 0.

The function transfers the byte at control-record offset 15 into byte offset 4 of the referenced object.

The transfer byte is distinct from the two copied destination bytes. The function does not explicitly replace control-record offset 15 during the initial copies. Aliasing can nevertheless affect what is read there.

The supplied representation does not establish the relative evaluation order of the source-byte read and destination-reference read within this transfer. Their exact ordering is therefore not part of this contract.

### Reference reload and callback resolution

After the object-byte store, the function reads the selected reference field from the control record again. It uses this reloaded reference for callback resolution.

This second reference read matters when the preceding byte store overlaps the control record or when externally mutable storage changes. The object receiving the byte and the object used to resolve the callback need not be identical.

Using the reloaded object reference, the function:

- Reads the object’s first 32-bit field as a dispatch-structure reference.
- Reads a callable reference at dispatch-structure offset 8.
- Invokes that callable.

The byte store occurs before callback-reference resolution. If that store overlaps an object or dispatch field involved in resolution, resolution observes the resulting storage rather than a guaranteed pre-store snapshot.

The supplied call expression contains no explicit arguments. It does not establish an object argument, a callback parameter list, a receiver register, or a portable callback prototype. Those calling-convention details remain unknown.

If the callback returns normally, F-2ee31179665d returns zero. If the callback does not return normally, no ordinary return from this function is established.

## Side effects

### Direct effects

The function directly performs:

- A one-byte write at control-record offset 13.
- A one-byte write at control-record offset 14.
- For a recognized selector, a one-byte write at offset 4 of the initially selected object.
- For a recognized selector, one indirect callback invocation.

The initial two writes are not rolled back when dispatch is rejected. No transactional or all-or-nothing behavior is present.

No direct allocation, deallocation, reference-count adjustment, ownership transfer, locking, logging, or explicit global-variable access appears in the supplied body.

That observation does not constrain the callback. Its effects on memory, ownership, global state, or control flow are unknown.

## Acceptance examples

These are conditional behavioral examples derived from the supplied static representation. They are not runtime test results.

### Stable selector zero

Given valid, non-overlapping records with:

- Input offset 16 containing zero.
- Input offset 17 containing 0x7A.
- Control-record offset 15 containing 0xC3.
- Control-record offset 4 referencing a valid object with a valid dispatch chain.

The required behavior is:

- Control-record offset 13 becomes zero.
- Control-record offset 14 becomes 0x7A.
- Byte offset 4 of the object referenced through control-record offset 4 becomes 0xC3.
- The callback resolved through the reloaded offset-4 reference is invoked once.
- The function returns zero if that callback returns normally.

### Stable selector one

With stable input offset 16 equal to one and otherwise valid storage, the object reference at control-record offset 0 is used instead. The initial copies still occur, followed by the selected-object byte transfer and one callback invocation.

### Stable unrecognized selector

With stable input offset 16 equal to two and valid storage for the initial accesses:

- Both input-byte copies occur.
- Neither selected-object reference is dereferenced for dispatch.
- No selected-object byte transfer occurs.
- No callback is invoked.
- The function returns zero.

The same branch outcome applies to every other stable byte value except zero and one.

### Initial copies alter the selector

Suppose control-record offset 14 aliases input offset 16, the original selector is one, and input offset 17 contains zero.

The first copy records one at control-record offset 13. The second copy then writes zero into the aliased selector location. The subsequent selector read observes zero, so the selector-zero branch is selected despite the initially copied selector being one.

This example assumes no other relevant overlap or intervening modification.

### Selected reference changes during the object write

If the selected object’s destination byte overlaps the selected reference field in the control record, the object-byte store can change that reference before it is reloaded.

Callback resolution must then use the post-store reference representation. The resulting address is not necessarily valid; successful dispatch is conditional on that representation identifying valid storage. No byte-order-independent numeric address can be specified from the supplied evidence.

### Callback does not return

If a recognized branch reaches a callback that terminates execution or otherwise fails to return normally, the function’s earlier writes have already occurred. An ordinary zero return is not established for that invocation.
