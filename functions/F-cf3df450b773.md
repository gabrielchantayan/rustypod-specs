# F-cf3df450b773

## Purpose

F-cf3df450b773 scans a contiguous prefix of bytes, accepts bytes according to a classification-table predicate, accumulates a base-ten-style value, and replaces a caller-supplied cursor with the position of the first rejected byte.

The established predicate is **bit 0x10 of the selected classification-table byte is set**. Acceptance is not established by comparison with the byte values 0x30 through 0x39.

Decimal parsing is inferred intent, supported by multiplication by ten and subtraction of 0x30. Actual decimal-only behavior depends on classification-table contents that are not supplied.

The classification-table addressing reference is evaluated afresh for every condition evaluation, including the condition that terminates scanning. The source does not establish an entry-time snapshot of that reference. If the reference changes during a scan, successive classifications may use different tables, subject to the target’s rules for such changes.

The return value does not distinguish an empty accepted prefix from an accepted prefix whose accumulated value is zero. The final cursor distinguishes these cases when it advances.

## Interface

### Argument and storage layout

The function receives one argument: the address of a readable and writable cursor slot.

The supplied representation loads and stores that slot as a four-byte object. Its contents are interpreted as a byte pointer. This establishes a four-byte cursor representation in the represented target, not a portable interface for wider pointers.

Three storage roles are relevant:

- **Cursor slot:** Four bytes holding the current input address, replaced on normal completion with the stopping address.
- **Input storage:** Byte-addressed storage beginning at the address initially obtained from the cursor slot.
- **Classification storage:** Byte-addressed table storage reached through a program-held addressing reference. An unsigned input-byte value selects the entry at that byte offset.

Input bytes have values from 0 through 255. The input value is zero-extended when used as a table index or as the numeric contribution. High-bit input bytes are not interpreted as negative character values.

The source representation uses a signed integer accumulator and an unsigned integer conversion for the contribution. A 32-bit integer model is consistent with the represented target. The exact arithmetic consequences, including signed multiplication and conversion back to the signed accumulator, are distinguished below.

### Output

On normal completion:

- The return value is the final integer accumulator.
- The cursor slot contains the address of the first rejected input byte.
- The rejected byte has been inspected for classification but has not been incorporated into the accumulator.
- No separate status, consumed length, or error indication is returned.

### Preconditions

A normally completing invocation requires:

- A valid cursor slot, with any alignment required by the target.
- A usable initial input address in that slot.
- Readable storage for every input-byte access actually performed.
- A usable classification-table addressing reference at each condition evaluation.
- A readable selected table entry for each classification.
- Valid address advancement through the accepted prefix.
- An eventual rejecting condition if normal termination is required.
- Arithmetic behavior that remains defined under the applicable target model.

No input length, table length, numeric limit, or designated terminator is supplied. The function contains no checks that establish these preconditions.

The function does not acquire ownership of any storage. It neither allocates nor releases memory. Storage lifetimes must cover the accesses actually performed.

## Behavior

### Initialization

The function obtains its internal scan cursor from the caller’s cursor slot and initializes the accumulator to zero.

The cursor slot is not used as an incremental progress record. Advancement during scanning changes the internal cursor, not the caller’s slot.

### Repeated classification

Each loop-condition evaluation uses:

- The current input byte, interpreted as an unsigned value.
- A fresh evaluation of the classification-table addressing reference.
- The table byte selected by adding that unsigned value as a byte offset to the evaluated reference.

The selected entry permits another iteration exactly when its bit 0x10 is set. All other bits are irrelevant to this predicate.

The addressing reference is evaluated on **every** condition evaluation:

- Before the first accepted byte.
- Before each later accepted byte.
- On the final evaluation that rejects a byte.

There is no source-level operation that first captures the table reference and then reuses that captured value throughout the scan.

The expression does **not** establish an evaluation order between the table-reference operand and the input-byte operand used to form the table-entry address. Neither “read the table reference first” nor “read the input byte first” is a supported ordering requirement.

Once those operand values are available, they determine the selected table-entry address. The table entry is then used for the bit test.

### Accepted positions

If classification succeeds, the byte at the current input position is read again for accumulation.

The conceptual numeric contribution is the unsigned byte value minus 48. The accumulator is multiplied by ten and combined with that contribution, subject to the actual integer operations described below.

After the accumulator update, the internal cursor advances by one byte. The next condition evaluates classification at that new position, again evaluating the table addressing reference rather than relying on an entry-time snapshot.

The classification read and contribution read are distinct in the supplied source-level structure. Their values cannot be assumed identical if the input changes between them. An accepted position may therefore be classified using one byte value and accumulated using another. This is an access-structure observation, not a guarantee that concurrent modification is valid.

### Rejected positions and completion

If classification fails, no contribution read or accumulator update is performed for that position, and the internal cursor does not advance.

The function then writes the stopping cursor into the caller’s cursor slot and returns the accumulator.

Even immediate rejection performs the final cursor-slot assignment. The stored address then equals the initial address; an unchanged value does not imply an absent store.

### Character treatment

There is no separate handling for whitespace, signs, zero bytes, base prefixes, separators, punctuation, or high-bit bytes.

Each is accepted or rejected solely by the selected table entry’s bit 0x10. In particular:

- A zero byte is not intrinsically a terminator.
- A sign byte is not processed as a sign.
- Whitespace is not skipped.
- A selected non-digit contributes through the same arithmetic as a selected digit.

### Arithmetic widths and conversions

For stable input containing only accepted byte values 0x30 through 0x39, the intended positional calculation is the previous accumulator multiplied by ten, plus the digit value. That mathematical description is exact only while the relevant operations and conversions preserve the value.

The represented expression has additional constraints:

1. Multiplication of the signed accumulator by ten is a signed integer operation. The unsigned conversion of the input byte does not make that multiplication itself unsigned.
2. Combining the multiplication result with the unsigned input-byte value uses unsigned integer arithmetic at the represented integer width.
3. Subtracting 48 occurs in that unsigned arithmetic domain.
4. The resulting unsigned value is assigned back to the signed accumulator.

Under a 32-bit integer interpretation, the unsigned additions and subtraction operate modulo 2³². However, this does not by itself establish modulo-2³² behavior for the whole function:

- Signed multiplication overflow is not resolved by a later unsigned addition.
- Conversion of an unsigned result above the signed maximum back to the signed accumulator requires target-specific semantics not established here.

A selected byte below 0x30 has a negative **mathematical contribution**, but that fact alone does not establish a negative returned integer. For example, a zero byte accumulated from an initial zero produces the unsigned intermediate value 2³² − 48 under the 32-bit model. Interpreting that value as the signed result −48 depends on the target’s unsigned-to-signed conversion behavior.

A selected byte above 0x39 contributes more than nine mathematically. Such a contribution can still produce an unambiguous result when all operations remain within the relevant signed range.

No overflow detection, saturation, range-error return, or alternate numeric representation is present.

## Side effects

The sole explicit write is the final four-byte cursor-slot store after rejection.

The function explicitly reads:

- The initial cursor slot.
- An input byte for each classification.
- The classification-table addressing reference on every condition evaluation, including the terminating evaluation.
- The selected classification-table byte.
- A further input byte for each accepted position’s contribution.

It does not explicitly modify input bytes, table entries, or the table addressing reference.

These storage roles are not established as disjoint. If the cursor slot overlaps input storage, a table entry, or the table reference, the final store can also modify storage serving that role. The source provides no non-aliasing guarantee.

There are no visible function calls, allocations, releases, callbacks, logging operations, or synchronization operations.

The source-level repeated evaluations do not establish exact compiled load counts or access widths. In particular, they do not prove that a processor reloads the table reference from memory on every iteration. Compiler transformations depend on the applicable language, aliasing, volatility, and target rules.

Likewise, repeated source evaluation is not a synchronization guarantee. It does not establish that concurrent changes to the input or table reference are valid, observed promptly, or observed coherently.

No explicit recovery path exists. Invalid storage, invalid address arithmetic, unsupported arithmetic behavior, or a scan that never rejects has no specified successful result. The evidence does not establish a completed final cursor update in such cases.

## Dependencies

No function dependencies are visible.

The material data dependency is the classification table and its addressing reference. The table reference participates anew in each condition evaluation; it is not merely an initialization dependency.

For each classification, the selected entry must be usable. An invocation need not inspect every possible table entry, but a byte value of 255 selects the entry at offset 255 if encountered.

The following dependency properties remain unknown:

- Actual table contents.
- Whether all ordinary decimal-digit bytes are accepted.
- Whether any non-digit bytes are accepted.
- Whether the table or its addressing reference can change under valid operating conditions.
- Whether table selection depends on locale or other process state.
- Any synchronization or volatility properties governing these objects.

Replacing the predicate with a conventional decimal-digit test is not justified without separate evidence of equivalent table contents.

Similarly, hoisting the table-reference evaluation into an entry-time snapshot is not an equivalent source-level contract. Whether a compiler may produce such machine behavior is a separate question requiring the relevant execution model.

## Acceptance examples

These are conditional deductions, not runtime observations. Unless otherwise stated, storage is valid and stable, the table reference is stable, arithmetic preserves the stated result, and a rejecting byte follows the described prefix.

1. **Immediate rejection.** If the first selected table entry has bit 0x10 clear, the result is zero. The cursor does not advance, but its slot is still written with the stopping address.

2. **Ordinary decimal prefix.** If bytes 0x31, 0x32, and 0x33 are accepted and the next byte is rejected, the result is 123. The final cursor points to that next byte.

3. **Leading zeroes.** If the bytes representing “0007” are accepted, the result is 7 and all four bytes are consumed.

4. **Zero versus empty consumption.** A selected byte 0x30 followed by rejection produces zero and advances the cursor by one. Immediate rejection also produces zero but leaves the cursor at its initial position.

5. **Rejected whitespace or sign.** If an initial space or minus byte is rejected, scanning stops there. Following digits are not reached. No whitespace skipping or sign processing occurs.

6. **Selected non-digit.** If byte 0x41 is accepted from an initial accumulator of zero and the next byte is rejected, the result is 17. Acceptance does not imply a contribution in the range zero through nine.

7. **Selected zero byte.** If byte 0x00 is rejected, it stops scanning. If accepted, it is consumed and accumulation occurs. Under 32-bit unsigned arithmetic the first update produces the unsigned value 2³² − 48 before assignment to the signed accumulator. A returned value of −48 additionally requires a target conversion rule yielding that signed value.

8. **Changed contribution byte.** Suppose classification accepts a position using byte 0x31, but a validly modeled intervening change makes the contribution read yield 0x32. Starting from zero, that iteration accumulates 2, not 1. This example requires an execution model permitting the stated change; it is not a concurrency guarantee.

9. **Changed table reference.** Suppose a valid execution model allows the table reference to change between condition evaluations. A byte accepted through the earlier reference need not predict acceptance of the next byte through the later reference. The terminating condition also evaluates the then-current reference. No order is asserted between evaluating that reference and reading the input byte within a condition.

10. **Arithmetic boundary.** A long accepted prefix receives no explicit range-error result. Exact behavior requires the signed multiplication and unsigned-to-signed conversion rules; unconditional wrapping cannot be inferred.
