# F-deca110c5079

## Purpose

F-deca110c5079 conditionally dispatches an action using a record obtained from a lookup dependency.

The function first obtains a lookup key from a caller-supplied object and requests a record using selector 0x3900. It reports failure if the lookup returns a null result or if a word in the returned record does not satisfy an additive comparison with a shared state value. Otherwise, it passes an opaque caller value and another field from the record to an action dependency, then reports success.

Here, “success” means that the lookup and comparison permitted the action call and that the action call returned normally. It does not establish that the action achieved any external effect: the action dependency’s return value is not inspected.

This contract describes the behavior established by the supplied static representation. No runtime tests have been performed.

## Behavior

### Lookup

The first established external memory access is the read of the 32-bit key at byte offset 8 from the caller-supplied object.

The function invokes F-682adfd5a561 with:

1. The key read from that field.
2. The numeric selector 0x3900, equivalent to decimal 14592.

This call occurs before the function can determine its normal result. There is no visible early rejection based on the caller value, object address, or key contents.

The lookup result is treated as either zero or an address-like value identifying a record.

### Null-result rejection

If F-682adfd5a561 returns zero, F-deca110c5079 returns 0.

On this path:

- The returned-record fields are not read.
- The shared comparison state is not read by the visible condition.
- F-c9e224cf0f7e is not invoked.

This short-circuit behavior is significant. A lookup miss does not require any record storage to exist or be readable.

The lookup dependency has already run. Returning 0 does not imply that no side effects occurred.

### Non-null comparison

For a nonzero lookup result, the function reads the integer field at byte offset 8 from the returned record and reads the shared comparison state.

It adds those values and checks whether the sum equals zero:

- A nonzero sum rejects the record and produces result 0.
- A zero sum permits the action call.

The comparison occurs after the lookup dependency returns. Consequently, it is not established to use the shared state that existed on entry. If the lookup dependency changes that state, the later read can observe the changed value.

The supplied representation does not establish an ordering between the record-field read and the shared-state read within the addition. A contract consumer must not depend on one of those two reads occurring first.

### Accepted action

When the sum is zero, the function reads the 32-bit field at byte offset 20 from the returned record and invokes F-c9e224cf0f7e with:

1. The original caller value.
2. The value read at record offset 20.

The offset-20 field is therefore conditionally accessed. A rejected record does not need that field for this function’s visible execution path; an accepted record does.

The action dependency’s result is discarded. If it returns normally, F-deca110c5079 returns 1 regardless of that result.

There is no visible second lookup, retry, comparison recheck, or inspection of record contents after the action call.

### Arithmetic boundary

The record comparison field is represented as a 32-bit integer. The shared operand’s declaration is absent, so the addition’s precise language-level type and overflow rules are not fully established.

For values whose addition is representable without overflow in the apparent signed 32-bit model, the acceptance condition is unambiguous: the two operands must sum to zero. For example, 7 and −7 satisfy it; 7 and −6 do not.

A wrapping 32-bit machine-addition interpretation would also accept any pair whose low 32-bit sum is zero, including 0x80000000 paired with 0x80000000. That interpretation is not promoted to an unconditional requirement here. Overflow handling remains documented_only pending authoritative target-level evidence.

Address-offset calculations have a similar limitation: valid, readable addresses at the documented offsets are required. Wraparound address construction is not a supported behavior established by this contract.

## Side effects

### Direct reads and writes

1. The lookup key from object offset 8.
2. For a non-null lookup result, the comparison field from record offset 8 and the shared comparison state.
3. For an accepted record, the action argument from record offset 20.

The supplied body contains no direct write to the caller-supplied object, lookup record, or shared state.

This is not a purity guarantee. Both dependencies may have side effects, and their implementations are unavailable.

### Dependency effects and ordering

The established phase order is:

- Read the key.
- Invoke the lookup dependency.
- If non-null, evaluate the comparison.
- If accepted, read the action field and invoke the action dependency.
- Return the branch result.

The key passed to the lookup is the value obtained before that call. A later mutation of the object’s key field does not cause a visible reread in this invocation.

The action field is read after the comparison succeeds. There is no visible snapshot of the whole record and no synchronization protecting these reads. Coherence under concurrent mutation is not established.

A failing comparison prevents the action call, but it does not undo effects of the lookup call.
