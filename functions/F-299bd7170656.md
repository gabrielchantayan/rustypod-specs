# F-299bd7170656

## Purpose

F-299bd7170656 dispatches a small set of numeric operation codes against a caller-supplied object and shared state. It may prepare shared state, retrieve an object-derived value, update a shared object or an embedded object, and publish a 32-bit result through a caller-supplied output location.

The Boolean return value and output word are separate parts of the contract:

- Recognized operations return true on ordinary completion.
- An unrecognized operation returns false without directly writing the output.
- Some recognized operations return true without directly writing the output.
- Shared preparation may occur even for an unrecognized operation.

Descriptions such as “preparation,” “update,” and “result extraction” describe the visible call structure, not established application-level meanings.

## Interface

### Inputs

The supplied representation exposes four arguments:

| Argument | Representation and use |
|---|---|
| Object base | A 32-bit integer-shaped address. Used as a dependency argument and as the base for accesses at byte offsets `0x8c` and `0x14c`. |
| Selector | A 32-bit value compared for equality with values obtained from shared slots. No signed ordering is applied to it. |
| Operation code | A 32-bit value selecting the behavior described below. |
| Output address | Address of storage receiving one 32-bit word on result-producing paths. |

The result is Boolean. Exact ABI encoding beyond true and false is not established.

### Relevant object layouts

Only the following portions of the supplied object are exposed:

- At byte offset `0x8c`: a field interpreted as a signed 32-bit integer.
- At byte offset `0x14c`: the beginning of an embedded object passed by address to dependencies. Its size and internal layout are unknown.

The shared object used by several paths supports an indirect call through a dispatch structure:

- Its first pointer-sized entry supplies the dispatch-structure address.
- The callable entry at byte offset `0x0c` in that structure is invoked with the shared object as its argument.

This describes the observed addressing pattern, not a complete object model.

### Shared-state terminology

This contract uses descriptive labels for otherwise opaque shared slots:

- **Preparation-state base:** supplies the address whose 32-bit field at offset `0x20` is tested.
- **Preparation handle:** passed to the preparation predicate and completion dependency.
- **Shared object:** used during preparation and operation `0x6612`.
- **Preparation descriptor:** a fixed address passed during preparation.
- **Preparation argument A** and **preparation argument B:** two shared values passed during preparation, in that order.
- **Selector A** and **selector B:** comparison values used by operations `0x6600` and `0x6604`.
- **Update selector:** comparison value used by operation `0x6613`.
- **Key zero**, **key one**, and **key other:** opaque shared values used to obtain update data.

These labels do not establish the slots’ application meanings, mutability, ownership, or independence from the supplied object and output storage.

### Preconditions

For ordinary completion, every address actually dereferenced on the selected path must be valid and suitably aligned for the corresponding access. In particular:

- The preparation-state field is accessed on every invocation.
- Operation `0x6612` requires the signed field at object offset `0x8c`.
- Result-producing paths require writable four-byte output storage.
- Paths using the embedded object require a valid object at offset `0x14c`.
- The indirect-call path requires valid shared-object, dispatch-structure, and callable-entry addresses.

The function performs no explicit null, bounds, alignment, or object-type validation. Paths without a direct output write do not themselves dereference the output address; that does not establish that arbitrary addresses or aliasing are safe in the presence of dependency effects.

## Behavior

### 1. Common preparation

Preparation is considered before operation dispatch, including before rejection of an unknown operation.

1. Read the 32-bit field at offset `0x20` from the preparation-state base.
2. If bit zero is set, skip the preparation calls.
3. If bit zero is clear, call F-b255b26284e6 with the preparation handle.
4. If that dependency returns zero, skip the remaining preparation calls.
5. If it returns nonzero:
   - Call F-398e0e9a318a with the shared object and the address of the preparation descriptor.
   - Pass its returned word to F-804adc29bbfb, followed by preparation argument A and preparation argument B.
   - Call F-d08d3ca17b81 with the preparation handle.

There is no explicit output write in this phase. There is also no explicit local-state update marking preparation complete. Any such change would have to be an effect of a dependency.

Shared values used after a dependency call must not be assumed to retain their earlier values. For example, the preparation handle supplied to the completion dependency need not equal the value supplied to the predicate if intervening calls change that shared slot.

### 2. Operations `0x6600` and `0x6604`

These two operation codes have identical dispatch behavior.

The selector is compared first with selector A. Only if it does not match selector A is the comparison with selector B needed.

- If the selector equals selector A, write the 32-bit value zero to the output and return true.
- Otherwise, if the selector differs from selector B, write zero to the output and return true.
- Otherwise, call F-19c0dbbb52a4 with the supplied object base, write its returned 32-bit word to the output, and return true.

Thus, the dependency-result path requires both:

- The selector does not equal selector A.
- The selector equals selector B.

If selector A and selector B have the same value during these comparisons, their common value selects the zero-output path, not the dependency-result path.

The source representation expresses part of this dispatch using subtraction by `0x6400` and comparison with `0x204`. At 32-bit width, the corresponding operation value is exactly `0x6604`. Operation `0x6600` is independently recognized and does not rely on the subtraction result. No additional operation is established by the scratch-register representation.

### 3. Operation `0x6612`

Read the signed 32-bit field at object offset `0x8c`.

If the field is negative:

- Invoke the shared object’s indirect callable entry at dispatch offset `0x0c`, passing that shared object.
- After the call, obtain the shared-object value used for subsequent processing.

If the field is zero or positive:

- Call F-f0da878d5c87 with the supplied object base.
- Call F-151ab4bfe553 with the then-current shared object and the returned word.
- After that call, obtain the shared-object value used for subsequent processing.

In both cases:

- Call F-44362605ab79 with the post-update shared-object value.
- Write its returned 32-bit word to the output.
- Return true.

The final shared-object selection occurs after the preceding callback or update dependency. It must not be treated as necessarily identical to the shared object passed into that preceding operation.

The field’s magnitude has no further direct effect: all negative values take one branch, and zero and all positive values take the other.

### 4. Operation `0x6613`

Compare the selector with the update selector.

If they differ:

- Return true.
- Do not directly write the output.
- Do not call the object-query or embedded-object update dependencies described below.

If they match, call F-19c0dbbb52a4 with the supplied object base. Interpret its result as a 32-bit integer for the following classification:

| Query result | Data key | Update operation |
|---|---|---|
| Exactly zero | Key zero | F-151ab4bfe553 |
| Exactly one | Key one | F-151ab4bfe553 |
| Any other value | Key other | F-1f62160dfd52 |

For all three cases, call F-9d0ecc5f6adf first, then call F-c0b020cd3882 with that dependency’s returned word and the selected key.

For query results zero or one, call F-151ab4bfe553 with:

- The embedded-object address at object offset `0x14c`.
- The word returned by F-c0b020cd3882.

For any other query result, call F-1f62160dfd52 with:

- The same embedded-object address.
- The word returned by F-c0b020cd3882.
- The original query result.

The “other” category includes negative results; there is no explicit rejection, normalization, or clamping.

Finally, call F-44362605ab79 on the embedded-object address, write its returned word to the output, and return true.

### 5. All other operations

After common preparation, return false.

There is no direct output write, no object-field read at offset `0x8c`, and no embedded-object update on this path.

## Side effects

### Direct memory accesses

The function directly exposes these effects:

- A read of the preparation-state field on every invocation.
- Conditional reads of shared handles, objects, selector values, arguments, and keys.
- A signed 32-bit field read at object offset `0x8c` only for operation `0x6612`.
- Dispatch-structure reads for the negative-field branch of operation `0x6612`.
- One 32-bit output write on each result-producing path.

It contains no explicit allocation, deallocation, ownership transfer, or direct write to the supplied object’s fields.

### Ordering

Common preparation completes before operation-specific behavior begins. Within each path, the dependency-call order given above is observable and must be preserved.

Where a path produces an output, the output write follows its relevant dependency calls. The zero-output path for operations `0x6600` and `0x6604` writes only after common preparation.

The source establishes reads on particular sides of dependency calls. It does not establish a universal evaluation order between separate argument loads belonging to the same call.

### Ownership and aliasing

All addresses and returned words remain ownership-opaque:

- No dependency result is explicitly released by this function.
- Passing a value to a dependency does not establish that the dependency borrows, retains, consumes, copies, or releases it.
- Dependencies may modify shared state unless their separate contracts forbid it.
- If the output aliases shared state or object storage, its final write may alter that state. No non-aliasing check is present.

Claims that an output is “unchanged” must therefore distinguish absence of a direct write from possible indirect effects through dependencies.

### Errors

No explicit error object, exception translation, retry, rollback, or cleanup path is visible.

Zero has context-specific handling:

- From F-b255b26284e6: skip the remaining preparation calls.
- From F-19c0dbbb52a4 during operation `0x6613`: select key zero.

Other dependency results are forwarded or published without an explicit validity check. Ordinary true returns do not certify dependency success or confirm that an update occurred.

## Acceptance examples

These are conditional contract examples, not runtime observations. Unless stated otherwise, assume valid storage and ordinary dependency returns.

1. **Unknown operation, preparation suppressed.**  
   With preparation-state bit zero set and operation `0x6601`, return false. Make no preparation calls and no direct output write.

2. **Unknown operation, preparation enabled.**  
   With bit zero clear and F-b255b26284e6 returning nonzero, perform the preparation call sequence before returning false for an unknown operation.

3. **Predicate rejects preparation.**  
   With bit zero clear and F-b255b26284e6 returning zero, omit F-398e0e9a318a, F-804adc29bbfb, and F-d08d3ca17b81. Continue normal dispatch.

4. **Selector A takes precedence.**  
   For operation `0x6600`, if the selector equals selector A, publish zero and return true, including when selector B has the same value.

5. **Selector B retrieves a result.**  
   For operation `0x6604`, if the selector differs from selector A and equals selector B, publish exactly the word returned by F-19c0dbbb52a4.

6. **Negative-field shared-object operation.**  
   For operation `0x6612` and field value −1, invoke the indirect entry rather than F-f0da878d5c87. Extract the output from the shared-object value obtained after that call.

7. **Zero is nonnegative.**  
   For operation `0x6612` and field value zero, call F-f0da878d5c87, then F-151ab4bfe553, then F-44362605ab79. Publish the final returned word.

8. **Recognized no-output operation.**  
   For operation `0x6613` with a selector mismatch, return true without a direct output write. If dependencies during preparation do not modify aliased output storage, its prior contents remain intact.

9. **Distinct zero and one updates.**  
   With a matching update selector, query results zero and one select their respective keys and the two-argument embedded-object update dependency.

10. **Negative query result is forwarded.**  
    With a matching update selector and query result −1, select key other and pass that original result to F-1f62160dfd52. No direct error return is introduced.

## Uncertainties

### Inferred intent

The preparation calls resemble conditional shared-state setup. The key-selection calls resemble lookup or formatting, and F-44362605ab79 resembles result extraction. These interpretations are not required to reproduce the established behavior.

### documented_only

The following remain unresolved:

- Application meanings of operation codes, selectors, keys, fields, and output words.
- Complete ABI details, pointer provenance, and exact object types.
- Embedded-object size and layout beyond its starting offset.
- Dependency mutation, allocation, retention, release, failure, and reentrancy behavior.
- Whether shared slots are stable or externally synchronized.
- Whether aliasing among inputs, output, and shared state is permitted.
- Indirect callable identity and failure behavior.
- Behavior after invalid memory accesses or nonordinary dependency termination.

No thread-safety guarantee or dependency-global-preservation guarantee is established.
