# F-51fa38a2223f

## Purpose

F-51fa38a2223f conditionally invokes runtime-selected operations based on a 32-bit mode selector and byte-valued state in a supplied object.

The accepted selectors are exactly 0 and 1:

- **Mode 1:** Requires a nonzero primary state. If the secondary state is also nonzero, a related object must have a nonzero state byte. Eligible execution proceeds directly to optional completion processing.
- **Mode 0:** Requires a nonzero secondary state. A nonzero primary state additionally selects preliminary dispatch before optional completion processing.
- **Other selectors:** Return without accessing the object or shared dispatch storage.

“Primary,” “secondary,” “related,” “preliminary,” and “completion” describe observable roles, not application semantics. The evidence does not establish whether this function activates, shuts down, notifies, or otherwise manages an application object.

The function contains no explicit stores. Its indirect callees have unknown effects and may alter storage subsequently read by this function.

## Interface

### Inputs and result

| Input | Representation | Use |
|---|---|---|
| Object address | 32-bit address-bearing value | Base for state, related-object, and operation fields |
| Mode selector | 32-bit integer | Compared for exact equality with 1 and 0 |

The function has no defined result value, status code, or diagnostic output. Rejected eligibility and ordinary completion are not distinguished through a return value.

The selector is neither truncated to one byte nor interpreted as a general Boolean. For example, 0x100 is not mode 0, and 0x101 is not mode 1.

The supplied representation uses four-byte address and function-address fields. State fields and one custom-operation argument occupy one byte each.

### Object layout

Offsets are measured in bytes from the supplied object address.

| Offset | Width | Role |
|---|---:|---|
| +0x04 | 1 byte | Primary state |
| +0x05 | 1 byte | Secondary state |
| +0x1C | 4 bytes | Related-object address |
| +0x1B0 | 4 bytes | Optional completion target |
| +0x1B4 | 4 bytes | Completion argument |
| +0x1B8 | 4 bytes | Optional custom preliminary target |
| +0x1BC | 4 bytes | Custom operation’s third argument |
| +0x1C0 | 1 byte | Custom operation’s second argument |

When required, the related object contributes a one-byte state at its own offset +0x05. Other related-object storage is not used directly.

All state tests distinguish zero from nonzero. No particular nonzero encoding is required, and no state normalization occurs.

The four-byte argument fields and provider result have unresolved semantic types. Their widths do not establish that they are pointers, handles, signed integers, or owned resources.

### Shared dispatch layout

Shared dispatch involves three distinct levels of storage:

1. A global location contains a **four-byte anchor value**.
2. At the address represented by that anchor value plus 0x04, a **four-byte receiver address** is stored.
3. At the receiver’s first four-byte word, a **dispatch-table address** is stored.

The dispatch table contains four-byte function-address entries at these offsets:

| Table offset | Role |
|---|---|
| +0xBC | Default preliminary operation |
| +0xC4 | Preliminary value provider |

The global location holding the anchor value is distinct from the receiver slot addressed through that value. Reading the receiver slot does not substitute for reading the global anchor value.

These structures are reached only in mode 0 when both local state bytes test nonzero. In the default preliminary branch, both the global anchor value and the receiver slot are read again.

### Preconditions and ownership

Normal execution requires every reached memory location to be readable at its specified width, and every invoked target to be callable under the applicable ABI.

There are no explicit null checks for the object, related object, anchor value, receiver, dispatch table, or table-selected function targets. The custom and completion slots are checked for zero, but each target is subsequently obtained again for invocation.

Validity is path-dependent. A rejected selector requires no readable object. An eligible path does not require unused fields or unselected table entries to be readable merely because they exist in the described layout.

No ownership transfer, retention requirement, allocation obligation, or release obligation is established. Continued validity across indirect calls is a prerequisite for later accesses, not a guarantee supplied by those calls.

## Behavior

### Mode selection

The selector is examined before any object access:

- Exactly 1 selects mode 1.
- Otherwise, exactly 0 selects mode 0.
- Every other value returns immediately.

No state or shared dispatch read occurs on the rejected-selector path.

### Mode 1 eligibility

The first object read obtains the primary state byte at +0x04.

If that byte is zero, execution returns. The secondary state and all later fields remain unread.

If the primary state is nonzero, the secondary state byte at +0x05 is read:

- **Secondary state zero:** Eligibility succeeds without reading the related-object address.
- **Secondary state nonzero:** The related-object address at +0x1C is read, followed by the related state byte at related-object offset +0x05.
  - A zero related state rejects eligibility.
  - A nonzero related state permits completion processing.

Mode 1 performs no preliminary dispatch. It does not inspect the custom-operation slot or shared dispatch structures.

### Mode 0 eligibility

The first object read obtains the secondary state byte at +0x05.

If it is zero, execution returns without reading the primary state or completion slot.

Otherwise, the primary state byte at +0x04 is read:

- **Primary state zero:** Skip preliminary dispatch and proceed to completion processing.
- **Primary state nonzero:** Perform preliminary dispatch, then proceed to completion processing if the required calls return normally.

Mode 0 does not read the related-object address or related state.

### Preliminary dispatch setup

When mode 0 requires preliminary dispatch, setup performs these dependent reads in order:

1. Read the four-byte global anchor value.
2. Read the four-byte receiver address at that value plus 0x04.
3. Read the four-byte dispatch-table address from the receiver’s first word.

The resulting table address is retained for the selected preliminary operation.

Only after this acquisition does the function test the object’s custom-operation slot at +0x1B8. Consequently, even a zero custom slot requires valid anchor, receiver-slot, and receiver-first-word accesses.

### Zero custom slot: default preliminary operation

A zero custom slot selects the table entry at +0xBC. The operation receives:

1. A receiver address obtained through a fresh shared lookup.
2. The integer value 1.

The fresh lookup reads the **global anchor value again**, then reads the receiver slot at that newly obtained value plus 0x04. It does not merely reread a slot relative to the anchor value used during setup.

The operation target is selected through the retained table address. The table is not reacquired from the receiver supplied as the argument.

With stable shared storage, the setup receiver and argument receiver coincide. If different values are observed, they can differ because:

- The global anchor value changed.
- The receiver slot changed.
- Both changed.

Thus, the retained table can originate from one receiver while the call receives another. This describes the lookup structure, not a guarantee that concurrent mutation is safe.

The evidence does not establish a total ordering between the table-entry read and the independent receiver-argument lookup. Within that lookup, reading the anchor value necessarily precedes reading the receiver slot it addresses.

The default operation’s result is unused. Normal return leads to completion processing.

### Nonzero custom slot: provider followed by custom operation

A nonzero custom slot selects the preliminary provider through retained-table offset +0xC4.

No explicit arguments are shown for this provider invocation. The provider returns a four-byte value used as the custom operation’s first argument.

After the provider returns, the function invokes the target obtained from the object’s +0x1B8 slot with these argument positions:

| Position | Supplied value |
|---|---|
| First | Four-byte provider result |
| Second | One-byte value from object +0x1C0 |
| Third | Four-byte value from object +0x1BC |

The custom target and both object argument fields are read after the provider returns. The initial nonzero slot test does not retain the target for invocation.

Accordingly, a provider can change the subsequently observed custom target or arguments. There is no second zero check before the custom invocation. If the provider clears the target, the function does not convert that change into a skipped call or fallback.

A zero provider result is passed onward without special treatment. The custom operation’s result is unused.

The evidence establishes argument positions, but not a total read order among the target and the two object argument fields within that invocation expression. It also does not establish the ABI’s signed or unsigned extension of the one-byte argument.

Normal return from the custom operation leads to completion processing.

### Completion processing

Completion is reached only after eligibility succeeds and any required preliminary sequence returns normally.

The function tests the four-byte completion-target slot at +0x1B0:

- **Zero:** Return without reading the completion argument.
- **Nonzero:** Invoke the target obtained from that slot, supplying the four-byte value at +0x1B4 as its sole explicit argument.

The invocation obtains the target again rather than necessarily using a retained copy of the tested value. There is no additional zero check protecting this later use.

Completion fields are examined after preliminary calls. Those calls may therefore affect whether completion is attempted, which target is used, and which argument is supplied. Eligibility states are not rechecked.

No completion result has an established consumer-visible use. No subsequent application operation is shown. Exact low-level call-versus-terminal-transfer mechanics remain unresolved.

### Observable ordering boundaries

The established ordering is:

- Selector checks precede object access.
- State reads follow the mode-specific short-circuit order.
- Initial global-anchor, receiver-slot, and dispatch-table reads precede the custom-slot test.
- Default dispatch uses the retained table but performs another global-anchor read followed by another receiver-slot read for its receiver argument.
- Provider return precedes custom-target and custom-argument reads.
- Preliminary return precedes completion-field processing.

Independent reads within one invocation expression have no further established total ordering. No atomic snapshot, synchronization, or safe concurrent-mutation guarantee follows from these relationships.

## Acceptance examples

These are conditional consequences of static evidence, not executed tests. Unless stated otherwise, reached storage is valid, observed values remain stable, call signatures are compatible, and invoked operations return normally.

| Conditions | Required behavior |
|---|---|
| Selector is 2 and object address is unusable | Return without accessing the object or shared dispatch storage |
| Selector is 0x100 or 0x101 | Reject; do not truncate the selector to select mode 0 or 1 |
| Mode 1; primary state zero | Read primary state and return without reading secondary state |
| Mode 1; primary nonzero, secondary zero | Process completion without reading the related-object address |
| Mode 1; both local states nonzero, related state zero | Read the related state, then return without completion |
| Mode 1; both local states and related state nonzero | Process completion without shared dispatch or custom-slot access |
| Mode 0; secondary state zero | Return without reading primary state or completion |
| Mode 0; secondary nonzero, primary zero | Process completion without reading the global anchor |
| Mode 0; both states nonzero, custom slot zero | Acquire the table through the initial anchor lookup; invoke the default operation using that table and a receiver from the repeated anchor lookup; then process completion |
| Mode 0; both states nonzero, custom slot nonzero | Invoke the provider, invoke the later-read custom target with its three arguments, then process completion |
| Completion reached; target slot zero | Return without reading the completion argument |
| Completion reached; target slot nonzero | Attempt completion with the subsequently obtained target and current four-byte argument |

Additional boundaries:

- A state byte of 0x80 passes a nonzero test just as 0x01 does.
- Mode 1 with secondary state zero does not require a valid related-object field.
- Mode 0 with primary state zero does not require valid shared dispatch storage.
- Preliminary setup still requires the global-anchor, receiver-slot, and receiver-first-word reads when the custom slot is zero.
- If setup observes one anchor value but the default argument lookup observes another, the argument receiver comes from the later anchor’s +0x04 slot. The table remains the one acquired during setup.
- If the anchor value remains unchanged but its receiver slot yields a different address on the repeated read, the later receiver is supplied with the retained table.
- Those differing-read cases do not establish supported concurrent mutation or guarantee normal execution.
- A zero provider result is passed to the custom operation unchanged.
- If the provider installs valid replacement custom fields, the later invocation uses those fields.
- If the provider clears the custom target, no second zero test skips the invocation.
- If a preliminary operation clears completion, completion is skipped. If it installs valid completion fields, those later values are used.
- Changes to eligibility bytes during preliminary calls do not trigger revalidation.

## Evidence

Established static evidence includes exact selector comparisons, byte-width state tests, four-byte address and value fields, fixed offsets, short-circuit paths, indirect target selection, explicit argument positions, and the absence of explicit stores.

The shared lookup specifically establishes an initial global-anchor read, a receiver-slot read through that value, and a receiver-first-word read yielding the retained table. The default receiver argument independently requires another global-anchor read followed by another receiver-slot read.

The provider precedes the custom target and argument reads. Preliminary calls precede completion processing. The evidence does not establish callee preservation, application semantics, safe concurrent mutation, or a total ordering of independent reads within an invocation expression.
