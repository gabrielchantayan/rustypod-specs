# F-967e83193b72

## Purpose

F-967e83193b72 rearranges existing links in place. For a well-formed parent-linked binary tree, the transformation is a left rotation: the selected node’s right child moves upward, the promoted node’s former left subtree moves to the selected node’s right side, and the promoted node replaces the selected node in its incoming root or parent link.

The link accesses and updates are established by the supplied static representation. Their interpretation as a binary-tree rotation is inferred intent, not independently established type information.

The operation performs no ordering comparisons, balance calculations, allocation, or payload updates. It does not validate structural consistency before mutation. Invalid or inconsistent inputs can therefore cause partial mutation, replacement of an unrelated link, or an invalid memory access rather than a checked failure.

## Interface

### Arguments and result

The function accepts two address-bearing arguments:

- **Context:** identifies storage containing a reference to a separate root-holder object.
- **X:** identifies the node selected for downward movement.

There is no explicit return value or success/failure status.

The supplied representation establishes four-byte accesses for the relevant stored links. This contract treats them as **32-bit link values**. It does not independently establish native pointer width, pointer provenance, or the complete relationship between these link values and machine addresses.

These are partial layouts. Object sizes, fields outside these locations, payloads, and ownership metadata are not established.

The following relationship labels are used:

- **Y:** the link value initially read from X’s right-child field. The function retains this selected value throughout the operation.
- **B:** Y’s initial left-child link under stable, noninterfering storage conditions.
- **P:** X’s initial parent link under those same conditions.
- **Root slot:** the four-byte field at offset 4 in the object reached through Context’s offset-16 reference when that reference is read.

Y is initially X’s right child. In a well-formed parent-linked tree, **Y’s initial parent is X**, whereas X’s initial parent is P. Without that structural assumption, Y’s previous parent value is unspecified: the function overwrites it without a dedicated read of its old value.

### Preconditions for the intended rotation

A meaningful completed tree rotation requires:

- X’s parent and right-child fields to be accessible for the executed reads and writes.
- Y to identify accessible storage with a writable parent field and readable/writable left-child field.
- Each nonzero transferred-subtree link used during execution to identify storage with a writable parent field.
- Context’s root-holder reference and the selected holder’s root field to be readable.
- The root field to be writable if its value equals X.
- On the non-root path, the parent selected from X’s parent field to have a readable left-child field and the selected writable child field.
- Node relationships and storage locations not to interfere through overlap.
- Relevant links to remain stable during the operation.

Y is not checked for zero before its left-child field is accessed. A nonzero link is not otherwise validated.

The function does not require or establish that a root’s parent link is zero. In the root case, X’s existing parent value is copied into Y’s parent field.

## Behavior

### Transfer and parent-link preparation

The first observed link read selects Y from X’s right-child field. The function then reads Y’s left-child link and writes that value into X’s right-child field.

Y’s left-child field is read again for a zero comparison. If that second read is nonzero, a further read of the same field supplies the destination whose parent field is set to X. Thus the copied link, the value tested for zero, and the link used to select the parent-update destination are separate reads.

For stable, nonoverlapping storage, these reads all yield B:

- X’s right child becomes B.
- If B is nonzero, B’s parent becomes X.
- If B is zero, no transferred-subtree parent store occurs.

The function next reads X’s parent field and copies that value into Y’s parent field. This replacement does not inspect or validate Y’s previous parent value. For a well-formed tree, it changes Y’s parent from X to P.

### Incoming-link selection

Only after those mutations does the function read Context’s root-holder reference, locate the root slot, and read its value.

If the root value equals X, that root slot is replaced with Y. No parent-child selection is performed on this path. The root-holder reference is not reread to select the destination of this replacement.

Otherwise, the function rereads X’s parent field and uses that value to select a parent object. This is a separate read from the earlier one copied into Y’s parent field. It then reads the selected parent’s left-child field:

- If the left-child value equals X, that field is replaced with Y.
- Otherwise, the selected parent’s right-child field is replaced with Y.

The right-child fallback does not first read or check that field’s value. A structurally inconsistent parent can consequently have an unrelated right-child link overwritten.

### Completion

After the incoming root or parent link has been replaced, the function writes X into Y’s left-child field. Its last explicit store writes Y into X’s parent field.

No subsequent structural validation, cleanup, or status production appears.

### Completed result under well-formed-tree assumptions

For stable storage with coherent, nonoverlapping node roles:

| Relationship | Before | After |
|---|---|---|
| X’s right child | Y | B |
| B’s parent, when B is nonzero | Y | X |
| Y’s parent | **X** | **P** |
| Incoming root or parent link | X | Y |
| Y’s left child | B | X |
| X’s parent | P | Y |

The “Y’s parent” row depends on the well-formed-tree assumption for its **Before** value. The function itself neither reads nor verifies that initial relationship. Its **After** value follows from copying X’s parent link, subject to the stated stability and noninterference assumptions.

If X was the root, Y becomes the root. Y’s resulting parent is X’s previous parent value, not an independently imposed zero.

If X was not the root, Y replaces X in P’s left-child field when that field equals X; otherwise, Y is stored in P’s right-child field.

X’s left-child field and Y’s right-child field are not directly accessed. Their storage remains unchanged unless it aliases a written location.

### Aliasing and changing storage

The normal result table is not a snapshot-based guarantee for arbitrary storage.

The first write to X’s right-child field precedes the repeated reads of Y’s left-child field. An overlap can therefore affect those later reads. The optional transferred-subtree parent store can also affect a later field access if storage overlaps.

Likewise, X’s parent is read before Y’s parent is written and is read again on the non-root path. If an intervening write affects X’s parent field, the value copied into Y and the parent selected for incoming-link replacement need not agree.

The retained Y value does not change when X’s right-child field is replaced. Other repeated accesses remain separate observations in the supplied representation.

No synchronization or atomic snapshot guarantee is established. The specified access ordering must not be interpreted as a concurrency-safety guarantee.

## Acceptance examples

These are conditional predictions from static evidence, not executed tests. Unless an example explicitly relaxes structural consistency, assume accessible, distinct storage and stable links.

### Root rotation with a transferred subtree

Given a well-formed tree in which the root slot contains X, X’s right child is Y, Y’s parent is X, and Y’s left child is nonzero B:

- The root becomes Y.
- X’s right child becomes B.
- B’s parent becomes X.
- Y’s left child becomes X.
- X’s parent becomes Y.
- Y’s parent becomes X’s original parent value, P.

If P is zero, Y’s resulting parent is zero. The function does not independently enforce that value.

### Non-root rotation from the left

Given that the root differs from X, X’s parent is P, P’s left child is X, and Y is X’s right child with parent X:

- P’s left child becomes Y.
- P’s right child is not selected for replacement.
- Y’s parent changes from X to P.
- The transferred-subtree and final X/Y links change as specified above.

### Non-root rotation from the right

Given that the root differs from X, P’s left child differs from X, and P’s right child is X:

- P’s right child becomes Y.
- P’s left child remains unchanged.
- Y’s parent becomes P.
- The remaining rotation stores proceed normally.

### Empty transferred subtree

Given that Y’s left child remains zero throughout its preliminary reads:

- X’s right child becomes zero.
- No transferred-subtree parent field is written.
- Y’s left child subsequently becomes X.
- Incoming-link replacement and the final parent update still occur.

Zero in this field skips one store; it does not cause an early return.

### Unexpected initial parent value in Y

Given accessible, nonoverlapping storage where X’s parent is P but Y’s initial parent contains some other value:

- The function does not compare that old value with X or P.
- Y’s parent is overwritten with P.
- There is no checked failure for the mismatch.

This example is outside the well-formed-tree assumptions. It establishes replacement behavior, not a guarantee that the completed structure is a valid tree.

### Inconsistent incoming parent link

- P’s right-child field is nevertheless replaced with Y.
- Its previous value is not checked or preserved.
- No structural error is reported.

### Missing promoted node
