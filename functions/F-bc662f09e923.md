# F-bc662f09e923

## Purpose

F-bc662f09e923 coordinates three ordered operations using three resources associated with a receiver and a caller-supplied four-word region.

The established sequence is:

1. Query the first resource, construct a region anchored at the supplied upper-left coordinates, and submit an operation using that region.
2. Advance the working upper boundary, query the second resource, construct a region anchored at the supplied lower boundary, and submit another operation.
3. Reduce the working lower boundary, query the third resource, and submit a final operation using the remaining working region.

An apparent intent is to place an upper segment and a lower segment, then fill the space between them. This interpretation follows from the coordinate arithmetic and dependency arguments; the actual rendering, copying, scaling, clipping, or compositing behavior belongs to dependencies and is not established here.

The function does not return a result or report dependency success.

## Interface

### Inputs

The function receives three arguments:

| Argument | Established use |
|---|---|
| Receiver address | Supplies three 32-bit resource values and the address of an embedded context. |
| Auxiliary word | A 32-bit argument that is not read by this function. |
| Region address | Points to four consecutive 32-bit words that are read into working storage. |

The receiver is addressed using these byte offsets:

| Offset | Use |
|---|---|
| `0xC4` | Address of an embedded context passed to operation dependencies. |
| `0x1E8` | First resource value. |
| `0x1EC` | Third resource value. |
| `0x1F0` | Second resource value. |

Each resource access reads a 32-bit value. The operation dependencies receive the address at offset `0xC4`, not a word loaded from that address. The extent and layout of that embedded context are unknown.

The input region occupies 16 bytes. Its four words are read in ascending order. For describing the arithmetic, this contract calls them **left**, **top**, **right**, and **bottom**. These are semantic labels inferred from usage, not an independently established coordinate convention.

The input right word is copied into working storage but does not participate in the first two constructed regions. In the visible direct data flow, it is preserved for the final operation.

### Outputs

There is no explicit return value.

The directly observable outputs are the ordered calls to dependencies, their arguments, and whatever effects those dependencies produce. This function itself contains no explicit store through the original region address or into receiver fields.

### Preconditions

The supplied addresses must support the accesses described above. Specifically:

- The region address must permit four consecutive 32-bit reads.
- The receiver must permit 32-bit reads at offsets `0x1E8`, `0x1EC`, and `0x1F0`.
- The address at receiver offset `0xC4` must be acceptable to the operation dependencies.
- Resource values must satisfy the respective dependencies’ requirements.

No null checks, resource-validity checks, coordinate checks, or bounds checks are present.

No region-ordering requirement is enforced. Any requirement that right be at least left, or bottom be at least top, is a caller or dependency precondition rather than a check implemented here.

## Behavior

### Working records and arithmetic

The function uses separate temporary records for:

- A working copy of the caller’s region.
- A four-word query result.
- A four-word copy of a query result, used by the first two operations.
- A 16-byte destination record prepared by a construction dependency.

All visible coordinate calculations use 32-bit words. This contract describes differences and sums in those words; it does not assume wider intermediates, saturation, or checked arithmetic.

For a queried record with words interpreted as left, top, right, and bottom:

- Its horizontal span is right minus left.
- Its vertical span is bottom minus top.

Those interpretations explain the argument relationships. Whether endpoints are inclusive or exclusive is not established.

The function performs no explicit handling of arithmetic overflow. Acceptance examples below use values whose differences and sums fit within the signed 32-bit range, avoiding dependence on unresolved overflow interpretation.

### 1. Snapshot the input region

The function reads all four input words before calling any dependency. It copies them into its working region.

Later calculations use that working copy rather than rereading the original region. Consequently, a later change to the original region storage does not, by itself, change the working coordinates already captured.

This is not a general aliasing guarantee. For example, the original region could overlap receiver fields, and a dependency could affect storage subsequently read through the receiver.

### 2. Query the first resource

The function reads the 32-bit resource value at receiver offset `0x1E8` and calls F-c24767c70ad0 with:

- The address of the query-result record.
- The loaded resource value.

It then copies all four words of the query result into the separate source record.

The caller treats the query result as complete. It does not inspect a success indicator or initialize a fallback record before using the result.

### 3. Construct and submit the first region

The function calls F-66c32a9130af with the destination-record address and four 32-bit coordinate values:

- Working left.
- Working top.
- Working left plus the horizontal span of the first query result.
- Working top plus the vertical span of the first query result.

It then reads the resource value at receiver offset `0x1E8` again and calls F-945301cd184f with, in order:

1. That newly read resource value.
2. The embedded-context address at receiver offset `0xC4`.
3. The source-record address.
4. The destination-record address.
5. The constant `0xFF`.

The two resource reads are distinct. The function does not cache a single first-resource value across the query, construction, and operation calls.

After F-945301cd184f returns, the function advances working top by the vertical span of the **source record as it exists at that time**.

That timing matters. The operation dependency received the source-record address before this span is calculated. The visible function does not establish that the dependency leaves the record unchanged. If the dependency changes its top or bottom word, the subsequent advance uses the changed words.

### 4. Query the second resource

The function reads the 32-bit resource value at receiver offset `0x1F0` and calls F-c24767c70ad0 with the query-result address and that resource value.

All four result words are then copied over the source record used for the first operation. Thus the second operation starts with a fresh copy of the second query result, not the possibly modified first source record.

### 5. Construct and submit the second region

The function calls F-66c32a9130af with the destination-record address and:

- Working left.
- Working bottom minus the vertical span of the second query result.
- Working left plus the horizontal span of the second query result.
- Working bottom.

It then rereads the resource value at receiver offset `0x1F0` and calls F-945301cd184f with:

1. The newly read resource value.
2. The embedded-context address.
3. The second source-record address.
4. The destination-record address.
5. The constant `0xFF`.

After this call returns, the function reduces working bottom by the vertical span of the **current second source record**.

As with the first operation, a modification to the source record by F-945301cd184f can affect this adjustment. The adjustment is not necessarily based on the original query result or on the destination region constructed before the operation.

### 6. Query the third resource and submit the final region

The function reads the 32-bit resource value at receiver offset `0x1EC` and calls F-c24767c70ad0 with the query-result address and that value.

Unlike the first two stages, it does not copy this query result into the separate source record and does not call F-66c32a9130af.

It rereads the resource value at receiver offset `0x1EC` and calls F-168345203dbe with:

1. The newly read resource value.
2. The embedded-context address.
3. The query-result address directly.
4. The working-region address directly.
5. The constant `1`.
6. The constant `0`.

Absent dependency-induced modifications to private temporary storage, the final working region has:

- The original left.
- The original top advanced by the first source record’s post-operation vertical span.
- The original right.
- The original bottom reduced by the second source record’s post-operation vertical span.

No further processing follows the final dependency call.

### Ordering and errors

On an execution in which every dependency returns normally, the call order is:

1. F-c24767c70ad0 for the first resource.
2. F-66c32a9130af for the first destination.
3. F-945301cd184f for the first operation.
4. F-c24767c70ad0 for the second resource.
5. F-66c32a9130af for the second destination.
6. F-945301cd184f for the second operation.
7. F-c24767c70ad0 for the third resource.
8. F-168345203dbe for the final operation.

There is no conditional early return, retry, rollback, or dependency-result check. A failure that prevents a dependency from returning normally can interrupt this sequence; its exact mechanism and effects are unknown.

## Side effects

### Direct effects

The function directly writes its own temporary records. Its direct external-memory accesses are reads of the initial region and reads of the three resource slots.

It does not explicitly update the caller’s region, replace receiver resources, allocate memory, or release memory.

### Dependency-mediated effects

The dependencies receive pointers to temporary records and, for operation calls, the embedded context. Their effects may include mutations to those records or other state. No claim that they preserve receiver state, globals, resource slots, or memory follows from this function alone.

In particular:

- Every resource slot is reread for its operation call after its query.
- The first two source records are read again after being passed to an operation dependency.
- The final operation receives the working region itself.

The temporary records exist for this invocation. No explicit ownership-transfer or release protocol is visible. Whether dependencies retain pointers or own any resource is documented_only; this function does not establish a safe lifetime for retaining pointers beyond its return.

## Acceptance examples

These are conditional static expectations, not runtime test results. Unless stated otherwise, assume each dependency returns normally, each query supplies four valid words, and dependencies do not alter records or receiver fields beyond the described query and construction outputs.

### Ordinary nonzero segments

Given an input region of `(10, 20, 110, 220)`:

- The first query returns `(3, 4, 33, 14)`, giving spans of 30 and 10.
- The first construction receives `(10, 20, 40, 30)`.
- Working top becomes 30.
- The second query returns `(7, 9, 47, 24)`, giving spans of 40 and 15.
- The second construction receives `(10, 205, 50, 220)`.
- Working bottom becomes 205.
- The final operation receives working region `(10, 30, 110, 205)`.

The queried records’ nonzero origins do not shift the constructed destination origins. Only their differences are used in destination construction.

### Input right does not constrain the first two regions

If the preceding example changes only input right from 110 to 25:

- Both construction calls receive exactly the same coordinates as before.
- The final working region is `(10, 30, 25, 205)`.

There is no explicit clipping of the first two constructed regions to input right.

### Combined segment heights exceed the available height

Given input `(0, 0, 50, 10)` and first and second vertical spans of 8 and 7:

- Working top becomes 8.
- Working bottom becomes 3.
- The final operation receives `(0, 8, 50, 3)`.

The function neither suppresses the final call nor normalizes the reversed vertical boundaries.

### Zero-height queried record

If the first query’s top and bottom are equal:

- The first construction receives equal top and bottom coordinates.
- The first operation is still submitted.
- Working top remains unchanged, provided the first operation does not change the source record’s vertical span.

### Source mutation affects the remaining region

Suppose the first query has vertical span 10, but the first F-945301cd184f call changes its source record to have vertical span 12.

- The first destination was already constructed using span 10.
- The later working-top adjustment uses span 12.

A contract that always advances top by the originally queried height would not capture this visible read order.

### Resource replacement between calls

If the first query uses resource value A, and an intervening dependency changes the first resource slot to B, the first F-945301cd184f call receives B.

The function does not enforce equality between the resource queried and the resource later operated on. The same reread rule applies to the second and third resource slots.

### Unused auxiliary argument

Changing only the auxiliary 32-bit argument does not change this function’s visible calculations or dependency arguments. It is not read.
