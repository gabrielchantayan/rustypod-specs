## Behavior

### Interpretation rules

The following sequence preserves the order shown in the supplied representation. It is not a claim about instruction-level ordering on hardware.

A value described as **captured** is the result of a particular read. Later memory changes do not cause that captured value to be automatically refreshed. Conversely, later reads must observe the storage as it exists when those reads occur.

All low-byte and low-halfword descriptions refer to truncation to eight or sixteen bits. For an address-derived value, this is truncation of its numerical representation, not a read from the addressed memory.

Aliasing is not excluded. Explicit arguments, implicit bases, derived addresses, and external slots may identify overlapping storage. Consequently, the sequence cannot be reduced to a final field-value table without additional non-aliasing assumptions.

1. Write the second argument as a 32-bit value at base B plus `0x14`.
2. Write the low eight bits of base A at base B plus `0x0D`.
3. Write the first argument as one byte at base A.

These are conditional static examples, not executed tests.

### Low-byte replacement

The function writes `0x123456AB` at base B plus `0x14` and later at base B plus `0x24`. Its later byte write at base B plus `0x0D` writes `0xAB`, replacing the earlier byte written there from base A.

This example does not imply that the earlier write can be omitted.

### Captured displacement and repeated store

Assume the displacement read yields `0x00001234`, and subsequent destinations are valid.

Both stores to base B plus `0x1234` have width sixteen bits and payload `0x1234`. A separate halfword store targets the sum of the captured external-slot-A value and `0x1234`.

If one of those destinations overlaps an input to an intervening operation, the resulting effect must follow the stated ordering rather than a simplified final-state description.

### OR is not offset addition

Assume the byte read produces `0x44`, with no signedness ambiguity.

The byte-derived writes target numerical addresses `0x89` for the word store and `0x88` for the later byte store. The first outgoing argument is `0x44`, because `0x44` OR `0x44` remains `0x44`; it is not `0x88`.

Successful execution additionally requires those low numerical addresses to be writable.

### High-bit byte ambiguity

Assume the byte read returns `0xFF`.

An unsigned-character interpretation produces byte-derived value `0x000000FF`. A conventional signed-character-to-32-bit-unsigned interpretation produces `0xFFFFFFFF`. Acceptance must remain conditional on the target interpretation; selecting either case without further evidence would overstate the contract.

### Captured outgoing payload

Assume the read at base B plus `0x44` captures a value, and a later store overlaps that same location.

The third represented outgoing argument remains the captured value. It is not replaced by the later memory contents.
