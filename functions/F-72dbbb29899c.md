# F-72dbbb29899c

## Purpose

The supplied static representation describes an entry sequence followed by an unconditional loop. The function reads a selector byte, uses that byte to choose a low numeric destination address, and writes one byte there. It interleaves these accesses with indirect calls and carries selected dependency results into subsequent call arguments.

No application-level purpose is established. The evidence does not identify the accessed locations as ordinary memory, device registers, an output stream, or valid addresses on the intended platform.

This contract describes the visible behavior conditional on the supplied reconstruction being accurate. That qualification is material: the supplied representation reports invalid instruction data and removal of unreachable regions. The apparent function boundary, calling conventions, and unconditional loop have not been independently validated.

## Behavior

### Arithmetic and address interpretation

Each selector read produces an unsigned byte, from 0 through 255. Adding 17 produces a numeric destination address from 17 through 272, inclusive. The following write affects one byte at that destination.

The selector address is formed by multiplying the fourth input by 1,024 and then adding 1. Both operations are displayed using signed integer arithmetic. Their behavior is unresolved where an intermediate or final result falls outside the signed 32-bit range.

The first call target is independently formed by adding 3,956 to the signed 32-bit link-register-derived entry value. This addition is representable for entry values no greater than 2,147,479,691. Larger signed entry values overflow the displayed signed arithmetic. No lower-bound overflow is possible from adding this positive constant to a valid signed 32-bit input.

For either address expression, a **conditional 32-bit machine-bitvector interpretation** would retain the low 32 bits of the arithmetic result. That is not an unconditional statement about the recovered signed expression, pointer conversion, or actual execution.

The first explicit input is unsigned 32-bit:

- Shifting it right by eight is a logical shift.
- Shifting it left by one retains the low 32 bits.

Consumed dependency results are recovered as signed 32-bit quantities. Their left shifts by two or 26 are not given a portable, defined meaning for negative operands or results outside the signed range. Assignment of a shifted result to an unsigned state value does not resolve uncertainty in the preceding signed shift.

### Entry sequence

The following observable operations occur in order:

1. Read one unsigned selector byte from the address derived from the fourth input.
2. Add 17 to that byte and write the low eight bits of the register-derived entry value to the resulting destination.
3. Invoke F-D01 at the target formed from the signed link-register-derived entry value plus 3,956. Its one explicit argument is the first input shifted left by one.
4. Invoke F-D02 with no explicit arguments. Retain its recovered signed 32-bit result as the initial carried result.

The entry write precedes both calls. In particular, uncertainty or failure in forming or invoking the F-D01 target does not introduce a visible check before that write.

F-D01’s result is not explicitly consumed. F-D02’s result supplies the first argument of the first loop-head call.

### Unsigned selector and entry ordering

Assume the entry selector read returns 255 and the register-derived entry value has low byte 171.

### First-target signed-addition boundary

For the next input value, 2,147,479,692, the mathematical sum is 2,147,483,648, outside the signed 32-bit range. The contract does not require an unconditionally defined target for this case.

Only under the additional 32-bit wrapping interpretation would the resulting target bit pattern be hexadecimal 80000000. This does not establish that the address is executable or that the call succeeds.

The entry byte write precedes the first call in either case; no overflow-validation branch is visible.

### Distinct loop heads

Assume all calls return and two iterations complete.

The first loop head invokes F-D03. The second invokes F-D04, and subsequent iterations continue using F-D04 rather than alternating targets.
