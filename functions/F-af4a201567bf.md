# F-af4a201567bf

## Purpose

F-af4a201567bf manages a buffered input-processing operation. It requests transfers from an internal output region to a caller-supplied address, accounts for those requests, obtains additional input, and invokes one of two transformation dependencies.

The source establishes transfer-dependency calls and subsequent count bookkeeping—not the dependency’s actual copying behavior. Descriptions of bytes reaching the destination are conditional on that dependency implementing the expected copy operation.

A preliminary phase examines newline-delimited segments and can compact input directly. The combination suggests a decoding reader with preliminary framing recognition. That is **inferred intent**, not an established encoding or protocol contract.

## Interface

### Arguments and return value

Three 32-bit arguments identify:

1. An object address.
2. A destination address.
3. An unsigned requested count.

Addresses, counts, offsets, and bookkeeping arithmetic use 32-bit representations. Several count comparisons interpret those representations as signed integers. Arithmetic wraps modulo \(2^{32}\); the source does not establish overflow rejection.

The unsigned 32-bit result is:

- The accumulated transfer-accounting total, if that total is nonzero.
- Otherwise, a saved input-dependency result, initially zero.
- Zero on initial eligibility failure or when a transformation failure clears the fallback without a nonzero accumulated total.

A negative input result can therefore be returned as its unsigned bit pattern. Transformation errors follow a different rule.

## Behavior

### Eligibility and mode transition

A zero destination returns zero without reading the object’s state-pointer field. Otherwise, the function reads that field. A zero state address returns zero before reading the input handle. A zero input handle also returns zero.

These early returns skip ordinary completion.

If the state’s mode is not `2`, the function performs these ordered actions:

1. Writes mode `2`.
2. Clears produced-output count.
3. Clears consumed-output offset.
4. Clears retained-input count.
5. Calls F-d852c8a9fd0c with the embedded context address.

It does not directly initialize the skip flag, preliminary-scanning flag, or activity field. The reset dependency’s additional effects are unknown. A zero requested count does not bypass this transition.

### Existing output

A signed-positive produced-output count triggers a transfer attempt before input-loop eligibility is checked—even when the request is zero or signed-negative.

The candidate count is the modular difference between produced count and consumed offset. A signed comparison limits it to the requested count.

Before calling the transfer dependency, the function calculates the modular sum of consumed offset and chosen count. An unsigned result greater than `0x5dd` invokes F-unresolved-02 with two zero arguments. The supplied source marks that call nonreturning. This guard does not detect wrapped additions or validate the destination.

Otherwise, F-unresolved-01 receives destination, output-storage address plus consumed offset, and chosen count.

After the call, the function reduces the remaining request and advances the destination. It then rereads the consumed offset and adds the chosen count. If the resulting offset equals the currently read produced count, it clears produced count and consumed offset, in that order.

The accumulated transfer-accounting total records the chosen count irrespective of whether the opaque dependency actually copied bytes. Post-call state reads can observe dependency mutations or aliased writes. This end-offset guard is not repeated for newly produced output.

### Input acquisition

Further input work requires both remaining request and activity/status to be signed-positive. Failure of either condition begins ordinary completion.

Thus retained input is not automatically processed merely because it exists at entry: an inactive state can prevent entering the input-processing path.

F-81e98a37a112 receives the object’s current input handle and input-storage address advanced by the retained count. No explicit capacity argument is visible.

For a signed-positive result, the function adds that result to the retained count read after the call and stores the modular sum.

For a zero or signed-negative result:

- It saves the result as the fallback.
- It fetches the object’s input handle again and reads that handle’s flags.
- If bit `0x8` is set, ordinary completion follows without a direct activity-field assignment.
- Otherwise, it stores the result in activity/status.
- A currently zero retained count causes completion.
- With retained input, processing continues using zero newly acquired bytes.

The handle inspected after the call need not be the handle passed into it. The retained count is also read after the dependency call.

### Preliminary scanning

A nonzero preliminary-scanning flag selects this phase. If object flag `0x100` is set, scanning is bypassed: retained count is cleared and transformation begins immediately, without applying the normal size threshold.

Otherwise, scanning begins at input-storage offset zero. Only byte `0x0a` is a delimiter; `0x0d` has no separate treatment.

For each newline:

- A nonzero skip flag is cleared, and the candidate segment starts immediately after that newline.
- Otherwise, F-7720e7e55f8d receives context, output storage, a temporary output-count address, candidate address, and candidate length including the newline.
- If its signed return is less than one, the temporary output count becomes the effective scan result.
- If that effective result is zero and the preliminary flag is still nonzero, the context is reset and the candidate begins after the newline.

The temporary count is not visibly initialized before the call. Paths consulting it require the dependency to have supplied a usable value. The preliminary flag is inspected after the transformation call, so dependency changes can affect selection.

Any other effective result selects the candidate. Selection first compacts the remaining suffix when the candidate starts after the input base. It reduces the local input length by the candidate’s displacement and directly copies that many bytes forward, one byte at a time. It then resets the context and clears the preliminary flag.

**Selection does not invariably trigger immediate transformation.** The function compares the current scan index, still measured from the original input beginning, with the possibly reduced local length:

- **Unequal:** clear retained count and transform immediately using the local length.
- **Equal:** execute scan-end handling instead, then return to input-loop eligibility.

The scan pointers are not rebased after compaction. Consequently, the equality branch can perform a second forward copy using the old candidate and scan-end addresses. Its reads can observe bytes changed by the first compaction.

### Scan-end handling

Scan-end handling also applies when scanning naturally exhausts the available input.

- If the candidate still equals the input base, a local length exactly `0x400` sets the skip flag to `1` and clears retained count. Other lengths cause no direct retained-count update on this branch.
- If the candidate differs from both the input base and the scan-end pointer, the function directly copies their intervening bytes forward and stores their pointer difference as retained count.
- If the candidate equals the scan-end pointer, there is no direct retained-count update.

The last case must not be interpreted as clearing all consumed input.

After scan-end handling, execution returns to loop eligibility. It does not immediately apply the normal transformation threshold. In the exceptional selection-equality case, preliminary scanning has already been cleared, but another input acquisition still precedes normal processing if loop eligibility holds.

### Normal processing threshold

When preliminary scanning is zero after input acquisition, transformation occurs if:

- The accumulated count is signed-greater than `0x3ff`; or
- Activity/status is not signed-positive.

Otherwise, execution returns to input-loop eligibility and may acquire more input.

A short final chunk can therefore be processed after a nonpositive input result, provided the earlier handle-flag and retained-count decisions permit it. Preliminary scanning has its own control flow and need not process that chunk.

### Stateful transformation

With object flag `0x100` clear, F-7720e7e55f8d receives context, output storage, the produced-count field’s address, input storage, and the current local input length.

After the call, retained count is cleared.

A signed-negative return enters the shared transformation-error path. A nonnegative return proceeds to output handling using the produced-count field, not the return value as an output length. The source does not validate that field or establish that the dependency always writes it.

### Alternate transformation and error handling

With object flag `0x100` set, the local input length is rounded down to a multiple of four by clearing its two low bits. F-22f5795a2978 receives output storage, input storage, and that rounded length.

When the rounded length is signed-greater than two, padding inspection occurs **after** the call:

- A final `=` subtracts one from the returned count.
- If the preceding byte is also `=`, another one is subtracted.
- The preceding byte is read only when the final byte is `=`.

These are modular 32-bit subtractions. They can produce a signed-negative adjusted result, including through unsigned underflow.

If the rounded and local lengths differ, F-unresolved-01 is called with input-base and suffix-address arguments. The supplied call does not establish a transfer-length argument. Afterward, retained count is set to the difference, ordinarily one to three bytes. If the lengths are equal, this branch does not explicitly clear retained count.

The function then clears produced count:

- A signed-positive adjusted result is stored as produced count, and processing status becomes `1`.
- Zero remains status zero.
- A signed-negative adjusted result remains negative.

A negative alternate result therefore enters the same transformation-error path as a negative stateful result. It is not converted to zero or one beforehand.

### Shared transformation error and new-output handling

For either transformation path, a signed-negative processing status causes:

1. Consumed offset to be cleared.
2. Produced count to be cleared.
3. Saved fallback to be cleared.
4. Ordinary completion.

The transformation’s negative status is not returned. Earlier transfer-accounting totals still take precedence if nonzero. Alternate suffix handling and padding adjustment occur before this shared error decision.

For nonnegative processing status, consumed offset is first cleared. The transfer count is the produced count, limited by remaining request through a signed comparison.

F-unresolved-01 receives current destination, output-storage address, and chosen count, including when that count is zero. Afterward, the function:

- Sets consumed offset to the chosen count.
- Adds the count to the accumulated total.
- Compares it with the produced count read after the call.
- Clears produced count and consumed offset if equal.
- Reduces remaining request and advances destination.
- Returns to input-loop eligibility.

There is no additional bounds guard here. Under conventional state and dependency assumptions, unconsumed output remains represented for a later invocation.

### Ordinary completion

Ordinary completion reads object flags, clears their low four bits while preserving the other bits in that write, then calls F-aeffcebde61f with the object address.

It subsequently returns the accumulated total if nonzero; otherwise it returns the saved fallback. A wrapped total of zero also selects the fallback.

The completion dependency may further alter flags or other state. No progress bound, retry limit, or general termination guarantee is established.

## Side effects

- Forward, byte-by-byte writes during scan compaction.
- Clearing the low four object-flag bits before ordinary completion’s dependency call.
- Calls to input, transformation, reset, transfer-like, completion, and failure dependencies.

Writes to the caller’s destination are **conditional effects of F-unresolved-01**, not independently established behavior. Likewise, transformation output writes and input acquisition depend on their callees’ contracts.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, memory is valid, arithmetic remains in the ordinary nonnegative range, and dependencies make only the effects specified by each example. Examples asserting destination bytes additionally assume F-unresolved-01 copies exactly the requested count.

1. **Zero destination.** Return zero without reading the object’s state pointer or invoking ordinary completion.

2. **Mode transition with zero request.** With valid pointers and mode other than `2`, write mode `2`, clear the three count/offset fields, and reset context. With no dependency changes, obtain no input and perform ordinary completion.

3. **Pending output.** Produced count `10`, consumed offset `3`, and request `4` cause a transfer call for four bytes from output offset `3`. If the dependency copies and preserves state, those bytes reach the destination, consumed offset becomes `7`, and the return is `4`.

4. **Pending guard.** A modular calculated end offset of `0x5dd` passes. `0x5de` invokes F-unresolved-02. This does not establish safety when addition wraps.

5. **Input failure precedence.** With zero retained input and no accumulated transfer count, a negative input result becomes the returned unsigned bit pattern after completion. A clear handle flag `0x8` also causes that result to be stored in activity/status. If the accumulated total is instead `5`, the return is `5`.

6. **Stateful failure.** A signed-negative F-7720e7e55f8d result clears retained count, consumed offset, produced count, and fallback. With no earlier accounted transfer, return zero.

7. **Alternate positive adjustment.** Rounded length `8`, dependency result `6`, and two trailing `=` bytes produce adjusted count `4` and positive processing status `1`. The ensuing transfer call is limited by the request.

8. **Alternate underflow.** Rounded length `4`, dependency result zero, and one trailing `=` produce `0xffffffff`. That signed-negative status reaches shared error handling. Output count, consumed offset, and fallback are cleared; the function does not request a huge output transfer from that result.

9. **Exceptional selected-segment equality.** Suppose accumulated input is six bytes: `A`, newline, `B`, `C`, newline, `D`. The skip flag discards the first segment, leaving candidate offset `2`. A selecting result at newline index `4` first compacts four bytes, yielding prefix `B`, `C`, newline, `D`. Reduced local length `4` now equals scan index `4`. Scan-end handling therefore copies three bytes from the old candidate offset `2`. Assuming the dependencies preserve input storage, that second copy reads newline, `D`, newline and stores retained count `3`. Preliminary scanning is cleared, but immediate transformation does not occur.

10. **High-bit request.** Request `0x80000000`, with no pending output, fails signed-positive loop eligibility and obtains no input. It is not an ordinary two-gibibyte request.
