# F-d8b7887cd7a1

## Purpose

F-d8b7887cd7a1 searches an embedded collection for a record whose first byte, interpreted as a zero-extended address value, equals the second input. If a match is found, it updates the record’s second byte. If traversal reports exhaustion before a match is found, it requests three bytes of storage, initializes a record, and submits its address to an indirect operation on the embedded collection.

This is a byte-keyed update-or-create operation only by inferred intent. The established comparison uses the entire pointer-width value of the second input, whereas creation stores only its low eight bits. Consequently, inputs outside the range 0 through 255 cannot match any existing record through the visible comparison, even though their low byte can be stored in a newly created record.

The function also returns a 64-bit composite of two working pointer values. The source does not establish that this composite is a conventional success result, a stable record handle, or an ownership transfer.

### Output

The returned value is 64 bits, composed as follows:

- Bits 63–32 contain the final 32-bit candidate-record pointer value.
- Bits 31–0 contain the final 32-bit working pointer value.

The working pointer initially holds the object address. On the creation path, it is replaced by the allocation result and is subsequently passed by address to the indirect operation. That operation can therefore replace it before the return value is assembled.

The candidate-record pointer is explicitly set to zero before traversal. Each traversal step receives its address and can replace it. Its value on a zero-status traversal result is not established.

No distinct Boolean, error code, or allocation-status result is constructed.

## Behavior

### 1. Establish traversal state

The function first makes local copies of all four inputs. The copies of the update value and additional value occupy the traversal-related storage described above.

It calls F-8ca21d3a8cca with:

1. The address of the first traversal-state word.
2. The object address advanced by 96 bytes.

Only after this call returns does the function explicitly set the candidate-record pointer to zero. Thus, initialization of the candidate pointer is ordered after traversal initialization, not before it.

The initializer’s return value, if any, is not used. The visible function provides no independent initialization-failure branch.

### 2. Advance traversal

The function invokes F-b38a3aba0e18 at least once. Each invocation receives:

1. The traversal-state address.
2. The address of the candidate-record pointer.

The returned status is tested against zero:

- Zero immediately selects the creation path.
- Any nonzero value selects candidate inspection.

The source supplies no separate handling for negative status values. If a dependency uses a negative value to represent an error, this caller would still treat it as the nonzero, candidate-present case.

The candidate pointer is not explicitly cleared between successive traversal calls. A dependency that returns a nonzero status must therefore make the resulting pointer usable for the subsequent byte read, whether by writing a new pointer or intentionally leaving a previously valid one in place.

### 3. Compare a candidate

For a nonzero traversal status, the function reads exactly the first byte of the candidate record for its visible comparison. That byte is treated as unsigned, producing a value from 0 through 255, and is extended to the apparent 32-bit pointer width.

The extended value is compared with the complete search operand. The search operand itself is not first truncated to a byte.

If unequal, traversal resumes. The function does not visibly write to that candidate record.

If equal, the function writes the low eight bits of the update value to offset 1 of the candidate record. It does not visibly change that record’s first byte or its byte at offset 2. It then proceeds to traversal finalization without requesting another traversal step.

The first matching candidate encountered ends the search. Later records, including possible duplicates, are not visited by this function after that match.

### 4. Create a record after zero traversal status

When traversal returns zero, the function calls F-8157a180d901 with the numeric request value 3.

The returned pointer replaces the working pointer. The function then performs three byte stores, in this order:

1. Offset 0 receives the low eight bits of the search operand.
2. Offset 1 receives the low eight bits of the update value.
3. Offset 2 receives zero.

There is no visible null-result check before these stores. The contract therefore requires the dependency to return suitably writable storage for normal completion; it does not establish a recoverable allocation-failure path.

After the three stores, the function reads the dispatch-table address from the collection subobject at object offset 96. It then reads the callable address at dispatch-table byte offset 28 and invokes that target with:

1. The address of the embedded collection subobject.
2. The address of the working pointer containing the new record address.

The dispatch reads occur after allocation and initialization. A dispatch target captured before those operations would not necessarily preserve the same behavior if intervening dependencies can alter the object.

Passing the record pointer by address permits the indirect target to replace the working pointer. Its return value, if any, is not inspected. The visible caller does not itself report submission failure, retry, or undo the three initialization stores.

The candidate-record pointer is not explicitly changed by the creation branch. In particular, zero traversal status does not cause this function to clear it. Its high-half contribution to the eventual return value depends on what the traversal dependency left there.

### 5. Finalize and return

Both ordinary paths converge on a call to F-d0d3f100effc with the traversal-state address:

- After updating a matching record.
- After initializing and submitting a new record.

The return composite is assembled after this finalization call. No separate direct record-release operation is visible.

This finalization is established only for control flow in which preceding reads, writes, and dependency calls complete normally. The source does not establish exception handling, recovery from invalid memory access, or cleanup after a dependency fails to return.

## Side effects

### Direct memory effects

The function directly:

- Copies inputs into local storage.
- Initializes the candidate pointer to zero after traversal initialization.
- Allows traversal to write the candidate pointer through its address.
- On a match, writes one byte at candidate offset 1.
- On creation, writes three consecutive bytes to the allocation result.
- Allows the indirect collection operation to replace the working pointer through its address.

It also reads candidate key bytes and, on creation, the dispatch-table and callable addresses.

These observations describe direct operations. They do not constrain additional reads or writes performed by dependencies.

### Ownership and lifetime

The allocation-like dependency is asked for three units, and the caller treats its result as at least three writable bytes. Whether the dependency is a general allocator, a pool operation, or another storage provider is unknown.

The new pointer is passed by address to the collection operation. This is consistent with insertion or ownership transfer, but does not prove either. The indirect target might adopt, copy, replace, retain, or release the pointer; its contract is unavailable.

Likewise, the traversal finalizer’s name or position does not establish that it only releases traversal resources. Its effects on collection state, records, globals, or retained addresses remain unknown.

The function contains no direct deallocation. That does not establish that no storage is released during execution, because opaque dependencies can have such effects.

### Preconditions and failures

Normal completion requires, along the executed path:

- Valid traversal-state handling by the three traversal dependencies.
- For every nonzero traversal status, a readable candidate byte at offset 0.
- On a match, writable candidate storage at offset 1.
- On creation, an allocation result writable for three consecutive bytes.
- On creation, a readable collection dispatch pointer and readable callable slot at the stated offsets.
- A callable indirect target with a compatible argument convention.
- Address calculations that designate the required storage in the apparent 32-bit address model.

No bounds, null, writability, or dispatch-validity checks are visible. The source provides no defined error result for violations of these requirements.

Termination is also conditional. A traversal dependency that continues returning nonzero candidates without producing a match can cause indefinite iteration.

### Creating after exhaustion

Suppose traversal returns zero, the search operand is 7, and the update value’s low byte is 52.

It must then obtain the indirect target from the collection dispatch table and pass the collection address and the address of the working pointer. Traversal finalization follows that call.

### Distinguishing full-width search from stored key

That record must not match: its extended key value is 1, not 257. If traversal eventually returns zero, the newly initialized record’s first byte must nevertheless be 1 because creation stores only the low eight bits.

This does not establish identical overall execution: the full 32-bit update value also initializes traversal-related storage, and its influence through dependencies is unknown.

### Zero-valued key

This does not permit a null candidate pointer: a nonzero traversal result still leads to reading the candidate record’s first byte.

### Nonzero negative traversal status
