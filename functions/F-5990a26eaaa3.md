# F-5990a26eaaa3

## Purpose

F-5990a26eaaa3 dispatches a single 32-bit input through an indirectly selected mandatory operation, with optional operations before and after it.

The established behavior is an ordered sequence:

1. Capture a base value from a global location.
2. Conditionally invoke an operation selected through the current global base, passing the input and zero.
3. Invoke a mandatory operation selected through the captured base, passing the input.
4. Conditionally invoke an operation selected through that same captured base, passing zero and one.

The two optional invocations use the same byte offset within their respective bases, but neither their target identities nor their relationship is guaranteed. The mandatory invocation uses a different offset.

**Inferred intent:** The optional invocations may bracket the mandatory operation, with their second arguments distinguishing entry and exit phases. This interpretation is not an established contract of the indirect targets. In particular, the exit-side invocation does not receive the original input.

### Output

## Behavior

### 1. Capture the base

Before invoking any dependency, F-5990a26eaaa3 reads the global base and retains that value for later use.

This captured value determines the base used for both:

- The mandatory target lookup at offset `0x18`.
- The final optional target lookup at offset `0x30`.

Capturing the base does not capture either target field. Those fields are read later, at their respective dispatch stages.

### 2. Perform the first optional dispatch

The function checks the target at offset `0x30` through the global base.

If the checked target is null, this invocation is skipped. Execution proceeds to the mandatory dispatch.

If the checked target is non-null, the represented call expression selects the target through the global base again and invokes it with two arguments, in this order:

1. The original 32-bit input.
2. Zero.

The supplied representation does not save the checked target for the invocation. Thus, the null check and the actual target selection are separate represented reads. Under stable state, they select the same target. If the global base or its target field changes between those reads, the checked target and invoked target need not match.

The function contains no synchronization or validation to make such changes safe. Whether these separate source-level reads correspond to distinct machine loads is not established by the fragment.

### 3. Perform the mandatory dispatch

After the first optional invocation returns normally—or immediately if it was skipped—the function reads the target at offset `0x18` through the originally captured base.

It invokes that target with the original 32-bit input as its sole represented argument.

There is no null check for this target. There is also no visible fallback target, error return, or recovery path for an invalid target.

Because the target field is read at this stage rather than captured at entry, an earlier invocation can affect which target is selected by modifying the field in the captured object. Changing only the global base does not redirect this lookup: the captured base remains in use.

### 4. Perform the final optional dispatch

After the mandatory invocation returns normally, the function reads the target at offset `0x30` through the originally captured base.

This target is retained for the immediately following null check and possible invocation.

- If it is null, the function returns without another invocation.
- If it is non-null, the function transfers control to that target with two arguments, in this order:
  1. Zero.
  2. One.

This field is read after the mandatory invocation. It is not a saved copy of the target used or checked during the first optional stage. Consequently, the mandatory invocation may enable, disable, or replace the final optional target by modifying the captured object.

The supplied representation marks this final transfer as an incompletely recovered indirect jump, modeled as a call. The selected target and represented arguments are available as static evidence; whether the transfer is an ordinary call followed by return or a tail transfer is not established.

### Ordering and completion

On a normally completing path, dependency entry order is:

1. First optional target, if selected.
2. Mandatory target.
3. Final optional target, if selected.

Each later stage depends on the preceding invocation returning normally. No visible cleanup construct guarantees execution of the final optional stage if an earlier dependency terminates execution, faults, unwinds, or otherwise fails to return.

The function itself contains no retry, loop, recursion, or alternate dispatch branch beyond the two null-dependent choices.

## Side effects

The supplied representation contains no direct write to the global base, either accessed target field, or any caller-supplied memory.

Its direct effects are reads and indirect control transfers. Any additional state changes occur through the selected dependencies.

In particular, an invoked dependency may change:

- The global base.
- Either target field in the captured object.
- Other memory or external state.

The fragment supplies no dependency contracts that would justify assuming otherwise.

The captured base remains the basis of later accesses even if a dependency changes the global base. Its continued validity is therefore a critical precondition. If an earlier dependency invalidates or releases the captured object, the function still attempts its later field reads through that captured value.

No allocation, release, ownership transfer, reference-count adjustment, or lifetime extension is directly shown. Passing the input does not establish that it conveys ownership. Passing zero likewise does not establish a null-pointer argument: the expected parameter types of the dependencies are unknown.

There is no explicit error reporting. Invalid storage, unreadable fields, incompatible targets, or failures inside dependencies have no locally represented handling. The precise machine or runtime consequence is undocumented.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Each assumes valid readable storage, compatible executable targets, and normal return from every dependency whose return is needed.

### Stable object with an optional target

Given a stable global base whose `0x30` field contains a non-null optional target and whose `0x18` field contains a valid mandatory target:

- The optional target first receives the original input and zero.
- The mandatory target next receives the original input.
- The optional target finally receives zero and one.

For example, an input with the bit pattern `0xFFFFFFFF` is forwarded unchanged at the first two stages. No signed interpretation is required.

### Stable object without an optional target

Given a stable global base with a null `0x30` field and a valid `0x18` target:

- The first optional invocation is skipped.
- The mandatory target receives the original input.
- The final optional invocation is skipped.

A null optional field does not suppress the mandatory invocation.

### First dependency replaces the global base

Suppose the captured base initially identifies object A. The first optional invocation then changes the global base to identify object B, without invalidating A.

The mandatory and final target lookups still use A. They do not switch to B merely because the global location changed.

### First dependency replaces the mandatory target

Suppose the first optional invocation changes A’s `0x18` field before returning.

The mandatory dispatch selects the replacement target because that field is read after the first invocation. The function does not retain an entry-time copy of the mandatory target.

### Mandatory dependency changes the final optional target

Suppose the mandatory invocation changes the captured object’s `0x30` field.

- Replacing it with null suppresses the final invocation.
- Replacing it with a non-null target selects that new target for the final invocation.
- Setting it non-null can enable the final invocation even when the first optional stage was skipped.

The final invocation still receives zero and one, not the original input.

### Invalid mandatory target

A null `0x18` target does not produce a graceful skip or an explicit error result. The represented behavior attempts an indirect invocation through it. The resulting fault or other runtime outcome is not established.
