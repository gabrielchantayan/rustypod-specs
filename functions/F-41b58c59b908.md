# F-41b58c59b908

## Purpose

F-41b58c59b908 performs an ascending, first-match search over a range whose signed length is captured from a caller-supplied object.

For each candidate index, it obtains a 32-bit candidate value from F-3b5d52fd8e4a and submits that value to an indirectly dispatched operation. A zero result from that operation accepts the candidate. The function returns the first accepted index, or signed −1 if the captured range contains no accepted candidate.

Two indirect operations prepare shared arguments and a secondary receiver before the range is checked. Consequently, an empty or negative range does not make this function side-effect-free.

The nature of the candidates, the meaning of the caller’s opaque argument, and the semantic meaning of acceptance beyond “the indirect operation returned zero” are not established.

- **Opaque argument:** one 32-bit value forwarded unchanged to the per-candidate indirect operation. It is not interpreted, dereferenced, validated, or arithmetically modified by this function.

The supplied representation uses 32-bit integers and four-byte opaque values. The following primary-receiver layout is relevant:

These are byte displacements, not established method numbers. Complete object layouts, pointer width, alignment requirements, and the platform calling convention are not independently established by the supplied evidence.

### Output

The result is a signed 32-bit integer:

- A nonnegative index identifies the earliest candidate whose acceptance operation returned zero.
- −1 indicates that no candidate was accepted within the captured range.

For a positive captured count, any successful result is strictly less than that count. No other ordinary return value is visible in the supplied function.

## Behavior

### Preparation precedes range rejection

The candidate count is read from the primary receiver before any dependency is called. This captured signed value determines the search limit for the entire invocation.

The initial candidate index is zero. Before deciding whether that index is within range, the function:

1. Invokes the primary receiver’s indirect operation at table displacement +0x18, obtaining a 32-bit reusable value.
2. Invokes the primary receiver’s indirect operation at table displacement +0x58, obtaining the secondary receiver.

These calls occur in that order, including when the captured count is zero or negative.

The second dispatch is resolved from the primary receiver after the first call has returned. The function does not visibly retain the first call’s dispatch-table reference for the second call. A change to the primary receiver’s dispatch-table reference during the first call can therefore affect which target is selected for the second call.

Each preparation result is captured once. Neither preparation operation is repeated for later candidates.

### Search range and order

The effective candidate range is:

- Empty when the captured signed count is zero or negative.
- The consecutive indices from zero through one less than the captured count when it is positive.

Candidates are visited in strictly ascending order. There is no visible skipping, reordering, retrying, or revisiting.

Before generating a candidate, the function compares the current index against the captured count using signed ordering. When the index is greater than or equal to that count, the function returns −1 without generating or checking another candidate.

Later modifications to the primary receiver’s stored count do not change this invocation’s limit. Dependencies may nevertheless observe or modify that storage; their own behavior is not constrained by the captured limit.

### Candidate generation and acceptance

For each in-range index, F-3b5d52fd8e4a is invoked with:

1. The primary receiver.
2. The current signed 32-bit index.

Its result is treated as a 32-bit value and passed to the per-candidate indirect operation.

After candidate generation returns, the function resolves the indirect operation at displacement +0x24 through the captured secondary receiver. In receiver-first notation, its arguments are ordered as follows:

| Position | Value |
|---|---|
| Receiver | Captured secondary receiver |
| First explicit argument | Caller’s opaque 32-bit argument |
| Second explicit argument | Captured reusable 32-bit value |
| Third explicit argument | Current candidate’s 32-bit value |
| Fourth explicit argument | The same captured reusable 32-bit value |

The repeated reusable value is identical at both argument positions. It is not recomputed between them or refreshed between candidates.

The indirect operation’s signed integer result is interpreted only by whether it equals zero:

- **Zero:** return the current index immediately.
- **Any nonzero value:** reject this candidate and advance to the next index.

Positive and negative nonzero results receive the same treatment. No nonzero result is propagated to the caller or visibly treated as a distinct error.

The first accepted candidate terminates the search. No later candidate is generated or checked.

### State changes between calls

The captured secondary receiver is reused throughout the search, but its dispatch-table reference is accessed for each per-candidate dispatch. The per-candidate target is not visibly cached.

Accordingly, changes made by candidate generation or an earlier indirect operation to the secondary receiver’s dispatch-table reference can affect a later target selection. This is a consequence of the visible access pattern, not a guarantee that such mutation is supported or safe.

The captured reusable value is passed by value. If that bit pattern represents an address or handle, the function does not establish that the referenced resource remains unchanged or valid.

### Integer boundaries

The count comparison and returned index use signed 32-bit semantics in the supplied representation.

A count whose high bit is set is negative and therefore gives an empty range. It is not interpreted as a large unsigned candidate count.

For the maximum positive signed 32-bit count, the largest candidate index passed to F-3b5d52fd8e4a is 2,147,483,646. If that candidate is rejected, the index advances to 2,147,483,647, where the range check terminates the search. Thus the visible search progression does not require signed overflow.

The opaque argument, reusable value, and candidate value undergo no visible arithmetic in this function.

## Acceptance examples

These are conditional contract examples derived from the supplied static evidence, not executed tests. Unless stated otherwise, every dependency returns normally and all required receiver accesses remain valid.

### Empty range still performs preparation

Given a captured count of zero:

- F-U01 executes.
- F-U02 executes afterward.
- Neither F-3b5d52fd8e4a nor F-U03 executes.
- The result is −1.

The same behavior applies to any negative captured count.

### First candidate succeeds

Given a captured count of four and a zero result from F-U03 for index zero:

- Only candidate zero is generated and checked.
- The function returns zero.
- Candidates one through three are not generated.

### Nonzero results do not propagate

Given a captured count of three and F-U03 results of −8, 5, and zero for successive candidates:

- Both −8 and 5 reject their respective candidates.
- The function returns two.
- Neither nonzero result becomes the function’s return value.

### Every candidate is rejected

Given a captured count of two and nonzero F-U03 results for both candidates:

- Candidate indices zero and one are generated and checked in that order.
- Candidate two is not generated.
- The function returns −1.

### Count mutation does not resize the range

Given an initially captured count of two, suppose F-U01 changes the stored count to zero.

If subsequent dependencies remain valid and both candidates are rejected, the function still checks indices zero and one, then returns −1. It does not reload the count to shorten the search.

Conversely, increasing the stored count after capture does not extend the range.

### Dispatch changes can affect subsequent calls

Suppose F-U01 changes the primary receiver’s dispatch-table reference. F-U02 is selected using the reference accessed after F-U01 returns.

Suppose candidate generation changes the captured secondary receiver’s dispatch-table reference. F-U03 for that candidate is selected through the secondary receiver after candidate generation returns.

These outcomes require the modified structures to remain valid for the subsequent dispatch.

### Argument reuse is exact

For any reached candidate, F-U03 receives the original opaque argument and two copies of the single value returned by F-U01. Neither copy is replaced with the candidate value or with a newly obtained preparation value.
