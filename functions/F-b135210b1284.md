# F-b135210b1284

## Purpose

F-b135210b1284 edits a length-tracked, byte-addressed object through a mutable handle. Its apparent intent is to replace a requested range with a requested number of bytes initialized by a dependency, using existing storage when permitted and otherwise obtaining replacement storage.

That intent is not a complete description of the established behavior:

- The removal quantity used to calculate the resulting length is bounded by available length, but the source address for the trailing transfer uses the original, unbounded removal request.
- An out-of-range position is reported but is not visibly clamped if reporting returns.
- Replacement bytes are produced by a dependency whose initialization value and semantics are unknown.
- The replacement-storage path delegates important construction details to dependencies. It does not visibly write the new length or a terminating byte.
- A prefix-transfer call exposes no explicit byte count in the supplied representation.

These distinctions are contractual limits, not implementation details that may safely be normalized away.

## Interface

### Arguments and return value

The function accepts four arguments:

1. **Handle:** a pointer to a mutable, 32-bit data-address cell.
2. **Position:** an unsigned 32-bit position.
3. **Requested removal:** an unsigned 32-bit quantity.
4. **Replacement count:** an unsigned 32-bit quantity.

The function returns the original handle address, not the resulting data address. A normal return may leave the handle pointing to its original storage, replacement storage, or a global empty representation.

No separate status value is returned.

### Object layout

For each data address used to inspect the existing object, the supplied representation establishes this layout:

| Offset relative to data address | Width | Observed use |
|---|---:|---|
| −12 bytes | 32 bits | Storage-state test controlling direct mutation |
| −8 bytes | 32 bits | Capacity comparison |
| −4 bytes | 32 bits | Stored logical length |
| 0 onward | Byte-addressed | Payload and, on the direct-mutation path, a trailing zero byte |

The storage-state word is not established to be a reference count, although that is a possible interpretation.

Replacement storage returned by F-fe78e25e82ff is treated as a block whose payload begins 12 bytes after its returned address. The caller does not independently establish the contents of that block’s header.

### Preconditions and arithmetic domain

The function performs no visible null, alignment, header-accessibility, or allocation-validity checks. Defined execution therefore requires a readable handle, accessible required header words, and sufficient accessible storage for the operations actually reached.

The representation uses 32-bit addresses and 32-bit arithmetic quantities. Unsigned comparisons and logical right shifts are significant. Arithmetic results used as unsigned quantities are described below modulo \(2^{32}\). Some intermediate expressions are presented as signed integers; their source-language overflow semantics are not established. Mathematical, unbounded arithmetic must not be substituted for the observed width.

Safe address ranges, overlap support, and successful dependency behavior are additional preconditions wherever the relevant dependency requires them.

## Behavior

### Initial position check

The function first reads the handle’s data address and the length word immediately preceding that data.

If this initial length is less than the position, it invokes F-5829ec5988c0 with:

- Diagnostic code **9**.
- The same fixed metadata address in two argument positions.
- The original position as the final argument.

The metadata’s contents and interpretation are unknown.

No visible return, abort, or effective position clamp follows this call. If the dependency returns, processing continues with the original position.

The diagnostic dependency receives no explicit handle argument. Nevertheless, its ability to modify shared state, including state reachable through aliases, is not excluded.

### Removal and size calculation

After the position check, the function rereads the current handle and stored length.

It computes a 32-bit available quantity as stored length minus position. The effective removal is the smaller, by unsigned comparison, of:

- The original requested removal.
- That available quantity.

For an ordinary valid position, this bounds removal to the remaining logical content. For an invalid position, subtraction may wrap; this is not a general bounds-recovery mechanism.

The function rereads the stored length again and subtracts the effective removal to obtain a remaining-length quantity.

It then computes a 32-bit threshold:

\[
T = \texttt{0xfffffff1} - \text{replacement count}.
\]

If \(T\) is less than or equal to the remaining-length quantity, F-5829ec5988c0 is called with:

- Diagnostic code **8**.
- The same fixed metadata address used by the earlier diagnostic, twice.
- The remaining-length quantity as the final argument.

The comparison includes equality. The subtraction producing \(T\) can itself wrap.

If reporting returns, the function does not visibly reduce the replacement count, effective removal, or eventual resulting length. A temporary assignment made around this diagnostic does not establish an effective size clamp on either subsequent storage path.

Next, the function obtains the data address again and reads its stored length. It computes:

- **Base length:** this newly read length minus the previously determined effective removal.
- **Resulting length:** base length plus replacement count, at 32-bit width.

Because stored length is read more than once, a dependency-induced state change can make these quantities differ from calculations based solely on the initial length.

### Empty result

If the resulting length is zero:

1. F-8a5aadac202f is called with the handle.
2. A global empty-data address is read after that call.
3. That address is written into the handle.
4. The original handle is returned.

The function does not directly write an empty payload or zero-length header on this path. Those properties, and the ownership of the global empty representation, depend on external state and dependency behavior.

The empty path is selected by the computed 32-bit result being zero. It is not restricted to a mathematically empty edit; wrapping arithmetic can also produce zero.

### Eligibility for direct mutation

For a nonzero result, the function computes a trailing-transfer quantity as base length minus position.

Direct mutation is selected only if both conditions hold:

- Adding one to the 32-bit storage-state word, then comparing unsigned, produces a value less than two.
- The resulting length is no greater than the capacity word.

The first condition accepts precisely storage-state bit patterns **0x00000000** and **0xffffffff**. It does not establish that all negative values, or all small values, are acceptable.

### Direct-mutation path

Operations occur in this order:

1. If the trailing-transfer quantity is nonzero, an external transfer primitive is invoked with:
   - Destination at the previously captured data address plus position plus replacement count.
   - Source at that data address plus position plus the **original requested removal**.
   - The trailing-transfer quantity.
2. If the replacement count is nonzero, F-8ff0260f6859 is invoked with:
   - A destination calculated from the handle’s then-current data address plus position.
   - The replacement count.
3. The resulting length is written into the length field preceding the handle’s then-current data address.
4. A zero byte is written at the resulting-length offset from the handle’s then-current data address.
5. The original handle is returned.

No explicit handle-address assignment occurs on this path. A dependency may nevertheless change the handle through other means; preservation is not assumed.

The first transfer uses the captured data address. Later operations reread the handle. Consequently, if the initialization dependency changes the handle, the final header and terminator writes can target storage different from the trailing transfer’s storage.

Overlap safety of the external transfer primitive is unknown.

### Replacement-storage path

If direct mutation is not selected, the function rereads the existing length and computes a preferred capacity, using 32-bit arithmetic:

\[
G = L + (L \mathbin{\gg} 1) + (L \mathbin{\gg} 3).
\]

It also computes \(L + 128\), at the same width. If \(G\) is smaller by unsigned comparison, \(G\) is replaced with that latter quantity.

The capacity argument passed to F-fe78e25e82ff is then:

- \(G\), if the resulting length is no greater than \(G\).
- Otherwise, the resulting length.

Absent wraparound, this expresses approximately 1.625-times growth with a minimum increase of 128. That description is inferred intent, not a guarantee for large 32-bit values.

F-fe78e25e82ff receives the handle, the selected capacity, and the resulting length. Its returned address is treated as a block base; the new payload address is 12 bytes beyond it.

The subsequent order is:

1. If position is nonzero, invoke a second external transfer primitive with the new payload address and the handle’s then-current data address. No third argument is explicit in this call’s supplied representation.
2. If replacement count is nonzero, invoke F-8ff0260f6859 at the new payload address plus position, with the replacement count.
3. If the trailing-transfer quantity is nonzero, invoke the second external transfer primitive with:
   - Destination at the new payload address plus position plus replacement count.
   - Source at the handle’s then-current data address plus position plus the original requested removal.
   - The trailing-transfer quantity.
4. Invoke F-8a5aadac202f with the handle.
5. Write the saved new payload address into the handle.
6. Return the original handle.

The old handle remains in place until the final assignment unless a dependency changes it. Source addresses used after allocation or initialization are obtained from the handle at those later points.

There is no explicit allocation-failure check. There is also no explicit length-field or terminating-byte write on this path. Such construction work may be performed by F-fe78e25e82ff, but that is not established here.

## Side effects

Established direct effects include:

- Reads of the handle, existing header words, and the global empty-data address.
- Diagnostic calls under the specified unsigned conditions.
- Transfers and initialization calls on the selected storage path.
- A direct length-field write and a direct trailing-zero write on the direct-mutation path.
- A handle-address replacement on the empty and replacement-storage paths.

Allocation, deallocation, reference-count changes, initialization contents, and diagnostic output are not established direct effects. They depend on callees.

F-8a5aadac202f is used before replacing the handle, but this alone does not prove that it frees storage, decrements a reference count, resets the handle, or preserves any global.

No rollback or transactional guarantee is visible. A dependency that fails after an earlier transfer or initialization may leave partial changes. Exception, termination, and error-return behavior are unknown.

## Acceptance examples

These examples are conditional static predictions. No runtime tests have been performed. Unless stated otherwise, dependencies return normally and do not alter the handle or relevant shared state unexpectedly.

### Ordinary direct mutation

Given length 10, position 3, requested removal 2, replacement count 4, an accepted storage-state word, and capacity at least 12:

- Effective removal is 2.
- Resulting length is 12.
- Trailing-transfer quantity is 5.
- Primitive A receives destination offset 7, source offset 5, and quantity 5.
- F-8ff0260f6859 receives destination offset 3 and count 4.
- Length 12 is stored, followed by a zero-byte write at offset 12.

The inserted byte values remain unspecified.

### End insertion

Given length 10, position 10, requested removal 0, and replacement count 3:

- Effective removal is zero.
- Resulting length is 13.
- Trailing-transfer quantity is zero, so no trailing transfer is invoked.
- Initialization is requested at offset 10 for count 3.

Storage eligibility determines whether initialization targets existing or replacement storage.

### Removal request beyond the end

Given length 10, position 3, requested removal 20, and replacement count 2:

- Effective removal is 7.
- Resulting length is 5.
- Trailing-transfer quantity is zero.

No trailing transfer occurs, so its unbounded source-offset issue is not exercised.

### Wrapped trailing-transfer quantity

Given length 10, position 11, requested removal 0, and replacement count 1, if diagnostic code 9 returns and execution remains otherwise viable:

- Position remains 11.
- Resulting length is 11.
- The trailing-transfer quantity is **0xffffffff**, not zero.

This case must not be accepted as a safely clamped edit. Dependency and memory-access outcomes are unknown.

### Exact size-diagnostic boundary

If the remaining-length quantity equals the 32-bit value of `0xfffffff1` minus replacement count, diagnostic code 8 is invoked. Equality is not an accepted non-diagnostic boundary.

If reporting returns, no effective size reduction is established.

### Empty result

Given length 4, position 0, requested removal 4, and replacement count 0:

- Resulting length is zero.
- F-8a5aadac202f is invoked.
- The global empty-data address is read afterward and installed.
- No transfer or replacement-byte initialization is requested.

### Replacement storage despite sufficient capacity

Given a nonzero result, sufficient existing capacity, and storage-state word 1, the direct-mutation condition fails. Replacement storage is requested.

For a stable old length of 100 and resulting length of 110, preferred capacity is 228: the proportional candidate is 162, while the minimum-increase candidate is 228.

## Uncertainties

The following are **documented_only**:

- The concrete object type, encoding, and meaning of the storage-state word.
- Exact external transfer semantics, particularly the missing explicit prefix count.
- Replacement-byte contents.
- Diagnostic severity, continuation behavior, and metadata interpretation.
- Allocation ownership, release responsibility, and failure behavior.
- Header and terminator initialization on the replacement-storage path.
- Whether dependencies modify the handle, globals, or existing storage.
- The intended semantics of signed-looking overflowing intermediates.
- Validity of extreme addresses, wrapped quantities, or overlapping transfer regions.

Ordinary replacement semantics are inferred intent. They are not grounds for repairing unusual offsets, supplying an absent transfer argument, assuming zero-fill, or assuming conventional allocator and destructor behavior.
