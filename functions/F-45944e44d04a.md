# F-45944e44d04a

## Purpose

F-45944e44d04a performs an initial transfer, then repeatedly removes pending records from a context-owned list and advances a circular position. Depending on a hidden transfer-width selector, each subsequently selected record causes no data transfer, a one-, two-, or four-byte transfer, or a call to an external transfer dependency. Processing ends when the pending-list head is null.

The visible behavior also includes completion accounting, an unsigned high-water update, conditional dependency calls, list maintenance, and final notification.

This is a source-facing contract, not a claim that the apparent two-argument interface is independently callable. Essential state is supplied through unexplained incoming machine state. The initial address calculation is also unresolved at the apparent operand width.

**Established:** the memory accesses, branch structure, and dependency-call order described below are present in the supplied representation.

**Inferred intent:** the context resembles a buffered destination with queued producers or requests.

**Unknown:** the actual public calling convention, object types, synchronization model, dependency contracts, and validity of the reconstructed entry expression.

## Interface

### Explicit arguments and result

The apparent interface has two explicit arguments:

- **First argument:** a signed integer shown as 32 bits. An apparent right shift by 32 produces the initial halfword destination or index.
- **Second argument:** an unsigned 32-bit value. Its initial interpretation depends on the first transfer branch: either the low 16 bits are written directly, or the value is treated as the address of a descriptor.

On the sole visible normal return, the result is the 32-bit value zero. There is no visible nonzero error result.

Normal return requires all preceding memory operations and dependencies to complete and the pending-list head eventually to be observed as null. Faults, dependency non-return, and continued processing are not converted into error results.

### Required incoming state

In addition to the explicit arguments, execution depends on:

- A **context address**.
- A **replacement value**, used in several stores and in circular-position reset.
- A **list-owner address**.
- A **comparison-object address**.
- A **transfer selector**.
- A **wrap limit**.

The representation obtains these from incoming register state without establishing them locally. They are required inputs to the observed behavior, but their relationship to any legitimate external interface is documented_only.

The replacement value must not be assumed to be zero. Likewise, the transfer selector must not be assumed to contain only zero, one, two, or four.

### Preconditions for defined execution

Every executed access requires appropriately readable or writable storage of the indicated width. Pointer chains must remain valid when dereferenced. Target-specific alignment and address-space requirements are not established.

There are no visible bounds checks, null checks for ordinary data pointers, list-cycle checks, or allocation checks.

The entry expression requires separate resolution: a signed 32-bit value shifted right by 32 does not establish an ordinary portable 32-bit result. No assumption about zero, sign extension, a masked shift count, or a hidden wider argument is justified here.

## Behavior

### Initial transfer

The initial transfer does **not** use the same dispatch rules as transfers selected later in the loop.

The unresolved entry expression produces a value used as an address or index. Its comparison with zero controls the first branch:

- If it equals zero, the function attempts a two-byte store of the second argument’s low 16 bits to that address. At face value, this is a write to address zero; the zero comparison is not a protective null check.
- Otherwise, if the transfer selector is four, the function reads the source pointer at descriptor offset 16, reads four bytes from that source, and writes them to the destination base plus four times the initial index.
- Otherwise, it calls **F-2489d48d501c**, supplying the destination base plus the selector multiplied by the initial index, and the word read from descriptor offset 16.

Consequently, an initial nonzero index with selector zero, one, or two reaches F-2489d48d501c. The specialized byte and halfword paths are reached only after a pending record has been selected.

Successful completion of this initial operation leads to completion accounting.

### Completion accounting

Each visit to the accounting phase performs these operations in order:

1. Read the context completion counter at offset 44 and write its incremented value.
2. Read the occupancy-like count at offset 16.
3. Read the high-water value at offset 48.
4. If the high-water value is smaller under an **unsigned 32-bit comparison**, write the count to offset 48.
5. If the sampled count equals one, read the context condition at offset 32. If that field is nonzero, call **F-6ad030b1b8cc**.
6. Read the pending-list head at context offset 20.

The high-water update precedes the special dependency call. The head is read after that call, so dependency modifications to the head or surrounding state can affect the next action.

The count is not incremented in this accounting phase. It is incremented when a pending record is selected, as described below.

### Empty pending list and return

If the head read at offset 20 is null, terminal handling begins:

1. Read the word at list-owner offset 8.
2. If it is nonzero, call **U-01** with that word as the visible argument.
3. If it is zero, read both comparison-object words, at offsets 8 and 12.
   - If those words differ, call U-01 with the word read from comparison-object offset 8.
   - If they match, read the byte at list-owner offset 1.
   - Call U-01 with that byte zero-extended to 32 bits if it is nonzero.
   - Suppress U-01 if that byte is zero.
4. Call **U-02**.
5. Return the 32-bit value zero.

The comparison-object words are not read when the list-owner word is nonzero. The terminal byte is not read when those comparison words differ.

U-02 is unconditional on the visible normal-return path, but its execution still depends on any preceding U-01 call returning.

### Removing and updating a pending record

For a nonnull pending-list head, the function performs the following ordered state transition:

1. Read the selected record’s next pointer at offset 0.
2. Write that pointer to context offset 20.
3. If the next pointer is nonzero, write the address of context offset 20 into the successor record’s offset-4 field.
4. Read the selected record’s flags at offset 28.
5. Clear bit 7 and write the resulting 32-bit word back to offset 28.
6. If the **entire resulting word** is zero:
   - Read the list-owner word at offset 8.
   - Write that word into the selected record’s offset-0 field.
   - Write the selected record’s address to list-owner offset 8.
7. Read the selected record’s field at offset 8.
8. If it is nonzero, call **F-f46257aeeddc**, then overwrite that field with the replacement value.
9. Read the selected record’s offset-16 pointer, then read the descriptor pointer at offset 4 of the referenced intermediate object.
10. Write the replacement value to descriptor offset 4.
11. Increment the context count at offset 16.
12. Increment the context position at offset 12.
13. If the incremented position equals the wrap limit, overwrite the position with the replacement value.
14. Read the context position again for transfer selection.

Only bit 7 is cleared from the flags. Any remaining bit prevents the secondary-list insertion, including bits outside the low byte.

The selected record is removed from the pending list before its conditional dependency call and descriptor processing. There is no visible rollback if a later operation fails.

The descriptor is obtained after F-f46257aeeddc returns. Therefore, the supplied representation does not justify replacing that later pointer traversal with an earlier cached descriptor.

### Transfer for a selected pending record

After record selection and position advancement, the transfer selector controls processing:

- **Zero:** perform no payload transfer and return directly to completion accounting.
- **One:** read the descriptor’s offset-16 source pointer, read one byte through it, and write one byte at destination base plus the current position.
- **Two:** read the descriptor’s offset-16 source pointer, read an unsigned two-byte value through it, and write that value at destination base plus twice the current position.
- **Four:** read the descriptor’s offset-16 source pointer, read four bytes through it, and write them at destination base plus four times the current position.
- **Any other value:** call F-2489d48d501c with destination base plus selector multiplied by current position, and the word read from descriptor offset 16.

Each completed transfer returns to completion accounting. Selector zero still performs all record-removal, descriptor-write, count, position, and completion-accounting operations.

Wrap handling is equality-based. The function does not visibly reduce the position modulo the limit, check whether it exceeds the limit, or guarantee that the replacement value lies within a valid range.

## Side effects

Direct writes can affect:

- Destination payload storage.
- Context offsets 12, 16, 20, 44, and conditionally 48.
- A successor record’s offset-4 backlink.
- The selected record’s flags and, conditionally, offsets 0 and 8.
- The list-owner word at offset 8.
- Descriptor offset 4.

There is no visible allocation or explicit deallocation. Removal from the pending list and possible insertion into the list-owner chain do not establish memory reclamation or ownership transfer.

The intermediate object, descriptor, source pointer, selected record, and destination buffer must remain usable for all subsequent accesses that reach them. No dependency may be presumed to preserve globals, preserve pointed-to storage, or release memory unless its own contract establishes that behavior.

The supplied representation contains no explicit atomic operations, locks, or memory barriers. Synchronization may exist in dependencies or caller preconditions, but is not established here.

Data stores are one, two, or four bytes according to the selected branch. No byte-order conversion is visible; the concrete byte layout follows the target’s native loads and stores.

Count, completion, position, and address arithmetic use values represented as 32-bit words. However, some operations appear signed and others unsigned. The unsigned high-water comparison is explicit; portable signed-overflow behavior and pointer-address wraparound are not established. This contract does not authorize out-of-range arithmetic merely because a machine might wrap it.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Each assumes that the entry ambiguity has been resolved, prior operations complete, and all required storage remains valid.

1. **Unsigned high-water update.** If accounting reads a count of `0x80000000` and a high-water value of `0x7fffffff`, it writes `0x80000000` to the high-water field. A signed comparison would produce the wrong decision.

2. **Selector zero still consumes a record.** With a nonnull pending head and selector zero, the record is removed, flags are updated, the descriptor field is written, and the count and position advance. No payload-source access is required by that transfer branch before accounting resumes.

3. **Clearing the last flag inserts into the secondary chain.** If the selected record’s flags equal `0x00000080`, clearing bit 7 produces zero. The former list-owner word is written into the record’s offset-0 field before the record address is stored in the list owner.

4. **Another flag prevents insertion.** If the flags equal `0x00000180`, the resulting value is `0x00000100`. No secondary-chain insertion occurs on that decision.

5. **A nonzero replacement value changes wrap behavior.** If the old position is six, the wrap limit is seven, and the replacement value is three, the selected transfer uses position three after the increment-and-reset sequence.

6. **Exceeding the limit does not trigger reset.** If the old position is seven and the wrap limit is seven, an otherwise valid increment to eight does not meet the equality condition. No reset occurs at that comparison.

7. **Terminal suppression requires all relevant conditions.** With a null pending head, a zero list-owner word, equal comparison words, and a zero terminal byte, U-01 is suppressed. U-02 is then called before return.

8. **A nonzero list-owner word short-circuits terminal reads.** With a null pending head and list-owner word 12, U-01 receives 12. Neither comparison word nor the terminal byte is read by this terminal branch.

9. **Initial dispatch differs from continuation dispatch.** Conditional on a valid nonzero initial index and selector one, the initial transfer calls F-2489d48d501c. A later selected record with selector one instead uses the direct one-byte transfer path.

## Uncertainties

The following remain **documented_only**:

- The meaning and executable semantics of the entry shift by 32.
- The real calling convention and provenance of the hidden inputs.
- Valid selector values, position ranges, wrap limits, and replacement values.
- Complete structure layouts and aliasing constraints.
- Whether address zero can legitimately accept the initial halfword store.
- Whether counter overflow and address arithmetic are defined by the original execution environment.
- Dependency behavior, including memory mutation, synchronization, ownership, and nonlocal exits.
- Whether list cycles, callbacks, or concurrent mutation can prevent termination.
- Behavior after invalid accesses, malformed pointer chains, arithmetic overflow, or dependency failure.

Names such as “count,” “position,” and “secondary chain” describe observed use rather than verified domain semantics.
