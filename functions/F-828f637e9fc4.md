# F-828f637e9fc4

## Purpose

F-828f637e9fc4 conditionally copies one four-byte value from a state-associated table into caller-provided storage. It returns a four-byte status indicating whether the copy occurred.

The selection is restricted to the table position immediately preceding a stored count or position value. The function does not search backward, inspect alternative entries, consume the selected entry, or update the stored position.

The established behavior distinguishes two ordinary results:

- **0:** the selected value was copied to the output destination.
- **3:** a gating condition prevented the copy.

Interpreting the state as an enabled object with a stack-like or history-like collection is plausible intent, not an established semantic requirement. In particular, the supplied evidence does not establish that a successful read removes an entry.

## Interface

### Inputs

The function receives two address-like arguments:

1. **State base:** the base address of a structured memory region.
2. **Output destination:** an address at which one four-byte value can be stored on success.

The supplied representation uses a 32-bit address model: the state base is represented through a four-byte integer, and addresses stored within the state occupy four bytes. The contract does not establish portability to a wider address model.

The function returns a four-byte status value. Both observed return constants, 0 and 3, have the same interpretation whether that return value is considered signed or unsigned.

### State layout

The following offsets are relative to the state base. Names describe roles within this contract, not established application-level meanings.

| Offset | Width | Contract role |
|---|---:|---|
| `0x10` | 4 bytes | Primary gate; zero prevents further processing |
| `0xE0` | 4 bytes | First eligibility field; compared with signed −1 |
| `0xE4` | 4 bytes | Second eligibility field; compared with signed −1 |
| `0x224` | 4 bytes | Position value used to select the preceding entry |

The selected marker and value use the same entry index. Each table has a four-byte stride. A marker is tested only for zero versus nonzero. A value is copied as an uninterpreted four-byte quantity.

The −1 eligibility sentinel is the 32-bit all-ones representation. Other eligibility-field values, including zero and other negative values, qualify as “not −1.”

Memory need only be accessible along the branch actually taken. For example, a zero primary gate avoids all table accesses and any output access.

For ordinary completion:

- Each state field reached by the decision sequence must be readable.
- If table selection is reached, the selected marker location must be readable.
- If the selected marker is nonzero, the selected value location must be readable and the output destination must be writable.
- Address calculations must identify valid locations under the actual execution model.

There are no explicit null checks, bounds checks, or alignment checks. The function does not provide an ordinary error result for invalid memory.

## Behavior

### Eligibility and early rejection

The function first reads the four-byte primary gate at offset `0x10`.

If it is zero, the function returns 3 immediately. It does not read either eligibility field, either table address, the position value, or the output destination.

If the primary gate is nonzero, the function reads the eligibility fields at offsets `0xE0` and `0xE4`, in that order. Both fields are read before eligibility determines whether processing continues.

Processing continues if **at least one** of the two fields differs from −1. It does not require both to differ from −1.

If both fields equal −1, the function returns 3. No position or table access is made.

### Position-based selection

Once eligibility is established, the function reads the four-byte position value at offset `0x224`.

A zero position causes return status 3 without accessing either table.

A nonzero position is reduced by one to obtain the selected entry index. The selected entry displacement is that index multiplied by four. The function uses this displacement for both tables.

For an ordinary positive position:

- Position 1 selects entry 0.
- Position 2 selects entry 1.
- Position \(n\) selects entry \(n-1\).

The position is not checked for positivity. A negative nonzero position reaches the same selection logic. Where the arithmetic and memory access remain valid, this can select memory before the table base. Such a position is not automatically rejected with status 3.

There is also no check that a positive position fits either table’s allocated extent. A valid allocation and a meaningful position are caller or surrounding-state responsibilities.

### Marker test and value transfer

After selecting an index, the function reads the marker-table address from offset `0x228`, then reads the four-byte marker at the selected displacement from that address.

If the selected marker is zero, the function returns 3. It does not read the value-table address or access the output destination.

If the selected marker is nonzero, the function reads the value-table address from offset `0x22C`, then reads the selected four-byte value from that table. It writes that value to the output destination and returns 0.

The marker is not copied to the output. The two eligibility fields are not copied to the output. A selected value of zero is still a successful result: success depends on the marker, not the value.

### Arithmetic boundaries

The supplied representation uses signed 32-bit quantities for the position and selected index. Selection involves subtracting one and forming a four-byte-scaled displacement.

The ordinary positive-position relationship above is established where those operations and the resulting addresses are valid. The supplied evidence does not establish the execution semantics of signed overflow, address wraparound, or an out-of-range pointer conversion. This contract therefore does not promise modular wraparound or a particular fault for extreme positions.

Notably, the most negative signed 32-bit position would require an out-of-range signed result when reduced by one. Other large-magnitude positions can make the four-byte scaling exceed the signed 32-bit range. These cases are **documented_only**, not defined successful selection cases.

## Side effects

### Observable memory-access order

On a successful, nonfaulting call, the source-level access sequence is:

1. Read the primary gate.
2. Read the first eligibility field.
3. Read the second eligibility field.
4. Read the position.
5. Read the marker-table address.
6. Read the selected marker.
7. Read the value-table address.
8. Read the selected value.
9. Write the four-byte value to the output destination.
10. Return 0.

A rejecting branch stops at its corresponding decision point and returns 3.

This describes the supplied static representation. It is not a guarantee about processor bus transactions, compiler treatment of nonvolatile memory, or synchronization with concurrent writers.

### Writes and aliasing

The only explicit memory write is the successful four-byte output store. Ordinary status-3 returns leave the output untouched.

The function contains no explicit update to the primary gate, eligibility fields, position, table addresses, selected marker, or selected value. However, the output destination is not checked for overlap with any of those locations. If it aliases state or table storage, the successful output store can modify that storage.

All reads needed to obtain the selected value precede the output store in the supplied representation. Thus, aliasing does not introduce a second lookup after the write.

### Ownership and lifetime

No allocation, deallocation, ownership transfer, or resource-release operation is present. The function copies four bytes; it does not establish what those bytes represent or who owns any resource they may identify.

The evidence does not establish reference counting, retention of the output destination, or any lifetime extension. Caller-provided memory must remain usable for the accesses performed during the call.

### Errors and concurrency

Status 3 represents a failed gate or an absent marker, not a general memory-error report.

There is no explicit exception handling, recovery, locking, or atomic snapshot mechanism. Fault behavior and behavior under concurrent mutation are not established. In particular, there is no guarantee that separately read state fields and table contents belong to one consistent logical state.

- Any nonzero primary-gate value passes the first check.
- Any nonzero selected marker passes the marker check.

- A negative nonzero position is not rejected merely for being negative. Its result depends on valid arithmetic and the addressed memory.
- Invalid table storage is not converted into status 3 merely because the function has a failure status.
