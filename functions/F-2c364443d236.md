# F-2c364443d236

## Purpose

F-2c364443d236 processes a 32-bit item address using either an explicit descriptor or an implicitly selected context.

Two paths are established by the supplied static representation:

- **Descriptor match:** find the first matching descriptor entry, modify its associated bit in the descriptor, and return without accessing item metadata.
- **Metadata processing:** for a nonzero item address not handled by a descriptor match, validate preceding metadata, update context accounting, and invoke downstream dependencies.

**Inferred intent:** descriptor matches release a descriptor-managed slot; metadata processing releases a separately managed allocation. Actual memory release, ownership transfer, and synchronization are not established by this function alone.

## Interface

The function accepts two inputs and returns no value.

| Input | Representation | Meaning |
|---|---|---|
| Descriptor address | Nullable pointer to 32-bit words | Selects explicit descriptor handling when nonnull; implicit context selection otherwise |
| Item address | 32-bit signed integer representation | Compared against descriptor entries and, when nonzero and metadata processing is reached, used to derive memory addresses |

The item is compared using its complete 32-bit representation. A descriptor match does not require the item address or its preceding metadata to be readable.

### Descriptor layout

Offsets are byte offsets from the descriptor address.

| Offset | Width | Observed role |
|---|---:|---|
| `0x00` | 32 bits | Context address; zero causes immediate return |
| `0x0C + 4 × index` | 32 bits | Entry compared with the item |
| `0x14` | 32 bits | Bit field updated on a match |
| `0x18` | 32 bits | Search count, interpreted as unsigned |

The entry region is not established as disjoint from the other fields. Entry index 2 occupies the bit-field word at `0x14`; entry index 3 occupies the count word at `0x18`. No maximum count or intended entry capacity is provided.

### Metadata layout

Offsets are relative to the item address.

| Offset | Width | Observed role |
|---|---:|---|
| `−8` | 32 bits, unsigned | Validation header and source of accounting amounts |
| `−4` | 16 bits, unsigned | First accounting index |
| `−2` | 16 bits, unsigned | Second accounting index |

The downstream metadata address is the item address minus eight, not the item address itself.

### Preconditions

Normal completion requires valid storage for every access actually reached, valid address calculations, and satisfaction of the called dependencies’ requirements.

Metadata processing additionally requires readable preceding metadata and writable context accounting locations selected by both metadata indices and the dependency-provided index. No bounds, alignment, allocation ownership, or disjointness checks are present.

The representation uses 32-bit integers and address-bearing values. Behavior on a different address model is not established. Some address calculations involve signed arithmetic; the valid-address precondition does not establish behavior for signed-overflow cases.

## Behavior

### Context selection and descriptor handling

**Null descriptor**

Call **F-2fd8826557a4** without arguments. After it returns, read the selected context value through the global context location.

The context is selected after the dependency call. The dependency may change that global state; preservation is not assumed.

There is no explicit zero-context check on this branch. A zero item ends processing after the global read. A nonzero item proceeds toward metadata processing even if the selected context value is zero.

**Nonnull descriptor**

Read and retain the context value at descriptor offset `0x00`.

- If it is zero, return immediately.
- Otherwise, search entries in increasing index order, starting at zero.

The search index is unsigned and 32 bits wide. Each loop condition compares it with the count at offset `0x18`, interpreted as unsigned. The count expression is evaluated for successive search conditions rather than explicitly captured once. This does not establish synchronization or guaranteed observation of concurrent writes.

A count with its high bit set is a large unsigned bound, not a negative bound that suppresses the search.

At each visited index, compare the entry with the full item value. On the first match:

1. Use the low eight bits of the entry index as the shift count.
2. Form the matching-bit mask by shifting a signed, 32-bit value of one.
3. Read the descriptor bit field, clear the selected bit, and store the result.
4. Return immediately.

For shift counts **0 through 30**, the selected-bit result is established: that bit is cleared and other bits are preserved.

For shift count **31**, the positive result is not representable as a signed 32-bit integer, so the supplied representation does not establish a defined result. Counts **32 through 255** exceed the operand width and likewise have no established result. There is no target-instruction evidence permitting these cases to be interpreted as unsigned shifting or shifting modulo 32.

Only the first matching entry is handled. Neither the entry nor the count is explicitly cleared. Because of layout overlap, however, writing the bit field also changes the storage viewed as entry index 2.

A zero item can match a descriptor entry and cause this write. The general zero-item check occurs only after descriptor handling.

If no entry matches, continue using the context value retained before the search.

### Zero-item return

After implicit context selection or an unsuccessful descriptor search, a zero item causes return.

No metadata is read and no accounting dependency is called on this path. Earlier actions still occur: implicit context preparation and the global read, or explicit descriptor reads and search comparisons.

### Header validation

For a nonzero item that reaches metadata processing, read the unsigned 32-bit header at item offset `−8`.

Validation rejects:

- A zero first header read.
- A nonzero first header read followed by a second header read whose least significant bit is set.

The second read occurs only when the first read is nonzero. The representation therefore does not establish validation against one stable header snapshot.

On rejection, call **F-a817d8d58c10** without arguments. The supplied representation identifies this dependency as nonreturning. No accounting write and no call to **F-c0fc6d033caa** precedes rejection.

With a stable header, validation accepts exactly the nonzero even values. It does not require a positive accounting amount and does not reject other header bits.

If the header changes between validation reads, a nonzero first read followed by a zero second read passes the displayed condition. There is no additional zero check on that second read.

### Accounting preparation and amount updates

After successful validation, call **F-c0fc6d033caa** with the retained context value.

No preservation of metadata, accounting storage, or globals is assumed across this call. The function does not reselect its context afterward.

After the dependency returns:

1. Read the first unsigned 16-bit index at item offset `−4` and derive its context-relative position.
2. Read the header again and retain its value masked with `0x3FFFFFFC`.
3. Subtract the retained amount from the 32-bit field at context offset `0x224 + 4 × first index`.
4. Subtract that same amount from the field at context offset `0x30C`.
5. Read the second unsigned 16-bit index at item offset `−2` and derive its context-relative position.
6. Subtract the retained amount from the field at context offset `0x0E0 + 4 × second index`.
7. Subtract that same amount from the field at context offset `0x220`.

The mask clears the top two and bottom two header bits. The amount is unsigned, ranges from zero through `0x3FFFFFFC`, and is divisible by four.

Each metadata index ranges from 0 through 65,535. Four times either index ranges from zero through 262,140. No check compares either index with an actual accounting-table capacity.

### Count updates and final amount update

Next, call **F-09dcb55e8e0a** without arguments. Its returned signed 32-bit value selects another context-relative field.

Then perform these updates in order:

1. Decrement the signed 32-bit field at context offset `0x310 + 4 × returned index`.
2. Decrement the signed 32-bit field at context offset `0x390`.
3. Read the header again, mask this fresh value with `0x3FFFFFFC`, and subtract that unsigned amount from the 32-bit field at context offset `0x08`.

The last amount is not necessarily the retained amount used for the first four amount subtractions. **F-09dcb55e8e0a**, intervening writes, or other mutations may change the header. There is no revalidation before the last subtraction.

### Arithmetic guarantees and limits

All **five amount subtractions** have an unsigned 32-bit operand. The field’s existing 32-bit value is converted to unsigned for subtraction, and the result is stored as 32 bits. These operations are established modulo \(2^{32}\), including underflow.

For example, subtracting 36 from a field containing 4 stores `0xFFFFFFE0`. This arithmetic result is established even though whether such accounting is meaningful remains unknown.

The **two count decrements** instead operate on signed 32-bit values. Decrementing the minimum signed value is not established as wrapping. Signed overflow in dependency-index multiplication or other signed address arithmetic is likewise not assigned a wrapping interpretation.

These arithmetic guarantees do not make an invalid memory access valid.

### Terminal calls

After the final accounting update:

1. Call **F-cc6c9b4a0f68** with the retained context value and the metadata address.
2. If that call returns, call **F-e586bff64fb7** with the retained context value.
3. Return if the latter call returns.

No returned value from these calls is used. This function performs no explicit metadata access after calling **F-cc6c9b4a0f68**.

## Side effects

### Direct reads and writes

Depending on the path, the function reads descriptor fields, the implicit global context location, item metadata, and context accounting fields.

A descriptor match performs one bit-field update when the shift has defined semantics. Metadata processing performs seven ordered accounting updates:

- Four subtractions using one retained unsigned amount.
- Two signed decrements.
- One subtraction using a fresh unsigned amount.

These are seven operations, not necessarily seven distinct locations. Metadata-derived indices may select other listed accounting fields. Later operations use the values present when reached, not an initial snapshot.

For example, first index 59 selects offset `0x310`, which is also the count field selected by a dependency result of zero. The amount subtraction occurs before that count decrement.

No disjointness check prevents descriptor, context, and metadata storage from overlapping. Earlier writes may therefore affect later reads where valid aliasing permits it. The representation establishes the ordering between the listed operations, but not an additional ordering between independent operand reads within a single arithmetic expression.

### Ownership and lifecycle

**Established:** the metadata address is passed to **F-cc6c9b4a0f68** only after accounting. The descriptor-match path does not call this dependency.

**Inferred intent:** the two paths implement different forms of allocation release or availability bookkeeping.

**Unknown:** whether dependencies free storage, retain addresses, transfer ownership, or invalidate the item. No safe caller post-return access rule can be derived from this function alone.

### Failure and interruption

Rejected headers enter the designated nonreturning dependency. Its exact termination mechanism is unknown.

Invalid addresses, unsuitable indices, arithmetic outside defined cases, dependency failures, and concurrent mutation have no explicit recovery path here. Accounting updates are sequential; no rollback is provided if processing stops partway through.

## Acceptance examples

These are conditional static criteria, not executed tests. Except where stated otherwise, addresses and calculations are valid, dependencies return normally, values remain stable, and no unmentioned mutation occurs.

### Explicit zero context

Given a nonnull descriptor whose context word is zero, return without searching entries or reading metadata, regardless of the item value.

### First matching entry

Given a nonnull descriptor with a nonzero context, count two, and the first match at index 1, clear bit 1 at offset `0x14` and return without metadata processing.

If both entries match, act only on index 0.

### Matching zero item

Given a zero item, a nonnull descriptor with a nonzero context, a positive search bound that visits index 0, and a zero entry at that index, clear bit 0 and return.

Neither a zero explicit context nor an empty search satisfies these reachability conditions.

### Implicit context and zero item

Given a null descriptor and zero item, call **F-2fd8826557a4**, then read the global context value, then return without accessing metadata or accounting fields.

### Invalid header reached

Given a nonzero item that reaches metadata validation—through implicit selection or through a nonzero explicit context with no descriptor match—a stable zero or odd header causes **F-a817d8d58c10** to be called before accounting preparation.

A zero explicit context or an earlier descriptor match bypasses rejection even if the item’s preceding storage contains an invalid header.

### Stable successful accounting

Given that metadata processing is reached, a stable header of `0x00000024`, first index 1, second index 2, and dependency result zero:

- Subtract 36 at offsets `0x228`, `0x30C`, `0x0E8`, and `0x220`, in order.
- Decrement offsets `0x310` and `0x390`, in order.
- Subtract 36 at offset `0x08`.
- Call **F-cc6c9b4a0f68**, then **F-e586bff64fb7**.

Assume distinct valid fields and representable signed decrements. An amount field initially containing 4 becomes `0xFFFFFFE0`; unsigned underflow does not introduce arithmetic uncertainty.

### Accepted zero amount

Given a nonzero item that reaches metadata processing and a stable header of `0x00000002`, validation succeeds and the masked amount is zero.

The amount-subtraction operations still occur, both count decrements occur, and the terminal dependencies are reached, subject to valid accesses and representable signed arithmetic. A descriptor match or zero explicit context would instead bypass this behavior.

### Changed final amount

Given metadata processing with retained amount 36, if **F-09dcb55e8e0a** changes the header to `0x00000040`, the first four amount subtractions use 36 and the final subtraction uses 64. The changed header is not revalidated.

### Shift boundary

For a reachable first match at index 30, bit 30 is cleared. For a reachable first match at index 31, the supplied representation does not establish the resulting bit-field value or normal completion. No modulo-32 shift rule is assumed.
