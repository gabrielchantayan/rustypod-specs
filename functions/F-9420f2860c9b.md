# F-9420f2860c9b

## Purpose

F-9420f2860c9b coordinates a size-dependent update of a descriptor associated with its first argument, using a temporary four-word argument record and several opaque dependencies.

The established behavior is:

- Capture a descriptor address through the first argument.
- Obtain an initial size-like result and derive a target one greater than that result.
- Pass the four arguments to a preparation dependency.
- Query the descriptor again and select growth, shrinkage, or neither.
- Clean up the temporary argument record.
- Invoke a final dependency with the original first argument.

The apparent intent is to prepare a value, increase a collection by one element, and then finalize the enclosing object. That interpretation is **inferred intent**, not an established collection API contract. The preparation dependency occurs between size queries, so the later descriptor state need not match the initial state.

A significant established detail is that the shrink path contains a transfer loop whose initial cursor already equals its stopping value. That loop performs no iterations. The contract therefore does not include the transfers that a conventional collection-erasure implementation might perform.

## Behavior

### 1. Capture the parent and prepare the argument record

The function first reads the parent address from the first argument’s field at offset `0x04`. It derives the descriptor address by adding `0x38` to that captured parent.

It then initializes the 16-byte temporary record with all four original arguments.

These captures matter if dependencies subsequently change the original object:

- The function does not reread the first argument’s parent field.
- Later descriptor operations continue to use the captured parent and descriptor addresses.
- The final dependency receives the original first argument, not a possibly modified first word from the temporary record.

### 2. Establish a target before preparation

The function calls F-f40dec111e7a with the descriptor address.

It derives the target from that first result by adding one. The target is retained across subsequent dependency calls; it is not recomputed from a later size query.

The function then calls F-8e6b333a43ea with the temporary record’s address and retains its 32-bit result for possible use in growth.

There is no visible assumption check that this preparation operation leaves the descriptor, temporary record, or other state unchanged.

### 3. Choose the growth path

After preparation returns, the function calls F-f40dec111e7a again with the same captured descriptor address.

If this result is unsigned-less-than the retained target, the growth path executes:

1. Read the 32-bit field at captured-parent offset `0x3C`.
2. Call F-f40dec111e7a a third time.
3. Calculate the unsigned 32-bit difference between the target and this third result.
4. Call F-ebbb7a35dd31 with, in order:
   - The descriptor address.
   - The saved `0x3C` field value.
   - The calculated difference.
   - The result previously returned by F-8e6b333a43ea.

The growth decision uses the second size-query result, but the requested difference uses the third. Consequently, the difference is not guaranteed to be positive or small. If the third result equals the target, the dependency receives zero. If it exceeds the target, the unsigned subtraction wraps.

The end-like field is captured **before** the third query. If that query changes the field, the growth dependency still receives the earlier saved value.

The function does not inspect a result from F-ebbb7a35dd31.

### 4. Choose the shrink path

If the second query result is not below the target, the function makes a third size query.

The shrink path is selected only when the target is unsigned-less-than this third result. If that comparison is false, neither growth nor shrinkage occurs.

Thus, equality in the second query does not itself settle the operation. The third query can still select shrinkage.

On entering shrinkage, the function:

1. Reads the end-like field at captured-parent offset `0x3C`.
2. Reads the descriptor’s start-address word.
3. Forms a target address by adding 16 times the retained target to that start address.
4. Reads the start-address word again and compares it with the saved end-like value.

If the latter start value equals the saved end-like value, the shrink body is skipped. There is no explicit descriptor write in that case.

### 5. Execute shrink cleanup without transfers

If the start/end comparison is unequal, the shrink body proceeds.

The apparent transfer loop does not execute: its source cursor is initialized to the saved end address, and its continuation condition requires that cursor to differ from that same saved end address. As a result:

- F-46f0b3cb316e is not called.
- No transfer is performed by that loop.
- The cleanup cursor remains at the calculated target address.

The function next rereads the end-like field and saves that value as a cleanup stopping address.

Starting at the calculated target address, it calls F-ad0d67a8ef2c once per 16-byte position until the cursor equals that saved stopping address. The stopping address is not refreshed between cleanup calls.

This is equality-based traversal, not a checked bounded traversal. The function does not verify that the target address precedes the stopping address, belongs to the same allocation, or differs from it by a multiple of 16. Under modular 32-bit address stepping, a stopping address in a different residue class modulo 16 is never reached. Even when reachable, traversal may cross invalid memory.

After cleanup traversal finishes, the function reads the end-like field again and writes back a shortened value. The amount subtracted is:

- The saved end address from entry to shrinkage,
- minus the calculated target address,
- with the low four bits cleared.

The update uses the field’s value **at the time of the final read**, not necessarily either previously saved end value. Cleanup dependencies may have changed it.

For a stable, consistent descriptor with a nonnegative, 16-byte-aligned distance between target and old end, this update places the end at the target address. That familiar truncation outcome is conditional; it is not guaranteed for arbitrary descriptor contents or dependency effects.

### 6. Perform common completion calls

After any normally returning branch, the function calls:

1. F-ad0d67a8ef2c with the temporary argument record’s address.
2. F-984e54cba569 with the original first argument.

The temporary-record cleanup therefore precedes finalization.

There is no visible error branch, retry, rollback, or status propagation. If an earlier dependency does not return normally, or shrink traversal does not finish, these common completion calls are not established to occur.

## Side effects

### Direct memory effects

The function directly:

- Initializes its local 16-byte argument record.
- Potentially writes the captured parent’s field at offset `0x3C` after shrink cleanup.

It does not visibly rewrite the first argument’s parent field or the descriptor’s start-address word.

Other writes may occur inside dependencies. Their absence cannot be assumed.

### Observable ordering

The principal call order is:

1. Initial size query.
2. Preparation using the temporary record.
3. Second size query.
4. Either a third query followed by growth, or a third query potentially followed by shrink cleanup.
5. Temporary-record cleanup.
6. Finalization with the original first argument.

On the shrink path, per-position cleanup calls precede the explicit end-field write. The temporary record is cleaned only after that write completes.

### Ownership and lifetime

The temporary record is local to this invocation. Passing its address does not establish permission for a dependency to retain and later dereference that address.

The function itself performs no visible allocation or direct release of heap memory. Although F-ad0d67a8ef2c is used in cleanup positions, its ownership effects are unknown. It cannot be assumed to free memory, preserve descriptor fields, or leave surrounding objects alive.

Likewise, the preparation result is forwarded to growth but receives no separate visible cleanup. Whether that is a borrowed handle, an owning value, an address, or an encoded scalar is unknown.

If any dependency invalidates the captured parent or descriptor, later accesses may become invalid. The caller’s required ownership discipline cannot be fully specified without those dependency contracts.

## Acceptance examples

These examples are conditional observations, not reports of executed tests.

### Stable size selects growth by one

Suppose all three size queries return `5`, preparation returns normally, and the end-like field remains stable.

The target is `6`. The second result selects growth, and the third result produces a difference of `1`. F-ebbb7a35dd31 receives that difference and the end-like field captured before the third query. Temporary-record cleanup and finalization follow if growth returns normally.

### Preparation changes the size to the target

Suppose the first query returns `5`, while both later queries return `6`.

The target remains `6`. Growth is not selected, and shrinkage is not selected. No growth call, per-position cleanup, or explicit end-field write occurs. Common completion still occurs.

### Third query changes the growth amount

Suppose the first query returns `5`, the second returns `4`, and the third returns `6`.

The second result selects growth, but the calculated difference is zero. F-ebbb7a35dd31 is still called.

If the third result is instead `7`, the difference is `0xFFFFFFFF` under 32-bit unsigned arithmetic. No local validation rejects that argument.

### Stable aligned shrinkage

Suppose the first result is `2`, the second and third results are `5`, and the descriptor remains stable with five contiguous 16-byte positions beginning at address \(B\). Its end-like value is \(B + 80\).

The target is `3`, and the target address is \(B + 48\). Assuming cleanup preserves the descriptor and returns normally:

- No transfer dependency is called.
- Cleanup receives \(B + 48\), then \(B + 64\).
- The explicit end-field write stores \(B + 48\).
- Temporary-record cleanup and finalization follow.

### Empty-address comparison suppresses shrink work

Suppose query results select shrinkage, but the directly read start address equals the saved end address.

The shrink body is skipped despite the query results. No per-position cleanup or explicit end-field write occurs.

### Cleanup changes the end field

Suppose shrink cleanup finishes, but a cleanup call changes the end-like field.

The final subtraction applies to the newly read field value. It is not guaranteed to restore or truncate to the previously calculated target.

No corrective interpretation is applied to that loop. Acceptance is based on the represented behavior, not on presumed collection semantics.
