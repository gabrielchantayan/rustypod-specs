# F-04d514823e0f

## Purpose

F-04d514823e0f attempts to obtain a glyph name from CFF-related state and place a bounded, zero-terminated representation at a caller-supplied destination.

Its two explicit return values distinguish failure of an initial service lookup from normal completion of the remaining operations:

- **2:** The service lookup returned zero, followed by four diagnostic calls.
- **0:** The service lookup returned nonzero and the selected subsequent operations completed normally.

A return value of zero does not establish that a name was obtained or that the destination was modified. A zero name result skips output production. A zero destination capacity also skips output production, but does not skip name resolution or the final cleanup call.

The glyph-name interpretation is supported by diagnostic labels and the operation sequence. The precise service, resolver, and cleanup semantics are not independently established.

## Interface

### Arguments and representation

The supplied representation uses four 32-bit arguments:

| Argument | Interpretation established by local use |
|---|---|
| Object address | Address used to read associated state and arguments for dependencies. |
| Glyph index | Signed 32-bit value used to select a two-byte table entry. |
| Destination address | Address passed to the initial service lookup and later used for optional output. |
| Destination capacity | Unsigned 32-bit value passed twice to the initial lookup and used to bound the selected copy count. |

Address-bearing values occupy 32 bits in the supplied representation. This does not establish behavior on another address width.

There is no local validation of the object address, destination address, glyph index, or reachable storage. Capacity zero prevents the later copy call and explicit terminator write, but the destination address is still passed to the service lookup.

### Return value

The return value is 32 bits.

| Value | Condition for an ordinary return |
|---|---|
| 2 | The service lookup returns zero and all four diagnostic calls return normally. |
| 0 | The service lookup returns nonzero and all selected dependency calls and memory accesses complete normally. |

No visible mechanism converts invalid memory accesses, dependency failures, exceptions, or nonlocal transfers into a defined return value.

## Behavior

### Initial reads and captured state

Before the first dependency call, the function performs these reads in order:

1. Read the associated-state address from object offset 0x28C.
2. Read the cleanup argument from object offset 0x64.
3. Read the service-lookup argument from object offset 0x60.

The first two values are retained for later use. If the service lookup subsequently changes those object fields, the function does not reload them.

Capturing an address does not preserve the memory it references. A dependency could change or invalidate the captured associated state; no preservation guarantee is available.

### Service lookup

F-c79a29304dfd receives five arguments, in this order:

1. The value read from object offset 0x60.
2. A fixed token associated with the PostScript character-map service.
3. The destination address.
4. The unsigned destination capacity.
5. The same unsigned destination capacity again.

Neither capacity argument is reduced to reserve a terminator.

The result is tested only for zero versus nonzero. A nonzero result is not subsequently used as the name pointer, passed to the resolver, or dereferenced locally.

Because this dependency receives the destination address and capacity, skipping the later copy path does not establish that the destination remains unchanged.

### Zero service result

If F-c79a29304dfd returns zero, F-4457a9a44a68 is called four times, in fixed order, with four fixed diagnostic fragments.

The available labels associate the fragments with the glyph-name operation, inability to obtain a CFF glyph name, and absence of the PSNames module. They do not establish complete literal text, separators, rendering, or output destination.

After all four calls return, the function returns 2.

On this branch, the function does not locally:

- Read the associated-state table field at offset 0x488.
- Read a table entry.
- Invoke the name resolver.
- Query a name length.
- Invoke the external copy operation.
- Write an output terminator.
- Invoke final cleanup.

These exclusions do not constrain effects performed inside the service or diagnostic dependencies.

### Nonzero service result and name resolution

After a nonzero service result, the function reads the table address from offset 0x488 of the previously captured associated-state address.

This table-address read occurs after the lookup. A lookup mutation to that field can therefore affect table selection even though replacing the object’s associated-state field would not change the already captured address.

The function then reads a two-byte entry at a displacement of twice the signed glyph index from the table address.

There is no visible check for a negative index, an upper bound, table length, or address validity. The supplied representation does not settle overflow behavior for every possible index and address combination. A portable contract must not assign defined wraparound behavior to all such cases.

F-b75751130389 receives:

1. The captured associated-state address plus 0x44.
2. The selected 16-bit entry.

Its result is treated as zero or as an address-like name value.

### Conditional output production

Output production occurs only if both the resolver result and destination capacity are nonzero.

Otherwise, the length query, external copy call, and explicit terminator write are all skipped. Execution continues to cleanup.

On the output-producing path, F-1cb585febd84 receives the resolver result. Its returned value is interpreted as an unsigned 32-bit length.

Let **L** denote that reported length, **C** the nonzero capacity, and **N** the selected copy count:

- If L is less than C, N is L.
- If L is greater than or equal to C, N is C − 1.

Consequently, N is always at most C − 1 on this path. The subtraction cannot underflow because C is already known to be nonzero.

An external dependency then receives the destination address, resolver result, and N, in that order. This call occurs even when N is zero.

After that dependency returns, the function directly writes one zero byte at destination plus N. The terminator is therefore written after the external operation and before cleanup.

Under ordinary byte-copy semantics, these operations copy N source bytes and append a zero byte. Interpreting the result as a correctly truncated name additionally requires the reported length to describe the intended source bytes and the source to remain valid throughout the operation.

No local handling preserves character boundaries or establishes an encoding.

### Destination storage requirements

For the direct terminator write alone, the byte at destination plus N must be writable.

Under ordinary byte-copy semantics, the external copy and terminator together require **N + 1 writable destination bytes**, starting at the destination, with valid address arithmetic. They do **not** necessarily require C writable bytes.

For example, a reported length of 3 and capacity of 100 select N = 3. Ordinary copying and termination then access four destination bytes, not 100.

Writable storage covering the entire capacity is a sufficient assumption for these destination accesses, provided the address range is valid. It is not a source-established mandatory precondition when the selected count is smaller.

This access requirement does not settle the requirements of the dependencies. In particular:

- The initial lookup receives the destination and the full capacity.
- The external operation’s exact memory-access contract is unavailable.
- Other dependencies might reach destination storage through aliases or global state.

Any additional storage requirements imposed by those dependencies remain unknown.

### Cleanup and completion

Every normally completing path after a nonzero service result invokes F-bf7242c98d06 with:

1. The value captured from object offset 0x64 before the service lookup.
2. The resolver result.

The second argument may be zero. Cleanup is also called when capacity is zero.

If output production occurred, cleanup follows both the external copy call and the explicit terminator write. Its return value is ignored, and the function returns 0.

The call placement is consistent with releasing a temporary name, but it does not establish ownership, deallocation, allocator identity, or zero-argument safety.

## Side effects

### Local memory operations

The only explicit local write is the single-byte zero terminator. The external copy operation may perform additional destination writes according to its own contract.

No explicit local write to the object, associated state, or entry table appears.

The function reads the object fields before service lookup, but reads the table address and selected entry only after a nonzero service result. Those timing differences are observable if dependencies mutate reachable state.

### Dependency ordering

The normal call sequences are:

| Selected path | Ordered operations |
|---|---|
| Service unavailable | Service lookup; four diagnostic calls. |
| Service available, no output production | Service lookup; name resolver; cleanup. |
| Service available, output production | Service lookup; name resolver; length query; external copy; direct zero-byte write; cleanup. |

No dependency is assumed to preserve globals, captured references, source bytes, destination bytes, or aliases.

The direct terminator write establishes the value written at that moment. It does not guarantee the same final buffer contents after cleanup if cleanup can affect overlapping storage.

### Safety and ownership

Safe execution requires the specific selected reads and writes to address valid storage, and each dependency’s preconditions to hold. No local recovery is shown for stale references, invalid indices, inaccessible storage, or dependency-level failure.

The resolver result must satisfy the requirements of the length and external copy operations when those operations are selected. The source does not establish whether that result is owned, borrowed, shared, or static.

When output production is skipped, there is no explicit clearing of prior destination contents. Dependency effects remain possible.

## Acceptance examples

These are conditional consequences of static evidence, not runtime observations. Unless an example states otherwise, assume valid selected accesses and normally returning dependencies.

1. **Service unavailable.**  
   If F-c79a29304dfd returns zero, four diagnostic calls occur in order, followed by return value 2. Name resolution and cleanup do not occur. There is no explicit local destination write.

2. **No resolved name.**  
   With a nonzero service result and a zero resolver result, no length query, copy call, or terminator write occurs. Cleanup receives the captured cleanup argument and zero. The function returns 0.

3. **Zero capacity.**  
   With a nonzero service result and capacity zero, table access and name resolution still occur. Output production is skipped, cleanup receives the resolver result, and the function returns 0. This does not prove that an invalid destination is acceptable to the initial lookup.

4. **Capacity one.**  
   With a nonzero name result and capacity one, every possible unsigned reported length selects count zero. The external copy operation is still invoked. If it returns, the first destination byte is set to zero before cleanup.

5. **Short name with much larger capacity.**  
   With reported length 3 and capacity 100, the selected count is 3. Under ordinary byte-copy semantics, three bytes are copied and the fourth is set to zero. These output operations require four writable bytes, not necessarily 100. Whether four bytes also satisfy the service and other dependency contracts is **documented_only**.

6. **Exact fit without terminator space.**  
   With reported length 4 and capacity 4, the selected count is 3. Under ordinary byte-copy semantics, only the first three source bytes are copied, followed by a zero byte.

7. **Empty name.**  
   With a nonzero name result, reported length zero, and positive capacity, the external operation receives count zero. A zero byte is then written at the destination.

8. **Maximum unsigned values.**  
   With both length and capacity equal to 4,294,967,295, the selected count is 4,294,967,294. The arithmetic does not establish that the resulting address range is valid or representable without address-related problems.

9. **Lookup changes captured fields.**  
   If the lookup replaces the object’s associated-state or cleanup field, later operations still use the captured values. If it instead changes the table-address field within the captured state, the later table-address read uses that field’s then-current value.

10. **Cleanup changes output.**  
    If cleanup modifies the destination through an alias, the function still returns 0 after cleanup returns. The earlier terminator write alone does not guarantee the final destination contents.
