# F-e2c9853ba515

## Purpose

F-e2c9853ba515 performs a staged configuration sequence: request high-speed timing, optionally request a bus-width change, optionally update host-side width configuration, perform a reset-related operation, read a device signature, and request interrupt enablement.

The visible returning paths produce a 32-bit result:

- **1:** Every reached stage satisfies the caller’s acceptance conditions.
- **0:** A command, status check, reset-related operation, read, signature check, or interrupt-related operation fails its acceptance condition.

Every explicit failure return is preceded by a diagnostic call, provided that dependency returns normally.

The sequence is not transactional. Failure does not visibly reverse earlier commands or the explicit host-side write.

**Established static evidence:** The call sequence, argument values, memory accesses, masks, branches, and return values described below are visible in the supplied representation.

**Inferred intent:** High-speed timing, bus width, reset, CE-ATA identification, and interrupt enablement are interpretations supported by diagnostic labels and argument patterns. They do not establish complete device-protocol semantics.

## Interface

### Input and result

The sole input is an unsigned 32-bit requested width. Its unsigned comparison with 1 determines whether the optional width-command stage is entered.

| Requested width | Width command | Contribution ORed into command base | Explicit host-side width write |
|---|---|---|---|
| 0 or 1 | Omitted | None | Omitted |
| 4 | Issued | `0x00000100` | Yes, after command acceptance |
| 8 | Issued | `0x00000200` | Yes, after command acceptance |
| Any other unsigned value greater than 1 | Issued | Zero | No |

Unsupported values are not explicitly rejected. For example, 3 and `0xFFFFFFFF` both enter the width-command stage with a zero contribution and can ultimately return 1.

The direct result is always explicitly 0 or 1 on visible returning paths. It does not expose dependency return values, command status, or the extent of partial configuration.

### External state and address selection

The function reads external values representing:

- A command context.
- A device-state base address.
- A high-speed command word.
- A width-command base word.

It retains an initial command context and an initial device-state base before invoking the first command. The first command nevertheless uses **separate external reads** for both its command context and its device-state base.

Consequently:

- The first command’s context need not equal the retained context used by the optional second command.
- The first command’s offset-`0x14` read need not address the same structure as the second command’s offset-`0x14` read.
- The later destination-pointer lookup uses the retained initial device-state base, not a new global base lookup.

The relevant structure accesses are:

| Byte offset | Access and use |
|---|---|
| `0x14` | Read a 32-bit value for the fourth command argument |
| `0x04` | Read a destination pointer, then write one 32-bit value through it |

The first offset-`0x14` access uses the separately loaded base. The optional second offset-`0x14` access and the offset-`0x04` pointer lookup use the retained initial base.

Pointer width, complete structure layout, alignment requirements, and whether the destination is ordinary memory or a hardware register remain undocumented.

### Temporary storage and preconditions

The function supplies dependencies with:

- The address of one 32-bit command-status slot, reused for both command calls.
- A destination address for a read requesting 16 bytes.

The caller does **not** initialize the status slot before either command. It does not clear or otherwise reinitialize that slot between commands. A nonzero command result causes the caller to inspect the slot’s **current value**, regardless of whether that command overwrote it.

For the first command, a meaningful status value depends on initialization or writing not established by the caller. For the second command, the current value can be the value retained from the first command if no intervening write changes it. Fresh-write guarantees are unknown dependency behavior, not requirements enforced by this function.

The read destination begins at storage represented as a 12-byte array. The two inspected signature-byte locations follow at offsets 12 and 13 from that starting address. The requested length is 16 bytes; the representation does not declare a single 16-byte array. The complete backing extent and object-boundary guarantees are therefore **documented_only**. No initialization of the read storage is visible.

Normal, defined execution requires valid addresses and sufficient accessible storage for the operations actually performed. Dependencies must use supplied temporary addresses within their valid lifetimes. The caller does not verify these conditions.

## Behavior

### 1. Request high-speed timing

After retaining the initial command context and device-state base, the function invokes **F-6e46c43c3113** with:

1. A separately read external command context.
2. The external high-speed command word.
3. The address of the status slot.
4. A 32-bit value read at offset `0x14` from a separately read external device-state base.

The result is interpreted only as zero or nonzero:

- **Zero:** Emit the high-speed command-failure diagnostic and return 0. The caller does not inspect the status slot on this path.
- **Nonzero:** Read the current status slot and test mask `0x00000080`.

If that bit is set, emit the high-speed status-rejection diagnostic and return 0. All other status bits are ignored by this acceptance check.

If the dependency returns nonzero without establishing an initialized status value, the supplied representation does not establish a deterministic status-check outcome. It does not justify treating the slot as zero.

No subsequent configuration stage is reached after either explicit high-speed failure.

### 2. Optionally request a width change

Requested widths 0 and 1 skip this stage.

For every unsigned width greater than 1, the function selects a contribution:

- Width 4: `0x00000100`.
- Width 8: `0x00000200`.
- Every other value: zero.

It combines that contribution with the external width-command base using bitwise OR. Existing bits in the base are not cleared. The construction therefore does not guarantee replacement of a clean width field.

The selected small values and their eight-bit shift do not overflow the represented 32-bit command word.

The function invokes **F-6e46c43c3113** with:

1. The retained initial command context.
2. The constructed width-command word.
3. The same status-slot address used by the first command.
4. A fresh 32-bit read at offset `0x14` from the retained initial device-state base.

This fourth argument is not a reuse of the first command’s fourth argument. Its address can differ because the first command used a separate base load; its contents can also differ because the memory may have changed.

The second command is accepted as follows:

- **Zero result:** Emit the width-command failure diagnostic carrying the original unsigned requested width, then return 0 without inspecting status.
- **Nonzero result, current status bit `0x80` set:** Emit the width status-rejection diagnostic and return 0.
- **Nonzero result, current status bit clear:** Continue.

There is no requirement enforced here that the second command produce a fresh status. If it returns nonzero without writing the slot, and nothing else changes that storage, the caller tests the first command’s retained accepted status. In that case the status check passes because the retained value already had bit `0x80` clear.

### 3. Optionally write host-side width configuration

After an accepted width command:

- Width 4 invokes **F-7ef29bbafb84** with the current 32-bit status value.
- Width 8 invokes the same dependency with the current status value.
- Every other width skips both this dependency and the explicit write.

For widths 4 and 8, the returned 32-bit value is transformed by clearing mask `0x0000000C`, then setting:

- `0x00000004` for width 4.
- `0x00000008` for width 8.

All bits outside `0x0000000C` are preserved. Within that mask, exactly the selected pattern remains.

Only **after F-7ef29bbafb84 returns**, the function reads the destination pointer at offset `0x04` of the retained initial device-state base. It writes the transformed 32-bit value through that pointer.

There is no visible failure check on the transformation result, no destination readback, and no verification of the write. The dependency is not known to preserve external globals or the structure’s pointer field. If it changes that field, the subsequent lookup observes the field as it exists then.

### 4. Perform the reset-related operation

The function invokes **F-87a40c3922d5** without explicit arguments.

Its acceptance convention differs from the command dependency:

- **Zero:** Continue.
- **Nonzero:** Emit the reset-sequence failure diagnostic and return 0.

This call follows any explicit host-side width write. Its failure does not trigger a visible rollback.

### 5. Read and validate the signature

After the reset-related dependency returns zero, the function invokes **F-581e46a18fa1** with:

1. Numeric value 0.
2. The temporary read destination.
3. Requested length `0x10`, meaning 16 bytes.

Its 32-bit result is tested only for zero:

- **Zero:** Emit the task-file-read failure diagnostic and return 0.
- **Nonzero:** Inspect the signature.

The caller does not compare the result with 16. It therefore does not establish that the result is a byte count or that a full 16-byte transfer occurred.

The required signature is:

| Offset from read destination | Required byte | Visible interpretation |
|---|---|---|
| 12 | `0xCE` | Signed byte equal to −50 |
| 13 | `0xAA` | Unsigned byte equal to 170 |

The success predicate requires both matches. The first-byte condition can establish failure without requiring the second byte for that predicate. On a mismatch, the diagnostic receives both observed byte values, with the first following the signed-byte interpretation and the second the unsigned-byte interpretation.

After the mismatch diagnostic, return 0. Exact printed formatting is not established.

### 6. Request interrupt enablement

Only a matching signature reaches **F-2ac0bc8c9f68**, called with numeric arguments 6 and 0.

- **Nonzero result:** Return 1.
- **Zero result:** Emit the interrupt-enable failure diagnostic and return 0.

Any nonzero result is sufficient; it need not equal 1.

## Side effects

### Observable ordering

For a path reaching all stages, the visible order is:

1. Retain the initial external command context and device-state base.
2. Obtain the first command’s arguments, including separate context and base reads and the offset-`0x14` value.
3. Invoke the high-speed command; check its result and, when nonzero, current status.
4. If requested width exceeds 1, obtain the width-command arguments using the retained context and retained base.
5. Invoke the width command with the same status slot; check its result and, when nonzero, current status.
6. For width 4 or 8, invoke the transformation dependency, obtain the destination pointer through the retained base, and perform one explicit 32-bit write.
7. Invoke the reset-related dependency.
8. Invoke the read dependency.
9. Check the signature.
10. Invoke the interrupt-related dependency.
11. Return 1 if accepted.

A failure diagnostic and return 0 terminate the sequence at the applicable stage. This ordering does not establish a total evaluation order among independent argument-expression reads within one call.

### Diagnostics and ownership

Each explicit failure path invokes **F-1b7fa166ef25** once. The categories distinguish command failure from status rejection, reset failure, read failure, signature mismatch, and interrupt-enable failure. Width-command failure includes the requested width; signature mismatch includes both observed bytes.

There is no explicit success diagnostic.

No allocation, deallocation, or ownership transfer is visible. Temporary addresses are available during the calls that receive them; the caller does not establish a right to retain them for later use. Dependency effects on memory ownership, globals, output, and hardware remain unknown.

## Acceptance examples

These examples are conditional static consequences, not executed tests. Except where specified otherwise, assume valid storage, normally returning dependencies, reset result zero, a nonzero read supplying `CE AA`, and a nonzero interrupt result.

1. **Width 1 or 0:** If the first command returns nonzero and current status bit `0x80` is clear, return 1. No width command, transformation call, or explicit host-side write occurs.

2. **Width 4:** Both commands are accepted. The second command receives the width base OR `0x100`. If the transformation result is `0xFFFFFFFF`, the explicit write is `0xFFFFFFF7`. Later acceptance conditions are still required.

3. **Width 8:** The second command receives the width base OR `0x200`. A transformation result of zero produces an explicit write of `0x00000008`.

4. **Unsupported width 3:** The second command uses the unchanged width base. No transformation call or explicit host-side width write occurs. Overall return 1 remains possible.

5. **Retained status:** The first command writes `0x00000020` and returns nonzero. The second returns nonzero without changing the slot, and no other write affects it. The second status check accepts `0x00000020`; for width 4 or 8, that same current value is passed to the transformation dependency.

6. **First status never established:** The first command returns nonzero without writing the initially uninitialized slot. No deterministic success or failure outcome is specified from this evidence; assuming a zero status would be unsupported.

7. **Distinct device-state bases:** The retained initial base identifies structure A, but the separate base read used for the first command identifies structure B. The first command’s fourth argument comes from B at offset `0x14`. The optional second command reads A at offset `0x14`, and any later destination-pointer lookup uses A at offset `0x04`.

8. **Second command rejection:** The first command passes. The second writes status containing `0x80` and returns nonzero. Emit the width status-rejection diagnostic and return 0 without a host-side write.

9. **Failure after a write:** Width 8 reaches its explicit write, then reset returns nonzero. Emit the reset diagnostic and return 0. No explicit rollback follows.

10. **Signature mismatch:** A nonzero read supplies `CE AB` or `00 AA`. Emit the signature diagnostic and return 0 without invoking interrupt enablement.

11. **Non-unit results:** A read result other than 16 but nonzero still reaches signature checking. A final dependency result other than 1 but nonzero still yields return 1.
