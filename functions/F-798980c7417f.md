# F-798980c7417f

## Purpose

F-798980c7417f coordinates a conditional update between two caller-supplied objects. It captures two signed 16-bit fields from the second object, asks a dependency to prepare the first object using those values, and performs further dependency calls and field writes only when preparation returns zero.

The established behavior is orchestration, not a proven deep-copy operation. The external operations’ implementations are unavailable. Their names, argument shapes, and placement do not establish whether they copy bytes, replace resources, allocate storage, or perform some other action.

The function returns the preparation dependency’s result. No separate success value is derived from the later operations.

## Behavior

### 1. Capture the source’s two signed fields

The function first reads the source’s two-byte field at `0x16`, then its two-byte field at `0x14`.

Each value is interpreted as signed 16-bit data and retained for later use. In this contract:

- **Count A** means the captured value from `0x16`.
- **Count B** means the captured value from `0x14`.

Each count ranges from −32,768 through 32,767. When passed in a 32-bit integer argument position, each is sign-extended rather than zero-extended.

The counts are captured before any dependency call. Later changes to the source’s corresponding fields do not cause the visible function to recapture them.

### 2. Invoke preparation

F-5fbfabc4db1c receives five arguments, in this positional order:

1. Destination address.
2. Count A, sign-extended to 32 bits.
3. Count B, sign-extended to 32 bits.
4. The fourth input’s four-byte value.
5. The same fourth input’s four-byte value again.

The third input is not substituted for either of the final two arguments.

If preparation returns nonzero, the function immediately returns that value. It does not perform the subsequent external calls, direct destination field writes, or finalization call.

This early return does **not** establish that either object remains unchanged: preparation may itself have side effects.

### 3. Perform the three unconditional post-preparation operations

When preparation returns zero, the following operations occur in order:

1. F-external-01 receives the destination and source four-byte values at `0x18`, in that order.
2. F-external-02 receives:
   - The destination four-byte value at `0x1c`.
   - The source four-byte value at `0x1c`.
   - Count A, sign-extended to 32 bits.
3. F-external-02 receives:
   - The destination four-byte value at `0x20`.
   - The source four-byte value at `0x20`.
   - The represented signed left-shift expression that shifts sign-extended Count B left by one bit.

The four-byte field arguments are read for their respective calls, after preceding calls have returned. They are not all captured before preparation. Consequently, changes made by preparation or an earlier external operation can affect values supplied to a later operation.

The relative evaluation order of the destination and source field reads within one argument list is not established by the supplied representation. The sequence of the calls themselves is established.

For nonnegative Count B, the third argument to the second F-external-02 call is exactly twice Count B, ranging from 0 through 65,534. That range fits a signed 32-bit integer.

For negative Count B, the representation uses a signed left shift of a negative value. Portable C-like semantics do not define that operation. An exact negative-input result requires evidence about the target instructions or applicable execution semantics. This contract does not silently replace that expression with portable multiplication.

No visible branch checks the results of these external operations. If they return normally, execution proceeds.

### 4. Evaluate the optional operation

After the three operations above:

1. Read the destination control byte at `0x10`.
2. If that byte is zero, do not read the source control byte and do not perform the optional operation.
3. If the destination byte is nonzero, read the source control byte at `0x10`.
4. If both observed bytes are nonzero, invoke F-external-01 with the destination and source four-byte values at `0x28`, in that order.

Every nonzero control-byte value enables its corresponding condition; the comparison is not restricted to the value one.

The control bytes are read after the preceding calls, so their initial entry values need not determine this branch. The destination condition uses the byte observed at its designated read; the visible logic does not reread it before the optional call.

When either condition fails, the `0x28` fields are not read by this function.

### 5. Store captured counts and finalize

After the optional operation is completed or skipped, the function performs these direct writes in order:

1. Store Count A as two bytes at destination offset `0x16`.
2. Store Count B as two bytes at destination offset `0x14`.

These are the originally captured values, not new reads from the source.

The function then calls F-eafa9af4344c with the destination address and, on normal return, returns the preparation result, which is zero on this path.

Finalization occurs after both direct writes. Its implementation is unavailable, so the contract does not guarantee that the written values remain unchanged after finalization.

## Side effects

### Direct memory activity

The visible body directly writes only the two destination count fields. Those writes occur only after preparation returns zero and all preceding invoked operations return normally.

Other direct accesses are reads:

- The two initial source count reads always occur.
- The four-byte fields at `0x18`, `0x1c`, and `0x20` are read only after successful preparation.
- The source control byte is read only if the destination control byte is nonzero.
- The `0x28` fields are read only if both control conditions pass.

No direct access is made to the third input.

### Dependency-mediated effects

Dependencies may change object contents, reachable storage, globals, or external state. No preservation guarantees are available. In particular:

- Preparation may modify state even when returning nonzero.
- An earlier external call may affect the field values read for a later call.
- Finalization may change destination state after the direct count writes.
- Absence of a visible return-value check does not establish that a dependency cannot fail.

The visible function contains no allocation, release, or ownership-transfer operation of its own. It also provides no evidence that its dependencies avoid those actions. Ownership, borrowing duration, and resource lifetime remain unspecified.

### Aliasing and partial completion

No visible check requires the destination and source to be distinct or nonoverlapping. Whether aliases are supported depends on the dependencies and memory model.

The two counts are captured before preparation, which preserves their inputs to later calls and stores despite subsequent source-field changes during a normally completing execution. Other relevant fields are read later and may reflect intervening changes.

There is no visible rollback or error-recovery path. If a dependency does not return normally, earlier effects may already have occurred. Invalid direct memory accesses likewise have no visible recovery handling.

## Acceptance examples

These examples describe conditional observations required by the static contract. They are not runtime test results. Unless otherwise stated, all executed accesses are valid and all invoked dependencies return normally.

### Nonzero preparation result

Suppose the captured counts are 7 and 9, and preparation returns −4.

Required observations:

- Preparation receives signed values 7 and 9 and two identical copies of the fourth input.
- No subsequent external operation or finalization is invoked by this function.
- Neither direct destination count write occurs.
- The return value is −4.

Any changes made inside preparation remain outside this function’s rollback guarantees.

### Successful preparation with positive counts

Suppose Count A is 5, Count B is 3, preparation returns zero, and both control bytes are nonzero when read.

Required observations:

- The `0x18` operation occurs first.
- The `0x1c` operation receives integer argument 5.
- The `0x20` operation receives integer argument 6.
- The optional `0x28` operation occurs after the control reads.
- The destination receives 5 at `0x16`, then 3 at `0x14`.
- Finalization is invoked after both stores.
- Normal completion returns zero.

No claim is made about the dependencies’ data transformation or the final post-finalization contents.

### Destination control byte is zero

If the destination control byte is zero when evaluated:

- The source control byte is not read.
- Neither `0x28` field is read.
- The optional operation is skipped.
- The count stores and finalization still occur.

### Source control byte is zero

If the destination control byte is nonzero and the source control byte is zero when read, both control reads occur, but the optional operation and its field reads do not.

### Source counts change during preparation

Suppose the initial captured counts are 8 and 4, and preparation changes the source fields to 12 and 10 before returning zero.

Required observations:

- Later integer arguments still derive from 8 and 4.
- The direct destination stores still write 8 and 4.
- Other field arguments may reflect preparation’s changes because they are read later.

### Integer boundaries

For Count A equal to −32,768, both preparation and the `0x1c` operation receive the negative, sign-extended value rather than 32,768.

For Count B equal to 32,767, the `0x20` operation receives 65,534.

For negative Count B, the exact shifted argument is documented_only pending target-semantic evidence.
