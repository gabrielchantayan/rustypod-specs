# F-a72107f22654

## Purpose

F-a72107f22654 rearranges links among a selected record, the record reached through its offset-12 link, and an enclosing structure.

For a conventional, well-formed binary-tree representation, the observable transformation is a left rotation:

- The selected record’s right child takes its place.
- That child’s left subtree becomes the selected record’s right subtree.
- The selected record becomes the promoted record’s left child.
- The enclosing root link or the former parent’s child link is redirected to the promoted record.
- Corresponding parent links are updated.

This interpretation is inferred from the link pattern. The established behavior is the ordered sequence of four-byte accesses described below. The function does not verify that the records form a tree, that parent and child links agree, or that the selected record has a valid right child.

## Interface

### Inputs

The function accepts two address-bearing arguments:

1. **Container address.** Identifies storage with an address-bearing field at byte offset 16. That field leads to another record whose offset-4 field is compared with the selected record’s address.
2. **Selected-record address.** Identifies the record whose offset-12 link supplies the record to be promoted.

The supplied representation declares both arguments as integer values. Memory operations use four-byte fields for the relevant links. Interpreting these values as addresses is established by their use in memory accesses; the exact machine ABI, pointer type, and address-space rules are not supplied.

### Record layout

The following names describe roles inferred from use, not independently established data types:

| Record role | Byte offset | Width | Observed use |
|---|---:|---:|---|
| Container | 16 | 4 bytes | Address of a root-holder record |
| Root holder | 4 | 4 bytes | Link compared with the selected record and conditionally replaced |
| Selected record | 4 | 4 bytes | Parent-like link |
| Selected record | 12 | 4 bytes | Link initially used to obtain the promoted record; later replaced |
| Promoted record | 4 | 4 bytes | Receives the selected record’s parent-like link |

No field at offset 0 is accessed. No payload, key, balance, color, count, or ownership metadata is explicitly inspected or changed.

### Output

There is no meaningful return value and no explicit status result. Successful completion is observable through memory changes.

### Preconditions for the tree-rotation interpretation

A caller seeking the conventional rotation result must provide:

- Valid, suitably accessible storage for every field reached on the executed path.
- A valid promoted record reached through the selected record’s offset-12 field.
- Consistent parent and child relationships.
- A container whose root-holder link identifies the appropriate enclosing structure.
- No concurrent or externally induced changes to the relevant links during execution.
- No overlapping records or fields that invalidate the intended tree relationships.

The function does not enforce these conditions. The exact behavior of malformed but accessible storage follows the accesses below rather than a separately validated tree operation.

## Behavior

### 1. Capture the promoted record

The function reads the selected record’s four-byte field at offset 12. The resulting address identifies the promoted record for the rest of the invocation.

This address is retained. The function does not subsequently rediscover the promoted record through the selected record’s offset-12 field.

There is no check for a zero promoted-record address before accessing its fields.

### 2. Replace the selected record’s offset-12 link

The function reads the promoted record’s field at offset 8 and writes that four-byte value into the selected record’s field at offset 12.

For a well-formed tree, this transfers the promoted record’s left subtree to the selected record’s right-child position.

The function then reads the promoted record’s offset-8 field again and compares the newly read value with zero.

- If this read yields zero, it skips the transferred-record parent update.
- If it yields a nonzero value, it reads the promoted record’s offset-8 field again to obtain the address whose offset-4 field is written. That field receives the selected record’s address.

These are distinct reads. The function does not use a single captured transferred-record address throughout this phase. If overlapping storage or external modification changes the field between accesses, the value written into the selected record and the record subsequently receiving a parent update need not correspond.

The nonzero test protects only this particular parent-update branch. It is not a general validity check.

### 3. Set the promoted record’s parent-like link

The function reads the selected record’s offset-4 field and writes the resulting four-byte value into the promoted record’s offset-4 field.

Under the tree interpretation, the promoted record inherits the selected record’s former parent.

This happens before the function reads the container’s root-holder address. Consequently, if storage overlaps, this write can affect values used in the following phase.

### 4. Redirect the enclosing link

The function reads the container’s offset-16 field to obtain the root-holder address. It then reads the root holder’s offset-4 field.

There are two paths.

**Root-holder match**

If the root holder’s offset-4 field equals the selected record’s address, the function writes the promoted record’s address into that same root-holder field.

On this path, it does not inspect either child field of the selected record’s former parent. It also does not independently force the promoted record’s parent field to zero or to a particular sentinel value. That field already contains whatever was copied from the selected record in the preceding phase.

**Root-holder mismatch**

If the root-holder comparison fails:

1. The function reads the selected record’s offset-4 field again to obtain a parent-record address.
2. It reads that parent record’s offset-8 field.
3. If the field equals the selected record’s address, it writes the promoted record’s address into that offset-8 field.
4. Otherwise, it writes the promoted record’s address into the parent record’s offset-12 field.

The fallback does not verify that the parent’s offset-12 field actually points to the selected record. A mismatch at offset 8 is sufficient to select the offset-12 write.

The parent address used here is obtained by a fresh read. It is not necessarily the same value copied to the promoted record earlier if aliasing or external modification has intervened.

### 5. Complete the local relationship

After redirecting the enclosing link, the function performs these writes in order:

1. The promoted record’s offset-8 field receives the selected record’s address.
2. The selected record’s offset-4 field receives the promoted record’s address.

The function then returns.

### Ordering and intermediate states

The phases above establish the source-level order of the relevant memory operations. Within an individual assignment, the supplied material does not establish a machine-instruction order for evaluating independent address and value expressions.

The operation is not presented as atomic. For an ordinary non-overlapping tree, intermediate states include:

- The selected record’s right link has changed before the enclosing link is redirected.
- The promoted record’s parent-like field has changed before its left link is replaced.
- The enclosing link has been redirected before the selected record’s parent-like field receives its final value.

No synchronization, rollback, or consistency barrier is shown.

## Side effects

On a completed invocation, the function executes five four-byte stores, plus one additional four-byte store when the transferred-link test is nonzero:

1. Replace the selected record’s offset-12 field.
2. Conditionally update a transferred record’s offset-4 field.
3. Replace the promoted record’s offset-4 field.
4. Replace exactly one enclosing link: the root-holder field, a parent’s offset-8 field, or a parent’s offset-12 field.
5. Replace the promoted record’s offset-8 field.
6. Replace the selected record’s offset-4 field.

These are store operations, not necessarily distinct destination fields when inputs alias.

The function contains no explicit allocation, release, reference-count operation, callback, logging, or external function call. It does not establish or transfer memory ownership. The caller remains responsible for providing accessible storage and whatever lifetime discipline the enclosing structure requires.

There is no explicit error path. Invalid addresses, insufficient storage, inappropriate alignment, or other invalid memory conditions are not translated into a return status. Their platform-specific consequences are unknown. A failure after some stores have occurred is not accompanied by any visible restoration mechanism.

All field transfers are four bytes wide. The function performs no key arithmetic, count adjustment, multiplication, or size calculation. Address calculations use fixed byte offsets. The supplied material does not establish overflow behavior, valid address ranges, or whether the original address representation has signed-integer constraints.

## Acceptance examples

The following examples are conditional expectations for accessible, non-overlapping records with stable fields. They describe observable results, not runtime-tested outcomes.

### Root rotation with a transferred subtree

Initially:

- The root holder identifies the selected record.
- The selected record’s right link identifies the promoted record.
- The promoted record’s left link identifies a transferred subtree.
- The selected record has a parent-like value appropriate to the enclosing representation.

After completion:

- The root holder identifies the promoted record.
- The promoted record’s parent-like field contains the selected record’s original parent-like value.
- The promoted record’s left link identifies the selected record.
- The selected record’s parent link identifies the promoted record.
- The selected record’s right link identifies the transferred subtree.
- The transferred subtree’s parent field identifies the selected record.

The selected record’s left link and the promoted record’s right link are not directly written.

### Non-root rotation through a left-child link

Suppose the root holder does not identify the selected record, and the selected record’s parent has its offset-8 field equal to the selected record’s address.

After completion, that parent’s offset-8 field identifies the promoted record. Its offset-12 field is not written by the enclosing-link phase. The promoted record receives the former parent address, and the local links change as described above.

### Non-root rotation through the fallback link

Suppose the root-holder comparison fails and the parent’s offset-8 field does not equal the selected record’s address.

The function writes the promoted record’s address into the parent’s offset-12 field. This occurs even if that field previously identified an unrelated record. Such input is not rejected or repaired beyond the specified writes.

### No transferred subtree

Suppose the promoted record’s offset-8 field remains zero through the transfer phase.

The selected record’s offset-12 field becomes zero. No transferred-record parent field is accessed or written. The remaining promotion and enclosing-link updates still occur.

### Root with a nonzero parent-like value

Suppose the root-holder comparison succeeds, but the selected record’s offset-4 field contains a nonzero sentinel address or another nonzero value.

The promoted record receives that value. Root recognition does not imply that its parent-like field is cleared.
