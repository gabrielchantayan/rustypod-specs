# F-cd96e43d3119

## Purpose

F-cd96e43d3119 selects between two shared-object operands and returns the selected operand’s 32-bit value. Before selection, it conditionally executes a common initialization sequence. After selection, it checks the selected branch’s readiness bit and may execute acquisition, production, registration, and completion calls.

These labels describe the apparent roles of the operations. The established contract is their ordering, memory-access structure, argument evaluation, and return behavior. Object construction, registration, synchronization, and publication are inferred intent, not established dependency semantics.

The selected branch is fixed once the selector is read. Its operands are **not** established as a branch-wide snapshot: several are evaluated at distinct points separated by dependency calls.

## Interface

**Explicit inputs:** None.

**Implicit inputs:** Shared storage, branch operands, dependency return values, and the two callable targets reached during common initialization.

**Output:** A 32-bit value obtained by evaluating the selected branch’s object operand at the return point. It is not necessarily the value previously passed to that branch’s producer. The evidence does not establish whether this representation is an address, handle, or ordinary integer.

There is no separate visible error return.

“Operand” identifies a source of a value, not a promise that the value is immutable. The supplied representation does not fully establish which operands are fixed addresses and which are read from mutable storage.

### Common-initialization indirection

Each common provider returns a value identifying storage. Reaching the callable target requires **two memory reads after the provider returns**:

1. Read the first 32-bit entry at the provider-returned location. That entry supplies an intermediate address.
2. Read the callable pointer stored at that intermediate address.
3. Invoke that callable target.

The first entry is therefore an address of callable-pointer storage, not the callable target itself. The callable-pointer load uses the target’s pointer representation; the visible representation is 32-bit. No explicit arguments appear for either indirect invocation, but hidden or calling-convention-specific inputs are not ruled out.

### Widths and validity requirements

- The common flag and selector are each one byte.
- The first entry read through each common provider result is 32 bits.
- The branch B readiness read is 32 bits.
- The function return and both producer results are 32-bit values.
- Acquisition is tested as an integer result against zero.
- The underlying width of the branch A readiness read is not established; only its low-bit test is established.

Whenever a path executes an access, its corresponding storage must be valid for that access. Common initialization additionally requires each provider-returned location to support the first read, each intermediate address to support the callable-pointer read, and each resulting target to be callable under the applicable convention.

Selected-branch operands must meet the invoked dependencies’ requirements at their respective evaluation points. The function visibly enforces none of these validity conditions.

## Behavior

### Common initialization

The function retains a control-region base before entering the common gate and reads the common flag.

If the flag is zero, it performs the following sequence:

1. Writes the byte value 1 to the common flag.
2. Calls F-bb3161cd1a23.
3. Reads the first 32-bit entry through that provider’s result.
4. Uses the entry as an intermediate address and reads the callable pointer there.
5. Invokes that target.
6. Calls F-0f7a1f274e25.
7. Performs the same two-stage memory lookup through the second provider’s result.
8. Invokes the second target.

Each step requiring a preceding call to return occurs only after that call returns normally. The second provider is not called until the first indirect invocation has returned.

If the common flag is nonzero, the function skips both providers, both indirect lookups, and both indirect invocations. A nonzero value other than 1 is not normalized.

The flag write precedes all these calls. It records entry into the sequence, not demonstrated completion. There is no visible rollback if a later operation fails or does not return.

### Selection

After the common gate, the function reads the selector at byte offset 1 from the retained control-region base.

- Zero selects branch A.
- Every nonzero byte selects branch B, including values whose high bit is set.

The selector is read after the common dependencies have run. A dependency’s change to that byte can therefore affect the current invocation, provided the retained storage remains valid. Replacing a separately stored control-region pointer is not itself established to redirect this selector read: the base used here was retained earlier.

The function does not visibly reread the selector after choosing a branch. Later changes to it do not cause a branch switch within this invocation.

### Branch A

The function reads the storage identified by the A guard operand and tests bit 0.

If bit 0 is set, it skips acquisition and all branch A initialization calls, then evaluates the A object operand for return.

If bit 0 is clear, it evaluates the A guard operand for the acquisition argument and calls F-b255b26284e6.

- A zero result skips production, registration, and completion.
- Any nonzero result enters the initialization sequence. There is no separate negative-result error branch.

On a nonzero acquisition result:

1. After acquisition returns, the function evaluates the A object operand and calls F-01bf675da847 with that value.
2. After the producer returns, it evaluates the two A registration operands and calls F-804adc29bbfb with the 32-bit producer result first, followed by those operands in their fixed argument positions.
3. After registration returns, it evaluates the A guard operand again and calls F-d08d3ca17b81 with that value.
4. After completion returns, it evaluates the A object operand again and returns its 32-bit value.

The producer result is forwarded without a visible success check or transformation. Zero is forwarded as zero.

Every normally returning branch A path returns the A object operand evaluated at the return point, including paths that skip initialization.

### Branch B

The function reads the 32-bit quantity at byte offset 12 from the B status base and tests bit 0.

If bit 0 is set, it skips acquisition and all branch B initialization calls, then evaluates the B object operand for return.

If bit 0 is clear, it evaluates the B guard operand and calls F-b255b26284e6. The B guard operand must not be assumed identical to the status base or the address of its status field.

A zero acquisition result skips production, registration, and completion. Any nonzero result causes:

1. Evaluation of the B object operand after acquisition returns, followed by F-39eed0c53080 with that value.
2. Evaluation of the B registration operands after the producer returns, followed by F-804adc29bbfb with the 32-bit producer result first and the two registration operands afterward.
3. Reevaluation of the B guard operand after registration returns, followed by F-d08d3ca17b81.
4. Reevaluation of the B object operand after completion returns, followed by return of its 32-bit value.

Every normally returning branch B path returns the B object operand evaluated at return, not the producer or acquisition result.

### Evaluation timing and value stability

The following distinctions apply to both branches:

- Readiness is tested before the acquisition argument is evaluated.
- The guard operand is evaluated for acquisition and again for completion after registration.
- The producer’s object argument is evaluated after acquisition.
- Registration operands are evaluated after the producer returns.
- The returned object value is evaluated after completion, or at the return point on a path that skipped some or all initialization calls.

Where these operands come from mutable storage, intervening dependencies can change their values. Consequently:

- Acquisition and completion are **not guaranteed to receive equal guard values**.
- The producer’s object argument and the function’s returned value are **not guaranteed equal**.
- Registration operands need not have the values they had before acquisition or production.
- An acquisition returning zero can still affect the object operand subsequently returned.

Argument positions are established; the relative evaluation order of the two registration operands is not. Their evaluation occurs after production and before entry to registration.

### Arithmetic and ordering

Only bit 0 determines readiness. Higher set bits do not independently suppress acquisition.

The explicit field displacements are one byte for the selector and 12 bytes for branch B’s status field. There is no visible length calculation, size multiplication, or counter update. Address validity remains a precondition; no checked address-arithmetic failure path is shown.

The function establishes sequencing of its accesses and calls, not memory-ordering guarantees. No explicit atomic operation, fence, or local locking primitive is shown.

## Side effects

The only directly established data write is the single-byte write of 1 when the common flag is read as zero.

Dependencies and indirect targets may have other effects. Their contracts are unavailable, so this specification does not assume they preserve globals, operands, pointed-to storage, guards, or objects. Subsequent evaluations must be understood in that context.

The function does not visibly:

- Write the selector.
- Directly set either readiness bit.
- Allocate, release, or copy an object.
- Validate a producer result.
- Inspect registration or completion results.
- Substitute a fallback object after acquisition returns zero.

Returning a value does not establish ownership transfer. Passing a producer result to registration does not establish whether that dependency retains, copies, registers, or releases anything.

If a dependency does not return normally, later operations are not established to occur. No local recovery, rollback, or compensating completion call is visible.

The early common-flag write permits a reentrant or concurrent invocation to encounter a nonzero flag before the first invocation finishes common initialization. Whether such execution is permitted or prevented externally is unknown.

## Acceptance examples

These are conditional static acceptance scenarios, not executed tests. Each assumes valid accesses and normally returning dependencies unless stated otherwise. Relevant values remain unchanged only where the scenario explicitly requires it.

1. **Skip common initialization and return branch A.**  
   With common flag 2, selector zero, and A readiness bit set, neither common provider nor any branch A dependency is called. The flag is not rewritten. The return is the A object operand evaluated at return.

2. **Perform both reads for each indirect call.**  
   With a zero common flag, 1 is written before the first provider call. Its result identifies a location containing a 32-bit intermediate address; the callable pointer is read from that intermediate address. Only after invoking that target and receiving a normal return does the second provider run and undergo its own two-read lookup.

3. **Common initialization changes selection.**  
   If a common dependency changes the selector in the retained control region from zero to 255 before selection, branch B is selected. No signed interpretation changes that result.

4. **Acquisition declines but changes the return operand.**  
   With branch A selected and readiness clear, acquisition is called. If it changes mutable A object-operand storage and returns zero, production, registration, and completion are skipped. The function returns the newly evaluated A object value, not a value cached before acquisition.

5. **Producer and return values differ.**  
   Suppose accepted branch B acquisition leaves the object operand with value P. The producer receives P. If registration or completion changes mutable object-operand storage to Q and Q remains there until return, the function returns Q. Equality between P and Q is not required.

6. **Acquisition and completion guards differ.**  
   Suppose branch A acquisition receives guard value G. If an intervening dependency changes mutable A guard-operand storage to H, completion receives H, provided it remains H when reevaluated. The visible body does not require completion to receive G.

7. **Registration operands reflect post-producer state.**  
   If the producer changes mutable storage supplying a registration operand, registration receives the value evaluated after that producer returns. Its first argument remains the producer’s 32-bit result.

8. **Higher readiness bits do not suffice.**  
   With branch B selected and status 2, acquisition is attempted because bit 0 is clear. With status 3, acquisition is skipped because bit 0 is set.

9. **Zero producer result is forwarded.**  
   After nonzero acquisition, a producer result of zero is passed as registration’s first argument. Completion follows if registration returns normally.

10. **Common initialization is interrupted.**  
    If the first indirect target does not return normally, the earlier flag write has already occurred. No second provider call, selector read, or normal return is established for that execution.
