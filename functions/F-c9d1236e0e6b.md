# F-c9d1236e0e6b

## Purpose

F-c9d1236e0e6b places a supplied entry at the head of a bucket selected by a new 32-bit key. It conditionally performs a further operation using a key preserved from the supplied entry before that insertion.

The insertion and two context-status writes precede the operation that can produce a nonzero return. A nonzero result therefore does not imply that the context, entry, or bucket table remains unchanged. No rollback is shown.

“Rekeying,” “replacement,” and “linked bucket chain” are inferred intent. The established contract is the sequence of calls, memory accesses, arithmetic, and branches below. Conventional final structures require additional nonoverlap and stability assumptions.

## Behavior

### Preparation and previous-key preservation

A local preserved-key value starts at zero. A local selected-entry value starts at the fallback-entry input.

The function first calls F-b93e3fe564f6 with no explicit arguments, then F-4c6b253a4fd3 with the supplied entry.

Only after both calls return does it inspect the supplied entry’s byte at `0x1E`. If that byte is nonzero, it reads the 32-bit field at `0x04` into the preserved-key value. Otherwise, this phase does not read that key field.

Thus preservation uses the entry state after preparation, not necessarily its state on function entry. Any nonzero byte enables preservation; it need not equal one. A preserved key of zero later skips previous-key processing, just as an unpreserved key does.

### Supplied-entry processing and lookup

The function calls F-e18a167b40e6 with the context and supplied entry. After return, it writes zero to the supplied entry’s byte at `0x1E`.

It then calls F-c1f06f89d6d7 with the context and original new key.

If lookup returns zero, the function writes zero to the supplied entry’s byte at `0x1E` again. This is a separate write after lookup.

If lookup returns a nonzero address, the function instead:

1. Calls F-e18a167b40e6 with the context and lookup result.
2. Calls F-d0d75bd453b2 with the lookup result.
3. Reads the lookup result’s byte at `0x1E`.
4. Writes that byte to the supplied entry’s byte at `0x1E`.

The copied value is observed after both calls. It is copied without normalization. No local check requires the lookup result to differ from the supplied entry.

Neither dependency’s ownership behavior is established. The subsequent byte read imposes a validity requirement; it does not prove that either call preserves the object.

### Metadata, key, and bucket selection

The function reads the context’s 32-bit field at `0x54` and calls F-811a25bdbe21 with that value and the original new key. The represented one-byte result is written to the supplied entry at `0x1C`.

The complete original new key is then written to the supplied entry at `0x04`.

Next, the function reads context field `0xCC` and forms the bucket index:

\[
\text{index} =
\bigl((\text{field at }0xCC - 1)\bmod 2^{32}\bigr)
\mathbin{\mathrm{AND}}
\text{new key}.
\]

This is bit masking, not division remainder. The source does not require or validate a positive power-of-two bucket count.

Bucket slots have a four-byte stride. In the represented 32-bit unsigned arithmetic, multiplying the index by four wraps modulo \(2^{32}\); the table-address expression also combines the table value with that unsigned displacement. This arithmetic does not establish that the resulting address identifies valid table storage or that the table contains a distinct slot for every possible index.

The index is computed once. Later insertion writes do not cause it to be recomputed, even if storage overlaps the context’s mask field.

### Ordered bucket insertion

The function reads the table address from context offset `0xD0`, then reads the selected four-byte bucket slot.

If this first head value is nonzero, it writes the supplied-entry address to that object’s field at `0x0C`.

It then performs the following operations:

1. Reads the table address from the context again.
2. Reads the selected bucket slot again.
3. Writes that second head value to the supplied entry at `0x08`.
4. Reads the table address from the context again and writes the supplied-entry address to the selected slot.
5. Writes zero to the supplied entry at `0x0C`.

The first head value controls the existing-head write. The second head value supplies the write to entry offset `0x08`. They are separate reads and need not agree under overlap or external mutation.

With stable, nonoverlapping storage, this sequence resembles insertion at the front of a doubly linked bucket chain. That interpretation is not an unconditional final-state guarantee. For example, a bucket slot overlapping entry offset `0x08` is subsequently overwritten with the entry address. Overlap with context offset `0xD0` can also affect later table-address reads.

No local check prevents duplicate membership, self-insertion, cycles, or overlapping storage. Actual support for such configurations remains unknown.

## Acceptance examples

These are conditional static criteria, not executed tests. All examples require valid storage and returning dependencies.

For examples describing conventional final structures, additionally assume stable table addresses and contents except for the specified writes; no unspecified dependency mutations; and nonoverlap among context storage, bucket-slot storage, and the relevant entry objects. A lookup result equal to the supplied entry is excluded from those conventional examples unless explicitly stated.

1. **No preserved key, empty bucket.**  
   If the inspected preservation byte is zero, lookup returns zero, and the selected slot initially contains zero, the supplied entry receives the new key and metadata. Its `0x1E`, `0x08`, and `0x0C` fields end at zero. The bucket points to it, context bytes `0x12` and `0x19` become one, previous-key processing is skipped, and the counter is decremented before a zero return.

2. **Empty slot overlapping the forward-link field.**  
   Departing from the nonoverlap assumptions, suppose the selected bucket slot occupies the supplied entry’s field at `0x08`, initially zero, while other relevant storage is distinct and stable. Both slot reads obtain zero. The function writes zero to entry offset `0x08`, then writes the supplied-entry address into that same slot. Consequently, entry offset `0x08` ends containing the entry address, not zero. This demonstrates the ordered accesses; it does not establish supported aliasing.

3. **Nonzero preservation byte with a zero key.**  
   If the inspected byte is nonzero but the preserved key is zero, F-133a6620fb39 is skipped. Preservation of a zero value does not activate the optional phase.

4. **Post-processing byte copy.**  
   If lookup returns a distinct object whose `0x1E` byte is `0x7F` after both processing calls, the supplied entry receives `0x7F`, not one, at that offset.

5. **Occupied, nonoverlapping bucket.**  
   With a stable distinct head, its `0x0C` field receives the supplied-entry address. The supplied entry’s `0x08` receives the old head, its `0x0C` becomes zero, and the bucket receives the supplied-entry address.

6. **Selected-entry replacement on success.**  
   If F-133a6620fb39 replaces the selected-entry value and returns zero, the subsequent status writes target the replacement. F-44d249c54e70 receives that selected value, assuming intervening calls do not alter it. The other F-6398fbab1062 call still has no explicit argument shown.

7. **Previous-key error.**  
   A nonzero previous-key result is returned unchanged after the conditional error dependency and counter decrement. Earlier insertion writes are not rolled back.

8. **Arithmetic boundaries.**  
   With context field `0xCC` equal to zero, the mask is `0xFFFFFFFF`, so the index equals the new key. For index `0x40000000`, the represented four-byte unsigned displacement wraps to zero. Neither condition guarantees a valid logical table configuration.

9. **Signed comparison boundary.**  
   A preserved key of `0xFFFFFFFF` participates as signed negative one in the error-path comparison. Against a signed bound of zero, the comparison succeeds; F-16d1285c814f is called if context field `0x54` is also nonzero.
