# F-e74532b2f6fa

## Purpose

F-e74532b2f6fa updates a state object, selects among notification and processing paths, and conditionally performs a release-like sequence with allocation-accounting updates.

Established operations include an entry-field decrement, conditional promotion of one state field into another, dependency calls, an indirect operation, allocation-prefix checks, and ordered accounting changes.

“Current,” “pending,” “notification,” and “release” are descriptive interpretations, not established application semantics. In particular, the available evidence does not identify which dependency, if any, frees storage.

This contract describes static evidence. Conditional examples are not runtime test results.

## Interface

### Inputs and result

The function accepts two 32-bit inputs:

- **State address:** used as the base of a writable state object.
- **Incoming value:** passed to dependencies and, on ordinary release paths, interpreted as a payload address.

There is no specified return value. Some paths return normally; others reach dependencies designated non-returning in the supplied representation.

Zero is a meaningful incoming value. It suppresses ordinary release handling but does not universally suppress notification or processing calls.

## Behavior

### Entry-field update

Before branch selection, the function reads the 32-bit field at state offset `0x4C`.

If that read is zero, it explicitly writes zero to the field. Otherwise, it reads the field again and writes the second value minus one.

The nonzero test is not a positivity test. Negative signed interpretations are not clamped to zero. The second read on the nonzero path is distinct from the first; the evidence does not justify replacing both with one captured value when intervening mutation is possible.

The operation has a 32-bit destination and no visible overflow check. Signed-overflow behavior is not independently established by the supplied representation.

### Initial selector is zero

After the entry update, the function reads state offset `0x84`. If it is zero, the function tests the pending field at `0x38`.

When pending is zero, it tests current at `0x34`:

- **Current is zero:** notify the original incoming value, then proceed to ordinary release handling.
- **Current is nonzero:** call F-85bcc83e394a with the state address, original incoming value, and `1`, then proceed to ordinary release handling for that original incoming value.

The zero-current notification path does not retest current afterward. Notification may therefore change state without changing that already selected path.

When pending is nonzero, the function performs promotion as described below.

### Initial selector is nonzero

The function first notifies the original incoming value, including when that value is zero.

For a nonzero incoming value, notification is followed by:

1. F-e0bf74703fb9 receiving the original incoming value.
2. F-feee9156a257 receiving the same value.

F-feee9156a257 is designated non-returning in the supplied representation. Under that designation, this path performs neither ordinary accounting nor the later state-update call. Behavior if the dependency unexpectedly returns is not established.

For a zero incoming value, notification is followed by F-0a5e6011a383. Its arguments are the state address and the values then read from state offsets `0x34` and `0x84`.

Those field values are obtained after notification; entry values must not be substituted. Their relative read order is not established.

After F-0a5e6011a383 returns, the function tests pending:

- Zero pending leads to return.
- Nonzero pending leads to promotion, followed by F-85bcc83e394a with the state address, zero, and `1`, then return.

This pending test observes state after F-0a5e6011a383. That dependency need not preserve the field.

### Promotion and subsequent processing

Promotion has three ordered memory effects:

1. Read the pending field at `0x38`.
2. Write that value to current at `0x34`.
3. Clear pending at `0x38`.

The copy uses a new pending read, not necessarily the value from the earlier nonzero test.

If promotion was selected with an initially zero selector:

- **Zero incoming value:** F-85bcc83e394a receives the state address, zero, and `1`; the function then returns.
- **Nonzero incoming value:** the function notifies that original incoming value and then rereads current.
  - If current is now zero, F-85bcc83e394a is skipped.
  - Otherwise, F-85bcc83e394a receives the state address, **zero**, and `1`.
  - Both cases subsequently enter ordinary release handling for the **original nonzero incoming value**.

Thus the processing argument and the value later subjected to release handling can differ. Notification mutations to current are observable on this path.

Promotion following F-0a5e6011a383 has no additional notification and no post-promotion current test before F-85bcc83e394a.

### Ordinary release handling

A zero value at this stage returns without prefix access or accounting.

For a nonzero original incoming value, the observable sequence is:

- F-e0bf74703fb9 receives that value.
- F-2fd8826557a4 is called without explicit arguments.
- The global accounting-context pointer is read and its value retained.
- The allocation header is validated.
- F-c0fc6d033caa receives the retained context.
- Accounting updates occur in the order described below.
- F-cc6c9b4a0f68 receives the retained context and the header address, eight bytes before the payload.
- F-e586bff64fb7 receives the retained context.
- The function returns if these dependencies return normally.

The prefix is not validated before F-e0bf74703fb9 or F-2fd8826557a4.

Header validation first reads the 32-bit header and tests it for zero. A zero value invokes F-a817d8d58c10. Otherwise, the header is read again and its least-significant bit is tested; a set bit invokes the same dependency.

F-a817d8d58c10 is designated non-returning. No recoverable error result or explicit rollback is visible.

These are separate header observations. If the first read is nonzero and the second read is zero, the second test does not reject zero: it tests only the least-significant bit. Validation also does not guarantee that later header reads retain either validated value.

### Accounting order, widths, and aliasing

Accounting begins after F-c0fc6d033caa returns.

The first unsigned 16-bit prefix index is read. The header is then read and masked with `0x3FFFFFFC`, producing a captured amount. That mask clears the lowest two and highest two bits; results range from zero through `0x3FFFFFFC` and are divisible by four.

Four read-modify-write operations follow, in this order:

1. Subtract the captured amount at `0x224 + 4 × first index`.
2. Subtract that same amount at `0x30C`.
3. Read the second unsigned 16-bit prefix index, then subtract the same amount at `0xE0 + 4 × second index`.
4. Subtract the same amount at `0x220`.

Next, F-09dcb55e8e0a is called without explicit arguments. Its result selects the word at `0x310 + 4 × result`, which is decremented by one. The word at `0x390` is then decremented by one.

Finally, the header is read again and masked with `0x3FFFFFFC`. This newly obtained amount is subtracted from the word at `0x08`. It need not equal the captured amount used by the first four operations.

Each update reads its destination’s then-current contents. Distinct operation descriptions do not imply distinct memory locations:

- A first prefix index of `0x3A` selects `0x30C`. The first two operations therefore subtract from the same word, successively.
- A dependency result of `0x20` selects `0x390`. The two count operations then decrement the same word successively.
- Other overlaps are not excluded. For example, a second prefix index of `0x50` selects `0x220`, making the third and fourth amount operations share a destination.

Aliasing can extend beyond these examples. The function contains no checks preventing accounting destinations from overlapping state, allocation metadata, or other relevant storage. Earlier writes can consequently affect later reads, including the second prefix index and final header read.

The two prefix indices are widened as unsigned values before multiplication by four. Each contributes at most `0x3FFFC` to its address expression. Array bounds and safe address formation are not established.

Amount subtraction uses an unsigned 32-bit masked amount and stores a 32-bit result; it is not saturating arithmetic. The count decrements and entry decrement are represented as signed operations, so their overflow behavior must not be equated with guaranteed unsigned wrapping. No arithmetic-error reporting is visible.

## Side effects

### State and dependency visibility

The entry field is always written. Promotion additionally writes current and then pending.

Dependencies may alter state, globals, allocation metadata, or accounting storage. No preservation guarantee is available. Relevant timing boundaries include:

- Notification precedes the alternate-path field arguments and the post-promotion current test.
- F-0a5e6011a383 precedes the subsequent pending test.
- F-2fd8826557a4 precedes capture of the global context pointer.
- F-c0fc6d033caa precedes reads of the accounting indices and captured amount.
- F-09dcb55e8e0a precedes both count updates and the final header read.

After context capture, later operations use the retained context address even if a dependency changes the global pointer. This does not imply that the retained context’s contents remain unchanged.

### Ownership and lifetime

Passing a nonzero incoming value to F-85bcc83e394a does not establish ownership transfer: ordinary release handling can subsequently process that same value.

Likewise, passing a value to notification or either release-like dependency does not prove retention, destruction, or deallocation. Required storage must remain accessible through every later reached access. The function provides no protection against a dependency invalidating that storage prematurely.

### Errors and synchronization

Visible error handling consists of the invalid-header terminal call. Pointer faults, invalid indirect targets, out-of-range indices, arithmetic hazards, and dependency failures have no established recovery protocol.

No rollback is visible for earlier state writes or dependency effects.

Dependencies surrounding accounting may have synchronization purposes, but that intent is unconfirmed. Atomic updates, mutual exclusion, reentrancy safety, and thread safety are not established.

## Acceptance examples

These are conditional static cases, not executed tests. Unless a case says otherwise, reached addresses are valid, returning dependencies preserve relevant storage, and arithmetic remains within defined ranges.

1. **Entry update.**  
   A stable entry field of zero receives an explicit zero write. A stable value of two becomes one. Negative values are not clamped merely because they are negative.

2. **Zero incoming value still notifies.**  
   If selector, pending, and current are all zero, notification receives zero. F-85bcc83e394a is not called, and no ordinary accounting occurs.

3. **Existing current value.**  
   With selector and pending zero, current nonzero, and incoming value nonzero, F-85bcc83e394a receives the original incoming value. Ordinary release handling subsequently processes that same value.

4. **Promotion with nonzero incoming value.**  
   With selector zero and pending nonzero, promotion precedes notification. If current remains nonzero afterward, F-85bcc83e394a receives zero; ordinary release handling still processes the original nonzero incoming value.

5. **Notification clears promoted current.**  
   Under the preceding conditions, clearing current during notification suppresses F-85bcc83e394a but not ordinary release handling.

6. **Alternate route with zero incoming value.**  
   Notification precedes F-0a5e6011a383. Pending is tested after that dependency. A resulting nonzero pending value is promoted and followed by F-85bcc83e394a with zero; a zero pending value leads to return.

7. **Alternate route with nonzero incoming value.**  
   Notification precedes F-e0bf74703fb9 and F-feee9156a257. Under the latter’s non-returning designation, ordinary accounting and F-0a5e6011a383 are not reached.

8. **Invalid stable header.**  
   A zero header, or a stable nonzero header with its least-significant bit set, reaches F-a817d8d58c10 after F-e0bf74703fb9 and F-2fd8826557a4. Under its non-returning designation, accounting does not begin.

9. **Stable header, operation-level accounting.**  
   A stable header of `0x40000012` passes validation and yields `0x10`. Each of the first four amount operations subtracts `0x10` from its selected word. The final amount operation also subtracts `0x10`. Each count operation subtracts one. These statements alone do not imply five distinct amount destinations or two distinct count destinations.

10. **Aliased amount destination.**  
    With that stable header and first prefix index `0x3A`, the first two operations both target `0x30C`. If no other operation or dependency changes that word, it decreases by `0x20`, not `0x10`.

11. **Aliased count destination.**  
    If F-09dcb55e8e0a returns `0x20`, both count operations target `0x390`. If no other operation or dependency changes that word, it decreases by two.

12. **Distinct-destination final deltas.**  
    The familiar final deltas—five words each reduced by `0x10` and two words each reduced by one—require all seven destinations to be pairwise distinct, stable header and indices, no interfering dependency or memory mutation, and no relevant aliasing with metadata. The function does not enforce these assumptions.
