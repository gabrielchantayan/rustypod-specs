# F-d2e8164cb441

## Purpose

F-d2e8164cb441 scans an ordered array of record pointers and conditionally updates a caller-supplied state object with a selected record and selection flags.

Two selection modes are established:

- **Direction-matched mode:** select the first record whose designated endpoint is strictly within a supplied signed threshold of the state’s position.
- **Fallback mode:** when enabled by a state flag, attempt a flag-selected endpoint match and otherwise retain records satisfying an interval-containment comparison.

Endpoint matches terminate the scan immediately. Fallback containment selections do not terminate the scan, so later qualifying records can replace earlier ones.

Interpreting the records as geometric intervals and the selection flags as endpoint classifications is inferred intent. The actual contract consists of the field accesses, arithmetic, comparisons, and mutations described below.

## Interface

The function has four inputs and no returned value.

| Input | Observed role |
|---|---|
| Collection address | Addresses an object containing a scan count and an array address. |
| State address | Addresses direction bytes, flags, a selected-record field, and a position. |
| Threshold | Signed 32-bit value used in strict endpoint-distance comparisons. |
| Requested direction | Signed 32-bit value compared with promoted direction bytes; also controls fallback flag interpretation. |

The supplied representation uses 32-bit integer fields and four-byte pointer slots. Compatibility with a different pointer width or data model is not established.

### Collection layout

Offsets are in bytes from the collection address.

| Offset | Width | Meaning |
|---|---:|---|
| +4 | 4 bytes | Signed scan count. |
| +12 | 4 bytes | Address of an array of four-byte record pointers. |

Other collection fields are not accessed.

Each array slot supplies one record address. Consecutive slots are four bytes apart.

### Record layout

Offsets are relative to an address obtained from the pointer array.

| Offset | Width | Meaning |
|---|---:|---|
| +0 | 4 bytes | Signed start value. |
| +4 | 4 bytes | Signed length or endpoint displacement. |

The second field is read for end-based distance calculations and for certain fallback containment comparisons. It is not read on every path.

### State layout

Offsets are in bytes from the state address.

| Offset | Width | Meaning |
|---|---:|---|
| +16 | 4 bytes | Unsigned flags word. |
| +20 | 1 byte | First direction candidate. |

The relevant flag masks are:

| Mask | Observed role |
|---|---|
| `0x10` | Added on an endpoint match. |
| `0x40` | Enables fallback scanning. |

These names describe observed effects, not an independently established application-level meaning.

### Preconditions

For a bounded, valid scan, the collection must provide a nonnegative count and an array containing at least that many accessible pointer slots. Records actually inspected must expose the fields required by the selected path. The state must be readable and, on selection paths, writable at the offsets above.

Null checks, bounds checks, alignment checks, and pointer validation are absent. A zero count does not eliminate the initial collection and state reads.

## Behavior

### Initial reads and direction selection

The function first reads and promotes the first direction byte. It computes the negation of the requested direction and reads the collection count.

If the first candidate equals either the requested direction or its negation, the second direction byte is not read. Otherwise, the second byte is read and becomes the candidate used for subsequent selection.

The pointer-array address is then read from the collection.

Direction-matched mode is used only when the chosen candidate is nonzero and matches the requested direction or its negation. Otherwise, the function enters fallback processing.

Consequences include:

- A matching first candidate takes precedence over the second candidate.
- A first candidate of zero prevents reading the second candidate when the requested direction is zero, but still leads to fallback because the chosen candidate is zero.
- A zero chosen candidate never enables direction-matched scanning.
- Direction values other than conventional small positive and negative values are not rejected.

The signedness of the one-byte candidates is not independently established. Values below `0x80` are unaffected by that uncertainty; values at or above `0x80` may compare differently depending on promotion semantics.

### Arithmetic model

Endpoint-distance calculations use 32-bit integer subtraction, followed by conditional negation when the result is negative, then a signed comparison with the threshold.

For ordinary representable arithmetic, this behaves as an absolute distance. The comparison is strictly less than the threshold: equality does not match.

Overflow cases must not be replaced by unbounded mathematical arithmetic without qualification:

- Start distance is formed from position minus start.
- End distance is formed by subtracting start from position and then subtracting length. It is not necessarily evaluated by first constructing an endpoint.
- Negating the most-negative signed 32-bit value cannot produce a positive signed 32-bit magnitude.
- Negating the most-negative requested direction has the same representability issue.

Under 32-bit wrapping execution, a distance result of −2,147,483,648 remains negative after negation and can satisfy a threshold comparison that an ordinary absolute distance would fail. Exact overflow behavior is a documented-only portability boundary of the supplied representation.

### Direction-matched scanning

The function checks the current local count before reading each array slot. A count of zero returns immediately.

For each record:

1. If the chosen candidate equals the requested direction, the function evaluates start distance.
2. Otherwise, if the candidate equals the negated requested direction, it evaluates end distance.
3. If the resulting signed distance is strictly less than the threshold, the function:
   - Reads the current state flags.
   - Writes those flags with `0x10` and the appropriate endpoint mask added.
   - Writes the current record address to the selected-record field.
   - Returns immediately.
4. If no match occurs, the local count is decremented and the array cursor advances by one slot.

Start matching adds `0x200`; end matching adds `0x400`.

The first endpoint match in array order wins. No containment selection occurs in this mode. If all records fail, the selected-record field and flags are unchanged by this function.

### Fallback entry and endpoint choice

Fallback begins by reading the state flags once.

If `0x40` is clear, the function returns without scanning records or writing state.

If `0x40` is set, the requested direction determines how the other two masks are interpreted:

| Requested direction | Start-selection mask | End-selection mask |
|---|---|---|
| Exactly 2 | `0x80` | `0x100` |
| Any other value | `0x100` | `0x80` |

For every scanned record:

- If the start-selection mask is present, start distance is tested.
- Otherwise, if the end-selection mask is present, end distance is tested.
- If neither is present, no endpoint-distance test occurs.

When both masks are present, start selection has priority. An unsuccessful start-distance test does not cause an end-distance test for that record.

The flags used for these decisions are the single value sampled at fallback entry. They are not reread for each record.

### Fallback endpoint success

If a fallback endpoint distance is strictly less than the threshold, the function performs these writes in order:

1. Store the current record address in the selected-record field.
2. Store the sampled flags with `0x10` and the corresponding endpoint mask added.
3. Return.

This write order is the reverse of direction-matched success: fallback writes the pointer before the flags.

Because fallback writes from its earlier flags snapshot, it does not merge intervening flag changes that might occur through aliasing or external mutation.

### Fallback containment selection

After an absent or unsuccessful endpoint test, the function performs a containment-related comparison.

It rereads the state position and the record start. It then decrements the local count.

- If start is greater than position under signed comparison, that record does not cause a containment write.
- Otherwise, the function reads length, forms a 32-bit start-plus-length result, and compares that signed result with position using an overflow-corrected signed comparison.

In ordinary non-overflowing cases, containment therefore means:

**start ≤ position ≤ start + length**

Both boundaries are inclusive.

On a containment success, the selected-record field is written with the current record address. No flag bits are added, cleared, or otherwise written.

The array cursor advances before this conditional pointer write. Scanning continues afterward.

Therefore:

- The last containment-qualified record wins if there is no endpoint success.
- A later endpoint success overrides earlier containment selections and returns immediately.
- If neither endpoint nor containment selection occurs, the existing selected-record value is retained.
- Containment can update the selected record even when neither endpoint-selection mask is enabled.

If start-plus-length overflows, containment is governed by the signed interpretation of the 32-bit sum, not an unbounded interval endpoint.

### Termination

A nonnegative count bounds the scan to at most that many records, with earlier return on endpoint success.

The loop checks for equality with zero, not for a positive count. Negative counts are not rejected. They do not behave as an empty collection and can cause traversal beyond the supplied array before any zero count is reached. No safe behavior is established for such inputs.

## Side effects

The only explicit writes are to the state’s flags and selected-record fields.

The function does not explicitly:

- Allocate or release memory.
- Modify collection metadata.
- Modify array slots.
- Modify record fields.
- Clear previous endpoint flags.
- Reset the selected-record field before scanning.
- Report success, failure, or invalid input through a return value.

Existing flag bits are preserved by OR operations in ordinary non-aliased execution. In particular, a start match does not clear a previously set end-match bit, or vice versa.

The selected-record field receives an address taken directly from the collection’s array. No copying of record contents occurs. No ownership transfer, lifetime extension, or release obligation is established.

Aliasing is not checked. If state fields overlap collection, array, or record storage, a write can affect subsequent reads. The stable-input descriptions above assume disjoint storage and no concurrent mutation. That is a precondition for the simple ordered-scan interpretation, not a guarantee enforced by the function.

No explicit error channel exists. Invalid addresses, insufficient storage, and arithmetic portability failures are not converted into reported errors.

## Acceptance examples

These are conditional contract examples, not executed tests. Unless stated otherwise, they assume valid disjoint storage, stable inputs, a nonnegative count, and arithmetic without overflow.

### 1. First matching direction takes precedence

The first candidate equals the requested nonzero direction. A first record starts at 100, position is 103, and threshold is 4.

Start distance is 3, so that record is selected. The flags receive `0x10` and `0x200` before the selected pointer is written. The second direction byte and the record length are not needed on this path.

### 2. Threshold equality is not sufficient

For a start-directed scan, position is 103, start is 100, and threshold is 3.

The record does not match because distance equals the threshold. If no later record matches, state remains unchanged.

### 3. Opposite direction selects the end calculation

The chosen candidate equals the negated requested direction. A record has start 100 and length 20; position is 118 and threshold is 3.

End distance is 2. The record is selected with `0x10` and `0x400` added to the flags.

### 4. Disabled fallback does not scan

Neither direction candidate matches, and `0x40` is clear.

The function returns without reading a record pointer or modifying state. Initial state and collection metadata reads still occur.

### 5. Both fallback endpoint masks prefer start

Fallback is enabled, requested direction is 2, and both `0x80` and `0x100` are present.

For a record starting at 100 with length 20, position 119, and threshold 2, start distance fails. The function does not then test end distance, even though the end is only one unit away. Containment succeeds, so the selected pointer is updated without adding endpoint-result bits.

### 6. Last fallback containment wins

Fallback is enabled with neither endpoint-selection mask present. Position is 15. Two records, in order, describe intervals 0 through 20 and 10 through 30.

Both contain the position. The second record remains selected after the scan. Flags are unchanged.

### 7. Later endpoint success overrides containment

An early fallback record contains the position but fails its endpoint test. A later record passes the selected endpoint test.

The early record can first be stored as selected. The later record replaces it, endpoint flags are written, and subsequent records are not examined.

### 8. Zero direction forces fallback

Requested direction and the first candidate are both zero.

The second candidate is not read. The zero candidate nevertheless forces fallback. Whether records are scanned then depends on `0x40`.

### 9. Ordinary nonpositive thresholds prevent endpoint matches

With no overflow, distances are nonnegative. A threshold of zero or a negative threshold cannot accept an endpoint.

Fallback containment can still select a record because it does not use the threshold.

### 10. Empty scans preserve selection

With count zero, no record pointer is read and no selection occurs. Initial reads and, where applicable, the fallback flags read still occur.
