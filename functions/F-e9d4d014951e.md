# F-e9d4d014951e

## Purpose

F-e9d4d014951e installs six values into fixed locations within a caller-supplied memory region. It rearranges the bytes of a 32-bit input, combines them with the two bytes of a 16-bit input, copies two additional inputs, and constructs a final 16-bit field from the low four bits of another input.

The established behavior is a sequence of unconditional stores. The function does not inspect the region’s previous contents, validate arguments, allocate memory, or call another function.

The arrangement suggests preparation of a structured record, but the record’s semantic purpose is not established. No protocol, device, or application-specific meaning is assigned to these fields by this contract.

## Behavior

### Field construction

For describing the Packed value, number its bytes by significance:

- Byte 0 contains bits 7–0.
- Byte 1 contains bits 15–8.
- Byte 2 contains bits 23–16.
- Byte 3 contains bits 31–24.

These are numeric byte positions, not memory-order positions.

The function performs the following stores in the stated order:

| Order | Destination offset | Store width | Value |
|---|---:|---:|---|
| 1 | `0x4C` | 16 bits | Low byte: Packed byte 0. High byte: Packed byte 3. |
| 2 | `0x4E` | 16 bits | Low byte: Packed byte 1. High byte: low byte of Companion value. |
| 3 | `0x50` | 16 bits | Low byte: Packed byte 2. High byte: high byte of Companion value. |
| 4 | `0x52` | 16 bits | Payload word, unchanged. |
| 5 | `0x1A` | 8 bits | Payload byte, unchanged. |
| 6 | `0x56` | 16 bits | Selector-derived value described below. |

These are complete field replacements, not merges with existing destination contents. In particular, neither the first three fields nor the last field preserves any previously stored bits.

All four bytes of Packed value contribute exactly once across the first three fields. Both bytes of Companion value also contribute exactly once. The destinations therefore contain a rearrangement of six input bytes, expressed as three numeric 16-bit values.

For the second store, shifting Companion value into the high-byte position does not preserve its original high byte in the stored result. The final 16-bit destination retains only the shifted low byte. The original high byte instead appears in the third store.

### Selector-derived field

The final field uses only Selector’s low nibble. That nibble is placed in bits 7–4, and bit 6 is forced to one. Every other bit of the 16-bit result is zero.

Consequently:

- Bits 3–0 and bits 15–8 are always zero.
- Bit 6 is always one.
- Output bits 4, 5, and 7 reflect input bits 0, 1, and 3, respectively.
- Input bit 2 cannot distinguish outputs because the corresponding output bit is forced to one.
- Input bits 15–4 have no effect.

The possible numeric field values are exactly `0x0040`, `0x0050`, `0x0060`, `0x0070`, `0x00C0`, `0x00D0`, `0x00E0`, and `0x00F0`.

The forced bit is combined using a bitwise operation, not arithmetic addition. A low nibble that already supplies bit 6 does not cause a carry.

### Memory layout and ordering

The table specifies numeric word values. Physical byte layout depends on the execution environment’s endianness, which is not established by the supplied evidence.

For example, a numeric word value of `0xA1D4` at offset `0x4C` corresponds to bytes `D4 A1` on a little-endian target and `A1 D4` on a big-endian target. The input-byte significance definitions remain unchanged in either case.
