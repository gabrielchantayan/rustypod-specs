# F-805a9ea2f734

## Purpose

F-805a9ea2f734 searches a context-associated structure using a comparison dependency, resolves a candidate or fallback selection, and invokes callbacks associated with a nonsentinel selection. Its result is the 32-bit bitwise OR of the callback results, or zero when no callbacks execute.

The search has a significant candidate-update rule: when a search comparison returns zero, the candidate becomes the target of the current node’s link at offset `0x08`, not the node just compared. This rule is part of the established behavior and must not be replaced with a conventional search algorithm.

The broader container abstraction, comparison relation, callback meaning, and ownership rules are not established. This contract distinguishes visible static behavior from inferred intent and unresolved dependency behavior. No runtime tests have been performed.

## Interface

### Inputs

The function receives three values:

| Input | Representation | Established use |
|---|---|---|
| Context | A 32-bit address-valued input | Locates the header field and comparison-state region. |
| Second argument | An opaque 32-bit word | Copied into the first word of a local comparison record. |
| Third argument | An opaque 32-bit word | Copied into the second word of that record and independently supplied to every callback. |

The comparison record contains two consecutive four-byte words, ordered second argument followed by third argument. Comparison calls receive the address of the first word.

The original third argument remains the callback argument. Changing the second word of the comparison record does not, by itself, change the value supplied to callbacks.

### Output

The return value is an unsigned 32-bit word formed by bitwise OR:

- Selection equal to the current context header produces zero without callback traversal.
- A nonsentinel selection with an empty callback list produces zero.
- Otherwise, the result combines every callback result obtained before normal list termination.

Zero does not distinguish these cases from a traversal in which all callbacks return zero. No separate error status is visible.

Every address actually dereferenced must be valid for its particular read or dispatch.

The search loop explicitly tests whether the current search-node address is zero. A zero address terminates that loop before the comparison call or any link read from that node. This is a search-termination test, not general pointer validation.

In particular, that test does not validate the context or header before the initial reads, an accepted candidate before callback-list access, the list sentinel or elements, or the receiver and dispatch table. No explicit alignment, ownership, or structural validation is visible for those objects.

## Behavior

### Search initialization

The function first reads the header address from context offset `0xA0` and then reads the initial search-node address from header offset `0x04`.

It reads context offset `0xA0` separately to initialize the search candidate. The initial node and candidate therefore depend on distinct context-field reads; they are not derived from one cached header value.

The second and third arguments are copied into the local comparison record before search comparisons begin.

If the initial search node is zero, no search comparison or search-node link read occurs. Candidate checking still follows.

### Search traversal

For each nonzero current search node, F-bcefa5957e76 receives these operands in order:

1. The comparison-state address at context plus `0xA9`.
2. The address at current node plus `0x10`.
3. The local comparison-record address.

Only whether the returned value is zero matters.

For a zero result:

- Read the current node’s link at offset `0x08`.
- Use that link target as both the next search node and the new candidate.

For a nonzero result:

- Read the current node’s link at offset `0x0C`.
- Use that target as the next search node.
- Leave the candidate unchanged.

Each link read occurs after the comparison dependency returns. A link mutation performed during that call can therefore affect the branch’s next address.

A zero-result branch can set the candidate to zero when its link target is zero. A nonzero-result branch can retain the initially observed header or a candidate established by an earlier zero-result branch.

The next loop condition tests the newly obtained search address. Zero ends traversal without a comparison or link read at address zero.

### Candidate checking

After search termination, the function freshly reads context offset `0xA0` into a local header slot and places the search candidate into a separate local candidate slot.

F-75663d4eabfa receives:

1. The address of the candidate slot.
2. The address of the header slot.

Because these slots are supplied by address, their contents must not be assumed unchanged after the call.

A nonzero return selects the fallback path immediately. Candidate extraction and the subsequent comparison do not occur on that path.

For a zero return, the function passes the then-current candidate-slot value to F-7c8e66f84179. That dependency returns an opaque 32-bit word. The function then invokes F-bcefa5957e76 with:

1. The comparison-state address at context plus `0xA9`.
2. The local comparison-record address.
3. The word returned by F-7c8e66f84179.

This reverses the relative positions of the record and node-related operand compared with search traversal. The extracted word’s interpretation is not established.

A zero result from this second comparison selects the candidate path. Any nonzero result selects fallback, without regard to sign or magnitude.

These branches do not independently establish that the candidate is valid, that the extraction result is a pointer, or that the candidate’s key equals a requested key.

### Selection and sentinel comparison

On the candidate path, selection is obtained from the candidate slot after the conditional dependency calls have completed.

On fallback, the function freshly reads context offset `0xA0` and uses that value as selection.

It then separately reads context offset `0xA0` for the selection-versus-sentinel comparison:

- Equality returns zero without accessing the selected entry’s callback list.
- Inequality enters callback traversal.

The fallback read and sentinel-comparison read are separate observations. The local header slot passed to F-75663d4eabfa is not used as the authoritative sentinel for this later comparison.

Consequently, fallback normally avoids callbacks when the context header remains stable, but fallback alone does not guarantee that result if the separately observed header values differ.

### Callback traversal

For a nonsentinel selection, the accumulator starts at zero.

The function reads the list-sentinel address from selection offset `0x24`, then reads the first-element address from the sentinel’s first word.

Before each potential callback, it rereads the sentinel address from selection offset `0x24` and compares the current element address with it. Equality ends traversal. This includes the first termination comparison after initialization.

For a current element unequal to the freshly read sentinel, the function obtains the receiver from element offset `0x0C`, obtains its dispatch-table address from the receiver’s first word, and dispatches through table offset `0x54`.

The callback receives:

1. The receiver address.
2. The element’s 32-bit word at offset `0x08`.
3. The original third input argument.

The callback’s 32-bit result is combined into the accumulator by bitwise OR.

Only after the callback returns does the function read the current element’s first word to obtain the next-element address. Traversal then repeats the sentinel comparison.

Observable consequences:

- A callback’s change to the current element’s next link affects the subsequent step.
- The sentinel field is reread for every termination comparison.
- Reaching an accumulator of `0xFFFFFFFF` does not stop traversal.
- There is no visible prefetch of the next element before dispatch.
- The current element must remain readable for the post-callback link read.
- A zero element address is not a dedicated callback-list termination condition. It stops traversal only if it equals the sentinel address observed at that comparison.

The accumulated word is returned after normal list termination.

## Acceptance examples

These are conditional criteria derived from static evidence, not executed tests. Each assumes valid accessed memory and normally returning dependencies, with mutation limited to what the example states.

### Zero initial search address

If the header’s initial search-node field contains zero, no search comparison executes and no search-node link is read. Candidate checking still executes.

The context-header and header-node reads have already occurred; this zero value does not make an invalid context or header safe.

### Candidate follows the zero-result link

If a search comparison returns zero and the current node’s `0x08` link names another node, that target becomes both the next search node and candidate.

Keeping the node just compared as the candidate would violate the contract. If the link is zero, both become zero and search terminates. Safe subsequent handling of the zero candidate depends on dependency behavior.

### Stable-header fallback

If F-75663d4eabfa returns nonzero and the context header remains unchanged through fallback selection and sentinel comparison, no extraction, second comparison, or callback occurs. The result is zero.

### Candidate-slot modification

Suppose F-75663d4eabfa changes the candidate slot to a different valid entry and returns zero. F-7c8e66f84179 must receive that replacement value.

If the second comparison returns zero and no later operation changes the slot, selection uses the replacement, not the original search candidate.

### Empty callback list

Suppose the candidate is accepted, differs from the current context header, and has a stable list sentinel whose first word points to itself.

No callback executes. The returned mask is zero.

### Bitmask aggregation without early exit

For three successive callbacks returning `0x00000001`, `0x80000000`, and `0x00000004`, followed by the sentinel, the result is `0x80000005`.

If an earlier callback instead produces `0xFFFFFFFF`, remaining elements are still visited. Saturation of the mask is not a stopping condition.

### Post-callback link mutation

If a callback changes its current element’s next link from one valid element to another, the replacement link determines the next iteration. Prefetching and using the old link would not match the established read order.

### Record mutation and original callback argument

If a comparison dependency changes the record’s second word, later comparisons may observe the changed word. Any later callback still receives the original third input argument, not the modified record word.

### Nonzero final comparison

If extraction occurs but the second comparison returns any nonzero value, selection uses a fresh context-header read. Extraction alone does not accept the candidate.
