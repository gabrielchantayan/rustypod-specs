# F-806b5f1d7132

## Purpose

F-806b5f1d7132 searches a dependency-driven sequence for a candidate whose 32-bit field at byte offset `0x4C` equals the caller’s second argument with bit 31 set.

On the first matching candidate, it performs a two-stage resolution through F-682adfd5a561, with an indirect method invocation between those stages. It then invokes F-d0d3f100effc and returns a 64-bit value containing:

- In bits 63–32: the first 32-bit word of its local traversal state, read after F-d0d3f100effc returns.
- In bits 31–0: the final resolution result, or zero if traversal reports termination before a match.

The roles “search,” “candidate,” “traversal,” and “resolution” describe the visible data flow. The semantic meaning of the objects, identifiers, and dependency-specific constants is not established.

## Interface

### Inputs

The interface has four arguments, each represented by 32 bits:

| Argument | Established use |
|---|---|
| First argument | An integer-valued base used to form an address at byte offset `0xA8`, passed to F-8ca21d3a8cca. |
| Second argument | An unsigned 32-bit value. It initializes the first traversal-state word, supplies the comparison key after setting bit 31, and is passed unchanged to the indirect method. |
| Third argument | An opaque 32-bit value that initializes the second traversal-state word. There is no subsequent direct interpretation of it in this function. |
| Fourth argument | A 32-bit value that initializes a local candidate slot. The slot’s address is passed to F-b38a3aba0e18. |

The second argument remains logically distinct from the mutable traversal-state word initialized from it. Changes to that state word do not change the comparison key or the argument supplied to the indirect method.

### Local storage exposed to dependencies

The supplied representation places three 32-bit local slots consecutively:

| Relative byte offset | Initial contents | Direct use |
|---|---|---|
| `0x00` | Second argument | Start of the state passed to traversal-related dependencies; later supplies the return value’s upper word. |
| `0x04` | Third argument | Adjacent state word; not directly inspected afterward. |
| `0x08` | Fourth argument | Candidate slot whose address is separately passed to F-b38a3aba0e18. |

This layout is static evidence about the supplied representation, not a complete definition of a dependency-owned state structure. In particular, the amount of storage each dependency accesses through the state address is unknown.

### Output

The function returns a 64-bit bit pattern assembled from two 32-bit words.

Let the upper word be the first traversal-state word after the final F-d0d3f100effc call. The lower word is:

- Zero on the traversal-termination path.
- The 32-bit result of the second F-682adfd5a561 invocation on the matching path.

The supplied return type is signed 64-bit. If bit 31 of the upper word is set, the resulting 64-bit bit pattern has its sign bit set. The function does not normalize the upper word into a Boolean or a small status code.

A zero lower word is not sufficient to distinguish traversal termination from a successful matching path: the final resolution dependency can also return zero.

### Preconditions

Normal completion requires all executed dependencies and the indirect method to return normally, and all executed memory accesses to be valid.

In particular:

- The address derived from the first argument plus `0xA8` must satisfy whatever access requirements F-8ca21d3a8cca imposes.
- After a nonzero traversal result, the current candidate must support a readable 32-bit field at offset `0x4C`.
- On a match, the first F-682adfd5a561 result must support the dispatch-pointer reads and the indirect call described below.
- The local storage passed to dependencies must satisfy their actual, undocumented size and alignment requirements.

The function does not enforce these preconditions.

## Behavior

### State preparation and initialization

Before invoking any dependency, the function initializes its local state from the second, third, and fourth arguments as described above.

It then calls F-8ca21d3a8cca with:

1. The address of the first traversal-state word.
2. The address formed from the first argument plus byte offset `0xA8`.

The call’s return value is not used. Its effects on the supplied state or other memory are not established.

The source representation uses 32-bit quantities for the address calculation. It contains no bounds or overflow check. The specification does not infer portable behavior for an invalid address or arithmetic overflow.

### Traversal and matching

After initialization, the function calls F-b38a3aba0e18 with:

1. The traversal-state address.
2. The address of the local candidate slot.

This call occurs at least once. The function does not inspect the initially supplied candidate before the first traversal call.

The traversal result controls the next action:

- **Zero:** traversal terminates immediately. The function does not read the candidate’s field at `0x4C`. It invokes F-d0d3f100effc and returns with a zero lower word.
- **Any nonzero value:** the function reads the current candidate slot, then reads the unsigned 32-bit field at byte offset `0x4C` from that candidate.

There is no distinction between positive and negative nonzero traversal results in the visible branch. If a dependency uses negative values for errors, those values still take the candidate-inspection path.

The candidate field must exactly equal the original second argument with bit 31 set. This is a full 32-bit equality comparison:

- Bits 0–30 retain their original values.
- Bit 31 is forced to one.
- An already-set bit 31 remains set.
- No other masking, range conversion, or normalization occurs.

If the field differs, the function calls F-b38a3aba0e18 again with the same two local addresses. It repeats until a match is found or traversal returns zero.

There is no iteration limit, cycle detection, or cancellation check in this function. A traversal dependency that continually returns nonzero while presenting nonmatching candidates can prevent completion indefinitely.

### Resolution of the first match

For the first matching candidate, the function performs these operations in order:

1. Calls F-682adfd5a561 with the current candidate value and the constant `0x1100`.
2. Treats the returned value as the address of a receiver-like object.
3. Reads the first 32-bit word at that address as a dispatch-table address.
4. Reads a callable entry at byte offset `0xE4` within that table.
5. Invokes that entry with the receiver-like object as its first argument and the original, unmodified second argument as its second argument.
6. Calls F-682adfd5a561 again with the indirect method’s 32-bit result and the constant `0x3B80`.
7. Retains the second resolution result as the prospective lower return word.

The constants `0x1100` and `0x3B80` are distinct opaque selectors. Their meaning is not available.

The indirect method receives the original second argument, not the comparison key with bit 31 forcibly set and not the current first state word.

The function does not continue searching after a match, even if either resolution result or the indirect method result is zero. It performs no explicit success check on those results.

### Final dependency call and return assembly

On both visible normal return paths, the function invokes F-d0d3f100effc with the traversal-state address.

The first state word is read for the upper return word **after** that call returns. Consequently:

- The upper word is not necessarily the original second argument.
- It can reflect changes made during initialization, traversal, or finalization.
- A change made by F-d0d3f100effc is included in the returned upper word.

On the matching path, the lower word comes from the second F-682adfd5a561 result obtained before F-d0d3f100effc. On the termination path, it is zero.

No additional dependency call is visible after F-d0d3f100effc.

## Side effects

### Direct local effects

The function initializes three local words and exposes their addresses to dependencies. The candidate slot may be updated through the address supplied to F-b38a3aba0e18. The traversal state may be modified through the state address supplied to F-8ca21d3a8cca, F-b38a3aba0e18, and F-d0d3f100effc.

The function itself does not directly write to candidate objects or to the receiver-like object. Its explicit object accesses are reads.

### Observable access order

Subject to the dependencies’ internal behavior, the visible sequence is:

1. Initialize local words.
2. Invoke F-8ca21d3a8cca.
3. Invoke F-b38a3aba0e18.
4. Only after a nonzero traversal result, read the current candidate and its field at `0x4C`.
5. Repeat traversal and candidate inspection for nonmatches.
6. On a match, invoke the first resolution, read the dispatch information, invoke the indirect method, and invoke the second resolution.
7. Invoke F-d0d3f100effc.
8. Read the first state word and return the assembled 64-bit value.

A zero traversal result prevents the candidate-field read for that iteration. It also prevents both resolution calls and the indirect method invocation.

### Ownership and lifetime

No explicit allocation, release, retain, or ownership transfer is established by this function alone.

F-d0d3f100effc occupies a finalization-like position, but its name and placement do not prove that it releases resources. Likewise, the resolution dependencies’ returned values cannot be assumed to be owned, borrowed, retained, or newly allocated.

The local state addresses refer to storage whose usable lifetime is bounded by this invocation. The visible function provides no mechanism to extend that lifetime. Whether any dependency retains those addresses is unknown.

### Failure behavior

There is no explicit null check, exception handling, rollback, or error translation.

For example, if the first resolution returns zero, the next visible operation attempts to read dispatch information through that value. If a nonzero traversal result leaves an invalid candidate, the function still attempts the field read.

The finalization call is reached on the two visible normal completion paths. Its execution is not guaranteed if an earlier dependency fails to return, an indirect call is invalid, or an invalid memory access interrupts execution.

## Acceptance examples

These examples are conditional deductions from the supplied static evidence. They are not runtime observations.

### Immediate traversal termination

Assume initialization returns normally, the first traversal call returns zero, and finalization leaves the first state word equal to `0x12345678`.

The returned bit pattern must be `0x1234567800000000`. No candidate-field read, resolution call, or indirect method invocation occurs.

### Exact high-bit comparison

For an original second argument of `0x00000025`, the matching field value is `0x80000025`.

A field of `0x00000025` does not match. A field of `0x80000024` does not match. Either nonmatch causes another traversal call.

If the original argument is already `0x80000025`, the matching field remains `0x80000025`.

### Original argument supplied to the indirect method

Assume the original second argument is `0x00000025`, traversal finds a field equal to `0x80000025`, and earlier dependencies change the first state word to some different value.

The indirect method still receives `0x00000025` as its second argument. Neither the matching field nor the modified state word replaces it.

### Finalization changes the upper word

Assume the second resolution returns `0xAABBCCDD`, and F-d0d3f100effc changes the first state word to `0x11223344`.

The returned bit pattern must be `0x11223344AABBCCDD`, provided all calls and accesses complete normally.

### Zero resolution result does not resume searching

Assume a candidate matches and the second resolution returns zero.

The function invokes F-d0d3f100effc and returns a zero lower word. It does not request another candidate.

### Nonzero traversal status is not independently validated

Assume F-b38a3aba0e18 returns a nonzero value but leaves the candidate slot unchanged.

The function uses the slot’s current value for the field read. It does not require evidence that the dependency wrote a new candidate. If the slot still contains the fourth argument, that value supplies the candidate address.
