# F-5ff4771492d5

## Purpose

F-5ff4771492d5 obtains a 32-bit value from a provider and, unless that value is the sentinel −1, passes it through two operations selected from the caller-supplied object’s dispatch table. The second operation receives both the first operation’s result and an indication of whether the obtained value differs from a stored value. After the second operation returns, the function records the obtained value and returns the second operation’s result.

The sentinel path returns zero without explicitly accessing the caller-supplied object.

**Established behavior:** the function performs conditional dispatch, compares a stored value, updates that stored value, and returns a 32-bit result.

**Inferred intent:** the stored value may represent a previously processed selection or identifier, and the comparison may indicate a change. The evidence does not establish the application-level meaning of the value, the stored field, or either dispatched operation.

## Interface

### Input

The function accepts one pointer, referred to here as the **target object**.

On the non-sentinel path, the target object must support the following accesses in the represented memory model:

| Location | Required interpretation |
|---|---|
| Byte offset 0 | Pointer to a dispatch table |
| Dispatch-table byte offset 0x130 | Callable entry for the first target operation |
| Dispatch-table byte offset 0x134 | Callable entry for the second target operation |
| Object byte offset 0xB8 | Readable and writable 32-bit stored-value field |

The stored-value offset follows from an index of 0x2E into 4-byte integer elements: 46 × 4 = 184 bytes, or 0xB8.

The function performs no explicit null, alignment, lifetime, bounds, or dispatch-entry validation. For normal completion on the non-sentinel path, the relevant storage and callable entries must remain valid whenever accessed.

On the sentinel path, this function does not explicitly dereference the target object. That narrower access behavior is not a general guarantee that an invalid target pointer is acceptable in every surrounding calling context.

### Provider interface

The function calls dependency F-938c950e5046 with no explicit arguments. Its result is treated as a pointer to a provider object whose first word supplies a dispatch-table pointer.

The provider dispatch entry at byte offset 0x168 is then invoked with no explicit arguments shown in the supplied representation. Its result is interpreted as a signed 32-bit integer.

The evidence does not establish whether an underlying calling convention supplies an implicit receiver or other machine-level context. No explicit provider-object argument is visible.

### Output

Normal completion produces one 32-bit result:

- If the provider operation returns −1, the result is zero.
- Otherwise, the result is the 32-bit value returned by the second target operation.

The non-sentinel result is not interpreted or checked. A zero result therefore does not uniquely identify the sentinel path.

The supplied representation supports 4-byte integer elements and 32-bit opaque intermediate and return values. Its dispatch layout is consistent with 4-byte function-pointer entries.

The sentinel comparison is against signed 32-bit −1, corresponding to the all-ones 32-bit representation. Other provider values, including other negative values, take the non-sentinel path.

The stored-value comparison is an equality comparison between 32-bit integer values. The function does not increment, scale, mask, or otherwise arithmetically transform the provider result.

## Behavior

### Provider lookup and query

The function first invokes F-938c950e5046. It then obtains the returned object’s dispatch-table pointer and invokes the entry at byte offset 0x168.

These operations precede any explicit access to the target object.

There is no explicit check that F-938c950e5046 returned a non-null provider object, that its dispatch table exists, or that the selected entry is callable. Validity of those accesses is a precondition for the represented execution to continue normally.

The provider operation’s returned integer becomes the **queried value** used throughout the remainder of this invocation. Later callbacks do not cause the function to query the provider again.

### Sentinel path

If the queried value is −1:

- Neither target operation is invoked.
- The target object’s stored-value field is not explicitly read or written.
- The function returns the 32-bit value zero.

F-938c950e5046 and the provider operation have already executed. Their effects are not undone.

### First target operation

For every queried value other than −1, the function resolves the target object’s dispatch entry at byte offset 0x130 and calls it with two explicit arguments, in order:

1. The target-object pointer.
2. The queried value.

Its 32-bit return value is retained as an opaque intermediate result. The function does not interpret it as a success flag, error code, pointer, count, or ownership-bearing handle.

The first target operation executes before the stored-value comparison used by the second target operation. Consequently, any change it makes to the stored-value field can affect that comparison.

### Second target operation

After the first target operation returns, the function resolves the target object’s dispatch entry at byte offset 0x134 and calls it with three explicit arguments, in order:

1. The target-object pointer.
2. The first target operation’s 32-bit result.
3. A Boolean-valued indication that the target object’s current stored value differs from the queried value.

The third argument is false when the values are equal and true when they differ. The exact ABI width or extension of that Boolean argument is not independently established.

The comparison is not a comparison against a value saved at function entry. It uses the stored field after the first target operation has returned.

The second dispatch operation is also expressed through the target object after the first operation returns. The function does not establish a contract that both target calls must use the dispatch table present before the first call. If the first call changes the target’s dispatch pointer, subsequent dispatch uses the target state available at that later point.

The evidence establishes that the first operation completes before the second operation is invoked. It does not establish a finer ordering between the second operation’s dispatch-table reads and evaluation of its comparison argument.

### Final state update and return

After the second target operation returns normally, the function writes the queried value into the target object’s stored-value field at byte offset 0xB8.

It then returns the second operation’s 32-bit result.

The final write occurs regardless of that result’s bit pattern. In particular, a zero or apparently error-like result does not suppress the write.

The function does not use the second operation’s result to update the field. It writes the original queried value. If the second operation changed the field, this final write replaces that change, provided the object remains valid and execution reaches the write.

## Acceptance examples

These are conditional contract examples derived from static evidence, not executed tests. Each assumes valid accesses and normal returns unless otherwise stated.

### Sentinel result

Given a provider operation returning −1, the function returns zero and makes neither target dispatch call. It performs no explicit target-field access, regardless of the field’s prior contents.

This example does not imply that the provider calls have no side effects.

### Equal stored value

Given a queried value of 17, and assuming the first target operation leaves the stored field equal to 17:

- The first target operation receives the target pointer and 17.
- The second receives the first operation’s result and a false inequality indication.
- After the second returns, the stored field is written with 17.
- The second operation’s result is returned unchanged.

### Different stored value

Given a queried value of 17 and a stored value of 9 when the comparison is evaluated, the second operation receives a true inequality indication. After normal completion, the stored field contains 17.

### First operation changes the comparison

Given a queried value of 17 and an initial stored value of 9, if the first target operation changes the field to 17, the second operation receives false.

Conversely, if the field initially equals 17 but the first operation changes it to 9, the second operation receives true.

### Second operation changes the field

Given a queried value of 17, if the second operation writes 99 into the stored field and returns normally, this function subsequently overwrites the field with 17.

### Zero final result

If the queried value is not −1 and the second target operation returns zero, both target operations still execute and the final field update still occurs. The public return value is zero.

### Other negative value

A queried value of −2 is not the sentinel. It is passed to the first target operation, participates in the stored-value comparison, and is written into the field after the second operation returns normally.
