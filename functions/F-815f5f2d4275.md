# F-815f5f2d4275

## Purpose

F-815f5f2d4275 obtains access to bytes through two dependencies, checks an eight-byte header and a table of four-byte entries, and conditionally installs state in a caller-supplied object.

The established behavior is structural validation and state installation. The application-level format, the meaning of the table entries, and ownership of the backing storage are not established.

The function returns a 32-bit status:

- **0** on the explicit success path.
- **8** on every explicit failure path.

Dependency error values are not forwarded.

This contract is based solely on the supplied static body. No runtime tests have been performed.

## Interface

### Arguments and result

| Argument | Width | Established use |
|---|---:|---|
| Object address | 32 bits | Identifies the object containing the state region |
| Operation token | 32 bits | Forwarded to acquisition, preparation, and late-rejection cleanup |
| Unused argument | 32 bits | Neither read nor forwarded by this body |
| Initial extent | Unsigned 32 bits | Initializes a mutable local extent slot before the first external call |

The result is a 32-bit status value.

The acquisition dependency receives the address of the local extent slot. Preparation receives an extent value, not that address. Nevertheless, the supplied contracts do not prevent acquisition from retaining the address or preparation from changing the slot through retained access. The extent used after preparation is therefore not necessarily the extent reported immediately after acquisition.

### Object state layout

The function passes the address of a 24-byte region beginning at object offset `0x2F0` to an external operation. Its explicit field accesses are:

| Object offset | Width | Established use |
|---|---:|---|
| `0x2F0` | 32 bits | Base-address slot passed to preparation and cleanup; subsequently read for parsing and address calculations |
| `0x2F4` | 32 bits | Base plus the extent-slot value read after preparation, modulo \(2^{32}\) |
| `0x2F8` | 32 bits | Base plus the declared boundary, modulo \(2^{32}\); later read for final comparison |
| `0x2FC` | 32 bits | Extent-slot value read during candidate installation minus the declared boundary, modulo \(2^{32}\) |
| `0x300` | 32 bits | Zero-extended header count; subsequently read back for table traversal |
| `0x304` | 8 bits | Written with 1 on success |
| `0x305`–`0x307` | 3 bytes | No explicit individual accesses; within the externally operated region |

These are explicit uses by this function, not guarantees about the effects of dependencies.

### Input-byte layout

After preparation succeeds, the address obtained from the base slot is interpreted as follows:

| Relative byte offset | Width | Interpretation |
|---|---:|---|
| 0 | 2 bytes | Big-endian unsigned discriminator |
| 2 | 2 bytes | Big-endian unsigned entry count |
| 4 | 4 bytes | Big-endian unsigned declared boundary |
| 8 onward | 4 bytes per entry | Entry table |

The discriminator must equal **1**.

Within each table entry, only bytes at entry-relative offsets 2 and 3 are explicitly read. Together they form a big-endian unsigned 16-bit contribution. The first two entry bytes are not explicitly read.

### Preconditions and limits

The body contains no explicit null checks, memory-accessibility checks, or allocation-size verification. Defined execution requires readable and writable memory for the accesses actually performed, including the object fields, local slot, header, and traversed table bytes.

A reported extent is an integer used in arithmetic and comparisons. It does not itself establish accessible storage.

Non-overlap between object state and backing bytes is a prerequisite for the ordinary interpretation that state installation does not modify the bytes being parsed. The body does not enforce this. It also does not establish synchronization against concurrent mutation.

## Behavior

### Initial operation and acquisition

The local extent slot is initialized from the fourth argument before the initial external operation.

The function then invokes an unmapped external region operation with:

- The address of the object region beginning at `0x2F0`.
- The numeric extent **24**.

Its semantics are unknown. Clearing or resetting the region is a possible interpretation, not an established effect.

**After this operation returns**, the function reads a value from static storage for the acquisition call. The body does not establish that this storage is immutable, that the initial operation preserves it, or that successive invocations observe the same value.

F-7b578d970f16 receives:

1. The object address.
2. The value read from static storage after the initial operation.
3. The operation token.
4. The address of the mutable local extent slot.

The static-storage value is an opaque argument, not an established constant.

If acquisition returns nonzero, the function returns **8**. It does not call preparation, late-rejection cleanup, or the region operation again.

If acquisition returns zero, the function reads the extent slot and requires its unsigned value to exceed **7**. A value from 0 through 7 causes the same early return of **8**.

### Preparation and subsequent extent reads

When acquisition succeeds and the extent gate passes, F-977b73bb902a receives:

- The operation token.
- The extent-slot value read for this call, passed by value.
- The address of the object’s base slot at `0x2F0`.

A nonzero preparation result causes an immediate return of **8**, without late-rejection cleanup or a second region operation.

A zero result permits parsing. Preparation is an external-call boundary: preservation of the local extent slot is not established. In particular, acquisition has already received the slot’s address, and no supplied dependency contract rules out retained access to it.

Following successful preparation, the function performs distinct extent-slot reads for:

1. The end-address calculation.
2. The later boundary-admission comparison, if reached.
3. The remaining-extent calculation, if reached.

These uses must be described by the slot’s value at the relevant read. They cannot unconditionally be identified with the value that passed the pre-preparation gate or the value passed into preparation.

The first explicit post-preparation state write is:

\[
\text{end address}
=
(\text{base read for this calculation}
+\text{extent read for this calculation})\bmod 2^{32}.
\]

It is written to `0x2F4` before header validation. The base slot is then read again to obtain the address used for header parsing.

### Header reads and admission

The function assembles the count and declared boundary before testing the discriminator.

- The count is an unsigned 16-bit quantity zero-extended to 32 bits.
- The boundary is an unsigned 32-bit quantity.
- All header assembly is big-endian.

Admission requires the following conditions, with later conditions reached only when earlier conditions pass:

1. The discriminator equals **1**.
2. The boundary exceeds **7**.
3. The count does not exceed the table capacity:
   \[
   \text{count}\leq
   \left\lfloor\frac{\text{boundary}-8}{4}\right\rfloor.
   \]
4. The extent-slot value read for this comparison satisfies:
   \[
   \text{extent at comparison}
   \geq
   ((\text{boundary}+1)\bmod 2^{32}).
   \]

The capacity calculation uses unsigned subtraction followed by a right shift of two bits. Its subtraction cannot underflow on this path because the boundary has already been required to exceed 7.

The increment in the fourth condition wraps at 32 bits. For boundaries below `0xFFFFFFFF`, the condition requires an extent at least one greater than the boundary. For boundary `0xFFFFFFFF`, the comparison threshold is zero, so every unsigned extent satisfies this particular condition.

There is no new requirement after preparation that the extent slot still exceed 7.

### Candidate state installation

After header admission, the function writes these fields in order:

1. Count at `0x300`.
2. Remaining extent at `0x2FC`, calculated as:
   \[
   (\text{extent read for this write}-\text{boundary})\bmod 2^{32}.
   \]
3. Boundary address at `0x2F8`, calculated as:
   \[
   (\text{base read for this write}+\text{boundary})\bmod 2^{32}.
   \]

The remaining-extent calculation reads the slot again; it does not use an established snapshot from acquisition or from the admission comparison.

These writes precede final validation. They are candidate state and do not imply that the function will return success.

The function then reads the count field back from the object and reads the base slot again to establish the table start. It does not exclusively reuse its earlier header count and base values.

### Table calculation

Under ordinary, non-interfering execution, the reloaded count is the zero-extended count just installed. Table traversal proceeds through that many entries in ascending address order, advancing four bytes per entry.

The initial computed endpoint is:

\[
(\text{table base}+8+4\times\text{reloaded count})\bmod 2^{32}.
\]

For each entry, the function reads its final two bytes, assembles an unsigned 16-bit contribution, multiplies it by **10**, and adds that product to the endpoint with 32-bit wrapping arithmetic.

Thus, when the reloaded count and backing bytes remain stable:

\[
\text{computed endpoint}
=
\left(
\text{table base}+8+4\times\text{count}
+10\sum_{i=0}^{\text{count}-1}\text{contribution}_i
\right)\bmod 2^{32}.
\]

Each product is at most **655,350**, so the individual multiplication fits in 32 bits. The accumulated endpoint can wrap.

For count zero, no entry bytes are read and the endpoint is the table base plus 8, modulo \(2^{32}\).

No additional data represented by the contributions is explicitly read. The contributions affect only the endpoint calculation.

### Final result and late rejection

The computed endpoint is compared, as an unsigned 32-bit value, with the value read from object offset `0x2F8`.

If the endpoint is less than or equal to that stored boundary address:

1. The byte at `0x304` is written with **1**.
2. The function returns **0**.

No explicit cleanup call occurs on success.

If any header admission condition fails, or the final endpoint comparison fails after successful preparation:

1. F-840cb7b3952f receives the operation token and the address of the base slot.
2. The external region operation is called again with the state-region address and extent 24.
3. The function returns **8**.

There is no explicit overflow rejection. The final comparison concerns wrapped address values; it is not a general proof that the represented structure fits within an allocation.

## Side effects

The established sequence is:

1. Initialize the local extent slot.
2. Invoke the initial region operation.
3. Read the static-storage acquisition argument.
4. Invoke acquisition.
5. Conditionally test the extent and invoke preparation.
6. After successful preparation, read the extent for the end calculation and write the end field.
7. Read header bytes.
8. Conditionally read the extent for boundary admission.
9. Conditionally install candidate fields, including another extent read.
10. Read back count and base, then traverse the table.
11. Either write the success marker, or invoke cleanup followed by the second region operation.
12. Return status.

Within a multi-byte expression, the evidence identifies the bytes contributing to the value but does not establish a portable total order for all individual byte reads. Likewise, an arithmetic expression using both a base read and an extent read does not establish their relative read order.

Failure is not transactional. Early failures retain whatever effects the initial operation and preceding dependencies produced. Late failures occur after the end-field write and may occur after all candidate fields were written. Their eventual contents depend on cleanup and the second region operation.

No allocation, release, ownership transfer, or preservation of unrelated state is independently established. Passing the local extent slot’s address permits access during the call; it does not establish a valid lifetime beyond the function’s return.

If backing bytes overlap object fields, earlier writes can change later input reads. No complete input snapshot or anti-aliasing protection is present.

## Acceptance examples

- Dependencies return normally and acquisition and preparation return zero.
- Memory is accessible and object state does not overlap backing bytes.
- Base and relevant state remain stable during parsing.
- The extent slot retains the stated value across preparation and subsequent reads.
- Address arithmetic does not wrap.
- The discriminator is 1.

With count 0 and boundary 8, the end field becomes base plus 8, then boundary admission fails.

Expected result: **8**, with cleanup and the second region operation. Treating the acquisition-reported value as preserved would predict the wrong result.
