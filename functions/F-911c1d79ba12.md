# F-911c1d79ba12

## Purpose

F-911c1d79ba12 processes an event against a caller-supplied state object. It resolves an associated object, queries its status, and selects either a restricted notification path or a field-population path. The latter can update presentation state, dispatch flag-controlled dependencies, and perform an event-specific reset.

**Established behavior:** Every explicitly represented normal return produces the 32-bit value `1`. This return value does not distinguish notification, field population, flag dispatch, or reset.

**Inferred intent:** The five embedded fields appear to contain presentation text, and the shared object appears to control its display. Those meanings are not required to describe the observed calls and memory accesses.

This contract is based on static evidence only. Unknown dependency behavior, fixed-data contents, and reconstruction details remain unresolved.

## Interface

### Inputs and layouts

The function receives two 32-bit machine-word inputs used as addresses:

- **State address:** Identifies storage containing a flag word and five embedded field destinations.
- **Event address:** Identifies storage containing an event code and a lookup argument.

The reached portions of these objects must support the accesses below.

| Event byte offset | Width | Use |
|---|---:|---|
| `+0x08` | 32 bits | Event code retained before the first dependency call |
| `+0x0c` | 32 bits | Argument supplied to the associated-object lookup |

| State byte offset | Access | Use |
|---|---|---|
| `+0x18` | 32-bit read or write | Stored flags |
| `+0x1c` | Address passed to helpers | First field destination |
| `+0x20` | 32-bit pointer read | Pointer whose first byte controls a presentation branch |
| `+0x24` | Address passed to helpers | Second field destination |
| `+0x2c` | Address passed to helpers | Third field destination |
| `+0x34` | Address passed to helpers | Formatted field destination |
| `+0x3c` | Address passed to helpers | Fourth directly populated field destination |

The pointer at `+0x20` lies within the region beginning at `+0x1c`. Its relationship to that field’s internal representation is not established. Field sizes, capacities, and complete layouts are unknown.

### Shared presentation lookup

After field population, the function reads a global pointer value once and retains that value as a **handle address**. The handle address is not the root-object address.

Each subsequent presentation-object lookup follows this chain:

1. Read a 32-bit root-object address from memory at the retained handle address.
2. Read a 32-bit presentation-object address from root-object offset `+0x440`.
3. Use the presentation object’s method table for the required indirect call.

Thus, a dependency can change the object selected by a later lookup either by replacing the root address stored through the retained handle or by changing a root object’s `+0x440` entry. Changing the original global pointer slot after capture does not, by itself, replace the retained handle value.

The final reset separately resolves the indirect method target and receiver through this chain. Their operand-read order is not established.

### Output, widths, and preconditions

On normal completion, the function returns the 32-bit value `1`.

Event codes, status comparisons, flag values, pointers, and pointer-bearing layout entries are represented at 32-bit width. Method-table offsets and object offsets are byte offsets.

The relevant masks are `0x00000002` and `0x00000200`. Payload offsets `+0x40`, `+0x41`, and `+0x42` identify individual bytes. The byte at `+0x42` is explicitly zero-extended into a 32-bit outgoing argument slot; the other two bytes’ signedness and argument promotion are not established.

The recognized event representations are `0x00010002`, `0x00010005`, and `0x00010008`. Two comparisons are expressed using subtraction of `0x00010000`. The recognized values do not require overflowing subtraction; original source-language overflow semantics for other inputs are not established.

No input-validation or error-return path is represented. Normal completion requires valid addresses, method tables, and call targets wherever the selected path reaches them. No bounds or address-wrap checks are represented.

## Behavior

### 1. Capture the event and resolve an associated object

The function first reads and retains the event code from event offset `+0x08`.

It then calls F-120cb3bb1627. Using the returned object, it invokes the method-table entry at byte offset `+0x24`, passing the 32-bit value read from event offset `+0x0c`.

The lookup argument is therefore not established to be a snapshot taken before F-120cb3bb1627. That dependency may affect reachable event storage.

The lookup result becomes the associated object. Its method-table entry at `+0x10` is invoked to obtain a status value. No null checks are represented for these objects or method tables.

### 2. Restrict processing when status is neither 0 nor 8

For any status other than `0` or `8`:

- If the retained event code is `0x00010005` or `0x00010008`, call F-3f15dcbf790f, then invoke the returned object’s method-table entry at `+0xfc` with explicit arguments `1`, `0`, and `0`.
- For every other event code, omit that notification.
- Return `1`.

This path does not explicitly query flags or payload, populate the five fields, capture the shared handle, dispatch flag-controlled dependencies, or perform the final reset.

These omissions describe this function’s direct behavior, not an absence of side effects in its dependencies.

### 3. Obtain a flag candidate and payload

For status `0` or `8`, invoke these associated-object methods in order:

1. Method-table entry `+0x00`, obtaining a 32-bit flag candidate.
2. Method-table entry `+0x1c`, obtaining a payload address or zero.

The flag candidate is retained across the subsequent calls. The flag-producing method is not queried again.

### 4. Populate the five fields

The destination order is:

1. State `+0x1c`
2. State `+0x24`
3. State `+0x2c`
4. State `+0x3c`
5. State `+0x34`

The last two destinations are deliberately not in ascending address order.

**Zero payload:** Call F-438680ffebfe for each destination in that order, supplying the same fixed data address as the second argument on every call. The fixed data’s contents are unavailable. “Clear” and “assign an empty string” are therefore not established semantics.

**Nonzero payload:** Perform the following operations in order:

- Call F-151ab4bfe553 for state `+0x1c`, supplying the payload address.
- Call it for state `+0x24`, supplying payload `+0x64`.
- Call it for state `+0x2c`, supplying payload `+0xa4`.
- Call it for state `+0x3c`, supplying payload `+0xe4`.
- Read the byte at payload `+0x42` and place its zero-extended value in a 32-bit outgoing stack argument slot.
- Invoke F-95f1655a5c87 with a temporary stack-buffer address, fixed format-data address, and byte values read from payload `+0x40` and `+0x41`.
- Call F-151ab4bfe553 for state `+0x34`, supplying the temporary buffer address.

The explicit outgoing slot is consistent with the `+0x42` byte being an additional formatting argument, but the complete formatting signature is not established.

All three formatting-byte reads occur after the first four field-helper calls. The `+0x42` read precedes the formatting call; no relative evaluation order is established between the reads at `+0x40` and `+0x41`. Unknown helper effects prevent treating these values as a payload snapshot from function entry.

The format contents, result representation, buffer capacity, termination rules, and maximum output length are unknown. No formatting bounds check is represented at this call site.

### 5. Capture the shared handle and select effective flags

After all five field-helper calls, read the shared global pointer value once and retain it as the handle address described in the interface.

If the flag candidate is zero:

- Read the 32-bit stored flags at state `+0x18`.
- Retain that value as the effective flags.
- Skip the candidate-driven presentation operations below.

A zero candidate therefore means reuse the stored flags as they exist after field population, not replace them with zero. Field-helper effects may influence that later read.

If the candidate is nonzero:

1. Write the candidate to state `+0x18`.
2. Read the pointer at state `+0x20`.
3. If nonzero, read its first byte.
4. Resolve a presentation object by reading the current root address through the retained handle, then reading root `+0x440`.

If the field pointer is zero or its first byte is zero, invoke presentation method `+0x78` with arguments `0`, `1`.

Otherwise:

1. Invoke presentation method `+0x78` with arguments `1`, `0`.
2. Resolve the presentation object again: reread the root address through the retained handle, then read that root’s `+0x440` entry.
3. Invoke the newly resolved object’s method `+0x84`.

The second call supplies these arguments in order:

- State `+0x1c`
- State `+0x24`
- State `+0x2c`
- State `+0x3c`
- State `+0x34`
- Constant `1`

The last three arguments are represented through outgoing stack slots.

The fresh lookup after `+0x78` is significant. That call may replace the root address stored through the retained handle; the subsequent `+0x84` call is not bound to either the earlier root or the earlier presentation object.

For a nonzero candidate, the retained candidate is the effective flag value even if presentation dependencies subsequently modify state `+0x18`.

### 6. Dispatch flag-controlled dependencies

Using the retained effective flags:

- If mask `0x00000002` is set, call F-2e773677b682 with the state address and retained event code.
- Then, if mask `0x00000200` is set, call F-7c5fbbfd2d2b with the same arguments.

When both bits are set, F-2e773677b682 runs first. Its changes to stored flags do not, by themselves, change the retained-bit test controlling the second call.

Other flag bits have no additional explicit dispatch effect here.

### 7. Perform the event-specific reset

After flag dispatch, event `0x00010005` or `0x00010002` causes:

1. A 32-bit zero write to state `+0x18`.
2. An indirect presentation call at method-table offset `+0x78`, with arguments `0`, `1`.

For this final call, the method target and receiver are separately resolved through the retained handle: each chain reads the current root address through that handle and then reads root `+0x440`. The method-target chain additionally accesses the selected object’s method table.

Do not collapse these operand resolutions into one cached presentation-object read or assert an evaluation order between them. The representation does not establish that order. Under intervening external mutation, it also does not establish that the two resolutions observe the same object.

These are fresh reads after flag-controlled dispatch. A dispatch dependency may have replaced the root address through the retained handle, not merely modified the old root’s presentation-object entry.

The function then returns `1`. The restricted-status path never reaches this reset.

## Side effects

Directly established effects include:

- Event-field reads and indirect object-method calls.
- Passing five embedded state-field addresses to helpers.
- Payload-byte reads and passing payload-relative addresses to helpers.
- Use of temporary stack storage for formatting.
- Conditional reads and writes of state `+0x18`.
- Conditional reading of state `+0x20` and its first pointed-to byte.
- One capture of the global handle value, followed by fresh reads through that retained handle where presentation operations require them.
- Ordered flag-controlled calls and conditional reset.

There is no explicit allocation, deallocation, ownership transfer, or reference-count operation in the represented body. Dependencies may perform such operations; none is assumed to copy, retain, own, or release its arguments.

The temporary formatting buffer has no visible lifetime extension beyond this invocation. Whether a helper copies its contents or retains its address is unresolved. Safe later use of any retained address would require a lifetime arrangement not established here.

No rollback is represented. Earlier writes and calls remain observable if a later dependency faults, fails, or does not return.

No synchronization or snapshot mechanism is represented. Dependencies may alter reachable memory, including the root address stored through the retained handle.

## Acceptance examples

These are conditional acceptance examples, not executed tests. They assume valid reached addresses and normally returning dependencies.

1. **Restricted status excludes reset.** With status `3` and event `0x00010002`, return `1` without direct field population, flag dispatch, shared-handle capture, or reset.

2. **Restricted notification.** With status `3` and event `0x00010008`, obtain the notification object and invoke its `+0xfc` method with `1, 0, 0`, then return `1`.

3. **Zero payload, reused flags.** With status `0`, zero payload, and zero candidate, make the five F-438680ffebfe calls in destination order. Capture the handle and read stored flags afterward. Skip candidate-driven presentation.

4. **Retained dispatch decision.** With effective flags `0x202`, call F-2e773677b682 before F-7c5fbbfd2d2b. The first dependency clearing stored flags does not cancel the second invocation.

5. **Absent field pointer.** With a nonzero candidate and a subsequently observed zero pointer at state `+0x20`, store the candidate and invoke presentation `+0x78` with `0, 1`. Do not dereference that zero pointer or invoke `+0x84` through this branch.

6. **Root replacement between presentation calls.** Suppose the first field is nonempty and `+0x78(1, 0)` replaces the root address stored through the retained handle. The subsequent `+0x84` lookup reads that replacement root and its `+0x440` entry rather than reusing the earlier root.

7. **Root replacement before reset.** With status `8`, effective flags `0x202`, and event `0x00010005`, dispatch both dependencies first, then write zero to stored flags. The final call resolves its operands through the retained handle after dispatch, observing a replacement root if the relevant reads see it.

8. **Global-slot replacement differs from root replacement.** If a dependency changes only the global pointer slot from which the handle was captured, later lookups still use the captured handle. They do not recapture that global slot.

9. **Final operand resolution is not a snapshot.** If external mutation occurs between the final call’s separate target and receiver resolutions, acceptance does not require matching objects or a particular read order.

10. **Event distinction.** For status `0` or `8`, event `0x00010008` does not trigger the final reset. Its notification significance applies only on the restricted path.
