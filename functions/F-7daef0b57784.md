# F-7daef0b57784

## Purpose

F-7daef0b57784 decodes two byte-sized selectors carried in separate 32-bit arguments and writes the corresponding 32-bit values into two fields of a caller-supplied object.

Processing is ordered and nontransactional. The first selector is validated and its destination written before the second selector is examined. An invalid second selector therefore leaves the first write in place. An invalid first selector prevents both destination writes.

The function returns a 64-bit result containing the original object-address argument in its upper 32 bits and a status value in its lower 32 bits. The lower half is zero on success and `0xFFFFFFCE` on an invalid selector.

The object’s broader purpose and the meanings of the selector values are not established. Interpreting these fields as flags, modes, or hardware settings would be inferred intent, not an established contract.

## Interface

### Inputs

The function accepts three arguments:

| Argument | Width | Established role |
|---|---:|---|
| Object address | 32 bits | Base address used to locate two destination fields; also returned in the upper half of the result. |
| First selector container | 32 bits | Supplies the byte that selects the first destination value. |
| Second selector container | 32 bits | Supplies the byte that selects the second destination value. |

Each selector container is copied into separate local 32-bit storage. The selector is the byte at the lowest address of that local storage. The other three bytes are not consulted when decoding that selector.

The supplied evidence does not independently establish target byte order:

- On a little-endian target, the selector is bits 7–0 of its container.
- On a big-endian target, the selector is bits 31–24.

It would therefore be stronger than the evidence to specify unconditional numeric truncation to the least significant byte.

### Destination layout

The two destination fields are addressed relative to the object-address argument:

| Field | Byte offset | Write width |
|---|---:|---:|
| First destination | `0xE30` | 32 bits |
| Second destination | `0xE34` | 32 bits |

These are adjacent four-byte fields. The function does not read their previous contents.

The address calculations use the 32-bit object-address value. At the integer-expression level, adding either offset wraps modulo \(2^{32}\). This does not establish that a wrapped address is valid or that accessing it is supported.

### Return value

The result is 64 bits wide and has this logical layout:

| Bits | Meaning |
|---|---|
| 63–32 | Original 32-bit object-address argument |
| 31–0 | Status word |

The established status words are:

- `0x00000000`: both selectors were recognized and both destination stores were reached.
- `0xFFFFFFCE`: an unrecognized selector was encountered.

The failure status has the signed 32-bit interpretation −50. That does not mean the entire 64-bit return value is the signed integer −50; its upper half contains the object address.

### Preconditions and ownership

For normal completion, every destination reached by processing must support a 32-bit store. Required alignment, access permissions, and platform-specific behavior for invalid addresses are not established.

There is no explicit null check, bounds check, object-size check, or alignment check. A zero object address is not rejected merely for being zero.

No allocation, deallocation, ownership transfer, or object-lifetime change is visible. The caller must provide usable destination storage when a recognized selector causes a store. The required extent of usable storage depends on how far processing proceeds.

## Behavior

### Shared-value preparation

Before either selector is dispatched, the function obtains values from an external 32-bit shared word.

Two values are prepared:

1. A captured value used by selector 1.
2. A derived value used by selector 7.

The derived value is expressed as a bitwise AND between the shared word and a combination of that word shifted right by 19 bits and left by 13 bits. The two shifted terms are combined by bitwise OR. All operations are 32-bit unsigned operations; the right shift is logical, and bits shifted beyond the left edge are discarded.

If all shared-word references involved in this computation observe the same value \(G\), the derived result is:

\(G \mathbin{\&} \operatorname{rotateRight}_{32}(G,19)\).

Equivalently, the rotation is left by 13 bits.

This simplification is conditional. The initial capture and the later derived expression are separate uses of the shared word. The supplied representation also refers to that word multiple times within the derived expression. It does not establish a coherent snapshot across those references, an exact machine-load count, or an evaluation order among the operands of that expression.

Both prepared values are computed before selector validation, including when the first selector is invalid or neither selector uses a shared-derived value.

### Selector mapping

Both selector positions use the same mapping:

| Selector byte | 32-bit destination value |
|---:|---|
| 0 | `0x00000000` |
| 1 | Initially captured shared value |
| 2 | `0x00000062` |
| 3 | `0x00000002` |
| 4 | `0x00000020` |
| 5 | `0x00000040` |
| 6 | `0x00000021` |
| 7 | Prepared derived value |
| 8 | `0x00008000` |
| 9–255 | Invalid; no destination store for that selector |

The table describes full-width assignments. Values are not ORed into existing destination contents, and no destination bits are preserved.

### Ordered processing

The externally significant sequence is:

1. Prepare the shared-derived values.
2. Read the first selector byte from its local container.
3. If the first selector is invalid, return the failure result without writing either destination.
4. Otherwise, write its mapped 32-bit value to the first destination.
5. Read the second selector byte from its local container.
6. If the second selector is invalid, return the failure result without writing the second destination or undoing the first write.
7. Otherwise, write its mapped 32-bit value to the second destination and return success.

There are exactly two selector positions. No third selector is consumed, no sentinel is sought, and selector zero is a valid value rather than a terminator.

The first destination store precedes the second selector read in the supplied representation. The second destination store, if reached, follows the first store. This ordering does not by itself establish concurrency synchronization, hardware memory barriers, or atomic multi-field publication.

### Error behavior

An invalid selector causes the explicit failure return described above. There is no separate reported status for different invalid byte values.

The function does not provide an explicit error return for inaccessible shared storage, inaccessible destination storage, or a faulting 32-bit store. Such conditions fall outside the demonstrated normal-return behavior.

Failure is not atomic:

- Invalid first selector: neither destination is written.
- Valid first selector and invalid second selector: only the first destination is written.
- Two valid selectors: both destinations are written, in order.

## Side effects

The established nonlocal accesses are reads of the shared word and conditional 32-bit writes to the destination fields.

The original selector arguments are passed by value. Their local copies are used to extract selector bytes; there is no caller-provided selector buffer that the function modifies.

Only the two specified destination fields are explicitly written. Other object bytes are not explicitly accessed. No explicit shared-word write, allocation, release, callback, I/O operation, or dependency invocation appears.

The shared-value preparation precedes the destination stores. The second selector therefore does not trigger a new shared-value computation after the first destination write. Both selector positions use the values prepared at entry.

If the object address causes a destination to alias other meaningful storage, the write still follows the same address calculation. In particular, the function contains no explicit protection against a destination aliasing the shared word. The resulting broader effects depend on the actual memory layout and are not established here.

## Dependencies

No called-function dependency is visible. No additional opaque function ID is needed for this contract.

- An external 32-bit shared word supplies selector-1 and selector-7 values.
- Target byte order determines which numeric byte of each selector container is read.
- The address space and access rules determine whether the two calculated destinations support the required stores.

No preservation or ownership guarantee is inferred from an unknown callee, because no callee is present in the supplied body.

## Acceptance examples

These examples are conditional specifications, not runtime observations. Each selector byte means the byte at the lowest address of its local 32-bit container. Destination stores are assumed valid unless stated otherwise.

### Two constant mappings

Given first selector 2 and second selector 8:

- The first destination receives `0x00000062`.
- The second destination receives `0x00008000`.
- The first store precedes the second.
- The return’s upper half is the original object address.
- The return’s lower half is zero.

The previous destination contents do not affect either result.

### Invalid first selector

Given first selector 9 and any second selector:

- Neither destination is written.
- The second selector is not dispatched.
- The return’s lower half is `0xFFFFFFCE`.
- Shared-value preparation has already occurred.

This case does not require a destination store, but it still relies on the shared-state preparation completing.

### Invalid second selector after a valid first selector

Given first selector 6 and second selector 255:

- The first destination receives `0x00000021`.
- The second destination is not written.
- The return’s lower half is `0xFFFFFFCE`.
- The first destination is not restored to its prior value.

### Stable shared value

If every relevant shared-word reference observes `0x00080001`, the prepared derived value is `0x00000001`: rotating that shared value right by 19 bits produces `0x00002001`, whose bitwise AND with the original value is 1.

With first selector 1 and second selector 7:

- The first destination receives `0x00080001`.
- The second destination receives `0x00000001`.
- The status is success.

This example requires stable observations; it does not establish synchronization.

### Zero is a normal selector

Given both selectors equal zero:

- Both destination fields receive a full 32-bit zero.
- Both stores occur.
- The status is success.

Neither zero selector terminates processing early.

### Container bytes not selected

For a fixed target byte order, changing only the three container bytes that are not read must not change selector decoding.

For example, on a little-endian target, numeric containers `0xAABBCC02` and `0x11223302` both select value `0x00000062`. That numeric example does not apply unconditionally to a big-endian target.

## Uncertainties

The following remain **documented_only**:

- Target byte order.
- Exact machine-level shared-word load count and operand-read ordering.
- Whether the shared word can change asynchronously, and whether any synchronization exists outside this function.
- Semantic names, units, or meanings for the shared word and destination fields.
- Object allocation size, provenance, lifetime, and alignment guarantees.
- Behavior of invalid, wrapped, unaligned, or memory-mapped destination addresses.
- Atomicity of individual 32-bit accesses and visibility to concurrent observers.
- The physical calling-convention representation of the 64-bit return value.
- Whether callers interpret the low status word as signed, unsigned, or part of a larger packed result.

A likely intent is to configure two fields from a compact selector vocabulary. That interpretation is not needed for conformance and is not promoted to established behavior.

## Evidence

This contract is based solely on static inspection of the supplied function representation.

Established static evidence includes the three argument widths, two local selector containers, byte-based dispatch, complete selector mapping, destination offsets, 32-bit stores, ordered partial-update behavior, shared-value expressions, and 64-bit return construction.
