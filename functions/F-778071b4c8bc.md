# F-778071b4c8bc

## Purpose

F-778071b4c8bc conditionally prepares an object reference, validates a one-byte discriminator, and produces an object-relative address together with a 16-bit dependency result.

The object-reference slot’s entry value selects the workflow:

- An initially zero slot follows the acquisition-like path and requires discriminator 1.
- An initially nonzero slot follows the existing-object path and requires discriminator 2. Acceptance on this path also increments a 32-bit context field.

Both accepted paths write the address output, invoke a final dependency, write its 16-bit result, and return zero. Rejected paths invoke a common dependency, clear both outputs, and return a previously selected status. A rejected path can also return zero if its selected external status is zero.

**Established static behavior:** Branch selection, dependency ordering, discriminator checks, field accesses, output-write ordering, and status selection follow the supplied representation.

**Inferred intent:** “Acquisition,” “preparation,” “counter,” and “cleanup” describe apparent roles only. They do not establish allocation, ownership transfer, destruction, or recovery semantics.

## Interface

The function accepts four arguments:

| Argument | Role | Visible representation |
|---|---|---|
| Context reference | Identifies context storage and is passed to dependencies | 32-bit address-bearing value |
| Object-reference slot | Supplies the entry object reference and can be updated by dependencies | Address of a readable, writable 32-bit address-bearing slot |
| Address-output slot | Receives a computed address or zero | Address of writable 32-bit storage |
| Value-output slot | Receives the final dependency’s result or zero | Address of writable 16-bit storage |

The return value is a 32-bit status represented as an integer in the supplied material.

The function directly accesses these fields:

| Storage | Byte offset | Width and interpretation |
|---|---:|---|
| Context | 28 | Unsigned 16-bit offset used to locate a displacement |
| Context | 88 | 32-bit integer incremented on accepted existing-object processing |
| Referenced object | 8 | One-byte discriminator |
| Referenced object-relative storage | Computed | Signed 16-bit displacement |

“Referenced object” means the address read from the object-reference slot at the relevant access. A dependency may replace that address. The function does not require later reads to use the address present at entry.

### Preconditions and validity limits

For normal completion, storage must be valid for every access actually reached:

- The object-reference slot must support the entry read and any dependency accesses.
- A reference used for the discriminator must permit a one-byte read at offset 8.
- The context must permit the offset-field read and, when reached, the counter read and write.
- The computed displacement location must permit a signed 16-bit read.
- Output slots must support their respective writes.
- Address formation and integer operations must have defined behavior under the actual execution model.

The function provides no explicit null, bounds, alignment, or overflow checks. In particular, a zero result from the acquisition-like dependency is followed by an object dereference without an independent nonzero-reference check.

Nonoverlapping storage is not explicitly enforced. Overlap can change later observations and final contents. The ordinary output descriptions below assume separate storage unless overlap is specifically discussed.

## Behavior

### Entry selection

The first visible operation reads the object-reference slot and tests whether it contains zero.

That test fixes the workflow for this invocation. Later changes to the slot do not restart selection or switch to the other workflow.

### Initially zero object-reference slot

The function invokes F-5f9a16493218 with the context reference, a zero second argument, and the object-reference slot.

If the dependency returns nonzero, that result becomes the selected failure status.

If it returns zero, the function reads the discriminator at byte offset 8 from the object then referenced by the slot:

- Discriminator 1 accepts this workflow.
- Any other discriminator selects status 37 and rejects it.

On acceptance, the signed 16-bit displacement is located at:

**object address + unsigned context offset − 6 bytes**

This workflow does not directly increment the context field at offset 88. Dependency-mediated changes to that field remain possible.

### Initially nonzero object-reference slot

The function performs these operations in order, subject to the stated gates:

1. Invoke F-4055be9c3f18 without arguments and retain its 32-bit result as a token-like value.
2. Read the first external status location. This read occurs even if the token is nonzero.
3. If the token is zero, reject the workflow using that external status.
4. Otherwise invoke F-b0f922796692 with the context reference and object-reference slot.
5. If that invocation returns nonzero, reject using its result.
6. Otherwise invoke F-5f9a16493218 with the context reference, retained token, and object-reference slot.
7. If that invocation returns nonzero, reject using its result.
8. Otherwise read the second external status location, then inspect the current object’s discriminator at byte offset 8.
9. If the discriminator is not 2, reject using the second external status.
10. If the discriminator is 2, increment the 32-bit context field at offset 88 and continue to accepted output production.

The first external status is not the fallback for every subsequent rejection: later dependency results or the second external status replace it at their respective decision points.

On acceptance, the displacement location is:

**object address + unsigned context offset − 2 bytes**

The counter increment precedes the displacement read, address-output write, and final dependency call. The function contains no rollback of that increment. If storage overlaps, the increment can itself alter storage read later.

### Accepted output production

Both accepted workflows converge on the same output sequence:

1. Read the signed 16-bit displacement from the workflow-specific location.
2. Add its sign-extended value to an object address read from the object-reference slot.
3. Store the resulting 32-bit address-bearing value in the address-output slot.
4. Invoke F-c4c1afdb3fb3 with the context reference and an object address read from the object-reference slot for that call.
5. Store the dependency’s 16-bit result in the value-output slot.
6. Return zero.

The displacement is signed: its range is −32768 through 32767. Negative values can produce an address below the object base. The context offset is unsigned, with range 0 through 65535; a set high bit does not make it negative.

The address output is written before the final dependency is invoked. Therefore, if that output overlaps the object-reference slot, the dependency can receive the newly stored address rather than the object base used in the displacement calculation.

The final dependency’s result is treated as a 16-bit value, not as a success/failure condition. Every returned bit pattern, including zero, is written to the value-output slot and followed by a zero function return.

There is no general restoration after this dependency. However, its return is followed by an unconditional 16-bit write to the value-output slot:

- Any dependency-made change to that slot is overwritten by the returned 16-bit value.
- If the slot overlaps the address output, context, object-reference slot, or object storage, that write can also overwrite dependency-made changes in the overlapping region.
- Other dependency-made changes are not explicitly reversed by this function.
- There is no separate rewrite of the address output, although overlapping value-output storage can modify it.

### Common rejection handling

Every rejected path performs the following sequence:

1. Invoke F-b0f922796692 with the context reference and object-reference slot.
2. Ignore that invocation’s return value.
3. Write a 32-bit zero to the address-output slot.
4. Write a 16-bit zero to the value-output slot.
5. Return the previously selected status.

The common dependency’s return does not replace the selected status. Changes it makes to either external status location likewise do not cause the saved status to be reread.

The existing-object workflow can call F-b0f922796692 twice: once during preparation and again during rejection handling. A nonzero result from its preparation invocation does not suppress the second call.

A rejected path is not guaranteed to return nonzero. If a selected external status is zero, rejection handling still occurs and the outputs are cleared, but the function returns zero.

### Arithmetic and ordering boundaries

The effective displacement-location corrections are exactly −6 bytes for the initially zero workflow and −2 bytes for the initially nonzero workflow.

Neither the displacement location nor the resulting address is checked against object extent. The function does not dereference the resulting address after storing it; validity requirements for a consumer’s later access are outside the visible behavior.

The supplied expression reads the object-reference slot for address formation more than once. It does not establish a complete order among all operand reads within that expression. This contract therefore does not promise a single object-reference snapshot or a total ordering between every context-field and object-reference read.

The counter is represented as a 32-bit integer increment. Overflow is not explicitly handled. Unconditional wraparound, saturation, or trapping cannot be promised without the actual execution model. Address-overflow behavior is likewise unresolved.

## Side effects

### Direct state changes

The function directly performs only the following writes:

- A counter increment at context offset 88 on accepted initially nonzero processing.
- A 32-bit address-output write followed, after F-c4c1afdb3fb3, by a 16-bit value-output write on accepted processing.
- A 32-bit zero write followed by a 16-bit zero write on rejection.

These writes are ordered operations, not an atomic pair or transaction.

### Dependency-mediated changes and ownership

Dependencies receive the context, object-reference slot, object reference, or token as described below. Their implementations and preservation guarantees are unavailable.

No dependency is assumed to:

- Preserve globals, context, object storage, or accessible outputs.
- Preserve or clear the object-reference slot.
- Allocate, retain, release, or transfer ownership of an object.
- Restore entry state after failure.

The common rejection call is therefore not a proven destructor or rollback operation. The function itself establishes no ownership transfer and no object-lifetime guarantee.

### Overlap and partial completion

Overlapping outputs can cause the final 16-bit write to overwrite part of the earlier 32-bit address result. On acceptance, that write also supersedes any mutation the final dependency made to those same bytes.

If the value-output slot overlaps context or object storage, the final write can alter that storage after the dependency returns. This is a subsequent write, not a general rollback.

A fault or abnormal dependency exit can leave partial effects. The counter may already be incremented, the address output may already be written, or rejection-side dependency changes may already have occurred before both outputs are cleared. No synchronization or exception-recovery mechanism is shown.

   The first external status is read. Preparation and acquisition are skipped. F-b0f922796692 is called through rejection handling, the outputs are cleared, and the saved external status is returned.

6. **Zero status on rejection**

   Existing-object preparation and acquisition succeed, but the discriminator is not 2 and the second external status is zero.

   Rejection handling occurs, both outputs are cleared, and the function returns zero. A zero return alone does not prove accepted output production.

7. **Final dependency mutates the value output**
