# F-20c927c36211

## Purpose

F-20c927c36211 performs a read-only compatibility check between a supplied object, two requested attributes, and ownership and list state reachable through that object.

The function returns one of two 32-bit results:

- **0:** No rejecting condition was encountered.
- **6:** A conflicting owner or qualifying conflicting list entry was encountered.

A result of 0 does not establish that the surrounding data structures are generally valid, that the requested attributes belong to an accepted enumeration, or that a later operation will succeed. Some paths return 0 without inspecting ownership or list state.

**Established behavior:** The function conditionally checks an exclusive-owner reference and then, under a separate condition, searches a linked list for a conflict.

**Inferred intent:** These checks appear to enforce compatibility or exclusivity for an object participating in shared state. Names such as “owner,” “category,” and “mode” below are descriptive labels, not established domain meanings.

## Interface

### Inputs

The function takes three arguments:

| Argument | Width and interpretation | Role |
|---|---|---|
| Object reference | Pointer represented in the supplied 32-bit address model | Identifies the object being checked and provides access to associated state. |
| Requested category | Signed 32-bit integer | Compared for exact equality with a 32-bit field in each inspected list entry; the value 1 also forces list inspection when the object is enabled. |
| Requested mode | Unsigned 32-bit integer | The value 2 forces list inspection when the object is enabled; the value 1 participates in a narrowly defined list-entry exception. |

There is no explicit null check for the object reference. Even the shortest successful path requires reading its enable byte.

No argument range validation is established. In particular, the requested mode remains a full 32-bit value even though the corresponding list-entry field is only one byte.

## Behavior

### Enable gate

The first logical data access is the object’s enable byte at offset 9.

If that byte is zero, the function returns 0 immediately. It does not inspect the context reference, exclusive-owner field, optional flag-bearing structure, or list.

Consequently, a disabled object does not need valid contents in those otherwise reachable fields for this function’s completed disabled-path behavior. The enable byte itself must still be accessible.

### Exclusive-owner check

For an enabled object, the function obtains the associated context through the object’s reference at offset 4 and reads the context’s exclusive-owner reference at offset 92.

The result is 6 if that owner reference is both:

- Non-null; and
- Different from the supplied object reference.

A null owner is accepted at this stage. An owner equal to the supplied object is also accepted.

A foreign owner causes an immediate return. The optional flag-bearing reference and list are not inspected on that path. Neither requested attribute exempts a foreign owner.

### Flag observation and decision to inspect the list

After the exclusive-owner check passes, the function reads the optional reference at object offset 0.

- If the reference is null, no flag-word read occurs.
- If it is non-null, the function reads the unsigned 32-bit flag word at offset 12 of the referenced structure.

This flag-word read occurs before deciding whether the requested category or requested mode forces list inspection. Therefore, an inaccessible non-null flag-bearing reference is not made harmless by requesting category 1 or mode 2.

The list is inspected if **any** of the following is true:

- The optional flag-bearing reference is null.
- Flag bit `0x4000` is clear.
- The requested mode is 2.
- The requested category is 1.

Equivalently, list inspection is skipped only when all of the following hold:

- The optional reference is non-null.
- Its flag word has bit `0x4000` set.
- The requested mode is not 2.
- The requested category is not 1.

If list inspection is skipped, the function returns 0.

Bits other than `0x4000` do not affect this decision.

### List inspection

When inspection is required, the function obtains the context through the object again and reads the list-head reference at context offset 88.

A null head represents an empty list and produces result 0.

For each reachable non-null entry, the function applies these conditions in order:

1. It reads the entry’s object reference.
2. If that reference equals the supplied object, the entry is not a conflict. Its category and mode need not be read.
3. Otherwise, it reads the entry’s category.
4. If that category differs from the requested category, the entry is not a conflict. Its mode need not be read.
5. Otherwise, it reads the entry’s one-byte mode and determines whether the narrow mode exception applies.

An entry belonging to a different object and matching the requested category is tolerated **only when both the entry mode and the requested mode equal 1**. Every other mode combination for such an entry causes immediate result 6.

Thus, equality between the two modes is not a general exemption. Matching modes of 0, 2, or any other value still conflict.

If an entry does not cause rejection, the function reads its next-entry reference at offset 12 and continues. If an entry does cause rejection, its next-entry reference is not needed.

Reaching a null next-entry reference without encountering a conflict produces result 0.

### Width-sensitive comparison

The one-byte entry mode is interpreted as an unsigned value in the range 0 through 255 when compared with the unsigned 32-bit requested mode. The requested mode is not truncated to a byte.

For example, requested mode 257 is not equivalent to mode 1. A matching-category entry belonging to another object rejects requested mode 257 even when its stored byte is 1.

The category comparison tests equality of the 32-bit values. There is no category ordering or range check.
