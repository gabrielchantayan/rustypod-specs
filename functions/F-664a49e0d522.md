# F-664a49e0d522

## Purpose

F-664a49e0d522 conditionally records a three-input request in a context obtained from F-7fba0909c452. When the request is rejected, it may instead record an error in that context, preserving an already nonzero error.

The established behavior has three outcomes:

- No operation after context acquisition, if the dependency returns a null pointer.
- An ordered update of five context fields, if the first input matches a configured selector and the second input is nonnegative.
- Conditional recording of an error, otherwise.

The apparent intent is to configure a pending operation and maintain a first-error latch. That interpretation is inferred from the assignments and control flow; no domain-specific meaning for the selectors or context fields is established.

## Interface

| Selector | 32-bit integer | Compared with a configured selector, that selector minus six, and two fixed constants; stored on acceptance. |
| Count | Signed 32-bit integer | Rejected when negative; sometimes normalized when zero; stored on acceptance. |

The width and offset descriptions below use the supplied representation’s four-byte integer layout. The underlying ABI and instruction-level arithmetic are not independently available.

### External state

Two global integer values participate:

- **Configured selector:** supplies the primary accepted selector. Its value minus six supplies the other accepted selector.
- **Configured rejection value:** supplies the candidate error when the selector is accepted but the count is negative. It is also read on the accepted, nonnegative-count path, although its value does not affect that path’s outcome.

These names are descriptive contract labels, not claims about the globals’ original names or intended domain.

## Behavior

### 1. Acquire the context

F-7fba0909c452 is called once, before this function examines either configuration global or validates any input.

If the dependency returns null, the function returns immediately. It performs no subsequent context access or configuration-global read shown in the supplied body.

The dependency’s own effects remain possible even in this case. A null result therefore establishes absence of subsequent effects by this function, not absence of effects from the overall call.

### 2. Determine whether the selector is accepted

For a nonnull context, the selector is accepted when either comparison succeeds:

- It equals the configured selector.
- It equals the configured selector minus six.

The first comparison is evaluated before the second. A successful first comparison skips the second comparison.

The two fixed selector values used later for count normalization do not independently make a selector acceptable. They matter only after this initial selector gate has passed.

The supplied expression refers to the configured selector separately in the two comparisons. It does not explicitly retain a single snapshot for every later use. A stable configuration value makes this distinction irrelevant; behavior under concurrent mutation or unusual memory access semantics is not established.

Subtraction by six is performed as an integer expression. The supplied evidence does not establish defined wraparound behavior when the configured selector is near the signed 32-bit minimum. A portable signed interpretation requires the subtraction to be representable whenever evaluated.

### 3. Accepted selector: read the configured rejection value

After the selector gate succeeds, the configured rejection value is read before checking whether the count is negative.

Consequently, this global is read even for requests that will succeed and never use the value.

If the count is negative, the function proceeds to error handling with this read value as its candidate error. It does not normalize or store the count, and it does not perform any of the successful-update writes.

If the count is nonnegative, processing continues to count normalization.

### 4. Normalize a zero count

A positive count is retained unchanged.

For a zero count, the effective count is selected in this priority order:

1. Selector `0x1400` produces an effective count of 1.
2. Otherwise, selector `0x1402` produces an effective count of 2.
3. Otherwise, a selector matching the configured selector minus six or the configured selector produces an effective count of 4.
4. If none of these normalization comparisons succeeds, the effective count remains zero.

The fixed-value cases take priority over the configured-selector case. Thus an accepted selector of `0x1400` produces 1, not 4; an accepted selector of `0x1402` produces 2, not 4.

With a stable configured selector and representable subtraction, the fourth possibility cannot occur: the initial gate has already established one of the configured-selector relationships. However, the normalization expression consults the configuration again, so the evidence does not justify removing that possibility from a contract that permits the configuration to change between reads.

The configured-selector comparisons during normalization have the opposite order from the initial gate: the subtraction-based comparison comes first, followed by direct equality if needed.

### 5. Commit an accepted request

For an accepted selector and a nonnegative count, the function performs these accesses in the order expressed by the supplied body:

| Order | Access |
|---:|---|
| 1 | Write the selector to context offset `0x1F4`. |
| 2 | Write the payload to context offset `0x1F8`. |
| 3 | Write integer 1 to context offset `0x1F0`. |
| 4 | Write the effective count to context offset `0x20C`. |
| 5 | Read the integer at context offset `0xAD8`. |
| 6 | Write that integer to context offset `0x1FC`. |

The snapshot source is therefore read after the first four writes, not at context acquisition or validation time.

The function then returns. It neither reads nor updates the error field at offset `0x000` on this path. In particular, acceptance does not clear a preexisting error.

This is an ordered sequence in the supplied representation, not an established atomic transaction or a guarantee about cross-thread visibility.

### 6. Handle rejection

If the selector fails its gate, the candidate error is `0x500`—decimal 1280. The configured rejection value is not read on this branch.

If the selector passes but the count is negative, the candidate error is the previously read configured rejection value.

The candidate is handled as follows:

- A zero candidate causes an immediate return without reading the context’s error field.
- A nonzero candidate causes a read of the error field at `0x000`.
- If the existing error is zero, the candidate is written there.
- If the existing error is nonzero, it is preserved.

No successful-update fields are accessed on either rejection path. In particular, the snapshot source at `0xAD8` is not read.

The preservation rule is an ordinary conditional read and write. No atomic compare-and-set, locking, or concurrency-safe first-error guarantee is established.

## Side effects

### Ownership and lifetime

The function uses the context pointer returned by F-7fba0909c452. It makes no explicit allocation, release, ownership-transfer call, or retention of the context pointer in the supplied body.

This does not establish whether the dependency allocates the context, returns shared storage, changes its lifetime, or releases other resources. Those properties require the dependency’s own contract.

The payload is copied as an integer value. There is no evidence that the function treats it as an address, acquires ownership of anything it might identify, or releases a previous payload.

### State changes

On acceptance, the function overwrites all five destination fields regardless of their previous contents. The activation field becomes exactly 1 rather than preserving or combining bits.

On rejection with a nonzero candidate error, only the field at `0x000` can be written. An existing nonzero error is not replaced.

No direct writes to the two configuration globals are shown. Whether context storage could alias those globals is not established; absence of an explicit global assignment alone does not prove non-aliasing.

### Failures outside explicit handling

Null context, selector mismatch, and negative count have explicit paths. Invalid nonnull pointers, inaccessible fields, arithmetic overflow, and concurrent mutation have no explicit recovery path in the supplied evidence.

The contract does not promise graceful handling for those conditions.

## Acceptance examples

These examples are conditional expectations derived from static evidence. They are not results of executed tests. Unless stated otherwise, assume four-byte integers, stable configuration, representable arithmetic, and valid context storage.

### Null context suppresses subsequent work

Given that F-7fba0909c452 returns null, any selector, count, and payload produce no subsequent context accesses or direct configuration reads by this function.

Effects internal to the dependency remain outside this expectation.

### Positive count is stored unchanged

Given:

- Configured selector is `0x1500`.
- Input selector is `0x1500`.
- Count is 7.
- Payload is 23.
- Snapshot source at `0xAD8` contains 91.

The function reads the configured rejection value, then writes:

- `0x1500` to `0x1F4`;
- 23 to `0x1F8`;
- 1 to `0x1F0`;
- 7 to `0x20C`;
- the subsequently read value 91 to `0x1FC`.

The existing error is untouched, whether zero or nonzero.

### Zero count uses the general default

Given a configured selector of `0x1500`, either selector `0x1500` or selector `0x14FA` is accepted. With count zero, neither is a fixed normalization special case, so the effective count is 4.

### Fixed normalization takes precedence

Given a configured selector of `0x1406`, selector `0x1400` passes as the configured value minus six. With count zero, the stored effective count is 1.

Given a configured selector of `0x1402`, selector `0x1402` passes directly. With count zero, the stored effective count is 2.

### A fixed normalization value can still be rejected

Given a configured selector of `0x1500`, selector `0x1400` fails the selector gate even though it has a special zero-count normalization rule.

With an initially zero error field, the function records `0x500`. It does not perform successful-update writes.

### Negative count uses the configured candidate

Given an accepted selector, count −1, a configured rejection value of 9, and an initially zero error field, the function writes 9 to `0x000`.

The same result applies to any representable negative count, including the signed 32-bit minimum. No count arithmetic is performed on this path.

### A zero configured candidate suppresses error-field access

Given an accepted selector, a negative count, and configured rejection value zero, the function returns without reading or writing the error field and without touching the successful-update fields.

### Existing errors are preserved

Given a rejected selector and an existing error of 12, the candidate error is `0x500`, but the stored error remains 12.

Likewise, an accepted selector with negative count does not replace 12 with a nonzero configured rejection value.
