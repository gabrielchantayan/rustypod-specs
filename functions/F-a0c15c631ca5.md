# F-a0c15c631ca5

## Purpose

F-a0c15c631ca5 performs a local, in-place rearrangement of linked records. It promotes the record referenced by an input record’s field at offset +8, reconnects the promoted record to the input record’s former position, and places the input record beneath the promoted record through the field at offset +12.

**Inferred intent:** With conventional binary-tree meanings for these fields, this is a right rotation:

- Offset +4: parent.
- Offset +8: left child.
- Offset +12: right child.

The operation also supports replacing a distinguished root reference reached indirectly through the first argument.

**Established behavior:** The function makes a fixed sequence of 32-bit memory accesses and conditional stores. It does not validate tree structure, check the promoted-record reference for null, allocate storage, release storage, or call another function.

The tree terminology below describes the apparent structural role of each field. It does not establish balancing rules, ordering rules, ownership, or the meaning of other record contents.

## Interface

### Inputs

The function accepts two arguments represented as integers in the supplied source:

| Argument | Behavioral role |
|---|---|
| Context address | Identifies an object containing a 32-bit address-valued field at offset +16. That field leads to an object whose offset +4 is the distinguished root-reference slot. |
| Node address | Identifies the record being moved down. Its offset +8 supplies the record to promote. |

The function has no return value and reports no explicit status.

### Preconditions

For an ordinary, structurally coherent rotation:

- The node address identifies an accessible node record.
- Its left-child reference identifies an accessible, non-null promoted record.
- The context’s offset +16 field identifies an accessible root-reference holder.
- If the promoted record’s right-child reference is nonzero when tested, that referenced record has a writable parent field.
- If the distinguished root reference does not equal the node address, the node’s parent reference identifies an accessible parent record.
- The relevant links describe a consistent tree fragment, with distinct records where required to avoid overlapping field roles.
- No concurrent or reentrant mutation changes these locations during execution.

## Behavior

### Structural effect under stable, non-overlapping tree conditions

Let the input node be the node being moved down. Its initial left child is the promoted record. The promoted record’s initial right child is the transferred subtree.

On successful completion:

1. The node’s left-child reference identifies the transferred subtree.
2. If that subtree is non-null, its parent reference identifies the node.
3. The promoted record’s parent reference equals the node’s former parent reference.
4. The reference that formerly attached the node to its enclosing tree position identifies the promoted record instead:
   - The distinguished root slot is replaced if it contained the node address.
   - Otherwise, the former parent’s right-child field is replaced if that field contained the node address.
   - Otherwise, the former parent’s left-child field is replaced without checking its prior value.
5. The promoted record’s right-child reference identifies the node.
6. The node’s parent reference identifies the promoted record.

The node’s right child and the promoted record’s left child are not directly selected as write destinations. Under ordinary distinct-record assumptions, those references remain unchanged.

### Ordered memory-access contract

The source establishes the following access order. Repeated reads matter when storage overlaps or changes externally.

1. Read the node’s 32-bit field at offset +8. Retain this address as the promoted record for the remainder of the operation.
2. Read the promoted record’s 32-bit field at offset +12.
3. Write that value into the node’s field at offset +8.
4. Read the promoted record’s field at offset +12 again and compare it with zero.
5. If that read was nonzero:
   - Read the promoted record’s field at offset +12 once more.
   - Use this latest value as an address and write the node address into its field at offset +4.
6. Read the node’s field at offset +4.
7. Write that value into the promoted record’s field at offset +4.
8. Read the context’s field at offset +16 to obtain the root-reference holder address.
9. Read the holder’s field at offset +4 and compare it with the node address.
10. If the root-reference comparison matches, write the promoted-record address into that root slot.
11. Otherwise:
    - Read the node’s field at offset +4 again to obtain the parent address.
    - Read that parent’s field at offset +12.
    - If the parent’s offset +12 field equals the node address, write the promoted-record address there.
    - If it does not equal the node address, write the promoted-record address into the parent’s field at offset +8. There is no preceding equality check on this destination.
12. Write the node address into the promoted record’s field at offset +12.
13. Write the promoted-record address into the node’s field at offset +4.
14. Return without a value.

The nonzero test and the subsequent destination-address read are separate accesses. The source does not promise that the tested reference and the subsequently used reference are identical under concurrent mutation or unusual aliasing.

Similarly, the parent value copied into the promoted record and the parent value later used for non-root attachment are obtained by separate reads.

### Branch precedence

The distinguished root comparison has precedence over parent-link inspection.

If the root slot equals the node address, the function updates that slot and does not inspect the former parent’s right-child field. It still copies the node’s parent field into the promoted record before making the root comparison. It does not force the promoted root’s parent to zero.

For a non-root node, the parent’s right-child field has precedence. If both parent child fields contain the node address, only the right-child field is selected for replacement.

### Arithmetic and representation

The operation uses constant byte offsets of +4, +8, +12, and +16. It performs no explicit element-count arithmetic, size calculation, balance calculation, or key comparison.

All observed link-field transfers are 32 bits wide. Equality comparisons concern zero or the supplied node address. No signed ordering comparison is present.

Valid address formation is a precondition for normal execution. The source does not establish a defined wraparound rule for invalid address-plus-offset calculations.

## Side effects

For stable, non-overlapping storage, normal completion performs five unconditional 32-bit writes:

- The node’s left-child field.
- The promoted record’s parent field.
- One attachment slot: either the root slot or a parent child slot.
- The promoted record’s right-child field.
- The node’s parent field.

It performs one additional 32-bit write when the transferred-subtree reference is nonzero: that subtree’s parent field.

These counts describe write operations, not necessarily changes in value or distinct physical destinations. Aliasing can make destinations overlap.

The operation is not transactional. Intermediate states do not represent the completed rotation. In particular, the node’s left-child reference is changed before the enclosing attachment slot and final parent-child relationship are updated. There is no visible rollback or recovery mechanism.

No allocation, deallocation, callback, global-symbol access, I/O, or explicit synchronization appears. Ownership is not transferred through an allocator or release operation. Any ownership meaning attached to the rewritten links is external to this function.

The context object is not directly written. Memory reached through it is written when the root branch is taken. Aliasing can make such distinctions collapse.

## Acceptance examples

These examples are conditional on accessible, stable, non-overlapping storage. They describe static consequences, not executed tests.

### Root rotation with a transferred subtree

Initially:

- The root slot identifies the node.
- The node’s parent is zero.
- The node’s left child is the promoted record.
- The promoted record’s right child is a non-null transferred subtree.

Expected completion:

- The root slot identifies the promoted record.
- The promoted record’s parent is zero.
- The promoted record’s right child is the node.
- The node’s parent is the promoted record.
- The node’s left child is the transferred subtree.
- The transferred subtree’s parent is the node.

### Non-root rotation with no transferred subtree

Initially:

- The root slot does not identify the node.
- The node’s parent identifies a former parent.
- That parent’s right child identifies the node.
- The promoted record’s right child is zero.

Expected completion:

- The former parent’s right child identifies the promoted record.
- The promoted record’s parent identifies the former parent.
- The node’s left child becomes zero.
- No transferred-subtree parent write occurs.
- The promoted record’s right child identifies the node, and the node’s parent identifies the promoted record.

### Left attachment selected by exclusion

If the root slot differs from the node address and the former parent’s right-child field also differs from the node address, the former parent’s left-child field is overwritten with the promoted-record address.

This remains the selected behavior even if that left-child field did not previously identify the node. The function does not reject the inconsistent relationship.

### Duplicate parent references

If a non-root node is referenced by both child fields of its former parent, the right-child field is replaced. The left-child field retains its previous value under the stated non-overlap assumptions. The function does not repair the duplicate reference.

### Root with a nonzero parent field

If the root slot identifies the node but the node’s parent field is nonzero, that value is copied into the promoted record’s parent field. The root slot is replaced without normalizing the copied parent to zero.

### Missing promoted record

A zero left-child reference is not an accepted empty-rotation case. The function attempts to read offset +12 through that zero-valued reference. No successful no-op, status return, or defined error response is established.
