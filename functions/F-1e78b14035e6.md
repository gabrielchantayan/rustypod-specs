# F-1e78b14035e6

## Purpose

F-1e78b14035e6 is a guarded indirect-call adapter. It checks two scalar inputs, selects one of two callable entries using a byte in associated state, adjusts a signed input using a field in the supplied object, and forwards seven arguments to the selected dependency.

Its result is a 64-bit bit pattern with separately constructed upper and lower 32-bit halves:

- On an accepted call that returns normally, the lower half is the dependency’s 32-bit result and the upper half is the first trailing payload word.
- On rejection, the lower half is all ones and the upper half is the incoming second argument.

The established behavior is dispatch and result construction. The domain meaning of the object, selector byte, adjusted input, payload words, and dependency result is unknown. In particular, rejection must not be assigned a named error category, and the dependency result must not be presumed to be a success code.

## Interface

### Inputs

The function receives seven arguments, described here by semantic-neutral roles:

| Position | Role | Width and interpretation |
|---|---|---|
| 1 | Object reference | Reference to storage accessed as a sequence of 32-bit words, some of which are used as addresses |
| 2 | Gate value | Signed 32-bit integer; accepted only when nonzero |
| 3 | Adjustment input | Signed 32-bit integer |
| 4 | Bounded value | Unsigned 32-bit integer; accepted only when at most 256 |
| 5 | Payload A | Opaque 32-bit word |
| 6 | Payload B | Opaque 32-bit word |
| 7 | Payload C | Opaque 32-bit word |

The width descriptions follow the supplied reconstructed interface and its 32-bit word accesses. They do not establish a portable host ABI, native pointer width, or a safe way to invoke the function from an unrelated execution environment.

All 32 bits of each payload are significant to this contract. No payload is locally interpreted as a pointer, Boolean, signed quantity, or ownership token.

### Object and associated storage

On the accepted path, the function uses the following object fields:

| Object-relative byte offset | Access | Established use |
|---|---|---|
| 0 | Read one 32-bit word | Obtain the address used as the callable-table base |
| 16 | Read one 32-bit word | Obtain the address used as the associated-state base |
| 24 | Read one signed 32-bit word | Obtain the adjustment base |

Two further layouts are relevant:

- At associated-state base plus 92 bytes, the function reads one byte. Zero selects the first callable entry; every nonzero byte selects the second.
- At callable-table base plus 176 bytes or plus 180 bytes, respectively, the function reads the selected callable address.

These offsets describe only the fields accessed here. They do not establish the complete sizes, allocation boundaries, ownership, or invariants of any object or table.

### Output

The return value is a 64-bit bit pattern:

- **Accepted path, normal dependency return:** upper 32 bits equal Payload A; lower 32 bits equal the dependency’s 32-bit result.
- **Rejected path:** upper 32 bits equal the Gate value’s original 32-bit representation; lower 32 bits equal `0xFFFFFFFF`.

Concatenation preserves bits. It does not sign-extend either half. A consumer may interpret the resulting 64 bits according to a separate API contract, but this function alone does not establish such an interpretation.

### Preconditions

A rejected invocation does not require readable object storage for any access performed by this function.

An accepted invocation requires, at minimum:

- Readable object fields at the offsets listed above.
- A readable selector byte at the associated-state address.
- A readable selected callable-table entry.
- A selected address that can be called using the observed argument and return convention.
- Valid arithmetic and address interpretation for the execution environment.

The selected dependency may impose additional preconditions. Those are unknown here. Local acceptance is therefore not proof that the forwarded operation is valid.

## Behavior

### 1. Admission decision

The function accepts the invocation only when both conditions hold:

1. The Gate value is nonzero.
2. The unsigned Bounded value is less than 257, equivalently within the inclusive range 0 through 256.

The Gate comparison is against zero, not against positivity. Negative Gate values satisfy the first condition.

The Bounded value is checked as unsigned. A 32-bit all-ones pattern is therefore 4,294,967,295 for this comparison and is rejected; it is not treated as negative one.

If either condition fails, the function returns the rejection result immediately. It does not read the object, inspect associated state, load a callable entry, read the adjustment base, or call either dependency.

This distinction matters for invalid object references: the function body does not dereference such a reference on rejection. This is not a general guarantee that an invalid reference is safe under the surrounding ABI or caller.

### 2. Selector read

After admission, the function obtains the associated-state address from the object field at byte offset 16 and reads the byte at that address plus 92.

Selection depends only on whether that byte is zero:

- Zero selects the entry at callable-table offset 176.
- Any nonzero value selects the entry at callable-table offset 180.

There is no special handling for particular nonzero byte values. For example, `0x01`, `0x80`, and `0xFF` all choose the same entry. Whether the byte is represented as signed or unsigned does not change this zero/nonzero decision.

The selector is not locally modified.

### 3. Callable selection

After determining the branch, the function reads the callable-table address from the object field at byte offset 0 and obtains the callable address from the selected table offset.

Only the selected entry is required by the observed operation. The function does not explicitly inspect the alternate entry or validate the selected address before calling it.

The selected callable is obtained before invocation. There is no local selector reread or dispatch retry.

### 4. Argument preparation and invocation

The function reads the signed 32-bit adjustment base from object byte offset 24 and adds the signed 32-bit Adjustment input.

The selected dependency receives seven arguments in this logical order:

1. The original Object reference.
2. The unchanged Gate value.
3. The sum of the adjustment base and Adjustment input.
4. The unchanged Bounded value.
5. Payload A.
6. Payload B.
7. Payload C.

Argument order here describes parameter positions, not a platform-specific register assignment or stack layout.

The function does not locally clamp, validate, scale, or otherwise normalize the sum. Where the mathematical sum is representable as a signed 32-bit integer, its value is established. Behavior for signed overflow is **documented_only**: the supplied representation does not safely establish whether the underlying operation wraps or has some other execution-level behavior.

On an accepted invocation, exactly one selected dependency call is shown, provided execution reaches the call. There is no local fallback to the other dependency if that call fails.

### 5. Result construction

If the dependency returns normally, its 32-bit result becomes the lower half of the return value. Payload A becomes the upper half.

Payload A has two independent observable roles: it is forwarded as the fifth dependency argument and reused as the upper return word. Payload B and Payload C are only forwarded.

The function does not inspect the dependency result for a special value. A dependency result of `0xFFFFFFFF` is preserved just like any other 32-bit result.

If the dependency does not return normally, no completed return-value construction is established by this contract.

## Side effects

### Local reads and their order

The established accepted-path sequence is:

1. Evaluate the scalar admission conditions.
2. Read the object’s associated-state address.
3. Read the selector byte.
4. Read the object’s callable-table address and the selected callable entry.
5. Read the adjustment base while preparing the call.
6. Invoke the selected dependency.
7. Construct the result from the dependency’s return word and Payload A.

The supplied representation establishes these dispatch and call-preparation stages. It does not establish machine-level atomicity, memory barriers, instruction selection, or a complete ABI-level argument evaluation order.

On rejection, none of the object-related reads occurs.

### Writes and external effects

No explicit write to the object, associated state, callable table, or other memory appears in this function. No allocation, release, or ownership transfer is explicitly performed here.

That observation does **not** establish that an accepted invocation is read-only. The selected dependency receives the object reference and all three payload words. Its writes, global-state changes, allocation behavior, callbacks, and resource handling are unknown.

The function performs no explicit restoration after the dependency returns. It must not be assumed to preserve global state or undo dependency effects.

### Ownership and lifetime

No ownership policy is established for the object, its associated storage, the callable table, or values represented by payload words.

The wrapper does not itself visibly acquire or release those resources. Whether a dependency retains references, consumes resources, releases memory, or changes object lifetime is **documented_only**. Callers must obtain those guarantees from the dependency contract rather than infer them from this wrapper.

## Acceptance examples

These are conditional acceptance criteria derived from the supplied static representation. They are not runtime test results.

### Zero Gate value rejects without object access

Given a Gate value of zero, the result is `0x00000000FFFFFFFF`, regardless of the Bounded value or payload words.

Neither dependency is invoked, and the object is not dereferenced by this function.

### Upper bound is inclusive

Given a nonzero Gate value and a Bounded value of 256, the invocation enters the dispatch path.

Given the same inputs except for a Bounded value of 257, it rejects. For a Gate value of 7, that rejection result is `0x00000007FFFFFFFF`.

A Bounded value of zero is also admitted when the Gate value is nonzero.

### Negative Gate values are admitted

Given a Gate value of negative one and a Bounded value of 12, the invocation enters the dispatch path, subject to valid memory and callable preconditions.

Given that same Gate value and a Bounded value of 257, it rejects with the 64-bit pattern `0xFFFFFFFFFFFFFFFF`.

### Selector values choose by zero versus nonzero

Given accepted scalar inputs and a selector byte of zero, F-dep-01 is invoked.

Given the same conditions but a selector byte of `0x80`, F-dep-02 is invoked. The high bit does not create a third case or cause rejection.

### Adjustment precedes dependency execution

Given an adjustment base of 100 and an Adjustment input of negative 25, the selected dependency receives 75 as its third argument.

The Gate value, Bounded value, and all payload words retain their incoming values in the corresponding forwarded positions.

### Returned halves preserve independent bit patterns

Given valid accepted-path state, Payload A equal to `0x12345678`, and a selected dependency that returns `0x89ABCDEF`, the wrapper returns `0x1234567889ABCDEF`.

If the dependency instead returns `0xFFFFFFFF`, the wrapper returns `0x12345678FFFFFFFF`. That lower word does not trigger local error handling.

### Result alone need not identify rejection

An accepted dependency call returning `0xFFFFFFFF`, with Payload A equal to 7, produces `0x00000007FFFFFFFF`.

A rejected call with Gate value 7 produces the same pattern. Therefore the returned bits alone do not universally distinguish local rejection from a dependency-produced result.

The following remain **documented_only**:

- **Pointer and calling ABI:** the exact runtime address model, native pointer width, callable-pointer representation, argument placement, and return-register convention.
- **Overflow:** the actual execution behavior when signed adjustment addition exceeds the signed 32-bit range.
- **Invalid storage:** behavior for unreadable fields, invalid address arithmetic, malformed table entries, or invalid callable targets. No explicit local recovery is shown.
- **Concurrency:** synchronization requirements and effects of concurrent changes to object fields, the selector, or table entries. No local synchronization is established.
- **Dependency behavior:** all domain semantics, writes, global effects, ownership changes, additional validation, and exceptional or nonreturning behavior.
- **Semantic names:** whether the bounded input represents a count, index, size, or another quantity; whether the adjustment represents an address, coordinate, or offset.
- **Result interpretation:** whether consumers treat either return half as status, data, or another encoding.

A plausible intent is to select between two operation modes while applying an object-specific adjustment. That is inference, not an additional requirement.
