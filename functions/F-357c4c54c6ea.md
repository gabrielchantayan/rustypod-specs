# F-357c4c54c6ea

## Purpose

F-357c4c54c6ea advances a caller-owned cursor through a linked structure. It changes the address stored in the cursor slot; it does not return a node address as a separate result.

The established behavior has two paths:

- If the current record has a nonzero link at byte offset +12, follow that link and then repeatedly follow links at +8, updating the cursor at every step.
- Otherwise, follow links at +4 while a relationship involving offset +12 holds, then conditionally replace the cursor with the final candidate.

**Inferred intent:** this resembles advancing an in-order iterator in a binary tree whose records contain a parent link at +4, a left-child link at +8, and a right-child link at +12. That interpretation explains the principal traversal paths, but the function does not establish a tree invariant, validate a sentinel convention, or define an abstract “end” value. The byte-offset behavior below is the contract; the tree terminology is explanatory only.

## Interface

### Input and output

The function receives one address identifying a writable cursor slot. The slot initially contains the address of the current record.

The supplied representation uses an integer slot to hold each address-bearing value. It is consistent with four-byte, 32-bit address-bearing slots. The offsets +4, +8, and +12 are explicit byte offsets, not element indices. Native pointer width, address-extension rules, alignment requirements, and endianness are not independently established.

The contract therefore distinguishes:

- **Cursor slot:** caller-owned storage containing an address-bearing value.
- **Current record:** the record addressed by the value presently in that slot.
- **Record links:** address-bearing values read from the offsets listed below.

There is no explicit result value and no status or error result. Successful completion is observable through the cursor slot and any intermediate writes to it.

### Relevant record layout

| Byte offset | Established use | Inferred tree role |
|---|---|---|
| +4 | Link used to select the next upward candidate | Parent |
| +8 | Link followed repeatedly after taking the initial +12 link | Left child |
| +12 | Initial branch selector, upward relationship check, and final guard | Right child |

No field at offset zero is directly accessed. No payload field is read or written. The function does not establish the complete record size or the meaning of any other storage.

### Preconditions for defined, terminating use

The cursor slot must be readable and writable. Every record field actually reached by the traversal must be readable for the width of its address-bearing value.

The initial cursor value is not checked for zero before use. A zero link is handled as a terminator only at particular points described below. In particular, a zero upward candidate is not automatically accepted as an end marker.

For ordinary tree-iterator semantics, the cursor slot should be separate from the record fields being traversed, links should remain stable during the call, and the relevant chains should terminate. The function does not enforce these conditions.

## Behavior

### Initial selection

The function reads the address from the cursor slot and reads the link at byte offset +12 of that record.

A nonzero link selects the downward path. A zero link selects the upward path.

There is no preliminary validation of the cursor address, the current-record address, or the record’s structure.

### Downward path

When the initial +12 link is nonzero:

1. The function writes that link value into the cursor slot.
2. It reads the +8 link of the record just selected.
3. If that link is nonzero, the function selects it, writes it into the cursor slot, and continues the same process.
4. A zero +8 link ends the traversal immediately.

The final cursor is the last nonzero record address selected along this path. The terminating zero is never written into the cursor slot by this path.

Intermediate writes are part of the behavior. The function does not first determine the final destination and then perform a single update. In particular, it updates the cursor before reading the selected record’s +8 field.

No +4 field is used on this path. After the initial +12 read, no further +12 field is needed.

A cycle consisting of nonzero +8 links has no detected termination condition. A malformed nonzero link can be written into the cursor before the subsequent field read fails.

### Upward path

When the initial +12 link is zero, the function obtains an upward candidate from the current record’s +4 field.

It then compares:

- the value at byte offset +12 of the candidate record; and
- the address currently held in the cursor slot.

If these values are equal:

- The candidate address is written into the cursor slot.
- The next candidate is read from offset +4 of the candidate record that was just selected.
- The comparison is repeated using the new candidate and the now-current cursor.

Thus, each successful comparison advances the cursor by one +4 link. The write to the cursor occurs before the next +4 field read.

The upward loop stops at the first candidate whose +12 link differs from the current cursor value. Stopping the loop does **not** immediately imply that this candidate will become the final cursor.

### Final conditional update

After the upward loop stops, the function reads the +12 field of the record currently addressed by the cursor.

- If that field differs from the candidate address, the function writes the candidate address into the cursor slot.
- If that field equals the candidate address, the function leaves the cursor unchanged.

These are two distinct relationship checks:

- The loop checks the candidate’s +12 link against the current record address.
- The final guard checks the current record’s +12 link against the candidate address.

Neither comparison may be replaced by the other. Both influence the final result.

The final +12 field is read anew. The function does not reuse the initial branch-selection value. After one or more upward steps, this read also concerns a different current record.

### Zero handling and termination

Zero has narrowly defined effects:

- An initial zero +12 link selects upward traversal.
- A zero +8 link ends downward traversal without storing zero.
- A zero +4 link becomes an upward candidate; the function then attempts to read the candidate’s +12 field.

Consequently, a conventional zero-terminated parent chain is not by itself a safe end-of-traversal representation. Safe termination of the upward path depends on the structure’s actual relationships, potentially including a nonzero sentinel or header record.

There is no traversal bound, cycle detector, or malformed-link recovery.

## Side effects

### Reads and writes

The only directly written storage is the cursor slot. The function performs no explicit record-field writes.

On the downward path, each selected record address is written before that record’s +8 link is read.

On the upward path, every successful relationship check is followed by a cursor write before reading the selected candidate’s +4 link. After the loop, there may be one additional cursor write, controlled by the final guard.

A call can therefore perform:

- Several cursor writes;
- One cursor write;
- No cursor writes, if the upward loop performs no step and the final guard suppresses replacement.

The last possibility is structurally available, although it may depend on aliasing or changing memory if the initial current record’s +12 field was read as zero and the final candidate is nonzero.

The supplied representation does not fix the relative evaluation order of the two operand reads within an equality comparison. No stronger ordering contract is established for those reads. The traversal and write ordering described above does not depend on choosing an operand evaluation order.

### Aliasing

If the cursor slot overlaps a record field, writing the cursor also changes that field’s stored value. Subsequent reads can observe the change.

The function contains no alias check, protective copy of the structure, or rollback. Ordinary tree-based descriptions are therefore conditional on non-overlapping cursor storage. The direct byte-offset behavior remains relevant when storage overlaps, but the usual graph interpretation may no longer hold.

### Ownership, allocation, and failure

The function does not explicitly allocate, release, acquire, or transfer ownership of any record or of the cursor slot. It does not invalidate the old record by an explicit operation.

There are no explicit global accesses and no explicit calls to other functions.

There is no handled error path. If a memory access is invalid, the supplied representation does not establish a portable failure result. Earlier cursor writes are not undone by any visible cleanup mechanism.

No synchronization or atomic access semantics are established. The function should not be treated as a concurrent traversal primitive.

## Dependencies

No opaque function dependencies are present in the supplied body. F-357c4c54c6ea performs direct memory reads, comparisons, address-offset accesses, and cursor writes.

Its external dependencies are structural rather than callable:

- A usable address representation for the stored links;
- Accessible storage at every field reached;
- Link relationships that produce the caller’s intended traversal;
- A termination convention compatible with the upward comparisons and final guard.

There is no visible callee whose memory ownership or global-state behavior must be assumed.

## Acceptance examples

The following examples are conditional static acceptance criteria, not executed tests. Named records denote distinct, valid, nonzero addresses. Fields remain stable, and the cursor slot does not overlap record storage unless stated otherwise.

### 1. Immediate downward destination

The cursor initially addresses record A. A’s +12 link addresses B, and B’s +8 link is zero.

Expected behavior:

- Write B into the cursor.
- Read B’s +8 link.
- Return with the cursor addressing B.

Zero is not stored.

### 2. Multiple downward steps

A’s +12 link addresses B. B’s +8 link addresses C. C’s +8 link addresses D. D’s +8 link is zero.

Expected cursor writes, in order: B, C, D.

The final cursor addresses D. No parent links are needed.

### 3. Direct upward replacement

A’s +12 link is zero. A’s +4 link addresses P. P’s +12 link addresses some record other than A.

The upward loop stops without writing the cursor. The final guard reads A’s +12 link, which remains zero. Since P is nonzero, the guard permits replacement.

Expected result: one cursor write, selecting P.

### 4. Climb before replacement

A’s +12 link is zero, and A’s +4 link addresses P. P’s +12 link addresses A. P’s +4 link addresses G. G’s +12 link differs from P.

The function first writes P into the cursor. It then stops climbing at candidate G.

If P’s +12 link differs from G, the final guard writes G. With the stated distinct addresses and P’s +12 link equal to A, that condition holds.

Expected cursor writes: P, then G.

### 5. Final guard preserves the climbed-to record

A’s +12 link is zero. A’s +4 link addresses H. H’s +12 link addresses A. H’s +4 link also addresses A.

The first upward comparison succeeds, so the cursor becomes H. The next candidate is A. A’s +12 link is zero, which differs from H, so the upward loop stops.

The final guard reads H’s +12 link and finds that it equals candidate A.

Expected result: the cursor remains H; there is no final write back to A.

This example establishes why the final guard matters without assigning H a required sentinel meaning.

### 6. Missing upward record

A’s +12 link is zero, and A’s +4 link is zero.

The function attempts to read the +12 field at the zero candidate address. It does not first return an end value or preserve the cursor through an explicit null-handling branch.

Successful completion is not guaranteed.

### 7. Nonterminating downward chain

A’s +12 link addresses B, and B’s +8 link addresses B.

The function repeatedly writes B and reads B’s +8 field. No cycle-detection exit is present.
