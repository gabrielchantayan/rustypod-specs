# F-3a8a0224b9df

## Purpose

F-3a8a0224b9df changes links among a supplied node, its child at byte offset 8, and the connection that previously led to the supplied node.

**Established static behavior:** the node initially referenced at offset 8 is selected for promotion. Its offset-12 link is copied into the supplied node’s offset-8 field. Associated offset-4 links are updated, a root or enclosing child slot is redirected, and the supplied node is attached at the promoted node’s offset 12.

**Inferred intent:** if node offsets 4, 8, and 12 denote parent, left child, and right child respectively, the operation is an in-place right rotation of a binary tree. This interpretation does not establish search ordering, balancing rules, sentinel conventions, or ownership.

The function neither searches for the supplied node nor validates the surrounding structure. Its observable result is a sequence of four-byte memory writes. A completed execution performs **five unconditional stores and, conditionally, one additional store: five or six stores in total**.

## Interface

### Arguments and result

The function accepts two address-bearing arguments:

| Argument | Observed use |
|---|---|
| Context address | Provides access to a four-byte field at byte offset 16 containing a root-record address. |
| Pivot address | Identifies the node whose offset-8 child is selected for promotion. |

The supplied representation uses 32-bit integer address values and four-byte link fields. It does not establish a portable interface using the host platform’s native pointer width.

There is no returned value or explicit success indicator. Completion is represented solely by memory mutation.

### Memory layout

All offsets below are byte offsets from the relevant object address.

| Object | Offset | Width | Established use |
|---|---:|---:|---|
| Context | 16 | 4 bytes | Address of the root record |
| Root record | 4 | 4 bytes | Root address, compared with the pivot and conditionally replaced |
| Node | 4 | 4 bytes | Link copied or replaced during parent-link updates |
| Node | 8 | 4 bytes | Promotion source, transfer destination, or enclosing child slot |

“Root record” names only the object reached through the context’s offset-16 field. Its other contents and broader purpose are not established.

The function performs no direct access to node offset 0 or payload fields. This does not protect such fields from writes through malformed or overlapping addresses.

For the ordinary tree-rotation interpretation:

- If the root slot does not equal the pivot address, the pivot’s offset-4 value must identify an accessible enclosing node.
- The enclosing node’s child links must be consistent with the intended rotation.
- Relevant objects and fields must not overlap in ways that interfere with the operation.

These conditions are caller obligations, not validations performed by the function. Exclusive access or suitable external coordination is required if observers must see a coherent structural operation.

## Behavior

### Terminology

The **pivot** is the node supplied as the second argument.

The **promoted node** is the address read from the pivot’s offset-8 field at the beginning of the operation. This selected address is retained; later writes to the pivot’s offset-8 field do not select a different promoted node.

The **transfer link** is the promoted node’s offset-12 field. Under the tree interpretation, its initial value identifies the subtree moved from the promoted node’s right side to the pivot’s left side.

The **root slot** is the offset-4 field of the record reached through the context’s offset-16 field.

### Ordered observable accesses

The following phases describe the established memory-access order. They distinguish repeated reads because those reads need not agree when memory overlaps or changes during execution.

**Promotion selection and transfer.** The operation first reads the pivot’s offset-8 field to select the promoted node. It then reads the promoted node’s offset-12 field and writes that four-byte value into the pivot’s offset-8 field.

The transfer link is read again for a zero comparison. If that read is nonzero, the transfer link is read a third time. This third value supplies the address of the object whose offset-4 field receives the pivot address.

Consequently, the copied transfer value, the value tested for zero, and the address used for the conditional parent-link write are separate observations. The function does not guarantee their equality. In particular, the nonzero comparison does not validate the address obtained by the following read.

**Parent inheritance.** After the optional transfer-parent write, the function reads the pivot’s offset-4 field and writes that value into the promoted node’s offset-4 field. This is the pivot’s parent link as observed at this stage, not necessarily its value on entry if earlier writes overlap it.

**Root inspection and enclosing reconnection.** The context’s offset-16 field is then read to locate the root record. The function reads the resulting root slot and compares it with the pivot address.

If the root slot equals the pivot address, that same located slot receives the promoted address. The enclosing node’s child fields are not inspected on this branch.

Otherwise, the pivot’s offset-4 field is read again to obtain an enclosing-node address. The enclosing node’s offset-12 field is compared with the pivot address:

- On equality, the enclosing node’s offset-12 field receives the promoted address.
- On inequality, the enclosing node’s offset-8 field receives the promoted address.

The selected enclosing-node address is retained for this comparison and replacement. The offset-8 fallback is not preceded by a check that the field contains the pivot.

**Final attachment.** After the enclosing connection is redirected, the promoted node’s offset-12 field receives the pivot address. Finally, the pivot’s offset-4 field receives the promoted address.

The function then returns without a value.

### Ordinary structural result

With stable memory, nonoverlapping objects, and consistent parent-child links:

- The promoted node takes the pivot’s former root or enclosing-child position.
- The promoted node receives the pivot’s former parent link.
- The promoted node’s former right child becomes the pivot’s left child.
- If that transferred child is nonzero, its parent link becomes the pivot.
- The pivot becomes the promoted node’s right child.
- The pivot’s parent link becomes the promoted node.

The promoted node’s left-child field and the pivot’s right-child field are not directly written. Their preservation as distinct fields depends on the nonoverlap assumptions.

For a root pivot, the promoted node inherits whatever parent-link value the pivot held when that link was read. The function does not independently clear the inherited value or replace it with a distinguished root sentinel.

### Branch precedence and inconsistent structures

Root-slot equality takes precedence over the enclosing-child logic. A matching root slot is redirected regardless of what the pivot’s parent link would otherwise imply.

For a non-root pivot, an offset-12 match takes precedence over offset 8. If both enclosing child fields contain the pivot, only offset 12 is selected for replacement.

If neither enclosing child field contains the pivot, offset 8 is nevertheless overwritten. The function does not search for another incoming link, report inconsistency, or undo preceding writes.

Aliasing can change later reads and destinations. In such cases, the ordered accesses above remain the applicable description; the ordinary rotation result is not guaranteed.

## Side effects

A completed execution performs these stores:

| Store | Condition |
|---|---|
| Replace the pivot’s offset-8 link with the observed transfer value | Unconditional |
| Set the transferred node’s offset-4 link to the pivot | Transfer-link zero comparison is nonzero |
| Set the promoted node’s offset-4 link to the observed pivot parent | Unconditional |
| Replace one root or enclosing child slot with the promoted address | Unconditional; destination depends on branching |
| Set the promoted node’s offset-12 link to the pivot | Unconditional |
| Set the pivot’s offset-4 link to the promoted address | Unconditional |

Thus there are **five unconditional four-byte stores**, plus **one conditional four-byte store**. The total is **five when the transfer check is zero, or six when it is nonzero**. These are executed-store counts, not counts of distinct destinations or changed values. Aliasing can merge destinations, and a store can write the value already present.

The operation is not transactional. The pivot’s child link changes before the enclosing connection is redirected, and the pivot’s parent link changes last. Intermediate memory states need not describe a valid tree.

No allocation, deallocation, external call, I/O, or direct reference to named global storage appears in the supplied body. Writes through the arguments could still affect globally reachable storage.

No ownership transfer or release is established. Existing address values are relinked; object lifetime and allocation ownership remain external.

There is no explicit error result, validation path, or rollback. If an access fails, completion and fault signaling depend on the execution environment. Earlier writes have no established recovery mechanism.

## Acceptance examples

These examples are conditional consequences of static evidence, not executed tests. Unless an example states otherwise, assume stable memory, accessible fields, nonoverlapping objects, and the conventional parent/left/right layout.

### Root pivot with a nonzero transfer

Initially, the root slot contains pivot P, P’s parent link is H, P’s left child is Q, and Q’s right child is a nonzero node T.

On completion:

- The root slot contains Q.
- Q’s parent link is H.
- Q’s right child is P.
- P’s parent link is Q.
- P’s left child is T.
- T’s parent link is P.

Q’s left child and P’s right child retain their prior values. H is copied, not normalized. This execution performs six four-byte stores.

### Zero transfer

Initially, P’s left child is Q, and Q’s offset-12 field remains zero throughout the transfer reads.

P’s offset-8 field becomes zero. No transferred-node parent-link store occurs. The enclosing connection, Q’s parent link, Q’s right-child link, and P’s parent link are still updated.

This execution performs five four-byte stores. The zero handling applies to the transfer link; it does not make a zero promoted-node address valid.

### Non-root right-child position

The root slot does not contain P. P’s parent is A, and A’s offset-12 field contains P.

A’s offset-12 field becomes Q; its offset-8 field is not selected for replacement. Q receives A as its parent, and P becomes Q’s right child.

### Non-root left-child position

The root slot does not contain P. P’s parent is A, A’s offset-12 field does not contain P, and A’s offset-8 field contains P.

A’s offset-8 field becomes Q. A’s offset-12 field remains unchanged.

### Neither enclosing child matches

The root slot does not contain P. P’s parent is A, but neither child field of A contains P.

The function still writes Q to A’s offset-8 field. It supplies no explicit error result and does not restore the preceding link changes. Structural validity is not an acceptance condition for this malformed input; the unconditional fallback mutation is.

### Both enclosing children match

The root slot does not contain P, and both child fields of A contain P.

The offset-12 comparison succeeds, so A’s offset-12 field becomes Q. A’s offset-8 field remains P. The function does not repair the duplicate incoming relationship.

### Root equality overrides enclosing links

The root slot contains P, and P’s parent link contains H.

The root slot becomes Q without an enclosing-child comparison through H. Q inherits H; a valid root rotation does not require H to be cleared by this function.
