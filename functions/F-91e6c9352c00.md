# F-91e6c9352c00

## Purpose

F-91e6c9352c00 unconditionally copies a four-byte field within a caller-supplied object. If a separate one-byte gate is zero, it then searches a linked structure for the first reachable record whose one-byte marker is zero. It publishes that record’s address, or zero if traversal reaches a null address.

The head access and the publication access each evaluate a global base expression. The supplied material does not establish that this expression is immutable or that both evaluations necessarily designate the same region. Consequently, the search origin and the publication destination must be described separately.

The copy, selection rule, and conditional publication are established static behavior. Application interpretations such as “snapshot,” “available record,” or “cached selection” are not established.

## Interface

### Input object

The function accepts one address-bearing argument represented as a 32-bit integer in the supplied material. It uses that argument to access these object-relative locations:

| Byte offset | Width | Access | Established role |
|---|---:|---|---|
| `0x14` | 1 byte | Read | Zero permits the search |
| `0x7c` | 4 bytes | Read | Source value |
| `0x84` | 4 bytes | Write | Destination value |

The source field is read and the destination field is written before the gate is read.

A conventional contiguous allocation encompassing these fields would extend through offset `0x87`, inclusive. The function requires the listed accesses, not access to every intervening byte. No object-size argument or bounds information is supplied.

A zero argument is not an explicitly supported empty-object case. The function attempts the source-field access without first validating the object address.

### Global base and relative fields

The body uses a global base expression in two places:

- To locate the head field before traversal.
- To locate the result field after traversal terminates.

Under the four-byte element interpretation in the supplied representation, the relative layout is:

| Relative byte offset | Width | Access | Established role |
|---|---:|---|---|
| `0x00` | 4 bytes | Read through the head-access base evaluation | Initial record address |
| `0x08` | 4 bytes | Write through the publication-base evaluation | Selected address or zero |

The result is addressed as element two, corresponding to byte offset `0x08` for four-byte elements. The intervening element at offset `0x04` is not explicitly accessed.

This is a layout relative to each evaluated base, not proof of one fixed global-storage allocation. If the two base evaluations designate the same region, the head and result occupy the stated offsets within that region. If they designate different regions, the head is read from the first region and the result is written into the second.

The supplied material contains no declaration establishing the base expression’s storage representation, mutability, or invariance. In particular, it does not establish the width of any separate storage that might hold the base itself. The two source-level evaluations must not be treated as proof of two physical memory reloads.

### Traversed records

Each nonzero address reached during traversal is used with this layout:

| Byte offset | Width | Access | Established role |
|---|---:|---|---|
| `0x1e` | 1 byte | Read | Zero selects the record |
| `0x2c` | 4 bytes | Read only after a nonzero marker | Next record address |

A zero address terminates traversal without a record access. A record with a zero marker is selected without reading its link.

The four-byte head and link fields carry addresses in the represented execution model. This does not establish compatibility with a wider-pointer environment.

### Output and preconditions

There is no explicit return value, status code, or error object. Observable results are memory writes and, for some inputs, failure to terminate.

Successful completion requires:

- Accessible source, destination, and gate locations in the object.
- For a zero gate, a usable head-access base and readable head field.
- Readable marker bytes for every visited nonzero record.
- Readable links only for visited records with nonzero markers.
- If traversal terminates, a usable publication base and writable result field.

These requirements concern the addresses actually used at the time of each access. Neither address validity nor ownership is checked locally.

## Behavior

### Object update and gate

The function reads the complete four-byte value at object offset `0x7c` and writes it to object offset `0x84`. The value is copied without masking, numerical conversion, or a nonzero requirement. The old destination value is not read.

Only after this write does the function read the gate at offset `0x14`.

A nonzero gate ends the operation without entering the global search. On this path, neither of the two global base expressions is evaluated by the shown search-and-publication logic, the head field is not read, and the result field is not explicitly written.

Every nonzero gate-byte pattern has the same branch effect. Signedness of the byte does not alter the zero-versus-nonzero decision.

A zero gate enables traversal.

### Search origin

On the search path, the function evaluates the global base expression for the head access and reads the four-byte address at relative offset zero.

This evaluation occurs after the object destination has been updated. If the base is mutable and its backing storage aliases that destination, the copy can affect the base used to locate the head. The evidence does not establish whether such aliasing is possible, but it does not exclude it.

The base used for the head is not shown being retained as the base for the final result write. The head address itself becomes the starting point of traversal; the head field is not repeatedly read.

A zero head immediately selects zero. No marker or link is accessed in that case. The copied object value is not used as a fallback result.

### Selection and traversal

For each nonzero record address, the marker byte at offset `0x1e` determines the next action:

- A zero marker selects the current record.
- A nonzero marker requires reading the four-byte link at offset `0x2c` and continuing from that address.

Selection therefore follows link order. Marker magnitude has no additional meaning: `1`, `0x80`, and `0xff` all require following the link.

Traversal stops at the first zero marker or the first zero address. An all-nonzero finite chain ending in a zero link selects zero, not the final record.

The function does not explicitly write record markers or links. It performs no cycle detection, traversal bound, timeout, or cancellation check.

### Publication

After a stopping condition is reached, the function evaluates the global base expression again for publication. It writes the selected four-byte address, including zero, at offset `0x08` relative to that evaluation’s result.

The previous result-field contents are not inspected. A terminating search performs the write even if the destination already contains the selected value.

The publication destination is not established to be relative to the same base value used for the head access. No equality check between the evaluations is shown, and no saved head-access base is explicitly reused for publication.

There are no explicit writes during traversal between the head read and publication. Thus, the body itself shows no intervening traversal write that changes a mutable base. This does not supply the missing declaration or establish invariance against external changes.

### Observable access order

The source-level ordering is:

1. Read the four-byte object source.
2. Write the four-byte object destination.
3. Read the one-byte object gate.
4. On the zero-gate path, evaluate the global base expression for the head access, then read the head.
5. Read each reached record’s marker; read its link only when that marker is nonzero.
6. After termination, evaluate the global base expression for publication, then write the selected address to its result field.

The base evaluations are included because they determine the effective access destinations. They are not assigned an unsupported physical load count.

This ordering describes the supplied static representation. It does not establish machine-level atomicity, memory barriers, or synchronization guarantees.

## Side effects

### Writes and aliasing

There are two explicit write operations:

- The object destination write, before gate evaluation.
- The result-field write, only after a zero-gate traversal terminates.

No explicit write targets the source field, gate, head field, markers, or links as such. That statement does not imply their underlying bytes cannot change through aliasing with a write destination.

The object, base-related storage, head region, publication region, and records are not established to be disjoint. Earlier writes must therefore be considered when determining later access values and addresses.

Two distinct aliasing possibilities matter:

- The object destination may overlap a field reached through the evaluated base, changing that field before it is read.
- If the base is held in mutable storage, the object destination may overlap that storage, changing which region a later base evaluation designates.

The second case concerns the base itself, not merely a head or result field within a presumed fixed region. Its feasibility and exact representation remain unresolved.

The final result write can also affect aliased storage. The shown body performs no further explicit data access after that write.
