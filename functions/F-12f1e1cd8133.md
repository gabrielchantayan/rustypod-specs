# F-12f1e1cd8133

## Purpose

F-12f1e1cd8133 selects between calculated-target reconciliation and fallback reconciliation to zero. When its initial state check indicates adjustment is needed, it invokes dependencies in potentially unbounded loops, then performs shared completion processing.

Completion processing compares identifiers and conditionally decrements a signed 16-bit field, clears fields, or dispatches a three-word event.

**Established static behavior:** Address capture and later pointer-holder reloads are distinct operations. Consequently, entry checks, adjustment loops, and return expressions need not address the same storage when pointer holders change. The routine does not itself ensure adjustment progress or successful arrival at the calculated target.

**Inferred intent:** The dependencies appear to adjust a resource or operating level and then handle completion or notification. The resource, event meanings, and significance of numeric results are not established.

## Interface

### Invocation and result

- No explicit arguments.
- Returns an unsigned 32-bit value.
- Reads shared pointer holders, pointed-to storage, and dependency results.
- Contains no explicit allocation, release, or ownership-transfer operation. Dependencies’ memory-management behavior is unknown.

The return is path-dependent:

- Calculated-target equality: a fresh current-state read through a freshly loaded pointer.
- Fallback initial zero: zero.
- Completion identifier mismatch: nine.
- Completion decrement: ten.
- Completion clearing: zero.
- Completion dispatch: the event’s middle 32-bit word after dispatch returns.

Nine and ten are not unique status indicators: the calculated-target equality path can return those values directly from state storage.

## Behavior

### Entry gating and control-address capture

The routine first reads the control-block pointer holder and retains that address for any later target calculation.

The initial gate does **not** use that retained address. Its two operands independently use the control-block pointer holder:

- A 32-bit flags read, masked with `0x46`.
- A 32-bit read at offset 12.

These operands are combined with bitwise OR. Both participate in the expression; a nonzero masked flags value does not short-circuit the gate-word access. Their relative evaluation order is not established. If the holder changes, either access can use a different block from the retained block or from the other access.

The mask selects flag bits 1, 2, and 6, numbering the least significant bit as bit 0.

If the combined result is nonzero, fallback processing is selected. The auxiliary gate and D-01 through D-03 are skipped.

If the combined result is zero:

1. The auxiliary gate is read and converted to unsigned 32-bit.
2. A nonzero converted value selects fallback.
3. Otherwise, D-01 is invoked. A nonzero result selects fallback.
4. A zero D-01 result causes D-02 to run, then D-03.
5. Immediately after D-03 returns, the current-state pointer holder is read and its address retained.
6. Only then is D-03’s result tested: zero selects target calculation; nonzero selects fallback.

Thus, the current-state address capture occurs even when D-03 selects fallback. It does not occur when an earlier gate selects fallback.

These sequences assume dependencies return normally.

### Target calculation

Target calculation uses the control-block address retained before entry gating, not a fresh holder read. It reads that block’s flags and then its requested value, both as unsigned 32-bit quantities. These reads occur after the gate dependencies and can observe contents different from those used at entry.

If flag bit 0 is clear, the requested value becomes the provisional target, and the limit is not read.

If bit 0 is set:

- The provisional candidate initially equals the requested value.
- The limit is read for an unsigned comparison against the requested value.
- If that limit read is less than or equal to the requested value, the limit is read **again**, and this second value replaces the candidate.
- A lower bound is applied to the candidate: one if bit 7 is clear, zero if bit 7 is set.

With stable limit storage, the candidate before the lower bound is the unsigned minimum of limit and request. Without stability, that minimum interpretation is invalid: the second limit read can exceed both the first limit read and the request.

The lower bound can itself exceed a stable limit. For example, with bit 0 set, bit 7 clear, and both limit and request zero, the provisional target becomes one.

The saved flags then determine overrides:

- Bit 3 set: target becomes one if bit 4 is clear, otherwise zero.
- Bit 3 clear and bit 5 set: a nonzero provisional target becomes zero; zero remains zero.
- Bit 4 has no effect when bit 3 is clear.
- With bit 3 set, bit 5 does not override the bit-3/bit-4 decision.

Comparisons and target values are unsigned 32-bit. The calculation introduces no arithmetic addition or subtraction that could overflow.

### Calculated-target equality and adjustment

The routine reloads the current-state pointer holder and compares the word at that address with the target.

If equal, it immediately reloads the pointer holder **again** and returns the word at that newly obtained address. Neither the address nor the value is required to match the comparison access. Adjustment and completion processing are skipped.

If unequal:

1. F-3b7c5b30bd55 receives 22.
2. F-f120802e6343 returns an opaque 32-bit token, retained for later use.
3. While the word at the previously captured current-state address is unsigned-greater than the target, F-c6c2e1b896e3 is invoked.
4. After that loop ends, while the word at the same captured address is unsigned-less than the target, F-a870a0416476 is invoked.
5. F-82729ee22091 receives the retained token.
6. Completion processing follows.

The loop address is the address captured immediately after D-03, not necessarily the address used by the equality comparison. Later holder changes do not redirect these loop reads. Changes to the pointed-to storage remain observable.

The target stays fixed. Setup dependencies may change state before the first loop condition, so an initial inequality does not guarantee any adjustment call.

The loops run only in the stated order. If the second loop overshoots above the target, the first loop is not revisited. Completion therefore does not establish final equality.

### Fallback reconciliation

On fallback entry, the routine captures an address from the fallback-state pointer holder. It then separately reloads that holder and tests the signed 32-bit word at the reloaded address.

If this initial test reads zero, the routine returns zero immediately, even if storage at the captured address is nonzero.

Otherwise:

1. F-3b7c5b30bd55 receives 22.
2. F-f120802e6343 supplies the retained 32-bit token.
3. F-c6c2e1b896e3 is repeatedly invoked while the word at the **captured** fallback address is nonzero.
4. F-82729ee22091 receives the token.
5. Completion processing follows.

The initial test and loop can observe different storage. In particular, a nonzero initial test can lead to setup followed by zero adjustment calls if the captured word is already zero.

Both positive and negative values satisfy the loop’s nonzero condition. The routine does not directly write either reconciliation-state word.

### Completion processing

The shared continuation is associated with F-5a0e2e961d01. The supplied body shows the continuation directly, not a separate invocation at this point.

After F-82729ee22091 returns, the routine:

1. Reads the completion-record address holder to retain a base for accesses at offsets `0x2c4` and `0x2c8`.
2. Separately reads that holder again to derive the identifier address at offset `0x2c0`.
3. Invokes D-04.
4. Compares the identifier at the captured identifier address with a reference identifier obtained through its pointer holder.

The two completion-address captures need not agree if the holder changes. D-04 runs after both captures; changes it makes to the holder do not redirect these captured accesses, although changes to the addressed contents can affect subsequent decisions.

The following branches assume normal dependency returns:

| Observed condition | Ordered actions | Result |
|---|---|---|
| Identifiers differ | Invoke D-05; select result nine | 9 |
| Identifiers match; signed 16-bit field is at least two | Separately reread and decrement that field; store the 16-bit result; invoke D-05; select result ten | 10 |
| Identifiers match; signed field is below two; offset `0x2c8` is zero | Store 16-bit zero at `0x2c4`; store 32-bit zero at the captured identifier address; invoke D-05; select result zero | 0 |
| Identifiers match; signed field is below two; offset `0x2c8` is nonzero | Invoke D-05; initialize event words to 15, 0, 22; dispatch through F-c81f7910921f; read the middle word | Post-dispatch middle word |

An identifier mismatch skips the count and offset-`0x2c8` checks. A count of at least two skips the offset-`0x2c8` check. Negative counts enter the below-two cases.

For decrementing, the comparison read and update read are distinct. With stable storage, values from 2 through 32767 become 1 through 32766. The subtraction is evaluated at 32-bit integer width, so decrementing any signed 16-bit reread cannot overflow that arithmetic width. If an intervening change supplies minus 32768, the mathematical result is minus 32769; its conversion back into signed 16-bit storage is not resolved here.

In the dispatch case, zero is only the middle word’s initial value. The dependency receives writable event storage, and the return reads it afterward.

## Side effects

Direct shared-memory writes occur only in completion processing:

- A 16-bit count update; or
- A 16-bit zero followed by a 32-bit identifier zero.

There is no direct write to the field at offset `0x2c8`, the pointer holders, or either reconciliation-state word.

Temporary event storage is initialized only on the dispatch branch, after D-05 returns. Its address is valid for the current invocation. Passing it does not establish ownership transfer, permission to retain it, or safe access after return.

Dependencies may affect globals, pointer holders, addressed storage, resources, or memory ownership. No preservation or release guarantees are available.

D-04 and D-05 surround completion decisions and writes in a pattern consistent with synchronization. That is inferred intent, not proof of exclusion or ordering guarantees.

There is no visible timeout, iteration bound, failure-status check, exception recovery, or compensating operation. A dependency that does not return can prevent every subsequent action. An adjustment condition that remains true can produce an unbounded loop.

## Acceptance examples

These are conditional static expectations, not executed tests. Assume valid storage and normal dependency returns. Stability assumptions apply only where stated.

1. **Early gate rejection.** With stable entry flags containing `0x02` and an initial fallback test reading zero, the result is zero. The initial gate-word operand is still evaluated. The auxiliary gate, D-01 through D-03, adjustment setup, and completion are skipped.

2. **Control capture differs from gate blocks.** Suppose the retained control address is block A, while subsequent holder reads make the initial flags and gate-word accesses use other blocks. If those gates permit calculation, target calculation still uses A.

3. **Current address captured before rejection.** If D-03 returns nonzero, the current-state pointer holder is nevertheless read before fallback entry. The captured current-state address is not used for the fallback loop.

4. **Stable minimum and lower bound.** With entry permitted, flags containing only bit 0, and stable zero limit and request, the target is one. Also setting bit 7 makes it zero.

5. **Changing limit defeats minimum semantics.** With bits 0 and 7 set, request five, a comparison limit read of three, and an assignment limit reread of nine, the target is nine, absent subsequent overrides.

6. **Flag override precedence.** With entry permitted, bit 3 set and bit 4 clear produce target one, even when bit 5 is set. Setting bit 4 as well produces zero.

7. **Equality return can use another object.** Suppose the target is seven, the equality access reads seven from one object, and the return’s holder reload points to another object containing eleven. The result is eleven; adjustment and completion are skipped.

8. **Loops use the earlier capture.** Suppose the post-D-03 capture points to a word containing the target, while the later equality access addresses a different, unequal word. Setup runs, but both loops can make zero adjustment calls if the captured word remains at target.

9. **Fallback test and loop differ.** Suppose fallback capture selects a zero word, but the separately reloaded initial-test address contains minus one. Setup runs, the fallback loop makes no adjustment calls, and completion follows.

10. **Fallback early return ignores captured contents.** If the initial-test reload addresses zero, the result is zero even when the captured fallback word is nonzero.

11. **Overshoot does not restart downward adjustment.** For target three, downward calls may move captured state from five to four to two. If one upward call then moves it to four, adjustment ends and completion follows.

12. **Stable completion decrement.** Matching identifiers and a stable count of two produce a 16-bit store of one, then D-05, then result ten.

13. **Negative completion count and clearing.** Matching identifiers, count minus one, and a zero offset-`0x2c8` field produce the 16-bit zero store, then the identifier zero store, then D-05, then result zero.

14. **Dispatch determines the result.** In the dispatch branch, an F-c81f7910921f call that changes the middle event word from zero to six and returns causes result six.

15. **No progress guarantee.** If a loop condition stays true and its dependency keeps returning, the routine can continue indefinitely without token restoration or completion.
