# F-ea943f448a78

## Purpose

F-ea943f448a78 modifies selected fields in an indirectly addressed record, transfers the halves of two 32-bit input fields into that record, and performs a bounded copy into record offset 0x52. On normal return, it returns the address of that copy destination.

The local copy writes at most five destination bytes. It can transfer an initial four-byte word, followed by one byte, or transfer individual bytes from the outset. A zero detected during individual-byte copying triggers a separate dependency call whose effects are unresolved.

Record initialization and installation of a short format identifier are inferred purposes, not established semantic requirements. The supplied evidence does not establish the actual source bytes or any filesystem-specific meaning.

This contract describes static evidence only. No runtime tests have been performed.

## Interface

### Inputs and address model

The visible interface has two 32-bit integer-valued arguments used as addresses:

- **First input:** Addresses an object with a readable 32-bit field at byte offset 0x04. The field supplies the **record base**.
- **Second input:** Addresses an object with readable 32-bit fields at byte offsets 0x0C and 0x10.

The record base is captured before the initial dependency call. The two fields in the second object are read later, at separate points interleaved with record writes.

Addresses and address calculations are represented at 32-bit width. The evidence does not establish a portable interface for wider pointers or a supported contract for arithmetic that wraps the address space.

### Output

On normal return, the result is the captured record base plus 0x52, designated below as the **copy destination**.

The visible result is pointer-valued and associated with a 32-bit unsigned element type. This does not establish four-byte alignment, a 32-bit object at the returned address, string termination, or ownership transfer.

There is no explicit success status, error code, or alternate failure result.

### Storage and execution preconditions

Execution requires valid storage for every access actually reached:

- A 32-bit read at first-input offset 0x04.
- The later 32-bit reads at second-input offsets 0x0C and 0x10.
- Five 16-bit record stores and two 8-bit record stores.
- The copy’s conditional 32-bit destination store and its individual 8-bit stores.
- Every 32-bit source read, including those used to select a single byte.

The source therefore requires more than five readable bytes in some paths. With five individual-byte iterations, the final source read starts four bytes after the initial source address and extends through byte offset seven.

All reached accesses must satisfy the execution environment’s alignment and protection requirements. An unaligned copy destination skips the word-copy attempt; it does not eliminate unaligned 32-bit source reads.

These conditions are not checked. The visible body provides no recovery from invalid addresses, access faults, unsupported alignment, or dependencies that do not return.

## Behavior

### Base capture and initial call

### Fixed writes and interleaved input reads

Two unresolved global values participate in the initial stores: a displacement and an initial value.

After the initial dependency returns, the established order is:

1. Capture the global displacement for use in the second store’s destination.
2. Store the initial value’s low 16 bits at the record base plus the displacement used by the first store’s address expression.
3. Read the 32-bit field at second-input offset 0x0C.
4. Store that field’s low 16 bits at the record base plus the captured displacement minus 0x38.
5. Store that field’s high 16 bits at record offset 0x1C8.
6. Read the 32-bit field at second-input offset 0x10.
7. Store that field’s low 16 bits at record offset 0x1CA.
8. Store that field’s high 16 bits at record offset 0x1CC.
9. Store the byte 0x00 at record offset 0x1BE.
10. Store the byte 0x0C at record offset 0x1C2.

Each high half is selected by interpreting the corresponding field as unsigned and shifting right by 16 bits. Signed interpretations of the original bit pattern do not cause sign extension.

The 16-bit stores retain only the low 16 bits of their supplied values. Their physical byte order depends on target endianness, which is not independently established.

The displacement is both captured separately and referenced in the first store’s expression. The evidence does not establish an atomic snapshot across those uses or the exact number and ordering of machine-level loads within that expression. If the displacement remains unchanged between those uses, the second destination is 0x38 bytes before the first. That relationship is not unconditional for mutable or aliased global storage.

### Aliasing and read timing

The input fields are not captured together at entry. Earlier writes can affect later reads if the corresponding storage overlaps:

- The initial 16-bit store precedes the read at second-input offset 0x0C.
- Both stores derived from that field precede the read at second-input offset 0x10.
- All fixed stores precede the copy phase and can affect source storage if it overlaps their destinations.
- Copy writes can affect later copy reads if source and destination overlap.

There is no established nonoverlap guarantee among the inputs, record destinations, globals, and static source.

The captured displacement determines destinations that can overlap other record fields. For overlapping bytes, a later local store replaces the earlier stored value, while intervening reads observe memory at their own points in the sequence.

The copy is not established to have overlap-safe behavior. Its result depends on the values actually read, not merely on the source contents at function entry or even at copy entry.

### Copy setup and word-screening path

After the fixed stores, the function captures a separate 32-bit global screening value. It selects a statically referenced source, sets the copy destination to record offset 0x52, and establishes a five-byte budget.

If the copy destination is not divisible by four, individual-byte copying starts immediately with the full budget.

If the destination is divisible by four, the function first reads a 32-bit source word. It calculates a screening result by combining these three 32-bit quantities with bitwise AND:

- The source word minus the screening value, using unsigned 32-bit subtraction.
- The bitwise complement of the source word.
- The screening value shifted left by seven bits, retaining the represented 32-bit result.

A nonzero screening result prevents the word store. Individual-byte copying then starts at the original source and destination positions with budget five. That phase rereads the source; the earlier screening read is not itself the first individual-byte transfer.

A zero screening result permits a single 32-bit store of the source word to the copy destination. The source and destination positions advance by four bytes, leaving a one-byte budget.

No second word store is possible because the remaining budget is less than four.

The screening value is unavailable. The expression resembles a zero-byte detector, but reliable zero detection is inferred intent rather than an established property. In particular, a permitted word store does not test its four destination bytes individually. Embedded zero bytes in that word do not independently trigger the final dependency.

### Individual-byte copying

While a positive budget remains, each individual-byte iteration performs the following observable actions in order:

1. Read a 32-bit quantity from the current source address.
2. Store its low eight bits at the current destination address.
3. Advance both positions by one byte and reduce the budget by one.
4. Test whether the selected byte was zero.

The byte tested is the selected value from the read, not a fresh read of destination memory.

The source access remains 32 bits wide even though only eight bits are stored. Successive source addresses differ by one byte and can therefore be unaligned.

On a little-endian target, the low eight bits correspond to the byte at the current source address. Without an established byte order, that correspondence is conditional; the operation established by the evidence is selection of the 32-bit read’s low eight bits.

A nonzero selected byte permits another iteration if budget remains. When the budget is exhausted without a selected zero byte, the function returns the original copy destination without the final dependency call.

A selected zero byte is stored before copying stops. The final dependency is then called even if that byte consumed the last available position.

The remaining budget can be zero through four. It is four if the first individual-byte transfer starts with the full budget and selects zero. It is zero if the fifth position selects zero, including after an initial four-byte transfer.

The argument pattern suggests padding, but the dependency is not established to zero-fill, limit its writes to the remaining destination region, preserve memory, or return normally.

If it returns, F-ea943f448a78 returns the original copy destination. There are no subsequent visible local record writes.

## Acceptance examples

These examples are conditional consequences of the static operations, not executed tests. Each assumes reached accesses are valid and reached dependencies return.

1. **Unsigned half extraction.**  
   If the field actually read at second-input offset 0x0C is 0x12345678, its low-half store receives 0x5678 and the store at record offset 0x1C8 receives 0x1234. If the later field read is 0x89ABCDEF, the stores at offsets 0x1CA and 0x1CC receive 0xCDEF and 0x89AB. These describe store values; subsequent overlapping writes can change the final bytes.

2. **Captured record base.**  
   If F-45fafa2bdf50 replaces the first object’s base field, later local addressing still uses the base captured before that call. Continued execution additionally requires that the captured storage remain valid.

3. **Later input observation.**  
   If the initial dependency changes second-input offset 0x10, and no intervening write changes it again, the later read uses that changed field rather than its entry value.

4. **Conditional five-byte identifier copy.**  
   On a little-endian target, suppose the source contains the five nonzero ASCII bytes spelling “FAT32” when the copy phase begins. Suppose also that destination writes do not alter values used by subsequent source reads, and no other actor changes the relevant source or destination contents during copying. Under those conditions, the local copy leaves those five bytes at the destination, regardless of whether the initial word transfer is permitted. No selected byte is zero, so the final dependency is not called. The local logic appends no terminator.

5. **Forward overlap changes the result.**  
   On a little-endian target, suppose the source is four-byte aligned, begins with “FAT32” at copy entry, and the destination is one byte after the source. Assume the overlapping storage is readable and writable and remains otherwise undisturbed. The destination is unaligned, so copying uses individual-byte transfers. Each store replaces the byte that the next read will select. The five destination bytes become “FFFFF,” not “FAT32.” No selected byte is zero. Initial source contents alone therefore do not determine the copied result.

6. **Zero on the third individual-byte transfer.**  
   If individual-byte copying starts with budget five and the third value actually selected is zero, three byte stores occur. The final dependency receives the original destination plus three and remaining budget two in both budget positions. The dependency’s effect on the remaining destination bytes is unknown.

7. **Zero in the last position.**  
   If the fifth position selects zero, that zero is stored and the final dependency is called with remaining budget zero. Exhaustion does not suppress this call.

8. **Rejected word screening.**  
   At an aligned destination, a nonzero screening result causes no word store. Individual-byte copying begins at the original positions with budget five and performs a fresh source read.

9. **Permitted word containing zero.**  
   If the screening expression evaluates to zero for a word containing a zero byte, the whole word is stored. That embedded zero does not trigger the final dependency. The call depends on the subsequently selected fifth-position byte.

10. **Aliased later input field.**  
    If a store derived from the field at second-input offset 0x0C changes storage belonging to offset 0x10, the later 32-bit read observes the resulting contents, not necessarily the original field.
