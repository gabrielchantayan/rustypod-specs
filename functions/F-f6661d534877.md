# F-f6661d534877

## Purpose

F-f6661d534877 dispatches a 32-bit event into shared-storage updates, object-counter updates, and dependency calls. Recognized events are 1, 4, 8, 32, and 64. Every locally returning path returns the 32-bit value zero.

The contract concerns explicit access widths, address selection, ordering, and calls. Application meanings are not established. “Active,” “initialization,” “selection,” and “notification” are descriptive labels, not proven domain semantics.

Some addresses are captured at entry; others are obtained by later reads of global pointer storage. These are distinct operations. They must not be treated as one stable address per storage region.

Invalid indices on events 4 and 8 invoke F-a817d8d58c10, which is marked non-returning. No ordinary error return is established.

## Interface

### Arguments and return value

| Argument | Width and supported interpretation |
|---|---|
| Object address | 32-bit address-valued input. Certain paths access a 32-bit counter at byte offset 720 or pass the address to dependencies. |
| Event | Signed 32-bit discriminator. |
| Detail | Unsigned 32-bit discriminator or index. |
| Auxiliary value | Unsigned 32-bit value copied into a mutable local cell. |

Normal completion returns zero as a 32-bit value. Dependency return values do not become the function’s return value.

Two mutable local cells initially contain the original detail and auxiliary inputs. Event 4 exposes both cells by address. Event 64, detail 6, exposes the detail cell by address.

### Storage layout

The state-block pointer identifies storage with these fields:

| Byte offset | Width | Locally observed role |
|---|---|---|
| 0 | 8 bits | Flag cleared on several paths |
| 1 | 8 bits | Active flag |
| 2 | 8 bits | Control-code field |
| 3 | 8 bits | Initialization flag |
| 4 | 32 bits | Selection-like field |
| 8 | 32 bits | Value read for notification calls |

The indexed-block pointer identifies two groups of three 32-bit entries. For a valid index \(i\), the corresponding offsets are \(4i\) and \(12+4i\).

The reset-block pointer identifies at least three writable 32-bit entries, at offsets 0, 4, and 8. Another global value supplies an argument to the event-64 indirect call.

These descriptions do not establish allocation boundaries, alignment, ownership, or disjointness. Blocks may overlap each other, the object, or global pointer storage. A write may therefore affect a later read even without an intervening dependency call.

### Entry-time address acquisition

Before dispatch, the visible sequence is:

1. Read the state-block global pointer and retain that address.
2. Read the indexed-block global pointer and retain that first address.
3. Read the indexed-block global pointer again and compute a second indexed address by adding four times the original detail.
4. Initialize the mutable detail and auxiliary cells.

The two indexed-pointer reads are separate. Their values are not proven equal. Computing the second indexed address does not dereference the indexed block.

Subsequent references to the **captured state address**, **first captured indexed base**, and **precomputed indexed address** mean these particular entry-time values.

The representation uses 32-bit address arithmetic. Scaling the unsigned detail by four retains a 32-bit result; no wider index or overflow validation is visible. Valid indexed accesses use only details 0–2. Address calculations for other details still occur at entry but do not themselves establish a pointed-to access.

### Preconditions

There are no explicit null checks, bounds checks beyond the event-4/event-8 index check, synchronization operations, or general pointer-validity checks.

Each path requires its executed global reads, pointed-to accesses, and dependency arguments to be valid. Even an ignored event performs the entry-time global-pointer reads. It does not, however, require a usable object counter merely because other paths access that counter.

For events 4 and 8, the valid detail range is unsigned 0–2. A bit pattern representing a negative signed integer is not a valid index.

## Behavior

### Dispatch

Only exact event matches 1, 4, 8, 32, and 64 receive special handling. Other events return zero after the entry work, with no further explicit pointed-to access, mutation, or dependency call.

### Event 1: control codes

Recognized details are 5, 6, 7, and 8. Other details return zero without a control-code store or dependency call.

For detail 5, 7, or 8:

1. Read the state-block global pointer afresh and write the detail as one byte at offset 2 of that address.
2. Clear the active byte at offset 1 of the captured state address.
3. Call the unidentified notification-context provider.
4. After it returns, read the 32-bit field at offset 8 of the captured state address.
5. Call F-23aadb16b673 with the provider’s result and that field value.
6. After that call returns, clear byte offset 0 of the captured state address.
7. Return zero.

The initial control-code store and subsequent state accesses need not address the same block. The recognized values fit in one byte.

For detail 6:

1. Read the state-block global pointer afresh and store byte value 6 at offset 2.
2. Read the active byte at offset 1 of the captured state address.
3. If that byte is nonzero, return zero.
4. Otherwise, perform the activation sequence.

The active-byte test occurs after the control-code store. If the relevant addresses overlap, the store may affect the test. The early-return path does not explicitly clear byte offset 0 or call a notification dependency.

### Activation sequence

Activation is reached from:

- Event 1, detail 6, when the active-byte test observes zero.
- Valid event 4 when the resulting auxiliary cell has low eight bits equal to 4.
- Every normally completing event-32 branch.

Its sequence is:

1. Write byte value 1 at offset 1 of the captured state address.
2. Call the unidentified notification-context provider.
3. Read the 32-bit field at offset 8 of the captured state address after the provider returns.
4. Call F-8becc2a0337c with the provider result and that field value.
5. Return zero.

There is no fresh state-pointer read in this sequence. Rebinding the global pointer does not redirect its explicit accesses. A dependency can nevertheless modify the captured block itself. No explicit offset-0 write occurs here.

### Event 4: indexed clearing and conditional activation

If the unsigned detail exceeds 2, invoke F-a817d8d58c10. No ordinary continuation is established.

For a valid original detail \(i\):

1. Read the indexed-block global pointer afresh and clear the 32-bit entry at offset \(4i\) from that address.
2. Clear the 32-bit entry at offset 12 from the precomputed indexed address.
3. Store the original detail as a full 32-bit value at offset 4 of the captured state address.
4. Clear byte offset 0 of the captured state address.
5. Clear the object’s 32-bit counter at offset 720.
6. Call the unidentified event-4 provider.
7. Call F-ca2888499290 with the provider result, the auxiliary-cell address, and the detail-cell address, in that argument order.
8. Inspect the low eight bits of the resulting auxiliary-cell value.
9. Activate if those bits equal 4; otherwise return zero.

The first indexed destination uses a new global-pointer read. The second uses the indexed-pointer value obtained by the second entry-time read. Neither destination is defined by the first captured indexed base.

The two indexed stores can therefore target different blocks. The first store cannot redirect the already-precomputed second destination.

A dependency modification to the detail cell does not change the completed stores or the original detail already written into the selection field. The activation decision is not a full-width comparison: both 4 and 260 qualify; 261 does not.

### Event 8: notification before indexed clearing

If the unsigned detail exceeds 2, invoke F-a817d8d58c10.

For a valid original detail \(i\):

1. Read the state-block global pointer afresh and clear its byte at offset 1.
2. Call the notification-context provider.
3. Read the 32-bit field at offset 8 of the captured state address.
4. Call F-23aadb16b673 with the provider result and that field value.
5. Call F-ed5938e2c6ce with the object address and original detail.
6. Clear the 32-bit indexed entry at offset \(4i\) from the first captured indexed base.
7. Clear the 32-bit entry at offset 12 from the precomputed indexed address.
8. Clear byte offset 0 of the captured state address.
9. Clear the full 32-bit field at offset 4 of the captured state address.
10. Return zero.

The initial active-byte clear uses a fresh state-pointer read; the notification-field read and final state stores use the captured state address.

The two indexed writes use the two separately captured entry-time pointer values. No indexed-pointer reread occurs here after dispatch. Rebinding the global during a dependency call does not redirect either destination.

Unlike event 4, event 8 performs its indexed clears after its dependency calls. Those calls can observe or modify the entries before the explicit clears.

### Event 32: initialization and repeated processing

Read the state-block global pointer afresh, then test its initialization byte at offset 3. This test need not address the captured state block.

If the tested byte is zero:

1. Clear the object counter at offset 720.
2. Call F-14e18f37a85b with the object address.
3. Read and retain the reset-block global pointer.
4. Read the reset-block global pointer again and clear the first 32-bit entry through this newly read address.
5. Clear the second 32-bit entry, at offset 4, through the retained reset address.
6. Clear the third 32-bit entry, at offset 8, through the retained reset address.
7. Write byte value 1 at offset 3 of the captured state address.

Thus, the first reset store can target a different block from the remaining two stores. A first store that changes global pointer storage does not redirect the retained destinations.

The initialization test uses a fresh state address, whereas the initialization write uses the captured state address. The write does not necessarily mark the block whose byte was tested.

If the tested initialization byte is nonzero:

1. Read the object counter.
2. Call F-d7be9cfb4000 with that 32-bit value and the integer 5.
3. Inspect a secondary machine-level result associated with the call.
4. If it is zero, call F-14e18f37a85b. An explicit argument list for this invocation is not established.
5. Otherwise, call F-69a51532c54a with the object address.

After either branch:

1. Read the current 32-bit object counter.
2. Add one and store the 32-bit result back to the same field.
3. Perform activation.

This increment uses the counter value after all preceding calls and stores, not necessarily its earlier zeroed value or the value supplied to F-d7be9cfb4000. Reset stores and the initialization-byte store may alias the counter.

At the represented machine width, adding one to all-one bits stores zero. No saturation, overflow error, or wider stored result is visible.

### Event 64: flag clear or indirect call

For detail 0, clear byte offset 0 of the captured state address and return zero.

For detail 6:

1. Call F-7a117b899bf6 with the detail-cell address; its initial value is 6.
2. Interpret the resulting 32-bit cell value as an address.
3. Obtain an indirect-call target from byte offset 12 at that address.
4. Invoke the target with the detail-cell address and the global callback-argument value.
5. Call F-ec22bd8215d3 with the same cell address.
6. Return zero.

The target is obtained using the cell value after F-7a117b899bf6. The callback argument is read for the indirect invocation after that dependency returns; its read order relative to the target lookup is not established by the supplied expression.

The indirect invocation can modify the cell before F-ec22bd8215d3 receives it. No explicit target-validity or null check occurs.

Other detail values return zero without further explicit state changes or calls.

## Side effects

Explicit writes affect individual bytes or 32-bit words as described above. The function reads the state field at offset 8 but has no explicit store directed to that field. Aliasing can still cause another write to affect it.

No explicit allocation, deallocation, ownership transfer, locking, or rollback appears. The separate indexed and reset stores are not established atomic transactions.

Dependencies may change shared contents, global pointer bindings, or the object counter. Nothing supplied establishes preservation of these values. Captured addresses remain the explicit destinations despite later pointer rebinding, but their contents need not remain unchanged.

Local-cell addresses are exposed to dependencies. The evidence does not establish whether callees retain them. Any use after the enclosing invocation returns requires a lifetime guarantee not supplied here.

If a dependency does not return normally, no local cleanup or recovery sequence is established. The event-64 final call is an ordered operation on the normal path, not evidence of guaranteed exception cleanup.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Call sequences assume dependencies return normally where continuation is described.

1. **Ignored event:** Event 2, or a negative event value, performs the entry-time pointer reads and returns zero without subsequent explicit block access or dependency call.

2. **Distinct state addresses:** If the fresh event-1 state-pointer read yields a different address from the captured one, detail 7 writes its control byte through the fresh address but clears the active byte and final offset-0 byte through the captured address.

3. **Already active:** Event 1, detail 6, returns without notification if the captured active byte reads nonzero after the control-code store. An initially nonzero byte alone is insufficient if that store aliases it.

4. **Invalid full-width index:** Event 4 with detail 4,294,967,295 invokes F-a817d8d58c10. The index is neither reduced to a byte nor accepted as a negative value.

5. **Event-4 split destinations:** For detail 2, the first indexed store clears offset 8 through the event-time pointer read; the second clears offset 20 through the pointer from the second entry-time indexed read.

6. **Low-byte activation:** If F-ca2888499290 leaves the auxiliary cell as 260, activation follows. If it leaves 261, the function returns without activation.

7. **Event-8 captured destinations:** For detail 1, F-ed5938e2c6ce runs before clears at offsets 4 and 16 through the respective entry-captured indexed bases. A dependency’s rebinding of the indexed global does not redirect those stores.

8. **First-use counter:** If F-14e18f37a85b leaves the counter at 9, and the intervening reset stores and initialization-byte store do not change it, the increment stores 10. More generally, it stores one plus the counter value actually read immediately before the update, retaining 32 bits.

9. **Split initialization locations:** If the event-32 test uses one block while the captured state address identifies another, a zero test leads to an initialization-byte store into the captured block. It does not establish that the tested block becomes initialized.

10. **Repeated-processing choice:** A zero secondary result from F-d7be9cfb4000 selects F-14e18f37a85b; a nonzero result selects F-69a51532c54a. This does not establish divisibility-by-five semantics.

11. **Indirect-cell mutation:** Event 64, detail 6, obtains its target using the cell after F-7a117b899bf6. F-ec22bd8215d3 then receives that same cell after any mutation made by the indirect invocation.
