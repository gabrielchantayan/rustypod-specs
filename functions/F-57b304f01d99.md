# F-57b304f01d99

## Purpose

F-57b304f01d99 searches a context-referenced sequence of fixed-stride records for the first record whose declared sequence of 16-bit units matches a prefix of an input sequence.

The context supplies a record-base pointer and a record count. This establishes a reference to the record storage, not ownership of that storage.

For stable memory, a candidate matches when its declared length is no greater than the requested quantity capped at 255, and every declared unit equals the corresponding input unit. The input need not end at the matching prefix.

An optional output address enables additional processing:

- Without a match, the function writes the capped quantity into the output’s first 16-bit field and calls a dependency with the input, the following output address, and twice the capped quantity.
- With a match, the function prepares a temporary representation and calls three dependencies, ultimately passing the output address, an interior address of the selected record, and the temporary representation.

The ordinary return value reports whether a record matched. It does not report whether the dependencies successfully produced an output.

“Record,” “length,” and “prefix” describe the visible access pattern; they do not establish an application-level format.

### Result

On an ordinary return:

- **0:** the input address was zero, or the search ended without a match.
- **1:** a candidate matched.

A zero-length candidate can match with a capped quantity of zero, without reading an input unit.

No separate error return is visible. Invalid memory access, dependency failure, or a nonlocal exit is not translated into a defined error result.

| Context plus `0xBA8` | Unsigned 32-bit record count |

A supplied output must support the initial 16-bit write, even when input is zero.

For nonzero input, the context must support the visible field reads. Record and input storage must support whichever reads the search actually reaches. The requested quantity alone does not cause the search to read that many input units: a candidate may be rejected, match early, or mismatch early.

Additional storage requirements on output paths depend on the callees. Their capacities, overlap restrictions, and memory-access behavior are not established here.

## Behavior

### Entry and zero-input path

If output is nonzero, the first visible memory action is writing zero to its first 16 bits. This precedes the input-address check and all context reads.

If input is zero, the function returns 0:

- No context field is read.
- No record or input unit is read.
- No dependency is called.
- The requested quantity is not used for comparison or output construction.

Thus, zero input does not require a usable context, but it does not bypass the write to a supplied output.

### Search initialization and traversal

For nonzero input, the function first loads the record-base pointer from context offset `0xBA4`, then caps the requested quantity at 255.

The candidate index starts at zero. Before every outer-loop admission check, the match state is reset to zero. The index is then compared with the unsigned count read from context offset `0xBA8`.

Consequences of this order:

- The record-base pointer is loaded even if the count is zero.
- The count is reread for successive admission checks.
- The record-base pointer is not reloaded during traversal.
- A mismatch cannot leave a successful return merely because that candidate temporarily entered comparison.

For each unsuccessful candidate, the current record address advances by `0x100` bytes and the unsigned index advances by one. Candidates are visited in increasing index order until one matches or the current count excludes the next index.

No record header is read when the first count check excludes index zero.

### Eligibility and unit comparison

Each visited candidate’s header is read for an unsigned comparison with the capped quantity.

If the header exceeds the cap, the candidate is skipped without comparing its payload to input.

Otherwise, comparison starts at unit index zero. The header is read again before each potential unit comparison:

- If the current index is at least the newly read header, the candidate matches.
- Otherwise, the input unit at byte offset twice the index is compared with the candidate unit at byte offset two plus twice the index.
- Unequal units abandon the candidate.
- Equal units advance the index.

The comparison expression establishes both unit reads, but not their relative machine-level order.

With stable headers and valid storage, this produces the prefix rule stated in Purpose. In particular:

- No terminator is consulted.
- An eligible zero-length candidate matches without reading either payload.
- Input units beyond the declared length do not affect selection.
- The first matching candidate wins, even if a later candidate would match a longer prefix.
- Duplicate matches resolve to the earliest visited candidate.

The cap limits eligibility using the first header read. It is not a separate bound checked on every comparison. If the header changes during comparison, the later header reads govern completion; comparison need not remain bounded by the initially observed length or capped quantity. Concurrent or externally changing storage therefore cannot be treated as a coherent snapshot.

### Output omitted

When output is zero, no output dependencies are called. The function returns the search result after performing the required search accesses.

Neither the temporary representation nor its header is initialized on this path.

### Output supplied after a completed search

For nonzero input and output, the function assigns the capped quantity to a function-local 16-bit temporary header. This assignment occurs on both the matched and unmatched output paths.

The capped value is exactly representable in 16 bits. Twice that value ranges from 0 through 510 and cannot overflow a 32-bit unsigned quantity.

#### No match

The function writes the temporary header value to the output’s first 16-bit field, then calls **F-ad023a375886** with:

1. The original input address.
2. The address two bytes after the output start.
3. Twice the capped quantity, expressed as a byte quantity.

The call occurs even when that byte quantity is zero.

This call shape is consistent with constructing a length-prefixed copy, but the dependency’s implementation is unavailable. The contract therefore establishes the direct header write and call arguments, not the final output body or even preservation of the header after the call.

#### Match

The temporary representation comprises an initial 16-bit field followed by a 510-byte region. Only the initial field is explicitly initialized by this function.

The dependency sequence is:

1. **F-ad023a375886** receives the original input address, the temporary region immediately after its header, and twice the capped quantity.
2. After that call returns, the selected record’s 16-bit header is read again.
3. **F-87bf9031895e** receives the temporary representation’s start address, the integer value 1, and that newly read header value.
4. **F-UNRESOLVED-03** receives the output address, the selected record address plus `0x80` bytes, and the temporary representation’s start address.

The first call uses the entire capped quantity, not merely the selected record’s declared length.

The header passed to F-87bf9031895e is read after F-ad023a375886. If the first dependency changes record storage, the later call can receive a different header from the one that established the match. The function does not repeat matching.

No visible return value from these dependencies changes the match result. If all return normally and execution remains valid, the function returns 1.

## Side effects

### Direct writes

The visible direct writes include:

- Zero to the first 16 bits of a supplied output at entry.
- The capped quantity to the local 16-bit temporary header after a search, whenever output is supplied.
- The capped quantity to the output’s first 16 bits on the no-match output path.

No direct writes to context, records, or input are visible except where caller-provided aliasing makes an output write overlap those regions.

The function does not itself initialize the temporary payload. Any population of that region depends on F-ad023a375886.

### Aliasing and observation order

No non-aliasing checks are visible.

The initial output write can alter later reads if output overlaps input, context, or records. For example, an output address equal to the input address causes the first input unit to be zeroed before comparison.

On the no-match path, the later output-header write also precedes F-ad023a375886. If output overlaps input, that dependency may receive input storage already modified by the function.

Selection finishes before output dependencies run. This does not imply that selected storage remains unchanged afterward: the matched header is reread following the first dependency, and later dependencies receive addresses into temporary and record storage.

Neither dependency preservation of globals nor isolation from referenced storage is assumed.

### Ownership and lifetime

The context references the record storage; its ownership is unresolved. No allocation, release, or explicit ownership transfer is visible in this function.

The temporary representation is function-local storage and has no supported lifetime after return. Whether a dependency retains its address is unknown; safe deferred access is not established.

The absence of direct release operations does not establish that dependencies preserve allocations. Their ownership and lifetime effects remain documented_only.

## Acceptance examples

Unless otherwise stated, these examples require valid, stable, non-overlapping storage and normally returning dependencies.

1. **Zero input.** With output supplied, its first 16 bits are written to zero and the result is 0. No context reads or dependency calls occur.

2. **Empty collection.** With nonzero input, zero record count, and output omitted, the record-base pointer is still loaded. No candidate header or input unit is read; the result is 0.

3. **Unsigned cap.** Requested quantity 300 produces cap 255. A stable header of 256 is ineligible. If an output path is reached, F-ad023a375886 receives byte quantity 510.

4. **Prefix match.** With quantity 4, a record declaring two units matches when those two units equal the first two input units. Additional input units do not prevent result 1.

5. **First match wins.** A first record declaring one matching unit is selected ahead of a later record declaring three matching units. The later record is not examined.

6. **Exhaustion after mismatches.** If every visited candidate is ineligible or mismatches, the result is 0. Entering comparison for an earlier candidate does not leave a successful result after exhaustion.

7. **Zero quantity.** A stable zero-length record matches without input-unit reads. With output supplied, the first dependency still receives byte quantity zero, followed by both remaining matched-output calls.

8. **No-match output.** With cap 3 and no match, the function writes output header 3 and calls F-ad023a375886 with input, output plus two bytes, and byte quantity 6. Final payload contents require that dependency’s contract.

9. **Post-selection header change.** If F-ad023a375886 changes the selected header before returning, F-87bf9031895e receives the changed header. The selected record is not revalidated.

10. **Crossing a nominal boundary.** With cap at least 128, a stable header of 128 is eligible. Its last compared unit begins at record offset `0x100`, crossing into the next nominal record. Acceptance requires accessible backing storage there.

11. **Output aliases input.** If both addresses designate the same first 16-bit unit, that unit is zeroed before search. Match expectations must use the modified input, not its entry value.
