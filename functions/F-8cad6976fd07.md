# F-8cad6976fd07

## Purpose

F-8cad6976fd07 dispatches a 32-bit selector into operations that may contribute values to a caller-supplied destination. Contributions can originate from global resources, eight-byte records, fixed text, a mode-dependent helper, or entries supplied by a secondary interface.

Its return value is a selector-dependent status, not a count of contributions or a reliable success indicator. Some selectors perform contribution calls and return zero. Other selectors return one even when an empty collection produces no contribution calls.

This contract describes the supplied static representation. It does not establish the application meaning of the selectors, the destination’s concrete type, or dependency internals.

### Object and record layout

Each listed object field is four bytes wide. Offsets are byte offsets from the first argument.

| Offset | Visible interpretation |
|---|---|
| `0x98` | Address of collection A |
| `0x9C` | Unsigned 32-bit count for collection A |
| `0xA0` | Address of collection B |
| `0xA4` | Unsigned 32-bit count for collection B |
| `0xA8` | Address of the secondary interface |

Both collections contain eight-byte records. A record’s first word occupies bytes zero through three; its second word occupies bytes four through seven. The selected word is forwarded without interpretation.

An interface object contains a four-byte table address at offset zero. The primary interface uses table byte offset `0x54`. The secondary interface uses table byte offsets `0x1AC` and `0x15C`. These accesses do not establish complete object layouts, named interfaces, or complete calling conventions.

The secondary-entry path uses a temporary represented as two four-byte words. Dependencies receive its starting address. Their complete memory-access requirements are unknown.

### Resource and captured-value terminology

The following labels distinguish resources without assigning application meaning:

- **Base resource:** one global word read twice during common setup.
- **Captured base:** the value from the first base-resource read.
- **Captured incremented value:** the result of adding two to the value from the separate, subsequent base-resource read.
- **Pair P:** two global words selected by `0x6206`.
- **Triple endpoints:** two global words used before and after the captured base by `0x6207`.
- **Pair Q:** two global words selected by `0x620D`.
- **Tail R:** the global word submitted second by `0x6213`.
- **Single S:** the global word submitted by `0x6216`.
- **Temporary seed:** the global word read when initializing each secondary-entry temporary.
- **Fixed text:** the resource passed directly to F-2484a607f41b by designated selectors.

The fixed-text reference suggests a decimal-digit sequence. Its complete bytes, terminator, and any suffix are not established. Exact output text therefore remains documented_only.

## Behavior

### Common setup and the two base-resource reads

Every invocation performs the following setup before selector dispatch:

1. Initialize the eventual return status to zero.
2. Initialize the temporary’s first word from the third argument and its second word from the fourth argument.
3. Call F-9d0ecc5f6adf without explicit arguments.
4. Call F-682adfd5a561 with that result and literal `0x80`.
5. Retain its result as the primary interface address.
6. Read the base resource and retain that value as the captured base.
7. Read the same base resource again, separately and subsequently; add two to this second read and retain the result as the captured incremented value.

The two reads are distinct. The captured incremented value is **not established as the captured base plus two** unless the base resource has the same value at both reads and the addition is defined. There is no explicit dependency call between these reads, but the representation supplies no stability, synchronization, or concurrency guarantee that makes them equal.

Both captured values are established before any selector-specific callback. Later callbacks that change the base resource do not refresh either captured value.

The addition is represented using a signed integer value in the 32-bit model. No overflow guard is present. Ordinary arithmetic examples require the second read plus two to be representable as a signed 32-bit value. Behavior outside that range is documented_only; this contract does not replace it with guaranteed wraparound.

### Primary contribution operation

A primary contribution invokes the indirect operation at primary table byte offset `0x54`, with three explicit arguments in this order:

1. Retained primary interface address.
2. Selected 32-bit contribution value.
3. Original destination value.

The dependency’s return value is ignored.

The primary interface address is retained from common setup, but its table and method target are fetched again for successive contribution calls. A callback that changes the table can therefore affect the next call target. This is not a single cached-target sequence.

Where the representation separately stages a later method target and a global contribution value, the target is fetched first, then the global value, then the call occurs. The representation does not establish every machine-level read order within compound call expressions.

### Collection traversal

Traversal uses an unsigned 32-bit index beginning at zero. Records are visited in increasing index order.

The count field is read for every loop condition. If the index is below the current count, the collection address is read to locate the selected word, and a primary contribution is made. The contribution finishes before the index advances and the next count check occurs.

Consequences include:

- Zero count produces no primary calls.
- Reducing the count during a callback can end traversal early.
- Increasing the count can extend traversal.
- Replacing the collection address can redirect subsequent record reads.
- Changing unvisited record contents can change later contributions.

This is not a snapshot traversal. No locking, storage retention, or count validation is visible.

A selected word is addressed at the current collection address plus eight times the index, plus four bytes for second-word selectors. Indices and counts are unsigned 32-bit quantities, and addressing uses the represented 32-bit model. No guard prevents arithmetic wrap or an out-of-storage access. Ordinary record behavior requires valid storage for every accessed address and arithmetic that addresses the intended records.

### Secondary-entry sequence: `0x6217`

First, F-f7cb977a5079 receives the original object address and the **captured incremented value**. That value was established from the second common base-resource read, not necessarily from the captured base.

After that call returns, the secondary interface is read through object offset `0xA8`, and its operation at table offset `0x1AC` is invoked. The supplied representation shows no explicit arguments for this call. An implicit receiver convention is not established.

The signed 32-bit result determines an unsigned 32-bit iteration bound:

- A result of zero sets the bound to zero.
- Otherwise, one is subtracted from the signed result and the result is assigned to the unsigned bound.

This bound is established once, before iteration. Later callbacks do not refresh it.

For each unsigned index beginning at zero and below the bound, the following operations occur in order:

1. Read the current temporary-seed global and write it into the temporary’s first word.
2. Write zero into the temporary’s second word.
3. Access the secondary interface again and invoke its operation at table offset `0x15C`, passing the secondary interface, current index, and temporary address.
4. Call F-44362605ab79 with the temporary address.
5. Call F-2484a607f41b with the original destination first and the preceding dependency’s result second.
6. Call F-289ec4311c64 with the temporary address.

The entry operation’s return value is ignored. Its writes to the temporary, if any, are dependency-defined. The temporary is initialized again for each iteration rather than carrying its previous contents forward unchanged.

Positive count results process one fewer entry than the reported count: one produces no iterations, two produces index zero only, and three produces indices zero and one.

Negative results are not rejected. For example, a result of minus one yields unsigned bound `0xFFFFFFFE` after the representable subtraction. The most negative signed 32-bit result presents a separate unresolved case: subtracting one is outside the signed range. No defined wraparound bound is promised for that case.

F-289ec4311c64 runs after contribution on each normally completed iteration. No exceptional-exit cleanup guarantee is visible.

## Acceptance examples

These are conditional deductions from static evidence, not executed tests. Unless stated otherwise, dependencies return normally, addresses are valid, and arithmetic is representable.

1. **Unrecognized selector.** For `0x7000`, both acquisition dependencies execute, followed by both ordered base-resource reads. No selector-specific call occurs, and the return is zero.

2. **Stable base resource.** If both common reads return ten, `0x6211` submits twelve, then ten, then fixed text. Changing the base resource during the first submission does not change either captured contribution.

3. **Different common read values.** If the first base-resource read returns ten and the second returns twenty, `0x6211` submits twenty-two, then ten, then fixed text. It must not substitute twelve for twenty-two or twenty for ten.

4. **Secondary preparation uses the second read’s result.** Under the same ten-then-twenty reads, `0x6217` passes twenty-two to F-f7cb977a5079. A later change to the base resource does not alter this argument.

5. **Same records, different status.** With stable collection B containing first words X and Y, both `0x620B` and `0x6215` submit X followed by Y. The former returns zero; the latter returns one.

6. **Second-word selection.** For stable collection B records `(X, U)` and `(Y, V)`, `0x620C` and `0x621A` submit U followed by V and return one.

7. **Empty traversal.** With collection A’s count zero, `0x6214` makes no primary contribution calls and returns one. Common setup still occurs.

8. **Late global read.** For `0x6206`, if the first primary callback changes pair P’s second global word, the second contribution uses the subsequently read value.

9. **Mutable count.** If collection B initially has count three but the first contribution changes it to one, `0x6215` stops after that contribution and returns one.

10. **Contributions with zero status.** With common reads ten then twenty, `0x6213` submits twenty-two and then the current tail R. It makes no fixed-text call and returns zero.

11. **Secondary boundary counts.** Count results zero and one both produce no entry, conversion, contribution, or temporary-processing iterations. Preparation and the count operation still occur; the return is one.

12. **One secondary iteration.** Count result two produces index zero only. The temporary is initialized, the entry operation runs, conversion runs, the converted result is contributed, and temporary processing runs, in that order.

13. **Negative count.** Count result minus one establishes bound `0xFFFFFFFE`. Completion of that many iterations requires additional validity and normal-return assumptions; it is not evidence that the secondary interface can supply those entries.
