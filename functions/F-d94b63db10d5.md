# F-d94b63db10d5

## Purpose

The selection depends only on whether the second input equals zero. The dependency receives both the selected variant information and the original second input. After the dependency returns, this function performs the same sequence of field writes for either variant.

The established behavior is partial initialization of returned storage. The fragment does not establish the object type, the meanings of its fields, whether the dependency allocates the storage, or how the initialized object becomes accessible to other code.

The dependency is then called once with six arguments, in this positional order:

By contrast, the initialization cells used after the call are not visibly sampled before it. Their post-call reads must not be modeled as an earlier snapshot.

### A dependency changes an initialization source

If the dependency instead changes the selected selection cell, the third argument of that already-executing call remains the value read beforehand.

### A byte write preserves neighboring bytes

Suppose the destination is ordinary writable memory and no other actor changes it during initialization. The write at offset 28 changes that byte to 9. It does not itself change offsets 29–31.

This conclusion is independent of the destination’s prior byte values. It is not a guarantee that the dependency left those bytes unchanged.

### The early retained value survives a later source change

Suppose the offset-0 store aliases initialization cell B and changes its contents. The subsequent offset-24 store still uses B’s value from the earlier post-call read, not its newly changed contents.

This distinguishes the established read order from an implementation that reads B immediately before writing offset 24.

### An invalid destination is not recovered

If the dependency returns an address that cannot support the first 32-bit store, the function attempts that store without a visible validity check. No successful completion, cleanup, or diagnostic is guaranteed by the fragment.
