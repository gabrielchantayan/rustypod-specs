# F-69a62b9a6385

## Purpose

F-69a62b9a6385 coordinates an operation on a shared service object, updates that service’s selected mode, and conditionally notifies the caller to navigate to “Now Playing.”

The established behavior has two operation paths:

- If the requested mode differs from the service’s initially reported mode, dispatch the operation without performing the equivalence checks.
- If the modes match, compare service state against a candidate state. A successful equivalence check suppresses dispatch but still counts as success for the subsequent notification.

The interpretation as playback or navigation coordination is inferred from the notification text and the shape of the calls. The exact application-level meaning of the operation, modes, candidate state, and service state is not established.

## Behavior

### 1. Acquire the service and capture mode inputs

The function calls F-b7af80e829ec without visible arguments.

If its result is nonnull, the pointer is adjusted backward by five 32-bit words: 20 bytes. The adjusted address is used as the service object. If the result is null, no adjustment occurs, but the subsequent virtual-table access still uses the null pointer.

The function then performs these calls in order:

1. Service virtual operation at `0x1c0`, capturing an unsigned 32-bit initial mode.
2. Caller virtual operation at `0x144`, capturing a 32-bit value.

The initial requested mode is the caller-provided value with bit zero toggled using exclusive-or with `1`. This is not a general Boolean negation. Values outside zero and one retain their other bits.

The dispatch-option value is selected separately:

- Argument 7 equal to zero selects `3`.
- Any nonzero argument 7 selects `0`.

If argument 6 is not `0xffffffff`, it replaces the derived requested mode with its low eight bits, zero-extended to 32 bits. The sentinel comparison occurs before truncation.

Consequently:

- `0xffffffff` means “use the derived mode,” not mode 255.
- `0x000000ff` explicitly selects mode 255.
- `0xfffffffe` explicitly selects mode 254.

The caller’s `0x144` operation is invoked even when an explicit override will replace its result.

### 2. Produce the source representation

The source object’s virtual operation at `0x08` is invoked with a 16-byte local destination and the source object.

This occurs after both initial mode queries and before choosing the direct-dispatch or comparison path. Its output is used by the operation-dispatch call if that call occurs.

The visible body contains no matching explicit destruction of this 16-byte representation. Whether it is trivially destructible, borrows other storage, or requires cleanup performed elsewhere is unknown.

### 3. Dispatch immediately when modes differ

The requested mode is compared with the captured initial service mode as a full 32-bit value.

If they differ, the function bypasses all comparison-object construction and equivalence checks. It stages the selected dispatch-option value and the candidate pointer in outgoing storage, then invokes the service operation at `0x54`.

The visible call operands consist of:

- The service receiver.
- The temporary source representation.
- Argument 2.
- A literal zero.
- Argument 3.

The nearby storage assignments are associated with this dispatch sequence, but the supplied representation does not explicitly identify them as additional call operands. Their exact calling-convention role is documented under Uncertainties.

The returned 32-bit value becomes the operation result.

### 4. Construct comparison state when modes match

If the requested and initial modes match, the function initializes four local objects, in this order:

1. A comparison object through F-827f378f8c92, using a service-relative address 632 32-bit words from the adjusted service base, equivalent to byte offset `0x9e0`.
2. A 24-byte service-side value through F-ba5a4c1e0746, with two zero arguments.
3. A 108-byte candidate comparison object through F-ffe1f163ffa0.
4. A 24-byte candidate-side value through F-ba5a4c1e0746, again with two zero arguments.

These are storage extents visible in the supplied representation, not established public structure definitions. The contents and invariants established by their initializers are unknown.

If the candidate pointer is nonnull:

1. Its virtual operation at `0x1f8` is invoked to populate the 108-byte comparison object.
2. F-88e2e41f5074 is called with a temporary destination, the source object, argument 2, and a literal zero.
3. F-a449eda002e0 transfers or applies that temporary value to the 24-byte candidate-side value.
4. F-4e292a3dd745 is invoked on the temporary.

No ownership-transfer semantics are established for this sequence. In particular, calling F-a449eda002e0 does not by itself establish whether it copies, moves, retains, or references underlying resources.

If the candidate pointer is null, these four calls are skipped. The initialized candidate-side objects remain eligible for comparison; null does not force dispatch.

### 5. Decide whether equivalence suppresses dispatch

The service virtual operation at `0x1a4` is called.

If it returns nonzero, the function dispatches the operation using the same dispatch sequence as the differing-mode path. No service-side value retrieval or equality comparison occurs.

If it returns zero, the function:

1. Calls the service virtual operation at `0x15c` to populate the 24-byte service-side value.
2. Calls F-05cc4e9ef0f4 on the candidate-side value.
3. Calls F-05cc4e9ef0f4 on the service-side value.
4. Compares the two returned 64-bit values for exact equality.

The candidate-side conversion precedes the service-side conversion. Dependencies may have side effects; they must not be assumed interchangeable or safely reorderable.

If the 64-bit values differ, the function dispatches the operation.

If they match, the first virtual entry of the service-derived comparison object is invoked with:

- That comparison object.
- The 108-byte candidate comparison object.
- A literal `1`.

If this comparison returns zero, the function dispatches the operation.

If it returns nonzero, dispatch is suppressed and the operation result is set to `1`.

Thus, dispatch is suppressed only when all of the following hold:

- Requested mode equals the initially captured service mode.
- The service’s `0x1a4` query returns zero.
- The two 64-bit values compare equal.
- The final comparison returns nonzero.

There is no visible special case requiring a nonnull candidate for this outcome.

### 6. Release comparison-path temporaries

After either dispatch or successful suppression on the matching-mode path, cleanup calls occur in this order:

1. F-4e292a3dd745 on the candidate-side 24-byte value.
2. F-7b7ee8a22aea on the 108-byte candidate comparison object.
3. F-4e292a3dd745 on the service-side 24-byte value.
4. F-7b7ee8a22aea on the service-derived comparison object.

These calls occur before applying the requested mode.

The direct differing-mode path does not construct these objects and does not execute these cleanup calls.

### 7. Apply mode and conditionally notify

After either path, the service virtual operation at `0x5c` is called with the requested mode.

On every normal path reaching this point, this call occurs regardless of:

- Whether dispatch occurred.
- Whether dispatch returned zero.
- Whether the requested mode matched the initial mode.

The mode value is the previously computed value. The function does not re-query the service or recompute it after intervening callbacks.

If the operation result is zero, no notification is constructed.

If it is nonzero:

1. F-9b9c1c7483f4 is called using local storage, the text `GotoNowPlaying`, and an additional four-byte local scratch address.
2. Its returned 32-bit value is passed to the caller’s virtual operation at `0x11c`.
3. F-8a5aadac202f is invoked on the notification’s local storage.

The caller notification therefore occurs after the mode-update call and, on the matching-mode path, after comparison cleanup.

## Acceptance examples

These are conditional contract examples, not executed tests. They assume valid receivers and normally returning dependencies.

1. **Explicit override truncation.** Argument 6 is `0x123456ab`. The requested mode is `0x000000ab`, regardless of the caller query result. The caller query still occurs.

2. **Sentinel and non-Boolean derivation.** Argument 6 is `0xffffffff` and the caller query returns `2`. The requested mode is `3`, not zero. A service mode of `3` enters the comparison path.

3. **Immediate dispatch fails.** Requested mode differs from initial service mode and dispatch returns zero. Comparison objects are not constructed. The service’s mode-update operation is still called with the requested mode. The caller receives no notification.

4. **Equivalent state suppresses dispatch.** Modes match, the service query returns zero, both 64-bit values match, and the final comparison returns nonzero. Dispatch is not called. Comparison cleanup occurs, the mode-update operation is called, and the caller receives the `GotoNowPlaying` notification.

5. **Unequal 64-bit values.** Modes match and the service query returns zero, but the two conversion results differ. The final comparison operation is skipped. Dispatch determines whether notification occurs.

6. **Nonzero service query.** Modes match but the service query returns nonzero. Comparison objects have already been constructed, and candidate extraction has already occurred if applicable. Service-side retrieval and both 64-bit conversions are skipped. Dispatch proceeds.

7. **Null candidate.** Candidate extraction and intermediate-value construction are skipped. The initialized candidate objects still participate in subsequent checks. Dispatch suppression remains possible if the dependencies produce matching values and a successful final comparison.

8. **Dispatch-option selection.** Argument 7 equal to zero stages option `3`; argument 7 equal to `-1` stages option `0`. No distinction is made among nonzero values.

- **Outgoing dispatch layout:** Two adjacent 32-bit storage locations are assigned the dispatch option and candidate pointer immediately before dispatch. The visible call expression does not establish the complete ABI-level argument list or ordering of any additional operands.
- **Object layouts:** The service-relative address at `0x9e0` and local storage extents are visible; field meanings, embedded-object boundaries, and public types are not.
