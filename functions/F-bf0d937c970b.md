# F-bf0d937c970b

## Purpose

F-bf0d937c970b conditionally populates three fixed-layout slots in a caller-supplied state object from externally configured lookup tables. Eligibility depends on a nonzero selector, a supported rate value, and a nonzero table base for that rate.

For each eligible slot, a lookup entry either marks the slot with a one-byte flag or selects a five-word record whose contents are copied into the slot. After all three slots have been processed, the function sets a separate one-byte overall flag to 1. If the eligibility conditions fail, it instead sets that overall flag to 0 without updating the slots.

This is a description of statically visible behavior. The interpretation of the rate as an audio sample rate, the five words as coefficients, and the slot flags as bypass indicators would be plausible intent, but is not established by the supplied evidence.

## Interface

### Input and return

The function receives one address-bearing argument identifying a mutable state object. The supplied representation declares the argument as an integer and accesses memory at fixed byte offsets from its value.

There is no returned value. Results are observable through memory writes.

The interface supplies no object length, table length, error-output argument, or ownership-transfer indicator.

### State-object layout

All offsets below are byte offsets from the supplied object address. Four-byte fields are accessed as complete four-byte quantities; flags are accessed as individual bytes.

| Offset | Width | Role |
|---|---:|---|
| 4 | 4 bytes | Rate discriminator, compared with 44100 and 48000 |
| 8 | 1 byte | Overall flag written by this function |
| 180 | 4 bytes | Selector used for eligibility and lookup addressing |

The object also contains three slot regions spaced 56 bytes apart. The following offsets are relative to the start of each slot region:

| Slot-relative offset | Width | Role |
|---|---:|---|
| 12 | 4 bytes | Receives record word at record offset 12 |
| 16 | 4 bytes | Receives record word at record offset 16 |
| 20 | 4 bytes | Receives record word at record offset 0 |
| 24 | 4 bytes | Receives record word at record offset 4 |
| 28 | 4 bytes | Receives record word at record offset 8 |
| 64 | 1 byte | Per-slot flag |

The three slot-region starting offsets are 0, 56, and 112. Consequently, the actual per-slot flag offsets are 64, 120, and 176. The flag’s relative offset lies beyond the 56-byte spacing; the spacing must not be mistaken for a complete, independently bounded slot structure.

The five destination words occupy:

- Slot 0: offsets 12, 16, 20, 24, and 28.
- Slot 1: offsets 68, 72, 76, 80, and 84.
- Slot 2: offsets 124, 128, 132, 136, and 140.

A conventional contiguous object covering every fixed field accessed would extend through byte offset 183 inclusive. That size alone does not establish that any lookup-table access is valid.

### External configuration

Three external address-bearing values participate:

- A lookup-table base, captured at function entry.
- A record-table base associated with rate 44100.
- A record-table base associated with rate 48000.

These are data dependencies, not callable functions. Their initialization, allocation, capacity, and mutability are not provided.

The lookup table is addressed as rows of 12 bytes, each containing three four-byte entries. Record tables are addressed as records of 20 bytes, each containing five four-byte words.

## Behavior

### Eligibility and configuration-read order

The lookup-table base is read and retained before the eligibility checks, even when the function will take the ineligible path.

The selector at object offset 180 is then read. If it is zero, the function writes 0 to the overall flag at offset 8 and returns. In this case, it does not read the rate or either rate-specific record-table base.

For a nonzero selector, the function reads the record-table base associated with 44100 and then reads the rate:

- If the rate is 44100, that record-table base is selected.
- Otherwise, the function reads the record-table base associated with 48000 and reads the rate again. The second comparison must equal 48000 for this alternative to qualify.

The selected base must also be nonzero. A supported rate with a zero corresponding base is ineligible.

A rate of 44100 with a zero 44100 base does not fall back to the 48000 base. The rate comparison has already selected the first alternative; the subsequent nonzero-base check fails.

For every eligibility failure, the only state-object write is a one-byte 0 at offset 8. Existing slot words and slot flags are left untouched by this function.

The two rate reads on the alternative path are distinct source-level reads. Under stable memory they observe the same value. Behavior involving concurrent changes or specially observable memory is not independently established.

### Lookup processing

When eligibility succeeds, the chosen record-table base is retained for the entire operation. The function processes slots in ascending order: slot 0, then slot 1, then slot 2.

For each slot, it rereads the selector at object offset 180. It does not reuse the selector value used for eligibility or the preceding slot.

The lookup-entry address is formed from:

- The retained lookup-table base.
- Twelve times the selector read for this slot.
- Four times the slot number.

One four-byte lookup entry is read from that address.

There is no visible validation that the selector names an existing row. In particular, eligibility rejects only zero, not negative selectors or selectors larger than a table’s capacity.

### Sentinel entry

If the lookup entry equals signed −1, the function writes 1 to that slot’s one-byte flag.

For this slot, it does not read a record and does not write any of the five destination words. Previously stored word contents remain in place.

The sentinel has the all-one-bits representation in the apparent 32-bit entry model. Other negative entries are not treated as sentinels.

### Record entry

For any lookup entry other than −1, the function derives a record address from the retained selected record-table base plus 20 times the entry.

It then performs five four-byte copies in this order:

| Order | Record source offset | Destination offset relative to slot start |
|---:|---:|---:|
| 1 | 0 | 20 |
| 2 | 4 | 24 |
| 3 | 8 | 28 |
| 4 | 12 | 12 |
| 5 | 16 | 16 |

Each source read precedes its corresponding destination write. The function does not first snapshot all five source words. After the fifth copy, it writes 0 to the slot’s one-byte flag.

The copied words are transferred without visible arithmetic conversion, normalization, or interpretation. Their meaning and numerical representation are unspecified.

There is no visible bounds check on the record index and no rejection of negative indices other than the −1 sentinel. A negative non-sentinel entry therefore enters the record-copy path rather than a defined error path.

### Completion

After all three slots have been processed, the function writes 1 to the overall flag at object offset 8 and returns.

This final flag is set even if all three entries were sentinels. It therefore does not mean that all three slots received record words.

The overall flag is not cleared before eligible processing begins. During processing it retains its incoming value until the final write. The operation is not transactional.

## Side effects

### Writes and preservation

On a normally completing ineligible path:

- The overall flag becomes 0.
- No slot word or slot flag is written.

On a normally completing eligible path:

- Each slot flag is written exactly once.
- Each sentinel slot retains all five existing destination words.
- Each non-sentinel slot receives five ordered four-byte writes.
- The overall flag is written to 1 after all slot writes.

Flag writes affect one byte, not an entire surrounding four-byte field. The function does not explicitly clear padding, neighboring bytes, or unused parts of the object.

### Aliasing and observable ordering

No non-aliasing guarantee is supplied for the object and table storage.

The order of operations matters if destination memory overlaps table memory. For example, an earlier destination write may change a later record source word before it is read. The behavior must not be described as an overlap-safe bulk copy or as copying an immutable five-word snapshot.

Likewise, writes for earlier slots may affect lookup data used by later slots if their storage aliases. The lookup base and selected record base are retained values, but the table contents are read as processing proceeds. The selector is also reread for each slot.

### Ownership and failures

The function contains no visible allocation, deallocation, reference-count operation, or ownership transfer. No callable dependency is invoked.

There is no explicit error return, exception handling, rollback, or recovery path. Invalid object addresses, invalid table addresses, insufficient backing storage, alignment violations, and invalid address arithmetic are not converted into a defined failure result by the shown behavior. Earlier writes may already have occurred if a later access cannot complete; the exact fault behavior is outside the established contract.

## Dependencies

There are no visible function-call dependencies, so no additional opaque function IDs are required.

The required external data are:

1. The lookup-table base.
2. The 44100 record-table base.
3. The 48000 record-table base.
4. Readable table contents at every address actually selected.
5. A state object readable and writable at the offsets used by the chosen path.

Successful eligible execution requires valid lookup storage even if every entry is a sentinel. Valid record storage is required only for entries that are not −1.

A nonzero rate-specific table base is merely an eligibility condition. It is not proof of readable storage or adequate capacity. The lookup-table base itself is not checked for zero.

## Acceptance examples

These examples are conditional on valid memory, stable configuration, and representable address calculations unless the example states otherwise. They are acceptance conditions derived from static evidence, not executed test results.

### Zero selector

Given a selector of zero and arbitrary existing slot contents:

- The overall flag becomes 0.
- Every slot word and slot flag remains unchanged.
- The lookup-base configuration is read, but no lookup entry is read.
- The rate and both record-table-base configurations need not be accessible on this path because they are not read.

### Unsupported rate

Given a nonzero selector and a stable rate of 32000:

- The function examines both rate alternatives.
- The overall flag becomes 0.
- No lookup entry is read and no slot data is written.

The configuration values used during those checks must still be readable.

### Supported rate with missing selected table

Given a nonzero selector, rate 44100, a zero 44100 record-table base, and a nonzero 48000 base:

- The overall flag becomes 0.
- No slot is processed.
- The 48000 base is not used as a fallback.

### Three sentinels

Given eligibility succeeds and all three selected lookup entries are −1:

- The three slot flags become 1.
- All fifteen destination words retain their incoming contents.
- The overall flag becomes 1 after the third slot flag write.
- No record word is read.

### Mixed entries and field placement

Given eligibility succeeds and the selected row contains entries 2, −1, and 0:

- Slot 0 receives record 2 and its flag becomes 0.
- Slot 1 retains its five destination words and its flag becomes 1.
- Slot 2 receives record 0 and its flag becomes 0.
- The overall flag becomes 1 last.

If record 2 contains, in increasing record-offset order, the words 101, 102, 103, 104, and 105, slot 0 receives:

- 104 at object offset 12.
- 105 at object offset 16.
- 101 at object offset 20.
- 102 at object offset 24.
- 103 at object offset 28.

The first destination written is offset 20, not offset 12.

### Negative non-sentinel entry

Given an entry of −2, the function does not mark the slot as a sentinel. It takes the record-copy path using the corresponding signed index displacement, subject to the unresolved arithmetic and memory-validity requirements. A defined, graceful rejection of this entry is not an acceptance requirement supported by the evidence.
