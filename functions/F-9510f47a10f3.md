# F-9510f47a10f3

## Purpose

F-9510f47a10f3 performs a comparison-directed search over an indexed receiver. It returns a signed 32-bit index selected using either an exact-match policy or a position-returning policy.

The established behavior is narrower than a general-purpose search API:

- A zero mode value requests an exact match. A completed search with a nonzero final comparison returns −1.
- Any nonzero mode value returns the matching index, when equality is encountered, or a position derived from the final comparison.
- Equality terminates the search immediately. Duplicate handling is not normalized to the first or last equal element.
- When the initial search interval is empty, the function returns 0 in both modes, without retrieving an indexed element or invoking the comparison operation.

The inferred intent is binary search, with an optional insertion-position result. That interpretation depends on the indexed data and comparison relation being consistent. The function does not establish or validate those properties.

### Output

The result is a signed 32-bit integer.

For ordinary nonnegative counts and valid, consistent search behavior, the result has one of these meanings:

- An encountered matching index.
- −1 for an unsuccessful exact-mode search.
- A position between 0 and the initial count, inclusive, for an unsuccessful nonzero-mode search.

The empty-interval behavior is an important exception to treating exact mode as “return −1 unless an element matched”: an initially empty interval returns 0 even though no element comparison occurs.

## Behavior

### Initialization and observable ordering

The function first reads the receiver’s count-like field and derives an inclusive upper bound by subtracting one. This happens before either receiver callback.

It then invokes the receiver operation at dispatch-table byte offset 0x18, passing the receiver as its argument. The returned 32-bit value is retained for later comparisons.

Next, it invokes the receiver operation at dispatch-table byte offset 0x58, again passing the receiver. Its result is retained as the comparison-object address.

These calls occur even if the initial count produces an empty search interval. The function does not bypass them for zero-length input.

The receiver dispatch-table address is obtained for each receiver dispatch. Consequently, the second dispatch is not specified to use the same table address observed by the first. Changes made by the first callback can affect the second dispatch.

The initial lower bound is 0. The candidate result and retained comparison result are also initially 0. The receiver’s count-like field is not explicitly reread to refresh the upper bound.

### Search iterations

An iteration occurs while the lower bound is less than or equal to the upper bound, using signed comparisons.

The selected index is the signed quotient of the sum of the two bounds divided by two. Within the ordinary nonnegative, non-overflowing search domain, this selects the lower middle index when the interval contains an even number of positions.

For each selected index:

1. F-3b5d52fd8e4a is invoked with the receiver and that index.
2. Its opaque 32-bit result becomes the element operand for comparison.
3. The comparison object’s current dispatch table is read.
4. The operation at dispatch-table byte offset 0x24 is invoked.

The comparison invocation receives, in order:

- The retained comparison-object address.
- The element operand returned by F-3b5d52fd8e4a.
- The retained 32-bit value from the first receiver callback.
- The original search operand.
- The same retained 32-bit value again.

The repeated argument is the same saved value in both positions. The first receiver callback is not reinvoked per comparison.

The signed 32-bit comparison result determines the next action:

| Comparison result | Effect |
|---|---|
| Zero | Stop immediately, retaining the current selected index |
| Negative | Continue only above the current index |
| Positive | Continue only below the current index |

There is no additional comparison to validate equality, establish a boundary among duplicates, or check the eventual insertion position.

### Final result selection

With **mode zero**:

- A zero retained comparison result leaves the candidate index unchanged.
- A nonzero retained comparison result replaces the result with −1.

With **mode nonzero**:

- A negative retained comparison result advances the candidate index by one.
- A zero or positive retained comparison result leaves the candidate index unchanged.

This policy uses the final comparison result, not a fresh examination of either bound or an element at the proposed position.

For an ordinary failed search:

- A final negative comparison returns the position immediately after the last selected element in nonzero mode.
- A final positive comparison returns the last selected index in nonzero mode.
- Either nonzero comparison returns −1 in exact mode.

### Empty and unusual counts

For an initial count of zero, the upper bound is −1. Both receiver callbacks run, but no indexed lookup or comparison runs. The initialized candidate and comparison result remain zero, so the return value is 0 for every mode.

The same outcome follows for a negative count when subtracting one is representable: the interval is initially empty, both receiver callbacks still run, and the result is 0. This does not establish that negative counts are valid application inputs.

The minimum signed 32-bit count cannot be decremented within signed 32-bit range. Its behavior is not established by the supplied representation.

### Arithmetic limits

The midpoint is calculated from the sum of the bounds. The evidence does not support replacing it with an overflow-avoiding formulation.

Even if each bound individually fits in a signed 32-bit integer, their sum can exceed the signed maximum. Therefore, a nonnegative count alone is not enough to establish safe arithmetic for every search trajectory.

A count no greater than 1,073,741,824 is a sufficient bound for avoiding midpoint-sum overflow across ordinary nonnegative search intervals. Some larger counts may also complete without overflow on particular comparison trajectories, but that is not a general guarantee.

No wraparound rule is specified here for overflowing signed arithmetic. Exact machine behavior would require additional evidence.

## Side effects

The function’s explicit state changes are to its own search state. No explicit receiver-field, indexed-element, or global-memory write is shown.

That does not make the operation externally read-only. Its dependencies can have observable effects:

- Both receiver operations run once on every normally progressing call.
- F-3b5d52fd8e4a runs once per reached iteration.
- The comparison operation runs once after each normally returning indexed lookup.

No supplied contract establishes that these dependencies preserve the receiver, indexed storage, dispatch tables, global state, or other objects.

Several retained values constrain the effect of such changes:

- The initial count determines the search bounds; later count changes do not explicitly refresh them.
- The first callback’s 32-bit result is retained unchanged for all comparison calls.
- The comparison-object address is obtained once.
- The comparison object’s dispatch-table address is read for each comparison, after the indexed lookup has returned.

Thus, mutation during an indexed lookup can affect the immediately following comparison dispatch. Mutation of the receiver’s count does not itself change the already established bounds.

No allocation, deallocation, retention, or release operation is explicit in this function. Ownership of the receiver, comparison object, retained value, search operand, and indexed lookup results is undocumented. Passing a value to a dependency does not establish transfer of ownership.

There is no explicit null check, bounds-error branch, exception translation, or dependency-failure recovery. If a dependency does not return normally, no subsequent action or normal return is guaranteed.
