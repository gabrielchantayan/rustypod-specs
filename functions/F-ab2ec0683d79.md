# F-ab2ec0683d79

## Purpose

F-ab2ec0683d79 updates a caller-owned location containing a node address. It either descends through one link and then repeatedly through another, or follows an upward-link chain subject to link-equality checks.

The link arrangement is consistent with advancing an iterator in a binary tree, potentially using a sentinel node. That interpretation is **inferred intent**, not an established requirement. The supplied body establishes address reads, comparisons, and updates; it does not establish node ordering, tree validity, sentinel identity, or an abstract “next element” result for every input.

The function produces no explicit return value. Its observable result is the address left in the caller-owned location.

## Interface

### Input and output location

The sole argument identifies a writable integer-sized location. This contract calls it the **cursor slot**. Its contents are interpreted as a node address, called the **current address**.

The same slot supplies the input and receives the output. The function may write it more than once during a single call. Intermediate addresses are therefore part of the mutation sequence, not merely temporary values held internally.

The supplied declaration represents both the slot contents and node-link contents as integers rather than pointer-typed fields. The exact integer width, pointer width, signed representation, and integer-to-address interpretation are not independently established by the supplied material.

A 32-bit address-bearing representation is consistent with the layout, but is not proven solely by the declaration. A consumer requiring a concrete binary interface must obtain the target ABI separately.

### Referenced record layout

Relative to an address interpreted as a node base, the function accesses three integer-sized fields:

| Byte offset | Contract name | Observed use |
|---|---|---|
| +4 | Upward link | Supplies the initial upward candidate and subsequent upward candidates |
| +8 | Descent link | Supplies the next address during the descending branch |
| +12 | Branch link | Selects the initial branch and participates in upward traversal checks |

These names describe use, not confirmed data-structure semantics. In a conventional binary-tree interpretation, they would correspond to parent, left-child, and right-child links respectively.

The function does not access a field at offset zero or inspect payload data. The total record size and any other fields are unknown.

### Preconditions for defined, completing execution

The following are requirements on the caller’s data, not checks performed by the function:

- The cursor slot is readable and writable.
- Every node field actually reached by the selected path is readable with the alignment and width required by the target ABI.
- Address-plus-offset calculations are meaningful under that ABI.
- Integer values interpreted as addresses designate appropriate readable storage.
- The chosen traversal reaches its stopping condition if termination is required.
- Concurrent or asynchronous modification does not invalidate the accesses or the intended state model.

Zero has a specific stopping role in the descending branch. It is **not** a universally safe node address or an independently validated end marker.

## Behavior

### Initial decision

The function reads the current address from the cursor slot and reads the branch-link field at that address, at byte offset +12.

A nonzero branch link selects the descending behavior. A zero branch link selects the upward behavior.

This decision is made from that initial field read. There is no separate validation of the current address, the link target, or the surrounding structure before traversal begins.

### Descending behavior

When the initial branch link is nonzero, that value becomes the first descent candidate.

The function writes that candidate into the cursor slot **before** reading the candidate’s descent-link field at offset +8.

If the descent link is nonzero, its value becomes the next candidate. The function again writes the candidate into the cursor slot before reading its descent link. This continues until a candidate’s descent-link field contains zero.

On ordinary completion:

- The cursor slot contains the last nonzero address reached.
- That address’s descent-link field was observed to be zero.
- The initial current address has been replaced.
- Every visited candidate was written to the cursor slot, including the final candidate.

This path does not read upward links. After the initial branch-link read, it does not use branch links to guide descent.

A nonzero invalid candidate is not rejected before use. It is first written into the cursor slot, after which reading its descent-link field may fail according to the execution environment. Consequently, a memory-access failure on this path can leave the caller’s slot modified.

A cycle consisting of nonzero descent links does not satisfy the stopping condition. The function contains no cycle detection or iteration limit.

### Upward behavior

When the initial branch link is zero, the function reads the current node’s upward link at offset +4. That value becomes an upward candidate.

Before writing the candidate into the cursor slot, the function reads the candidate’s branch-link field at offset +12 and compares it with the address currently held in the cursor slot.

If those values are equal:

1. The function writes the candidate into the cursor slot.
2. It reads the upward-link field at offset +4 from that candidate.
3. The resulting address becomes the next candidate.
4. It repeats the comparison using the new candidate and the updated cursor slot.

Thus, each successful comparison moves the cursor slot upward by one link. The comparison is an address-value equality check; it does not compare node contents or payloads.

When the candidate’s branch-link field does **not** equal the current slot contents, the upward loop stops. At that point, the candidate has not yet been written into the slot by that failed comparison.

The function then performs a separate final check:

- It reads the branch-link field at offset +12 from the address currently in the cursor slot.
- It compares that field value with the candidate.
- If the two differ, it writes the candidate into the cursor slot.
- If they are equal, it leaves the cursor slot unchanged.

This final check is behaviorally significant. The function does not unconditionally install the first candidate that ends the upward loop.

### Zero and boundary behavior

Only the descending branch explicitly treats a zero link as a normal traversal terminator.

In the upward branch, a zero candidate is not checked before its branch-link field is accessed. Under ordinary address interpretation, that would attempt an access at address zero plus 12. Whether such an access faults, is unmapped, or has some other consequence depends on the environment.

Accordingly, an upward link of zero is not established as a valid root boundary for this function. A sentinel or other nonzero boundary object is a plausible structural requirement, but its exact shape is unknown.

### Access ordering and repeated reads

The following sequencing is established by the body:

- The initial branch-link read occurs before any explicit cursor-slot write.
- Each descending candidate is written into the slot before its descent-link field is read.
- Each successful upward-loop comparison occurs before the candidate is written into the slot.
- After that upward write, the next upward candidate is read from the just-selected candidate.
- The final branch-link check occurs after the upward loop exits and before any final replacement of the slot.

The upward-loop comparison contains both a node-field read and a cursor-slot read. The supplied expression does not establish a relative evaluation order between those two reads. It does establish that the comparison is completed before the loop body’s write.

These are source-level logical accesses and sequencing constraints. Without target code or volatile-access information, they are not a guarantee of a particular machine-instruction trace or externally observable bus-access sequence.

## Side effects

### Explicit writes

Every explicit write targets the caller-provided cursor slot.

The function does not directly assign to any node-link field. However, if the cursor slot overlaps a node field, writing the slot also changes that field’s storage. The supplied body contains no alias checks or protection against this.

For the ordinary traversal interpretation, the cursor slot should be separate from the node records being traversed. With overlapping storage, subsequent reads can observe values changed by earlier slot writes; the ordinary tree-navigation interpretation is then not a reliable substitute for the actual access sequence.

### Ownership and lifetime

The function performs no explicit allocation, deallocation, reference-count adjustment, or ownership transfer. It requires referenced storage to remain usable for the duration of the accesses.

Updating the slot changes the stored address. It does not, by itself, establish acquisition of ownership of the new node or release of ownership of the old node.

### Failure and partial mutation

There is no explicit error result, exception mechanism, rollback, or structural validation in the supplied body.

If execution fails after a slot write, the function provides no restoration of the input address. If a traversal does not terminate, the function does not return normally; the descending branch or successful upward iterations may continue writing the slot.

There are no explicit global-variable accesses, dependency calls, synchronization operations, logging operations, or I/O operations.

## Dependencies

No dependency calls are present in the supplied body.

The remaining environmental dependencies are the target ABI, memory-access semantics, and the caller’s record layout and lifetime guarantees. No behavior of another opaque function is needed to describe the visible control flow.

## Acceptance examples

These examples assume stable memory, a cursor slot that does not overlap node records, valid address arithmetic, and readable fields wherever an access is described. Letters denote distinct nonzero node addresses, not payload values.

### 1. A single descending candidate

Given:

- The slot initially contains A.
- A’s branch link is B.
- B’s descent link is zero.

Required behavior:

- Write B into the slot.
- Then read B’s descent link.
- Return with B in the slot.

B’s upward link and branch link do not affect this path.

### 2. A longer descending chain

Given:

- The slot initially contains A.
- A’s branch link is B.
- B’s descent link is C.
- C’s descent link is D.
- D’s descent link is zero.

Required slot-write order: B, C, D.

The final slot value is D. In particular, the function must not merely compute D and perform one final slot write; the supplied behavior includes the intermediate updates.

### 3. An upward candidate accepted immediately

Given:

- The slot initially contains A.
- A’s branch link is zero.
- A’s upward link is B.
- B’s branch link is not A.

The upward loop performs no slot write. The final check reads A’s branch link, which remains zero under these assumptions. Since B is nonzero, that value differs from B.

Required result: one slot write, installing B.

### 4. Multiple upward steps before replacement

Given:

- The slot initially contains A.
- A’s branch link is zero.
- A’s upward link is B.
- B’s branch link is A.
- B’s upward link is C.
- C’s branch link is B.
- C’s upward link is D.
- D’s branch link is not C.

Required behavior:

- Install B after the first successful comparison.
- Install C after the second successful comparison.
- Stop the loop at candidate D.
- Read C’s branch link, which is B.
- Since B differs from D, install D.

Required slot-write order: B, C, D.

### 5. The final check suppresses replacement

Given:

- The slot initially contains A.
- A’s branch link is zero.
- A’s upward link is B.
- B’s branch link is A.
- B’s upward link is A.

Required behavior:

- The first comparison succeeds, so the slot becomes B.
- The next candidate is A.
- A’s branch link is zero, which differs from the current slot value B, so the loop stops.
- The final check reads B’s branch link, which equals candidate A.
- No final replacement occurs.

The final slot value is B. This example establishes the final equality guard without asserting that the cyclic arrangement is a valid tree.

### 6. Invalid or nonterminating structures

If the descending links form a nonzero cycle, completion is not required by the supplied behavior.

If the initial branch link is zero and the upward link is zero, a clean “end reached” result is not established. The function proceeds toward a branch-field read using the zero candidate.

If a descending candidate is nonzero but unreadable, its address is written into the slot before the attempted descent-field read. Any failure outcome beyond that sequencing is environment-dependent.
