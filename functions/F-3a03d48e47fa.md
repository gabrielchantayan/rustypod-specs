# F-3a03d48e47fa

## Purpose

F-3a03d48e47fa performs an in-place rearrangement of linked records. Under a conventional binary-tree interpretation, it rotates a selected node to the left: the selected node’s right child takes its position, and the selected node becomes that child’s left child.

The pointer-field updates are established by the supplied static evidence. Their interpretation as a tree rotation is inferred intent. The function does not establish that its inputs form a tree, verify parent-child consistency, or reject a missing right child.

The contract distinguishes:

- **Established behavior:** the observed field accesses, conditional decisions, and writes.
- **Inferred structural meaning:** parent, left-child, right-child, and root roles assigned to those fields.
- **documented_only unknowns:** surrounding type definitions, runtime guarantees, synchronization, and failure behavior not established by the evidence.

No runtime tests have been performed.

## Interface

The function accepts two address-bearing arguments and has no explicit result value.

| Argument | Contract role |
|---|---|
| First argument | Address of a context record containing, at byte offset 16, an address used to locate a root-link slot. |
| Second argument | Address of the selected node whose links are rearranged. |

For description, the selected node is **X**. The address initially read from X’s byte offset 12 is **Y**, the node being promoted.

### Accessed layouts

The function uses the following fields:

| Record | Byte offset | Access width | Established use |
|---|---:|---:|---|
| Context | 16 | 4 bytes | Address of another record |
| Record addressed by the context field | 4 | 4 bytes | Link compared with X and conditionally replaced with Y |
| Node | 4 | 4 bytes | Parent-like link |
| Node | 8 | 4 bytes | Left-child-like link |
| Node | 12 | 4 bytes | Right-child-like link |

The root-link slot is not directly at context offset 20. The function first reads the address stored at context offset 16, then accesses offset 4 relative to that address.

The supplied representation uses four-byte link values. Exact pointer ABI, byte order, alignment requirements, and address-overflow behavior are not independently established. The offsets are byte offsets; they are not array indices.

There is no established signed arithmetic on link contents. Link values are loaded, compared with zero or another address-bearing value, and used as addresses. Address calculations add fixed offsets. Valid operation requires these calculations to identify accessible fields without unsupported address wraparound.

### Preconditions for the intended structural result

For a valid left rotation:

- The context and its referenced root-link record must be readable at the accessed fields.
- X must identify a writable node.
- X’s right-child-like field must identify a valid, writable Y; it must not be zero.
- If Y has a nonzero left-child-like link, that link must identify a node with a writable parent-like field.
- If X is not identified by the root-link slot, X’s parent-like link must identify a valid parent record.
- In that non-root case, X must be the parent’s left or right child, with consistent links.
- Records must not overlap in ways that change the meaning of fields during the update.
- Concurrent access must not invalidate the reads, writes, or branch decisions.

These are structural and memory-safety preconditions, not checks performed by the function.

## Behavior

### Link interpretation

Under the inferred tree interpretation:

- Offset 4 is the parent link.
- Offset 8 is the left-child link.
- Offset 12 is the right-child link.
- The context-selected slot holds the tree root.

Let **B** denote Y’s original left child, and **P** denote X’s original parent. These labels describe ordinary, non-overlapping, stable inputs. They do not imply that the implementation snapshots every such value before modifying memory.

### Ordered accesses and updates

The following order is established by the supplied static representation. It describes source-level memory effects, not a guarantee of machine-level atomicity or a concurrent-observer memory model.

1. **Read the promoted-node address.**  
   Read four bytes at X offset 12. Use that value as Y for the rest of the operation.

2. **Replace X’s right link.**  
   Read four bytes at Y offset 8 and write that value to X offset 12.

3. **Conditionally repair the transferred node’s parent link.**  
   Read Y offset 8 again and compare the value with zero. If nonzero, read Y offset 8 again to obtain the destination record address, then write X to that record’s offset 4.

   Consequently, Y’s left link is not represented as a single saved value used for all three purposes. For stable, non-overlapping records, the reads agree and the transferred node is B. With overlapping storage or intervening mutation, they need not agree.

4. **Assign Y’s parent link.**  
   Read X offset 4 and write that value to Y offset 4.

5. **Locate and inspect the root-link slot.**  
   Read the address at context offset 16. Access the four-byte slot at offset 4 relative to that address, and compare its contents with X.

   This lookup occurs after the preceding writes. The context’s root-link-record address is not established as having been captured before those writes.

6. **Reconnect the incoming link to Y.**
   - If the root-link slot equals X, write Y to that slot.
   - Otherwise, read X offset 4 to obtain the parent record address. Read that parent’s offset 8. If this value equals X, write Y to the parent’s offset 8.
   - If the parent’s offset 8 does not equal X, write Y to the parent’s offset 12.

   The last case does not check whether the parent’s right link actually equals X. It is an unconditional fallback once the root comparison and parent-left comparison both fail.

7. **Make X the left child of Y.**  
   Write X to Y offset 8.

8. **Complete X’s new parent link.**  
   Write Y to X offset 4.

The function then returns without an explicit result.

### Result for a well-formed tree

For stable, non-overlapping records satisfying the structural preconditions:

- Y replaces X in the root slot or in P’s child link.
- Y’s parent becomes X’s former parent.
- Y’s left child becomes X.
- X’s parent becomes Y.
- X’s right child becomes B.
- If B is nonzero, B’s parent becomes X.
- X’s original left child remains unchanged.
- Y’s original right child remains unchanged.
- The parent’s other child link remains unchanged.

No explicit root-specific clearing of Y’s parent occurs. Even when X is the root, Y receives the value read from X’s parent field. If the surrounding structure uses a sentinel rather than zero for the root’s parent, that value is carried forward.

### Malformed structures

The function does not validate tree invariants.

In particular:

- A zero right link in X is still used to address Y’s fields.
- A nonzero transferred-child link is assumed to identify writable storage.
- A non-root X is assumed to have a usable parent link.
- Failure to find X in the parent’s left link causes a write to the parent’s right link, without verifying that link.
- Cycles, self-links, and overlapping records are not detected.

The well-formed-tree result must not be generalized to those cases. Earlier writes can change fields that later operations read.

## Side effects

The function changes shared record storage directly.

### Explicit writes

Depending on the branch taken, the function writes:

- X offset 12.
- The transferred node’s offset 4, if the repeated Y-left check is nonzero.
- Y offset 4.
- Exactly one incoming-link slot: the root-link slot, the parent’s offset 8, or the parent’s offset 12.
- Y offset 8.
- X offset 4.

For ordinary non-overlapping records, this is five four-byte writes when B is zero, or six when B is nonzero.

The function does not explicitly write node payloads, balance information, colors, counts, allocation metadata, or fields outside the listed offsets. Such fields could nevertheless be affected if the caller supplies overlapping or incompatible storage.

### Ownership and lifetime

There are no explicit allocations, deallocations, or calls to ownership-management routines. No record is copied as a whole. The function rewires links between existing records.

No ownership transfer or lifetime extension is established. The caller must supply storage that remains valid throughout all accesses.

### Partial updates and synchronization

The update is not represented as a transaction. Several writes occur before the incoming parent or root link is replaced, and the final two writes occur afterward.

There is no explicit locking, validation barrier, rollback, or error recovery. If an access fails after an earlier write, a partially modified structure may remain, depending on the execution environment.

The supplied evidence does not establish that concurrent readers or writers can safely observe or participate in this operation.

## Acceptance examples

These examples specify conditional expectations from static evidence, not observed executions. Except where stated otherwise, assume valid, stable, non-overlapping storage.

### Root rotation with a transferred subtree

Initially, the root-link slot contains X. X’s right child is Y, and Y’s left child is B, where B is nonzero.

After return:

- The root-link slot contains Y.
- X’s right link contains B.
- B’s parent link contains X.
- Y’s parent link contains X’s former parent value.
- Y’s left link contains X.
- X’s parent link contains Y.

X’s left link and Y’s right link are unchanged. Y’s parent is not independently forced to zero.

### Rotation at a parent’s left child

Initially, the root-link slot does not contain X. X’s parent is P, and P’s left link contains X.

After return, P’s left link contains Y. P’s right link is unchanged. The remaining local links have the well-formed rotation result described above.

### Rotation at a parent’s right child

Initially, the root-link slot does not contain X. X’s parent is P, P’s left link does not contain X, and P’s right link contains X.

After return, P’s right link contains Y. P’s left link is unchanged.

The right-child identification here follows from the example’s precondition, not from an explicit right-link comparison.

### Empty transferred subtree

Initially, Y’s left link is zero.

X’s right link becomes zero. No transferred-node parent write occurs. Y still becomes the incoming link’s target, Y’s left link becomes X, and X’s parent becomes Y.

### Root selection takes precedence

Initially, the root-link slot contains X, while X’s parent field contains a nonzero value.

The function follows the root branch. It writes Y to the root-link slot and copies X’s parent value into Y’s parent field. It does not inspect that parent record’s child links for reconnection.

### Inconsistent parent-child links

Initially, the root-link slot does not contain X. X’s parent field identifies P, but neither of P’s child links contains X.

Provided all accesses remain valid, the function overwrites P’s right link with Y. It does not report the inconsistency or preserve that right link as an error-handling measure.

### Missing promoted node

Initially, X’s right link is zero.

There is no established successful-rotation outcome. The function attempts field access using that zero value as Y’s address. A clean return, status code, or rollback must not be required from this evidence.
