# F-391a10e7bae2

## Purpose

The structure and repair cases are consistent with red-black tree insertion. That interpretation is **inferred intent**, not an independently established guarantee. Correct tree insertion requires a compatible initial structure and dependency behavior not established by the supplied body.

The function does not search for an insertion position. The caller supplies the proposed parent and an attachment-control value. There is no visible duplicate rejection, capacity check, rollback, or recoverable-error result.

## Behavior

### Creation, payload copy, and count update

The first visible operation calls F-d988be290708 with the container address. The returned address is retained as the created node and is the address eventually published.

The function tests whether the address sixteen bytes beyond that node is nonzero. If it is nonzero, the function reads four bytes from the value location and writes four bytes at created-node offset +16.

This test is not a conventional null-node check:

- A null node address does not itself make the derived address zero.
- Skipping the payload copy does not skip attachment or repair.
- Later accesses still require a usable created node.

The copy does not establish construction, deep copying, or ownership of any resource represented by the four copied bytes. Pointer arithmetic at address-space boundaries remains **documented_only**.

After the conditional copy, the function reads the four-byte count at container offset +20, adds one, and writes the result back. This precedes comparison and attachment.

There is no visible overflow check. The representation uses an integer addition, but width alone does not establish portable modular-wrap semantics. Defined completion requires an increment valid under the applicable execution model; behavior at the arithmetic boundary remains **documented_only**.

### Attachment selection

The function reads the container’s header pointer and compares it with the proposed parent. Left attachment is selected without comparison if either:

- The proposed parent equals that header; or
- The attachment control is nonzero.

Otherwise, F-b61726ba491f is called with these arguments, in order:

1. The address at container offset +25.
2. The original value location.
3. The address at proposed-parent offset +16.

A nonzero result selects left attachment. Zero selects right attachment.

| Parent relative to header | Attachment control | Comparison | Selected side |
|---|---|---|---|
| Equal | Any value | Bypassed | Left |
| Different | Nonzero | Bypassed | Left |
| Different | Zero | Nonzero result | Left |
| Different | Zero | Zero result | Right |

No ordering interpretation of the comparison result is established beyond this zero/nonzero decision. In particular, zero is not a duplicate-rejection result here.

The comparator receives the original value address, not the created node’s stored-value address. The copied value and compared value therefore need not be an immutable snapshot: aliasing or dependency side effects may affect what is observed.

### Attachment writes and header maintenance

For left attachment, the first link write places the created node in the proposed parent’s +8 field. The header pointer is then read again.

If this newly read header differs from the proposed parent, its +8 link is inspected and replaced with the created node only when it equals the proposed parent.

If this newly read header equals the proposed parent:

1. Its +4 root link is written with the created node.
2. The header pointer is read again from the container.
3. That header’s +12 link is written unconditionally with the created node.

With a stable header equal to the proposed parent, this establishes the new node as root and both extrema. The header-link write order is +8, then +4, then +12.

For right attachment:

1. The created node is written into the proposed parent’s +12 field.
2. The header pointer is read again.
3. The header’s +12 link is replaced with the created node only if it equals the proposed parent.

After either attachment path and its applicable header updates, the created node’s +4 parent field is written with the original proposed-parent address.

Repeated header reads matter. A dependency may have changed the header before attachment, and the body does not enforce consistency between the header used to select the path and the header later used for maintenance.

### Repair entry and stopping conditions

Repair begins with the created node as the current node.

At each loop test, the function reads the header through the container and the root through that header. If the current node equals the root, repair stops without inspecting its parent color.

Otherwise, it reads the current node’s parent and that parent’s color:

- A nonzero parent color stops repair.
- A zero parent color enters an ancestor repair case.

The current node’s own color is not tested at this entry. Describing zero as “red” and one as “black” is consistent with the inferred algorithm, but the established behavior is the byte-level branching and writes described here.

The function obtains the grandparent through the parent link and compares the parent with the grandparent’s left-child pointer.

2. Writes one to the uncle’s color.
