# F-98f879e5f674

## Purpose

F-98f879e5f674 copies a dimensioned sequence of bytes from a captured source address to a captured destination address, accumulates unsigned byte contributions, and compares the resulting signed 32-bit accumulator with a result obtained from F-1654b76744c9 using a trailing four-byte word.

Copying precedes validation. A mismatch does not undo destination writes. Equality causes four ordered cursor-publication stores and returns status 0; inequality skips those stores and returns status 4.

An additive integrity check is the inferred intent. The established contract is the sequence of memory accesses, arithmetic conversions, dependency invocation, comparison, and conditional publication described below. In particular, the unsigned addition is defined modulo \(2^{32}\), but the subsequent conversion back to signed storage prevents an unconditional, portable modulo-\(2^{32}\) validation contract.

## Interface

### Arguments

The function has seven positional arguments:

| Position | Contract name | Representation and role |
|---|---|---|
| 1 | Context word | A 32-bit word passed unchanged to F-1654b76744c9. Its interpretation is unknown. |
| 2 | Source cursor slot | Address of a four-byte word containing the initial source address. Read on entry and overwritten on equality. |
| 3 | Source result slot | Address of a four-byte word written with the final source address on equality. Its previous contents are not explicitly read. |
| 4 | Destination cursor slot | Address of a four-byte word containing the initial destination address. Read on entry and overwritten on equality. |
| 5 | Destination result slot | Address of a four-byte word written with the final destination address on equality. Its previous contents are not explicitly read. |
| 6 | Outer dimension | Signed 32-bit integer controlling the outer iteration count. |
| 7 | Inner dimension | Signed 32-bit integer controlling the number of bytes processed within each outer iteration. |

Address-bearing words are interpreted as pointers in the represented environment. This is a four-byte-word interface, not a portable interface with arbitrary pointer widths.

There are no explicit capacity, stride, alignment, or trailer-length arguments.

### Return value

The function explicitly returns one of two 32-bit status values:

- **0:** the dependency result compares equal to the accumulator, and all four publication stores have completed.
- **4:** the values compare unequal, and none of the four publication stores executes.

Invalid accesses, an implementation-defined arithmetic-conversion signal, or abnormal dependency execution are not mapped to another documented status. If such an event prevents normal completion, neither normal return is guaranteed.

### Preconditions for normal completion

The execution requires:

- Readable source and destination cursor slots at entry.
- Readable storage for each source-byte access actually performed.
- Writable storage for each destination-byte store actually performed.
- A supported four-byte read at the source position reached after payload processing.
- Writable publication slots if equality selects the success path.
- Valid address progression throughout the operation, including the additional four-byte source advance on success.
- Satisfaction of F-1654b76744c9’s requirements.
- Arithmetic conversions that permit execution to continue.

The source result slot and destination result slot are not explicitly accessed on inequality. This is a path-specific observation, not a general promise that invalid pointers are acceptable arguments.

No ownership transfer, allocation, or release is established by this function’s own operations. The dependency’s ownership behavior is unknown.

## Behavior

### 1. Capture the starting addresses

The first caller-memory read obtains the source address from the source cursor slot. The next obtains the destination address from the destination cursor slot.

These captured addresses become the working cursors. The function does not explicitly reload either slot during copying or after the dependency call. Later modification of a cursor slot therefore does not itself redirect traversal.

The signed 32-bit accumulator starts at zero.

### 2. Select the payload through signed loop bounds

The dimensions are tested as signed 32-bit values. Each loop starts at zero and continues while its index is strictly less than its corresponding dimension.

When both dimensions are positive, the number of processed bytes is their mathematical product, assuming execution remains valid and completes. The function does not calculate this product as a 32-bit byte count. A large product therefore does not introduce a separate product-overflow operation, although address validity and accumulator conversion remain constraints.

Traversal is contiguous. There is no row stride, padding, row header, or reset of either cursor between outer iterations.

If the outer dimension is zero or negative, no payload iteration occurs.

If the outer dimension is positive and the inner dimension is zero or negative, each outer iteration performs no payload operation. Both working cursors remain unchanged, and the accumulator remains zero.

Nonpositive dimensions do not independently cause an error return. The trailing-word read and dependency call still occur.

For every positive signed 32-bit dimension, its loop index can reach the terminating bound without incrementing beyond the largest signed 32-bit value. The accumulator’s conversion issue is separate from loop-index arithmetic.

### 3. Process each byte in forward order

Each payload iteration has this observable access order:

1. Read the byte at the current source address for accumulation.
2. Incorporate its unsigned value, from 0 through 255, using the arithmetic described below.
3. Read the byte at that same source address again for copying.
4. Write the second observed value to the current destination address.
5. Advance the source and destination working cursors by one byte.

The accumulation read and copy read are distinct in the supplied representation. Stable ordinary memory yields the same value for both. Externally changing storage or other unusual memory may not.

Destination writes occur immediately, in traversal order. The function does not collect the payload into an intermediate buffer and does not defer writes until validation.

### 4. Apply unsigned addition, then signed conversion

Although the accumulator is stored as a signed 32-bit integer, each byte is explicitly converted to an unsigned 32-bit integer before addition.

Consequently, every accumulation step has two distinct arithmetic stages:

- The current signed accumulator is converted to unsigned 32-bit form, then added to the unsigned byte contribution. This addition is unsigned 32-bit arithmetic and reduces modulo \(2^{32}\).
- That unsigned result is assigned back to the signed 32-bit accumulator.

If the unsigned result is at most 2,147,483,647, assignment preserves its numerical value. If it exceeds that limit, the unsigned-to-signed conversion has implementation-defined behavior, potentially including an implementation-defined signal.

This is **not signed-addition overflow**. The modulo behavior of the addition is established; the unresolved part is what happens when its result is placed back into signed storage.

Until the first out-of-range conversion, the accumulator equals the ordinary mathematical sum of the unsigned byte contributions. After such a conversion, continued accumulation depends on the implementation’s conversion rule. Each later addition still uses unsigned modulo-\(2^{32}\) arithmetic, but its starting value is the signed value produced by the preceding conversion.

If the environment maps each unsigned result to the signed value with the same 32-bit representation and continues normally, the accumulator tracks the modulo-\(2^{32}\) byte sum through that signed representation. That mapping is a condition, not an established guarantee for every environment.

### 5. Read the trailing word and invoke the dependency

After payload processing, the function performs one four-byte read at the current source address.

This is the first source position after the payload, or the original source address if no bytes were processed. There is no explicit source-cursor advance before this read or before the call.

F-1654b76744c9 then receives:

- The original context word.
- The four-byte value just loaded.

There is no second trailer read after the call. The supplied evidence does not establish the load’s byte order, alignment tolerance, or the dependency’s interpretation of the word.

All payload writes precede this read. If those writes overlap the trailer, the dependency receives the value present after copying, not necessarily the original trailing value.

### 6. Compare signed stored values

The dependency result is captured in a signed 32-bit value and compared for equality with the signed 32-bit accumulator.

The comparison does not recalculate the sum or reread the copied data. Dependency changes to the buffers do not replace the already accumulated value.

A portable statement that validation accepts exactly a particular modulo-\(2^{32}\) checksum requires evidence about both:

- Conversion of out-of-range unsigned accumulation results back to signed storage.
- The dependency’s return contract and the interpretation of its returned value in the signed comparison.

The source establishes the equality decision, not an independent byte-order or unsigned-checksum protocol.

### 7. Publish cursors on equality

On equality, four stores occur in this order:

1. Write the post-payload source address plus four bytes to the source cursor slot.
2. Write that same source address to the source result slot.
3. Write the post-payload destination address to the destination cursor slot.
4. Write that same destination address to the destination result slot.

The function then returns 0.

The published source address includes the trailer’s four bytes. The published destination address includes only payload bytes. No explicit operation copies the trailer to the destination.

The publication is sequential, not atomic. If a store prevents further execution, the source provides no rollback for earlier stores.

### 8. Return on inequality

On inequality, the function returns 4 without executing any publication store.

This does not imply unchanged caller memory. Payload stores have already occurred, may have overlapped slots or other source storage, and may be followed by additional dependency effects. No restoration is performed.

## Side effects

### Forward overlap

The function always traverses forward. It does not choose a direction based on overlap and does not establish overlap-safe bulk-move behavior.

A destination store that changes a source byte needed by a later iteration changes what that later iteration reads and accumulates. Overlap with the trailing word can also change the dependency argument.

When the source and destination addresses are identical and memory remains stable, each payload byte is read twice and written back to its own address. Validation still occurs afterward.

### Slot aliasing

The four publication stores have an observable order. When slots share storage, later stores can overwrite earlier results.

If all four slots are the same aligned word, both starting cursors are captured from that word. Assuming the invocation otherwise remains valid and equality is reached, the final publication writes the post-payload destination address into the shared word. The source address including the trailer is written earlier and does not remain there.

Slots can also overlap payload or trailer storage. Such overlap may change bytes subsequently accessed or leave slot contents modified even on inequality. Entry capture prevents these changes from automatically redirecting the working cursors.

No explicit alias check is present.

### External state and ownership

The function contains no explicit allocation, release, or direct global-state access. Those absences do not establish that execution preserves global state or storage ownership.

F-1654b76744c9 may access or modify external state. Its memory effects, allocations, releases, and ownership requirements remain unknown. Continued execution after the call requires that any storage needed by subsequent publication remain usable.

## Acceptance examples

These are conditional deductions from static evidence, not executed tests. Unless stated otherwise, assume stable valid memory, supported word accesses, disjoint payload and slot storage, valid address progression, and a dependency that returns normally without modifying the example’s storage.

### Six-byte success

With dimensions 2 and 3 and payload bytes 1, 2, 3, 4, 5, and 6:

- Six consecutive bytes are copied in that order.
- The accumulator becomes 21 without an out-of-range conversion.
- The dependency receives the word loaded at source offset 6.
- If its captured signed result is 21, the return status is 0.
- Both source slots receive the starting source address plus 10.
- Both destination slots receive the starting destination address plus 6.

There is no special access or cursor adjustment between the third and fourth bytes.

### Mismatch after copying

For the same payload, a captured dependency result of 22 produces status 4.

All six destination writes have already occurred. No publication store executes. Under the disjointness and dependency assumptions, the four slots retain their entry contents.

### Unsigned byte contribution

For a one-byte payload containing 255, the contribution is 255, not −1. The copied byte is also 255 under stable-memory assumptions.

A captured dependency result of 255 produces status 0, with source publication five bytes beyond the start and destination publication one byte beyond the start.

### No payload

With outer dimension 0, no payload byte is accessed, regardless of the inner dimension. The trailer is read at the starting source address.

A captured dependency result of zero produces status 0, source publication at starting source plus four, and destination publication at its unchanged starting address.

With dimensions 3 and −2, the payload is likewise empty. A nonzero captured dependency result produces status 4 and no publication stores.

### First out-of-range signed conversion

Consider one outer iteration and 8,421,505 inner iterations. Let the first 8,421,504 payload bytes be 255 and the final byte be 128.

Before the final byte, the accumulator is 2,147,483,520. The final addition produces unsigned value 2,147,483,648. The addition itself is defined unsigned arithmetic; assigning its result back to the signed accumulator is the implementation-defined step.

If the environment maps that value to −2,147,483,648 without signaling, and the dependency’s captured result is also −2,147,483,648, equality produces status 0.

Without that conversion condition, the signed accumulator value and normal completion are not established. If the conversion signals before execution continues, the final byte’s copy has not yet occurred, because accumulation precedes copying.

### Forward overlap

Suppose the first three source bytes initially contain 7, 8, and 9, the destination begins one byte after the source, and the payload length is three bytes.

The first store replaces the second source byte with 7. The next iteration reads 7 and replaces the third source byte with 7. The final iteration also reads 7. The accumulated value is therefore 21, not 24.

The last store reaches the first trailer byte. The status consequently depends on the dependency result for the modified trailing word.

## Uncertainties

The following remain **documented_only**:

- Target byte order and exact alignment requirements for word reads and stores.
- The implementation-defined conversion of unsigned results above 2,147,483,647 to the signed accumulator, including whether a signal is raised.
- The dependency’s full return contract and how its result is interpreted when captured for the signed comparison.
- Behavior when address progression leaves valid storage or exceeds the represented address range.
- Dependency memory effects, external-state effects, ownership behavior, and abnormal execution.
- Any caller convention restricting buffer overlap, slot aliasing, or changing source memory.
- Fault behavior for invalid slots, inaccessible payload or trailer storage, or failed publication.

Unsigned accumulation additions are established as modulo-\(2^{32}\) operations; their wrapping is not an uncertainty. What remains unresolved is the intervening signed conversion and the complete validation interpretation.

Calling the trailing word a checksum describes inferred intent, not an independently established format.
