# F-c801f2aa28a2

## Purpose

F-c801f2aa28a2 performs ordered dispatch using a receiver and a separate record. It conditionally invokes a notification dependency, conditionally invokes an early handler, selects one of two main handlers, and conditionally invokes a final matching handler.

On normal completion, its result is the first nonzero integer returned by an invoked result-producing handler, or zero if all such results are zero. The notification dependency’s result does not participate in this selection.

Classification is stage-specific. The initial notification, early-handler, and main-handler stages can inspect a nested subtype when the record type is `0x16`. The final stage does not inspect that nested subtype: it checks for type `0x0f` and, only for that type, compares two fields.

Later stages read their relevant fields again. A dependency may change the record, its nested-record pointer, nested storage, receiver fields, or dispatch information. Earlier observations therefore do not establish later eligibility.

“Receiver,” “record,” “subtype,” “notification,” and “handler” describe structural roles. Their application-level meanings are not established.

## Interface

### Arguments and result

The function accepts two arguments:

- **Receiver address:** identifies storage containing a dispatch-table address and additional fields.
- **Record address:** identifies storage containing a type and a type-dependent field.

Every indirect handler receives these original receiver and record addresses, in that order. The notification dependency instead receives the original receiver address and a character-converted receiver field.

The result is an integer, not necessarily a Boolean. A nonzero handler result is returned unchanged, including a negative result. Zero means that no invoked result-producing handler returned nonzero; no application-level success or failure interpretation is established.

The supplied representation uses four-byte integer words and a recovered 32-bit address model. The offsets and widths below follow that model. The evidence does not independently establish the original ABI, complete object definitions, alignment requirements, byte order, or address-space rules.

### Record and nested-record layout

|---|---|---|---|

That rule does **not** apply to the final classification. If the final type read yields `0x16`, the function returns zero without reading the nested-record pointer or subtype.

The function does not directly access record offset `0x00` or any other nested-record field.

### Conditional preconditions

There is no explicit pointer validation, bounds checking, or call-target validation. Defined continuation requires usable storage and compatible targets for every operation actually reached:

- Each reached stage requires a readable record type word.
- Each of the first three stages that observes type `0x16` requires a readable nested-record address and a readable subtype through that address.
- A notification call requires a readable receiver word at `0x108`.
- An indirect call requires a readable current receiver table base, a readable selected table entry, and a compatible callable target.
- The final stage requires the record word at `0x08` and receiver word at `0x50` only when its type read yields `0x0f`.

The final stage never requires nested-record storage. In particular, its observation of type `0x16` imposes no nested-pointer or subtype-read requirement.

Storage requirements are path-dependent. A nonzero handler result prevents later stages and removes any requirement arising solely from their unreached accesses.

## Behavior

### Initial notification decision

The function first reads the record type at offset `0x04`.

If the type is not `0x16`, this stage does not read the nested-record address, nested subtype, or notification argument.

If the type is `0x16`, the function reads the nested-record address from record offset `0x08`, then reads the subtype at nested offset `0x04`. It subtracts `0x2500` from the subtype and tests whether the result equals `2`.

Subtype `0x2502` satisfies that arithmetic comparison without overflow. For that value, the notification condition is established. Exact behavior for subtype values causing signed arithmetic overflow is not established; the contract does not replace the supplied arithmetic with an unconditional bit-pattern equality rule.

When the condition holds, the function:

1. Reads the receiver integer word at `0x108`.
2. Converts that word to a character-width value.
3. Invokes F-4fd087f2325e with the receiver address and converted value.

The full receiver word is not forwarded unchanged. Character width, signedness, and out-of-range conversion behavior remain unresolved.

Any notification result is ignored. If the dependency returns normally, execution continues to a fresh early-handler classification.

### Optional early handling

The function reads the record type again, regardless of whether notification occurred.

If this read yields `0x16`, it reads the current nested-record address and then the subtype through that address. If the subtype is zero, it reads the receiver’s current dispatch-table base, loads the entry at `0x124`, and invokes F-indirect-A.

- A nonzero result is returned immediately.
- A zero result permits the main stage.
- A different observed type or subtype skips the early call.

Notification can affect this decision, but no particular mutation is assumed. Writing zero to previously referenced nested storage is insufficient to guarantee early handling: notification might also change the record type or replace the nested-record pointer.

### Main-handler selection

Unless the early handler returned nonzero, the function performs another classification.

It reads the record type. If that type is `0x16`, it reads the current nested-record address and then the subtype through that address.

The selection is:

- **F-indirect-B** if the reads observe type `0x16` and subtype `0x2a`.
- **F-indirect-C** for every other classification.

A type other than `0x16` selects F-indirect-C without a nested-record dereference at this stage.

After classification, the function reads the receiver’s current dispatch-table base and loads only the selected entry: `0x10c` for F-indirect-B or `0x110` for F-indirect-C. It invokes the selected target with the original receiver and record addresses.

A nonzero result is returned unchanged. A zero result permits final matching.

Exactly one main-handler call occurs on normal execution reaching this stage. Neither a completed notification nor an early-handler result of zero substitutes for the main call.

Earlier type, pointer, subtype, and dispatch-table observations are not reused to determine this selection. An early handler’s mutation influences routing only through the values subsequently read.

### Final matching

After the main handler returns zero, the function reads the record type again.

If the type is not `0x0f`, the function returns zero. This includes type `0x16`: the final stage does not read the nested-record pointer or subtype for that type, or for any other type.

If the final type is `0x0f`, the function reads:

1. The integer word at record offset `0x08`.
2. The integer word at receiver offset `0x50`.

If these values differ, it returns zero without a final handler call.

If they are equal, the function reads the receiver’s current dispatch-table base, loads the entry at `0x0e0`, and invokes F-indirect-D with the original receiver and record addresses.

A nonzero result is returned unchanged. A zero result yields zero.

The final decision uses observations made after the main handler returns. Entry-state type and comparison values do not determine it.

### Ordering and termination

The possible dependency-call order is:

1. F-4fd087f2325e.
2. F-indirect-A.
3. Exactly one of F-indirect-B and F-indirect-C, if reached.
4. F-indirect-D.

Each position is invoked at most once by this function body. Dependencies may themselves recurse or invoke other operations; their implementations are unavailable.

All four positions can occur in one execution if intervening dependencies establish the necessary later conditions and the early and main handlers return zero. Their eligibility conditions need not coexist at entry.

A nonzero result from an indirect handler prevents all later stages, including their reads. No loop, retry, or local recovery path is visible.

The stated ordering describes the supplied control flow. It does not establish atomicity, synchronization, or hardware-level ordering guarantees.

## Acceptance examples

These are conditional static acceptance scenarios, not runtime observations. Unless stated otherwise, they assume usable storage and compatible targets for reached operations, no additional state changes beyond those described, and normal dependency returns.

### Stable notification subtype

If the first three classifications observe type `0x16` and subtype `0x2502`:

- F-4fd087f2325e receives the character-converted receiver word.
- F-indirect-A is skipped.
- F-indirect-C is selected.
- A nonzero main result is returned immediately.
- If the main result is zero and the final type remains `0x16`, the function returns zero after the final type read, without reading a nested pointer, subtype, or final comparison field.

### Negative early result

If the early classification observes type `0x16` and subtype zero, and F-indirect-A returns `-7`, the function returns `-7`.

No main handler or final classification follows. This demonstrates nonzero propagation, not an application-level meaning for `-7`.

### Early mutation changes main routing

Suppose F-indirect-A is invoked and returns zero.

If the subsequent main reads observe type `0x16` and subtype `0x2a` through the then-current nested-record pointer, F-indirect-B is selected.

Changing only the previously referenced subtype does not guarantee that selection. A subsequent type other than `0x16` selects F-indirect-C without a nested read; a replacement nested pointer makes its referenced subtype decisive.

### Notification changes early eligibility

Suppose notification occurs and returns normally.

F-indirect-A is invoked only if the subsequent early reads observe type `0x16` and subtype zero through the current nested-record pointer. A notification write of zero to old nested storage alone is insufficient.

### Final matching uses subsequent observations

Suppose the main handler returns zero.

If the final type is `0x0f` and the subsequently read record and receiver comparison words are equal, F-indirect-D is invoked. Its result becomes the function result, whether zero or nonzero.

Unequal words skip that call and produce zero. If the final type is not `0x0f`, neither comparison word is read.

### Final type `0x16` with unusable nested storage

Suppose the main classification observes a type other than `0x16`, so it selects F-indirect-C without accessing nested storage.

Before returning zero, that handler changes the record type to `0x16` and leaves an unusable nested-record address at record offset `0x08`.

The final stage reads type `0x16` and returns zero. It does not read record offset `0x08` or dereference the unusable address. This scenario requires no usable nested storage after the main handler.

### Non-special stable type

For a stable type other than `0x16` and `0x0f`, with F-indirect-C returning zero:

- Notification and early handling are skipped.
- F-indirect-C is invoked once.
- Final matching is skipped.
- The result is zero.
- No nested-record dereference occurs anywhere in the function.

### Unusable nested storage in an earlier stage

If the initial notification, early-handler, or main-handler classification observes type `0x16`, it attempts to read the nested subtype through the current nested-record address.

An unusable address on such a path is not treated as an ordinary unrecognized subtype. No defined local error result or recovery behavior is established. This requirement does not extend to the final classification.
