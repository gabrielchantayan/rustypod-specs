# F-202c56ba1760

## Purpose

F-202c56ba1760 performs five memory writes, evaluates a shared address-base word twice, and transfers control indirectly with one explicit computed argument.

The two shared-base evaluations serve different purposes:

- The **first evaluation** captures a value for the outgoing bitwise-OR argument.
- The **second evaluation** supplies the base used to form the third write’s destination.

These values are not guaranteed to be equal. Equality requires an additional assumption that the shared storage remains stable and that its reads have ordinary, repeatable semantics.

The static representation establishes these operations and their represented order. It does not establish an object format, device protocol, initialization routine, or dispatch protocol. Such interpretations are not requirements of this contract.

Behavior depends on explicit parameters, additional incoming execution state, shared storage, and an unresolved indirect dependency. No runtime tests have been performed.

## Behavior

### Ordered operations

For an execution in which preceding operations complete normally, the supplied representation establishes this sequence:

1. **First write: 8 bits.**  
   The destination is twice the second explicit input. The payload is the low eight bits of the first unsigned ambient comparison value.

2. **Second write: 16 bits.**  
   The destination is twice the ambient address-driving integer. The payload is the low 16 bits of the first explicit input.

3. **First shared-base evaluation: capture for the outgoing argument.**  
   The shared base word is evaluated and its value retained. This captured value is later combined with the computed result by bitwise OR.

4. **Computed-result formation.**  
   The second unsigned ambient comparison value is compared with the first. The contribution is one when the second is less than or equal to the first, including equality; otherwise it is zero.

   The computed result combines the first explicit input, the second explicit input, and this contribution, with the arithmetic qualifications below.

5. **Second shared-base evaluation: base for the third destination.**  
   The shared base word is evaluated again, after the computed result has been formed. This second value, rather than the earlier captured value, is added to the computed result to form the third write’s destination.

6. **Third write: 8 bits.**  
   The low eight bits of the computed result are written at the destination formed using the second shared-base evaluation.

7. **Fourth write: 32 bits.**  
   The entire ambient 32-bit payload is written at twice the second explicit input—the same starting address as the first write.

8. **Fifth write: 16 bits.**  
   The destination is the sum of the fourth and second explicit inputs. The payload is the low 16 bits of the second input.

9. **Indirect transfer.**  
   Control transfers to F-INDIRECT-01 with one explicit argument: the computed result bitwise-OR the value captured by the **first** shared-base evaluation.

10. **Return, if reached.**  
    If the indirect operation returns normally, the represented body returns without further visible memory writes.

The two shared-base evaluations are distinct in the representation. This does not prove that an implementation performs two physical load transactions. Load coalescing, compiler treatment, device transactions, and concurrent visibility are not established.

### Arithmetic requirements and limits

The comparison is unsigned and inclusive. Under the indicated 32-bit model, a comparison operand with its high bit set is treated as a large unsigned value, not as a negative signed value.

The first and second explicit inputs are added as signed integers before the unsigned comparison contribution is incorporated. Therefore:

- If that signed sum is representable, it is converted as required for combination with the unsigned contribution.
- The resulting unsigned arithmetic is consistent with a 32-bit result.
- If the signed sum overflows, guaranteed wraparound is **documented_only**; the supplied representation does not independently establish the underlying machine behavior.

For example, a representable signed sum of −1 combined with a contribution of one produces zero under the indicated 32-bit unsigned conversion and arithmetic. This does not justify treating an overflowing signed addition as defined modular arithmetic.

The doubled destinations and the sum forming the fifth destination also involve signed integer expressions. Their overflow cases remain **documented_only**.

The third destination is formed by addition using the second base evaluation. The outgoing argument is formed by bitwise OR using the first base evaluation. These operations differ even when both evaluations return the same value.

Narrowing a stored payload does not narrow the value used elsewhere. A first input of 65,537 supplies a 16-bit payload of 1 to the second write while retaining its full value in the computed-result calculation.

### Aliasing and changing shared state

No disjointness requirement is visible.

The first and fourth writes necessarily share a starting address. On ordinary byte-addressable memory, the fourth write covers the byte affected by the first write and three additional bytes. The earlier byte write remains part of the behavior even if the final ordinary-memory contents no longer distinguish it.

Other destinations may overlap one another or the storage holding the shared base.

The timing of both base evaluations matters:

- The first two writes precede both evaluations. If either overlaps shared-base storage, both evaluations occur after that write.
- No explicit store by this body occurs between the two evaluations.
- Nevertheless, equality of the evaluations is not guaranteed without a stability assumption. External mutation or non-repeatable read semantics could produce different values; whether such behavior is supported by the execution environment is unknown.
- The third and later writes occur after both evaluations. They do not refresh the captured value used for the outgoing argument.
- The third destination is already formed using the second evaluation before the third write takes effect.

This contract does not establish synchronization, atomicity, or a language-level concurrency model. In particular, it does not promise that unsynchronized concurrent access is valid.

The third destination still uses the second evaluated value. Neither use is refreshed because of these later writes.

### Failure before dispatch
