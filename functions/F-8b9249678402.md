# F-8b9249678402

## Purpose

F-8b9249678402 conditionally returns an addressed item to a range-associated free chain. It first consults a dependency, then searches a linked list for the first record whose inclusive address range contains the supplied item address.

For a matching record, the function increments a 32-bit counter. Ordinarily it writes a chain link into the item and installs the item as the record’s free-chain head. If the incremented counter equals a stored threshold, the function may instead unlink and reclaim the entire record, updating several allocator-associated accounting fields.

A sole record in the caller-visible list is retained rather than reclaimed. Reclamation also requires a tag comparison; a failed comparison causes an early return after the counter increment, without linking the item.

The range-record, free-chain, and reclamation terminology describes inferred roles. The observable reads, writes, branches, and dependency calls below are the established contract of the supplied static representation.

## Interface

The function has two inputs and no exposed return value:

- **Container address:** a 32-bit address. The word at byte offset `+0x0c` supplies the initial range-list head.
- **Item address:** a 32-bit address used both for range selection and, on the ordinary return path, as the destination of a 32-bit write.

No explicit null, alignment, writability, or allocation-validity checks protect either input. Whether an input is dereferenced depends on the branch taken.

Each traversed record uses the following fields:

|---|---:|---|
| `+0x00` | 32 bits | Tag compared against a shared tag value before reclamation |
| `+0x04` | 32 bits | Owner address; its `+0x0c` field supplies an unlinking-list head |
| `+0x08` | 32 bits | Next range-record address |

The item need not point to a particular field of the record. The visible selection rule is only membership in the inclusive address interval.

### Reclamation prefix

The reclamation path reads metadata immediately before the selected record:

| Relative byte offset | Width | Observed use |
|---|---:|---|
| `-0x08` | 32 bits | Header validity checks and masked accounting quantity |
| `-0x04` | 16 bits, unsigned | Index for one accounting array |
| `-0x02` | 16 bits, unsigned | Index for another accounting array |

The address at `-0x08`, rather than the record address itself, is passed to the release dependency.

### Preconditions for defined completion

Depending on the chosen path, accessible storage is required for the container, traversed records, item, owner object, prefix metadata, shared state, and computed accounting fields.

Additional structural preconditions include:

- A terminating traversal, or a reachable matching record.
- A valid owner-list structure when unlinking is attempted.
- Valid accounting indices and addresses on reclamation.
- Writable item storage on the ordinary return path.

These conditions are not validated comprehensively. No duplicate-return check, membership ledger, counter-overflow check, or accounting-underflow check is visible.

## Behavior

### 1. Consult the initial dependency

The first action is a call to **F-8ff94386ac71**, with no explicit arguments.

- If its result is zero, the function returns without performing any visible body-level read of the container or item.
- If its result is nonzero, list processing begins.

The dependency may itself have side effects. A zero result therefore does not establish that the entire invocation was side-effect-free.

### 2. Select the first matching range

After the initial dependency returns nonzero, the function reads the container’s list head at `+0x0c`.

Starting at that head, it examines records in next-link order. A record matches when:

- Its lower bound is no greater than the item address; and
- The item address is no greater than its upper bound.

Both endpoints are included. The lower-bound condition is evaluated first; the upper-bound condition is reached only when the lower-bound condition succeeds.

The first matching record is selected. Overlapping ranges are not resolved by size, specificity, or any later criterion.

If traversal reaches a null link, the function returns. On that path, the visible body does not write the item or a record counter.

The supplied representation does not establish a portable ordering rule for unrelated pointers. The observed operation is address-range comparison in the represented 32-bit environment.

### 3. Increment the selected record’s counter

The function reads the selected record’s 32-bit counter, adds one, and stores the result back before deciding whether to reclaim the record.

It compares the incremented value with the record’s threshold:

- **Unequal:** proceed to ordinary item linking.
- **Equal:** evaluate whether the record should be retained or reclaimed.

Equality is the only completion condition. An incremented value greater than the threshold does not trigger reclamation merely because it exceeds the threshold.

No overflow guard is present. The visible operations use 32-bit storage; no wider counter or saturation behavior is evidenced. Exact signed-overflow semantics are not established by the supplied representation.

### 4. Retain a sole caller-visible record

When the incremented counter equals the threshold, the function re-reads the container’s list head.

It retains the record if both conditions hold:

1. The selected record is that head.
2. The selected record’s next link is null.

This is the sole-record exception. It proceeds to ordinary item linking rather than checking the tag or entering reclamation.

The exception is based on the supplied container’s head. It is not based on the owner field inside the selected record.

### 5. Validate the tag before reclamation

For an equality-triggered record that is not retained by the sole-record exception, the function compares the record’s tag with a shared tag value.

If the values differ, the function returns immediately.

At that point:

- The counter increment has already been stored.
- The item has not been added to the free chain by this function.
- The record has not been unlinked by this function.
- No reclamation dependencies have been called.

No rollback or error result is visible.

### 6. Attempt unlinking through the recorded owner

After a successful tag comparison, the function reads the owner address from the selected record, then reads that owner’s list head at `+0x0c`.

- If the owner’s head is the selected record, the head is replaced with the selected record’s next link.
- Otherwise, the function walks the owner list looking for a record whose next link is the selected record. When found, that predecessor’s next link is replaced with the selected record’s next link.
- If the search reaches null without finding a predecessor, reclamation still continues.

Failure to locate the record in its owner’s list is therefore not treated as a reported error or a reason to retain the allocation.

The owner address is obtained from the record, not assumed equal to the original container address. Cycles in the owner list have no visible detection mechanism.

### 7. Prepare and capture accounting state

After the unlinking attempt, the function calls **F-2fd8826557a4**, with no explicit arguments.

Only after that call does it read a shared pointer to obtain the accounting-state base. This ordering matters: the dependency is not assumed to preserve that shared pointer.

The captured base is used for the subsequent explicit accounting accesses and relevant dependency arguments.

### 8. Validate the prefix header

The 32-bit word eight bytes before the selected record is checked.

The function calls **F-a817d8d58c10** if either condition holds:

- The header word is zero.
- Bit 0 of the header word is set.

The supplied representation marks this call as non-returning. It does not establish whether the mechanism is termination, a trap, or another nonlocal transfer.

This check occurs after the counter increment, unlinking attempt, preparation call, and accounting-state capture. No reversal of those earlier effects is visible.

If validation succeeds, the function calls **F-c0fc6d033caa** with the captured accounting-state base. The name and placement do not establish a locking contract.

### 9. Update accounting

Following the return of F-c0fc6d033caa, the function performs the following ordered accounting operations.

First, it reads the unsigned 16-bit index at record-relative offset `-0x04`. It then reads the prefix header and extracts an accounting quantity by retaining only bits selected by `0x3ffffffc`.

That quantity is subtracted from:

1. The 32-bit field at state base plus `0x224`, indexed in four-byte units by the first index.
2. The 32-bit field at state base plus `0x30c`.

Next, it reads the unsigned 16-bit index at record-relative offset `-0x02`. The same saved quantity is subtracted from:

3. The 32-bit field at state base plus `0x0e0`, indexed in four-byte units by the second index.
4. The 32-bit field at state base plus `0x220`.

The function then calls **F-09dcb55e8e0a**, with no explicit arguments. Its returned value selects a four-byte accounting entry beginning at state offset `0x310`.

The function:

5. Decrements that selected 32-bit entry by one.
6. Decrements the 32-bit field at state offset `0x390` by one.
7. Re-reads the prefix header, masks it with `0x3ffffffc`, and subtracts that newly read quantity from the 32-bit field at state offset `+0x08`.

The final subtraction does not necessarily use the earlier saved quantity. F-09dcb55e8e0a occurs between the two header reads, and its effects are unknown.

The two prefix indices are zero-extended 16-bit values before multiplication by four. No bounds checks are visible for either index or for the value returned by F-09dcb55e8e0a. Subtractions and decrements have no visible underflow checks.

### 10. Release and finish

2. **F-e586bff64fb7**, passing the same captured accounting-state base.

It then returns.

On this path, the visible body does not write the item or install it in the record’s free chain. Whether either dependency releases memory, changes global state, or performs synchronization is not established.

### Ordinary item linking

When the counter does not equal the threshold, or when the sole-record exception applies, the function performs two ordered 32-bit stores:

1. Copy the selected record’s current free-chain-head value into the item.
2. Store the item address as the selected record’s free-chain head.

This is consistent with pushing an item onto an intrusive singly linked free chain.

There is no visible check that the item is absent from that chain, properly aligned, or distinct from record metadata. Aliasing can affect the result: the contract is the ordered reads and writes above, not an unconditional abstract insertion into a well-formed chain.

## Side effects

The visible body may modify:

- The selected record’s counter.
- The first word at the item address.
- The selected record’s free-chain head.
- The recorded owner’s list head or a predecessor’s next link.
- Seven accounting locations during reclamation, potentially with aliasing between computed addresses.

The accounting writes occur sequentially, not as a demonstrated transaction.

There is no explicit allocation and no returned ownership token. Ordinary linking makes the item reachable through the record’s free chain. Reclamation passes the record-prefix address to an external dependency; actual deallocation and ownership transfer remain unknown.

No synchronization guarantee follows from the placement of dependency calls. In particular, counter updates and unlinking precede F-c0fc6d033caa.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless stated otherwise, referenced storage is valid, arithmetic remains within the applicable representation, and dependencies return without changing relevant memory.

1. **Initial rejection.**  
   F-8ff94386ac71 returns zero. The function makes no subsequent body-level container read or item write. This case does not require a readable container for the visible body.

2. **No matching interval.**  
   The initial dependency returns nonzero, and traversal terminates without a match. No record counter or item word is modified by the visible body.

3. **Inclusive endpoints.**  
   An item equal to either bound matches that record. If an earlier record also contains the address, the earlier record wins.

4. **Ordinary insertion.**  
   A selected record has counter 4, threshold 9, and free-chain head H. The counter becomes 5; the item receives H; the free-chain head becomes the item address.

5. **Threshold exceeded rather than reached.**  
   A selected record has counter 9 and threshold 9. Incrementing to 10 does not enter the equality-triggered reclamation path. Ordinary linking follows.

6. **Sole record reaches its threshold.**  
   The selected record is the re-read container head and has a null next link. Reaching the threshold retains it and links the item. Its tag is not checked on this path.

7. **Tag mismatch after completion.**  
   A non-sole record reaches its threshold but has a mismatching tag. The increment remains stored. The function returns without item linking or unlinking.

8. **Record missing from owner list.**  
   A qualifying record’s owner list terminates without containing it. The function still proceeds to preparation, prefix validation, accounting, and the release-related calls, subject to their behavior.

9. **Invalid prefix after unlinking.**  
   The record is successfully unlinked, but its prefix header is zero. F-a817d8d58c10 is invoked after that unlinking. No rollback is visible.

10. **Masked quantity and header re-read.**  
    A valid header of `0x40000022` produces an initial masked quantity of `0x20`. If F-09dcb55e8e0a changes that header to `0x40000042`, the first four quantity subtractions use `0x20`, while the final state-`+0x08` subtraction uses `0x40`.
