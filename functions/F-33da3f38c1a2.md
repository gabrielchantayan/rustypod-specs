# F-33da3f38c1a2

## Purpose

F-33da3f38c1a2 updates a caller-supplied object to represent a requested span. It selects between two paths:

- Request storage, invoke a mode-dependent data-producing dependency, and perform two zero-byte writes.
- Invoke an object-management dependency, then install an address derived from an earlier dependency result.

Every normally completing path writes the requested length into the object. The function returns a status determined by the storage-request and data-producing calls, or zero when neither supplies a status.

The apparent intent is to choose between a storage-backed representation and a directly referenced representation. That interpretation is inferred from the operations, not an established ownership or copying contract. The supplied evidence does not establish what data the dependencies produce, whether any memory is allocated or released, or how long an installed address remains valid.

## Interface

The offset, length, and availability comparison are represented as signed integer operations. There is no local rejection of negative values. Arithmetic behavior outside the representable signed range is not established by the supplied material.

### Object layout accessed locally

### Result

The result is a 32-bit status:

- Zero on the direct-address path.
- The storage-request result if that result is nonzero.
- Otherwise, the selected data-producing dependency’s result.

An object-management call does not replace the retained result. The initial dependency’s return value is retained for address construction, not propagated as the function’s status.

## Behavior

### Initial dependency selection

The function begins with status zero and a separate 32-bit availability value initialized to zero.

For zero mode, it calls F-2c622e30ab32 with the source token and the address of that availability value. The call’s return value is retained separately. The supplied interface permits the dependency to update availability, but its actual output and error conventions are unknown.

For nonzero mode, it instead calls F-43cbbc4d8bad with no explicit arguments visible in the supplied representation. No local operation changes availability from its initialized zero value on this path.

The initial return value is not checked for success or failure. It is used only if execution selects the direct-address path.

### Route selection and conditional reads

The storage-backed path is selected when either:

1. Availability is less than the start offset plus the requested length; or
2. Bit `0x0040` is set in the 16-bit field at `0x1C`, and the 32-bit field at `0x20` equals zero.

Otherwise, execution selects the direct-address path.

The predicate is short-circuited:

- When the availability comparison is true, neither object-state field is read for this decision.
- Otherwise, the field at `0x1C` is read.
- The field at `0x20` is read only when the tested bit is set.

These reads occur after the initial dependency returns. Entry-time values of those fields are not necessarily the values used for selection.

Equality in the availability comparison does not force storage. The separate object-state condition can still do so.

For nonzero mode, the locally initialized availability is zero. This does not universally force storage: when the offset-plus-length sum is zero or negative, the signed comparison can be false, subject to arithmetic representability.

### Storage-backed path

The function calls F-05077d384bfe with:

1. The object address.
2. Requested length plus two.
3. Zero.

The call’s result replaces the status.

If that result is nonzero, the function performs none of its subsequent representation-field writes, data-producing calls, zero-byte writes, or object-management calls on this path. It proceeds to the final length write and returns the storage-request result.

This is not failure atomicity. F-05077d384bfe may have changed the object or other state before returning a nonzero value.

If the storage-request result is zero, the function performs these local writes in order:

1. Write the 16-bit value `0x0070` at `0x1C`.
2. Write the 8-bit value `0` at `0x1F`.
3. Write the 8-bit value `4` at `0x1E`.

The first write replaces the whole 16-bit field; it is not a bit-preserving update.

The function then selects a data-producing dependency:

- For zero mode, F-94e0df6353ed receives the source token, start offset, requested length, and a 32-bit value read from `0x14`.
- For nonzero mode, F-d03652a548f9 is called with no explicit arguments visible in the supplied representation.

The selected call’s result replaces the status.

After that call returns, the function performs two distinct read-and-write operations, in this order:

1. Read the current 32-bit data-address field at `0x14`; write one zero byte at that address plus the requested length.
2. Read the data-address field at `0x14` again; write one zero byte at this newly read address plus the requested length plus one.

Both writes occur regardless of whether data production returned zero or nonzero.

There is no shared address snapshot across the two writes. The first zero-byte write can itself overlap and change the field at `0x14`. Consequently, the second destination need not be adjacent to the first, even when arithmetic is representable and every access is valid. Consecutive destinations follow only if the two field reads produce the same value.

The earlier read used as an argument to F-94e0df6353ed is also independent of these later reads. The data-producing dependency is not established to preserve the object’s address field.

After both zero-byte writes, a nonzero data-producing status causes a call to F-74b5a05d0094 with the object address. The function retains the data-producing status across this call.

Execution then reaches the final length write.

### Direct-address path

The function performs these operations in order:

1. Call F-74b5a05d0094 with the object address.
2. Write the retained initial dependency result plus the start offset into the 32-bit field at `0x14`.
3. Write the 16-bit value `0x0110` at `0x1C`.
4. Write the requested length at `0x18`.
5. Return zero.

This path makes no storage request, invokes no data-producing dependency, and performs no local zero-byte writes to data storage.

The installed address is derived from the retained initial return value, not from an object field read after the management call.

There are no explicit local writes to `0x1E`, `0x1F`, or `0x20` on this path. That does not guarantee preservation of their entry values: dependencies may modify them.

### Completion and arithmetic boundaries

Every path that reaches normal completion writes the requested length as a 32-bit value at `0x18`. This includes both storage-request failure and data-producing failure.

The final length is not a count of bytes confirmed to have been produced. It is the supplied requested length.

Relevant arithmetic includes:

- Start offset plus requested length.
- Requested length plus two.
- Initial dependency result plus start offset.
- Each freshly read data address plus requested length, with an additional one for the second zero-byte write.
- Object-base additions for field accesses.

No explicit widening, overflow check, saturation, bounds check, or address-wrap handling is visible. Exact behavior at arithmetic limits is documented_only. In particular, a negative requested length is not locally converted into a valid nonnegative storage size.

There is no visible local exception or fault handler. A nonreturning dependency, invalid memory access, or other abnormal interruption can prevent later operations, including the final length write.

## Side effects

Established local effects are:

- Conditional reads of the state fields at `0x1C` and `0x20`.
- Dependency calls selected by mode, route, and returned status.
- Representation metadata replacement following a zero storage-request result.
- Two ordered zero-byte writes following data production, including when data production reports failure.
- Direct installation of a derived address on the direct-address path.
- A requested-length write before every normal return.

Aliasing can make a nominal data write also mutate object fields. Later reads observe the resulting contents, and later stores can overwrite earlier effects. For example, the first zero-byte write may change the address used by the second; the final length write may replace bytes previously affected through an overlapping data address.

No allocation or release primitive is directly established. The storage-request and object-management roles are inferred descriptions of their use here, not guarantees about their internals.

The function does not establish ownership transfer, reference counting, release behavior, thread safety, reentrancy, or preservation of globals. Nonzero status does not imply an unchanged object.

## Acceptance examples

These are conditional checks derived from static evidence, not executed tests. Unless an example states otherwise, arithmetic is assumed representable, accesses valid, and dependencies normally returning. Address-field stability is an additional condition where explicitly stated.

### Sufficient availability and direct-address selection

Given zero mode, availability `100`, start offset `10`, requested length `20`, and bit `0x0040` clear when read:

- The direct-address path is selected.
- F-74b5a05d0094 runs before the address and state stores.
- The installed address is the initial dependency result plus `10`.
- State becomes `0x0110`, length becomes `20`, and the result is zero.
- There are no local data zero-byte writes.

Availability `30` also passes the availability comparison for this span. The object-state condition remains relevant.

### Object state forces storage

Given sufficient availability, bit `0x0040` set, and `0x20` equal to zero when read, storage is requested.

If `0x20` is nonzero instead, that state condition does not force storage. If availability is insufficient, the decision does not require either state-field read.

### Storage-request failure

Given selection of the storage-backed path, requested length `20`, and storage-request result `7`:

- F-05077d384bfe receives size `22`.
- No local representation metadata update, data-producing call, or zero-byte write follows.
- The final length becomes `20`.
- The function returns `7`.

Mutations inside the storage-request dependency are not ruled out.

### Data-producing failure

Given zero storage-request result and data-producing result `9`:

- The metadata writes occur before data production, in the specified order.
- Both zero-byte writes occur after data production.
- Each zero-byte destination uses its own current address-field read.
- F-74b5a05d0094 runs after both writes.
- The final length is written, and the retained result is `9`.

The two destinations need not be consecutive.

### Zero-length request with stable address field

Given requested length zero, selection of the storage-backed path, and zero storage-request result:

- The storage size argument is `2`.
- The selected data-producing dependency is still called.
- The first zero-byte destination is the address read from `0x14` for that operation.
- The second destination is the address separately read from `0x14` for the second operation, plus one.

Only if the field remains unchanged between those reads are the destinations the same base address and its next byte.

A direct-address path with zero length performs neither zero-byte write. There is no zero-length early return.

### Zero-length request with address-field aliasing

Suppose the first zero-byte destination overlaps the field at `0x14`, and storing zero there changes the field’s 32-bit value. If all resulting accesses remain valid:

- The second write uses the changed field value plus one.
- It is not required to target the byte following the first destination.
- The function does not restore the original address before the second read.

This follows from the separate reads; it requires no arithmetic overflow or asynchronous mutation.

### Nonzero mode and a zero span end

Given nonzero mode, start offset zero, and requested length zero, the local availability comparison is false because both sides are zero.

If the state condition also does not force storage, execution takes the direct-address path. Nonzero mode alone therefore does not guarantee a storage request.
