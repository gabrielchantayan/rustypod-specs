# F-6117aaae3952

## Purpose

F-6117aaae3952 conditionally performs a forward sequence of dependency calls followed, on some paths, by a reverse-indexed sequence of object-dispatched calls. It returns a 32-bit value of zero or one.

The established behavior is defined by call arguments, call ordering, integer operations, and branch conditions. A collection search followed by backward submission is a plausible interpretation, but the dependency contracts needed to establish that interpretation are unavailable.

Two helpers receive the same saved object-relative address: one before the enable-field read and one before each visible normal return. Their placement suggests entry and exit synchronization, but **locking, unlocking, mutual exclusion, and serialized execution are not established**.

Likewise, dependency names such as “initialization,” “indexed access,” “comparison,” “transfer,” and “cleanup” describe inferred roles only. The supplied body does not establish what those dependencies read, write, allocate, release, or transform.

A significant boundary behavior is established independently of those interpretations: after a zero query result at reverse index zero, the function calls a dependency with index bits 0xFFFFFFFF, then performs another object submission and query before returning zero, provided those calls return normally.

## Behavior

### Entry helper and enable decision

The function computes the object-relative address at offset 0xA4C and calls the entry helper with that address.

After the helper returns, the function reads the 32-bit field at object offset 0x054. Consequently, the decision uses the field’s value after any effects of that helper, not necessarily its value at function entry.

If the field is zero, the function calls the exit helper with the saved address and returns zero. No mapped dependency or indirect object operation described below is invoked on this path.

The body does not explicitly reread the enable field. Later changes to it do not create a second enable decision in this function.

### Enabled-path preparation

For a nonzero enable field, the following calls occur in order:

1. F-df2422ba76c2 receives the collection storage address and two zero arguments.
2. F-2588e3ea1153 receives the collection storage address. Its result is retained as an unsigned 32-bit value, called the **count**.
3. F-961dd3c5e67e receives the target storage address and the object-relative address at offset 0x074.

“Collection preparation,” “count query,” and “target acquisition” are inferred roles. Established behavior is limited to the stated arguments, order, and use of the returned count.

F-961dd3c5e67e is called even when the count is zero. Its call does not prove that object data is converted into, or written to, the target storage.

The count is obtained once. The body does not refresh it after later dependency or object calls. This does not imply that collection storage, object data, globals, or other reachable state remain unchanged.

When the count is zero, the function calls F-ccf4fcd3c34d with the collection storage, calls the exit helper with the saved address, and returns zero.

### Forward phase

For a nonzero count, the function first calls F-e478ae4ee528 with:

- The current storage address.
- The collection storage address.
- Index argument zero.

It then begins a forward phase with an unsigned 32-bit position initially equal to one.

At each forward decision, F-d45d65316ed3 receives the target storage address followed by the current storage address. Its result is used only to distinguish zero from nonzero.

The function continues forward only if:

- That result is zero; and
- The position is less than the retained unsigned count.

The dependency call occurs before the count comparison. Thus, the current storage is passed to F-d45d65316ed3 even when the position has already reached the count.

Each continuation performs these actions in order:

1. Calls F-e478ae4ee528 with the reusable scratch storage, collection storage, and current position.
2. Calls F-1033f0501634 with the current storage address followed by the reusable scratch storage address.
3. Increments the unsigned position.
4. Returns to the next F-d45d65316ed3 call.

This sequence does not establish that F-e478ae4ee528 retrieves an entry or that F-1033f0501634 copies it. Their write directions, accessed extents, and transformations remain unknown. The observable guarantee is the sequence of pointer and index arguments.

The comparison/search interpretation is also inferred: the body does not establish whether a nonzero result means equality, inequality, validity, or another predicate.

Using indices solely to identify successive forward calls:

- If the first nonzero F-d45d65316ed3 result follows the call associated with index \(j\), the position is \(j+1\).
- If every such result is zero, the position reaches the retained count.
- If the position remains one, reverse processing is skipped.

Therefore, a nonzero result at the first forward decision prevents reverse processing. A count of one also prevents reverse processing, regardless of that decision’s result.

### Reverse phase

If the forward position is not one, the function subtracts two using the represented 32-bit arithmetic and interprets the result as a signed 32-bit reverse index.

It calls F-e478ae4ee528 with the initial reverse storage address, collection storage address, and that reverse index.

Each reverse iteration then performs:

1. F-1033f0501634 receives the current storage address and the selected scratch address.
2. The indirect object operation at dispatch-table byte offset 0x054 receives the object pointer, current storage address, and additional arguments **0, 0, 3, 3, 0**, in that order.
3. The indirect object operation at dispatch-table byte offset 0x16C receives the object pointer.
4. The function tests the latter operation’s result for zero versus nonzero.

The selected scratch address is the initial reverse storage on the first iteration and the reusable scratch storage on subsequent iterations.

“Submission” and “query” below are inferred names for these indirect operations. No return value from the submission controls visible branching.

If the query returns nonzero, iteration stops immediately. The function then checks whether the signed reverse index is nonnegative.

For a nonnegative index, it:

1. Calls the object operation at dispatch-table byte offset 0x0E0 with the object pointer and additional arguments **0xFFFFFFFF, 0, 0, 0**.
2. Calls F-ccf4fcd3c34d with collection storage.
3. Calls the exit helper with the saved address.
4. Returns one.

The all-ones argument is established as a 32-bit bit pattern. Its semantic interpretation as a negative value, unsigned maximum, or sentinel is unknown.

For a negative index, the nonzero query instead leads to F-ccf4fcd3c34d, the exit helper, and return zero. The operation at offset 0x0E0 is not called.

If the query returns zero, the function checks the signed index:

- If negative, reverse processing ends with return zero after the two final helper calls.
- If nonnegative, the function decrements it, calls F-e478ae4ee528 with reusable scratch storage, collection storage, and the new index, then begins another iteration.

### Negative-index boundary

There is no nonnegative-index guard before the initial reverse dependency call or before a reverse submission.

In an ordinary descending traversal, a zero query at index zero causes the index to become −1. The function then:

1. Calls F-e478ae4ee528 with index bits 0xFFFFFFFF.
2. Calls F-1033f0501634 with current storage and reusable scratch storage.
3. Calls the object submission.
4. Calls the object query.

If these calls return normally, either query result leads to return zero without the operation at offset 0x0E0.

Whether F-e478ae4ee528 accepts this argument, treats it specially, or performs an invalid access is unknown. An implementation that stops before making these calls would not preserve the established call behavior.

### Integer boundaries

The retained count and forward position are unsigned 32-bit values. The position does not wrap in the visible forward loop: an increment occurs only after a position strictly less than the count.

The initial reverse index has the bit pattern of the forward position minus two:

- Positions from 2 through 0x80000001 produce nonnegative signed reverse indices.
- Positions from 0x80000002 through 0xFFFFFFFF produce negative signed reverse indices.

Even an initially negative index is passed to F-e478ae4ee528 and participates in one submission/query iteration before the negative-index outcome is applied. Such a path cannot return one.

The ordinary decrement from zero to −1 does not overflow signed 32-bit range. An already negative reverse index is not decremented by this loop.
