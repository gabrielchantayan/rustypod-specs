# F-550cd22693e0

## Purpose

F-550cd22693e0 links a newly obtained node into a tree-shaped container, performs color-based insertion repair, and returns the new node through caller-provided storage.

The visible structure is consistent with red-black-tree insertion: nodes have a color byte, parent and child links, and repair proceeds through recoloring and calls consistent with left and right rotations. That interpretation is inferred intent. The established contract is the sequence of calls, field accesses, conditional writes, and output assignment described below.

This operation is not a visible search or duplicate-checking operation. Its caller supplies an attachment node and a selector that influences which child link is written. The function does not itself establish that the resulting position is valid for the container’s ordering relation.

## Interface

The function accepts five arguments:

| Argument | Role established by the visible body |
|---|---|
| Result storage | Address receiving one 32-bit node-pointer value at normal completion. |
| Container | Address of mutable state containing a header pointer, a count, and comparator-related storage. |
| Attachment selector | A 32-bit scalar. Zero and nonzero select different attachment behavior. It is also forwarded to node preparation. |
| Attachment node | Address of the node or header under which the new node is to be attached. |
| Incoming value | An opaque 32-bit value forwarded to dependencies. Its representation and ownership are not established. |

There is no explicit return value. The result is communicated by writing the new node’s address to result storage.

|---|---|

| +0x19 | Address passed to the comparison dependency. No direct access to its contents is visible here. |

Header-relative fields:

| Offset | Observed role |
|---|---|
| +0x04 | Root pointer. |
| +0x08 | Endpoint pointer maintained by attachment on the +0x08 side. |

Node-relative fields:

| Offset | Access |
|---|---|
| +0x00 | One-byte color or state. Zero receives the treatment conventionally associated with red; any nonzero value receives the treatment conventionally associated with black. Writes use exactly zero or one. |
| +0x04 | Four-byte parent pointer. |
| +0x08 | Four-byte first child pointer, conventionally the left child. |
| +0x0c | Four-byte second child pointer, conventionally the right child. |

These are accessed fields, not a complete declaration of either object. Padding, payload size, allocation size, alignment requirements, and other fields remain unspecified.

### Preconditions

Normal completion requires accessible, writable storage for every field reached by the selected execution path. In particular:

- Result storage must accept a four-byte pointer write.
- The container must provide the visible fields.
- Node preparation must return a usable node address.
- The attachment node must support the selected child-link write.
- Parent and ancestor links used during repair must lead to valid objects.
- The header’s root link must designate a node whose first byte can be written at finalization.

There is no visible validation of these conditions. Null checks exist for certain uncle pointers, not for the container, header, returned node, parent, or grandparent generally.

## Behavior

### 1. Obtain a node

The first observable call is to F-3c2615c72aa2. Its six arguments, in order, are:

1. Container address.
2. Incoming value.
3. Attachment selector.
4. Attachment node address.
5. Attachment selector again.
6. Attachment node address again.

The returned address becomes the new node address and remains the address eventually written to result storage, regardless of which node becomes the focus of balancing.

The dependency’s internal reads, writes, allocation behavior, and failure behavior are unknown. Fields subsequently read from the container are read after this call; their entry values are not guaranteed to remain intact.

### 2. Increment the count

After node preparation returns, the function reads the four-byte field at container +0x14 and writes back its value increased by one.

This happens before attachment selection, comparison, or balancing. There is no visible overflow check, saturation, or rollback.

The recovered expression uses a signed 32-bit value. Behavior at signed overflow is not established by the supplied representation; a portable modulo-\(2^{32}\) guarantee must not be inferred.

### 3. Select and write the attachment link

The function reads the current header pointer from container +0x10.

It takes the first-child attachment path if either:

- The attachment node equals that header pointer; or
- The attachment selector is nonzero.

Otherwise, it calls F-31a0b2b5649a with:

1. The address container +0x19.
2. The incoming value.
3. The address attachment node +0x10.

Any nonzero comparison result selects first-child attachment. A zero result selects second-child attachment. There is no distinction among positive and negative nonzero results, and no visible duplicate-rejection branch.

#### First-child attachment

The function writes the new node address at attachment node +0x08.

It then reloads the container’s header pointer.

If the reloaded header differs from the attachment node:

- The function reads that header’s +0x08 endpoint.
- It replaces the endpoint with the new node only if the previous endpoint equals the attachment node.

If the reloaded header equals the attachment node:

- The function writes the new node to that object’s +0x04 root field.
- It reloads the container’s header pointer again.
- It writes the new node to the reloaded header’s +0x0c endpoint without an equality test.

Under ordinary nonaliasing, unchanged-header conditions, attachment to the header therefore establishes the new node as the root and both endpoints. The actual behavior is governed by the reloads, not by a permanently cached header address.

#### Second-child attachment

The function writes the new node address at attachment node +0x0c.

It then reloads the header pointer and examines that header’s +0x0c endpoint. The endpoint is replaced with the new node only when its previous value equals the attachment node.

No header +0x08 endpoint update is made on this path.

### 4. Establish the parent link

After the attachment and endpoint writes, the function writes the attachment node address to new node +0x04.

There is no direct initialization here of the new node’s color or child links. Correct initialization of those fields is an external precondition or a dependency responsibility, not an established effect of this function.

### 5. Repair color and ancestry relationships

The repair focus initially equals the new node.

At each iteration, the function reloads the header and reads its root pointer. If the focus equals the root, repair stops without first testing the parent’s color.

Otherwise, it reads the focus’s parent pointer and then the parent’s first byte. If that byte is nonzero, repair stops. If it is zero, repair continues using the parent’s parent as the grandparent.

The two structural cases are mirror images in intended tree terminology, with a dependency-call detail noted below.

#### Parent occupies the grandparent’s first-child link

The function compares the parent with grandparent +0x08. If equal, the uncle is read from grandparent +0x0c.

If the uncle is nonnull and its color byte is zero:

1. Write one to the parent’s color byte.
2. Write one to the uncle’s color byte.
3. Re-read the focus’s parent and that parent’s parent, then write zero to the resulting grandparent’s color byte.
4. Re-read that ancestry and move the repair focus to the grandparent.
5. Repeat the root and parent-color checks.

If the uncle is null or has a nonzero color byte:

- If the focus equals parent +0x0c, call F-4b53288e056a with the container and parent. After it returns, set the repair focus to the parent address saved before that call.
- Read the repair focus’s current parent and write one to that parent’s color byte.
- Re-read the focus’s parent and grandparent, then write zero to the grandparent’s color byte.
- Re-read the ancestry and call F-63a2b3ccf83b with the container and resulting grandparent address.
- Repeat the loop checks.

#### Parent does not occupy the grandparent’s first-child link

The function does not separately prove that the parent occupies grandparent +0x0c. Any unequal parent follows this branch.

Here the candidate uncle is the value read from grandparent +0x08.

If that pointer is nonnull and its first byte is zero, the same parent-and-uncle recoloring and upward focus movement occur.

Otherwise:

- If the focus equals parent +0x08, call F-63a2b3ccf83b using the operand sequence described under Dependencies. After it returns, set the focus to the parent address saved before the call.
- Write one to the focus’s current parent color byte.
- Re-read its ancestry and write zero to the grandparent color byte.
- Re-read the ancestry and call F-4b53288e056a with the container and resulting grandparent address.
- Repeat the loop checks.

The function does not visibly impose an iteration limit or detect malformed cycles.

### 6. Finalize and report the inserted node

After repair stops:

1. Reload the container’s header pointer.
2. Read that header’s root pointer.
3. Write one to the root’s first byte.
4. Write the original new node address to result storage.

The reported node is therefore the node obtained initially, not necessarily the root or the final repair focus.

## Side effects

Direct visible writes comprise:

- One count increment.
- One attachment child-link write.
- Conditional endpoint writes, or root and endpoint initialization when attaching to the header.
- One new-node parent-link write.
- Zero or more repair color writes.
- One final root-color write.
- One result-storage write.

Dependencies may perform additional effects. Their effects are not bounded by this body.

The operation is incremental rather than transactional. The count changes before the comparison call and before attachment completes. Later interruption can leave earlier writes visible; no rollback or error-result protocol is shown.

No direct deallocation or release is visible. That does not establish that dependencies allocate, retain, copy, release, or transfer ownership of the incoming value or node storage. The caller’s obligations after completion remain documented_only.

Aliasing is not prohibited by an explicit check. Aliasing result storage, container fields, header fields, or node fields can make earlier writes affect later reads. The ordered field-access contract remains applicable, but ordinary tree semantics require suitable separation. In particular, the final result write occurs after the final root-color write.

## Acceptance examples

These examples are conditional static consequences, not executed tests.

1. **Insertion through the header.**  
   Given a stable header, nonaliasing storage, and an attachment node equal to that header, comparison is skipped. The new node is written to the header’s +0x08, +0x04, and +0x0c fields, and its parent becomes the header. The initial repair focus equals the root, so repair stops immediately. Finalization writes one to the root color and returns the new node through result storage.

2. **Nonzero selector under a nonheader node.**  
   Comparison is skipped regardless of the incoming value. The attachment node’s +0x08 link receives the new node. The header’s +0x08 endpoint changes only if it previously equaled the attachment node.

3. **Zero selector with zero comparison result.**  
   For a nonheader attachment node, F-31a0b2b5649a is called. A zero result writes the new node to attachment node +0x0c. Only the header’s +0x0c endpoint is considered for conditional replacement.

4. **Zero selector with any nonzero comparison result.**  
   Positive and negative nonzero results both select the +0x08 attachment path. Neither independently causes rejection or an error result.

5. **Nonroot focus with a nonzero parent color.**  
   Repair stops at the parent-color check. Finalization still forces the current root color to one and writes the initially obtained node address to result storage.

6. **Zero-colored parent and zero-colored nonnull uncle.**  
   Parent and uncle become one; the grandparent becomes zero; repair continues from the grandparent. If that grandparent is the current root, finalization subsequently makes its color one.

7. **Null uncle.**  
   The null uncle is not dereferenced for its color. Repair takes the rotation-oriented path, conditional on the inner-child relationship.

8. **Node preparation fails to return.**  
   If the initial dependency does not return normally, no subsequent count increment or result write by this body occurs. Effects already performed by that dependency remain unknown.
