# F-966f73c8580e

## Purpose

F-966f73c8580e conditionally records a state transition for a caller-supplied handle and an associated shared object. It publishes a context value, recognizes already-satisfied requests, checks compatibility, obtains resource availability, and performs additional operations for nonzero requests.

The request is a signed 32-bit integer. Three predicates govern behavior: equal to zero, nonzero, and greater than one. Negative requests follow the nonzero path but not the greater-than-one path. No restriction to requests 0, 1, and 2 is established.

The result is a 32-bit unsigned status. Zero indicates an already-satisfied request or completion of the function’s state-recording path. Locally selected failure statuses are 5 and 8. Dependencies can also return failures, including those same numbers. In particular, returned status 8 does not establish that the shared object’s rejection flag was nonzero.

“Handle,” “shared object,” “resource,” and “state” are descriptive terms. Domain interpretations such as locking, transactions, or read/write access are not established.

## Behavior

### Entry publication and already-satisfied requests

The shared-object reference is read from the handle before F-0b4658e20c99 is called without arguments. After that call returns, the handle’s current first word is read and written to offset +4 of the captured shared object.

Consequently, a dependency change to the handle’s shared-object field does not redirect this invocation’s later shared-object accesses. A change to the handle’s first word can affect the published value. Publication occurs before satisfaction or compatibility checks, including on paths that ultimately reject the request.

The handle-state byte is then examined:

- State 2 satisfies every request immediately.
- State 1 satisfies a zero request immediately.
- Other combinations proceed to compatibility checks.

The first state comparison tests for 2. If it does not match, the source expresses a further state read for comparison with 1. No atomic snapshot across those reads is established.

An already-satisfied request skips acquisition, compatibility checks, and direct state recording. It still performs entry publication and calls F-96dd78c4ca33 with the original handle before returning zero.

States outside 0, 1, and 2 are not independently rejected.

### Initial compatibility checks

For an unsatisfied request, shared-object byte +17 is read. A nonzero byte causes local status 8 only when the request is nonzero. The read itself precedes that request-dependent decision, including for zero requests.

If this check permits continuation, shared-state byte +48 is examined:

- Shared state 2 rejects a nonzero request with local status 5.
- Shared state 2 permits a zero request to continue.
- Shared state other than 2 requires eligibility-list traversal only for requests greater than one.

Traversal begins at shared-object offset +88. Each encountered node’s handle reference must equal the input handle. A mismatch immediately selects status 5, without needing to read that node’s next reference. A match permits reading its next reference and continuing.

An empty list passes. Multiple nodes naming the input handle pass if traversal terminates. A cycle containing only matching references can prevent termination.

These initial status-5 and status-8 rejections go directly to finalization. They do not call F-ce2b2a7a0121.

### Availability and retained status

The acquisition phase begins with retained status zero on its first entry. It reads the resource field at shared-object offset +12.

If that field is zero, F-b5915edc3f5a is called with the captured shared object. Its 32-bit result replaces the retained status. The resource field is then reread, and its value is combined with that status by bitwise OR for the waiting decision.

Acquisition calls continue only while both the reread resource field and retained status are zero. Thus:

- An initially nonzero resource skips the acquisition dependency.
- A zero acquisition result with no resource causes another acquisition call.
- A nonzero acquisition result stops the wait even if no resource appeared.
- Installing a resource does not cancel a nonzero acquisition result.

After the wait, retained status zero permits request processing. A nonzero retained status enters cleanup.

On retry, the retained status is not automatically reset. The resource field is first read without combining it with that retained status. Therefore, a nonzero resource on retry can skip acquisition while leaving status 5 intact, producing another cleanup cycle rather than success.

### Request-specific processing

For a zero request, resource availability with retained status zero leads directly to state recording. This path does not call F-14d1c687a87a or F-bbff782234dd and does not directly clear shared-object byte +16.

For a nonzero request, byte +17 is checked again. A nonzero value now selects status 8 and enters cleanup, unlike the initial flag rejection, which bypasses cleanup.

If the later flag check passes:

1. The current resource reference is read again from shared-object offset +12.
2. The 32-bit word at that resource’s offset +72 is read.
3. F-14d1c687a87a receives that word and a Boolean indicating whether the signed request is greater than one.
4. Only if its status is zero is F-bbff782234dd called with the captured shared object.

A nonzero result from either operation becomes the retained failure status and enters cleanup. This includes dependency-provided status 8 even when both flag checks observed zero.

When both operations return zero, shared-object byte +16 is cleared before state recording. The Boolean supplied to F-14d1c687a87a is false for negative requests and request 1, and true for requests 2 through the maximum positive signed 32-bit value.

### Cleanup and retry

Failures from acquisition or request-specific processing call F-ce2b2a7a0121 with the captured shared object. Its return value is not used.

After cleanup returns:

- Any retained failure other than 5 exits toward finalization.
- Status 5 also exits if the current shared-state byte +48 is nonzero.
- For status 5 with current shared state zero, the current 32-bit value at shared-object offset +4 is read and used as an address base displaced by 316 bytes. F-f0bae2500f54 receives that derived address.
- A zero result from F-f0bae2500f54 ends retry processing.
- A nonzero result returns to acquisition with retained status 5.

The retry decision uses values read after cleanup, not preserved entry values. In particular, cleanup may affect whether retry consultation occurs and which address it receives.

Approved retry does not guarantee progress. If the resource remains nonzero, acquisition can be skipped while retained status 5 causes cleanup again. If it is zero, another acquisition call can replace the retained status.

Retry does not repeat initial handle satisfaction, initial compatibility checks, or eligibility traversal. A retry that eventually reaches nonzero-request processing does repeat the later flag check.

### Successful state recording

The handle-state byte is reread at commit. If it is zero, the 32-bit counter at shared-object offset +52 is read, incremented by one, and written back. Counter eligibility depends on this commit-time state, not the earlier satisfaction checks.

The chosen new state is 1 for a zero request and 2 for any nonzero request. Direct operations then occur in this order:

1. Write the chosen byte to handle offset +8.
2. Read shared-object byte +48 as an unsigned value.
3. Write the chosen state there only if the current unsigned value is smaller.
4. For a request greater than one, write the input handle reference to shared-object offset +92.

The shared-state operation never directly lowers its observed unsigned value. For example, an observed value of 200 remains unchanged when the chosen state is 1 or 2.

The counter is a 32-bit operation represented as signed addition. Overflow behavior is unresolved; neither saturation nor portable wraparound is promised.

### Finalization and return

The direct stores described above occur before this dependency. Its preservation properties are unknown, so successful state recording is not an unconditional guarantee that those contents remain unchanged after finalization.
