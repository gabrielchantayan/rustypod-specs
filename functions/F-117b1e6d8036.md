# F-117b1e6d8036

## Purpose

F-117b1e6d8036 accumulates compact records associated with one row-like coordinate. Each record contains a signed-coordinate field, a 16-bit extent field, and an 8-bit magnitude. A new request either:

- Produces no record because its normalized magnitude is zero.
- Extends the most recent record when its row, endpoint, and magnitude match.
- Appends a record to the current batch.
- Starts a replacement batch, optionally delivering the previous batch to an indirect callback first.

“Row,” “coordinate,” “extent,” and “magnitude” describe inferred roles. The established behavior is the arithmetic, comparisons, memory accesses, and callback conditions below. No rendering, clipping, allocation, or eventual consumption of the final pending batch is established.

| Offset | Width | Access and meaning |

| Record-relative offset | Width | Meaning |

The inline area from `0x408` through `0x4C7` accommodates 32 records without overlapping the count field. This layout agrees with the append threshold of 32.

The conventional valid-state precondition is a count from 0 through 32, with that many initialized records and an appropriate current-row value. The function does not validate this precondition. Behavior for other counts is described where established, but memory safety is not guaranteed.

No input extent positivity check, coordinate-range check, null-state check, or alignment check is present.

## Behavior

### Magnitude normalization

The magnitude input first undergoes a signed right shift by nine bits. The resulting signed value is made nonnegative.

Under arithmetic signed-right-shift behavior, the shifted range is −4,194,304 through 4,194,303. Negating a negative shifted result therefore does not encounter the signed minimum-value negation problem.

The flag word is then read. Only bit `0x2` affects this function.

When that bit is clear, the nonnegative shifted magnitude is saturated at 255.

When that bit is set:

1. Only the low nine bits of the nonnegative shifted magnitude are retained, producing a value from 0 through 511.
2. Values above 256 are reflected about 256: their result is 512 minus that value.
3. A value of exactly 256 becomes 255.
4. Values below 256 remain unchanged.

The resulting magnitude is always from 0 through 255. With the flag set, magnitude is periodic after taking the absolute shifted value; it is not simply saturated.

Signed-right-shift semantics matter for negative inputs. With arithmetic shifting, an input of −1 becomes −1 before absolute value, and therefore yields magnitude 1 rather than zero. The supplied representation expresses a signed shift, but no independent execution evidence establishes the underlying shift instruction.

### Coordinate adjustment and zero-magnitude exit

After normalization, the function reads the row offset and adds it to the row input. It then reads the horizontal offset and adds it to the horizontal input.

Both adjusted coordinates retain 32-bit values. Subsequent row comparisons use the complete 32-bit adjusted row. The horizontal coordinate is not narrowed to 16 bits until a new record is written.

These offset reads and additions occur even when the normalized magnitude is zero. If the magnitude is zero, the function then returns:

- No count or record inspection follows.
- No callback is invoked.
- No state write is performed by this function.

For overflowing coordinate addition, the intended machine-level interpretation is low-32-bit arithmetic. The supplied source representation alone does not establish portable signed-overflow semantics.

### Attempting to extend the most recent record

For a nonzero magnitude, the function reads the signed record count.

Only a count greater than zero enables a merge attempt. The most recent record is the record at index count minus one.

The merge checks are ordered:

1. Read and compare the current batch row with the adjusted row.
2. If the rows match, read the previous record’s extent as unsigned 16 bits.
3. Read the previous record’s horizontal coordinate as signed 16 bits and form its endpoint by adding the unsigned extent.
4. Compare that endpoint with the full adjusted horizontal coordinate.
5. Only if the endpoint matches, read and compare the previous record’s magnitude byte.

The endpoint can range from −32,768 through 98,302, so its construction does not require signed 32-bit overflow.

If all three conditions match—row, endpoint, and magnitude—the previous extent is replaced by the low 16 bits of its sum with the signed 16-bit extent input. The function then returns.

A successful merge:

- Changes only the previous record’s extent field through this function’s direct writes.
- Does not increment the count.
- Does not change the current row.
- Does not invoke the callback.
- Does not enforce a maximum or nonnegative extent.

Extent addition is therefore effectively modulo 65,536 at storage. Zero and negative extent inputs are accepted, including when they shrink or wrap the stored extent.

A count of 32 does not force delivery before this merge attempt. A matching request can extend the last record of a full batch.

### Appending without replacing the batch

If merging does not occur, the function reads the current-row field again.

If that value equals the adjusted row and the previously read signed count is less than 32, it selects the record slot at that count and appends there. The count need not be positive for this branch to be taken.

For valid counts from 0 through 31, this is an append within the inline area. In particular, a zero count with a matching current row appends without first rewriting the row or count.

For a negative count with a matching row, the selected address precedes the normal record area. There is no validation to prevent this. Such a state is outside the ordinary safe-use precondition.

### Replacing or delivering the batch

If the current row differs, or the saved count is at least 32, the function selects the first inline record slot for the incoming record.

It reads the callback address. The callback is invoked exactly when:

- Its address is nonzero; and
- The saved signed count is greater than zero.

The callback receives four values:

1. The current-row field read for the call.
2. The saved signed record count.
3. The address of the first inline record.
4. The 32-bit callback context field.

The callback runs before the function resets the count, changes the row, or writes the incoming record. A callback that inspects ordinary unchanged state can therefore observe the old batch at that point.

A null callback does not prevent replacement. In that case, the old batch is overwritten without delivery by this function. A zero or negative saved count also suppresses the callback.

After any normally returning callback—or immediately when no callback is made—the function writes count zero and then writes the adjusted row as the current batch row. These writes occur even if the callback changed those fields.

If the callback does not return normally, none of those subsequent writes is established to occur.

### Writing the incoming record

On either append path, the selected record receives these writes in order:

1. The low 16 bits of the adjusted horizontal coordinate.
2. The 16-bit extent input.
3. The normalized magnitude byte.

The sixth byte of the record is left unchanged.

The function then rereads the count field and stores that value plus one. For a valid same-row append, this ordinarily advances the saved count by one. For a replacement batch, the preceding reset ordinarily makes the final count one.

The reread is observable: the final increment is not specified as using only the earlier count snapshot. Invalid overlapping addresses, concurrent mutation, or other interference cannot safely be modeled as an ordinary append.

## Side effects

Direct writes are limited to:

- The previous extent field on a successful merge; or
- A selected record’s coordinate, extent, and magnitude fields, followed by the count increment; and
- The count reset and current-row replacement when starting a replacement batch.

The function does not directly write the flags, coordinate offsets, callback address, callback context, or record padding byte.

The callback can have additional effects that are not bounded by this function’s supplied body. In particular, there is no evidence that it preserves state, globals, record contents, or memory ownership.

Record storage is inline in the state object. No allocation or deallocation operation is directly present. Passing that storage to the callback does not establish permission to retain it, free it, or invalidate the containing state. Safe completion requires that the state remain writable after the callback returns, because subsequent state and record writes are unconditional.

No explicit locking, atomic access, error return, or recovery path is present. Reentrant or concurrent access is not established as supported.

## Acceptance examples

These are conditional static expectations, not executed tests. They assume valid accessible state, no concurrent interference, and arithmetic signed-right-shift behavior. Unless noted, the callback returns normally without changing relevant memory.

1. **Zero magnitude still reads offsets.**  
   With magnitude input 511, normalization yields zero. The row and horizontal offsets are still read and applied, but no record is inspected or changed and no callback occurs.

2. **Negative values near zero are asymmetric.**  
   Magnitude input −1 yields magnitude 1, while input +1 yields zero. This follows from arithmetic right shifting before taking the absolute value.

3. **Saturation and folding differ.**  
   With magnitude input 262,144, the shifted value is 512. With flag bit `0x2` clear, the magnitude is 255. With that bit set, the magnitude is zero, so the function performs no record update.

4. **The folding peak is capped.**  
   With magnitude input 131,072, the shifted value is 256. Either normalization mode produces 255, not 256 or zero.

5. **A matching record is extended.**  
   Suppose the adjusted row matches the current row, and the last record contains horizontal coordinate 10, extent 5, and magnitude 7. A request with adjusted horizontal coordinate 15, magnitude 7, and extent 3 changes that extent to 8. The count remains unchanged.

6. **A full batch can still merge.**  
   With count 32 and the same matching conditions as above, the merge occurs without a callback. Capacity handling is reached only if merging fails.

7. **A full batch that cannot merge is replaced.**  
   With count 32, a nonmatching request reaches batch replacement even when its row is unchanged. A nonnull callback receives the previous row, count 32, inline record address, and context before reset. The incoming record becomes the first record and the final count is one.

8. **Row comparison is not narrowed.**  
   Two adjusted rows with different 32-bit values cause replacement even if their low 16 bits match.

9. **Coordinate storage is narrower than comparison.**  
   An adjusted horizontal coordinate of 65,536 is stored as zero in a newly appended record. A later adjacency check reads that stored coordinate as signed 16 bits, not as the original 65,536.

10. **Extent addition wraps.**  
    A last record at horizontal coordinate zero with unsigned extent 65,535 has endpoint 65,535. A matching request there with extent 1 merges and stores extent zero.

11. **Null callback does not preserve pending records.**  
    A positive-count batch whose row differs from the incoming row is reset and replaced even when the callback address is zero.

12. **Padding survives an append.**  
    The byte at record-relative offset 5 retains its prior value after that slot receives a new record.
