# F-5716506dd88c

## Purpose

F-5716506dd88c initializes an object obtained from F-bf74dfda5df0, installs a dispatch-table value, initializes several object fields, and establishes an associated handle.

An existing association is retained when it passes a two-part presence check. Otherwise, the function consults external lookup state and either:

- constructs a replacement association; or
- assigns an association from a global holder, then assigns a zero-derived temporary to that holder.

One lookup outcome invokes F-a817d8d58c10, which is marked non-returning in the supplied evidence. Every normal path ends with an indirect method call and returns the object pointer.

The apparent intent is constructor-like initialization with association acquisition or transfer. That interpretation does not establish allocation ownership, reference-counting rules, or the meanings of the lookup results.

## Behavior

### 1. Obtain and initialize the object

The function calls F-bf74dfda5df0 with the first and third arguments.

Using the returned pointer, it performs these operations in order:

1. Writes the supplied dispatch-table value into the object’s first four bytes.
2. Writes zero to each of the bytes at offsets 176, 177, and 178, in that order.
3. Reads the first four bytes addressed by the second argument and calls F-83300d26ff95 with the address of the association field and that word.
4. Writes signed 32-bit −1 to the field at offset 184.
5. Captures the current value of an external root global for possible later use.

The association field is initialized by a dependency rather than by a visible direct assignment. Its state after that call is therefore determined by F-83300d26ff95.

### 2. Decide whether acquisition is necessary

The function reads the association field.

- If it is zero, acquisition is necessary.
- If it is nonzero, the function reads a four-byte word at offset 4 from the referenced association.
- If that nested word is zero, acquisition is necessary.
- If both values are nonzero, the acquisition block is skipped.

The nested read is short-circuited: it does not occur when the association field is zero.

This is a presence check, not a demonstrated validity or ownership check. No other association content is inspected.

### 3. Perform the first lookup when acquisition is necessary

The acquisition block creates a temporary key-like value through F-9b9c1c7483f4. Its arguments are:

- the address of a four-byte temporary storage area;
- the four-byte word at offset 4 from the root obtained by a fresh read of the root global; and
- another four-byte temporary storage area.

This fresh global read is distinct from the root value captured before the association check.

After F-9b9c1c7483f4 returns, the function captures the current value of a separate lookup-context global. It calls F-8094c3d72052 with that captured context and the value returned by F-9b9c1c7483f4.

It then calls F-8a5aadac202f on the first temporary storage area. Only after this cleanup call does it branch on the saved lookup result.

Consequently:

- lookup observes the context captured after key construction;
- cleanup precedes either acquisition outcome;
- cleanup does not cause the saved result to be recomputed;
- the captured context remains the argument for the second lookup, if that lookup is reached.

The exact key representation and lookup semantics are unknown.

### 4. First lookup returns zero: construct an association

A zero result from F-8094c3d72052 selects this sequence:

1. Write the byte value 1 at object offset 178.
2. Call F-8157a180d901 with the numeric argument 72.
3. Pass its result to F-df2422ba76c2 together with two zero arguments.
4. Pass that result to F-7ec0b694cf72, along with the address of a four-byte temporary area and a final zero argument.
5. Pass the value returned by F-7ec0b694cf72 to F-4fbcfd10cfdf, with the object association-field address as destination.
6. Call F-561858688f94 on that temporary area.

The argument 72 is established; its interpretation as an allocation size is inferred, not guaranteed. There is no visible null check between the first two dependency calls.

The assignment to the association field is helper-mediated. The function does not directly establish whether this operation copies, shares, retains, replaces, or transfers a resource.

This branch has no later explicit store to the byte at offset 178. Dependencies and the final indirect method may nevertheless modify it; the function does not prove its final value is 1.

### 5. First lookup returns nonzero: validate a second lookup

A nonzero result from F-8094c3d72052 selects a second key construction and lookup.

The second call to F-9b9c1c7483f4 reads the word at offset 4 from the root captured before the association check. It does not freshly reload the root global for this access.

The function then calls F-1b0572bf841e with:

- the lookup context captured before the first lookup; and
- the second constructed value.

It calls F-8a5aadac202f on the second key temporary before examining the saved second lookup result.

Validation then proceeds as follows:

- If the second lookup result is zero, invoke F-a817d8d58c10 immediately.
- Otherwise, call F-e38e6836b640 with the address at byte offset 20 from the previously captured root.
- Compare the result of F-e38e6836b640 with the saved second lookup result.
- If they differ, invoke F-a817d8d58c10.
- If they are equal, continue.

The address at root plus 20 is passed directly; this function does not first load the word at that address. The evidence does not establish the arithmetic behavior for an invalid or overflowing root address.

The second result is tested for zero before F-e38e6836b640 is called. A zero result therefore suppresses that dependency call.

### 6. Validation succeeds: use and reset a global holder

After successful validation, the function:

1. Reads the current global-holder value and passes it to F-4fbcfd10cfdf as the source for assignment to the object association field.
2. Calls F-7ec0b694cf72 with a temporary-storage address and two zero values.
3. Reads the global-holder value again and passes it as the destination argument to F-4fbcfd10cfdf, using the newly returned temporary value as the source.
4. Calls F-561858688f94 on that temporary storage.
5. Writes zero to the byte at object offset 178.

The two reads of the global holder are separate. Calls between them may change that global; the function does not guarantee both operations address or reference the same holder value.

The visible behavior resembles moving an association out of shared storage and resetting that storage. This intent is not a proven ownership contract. In particular, the zero-derived temporary is not established to be an empty handle without the dependency contract.

### 7. Complete through indirect dispatch

Every normal path reaches a final indirect call.

At this point, the function reads the object’s current first word, obtains the method entry at table byte offset 180, and calls it with:

- the object pointer;
- the value 111; and
- the value 2.

The dispatch table is read at this late point. It is not guaranteed to remain the initially installed table if an intervening dependency changed the object.

After that call returns, the function returns the original object pointer. It performs no further visible field writes or cleanup.

## Side effects

Directly established side effects are:

- the object-field writes listed above;
- conditional acquisition and assignment calls;
- conditional access to global lookup state and the global association holder;
- cleanup calls for constructed temporaries;
- a possible non-returning failure call;
- the final indirect method call on every normal path.

There is no explicit direct free operation in this function. That does not imply the dependencies refrain from releasing memory, replacing references, modifying globals, or changing object fields.

The temporary areas passed to dependencies are four-byte local storage regions. Their addresses are supplied for the duration of the relevant calls. Whether a callee retains those addresses is not established; this function itself does not make the temporary storage durable.

No rollback is visible. If a dependency fails, terminates execution, or performs a nonlocal exit, earlier object writes and external effects have already occurred.

## Acceptance examples

These examples are conditional observations, not executed tests. Dependency behavior must be specified separately where an example relies on it.

### Existing association passes the presence check

Given that F-83300d26ff95 leaves a nonzero association whose word at offset 4 is nonzero:

- neither lookup is called;
- neither acquisition branch runs;
- no additional explicit write changes the initially zero byte at offset 178;
- the final indirect call receives the object, 111, and 2;
- if that call returns, the returned pointer equals the pointer supplied by F-bf74dfda5df0.

### Zero association enters acquisition without a nested read

Given a zero association field after initialization:

- the association-relative offset-4 read is skipped;
- the first key construction and lookup occur;
- the first key cleanup occurs before either acquisition branch begins.

### First lookup is zero

Given that the first lookup returns zero:

- the byte at offset 178 is written with 1 before the call with argument 72;
- the construction, temporary creation, object-assignment, and temporary-cleanup calls occur in the stated order;
- the second lookup and validation dependency are not called;
- normal completion still requires the final indirect call.

### First lookup is nonzero, second lookup is zero

Given these two results:

- both key cleanups occur;
- F-e38e6836b640 is not called;
- F-a817d8d58c10 is called;
- under its stated non-returning behavior, neither global-holder assignment nor final indirect dispatch occurs.

### Nonzero second lookup fails comparison

Given a nonzero second lookup result unequal to the result of F-e38e6836b640:

- the comparison dependency receives captured-root plus 20;
- F-a817d8d58c10 is called;
- no successful global-holder sequence follows.

### Validation succeeds

Given a nonzero second result equal to the comparison result:

- assignment from the global holder precedes construction of the zero-derived temporary;
- the holder is read again for the subsequent assignment destination;
- temporary cleanup precedes the explicit zero store at object offset 178;
- final dispatch follows that store.

### A dependency changes the root global

If the first key-construction dependency changes the root global, the second key construction still uses the root captured before the association check. It does not use that changed global value.

Similarly, changing the lookup-context global during the first lookup does not change the captured context passed to the second lookup.
