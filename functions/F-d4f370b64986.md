# F-d4f370b64986

## Purpose

F-d4f370b64986 counts a leading sequence of candidates whose running contribution satisfies a signed limit. It obtains candidates and evaluates their contributions through opaque dependencies. It returns the accepted count and, on the nonzero-context path, optionally writes the accepted cumulative contribution.

Acceptance is inclusive: a candidate is accepted when its contribution added to the previously accepted total is less than or equal to the limit. Processing stops at the first candidate that would exceed the limit or when the requested count is exhausted.

The limit constrains acceptance, not dependency side effects. A rejected candidate has already been acquired and evaluated. This function does not undo those calls.

**Inferred intent:** bounded prefix selection using an accumulated measure. The source does not establish that candidates are characters, that contributions measure width or size, or that negative contributions indicate errors.

## Behavior

### Initialization and setup

The function first initializes the four local input copies. It then invokes F-ead3143314e1 with argument 4 and the address of the context slot.

The setup dependency’s direct return value is not used. After setup returns, this function initializes the return count to zero and reads the context slot to choose its processing path.

If the context is zero:

- Neither candidate acquisition nor contribution evaluation occurs.
- This function performs no explicit store through argument 7.
- The return value is zero.

This is an absence-of-store guarantee for this function, not a guarantee that the caller’s output storage remains unchanged. Setup could affect that storage through another alias or shared state. Preservation requires an additional condition that no such write occurs.

If the context is nonzero, the accepted total and accepted count start at zero, and candidate processing becomes eligible.

### Candidate processing

The loop is entered only while the remaining signed requested count is greater than zero. An initial count of zero or any negative signed 32-bit value therefore causes no candidate calls, even when setup produced a nonzero context.

For each attempted candidate, the established order is:

1. Call F-2be305f439e7 with the address of the local word initialized from argument 2.
2. Pass its opaque 32-bit result to F-45a46fdfce32, together with argument 4, the current context-slot value, and argument 5 masked with 8.
3. Use the evaluator’s signed 32-bit result as the candidate contribution.
4. Form the prospective total from the accepted total plus that contribution.
5. Compare the limit against that prospective total using a signed comparison.
6. If the prospective total exceeds the limit, stop processing without accepting the candidate.
7. Otherwise, increment the accepted count, decrement the remaining requested count, and add the contribution to the accepted total, in that represented order.

No independent precheck compares the initial total of zero with the limit. Even when the limit is negative, a positive count and nonzero initial context cause the first candidate to be acquired and evaluated.

The context value supplied to an evaluation is read after candidate acquisition. The initial nonzero-context check does not establish that the slot remains unchanged throughout processing. There is no repeated branch that exits merely because a later context value becomes zero.

### Acceptance boundary and stopping

Equality is accepted. A prospective total equal to argument 6 contributes to both the accepted count and the accepted total.

On rejection:

- The rejected candidate contributes to neither returned count nor final accepted total.
- Its acquisition and evaluation have already occurred.
- No rewind, retry, compensation, or release is explicitly performed.
- No later candidate is attempted.

Provided dependencies do not disrupt the represented control flow, exhaustion of the count means every attempted candidate was accepted. Termination by the limit comparison means exactly one more candidate was attempted than accepted.

The function selects a prefix. It does not skip an excessive candidate to seek a later candidate with a smaller contribution.

### Flags

The evaluator’s final argument is a 32-bit mask result, either 0 or 8.

Bit 3 set in argument 5 produces 8, not the normalized Boolean value 1. All other flag bits are discarded for this explicit evaluator argument. No other direct use of argument 5 is visible.

### Signed arithmetic

The requested count, limit, contribution, accepted total, and accepted count are represented as signed 32-bit integers.

No nonnegativity or error-sentinel check is applied to a contribution. Within signed range:

- Zero contributions can be accepted without changing the total.
- Negative contributions can reduce the total.
- Negative prospective totals can satisfy negative limits.
- Accepted totals need not increase monotonically.

The comparison uses an addition, and acceptance performs another addition to update the stored total. Neither addition is shown with an overflow check.

The source does not establish wrapping, saturation, trapping, or a wider intermediate representation. Arithmetic outside −2,147,483,648 through 2,147,483,647 is therefore **documented_only**. This contract does not derive an acceptance decision from a mathematically unbounded sum when the represented signed addition overflows.

For an initially positive requested count, the visible count decrement and accepted-count increment stay within signed 32-bit range under normal loop progression.

### Output publication

After processing ends on the nonzero-context path, the function tests argument 7 for null.

- If non-null, it performs one explicit 32-bit store of the accepted total.
- If null, it performs no explicit output store.

It then returns the accepted count.

Thus, a nonzero-context invocation can explicitly publish zero even when no candidate was accepted. A zero-context invocation does not perform that store at all.

These statements count this function’s explicit output stores. They do not count or restrict writes performed by dependencies through aliases or shared state.

No normal output-publication or return guarantee applies if a dependency does not return normally.

## Side effects

The established direct effects are local-state initialization, dependency calls, local count and total updates, and the conditional output store.

Local addresses are exposed to dependencies:

- Setup receives the address of the context slot.
- Candidate acquisition receives the same local-state address on each attempt.

The function does not visibly restore that state between attempts. Mutations made by acquisition can therefore remain present for subsequent calls, subject to the dependency’s actual access contract.

There is no explicit allocation, deallocation, ownership transfer, context release, or cleanup call. Absence of such operations here does not establish that dependencies perform none, or that any context resource needs no release.

No global-state preservation guarantee is established. Dependencies may modify shared state or storage accessible through other aliases. Consequently:

- No explicit output store does not imply output-memory preservation.
- Null output suppresses only this function’s final output store; it does not suppress dependency calls.
- Rejected-candidate side effects are not rolled back.
- The initial context value is not guaranteed to remain stable.

The local storage exists for the duration of the invocation. Passing its address does not establish ownership transfer or permission to retain and later dereference it. Retention behavior and obligations are **documented_only**.
