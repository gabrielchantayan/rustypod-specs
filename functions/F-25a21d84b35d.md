# F-25a21d84b35d

## Purpose

F-25a21d84b35d performs a bounded, first-match lookup. It examines up to 34 fixed-stride records in increasing index order, comparing a 32-bit field from each record with a globally supplied 32-bit selector. On the first equality, it returns a one-byte field from that record. If all 34 comparisons fail, it returns a zero byte.

A zero result is ambiguous: it can mean either “no record matched” or “the first matching record contains a zero result byte.” The interface provides no separate success indicator.

This contract describes behavior established by the supplied static representation. Record meanings, ownership rules, concurrency guarantees, and the intended use of the result are not established.

## Behavior

### Search scope and precedence

The function begins with record index zero. For each visited record, it compares the four-byte field at offset 12 with the selector.

A successful comparison immediately ends the search. The function reads the one-byte field at offset 16 for that index and returns it. It does not examine later records to resolve duplicates, prefer a nonzero result, or select a “better” match.

After a failed comparison, the index advances by one. The search continues only while the next index is less than 34. Consequently:

- Record zero is always attempted.
- Record 33 is eligible to match.
- Record 34 is never examined.
- There is no sentinel-based early termination.
- Result bytes in nonmatching records are not read by the represented lookup.

If every comparison fails, the function returns zero without reading any record’s result field.

### Observable read ordering

The representation establishes the following logical ordering:

1. The comparison for a lower index precedes the comparison for a higher index.
2. A record’s successful comparison precedes the read of the returned result byte.
3. An unsuccessful comparison precedes advancement to the next record.
4. The no-match return occurs only after the comparison at index 33 fails.

It does **not** establish the relative evaluation order of the table-derived comparison-field read and the selector read within a single equality expression. A contract requiring one of those reads to happen first would exceed the evidence.

The selector is referenced in the repeated comparison expression rather than explicitly copied into a stable local snapshot. The table-base binding is likewise referenced in the access expressions, including the result-byte access after a match. The supplied representation does not justify assuming that either binding is immutable throughout execution.

Accordingly, the ordinary description “return a byte from the matching record” has a stability condition: the relevant table base and data must remain consistent between comparison and result access. If they change, the representation provides no atomic lookup guarantee. Exact machine-level reload behavior, compiler transformations, and memory-model guarantees are documented_only unknowns.

### Widths and address calculations

The index is represented as a 32-bit unsigned integer. It starts at zero and advances only after failed comparisons. Its largest value during a record access is 33; it may become 34 solely to terminate the search. No index wraparound is reachable within this control flow.

The largest stride product used is 33 × 20 = 660 bytes. Relative to an unchanged table base:

- The last comparison occupies byte offsets 672 through 675.
- The last possible result-byte read is at offset 676.
- A nominal array of 34 complete, 20-byte records spans 680 bytes.

The function itself does not read every byte in that nominal extent. Earlier success makes all later records irrelevant to that execution. On a complete miss, the result bytes are not needed.

These small offsets do not establish that adding them to an arbitrary table base is safe. The pointer/address width, address-space bounds, alignment, and fault behavior are not specified by the supplied material. Byte order is also not established; comparison fields and the selector are interpreted through the target’s integer-read semantics, not through a specified serialized byte order.

## Acceptance examples

These examples are conditional on valid accesses, stable inputs, and a consistent interpretation of the 32-bit comparison values.

1. **First record matches.**  
   Record zero’s comparison value equals the selector, and its result byte is `0x7B`. The result is `0x7B`. No later record’s comparison or result is needed.

2. **Duplicate keys.**  
   Records 4 and 9 match, while records 0 through 3 do not. Their result bytes are `0x12` and `0xE4`, respectively. The result is `0x12`; record 9 does not affect the outcome.

3. **Zero-valued first match.**  
   Record 2 is the first match and contains result byte `0x00`. A later matching record contains `0x55`. The result is zero. The search does not continue merely because the first result is zero.

4. **Last eligible record matches.**  
   Records 0 through 32 do not match, and record 33 matches with result byte `0xFF`. The result is the byte `0xFF`, without an established signed interpretation.

5. **No eligible match.**  
   All 34 comparison fields differ from the selector. The result is zero, and no result-byte read is required.

6. **Match outside the search range.**  
   Records 0 through 33 do not match, but a physically present record 34 does. The result remains zero. Additional storage does not extend the search.

7. **Early success before inaccessible later storage.**  
   Record zero’s required fields are accessible and match. Later record storage is inaccessible. The represented path returns record zero’s result without accessing those later records.

8. **Inaccessible required comparison.**  
   No earlier record matches, and the next required comparison field is inaccessible. A successful zero return is not an acceptance requirement; this violates the valid-access precondition.

9. **Inputs change during the lookup.**  
   The selector or table base changes between accesses. No single-snapshot result is promised. A deterministic expected byte requires an additional, externally supplied stability or synchronization rule.
