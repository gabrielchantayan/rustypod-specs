# F-60e7318a3858

## Purpose

F-60e7318a3858 computes and stores two bounds derived from a primary object's extent and, when present, a related object's position and count. A nonzero control argument additionally permits one of two dependency calls before the bounds are stored.

The apparent intent is to maintain a position-centered range, with a one-time initialization path and a subsequent range-update path. That interpretation is inferred, not established: the supplied material does not identify the objects, the units of the extent, or the dependencies’ actual effects.

The established behavior is narrower and more precise:

- The lower bound starts at zero.
- The upper bound starts at zero.
- When a related object exists, its position and count determine the bounds.
- A byte in the primary object selects between initialization and range-update calls.
- The final bounds are written whether or not dependency calls are enabled.

This is a static behavioral contract. No runtime tests have been performed.

## Behavior

### Reads and local computation

The function first reads the related-object address from primary offset `0x30`. It then reads the unsigned extent at primary offset `0x34` and obtains its half by a logical right shift of one bit.

For a 32-bit unsigned extent, this half is the extent divided by two, rounded down. Its range is 0 through 2,147,483,647, so its later signed comparison does not introduce a negative value.

The initial lower and upper bounds are both zero.

If the saved related-object address is zero, the function performs no related-object reads and no dependency dispatch. It proceeds to the final writes. The extent read still occurs in this case.

If the related address is nonzero, the function reads, in order:

1. The signed position at related offset `0x2b4`.
2. The signed count at related offset `0x2b8`.

These values and the extent half are captured before any dependency call.

### Lower-bound rule

If the signed position is greater than the extent half, the lower bound is their difference. Otherwise, the lower bound remains zero.

Consequences include:

- A negative position always leaves the lower bound at zero.
- A position equal to the extent half leaves the lower bound at zero.
- With a zero extent half, a positive position becomes the lower bound.

Although the subtraction combines signed and unsigned operands in the supplied representation, its guarded mathematical result is nonnegative and fits in a signed 32-bit integer. No overflow is needed to describe the lower-bound result.

### Upper-bound rule

The initial upper-bound candidate is the position plus the extent half.

The addition combines a signed position with an unsigned half. Under the apparent 32-bit model, the addition is unsigned and wraps modulo 2³² before assignment to the signed upper-bound value. On the conventional two’s-complement interpretation, a result with its high bit set is subsequently negative.

The count is then compared with this signed upper-bound candidate:

- If the count is greater than the candidate, the candidate is retained.
- If the count is less than or equal to the candidate and the count is zero, the upper bound becomes zero.
- If the count is less than or equal to the candidate and the count is nonzero, the upper bound becomes the count minus one.

This is not a general validity check or a guarantee of a nonnegative, ordered range. In particular:

- A negative upper-bound candidate can be retained.
- A zero count does not necessarily force a zero upper bound: a negative candidate is retained because zero is greater than that candidate.
- A negative count can produce a negative upper bound.
- The lower bound is not adjusted after the upper bound is limited.
- The stored lower bound may exceed the stored upper bound.

Subtracting one from the minimum signed 32-bit count presents a separate signed-overflow issue. The excerpt does not establish a portable result for that case; see **Uncertainties**.

### Optional dependency dispatch

Dispatch occurs only when both conditions hold:

- The saved related-object address is nonzero.
- The control argument is nonzero.

When either condition is false, the function does not read the state byte and does not call either dependency.

When dispatch is enabled, the function reads primary offset `0x59`:

- If the byte is zero, it calls **F-347ac300c18c** with the primary-object address. After that call returns, it writes exactly 1 to primary offset `0x59`.
- If the byte is nonzero, it calls **F-3e07bce3ca68** with the primary-object address, computed lower bound, and computed upper bound, in that order. This branch does not itself write the state byte.

Every nonzero byte value selects the second branch; the byte need not equal 1.

The zero-byte branch does not also invoke the range-update dependency. Any bounds supplied to or used after dispatch are the values computed before the call. Changes made by a dependency to the extent, related address, position, or count do not trigger recomputation during this invocation.

### Final writes

After any selected dependency returns, the function writes:

1. The computed lower bound to primary offset `0x38`.
2. The computed upper bound to primary offset `0x3c`.

If there is no related object, these writes store zero and zero.

The final writes occur after the optional state-byte write. They are not suppressed by a zero control argument, an already-nonzero state byte, or a zero count.

## Side effects

The function’s direct writes are limited to the two bound fields and, on the initialization branch, the state byte.

The relative ordering is significant:

- The related address and extent are read before the related-object fields.
- Both related-object fields are read before dispatch.
- The selected dependency runs before either final bound write.
- On the initialization branch, the state byte is set to 1 after the dependency returns and before the bounds are stored.
- The lower-bound store precedes the upper-bound store.

Thus, the dependencies are not guaranteed to observe freshly stored bounds. F-3e07bce3ca68 receives the new bounds as arguments, but this function has not yet published them through the bound fields.

A dependency may change memory, globals, or resource ownership. None of those effects may be assumed absent. In particular:

- If a dependency changes either bound field, the subsequent direct stores replace those changes, provided the destination remains valid.
- If F-347ac300c18c changes the state byte, the subsequent direct store replaces that byte with 1.
- If a dependency replaces the related address, the function does not reread it.
- If a dependency releases or invalidates the primary object, subsequent accesses have no established safe behavior.

No allocation, deallocation, ownership transfer, lock operation, or error report is directly visible. That observation does not establish that the dependencies perform none of those actions.

There is no visible recovery mechanism for invalid memory, dependency failure, abnormal return, or arithmetic outside the defined representation model. If a dependency does not return normally, the writes following it are not guaranteed to occur.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Unless stated otherwise, they assume valid memory, normally returning dependencies, and conventional 32-bit two’s-complement interpretation.

1. **Absent related object**  
   With a zero related address, any extent, any control value, and any state byte, the extent is still read. Neither dependency is called, the state byte is not read, and the final bounds are zero and zero.

2. **Ordinary centered range**  
   With extent 10, position 20, count 100, and control zero, the half is 5. The final bounds are 15 and 25. No state-byte access occurs.

3. **Odd extent**  
   With extent 11, position 20, count 100, and control zero, the final bounds are also 15 and 25. The half rounds down rather than up.

4. **Lower clamp and upper limit**  
   With extent 10, position 3, count 8, and control zero, the initial bounds are 0 and 8. Equality between count and upper candidate triggers the limit, so the final bounds are 0 and 7.

5. **Initialization branch**  
   With extent 10, position 20, count 100, nonzero control, and a zero state byte, F-347ac300c18c receives the primary address. On normal return, the state byte becomes 1, then the bounds become 15 and 25. F-3e07bce3ca68 is not called.

6. **Update branch accepts any nonzero state byte**  
   With the same numeric inputs and state byte 255, F-3e07bce3ca68 receives the primary address, 15, and 25. This function does not normalize the byte to 1.

7. **Bounds need not be ordered**  
   With extent zero, position 5, count zero, and control zero, the final lower bound is 5 and the final upper bound is zero.

8. **Zero count with a negative candidate**  
   With extent zero, position −3, count zero, and control zero, the final bounds are 0 and −3. The zero count is greater than the candidate, so no upper replacement occurs.

9. **Negative count**  
   With extent zero, position zero, count −2, and control zero, the final bounds are 0 and −3. No rejection or normalization of the negative count occurs.

10. **High-bit upper result**  
    With extent 2, position 2,147,483,647, count 100, and control zero, the lower bound is 2,147,483,646. Under conventional two’s-complement conversion, the upper candidate becomes −2,147,483,648 and is retained because 100 is greater than it.

11. **Dependency mutation does not recompute bounds**  
    If a normally returning dependency changes the related position after bounds 15 and 25 have been computed, the final stores still publish 15 and 25, provided the primary object remains valid.
