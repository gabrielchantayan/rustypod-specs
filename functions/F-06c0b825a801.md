# F-06c0b825a801

## Purpose

F-06c0b825a801 conditionally replaces a pair of stored 32-bit values and writes a one-byte change indication.

The operation first compares the stored second value with the fourth argument. Only if that comparison succeeds does it compare the stored first value with the third argument. If both comparisons succeed, it returns without writing anything. Otherwise, it writes both supplied values, then writes the byte value 1 to a separate location.

This comparison-and-update behavior is established by the supplied static representation. Describing the pair as cached state, or the byte as a dirty or notification flag, is inferred intent rather than an established application-level meaning.

## Behavior

### Comparison and early return

The first observation is a read of the state address from the first argument at offset `0xF00`. Through that address, the function reads the 32-bit value at offset `0xB48` and compares it with the fourth argument.

If those values differ, the function proceeds directly to the update path. It does not read the first stored value for comparison on that path.

If those values match, the function reads the state address from the first argument again. Through this newly obtained address, it reads the 32-bit value at offset `0xB44` and compares it with the third argument.

If this second comparison also matches, the function returns immediately:

- Neither stored value is written.
- The change-indication byte is neither read nor written.
- An existing indication byte of 0, 1, or any other byte value is left unchanged.
- No update-path read of the state address occurs.

The two comparisons therefore need not use the same state address if the address-bearing location changes between reads. The supplied body does not establish a snapshot, lock, or other consistency mechanism.

### Update path

Either failed comparison selects the same update path.

The function first reads the state address from the first argument again and retains that address for the two full-width stores. It then performs these writes in this order:

1. Stores the third argument as a 32-bit value at offset `0xB44`.
2. Stores the fourth argument as a 32-bit value at offset `0xB48`.

Both writes occur whenever the update path is reached, even if one of the stored values already equals its requested replacement. This is not a per-field conditional update.

After those writes, the function reads the state address from the first argument once more. Through this newly obtained address, it stores the 8-bit value 1 at offset `0xB90`.

The final store is an unconditional byte replacement on the update path. It does not inspect the previous byte, preserve selected bits, increment a counter, or merge a bit mask.

The function then returns without a result value.

### Address reuse and repeated reads

At the level of the supplied static representation, the access paths have the following distinction:

| Path | State-address reads | Pair stores | Indication-byte stores |
|---|---:|---:|---:|
| Both comparisons match | 2 | 0 | 0 |
| Second stored value differs immediately | 3 | 2 | 1 |
| Second stored value matches, first differs | 4 | 2 | 1 |

The two pair stores share one retained state address. The comparison reads and final indication store do not necessarily share that retained address.

For stable, non-overlapping objects, these distinctions do not change the simple result: a mismatching pair is replaced and its indication byte becomes 1. They matter when address-bearing storage can change or when unusual aliasing exists. The body does not justify treating every access as if it were made through one address captured at entry.

The ordering above describes the supplied representation. It is not an additional guarantee about hardware memory ordering, atomic visibility, or compiler treatment of concurrent accesses.

## Side effects

The only explicit modifications are the two 32-bit stores and the final 8-bit store on the update path. The successful equality path performs reads only.

No allocation, deallocation, ownership transfer, callback, logging operation, or external function invocation is visible. The function uses the supplied address to access storage; it does not establish who owns that storage or how long it remains valid.

No write explicitly targets the address-bearing location at first argument + `0xF00`. However, the evidence supplies no non-aliasing guarantee. If a derived write location overlaps that location, a store could change the address used by a later read. In particular, the final byte store uses a fresh address read after both pair stores.

There is no explicit transactional behavior:

- The first pair store precedes the second.
- The indication-byte store follows both pair stores.
- There is no rollback path.
- There is no explicit barrier or synchronization operation.
- No guarantee establishes that another observer sees the pair and indication change atomically.

The function provides no error result or explicit recovery path. The evidence does not define the outcome of an inaccessible address, an unsupported alignment, or an interrupted execution.

## Acceptance examples

These are conditional examples derived from static evidence. No runtime tests have been performed.

### Matching pair preserves an unset indication

Assume the state address remains stable, the accessed objects do not overlap, and all accesses are valid. The stored first and second values are 10 and 20; the third and fourth arguments are also 10 and 20. The indication byte initially contains 0.

Expected behavior: the second-value comparison succeeds, then the first-value comparison succeeds. The function returns without any store. The indication byte remains 0.

An interpretation that every call sets the indication would fail this example.

### Matching pair preserves an arbitrary indication

Under the same memory assumptions, both requested values match the stored pair, and the indication byte initially contains `0xA5`.

Expected behavior: no writes occur, and the indication remains `0xA5`. The function neither validates nor normalizes it on the equality path.

### Second value differs

Assume stable, valid, non-overlapping storage. The stored pair is 10 and 20; the requested pair is 10 and 21.

Expected behavior: the comparison against the stored second value fails. The stored first value is not read for comparison. Both requested values are nevertheless written, first 10 and then 21, followed by a byte store of 1 to the indication location.

The first store remains part of the behavior even though its value is unchanged.

### Only the first value differs

Under the same assumptions, the stored pair is 10 and 20; the requested pair is 11 and 20.

Expected behavior: the second-value comparison succeeds and the first-value comparison fails. The function writes 11 to the first location, writes 20 to the second location, and finally writes the indication byte as 1.

### Existing indication bits are replaced

Assume a mismatch selects the update path and the indication initially contains `0xA5`.

Expected behavior: after successful completion, the indication byte is exactly `0x01`, not `0xA5` with an additional bit set.

### The state address changes before indication

Suppose the comparison and pair-update address reads select one valid state object, but the final address read selects a different valid object.

Conditional behavior: the two pair stores target the retained update address; the indication store targets the final address. The supplied body contains no step that redirects the completed pair stores to the newly selected object.

This example documents address-resolution behavior, not a guarantee that concurrent address changes are safe.
