# F-774487f31a0a

## Purpose

F-774487f31a0a conditionally invokes two fixed dependencies and dispatches an event-like record through an object-associated function table. It returns the first nonzero result from a result-bearing invocation, or zero if every result-bearing invocation actually performed returns zero.

The observable ordering is significant:

1. A particular record subtype triggers a preliminary notification.
2. A particular record kind and embedded-address match can trigger an early handler.
3. Unless that handler returns nonzero, exactly one of two primary dispatch slots is invoked.
4. If primary dispatch returns zero, a fresh record-kind and address check can trigger a final handler.

“Event,” “object,” “notification,” and “handler” describe inferred roles. The supplied static representation establishes the comparisons, address calculations, call order, and return behavior, not the application-level meanings of the numeric values.

## Interface

### Inputs

The function accepts two pointer-valued arguments:

- **Object argument:** a pointer to storage containing a dispatch-table address, an embedded region, a stored comparison address, and a scalar field used by the preliminary notification.
- **Record argument:** a pointer to storage containing a kind field and an associated address.

Both arguments are forwarded unchanged to result-bearing dependencies. The preliminary notification instead receives the object argument and a character-width conversion of one object field.

Neither argument is declared read-only in the supplied representation. Dependencies may therefore change the object, record, referenced storage, or other state. This function provides no isolation from those changes.

### Layout and widths

The supplied representation uses integer-indexed storage and integer-held addresses. Under its apparent 32-bit layout, the relevant fields are:

| Storage | Byte offset | Role |
|---|---:|---|
| Object | `+0x00` | Address of a function-pointer dispatch table |
| Object | `+0x50` | Stored address used in the final eligibility comparison |
| Object | `+0xb0` | Address of the embedded region used in the early eligibility comparison |
| Object | `+0x110` | Integer converted to a character-width preliminary-notification argument |
| Record | `+0x04` | Kind discriminator |
| Record | `+0x08` | Address interpreted according to the current kind |
| Referenced storage | `+0x04` | Subtype discriminator when the current record kind is `0x16` |

The embedded-region comparison uses the address **object base plus `0xb0`**. It does not load a pointer from that location.

The final comparison instead loads the address stored **at object base plus `0x50`**.

The relevant dispatch-table entries are at byte offsets `+0x10c`, `+0x110`, and `+0xe0`. These offsets are relative to the table address loaded from the object’s first field. They are not object-field offsets.

The 32-bit interpretation follows the apparent reconstructed layout; a complete target ABI is not supplied. In particular, the source does not independently establish pointer width, byte order, alignment requirements, or plain-character signedness. Those limitations must not be replaced with an assumed portable layout.

### Output

The return value is represented as a signed integer:

- A nonzero early-handler result is returned unchanged.
- Otherwise, a nonzero primary-dispatch result is returned unchanged.
- Otherwise, a nonzero final-handler result is returned unchanged.
- If no result-bearing invocation returns nonzero, the result is zero.

Negative values are nonzero and therefore stop processing just as positive values do. No conversion to a Boolean result is shown.

### Preconditions

Execution requires every address actually read or invoked along the chosen path to be valid for that operation. This includes the object, record, conditionally referenced subtype storage, selected dispatch-table entry, and selected function target.

There are no explicit null checks, bounds checks, dispatch-target checks, or lifetime checks. Invalid storage or an incompatible function target has no defined recovery behavior in the supplied evidence.

## Behavior

### 1. Preliminary notification

The function first reads the record kind.

If that kind is `0x16`, it obtains the address from the record’s associated-address field, reads the integer at that address plus four bytes, and subtracts `0x2500` from the value.

A subsequent kind check gates use of that subtraction result. If the kind is still `0x16` and the subtraction result is `2`, F-fc6825c04c54 is invoked with:

- The original object argument.
- The object integer at offset `+0x110`, converted to plain character type.

For defined ordinary integer arithmetic, the triggering subtype is `0x2502`. This is an equality trigger, not a range test.

The conversion narrows the integer to the target’s plain-character representation. On an eight-bit-character target, values representable as positive eight-bit characters are unambiguous. Values outside the plain-character range require the target’s conversion rules; character signedness is not established.

The preliminary dependency’s result, if any, is not used. The function does not stop because this call occurred. It proceeds to the early-handler eligibility check.

There is no shown dependency invocation between the two initial kind checks. The repeated checks are nevertheless present in the supplied representation. Exact machine-load count and behavior under concurrent mutation are not established.

### 2. Early-handler eligibility

After the preliminary stage, the function reads the record kind again.

Only kind `0x0f` is eligible. For that kind, the record’s associated address is compared with the address of the embedded region at object base plus `0xb0`.

If both conditions match, F-3718c422eac3 is invoked with the original object and record arguments.

- A nonzero result is returned immediately.
- A zero result permits primary dispatch.
- If either eligibility condition fails, this dependency is not invoked.

The address comparison does not inspect the contents of the embedded region. Equal contents at a different address do not qualify.

Because the preliminary dependency can run first, this stage observes the record state available after that dependency returns. The initial kind and subtype are not a retained classification for later stages.

### 3. Primary dispatch

Unless the early handler has already returned nonzero, the function reads the record kind afresh to choose one primary dispatch slot.

If the kind is `0x16`, the function reads the current associated address and then reads the subtype at that address plus four bytes.

The selected table entry is:

- **Slot `+0x10c`** when the current kind is `0x16` and the current subtype is `0x2a`.
- **Slot `+0x110`** in every other case.

For a kind other than `0x16`, subtype storage is not read for this selection.

The dispatch-table address is obtained from the object’s first field, and the selected function target is loaded from that table. The target is then invoked with the original object and record arguments.

Exactly one primary target is invoked on every normally progressing path that reaches this stage.

- A nonzero result is returned immediately.
- A zero result permits the final eligibility check.

The table is selected after any preliminary and early-handler calls. No preservation of the object’s table address or table contents across those calls may be assumed.

### 4. Final-handler eligibility

After primary dispatch returns zero, the function reads the record kind again.

Only kind `0x0f` is eligible. For that kind, the record’s current associated address is compared with the address currently stored in the object field at offset `+0x50`.

If both conditions match, the function obtains the current dispatch-table address from the object’s first field and invokes the target at table slot `+0xe0`, passing the original object and record arguments.

- A nonzero result is returned immediately.
- A zero result leads to a zero function result.
- If eligibility fails, the function returns zero without invoking this slot.

This is a post-primary check. A primary dependency that changes the record kind, associated address, object comparison field, or dispatch table can affect whether and where this final call occurs.

The early and final address conditions are independent. Both handlers may run during one invocation if the relevant conditions hold when each check is reached and intervening result-bearing calls return zero.

## Side effects

The function contains no explicit assignment to caller-provided storage, allocation, deallocation, or ownership transfer.

That does **not** establish that the invocation is side-effect-free:

- F-fc6825c04c54 can run before all result-bearing dispatch.
- F-3718c422eac3 can run before primary dispatch.
- The selected primary target can run before the final eligibility check.
- The final target can run last.

The effects of these dependencies are unknown. They must not be assumed to preserve global state, preserve input contents, retain or release memory, or leave dispatch-table entries unchanged.

The function retains no ownership state visible in the supplied representation. Passing a pointer to a dependency is not evidence that ownership transfers to that dependency.

Normal call order is established; completion is not guaranteed. If a dependency does not return, subsequent stages are not reached. If it invalidates storage needed afterward, the function shows no protective mechanism.

## Acceptance examples

These are conditional acceptance cases derived from static evidence, not executed tests. Assume valid storage, compatible callable targets, ordinary defined arithmetic, and no dependency mutation except where explicitly stated.

1. **Default primary path.**  
   With kind different from both `0x0f` and `0x16`, no preliminary or early dependency is invoked. Primary slot `+0x110` is invoked. If it returns zero and the kind remains unchanged, the function returns zero without invoking the final slot.

2. **Special primary subtype.**  
   With kind `0x16` and subtype `0x2a`, the preliminary notification does not run. Primary slot `+0x10c` runs. If it returns `-7`, the function returns `-7`, with no final eligibility processing.

3. **Notification subtype.**  
   With kind `0x16`, subtype `0x2502`, and object scalar `65`, F-fc6825c04c54 receives the object and the character value corresponding to `65`. If it leaves the relevant state unchanged, primary dispatch subsequently uses slot `+0x110`, not slot `+0x10c`.

4. **Early termination.**  
   With kind `0x0f` and associated address equal to object base plus `0xb0`, F-3718c422eac3 runs. If it returns `9`, the function returns `9`; neither primary nor final dispatch occurs.

5. **Early handler declines.**  
   Under the same early eligibility conditions, a zero result from F-3718c422eac3 permits primary dispatch. Without mutation, the primary slot is `+0x110`.

6. **Final dispatch.**  
   If primary dispatch returns zero and the post-primary record has kind `0x0f` with associated address equal to the object’s stored address at `+0x50`, slot `+0xe0` runs. Its result `-3` becomes the function result.

7. **Primary mutation changes final eligibility.**  
   A record initially having a different kind can become final-handler eligible if primary dispatch changes it to kind `0x0f` and supplies the required associated address before returning zero.

8. **Primary nonzero suppresses the final stage.**  
   Even if primary dispatch leaves the record in a state satisfying the final address condition, its nonzero return is returned immediately. The final target is not invoked.

9. **Address identity, not contents.**  
   A kind-`0x0f` record pointing to separate storage containing bytes identical to the embedded object region does not qualify for the early handler solely because those bytes match.

## Uncertainties

The following are **documented_only**, not supplied behavior:

- Application meanings of kinds `0x0f` and `0x16`, subtypes `0x2a` and `0x2502`, and nonzero results.
- Full object, record, and referenced-storage layouts.
- Exact target ABI, pointer width, byte order, alignment rules, and character signedness.

- Identities and semantics of indirect targets.

- Recovery behavior for invalid addresses, invalid targets, or dependency failures.

The subtraction deserves a separate boundary qualification. Under signed 32-bit arithmetic, subtracting `0x2500` from sufficiently negative values overflows. The supplied representation does not establish whether the actual execution model wraps, traps, or has another consequence. The ordinary-value trigger `0x2502` is established; portable behavior for every possible subtype bit pattern is not.
