# F-749f6975a7ca

## Purpose

F-749f6975a7ca performs an ordered transformation of externally supplied memory, including linked-address traversal, mixed-width field updates, computed-address stores, and a final unresolved indirect invocation.

The established behavior is the access sequence, not a recognized object model or service. Constants such as `0x73`, `0x74`, and `0x66` are stored values with unknown application meaning.

Execution depends on four explicit inputs, two implicit addresses, three global storage locations, and addresses obtained through memory. No validation, rollback, or explicit error reporting is shown.

This contract describes static evidence only. No runtime tests have been performed.

## Behavior

### Initial publication and traversal

Context `0x74` is read, then replaced with the incoming-object address. The initial payload is written at offset `0x30` of the previously selected object. Publication therefore precedes the payload write without changing its captured destination.

Incoming-object `0x14` selects an object whose `0x09` byte receives the initial byte. Context `0x54` then receives the context address. Next, the four-byte value anchor minus `0x74` is written at anchor minus `0x20`.

Only after that write is the selected object’s `0x14` field read to select a further destination. Incoming-object byte `0x11` receives the incoming byte. A fresh four-byte incoming-object `0x14` read supplies the low byte written at that further destination’s `0x15`.

### Early links and state capture

A fresh incoming-object `0x14` read selects the **early object**. Context `0x64` is read and written back as four bytes. Call this captured value the **first state**.

The following writes occur in order:

1. Byte `0x73` at early-object `0x0C`.
2. The first state’s low byte at context `0x15`.
3. The four-byte incoming-field value captured immediately before the preceding destination-byte write at incoming-object `0x34`.

Early-object `0x74` is captured as the **earlier link**. The early object receives its own address at `0x54`. Incoming-object byte `0x0D` receives the context address’s low byte. Incoming-object `0x54` receives the same captured incoming-field value, and incoming-object `0x14` receives the early-object address.

Context `0x64` is read again, producing the separately saved **second state**. The next writes are:

1. One-byte `0x74` at early-object `0x10`.
2. Four-byte `0x74` at context `0x54`.
3. Four-byte `0x74` at early-object `0x10`.

Early-object `0x74` is then reloaded as the **later link**. It need not equal the earlier link. Incoming-object `0x54` receives the incoming-object address, and early-object `0x30` receives four-byte `0x74`.

### Context replacement and relinking

Context byte `0x01` receives the first state’s low byte. At the address represented by the first state, byte `0x09` receives the second state’s low byte. Context `0x74` receives the full second state.

Context byte `0x11` receives `0x74`. Early-object `0x60` is then read. Context byte `0x11` is replaced by the first state’s low byte, context `0x34` receives the second state, and early-object byte `0x10` receives the captured `0x60` value’s low byte.

Context `0x14` selects a **context-linked object**. Incoming-object byte `0x11` receives the earlier link’s low byte. Context `0x44` receives the incoming-object address, and context byte `0x11` receives the second state’s low byte.

Context `0x74` is read and saved. Context byte `0x0D` then receives the incoming-object address’s low byte. The next writes have this exact order:

1. Four-byte `0x66` at context-linked-object `0x10`.
2. The incoming-object address at context `0x44`.
3. One-byte `0x66` at context-linked-object `0x10`.
4. Four-byte `0x66` at context `0x54`.
5. Four-byte `0x66` at context-linked-object `0x60`.

A fresh context `0x74` read selects the **replacement object**. Context `0x74` is then assigned the incoming-object address. Replacement-object `0x40` receives four-byte `0x66`. Context byte `0x0D` receives the low byte of the preceding, separately saved context `0x74` value.

Replacement-object `0x44` is captured. Context `0x54` receives the context address. The object designated by the later link receives its own address at `0x54`.

Replacement-object `0x14` is now read, selecting a **fixed byte destination**. Only afterward does incoming-object byte `0x11` receive the captured replacement-object `0x44` value’s low byte. A fresh incoming-object `0x14` read supplies the low byte written at fixed-byte-destination `0x15`.

The destination remains the address captured before the incoming-object byte replacement, even if that replacement changes the stored representation of replacement-object `0x14`.

### Propagation and publication

Incoming-object `0x14` is reloaded to select a **propagation object**. Context `0x64` is read as the **first propagation snapshot**. Propagation-object `0x20` receives four-byte `0x73`. Context `0x64` is read again as the **second propagation snapshot**, whose low byte is written at propagation-object `0x09`.

Propagation-object `0x74` selects a **successor**. Successor byte `0x0D` receives the context address’s low byte. Successor `0x54` is read and written back as four bytes, then successor byte `0x09` receives `0x74`.

Context `0x44` receives the first propagation snapshot. Successor `0x34` receives the context address. Successor `0x04` selects a **carrier**, whose `0x24` receives the second propagation snapshot. Context byte `0x19` receives the first propagation snapshot’s low byte.

Carrier `0x74` and `0x04` are read in that order, producing the **retained link** and **retained state**, respectively.

A fresh context `0x74` read selects a **publication base**. Publication-base `0x14` selects an object whose `0x54` receives the retained link. Publication-base `0x04` then selects another object.

Context byte `0x0D` receives the second propagation snapshot’s low byte twice consecutively. Context `0x64` receives the retained state. The object just selected through publication-base `0x04` receives four-byte `0x74` at `0x30`.

Publication-base `0x04` is read again. That newly selected object’s `0x74` selects the **principal object**. Reusing the previous `0x04` selection would not preserve behavior under arbitrary aliasing.

### Late context and object updates

A fresh four-byte context `0x64` read supplies a saved low byte, which is written at context `0x1D`.

A traversal through context `0x44`, then the selected object’s `0x14`, supplies a **new context link**. Principal-object `0x34` receives the retained link before context `0x14` receives the new context link.

Context `0x54` is captured. The new-context-link object’s `0x09` byte receives the context address’s low byte.

A traversal through principal-object `0x04`, then the selected object’s `0x74`, selects a **late successor**. Its byte `0x15` receives the retained link’s low byte. Context `0x54` receives the context address. Context byte `0x11` receives the principal-object address’s low byte. Late-successor byte `0x11` receives the previously captured context `0x54` value’s low byte.

Late-successor `0x64` is read as the **late state**. Context byte `0x09` receives the low byte saved from the earlier context `0x64` read.

A fresh principal-object `0x04` read selects the **terminal object**. Its byte `0x09` receives the context address’s low byte. Its `0x50` field is captured, its byte `0x11` receives the late state’s low byte, and its byte `0x09` again receives the context address’s low byte.

Context `0x14` receives the full late state. Context byte `0x0D` receives the terminal-object address’s low byte. Terminal-object byte zero receives the captured terminal `0x50` value’s low byte.

### Computed-address writes and transfer

The first address global is read. A fresh context `0x74` read then supplies the **tail context value**.

The tail context value’s low sixteen bits are written as two bytes at context address plus tail context value. The first address value’s low sixteen bits are then written at twice the child address.

Next, one byte is read at context address plus tail read offset. Its plain-character value is converted to a 32-bit unsigned value, the **tail operand**:

- Under signed plain-character interpretation, byte patterns `0x80`–`0xFF` represent negative values, which convert to unsigned values `0xFFFFFF80`–`0xFFFFFFFF`.
- Under unsigned plain-character interpretation, those patterns convert to `0x00000080`–`0x000000FF`.
- Patterns `0x00`–`0x7F` produce the same operand under either interpretation.

The supplied evidence does not select between these target-dependent interpretations.

The tail context value’s low sixteen bits are written at first address value plus tail context value. The two-byte store at context address plus tail context value is then repeated using the same captured value.

Four-byte `0x45` is written at tail operand plus `0x45`, with unsigned 32-bit wraparound.

Only afterward are the second address global, global payload, and context `0x44` read, in that order. Using their captured values, the function writes:

1. One-byte `0x44` at tail operand plus `0x44`, with unsigned 32-bit wraparound.
2. The four-byte global payload at twice the second address value.
3. The second address value’s low sixteen bits at retained link plus second address value.

Finally, D-01 is invoked with:

2. The captured second address value.

## Acceptance examples

These are conditional static obligations, not executed tests.

1. **Captured initial destination.** With distinct accessible objects and no relevant aliasing, the initial payload reaches the object selected by the entry context `0x74` read, despite publication of the incoming-object address before the payload write.

2. **Exact `0x66` ordering.** An observable trace places the context `0x54` four-byte `0x66` write after the context-linked object’s one-byte `0x10` write and before its four-byte `0x60` write. Final memory alone is insufficient to establish this order.

3. **Destination captured before replacement.** If incoming-object `0x11` overlaps replacement-object `0x14`, changing that stored pointer representation does not change the already captured destination for the subsequent `0x15` write. Its payload still comes from the later incoming-object `0x14` read.

4. **Anchor-induced traversal change.** If anchor minus `0x20` overlaps a subsequently read graph field, later traversal uses that field’s post-write contents, not an entry-time graph snapshot.

5. **Mixed-width replacement.** The four-byte `0x74` write at early-object `0x10` is later followed by a one-byte write at that address. That byte write does not itself replace the other three addressed bytes. Interpretation depends on endianness and intervening writes.

6. **Target-dependent high-bit byte.** For tail-read byte pattern `0x80`, the conditional outcomes are:

   | Plain-character interpretation | Tail operand | First invocation argument | Four-byte store address | One-byte store address |

7. **OR differs from addition.** For tail operand `0x01`, the one-byte store address and first invocation argument both equal `0x45`; the four-byte store starts at `0x46`. For tail operand `0x44`, the first invocation argument is `0x44`, while the one-byte store address is `0x88`.
