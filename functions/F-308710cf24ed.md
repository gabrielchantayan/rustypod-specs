# F-308710cf24ed

## Purpose

F-308710cf24ed attempts to increase an object's recorded count in response to an unsigned request. It scans existing bitmap coverage, conditionally requests backing growth, publishes a derived count, and, when coverage is insufficient, initializes additional records and marks their indices in bitmap storage.

“Capacity growth,” “allocation-map records,” and “available-capacity accounting” are **inferred intent**. The established behavior consists of the accesses, arithmetic, calls, branches, and status handling described below.

The operation is not transactional. Failure can occur after backing changes, count publication, record initialization, link changes, or bitmap writes. No explicit rollback occurs. A zero return can also arise from the missing-chain path if its sampled status is zero; that path does not perform normal success accounting.

## Interface

### Inputs and result

- **Object reference:** a 32-bit address-like input identifying writable object storage.
- **Requested count:** an unsigned 32-bit integer.
- **Result:** a 32-bit status value.

An already-satisfied request returns zero immediately. Normal completion returns zero. Checked dependency failures propagate their statuses after cleanup. A missing bitmap-chain reference selects a value read from an opaque global, not an established immutable error constant.

No explicit validation handles invalid addresses, malformed structures, unsuitable record sizes, or arithmetic overflow.

### Relevant layout

| Location | Width | Established use |
|---|---:|---|
| Object +0x04 | 32 bits | Handle; dereferencing its first word obtains a backing-descriptor address |
| Object +0x1c | 16 bits, unsigned | Record size, initially captured and later reread on bitmap transitions |
| Object +0x20 | 32 bits, unsigned | Recorded count |
| Object +0x24 | 32 bits | Counter updated during normal success accounting |
| Object +0x2c | 32 bits | Flags; bit 0 set during normal success accounting |
| Object +0x44 | 32-bit function pointer | Indirect backing-growth callback |
| Backing descriptor +0x10 | 32 bits, unsigned | Low size component |
| Backing descriptor +0x14 | 32 bits | High size component |

Two temporary descriptors each contain five 32-bit words. Only their first words are explicitly initialized, to zero. The first word supplies a record address at later access points; the meanings and initialization requirements of the remaining words are unknown.

For records obtained through these descriptors:

- A 16-bit field at +10 receives 1.
- An 8-bit field at +8 receives 2.
- A 16-bit field at captured record size minus 4 receives the low 16 bits of captured record size minus 6.
- On a later bitmap-record load, the 16-bit field at freshly read record size minus 2 is interpreted as a **signed** displacement from that record's address.
- Bitmap words are accessed as 16-bit values.

This is not a complete record schema. Byte order is not established independently of the dependencies.

### Preconditions

Safe execution requires all accessed addresses, callback targets, descriptor contents, and dependency outputs to be usable when consumed. No minimum record size is enforced. Small sizes can place trailer accesses before the intended record region; subtraction used for metadata and helper arguments can wrap.

Progress is not guaranteed by the function. Chains can cycle, capacities can fail to advance coverage, and one unsigned endpoint value prevents bitmap-loop termination through its normal comparison.

## Behavior

### Entry and initial coverage scan

The first observable object access reads the original count from +0x20. If the requested count is no greater, the function returns zero without calling dependencies, reading record size, or writing object fields.

Otherwise, it captures the unsigned 16-bit record size and resolves the backing-descriptor address through object +0x04. This resolution occurs **before** the initial scan. The captured backing-descriptor address is subsequently reused; the function does not resolve a replacement after dependencies run.

After initializing the first word of both temporary descriptors, the function scans existing records:

1. F-778071b4c8bc receives the object, first descriptor, and output locations for a bitmap address and capacity information.
2. A nonzero status selects common failure cleanup.
3. The low 16 bits of the capacity output are multiplied by 8.
4. This capacity is added to a running unsigned 32-bit coverage total.
5. F-4055be9c3f18 receives the descriptor's current record address. A nonzero result repeats the scan; zero ends it.

The scan retains the final record's bitmap address, bit capacity, total coverage, and coverage preceding that record. How F-778071b4c8bc advances is unknown.

The opaque status global used during later bitmap transitions is **not explicitly read by this initial scan**.

### Conditional backing growth and count publication

The requested count is multiplied by the captured record size using unsigned 32-bit arithmetic. Overflow is discarded; no wider product is checked.

The indirect callback is called only if the captured backing descriptor has:

- A zero high size component; and
- A low size component strictly smaller than the wrapped product.

Equality skips the callback. Any nonzero high component also skips it.

The callback receives the handle then read from object +0x04, the wrapped product, and 0xffffffff. Its function pointer is obtained from object +0x44. A nonzero result selects common failure cleanup.

F-1e0edc6e0bc9 then receives the captured backing descriptor's current low and high size components, the captured record size, and zero. Its 32-bit result is the **derived count**.

The derived count is immediately written to object +0x20, before record creation or bitmap modification. The function does not check that it reaches the request, is at least the original count, or is consistent with coverage.

### Selecting the coverage path

If accumulated coverage is at least the derived count, no new records or bitmap bits are directly changed. F-b0f922796692 receives the object and first descriptor.

- Zero proceeds to normal success accounting.
- Nonzero selects common failure cleanup, including another call to F-b0f922796692 on that same descriptor.

The additional-record count is zero on this path.

If coverage is smaller, the function passes F-d7be9cfb4000:

- The unsigned shortfall shifted right by 3, discarding its low three bits.
- The low 16 bits of captured record size minus 20.

Its result undergoes a **signed 32-bit increment by one**, producing the additional-record count. Division, rounding, and other behavior inside the dependency are unknown. A signed increment outside the representable range has no established safe contract.

Endpoint construction is different: because the original count is unsigned, the endpoint is the original count plus the additional-record count, minus one, in **unsigned 32-bit arithmetic**. The endpoint can therefore wrap even when the signed increment itself is representable.

### Additional-record initialization

Before obtaining any additional record, F-946cac4b59bc receives the original count and the final existing record address. No result is checked. Interpreting this as link installation is inferred intent.

Initialization starts at the original count and executes at least once:

1. F-b00cf3174ef8 receives the object, current unsigned index, and second descriptor. A nonzero status selects cleanup.
2. The obtained record receives, in order:
   - A 16-bit write of 1 at +10.
   - An 8-bit write of 2 at +8.
   - The 16-bit trailer write at captured size minus 4.
3. Equality between the current index and endpoint is evaluated before the index advances.
4. The unsigned index advances by one.
5. For a non-final record, F-946cac4b59bc receives that advanced index and the current record address.
6. F-f7c5b7585b2d receives the object, second descriptor, zero, and 0x100. A nonzero status selects cleanup.

After successful submission of the record whose pre-increment index equals the endpoint, initialization ends. This equality-based termination works even when the endpoint is 0xffffffff: advancing the index wraps, but the already-established equality ends initialization.

No explicit terminating link is written to the final record. The function cannot be assumed to obtain one from dependency behavior.

For ordinary positive additional-record counts without endpoint wrap, this initializes the corresponding inclusive interval. Wrapped or nonpositive-count cases must instead be understood through the unsigned index progression and equality test. For example, a representable additional-record count of zero yields an endpoint one below the original count and does not produce an empty initialization loop.

All initialization submissions complete before bitmap marking starts.

### Bitmap selection and boundary transitions

Bitmap marking restarts its unsigned index at the original count and initially uses the final bitmap record retained from the scan.

The relative index is the unsigned 32-bit difference between the current index and current coverage base. The current bitmap is usable only when that difference is strictly smaller than its capacity.

Whenever it is not:

1. F-4055be9c3f18 receives the current first-descriptor record address.
2. **Immediately after that call returns, the opaque status global is read.** This read occurs whether the returned next reference is zero or nonzero, and before descriptor submission or loading.
3. If the next reference is zero, the sampled global value becomes the return status through common failure cleanup.
4. Otherwise, F-f7c5b7585b2d receives the object, first descriptor, zero, and 0x100. A nonzero status supersedes the sampled value and selects cleanup.
5. F-5f9a16493218 receives the object, next reference, and first descriptor. A nonzero status selects cleanup.
6. Object +0x1c is reread. The signed 16-bit trailer displacement at that size minus 2 is added to the loaded record address to obtain the bitmap address.
7. F-c4c1afdb3fb3 receives the object, loaded record address, and zero.
8. Its **full 32-bit result** is multiplied by 8, with unsigned 32-bit wrap, to obtain capacity.
9. The previous accumulated coverage becomes the new base; the new capacity is added to form the new accumulated coverage. Coverage selection repeats for the same index.

Unlike initial scanning, this capacity calculation does not mask the helper result to 16 bits.

The global's mutability is unspecified. F-4055be9c3f18 may affect what is sampled, and later calls may change the global again. A missing-reference return uses the sampled value, not a fresh read after cleanup.

### Bitmap modification and termination

For a covered index:

- The word offset is twice the relative index shifted right by 4.
- The mask starts at bit 15 for relative position zero and reaches bit 0 for relative position fifteen.
- F-0ec8efa9c769 receives that 16-bit mask.
- The existing 16-bit bitmap word is read after the mask-transform call and ORed with its 16-bit result.
- The resulting word is written back.

The destination address is determined before the mask-transform call. No assumption is made that the dependency preserves the buffer's contents. OR preserves bits set in the word as read; the actual stored mask depends on the dependency.

The unsigned index advances by one before the word write and the termination comparison. Marking stops only when the endpoint is **strictly smaller than the advanced index**.

Thus, ordinary nonwrapping intervals ending below 0xffffffff are marked inclusively. This is not an unconditional inclusive-interval contract:

- When the endpoint is 0xffffffff, advancing from that index wraps to zero.
- No unsigned 32-bit index can exceed that endpoint.
- The termination comparison therefore never ends bitmap marking for that endpoint, even after its nominal final bit has been written.

Execution can instead fail, become nonterminating elsewhere, or continue processing wrapped indices. Coverage selection after wrapping still uses unsigned subtraction; it is not reset to the beginning of the bitmap chain.

After the termination comparison succeeds, F-f7c5b7585b2d submits the current first descriptor with zero and 0x100. Zero proceeds to normal success accounting; nonzero selects cleanup.

### Normal success accounting and cleanup

Normal success performs these writes in order:

1. Write the retained derived count to object +0x20 again.
2. Read object +0x24 and add derived count minus original count minus additional-record count, using unsigned 32-bit arithmetic.
3. Read object +0x2c and write it back with bit 0 set.
4. Return zero.

The counter and flags use their values at this stage, not entry snapshots.

Common failure cleanup calls F-b0f922796692 first on the object and first descriptor, then on the object and second descriptor. Both results are ignored. The previously selected status is returned.

Cleanup does not explicitly restore object fields, backing size, records, links, or bitmap words. If the missing-reference path sampled zero, cleanup returns zero **without** executing normal success accounting.

## Side effects

Established direct effects include early and success-time count writes, success-time counter and flag updates, ordered record metadata writes, and 16-bit bitmap read-modify-write operations.

The opaque status global is explicitly read on every bitmap-coverage transition attempt, including successful next-reference discovery. No direct write to it is shown.

Dependency calls may have further effects. No dependency is established to preserve globals, object fields, captured storage, or descriptors. Capturing an address does not establish that its contents remain unchanged.

Ownership and lifetime are **documented_only**. The function contains no explicit allocation or deallocation primitive. Submission and cleanup call placement does not prove flushing, release, ownership transfer, descriptor clearing, or repeated-call safety.

## Acceptance examples

These are conditional static expectations, not executed tests.

1. **Immediate no-op.** With original count 100 and request 99 or 100, return zero after the count comparison. No dependency is called and no object write occurs.

2. **Callback threshold and overflow.** With size 512 and request 20, the product is 10,240. A zero high component and low component 10,239 invoke the callback; low component 10,240 does not. A nonzero high component skips it. With request 8,388,608, the wrapped product is zero, not 4,294,967,296.

3. **Existing coverage.** With original count 100, derived count 120, coverage 128, and successful finalization, no additional records or bitmap bits are directly modified. Normal accounting adds 20 to the counter and sets flag bit 0, using then-current field values.

4. **Ordinary additional interval.** With original count 100, derived count 140, insufficient coverage, and F-d7be9cfb4000 returning 2, the additional-record count is 3 and endpoint is 102. Conditional on successful dependencies and usable coverage, records and bitmap indices 100–102 are processed. Normal accounting adds 37 modulo 2³².

5. **Missing-reference sampling.** At a bitmap boundary, suppose F-4055be9c3f18 returns zero and the immediately following global read yields a status value. Cleanup runs and that sampled value is returned, even if cleanup changes the global. Neither descriptor submission nor loading occurs at that boundary.

6. **Sampling despite a next reference.** If F-4055be9c3f18 returns a nonzero reference, the global is still read before submission and loading. Successful subsequent operations do not treat the sampled value as a failure status.

7. **Zero sampled status.** If a missing-reference boundary samples zero, the function returns zero after cleanup but does not perform normal success accounting. Earlier count publication and other partial changes are not explicitly undone.

8. **Maximum endpoint.** With original count 0xfffffffe and a representable additional-record count of 2, the endpoint is 0xffffffff. Successful initialization ends after the second record. Bitmap marking does not end after marking those two indices: its index wraps to zero, and the endpoint comparison remains false.

9. **Bitmap word boundary.** Relative indices 15 and 16 select different words and pre-transformation masks 0x0001 and 0x8000, respectively. Stored masks remain conditional on F-0ec8efa9c769.

## Uncertainties

The following remain **documented_only**:

- Semantic meanings, valid ranges, and external format invariants.
- Dependency arithmetic, including division and zero-divisor behavior.
- The opaque global's value, mutability, and intended error meaning.
- Descriptor ownership, persistence, release, and repeated-cleanup safety.
- Dependency effects on globals, fields, descriptors, and previously returned storage.
- Locking, concurrency, durability, and crash consistency.
- Behavior of invalid addresses, malformed chains, aliased storage, invalid trailer offsets, or nonprogressing capacities.

Signed overflow in the additional-record-count increment is unresolved. Endpoint construction and bitmap-index advancement, however, are explicitly unsigned 32-bit operations. Their wrap behavior—including the maximum-endpoint termination failure—is not limited to signed-overflow cases.
