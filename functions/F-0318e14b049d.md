# F-0318e14b049d

## Purpose

F-0318e14b049d processes a record against an object and returns a 32-bit recognition result.

Two record-kind values have established behavior:

- Kind `0x0F` toggles the low bit of a shared value and invokes two dependencies in sequence.
- Kind `0x13` attempts a primary match, followed by a conditional secondary match. A successful match invokes an indirect object operation and returns `1`.

Other kinds return `0` without entering either matching path.

The apparent intent is event handling with a mode-toggle action and two alternative activation conditions. The event interpretation is inferred; the comparisons, calls, and return values are established by the supplied static representation.

## Interface

### Inputs

The function receives two address-valued arguments:

1. **Object address.** Identifies readable object storage containing a dispatch-table pointer, comparison fields, a secondary-match enable field, and an embedded region passed to a dependency.
2. **Record address.** Identifies readable storage containing a kind and two comparison values.

The supplied representation uses 32-bit integer fields. The byte layouts below follow its four-byte integer indexing and address arithmetic.

| Storage | Byte offset | Established use |
|---|---:|---|
| Object | `0x00` | Dispatch-table pointer used for indirect calls |
| Object | `0x40` | Primary first-coordinate comparison value |
| Object | `0x44` | Primary second-coordinate comparison value |
| Object | `0x98` | Secondary second-coordinate comparison value |
| Object | `0x9C` | Secondary enable field; zero disables, any nonzero value enables |
| Object | `0x1F4` | Address of embedded storage passed to F-ec4cfa552cce |
| Record | `0x04` | Kind |
| Record | `0x08` | First comparison value |
| Record | `0x0C` | Second comparison value |

“Coordinate” is a descriptive label for the paired comparisons, not an established geometric interpretation.

The dispatch table supplies callable targets at byte offsets `0xD4` and `0xA0`. Their concrete identities and broader interfaces are unavailable.

### Output

The return value is a 32-bit quantity:

- `1` after either matching path invokes its indirect dependency and that dependency returns normally.
- `0` when the post-action kind is not `0x13`, or when neither matching path succeeds.

A `0` result does not imply that no action occurred. A kind-`0x0F` invocation can toggle shared state and call both direct dependencies before returning `0`.

### Preconditions

All storage and callable targets actually reached by an execution must be valid for the corresponding accesses and calls. The function performs no visible null, bounds, object-type, or dispatch-target validation.

Validity requirements are path-dependent. For example, an ordinary unrecognized kind requires access to the record kind but does not visibly dereference object fields. Kind `0x13` requires the comparison fields reached by its matching path; a successful match additionally requires a usable dispatch table and target.

The required extent and interpretation of the embedded storage at object offset `0x1F4` depend on F-ec4cfa552cce and are unknown.

## Behavior

### Initial kind check and toggle action

The function first reads the 32-bit record kind at offset `0x04`.

If that value equals `0x0F`, it performs the following operations in order:

1. Reads a shared toggle location, applies exclusive OR with `1`, and writes the result back to that location.
2. Calls F-92bea7c30bd6 with the object address.
3. Calls F-ec4cfa552cce with the address formed by adding `0x1F4` bytes to the original object address.

The toggle is a low-bit operation, not logical negation or assignment to a Boolean. For example, if the location supports the represented ordinary integer operation, `2` becomes `3`, rather than becoming `0` or `1`. The location’s storage width is not established by the supplied declarations.

The second dependency receives the embedded-region address, not the object base and not a pointer loaded from that region. Its contents are not copied by this function before the call.

Both dependency return values are ignored. No visible failure check separates the calls.

### Kind recheck

After the optional toggle action, the function reads the record kind again from offset `0x04`.

If this read is not `0x13`, it immediately returns `0`.

This is a fresh read, not reuse of the initial kind. Consequently, the result of processing an initial kind `0x0F` depends on any record changes made before the second read. The dependencies receive no explicit record argument, but that does not establish that they cannot reach or modify it through aliases or other state.

If either earlier dependency does not return normally, the later read and subsequent behavior are not reached.

### Primary match

When the second kind read equals `0x13`, the function reads the record’s second comparison value from offset `0x0C`. It retains that value for the primary comparison and any subsequent secondary comparison.

It next reads the object’s primary second-coordinate value at offset `0x44`.

If those values differ, it skips the remaining primary-match reads and proceeds to secondary matching.

If they are equal, it:

1. Reads the record’s first comparison value at offset `0x08`.
2. Reads the object’s primary first-coordinate value at offset `0x40`.
3. Accepts equality between those first-coordinate values immediately.
4. Only if those values differ, reads a shared alternate primary value and compares the already-read record first-coordinate value against it.

Thus, the primary match requires:

- Equality of the second comparison values; and
- A record first comparison value equal to either the object’s primary first-coordinate value or the shared alternate primary value.

The alternate shared value is not visibly read when the object’s own first-coordinate value already matches.

On a primary match, the function loads the object’s dispatch-table pointer, resolves its entry at byte offset `0xD4`, and calls that target with the object address. If the call returns normally, F-0318e14b049d returns `1`.

Primary success takes precedence over secondary matching. The secondary enable and comparison fields are not read on that successful path.

### Secondary match

If the primary match does not succeed, the function reads the object’s 32-bit secondary enable field at offset `0x9C`.

If that field is zero, it returns `0` without reading the secondary second-coordinate field or secondary first-coordinate inputs.

If the enable field is nonzero, the function reads the object’s secondary second-coordinate value at offset `0x98` and compares it with the record second comparison value retained earlier.

If those values differ, it returns `0`. It does not reread the record’s second comparison value.

If they are equal, it reads:

1. The record’s first comparison value at offset `0x08`.
2. A shared secondary first-coordinate comparison value.

These are new reads on the secondary path. In particular, the record’s first comparison value can be read again after an unsuccessful primary attempt; it is not necessarily reused from that attempt.

If these first-coordinate values differ, the function returns `0`.

If they match, the function:

1. Calls F-5710a8628cba with no explicit arguments.
2. Retains an 8-bit result from that call.
3. Loads the object’s dispatch-table pointer and its entry at byte offset `0xA0`.
4. Calls that target with the object address and the retained 8-bit value.
5. Returns `1` if the indirect call returns normally.

The dispatch-table lookup occurs after F-5710a8628cba returns. The supplied evidence does not justify moving that lookup earlier or assuming that the dependency leaves object or global state unchanged.

### Arithmetic and comparison boundaries

The comparisons are equality tests on represented 32-bit integer values. They do not impose a positive range or reject negative representations.

The embedded-region address uses a fixed displacement of `0x1F4` bytes. No checked arithmetic or overflow handling is visible. Valid formation and use of that address are caller-side preconditions.

No arithmetic increment, coordinate normalization, masking of comparison values, or Boolean normalization of the secondary enable field is established.

## Side effects

The only explicit data write in the function body is the shared toggle update on the initial kind-`0x0F` path.

Other effects arise through dependencies:

- F-92bea7c30bd6 receives the object address.
- F-ec4cfa552cce receives an address within the object.
- The primary indirect operation receives the object address.
- F-5710a8628cba has no explicit arguments but may access other state.
- The secondary indirect operation receives the object address and an 8-bit value.

Their mutations, external interactions, allocation behavior, and failure behavior are unknown. The function must not be described as read-only merely because most of its own operations are reads.

No explicit allocation, deallocation, ownership transfer, or memory release appears in the function body. Passing an address establishes access by a dependency, not ownership transfer or guaranteed retention. Dependency ownership behavior remains undocumented.

No synchronization or atomic toggle operation is established. Concurrent mutation behavior is outside the supported contract.

## Acceptance examples

These examples are conditional static acceptance criteria, not observed executions. Unless stated otherwise, assume valid memory, normally returning dependencies, and no intervening mutation.

1. **Unrecognized kind.** If both kind reads produce `0x07`, the result is `0`. No toggle, matching-field access, or dependency call is required.

2. **Toggle without recognition.** If the initial kind is `0x0F` and remains `0x0F`, the shared low bit is toggled, F-92bea7c30bd6 runs, then F-ec4cfa552cce runs. The result is `0`.

3. **Toggle followed by matching.** If the initial kind is `0x0F` and a dependency changes the kind to `0x13` before the recheck, matching proceeds after both direct calls. A later match may produce `1`.

4. **Primary object-value match.** For kind `0x13`, suppose the record pair equals the object’s primary pair. F-INDIRECT-01 is called and the result is `1`. Neither the alternate primary shared value nor the secondary enable field is needed.

5. **Primary alternate-value match.** Suppose the second values match, the record first value differs from the object’s primary first value, and it equals the shared alternate primary value. F-INDIRECT-01 is called and the result is `1`.

6. **Disabled secondary path.** Suppose primary matching fails and the secondary enable field is zero. The result is `0`; F-5710a8628cba and both indirect dependencies are not called.

7. **Enabled secondary match.** Suppose primary matching fails, the enable field is any nonzero 32-bit value, the retained record second value equals the object’s secondary second value, and the newly read record first value equals the shared secondary first value. F-5710a8628cba runs before F-INDIRECT-02, which receives its retained 8-bit result. The result is `1`.

8. **Primary precedence.** If both match conditions would otherwise hold, primary success invokes only F-INDIRECT-01. It does not also invoke F-5710a8628cba or F-INDIRECT-02.
