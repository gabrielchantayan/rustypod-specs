# F-046e6fa86957

## Purpose

F-046e6fa86957 performs a bounded, first-eligible-slot update in a table referenced through global state. Each slot contains a 32-bit key followed by a 32-bit payload. A slot is eligible when its key equals the requested key or is zero.

The function searches from the beginning of the table. At the first eligible slot, it writes the requested key and payload, then returns success. If all 80 slots contain nonzero keys different from the requested key, it returns failure without executing either table write.

This is not necessarily a search for an existing key followed by a search for free space. An earlier zero-key slot takes precedence over a matching key farther into the table.

The likely intent is insertion or replacement in a fixed-capacity association table. That interpretation is inferred. The established behavior is the bounded scan and pair of stores described below.

## Interface

**Inputs**

- **Requested key:** a 32-bit integer used for equality comparison and stored in the selected slot. Zero is accepted; there is no rejection or separate zero-key path.
- **Payload:** a 32-bit uninterpreted value copied into the selected slot. The function does not inspect or dereference it.

**Implicit input**

- A global table-base value supplies the addresses used for the scan and the key write.
- The function also captures that global value once at entry and retains the captured value for the payload write.

**Output**

A 32-bit result:

| Result | Meaning |
|---|---|
| 1 | An eligible slot was found and both specified stores completed before the ordinary return. |
| 0 | All 80 inspected slots were ineligible. |

There is no distinct result for insertion versus replacement, and no returned slot index or displaced payload.

These results describe ordinary completion. Invalid memory access and interference are not converted into documented error results.

**Table layout**

The source establishes the following slot layout:

| Component | Offset within slot | Width |
|---|---:|---:|
| Key | 0 bytes | 4 bytes |
| Payload | 4 bytes | 4 bytes |

The slot stride is 8 bytes. Valid scan indices are 0 through 79 inclusive.

With a stable table base:

- The first slot has its key at byte offset 0 and payload at byte offset 4.
- The last inspected slot has its key at byte offset 632 and payload at byte offset 636.
- The complete nominal table footprint is 640 bytes.

The evidence does not establish byte order, allocation origin, memory protection, or a supported external serialization format.

## Behavior

### Base capture and bounded search

Before inspecting any key, the function reads the global table-base value and captures it for a potential payload store.

It then inspects slots in increasing index order, beginning with index 0. For each slot:

- It obtains the current global table-base value for that key access.
- It reads the 32-bit key at the corresponding 8-byte-stride offset.
- It accepts that slot if the read key equals the requested key or equals zero.
- If neither condition holds, it advances to the next index.

There are at most 80 key inspections. The function does not inspect a slot beyond index 79.

The scan examines keys only. It does not read payloads to determine eligibility, compare payloads, or retain the previous payload.

The same key read supplies the eligibility decision for a slot. The two equality conditions do not require two reads of the slot’s key.

### Successful update

At the first eligible index, the function performs two distinct stores in this source-level order:

1. It writes the requested 32-bit key at the selected index, using the global table-base value obtained for that store.
2. It writes the supplied 32-bit payload at the selected index using the table-base value captured at entry.

It then returns 1 immediately. No later slot is inspected.

Under a stable-base, noninterfering memory model, both stores address the same slot. The key is written even when it already equals the requested key. The payload is replaced without first being read.

The two stores are not established to be an atomic pair. The supplied evidence provides no lock, transaction, rollback, or publication protocol. An observer or interruption between stores may therefore matter, but the precise concurrency behavior is not specified.

### Full-table failure

If every inspected key is both nonzero and different from the requested key, the function returns 0 after inspecting index 79.

On this path, the function executes no explicit table store. It still reads and captures the global base at entry and performs the scan’s key reads.

A table need not contain an empty slot for the function to succeed: a matching key remains eligible even when all 80 keys are nonzero.

### Zero-key behavior

Zero has two roles in the eligibility rule:

- A stored zero makes a slot eligible for any requested key.
- A requested key of zero matches a stored zero.

Consequently, a request with key zero selects the first zero-key slot and writes zero back into its key field. It also replaces that slot’s payload and returns 1.

Such a successful call does not make the slot ineligible for a later nonzero-key request. A later request can select the same slot because its key remains zero.

If all 80 keys are nonzero, a zero-key request returns 0.

### Duplicate keys and early empty slots

The function stops on the first eligible slot, regardless of why it is eligible.

Accordingly:

- Among multiple matching keys, it updates the earliest one, unless an earlier zero-key slot is encountered.
- If a zero-key slot precedes an existing match, the zero-key slot is selected and the later match is untouched by the function’s explicit stores.
- The function does not enforce key uniqueness, remove duplicates, compact entries, or repair table ordering.

Any invariant requiring all existing matches to precede all empty slots must be maintained elsewhere. It is not checked here.

### Integer and address arithmetic

The scan index starts at zero and increases only while searching the fixed 80-slot range. Its executed values do not approach the limits of a 32-bit signed integer.

The slot offset ranges from 0 through 632 bytes. The payload offset ranges from 4 through 636 bytes. These small offsets do not themselves require signed overflow.

This does not prove that adding an offset to the supplied table base produces a valid address. Address-width rules, base-address validity, alignment requirements, and address-space boundaries are not established by the supplied evidence.

Key comparison is equality, not ordering. Negative keys receive no special treatment.

## Side effects

Under stable-base conditions, successful ordinary completion executes one 32-bit key store followed by one 32-bit payload store at the selected slot. Unsuccessful ordinary completion executes neither store.

The function explicitly contains:

- No allocation or deallocation.
- No payload dereference.
- No clearing of a displaced value.
- No callback or other function invocation.
- No explicit synchronization.
- No explicit validation of table storage.
- No explicit assignment to the global table-base object.

These are limits on the function’s explicit operations, not guarantees about aliased memory or platform behavior.

In particular, the evidence does not establish that the table storage is disjoint from the global base object. A store through an aliased table address could affect that object or other state. Likewise, the source does not establish protection against changes made by another execution context.

### Captured and current bases

The function does not consistently use one captured base for all accesses:

- The payload write uses the entry-time captured base.
- Each key read uses a value obtained from the global base for that access.
- The successful key write uses a value obtained from the global base for that store.

If the global base changes during execution, the selected key, written key, and written payload need not reside in the same table allocation. The function contains no consistency check or restart to address that possibility.

A caller that needs a coherent update to one table must ensure an appropriate stable-base and noninterference precondition. The source does not show how callers provide that guarantee.

### Ownership

The function provides no evidence of ownership transfer for either argument or the table storage.

A payload may happen to encode an address, but this function treats it only as a 32-bit value. It does not acquire, retain, release, or validate an object represented by that value. Any resource-lifetime meaning belongs to an external contract not supplied here.
