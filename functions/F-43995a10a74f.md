# F-43995a10a74f

## Purpose

F-43995a10a74f performs a gated, multi-stage operation on a mutable record and its associated context. It validates eligibility, prepares related state, obtains two helper-produced values, optionally processes an indexed entry, and then invokes two finalization stages.

The established behavior is the order of checks, dependency calls, direct memory accesses, status propagation, and conditional record updates described below. The business meaning of the operation, its status codes, and its associated objects is not established. Terms such as “record,” “context,” “working object,” and “resource” identify roles within this contract, not proven domain types.

The operation is not demonstrably transactional. Earlier dependency effects and direct writes are not rolled back when a later stage returns an error.

## Behavior

### 1. Initial dispatch

The function first reads the record’s root reference, then obtains and retains the context reference from root offset `0x04`.

It reads the context byte at `0x30`:

- If the byte is not 2, it reads context byte `0x11` and returns **1** when that byte is zero, otherwise **8**.
- If the byte is 2, it examines the low eight bits of the record word at `0x40`. Zero returns **3**.

These early paths make no dependency calls and perform no direct writes.

With the gates satisfied, it invokes **F-fa3b853f090d** with the record’s root reference, the record value at `0x14`, and the record pointer. These record values are read at this stage; the context reference already retained is not recomputed.

Any nonzero result from this dependency becomes return status **6**, regardless of the dependency’s exact result.

### 2. Stored-status shortcut or preparation

After a zero eligibility result, the function reads record mode byte `0x43`.

If the mode is 3, it returns the current 32-bit value at record offset `0x50`. No later dependency is called.

For every other mode:

1. Call **F-20557aeabe2e** with the record pointer. Its result is not used.
2. Call **F-533f1c9e9e0b** with the retained context, the current record value at `0x14`, and the record pointer.
3. Return the latter dependency’s result if nonzero.

The record is mutable across these calls. The second call’s `0x14` argument is not established to equal the value previously passed to the eligibility dependency.

### 5. Conditional entry processing

Following main-operation success, the function branches on the signed output of the preliminary operation.

#### Zero preliminary output

The record mode at `0x43` is read again. Only mode 1 triggers indexed-entry processing.

First, **F-81c906bf6e3a** is called with the 32-bit value at working-object offset `0x48`. A nonzero return is propagated immediately.

Next, an entry address is derived:

- Read an unsigned 16-bit displacement from working-object offset `0x0e`.
- Read the current 32-bit record index at `0x1c`.
- Add twice the index to the displacement.
- Read the table base from working-object offset `0x44`.
- Read two adjacent bytes at that table base plus the calculated displacement.
- Interpret the first byte as the high byte and the second as the low byte of an unsigned 16-bit offset.
- Add that unsigned offset to the table base to obtain the entry address.

The two-byte table entry therefore has an explicit high-byte-first interpretation, independently of native word endianness.

If working-object byte `0x04` is zero, an unmapped external dependency is called with the resource, entry address, and constant **4**. Its result is not consulted. The supplied evidence does not establish whether this is a copy, read, synchronization, or another operation.

Then:

1. Call **F-38c1baaad724** with the working object and computed entry address; retain its 32-bit result.
2. Call **F-d153bcc89350** with the same working object and entry address.
3. If the second call returns nonzero, return that status without calling the next dependency.
4. Otherwise call **F-defc2fecf605** with the working object, the current record index, and the retained result from the first call. Its result is not used.

The entry address is retained across these calls. The index passed to the last call is read again; it need not equal the index used to calculate the address if an intervening dependency changes the record.

#### Negative preliminary output

If the preliminary output is negative, the function reads the 16-bit field at working-object offset `0x14`.

When that field is nonzero, it performs these direct writes in order:

1. Increment the record’s 32-bit index at `0x1c` by one.
2. Store 16-bit zero at record offset `0x3e`.
3. Store 8-bit zero at record offset `0x42`.

These writes occur before final application and are not explicitly undone if finalization fails.

If the 16-bit field is zero, none of these writes occurs.

#### Positive preliminary output

A positive preliminary output causes neither indexed-entry processing nor the negative-result writes.

## Side effects

The only direct writes established within this function are the three negative-result-path writes: index increment, 16-bit clear, and byte clear.

Dependency calls can have additional effects. No supplied contract establishes that they preserve globals, leave referenced objects unchanged, retain ownership, or refrain from releasing memory. Safe execution requires that objects subsequently accessed remain valid despite those calls.

Important temporal distinctions include:

- Context is captured before eligibility processing.
- Working object is captured after preliminary success but before context preparation.
- Resource is read after context preparation and retained thereafter.
- Mode is read separately for the stored-status shortcut and the later mode-1 branch.
- Index is read at multiple stages rather than captured once.
- Entry address is computed once and reused across the indexed-entry dependencies.

No explicit allocation, deallocation, rollback, exception handling, or ownership transfer appears in the function itself. This does not establish their absence inside dependencies.

The two local output slots are not visibly initialized before their respective calls. The consumed value of each slot must therefore be supplied by the corresponding successful dependency for defined, meaningful operation. Retention of those local addresses beyond the calls is not supported by the visible lifetime.

## Acceptance examples

These are conditional acceptance criteria derived from static evidence, not executed tests. Each assumes valid memory and dependencies that leave later-required objects accessible.

1. **Context mismatch takes precedence.** If context type is not 2 and context byte `0x11` is zero, return 1 even if the record’s enable value is also zero. No dependency is called. A nonzero `0x11` byte instead selects 8.

2. **Only the low eight enable bits count.** With context type 2 and enable word `0x00000100`, return 3 without calling eligibility. A nonzero full word alone is insufficient.

3. **Eligibility statuses collapse.** If eligibility returns either a positive or negative nonzero value, return 6. Do not inspect mode or return the dependency’s original status.

4. **Stored status is not forced to failure.** If eligibility succeeds, mode is 3, and stored status is zero, return zero without running preparation, operation, or finalization dependencies.

5. **Resource is observed after preparation.** If context preparation leaves the resource field zero, return 7 without calling the main operation. This remains true even if that field was nonzero before the preparation call.

6. **Table entries are high-byte-first.** Suppose the preliminary output is zero, mode is 1, entry preparation succeeds, the table displacement is 16, and the current index is 3. The two table bytes are read at base offsets 22 and 23. Values `0x01` and `0x20` select an entry at base plus `0x0120`, not base plus `0x2001`.

7. **Entry failure stops later stages.** If the entry-processing gate returns a nonzero status, return it without the entry-update dependency, final application, or subsequent finalization.

8. **Negative output updates before failure.** With negative preliminary output, nonzero working-object field `0x14`, and index 9, write index 10 and clear the two specified fields before final application. If final application then fails, the function performs no rollback.

9. **Positive output bypasses both special branches.** A positive preliminary output neither processes the indexed entry nor advances the index, regardless of mode.

10. **Completion requires both final gates.** The final record dependency is called only when final application and subsequent finalization both return zero. Its own return cannot change the function’s zero result.
