# F-958d94a9f3f3

## Purpose

F-958d94a9f3f3 has a recovered behavior consisting of a single byte-sized memory write followed by an unbounded sequence of architecture-specific coprocessor operations.

The memory write derives its value from an incoming character-sized value. The coprocessor operation initially receives a value derived from an incoming unsigned address-bearing value; subsequent iterations receive zero through that same operand position.

No normal return, completion status, allocation, or release operation is visible.

This is a static, source-facing contract, not a verified machine-level specification. The supplied representation includes warnings about invalid instruction data and removed unreachable regions. Accordingly, the behavior below describes the recovered path; it does not establish that the original executable has exactly this control flow.

### Implicit inputs

The recovered body uses four incoming values:

- **Character input:** a character-sized value shifted left before conversion to the value stored by the byte write.

## Behavior

### Initial memory write

The recovered path first forms an address by adding decimal ten to the incoming address-bearing value. It then attempts a character-sized write at that address.

The written value is formed by shifting the incoming character value left by six bits and converting the result to the destination character representation.

Under the conventional interpretation of eight-bit bytes, a defined shift, and retention of the low eight result bits, the stored byte depends only on the low two bits of the incoming character value:

| Low two input bits | Stored byte |
|---|---:|
| 00 | 0x00 |
| 01 | 0x40 |
| 10 | 0x80 |
| 11 | 0xC0 |

This table is conditional rather than an unconditional language-level guarantee. The representation does not establish character signedness. A negative signed character can make a left shift problematic under source-language rules, and conversion of an out-of-range result to a signed character requires additional interpretation.

The recovered body contains no validation of the destination, no check of the character value, and no explicit handling of a failed write.

### Entry into the repeating operation

After the initial write, execution enters a loop whose recovered continuation condition is always true.

On the first iteration:

1. A logical right shift by eleven bits is applied to the incoming unsigned address-bearing value.
2. The loop’s address-bearing state is replaced with zero.
3. A coprocessor operation is issued with the shifted result, the two auxiliary inputs, and the literal selector values 8, 5, and 4.

The shifted result is determined before the loop state is replaced. Consequently, resetting that state does not erase the operand supplied to the first operation.

The ordering is material: the memory write precedes the first coprocessor operation in the recovered path. There is no recovered alternative branch that issues the operation before attempting the write.

### Subsequent iterations

In the recovered dataflow, the next iteration begins with the address-bearing loop state equal to zero. Its right shift therefore produces zero, and the state is again assigned zero before the coprocessor operation.

Thus, if execution continues normally through the repeated operation without effects that invalidate the recovered state model:

- The first operation’s derived operand is the original address-bearing value shifted right by eleven.
- Every later operation’s derived operand is zero.
- The same two auxiliary input expressions are supplied on every iteration.
- The selector values remain 8, 5, and 4.

This does not establish that the coprocessor operation is harmless, returns normally, or preserves unrelated state. Its effects are unspecified by the supplied material.

### Integer arithmetic

The right shift is represented as operating on an unsigned integer. Under a 32-bit interpretation, shifting right by eleven produces a value from zero through 0x001FFFFF.

The address addition is also represented using the unsigned address-bearing input. Under 32-bit unsigned arithmetic, adding ten wraps modulo 2³² before the result is interpreted as an address. That arithmetic observation does not imply that the resulting address is valid or writable.

The replacement of the loop’s address-bearing state with zero is not a write of zero to memory at that address. The only explicit ordinary-memory write in the recovered body is the initial character-sized store.

### Termination and failure

No exit condition or normal return is visible. If the initial write succeeds and every coprocessor operation permits execution to continue, the recovered loop continues indefinitely.

A memory fault, unsupported operation, privilege exception, trap, external interruption, or nonreturning coprocessor effect could prevent further progress. The body supplies no explicit recovery behavior for these events. Their outcomes remain environment-dependent.

## Acceptance examples

Expected recovered behavior:

- Attempt to write 0x40 at address 0x0000180A.
- Derive the first operation’s unsigned operand as 3.

### Truncation of the shifted character value

Assume eight-bit bytes and an interpretation that retains the low eight bits of the shifted result.

Character inputs of 1 and 5 both yield a stored byte of 0x40. Their differing higher bits do not survive that interpretation of the character-sized store.

This example does not resolve signed-character conversion rules.

### Zero first derived operand

Assume a 32-bit unsigned address-bearing input below 0x00000800 and a successful initial store.

The first right shift produces zero. The recovered repeated operand sequence is therefore zero from the first operation onward, rather than becoming zero only after the first operation.

### Maximum unsigned input

Assume a 32-bit unsigned address-bearing input of 0xFFFFFFFF.

Unsigned addition of ten produces 0x00000009, while shifting the original input right by eleven produces 0x001FFFFF. The first operation uses the latter value if execution reaches it.

No claim is made that address 0x00000009 is writable.

### Initial-store failure
