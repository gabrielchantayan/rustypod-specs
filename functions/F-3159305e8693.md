# F-3159305e8693

## Purpose

F-3159305e8693 performs an ordered search over at most 205 record positions and returns a 32-bit Boolean-like result. It compares an input identifier with each record identifier and, for an enabled match, compares a derived reference value with two derived bounds.

Record order affects the result. A matching record with zero status immediately returns zero. An enabled matching record also immediately returns zero if the reference is below its derived lower bound. Only an enabled match whose reference is at least the lower bound but greater than the upper bound permits the search to continue. A reference satisfying both inclusive bounds returns one.

Consequently, this function is not an unrestricted “any matching interval qualifies” query: an earlier record can prevent consideration of later qualifying records.

Time-window membership is inferred intent. The established behavior consists of dependency calls, corrections involving 60 and 3,600, and unsigned comparisons. Units, calendar conventions, and the application meaning of the identifiers are not established.

## Interface

### Input

One unsigned 32-bit identifier.

The complete identifier is passed to F-cb3a86d90510. Record matching compares the complete input against an unsigned 16-bit record identifier widened without sign extension. The input is not truncated to 16 bits.

An input greater than 65,535 therefore cannot match a record under this representation. It still causes the initialization calls and, assuming execution proceeds normally, all 205 identifier comparisons.

### Output

A 32-bit value, either zero or one:

- **One:** An enabled matching record has a derived reference at least as large as its lower bound and no larger than its upper bound.
- **Zero:** A matching record has zero status; an enabled matching record has a reference below its lower bound; or the search exhausts all 205 positions without returning one.

There is no distinct error result. Invalid storage, incomplete dependency outputs, and dependency-specific failure indications have no established recovery behavior.

Valid, accessible storage is a precondition for every access actually reached. A complete unsuccessful scan requires readable identifiers at all 205 positions. Matching records additionally require readable 16-bit status fields.

## Behavior

### Initialization and reference derivation

Before examining any record, the function makes these calls in order:

1. F-3b3feb156f36 receives the address of the initial object.
2. F-b8274406a146 receives that address and the integer argument one.
3. F-59067e4d309c receives the first auxiliary output address followed by the second auxiliary output address.
4. F-cb3a86d90510 receives the complete input identifier.

The initial conversion result and initial identifier-dependent correction are retained for the reference calculation. After these calls, the function reads and captures the global reference to the table-owning object.

The reference is then formed from:

- The initial conversion result;
- Minus 60 times the initial identifier-dependent correction;
- Minus 60 times the character value read from the first element of the second auxiliary output area.

The result is retained as an unsigned 32-bit value for all later comparisons.

The auxiliary character is used numerically, not merely as a Boolean. For an unambiguously positive character value of two, its contribution is a subtraction of 120. It does not cause a subtraction of 3,600 at this stage.

The reference is not recomputed for later records. Subsequent changes to the auxiliary output or initial object do not retroactively change the retained reference.

The first auxiliary output area is not explicitly read afterward by this function. Its address and the call that receives it remain observable to F-59067e4d309c.

### Ordered traversal

The initial index is zero. Records are examined in increasing index order through index 204 inclusive.

For each position, the function:

- Reads the record-array address from offset 8 of the captured table-owning object.
- Uses that address plus 16 times the current index to locate the record.
- Reads its unsigned 16-bit identifier.
- Compares that identifier against the complete unsigned 32-bit input.

On an identifier mismatch, the function does not read the status field and does not request boundary generation. It advances to the next position.

The global reference to the table-owning object is not explicitly reloaded during traversal. The record-array address inside that object is reloaded for each position. Thus, a dependency that changes the global reference alone does not redirect this captured reference, whereas a change to the captured object’s array-address field can affect a subsequent iteration.

No snapshot, immutability, or synchronization guarantee is established.

### Matching record with zero status

For a matching identifier, the function reads the 16-bit field at record offset 2 and narrows it to a character-sized value.

If that narrowed value is zero, the function immediately returns zero. It neither generates boundaries nor considers later records.

A nonzero high byte cannot enable a record whose low eight bits are zero. For example, a status field numerically equal to 0x0100 takes the zero-status path.

For this zero/nonzero decision, uncertainty about character signedness does not change which low-eight-bit values are zero.

### Boundary generation for an enabled match

For a matching record with nonzero status, F-09958d49214d receives, in order:

1. The zero-based record index.
2. The first 32-bit component of the initial object.
3. Its second 32-bit component.
4. Its third 32-bit component.
5. The first boundary object’s address.
6. The second boundary object’s address.

The dependency receives an index, not the matching record’s address. The initial-object components are supplied by value at this call; they are not established to be an immutable snapshot of their values immediately after initialization.

### Lower-bound derivation

After boundary generation, the function:

1. Calls F-b8274406a146 on the first boundary object, with second argument one.
2. Calls F-cb3a86d90510 with the complete input identifier.
3. Forms a lower-bound value from this conversion result minus 60 times this correction, retaining an unsigned 32-bit result.
4. Reads the relevant auxiliary character again.
5. Subtracts 3,600 from the lower bound if that character is greater than zero.

This positive-character test is distinct from the earlier numerical contribution to the reference. A value of two still causes only one subtraction of 3,600 from the lower bound.

The character read here need not equal its earlier value unless a dependency contract guarantees stability. The function has supplied the auxiliary area’s address to a dependency, and no supplied contract rules out retained access or later modification.

### Second-boundary calls and decision order

Before comparing the reference with the lower bound, the function:

1. Calls F-b8274406a146 on the second boundary object, with second argument one.
2. Calls F-cb3a86d90510 again with the complete input identifier.

These calls occur even when the lower-bound comparison will immediately reject the record.

The decision sequence is then:

- If the reference is below the lower bound under unsigned 32-bit ordering, return zero immediately.
- Otherwise, evaluate the upper-bound comparison.
- If the reference is no larger than the upper bound, return one.
- Otherwise, advance to the next record.

The upper-bound expression uses the second-boundary conversion result, subtracts 60 times the latest correction, and subtracts 3,600. Unlike the lower-bound adjustment, the upper-bound subtraction of 3,600 is unconditional whenever this expression is evaluated. It does not depend on the auxiliary character.

The second-boundary dependency calls precede lower-bound rejection; evaluation of the upper-bound comparison follows that rejection check.

Each correction call is a separate observation. The initial correction, first-boundary correction, and second-boundary correction must not be substituted for one another without an additional stability guarantee.

### Comparison and arithmetic properties

Successful membership includes both endpoints:

- Reference equal to the lower bound can qualify.
- Reference equal to the upper bound can qualify.

Both comparisons use unsigned 32-bit ordering. A numerically larger lower bound than upper bound does not describe a wrapping interval. No reference can satisfy both comparisons for that record.

The reference and initial lower-bound expressions contain signed 32-bit intermediate arithmetic before their results are retained as unsigned values. Unrestricted overflow behavior for those intermediates is not established.

The additional lower-bound subtraction operates on an unsigned 32-bit value. The upper-bound expression’s final subtraction also has unsigned 32-bit arithmetic. Such unsigned subtraction wraps modulo 4,294,967,296. Signed intermediate overflow must not be assumed to have the same guaranteed behavior.

### Exhaustion

After a mismatch or an enabled match above the upper bound, the index increases by one. Once the index exceeds 204, the function returns zero.

Index 204 remains eligible for every matching-record outcome. Index 205 is not accessed. At most 205 record positions are examined.

## Acceptance examples

These are conditional consequences of the static representation, not executed tests. Unless an example states otherwise, assume accessible storage, sufficiently initialized outputs, stable relevant state, and no out-of-range signed intermediate arithmetic.

1. **No matching identifier.**  
   If all 205 identifiers differ from the input, return zero after examining index 204. Initialization still occurs. No status field is read and no boundary-generation call occurs.

2. **Input exceeds the record identifier range.**  
   For input 65,536, every unsigned 16-bit identifier fails the comparison. The initialization correction call still receives 65,536, and the scan reaches all 205 positions before returning zero.

3. **Zero-status match blocks later success.**  
   If index 3 matches with low status bits zero, return zero at index 3. A qualifying record at index 4 is not examined.

4. **Status uses the narrowed value.**  
   A matching status field of 0x0100 returns zero. A status field of 0x0001 proceeds to boundary generation. Both outcomes require the represented 16-bit status read.

5. **Inclusive endpoints.**  
   With derived lower bound 100 and upper bound 200, a reference of 100 returns one. A reference of 200 also returns one.

6. **Lower-bound rejection blocks later success.**  
   An enabled match with reference 99 and lower bound 100 returns zero immediately, regardless of a qualifying later record. Its second-boundary conversion and correction calls have already occurred.

7. **Above-upper-bound continuation.**  
   An enabled match with reference 201, lower bound 100, and upper bound 200 permits the scan to continue. A later record may return one, return zero, or allow further traversal.

8. **Reversed bounds are not wrapping membership.**  
   With lower bound 200 and upper bound 100, reference 150 returns zero at the lower-bound check. Reference 250 passes that check but exceeds the upper bound, so traversal continues.

9. **Auxiliary character value two.**  
   If the relevant character remains two, its reference contribution subtracts 120. Its later positive test subtracts 3,600 from the lower bound, not 7,200. The upper-bound expression subtracts 3,600 independently.

10. **Distinct correction results.**  
    Corrections of two, three, and four for initialization, first boundary, and second boundary contribute subtractions of 120, 180, and 240 respectively. Reusing the initial correction would change the behavior.

11. **Final position.**  
    A qualifying match at index 204 returns one. A mismatch there, or an enabled match above its upper bound, leads to zero without accessing index 205.

12. **Unsigned upper-bound underflow.**  
    If the value entering the final unsigned upper-bound subtraction is 100, subtracting 3,600 produces 4,294,963,796. Provided the lower-bound check passes, comparison uses that large unsigned value, not negative 3,500.

## Uncertainties

- **Signed intermediate overflow.** The representation includes signed 32-bit multiplication and addition. Its treatment of out-of-range intermediates is not independently established.
- **Byte order.** Numerical narrowing selects the low eight bits of the status field; their physical byte location is not established here.
- **Dependency outputs and failures.** Output completeness, result ranges, error conventions, pointer retention, ownership behavior, and external mutations are unknown.
- **Domain meaning.** Time, timezone, daylight-saving, scheduling, and calendar interpretations are not established contracts.

- **Address arithmetic outside valid storage.** The represented 32-bit addresses, field offsets, and record spacing do not establish a portable contract for overflow or inaccessible resulting addresses.

These unknowns do not alter the established branch precedence: zero status and lower-bound rejection terminate the search; exceeding the upper bound permits continuation.
