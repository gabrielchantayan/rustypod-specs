# F-6215ca9e3428

## Purpose

F-6215ca9e3428 performs ordered dispatch for an object and an event-like record. It may first invoke a notification dependency, then conditionally invoke a preliminary virtual handler, then invoke exactly one of two main virtual handlers. If dispatch has not returned a nonzero result, it may invoke a final virtual handler.

A nonzero result from a result-bearing handler terminates processing and is returned unchanged. Zero allows processing to continue. If no invoked result-bearing handler returns nonzero, the function returns zero.

“Object,” “event,” “notification,” and “handler” describe inferred roles, not established application-level meanings. The established behavior is conditional memory access and indirect invocation. In particular, the function rereads event fields after callbacks; it does not dispatch entirely from an entry-time snapshot.

## Interface

### Inputs

The function accepts two arguments:

- **Object reference:** a reference to storage containing a dispatch-table reference and additional fields.
- **Event reference:** an address of storage containing a discriminator and an associated value or payload reference.

Neither argument is checked for nullness, validity, alignment, or sufficient accessible extent.

The following byte offsets are observable:

| Storage | Offset | Use |
|---|---:|---|
| Object | `0x00` | Dispatch-table reference, loaded when an indirect handler is needed |
| Object | `0x50` | Comparison value used only by the final conditional stage |
| Object | `0x11C` | Integer field converted to a character-width argument for F-c3a316e4c3b2 |
| Event | `0x04` | Discriminator, read independently at successive stages |
| Event | `0x08` | Payload reference when the discriminator is `0x16`; comparison value when it is `0x0F` |
| Payload | `0x04` | Subtype or operation value, reached through the event’s payload reference |

The object field at `0x11C` is accessed as an integer before conversion. It is not established as a one-byte memory read.

The dispatch table contains callable entries at these byte offsets:

| Table offset | Role in this contract | Arguments |
|---:|---|---|
| `0x124` | Preliminary handler | Object reference, event reference |
| `0x10C` | Special main handler | Object reference, event reference |
| `0x110` | General main handler | Object reference, event reference |
| `0x0E0` | Final handler | Object reference, event reference |

These offsets identify dispatch locations, not stable function identities. The functions occupying them are unknown.

### Widths and representation

The supplied representation uses integer accesses and a four-byte integer stride. The layout is consistent with 32-bit integer fields and 32-bit address-bearing words. This contract therefore describes the visible fields and handler results as 32-bit words under that representation.

The target ABI is not separately supplied. Pointer width, byte order, alignment requirements, and exact character signedness remain **documented_only** uncertainties. The byte offsets above are explicit; the ABI interpretation is not independently verified.

The notification argument undergoes an integer-to-character conversion. On an eight-bit-character target, its retained bit pattern is the low eight bits of the integer field. Whether a high-bit-set pattern is interpreted as negative depends on the target’s character signedness and calling convention.

### Output

The result is an integer:

- The first nonzero result produced by a result-bearing handler that is actually invoked, returned without normalization.
- Otherwise, zero.

The return does not identify which handler produced it. Negative nonzero results terminate processing just as positive nonzero results do.

The notification dependency’s result, if it has one, does not control this function’s return or subsequent dispatch.

## Behavior

### 1. Optional notification

The function first reads the event discriminator at offset `0x04`.

If it is not `0x16`, this stage does not access the payload.

If it is `0x16`, the function reads the payload reference at event offset `0x08`, then reads the payload value at payload offset `0x04`. It subtracts `0x2500` from that value and tests whether the result equals `2`.

When that test succeeds:

1. The object’s integer field at offset `0x11C` is read.
2. That integer is converted to character width.
3. F-c3a316e4c3b2 is invoked with the object reference and the converted value.

For the ordinary 32-bit interpretation, payload value `0x2502` satisfies this test. It is a single-value test, not a range test.

No value from this invocation is used to stop dispatch. Subsequent stages execute unless the dependency does not return normally.

The subtraction’s overflow behavior is not independently established. The accepted value `0x2502` itself requires no overflow; behavior for values that would overflow signed subtraction must not be specified by assuming an unavailable source-language overflow model.

### 2. Optional preliminary dispatch

The event discriminator is read again, including when the notification ran.

If this new value is `0x16`, the payload reference and payload value are read again. If the payload value is zero, the function:

1. Reads the object’s dispatch-table reference.
2. Obtains the callable entry at table offset `0x124`.
3. Invokes it with the original object and event references.

A nonzero result is returned immediately. A zero result allows main dispatch.

If the discriminator is not `0x16`, or the payload value is nonzero, this handler is not invoked.

Notification-side changes can therefore affect preliminary dispatch. For example, the notification may change the payload value from `0x2502` to zero, causing the preliminary handler to run. No preservation of event contents or object state is assumed.

### 3. Mandatory main dispatch on the continuing path

If processing has not already returned, the event discriminator is read again.

- If it is `0x16`, the payload reference and payload value are read again.
- If that payload value is `0x2A`, the special main handler at dispatch-table offset `0x10C` is selected.
- Otherwise, the general main handler at offset `0x110` is selected.

The object’s dispatch-table reference is loaded to obtain the selected entry. The selected handler receives the original object and event references.

Exactly one main handler is invoked on every execution that reaches this stage and proceeds normally through the required accesses. The two main handlers are alternatives, not a fallback chain.

A nonzero main-handler result is returned immediately. A zero result allows the final conditional stage.

If a preliminary handler ran and returned zero, any changes it made to the discriminator, payload reference, payload value, or dispatch-table reference can affect this stage. Earlier field values are not reused as a permanent dispatch snapshot.

### 4. Optional final dispatch

After a zero main-handler result, the event discriminator is read again.

If it is not `0x0F`, the function returns zero without performing the final comparison or invoking the final handler.

If it is `0x0F`:

1. The value at event offset `0x08` is read.
2. The object value at offset `0x50` is read.
3. The two values are compared for equality.

This comparison treats the event field as a value. It does not dereference that value as a payload reference.

If the values differ, the function returns zero.

If they are equal, the function loads the object’s current dispatch-table reference and invokes the entry at offset `0x0E0`, passing the original object and event references. A nonzero result is returned unchanged. A zero result leads to a zero return.

The main handler can create or remove eligibility for this stage by changing the event discriminator, the event comparison value, or the object comparison field.

### Ordering guarantees and limits

The stage order is:

1. Optional notification.
2. Optional preliminary handler.
3. One main handler, unless an earlier result terminated processing.
4. Optional final handler, only after a zero main result.

There is no loop, retry, broadcast, or second main-handler attempt.

Each later discriminator read occurs after the preceding callback has returned. Dispatch-table references are loaded for the applicable invocation rather than captured once at entry.

These are sequential access observations, not a thread-safety guarantee. Concurrent mutation, synchronization requirements, and hardware memory-ordering effects are not established.

## Side effects

The function contains no explicit assignment to object, event, payload, or dispatch-table storage. Its direct memory operations are reads.

Observable effects may nevertheless include:

- Invocation of F-c3a316e4c3b2.
- Invocation of up to three result-bearing handlers.
- Mutations, resource operations, external effects, or abnormal termination performed by those dependencies.
- Different later dispatch decisions caused by dependency mutations.
- Access faults caused by invalid references or dispatch entries.

At most four dependency invocations occur: one notification, one preliminary handler, one main handler, and one final handler. That count does not include any nested work performed by dependencies.

No allocation, release, ownership transfer, reference-count operation, or cleanup is explicit in this function. This does **not** establish that dependencies preserve memory ownership or global state.

For normal completion, every storage location subsequently accessed must remain valid when accessed. If a dependency invalidates the object, event, payload, or dispatch table, the function provides no protective check before its later reads or calls.

No rollback occurs when a handler returns nonzero. Earlier effects remain outside this function’s control.

## Acceptance examples

These examples are conditional specifications, not executed tests. They assume valid memory, callable dispatch entries, normal callback return, and the stated mutations or lack of mutation.

1. **Ordinary general dispatch.**  
   The discriminator remains different from `0x16` and `0x0F`. The general main handler runs. If it returns zero, the function returns zero. Neither payload dereference nor final comparison is required.

2. **Notification argument conversion.**  
   The initial discriminator is `0x16`, the payload value is `0x2502`, and the object notification field is `0x1234`. On an eight-bit-character target, F-c3a316e4c3b2 receives character value `0x34`. If it leaves relevant state unchanged, preliminary dispatch is skipped and general main dispatch follows.

3. **Notification changes the next stage.**  
   The initial payload value is `0x2502`. F-c3a316e4c3b2 changes that value to zero while preserving discriminator `0x16`. The preliminary handler runs because its condition uses a fresh read.

4. **Preliminary handler terminates processing.**  
   The preliminary-stage discriminator is `0x16` and payload value is zero. The handler at `0x124` returns `-7`. The function returns `-7`; no main or final handler runs.

5. **Preliminary handler changes main selection.**  
   The preliminary handler runs, changes the payload value to `0x2A`, and returns zero. If the discriminator remains `0x16`, the special main handler runs.

6. **Special main dispatch is exclusive.**  
   At main selection, the discriminator is `0x16` and payload value is `0x2A`. Only the handler at `0x10C` runs at that stage. If it returns zero, the handler at `0x110` is not attempted.

7. **Main result prevents final dispatch.**  
   The main handler returns `5`, even if the event would otherwise qualify for the final handler. The function returns `5` without the final-stage reads.

8. **Main mutation enables final dispatch.**  
   The main handler sets the discriminator to `0x0F`, makes the event comparison value equal to the object value at `0x50`, and returns zero. The final handler runs using the dispatch table read after that mutation.

9. **Final comparison mismatch.**  
   After a zero main result, the discriminator is `0x0F`, but the compared values differ. The final handler is skipped and the function returns zero.

10. **Final handler result propagation.**  
    The final condition matches and its handler returns a nonzero integer. That exact result is returned. A zero final result instead produces zero.
