# F-88503fb8bb83

## Purpose

F-88503fb8bb83 conditionally updates accounting fields associated with an encoded reference, then passes a reference-associated header address to a dependency.

On an ordinary active path, it performs four amount subtractions using one captured header-derived amount, two count decrements, and one amount subtraction using a fresh header read.

“Allocation accounting followed by header processing” is inferred intent. The supplied body does not establish deallocation, ownership transfer, storage reuse, or invalidation of the caller’s reference.

Processing requires a nonzero context enable byte, a nonzero encoded reference, and a nonzero decoded base address. A failed header check invokes a dependency marked as non-returning.

All behavior below is based on static evidence. No runtime execution or tests have been performed.

## Interface

### Inputs and result

The function receives:

- **Context address:** the base address used for control and accounting accesses.
- **Encoded reference:** an unsigned 32-bit value used to locate a displacement and calculate a decoded base address.

There is no explicit return value or returned error indication.

The represented memory model uses 32-bit addresses and accounting words, unsigned 16-bit metadata indices, and an 8-bit enable field. Address calculations and accounting results are described at that width, rather than as unbounded mathematical arithmetic.

### Reference-associated layout

After the enable and nonzero-reference gates pass:

- A 32-bit displacement is read at the original encoded reference minus 4.
- Bit 31 of the encoded reference is cleared.
- The displacement is subtracted from that masked reference using 32-bit address arithmetic.

The result is the **decoded base**.

For a nonzero decoded base, the associated locations are:

| Address | Width | Observed use |
|---|---:|---|
| Decoded base minus 8 | 32 bits | Header |
| Decoded base minus 4 | Unsigned 16 bits | First index |
| Decoded base minus 2 | Unsigned 16 bits | Second index |

The displacement read uses the original reference, including bit 31. Clearing that bit affects only the decoded-base calculation.

Storage must support each access actually reached:

- The context enable byte must be readable even when the reference is zero.
- A disabled context does not require readable reference-associated storage.
- An enabled context with a nonzero reference requires a readable displacement.
- A nonzero decoded base requires readable header storage.
- Continued execution after validation requires the metadata reads and selected 32-bit accounting reads and writes.

There are no explicit pointer-validity, alignment, index-bound, counter-balance, or address-overflow checks.

Dependencies can potentially change storage or its lifetime. Earlier successful accesses do not establish that later accesses remain valid. Fault handling and alignment requirements are documented_only.

## Behavior

### Gates and reference decoding

The enable byte is read first.

If it is zero, the function returns without reference-associated reads, accounting writes, or dependency calls.

If the enable byte is nonzero but the encoded reference is zero, the function returns without further memory access or dependency calls. A zero reference therefore does not eliminate the requirement to read the enable byte.

Otherwise, the displacement is read and the decoded base is calculated. If the decoded base is zero, the function returns. This path has performed the displacement read but does not access a header, update accounting, or call a dependency.

A zero decoded base is a no-op condition, not a header-validation failure.

### Header validation

For a nonzero decoded base, validation uses the header address at decoded base minus 8.

The visible checks are ordered:

1. Read the 32-bit header and test whether it is zero.
2. If that check passes, read the header again and test bit 0.

A zero first read or a set bit 0 in the second read invokes F-a817d8d58c10. That dependency is marked as non-returning. No ordinary recovery path or returned error is shown.

With stable memory, accepted headers are exactly the nonzero values with bit 0 clear. Other bits are not validated.

The two reads are not an atomic snapshot. A nonzero first read followed by a zero second read passes: the second check tests only bit 0.

### Entry dependency

After successful validation, the function calls F-c0fc6d033caa with the interior context address at offset `0x7C`. Its return value is ignored.

This call precedes both metadata-index reads and all direct accounting writes. No header revalidation follows it.

The dependency’s implementation is unavailable. Later reads may observe changes it makes to the header, metadata, counters, or other storage. Preservation of relevant memory and its lifetime is not established.

### Captured amount and first four updates

After the entry dependency returns, the function reads the first unsigned 16-bit index and determines the first selected amount-counter address. It then reads the header and captures its value masked by `0x3FFFFFFC`.

The **captured amount**:

- Retains header bits 2 through 29.
- Clears bits 0, 1, 30, and 31.
- Is a multiple of four between zero and `0x3FFFFFFC`, inclusive.

A successfully validated header can produce a zero amount. The captured header value can differ from either validation read because capture occurs after the entry dependency.

The following updates occur in order:

1. Subtract the captured amount from the selected counter at `0x2A0 + 4 × first index`.
2. Subtract the captured amount from the aggregate counter at `0x388`.
3. Read the second unsigned 16-bit index.
4. Subtract the captured amount from the selected counter at `0x15C + 4 × second index`.
5. Subtract the captured amount from the aggregate counter at `0x29C`.

All four subtractions use the same captured amount. Changes to the header during those updates do not change that captured value.

The second index is read after the first two accounting writes. If either destination overlaps its metadata storage, the second-index read can observe this function’s own writes. A header overlap can likewise change the header before subsequent operations.

Each metadata index lies between zero and 65,535. Scaling an index by four produces at most `0x3FFFC`, so this multiplication alone fits in 32 bits. Address additions remain 32-bit calculations without visible bounds or overflow validation.

### Count selection and decrements

After the four amount updates, F-09dcb55e8e0a is called without explicit arguments.

Its 32-bit integer result selects the count-counter address:

**context + `0x38C` + four times the selector result**

The function then decrements that selected 32-bit counter by one, followed by the 32-bit counter at context offset `0x40C`.

No check requires the selector result to be nonnegative or within an indexed region. Unlike the metadata indices, it is not restricted to an unsigned 16-bit range. Scaling and address calculation have no visible overflow check.

The selector dependency runs after the four amount updates and before either count decrement. Its effects on memory are unknown. Count-counter writes can themselves modify header or metadata storage if their destinations overlap those locations.

### Additional amount update

After both count decrements, the function updates the counter at context offset `0x84`, subtracting a freshly read header value masked by `0x3FFFFFFC`.

This is not reuse of the captured amount. The final subtraction can differ from the earlier four if the header has changed through dependency effects, this function’s accounting stores through aliasing, or external activity.

The update occurs after both count decrements. Within this update, the supplied expression does not establish the relative order of reading the counter’s old value and reading the header.

### Final dependencies and return

After the additional amount update, the function calls:

1. F-cc6c9b4a0f68 with the interior context address and header address.
2. F-e586bff64fb7 with the interior context address, if the preceding call returns normally.

Their return values are ignored. If both return normally, this function returns without a value.

No visible control-flow mechanism guarantees execution of either final dependency after a prior fault or nonreturning transfer of control.

## Side effects

### Direct writes and arithmetic

An ordinary active execution reaching the end performs seven direct 32-bit accounting updates:

- Four amount subtractions using the captured amount.
- Two decrements by one.
- One amount subtraction using a fresh masked header read.

A zero subtraction amount does not introduce a skip; the corresponding read-and-write update remains present.

No store explicitly targets the header or metadata through their reference-derived addresses. This does **not** establish that those locations remain unchanged: accounting stores can modify the same bytes through aliasing. Dependencies may also modify them.

No saturation, balance check, or checked-arithmetic error path is visible. At the represented 32-bit word level, subtraction retains the low 32 bits. Subtracting `0x40` from `0x10` produces `0xFFFFFFD0`; decrementing zero produces `0xFFFFFFFF`.

Atomic updates, memory barriers, and a complete synchronization protocol are not established.

### Aliasing and ordered observations

Conceptually named fields need not occupy separate storage. Selected counters can coincide with aggregate counters, other selected counters, the header, or either metadata field. Partial overlap is not excluded by the supplied layout evidence.

Later reads use the storage state available when those reads occur. In particular:

- A first selected-counter write can change the value subsequently read for the first aggregate update.
- Either of the first two amount writes can change the subsequently read second index.
- Any preceding accounting write that overlaps the header can affect the final masked-header read.
- Header changes after capture do not change the amount already captured for the first four subtractions.

The function does not combine duplicate destinations or suppress repeated updates.

No explicit rollback appears in the body. However, dependencies may overwrite or restore affected storage, and the surrounding environment determines fault consequences. The lasting persistence or external observability of earlier writes after later faults or dependency execution is not established.

### Ownership and lifetime

Passing the header address to F-cc6c9b4a0f68 does not establish ownership transfer, deallocation, retention, or recycling.

There is no explicit operation that clears or replaces the caller’s encoded-reference value. The validity of repeated invocation, continued usability of the reference, and survival of associated storage are documented_only.

No dependency is assumed to preserve globals, context fields, header storage, metadata, or memory lifetimes.

## Acceptance examples

These are conditional static expectations, not executed tests. Unless stated otherwise, assume valid stable storage, no relevant aliasing, valid selected addresses, and normally returning dependencies that do not modify relevant memory.

### Disabled context or zero reference

An enable byte of zero causes return after that byte is read, regardless of the encoded reference. No displacement read or dependency call occurs.

With a nonzero enable byte and zero reference, the enable read still occurs, but no reference-derived access follows.

### Zero decoded base

For reference `0x2000` and displacement `0x2000` stored at `0x1FFC`, the decoded base is zero.

The displacement is read, but no header access, accounting update, or dependency call follows.

### High-bit reference

For reference `0x80002000`, the displacement is read at `0x80001FFC`, not `0x1FFC`.

If that displacement is `0x1000`, the decoded base is `0x1000`, and the header address is `0x0FF8`.

### Validation outcomes

A stable zero header invokes F-a817d8d58c10 after the first header read.

A stable header of `0x41` passes the zero check but invokes that dependency after the bit-0 check.

Neither reaches accounting under the non-returning annotation.

If the first header read is nonzero and the second is zero, validation passes. Later behavior depends on subsequent reads and dependency effects.

### Ordinary accounting

For header `0x42`, first index 2, second index 3, and selector result 1, the captured amount is `0x40`.

The four amount subtractions target context offsets `0x2A8`, `0x388`, `0x168`, and `0x29C`, in that order. Count decrements target `0x390` and `0x40C`. The final subtraction at `0x84` uses `0x40`, followed by the two final dependencies.

### Accepted zero amount

A stable header of `0x2` passes validation and produces amount zero.

All five amount-update operations remain present, both count decrements occur, and the dependency sequence is unchanged.

### Header mutation by a dependency

If the captured amount is `0x40` and F-09dcb55e8e0a changes the header so its masked value becomes `0x80`, the first four amount updates use `0x40`, while the final update uses `0x80`, provided storage remains valid.

### Header mutation by an accounting store

Suppose the header address equals context offset `0x388`, its initial value is `0x42`, the first index is 2, the second index is 3, and the selector result is 1. Assume no other relevant overlap.

The captured amount is `0x40`. The first selected update subtracts `0x40` at `0x2A8`. The first aggregate update then writes `0x2` to `0x388`, thereby modifying the header itself.

The remaining two captured-amount updates still subtract `0x40`. The final header-derived subtraction at `0x84` subtracts zero because the freshly read header is now `0x2`.

This behavior requires no dependency-side mutation.

### Repeated update of one destination

With first index 58, the first selected counter is at `0x388`, the first aggregate counter’s address.

For captured amount `0x40` and initial counter `0x100`, the first write stores `0xC0`; the next update reads that result and stores `0x80`.

### Dependency restoration

After the direct updates, F-cc6c9b4a0f68 could restore affected fields and transfer control without returning. Its unknown implementation does not exclude this.

The direct updates precede that call, but persistence of their values and execution of the final dependency are not guaranteed.
