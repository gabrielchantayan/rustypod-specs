# F-44dac8405e04

## Purpose

F-44dac8405e04 changes a 32-bit object field, applies direction-dependent boundary handling, and invokes dependencies using the resulting state. A feature gate controls additional shared-state preparation, conditional initialization, and either notification dispatch or activation-related processing.

The established contract concerns memory accesses, arithmetic, branches, dependency arguments, and call order. “Selection,” “initialization,” “notification,” and “activation” are descriptive interpretations, not established application semantics.

## Interface

### Inputs and result

| Input | Established representation |
|---|---|
| Object address | A 32-bit address representation. For nonzero adjustment, the object must provide a readable and writable 32-bit field at byte offset `0xb0`. |
| Adjustment | A signed 32-bit value. Zero returns immediately; otherwise its sign selects boundary recovery behavior. |

No return value is exposed.

The zero-adjustment path does not dereference the object or invoke a dependency. A valid object address is therefore unnecessary for that path.

For other paths, memory must remain valid through each actual access. This includes addresses obtained from shared storage or dependency results, not just the input object.

### Referenced storage

All offsets below are byte offsets. Names identify observed roles rather than application types.

| Storage | Observed layout |
|---|---|
| Input object | `+0xb0`: 32-bit selection field. |
| Feature record | `+0x69`: one-byte gate, tested for zero. |
| Control object | `+0x02`: one-byte initialization marker; `+0x14`: 32-bit guard word, also passed by address. |
| Root or linked node | `+0x1c`: 32-bit initialization field; `+0x3c`, `+0x3d`, `+0x3e`: separate byte fields; `+0x40`: 32-bit next-node address; `+0x44`: 32-bit auxiliary field; `+0x48`: 32-bit attachment value. |
| Mode storage | Indirectly addressed storage whose bits 0 and 1 are tested in separate expressions. |
| Notification block | A requested allocation of `0x18` bytes, with 32-bit fields written at `+0x10` and `+0x14`. |

Shared storage supplies the control-object address, root address, mode-storage address, two preparation arguments, and an initialization value.

Three root roles must remain distinct:

- **Initialization root:** captured after F-bb58811af262; used for conditional initialization and the later `+0x3e` write.
- **Activation root:** captured from shared root storage after that byte write.
- **Attachment-source root:** obtained by a separate, subsequent read of shared root storage, solely to read `+0x48`.

These addresses are not guaranteed equal. In particular, the attachment read is not through the captured activation root.

Byte order, public calling convention, alignment guarantees, and the full access width of mode storage are not established.

## Behavior

### 1. Immediate exit

Adjustment zero causes an immediate return. No body-level memory access or dependency call precedes this return.

All remaining behavior requires a nonzero adjustment.

### 2. Field adjustment and boundary recovery

The function reads the object’s 32-bit field at `+0xb0`, adds the adjustment, and writes the result back.

It then calls F-d1f5b0df9add. After that call, it reads the field again and compares the dependency result with the field as unsigned 32-bit quantities. Thus, a dependency-side change to the field can affect the comparison.

Recovery occurs when the dependency result is less than or equal to the freshly read field:

- For a positive adjustment, the function writes zero to the field.
- For a negative adjustment, it calls F-d1f5b0df9add again and writes the second result minus one.

There is no further boundary check. The second dependency result need not equal the first.

This is not established as modulo reduction by a collection size. A positive overshoot resets to zero rather than preserving a remainder. Negative recovery uses the second boundary result minus one, regardless of the magnitude of the adjustment.

The addition is represented as signed 32-bit arithmetic, as is the subtraction used for negative recovery. Behavior outside the representable signed range is `documented_only`; this contract does not infer wrapping or saturation. The unsigned comparison itself is established.

### 3. Selection-related dependencies and feature gate

After boundary handling, the function calls, in order:

1. F-97846fa3693f with the input object address.
2. F-201cc1dba22a with no explicit arguments.
3. F-9eca458298f2 with the preceding result and a fresh read of the object’s `+0xb0` field.
4. F-6ac70711bbb5 with `1`.

The field passed to F-9eca458298f2 is not necessarily the value last written by this function: the preceding dependencies may modify accessible state.

After F-6ac70711bbb5 returns, the function captures the shared control-object address. It then reads byte `+0x69` of the returned feature record.

If that byte is zero, the function returns. The selection adjustment and all four calls above have already occurred. The control address has been captured, but the disabled-feature path does not dereference it.

### 4. Guard-dependent preparation

With the feature enabled, the function tests bit 0 of the 32-bit guard word at `+0x14` of the control object obtained from shared storage at that evaluation.

If the bit is set, preparation is skipped. Otherwise, F-b255b26284e6 is called with guard-storage address `+0x14`, obtained using another read of the shared control address.

A zero result skips preparation. A nonzero result causes these calls, in order:

1. F-f99b15cea102 with the shared root address read for that call.
2. F-804adc29bbfb with the preceding result and two shared argument values, in their supplied argument positions.
3. F-d08d3ca17b81 with `+0x14` of the control object captured before the feature-byte test.

The guard test, acquisition argument, and concluding argument are not one permanently bound control-object reference. The concluding call specifically uses the earlier captured control object. Equality requires stability of the relevant shared address.

The names and pattern do not establish locking, exclusion, or any memory-preservation guarantee.

### 5. Conditional root initialization

The function calls F-bb58811af262 and retains its result. It then captures the shared root address as the initialization root.

It tests byte `+0x02` of the previously captured control object.

A nonzero marker skips the initialization block without normalizing the marker. A zero marker causes the following ordered actions:

1. Call F-a6b82b58e9b2.
2. Call F-a9f18648147b with that result, zero, and the initialization root.
3. Read the shared initialization value and write it to the initialization root’s 32-bit field at `+0x1c`.
4. Call F-2b20f2572237 with the initialization root and `1`.
5. Traverse from the initialization root, clearing byte `+0x3c` of every visited node.
6. Write `1` to byte `+0x02` of the captured control object.

For each traversal step, the byte write occurs before the 32-bit next address at `+0x40` is read. A null next address or a next address equal to the starting root ends traversal.

The root is visited unconditionally; a null starting root is not recognized as an empty chain. A self-link visits the root once. A cycle excluding the starting root has no explicit termination condition.

The marker is written only after traversal completes. No rollback is visible if an earlier operation fails or does not return.

### 6. Mode sampling

After optional initialization, the function reads mode storage and retains its bit-0 value. It separately reads mode storage again to test bit 1.

These are separate reads, not a guaranteed atomic snapshot. The retained bit-0 value controls the later byte value or notification decision, even if the second read observes different mode contents. Stability of the mode-storage address is likewise not guaranteed.

### 7. Bit 1 clear: return or notification dispatch

If the second mode read has bit 1 clear:

- Retained bit 0 clear: return.
- Retained bit 0 set: perform notification dispatch, then return.

The dispatch sequence is:

1. Call F-d33f6d597e5d requesting `0x18` bytes.
2. Call X-01 with the returned address and `0x18`.
3. Write 32-bit value `500` at block offset `+0x10`.
4. Write 32-bit value `2` at block offset `+0x14`.
5. Invoke indirect dependency X-02 with arguments `2`, block address, `5`, and `0`.

The allocation result is not checked for null. The function does not explicitly release the block. X-01’s effect on the block and X-02’s retention or ownership behavior are unknown.

This branch does not enter activation processing.

### 8. Bit 1 set: activation processing

If the second mode read has bit 1 set, the function first writes byte `+0x3e` of the initialization root:

- `0` when retained bit 0 is clear.
- `2` when retained bit 0 is set.

It then performs two distinct reads of shared root storage:

1. Capture the first address as the activation root.
2. Read the shared root address again and read the 32-bit attachment value at `+0x48` of that second address.

The attachment-source root may differ from the activation root. No dependency call occurs between these two shared-address reads, but the representation still contains separate reads; this contract does not merge them or assume shared-address stability.

Next, the function calls X-03 with the retained F-bb58811af262 result, then calls X-04 with no explicit arguments.

If X-04 returns zero, the function returns. Conditional initialization, the `+0x3e` write, and the attachment read have already occurred.

For a nonzero X-04 result, processing continues:

1. Call F-e7094617a462 with that result and the captured activation root.
2. Call F-c1c76d9cc652 with the same result.
3. Read byte `+0x3e` of the activation root. If bit 1 is set, call F-e282dcfd746e with `500` and `2`.
4. If the captured attachment value is nonzero:
   - Call F-66c822b72d41 with the X-04 result and that attachment value.
   - Read the 32-bit auxiliary value at `+0x44` of the activation root.
   - Call X-03 again, now with no explicit arguments.
   - Call X-05 with this later X-03 result, `1`, the captured attachment value, and the captured auxiliary value.
5. Traverse from the activation root, writing `1` to byte `+0x3d` of every visited node.

This final traversal uses the same write-before-next-read ordering and null-or-return-to-start termination rule as initialization traversal.

The later `+0x3e` test is a fresh read after two dependencies. It does not reuse the mode sample or necessarily inspect the root previously written. Similarly, `+0x44` comes from the activation root, not necessarily the attachment-source root, and is read after F-66c822b72d41.

## Side effects

Direct writes, conditional on reaching their paths, are:

- Object `+0xb0`: adjusted 32-bit field and possible recovery overwrite.
- Initialization root `+0x1c`: shared initialization value.
- Initialization chain `+0x3c`: zero bytes.
- Captured control object `+0x02`: marker value `1`.
- Notification block `+0x10` and `+0x14`: 32-bit values `500` and `2`.
- Initialization root `+0x3e`: byte value `0` or `2`.
- Activation chain `+0x3d`: byte value `1`.

Dependencies may introduce other effects, including changes to shared addresses or memory lifetime. Nothing here establishes their preservation behavior.

No explicit deallocation, rollback, error status, or invalid-address recovery is visible. X-04 returning zero is a branch condition, not an exposed error result. Successful completion requires each dependency to return normally and each accessed address to remain valid at its actual use.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Except where a case explicitly varies state, assume valid memory, normal dependency returns, stable relevant state, terminating chains, and representable arithmetic.

1. **Zero adjustment:** An invalid object address does not prevent the immediate return because the function does not dereference it.

2. **In-range adjustment:** Selection `2`, adjustment `1`, and comparison result `5` leave the field at `3` before selection-related calls, provided the comparison dependency does not change it.

3. **Positive boundary:** Selection `4`, adjustment `1`, and comparison result `5` produce writes of `5`, then `0`. Only one boundary call occurs.

4. **Negative boundary changes:** Selection `0` and adjustment `-1` produce the signed value `-1`, compared as unsigned `4,294,967,295`. A first boundary result `5` triggers recovery. A second result `8` causes a write of `7`.

5. **Comparison observes mutation:** If F-d1f5b0df9add returns `5` but changes the adjusted field to `6`, recovery follows the fresh field value, not the earlier addition result.

6. **Feature disabled:** A zero feature byte permits all preceding selection work but prevents guard processing, initialization, mode processing, and dispatch.

7. **Marker and traversal:** A nonzero marker skips initialization. With a zero marker and a root-to-second-node-to-null chain, both `+0x3c` bytes are cleared before the marker becomes `1`. A root self-link clears the root once.

8. **Separate mode samples:** If the first read has bit 0 set and the second has bit 1 clear, notification dispatch occurs even if bit 0 is clear in the second read.

9. **Notification:** The notification branch requests 24 bytes, calls X-01, writes `500` and `2` at the specified offsets, then invokes X-02. It does not perform activation calls.

10. **Distinct root reads:** Suppose the initialization root is A, the first later shared-root read yields B, and the separate attachment-source read yields C. The function writes A’s `+0x3e`, captures the attachment from C’s `+0x48`, and uses B for activation calls, the later `+0x3e` test, optional `+0x44` read, and final traversal. A, B, and C need not be equal.

11. **Unavailable activation:** A zero X-04 result leaves earlier writes intact but prevents subsequent activation dependencies and `+0x3d` traversal.

12. **Fresh activation byte:** Clearing bit 1 of the activation root’s `+0x3e` during an intervening dependency prevents F-e282dcfd746e, even when retained mode bit 0 was set.

13. **Captured attachment and later auxiliary read:** Changing the attachment-source field after capture does not replace the stored attachment argument. F-66c822b72d41 can affect the subsequent auxiliary read, which remains at activation-root `+0x44`.

## Uncertainties

The following are `documented_only`:

- Signed overflow behavior in adjustment or recovery subtraction, and out-of-range address arithmetic.
- Meaning, validity, and stability of boundary results.
- Dependency effects beyond their visible interfaces, including global mutation, ownership, retention, release, and failure behavior.
- X-01’s initialization effects and X-02’s ownership treatment.
- Exact signatures and ABI details of unmapped dependencies.
- Atomicity, synchronization, and external mutation rules for shared storage.
- Full mode-storage access width.
- Fault behavior for null, invalid, misaligned, or released memory.
- Guaranteed termination for chains containing a cycle excluding their starting root.
- Behavior absent from the supplied recovered representation.

Distinct shared-address reads are established; conditions under which they can observe different values are not. Assuming stability is sufficient to equate their results, but stability is not supplied by this body.
