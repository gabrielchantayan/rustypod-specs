# F-0a29566d2e48

## Purpose

F-0a29566d2e48 transforms three signed input components using a fourth signed input, context-provided scales and offsets, and opaque arithmetic dependencies. It writes four 32-bit results into the input/output record.

The established behavior is a bounded-component calculation with two arithmetic paths selected by the high bits of the fourth input. The first two component results receive context offsets. The third receives a different context offset and is then subjected to an ordered, signed limiting operation.

**Inferred intent:** the arrangement resembles fixed-point projection or normalization, with the fourth input acting as a depth or denominator. This interpretation does not establish the arithmetic performed by any dependency. In particular, neither factor-producing dependency is proven here to compute a reciprocal.

## Behavior

### Arithmetic conventions

The following descriptions distinguish numerical operations from bit extraction:

- **Signed right shift:** the supplied representation uses sign-propagating right shifts for signed values.
- **Middle-product extraction:** form an exact signed 64-bit product of two signed 32-bit values, then retain product bits 16 through 47 as a 32-bit word. This is not an unbounded quotient and does not saturate.
- **Left-shifted factor:** shift the factor’s 32-bit pattern left by the stated amount, retaining the 32-bit destination pattern under the represented machine-word interpretation.

For a negative product, middle-product extraction corresponds to a sign-propagating shift by 16 followed by retention of the low 32 bits. It need not equal division rounded toward zero.

The representation contains potentially overflowing signed additions, negation, and left shifts. Exact language-level overflow semantics are not independently established; cases requiring those semantics are identified under **Uncertainties**.

### 1. Capture the limit and prepare the components

The external signed limit is read before the record inputs.

The selector at record offset `0x1C` is then read. Its negation supplies a provisional lower bound.

Each input component is processed in this order:

1. First component at `0x10`.
2. Second component at `0x14`.
3. Third component at `0x18`.

For each component, a value below the negated selector is first raised to that lower bound. The resulting value is then lowered to the selector if it exceeds the selector. All comparisons are signed.

For a nonnegative selector, this is an ordinary inclusive clamp between the selector’s negation and the selector.

For a negative selector whose negation is representable, the bounds are reversed. The ordered comparisons then produce the selector itself for every component. The function does not reject that input or reorder the bounds.

All three prepared component values are established before any dependency call. Subsequent dependency changes to the original component fields do not cause those components to be reread by this routine.

### 2. Select the arithmetic path

The selector is shifted right by 24 with sign propagation.

The small-magnitude path is used when that result is either zero or negative one. For signed 32-bit selectors, this is the inclusive range:

**−16,777,216 through 16,777,215.**

All other selector values use the large-magnitude path.

Thus the positive and negative transition points are asymmetric by one: positive 16,777,216 uses the large path, while negative 16,777,216 still uses the small path.

### 3. Small-magnitude path

If the selector is zero, the factor is set to zero without calling a factor-producing dependency.

Otherwise, F-829ee7540d02 is called. The supplied representation shows no explicit arguments for this call. Its 32-bit result becomes the factor. No contract relating that result to the selector can be established here.

The function then performs these actions in order:

1. Store the factor shifted left by 12 at record offset `0x28`.
2. Form the middle-product extraction of the factor and prepared first component.
3. Read context field `0x140` and call F-e713aa9f4f3b with the extracted word and that field.
4. After the call, read context offset `0x134`, add it to the dependency result, and store the sum at record offset `0x20`.
5. Form the corresponding middle-product extraction for the prepared second component.
6. Read context field `0x144` and call F-e713aa9f4f3b.
7. After the call, read context offset `0x138`, add it to the result, and store the sum at record offset `0x24`.
8. Form the middle-product extraction of the factor and prepared third component.
9. Read the third scale word from context offset `0x8DC`.
10. Use those last two words as the arguments to the final F-e713aa9f4f3b call.

A zero selector therefore establishes a zero factor and zero product-derived first arguments. It does **not** establish zero transformed results: the dependency’s behavior for zero inputs is unknown, and context offsets still apply.

### 4. Large-magnitude path

F-dc13818ac82a is called with the selector shifted right by 8 using sign propagation. Its 32-bit result becomes the factor.

The function then performs these actions in order:

1. Store the factor shifted left by 4 at record offset `0x28`.
2. Shift the prepared first component right by 8, form its signed product with the factor, and extract product bits 16 through 47.
3. Read context field `0x140` and call F-e713aa9f4f3b with that extraction and the context field.
4. After the call, read context offset `0x134`, add it to the result, and store the sum at record offset `0x20`.
5. Repeat the corresponding component calculation for the prepared second component, using context scale `0x144`, then read offset `0x138` after the call and write record offset `0x24`.
6. Read context scale `0x8DC` as a signed 32-bit value, multiply it by the factor, and extract product bits 16 through 47.
7. Shift the prepared third component right by 8.
8. Call F-e713aa9f4f3b with the shifted third component as its first argument and the extracted factor/scale product as its second argument.

The third-component arrangement differs materially between paths. In the small path, the factor is combined with the component before the dependency call. In the large path, it is combined with the context scale instead. These arrangements must not be treated as interchangeable without an independent contract for F-e713aa9f4f3b.

### 5. Offset and limit the third result

After the final F-e713aa9f4f3b call:

1. Read context offset `0x8D8`.
2. Add it to the dependency result.
3. Interpret the resulting 32-bit value as signed for the limiting comparisons.
4. If it is negative, replace it with zero.
5. Otherwise, if it exceeds the entry-time signed limit, replace it with that limit.
6. Store the result at record offset `0x2C`.

This is an ordered conditional operation, not necessarily a clamp to a valid interval.

If the limit is nonnegative, the operation bounds the pre-limit value between zero and the limit. If the limit is negative:

- A negative pre-limit value produces zero.
- A nonnegative pre-limit value produces the negative limit.

The limit is not reread after dependency calls.

## Side effects

The routine explicitly writes four 32-bit record fields in this order:

1. `0x28`: shifted factor.
2. `0x20`: first transformed result.
3. `0x24`: second transformed result.
4. `0x2C`: limited third result.

It does not explicitly modify the four input fields.

The writes are not transactional. A dependency that fails to return can leave earlier outputs updated and later outputs unchanged. No rollback or error-result path is shown.

Dependency calls occur between these writes. Consequently:

- Arithmetic dependencies can observe earlier output writes if they can access the relevant storage.
- Context scale and offset fields are not captured as one entry-time snapshot.
- The first and second offsets are read after their corresponding arithmetic calls.
- The third scale is read after the second output has been written.
- The third offset is read after the final arithmetic call.

If context and record storage overlap, earlier writes can affect later context reads. The routine contains no explicit protection against this.

Dependencies may have additional side effects. Their absence cannot be inferred from this routine.
