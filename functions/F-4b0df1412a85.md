# F-4b0df1412a85

## Purpose

F-4b0df1412a85 creates or reuses a cached request, refreshes per-constraint eligibility, invokes an indirect callback, validates its usage outputs, and returns two 32-bit result words packed into a 64-bit value.

The validation rejects positive usage for a constraint whose eligibility byte is zero. Validation failure takes precedence over callback-status handling.

**Inferred intent:** The request appears to describe constraints and optional ordering preferences for a strategy-selection callback. These semantic labels do not establish a complete external ABI.

**Status: documented_only.** This contract describes static evidence. No runtime tests have been performed. External dependency behavior, global values, ownership rules, and permitted callback mutations remain partially unknown.

## Behavior

### 1. Initial snapshots

The function first reads the cache slot. It then captures the metadata address from descriptor offset 12, before allocation or any other dependency call.

Both addresses are retained locally:

- Later changes to the cache slot do not redirect the current invocation to a different request.
- Later changes to descriptor offset 12 do not redirect callback lookup or invalid-usage reporting.
- Metadata contents are not snapshotted: callback lookup and reporting read through the retained metadata address later.

A zero initial cache address selects creation. A nonzero address selects reuse.

### 2. Creation: counting and ordering acceptance

Constraint counting and descriptor population are separate passes, with allocation between them.

For counting, the record-array address is loaded once. The loop rereads the collection’s signed count while traversing records in ascending index order. A record qualifies when:

1. Its signed 16-bit field at offset 6, sign-extended to 32 bits, equals descriptor offset 24.
2. Its 16-bit flags have neither bit selected by `0x0081` set.

The comparison word is reread during selection. Flags are needed only for matching records. A nonpositive record count causes no counting iterations.

Ordering acceptance initially yields zero entries. If input 7 is present, its signed count is captured and entries are checked in order. Each must have discriminator `0x95` and an associated-object comparison word equal to descriptor offset 24. The first failure stops acceptance.

The captured ordering count is accepted only if the scan index equals that count:

- A positive count is accepted only after every entry passes.
- Zero is accepted as zero without visiting entries.
- A negative count causes no iterations; the scan index remains zero and does not equal the negative count. The accepted ordering count therefore remains zero.

A negative ordering count does **not** contribute a negative term to allocation sizing.

### 3. Allocation and population

F-f053f140662a receives the context slot’s current word and the size computed from the counting-pass results.

If allocation returns zero:

1. F-2022b0f73f3b reports allocation failure.
2. The lower failure global is read.
3. The upper failure global is read.
4. Those words are packed and returned.

This path performs no direct cache-slot write and does not invoke the callback. Neither dependency is established to preserve the cache slot, input structures, or globals.

On allocation success, layout addresses are computed from the counted values. Direct writes occur in this order:

1. Publish the allocation address in the cache slot.
2. Store the ordering-descriptor address at request offset 12.
3. Store the usage/output address at offset 16.
4. Store the constraint-descriptor address at offset 4.
5. Store accepted ordering count at offset 8.
6. Store counted constraint count at offset 0.

The constraint population pass then reloads the record-array address and rereads the collection count, descriptor comparison word, and record fields. Qualifying records are visited in current collection order. For each, it writes the sign-extended identifier, original index, and low flag byte, in that order.

The populated count is not reconciled with the earlier counted value. An allocator that changes relevant input data can therefore cause fewer populated descriptors, more populated descriptors, or different contents than the allocated layout anticipates. Safe creation requires consistency across these passes; this function does not enforce it.

Ordering population uses the previously accepted count but rereads entry-array addresses, associated-object addresses, copied object words, and ordering-entry bytes after allocation. It does not repeat discriminator or comparison checks. Thus acceptance of the earlier data does not validate replacement data introduced by allocation-side effects.

### 4. Reuse and eligibility refresh

Reuse bypasses counting, ordering acceptance, allocation, and descriptor population. It does not refresh cached identifiers, flags, original indices, or ordering descriptors.

Before eligibility refresh, the function captures:

- The constraint-descriptor address from request offset 4.
- The usage/output address from request offset 16.

The latter address remains retained through the region operation, callback, and validation.

For each cached constraint, its saved original index selects a record from the current record-array address. The array address is read during each iteration. Eligibility is written as one exactly when both conditions hold:

- Record offset 28 intersected with input 6 is zero.
- Record offset 24 intersected with input 5 is zero.

The offset-28 test occurs first; a nonzero intersection makes eligibility zero without requiring the offset-24 test.

The request’s signed constraint count governs iteration. Compatibility of cached indices with the current collection is not checked.

### 5. Region operation, cleanup, and initialization

D-01 is called with the retained usage/output address and a 32-bit size formed by shifting the then-current constraint count left three bits. Its actual memory operation is unknown; guaranteed zeroing cannot be inferred.

Only after D-01 returns does the function read request offset 28. If nonzero, it reads offset 24 and passes that word to F-94cb53877c15. Consequently, D-01 can affect the cleanup decision or argument.

After the optional cleanup call returns, direct initialization proceeds:

1. Set request offset 24 to zero.
2. Set offset 20 to zero.
3. Set offset 28 to zero.
4. Set offset 32 to zero.
5. Read the upper initialization global and retain its word.
6. Read the lower initialization global and store it at offset 40.
7. Store the retained upper word at offset 44.
8. Capture the current ordering count from offset 8.

The upper-global read therefore precedes both the lower-global read and lower-result store. The upper-result store uses the saved upper word. Unknown aliasing can make this ordering observable.

The captured ordering count reflects any changes made by D-01 or F-94cb53877c15. If it is nonzero and input 8 is zero, offset 8 is set to zero. Ordering storage and its address are not directly cleared.

### 6. Callback and validation

Using the retained metadata address, the function reads the callback object and follows its method table. D-02 receives the callback-object address and retained request address. Its return is interpreted as a 32-bit status.

Validation then uses a mixture of retained and current state:

- Constraint count: read from the post-callback request.
- Constraint-descriptor address: read from the post-callback request.
- Usage/output address: the address retained before eligibility refresh, **not** a reload of request offset 16.

In ascending constraint order, rejection occurs when the current descriptor’s eligibility byte is zero and the corresponding retained-region entry’s first word, interpreted as signed 32-bit, is greater than zero. The usage word need not be read when eligibility is nonzero. The second usage word is not inspected.

On the first rejection:

1. The metadata word at offset 0 is obtained through the retained metadata address.
2. F-2022b0f73f3b reports invalid usage with that word.
3. The lower failure global is read.
4. The upper failure global is read.
5. Their packed value is returned.

Callback-status handling and direct ordering-count restoration are skipped. In particular, suppressed ordering is not restored by this function on rejection. The callback or reporting dependency may nevertheless have changed that field.

### 7. Status handling and ordinary completion

After successful validation:

- Status zero causes no status-specific call or write.
- Status 7 rereads the context slot and writes byte value 1 at offset 30 of the addressed object.
- Any other nonzero status calls F-d5aed6d90713, then passes its returned word to F-2022b0f73f3b for reporting.

A nonzero status alone does not select the failure globals.

After status handling, the function writes the saved ordering count back to request offset 8, then reads offset 40 followed by offset 44 and packs them.

These result words can reflect initialization, callback writes, intervening dependency effects, and aliasing with other writes. In particular, for nonzero statuses other than 7, both status-related dependencies execute before the result reads. Callback-written result words are not unconditionally preserved.

## Acceptance examples

These are conditional static examples, not executed tests. Unless stated otherwise, inputs remain stable, arithmetic is representable, addresses remain valid, and dependencies preserve fields not deliberately changed.

1. **Selection and signed comparison.** Matching records with flags `0x0000`, `0x0001`, `0x0080`, and `0x0100` retain original indices 0 and 3. The last copied flag byte is zero. A comparison field of −1 matches descriptor word `0xFFFFFFFF`, not `0x0000FFFF`.

2. **Ordering boundaries.** Two valid entries are accepted together. Failure of the second accepts neither. A signed ordering count of −2 performs no entry reads, accepts zero entries, and contributes zero ordering bytes to allocation sizing.

3. **Allocation layout.** Three counted constraints and two accepted ordering entries request 124 bytes: 48 header, 36 constraint, 16 ordering, and 24 usage/output bytes.

4. **Mutation between passes.** If allocation changes the source so that four records qualify after only three were counted, population attempts four descriptors while the header and region boundaries still reflect three. This is a consistency hazard, not an automatic recount or allocation retry.

5. **Eligibility.** Record words `0x04` at offset 24 and `0x10` at offset 28 with masks `0x02` and `0x08` yield eligibility one. Changing input 5 to `0x04` yields zero.

6. **Retained usage address.** If the pre-refresh usage address is A and the callback changes request offset 16 to B, validation still reads usage entries at A. It uses the callback-visible post-call constraint count and descriptor address.

7. **Suppression and precedence.** With saved ordering count 2 and input 8 zero, the callback initially sees zero. Valid usage leads to restoration of 2. Invalid usage skips that restoration and skips the status-7 write even if the callback returned 7.

8. **Signed usage boundary.** For eligibility zero, first usage words 0 and −1 do not reject; 1 rejects. Reporting occurs before failure globals are read, lower first and upper second.

9. **Conditional result packing.** If offsets 40 and 44 hold `0x11223344` and `0x55667788` when finally read, the result is `0x5566778811223344`. Callback writes establish those returned words only if intervening status actions, dependencies, restoration, and aliasing preserve them.

10. **Metadata retention and initialization order.** Changing descriptor offset 12 during allocation does not redirect this invocation’s metadata access. If writing lower initialization output aliases the upper initialization source, the upper output still uses the word saved before that write.
