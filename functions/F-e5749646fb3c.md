# F-e5749646fb3c

## Purpose

F-e5749646fb3c conditionally dispatches an indirect operation on an object selected by an integer-like input, then clears a corresponding table entry and decrements a state counter.

The established behavior is a sequence of table access, indirect dispatch, slot clearing, and counter adjustment. Describing this as “removal,” “release,” or “destruction” is inferred intent, not an established ownership contract: the indirect operation’s behavior is unavailable.

An important boundary property is that input zero is eligible when the signed table bound is positive. The initial comparison with a null pointer does not make zero an unconditional no-op.

## Interface

### Input

The function accepts one argument recovered as a pointer to an integer. Its observable use is instead as a signed integer selector:

- The argument is never dereferenced.
- Its value is interpreted through a signed integer conversion.
- Negative interpreted values are rejected.
- Nonnegative interpreted values are compared with a bound obtained from shared state.
- An accepted value selects a four-byte table entry.

For this contract, **selector** means the signed interpretation used by those comparisons and address calculations. The pointer-shaped declaration does not establish that callers must supply an address of readable integer storage.

The supplied representation uses four-byte integer fields and four-byte table entries. Its conversions between pointers and integers indicate a 32-bit address-oriented model. Exact original-language conversion rules and target ABI are not independently established.

### Output

There is no explicit return value.

Normal completion has one of three observable outcomes:

1. No eligible entry is accessed.
2. An eligible entry is read and found to be zero.
3. An eligible, nonzero entry triggers an indirect operation, followed by a slot clear and counter decrement.

The function has no explicit error result, diagnostic, or recovery path.

### State layout

A call to F-ecd921e533b1 supplies the state address used by this invocation. The relevant layout is:

| Location relative to state | Role established by use | Width |
|---|---|---|
| Byte offset `0x78` | Table-base field | Four bytes |
| Byte offset `0x7C` | Signed selector-bound field | Four bytes |
| Byte offset `0x80` | Counter updated after dispatch | Four bytes |

The table contains four-byte entries. A nonzero entry is treated as an object address.

At the object address, the first pointer-sized field is used as a dispatch-table address. The dispatch target is read at byte offset `0x40` from that dispatch-table address.

Field names above describe observable use, not verified application-level types or invariants. In particular, the bound is not established to equal the allocation length, and the counter is not established to equal the number of nonzero entries.

## Behavior

### State acquisition precedes input rejection

Every invocation first calls F-ecd921e533b1. This occurs even when the selector is negative or will otherwise be rejected.

Consequently, a rejected input does not imply that the invocation has no effects. Effects of F-ecd921e533b1 remain possible.

The resulting state address is retained for subsequent accesses. There is no second call to acquire state after indirect dispatch.

### Eligibility

For a negative selector:

- The bound field is not read by the visible selection logic.
- No table entry is read.
- No indirect object operation is invoked.
- Neither the slot clear nor the counter decrement occurs.

For a nonnegative selector, the function reads the bound at state offset `0x7C`. Eligibility requires both:

- The selector is not equal to the bound.
- The selector is less than or equal to the bound under a signed comparison.

Together, these conditions admit exactly nonnegative selectors strictly below the signed bound.

The practical boundary behavior is therefore:

- A positive bound permits selectors from zero through one less than the bound.
- A zero bound permits no selector.
- A negative signed bound permits no selector.
- A selector equal to the bound is rejected.

The bound is read for every nonnegative selector, including zero. The visible logic does not reject zero before consulting it.

### Entry lookup

For an eligible selector, the function reads the table base from state offset `0x78`, computes a displacement of four bytes times the selector, and reads the four-byte entry at that displacement.

If the entry is zero, the function returns without:

- Dispatching an object operation.
- Writing the table entry.
- Reading or updating the counter as part of this path.

A zero entry is therefore a silent no-op after state acquisition, bound validation, and table access.

### Indirect operation

For a nonzero entry, the function:

1. Reads the object’s first pointer-sized field.
2. Uses that value as a dispatch-table address.
3. Reads an indirect call target at dispatch-table byte offset `0x40`.
4. Calls that target.

No explicit arguments or return-value use are shown for this call. The evidence does not establish an implicit receiver, a particular calling convention, or any ownership-transfer semantics.

The function performs no visible validation of the object address, dispatch-table address, or call target before using them.

### Post-dispatch mutation

If the indirect operation returns normally, the function clears a table entry and decrements the counter, in that order.

The clear does **not** necessarily target the exact storage location read before dispatch. The function rereads the table-base field at state offset `0x78`, then uses the original selector to locate the entry to clear.

This has several consequences:

- If the indirect operation changes the table-base field, the clear uses the replacement base.
- If the indirect operation replaces the selected entry, the clear does not compare the replacement with the original object address.
- If the indirect operation changes the bound, that new bound is not checked before the clear.
- The state address used for these operations remains the one acquired at entry.

After storing four-byte zero into the selected entry, the function reads the four-byte counter at state offset `0x80`, subtracts one, and writes the result back.

The counter is therefore sampled after dispatch and after the slot clear. It is not a saved pre-dispatch value.

There is no visible protection against a zero or negative counter. There is also no visible consistency check connecting the counter, bound, and table contents.

### Arithmetic limits

The stride is four bytes, and the recovered address expression multiplies the signed selector by four before combining it with the table base.

Eligibility alone does not establish that this arithmetic is safe. A sufficiently large positive bound can admit a selector whose scaled displacement exceeds the signed 32-bit range. Nor does eligibility establish that the resulting address lies inside an allocated table.

Similarly, decrementing the counter at the minimum signed 32-bit value exceeds the representable signed range.

The supplied representation does not resolve whether these cases wrap at machine width or are governed by another execution or language model. Portable overflow behavior must not be inferred. For ordinary, nonoverflowing use, the required preconditions include representable address arithmetic, accessible selected storage, and a representable counter decrement.

## Side effects

### Visible reads

Subject to branch eligibility, the function performs these relevant accesses in order:

1. Calls F-ecd921e533b1.
2. Reads the bound for a nonnegative selector.
3. Reads the table base for an eligible selector.
4. Reads the selected table entry.
5. For a nonzero entry, reads the object’s dispatch-table address and the indirect target.
6. Calls the indirect target.
7. After normal return, rereads the table base.
8. Clears the selected entry.
9. Reads the counter and writes its decremented value.

The function does not cache the table base across the indirect call. It does retain the original selector and acquired state address.

### Visible writes

The function’s own explicit writes occur only after a nonzero entry’s indirect operation returns normally:

- A four-byte zero store to the selected entry under the then-current table base.
- A four-byte counter update equivalent to subtracting one, subject to the arithmetic uncertainty above.

Rejected selectors and zero entries do not trigger either explicit write.

### Ownership and lifetime

No direct allocation or deallocation operation is visible.

The indirect operation may affect object lifetime, but that is unknown. Clearing an entry does not by itself prove that the object was destroyed, freed, detached, or transferred.

Normal post-dispatch completion requires the retained state address and the subsequently read table base to remain usable. The visible function does not establish or enforce that lifetime guarantee.

### Reentrancy, concurrency, and failures

No locking, atomic read-modify-write, or reentrancy guard is visible.

Changes made during indirect dispatch can affect the subsequent clear and counter decrement. The outer invocation does not revalidate its selected entry after such changes.

If indirect dispatch does not return normally, the visible post-dispatch stores are not reached. There is no explicit cleanup mechanism shown.

A failure after the slot clear but before completion of the counter update can leave the two pieces of state only partially updated. No rollback is visible.

## Acceptance examples

These examples are conditional predictions from static evidence, not executed tests. Except where stated otherwise, assume valid memory, nonoverflowing arithmetic, a normally returning state accessor, and a normally returning indirect operation.

### Negative selector

Given selector `−1`, the function calls F-ecd921e533b1 and then returns without reading the bound or table.

Acceptance condition: neither explicit mutation occurs. Effects inside the accessor are outside that guarantee.

### Zero selector with a positive bound

Given selector `0`, bound `3`, and a nonzero entry at table index zero, the indirect operation is invoked for that entry.

After normal return, index zero under the reread table base is cleared, then the current counter is decremented.

Acceptance condition: zero is treated as an eligible selector, not rejected merely because its pointer-shaped representation is null.

### Empty range and upper boundary

Given bound `0` and selector `0`, the selector is rejected.

Given bound `3` and selector `3`, the selector is also rejected.

Acceptance condition: neither case reads a table entry or performs explicit mutation.

### Negative signed bound

Given a negative signed bound and any nonnegative selector, the selector is rejected after the bound read.

Acceptance condition: an unsigned interpretation must not turn that bound into a large eligible range.

### Eligible zero entry

Given bound `5`, selector `2`, and a zero entry at index two, the entry is read and the function returns.

Acceptance condition: no dispatch occurs and the counter remains untouched by this function.

### Table replacement during dispatch

Given an eligible nonzero entry, suppose the indirect operation changes the table-base field from one valid table to another.

Acceptance condition: the post-dispatch clear affects the original selector’s entry in the replacement table. The function does not use the original table base for that store.

### Counter replacement during dispatch

Given a counter initially equal to `8`, suppose the indirect operation changes it to `20`.

Acceptance condition: after clearing the selected entry, the function reads `20` and writes `19`, assuming no intervening modification.

### No normal return from dispatch

Given an eligible nonzero entry whose indirect operation does not return normally, the clear and decrement are not reached in the visible control flow.

Acceptance condition: this function provides no independent guarantee of either mutation or rollback.
