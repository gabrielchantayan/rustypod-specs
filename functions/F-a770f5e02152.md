# F-a770f5e02152

## Purpose

F-a770f5e02152 updates selection-related state in a caller-supplied object, deactivates an existing referenced item when present, and conditionally obtains and activates a replacement. A nonzero third argument additionally requests a sequence of downstream update operations.

“Selection,” “activation,” and “notification” describe inferred intent. The established behavior is a sequence of dependency calls, 32-bit field reads and writes, and branches. The supplied evidence does not establish the object’s type, the meaning of its referenced items, or the external effects of the dependencies.

The operation is not shown as transactional. Existing state is processed before replacement eligibility is tested, and no rollback or error-recovery path is visible.

## Interface

The function accepts three arguments:

1. **State-object address.** The first argument is represented as a 32-bit address-bearing value. It identifies storage accessed at the offsets below.
2. **Update input.** The second argument is an opaque 32-bit value forwarded to F-870c4fcf7295. No local interpretation or validation is shown.
3. **Additional-update flag.** The third argument is tested for equality to zero. Zero skips the final dependency sequence; every nonzero value requests it. There is no restriction to the value one.

## Behavior

### 1. Obtain and store the eligibility value

The function reads the four-byte field at `0xEC` and calls F-870c4fcf7295 with:

- The second function argument.
- The value read from `0xEC`.

After that call returns, the function stores a captured secondary result into `0xFC`.

The evidence associates this result with the machine’s secondary result register, rather than with an ordinary explicitly named return value. Its representation is four bytes. Its application-level meaning and the complete return convention of F-870c4fcf7295 are unknown.

This call occurs before the function reads `0xF8` to decide whether existing-item processing is needed. Consequently, any dependency-induced changes to the object may affect that decision.

### 2. Process an existing reference

The function reads `0xF8` and tests whether its 32-bit value is nonzero.

If it is zero, the function skips this entire phase. In particular, this phase does not write `0x100`.

If it is nonzero:

1. The function reads `0xF8` again and calls F-682adfd5a561 with that value and the constant `0x1100`.
2. It tests the dependency’s returned 32-bit value against zero.
3. If the result is zero, it reads `0xF8` again and calls F-acf5413f3abe with the field’s then-current value and a second argument of zero.
4. If the result is nonzero, it calls F-cad2dd93d855 with that returned value and a second argument of zero.
5. After the selected call returns, it reads `0xF8` again and writes that value to `0x100`.
6. It then writes zero to `0xF8`.

The repeated reads are significant. The value copied into `0x100` is the value present after the selected downstream call returns, not necessarily the value that caused entry into this phase or the value supplied to F-682adfd5a561.

Likewise, in the zero-result branch, the value supplied to F-acf5413f3abe is read after F-682adfd5a561 returns. The function does not enforce that these reads produce identical values.

The final zero write occurs even if a dependency changed `0xF8` during this phase, provided the calls return normally.

### 3. Decide whether to obtain a replacement

After existing-item processing, the function reads `0xFC` and interprets the four-byte value as a signed 32-bit integer.

- If the value is negative, it skips replacement acquisition and activation.
- If the value is nonnegative, it performs the replacement phase.

The decision uses the field’s value at this point. It is not necessarily based on an unchanged copy of the result originally stored after F-870c4fcf7295: intervening dependencies are not established to preserve object memory.

The eligibility boundary is therefore:

- `0x00000000` through `0x7FFFFFFF`: eligible.
- `0x80000000` through `0xFFFFFFFF`: ineligible under the signed interpretation.

The magnitude of an eligible value is not otherwise used directly by this function.

### 4. Obtain and activate a replacement

For an eligible value:

1. The function calls F-9b5186ad9dac with the state-object address.
2. It writes that dependency’s four-byte return value to `0xF8`.
3. It calls F-682adfd5a561 with the returned value and `0x1100`.
4. It tests the latter dependency’s result against zero.
5. If the result is zero, it reads `0xF8` and calls F-acf5413f3abe with the then-current field value and a second argument of one.
6. If the result is nonzero, it calls F-cad2dd93d855 with that result and a second argument of one.

There is no check that F-9b5186ad9dac returns a nonzero value. A zero result is stored and passed to F-682adfd5a561 like any other result.

The value passed to F-682adfd5a561 is the result obtained from F-9b5186ad9dac. By contrast, the fallback call to F-acf5413f3abe uses a fresh field read after the lookup returns.

There is no further direct write to `0xF8` after the activation call. Its final value may therefore reflect changes made by that call or by subsequent dependencies.

### 5. Perform the optional additional-update sequence

Only after the preceding phases does the function examine the third argument.

If it is zero, the function returns without invoking this sequence.

If it is nonzero, the function performs these calls in order:

1. F-3b446a4ac5a2 receives the state-object address.
2. F-a66a9be680df is called without explicit arguments.
3. F-c5a232e4455b receives the preceding result and `0xC`.
4. F-afb630a7107c receives:
   - The result from F-c5a232e4455b.
   - A fresh read of the four-byte field at `0x104`.
   - An address referring to stack-local storage.
   - The constant four.
5. F-cad482b79b8f receives the result from F-afb630a7107c and a second argument of zero.

The function then returns.

This sequence is independent of whether replacement was eligible or whether an existing reference was present. The read at `0x104` occurs after the first three calls in this sequence, so those dependencies may influence the value supplied.

The evidence does not establish the contents, extent, or input/output role of the stack-local storage. The adjacent argument of four must not, without the dependency’s contract, be treated as proof of a four-byte buffer operation.

## Side effects

### Direct memory effects

On normal execution, the function always writes the captured secondary result to `0xFC`.

Additional direct writes are conditional:

- Existing-reference path: write the then-current `0xF8` value to `0x100`, then clear `0xF8`.
- Eligible-replacement path: write the result of F-9b5186ad9dac to `0xF8`.

The function does not directly clear `0x100` when no existing reference is present. It also does not directly overwrite `0x100` during replacement acquisition.

These are direct-write guarantees, not guarantees of final field contents. Dependencies may alter the same memory.

### Ownership and lifetime

The stack-local address is passed to F-afb630a7107c. The evidence does not show whether that dependency retains it. Safe use beyond the current call’s lifetime cannot be assumed.

### Errors and interruption

No retry, rollback, or explicit error report is visible. If a dependency fails to return normally, subsequent writes and calls are not guaranteed to occur. Earlier effects may already have happened.

## Acceptance examples

These examples are conditional contracts, not runtime observations. Unless stated otherwise, dependencies return normally and do not modify the object except through effects explicitly described.

### No existing reference, negative eligibility

Given `0xF8` is zero after the initial call and the stored eligibility value is `0xFFFFFFFF`:

- No existing-item deactivation occurs.
- No replacement is obtained.
- `0x100` receives no direct write.
- With a zero third argument, the optional sequence does not occur.

### Existing reference, no replacement

Given `0xF8` contains reference A and `0xFC` remains negative:

- The lookup receives A and `0x1100`.
- Exactly one deactivation route is selected according to whether the lookup result is zero.
- A is copied to `0x100`, then `0xF8` is cleared.
- No replacement call occurs.

### Zero eligibility permits replacement

Given `0xFC` is zero at the eligibility check:

- F-9b5186ad9dac is called.
- Its result is stored at `0xF8`.
- The activation lookup occurs even if that result is zero.

Thus zero eligibility is distinct from a negative value, and zero replacement is not locally rejected.

### Dependency mutation affects the saved reference

Suppose the existing-reference phase begins with A, but its selected deactivation dependency changes `0xF8` to B before returning:

- `0x100` receives B.
- The function then clears `0xF8`.

Saving A instead would not match the established read order.

### Lookup mutation affects the fallback argument

Suppose the replacement lookup returns zero and changes `0xF8` from the stored replacement to C:

- F-acf5413f3abe receives C and one.
- It does not necessarily receive the original replacement result.

### Nonzero optional flag

Given a third argument of negative one:

- The optional sequence runs after replacement processing or its omission.
- It uses a fresh read of `0x104`.
- Its execution is not restricted to a successful or nonzero replacement.
