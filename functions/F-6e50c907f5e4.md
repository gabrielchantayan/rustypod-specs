# F-6e50c907f5e4

## Purpose

F-6e50c907f5e4 rewires a set of linked records. Under a conventional binary-tree interpretation, it performs a right rotation around a supplied pivot: the pivot’s left child moves into the pivot’s former position, and the promoted record’s right subtree becomes the pivot’s left subtree.

That interpretation is inferred intent. The established behavior is a sequence of field reads, comparisons, and four-byte writes. The routine does not verify that the supplied records form a tree, that parent and child links agree, or that the pivot has a usable left child.

The routine returns no value. Its observable result is the modified memory graph.

## Interface

### Inputs

The routine accepts two machine-level values used as addresses:

- **Container address:** identifies an object with an address-bearing field at offset `0x10`.
- **Pivot address:** identifies a record with address-bearing fields at offsets `0x04`, `0x08`, and `0x0c`.

The supplied representation declares both arguments as `int`, then uses them to form addresses. It also represents the manipulated fields as integers or four-byte quantities. A 32-bit address model is the natural interpretation, but the source alone does not establish a portable host ABI or authorize execution with arbitrary native-width pointers.

This contract therefore describes the represented four-byte field operations. Address interpretation, address validity, byte order, alignment requirements, and arithmetic behavior outside the intended address range remain environmental prerequisites.

For the normal, non-overlapping case, define:

- **Promoted record:** the record initially referenced by the pivot’s field at `0x0c`.
- **Transferred record:** the record initially referenced by the promoted record’s field at `0x08`, if that value is nonzero.
- **Former parent:** the record initially referenced by the pivot’s field at `0x04`.
- **Root slot:** the four-byte field at offset `0x04` in the root holder reached through the container.

### Output and ownership

### Preconditions for the conventional rotation result

A caller seeking a well-formed tree rotation must provide, at minimum:

- A readable container field at `0x10` containing a valid root-holder address.
- A readable root slot and a writable root slot when the pivot is the recorded root.
- A valid pivot with readable and writable link fields as used below.
- A valid, nonzero promoted-record address with the required readable and writable fields.
- If the transferred-record address is nonzero, a writable parent-like field at its offset `0x04`.
- If the pivot is not the recorded root, a valid former-parent record with the required readable and writable child fields.
- A consistent, non-overlapping tree topology and no interfering mutation during the operation.

These are caller obligations, not checks performed by the routine.

## Behavior

### Established access and update sequence

The following phases preserve the order established by the supplied statements. Reads within a single expression are not assigned a stricter ordering than the representation supports.

1. **Obtain the promoted-record address.**  
   Read the pivot’s field at `0x0c`. Retain this address for later accesses to the promoted record. There is no check that it is nonzero.

2. **Replace the pivot’s left-like link.**  
   Read the promoted record’s field at `0x08` and write that four-byte value to the pivot’s field at `0x0c`.

3. **Conditionally repair the transferred record’s parent-like link.**  
   Read the promoted record’s field at `0x08` again and compare it with zero.

   - If zero, perform no transferred-record parent write.
   - If nonzero, read the promoted record’s field at `0x08` again to obtain the destination address, then write the pivot address to that record’s field at `0x04`.

   The value used for the zero test and the value used to locate the destination are separate reads. With ordinary stable, non-overlapping records they agree. The routine does not enforce that agreement.

4. **Give the promoted record the pivot’s current parent-like link.**  
   Read the pivot’s field at `0x04` and write its four-byte value to the promoted record’s field at `0x04`.

5. **Locate and inspect the root slot.**  
   Read the container’s field at `0x10`, form the address of the root-holder field at `0x04`, and retain that slot address. Read the slot and compare its value with the pivot address.

6. **Reconnect the former incoming link.**

   - **Root case:** If the root slot equals the pivot address, write the promoted-record address to that retained root slot.
   - **Non-root case:** Otherwise, read the pivot’s field at `0x04` again to obtain a parent-record address. Read that record’s field at `0x08`.
     - If it equals the pivot address, write the promoted-record address to that same parent record’s field at `0x08`.
     - Otherwise, write the promoted-record address to that parent record’s field at `0x0c`.

   The non-root case does not verify that the parent’s field at `0x0c` actually references the pivot. Failure of the right-link comparison is sufficient to select the left-link write.

7. **Attach the pivot beneath the promoted record.**  
   Write the pivot address to the promoted record’s field at `0x08`.

8. **Set the pivot’s new parent-like link.**  
   Write the promoted-record address to the pivot’s field at `0x04`.

The routine then returns.

### Result for a stable, well-formed tree

Assuming valid, distinct records and no interfering mutation:

- The pivot’s left-like link becomes the promoted record’s former right-like link.
- A nonzero transferred record receives the pivot as its parent-like link.
- The promoted record receives the pivot’s former parent-like link.
- The incoming reference formerly identifying the pivot is redirected to the promoted record:
  - the root slot when the pivot was the recorded root;
  - otherwise the former parent’s right-like link if that link identified the pivot;
  - otherwise the former parent’s left-like link.
- The promoted record’s right-like link becomes the pivot.
- The pivot’s parent-like link becomes the promoted record.

No key comparison or payload inspection occurs. Preservation of search-tree ordering depends on the caller’s original structure and interpretation; it is not checked here.

### Repeated reads and aliasing

The retained promoted-record address is taken from the pivot’s left-like link before that link is overwritten. Later accesses to the promoted record continue to use that retained address.

Other values are not retained in the same way:

- The promoted record’s right-like link is read once for the pivot update, again for the zero test, and conditionally again for the transferred-record destination.
- The pivot’s parent-like link is read before updating the promoted record’s parent-like link, then read again if the non-root branch is taken.
- The root-slot address is retained after reading the container field; the container field is not reread to locate the root-case write.

Consequently, a description using only initial field values is valid for the normal stable, non-overlapping case, not for all possible address arrangements.

If objects or fields overlap, an earlier write can change a later read. The routine contains no alias detection. The ordered accesses above remain the available static description; a well-formed rotation result is not promised for overlapping records.

## Side effects

### Writes

With distinct fields, the routine performs five unconditional four-byte writes:

1. Pivot left-like link.
2. Promoted-record parent-like link.
3. Selected incoming link: root slot or former-parent child field.
4. Promoted-record right-like link.
5. Pivot parent-like link.

It performs one additional four-byte write when the promoted record’s right-like link is nonzero at the conditional test: the transferred record’s parent-like link.

Thus a normal invocation performs five or six field writes. These are write operations, not necessarily five or six distinct addresses in an aliased layout.

Fields outside these destinations are not explicitly written. In particular, with distinct records, the pivot’s right-like link, the promoted record’s left-like link, and unrelated payload fields are unchanged.

### Intermediate state

The transformation is not atomic as a whole. Earlier links are changed before later links are repaired. For example, the pivot’s left-like link changes before the incoming root or parent link is redirected, and the incoming link changes before the final two writes attach the pivot beneath the promoted record.

No locking, transaction boundary, rollback, or synchronization operation is visible. Concurrent readers can therefore not be promised a coherent tree throughout the call.

### Invalid accesses and errors

There is no explicit error path, validation result, or recovery mechanism.

- A zero promoted-record address is not treated as an empty-child case; subsequent accesses still use it as an address base.
- A zero transferred-record value is explicitly supported and skips its parent-link write.
- A zero former-parent value is not dereferenced in the ordinary root branch, but is used as an address base if the non-root branch selects it.
- An invalid root holder is not bypassed merely because the caller considers the pivot to be a root.

If an access fails, earlier writes may already have occurred. The supplied representation does not establish the platform’s fault behavior or any resulting recovery guarantees.

## Acceptance examples

These are conditional contract examples, not runtime observations. Unless stated otherwise, all referenced records are distinct, accessible, stable, and use the layout above.

### Root rotation with a transferred record

Given:

- The root slot identifies the pivot.
- The pivot’s left-like link identifies the promoted record.
- The pivot’s parent-like link contains a sentinel value.
- The promoted record’s right-like link identifies a transferred record.

On return:

- The root slot identifies the promoted record.
- The promoted record’s parent-like link contains the original sentinel value.
- The promoted record’s right-like link identifies the pivot.
- The pivot’s parent-like link identifies the promoted record.
- The pivot’s left-like link identifies the transferred record.
- The transferred record’s parent-like link identifies the pivot.

The sentinel need not be dereferenced on this root path. This does not establish a general sentinel convention.

### Non-root pivot referenced through a right-like link

Given a root slot not equal to the pivot, and a former parent whose right-like link equals the pivot:

- The former parent’s right-like link becomes the promoted record.
- Its left-like link remains unchanged.
- The promoted record’s parent-like link becomes the former parent.
- The remaining links change as described by the rotation.

### Non-root pivot referenced through a left-like link

Given a root slot not equal to the pivot, a former parent whose right-like link does not equal the pivot, and whose left-like link does equal the pivot:

- The former parent’s left-like link becomes the promoted record.
- Its right-like link remains unchanged.

This branch is selected by the failed right-link comparison, not by a successful left-link comparison.

### No transferred record

Given a zero promoted-record right-like link:

- The pivot’s left-like link becomes zero.
- No transferred-record parent field is accessed for writing.
- The promoted record’s right-like link subsequently becomes the pivot.

### Inconsistent parent linkage

Given a non-root pivot whose recorded parent has neither child field equal to the pivot:

- The routine still replaces that parent’s left-like link with the promoted-record address.
- It does not report the inconsistency.
- Any prior left-like link value is overwritten.

A consumer requiring topology validation must provide it outside this routine.

### Missing promoted record

Given a zero pivot left-like link, no successful no-op or rejection behavior is established. The routine proceeds to access the promoted record’s right-like field using that zero-derived base. Normal rotation acceptance does not apply.
