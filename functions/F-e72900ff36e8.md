# F-e72900ff36e8

## Purpose

F-e72900ff36e8 conditionally removes a node from a pointer-linked binary tree, performs color-based repair, invokes a removal-related dependency, decrements a 32-bit container field, and writes a 32-bit result to caller-provided storage.

The supplied representation supports interpreting the structure as a red-black tree with a header containing root and endpoint links. That interpretation is inferred intent, not proof that every represented path preserves red-black invariants.

The established contract is narrower:

- An initial dependency decides whether structural removal is bypassed.
- The bypass path returns a freshly read header pointer.
- The removal path selects and unlinks a node, possibly relocating its successor.
- Repair uses node color bytes, parent links, child links, and rotation-like dependencies.
- A final dependency receives the originally selected node and the literal value one.
- The container’s 32-bit field at offset 20 is then decremented.
- The output value on the removal path comes from a mutable local word passed to an earlier dependency.

No runtime tests have been performed.

## Interface

### Arguments and result

The interface has three arguments and no explicit return value:

| Argument | Required role |
|---|---|
| Output address | Writable storage for one 32-bit word |
| Container address | Address of an object with a header pointer at byte offset 16 and a 32-bit count-like field at byte offset 20 |
| Input-word address | Readable storage for one 32-bit word, normally interpreted as a node pointer |

The input word is read at least twice on the removal path. The first value is copied into temporary storage before the initial dependency call. The selected node is obtained by rereading the input word after the next dependency returns.

The implementation does not validate these addresses, their alignment, or their relationships.

### Represented widths and layouts

The supplied representation uses 32-bit pointer-bearing words and 32-bit integer fields.

A node exposes the following fields:

| Byte offset | Width | Observed use |
|---|---:|---|
| 0 | 8 bits | Color or repair-state byte |
| 4 | 32 bits | Parent pointer |
| 8 | 32 bits | Left-child pointer |
| 12 | 32 bits | Right-child pointer |

Zero child pointers represent absent children. The repair logic treats color zero and color one differently. Red and black are useful inferred names for zero and one, respectively.

Bytes 1 through 3 are not explicitly modified here. No payload layout beyond the first 16 bytes is established.

The object reached through container offset 16 acts as a header:

| Header byte offset | Width | Observed use |
|---|---:|---|
| 4 | 32 bits | Root pointer |
| 8 | 32 bits | Left endpoint pointer |
| 12 | 32 bits | Right endpoint pointer |

In the explicit single-node removal case, the root becomes zero and both endpoints become the header address. Other properties of the header, including its color byte, are not established.

### Preconditions

Defined completion requires every actually dereferenced address to be valid and every invoked dependency to return normally.

For ordinary tree-removal use, the caller must supply consistent parent, child, root, and endpoint relationships. The function does not establish membership before altering the selected node’s links, except for whatever the initial dependency may do.

There is no documented null-argument behavior, malformed-tree recovery, count-underflow rejection, or transactional rollback.

Aliasing is not prohibited by the visible implementation. However, aliases among the output, input word, container, and nodes can change behavior. In particular, the final output store can overwrite an earlier structural or count update if its destination aliases that storage.

## Behavior

### 1. Initial decision and result preparation

The function first:

1. Reads the 32-bit input word into a local result word.
2. Reads the container’s header pointer into a second local word.
3. Passes the addresses of both local words to F-356e3995b10d.

These are mutable local words, not immutable argument snapshots. Their post-call values depend on the dependency.

If F-356e3995b10d returns nonzero:

- The function rereads the header pointer from container offset 16.
- That reread value replaces the local result.
- The function writes the result to the output address and returns.

This path performs no explicit unlinking, final removal call, or count decrement. Effects produced inside F-356e3995b10d remain possible.

If the dependency returns zero:

- F-59fbf5893c3b receives the address of the local result word.
- After that call returns, the function rereads the input word and treats it as the node to remove.

Consequently, the node removed need not equal the input value captured before the first dependency call. The final removal-path output is the local result word as left by the dependencies, not a separately established successor value.

### 2. Selecting the physical removal position

The selected node’s left link is read first.

- **No left child, but a right child:** the right child becomes the replacement.
- **Left child, but no right child:** the left child becomes the replacement.
- **Both children:** traversal starts at the right child and repeatedly follows left links until reaching a node with no left child. This successor is relocated into the selected node’s position. Its right child is the initial replacement.
- **Neither child:** the selected node is detached directly, using its parent as the subsequent repair cursor.

For the two-child case, relocation changes links and color bytes. The visible function does not copy payload data between the selected node and successor.

### 3. Detaching a leaf

The parent pointer is read from the selected leaf.

If that parent equals the current header pointer, the function performs the following explicit writes, in order:

1. Header right endpoint becomes the parent/header address.
2. Header left endpoint becomes that address.
3. Header root becomes zero.

Otherwise, it determines whether the leaf equals its parent’s left child.

- If so, it clears the parent’s left link.
- Otherwise, it clears the parent’s right link.

These leaf-link clears are represented as four separate byte stores, rather than a single 32-bit store.

The function then checks the corresponding header endpoint:

- A left-child removal checks the left endpoint.
- A right-child removal checks the right endpoint.

If that endpoint equals the removed leaf, it is replaced with the parent pointer. The parent remains the repair cursor.

### 4. Replacing a node with its only child

For a selected node with exactly one child:

1. The child’s parent field receives the selected node’s parent.
2. The header root is checked.
3. If the selected node is the root, the root becomes the child.
4. Otherwise, the parent’s left link is checked; the matching left link, or otherwise the right link, becomes the child.

Endpoint maintenance follows root/parent relinking.

For the left endpoint:

- If it does not equal the selected node, it is unchanged.
- If it equals the selected node and the selected node has no right child, it becomes the selected node’s parent.
- Otherwise, F-91fe39e6f6dc is called with the replacement, and its 32-bit result is stored into the left endpoint of the header reread after the call.

For the right endpoint:

- If it does not equal the selected node, it is unchanged.
- If it equals the selected node and the selected node has no left child, it becomes the selected node’s parent.
- Otherwise, F-a4d0b2395344 is called with the replacement, and its result is stored into the right endpoint of the header reread after the call.

Interpreting these dependencies as minimum- and maximum-node searches is consistent with the layout, but their implementations are unavailable.

### 5. Relocating a successor

When both children exist, the successor is the leftmost node in the selected node’s right subtree.

The visible structural order is:

1. The selected node’s left child receives the successor as its parent.
2. The successor receives the selected node’s left-child link.
3. The successor is detached or adjusted within the right subtree.
4. The root or the selected node’s parent link is redirected to the successor.
5. The successor receives the selected node’s parent.
6. Their color bytes are exchanged.

Step 3 has two cases:

- **Immediate right-child successor:** a nonzero replacement child receives the successor as its parent. The successor’s existing right link remains in place.
- **Deeper successor:** a nonzero replacement child receives the successor’s former parent. That former parent’s left link becomes the replacement. The successor receives the selected node’s right link, and that right subtree’s parent becomes the successor.

If the successor’s initial replacement child is zero, the function substitutes the relocated successor itself as the repair cursor. This is an explicit behavior of the supplied representation; it must not be replaced in this contract by a conventional null-child repair model.

After relocation, the originally selected node remains the node passed to the final removal-related dependency. Its color byte now contains the successor’s former color.

### 6. Color-based repair

Repair is entered only when:

- The repair cursor differs from the header pointer read at this stage; and
- The byte at the removal node’s offset zero is nonzero.

For this entry condition, any nonzero color byte qualifies. Inside the repair loop, continuation specifically requires the cursor’s color to equal one.

If repair is entered, each iteration first stops when the cursor is the current root or its color is not one. Otherwise, the cursor’s parent and its position relative to the parent determine the sibling side.

#### Cursor on the left

The sibling is the parent’s right child.

- A zero-colored sibling is changed to one; the parent is changed to zero; F-c470755d11e4 is called with the container and parent. Parent and sibling links are then reloaded.
- If the sibling is absent, the cursor is changed to zero and repair moves to the parent.
- If both sibling children are absent or have color one, the sibling becomes zero and repair moves to the cursor’s parent.
- Otherwise, if the sibling’s right child is absent or has color one, the existing left child becomes one, the sibling becomes zero, and F-b951efde8a28 is invoked in the one-explicit-argument form represented in the supplied material. The sibling is reloaded afterward.
- If that reload produces no sibling, the loop exits to final cursor recoloring.
- Otherwise, the sibling receives the parent’s color, the parent becomes one, the sibling’s existing right child becomes one, and F-c470755d11e4 is called with the container and cursor’s current parent. Repair then exits.

#### Cursor not on the left

The sibling is the parent’s left child. The treatment is mirrored:

- A zero-colored sibling becomes one; the parent becomes zero; F-b951efde8a28 is called with the container and parent.
- An absent sibling causes the cursor to become zero and repair to move to the parent.
- Two absent-or-one-colored sibling children cause the sibling to become zero and repair to move upward.
- If preparation is needed because the sibling’s left child is absent or one-colored, the existing right child becomes one, the sibling becomes zero, and F-c470755d11e4 is invoked in its represented one-explicit-argument form.
- After a successful sibling reload, the sibling receives the parent’s color, the parent becomes one, the existing sibling left child becomes one, and F-b951efde8a28 is called with the container and cursor’s current parent.

Whenever repair was entered, the final repair cursor is written with color one before removal processing continues.

The apparent symmetry does not justify assuming that the dependencies are pure rotations or that their omitted arguments can be reconstructed.

### 7. Final removal, decrement, and output

After structural work and any repair:

1. F-1b2e0c144326 receives the container, the originally selected node, and the literal value one.
2. On normal return, the 32-bit field at container offset 20 is read and decremented by one.
3. The resulting 32-bit value is stored back.
4. The local result word is written to the output address.

The decrement uses the field value observed after the dependency returns. It does not use an entry snapshot.

There is no explicit zero guard. At the represented 32-bit word level, subtracting one from zero produces all one bits. Whether a higher-level signed-language overflow model applies is not established by the supplied material.

- Header root and endpoint links.
- Parent and child links of the selected node’s relatives.
- Successor links during relocation.
- Color bytes of the selected node, successor, repair cursor, parents, siblings, and sibling children.
- The container’s count-like field.
- The caller’s output word.

Calls may have additional effects. No dependency is assumed to preserve unrelated memory or global state.

The ordering described above is the represented access order, not a concurrency guarantee. No locking, atomic publication, or rollback mechanism is established.

## Acceptance examples

These are conditional static acceptance cases, not executed tests. Unless otherwise stated, they assume valid, nonaliasing storage, normally returning dependencies, and no dependency mutations beyond those explicitly stated.

### Initial bypass

If F-356e3995b10d returns nonzero, the output must equal the container’s header pointer reread after that call. No explicit count decrement or final removal call occurs, even if the initial local result was modified.

### Removal-path output transformation

If the initial dependency returns zero and F-59fbf5893c3b changes the local result to a particular 32-bit word, that word is eventually written to the output on normal completion. It is not replaced merely because a different node becomes the structural successor.

### Removing the sole node

If the selected node has no children and its parent is the header:

- Both endpoint fields become the header address.
- The root becomes zero.
- Repair is skipped because its cursor equals the header.
- F-1b2e0c144326 receives the selected node and one.
- A count of one becomes zero before the output store.

### Removing a zero-colored leaf

If a non-root leaf has color zero, its parent link is cleared and an applicable endpoint is moved to the parent. The color-based repair block is not entered, regardless of the parent’s color.

### Removing a root with one child

If the selected root has one child, that child receives the old root’s parent pointer and becomes the header root. If repair is entered, the cursor is already the root, so iterative repair stops and the child’s color is set to one.

### Two-child removal with a successor lacking a right child

The successor is relocated into the selected node’s position and their color bytes are exchanged. The successor becomes the repair cursor because its initial replacement was zero. The final removal dependency still receives the originally selected node.

### Count changed by the final dependency

If F-1b2e0c144326 leaves the count field equal to nine, the function stores eight, regardless of its value before that call.

### Aliased output

If the output address aliases the count field, the final result-word store overwrites the decrement’s stored value. A contract requiring both independent results must therefore require nonaliasing storage.
