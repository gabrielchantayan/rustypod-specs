# F-03695be47fb6

## Purpose

F-03695be47fb6 applies a fixed set of memory updates using addresses obtained from two dependencies. It writes an opaque global value through the first returned address, invokes the second dependency with a displaced address, and then uses the second result as the reference for selective copies and clears.

The direct updates comprise four 32-bit source-field copies, one 8-bit source-field copy, eight 32-bit clears, and one 8-bit clear. They do not initialize a complete contiguous region.

An initialization role is inferred from the combination of fixed-offset copies and zero writes. Allocation, object identity, field meanings, successful construction, and ownership transfer are not established.

This contract distinguishes the function’s direct effects from the unknown effects of its dependencies. In particular, values present at function entry are not necessarily the values later consumed.

## Behavior

### Dependency boundary and initial update

F-e9175b650588 is called first, with no explicit arguments shown. Its result supplies the initial address.

After that call returns, the function reads the opaque 32-bit global and writes the obtained value at the initial address. Consequently, the value consumed is the global’s value after the first dependency returns. There is no basis for assuming that dependency preserves the global’s entry-time value.

F-a891c2749310 is then called with an address 204 bytes, or 0xCC bytes, beyond the initial address. This displacement comes from 51 four-byte elements; it is not a 51-byte displacement.

The second result supplies the destination reference. It need not equal the argument, the initial address, or any fixed displacement from either. Both dependency calls complete before any of the five direct source-field reads.

### Selective update semantics

With valid, disjoint storage and no concurrent interference, the final destination contains the five source values according to the mapping in the interface, and zero in each listed clear field.

That final-state description is insufficient when regions overlap. The contract therefore also preserves the ordering constraints below.

The copies from source +0x68 and +0x6C occur first, in that order, before any destination clear. Each copy reads its source before writing its destination.

The four clears at destination +0xB8 through +0xC4 occur in increasing offset order. They follow the first two copies and precede the byte clear at −0x04. That byte clear precedes the four-byte clear at +0xCC.

The read of source +0x70 occurs after the +0xCC clear but before the +0xD0 clear. Its value is retained across the +0xD0 clear and then written to destination −0x08. Thus the retained value, not a reread of the source, determines that destination field.

The +0xD4 clear follows that retained-value copy. The source +0x74 copy follows the +0xD4 clear and precedes the source +0x78 byte copy. The +0xD8 clear occurs last, after the byte copy.

There are no further dependency calls in this direct update sequence. Completion follows the final clear.

These are ordering facts from the supplied static representation. They do not establish atomicity, synchronization, hardware memory-order guarantees, or safe observation by concurrent code.

### Overlap and read timing

The function does not take a complete snapshot of the source before modifying memory. Each field is read at its own point in the update sequence.

An earlier destination write can therefore change a later source read if the corresponding addresses overlap. Replacing the behavior with a bulk source snapshot could change the result, even if the same final field mapping were used.

The retained read from source +0x70 is particularly significant: it occurs before the +0xD0 clear, while its destination write occurs afterward. An overlapping +0xD0 clear cannot retroactively change the value already retained.

The initial global-value write may also affect later source reads if the initial address overlaps source storage. Likewise, the second dependency may observe or replace the initial write before the direct field updates begin.

These consequences are conditional on the overlapping accesses being valid in the execution environment. The evidence does not establish which overlapping object arrangements are permitted.

### Width and address arithmetic

Every wide copy and clear affects exactly four bytes. Every narrow copy and clear affects exactly one byte.

The byte clear at destination −0x04 does not directly clear bytes −0x03 through −0x01. The byte copy at +0xC8 does not directly write +0xC9 through +0xCB. Other gaps between listed fields likewise receive no direct write from this body.

There are no explicit bounds checks, address-overflow checks, saturation rules, or recovery branches. Invalid address calculations must not be assigned convenient wraparound behavior on the basis of this evidence. Their actual consequences remain **documented_only**.

Accordingly, “not directly written by this body” does not mean “unchanged since function entry.” Preservation claims for untouched destination bytes require a suitable observation boundary after the dependencies, together with valid non-overlap and no-interference assumptions.

These examples are conditional specifications, not executed tests.

### Narrow writes do not clear neighboring bytes

Suppose destination bytes +0xC8 through +0xCB initially contain, in address order, 0x10, 0x20, 0x30, and 0x40, and source +0x78 contains 0xA5.

After completion, those four destination bytes contain 0xA5, 0x20, 0x30, and 0x40.

Similarly, specified post-call contents at destination −0x03 through −0x01 remain unchanged under these assumptions. The clear at −0x04 is only one byte wide.

These are post-dependency preservation claims, not promises about entry-time contents.

### The consumed global value is post-call

Suppose F-e9175b650588 changes the opaque global to 0xCAFEBABE before returning.

The subsequent initial write stores 0xCAFEBABE. That is an observation about the write itself, not a guarantee about the initial location at function exit: the second dependency or later overlapping writes could replace it.

### A clear can determine a later overlapping copy

Override disjointness with a valid layout in which source +0x74 coincides with destination +0xB8.

The earlier +0xB8 clear makes the later source +0x74 read obtain zero, provided no intervening effect changes those bytes. Destination −0x0C consequently receives zero, regardless of the shared field’s earlier contents.

### A retained read survives a later overlapping clear

The shared location is subsequently cleared, but destination −0x08 receives the retained value 0x12345678.
