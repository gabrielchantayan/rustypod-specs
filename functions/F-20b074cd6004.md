# F-20b074cd6004

## Purpose

F-20b074cd6004 executes a repeating sequence of indirect calls, memory reads and writes, arithmetic, and a software breakpoint. The supplied representation contains an unconditional back edge and no normal return.

Reaching another iteration requires the intervening dependencies to return, memory operations to succeed, execution to continue after the breakpoint, and arithmetic to have an applicable execution interpretation. An unconditional loop does not establish uninterrupted or infinite execution.

No application-level purpose is established. Initialization, object construction, device control, and protocol processing would be unsupported interpretations.

## Interface

**Explicit interface:** No declared parameters and no returned value. Observable outputs consist of dependency invocations, memory writes, the breakpoint, and changes to implicit execution state.

**Implicit inputs:**

- An incoming continuation value that determines the first indirect-call target.
- Register-backed working-base state, consulted at several distinct points.
- A register-associated contribution used in the final byte-store address, with incoming provenance and no visible local assignment.
- Two global 32-bit values, read separately during each iteration.
- Memory at fixed and computed addresses.
- Dependency results, including primary values and secondary register-associated contributions.

**Widths and interpretation:**

- Bytes, halfwords, and words are respectively 8, 16, and 32 bits.
- Address-bearing integers and the represented addresses are 32 bits.
- **Three dependency results—D05, D09, and D28—are carried in 64-bit containers and separated into lower and upper 32-bit words.**
- Unsigned halfword reads are zero-extended when used as wider values.
- Byte and halfword stores modify only their respective widths.
- Explicit unsigned 32-bit shifts have unsigned semantics.
- Signed 32-bit expressions also occur. Universal wrapping is not established for signed overflow, negative signed left shifts, out-of-range signed conversions, or overflowing signed address calculations.

A separate machine-arithmetic interpretation could specify wrapping and bit-pattern conversions. This contract does not silently adopt that interpretation.

**Memory preconditions:** Every reached access requires a valid address for its width and operation. Alignment, byte order, mapping, concurrency rules, and fault handling are not established. No address, bounds, lifetime, or alignment validation is visible.

## Behavior

A retained value is reused after intervening calls without a visible reload. This does not mean the underlying memory remains unchanged.

4. D04 executes.
5. D05 supplies a 64-bit result, retained as lower and upper words.

## Acceptance examples

These are conditional consequences of static evidence, not runtime observations. Each requires all preceding operations to reach the relevant point successfully.

1. **Ordinary initial sum.** If D05 supplies lower word `7` and upper word `9`, D06 receives `7` and `16`. The known-zero contribution changes neither value.

2. **Initial signed overflow.** If D05 supplies lower word `0x7fffffff` and upper word `1`, the signed sum exceeds the signed 32-bit range. A wrapped argument is not required without an additional arithmetic interpretation.

3. **Unsigned shifts.** If D09’s lower word is `0x80000001`, the working-region write stores `32`, and the selected-destination write stores `4`. These operations do not have the later signed-shift uncertainty.

4. **Defined table write.** If the table base is `0x1200` and D19 returns `3`, the table halfword write targets `0x120c` and stores `0x1200`, provided breakpoint execution continues and the destination is writable.

5. **Signed index boundary.** D19 returning `0x1fffffff` produces displacement `0x7ffffffc`. Returning `0x20000000` does not establish displacement `0x80000000` under signed-expression rules.

6. **Retained field.** If the field read yields `0xabcd`, both record-field word stores write `0x0000abcd`, even if D30 changes the original halfword.

7. **Captured destination versus live base.** A change to the first global during D04 does not redirect the two initial byte writes. A change to the working base during D10 does affect the subsequent working-region read at offset `0x320`.

8. **Conditional next-iteration base.** Suppose execution resumes after the breakpoint and reaches the next iteration; every intervening dependency and breakpoint handler preserves the working base; and the explicit decrement and all other required arithmetic and accesses have defined, successful interpretations. Then the next iteration’s base is the preceding entry base minus `0xf4`. Dependencies preserving the base alone are insufficient: breakpoint handling must preserve it too. A modulo-32-bit result additionally requires a wrapping interpretation.

9. **Breakpoint stop.** If execution stops permanently at breakpoint `0x92`, none of the subsequent table or record writes occurs in that iteration. Earlier calls and writes remain observable.

10. **Equal target, different interface use.** D19 and D31 calculate the same target. D19 explicitly receives a word and supplies the index source; D31 has no explicit argument shown and supplies a secondary address contribution. Their common target does not erase those differences.
